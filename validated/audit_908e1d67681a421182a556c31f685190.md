### Title
Protocol fee bypass on Nep245/Imt `TokenDiff` transfers via unit-size (`|delta|==1`) splitting - (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` unconditionally returns `Pips::ZERO` whenever the absolute delta on a `Nep245`/`Imt` token is `1`, regardless of `protocol_fee`. Because the fee is computed independently per `TokenDiff` intent (not aggregated across a batch or across time), a signer (and a cooperating counterparty, which can be the attacker's own second account) can move an arbitrarily large total quantity of a high‑value NEP‑245/IMT token by splitting it into many `|delta|==1` `TokenDiff` intents, paying zero protocol fee on the entire moved volume instead of the fee that a single bulk `TokenDiff` of the same total amount would incur.

### Finding Description
The broken binding: `sum(fee_ceil(protocol_fee, |delta_i|) for each executed TokenDiff leg on token T)` should equal `fee_ceil(protocol_fee, total_volume_moved_of_T)` (approximately, for equal total volume), but is instead forced to `0` whenever every individual leg has `|delta_i| == 1`.

Root cause is in `TokenDiff::token_fee`: [1](#0-0) 

which is invoked per-intent inside `execute_intent`, where the fee is computed from the `amount` of that single intent's delta only: [2](#0-1) 

Global conservation of value across a batch is enforced only in `TransferMatcher::finalize` (via `contracts/defuse/core/src/engine/state/deltas.rs`), which requires deposits and withdrawals of each token to net to zero (`InvariantViolated::UnmatchedDeltas` otherwise): [3](#0-2) [4](#0-3) 

This matcher only checks that the *raw* signer-side deltas balance out; it has no notion of a "fee obligation" that must be honored — the fee-adjusted counterparty deltas are expected to be constructed off-chain using `TokenDiff::closure_delta`/`supply_delta`, which itself calls `token_fee` and therefore also yields a zero-fee closure for `|delta|==1` legs: [5](#0-4) 

Attacker's exact payload: sign a `MultiPayload` (or a sequence of them) containing many `TokenDiff` intents, each with `diff = { Nep245Token: -1 }` matched by a counterparty leg `diff = { Nep245Token: +1 }` (the counterparty can be the attacker's own second Defuse account holding the same balance in the ledger). Because each leg's `amount.unsigned_abs() == 1`, `token_fee` returns `Pips::ZERO` for every leg, so `fees_collected` stays empty for the whole chain even though the cumulative volume moved (`N` units) can be made arbitrarily large.

Existing guards do not prevent this: `MultiPayload::verify`, nonce/signature checks, and `TransferMatcher::finalize`'s zero-sum invariant all pass normally because the *value* conservation (sum of deltas = 0) is untouched — only the *fee* is skipped. There is no per-batch or per-token aggregate check on the sum of `|delta|` values used for fee purposes across multiple `TokenDiff` intents.

### Impact Explanation
The `fee_collector` account is under-collected relative to `protocol_fee * total_volume_moved` for any NEP‑245/IMT token that is used fungibly (i.e., where individual token_ids can hold large per-unit balances). This matches the "protocol fees bypassed" Critical impact category: the Verifier moves real, previously-deposited token value between accounts while consistently avoiding the fee it is configured to charge. The blast radius covers any NEP‑245 (`Nep245`) or `Imt` token id registered in the Verifier; it is fully repeatable across accounts, tokens, and batches, limited in practice only by gas per transaction (out-of-scope resource concerns), not by any economic or protocol-level cap.

### Likelihood Explanation
Preconditions: attacker needs a positive Verifier-ledger balance of a NEP‑245/IMT token (their own deposited tokens) and control of two accounts (or a willing/colluding counterparty) to provide the matching `+1`/`-1` legs required by `TransferMatcher::finalize`'s zero-sum requirement. No privileged role, relayer key, or victim key is required — an ordinary user can self-custody both sides of the trade. Cost is simply gas for signing/executing many small intents, which is linear in the number of unit legs; splitting large transfers into many `execute_intents` calls (across multiple transactions if needed) is entirely feasible for an unprivileged actor.

### Recommendation
Compute and charge fees based on the aggregate `|delta|` per token accumulated across all `TokenDiff` legs affecting the same `(token_id, signer or batch)` within an execution (or remove the `amount > 1` exemption for `Nep245`/`Imt` and instead handle the "100%-fee-on-tiny-amounts" rounding problem differently, e.g. by accumulating fractional fee remainders, or by fee-exempting only tokens that are provably non-fungible, such as those with a fixed total supply of 1 per `token_id`). At minimum, do not key the zero-fee exemption purely off a single intent's `amount == 1`; use running totals that persist across all `TokenDiff` intents processed within `execute_intents`.

    fn supply_delta(token_id: &TokenId, delta: i128, fee: Pips) -> Option<i128> {

    // Finalizes transfer of this token, or returns unmatched delta.
    // If returned delta is zero, then overflow happened
    pub fn finalize_into(self, token_id: &TokenId, transfers: &mut Transfers) -> Result<(), i128> {
        // sort deposits and withdrawals in descending order
        let [mut deposits, mut withdrawals] = [self.deposits, self.withdrawals].map(|amounts| {
            let mut amounts: Vec<_> = amounts.into_iter().collect();
            amounts.sort_unstable_by_key(|(_, amount)| Reverse(*amount));
            amounts.into_iter()
        });

        // take first sender and receiver
        let (mut deposit, mut withdraw) = (deposits.next(), withdrawals.next());

        // as long as there is both: sender and receiver
        while let Some(((sender, send), (receiver, receive))) =
            withdraw.as_mut().zip(deposit.as_mut())
        {
            // get min amount and transfer
            let transfer = (*send).min(*receive);
            transfers
                .transfer(sender.clone(), receiver.clone(), token_id.clone(), transfer)
                // no error can happen since we add only one transfer for each
                // combination of (sender, receiver, token_id)
                .unwrap_or_else(|| unreachable!());

            // subtract amount from sender and receiver
            *send = send.saturating_sub(transfer);
            *receive = receive.saturating_sub(transfer);

            if *send == 0 {
                // select next sender
                withdraw = withdrawals.next();
            }
            if *receive == 0 {
                // select next receiver
                deposit = deposits.next();
            }
        }

        // only sender(s) left
        if let Some((_, send)) = withdraw {
            return Err(withdrawals
                .try_fold(send, |total, (_, s)| total.checked_add(s))
                .and_then(|total| i128::try_from(total).ok())
                .and_then(i128::checked_neg)
                .unwrap_or_default());
        }
        // only receiver(s) left
        if let Some((_, receive)) = deposit {
            return Err(deposits
                .try_fold(receive, |total, (_, r)| total.checked_add(r))
                .and_then(|total| i128::try_from(total).ok())
                .unwrap_or_default());
        }

        Ok(())
    }
