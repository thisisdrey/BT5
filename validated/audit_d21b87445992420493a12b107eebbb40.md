**Analysis:**

The gate in question is `check_account_existence` in `runtime/runtime/src/actions.rs`, called before executing any action, including `CreateAccount`. For `Action::CreateAccount`, it checks `account.is_some()` (already exists → `AccountAlreadyExists`) or, if the account doesn't exist, whether `account_is_implicit(account_id, ...)` is true — and if so, it unconditionally returns `OnlyImplicitAccountCreationAllowed`. [1](#0-0) 

This check is purely syntactic: it only inspects whether `account_id` matches the NEAR-implicit (64-hex-char) or ETH-implicit id format via `account_is_implicit`/`get_account_type`, and whether an `Account` record already exists at that id in the trie. It has no notion of "who owns public key P" or whether P is currently an active access key on some other named account. The attacker's premise — that having P as an `AddKey` on their own named account somehow makes the runtime treat `hex::encode(P)` as "already theirs" — has no code path support: nothing in `check_account_existence`, `action_create_account`, or `account_is_implicit` reads any other account's key set, and no cross-account key-ownership check exists in this gate. [2](#0-1) 

Consequently, submitting `CreateAccount` targeting `derive_near_implicit_account_id(P)` will be rejected by `OnlyImplicitAccountCreationAllowed` regardless of whether P is simultaneously an access key on another account — the check fires purely because the target id is syntactically implicit and does not yet exist, exactly as tested in `trying_to_create_implicit_account` and the meta-tx equivalent `meta_tx_create_implicit_account_fails`. [3](#0-2) [4](#0-3) 

There is no confusion between "reached via `action_create_account`" vs. "reached via transfer path" — `check_account_existence` runs before either handler and applies the same implicit-id check independent of caller intent, prior key possession, or which other account holds P as an access key. The only way to create an account at that id is via a lone `Transfer` action, which then seeds the `full_access` key derived from the id itself (`action_implicit_account_creation_transfer`), not from any pre-existing `AddKey` elsewhere. [5](#0-4)
