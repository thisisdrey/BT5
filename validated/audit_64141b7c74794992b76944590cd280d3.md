### Title
Wrong reward-cycle assignment for boundary-straddling tenures in `TenureStartEnd::from_inventory` - ([File: stackslib/src/net/download/nakamoto/tenure.rs])

### Summary
`TenureStartEnd::from_inventory` mislabels the `start_reward_cycle`/`end_reward_cycle` fields for any tenure whose start or end block lies across the `rc`/`rc+1` boundary. The function hard-codes `start_reward_cycle = rc` and derives `end_reward_cycle` from `wt_start.burn_height` (not `wt_end.burn_height`), which is backwards for the two boundary sub-cases, so the emitted `AvailableTenures` entry carries a reward-cycle number that does not match the sortition DB's true reward-cycle assignment for that block. Note: the question names `stackslib/src/net/connection.rs` as the target, but `TenureStartEnd`/`from_inventory` actually live in `stackslib/src/net/download/nakamoto/tenure.rs`.

### Finding Description
The cross-boundary loop (`next_wanted_tenures` branch) builds `TenureStartEnd` like this: [1](#0-0) 

- `start_reward_cycle` is unconditionally set to `rc`, even when the discovered `wt_start` was found in `next_wanted_tenures` (`in_next == true`), i.e. its true burn height belongs to `rc+1`.
- `end_reward_cycle` is computed via `pox_constants.block_height_to_reward_cycle(first_burn_height, wt_start.burn_height)` — using `wt_start`'s height, not `wt_end`'s. When `wt_start` is still within `rc` (`in_next == false`, so the tenure-start commit is in `rc` but its end block was only found in `next_wanted_tenures`, i.e. `rc+1`), `end_reward_cycle` is computed as `rc` instead of the correct `rc+1`.

This is exactly the scenario the function's own doc comment describes as needing look-ahead into the next reward cycle: [2](#0-1) 

Because `wanted_tenures`/`next_wanted_tenures` are built from the local sortition DB (not attacker data) but the *inv bits* selecting which index becomes `wt_start`/`wt_end` come entirely from the remote peer's `NakamotoInv`, a sole inventory-source peer fully controls which sub-case is hit for the boundary tenure by choosing which bits it reports set/unset at the last indices of `rc` and the first indices of `rc+1`. This lets a remote peer deterministically force the mislabeled branch for the tenure that straddles the reward-cycle boundary.

Downstream, these fields are used to select which `RewardSet` to verify tenure block signatures against: [3](#0-2) 

If the wrong cycle number is looked up, the schedule entry is skipped ("no known … reward set for cycle") every time this deterministic computation re-runs, or — if a reward set does happen to exist under the wrong cycle number — the wrong signer public keys get passed into `NakamotoTenureDownloader::new` as `start_signer_keys`/`end_signer_keys`, which are documented as the keys used to validate that specific block's signer signatures. [4](#0-3) 

### Impact Explanation
For the tenure that straddles a reward-cycle boundary, the download machinery either (a) permanently fails to resolve a reward set for the (wrong) cycle number it computed, causing that tenure's download to be skipped/stalled every scheduling pass, or (b) fetches the reward set for the wrong cycle and attempts to validate the tenure-start/end block's signer signatures against the wrong `RewardSet`, causing legitimate signatures to fail verification. Both outcomes match the "High" category: steering the node off the tip via false/incorrectly-derived inventory data at the reward-cycle boundary, and/or signer-signature verification against the wrong `RewardSet`. This affects every node using that peer as an inventory source for the affected reward cycle, and is deterministic/repeatable since `from_inventory`'s output for a fixed `rc`/inv state never changes.

### Likelihood Explanation
No signature or admission check gates this: the caller only needs to be a normal, unprivileged remote peer serving a `NakamotoInv` response and being used (e.g., sole/preferred) as the inventory source for the boundary reward cycle — a condition that arises naturally, not requiring adversarial crafting, since the buggy branch is exactly the "normal" cross-boundary code path the algorithm is designed to exercise. A malicious peer can reliably choose which specific boundary tenure hits the `in_next == true` vs `in_next == false` sub-case by shaping its inventory bits, making the exact failure mode selectable and repeatable at will, at zero cost (a single `NakamotoInv` message).

### Recommendation
In the cross-boundary branch of `from_inventory`, compute `start_reward_cycle` from `wt_start.burn_height` (via `block_height_to_reward_cycle`) rather than hard-coding `rc`, and compute `end_reward_cycle` from `wt_end.burn_height` rather than `wt_start.burn_height`. Add unit-test assertions on `start_reward_cycle`/`end_reward_cycle` (not just `start_block_id`/`end_block_id`) in the existing boundary test at `stackslib/src/net/tests/download/nakamoto.rs` to catch this class of regression.

### Proof of Concept
Extend the existing boundary test at `stackslib/src/net/tests/download/nakamoto.rs:1237-1319` (or write a focused unit test in `tenure.rs`) with:
1. Construct `wanted_tenures` (rc) and `next_wanted_tenures` (rc+1) with known burn heights, `pox_constants`, `first_burn_height`.
2. Build a `NakamotoTenureInv` where `invbits` for `rc` has consecutive set bits at indices `k` and `k+1` (with `k+1` being the last index in `wanted_tenures`), and `next_invbits` for `rc+1` has bit `0` set (all other bits unset) — this forces the "wt_start in rc, wt_end in rc+1" sub-case.
3. Call `TenureStartEnd::from_inventory(rc, &wanted_tenures, Some(&next_wanted_tenures), &pox_constants, first_burn_height, &invs)`.
4. Look up the returned entry for `wanted_tenures[k].tenure_id_consensus_hash` and assert `entry.end_reward_cycle == rc + 1` (the true reward cycle of `next_wanted_tenures[0]`'s burn height) — the current code will instead yield `entry.end_reward_cycle == rc`, failing the assertion and demonstrating the incorrect reward-cycle assignment.
