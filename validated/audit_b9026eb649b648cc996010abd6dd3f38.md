### Title
Fixed-window stream throttling allows unstaked clients to burst 2x `max_streams_per_throttling_interval` across window boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a strict **fixed-window** counter: it only resets `stream_count` to `0` and rewinds `last_throttling_instant` when `Instant::now().duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL` [1](#0-0) . `throttle_stream` only sleeps (and only increments `throttled_streams`) when `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` at the moment it is called [2](#0-1) . Nothing in the call path enforces a sliding-window bound; the counter is reset unconditionally to `0` as soon as the fixed window elapses, discarding all history of the prior window. An attacker who opens `max_streams_per_throttling_interval` streams at `last_throttling_instant + STREAM_THROTTLING_INTERVAL - ε` (all counted, never throttled since they are exactly under the cap) and then immediately opens another full batch at `+ε` past the boundary (after `reset_throttling_params_if_needed` zeroes the counter and moves `last_throttling_instant` forward) will never hit the `>=` throttle condition in either window, despite the two bursts landing within `2ε` of real time — far less than `STREAM_THROTTLING_INTERVAL`.

### Impact Explanation
This lets an unstaked connection push up to `2 * max_streams_per_throttling_interval` streams within an arbitrarily short real-time span straddling the reset boundary, momentarily doubling the intended per-connection QoS budget for that connection. Since `max_unstaked_load_in_throttling_window` is derived from `MAX_UNSTAKED_TPS` (200) over a 100ms window [3](#0-2) [4](#0-3) , this is a bounded QoS-evasion issue affecting fairness among co-tenant unstaked/staked connections sharing TPU capacity, not an unbounded resource exhaustion or panic.

### Likelihood Explanation
Exploitation only requires an unstaked client to time stream opens against `last_throttling_instant`, which is readable indirectly by observing throttling behavior (sleep delays) from client-observable round-trip timing, or simply by opening streams continuously at high rate — since a continuously-bursting sender will naturally straddle every window boundary this way. No special privileges are needed beyond an unstaked QUIC connection to the TPU port. The effect is bounded to a single window-boundary doubling per boundary crossed, not a compounding advantage.

### Recommendation
Replace the fixed-window reset in `ConnectionStreamCounter::reset_throttling_params_if_needed` with a sliding-window or token-bucket algorithm (e.g., decay `stream_count` proportionally to elapsed time, or track a rolling deque/timestamp bucket of accepted streams) so that no rolling window of length `STREAM_THROTTLING_INTERVAL` can ever exceed `max_streams_per_throttling_interval`, instead of only bounding fixed, non-overlapping windows.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test]
async fn test_fixed_window_boundary_burst_doubles_budget() {
    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;

    // Burst A: consume full budget just before window end.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);

    // Sleep until just past STREAM_THROTTLING_INTERVAL boundary.
    tokio::time::sleep(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst B: counter is reset to 0, full budget consumed again immediately after.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }

    // Assertion that SHOULD hold for a sliding-window bound but FAILS today:
    // total streams accepted within any STREAM_THROTTLING_INTERVAL-length window
    // should never exceed max_streams, but here 2*max_streams were accepted
    // with 0 throttled_streams recorded, within ~1ms of real elapsed slack.
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0); // demonstrates no throttling triggered
    assert_eq!(counter.stream_count.load(Ordering::Relaxed), max_streams); // window reset discarded prior burst's count
}
```
This test demonstrates that `2 * max_streams_per_throttling_interval` streams are accepted with `throttled_streams` remaining `0`, confirming the fixed-window reset in `reset_throttling_params_if_needed` fails to bound streams over a sliding window.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
