### Title
`GET /v3/blocks/<id>` serves non-canonical (unprocessed/orphaned) Nakamoto block bytes as if canonical - ([File: stackslib/src/net/api/getblock_v3.rs])

### Summary
`RPCNakamotoBlockRequestHandler::try_handle_request` resolves and streams any block found in `nakamoto_staging_blocks` purely by `index_block_hash`, with no `processed = 1 AND orphaned = 0` filter anywhere in the lookup chain. An unprivileged remote peer can obtain (via gossip) and unauthenticated-upload a validly-signed but non-canonical (superseded-sibling or later-orphaned) block via `/v3/blocks/upload/` and then retrieve it via `GET /v3/blocks/<block_id>`, receiving it as ordinary "OK" block bytes indistinguishable from a canonical block.

### Finding Description
The equality that should hold is: a byte stream returned by `GET /v3/blocks/<block_id>` with HTTP 200 implies `block_id` was committed by the canonical Nakamoto chain (`processed = 1 AND orphaned = 0`). This equality is broken.

`RPCNakamotoBlockRequestHandler::try_handle_request` calls `chainstate.nakamoto_blocks_db().get_tenure_and_parent_block_id(&block_id)`: [1](#0-0) 
whose SQL is unfiltered: [2](#0-1) 
`NakamotoBlockStream::new` then resolves the rowid via `get_nakamoto_block_rowid`, which is likewise unfiltered by `processed`/`orphaned`: [3](#0-2) 
and streams the raw block bytes straight from the blob (`generate_next_chunk`), with no canonical-tip check at all: [4](#0-3) 

Contrast this with sibling queries in the same file that *do* filter correctly, e.g. `next_ready_nakamoto_block`'s `processed = 0 AND orphaned = 0` and `get_nakamoto_blocks_in_tenure`'s `processed = 1`: [5](#0-4) 

The staging DB genuinely stores non-canonical rows long-term: `store_block_if_better` explicitly allows storing a "sibling" block for the same tenure that carries more signing weight even after a different block from that tenure has already been processed, and the accompanying test comment confirms this is intentional ("This is allowed because we don't commit to signatures"): [6](#0-5) [7](#0-6) 
Rows are also never deleted when a block is orphaned; `set_block_orphaned` only flips `orphaned = 1` on the row and its dependents, leaving the data blob (and its `index_block_hash`) queryable forever: [8](#0-7) 

The attacker's exact message: a validly-signed `NakamotoBlock` (obtained via P2P gossip, or as a losing sibling from a natural signer/miner equivocation) POSTed as raw `application/octet-stream` to `/v3/blocks/upload/` without `broadcast=1` (so no `authorization` header is required): [9](#0-8) 
`accept_block` only rejects blocks that fail signature/burnchain validation or are already known; a genuinely signer-signed-but-non-canonical sibling passes `verify_signer_signatures` and gets stored via `store_block_if_better` (case 1, new sighash) with `processed = 0, orphaned = 0`: [10](#0-9) 
The attacker then issues `GET /v3/blocks/<that block_id>` and receives the raw block bytes as if canonical, exploiting the missing filter described above.

### Impact Explanation
Any RPC caller of the targeted node (this endpoint has no authentication) can be served a non-canonical, unprocessed, or orphaned Nakamoto block indistinguishable from a canonically committed one. This matches the High-severity category "serving non-canonical state as canonical": downstream consumers (indexers, wallets, other tooling that trusts a 200 response from `/v3/blocks/<id>`) can be fed a block that never became part of the canonical chain, and repeated arbitrarily for any block the attacker can source (each upload + fetch pair yields one forged-canonical read). It does not corrupt the node's actual chainstate/MARF (the read endpoint doesn't affect `processed`/`burn_attachable` state machine), but it does violate the served-content guarantee of a read RPC.

### Likelihood Explanation
- Attacker needs no privileged role, no RPC secret, and only remote connectivity to the target's RPC port (`/v3/blocks/upload/` is unauthenticated for `broadcast=0`).
- Attacker needs a genuinely valid signer-signed block that is not (or is no longer) canonical for the target node — obtainable by observing gossip of signer equivocations, natural forks that get orphaned, or blocks that a target node simply hasn't processed/heard was superseded yet. This does not require forging cryptographic signatures.
- Fully repeatable per distinct non-canonical block the attacker can source.
- Preconditions are moderate (requires the existence of a genuinely signed non-canonical block, which is a known/possible occurrence documented by the codebase's own "sibling" store logic and orphan-marking design), not attacker-controlled forgery.

### Recommendation
Add `AND processed = 1 AND orphaned = 0` (or equivalent state check) to `get_tenure_and_parent_block_id`, `get_nakamoto_block_rowid`, `get_nakamoto_block_size`, and `has_nakamoto_block_with_index_hash` when used from the public read RPC path (`getblock_v3.rs`, `getblockbyheight.rs`, `blockreplay.rs`), or add an explicit canonical-tip/ancestry check in `RPCNakamotoBlockRequestHandler::try_handle_request` before streaming block bytes, so the handler only serves blocks that are part of the canonical Nakamoto chain.

### Proof of Concept
Rust test in `stackslib::net::api::getblock_v3` (or a new integration test module):
1. Set up a `StacksChainState` with an open Nakamoto staging DB (as done in `chainstate/nakamoto/tests/mod.rs`).
2. Construct two sibling `NakamotoBlock`s for the same tenure/consensus hash and call `staging_tx.store_block_if_better(...)` for both, giving one the lower signing weight (this reproduces what an attacker's uploaded-but-non-canonical sibling would produce), or alternatively call `staging_tx.set_block_orphaned(&sibling_block_id)` to mark one orphaned directly.
3. Confirm `NakamotoChainState::get_canonical_block_header` / the tip resolution logic does **not** point to the sibling/orphaned block's `block_id`.
4. Construct `RPCNakamotoBlockRequestHandler { block_id: Some(sibling_block_id) }`, call `try_handle_request` with a synthetic `StacksNodeState`/`HttpRequestPreamble`.
5. Assert the response is HTTP 200 (not 404), and decode the returned chunked bytes via `NakamotoBlock::consensus_deserialize`, asserting `decoded.block_id() == sibling_block_id` — proving the handler served a non-canonical block as if it were valid/canonical, i.e. `served_block_id != canonical_tip_at_that_height`.

    fn generate_next_chunk(&mut self) -> Result<Vec<u8>, String> {
        let mut blob_fd = self
            .staging_db_conn
            .open_nakamoto_block(self.rowid, false)
            .map_err(|e| {
                let msg = format!(
                    "Failed to open Nakamoto block {}: {:?}",
                    &self.index_block_hash, &e
                );
                warn!("{}", &msg);
                msg
            })?;

        blob_fd.seek(SeekFrom::Start(self.offset)).map_err(|e| {
            let msg = format!(
                "Failed to read Nakamoto block {}: {:?}",
                &self.index_block_hash, &e
            );
            warn!("{}", &msg);
            msg
        })?;

        let mut buf = vec![0u8; self.hint_chunk_size()];
        let num_read = blob_fd.read(&mut buf).map_err(|e| {
            let msg = format!(
                "Failed to read Nakamoto block {}: {:?}",
                &self.index_block_hash, &e
            );
            warn!("{}", &msg);
            msg
        })?;

        buf.truncate(num_read);

        self.offset += num_read as u64;
        self.total_bytes += num_read as u64;

        Ok(buf)
    }

        &self,

                let ch: ConsensusHash = row.get(0)?;

            .optional()?)
