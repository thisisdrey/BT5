### Title
Uninitialized `accountIndexOf` grants instant unclaimed rewards equal to full token balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` reads `accountIndexOf[token_][account_]`, which is `0` for any account that has never interacted since a reward token was activated. The guard that falls back to `INITIAL_INDEX` only fires when `_tokenIndex > INITIAL_INDEX`. When the supply index is exactly `INITIAL_INDEX` — i.e., the window between `updateTokenSpeed` initializing `tokenStates[token_]` and the first interest accrual (`_deltaTimestamps > 0 && _speed > 0` in `_calculateTokenIndex`) — the fallback is skipped and `_deltaIndex = INITIAL_INDEX - 0 = 1e18`. The account's entire `token_.balanceOf(account_)` is then booked as claimable rewards.

### Finding Description
The analog to CVE-2024-0340 (use of uninitialized memory) is the read of the uninitialized `accountIndexOf` mapping. Relevant flow, all callable by an unprivileged account:

- `claimRewards(accounts_, tokens_)` is public `nonReentrant` and calls `_updateTokensAccruedOf(_token, account)` for any arbitrary `accounts_[j]` when `tokenStates[_token].index > 0` (`RewardsDistributor.sol:150-168`).
- `_updateTokensAccruedOf` → `_calculateTokenDelta` (`RewardsDistributor.sol:261-266`, `217-231`):
```solidity
_accountIndex = accountIndexOf[token_][account_];          // 0, uninitialized
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {   // false when index == 1e18
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;         // = 1e18
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex); // = full balance
```
- `tokensAccruedOf[account_] += balance`, and `_transferRewardIfEnoughTokens` pays out `rewardToken` up to the distributor's balance (`RewardsDistributor.sol:248-256`).

Attack path: the attacker holds a `DepositToken` balance (deposited via `Pool`/`DepositToken.deposit`). A governor `updateTokenSpeed`/`updateTokenSpeeds` tx sets `tokenStates[token_] = {index: INITIAL_INDEX, timestamp: now}` (`RewardsDistributor.sol:298`). In the same block (index still exactly `1e18`), the attacker back-runs it by calling `claimRewards(attacker, [depositToken])` directly or via `Operator.execute`. `_updateTokenIndex` is a no-op (`_deltaTimestamps == 0`), `_calculateTokenDelta` books `tokensDelta == attackerBalance`, and `rewardToken.safeTransfer` drains the distributor.

### Impact Explanation
Theft of unclaimed yield / direct theft of protocol-held `rewardToken`: the attacker is credited `tokensAccruedOf` equal to their entire deposit-token balance without any time having accrued. Scaling the deposit (deposit size is attacker-chosen) converts an arbitrarily large fraction of the distributor's `rewardToken` balance into an instant claim, stealing rewards owed to all other users.

### Likelihood Explanation
Requires a `DepositToken`/`DebtToken` balance in the attacker account plus the ability to call `claimRewards` in the same block as a governor speed-activation tx (public mempool, trivially back-runnable). Repeatable once per token activation and again after any index-reset path. No privileged role is needed for the exploit call itself; the trigger is a normal, expected governor action. Likelihood is therefore bounded by reward-program activation events but the exploit itself is deterministic.

### Recommendation
Initialize the account index unconditionally: change `_calculateTokenDelta` so that `_accountIndex == 0` always maps to the current `_tokenIndex` (or at least `INITIAL_INDEX`), e.g. `if (_accountIndex == 0) _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;` — or simply `_accountIndex = _tokenIndex` when unset — so `deltaIndex` is `0` for first-time accounts. Alternatively, write `accountIndexOf[token_][account_] = INITIAL_INDEX` at index-initialization time for existing holders is infeasible, so the unconditional fallback is the correct fix.

### Proof of Concept
```solidity
// Hardhat fork sketch
// 1. attacker deposits underlying via DepositToken.deposit -> holds D depositTokens
// 2. governor tx: rewardsDistributor.updateTokenSpeed(depositToken, speed) // index=1e18, ts=now
// 3. same block (backrun):
await rewardsDistributor.connect(attacker).claimRewards(
    [attacker.address],
    [depositToken.address]
);
// expect: tokensAccruedOf[attacker] == D  (wadMul(balance, 1e18))
// and rewardToken.balanceOf(attacker) == min(D, distributorBalance)
// Invariant broken: reward accrual proportional to time*speed, not instantaneous full balance
```
Assert in-test: set `speed` such that `index` never exceeds `INITIAL_INDEX` within the block, confirming `accountIndexOf` fallback is bypassed and `tokensDelta == balanceOf(attacker)`.
