### Title
Git argument injection via unsanitized `Url` in `cloneFromURLCommand` allows `-u`/`--upload-pack` and transport-scheme (`ext::`, `fd::`) command execution - (File: internal/gitaly/service/repository/create_repository_from_url.go)

### Summary
`cloneFromURLCommand` places the caller-controlled `Url` (from `CreateRepositoryFromURLRequest`) directly as a positional `Args` element of a `git clone` invocation without validating it against `gitcmd`'s `flagRegex`, without inserting a `--` end-of-options marker, and without restricting the URL scheme. Because git's own argument parser treats any leading-dash token as an option rather than a positional operand, and dangerous "user" protocol helpers such as `ext::`/`fd::` are not blocked (no `GIT_ALLOW_PROTOCOL`/`GIT_PROTOCOL_FROM_USER=0` is set anywhere in the command construction), an attacker-controlled `Url` value can be interpreted by `git-clone(1)` as `--upload-pack=<arbitrary command>` or as a transport-helper invocation, leading to command execution on the Gitaly host.

### Finding Description
`cloneFromURLCommand` builds the clone invocation as: [1](#0-0) 

The only transformation applied to the URL is `url.Parse`/`u.String()` (for stripping userinfo into an `Authorization` header) and an optional resolved-address rewrite; there is no check that `urlString` doesn't begin with `-` and no allowlist of schemes (`http`, `https`, `git`, `ssh`): [2](#0-1) 

`validateCreateRepositoryFromURLRequest` only checks that the URL is non-empty: [3](#0-2) 

Compare this to `gitcmd.Flag`/`ValueFlag`, which do enforce `flagRegex` (`^(-|--)[[:alnum:]]`) to reject anything that looks like an option when building **flags**: [4](#0-3) [5](#0-4) 

However, this validation is never applied to positional `Args` entries such as the clone URL, and the command is built without a `--` separator to force git to stop option parsing: [6](#0-5) 

Consequences:
1. A `Url` value beginning with `-` (e.g. `-uCMD`) is parsed by git's own `parse-options` as the short alias for `--upload-pack=CMD` rather than as the repository operand, because it occupies the first positional slot before any `--` marker. `--upload-pack` designates an arbitrary local command that git will exec on the "server" side of a local/ssh/`ext::` transport, giving command execution.
2. A `Url` value using the `ext::` (or `fd::`) transport scheme is passed straight to git, which will spawn the given shell command as a remote-helper unless `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow`/`GIT_PROTOCOL_FROM_USER=0` restrict it — none of these are set by `cloneFromURLCommand` or by `gitCmdFactory.NewWithoutRepo` in this path.

Neither of Gitaly's usual defenses apply here: `storage.ValidateRelativePath` only governs the repository's relative path, not the remote URL; `git.ValidateRevision` is irrelevant (this isn't a revision); the `gitcmd` Flag/ValueFlag `flagRegex` allowlist is never invoked on `Args`; and `helper.SanitizeString` is a logging sanitizer, not an argument validator.

### Impact Explanation
This is git argument/config injection leading to remote code execution on the Gitaly node, matching GitLab's "RCE" bounty impact class — the highest severity for a Gitaly finding, since it lets an unprivileged user who can trigger repository-from-URL creation/import (e.g., "Import project from URL"/repository mirroring) execute arbitrary commands as the Gitaly process user, well beyond the scope of their own repository.

### Likelihood Explanation
The precondition is simply that the attacker end-to-end controls the `Url` field of a `CreateRepositoryFromURLRequest`, which is exactly what an ordinary GitLab user does when using "Import project by URL" or configuring a repository mirror — both standard, unprivileged actions. No special role, secret, or non-default configuration is required, making this readily reachable and repeatable.

### Recommendation
- Reject any `Url` value that matches `flagRegex` (i.e., begins with `-`) before constructing the clone command, mirroring the check already applied to `Flag`/`ValueFlag`.
- Insert a `--` end-of-options separator before the URL/path positional arguments passed to `git clone`.
- Enforce an explicit scheme allowlist (`http`, `https`, `git`, `ssh`) on the parsed URL, rejecting `ext::`, `fd::`, `file::`, and any other "user" protocol helper.
- Additionally set `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (or `GIT_PROTOCOL_FROM_USER=0` plus explicit `protocol.<name>.allow=never` for helper protocols) in the command's environment as defense in depth.

### Proof of Concept
```go
func TestCreateRepositoryFromURL_ArgInjection(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repoClient := setupRepositoryService(t) // existing test setup helper

    req := &gitalypb.CreateRepositoryFromURLRequest{
        Repository: &gitalypb.Repository{
            StorageName:   cfg.Storages[0].Name,
            RelativePath:  gittest.NewRepositoryName(t),
        },
        // A dash-prefixed URL is parsed by git as "--upload-pack=touch /tmp/pwned"
        // rather than as the repository operand.
        Url: "-utouch /tmp/pwned;#",
    }

    _, err := repoClient.CreateRepositoryFromURL(ctx, req)
    // Expected today: git fails with an "unknown option" / weird transport error
    // instead of a clean "invalid argument" from Gitaly-side validation,
    // demonstrating that the raw value reached git's argv unfiltered.
    // With ext:: scheme:
    req.Url = "ext::sh -c touch\\ /tmp/pwned2"
    _, err = repoClient.CreateRepositoryFromURL(ctx, req)
    require.NoError(t, err) // arbitrary command executes as remote-helper
    require.FileExists(t, "/tmp/pwned2")
}
```
Expected result after the fix: both requests are rejected at `validateCreateRepositoryFromURLRequest`/`cloneFromURLCommand` with `InvalidArgument` before any `git clone` process is spawned, and `/tmp/pwned2` is never created.
