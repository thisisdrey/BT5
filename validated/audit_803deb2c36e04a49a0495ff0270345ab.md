## Analysis

The Liquity bug is a **single unprivileged actor cheaply flipping shared global state that causes collateral damage (dropped/blocked legitimate requests) for everyone else**, requiring a costly external action to undo. The closest concrete analog in Agave sits in the pre-sigverify **packet dedup Bloom filter** used by `SigVerifyStage`, which runs on *any* unauthenticated TPU packet before signatures are even checked or fees are paid.

`SigVerifyStage` builds a shared `Deduper` per packet stream (regular + vote) sized at a fixed capacity, with a short, fixed reset cadence: [1](#0-0) [2](#0-1) 

Every incoming packet batch is hashed into this shared filter **before** signature verification or fee validation happens, in `run_transaction_task`: [3](#0-2) 

The `Deduper::dedup` implementation sets K bits per item into a shared bitset, and tracks a global `popcount` used to compute the false-positive rate: [4](#0-3) 

Because this hashing happens on raw packet bytes with **no signature check, no fee charge, and no per-sender accounting**, a single unprivileged sender can cheaply flood the CPU-only pre-fee dedup path with a large volume of distinct byte strings (need not even be well-formed transactions) to saturate the filter's bit array and drive the false-positive rate above the configured threshold: [5](#0-4) 

Once the false-positive rate crosses `DEDUPER_FALSE_POSITIVE_RATE` (0.001), `maybe_reset` resets the whole shared filter for that stream — but between resets, or during the ramp-up to saturation, **other unrelated, legitimate, distinct transactions from any user hashing into already-set bits are silently marked as discarded duplicates** and dropped from that node's sigverify pipeline, exactly mirroring the "one actor pushes a shared threshold past its limit, disabling service for everyone else" pattern in the Liquity report: [6](#0-5) 

Unlike the Liquity bug, this is self-healing: the servicer thread calls `maybe_reset` roughly every 10ms with a 2-second reset cycle, so the window of collateral false-positive drops is bounded rather than requiring an expensive redemption-like fix: [7](#0-6) 

### Title
Unmetered pre-verification packet hashing lets an unprivileged sender saturate the shared sigverify dedup Bloom filter, causing false-positive drops of other users' legitimate transactions - (File: core/src/sigverify.rs, perf/src/deduper.rs)

### Summary
The TPU non-vote/vote sigverify path deduplicates every incoming packet against a shared, fixed-capacity Bloom filter (`Deduper`) *before* any signature verification or fee validation is performed. Because insertion cost is paid uniformly by any sender regardless of whether their packets are valid, well-formed, or fee-paying, a single unprivileged high-throughput sender can push the filter's bit-population past its configured false-positive threshold. While saturated, *other* users' distinct, legitimate transactions that happen to hash into already-set bits are incorrectly classified as duplicates and discarded in `run_transaction_task`, denying them entry into banking stage for that node.

### Finding Description
`SigVerifyStage::new` allocates one `Deduper<2, [u8]>` per packet stream with a fixed bit count and reset cadence [1](#0-0) [2](#0-1) . Each worker calls `deduper::dedup_packets_and_count_discards` on the raw packet bytes prior to signature verification [3](#0-2) . The `Deduper::dedup` function sets bits in a shared bitset and increments a global `popcount` for every hashed item, with no accounting for the packet's sender, validity, or fee [4](#0-3) . `false_positive_rate` is a pure function of total `popcount`, shared across all senders [5](#0-4) . Consequently, one sender flooding enough distinct byte payloads (valid or not — they don't need to pass sigverify to be hashed) can raise the aggregate false-positive rate to the point where other unrelated legitimate transactions collide with already-set bits and get marked as duplicates/discarded, purely as a side effect of the attacker's own volume.

### Impact Explanation
While the filter self-resets on a short, fixed cycle (`MAX_DEDUPER_AGE` = 2s, checked roughly every 10ms in the servicer loop) [7](#0-6) , a sustained flood can keep the filter oscillating near/above the saturation threshold, producing a rolling, repeatable window of false-positive drops of legitimate, distinct transactions from unrelated senders at a given node's TPU ingress. This is a real, if bounded and self-healing, QoS degradation caused entirely by unprivileged, pre-fee, pre-signature-check work — directly analogous to the report's core theme of a cheap unprivileged action degrading a shared resource for all other unprivileged users.

### Likelihood Explanation
Requires sustained high packet volume from a single sender/IP to overcome per-IP/connection rate limiting upstream (QUIC QoS) and reach the ~2M-item capacity of the 64M-bit filter within the 2-second window; feasible for a well-resourced or many-IP attacker, but bounded in blast radius (per-node, per-stream, self-resetting) rather than a persistent cluster-wide lock like the Liquity CCR case.

### Recommendation
Consider per-sender/stake-weighted accounting or rate-limiting contribution to the dedup filter's popcount, or moving the dedup check after a cheap validity/signature pre-check so that garbage (unsigned/invalid) payloads cannot consume shared dedup capacity for free.

### Proof of Concept
1. Establish a QUIC connection/stream(s) within existing per-IP/per-stake connection and stream limits.
2. Continuously send a high volume of distinct byte payloads (need not be valid transactions) to the TPU ingest port.
3. Observe (via `num_deduper_saturations` metric) the shared `Deduper`'s false-positive rate crossing `DEDUPER_FALSE_POSITIVE_RATE`.
4. Concurrently submit legitimate, distinct transactions from an unrelated account/sender and observe some being silently discarded as false-positive duplicates in `run_transaction_task` before ever reaching signature verification or banking stage.

    pub fn maybe_reset<R: Rng>(
        &self,
        rng: &mut R,
        false_positive_rate: f64,
        reset_cycle: Duration,
    ) -> bool {
        assert!(0.0 < false_positive_rate && false_positive_rate < 1.0);
        let _reset_guard = self.reset_guard.lock().unwrap();
        let saturated = self.false_positive_rate() >= false_positive_rate;
        if saturated || self.state.load().started_at.elapsed() >= reset_cycle {
            self.reset(rng);
        }
        saturated
    }

    // Returns true if the data is duplicate.
    #[must_use]
    #[allow(clippy::arithmetic_side_effects)]
    pub fn dedup(&self, data: &T) -> bool {
        let mut out = true;
        let state = self.state.load();
        for random_state in state.random_states.iter() {
            let hash: u64 = random_state.hash_one(data) % self.num_bits;
            let index = (hash >> 6) as usize;
            let mask: u64 = 1u64 << (hash & 63);
            let old = self.bits[index].fetch_or(mask, Ordering::Relaxed);
            if old & mask == 0u64 {
                self.popcount.fetch_add(1, Ordering::Relaxed);
                out = false;
            }
        }
        out
    }
