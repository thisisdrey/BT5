### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiled-contract ABI decoding causes node OOM/DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Several TVM precompiled contracts (the multi-signature/batch-signature validation precompiles that consume ABI-encoded arrays) decode a "count" word directly from caller-supplied calldata and immediately allocate a Java array of that size, without first checking that the declared count is consistent with the actual size of the remaining calldata. This mirrors the Facebook Thrift CVE-2019-11939 pattern: a message declares a container size far larger than the payload actually contains, and the runtime allocates memory for the declared size before validating it, letting a tiny message trigger a huge allocation.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` in `PrecompiledContracts.java` read a length field straight out of the ABI-decoded `DataWord[] words` array (fully attacker-controlled calldata to a precompiled contract call) and use it to size a Java array before any bound check against the actual calldata length: [1](#0-0) [2](#0-1) [3](#0-2) 

In each of these, `len = words[offset].intValueSafe()` is taken directly from a single 32-byte calldata word supplied by the caller. `intValueSafe()` on `DataWord` clamps to `Integer.MAX_VALUE` rather than rejecting the value, so a caller can set this word to any large value (e.g. `0x7fffffff`) using only a handful of bytes of transaction data. The code then does:

```java
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];   // or byte[][] bytesArray = new byte[len][];
```

This allocates an array of up to ~2.1 billion object references (≈17 GB on a 64-bit JVM with compressed oops, more without) purely from the declared length, with no comparison to `data.length` (the actual size of the calldata actually sent). Only *after* this allocation attempt does the code try to read entries via `extractBytes`, which is where an out-of-bounds/short-payload condition would normally be caught — but by then the JVM has already attempted (and likely failed) the oversized allocation, throwing `OutOfMemoryError`.

This is the same root cause described in the external report: a length/count field taken from a short, cheap message is trusted to size a memory allocation before the parser verifies that the declared size is actually backed by data present in the message.

### Impact Explanation
A single, cheap smart-contract call (or a transaction invoking a contract that in turn calls one of these precompiled contracts) can force the executing node to attempt an enormous heap allocation. Because the JVM heap for TVM execution is shared with the rest of the node process, a large-but-failed allocation, or GC pressure from many such attempts, can crash the node (`OutOfMemoryError` propagating out of critical VM execution paths) or make the node unresponsive to further transaction processing — a denial-of-service against a full node/SR that executes the transaction, satisfying the "node crash or halt" bar for a Medium/High severity finding.

### Likelihood Explanation
Any unprivileged account can broadcast a transaction that triggers a `TriggerSmartContract` call reaching these precompiled contracts (they are dispatched through `PrecompiledContracts.getContractForAddress`, reachable from ordinary contract execution). Crafting the calldata only requires setting one 32-byte word to a large value; it requires no special privileges, no prior state, and minimal fee, making this trivially and repeatedly triggerable by any anonymous broadcaster.

### Recommendation
Before allocating `bytesArray`/`bytes32Array` sized by `len`, validate `len` against the size of the actual supplied calldata (e.g., require `len <= (data.length - offset expected minimums)` and impose a sane hard cap consistent with the maximum item/array sizes these precompiles are designed to support), rejecting the call (returning failure) instead of allocating when the declared count cannot possibly be backed by the available data. This mirrors the fix pattern already applied elsewhere in the codebase, e.g. the length/availability check used by `verifyLength` in `RLP.java` and the bound check added in `ContractEventParser.subBytes`: [4](#0-3) [5](#0-4) 

### Proof of Concept
1. Deploy or call a contract that invokes the multi-signature/batch-signature-validation precompiled contract path that uses `extractBytesArray`/`extractSigArray`/`extractBytes32Array` (address dispatch in `PrecompiledContracts.getContractForAddress`).
2. Construct calldata for that precompile where the ABI-encoded "count" word at the expected `offset` is set to a very large value (e.g. `0x000000000000000000000000000000000000000000000000000000007fffffff`), while the rest of the calldata is only a few bytes long (well short of what `len` implies).
3. Submit the transaction; when `PrecompiledContract.execute(byte[] data)` is invoked, `extractBytesArray`/`extractSigArray`/`extractBytes32Array` computes `len` from the forged word and executes `new byte[len][]`, attempting a multi-gigabyte allocation from a call whose actual calldata is tiny — reproducing the "short message → large memory allocation" condition described in the Thrift advisory, on the node executing/validating the transaction.

Note: I was not able to fully trace, within the remaining tool budget, the exact class name and `getEnergyForData` cost formula for the precompiled contract(s) that invoke `extractBytesArray`/`extractSigArray` (test files `ValidateMultiSignContractTest.java` and `BatchValidateSignContractTest.java` reference this code path, suggesting the multi-sign/batch-sign validation precompile), so I cannot state with certainty whether the energy charged for these calls scales with the declared array length before the allocation occurs. This should be verified as part of remediation to confirm energy metering does not already bound `len` before the allocation is attempted.
