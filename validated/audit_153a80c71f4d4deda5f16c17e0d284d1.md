### Title
Permission/ACL check only covers the first contract in a multi-contract transaction, allowing unauthorized contract types to execute - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
The Consul CVE stems from an ACL check being enforced for the top-level "session" operation but not for a sub-operation batched inside the transaction API. java-tron's `Transaction.raw.contract` field is a `repeated Contract`, so a single signed transaction can in principle carry more than one contract/operation. However, all of the permission-enforcement logic that maps a signer's `permission_id` to the allowed `ContractType` bitmap inspects **only `contract(0)`**, while the code that turns the transaction into executable actuators walks the **entire contract list** and executes every one of them.

### Finding Description
Signature/permission validation is centered on index 0 of the contract list:
- `TransactionCapsule.validateSignature` dispatches based on `this.getInstance().getRawData().getContract(0)` only [1](#0-0) .
- The static `validateSignature(...)` helper that actually checks the permission's `operations` bitmap against the contract type explicitly reads `transaction.getRawData().getContractList().get(0)` and calls `checkPermission(permissionId, permission, contract)` for that single contract [2](#0-1) .
- `checkPermission`/`checkPermissionOperations` verify that the signer's `Active` permission's 32-byte operations bitmap has the bit set for the contract's `ContractType` — this is the exact mechanism analogous to Consul's per-operation ACL (`session:write`) [3](#0-2) [4](#0-3) .

Meanwhile, actuator construction/execution does not stop at index 0 — it iterates `rawData.getContractList()` and builds/executes an `Actuator` for **every** contract entry:
- `ActuatorCreator.createActuator` loops `for (Contract contract : rawData.getContractList())` and adds an actuator per contract [5](#0-4) .
- `ActuatorFactory.createActuator` does the same via `rawData.getContractList().forEach(...)` [6](#0-5) .
- `RuntimeImpl.execute` for non-VM contract types calls `ActuatorCreator.getINSTANCE().createActuator(...)` and then runs `act.validate()` / `act.execute(...)` for every actuator in the resulting list, with no additional per-contract permission re-check [7](#0-6) .

The comment in `validateSignature` — "Do not support multi contracts in one transaction" — shows the signature/permission-check code was written assuming exactly one contract, but nothing in the reviewed validation path enforces `getContractCount() == 1` before actuators for the remaining contracts are built and executed. If such a hard limit does not exist elsewhere in block/transaction acceptance (I was not able to locate one in the indexed code within the available search budget), an attacker whose Active permission bitmap only authorizes contract type X (e.g., `TransferContract`) can place that authorized contract at index 0 to pass `checkPermissionOperations`, and place an additional, unauthorized contract type (e.g., `AccountPermissionUpdateContract`, `WitnessUpdateContract`, `FreezeBalanceV2Contract`, etc.) at index 1+. Only the first contract's type is checked against the operations bitmap; the trailing contract(s) are still turned into actuators and executed by `ActuatorCreator`/`ActuatorFactory` with no independent permission enforcement.

### Impact Explanation
If reachable (i.e., if no other layer rejects `contractCount > 1`), this allows a holder of a narrowly-scoped multisig `Active` permission (e.g., authorized only to send TRC transfers) to smuggle in and execute a completely different, more privileged contract type — such as permission updates, freezing/unfreezing balances, voting, or asset operations — bypassing the very operations-bitmap ACL the multisig permission system exists to enforce. This is a direct authorization-bypass analog to the Consul session-deletion bug: a specific operation embedded in a composite request skips the ACL check that governs it, enabling account-state changes an authorized signer should not be able to perform on their own.

### Likelihood Explanation
Likelihood depends entirely on whether the node accepts and processes transactions with `contract_count > 1` at all. I could not confirm within the available searches that such a global single-contract constraint exists elsewhere in the codebase (e.g., in `Manager`, `TransactionUtil`, or block/tx acceptance validation) that would neutralize this gap. Given the protobuf schema explicitly supports a repeated `contract` field and the `validateSignature` comment acknowledges (but doesn't defend against) multi-contract transactions, this is a plausible but **unconfirmed** reachable path — it should be treated as requiring verification against the full transaction-acceptance pipeline (e.g., `TransactionCapsule` constructors, `Manager.pushTransaction`, and `TransactionUtil.validate`) before being treated as conclusively exploitable.

### Recommendation
- Enforce that every contract in `rawData.getContractList()` is checked against the signer's permission `operations` bitmap during signature validation, not just `contract(0)`.
- Alternatively/additionally, explicitly reject any transaction with `getContractCount() != 1` at the earliest validation stage if multi-contract transactions are not an intended, fully-supported feature — removing the ambiguity referenced by the "Do not support multi contracts in one transaction" comment.
- Add regression tests that construct a transaction with two contracts of different types signed by an `Active` permission scoped to only one of the types, and assert that the second contract is rejected.

### Proof of Concept
1. Create an account and set up an `AccountPermissionUpdateContract` giving it an `Active` permission whose 32-byte `operations` bitmap authorizes only `TransferContract` (bit for `TransferContract`'s `ContractType` value set, all others cleared), per `AccountPermissionUpdateActuator.checkPermission` [8](#0-7) .
2. Craft a `Transaction.raw` whose `contract` list contains two entries: index 0 = a valid `TransferContract` (authorized type), index 1 = an unauthorized contract type such as `WitnessUpdateContract` or `FreezeBalanceV2Contract`, both attributed to the same `owner_address`/`permission_id`.
3. Sign the transaction with keys satisfying the Active permission's threshold.
4. Submit via broadcast; `TransactionCapsule.validateSignature` → `validateSignature(transaction, ...)` only inspects `getContractList().get(0)` (the authorized `TransferContract`) for the bitmap check [2](#0-1) , so the signature check passes.
5. During execution, `ActuatorCreator.createActuator` builds actuators for both contracts [5](#0-4) , and `RuntimeImpl.execute` runs `validate()`/`execute()` on all of them [7](#0-6) , causing the unauthorized second contract's operation to execute despite the signer's permission never having been granted that operation type.

**Note:** I was unable to confirm, within the available indexed code, whether an upstream check rejects transactions with more than one contract before reaching this stage. This must be verified against `Manager`, `TransactionUtil`, and any transaction pre-broadcast validation to determine actual exploitability.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
