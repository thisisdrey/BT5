### Title
Orphaned self-call `PostponedReceipt` containing `DeployContractAction` survives `DeleteAccount` and executes on a recreated account, allowing arbitrary contract deployment without owner authorization - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account()` deletes an account's `Account`, `ContractCode`, access keys, gas keys, and `ContractData` entries, but never purges any `TrieKey::PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` entries keyed to that account. An attacker who owns account `A` can queue a self-call `DeployContractAction` (`predecessor_id == receiver_id == A`) as a postponed receipt awaiting an attacker-controlled data dependency, delete `A`, wait for an unrelated third party to recreate/fund `A`, and then release the dependency so the stale receipt executes and silently deploys malicious code onto the victim-funded account.

### Finding Description
A postponed action receipt is created whenever an incoming `ActionReceipt`'s `input_data_ids` are not yet all satisfied (`runtime/runtime/src/lib.rs`, `set_postponed_receipt`/`get_postponed_receipt` helpers in `core/store/src/utils/mod.rs:120-143`). The attacker's own contract on account `A` can trigger this via the standard `promise_batch_action_deploy_contract` host call chained with `.then()` on a promise the attacker fully controls the completion timing of (e.g., a multi-hop cross-contract call chain among attacker-owned accounts) — this is ordinary, unprivileged contract logic, not a validator/node capability. The resulting receipt has `predecessor_id = A`, `receiver_id = A`, action `DeployContract{code: malicious_wasm}`, and unmet `input_data_ids`, so it is stored under `TrieKey::PostponedReceipt{receiver_id: A, ...}` (plus a `PostponedReceiptId`/`PendingDataCount` link).

While that receipt is parked, the attacker submits a self-authorized `DeleteAccount` action on `A` (`check_actor_permissions` in `runtime/runtime/src/actions.rs:761-776` only requires `actor_id == account_id` and zero `locked` stake — trivially satisfied for a self-delete). `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which removes the account record, code, keys, and contract data — but leaves the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` trie entries untouched.

A third party, unaware of the dangling receipt, recreates account `A` (via `CreateAccount`+`Transfer` or implicit-account transfer) and deposits funds.

The attacker then triggers the pending dependency to arrive as a `Data` receipt. `process_receipt` (`runtime/runtime/src/lib.rs:1367-1474`) looks up the `PostponedReceiptId`, decrements `PendingDataCount`, and once it reaches zero, fetches the stored receipt with `get_postponed_receipt` and executes it via `apply_action_receipt` (`runtime/runtime/src/lib.rs:773-956`). Inside, `actor_id` is initialized from `receipt.predecessor_id().clone()` (`runtime/runtime/src/lib.rs:855`) — the value frozen at receipt-creation time, i.e., `A` — and the account is freshly loaded from current state (`runtime/runtime/src/lib.rs:853`), which now is the third party's recreated, funded account. `check_account_existence` (`runtime/runtime/src/actions.rs:834-845`) passes since the account now exists; `check_actor_permissions` (`runtime/runtime/src/actions.rs:745-760`) passes because `actor_id (A) == account_id (A)` by construction of the stored receipt, with no re-validation that this "self" authorization is still meaningful after account deletion/recreation. `action_deploy_contract` (`runtime/runtime/src/actions.rs:297`) then deploys the attacker's malicious code onto the victim's account. ### Impact Explanation
This is an authorization-escalation bug: an ordinary attacker deploys arbitrary contract code onto an account they no longer own, targeting a victim who now believes their freshly-created account holds no code. Once deployed, the attacker's contract can drain any balance the victim subsequently deposits (transfer, storage-staking deposit, etc.), since the victim's assumption "this account has no contract, so a Transfer is safe" is violated. This matches the "authorization escalation across accounts or promises" and "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions are entirely within an unprivileged attacker's control: deploying a contract that issues chained cross-contract promises to control dependency-resolution timing, self-deleting the account (a normal signed transaction), and later releasing the dependency. No validator, RPC operator, or leaked-key access is needed. The window during which a third party must "recreate and fund" the exact account name is the main external dependency and constrains repeatability/targeting — the attacker cannot force a specific victim to fund a specific recycled account name on a predictable schedule, but the primitive itself (planting a self-authorized action that fires after deletion/recreation) is fully reproducible and reliable once that account-name recycling occurs (a real, if less common, real-world pattern, e.g., "vanity"/short account names being abandoned and re-registered).

### Recommendation
`remove_account` in `core/store/src/utils/mod.rs` should also enumerate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries scoped to the account being deleted (and the corresponding `PromiseYield*` entries, if applicable) before the account is considered deleted — mirroring the existing cleanup already performed for access keys and contract data. Alternatively/additionally, `apply_action_receipt`/`check_actor_permissions` should not honor a self-call permission derived solely from a receipt's static `predecessor_id` once the destination account has been deleted and recreated in the interim (e.g., by tracking an account "generation"/incarnation counter and invalidating stale receipts targeting a prior incarnation).

### Proof of Concept
Runtime/test-loop integration test:
1. Deploy an attacker contract to account `A` implementing a `call_promise`-style batch that creates a chained cross-contract promise (e.g., a call to attacker-owned account `B` on another shard) `.then()`-followed by `promise_batch_action_deploy_contract(account_id = A, code = malicious_wasm)`.
2. Apply the chunk containing this call so the `DeployContract` action receipt is stored as `PostponedReceipt{receiver_id: A}` (verify via `get_postponed_receipt` in test helpers).
3. In a subsequent chunk (before the `B` promise resolves), submit a self `DeleteAccount{beneficiary_id: attacker_refund}` receipt for `A`; apply and confirm `get_account(A)` is `None` while `get_postponed_receipt(A, receipt_id)` still returns `Some(..)`.
4. Submit `CreateAccount` + `Transfer` from an unrelated third-party account to recreate and fund `A`; apply and confirm the account exists with `local_contract_hash() == None`.
5. Let the `B` promise complete and deliver its `Data` receipt to `A`, triggering `process_receipt`'s postponed-receipt execution path.
6. Assert `get_account(A).unwrap().local_contract_hash()` now equals the hash of `malicious_wasm`, and that the account owner (the third party) never signed any `DeployContract` action — proving unauthorized contract deployment onto their funded account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,

    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

        | Action::UseGlobalContract(_)

        }

                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),

                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}
