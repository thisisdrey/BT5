### Title
ExchangeInjectContract has no slippage control on liquidity injection ratio, enabling front-run/back-run sandwich extraction against the exchange creator - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
The TRON built-in bancor-like `Exchange` (TRC10↔TRX or TRC10↔TRC10 AMM) exposes `ExchangeInjectContract`, which lets the exchange **creator** add liquidity to their pool by specifying only `token_id` and `quant` of one side. The counter-side amount (`anotherTokenQuant`) is computed automatically from the *current* on-chain reserve ratio at execution time, with no user-supplied bound, min/max ratio, or price tolerance parameter — unlike `ExchangeTransactionContract` (the swap contract) which does carry an `expected` (minimum-received) field that is checked before execution. This is structurally identical to the Arrakis `ArrakisMetaVaultPrivate::fund` issue: a privileged actor deposits liquidity at whatever price the pool happens to be at, with no way to bound the price/ratio, and anyone can move that price beforehand via a permissionless action (here, `ExchangeTransactionContract`), extracting value from the depositor's contribution.

### Finding Description
`ExchangeInjectActuator.execute` computes the required amount of the other token purely from the pool's current balances: [1](#0-0) 

The validation path recomputes the same ratio-based amount and enforces only that it is positive and within the overall balance cap — there is no parameter in `ExchangeInjectContract` (owner_address, exchange_id, token_id, quant) that lets the creator express a bound on the price/ratio at which liquidity is added: [2](#0-1) 

In contrast, `ExchangeTransactionActuator` (a swap, callable by anyone) explicitly supports a caller-chosen minimum-output guard (`expected`), and rejects the swap if slippage exceeds it: [3](#0-2) 

Because swaps use a bancor/constant-formula (`ExchangeCapsule.transaction`) that mutates `firstTokenBalance`/`secondTokenBalance` and therefore the pool price, any account can permissionlessly and arbitrarily move the pool's price before the creator's `ExchangeInjectContract` executes: [4](#0-3) 

`ExchangeInjectContract` itself is restricted to the pool creator (`account is not creator` check), which is the analog of the "vault owner" in the Arrakis report: [5](#0-4) 

### Impact Explanation
An attacker observing a pending `ExchangeInjectContract` from a pool creator can:
1. Front-run with an `ExchangeTransactionContract` swap that shifts the pool ratio to an extreme (e.g., dumping one side), moving the price far from fair value.
2. Let the creator's inject transaction execute — since `anotherTokenQuant` is derived from the now-skewed ratio, the creator is forced to inject an unbalanced amount, adding liquidity that values one asset far below (or above) its true worth.
3. Back-run with a reverse `ExchangeTransactionContract` swap against the now-larger, mispriced pool, extracting the value the creator just donated at the unfavorable price — exactly mirroring the Alice/Bob sandwich described in the Arrakis report.

This results in a direct, unbounded loss of funds for the exchange creator on every `ExchangeInjectContract` they submit, and a guaranteed extractable profit for any unprivileged attacker who can observe the pending transaction and place transactions before/after it in the same or adjacent blocks. This satisfies "concrete unauthorized... theft... of funds."

### Likelihood Explanation
Both required primitives are fully permissionless and require no special privilege: `ExchangeTransactionContract` can be sent by any account holding the relevant asset/TRX, and observing a pending `ExchangeInjectContract` in the transaction pool/relayed traffic is a standard front-running assumption (same assumption used and accepted in the original Sherlock report). The only actor who is "privileged" is the pool creator invoking `ExchangeInjectContract` for their own pool — which is analogous to the "private vault owner" role in the original finding, not a validator/witness/node operator, so it is in scope per the reachable-actor rules. Given that TRON's on-chain `Exchange` markets are typically thin (low liquidity, since these are legacy TRC10 bancor pools), the price impact needed to skew the ratio is readily achievable, making this practically exploitable, not merely theoretical.

### Recommendation
Add slippage-control parameters to `ExchangeInjectContract` analogous to `ExchangeTransactionContract`'s `expected` field — e.g., a caller-supplied minimum/maximum acceptable `anotherTokenQuant` (or an acceptable price band) — and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()`, rejecting the injection if the computed ratio falls outside the creator-specified bounds.

### Proof of Concept
1. Pool state: Exchange with `firstTokenBalance = A`, `secondTokenBalance = B` (ratio A:B).
2. Creator broadcasts `ExchangeInjectContract{token_id=first, quant=Q}` intending to inject at the current A:B ratio.
3. Attacker sees this pending tx and submits `ExchangeTransactionContract{token_id=second, quant=X, expected=1}` before it, which via `ExchangeCapsule.transaction` (lines 124-169) skews the pool to a much less favorable A':B' ratio.
4. Creator's inject executes against the actuator logic at lines 71-83, computing `anotherTokenQuant` from the skewed A':B' ratio and locking in an overvalued/undervalued deposit.
5. Attacker submits a reverse `ExchangeTransactionContract` swap to unwind their initial swap plus profit extracted from the mispriced pool now enlarged by the creator's injected liquidity — net profit to attacker, net loss to creator, with no protocol-level check to prevent any step.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
