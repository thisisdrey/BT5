### Title
`TokenDiff::token_fee` fee-exemption is bypassable by wrapping any value as a self-issued NEP-245 token and settling in unit-sized legs - (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives protocol fees on `TokenIdType::Nep245`/`Imt` whenever the per-leg `amount <= 1`, and this type is derived purely from which deposit entry point (`ft_on_transfer` vs `mt_on_transfer`) produced the `TokenId`. Since any unprivileged account can deploy its own NEP-245 contract and deposit arbitrary value through `mt_on_transfer`, and then settle that value through the Verifier in a sequence of `amount = 1` `TokenDiff` legs, it can make an economically fungible asset permanently fee-exempt, while the same value deposited as NEP-141 always pays `fee.fee_ceil(amount)`.

### Finding Description
The claimed binding is: `token_fee(asset, V)` should reflect a fee schedule tied to the economic nature of `asset`, i.e. `fee(asset_as_Nep141, V) == fee(asset_as_Nep245, V)` for the same signer-chosen value `V`. In the code, this equality is broken: [1](#0-0) 

`token_fee` matches on `TokenIdType` (derived from the `TokenId` enum variant) and returns `Pips::ZERO` unconditionally for `Nep171`/`Nep245`/`Imt` whenever `amount <= 1`, with no reference to whether the wrapped value is fungible or how large the total `mt_on_transfer` deposit was: [2](#0-1) 

The `TokenId` variant (and hence `TokenIdType`) is fixed purely by which receiver hook constructed it — `Nep141TokenId` from `ft_on_transfer`, or `Nep245TokenId` from `mt_on_transfer` — both of which are fully attacker-controlled since anyone can deploy their own FT or MT contract and call `mt_transfer_call`/`mt_on_transfer` with no whitelist check other than "not self-wrapping": [3](#0-2) 

Deposits mint the corresponding balance 1:1 with no re-classification logic based on economic fungibility: [4](#0-3) 

**Exploit flow:**
1. Attacker deploys their own NEP-245 contract, mints/holds `V` units under a single `token_id` (fungible semantics entirely at the attacker's discretion).
2. Attacker calls `mt_transfer_call` into the Verifier, which constructs `TokenId::Nep245(attacker_mt_contract, token_id)` for the full `V` via `mt_on_transfer`/`Contract::deposit`.
3. Attacker (optionally using a second account they control) executes `V` `TokenDiff` intents in one batch, each moving exactly `delta = -1`/`+1` of that `Nep245` token against a counter-leg (e.g. another unit-sized Nep245 asset), so `TransferMatcher::finalize` nets to zero per `Loderfordw/intents--007 contracts/defuse/core/src/engine/state/deltas.rs:265-284` without triggering `InvariantViolated`.
4. Each leg calls `Self::token_fee(token_id, amount=1, fee)`, which hits the `Nep245 | Imt if amount > 1 => {}` guard's else-branch and returns `Pips::ZERO`, so `fee_ceil(1) = 0` for every leg. Total fee collected over `V` legs = 0.
5. The identical economic value deposited as `Nep141` and moved in one `TokenDiff` with `delta = -V` computes `token_fee = fee` (non-zero) and `fee.fee_ceil(V) > 0` (and even a `Nep141` leg of `amount=1` pays `fee_ceil(1) >= 1` whenever `fee > 0`, since `Nep141` never hits the zero-fee branch).

No existing guard (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize`, `checked_*` arithmetic) prevents this: the invariant check only enforces that deltas net to zero across the batch, which the attacker satisfies trivially by round-tripping with a self-controlled counterparty leg; it says nothing about fee correctness per asset class.

### Impact Explanation
This under-collects protocol fees on economically fungible value that the depositor chooses to route through a self-deployed NEP-245 (or IMT) wrapper instead of the canonical NEP-141 path, matching the explicitly listed Critical category "protocol fees bypassed or over-collected." No Verifier custody imbalance occurs (deposits/withdrawals stay 1:1), but the fee schedule intended to apply per-asset is fully controllable by the depositor merely by choosing the wrapping contract and standard, and by splitting settlement into unit legs. This is repeatable indefinitely, for any `V`, by any signer, at zero cost beyond deploying a trivial MT contract and paying gas for `V` legs, and applies to every token the fee-collector would otherwise earn revenue on.

### Likelihood Explanation
No privileged role, relayer key, or upgrade is needed. Preconditions are: attacker deploys a NEP-245 contract (fully permissionless), deposits value through `mt_on_transfer` (no whitelist beyond disallowing self-wrap), and signs `TokenDiff` intents from one or two accounts they control. Splitting into `V` unit legs costs proportional gas/transaction overhead but no economic cost, making it fully feasible and directly incentivized whenever `fee > 0`.

### Recommendation
Compute `token_fee` based on total economic value moved for a given token across the whole `TokenDiff`/batch rather than per-leg `amount`, or restrict the `amount <= 1` fee exemption to token classes that are provably non-fungible (e.g. only `Nep171`, and NEP-245/IMT token_ids explicitly marked non-fungible/supply-capped at issuance), instead of exempting any `Nep245`/`Imt` `TokenId` whenever a single leg happens to be `<= 1`.
