### Title
Order-execution instructions inherit the entropyCallback pause-lockout bug class: `ProtocolPaused` on `StartExecuteOrder`/`EndExecuteOrder` after fee-paid `PlaceOrder` can strand paid orders with no refund - (File: `programs/marginfi/src/instructions/marginfi_account/order.rs`)

### Summary
`marginfi_account_place_order` charges the user an upfront, non-refundable SOL fee (transferred to `global_fee_wallet` via `PlaceOrder::transfer_flat_fee`) and requires the protocol be unpaused at placement time. The order's later execution instructions, `StartExecuteOrder` and `EndExecuteOrder`, independently re-check `!group.load()?.is_protocol_paused()`. This reproduces the exact bug class from the external report: a two-phase flow where the fee is paid up front in phase 1 (unpaused) but phase 2 (the actual execution, gated by market/trigger conditions) can be blocked by an admin pause, with no built-in compensation for the wasted fee or the market exposure the order was meant to protect against.

### Finding Description
`PlaceOrder` requires the group to be unpaused and charges a flat fee before creating the `Order` account: [1](#0-0) [2](#0-1) 

Execution of that order later happens via `StartExecuteOrder`/`EndExecuteOrder`, both of which also gate on the same pause check: [3](#0-2) [4](#0-3) 

`EndExecuteOrder` further enforces a slippage/max-fee constraint against the account's live health at execution time: [5](#0-4) 

If the protocol is panic-paused (admin/pause-delegate action, up to 6 hours per the `PanicState::PAUSE_DURATION_SECONDS` constant) while a placed stop-loss/take-profit order's trigger condition is met, `StartExecuteOrder`/`EndExecuteOrder` will revert with `ProtocolPaused` for the entire pause window: [6](#0-5) 

The only permitted-during-pause exceptions are forced deleverage and admin-initiated bankruptcy handling — regular order execution is explicitly listed as blocked: [7](#0-6) 

There is no refund mechanism for the flat order-placement fee if the order later fails to execute (e.g., because market conditions moved past the `max_slippage`/`max_fee` bounds while paused, causing a permanent `EndExecuteOrder` revert once unpaused). `CloseOrder` lets the user reclaim only account rent, not the fee, and has no pause-aware compensation path: [8](#0-7) 

### Impact Explanation
This is the same structural flaw the external report flags: a fee is collected for a service (protective stop-loss/take-profit execution) whose actual delivery can be blocked by an unrelated, unpaid-for admin pause, with the user having no way to recover the fee or the position protection they paid for. During the pause window the user's leveraged position remains exposed with no working stop-loss/take-profit, and once the pause ends, the trigger's slippage bound (`slippage_frac`/`max_fee_frac` in `end_execute_order`) may make the order permanently unexecutable, effectively voiding the paid-for order while offering no automated refund. This can lead to unrecovered market losses on the user's collateral position plus a wasted, non-refunded fee — a concrete loss of funds for an unprivileged user in a core margin-account path.

### Likelihood Explanation
Requires the `global_fee_admin`/`pause_delegate_admin` to trigger `panic_pause` (an intended emergency action, not attacker-controlled) coinciding with an active order whose trigger condition is met during the pause window. Given pauses can last up to 6 hours and are meant to be invoked during exactly the kind of market stress (oracle manipulation, exploit response) that would also cause stop-loss/take-profit triggers to fire, the overlap is plausible rather than purely theoretical, though it depends on external market timing and is not directly exploitable by an attacker at will.

### Recommendation
Reconsider the strict `ProtocolPaused` gate on `StartExecuteOrder`/`EndExecuteOrder` for orders that were placed (and fee-paid) prior to the pause. Options include: allowing execution of pre-existing orders to proceed during pause (similar to how deleverage/bankruptcy are carved out as pause exceptions), or building an explicit, permissionless refund path for orders that fail to execute due to a pause window, so users aren't left holding a paid, undeliverable order with position risk unmitigated.

### Proof of Concept
1. User calls `marginfi_account_place_order` while the protocol is unpaused; the flat fee is transferred to `global_fee_wallet` per `PlaceOrder::transfer_flat_fee` (`order.rs:568-579`), and an `Order` account is created with a stop-loss/take-profit trigger.
2. Market price moves such that the order's trigger condition is satisfied.
3. Before a keeper/user can call `marginfi_account_start_execute_order`/`marginfi_account_end_execute_order`, `global_fee_admin` or `pause_delegate_admin` calls `panic_pause`.
4. Any attempt to call `StartExecuteOrder`/`EndExecuteOrder` reverts with `MarginfiError::ProtocolPaused` due to the `!group.load()?.is_protocol_paused()` constraints (`order.rs:662`, `order.rs:728`), for up to `PanicState::PAUSE_DURATION_SECONDS` (6 hours).
5. If the underlying position continues moving adversely during the pause, once the pause ends the `slippage_frac`/`max_fee_frac` check in `end_execute_order` (`order.rs:396-421`) may cause execution to permanently fail, leaving the user with a wasted order fee and an unprotected position that already lost value — with no refund instruction available (only `CloseOrder`, which returns rent, not the fee).

### Blocked while paused

All normal user flows are disabled:

- Deposit, Borrow, Withdraw, Repay (both native banks and integration banks — Kamino, Drift,

- Order placement / order flows
- Account transfer
- Classic liquidation (`LendingAccountLiquidate`)

- Permissionless bad-debt settlement (`HandleBankruptcy` when called by a non-admin, even on banks
