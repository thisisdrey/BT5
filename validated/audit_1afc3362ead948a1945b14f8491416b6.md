Audit Report

## Title
Snowbridge relayer reward claims are permanently cleared from storage before the XCM-based payout to the beneficiary is confirmed executed - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`pallet-bridge-relayers::do_claim_rewards` removes the relayer's pending reward from `RelayerRewards` as soon as `T::PaymentProcedure::pay_reward` returns `Ok(())`. For the Snowbridge reward path, `pay_reward` is implemented by `PayAccountOnLocation::pay_reward`, which returns `Ok(())` once the `DepositAsset` XCM has merely been validated and enqueued for delivery to AssetHub, with no confirmation that the remote `DepositAsset` execution actually succeeds.

## Finding Description
`do_claim_rewards` takes the reward balance out of `RelayerRewards` inside a `try_mutate_exists` closure, calls `T::PaymentProcedure::pay_reward`, and only reverts the storage removal if `pay_reward` returns `Err`; on `Ok(())` it commits the removal and emits `RewardPaid`: [1](#0-0) 

For `BridgeReward::Snowbridge`, `pay_reward` is delegated to `snowbridge_core::reward::PayAccountOnLocation::pay_reward`, which builds an XCM containing `UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, and `DepositAsset` targeting AssetHub, and returns `Ok(())` purely based on `validate_send` succeeding and `XcmSender::deliver(ticket)` succeeding — i.e., on successful local queuing of the message, not on remote execution: [2](#0-1) 

The `bp_relayers::PaymentProcedure` trait used here has no async status-check/retry mechanism, unlike `frame_support::traits::tokens::pay::Pay`, which explicitly separates `pay` (returns an id) from `check_payment` (returns `PaymentStatus`) precisely because payment execution can be asynchronous/remote: [3](#0-2) 

`pallet-treasury` uses that pattern to only clear its `Spends` storage entry after `check_payment` reports `Status::Success`, retaining the entry (and allowing retry via `Failed` state) if the remote/off-chain payment did not conclude successfully: [4](#0-3) 

`bp_relayers::PaymentProcedure::pay_reward` has no equivalent `check_payment`/status concept at all: [5](#0-4) 

Because the local success condition (`validate_send` + `charge_fees` + `deliver`) is entirely decoupled from remote success (AssetHub barrier/trust config for the reserve asset, weight limits, beneficiary existential deposit, sovereign/reserve pot funding), any failure on the AssetHub side after message delivery results in the relayer's reward already being irreversibly removed from `RelayerRewards` and a `RewardPaid` event already emitted, with no funds actually delivered to the beneficiary and no retry path exposed by the pallet.

## Impact Explanation
This violates the invariant that bridge reward payouts must settle exactly once to the rightful beneficiary and amount. A relayer who legitimately earned a reward can have their internal accounting entry deleted permanently while the actual value transfer to the beneficiary fails on the remote (AssetHub) leg, resulting in a silent, permanent loss of the relayer's earned reward with no local record and no retry mechanism. This falls under the "duplicate/incorrect settlement" and "permanent user-fund or bridge-state lock" impact categories, and degrades the relayer incentive structure underpinning Snowbridge message delivery.

## Likelihood Explanation
No malicious or privileged actor is needed — any relayer with a legitimate reward calling `claim_rewards`/`claim_rewards_to` triggers `do_claim_rewards`, which is a public, unprivileged extrinsic path. The failure trigger (AssetHub-side execution failure post-delivery, e.g., beneficiary account not meeting existential deposit, reserve/trust misconfiguration, or transient congestion) depends only on conditions outside BridgeHub's control at the time `pay_reward` runs, making this readily and repeatably reproducible without any special privilege.

## Recommendation
Do not finalize/remove the `RelayerRewards` entry based solely on successful XCM delivery. Adopt an asynchronous payment pattern analogous to `pallet-treasury`'s `Pay`/`check_payment`/`PaymentState`: track an attempted-payment identifier/state for the Snowbridge reward path, and only remove the `RelayerRewards` entry once execution success on AssetHub is confirmed (e.g., via a receipt or reporting mechanism), with a defined retry/failure path if remote execution does not succeed.

## Proof of Concept
1. Set up a scenario where the beneficiary account passed to `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` does not meet AssetHub's existential deposit for the reserve asset (or otherwise causes `DepositAsset` to fail on execution).
2. A relayer with a nonzero `RelayerRewards` entry calls `claim_rewards_to`.
3. `do_claim_rewards` calls `PayAccountOnLocation::pay_reward`, which succeeds in `validate_send`, `charge_fees`, and `XcmSender::deliver`, returning `Ok(())` per `bridges/snowbridge/primitives/core/src/reward.rs` lines 145-150.
4. `try_mutate_exists` commits, deleting the `RelayerRewards` entry and emitting `RewardPaid`.
5. On AssetHub, `DepositAsset` traps/fails during execution of the delivered XCM, so the beneficiary receives no funds.
6. Result: `RelayerRewards` shows the claim as fully settled while no tokens were delivered — permanent loss with no retry entry point in `pay_reward`/`PaymentProcedure`.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
