Audit Report

## Title
`process_delivery_receipt` pays relayer reward and settles pending order regardless of on-chain execution outcome (`success` field never checked) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event log carries a `success: bool` field indicating whether the message actually executed successfully on Ethereum [3](#0-2) . `Pallet::process_delivery_receipt` never reads or checks this field: it unconditionally pays the relayer reward from `order.fee` and removes the `PendingOrder`, treating the receipt as final settlement regardless of whether the underlying message actually succeeded [1](#0-0) .

## Finding Description
The pallet's doc comment states the intended flow explicitly: "When the message has been verified **and executed**, the relayer will call the extrinsic `submit_delivery_receipt`" to fetch the pending order, pay reward, and remove the order [4](#0-3) . This makes clear that settlement is meant to be gated on actual successful execution, which is what `success` is designed to convey.

In `process_delivery_receipt`, the only guards are: (1) `receipt.gateway == T::GatewayAddress::get()`, and (2) `PendingOrders::<T>::get(nonce)` existing [5](#0-4) . After these checks, the function unconditionally calls `T::RewardPayment::register_reward` when `order.fee > 0` and then unconditionally calls `<PendingOrders<T>>::remove(nonce)` [6](#0-5) . The `receipt.success` field, though correctly decoded from the verified log in `DeliveryReceipt::try_from` [7](#0-6) , is never referenced anywhere in the settlement logic. `T::Verifier::verify` and the gateway/nonce checks only establish that a genuine log was emitted by the known Gateway contract for a given nonce — they say nothing about whether the dispatched message actually executed successfully on Ethereum. As a result, a message that reverted/failed on Ethereum (emitting `success: false`) still results in full reward payout to the relayer and permanent, irreversible deletion of the `PendingOrder` — identical treatment to a genuinely successful delivery.

## Impact Explanation
This is a public-entrypoint (`submit_delivery_receipt`, callable by any signed relayer) accounting flaw causing settlement to proceed without verifying the actual execution outcome it is designed to gate on. Relayer rewards (`order.fee`) are paid and `PendingOrders` state — the sole record preventing double-claiming/tracking pending settlement — is deleted regardless of the true success value, matching "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" from the impact gate. This also permanently forecloses any retry/compensation path for failed messages, since the `PendingOrder` record is deleted on the first receipt regardless of outcome.

## Likelihood Explanation
Likelihood is high: `success` is a real, decoded field of a genuine event log; any relayer submitting a completely legitimate, correctly-proven `InboundMessageDispatched` log with `success: false` (an outcome fully reachable by an ordinary failed dispatch on the Ethereum side, not requiring any malicious actor) will still trigger full reward payment and order removal, because no code path distinguishes `success: true` from `success: false`. No privileged, malicious, or off-repo actor is needed — a normal relayer submitting a legitimately verified but failed-delivery receipt is sufficient.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: if `true`, proceed with the existing reward payment and `PendingOrders::remove`; if `false`, skip/adjust the reward payout and handle the order distinctly (e.g., emit a "delivery failed" event, and either remove it via a separate state transition or retain it for retry/governance handling), so that payout and settlement state track the actual on-chain execution outcome as the module's own documentation specifies.

## Proof of Concept
1. `do_process_message` queues a message with `order.fee > 0`, inserting `PendingOrders::<T>::insert(nonce, order)` [8](#0-7) .
2. On Ethereum, the dispatch fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits this genuine log via `submit_delivery_receipt` [9](#0-8) ; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` correctly decodes `success: false`.
4. `process_delivery_receipt` checks only gateway match and pending-order existence, then unconditionally pays `order.fee` and removes the order [10](#0-9)  — the relayer is rewarded and the order permanently cleared despite the message having failed on Ethereum.

		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward

					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
