### Title
Unchecked attacker-controlled array-length field causes unbounded memory allocation in TVM precompiled-contract ABI decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Pillow ICO bug is a classic "declared size taken from untrusted input is used directly to size a memory allocation, without validating it against the actual available data," leading to a memory-consumption DoS. The same pattern exists in java-tron's TVM precompiled-contract data decoders, which extract an array length directly from attacker-supplied call data words and use it to size a Java array before any bound check against the actual remaining call-data size.

### Finding Description
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read a length value from the raw ABI-encoded `data`/`words` supplied in a TVM `CALL` to a precompiled contract address, and immediately allocate an array of that length: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `len` is derived from `words[offset].intValueSafe()` — a 256-bit value taken from the caller's own call data and coerced into an `int` — and is used directly as the size of a new `byte[len][]` array (`extractBytesArray`/`extractSigArray`) or `byte[][]` (`extractBytes32Array`). There is no check that `len` is consistent with the actual number of words remaining in `data`/`words` before the array is allocated (only `offset > words.length - 1` is checked in `extractBytesArray`/`extractSigArray`, and `extractBytes32Array` has no bound check at all). This mirrors the ICO DoS root cause: a size field taken from the input container is trusted for allocation sizing instead of being validated against the real, bounded amount of available data.

Any contract execution that reaches a precompiled contract using these helpers (e.g., multi-signature / batch-validate style precompiles) can pass a crafted length word (up to `Integer.MAX_VALUE`) to force allocation of a huge Java array of references before any of the loop body executes or any exception is thrown for out-of-range access.

### Impact Explanation
An attacker who can submit a transaction that triggers a `CALL`/`STATICCALL` to the affected precompiled contract with attacker-controlled call data can force the node to attempt to allocate an oversized array (up to ~2^31 references), which can throw `OutOfMemoryError` or otherwise cause severe GC pressure/memory exhaustion on validating/full nodes processing the transaction. This can crash or stall node processing — a denial-of-service condition consistent with the "High" severity classification of the analog Pillow bug (memory-consumption DoS from unchecked declared size).

### Likelihood Explanation
The path is reachable by any unprivileged transaction sender/contract deployer capable of invoking a `TriggerSmartContract` that performs a `CALL` to the precompiled-contract address using these decoding helpers, requiring no special privileges — only a single crafted transaction with a manipulated ABI length word.

### Recommendation
Bound-check the extracted `len` against the actual remaining length of `data`/`words` (as already partially done for `offset`) before allocating `byte[len][]`, rejecting or truncating the request when `len` exceeds what the supplied call data can possibly contain, similar to the `verifyLength` bound-checking pattern already used in `RLP.decode`.

### Proof of Concept
Not independently executed; based on static analysis of `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, where `len` is taken unchecked from an attacker-supplied `DataWord` and used to size the allocation. I was unable to fully trace, within the available iterations, which specific precompiled contract's `execute()` calls these helpers and whether that contract's `getEnergyForData` energy cost bounds `len` before this allocation occurs — this should be verified by inspecting the callers of these three methods in `PrecompiledContracts.java` (e.g., the batch/multi-sign validation contract) and its associated energy-cost function.
