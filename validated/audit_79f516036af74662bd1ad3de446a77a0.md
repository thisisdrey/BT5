Confirmed: the chunk push path (`process_pushed_stacker_db_chunks` → `StackerDBSyncResult::from_pushed_chunk` → `try_replace_chunk`) uses the untrusted `contract_id` field from the attacker-controlled `StackerDBPushChunkData` envelope to select which StackerDB's slot-signer table to check against, while the actual cryptographic commitment (`SlotMetadata::auth_digest`) never includes that contract identifier. Combined with the fact that the `.signers-X-1/2/3` boot contracts assign identical `(signer → slot_id)` mappings for a given signer set (confirmed by `signers_db_get_slots` test and `signers.clar`'s single `stackerdb-get-signer-slots-page` list reused by every message-lane contract), this allows any remote peer to take a chunk it observed being gossiped for one signer message lane and re-post it as a `StackerDBPushChunk` claiming a different lane's `contract_id`, causing the node to accept and store it there too.

### Title
Cross-Contract StackerDB Chunk Signature Replay Due to Missing Contract Binding in `SlotMetadata::auth_digest` - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` binds a chunk's signature only to `(slot_id, slot_version, data_hash)` and never to the identity of the StackerDB smart contract it is being written into. [1](#0-0)  Because the `.signers-<set>-1`, `.signers-<set>-2`, and `.signers-<set>-3` boot contracts (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit` lanes) all derive their slot ↔ signer mapping from the same underlying signer list for a given signer set [2](#0-1) , a signer's slot_id is identical across all three lane contracts, verified by the `signers_db_get_slots` test which shows the exact same slot list returned for every `message_id` in a signer set. [3](#0-2)  Any remote peer that observes a validly signed `StackerDBChunkData` gossiped for one lane can re-wrap it in a `StackerDBPushChunk` message that declares a *different* lane's `contract_id`, and the receiving node's write path will accept and store it there.

### Finding Description
The chunk write path — reached either via the p2p push handler `handle_unsolicited_StackerDBPushChunk` / `process_pushed_stacker_db_chunks` or via the RPC `POST /stackerdb chunk` handler — validates a chunk by looking up the slot's expected signer *within the smart_contract_id supplied in the untrusted message envelope*, then calls `SlotMetadata::verify()`: [4](#0-3) 

`try_replace_chunk`, used by both the p2p sync/push path and the HTTP `poststackerdbchunk` endpoint, performs the identical check purely against the `smart_contract` parameter it is called with: [5](#0-4) 

The signature itself, however, is computed over `auth_digest = SHA512/256(slot_id || slot_version || data_hash)`, with no domain separation for the target contract: [1](#0-0) 

The contract identifier is carried only in the outer, unsigned `StackerDBPushChunkData.contract_id` field: [6](#0-5)  — this field is fully attacker-controlled and is exactly the value used to select which contract's slot-signer table to check the signature against, in `from_pushed_chunk`/`process_pushed_stacker_db_chunks`: [7](#0-6) 

Since the `.signers-<X>-1/2/3` lane contracts (BlockResponse, StateMachineUpdate, BlockPreCommit) are all populated from the identical `stackerdb-get-signer-slots-page` list for a given signer set, every signer occupies the *same* `slot_id` in all three contracts: [2](#0-1) 

An attacker who observes any signer's chunk gossiped on lane A (e.g. `.signers-0-1`) can copy that exact `StackerDBChunkData` (unmodified: same `slot_id`, `slot_version`, `sig`, `data`) into a `StackerDBPushChunk` whose `contract_id` names lane B (e.g. `.signers-0-2`), and push it to any remote node. The node resolves the slot-signer for lane B using the same `slot_id`, finds the same signer address, and `SlotMetadata::verify()` succeeds because the digest never referenced which contract it was for — so the chunk is written into lane B's StackerDB slot and re-gossiped to that node's peers as legitimate lane-B data, provided the target slot's stored version in lane B is lower than the replayed chunk's `slot_version` (an easy condition to satisfy, since versions across lanes are independently incremented by the honest signer and are visible to anyone by querying `StackerDBChunkInv`).

At the raw StackerDB storage/relay layer, this write and its propagation to other peers succeed unconditionally — the type-prefix/lane consistency check (`signer_message_payload_matches_lane`) exists only in the higher-level signer-message decoding path in `libsigner`, and is not enforced by the StackerDB storage/replication layer itself. [8](#0-7)  Consequently the underlying protocol invariant that a stored chunk's signature attests to "signer S authorized *this* data for *this specific StackerDB replica*" is broken: the same signature is valid across any StackerDB contract in which the signer happens to occupy the same slot_id, regardless of the application-level semantics the two contracts carry.

### Impact Explanation
This breaks the equality that "a stored StackerDB chunk was authorized, by its owning signer, specifically for the contract/lane it is stored in." A remote, unauthenticated peer (no private key needed — only relaying observed public gossip) can force cross-lane writes/propagation of a chunk into a StackerDB contract it was never signed for, polluting that lane's slot content and forcing it to be replicated network-wide as if legitimate for that lane. This corresponds to "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged[-context] data" per the accepted-impact categories, even though the concrete downstream damage in the current miner-facing consumer (`libsigner`'s lane/type-prefix filter) is bounded because a mismatched type-prefix byte causes the higher-level `SignerMessage` decode to discard the payload. The underlying protocol-level guarantee at the StackerDB layer is nonetheless violated, and any future or alternate consumer of a `.signers-X-Y` StackerDB contract that does not perform independent type/lane validation (or any other StackerDB application built on the same `libstackerdb` primitive with slot-reuse across contracts) is directly exposed to unauthorized data injection.

### Likelihood Explanation
Exploitation requires no privileged key: the attacker only needs to observe a single signer's real, publicly-gossiped chunk (trivial, since gossip is broadcast by design) and re-transmit it while claiming a different, sibling contract_id. The precondition (identical slot_id assignment across `.signers-X-{1,2,3}`) is a structural property of the current boot-contract slot allocation and always holds within a signer set, and the destination lane's version-freshness requirement is trivially satisfiable by monitoring `StackerDBChunkInv` gossip.

### Recommendation
Bind the StackerDB contract identifier into the signed digest. Modify `SlotMetadata::auth_digest()` (and the corresponding `sign`/`verify` call sites) to also hash in the `QualifiedContractIdentifier` of the target StackerDB, so a signature is only valid for the specific contract it was produced for: [1](#0-0)  This requires plumbing the contract id through `StackerDBChunkData::sign`/`verify`/`recover_pk` and all call sites (`try_replace_chunk`, `validate_received_chunk`, the RPC handler, and the signer/miner clients that sign outgoing chunks).

### Proof of Concept
1. Observe (via normal StackerDB gossip/chunk-inv download) a validly signed `StackerDBChunkData` for signer S at `slot_id = k`, `slot_version = v`, in contract `.signers-0-1` (BlockResponse lane).
2. Construct a `StackerDBPushChunk` message with `contract_id = .signers-0-2` (StateMachineUpdate lane) and `chunk_data` set to the *exact same* `slot_id`, `slot_version`, `sig`, and `data` bytes observed in step 1 (no cryptographic work required — pure byte copy).
3. Send this `StackerDBPushChunk` to any Stacks node that replicates `.signers-0-2` and currently has a stored version for slot `k` less than `v` (discoverable via `StackerDBChunkInv`).
4. Observe that `PeerNetwork::handle_unsolicited_StackerDBPushChunk` → `process_pushed_stacker_db_chunks` → `try_replace_chunk` accepts and stores the chunk under `.signers-0-2`, because `get_slot_signer(".signers-0-2", k)` resolves to the same signer address S, and `SlotMetadata::verify()` succeeds since the digest carries no contract binding. [9](#0-8)  The node then re-gossips this cross-lane chunk to its own peers as legitimate `.signers-0-2` data.
