### Title
Denial of Service via CREATE2 Address Front-Running Blocks Contract Deployment - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The Sherlock report describes an attacker front-running a proxy's `initialize()` to seize control of a deterministic deployment address before the legitimate deployer can act, permanently denying the intended deployment. The closest reachable analog in java-tron is the CREATE2 deployment path in `Program.createContractImpl()` [1](#0-0) , where the resulting contract address is fully predictable off-chain (`sender ++ salt ++ keccak256(code)`, TRON prefix `0x41`) via `WalletUtil.generateContractAddress2` [2](#0-1) , allowing any unprivileged account to act on that address before the real deploy transaction lands.

### Finding Description
Any account can predict a CREATE2 target address in advance (as demonstrated in the test suite's `getCreate2Addr` helpers) and interact with it before the factory contract executes the real `create2`. In `createContractImpl`, when `getContractState().getAccount(newAddress)` returns a pre-existing (non-contract) account, `contractAlreadyExists` is computed via `isContractExist(existingAccount, getContractState())` [3](#0-2) . If that pre-existing account is not yet recognized as a contract, the deploy path continues by mutating it in place (`updateAccountType`, `clearDelegatedResource`) [4](#0-3) . This is precisely the "front-run a deterministic deployment address" bug class named in the report, ported to TRON's CREATE2/TVM address-derivation mechanics rather than a Solidity proxy `initialize()`.

### Impact Explanation
I was not able to fully verify, within the available tool budget, whether the current mitigations (`isContractExist`, `clearDelegatedResource`, and the `freezeV2Check` gate referenced in `Program.java`) fully close this class of issue for all pre-existing-account states (e.g., an account with active FreezeV2 delegated resources or pending unfreeze entries at the predicted address). The test suite (`FreezeTest.testFreezeAndUnfreezeToCreate2Contract`, `testCreate2SuicideToBlackHole`, `testCreate2SuicideToAccount`) explicitly exercises "freeze/delegate resource to a not-yet-deployed CREATE2 address, then deploy" scenarios, which strongly suggests this exact front-running class was previously identified and is now deliberately tested — but I could not read the full `freezeV2Check`/`createContractImpl` interaction (call site gating deployment) to confirm whether an attacker can still force deployment to permanently fail (denial of service) by leaving unresolved delegated/frozen resources at the predicted address, rather than just losing funds or having state cleared.

### Likelihood Explanation
Reaching this path only requires an unprivileged account with TRX to: (1) observe a pending CREATE2 factory-trigger transaction in the mempool, (2) compute the deterministic target address using the known TRON CREATE2 formula, and (3) submit a competing transaction (transfer/freeze/delegate) to that address before the real deployment executes. This requires no special privilege beyond normal transaction broadcasting.

### Recommendation
Because I could not confirm the actual runtime behavior of `freezeV2Check` and the full gating logic around `createContractImpl` in this session, I cannot assert with certainty that an exploitable, high/medium-severity DoS or fund-freezing condition currently exists versus being already mitigated by the tested `clearDelegatedResource`/`isContractExist` logic. A follow-up review should specifically read `freezeV2Check`'s call site and the `contractAlreadyExists` branch to determine whether an attacker can make legitimate CREATE2 deployment revert indefinitely (DoS) by pre-loading the predicted address with resources that `createContractImpl` refuses to clear/overwrite automatically.

### Proof of Concept
Not concretely established — the existing test cases (`FreezeTest.java` lines 372-412, 489-548) already simulate the "freeze/delegate to a not-yet-deployed CREATE2 address" scenario and assert specific pass/fail behavior, but a full walkthrough of whether these assertions represent a genuine unresolved DoS/impact (vs. correctly-mitigated behavior) could not be completed within the available investigation budget.   private void createContractImpl(DataWord value, byte[] programCode, byte[] newAddress,
      boolean isCreate2) {
    byte[] senderAddress = getContextAddress();

    if (logger.isDebugEnabled()) {
      logger.debug("creating a new contract inside contract run: [{}]",
          Hex.toHexString(senderAddress));
    }

    long endowment = value.value().longValueExact();
    if (getContractState().getBalance(senderAddress) < endowment) {
      stackPushZero();
      return;
    }

    AccountCapsule existingAccount = getContractState().getAccount(newAddress);
    boolean contractAlreadyExists = existingAccount != null;

    if (VMConfig.allowTvmConstantinople()) {
      contractAlreadyExists =
          contractAlreadyExists && isContractExist(existingAccount, getContractState());
    }
    Repository deposit = getContractState().newRepositoryChild();
    if (VMConfig.allowTvmConstantinople()) {
      if (existingAccount == null) {
        deposit.createAccount(newAddress, "CreatedByContract",
            AccountType.Contract);
      } else if (!contractAlreadyExists) {
        existingAccount.updateAccountType(AccountType.Contract);
        existingAccount.clearDelegatedResource();
        deposit.updateAccount(newAddress, existingAccount);
      }

  public static byte[] generateContractAddress2(byte[] address, byte[] salt, byte[] code) {
    byte[] mergedData = ByteUtil.merge(address, salt, Hash.sha3(code));
    return Hash.sha3omit12(mergedData);
  }
