Java-tron's `Exchange` module (Bancor-style TRC10↔TRC10/TRX AMM pairs, exposed to any unprivileged account via `ExchangeCreateContract`) has a directly analogous bug class to the Vader "first LP sets extreme rate" issue.

### Title
Exchange creator can set an arbitrarily skewed first/second token ratio, corrupting Bancor-formula math and permanently freezing/breaking the trading pair - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java)

### Summary
`ExchangeCreateActuator` lets any account create a token-pair exchange and unilaterally set both `first_token_balance` and `second_token_balance` (i.e., the pool's initial "price"/ratio), the same role the "first LP" plays in the Vader report.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks that each side's balance is `> 0` and `<= dynamicStore.getExchangeBalanceLimit()`; it never bounds the *ratio* between the two sides [1](#0-0) . This means an attacker can create a pair with e.g. `firstTokenBalance = 1` and `secondTokenBalance = balanceLimit`, exactly mirroring the "first depositor sets extreme rate" pattern from the report.

That skewed ratio then feeds the Bancor-style relay math in `ExchangeCapsule.transaction()` / `ExchangeProcessor`, which by default runs with unchecked double arithmetic and raw (non-`Math.*Exact`) long updates: [2](#0-1) 

The core formula divides `quant` by `newBalance` and raises to a fractional power, and the inverse formula divides `supplyQuant` by a *local, reset-every-call* `supply` constant: [3](#0-2) 

With an extremely small `firstTokenBalance` (e.g. `1`), even modest trade sizes make `quant/newBalance` huge, which can push the `Math.pow`/double computation to `Infinity`/`NaN` or produce a `long` cast that silently truncates/overflows since the non-hardened path updates balances with plain `+`/`-` rather than `addExact`/`subtractExact` (only `hardenedCalc` does the exact-math path): [4](#0-3) 

The presence of `SafeExchangeProcessor`, `StrictMathWrapper`, and the `allowHardenExchangeCalculation`/`hardenedCalc` governance-gated code paths [5](#0-4)  confirms this exact overflow/precision class of bug was identified for the Exchange math, but the fix is opt-in via a committee proposal (`allowHarden()`), not the default behavior, so the legacy `ExchangeProcessor`/plain-arithmetic path remains reachable and exploitable whenever hardening is not enabled on chain, and even when it is, `ExchangeCreateActuator.doValidate()` itself still applies no ratio sanity check regardless of the harden flag.

### Impact Explanation
Once a pool's ratio is set to an extreme value at creation, subsequent `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` calls that depend on `firstTokenBalance`/`secondTokenBalance` proportions can be pushed into corrupted states (silently wrapped/truncated long balances, or `ArithmeticException`s that make every future call on that pair fail). This can (a) permanently freeze the pair so no legitimate participant can trade, inject, or withdraw from it (DoS of that Exchange's funds), or (b) in the non-hardened legacy path where balances are updated with unchecked arithmetic, produce an inconsistent/unbacked balance for one side of the pool.

### Likelihood Explanation
`ExchangeCreateContract` is fully permissionless - reachable by any signed transaction from any account, requiring only enough balance/asset to fund the two initial deposits and the fixed creation fee. No special privilege, SR/witness status, or committee action is needed to trigger the extreme-ratio state; a single attacker transaction suffices.

### Recommendation
Add a minimum-balance and/or maximum-ratio constraint between `firstTokenBalance` and `secondTokenBalance` in `ExchangeCreateActuator.doValidate()` (analogous to Uniswap's minimum liquidity lock), and make the exact-math/`SafeExchangeProcessor` hardened path (already implemented) the unconditional default rather than an opt-in governance parameter.

### Proof of Concept
1. Attacker account holds a tiny amount of `tokenA` (or TRX) and a very large amount of `tokenB` (up to `getExchangeBalanceLimit()`).
2. Attacker broadcasts `ExchangeCreateContract` with `first_token_balance = 1`, `second_token_balance = exchangeBalanceLimit`.
3. `ExchangeCreateActuator.doValidate()` accepts it since both values are `>0` and `<= balanceLimit` [1](#0-0) .
4. Any subsequent `ExchangeTransactionContract` against this pair drives `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` with an extreme `quant/newBalance` ratio, producing corrupted/overflowed results via the non-`Exact` arithmetic in `ExchangeCapsule.transaction()` [6](#0-5) , permanently breaking further trading/injection/withdrawal on that pair.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
