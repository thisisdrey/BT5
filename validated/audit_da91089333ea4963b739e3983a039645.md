### Title
Missing 256-contract bound enforcement in `update_from_stacker_db_handshake_data` allows unbounded StackerDB replication list growth - (File: stackslib/src/net/chat.rs)

### Summary
`ConversationP2P::update_from_stacker_db_handshake_data` unconditionally clones the entire attacker-supplied `smart_contracts` vector from a `StackerDBHandshakeAccept`/`StackerDBHandshake` message into `self.db_smart_contracts` with no check against the documented protocol bound of 256 StackerDB sets. Any peer that a node performs an outbound handshake against (or which sends this message inbound while supporting the stackerdb service flag) can force the local node to store and later repeatedly iterate an oversized contract-identifier list.

### Finding Description
The claimed equality is: `smart_contracts.len() <= 256` (the documented protocol bound in `net/stackerdb/mod.rs`) should hold for any stored `db_smart_contracts`. The code that stores this value is: [1](#0-0) 

This function performs `self.db_smart_contracts.clone_from(&stacker_db_data.smart_contracts)` with no length validation whatsoever — the equality is never checked, so the fault is real: any attacker-controlled `smart_contracts` vector of arbitrary length within wire-message size limits is accepted verbatim.

The reachable path is the P2P handshake accept flow: when the local node walks out to a peer (or accepts one) and both sides advertise `supports_stackerdb()` in their services bitfield, the reply is built as `StacksMessageType::StackerDBHandshakeAccept(... StackerDBHandshakeData { smart_contracts: ... })`: [2](#0-1) 

An attacker-controlled peer being handshaked with can populate `smart_contracts` with far more than 256 entries in its reply. When the local node processes that accept message, `update_from_stacker_db_handshake_data` is invoked and stores the full list unbounded by the 256 cap that the protocol comment claims. The only real ceiling on the vector's size is the overall P2P message size limit (`MAX_MESSAGE_LEN`/preamble payload length checks enforced during message deserialization), not any StackerDB-specific cap — so the attacker can inflate the list to whatever a single P2P frame permits (tens of thousands of `QualifiedContractIdentifier` entries), which is orders of magnitude beyond the intended 256-set bound.

This stored list is later read via `get_stackerdb_contract_ids()` and iterated during StackerDB neighbor/replica lookups, so each malicious peer imposes a per-lookup iteration cost proportional to the oversized list, repeatable on every subsequent StackerDB sync/neighbor-selection pass touching that peer's state.

### Impact Explanation
A remote, unprivileged peer (one the node walks to, or one it accepts a handshake from) can cause the local node to store and repeatedly iterate an attacker-controlled `Vec<QualifiedContractIdentifier>` that is far larger than the protocol-mandated 256-entry bound, without any signature/authorization requirement beyond a normal handshake. This is a bounded (by max message size) but excessive per-peer memory/compute cost inflicted on every subsequent StackerDB-related lookup involving that conversation — matching the "bounded compute DoS on a read endpoint" category. It does not corrupt consensus state or allow forged writes to StackerDB chunks themselves; the effect is confined to the in-memory `ConversationP2P::db_smart_contracts` field of the connection object on the victim node.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to run a normal P2P peer, advertise the `supports_stackerdb` service flag, and be walked-to (or handshake inbound) by the target node — no secret, no privileged role, no existing StackerDB slot ownership required. Cost to the attacker is a single crafted message. The condition is repeatable on every handshake/reconnect cycle with that peer, and the target's own `ibd` state does not block this path because the vulnerable store (`update_from_stacker_db_handshake_data`) fires whenever an accept message is *received*, not merely when the local node itself replies during `ibd`.

### Recommendation
Enforce the documented 256-contract bound explicitly in `update_from_stacker_db_handshake_data` (or in the codec deserialization of `StackerDBHandshakeData`), rejecting/truncating oversized `smart_contracts` lists before storing them in `self.db_smart_contracts`, e.g. return an error/drop the connection if `stacker_db_data.smart_contracts.len() > STACKERDB_MAX_SETS` (256).

### Proof of Concept
Rust test in `stackslib::net::chat`:
1. Construct a `ConversationP2P` in the test harness (as done in existing `chat.rs` unit tests).
2. Build a `StackerDBHandshakeData` with `smart_contracts` populated with 100,000 synthetic `QualifiedContractIdentifier` entries (well within the P2P frame size limit, at ~25-40 bytes per entry).
3. Call `conversation.update_from_stacker_db_handshake_data(&stacker_db_data)`.
4. Assert `conversation.get_stackerdb_contract_ids().len() == 100_000`, demonstrating no cap enforcement against the documented 256-entry protocol bound.
