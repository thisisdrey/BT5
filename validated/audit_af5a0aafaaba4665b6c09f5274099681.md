### Title
Unprivileged shareholder can grief loan funding and redemption approvals by cheaply consuming shared `idleLiquidity` via `requestDeposit`/`cancelDepositRequest` cycling - (File: tare-io__tare-contracts/contracts/PortfolioVault.sol)

### Summary
`PortfolioVault.fundLoan`/`fundLoans` and `approveRedemption` are gated on a shared, globally-consumable resource — `idleLiquidity` (vault USDC balance minus `totalPendingDepositAssets` minus `totalClaimableRedeemAssets`). Any registered shareholder can inflate `totalPendingDepositAssets` via `requestDeposit` to drive `idleLiquidity` to zero, causing these operations to revert for the Portfolio Manager and other shareholders, and can then reclaim their capital at will via `cancelDepositRequest`, repeating the attack at only gas cost. This mirrors the OptimismPortal `ResourceMetering` bug class: a shared per-period/global capacity limit that an unprivileged actor can consume cheaply and reversibly to censor other legitimate users of the same resource.

### Finding Description
`requestDeposit` [1](#0-0)  is callable by any account that passes `_requireInvestor` (i.e. any registered `SHAREHOLDER_ROLE` holder), pulls `assets` USDC from the caller, and increments `pendingDepositAssets[controller]` and the global `totalPendingDepositAssets` counter.

Per the vault spec, `idleLiquidity()` is defined as `usdc.balanceOf(vault) - totalPendingDepositAssets - totalClaimableRedeemAssets`, and both `fundLoan`/`fundLoans` and `approveRedemption` require the requested amount to be `<= idleLiquidity()`, reverting with `InsufficientLiquidity` otherwise [2](#0-1) . This is confirmed by the test suite, which shows `fundLoan` reverting once `totalPendingDepositAssets` consumes the idle balance [3](#0-2) .

`cancelDepositRequest` is documented as "always available regardless of NAV state" and NAV-neutral, returning the USDC to the receiver and decrementing `totalPendingDepositAssets` [4](#0-3) , meaning a shareholder can inflate then immediately deflate the counter at will.

This produces the same root cause as the OP `ResourceMetering` bug: a global, easily-refillable/consumable capacity variable (`params.prevBoughtGas` in OP; `totalPendingDepositAssets`/`idleLiquidity` in Tare) gates a shared operation (`depositTransaction` in OP; `fundLoan`/`approveRedemption` in Tare) for *all* other users, and the attacker's cost of temporarily monopolizing that capacity is near-zero (the deposit is not spent, merely locked and later reclaimed via `cancelDepositRequest`, at the cost of gas only).

### Impact Explanation
An unprivileged shareholder — not a guardian, admin, or portfolio manager — can, at will and repeatedly, block:
- `fundLoan`/`fundLoans` (loan disbursement/funding to borrowers) for every loan the Portfolio Manager is trying to originate, and
- `approveRedemption` (approvals that unlock withdrawal claims for all other shareholders).

Both are explicitly listed allowed impacts ("Material production DoS ... that blocks funding, disbursement, withdrawals, claims, NAV-sensitive approvals, or loan settlement across users"). The attacker does not need any privileged role; only `SHAREHOLDER_ROLE`, which is the standard role granted to any onboarded investor. The griefing is essentially free — the attacker's own capital is never lost, only temporarily parked, and can be withdrawn via `cancelDepositRequest` the moment the manager attempts (and fails) to fund a loan or approve a redemption, then re-deposited to repeat the block on the next attempt.

### Likelihood Explanation
Any registered shareholder can execute this without special timing (front-running is not even required — the attacker simply keeps a large pending deposit outstanding at all times, cycling it via cancel/re-request as needed to react to changes in vault balance). The capital requirement is bounded only by the shareholder's own USDC holdings (which they get back), making this a low-cost, high-availability griefing vector rather than a one-off MEV race. The main uncertainty is the precise `idleLiquidity()`/`fundLoan` implementation, which the index did not surface directly (only via spec and tests) — this should be confirmed by reading `contracts/PortfolioVault.sol` in full.

### Recommendation
Do not let `requestDeposit`'s temporary/cancelable pending balance be the sole gate for `fundLoan`/`approveRedemption` liquidity checks. Consider:
- Reserving a portion of vault liquidity independent from freely cancelable pending deposits, or
- Applying a minimum holding period / cooldown before a pending deposit can be cancelled, removing the "consume-then-instantly-reclaim" griefing loop, or
- Allowing the Portfolio Manager to prioritize/queue funding operations ahead of newly arrived pending deposits, similar to how OP's fix moved deposit gas accounting off a single global mutable limit that any actor could race to fill.

### Proof of Concept
1. Vault has `idleLiquidity = X` USDC available; Portfolio Manager is about to call `fundLoan(loanId, X, ...)`.
2. Attacker (a registered shareholder, unprivileged) front-runs or simply maintains standing large pending deposits: calls `requestDeposit(X, attacker, attacker)`, transferring `X` USDC into the vault and incrementing `totalPendingDepositAssets` by `X`.
3. `idleLiquidity()` drops to `0`; Portfolio Manager's `fundLoan`/`fundLoans` call reverts with `InsufficientLiquidity` (as demonstrated in `test_FundLoan_Reverts_WhenPendingDepositsConsumeIdleLiquidity` — showing the exact mechanic, albeit exercised there for test setup rather than attack framing) [5](#0-4) . Any pending `approveRedemption` for other shareholders is similarly blocked.
4. Attacker calls `cancelDepositRequest(attacker, attacker)`, immediately recovering the `X` USDC in full (NAV-neutral, always available).
5. Attacker repeats steps 2–4 indefinitely at only the cost of gas, continuously denying loan funding/redemption approvals to legitimate users.

  function requestDeposit(
    uint256 assets,
    address controller,
    address owner
  ) external nonReentrant whenNotPaused onlyAccountOrOperator(owner) returns (uint256 requestId) {
    require(controller != address(this), InvalidController());
    _requireInvestor(owner);
    _requireInvestor(controller);
    require(assets > 0, ZeroAmount());

    assetToken.safeTransferFrom(owner, address(this), assets);

    pendingDepositAssets[controller] += assets;
    totalPendingDepositAssets += assets;

    emit DepositRequest(controller, owner, 0, msg.sender, assets);
    return 0;
  }
