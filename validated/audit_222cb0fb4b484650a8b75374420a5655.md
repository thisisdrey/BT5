Audit Report

## Title
`ERC20Transactor::withdraw_asset_with_surplus` credits XCM holding with the requested `amount` instead of the checking account's actual balance delta, letting fee-on-transfer/rebasing ERC20 tokens desynchronize the shared checking account and strand other users' deposits - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls `IERC20::transfer(checking_address, amount)` on any arbitrary ERC20 contract matched via `ERC20Matcher`/`AccountKey20ToH160` and, as long as the call does not revert and the boolean return is `true`, unconditionally credits the XCM holding register with the requested `amount` — never the checking account's observed balance delta. [1](#0-0)  The corresponding `deposit_asset_with_surplus` later moves `amount` (carried through `Erc20Credit`) out of the same pooled `TransfersCheckingAccount`, again without checking the account's live balance. [2](#0-1) 

## Finding Description
`ERC20Matcher`, used to match assets for this transactor in `asset-hub-westend`, is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, which accepts any `AccountKey20`-junction location — i.e., any deployed contract address, with no allow-list of "standard" ERC20 implementations. [3](#0-2) 

In `withdraw_asset_with_surplus`, the transactor performs `IERC20::transferCall { to: checking_address, value: amount }` from the user's account, and on success (`!did_revert()` and decoded return `true`) constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — using the value the XCM message requested, not any measured change in the checking account's ERC20 balance. [4](#0-3)  `Erc20Credit` is explicitly documented as not performing runtime-level balance enforcement, relying entirely on the ERC20 contract itself. [5](#0-4)  `deposit_asset_with_surplus` mirrors this by transferring `amount` from the shared `TransfersCheckingAccount` to the beneficiary, again trusting the value carried in holding rather than the checking account's real balance. [6](#0-5) 

Because `TransfersCheckingAccount` is one shared pooled account for all ERC20 transfers of a given asset (confirmed by the `ERC20TransfersCheckingAccount` singleton used across withdraw/deposit flows in the asset-hub-westend integration test), a fee-on-transfer or rebasing ERC20 token can cause the checking account's real balance to be smaller than the sum of `Erc20Credit` values the runtime believes are backed by it. [7](#0-6)  Neither `withdraw_asset_with_surplus` nor `deposit_asset_with_surplus` snapshots or compares the checking account's balance before/after the transfer; the only checks performed are `did_revert()` and the decoded boolean return value, neither of which detects a fee-on-transfer shortfall or a later rebase-driven balance shrink.

Once the checking account's real balance is exhausted below the aggregate outstanding credits, subsequent `deposit_asset_with_surplus` calls for other users' legitimate XCM programs referencing the same asset will fail (`did_revert()` true, decode error, or `transferCall` returning `false`), leaving their holding undeliverable mid-XCM-execution.

## Impact Explanation
This is a public, permissionless denial-of-service / fund-desynchronization condition on the pooled `TransfersCheckingAccount`: an unprivileged user can, via a normal `PolkadotXcm::execute` call referencing an arbitrary ERC20 contract address (permitted by `ERC20Matcher`), desynchronize the runtime's internal `Erc20Credit` bookkeeping from the checking account's real on-chain balance. This causes other, unrelated users' subsequent ERC20 deposits routed through the same checking account to fail/revert, stranding their intended tokens mid-XCM execution — matching the "public underpriced work that … stalls … processing" and fund-lock impact classes for this program.

## Likelihood Explanation
No privileged action, compromised relayer, or leaked key is required. Any user can deploy a fee-on-transfer or rebasing ERC20 contract on the parachain and route it through the ERC20 XCM transactor exactly as demonstrated by the existing `withdraw_and_deposit_erc20s` integration test pattern, which shows a user-supplied, freshly-deployed contract being matched and transferred through `ERC20TransfersCheckingAccount` with no restriction to "standard" fixed-balance semantics. [8](#0-7)  This is fully repeatable and requires no special timing or race condition — only a non-standard token contract and two ordinary XCM executions.

## Recommendation
- In `withdraw_asset_with_surplus`, read the checking account's ERC20 balance before and after the `transfer` call and credit `AssetsInHolding` with the observed delta rather than the requested `amount`.
- In `deposit_asset_with_surplus`, cap the outgoing transfer to the checking account's currently available real balance, or fail closed if insufficient, instead of unconditionally trusting the value carried in the holding register.
- Restrict `ERC20Matcher`/asset registration to ERC20 contracts verified to have standard, non-fee, non-rebasing transfer semantics, or explicitly document this trust assumption if balance reconciliation is not implemented.

## Proof of Concept
1. Deploy a fee-on-transfer ERC20 contract where `transfer(to, amount)` returns `true` but credits `to` with less than `amount` (or a rebasing token that later shrinks `TransfersCheckingAccount`'s balance).
2. User A executes an XCM program via `PolkadotXcm::execute` with `withdraw_asset((EvilToken, amount))` followed by `deposit_asset(..., beneficiary)`. `withdraw_asset_with_surplus` succeeds and credits `AssetsInHolding` with the full `amount` per lines 197-203 of `erc20_transactor.rs`, even though `TransfersCheckingAccount`'s real balance increased by less.
3. Repeat with additional users/amounts to further widen the gap between the checking account's real ERC20 balance and the sum of `Erc20Credit` values recorded across executions.
4. Once the checking account's real balance is exhausted below outstanding credits, a subsequent legitimate `deposit_asset_with_surplus` call for the same asset reverts or returns `false` at lines 270-298, leaving that user's holding undeliverable and their intended ERC20 tokens stuck mid-XCM.

pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
