It only checks that `from` is not one of *my* own addresses [1](#0-0) . ### Title
Relay `CreateRelayRequest`/`CreateRelayResponse` accept attacker-claimed `RelayFromAddr` without binding it to the sender's certified VPN address, allowing relay state poisoning - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` and `handleCreateRelayResponse` derive `from`/`relayFrom` purely from attacker-controlled fields in the `NebulaControl` message (`RelayFromAddr`/`OldRelayFromAddr`) and use that value directly as the key for relay-state bookkeeping (`AddRelay`, `QueryRelayForByIp`, `InsertRelay`), never checking it equals the sending peer's actual, certificate-verified `vpnAddrs`.

### Finding Description
An authenticated Nebula peer `h` (any node that has completed a valid, cert-verified handshake) sends a `Control` message that is routed to `relayManager.HandleControlMsg` and, for `CreateRelayRequest`, into `handleCreateRelayRequest` [2](#0-1) . The function extracts `from := protoAddrToNetAddr(m.RelayFromAddr)` directly from the message body [3](#0-2) . The only sanity check performed is that `from` is not one of the local node's own addresses, i.e. `f.myVpnAddrsTable.Contains(from)` [4](#0-3) . There is no check anywhere in this function that `from == h.vpnAddrs[0]` (the actual, certificate-authenticated identity of the peer that sent the control message).

This `from` value is then used as the trust anchor for establishing relay state: it becomes the `vpnIp` key inserted via `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` [5](#0-4) , and the response is built from and keyed by that same unverified `from` value [6](#0-5) . This mirrors the reported bug class exactly: a value that is supposed to be intrinsically "associated" with the calling party (their own certified vpn address, analogous to the treasury's associated token account) is accepted from attacker input with no strict equality check against the verified identity (`h.vpnAddrs[0]`, analogous to the derived/expected associated account).

By contrast, the codebase does enforce this kind of binding elsewhere — e.g. `handleCreateRelayRequest`'s companion check on the *target* address is legitimate because it is compared against the local node's own certificate-derived table (`f.myVpnAddrsTable`), and the firewall's `Drop()` function strictly binds `fp.RemoteAddr` to `h.vpnAddrs`/`h.networks`, which are derived from the peer's verified certificate [7](#0-6) . The relay-request handler is the one place where an attacker-suppliable field is used as if it were an authenticated identity, without the same class of check.

### Impact Explanation
An authenticated peer can claim `RelayFromAddr` = an arbitrary victim's real VPN address (not its own) when sending a `CreateRelayRequest` to a node that is the intended relay target. The target node will then install relay state (`Relays`/`relayState`) associating that victim address with a relay path through the attacker's `HostInfo`, and will respond with a `CreateRelayResponse` accepting the attacker as though it legitimately fronts for the victim's address. This is remote state poisoning of the relay subsystem: it can corrupt/occupy relay-for-address bookkeeping for a victim address the attacker does not control, potentially causing relay-selection confusion, blocked/hijacked legitimate relay attempts for that victim (denial of relay service), or subsequent relay traffic being associated with the wrong `PeerAddr` in logs/state, undermining the integrity of the peer/relay directory that Nebula's SDN model relies on.

### Likelihood Explanation
Any already-handshaked peer of the target node (which, per Nebula's trust model, only requires possession of a certificate signed by a CA in the same trust pool — not a privileged/special role) can trigger this by sending a single crafted `Control`/`CreateRelayRequest` message with a spoofed `RelayFromAddr`. No race condition, timing, or additional bypass is required beyond having an established encrypted tunnel to the target, which is the normal operating condition for any two mesh peers, including intentionally malicious but certificate-holding nodes relaying through a permissive relay-capable host.

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`/`EstablishRelay` where relevant), require that the claimed `RelayFromAddr` matches one of the sending `HostInfo`'s certificate-verified `vpnAddrs` when the local node is establishing itself as the relay for the initiator (`TerminalType` case), i.e. add an explicit equality/set-membership check `from ∈ h.vpnAddrs` before calling `AddRelay`/updating relay state, mirroring the strict-equality remediation recommended for the associated-token-account issue. Reject and log the message if the check fails, the same way self-address and nil-address checks are already handled in this function.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

	// Make sure remote address matches nebula certificate, and determine how to treat it
	if h.networks == nil {
		// Simple case: Certificate has one address and no unsafe networks
		if h.vpnAddrs[0] != fp.RemoteAddr {
			f.metrics(incoming).droppedRemoteAddr.Inc(1)
			return ErrInvalidRemoteIP
		}
