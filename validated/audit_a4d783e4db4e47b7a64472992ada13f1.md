### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `DepositToken` transfers, permanently blocking new deposits/borrows and collateral top-ups - (File: contracts/Pool.sol)

### Summary
`Pool` tracks each account's deposit tokens and debt tokens in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30`. Any first-time receipt of a `DepositToken` (transfer, `deposit(onBehalfOf)`, or liquidation `seize`) or `DebtToken` (mint via `issue`/`SmartFarmingManager`) calls `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, which revert with `UserReachedMaxTokens` once the combined list length reaches 30 (`Pool.sol:143-148`). Because `DepositToken._transfer` unconditionally registers the recipient on any nonzero incoming balance (`DepositToken.sol:517-520`), an unprivileged attacker can dust-transfer 1 wei of every pool deposit token to a victim, saturating the victim's list. Afterward, the victim cannot deposit a new collateral type, cannot issue a debt token they don't already hold, and cannot receive a new deposit token — including a collateral top-up needed to cure a declining position before liquidation.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0 && amount_ > 0` (`DepositToken.sol:517-520`). `transfer`/`transferFrom` only check the *sender's* unlocked balance, never the recipient's list size.
- `DepositToken._mint` does the same on `deposit(amount_, onBehalfOf_)` (`DepositToken.sol:485-488`), so attacker-controlled `deposit(amount, victim)` also fills slots without any consent from the victim.
- `DebtToken._mint` registers the borrower via `pool.addToDebtTokensOfAccount(account_)` (`DebtToken.sol:597-600`), and `DebtToken.issue` mints to `_msgSender`, so a saturated victim cannot open a debt position in a new synthetic asset.
- `Pool.onlyIfAdditionWillNotReachMaxTokens` sums `debtTokensOfAccount.length + depositTokensOfAccount.length` and reverts at `>= 30` (`Pool.sol:143-148`, `204-208`), and removal only happens on a zero balance, so each dust unit permanently occupies a slot until the victim manually transfers it out.

Attack path (all public entry points, no privileged role):
1. Attacker deposits a small amount into each of the pool's deposit tokens (or uses `deposit(amount, victim)` with an `onBehalfOf` beneficiary, which requires no approval or action from the victim).
2. Attacker calls `DepositToken.transfer(victim, 1)` (or deposits `onBehalfOf_ = victim`) for up to 30 distinct tokens, filling `depositTokensOfAccount[victim]`.
3. Any subsequent first-time receipt or issuance reverts with `UserReachedMaxTokens`.

Broken invariant: liveness — a core protocol operation (collateral deposit / debt issuance) becomes unavailable to a targeted account through attacker-only actions.

Not stopped by existing guards: `whenNotPaused`, `nonReentrant`, `SynthContext` sender checks, supply caps (`SurpassMaxDepositSupply` only limits total supply, dust passes), and `_revertIfLocked` (checks sender balance, not recipient list) all permit the dust transfers. The pool supports enough `depositTokens` (governor can add up to `MAX_TOKENS_PER_USER`, `Pool.sol:703`) for a full saturation attack.

### Impact Explanation
A victim whose position is trending unhealthy and who needs to add a *different* collateral type to restore health is blocked — `deposit` reverts inside `_mint` — so their position can be liquidated when a top-up would have saved it, causing direct loss via liquidation penalty. The victim also cannot open new borrow positions. The freeze is temporary only in that the victim can expend gas to transfer each dust token out to recover slots (and the attacker can cheaply re-fill them), matching the CVE's bug class of a size-limit-induced denial of service on a bounded buffer.

### Likelihood Explanation
Low-to-medium. The attack requires no privileges, no oracle manipulation, and no privileged roles — only gas and minimal capital for dust deposits across the pool's listed deposit tokens. However, the realized harm depends on the victim actually needing a new token type (e.g., collateral top-up during a drawdown or first borrow); a victim with an already-held collateral token can still top up that same token (`balanceBefore != 0` skips the add), which narrows the exploit window. The victim can self-recover slots by transferring dust balances out, so a motivated victim is not permanently locked — but the attacker can repeat the griefing at low cost.

### Recommendation
Make the per-account limit accounting consent-based rather than receipt-based:
- Do not register tokens into `depositTokensOfAccount` on inbound `transfer`/`deposit(onBehalfOf)` unless the recipient opts in (e.g., only register on `deposit` where `onBehalfOf_ == _msgSender()`, or require a whitelist/registration step), or
- Exclude zero-value dust by enforcing a minimum first-deposit amount, or
- Allow `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to silently no-op (instead of reverting) when the cap is reached and instead treat unlisted balances correctly in `debtPositionOf`, though this requires auditing all consumers of the lists (`debtPositionOf` iterates them to value collateral — unlisted balances must still be counted or the cap changed to only bound iterations safely).

### Proof of Concept
Reproducible on a mainnet/Base fork (Hardhat). Outline:

```ts
// fork mainnet; pool = deployed Pool proxy, deployer = attacker EOA, victim = any EOA
const depositTokens: string[] = await pool.getDepositTokens();

// 1. Attacker approves+deposits dust into each listed DepositToken with victim as beneficiary
for (const dt of depositTokens) {
  const dep = await ethers.getContractAt("DepositToken", dt);
  const underlying = await ethers.getContractAt("IERC20", await dep.underlying());
  await getWhaleTokens(underlying, attacker, "1"); // fund attacker
  await underlying.approve(dt, ethers.constants.MaxUint256);
  await dep.deposit(1n, victim.address); // _mint -> addToDepositTokensOfAccount(victim)
}

// list is now full for victim
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// 2. Victim tries to deposit into a deposit token they don't hold yet -> reverts
const newDep = await ethers.getContractAt("DepositToken", someTokenVictimDoesNotHold);
await expect(
  newDep.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 3. Victim tries to issue a synthetic whose debt token is not in their list -> reverts
await expect(
  debtToken.connect(victim).issue(mintAmount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 4. Consequence: victim cannot add a new collateral type while position drifts
//    unhealthy -> liquidator seizes collateral via pool.liquidate (works fine),
//    victim eats the liquidation penalty that a top-up would have avoided.
```

Uncertain items: exact count of deployed deposit tokens per chain (cap is 30 and tests show the list can be filled with `max/2` deposits + `max/2` debts; a single `deposit(amount, victim)` per token suffices, so the attacker only needs as many distinct deposit/debt registrations as are listed). If the deployed pool lists fewer than 30 deposit tokens, the attacker combines dust deposits with self-issued debt transfers where applicable — but `DebtToken` is non-transferable, so saturation may only reach the number of listed deposit tokens; whether that alone reaches 30 depends on deployment configuration.
