### Title
Dust `DepositToken` transfers fill the recipient's per-account token list up to `MAX_TOKENS_PER_USER`, permanently blocking the victim's deposits and token receipts — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2017-15128 (a missing size check leading to a denial of service), `DepositToken._transfer` performs no minimum-amount check and unconditionally calls `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero. `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` and reverts with `UserReachedMaxTokens` once the combined deposit/debt token list is full. An unprivileged attacker can deposit a minimal amount into each listed deposit token and `transfer` 1 wei of each to a victim, permanently DoS-ing that victim's ability to deposit new collateral or receive any deposit token — every such call reverts inside `_transfer`/`_mint`.

### Finding Description
- `DepositToken.transfer` calls `_revertIfLocked` then `_transfer`; there is no `amount_ == 0` or dust threshold check (`contracts/DepositToken.sol:348-354`).
- `_transfer` adds the token to the recipient's per-account list whenever `_recipientBalanceBefore == 0 && amount_ > 0` (`contracts/DepositToken.sol:517-520`), and `_mint` does the same on deposit (`contracts/DepositToken.sol:485-488`).
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert via `onlyIfAdditionWillNotReachMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (`contracts/Pool.sol:143-148`, `:204-220`).
- Once a victim's list reaches 30 entries, any `deposit(onBehalfOf = victim)` into a new token reverts inside `_mint → addToDepositTokensOfAccount → UserReachedMaxTokens`, and any incoming `transfer`/`transferFrom`/`seize` of a token the victim doesn't already hold also reverts after balances were mutated — rolling back the whole tx.
- The victim cannot remove entries unilaterally: `removeFromDepositTokensOfAccount` is only callable by the token itself when a balance reaches zero (`contracts/DepositToken.sol:522-525`). The victim must send away the dusted tokens one by one (or withdraw them, incurring `withdrawFee`), which costs gas per token, and the attacker can re-grief the freed slot at dust cost — a persistent liveness failure.

### Impact Explanation
Temporary/persistent freezing of funds-inflow: the victim is unable to deposit any additional collateral type, cannot receive msdTOKEN transfers or liquidation-seized collateral (`DepositToken.seize` → `_transfer`), and cannot be the beneficiary of leveraged positions that mint new token types (`SmartFarmingManager`). With multiple pools and >30 listed deposit/debt tokens across deployments, the attack is cheap: it costs the attacker only the dust deposits plus transfer gas, and re-griefing freed slots is repeatable. This matches the "denial of service via unchecked input" class of the CVE.

### Likelihood Explanation
- Fully permissionless: `deposit` + `transfer` are public, no privileged role needed.
- Attack cost is bounded by 30 token additions; each requires only a 1-wei-class deposit (no minimum deposit enforced) and one transfer.
- No mitigating checks: `whenNotPaused`, `nonReentrant`, `SynthContext` sender resolution — none prevent this; the `UserReachedMaxTokens` revert is exactly the mechanism that turns the missing minimum-amount check into a DoS.
- Constraint: requires the pool to list enough deposit tokens (or the attacker already having a victim with some entries). Mainnet/Base/Optimism deployments list many deposit tokens; combined with debt tokens the 30-slot cap is reachable.

### Recommendation
Enforce a minimum mint/transfer amount (e.g., a `minDeposit`/`minTransfer` floor or only adding to the per-account list when the minted/transferred amount exceeds a USD-valued dust threshold via `masterOracle`), or relax the limit by allowing the recipient to prune entries (public `removeFromDepositTokensOfAccount` for tokens with zero balance) so a victim can self-heal without paying withdraw fees.

// Foundry fork test (e.g. base fork), pseudocode over deployed Pool
function testDustGriefingDoS() public {
    address victim = address(0xBEEF);
    IDepositToken[] memory dts = pool.getDepositTokens(); // all listed deposit tokens

    // attacker deposits dust into each deposit token and transfers 1 wei to victim
    for (uint i; i < dts.length && pool.depositTokensOfAccountLength(victim) < 30; ++i) {
        IERC20 underlying = dts[i].underlying();
        deal(address(underlying), attacker, 1e6);
        underlying.approve(address(dts[i]), 1e6);
        dts[i].deposit(1e6, attacker);          // mints msdToken to attacker
        dts[i].transfer(victim, 1);             // adds dts[i] to victim's list
    }
    assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

    // victim tries to deposit a token not yet in its list -> revert
    vm.startPrank(victim);
    underlying2.approve(address(newToken), 1e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newToken.deposit(1e18, victim);

    // incoming transfer of a new token also reverts for the sender
    vm.stopPrank();
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    otherToken.connect(attacker).transfer(victim, 1);
}
