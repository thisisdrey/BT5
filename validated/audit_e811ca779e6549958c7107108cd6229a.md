### Title
XCM `Transact` credits a self-reported `actual_weight` into `total_surplus`, letting a malicious call under-report real computation to buy unaccounted extra execution - ([File: polkadot/xcm/xcm-executor/src/lib.rs])

### Summary
The Ethereum-side report shows how an attacker-controlled callback (`onERC721Received`) can consume an unbounded, attacker-chosen amount of the parent flow's metered resource, corrupting the accounting the parent flow relies on to safely finish (store the failed message). The direct analog inside the Polkadot SDK's XCM executor is the `Transact` instruction: it trusts the dispatched call's self-reported `PostDispatchInfo.actual_weight` as the *true* amount of work performed and folds the difference between the declared and reported weight into `total_surplus`, which is later subtracted from the weight the caller (e.g. `pallet-message-queue`) believes was consumed.

### Finding Description
In `XcmExecutor::process_instruction` for `Transact`, the executor gets the statically declared weight of the call (`message_call.get_dispatch_info().call_weight`), dispatches it, and then computes a "surplus" from whatever `actual_weight` the dispatched call chooses to report in its `PostDispatchInfo`: [1](#0-0) 

```
let weight = message_call.get_dispatch_info().call_weight;
...
let actual_weight = maybe_actual_weight.unwrap_or(weight);
let surplus = weight.saturating_sub(actual_weight);
self.total_surplus.saturating_accrue(surplus);
```

`total_surplus` is never validated against how much real computation the call performed — it is exactly what the dispatchable's own `PostDispatchInfo` claims. At the end of the message, `post_process` uses this accumulated surplus to compute `weight_used`: [2](#0-1) 

That `weight_used` is exactly the value credited back to the caller's own weight meter, e.g. in `pallet-message-queue`'s `ProcessXcmMessage`: [3](#0-2) 

```
Outcome::Complete { used } => { ... (used, Ok(true)) },
...
meter.consume(consumed);
```

This mirrors the LZ bug's broken invariant precisely: a nested, attacker-influenced sub-execution is allowed to report *how much of the parent's metered budget it used*, and that self-report — not an independently measured value — becomes the truth the surrounding bookkeeping (here, the `WeightMeter` that gates how much real block-production time `on_initialize` is allowed to spend servicing queues) relies on. Just as `_blockingLzReceive` trusted `gasleft()` after an attacker-controlled callback and had no way to force the callback to report honestly, the XCM executor trusts `actual_weight` after dispatching a call whose internal logic is fully attacker/pallet controlled, with no mechanism to verify it reflects real computation.

### Impact Explanation
If a dispatchable reachable through `Transact` (subject only to `SafeCallFilter`, which filters by call type, not by weight-honesty) under-reports its `actual_weight` relative to the real computation it performs, the difference is credited to `total_surplus` and subtracted from `weight_used`. Any XCM message built from repeated `Transact` instructions targeting such calls can perform far more real computation per unit of accounted weight than the weight system assumes, so `pallet-message-queue`'s per-block `WeightMeter` (and any other weight-based scheduler relying on `Outcome::Complete { used }`) will let far more real work through `on_initialize` than its configured limit allows. This is exactly the "public underpriced work that degrades block production" impact class: block authoring/import time balloons beyond what the runtime's own accounting believes was spent, without any malicious validator, collator, or governance actor involved — a plain user submitting/relaying an XCM message is sufficient.

### Likelihood Explanation
Exploitability depends on the existence of at least one dispatchable reachable via `Transact` whose `PostDispatchInfo.actual_weight` computation can diverge (deliberately or through a benchmarking edge case) from the real work performed while still passing `SafeCallFilter`. This is a realistic scenario in a large, evolving runtime with many pallets exposing dispatchables through XCM `Transact`, since weight benchmarking correctness for `actual_weight` is not enforced or cross-checked by the XCM executor itself — it is simply trusted. The mechanism itself (crediting `total_surplus` from self-reported weight) is present in every runtime using the standard `XcmExecutor`, making the likelihood of *some* exploitable call existing non-negligible, though it requires finding a specific under-reporting call as the trigger.

### Recommendation
- Do not fully trust `PostDispatchInfo.actual_weight` from `Transact`-dispatched calls for crediting `total_surplus`; consider capping the credited surplus (e.g. bound it to a small multiple of a conservatively re-measured cost, or disallow surplus credit entirely for calls reached through `Transact` with untrusted dispatch origins).
- Add PoV/ref-time re-measurement (similar to `cumulus-pallet-weight-reclaim`'s host-side proof-size measurement) around `Transact` dispatch so the credited surplus is bounded by an independently measured quantity rather than a self-report.
- Audit dispatchables exposed to `SafeCallFilter` for cases where `actual_weight` can be made much smaller than real computation.

### Proof of Concept
1. Configure a runtime where `SafeCallFilter` permits `Transact` to reach a dispatchable `Call::X` whose `PostDispatchInfo.actual_weight` can be manipulated (e.g., via input length or internal branching) to report a small weight while its call_weight was declared much higher, or better, whose real execution cost scales with attacker-supplied input while its reported `actual_weight` stays low.
2. Craft an XCM message with `weight_limit` X containing many `Transact` instructions each invoking `Call::X`, each of which is declared at weight `W_i` but reports `actual_weight` near `0`, and each of which performs computation proportional to `W_i` in real block-production time.
3. Submit via `pallet-message-queue`/`ProcessXcmMessage`; `WeightMeter::consume(consumed)` only registers `xcm_weight - total_surplus`, i.e., almost nothing, while the block producer actually spends close to `sum(W_i)` real time executing the calls.
4. Repeat across many enqueued messages within a single `on_initialize` weight budget — the queue believes it stayed within budget while the node performs work far exceeding the intended per-block ceiling, stalling block production.
