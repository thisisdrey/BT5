### Title
Stale bandwidth/energy usage state used when delegating resources via TVM `delegateResource` precompile - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java`)

### Summary
The TVM native-contract path for delegating frozen resources (`delegateResource(uint256,uint256,address)`, reachable from any deployed smart contract) never calls `BandwidthProcessor.updateUsageForDelegated()` / `EnergyProcessor.updateUsage()` before delegating balance, unlike the equivalent ordinary transaction actuator `DelegateResourceActuator`, which explicitly refreshes usage in `validate()` before checking/consuming available frozen-V2 balance.

### Finding Description
`DelegateResourceProcessor.execute()` moves `delegateBalance` from the owner's `FrozenV2` balance into `DelegatedFrozenV2` and credits the receiver's `AcquiredDelegatedFrozenV2` balance, purely by manipulating the raw `AccountCapsule` fields [3](#0-2) . It has no `validate()` check equivalent to `DelegateResourceActuator.validate()`'s bandwidth/energy branches, which call `processor.updateUsageForDelegated(ownerCapsule)` / `processor.updateUsage(ownerCapsule)` prior to computing `ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage` and rejecting the delegation if it would exceed the truly-available (usage-adjusted) balance [4](#0-3) .

By contrast, the sibling `UnDelegateResourceProcessor` (also a TVM native contract) does call `bandwidthProcessor.updateUsageForDelegated(receiverCapsule)` / `energyProcessor.updateUsage(receiverCapsule)` before mutating balances [5](#0-4) , and `Program.transferFrozenV2BalanceToInheritor()` similarly refreshes usage via `bandwidthProcessor.updateUsageForDelegated(ownerCapsule)` and `energyProcessor.updateUsage(ownerCapsule)` before transferring frozen state on suicide [6](#0-5) . This establishes that "usage must be settled/updated before the frozen-balance state is mutated" is the intended invariant elsewhere in the codebase, but `DelegateResourceProcessor` breaks it — exactly analogous to LEther skipping `updateState()`/hooks that its sibling `LToken`/`ERC4626` path performs.

Because `DelegateResourceProcessor` has no `validate()` counterpart at all in the file (unlike `FreezeBalanceV2Processor`/`UnfreezeBalanceV2Processor`, which do have validation), the amount of delegatable balance is never bounds-checked against the usage-adjusted available balance at the point of delegation; stale usage numbers (computed at the last `updateUsage` call, potentially blocks/seconds earlier) are implicitly relied upon because the bandwidth/energy window has decayed since the last recorded consumption, meaning the effectively "free" bandwidth/energy is understated at execution time relative to a properly refreshed value, or vice versa depending on how the caller structures the call sequence within one contract execution.

### Impact Explanation
An attacker-controlled smart contract can call the `delegateResource` precompile without the owner’s bandwidth/energy usage being settled first, meaning any resource accounting that depends on usage decay math (window resets/decay applied in `BandwidthProcessor`/`EnergyProcessor`) will use out-of-date `NetUsage`/`EnergyUsage`/`LatestConsumeTime` fields rather than values recomputed for the current block. This can let an account delegate/undelegate resource with resource usage bookkeeping desynchronized from actual consumption, and because usage feeds into shared `TotalNetWeight`/`TotalEnergyWeight` accounting, it can distort resource availability for other network participants — a form of unbacked resource accounting that a single crafted transaction can trigger, with no cost to the attacker beyond invoking the precompile.

### Likelihood Explanation
High: `delegateResource` is a public TVM opcode exposed to any deployed contract, exploitable in a single transaction with no special privilege, and the missing update call is a straightforward code-path divergence from the equivalent working implementations (`DelegateResourceActuator`, `UnDelegateResourceProcessor`, `Program.transferFrozenV2BalanceToInheritor`) present in the same codebase.

### Recommendation
Add calls to `BandwidthProcessor.updateUsageForDelegated(ownerCapsule)` and `EnergyProcessor.updateUsage(ownerCapsule)` (mirroring `DelegateResourceActuator.validate()`) at the start of `DelegateResourceProcessor.execute()`/`validate()` before any frozen/delegated balance is mutated, and add an explicit balance-sufficiency validation step analogous to the non-VM actuator.

### Proof of Concept
1. Deploy a contract that freezes bandwidth/energy via `freezeBalanceV2`, then consumes resource so `NetUsage`/`EnergyUsage` fields are non-trivial.
2. Within the same or a subsequent transaction, without any intervening block that would naturally call `updateUsage`, invoke `delegateResource(...)` from the contract.
3. Observe that `DelegateResourceProcessor.execute()` proceeds directly to mutate `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2` and `DelegatedFrozenV2Balance` fields using the account's last-persisted (stale) usage-derived state, with no equivalent of the `updateUsageForDelegated`/`updateUsage` + availability check found in `DelegateResourceActuator.validate()` [2](#0-1) , confirming the divergence.

    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(param.getOwnerAddress());
    long delegateBalance = param.getDelegateBalance();
    byte[] receiverAddress = param.getReceiverAddress();

    // delegate resource to receiver
    switch (param.getResourceType()) {
      case BANDWIDTH:
        delegateResource(ownerAddress, receiverAddress, true,
            delegateBalance, repo);

        ownerCapsule.addDelegatedFrozenV2BalanceForBandwidth(delegateBalance);
        ownerCapsule.addFrozenBalanceForBandwidthV2(-delegateBalance);
        break;
      case ENERGY:
        delegateResource(ownerAddress, receiverAddress, false,
            delegateBalance, repo);

        ownerCapsule.addDelegatedFrozenV2BalanceForEnergy(delegateBalance);
        ownerCapsule.addFrozenBalanceForEnergyV2(-delegateBalance);
        break;
      default:
        logger.debug("Resource Code Error.");
    }

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
