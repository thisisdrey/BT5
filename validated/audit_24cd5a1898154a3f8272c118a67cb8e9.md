### Title
Uncontrolled memory allocation from unvalidated Git object size field in commit/tag parsing (DoS) - (File: internal/git/catfile/parse_commit.go, internal/git/catfile/parser.go)

### Summary

### Finding Description
Gitaly's `catfile` package extracts an object's size from the header line emitted by `git cat-file --batch`/`--batch-check` and trusts it unconditionally when later allocating a buffer to hold the object body. `ParseObjectInfo` parses the third field of the info line directly into an `int64` with no upper bound check: [1](#0-0) 

This `ObjectInfo.Size` is exposed as `object.ObjectSize()` and is used as `bytesRemaining` in both the commit-body and tag-message parsers, where it is passed straight into `make([]byte, bytesRemaining)` *before* any data has actually been read/validated against that size: [2](#0-1) [3](#0-2) 

The declared object size is not cross-checked against the actual number of bytes available before the allocation happens — the mismatch is only detected *after* the allocation, via the trailing `io.Copy(io.Discard, ...)` / length-mismatch error. Test coverage in `request_queue_test.go` demonstrates that the size reported by `git cat-file` for an object header and its real, readable content can diverge (a "truncated object" case where the header claims `Size: 10` but only 3 bytes are actually present): [4](#0-3) 

This is the same bug class as the referenced Monero report: a length/size field taken from data under attacker influence is used directly as an allocation size (`reserve()` / `make([]byte, size)`) with no sanity bound, so a crafted value near the `int64` maximum results in an attempted multi-exabyte allocation and process crash/OOM — functionally identical to the ~4 exabyte allocation triggered by `portable_storage::load_from_binary()`.

Any Gitaly RPC that walks commits or tags through the `catfile.Parser` (e.g. `GetCommit`, `FindCommit`, `ListCommits`, `GetTag`, `FindTag`, `ListTagNamesContainingCommit`, and other commit/ref services built on `ParseCommit`/`ParseTag`) will reach this code path once the target repository contains a commit or tag object whose declared object-header size does not match its real content length. Since Git object content is hashed exactly as-authored (including its `"<type> <size>\0"` header), a user with push access can construct such an object out-of-band (e.g. crafting the loose/pack object bytes directly) and push it into a repository that Gitaly serves.

### Impact Explanation
When Gitaly parses the malicious commit/tag object, `bytesRemaining` (attacker-controlled, up to ~9.2×10^18) is passed to `make([]byte, bytesRemaining)`. This triggers an enormous, synchronous memory allocation attempt on the Gitaly process handling that RPC. On most systems this either panics with an out-of-memory condition or is killed by the OOM killer, crashing the Gitaly process and disrupting service for all repositories co-located on that Gitaly node — a remote, unauthenticated-relative-to-repo-access, project-scoped denial of service.

### Likelihood Explanation
Reaching this code path only requires the ability to push a repository/object to a location Gitaly will later read via `git-cat-file`, which is a standard, low-privilege capability for any user with write access to a repository. No special network position, leaked credentials, or malicious peer/node cooperation is needed — a single crafted object is sufficient, and the vulnerable code path (`ParseCommit`/`parseTag`) is exercised by many common read-side RPCs.

### Recommendation
Bound the declared object size against a sane maximum (e.g. `helper.MaxCommitOrTagMessageSize` or a hard per-object cap) *before* allocating the `body`/`message` buffer, and/or allocate incrementally (e.g. via `io.CopyN` into a growable `bytes.Buffer` with a capped `Grow`) rather than eagerly allocating `bytesRemaining` bytes up front. Reject or truncate objects whose declared size exceeds the configured limit prior to allocation, consistent with how `ReadObjectWithLimit` already caps reads elsewhere in `internal/git/localrepo/objects.go`.

### Proof of Concept
1. Construct a Git commit (or tag) object whose header falsely declares an extremely large size, e.g. author/committer content followed by a body, but craft the raw object bytes (`"commit <hugesize>\0<small content>"`) directly and compute its OID over those exact bytes (bypassing normal `git commit-tree`, e.g. by using `git hash-object -w --stdin -t commit --literally` or writing the loose object file directly with correct zlib framing).
2. Push this object into a repository/reference that Gitaly serves (e.g. as part of a branch update), or otherwise get it stored via Gitaly's object write path.
3. Invoke any commit/tag-reading RPC that resolves this object through `catfile.Parser` (e.g. `CommitService.FindCommit`/`GetCommit`, `RefService.FindTag`), causing `ParseCommit`/`parseTag` to execute `body := make([]byte, bytesRemaining)` with the forged multi-exabyte size, crashing/OOM-killing the Gitaly process.
