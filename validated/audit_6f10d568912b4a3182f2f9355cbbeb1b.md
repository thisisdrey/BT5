### Title
FetchRemote RPC omits the `transfer.bundleURI=false` guard applied in CreateRepositoryFromURL, allowing bundle-URI-driven SSRF - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`CreateRepositoryFromURL`'s `cloneFromURLCommand` explicitly disables Git's bundle-URI feature via `gitcmd.WithGlobalOption(gitcmd.ConfigPair{Key: "transfer.bundleURI", Value: "false"})` to prevent a malicious remote from redirecting the client to fetch a bundle from an attacker-chosen (e.g. internal) URI. The sibling RPC `FetchRemote`, which also fetches from a fully attacker-controlled `RemoteParams.Url`, does not apply this same mitigation anywhere in its call path (`fetchRemoteAtomic` → `buildCommandOpts` → `localrepo.Repo.FetchRemote`).

### Finding Description
`CreateRepositoryFromURL` → `cloneFromURLCommand` (internal/gitaly/service/repository/create_repository_from_url.go:72-75) sets the global git config `transfer.bundleURI=false` before invoking `git clone` against the attacker-supplied `req.GetUrl()`, specifically to stop a malicious server from advertising a bundle-URI capability that points at an internal address and having the client fetch it.

`FetchRemote` (internal/gitaly/service/repository/fetch_remote.go:30-46) accepts `req.GetRemoteParams().GetUrl()`, also fully attacker-controlled since a low-privileged user can trigger repository mirroring/import with an arbitrary URL. It flows into `fetchRemoteAtomic` → `buildCommandOpts` (fetch_remote.go:260-304), which only sets `remote.inmemory.fetch`, `remote.inmemory.url`, optional proactive-auth, and HTTP auth headers — no `transfer.bundleURI` override. This is passed to `quarantineRepo.FetchRemote(ctx, "inmemory", opts)`, which resolves to `localrepo.Repo.FetchRemote` (internal/git/localrepo/remote.go:79-138). That function's `commandOptions` list (lines 94-119) sets `advice.fetchShowForcedUpdates` and `remote.<name>.followremotehead`, but likewise contains no bundle-URI guard before executing `git fetch`.

Because git-fetch (protocol v2) also supports server-advertised bundle-URI capability and the client will act on it unless `transfer.bundleURI` is disabled, an attacker-controlled remote reached through `FetchRemote` can advertise a bundle URI pointing to an internal service (e.g., `http://169.254.169.254/...` or an internal Gitaly/Rails admin endpoint), and Gitaly's git-fetch subprocess would attempt to retrieve it — exactly the SSRF vector the sibling code path explicitly closed.

### Impact Explanation
This is a same-class SSRF as the one already mitigated in `CreateRepositoryFromURL`: an unprivileged user who can trigger a pull-mirror update or `FetchRemote` call against a URL they control can direct the Gitaly host to make outbound HTTP(S) requests to arbitrary internal/private addresses via the bundle-URI mechanism, without needing the target URL itself to be attacker-controlled for the secondary request (only the advertised bundle URI is). This maps to GitLab's SSRF bounty impact class, potentially exposing internal metadata endpoints, internal-only services, or triggering internal network reconnaissance.

### Likelihood Explanation
Preconditions match the described unprivileged threat model exactly: the attacker only needs to control a Git server that GitLab is instructed to fetch from (e.g., a pull mirror, import-by-URL/fetch source, or any feature invoking the `FetchRemote` RPC with a user-supplied URL), which is a normal, unprivileged user capability. No admin access, secret leakage, or peer compromise is required. This is highly feasible and repeatable — the attacker simply hosts a Git server (protocol v2 capable) advertising a bundle-URI capability pointing at the desired internal target, then triggers a fetch/mirror-update against it.

### Recommendation
Add the same mitigation used in `cloneFromURLCommand` to the `FetchRemote` code path: append `gitcmd.WithGlobalOption(gitcmd.ConfigPair{Key: "transfer.bundleURI", Value: "false"})` (or equivalent `gitcmd.WithConfig`) to the options built in `buildCommandOpts` (internal/gitaly/service/repository/fetch_remote.go) or, more robustly, inside `localrepo.Repo.FetchRemote` (internal/git/localrepo/remote.go) so that every caller of `FetchRemote`/`FetchInternal` (including any future or existing mirror-update paths) inherits the guard uniformly, rather than requiring each call site to remember to add it.
