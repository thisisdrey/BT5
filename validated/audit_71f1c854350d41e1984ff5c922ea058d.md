### Title
Global resource limit calculation truncates weight before multiplying by totalLimit, causing bandwidth/energy limits to round down to zero for small frozen balances - (File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java)

### Summary
`ResourceProcessor.calculateGlobalLimitV1` computes an account's proportional global bandwidth/energy limit by first performing an integer division (`frozeBalance / TRX_PRECISION`) and only afterward multiplying the result by `totalLimit`, mirroring the exact "division-before-multiplication" bug class described in the external report where doing division first causes premature truncation that a later multiplication cannot recover.

### Finding Description
`calculateGlobalLimitV1` is defined as: [1](#0-0) 

```java
protected long calculateGlobalLimitV1(long frozeBalance,
    long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))
      .longValueExact();
}
```

The intended calculation is `frozeBalance * totalLimit / (TRX_PRECISION * totalWeight)`, but the code instead computes `(frozeBalance / TRX_PRECISION) * totalLimit / totalWeight`. Because `frozeBalance / TRX_PRECISION` is an integer division performed with `long` arithmetic *before* the multiplication by `totalLimit`, any `frozeBalance` value smaller than `TRX_PRECISION` (1,000,000 sun = 1 TRX) truncates `weight` to `0`, which zeroes out the entire global-limit result regardless of `totalLimit`. This is structurally identical to the reported `owedAmount = (currentShareRaw / currentGlobalShare) * value` pattern: an early division discards the fractional/proportional information that the later multiplication was supposed to scale up.

The comment directly above the sibling method `calculateGlobalLimitV2` confirms the intended, corrected semantics (multiply first, then divide by the combined denominator), and explicitly documents that `calculateGlobalLimitV1` is the "legacy" formula being replaced: [2](#0-1) 

Both `calculateGlobalLimitV1` and `calculateGlobalLimitV2` are referenced from `BandwidthProcessor.java` and `EnergyProcessor.java`, which are on the transaction-processing path used to determine how much bandwidth/energy an account can consume based on its frozen TRX. I was not able to fully verify, within the remaining tool budget, the exact conditional (`hardenCalculation()`/`allowHardenResourceCalculation()`) that selects between V1 and V2 at each call site in `BandwidthProcessor.java` / `EnergyProcessor.java`, so it is uncertain whether V1 is reachable by default on the current chain configuration or only under a legacy/disabled-hardening code path.

### Impact Explanation
If the V1 path is reachable (e.g., when `allowHardenResourceCalculation()` is not enabled), any account whose frozen balance for bandwidth/energy is below 1 TRX (1,000,000 sun) will have its computed global resource limit contribution truncated to zero, meaning that portion of frozen TRX yields no bandwidth/energy benefit. This does not directly create unbacked balances or fund theft, but it silently discards a user's expected resource allocation derived from their staked TRX — a legitimate account-operation/accounting defect matching the "permanent freezing of [resource] value" impact class analogous to the original report's "stuck rewards."

### Likelihood Explanation
The truncation only occurs when an individual account's frozen balance is less than 1 TRX, which is a much narrower condition than the original report's "almost always" scenario (there, any share smaller than the pool's cumulative share triggers it). Given typical freeze amounts are well above 1 TRX, the practical likelihood is lower than the original finding, and I could not confirm from the code inspected whether the V1 path is still the actively used default versus a superseded/hardened-off fallback.

### Recommendation
Ensure the resource-limit calculation always multiplies before dividing, consistent with `calculateGlobalLimitV2`:
```diff
- long weight = frozeBalance / TRX_PRECISION;
- return BigInteger.valueOf(weight)
-     .multiply(BigInteger.valueOf(totalLimit))
-     .divide(BigInteger.valueOf(totalWeight))
-     .longValueExact();
+ return BigInteger.valueOf(frozeBalance)
+     .multiply(BigInteger.valueOf(totalLimit))
+     .divide(BigInteger.valueOf(TRX_PRECISION).multiply(BigInteger.valueOf(totalWeight)))
+     .longValueExact();
```
If `calculateGlobalLimitV1` is retired/dead code (superseded entirely by V2), it should be removed to eliminate the risk of it being invoked under any configuration flag.

### Proof of Concept
Given `frozeBalance = 500_000` (0.5 TRX), `TRX_PRECISION = 1_000_000`, `totalLimit = 43_200_000_000`, `totalWeight = 1000`:
- V1: `weight = 500_000 / 1_000_000 = 0` → result `= 0 * totalLimit / totalWeight = 0`.
- Correct (V2-style): `500_000 * 43_200_000_000 / (1_000_000 * 1000) = 21,600,000` (nonzero, proportional).

This confirms the truncation-to-zero behavior for sub-1-TRX frozen balances when the V1 formula path is exercised. I was unable to confirm within the available tool calls the precise runtime condition that selects `calculateGlobalLimitV1` versus `calculateGlobalLimitV2` in `BandwidthProcessor.java`/`EnergyProcessor.java`; a Devin session with full repository access would be needed to trace those call sites and confirm current reachability/default configuration.

   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
