### Title
Out-of-bounds slice index panic reading ELF symbol names during linking - ([File: src/cmd/link/internal/loadelf/ldelf.go])

### Summary
`readelfsym` in the Go linker's ELF object reader indexes the in-memory string-table buffer with an attacker-controlled, unvalidated 32-bit offset (`b.Name`) taken directly from the symbol table entry of an ELF object file, with no bounds check against the string table's length before slicing. This mirrors the FontForge `readttfcopyrights` bug class (trusting an offset field from a binary format to slice into a buffer without validating it against the buffer size), but in Go the effect is a slice-bounds-out-of-range runtime panic rather than a silent heap over-read.

### Finding Description
Attacker input: a crafted ELF relocatable object file (`.o`/`.a`) supplied to `go build`/`go tool link` (e.g., via cgo compilation of a third-party package, or a precompiled `.syso`/archive dependency).
Entry point: `loadelf.Load` in [1](#0-0)  reads the section string table and the symbol table (`elfobj.symtab`, `elfobj.symstr`), which are later consumed by `readelfsym`.
Failing function: [2](#0-1) . The code parses `elf.Sym64`/`elf.Sym32` from the object's symbol table and does `elfsym.name = cstring(elfobj.symstr.base[b.Name:])` for both the 64-bit and 32-bit paths, where `b.Name` is a raw `uint32` field taken straight from attacker-supplied bytes.
Failed check: unlike the public `debug/elf` package, which validates offsets via `getString` (bounds-checked, e.g. used in `f.getSymbols64` at [3](#0-2) ) and unlike `debug/macho`'s `parseSymtab`, which explicitly checks `n.Name >= uint32(len(strtab))` before slicing ( [4](#0-3) ), `loadelf.readelfsym` performs no equivalent `b.Name >= uint32(len(elfobj.symstr.base))` check.
Sink: `elfobj.symstr.base[b.Name:]` — a Go slice expression that panics with "slice bounds out of range" if `b.Name` exceeds `len(elfobj.symstr.base)`, since `elfobj.symstr.base` is a fixed-length byte slice read from the file via `elfmap`/`f.Slice` ( [5](#0-4) ).

### Impact Explanation
The immediate effect is a runtime panic (crash) of the `go` toolchain / linker process during a build, i.e., a build-time denial of service triggered by a malformed ELF object supplied through a build dependency chain (cgo object files, precompiled archives, `.syso` files). This is not a memory-disclosure or code-execution primitive as in the C-based FontForge bug, because Go slice indexing is always bounds-checked at runtime — there is no heap over-read, only a panic. Under Go's security-bug classification this would at most be a low-severity/likely-PUBLIC-track "malformed input causes toolchain panic" issue, not a memory-safety CVE; Go's own security policy explicitly excludes "go build must not run malicious source" concerns that involve execution, and separately treats crashes from malformed build inputs as lower severity than runtime-facing parsers reachable from network input.

### Likelihood Explanation
Reachability requires an attacker to control an ELF object file that gets linked into a victim's build (e.g., a malicious cgo dependency, prebuilt `.a`/`.syso` shipped in a module, or a linker invoked directly on attacker-supplied object files). This is a real but narrower workflow than a network-facing parser; it requires the victim to build/link attacker-influenced native code, which is a somewhat expected trust boundary for build inputs (comparable to "supply-chain" scenarios already acknowledged for `go build`).

### Recommendation
Add an explicit bounds check before slicing, e.g. `if b.Name >= uint32(len(elfobj.symstr.base)) { return fmt.Errorf("invalid symbol name offset") }` prior to `cstring(elfobj.symstr.base[b.Name:])`, mirroring the checks already present in `debug/macho.parseSymtab` and `debug/elf.getString`.

### Proof of Concept
Not produced as a full runnable Go test — reproducing this requires constructing a valid-enough ELF object with `symtab`/`strtab` sections and a symbol whose `Name` field exceeds the string table size, then invoking `cmd/link`'s internal `loadelf.Load` (an internal, non-exported package) or driving it end-to-end via `go build` with a crafted object file. I was not able to execute or validate this within the available tooling; this should be treated as an unverified analog requiring a background agent with build/test execution capability to confirm the panic reproduces and is not already guarded elsewhere in the call chain (e.g., truncation/validation upstream in `Load` for legitimate toolchains' ELF output that I did not fully trace).

**Caveat / uncertainty:** I could not fully verify (a) whether some earlier validation step in `loadelf.Load` (before `readelfsym` is invoked) already rejects symbol tables with out-of-range name offsets, or (b) whether this exact code path is already covered by a fuzz test or has been patched in a newer version of this file than what's indexed. Given the tool's read-only, indexed nature, I recommend a Devin session with full repository/build access to confirm reachability and reproduce the panic before treating this as confirmed.

func elfmap(elfobj *ElfObj, sect *ElfSect) (err error) {
	if sect.base != nil {
		return nil
	}

	if sect.off+sect.size > uint64(elfobj.length) {
		err = fmt.Errorf("elf section past end of file")
		return err
	}

	elfobj.f.MustSeek(int64(uint64(elfobj.base)+sect.off), 0)
	sect.base, sect.readOnlyMem, err = elfobj.f.Slice(sect.size)
	if err != nil {
		return fmt.Errorf("short read: %v", err)
	}

	return nil
}
