### Title
Heap buffer over-read / `ArrayIndexOutOfBoundsException` in `PrecompiledContracts.extractBytes` via unchecked offset/length arithmetic - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
CVE-2019-11009 describes a heap-based buffer over-read in GraphicsMagick's `ReadXWDImage`, caused by trusting an attacker-controlled length/offset field from a file header and reading past the end of the allocated buffer. The analogous bug class in java-tron is unchecked, attacker-controlled offset/length arithmetic used to slice a `byte[]` inside the `BatchValidateSign` precompiled contract's ABI-decoding helpers.

### Finding Description
`extractSigArray` and `extractBytesArray` in `PrecompiledContracts.java` decode ABI-encoded arrays embedded in TVM precompile call data by reading a `DataWord[] words` array (produced from the raw call data) and using attacker-supplied word values as offsets/lengths, without validating them against the bounds of the underlying `data` byte array: [1](#0-0) 

`extractBytes` performs a raw `Arrays.copyOfRange(data, offset, offset + len)` with no bounds validation of `offset`/`len` against `data.length`: [2](#0-1) 

`extractBytesArray` has an identical pattern, computing `bytesOffset` and `bytesLen` from attacker-controlled `words` entries and passing them straight into `extractBytes`: [3](#0-2) 

Only the top-level `offset > words.length - 1` is checked; the derived `bytesOffset`/`bytesLen` values (attacker-controlled 32-byte words interpreted via `intValueSafe()`) are never validated against `data.length` before being used as `Arrays.copyOfRange` bounds. A crafted call to the `BatchValidateSign` precompiled contract (address `0x66`) supplying a small `data` buffer but declaring large offsets/lengths in the embedded words will cause `Arrays.copyOfRange` to throw `ArrayIndexOutOfBoundsException`, or, depending on `intValueSafe()` clamping/overflow, may allocate a huge or negative-length array.

### Impact Explanation
This code path is reached by any unprivileged account issuing a `TriggerSmartContract`/`CREATE`/message call whose bytecode calls the precompiled contract at `BatchValidateSign`'s address, i.e., a fully unauthenticated on-chain interaction. If the resulting uncaught exception propagates instead of being converted into a clean VM revert, it can crash or halt block/transaction processing on the node executing it (via `Manager`'s block application / TVM execution path), which is a denial-of-service against the node. This matches the "node crash or halt" impact bar in scope.

### Likelihood Explanation
Likelihood is uncertain without confirming (a) whether callers of `extractSigArray`/`extractBytesArray` wrap execution in a try/catch that safely converts any `RuntimeException` (including `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`) into a revert, and (b) whether `DataWord.intValueSafe()` clamps values so that resulting offsets can never realistically exceed `data.length` in a way that triggers the exception. The surrounding `execute()` method for `BatchValidateSign` was only partially visible in the retrieved context; I could not confirm the exact exception-handling wrapper for this specific precompile within the scope of this investigation.

### Recommendation
Add explicit bounds checks in `extractBytes`, `extractSigArray`, and `extractBytesArray` verifying `offset >= 0`, `len >= 0`, and `offset + len <= data.length` before calling `Arrays.copyOfRange`, returning an empty/zero result (consistent with the existing `offset > words.length - 1` guard) instead of allowing an unchecked slice. Ensure the `BatchValidateSign` `execute()` method catches any resulting `RuntimeException` and converts it into a clean revert rather than propagating an uncaught exception through TVM execution.

### Proof of Concept
Not fully verifiable within this investigation — reproducing this requires confirming the exact call path and exception handling around `BatchValidateSign.execute()`, which is at (or beyond) the boundary of the indexed content available. A background Devin session with full repository access would be needed to construct and validate a concrete `TriggerSmartContract` payload that reaches `extractSigArray`/`extractBytesArray` with an out-of-bounds offset/length and to confirm whether the resulting exception is caught or escapes to crash the node.
