## Finding: Unchecked git submodule error code in `update_submodules` — (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`'s submodule handling ignores the exit code of `git submodule update --init [--recursive] --checkout --force`, unlike every other git invocation in the same file. A submodule fetch/checkout failure is silently swallowed, and Bazel reports the repository fetch as successful and reproducible even though the checked-out tree is incomplete or stale.

### Finding Description
Every other git command wrapper in `tools/build_defs/repo/git_worker.bzl` checks `st.return_code` and calls `_error()` (which `fail()`s the build) on non-zero exit: `init` [1](#0-0) , `_git` [2](#0-1) , `fetch` [3](#0-2) , `_git_sparse_checkout_config`/`_git_sparse_checkout` [4](#0-3) .

But `update_submodules` calls `_git_maybe_shallow(...)` and discards the returned `exec_result` entirely, never inspecting `return_code`: [5](#0-4) 

`_git_maybe_shallow` itself only checks the return code of its *first* (shallow) attempt to decide whether to retry non-shallow — it returns the second `exec_result` unconditionally without the caller ever checking it: [6](#0-5) .

`_update` invokes `update_submodules` and then simply returns, so a failed submodule update does not stop the pipeline: [7](#0-6) . Control then returns to `git_repo`, which records `actual_commit`/`shallow_since` from the *top-level* repo's HEAD only — it never records or verifies submodule state — and returns success: [8](#0-7) . `git.bzl`'s `_git_repository_implementation` treats this as success and, for pinned commits, marks the fetch `reproducible = True`: [9](#0-8) .

### Impact Explanation
An attacker who controls (or can influence) a submodule's remote — an unprivileged party publishing content that a victim's `git_repository(..., init_submodules=True)` or `recursive_init_submodules=True` build consumes — can cause `git submodule update --init` to fail (e.g., by force-pushing/removing the referenced submodule commit, breaking `uploadpack.allowReachableSHA1InWant` for that ref, returning transient errors only for the submodule fetch, or supplying a submodule URL that errors out for a specific client/hash). Because the non-zero exit is never checked, Bazel does not `fail()`: the outer repository is still reported as fetched successfully with `MODULE.bazel.lock`/`attrs_for_reproducibility` recording the pinned outer `commit` as reproducible, while the submodule directories are left empty, partially checked out, or containing stale content from a prior fetch (working directory is only deleted for the top-level repo in `_update`, not necessarily consistent for submodules). This is a silent content-integrity break: the build proceeds using unintended/incomplete/stale source content under a "pinned and reproducible" repository rule, without any build failure or warning surfaced to the user, undermining the hermeticity guarantee `git_repository`/lockfile mode is meant to provide.

### Likelihood Explanation
Reasonably likely wherever `init_submodules` or `recursive_init_submodules` is used with an external/untrusted submodule remote — a common pattern for third-party dependencies. No special privileges are needed beyond control of (or timed interference with) the submodule's git remote; default flags on a current release do not add any additional integrity check for submodule content (unlike `http_archive`'s mandatory `sha256`/`integrity`).

### Recommendation
In `update_submodules`, capture the `exec_result` from `_git_maybe_shallow` and check `st.return_code != 0`, calling `_error(ctx.name, cmd, st.stderr)` exactly as done in `_git`, `init`, and the sparse-checkout helpers, so a failed submodule fetch/checkout causes the repository rule to fail rather than being silently accepted as a successful, reproducible fetch.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to `src/test/shell/bazel/starlark_git_repository_test.sh` can demonstrate this: create a git repo with a submodule pointing at a remote path, then remove/corrupt the submodule's referenced commit from the submodule remote before the outer clone's submodule update runs (or replace the submodule remote so `git submodule update --init` returns non-zero, e.g. permission-denied path). Run:
```
git_repository(
    name = "with_submodule",
    remote = "<attacker-controlled or corrupted submodule outer repo>",
    commit = "<pinned commit>",
    recursive_init_submodules = True,
)
```
and observe that `bazel fetch //...` currently reports success (no `expect_log "error running"` triggered) despite the submodule directory being empty/incomplete, whereas after the fix the build should fail with an explicit git error, matching the existing pattern used by `test_invalid_strip_prefix_error`/`test_strip_prefix_errors` in `starlark_git_repository_test.sh` [10](#0-9) .

```text
def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
```

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```

```text
def _git_maybe_shallow(ctx, git_repo, command, *args):
    start = [command]
    args_list = list(args)
    if git_repo.shallow:
        st = _execute(ctx, git_repo, start + [git_repo.shallow] + args_list)
        if st.return_code == 0:
            return st
    return _execute(ctx, git_repo, start + args_list)
```

```text
def _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file):
    """Initialize the repo with patterns for a sparse checkout.

    Args:
        ctx: Context of the calling rules.
        git_repo: The Git repository to initialize for sparse checkout.
        sparse_checkout_patterns_or_file: Either a list of patterns or a Label for a sparse-checkout file.
    """

    # Note: `init` is deprecated, but needed for older versions of Git. This command may be removed
    # in future versions.
    init_command = ["sparse-checkout", "init", "--no-cone"]
    st = _execute(ctx, git_repo, init_command)
    if st.return_code != 0:
        _error(ctx.name, init_command, st.stderr)

    if type(sparse_checkout_patterns_or_file) == "list":
        sparse_checkout_patterns = sparse_checkout_patterns_or_file
        set_command = ["sparse-checkout", "set"] + sparse_checkout_patterns
        st = _execute(ctx, git_repo, set_command)
        if st.return_code != 0:
            _error(ctx.name, set_command, st.stderr)
```
