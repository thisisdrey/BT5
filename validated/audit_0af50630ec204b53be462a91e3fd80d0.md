The reported issue (Parse Server's `protectedFields` CLP bypass via dot-notation in query/sort parameters) is an access-control primitive specific to a database-backed application layer: it depends on the framework enumerating dot-notation object paths in a query WHERE clause or sort spec, extracting the "root field," and checking it against a per-class protected-fields permission list. This is a CWE-284 improper access control issue tied to Parse Server's own query-building and permission-enforcement code — a pattern that has no structural analog in the Go standard library / toolchain repository (`Kohvert/go--005`).

The closest superficially related constructs found in the Go repo are all field/dot-chain *resolution* mechanisms used for entirely different purposes — none of which implement or bypass an access-control permission list:

- `text/template`'s field-chain evaluator, which walks `.Field1.Field2` chains against Go values with no access-control concept at all [1](#0-0) .
- The compiler's struct/interface field lookup (`Lookdot`, `adddot1`), which resolves selector expressions at compile time, not runtime data access control [2](#0-1) .
- `encoding/json`'s struct field flattening, which governs marshaling visibility (exported vs. unexported), not a permissions system with protected fields keyed by dot-path [3](#0-2) .
- `reflect.VisibleFields`, which enumerates visible struct fields for reflection, unrelated to any permission enforcement [4](#0-3) .

None of these represent an unauthenticated HTTP entry point that parses a query/sort key, strips or fails to strip a dot-notation suffix, and checks the wrong (full) key against a protected/permission list, which is the exact primitive in the advisory. Since the Go standard library has no equivalent "class-level permission" or "protected fields" enforcement layer over queries, there is no valid analog to report.
