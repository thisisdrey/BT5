### Title
Integer truncation in MVCC manifest chunk-table parsing allows bounds-check bypass and out-of-bounds slicing - (File: internal/git/mvcc/manifest.go)

### Summary
`ParseManifest` in the gitaly-mvcc-backend reference-format reader converts attacker/producer-controlled `uint64` chunk offsets into Go `int` before validating them, mirroring the C4 report's root cause: an unchecked arithmetic/type-conversion operation that silently wraps instead of erroring, defeating a subsequent bounds check.

### Finding Description
`parseChunks` reads 8-byte big-endian TOC offsets straight out of the manifest body and truncates them to `int` before any range validation is applied: [1](#0-0) 

`chunkOffsetInFile` and `nextChunkOffsetInFile` are produced via `int(binary.BigEndian.Uint64(...))`. If the encoded `uint64` value has its high bit set (≥ 2^63) — trivial to encode in an 8-byte TOC field — the conversion to Go's platform `int` wraps to a negative number rather than erroring or saturating. The subsequent guard,

```go
if chunkOffsetInFile > dataEnd || nextChunkOffsetInFile > dataEnd || nextChunkOffsetInFile < chunkOffsetInFile {
```

can then be bypassed: a negative `chunkOffsetInFile` will never be `> dataEnd`, and two crafted negative offsets can satisfy `nextChunkOffsetInFile >= chunkOffsetInFile` while `chunkSize = nextChunkOffsetInFile - chunkOffsetInFile` produces an arbitrary (attacker-chosen) value once the two truncated values are subtracted. The derived `manifestChunk.offset`/`.size` are then used unchecked to slice `data` when extracting the `PATH`, `OBJS`, and `REFS` chunks (`data[start:start+pw]`, `data[objsChunk.offset:objsChunk.offset+8]`, etc.), which can panic on an out-of-range slice or, depending on the resulting (now-positive) computed offsets, read/interpret memory regions of the buffer that were never intended to be reachable by that chunk's declared bounds.

This is structurally identical to the report's bug class: a value that is supposed to "wrap" safely under one numeric representation instead overflows/underflows once cast to a different width/signedness, silently invalidating an adjacent safety check (`applyL1ToL2Alias`'s `uint160` addition vs. the report's fixed-width wraparound assumption; here, `uint64`→`int` truncation vs. the offset/size bounds checks).

The self-describing SHA-256 trailer offers no real protection here: whoever supplies the raw manifest bytes computes the trailer themselves (`sha256.Sum256(data[:payloadEnd])` is over the attacker-controlled prefix), so the checksum only proves internal self-consistency, not provenance/trust of the content.

### Impact Explanation
A malformed manifest that passes the header/checksum gate can:
- Trigger an out-of-bounds slice panic in `ParseManifest`, crashing/aborting the Gitaly process handling the RPC that hydrates the MVCC cache (`LocalCache.prepare` → `prepareManifestFile` → `ParseManifest`), a DoS of the RPC handler for any repository using the `mvcc` reference backend.
- Depending on the exact wrapped values, cause `objStart`/`objCount`/chunk `offset`/`size` to compute to unintended but in-range values, letting the OBJS/REFS chunk resolution point `ObjPaths()`/`RefPaths()` at attacker-influenced byte ranges within the manifest body, potentially yielding corrupted or attacker-chosen artifact paths being treated as trusted repository object/reftable locations to fetch/write.

This matches the report's "Medium" character: a real, confirmed integer-handling flaw whose blast radius depends on exploitation constraints, rather than a straightforward RCE.

### Likelihood Explanation
Exploitability is gated by who can get arbitrary bytes into `ParseManifest`. In the current (POC/"vibe coding", per `doc/mvcc_rpc_flow.md`) MVCC design, manifest bodies are meant to be generated exclusively by Gitaly itself via `SerializeManifest` and fetched by content hash from the configured remote object storage (S3-backed `ObjectStorage`/`RemoteStorage`). Reaching this code path with attacker-chosen bytes therefore currently requires either compromising/tampering with the shared object-storage bucket or another mechanism to influence the manifest hash pointer that an ordinary Git push/fetch client does not have — this is closer to a privileged/infrastructure-trust issue than a bug directly reachable from an ordinary user's push, fetch, fork, or crafted RPC field. I could not find a code path where a normal git-push/fetch payload is parsed directly as manifest bytes; the feature is explicitly still under active development.

### Recommendation
Regardless of current reachability, the parser should not rely on an unvalidated widening/truncating cast. Read offsets/sizes as `uint64`, bounds-check them against `dataEnd` (also as `uint64`) before any conversion to `int`, and reject any offset ≥ 2^63 or greater than `dataEnd` prior to truncation. Only convert to `int` after the value is proven to be within `[0, len(data)]`. Add fuzz/unit tests feeding crafted TOC offsets near `math.MaxUint64` and `1<<63` to `parseChunks`/`ParseManifest`.

### Proof of Concept
1. Build a manifest body with `numChunks = 1`, a single PATH chunk TOC row.
2. Set that chunk's declared file offset field (`data[chunkOffset+4:chunkOffset+12]`) to `0x8000000000000010` (a `uint64` with the high bit set).
3. Set the terminating sentinel row's offset field to a value equal to or slightly larger, e.g. `0x8000000000000020`.
4. Recompute and append the trailing SHA-256 over the crafted payload (attacker fully controls all preceding bytes, so this always succeeds).
5. Call `mvcc.ParseManifest(body)`: on a 64-bit `int` platform, both truncated offsets become large negative numbers; `chunkOffsetInFile > dataEnd` is false, `nextChunkOffsetInFile > dataEnd` is false, and `nextChunkOffsetInFile < chunkOffsetInFile` can be made false by choosing the second value slightly greater (less negative) than the first — the malformed chunk passes validation with a `chunkSize` computed from two negative numbers, and later use of `pathChunk.offset`/`size` to slice `data` (`data[start:start+pw]`) panics with an out-of-range slice.
