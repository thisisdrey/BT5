### Title
Non-constant-time RPC auth token comparison enables timing side-channel to recover `auth_token` - (File: `stackslib/src/net/api/blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_v3.rs`, `txsimulate.rs`)

### Summary
Multiple sensitive `/v3` HTTP RPC endpoints authenticate requests by comparing the client-supplied `authorization` header directly against the node's configured secret using Rust's built-in `String`/`&str` equality operator (`!=`). This is a byte-wise, short-circuiting comparison, not a constant-time comparison, mirroring the class of bug in the referenced AWS-LC advisory: an observable timing discrepancy on a security-critical equality check (there, MAC tag validity; here, secret-token validity) lets a remote, unauthenticated attacker use timing analysis to test/recover the secret without needing to already possess it.

### Finding Description
Each of the following handlers guards a privileged endpoint with a plain string comparison between the incoming header and the stored password/token: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

In each case, the pattern is:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`auth_header != password` resolves to `str`/`String`'s `PartialEq`, which is implemented as a length check followed by a byte-slice comparison that returns as soon as a mismatching byte is found (this is the same class of "fail fast on first differing byte" comparison responsible for AES-CCM tag-verification timing leaks in the referenced advisory — CWE-208). This means the time taken to reject a guess is correlated with the number of leading bytes that match the true `auth_token`/password configured via `connection_options.auth_token` (documented at `docs/rpc/openapi.yaml:44-47`), allowing a byte-by-byte timing-based recovery of the secret by an unauthenticated remote attacker who can send repeated requests and measure response latency.

This equality check is the sole authorization gate for these endpoints (block replay, block simulate, fast-call-read-only, block broadcast on `/v3/block_proposal`... i.e., `postblock_v3` broadcast path, and transaction simulate) — breaking it via timing (rather than needing the secret up front) directly undermines the "authenticated vs. stored" equality the advisory calls out.

### Impact Explanation
If exploited, an attacker who statistically recovers the auth token gains write access to sensitive miner/RPC-only endpoints — most notably `postblock_v3`'s `broadcast=1` path, which requires authentication to force block relay/broadcast (`stackslib/src/net/api/postblock_v3.rs:99-122`), and `fastcallreadonly`/`txsimulate`/`blocksimulate` which allow arbitrary contract-call/simulation compute on the node. This matches the "unauthenticated/unauthorized write to state" and "bounded compute DoS on a read endpoint" categories described as Critical/High impact classes for this repo, since it effectively provides an auth-bypass path once the token is inferred through repeated timing probes.

### Likelihood Explanation
Exploitation requires a remote attacker to be able to (a) reach these `/v3` endpoints (they are typically only exposed to trusted signer/miner peers, and many operators may not expose them publicly) and (b) perform a practical, low-noise timing side-channel attack over the network, which is generally harder than a local/co-located timing attack (network jitter reduces signal-to-noise). This lowers real-world likelihood relative to the original in-process AES-CCM case, but the vulnerable pattern is present and unauthenticated exploitation is the documented threat model per CWE-208/GHSA-65p9-r9h6-22vj.

### Recommendation
Replace the direct `!=`/`==` string comparisons on `auth_header` vs the configured secret with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or `ring`/`hmac`-based comparison) across all handlers that gate on `self.auth`/`password`: `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_v3.rs`, `txsimulate.rs`, and any other handler using the same pattern (e.g., `postblock_proposal.rs`, which also stores an `auth` field). Centralize this into a single shared helper function to avoid re-introducing the bug in future endpoints.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. As a remote attacker, repeatedly send POST requests to `/v3/transactions/simulate` (or `/v3/blocks/replay/...`, `/v3/blocks/simulate/...`, `/v3/contracts/fast-call-read/...`, or `/v3/block?broadcast=1`) with an `authorization` header guess that shares an increasing number of correct leading bytes with the real token.
3. Measure response latency for the 401 rejection at `auth_header != password` in the relevant handler (e.g., `stackslib/src/net/api/txsimulate.rs:358-360`); statistically, guesses matching more leading bytes take marginally longer to be rejected due to comparison-length-dependent execution time.
4. Iteratively refine the guess byte-by-byte using timing statistics until the full token is recovered, then use it to submit unauthorized calls (e.g., forced `broadcast=1` block posts via `postblock_v3.rs`).
