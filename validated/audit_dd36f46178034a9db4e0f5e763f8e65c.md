### Title
Unvalidated `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` in `PreReceiveHook` allows storage-path escape outside the repository - (File: `internal/gitaly/hook/prereceive.go`)

### Summary
`validatePreReceiveHookRequest` only checks that the target repository itself is valid [1](#0-0) , but the quarantine object-directory values that end up populating that repository's `GitObjectDirectory`/`GitAlternateObjectDirectories` fields are derived from `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` entries inside the request's own `environment_variables` list, and are converted to relative paths with a bare `filepath.Rel` call that performs no containment check.

### Finding Description
In `preReceiveHook`, the object directory environment values taken from the request's `environment_variables` are converted into `repo.GitObjectDirectory`/`repo.GitAlternateObjectDirectories` via `getRelativeObjectDirs`: [2](#0-1) 

`getRelativeObjectDirs` itself performs no validation that the resulting relative path stays inside the repository: [3](#0-2) 

This is in sharp contrast to the equivalent, hardened code path in `localrepo.Repo.ObjectDirectoryPath`, which explicitly calls `storage.ValidateRelativePath` and additionally enforces that any path failing that check must fall under the storage's expected `QuarantineDirectoryPrefix` for that specific repository before it is trusted: [4](#0-3) 

Because `getRelativeObjectDirs` skips this containment/ownership check, an attacker-supplied `GIT_OBJECT_DIRECTORY=/anything` (or a value containing `../` segments) is accepted and stored as `repo.GitObjectDirectory`. That value is then:
1. Sent to GitLab Rails' `/internal/allowed` endpoint as `GitObjectDirectory`/`GitAlternateObjectDirectories` [5](#0-4) , which Rails re-uses for follow-up Gitaly RPCs that "look at objects being pushed" per the quarantine design doc [6](#0-5) .
2. Directly joined with the real repository path and exported as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` for the *actual* custom `pre-receive` hook subprocess, again without any containment check: `filepath.Join(repoPath, alternateObjectDirectory)` [7](#0-6) .

This is the same class of bug described in the report: state that is supposed to be scoped/owned by one legitimate flow (the real quarantine directory Git creates for a specific push) is consumed by a handler that never verifies it actually belongs to/was generated for the request at hand — allowing the "pending" quarantine value to be forged/redirected.

### Impact Explanation
If an attacker can reach `PreReceiveHook` (or `PostReceiveHook`, which follows the same `GIT_OBJECT_DIRECTORY` extraction pattern) with a crafted `environment_variables` field for a repository they have push access to, they can point `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` at an arbitrary filesystem path outside the intended quarantine/repository tree. Custom hooks and Git subprocesses spawned during the push would then read/search objects from that arbitrary path (potential cross-repository object disclosure or storage escape), and the same forged path is round-tripped to GitLab Rails and back into subsequent Gitaly RPCs, extending the confused-deputy effect beyond the single hook invocation.

### Likelihood Explanation
Reachability depends on whether `HookService` is only invoked internally by the `gitaly-hooks` binary spawned during a real push (in which case `GIT_OBJECT_DIRECTORY` is normally set by Git itself and not directly attacker-chosen), or whether it is additionally exposed on Gitaly's externally-authenticated socket. The test suite explicitly documents this as an open concern: `HookService` is currently reachable over the external API even though "it is a service intended only to be used internally by Gitaly for hook callbacks," tracked as a known issue [8](#0-7) . Given that exposure, and given that `validatePreReceiveHookRequest` does no verification of the environment-derived object-directory values beyond validating the target repository, an authenticated ordinary user able to reach this RPC directly (bypassing the real `git receive-pack` quarantine setup) can supply the crafted values. I could not fully confirm from the index whether external-socket exposure is present in this exact version's routing configuration, so likelihood should be treated as moderate/uncertain pending confirmation of `HookService` registration on the external listener.

### Recommendation
Apply the same containment logic used in `localrepo.Repo.ObjectDirectoryPath` (`storage.ValidateRelativePath` plus the transaction/manual quarantine-prefix check) inside `getRelativeObjectDirs` before assigning `repo.GitObjectDirectory`/`GitAlternateObjectDirectories`, rejecting any value that resolves outside the repository or outside the expected `QuarantineDirectoryPrefix` for that specific repository. Additionally, confirm and close the `HookService`-on-external-socket gap referenced in the test comments so that these hook RPCs can only be invoked by the internal `gitaly-hooks` process for a genuine, Git-generated quarantine directory.

### Proof of Concept
1. Obtain (or forge, if reachable externally) a valid `GITALY_HOOKS_PAYLOAD` for a repository the caller has legitimate access to.
2. Call `PreReceiveHook` directly (bypassing `git receive-pack`), setting `environment_variables` to include the payload plus:
   `GIT_OBJECT_DIRECTORY=/path/outside/repo/objects`
   `GIT_ALTERNATE_OBJECT_DIRECTORIES=/path/outside/repo/objects2`
3. `preReceiveHook` calls `getRelativeObjectDirs(repoPath, "/path/outside/repo/objects", "/path/outside/repo/objects2")`, which computes `filepath.Rel` results such as `../../objects` with no rejection [3](#0-2) .
4. These traversal paths are stored on `repo.GitObjectDirectory`/`GitAlternateObjectDirectories`, sent to Rails' `/internal/allowed`, and later joined back onto `repoPath` in `customHooksEnv` to build `GIT_OBJECT_DIRECTORY` for the actual custom hook execution [7](#0-6) , causing the hook's Git subprocess to search for objects outside the intended repository/quarantine tree.

```go
func getRelativeObjectDirs(repoPath, gitObjectDir, gitAlternateObjectDirs string) (string, []string, error) {
	repoPathReal, err := filepath.EvalSymlinks(repoPath)
	if err != nil {
		return "", nil, err
	}

	gitObjDirRel, err := filepath.Rel(repoPathReal, gitObjectDir)
	if err != nil {
		return "", nil, err
	}

	var gitAltObjDirsRel []string

	for _, gitAltObjDirAbs := range strings.Split(gitAlternateObjectDirs, ":") {
		gitAltObjDirRel, err := filepath.Rel(repoPathReal, gitAltObjDirAbs)
		if err != nil {
			return "", nil, err
		}

		gitAltObjDirsRel = append(gitAltObjDirsRel, gitAltObjDirRel)
	}

	return gitObjDirRel, gitAltObjDirsRel, nil
}
```

```go
func (m *GitLabHookManager) preReceiveHook(ctx context.Context, payload gitcmd.HooksPayload, repo *gitalypb.Repository, pushOptions, envs []string, changes []byte, stdout, stderr io.Writer) error {
	repoPath, err := m.locator.GetRepoPath(ctx, repo)
	if err != nil {
		return structerr.NewInternal("getting repo path: %w", err)
	}

	if gitObjDir, gitAltObjDirs := env.ExtractValue(envs, "GIT_OBJECT_DIRECTORY"), env.ExtractValue(envs, "GIT_ALTERNATE_OBJECT_DIRECTORIES"); gitObjDir != "" && gitAltObjDirs != "" {
		gitObjectDirRel, gitAltObjectDirRel, err := getRelativeObjectDirs(repoPath, gitObjDir, gitAltObjDirs)
		if err != nil {
			return structerr.NewInternal("getting relative git object directories: %w", err)
		}

		repo.GitObjectDirectory = gitObjectDirRel
		repo.GitAlternateObjectDirectories = gitAltObjectDirRel
	}
```

```go
	parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
	baseDir := filepath.Base(relativeObjectDirectoryPath)
	isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))

	// Transactions quarantine a repository by pointing the object directory to a 'quarantine' named
	// directory in the transaction's temporary directory. If the base directory is `quarantine`,
	// Git push may apply an additional layer of quarantine such as `/quarantine/tmp_objdir-incoming-Gbc29N`
	// so we don't assert the `/quarantine` being the last element of the path. We thus also check for
	// whether the parent directory is in `quarantine` and whether the base directory has the expected
	// `tmp_objdir` suffix.
	if !isTransactionQuarantineDir {
		// We need to check whether the relative object directory as given by the repository is
		// a valid path. This may either be a path in the Git repository itself, where it may either
		// point to the main object directory storage or to an object quarantine directory as
		// created by git-receive-pack(1). Alternatively, if that is not the case, then it may be a
		// manual object quarantine directory located in the storage's temporary directory. These
		// have a repository-specific prefix which we must check in order to determine whether the
		// quarantine directory does in fact belong to the repo at hand.
		if _, origError := storage.ValidateRelativePath(repoPath, objectDirectoryPath); origError != nil {
			tempDir, err := repo.locator.TempDir(repo.GetStorageName())
			if err != nil {
				return "", structerr.NewInvalidArgument("getting storage's temporary directory: %w", err)
			}

			expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))
			absoluteObjectDirectoryPath := filepath.Join(repoPath, objectDirectoryPath)

			// The relative path is outside of the repository
			if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
				return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
```

```markdown
During the POST, the internal GitLab API makes Gitaly calls back into the repo to
examine the objects being pushed. For example, if force pushes are not
allowed, GitLab will call the IsAncestor RPC. That RPC call then wants
to look at a commit that is in the process of being pushed. But
because that commit is in quarantine, the RPC will fail because the
commit cannot be found.

### How GitLab passes the object quarantine information around

To overcome this problem, the GitLab `pre-receive` hook
[reads the object directory configuration from its environment](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitlabshell/env.go#L9).
and passes this information
[along with the HTTP API call](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitaly/hook/manager.go#L30-46).
On the Rails side, we then
[put the object directory information in the "request store"](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/api/internal/base.rb#L43)
(i.e., request-scoped thread-local storage). And then during that
Rails request, when Rails makes Gitaly requests on this repo, we send back the quarantine information
[in the Gitaly `Repository` struct](https://gitlab.com/gitlab-org/gitlab/-/blob/f81f30c29a0edce20f6737fdccc3315c8baab9d1/lib/gitlab/gitaly_client/util.rb#L8-17).
```
