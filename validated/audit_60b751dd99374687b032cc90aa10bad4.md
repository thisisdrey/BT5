### Title
Zero `accountIndexOf` bypasses `INITIAL_INDEX` normalization, inflating accrued rewards to the user's full token balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta()` treats an `accountIndexOf` value of `0` as "account never synced" and normalizes it to `INITIAL_INDEX` (1e18) — but only when the global token index is strictly greater than `INITIAL_INDEX`. When the token index equals `INITIAL_INDEX` exactly, the zero fallback is skipped and `_deltaIndex = INITIAL_INDEX - 0`, crediting the account `balance * 1e18` wad (i.e., its entire deposit/debt balance) as claimable rewards. This mirrors the CVE class (a zero/default value bypasses the validation/normalization path) and allows an unprivileged user to mint claimable reward entitlement equal to their balance and drain the distributor's reward-token holdings.

### Finding Description
In `_calculateTokenDelta` ( [1](#0-0) ):

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

`tokenStates[token_].index` is initialized to `INITIAL_INDEX` when the governor first registers a speed for a DepositToken/DebtToken ( [2](#0-1) ). The index only advances when `_tokensAccrued.wadDiv(totalSupply)` produces a nonzero ratio ( [3](#0-2) ), so `index == INITIAL_INDEX` persists for every block in which `delta * speed < totalSupply` — a window that always includes the same block as registration and can be arbitrarily long for small speeds or large supplies.

For any account never touched by `_updateTokensAccruedOf` (`accountIndexOf == 0`), the `> INITIAL_INDEX` guard is false, `_deltaIndex = 1e18`, and `wadMul` by 1e18 returns the full token balance as `_tokensDelta`. `updateBeforeMintOrBurn`/`updateBeforeTransfer` are called by `DepositToken._mint/_burn/_transfer` and `DebtToken` mint/burn ( [4](#0-3) ; [5](#0-4) ), so any user-triggered balance change lands the inflated delta in `tokensAccruedOf`. `claimRewards` then pays it out, capped only by the distributor's reward-token balance ( [6](#0-5) ).

### Impact Explanation
Reward-accrual invariant broken: an attacker with a large deposit-token (or debt-token) balance instantly accrues `tokensAccruedOf` equal to that balance regardless of time or emission speed, then calls `claimRewards` to extract reward tokens up to the contract's full balance. This is theft of other users' unclaimed yield and of protocol reward funds. With a flash loan / leverage via `SmartFarmingManager`, the "balance" can be momentarily inflated far beyond the attacker's capital before triggering `updateBeforeMintOrBurn`, amplifying the theft to the full distributor balance in a single transaction.

### Likelihood Explanation
The trigger requires a registered reward token whose index is still `INITIAL_INDEX` — trivially true right after `updateTokenSpeed`/`syncTokenSpeed` registers or re-registers a token, and persistently true whenever accrued emissions round to zero. The attacker needs no privileged role: `deposit`, `transfer`, `issue`, or `flashIssue` on the tracked token invokes the modifier that calls `updateBeforeMintOrBurn`, and `claimRewards` is permissionless. No pause flag, supply cap, health check, or reentrancy guard intercepts this path; `claimRewards` is `nonReentrant` but the entire exploit is non-reentrant.

### Recommendation
Change the normalization guard in `_calculateTokenDelta` to apply whenever the stored account index is zero and the token index is at least `INITIAL_INDEX` — e.g. `if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) _accountIndex = _tokenIndex;` (initialize late-joining accounts at the *current* index, not `INITIAL_INDEX`). Equivalently, record `accountIndexOf` at mint time so a zero stored value can never produce a nonzero delta.

### Proof of Concept
Hardhat sketch against the repo's own mocks (pattern follows `test/RewardDistributor.test.ts`):

```ts
// setup: pool registered, rewardDistributor funded with rewardToken
await rewardToken.mint(rewardDistributor.address, parseEther('10000'))

// governor registers a speed for the deposit token; tokenStates.index = INITIAL_INDEX = 1e18
await rewardDistributor.updateTokenSpeed(metDepositToken.address, 1) // tiny speed → ratio rounds to 0

// attacker deposits to establish balance BEFORE triggering accrual
await metDepositToken.connect(attacker).deposit(parseEther('5000'), attacker.address)
// (first deposit minted before token tracking mattered, or deposit now — accountIndex stays 0
//  because updateBeforeMintOrBurn only runs when index > 0; index IS > 0 here, so the
//  bug fires on the FIRST balance-changing call: accrued = balance * 1e18 wad = balance)
await metDepositToken.connect(attacker).deposit(1, attacker.address)

expect(await rewardDistributor.claimable(attacker.address)).to.eq(parseEther('5000'))

// drain
await rewardDistributor.connect(attacker).claimRewards(attacker.address)
expect(await rewardToken.balanceOf(attacker.address)).to.be.gt(0) // limited only by contract balance
```

Key assertion: after the second `deposit`, `tokensAccruedOf[attacker] == attacker.balanceOf(depositToken)` even though zero emission time has effectively accrued — demonstrating that the zero `accountIndexOf` bypasses the `INITIAL_INDEX` normalization.
