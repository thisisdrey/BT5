Unbounded in-memory buffering of all tree entries before pagination in GetTreeEntries causes DoS - ([File: internal/gitaly/service/commit/get_tree_entries.go])

### Summary
`sendTreeEntriesUnified` fully materializes every entry of a requested tree (via `tree.Walk`) into an `entries []*gitalypb.TreeEntry` slice, sorts the entire slice, and only afterwards calls `paginateTreeEntries` to truncate it to the caller-supplied `PaginationParameter.Limit`. An attacker who controls the content of a repository they own can push a tree with an extremely large number of entries and issue a single `GetTreeEntries` RPC with `Recursive=true` and a tiny `Limit`, forcing Gitaly to allocate memory and CPU proportional to the full tree size regardless of the requested page size.

### Finding Description
In `internal/gitaly/service/commit/get_tree_entries.go`, `sendTreeEntriesUnified` calls `repo.ReadTree(..., localrepo.WithRecursive())` [1](#0-0)  which, for the recursive case, internally calls `rootEntry.populate(ctx, repo)` in `internal/git/localrepo/tree.go`. `populate` runs `git ls-tree -r` for the whole subtree and builds a full in-memory `TreeEntry` graph via a `treeStack`, with no cap on entry count [2](#0-1) .

After `ReadTree` returns, `sendTreeEntriesUnified` walks that in-memory tree with `tree.Walk`, appending every single entry into a plain Go slice `entries` with unbounded growth (`entries = append(entries, newEntry)`), then sorts the entire slice with `sortTrees`, and only then applies pagination: [3](#0-2) .

`paginateTreeEntries` performs a simple slice operation to truncate the already fully-built and fully-sorted slice down to `p.GetLimit()` [4](#0-3) . There is no upstream cap on the number of tree entries a repository/tree may contain, no streaming/early-termination in `tree.Walk`/`populate`, and no RPC-level limit on tree size in this service. The only "checks" performed (`validateGetTreeEntriesRequest`) validate the repository and revision/path format, not the tree cardinality [5](#0-4) , so none of them mitigate this.

An unprivileged user can create/fork a repository, commit a tree with millions of small blobs in a flat directory (a normal, valid git operation requiring no privileged Gitaly access), and then call `GetTreeEntries` with `Recursive=true` and `PaginationParameter.Limit=1`. Gitaly will still spawn `git ls-tree -r`, parse all N entries into `TreeEntry` objects, walk them into a second slice of `gitalypb.TreeEntry` protobuf objects (each with allocated `Path`/`Oid`/`FlatPath` byte slices), sort the whole slice, and only discard N-1 of them at the last step.

### Impact Explanation
A single RPC call from any repository owner can force the Gitaly process to allocate memory and CPU proportional to the size of an attacker-controlled tree (potentially many millions of entries), independent of the requested pagination limit. This can lead to significant memory pressure, GC thrash, or OOM on the Gitaly node, degrading or crashing the process and affecting other repositories/tenants served by the same node — a resource exhaustion of an RPC handler, matching GitLab's DoS bounty impact class.

### Likelihood Explanation
The precondition is minimal: the attacker only needs to own or fork a repository (default capability of any authenticated GitLab user) and be able to push commits and call a read-only RPC (`GetTreeEntries`) that is reachable from normal GitLab web/API usage (e.g., browsing a repository tree). Constructing a tree with millions of entries is a standard, unprivileged git operation (`git mktree`/`git commit-tree`) requiring no special server-side configuration. The attack is fully repeatable and can be triggered repeatedly to sustain pressure on the Gitaly node.

### Recommendation
Bound the work done before pagination is applied:
- Stream tree entries directly to `paginateTreeEntries`/the response sender rather than buffering the entire tree into `entries` first, or apply pagination during the `tree.Walk` callback (stop walking once `limit` entries past the start index have been collected, when no cursor-based re-sort is required).
- Alternatively, when sorting is required (`sort != DEFAULT`), still enforce a hard maximum tree entry count in `populate`/`listEntries`/`tree.Walk` and reject or truncate with an explicit resource-limit error rather than buffering unbounded data.
- Consider adding a configurable maximum number of tree entries per `GetTreeEntries` request, returning a `ResourceExhausted` gRPC error when exceeded.

```go
func paginateTreeEntries(ctx context.Context, entries []*gitalypb.TreeEntry, p *gitalypb.PaginationParameter, rootTreeOID git.ObjectID) ([]*gitalypb.TreeEntry, string, error) {
	limit := int(p.GetLimit())

	start, tokenTreeOID, tokenType := decodePageToken(p.GetPageToken())

	index := -1

	// No token means we should start from the top
	if start == "" {
		index = 0
	} else {
		for i, entry := range entries {
			if buildEntryToken(entry, tokenType) == start {
				index = i + 1
				break
			}
		}
	}

	if index == -1 {
		return nil, "", structerr.NewInvalidArgument("could not find starting OID: %s", start).WithMetadataItems(
			structerr.MetadataItem{Key: "page_token_tree_oid", Value: tokenTreeOID},
			structerr.MetadataItem{Key: "tree_oid", Value: rootTreeOID.String()},
			structerr.MetadataItem{Key: "token_type", Value: tokenType},
		)
	}

	if limit == 0 {
		return nil, "", nil
	}

	if limit < 0 || (index+limit >= len(entries)) {
		return entries[index:], "", nil
	}

	paginated := entries[index : index+limit]

	newPageToken, err := encodePageToken(paginated[len(paginated)-1], rootTreeOID)
	if err != nil {
		return nil, "", fmt.Errorf("encode page token: %w", err)
	}

	return paginated, newPageToken, nil
}
```

```go
func (t *TreeEntry) populate(
	ctx context.Context,
	repo *Repo,
) error {
	if t.OID == "" {
		return errors.New("oid is empty")
	}

	t.Entries = nil

	entries, err := repo.listEntries(
		ctx,
		git.Revision(t.OID),
		"",
		true,
	)
	if err != nil {
		return err
	}

	stack := treeStack{t}

	// The output of ls-tree -r is the following:
	// a1
	// dir1/file2
	// dir2/file3
	// f2
	// f3
	// Whenever we see a tree, push it onto the stack since we will need to
	// start adding to that tree's entries.
	// When we encounter an entry that has a lower depth than the previous
	// entry, we know that we need to pop the tree entry off to get back to the
	// parent tree.
	for _, entry := range entries {
		if levelsToPop := len(stack) - depthByPath(entry.Path); levelsToPop > 0 {
			for i := 0; i < levelsToPop; i++ {
				stack.pop()
			}
		}

		entry.Path = filepath.Base(entry.Path)
		stack.peek().Entries = append(
			stack.peek().Entries,
			entry,
		)

		if entry.Type == Tree {
			stack.push(entry)
		}
	}

	if err != nil {
		return fmt.Errorf("listing entries: %w", err)
	}

	return nil
}
```
