### Title
Unbounded per-chunk 32KB buffer allocation/zeroing in `StacksHttpRecvStream::consume_data` allows CPU/allocator amplification DoS via tiny HTTP chunks - (File: stackslib/src/net/httpcore.rs)

### Summary
`StacksHttpRecvStream::consume_data` allocates and zero-initializes a fresh `vec![0u8; CHUNK_BUF_LEN]` (32768 bytes) on every pass of its inner `while !blocked` loop, regardless of how few bytes `self.state.do_read` actually decodes on that pass. A malicious HTTP peer that this node is fetching chunked-transfer-encoded response data from can send many tiny chunks (e.g. minimal `1\r\nX\r\n`-style chunk framing) to force many such 32KB allocation/zero passes for a small amount of wire data, amplifying allocator/memset work relative to bytes actually transferred.

### Finding Description
The loop body allocates `decoded_buf` fresh each iteration: [1](#0-0) 
Each iteration calls `self.state.do_read(fd, &mut decoded_buf)`, and as long as it returns `num_read > 0` (i.e. not blocked), the loop continues and reallocates a brand-new 32768-byte, zero-filled `Vec<u8>`, even if `num_read` for that pass was just 1 or a few bytes. There is no reuse of a single buffer across iterations, and no floor on how many encoded bytes must be consumed per pass to bound the number of passes relative to `CHUNK_BUF_LEN`. Since HTTP chunked-transfer framing allows arbitrarily small chunk sizes (down to 1-byte payloads), a peer serving the response can encode its payload as a very large number of tiny chunks within a single TCP read event, causing `consume_data` to execute many loop passes — and therefore many 32KB allocate+zero operations — while transferring comparatively few actual bytes over the wire in that call.

This is bounded, however, by the size cap already imposed on the decoded stream: `StacksHttpRecvStream::new(max_size)` constructs `HttpChunkedTransferReaderState::new(max_size)`, and `self.state.do_read` enforces that cap (attempts to exceed it produce an error/abort, not further reads). So the number of loop passes within a single logical HTTP response is bounded by `max_size` divided by the minimal per-chunk decode granularity, not unbounded — the attack is a constant-factor (up to ~32768x) amplification of allocation/zeroing work relative to bytes actually decoded, not an unbounded loop.

### Impact Explanation
The affected code path is exercised on the client side when this node issues outgoing HTTP requests to another peer and receives a chunked response (e.g. fetching data via the RPC/P2P HTTP client machinery). A malicious peer that this node connects to can shape its chunked response encoding to maximize the number of small chunks, forcing this node to perform a disproportionate number of 32KB buffer allocations/zero-fills per unit of actual payload received. This consumes extra CPU and allocator churn on the fetching node for every such response, and is repeatable on every request/response cycle the attacker peer serves. This matches the "bounded compute DoS on a read endpoint" category, since the amplification is capped by the message's `max_size`, but the overhead is disproportionate to bytes transferred (up to ~32768x memset work per chunk).

### Likelihood Explanation
Precondition: the node must actively be fetching chunked HTTP response data from a peer that the attacker controls (e.g. the attacker runs a peer/HTTP server that this node connects to for RPC-style responses). This requires no privileged role, no secret, and no other node's key — only that the victim node chooses to fetch data from the attacker's endpoint, which is a normal peer interaction. The attacker's cost is minimal: crafting many tiny HTTP chunks is cheap and requires no special resources, and the effect is repeatable on each response served by the attacker.

### Recommendation
Allocate `decoded_buf` once, outside the `while !blocked` loop, and reuse it across iterations (only re-zeroing/reusing the portion actually written each pass), so buffer allocation is amortized across a single `consume_data` call rather than paid per read pass. Additionally, consider tracking the number of decode iterations or minimum bytes-per-pass to detect/reject peers sending degenerate, excessively fragmented chunk streams.

### Proof of Concept
Add a test in `stackslib/src/net/httpcore.rs` (or a new test module) that:
1. Constructs a `StacksHttpRecvStream::new(max_size)` with a large enough `max_size`.
2. Feeds it an in-memory `Read` source containing many minimal chunks, e.g. repeating `b"1\r\nX\r\n"` thousands of times followed by the terminating `0\r\n\r\n`.
3. Instruments (or wraps) the allocation of `decoded_buf` (e.g. via a custom allocator counter or by refactoring temporarily to count loop iterations) to assert that the number of `CHUNK_BUF_LEN`-sized allocations is proportional to `total_encoded_bytes / CHUNK_BUF_LEN` rather than to `total_encoded_bytes / 6` (the minimal chunk size), demonstrating the amplification: `assert!(allocation_count * CHUNK_BUF_LEN <= total_bytes_transferred * K)` fails for small `K` given the crafted tiny-chunk input, proving allocation work scales with chunk count, not with bytes transferred.
