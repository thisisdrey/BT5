## Title
SSRF via peer-supplied `data_url`: authenticated remote peers can steer node-initiated HTTP requests to arbitrary internal targets - (File: `stackslib/src/net/chat.rs`, `stackslib/src/net/server.rs`, `stackslib/src/net/neighbors/rpc.rs`)

### Summary
Any remote peer that completes the p2p handshake can advertise an arbitrary `data_url` (an HTTP endpoint string, not the socket it connected from). Once the node resolves this URL's DNS/IP and stores it on the `ConversationP2P`, the download/RPC layers (`NeighborRPC::send_request`, `PeerNetwork::connect_or_send_http_request` → `HttpPeer::connect_http`) will open an outbound HTTP connection to whatever address that URL resolves to — with no check that the resolved address is not a loopback/private/internal address.

### Finding Description
`ConversationP2P::try_decode_data_url_ipaddr`/DNS resolution in `stackslib/src/net/chat.rs:2805-2910` resolves `self.data_url` (a value supplied by the *remote* peer during handshake) to `self.data_ip`, with no filtering against `PeerAddress::is_in_private_range()` or loopback addresses anywhere in this resolution path. Once resolved, `NeighborRPC::send_request` (`stackslib/src/net/neighbors/rpc.rs:195-228`) reads `convo.data_url` / `convo.data_ip` directly and calls `PeerNetwork::with_http(...).connect_http(...)`, which in `stackslib/src/net/server.rs:118-150` opens a raw `NetworkState::connect(&addr, ...)` TCP connection to that address and (for Nakamoto tenure/unconfirmed downloaders in `stackslib/src/net/download/nakamoto/tenure_downloader.rs:708-751` and `tenure_downloader_set.rs`) sends a crafted `StacksHttpRequest` (e.g., a GetBlock/GetTenure-style request) to it.

Contrast this with `stackslib/src/net/p2p.rs:1880-1936` (`can_register_peer`), which *does* reject a **p2p neighbor's own socket address** if it's in a private range (unless `private_neighbors` is enabled), and with `stackslib/src/net/mempool/mod.rs:485-498`, which explicitly re-checks `PeerAddress::from_socketaddr(addr).is_in_private_range()` immediately before issuing the mempool-sync HTTP query. No equivalent check exists for the `data_url`-resolved address used by `connect_or_send_http_request`/`connect_http`/`NeighborRPC::send_request`, which is a **separate, attacker-supplied field** distinct from the peer's connecting socket address. This breaks the intended equality "outbound HTTP targets == vetted, non-internal peer addresses," analogous to the OpenClaw Feishu SSRF where a remote-influenced URL bypassed policy checks that existed elsewhere in the codebase.

The `blocked_urls` DNS-ban mechanism that could mitigate this exists only in `stackslib/src/net/download/epoch2x.rs`, which is explicitly out of scope (legacy epoch2x downloader), and does not filter by private-IP range anyway — it only bans URLs that fail to connect/time out, not internal targets that succeed.

### Impact Explanation
A single unprivileged, remote peer that authenticates over p2p (from a public IP, satisfying `can_register_peer`) can set its handshake `data_url` to point at an internal service (e.g., `http://127.0.0.1:<port>`, `http://169.254.169.254/...`, or an internal admin port), and cause the victim node to issue an HTTP request there whenever a Nakamoto tenure/unconfirmed downloader or other `NeighborRPC`-based download path selects that neighbor. Depending on the internal service, this can yield internal reconnaissance/probing (open-port detection via timing/response), or interaction with unauthenticated internal HTTP endpoints reachable only from localhost/the private network. This matches the High-severity SSRF pattern in the source report (unauthenticated write/read triggered against internal services via an attacker-controlled URL fetch), though the concrete blast radius depends on what is reachable on the node's local network.

### Likelihood Explanation
Likelihood is limited by the requirement that a remote peer first complete the p2p handshake (which is not privileged — anyone can run a Stacks node and connect outbound/inbound) and then be selected as a download source by a Nakamoto downloader or `NeighborRPC` consumer. This does not require the node secret or any elevated role, and node operators commonly accept inbound connections from arbitrary IPs, making this reachable by any remote, unauthenticated (in the application sense) participant.

### Recommendation
Before resolving/using a peer-supplied `data_url` for outbound HTTP (in `chat.rs` DNS resolution and in `server.rs::connect_http` / `httpcore.rs::connect_or_send_http_request`), apply the same `PeerAddress::is_in_private_range()` / anynet / loopback checks that are already applied to raw p2p neighbor socket addresses in `p2p.rs::can_register_peer` and to mempool-sync targets in `mempool/mod.rs`, respecting the `private_neighbors` config flag uniformly across all outbound-HTTP call sites (including the Nakamoto downloader paths), not just the legacy epoch2x downloader and mempool sync.

### Proof of Concept
1. Run a malicious Stacks node and configure it (or patch it) to advertise `data_url = "http://127.0.0.1:<internal_port>"` in its p2p handshake `HandshakeData`.
2. Connect this malicious node as a peer to a victim node (satisfies `can_register_peer` since the *connecting* socket address is public).
3. Wait for the victim's Nakamoto downloader (or any `NeighborRPC` consumer) to select this neighbor and call `send_next_download_request` → `NeighborRPC::send_request` (`stackslib/src/net/neighbors/rpc.rs:195`).
4. Observe (e.g., via a local listener on the victim host at the advertised port, or timing/behavior differences) that the victim node opens a TCP/HTTP connection to `127.0.0.1:<internal_port>` — an address never reachable to the remote attacker directly, confirming SSRF via the p2p peer's `data_url`.
