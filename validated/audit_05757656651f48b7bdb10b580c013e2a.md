### Title
Snowbridge Outbound Queue V2 `validate()` Omits Destination/Channel Registration Check Present in V1 - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`)

### Summary
The external report's core broken invariant is: a public bridge-out entry point lets a caller select an arbitrary destination without verifying that the destination is actually configured/registered to receive the message, so value gets irreversibly burned/sent into a black hole. The exact same invariant is missing in Snowbridge's V2 outbound queue: unlike its own V1 sibling, the V2 `SendMessage::validate` implementation never checks that the message's `origin` corresponds to a registered channel/agent before the message is queued, fee-charged, committed into the Ethereum-bound merkle root, and a `PendingOrder` created for relayer reward.

### Finding Description
In the V1 pallet, `SendMessage::validate` explicitly guards against unregistered destinations: [1](#0-0) 

This ensures a message can only be accepted if `T::Channels::contains(&message.channel_id)` is true — i.e., there is a real channel configured to receive it on the Ethereum side.

In the V2 pallet, the analogous `validate` function performs only a size check and returns `Ok` unconditionally, with no equivalent check on `message.origin` against any registry of valid channels/agents: [2](#0-1) 

The pallet's own error enum even still defines `InvalidChannel` as a variant that is never actually raised for outbound submission in V2: [3](#0-2) 

Once `validate`/`deliver` succeed, `do_process_message` unconditionally converts the message to an `OutboundMessage`, appends it to `Messages`/`MessageLeaves`, creates a `PendingOrder` charging the message's `fee`, and increments `Nonce` — with no re-validation of `origin` against a channel registry: [4](#0-3) 

The merkle root is then committed into the parachain header digest for offchain relayers to prove and deliver to Ethereum: [5](#0-4) 

This is structurally the same class of bug as the report: a public "bridge-out" pipeline accepts and commits a payload for an arbitrary/unvalidated destination identifier (`origin`/agent), with the fee already deducted and consumed and the item already "burnt"/queued on the source side, while nothing guarantees the destination-side agent/channel actually exists or is authorized to process that origin on Ethereum.

### Impact Explanation
If `origin` does not correspond to a channel/agent that the Ethereum Gateway recognizes, the committed message will still be included in the merkle root and a `PendingOrder` will still be created with the fee reserved for a relayer. Funds paid for delivery (`fee`) are consumed and the message occupies queue/commitment capacity, but on the Ethereum side dispatch for an unregistered agent/channel would fail or be unroutable, mirroring the reported "item lost because destination not configured" bug: value/state is consumed on the source chain with no way to recover it, and no successful settlement occurs on the destination side. This falls under the "public underpriced work that degrades bridge processing" / "duplicate settlement or payout" and "permanent user-fund or bridge-state lock" impact classes, since the relayer/fee-payer's fee is spent for a message that cannot be meaningfully delivered.

### Likelihood Explanation
This is a public-entrypoint issue reachable by any caller who can construct a V2 `Message` (via XCM export through `EthereumBlobExporter`/`snowbridge-pallet-system-v2::send`) with an origin/agent that has not been registered as a channel. No malicious relayer, validator, governance actor, or privileged role is required — an ordinary unprivileged caller supplying an arbitrary/incorrect origin triggers the missing-check path directly through the standard XCM/system-v2 send flow.

### Recommendation
Add the same registered-channel/agent existence check to `outbound-queue-v2`'s `validate()` that V1 already enforces, e.g.:
```rust
ensure!(T::Channels::contains(&message.origin), SendError::InvalidChannel);
```
requiring a `Config::Channels` (or equivalent agent registry) associated type in `outbound-queue-v2::Config`, populated by `snowbridge-pallet-system-v2` agent/channel registration, and validated before the message is queued, fee-charged, or committed.

### Proof of Concept
1. Construct (or have `snowbridge_pallet_system_v2::Pallet::send` / `EthereumBlobExporter` construct) a V2 `Message { origin: <unregistered_agent_id>, id, fee, commands }`.
2. Call `OutboundQueue::validate(&message)` (per `SendMessage` impl at `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs:23-32`) — it succeeds because only payload size is checked.
3. `deliver(ticket)` enqueues the message via `T::MessageQueue::enqueue_message` — no origin/channel check occurs.
4. `do_process_message` processes it into `Messages`/`MessageLeaves`, creates a `PendingOrder` with the attached `fee`, increments `Nonce`, and emits `MessageAccepted` — all without ever verifying `origin` is a registered channel.
5. The message is committed into the header digest merkle root and relayed off-chain; on the Ethereum Gateway, dispatch for the unregistered agent/origin cannot be correctly attributed/executed, while the fee has already been reserved in `PendingOrders`, reproducing the "item bridged to inactive/unconfigured destination" loss pattern from the report.

impl<T> SendMessage for Pallet<T>
where
	T: Config,
{
	type Ticket = Message;

	fn validate(message: &Message) -> Result<Self::Ticket, SendError> {
		// The inner payload should not be too large
		let payload = message.encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		Ok(message.clone())
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = ticket.origin.into();

		let message =
			BoundedVec::try_from(ticket.encode()).map_err(|_| SendError::MessageTooLarge)?;

		T::MessageQueue::enqueue_message(message.as_bounded_slice(), origin);
		Self::deposit_event(Event::MessageQueued { message: ticket.clone() });
		Ok(ticket.id)
	}
