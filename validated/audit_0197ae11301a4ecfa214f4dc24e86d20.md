## Analysis

The bug class in the report — a periodically-refreshed, off-critical-path state variable (`pricePerShare`) that consumers trust without a freshness check, letting an attacker act while it is stale and profit once it catches up — has a reachable analog in the QUIC streamer's stake-weighted QoS throttling, which is explicitly in-scope (unprivileged client path).

### Title
Stale/lagging `StakedStreamLoadEMA` load estimate lets a staked QUIC client evade stake-weighted stream throttling - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`SwQos` gates how many QUIC streams a staked peer may open per 100 ms window using `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration`, which switches behavior based on a boolean `staked_throttling_enabled` flag [1](#0-0) . That flag is derived from a smoothed EMA of recent global staked-stream load that is only recomputed opportunistically (on stream accept/error/close) and at most once every `STREAM_LOAD_EMA_INTERVAL_MS` (5 ms), similar in spirit to `WrappedIbbtcEth.pricePerShare` only being refreshed by an external, best-effort trigger.

### Finding Description
`update_ema_if_needed` only recomputes the EMA when a stream event happens to call it, and it is deliberately smoothed to avoid reacting to short bursts: [2](#0-1) [3](#0-2) 

While `staked_throttling_enabled` is `false` (i.e., the EMA has decayed below `staked_throttling_on_load_threshold`, which happens naturally during idle periods or at the very start of a leader slot), `available_load_capacity_in_throttling_duration` grants **any** staked peer, regardless of its stake fraction, the *entire* `max_staked_load_in_throttling_window` — not a stake-weighted share: [4](#0-3) 

Only once sustained load pushes the EMA back over the threshold does `available_load_capacity_in_throttling_duration` fall back to the intended stake-proportional formula (`max_staked_load_in_throttling_window * stake / total_stake`). This is directly analogous to the reported bug: a value cached/derived from an external, event-driven update path (`pricePerShare` / `staked_throttling_enabled`) is consumed by downstream logic (`mint`/`burn` / QoS admission) without verifying it reflects current ground truth, and there is no bound on how stale it may be beyond "whenever an update happens to fire."

### Impact Explanation
A staked (even minimally staked) client can time a burst of QUIC stream opens for the window where `staked_throttling_enabled` is `false` — e.g., immediately following an idle interval or at the very start of a new leader's slot, which the code comments acknowledge can span up to ~40 ms of un-throttled absorption by design — and receive the full staked throttling budget instead of its proportional stake share. This is a QoS evasion: a low-stake unprivileged peer obtains disproportionate TPU stream/packet ingestion bandwidth relative to well-behaved peers, which is one of the explicitly accepted impact categories for this analysis.

### Likelihood Explanation
The condition is reachable by any unprivileged staked QUIC client without any validator/operator role, requiring only stake (even minimal, since capacity is not stake-weighted while the flag is off) and an ordinary QUIC connection to the TPU/TPU-forward endpoints. The staleness window is deterministic and partially observable/predictable (leader-slot boundaries, low-traffic periods), making the exploit conditions reasonably attainable, though the magnitude is bounded by the short EMA smoothing window (tens of ms) rather than unbounded.

### Recommendation
Bound the maximum time the throttling decision may rely on a stale EMA snapshot independent of externally-driven update triggers — e.g., drive `update_ema_if_needed` from a dedicated background timer instead of purely from stream events, or cap the burst capacity granted while `staked_throttling_enabled` is `false` to a stake-weighted value rather than the unscaled `max_staked_load_in_throttling_window`, so no peer can receive more than its fair share even during EMA catch-up.

### Proof of Concept
1. A staked peer observes/predicts a window where global staked stream load is low (e.g., right after an idle period, or right at the start of a new leader slot as acknowledged in the code comment at [2](#0-1) ).
2. During this window `staked_throttling_enabled` is `false` because the smoothed EMA has decayed.
3. The peer opens a burst of QUIC uni-streams; `available_load_capacity_in_throttling_duration` grants it up to `max_staked_load_in_throttling_window` streams (the full staked budget) rather than its `stake / total_stake` proportional share [5](#0-4) .
4. Only after enough streams accumulate does `update_ema` (triggered by `on_stream_accepted`) push the EMA back over threshold and re-enable proportional throttling [6](#0-5) , by which point the disproportionate burst has already been admitted.

    pub(crate) fn update_ema_if_needed(&self) {
        const EMA_DURATION: Duration = Duration::from_millis(STREAM_LOAD_EMA_INTERVAL_MS);
        // Read lock enables multiple connection handlers to run in parallel if interval is not expired
        if Instant::now().duration_since(*self.last_update.read().unwrap()) >= EMA_DURATION {
            let mut last_update_w = self.last_update.write().unwrap();
            // Recheck as some other thread might have updated the ema since this thread tried to acquire the write lock.
            let since_last_update = Instant::now().duration_since(*last_update_w);
            if since_last_update >= EMA_DURATION {
                *last_update_w = Instant::now();
                self.update_ema(since_last_update.as_millis());
            }
        }
    }

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
