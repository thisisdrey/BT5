### Title
Unbounded `pages_indexes` token parsing before `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` cap is enforced - (File: stackslib/src/net/api/getattachmentsinv.rs)

### Summary
`RPCGetAttachmentsInvRequestHandler::try_parse_request` parses every comma-separated token of the `pages_indexes` query parameter into a `u32` and inserts it into a `HashSet`, with no limit on the number of tokens processed. The 8-entry cap (`MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`) is only checked afterward, in `try_handle_request`, meaning an attacker-controlled token count directly drives the cost of `try_parse_request` regardless of the eventual rejection.

### Finding Description
The equality that should hold is: *work done parsing `page_indexes` == work bounded by `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`*. Instead, `try_parse_request` at `stackslib/src/net/api/getattachmentsinv.rs:96-100` iterates `pages_indexes_value.split(',')` and performs a `u32::parse` plus a `HashSet::insert` per token with no early exit or count limit. Only later, in `try_handle_request` (`stackslib/src/net/api/getattachmentsinv.rs:159-168`), is `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) checked and the request rejected with `HttpBadRequest`. An unauthenticated remote client hitting `GET /v2/attachments/inv?index_block_hash=...&pages_indexes=0,1,2,...,N` forces full parsing and hashing of N tokens before the 8-item bound is ever enforced.

However, this cost is bounded by whatever HTTP request-line/query-string length limit exists elsewhere in the HTTP preamble parsing layer (e.g., total request line/header size caps). I was unable to locate and confirm the exact numeric cap on overall URL/query length in this codebase within the available search results, so I cannot definitively state the maximum N achievable, but such generic line-length limits are explicitly called out as out-of-scope/already assumed bounding in the question itself ("bounded only by generic HTTP line-length limits elsewhere").

### Impact Explanation
Per request, the attacker forces the node to perform O(N) `u32` parses and hash-set insertions for values of N up to whatever the outer HTTP line-length limit permits, before the request is rejected for exceeding the 8-page cap. This is a bounded compute amplification on a read endpoint (`/v2/attachments/inv`), repeatable per request, and does not require any privileged role — matching the "bounded compute DoS on a read endpoint" category under High severity. It does not cause a crash, forged/stored state, or write — the request is ultimately rejected and no attachment data is served or persisted incorrectly.

### Likelihood Explanation
No preconditions beyond network reachability to the node's RPC port are required — no secret, no peer relationship, no StackerDB slot. Attacker cost is a single crafted HTTP GET request with a long `pages_indexes` query parameter, and it is trivially repeatable at will, limited only by however large a query string the server's outer HTTP preamble/URL length limit permits.

### Recommendation
Enforce the token/entry count cap on `pages_indexes` inline during the `split(',')` loop in `try_parse_request` (e.g., break/return `Err(Error::DecodeError(...))` once more than `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` distinct or raw tokens have been seen), rather than deferring the length check to `try_handle_request`. This bounds parsing work to O(cap) regardless of attacker-supplied token count.
