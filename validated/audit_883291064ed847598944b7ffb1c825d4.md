### Title

Deposit-token dust can exhaust `feeCollector`'s account-token cap and block fee-bearing withdrawals and liquidations - ([File: contracts/Pool.sol])

### Summary

`Pool` enforces a global `MAX_TOKENS_PER_USER` limit of 30 combined deposit and debt tokens per account, including the protocol `feeCollector`. An unprivileged user can transfer one wei of distinct registered `DepositToken` shares to `feeCollector`, permanently occupying its available slots. Subsequent deposits, withdrawals, or liquidations that would pay a fee in a deposit token not already present in the fee collector's list revert while attempting to add that token. This can temporarily freeze withdrawals or prevent liquidations until governance changes the fee collector, fees are disabled, or the collector removes balances.

### Finding Description

`Pool.addToDepositTokensOfAccount` rejects an addition whenever the target account already has 30 total tracked tokens. [1](#0-0) [2](#0-1) 

Every public `DepositToken.transfer` calls `_transfer`, and `_transfer` adds the token to the recipient's per-account list whenever the recipient previously had zero balance and receives a nonzero amount. [3](#0-2) [4](#0-3) 

The same list insertion occurs when deposit fees are minted to the fee collector and when withdrawal fees are transferred to it. [5](#0-4) [6](#0-5) 

Liquidations also transfer the protocol-fee portion to `poolRegistry.feeCollector()` through `DepositToken.seize`, which uses the same `_transfer` path. [7](#0-6) [8](#0-7) 

### Impact Explanation

Once the fee collector's combined list reaches 30 entries, any operation requiring a positive fee in a new deposit token reverts with `UserReachedMaxTokens` after the balance transfer has been initiated. Because the whole transaction reverts, fee-bearing withdrawals cannot complete, fee-bearing liquidations cannot complete, and deposits whose fee mint would introduce a new token cannot complete. [9](#0-8) [7](#0-6) 

This is not merely an expensive loop: the fixed cap causes a deterministic state transition failure, and the attacker can establish it without privileged access. Funds remain recoverable only if the existing collateral token is already in the collector list, its fee is zero, the fee configuration changes, governance replaces the fee collector, or the collector can move enough listed balances to free a slot. [1](#0-0) 

### Likelihood Explanation

The attack requires only balances of registered `DepositToken` shares and public ERC-20-style transfers. An attacker can acquire small positive balances by depositing small amounts into active deposit tokens and then transfer one unit of each token to `feeCollector`; `transfer` checks only the sender's unlocked balance and allows an arbitrary recipient. [10](#0-9) [3](#0-2) 

The attack is conditional on a deployed pool having enough registered deposit tokens to fill the fee collector's remaining slots and on positive deposit, withdrawal, or liquidation protocol fees. The nonReentrant guards, pause flags, deposit-token existence checks, and collateral locks do not prevent an unencumbered attacker from sending dust to the fee collector. [11](#0-10) [4](#0-3) 

### Recommendation

Do not enforce `MAX_TOKENS_PER_USER` for protocol accounting recipients that are forced to accept fees, particularly `feeCollector`, or track deposit tokens for `feeCollector` separately without a cap. Alternatively, make `Pool.addToDepositTokensOfAccount` tolerate `feeCollector` additions and exclude that account from user-position enumeration, while preserving bounded iteration for normal borrowers and suppliers.

### Proof of Concept

```ts
// Hardhat fork test sketch.
// Assumptions:
// - pool has at least 30 registered DepositToken contracts;
// - withdrawFee or liquidation protocolFee is nonzero;
// - victim holds collateral depositTokenToBlock not yet held by feeCollector.

const pool = await ethers.getContractAt("IPool", POOL);
const registry = await ethers.getContractAt("IPoolRegistry", REGISTRY);
const feeCollector = await registry.feeCollector();

const tokens = await pool.getDepositTokens();

// Deposit or otherwise obtain a nonzero balance of each token, then dust
// feeCollector until its combined tracked-token count reaches the cap.
for (const tokenAddress of tokens) {
  const depositToken = await ethers.getContractAt("IDepositToken", tokenAddress);
  await depositToken.connect(attacker).transfer(feeCollector, 1);
}

expect(
  (await pool.getDepositTokensOfAccount(feeCollector)).length +
    (await pool.getDebtTokensOfAccount(feeCollector)).length
).to.equal(await pool.MAX_TOKENS_PER_USER());

// Pick a deposit token that was not transferred to feeCollector above.
const blockedToken = await ethers.getContractAt(
  "IDepositToken",
  tokenNotHeldByFeeCollector
);

// If withdrawFee > 0, the fee transfer tries to add blockedToken to
// feeCollector's already-full list and the whole withdrawal reverts.
await expect(
  blockedToken.connect(victim).withdraw(victimBalance, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// Likewise, Pool.liquidate(...) reverts when its protocol fee calls
// depositToken.seize(account, feeCollector, fee) for an unlisted token.
await expect(
  pool.connect(liquidator).liquidate(
    syntheticToken,
    victim.address,
    amountToRepay,
    blockedToken.address
  )
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

The decisive assertion is that `feeCollector` reaches `MAX_TOKENS_PER_USER` and a fee transfer in an unlisted `DepositToken` reverts, because `_transfer` attempts `pool.addToDepositTokensOfAccount(feeCollector)`. [1](#0-0) [4](#0-3)
