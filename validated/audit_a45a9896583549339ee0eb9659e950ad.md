Based on my investigation, I found a concrete analog to CVE-2020-10752's bug class (sensitive data leaking into logs on error/panic path).

### Title
Uncaught exceptions in shielded-transaction HTTP servlets leak spend-authorizing keys (ask/nsk/ovk/spending key) into node logs via the global `RateLimiterServlet` error handler - (File: `framework/src/main/java/org/tron/core/services/http/RateLimiterServlet.java`)

### Summary
Every HTTP API servlet in java-tron extends `RateLimiterServlet`, whose overridden `service()` method wraps the dispatch to the concrete servlet in a catch-all handler. Any exception that is not a `ServletException`/`IOException`/`BadMessageException` and is not already swallowed inside the specific servlet's own `doGet`/`doPost` is logged at ERROR level with the full exception object (stack trace, message, and cause chain) via `logger.error("Http Api {}, Method:{}. Error：", url, req.getMethod(), unexpected)`. [1](#0-0) 

Several shielded-transaction endpoints accept highly sensitive secret key material directly as request parameters/body fields: `ask` (spend authorizing key), `nsk` (proof authorizing key), `ovk` (outgoing viewing key), and the raw Sapling spending key (`sk`). These are carried end-to-end as raw bytes through `PrivateParameters`, `PrivateParametersWithoutAsk`, `PrivateShieldedTRC20Parameters`, `SpendAuthSigParameters`, and processed by servlets such as `CreateShieldedContractParametersWithoutAskServlet`, `GetExpandedSpendingKeyServlet`, and `GetIncomingViewingKeyServlet`. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The design mirrors the OpenShift bug class exactly: a generic panic/error-recovery layer (`wrap.go` in the CVE; `RateLimiterServlet.service()` here) logs the full exception object for *any* endpoint, without any awareness of which endpoints carry secret material. In java-tron, exceptions thrown deep inside native zk-SNARK binding calls (`JLibrustzcash`) or key-derivation code (`ExpandedSpendingKey`, `SpendingKey`) that are *not* explicitly caught inside the specific servlet's own try/catch (which most, but not necessarily all, code paths do) will propagate to this top-level handler and be written verbatim — with full stack trace and exception message/cause chain — into the file-based application log at ERROR level. [5](#0-4) 

The log line uses SLF4J's variadic form with the `Throwable` as the final argument, which causes the full stack trace (including nested cause exceptions and their `getMessage()` content) to be printed. Because Java exceptions frequently embed the offending input value in their message (e.g. `NumberFormatException`, `ArrayIndexOutOfBoundsException` with index derived from an attacker-controlled byte array length, or custom exceptions thrown by JNI/native zk-SNARK code), a malformed or malicious shielded-transaction request carrying `ask`/`nsk`/`ovk`/spending-key bytes has a realistic path to have those secret values embedded in an exception's message and thus written to `./logs/tron.log`. [6](#0-5) 

Unlike gRPC's `createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig` handlers in `RpcApiService`, which explicitly catch `Exception` and only log `e.getMessage()` (still a smaller, but present, leak surface), the generic `RateLimiterServlet` catch-all is a single shared choke point for *all* HTTP endpoints and was clearly not designed with secret-bearing endpoints in mind — it logs the throwable object itself rather than a sanitized message. [7](#0-6) 

Note: `DesensitizedConverter` exists to scrub IP addresses from log output, showing the project is aware log content needs sanitization for some categories of sensitive data — but it only targets IPv4 addresses, not key material. [8](#0-7) 

### Impact Explanation
If `ask`/`nsk`/`ovk` or the spending key leak into the plaintext, rolling log files (`./logs/tron.log`, retained up to 7 days / 50GB), anyone with read access to those logs (log aggregation systems, support staff, a secondary vulnerability granting file read, or a misconfigured log-shipping pipeline) can reconstruct the full spend authority for a shielded (zk-SNARK) address and steal shielded funds — a direct, permanent, unauthorized theft of funds, matching the "concrete unauthorized account operation / theft of funds / key disclosure" bar required by the validation criteria.

### Likelihood Explanation
This requires: (1) locating a code path in the shielded-transaction processing chain (native `JLibrustzcash` bindings, `ExpandedSpendingKey`, `ZenTransactionBuilder`) that throws an exception embedding raw secret bytes in its message when given malformed/edge-case attacker-supplied input, and (2) that exception not being caught by the specific servlet's own try/catch (only escaping to the shared `RateLimiterServlet` handler). I was not able to conclusively prove within the indexed code that such an exception message-embedding-secret-bytes case exists in the native/derivation layer (this would require deeper inspection of `JLibrustzcash` native call error paths and JNI exception construction, which the index does not fully expose). This is a plausible but not fully proven concrete trigger, which is why likelihood is Medium rather than High — the architectural leak point (RateLimiterServlet's shared catch-all logging full throwables for secret-bearing endpoints) is proven; the specific exception-message-embeds-secret trigger is not.

### Recommendation
- In `RateLimiterServlet.service()`, do not log the raw `Throwable` object (or its full message/cause chain) for any endpoint; log only exception class name and a generic correlation ID, or explicitly redact known-sensitive field names before logging.
- Audit every servlet/actuator/native binding on the shielded-transaction path (`ask`, `nsk`, `ovk`, spending key, `alpha`) to ensure no exception constructor embeds raw key bytes in `getMessage()`.
- Extend `DesensitizedConverter` (or add a dedicated sanitizer) to redact hex-encoded 32/64-byte sequences appearing in log output for shielded-key-bearing log categories (e.g. topic `"shieldTransaction"`, `"API"`).
- Lower the log level or suppress logging entirely for exceptions originating from shielded/private-key-bearing endpoints, routing them instead to a metric/counter without payload content.

### Proof of Concept
Concrete reproduction was not established because the exact native/derivation code path that embeds raw `ask`/`nsk`/`ovk` bytes into an exception message could not be confirmed with the available index (native JNI call error construction in `JLibrustzcash` was not inspected). Conceptually: send a malformed `PrivateShieldedTRC20ParametersWithoutAsk` (or `PrivateParameters`) HTTP/gRPC request with a validly-sized but cryptographically-invalid `ask`/`nsk`/`ovk`/spending key to `/wallet/createshieldedcontractparameterswithoutask` or the shielded gRPC equivalents, crafted so that native key derivation fails deep in the call stack with an uncaught `RuntimeException`; if that exception's message includes the offending byte array (as many JNI wrapper failures do via `Arrays.toString`/`Hex.toHexString` style messages), it will propagate past the servlet and be written in full via `RateLimiterServlet`'s `logger.error(...)` call, or via `RpcApiService`'s `logger.info("... exception caught: " + e.getMessage())` calls for the gRPC path.     boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);

    String contextPath = req.getContextPath();
    String url = Strings.isNullOrEmpty(req.getServletPath())
        ? MetricLabels.UNDEFINED : contextPath + req.getServletPath();
