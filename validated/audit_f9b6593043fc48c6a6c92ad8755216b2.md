### Title
Reserved-balance shortfall during fast-unstake settlement permanently halts the pallet and locks all queued deposits - (File: `substrate/frame/fast-unstake/src/lib.rs`)

### Summary
The external report's core defect is: a user-controlled value is accepted and advances shared/global process state without full validation, and a later mandatory settlement step re-checks that value, fails, and the failure corrupts state for *everyone*, not just the requester. `pallet-fast-unstake` has the same shape: `register_fast_unstake` reserves a deposit and enqueues the stash into a single, pallet-wide `Head`/`Queue` state machine [1](#0-0) . The final settlement step, `unstake_stash`, unconditionally calls `Self::halt(...)` — which disables the *entire pallet for all users* — the moment a single account's reserved balance does not fully cover its deposit at unreserve time [2](#0-1) .

### Finding Description
`register_fast_unstake` reserves `T::Deposit::get()` on the caller's account using the generic (non-named) `Currency::reserve` [3](#0-2) . Because this is an un-named reserve, it is fungible with *any other* reserved balance the same account may accumulate for unrelated purposes (e.g. other reserve-based holds in the runtime that share the same `Currency` reserve counter). Nothing in `register_fast_unstake` pins or isolates this specific deposit.

Later, when the request reaches the head of the single global `Head` queue, `do_on_idle` unbonds the stash via `unstake_stash`:
```rust
let unstake_stash = |stash: T::AccountId, deposit| {
    let result = T::Staking::force_unstake(stash.clone());
    let remaining = T::Currency::unreserve(&stash, deposit);
    if !remaining.is_zero() {
        Self::halt("not enough balance to unreserve");
    }
    ...
};
``` [2](#0-1) 

If the account's *total* reserved balance has dropped below `deposit` by the time this runs (for example, because some other reserve-consuming mechanism reduced the shared reserve pool in the interim), `unreserve` returns a non-zero `remaining`, and `Self::halt` is invoked:
```rust
pub(crate) fn halt(reason: &'static str) {
    frame_support::defensive!(reason);
    ErasToCheckPerBlock::<T>::put(0);
    Self::deposit_event(Event::<T>::InternalError)
}
``` [4](#0-3) 

Setting `ErasToCheckPerBlock` to `0` does not just fail the one offending request — it is the pallet-wide kill switch. Both public entry points gate on this value:
- `register_fast_unstake`: `ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed);` [5](#0-4) 
- `deregister`: `ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed);` [6](#0-5) 
- `do_on_idle` also early-exits entirely when `ErasToCheckPerBlock` is `0` [7](#0-6) 

This is exactly the reported bug class: a value accepted at "deposit" time (`register_fast_unstake` reserving a deposit into a shared, un-isolated reserve pool) is not validated against everything that could shrink it before the mandatory "processDeposit"-equivalent step (`unstake_stash`'s `unreserve`) runs. The existing guard (`if !remaining.is_zero() { halt }`) does not just fail the individual request — it stops progress for the whole system, exactly mirroring how the SteadeFi bug's per-user `minSharesAmt` check corrupted shared contract state (`Status`) for all users.

### Impact Explanation
Once `halt` fires:
- Every account still sitting in `Queue` or in `Head` has its deposit permanently reserved and can never call `deregister` to reclaim it, because `deregister` is gated by the same `ErasToCheckPerBlock != 0` check — this is a **permanent user-fund lock**.
- No new account can call `register_fast_unstake`, disabling the feature chain-wide for an indefinite period until a privileged `control` origin manually re-enables it via `Pallet::control` [8](#0-7) .
- This is triggerable through fully public, unprivileged extrinsics (`register_fast_unstake`), matching the "public underpriced work that... stalls processing" and "permanent user-fund lock" impact classes, without needing a malicious validator, collator, or governance actor.

### Likelihood Explanation
The exact external condition needed to shrink an account's *total reserved balance* below its fast-unstake deposit depends on what else reserves funds against the same account using the generic `Currency::reserve`/`unreserve` interface in a given runtime configuration (this pallet's `Currency` type is runtime-configurable and not necessarily `NamedReservableCurrency`). Confirming a concrete runtime where another pallet reduces the same reserve pool concurrently (e.g. via `slash_reserved`, or another reserve-consuming call reducing the shared pool while a fast-unstake deposit is outstanding) would require inspecting the specific runtime's pallet configuration, which is outside what the index surfaced. The vulnerable code path and the pallet-wide `halt` blast radius are unambiguous and directly verifiable in this repository, but the exact trigger for a non-zero `remaining` is runtime/configuration dependent, so likelihood should be treated as configuration-dependent rather than universally guaranteed.

### Recommendation
- Use a *named* reserve (`ReservableCurrency`'s named/hold variant, e.g. `fungible::MutateHold` with a dedicated `HoldReason`) for the fast-unstake deposit so it cannot be depleted by unrelated reserve operations on the same account.
- Do not use a single pallet-wide `halt` in response to a per-account settlement anomaly; instead, fail only the affected request (e.g. emit `Event::InternalError` scoped to that stash, force-unstake anyway, and continue processing the rest of the batch/queue) rather than zeroing `ErasToCheckPerBlock` for all users.
- If a global halt is genuinely required as a safety valve, provide a permissionless/automatic recovery path (or at minimum allow `deregister` to succeed even while halted) so user funds are never irrecoverably locked pending governance action.

### Proof of Concept
Conceptual PoC (requires a runtime where `pallet_fast_unstake::Config::Currency` is a `Currency` implementation whose reserve counter is shared with another reserve-consuming mechanism reachable by the same account):
1. Attacker account `A` calls `register_fast_unstake`, reserving `Deposit` via the shared `Currency::reserve` [3](#0-2) .
2. Before `A`'s request reaches settlement in `do_on_idle`, `A` (or an external process acting on `A`'s account) triggers any other operation in the runtime that consumes/slashes part of `A`'s *total* reserved balance below the outstanding fast-unstake `Deposit` (e.g. a slash on reserved funds used by another feature sharing the same `Currency`).
3. When `do_on_idle` processes `A`'s batch and calls `unstake_stash`, `T::Currency::unreserve(&A, deposit)` returns `remaining > 0` [2](#0-1) .
4. `Self::halt("not enough balance to unreserve")` sets `ErasToCheckPerBlock` to `0` pallet-wide [4](#0-3) .
5. All other users currently in `Queue`/`Head` can no longer `deregister` (blocked by the same flag) [6](#0-5) , and no new `register_fast_unstake` calls succeed [5](#0-4)  until a privileged `control` call restores `ErasToCheckPerBlock`.

			let ctrl = ensure_signed(origin)?;
