### Title
StackerDB chunk signatures are not bound to the target contract/StackerDB, allowing cross-contract signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` — the digest that is actually signed and verified for every StackerDB chunk write — is computed only from `slot_id`, `slot_version`, and `data_hash`. It does not include the `smart_contract_id` (the StackerDB instance/contract) that the chunk is destined for. Any valid `(slot_id, slot_version, sig, data)` tuple observed on one StackerDB contract can therefore be replayed verbatim against a *different* StackerDB contract that happens to assign the same `slot_id` to the same signing key, bypassing the intended per-contract authorization scoping — the same "signature reused across an unintended context" bug class as the external report (there the signature was reusable across `stakeTokens`/`upgradeStakeTokens`; here it is reusable across different StackerDB contract instances).

### Finding Description
The digest that binds a chunk write to a slot owner is: [1](#0-0) 

This digest is used both when signing (`SlotMetadata::sign`) and when verifying (`SlotMetadata::verify`) a chunk: [2](#0-1) 

Note that `verify` only checks that the recovered public key hash matches the given `principal` — it never checks which `smart_contract_id` the caller is validating against, because that information was never part of the signed payload in the first place.

The verification is invoked per-contract by resolving the expected signer address from the target contract's slot table, but the signed message itself carries no contract binding: [3](#0-2) 

The same pattern is used on the write path exposed via the unauthenticated HTTP RPC endpoint `POST /v2/stackerdb/:principal/:contract/chunks`, which decodes a `StackerDBChunkData` (containing only `slot_id`, `slot_version`, `sig`, `data` — no contract identifier) and passes it straight to `try_replace_chunk` for whatever contract is named in the URL path: [4](#0-3) [5](#0-4) 

Because the `sig` field only commits to `(slot_id, slot_version, data_hash)`, and slot ownership (which `StacksAddress` owns `slot_id` N) is configured independently per contract via the on-chain contract's signer set, any signer address that is granted the same `slot_id` in two or more StackerDB contracts (which is a normal, expected occurrence — e.g. the signer set for consecutive reward cycles, or the miner-info/signer-message DBs, frequently reuse identical slot layouts and signer keys) will have their signature accepted by every such contract for identical `(slot_id, slot_version, data)` triples, regardless of which contract the signature was originally produced for.

### Impact Explanation
An attacker who observes a legitimately-signed chunk broadcast on the P2P StackerDB gossip layer or served via the `GET /v2/stackerdb/.../chunks/...` read endpoint can resubmit the exact same `(slot_id, slot_version, sig, data)` to a *different* StackerDB contract URL where the corresponding signer address also owns that `slot_id`. If that contract's replica accepts it (`try_replace_chunk` succeeds because `SlotMetadata::verify` only checks the signature against the digest, not the contract), the node will store attacker-replayed data as if it were freshly authored for that contract, and will further relay it via `StackerDBPushChunk` gossip to the rest of the network: [6](#0-5) 

This is an unauthenticated write of forged/mis-contextualized data into a StackerDB instance and its network-wide propagation, matching "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" impact categories.

### Likelihood Explanation
Exploitability depends on whether any signer key is configured to own the same `slot_id` across two or more concurrently-live StackerDB contracts on the same node — this is a realistic and common deployment pattern in the Stacks signer/miner ecosystem (identical signer sets reused across successive reward-cycle contracts, and identical slot layouts across different message-type StackerDB contracts for the same signer set). No special privileges are needed by the attacker beyond capturing a publicly-broadcast chunk and re-POSTing it to a different contract path, both of which are unauthenticated, remote operations.

### Recommendation
Include the `smart_contract_id` (StackerDB contract identifier) as part of the signed digest in `SlotMetadata::auth_digest`, so that a signature is only valid for the specific StackerDB instance it was produced for. This mirrors the report's own recommendation of scoping/expiring authorization data to the specific action it was intended for.

### Proof of Concept
1. Configure two StackerDB contracts, `contract-A` and `contract-B`, both assigning `slot_id = 0` to the same `StacksAddress` (derived from `privkey`).
2. A legitimate client signs and pushes a chunk to `contract-A`: `StackerDBChunkData { slot_id: 0, slot_version: 1, sig, data }` where `sig = privkey.sign(auth_digest(0, 1, hash(data)))`.
3. An attacker observes this chunk (via P2P StackerDB gossip or the public `GET` chunk endpoint).
4. The attacker submits an identical `StackerDBChunkData` payload (same `slot_id`, `slot_version`, `sig`, `data`) to `POST /v2/stackerdb/<addr>/contract-B/chunks`.
5. `try_replace_chunk` for `contract-B` calls `SlotMetadata::verify`, which recomputes `auth_digest(0, 1, hash(data))` — identical to the one signed for `contract-A` — and successfully recovers the same owning address, so the write is accepted for `contract-B` even though the signature was never produced with `contract-B` in mind, and the node relays it network-wide via `StackerDBPushChunk`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
