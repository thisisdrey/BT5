### Title
Unauthenticated UDP-replay reflection of cached stage-2 handshake response via `ErrAlreadySeen` path - ([File: handshake_manager.go])

### Summary
`handleCheckAndCompleteError`'s `ErrAlreadySeen` branch unconditionally resends `existing.HandshakePacket[handshakePacketStage2]` to `via` regardless of whether `existing.SetRemoteIfPreferred` succeeded, and `via.UdpAddr` is derived directly from the incoming UDP packet's (spoofable) source address. An attacker who has captured a legitimate stage-0 (`msg1`) packet byte-for-byte can replay it from any spoofed UDP source and get the responder to send a full stage-2 handshake response toward that spoofed address, and, if the spoofed address happens to satisfy `SetRemoteIfPreferred`'s criteria, also trigger a `Test`/`TestRequest` send and touch the live hostinfo's remote-tracking state.

### Finding Description
`HandleIncoming` routes any `MessageCounter == 1` packet with `RemoteIndex == 0` to `beginHandshake` [1](#0-0) , which builds a brand-new responder `handshake.Machine`, runs `ProcessPacket` on the replayed bytes, validates the peer cert cryptographically (this succeeds because the bytes are a byte-identical, previously-valid message, not a forged one), and then calls `CheckAndComplete` keyed on `handshakePacketStage0` [2](#0-1) . `CheckAndComplete` compares the new stage-0 bytes against every cached stage-0 packet for that vpnAddr already in the main hostmap, and if they match byte-for-byte returns `ErrAlreadySeen` with the *existing*, already-tunnel-established `HostInfo` [3](#0-2) .

`handleCheckAndCompleteError`'s `ErrAlreadySeen` case then does two things:
1. Calls `existing.SetRemoteIfPreferred(f.hostMap, via)` and only conditionally sends a `Test`/`TestRequest` if that returns true.
2. Unconditionally resends the cached stage-2 packet to `via` via `hm.sendHandshakeResponse(via, msg, existing, true)`, independent of the `SetRemoteIfPreferred` outcome [4](#0-3) .

`sendHandshakeResponse` writes the message directly to `via.UdpAddr` with no additional authentication of the address [5](#0-4) . `via.UdpAddr` is populated straight from the inbound UDP packet's source address at the listener layer, which is attacker-controllable since UDP allows arbitrary source-address spoofing. No return-routability check (e.g., a fresh nonce/cookie the sender must echo back) gates this send — only byte-equality of the previously-observed stage-0 packet is checked, which an eavesdropper can capture once and replay indefinitely from any spoofed source.

### Impact Explanation
This is a reflection/amplification primitive: an attacker who has captured one legitimate stage-0 packet can cause the responder to emit a full stage-2 handshake packet toward an arbitrary, attacker-chosen (spoofed) UDP address, at will and repeatedly, without needing any certificate of their own. Additionally, `existing.SetRemoteIfPreferred` is invoked with the attacker-controlled `via`, meaning the already-established peer's remote-address bookkeeping code is exercised using a spoofed source — the extent to which this can flip `CurrentRemote` to the attacker's address depends on `SetRemoteIfPreferred`'s internal preferred-range gating (not fully confirmed here), but the reflection send itself is unconditional and confirmed in code.

### Likelihood Explanation
Requires the attacker to have previously captured (passively observed) one legitimate stage-0 packet exchanged between two real Nebula peers — a realistic precondition for a network eavesdropper (e.g., shared/compromised network segment, ISP-level observation) — plus the ability to spoof UDP source addresses, which is a well-known limitation of UDP-based protocols lacking return-routability checks. No CA-signed certificate, private key, or host access is needed by the attacker, satisfying the stated constraints. The replay is trivially repeatable since the byte-equality check in `CheckAndComplete` has no time or single-use limitation.

### Recommendation
Do not use `via` (attacker-controlled/spoofed source) unconditionally as the destination for the resend in the `ErrAlreadySeen` path. Require the address used for replies (and any `SetRemoteIfPreferred` call) to be validated by data-plane traffic that has passed AEAD decryption (i.e., only update remotes / respond to a byte-identical stage-0 replay if it also arrives on the previously recorded, packet-verified remote, or gate the stage-2 resend the same way `SetRemoteIfPreferred` gates the `Test` send) so that address changes and reflected sends require cryptographically fresh proof-of-possession rather than mere byte-identical replay.

### Proof of Concept
Integration test extending `e2e/handshake_manager_test.go` (pattern used by `TestHandshakeRetransmitDuplicate`/`TestHandshakeAlreadySeenPreferredRemote`):
1. Complete a normal handshake between `myControl` and `theirControl`, establishing a tunnel and capturing `myControl`'s original stage-0 (`msg1`) bytes.
2. Construct a `udp.Packet` with `Data` identical to the captured `msg1` but `From` set to a third, unrelated spoofed `netip.AddrPort` (not `myUdpAddr`).
3. Inject this forged packet into `theirControl`.
4. Assert that `theirControl.GetFromUDP(true)` yields a stage-2 handshake response addressed `To` the spoofed address (confirming reflection to an address the attacker chose, not the legitimate peer).
5. Additionally assert on `theirControl.GetHostInfoByVpnAddr(...).CurrentRemote` to determine whether/under what conditions `SetRemoteIfPreferred` altered the established tunnel's remote based solely on this spoofed replay, and that no fresh cryptographic proof was required for either action.
