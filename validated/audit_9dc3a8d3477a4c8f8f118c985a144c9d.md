### Title
Missing Bounds Validation in Precompiled Contract Array Parsers Causes DoS via Crafted Transaction Input - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `PrecompiledContracts.extractBytes32Array` and `extractBytesArray` helper methods decode dynamic array structures out of the raw `DataWord[]` input supplied to precompiled contracts (e.g. the multi-signature/batch-validate precompiles reachable via the TVM `CALL` opcode). Both methods read an attacker-controlled length field from the input and use it directly to size and index into arrays without validating that the declared length is consistent with the actual size of the input, mirroring the coreMQTT flaw where a property length field was used without bounds validation before being consumed, leading to a crash.

### Finding Description
`extractBytes32Array` reads a length word from caller-controlled `words[offset]` and immediately allocates an array of that size and then loops reading `words[offset + i + 1]` for `i` in `[0, len)` with no check that `offset + i + 1 < words.length`: [1](#0-0) 

`extractBytesArray` performs a partial check (`offset > words.length - 1`) but the inner loop still indexes `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` using values derived entirely from attacker-supplied `intValueSafe()` results, with no verification that these indices remain within `words.length` before the array is sized and iterated: [2](#0-1) 

Because `len` comes straight from `DataWord.intValueSafe()` on a caller-supplied word, a malicious contract caller can set it to an arbitrarily large positive value. This causes either:
1. An `OutOfMemoryError`/excessive allocation from `new byte[len][]` before any bound is checked against the real input size, or
2. An `ArrayIndexOutOfBoundsException` when the loop reads `words[offset + i + 1]` past the end of the actual `words` array.

This is directly analogous to the coreMQTT flaw: a length/count field taken from untrusted input is used to drive parsing/allocation before being validated against the bounds of the buffer that supplied it, and an uncaught error during execution of a transaction can be triggered by any transaction broadcaster.

### Impact Explanation
An unprivileged user who can invoke a smart contract that calls a precompiled contract's `execute` path exercising these helpers can trigger an uncaught runtime exception (`ArrayIndexOutOfBoundsException`) or excessive memory allocation (`OutOfMemoryError`) during transaction execution in every full node that processes the transaction. Depending on how exceptions from precompiled-contract execution propagate through the TVM `Program`/actuator dispatch path, this can manifest as a node crash or halt when processing an otherwise valid, low-cost transaction — a denial-of-service impacting the whole network's ability to process transactions, consistent with the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Likelihood is high for any node that executes such a transaction: the trigger only requires crafting `CALL` data to the relevant precompiled contract address with an oversized length word in the array-encoding region, something any contract deployer/caller can construct without special privileges, matching the "unprivileged transaction broadcaster/contract deployer" reachability requirement.

### Recommendation
Add explicit bounds validation in both `extractBytes32Array` and `extractBytesArray` before allocation and before each array read: verify `len >= 0` and that `offset + len` (and, for `extractBytesArray`, all derived `bytesOffset`/`bytesLen` values) stay within `words.length`/`data.length`, returning an empty array or throwing a handled `ContractValidateException`/`Program.Exception` instead of letting an unchecked `ArrayIndexOutOfBoundsException` or `OutOfMemoryError` escape.

### Proof of Concept
1. Craft a transaction that calls (via `CALL`/`STATICCALL`) the precompiled contract address whose `execute` method invokes `extractBytes32Array`/`extractBytesArray` (e.g. the batch/multi-signature validation precompile).
2. Encode the input so the length word at the expected `offset` decodes (via `DataWord.intValueSafe()`) to a very large positive integer (e.g. `Integer.MAX_VALUE`), while the actual `words`/`data` array supplied is short.
3. Broadcast the transaction; on execution, `new byte[len][]` at [3](#0-2)  attempts a huge allocation, or the subsequent loop reads past `words.length`, raising an unchecked exception that is not accounted for by the intended validation logic of the precompile.
