### Title
`NativeWithdraw` permanently burns a user's internal wNEAR balance with no refund when the NEAR transfer to `receiver_id` fails - (File: contracts/defuse/src/contract/tokens/nep141/native.rs)

### Summary
Unlike every other withdrawal path in `contracts/defuse` (`FtWithdraw`, `NftWithdraw`, `MtWithdraw`), the `NativeWithdraw` intent debits the signer's internal wNEAR balance and fires an unwrap-and-transfer `Promise` chain with **no resolver/callback that checks the outcome of the final transfer and refunds on failure**. If the final `Promise::new(receiver_id).transfer(amount)` fails (e.g. `receiver_id` does not exist, which is explicitly called out in the intent's own doc comment), the unwrapped NEAR stays stranded in the contract's own account balance, unreachable by any user-facing intent, while the signer's internal wNEAR balance has already been irreversibly subtracted.

### Finding Description
`NativeWithdraw::execute_intent` calls `engine.state.native_withdraw(...)`, which for the on-chain `Contract` implementation:
1. Calls `self.withdraw(...)` to subtract `withdraw.amount` of wNEAR from the owner's internal ledger balance [4](#0-3) .
2. Calls `wnear::near_withdraw()` to unwrap wNEAR into raw NEAR held by the contract's own account, then chains `do_native_withdraw(withdraw)` [5](#0-4) .
3. `do_native_withdraw` only checks that `near_withdraw` succeeded, then does a fire-and-forget `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` with **no `.then(...)` resolver** [6](#0-5) .

If the transfer action fails (the intent's own doc explicitly cites "receiver_id account does not exist" as an example [7](#0-6) ), there is no code path to detect the failure and re-credit the user. The already-unwrapped NEAR remains in the contract's account, disconnected from any user's ledger entry.

This breaks the custody binding "value debited versus value delivered plus refunded": the internal wNEAR balance is debited unconditionally in step 1, but delivery in step 3 is never verified nor refunded on failure.

Contrast this with the `FtWithdraw`, `NftWithdraw`, and `MtWithdraw` paths, which all have dedicated `*_resolve_withdraw` callbacks that inspect the promise result and `self.deposit(...)` a refund back to the sender when the outer transfer fails [8](#0-7) [9](#0-8) [10](#0-9) . `NativeWithdraw` is the only withdrawal intent lacking this safety net.

### Impact Explanation
Any user (or relayer acting for a user) who submits a `NativeWithdraw` intent targeting a `receiver_id` that does not exist on-chain (a typo, a not-yet-created implicit account, a since-deleted account, etc.) permanently loses the withdrawn amount: their internal wNEAR balance is debited, but the unwrapped NEAR is stranded in the Defuse contract's own account balance with no ledger entry crediting anyone. This is a Critical impact per the funds-permanently-frozen criterion — value is debited from the user's custody-tracked balance without being delivered or refunded, and the contract has no mechanism to recover or reattribute it.

### Likelihood Explanation
This requires no attacker privilege beyond being a normal signer of a `NativeWithdraw` intent (or being tricked/mistaken into targeting a bad `receiver_id`); it can also be triggered adversarially by a griefer having a victim sign a withdraw to a non-existent `receiver_id` obtained via social engineering of the *destination*, or simply through routine operational error, since the failure mode is explicitly acknowledged in the intent's own documentation as an expected occurrence rather than an edge case guarded against.

### Recommendation
Add a `native_resolve_withdraw` callback analogous to `ft_resolve_withdraw` / `nft_resolve_withdraw` / `mt_resolve_withdraw`: chain it after the `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw`, inspect the promise result, and re-credit (`self.deposit(...)`) the sender's wNEAR balance for the full amount when the transfer fails.

### Proof of Concept
1. User has `N` wNEAR credited internally in Defuse.
2. User signs and submits a `NativeWithdraw { receiver_id: "does-not-exist.near", amount: N }` intent.
3. `native_withdraw` subtracts `N` wNEAR from the user's balance, unwraps `N` NEAR from wNEAR into the contract's own balance, then schedules `do_native_withdraw`.
4. `do_native_withdraw` issues `Promise::new("does-not-exist.near").transfer(N)`, which fails on-chain because the account does not exist.
5. No resolver exists to catch this failure; the user's internal ledger balance remains `0` for that amount, and the `N` NEAR is now sitting in the Defuse contract's own account balance with no on-chain reference tying it back to the user — permanently unrecoverable through any exposed intent.

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }

#[near]
impl MultiTokenWithdrawResolver for Contract {
    #[private]
    fn mt_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        is_call: bool,
    ) -> Vec<U128> {
        require!(
            token_ids.len() == amounts.len() && !amounts.is_empty(),
            "invalid args"
        );

        let mut used = if is_call {
            // `mt_batch_transfer_call` returns successfully transferred amounts
            match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
                Ok(Ok(used)) if used.len() == amounts.len() => used,
                Ok(_) => vec![U128(0); amounts.len()],
                // do not refund on failed `mt_batch_transfer_call` due to
                // NEP-141 vulnerability: `mt_resolve_transfer` fails to
                // read result of `mt_on_transfer` due to insufficient gas
                Err(_) => amounts.clone(),
            }
        } else {
            // `mt_batch_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amounts.clone()
            } else {
                vec![U128(0); amounts.len()]
            }
        };

        self.deposit(
            sender_id,
            token_ids
                .into_iter()
                .zip(amounts)
                .zip(&mut used)
                .filter_map(|((token_id, amount), used)| {
                    // update min during iteration
                    used.0 = used.0.min(amount.0);
                    let refund = amount.0.saturating_sub(used.0);
                    if refund > 0 {
                        Some((Nep245TokenId::new(token.clone(), token_id).into(), refund))
                    } else {
                        None
                    }
                }),
            Some(REFUND_MEMO),
        )
        .unwrap_or_else(|err| err.panic());

        used
    }
