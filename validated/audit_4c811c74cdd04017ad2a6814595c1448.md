## Title
Heap buffer over-read via unchecked Zip64 extra-field attribute index in `LH::compressed_file_size()`/`uncompressed_file_size()` - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` (the Bazel tool that merges JAR/ZIP entries when assembling deploy jars from dependency archives) parses the Local File Header (`LH`) of each ZIP entry and, when a 32-bit size field is `0xFFFFFFFF`, resolves the real 64-bit size from the accompanying `Zip64ExtraField`. The lookup index into that field's flexible-array member is hard-coded rather than derived from the field's actual declared attribute count, so a maliciously crafted (attacker-supplied) JAR/ZIP dependency can make singlejar read past the bounds of the parsed extra-field payload — a heap/mmap buffer over-read directly analogous to the `Map1toN` over-read in `SDL_pixels.c` (ALPINE-CVE-2019-7638), where a size/index derived from untrusted input is used to index into a buffer without validating it against the buffer's actual declared length.

### Finding Description
`ExtraField::find` only validates that the extra field's own declared boundaries (`tag_` + `payload_size_` + payload) fit inside the caller-supplied `[start, end)` window of the local header's `extra_fields` region: [1](#0-0) 

`Zip64ExtraField` exposes `attr64(index)` and `attr_count()` (derived from `payload_size()/sizeof(uint64_t)`), but nothing enforces that a caller only reads indices `< attr_count()`: [2](#0-1) 

`LH::compressed_file_size()` and `LH::uncompressed_file_size()` unconditionally call `attr64(1)` and `attr64(0)` respectively whenever the corresponding 32-bit field is `0xFFFFFFFF`, with no check that the located `Zip64ExtraField` actually contains that many 64-bit attributes: [3](#0-2) 

By contrast, the Central Directory Header (`CDH`) version of the same accessor derives the index dynamically based on whether the *other* size field also needs a 64-bit extension, correctly handling the variable-presence semantics of the Zip64 extra field: [4](#0-3) 

The Local Header's version has no equivalent logic — it assumes both attributes are always present at fixed indices 0 and 1, contradicting the fact that `attr_count()` (and thus the number of actually-present 64-bit values) is attacker-controlled via `payload_size_`.

These accessors are reached from real ZIP-entry-content extraction paths used when singlejar reads sizes directly out of the local header (the non-streaming case): [5](#0-4) 

which is invoked when merging jar entries from dependency archives, e.g. `Concatenator::Merge` and `Java8DesugarDepsChecker::Merge`: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who controls the contents of a dependency archive (e.g. a `.jar` fetched via `http_archive`, a Maven artifact, or any file in an untrusted-branch CI build that singlejar processes) can craft a Local Header whose 32-bit `compressed_file_size32_` (or `uncompressed_file_size32_`) is `0xFFFFFFFF`, while attaching a `Zip64ExtraField` whose `payload_size_` only covers one 8-byte attribute (or zero). `attr64(1)` (or `attr64(0)` on an empty field) then reads 8 bytes past the extra field's validated payload boundary. Because the extra-field bytes are backed by a `mmap`'d input file buffer (see `InputJar`/`MappedFile` in `src/tools/singlejar/input_jar.cc`), this over-read can consume adjacent heap/mapped-file memory or, if the field sits at the very edge of the mapped region, cross into unmapped memory and crash the build, or leak adjacent memory content into the resulting size computation used for subsequent buffer copies.

### Likelihood Explanation
Exploitability requires only the ability to publish/serve a JAR/ZIP file that a victim's Bazel build fetches and processes with singlejar (e.g. as a `java_import`, `deps` artifact, or merged via `singlejar` combiners) — squarely within the unprivileged "hostile origin server / untrusted branch content" threat model. No checksum bypass is needed because the vulnerability is not about tampering with a byte that is checksum-verified — it's a structural parsing bug inside the (correctly-downloaded, correctly-checksummed) file's ZIP metadata itself.

### Recommendation
In `LH::compressed_file_size()` and `LH::uncompressed_file_size()`, validate `z64->attr_count()` against the required index before calling `attr64()`, mirroring the dynamic-index logic already used in `CDH`'s accessors, and treat a Zip64 extra field with insufficient attributes as a parse error rather than performing the read.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction would:
1. Construct a minimal ZIP with one local file header where `compressed_file_size32_ = 0xFFFFFFFF` and `uncompressed_file_size32_` is a normal, small value.
2. Attach a Zip64 extra field (tag `0x0001`) with `payload_size_ = 8` (one 64-bit attribute only, representing `uncompressed_file_size` per the spec's variable-presence rule, i.e. `attr_count() == 1`).
3. Place this local header/extra field at the very end of the mapped input buffer (e.g., truncate the "file data" section to trigger a read into unmapped memory), or run under ASan/Valgrind to detect the heap-buffer-overflow read when `LH::compressed_file_size()` calls `z64->attr64(1)`.
4. Feed this crafted archive to `singlejar` (or a test harness invoking `Concatenator::Merge`/`TransientBytes::ReadEntryContents`) and observe the ASan report of a read past the allocated/mapped buffer, or an incorrect size value derived from adjacent memory.

  static const ExtraField* find(uint16_t tag, const uint8_t* start,

    while (start < end) {

        break;
      }

        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
