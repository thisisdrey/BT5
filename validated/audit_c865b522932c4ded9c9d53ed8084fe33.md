### Title
Positions spanning more than 3 stale-price assets become permanently un-liquidatable due to the fixed 3-feed cap in `write-feeds` - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`price-resolve` unconditionally reverts with `ERR-ORACLE-INVARIANT` whenever any asset's oracle timestamp is older than its `max-staleness`, and `price-multi-resolve` (called by `get-assets`/`get-notional-evaluation` for every asset in a position's mask) propagates that failure as `ERR-ORACLE-MULTI`, aborting the whole transaction. The only in-transaction remedy, `write-feeds`, accepts at most 3 Pyth feed buffers. A position/mask can legitimately hold far more than 3 distinct collateral/debt assets (the registry/mask design supports up to 64 collateral + 64 debt slots), so if more than 3 of the assets held by one account become simultaneously stale, no single call — including `liquidate` — can supply enough feed updates to make the health/notional evaluation succeed. This mirrors the reported bug class: a requirement (all-asset price freshness) that scales with an attacker-controllable, effectively unbounded quantity (assets held in one position) is checked against a capacity that is fixed and much smaller (3 feeds per call), so the check becomes permanently unsatisfiable once the quantity exceeds the cap.

### Finding Description
`collateral-add`, `collateral-remove`, `borrow`, and `liquidate` all evaluate a user's *entire* current mask of held collateral/debt assets to compute notional collateral/debt value for health checks (`get-assets` → `get-notional-evaluation`), using `price-multi-resolve` over every asset in the mask: [4](#0-3) 

Each individual asset price is validated by `price-resolve`, which hard-fails if the last update timestamp is older than the asset's configured `max-staleness`: [5](#0-4) 

The only path to refresh a stale price within the same call is `write-feeds`, which is capped to 3 buffers regardless of how many assets require refreshing: [6](#0-5) 

This cap of 3 is baked into every public entry point's signature, including `liquidate`: [3](#0-2) 

Since a position's mask can legitimately span an asset count far greater than 3 (the underlying map/list structures throughout the codebase are explicitly sized for up to 64 collateral and 64 debt assets, e.g. `ITER-UINT-64`/`(list 64 ...)` used for `mask-to-list-collateral`, `accrue-user-collateral`, `accrue-user-debts`, `price-multi-resolve`), any account (an ordinary, unprivileged principal) can hold collateral/debt across more assets than the 3-feed refresh cap supports. Once more than 3 of those assets' prices lapse past `max-staleness` at the same time, `get-notional-evaluation` can never be computed successfully for that account in a single call, because no combination of ≤3 feed refreshes is enough to bring every held asset's price back within `max-staleness`. This blocks not only the position owner's own operations but also third-party `liquidate` calls against that account, since `liquidate` performs the same full-mask notional evaluation (`total-collateral-usd`/`other-coll-usd` derived from `pos-full`/`get-full-position`, covering all collateral the account holds, not just the pair being liquidated).

### Impact Explanation
If a borrower's position becomes economically unhealthy while spanning more than 3 assets with simultaneously stale prices, no liquidator can execute `liquidate` against that account — the transaction will always revert with `ERR-ORACLE-INVARIANT`/`ERR-ORACLE-MULTI` before the liquidation logic runs, because the mandatory full-mask notional evaluation cannot succeed. This can result in bad debt accumulating without any way to seize collateral, i.e., protocol insolvency risk, or at minimum a temporary freezing of funds for the account itself (which cannot add/remove collateral or borrow/repay either, once its position spans more stale assets than the 3-feed cap can refresh in one call).

### Likelihood Explanation
No privileged action or DAO compromise is required — an ordinary account can open collateral/debt positions across many enabled assets simply by using the market normally (egroups can and do support multi-asset masks by design). Staleness accrues naturally per-asset based on each oracle's own `max-staleness` and publish cadence; assets with thinner markets/keeper coverage are more likely to lapse. An attacker (or even an unlucky ordinary user) can deliberately or incidentally accumulate more than 3 stale-eligible assets in one position, after which the position is stuck until enough of those feeds happen to be refreshed by unrelated third-party transactions — something an attacker can prevent by choosing thinly-updated assets.

### Recommendation
- **Short term:** Decouple price freshness validation from full-mask evaluation, or allow `write-feeds`/its callers to accept and refresh more than 3 buffers (e.g., size the list to the maximum supported assets, or loop/paginate feed refresh across multiple calls before evaluation), so that a health check is never permanently blocked by more stale assets than can be refreshed in one call. Alternatively, exclude assets irrelevant to the specific liquidation pair from the mandatory freshness check in `liquidate`.
- **Long term:** Perform threat modeling on any check whose requirement scales with a user-controlled quantity (number of assets in a position) against a fixed per-call capacity (feed refresh limit), and ensure liquidation/health paths remain reachable regardless of how many assets a position holds or how stale unrelated assets' oracles become.

### Proof of Concept
1. Attacker deploys/uses an account and, via `collateral-add`/`borrow`, builds a position holding collateral or debt across more than 3 distinct assets that are enabled by an egroup mask (e.g., 4+ assets), each with independent oracle staleness windows.
2. Time passes such that more than 3 of those assets' last-known prices exceed their configured `max-staleness` simultaneously (natural if keepers for some assets update infrequently, or accelerated by the attacker simply not refreshing them and choosing thinly-traded assets).
3. The attacker's position becomes underwater (e.g., due to price movement on one asset).
4. A liquidator calls `liquidate`, supplying up to 3 fresh Pyth feed buffers via `price-feeds` — the maximum allowed by `write-feeds`.
5. `get-notional-evaluation`/`price-multi-resolve` still needs prices for the remaining stale assets (>3) in the account's full mask; `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for those, causing `price-multi-resolve` to fail with `ERR-ORACLE-MULTI`, and the entire `liquidate` call reverts.
6. No sequence of calls with ≤3 feed refreshes each can resolve all stale assets within the same atomic evaluation, so the position remains permanently un-liquidatable while unhealthy, until/unless unrelated transactions happen to refresh those specific feeds.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
