### Title
Fee-on-transfer / non-standard NEP-141 tokens allow over-crediting of internal MT balances in `ft_on_transfer` - ([File: contracts/defuse/src/contract/tokens/nep141/deposit.rs])

### Summary
`Contract::ft_on_transfer` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs` credits the caller-supplied `amount` parameter directly to the depositor's internal multi-token (MT) ledger via `Contract::deposit`, without verifying that the Defuse contract's actual NEP-141 balance increased by that same amount. This mirrors the referenced Gearbox `PoolService.sol` bug class: minting is driven by the nominal transfer amount rather than the balance actually received.

### Finding Description
When a NEP-141 token is deposited, the token contract calls `ft_transfer_call` -> `ft_on_transfer(sender_id, amount, msg)` on Defuse. Defuse trusts `amount` as-is: [1](#0-0) 

and `Contract::deposit` unconditionally increments both `total_supplies` and the receiver's `token_balances` by `amount` for every token in the iterator, with no cross-check against the contract's real, actual on-chain FT balance for that token: [2](#0-1) 

For any NEP-141 whose `ft_transfer`/`ft_transfer_call` implementation is fee-on-transfer, deflationary/rebasing, or otherwise delivers less than the nominal `amount` to the recipient's balance (e.g., a "transfer tax" token, analogous to fee-charging USDT-style tokens referenced in the report), Defuse's ledger will record having received `amount`, while the contract's actual token holdings only increase by `amount - fee`. This breaks the binding: `sum(internal token_balances credited)` == `actual tokens custodied by the contract` for that `TokenId`.

By contrast, the withdrawal path in the same module is careful to reconcile against the actual promise outcome — `ft_resolve_withdraw` only treats `amount` as "used" if the transfer promise succeeds, and refunds the unused portion: [3](#0-2) 

No equivalent reconciliation (e.g., comparing `ft_balance_of` before/after, or capping `amount` by any independently observed delta) exists on the deposit side.

### Impact Explanation
Every unit of shortfall from a fee-on-transfer token creates phantom MT balance: the depositor (and anyone they transfer/trade the credited MT balance to inside Defuse) holds a claim on tokens the contract never actually received. Because `TokenId` for NEP-141 tokens is minted 1:1 assuming faithful custody, this results in an under-collateralized pool for that `TokenId` — the sum of internally tracked balances exceeds the tokens actually escrowed. Eventual withdrawals will fail for the last claimants once the real balance is exhausted, i.e., funds become effectively frozen/lost for some holders of that `TokenId`, and an attacker can deposit such a token to mint excess internal balance and immediately swap/transfer/withdraw it against other users' genuinely deposited tokens before the shortfall is discovered — a direct token-moved-without-equivalent-value-delivered scenario.

### Likelihood Explanation
Exploitability depends entirely on Defuse listing/accepting a non-standard NEP-141 token (fee-on-transfer, deflationary, or otherwise not delivering the full nominal `amount`). Any unprivileged user (or the token issuer) can trigger this simply by calling `ft_transfer_call` from such a token contract into Defuse with a normal deposit — no privileged role, relayer key, or victim key is required, since `ft_on_transfer` is a public NEP-141 receiver hook invoked by the token contract itself.

### Recommendation
On deposit, reconcile the internal credit against the actual balance delta observed on the Defuse contract for that token (e.g., query `ft_balance_of(current_account_id)` before and after, or otherwise cap the amount credited in `Contract::deposit`/`ft_on_transfer` by the verified increase in custody) instead of trusting the caller-supplied `amount` unconditionally, mirroring the accounting rigor already applied on the withdrawal path in `ft_resolve_withdraw`.

### Proof of Concept
1. List/accept (or have a user deposit) a NEP-141 token contract `T` whose `ft_transfer_call` implementation deducts a transfer fee `f` from `amount`, so Defuse's real `T` balance only increases by `amount - f`.
2. User calls `T::ft_transfer_call(defuse_id, amount, msg="")`.
3. `T` invokes `Contract::ft_on_transfer(sender_id, amount, "")` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs`, which calls `self.deposit(receiver_id, [(TokenId::Nep141(T), amount)], ...)`.
4. `Contract::deposit` (`contracts/defuse/src/contract/tokens/mod.rs`) adds full `amount` to `total_supplies` and to the receiver's `token_balances`, even though only `amount - f` tokens were actually received by the Defuse contract.
5. The receiver now holds an MT balance of `amount` for `TokenId::Nep141(T)`, redeemable/tradable against other users' funds, while the contract only custodies `amount - f` — a systemic shortfall of `f` per deposit that compounds with repeated deposits.

        &mut self,
