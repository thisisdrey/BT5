### Title
Fixed-window per-connection stream throttling allows boundary-straddling bursts to evade `max_streams_per_throttling_interval` - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a *fixed*, connection-local reset window rather than a sliding-window/token-bucket limiter, and the reset instant is only advanced lazily on the next `throttle_stream` call after `STREAM_THROTTLING_INTERVAL` has elapsed. An unprivileged remote client controlling exactly when it opens QUIC uni-streams on its own connection can straddle this reset boundary to get up to `2 * max_streams_per_throttling_interval` streams admitted within a real-time span far smaller than `STREAM_THROTTLING_INTERVAL`.

### Finding Description
`throttle_stream` gates each new QUIC stream by comparing `stream_count` against `max_streams_per_throttling_interval` within a window bounded by `last_throttling_instant`: [1](#0-0) 

The reset is lazy and per-connection: `last_throttling_instant` only advances when a call happens with `elapsed > STREAM_THROTTLING_INTERVAL`, and at that moment `stream_count` is zeroed atomically with the instant update. `throttle_stream` then checks `stream_count` against the quota: [2](#0-1) 

Because the window boundary is not aligned to a global clock but instead to whenever the attacker's own next stream request happens to arrive, the attacker fully controls the timing of the boundary: it opens `M-1` streams at `T0 + INTERVAL - ε` (all counted in window `k`, since elapsed `< INTERVAL` so no reset fires), then, after `2ε`, opens another `M-1` streams at `T0 + INTERVAL + ε`. The first of that second batch triggers the reset in `reset_throttling_params_if_needed` (zeroing `stream_count` and resetting `last_throttling_instant`), so the remaining streams of that batch are counted against the brand-new window `k+1` and pass unthrottled. The result is `~2(M-1)` streams admitted within `~2ε` real time — far less than `STREAM_THROTTLING_INTERVAL` — directly violating the intended per-source, per-interval cap.

This is reachable by any unstaked/unprivileged client: streams are consumed sequentially in `handle_connection`'s loop (`connection.accept_uni()` → `qos.on_new_stream(&context).await` → `qos.on_stream_accepted`), so a client that simply schedules its stream opens can trigger this pattern: [3](#0-2) 

No other guard prevents this: the counter update in `on_stream_accepted` is a simple `fetch_add` after `throttle_stream` returns, and there is no sliding-window or leaky-bucket accounting (unlike `simple_qos.rs`'s `TokenBucket`-based limiter, which is not used by the `SwQos` path exercised by `stream_throttle.rs`).

### Impact Explanation
This falls under Agave's QoS-evasion category: an unstaked/low-stake connection can locally double its admitted stream rate around each self-timed window boundary, increasing sigverify/dedup/packet-ingestion CPU work relative to the fees paid for that traffic, without needing any staked/privileged position. The effect is a repeatable local 2x spike bounded by `max_streams_per_throttling_interval` (itself bounded by `MAX_UNSTAKED_TPS`/stake ratio), so the sustained long-run average is largely unaffected, but the instantaneous admitted-stream-count-per-sliding-window invariant is provably violated at each transition the attacker chooses to align with.

### Likelihood Explanation
Fully feasible with a single unstaked/unstaked-rate-limited connection and no special privileges — the attacker only needs to control local send timing (delay opening a batch of uni-streams by roughly `STREAM_THROTTLING_INTERVAL`, then fire two back-to-back bursts around the boundary). It is deterministically reproducible in a unit/fuzz test operating directly on `ConnectionStreamCounter`/`throttle_stream` without needing network-level timing precision beyond typical async scheduling granularity.

### Recommendation
Replace the fixed lazy-reset window with a true sliding-window or token-bucket accounting scheme (e.g., decay `stream_count` proportionally to elapsed time each call, similar to `simple_qos.rs`'s `TokenBucket`, or track timestamps of individual admissions and count only those within the trailing `STREAM_THROTTLING_INTERVAL`) so that no `STREAM_THROTTLING_INTERVAL`-sized sliding window can ever admit more than `max_streams_per_throttling_interval` streams regardless of when the caller chooses to invoke the check.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_boundary_straddle_doubles_admitted_streams() {
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max = 10u64; // max_streams_per_throttling_interval

    // Fill window k just before its lazy boundary.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL - Duration::from_millis(1)).await;
    for _ in 0..max {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, addr, &counter, max).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    let admitted_before = counter.stream_count.load(Ordering::Relaxed);

    // Cross the boundary by a hair, then immediately fill window k+1.
    tokio::time::advance(Duration::from_millis(2)).await;
    for _ in 0..max {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, addr, &counter, max).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    let admitted_after = counter.stream_count.load(Ordering::Relaxed);

    // Assert: total streams admitted within a real-time span << STREAM_THROTTLING_INTERVAL
    // exceeds max_streams_per_throttling_interval, violating the sliding-window invariant.
    assert!(admitted_before + admitted_after > max,
        "2x burst admitted within a single STREAM_THROTTLING_INTERVAL-sized sliding window");
}
```
Fuzz variant: randomize the exact offsets around `STREAM_THROTTLING_INTERVAL` and assert, for every sliding window of size `STREAM_THROTTLING_INTERVAL` over the full admission timeline, that the count of admitted streams never exceeds `max_streams_per_throttling_interval`; the assertion fails at boundary-straddling offsets.

    /// Reset the counter and last throttling instant and
    /// return last_throttling_instant regardless it is reset or not.
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
