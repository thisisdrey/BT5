### Title
Contracts/Revive `seal_random` and `call_runtime` let a contract query or roll back on-chain randomness before committing state, defeating the intended unpredictability of `Randomness`-derived draws - ([File: substrate/frame/contracts/src/wasm/runtime.rs])

### Summary
Any pallet in the runtime that produces a "random" outcome via `T::Randomness::random(subject)` (e.g. `pallet-lottery`'s ticket draw, `pallet-society`'s intake/defender selection, `polkadot-runtime-common`'s auction winner) derives its seed from `RandomnessCollectiveFlip`, a **known low-influence, block-hash-based** source explicitly documented as insecure for anything beyond testing. [1](#0-0)  `pallet-contracts` (and `pallet-revive`) expose two host functions to arbitrary contracts that turn this weakness into the exact brute-force/revert primitive described in the NFTX report: `seal_random`, which lets a contract directly query the chain's random seed for an attacker-chosen `subject` and inspect the result inside the same call before deciding whether to commit, [2](#0-1)  and `call_runtime`/`seal_call_runtime`, which lets a contract dispatch any allow-listed `RuntimeCall` (such as a lottery/society/auction-style draw call) and then trap to unwind the whole extrinsic if the outcome is unfavorable. [3](#0-2) 

### Finding Description
The `Randomness` trait's `random(subject)` is explicitly documented as being predictable/gameable: "Any block producer has significant influence over their block hashes… hashing the result of this function will remove any low-influence properties." [4](#0-3)  Multiple pallets consume this primitive to select "random" outcomes for users — e.g. `pallet-lottery::choose_ticket`/`generate_random_number`, which explicitly loops over subjects to "generate new numbers until we hit the limit" and calls `T::Randomness::random(&(PalletId, seed).encode())`. [5](#0-4) 

`pallet-contracts` gives WASM contracts a direct API to read this same seed themselves, for any subject string of the caller's choosing, via `ctx.ext.random(subject)`. [2](#0-1)  A contract can loop over many candidate subjects/nonces off the back of a single dispatched extrinsic, compute the resulting seed for each, and select or influence downstream logic to only "commit" state when a favorable value is found — this is strictly more powerful than the brute-force-and-revert exploit in the report, because no repeated on-chain transactions are even required; the search can be done entirely within contract execution before any host call that would fix the on-chain outcome.

Independently, `call_runtime` lets a contract dispatch an arbitrary allow-listed pallet call (subject to `T::CallFilter`) and then, based on the dispatch's `Ok`/error result or on subsequently reading storage/events it wrote, choose to trap. [3](#0-2)  When a contract traps, the top-level `call`/`instantiate` dispatchable converts this into `ContractReverted`, and the runtime call filter must be checked, but the underlying mechanism — "act on a public dispatchable's random outcome, then unwind the whole extrinsic if not favorable" — is exactly the NFTX bug pattern: `pallet-contracts::Pallet::call` rejects any `did_revert()` output and rolls back the whole transaction's storage changes, allowing the caller to pay only gas for a discarded attempt and retry. [6](#0-5) 

No `onlyEOA`-style guard exists in `pallet-contracts`/`pallet-revive`: `call_runtime` and `random` are available to any contract account, and `CallFilter`/`UnsafeUnstableInterface` gates limit *which* calls/APIs are permitted but do nothing to prevent read-then-revert probing of whatever randomness-consuming calls are allowed.

### Impact Explanation
Any runtime that (a) enables `pallet-contracts`/`pallet-revive` with a `CallFilter` permitting calls into a randomness-consuming pallet (lottery, society, or a custom NFT/reward pallet built on `Randomness`), and (b) does not itself commit-then-reveal its randomness, allows a contract-based attacker to bias or fully predict outcomes that are supposed to be fair/random — e.g., picking a lottery winner, biasing society membership/defender selection, or (for any custom pallet reusing this pattern for NFT/reward distribution) selecting the specific reward instead of a random one. This subverts the fairness guarantee of the affected pallet's payout logic without needing any privileged role, malicious validator, or off-chain infrastructure — it only requires deploying a contract.

### Likelihood Explanation
Likelihood is high wherever `pallet-contracts`/`pallet-revive` is enabled with a non-empty `CallFilter` that permits calls into any `Randomness`-consuming extrinsic, since the primitives (`seal_random`, `call_runtime`) are first-class, documented contract APIs requiring no special permission beyond normal contract deployment. In the reference `substrate/bin/node/runtime` the `CallFilter` is set to `Nothing`, [7](#0-6)  which mitigates the `call_runtime` vector there specifically, but `seal_random` itself is unaffected by `CallFilter` and remains directly reachable by any deployed contract in that runtime configuration, and any production chain that widens `CallFilter` to allow useful pallet calls (a common customization) reopens the `call_runtime` vector as well.

### Recommendation
- Do not rely on `RandomnessCollectiveFlip`/`Randomness::random` for any economically meaningful selection (lottery winner, reward/NFT allocation, membership rotation) that is reachable, directly or indirectly, from contract execution; use a verifiable, off-chain-unpredictable source (VRF-based `ParentBlockRandomness`/BABE randomness with sufficient reveal delay) and ensure the reveal block is strictly later than the block in which any contract could have observed/probed it.
- For any pallet whose random draw can be triggered or observed via a call permitted through `CallFilter`, enforce a commit-reveal split so that the committing extrinsic cannot be atomically followed, within the same origin's call stack, by inspection-and-revert; alternatively, disallow such calls from contract-originated `call_runtime` entirely.
- Treat `seal_random`/`ctx.ext.random` as unsuitable for high-stakes randomness (as already documented) and ensure no in-tree or downstream pallet's fairness relies on values a contract can also read directly.

### Proof of Concept
1. Deploy a contract `C` on a chain running `pallet-contracts` with `CallFilter` permitting `pallet-lottery::Call` (or any custom pallet using `T::Randomness::random`).
2. Inside `C`'s call handler, use `seal_random`/`ext.random(subject)` with attacker-controlled `subject` bytes to compute, off the current on-chain seed, what `pallet-lottery::generate_random_number`/`choose_ticket` would return for that seed — this uses the same `T::Randomness::random` values documented in [8](#0-7) .
3. If the seed does not yield the outcome the attacker wants, have `C` dispatch the draw via `call_runtime` (host function at [3](#0-2) ) and then deliberately trap; `pallet_contracts::Pallet::call` treats the reverted result as `ContractReverted` and unwinds all storage changes from that call, per [6](#0-5) , at the cost of gas only.
4. Repeat across blocks/subjects until the observed/predicted draw matches the attacker's desired winner/reward, then let the transaction commit — reproducing the NFTX "brute-force randomness via revert" pattern against an on-chain randomness consumer instead of an EVM vault contract.

	/// Stores a random number for the current block and the given subject into the supplied buffer.
	///
	/// The value is stored to linear memory at the address pointed to by `out_ptr`.
	/// `out_len_ptr` must point to a u32 value that describes the available space at
	/// `out_ptr`. This call overwrites it with the size of the value. If the available
	/// space at `out_ptr` is less than the size of the value a trap is triggered.
	///
	/// The data is encoded as `T::Hash`.
	#[prefixed_alias]
	#[deprecated]
	fn random(
		ctx: _,
		memory: _,
		subject_ptr: u32,
		subject_len: u32,
		out_ptr: u32,
		out_len_ptr: u32,
	) -> Result<(), TrapReason> {
		ctx.charge_gas(RuntimeCosts::Random)?;
		if subject_len > ctx.ext.schedule().limits.subject_len {
			return Err(Error::<E::T>::RandomSubjectTooLong.into());
		}
		let subject_buf = ctx.read_sandbox_memory(memory, subject_ptr, subject_len)?;
		Ok(ctx.write_sandbox_output(
			memory,
			out_ptr,
			out_len_ptr,
			&ctx.ext.random(&subject_buf).0.encode(),
			false,
			already_charged,
		)?)
	}

	fn choose_ticket(total: u32) -> Option<u32> {
		if total == 0 {
			return None;
		}
		let mut random_number = Self::generate_random_number(0);

		// Best effort attempt to remove bias from modulus operator.
		for i in 1..T::MaxGenerateRandom::get() {
			if random_number < u32::MAX - u32::MAX % total {
				break;
			}

			random_number = Self::generate_random_number(i);
		}

		Some(random_number % total)
	}

	/// Generate a random number from a given seed.
	/// Note that there is potential bias introduced by using modulus operator.
	/// You should call this function with different seed values until the random
	/// number lies within `u32::MAX - u32::MAX % n`.
	/// TODO: deal with randomness freshness
	/// https://github.com/paritytech/substrate/issues/8311
	fn generate_random_number(seed: u32) -> u32 {
		let (random_seed, _) = T::Randomness::random(&(T::PalletId::get(), seed).encode());
		let random_number = <u32>::decode(&mut random_seed.as_ref())
			.expect("secure hashes should always be bigger than u32; qed");
		random_number
	}
