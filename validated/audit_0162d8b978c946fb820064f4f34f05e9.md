### Title
Unbounded `read_to_end` in `run_http_request` allows memory-exhaustion DoS via oversized StackerDB chunk response - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` in `libsigner/src/http.rs` reads the entire HTTP response body into memory with an unbounded `sock.read_to_end(&mut buf)` before any size check occurs. The only size enforcement, in `StackerDBSession::get_latest_chunks`, happens after the full body has already been buffered, so a malicious node can force the signer client to allocate and hold an arbitrarily large buffer per request.

### Finding Description
`libsigner/src/http.rs:249-251`:
```rust
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
```
This reads the full response (headers + body) with no cap on total bytes read. `decode_http_body` (lines 197-217) only applies `MAX_MESSAGE_LEN` bound when the response uses `Transfer-Encoding: chunked` (via `HttpChunkedTransferReader`); for a non-chunked response with a `Content-Length` header (or none), the body bytes are taken as-is (`buf.to_vec()` at line 213) with no size limit applied during the read itself.

`StackerDBSession::get_latest_chunks` (`libsigner/src/session.rs:230-248`) computes a `limit` (`SIGNERS_STACKERDB_CHUNK_SIZE` for signer contracts, else `STACKERDB_MAX_CHUNK_SIZE`) and compares `body_bytes.len() > limit` only *after* `rpc_request` → `run_http_request` has already returned the fully-read body. This is a post-hoc filter, not a read-time bound: the socket read itself (`read_to_end`) has no cap tied to `limit`.

Attack: a malicious node that the signer is configured to query via `StackerDBSession` (self.host) responds to a `GET /v2/stackerdb/.../<slot_id>` request with a valid HTTP response containing a `Content-Length` (or no length header, just streaming until close) body of many megabytes/gigabytes. `run_http_request` will buffer the entire response before `decode_http_response`/`decode_http_body` even run, and only after that does `get_latest_chunks` discard it as `None` for exceeding `limit`.

### Impact Explanation
A single malicious/compromised node that a signer's `StackerDBSession` connects to can force the signer process to allocate memory proportional to the attacker-chosen response size (no upper bound enforced at read time), for every `GET` chunk-fetch call. Repeated calls (`list_chunks`, `get_chunks`, `get_latest_chunks` are called periodically/each StackerDB polling round) allow sustained memory pressure, potentially exhausting signer process memory — a Critical unauthenticated DoS against a signer's client-side networking code, matching "remote crash/unauthenticated DoS from few messages."

### Likelihood Explanation
Preconditions: the signer must have `self.host` pointed at (or be induced to query) a node controlled by the attacker, and the port must be the node's RPC port, which is reachable without authentication for these StackerDB read endpoints. No secret, signature, or privileged role is required from the attacker — they just need to run the queried node/peer and return an oversized, well-formed HTTP response. This is repeatable on every poll cycle at low attacker cost (a single crafted response).

### Recommendation
Bound the read in `run_http_request` (or `decode_http_body`) to the expected/allowed maximum (e.g., `STACKERDB_MAX_CHUNK_SIZE`/`SIGNERS_STACKERDB_CHUNK_SIZE` plus a small header allowance), by reading incrementally with a capped reader (e.g., wrap `sock` with a `Take`/limited reader, or loop `read()` calls tracking cumulative bytes and abort/error once the cap is exceeded) instead of calling `read_to_end` unconditionally. Apply the same cap to the non-chunked path in `decode_http_body`, not just the chunked path via `MAX_MESSAGE_LEN`.

### Proof of Concept
Rust test plan:
1. Spin up a `TcpListener` acting as a fake node.
2. On accept, read the request line/headers (to unblock the client), then write back a valid HTTP/1.1 200 response with `Content-Length: <N>` (or without any length header, closing after writing N bytes) where `N` is e.g. 10x `SIGNERS_STACKERDB_CHUNK_SIZE`.
3. Call `libsigner::http::run_http_request` (or `StackerDBSession::get_latest_chunks` end-to-end against this listener with a signer-named contract id) and assert/measure that the returned/intermediate `buf` inside `run_http_request` grows to `N` bytes (e.g., instrument via a wrapped `Read` that counts bytes, or observe process RSS) before `get_latest_chunks` discards it as `None` for exceeding `SIGNERS_STACKERDB_CHUNK_SIZE`.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
