Audit Report

## Title
`claim_swap` unconditionally deletes the `PendingSwap` record even when the underlying claim only partially succeeds, permanently stranding the source's reserved funds - (File: `substrate/frame/atomic-swap/src/lib.rs`)

## Summary
`claim_swap` calls `swap.action.claim(&swap.source, &target)` and then removes the `PendingSwaps` entry unconditionally regardless of the claim's actual transfer outcome. For `BalanceSwapAction`, `claim()` reduces to `C::repatriate_reserved(...).is_ok()`, and `repatriate_reserved` uses `BestEffort`/`Polite` semantics that can transfer less than the requested value (even zero) while still returning `Ok`, so `is_ok()` is `true` even on partial transfer.

## Finding Description
In `substrate/frame/atomic-swap/src/lib.rs`, `claim` is implemented as:
```rust
fn claim(&self, source: &AccountId, target: &AccountId) -> bool {
	C::repatriate_reserved(source, target, self.value, BalanceStatus::Free).is_ok()
}
``` [1](#0-0) 

and `claim_swap` uses the boolean result only for the emitted event, while unconditionally removing the storage entry:
```rust
let succeeded = swap.action.claim(&swap.source, &target);
PendingSwaps::<T>::remove(target.clone(), hashed_proof);
``` [2](#0-1) 

The `repatriate_reserved` implementation in `substrate/frame/balances/src/impl_currency.rs` explicitly performs a `BestEffort`, `Polite` transfer and returns `Ok` with the actual moved amount subtracted, meaning it can legitimately move less than `value` (down to zero) while still returning `Ok`:
```rust
fn repatriate_reserved(...) -> Result<Self::Balance, DispatchError> {
	let actual =
		Self::do_transfer_reserved(slashed, beneficiary, value, BestEffort, Polite, status)?;
	Ok(value.saturating_sub(actual))
}
``` [3](#0-2) 

Once `PendingSwaps::remove` executes, the only other path capable of releasing the source's reserved balance, `cancel_swap`, requires the entry to still exist:
```rust
let swap = PendingSwaps::<T>::get(&target, hashed_proof).ok_or(Error::<T>::NotExist)?;
``` [4](#0-3) 

Since the entry is already gone, `cancel_swap` can never be invoked again for that swap, leaving any un-transferred portion of the original reservation (made via `action.reserve(&source)` in `create_swap`) permanently locked in the source's reserved balance with no dispatchable call to release it.

## Impact Explanation
This is a permanent, unrecoverable lock of the swap source's reserved funds whenever `repatriate_reserved`'s `Polite` liveness check prevents full transfer (e.g., the source has frozen/locked balance from staking, vesting, or governance locks). It also causes the pallet to emit a misleading `SwapClaimed { success: true }` event despite only a partial (or zero) transfer having occurred. This matches the "permanent user-fund lock" impact category.

## Likelihood Explanation
No privileged access is required — both `create_swap` and `claim_swap` are ordinary signed extrinsics available to any account. The triggering condition (the source account having non-reserved frozen/locked balance at claim time) is common for real accounts engaged in staking, vesting, or governance locks, and can be deliberately engineered by a counterparty who is aware of the source's lock state, or can occur unintentionally through normal use.

## Recommendation
Do not unconditionally remove the `PendingSwaps` entry based solely on a boolean success flag. Either:
- Change `SwapAction::claim` to return the actual amount transferred (or a result capturing partial success), and only fully remove the storage entry when the complete committed value was moved, otherwise retain a reduced entry so `cancel_swap` can reclaim the remainder; or
- Use `Exact` (non-`BestEffort`) precision in `repatriate_reserved` so a partial transfer fails atomically, leaving the `PendingSwap` entry (and reserved funds) intact for later `cancel_swap`.

## Proof of Concept
1. Source `A` calls `create_swap(target = B, hashed_proof, action = BalanceSwapAction::new(100), duration)`, reserving `100` from `A`'s free balance via `action.reserve(&source)`.
2. Before `B` claims, `A`'s account accrues a `frozen`/lock amount (e.g., via staking bond or vesting) such that a `Polite` transfer of the full `100` would push `A`'s total balance below the frozen threshold.
3. `B` calls `claim_swap(proof, action)`; `repatriate_reserved` runs with `BestEffort`+`Polite`, moves less than `100` (possibly `0`) to `B`, and returns `Ok(remaining)`, so `claim()` returns `true`.
4. `claim_swap` removes the `PendingSwap` entry and emits `SwapClaimed { success: true }` despite the shortfall.
5. `A` calls `cancel_swap` and receives `Error::NotExist` because the entry was already removed, permanently stranding the un-transferred remainder of the original `100` reservation in `A`'s reserved balance.
