### Title
Missing bounds check on receiver's net/energy usage counter in `UnDelegateResourceActuator.execute()` can drive resource usage negative - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.execute()` computes a `transferUsage` amount and subtracts it directly from the receiver's `netUsage`/`energyUsage` counter with no floor/bounds check, unlike other resource-counter mutators in the same codebase (e.g. `AccountCapsule.safeAddAcquiredDelegatedFrozenBalanceForBandwidth`) which explicitly clamp results with `max(0, ...)`. This is the same bug class as CVE-2025-21647 (sch_cake): a per-entity accounting counter is decremented by an attacker-influenced amount without a bounds check, risking underflow of a value that is later used to gate resource consumption.

### Finding Description
In `execute()`: [1](#0-0) 

`transferUsage` is derived from `receiverCapsule.getNetUsage() * (unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth())`, capped only by `unDelegateMaxUsage` computed from an independent formula (`unDelegateBalance / TRX_PRECISION * totalNetLimit / totalNetWeight`) — not by `receiverCapsule.getNetUsage()` itself: [2](#0-1) 

Because `transferUsage` is never clamped to `min(transferUsage, netUsage)`, and the two cap computations (`unDelegateMaxUsage` vs. the ratio-based estimate) use different denominators (`totalNetWeight` vs. `receiverCapsule.getAllFrozenBalanceForBandwidth()`), a receiver whose own frozen-for-bandwidth balance is small relative to `unDelegateMaxUsage`'s cap can end up with `transferUsage > receiverCapsule.getNetUsage()`. The subsequent line:
```
long newNetUsage = receiverCapsule.getNetUsage() - transferUsage;
receiverCapsule.setNetUsage(newNetUsage);
```
stores a negative value directly into the persisted `AccountCapsule` with no bounds check — the same missing-bounds-check pattern flagged in the CVE. The identical unguarded-subtraction pattern is repeated for the ENERGY branch: [3](#0-2) 

Elsewhere in the codebase, similar counter mutations are explicitly hardened against going negative (e.g. `max(0, ..., useStrict)`): [4](#0-3) 

This shows the project is aware of and defends against exactly this failure mode elsewhere, but the `netUsage`/`energyUsage` subtraction in `UnDelegateResourceActuator` was not given the same treatment.

I was not able to fully trace `receiverCapsule.getAllFrozenBalanceForBandwidth()` / `getAllFrozenBalanceForEnergy()` and `calculateGlobalNetLimit()` implementations within the available tool budget to conclusively prove the ratio can exceed 1 in a reachable, single-transaction scenario (e.g. via a receiver that is a TVM-created/self-destructed contract account with mismatched frozen totals, a path the code comments explicitly acknowledge — "A TVM contract suicide, re-create will produce this situation"). This uncertainty should be resolved by a deeper trace of those two methods before treating this as confirmed-exploitable.

### Impact Explanation
If `netUsage`/`energyUsage` can be driven negative, subsequent bandwidth/energy accounting (`netLimit - netUsage` style checks in `BandwidthProcessor`/`EnergyProcessor`) would treat the account as having significantly more headroom than it should, effectively granting unbacked free bandwidth/energy to that account — a resource-accounting integrity violation reachable by any account that is the receiver of a `DelegateResourceContract`/`UnDelegateResourceContract` pair, i.e., any unprivileged transaction sender.

### Likelihood Explanation
Reaching this code path only requires a normal signed `UnDelegateResourceContract` transaction from any account, no special privileges needed. The trigger condition requires a receiver account state (frozen balance vs. delegated balance mismatch) that the code comments themselves say can arise from ordinary TVM contract lifecycle events (create/suicide/re-create). Full confirmation of an end-to-end exploit requires further analysis of `getAllFrozenBalanceForBandwidth()`/`calculateGlobalNetLimit()`, which I could not complete.

### Recommendation
Clamp `transferUsage` to `Math.min(transferUsage, receiverCapsule.getNetUsage())` (and analogously for energy) before subtracting, and additionally clamp the result of the subtraction with `Math.max(0, newNetUsage)` before calling `setNetUsage`/`setEnergyUsage`, mirroring the `max(0, ...)` pattern already used in `AccountCapsule`'s other safe-add helpers.

### Proof of Concept
Not independently constructed/verified — a concrete PoC would require constructing a receiver account whose `getAllFrozenBalanceForBandwidth()` (or energy equivalent) is smaller than what the `unDelegateMaxUsage` formula implies, then issuing `DelegateResourceContract` followed by `UnDelegateResourceContract` from an owner account to that receiver, and observing `receiverCapsule.getNetUsage()` become negative after `execute()`. This requires the deeper trace mentioned above to confirm feasibility; I flag this as unverified rather than asserting confirmed exploitability.
