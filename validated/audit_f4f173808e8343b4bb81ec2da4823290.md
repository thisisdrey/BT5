### Title
CREATE2 contract-collision path silently repurposes an attacker-owned account without clearing its multisig permission, letting the original key-holder retain signing control over a "contract" address - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.createContractImpl()` allows an EOA that was created in advance at a to-be-deployed CREATE/CREATE2 address to have its account type flipped to `Contract` while its previously configured multisig `Permission` (owner/active) is left untouched. Because TRON's signature/permission verification (`TransactionCapsule.validateSignature` / `checkWeight`) never checks `AccountType`, the original key-holder still authorizes ordinary transactions from that address after it becomes a "contract," which is exactly the class of bug the reference report describes: an object identifier (`bytes32`/account address) that is reachable and can be squatted before the system marks/converts it, letting the pre-existing owner retain privileges that should belong exclusively to the new object type.

### Finding Description
When a contract creates a new contract via `CREATE`/`CREATE2`, `createContractImpl()` computes the deterministic address and checks whether an account already exists there: [1](#0-0) 

If an account already exists at that address (attacker pre-funded/pre-created it with `AccountCreateContract` or a plain transfer, and configured its multisig `Permission` via `AccountPermissionUpdateContract` while it was still a normal EOA under their control), the code only calls `existingAccount.updateAccountType(AccountType.Contract)` and `existingAccount.clearDelegatedResource()`. It never resets the account's `ownerPermission`/`activePermission` structure, unlike the codebase's own precedent for repurposing a special account, `Manager.resetBlackholeAccountPermission()`, which explicitly overwrites the permission with a fresh, key-less default when converting the Blackhole account: [2](#0-1) 

Transaction/permission verification is keyed purely off the `ownerAddress` and its stored `Permission`, with no dependency on `AccountType`: [3](#0-2) [4](#0-3) 

So once the address flips to `Contract`, the original private key(s) that satisfy that `Permission` can still sign ordinary `TransferContract`/`TriggerSmartContract`/etc. transactions with `ownerAddress` equal to the "contract" address, moving out any TRX/TRC10 balance the contract accumulates, entirely bypassing the deployed contract's bytecode logic. `CreateAccountActuator.validate()` also confirms nothing requires proof of key ownership for the target `accountAddress` when creating it, so any address (including a future CREATE2 target) can be squatted first: [5](#0-4) 

This mirrors the Nayms report's core defect: object identifiers/addresses that are not properly "reset"/"validated" when repurposed for a new (privileged) object type allow the previous owner to retain access that should be exclusive to the new type — java-tron even demonstrates it knows the correct fix pattern (`resetBlackholeAccountPermission`) but does not apply it in the CREATE2/CREATE collision path.

### Impact Explanation
Any user interacting with a contract deployed via `CREATE2` at a squatted address risks having funds sent to that "contract" siphoned off by whoever pre-created the account and set its permission, because the account's signing authority was never revoked when it converted to `AccountType.Contract`. This is a direct theft-of-funds vector: TRX/TRC10 balances, and any assets a dApp assumes are locked behind contract logic, can instead be moved by an ordinary signed transaction from the squatter's key(s).

### Likelihood Explanation
Exploitation requires the attacker to predict (or control) the `CREATE`/`CREATE2` target address ahead of deployment (feasible for `CREATE2`, which is address-deterministic from sender/salt/init-code, and it is already a known general precondition of `CREATE2` squatting attacks), then front-run with an `AccountCreateContract`/transfer plus an `AccountPermissionUpdateContract` to install a permission they control, before the intended deployer's `CREATE2` transaction lands. This requires no special privilege beyond ordinary account/contract-deployment transactions, making it reachable by any unprivileged broadcaster.

### Recommendation
When `createContractImpl()` repurposes a pre-existing account for a new contract (the `existingAccount != null && !contractAlreadyExists` branch), reset the account's owner/witness/active `Permission` fields to the address-derived default (single-key-none / non-signable) in the same way `Manager.resetBlackholeAccountPermission()` does for the Blackhole account, in addition to `updateAccountType` and `clearDelegatedResource`, so that no previously configured signer retains authority over the address once it becomes a contract.

### Proof of Concept
1. Attacker computes the deterministic CREATE2 address `X` that a victim's factory contract will use for a specific `salt`/init-code (`generateContractAddress2`, as tested in `Create2Test`).
2. Attacker submits `AccountCreateContract` (any funder/ownerAddress can create `accountAddress = X` per `CreateAccountActuator.validate()`, which never checks key ownership of `X`).
3. Attacker submits `AccountPermissionUpdateContract` for `X`, signed with `X`'s own freshly-generated key (which the attacker controls since they created the account and can supply a self-consistent default permission, or, if multisig is enabled, install their own key as owner/active signer).
4. Victim's factory later executes `CREATE2` to deploy the real contract at `X`. `Program.createContractImpl()` sees `existingAccount != null`, sets `AccountType.Contract`, clears delegated resources, but leaves the `Permission` set in step 3 intact.
5. Users send TRX/TRC10 to `X` believing it is governed solely by the deployed contract's bytecode.
6. Attacker submits an ordinary `TransferContract`/`TransferAssetContract` with `ownerAddress = X`, signed with the key installed in step 3; `TransactionCapsule.validateSignature`/`checkWeight` authorize it because they only consult `Permission`, not `AccountType`, draining the funds.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public void addSign(byte[] privateKey, AccountStore accountStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = this.transaction.getRawData().getContract(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwnerAddress();
    AccountCapsule account = accountStore.get(owner);
    if (account == null) {
      throw new PermissionException("Account is not exist!");
    }
    Permission permission = account.getPermissionById(permissionId);
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    List<ByteString> approveList = new ArrayList<>();
    SignInterface cryptoEngine = SignUtils
        .fromPrivate(privateKey, CommonParameter.getInstance().isECKeyCryptoEngine());
    byte[] address = cryptoEngine.getAddress();
    if (this.transaction.getSignatureCount() > 0) {
      checkWeight(permission, this.transaction.getSignatureList(),
          this.getTransactionId().getBytes(),
          approveList);
      if (approveList.contains(ByteString.copyFrom(address))) {
        throw new PermissionException(encode58Check(address) + " had signed!");
      }
    }

    long weight = getWeight(permission, address);
    if (weight == 0) {
      throw new PermissionException(
          ByteArray.toHexString(privateKey) + "'s address is " + encode58Check(address)
              + " but it is not contained of permission.");
    }
    ByteString sig = ByteString.copyFrom(cryptoEngine.Base64toBytes(cryptoEngine
        .signHash(getTransactionId().getBytes())));
    this.transaction = this.transaction.toBuilder().addSignature(sig).build();
  }
