### Title
Non-atomic check-then-update replay window allows a duplicate/replayed packet to be processed twice under concurrent delivery - ([File: connection_state.go])

### Summary
The external report describes a reentrancy guard (`_reentrancyStatus`) that is checked and cleared in two separate, non-atomic steps, letting an attacker slip a second call through the window between the check and the reset. The closest reachable analog in this codebase is `ConnectionState.Decrypt` / `VerifyRelay`, where the anti-replay guard (`Bits.Check` then `Bits.Update`) is also split into two separate lock/unlock critical sections with the expensive AEAD decrypt operation sandwiched in between, rather than being executed as one atomic "check-and-mark-seen" operation.

### Finding Description
`ConnectionState.Decrypt` implements the anti-replay protection like this: [1](#0-0) 

The pattern is:
1. Lock, call `window.Check(messageCounter)`, unlock.
2. Perform the AEAD decrypt (`DecryptDanger`) with no lock held.
3. Lock again, call `window.Update(messageCounter)`, unlock.

`Bits.Check` and `Bits.Update` are only individually protected — the *sequence* "check-not-seen, decrypt, mark-seen" is not atomic: [2](#0-1) [3](#0-2) 

If two threads receive the same encrypted packet (or an attacker replays it) at nearly the same time, both can pass `Check()` before either calls `Update()`, because the lock is released between the two calls. Both will then run the (expensive, CPU-bound) decrypt operation for the same counter, and only the second `Update()` call will detect the duplicate and reject it — but by then the plaintext has already been produced and, depending on how the caller uses the returned bytes before checking the error, could already have been forwarded/acted on. This mirrors the report's root cause: a guard meant to make a two-step protected sequence atomic is implemented as two independently-locked steps, so a second "reentrant" call can land in the gap and be treated as if it were the sole caller — exactly parallel to `_nonReentrantBefore`/`_nonReentrantAfter` being bypassable because the flag is reset unconditionally rather than the whole entry-to-exit sequence being treated as a single, indivisible unit.

`VerifyRelay` (used for relay-forwarded traffic, i.e., also reachable without holding a CA-signed cert on the path in between) has the identical pattern: [4](#0-3) 

### Impact Explanation
If the surrounding call sites are (or become) multi-threaded per-`ConnectionState` (e.g., multiple socket-reader goroutines feeding the same tunnel, or relayed traffic processed concurrently), this gap allows a genuinely replayed ciphertext to be decrypted and processed twice instead of being uniformly rejected on the second occurrence. This is a data-plane replay-protection weakness: at minimum it produces double-processing of a single wire message; if any caller acts on the decrypted bytes before observing the final error return, it becomes an actual replay of application data.

### Likelihood Explanation
I was not able to fully confirm, within the scope of this investigation, whether `Decrypt`/`VerifyRelay` are ever invoked concurrently for the same `ConnectionState` by multiple reader goroutines in the current version of `interface.go`/`outside.go` (I found references to multiple listen routines in `main.go`/`interface.go` but could not trace whether packets for one tunnel are guaranteed to be serialized onto a single goroutine before reaching `Decrypt`). This uncertainty limits how confidently the race can be judged externally triggerable versus only a latent code-level correctness issue if such serialization is enforced elsewhere. Flagging this explicitly since I could not conclusively verify it with the tools available in this session — a Devin session with full repository access would be needed to trace the packet-reader-to-`ConnectionState` dispatch path and confirm or rule out concurrent delivery.

### Recommendation
Hold a single lock (or otherwise make the operation atomic) across the entire "check window → decrypt → mark window" sequence in `Decrypt` and `VerifyRelay`, so a second thread cannot observe "not yet seen" for a counter that is concurrently being processed. Alternatively, reserve the slot (mark provisionally) before decrypting and only finalize/roll back based on decrypt success, so no two callers can ever be mid-flight on the same counter simultaneously.

### Proof of Concept
Conceptual (not verified against actual concurrent dispatch in this codebase):
1. Attacker captures one valid encrypted UDP packet on an established tunnel.
2. Attacker (or a NAT/network duplication) delivers two identical copies of the packet to the receiver at nearly the same instant.
3. If the receiver's packet pipeline can dispatch both copies to `ConnectionState.Decrypt` concurrently, both may pass `window.Check()` before either calls `window.Update()`, causing both to execute `DecryptDanger` for the same message counter — i.e., the same ciphertext is decrypted twice instead of the second copy being rejected as a replay at the check stage.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
