### Title
HTTP response body decoding ignores `Content-Length`, allowing response smuggling in `StackerDBSession::rpc_request` - (File: libsigner/src/http.rs)

### Summary
`decode_http_body` in the non-chunked branch returns the entire remainder of the buffer (`buf.to_vec()`) after `body_offset`, without ever checking it against the declared `Content-Length` header. Since `run_http_request` reads the full socket stream via `sock.read_to_end` before calling `decode_http_response`/`decode_http_body`, a malicious StackerDB peer can append arbitrary trailing bytes after a legitimate, correctly-sized body and have them silently included in the "body" handed back to the caller.

### Finding Description
The broken equality: the bytes returned from `decode_http_body` must equal exactly the `Content-Length`-declared body, but the function returns everything past `body_offset` unconditionally: [1](#0-0) 

`run_http_request` buffers the entire response with `sock.read_to_end(&mut buf)` before any length validation occurs, then computes `body_offset` purely from header parsing and slices `buf[body_offset..]` for the body: [2](#0-1) 

Because the connection is closed by the server (`Connection: close` is requested by the client, and the read loop relies on EOF via `read_to_end`), a malicious StackerDB peer being queried by `StackerDBSession::rpc_request` fully controls when the socket closes and what bytes precede that closure. It can send a well-formed response with `Content-Length: N` and a genuine `N`-byte JSON body (e.g., a `StackerDBChunkAckData`), then append additional attacker-chosen bytes before closing the socket. `decode_http_body`'s non-chunked path never truncates to `N`, so the extra bytes are included in the returned `Vec<u8>` and passed on to whatever parses the response (e.g., `serde_json::from_slice` in the caller).

### Impact Explanation
This is a request/response desynchronization / response-smuggling primitive against the signer acting as an HTTP client to a StackerDB peer. The immediate effect is corruption of what the signer believes was returned for its own PUT-chunk acknowledgement path, and depending on how the caller parses the returned bytes (`serde_json::from_slice` typically stops at the first valid JSON value, but if the caller instead expects the buffer to be exactly the declared length, or logs/relays it elsewhere), extraneous attacker-controlled bytes can pollute downstream processing. At minimum this is a violation of HTTP framing semantics that breaks the length-invariant the code purports to enforce, enabling one malicious StackerDB peer to inject unbounded extra data into a client-side HTTP response buffer it does not own.

### Likelihood Explanation
This requires only a remote party running its own StackerDB replica/peer that the signer's `StackerDBSession::rpc_request` connects to and queries — no secret, no privileged role, and no special peer state is needed beyond being a normal, connectable peer. The attacker fully controls the raw bytes and timing of socket closure on their side of the connection, making this trivially and repeatably triggerable on every RPC request the signer issues to that peer.

### Recommendation
In `decode_http_body`, parse the `content-length` header (when `transfer-encoding` is absent) and truncate/validate the non-chunked body to exactly that length, returning an error (e.g., `RPCError::MalformedResponse`) if the actual buffer length does not match the declared `Content-Length`.

### Proof of Concept
Rust unit test in `libsigner/src/tests/http.rs`-style: construct headers map with `content-length: "10"`, build a `buf` of 200 bytes (10 legitimate body bytes + 190 arbitrary trailing bytes), call `decode_http_body(&headers, &buf)`, and assert `result.len() == 200` instead of the expected `10` — demonstrating the framing violation. A full network-level PoC would spin up a mock TCP listener acting as a malicious StackerDB peer that returns a response with `Content-Length: 10` but writes 200 bytes before closing the socket, then call `run_http_request` against it and assert the returned body is longer than declared.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
