### Title
Read-only gating is enforced only at the storage-transaction layer, not at the MVCC cache layer, letting `OptimizeRepository` bypass write gating - (File: internal/grpc/middleware/mvcc/mvcc.go)

### Summary
Gitaly enforces "this RPC must not write" via two independent mechanisms that are supposed to agree: the storage transaction manager's `isReadOnly()`/`forceReadOnly` override, and the MVCC cache interceptor's own read-only decision. These two mechanisms are implemented with different logic, and the second one silently ignores the override the first one relies on — mirroring the `PhiNFT1155` root cause, where the pause gate (`PausableUpgradeable`) was applied on the wrong layer/inheritance path and simply didn't cover the actual mutating code path (`ERC1155._update`).

### Finding Description
`internal/gitaly/storage/storagemgr/middleware.go` computes whether an RPC's storage-level transaction should be read-only via: [1](#0-0) 
`OptimizeRepository` is annotated `MAINTENANCE` in the proto (not `ACCESSOR`), but is force-classified as read-only here because "it invokes the housekeeping manager that starts its own write transactions if necessary. The RPC itself doesn't need to be considered a write for that reason." [2](#0-1) 

Separately, the MVCC cache interceptor (`internal/grpc/middleware/mvcc/mvcc.go`) decides whether the `mvcc.LocalCache` it hands to the RPC handler is read-only using a completely different, unlinked computation — the raw proto operation type, with no reference to `forceReadOnly`: [3](#0-2) 

Because `OptimizeRepository`'s op type is `MAINTENANCE`, `op == protoregistry.OpAccessor` evaluates `false`, so `mvcc.NewLocalCache(..., readOnly=false)` is created — a *mutator* cache — even though the surrounding storage transaction was begun as `ReadOnly: true`: [4](#0-3) 

With `readOnly=false`, `LocalCache.prepare()` provisions a mutable manifest (`GIT_MVCC_MANIFEST_PATH`) instead of a pinned read snapshot (`GIT_MVCC_MANIFEST`): [5](#0-4) 
and at RPC completion, `Commit()` — which is a no-op only when `m.readOnly` is true — proceeds to upload new artifacts and perform a compare-and-swap advance of the canonical manifest pointer directly against object storage: [6](#0-5) 

That `rs.Commit()` call is a side-channel to the object-storage-backed manifest store; it does not go through the Gitaly `TransactionManager`/WAL that the storage-level `ReadOnly: true` transaction was supposed to gate. `git housekeeping/optimization_strategy.go` confirms `OptimizeRepository`'s housekeeping logic is itself MVCC-backend aware, so this path is live rather than purely theoretical for repositories using the MVCC reference backend.

### Impact Explanation
An ordinary user triggering repacking/housekeeping (`OptimizeRepository`, which any client with repository access can invoke, and which Praefect/replication treats as a lightweight/read-only-ish operation per `forceReadOnly`) can cause the canonical MVCC manifest pointer to be advanced and new artifacts published to durable object storage outside of the transaction/voting/replication machinery that every other mutator RPC is required to go through (`doc/transactions.md` describes the two-vote requirement for mutators). This can silently desynchronize the manifest pointer from what Praefect/replicas believe is committed, since the write was never voted on nor logged in the WAL, and it happened via a path explicitly modeled as "read-only." The result class matches "DoS of a handler / cross-cutting consistency bypass": corrupted or divergent repository state, or torn writes if `OptimizeRepository` races with a real mutator RPC that legitimately advances the manifest, since neither RPC's storage-level transaction is aware of the other's MVCC-level write.

### Likelihood Explanation
This requires the repository to be using the (experimental, feature-flag-gated) MVCC reference backend, and `internal/git/housekeeping/optimization_strategy.go`'s MVCC-aware logic to actually trigger a write during `OptimizeRepository`. The MVCC backend and its RPC-flow documentation (`doc/mvcc_rpc_flow.md`) describe it as work-in-progress ("this is probably a result of the vibe coding"), so it is not yet a default/GA code path, which lowers likelihood versus a fully production feature. Still, the mismatch between `forceReadOnly` and the MVCC interceptor's independent classification is a concrete, reachable code defect rather than a theoretical concern, since any repository-scoped `MAINTENANCE`/`MUTATOR` RPC that is deliberately forced read-only at the storage layer will silently get mutator treatment from the MVCC cache unless its full method name also happens to equal `OpAccessor`.

### Recommendation
Have `internal/grpc/middleware/mvcc/mvcc.go`'s `buildCache` call the same read-only determination the storage transaction manager uses (i.e., export and reuse `storagemgr.isReadOnly`/`forceReadOnly`, or thread the already-computed transaction's `ReadOnly` flag from context into `buildCache`) instead of independently re-deriving read-only status from `methodInfo.Operation`. This ensures a single source of truth for "does this RPC write" the same way `ERC1155PausableUpgradeable._update` centralizes the pause check on the one function all transfer paths funnel through.

### Proof of Concept
1. Enable the MVCC reference backend for a repository (`git.ReferenceBackendMVCC`), per `internal/git/gittest/repo.go` / `internal/git/reference_backend.go` test helpers.
2. Call `RepositoryService.OptimizeRepository` on that repository as an ordinary authorized client, while housekeeping (per `internal/git/housekeeping/optimization_strategy.go`) triggers a change that would update reftables/objects.
3. Observe that:
   - `storagemgr/middleware.go` begins the storage transaction with `ReadOnly: true` (because `forceReadOnly[OptimizeRepository] == true`), so no WAL entry / vote is produced for this RPC.
   - `mvcc/mvcc.go`'s `buildCache` computes `op == protoregistry.OpAccessor` as `false` (since `OptimizeRepository`'s annotated op is `MAINTENANCE`), constructing the cache with `readOnly=false`.
   - At the end of the RPC, `LocalCache.Commit()` (not a no-op, since `m.readOnly=false`) uploads artifacts and calls `rs.Commit(ctx, repositoryID, baseHash, newHash)`, advancing the canonical manifest pointer in object storage — a durable, cluster-visible write — with no corresponding transaction vote or WAL entry having been produced.
4. This can be directly compared against `internal/git/mvcc/cache_test.go`, which shows `Commit()` is a no-op precisely when `readOnly=true` is passed to `NewLocalCache` — confirming that the `OptimizeRepository` path receives the wrong value for this flag relative to how the storage layer classifies the same RPC.

func (m *CacheInterceptor) buildCache(ctx context.Context, repo *gitalypb.Repository, op protoregistry.OpType) (*mvcc.LocalCache, error) {
	if !m.isMvccReferenceBackend(ctx, repo) {
		return nil, nil
	}

	storagePath, err := m.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, err
	}

	// This is a temporary solution. Ideally, the ObjectStorage here should be a shared-instance
	// (singleton)for the whole Gitaly process. However, Gitaly has the concept of `Storages`,
	// which are different locations on disk where a repository can be stored. Given the state of
	// discussions with how we want to go with object pools, I don't think we will support multiple
	// `Storages` in the long term. For now, let's just create the ObjectStorage here. Once the
	// `Storages` concept becomes obsolete, we can move the creation of the ObjectStorage further
	// up in the call stack to have a singleton.
	m.poolMutex.Lock()
	defer m.poolMutex.Unlock()

	objectStorage, ok := m.objectStoragePool[storagePath]
	if !ok {
		st := mvcc.NewLocalStorage(storagePath)
		m.objectStoragePool[storagePath] = st
		objectStorage = st
	}

	if fields := logger.CustomFieldsFromContext(ctx); fields != nil {
		fields.RecordMetadata("mvcc.used", true)
	}

	cache := mvcc.NewLocalCache(objectStorage, m.runtimeDir, storagePath, repo.GetRelativePath(), op == protoregistry.OpAccessor)
	return cache, nil
}

// Commit publishes any MVCC artifacts that have been produced by the LocalCache, and
// updates the repository to point to the latest manifest.
func (m *LocalCache) Commit(ctx context.Context) error {
	if m.readOnly {
		return nil
	}

	if m.ManifestPath() == "" {
		return fmt.Errorf("empty GIT_MVCC_MANIFEST_PATH")
	}

	// Assert the at-most-once property: advancing the canonical pointer more than
	// once for a single RPC would result in a torn write.
	if m.committed {
		return fmt.Errorf("mvcc: commit called more than once")
	}
	m.committed = true

	newHashBytes, err := os.ReadFile(m.ManifestPath())
	if err != nil {
		return fmt.Errorf("read from manifest path: %w", err)
	}
	newHash := strings.TrimSuffix(string(newHashBytes), "\n")
	if newHash == m.baseHash {
		return nil // no changes, nothing to publish
	}

	// Upload the new artifacts before advancing the pointer so the pointer never
	// references an artifact that is not yet durable.
	if err := m.putNewArtifacts(ctx, newHash); err != nil {
		return fmt.Errorf("put new artifacts: %w", err)
	}

	// Atomically advance the canonical manifest pointer.
	return m.rs.Commit(ctx, m.repositoryID, m.baseHash, newHash)
}
