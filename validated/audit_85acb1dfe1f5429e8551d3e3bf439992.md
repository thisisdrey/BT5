### Title
Attacker can fill a victim's per-account token list (`MAX_TOKENS_PER_USER`) with dust deposits/transfers, permanently reverting `UserReachedMaxTokens` on the victim's new deposits, mints, and receipt of deposit tokens — ([File: contracts/Pool.sol])

### Summary
The OpenVPN CVE is a memory-leak DoS: a client holding a valid credential repeatedly allocates server-side state that is never freed, exhausting a finite resource. The Metronome analog is exhaustion of a victim's bounded per-account token lists. `Pool` tracks `depositTokensOfAccount` / `debtTokensOfAccount` in `MappedEnumerableSet`, capped at `MAX_TOKENS_PER_USER = 30`, enforced by `onlyIfAdditionWillNotReachMaxTokens` in `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` (`contracts/Pool.sol:143-148, 204-220`). Because `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary beneficiary (`contracts/DepositToken.sol:211-237` → `_mint` → `pool.addToDepositTokensOfAccount(onBehalfOf_)` at lines 485-488) and `DepositToken.transfer`/`seize` add the token to the *recipient's* list (`_transfer` at lines 517-520), any unprivileged EOA can stuff a victim's list with 1-wei positions of every deposit token in the pool. Once the combined count reaches 30, every subsequent add reverts with `UserReachedMaxTokens`.

### Finding Description
- `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once `len(depositTokensOfAccount) + len(debtTokensOfAccount) >= 30` (`contracts/Pool.sol:143-148`).
- `DepositToken.deposit(1 wei, victim)` calls `_mint(victim, dust)` which calls `pool.addToDepositTokensOfAccount(victim)` whenever the victim's prior balance is 0 (`contracts/DepositToken.sol:486-488`). No consent is required; `onBehalfOf_` is attacker-chosen. With a nonzero `depositFee`, the attacker just deposits slightly more than the fee so `_deposited > 0`.
- Equivalently, `DepositToken.transfer(victim, 1)` adds the token to the victim's list via `_transfer` (`contracts/DepositToken.sol:517-520`).
- The attacker's own `DebtToken` debt cannot be force-added (debt tokens are non-transferable; `issue`/`mint` add only to the caller's list, `contracts/DebtToken.sol:598-600`), so the attacker fills the `depositTokens` side, up to the number of deposit tokens registered in the pool.

Once filled, for the victim:
- `DepositToken.deposit` into any *new* collateral type reverts (`_mint` → add → `UserReachedMaxTokens`).
- `DebtToken.issue` for any *new* synthetic reverts (`_mint` → `addToDebtTokensOfAccount` → `UserReachedMaxTokens`), and `DebtToken.mint` via `SmartFarmingManager.leverage` reverts the same way.
- Incoming `transfer`/`transferFrom`/`seize` of any deposit token the victim doesn't already hold reverts — this also means liquidations via `DepositToken.seize` revert if the *liquidator's* own list was pre-filled, and airdropped/OTC msdTOKEN transfers to the victim fail.

The victim can free slots by transferring dust out to zero-balance (`_transfer` → `removeFromDepositTokensOfAccount`, `contracts/DepositToken.sol:523-525`) or by withdrawing, but the attacker can re-fill a slot in the same or next transaction at dust cost — the leak is cheaper to cause than to clean, matching the CVE's asymmetric resource exhaustion.

### Impact Explanation
Temporary freezing of funds / liveness denial. A targeted victim is blocked from opening positions with new collateral types, issuing any new synthetic debt, leveraging via `SmartFarmingManager`, and receiving msdTOKEN transfers of tokens they don't already hold. Recovery requires the victim to spend gas evicting entries, and the eviction can be re-griefed indefinitely, so positions approaching liquidation cannot add new collateral to restore health while the attack is active — potentially converting to bad debt if the victim's only path to solvency was depositing a new collateral type.

### Likelihood Explanation
Requires no privileged role: any EOA can call `deposit(amount, victim)` or `transfer(victim, 1)`. Cost is dust collateral × number of pool deposit tokens. The constraint is that the attacker can only add up to `pool.getDepositTokens().length` distinct entries, so the attack only fully locks a victim when that count plus the victim's existing entries reaches 30; pools with many registered deposit tokens (the `depositTokens` set is capped by `ReachedMaxDepositTokens` but can hold well over 15) make this reachable. Not stopped by `whenNotPaused`, `nonReentrant`, `SynthContext`, or `_revertIfLocked` (the *recipient* has no lock check on receiving).

### Recommendation
- Make list membership opt-in or victim-controlled: e.g., only add to `depositTokensOfAccount` on `deposit` when `onBehalfOf_ == _msgSender()`, or require an explicit `claim`/opt-in for transfers that would create a new entry.
- Alternatively, decouple the health-check iteration from the cap: iterate over `depositTokens`/`debtTokens` filtered by nonzero balance instead of per-account sets, or raise/remove the per-user cap while bounding iteration.
- Add a sweep/self-clean function so a victim can batch-remove zero/low-balance entries in one call.

### Proof of Concept
Hardhat fork/test sketch:

```ts
// setup: pool with N registered deposit tokens, victim has some position
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber() // 30
const depositTokens = await pool.getDepositTokens()

// attacker fills victim's list with dust deposits on behalf of victim
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt)
  const underlying = await ethers.getContractAt('ERC20', await token.underlying())
  await underlying.connect(attacker).approve(token.address, MaxUint256)
  // deposit just above depositFee so _deposited > 0
  await token.connect(attacker).deposit(ethers.utils.parseUnits('1', decimals), victim.address)
}

expect(await pool.getDepositTokensOfAccount(victim.address)).length.to.be.gte(max)

// victim can no longer deposit a new collateral type or issue new debt
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

await expect(
  debtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// incoming transfer of a new msdTOKEN to victim also reverts
await expect(
  anyDepositToken.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Note: if the pool's registered deposit tokens are fewer than needed to reach 30 for a given victim, combine with the victim's own existing deposit/debt entries; the attack fully locks victims whose existing list length `L` satisfies `L + depositTokens.length >= 30`.
