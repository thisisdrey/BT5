All six privileged RPC endpoints compare the `Authorization` header against the configured secret using plain string inequality (`auth_header != password`), with no constant-time comparison utility (`subtle`, `constant_time_eq`, etc.) used anywhere in the codebase.

### Title
Non-constant-time HTTP authorization token comparison enables timing side-channel token recovery - (File: stackslib/src/net/api/postblock_proposal.rs, postblock_v3.rs, blocksimulate.rs, txsimulate.rs, fastcallreadonly.rs, blockreplay.rs)

### Summary
The `auth_token` configured via `connection_options.auth_token` is used to gate several `/v3` RPC endpoints (`/v3/block_proposal`, `/v3/blocks/simulate/:id`, `/v3/blocks/replay/:id`, `/v3/transactions/simulate`, `/v3/contracts/fast-call-read/...`) and the `broadcast=1` mode of `/v2/blocks` (`postblock_v3.rs`). Each handler's `try_parse_request` compares the client-supplied `authorization` header to the stored secret with a plain `!=` comparison on `String`, e.g.: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Rust's `String`/`&str` `PartialEq` (and the underlying `memcmp`-based slice comparison) short-circuits on the first mismatched byte, so comparison time is a monotonic function of the length of the matching prefix. This is the same bug class as GHSA-c6wg-cm5x-rqvj (CWE-208, Observable Timing Discrepancy) — the OpenSearch internal basic auth IdP leaked user existence via response-time variance; here the equivalent primitive leaks how many leading bytes of an attacker-supplied token match the real secret.

### Finding Description
Every one of these handlers implements the exact same pattern:
```rust
let Some(password) = &self.auth else { ... };
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
No handler in `stackslib/src/net/api/**` uses a constant-time comparison primitive — a codebase-wide search for `subtle::` / `constant_time_eq` found no matches. Because the comparison is a byte-wise, early-exit equality check, an attacker who can measure per-request latency precisely enough (repeated sampling to average out network jitter) can incrementally recover the `auth_token` byte-by-byte: guesses that share a longer correct prefix with the true token take measurably longer to fail than guesses that diverge earlier, mirroring exactly the "user exists vs. does not" timing oracle described in the OpenSearch advisory, but applied to secret-recovery rather than user enumeration.

This differs from a typical local/localhost-only mitigating factor: `auth_token`-gated endpoints are explicitly meant to be reachable from a network-adjacent `stacks-signer` and, in the `broadcast=1` case on `postblock_v3.rs`, from any remote peer who knows the token — the whole point of `auth_token` is to be a bearer secret usable over the network per the node's own documentation: [7](#0-6) 

### Impact Explanation
If an attacker recovers `auth_token` via timing analysis, they gain the same authorization as a legitimate `stacks-signer`, which allows:
- Unauthenticated/unauthorized write to state: POSTing to `/v3/block_proposal` (`RPCBlockProposalRequestHandler`) or to `/v2/blocks?broadcast=1` (`RPCPostBlockRequestHandler` in `postblock_v3.rs`), both of which are otherwise gated specifically because they can trigger consensus-relevant block validation/broadcast paths.
- Read-access to sensitive read endpoints (`fast-call-read`, `blocks/simulate`, `blocks/replay`, `transactions/simulate`) that are deliberately not exposed without the token, per their own comments ("If no authorization is set, then the ... endpoint is not enabled").

This satisfies the "unauthenticated/unauthorized write to state" Critical-tier impact bucket, since the auth token is the sole gate protecting a write/broadcast-capable endpoint.

### Likelihood Explanation
Exploitability requires many timing samples per byte position to overcome network jitter, and the underlying `String::eq`/slice comparison in optimized Rust builds may not always exhibit a large, cleanly measurable timing difference (compilers can vectorize short comparisons). This makes practical, remote exploitation harder than a classical unbounded timing oracle, but it remains a genuine, reachable, remotely-triggerable equality-check flaw that departs from best practice and directly matches the cited advisory's bug class (CWE-208) applied to bearer-token authentication rather than username enumeration.

### Recommendation
Replace all six `auth_header != password` (and the equivalent equality check) with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` trait or a hash-then-compare approach (compare `Sha256(auth_header)` against a precomputed `Sha256(password)` using a constant-time equality), consistently across `postblock_proposal.rs`, `postblock_v3.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, and `blockreplay.rs`. Consider centralizing this into a shared helper function to avoid the pattern being reintroduced in future endpoints.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<32+ char secret>"`.
2. Send repeated POST requests to `/v3/block_proposal` (or any of the six endpoints) with the `authorization` header set to guesses that share increasing correct prefixes of the real token (e.g., `"a", "aa", "aab", ...`) versus guesses with an incorrect first byte.
3. Statistically average round-trip time per guess (many repetitions to cancel jitter); guesses with a longer matching prefix should show a small but consistent time increase over guesses that mismatch immediately, since the `PartialEq`/`memcmp`-style comparison exits early on first mismatch.
4. Use this signal to binary/byte-search the token space, iterating until the full `auth_token` is reconstructed, then use it to POST an unauthorized block proposal or broadcast request.
