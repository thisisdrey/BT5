### Title
`StacksMessage::consensus_deserialize` never bounds relayer/payload reads to `preamble.payload_len`, allowing an undersized `payload_len` to smuggle bytes from the next queued message - (File: stackslib/src/net/codec.rs)

### Summary
`Preamble::consensus_deserialize` (codec.rs:158-211) only checks that `payload_len` is between 5 and `MAX_MESSAGE_LEN`, but never uses that value as a boundary when the payload is actually parsed. `StacksMessage::consensus_deserialize` (codec.rs:1346-1363) then reads the relayers vector and the `StacksMessageType` payload with `read_next_at_most`/`read_next` directly on the shared `fd`, with no `BoundReader` limiting the read to `payload_len` bytes.

### Finding Description
The claimed equality — "bytes `StacksMessageType::consensus_deserialize` actually reads for the payload == `preamble.payload_len`" — is never enforced anywhere in this code path: [1](#0-0) 

only bounds the *declared* value, and [2](#0-1) 

reads `relayers` via `read_next_at_most(fd, MAX_RELAYERS_LEN)` and `payload` via `read_next(fd)` directly against the raw stream, with no `BoundReader::new(fd, preamble.payload_len as u64)` wrapper and no post-hoc check comparing bytes actually consumed to `preamble.payload_len`. `BoundReader` is imported into this file (line 34) and used elsewhere, but not here.

Concretely, a remote peer can send a `Preamble` with `payload_len = 5` (the documented minimum: empty relayers vector + 1-byte `StacksMessageID`) but pick a message ID (e.g. `StackerDBHandshakeAccept`, `NakamotoBlocks`, `Handshake`, etc.) whose variant `consensus_deserialize` implementation (see the match arms around codec.rs:1280-1333) unconditionally reads more struct fields than the 0 remaining declared bytes. Since the read happens on the shared connection stream/cursor rather than a reader capped at `payload_len`, those extra reads pull bytes that belong to whatever the peer queued immediately afterward (i.e., the next message on the wire) into the current message's payload fields.

### Impact Explanation
If the connection-buffer/cursor used by the P2P read loop is not itself already truncated to exactly `payload_len` bytes before calling `StacksMessage::consensus_deserialize`, this causes:
- Stream desynchronization: bytes belonging to the next legitimate message are consumed as part of the current (undersized) message's payload, corrupting or dropping the subsequent message, and/or causing the parser to interpret attacker-chosen boundary bytes as arbitrary fields of a "well-formed" message (message smuggling).
- This is repeatable per-connection with a single crafted message and requires no privileged role — any peer that can open a P2P connection can attempt it.

This matches the Critical category ("network-wide propagation of forged data" / "request smuggling") *if* the caller does not already scope the reader to `payload_len` before dispatch.

### Likelihood Explanation
I was not able to verify, within the available tool budget, whether the P2P connection/read-loop code (outside codec.rs, e.g. in `net/connection.rs` or `net/p2p.rs`) wraps the accumulated socket buffer in a bounded reader/cursor sized to the declared `payload_len` before invoking `StacksMessage::consensus_deserialize`. If such an outer bound exists, the malformed payload parse would simply hit `UnexpectedEof`/`DeserializeError` cleanly against the truncated buffer and no over-read into the next message would occur — the gap described here would be latent but not exploitable. Codec.rs itself, in isolation, does not enforce the `payload_len` boundary during payload parsing, which is a genuine internal inconsistency between the documented invariant (comment at line 170) and the implementation.

### Recommendation
Wrap the relayers and payload reads in `StacksMessage::consensus_deserialize` with a `BoundReader` scoped to `preamble.payload_len`, and verify after parsing that the bound reader was fully consumed (or return an error if bytes remain/are exceeded), so that the number of bytes consumed for a message's body is always exactly `payload_len` regardless of the specific `StacksMessageType` variant's field layout.

### Proof of Concept
Because I could not confirm within this session whether an outer caller already bounds the reader to `payload_len` before parsing (I was unable to inspect `net/connection.rs`/`net/p2p.rs` read-loop code in the remaining tool budget), I cannot state with certainty that the over-read is reachable end-to-end from a raw socket. A concrete proof-of-concept test would need to:
1. Serialize a `Preamble` with `payload_len = 5`.
2. Append an empty relayers vector (4 zero bytes) + a `StacksMessageID` tag (e.g. `StackerDBHandshakeAccept = 1 byte`) whose variant requires reading a `HandshakeAcceptData` + `StackerDBHandshakeData` (far more than 0 remaining bytes).
3. Append a second, fully well-formed `StacksMessage` immediately after.
4. Feed the concatenated bytes to `StacksMessage::consensus_deserialize` via a `Cursor` over the *entire* buffer (unbounded, matching codec.rs's own reader usage) and assert whether it (a) errors cleanly consuming only 5+ bytes matching the first message boundary, or (b) succeeds/fails after consuming bytes belonging to message two, and whether the cursor position after the call equals `PREAMBLE_ENCODED_SIZE + payload_len`.

Given the inability to confirm the outer network-loop's buffering behavior, I present this as a finding scoped strictly to `codec.rs`'s internal lack of a `payload_len`-bounded reader — a genuine root-cause gap — while flagging that end-to-end exploitability depends on code outside this file that I could not fully verify in this session.

        let preamble: Preamble = read_next(fd)?;
        if preamble.payload_len > MAX_MESSAGE_LEN - PREAMBLE_ENCODED_SIZE {
            return Err(codec_error::DeserializeError(
                "Message would be too big".to_string(),
            ));
        }

        let relayers: Vec<RelayData> = read_next_at_most::<_, RelayData>(fd, MAX_RELAYERS_LEN)?;
        let payload: StacksMessageType = read_next(fd)?;

        let message = StacksMessage {
            preamble,
            relayers,
            payload,
        };
        Ok(message)
    }
