### Title
Missing `accrue` call in `socialize-debt` before writing down debt/liquidity index leads to incorrect emissions/interest distribution - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults)

### Summary
Every state-mutating vault entrypoint that changes `principal-scaled`, `total-borrowed`, or `assets` first calls `(try! (accrue))` to bring the borrow index (`index`) and liquidity index (`lindex`) up to date — except `socialize-debt`, which reads the stale `index`/`lindex` directly and uses them to compute the debt write-down and the resulting liquidity-index reduction.

### Finding Description
In the vault contracts, `deposit`, `redeem`, `system-borrow`, `system-repay`, and `flashloan` all begin with `(u (try! (accrue)))` before touching `assets`/`principal-scaled`/`total-borrowed`: [1](#0-0) [2](#0-1) [3](#0-2) 

`socialize-debt`, however, reads `index`, `lindex`, `principal-scaled`, `total-borrowed`, and `assets` directly via `var-get` with no preceding `accrue` call, then uses the current (potentially stale) `idx` to convert `scaled-amount` into `debt-reduction`, and uses the stale `lindex`/`old-total-assets` to compute a new liquidity index: [4](#0-3) 

This is the same class of bug as the Blend `execute_draw`/`execute_donate` finding: a function that mutates the same accounting state consumed by an index/emissions calculation, without first bringing that index up to the current block. Here, any interest that accrued between the vault's `last-update` and the `socialize-debt` call is never folded into `index`/`lindex` before the write-down math runs. The write-down is then computed against a debt/asset base that omits pending accrued interest, and — critically — the new `lindex` is derived from `old-total-assets` (via `total-assets`, which itself is a function of the stale `index`) rather than the true up-to-date total assets.

### Impact Explanation
Because `lindex` (the liquidity/share-value index for suppliers) is rewritten using a base that hasn't been accrued, the interest that depositors earned since the last accrual is silently dropped from the liquidity index computation at the moment of the write-down. That yield becomes permanently unrecoverable — it was never captured into `lindex` before the debt-socialization event overwrote it based on a smaller, stale `old-total-assets`. This lands in the in-scope "permanent freezing/loss of unclaimed yield" impact class for vault share math and interest accrual. It can also distort `principal-scaled`/`total-borrowed` bookkeeping relative to the true (accrued) debt, producing an accounting mismatch between vault `assets` and true obligations.

### Likelihood Explanation
`socialize-debt` is caller-gated by `check-caller-auth` (restricted to authorized contracts, i.e., the market contract), and is invoked as part of bad-debt socialization during liquidation flows described in the protocol's liquidation workflow, which is itself triggered by an ordinary, unprivileged `liquidate` call on `market.clar`. Because liquidations (and therefore debt socialization events) can occur at any time relative to the vault's last `accrue()` call, and Stacks blocks/time can pass between accruals, the staleness window is realistic and not attacker-exclusive — any liquidator invoking `liquidate` when the vault hasn't been accrued recently will trigger this gap. I was not able to fully trace the exact line-level call path inside `v0-4-market.clar`'s liquidation logic to `socialize-debt` (20 textual matches were found but not read in full), so the precise triggering conditions in the market contract remain unverified within this session.

### Recommendation
Add `(try! (accrue))` as the first operation in `socialize-debt`, mirroring `system-borrow`, `system-repay`, and `flashloan`, so that `index` and `lindex` (and therefore `debt-reduction`, `principal-reduction`, and `new-lindex`) are computed against fully up-to-date state before the debt write-down is applied.

### Proof of Concept
1. Vault has outstanding debt; time passes such that `next-index()` > current `index` (unaccrued interest exists), but no `deposit`/`redeem`/`borrow`/`repay` has triggered `accrue()` in the interim.
2. A liquidation event causes the market to call `socialize-debt` on the vault with some `scaled-amount`.
3. `socialize-debt` reads the stale `idx`/`lindex`/`assets` (see [5](#0-4) ) instead of accruing first.
4. `debt-reduction` and `new-lindex` are computed using the stale base; the pending unaccrued interest is never reflected in `lindex`, so it is dropped from future share-value calculations for suppliers — a permanent loss of that unclaimed yield.

```text
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
```
