### Title
Unverified attachment content hash lets a remote peer make a node store and serve arbitrary content under any hash via `/v2/attachments/{hash}` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the `AttachmentsDownloader` fetches an attachment from a peer to fulfil an `AttachmentRequest`, it never checks that the returned `Attachment.content` actually hashes to the requested `content_hash`. `extend_with_attachments` blindly accepts whatever bytes the peer returns, and `run()` unconditionally calls `insert_instantiated_attachment(&attachment)`, which stores the content keyed by its self-computed `attachment.hash()` with `was_instantiated = 1`, independent of whether any `AttachmentInstance` (i.e., any confirmed on-chain BNS/atlas event) ever referenced that hash. Since `RPCGetAttachmentRequestHandler::try_handle_request` serves any row in the `attachments` table with `was_instantiated = 1` found via `find_attachment`, this lets any peer the victim node happens to sync attachments from inject and permanently host attacker-chosen content at an arbitrary hash on the victim node's public `/v2/attachments/{hash}` endpoint.

### Finding Description
The invariant that should hold is: `served_bytes_for_hash == bytes_committed_by_confirmed_name_op`, i.e., a client requesting `/v2/attachments/{hash}` should only ever receive content whose hash was declared by a confirmed on-chain `AttachmentInstance.content_hash`.

The attack path:
1. The victim node has at least one legitimate, unresolved `AttachmentInstance` with `content_hash = X` (from a real BNS name-update event), so it queues an `AttachmentRequest{ content_hash: X, ... }` and issues `GET /v2/attachments/X` to a peer, per `AttachmentRequest::make_request_type` (`stackslib/src/net/atlas/download.rs:1104-1118`).
2. A malicious peer that is one of the node's `outbound_sync_peers` (attacker just needs to be an ordinary connected peer, not privileged) responds to this request with an `Attachment` whose `content` is arbitrary attacker-chosen bytes `b`, i.e. `hash(b) = Y != X`.
3. `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-553`) decodes the response via `decode_atlas_get_attachment()` and does `self.attachments.insert(response.attachment)` with **no check** that `response.attachment.hash() == request.content_hash`.
4. In `AttachmentsDownloader::run()` (`stackslib/src/net/atlas/download.rs:153-169`), for each attachment in `context.attachments.drain()`, the code computes `attachment.hash()` (== `Y`, the attacker-controlled value) and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` **unconditionally** — this call happens regardless of whether `find_all_attachment_instances(&Y)` returned anything.
5. `insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (Y, b, 1, now)`, so content `b` is now stored under hash `Y` with `was_instantiated = 1`, marked resolved, with **no corresponding `attachment_instances` row** referencing `Y`.
6. Any remote client can now `GET /v2/attachments/Y`. `RPCGetAttachmentRequestHandler::try_handle_request` (`stackslib/src/net/api/getattachment.rs:93-130`) calls `find_attachment(&Y)`, which is a raw lookup by primary key on `was_instantiated = 1` (`stackslib/src/net/atlas/db.rs:641-648`) with no join/check against `attachment_instances`, and returns 200 with the attacker's content `b`.

This breaks the content-addressing invariant BNS/Atlas relies on: a hash a client trusts as "committed by an on-chain name operation" can instead serve arbitrary attacker data that was never referenced by any `AttachmentInstance`.

### Impact Explanation
A remote, unprivileged peer can cause a victim node to permanently cache and publicly serve attacker-chosen bytes under an attacker-chosen hash via the node's own `/v2/attachments/{hash}` RPC endpoint. Any client (wallet, indexer, BNS resolver) that queries that node for a hash it believes is content-addressed (e.g., because it saw the hash referenced somewhere, or because a poisoning peer socially engineers a client into fetching a bogus hash) will be served forged content as if it were validated Atlas/BNS data. This matches "High: serving non-canonical state as canonical, attachment/BNS mismatch" since data with no corresponding confirmed `AttachmentInstance` is served indistinguishably from genuinely committed attachment content. It is fully repeatable per distinct hash and requires only that the node ever pull attachments from the attacker's peer connection during normal Atlas sync.

### Likelihood Explanation
Preconditions are minimal: the attacker just needs to be a normal peer that the victim's `AttachmentsDownloader` selects from `get_outbound_sync_peers()` when resolving any legitimate queued `AttachmentInstance` (this happens naturally as part of ordinary BNS/Atlas sync activity, e.g., whenever any name-update attachment needs fetching, not just attacker-controlled names). The attacker needs no secret, no special role, and can be an arbitrary remote node speaking the public P2P protocol. Cost is a single crafted HTTP response to an outbound `GET /v2/attachments/{hash}` request the victim itself initiates. This is directly and easily repeatable for any number of distinct hashes.

### Recommendation
In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), verify `response.attachment.hash() == request.content_hash` before accepting the attachment; treat a mismatch as a failed request (`report.bump_failed_requests()`), the same as a decode failure. Additionally, as defense in depth, `AttachmentsDownloader::run()` should only call `insert_instantiated_attachment` when `find_all_attachment_instances(&attachment.hash())` returns non-empty (i.e., only store content actually claimed by a queued/confirmed `AttachmentInstance`), preventing storage of unsolicited-hash content even if the hash check is bypassed elsewhere.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/download.rs` or `tests.rs`, mirroring `test_downloader_context_attachment_requests`):
1. Construct an `AttachmentsBatchStateContext` with one `AttachmentRequest { content_hash: X, ... }` for a legitimate pending `AttachmentInstance`.
2. Build a `BatchedRequestsResult` where the "succeeded" response for that request is a `GetAttachmentResponse { attachment: Attachment::new(b"malicious-content".to_vec()) }` whose hash `Y = Hash160::from_data(b"malicious-content")` is deliberately `!= X`.
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the attacker's `Attachment` (demonstrating no hash-match check).
4. Drive `AttachmentsDownloader::run()` (or directly call `atlasdb.insert_instantiated_attachment(&attachment)` as the `Done` branch does) and then call `atlasdb.find_attachment(&Y)`, asserting `Some(attachment)` is returned even though `atlasdb.find_all_attachment_instances(&Y)` is empty.
5. End-to-end: issue `StacksHttpRequest::new_getattachment(host, Y)` against the node's RPC handler `RPCGetAttachmentRequestHandler::try_handle_request` and assert a `200 OK` `GetAttachmentResponse` is returned, proving `/v2/attachments/{Y}` serves content with no backing `AttachmentInstance`.
