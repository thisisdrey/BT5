### Title
Out-of-bounds slice panic in `suffixarray.Index.Read` via unchecked serialized buffer-size field - (File: src/index/suffixarray/suffixarray.go)

### Summary
`index/suffixarray.Index.Read` deserializes an `Index` from an arbitrary `io.Reader`, and its own doc comments for the related `readSlice`/`readInt` machinery acknowledge the encoding "may be corrupt, or may be provided by an untrustworthy attacker" (this is the exact analog of stringstream's untrusted, attacker-controlled length field driving an unsafe buffer access). `readSlice` reads a "buffer size" varint from the stream and slices the shared read buffer with it (`buf[binary.MaxVarintLen64:size]`) without ever checking that `size` fits within `len(buf)` (`bufSize = 16<<10`), leading to a slice-bounds-out-of-range panic on corrupted/malicious input.

### Finding Description
Attacker-controlled bytes flow into the public API `(*Index).Read(r io.Reader)` [1](#0-0) , which allocates a fixed-size scratch buffer `buf := make([]byte, bufSize)` (`bufSize = 16<<10`) [2](#0-1)  and repeatedly calls `readSlice(r, buf, sa, uint64(n))` to decode the suffix-array indices [3](#0-2) .

Inside `readSlice`, the "index slice buffer size" is read directly from the stream as `size64` via `readInt`, and the only validation performed is that it fits in an `int` and is non-negative — there is no check that `size <= len(buf)`: [4](#0-3) 

The subsequent expression `buf[binary.MaxVarintLen64:size]` is evaluated against the fixed-capacity `buf` (`cap(buf) == bufSize == 16384`). If the attacker sets the encoded size field larger than `bufSize`, this slicing operation panics with "slice bounds out of range" before `io.ReadFull` is even invoked — this is a genuine out-of-bounds slice access reachable purely from attacker-supplied stream bytes, analogous to the uninitialized/out-of-bounds buffer read in the `stringstream` advisory where an attacker-controlled length value drives an unsafe memory access.

Note this is a distinct, still-unguarded case from the already-fixed go.dev/issue/53352 (which only guards against too many decoded *indices*, i.e. `n >= len`/`x >= maxIndex` inside the decode loop) [5](#0-4) ; the size-of-encoded-chunk field itself is never bounded against `bufSize`.

### Impact Explanation
Any consumer that deserializes a suffix-array index from an untrusted source (e.g., a persisted/downloaded search index, or an index transmitted over a network/pipe) can be crashed by supplying a corrupted stream: this is a reachable, deterministic runtime panic (denial of service) triggered purely by parsing attacker-supplied bytes via the public `Index.Read` API, which is Go's documented allowance for "plausible malicious-input parser panic." This would be a Go **PUBLIC** track issue (a stdlib parsing panic on malformed/untrusted input), not a memory-disclosure vulnerability like the original stringstream OOB read, but it shares the same root-cause pattern: an attacker-controlled length field used to slice a buffer without a bounds check against the buffer's actual capacity.

### Likelihood Explanation
The victim workflow is straightforward: any program that calls `(*suffixarray.Index).Read` on data it did not fully trust (index caches, cross-process/cross-host transfer of prebuilt indices, etc.) is affected. The attacker only needs to supply/tamper with the serialized index bytes — no privileges, credentials, or special access are required, matching the "ordinary/unauthenticated input consumed by a normal victim workflow" premise.

### Recommendation
In `readSlice` (`src/index/suffixarray/suffixarray.go`), validate `size` against `len(buf)` (in addition to the existing `int64(int(size64)) != size64 || int(size64) < 0` check) before slicing, e.g. reject with `errCorrupted` if `size < binary.MaxVarintLen64 || size > len(buf)`.

### Proof of Concept
```go
package suffixarray

import (
	"bytes"
	"encoding/binary"
	"testing"
)

// TestReadSliceOOBSizePanic demonstrates that a corrupted "index slice buffer
// size" field larger than bufSize (16<<10) causes an out-of-bounds slice
// panic in readSlice, reachable via the public Index.Read API on
// attacker-controlled input.
func TestReadSliceOOBSizePanic(t *testing.T) {
	data := []byte("x")
	index := New(data)

	var buf bytes.Buffer
	if err := index.Write(&buf); err != nil {
		t.Fatal(err)
	}
	encoding := buf.Bytes()
	n := len(data)

	// Patch the 10-byte "index slice buffer size" field (located right after
	// the n data bytes) with a value larger than bufSize (16384).
	var tmp [10]byte
	binary.PutVarint(tmp[:], 1<<20) // 1MB > bufSize
	copy(encoding[10+n:10+n+10], tmp[:])

	defer func() {
		if r := recover(); r == nil {
			t.Fatal("expected an out-of-bounds slice panic, got none")
		} else {
			t.Logf("got expected panic: %v", r)
		}
	}()

	var y Index
	_ = y.Read(bytes.NewReader(encoding)) // panics: slice bounds out of range
}
```
Expected: the test recovers a panic such as `slice bounds out of range [:1048576] with capacity 16384`, confirming the unchecked, attacker-controlled length field drives an out-of-bounds slice operation in `readSlice`.

func readSlice(r io.Reader, buf []byte, data ints, maxIndex uint64) (n int, err error) {
	// read buffer size
