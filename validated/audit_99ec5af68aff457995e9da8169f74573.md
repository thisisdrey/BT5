### Title
Per-IP connection rate limiter is bypassable via parallel handshake burst (TOCTOU between `is_allowed` and `register_connection`) - (File: streamer/src/nonblocking/quic.rs)

### Summary
The QUIC accept loop in `run_server` checks `rate_limiter.is_allowed(&ip)` before the costly TLS handshake, but only calls `rate_limiter.register_connection(&ip)` after the handshake completes inside `setup_connection`. Because `is_allowed` is a non-mutating read (confirmed by its own doc comment and the existing unit test "just checking should not mutate state"), an unstaked attacker can open many parallel handshakes from the same source IP within one accept-loop iteration; all of them observe `is_allowed == true` (since none has registered yet) and proceed to perform the full costly handshake before the per-IP limiter has a chance to reject any of them.

### Finding Description
In `run_server`'s accept loop (`streamer/src/nonblocking/quic.rs`), for each incoming connection the per-IP check is performed at: [1](#0-0) 

This call only reads current token count via `ConnectionRateLimiter::is_allowed`: [2](#0-1) 

If it passes, the loop accepts the connection and spawns `setup_connection` as an async task: [3](#0-2) 

`setup_connection` then performs the actual expensive work — awaiting the QUIC/TLS handshake with a timeout — and only afterward calls `register_connection`, which is the only method that mutates the per-IP token bucket: [4](#0-3) [5](#0-4) 

Because `is_allowed` never consumes a token, and the accept loop dispatches each incoming connection to its own concurrently running `setup_connection` task, an attacker opening K parallel connection attempts from one IP within a single `WAIT_FOR_CONNECTION_TIMEOUT` window will have all K pass the `is_allowed` check (each observes the unregistered/full bucket state), and all K will proceed to run the handshake (`timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)`) concurrently. Only after each handshake completes does `register_connection` get called, and only then does the per-IP limiter start rejecting connections — but by that point the CPU/crypto cost of the handshake has already been paid for all K attempts, not just the ones actually allowed by the configured per-IP rate.

The only gates that occur *before* the handshake are: the global `overall_connection_rate_limiter.current_tokens() == 0` check (a cluster-wide, not per-IP, limiter) and `ClientConnectionTracker::new(...)` bounding total concurrent connections against `qos.max_concurrent_connections()` (again a global cap, not IP-specific). Neither of these prevents a single IP from consuming a disproportionate share of handshake capacity up to the global caps, entirely bypassing the intended per-IP throttle during the burst window.

### Impact Explanation
This allows an unstaked/unauthenticated remote attacker to force the validator to perform full QUIC/TLS handshake CPU and cryptographic work for a burst of connections from a single IP far beyond `max_connections_per_ipaddr_per_min`, up to the global connection-rate and max-concurrent-connection ceilings. This degrades TPU responsiveness for legitimate senders by consuming handshake-processing threads/CPU on connections that should have been rejected pre-handshake by per-IP QoS, i.e., a QoS/rate-limit evasion enabling CPU-exhaustion-style resource starvation of TPU ingress.

### Likelihood Explanation
The precondition is only that the attacker can open multiple simultaneous QUIC connection attempts from one IP (trivial for any remote client — no stake, keys, or special access required) within the `WAIT_FOR_CONNECTION_TIMEOUT` (1s, `streamer/src/nonblocking/quic.rs:283`) accept-loop window, before any of those connections complete their handshake and register. This is straightforward, repeatable, and does not depend on validator/operator configuration to fix (the gap is structural in the check-then-act flow); it is bounded in practice by the global `overall_connection_rate_limiter` and global max-concurrent-connections cap, but per-IP limiting is meant to specifically bound single-source abuse and this bug lets a single IP consume up to those global caps instead of its fair per-IP share.

### Recommendation
Reserve/consume a per-IP token optimistically at accept time (before spawning the handshake task) rather than only checking availability, and release/refund it if the handshake fails or times out, or restructure so `is_allowed`+reservation is atomic (e.g., have the accept loop call `register_connection` before spawning `setup_connection`, and have `setup_connection` release the slot on handshake failure/timeout). This closes the window where multiple parallel accepts can all observe an unconsumed bucket.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/quic.rs` or a new test module):
1. Set up a `ConnectionRateLimiter::new(limit_per_minute, max_burst, num_shards)` with a small `max_burst` (e.g., 2).
2. Spawn `K` (e.g., 20) concurrent tasks that each call `rate_limiter.is_allowed(&ip)` at the same instant, before any of them calls `register_connection(&ip)`.
3. Assert that far more than `max_burst` tasks observe `is_allowed == true` (demonstrating the TOCTOU window), e.g. assert `count_where(is_allowed==true) > max_burst`.
4. Extend to a full-stack integration test using the actual QUIC server (`spawn_server`/`run_server`): from a single client IP, fire `K` parallel raw QUIC connection attempts within `WAIT_FOR_CONNECTION_TIMEOUT`, and measure via `StreamerStats.total_incoming_connection_attempts` / `outstanding_incoming_connection_attempts` that the number of handshakes actually attempted (before `connection_rate_limited_per_ipaddr` is incremented in `setup_connection`) exceeds `max_connections_per_ipaddr_per_min`, confirming handshake CPU work is not bounded to the configured per-IP rate.

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
