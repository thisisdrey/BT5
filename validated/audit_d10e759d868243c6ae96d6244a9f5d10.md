### Title
Out-of-bounds slice panic in the reftable ref-block parser causes an unrecovered crash of any RPC that reads references from a reftable-backend repository - (File: internal/git/reftable/reftable.go)

### Summary
Gitaly ships a hand-written Go parser for the reftable ref-storage format (`internal/git/reftable/reftable.go`). When decoding a reference block, `Table.getRefsFromBlock` reads variable-length integers (`prefixLength`, `suffixLength`, symref `size`) from the table bytes and immediately uses them to slice the in-memory buffer (`src[idx:idx+suffixLength]`, `prefix[:prefixLength]`, `src[idx:idx+size]`) without ever validating that the decoded length actually fits inside the remaining buffer. This mirrors the Tally-VM `call_result_write` bug class: an attacker-controlled length value drives a slice/array index operation that is never bounds-checked before use, producing a Go runtime panic ("slice bounds out of range") instead of a handled error.

### Finding Description
`Table.getVarInt` (reftable.go:204-219) only checks that the *cursor* used while decoding the multi-byte varint does not exceed `blockEnd`; it does not check the *decoded value* itself: [1](#0-0) 

That unchecked value is then used directly for slicing in `getRefsFromBlock`: [2](#0-1) 
and for the symref case: [3](#0-2) 

None of these lines verify `idx+suffixLength <= len(src)`, `prefixLength <= len(prefix)`, or `idx+size <= len(src)` before slicing. A crafted reftable block whose `suffixLength`/`prefixLength`/symref `size` fields decode to a value larger than the remaining bytes in the loaded buffer will cause Go to panic with an out-of-range slice/string index, exactly the same failure mode as the WASM `call_result_write` bug (`target.index(index as u64)` / `call_value[index as usize]` panicking on an unchecked attacker-supplied length).

`GetReferences()` (which triggers this parsing path) is invoked from production RPC code paths, not just tests, e.g. `internal/backup/repository.go` and `internal/gitaly/service/repository/replicate.go`: [4](#0-3) 

### Impact Explanation
Gitaly wraps RPC handlers with a panic-recovery interceptor (`panichandler.UnaryPanicHandler` / `StreamPanicHandler`), so a panic in this code path is caught and converted into a `codes.Internal` gRPC error rather than crashing the whole `gitaly-server` process: [5](#0-4) 

This means the blast radius is materially smaller than the SEDA Tally-VM case (which crashed every validator process and halted the chain). However, because the malformed data lives on disk in the repository's `reftable/` directory, **every** subsequent RPC that needs to enumerate references for that repository (e.g. `ListRefs`, `Backup`, `ReplicateRepository`, internal WAL/transaction-manager reference reads) will hit the same unchecked slice operation and panic again. This is a persistent, repeatable Denial-of-Service of the reference-reading code path for the affected repository, satisfying the "DoS of a handler" acceptance criterion, even though it does not bring down the entire Gitaly node.

### Likelihood Explanation
Exploitability depends on an attacker's ability to get a crafted byte sequence into a repository's `reftable/*.ref` file. Reftable files are normally produced by Gitaly's own reftable-backend write path (going through the transaction manager and git's `pack-refs`/ref transaction machinery), so a plain `git push` alone does not let a client control the raw table bytes. I was not able to confirm within the available codebase context a concrete unprivileged path (ordinary push/fetch/fork/import) that lets a client write arbitrary bytes directly into `reftable/*.ref` files bypassing Git's own writer; the clearest callers of `GetReferences()` I found (`internal/backup/repository.go`, `internal/gitaly/service/repository/replicate.go`) consume reftable files that are expected to have been produced by trusted Git/Gitaly write paths. Because of this uncertainty, likelihood should be treated as **unconfirmed/moderate** rather than proven — the root-cause bug (missing bounds validation on decoded varint lengths before slicing) is concretely demonstrated, but the concrete unprivileged delivery vector into gitaly's own repository storage was not conclusively located in this pass.

### Recommendation
Add explicit bounds checks after decoding `prefixLength`, `suffixLength`, and the symref `size` in `Table.getVarInt`/`Table.getRefsFromBlock`, verifying that `idx+length <= len(src)` (and `prefixLength <= len(prefix)`) before performing any slice operation, returning a descriptive parse error instead of allowing the runtime to panic. This mirrors the recommended Tally-VM fix of validating attacker-controlled lengths against the actual buffer size before indexing/copying.

### Proof of Concept
Conceptual repro (not executed, derived from code inspection):
1. Obtain or construct a `.ref` reftable file whose ref-block contains a varint-encoded `suffix_length` (or `prefix_length`, or symref `size`) that decodes to a value larger than the number of bytes remaining in the loaded block/file buffer.
2. Place this file (with a correctly matching header/footer checksum, or via a path that skips checksum validation) into a repository's `reftable/` directory as referenced by `tables.list`.
3. Call `reftable.ParseTable(path)` followed by `table.GetReferences()` (reached in production via RPCs such as `Backup`/`ReplicateRepository`, or internal reference reads).
4. `getRefsFromBlock` executes `src[idx:idx+suffixLength]` (or the prefix/symref equivalent) with `idx+suffixLength > len(src)`, causing a Go runtime panic: `slice bounds out of range [:N] with capacity M`. The panic is caught by `panichandler`, turning the RPC into an `Internal` error, but the underlying malformed table file continues to trigger the same panic on every future ref-read of that repository.

func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

func (t *Table) GetReferences() ([]git.Reference, error) {
	headerOffset := uint(t.footer.Version.HeaderSize())
	offset := uint(0)
	var allRefs []git.Reference

	if _, err := t.src.Seek(0, io.SeekStart); err != nil {
		return nil, fmt.Errorf("seek start: %w", err)
	}

	src, err := io.ReadAll(t.src)
	if err != nil {
		return nil, fmt.Errorf("read all: %w", err)
	}

	for offset < t.footerOffset {
		blockStart, blockEnd := t.getBlockRange(offset, t.blockSize)
		if blockStart == 0 && blockEnd == 0 {
			break
		}

		// If we run out of ref blocks, we can stop the iteration.
		if src[blockStart+headerOffset] != 'r' {
			return allRefs, nil
		}

		references, err := t.parseRefBlock(src, headerOffset, blockStart, blockEnd)
		if err != nil {
			return nil, fmt.Errorf("parsing block: %w", err)
		}

		if len(references) == 0 {
			break
		}

		allRefs = append(allRefs, references...)

		offset = blockEnd
	}

	return allRefs, nil
}

// UnaryPanicHandler creates a new unary server interceptor that handles panics.
func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}

// StreamPanicHandler creates a new stream server interceptor that handles panics.
func StreamPanicHandler(logger log.Logger) grpc.StreamServerInterceptor {
	return func(srv interface{}, stream grpc.ServerStream, info *grpc.StreamServerInfo, handler grpc.StreamHandler) (err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(srv, stream)
	}
}
