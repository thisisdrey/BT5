Audit Report

## Title
Reentrancy-protection bypass for value-transferring EVM `CALL`/`transfer`/`send` in pallet-revive — ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

## Summary
In `run_call` (`substrate/frame/revive/src/vm/evm/instructions/contract.rs`), the match statement that selects `ReentrancyProtection::AllowNext` vs `ReentrancyProtection::AllowReentry` keys its decision on `(value.is_zero(), gas_limit == CALL_STIPEND)` with `value.is_zero() == false` unconditionally short-circuiting to `AllowReentry`. This means the standard Solidity `.transfer(amount)`/`.send(amount)` idiom (nonzero value, solc-emitted `gas_limit = 0` with the EVM's implicit 2300 stipend) never receives the `AllowNext` guard, while only the degenerate zero-value `transfer(0)`/`send(0)` case (which carries no real risk since no value moves) gets it. [1](#0-0) 

## Finding Description
The reentrancy dispatch logic is exactly as described in the claim: [1](#0-0)  The first match arm `(false, _) => (true, ReentrancyProtection::AllowReentry)` fires for any nonzero-value call regardless of the actual `gas_limit`, so a `.transfer(amount)`/`.send(amount)` call (which solc compiles to `value > 0`, `gas_limit = 0`, relying on the EVM's implicit 2300 stipend) falls into this branch and gets `AllowReentry` — not the `AllowNext` protection that the pallet's own documentation says is required to compensate for the fact that "due to gas scale differences that guarantee does not automatically hold in revive." [2](#0-1) 

`add_stipend = true` is still set for the `(false, _)` branch, so `CallResources::from_ethereum_gas` still grants the converted stipend weight budget (confirmed in `substrate/frame/revive/src/metering/math.rs`'s `new_nested_meter` functions, which treat `add_stipend` uniformly regardless of the accompanying `ReentrancyProtection` value). This means the *only* thing distinguishing these two code paths for `value>0` transfers versus the `AllowNext` path is the explicit re-entrancy guard itself — the resource budget is identical in both. The pallet's own comment states that whether the stipend-equivalent weight is sufficient for a reentrant call is not a guarantee that can be relied upon at revive's gas scale, which is precisely why `AllowNext` was introduced as an explicit backstop. By excluding the common nonzero-value/implicit-stipend case from that backstop, the code leaves exactly the risk scenario the comment warns about unmitigated for the most common ETH-payout pattern in Solidity.

I was unable to fully trace, within the available tool budget, the concrete runtime enforcement mechanism of `ReentrancyProtection::AllowNext` vs `AllowReentry` inside `exec.rs` (i.e., how the reentrancy flag is propagated through the call stack and checked against caller/callee frame identity) to confirm the precise mechanics of how `AllowNext` blocks a second-level reentrant call. However, the code path itself — the match statement's structure, its citation, and the enum documentation — matches the claim's description exactly and is verifiably present in the current codebase.

## Impact Explanation
If the converted stipend weight budget is sufficient for a callee to perform a further external call (which the pallet's own documentation flags as a real possibility due to gas-scale differences between Ethereum and revive), an attacker-controlled contract receiving a `.transfer()`/`.send()` payout can reenter the paying contract before its state is finalized. This is a classic reentrancy primitive that can enable duplicate withdrawal/double-payout against any deployed EVM-compatible contract using the `.transfer()`/`.send()` idiom — a duplicate-settlement/unbacked-payout impact directly in scope for the Polkadot SDK gate ("theft or unbacked mint or unlock, duplicate settlement or payout").

## Likelihood Explanation
The path is reachable by any unprivileged external account calling any deployed contract that performs `.transfer()`/`.send()` to an attacker-supplied address, which is one of the most common ETH-payout patterns in Solidity. No privileged access, governance action, or compromised infrastructure is required — only a normal contract call with an attacker-controlled recipient whose `receive()`/`fallback()` attempts a reentrant call.

## Recommendation
Change the match logic so that the reentrancy-guard decision is keyed off whether the call is a stipend-style transfer (`gas_limit == 0` or `gas_limit == CALL_STIPEND`), independent of whether `value` is zero, so that `.transfer(amount)`/`.send(amount)` calls with `amount > 0` receive `ReentrancyProtection::AllowNext` just like the `value == 0` case currently does.

## Proof of Concept
1. Deploy a victim contract `V` with a payout function using `payable(msg.sender).transfer(amount)` following checks-effects-interactions.
2. Deploy attacker contract `A` whose `receive()` reenters `V`'s payout function.
3. Call `V`'s payout function with `A` as recipient; in `run_call`, `value.is_zero() == false` selects `(true, ReentrancyProtection::AllowReentry)` regardless of `gas_limit` being the solc-emitted `0`. [1](#0-0) 
4. If the granted stipend-equivalent weight is sufficient for `A.receive()` to perform another call into `V`, `A` reenters and drains funds via duplicate withdrawal — a Rust integration test analogous to `testTransferReentrancy` in `substrate/frame/revive/fixtures/contracts/Stipends.sol` but targeting a real nonzero-value `.transfer()` call instead of the zero-value fixture would reproduce this.
