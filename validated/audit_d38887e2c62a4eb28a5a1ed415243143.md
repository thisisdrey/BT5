### Title
Same-block AddKey nonce reseed can drop below an already-used nonce, re-opening a stale transaction for replay - (File: runtime/runtime/src/access_keys.rs)

### Finding Description
`initial_nonce_value` sets a recreated key's nonce floor to `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` at the height the `AddKeyAction` executes [1](#0-0) , and `add_regular_key` writes that value as the new `access_key.nonce` [2](#0-1) . This scheme (from near/nearcore#3779) is only safe if the recreation height is strictly greater than the height at which the pre-deletion instance of the key last advanced its nonce, because `verify_nonce`'s upper bound for any height `H` is `H * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [3](#0-2) .

If a signer, using key `K`, submits a transaction with `nonce = H*M - 1` (the maximum nonce admissible at height `H`) and it is applied, and — in a *later* chunk that still executes actions on the account (the delete/re-add can be signed with a different full-access key `K2` on the same account, so it does not need to compete with `K`'s own nonce for ordering) — `K` is deleted and re-added via `DeleteKeyAction`/`AddKeyAction`, the new floor for `K` becomes `(H-1)*M`, which is *lower* than the nonce (`H*M-1`) already consumed by the pre-deletion instance of `K`. Because NEAR's only anti-replay mechanism at the deterministic state-transition level is the per-access-key nonce check plus `block_hash` freshness (`transaction_validity_period`, 86400 blocks on mainnet) [4](#0-3)  — there is no independent "this exact transaction hash was already applied" check inside `Runtime::verify_and_charge_transaction`/`verify_nonce` — the original signed bytes of the earlier high-nonce transaction remain admissible: `tx_nonce (H*M-1) > current_nonce ((H-1)*M)` and `tx_nonce < upper_bound` for any subsequent height. If that exact transaction is resubmitted to the network afterward, an honest chunk producer whose local mempool does not still hold/flag it as "already in the chain" (a node-level courtesy, not a runtime-enforced rule) can include it again, and the runtime will accept and re-execute it.

### Impact Explanation
Re-execution of an already-applied transaction is a replay/double-spend: if the original transaction moved funds (`Transfer`, `FunctionCall` with a deposit, etc.), its effects (balance changes, promises) occur a second time, causing token duplication or double debit — falling under "double-spend/replay" and "token inflation or loss" in the bounty categories.

### Likelihood Explanation
Exploitability depends on: (1) the signer being able to push its access key's nonce near the per-height ceiling and then get an ordinary DeleteKey/AddKey cycle for the same public key applied afterward — both are actions an unprivileged account owner can perform on their own account with their own keys; (2) the recreated key floor `(H-1)*M` being reached before the stale nonce `H*M-1` is naturally passed by legitimate traffic; (3) the original signed transaction bytes surviving and being resubmitted within `transaction_validity_period`, and reliance on an honest chunk producer's mempool not filtering already-seen-on-chain hashes reliably. This last point is a node/mempool behavior, not a hard consensus guarantee enforced by the runtime state-transition function itself, so it cannot be assumed to always block replay. However, exploitation requires deliberately reproducing this exact edge case (delta only realizable if `initial_nonce_value` uses the *current* apply height rather than tracking the maximum previously used nonce for that key), and the underlying design gap (documented as intentional in earlier issue #3779) is the same root cause already covered by prior related findings (Q1/Q6); it is not a new distinct code path introduced by chunk-vs-per-tx granularity.

### Recommendation
Do not derive a recreated key's nonce floor purely from the current block height. Either (a) track and persist the highest nonce ever used by a given public key on an account even across deletion (so recreation can never regress below it), or (b) require `initial_nonce_value` to use `max(current stored/removed nonce, (block_height-1)*M)`, ensuring the new floor is always ≥ any nonce that could have been legitimately consumed up to the current height, closing the same-block/same-chunk gap.

### Proof of Concept
Runtime integration test (apply.rs-style):
1. Create account with full-access key `K` and a second full-access key `K2`, at height `H`.
2. Apply a chunk at height `H` with: (a) a transaction signed by `K` with `nonce = H*M - 1` performing a `Transfer`; (b) a transaction signed by `K2` containing `DeleteKeyAction { public_key: K }`; (c) a transaction signed by `K2` containing `AddKeyAction { public_key: K, access_key: FullAccess }`.
3. Assert all three succeed and `K`'s stored nonce is `(H-1)*M`.
4. Re-submit the *original signed bytes* from step 2(a) in a subsequent chunk (height `H+1`, still within `block_hash` validity).
5. Assert `verify_nonce`/`verify_and_charge_transaction` incorrectly accepts it (`tx_nonce > current_nonce` and `< upper_bound`), and the `Transfer` action executes a second time, doubling the balance change — demonstrating the replay.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```
