## Title
Single key holder can inflate approval weight past a multisig threshold by resubmitting a malleable ECDSA signature to the `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract computes a permission's approval weight by iterating over a caller-supplied signature array and summing the weight of each recovered signer address. Its de-duplication logic only skips an entry when the *exact byte-for-byte* signature is repeated for an address it has already seen; if the same address is recovered again from a *different* signature (e.g. an ECDSA-malleated variant with `s' = n - s`, which still recovers to the same address), the loop does not skip it and instead adds that key's weight to the total a second time. This lets a single private-key holder satisfy a multi-signature threshold alone, mirroring the reported `QVBaseStrategy.reviewRecipients()` flaw where one privileged actor could cast more than one "vote" toward a threshold meant to require distinct approvers.

### Finding Description
`ValidateMultiSign.execute()` iterates the signatures supplied in the calldata: [1](#0-0) 

For each signature, it recovers the signer address via `recoverAddrBySign` and merges the address with the raw signature bytes into `sign`. The de-duplication check is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
If `recoveredAddr` was already seen but the *merged signature bytes* differ from any prior entry (which happens whenever the second signature is a different-but-valid signature for the same hash/key, such as the classic ECDSA `s`/`n-s` malleability), the code falls through instead of skipping, and adds that same key's weight to `totalWeight` again.

This contrasts with the correct implementation used for real transaction execution, `TransactionCapsule.checkWeight`, which de-duplicates strictly by the *recovered address* (independent of the raw signature bytes) and throws a `PermissionException` ("has signed twice!") if the same address appears more than once: [2](#0-1) 

The precompile's weaker, signature-byte-based de-duplication is the root cause: it conflates "same signature" with "same signer," when only the latter should determine whether a vote/weight has already been counted.

### Impact Explanation
Any smart contract can invoke the `ValidateMultiSign` precompile (reachable from ordinary `TriggerSmartContract` calls, i.e. a fully unprivileged transaction). If a contract relies on this precompile to gate privileged operations (e.g., releasing funds, executing an on-chain multisig action) behind an account `Permission` with `threshold > 1` and multiple keys, a single key holder controlling only one of the keys (with insufficient weight alone) can craft two different valid signatures over the same hash from that one key (using ECDSA signature malleability) and have the precompile report the permission as satisfied (`dataOne()`), even though no second distinct approver actually signed. This is a broken-access-control / unauthorized-operation primitive: it can cause execution of actions that should require multiple independent approvers, e.g. unauthorized fund transfer/authorization in any contract that gates on `ValidateMultiSign`.

### Likelihood Explanation
The bug is deterministically reachable by any unprivileged contract deployer/caller: it requires only crafting the calldata for the `ValidateMultiSign` precompile with two differently-encoded (malleated) signatures from the same key. No special SR/witness/committee privilege or race condition is needed, and the flawed logic is unconditionally present in the precompile's execute path.

### Recommendation
Change the de-duplication logic in `ValidateMultiSign.execute()` to key strictly on `recoveredAddr` (as `TransactionCapsule.checkWeight` already does), rejecting/skipping any subsequent signature that recovers to an address already counted, regardless of whether the raw signature bytes differ:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  continue; // address already counted, ignore duplicate/malleated signature
}
```
Additionally, consider enforcing canonical (low-`s`) signatures at signature-format validation time to eliminate ECDSA malleability as an attack vector across all signature-recovery code paths.

### Proof of Concept
1. Create an account with an `Active` `Permission` of `threshold = 2` containing two keys, `key1` (weight 1) and `key2` (weight 1) — attacker controls only `key1`.
2. Attacker computes `hash` per the precompile's ABI (`address || permissionId || data`, SHA-256'd).
3. Attacker produces `sig1 = key1.sign(hash)` and then derives a malleated signature `sig1' = (r, n-s, recovered v flipped)` — a distinct byte sequence that still recovers to `key1`'s address (standard secp256k1 malleability).
4. Attacker calls the `ValidateMultiSign` precompile with `signatures = [sig1, sig1']`.
5. In `execute()`, `sig1` is processed normally (`totalWeight = 1`). For `sig1'`, `recoveredAddr` matches the already-seen `key1` address, but `sign` (merged bytes) differs from the previously stored `sign1`, so the `continue` is skipped, `MUtil.checkCPUTime()` is called, and `weight` (1) is added again → `totalWeight = 2`.
6. `totalWeight (2) >= permission.getThreshold() (2)` is now true, and the precompile returns `dataOne()` (success), despite only one real signer having participated. [3](#0-2)

    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
