Audit Report

## Title
Unrestricted `vested_transfer` target lets any account permanently block `Purchase::payout` for any DOT-purchase participant - (File: `polkadot/runtime/common/src/purchase/mod.rs`)

## Summary
`Purchase::payout()` and `Purchase::create_account()` reject any account for which `T::VestingSchedule::vesting_balance(&who)` returns `Some(_)`, but `vesting_balance` returns `Some(_)` whenever *any* entry exists in `pallet_vesting`'s `Vesting` storage map for that account, even if the schedule is fully unlocked (balance `0`). [1](#0-0) [2](#0-1)  Because `pallet_vesting::vested_transfer` is a fully public extrinsic with no relationship requirement between `transactor` and `target`, and stale/fully-vested schedules are only removed by an explicit `vest`/`vest_other` call, an unprivileged attacker can plant (and repeatedly replant) a dust vesting schedule on a victim's address to permanently block their `Purchase` payout. [3](#0-2) [4](#0-3) 

## Finding Description
`payout()` checks `T::VestingSchedule::vesting_balance(&who).is_none()` before transferring `free_balance`/`locked_balance` out of `PaymentAccount`. [5](#0-4)  `create_account()` has the identical guard. [6](#0-5) 

`vesting_balance` in `pallet_vesting` returns `Some(_)` as soon as a `Vesting` entry exists for the account, computing the locked amount from the schedule but still wrapping it in `Some` even when that locked amount is `0`: [7](#0-6) 

Vesting entries are removed from storage only by `write_vesting`, called from `do_vest`/`do_vest_other`, which is invoked explicitly via the `vest`/`vest_other` extrinsics — never automatically on schedule completion. [4](#0-3) 

`vested_transfer` can be called by any signed account (`transactor`) against any `target`, with no consent check on the target: [3](#0-2) 

Combining these: an attacker calls `vested_transfer(origin=attacker, target=victim, schedule)` with a schedule whose `starting_block` is already in the past, so the schedule is instantly (or almost instantly) fully unlocked. This creates a `Vesting` entry for `victim`, moving funds from the attacker to the victim (the attacker doesn't lose net value — the transferred amount is refunded/unlocked). The entry persists in storage until someone calls `vest`/`vest_other(victim)`. In the meantime, `Purchase::payout(victim)` and `Purchase::create_account(victim)` both revert with `Error::VestingScheduleExists`, confirmed by the existing test `payout_handles_basic_errors`, which demonstrates exactly this guard triggering off mere presence of a vesting schedule. [5](#0-4) 

The existing check assumes "vesting schedule exists" implies "funds are locked," but the code confirms this assumption is false: `vesting_balance` can return `Some(0)`.

## Impact Explanation
This matches the "permanent user-fund lock" impact category: a legitimate purchaser's already-allocated `free_balance`/`locked_balance` in `Accounts::<T>` becomes unpayable as long as an attacker maintains a non-empty `Vesting` entry on the victim's address. Since `vested_transfer` remains permissionless forever, the victim (or any third party) clearing the schedule via `vest_other` does not provide lasting relief — the attacker can immediately re-poison the account with another `vested_transfer` before the victim's `payout` transaction is included, since both are ordinary signed extrinsics competing for block inclusion.

## Likelihood Explanation
High. No governance, validator, or privileged role is required. The attacker only needs the target's address (visible via `Accounts` storage/events) and the pallet's `MinVestedTransfer` amount, which is not lost (it unlocks to the victim immediately since the schedule can be constructed to already be fully vested). The attack is repeatable indefinitely and requires no timing/front-running of a specific victim transaction — it can be executed proactively at any time.

## Recommendation
- Treat `vesting_balance(&who) == Some(0)` equivalently to `None` in the `purchase` pallet's checks (i.e., check that the *locked amount* is zero rather than that the `Option` is `None`).
- Alternatively, have `payout()`/`create_account()` sweep fully-vested schedules for `who` (invoke the equivalent of `do_vest`) before evaluating `VestingScheduleExists`.
- More generally, any pallet gating logic on "no vesting schedule exists" must recognize that `pallet_vesting::vested_transfer` is a fully public, targetable primitive, and a nonzero entry in `Vesting` does not imply actual balance lock.

## Proof of Concept
1. `ValidityOrigin` calls `create_account`, `update_validity_status(ValidHigh)`, and `update_balance(who=victim, free=X, locked=Y, vat)` to set up `victim`'s purchase entry.
2. Attacker (unrelated, unprivileged account) calls:
   ```
   Vesting::vested_transfer(
       RuntimeOrigin::signed(attacker),
       victim,
       VestingInfo::new(MinVestedTransfer, MinVestedTransfer, current_block.saturating_sub(1)),
   )
   ```
   This creates a `Vesting` entry for `victim` that is already fully unlocked but remains in storage per `write_vesting`.
3. `PaymentAccount` calls `Purchase::payout(RuntimeOrigin::signed(payment_account), victim)`. This reverts with `Error::<T>::VestingScheduleExists`, as confirmed by the existing unit test pattern in `payout_handles_basic_errors` (`polkadot/runtime/common/src/purchase/tests.rs` lines 467-513), because `vesting_balance(&victim)` returns `Some(0)`, not `None`.
4. Even if a third party calls `Vesting::vest_other(victim)` to clear the schedule, the attacker repeats step 2, indefinitely denying payout to `victim`.

		let (schedules, locked_now) =
			Self::exec_action(schedules.to_vec(), VestingAction::Passive)?;

	fn vesting_balance(who: &T::AccountId) -> Option<BalanceOf<T>> {
		if let Some(v) = Vesting::<T>::get(who) {
			let now = T::BlockNumberProvider::current_block_number();
			let total_locked_now = v.iter().fold(Zero::zero(), |total, schedule| {
				schedule.locked_at::<T::BlockNumberToBalance>(now).saturating_add(total)
			});
			Some(T::Currency::free_balance(who).min(total_locked_now))
		} else {
			None
		}
	}
