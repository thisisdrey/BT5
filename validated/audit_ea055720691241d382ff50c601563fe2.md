Audit Report

## Title
Reward pool state (`stake`/`unstake`/`harvest_rewards`) permanently DoS'd when a non-monotonic `BlockNumberProvider` regresses, locking staked funds and unclaimed rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes reward-per-token accrual using `ensure_sub` on the delta between the current block number (sourced from the generic `T::BlockNumberProvider`) and the stored `last_update_block` [1](#0-0) . Because `update_pool_rewards` unconditionally overwrites `last_update_block` with the current provider value on every successful call [2](#0-1) , and the pallet's own changelog documents that it was generalized specifically to support relay-chain-backed providers for parachain deployments [3](#0-2) , a single non-monotonic regression of that provider's reported block number — an explicitly undocumented-as-excluded property of `RelaychainStateProvider` [4](#0-3)  — causes `reward_per_token` to underflow and return a hard `DispatchError`, which propagates unconditionally from `stake`, `unstake`, and `harvest_rewards` via `update_pool_and_staker_rewards`.

## Finding Description
`reward_per_token` computes `last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)?` [1](#0-0) , where `last_block_reward_applicable` returns `min(now, expiry_block)` and `now = T::BlockNumberProvider::current_block_number()` [5](#0-4) . `update_pool_rewards` stores `now` as `last_update_block` on every successful pool update [6](#0-5) . This computation is reached from every state-mutating public extrinsic through `update_pool_and_staker_rewards`, which is invoked at the top of `stake` [7](#0-6) , `unstake` [8](#0-7) , and `harvest_rewards` [9](#0-8) . Using `ensure_sub` instead of a saturating subtraction means that once `now` (as reported by the configured provider) is smaller than the previously persisted `last_update_block`, the subtraction underflows and the call returns `Err`, aborting the extrinsic before any state changes occur — and since a successful call is required to ever advance `last_update_block` again, the failure recurs on every subsequent attempt. This contrasts with `pallet-vesting`'s analogous `locked_at`, which explicitly uses `saturating_sub` to tolerate `n < starting_block` [10](#0-9) .

## Impact Explanation
Once triggered for a pool, stakers can no longer `unstake` their frozen tokens nor `harvest_rewards`, since both unconditionally call the failing update path before any other logic executes. This matches the "permanent user-fund … lock" impact category in the accepted impact gate — frozen staking-asset tokens and unclaimed reward-asset balances become permanently inaccessible for the affected pool, with no governance or admin action able to remedy it (the corrupted state is `Pools::<T>::get(pool_id).last_update_block`, which becomes irrecoverably stale relative to the regressed provider value).

## Likelihood Explanation
The vulnerable configuration — a non-local, relay-chain-derived `BlockNumberProvider` — is not hypothetical: the pallet's `BlockNumberProvider` generalization was introduced precisely to enable this configuration for parachains [3](#0-2) , and the underlying `RelaychainStateProvider::current_relay_chain_state` trait is explicitly documented as not guaranteed to return monotonically increasing relay parents [4](#0-3) . A sibling pallet, `pallet-society`, required dedicated hardening for this exact non-monotonic/non-consecutive block-provider behavior [11](#0-10) , confirming this is a recognized, real occurrence rather than a purely theoretical edge case. `pallet-asset-rewards` received no equivalent hardening in the reviewed code.

## Recommendation
Replace `ensure_sub` with `saturating_sub` (or explicitly clamp to zero when `now < last_update_block`) in `reward_per_token`'s elapsed-blocks computation, mirroring `pallet-vesting`'s `locked_at` pattern. Additionally, `update_pool_rewards` should avoid regressing `last_update_block` backward if the provider's `now` is smaller than the currently stored value, to prevent silently reversing reward accounting once the provider value catches back up.

## Proof of Concept
1. Configure a runtime's `pallet_asset_rewards::Config::BlockNumberProvider` to a relay-chain-backed provider (the documented, supported configuration for parachain deployments per the pallet's changelog).
2. Create a pool and have a staker call `stake`, setting `Pools::<T>::get(pool_id).last_update_block = N` via `update_pool_rewards`.
3. On a subsequent parachain block, the provider's `current_block_number()` regresses below `N` — a behavior not excluded by `RelaychainStateProvider`'s contract.
4. Call `unstake` or `harvest_rewards` for that pool; `last_block_reward_applicable(...).ensure_sub(pool_info.last_update_block)?` underflows and returns `Err`, aborting the extrinsic.
5. Because no future call can ever succeed in advancing `last_update_block` past the regression point, the staker's frozen tokens and accrued rewards in that pool remain permanently locked.

	pub fn locked_at<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
		n: BlockNumber,
	) -> Balance {
		// Number of blocks that count toward vesting;
		// saturating to 0 when n < starting_block.
		let vested_block_count = n.saturating_sub(self.starting_block);
		let vested_block_count = BlockNumberToBalance::convert(vested_block_count);
		// Return amount that is still locked in vesting.
		vested_block_count
			.checked_mul(&self.per_block()) // `per_block` accessor guarantees at least 1.
			.map(|to_unlock| self.locked.saturating_sub(to_unlock))
			.unwrap_or(Zero::zero())
	}
