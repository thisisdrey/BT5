## Analysis

The reported bug class is a **fixed-window boundary exploit**: a time-bounded quota (deposit duration, in the original report) is calculated using a naive elapsed-time/window check rather than a continuously-accounted (time-weighted) mechanism, letting an actor straddle the window boundary to receive far more benefit than intended in a negligible amount of real time.

The closest reachable, unprivileged-actor analog in Agave is the per-connection **QUIC stream throttling window** used by the stake-weighted QoS controller.

### Title
Fixed-window QUIC stream throttle allows burst-at-boundary QoS evasion - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed-window rate limiter for QUIC streams per connection: it tracks a `stream_count` and resets it to `0` only when more than `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since the last reset. Because the counter is reset in a single atomic step rather than continuously decayed (e.g., a leaky/token bucket), any client can send its full quota of streams at the very end of one window and immediately send another full quota right after the reset, achieving roughly double the intended per-connection stream rate within a very short real-time span.

### Finding Description
`throttle_stream` in [1](#0-0)  calls `stream_counter.reset_throttling_params_if_needed()` and only sleeps/throttles if `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` within the *current* window. The window itself is a coarse fixed bucket defined in [2](#0-1) : `stream_count` is zeroed only once `STREAM_THROTTLING_INTERVAL` has elapsed since `last_throttling_instant`, and then the timer restarts from `Instant::now()`.

This is invoked for every new QUIC stream via `SwQos::on_new_stream` in [3](#0-2) , which gates per-connection transaction submission throughput for both staked and unstaked peers based on `max_streams_per_throttling_interval` (derived from `available_load_capacity_in_throttling_duration`, itself computed from `StakedStreamLoadEMA` in [4](#0-3) ).

Because the reset only happens lazily on the next `on_new_stream` call after the interval elapses (not on a fixed wall-clock grid), an unprivileged client fully controls when it "closes out" a window: it can send up to `max_streams_per_throttling_interval` streams, wait until just past the 100ms mark (which the client can precisely time), send its next stream to trigger the reset, and then immediately open another full quota of streams. In effect, this yields up to 2x the intended stream (transaction) throughput per connection in a span close to zero additional wall-clock time, defeating the purpose of the per-connection QoS cap in the same way the original report defeats the weekly deposit-duration requirement by acting right at the boundary.

### Impact Explanation
This directly weakens the stake-weighted QoS (SWQoS) mechanism that is meant to fairly bound how many streams (i.e., transactions) a single connection—staked or unstaked—can push into the validator's ingest path. An attacker exploiting the boundary can push roughly double the configured `max_streams_per_ms`-derived allowance through one connection, increasing load on `handle_connection`/packet ingestion beyond what the QoS model intends, and unfairly advantaging the attacker relative to well-behaved peers sharing the same stake-based budget. This is a QoS evasion, which is explicitly in scope.

### Likelihood Explanation
Any unprivileged peer that can open a QUIC connection to the validator's TPU (staked or unstaked, subject to existing connection-count and per-IP limits) can trigger this by locally timing its own stream submissions around the 100ms interval; no special privilege or validator role is required, and the timing threshold (100ms) is coarse and easy to hit consistently from a client.

### Recommendation
Replace the fixed-window `stream_count` reset with a continuously accounted mechanism (e.g., a token bucket that refills proportionally to elapsed time, similar to `TokenBucket`/`KeyedRateLimiter` already used for `ConnectionRateLimiter` in [5](#0-4) ), so that quota is smoothly consumed/replenished instead of being fully reset at each window boundary.

### Proof of Concept
1. Open a QUIC connection as an unstaked (or low-stake) peer to the TPU/TPU-forward QUIC endpoint.
2. At `t = 0`, open `max_streams_per_throttling_interval` streams in rapid succession (each call goes through `SwQos::on_new_stream` → `throttle_stream`); this consumes `stream_count` up to the limit without sleeping.
3. At `t = ~100ms` (i.e., just after `STREAM_THROTTLING_INTERVAL` elapses since `last_throttling_instant`), open one more stream. `reset_throttling_params_if_needed` ( [6](#0-5) ) detects the elapsed interval and resets `stream_count` to `0`, and `last_throttling_instant` to `Instant::now()`.
4. Immediately (at `t ≈ 100ms + ε`) open another full batch of `max_streams_per_throttling_interval` streams before the next window naturally would have permitted them under a smooth/continuous accounting model.
5. Total streams opened in ~100ms ≈ `2 * max_streams_per_throttling_interval`, roughly double the intended per-connection quota for that interval.

    /// Reset the counter and last throttling instant and
    /// return last_throttling_instant regardless it is reset or not.
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
