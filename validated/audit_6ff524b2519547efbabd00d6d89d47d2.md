### Title
Weak `ValidateGitDirectory` "leaf repository" check allows cross-repository object/ref disclosure via directory-snapshot escape - (File: internal/gitaly/storage/locator.go)

### Summary
`storage.ValidateGitDirectory` decides whether a filesystem path is a "valid Git repository" purely by checking that three names (`objects`, `refs`, `HEAD`) exist under it, exactly like the Palmera `isSafe()` bug, which decided a contract was a "Safe" purely because `getThreshold()` returned a non-zero value. Neither check verifies that the object actually behaves like/represents the thing it's supposed to gate. In Gitaly this weak "is-a-repo" signal is explicitly relied upon as a security boundary to prevent transaction snapshots from being taken of a *non-leaf* directory (e.g. an intermediate hashed-storage prefix that is the parent of many unrelated repositories), yet nothing prevents an attacker from placing sibling `objects`/`refs`/`HEAD` entries at such a shared/parent path to make that check pass.

### Finding Description
`ValidateGitDirectory` is documented as validating "whether a directory looks like a valid Git repository", but its implementation only stats three fixed names: [1](#0-0) 

It does not check that `objects`/`refs` are directories (vs. plain files), does not check `HEAD` content, and critically does not check that the candidate directory is a *leaf* (i.e. has no other unrelated repository directories as siblings). This function is the sole gate used by `configLocator.ValidateRepository` for all repository-path validation reachable from ordinary RPCs: [2](#0-1) 

It is also used explicitly as a directory-hierarchy boundary check in the transactional snapshot logic. The code comment states the intended security property directly: the check exists so that a caller cannot "snapshot an entire subtree" by targeting a non-leaf, hashed-storage prefix directory (e.g. `@hashed/xx`): [3](#0-2) 

Because `ValidateGitDirectory` only checks for the *presence* of three names anywhere under the candidate path — not that the path is an actual leaf repository directory with no unrelated content — an attacker who can create a repository at an attacker-chosen relative path (e.g. via `CreateRepository`, `CreateFork`, `ReplicateRepository`, or any RPC that accepts a `RelativePath`, which is only checked for path-escape via `ValidateRelativePath`, not for hierarchy depth) can target a shared/parent directory that already contains other tenants' repositories as subdirectories. Standard repository initialization will write `HEAD`, `objects/`, and `refs/` directly into that directory, which is enough to make `ValidateGitDirectory` (and thus the "leaf repository" protection) return success for a directory that is not actually a leaf and that has unrelated sibling repository data alongside it.

Once this crafted directory passes the check, `createRepositorySnapshot` recursively walks and hard-links the *entire* directory tree at that path into the transaction snapshot: [4](#0-3) [5](#0-4) 

The set of files/directories included in that walk is controlled by a `Filter`. While `NewRegexSnapshotFilter` restricts inclusion to known Git-repo-internal path shapes, `NewDefaultFilter` — used, among other cases, during "leftover migration" and as the general default filter — includes *everything* except worktree paths: [6](#0-5) 

With this permissive filter in effect, an unrelated sibling repository sitting under the same attacker-targeted parent directory would be walked and hard-linked wholesale into the attacker's transaction snapshot, exposing another repository's Git objects and refs to the attacker's transaction.

### Impact Explanation
This breaks the documented isolation boundary between repositories stored under the same storage hierarchy: an attacker-controlled repository creation targeting a shared/parent directory can, via the weak `ValidateGitDirectory` "leaf" check, cause the snapshot machinery to hard-link an entire subtree — including unrelated tenants' Git objects and refs — into a transaction the attacker controls, resulting in cross-repository data disclosure. This maps to the "concrete cross-repository object access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to create/replicate a repository at an attacker-chosen `RelativePath` that resolves to a non-leaf, populated parent directory in the storage hierarchy, and for the transaction snapshot logic to run against that path with the permissive (`NewDefaultFilter`) filter rather than the restrictive regex filter. `RelativePath` is validated only for storage-root escape (`ValidateRelativePath`), not for hierarchy depth or leaf-ness, so the precondition is plausibly reachable from ordinary repository-creation/replication RPCs. I was not able to fully trace, within the available index, every call site that decides which `Filter` (`NewDefaultFilter` vs `NewRegexSnapshotFilter`) is passed into `newSnapshot`/`createRepositorySnapshots` for standard (non-migration) transactions, so the exact conditions under which the permissive filter applies to normal read/write transactions remain uncertain and would need confirmation in a full Devin session with complete codebase access.

### Recommendation
Strengthen `ValidateGitDirectory` (or add a dedicated check for the snapshot subtree-protection use case) to verify actual leaf-repository semantics rather than mere presence of three names: verify `objects` and `refs` are directories with expected substructure, verify `HEAD` is a regular file with valid ref-pointer/hash content, and, most importantly for the snapshot use case, reject directories that contain unexpected sibling entries not belonging to the Git repository layout (i.e., enforce that the directory is a leaf with no other repository-like children). Additionally, ensure the restrictive `NewRegexSnapshotFilter` (not `NewDefaultFilter`) is used for any snapshot path reachable from ordinary user-triggered transactions, since the default filter's blanket inclusion is what turns the weak leaf check into a full data-disclosure primitive.

### Proof of Concept
1. Determine or influence the relative-path hierarchy such that a legitimate repository R2 already exists at `<storage>/@hashed/6b/86/<hash>.git`.
2. Issue a repository-creation RPC (e.g. `CreateRepository`/`CreateFork`/`ReplicateRepository`) with `RelativePath = "@hashed/6b"` — this passes `ValidateRelativePath` (no path escape) and standard init writes `HEAD`, `objects/`, `refs/` directly into `@hashed/6b`, which now sits as a sibling of the real `86/` subdirectory containing R2.
3. `storage.ValidateGitDirectory("@hashed/6b")` now returns `nil` (all three entries present), so the "leaf repository" protection in `createRepositorySnapshots` is bypassed.
4. Trigger a transaction/operation on the attacker's repository (`@hashed/6b`) that causes `newSnapshot`/`createRepositorySnapshot` to run with a permissive filter (e.g. `NewDefaultFilter`); `createDirectorySnapshot` walks the entire `@hashed/6b` subtree and hard-links R2's `objects`/`refs` (under `86/<hash>.git`) into the attacker's snapshot.
5. The attacker's transaction now has access to R2's Git objects and refs, which it should never have been able to reach.

// ValidateGitDirectory validates the directory at the given path looks like a valid
// Git repository. If the path points to a valid directory which doesn't contain the
// expected entries InvalidGitDirectoryError is returned. A directory is considered to
// be valid Git directory if it contains 'objects', 'refs' and 'HEAD'.
func ValidateGitDirectory(path string) error {
	if info, err := os.Stat(path); err != nil {
		return fmt.Errorf("stat: %w", err)
	} else if !info.IsDir() {
		return errors.New("not a directory")
	}

	for _, file := range []string{"objects", "refs", "HEAD"} {
		if _, err := os.Stat(filepath.Join(path, file)); err != nil {
			if !errors.Is(err, fs.ErrNotExist) {
				return fmt.Errorf("stat %q: %w", file, err)
			}

			return InvalidGitDirectoryError{MissingEntry: file}
		}
	}

	return nil
}

func createDirectorySnapshot(ctx context.Context, originalDirectory, snapshotDirectory string, matcher Filter, stats *snapshotStatistics) error {
	if err := filepath.Walk(originalDirectory, func(oldPath string, info fs.FileInfo, err error) error {
		if err != nil {
			if errors.Is(err, fs.ErrNotExist) && oldPath == originalDirectory {
				// The directory being snapshotted does not exist. This is fine as the transaction
				// may be about to create it.
				return nil
			}

			return err
		}

			return fmt.Errorf("rel: %w", err)
		}

			if info.IsDir() {
				return fs.SkipDir

// NewDefaultFilter include everything.
func NewDefaultFilter(ctx context.Context) FilterFunc {
	return func(path string) bool {
		// When running leftover migration, we want to include all files to fully migrate the repository.
		if featureflag.LeftoverMigration.IsEnabled(ctx) {
			return true
		}

		// Don't include worktrees in the snapshot. All the worktrees in the repository should be leftover
		// state from before transaction management was introduced as the transactions would create their
		// worktrees in the snapshot.
		if path == housekeeping.WorktreesPrefix || path == housekeeping.GitlabWorktreePrefix {
			return false
		}
		return true
	}
}
