This confirms the vulnerability: nothing in the request path binds the signature check to `contract_identifier`. The RPC handler `try_handle_request` in `stackslib/src/net/api/poststackerdbchunk.rs` takes the `contract_identifier` purely from the URL path and passes it to `try_replace_chunk`, but the signature verification inside (`slot_desc.verify(&slot_validation.signer)`) is fully agnostic to which contract that `slot_validation` came from — it only checks `(slot_id, slot_version, data_hash)` against the recovered signer address for that slot in whatever `smart_contract` was resolved. Also confirmed via `stackslib/src/chainstate/stacks/boot/signers.clar` and `signer_set.rs` that signer-slot allocation is deterministic per reward-cycle-parity/page, so the same signer address can legitimately retain the same `slot_id` across different `.signers-X-Y` StackerDB contracts (across cycles or pages), satisfying the "same address owns the same slot across two DBs" precondition without any attacker-side privilege beyond relaying already-public gossip data.

### Title
Cross-StackerDB chunk replay via contract-agnostic `SlotMetadata::auth_digest` - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` signs only `(slot_id, slot_version, data_hash)` and omits the StackerDB's `smart_contract_id`, so a validly signed chunk for one StackerDB contract is also a validly signed chunk for any other StackerDB contract in which the same signer address happens to hold the same slot number. Because signer-slot assignment for `.signers-*` contracts is deterministic and can be identical across pages/cycles, and because chunk `(sig, slot_id, slot_version, data)` tuples are public (gossiped over p2p and returned by read RPC endpoints), an unprivileged remote party can replay/relay a chunk captured from contract A into contract B via `POST /v2/stackerdb/:addr/:contractB/chunks`.

### Finding Description
`auth_digest` in [1](#0-0)  hashes `slot_id || slot_version || data_hash` with no `smart_contract_id` component, and `SlotMetadata::verify`/`sign` operate purely on this digest [2](#0-1) . `StackerDBTx::try_replace_chunk` resolves the slot's expected signer strictly from the target `smart_contract`'s validation table via `get_slot_validation(smart_contract, slot_desc.slot_id)` and then calls `slot_desc.verify(&slot_validation.signer)` [3](#0-2) ; the contract identifier is used only to select which table's signer/version to check against, never mixed into the signed material itself. The public RPC handler `RPCPostStackerDBChunkRequestHandler::try_handle_request` takes `contract_identifier` from the URL path and the chunk body from an unauthenticated POST, and forwards them directly to `try_replace_chunk` with no additional binding check [4](#0-3) . Consequently, if address X owns `slot_id=S` in both contract A and contract B, a chunk `(S, V, data)` signed once by X for A is also accepted for B, since the digest and signature are identical in both contexts. Signer-slot allocation for the `.signers-N-M` contracts is computed deterministically per reward-cycle parity from the sorted signer set [5](#0-4) , so the same address retaining the same slot index across different message-page contracts or across cycles is a realistic, non-adversarial occurrence, not requiring the attacker to control any private key.

### Impact Explanation
An unprivileged relayer who observes a signed chunk broadcast for StackerDB contract A (chunks are gossiped and served by public read RPCs, not secret) can re-POST that exact byte sequence to a different contract B's chunk endpoint on any node. If B assigns the same slot to the same signer address and B's current version/max-writes checks happen to be satisfied, the node accepts and stores/relays it as B's legitimate chunk via `set_relay_message(StacksMessageType::StackerDBPushChunk(..))` [6](#0-5) , propagating cross-context data network-wide under a false contract association. This can desynchronize or confuse consumers that key StackerDB payload interpretation strictly by `contract_id` (e.g., signer message pages, distinct reward cycles), causing stale/foreign data to be served/relayed as canonical for the wrong DB.

### Likelihood Explanation
Exploitation requires only that some signer address coincidentally (or by design, given deterministic slot allocation) holds the same `slot_id` across two contracts, and that the replayed `(slot_version, data_hash)` tuple clears the target DB's freshness/`max_writes` checks — a condition entirely outside attacker control and dependent on state alignment, making it opportunistic rather than reliably attacker-triggered on demand. The attacker needs no privileged role, secret, or key; only observation of gossiped/public chunk data and the ability to send an HTTP POST to a target node's public RPC port.

### Recommendation
Include `smart_contract_id` (or a stable, unique DB identifier) as part of the material hashed in `SlotMetadata::auth_digest`, and thread the contract identifier into `sign`/`verify`/`recover_pk` so a signature is cryptographically bound to the specific StackerDB it was produced for.

### Proof of Concept
Add a test in `stackslib/src/net/stackerdb/tests/db.rs`: create two `StackerDBs` (or two `smart_contract` entries in one DB) both assigning slot 0 to the same address; sign one `StackerDBChunkData` for slot 0/version 1 with that address's key; call `tx.try_replace_chunk(&contract_A, &chunk.get_slot_metadata(), &chunk.data)` (expect success), then call `tx.try_replace_chunk(&contract_B, &chunk.get_slot_metadata(), &chunk.data)` with the identical signature/data and assert it also succeeds — demonstrating the same signature is valid across distinct `smart_contract_id` namespaces, confirmed by both `get_slot_metadata(&contract_A, 0)` and `get_slot_metadata(&contract_B, 0)` returning matching `signature` fields despite belonging to logically distinct DBs.
