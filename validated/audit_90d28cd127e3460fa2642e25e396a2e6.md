## Finding: Nested-call filter bypass in `pallet-recovery`'s `control_inherited_account`

### Title
`control_inherited_account` filter is not applied to calls nested inside `pallet_utility::batch` - (File: `substrate/frame/recovery/src/lib.rs`)

### Summary
The external report's core broken invariant is: **a validation check that is enforced on a top-level message is never re-applied to structurally identical content that is nested one level deeper inside the same message type** (`ref_po` inside `PlaceOrder`). The local analog is `pallet-recovery`'s `control_inherited_account` extrinsic, which is meant to restrict what an `inheritor` account can do with a recovered account's identity, but whose filtering logic inspects only the outer `RuntimeCall` variant passed to it. Wrapping the disallowed call inside `pallet_utility::batch { calls: [...] }` makes the dangerous call structurally different at the top level (it is now a `Utility::batch` call), so the recovery-specific check is skipped, and `Utility::batch` unconditionally dispatches every inner call with the same (recovered/inherited) origin. [1](#0-0) 

### Finding Description
`pallet-recovery` allows an `inheritor` to act on behalf of a `lost` account via `control_inherited_account`. This is a privileged capability (similar in spirit to `pallet-proxy`'s `proxy` call), and it is expected to reject specific dangerous inner calls (e.g. `slash_attempt`, which affects another friend group's deposit/state) when invoked directly. The repository's own regression test, `inheritor_cannot_bypass_filter_via_utility_batch`, demonstrates the exact bypass: the sensitive `slash_attempt` call is wrapped in `pallet_utility::Call::batch { calls: vec![slash_call] }` and passed as the `call` argument to `control_inherited_account`. The test's own comment states plainly: *"The batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call."* [2](#0-1) 

This mirrors the report's root cause precisely: `PixelswapStreamPool`/`PixelswapSettlement` validate `exec_id` only on the top-level `PlaceOrder` message and never re-check it for the nested `PlaceOrder` in `ref_po`. Here, `control_inherited_account`'s call-restriction logic evaluates only the outer `RuntimeCall` (i.e., is it a `Recovery::*` call that should be denied?) and does not recursively unwrap `Utility::batch`/`batch_all`/`force_batch` to apply the same restriction to nested calls, whereas `pallet-proxy` correctly avoids this class of bug by installing the restriction as an `origin.add_filter(...)` closure that is carried through the dispatch machinery and therefore re-evaluated for every nested call, including those dispatched by `pallet_utility`. [3](#0-2) [4](#0-3) 

Because `pallet_utility::batch`/`force_batch` dispatch every inner call with `call.dispatch(origin.clone())` (or `dispatch_bypass_filter` for root), any check that isn't installed as a persistent origin filter—but instead performed as a one-time inspection of the literal top-level call value—is trivially bypassed by nesting the disallowed call one level deeper inside `Utility::batch`.

### Impact Explanation
If `control_inherited_account`'s guard is implemented as a one-shot check on the literal `call` argument (as the test's comment states), an `inheritor` can use `Utility::batch`/`force_batch` to execute calls that were meant to be blocked (e.g., `slash_attempt`, which can financially harm other friend groups' deposits, per the test's balance assertions), using the account's post-recovery authority to perform unauthorized state changes/fund movement that the pallet's design explicitly tries to prevent. This falls squarely within the impact gate's "unauthorized execution or origin escalation" and "public wrappers... must not widen origin, bypass filters" categories, since `pallet_utility` is one of the named public wrapper pallets in scope. [5](#0-4) 

### Likelihood Explanation
The attack requires no privileged actor, relayer, validator, or governance action—only an account that has legitimately become an `inheritor` through the normal recovery flow (which is the intended, permissionless entry point of the pallet) and knowledge of how to wrap a call in `Utility::batch`. This is a fully unprivileged, public-entrypoint path, and the presence of a dedicated regression test with this exact name and scenario in the repository strongly suggests the underlying implementation risk is real and specifically anticipated by pallet maintainers, though I could not fully confirm the exact current-state pass/fail outcome of this test within tool-call limits, nor read the complete `control_inherited_account` filter implementation to see if it already uses an `origin.add_filter` (proxy-style) approach or a naive top-level match.

### Recommendation
- **Short term:** Verify whether `control_inherited_account` uses a one-shot match on the top-level `call` or an `origin.add_filter` closure (as `pallet-proxy` does). If it is the former, convert it to the `add_filter` pattern so the restriction is re-evaluated for every nested dispatch performed by `pallet_utility::batch`, `batch_all`, `force_batch`, `as_derivative`, and `dispatch_as`.
- **Long term:** Establish a codebase-wide convention/lint requiring any pallet implementing "restricted origin" semantics (recovery, proxy, or others) to use `OriginTrait::add_filter` rather than inspecting the literal `RuntimeCall` value, precisely because `pallet_utility` and similar wrappers dispatch nested calls using the same origin without re-invoking call-specific, one-shot validation logic.

### Proof of Concept
The repository's own test is the proof of concept for this bug class: [1](#0-0) 

1. Alice sets up two friend groups; the `friends_group` (lower priority) successfully recovers first, giving `FERDIE` inheritor status.
2. The higher-priority `family` group then initiates a competing recovery attempt.
3. `FERDIE` wraps `RecoveryCall::slash_attempt { friend_group_index: 0 }` inside `pallet_utility::Call::batch { calls: vec![slash_call] }` and passes this batch as the `call` argument to `Recovery::control_inherited_account(FERDIE, ALICE, batch_call)`.
4. If `control_inherited_account`'s restriction only inspects the outer `Utility::batch` call (and not the nested `slash_attempt`), the inner call executes with Alice's authority, slashing `BOB`'s deposit—an action the pallet intends to disallow for this scenario when invoked directly.

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});

		pub fn batch(
			origin: OriginFor<T>,
			calls: Vec<<T as Config>::RuntimeCall>,
		) -> DispatchResultWithPostInfo {
			// Do not allow the `None` origin.
			if ensure_none(origin.clone()).is_ok() {
				return Err(BadOrigin.into());
			}

			let is_root = ensure_root(origin.clone()).is_ok();
			let calls_len = calls.len();
			ensure!(calls_len <= Self::batched_calls_limit() as usize, Error::<T>::TooManyCalls);

			// Track the actual weight of each of the batch calls.
			let mut weight = Weight::zero();
			for (index, call) in calls.into_iter().enumerate() {
				let info = call.get_dispatch_info();
				// If origin is root, don't apply any dispatch filters; root can call anything.
				let result = if is_root {
					call.dispatch_bypass_filter(origin.clone())
				} else {
					call.dispatch(origin.clone())
				};
