### Title
Vault share accounting (`assets` data-var) is never reconciled with the real underlying token balance, allowing share price to desynchronize and causing insolvency for late redeemers - (File: `mainnet/contracts/vault/v0-vault-ststx.clar` and identical logic in `v0-vault-ststxbtc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
Every Zest v0 vault tracks the underlying it custodies purely through an internal counter, `assets`, that is incremented/decremented by `deposit`, `redeem`, `system-repay`, and `socialize-debt`. This counter is used exclusively for share pricing (`total-assets`, `total-assets-preview`, `get-available-assets`) and is never checked against the vault's actual on-chain token balance. Each vault defines a helper, `ubalance`, that queries the real balance held by the contract, but this helper is dead code with respect to share pricing — it is not called anywhere inside `total-assets`, `total-assets-preview`, `convert-to-shares-preview`, or `convert-to-assets-preview`.

### Finding Description
`assets` is declared as a plain data-var [1](#0-0)  and is the sole basis for the vault's notion of how much underlying it holds: [2](#0-1) 

`ubalance` is defined as a real query against the underlying token contract, but is only defined — never invoked from any of the accounting/pricing paths: [3](#0-2) 

Share/asset conversion, which determines how many shares a depositor gets and how much underlying a redeemer receives, is computed exclusively from `total-assets-preview`/`total-supply-preview`, i.e., from the internal `assets` var, not from the real balance: [4](#0-3) 

`assets` is mutated independently in several code paths (`deposit` adds the user-declared `amount`, `redeem` subtracts `inkind`, `system-repay` adds `interest-paid`, `socialize-debt` subtracts `principal-reduction`): [5](#0-4) [6](#0-5) [7](#0-6) 

None of these updates are ever cross-checked against `ubalance()`. As in the Cabal report — where `staked_amounts` was blindly incremented without ever calling `pool_router::get_real_total_stakes` to detect slashing — Zest's `assets` counter is blindly maintained and never synchronized to the actual custody balance returned by `ubalance`. Any divergence between the tracked `assets` value and the real underlying balance (e.g., loss of value in the underlying liquid-staking token `stSTX`/`stSTXbtc` held by the vault due to slashing or shortfall events in the third-party staking protocol that Zest does not control, or accumulated `mul-div-down` truncation drift across `system-repay`/`socialize-debt`/`accrue` operations over many blocks) permanently corrupts the share price with no self-healing mechanism, because pricing never re-reads `ubalance()`.

### Impact Explanation
Because `convert-to-shares-preview`/`convert-to-assets-preview` price shares strictly off the stale `assets` counter:
- If the real balance (`ubalance`) falls below the tracked `assets` value, `total-assets` is overstated. Existing/early redeemers calling `redeem` receive `inkind = amount * ta / ts` computed against the inflated `ta`, extracting more real underlying than is actually backed. `redeem`'s only liquidity guard, `(asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)` [8](#0-7) , itself is computed from the same stale `assets` var (`get-available-assets`) [9](#0-8) , so it does not protect against the real shortfall — it will allow redemptions to proceed against phantom assets until the contract's real token balance is exhausted.
- This produces protocol insolvency: the last shareholders to redeem cannot get their fair share of real underlying back, because earlier redeemers were paid out based on an inflated internal accounting figure. This is a permanent freezing of funds for the remaining holders, and functionally a transfer of real value from later redeemers to earlier ones — the same dilution mechanism described in the Cabal report, applied to Zest's vault share math instead of Cabal's `sxINIT` staking wrapper.

### Likelihood Explanation
No privileged action or DAO compromise is required to reach the vulnerable code path — every regular `deposit`/`redeem` call goes through the unreconciled `total-assets`/`get-available-assets` functions. The triggering precondition (real custody balance falling below the tracked `assets` counter) is an external event outside the vault's own transaction flow, exactly analogous to the "slashing" trigger in the Cabal report, and the vault code provides no mechanism (admin or automatic) to detect or correct such drift — `ubalance()` exists but is dead code for pricing purposes, confirming the gap was never closed.

### Recommendation
Reconcile the vault's `assets` accounting with the real underlying balance:
- Replace `(var-get assets)` in `total-assets`/`total-assets-preview`/`get-available-assets` with a value derived from (or checked against) `ubalance()`, so share pricing always reflects the vault's real custody balance.
- Alternatively, add an explicit sync/reconciliation step (called during `accrue`) that clamps `assets` to `min(assets, ubalance())`, socializing any detected shortfall across share price immediately rather than allowing it to be silently ignored until a run of redemptions exposes the shortfall.

### Proof of Concept
1. Vault `v0-vault-ststx` starts with `assets = 1,000,000`, `zft` total supply `= 1,000,000` (1:1 exchange rate).
2. The real balance of `stSTX` held by the vault (`ubalance()`) drops to `950,000` due to an external event in the underlying liquid-staking protocol (outside Zest's control) — `assets` var is untouched by this event since nothing in `v0-vault-ststx.clar` calls `ubalance()` to detect it.
3. `total-assets` still reports `1,000,000` (per line 334-339), so `convert-to-assets-preview(1000)` returns `1000 * 1,000,000 / 1,000,000 = 1000` — a 1:1 rate that is no longer true.
4. Early redeemers call `redeem`, each successfully passing the `available-assets >= inkind` check (line 813) since it is computed from the same stale `assets` var, and receive full 1:1 payouts drawn from the shrunken real `stSTX` balance.
5. Once enough redemptions occur, the last redeemers' `send-underlying` calls fail because the vault's actual `stSTX` balance is exhausted even though their `zft` shares and the internal `assets`/`total-supply` bookkeeping indicate they are still entitled to redeem at 1:1 — their funds are permanently frozen/lost, while earlier redeemers extracted more than their real share.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,

        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,

        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
