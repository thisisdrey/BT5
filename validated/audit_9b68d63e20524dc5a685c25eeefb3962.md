### Title
Unsanitized `remote` attribute in `git_repository`/`new_git_repository` permits arbitrary command execution via Git's `ext::` transport helper - ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
`git_repository`'s `remote` attribute is passed to `git remote add origin <remote>` and subsequently `git fetch origin` without any scheme/protocol validation. Git supports a `ext::<command>` (and `fd::`) remote helper transport that executes an arbitrary local command as the transport handler. A remote value controlled by an untrusted party (e.g. a value coming from a transitive/registry-published `MODULE.bazel` module extension invocation, or any place where a `remote` string is plumbed through without being restricted to `http(s)/git/ssh` schemes) results in local command execution on the machine running `bazel fetch`/`bazel build`, mirroring the Composer Perforce `rsh:`/`jsh:` P4PORT injection (BIT-composer-2026-84361 / CVE-2026-84361).

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` builds a `_GitRepoInfo` directly from `ctx.attr.remote` [1](#0-0) , then calls `_update`, which calls `add_origin(ctx, git_repo, ctx.attr.remote)` [2](#0-1) . `add_origin` shells out to `git remote add origin <remote>` with no validation of the string's contents or scheme [3](#0-2) , and `fetch()`/`_git_maybe_shallow` then run `git fetch origin -- <fetch_ref>` against that configured remote [4](#0-3) . The `remote` attribute is declared as a plain mandatory string with no format restriction in `tools/build_defs/repo/git.bzl` [5](#0-4) .

Git's own transport layer treats a URL of the form `ext::<shell-command>` (or the `fd::` helper) as an instruction to invoke `git remote-ext`, which directly executes `<shell-command>` as a subprocess to serve the Git protocol over its stdio — this is a documented Git feature, not a bug in Git, but it means *any* code path that lets an attacker control the string handed to `git remote add`/`git fetch` grants that attacker arbitrary local command execution with the privileges of the user/CI account running Bazel. `_execute()` invokes `git` with the user's full environment (`ctx.os.environ`) merged with a small denylist of Git-internal variables [6](#0-5)  — there is no `GIT_ALLOW_PROTOCOL` restriction anywhere in this code path, and no check rejecting `ext::`/`fd::`/other non-network schemes before the value reaches `git`.

This is the direct structural analog of the Composer bug: Composer's `Perforce` utility passed an attacker-supplied `source.url` (`rsh:`/`jsh:` P4PORT) straight to the `p4` client, which spawns a local command; here, Bazel's git repository-rule tooling passes an attacker-supplied `remote` string straight to `git`, which can spawn a local command via `ext::`.

Where does the untrusted `remote` value actually originate in a build a victim didn't author themselves? Any dependency that is resolved through Bzlmod module extensions (declared in a `bazel_dep`'d module's `MODULE.bazel`, which is not root-repo, attacker-published content when using a custom/malicious registry or a compromised transitive dependency) can invoke a repository rule such as `git_repository` (or a custom extension wrapper around `git_repo()`/the same worker) with a `remote` value taken from tag-class attributes that are entirely under the publishing module's control. Because Bzlmod evaluates and executes these extensions as part of ordinary dependency resolution, this reaches `_execute()`/`git` without the root repo's consent or review of the exact string, and the victim only sees this at fetch time (or not at all if it's quiet).

### Impact Explanation
If reached with a hostile `remote` string, this results in local arbitrary command execution on the machine performing `bazel fetch`/`bazel build`/`bazel sync`, with the privileges of the invoking user or CI service account. This can lead to credential theft (CI secrets, cloud metadata tokens), lateral movement, or full workstation/CI compromise — a supply-chain remote-code-execution primitive triggered purely by resolving a dependency, matching the severity class of the Composer advisory (High).

### Likelihood Explanation
Likelihood depends entirely on whether an untrusted `remote` string can reach `git_repo()`/`add_origin()` without going through hand-authored, trusted root-repo Starlark. Under Bzlmod, a malicious or compromised module hosted in a custom registry (or a transitive dependency accepted via `bazel_dep`) can define a module extension that calls `git_repository`/`git_repo` with a `remote` value it fully controls; this is squarely in-scope per the threat model here (untrusted content served/published by an outside party that a victim's build consumes), not root-repo-trusted Starlark. No sha256/integrity mechanism binds or restricts the `remote` field the way `http_archive`'s `sha256`/`integrity` binds archive contents — there is no equivalent "pin" that would stop an `ext::` string from being accepted, so nothing in the existing code intercepts this before `git` is invoked.

### Recommendation
- Validate `remote` (and any Git URL passed into `git_worker.bzl`) against an allow-list of expected schemes (`http://`, `https://`, `ssh://`, `git://`, `file://`, or a bare `scp`-like `user@host:path`) before calling `git remote add`/`git fetch`; reject `ext::`, `fd::`, and any other command-invoking transport strings.
- Alternatively/additionally, set `GIT_ALLOW_PROTOCOL` (or pass `-c protocol.ext.allow=never -c protocol.fd.allow=never`) in the environment/config used by `_execute()` in `git_worker.bzl` so Git itself refuses these transports regardless of the string's shape.
- Apply the same validation everywhere a repository-rule `remote`/URL-like attribute is passed to an external VCS client binary (`git`, `hg`, `p4`, `svn`) inside `tools/build_defs/repo/`.

### Proof of Concept
A `src/test/shell/bazel/starlark_git_repository_test.sh`-style reproduction:
```
cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "pwn",
    remote = "ext::sh -c 'touch $TEST_TMPDIR/pwned; exit 1'",
    commit = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
)
EOF
bazel fetch @pwn >& $TEST_log
[ -e "$TEST_TMPDIR/pwned" ] && fail "Arbitrary command executed via ext:: remote transport"
```
This exercises `add_origin`/`fetch` in `tools/build_defs/repo/git_worker.bzl` [7](#0-6) ; because `remote` is never scheme-validated, `git remote-ext` runs `sh -c '...'` on the host performing the fetch.

**Uncertainty note:** I was not able to fully trace, within the indexed content available, a concrete first-party Bzlmod module-extension code path (i.e., a specific `.bzl` file shipped in this repo) that forwards a registry/tag-class-controlled string directly into `git_repo()`'s `remote` parameter without any intervening trusted root-repo authoring step. The vulnerable primitive (`git_worker.bzl` passing an unvalidated `remote` to `git remote add`/`git fetch`) is confirmed directly in code, but confirming the exact "attacker-published module extension" reachability chain end-to-end would benefit from a full-repository review (e.g., via a Devin session) rather than the indexed excerpts available here.
