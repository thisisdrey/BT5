### Title
Precompiled contract ABI array-length parsing allocates unbounded arrays before validating against actual calldata size - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an attacker-controlled "array length" word directly out of the precompile's `data` calldata and immediately allocate a Java array of that size, before any check that the declared length is consistent with the actual amount of data supplied.

### Finding Description
The three helper methods used by ABI-decoding logic in precompiled contracts extract a length from a `DataWord` in the calldata and use it directly to size an allocation: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `len` comes from `words[offset].intValueSafe()`. `intValueSafe()` only clamps overflow to `Integer.MAX_VALUE` — it performs no check that `len` fits within the bounds of the remaining calldata: [4](#0-3) 

So a caller can supply a small `data` buffer with a length-word set to a large value (e.g. `0x7fffffff`), and `new byte[len][]` (or `new byte[len]` inside the loop via `extractBytes`) is executed before the code ever validates that `len` bytes/elements are actually present in `data`. This is the same bug class as the reported Bouncy Castle CVE-2026-12185: allocation sized from an untrusted length field performed before any integrity/consistency check against the actual payload.

By contrast, other array-length parsing paths in the same file — e.g. the shielded transfer proof precompile — explicitly bound-check the count before allocating (`spendCount < 1 || spendCount > 2 …`) at [5](#0-4) , showing the codebase is aware of this class of bug in some places but not in `extractBytes32Array`/`extractBytesArray`/`extractSigArray`.

### Impact Explanation
Any account able to trigger execution of a smart contract that calls into the precompile(s) using these array-extraction helpers can pass calldata whose embedded length word declares an enormous element count while providing only a small amount of actual calldata. This drives `new byte[len][]` with `len` up to `Integer.MAX_VALUE`, causing an immediate `OutOfMemoryError`/huge heap allocation inside the TVM execution path of the full node processing the transaction. Because TVM execution runs in-process with the rest of the node (block application, API serving), a crash or severe GC pressure here can crash or halt the node processing the block, i.e. node crash/halt — one of the explicitly in-scope impacts.

### Likelihood Explanation
Reaching this code only requires broadcasting a transaction that invokes a contract call which hits the precompiled contract(s) using these helpers; no special privilege, witness/SR role, or network position is required — any transaction broadcaster or contract deployer can construct the calldata. The energy charged for the call is generally based on `data.length` (the actual, small calldata payload), not on the declared internal length, so the attacker pays comparatively little energy to trigger an allocation attempt many orders of magnitude larger.

### Recommendation
Add a bounds/sanity check on the decoded `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating (e.g., verify `len >= 0` and that `len` is consistent with the remaining size of `data`/`words`, similar to the explicit bound check already used for `spendCount`/`receiveCount` in `VerifyTransferProof.execute`), rejecting the precompile call instead of allocating first.

### Proof of Concept
I was unable to directly confirm from the indexed snippets which specific precompiled contract(s) invoke `extractBytesArray`/`extractSigArray`/`extractBytes32Array` (grep only surfaced matches within `PrecompiledContracts.java` itself, and call-site context beyond the definitions was not returned by the tools). This limits certainty about the exact reachable precompile entry point (e.g. the batch/multi-signature validation precompile is the most likely candidate based on the helper names and `SIG_LENGTH` usage), and a full PoC transaction cannot be constructed without that confirmation. A Devin session with full repository access would be needed to trace the exact call sites and craft a concrete calldata PoC.
