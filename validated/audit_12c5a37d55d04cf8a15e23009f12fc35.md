### Title
Attacker can dust-fill a victim's per-account token list (`depositTokensOfAccount`) to permanently block that account from opening new positions - (File: contracts/DepositToken.sol)

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` combined deposit + debt tokens per account via `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143-148`). Any first-time receipt of a `DepositToken` — including a permissionless ERC20 `transfer` of 1 wei from an attacker — calls `pool.addToDepositTokensOfAccount(recipient)` (`DepositToken.sol:517-520`), which reverts once the account's list hits the cap. An attacker can therefore grief any targeted account by pushing dust msdTOKEN balances of every registered collateral to the victim, making all subsequent `deposit`, `issue`, and `SmartFarmingManager.leverage` calls that would add a *new* token to the victim's list revert with `UserReachedMaxTokens`. This mirrors the Asterisk bug class: a cheap, repeatable unprivileged action that denies new session/position establishment.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's list whenever the recipient's prior balance is zero (`DepositToken.sol:517-520`). There is no opt-in; receiving dust is forced.
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:143-148`, `Pool.sol:79`).
- The same modifier guards `addToDebtTokensOfAccount` (`Pool.sol:204`), so once the list is full the victim can neither deposit a new collateral type (`DepositToken._mint` → `addToDepositTokensOfAccount`, `DepositToken.sol:485-488`) nor issue a new synth (`DebtToken._mint` → `addToDebtTokensOfAccount`).
- Attack path (all public entry points, no privileged role):
  1. For each deposit token `msdX` registered in the pool: `underlying.approve(msdX, dust)` → `msdX.deposit(dust, attacker)` (`DepositToken.sol:211`) → `msdX.transfer(victim, 1)` (`DepositToken.sol:348`). The transfer passes `_revertIfLocked` because the attacker has no debt (`unlockedBalanceOf` returns full balance when `_debtInUsd == 0`, `DepositToken.sol:383-398`).
  2. Once the victim's combined list reaches 30 entries, every `deposit`/`issue`/`leverage` touching a new token reverts.
- The pool's `addDepositToken` itself caps registered deposit tokens at `MAX_TOKENS_PER_USER` (`Pool.sol:703`), so the attacker can fill at most `N` slots where `N` is the number of registered deposit tokens; the attack lands whenever `victim_existing_entries + N >= 30` — i.e., it fully blocks fresh accounts only on pools listing ~30 collaterals, and blocks any account whose existing positions plus `N` reach the cap. Debt tokens cannot be pushed (`issue` mints debt to `_msgSender`, `DebtToken.sol:250-262`), so only the deposit-token side is attacker-controllable.

### Impact Explanation
Denial of service on position initiation for a targeted account: the victim cannot add new collateral types or open debt in new synths for as long as the dust positions remain, and the attacker can re-dust after any removal, making the DoS continuous — analogous to the Asterisk attack continuously denying new DTLS-SRTP calls. Secondary effect: `depositOf`/`debtOf` iterate the victim's list (`Pool.sol:274-288`), slightly raising gas for every health check on the account. Impact is "temporary freezing of funds / DoS" class; it does not steal funds directly.

### Likelihood Explanation
Cost is dust deposits (bounded by per-token deposit fees) plus gas for ~`N` deposits+transfers per victim, repeatable for many victims since dust is reusable per token (attacker keeps `balance - 1` and can top up). No privileged role, oracle manipulation, or malicious infrastructure is needed — only public `deposit`/`transfer`. The main constraint is that it only *fully* bricks an account when registered deposit tokens plus the victim's existing entries reach 30; pools with few collaterals only partially fill the list, reducing severity there. `whenNotPaused`/`nonReentrant` guards do not interfere, and SynthContext meta-sender paths (`Operator.execute`) give an alternative delivery vector but are not required.

### Recommendation
- Do not auto-add tokens to `depositTokensOfAccount` on inbound `transfer`/`transferFrom`; only track tokens acquired via `deposit`/`seize`, or make receipt opt-in.
- Alternatively, keep add-on-transfer but exempt sub-dust amounts (e.g., only register when transferred amount ≥ a minimum), or allow `addToDepositTokensOfAccount` to silently skip rather than revert when the cap is hit and let `deposit` itself enforce the cap only for minting.
- Consider removing entries on outbound dust transfers regardless of residual balance threshold, so victims can cheaply evict forced entries.

### Proof of Concept
Reproducible in Hardhat/Foundry fork (mock oracle prices as in `test/Pool.test.ts`):

```solidity
// attacker deposits 2 wei of each registered collateral, keeps 1, sends 1 to victim
for each msdX in pool.getDepositTokens() {
    underlyingX.approve(msdX, 2);
    msdX.deposit(2, attacker);                 // DepositToken.sol:211
    msdX.transfer(victim, 1);                  // adds msdX to victim list (DepositToken.sol:517-520)
}
// victim list length == N (registered deposit tokens)
// once debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30:
msdNew.deposit(amount, victim);                // reverts UserReachedMaxTokens (Pool.sol:144-146)
debtTokenY.issue(amount, victim);              // reverts UserReachedMaxTokens via addToDebtTokensOfAccount
```

Assumptions/limitations not fully verifiable from the index: the exact number of registered deposit tokens per deployed pool determines whether a fresh account can be fully capped (cap is 30; `addDepositToken` allows up to 30 tokens). If the deployed pool has fewer than ~30 deposit tokens and the victim has no existing positions, the attack only partially fills the list rather than fully blocking — the DoS then requires the victim to already hold some positions, which still satisfies the "deny new position initiation" class for those users.
