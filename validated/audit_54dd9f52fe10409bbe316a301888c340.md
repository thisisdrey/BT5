### Title
`LinkRepositoryToObjectPool` links an arbitrary repository to an arbitrary object pool without verifying they belong to the same fork network - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` accepts two independently-supplied identifiers — a `repository` (target) and an `object_pool` (additional repository) — and unconditionally writes the pool's path into the repository's `objects/info/alternates` file. Unlike other object-pool relationships that are supposed to be scoped to a single fork network (source repo → pool → forks of that repo), this RPC never checks that the `object_pool` actually originated from, or is otherwise associated with, the `repository` being linked. This mirrors the reported `addLiquidity()` flaw, where an operation that should only apply to a caller-owned resource instead accepts an arbitrary counterpart parameter with no cross-reference check.

### Finding Description
The handler resolves the pool and repository independently and links them with no relationship check: [1](#0-0) 

`poolForRequest` only validates that the supplied `object_pool` points to a structurally valid pool repository (i.e. it passes `objectpool.FromProto`/`IsPoolRepository`-style checks) — it performs no check that the pool was created from, or is otherwise entitled to serve, the `repository` parameter: [2](#0-1) 

The low-level `Link` function that actually performs the write is likewise agnostic to provenance. It only refuses to overwrite an alternates file that already points to a *different* pool; it never asks "is this pool associated with this repository": [3](#0-2) 

By contrast, `CreateObjectPool` and `CreateFork` establish the pool/fork relationship explicitly at creation time via the `origin`/`source_repository` fields [4](#0-3) , but `LinkRepositoryToObjectPool` is a standalone follow-up RPC that re-derives the pool purely from caller-supplied protobuf fields and never re-validates that binding. This is analogous to `addLiquidity()` trusting a caller-supplied `router` address instead of deriving it from `msg.sender`/an established relationship — the RPC trusts caller-supplied linkage between two independent identifiers instead of verifying it against the authoritative origin relationship recorded at pool-creation time.

### Impact Explanation
Linking a repository to an object pool causes Git to treat the pool's objects directory as an alternate object store for that repository (via `objects/info/alternates`), and `Link` additionally strips the repository's own bitmap. Any client capable of invoking `LinkRepositoryToObjectPool` with a `repository` it can write to, and a `object_pool` reference to a repository/object pool it does not own (only needing to know its storage name and relative/replica path), can:
- Attach an unrelated pool to its own repository, causing objects from that pool to become locally resolvable/fetchable through the linked repository (cross-repository object exposure), and
- Corrupt the state of unrelated pools/members by triggering `removeMemberBitmaps` or subsequent housekeeping operations against a pool it has no legitimate relationship with.

This lines up with the "cross-repository object access" bug class called out as an acceptable analog, and with the root cause pattern of the reported bug: a mutating RPC operates on a caller-supplied identifier belonging to another entity without verifying the caller/target is entitled to that relationship.

### Likelihood Explanation
`LinkRepositoryToObjectPool` is a normal, exposed Gitaly RPC (`ObjectPoolService`) reachable by any client that can address a `repository` and an `object_pool` by storage name and relative path — both are ordinary protobuf fields, not privileged tokens. No additional authorization beyond `ValidateRepository`/pool-format validation is performed at the Gitaly layer itself.

### Recommendation
When linking, verify that the `object_pool` was actually derived from (or is otherwise explicitly authorized for) the `repository` being linked — e.g., by checking recorded pool-membership/origin metadata (as tracked for forks/pools at creation time) rather than trusting the caller-supplied pair of identifiers at link time. Reject the request if no such association exists.

### Proof of Concept
1. Create repository `A` and object pool `P_A` from `A` via `CreateObjectPool` (origin = A).
2. Create an unrelated repository `B` (no fork/origin relationship to `A` or `P_A`).
3. Call `LinkRepositoryToObjectPool(repository = B, object_pool = P_A)`.
4. Observe the call succeeds (as demonstrated by the existing "successful" test case pattern in `internal/gitaly/service/objectpool/link_test.go` lines 133-139, which performs exactly this call shape with no provenance check), and `B`'s `objects/info/alternates` now points at `P_A`'s object directory, exposing `P_A`'s objects to `B`. func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}
