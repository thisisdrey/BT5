Based on my investigation, I found a valid analog: certificate blocklisting in nebula is only enforced at handshake time and periodically via the connection manager's traffic-check timer — not on every data packet — which mirrors the Sherlock finding that blacklisting doesn't stop already-flowing transactions until an explicit enforcement step runs.

### Title
Blocklisted certificates continue to transact on already-established tunnels until the next periodic check - (File: connection_manager.go)

### Summary
Nebula's certificate blocklist (`pki.blocklist`, `CAPool.certBlocklist`) is only consulted in two places: during certificate verification at handshake time (`cert.CAPool.verify` / `VerifyCertificate`) [1](#0-0) , and during the connection manager's periodic `isInvalidCertificate` check, which runs from the traffic timer wheel on an interval controlled by `timers.connection_alive_interval` (default 5s) [2](#0-1) . The data-plane packet path in `readOutsidePackets`/`handleOutsideMessagePacket` decrypts and forwards traffic based solely on `hostinfo.ConnectionState` and firewall rules — it never re-checks `CAPool.IsBlocklisted`/`VerifyCachedCertificate` per packet [3](#0-2) .

### Finding Description
Once a peer certificate has been added to the blocklist mid-session (via `pki.blocklist` config reload or an operator invoking `BlocklistFingerprint`), an already-established tunnel to that peer is not immediately closed. The tunnel keeps decrypting and forwarding data (`hostinfo.ConnectionState.Decrypt`, then firewall check, then write to tun) for every inbound packet until `connectionManager.makeTrafficDecision` fires for that `localIndex` and calls `isInvalidCertificate`, which is the only runtime consumer of `cert.ErrBlockListed` outside of the handshake path [4](#0-3) . This is directly analogous to the Stablecoin bug where `_update` never checked `blacklisted(from)`/`blacklisted(to)`, so blacklisting only affected balance seizure but not ongoing transfers — here, blocklisting a fingerprint only affects new handshake verification and CA-pool checks, not the live data path, so the enforcement is deferred to a background timer rather than being synchronous with traffic.

### Impact Explanation
This is a remote-state/enforcement-bypass style issue: a certificate that the operator believes is blocked can continue to send and receive encrypted application traffic across an existing tunnel for up to `checkInterval` (and, if the tunnel is on the non-primary path or the check races with `shouldSwapPrimary`/`migrateRelays` logic, longer) after being blocklisted. For a security feature whose entire purpose is to immediately stop an untrusted host from communicating (e.g., a compromised or malicious node's cert), a window during which it can still transact is a meaningful weakening of that control, mirroring the "manually administered security feature" medium-impact classification in the original report.

### Likelihood Explanation
This requires no attacker action beyond having previously completed a valid handshake before being blocklisted — it is a design/timing gap rather than a crafted-packet exploit, so likelihood of the window existing is high (it happens on every blocklist event against an active tunnel) but the impact window is bounded by `checkInterval`.

### Recommendation
Enforce the blocklist synchronously on the data path, not only at handshake and on the periodic timer: check `IsBlocklisted`/`VerifyCachedCertificate` (or at least the blocklist subset) for the relevant `hostinfo.GetCert()` fingerprint in `readOutsidePackets` before decrypting/forwarding, or trigger an immediate `closeTunnel` sweep across all active `HostInfo`s whenever `BlocklistFingerprint`/`pki.blocklist` is updated, instead of waiting for the next `trafficTimer` tick per `localIndex`.

### Proof of Concept
1. Establish a tunnel between host A and host B with valid certs signed by a common CA.
2. While the tunnel is active and passing traffic, add B's certificate fingerprint to A's `pki.blocklist` and trigger a config reload (`loadCAPoolFromConfig` calls `caPool.BlocklistFingerprint(fp)` for each configured entry [5](#0-4) ).
3. Continue sending data packets from B to A immediately after the reload. Because `readOutsidePackets` decrypts/forwards without consulting the blocklist [6](#0-5) , packets keep flowing until `connectionManager`'s next tick for that `localIndex` invokes `isInvalidCertificate` and issues `closeTunnel` [7](#0-6) , demonstrating the "still transacts after blacklisting" window.

func (cm *connectionManager) makeTrafficDecision(localIndex uint32, now time.Time) (trafficDecision, *HostInfo, *HostInfo) {
	// Read lock the main hostmap to order decisions based on tunnels being the primary tunnel
	cm.hostMap.RLock()
	defer cm.hostMap.RUnlock()

	hostinfo := cm.hostMap.Indexes[localIndex]
	if hostinfo == nil {
		cm.l.Debug("Not found in hostmap", "localIndex", localIndex)
		return doNothing, nil, nil
	}

	if cm.isInvalidCertificate(now, hostinfo) {
		return closeTunnel, hostinfo, nil
	}

// isInvalidCertificate decides if we should destroy a tunnel.
// returns true if pki.disconnect_invalid is true and the certificate is no longer valid.
// Blocklisted certificates will skip the pki.disconnect_invalid check and return true.
func (cm *connectionManager) isInvalidCertificate(now time.Time, hostinfo *HostInfo) bool {
	remoteCert := hostinfo.GetCert()
	if remoteCert == nil {
		return false //don't tear down tunnels for handshakes in progress
	}

	caPool := cm.intf.pki.GetCAPool()
	err := caPool.VerifyCachedCertificate(now, remoteCert)
	if err == nil {
		return false //cert is still valid! yay!
	} else if err == cert.ErrBlockListed { //avoiding errors.Is for speed
		// Block listed certificates should always be disconnected
		hostinfo.logger(cm.l).Info("Remote certificate is blocked, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else if cm.intf.disconnectInvalid.Load() {
		hostinfo.logger(cm.l).Info("Remote certificate is no longer valid, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else {
		//if we reach here, the cert is no longer valid, but we're configured to keep tunnels from now-invalid certs open
		return false
	}
}
