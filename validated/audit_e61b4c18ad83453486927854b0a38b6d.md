### Title
Unstaked QUIC connections keyed by ephemeral self-signed pubkey bypass per-peer connection cap via identity churn - ([File: streamer/src/nonblocking/quic.rs])

### Summary
Agave's QUIC transport requires every client to present a self-signed TLS certificate, from which `get_remote_pubkey` always extracts `Some(pubkey)`. Because `ConnectionTableKey::new` builds its key from `remote_pubkey` whenever it is `Some`, independent of whether `get_connection_stake` resolves the peer to `ConnectionPeerType::Unstaked`, an attacker who mints a fresh keypair per connection is treated as a brand-new "peer" in the `unstaked_connection_table` `IndexMap` each time, sidestepping the `max_connections_per_peer` cap that is enforced per-key rather than per-IP.

### Finding Description
`ConnectionTableKey::new(remote_address, remote_pubkey)` produces `ConnectionTableKey::Pubkey(pubkey)` whenever a TLS-negotiated pubkey is present, and only falls back to `ConnectionTableKey::IP(remote_address)` when `remote_pubkey` is `None`. Because Solana's QUIC transport mandates a self-signed client certificate for every connection (staked or not), `remote_pubkey` is essentially always `Some`, so the keying decision does not actually depend on stake status — an unstaked attacker's connections are keyed by `Pubkey` in `try_add_connection` just like staked peers, not aggregated by source `IP`. Since `try_add_connection`'s `max_connections_per_peer` check operates on the vector stored under a single `IndexMap` key, an attacker who generates a new ephemeral keypair for every QUIC handshake causes each connection to land under a distinct, never-before-seen key, so the per-key cap check always sees an empty/short vector and admits the new connection. The only remaining backstop is the *total* size limit of the `unstaked_connection_table` (LRU eviction once the table is full), which is a global capacity limit shared by all unstaked peers — not a per-IP or per-peer limit as the invariant claims. This lets one attacker (from one or many source IPs) consume a disproportionate share of the shared unstaked table capacity by churning identities, crowding out other legitimate unstaked peers from connecting to the TPU port.

### Impact Explanation
This is a QoS/admission-control evasion: the per-peer connection cap intended to give fair, bounded access to the unstaked capacity pool can be bypassed by identity churn, letting a single unprivileged attacker capture a disproportionate share of TPU unstaked connection slots and streams, degrading transaction ingress fairness/availability for other unstaked clients. This matches the "QoS evasion" / unfair capacity capture bounty category rather than a data-integrity or consensus-safety bug.

### Likelihood Explanation
Fully attacker-controlled and cheap: generating an ed25519 keypair and presenting it as a QUIC/TLS client identity requires no stake, no validator cooperation, and can be done in a tight loop without cryptographic or economic cost. The only limiting factor is the global unstaked table size and connection-rate limiter, meaning the technique is highly repeatable within those bounds.

### Recommendation
Key `ConnectionTableKey` (or at minimum enforce `max_connections_per_peer`/`max_connections_per_ip`) based on remote IP address for connections resolved to `ConnectionPeerType::Unstaked`, reserving `Pubkey`-based keying for peers that are actually confirmed staked via `get_connection_stake`. This ensures the per-peer cap cannot be evaded merely by rotating self-generated identities.

### Proof of Concept
```rust
// streamer/src/nonblocking/quic.rs (test module)
#[test]
fn test_unstaked_key_falls_back_to_ip_not_pubkey() {
    let ip = IpAddr::from([127, 0, 0, 1]);
    let pubkey = Some(Pubkey::new_unique());
    let peer_type = ConnectionPeerType::Unstaked;
    let key = ConnectionTableKey::new_for_peer_type(ip, pubkey, peer_type);
    // Expect IP keying for unstaked peers regardless of presented pubkey
    assert_eq!(key, ConnectionTableKey::IP(ip));
}

#[tokio::test]
async fn test_unstaked_identity_churn_cannot_exceed_per_ip_cap() {
    let mut table = ConnectionTable::new();
    let ip = IpAddr::from([127, 0, 0, 1]);
    let max_connections_per_peer = 4;
    for _ in 0..100 {
        let pubkey = Some(Pubkey::new_unique()); // fresh identity each iteration
        let key = ConnectionTableKey::new(ip, pubkey); // current (buggy) behavior
        table.try_add_connection(
            key, ip, 0, None, ConnectionPeerType::Unstaked, 0, max_connections_per_peer,
        );
    }
    // Aggregate count of unstaked connections from this IP should not exceed
    // max_connections_per_peer, but with pubkey-keying it will reach 100.
    let total_from_ip = table.total_connections_from_ip(ip);
    assert!(total_from_ip <= max_connections_per_peer,
        "per-IP cap bypassed via identity churn: {total_from_ip} connections admitted");
}
```
Expected result with current code: the second test fails because `total_from_ip` reaches 100 (bounded only by table capacity, not `max_connections_per_peer`), demonstrating the bypass. After applying the fix (IP-keying for unstaked peers), the assertion passes.
