### Title
StackerDB chunk signature omits target StackerDB contract identity, enabling cross-contract signature-wrapping replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the signed digest as `hash(slot_id || slot_version || data_hash)` and never binds the signature to the specific StackerDB smart-contract instance (`contract_id`) the chunk is meant for. All of the write-acceptance paths (`StackerDBTx::try_replace_chunk`, `PeerNetwork::validate_received_chunk`, `StackerDBSync::validate_downloaded_chunk`) verify only `slot_id`, `slot_version`, `data_hash`, and the signer address recorded for *that* contract — they never check that the signature was produced with intent for that particular `contract_id`. Because multiple independent StackerDB replicas (e.g. the various `signers-(0|1)-N` message-lane contracts) are provisioned from the *same* address→slot_id assignment (`stackerdb-get-signer-slots-page`, keyed only by reward-cycle parity, in `stackslib/src/chainstate/stacks/boot/signers.clar`), a validly-signed chunk broadcast/observed for one contract is cryptographically indistinguishable from a chunk intended for a different contract sharing that same slot layout. This is the direct analog of the SAML XML "signature wrapping" bug class: a signature is accepted as authenticating content in a context (contract/document) it was never made for, because the digest fails to include a domain/context separator.

### Finding Description
`SlotMetadata::auth_digest` [1](#0-0)  only hashes `slot_id`, `slot_version`, and `data_hash` — the `contract_id`/smart-contract identifier of the StackerDB the chunk is destined for is never part of what is signed or verified in `SlotMetadata::verify` [2](#0-1) .

Server-side acceptance in `StackerDBTx::try_replace_chunk` looks up the expected signer for `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` [3](#0-2)  — it never checks that the signature itself commits to `smart_contract`. Likewise, the P2P inbound-chunk validator `PeerNetwork::validate_received_chunk` fetches the expected signer for `smart_contract_id`/`slot_id` and calls `slot_metadata.verify(&addr)` [4](#0-3) , and `StackerDBSync::validate_downloaded_chunk` simply forwards to the same routine [5](#0-4) .

Slot-to-address assignment for the signer StackerDB families is derived from a single shared table per reward-cycle parity (`stackerdb-signer-slots-0` / `stackerdb-signer-slots-1`), explicitly documented as being reused by *all* `.signers-(0|1)-xxx` contracts: `"called by .signers-(0|1)-xxx contracts to get the signers for their respective signing sets"` [6](#0-5) . Consequently, the same `StacksAddress` occupies the identical `slot_id` in every message-lane contract for a given cycle parity.

The only place that distinguishes *which* signer-message contract a chunk's payload is meant for is an application-layer, client-side heuristic (`signer_message_payload_matches_lane`) applied when converting a `StackerDBChunksEvent` into a `SignerEvent` [7](#0-6)  — explicitly noted in-code as fragile ("the mapping ... is fixed to v0 ... future signer-message versions must extend that mapping, or their chunks will not be recognized here"). This check happens only after the chunk has already been accepted and durably stored by the node's StackerDB replication layer (`try_replace_chunk`/`validate_received_chunk`); it is not enforced as part of signature/authorization validation at write time.

As a result, an unprivileged network peer that observes a validly-signed `StackerDBPushChunk` for one contract (e.g. via ordinary p2p gossip, which requires no special privilege to observe or relay) can replay the identical `(slot_id, slot_version, sig, data)` tuple as a `StackerDBPushChunk` targeting a *different* smart-contract StackerDB that happens to assign the same signer address to the same `slot_id` (all sibling `.signers-(0|1)-xxx` contracts for that cycle parity). Since the digest never encodes `contract_id`, the signature verifies and the write succeeds, storing attacker-selected — but not attacker-forged — content into the wrong StackerDB replica/slot.

### Impact Explanation
This breaks the equality "signed-for-this-StackerDB" vs. "signed-for-any-StackerDB-with-the-same-slot-layout," resulting in unauthorized cross-contract writes of otherwise-legitimate signed data into a StackerDB slot that the signer never intended to write to at that moment. This can pollute a different message lane (e.g., injecting a stale/foreign `BlockResponse` chunk into a `StateMachineUpdate` lane's slot, or vice versa) that downstream node/relayer logic consumes, causing state confusion, spurious acceptance/rejection signals, or denial of expected updates for that signer's slot in the wrong contract — a form of forged/mismatched data propagation across the network via StackerDB replication (matches the "High" bar: mismatch of StackerDB data served/stored as canonical for the wrong context).

### Likelihood Explanation
Exploitability requires no private key and no special role: the attacker only needs to observe a legitimately-broadcast chunk (which travels over the unauthenticated p2p StackerDB push/replication mechanism) and re-send it, unmodified, as a push targeted at a sibling contract sharing the victim signer's slot assignment. The chunk-version/staleness and chunk-size checks in `try_replace_chunk`/`validate_received_chunk` are the only other gates, and both are satisfiable by picking an appropriate target contract/slot state. The precondition — multiple StackerDB contracts sharing identical address→slot_id layouts — is structurally guaranteed by the current signer-slot design (`signers.clar`), not an edge case.

### Recommendation
Include the target `contract_id` (and ideally a chain/network domain separator) inside `SlotMetadata::auth_digest()` so that a signature only authenticates a chunk for the specific StackerDB smart contract it was created for. This requires re-plumbing `sign`/`verify` (and any wire format that already commits to signature bytes without contract context) to take the `QualifiedContractIdentifier` as an explicit signed field, then updating all callers (`try_replace_chunk`, `validate_received_chunk`, `validate_downloaded_chunk`, and libsigner's `StackerDBChunkData::sign`/`recover_pk`) accordingly. This is a wire/protocol-level change and needs careful cross-version rollout planning.

### Proof of Concept
1. Set up two sibling StackerDB contracts for the same reward-cycle parity (e.g. `signers-0-1` and `signers-0-2`) that share the same `(address, slot_id)` layout, as produced by `stackerdb-set-signer-slots` / `stackerdb-get-signer-slots-page` in `signers.clar`.
2. Have a legitimate signer sign and push a chunk `C` (`slot_id=k`, `slot_version=v`, `data=D`) to `signers-0-1` via `StackerDBPushChunkData`; this is accepted by `try_replace_chunk`/`validate_received_chunk` because the address owns slot `k` there.
3. As an unprivileged observer of this chunk on the p2p network, replay the exact same `StackerDBChunkData` (same `sig`, `slot_id`, `slot_version`, `data`) inside a new `StackerDBPushChunkData` whose `contract_id` is `signers-0-2` instead, adjusting only the (unsigned) `rc_consensus_hash` to match `signers-0-2`'s current view.
4. Observe that `PeerNetwork::validate_received_chunk` / `StackerDBTx::try_replace_chunk` accept and store the chunk into `signers-0-2`'s slot `k`, even though it was never signed with intent for that contract — because `SlotMetadata::verify` [2](#0-1)  only checks `slot_id`/`slot_version`/`data_hash` against the recovered signer, not `contract_id`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )

    }
