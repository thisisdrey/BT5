### Title
Liquidation-triggered bad-debt socialization aborts entire liquidation if any single debt-asset's vault call fails - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate()` bundles socialization of *all* of a borrower's remaining debt assets into one atomic `fold` when the borrower's last collateral is seized. If the vault call for any one of those bundled debt assets fails (e.g. that vault is paused, or otherwise reverts), the `unwrap!` inside `socialize-debt-asset` propagates a failure that causes the entire `liquidate()` call to abort via `ERR-BAD-DEBT-SOCIALIZATION-FAILED`, even though the specific debt/collateral pair being liquidated was otherwise fully valid. This mirrors the "reward claim loop depends on one paused/failing token" class of bug: an unrelated asset's failure blocks an otherwise-healthy, unrelated operation bundled with it in the same transaction.

### Finding Description
In `liquidate()`, once collateral is fully seized (`no-collateral-left`), the contract collects the borrower's remaining debt list and runs a `fold` over every remaining debt asset: [1](#0-0) 

Each entry is processed by `socialize-debt-asset`, which performs, per asset, three chained calls—`vault-socialize-debt`, a `vault-accrue` cache refresh, and `debt-remove-scaled` on `v0-market-vault`—each wrapped in `unwrap!`: [2](#0-1) 

If any one of these calls for *any* debt asset in the list returns an error (for example, a target vault contract is paused/misbehaving, or `vault-accrue`/`debt-remove-scaled` reverts for that asset), `socialize-debt-asset` short-circuits and returns `{ success: false }` and any subsequent debt entries are skipped (`if (not (get success acc)) acc`). The `success` flag then flows back to `liquidate()`: [3](#0-2) 

`(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` reverts the *whole* `liquidate()` call — including the debt-repay (`vault-system-repay`) and collateral-seizure (`collateral-remove`) that already succeeded for the primary, healthy debt/collateral pair being liquidated. This is architecturally identical to the reported bug class: multiple distinct assets/reward-streams are bundled into a single atomic loop, and a fault on any one of them (analogous to a pausable ERC20 blocking `IERC20.transfer`) blocks the entire operation, even parts unrelated to the faulting asset.

The identical pattern exists in the `local-testing` mirror at `market.clar`: [4](#0-3) 

### Impact Explanation
When a borrower's last unit of collateral is seized and they still carry debt in one or more other assets, `liquidate()` requires *all* of those other debt-asset vaults to successfully process `vault-socialize-debt` in the same atomic transaction. If any one of the borrower's other debt-bearing vaults is paused, reverts, or otherwise fails at that moment, liquidators cannot complete liquidation of the position at all — the entire transaction, including the seizure that should have succeeded, is rolled back. This causes: (a) temporary freezing of the ability to liquidate/close out an unhealthy position (freezing of the liquidator's expected proceeds and blocking risk resolution for the protocol), and (b) the underlying bad debt for the position remains un-socialized/unremoved, so the protocol continues to carry uncollected losses instead of writing them down — this is a temporary freezing-of-funds impact under the market's core debt-accounting/socialize-debt logic, which is explicitly in scope per the rules.

### Likelihood Explanation
This requires the borrower to hold debt in more than one asset (multi-debt egroup position) and for at least one of the debt-asset vaults to be paused or fail at the exact moment their last collateral gets liquidated. This is a plausible operational scenario: admins can pause a vault's public operations at any time for maintenance/incident response, and if a borrower happens to owe debt in that vault at the moment they're fully liquidated elsewhere, the liquidation atomically fails. Because socialize-debt-asset unwraps on any vault-level failure (not just an explicit "pause" state), any transient vault-level revert for one of several bundled debt assets is sufficient to block the whole liquidation — a scenario judged Medium severity in the analogous audit finding due to reliance on external/operational conditions.

### Recommendation
Do not make successful liquidation of the primary debt/collateral pair contingent on the *all-or-nothing* success of socializing every other debt asset in the same transaction. Instead: (1) attempt socialization for each remaining debt asset independently and continue processing the others even if one fails (already partially done via the `success` accumulator, but the flag should not gate reverting the whole `liquidate()` call), or (2) decouple bad-debt socialization into a separate, retryable, permissionless follow-up call (e.g. `socialize-bad-debt(borrower)`) that can be invoked once problematic vaults are unpaused, rather than requiring it to complete atomically inside `liquidate()`.

### Proof of Concept
1. Borrower has collateral in asset A and debt in both asset B (USDC) and asset C (USDH).
2. Admin pauses vault C (`v0-vault-usdh`) for maintenance (a legitimate, non-malicious admin action, not a DAO compromise).
3. Liquidator calls `liquidate(borrower, A, B, debtAmountB, ...)` to fully seize collateral A and repay debt B. Debt B repayment (`vault-system-repay`) and collateral A removal succeed.
4. Because `no-collateral-left` is true, the code proceeds to socialize remaining debt (asset C) via `fold socialize-debt-asset`.
5. `vault-socialize-debt` (or `vault-accrue`) for vault C fails because vault C is paused, `unwrap!` triggers `failed-status`, `success` becomes `false`.
6. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` reverts the entire `liquidate()` call, rolling back the otherwise-valid seizure of collateral A and repayment of debt B.
7. Until vault C is unpaused, this borrower's position (already unhealthy in the debt B/collateral A pair) cannot be liquidated at all, leaving bad debt unresolved on-chain.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
