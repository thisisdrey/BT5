### Title
Bridged synthetic tokens can be stranded when `maxBridgedInSupply` is saturated before destination mint - (File: contracts/SyntheticToken.sol)

### Summary

An unprivileged attacker can temporarily strand a victim’s bridge transfer by filling the destination chain’s `maxBridgedInSupply` before the victim’s LayerZero message is executed. The victim’s tokens are burned on the source chain by `ProxyOFT._debitFrom()`, but the destination mint reverts inside `SyntheticToken._mint()` and is only stored as a retryable failed message. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`ProxyOFT.sendFrom()` performs the source-chain debit before dispatching the LayerZero message, and `_debitFrom()` burns the sender’s synthetic tokens after checking only that bridging and the destination route are active. [4](#0-3) [1](#0-0) 

On the destination chain, `_sendAck()` calls `_creditTo()`, which delegates to `SyntheticToken.mint()`. [5](#0-4) [6](#0-5) 

When the caller is `proxyOFT`, `_mint()` increments `totalBridgedIn` and reverts if the resulting net `bridgedInSupply()` exceeds `maxBridgedInSupply`. [7](#0-6) [8](#0-7) 

`NonblockingLzAppUpgradeable` catches that destination failure and stores the payload hash instead of minting or refunding the source-chain burn. [9](#0-8) 

`retryMessage()` can later execute the stored payload, but it reverts again as long as the bridge-in cap remains saturated. [10](#0-9) 

Because `lzReceive()` accepts any valid message delivered by the configured endpoint from a trusted remote path, an attacker can use their own legitimate bridge transfer to consume the available cap before the victim’s message is delivered. [11](#0-10) 

### Impact Explanation

The victim’s source-chain synthetic tokens are irreversibly burned once `sendFrom()` succeeds, while the corresponding destination-chain mint can be forced to remain pending in `failedMessages`. [1](#0-0) [10](#0-9) 

This temporarily freezes the victim’s bridged funds and breaks the expected burn-to-mint completion window until net bridged-in supply is reduced or the cap is raised. [8](#0-7) [7](#0-6) 

### Likelihood Explanation

The attacker needs only synthetic tokens, the LayerZero fee, and the ability to get a valid inbound message executed before the victim’s message. [12](#0-11) [11](#0-10) 

A same-route attacker must use an earlier nonce, while a different trusted source route can compete independently for the shared `maxBridgedInSupply` limit. [13](#0-12) [14](#0-13) 

### Recommendation

Avoid treating the bridge-in cap as a reason to permanently hold an otherwise valid credited transfer. Either reserve the destination cap at source-debit time, allow failed PT_SEND payloads to credit into an explicit escrow/refund state, or add a separate admin-controlled claim path that can mint or reimburse stored failed transfers after accounting for the source burn. [10](#0-9) [6](#0-5) 

### Proof of Concept

```solidity
// Foundry destination-chain fork test.
function test_BridgeInCapCanStrandVictim() public {
    ProxyOFT oft = ProxyOFT(DEPLOYED_PROXY_OFT);
    SyntheticToken synth = SyntheticToken(oft.token());
    address endpoint = address(oft.lzEndpoint());

    uint16 srcChain = SRC_LZ_CHAIN_ID;
    bytes memory srcAddress = abi.encodePacked(REMOTE_PROXY_OFT, address(oft));

    uint256 cap = synth.maxBridgedInSupply();
    uint256 available = cap - synth.bridgedInSupply();

    // Attacker's valid earlier message consumes all remaining cap.
    bytes memory attackerPayload =
        abi.encode(uint16(0), abi.encodePacked(attacker), available);
    vm.prank(endpoint);
    oft.lzReceive(srcChain, srcAddress, 1, attackerPayload);
    assertEq(synth.bridgedInSupply(), cap);

    // Victim already burned tokens on the source chain. Delivery cannot mint.
    bytes memory victimPayload =
        abi.encode(uint16(0), abi.encodePacked(victim), victimAmount);
    vm.prank(endpoint);
    oft.lzReceive(srcChain, srcAddress, 2, victimPayload);

    assertEq(synth.balanceOf(victim), 0);
    assertGt(uint256(oft.failedMessages(srcChain, srcAddress, 2)), 0);

    // The retry remains unavailable while bridgedInSupply is saturated.
    vm.expectRevert(SurpassMaxBridgingSupply.selector);
    oft.retryMessage(srcChain, srcAddress, 2, victimPayload);
}
```

The source-side half of the same transfer is guaranteed to burn the victim before dispatch because `_send()` calls `_debitFrom()` before `_lzSend()`, and `_debitFrom()` calls `syntheticToken.burn()`. [4](#0-3) [1](#0-0)

    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
