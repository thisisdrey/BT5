### Title
Missing 24-hour reward-withdrawal cooldown in TVM `withdrawreward` opcode path lets contracts bypass the throttle enforced by `WithdrawBalanceActuator` - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java])

### Summary
This is the java-tron analog of the Illuminate report: the same underlying operation (withdrawing an SR/voter's accrued reward `allowance` into spendable `balance`) is reachable through two different entry points, but a security/rate-limiting check present in one path (`WithdrawBalanceActuator`) is missing from the other (`WithdrawRewardProcessor`, reached via the TVM `withdrawreward` opcode).

### Finding Description
`WithdrawBalanceActuator.validate()` enforces several checks before allowing a reward withdrawal, including a 24-hour cooldown between withdrawals: [1](#0-0) 

This uses `dynamicStore.getWitnessAllowanceFrozenTime() * FROZEN_PERIOD` compared against `accountCapsule.getLatestWithdrawTime()` to reject a second withdrawal within the frozen window, and also rejects withdrawal when there is no allowance/reward to claim.

The same "withdraw reward" functionality is also reachable from a smart contract via the TVM `withdrawreward` opcode, implemented in `OperationActions.withdrawRewardAction` → `Program.withdrawReward()` → `WithdrawRewardProcessor`: [2](#0-1) 

`WithdrawRewardProcessor.validate()` only checks that the address is not a genesis-block guard representative; it does **not** check `latestWithdrawTime`/`witnessAllowanceFrozenTime`, nor does it reject a zero/negative allowance (it just returns 0 silently): [3](#0-2) 

Compare this directly to the actuator's equivalent checks that are absent here: [4](#0-3) 

This mirrors the reported bug class exactly: `redeem` (the primary, fully-guarded entry point) vs. `autoRedeem`/`authRedeem` (alternate entry points missing the `unpaused` guard) — here, `WithdrawBalanceContract` (fully-guarded, including the 24h cooldown) vs. the TVM `withdrawreward` opcode / `WithdrawRewardProcessor` (missing the cooldown guard).

### Impact Explanation
Any account can deploy a trivial contract that calls the `withdrawreward` TVM opcode in a loop across many transactions (each is a separate top-level transaction, since the account being credited is `getContextAddress()` — the calling contract/account itself) to withdraw its accrued `allowance` into `balance` without respecting the `witnessAllowanceFrozenTime` cooldown that the protocol otherwise enforces on `WithdrawBalanceContract`. This is a rate-limit/anti-abuse control bypass on-chain: an account can withdraw voting rewards far more frequently than the protocol's documented 24-hour throttle allows, undermining consensus-parameter enforcement (`getWitnessAllowanceFrozenTime`) that the actuator path enforces uniformly. It does not appear to allow the withdrawal of more total reward than is legitimately owed (accounting math is otherwise per the `VoteRewardUtil`/`MortgageService` reward algorithm), so the "theft of funds" bar may not be met, but it is a concrete, reproducible bypass of an on-chain, committee-controlled access-control invariant, achievable by a single unprivileged contract call.

### Likelihood Explanation
High reachability: `withdrawreward` is a normal TVM opcode available to any smart contract once `allowTvmVote` is enabled (a standard, already-active feature flag on mainnet), requiring no special privileges — any account can deploy a contract and call it directly.

### Recommendation
Add the same `witnessAllowanceFrozenTime` / `latestWithdrawTime` cooldown check (and ideally the "no allowance to withdraw" validation) to `WithdrawRewardProcessor.validate()` so behavior for reward withdrawal is consistent regardless of whether it's triggered via `WithdrawBalanceContract` or the TVM `withdrawreward` opcode.

### Proof of Concept
1. Enable `allowTvmVote` (already default-on in current networks) and `allowChangeDelegation`.
2. Deploy a contract whose function calls `address(this).withdrawreward()` (per `RewardBalanceTest`/`VoteTest` patterns already in the test suite, e.g. `withdrawRewardMethod` in `framework/src/test/java/org/tron/common/runtime/vm/VoteTest.java`).
3. From the same account, repeatedly (more than once within the `witnessAllowanceFrozenTime` window) send top-level transactions that trigger this contract's withdraw function.
4. Observe that each call succeeds and drains `allowance` into `balance`, whereas an equivalent sequence of `WithdrawBalanceContract` transactions within the same window would be rejected with "The last withdraw time is ..., less than 24 hours" by `WithdrawBalanceActuator.validate()`.

  public void validate(WithdrawRewardParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();

    boolean isGP = CommonParameter.getInstance()
        .getGenesisBlock().getWitnesses().stream().anyMatch(witness ->
            Arrays.equals(ownerAddress, witness.getAddress()));
    if (isGP) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(ownerAddress)
              + "] is a guard representative and is not allowed to withdraw Balance");
    }
  }

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
