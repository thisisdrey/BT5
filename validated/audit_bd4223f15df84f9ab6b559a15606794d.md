### Title
Firewall CA-scoped rules silently fall through to CA-name matching without verifying the peer's CA is actually trusted - ([File: firewall.go])

### Summary
The Morpho report describes a case where a security-gating parameter (`forceDeallocatePenalty`), when left at its zero/default value, silently removes the authorization check that was supposed to gate a privileged action, letting an unauthenticated actor perform it anyway. The structurally closest analog in Nebula's firewall enforcement path is `FirewallCA.match`, where the `ca_name`-keyed branch performs a lookup via `caPool.GetCAForCert` but never validates the returned signer against the rule's intended CA identity beyond a name match, and more importantly runs this lookup unconditionally after the `CAShas` branch fails, regardless of whether the caller intended a strict `ca_sha`/`ca_name` AND relationship documented in `sanity()`.

### Finding Description
`sanity()` at `firewall.go:1009-1056` documents that rules are evaluated as `port AND proto AND (ca_sha OR ca_name) AND (host OR group OR groups OR cidr) AND local_cidr` [1](#0-0) . In `FirewallCA.match`, the CA-scoped rule tree is checked in this order: first `fc.Any` (rules with no CA restriction), then `fc.CAShas[c.Certificate.Issuer()]` (exact issuer fingerprint match), and finally, unconditionally, `fc.CANames[s.Certificate.Name()]` where `s` comes from `caPool.GetCAForCert(c.Certificate)` [2](#0-1) . `GetCAForCert` only resolves the *issuer field* on the certificate to a CA already present in the pool — it performs no signature or trust-chain verification of its own (`// No signature validation is performed` per its doc comment) [3](#0-2) . `FirewallCA.match` is called only after the packet's peer certificate has already passed `CAPool.VerifyCertificate`, so the certificate is authentic; however, the CA-name resolution step here reuses the *same trust link* (issuer→CA) that was already established during verification, and any rule keyed to `ca_name` becomes reachable by any certificate signed by *any* CA in the pool whose name happens to match the string configured in the rule — including CAs the curator did not intend to grant that specific rule to, since the check is a bare string comparison of `Name()` with no scoping to which CA the rule author actually meant (two different fingerprints could plausibly bear the same CA `Name()` if a compromised/rotated CA in the same pool reuses the name).

This mirrors the `forceDeallocatePenalty=0` bug class: a configuration surface (`ca_name` in a firewall rule) that is intended as an authorization gate silently degrades to a broader-than-intended trust check (name string equality rather than fingerprint-pinned identity) because the underlying lookup (`GetCAForCert`) does no independent verification and the rule evaluator does not defend against multiple pool entries sharing a `Name()`.

### Impact Explanation
If exploited, this allows a certificate signed by an unintended-but-pool-trusted CA (e.g. a CA added for a different purpose, or one that shares a name with the intended CA) to match a firewall allow rule that was scoped via `ca_name` to a specific, narrower CA — a firewall enforcement/authorization bypass reachable purely through certificate content interpretation during packet filtering.

### Likelihood Explanation
Medium: it requires an operator to configure `ca_name`-scoped rules and to have multiple CAs in the pool, but no attacker action beyond presenting a certificate signed by any pool-trusted CA is needed to reach the vulnerable comparison — the check itself is inherently weak (name equality, not fingerprint equality) analogous to the zero-penalty case being reachable by "anyone."

### Recommendation
Scope `ca_name` matching to a specific CA fingerprint resolved at config-load time (as is already done for `ca_sha`) rather than resolving by name at packet-match time via `GetCAForCert`, and reject configurations where multiple CAs in the pool share a `Name()` used in a `ca_name` rule.

### Proof of Concept
Not independently constructible from the indexed context alone — a full config-driven repro (two CA certs sharing a `Name()`, both added to the same `CAPool`, a firewall rule with `ca_name` referencing that name, and a handshake using the certificate signed by the *unintended* CA of the two) would need to be built and run against `firewall_test.go`/`e2e` harnesses to confirm reachability; this is stated as an assumption based on the code paths cited above, not verified by execution.

func (fc *FirewallCA) match(p firewall.Packet, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	if fc == nil {
		return false
	}

	if fc.Any.match(p, c) {
		return true
	}

	if t, ok := fc.CAShas[c.Certificate.Issuer()]; ok {
		if t.match(p, c) {
			return true
		}
	}

	s, err := caPool.GetCAForCert(c.Certificate)
	if err != nil {
		return false
	}

	return fc.CANames[s.Certificate.Name()].match(p, c)
}

// GetCAForCert attempts to return the signing certificate for the provided certificate.
// No signature validation is performed
func (ncp *CAPool) GetCAForCert(c Certificate) (*CachedCertificate, error) {
	issuer := c.Issuer()
	if issuer == "" {
		return nil, fmt.Errorf("no issuer in certificate")
	}

	signer, ok := ncp.CAs[issuer]
	if ok {
		return signer, nil
	}

	return nil, ErrCaNotFound
}
