### Title
RewardsDistributor permanently loses reward emissions while a reward token's supply is zero - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` accrues emissions per second (`tokenSpeeds[token_] * deltaTime`) into a per-share index. When the reward-bearing token's `totalSupply()` is `0`, the accrued ratio is forced to `0`, yet the state timestamp is still advanced. The emissions for the entire zero-supply window are never added to the index and can never be claimed by anyone — the same bug class as the MultiRewards report (rewards emitted with no stakers are lost). No pause, recovery, or sweep mechanism exists for the stranded `rewardToken` balance.

### Finding Description
In `_calculateTokenIndex` (`contracts/RewardsDistributor.sol:197-212`):

```solidity
uint256 _totalSupply = token_.totalSupply();
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
```

When `totalSupply() == 0`, `_ratio = 0`, so `_newIndex` stays flat but `_newTimestamp` is written by `_updateTokenIndex` (`lines 271-282`). The skipped `_tokensAccrued` are gone permanently: they are not carried into a later index update, not credited to any account, and `claimRewards`/`_transferRewardIfEnoughTokens` only ever distributes amounts recorded via `tokensAccruedOf`. Any user who later mints/deposits starts accruing only from the new timestamp.

Reachable state: every DepositToken or DebtToken passes through `totalSupply() == 0` at launch, and again whenever the last holder exits (withdraw/repay/burn, seize, transfer). An unprivileged user cannot force others out, but the loss is triggered by ordinary public calls — e.g., the last depositor calling `withdraw`, or the first depositor arriving only after a long zero-supply period while `speed > 0`. Since `updateBeforeMintOrBurn` is callable by anyone, the timestamp advancement (and hence the permanent skip) cannot even be deferred.

### Impact Explanation
Reward tokens are permanently stranded inside `RewardsDistributor` for every second a reward token had `speed > 0` and zero supply. This is permanent freezing/loss of unclaimed yield proportional to the zero-supply duration; there is no function to recover or re-emit the skipped emissions.

### Likelihood Explanation
Low-to-medium. It requires a configured `tokenSpeeds[token] > 0` while the corresponding DepositToken/DebtToken has zero supply — guaranteed at initialization before the first deposit and after any full exit. Loss magnitude scales with how long supply stays at zero and the configured speed.

### Recommendation
Do not advance `TokenState.timestamp` when `totalSupply() == 0` (i.e., freeze accrual time while there are no holders), or carry the unallocated `_tokensAccrued` forward into a later accrual epoch. Alternatively, add a governance sweep to recover emissions accrued during zero-supply windows so they can be re-notified.

### Proof of Concept
```solidity
// Foundry-style PoC against contracts/RewardsDistributor.sol
function test_rewardsLostWhileZeroSupply() public {
    // msToken: a DepositToken/DebtToken registered with speed > 0
    IERC20 msToken = depositToken; // reward-bearing token
    uint256 speed = 1 ether;

    // governor configures emissions while supply == 0 (pre-launch or after full exit)
    vm.prank(governor);
    rewardsDistributor.updateTokenSpeed(msToken, speed);

    // let emissions run with no holders
    skip(1 weeks);
    // anyone can poke the index; timestamp advances, index does not
    rewardsDistributor.updateBeforeMintOrBurn(msToken, address(0xdead));
    (uint224 index1, uint32 ts1) = rewardsDistributor.tokenStates(msToken);

    // a user now mints/deposits -> nonzero supply
    vm.startPrank(alice);
    stakingToken.approve(address(pool), type(uint256).max);
    pool.deposit(address(depositToken), 100 ether); // mints msToken to alice
    vm.stopPrank();

    skip(1 weeks);
    rewardsDistributor.claimRewards(alice, toArray(msToken));

    // Alice only earned the second week's emissions.
    // speed * 1 week of rewards emitted during zero supply are stranded:
    // no account index can ever reference them, and there is no sweep function.
    (uint224 index2,) = rewardsDistributor.tokenStates(msToken);
    assertGt(index2, index1);                       // accrual resumes
    assertEq(rewardsDistributor.claimable(alice, msToken), speed * 1 weeks); // only post-deposit
    // stranded: speed * 1 week of rewardToken sits in the distributor, unclaimable forever
}
```
