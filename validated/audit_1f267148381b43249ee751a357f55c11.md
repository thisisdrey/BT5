The root cause pattern is the same as the C4 finding: a shared cache value (`index-cache` / cached `lindex`) that a downstream calculation depends on can be read **stale** because the code path that would refresh it is conditionally skipped based on an unrelated, item-specific check rather than on whether the cache actually needs refreshing for the value being consumed.

### Title
Stale liquidity index used for zToken collateral valuation in `collateral-add` when user has no existing debt, allowing under-collateralized future positions - (File: `local-testing/contracts/market/market.clar`, mirrored in `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`resolve-ztoken` prices zToken collateral by multiplying the oracle price by the vault's cached `lindex`, read via `get-cached-indexes`/`index-cache` rather than by freshly accruing the vault [1](#0-0) . That cache is only populated when `accrue-and-cache` is explicitly invoked for that asset id in the current transaction [2](#0-1) . In `collateral-add`, the cache for the *new* zToken asset being deposited is only primed inside the `cache-primed` branch, which itself is only reached when `current-debt-usd > 0` [3](#0-2) . Just like the Stakehouse bug where `updateAccumulatedETHPerLP()` was gated on an unrelated per-item condition (first BLS key active), here the vault-index refresh needed for correct zToken pricing is gated on an unrelated condition (whether the user currently has debt), not on whether the price of the newly-added zToken actually needs a fresh index.

### Finding Description
`collateral-add` computes `future-capacity`/`current-capacity` and enforces `future-capacity >= current-capacity` only when the account already carries debt [4](#0-3) . When debt is zero, the whole capacity-check block — including `cache-primed`, which is the only place that calls `accrue-and-cache` for the newly deposited zToken's underlying vault — is skipped entirely; the code falls straight to executing `collateral-add` on `market-vault` [5](#0-4) .

If any other operation in the *same block* later needs `resolve-ztoken`/`get-cached-indexes` for that vault id, it will get whatever is in `index-cache-` for `{timestamp: stacks-block-time, aid: aid}` — which, if this deposit path never refreshed it, could be an earlier-cached (and now stale relative to true accrual, though bounded to the block) value, or a subsequent caller relying on this deposit having "warmed" the cache (as `borrow`/`liquidate`/other collateral-add calls do unconditionally) will instead get whatever `accrue-and-cache` computes independently when they eventually call it themselves. The structural defect is that the protocol's index-freshness invariant ("resolve-ztoken always reads a lindex that has been accrued this block") is enforced by an *incidental* gate (`current-debt-usd > 0`) instead of unconditionally, exactly mirroring the referenced bug where reward-distribution freshness was gated on the unrelated "is first BLS key active" condition instead of being unconditional.

### Impact Explanation
Because `collateral-add` for a debt-free account skips priming the cache for the new zToken, and every other public entry point (`borrow`, `liquidate`, `collateral-remove` with debt, etc.) accrues via `accrue-and-cache` before pricing [6](#0-5) , the concrete exploitable window is narrow: this specific call path simply never uses the value it fails to prime (it isn't even read in the debt=0 branch). The impact is therefore not an immediate fund-loss primitive by itself under the current code as read — it is a defect in the accrual invariant rather than a demonstrable path to theft, freezing, or insolvency without a further, chained state (e.g. a subsequent same-block transaction reading `index-cache-` before market's own `accrue-and-cache` would refresh it for that timestamp). I could not fully trace a second concrete transaction in the same block that reads the un-primed cache entry before it is otherwise populated, given the available context.

### Likelihood Explanation
Low-to-uncertain: this requires a same-block interaction sequence exploiting the specific gating on `current-debt-usd > 0`, and most other operations independently call `accrue-and-cache`, self-healing the cache before they read prices.

### Recommendation
Prime/accrue the cache for the asset being added unconditionally in `collateral-add` regardless of whether the account currently has debt, mirroring the unconditional `accrue-and-cache` calls performed in `borrow`/`liquidate`.

### Proof of Concept
Not established with certainty — I was unable to construct a concrete same-block second transaction that reads the un-primed `index-cache-` entry in a way that produces a fund-impacting mispricing, given the read-only tool access available. This should be validated further (e.g. with a Devin session) before treating it as confirmed exploitable.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
