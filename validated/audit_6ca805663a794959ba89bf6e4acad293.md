### Title
Attacker-controlled `remote_ip` field lets clients bypass pack-objects concurrency limiting, enabling resource-exhaustion DoS - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
`PackObjectsHookWithSidechannel` decides whether to apply per-IP concurrency limiting to the expensive `git-pack-objects` invocation based on the `RemoteIp` field of the RPC request. Loopback addresses are explicitly exempted from limiting. This field is attacker-influenceable, so a client can spoof a loopback value and have every one of its concurrent fetch requests run fully unthrottled, defeating the resource-exhaustion protection the limiter exists to provide — conceptually the same class of bug as the reference report: a security-relevant gate (checks/effects) is skipped/mis-ordered relative to the expensive external action (spawning `git-pack-objects`), allowing repeated/unbounded invocation of the guarded operation.

### Finding Description
`packObjectsHook` computes whether to route the request through the concurrency limiter purely from `req.GetRemoteIp()`: [1](#0-0) 

If the parsed IP `IsLoopback()`, the function calls the unlimited `runPackObjects` path instead of `runPackObjectsLimited`: [2](#0-1) 

`RemoteIp` originates from `gitaly-hooks`' `packObjectsHook`, which forwards `payload.UserDetails.RemoteIP` from the `HooksPayload` into the gRPC request: [3](#0-2) 

The payload's `RemoteIP` is populated when Gitaly constructs the pack-objects-hook environment via `WithPackObjectsHookEnv`, which pulls the value from gRPC-request metadata (`metadata.GetValue(ctx, "remote_ip")`): [4](#0-3) 

Configuration and proto docs confirm the field is meant to be the "original IP of the initiator of the fetch" and is explicitly "used as the key for concurrency limiting before we trigger git-pack-objects command": [5](#0-4) [6](#0-5) 

Test coverage confirms the loopback bypass behavior is intentional/by-design for local traffic, but it demonstrates the exact mechanism an attacker can abuse: any request whose `RemoteIp` parses to `127.0.0.1` or `::1` receives no concurrency limiting at all: [7](#0-6) 

Because the `remote_ip` metadata value that seeds `UserDetails.RemoteIP` is derived from client-supplied/proxy-forwarded request metadata rather than a value Gitaly independently and trustworthily verifies as the true peer address, a client (or a compromised/adversarial intermediary in the request path that sets this metadata) can cause its `RemoteIp` to resolve to a loopback address. This defeats the entire purpose of `PackObjectsLimiting`, which exists specifically to bound the number of concurrent, CPU/memory-heavy `git-pack-objects` subprocesses spawned per remote source (default concurrency 200 per IP, configurable, with a global queue as backstop). With the bypass, an attacker can issue an effectively unbounded number of concurrent fetch/pack-objects operations against a repository, all fully unthrottled, exhausting CPU, memory, and process-table resources on the Gitaly node.

This mirrors the reported reentrancy bug class: `claimRewards` uses caller-triggerable execution (an ERC777 callback) to re-enter and repeatedly invoke a state-changing operation before its accounting effect is applied, because the effect is misordered around external interaction. Here, the "effect" (concurrency-limit enforcement) is skipped entirely for a caller-influenceable input, and the "expensive/external interaction" (`git-pack-objects` subprocess spawning) can be invoked without bound as a result.

### Impact Explanation
An attacker able to reach `PackObjectsHookWithSidechannel` (any user capable of doing `git fetch`/`git clone` operations against a Gitaly-served repository) can flood the node with concurrent pack-objects requests that spoof a loopback `remote_ip`, bypassing `[pack_objects_limiting]` entirely. This can exhaust Gitaly's CPU and memory, causing a denial of service for the Gitaly node and, potentially, cascading effects for other repositories/tenants served by that node (noisy-neighbor DoS). This is a DoS of an RPC handler's resource-limiting mechanism, which is explicitly within the accepted class of findings for this analysis.

### Likelihood Explanation
Likelihood is dependent on exactly how/where the `remote_ip` metadata value is populated and validated before reaching `WithPackObjectsHookEnv`/`packObjectsHook` — this determines whether an ordinary, non-privileged client request can directly control it, or whether it is set only by a trusted internal component (e.g., Praefect/Workhorse) after validating the real peer address, in which case the bypass would require a compromised intermediary rather than an ordinary end user. The codebase available here shows the field flowing from gRPC metadata into the hook payload without an inline trust/validation check at the point of use in `pack_objects.go`, but the full metadata-population path (where the `"remote_ip"` gRPC metadata key is first set from the incoming request) was only partially inspected due to the file/context not being enumerated in the indexed search results. This should be verified in the full source (e.g., `internal/grpc/middleware/requestinfohandler` and where it stores metadata reachable via `internal/grpc/metadata`) to confirm whether external, untrusted callers can directly set this metadata value.

### Recommendation
- Do not rely on a caller/metadata-supplied string for a security-relevant concurrency-limit decision. Derive the "remote IP" strictly from the transport-level peer address (`peer.FromContext`) at the point closest to the actual network connection, and treat any value carried in application-level metadata/hook-payload fields as untrusted/advisory only for logging.
- If loopback exemption is required for legitimate local components (e.g., gitaly-hooks talking back to Gitaly over localhost), gate that exemption on the actual gRPC peer address of the `PackObjectsHookWithSidechannel` call (which does originate over a local Unix/TCP loopback socket in that specific call path), not on the `RemoteIp` field value carried inside the request payload.
- Add a fallback/default-deny behavior: if the "trusted" peer-derived remote address cannot be established, apply the limiter rather than skipping it.

### Proof of Concept
Conceptual PoC (cannot be fully executed without the complete metadata-population code path, but is demonstrated by existing test behavior):
1. A client authenticates normally to Gitaly and initiates many concurrent `git fetch`/`clone` operations against a repository, causing `gitaly-hooks` to invoke `PackObjectsHookWithSidechannel` for each.
2. The client (or an intermediary component under the client's control) arranges for the `remote_ip` value that ends up in `UserDetails.RemoteIP` → `PackObjectsHookWithSidechannelRequest.RemoteIp` to be `"127.0.0.1"` (or `::1`).
3. Per `packObjectsHook`'s logic, every one of these requests takes the `ipAddr.IsLoopback()` branch and calls `runPackObjects` (unlimited) instead of `runPackObjectsLimited`, exactly as demonstrated by the existing "IPv4 loopback addresses" / "IPv6 loopback addresses" test cases which assert `shouldLimit: false`: [7](#0-6) 
4. The attacker repeats this at high volume; because no per-IP/queue limiting applies, the Gitaly node spawns unbounded concurrent `git-pack-objects` subprocesses, exhausting CPU/memory and causing a denial of service.

			// Best effort, maybe the remote IP includes source port
			if ip, _, err := net.SplitHostPort(req.GetRemoteIp()); err == nil {
				ipAddr = net.ParseIP(ip)
			}

		// Ignore loop-back IPs
		if ipAddr != nil && !ipAddr.IsLoopback() {
