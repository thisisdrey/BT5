Based on my analysis, I found a valid analog in the permission-operations bit-check logic, which shares the exact bug class from the report: an unvalidated numeric field is used directly as a bit-index into a fixed-size bitmap via unchecked division/modulo, with no bounds check on the source value before it's used to derive the offset.

### Title
Unbounded `Contract.type` value used as bit-index into fixed 32-byte permission `operations` bitmap causes `IndexOutOfBoundsException` during transaction signature validation - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`, `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`checkPermissionOperations()` computes a bit position from `contract.getTypeValue()` and indexes directly into the 32-byte (256-bit) `permission.getOperations()` `ByteString` without validating that the raw protobuf enum value actually falls in the `0-255` range the bitmap can represent, mirroring the reported `ChainlinkRoundLib.phaseId()` flaw where a hard-coded bit-width assumption is applied to an unchecked value.

### Finding Description
`WalletUtil.checkPermissionOperations` and the duplicate logic in `TransactionCapsule.java`/`TransactionUtil.java` implement the multi-sig "Active permission operations" bitmap check: [1](#0-0) 

The code assumes `contract.getTypeValue()` (the raw `int32` backing the `Transaction.Contract.type` enum field) is always within `[0, 255]`, since it divides by 8 and shifts `1 << (contractType % 8)` to pick a bit inside a fixed 32-byte buffer. However, in protobuf, an enum field's `getTypeValue()` returns the *raw stored integer*, which is **not** constrained to the set of known enum constants — a transaction can be constructed (e.g., via raw-data hex, JSON `packTransaction`, or gRPC) with a `Contract.type` value outside the declared `ContractType` enum range (negative, or greater than the ~90 known contract types, up to `Integer.MAX_VALUE`). There is no `ContractType.forNumber()` / range validation performed before this check runs.

This is functionally analogous to the reported bug: `PHASE_OFFSET`/bit-shift math is applied to an input whose width/range was never validated, and out-of-range inputs are not rejected safely — they are fed straight into the bit-extraction arithmetic.

### Impact Explanation
If `contractType` exceeds `255` (e.g. `300`), `contractType / 8 = 37`, which is out of bounds for the 32-byte (`0-31`) `operations` `ByteString`, causing `ByteString.byteAt()` to throw an `IndexOutOfBoundsException`. This function is reached from the **hot transaction-processing path**: `Manager.pushTransaction()` → `TransactionCapsule.validateSignature()` → `TransactionCapsule.checkPermission()` → `checkPermissionOperations()` [2](#0-1) [3](#0-2) , as well as `Manager.processTransaction()` for block application [4](#0-3) .

Whether this manifests as unhandled crash propagation depends on the surrounding exception handling: `Wallet.getTransactionApprovedList` and `TransactionUtil.getTransactionSignWeight` do catch generic `Exception` around the block that calls this function [5](#0-4) , so those particular query paths degrade gracefully to an error response rather than crashing. However, `Manager.pushTransaction` / `processTransaction` (used both for API-submitted broadcast transactions and block application) do **not** wrap `validateSignature` in a catch for unchecked `RuntimeException`/`IndexOutOfBoundsException` — only checked exceptions (`ValidateSignatureException`, `ContractValidateException`, etc.) are declared/caught by callers [6](#0-5) . An uncaught `IndexOutOfBoundsException` thrown here during block processing could propagate up and disrupt normal transaction/block processing flow for that node.

### Likelihood Explanation
Any unprivileged client that can construct and broadcast a raw transaction (bypassing the SDK's normal `ContractType` enum construction, e.g. by directly crafting protobuf bytes or via `Util.packTransaction` with a raw JSON `type` value) can set an arbitrary `Contract.type` integer as long as `permissionId != 0` is also set to route through `checkPermission`. This only requires a valid signed transaction with a non-zero `permissionId` referencing an existing active permission — well within reach of a single unprivileged transaction broadcaster with no special access.

### Recommendation
Validate that `contract.getTypeValue()` corresponds to a known `ContractType` (e.g., `ContractType.forNumber(contractType) != null`) — or explicitly bound-check it against `[0, 255]` — before using it to compute `operations.byteAt(contractType / 8)`, and reject the transaction with a `PermissionException`/`ContractValidateException` if out of range, mirroring the recommendation to properly validate/parameterize any hard-coded bit-width assumption instead of applying it blindly to attacker-controlled input.

### Proof of Concept
1. Craft a `Transaction` where `raw_data.contract[0].type` is set to an out-of-range integer (e.g., `300`) using raw protobuf/hex construction (bypassing the Java SDK's enum-only API), while `parameter` still unpacks to some contract type, and set `Contract.Contract.permission_id` to a non-zero value referencing an account's existing Active permission.
2. Sign the transaction with a key present in that Active permission and broadcast it via `Wallet.broadcastTransaction` → `Manager.pushTransaction`.
3. During `validateSignature()` → `checkPermission()` → `checkPermissionOperations()`, `contractType / 8` evaluates to `37`, exceeding the 32-byte bound of `permission.getOperations()`, causing `ByteString.byteAt()` to throw `IndexOutOfBoundsException`, which is not caught by the surrounding checked-exception handlers in `Manager.pushTransaction`/`processTransaction`.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
