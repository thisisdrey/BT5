### Title
Wallet Contract fails to enforce self-target for `AddKey`/`DeleteKey` actions when `target` resolves to `OtherNearAccount`, allowing cross-account key deletion/addition - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs])

### Summary
`parse_rlp_tx_to_action` only forces `AddKey`/`DeleteKey` ("`SelfNearNativeAction`") to be redirected/self-scoped when `target_kind == TargetKind::EthImplicit`. When `target_kind == TargetKind::OtherNearAccount` (i.e. the caller-supplied `target` is a named NEAR account, not an eth-implicit wallet), the raw `Action::AddKey`/`Action::DeleteKey` decoded purely from attacker-controlled ABI calldata is passed through unchanged and is later turned into `Promise::new(target).delete_key(...)`/`.add_access_key_allowance_with_nonce(...)` — i.e. sent to the caller-chosen `target`, not to `context.current_account_id`. Since `to == account_id_to_address(target)` is satisfiable by the attacker for any `target` they pick (they sign their own RLP transaction), this breaks the "self-target-only" invariant the security question assumes holds.

### Finding Description
In `parse_tx_data` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:297-304`), the `DELETE_KEY_SELECTOR` branch (and identically the `ADD_KEY_SELECTOR` branch at lines 272-296) never checks `target` against anything — unlike `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR` which explicitly require `target.as_str() == receiver_id.as_str()` [1](#0-0) . It just returns `Action::DeleteKey { public_key_kind, public_key }` tagged `ParsableTransactionKind::SelfNearNativeAction` [2](#0-1) .

Back in `parse_rlp_tx_to_action`, the only special handling for `SelfNearNativeAction` is:
```
Ok((action, ParsableTransactionKind::SelfNearNativeAction)) => {
    if let TargetKind::EthImplicit(_) = target_kind {
        // convert to a Transfer to `target`
    } else {
        (action, TransactionKind::NearNativeAction)   // <-- OtherNearAccount falls here too
    }
}
``` [3](#0-2) 

Note the `else` branch is reached both for `TargetKind::CurrentAccount` (safe/intended) **and** `TargetKind::OtherNearAccount` (any named NEAR account, unsafe). For `OtherNearAccount`, the code passes the raw `AddKey`/`DeleteKey` action through unmodified with `target` still equal to the caller-supplied account.

`validate_tx_relayer_data` validates that `to == account_id_to_address(target)` when `target_kind` is `OtherNearAccount` [4](#0-3) . Since the attacker fully controls both the RLP transaction they sign (including `to`) and the `target` argument passed into `rlp_execute` (a public, unauthenticated method — `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-93`), the attacker can trivially satisfy this check for `target = "victim.near"` by setting `to = account_id_to_address("victim.near")`.

The resulting `near_action::Action::DeleteKey` (built via `construct_public_key` from fully attacker-chosen `public_key_kind`/`public_key` bytes — `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs:291-296,302-316`) is finally converted into a promise via `action_to_promise(target, action)`:
```
near_action::Action::DeleteKey(action) => Ok(Promise::new(target).delete_key(action.public_key)),
``` [5](#0-4) 

Here `target` is the caller-chosen `"victim.near"`, not `context.current_account_id`. NEAR's receipt-level `DeleteKey`/`AddKey` action processing does not require predecessor == receiver (that "self-only" rule is only enforced at `SignedTransaction` validation time, not for actions dispatched via a cross-contract `Promise`), so a receipt containing `DeleteKey{public_key}` sent to `victim.near` will delete that access key from `victim.near` if it exists there — regardless of who created the promise.

This directly contradicts the security question's premise ("promise is always scoped to `target=current_account_id`") — that scoping is only enforced for the `EthImplicit` sub-case, not for `OtherNearAccount`.

### Impact Explanation
This is authorization escalation across accounts, not the benign "no-op self delete" the question hypothesized:
- **DeleteKey**: An attacker who knows any existing public key of a victim account (public key material is publicly visible via RPC `view_access_key_list`) can craft a self-signed RLP transaction through their own wallet contract targeting `victim.near`, causing that key to be deleted from `victim.near` without the victim's or victim's relayer's authorization. If it is the victim's only full-access key, this permanently locks the victim out of their account (permanent freezing of funds/account — a recognized NEAR bounty category).
- **AddKey** (same missing check applies to `ADD_KEY_SELECTOR`): could add an access key to a victim's account, though `action_to_promise` currently rejects full-access `AddKey` (`UnsupportedAction::AddFullAccessKey`) and only permits `FunctionCall`-scoped keys, limiting — but not eliminating — this vector (an attacker-added `FunctionCall` key on `victim.near` restricted to a `receiver_id`/`method_names` of the attacker's choosing could still be used for further attacks such as griefing storage or interacting with contracts on the victim's behalf within the allowance).

### Likelihood Explanation
- Attacker only needs: an eth-implicit account with the wallet contract deployed (which is standard for all eth-implicit accounts), the ability to sign their own Ethereum-style transaction, and to call the public `rlp_execute` method themselves (no relayer trust needed since they can be their own relayer, or if a relayer error occurs the relayer that is not itself the attacker would get banned, but the attacker acting as its own relayer bypasses this deterrent entirely).
- The attacker needs to know a target account and one of its currently valid public keys — both retrievable from public RPC.
- Fully repeatable and requires no privileged access, matching the "unprivileged attacker" threat model exactly.

### Recommendation
In `parse_rlp_tx_to_action` (`internal.rs`), the `SelfNearNativeAction` branch must reject or redirect for **any** `target_kind != TargetKind::CurrentAccount`, not just `TargetKind::EthImplicit`. I.e., change:
```rust
if let TargetKind::EthImplicit(_) = target_kind { ... } else { (action, TransactionKind::NearNativeAction) }
```
to explicitly match all three `TargetKind` variants, only allowing the raw `AddKey`/`DeleteKey` action through when `target_kind == TargetKind::CurrentAccount`, and treating both `EthImplicit` and `OtherNearAccount` as "convert to a Transfer to `target`" (or reject with `RelayerError::InvalidTarget`) — mirroring the explicit `target == receiver_id` checks already used for `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR`.

### Proof of Concept
Unit test in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs` (or the integration test harness in `src/tests/`):
1. Set up `ExecutionContext` for attacker's eth-implicit account (`current_account_id = "0xattacker...", current_address` derived accordingly).
2. Construct an RLP transaction: `to = account_id_to_address(&"victim.near".parse().unwrap())`, `data = DELETE_KEY_SELECTOR || abi_encode(public_key_kind, public_key_bytes_of_a_known_victim_key)`, signed by the attacker's key, `chain_id = CHAIN_ID`, correct `nonce`.
3. Call `internal::parse_rlp_tx_to_action(&tx_b64, &"victim.near".parse().unwrap(), &context, expected_nonce)`.
4. Assert that the returned `(near_action::Action, TransactionKind)` is `Action::DeleteKey(DeleteKeyAction{ public_key })` with `TransactionKind::NearNativeAction` (confirming it is NOT converted to a `Transfer`), then trace through `action_to_promise("victim.near".parse().unwrap(), action)` and assert the resulting `Promise` target is `"victim.near"` rather than `context.current_account_id`.
5. Expected (fixed) behavior: the call should either fail with `Error::Relayer(RelayerError::InvalidTarget)`/similar, or force `Action::Transfer` to `target`, and must never produce a `DeleteKey`/`AddKey` promise whose receiver differs from `context.current_account_id`.
