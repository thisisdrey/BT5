This confirms the vulnerability: `do_native_withdraw` has no resolver checking the final `Promise::new(receiver_id).transfer(amount)` outcome, unlike every other withdraw path (`ft_resolve_withdraw`, `mt_resolve_withdraw`, `nft_resolve_withdraw`) which check `promise_result_checked_void` and refund via `self.deposit(...)` on failure.

### Title
`native_withdraw` permanently burns a user's internal wNEAR balance when the final raw-NEAR transfer fails, with no resolver to refund - (File: `contracts/defuse/src/contract/tokens/nep141/native.rs`)

### Summary
`native_withdraw` debits the caller's internal wNEAR ledger balance and unwraps it into raw NEAR held by the contract, then sends that raw NEAR to an arbitrary attacker-supplied `receiver_id` via a bare, un-resolved `Promise::transfer`. If that final transfer action fails (e.g., `receiver_id` doesn't exist or is otherwise unable to receive the transfer), the NEAR is refunded to the contract account itself, but the user's internal ledger is never credited back. This is the same class of bug as the ThorChain report: state is finalized on the assumption that the final leg of a transfer succeeds, without verifying it.

### Finding Description
`native_withdraw` ( [1](#0-0) ) first calls `self.withdraw(...)`, which subtracts `withdraw.amount` of wNEAR from `owner_id`'s internal balance unconditionally, then schedules `wnear.near_withdraw()` followed by `Contract::do_native_withdraw`.

`do_native_withdraw` ( [2](#0-1) ) only verifies that `near_withdraw` (the wNEAR→NEAR unwrap) succeeded via `promise_result_checked_void(0)`. It then issues a bare `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` with no `.then(...)` resolver attached, and `native_withdraw` immediately `.detach()`es the whole promise chain ( [3](#0-2) ). There is no callback to check whether this final transfer receipt actually succeeded.

Contrast this with every other withdraw path in the same module, all of which check the final transfer's promise result and refund the unsent amount back to the sender on failure:
- `ft_resolve_withdraw` [4](#0-3) 
- `mt_resolve_withdraw` [5](#0-4) 
- `nft_resolve_withdraw` [6](#0-5) 

If the final `Promise::new(receiver_id).transfer(amount)` action fails (target account non-existent, deleted, or otherwise unable to accept the transfer per NEAR runtime rules), the attached NEAR balance is refunded to the receipt's predecessor — the `intents` contract account itself — not to the withdrawing user. The user's internal ledger was already decremented by `internal_sub_balance` inside `self.withdraw()`, and nothing ever re-credits it. The invariant broken is: *value debited from the user's ledger == value delivered to the receiver + value refunded to the user*. Here, value debited can exceed value delivered-plus-refunded, permanently.

### Impact Explanation
This is a Critical-tier "funds permanently frozen"/loss scenario: an unprivileged withdrawer's specified `receiver_id` (fully attacker/caller controlled, per `NativeWithdraw { receiver_id, amount }` in [7](#0-6) ) can be any account, including one that does not exist or cannot accept the transfer receipt. The withdrawn NEAR is stranded in the contract's own raw account balance (outside the tracked ledger), while the withdrawing user's internal wNEAR/native balance is gone with no refund path — a direct, unauthorized loss of user funds.

### Likelihood Explanation
Likelihood is not purely theoretical: the withdrawer chooses `receiver_id` for their own `NativeWithdraw` intent (or a compromised/malicious relayer could specify one). Because near-account non-existence is a common and easily-triggered failure condition (e.g., a typo'd or unregistered account, or an account deleted between intent signing and execution), this can be hit accidentally, and can also be deliberately triggered as a griefing/loss vector by any signer withdrawing to a bogus destination — though note the loss lands on the signer's own balance in that specific case; more concerning is the systemic absence of the safety net that every other withdraw path in this contract has.

### Recommendation
Add a `#[private]` resolver method analogous to `ft_resolve_withdraw`/`mt_resolve_withdraw`/`nft_resolve_withdraw` that is chained after the `Promise::new(receiver_id).transfer(amount)` call, checks `promise_result_checked_void` on that final transfer, and calls `self.deposit(owner_id, [(wnear_token_id, amount)], Some(REFUND_MEMO))` when it fails, mirroring the existing refund pattern used for NEP-141/171/245 withdrawals.

### Proof of Concept
1. User deposits wNEAR into the intents contract, giving them an internal balance for `Nep141TokenId::new(wnear_id)`.
2. User signs and executes a `NativeWithdraw { receiver_id: <account that does not exist>, amount }` intent.
3. `native_withdraw` ( [1](#0-0) ) subtracts `amount` from the user's ledger and schedules `near_withdraw` → `do_native_withdraw`.
4. `do_native_withdraw` ( [2](#0-1) ) unwraps the NEAR successfully, then issues `Promise::new(receiver_id).transfer(amount)`, which fails at the NEAR-runtime level because `receiver_id` does not exist.
5. The transferred NEAR balance is refunded to the intents contract account (not the user); no resolver observes or acts on this failure.
6. Final state: user's internal ledger balance for wNEAR is permanently reduced by `amount`, with no corresponding NEAR delivered to `receiver_id` and no refund credited back to the user — compare this to the existing `native_withdraw_intent` test ( [8](#0-7) ), which only exercises the success path and never asserts recovery behavior on a failed final transfer.

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }

    fn mt_resolve_withdraw(

            match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {

                Ok(_) => vec![U128(0); amounts.len()],

                // NEP-141 vulnerability: `mt_resolve_transfer` fails to
                // read result of `mt_on_transfer` due to insufficient gas
                Err(_) => amounts.clone(),
            }
        } else {
            // `mt_batch_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amounts.clone()
            } else {
                vec![U128(0); amounts.len()]
            }
        };

            sender_id,

                .into_iter()
                .zip(amounts)

                    } else {
                        None
                    }
                }),
            Some(REFUND_MEMO),
        )
        .unwrap_or_else(|err| err.panic());

    }
