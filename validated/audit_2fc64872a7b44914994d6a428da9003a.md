### Title
Unpriced compute-unit-limit gaming lets near-zero-fee transactions out-prioritize legitimately-fee-paying, compute-heavy transactions and clear `SchedulerPriorityFloor` - ([File: core/src/transaction_priority.rs])

### Summary
`calculate_priority_and_cost` computes `P = R / (1 + C)` where `C` comes from `CostModel::calculate_cost_for_executed_transaction` using the *requested* `compute_unit_limit`, which an unprivileged sender can set to `1` with no minimum floor enforced. Because signature/write-lock/data costs form a small, near-fixed baseline (~600-2000 CU) while a real compute-heavy transaction's cost is dominated by its actual CU need (up to 1.4M CU), a spam transaction with `compute_unit_limit=1` and zero `compute_unit_price` gets a priority driven almost entirely by the mandatory base signature fee reward divided by a tiny denominator - often far exceeding the priority of a genuine, larger-absolute-fee transaction that needs real compute. This inflated priority is exactly what `calculate_priority_from_bytes` publishes to `SchedulerPriorityFloor`/`SigVerifyWorkerState`, letting the attacker's cheap packets both clear the floor and dominate the scheduler's priority queue ahead of costly legitimate work.

### Finding Description
`calculate_priority_and_cost` in `core/src/transaction_priority.rs` computes cost via `CostModel::calculate_cost_for_executed_transaction(transaction, u64::from(transaction_configuration.compute_unit_limit), ...)` [1](#0-0) . The `compute_unit_limit` used here comes straight from the sender-controlled `ComputeBudgetInstruction::set_compute_unit_limit`, sanitized only by `sanitize_and_convert_to_compute_budget_limits`, which clamps only the *maximum* (`.min(MAX_COMPUTE_UNIT_LIMIT)`) and applies no minimum floor - `set_compute_unit_limit(1)` is explicitly accepted and tested as valid [2](#0-1) [3](#0-2) .

`CostModel::calculate_transaction_cost` sums `signature_cost + write_lock_cost + data_bytes_cost + programs_execution_cost + loaded_accounts_data_size_cost` [4](#0-3) , where `programs_execution_cost` is exactly the declared `compute_unit_limit` [5](#0-4) . The other terms are effectively fixed for a minimal transaction (e.g. a simple 1-signature transfer measured at `signature_cost=1440`(2 sigs)/`write_lock_cost=600`/`data_bytes_cost≈19` in existing tests) [6](#0-5) . So setting `compute_unit_limit=1` collapses `C` to roughly this small fixed baseline (a few hundred to ~2000 CU), regardless of whether the transaction would otherwise legitimately need hundreds of thousands of CU.

Meanwhile `R` (reward) is the fee deposit from `solana_fee::calculate_fee_details`, which includes the mandatory signature fee plus any declared priority fee. A transaction with zero `compute_unit_price` still generates a non-zero `R` purely from the base signature fee. Because `C` is artificially tiny, `P = R/(1+C)` for this near-zero-cost spam transaction can exceed the `P` of a real, expensive, well-paying transaction whose `C` is dominated by its genuine large `compute_unit_limit`. The code comment in `calculate_priority_and_cost` even asserts "Current minimum costs are on the order of several hundred, so the denominator is effectively C ... Any difference in the prioritization is negligible for the current transaction costs" [7](#0-6)  - an assumption that breaks down precisely when `compute_unit_limit` is set to `1`, since the "several hundred" baseline is no longer negligible relative to a legitimate multi-hundred-thousand-CU transaction's cost.

This priority value is exactly what feeds `SchedulerPriorityFloor`: `calculate_priority_from_bytes` runs the identical computation on raw packet bytes and is used by `SigVerifyWorkerState` to drop at-or-below-floor packets ahead of ed25519 verification [8](#0-7) [9](#0-8) . It is also the same priority used by the scheduler's container to determine `get_min_max_priority` for publishing the floor [10](#0-9) . A flood of `compute_unit_limit=1` transactions can therefore (a) themselves reliably clear the floor, and (b) if they occupy the scheduler's retained buffer, raise the effective floor above the priority of genuine higher-absolute-fee/higher-CU transactions, causing those legitimate packets to be dropped by `SigVerifyWorkerState` before signature verification even runs - a QoS/backpressure inversion, not merely "unfair" scheduling.

No existing guard mitigates this: there's no minimum `compute_unit_limit` enforcement, no fee-per-CU normalization independent of a fixed baseline, and dedup/rate limiting in `SigVerifyWorkerState` operates on packet content dedup, not priority fairness.

### Impact Explanation
This falls under QoS/fee-market evasion and "grossly underpriced pre-fee work": an attacker can achieve outsized scheduling priority (able to starve/drop legitimately more valuable transactions ahead of sigverify via the shared `SchedulerPriorityFloor`) while paying only the mandatory base signature fee, not a market-competitive fee for the blockspace/CU they are effectively denying to others. Each such packet still forces a full `ed25519_verify` and consumes a scheduling/buffer slot in banking stage, so the attacker imposes real verification and buffering cost on the validator while paying disproportionately little for the priority gained. This does not cause a crash/panic/invalid block, but it is a real economic/QoS design flaw in the priority formula as consumed by the newly-introduced `SchedulerPriorityFloor` gate.

### Likelihood Explanation
Fully reachable by an unprivileged, unstaked client: any funded account can submit ordinary transactions with `ComputeBudgetInstruction::set_compute_unit_limit(1)` and `compute_unit_price = 0` over the public TPU/QUIC ingress. No special permissions, staking, or validator control are required - only a funded fee-payer account (5000 lamports/signature by default) and the ability to open QUIC connections and send packets, both explicitly in-scope for an unprivileged attacker. The condition is easily and repeatably triggered under any load that saturates the scheduler's buffer (the precondition for `SchedulerPriorityFloor` to be active at all).

### Recommendation
Do not let sender-declared `compute_unit_limit` alone determine the cost denominator used for priority/floor comparisons. Options: (1) enforce a realistic minimum `compute_unit_limit` (or a minimum cost floor) that scales with instruction count/complexity rather than trusting the sender's declared value verbatim for prioritization purposes; (2) normalize priority using effective fee-per-CU with a cost floor that reflects worst-case verification+scheduling overhead rather than actual declared CU, so gaming `compute_unit_limit` cannot arbitrarily shrink the denominator relative to genuine workloads; (3) incorporate the fixed signature/write-lock overhead into a separate fairness/rate-limiting mechanism decoupled from the priority formula so `SchedulerPriorityFloor` isn't solely driven by a value trivially minimized by the sender.

### Proof of Concept
Rust unit test extending `core/src/transaction_priority.rs`'s existing test module, showing a zero-fee, `compute_unit_limit=1` transaction outranks a genuine, fee-paying, high-CU transaction:

```rust
#[test]
fn cu_limit_one_zero_fee_tx_outranks_real_high_cu_paying_tx() {
    let (bank, mint) = test_bank_with_lamports_per_signature(5_000);

    // "Spam" tx: compute_unit_limit = 1, compute_unit_price = 0.
    let spam_bytes = {
        let to = Pubkey::new_unique();
        let transfer = system_instruction::transfer(&mint.pubkey(), &to, 1);
        let cu_limit = ComputeBudgetInstruction::set_compute_unit_limit(1);
        let message = Message::new(&[transfer, cu_limit], Some(&mint.pubkey()));
        let tx = Transaction::new(&[&mint], message, bank.last_blockhash());
        bincode::serialize(&VersionedTransaction::from(tx)).unwrap()
    };

    // "Legit" tx: real 200_000 CU need, paying a modest but non-trivial priority fee.
    let legit_bytes = {
        let to = Pubkey::new_unique();
        let transfer = system_instruction::transfer(&mint.pubkey(), &to, 1);
        let cu_limit = ComputeBudgetInstruction::set_compute_unit_limit(200_000);
        let cu_price = ComputeBudgetInstruction::set_compute_unit_price(1_000); // pays real money
        let message = Message::new(&[transfer, cu_limit, cu_price], Some(&mint.pubkey()));
        let tx = Transaction::new(&[&mint], message, bank.last_blockhash());
        bincode::serialize(&VersionedTransaction::from(tx)).unwrap()
    };

    let spam_priority = calculate_priority_from_bytes(&bank, &spam_bytes).unwrap();
    let legit_priority = calculate_priority_from_bytes(&bank, &legit_bytes).unwrap();

    // The near-zero-fee spam tx (only base signature fee, no priority fee)
    // achieves higher priority than a tx paying a real, larger absolute fee
    // for genuine compute needs — demonstrating the denominator-gaming flaw.
    assert!(
        spam_priority > legit_priority,
        "spam_priority={spam_priority} legit_priority={legit_priority}"
    );
}
```

/// Evaluate raw packet bytes against the pf-floor, returning the computed
/// priority.
///
/// Returns `None` if the bytes don't parse as a valid transaction, in which
/// case the caller should leave the packet to downstream stages to reject.
pub(crate) fn calculate_priority_from_bytes(bank: &Bank, data: &[u8]) -> Option<u64> {
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}

    /// Update the scheduler priority floor.
    ///
    /// Semantics: when the retained scheduler buffer is nearly full, drop
    /// arrivals that are at-or-below the current queue-min priority, i.e. no
    /// better than what the bounded scheduler candidate set would evict.
    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {
        let buffer_size = self.container.buffer_size();
        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);
        let priority_floor = if saturated {
            self.container
                .get_min_max_priority()
                .map_or(0, |(min, _)| min)
        } else {
            0
        };

        self.saturation_state.publish_floor(priority_floor);
    }
