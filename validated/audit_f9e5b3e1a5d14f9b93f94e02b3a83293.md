### Title
Dust-transfer griefing fills a victim's 30-token account list with locked msdTokens, permanently blocking new collateral deposits and forcing liquidation - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`DepositToken._transfer` auto-registers the recipient in the pool's per-account token list via `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero [1](#0-0) . `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` and reverts with `UserReachedMaxTokens` once the combined debt+deposit token count hits the cap [2](#0-1) [3](#0-2) [4](#0-3) . Because `transfer`/`transferFrom` are public and permissionless, an attacker can dust-send 1 wei of every listed deposit token to any victim, filling all 30 slots. Any subsequent legitimate action that would register a *new* token in the victim's list — `deposit` of a new collateral type, or `DebtToken` mint/`SmartFarmingManager.leverage` for a new synthetic — reverts, mirroring the Fedimint bug where an unauthenticated public call deterministically crashes the victim's flow.

### Finding Description
The analog maps cleanly:

- Fedimint: unauthenticated public route + `expect("Must have client module")` → deterministic panic → liveness/boot loop.
- Metronome: unprivileged `DepositToken.transfer(victim, 1)` + `addToDepositTokensOfAccount` cap revert → deterministic revert of every state-changing call that must register a new token for the victim.

Attack trace (all public, no privileges):

1. Attacker deposits dust of each supported underlying into each `DepositToken` (or buys 1 wei on a market), receiving msdTokens.
2. For each deposit token `d` not already in the victim's list, attacker calls `d.transfer(victim, 1)`. `_transfer` sees `balanceOf[victim] == 0` and calls `pool.addToDepositTokensOfAccount(victim)` [5](#0-4) .
3. After ~30 tokens, `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` and every subsequent registration reverts.

The victim cannot self-clean while they carry debt: removing a dust token requires transferring it out, but `transfer` calls `_revertIfLocked`, which checks `unlockedBalanceOf` — dust collateral counted against the position is locked when `_issuableInUsd` is small [6](#0-5) [7](#0-6) . So a victim with an open borrow is stuck with the attacker's filler entries until they fully deleverage.

Consequences while poisoned:

- `DepositToken.deposit` / `NativeTokenGateway` / `VesperGateway` deposits of any collateral type the victim doesn't already hold revert at `_mint` → `addToDepositTokensOfAccount` [8](#0-7) .
- `Pool.mint`/`SmartFarmingManager.leverage` of a synthetic the victim hasn't borrowed reverts via `addToDebtTokensOfAccount` [9](#0-8) .
- A victim whose position drifts unhealthy cannot top up with a *new* collateral asset — the canonical emergency action — and is liquidated instead.

No modifier stops this: `transfer` has no `onlyIfAdditionWillNotReachMaxTokens` bypass, no allowlist, no min-amount, and the check order in `_transfer` (balance update, then pool call) makes the revert atomic with the whole call so even a same-token rescue transfer fails.

### Impact Explanation
Temporary freezing of protocol functionality and conditional loss of user funds: a borrowed victim is denied the ability to add new collateral or open new debt positions, and is forcibly liquidated if their existing collateral deteriorates — economically equivalent to the Fedimint case where a public call renders a service unusable until an external recovery action (full repay) is taken. Attacker cost is bounded by ~30 dust deposits plus gas.

### Likelihood Explanation
Requires only an EOA and ~30 cheap ERC-20 transfers on any deployed pool (mainnet/base/optimism deployments all show `MAX_TOKENS_PER_USER = 30` in `Pool.json` ABIs). No privileged role, oracle manipulation, or governance state needed. Profit is indirect (griefing / possibly bidding in the resulting liquidation), so severity is medium rather than high.

### Recommendation
Do not auto-register recipients on plain transfers, or bound the effect:

- Only call `addToDepositTokensOfAccount` in `_mint`/deposit paths, not in `_transfer`; treat transferred-in dust as unregistered collateral that doesn't count toward `depositOf`, or
- Replace the hard revert in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` with a no-op-on-cap plus explicit registration on user-initiated actions, so attacker-pushed tokens can't consume the victim's slots, and
- Allow a user to `removeFromDepositTokensOfAccount` their own dust tokens (e.g., a `sweepDust` that ignores `_revertIfLocked` for balances below a threshold, since dust contributes negligibly to collateral value).

### Proof of Concept
Hardhat sketch (fork a deployment with ≥2 deposit tokens listed):

```solidity
// victim has an open debt position (deposit + mint) so dust is locked
for (uint i = 0; i < allDepositTokens.length; i++) {
    // attacker deposits 1 wei underlying to get dust msdToken (skip tokens victim already holds)
    IERC20(underlying[i]).approve(address(dt[i]), 1);
    dt[i].deposit(1);
    dt[i].transfer(victim, 1); // registers victim in depositTokensOfAccount
}
// now pool.depositTokensOfAccount(victim).length + debtTokens == 30

// victim tries emergency top-up with a collateral type they never held:
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(amount);

// victim tries to shed a dust token; locked by debt:
vm.prank(victim);
vm.expectRevert(IDepositToken.TransferNotAllowed.selector); // _revertIfLocked
dt[0].transfer(attacker, 1);
```

If the collateral-cap top-up path is judged too indirect, the weaker unconditional variant (blocking `leverage`/`mint` of new synthetics and new-collateral deposits for a debt-free victim until they manually transfer dust out — which costs them gas and a tx per token) still demonstrates the same unauthenticated-trigger → deterministic-revert class.

    function _transfer(
        address sender_,
        address recipient_,
        uint256 amount_
    ) private updateRewardsBeforeTransfer(sender_, recipient_) {
        if (sender_ == address(0)) revert TransferFromTheZeroAddress();
        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
