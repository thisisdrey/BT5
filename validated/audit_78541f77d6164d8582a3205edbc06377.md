### Title
`ACCOUNT_IN_ORDER_EXECUTION` flag is never actually set to `true` in `start_execute_order`, defeating cross-instruction exclusivity guards - ([File: programs/marginfi/src/instructions/marginfi_account/order.rs])

### Summary
This is the closest reachable analog to the reported bug class ("a state flag that is supposed to transition is left in the wrong value, so downstream logic keeps treating the account inconsistently"). Instead of a `removeLoanImpairment`-style function failing to clear a flag, here `start_execute_order` fails to *set* the `ACCOUNT_IN_ORDER_EXECUTION` flag, so every other instruction that relies on this flag to detect "an order execution is currently in progress" is permanently fooled into thinking no order execution is active.

### Finding Description
`start_execute_order` calls: [1](#0-0) 

```rust
let mut marginfi_account = marginfi_account_loader.load_mut()?;
let mut order = order_loader.load_mut()?;

marginfi_account.set_flag(ACCOUNT_IN_ORDER_EXECUTION, false);
```

The account arrives at this point already guaranteed to have `ACCOUNT_IN_ORDER_EXECUTION == false`, because the `StartExecuteOrder` account-validation constraint requires `!acc.get_flag(ACCOUNT_IN_ORDER_EXECUTION)` before the instruction body runs: [2](#0-1) 

Setting the flag to `false` here is therefore a no-op — the flag is never actually flipped to `true` to mark that the account is now mid order-execution. The only other place this flag is touched in the order-execution flow is `end_execute_order`, which *unsets* it (again a no-op, since it was never set): [3](#0-2) 

Meanwhile, `EndExecuteOrder`'s own account constraint *requires* the flag to be `true`: [4](#0-3) 

and numerous other permissionless/exclusive-state entry points (flashloan start, liquidation start, account transfer, withdraw, and Kamino/Drift/JupLend withdraw) gate themselves on `!acc.get_flag(ACCOUNT_IN_ORDER_EXECUTION)` to avoid being interleaved with an in-progress order execution (during which a keeper is granted elevated withdraw/repay authority over the account): [5](#0-4) [6](#0-5) [7](#0-6) 

Because the flag never transitions to `true`, these mutual-exclusion checks are permanently bypassed for the duration of an order-execution sequence.

### Impact Explanation
The `ACCOUNT_IN_ORDER_EXECUTION` flag exists specifically to prevent other privileged/temporary-authority states (flashloan, receivership/liquidation, account transfer) from being entered while a keeper already holds temporary elevated withdraw/repay authority over the account during order execution. With the flag stuck at `false`, a keeper (an unprivileged, permissionless caller of `StartExecuteOrder`) could in principle compose a single transaction that starts order execution and also starts a flashloan or liquidation against the same account without tripping the `UnexpectedOrderExecutionState`/flashloan/liquidation exclusivity constraints, since those constraints all check the same (never-true) flag. This risks interleaved, inconsistent health/state computations across the two "exclusive" flows on the same account, which is the kind of state-consistency defect that can lead to unauthorized withdrawals or under-collateralized states — i.e., insolvency/bad debt exposure, matching the "incorrect handling of a should-have-transitioned flag" root cause of the external report.

### Likelihood Explanation
`StartExecuteOrder`/`EndExecuteOrder` are explicitly documented as callable by any permissionless keeper, and the guard being bypassed is a first-class safety mechanism referenced by name (`ACCOUNT_IN_ORDER_EXECUTION`) throughout the codebase (flashloan, liquidate_start, transfer_account, withdraw, and the three external-protocol withdraw handlers). Given the flag is effectively dead code today (set to `false`/unset to `false`), the exclusivity it is meant to provide is not enforced at all in the current build. This should be verified by running the existing `limit_orders*` and `flashloan`/`liquidate_start` test suites while attempting to interleave a flashloan or liquidation start with `StartExecuteOrder` in one transaction; the existing tests observed only exercise trigger/slippage failure paths and did not confirm whether interleaving is currently blocked by some mechanism outside the flag itself (e.g. `validate_not_cpi_by_stack_height` or `validate_instructions` position checks), so this should be treated as unconfirmed until reproduced.

### Recommendation
Change `start_execute_order` to actually set the flag:
```rust
marginfi_account.set_flag(ACCOUNT_IN_ORDER_EXECUTION, true);
```
so that `EndExecuteOrder`'s constraint (`acc.get_flag(ACCOUNT_IN_ORDER_EXECUTION)` must be `true`) is meaningful, and so that all other instructions' `!acc.get_flag(ACCOUNT_IN_ORDER_EXECUTION)` exclusivity checks correctly reject execution while an order is in progress. Add a regression test that attempts to interleave `StartExecuteOrder` with `flashloan_start`/`liquidate_start`/`transfer_account` in the same transaction and asserts the transaction is rejected with `UnexpectedOrderExecutionState`/`UnexpectedFlashloanState`/`UnexpectedLiquidationState`.

### Proof of Concept
Not independently executed against a live/test validator; based on static code review:
1. Call `marginfi_account_start_execute_order` — per the code at [1](#0-0)  the account's `ACCOUNT_IN_ORDER_EXECUTION` flag remains `false` after this call (the `set_flag(..., false)` call is a no-op).
2. In the same transaction, before `marginfi_account_end_execute_order`, include an instruction guarded by `!acc.get_flag(ACCOUNT_IN_ORDER_EXECUTION)` (e.g. `lending_account_start_flashloan` or `start_liquidation`) — its Anchor account constraint will evaluate `!false == true` and pass, even though an order execution is logically in progress.
3. This would need to be confirmed with an integration test that constructs exactly this multi-instruction transaction and inspects whether the runtime actually permits it, since other structural checks (e.g. `validate_not_cpi_by_stack_height`, instruction-sysvar ordering checks in `validate_instructions`) were not fully traced and could coincidentally prevent some interleavings independent of this flag.
