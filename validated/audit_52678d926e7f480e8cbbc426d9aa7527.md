Based on my research, I found a genuine analog to the described CVE class (integer overflow in statistics/measurement math due to an incomplete/optional fix that isn't applied by default). I was not able to confirm the exact default value of the `ALLOW_HARDEN_RESOURCE_CALCULATION` dynamic property within the remaining budget — this should be treated as an open item for further verification.

### Title
Integer overflow in resource window-size/limit accounting due to disabled-by-default overflow hardening - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
`java-tron` recently introduced a "hardened" calculation path using `BigInteger` for resource (bandwidth/energy) window-size and global-limit arithmetic, gated behind a dynamic chain parameter (`hardenCalculation()` / `ALLOW_HARDEN_RESOURCE_CALCULATION`). The legacy, un-hardened `long`/`double` arithmetic path remains in the code and is used whenever that governance flag is not enabled. This mirrors the bug class in ALPINE-CVE-2025-48964: a prior fix (for `CVE-2025-47268`) addressed one overflow scenario but left another unguarded path reachable, because the fix is conditional rather than universally applied.

### Finding Description
`ResourceProcessor.getNewWindowSize` computes a new window size for delegated bandwidth/energy using plain `long` multiplication when `hardenCalculation()` is false: [1](#0-0) 

The same conditional pattern (BigInteger-hardened vs. raw `long`/`double` arithmetic) recurs in `ResourceProcessor.increase`, `ResourceProcessor.unDelegateIncreaseV2`, `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2`, and `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

These non-hardened branches multiply usage/window values (`lastUsage * lastWindowSize + usage * windowSize`, `netWeight * (totalNetLimit/totalNetWeight)`) that are reachable and influenced by ordinary user actions — `FreezeBalanceV2`, `DelegateResource`, and `UnDelegateResource` contracts (`UnDelegateResourceProcessor.execute`, `UnDelegateResourceActuator`) — via a single signed transaction: [6](#0-5) 

There is dedicated test coverage explicitly demonstrating that with hardening disabled, overflow is silently produced (whereas with hardening enabled, an `ArithmeticException` is deliberately thrown to prevent silent corruption): [7](#0-6) 

The existence of this "hardened vs. legacy" split — with the safe path only active under a governance-controlled flag rather than unconditionally — is functionally identical to the CVE's root cause: an incomplete fix that leaves specific numeric-overflow scenarios (here, large usage/window products) unguarded whenever the flag is not set.

### Impact Explanation
If the hardening flag (`ALLOW_HARDEN_RESOURCE_CALCULATION`) is not enabled on a given network — which I could not conclusively verify as enabled by default within this analysis — an attacker or even a legitimate large-stake ("whale") account performing freeze/delegate/undelegate operations with sufficiently large usage or balance values can overflow the `long` arithmetic in window-size or global-limit computation. Overflowed/wrapped results get persisted to on-chain account state (`accountCapsule.setNewWindowSizeV2`, `setUsage`, etc.), corrupting bandwidth/energy accounting. This can result in incorrect resource limits (unbacked "free" bandwidth/energy generation, i.e., unbacked resource entitlement) or in resource starvation/DoS for the affected account, which given the open rules ("bandwidth accounting, stake/delegation/reward math") qualifies as a Medium-severity, reachable-by-single-transaction accounting integrity issue.

### Likelihood Explanation
Reaching the vulnerable code path requires only ordinary `FreezeBalanceV2Contract`/`DelegateResourceContract`/`UnDelegateResourceContract` transactions, which any account holder can broadcast — no special privilege is required. However, triggering an actual overflow requires very large usage/balance magnitudes (potentially unrealistic under current total TRX supply / resource limit configurations), and depends on whether `ALLOW_HARDEN_RESOURCE_CALCULATION` is left disabled in production, which I was unable to confirm. This uncertainty should be resolved before treating this as fully confirmed exploitable.

### Recommendation
Make the `BigInteger`-based hardened arithmetic in `ResourceProcessor`, `BandwidthProcessor`, and `EnergyProcessor` unconditional (remove the `hardenCalculation()` gate) rather than governance-flag-dependent, so that overflow protection is always active regardless of chain configuration state — this closes the "incomplete fix" gap analogous to the CVE, where safety is conditional rather than universal.

### Proof of Concept
Not independently reproduced with concrete numeric bounds; conceptually: repeatedly freeze/delegate/undelegate very large balances via `DelegateResourceContract`/`UnDelegateResourceContract` while `ALLOW_HARDEN_RESOURCE_CALCULATION` proposal is inactive, driving `lastUsage * lastWindowSize` in `ResourceProcessor.getNewWindowSize` (or equivalent products in `unDelegateIncreaseV2`/`BandwidthProcessor.calculateGlobalNetLimit`) past `Long.MAX_VALUE`, as directly exercised (under the hardened path, which throws) by `CalculateGlobalLimitHardenTest.testGlobalNetLimitOverflowDetectedWithHardening`.   private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
      long windowSize, long newUsage) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
          .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
