## Analysis

The reported bug class is: **a per-actor proportional-share reward calculation (`share = actorAmount / totalAmount * pool`) that truncates/rounds down, so the sum of all individually claimed shares is strictly less than the pool, and the remainder is permanently unrecoverable because no code path ever reclaims or redistributes it.**

The closest reachable analog in java-tron is the legacy vote-reward distribution formula in `MortgageService`, used for any voting cycle prior to `newRewardAlgorithmEffectiveCycle`. This code path is reachable by any account: freeze TRX for votes, vote for a witness (`VoteWitnessContract`), and later call `WithdrawBalanceContract`/`queryReward` (or the TVM `vote()`/`withdrawReward()` precompile path in `VoteRewardUtil`), all of which are ordinary signed transactions from unprivileged accounts.

### Title
Precision loss in legacy per-voter reward split (`MortgageService.computeReward(cycle, votes)`) permanently strands a fraction of the witness reward pool - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` distributes a witness's per-cycle reward pool (`totalReward`) to voters proportionally to their vote weight, using floating point math truncated to `long`: [1](#0-0) 

Each voter's share is computed independently as `voteRate * totalReward` with `voteRate = (double) userVote / totalVote`, and the result is added to a `long reward` accumulator, truncating any fractional token amount for every voter on every call.

### Finding Description
`totalReward` (obtained from `delegationStore.getReward(cycle, srAddress)`) is a fixed pool allocated for a witness for a given cycle via `payReward`: [2](#0-1) 

This is structurally the same pattern as `DebitaIncentives.claimIncentives()`: a fixed incentive/reward pool for a period, split among participants by their proportional contribution (vote weight vs. total vote weight), where each individual's claim is rounded down to an integer amount. Because `double` arithmetic followed by `long` truncation is applied independently per voter, and there is no bookkeeping of "amount already distributed" vs. "pool remaining" that would let a final claimant sweep the dust, the sum of all voters' truncated shares for a given `(cycle, srAddress)` is strictly ≤ `totalReward`. The shortfall is never credited to anyone — not the last claimer, not the witness, not the protocol.

This differs from the newer Vi-based algorithm (`DECIMAL_OF_VI_REWARD = 1e18`) which keeps essentially all precision via `BigInteger` scaling before truncation, so residual loss there is negligible (sub-`1e-18` scale). The legacy path, `getOldReward`, still uses this lossy `double`-based per-voter formula and remains reachable for any cycle before `newRewardAlgorithmEffectiveCycle`, and this cutover point is a protocol parameter, not something an attacker/user controls, but the path itself continues to execute for historical cycles whenever a user with pre-cutover cycles calls to claim. [3](#0-2) 

### Impact Explanation
Reward value allocated to witnesses (funded from block rewards / transaction fee pool via `payReward`) is silently lost per voter, per cycle, whenever a witness's total vote is split across multiple accounts such that `userVote/totalVote * totalReward` is not an exact integer. This is a permanent, unrecoverable loss of value for voters — not a theoretical rounding within a wallet UI, but funds that are computed as owed (`totalReward` reflects real minted/collected reward) yet never added to any account's `allowance`. Over the life of the chain, with many witnesses and many voters each cycle, this compounds. This falls under "stake/delegation/reward math" explicitly listed as in-scope and matches "permanent freezing/loss of funds" impact.

### Likelihood Explanation
This executes automatically on every reward withdrawal/query touching cycles before the new-algorithm cutover — reachable by any account that voted for a witness and calls the standard withdraw/query reward paths (`MortgageService.withdrawReward`/`queryReward`, or the TVM `VoteRewardUtil.withdrawReward`/`queryReward` equivalents). It requires no special privilege, only ordinary voting and reward-claim transactions, so it is straightforward to trigger, though its financial impact per claim is small (fractional token dust) and shrinks over time as the new Vi-based algorithm cycle advances.

### Recommendation
For the legacy `getOldReward`/`computeReward(cycle, votes)` path, replace independent per-voter `double`-truncated computation with an exact `BigInteger`-based proportional split (as already done for the new Vi algorithm), or track cumulative distributed amount per `(cycle, srAddress)` so that a designated final action (e.g., end-of-cycle sweep) can recover/redistribute any rounding remainder instead of letting it silently vanish.

### Proof of Concept
Given a witness with `totalVote = 3` split across three voters each with `userVote = 1`, and `totalReward = 10`:
- Each voter's `voteRate = 1/3 = 0.333...`
- `reward += voteRate * totalReward` → `0.333... * 10 = 3.333...` → truncated to `3` per voter.
- Sum claimed = `3 + 3 + 3 = 9`, while `totalReward = 10`.
- `1` unit of the witness's reward pool for that cycle is never credited to any account and is permanently unclaimable, matching the reported precision-loss/locked-incentive bug class. [4](#0-3)

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
