### Title
Unbounded external-remote fetch with attacker-controlled/optional `Timeout` causes indefinite resource pinning and Gitaly-node-wide DoS - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemote` (and the related `UpdateRemoteMirror` flow) let a caller point Gitaly at an arbitrary, externally-controlled Git remote (`RemoteParams.Url`, optionally with `SshKey`/`KnownHosts`) and only apply a request-supplied `Timeout` if it is greater than zero. If the timeout is omitted or zero, the underlying `git fetch`/`git ls-remote` subprocess and its network connection run with no server-enforced deadline, so a slow or intentionally hanging remote can keep the RPC — and the goroutine, TCP connection, subprocess, and quarantine directory it holds — blocked indefinitely. This mirrors the reported bug class: an external system that "changes in unexpected ways" (here, simply refuses to respond) can lock up resources that Gitaly has no independent mechanism to reclaim.

### Finding Description
`FetchRemote` only wraps the fetch in a context deadline when the client explicitly sets a positive timeout: [1](#0-0) 

If `req.GetTimeout()` is `0` (the default, and a value fully controlled by the RPC caller/proto field), no `context.WithTimeout` is ever applied to `ctx`, and the fetch proceeds with whatever deadline (if any) was set upstream — which, for many internal callers, may be none at all.

The actual fetch spawns a `git fetch` process talking to the attacker-influenced `RemoteParams.Url` (HTTP(S) or SSH, optionally with a caller-supplied SSH key/known-hosts), and blocks on `cmd.Wait()`: [2](#0-1) 

Similarly, `UpdateRemoteMirror` performs a `GetRemoteReferences` call (`git ls-remote`) against the caller-supplied remote with no independent timeout enforcement beyond the request's own context: [3](#0-2) [4](#0-3) 

The test suite explicitly documents that a `Timeout` field must be set for the RPC to be bounded, e.g., a slow HTTP server hangs unless `Timeout: 1` is supplied: [5](#0-4) 

The `[[concurrency]]` per-RPC backpressure mechanism documented for Gitaly is opt-in and configured per RPC in `config.toml`: [6](#0-5) 

No such concurrency entry is bundled by default for `FetchRemote`/`UpdateRemoteMirror`, in contrast to `ReplicateRepository`, which does get a hardcoded default limiter: [7](#0-6) 

Without either (a) a caller-supplied `Timeout`, or (b) an operator-configured `[[concurrency]]` entry with `max_queue_wait`, there is nothing in Gitaly itself that reclaims a stuck fetch. Each hung request holds a goroutine, an open socket/SSH session, a spawned `git` child process, and a quarantine directory on disk indefinitely.

### Impact Explanation
Because the timeout is opt-in and the remote endpoint is attacker/user-influenced (mirror configuration, project import, or fork/mirror sync features ultimately drive `FetchRemoteRequest.RemoteParams.Url`), a small number of such requests directed at a non-responsive endpoint can pin OS threads, file descriptors, and subprocess slots on the Gitaly node without bound. Repeated invocation exhausts goroutines/FDs/process table entries, degrading or halting service for all other RPCs and repositories on that node — a node-wide denial of service, analogous to the reported issue where an unresponsive external dependency locks up the whole system with no automatic recovery path.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `Timeout` is not consistently set by the calling application (e.g., GitLab Rails) for every mirror/fetch invocation, or where an operator has not configured `[[concurrency]]` limits with `max_queue_wait` for `FetchRemote`/`UpdateRemoteMirror`. Any user able to configure a repository mirror/remote URL (a normal, unprivileged product feature) can point it at infrastructure they control and simply stall the TCP handshake or HTTP response indefinitely, requiring no special access to Gitaly internals.

### Recommendation
- Enforce a mandatory, server-side maximum deadline for `FetchRemote`, `UpdateRemoteMirror`, and any other RPC that dials caller-supplied remote URLs, independent of whether the caller supplies `Timeout`/`0`.
- Apply a sane default (e.g., via `context.WithTimeout` unconditionally, falling back to a configured maximum if the caller's value is unset or exceeds it) rather than treating `0` as "no limit."
- Document and ship default `[[concurrency]]` entries (with `max_queue_size`/`max_queue_wait`) for remote-fetching RPCs, similar to the built-in default already applied to `ReplicateRepository`.

### Proof of Concept
1. Configure a mirror/remote whose URL points to an HTTP(S) or SSH endpoint controlled by the attacker (e.g., a server that accepts the connection but never completes the response), similar to the existing test harness pattern: [8](#0-7) 
2. Invoke `FetchRemote` (or `UpdateRemoteMirror`) without setting `Timeout` (or with `Timeout: 0`).
3. Observe that the RPC, its underlying `git fetch`/`git ls-remote` subprocess, and the associated quarantine directory remain open/blocked indefinitely because no context deadline is applied when `Timeout <= 0`.
4. Repeat concurrently (no default per-RPC concurrency limiter exists for these RPCs) to exhaust goroutines/FDs/process slots on the Gitaly node, degrading service for unrelated repositories and RPCs.

func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}

	tagsChanged, repoChanged, err := s.fetchRemoteAtomic(ctx, req)
	if err != nil {
		return nil, err
	}

	return &gitalypb.FetchRemoteResponse{TagsChanged: tagsChanged, RepoChanged: repoChanged}, nil
}

// GetRemoteReferences lists references of the remote. Peeled tags are not returned.
func (repo *Repo) GetRemoteReferences(ctx context.Context, remote string, opts ...GetRemoteReferencesOption) ([]git.Reference, error) {
	var cfg getRemoteReferenceConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	var env []string
	if cfg.sshCommand != "" {
		env = append(env, envGitSSHCommand(cfg.sshCommand))
	}

	stdout := &bytes.Buffer{}
	stderr := &bytes.Buffer{}
	if err := repo.ExecAndWait(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Flags: []gitcmd.Option{
				gitcmd.Flag{Name: "--refs"},
				gitcmd.Flag{Name: "--symref"},
			},
			Args: append([]string{remote}, cfg.patterns...),
		},
		gitcmd.WithStdout(stdout),
		gitcmd.WithStderr(stderr),
		gitcmd.WithEnv(env...),
		gitcmd.WithConfigEnv(cfg.config...),
	); err != nil {
		return nil, fmt.Errorf("create git ls-remote: %w, stderr: %q", err, stderr)
	}

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
