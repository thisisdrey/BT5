### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` state survives account deletion and resolves against a re-created account - (File: `core/store/src/utils/mod.rs`, function: `remove_account`)

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs:505-575` only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` for the deleted account: [1](#0-0) [2](#0-1) 

It never touches `TrieKey::PromiseYieldReceipt{receiver_id, data_id}`, `TrieKey::PromiseYieldStatus`, the yield's `TrieKey::PromiseYieldTimeout` queue entry, or `PostponedReceiptId`/`PendingDataCount`/`ReceivedData`/yield-id mapping keys tied to that account. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` after only checking storage-usage size and gas-key-balance caps — there is no check for outstanding promise-yield state, so `DeleteAccount` succeeds even while a yield created via `promise_yield_create` is still pending on that account: [3](#0-2) 

A `PromiseYield` receipt is always a "self receipt": `promise_yield_create` calls `create_promise_yield_receipt(self.context.current_account_id.clone())`, so its `receiver_id` equals the creating account, and `function_call.rs` sets `predecessor_id: account_id.clone()` for it, i.e. `predecessor_id == receiver_id == A`: [4](#0-3) [5](#0-4) 

Because the timeout queue entry (`PromiseYieldTimeout{account_id: A, data_id, expires_at}`) also survives deletion, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) will, at the recorded `expires_at` height, find that `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` still `contains_key` (because it was never removed by `remove_account`), and *automatically* synthesizes a `PromiseResume` receipt with `predecessor_id: A, receiver_id: A` — with no attacker action required after the account is recreated: [6](#0-5) 

When that `PromiseResume` is processed, `apply_action_receipt` looks up the stale receipt purely by `(account_id, data_id)` — it has no notion of "account incarnation" — and executes its `FunctionCall` action(s) against whatever account/contract now exists at `A`: [7](#0-6) 

`check_account_existence`/`check_actor_permissions` only gate administrative actions (`DeployContract`, `AddKey`, `Stake`, etc.); `FunctionCall` has no such restriction, so the callback runs with `predecessor_id == receiver_id == A` (a genuine self-call from the protocol's point of view) against the account currently owned by whoever re-created `A`, invoking the method name/arguments chosen by the original (deleted) contract execution.

### Impact Explanation
This breaks the invariant that deleting an account purges all of its state, and lets a would-be attacker plant a delayed, automatically-firing "self-call" (predecessor==receiver==self) against any future occupant of the same `AccountId`. If a platform recycles named (sub-)account IDs for different tenants (a common wallet/marketplace-as-a-service pattern) and deploys the same standard contract template to each new tenant, the stale receipt's `method_name`/`arguments` will match a real method on the new contract, and the call executes with `predecessor_account_id() == current_account_id()` — the exact condition most "self-only" privileged callbacks (fund releases, internal ledger updates, etc.) check for authorization. This is a cross-incarnation authorization bypass that can be leveraged to run privileged self-callback logic against a new owner's funds/state without their consent (NEAR bounty category: authorization escalation / potential theft of funds).

### Likelihood Explanation
Preconditions: (1) an attacker-controlled account (e.g. attacker's own sub-account, which the attacker can freely create/delete) with a small deployed contract that calls `promise_yield_create` with attacker-chosen `method_name`/`arguments`, (2) `DeleteAccountAction` on that account (no check blocks this while a yield is pending), (3) the exact `AccountId` string being reused later by a new tenant/contract deployment — realistic on platforms that programmatically assign/reassign named sub-accounts. Cost to the attacker is a handful of cheap transactions (create account, call yield-create, delete account) and does not require any privileged access, matching the stated "ordinary unprivileged client" threat model. The exploit is deterministic once the account name is reused and requires no cooperation from the timeout/resume path beyond the protocol's own automatic timeout resolution.

### Recommendation
When deleting an account in `remove_account` / `action_delete_account`, also purge all promise-yield-related and postponed-receipt state scoped to that account: iterate and remove `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, associated yield-id mapping keys, `PostponedReceiptId`/`PendingDataCount` entries, and dequeue (or mark tombstoned) any `TrieKey::PromiseYieldTimeout` entries referencing the account — or alternatively reject `DeleteAccountAction` outright while any such state exists for the account, mirroring the existing `DeleteAccountStaking`/`GasKeyBalanceTooHigh` guards.

### Proof of Concept
Integration/test-loop test plan:
1. Create account `sub.attacker.near` funded and deployed with a minimal contract exposing a `yield_create` method that calls `promise_yield_create("victim_method", attacker_args, ...)`, and record the returned `data_id`.
2. Submit `DeleteAccountAction` for `sub.attacker.near` (beneficiary = attacker) — assert it succeeds even though the yield/timeout entries are still in state (query `TrieKey::PromiseYieldReceipt`/`PromiseYieldTimeout` directly from the trie to confirm survival).
3. Recreate `sub.attacker.near` (e.g. as the same parent) and deploy a "victim" contract exposing a self-only-gated `victim_method` (guarded by `predecessor_account_id() == current_account_id()`) and fund it with a deposit.
4. Advance the chain past `expires_at` so `resolve_promise_yield_timeouts` fires automatically; assert a `PromiseResume` receipt with `predecessor_id == receiver_id == sub.attacker.near` is produced and executed.
5. Assert the new contract's `victim_method` was invoked (e.g. via a state flag or emitted log) despite the new owner never calling `promise_yield_create` or authorizing this callback, demonstrating the cross-incarnation self-call.
