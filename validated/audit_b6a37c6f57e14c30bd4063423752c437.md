### Title
Toggling `AllowHardenExchangeCalculation` creates inconsistent enforcement of the exchange-transaction safety gate in `Manager.pushTransaction` - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.pushTransaction` contains a gate that rejects `ExchangeTransactionContract` transactions from the local mempool only while the governance-controlled dynamic property `AllowHardenExchangeCalculation` is disabled. `isExchangeTransaction` reflects this: it returns `true` (transaction rejected) when hardened math is off, and `false` (transaction bypassed/allowed) when hardened math is on. Because the gate is evaluated only at `pushTransaction` time and only affects the mempool-submission path, while the actual arithmetic safety behavior in `ExchangeTransactionActuator`/`AbstractExchangeActuator` is separately re-evaluated at execution time via `allowHarden()`, the two checks can disagree whenever the flag is toggled between when a transaction is queued/observed and when it is actually executed (or when the transaction reaches execution through a different path than `pushTransaction`, e.g. block application). This mirrors the RubiconMarket `matchingEnabled` bug class: a single boolean toggle is relied upon by multiple code paths that assume it is static, and toggling it after transactions/orders already exist breaks the invariant those paths depend on.

### Finding Description
`Manager.pushTransaction` unconditionally rejects any `ExchangeTransactionContract`-typed transaction while `isExchangeTransaction` returns `true`: [1](#0-0) 

The helper's outcome flips based purely on the *current* value of the dynamic property `AllowHardenExchangeCalculation`, confirmed directly by the test suite exercising `isExchangeTransaction` via reflection: [2](#0-1) 

Independently, `AbstractExchangeActuator.allowHarden()` re-reads the same dynamic property at *execution* time to decide whether `addExact`/`subtractExact` use `StrictMathWrapper` (overflow-checked) or raw `+`/`-` (unchecked) arithmetic: [3](#0-2) 

`ExchangeTransactionActuator.execute` calls these helpers directly when adjusting account balances for both legs of the exchange: [4](#0-3) 

The design assumes the flag is monotonic ("we intend to only keep our value at true", as in the Rubicon disputed response), but nothing in the codebase enforces that `AllowHardenExchangeCalculation` cannot be toggled back to `0` by a committee proposal after being `1` (or vice-versa). Because the reject-gate in `pushTransaction` and the arithmetic-mode gate in the actuator are two independently-read snapshots of the same mutable flag, an `ExchangeTransactionContract` that is validated/queued/accepted under one flag value can be executed under a different flag value if the flag flips between transaction submission and actual execution (block packing, resync, or admission through any code path other than `pushTransaction`, such as `processTransaction` invoked directly during `applyBlock`/re-sync, which is not gated at all).

This is the direct analog of the RubiconMarket bug: `matchingEnabled` was a single toggle relied on by multiple functions (`isOfferSorted`, `_unsort`, `_hide`) that assumed offers were created consistently with the current flag state; flipping it broke that assumption for already-existing offers. Here, `AllowHardenExchangeCalculation` is a single toggle relied on by two independent gates (mempool admission vs. arithmetic safety mode) that assume the flag is stable; flipping it breaks that assumption for exchange transactions whose execution/admission decisions were made under a different flag value than the one active at balance-mutation time.

### Impact Explanation
If the flag is disabled after having been enabled (or vice versa) between transaction broadcast and inclusion, exchange transactions can execute using unchecked (`allowHarden()==false`) arithmetic that the mempool-admission logic never intended to allow for that transaction, or transactions that should have been rejected outright can still reach execution via a code path that bypasses `pushTransaction`'s reject check entirely (e.g., transactions arriving through block sync/`applyBlock` rather than local broadcast). Because unchecked arithmetic in `AbstractExchangeActuator.addExact/subtractExact` is not overflow-safe, this can lead to incorrect balance crediting/debiting during exchange settlement, i.e., an unbacked balance or loss of funds for exchange participants — the same class of impact (fund-accounting invariant violation) as the original Rubicon finding, reachable by any account submitting an `ExchangeTransactionContract`.

### Likelihood Explanation
Governance toggles of dynamic properties in java-tron are a normal, expected operational action (committee proposals), so the precondition — the flag being flipped after it was previously set — is realistic and not a contrived edge case, exactly as judged in the original Rubicon finding ("valid even if it's an edge case"). The only barrier is the flag actually being toggled back and forth by governance; no on-chain user-level action is needed to reach the actuator once such a toggle occurs, only ordinary exchange-transaction submission.

### Recommendation
Do not gate `ExchangeTransactionContract` admission and execution arithmetic-mode independently from two separate reads of the same mutable dynamic property. Either: (1) make `AllowHardenExchangeCalculation` a one-way, monotonic hard fork flag that cannot be reset to `0` once enabled (consistent with the stated intent "we intend to only keep our value at true"), or (2) enforce the same `isExchangeTransaction`/`allowHarden` gate uniformly across all transaction-admission paths (`pushTransaction`, `processTransaction`, `applyBlock`) so that no path can execute an exchange transaction under a flag value inconsistent with the one used at admission time.

### Proof of Concept
1. Set `AllowHardenExchangeCalculation = 0`. Any `ExchangeTransactionContract` transaction submitted through `Manager.pushTransaction` is rejected with `"ExchangeTransactionContract is rejected"` per [1](#0-0) , confirmed by [5](#0-4) .
2. Toggle `AllowHardenExchangeCalculation = 1` via governance proposal. `isExchangeTransaction` now returns `false`, per [6](#0-5) , so the same contract type is no longer rejected and reaches `ExchangeTransactionActuator.execute`, which computes `subtractExact`/`addExact` using `allowHarden()`'s *current* value read at execution time [3](#0-2) .
3. Because the admission decision (step 1) and execution arithmetic mode (step 2) are independently re-derived from the same mutable flag at different points in time, a race between flag toggling and transaction inclusion produces execution under an arithmetic-safety assumption inconsistent with the one enforced at admission — the same "toggle breaks invariant for already-existing state" pattern as the original `matchingEnabled` finding.

Note: I was not able to view the exact body of the private `isExchangeTransaction` method itself (only its externally-observed behavior via the `ManagerTest` reflection calls), so the precise conditional logic inside that method is inferred from test behavior rather than directly read. If further certainty is needed, a Devin session with full file access should confirm `isExchangeTransaction`'s implementation directly.
