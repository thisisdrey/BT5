### Title
NEAR-implicit account nonce reset on same-height delete+recreate enables signed-transaction replay - (`runtime/runtime/src/actions.rs:213` `action_implicit_account_creation_transfer`)

### Summary
`action_implicit_account_creation_transfer` seeds a recreated NEAR-implicit account's FullAccess key nonce with `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) . If an implicit account's access key already consumed a nonce `N` at height `H`, and the account is deleted and re-funded (recreated) again at the *same* height `H` (both possible within one chunk since consecutive same-signer transactions with monotonically increasing nonces can be batched and applied sequentially in a single chunk), the freshly-seeded nonce is reset to `(H-1)*MULTIPLIER`, which is strictly less than the previously-consumed `N`. This lets the attacker later resubmit the exact same signed transaction (nonce `N`) and have it pass `verify_nonce`'s Monotonic check again.

### Finding Description
`initial_nonce_value(block_height)` is used both on first creation and on every recreation of a NEAR-implicit account's access key [2](#0-1) . The value depends solely on the *current* `block_height`, with no persisted memory of previously consumed nonces for that account/public-key pair once the account (and its access key row) is deleted via `action_delete_account`, which fully removes the account and its keys (`*account = None;`) [3](#0-2) .

`verify_nonce` in Monotonic mode only requires `tx_nonce > current_nonce`, plus an upper bound of `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [4](#0-3) . The original NEP-71 fix (tested in `access_key_nonce_for_implicit_accounts.rs`) relies on the implicit assumption that recreation of a previously-used implicit account id always happens at a *later* block height than any nonce that was consumed on it, so the reset value `(H2-1)*MULTIPLIER` for `H2 > H` is guaranteed to exceed any nonce `N < H*MULTIPLIER` used earlier [5](#0-4) .

That assumption breaks if the consuming transaction, the `DeleteAccount` transaction, and the re-funding `Transfer` all get applied within the **same** chunk/height `H`:
1. Attacker's implicit-account key signs tx1 with nonce `N` (any regular transaction), satisfying `(H-1)*MULTIPLIER < N < H*MULTIPLIER`; applied at height `H`, stored nonce becomes `N`.
2. Attacker signs tx2 = `DeleteAccount` with nonce `N+1` (still valid against the pre-chunk stored nonce, since Monotonic mode only needs `> current_nonce` and N+1 trivially satisfies this too); applied later in the same chunk, removing the account and its access key.
3. A third transaction (attacker's own named account, or any account) sends a `Transfer` to the same implicit account id, re-creating it in the same chunk/height `H` via `action_implicit_account_creation_transfer`. The new access key nonce is reset to `(H-1)*MULTIPLIER`, which is `< N`.

Because these three transactions are ordinary signed transactions from an unprivileged account, they can all be submitted to a public RPC in quick succession; NEAR's Monotonic nonce mode allows tx1 and tx2 to both pass mempool/chunk-inclusion nonce checks against the same pre-chunk state (since `N+1 > current_nonce` holds independent of `N`), and sequential in-chunk application updates state so tx2 sees tx1's effect. No validator or node-operator privilege is required, only favorable timing/chunk packing, which the attacker can retry at will.

Once nonce is reset to `(H-1)*MULTIPLIER < N`, resubmitting the exact same tx1 (nonce `N`) at any later height passes `verify_nonce` (`N > (H-1)*MULTIPLIER` and `N < H2*MULTIPLIER` for any `H2 ≥ H`), so it is accepted and re-executed — a genuine transaction replay against a resurrected implicit account.

### Impact Explanation
This is a double-spend/replay of a stale signed transaction. Any transaction the attacker previously executed from the implicit account (e.g., a `Transfer` moving funds out, or a `FunctionCall` invoking some other contract) can be re-executed a second time after the account is deleted and refunded at the same height, effectively duplicating whatever action/value transfer the original transaction performed — a fund-theft/double-spend vector matching the "double-spend/replay" bounty category.

### Likelihood Explanation
Preconditions: attacker must control the implicit account's private key (trivial — it's self-generated), must fund/delete/refund the account, and must get the nonce-consuming tx, the delete tx, and the recreation tx applied within the same block height. This is not validator-controlled; it depends on ordinary chunk-packing behavior and can be retried indefinitely at negligible cost until the timing aligns, since Monotonic nonce mode does not require strict adjacency and same-signer transactions are typically queued/applied in submission order within a chunk. This makes the attack probabilistically repeatable rather than deterministic on the first attempt, but feasible for a patient, unprivileged attacker.

### Recommendation
Do not derive the recreated NEAR-implicit access key's nonce purely from the current `block_height`. Either (a) persist a per-account-id high-water-mark nonce that survives `DeleteAccount` (e.g., in a side "tombstone" record) and seed the new key with `max(initial_nonce_value(block_height), tombstone_nonce + 1)`, or (b) forbid recreating an implicit account within the same block height at which it (or a same-id predecessor) was last deleted, forcing at least one height of separation as the original NEP-71 fix implicitly assumed.

### Proof of Concept
Extend `integration-tests/src/tests/features/access_key_nonce_for_implicit_accounts.rs`:
1. Create a NEAR-implicit account at height `H` via a funding `Transfer` (as in `get_status_of_tx_hash_collision_for_near_implicit_account`).
2. In the *same* chunk (same target height, by submitting all three txs before block production and asserting they land in one chunk/height), submit: tx1 signed by the implicit key with nonce `N` (e.g., a self no-op transfer) to consume nonce `N`; tx2 = `DeleteAccount` signed by the implicit key with nonce `N+1`; tx3 = funding `Transfer` from `test1` recreating the same implicit account id.
3. Produce one block and assert all three succeeded at the same `block_height` and that the recreated access key's nonce (`view_access_key`) equals `(H-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, i.e., `< N`.
4. Resubmit tx1 (nonce `N`) again against the recreated account.
5. Assert (expected-safe behavior) `ProcessTxResponse::InvalidTx(InvalidTxError::InvalidNonce{..})`; current code instead returns `ProcessTxResponse::ValidTx` and the transaction executes a second time, demonstrating the replay.

fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())

/// Helper for checking that duplicate transactions from NEAR-implicit accounts are properly rejected.
/// It creates NEAR-implicit account, deletes it and creates again, so that nonce of the access
/// key is updated. Then it tries to send tx from NEAR-implicit account with invalid nonce, which
/// should fail since the protocol upgrade.
fn get_status_of_tx_hash_collision_for_near_implicit_account(
    protocol_version: ProtocolVersion,
    near_implicit_account_signer: Signer,
) -> ProcessTxResponse {
    let epoch_length = 100;
    let mut genesis = Genesis::test(vec!["test0".parse().unwrap(), "test1".parse().unwrap()], 1);
    genesis.config.epoch_length = epoch_length;
    genesis.config.transaction_validity_period = epoch_length * 2;
    genesis.config.protocol_version = protocol_version;
    let mut env = TestEnv::builder(&genesis.config).nightshade_runtimes(&genesis).build();
    let genesis_block = env.clients[0].chain.get_block_by_height(0).unwrap();
    let deposit_for_account_creation = Balance::from_millinear(100);
    let mut height = 1;
    let blocks_number = 5;
    let signer1 = InMemorySigner::test_signer(&"test1".parse().unwrap());
    let near_implicit_account_id = near_implicit_account_signer.get_account_id();

    // Send money to NEAR-implicit account, invoking its creation.
    let send_money_tx = SignedTransaction::send_money(
        1,
        "test1".parse().unwrap(),
        near_implicit_account_id.clone(),
        &signer1,
        deposit_for_account_creation,
        *genesis_block.hash(),
    );
    height = check_tx_processing(&mut env, send_money_tx, height, blocks_number);
    let block = env.clients[0].chain.get_block_by_height(height - 1).unwrap();

    // Delete NEAR-implicit account.
    let delete_account_tx = SignedTransaction::delete_account(
        // Because AccessKeyNonceRange is enabled, correctness of this nonce is guaranteed.
        (height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER,
        near_implicit_account_id.clone(),
        near_implicit_account_id.clone(),
        "test0".parse().unwrap(),
        &near_implicit_account_signer,
        *block.hash(),
    );
    height = check_tx_processing(&mut env, delete_account_tx, height, blocks_number);
    let block = env.clients[0].chain.get_block_by_height(height - 1).unwrap();

    // Send money to NEAR-implicit account again, invoking its second creation.
    let send_money_again_tx = SignedTransaction::send_money(
        2,
        "test1".parse().unwrap(),
        near_implicit_account_id.clone(),
        &signer1,
        deposit_for_account_creation,
        *block.hash(),
    );
    height = check_tx_processing(&mut env, send_money_again_tx, height, blocks_number);
    let block = env.clients[0].chain.get_block_by_height(height - 1).unwrap();

    // Send money from NEAR-implicit account with incorrect nonce.
    let send_money_from_near_implicit_account_tx = SignedTransaction::send_money(
        1,
        near_implicit_account_id.clone(),
        "test0".parse().unwrap(),
        &near_implicit_account_signer,
        Balance::from_yoctonear(100),
        *block.hash(),
    );
    let response =
        env.rpc_handlers[0].process_tx(send_money_from_near_implicit_account_tx, false, false);

    // Check that sending money from NEAR-implicit account with correct nonce is still valid.
    let send_money_from_near_implicit_account_tx = SignedTransaction::send_money(
        (height - 1) * AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER,
        near_implicit_account_id,
        "test0".parse().unwrap(),
        &near_implicit_account_signer,
        Balance::from_yoctonear(100),
        *block.hash(),
    );
    check_tx_processing(&mut env, send_money_from_near_implicit_account_tx, height, blocks_number);

    response
}
