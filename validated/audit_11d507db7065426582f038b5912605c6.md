### Title
`Locked` backoff state in `pallet-scarcity` is keyed only by purse account, not by NFT instance/state-nonce, letting a stale lock block transfer of an unrelated, later-held NFT — ([File: substrate/frame/scarcity/src/extension.rs])

### Summary
`pallet-scarcity`'s `AsScarcity` transaction extension mirrors the BondNFT pattern: a transfer is gated by an auxiliary piece of state (`Locked<T>`) that is supposed to reflect the freshness/validity of the *specific* NFT being moved, but is actually tracked per-account rather than per-instance. Once a purse key accumulates a failed-dispatch lock, that lock blocks transfer of **any** NFT subsequently held at that key — including one that has nothing to do with the transaction that caused the lock — exactly like BondNFT's `epoch[tigAsset]` check blocked transfers of bonds unrelated to why the epoch was stale.

### Finding Description
`Locked<T>` is a `StorageMap<_, Blake2_128Concat, T::AccountId, LockInfo>` [1](#0-0) , keyed solely by the purse-key account. It is written whenever a dispatch authorized through `AsScarcity` fails, with an **exponentially growing** backoff (`2^retries * LockPeriod`, capped at `2^63`) and is only cleared on a subsequent success: [2](#0-1) [3](#0-2) 

`validate()` rejects any `AsScarcity`-authorized transaction from a locked account regardless of which instance/state-nonce is being authorized: [4](#0-3) 

The instance/state-nonce check that is supposed to bind the authorization to the *current* NFT (`nft.instance != *instance || nft.state_nonce != *state_nonce`) is a separate, later check — the `Locked` gate fires first and unconditionally, independent of instance identity: [5](#0-4) 

Nothing in the pallet clears `Locked` for a purse key when a *new* NFT arrives there. `do_force_transfer` only clears `Locked` for the outgoing `from` account, never for `to`: [6](#0-5) 

The `mint` path (`do_mint`) is documented as being able to place a fresh NFT "into any empty purse key" with no destination consent [7](#0-6) , and nothing there is shown to purge a stale `Locked` entry either.

This is the structural analog of the BondNFT issue: BondNFT gated *every* transfer on `epoch[tigAsset]` being fresh, a value unrelated to the specific bond's own expiry; here, every `AsScarcity` transfer is gated on `Locked[owner]` being clear, a value that persists from a stale, unrelated prior failure rather than being scoped to the current `(instance, state_nonce)` pair actually being authorized.

### Impact Explanation
A purse key that has ever accumulated backoff retries becomes progressively (and, past a modest number of retries, effectively permanently, given `2^retries` growth) unable to use the feeless `AsScarcity` transfer/burn path for **any** NFT it subsequently holds — even one minted or force-transferred into it long after the failure and completely unrelated to the original cause. Because the coinage/purse model gives at most one NFT per key and consent-less minting into empty keys, an attacker's own key (or, given typical block-inclusion nondeterminism, any key that can be made to race a same-block `AddressOccupied` failure) can be pushed into a lock state whose duration outlives the specific asset that triggered it. This matches the "permanent user-fund/asset lock" impact class: legitimate NFT transfers revert/are rejected due to stale auxiliary state that is not scoped to the asset being moved, not because the asset itself is invalid.

### Likelihood Explanation
Triggering an initial failed dispatch is fully self-contained and requires no privileged actor: an account controlling two purse keys can cause a benign `AddressOccupied` dispatch failure by submitting two `AsScarcity`-authorized transfers into the same destination within one block (both pass `validate()`'s destination-emptiness pre-check, but only one can win at dispatch time — see the `ensure!(!NftsByOwner::<T>::contains_key(&to)...)` in the call body vs. the extension's own pre-check) [8](#0-7) . Repeating this a handful of times (self-inflicted, no governance/admin/relayer/validator involvement) is sufficient to demonstrate the design flaw; whether a third party can force it onto someone else's key without their cooperation depends on same-block ordering and is not required to prove the core invariant violation.

### Recommendation
Scope the backoff lock to the specific ownership state being protected instead of the bare account: key `Locked` by `(AccountId, InstanceId, state_nonce)` (or at minimum invalidate/clear any existing `Locked` entry for a purse key whenever a new NFT is minted into it or force-transferred into it), so that a lock created for one NFT's failed dispatch can never block a transfer of a different, later-held NFT — mirroring the BondNFT fix of binding the check to `bond.expireEpoch`/the specific asset rather than a shared, staleness-prone global value.

### Proof of Concept
1. Attacker controls purse keys `A` (holding NFT #1, `state_nonce=0`) and `X` (holding NFT #2), and both authorize an `AsScarcity` transfer to the same destination `D` in the same block.
2. Both extrinsics pass `validate()` (each independently observes `D` empty at validation time) [9](#0-8) .
3. Block inclusion executes `X → D` first, succeeding; `A → D` then fails in the call body with `Error::<T>::AddressOccupied` [10](#0-9) .
4. `post_dispatch_details` for `A`'s extrinsic restores NFT #1 to `A` and inserts a `Locked` entry with an exponential backoff `until` timestamp [11](#0-10) .
5. Later, NFT #1 at `A` is burned/transferred away and a brand-new, unrelated NFT #3 is minted into `A` (a valid, consent-less mint per the pallet's purse-key model).
6. `A` attempts to transfer NFT #3 via `AsScarcity`; `validate()` still finds `Locked::<T>::get(&A)` with `lock.until > now` and rejects the transaction with `NftTemporarilyLocked`, even though NFT #3 has no relation to the prior failure [4](#0-3) .

Note: full confirmation that no other code path (e.g. a runtime-specific contract adapter or `do_mint` internals not shown in the excerpts read) clears `Locked` on mint could not be completed within the available reads; the cited storage definition, `validate()`, and `do_force_transfer` show no such clearing, but a Devin session with full repository access should double-check `do_mint`'s body before treating this as fully confirmed.

		fn do_force_transfer(
			owner: &T::AccountId,
			instance: InstanceId,
			to: T::AccountId,
		) -> DispatchResult {
			let from = Instances::<T>::get(instance).ok_or(Error::<T>::UnknownInstance)?;
			let nft = NftsByOwner::<T>::get(&from).ok_or(Error::<T>::UnknownInstance)?;
			ensure!(nft.instance == instance, Error::<T>::UnknownInstance);
			let info =
				Collections::<T>::get(nft.collection).ok_or(Error::<T>::UnknownCollection)?;
			ensure!(info.owner == *owner, Error::<T>::NoPermission);
			ensure!(to != from, Error::<T>::SelfTransfer);
			ensure!(!NftsByOwner::<T>::contains_key(&to), Error::<T>::AddressOccupied);

			let state_nonce =
				nft.state_nonce.checked_add(1).ok_or(Error::<T>::StateNonceOverflow)?;
			let nft = Nft { last_moved: T::UnixTime::now().as_secs(), state_nonce, ..nft };
			NftsByOwner::<T>::remove(&from);
			Locked::<T>::remove(&from);
			NftsByOwner::<T>::insert(&to, nft);
			Instances::<T>::insert(instance, &to);
			Self::deposit_event(Event::ForceTransferred { instance, from, to });
			Ok(())
		}

	fn failed_dispatch_lock(previous: Option<LockInfo>) -> LockInfo {
		let retries = previous.map(|lock| lock.retries.saturating_add(1)).unwrap_or(1);
		let exponent = retries.saturating_sub(1);
		let multiplier = 2u64.saturating_pow(u32::from(exponent).min(63));
		LockInfo {
			retries,
			until: T::UnixTime::now()
				.as_secs()
				.saturating_add(multiplier.saturating_mul(T::LockPeriod::get())),
		}
	}

	fn post_dispatch_details(
		pre: Self::Pre,
		_info: &DispatchInfoOf<<T as frame_system::Config>::RuntimeCall>,
		_post_info: &PostDispatchInfoOf<<T as frame_system::Config>::RuntimeCall>,
		_len: usize,

				NftsByOwner::<T>::insert(&owner, nft);
