### Title
`total_joining_power` Not Decremented on `unlock_with_cap` Allows Inflation of Validator Joining Limit — (`stake.move`)

### Summary

In `stake.move`, `total_joining_power` is incremented whenever an active or pending-active validator adds stake via `add_stake_with_cap`, but it is **never decremented** when that same validator calls `unlock_with_cap` (moving stake from `active` to `pending_inactive`). Combined with `reactivate_stake_with_cap` (which moves stake back from `pending_inactive` to `active` without touching `total_joining_power`), any active validator can cycle `add_stake → unlock → reactivate_stake` repeatedly within a single epoch to inflate `total_joining_power` far beyond the actual net new stake entering the system, causing the `voting_power_increase_limit` guard to falsely trigger and block legitimate new validators from joining the set for the remainder of that epoch.

### Finding Description

`ValidatorSet` tracks two counters:

- `total_voting_power`: current epoch's active voting power
- `total_joining_power`: cumulative new stake added this epoch, enforced against `voting_power_increase_limit` [1](#0-0) 

`add_stake_with_cap` increments `total_joining_power` for any active or pending-active validator: [2](#0-1) 

`update_voting_power_increase` only ever adds to `total_joining_power`: [3](#0-2) 

`unlock_with_cap` moves coins from `active` to `pending_inactive` but does **not** decrement `total_joining_power`: [4](#0-3) 

`reactivate_stake_with_cap` moves coins back from `pending_inactive` to `active` and explicitly notes it does not count as a voting power change — so `total_joining_power` is also not touched: [5](#0-4) 

The `leave_validator_set` path only decrements `total_joining_power` for the `pending_active` case, not for active validators: [6](#0-5) 

**Exploit cycle** (attacker is an active validator with `W` APT in wallet and `A` APT active):

```
repeat N times:
  add_stake(X)        → total_joining_power += X  (coins go to pending_active)
  unlock(X)           → active -= X, pending_inactive += X  (total_joining_power unchanged)
  reactivate_stake(X) → pending_inactive -= X, active += X  (total_joining_power unchanged)
```

After N iterations, `total_joining_power` has grown by `N * X` while the validator's net active stake is unchanged. Each iteration consumes `X` APT from the wallet (deposited into `pending_active`), so the cost is real but the inflation is unbounded within wallet balance.

The guard that is broken:

```move
assert!(
    validator_set.total_joining_power
        <= validator_set.total_voting_power * voting_power_increase_limit / 100,
    error::invalid_argument(EVOTING_POWER_INCREASE_EXCEEDS_LIMIT)
);
``` [7](#0-6) 

Once `total_joining_power` is inflated to the limit, any call to `join_validator_set` or `add_stake` by any other validator will abort with `EVOTING_POWER_INCREASE_EXCEEDS_LIMIT`, blocking all new validator set entries for the rest of the epoch.

### Impact Explanation

An active validator can prevent all other validators from joining the set or adding stake within the current epoch. `total_joining_power` resets to zero at epoch end (`on_new_epoch` line 1403), so the effect is per-epoch. However, the attacker can repeat the attack every epoch at the cost of `N * X` APT per epoch (which accumulates in `pending_active` and is recoverable next epoch). This constitutes a material, repeatable chain availability impact on the validator set admission mechanism. [8](#0-7) 

### Likelihood Explanation

Any existing active validator can execute this with no special privilege beyond holding sufficient APT. The cycle of `add_stake` + `unlock` + `reactivate_stake` is composed entirely of public entry functions with no epoch-boundary constraints. The attacker recovers their staked APT at the next epoch, making the net cost low relative to the disruption caused.

### Recommendation

Decrement `total_joining_power` in `unlock_with_cap` by the amount unlocked, mirroring the decrement already done in `leave_validator_set` for `pending_active` validators:

```move
public fun unlock_with_cap(amount: u64, owner_cap: &OwnerCapability)
    acquires StakePool, ValidatorSet {
    // ... existing logic ...
    let unlocked_stake = coin::extract(&mut stake_pool.active, amount);
    coin::merge<AptosCoin>(&mut stake_pool.pending_inactive, unlocked_stake);

    // Decrement total_joining_power to reflect that this stake is no longer
    // net-new joining power for this epoch.
    let validator_set = borrow_global_mut<ValidatorSet>(@aptos_framework);
    if (validator_set.total_joining_power >= (amount as u128)) {
        validator_set.total_joining_power -= (amount as u128);
    } else {
        validator_set.total_joining_power = 0;
    };
}
```

### Proof of Concept

```move
// Attacker is an active validator with 1000 APT in wallet, 100 APT active.
// voting_power_increase_limit = 50%, total_voting_power = 1000 APT
// => max total_joining_power = 500 APT

// Cycle 10 times with X = 50 APT:
for i in 0..10 {
    stake::add_stake(attacker, 50);        // total_joining_power += 50
    stake::unlock(attacker, 50);           // no change to total_joining_power
    stake::reactivate_stake(attacker, 50); // no change to total_joining_power
}
// total_joining_power is now 500 APT (at the limit)

// Any other validator trying to join now fails:
stake::join_validator_set(victim, victim_pool_address);
// aborts with EVOTING_POWER_INCREASE_EXCEEDS_LIMIT
```

    public fun reactivate_stake_with_cap(
        owner_cap: &OwnerCapability, amount: u64
    ) acquires StakePool {
        assert_reconfig_not_in_progress();
        let pool_address = owner_cap.pool_address;
        assert_stake_pool_exists(pool_address);

        // Cap the amount to reactivate by the amount in pending_inactive.
        let stake_pool = borrow_global_mut<StakePool>(pool_address);
        let total_pending_inactive = coin::value(&stake_pool.pending_inactive);

        coin::merge(&mut stake_pool.active, reactivated_coins);

        event::emit(ReactivateStake { pool_address, amount });
    }

    public fun unlock_with_cap(amount: u64, owner_cap: &OwnerCapability) acquires StakePool {
        assert_reconfig_not_in_progress();
        // Short-circuit if amount to unlock is 0 so we don't emit events.
        if (amount == 0) { return };

        // Unlocked coins are moved to pending_inactive. When the current lockup cycle expires, they will be moved into
        // inactive in the earliest possible epoch transition.
        let pool_address = owner_cap.pool_address;
        assert_stake_pool_exists(pool_address);
        let stake_pool = borrow_global_mut<StakePool>(pool_address);
        // Cap amount to unlock by maximum active stake.
        let amount = min(amount, coin::value(&stake_pool.active));
        let unlocked_stake = coin::extract(&mut stake_pool.active, amount);
        coin::merge<AptosCoin>(&mut stake_pool.pending_inactive, unlocked_stake);

        event::emit(UnlockStake { pool_address, amount_unlocked: amount });
    }

    fun update_voting_power_increase(increase_amount: u64) acquires ValidatorSet {
        let validator_set = borrow_global_mut<ValidatorSet>(@aptos_framework);
        let voting_power_increase_limit =
            (
                staking_config::get_voting_power_increase_limit(&staking_config::get()) as u128
            );
        validator_set.total_joining_power +=(increase_amount as u128);

        // Only validator voting power increase if the current validator set's voting power > 0.
        if (validator_set.total_voting_power > 0) {
            assert!(
                validator_set.total_joining_power
                    <= validator_set.total_voting_power * voting_power_increase_limit
                        / 100,
                error::invalid_argument(EVOTING_POWER_INCREASE_EXCEEDS_LIMIT)
            );
        }
    }
