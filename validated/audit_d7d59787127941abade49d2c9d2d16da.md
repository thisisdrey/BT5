## Finding

### Title
Precompiled-contract array length fields trigger unbounded `byte[][]` allocation from small calldata - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytes32Array` and `extractBytesArray` read an attacker-controlled 32-byte ABI word, convert it with `DataWord.intValueSafe()`, and immediately allocate a Java array sized by that value — with no check that the declared length is consistent with the actual size of the precompile's input `data`. This mirrors the libexpat pattern where a tiny input document supplies a length/count value that the parser trusts before allocating memory proportional to it.

### Finding Description
`extractBytes32Array` and `extractBytesArray` (and the sibling `extractSigArray`) read `len` directly from calldata and allocate an array of that size before validating it against the remaining input: [1](#0-0) 

`DataWord.intValueSafe()` is designed to clamp overflowed values to `Integer.MAX_VALUE` rather than throwing: [2](#0-1) 

Because `len` is taken straight from `words[offset]` (a single attacker-supplied 32-byte word inside the precompile's calldata) and is used to size `new byte[len][]` (or `new byte[][]` in the sibling method) before any bound check against `data.length`, an attacker can submit a very small calldata payload (well under the transaction/data size limits) that encodes a length word such as `0xFFFFFFFF...` (or any value that decodes past 4 bytes), causing `intValueSafe()` to return `Integer.MAX_VALUE` and the subsequent `new byte[Integer.MAX_VALUE][]` allocation to be attempted. This is analogous to the libexpat issue where a small document supplies a large declared size that the library trusts before allocating memory.

A separate helper `isValidAbiEncoding` exists to sanity-check ABI encoding shape, but it is not shown to gate these two extraction helpers in the visible code path, and the allocation in `extractBytes32Array`/`extractBytesArray` happens unconditionally on entry, before any bounds are cross-checked against `data.length`.

### Impact Explanation
An unprivileged contract caller (any account that can invoke a `CALL`/`STATICCALL`/`TRIGGER_SMART_CONTRACT` transaction targeting the precompiled contract address that uses these helpers) can submit a small, cheap calldata payload that forces the node's JVM to attempt an allocation of up to `Integer.MAX_VALUE` array slots. This can throw `OutOfMemoryError` inside TVM execution, and depending on where it propagates, can crash or destabilize the executing full node/SR — a resource-exhaustion/DoS impact on a node's ability to keep serving/validating.

### Likelihood Explanation
Reaching this requires only a single signed transaction invoking the vulnerable precompiled contract with a crafted 32-byte length word; no special privileges, staking, or witness/committee status are required.

### Recommendation
Validate the declared `len` against the actual bounds of `data` (e.g., via `isValidAbiEncoding` or an explicit check that `offset + len` does not exceed `words.length`/`data.length`) before allocating `byte[len][]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`.

    int len = words[offset].intValueSafe();

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
