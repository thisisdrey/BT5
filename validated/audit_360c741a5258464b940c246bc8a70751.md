### Title
Case-insensitive reservation check but case-sensitive uniqueness check allows registering near-identical TRC10 asset names - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator.validate()` enforces asset-name uniqueness (when `AllowSameTokenName == 0`) via a raw byte-array lookup against `AssetIssueStore`, which is strictly case-sensitive, while the adjacent "reserved name" check for `trx` is explicitly case-insensitive. This inconsistency lets any account (asset issuer) register a TRC10 token whose name differs from an already-registered token only by letter case (e.g. `USDT` vs `usdt`), exactly mirroring the reported bug class of a case-sensitive duplicate check that should be case-insensitive.

### Finding Description
Inside `validate()`, the "can't be trx" check normalizes the name before comparing: [1](#0-0) 

But the actual uniqueness/duplicate-token check a few lines later compares the raw, non-normalized bytes of the name directly against the store key: [2](#0-1) 

Because `AssetIssueStore.get()` keys assets by the exact byte value of `assetIssueContract.getName()`, two different accounts (or the same account, subject to the "one asset per account" rule, but different accounts are unrestricted) can register `"USDT"` and `"usdt"` as two distinct, independently valid TRC10 assets. Any unprivileged transaction sender can broadcast an `AssetIssueContract` transaction to become an "asset issuer" — no special permission is required — so this path is fully reachable by an anonymous transaction broadcaster.

### Impact Explanation
This is the same bug class as the reported Octopus Network issue: a case-sensitive duplicate check that should be case-insensitive, enabling name-squatting of financial assets. On java-tron this allows an attacker to register a TRC10 token whose name is visually/textually indistinguishable from a legitimate, already-issued token (differing only by case), enabling asset impersonation/phishing. Users, wallets, or exchanges that resolve tokens by name string can be tricked into interacting with the attacker's imposter token instead of the legitimate one, fragmenting liquidity and potentially resulting in users sending TRX or transferring value to the wrong (attacker-controlled) asset — a concrete unauthorized-value-misdirection vector consistent with the original report's Medium severity rating (Impact 3, Likelihood 3).

### Likelihood Explanation
Any account can trigger this by broadcasting a standard `AssetIssueContract` transaction with a lower/upper-cased variant of an existing token's name; no elevated privileges, timing, or race conditions are required, making this trivially and repeatably exploitable by any unprivileged actor with enough TRX to pay the `AssetIssueFee`.

### Recommendation
Normalize (e.g., lowercase) the asset name before both the reserved-name (`trx`) check and the duplicate/uniqueness check in `AssetIssueActuator.validate()`, so the `assetIssueStore` uniqueness lookup is performed case-insensitively (or store/index a normalized form of the name for existence checks), consistent with how the `trx` reservation is already handled.

### Proof of Concept
1. Attacker/user A broadcasts `AssetIssueContract` with `name = "USDT"`; validation passes the `Token exists` check because no prior entry exists at that exact byte key, and the asset is created (`assetIssueStore.get(assetIssueContract.getName().toByteArray()) == null`) per [2](#0-1) .
2. Attacker/user B (different account) broadcasts `AssetIssueContract` with `name = "usdt"`. The lowercase-normalized `trx`-reservation check does not block it (it is not "trx"), and the `Token exists` lookup on the raw bytes `"usdt"` finds no match (different key than `"USDT"`), so the transaction succeeds and a second, visually confusable token is created.
3. Both tokens now coexist under the same displayed/represented symbol modulo case, which can be leveraged for phishing or asset impersonation against users and integrators that resolve tokens by name.
