### Title
Heap buffer over-read in `InputZipFile::ProcessCentralDirEntry` due to unchecked extra-field length increments - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s ZIP/JAR central-directory parser reads attacker-controlled length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and then walks a nested extra-field loop that advances its cursor by an attacker-controlled `data_size` with no bound checks against the mapped input buffer, mirroring the CVE-2017-16353 pattern of "increments that are never checked" leading to an out-of-bounds read while parsing embedded metadata records.

### Finding Description
`ProcessCentralDirEntry` reads the fixed 46-byte CDH fields, then the variable-length fields, and advances `p` by attacker-supplied `file_name_length` / `extra_field_length` / `file_comment_length` values with **no `EnsureRemaining()` bounds check**, unlike `SkipFile`/`ProcessFile`, which explicitly call `EnsureRemaining` before reading data at `p`: [1](#0-0) 

The nested extra-field loop is worse: it walks `extra_p` from `p` (the start of extra fields) up to the previously computed `p` (start + `extra_field_length`) using `while (extra_p != p)`, reading `header_id`/`data_size` with `get_u2le` and then advancing `extra_p += data_size` where `data_size` is fully attacker-controlled and never validated against the remaining extra-field span or the mapped file length: [2](#0-1) 

If a crafted `data_size` causes `extra_p` to jump past `p` (e.g. skip over the exact end pointer instead of landing on it), the `!=` loop-termination test never becomes true again, so the loop keeps calling `get_u4le`/`get_u2le`/`get_u8le` on `extra_p` far beyond the legitimate extra-field region and beyond the mapped file — an out-of-bounds heap read, directly analogous to GraphicsMagick's `DescribeImage` IPTC-profile loop where pointer increments were never checked against the buffer bounds. The function's own comment ("the central directory is always followed by another data structure that has a signature, so parsing it this way is safe") is the same kind of unfounded trust-in-structure assumption that caused the original CVE.

Compare this to `third_party/ijar/output_jar` / `singlejar`'s `ExtraField::find`, which does perform the equivalent bound check (`ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)` before dereferencing) and to `src/tools/singlejar/output_jar.cc`'s extra-field copy loops, which validate `ef + sizeof(ExtraField) > ef_end` and `ef + ef->size() > ef_end` before every dereference: [3](#0-2) [4](#0-3) 

`ijar/zip.cc`'s equivalent code path has no such check, so the invariant that "untrusted content stays data" (bounded reads only) is broken specifically in `ijar`.

### Impact Explanation
`ijar` is invoked by Bazel's Java toolchain to derive interface jars from `.jar` inputs, including jars that originate from external dependencies fetched by build rules (e.g. `java_import`, jars pulled in through `http_jar`/`maven_install`/other repository rules). A hostile origin serving a crafted `.jar` (an "archive a victim's build consumes") reaches `InputZipFile::ProcessCentralDirEntry` with no checksum-independent bounds validation on the central-directory/extra-field parsing path. The result is an out-of-bounds heap read inside the `ijar` binary process, which can leak adjacent heap memory contents (into computed sizes/offsets that influence subsequent processing) or crash the build (info disclosure primitive matching the CVE's C:H/I:N/A:N profile).

### Likelihood Explanation
Exploitation requires only publishing/serving one attacker-crafted `.jar` file that a build depends on — no MITM, no credential access, no privileged position is needed. The malformed extra-field length values are trivial to construct and the missing bounds check is unconditional (no flag gates this code path), so likelihood is comparable to the original CVE: moderate-to-high given a plausible but non-default consumption of an untrusted `.jar` by an `ijar`-processing build rule.

### Recommendation
Add explicit bounds checks (mirroring `singlejar`'s `ExtraField::find`) in `ProcessCentralDirEntry` before every field read: validate `file_name_length`, `extra_field_length`, and `file_comment_length` against `EnsureRemaining()`/the mapped file length before advancing `p`, and inside the extra-field loop validate that `extra_p + 4` and `extra_p + 4 + data_size` never exceed the extra-field end pointer before dereferencing, erroring out (as `EnsureRemaining` already does elsewhere) instead of trusting length fields taken directly from the input.

### Proof of Concept
A reproducible JUnit/gtest analog (in the spirit of the existing `CreateZipWithMalformedExtraField` helper already present in `src/tools/singlejar/output_jar_simple_test.cc`) would:
1. Build a minimal ZIP/JAR whose Central Directory Header sets `extra_field_length` to a small value (e.g. 4) but embeds an extra-field record whose declared `data_size` (e.g. `0xFFFF`) is far larger than the remaining extra-field bytes.
2. Feed this file to `ijar`'s `InputZipFile::Open`/`ProcessNext` (or directly unit-test `ProcessCentralDirEntry`) and observe that `extra_p` walks past the legitimate extra-field boundary and past the mapped input buffer under ASan, producing a heap-buffer-overflow (read) report — confirming the unchecked-increment out-of-bounds read.
