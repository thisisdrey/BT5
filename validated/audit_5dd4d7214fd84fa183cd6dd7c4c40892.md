### Title
Command Execution via Unrestricted Git `ext::` Transport in `remote` Attribute of `git_repository` — ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
The Bzlmod `source.json` registry format lets a module version declare `type: git_repository`, forwarding a registry-supplied `remote` string verbatim into Bazel's `git_repository` repo rule [1](#0-0) . That `remote` value is passed unmodified to `git remote add origin <remote>` and subsequently used by `git fetch origin ...`, with no restriction on Git's transport scheme (`file`, `ssh`, `ext`, etc.) [2](#0-1) . Git's `ext::` transport helper executes an arbitrary shell command embedded in the URL itself (e.g. `ext::sh -c "id > /tmp/pwned"`), so any registry (or `--registry` mirror) that a build consumes can achieve command execution on the machine running `bazel fetch`/`bazel build` simply by publishing a module version whose `source.json` sets `"type": "git_repository", "remote": "ext::sh -c ..."`.

### Finding Description
`docs/external/registry.mdx` documents that for `source.json` entries with `"type": "git_repository"`, the `remote`, `commit`, `shallow_since`, `tag`, `init_submodules`, `verbose`, `strip_prefix`, and `patch_strip` fields are "directly forwarded to the underlying `git_repository` repo rule" [1](#0-0) . This means the `remote` string, which is registry-controlled content (an "outsider [who] publishes... a registry module version"), flows straight into the git worker without any scheme allow-list.

In `tools/build_defs/repo/git_worker.bzl`, `git_repo()` builds a `_GitRepoInfo` with `remote = str(ctx.attr.remote)` [3](#0-2)  and `_update()` calls `add_origin(ctx, git_repo, ctx.attr.remote)` followed by `fetch(ctx, git_repo)` [4](#0-3) . `add_origin` runs `git remote add origin <remote>` [5](#0-4) , and `fetch` subsequently executes `git fetch origin -- <fetch_ref>` (with a shallow retry) [6](#0-5) .

All actual `git` invocations go through `_execute()`, which only sets `-c core.fsmonitor=false` and unsets a fixed list of `GIT_*` environment variables unrelated to transport security (`GIT_DIR`, `GIT_CONFIG`, etc.) [7](#0-6) . There is no `-c protocol.ext.allow=never`, no `GIT_ALLOW_PROTOCOL` restriction, and no validation of the `remote` string's scheme anywhere in `git.bzl` or `git_worker.bzl`. Git's own default policy for "user" class protocols (which includes `ext` and `file`) is to allow them when the command is invoked directly by a tool/user rather than recursively (e.g., not through a submodule fetch triggered without `GIT_PROTOCOL_FROM_USER=0`), so a direct `git fetch` from Bazel's git worker is not blocked by Git itself.

Because `remote` is forwarded straight from a `source.json` field with no sanitization, a hostile registry (reachable via `--registry`, a compromised BCR mirror, or any registry configured for the build) can supply `"remote": "ext::sh -c '<arbitrary command>'"` for any module version using `type: git_repository`. There is no integrity check analogous to the `integrity` field used for `archive`-type sources — `git_repository` sources have no hash/digest over the transport target itself; only `commit` pins a ref, which is irrelevant once the transport helper has already executed attacker code.

### Impact Explanation
An unprivileged registry operator (or anyone who can get a project to add `--registry` pointing at their host, or a compromise of any registry already trusted by a project, including a BCR mirror) can achieve arbitrary command execution on the machine that runs `bazel fetch`/`bazel build`/`bazel sync`, at the moment Bazel resolves and fetches that module. This is a full authentication/trust-boundary bypass: registries are supposed to only supply *data* describing where/how to fetch sources, not to run code on the client, yet the `ext::` transport turns the `remote` field into a code-execution primitive. Impact is remote code execution with the privileges of the build user — confidentiality, integrity, and availability are all fully compromised (matches the CVSS 9.0 profile of the analog report).

### Likelihood Explanation
Likelihood is high for any project that resolves modules from a registry not fully controlled/audited by the build owner (custom internal registries, third-party registries added via `--registry`, or any registry whose content isn't cryptographically pinned in the lockfile before use). Since `git_repository`-type `source.json` entries are an officially supported registry format and the `remote` field is documented as "directly forwarded," no unusual configuration is required beyond using `--registry` with an untrusted/attacker-influenced registry or depending on a module version whose `source.json` was tampered with.

### Recommendation
- In `tools/build_defs/repo/git_worker.bzl`, restrict Git to only the intended transports before any `git remote add`/`git fetch` call, e.g. pass `-c protocol.ext.allow=never -c protocol.file.allow=user` (or an explicit allow-list of `http`/`https`/`ssh`/`git`) to every `_execute()` invocation, or set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` in the execution environment.
- Validate the `remote` attribute in `git.bzl`/`git_worker.bzl` against an allow-list of URL schemes before use, rejecting `ext::`, `fd::`, and other transport-helper syntaxes.
- When forwarding registry-supplied `source.json` fields of `type: git_repository` into the repo rule, apply the same scheme validation server/client-side so a hostile `source.json` cannot smuggle an `ext::` remote.

### Proof of Concept
1. Stand up (or compromise) a registry served via `--registry=<attacker-registry>` (or a mirror in the resolution chain) containing a module version whose `source.json` is:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c \"touch /tmp/pwned\"",
  "commit": "0000000000000000000000000000000000000000"
}
```
2. Add that module as a (transitive) dependency in `MODULE.bazel` of a victim project, or have the victim add the malicious `--registry` flag.
3. Run `bazel fetch //...` (or any command that triggers repo resolution for that module).
4. Bazel's Bzlmod machinery forwards `remote`/`commit` into the `git_repository` rule; `git_worker.bzl`'s `add_origin` then executes `git remote add origin "ext::sh -c \"touch /tmp/pwned\""`, and `fetch()` runs `git fetch origin ...`, causing Git's `ext` transport helper to execute `sh -c "touch /tmp/pwned"` on the victim's machine — observable via the creation of `/tmp/pwned` (or any attacker-chosen command) with the privileges of the Bazel build user.

A `src/test/shell/bazel` integration test can automate this by serving a local registry (`--registry=file://...`) with the malicious `source.json` above and asserting that the injected marker file/command executed after `bazel fetch @mod//...`.

def add_origin(ctx, git_repo, remote):
    _git(ctx, git_repo, "remote", "add", "origin", remote)

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)

# List of variables to unset when calling `git` to ensure no interference of
# operation. This is in the form of a dict that can be passed to `execute()`.
# This list is taken from the output of `git rev-parse --local-env-vars`

    "GIT_ALTERNATE_OBJECT_DIRECTORIES": None,
    "GIT_CONFIG": None,
    "GIT_CONFIG_PARAMETERS": None,
    "GIT_CONFIG_COUNT": None,
    "GIT_OBJECT_DIRECTORY": None,
    "GIT_DIR": None,
    "GIT_WORK_TREE": None,
    "GIT_IMPLICIT_WORK_TREE": None,
    "GIT_GRAFT_FILE": None,
    "GIT_INDEX_FILE": None,

    "GIT_REPLACE_REF_BASE": None,
    "GIT_PREFIX": None,
    "GIT_INTERNAL_SUPER_PREFIX": None,
    "GIT_SHALLOW_FILE": None,
    "GIT_COMMON_DIR": None,
}

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
