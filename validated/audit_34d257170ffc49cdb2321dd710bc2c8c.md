### Title
Unauthenticated inventory claims combined with a broken reliability-score formula let a single non-responsive peer be repeatedly preferred as the sole download source for an `AttachmentRequest`, permanently starving legitimately-committed attachments - (File: stackslib/src/net/atlas/download.rs)

### Summary
`sources.insert(peer_url.clone(), report.clone())` at `stackslib/src/net/atlas/download.rs:458` populates `AttachmentRequest.sources` purely from an unauthenticated `GetAttachmentsInvResponse` inventory-bit claim, with no proof of possession. Because `AttachmentRequest::get_url()` only queries the single "most reliable" source ` [1](#0-0) ` and `ReliabilityReport::score()` weights raw request volume (`+ n`) more than success ratio ` [2](#0-1) `, a peer that lies about having an attachment and then never serves it can, over repeated retries, accumulate enough `total_requests_sent` to keep outscoring an honest peer, causing the batch to be retried against the malicious peer until `max_attachment_retry_count` is exhausted and dropped ` [3](#0-2) `.

### Finding Description
The claimed equality/fault is: inventory-bit possession claims are trusted without verification, and the peer-selection/scoring logic can end up preferring the lying peer over an honest one across retries, so a committed, resolvable attachment becomes permanently "unresolved" from this node's perspective.

Tracing the code:
1. `get_prioritized_attachments_requests` builds `sources` for each missing `content_hash` purely from whether a peer's previous `GetAttachmentsInvResponse` inventory bit at `position_in_page` is `1` (`stackslib/src/net/atlas/download.rs:434-459`). There is no cryptographic or possession check tied to this bit — any peer can set it for content it has never held.
2. `AttachmentRequest::get_url()` does not fan out to all `sources`; it calls `get_most_reliable_source()`, which picks the single URL with the highest `ReliabilityReport::score()` (`download.rs:1073-1108`). Thus only one peer is actually queried per retry cycle for that `content_hash`, even if honest peers are also listed in `sources`.
3. `ReliabilityReport::score()` computes `total_requests_success * 1000 / (n * 1000) + n` (`download.rs:1299-1305`). Because of the additive `+ n` term, a peer with many total interactions (successes or failures) can outscore a peer with fewer but consistently successful interactions. Inventory-request successes (which are cheap to fabricate and always "succeed" as long as the response decodes, regardless of the bits' truthfulness — `download.rs:507-522`) and any interaction at all increment `total_requests_sent`, inflating `n` and thus the score, over many retries.
4. Reliability reports persist across batch retries in `AttachmentsDownloader.reliability_reports` (`download.rs:47`, updated at `download.rs:182-185`), so a malicious peer's inflated `n` accumulates across the retry loop driven by `bump_retry_count`/`max_attachment_retry_count` (`download.rs:188-204`).
5. If the malicious peer is (or becomes, via this scoring quirk) the top-scored source each retry, the actual content request is sent only to it. It simply never responds (or times out), the request lands in `faulty_peers` with no reliability penalty for that specific interaction path (`download.rs:868-885`), and the cycle repeats until `retry_count >= max_attachment_retry_count`, at which point the batch — including the legitimately committed attachment — is dropped and never resolved (`download.rs:199-204`), even though other honest peers in `context.peers` were queried for inventory and may hold the real content.

Existing guards that do NOT prevent this: attachment content received is validated by recomputing `attachment.hash()` against DB state (`download.rs:154-168`), which correctly prevents a forged attachment payload from being accepted — but this only matters if the malicious peer actually responds; it does nothing to stop the peer from being repeatedly selected as sole query target while never responding at all. There is no possession-proof requirement (e.g., Merkle/inventory freshness challenge) gating entry into `sources`.

### Impact Explanation
This is an availability degradation specific to the Atlas attachment subsystem (BNS zonefiles / off-chain attachments): a validly committed attachment can be permanently marked unreachable/dropped by the local node's downloader despite being served by honest peers, because the request-routing logic (`get_most_reliable_source`) and the flawed reliability scoring can keep steering retries at the same lying, non-responding peer. This matches the "attachment/BNS mismatch" / non-canonical-state-served-as-absent category (a legitimately committed attachment treated as unresolved). It affects only the local node's Atlas view (no forged data is propagated network-wide, no crash, no unauthenticated write), so the severity is bounded to a single-node resolution DoS for specific attachments, contingent on the scoring-formula weakness actually causing the malicious peer to be repeatedly top-ranked, which requires it to accumulate a large `n` relative to honest peers.

### Likelihood Explanation
The attacker only needs to run an ordinary peer that the victim node includes in `network.get_outbound_sync_peers()`, and answer `GetAttachmentsInvResponse` inventory requests with fabricated "has it" bits — both are within the unprivileged remote-peer capability described. However, actually causing sustained top-ranking of the malicious peer depends on the `score()` formula's `+n` bias dominating over time relative to whatever honest peers' scores are, which is dependent on request volume/history and is not deterministic on the first retry; it requires several retry cycles to manifest. This makes the finding a genuine but probabilistic/scoring-design weakness rather than a guaranteed single-message exploit.

### Recommendation
- Do not let raw request count (`n`) inflate the reliability score independent of success ratio; use a bounded ratio-based score (e.g., `success / total`, with tie-breaking by volume only as a secondary key), so peers with poor success rates cannot outrank peers with better success rates purely by having more (even failed) interactions.
- Penalize (bump `total_requests_sent` without success) for inventory claims that are later falsified when the corresponding attachment fetch fails, and consider deprioritizing/blacklisting a `peer_url` after repeated fetch failures for a given `content_hash` within the same batch's retry loop rather than relying solely on the cross-batch persisted score.
- Consider having `AttachmentRequest`/`get_prioritized_attachments_requests` attempt multiple sources per retry (not just the single most-reliable one) so one lying peer cannot monopolize resolution attempts for a `content_hash`.

    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Ord for AttachmentRequest {

        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();

pub struct ReliabilityReport {
    pub total_requests_sent: u32,
    pub total_requests_success: u32,
}

impl ReliabilityReport {
    pub fn bump_successful_requests(&mut self) {
        self.total_requests_sent += 1;
        self.total_requests_success += 1;
    }

    pub fn bump_failed_requests(&mut self) {
        self.total_requests_sent += 1;
    }
}

impl ReliabilityReport {
    pub fn new(total_requests_sent: u32, total_requests_success: u32) -> ReliabilityReport {
        ReliabilityReport {
            total_requests_sent,
            total_requests_success,
        }
    }

    pub fn empty() -> ReliabilityReport {
        ReliabilityReport {
            total_requests_sent: 0,
            total_requests_success: 0,
        }
    }

    pub fn score(&self) -> u32 {
        let n = self.total_requests_sent;
        if n == 0 {
            return n;
        }
        self.total_requests_success * 1000 / (n * 1000) + n
    }
}

impl Ord for ReliabilityReport {
    fn cmp(&self, other: &ReliabilityReport) -> Ordering {
        self.score().cmp(&other.score()).then_with(|| {
            self.total_requests_success
                .cmp(&other.total_requests_success)
        })
    }
}

impl PartialOrd for ReliabilityReport {
    fn partial_cmp(&self, other: &ReliabilityReport) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}
