Let me check `DebtToken.accrueInterest` and other time-based accrual math for an analogous "wrong start timestamp" bug.### Title
`RewardsDistributor._calculateTokenDelta` credits existing holders with `balance × INITIAL_INDEX` when their `accountIndexOf` is 0 — new/untracked accounts receive rewards as if they held since before reward tracking began — ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
Analogous to the `previewPoints` bug (duration measured from `startEpoch` instead of the user's `start`), `RewardsDistributor` computes an account's accrued rewards as `balance * (tokenIndex - accountIndex)`. For an account whose `accountIndexOf` was never initialized, the baseline `accountIndex` is `0` rather than the current token index, so the "elapsed index" is measured from zero instead of from the point the account actually became tracked — inflating rewards the same way measuring staking duration from epoch start inflated points.

### Finding Description
`updateBeforeMintOrBurn` and `updateBeforeTransfer` only set `accountIndexOf[token][account]` when `tokenStates[token_].index > 0`. A user can therefore hold a `DepositToken`/`DebtToken` balance while the distributor has no entry for that token (`index == 0`), leaving `accountIndexOf[token][account] == 0`.

When the governor later enables a speed via `updateTokenSpeed`, the token state is initialized to `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (`INITIAL_INDEX = 1e18`).

In `_calculateTokenDelta`:

```solidity
// contracts/RewardsDistributor.sol
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback to `INITIAL_INDEX` only applies when `_tokenIndex > INITIAL_INDEX`. While `_tokenIndex == INITIAL_INDEX` (i.e., in the window before the first index accrual after enabling rewards — the same block, or any period where `_deltaTimestamps == 0`), the fallback does not trigger. The delta becomes `INITIAL_INDEX - 0 = 1e18`, and `_tokensDelta = balance.wadMul(1e18) = balance`. The account is credited `tokensAccruedOf += balance` — one reward token per deposited/debt token — despite having accrued nothing. This is the same wrong-baseline class: the start point of accrual is implicitly `0` (equivalent to epoch start) instead of the account's actual tracking start.

### Impact Explanation
Theft of unclaimed yield: an account holding a large `DepositToken` balance before rewards are enabled can call `claimRewards` in the same block as the governor's `updateTokenSpeed` transaction (via front-running / builder bundles, or because the index naturally stays `INITIAL_INDEX` when `speed` is set and `deltaTimestamps` is still 0) and instantly receive `balance` units of `rewardToken`, draining the distributor's balance up to its holdings. Other legitimate users' accrued rewards are diluted/drained because `_transferRewardIfEnoughTokens` pays out from a shared balance.

### Likelihood Explanation
- Requires a token whose speed is enabled while users already hold balances — a normal operational sequence (rewards are typically enabled after a deposit/debt token already has supply).
- Requires claiming while `tokenIndex == INITIAL_INDEX`, i.e., within the same timestamp as `updateTokenSpeed` (or whenever `_deltaTimestamps == 0`, e.g., speed enabled but index not yet advanced). Front-running the governor transaction in the same block is an unprivileged action within scope.
- No modifiers stop it: `claimRewards` is permissionless, and `updateBeforeMintOrBurn` skipping `accountIndexOf` writes for unregistered tokens is the root cause.

### Recommendation
Initialize `accountIndexOf` for the account's effective baseline correctly: the fallback should apply whenever `accountIndexOf[token][account] == 0`, not only when `_tokenIndex > INITIAL_INDEX`:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;
}
```

or, equivalently, treat an unset account index as "just joined now" (`_deltaIndex = 0`) rather than `0`. Additionally, consider writing `accountIndexOf` on first balance acquisition even when `tokenStates[token_].index == 0`.

### Proof of Concept
Hardhat-style fork test sketch:

```ts
// 1. Deploy pool, DepositToken (msdETH), RewardsDistributor.
// 2. Alice deposits underlying -> receives msdETH balance.
//    tokenStates[msdETH].index == 0, so accountIndexOf[msdETH][alice] stays 0.
// 3. Governor calls updateTokenSpeed(msdETH, speed) // index = INITIAL_INDEX (1e18), timestamp = now
// 4. In the same block (front-run / same timestamp), Alice calls:
await rewardsDistributor.claimRewards([alice.address], [msdETH.address]);
// 5. _calculateTokenDelta: _accountIndex = 0, _tokenIndex = INITIAL_INDEX
//    condition `_tokenIndex > INITIAL_INDEX` is false -> _accountIndex stays 0
//    _deltaIndex = 1e18 -> _tokensDelta = balanceOf(alice) * 1e18 / 1e18 = balance
// 6. Alice receives `msdETH.balanceOf(alice)` rewardToken for zero elapsed accrual.
expect(await rewardToken.balanceOf(alice.address)).to.eq(await msdETH.balanceOf(alice.address));
```
