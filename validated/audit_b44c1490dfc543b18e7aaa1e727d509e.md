### Title
Unsigned relayer provenance in `RelayData` lets a peer forge/inflate its relay chain, poisoning relay statistics and enabling selective message-relay censorship - (File: stackslib/src/net/chat.rs, stackslib/src/net/p2p.rs)

### Summary
The Solidity report's root cause is that a "referrer" identity is only checked for basic non-self/non-zero validity (`_isValidReferrer`), with no proof that the referrer actually participated, letting the caller freely name any address (including a sybil alias) as referrer and receive repeated, unverified credit. The `stackslib/src/net` analog is `RelayData`/relayer processing: the `relayers: Vec<RelayData>` field attached to every gossiped P2P message is *not* cryptographically bound to the peers it names. Only the outer message envelope (the single "current hop" signature) is verified; the relayer list itself is taken on faith from the immediate sender, checked only for "no duplicate public_key_hash" and "not equal to me," exactly mirroring the referral bug's weak validity check (`referrer != 0 && referrer != user`) with no proof of authenticity.

### Finding Description
`ConversationP2P::process_relayers` validates a received message's `relayers: Vec<RelayData>` with two checks: [1](#0-0) 

- `check_relayer_cycles` only ensures no `public_key_hash` repeats in the list.
- `check_relayers_remote` only ensures the local peer's own `public_key_hash` is not present.

Neither check verifies that the named relayer peers actually signed or forwarded the message — `RelayData { peer: NeighborAddress, seq: u32 }` carries no signature of its own. The overall message is signed once, by the *current* hop's private key, over `relayers || payload`: [2](#0-1) 

This means the sender of a hop can put *arbitrary* `NeighborAddress`/`public_key_hash` values into `relayers` (as long as they're distinct from each other and from the receiver), and the outer signature will still validate, because the signature only proves who sent *this* hop, not who is asserted to have relayed it previously.

After passing the two weak checks, `process_relayers` unconditionally credits per-hop statistics to whatever peer identity is listed: [3](#0-2) 

These forged/inflated relayer identities feed `RelayerStats`, which drives which real peers get selected to receive re-broadcast gossip: [4](#0-3) 

Critically, `sample_broadcast_peers` builds `relay_pubkhs` straight from the (attacker-controlled) `relay_hints`/relayers list and then removes any convo whose live public key hash matches an entry in that set from both the outbound and inbound candidate distributions — on the stated rationale "don't send a message to anyone who sent this message to us." Since the relayer list is unauthenticated, an attacker can name a legitimate victim peer's `public_key_hash` as if it had already relayed the message, causing this node (and, transitively, every node that repeats the same forwarding logic) to skip sending that gossip item to the victim — a selective-censorship/eclipse effect achieved purely by forging metadata inside a normal P2P `Blocks`/`Microblocks`/`NakamotoBlocks`/`Transaction`/`StackerDBPushChunk` push, with `broadcast_message` applying the same "already relayed it" skip using the caller-supplied `relay_hints`: [5](#0-4) 

This is structurally the same equality-of-identity failure as the referral bug: the system trusts a caller-supplied identity as proof of a real action (referral in the Solidity report; having relayed a message here) without any signature/authentication tying that claim to the named party, letting the attacker manufacture "credit"/state for arbitrary addresses of their choosing.

### Impact Explanation
An unprivileged remote peer can, within a single normal gossip message, list one or more forged/victim `NeighborAddress` entries in `relayers`. This:
1. Poisons `NeighborStats`/`RelayerStats` relay-ranking data with fabricated provenance, skewing peer selection for future broadcasts.
2. Causes the receiving node (and any node reusing the same relayer list when it re-broadcasts, since `relay_hints` is threaded from the received message) to withhold gossip data from a legitimate, targeted peer, functioning as a lightweight, remote, unauthenticated censorship/partial-eclipse primitive — achieved with a handful of forged bytes, not volumetric traffic.

This matches the "High" bucket ("steering a node off the tip via false inventory"/analogous denial of legitimate propagation) rather than a full network-wide state corruption, since it affects propagation routing/censorship rather than consensus data itself, and the attacker cannot forge data that is separately validated (blocks/chunks are still separately checked before storage).

### Likelihood Explanation
High. Any authenticated but unprivileged P2P peer can trigger this on every message it forwards — `relayers` is a plain, attacker-populated field in every `StacksMessage`, and only trivial local list-uniqueness/self-exclusion checks are applied before the (forged) data is trusted and propagated into peer-selection logic.

### Recommendation
Do not trust caller-supplied `RelayData` identities as proof of participation:
- Either cryptographically chain-sign each hop (so a relayer's inclusion must be backed by that relayer's own signature over the relay chain up to that point), or
- Stop using the unauthenticated `relayers` list as an input to peer-exclusion/ranking decisions (`sample_broadcast_peers`, `broadcast_message`) entirely, and instead derive "who already has this data" only from directly-observed, locally-authenticated events (e.g., the actual conversation that delivered the message to this node), not from self-reported hop history.

### Proof of Concept
Conceptual PoC (matches existing test scaffolding for `process_relayers`/`sign_relay_message` in `stackslib/src/net/chat.rs`):
1. Attacker `A` is a normal authenticated peer of victim node `V`.
2. `A` crafts a `StacksMessage` (e.g., `Blocks`/`Transaction`) with `relayers = [RelayData { peer: NeighborAddress{ public_key_hash: victim_B_pubkeyhash, .. }, seq: 1 }]`, where `B` is some other real peer `A` wants excluded from receiving this gossip via `V`.
3. `A` signs only the outer envelope with its own key and sends it to `V`.
4. `check_relayer_cycles`/`check_relayers_remote` pass (single distinct entry, not equal to `V`), so `process_relayers` accepts it and records stats crediting `B` as a relayer.
5. When `V` subsequently calls `broadcast_message`/`sample_broadcast_peers` with `relay_hints` derived from this message's relayers, `B`'s live connection is filtered out of the candidate recipients ("it has already relayed it"), even though `B` never saw this message — `V` silently withholds propagation to `B`.     /// Verify that there are no cycles in our relayers list.
    /// Identify relayers by public key hash
    fn check_relayer_cycles(relayers: &[RelayData]) -> bool {
        let mut addrs = HashSet::new();
        for r in relayers.iter() {
            if addrs.contains(&r.peer.public_key_hash) {
                return false;
            }
            addrs.insert(r.peer.public_key_hash.clone());
        }
        true
    }

    /// Verify that we aren't in this relayers list
    fn check_relayers_remote(local_peer: &LocalPeer, relayers: &[RelayData]) -> bool {
        let addr = local_peer.to_neighbor_addr();
        for r in relayers.iter() {
            if r.peer.public_key_hash == addr.public_key_hash {
                return false;
            }
        }
        return true;
    }

    /// Check that a message was properly relayed.
    /// * there are no relay cycles
    /// * we didn't send this
    ///
    /// Update relayer statistics for this conversation
    fn process_relayers(
        &mut self,
        local_peer: &LocalPeer,
        preamble: &Preamble,
        relayers: &[RelayData],
    ) -> bool {
        if !ConversationP2P::check_relayer_cycles(relayers) {
            warn!(
                "Invalid relayers -- message from {:?} contains a cycle",
                self.to_neighbor_key()
            );
            return false;
        }

        if !ConversationP2P::check_relayers_remote(local_peer, relayers) {
            warn!(
                "Invalid relayers -- message originates from us ({})",
                local_peer.to_neighbor_addr()
            );
            return false;
        }

        for relayer in relayers.iter() {
            self.stats
                .add_relayer(&relayer.peer, (preamble.payload_len - 1) as u64);
        }

        return true;
    }

    fn sample_broadcast_peers<R: RelayPayload>(
        &self,
        relay_hints: &[RelayData],
        payload: &R,
    ) -> Result<Vec<NeighborKey>, net_error> {
        // coalesce
        let mut outbound_neighbors = vec![];
        let mut inbound_neighbors = vec![];

        for (_, convo) in self.peers.iter() {
            if !convo.is_authenticated() {
                continue;
            }
            let nk = convo.to_neighbor_key();
            if convo.is_outbound() {
                outbound_neighbors.push(nk);
            } else {
                inbound_neighbors.push(nk);
            }
        }

        let mut outbound_dist = self
            .relayer_stats
            .get_outbound_relay_rankings(&self.peerdb, &outbound_neighbors)?;
        let mut inbound_dist = self.relayer_stats.get_inbound_relay_rankings(
            &inbound_neighbors,
            payload,
            RELAY_DUPLICATE_INFERENCE_WARMUP,

        let mut relay_pubkhs = HashSet::new();
        for rhint in relay_hints {
            relay_pubkhs.insert(rhint.peer.public_key_hash.clone());
