### Title
Unconditional block relay in `try_handle_request` bypasses the `broadcast`/`authorization` gate - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` only requires authentication when the caller explicitly requests `broadcast=1`; an unauthenticated caller with `broadcast` omitted/0 is permitted through with `authenticated=false`, `broadcast=false`. However, `try_handle_request` relays the block to the network via `node.set_relay_message(...)` solely based on whether the block was locally *accepted*, never checking `self.broadcast` or authentication state.

### Finding Description
In `try_parse_request`, the 401 check is narrowly scoped: [1](#0-0) 

`broadcast && !authenticated` is the only guard — an unauthenticated request with `broadcast` omitted (defaults to `false`) sails through with no 401, setting `self.broadcast = Some(false)`.

In `try_handle_request`, `self.broadcast` is passed into `Relayer::process_new_nakamoto_block_ext` as the local "should announce/store" flag, but the *network relay* decision is made independently: [2](#0-1) 

Specifically, `if data_resp.accepted { node.set_relay_message(StacksMessageType::NakamotoBlocks(...)) }` at lines 198-202 is unconditional — it does not consult `self.broadcast` or any authentication flag at all. Any block that chainstate accepts as valid (a normal, syntactically/consensus-valid Nakamoto block an attacker crafts or copies) gets queued into the node's relay/gossip pipeline (`set_relay_message`) regardless of whether the poster supplied `broadcast=1` and a valid `authorization` header. The equality the question poses — "relayed blocks == blocks posted with broadcast=1 AND valid auth" — is broken: an unauthenticated, `broadcast=0` (or omitted) POST of an accepted block is relayed anyway.

The `broadcast` flag therefore only affects what's passed as the `announce`/local-processing parameter into `process_new_nakamoto_block_ext`, not whether the block reaches `node.set_relay_message`, which is the mechanism that pushes messages out to the node's peer-network relay queue.

### Impact Explanation
Any unprivileged remote party who can reach the RPC port can submit a valid Nakamoto block (one that passes chainstate validation) via `POST /v3/blocks/upload/` without any `authorization` header and with `broadcast` omitted or `0`, and still have that block queued for network-wide relay to the node's peers. This defeats the intended purpose of gating `broadcast=1` behind the RPC secret — the auth_token protection for controlling propagation is bypassed entirely for any block the node's chainstate deems acceptable. This is a network-wide propagation / auth-bypass issue matching the "Critical: network-wide propagation of forged data / auth bypass" category, since it lets an unauthenticated caller cause the node to broadcast attacker-supplied (albeit validly-formed) blocks to the wider network on the node's behalf, repeatable per POST.

### Likelihood Explanation
Preconditions are minimal: RPC port reachable (standard configuration), `connection_options.auth_token` configured (this is exactly the config meant to restrict `broadcast=1`), and the attacker only needs a syntactically/consensus-valid `NakamotoBlock` (e.g., one it observed elsewhere, or a block for a fork it can legitimately construct). No secret, no privileged role, and no special peer state beyond normal RPC reachability is required. It is fully repeatable per block/request.

### Recommendation
Gate the `node.set_relay_message(...)` call in `try_handle_request` on `self.broadcast.unwrap_or(false)` (and thus transitively on `authenticated`, since `try_parse_request` already forces `authenticated == true` whenever `broadcast == true`). I.e., change:
```rust
if data_resp.accepted {
    node.set_relay_message(...)
}
```
to:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...)
}
```
so that only explicitly-authenticated, `broadcast=1` requests result in network relay.

### Proof of Concept
Rust test in `stackslib/src/net/api/tests/postblock_v3.rs`:
1. Construct `RPCPostBlockRequestHandler::new(Some("supersecret".to_string()))`.
2. Build an `HttpRequestPreamble` for `POST /v3/blocks/upload/` with no `authorization` header and no `broadcast` query parameter (or `broadcast=0`), content-type `application/octet-stream`, body = a valid serialized `NakamotoBlock` that chainstate will accept.
3. Call `try_parse_request` — assert it returns `Ok(..)` (no 401) and `handler.broadcast == Some(false)`.
4. Set up a `TestPeer`/`StacksNodeState` such that `process_new_nakamoto_block_ext` returns an "accepted" result for this block.
5. Call `try_handle_request` and then inspect the node state's queued relay message (e.g., via the mechanism `set_relay_message` populates, checked through `PeerNetwork`/`chat.rs` relay message field or an event observer hook) — assert a `StacksMessageType::NakamotoBlocks` message containing the block is present, despite `handler.broadcast == Some(false)` and no authentication having occurred.

Note: I was unable to fully trace, due to iteration limits, the exact downstream consumer of `set_relay_message` in `stackslib/src/net/chat.rs` / `stackslib/src/net/mod.rs` to confirm the precise mechanics of how the queued message is dispatched to peers (i.e., whether it goes straight to p2p broadcast or some additional check exists further downstream). Based on the code directly in `postblock_v3.rs`, the relay call is unconditionally reached without any broadcast/auth check, which is the core bug regardless of downstream dispatch details.
