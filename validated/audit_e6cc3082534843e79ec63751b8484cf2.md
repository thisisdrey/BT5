Based on the evidence gathered, I found a real local analog: an unbounded, user-supplied gas value that is trusted verbatim by the fee-calculation logic for Snowbridge V2 outbound messages.

### Title
Attacker-controlled `gas` field in `Command::CallContract` is trusted directly for fee calculation, enabling underpriced Ethereum dispatch and stuck/failed cross-chain calls - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

### Summary
The Wormhole report's root cause is that gas-cost estimation used to price message delivery is disconnected from the actual gas that will be required to execute on the destination chain, allowing execution to fail with insufficient gas while fees were already collected/committed. Snowbridge V2 has a structurally similar bug in the opposite direction: instead of an *immutable* value going stale, the gas figure used to price delivery for `Command::CallContract` is *fully attacker-controlled* and passed straight through to the fee meter without any bound, so a low-privilege XCM sender determines their own delivery price while the same number is what limits execution on Ethereum.

### Finding Description
The `GasMeter` trait implementation for V2 messages computes the priced gas for a `CallContract` command by simply returning the caller-supplied value verbatim: [1](#0-0) 
This `gas` originates from `ContractCall::V1 { gas, .. }`, decoded from an XCM `Transact` payload that any account able to submit XCM (e.g. any parachain or user via `PolkadotXcm::execute`/`send`) can construct: [2](#0-1) [3](#0-2) 

The converter (`XcmConverter::convert`) validates only that the fee asset is present and, for value transfers, that `value` does not exceed the amount reserved (`CallContractValueInsufficient`) — there is no validation, minimum, or maximum bound on `gas` itself. That `gas` value then flows unchanged into `Command::CallContract`, and from there directly into `GasMeter::maximum_dispatch_gas_used_at_most`, which is the quantity used to compute the delivery fee (analogous to `calculate_fee`/`calculate_remote_fee` in the V1 pallet, which multiplies gas by `fee_per_gas` and adds the relayer `reward`): [4](#0-3) 

Because the same `gas` value is both (a) the sole input used to price the message (fee charged to the user) and (b) the maximum gas forwarded to the target contract call on Ethereum, an unprivileged sender can set an arbitrarily low `gas` (e.g. `40000` as used even in the emulated test fixtures) to minimize the fee paid while still passing conversion — with no chain-side sanity floor tied to realistic Ethereum execution cost for whatever `target`/`calldata` is being called. This mirrors the Wormhole bug's "static/uncoupled gas estimate causes execution failure on the target chain," except here the value is not merely stale — it is adversarially chosen by the message's own author, and it is used to *both* underprice the relayer reward *and* under-provision the Ethereum-side call.

### Impact Explanation
If the `gas` supplied is too low for the target contract call to succeed, the `CallContract` command will revert/fail on Ethereum execution (out-of-gas), while assets deposited via preceding `DepositAsset` commands in the same message may already have settled to the beneficiary depending on Gateway contract ordering — this can strand a bridge-side effect against a chain that already collected the (deliberately underpriced) relayer reward, or leave a message permanently unexecutable on Ethereum with no on-chain retry/adjustment mechanism, since `gas` is embedded once into the immutable committed message and cannot be revised after commitment (the equivalent of the report's "gas limit has no impact on pending transfers already ready for execution"). This also lets any XCM sender systematically underpay the relayer/gas component of the fee relative to actual required Ethereum gas, degrading the economic security of the delivery-fee model described in the module docs (`RemoteFee(Message) = MaxGasRequired(Message) * Params.MaxFeePerGas + Params.Reward`), which assumes `MaxGasRequired` reflects a real, chain-enforced bound rather than a value chosen by the fee payer.

### Likelihood Explanation
Any account capable of executing or sending XCM through `PolkadotXcm` with a `Transact`/`ContractCall::V1` targeting Ethereum can trigger this without governance, admin, relayer, or validator collusion — it is a pure unprivileged-user public entrypoint path (`EthereumBlobExporter` / `XcmConverter::convert`), matching the "public underpriced work" and "unauthorized/uncharged nested execution" pivot criteria.

### Recommendation
Enforce a governance-configured minimum and maximum bound on the `gas` field accepted by `XcmConverter::convert` for `Command::CallContract` (similar to the fixed per-command gas figures used for `SetOperatingMode`, `UnlockNativeToken`, etc. in `ConstantGasMeter`), rather than trusting the caller-supplied value outright, so the fee-pricing input cannot be manipulated independently of the value actually needed/enforced for execution.

### Proof of Concept
1. An unprivileged account on AssetHub/Penpal submits `PolkadotXcm::execute` with an XCM program containing `InitiateTransfer { destination: ethereum(), remote_xcm: [DepositAsset, Transact { call: ContractCall::V1{ target, calldata, gas: <very low value>, value }.encode() }, SetTopic] }`, exactly as done in the existing test `transact_with_agent_from_asset_hub` (which itself uses `gas: 40000`, an arbitrary, unvalidated figure).
2. `XcmConverter::convert` accepts this without checking `gas` against any minimum required for `target`/`calldata`, producing `Command::CallContract { target, calldata, gas, value }`.
3. `ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns `gas` verbatim, and this is what determines the fee charged to the sender for remote execution.
4. On Ethereum, the Gateway contract forwards at most `gas` to the target call; if it is insufficient for the target logic, the call fails while the sender paid a fee sized to their own understated `gas`, and the committed message (embedding this gas value) cannot be repriced after commitment. impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
