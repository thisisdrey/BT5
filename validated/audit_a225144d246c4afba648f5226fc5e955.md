### Title
Unbounded, caller-supplied `gas` value for `Command::CallContract` lets unprivileged senders underprice Snowbridge outbound delivery fees - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

### Summary
The external report's core defect is: a trusted value (`authority`-set `nominals`) is consumed downstream in a settlement calculation with no bound/sanity check, letting whoever controls that value force an economically wrong outcome (drain the vault). The closest verifiable local analog is in the Snowbridge v2 `GasMeter` implementation used by the outbound-queue pallet to compute delivery fees. For every other `Command` variant, `ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns a fixed, conservative constant chosen from gas-report benchmarking. For `Command::CallContract`, it instead echoes back the `gas` field taken directly from the command payload with no minimum, maximum, or plausibility check: [1](#0-0) 

### Finding Description
`GasMeter::maximum_dispatch_gas_used_at_most` is the sole input that downstream fee/commit logic in `outbound-queue-v2` uses to (a) compute the on-chain committed `gas` attached to the message for Ethereum-side execution, and (b) size the delivery fee charged upfront to cover relayer compensation: [2](#0-1) 

For every hard-coded command (`SetOperatingMode`, `Upgrade`, `UnlockNativeToken`, `RegisterForeignToken`, `MintForeignToken`), the gas estimate is a fixed constant derived from measured worst-case Solidity gas usage, so the value cannot be manipulated by whoever constructs the message. `CallContract` breaks this invariant by trusting the caller-supplied `gas` field verbatim: [3](#0-2) 

Because `Command::CallContract` is reachable from XCM (`bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs` builds `Command`s, including `CallContract`, from XCM instructions exported by `SnowbridgeMessageExporter`/AssetHub users), an unprivileged sender who can trigger a bridge export can choose an arbitrarily low `gas` value for their command. This directly and proportionally lowers the computed remote fee, since `calculate_fee`-style logic (see the v1 sibling pallet for the same pattern) scales the fee with `gas_used_at_most`: [4](#0-3) 

No code path clamps `gas` to a sane floor/ceiling before it is used both as the fee basis and as the gas actually committed for execution on Ethereum, so the "authority sets nominal = 0" pattern from the external report reappears here as "unprivileged sender sets `gas` = 0 (or 1)".

### Impact Explanation
A near-zero `gas` in `Command::CallContract` produces a near-zero remote-fee contribution while the message still consumes a slot in `MessageLeaves`/`Messages` (bounded by `MaxMessagesPerBlock`) and is committed into the merkle root for Ethereum delivery. This is "public underpriced work" that can be used to flood the outbound queue with cheap-to-produce, expensive-to-relay (or execution-doomed) commitments, degrading relayer economics and potentially stalling bridge message throughput — one of the explicitly accepted impact classes for this program.

### Likelihood Explanation
The `gas` field is command-payload data, not derived from any privileged or governance-only origin at the `GasMeter` layer itself; the pallet's own trait design treats it as untrusted input for every other variant (hence the fixed constants) but not for `CallContract`. This makes the path reachable without any admin, relayer, or validator compromise — only an ordinary bridge user with access to the XCM export path is required. I could not fully verify inside this session which precise XCM instruction sequence reaches `convert.rs`'s `CallContract` construction, so likelihood should be treated as plausible-but-unconfirmed pending that file's full contents.

### Recommendation
Clamp `Command::CallContract`'s `gas` to a governance-configured `[MIN_CALL_GAS, MAX_CALL_GAS]` range inside `ConstantGasMeter::maximum_dispatch_gas_used_at_most`, rejecting or saturating out-of-range values before they influence fee calculation, consistent with how every other `Command` variant already uses a fixed, audited constant.

### Proof of Concept
Conceptual PoC (bounded by the same uncertainty noted above):
1. An unprivileged AssetHub user constructs an XCM message that is exported to Ethereum containing a `Transact`/`CallContract`-equivalent instruction targeting an arbitrary Ethereum contract, specifying `gas: 1`.
2. `convert.rs` converts this into `Command::CallContract { gas: 1, .. }`.
3. `ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns `1` verbatim (`message.rs:303`), which is used both as the committed `gas` in `CommandWrapper` and as the input to remote-fee computation, yielding a delivery fee far below the actual cost of dispatching/verifying the message.
4. The message is committed to `MessageLeaves` and consumes one of `MaxMessagesPerBlock` slots at negligible cost, which can be repeated to cheaply saturate outbound queue capacity per block.

Note: step 1–2 rely on `convert.rs`, which I was unable to fully inspect in this session — confirming the exact caller-reachable entry point requires reading that file's full contents (recommended before treating this as fully proven).

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
