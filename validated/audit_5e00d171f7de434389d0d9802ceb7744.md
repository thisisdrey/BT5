The claimed equality/fault — that a peer's response bytes should hash-match the requested `content_hash` before `ReliabilityReport.bump_successful_requests()` is called — is broken in the code. No such check exists.

### Title
Reliability score poisoning via unauthenticated attachment hash mismatch - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` calls `report.bump_successful_requests()` for any peer response that successfully JSON-decodes via `decode_atlas_get_attachment()`, without ever comparing the decoded `Attachment`'s hash to the `AttachmentRequest.content_hash` that was actually requested. Any remote unprivileged peer serving arbitrary decodable bytes (any content ≤ `attachments_max_size`) is rewarded with a `bump_successful_requests()` instead of `bump_failed_requests()`, inflating its `ReliabilityReport` score used by `AttachmentRequest::get_most_reliable_source()`.

### Finding Description
`AttachmentRequest` stores `content_hash: Hash160` and a `sources: HashMap<UrlString, ReliabilityReport>` [1](#0-0) . Requests are dispatched to the most-reliable source via `get_most_reliable_source()`, which picks the peer with the highest `ReliabilityReport::score()` [2](#0-1) .

When the batched HTTP responses come back, `extend_with_attachments` processes each `(request, response)` pair:

```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [3](#0-2) 

`decode_atlas_get_attachment` only parses the HTTP body as JSON and builds an `Attachment` from the hex-decoded bytes — it performs no comparison against `request.content_hash` [4](#0-3) . `ReliabilityReport::bump_successful_requests()` simply increments both counters unconditionally [5](#0-4) .

So a malicious peer that is queried for `content_hash` can return any well-formed JSON `GetAttachmentResponse` whose content hashes to something else entirely (size-bounded only by `attachments_max_size`/HTTP body limits), and it will still be scored as a successful request.

Downstream, the forged `Attachment` is inserted into `self.attachments` (a `HashSet<Attachment>`), and in `AttachmentsDownloader::run` the code looks up `find_all_attachment_instances(&attachment.hash())` and calls `insert_instantiated_attachment(&attachment)`, then `context.attachments_batch.resolve_attachment(&attachment.hash())` [6](#0-5) . Because `insert_instantiated_attachment` keys both the `attachments` table insert and the `attachment_instances` update by `attachment.hash()` (the forged data's own hash) rather than by the originally requested `content_hash` [7](#0-6) , the forged content is not bound to the legitimately-requested `AttachmentInstance`; the real batch entry for `content_hash` remains unresolved and is retried/eventually dropped after `max_attachment_retry_count`.

The actual, real impact is therefore not "wrong data served as canonical" for the *requested* hash, but reliability-score poisoning: the malicious peer's `ReliabilityReport.total_requests_success`/`total_requests_sent` are bumped as if it correctly served data, so `get_most_reliable_source()` and `Ord for ReliabilityReport`/`AttachmentRequest` will preferentially route future attachment/BNS zonefile requests to that peer [8](#0-7) , letting it repeatedly stall or delay resolution of legitimate BNS attachments for other peers that rely on the shared `reliability_reports` map in `AttachmentsDownloader` (persisted across batches and peers) [9](#0-8) .

### Impact Explanation
An unprivileged peer can indefinitely inflate its own reliability score for zero-cost (serving trivial junk bytes that merely decode as valid hex/JSON), causing the node to systematically prefer that peer for future attachment fetches. This does not corrupt the on-disk `attachments`/`attachment_instances` tables for the originally requested content (because storage/update keys off the forged data's own hash), so it does not achieve "attachment/BNS mismatch" in the sense of the wrong content being bound to and served for a legitimate content-hash query — that binding is protected by the `WHERE content_hash = attachment.hash()` clause. The realized impact is limited to reliability-score manipulation causing repeated stalls/delays in legitimate attachment resolution (denial/delay, bounded per retry-count), not serving of non-canonical data as canonical.

### Likelihood Explanation
Trivial and repeatable: any peer already selected as an outbound sync peer with a `data_url` can be queried for any `content_hash`, and simply returning a validly-JSON-encoded but wrong-hash `GetAttachmentResponse` triggers `bump_successful_requests()` on every request, for free, with no signature or hash check blocking it.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, compare `response.attachment.hash()` to `request.content_hash` before calling `report.bump_successful_requests()`; call `report.bump_failed_requests()` (and optionally treat as a faulty peer) when the hashes don't match.

### Proof of Concept
Rust test (in `stackslib/src/net/atlas/tests.rs` style, using `new_attachment_request`/`BatchedRequestsResult`):
1. Build an `AttachmentRequest` with `content_hash = Hash160::from_data(b"real")` and a single source peer in `sources`.
2. Construct a fake `StacksHttpResponse` whose JSON body decodes via `decode_atlas_get_attachment()` to `Attachment::new(b"forged".to_vec())` (hash differs from `content_hash`).
3. Put `(request.clone(), Some(fake_response))` into `BatchedRequestsResult::succeeded`.
4. Call `context.extend_with_attachments(&mut results)`.
5. Assert `context.peers.get(&peer_url).unwrap().total_requests_success == 1` (and `total_requests_sent == 1`), proving the forged/mismatched response was scored as fully successful with no `bump_failed_requests()` call — i.e., no penalty for hash forgery.
