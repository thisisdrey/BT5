Confirmed: the `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` list in `core/primitives/src/trie_key.rs:89-102` explicitly excludes `DelayedReceipt`/`DelayedReceiptIndices` and `BufferedReceipt`/`BufferedReceiptIndices` — these keys carry only an `index`/`receiving_shard`, never an `account_id` [1](#0-0) [2](#0-1) . `remove_account` only ever removes `TrieKey::Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` [3](#0-2)  — it has no way to reach into these global FIFO queues.

### Title
Authorization escalation via delete/recreate of an account whose self-addressed receipt is stuck in the DelayedReceipt/BufferedReceipt congestion queues - ([File: runtime/runtime/src/lib.rs])

### Summary
`apply_action`/`check_actor_permissions` authorize privileged actions (`AddKey`, `DeleteKey`, `DeployContract`, `Stake`, `WithdrawFromGasKey`, `UseGlobalContract`, `DeleteAccount`) purely by comparing `actor_id == account_id` as `AccountId` strings, where `actor_id` is freshly initialized from `receipt.predecessor_id()` at the moment the receipt is finally executed [4](#0-3) [5](#0-4) . Because a self-addressed receipt (`predecessor_id == receiver_id == "victim.near"`) trivially satisfies this check regardless of when it is dequeued, an attacker can queue such a receipt (via congestion backpressure into `DelayedReceiptQueue`), delete the account, have a third party recreate the same `AccountId`, and have the queued receipt still execute the privileged action against the new account.

### Finding Description
`check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) gates `AddKey`, `DeployContract`, `Stake`, `DeleteKey`, `UseGlobalContract`, `WithdrawFromGasKey`, and `DeleteAccount` on `actor_id == account_id` [6](#0-5) . `actor_id` is not a persisted, ownership-bound value; it is recomputed every time a receipt is executed, seeded from the serialized receipt's own `predecessor_id` field: `let mut actor_id = receipt.predecessor_id().clone();` in `apply_action_receipt` [7](#0-6) . For a receipt an account sends to itself (`predecessor_id == receiver_id`), this check passes unconditionally, independent of the account's storage/ownership state at execution time.

Such self-receipts do not need to be postponed on input data — they can also sit in the global, non-account-keyed `DelayedReceiptQueue` (`TrieKey::DelayedReceipt`) when the chunk's compute/gas limit is exhausted (`process_delayed_receipts`, `runtime/runtime/src/lib.rs:2464-2557`; queue push/pop in `DelayedReceiptQueueWrapper`, `congestion_control.rs:802-889`), or in the per-destination `BufferedReceipt` queue when outgoing bandwidth/congestion limits block forwarding (`ReceiptSinkV2WithInfo::forward_or_buffer_receipt`, `congestion_control.rs:292-325`). Both queues store receipts keyed only by `index`/`receiving_shard`, confirmed to have **no `account_id` in their trie key** by their absence from `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` [1](#0-0) .

`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` keys — it has no mechanism to scan or purge global queues, and doing so would be operationally infeasible (would require draining/rewriting the entire FIFO queue on every `DeleteAccount`). Thus this path is structurally outside anything `remove_account` could ever fix; the root cause is that `check_actor_permissions`/`apply_action` never validate that the account executing a queued receipt is the *same account incarnation* that created it.

Exploit flow:
1. Attacker account `victim.near` builds up chunk/shard congestion (e.g., saturates the local compute limit for its shard with cheap self-receipts, or exploits bandwidth-scheduler backpressure) so that a crafted self-receipt (`predecessor_id = receiver_id = "victim.near"`, containing e.g. an `AddKey(attacker_pubkey, FullAccess)` action) is pushed into `DelayedReceiptQueue` instead of executing immediately.
2. While the receipt is queued, attacker submits `DeleteAccount(beneficiary)` on `victim.near`, passing `check_actor_permissions`'s `actor_id == account_id` check trivially (self-action) and calling `remove_account`, which removes the account record and keys but does nothing to the delayed receipt.
3. A third party (or the `near`/`testnet` registrar contract on behalf of a new user) issues `CreateAccount` for `victim.near` again (a legitimate re-registration of a freed name), depositing funds and adding their own keys.
4. In a later chunk, `process_delayed_receipts` pops the queued receipt and executes it via `apply_action_receipt` → `apply_action`. `actor_id` is seeded from `receipt.predecessor_id()` = `"victim.near"`, and `account_id` = `receiver_id()` = `"victim.near"`; `check_actor_permissions` passes, and the attacker's `AddKey` (or `DeployContract`/`Stake`/etc.) executes against the **new** owner's account without the new owner's authorization.

### Impact Explanation
This is an authorization escalation across the account-deletion/recreation boundary: the original attacker regains full control (`AddKey FullAccess`) or otherwise manipulates (deploy contract, stake, drain via `WithdrawFromGasKey`) an account now funded and controlled by an unrelated party, without any signature from the new owner. Concretely this is theft of funds deposited into the recreated account and/or hijacking of a freshly-registered account identity — matching the "authorization escalation across accounts" and "theft of funds" bounty categories.

### Likelihood Explanation
Feasibility hinges on two preconditions that are hard to guarantee for an unprivileged attacker in isolation: (1) reliably forcing a *self*-receipt into the `DelayedReceiptQueue` requires winning a race against a shard's compute/gas limit under real network conditions — the spec notes that same-shard sends get `Gas::MAX` treatment in `ReceiptSink::new` (`congestion_control.rs:105-110`), so a self-receipt is far more likely to be admitted via `process_incoming_receipts`'s local/incoming path being pushed into `DelayedReceiptQueue` only when the *whole chunk's* compute budget is exhausted by other traffic, not through `BufferedReceipt` (which is keyed to cross-shard destinations and a same-shard self-receipt never buffers there); and (2) getting an outside party to recreate the exact deleted `AccountId` in the delay window is plausible for `.near`-registrar-mediated named subaccounts (`action_create_account` requires the predecessor to be the direct parent, `actions.rs:155-181`) but is not attacker-controlled timing. Both steps are achievable without validator/node privileges (only self-transactions and a plausible external re-registration), but the timing window (must land inside the same delay interval before the queued receipt drains) makes this an opportunistic, not fully attacker-deterministic, exploit — still reproducible in a controlled test-loop/apply-path setting.

### Recommendation
Bind `actor_id`/authorization for privileged actions to something more durable than the bare `AccountId` string comparison across a delete/recreate boundary — e.g., invalidate/drop in-flight receipts addressed to an account at `DeleteAccount` time (impractical for global queues as shown), or introduce an account "generation"/incarnation counter that is bumped on every `CreateAccount` and checked against a generation captured on the queued receipt/promise, so a receipt created against generation N cannot execute privileged actions against generation N+1 of the same `AccountId`. This must live in the actor-permission check (`check_actor_permissions`/`apply_action`), not in `remove_account`, since the affected queues (`DelayedReceipt`, `BufferedReceipt`) are structurally global and not account-keyed.

### Proof of Concept
Integration test in the apply-path / test-loop harness:
1. Configure a low `gas_limit`/congestion config via `ApplyState` so a controlled sequence of receipts to `victim.near` exceeds the chunk compute budget, forcing a crafted self-receipt (`predecessor_id = receiver_id = victim.near`, action = `AddKey(attacker_key, FullAccess)`) into `DelayedReceiptQueue` (assert via `DelayedReceiptQueue::load` that the receipt is present after one `apply`).
2. In the next chunk, submit `DeleteAccount(beneficiary)` from `victim.near` and assert `get_account(state_update, "victim.near")` returns `None` while the delayed receipt entry still exists in the queue.
3. Submit `CreateAccount` for `victim.near` with a new owner's key (simulating third-party re-registration) and fund it.
4. Run further chunks until `process_delayed_receipts` drains the queued `AddKey` receipt; assert that the new account's access keys do **not** include the attacker's `attacker_key` (expected/fixed behavior) — currently, without a fix, the test would show the attacker's key present on the account, demonstrating the escalation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}
