### Title
`nft_resolve_withdraw` re-credits an NFT balance whose underlying token was already delivered by an attacker-controlled `nft_transfer_call` returning malformed JSON - ([File: contracts/defuse/src/contract/tokens/nep171/withdraw.rs])

### Summary
`NonFungibleTokenWithdrawResolver::nft_resolve_withdraw` treats any promise result that fails to deserialize as `bool` as `used = false` and unconditionally re-credits the withdrawn NFT unit back to `sender_id`, even though the promise succeeded and the underlying NFT contract may have already transferred the token. Since `token` and `receiver_id` are both attacker-controlled, the attacker can deploy an NFT contract whose `nft_transfer_call` performs a genuine transfer but returns a non-bool JSON body (e.g. a string), forcing the resolver down the `Ok(Err(_deserialization_err)) => false` branch and re-minting an internal ledger balance for an NFT that Defuse no longer custodies.

### Finding Description
Binding: `total_supplies[Nep171TokenId] == 1` (NFT physically custodied by the Verifier) must always equal outstanding internal claims on that id. The withdraw path breaks this:

1. `internal_nft_withdraw` (contracts/defuse/src/contract/tokens/nep171/withdraw.rs:58-110) calls `self.withdraw(...)`, which decrements the owner's balance and `total_supplies` for the `Nep171TokenId` by 1 [1](#0-0) , then schedules `do_nft_withdraw` → `ext_nft_core::nft_transfer_call` on the attacker-supplied `token` contract, followed by `nft_resolve_withdraw` as a callback [2](#0-1) .
2. Because `token` is a contract the attacker deploys and controls, its `nft_transfer_call` can legitimately transfer/burn the NFT to `receiver_id` (also attacker-controlled) yet return a JSON body that isn't a `bool` (e.g., `"ok"`).
3. In the callback, `promise_result_checked_json::<bool>(0)` succeeds at the promise level (no panic) but `serde_json::from_slice::<bool>` fails, yielding `Ok(Err(_deserialization_err))`, which is explicitly mapped to `used = false` [3](#0-2) .
4. Since `used == false`, the resolver calls `self.deposit(sender_id, [(Nep171TokenId::new(token, token_id).into(), 1)], ...)`, re-adding 1 unit to `sender_id`'s balance and to `total_supplies` [4](#0-3) . The `deposit` function only rejects the re-credit if `total_supply > 1` after the add [5](#0-4) ; since it was decremented to 0 by the withdraw step, the re-add brings it back to exactly 1, so the guard never fires.

Net effect: the ledger again shows `sender_id` owning the NFT (`total_supplies = 1`), but the actual NFT was already delivered off-chain to the attacker's own `receiver_id` on the attacker's own contract — Defuse no longer has custody. This is a genuine double-credit of a unique NFT id, exactly matching the CONSERVATION/`NftAlreadyDeposited` invariant this check is meant to protect, because the check only guards against re-depositing while custody is still intended to be tracked, not against a resolver credit issued after custody has verifiably left the contract via a successful (if malformed) promise result.

Existing guards do not prevent this: `#[private]` only restricts the caller of `nft_resolve_withdraw` to the contract itself (satisfied via the scheduled callback), and the `Err(_) => true` branch (comment about the NEP-141/`nft_on_transfer` gas issue) only covers promise *failure*, not a *succeeding* promise with an unparsable body — which is exactly the gap the attacker exploits by controlling the callee's response format.

### Impact Explanation
The attacker obtains one unit of internal Defuse balance for an `Nep171TokenId` that is no longer backed by custody the Verifier holds — the real NFT already left the contract's control during the same withdrawal. This falsely-recredited balance can subsequently be used inside further intents (e.g., traded/settled against a counterparty's real tokens via `execute_intents`), so real value can leave the Verifier or be extracted from a counterparty without any corresponding backing NFT, and the accounting invariant (`total_supplies` matching real custody) is violated. This matches the Critical category: a refund/resolver credit that does not match what actually failed to settle, breaking the conservation invariant. It is repeatable per attacker-deployed NFT contract/`token_id`, but bounded to NFTs the attacker deposited and controls the withdrawal target for — each exploitable NFT id yields one fraudulent re-credit.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: they deploy their own NFT contract, mint/deposit an NFT into Defuse (attacker owns the `Nep171TokenId` balance of 1), then call `nft_withdraw` with `msg: Some(...)` (setting `is_call() == true`) pointing `token` at their malicious contract and `receiver_id` at their own account. No relayer key, DAO role, or victim key is required — attacker cost is just gas plus deploying a trivial NFT contract with a custom `nft_transfer_call` return value. This is straightforward and fully reproducible in a sandbox test.

### Recommendation
Do not treat a successfully-returned-but-unparsable promise result as `used = false`. Either (a) require strict JSON schema validation and panic/require on malformed-but-successful results (fail closed instead of silently refunding), or (b) track NFT custody state independent of the promise's return payload (e.g., verify actual ownership via a follow-up `nft_token` view call before re-crediting), or (c) reject `nft_transfer_call` targets whose return body doesn't parse as `bool`, refusing to re-credit and instead treating it the same as the promise-failure branch (`used = true`, i.e., assume the transfer succeeded and do not refund) since an attacker-controlled contract's malformed response should not be trusted to justify minting Verifier-side balance.
