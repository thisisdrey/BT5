### Title
StackerDB reconfiguration guard compares the wrong counter, silently defeating the shrink-safety check and letting stale/unauthorized slots persist - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to reconfigure (and potentially shrink) a StackerDB replica by comparing two quantities that are supposed to represent the same thing — the total slot count before vs. after — much like the Hats bug compares `enabledModuleCount` before/after a transaction. Here, the "before" side of the comparison uses the wrong counter (`signers.len()`, i.e. the number of distinct signer entries) instead of the total number of slots (`num_slots()`), so the equality check that is explicitly meant to catch drift between the config-declared slot count and the persisted slot count (guarding against the historical "stackerdb could never shrink" bug, #5142) can silently pass even when the two are actually out of sync.

`new_config.signers` is `Vec<(StacksAddress, u32)>` — one entry per distinct signer, each carrying a `num_slots` count — while the *total* slot count is computed by `num_slots()`: [2](#0-1) 

`get_slot_versions(...)?.len()` returns the actual number of persisted slot rows for the StackerDB (one row per slot, not per signer). The comment makes clear the intent of the check: detect when the *persisted slot count* no longer matches what the *current config* says it should be, and if so, force `reconfigure_stackerdb` (which is what actually shrinks/grows the slot table via `StackerDBTx::reconfigure_stackerdb` / `shrink_stackerdb`): [3](#0-2) 

But the comparison uses `signers.len()` (count of signer entries) instead of `num_slots()` (sum of each signer's slot count). Any time a signer owns more than one slot (a very common case — e.g. the `.miners` StackerDB config assigns `MINER_SLOT_COUNT` slots per signer, and boot signer-DB contracts frequently allocate multiple slots per principal), `signers.len()` will not equal the true total slot count by construction. This means:
- The check can fire even when nothing actually needs reconfiguring (spurious churn), and, more importantly,
- The check can *fail to fire* precisely in cases where the true slot count has drifted from what the config specifies (the #5142 resurgence case) if `signers.len()` happens to coincidentally equal the stale persisted slot count.

Because `reconfigure_stackerdb`/`shrink_stackerdb` is the only code path that removes stale slots when a StackerDB's authorized signer set shrinks, defeating this guard means slots belonging to signers who are no longer part of the current signer set can remain live indefinitely: they continue to be servable and writable (subject to normal per-slot signature checks against the *old* signer recorded in the `chunks` table), and their (stale) data keeps being gossiped/served to peers as current, valid StackerDB inventory, even though the smart-contract-declared configuration no longer authorizes them.

### Impact Explanation
This defeats a shrink-safety invariant that the code explicitly documents as a fix for a prior "StackerDB never shrinks" bug (#5142). The practical effect is that stale, no-longer-authorized slots can continue to be treated as canonical StackerDB state (served in `StackerDBChunkInv`, downloadable via `StackerDBGetChunk`, and gossiped via `StackerDBPushChunk`) instead of being removed when the governing contract's signer/slot configuration changes. This is a non-canonical-state-served-as-canonical condition and results in unauthorized-looking data (from removed signers) persisting and propagating across the network, which maps to the "High: serving non-canonical state as canonical" / "Critical: network-wide propagation of forged/stale data" categories in scope.

### Likelihood Explanation
The bug is deterministic and always present in the code path — it will manifest whenever a StackerDB's signer set changes such that the total slot count shrinks (or otherwise changes) while the arithmetic coincidence `signers.len() == old_slot_count` holds, or more generally whenever this miscomparison masks a real shrink. Reaching this condition does not require compromising the node or an admin role; it results purely from normal, permissionless reward-cycle signer-set rotation (any principal that stacks becomes part of a signer set and can affect the corresponding StackerDB's `stackerdb-get-signer-slots` output), which is the mechanism this comparison is trying to correctly detect changes in.

### Recommendation
Replace `new_config.signers.len()` with `new_config.num_slots()` in the comparison so the check correctly measures total slot count against `self.get_slot_versions(&stackerdb_contract_id)?.len()`, restoring the intended shrink-safety guard.

### Proof of Concept
1. Configure a StackerDB-controlling contract with signers such that `signers.len() == N` while the true slot total (`num_slots()`) is `M != N` (e.g., one signer with `num-slots: u3` → `signers.len() == 1`, `num_slots() == 3`).
2. Let the persisted DB already have `1` stale slot (matching `signers.len()`) from a previous config, due to any prior drift.
3. On the next `create_or_reconfigure_stackerdbs` call, `new_config == stackerdb_config` (unchanged) and `new_config.signers.len() (1) == get_slot_versions().len() (1)` — the guard's inequality check is false, so `reconfigure_stackerdb`/`shrink_stackerdb` is never invoked even though the true intended slot count is `3`, not `1`, illustrating the miscomparison directly at [1](#0-0) .
4. More generally, construct a signer-set rotation where the removed-signers' slot rows happen to sum to a count equal to `signers.len()` of the new config; the shrink never executes and those stale slots continue to be reported in `StackerDBChunkInv`/served via chunk-fetch RPCs indefinitely.

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
