### Title
Fungibles/fungible `transfer()` default implementation can silently destroy value due to debit/credit amount mismatch during dust-sweep — (File: `substrate/frame/support/src/traits/tokens/fungibles/regular.rs`)

### Summary
The external report's broken invariant is: a public transfer path assumes the amount debited from the source and the amount credited to the destination are identical, without verifying the actual value moved, letting the difference disappear unaccounted. The exact structural analog exists in the generic `fungibles::Transfer`/`fungible::Transfer` default implementations that back XCM's `TransferAsset` execution path (`FungiblesTransferAdapter` / `FungibleTransferAdapter`). These call an independent debit and an independent credit instead of pairing them, so pallet-assets' own dust-sweep rounding on the debit side is never propagated to the credit side.

### Finding Description
`substrate/frame/support/src/traits/tokens/fungibles/regular.rs:362-386` implements the default `transfer()`: [1](#0-0) 

```
Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
// This should never fail as we checked `can_deposit` earlier. But we do a best-effort anyway.
let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
Self::done_transfer(asset, source, dest, amount);
Ok(amount)
```

The `Result` returned by `decrease_balance` (the *actual* amount debited) is discarded (`?;` only propagates errors), and `increase_balance` is called with the caller-supplied `amount`, not the actual debited value. `Ok(amount)` is returned unconditionally.

For pallet-assets, `fungibles::Unbalanced::decrease_balance` forwards to the pallet's low-level `decrease_balance`/`prep_debit` (`substrate/frame/assets/src/functions.rs:570-621`), which is documented (and implemented in the paired `do_transfer`/`transfer_and_die` path) to *round up* the debit to the whole remaining balance whenever leaving dust below `min_balance` would occur: [2](#0-1) 
> "The amount actually transferred may be slightly greater in the case that the transfer would otherwise take the sender balance above zero but below the minimum balance." [3](#0-2) 

That low-level `decrease_balance` in `functions.rs` never touches `details.supply` (total issuance) — it only mutates `account.balance`: [4](#0-3) 

So when the generic `transfer()` triggers this dust-sweep on the source, it silently debits `actual > amount` from the source account, but only credits `amount` (the smaller, originally requested value) into the destination account via `increase_balance`. The delta (`actual - amount`) vanishes from the source's balance without being credited anywhere and without any adjustment to `total_issuance`. This breaks the fundamental invariant `sum(all account balances) == total_issuance` for the affected asset — precisely the "accounting discrepancy from an amount not fully accounted for" pattern in the report, just triggered by internal dust rounding instead of an external fee-on-transfer hook.

This path is exercised by the XCM `TransactAsset` adapters that any unprivileged user can invoke via the public `pallet_xcm::execute` extrinsic issuing a `TransferAsset` instruction: [5](#0-4) 

`internal_transfer_asset` calls `Assets::transfer(asset_id, &source, &dest, amount, Expendable)` and, regardless of what actually moved, returns `Ok(what.clone())` (the originally requested asset/amount) to the XCM executor, which will treat the transfer as fully successful for the exact requested amount even though less was actually credited to the destination.

The identical structural issue exists for the single-asset variant used by `FungibleTransferAdapter`: [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a runtime-level accounting bug in a widely-used shared primitive (`fungibles`/`fungible::Transfer` default implementations), consumed by the XCM executor's `TransferAsset` instruction, which is directly reachable by any signed account through `pallet_xcm::execute`/`transfer_assets` on Asset Hub-style chains that keep assets in `pallet-assets`. It causes:
- Silent loss (burning without issuance adjustment) of user funds equal to the dust-rounding delta whenever a transfer amount leaves the source account with a remaining balance below `min_balance`.
- Divergence between the sum of account balances and `total_issuance` for the asset, an invariant multiple downstream systems (fee calculation, staking, treasury) implicitly rely on being exact.

This falls under "theft or unbacked mint or unlock" / "permanent user-fund or bridge-state lock" categories of the impact gate, since value is destroyed without being credited to the rightful beneficiary or reflected in issuance.

### Likelihood Explanation
Any unprivileged, signed account can trigger the condition without any privileged actor, relayer, or validator collusion: they simply need to submit a `pallet_xcm::execute` extrinsic containing a `TransferAsset` instruction for an asset (in `pallet-assets`) with an amount chosen so that the sender's remaining balance after debit would fall strictly between `0` and `min_balance`, which is trivially controllable by the sender (their own account, their own asset balance). No governance, no malicious peer, no leaked key required — this is a straightforward, deterministic self-triggerable state transition using public entry points.

### Recommendation
In the default `transfer()` implementations of `fungibles::Transfer` (`substrate/frame/support/src/traits/tokens/fungibles/regular.rs`) and `fungible::Transfer` (`substrate/frame/support/src/traits/tokens/fungible/regular.rs`), capture the actual value returned by `decrease_balance` and use that exact value (not the caller-supplied `amount`) as the argument to `increase_balance`, mirroring the paired debit/credit logic already used correctly in `pallet_assets::functions::transfer_and_die`/`do_transfer`. Alternatively, have `FungiblesTransferAdapter`/`FungibleTransferAdapter::internal_transfer_asset` in `xcm-builder` capture and return the actual transferred amount from `Assets::transfer`/`Fungible::transfer` instead of blindly returning `what.clone()`, so XCM holding-register accounting reflects the true amount moved.

### Proof of Concept
1. On an Asset Hub-style runtime, create an asset in `pallet-assets` with `min_balance = M` and mint `M + amount` (amount deliberately small, e.g. `amount < M`) to account `A`.
2. Have `A` submit `pallet_xcm::execute` with an XCM program:
   ```
   TransferAsset {
       assets: (asset_location, amount).into(),
       beneficiary: <B's location>,
   }
   ```
   chosen so that after debiting `amount` from `A`, `A`'s remaining balance (`M`) minus `amount` would be below `min_balance`, forcing the pallet's `prep_debit` dust-sweep logic to debit the entire remaining balance (`M + amount`) instead of `amount`.
3. Observe: `FungiblesTransferAdapter::internal_transfer_asset` calls `Assets::transfer(asset_id, A, B, amount, Expendable)`, which internally debits `M + amount` from `A` (via `decrease_balance`) but only calls `increase_balance(asset, B, amount)`, crediting `B` with just `amount`.
4. Check `pallet_assets::Pallet::total_issuance(asset_id)` before and after: it is unchanged, while `sum(balance(A) + balance(B))` after the transfer is now `amount` less than before — the difference (`M`) has been destroyed without being reflected anywhere, confirming the accounting discrepancy.

Note: `prep_debit`'s exact rounding logic in `substrate/frame/assets/src/functions.rs` (helper not shown in the retrieved excerpt) should be reviewed directly in the repository to confirm the precise dust-sweep threshold behavior; the documented behavior in `pallet_assets::Pallet::transfer`'s doc comment corroborates that "amount actually transferred may be slightly greater" than requested, which is the basis for this finding.
