### Title
Uninitialized `accountIndexOf` read as zero inflates first accrual to the holder's full balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
When a token's reward index equals `INITIAL_INDEX` (i.e., a reward token that was just added via `updateTokenSpeed` and whose index has not yet grown), `_calculateTokenDelta` fails to substitute the `INITIAL_INDEX` fallback for accounts whose `accountIndexOf` is still `0` (uninitialized storage). The delta is computed as `INITIAL_INDEX - 0`, so any account holding a balance of that token is credited `balance * 1e18` worth of accrued rewards the first time `updateBeforeMintOrBurn`, `updateBeforeTransfer`, or `claimRewards` touches it — all of which are callable by anyone for arbitrary accounts.

### Finding Description
The h2o CVE treats uninitialized memory as legitimately received frames; the analog here is treating an uninitialized `accountIndexOf` entry as a real index of `0` instead of the intended `INITIAL_INDEX` baseline.

In `_calculateTokenDelta` (contracts/RewardsDistributor.sol:217-231):

```solidity
_accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback only fires when `_tokenIndex > INITIAL_INDEX`. When a new reward token is registered, `_updateTokenSpeed` sets `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (lines ~296-298). Until `_calculateTokenIndex` advances the index (requires `block.timestamp > timestamp` and `speed > 0`), the global index is exactly `INITIAL_INDEX`. For an account with `accountIndexOf == 0`:

- `_deltaIndex = INITIAL_INDEX - 0 = 1e18`
- `_tokensDelta = balance.wadMul(1e18) = balance`

The account's entire DepositToken/DebtToken balance is booked as claimable `tokensAccruedOf`, then paid out by `_transferRewardIfEnoughTokens` up to the distributor's reward-token balance.

Reachability: `updateBeforeMintOrBurn(IERC20, address)` and `claimRewards(address[] , IERC20[])` are permissionless and accept arbitrary accounts. Any DepositToken or DebtToken holder whose position predates the reward-token registration necessarily has `accountIndexOf[token][holder] == 0` while holding `balance > 0` — balances can exist without an index entry because balances accrue via mint/transfer while the reward token didn't exist yet.

### Impact Explanation
Direct theft of reward tokens (unclaimed yield / distributor funds). An attacker holding a large DepositToken balance at the moment a reward token is added is credited `tokensAccruedOf[attacker] = balance`, then `claimRewards` transfers `rewardToken` up to the contract's full balance. The same flaw also incorrectly credits any other pre-existing holder touched by `updateBeforeTransfer`, corrupting the reward-accounting invariant (rewards paid exceed `speed * time` emitted by the index).

### Likelihood Explanation
Requires an active `updateTokenSpeed`/`updateTokenSpeeds` governor transaction registering a new reward token (or re-adding one after removal leaves `index == INITIAL_INDEX`... note removal sets speed to 0 and a later re-add reuses the grown index, so this applies to first-time additions). The attacker must hold a balance of that token beforehand and call `updateBeforeMintOrBurn`/`claimRewards` in the same block as, or before the first index-advancing update after, the registration — front-running is within the attacker model. Given large reward-token balances sitting in the distributor, payoff is high.

### Recommendation
Change the fallback condition so an uninitialized account index is always anchored:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

i.e., when `accountIndexOf == 0`, use `INITIAL_INDEX` only if the global index has actually grown past it; otherwise use the current index itself (yielding a zero delta). Equivalently, initialize `accountIndexOf` to the token's current index on first touch regardless of index value.

### Proof of Concept
```ts
// Hardhat, based on test/RewardDistributor.test.ts fixture
// alice holds msdTOKEN1 deposit balance BEFORE reward tracking starts
msdTOKEN1.totalSupply.returns(parseEther('100'))
msdTOKEN1.balanceOf.returns(parseEther('50')) // alice's deposit-token balance

// governor registers reward token; tokenStates[token].index = INITIAL_INDEX, timestamp = now
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))

// same block / before index advances: attacker (or anyone) pokes alice's entry
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)

// BUG: deltaIndex = INITIAL_INDEX - 0 -> tokensDelta = 50 * 1 = 50 reward tokens
expect(await rewardDistributor.tokensAccruedOf(alice.address)).to.eq(parseEther('50'))
// claimRewards(alice) then transfers 50 rewardToken from the distributor despite ~0 elapsed time
```

The invariant broken is reward accrual conservation: `tokensAccruedOf` must equal `balance * (index - accountIndex)` where a fresh account's baseline is the index at registration (`INITIAL_INDEX`), not `0`.
