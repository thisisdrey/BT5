### Title
Wallet contract `parse_rlp_tx_to_action` fails to enforce `target == current_account_id` for AddKey/DeleteKey, letting the wallet's owner escalate authorization onto arbitrary victim accounts - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
`parse_rlp_tx_to_action` classifies AddKey/DeleteKey as `ParsableTransactionKind::SelfNearNativeAction`, but only neutralizes the action into a harmless self-`Transfer` when `target_kind == TargetKind::EthImplicit(_)`. When `target_kind == TargetKind::OtherNearAccount(_)` (any non-eth-implicit account string, e.g. an arbitrary named account), the original AddKey/DeleteKey action is passed through unmodified together with the attacker-chosen `target`, and `action_to_promise` schedules `Promise::new(target).add_access_key_allowance_with_nonce(...)` / `.delete_key(...)` with no re-validation that `target` equals `current_account_id`.

### Finding Description
`parse_tx_data` maps the `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` calldata to `ParsableTransactionKind::SelfNearNativeAction` [1](#0-0) . In `parse_rlp_tx_to_action`, the handling of that classification is: [2](#0-1) 

This only rewrites the action to a self-transfer when `target_kind` is `EthImplicit(_)`; for `TargetKind::OtherNearAccount(_)` the branch falls through to `(action, TransactionKind::NearNativeAction)`, keeping the original AddKey/DeleteKey action with the attacker-supplied `target` untouched.

`validate_tx_relayer_data` only checks `to == account_id_to_address(target)` in the `OtherNearAccount` case ( [3](#0-2) ) — it never checks `target == current_account_id` for this branch. Since the attacker signs their own Ethereum transaction (controls `tx.to`) and also supplies `target` as a plain call argument to `rlp_execute`, both values are fully attacker-controlled and trivially made consistent (`to = keccak256(target)[12..32]`).

The resulting action then reaches `action_to_promise` unchanged: [4](#0-3) 

There is no check anywhere in this function (or its caller `inner_rlp_execute`, [5](#0-4) ) that `target == current_account_id` before creating `Promise::new(target)` for AddKey/DeleteKey.

Crucially, NEAR's runtime applies AddKey/DeleteKey to whatever receipt `receiver_id` is chosen by the promise creator with no predecessor-must-equal-receiver check: `action_add_key` operates directly on `account_id`, which is the receipt's receiver, not the predecessor [6](#0-5) [7](#0-6) . So nothing at the protocol layer stops a wallet contract's own receipt from mutating an unrelated account's access-key set.

Exploit flow: the attacker owns their own eth-implicit account/wallet contract (unprivileged: funds an account and controls its private key). They sign an Ethereum tx with `to = keccak256("victim.near")[12..32]` and ABI-encoded AddKey calldata (`is_full_access=false` since full-access is explicitly blocked by `action_to_promise`, `allowance` omitted so it resolves to `Allowance::Unlimited`, arbitrary `receiver_id`/`method_names`). They call `rlp_execute(target="victim.near", tx_bytes_b64=...)`. `validate_tx_relayer_data` passes (target_kind = `OtherNearAccount`, `to` matches hash(target)); `parse_tx_data` returns the AddKey action; the `SelfNearNativeAction` branch does not rewrite it because `target_kind != EthImplicit`; `action_to_promise` issues `Promise::new("victim.near").add_access_key_allowance_with_nonce(attacker_pubkey, Unlimited, receiver_id, method_names, nonce)`, which nearcore applies to `victim.near`'s state unconditionally.

### Impact Explanation
This is an authorization escalation across accounts: an unprivileged attacker (owner of an eth-implicit wallet contract) can add a `FunctionCallPermission` access key with unlimited allowance to any existing NEAR account, letting them call arbitrary methods on a chosen contract funded by the victim's own balance (impersonation / gas-fee-funded actions from the victim's identity). The equivalent `DeleteKey` path lets the attacker delete a known (publicly observable) access key belonging to the victim, which, if it is the victim's only key, permanently locks the victim out of their own account — a permanent freezing-of-funds scenario. Both map to the "authorization escalation across accounts" and "theft or permanent freezing of user funds" bounty categories.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's control: fund an account, control an eth-implicit address's private key, and craft an ABI-encoded AddKey/DeleteKey Ethereum transaction with `to` matching `keccak256(target)`. No relayer, validator, or victim cooperation is needed — the attacker can self-relay. The attack is repeatable against any existing named NEAR account (subject only to the target key not already existing on that account for AddKey, or the target key existing for DeleteKey — both are publicly discoverable via `view_access_key`/`view_access_key_list`).

### Recommendation
In `parse_rlp_tx_to_action`, for `ParsableTransactionKind::SelfNearNativeAction`, unconditionally require `target == context.current_account_id` before accepting the AddKey/DeleteKey action; otherwise return a `UserError`/`RelayerError` (as is already done for unparsable payloads sent to `TargetKind::OtherNearAccount`). Additionally, add a defense-in-depth check inside `action_to_promise` (or its caller) asserting `target == current_account_id` before constructing AddKey/DeleteKey promises, so a future parsing regression cannot resurrect this class of bug.

### Proof of Concept
Unit test in `internal.rs`:
1. Build a `NormalizedEthTransaction`/context where `current_account_id = "0x<hash-of-attacker-address>"`.
2. Craft ABI-encoded AddKey calldata with `is_full_access=false`, `allowance=None`, `receiver_id="attacker.near"`, `method_names=["withdraw"]`.
3. Set `tx.to = account_id_to_address(&"victim.near".parse().unwrap())`.
4. Call `parse_rlp_tx_to_action(&tx_bytes_b64, &"victim.near".parse().unwrap(), &context, expected_nonce)`.
5. Assert the call returns `Err(Error::User(_))` or `Err(Error::Relayer(RelayerError::InvalidTarget))` (expected/fixed behavior) rather than `Ok((Action::AddKey { .. }, TransactionKind::NearNativeAction))` targeting `"victim.near"` (current buggy behavior).

Integration test: drive `inner_rlp_execute` with the same payload and assert no `Promise::new("victim.near")` AddKey/DeleteKey receipt is produced; the response must be a `UserError`, confirming the wallet contract can never mutate access keys on an account other than `current_account_id`.

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
