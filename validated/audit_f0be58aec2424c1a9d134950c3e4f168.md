### Title
Missing slippage/minimum-amount protection in `ExchangeInjectActuator` liquidity provisioning - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The bancor-style TRC10↔TRC10/TRX AMM exchange in java-tron supports the standard "add liquidity" operation `ExchangeInjectContract`/`ExchangeInjectActuator`. Unlike its sibling operations `ExchangeTransactionContract` (swap, has an `expected` slippage-floor field) and `ExchangeWithdrawContract` (remove liquidity, has an on-chain precision-ratio check), the inject/deposit path computes the paired token amount to be deducted from the caller purely from the pool's current instantaneous ratio at execution time, with no user-supplied bound and no post-condition check protecting the caller.

### Finding Description
In `ExchangeInjectActuator.execute()`, the caller supplies only `tokenID` and `tokenQuant` (from `ExchangeInjectContract`), and the actuator computes the paired amount `anotherTokenQuant` from the exchange's balances at execution time: [2](#0-1) 
This mirrors validation logic in `doValidate()`, which recomputes the same ratio-based `anotherTokenQuant` for balance checks, but again with no upper bound supplied by the caller: [3](#0-2) 

Both amounts are then deducted from the caller's account: [4](#0-3) 

The pool's exchange rate can be moved arbitrarily within the same block by any other transaction that reaches `ExchangeTransactionActuator` (swap) or another `ExchangeInjectActuator`/`ExchangeWithdrawActuator` call, since Tron allows multiple transactions to be packed into the same block by the block-producing SR, and transaction ordering within a block is fully controlled by whoever proposes it. Compare this with `ExchangeTransactionActuator`, which has an explicit `expected` parameter checked against the computed output: [5](#0-4) 
and `ExchangeWithdrawActuator`, which at least validates the computed ratio is "precise enough" (a data-integrity check, not a slippage check, but still a bound on the derived quantity): [6](#0-5) 

`ExchangeInjectContract` has no equivalent field to cap the amount of the paired token the sender is willing to part with: [7](#0-6) 

### Impact Explanation
A broadcaster can be economically harmed when injecting liquidity into an exchange pool: if the pool ratio is manipulated (e.g., by a swap transaction placed immediately before the inject transaction in the same block, then reversed immediately after), the victim's inject transaction executes at the manipulated ratio, silently transferring a far larger amount of the paired asset out of the victim's account than they intended, with no way to cap or reject this at the protocol level. Because `ExchangeInjectActuator` is only usable by the exchange's creator (`account[...] is not creator` check exists), the practical blast radius is limited to pool creators/liquidity managers, but the loss of funds (excess paired-token deduction) is real and unbounded relative to any expectation the caller had, matching the "theft/unbacked-loss" class from the report.

### Likelihood Explanation
Exploitation requires the attacker to control transaction ordering within a block containing the victim's inject transaction (or to race it), which is feasible for any account able to submit transactions around the target's inject call, particularly a block-producing SR or a party using front-running via mempool observation. The exchange is a public bancor-relayer-like AMM that any TRC10 asset issuer can create and interact with, so the attack surface (pools with meaningfully manipulable ratios and liquidity providers periodically injecting) is broadly reachable and does not require any privileged role beyond controlling transaction ordering, which is a routine capability of block producers.

### Recommendation
Add a caller-supplied bound (e.g., `expected`/`max_another_token_quant`) to `ExchangeInjectContract`, and validate in `ExchangeInjectActuator.doValidate()`/`execute()` that the actually-computed `anotherTokenQuant` does not exceed the caller's specified maximum, analogous to the `expected` floor check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Pool P has `firstTokenBalance = 1_000_000`, `secondTokenBalance = 1_000_000` (1:1 ratio).
2. Creator/LP broadcasts `ExchangeInjectContract{tokenId=first, quant=100_000}`, expecting to pay ~100_000 of the second token (per the current 1:1 ratio), per the computation in `ExchangeInjectActuator.execute()`. [8](#0-7) 
3. Before this transaction is applied (same block, earlier index), an attacker broadcasts a large `ExchangeTransactionContract` swap that skews the ratio to e.g. 1:10 in favor of the second token, then a follow-up swap after the victim's inject that restores the ratio (a sandwich).
4. The victim's inject transaction executes at the skewed intermediate ratio: `anotherTokenQuant` is computed at 10x the amount the victim expected, and this larger amount is deducted from the victim's account balance/asset in `ExchangeInjectActuator.execute()`, with no on-chain check rejecting this deviation, since `ExchangeInjectContract` carries no minimum/maximum bound field.
