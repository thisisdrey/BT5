### Title
Null-pointer dereference in `RepositoryImpl.saveCode()` can crash the node when creating a contract via TVM `CREATE`/`CREATE2` - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.saveCode()` calls `getContract(address)` and immediately dereferences the result (`contract.setCodeHash(...)`) without checking for `null`, mirroring the exact bug class in CVE-2024-26612 (dereference before null-check). This method is reachable from an unprivileged, attacker-controlled path: any contract deployment or internal `CREATE`/`CREATE2` performed by a smart contract triggered through a normal signed transaction.

### Finding Description
`RepositoryImpl.saveCode()`: [1](#0-0) 
does:
```
if (VMConfig.allowTvmConstantinople()) {
  ContractCapsule contract = getContract(address);
  byte[] codeHash = Hash.sha3(code);
  contract.setCodeHash(codeHash);   // dereferenced without a null check
  updateContract(address, contract);
}
```
`getContract(address)` can legitimately return `null` if no `ContractCapsule` has been created/committed for `address` yet at the point `saveCode` runs. `saveCode` is invoked from the internal `CREATE`/`CREATE2` opcode handling in `Program.createContractImpl()`: [2](#0-1) 
after a nested contract-creation sub-call completes (`deposit.saveCode(newAddress, code)`), and also from the top-level contract creation path in `VMActuator`: [3](#0-2) 

The nested `deposit` used in `createContractImpl` is a *child* repository (`getContractState().newRepositoryChild()`), and the `ContractCapsule` for `newAddress` is created on that child deposit via `deposit.createContract(newAddress, new ContractCapsule(newSmartContract))` only inside the `if (VMConfig.allowTvmConstantinople())` branch when the account did not already exist as a contract: [4](#0-3) 
If the inner execution path reaches `saveCode` while the created-contract entry has not yet been committed to a layer that `getContract()` can see (e.g., due to caching/parent-lookup semantics in `RepositoryImpl.getContract`), or if a code path calls `saveCode` for an address whose `ContractCapsule` creation was skipped/rolled back, `getContract(address)` returns `null` and `contract.setCodeHash(...)` throws an uncaught `NullPointerException`.

### Impact Explanation
An uncaught `NullPointerException` during TVM execution inside contract creation (`CREATE`/`CREATE2`) is not caught by the normal `ContractExeException`/`ContractValidateException` handling used elsewhere in the actuator layer, and can propagate up through block application in `Manager`, causing the node processing the block to crash or halt (denial of service against the node). Since contract deployment/`CREATE2` is reachable by any address broadcasting a `CreateSmartContract` or `TriggerSmartContract` transaction that internally executes `CREATE`/`CREATE2`, this is reachable by any unprivileged contract deployer.

### Likelihood Explanation
Medium: the specific ordering of repository-child creation, caching, and `getContract` lookups needs to line up so that the just-created `ContractCapsule` isn't visible via `getContract(address)` when `saveCode` executes. This requires precise crafting of a `CREATE`/`CREATE2` sequence (e.g., interacting with `allowTvmConstantinople` flag state, existing-account-without-contract-type edge cases per `isContractExist`) but does not require any special privilege — only a normal transaction broadcaster deploying/triggering a contract.

### Recommendation
In `RepositoryImpl.saveCode()`, check `getContract(address)` for `null` before dereferencing, mirroring the CVE-2024-26612 fix pattern ("check first, then dereference"):
```java
ContractCapsule contract = getContract(address);
if (contract != null) {
  byte[] codeHash = Hash.sha3(code);
  contract.setCodeHash(codeHash);
  updateContract(address, contract);
}
```
Alternatively, ensure the `ContractCapsule` is always committed/visible before `saveCode` is invoked, and add defensive null-handling around all similar `getContract(...)`/`getAccount(...)` dereferences in `RepositoryImpl` and `Program.java`.

### Proof of Concept
Not concretely constructible from static analysis alone — an actual PoC would require crafting a `CreateSmartContract`/`TriggerSmartContract` transaction whose bytecode issues an internal `CREATE`/`CREATE2` such that the created contract's `ContractCapsule` is not yet visible to `getContract(address)` at the moment `saveCode` runs on that same address. I was not able to fully confirm from the indexed code snippets whether `getContract`'s cache/parent-chain lookup can actually return `null` in that exact window (this depends on `RepositoryImpl.getContract()` internals, which were only partially inspected), so this should be verified with a live/debug trace of a `CREATE2` transaction before treating it as a fully proven exploitable path.
