### Title
Remote unauthenticated crash via `assert!` panic on undersized `payload_len` in P2P push-message validators - (File: `stackslib/src/net/chat.rs`)

### Summary
`ConversationP2P::validate_blocks_push`, `validate_microblocks_push`, `validate_transaction_push`, and `validate_stackerdb_push` each begin with a hard `assert!` on `preamble.payload_len` before doing an unchecked `u64` subtraction, e.g. `assert!(preamble.payload_len > 5)` for `Blocks`/`Microblocks` and `assert!(preamble.payload_len > 1)` for `Transaction`/`StackerDBChunk`/`StackerDBPushChunk`, followed immediately by `(preamble.payload_len as u64) - 5` or `- 1`. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the report's bug class: code assumes an invariant about a length/growth field ("value X will always be larger than Y") and performs subtraction based on that assumption, without actually re-verifying it at the point of use. In the Trident report, the mitigation was to make the subtraction tolerant of the violated assumption (unchecked math). Here the analogous defect is the opposite failure mode of the same root cause: the invariant `preamble.payload_len > N` is enforced with a *panicking* `assert!` rather than a graceful rejection, and — critically — nothing in the message-dispatch path (`dispatch_message` in `chat.rs`, around the `StacksMessageType::Blocks`, `Microblocks`, `Transaction`, `StackerDBChunk`/`StackerDBPushChunk` arms) re-validates `payload_len` against a minimum before calling these validators. [3](#0-2) 

`preamble.payload_len` is a wire-controlled `u32` field of `Preamble`, read directly off the socket during deserialization. The only length check performed during deserialization (`StacksMessage::consensus_deserialize` in `codec.rs`) is an upper bound (`payload_len > MAX_MESSAGE_LEN - PREAMBLE_ENCODED_SIZE` is rejected), not a lower bound tied to the message type actually decoded: [4](#0-3) 

I was not able to conclusively verify within the tool budget whether `payload_len` is cross-checked against the number of bytes actually consumed for the specific payload variant (e.g., that a `Blocks` message payload cannot be encoded/accepted with a `payload_len` of 0–5). If no such cross-check exists elsewhere in the read/verify path (`connection.rs`'s `consume_payload_known_length`/`verify_payload_bytes`, which use `payload_len` only to know how many bytes to slice, not to validate a type-specific minimum), then a remote peer can craft (or relay) a signed `StacksMessage` whose `payload` decodes as `Blocks`/`Microblocks` (needing `payload_len > 5`) or `Transaction`/`StackerDBChunk`/`StackerDBPushChunk` (needing `payload_len > 1`) while `preamble.payload_len` is set to a smaller value (e.g. 0 or 1). When such a message reaches `dispatch_message`, the corresponding `validate_*_push` function's `assert!` fires and panics the process — since `assert!` (unlike `debug_assert!`) is never compiled out in release builds.

### Impact Explanation
If reachable, this is a remote, unauthenticated (post-handshake) crash of the p2p worker/node from a single crafted or relayed message — matching the report's "Critical: remote crash / unauthenticated DoS from few messages" bar, since these push-message handlers are reachable from any connected peer and forwarded/relayed further (amplifying blast radius across the network if relayed messages aren't independently re-validated for this invariant).

### Likelihood Explanation
Likelihood depends entirely on whether `payload_len` is independently constrained to match the actual decoded payload elsewhere in the codec/verification pipeline (which I could not fully confirm from the available index). If it is not constrained beyond the `MAX_MESSAGE_LEN` upper bound shown in `codec.rs`, the crash is trivially triggerable by any connected peer with a single malformed message; if strict, cross-checked equality is enforced elsewhere (unseen in the indexed slices), this degrades to an unreachable defensive assertion.

### Recommendation
- Replace the `assert!(preamble.payload_len > N)` invariants in `validate_blocks_push`, `validate_microblocks_push`, `validate_transaction_push`, and `validate_stackerdb_push` (`stackslib/src/net/chat.rs`) with a checked comparison that returns `Err(net_error::InvalidMessage)` (as already done for the relayer-cycle check just above each assert) instead of panicking.
- Use `preamble.payload_len.checked_sub(N)` (or `saturating_sub`) for the bandwidth-accounting subtraction, and reject/log rather than assert if the subtraction cannot be performed safely.
- Independently, verify that `payload_len` is validated against the actual bytes consumed for the specific decoded payload type at deserialization time, closing the gap between "declared preamble length" and "actual message length" for these variants.

### Proof of Concept
Conceptual (cannot be fully executed without the full codec/deserialization internals):
1. Craft a `StacksMessage` with `payload = StacksMessageType::Transaction(tx)` (or `StackerDBPushChunk`), sign it validly per protocol.
2. Set `preamble.payload_len = 1` (or `0`) while the actual serialized transaction payload is larger — if the wire/decode path accepts this mismatch (only bounded above by `MAX_MESSAGE_LEN`), send it to a connected/authenticated peer.
3. `dispatch_message` routes to `validate_transaction_push`/`validate_stackerdb_push`, hitting `assert!(preamble.payload_len > 1)`, which panics and crashes the peer's p2p thread/process. [5](#0-4) [6](#0-5)
