### Title
Wrong Guard Function: Java `assert` Used for Reachable Invariant in Energy Limit Calculation Allows Divide-by-Zero / Unlimited Energy - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit` guards the invariant "`totalEnergyWeight > 0`" with a Java `assert` statement instead of a real conditional check/exception, exactly the "wrong guard function" pattern described in the report (using `assert()` for a condition that is derived from mutable state and can legitimately be false). [1](#0-0)  In Java, `assert` statements are stripped/no-ops at runtime unless the JVM is started with `-ea`, which production java-tron nodes are not. This makes the "guard" completely inert in production — the exact failure mode the report warns about (a guard that should always hold but can be false), except worse: the check never runs at all rather than reverting.

### Finding Description
`calculateGlobalEnergyLimit` is invoked on every energy-consuming transaction path (TVM contract triggers) to compute an account's global energy limit from its frozen balance and `totalEnergyWeight`: [2](#0-1) 

The early-return that would normally prevent `totalEnergyWeight <= 0` from reaching the division only fires when `dynamicPropertiesStore.allowNewReward()` is true:
```
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
```
If `allowNewReward()` is false (a committee-controlled proposal that may be disabled) and `totalEnergyWeight` is `0`, the `assert` — being compiled out in production — does nothing, and execution falls through to:
```
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
Dividing a positive `double` by `0.0` yields `Double.POSITIVE_INFINITY`; multiplying by a positive `energyWeight` remains `Infinity`; casting `Infinity` to `long` in Java yields `Long.MAX_VALUE`. The function therefore returns `Long.MAX_VALUE` as the account's energy limit instead of throwing or returning a safe value. On the `hardenCalculation()` branch, the equivalent `calculateGlobalLimitV1` performs `BigInteger` division by `totalWeight`, which throws an uncaught `ArithmeticException` for a zero divisor. [3](#0-2) 

A structurally identical dead guard exists in `ResourceProcessor.increase`, where `assert now > lastTime;` is meant to enforce monotonic time but is a no-op in production, allowing negative `delta` values to flow into the decay computation used for bandwidth/energy usage accounting for every transaction. [4](#0-3) 

### Impact Explanation
If `totalEnergyWeight` reaches `0` while `allowNewReward()` is disabled, any account with a non-zero frozen-for-energy balance receives an energy limit of `Long.MAX_VALUE`, effectively granting unlimited free TVM execution — a direct resource-theft/DoS vector reachable by any unprivileged contract-calling transaction, since energy accounting underlies every smart contract invocation. On the hardened path, the same state instead crashes the node with an uncaught `ArithmeticException` during transaction processing, a node halt/DoS. Both outcomes are Medium/High severity: one enables unbacked resource consumption, the other a node crash triggerable through normal contract execution.

### Likelihood Explanation
Reaching `totalEnergyWeight == 0` requires all energy-frozen TRX in the network to be withdrawn, which is an edge condition rather than a routine one, and `allowNewReward()` is typically enabled on mainnet, which reduces likelihood. However, the guard exists precisely because this condition was anticipated as reachable ("if allowNewReward is off"), and the use of a compiled-out `assert` means the codebase's own invariant enforcement silently does nothing in production — the same "wrong guard" class flagged in the report, just manifesting as complete guard removal rather than gas-waste on revert.

### Recommendation
Replace both `assert` statements with explicit checks that fail safe:
- In `EnergyProcessor.calculateGlobalEnergyLimit`, return `0` (or throw) whenever `totalEnergyWeight <= 0`, regardless of `allowNewReward()`, instead of relying on `assert totalEnergyWeight > 0;`.
- In `ResourceProcessor.increase`, replace `assert now > lastTime;` with an explicit branch/clamp handling `now <= lastTime` instead of allowing execution to continue on an unverified assumption.

### Proof of Concept
1. Disable/never-activate the `allowNewReward` proposal on a private/test chain (`dynamicPropertiesStore.allowNewReward() == false`).
2. Drive `totalEnergyWeight` to `0` by having all accounts unfreeze their energy-frozen balance (achievable on a test network under attacker's control).
3. Freeze a small TRX amount for `ENERGY` on an attacker account (`frozeBalance > 0`).
4. Call `EnergyProcessor.calculateGlobalEnergyLimit` (indirectly via any TVM contract-triggering transaction from that account) — non-hardened path returns `Long.MAX_VALUE` as the energy limit (unlimited free contract execution); hardened path (`calculateGlobalLimitV1`) throws `ArithmeticException` uncaught up the transaction-processing call stack.
