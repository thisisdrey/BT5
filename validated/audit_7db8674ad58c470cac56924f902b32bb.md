### Title
Unbounded array length from attacker-controlled ABI input causes OutOfMemoryError/ArrayIndexOutOfBoundsException in TVM precompiled-contract signature/bytes decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` decode dynamic arrays from raw precompile call data by reading a length word directly from attacker-supplied ABI input and using it, unchecked, to size a Java array and drive subsequent pointer arithmetic into the `data` buffer, mirroring the OpenSSL CVE-2016-2177 bug class of trusting length/offset fields for pointer arithmetic without validating them against the actual buffer bounds.

### Finding Description
`extractSigArray` and `extractBytesArray` read `len` straight from `words[offset].intValueSafe()`: [1](#0-0) 
`intValueSafe()` only clamps to `Integer.MAX_VALUE` when the word doesn't fit in 4 bytes, so `len` can be any positive `int` up to ~2^31-1 under full attacker control (a contract calling the precompile with crafted calldata): [2](#0-1) 
With a huge `len`, `new byte[len][]` in `extractSigArray`/`extractBytesArray` immediately attempts to allocate an oversized array of references, and the subsequent loop indexes `words[offset + i + 1]` with no bound check against `words.length`, and computes byte offsets into `data` (`(bytesOffset + offset + 2) * WORD_SIZE`) that are also unchecked before being passed to `extractBytes`, which does a raw `Arrays.copyOfRange(data, offset, offset + len)`: [3](#0-2) [4](#0-3) 
Both `words` array indexing and `Arrays.copyOfRange` on `data` will throw `ArrayIndexOutOfBoundsException` for a moderately crafted input, or trigger `OutOfMemoryError` for a very large `len`, exactly analogous to the CVE's "incorrect pointer arithmetic for heap-buffer boundary checks" causing "integer overflow and application crash... by leveraging unexpected malloc behavior." Notably, a nearby helper `recoverAddrBySign` in the same file explicitly wraps signature-recovery logic in `catch (Throwable any)` to defend against such crashes, but `extractBytesArray`/`extractSigArray` have no equivalent protection, showing an inconsistency in defensive coding for this same input-decoding surface: [5](#0-4) 

### Impact Explanation
These helpers back TVM precompiled contracts used for batch signature/array validation (e.g., the batch-validate-sign precompile, exercised by `BatchValidateSignContractTest`), which any account can reach by simply calling the precompile address from a smart contract in a normal, signed transaction. An `OutOfMemoryError` is an unchecked `Error`, not an `Exception`; if the surrounding TVM execution path does not specifically catch `Throwable`/`Error` around precompile execution, this can escape normal exception handling and crash or destabilize the executing node process during transaction/block processing — a denial-of-service on any validator or full node that processes the malicious transaction, which is worse than a simple revert since it can affect all nodes deterministically executing the same transaction (potential chain-wide liveness impact, matching the CVE's DoS/crash impact class).

### Likelihood Explanation
Likelihood is high for triggering the bug (any account can construct calldata with an arbitrary `len` word and call the precompile), but the ultimate severity (crash vs. caught exception/revert) depends on whether TVM's precompile-invocation wrapper catches `Throwable`/`OutOfMemoryError` generically elsewhere in the call chain — this could not be fully confirmed from the code reviewed. If only `Exception` (not `Error`) is caught at the top level, this is directly exploitable as a network-wide DoS; if `Throwable` is caught, impact is reduced to a wasted-energy/exception path rather than a crash.

### Recommendation
In `extractBytesArray` and `extractSigArray`, validate `len` and all derived offsets/indices against `words.length` and `data.length` before allocating arrays or slicing, similar to the bounds checks already present in `RLP.verifyLength`. Cap `len` to a sane maximum (e.g., derived from `data.length / WORD_SIZE`) before calling `new byte[len][]`, and bound-check `bytesOffset`/computed byte ranges before calling `Arrays.copyOfRange`, throwing a normal `BytecodeExecutionException` (caught by the VM) instead of allowing unchecked `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` to propagate.

### Proof of Concept
Deploy a contract that performs a low-level `call` to the batch-validate-sign precompile address, supplying ABI-encoded calldata where the "array length" word (consumed via `words[offset].intValueSafe()`) is set to a very large value (e.g., `0x7FFFFFFF`) while the actual `data` buffer is short. This drives `extractSigArray`/`extractBytesArray` to either allocate an oversized `byte[len][]` (triggering `OutOfMemoryError`) or to index `words[offset + i + 1]` beyond `words.length` (triggering `ArrayIndexOutOfBoundsException`) before any bounds validation occurs, exactly as reachable by an unprivileged contract-call transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
