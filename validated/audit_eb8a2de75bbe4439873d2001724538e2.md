### Title
`applyBlack()` uses a hard-coded `/2` subsample divisor incompatible with non-standard (flex-mode) subsampling ratios, causing incorrect/out-of-bounds pixel indexing - (File: src/image/jpeg/reader.go)

### Summary
`image/jpeg`'s decoder was extended to support "non-standard subsampling ratios" via a `flex` mode (tracked per-component with `expandH`/`expandV` fields computed in `processSOF`), allowing sampling factor combinations beyond the classic 4:4:4/4:2:2/4:2:0/etc. sets. However, `applyBlack()`, which reassembles a 4-component (CMYK/YCbCrK) image from `d.img3` and `d.blackPix`, still assumes the old fixed 2x subsampling model when translating destination pixel coordinates to source offsets.

### Finding Description
An attacker supplies a crafted JPEG with an SOF marker declaring 4 components (`processSOF`, [1](#0-0) ) where component sampling factors are unequal (e.g. comp0 = 0x22, comp1..3 = 0x11), which is an accepted/validated combination. This makes some channels subsampled relative to comp0. In `applyBlack()`, the per-channel loop computes source coordinates with a hard-coded halving: [2](#0-1) 
The `subsample` boolean only decides whether to divide `sx`/`sy`, but always divides by exactly `2` (`sy /= 2`, `sx /= 2`) regardless of the component's actual expansion factor (`d.comp[t].expandH`/`expandV`, computed in `processSOF` at lines 420-424 as `d.maxH/d.comp[i].h` and `d.maxV/d.comp[i].v`, which can be values other than 2 when the "flex" non-standard-subsampling path is exercised elsewhere in the decoder, e.g. `scan.go`'s `reconstructBlock` flex-expansion logic at lines 483-489/509-524). When the true expansion factor differs from 2 (the code only currently allows h,v ∈ {1,2,4} and enforces divisibility only for the 3-component path in `processSOF` lines 410-418 — the 4-component path does not independently validate that a `/2` assumption holds for all accepted hv combos), the computed `sy`/`sx` will not correctly map back into `translation.src`'s actual stride/height, and `img.Pix[i] = 255 - translation.src[sy*translation.stride+sx]` can read outside the bounds of the subsampled channel slice (`d.img3.Cb`, `d.img3.Cr`, or `d.blackPix`), analogous to the ffjpeg `jfif_decode()` `ALIGN` miscalculation that produced out-of-bounds access from an unvalidated scaling/alignment computation.

### Impact Explanation
A malicious JPEG image decoded by a normal `image.Decode`/`jpeg.Decode` caller (an ordinary victim workflow, e.g. a web service or CLI resizing user-uploaded JPEGs) can trigger an out-of-bounds read into `img.Pix[i]`, which is a slice index computed from attacker-controlled sampling factors. Depending on how far `sy*translation.stride+sx` diverges from valid bounds, this manifests as a panic (index out of range) — a real parser panic on malicious input, which qualifies under Go's security policy — or, in the worst case, reads adjacent heap memory into the output image (information disclosure of adjacent buffer content). This would be assessed under Go's PUBLIC track since it's a memory-safety issue in the standard library reachable via untrusted, unauthenticated image input with a concrete crash/disclosure primitive, not merely unbounded resource use.

### Likelihood Explanation
Reachability requires only calling the standard `image/jpeg` `Decode` (or `image.Decode` with jpeg auto-registered) on an attacker-supplied 4-component JPEG with Adobe APP14 metadata absent or set to a non-"Unknown" transform, and component sampling factors that are validated by `processSOF` but not covariant with the `/2` assumption in `applyBlack`. This is a common, unauthenticated attack surface (any service that decodes user-uploaded JPEGs).

### Recommendation
In `applyBlack()`, replace the hard-coded `sy /= 2; sx /= 2` with the actual per-component expansion factors already computed in `processSOF` (`d.comp[t].expandV`, `d.comp[t].expandH`), i.e. `sy /= d.comp[t].expandV` and `sx /= d.comp[t].expandH`, or reject (`UnsupportedError`) 4-component images with non-2x subsampling factor combinations before reaching `applyBlack`.
