### Title
HookService Is Registered on Gitaly's External gRPC Socket, Letting Any Client Invoke Pre/Post-Receive Hooks Directly Without Going Through an Actual `git-receive-pack` Push - (File: internal/gitaly/server/server.go, internal/cli/gitaly/serve.go, internal/gitaly/service/hook/pre_receive_test.go)

### Summary
The `BatcherPaymentService` report describes a design where an outer contract enforces checks (Merkle root/signature verification, pause state, fee accounting) before delegating to an inner contract (`AlignedLayerServiceManager`), but the inner contract has no protection of its own, so anyone can call it directly and skip every guarantee the outer wrapper was supposed to provide. Gitaly has a structurally identical pattern: `HookService` is documented and designed to be invoked *only* by the internal `gitaly-hooks` binary over Gitaly's internal socket, as part of the `git-receive-pack` flow (quarantine → pre-receive → update → migrate → reference-transaction → post-receive). However, `HookService` is also registered on Gitaly's external gRPC socket, so any client that can reach that socket can call `PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, and `ReferenceTransactionHook` directly, decoupled from any real push, quarantine, or reference-transaction sequencing.

### Finding Description
`HookService` RPCs are meant to be invoked exclusively through the `gitaly-hooks` gateway binary, itself invoked by Git as a `core.hooksPath` hook during `git-receive-pack`/`OperationService` mutators [1](#0-0) . Setup registers `HookService` (via `setup.RegisterAll`) identically on every configured listener — including the external, non-internal sockets — with no distinction made for `HookService` methods: [2](#0-1) 

The server factory itself documents the intent that only `HookService` calls should arrive through the internal socket, yet nothing enforces that at the RPC-registration or interceptor level for the external listener — it only conditionally adds unrelated transaction/housekeeping middleware when `external == true`: [3](#0-2) 

The individual hook handlers (`PreReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`) validate only that the `Repository` message is well-formed via `locator.ValidateRepository`; they perform no check that the call originates from the internal socket, from `gitaly-hooks`, or from an in-progress transaction: [4](#0-3) [5](#0-4) 

A test explicitly acknowledges this: it has to work around the fact that `HookService` answers on the external API even though "this is a service intended only to be used internally by Gitaly for hook callbacks," referencing the tracked but apparently still-open gap: [6](#0-5) 

`PreReceiveHook`'s implementation shows the concrete consequence of decoupling the call from a real push: it calls Rails' `/internal/allowed` endpoint and then increments a per-repository reference counter via `gitlabClient.PreReceive`, entirely independent of whether an actual `git-receive-pack` invocation with real object updates is underway: [7](#0-6) 

Per Gitaly's own documentation, this counter is used by GitLab to know "when a certain repository can be moved" — non-zero means active pushes are in progress: [8](#0-7) 

Because `PreReceiveHook` and `PostReceiveHook` are independent, externally reachable RPCs with no linkage enforced between an increment and its matching decrement, a caller can invoke `PreReceiveHook` (with any inputs that pass Rails' `Allowed` check for a repository they have legitimate push access to) repeatedly while never calling the corresponding `PostReceiveHook`, permanently inflating the counter and blocking repository moves for that repository — a self-inflicted but externally triggerable state that would otherwise only occur if the real push flow crashed mid-way.

### Impact Explanation
Any client capable of authenticating to Gitaly's external gRPC endpoint at the level required for ordinary Git operations (the same trust tier used for normal pushes/fetches through Workhorse/gitlab-shell) can call `HookService` RPCs directly, bypassing:
- The actual object quarantine / receive-pack sequencing that `pre-receive`, `update`, and `reference-transaction` hooks are supposed to observe.
- The 1:1 pairing between `PreReceiveHook`'s counter increment and `PostReceiveHook`'s decrement, enabling indefinite starvation of the "repository can be moved" state for a repository (DoS of a housekeeping/administration capability).
- The ordering guarantee that `UpdateHook`/`ReferenceTransactionHook` only run in the context of a genuine reference update, letting a caller trigger arbitrary custom-hook executions with attacker-supplied old/new SHAs and ref names outside of any real push.

This is not merely theoretical: the pattern mirrors the external report's root cause exactly — an "outer" trusted flow (real `git-receive-pack` via `gitaly-hooks`) has all the sequencing/consistency guarantees, while the "inner" service (`HookService`) that implements the actual side effects has none of its own and is reachable directly.

### Likelihood Explanation
Likelihood is high for any deployment that exposes Gitaly's regular external socket to clients that also have ordinary push credentials (which is the normal, intended deployment topology — GitLab Rails/Workhorse/gitlab-shell all talk to the external socket). No special network position, leaked internal token, or privileged role is required beyond what's needed to perform an ordinary authenticated Git operation against the server; the internal-socket token (`InternalSocketToken`) is not needed to reach `HookService` on the external listener at all.

### Recommendation
- Do not register `HookService` on external/non-internal listeners; only register it on Gitaly's internal socket (`CreateInternal`), consistent with the code's own stated intent.
- If backward compatibility requires keeping it reachable externally in the short term, add a server-side check that rejects `HookService` calls on the external listener unless they carry proof of originating from `gitaly-hooks` (e.g., verifying the `InternalSocketToken`/hooks payload correlation) or from an active, server-tracked transaction/quarantine context.
- Track and enforce a strict pairing between `PreReceiveHook`'s counter increment and a guaranteed `PostReceiveHook` decrement (or move this bookkeeping so it cannot be invoked independently of the actual push transaction lifecycle).
- Resolve the referenced tracked issue (gitlab-org/gitaly#3746) rather than leaving the workaround in tests.

### Proof of Concept
1. Obtain the standard credentials used for normal Git operations against Gitaly's external gRPC socket (the same token/cert any legitimate `git push` client uses via Workhorse/gitlab-shell) for a repository the caller can push to.
2. Open a `HookService.PreReceiveHook` bidirectional stream directly against the external socket, supplying a `HooksPayload` env with `UserDetails` matching the caller and a synthetic `changes` line that will pass Rails' `/internal/allowed` check for that repository (e.g., a no-op ref update the user is authorized to perform).
3. Observe that the RPC succeeds and Rails' `PreReceive`/reference-counter-increment endpoint is called, exactly as in `internal/gitaly/hook/prereceive.go` lines 197–201, without ever having run `git-receive-pack`.
4. Repeat step 2 multiple times without ever invoking the matching `PostReceiveHook`, inflating the repository's push-in-progress reference counter and preventing GitLab from considering the repository movable/idle — reproducing the "wrapper checks bypassed by calling the inner service directly" bug class from the source report, adapted to Gitaly's hook-service boundary.
