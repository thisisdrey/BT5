### Title
Stale per-block `index-cache` in v0-4-market.clar causes incorrect debt/collateral notional valuation - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` caches vault borrow/liquidity indexes in `index-cache`, keyed by `{timestamp: stacks-block-time, aid}`, to avoid repeated cross-contract calls within the same block. The cache is only populated on a **miss** and is only explicitly refreshed in one specific code path (`socialize-debt-asset`, after bad-debt write-down). Every other state-changing vault operation that mutates the vault's live `index`/`lindex` (deposit, redeem, `system-borrow`, `system-repay`) updates the vault's own `var-get index`/`lindex` directly via `var-set` inside the vault's `accrue` function, without going through, or invalidating, the market's `index-cache`. This is structurally the same defect class as the reported `totalExcludedSupply` bug: a cached aggregate value that mirrors live state is updated on only some code paths (cache-miss / explicit socialize refresh) and not on all paths that actually change the underlying state, so it drifts from reality within its validity window (one block).

Meanwhile, every vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) advances its own `index`/`lindex` state variables directly on `deposit`, `redeem`, `system-borrow`, and `system-repay` via its internal `accrue` function: [4](#0-3) 

None of these vault-level calls go through, or invalidate, the market's `index-cache` map. So if the market has already cached an asset's index earlier in a block (e.g., from a health check on any account's position), and a vault-mutating operation subsequently changes that vault's real index within the same block, later market operations in that same block that reuse the cache will value collateral/debt using the stale, pre-mutation index — exactly analogous to `totalExcludedSupply` continuing to reflect a stale value after excluded-account balances change through paths other than `setAccountExcluded`/`setBreakageSink`.

### Impact Explanation
Debt/collateral notional values feed directly into LTV/health checks that gate borrowing, collateral withdrawal, and liquidation eligibility. A stale, lower cached borrow index understates a borrower's actual debt-notional, letting health checks pass when the real debt (after normal accrual in another transaction that same block) would fail them, or letting collateral be withdrawn/borrowed against beyond what current state allows. This falls under temporary freezing of funds / theft-adjacent risk if it allows over-borrowing or a liquidation to be evaded within the stale-cache window; the effect resolves at the next block since `stacks-block-time` changes and the cache key rolls over, but the exposure exists within the vulnerable block.

### Likelihood Explanation
Requires only two ordinary transactions landing in the same block: one that primes the market's `index-cache` for an asset (any position lookup / health check touching that asset), and a second that mutates the vault's real index for that asset through a normal deposit/redeem/borrow/repay. Both are unprivileged actions reachable by any user, so likelihood is non-trivial but bounded by needing same-block ordering, which is influenced by mempool/miner ordering rather than attacker-guaranteed control.

### Recommendation
Invalidate or refresh the relevant `index-cache` entry every time a vault operation that changes `index`/`lindex` executes through the market (deposit, redeem, `system-borrow`, `system-repay`), not just after `socialize-debt-asset`. Alternatively, remove the block-scoped cache and always call `vault-accrue` fresh for any notional/health computation, matching the fix pattern applied in the referenced report (update the cached aggregate on every state-changing path rather than a subset of them).

### Proof of Concept
1. Transaction A (any user) triggers a market health check or notional evaluation that touches asset `X`, causing `accrue-and-cache` to populate `index-cache` for `{timestamp: T, aid: X}` with index `I0`.
2. Transaction B (any user, same block `T`) calls `deposit`/`redeem`/`system-borrow`/`system-repay` on vault `X`, whose internal `accrue` advances `index` to `I1 > I0` via direct `var-set`, without touching the market's `index-cache`.
3. Transaction C (same block `T`) performs a borrow/withdraw/liquidation health check involving asset `X`; `calculate-asset-notional-value` calls `accrue-and-cache`, which hits the still-cached `I0` instead of the vault's actual `I1`, producing an understated debt-notional (or otherwise stale) value and an incorrect health/LTV determination for the duration of block `T`.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
