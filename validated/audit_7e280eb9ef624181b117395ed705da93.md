### Title
Disabling `relay.am_relay` via config reload does not stop already-established relay sessions from continuing to forward traffic - (File: `outside.go`)

### Summary
Nebula's relay subsystem allows a node to act as either a `ForwardingType` relay (forwarding encrypted packets between two other peers it does not own) or a `TerminalType` relay endpoint. Whether a node is *allowed* to take on the `ForwardingType` relay role is gated by the `relay.am_relay` config flag, checked only at the moment a new relay is requested/created. Once a relay entry exists in a `HostInfo`'s `relayState` and is `Established`, the packet-forwarding hot path never re-checks `relay.am_relay`, so toggling that flag off via a config reload (the Nebula analog of an admin "removing" a communication-capable agent) does not stop already-established forwarding sessions from continuing to relay traffic between two other peers.

### Finding Description
The admission check for becoming a forwarding relay lives in `relay_manager.go`'s `handleCreateRelayRequest`, which only allows a *new* `ForwardingType` relay to be created if `rm.GetAmRelay()` is true: [1](#0-0) 

However, the actual data-plane forwarding logic in `handleOutsideRelayPacket` (which processes already-established relay traffic arriving over the wire) never calls `rm.GetAmRelay()` at all. It only inspects the relay's `State`/`Type` fields stored in the `HostInfo.relayState`: [2](#0-1) 

Specifically, for the `ForwardingType` case, the only gate is `targetRelay.State == Established` — there is no re-validation that this node is still configured/allowed to be a relay: [3](#0-2) 

The `relayManager.reload()` function does update the in-memory `amRelay` flag on a config reload, but it performs no corresponding teardown of existing `relayState` entries on the affected `HostInfo` objects when the flag flips from `true` to `false`: [4](#0-3) 

This mirrors the external report's root cause exactly: a state toggle intended to disable a communication capability (`toggleBridgeAgent` / `isBridgeAgent` vs. `relay.am_relay`) is enforced only at the "creation"/"admission" call site (`handleCreateRelayRequest` vs. `removeBranchBridgeAgent`), while the actual traffic-forwarding call path (`callOut()` vs. `handleOutsideRelayPacket`) never re-checks the current state before continuing to communicate/forward.

### Impact Explanation
An operator who disables relaying on a node (e.g., in response to a policy change, compromise concern, or to stop the node acting as a relay) expects that action to take effect immediately for the emergency/administrative purpose it serves. Because the forwarding hot path does not re-validate `am_relay`, any relay sessions established prior to the config change keep silently forwarding third-party traffic through the node indefinitely (until the relay's underlying tunnels are torn down for unrelated reasons). This undermines an administrative/emergency control, similar to the Medium-severity judgment in the referenced Maia finding: no direct token/fund loss, but the intended "stop acting as relay" control is rendered ineffective for live sessions.

### Likelihood Explanation
This requires no attacker action beyond passively continuing to use an already-established relay path; it is triggered purely by normal operational use (reloading config to disable relaying) combined with pre-existing relay sessions, making it fully and reliably reachable whenever an operator toggles `relay.am_relay` off while relay sessions are active.

### Recommendation
When `relay.am_relay` transitions from `true` to `false` during a config reload, either:
1. Tear down / disestablish all `ForwardingType` relay entries where the local node is acting as the forwarding hop (mirroring `unlockedDisestablishVpnAddrRelayFor`), or
2. Add an explicit `rm.GetAmRelay()` check in `handleOutsideRelayPacket`'s `ForwardingType` branch before calling `f.SendVia`, dropping the packet and disestablishing the relay entry if relaying is no longer permitted.

### Proof of Concept
1. Start node `R` with `relay.am_relay: true`; nodes `A` and `B` are configured to relay through `R`.
2. `A` and `B` establish a `ForwardingType`/`TerminalType` relay pair through `R` via `handleCreateRelayRequest` (admission check passes because `am_relay` is true at that time).
3. Operator reloads `R`'s config with `relay.am_relay: false` (e.g., to stop `R` from being usable as a relay).
4. `relayManager.reload()` updates `rm.amRelay` to `false`, but no existing `relayState` entries on `R`'s `HostInfo` objects are torn down.
5. `A` continues sending relayed traffic to `B` through `R`. On `R`, `readOutsidePackets` → `handleOutsideRelayPacket` finds the existing `Established` `ForwardingType` relay and forwards the packet via `SendVia` without ever consulting `rm.GetAmRelay()`, so traffic keeps flowing through `R` even though relaying was just disabled.

func (rm *relayManager) reload(c *config.C, initial bool) error {
	if initial || c.HasChanged("relay.am_relay") || c.HasChanged("relay.use_relays") {
		amRelay := c.GetBool("relay.am_relay", false)
		rm.amRelay.Store(amRelay)
		rm.useRelays.Store(c.GetBool("relay.use_relays", true) && !amRelay)
	}
	return nil
}

func (f *Interface) handleOutsideRelayPacket(hostinfo *HostInfo, via ViaSender, out []byte, packet []byte, h *header.H, fwPacket *firewall.Packet, lhf *LightHouseHandler, nb []byte, q int, localCache firewall.ConntrackCache) {
	// Successfully validated the thing. Get rid of the Relay header and the AEAD tag
	signedPayload := packet[header.Len : len(packet)-hostinfo.ConnectionState.dKey.Overhead()]
	// Pull the Roaming parts up here, and return in all call paths.
	f.handleHostRoaming(hostinfo, via)
	// Track usage of both the HostInfo and the Relay for the received & authenticated packet
	f.connectionManager.In(hostinfo)
	f.connectionManager.RelayUsed(h.RemoteIndex)

	relay, ok := hostinfo.relayState.QueryRelayForByIdx(h.RemoteIndex)
	if !ok {
		// The only way this happens is if hostmap has an index to the correct HostInfo, but the HostInfo is missing
		// its internal mapping. This should never happen.
		hostinfo.logger(f.l).Error("HostInfo missing remote relay index",
			"relayRemoteIndex", h.RemoteIndex,
		)
		return
	}

	switch relay.Type {
	case TerminalType:
		// If I am the target of this relay, process the unwrapped packet
		// From this recursive point, all these variables are 'burned'. We shouldn't rely on them again.
		via = ViaSender{
			UdpAddr:   via.UdpAddr,
			relayHI:   hostinfo,
			relay:     relay,
			IsRelayed: true,
		}
		f.readOutsidePackets(via, out[:0], signedPayload, h, fwPacket, lhf, nb, q, localCache)
	case ForwardingType:
		// Find the target HostInfo relay object
		targetHI, targetRelay, err := f.hostMap.QueryVpnAddrsRelayFor(hostinfo.vpnAddrs, relay.PeerAddr)
		if err != nil {
			hostinfo.logger(f.l).Info("Failed to find target host info by ip",
				"relayTo", relay.PeerAddr,
				"relayFrom", hostinfo.vpnAddrs[0],
				"error", err,
			)
			return
		}

		// If that relay is Established, forward the payload through it
		if targetRelay.State == Established {
			switch targetRelay.Type {
			case ForwardingType:
				// Forward this packet through the relay tunnel, rebuilding it in place.
				// Encode overwrites the old outer header, and the new AEAD tag lands where the old one was
				fwdBuf := packet[:0:len(packet)] // Cap to len(packet) to protect memory from a larger parent buffer
				f.SendVia(targetHI, targetRelay, signedPayload, nb, fwdBuf, true)
			case TerminalType:
				hostinfo.logger(f.l).Error("Unexpected Relay Type of Terminal")
				return
			default:
				if f.l.Enabled(context.Background(), slog.LevelDebug) {
					hostinfo.logger(f.l).Debug("Unexpected targetRelay Type", "from", via, "relayType", targetRelay.Type)
				}
				return
			}
		} else {
			hostinfo.logger(f.l).Info("Unexpected target relay state",
				"relayTo", relay.PeerAddr,
				"relayFrom", hostinfo.vpnAddrs[0],
				"targetRelayState", targetRelay.State,
			)
			return
		}
