### Title
Unchecked `ECPoint.Fp` cast in ECDSA public-key recovery can throw `ClassCastException`, crashing signature verification for any broadcast transaction - (File: `crypto/src/main/java/org/tron/common/crypto/ECKey.java`)

### Summary
The upstream Go bug (CVE-2025-58188) is a bug-class of "unchecked type assumption during untrusted-input verification causing a panic": `crypto/x509` blindly casts a certificate's public key to an interface it assumes is implemented, and a DSA key breaks that assumption, crashing the process. `ECKey.recoverPubBytesFromSignature`, which every signed transaction goes through during `checkWeight`/`validateSignature`, contains the same pattern: it unconditionally casts a BouncyCastle `ECPoint` computation result to the concrete subtype `ECPoint.Fp`, assuming the result can never be represented by a different `ECPoint` implementation (e.g., the curve's "point at infinity" special class).

### Finding Description
`ECKey.recoverPubBytesFromSignature` recovers a candidate public key point from attacker-supplied `(r, s, recId)` signature components and a message hash: [1](#0-0) 

```
BigInteger eInv = BigInteger.ZERO.subtract(e).mod(n);
BigInteger rInv = sig.r.modInverse(n);
BigInteger srInv = rInv.multiply(sig.s).mod(n);
BigInteger eInvrInv = rInv.multiply(eInv).mod(n);
ECPoint.Fp q = (ECPoint.Fp) ECAlgorithms.sumOfTwoMultiplies(CURVE
    .getG(), eInvrInv, R, srInv);
return q.getEncoded(/* compressed */ false);
```

`ECAlgorithms.sumOfTwoMultiplies(...)` returns a generic `org.bouncycastle.math.ec.ECPoint`. For an `Fp` curve this is normally an `ECPoint.Fp` instance, but if the two scalar multiplications sum to the curve's point at infinity, BouncyCastle represents that result with the curve's dedicated infinity point implementation rather than a generic `ECPoint.Fp` — the concrete class differs by BouncyCastle version/curve implementation. The code performs a hard cast with no `instanceof` guard and no exception handling around it, exactly mirroring the Go bug's blind interface-cast assumption on attacker-influenced key material.

The identical unguarded-cast pattern exists in the SM2 sign-scheme analogue as well: [2](#0-1) 

This function is reached from every transaction's mandatory signature check. `TransactionCapsule.checkWeight` calls `SignUtils.signatureToAddress` → `ECKey.signatureToAddress` → `signatureToKeyBytes` → `recoverPubBytesFromSignature` for each provided signature: [3](#0-2) 

`checkWeight` is invoked from `validateSignature`, which is invoked from `validatePubSignature`, whose only catch clauses are checked exceptions (`SignatureException | PermissionException | SignatureFormatException`) — a `ClassCastException` is an unchecked `RuntimeException` and is **not** caught here: [4](#0-3) 

`validatePubSignature`/`validateSignature` is invoked both from `Manager.pushTransaction` (single broadcast transaction path) and from `Manager.processTransaction` (block-application path, used per-transaction inside `processBlock` while a block is being applied): [5](#0-4) [6](#0-5) 

For the single-broadcast path, `Wallet.broadcastTransaction` has a generic `catch (Exception e)` fallback that would absorb the `ClassCastException` and return an error response rather than crashing: [7](#0-6) 

However, `processBlock`'s per-transaction loop calling `processTransaction` has no such blanket `catch (Exception|RuntimeException)` guard around signature validation; an uncaught `ClassCastException` there would propagate out of `processBlock` unhandled by the declared checked-exception signature, which is a distinct failure mode from a normal validation error and can abort block application/synchronization on any node that processes a block containing such a crafted signature.

### Impact Explanation
If the point-at-infinity case is reachable for a small set of crafted `(r, s, recId)` values on the secp256k1 curve (this is the same math BouncyCastle already documents having NPE edge cases for elsewhere in this same codebase — see the existing NPE-catching comments in `SM2.verify`/`verifyMessage`), an attacker can craft a transaction signature that throws `ClassCastException` deep inside signature recovery instead of returning `null`/failing gracefully. Because this exception is unchecked and not covered by the checked-exception catch lists used throughout the transaction-verification call chain, it can escape signature verification entirely and propagate into block application (`processBlock`) or transaction-signing-service worker threads (`preValidateTransactionSign`'s `ValidateSignTask`), producing node crashes/halts or a denial-of-service condition reachable by any unprivileged transaction broadcaster, without needing any special permission.

### Likelihood Explanation
Likelihood is **uncertain** without confirming whether the specific `(r, s)` values that make `sumOfTwoMultiplies` return the curve's infinity-point class are actually reachable/producible by an attacker (this requires solving for r, s such that `eInvrInv*G + srInv*R` is infinity, which may or may not be computationally feasible depending on curve/BouncyCastle internals) — the analog to CVE-2025-58188 is only a bug-class hint, not proof that this exact class-cast is triggerable. That said, the code pattern itself (blind cast on attacker-influenced elliptic-curve computation output, no `instanceof`/try-catch) is a clear latent weakness identical in shape to the reported Go vulnerability, and this code path is unconditionally exercised on every signed transaction and every block.

### Recommendation
- Replace the unchecked `(ECPoint.Fp) ...` casts in `ECKey.recoverPubBytesFromSignature` (and the analogous `SM2.recoverPubBytesFromSignature`/`ECCurve.Fp` casts) with an `instanceof` check, returning `null` (treated as "signature invalid, try next recId") on mismatch instead of letting a `ClassCastException` escape.
- Wrap the whole EC point recovery computation in a try/catch that converts any `RuntimeException` (not just checked exceptions) into the existing `SignatureException`/`null`-return contract, consistent with the NPE-catching pattern already used in `SM2.verify`/`verifyMessage`.
- Audit `TransactionCapsule.validatePubSignature`/`checkWeight` and `Manager.processTransaction`/`processBlock` to ensure any `RuntimeException` thrown during signature recovery is caught and converted to `ValidateSignatureException` rather than propagating uncaught through block application.

### Proof of Concept
Not established. A concrete PoC would require finding/deriving `(r, s, recId)` values for secp256k1 for which BouncyCastle's `ECAlgorithms.sumOfTwoMultiplies` returns the curve's dedicated infinity-point implementation (rather than a generic `ECPoint.Fp`), then submitting a transaction signed with those raw signature bytes via `Wallet.broadcastTransaction` or embedding it in a block reaching `Manager.processTransaction`. This was not verified against the actual BouncyCastle version pinned by this project, so exploitability of the class-cast is unconfirmed.
