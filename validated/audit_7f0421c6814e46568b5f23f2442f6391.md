### Title
Missing public-key-hash verification in `neighbor_handshakes_try_finish` allows a neighbor-of-neighbor to register under a forged identity - ([File: stackslib/src/net/neighbors/walk.rs])

### Summary
`check_handshake_pubkey_hash` (walk.rs:1663-1680), which verifies that `Hash160(data.handshake.node_public_key)` matches the expected `naddr.public_key_hash`, is only called from `pingback_handshakes_try_finish` (walk.rs:1714). `handle_neighbor_handshake_accept` (walk.rs:1092-1124), which is invoked from `neighbor_handshakes_try_finish` (walk.rs:1147-1231) for neighbor-of-neighbor discovery, calls `add_or_schedule_replace_neighbor` directly with `data.handshake` (walk.rs:1104-1110) without ever calling `check_handshake_pubkey_hash` against the `naddr` that was supplied to it.

### Finding Description
`neighbor_handshakes_try_finish` iterates over `(naddr, message)` pairs collected from in-flight handshake requests sent to neighbors that `cur_neighbor` advertised via `GetNeighbors`/`Neighbors` (walk.rs:1147). Each `naddr: NeighborAddress` carries a `public_key_hash` field that was claimed for that peer during discovery. When a `HandshakeAccept`/`StackerDBHandshakeAccept` is received, the code goes straight to:

```
self.handle_neighbor_handshake_accept(network, naddr, &message.preamble, data, db_data)?;
```
(walk.rs:1224-1230)

and inside `handle_neighbor_handshake_accept`, `data.handshake` (which contains `node_public_key`, fully attacker controlled) is passed straight into `self.neighbor_db.add_or_schedule_replace_neighbor(...)` (walk.rs:1104-1110), which ultimately writes to `self.frontier` / `self.new_frontier` and to the `PeerDB` (via `insert_or_replace_peer`), without any call to `check_handshake_pubkey_hash` comparing `naddr.public_key_hash` to `Hash160(data.handshake.node_public_key)`.

This is the exact same threat model that `pingback_handshakes_try_finish` explicitly guards against at walk.rs:1713-1716, where the code fetches `peer_nk` from the returned handshake and calls `Self::check_handshake_pubkey_hash(&peer_nk, data, &naddr)` before proceeding to `add_or_schedule_replace_neighbor`. The neighbor-of-neighbor discovery path lacks the analogous check.

By contrast, `handshake_try_finish` (walk.rs:742-813) / `handle_handshake_accept` (walk.rs:676-737) handshake directly with `cur_neighbor`, whose identity/public key is being learned for the first time (there is no independently-advertised `public_key_hash` to validate against) — so the absence of the check there is not itself a vulnerability. The gap is specifically in the neighbor-of-neighbor flow, where a previously-claimed `public_key_hash` (from `naddr`) exists and should be, but is not, checked.

### Impact Explanation
A malicious peer `cur_neighbor`, when asked for its neighbors, can advertise a `NeighborAddress` (IP, port, `public_key_hash`) for a victim third-party node. When the walker attempts to handshake with that advertised address, the attacker (or a peer colluding with `cur_neighbor`, e.g. by controlling the IP:port advertised) can respond with a `HandshakeAccept` containing an arbitrary `node_public_key` that does not hash to the originally advertised `public_key_hash`. Because `check_handshake_pubkey_hash` is never invoked on this path, `add_or_schedule_replace_neighbor` will persist this neighbor into `self.frontier`/`self.new_frontier` and the `PeerDB` under a public key that was never authenticated against the original claim. This is an unauthenticated write of unproven identity data into the frontier/PeerDB, matching the "unauthenticated/unauthorized write to state" Critical category.

### Likelihood Explanation
The attacker only needs to run one or more ordinary P2P peers reachable by the victim node and to have the node reach the "get neighbors of neighbor" discovery phase (`neighbor_handshakes_try_finish`), which is a normal, frequently-exercised part of the neighbor walk. No privileged role, secret, or non-standard reachability is required — sending a crafted `HandshakeAccept`/`StackerDBHandshakeAccept` with an arbitrary `node_public_key` is trivial and repeatable on every walk cycle.

### Recommendation
Add a `check_handshake_pubkey_hash`-style verification inside `handle_neighbor_handshake_accept` (or immediately before calling it in `neighbor_handshakes_try_finish`), comparing `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key)` against `naddr.public_key_hash`, and reject/drop (rather than register) the neighbor when the hashes don't match — mirroring the guard already present in `pingback_handshakes_try_finish` at walk.rs:1713-1716.

### Proof of Concept
Add a unit test in `stackslib/src/net/neighbors/walk.rs`'s test module:
1. Construct a `NeighborWalk` in the `GetHandshakesFinish` state with a `naddr: NeighborAddress` whose `public_key_hash` corresponds to key `A`.
2. Craft a `HandshakeAcceptData` where `data.handshake.node_public_key` corresponds to a different key `B` (so `Hash160(B) != naddr.public_key_hash`).
3. Feed this via `self.comms` mock/stub so `neighbor_handshakes_try_finish` picks it up, calling `handle_neighbor_handshake_accept(network, naddr, preamble, &data, None)`.
4. Assert that, after the call, `self.new_frontier` (or `self.frontier`) contains an entry for `naddr` — showing that the mismatched-key neighbor was still inserted, in contrast to the equivalent test against `pingback_handshakes_try_finish` where `check_handshake_pubkey_hash` correctly causes the entry to be skipped (`continue` at walk.rs:1715).

Note: full verification of `add_or_schedule_replace_neighbor`/`neighbor_from_handshake` internals in `stackslib/src/net/neighbors/db.rs` could not be completed within the available tool budget; if those functions independently re-verify `naddr.public_key_hash` against the handshake key before writing to `PeerDB`, this finding would be mitigated. Based on the code reachable and read in `walk.rs`, no such check is applied at the `neighbor_handshakes_try_finish` → `handle_neighbor_handshake_accept` call site.         preamble: &Preamble,

    ) -> Result<Neighbor, net_error> {
        let local_peer_str = format!("{:?}", network.get_local_peer());

        let mut neighbor_from_handshake = self
            .neighbor_db
            .neighbor_from_handshake(network, preamble, data)?;

        // if the neighbor accidentally gave us a private IP address, then
        // just use the one we used to contact it.  This can happen if the
        // node is behind a load-balancer, or is doing port-forwarding,
        // etc. But do nothing if both cur_neighbor and its reported address are private.
        if (neighbor_from_handshake.addr.addrbytes.is_in_private_range()

            && !self.cur_neighbor.addr.addrbytes.is_in_private_range()
        {
            debug!(
                "{}: outbound neighbor gave private IP address {:?}; assuming it meant {:?}",
                local_peer_str, &neighbor_from_handshake.addr, &self.cur_neighbor.addr
            );
            neighbor_from_handshake.addr.addrbytes = self.cur_neighbor.addr.addrbytes.clone();
            neighbor_from_handshake.addr.port = self.cur_neighbor.addr.port;
        }

        if self.walk_outbound && neighbor_from_handshake.addr != self.cur_neighbor.addr {
            // somehow, got a handshake from someone that _isn't_ cur_neighbor.
            // Note that this does not matter for inbound walks, because we don't always know the
            // real address anyway (since an inbound neighbor might be NAT'ed from us).
            debug!("{}: got unsolicited (or bootstrapping) HandshakeAccept from outbound {:?} (expected {:?})", 
                       local_peer_str,
                       &neighbor_from_handshake.addr,
                       &self.cur_neighbor.addr);

            return Err(net_error::PeerNotConnected(format!("Got unsolicited (or bootstrapping) HandshakeAccept from outbound {:?} (expected {:?})", &neighbor_from_handshake.addr, &self.cur_neighbor.addr)));
        };

        debug!(
            "{}: Connected with {:?}",
            local_peer_str, &self.cur_neighbor.addr
        );

        // update our view of `cur_neighbor`, but only if `cur_neighbor` is routable for us.
        // That is not guaranteed to be the case in one instance: this is an inbound walk, and
        // `cur_neighbor` is the very first neighbor we're querying.
        if self.walk_outbound || self.first_neighbor.addr != self.cur_neighbor.addr {
            let cur_neighbor = self.cur_neighbor.clone();
            let new_cur_neighbor =
                self.neighbor_db
                    .update_neighbor(network, cur_neighbor, Some(data), db_data)?;
            self.cur_neighbor = new_cur_neighbor;
        }
        self.new_frontier
            .insert(self.cur_neighbor.addr.clone(), self.cur_neighbor.clone());
        self.neighbor_from_handshake = neighbor_from_handshake.addr;

        Ok(self.cur_neighbor.clone())

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }
