### Title
Orphaned ReceivedData/PostponedReceipt/PendingDataCount/PromiseYieldReceipt/PromiseYieldStatus/Yield↔DataId trie rows are never removed by `remove_account`, allowing unbounded unaccounted state bloat via repeated ephemeral-account create/delete - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:504-575) only deletes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie rows for an account. It never scans or removes `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldTimeout`/`PromiseYieldIndices`, or `YieldIdToDataId`/`DataIdToYieldId` rows that reference the account as `receiver_id`. An attacker who leaves such rows unresolved before calling `DeleteAccount` causes them to survive permanently in the trie with no owning account to ever pay for or clean them up.

### Finding Description
`action_delete_account` (runtime/runtime/src/actions.rs:314-390) performs two size checks before deleting an account: `account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` [1](#0-0)  and `gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN` [2](#0-1) . Neither check inspects whether the account has outstanding `PostponedReceipt`/`PendingDataCount`/`ReceivedData` entries (from a 2-dependency data receipt where only one dependency resolved) or an unresolved `PromiseYieldReceipt`/yield-id mapping. After these checks pass, it calls `remove_account(state_update, account_id)` [3](#0-2) , which is implemented as: [4](#0-3) 

The function iterates only the `access_keys` prefix and the `contract_data` prefix for the account; the trie-key namespace defined in `TrieKey::append_into` (core/primitives/src/trie_key.rs:456-549) includes many additional per-account columns — `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt` — none of which are ever removed for the deleted account [5](#0-4) .

Exploit flow: an attacker deploys a contract on an ephemeral account `name_i` that issues a self-targeted receipt with two input data dependencies (or a `promise_yield`), resolves only one dependency (or never resumes the yield), so a `ReceivedData`+`PostponedReceipt`+`PendingDataCount` row (or `PromiseYieldReceipt`/yield-id-mapping row) is persisted with `receiver_id = name_i`. The attacker then submits `DeleteAccount(name_i)` in the same or a later transaction. Because `remove_account` never scans these prefixes, the rows remain in the trie forever with no account left to be charged storage staking for them, while the attacker's storage-staking deposit for `name_i` is fully refunded to the beneficiary via `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` [6](#0-5) . Repeating with new `name_i` values grows shard state monotonically.

### Impact Explanation
This is a permanent, unaccounted trie/state-root growth issue narrowly scoped to the `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldTimeout`, and yield-id mapping `TrieKey` variants proven orphaned by `remove_account`. It violates the value-conservation invariant that all retained trie state must be backed by a storage-staking deposit, and the liveness invariant that unbounded state growth should not be achievable for free (net of gas costs). This falls under NEAR's state-bloat / resource-exhaustion bounty category rather than direct fund theft, since no balance is stolen — the attacker's account balance is refunded normally; what leaks is trie space with no accountable owner.

### Likelihood Explanation
Preconditions are fully within reach of an unprivileged sender: create an account, deploy a wasm contract, submit a function call that creates a 2-dependency data receipt or a `promise_yield` targeting itself, and submit `DeleteAccount` without ever satisfying the second dependency/resuming the yield. Each iteration costs normal gas/storage-staking fees for account creation and contract deployment/calls, which are refunded on deletion except for the gas burnt; there is no per-orphan-row storage fee charged that isn't fully refunded, so the marginal cost of leaving behind orphaned rows approaches only the gas cost of the transactions, and the process is trivially repeatable at scale with new account names.

I was not able to fully verify from the available index (1) the exact code path in `runtime/runtime/src/lib.rs` that increments `Account.storage_usage` when a `PostponedReceipt`/`ReceivedData`/`PromiseYieldReceipt` is written for a receiver, and (2) whether that increment would push `account_storage_usage` past `MAX_ACCOUNT_DELETION_STORAGE_USAGE` for a single large-enough attack round (which would only rate-limit, not prevent, the exploit across many ephemeral accounts). This gap does not change the core finding — `remove_account` unconditionally skips these columns for any account under the deletion-size cap.

### Recommendation
Extend `remove_account` (core/store/src/utils/mod.rs) to also iterate and remove, for the account being deleted (as `receiver_id`): `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, and `PromiseYieldReceipt`/yield-id mapping rows, mirroring the existing access-key/contract-data prefix-iteration pattern. Alternatively/additionally, disallow `DeleteAccount` while the account has any outstanding postponed receipts or unresolved promise-yields (analogous to the existing `DeleteAccountStaking` check), forcing resolution or timeout before deletion, and ensure any associated storage cost is either refunded from a dedicated escrow or burned instead of silently orphaned.

### Proof of Concept
Integration/test-loop test plan (e.g., extending `test-loop-tests/src/tests/create_delete_account.rs` or `runtime/runtime/src/access_keys.rs` unit-test style used for `remove_account`):
1. Create an ephemeral account `alice_i`, deploy a contract exposing a method that issues a `FunctionCall` receipt with two `Action::FunctionCall` input dependencies targeting itself (or calls `promise_yield_create` targeting itself).
2. Trigger data-receipt processing so only one dependency resolves, leaving a `PostponedReceipt`/`PendingDataCount`/`ReceivedData` row (or leave the yield unresumed).
3. Submit `Action::DeleteAccount(beneficiary)` for `alice_i` and assert it succeeds (`ActionResult.result.is_ok()`).
4. After commit, iterate the trie for `TrieKey::PostponedReceipt { receiver_id: alice_i, .. }` / `TrieKey::ReceivedData { receiver_id: alice_i, .. }` / `TrieKey::PromiseYieldReceipt { .. }` prefixes and assert the rows still exist (count > 0) even though `get_account(&state_update, &alice_i)` returns `None`.
5. Repeat for N ephemeral accounts and assert the shard's total trie key count for these columns grows linearly with N while `Account.storage_usage`/storage-staking charged against any live account remains unaffected, demonstrating unrefunded, unaccounted, permanent growth.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
