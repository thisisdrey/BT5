## Analysis: Unbounded thread-pool queue growth from uncancelled tasks in `BatchValidateSign` precompile

The CVE describes a resource-cleanup bug class: a scheduled background task (hrtimer) that is not cancelled when its owning object is torn down, so it keeps running against/holding a freed resource. The closest reachable analog in java-tron is in the TVM precompiled contract `BatchValidateSign`, which submits worker tasks to a static, shared, **unbounded** thread pool and does **not cancel** them when the per-transaction CPU deadline is hit — exactly mirroring the "background task outlives the deadline/lifetime it was tied to" bug class, but reachable by any transaction sender through a TVM opcode/precompile call.

### Title
Unbounded background-task accumulation in `BatchValidateSign` TVM precompile due to missing future cancellation on timeout - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.BatchValidateSign` submits one `RecoverAddrTask` per signature to a static `ExecutorService workers` shared by *all* TVM executions on the node [1](#0-0) . When the countdown latch does not complete within the transaction's remaining CPU budget, the code throws a "not enough time" exception without cancelling the outstanding `Future`s [2](#0-1) . The pool is created via `ExecutorServiceManager.newFixedThreadPool`, which uses `Executors.newFixedThreadPool`, backed by an **unbounded** `LinkedBlockingQueue` [3](#0-2) .

### Finding Description
Any TVM contract can call the `BatchValidateSign` precompile with up to `MAX_SIZE = 16` signatures per call [4](#0-3) . On every call, up to 16 `RecoverAddrTask`s are submitted to the shared static `workers` pool and a `CountDownLatch.await` is bounded by `getCPUTimeLeftInNanoSecond()` — i.e., by the *caller's* remaining CPU/time budget for that transaction, not by an independent timeout [5](#0-4) . If the transaction's CPU budget is already close to exhaustion when `BatchValidateSign` runs (a condition fully controllable by the caller, e.g. via prior expensive opcodes or nested calls), `countDownLatch.await` returns `false` almost immediately, `Program.Exception.notEnoughTime` is thrown, and execution moves on — but the submitted `RecoverAddrTask` futures are **never cancelled**. They remain queued/running in the shared, unbounded pool `workers` (and the analogous pattern exists for `VerifyTransferProof`'s `workersInConstantCall` / `workersInNonConstantCall` pools [6](#0-5) ).

Because the pool is a `static` field shared across the whole node process, and because there is no cap on the backlog of orphaned tasks and no cancellation on the timeout path, a stream of crafted transactions that each intentionally trigger the timeout branch will continuously append 1–16 new tasks to the same shared `LinkedBlockingQueue` without ever being drained faster than they arrive relative to node throughput, growing memory usage over time.

### Impact Explanation
This is directly reachable by any unprivileged account able to broadcast a transaction that deploys or calls a contract invoking the `BatchValidateSign` precompile — no special permission required. Continuous exploitation drives unbounded heap growth in the shared worker queue, which can exhaust node memory (OutOfMemoryError) and crash or destabilize the node, denying the node's ability to keep processing/serving transactions — matching the "node crash or halt" / "API the node can no longer serve" impact bar.

### Likelihood Explanation
The attacker only needs to control transaction structure/energy consumption so that the precompile call occurs when the transaction's CPU time budget is nearly spent (deterministic and fully attacker-controlled, since `vmShouldEndInUs`/CPU budget is derived from the transaction's own energy limit and prior execution, see `calculateCpuLimitInUs`/`checkCPUTimeLimit` usage in `VMActuator`/`VM.play` [7](#0-6) ). Repeating this pattern across many transactions is inexpensive for the attacker (bounded by normal energy fees) yet cheaply accumulates unbounded server-side backlog, making this a low-cost, high-repeatability resource-exhaustion vector.

### Recommendation
- In `BatchValidateSign.doExecute` (and the analogous `VerifyTransferProof`/Sapling code path), when `withNoTimeout` is `false`, explicitly `cancel(true)` all outstanding `Future`s before throwing, so orphaned tasks are interrupted/removed promptly.
- Bound the shared `workers` pool's queue (use a bounded `ArrayBlockingQueue` with a `RejectedExecutionHandler`) instead of the default unbounded queue from `Executors.newFixedThreadPool`, so backlog cannot grow without limit.
- Consider tracking/limiting total in-flight precompile worker tasks per node, independent of any single transaction's CPU budget.

### Proof of Concept
1. Deploy a contract that calls the `BatchValidateSign` precompile with the maximum 16 signatures, after first burning most of the transaction's allotted energy/CPU time via a cheap busy loop or nested calls so `getCPUTimeLeftInNanoSecond()` is near zero when `BatchValidateSign` executes.
2. Broadcast many such transactions concurrently/sequentially; each call reliably falls into the `!withNoTimeout` branch [8](#0-7) , throwing `notEnoughTime` while leaving up to 16 submitted `RecoverAddrTask` futures alive in the static `workers` pool.
3. Observe the JVM heap and thread pool queue size growing without bound as more such transactions are processed, eventually leading to memory pressure/OutOfMemoryError on the node.
