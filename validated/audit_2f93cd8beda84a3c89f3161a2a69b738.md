### Title
Single-step, unchecked authority transfer in `TransferToNewAccount`/`TransferToNewAccountPda` permanently locks user funds if wrong address is supplied - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The unprivileged, user-facing account-migration instructions `transfer_to_new_account` and `transfer_to_new_account_pda` let a `MarginfiAccount` authority move their entire position to a brand-new account under a `new_authority` that is completely unchecked and requires no acceptance step, exactly the single-step-ownership-transfer anti-pattern described in the external report, but here it endangers user funds rather than admin functions.

### Finding Description
Both instructions accept a `new_authority: UncheckedAccount<'info>` with the explicit code comment `WARN: New authority is completely unchecked` [1](#0-0) [2](#0-1) . Neither instruction requires `new_authority` to sign or to co-sign an acceptance transaction; it is only validated to be the correct account by the signer's choice at call time.

The migration is committed atomically and irreversibly in a single transaction: `initialize_migrated_account` sets `new_account.authority` (via `initialize`) to `new_authority.key()` [3](#0-2) , and in the same instruction `finalize_migrated_old_account` disables the old account, zeroes its `lending_account`, and sets `migrated_to` to the new account key [4](#0-3) . A subsequent explicit guard prevents re-migrating the same old account (`check_eq!(old_account.migrated_to, Pubkey::default(), ...)`), so there is no retry/undo path once `migrated_to` is set [5](#0-4) .

If the authority supplies an incorrect, inaccessible, or unintended `new_authority` pubkey (typo, wrong keypair, accidental reuse of an address they don't control), all lending-account balances (deposits and borrows) become permanently controlled by an authority key that can never sign a subsequent instruction to reclaim them, while the old account is simultaneously disabled and can no longer be used. There is no claim/acceptance step analogous to `Ownable2Step`'s `acceptOwnership`, so the classic single-step ownership transfer bug class applies directly to user assets instead of admin privileges.

### Impact Explanation
This is a concrete permanent lock/freeze of user funds, not a theoretical or admin-only issue: the old account is disabled and its `lending_account` zeroed [6](#0-5) , and the new account's authority is set to whatever unchecked pubkey was passed in [7](#0-6) . Any deposited collateral and any position value tied to the account become uncontrollable and unrecoverable by the original user once this executes with a bad `new_authority`.

### Likelihood Explanation
Low-to-moderate: it requires user error (or a malicious front-end/dApp misleading the user) when supplying `new_authority` for `TransferToNewAccount`/`TransferToNewAccountPda`, similar to the "requires admin error" likelihood noted in the original report, but here the actor is any regular account authority rather than a privileged admin, and this instruction is a normal, reachable user-facing account-migration flow used elsewhere in the codebase (e.g., `p0-cli/src/processor/account.rs::marginfi_account_transfer`) [8](#0-7) .

### Recommendation
Add a two-step acceptance flow for account authority migration: require `new_authority` to be a `Signer` (or to co-sign/claim via a follow-up instruction) before the old account is disabled and funds are migrated, mirroring the `Ownable2Step` pattern recommended in the source report. At minimum, require the `new_authority` account to sign the `TransferToNewAccount`/`TransferToNewAccountPda` instruction so a non-existent or inaccessible key cannot be supplied.

### Proof of Concept
1. User A creates a `MarginfiAccount`, deposits funds, and calls `transfer_to_new_account` supplying a `new_authority` pubkey for which no private key is held (e.g., a mistyped address or an address they do not control) — `new_authority` is `UncheckedAccount` and is never required to sign [9](#0-8) .
2. The instruction succeeds: `old_account` is disabled and zeroed, `new_account.authority` is set to the unchecked pubkey, and `old_account.migrated_to` is permanently set [10](#0-9) .
3. User A can no longer operate the old account (`ACCOUNT_DISABLED` flag set) and cannot sign as the new account's authority, permanently losing access to all migrated deposits/borrows.

}

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
