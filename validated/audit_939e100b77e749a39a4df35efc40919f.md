Based on my investigation, I found a strong structural analog to the `claimReceipts()` bug class in Gitaly's Object Pool service.

### Title
`LinkRepositoryToObjectPool` links an arbitrary repository to an arbitrary object pool without verifying the pool actually belongs to that repository, enabling cross-repository object disclosure - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The external report's root cause is that `Account.claimReceipts()` accepts a `market` parameter that identifies which pool to draw funds from, but never checks that this `market` actually matches the market recorded on the `receipt` being claimed (`receipt.tracer`). This lets a caller point a legitimate receipt at an unrelated, attacker-controlled market and drain funds from it.

The Gitaly analog is `ObjectPoolService.LinkRepositoryToObjectPool`. Its request carries two independent repository references — `repository` (the pool member, annotated `target_repository`) and `object_pool` (annotated `additional_repository`) [1](#0-0) . The handler validates that `repository` is a well-formed repository and that `object_pool` is a structurally valid pool directory, but it never checks that `object_pool` is the pool that `repository` is actually supposed to be a member of (e.g., that it was forked from it, or that the caller has any established relationship between the two): [2](#0-1) 

`poolForRequest`/`objectpool.FromProto` only validates that the pool path itself is a legitimate git directory, not that it corresponds to `repository`: [3](#0-2) 

### Finding Description
`Link()` in `internal/git/objectpool/link.go` performs the actual linking by writing the pool's object directory path into the member repository's `objects/info/alternates` file: [4](#0-3) 

Git treats `objects/info/alternates` as an implicit read path: once written, any object present in the pool repository becomes readable from the member repository (via `git cat-file`, `git show`, clone/fetch of the member, etc.), even if that object was never pushed into the member itself.

Because the RPC-level check only confirms "is `object_pool` a valid pool" and "is `repository` a valid repository" — and never cross-validates that the two are legitimately associated — a caller who controls the `repository` field (their own, or any repo they can address) can supply an arbitrary `object_pool` value pointing at someone else's object pool. This is structurally identical to `claimReceipts()` accepting a `market` parameter that is never checked against `receipt.tracer`: a secondary reference field that should be derived from / verified against the primary object is instead taken at face value from the caller.

Field annotations documented in `doc/protobuf.md` show that `target_repository` and `additional_repository` are primarily used by Praefect to determine storage routing/replication, not to enforce that the two repositories are semantically related: [5](#0-4) . Gitaly itself has no notion of "does this member belong to this pool" prior to linking — that relationship is only established as a side effect of a successful `Link()` call.

### Impact Explanation
A successful call causes the target repository to gain a permanent alternates link into a pool repository the caller does not otherwise legitimately control. Since alternates grant transparent read access to every git object in the pool, this is a cross-repository object disclosure primitive: private commits, blobs, and trees stored in the pool repository (e.g., a private fork-source repository) become fetchable/readable through the now-linked (attacker-influenced) repository. This mirrors the "high impact" characterization in the source report, where an unchecked cross-entity reference is exploited to reach into another actor's protected resource.

### Likelihood Explanation
Exploitability depends entirely on whether the caller can reach `LinkRepositoryToObjectPool` with an `object_pool` value they don't legitimately own/control while GitLab Rails' authorization layer does not independently re-derive and verify the pool-to-member relationship before issuing the RPC. Because Gitaly's own handler performs no such verification (as shown above), any upstream caller that fails to enforce this relationship — or any direct/crafted RPC reaching Gitaly — can trigger the unauthorized link. This is the same "any caller of the RPC with a crafted field" reachability pattern called out in the source report for `claimReceipts()`.

### Recommendation
Do not trust the caller-supplied `object_pool` value as authoritative. Before calling `pool.Link()`, verify that the `object_pool`/pool relative path is one that Gitaly (or the upstream orchestrator) has already established for `repository` (e.g., only permit linking to a pool created via `CreateObjectPool` from that same origin repository, or require the pool's recorded origin/member set to include `repository` prior to allowing the link). Alternatively, derive the expected pool location deterministically from `repository`'s own metadata rather than accepting an independently-supplied `object_pool` field, analogous to the source report's recommendation to derive `market` from `receipt.tracer` instead of accepting it as a separate parameter.

### Proof of Concept
1. Actor A has push/administrative access to `repoA` (target_repository) but no legitimate relationship to `poolB`, a private object pool backing a repository the actor cannot otherwise read (additional_repository).
2. Actor A issues `LinkRepositoryToObjectPool(repository=repoA, object_pool=poolB)`.
3. `internal/gitaly/service/objectpool/link.go` validates only that `repoA` is a valid repository and `poolB` is a structurally valid pool directory — it performs no check that `poolB` is the pool `repoA` was forked from or is otherwise entitled to join.
4. `objectpool.Link()` writes `poolB`'s object directory into `repoA/objects/info/alternates`.
5. Actor A can now run `git cat-file`/`git show`/clone against `repoA` and transparently read any object stored in `poolB`, including objects that were never part of `repoA`'s own history.

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
```

```go
			return nil, errInvalidPoolDir
```

```go
// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
```

```markdown
The target repository represents the location or address of the repository being
modified by the operation. This is needed by Praefect (Gitaly Cluster) in order
to properly schedule replications to keep repository replicas up to date.

The target repository annotation marks where the target repository can be found
in the message. The annotation is added near `gitaly.Repository` field (e.g.

isn't `gitaly.Repository` type then it has to contain field annotated
`[(repository)=true]` with correct type. Having separate `repository` annotation
allows to have same field in child message annotated as both `target_repository`
and `additional_repository` depending on parent message.

The additional repository is annotated similarly to target repository but
```
