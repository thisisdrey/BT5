### Title
Missing slippage/bound protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables front-running/sandwich attacks against the TRX Bancor-style AMM - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron implements an on-chain Bancor-style AMM (the `Exchange`/`ExchangeV2` pair) whose pool ratio is mutable and can be moved by any account via `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract`. Unlike `ExchangeTransactionContract`, which carries an `expected` field that is validated against the computed output amount [1](#0-0) , the `ExchangeInjectContract` and `ExchangeWithdrawContract` messages carry no analogous minimum/maximum bound field for the counter-asset amount that the protocol computes on their behalf.

### Finding Description
`ExchangeInjectActuator.execute()` computes the counter-token amount a user must deposit purely from the exchange pool's live balances at execution time: [2](#0-1) 
The only user-supplied input is `tokenQuant` for one side of the pair; `anotherTokenQuant` is derived from `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction executes, with no caller-specified maximum limiting how much of the counter-asset the user is willing to contribute.

Similarly, `ExchangeWithdrawActuator.execute()` computes the counter-token amount a user receives back purely from the live pool ratio: [3](#0-2) 
There is no caller-supplied minimum amount the withdrawer is willing to accept for `anotherTokenQuant`; the only related check is a "Not precise enough" rounding guard [4](#0-3) , which is a rounding-quality check, not an economic slippage bound.

By contrast, `ExchangeTransactionActuator` explicitly protects the trader by validating the caller-supplied `expected` field against the pool-computed output before allowing the trade to proceed [5](#0-4) . `ExchangeInjectContract` and `ExchangeWithdrawContract` never got this protection, so an attacker can:
1. Observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction in the mempool.
2. Submit their own `ExchangeTransactionContract` swap immediately before it to shift `firstTokenBalance`/`secondTokenBalance` in a favorable direction, changing the pool ratio.
3. Let the victim's inject/withdraw execute at the manipulated ratio, causing them to deposit more counter-asset than intended (inject) or receive less counter-asset than expected (withdraw).
4. Optionally submit a reversing swap afterward to restore the ratio and capture the difference — a classic sandwich attack, directly analogous to the reported `_curveSimpleSwap`/`_swapBalancerSimple` bug class where `min_dy`/`minAmountOut` was hardcoded to an unprotective value.

### Impact Explanation
This causes an unbacked/unfair value transfer between accounts interacting with the same `Exchange` pool: victims of `ExchangeInjectContract` overpay in the counter-asset relative to their intended contribution, and victims of `ExchangeWithdrawContract` receive less than the fair-value counter-asset for the liquidity they are removing. Because `Exchange` balances hold real TRX and TRC10 asset balances tracked in `AccountCapsule`, this is a concrete theft-of-funds vector reachable by any account issuing ordinary, unprivileged transactions — no special permission or contract deployment is required.

### Likelihood Explanation
Any account can create `ExchangeTransactionContract` transactions cheaply (fee is `0`, see `calcFee()` in `ExchangeTransactionActuator.java`) to shift the pool ratio just before a target's `ExchangeInjectContract`/`ExchangeWithdrawContract` is packed into a block, since transaction ordering within a block is controlled by the block-producing witness/transaction pool ordering, which is influenced by fee/ordering incentives and is not guaranteed to preserve submission order. This makes the attack readily executable by any unprivileged transaction broadcaster.

### Recommendation
Add a caller-supplied bound field to `ExchangeInjectContract` (e.g. `max_another_token_quant`, a cap on how much counter-asset the user is willing to contribute) and to `ExchangeWithdrawContract` (e.g. `min_another_token_quant`, the minimum counter-asset acceptable on withdrawal), analogous to the existing `expected` field in `ExchangeTransactionContract`. Validate these bounds in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` before mutating balances, rejecting the transaction if the computed `anotherTokenQuant` violates the caller's bound.

### Proof of Concept
1. Pool `P` has `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Victim broadcasts `ExchangeInjectContract{tokenId=first, quant=Q}` expecting to also spend `~B*Q/A` of the second token.
3. Attacker broadcasts `ExchangeTransactionContract` that trades a large amount of the second token into the pool for the first token immediately before the victim's transaction is included, shifting the ratio so `B'/A'` is much larger than `B/A`.
4. Victim's inject executes with the manipulated ratio: `anotherTokenQuant = floorDiv(secondTokenBalance' * Q, firstTokenBalance')` [6](#0-5) , forcing the victim to spend significantly more of the second token than intended, with no on-chain check to reject this because no bound field exists on `ExchangeInjectContract`.
5. Attacker reverses their swap afterward, extracting the difference as profit — mirroring the sandwich-attack pattern described in the external report for unset `minAmountOut`/`limits` parameters.
