### Title
Unbounded Memory Growth in JSON-RPC `eth_newFilter`/`eth_newBlockFilter` Result Queues via Unpolled Filters - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogFilterAndResult.java`)

### Summary
The JSON-RPC filter subsystem accumulates matched log elements and block hashes into unbounded, in-memory `LinkedBlockingQueue`s per registered filter, with no limit on queue size. An anonymous JSON-RPC client can create filters (bounded only by a count limit, `jsonRpcMaxLogFilterNum`/`jsonRpcMaxBlockFilterNum`) and simply never poll them via `eth_getFilterChanges`/`eth_getFilterLogs`. As the chain produces new blocks/logs, the node keeps pushing matched results into these queues indefinitely until the filter's 5-minute expiry — and a broad "match-all" filter on a busy chain can accumulate a very large volume of `LogFilterElement`/block-hash entries during that window, and the pattern can be repeated by re-creating filters before they expire, producing sustained, attacker-controlled server-side memory growth. This mirrors the reported Undici bug class (CWE-770): server-side accumulation of response data for a downstream consumer with no bound, driven by an external, low-cost request pattern.

### Finding Description
`LogFilterAndResult` and `BlockFilterAndResult` both extend `FilterResult<T>`, which wraps a `BlockingQueue<T> result` with no capacity bound: [1](#0-0) [2](#0-1) 

`FilterResult` only tracks an expiry timestamp with no size cap: [3](#0-2) 

Every time the node processes a new block, `handleLogsFilter`/`handleBLockFilter` push matched results into **every non-expired filter's queue**, without checking queue size: [4](#0-3) [5](#0-4) 

The only controls that exist are:
- A cap on the *number* of concurrently registered filters (`maxLogFilterNum`/`maxBlockFilterNum`), enforced at `newFilter`/`newBlockFilter` creation time.
- A 5-minute expiry (`EXPIRE_SECONDS`) that is only checked/reset when the filter is polled or dispatched to.
- The pull-based `eth_getLogs`/`eth_getFilterLogs` path (`LogMatch.matchBlockOneByOne`, `LogBlockQuery.MAX_RESULT`) caps a single *query* result to 10,000 elements — but this cap is entirely separate from, and does not apply to, the push-based accumulation into `LogFilterAndResult.result`/`BlockFilterAndResult.result` performed by `handleLogsFilter`/`handleBLockFilter`.

None of these controls bound the size of an individual filter's queue between polls. A client can register a broad (empty address/topics) filter via `eth_newFilter`, then simply not call `eth_getFilterChanges`/`eth_getFilterLogs` for up to 5 minutes; during that time every matching log across every processed block (solidified or full) is appended to the queue via `logFilterAndResult.getResult().addAll(localResults)`, with no upper bound on the queue's total element count. This is directly analogous to the Undici deduplication handler bug: response data destined for a consumer is buffered server-side without limit while the consumer doesn't (or maliciously won't) drain it.

### Impact Explanation
This is a resource-exhaustion / availability issue reachable via the anonymous JSON-RPC query surface (`TronJsonRpcImpl`, exposed by `httpFullNodeEnable`/`httpSolidityEnable`/`httpPBFTEnable` JSON-RPC endpoints). By registering filters and withholding polls, an attacker can force the FullNode/SolidityNode to buffer log/block data proportional to on-chain activity across the filter's lifetime, with no per-filter memory ceiling. Repeating filter creation just before each expires (or creating multiple filters up to the per-node limit) sustains and multiplies memory pressure, potentially leading to high GC pressure, degraded service, or an OOM crash of the node process — a node crash/DoS on a publicly reachable API path, consistent with the "Medium" scoring rules for this analog.

### Likelihood Explanation
The JSON-RPC filter APIs (`eth_newFilter`, `eth_newBlockFilter`, `eth_getFilterChanges`, `eth_getFilterLogs`) require no authentication or special privilege — any anonymous API client that can reach the JSON-RPC HTTP endpoint can exploit this. The only friction is the configured filter-count limit and the 5-minute expiry window, both of which an attacker can work within by using few filters with broad matching criteria and repeatedly refreshing them. This makes the issue plausible for any node with JSON-RPC enabled and receiving normal transaction/log throughput.

### Recommendation
Bound the accumulated result size per filter (e.g., cap `LogFilterAndResult`/`BlockFilterAndResult` queue length, dropping oldest entries or marking the filter as "overflowed"/forcing re-sync similar to Geth's filter overflow semantics) in `processLogFilterEntry`/`handleBLockFilter`, independent of and in addition to the existing `LogBlockQuery.MAX_RESULT` query-time cap. Consider also capping total memory across all filters (not just filter count) and/or shortening result retention more aggressively when a global memory/queue-size threshold is exceeded.

### Proof of Concept
1. Enable JSON-RPC (`jsonrpc.httpFullNodeEnable = true`).
2. As an anonymous client, call `eth_newFilter` with an empty filter object (no address/topics) — this creates a "match everything" filter, registered in `eventFilter2ResultFull` via `LogFilterAndResult` [6](#0-5) .
3. Do not call `eth_getFilterChanges`/`eth_getFilterLogs` for this filter ID.
4. As normal chain activity continues, every processed block's matching logs are appended without bound via `handleLogsFilter` → `processLogFilterEntry` → `logFilterAndResult.getResult().addAll(localResults)` [7](#0-6) .
5. Just before the 5-minute expiry (`EXPIRE_SECONDS`), issue a lightweight call that touches `updateExpireTime()` indirectly is not required — simply create additional filters (up to `maxLogFilterNum`, default 20,000) or repeat step 2 with new filters to keep queues alive and multiply accumulated memory across many concurrently tracked filters, since queue growth per filter is otherwise only capped by node uptime/expiry, not by size.

  public void handleBLockFilter(BlockFilterCapsule blockFilterCapsule) {
    Iterator<Entry<String, BlockFilterAndResult>> it;

    if (blockFilterCapsule.isSolidified()) {
      it = getBlockFilter2ResultSolidity().entrySet().iterator();
    } else {
      it = getBlockFilter2ResultFull().entrySet().iterator();
    }

    if (!it.hasNext()) {
      return;
    }
    final String originalBlockHash = ByteArray.toJsonHex(blockFilterCapsule.getBlockHash());
    String cachedBlockHash;
    try {
      // compare with hashcode() first, then with equals(). If not exist, put it.
      cachedBlockHash = blockHashCache.get(originalBlockHash, () -> originalBlockHash);
    } catch (ExecutionException e) {
      logger.error("Getting/loading blockHash from cache failed", e); // never happen
      cachedBlockHash = originalBlockHash;
    }
    while (it.hasNext()) {
      Entry<String, BlockFilterAndResult> entry = it.next();
      if (entry.getValue().isExpire()) {
        it.remove();
        continue;
      }
      entry.getValue().getResult().add(cachedBlockHash);
    }
  }

  private void processLogFilterEntry(
      Map.Entry<String, LogFilterAndResult> entry,
      Map<String, LogFilterAndResult> eventFilterMap,
      LogsFilterCapsule logsFilterCapsule) {
    LogFilterAndResult logFilterAndResult = entry.getValue();
    if (logFilterAndResult.isExpire()) {
      eventFilterMap.remove(entry.getKey());
      return;
    }

    long blockNumber = logsFilterCapsule.getBlockNumber();
    long fromBlock = logFilterAndResult.getLogFilterWrapper().getFromBlock();
    long toBlock = logFilterAndResult.getLogFilterWrapper().getToBlock();
    if (!(fromBlock <= blockNumber && blockNumber <= toBlock)) {
      return;
    }

    if (logsFilterCapsule.getBloom() != null && !logFilterAndResult.getLogFilterWrapper()
        .getLogFilter().matchBloom(logsFilterCapsule.getBloom())) {
      return;
    }

    LogFilter logFilter = logFilterAndResult.getLogFilterWrapper().getLogFilter();
    List<LogFilterElement> elements =
        LogMatch.matchBlock(logFilter, blockNumber, logsFilterCapsule.getBlockHash(),
            logsFilterCapsule.getTxInfoList(), logsFilterCapsule.isRemoved());

    List<LogFilterElement> localResults = new ArrayList<>(elements.size());
    for (LogFilterElement element : elements) {
      LogFilterElement cachedElement;
      try {
        // compare with hashcode() first, then with equals(). If not exist, put it.
        cachedElement = logElementCache.get(element, () -> element);
      } catch (ExecutionException e) {
        logger.error("Getting/loading LogFilterElement from cache fails", e); // never happen
        cachedElement = element;
      }
      localResults.add(cachedElement);
    }
    logFilterAndResult.getResult().addAll(localResults);
