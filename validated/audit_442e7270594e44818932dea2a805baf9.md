### Title
Front-runnable Pyth price-feed submissions allow griefing of `collateral-add`/`borrow`/`liquidate` transactions - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
Market entry points accept an optional bundle of raw Pyth update payloads (`price-feeds`) that are applied atomically before the operation executes. Because Pyth's storage layer only accepts a price update if its `publish-time` is strictly newer than the last stored one, any unprivileged party can race a victim's transaction with their own (also valid, publicly obtainable) Pyth update for the same feed and cause the victim's embedded update to be rejected, reverting the victim's entire operation.

### Finding Description
`collateral-add`, `borrow`, and `liquidate` accept `price-feeds: (optional (list 3 (buff 8192)))` and process them via `write-feeds` → `write-feed`, both wrapped in `try!`: [1](#0-0) [2](#0-1) 

`write-feed` calls `pyth-oracle-v4.verify-and-update-price-feeds`, and any failure from the underlying Pyth stack is converted to `ERR-PRICE-FEED-UPDATE-FAILED` and propagated with `try!`, aborting the whole caller transaction.

Downstream, `pyth-storage-v4.write-batch-entry` enforces `(asserts! (is-price-update-more-recent (get price-identifier entry) publish-time) ERR_NEWER_PRICE_AVAILABLE)`: [3](#0-2) 

This "must be strictly newer" gate is the equivalent of the analog's unconfirmed-input problem: the victim's transaction is built assuming the current on-chain price state (an "unconfirmed", not-yet-applied condition, since Pyth prices update every few seconds and are publicly available off-chain), but any unprivileged actor can grab a fresher, equally valid signed Pyth update for the same `price-identifier` from Pyth's public network and submit it first (or in the same block with higher fee/priority). When the victim's bundled update then lands, its `publish-time` is no longer the newest, `write-batch-entry` reverts with `ERR_NEWER_PRICE_AVAILABLE`, `write-feed` converts this to `ERR-PRICE-FEED-UPDATE-FAILED`, and the entire `collateral-add`/`borrow`/`liquidate` call aborts via the `try!` chain — even though the attacker's action was itself a legitimate price update, not a manipulation of price value.

An attacker can repeat this at negligible cost every time a target (especially a liquidator racing to liquidate an unhealthy position, or a borrower reacting to a price move) submits a feed-bundled transaction, indefinitely griefing that specific market entry point for that user during time-critical windows.

### Impact Explanation
This is a temporary-freezing-of-funds analog: a liquidator's time-sensitive `liquidate` call (which is itself in-scope as a market entry point / health-check path) can be repeatedly griefed during exactly the window when fast execution matters, delaying seizure of collateral and repayment of debt. Similarly, a borrower attempting to `collateral-add`/`borrow` with a fresh price to pass a health check can have that specific attempt reverted repeatedly, temporarily freezing their ability to act on their own position during volatile price movements. No privileged access or DAO compromise is required — the price update raced in is a legitimately signed Pyth payload, so this is not "incorrect data from a third-party oracle" (out of scope) but a griefing pattern caused by how this contract structures its own atomic price-update-then-use flow.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: Pyth price updates are public and free to fetch/relay, mempool transactions carrying `price-feeds` payloads are visible before confirmation, and repeatedly front-running a specific target's bundled update requires only monitoring the mempool for calls to `collateral-add`/`borrow`/`liquidate` with a non-`none` `price-feeds` argument targeting a feed the attacker also wants to bump.

### Recommendation
Avoid hard-failing the entire user operation solely because a bundled price update was superseded by a legitimately newer update; treat `ERR_NEWER_PRICE_AVAILABLE` from `write-feed`/`write-feeds` as a soft/no-op success (since a newer price is already stored and can be consumed) rather than propagating it as a fatal error via `try!`.

### Proof of Concept
1. Borrower/liquidator Bob crafts a `collateral-add`/`borrow`/`liquidate` transaction with `price-feeds` containing a signed Pyth update for feed `F` with `publish-time = t`.
2. Attacker Alice, watching the mempool, obtains a newer valid Pyth update for the same feed `F` with `publish-time = t' > t` (trivially available from Pyth's public price service) and submits it in a transaction that lands before Bob's.
3. Bob's transaction executes; `write-feeds` → `write-feed` → `verify-and-update-price-feeds` → `pyth-storage-v4.write-batch-entry` rejects Bob's now-stale update with `ERR_NEWER_PRICE_AVAILABLE`.
4. `write-feed`'s `try!` converts this into `ERR-PRICE-FEED-UPDATE-FAILED`, which propagates via `try!` at `mainnet/contracts/market/v0-4-market.clar:1050`, reverting Bob's entire `collateral-add`/`borrow`/`liquidate` call.
5. Alice repeats this for every subsequent attempt by Bob, indefinitely blocking Bob's time-sensitive operation on that market entry point.
