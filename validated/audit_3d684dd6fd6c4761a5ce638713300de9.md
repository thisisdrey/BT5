### Title
Precompile Signature Verification Cost Is Flat Per-Signature and Ignores Message Size, Allowing Underpriced CPU-Heavy Hashing/Recovery Work - (File: cost-model/src/block_cost_limits.rs)

### Summary
The cost model charges a **fixed** compute-unit cost per secp256k1/ed25519/secp256r1 precompile signature (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`), regardless of the size of the message that is actually hashed/verified for that signature. The real verification work performed inside the precompile (`solana_keccak_hasher::hash` over the referenced message slice, plus an ECDSA/Ed25519 recovery/verify) scales with the attacker-controlled `message_data_size` field (up to 65,535 bytes, `u16`), and up to 255 such signature entries can be packed into a single instruction. Because this work executes as a flat-cost "builtin" outside the SVM's per-instruction compute meter, the actual CPU cost of a transaction's precompile verification is decoupled from both the fee charged and the CU accounting used to bound block/transaction cost. This is the same underlying bug class as the reported "EIP 160 EXP cost increase" gap: a computational primitive whose price does not scale with the size of its input, enabling disproportionately cheap CPU-heavy work.

### Finding Description
`precompiles/src/secp256k1.rs::verify` iterates up to `count` (a `u8`, so up to 255) signature entries per instruction [1](#0-0) . For each entry it:
- Extracts a `message_slice` of length `offsets.message_data_size` (a `u16`, up to 65,535 bytes) from any instruction in the transaction [2](#0-1) 
- Computes `solana_keccak_hasher::hash(message_slice)` and then a full secp256k1 ECDSA public-key recovery [3](#0-2) 

`precompiles/src/ed25519.rs::verify` has the same pattern: it extracts a message of up to 65,535 bytes per signature entry and performs a strict Ed25519 signature verification over it [4](#0-3) . `offsets.message_instruction_index`/`message_data_offset` can reference the same instruction data repeatedly across all `count` entries, so a single large message blob can be re-hashed/re-verified up to 255 times by one instruction.

The cost model that determines how many compute units (and thus fee/priority accounting) a transaction is charged for these signatures is a **flat per-signature constant** independent of `message_data_size`: [5](#0-4) 

This flat cost is what's actually applied per transaction: [6](#0-5) 

Critically, this cost estimate is not what's charged against the SVM's live compute-unit meter during actual instruction execution — the precompile check runs as a builtin whose real work is unmetered by the CU meter. This is directly confirmed by a test comment stating that executing a precompiled instruction "consume[s] 0 from CU-meter", with the entire builtin CU allocation refunded as unused: [7](#0-6) 

In other words: the fee and the nominal compute-cost accounting for a secp256k1/ed25519 signature instruction are fixed per signature count, but the actual CPU work (keccak-256 hashing plus signature recovery/verification over up to 65 KB per entry, times up to 255 entries) scales with attacker-chosen message size and is not gated by the compute-unit budget mechanism that is supposed to bound per-instruction/per-transaction work.

### Impact Explanation
An attacker can construct a transaction containing a secp256k1 (or ed25519) precompile instruction with `count` close to 255, where every signature-offset entry references the same large message blob (up to the maximum allowed by the transaction's message size) rather than 255 distinct small messages. This forces the validator to perform up to 255 keccak-256 hashes over large buffers plus 255 secp256k1 ECDSA recoveries (or 255 Ed25519 verifications) per transaction, while the fee and the compute-unit cost recorded against the block-cost limit are determined only by the flat per-signature constants (`SECP256K1_VERIFY_COST` etc.), not by the size of data hashed/verified. This is grossly underpriced pre-fee/pre-metered CPU work reachable by any unprivileged transaction submitter, and can be used to slow down transaction processing (sigverify/precompile check path) disproportionately to the fee paid — the same DoS pattern the external report describes for RSK's missing EXP-cost-increase (EIP-160) analog.

### Likelihood Explanation
Likelihood is high: constructing such a transaction requires no special privileges, only a validly formed instruction with a legal `SecpSignatureOffsets`/`Ed25519SignatureOffsets` table pointing repeatedly at the same message data — well within a normal user's ability to submit transactions to the cluster. The only constraint is total transaction size, which still permits packing meaningful message sizes (tens of KB) referenced repeatedly by up to 255 signature entries in one instruction.

### Recommendation
Scale the compute-unit (and ideally fee) cost of secp256k1/ed25519/secp256r1 precompile verification with the size of the message actually hashed/verified for each signature entry (`message_data_size`), not merely with signature count, mirroring how EIP-160 corrected the flat EXP opcode price to account for operand size. Additionally, ensure the compute-unit meter used during actual precompile execution reflects real work performed (or, if precompile verification is intentionally kept outside SVM metering, bound `message_data_size` far more tightly, and/or cap the number of repeated references to the same message region within one instruction) so the cost model used for block-cost limiting cannot be circumvented by referencing the same large payload many times.

### Proof of Concept
Conceptual PoC (not executed, derived from code paths cited above):
1. Craft one instruction with `program_id = secp256k1_program::id()`.
2. Set `count = 255` in the instruction data.
3. For all 255 `SecpSignatureOffsets` entries, set `message_instruction_index`/`message_data_offset` to reference the *same* large data blob (e.g., placed in another instruction's data, sized close to the maximum allowed transaction size) and set `message_data_size` to its maximum practical size.
4. Submit the transaction with a minimal number of actual required transaction signatures (fee is dominated by the flat `SIGNATURE_COST`/`SECP256K1_VERIFY_COST` constants, not by message size).
5. Each validator processing this transaction performs 255 keccak-256 hashes over the large blob plus 255 secp256k1 recoveries in `precompiles/src/secp256k1.rs::verify`, while the block-cost/CU accounting only reflects the flat `SECP256K1_VERIFY_COST * 255` and, per `core/tests/scheduler_cost_adjustment.rs::test_builtin_ix_precompiled`, the actual execution consumes 0 units from the live CU meter — demonstrating the accounted cost is disconnected from the real work performed.

Note: I could not fully trace, within the tool-call budget available, the exact call site(s) in `svm/src/transaction_processor.rs` / `runtime/src/bank.rs` that invoke `verify_if_precompile` in the current pipeline (whether gated by `move_precompile_verification_to_svm` or run earlier during sanitization), so the precise pipeline stage(s) at which this unmetered work executes should be confirmed by a follow-up review of `svm/src/transaction_processor.rs` and `runtime/src/bank.rs`.

    /// Returns signature details and the total signature cost
    fn get_signature_cost(transaction: &impl TransactionMeta) -> u64 {
        let signatures_count_detail = transaction.signature_details();

        signatures_count_detail
            .num_transaction_signatures()
            .saturating_mul(SIGNATURE_COST)
            .saturating_add(
                signatures_count_detail
                    .num_secp256k1_instruction_signatures()
                    .saturating_mul(SECP256K1_VERIFY_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_ed25519_instruction_signatures()
                    .saturating_mul(ED25519_VERIFY_STRICT_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_secp256r1_instruction_signatures()
                    .saturating_mul(SECP256R1_VERIFY_COST),
            )
    }
