### Title
Global `overall_connection_rate_limiter` token bucket is stake-blind and can be exhausted by a distributed unstaked-IP flood, starving legitimate (including staked) connections - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server` enforces a single process-wide `TokenBucket` (`overall_connection_rate_limiter`, capacity `MAX_CONNECTION_BURST` = 1000, refill `TOTAL_CONNECTIONS_PER_SECOND` = 2500/s) shared by *all* incoming QUIC connections, checked and consumed *before* stake is ever determined. An unprivileged attacker controlling many distinct IPs can keep each IP under the independent per-IP `ConnectionRateLimiter` threshold while collectively driving total connection attempts above the global bucket's refill rate, draining the shared budget and causing legitimate single-IP unstaked *and staked* clients to be rejected purely by the global limiter.

### Finding Description
In `run_server`, two layers of admission control gate new QUIC connections:
1. A global, unkeyed `TokenBucket` `overall_connection_rate_limiter` with capacity/burst `MAX_CONNECTION_BURST` (1000) and refill rate `TOTAL_CONNECTIONS_PER_SECOND` (2500.0/s): [1](#0-0) 
2. A per-IP `ConnectionRateLimiter` keyed by `IpAddr`, configured with `max_connections_per_ipaddr_per_min` and a 10x burst allowance: [2](#0-1) 

The accept loop checks the global bucket first (non-consuming `current_tokens() == 0` peek) and the per-IP limiter second, both *before* the handshake completes and before any stake/pubkey information is known: [3](#0-2) 

After the handshake, `setup_connection` registers/consumes both limiters again, still strictly before `qos.build_connection_context` / `qos.try_add_connection` (which is where stake-based prioritization, e.g. `SwQos`'s staked/unstaked connection tables and pruning, is applied): [4](#0-3) 

Because the global bucket has no per-source or per-stake weighting, and its default capacity (`MAX_CONNECTION_BURST` = 1000 tokens, 2500/s refill) is far smaller than what a botnet of, e.g., a few thousand unstaked IPs can generate while each individual IP stays below `max_connections_per_ipaddr_per_min * 10` burst allowed by `ConnectionRateLimiter`, an attacker can keep the global bucket persistently empty. `QosController`/`SwQos` staked-connection prioritization (`try_add_connection`, `prune_random`, etc.) never gets a chance to run for legitimate staked validators' connection attempts, because they are already rejected earlier at the global-bucket check with `connection_rate_limited_across_all`: [5](#0-4) 

The per-IP `ConnectionRateLimiter` is fundamentally incapable of preventing this since it only bounds *each key's* rate, not the aggregate across many keys — this is confirmed by its design/tests which only assert per-IP token exhaustion behavior, with no interaction with the global bucket: [6](#0-5) 

### Impact Explanation
This is a QoS evasion / stake-priority-bypass issue: the design intent of the streamer QoS layer (`SwQos`, `SimpleQos`) is that staked validators/forwarders get prioritized admission over unstaked peers via separate connection tables and pruning of low-stake connections. However, the global `overall_connection_rate_limiter` sits in front of that logic and treats all sources identically. A distributed unstaked flood (botnet) that never triggers per-IP limits can starve the shared admission budget, denying new connections to legitimate staked and unstaked clients alike at the TPU ingress point, before stake-aware admission control is ever consulted. This degrades transaction ingestion availability for legitimate leaders' clients — a scoped "QoS evasion" impact against the shared admission budget as posed in the question.

### Likelihood Explanation
The precondition is only an unprivileged attacker capable of opening QUIC connections from many distinct source IPs (a botnet) to a public TPU port — no stake, keys, or validator control required. The per-IP burst allowance (`max_connections_per_ipaddr_per_min * 10`, default 8*10=80 per IP) and the small fixed global budget (`MAX_CONNECTION_BURST` = 1000, refill 2500/s) mean a botnet of a few hundred to low-thousands of distinct IPs, each issuing bursts within its own allowance, easily and repeatably keeps `overall_connection_rate_limiter.current_tokens() == 0`. This requires no timing precision beyond simple distributed low-and-slow request pacing and is trivially repeatable/sustained for as long as the botnet operates.

### Recommendation
Make the global admission budget stake-aware, e.g., reserve a portion of `overall_connection_rate_limiter` tokens exclusively for staked/verified-pubkey connections (checked after handshake once stake is known, similar to how `SwQos` separates staked/unstaked tables), or apply the global limiter only to the unstaked connection path while giving staked connections a separate, protected token budget. Alternatively, scale/derive the global limit dynamically based on observed distinct-IP diversity, or move the global check to occur after per-IP-key connection admission has been decided so unstaked floods are capped by aggregate distinct-source heuristics (e.g., an IP-subnet-based aggregate limiter) rather than a flat global bucket blind to identity/stake.

### Proof of Concept
Integration test plan (extends existing pattern from `connection_rate_limiter.rs` tests and `run_server` wiring):
```rust
#[tokio::test]
async fn test_distributed_ip_flood_exhausts_global_bucket() {
    use std::net::{IpAddr, Ipv4Addr};
    // Reproduce overall_connection_rate_limiter parameters directly via TokenBucket,
    // mirroring run_server's construction:
    let overall = TokenBucket::new(1000 /* MAX_CONNECTION_BURST */, 1000, 2500.0 /* TOTAL_CONNECTIONS_PER_SECOND */);
    let per_ip = ConnectionRateLimiter::new(8 /* max_connections_per_ipaddr_per_min */, 80, 4);

    // Simulate 200 distinct attacker IPs, each issuing 6 connections (below the 80 burst
    // allowance and well below the per-minute steady rate), consuming from both limiters
    // exactly as setup_connection does.
    for i in 0..200u8 {
        let ip = IpAddr::V4(Ipv4Addr::new(10, 0, 0, i));
        for _ in 0..6 {
            assert!(per_ip.register_connection(&ip), "per-IP limiter should not block attacker");
            let _ = overall.consume_tokens(1); // mirrors overall_connection_rate_limiter.consume_tokens
        }
    }
    // 200 * 6 = 1200 > MAX_CONNECTION_BURST (1000): global bucket now exhausted
    assert_eq!(overall.current_tokens(), 0);

    // A legitimate, previously-unseen single IP now attempts a connection and is blocked
    // purely by the global bucket, despite being far under any per-IP limit.
    let legit_ip = IpAddr::V4(Ipv4Addr::new(192, 168, 1, 1));
    assert!(per_ip.is_allowed(&legit_ip), "per-IP limiter allows legitimate client");
    assert!(overall.consume_tokens(1).is_err(), "global bucket denies legitimate client despite per-IP compliance");
}
```
Expected assertion: `overall.consume_tokens(1)` fails for the legitimate single IP even though `per_ip.is_allowed(&legit_ip)` and `per_ip.register_connection` for that IP would succeed, demonstrating that `connection_rate_limited_across_all` (in `streamer/src/nonblocking/quic.rs`) triggers due to distributed multi-IP abuse rather than the legitimate client's own behavior. A full end-to-end variant would drive this through `run_server`/`setup_connection` with real QUIC `Endpoint`s from 200+ ephemeral local sockets/IPs (or a mocked `remote_address()`), asserting `stats.connection_rate_limited_across_all` increments for a final legitimate connection attempt.

impl ConnectionRateLimiter {
    /// Create a new rate limiter per IpAddr. The rate is specified as the count per minute to allow for
    /// less frequent connections. Higher limit also allows higher bursts.
    /// num_shards controls how many shards are used in the underlying dashmap,
    /// should be set >= number of contending threads.
    pub fn new(limit_per_minute: u64, max_burst: u64, num_shards: usize) -> Self {
        Self {
            limiter: KeyedRateLimiter::new(
                CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD,
                TokenBucket::new(limit_per_minute, max_burst, limit_per_minute as f64 / 60.0),
                num_shards,
            ),
        }
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
