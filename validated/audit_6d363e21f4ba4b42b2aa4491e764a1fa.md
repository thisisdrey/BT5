### Title
Missing `supportUnfreezeDelay` feature-toggle check in `WithdrawExpireUnfreezeProcessor` (TVM path) - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java])

### Summary
The reported analog for the ubiquity bug ("a follow-up 'collect'/claim action skips a feature-enable check that the sibling initiating/entry action performs") maps to java-tron's frozen-balance-V2 withdrawal flow. The externally-callable transaction actuator `WithdrawExpireUnfreezeActuator` gates itself on the committee-controlled `supportUnfreezeDelay()` flag, but the smart-contract-reachable TVM native processor that performs the identical operation, `WithdrawExpireUnfreezeProcessor`, does not perform this check.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` (broadcast transaction path) explicitly requires the feature to be enabled by governance before allowing a withdrawal of expired unfreeze balances: [1](#0-0) 

The equivalent logic reachable from a smart contract via the TVM `withdrawExpireUnfreeze` opcode, implemented in `WithdrawExpireUnfreezeProcessor.validate()`, performs address/account/overflow checks but never calls `dynamicStore.supportUnfreezeDelay()`: [2](#0-1) 

This processor is invoked directly from contract bytecode through `Program.withdrawExpireUnfreeze()`: [3](#0-2) 

The sibling `CancelAllUnfreezeV2Processor` (also a TVM native-contract path) similarly omits any `supportUnfreezeDelay()`/`supportDR()` gate: [4](#0-3) 

By contrast, the actuator-level counterpart for the related delegate/undelegate flow, `UnDelegateResourceActuator`, checks both `supportDR()` and `supportUnfreezeDelay()`: [5](#0-4) 
while its TVM counterpart `UnDelegateResourceProcessor` only checks `supportDR()`, omitting `supportUnfreezeDelay()`: [6](#0-5) 

This is structurally identical to the reported bug class: a governance/enable-flag check exists on one entry point into a shared piece of state (frozen/unfrozen balances) but is missing on an alternate, contract-reachable entry point that manipulates the exact same state.

### Impact Explanation
`supportUnfreezeDelay()` is the committee-controlled switch gating the entire "unfreeze V2" delayed-withdrawal resource model (`UNFREEZE_DELAY_DAYS` chain parameter). It is intended as a hard requirement before any of freeze-V2/unfreeze-V2/delegate/withdraw-expire-unfreeze/cancel-unfreeze operations are permitted, presumably to allow the network to stage the rollout of the mechanism and to enforce that clients/toolchains handle the semantics correctly before the feature is live. Because `WithdrawExpireUnfreezeProcessor` and `CancelAllUnfreezeV2Processor` do not check it, a smart contract calling the TVM opcode bypasses that gate entirely and unconditionally allows withdrawal/cancellation logic to run based purely on the presence of `unfrozenV2` records, independent of the flag's state — inconsistent enforcement of a chain-level feature guard between the transaction-actuator surface and the TVM/precompile surface.

I was not able to fully verify from the available index whether `supportUnfreezeDelay()` can ever transition from enabled to disabled after activation (i.e., whether this is a strictly one-way hard-fork flag or a toggle-able committee parameter), which materially affects whether this gap is exploitable in practice today versus only being a latent inconsistency that matters if/when the parameter is ever toggled or during a staged rollout window. This should be confirmed by inspecting `ProposalUtil.java` / `ChainParameterEnum.java` and the parameter's set/get semantics in `DynamicPropertiesStore.java` before treating this as immediately exploitable.

### Likelihood Explanation
Exploitability requires only deploying/calling a contract that invokes the corresponding TVM builtin (`withdrawExpireUnfreeze()` / `cancelAllUnfreezeV2` opcode path) — no special privilege is needed, consistent with the "actuator/opcode/precompile reachable by any transaction" scope for these analogs. The actual security relevance is bounded by whether the flag can be in a disabled state while unfrozen-V2 balances already exist in accounts (a scenario tied to chain configuration/rollout timing that I could not fully confirm).

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` (and, for the delegate/undelegate pair, `supportDR()`) checks to the TVM-reachable processors so they mirror the actuator-level validation:
- `WithdrawExpireUnfreezeProcessor.validate()`
- `CancelAllUnfreezeV2Processor.validate()`
- `UnDelegateResourceProcessor.validate()` (add `supportUnfreezeDelay()` alongside the existing `supportDR()` check)

### Proof of Concept
1. Deploy a contract that calls the TVM opcode corresponding to `withdrawExpireUnfreeze` (exposed via `Program.withdrawExpireUnfreeze()` at [7](#0-6) ) for an account holding `unfrozenV2` entries with `unfreezeExpireTime <= now`.
2. If the network is in a state where `supportUnfreezeDelay()` is false (e.g. during a staged/partial rollout or if the parameter is later found to be revertible), a direct `WithdrawExpireUnfreezeContract` transaction via `WithdrawExpireUnfreezeActuator` would be rejected with "Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee" ( [1](#0-0) ).
3. The same withdrawal performed through the TVM opcode via `WithdrawExpireUnfreezeProcessor.validate()`/`execute()` succeeds unconditionally, since no equivalent check exists ( [8](#0-7) ), demonstrating the enforcement gap between the two entry points into the same state.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }

    if (accountCapsule.hasInvalidDelegatedV2()) {
      MUtil.checkCPUTimeForInvalidDelegatedV2Balance();
    }
  }

  private long getTotalWithdrawUnfreeze(List<Protocol.Account.UnFreezeV2> unfrozenV2List, long now) {
    return getTotalWithdrawList(unfrozenV2List, now).stream()
        .mapToLong(Protocol.Account.UnFreezeV2::getUnfreezeAmount).sum();
  }

  private List<Protocol.Account.UnFreezeV2> getTotalWithdrawList(List<Protocol.Account.UnFreezeV2> unfrozenV2List, long now) {
    return unfrozenV2List.stream().filter(unfrozenV2 -> unfrozenV2.getUnfreezeExpireTime() <= now)
        .collect(Collectors.toList());
  }

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
