### Title
Downloaded `Attachment` content is inserted via `insert_instantiated_attachment` without any check against `AtlasConfig.attachments_max_size` - ([File: stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/db.rs])

### Summary
The Atlas attachment-download path (`AttachmentsDownloader::run` / `extend_with_attachments` / `AtlasDB::insert_instantiated_attachment`) never calls the size-check logic (`AtlasDB::should_keep_attachment`) that compares `attachment.content.len()` against `AtlasConfig.attachments_max_size`. Any `Attachment` decoded from a peer's `GET /v2/attachments/{hash}` response is stored directly, regardless of size, breaking the invariant `content.len() <= attachments_max_size`.

### Finding Description
`AttachmentsBatchStateContext::extend_with_attachments` decodes each peer HTTP response via `response.decode_atlas_get_attachment()` and, on success, inserts the resulting `Attachment` straight into `self.attachments: HashSet<Attachment>` with no size check whatsoever: [1](#0-0) 

Later, `AttachmentsDownloader::run` drains that set and persists every attachment unconditionally: [2](#0-1) 

`AtlasDB::insert_instantiated_attachment` itself performs a raw `INSERT OR REPLACE` with no size validation at all: [3](#0-2) 

The only place in `AtlasDB` that enforces `attachments_max_size` is `should_keep_attachment`, which is a separate helper not invoked anywhere in this download/insert path: [4](#0-3) 

Root cause: the size-bound check exists in the codebase (`should_keep_attachment`) but is only wired into a different ingestion path (locally-posted/broadcast attachments), not into the outbound-peer-download path that calls `decode_atlas_get_attachment` → `insert_instantiated_attachment`. As a result, an attacker who is selected as one of the node's outbound Atlas peers (`network.get_outbound_sync_peers()`) can respond to the node's own `GET /v2/attachments/{hash}` request with an oversized hex-encoded body; whatever `Attachment` results from decoding gets written to the `attachments` SQLite table unconditionally.

I was not able to fully re-verify, within the available tool budget, the exact `Deserialize`/`hex_bytes` code in `stackslib/src/net/atlas/mod.rs` (the file returned matches in grep but its content wasn't re-read directly this session), so the claim about the pre-allocation cost of `hex_bytes` prior to any length cap could not be independently confirmed line-by-line. However, the downstream gap — no `attachments_max_size` comparison anywhere between decode and `insert_instantiated_attachment` — is confirmed directly from `download.rs` and `db.rs`.

### Impact Explanation
A malicious (or compromised) outbound Atlas peer can cause the victim node to store attachment blobs of arbitrary size in its local `AtlasDB`, silently violating the configured `attachments_max_size` bound. This is a state-integrity violation (oversized/uncapped content persisted despite an explicit operator-configured limit) and, depending on how large the attacker makes the payload, can also degrade node performance/memory via repeated oversized downloads, since nothing in this path re-checks or rejects on size before writing to the SQLite `attachments` table.

### Likelihood Explanation
Preconditions: the attacker must be one of the node's `outbound_sync_peers` for Atlas (i.e., a peer the victim has decided to sync attachments from) and must serve responses to the victim's own outbound `GET /v2/attachments/{hash}` requests — no privileged role, secret, or StackerDB slot ownership is required, just running a normal peer that the victim's node talks to. This is a plausible and repeatable attack path: every attachment fetch cycle offers a fresh opportunity, and the attacker fully controls the response body content and its (hex-encoded) size.

### Recommendation
Call `AtlasDB::should_keep_attachment` (or an equivalent size/content-hash check) immediately after `decode_atlas_get_attachment()` succeeds in `extend_with_attachments`, and again before `insert_instantiated_attachment` is invoked in `AttachmentsDownloader::run`, rejecting/dropping any attachment whose `content.len()` exceeds `AtlasConfig.attachments_max_size` (and treating the source peer as unreliable/faulty in that case).

### Proof of Concept
In `stackslib/src/net/atlas/tests.rs` (or a new test module):
1. Construct an `AtlasDB::connect_memory` with a small `attachments_max_size` (e.g., 10 bytes) in `AtlasConfig`.
2. Build an `Attachment { content: vec![0u8; 1_000_000] }` (simulating what `decode_atlas_get_attachment` would produce from an oversized hex body).
3. Call `atlas_db.insert_instantiated_attachment(&oversized_attachment)` directly (mirroring the call in `download.rs::run`, line 161).
4. Assert that the call succeeds and that `atlas_db.find_attachment(&oversized_attachment.hash())` returns the full 1,000,000-byte content — demonstrating that no size check rejects it, in contrast to `should_keep_attachment`, which would return `false` for the same input if it were called.

```rust
    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
```

```rust
    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
```
