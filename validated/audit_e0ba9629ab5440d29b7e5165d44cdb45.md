## Title
Negative Pyth prices cause an uncatchable runtime panic in oracle resolution instead of a handled error, bricking borrow/repay/liquidate for the affected asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`normalize-pyth` converts the signed `price` int returned by the Pyth oracle to `uint` using Clarity's `to-uint` without first checking its sign. In Clarity, `to-uint` on a negative `int` is a **runtime abort** of the whole transaction — it is not a `(response ... err)` value and therefore cannot be intercepted by `try!`/`unwrap!`/`asserts!`. This is the exact analog of the GMX finding: `SafeCast.toUint256()` reverting with a plain, uncategorized `revert(string)` on a negative Chainlink price, which bypassed `OracleUtils.isEmptyPriceError()` handling and caused unrelated in-flight orders to be forcibly canceled instead of gracefully failing. [1](#0-0) 

### Finding Description
`resolve-pyth` fetches the raw Pyth entry and passes its signed `price` straight into `normalize-pyth`, which calls `to-uint`: [2](#0-1) 

The only positivity check in the oracle pipeline, `oracle-price-legal`, runs *after* this conversion has already happened, inside `price-resolve`: [3](#0-2) 

If Pyth ever publishes (or the price genuinely settles at) a negative value for a feed — Pyth's protocol supports signed prices for exactly this reason, and the sponsor in the referenced GMX report confirmed real assets can go negative — `to-uint` in `normalize-pyth` aborts the entire Clarity transaction with an uncatchable runtime error. This happens *before* `oracle-price-legal`, `try!`, or any `asserts!` gets a chance to run, so none of the protocol's designed error paths (`ERR-ORACLE-PYTH`, `ERR-ORACLE-INVARIANT`, etc.) are ever reached; the call simply reverts with no recoverable state and no distinguishing error code, exactly like the unclassified `revert(string)` from `SafeCast.toUint256()` in the GMX report.

Every price-dependent entry point in the market goes through `price-resolve`/`resolve-pyth` for the affected asset — `borrow`, `repay`, `collateral-add`/`withdraw`, and critically `liquidate` (which calls `get-asset-value`/`get-notional-evaluation` → `price-resolve` for both collateral and debt assets): [4](#0-3) [5](#0-4) 

While the current-implementation `oracle-price-legal` check was clearly *intended* to reject non-positive prices, it can never fire for negative Pyth prices because the panic occurs upstream in `normalize-pyth`.

### Impact Explanation
While a negative price for the affected feed persists (until the next healthy Pyth update overwrites the stored entry), every market operation that needs to price that asset — including `liquidate` — unconditionally reverts with a hard runtime abort. Liquidators cannot use `try!`/error branches to work around it because it is not a typed application error; the transaction simply cannot complete. This blocks liquidation of under-collateralized positions in the affected asset for the duration of the bad price, which is a **temporary freezing of funds** (the same impact class the referenced report was ultimately validated for — canceled/blocked liquidation-adjacent operations causing losses/freezes). If the negative reading persists through a period where positions should be liquidated, bad debt can accrue and be socialized, compounding the loss.

### Likelihood Explanation
Negative prices are rare for crypto spot assets but are not excluded by the Pyth protocol or by this codebase — the code contains a bespoke positivity check (`oracle-price-legal`) explicitly acknowledging the need to reject non-positive prices, showing the developers anticipated this case but placed the check after the point where the panic already occurs. No malicious actor is even required; a single non-positive tick published to the on-chain Pyth storage for any listed feed (STX, BTC, USDC, etc., all routed through `resolve-pyth`/`normalize-pyth`) is sufficient to trigger the DoS for that asset across `borrow`, `repay`, `collateral-add`, `withdraw`, and `liquidate`.

### Recommendation
Validate the sign of the raw Pyth `price` (and `ema-price` if used) *before* calling `to-uint`, and return a typed, catchable error (e.g. `ERR-ORACLE-NEGATIVE-PRICE`) via `asserts!`/`unwrap!` rather than allowing `to-uint` to abort the transaction. This preserves the existing `try!` chain so all callers of `price-resolve`, including `liquidate`, fail gracefully with an application error, and any special-casing consumers (e.g. distinguishing "pausable/retryable" oracle errors) can react appropriately instead of hitting an unrecoverable runtime panic.

### Proof of Concept
1. Pyth publishes a legitimate signed update for, say, the BTC/USD feed with `price = -1` (or the update batch supplied via `write-feeds` in `borrow`/`liquidate` momentarily carries a negative tick, e.g. during extreme market dislocation or an upstream Pyth publisher issue for a supported symbol).
2. `pyth-storage-v4` stores this entry as-is (storage layer does not validate sign).
3. Any subsequent call into the market that needs a price for that asset — `borrow`, `repay`, `withdraw`, `collateral-add`, or `liquidate` — invokes `resolve-pyth` → `normalize-pyth` → `to-uint` on the negative `price`.
4. The Clarity VM aborts the transaction with a runtime error, not a typed `(err ...)` response; `try!` cannot intercept it.
5. As long as the stored value remains negative, `liquidate` cannot execute for that asset, blocking liquidation of unhealthy positions denominated in/collateralized by it, and freezing settlement of those positions until a corrected price is published. [6](#0-5)

;; -- Oracle: price resolution -----------------------------------------------

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
