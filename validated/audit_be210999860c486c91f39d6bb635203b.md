### Title
Out-of-bounds heap read in TVM precompile ABI-array decoders (`extractBytesArray`/`extractSigArray`) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign`/`ValidateMultiSign` precompiled contracts (addresses `0x9`/`0xa`, reachable from any TVM contract call) decode attacker-supplied calldata into `DataWord[]` and then call helper methods `extractBytesArray`, `extractBytes32Array` and `extractSigArray` to pull out variable-length sub-arrays whose lengths and offsets are taken directly from the calldata, without validating them against the actual size of the `words`/`data` arrays.

### Finding Description
`extractBytes32Array` and `extractBytesArray`/`extractSigArray` read a length field straight from attacker-controlled input and then index into the `words` array (and the raw `data` byte array) using offsets computed from further attacker-controlled words: [1](#0-0) 

- `extractBytes32Array`: `len = words[offset].intValueSafe()` can be any value up to `Integer.MAX_VALUE`; the subsequent loop reads `words[offset + i + 1]` with no bound check against `words.length`.
- `extractBytesArray`/`extractSigArray`: `bytesOffset` and `bytesLen` are derived from further attacker-controlled `DataWord`s and used to compute a byte offset into `data` (`(bytesOffset + offset + 2) * WORD_SIZE`) that is passed to `extractBytes`, which does `Arrays.copyOfRange(data, offset, offset + len)`. `Arrays.copyOfRange` throws `ArrayIndexOutOfBoundsException` (not silently pads) when `from` is negative or beyond `data.length`, and `NegativeArraySizeException` when `len` is negative, so a crafted `bytesOffset`/`bytesLen` combination produces an unhandled exception rather than a controlled failure.

This mirrors the root cause class of CVE-2021-3605 (OpenEXR `rleUncompress`): a length/offset value taken from untrusted input is used to index into a buffer without validating it against the buffer's actual bounds before the read.

### Impact Explanation
An attacker who deploys or calls a contract that invokes the `BatchValidateSign` (`0x...9`) or `ValidateMultiSign` (`0x...a`) precompile with crafted calldata can trigger `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or an `OutOfMemoryError` (via `new byte[len][]` with an attacker-chosen huge `len`) deep inside TVM execution. Because this executes during block application by every full node processing the same transaction, an unhandled runtime exception or resource exhaustion in this path can crash the node process or halt transaction processing across the network — a concrete availability impact matching the CVE's "greatest risk ... to application availability."

### Likelihood Explanation
The precompile is reachable by any account able to broadcast a `TriggerSmartContract` transaction that calls a contract invoking address `0x9` or `0xa` (no special privilege required — any unprivileged contract caller can construct the calldata). Whether the surrounding VM/actuator layer already catches all `RuntimeException`/`Error` types thrown from precompile execution (turning this into a caught "contract execution failed" outcome rather than a node crash) could not be fully confirmed in this pass — this is the key open uncertainty for judging exploitability severity.

### Recommendation
Add explicit bounds validation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before indexing: verify `len >= 0`, `offset + len + 1 <= words.length`, and that computed `bytesOffset`/`bytesLen` keep the resulting byte range within `[0, data.length]` before calling `extractBytes`/`Arrays.copyOfRange`. Reject the call (revert) instead of throwing an unchecked exception when the encoding is malformed.

### Proof of Concept
Not independently verified end-to-end (would require constructing full `BatchValidateSign`/`ValidateMultiSign` calldata and confirming whether an enclosing try/catch in `Program`/`OperationRegistry` intercepts the resulting exception before it can crash the node). Conceptually: deploy a contract that `staticcall`s address `0x...a` with a calldata word at the "array length" position set to a very large value (e.g., `0xFFFFFFFF`) or with an inner offset word crafted so `(bytesOffset + offset + 2) * WORD_SIZE` exceeds `data.length`, then invoke it via a normal `TriggerSmartContract`.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
