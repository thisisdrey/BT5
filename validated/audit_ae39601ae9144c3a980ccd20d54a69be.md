### Title
Stale PostponedReceipts survive account deletion and execute against a differently-owned recreated account - ([File: core/store/src/utils/mod.rs])

### Finding Description
`remove_account` in [1](#0-0)  removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys and contract data for the account, but it never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by `receiver_id == account_id`. These postponed-receipt bookkeeping keys are only ever removed when the matching `DataReceipt` finally arrives, in `process_receipt`'s `Data` branch [2](#0-1) , or when the receipt is first created and immediately resolvable in `process_action_receipt` [3](#0-2) .

Any unprivileged account owner can generate a self-addressed `ActionReceipt` with an unmet `input_data_id` (e.g. via `promise_then`/`promise_batch_action_add_key` targeting `current_account_id()`), which gets persisted as a postponed receipt keyed by `(receiver_id=self, receipt_id)` with a `PostponedReceiptId` link keyed by `(receiver_id=self, data_id)`. The owner can then delete their own account with `DeleteAccountAction`, which calls `remove_account` [4](#0-3)  — the account, keys and code disappear, but the postponed `AddKey` receipt and its `PendingDataCount`/`PostponedReceiptId` entries remain in the trie.

A later, unrelated party can then re-register the now-available account name via `CreateAccountAction` (allowed because `check_account_existence` only checks `account.is_some()` [5](#0-4) ). Whenever the original `DataReceipt` that satisfies the stale `data_id` eventually arrives (which the original attacker fully controls the timing/content of, since it derives from their own promise chain), `process_receipt`'s `Data` branch looks up `PostponedReceiptId`/`PendingDataCount` purely by `(receiver_id, data_id)` — with no check that the account is still owned by the same party — decrements the count, and once it hits zero, fetches and executes the stale `AddKey` postponed receipt via `apply_action_receipt` [6](#0-5) . Critically, `apply_action_receipt` loads the account fresh at execution time (`get_account(state_update, account_id)` [7](#0-6) ) rather than validating anything about the account's identity/history, so `check_account_existence`/`action_add_key` operate against whatever account currently occupies that name — the new owner's account — and happily add the original (stale) owner's public key to it.

Because two different prior owners can each leave such a stale postponed `AddKey` receipt before deleting, and both receipts are independently keyed only by `(receiver_id, receipt_id)`/`(receiver_id, data_id)` with no session/generation tag tying them to a specific "incarnation" of the account, both stale receipts can independently resolve and fire against the same recreated account, regardless of order.

### Impact Explanation
This is authorization escalation across accounts: an account name's *new*, unrelated owner can end up with attacker-controlled full-access keys silently added to their account by a party who no longer owns or ever should have had authority over it. This matches the "authorization escalation across accounts or promises" bounty category, since the escalation lets a former (or racing) owner regain full signing control over the recreated account's balance and any assets/roles associated with it.

### Likelihood Explanation
Preconditions are attacker-affordable and fully within an ordinary user's capability: sign a `FunctionCall`/promise batch that creates a self-targeted `AddKey` receipt with an unmet `input_data_id`, then submit `DeleteAccount`. Both are ordinary signed-transaction/receipt operations requiring no special privileges, validator access, or leaked keys. The only external dependency is that a third party re-registers the same account name and that the attacker later triggers/allows the deferred `DataReceipt` to resolve — both are plausible on a public network where account names are freely re-registrable after deletion, and the attacker fully controls when/whether their own promise chain resolves.

### Recommendation
When deleting an account in `remove_account` (or `action_delete_account`), also scan and remove any `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries whose `receiver_id` equals the account being deleted (mirroring how access keys/contract data are iterated and purged today), so no stale receipt can outlive the account's deletion and later fire against a differently-owned recreation of the same name.

### Proof of Concept
Integration/runtime test-loop plan:
1. Owner1 creates account `victim.near`, issues a promise batch that creates a postponed `AddKey(owner1_pubkey)` self-receipt with an unmet `input_data_id` (e.g., call another contract with a slow/never-resolved-yet callback), then submits `DeleteAccount(beneficiary=owner1_refund)` for `victim.near` before the data receipt resolves. Assert via state that `TrieKey::PostponedReceipt{receiver_id: victim.near, ..}` still exists after deletion.
2. Owner2 creates `victim.near` fresh with `CreateAccountAction`, repeats the same pattern: postpone an `AddKey(owner2b_pubkey)` self-receipt with an unmet dependency, then `DeleteAccount`. Assert the second stale postponed receipt also persists.
3. Owner3 creates `victim.near` again with `CreateAccountAction` (its own key).
4. Deliver the two outstanding `DataReceipt`s (satisfying owner1's and owner2's original `input_data_ids`) in any order.
5. Assert that `victim.near`'s final access-key set includes `owner1_pubkey` and `owner2b_pubkey` in addition to owner3's key — demonstrating that stale, unauthorized full-access keys from two prior, unrelated owners were silently installed on owner3's account.
