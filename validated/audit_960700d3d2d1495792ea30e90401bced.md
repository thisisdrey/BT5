### Title
DeleteAccount storage-usage gate ignores TrieKey::PostponedReceipt/PromiseYieldReceipt bytes, permanently orphaning megabyte-scale receipt data in state - (File: runtime/runtime/src/actions.rs, core/store/src/utils/mod.rs)

### Summary
`action_delete_account` gates account deletion on `Account::storage_usage()` (minus contract-code bytes), which never includes bytes stored under `TrieKey::PostponedReceipt` or `TrieKey::PromiseYieldReceipt`. `remove_account` only deletes `TrieKey::Account`, `ContractCode`, access/gas keys, and `ContractData`, leaving postponed/promise-yield receipts untouched. This lets an attacker keep an account's billed `storage_usage` under `MAX_ACCOUNT_DELETION_STORAGE_USAGE` while it holds large postponed receipts, delete the account, and permanently orphan that state with no owner and no billing.

### Finding Description
`action_delete_account` computes `account_storage_usage` from `account_ref.storage_usage()` (adjusted only for contract-code length) and rejects deletion only if that value exceeds `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`: [1](#0-0) 

If the check passes, `remove_account` is invoked, which removes `TrieKey::Account`, `TrieKey::ContractCode`, all access keys/gas-key nonces (via `get_raw_prefix_for_access_keys`), and all `TrieKey::ContractData` entries — but never touches `TrieKey::PostponedReceipt` or `TrieKey::PromiseYieldReceipt`: [2](#0-1) 

The writer/getter helpers for postponed and promise-yield receipts exist as separate, independently-keyed entries (`set_postponed_receipt`, `remove_postponed_receipt`, `set_promise_yield_receipt`, `remove_promise_yield_receipt`) and are stored under keys keyed by `receiver_id`/`receipt_id` or `receiver_id`/`data_id`, distinct from the account's `storage_usage`-tracked namespaces: [3](#0-2) [4](#0-3) 

Per `docs/RuntimeSpec/Receipts.md`, when an incoming `ActionReceipt`'s `input_data_ids` are not all satisfied, runtime stores it as a Postponed ActionReceipt in the trie and waits for the missing `DataReceipt`s to arrive before applying and removing it: [5](#0-4) 

An unprivileged attacker can deploy a contract to their own account that issues several `FunctionCall` receipts to itself with large arguments and unresolved `input_data_ids` (e.g., depending on a promise that is never resolved, or resolved only after the account is deleted), causing these receipts to be persisted as `PostponedReceipt` entries whose payload size is not reflected in `Account::storage_usage`. Because `storage_usage` only tracks `Account`/`AccessKey`/`ContractData`/contract bytes (not postponed/promise-yield receipts), the attacker's account can maintain a small, cap-compliant `storage_usage` while carrying megabyte-scale postponed receipt blobs. The attacker then submits a `DeleteAccount` action; the size check passes (small `storage_usage`), `remove_account` deletes the account and its billed sub-state, but the `PostponedReceipt` trie entries are never removed, orphaning the data permanently with no owner account and no storage fee ever collected for it.

### Impact Explanation
This matches an unbounded, permanently-orphaned state growth defect: bytes are held in the trie indefinitely (there is no owner account to charge storage rent to and no cleanup path is triggered by `DeleteAccount`), inflating global state size for all validators without possibility of reclamation. This is a genuine metering/cleanup asymmetry reachable purely through account-level actions (deploy contract, create receipts with unmet data dependencies, delete account) available to any funded account — no validator, node-operator, or privileged access required.

### Likelihood Explanation
The attack requires only: funding a NEAR account, deploying a wasm contract, and issuing self-calls that create receipts with `input_data_ids` that never resolve (or resolve too slowly), followed by `DeleteAccount`. This is fully repeatable and cheap relative to the amount of orphaned state produced (attacker pays gas for a few cross-contract calls but never pays ongoing storage staking for the postponed payload, and reclaims their remaining balance via the beneficiary refund on deletion). The size cap (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`) that is meant to bound deletion cost is ineffective here because it measures the wrong quantity.

### Recommendation
Before allowing `DeleteAccount` to proceed, `action_delete_account` should also check for (and either block deletion on, or account for and clean up) any `TrieKey::PostponedReceipt` / `TrieKey::PromiseYieldReceipt` / associated pending-data-count and pending-data-receipt-index entries scoped to `account_id`. At minimum, extend `remove_account` to iterate and remove postponed/promise-yield receipts (and their pending-data indices) for the account, and include their byte size in the `account_storage_usage` computation used by the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` gate so large postponed payloads correctly block deletion (or get properly billed/cleaned up) rather than being silently orphaned.

### Proof of Concept
Integration test plan (runtime-loop/apply test):
1. Deploy a contract to account `alice` that, on a specific method, issues multiple `FunctionCall` action receipts targeted at `alice` itself, each with a large (e.g., several hundred KB to low-MB aggregate) argument payload, and with `input_data_ids` referencing a `data_id` that is never supplied (or supplied only after account deletion in a later block).
2. Execute this call so the receipts are persisted via `set_postponed_receipt` under `TrieKey::PostponedReceipt { receiver_id: "alice", receipt_id }`.
3. Assert `get_account(trie, "alice").storage_usage()` is well below `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`.
4. Submit a `DeleteAccount` transaction from `alice` (with a valid access key) targeting a beneficiary account.
5. Assert the transaction succeeds (`ActionErrorKind::DeleteAccountWithLargeState` is NOT raised) and `get_account(trie, "alice")` returns `None`.
6. Directly query the trie for `TrieKey::PostponedReceipt { receiver_id: "alice", receipt_id }` (via `get_postponed_receipt` or raw trie read) post-deletion and assert the large payload is still present, proving orphaned unbilled state with no owning account and no reachable cleanup path.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

## Processing ActionReceipt

For each incoming [`ActionReceipt`](#actionreceipt) runtime checks whether we have all the [`DataReceipt`s](#datareceipt) (defined as [`ActionsReceipt.input_data_ids`](#input_data_ids)) required for execution. If all the required [`DataReceipt`s](#datareceipt) are already in the [storage](#received-datareceipt), runtime can apply this `ActionReceipt` immediately. Otherwise we save this receipt as a [Postponed ActionReceipt](#postponed-actionreceipt). Also we save [Pending DataReceipts Count](#pending-datareceipt-count) and [a link from pending `DataReceipt` to the `Postponed ActionReceipt`](#pending-datareceipt-for-postponed-actionreceipt). Now runtime will wait for all the missing `DataReceipt`s to apply the `Postponed ActionReceipt`.

#### Postponed ActionReceipt

A Receipt which runtime stores until all the designated [`DataReceipt`s](#datareceipt) arrive.

- **`key`** = `account_id`,`receipt_id`
- **`value`** = `[u8]`

_Where `account_id` is [`Receipt.receiver_id`](#receiver_id), `receipt_id` is [`Receipt.receipt_id`](#receipt_id) and value is a serialized [`Receipt`](#receipt-1) (which type must be [ActionReceipt](#actionreceipt))._
