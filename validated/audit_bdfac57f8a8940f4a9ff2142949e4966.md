### Title
Unbounded Concurrency for Git Read/Fetch RPCs by Default Enables Resource-Exhaustion DoS - ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
Gitaly's only defense against a flood of concurrent Git operations (e.g., `PostUploadPack`/`PostUploadPackWithSidechannel`, `SSHUploadPack`, `UploadArchive`) is the opt-in `[[concurrency]]` configuration block. Unless an operator explicitly configures per-RPC concurrency limits, `UnaryInterceptor`/`StreamInterceptor` fall straight through to the handler with no bound on the number of simultaneous requests any single client (or set of clients) can issue for the same repository, mirroring the class of DoS described in the referenced report where large numbers of unthrottled read requests overwhelmed a node.

### Finding Description
The concurrency-limiting middleware only enforces a limit if a `limiter.Limiter` has been registered for the RPC's `FullMethod`: [1](#0-0) 

The limiter map (`methodLimiters`/`methodLimitersUnauthenticated`) is populated exclusively from `cfg.Concurrency`, which is empty unless an administrator adds `[[concurrency]]` stanzas to Gitaly's TOML config: [2](#0-1) 

`doc/backpressure.md` confirms this is opt-in per-RPC configuration and explicitly states that rate limiting (a complementary mechanism) "has been removed from Gitaly": [3](#0-2) 

The only RPC that receives an automatic default limiter, regardless of configuration, is `ReplicateRepository`: [4](#0-3) 

Consequently, the high-value, unprivileged-reachable Git data-access RPCs referenced in `doc/backpressure.md`'s own example (`PostUploadPackWithSidechannel`, i.e. Git fetch/clone) — as well as `SSHUploadPack`, `UploadArchive`, `GetBlobs`, etc. — have **no built-in concurrency ceiling** on out-of-the-box Gitaly deployments. An ordinary user entitled to fetch/clone a repository can open an unbounded number of parallel fetch/upload-pack RPCs against the same repository (or across many repositories), each of which spawns a `git-upload-pack`/`git-pack-objects` subprocess and consumes CPU, memory, and file descriptors on the Gitaly node, with nothing in the gRPC layer to queue, throttle, or reject excess concurrent load by default.

### Impact Explanation
This mirrors the reported bug class directly: a bounded number of legitimate, "public" read/fetch requests replayed at high concurrency can exhaust process/goroutine/subprocess resources on a Gitaly node, degrading or denying service for all other repositories and RPCs served by that node — the same "unreachable network as long as the attack is going on" effect described in the source report, translated to Gitaly's default (unconfigured) resource-limiting posture.

### Likelihood Explanation
Likelihood is high for any Gitaly deployment relying on Gitaly's shipped defaults, since `[[concurrency]]` is not automatically populated for common read RPCs and must be manually curated by each operator per RPC name. Any authenticated caller (via `gitlab-shell`/Workhorse forwarding a legitimate user's fetch/clone) can trivially open hundreds of parallel connections, exactly as demonstrated in the referenced attack.

### Recommendation
- Ship sane, non-zero default `max_per_repo`/`max_queue_size`/`max_queue_wait` concurrency limits for the well-known high-cost read RPCs (`PostUploadPack`, `PostUploadPackWithSidechannel`, `SSHUploadPack`, `SSHUploadArchive`, `UploadArchive`, `GetBlobs`, etc.) instead of requiring explicit opt-in configuration.
- Consider adding a global fallback concurrency/queue limiter (analogous to the `ReplicateRepository` special-case in `WithConcurrencyLimiters`) that applies to any RPC lacking an explicit `[[concurrency]]` entry, keyed by lock key and/or client identity.
- Document and alert when Gitaly is running with zero effective concurrency limits configured for Git data-access RPCs.

### Proof of Concept
1. Deploy Gitaly with a default/empty `[[concurrency]]` configuration (as shipped).
2. As an ordinary authenticated user with fetch access to a repository, issue hundreds of concurrent `PostUploadPackWithSidechannel` (git fetch/clone) RPCs against that repository from one or more clients.
3. Observe that `UnaryInterceptor`/`StreamInterceptor` pass every request straight to the handler (`lockKey`/`limiter` resolve, but `methodLimiters[FullMethod]` is `nil`), spawning unbounded concurrent `git-upload-pack` subprocesses until the node's CPU/memory/file-descriptor limits are exhausted, denying service to other repositories/RPCs on the same node.

func (c *LimiterMiddleware) UnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
		lockKey := c.getLockKey(ctx)
		if lockKey == "" {
			return handler(ctx, req)
		}

		// Check if request is authenticated
		limiter := c.methodLimiters[info.FullMethod]
		unauthLimiter, ok := c.methodLimitersUnauthenticated[info.FullMethod]
		if !auth.IsAuthenticated(ctx) && ok {
			limiter = unauthLimiter
		}

		if limiter == nil {
			// No concurrency limiting
			return handler(ctx, req)
		}

		return limiter.Limit(ctx, lockKey, func() (interface{}, error) {
			return handler(ctx, req)
		})
	}

// WithConcurrencyLimiters sets up middleware to limit the concurrency of
// requests based on RPC and repository
func WithConcurrencyLimiters(cfg config.Cfg) (map[string]*limiter.AdaptiveLimit, map[string]*limiter.AdaptiveLimit, SetupFunc) {
	perRPCLimits := map[string]*limiter.AdaptiveLimit{}
	perRPCLimitsUnauthenticated := map[string]*limiter.AdaptiveLimit{}

	for _, concurrency := range cfg.Concurrency {
		// Create authenticated limiter
		limitName := fmt.Sprintf("perRPC%s", concurrency.RPC)
		if concurrency.Adaptive {
			perRPCLimits[concurrency.RPC] = limiter.NewAdaptiveLimit(limitName, limiter.AdaptiveSetting{
				Initial:       concurrency.InitialLimit,
				Max:           concurrency.MaxLimit,
				Min:           concurrency.MinLimit,
				BackoffFactor: limiter.DefaultBackoffFactor,
			})
		} else {
			perRPCLimits[concurrency.RPC] = limiter.NewAdaptiveLimit(limitName, limiter.AdaptiveSetting{
				Initial: concurrency.Concurrency(),
			})
		}

		// Create unauthenticated limiter if configured
		unauthLimits := concurrency.Unauthenticated
		if unauthLimits.IsSet() {
			limitNameUnauth := fmt.Sprintf("perRPC%s-unauthenticated", concurrency.RPC)
			if unauthLimits.Adaptive {
				perRPCLimitsUnauthenticated[concurrency.RPC] = limiter.NewAdaptiveLimit(limitNameUnauth, limiter.AdaptiveSetting{
					Initial:       unauthLimits.InitialLimit,
					Max:           unauthLimits.MaxLimit,
					Min:           unauthLimits.MinLimit,
					BackoffFactor: limiter.DefaultBackoffFactor,
				})
			} else if unauthLimits.Concurrency() > 0 {
				perRPCLimitsUnauthenticated[concurrency.RPC] = limiter.NewAdaptiveLimit(limitNameUnauth, limiter.AdaptiveSetting{
					Initial: unauthLimits.Concurrency(),
				})
			}
		}
	}

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
