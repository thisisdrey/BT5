### Title
Unauthenticated `RelayFromAddr` accepted as trusted identity in `handleCreateRelayRequest` allows a peer to establish relay/routing state impersonating an arbitrary third-party VPN address - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest()` derives the value `from` directly from the attacker-controlled protobuf field `m.RelayFromAddr` of an incoming `NebulaControl_CreateRelayRequest` message, and then uses that unauthenticated value as the *key* under which persistent relay routing state is installed (`h.relayState`/`peer.relayState`), without ever checking that `from` corresponds to the actual authenticated identity of the sending peer `h` (i.e. `h.vpnAddrs`). This is structurally the same class of bug as the reported `cancelRedeemRequest()` issue: an attacker-supplied identity parameter (`operator`/here `from`) is used to key/mutate state that should be scoped to a verified owner (`owner`/here `h`'s own certificate-bound VPN address), with no authorization check binding the two.

### Finding Description
`handleCreateRelayRequest` is invoked from `HandleControlMsg` after only unmarshaling the message and checking that `RelayFromAddr`/`RelayToAddr` are non-nil [1](#0-0) . The `from` address used throughout the function comes straight from that message field, not from the sender's certificate: [2](#0-1) 

The only identity check performed is that `from` is not one of *my own* addresses (self-relay loop protection); there is no check that `from == h.vpnAddrs[0]` (i.e., that the claimed origin matches the actual, cert-authenticated peer who sent the message): [3](#0-2) 

In the terminal branch (I am the relay target), the code installs an `Established`/`Requested` relay entry keyed by the attacker-controlled `from`, on the hostinfo `h` of the actual sender, and replies confirming the relay: [4](#0-3) 

In the forwarding branch (I am acting as the relay hop, forwarding toward `target`), the code again keys the newly created relay state on `peer.relayState` using the unauthenticated `from`, and separately tracks half-created relay state on `h.relayState` keyed by `target`: [5](#0-4) 

Notably the outbound `CreateRelayRequest` sent to `peer` reports `RelayFromAddr = h.vpnAddrs[0]` (the verified sender) while the actual relay state just installed on `peer` was keyed by the unverified `from` [6](#0-5) , which is inconsistent and shows the code never reconciles/validates the two identities against each other.

This mirrors the report's root cause exactly: the report's `cancelRedeemRequest()` used `req.byOperator[operator]` (an unauthorized, attacker-supplied identity) to act on state that should be authorized-and-keyed by `owner`, with no allowance/permission check binding `operator` to `owner`. Here, `from` (attacker-supplied) is used to key/mutate persistent relay-routing state that should be bound to `h` (the actual, certificate-authenticated peer), with no check that `from` belongs to `h`.

### Impact Explanation
Any authenticated Nebula peer (no special privilege required, high likelihood) can send a `CreateRelayRequest` claiming an arbitrary `RelayFromAddr` equal to some other legitimate VPN node's address. A relay-capable node (`am_relay: true`) or the actual target of the "relay" will then:
- Install `Established`/`Requested`/`PeerRequested` relay state on the local hostmap tied to that forged address, causing the node to believe it has a legitimate relay relationship for a peer that never requested one.
- Route/forward traffic under that misattributed relay-index association, enabling relay-state poisoning and traffic misdirection/impersonation for a third party's VPN address without that party's participation or consent — an unauthorized-actor-controls-another-identity's-state class of bug, directly analogous to burning another owner's shares via `req.byOperator[operator]`.
- Because no signature or cert binds `RelayFromAddr` to the sender, this can also be used to attempt to disrupt/hijack existing relay sessions for the impersonated VPN address (state confusion / remote-state poisoning), and potentially to redirect traffic intended for that peer through the attacker-controlled path.

### Likelihood Explanation
High. `CreateRelayRequest` is processed for any already-authenticated peer (the handshake/cert layer authenticates `h`, but the relay logic never re-validates the claimed `from` field against `h`'s certificate networks). No additional permission, allow-list, or signature check exists on `RelayFromAddr` (`grep` for relay allow-list/authorization logic found none). Any peer capable of completing a normal Nebula handshake with a relay-capable or targeted node can send this control message.

### Recommendation
In `handleCreateRelayRequest`, validate that the claimed `from` address is actually one of `h.vpnAddrs` (the certificate-bound addresses of the authenticated sender `h`) before using it to key any relay state (`h.relayState`, `peer.relayState`) or before establishing/forwarding a relay on its behalf. Reject the request (as is already done for `from == myself`) whenever `from` does not belong to `h`'s verified identity, mirroring the report's recommendation of validating `req.byOperator[owner]`/allowance checks instead of trusting an unauthenticated `operator`/`from` parameter.

### Proof of Concept
1. Attacker `H` establishes a normal, valid Nebula handshake with relay-capable node `R` (`relay.am_relay: true`) or with the intended target `T`, so `H` is an authenticated peer with its own certificate-bound VPN address `H_ip`.
2. `H` crafts a `NebulaControl` message of type `CreateRelayRequest` with `RelayFromAddr = victim_ip` (a different, legitimate peer `V`'s VPN address) and `RelayToAddr = target_ip`.
3. `H` sends this message over its already-established tunnel to `R`/`T`.
4. `handleCreateRelayRequest` extracts `from = victim_ip` from the message without checking `from == h.vpnAddrs[0]`, and calls `AddRelay(..., h, ..., from, ..., TerminalType/ForwardingType, Established/Requested/PeerRequested)` (or the analogous `peer.relayState` install in the forwarding branch), installing relay state that attributes `H`'s relay to `V`'s identity.
5. `R`/`T` now holds `Established`/`Requested` relay routing state believing it relates to peer `V`, even though `V` never participated in this exchange — demonstrating unauthorized manipulation of another peer's relay/routing state via an unauthenticated identity field, analogous to the reported `cancelRedeemRequest()` operator/owner confusion.
