### Title
Uninitialized `accountIndexOf` treated as zero (instead of `INITIAL_INDEX`) lets existing token holders instantly claim rewards equal to their full balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` contains a read-before-initialization bug analogous to CVE-2016-9103 (QEMU `v9fs_xattrcreate` returning uninitialized heap data when an xattr is read before being written). When a reward token is first registered, `tokenStates[token].index` is set to `INITIAL_INDEX` (1e18), but accounts that already hold the `DepositToken`/`DebtToken` still have `accountIndexOf[token][account] == 0`. The fallback that substitutes `INITIAL_INDEX` for a zero account index only fires when `_tokenIndex > INITIAL_INDEX`, so while the global index is still exactly `INITIAL_INDEX` an untouched account index of `0` is used verbatim, producing `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account)`.

### Finding Description
In `_calculateTokenDelta`: [1](#0-0) 

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a token is registered via `_updateTokenSpeed`, its state is initialized to `{index: INITIAL_INDEX, timestamp: block.timestamp}`: [2](#0-1) 

`_calculateTokenIndex` only increases the index when `_deltaTimestamps > 0 && _speed > 0`; in the same block as registration (`_deltaTimestamps == 0`) the index remains `INITIAL_INDEX`. It also remains `INITIAL_INDEX` whenever `totalSupply == 0` was true at every past update (ratio = 0): [3](#0-2) 

Any unprivileged account can trigger the flawed path through `claimRewards(address[], IERC20[])` (public, no auth on the accounts) or `updateBeforeMintOrBurn` / `updateBeforeTransfer` (callable by anyone, only gated on `tokenStates[token_].index > 0`): [4](#0-3) [5](#0-4) 

`_updateTokensAccruedOf` then credits `tokensAccruedOf[account] += balance * INITIAL_INDEX / 1e18 = balance`, and `_transferRewardIfEnoughTokens` pays out `rewardToken` up to the distributor's balance: [6](#0-5) [7](#0-6) 

### Impact Explanation
Theft of unclaimed yield / direct drain of the distributor. Every account holding a `DepositToken` (or `DebtToken`) balance at the moment the token's reward speed is first set can claim `rewardToken` equal to its full token balance, before a single second of legitimate accrual. Multiple holders can do this in the same block, and the payout is only bounded by the distributor's `rewardToken` balance. Legitimate depositors' accrued rewards are stolen; the reward reserve is drained by indexing uninitialized state, exactly the "read before write" pattern of the reference bug.

### Likelihood Explanation
Requires a token whose `accountIndexOf` is uninitialized (`0`) while the global index equals `INITIAL_INDEX`. This deterministically occurs in the same block that governance registers a reward token (`updateTokenSpeed`/`syncTokenSpeed` on an existing `DepositToken`/`DebtToken` with live balances), which is a routine operation — rewards are commonly added to already-live pools. An attacker only needs to hold or borrow the token beforehand and back-run the governance transaction in the same block (standard MEV ordering), or act any time the index has not yet grown past `INITIAL_INDEX` (e.g., while `totalSupply == 0` kept the ratio at 0). No privileged role, oracle manipulation, or reentrancy is needed; `nonReentrant` and `SynthContext` do not intervene.

### Recommendation
Treat an uninitialized account index as `INITIAL_INDEX` whenever the token index is nonzero, not only when it exceeds `INITIAL_INDEX`:

```solidity
if (_accountIndex == 0 && _tokenIndex > 0) {
    _accountIndex = INITIAL_INDEX;
}
```

Equivalently, initialize `accountIndexOf` to `INITIAL_INDEX` on every account's first interaction, or store account indices offset by `INITIAL_INDEX` so the zero default cannot be misread as a baseline of `0`.

### Proof of Concept
Hardhat test sketch (fork or fixture with a live Pool, DepositToken `msdTOKEN`, and funded `RewardsDistributor`):

```ts
// Pre-condition: alice holds DepositToken balance before reward speed is set.
// (deposit normally; at this point tokenStates[msdTOKEN].index == 0, so
//  updateBeforeMintOrBurn is skipped and accountIndexOf[alice] == 0)
await depositToken.mint(alice.address, parseEther('100')); // or via pool.deposit

// Fund distributor with rewardToken
await rewardToken.mint(rewardDistributor.address, parseEther('1000'));

// Governor registers the reward token (same block / next tx same timestamp)
await rewardDistributor.updateTokenSpeed(msdTOKEN.address, parseEther('1'));
const { index } = await rewardDistributor.tokenStates(msdTOKEN.address);
expect(index).eq(INITIAL_INDEX); // still 1e18 in the same block

// Alice (or anyone calling on her behalf via claimRewards(accounts, tokens))
await rewardDistributor['claimRewards(address,address[])'](
  alice.address,
  [msdTOKEN.address],
);

// BUG: tokensDelta = balanceOf(alice).wadMul(INITIAL_INDEX - 0) = 100
// => alice received 100 rewardToken with zero elapsed accrual
expect(await rewardToken.balanceOf(alice.address)).eq(parseEther('100'));
```

The same result is obtained by calling `rewardDistributor.updateBeforeMintOrBurn(msdTOKEN.address, alice.address)` followed by `claimRewards`, since `updateBeforeMintOrBurn` is permissionless when `index > 0`.
