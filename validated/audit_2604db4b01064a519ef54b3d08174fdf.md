## Title
Missing minimum-balance enforcement on partial `UnDelegateResourceContract` allows dust delegated-resource records below the protocol's enforced minimum - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The reported Blueberry bug class is that `minPositionSize` is enforced when *opening* a position but not re-checked on *partial* closes, letting a position shrink below the protocol's minimum invariant. The equivalent invariant in java-tron is the 1 TRX minimum enforced when creating a resource delegation. `DelegateResourceActuator` enforces `delegateBalance >= TRX_PRECISION` (1 TRX) when a delegation ("position") is opened, but `UnDelegateResourceActuator`, which handles partial or full withdrawal of a delegation, never re-validates that the remaining delegated balance stays at or above that same minimum (or is fully closed).

### Finding Description
When a user delegates bandwidth/energy resources, `DelegateResourceActuator.validate()` requires the delegated amount to be at least `TRX_PRECISION` (1 TRX): [1](#0-0) 

This minimum is intended to prevent creation of dust `DelegatedResourceCapsule` entries. However, `UnDelegateResourceActuator.validate()` — the "closing" counterpart — only checks that the requested `unDelegateBalance` is positive and does not exceed the currently delegated amount; it never checks whether the *remaining* delegated balance after a partial undelegate stays ≥ 1 TRX (or becomes exactly 0): [2](#0-1) 

As a result, any account holder can call `UnDelegateResourceContract` with an amount that leaves an arbitrarily small (down to 1 sun) delegated balance on a `DelegatedResourceCapsule` record, in direct contradiction to the invariant enforced at delegation time.

### Impact Explanation
This breaks the protocol invariant that all delegated-resource entries respect a 1 TRX minimum, the same invariant class flagged as Medium severity in the source report (unexpected "dust positions" the protocol did not intend to allow). It allows an unprivileged account to leave persistent sub-minimum `DelegatedResourceCapsule` records in `DelegatedResourceStore`, which downstream logic (e.g., resource usage/weight calculations in `UnDelegateResourceProcessor`, `DelegateResourceProcessor`) was not designed to expect, given the minimum is enforced only at creation.

### Likelihood Explanation
Trivially reachable by any account that has ever delegated resources: simply issue an `UnDelegateResourceContract` transaction with a `balance` value chosen so the remainder is below `TRX_PRECISION`. No special privileges required.

### Recommendation
In `UnDelegateResourceActuator.validate()`, after computing the remaining delegated balance for the resource type being undelegated, require that it be either `0` (full close) or `>= TRX_PRECISION`, mirroring the check already present in `DelegateResourceActuator.validate()`.

### Proof of Concept
1. Account A delegates exactly `1,000,000` sun (1 TRX) of BANDWIDTH to account B via `DelegateResourceContract` (passes the `delegateBalance >= TRX_PRECISION` check in `DelegateResourceActuator.validate()`).
2. Account A then submits `UnDelegateResourceContract` requesting `unDelegateBalance = 999,999` sun.
3. `UnDelegateResourceActuator.validate()` only checks `unDelegateBalance <= 0` and `delegateBalance < unDelegateBalance` — both pass since `999,999 <= 1,000,000`.
4. The transaction succeeds, leaving a `DelegatedResourceCapsule` with `1` sun of frozen delegated BANDWIDTH balance, violating the 1 TRX minimum invariant enforced elsewhere in the codebase.
