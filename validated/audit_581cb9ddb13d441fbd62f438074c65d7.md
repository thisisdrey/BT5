### Title
Uninitialized `accountIndexOf` lets any holder drain reward tokens when `tokenStates.index == INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
Analogous to CVE-2021-46966 (state freed/stale yet still consumed by later calls), `_calculateTokenDelta` treats a never-initialized `accountIndexOf[token][account]` as a live index of `0` whenever the global index has not yet advanced past `INITIAL_INDEX`. Any account holding a DepositToken/DebtToken balance before that token's reward speed was activated can claim `balance * 1e18` worth of `rewardToken` without accruing anything, because the `INITIAL_INDEX` fallback only applies when `_tokenIndex > INITIAL_INDEX`.

### Finding Description
`claimRewards(accounts_, tokens_)` is permissionless and pays out to `accounts_[j]` directly. [1](#0-0) 

Inside `_calculateTokenDelta`, the "new account" baseline is only applied when the global index strictly exceeds `INITIAL_INDEX`: [2](#0-1) 

When a token is first activated, `_updateTokenSpeed` stores `TokenState({index: INITIAL_INDEX, timestamp: ...})`. [3](#0-2)  If `accountIndexOf[token][account] == 0` and `tokenStates[token].index == INITIAL_INDEX` (i.e. index has not grown yet — speed was just set, or was set and zeroed again in the same window), the condition `_tokenIndex > INITIAL_INDEX` is false, `_accountIndex` stays `0`, and `_deltaIndex = 1e18 - 0 = 1e18`. The account is credited `balance.wadMul(1e18) = balance` reward tokens.

Accounts reach this state legitimately: `updateBeforeMintOrBurn`/`updateBeforeTransfer` are no-ops while `tokenStates[token_].index == 0`, [4](#0-3)  so every user who deposited before the reward speed for that token was enabled retains `accountIndexOf == 0`.

`_transferRewardIfEnoughTokens` then pays out as long as the distributor holds enough `rewardToken`. [5](#0-4) 

### Impact Explanation
Direct theft of unclaimed yield: the attacker mints reward tokens equal to their token balance with zero accrual time, draining the distributor's `rewardToken` balance up to that amount, depriving legitimate depositors of emissions. Repeatable per token and per account; an attacker can also pass many victim accounts — but victims get paid, so the practical exploit is self-claim with a large deposited (or flash-borrowed-into-DebtToken) balance.

### Likelihood Explanation
- Trigger conditions are routine: a reward token is enabled via `updateTokenSpeed`/`syncTokenSpeed` after users already hold the DepositToken, or speed is raised then returned to `0` before the index advances past `INITIAL_INDEX`.
- No privileged call is needed for the exploit itself — `claimRewards` is public and `nonReentrant` does not block it.
- No existing check stops it: `onlyIfTokenExists` only gates speed updates, not claims; `tokenStates[_token].index > 0` is satisfied the moment the token is registered.

### Recommendation
In `_calculateTokenDelta`, treat an uninitialized account index as the current global index whenever `tokenStates` exists, not only when it exceeds `INITIAL_INDEX`:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

Equivalent fix: initialize `accountIndexOf` to `INITIAL_INDEX` (or the current index) on first touch inside `_updateTokensAccruedOf`.

### Proof of Concept
Hardhat sketch (fork or local deploy):

```ts
// 1. User deposits before reward speed is enabled for msdToken.
await depositToken.deposit(amount, attacker.address); // index==0 -> hook no-op, accountIndexOf stays 0

// 2. Governor enables rewards on that token.
await rewardsDistributor.connect(governor).updateTokenSpeed(depositToken.address, speed);
// tokenStates[msdToken].index == INITIAL_INDEX (1e18)

// 3. Same block / before index grows past 1e18, attacker claims.
const bal = await depositToken.balanceOf(attacker.address);
await rewardsDistributor.claimRewards(attacker.address, [depositToken.address]);

// 4. tokensAccruedOf[attacker] == bal * 1e18-scaled => attacker receives `bal` rewardToken
expect(await rewardToken.balanceOf(attacker.address)).to.eq(bal);
```

Expected: zero claimable (no time accrued); actual: payout equal to the attacker's token balance, limited only by the distributor's `rewardToken` inventory.
