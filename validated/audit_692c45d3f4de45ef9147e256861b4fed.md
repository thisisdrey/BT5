### Title
Attachment download path fails to verify served attachment hash matches requested content_hash, allowing peer reliability score poisoning - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a `GetAttachmentResponse` from a peer and unconditionally inserts `response.attachment` into `self.attachments` and calls `report.bump_successful_requests()`, without ever checking that `response.attachment.hash()` equals the `request.content_hash` that was actually requested. A malicious outbound-sync peer can serve arbitrary, self-consistent-but-unrelated attachment bytes for any `/v2/attachments/<content_hash>` request and be rewarded with an inflated reliability score.

### Finding Description
The broken equality is: `response.attachment.hash() == request.content_hash`. This is never checked. In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), for each successfully-completed `AttachmentRequest`, the code does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
```
`decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) merely JSON-deserializes the HTTP body into `GetAttachmentResponse { attachment }` — it performs no hash validation against the original request. The `AttachmentRequest.content_hash` (set from `get_prioritized_attachments_requests`, `stackslib/src/net/atlas/download.rs:404-478`) that drove the request is available in `request` at this point but is discarded/ignored for validation purposes.

Downstream, `AttachmentsDownloader::run`'s `Done` arm (`stackslib/src/net/atlas/download.rs:153-169`) drains `context.attachments`, computes `attachment.hash()` itself (self-consistent, so it does not falsely resolve an unrelated `AttachmentInstance`), and calls `context.attachments_batch.resolve_attachment(&attachment.hash())`. Because `resolve_attachment` is keyed by the attachment's own hash rather than by which `AttachmentRequest` produced it, a mismatched attachment does not get associated with the wrong `AttachmentInstance` — but the batch's requested content hash is never marked resolved either, so the original request will eventually retry/expire. Meanwhile, the reliability report update in `extend_with_attachments` happens purely based on "did decode succeed", not "did the peer serve what was asked for", so the malicious peer's `ReliabilityReport::bump_successful_requests()` (`stackslib/src/net/atlas/download.rs`) is called regardless of the mismatch.

### Impact Explanation
A remote, unprivileged peer that a node has selected as an outbound-sync peer (via ordinary P2P handshake/inventory gossip — no special role needed) can respond to every `AttachmentRequest` with unrelated, self-consistent attachment bytes and have its `ReliabilityReport` score inflated as if it were reliably serving the exact content requested. Because `get_prioritized_attachments_requests` (`stackslib/src/net/atlas/download.rs:404-478`) uses `ReliabilityReport` (successful/failed counts) to select which peer to prefer for rarest-first attachment fetching (visible in `test_downloader_context_attachment_requests`, `stackslib/src/net/atlas/tests.rs:669-761`, where peer selection follows reliability history), an attacker can steer future attachment-fetch preference toward itself while never actually serving the correct BNS zonefile/attachment content, degrading data availability and skewing peer trust — this matches the "attachment/BNS mismatch" High-severity category.

### Likelihood Explanation
Preconditions are modest: the attacker must be selected as one of `network.get_outbound_sync_peers()` (`stackslib/src/net/atlas/download.rs:116`) and be included among `sources` in a constructed `AttachmentRequest` after inventory-gossip claims availability — both achievable by any peer that completes a normal P2P handshake and responds to `/v2/attachments/inv` requests, no secret or privileged role required. The attack is cheap and fully repeatable per request/response cycle since no additional signature or state is needed beyond a normal HTTP RPC reply.

### Recommendation
In `extend_with_attachments`, after successfully decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments` and before calling `report.bump_successful_requests()`; treat a mismatch as a failed request (`report.bump_failed_requests()`), and optionally penalize/deregister the offending peer.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` analogous to `test_downloader_context_attachment_requests`: construct an `AttachmentRequest` with `content_hash = H1` (from `new_attachment_from("facadeAA")`), build a `GetAttachmentResponse`/`StacksHttpResponse` wrapping a different `Attachment` whose content hashes to `H2 != H1` (e.g., `new_attachment_from("facadeBB")`), insert it into `BatchedRequestsResult::succeeded`, call `context.extend_with_attachments(&mut results)`, then assert that `context.peers.get(&peer_url).unwrap()` shows an incremented successful-request count (`report.request_count()`/success ratio increased) despite `attachment.hash() != H1`, and that `context.attachments` contains the mismatched attachment — demonstrating the reliability report is falsely inflated with no hash validation.     pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
