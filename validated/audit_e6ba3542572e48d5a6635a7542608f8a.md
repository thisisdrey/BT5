### Title
`RewardsDistributor` Pays Claims From Raw `balanceOf` Without Reserving Other Accounts' Accrued Rewards — Late Claimants' Yield Is Permanently Frozen - (File: contracts/RewardsDistributor.sol)

### Summary
The same bug class as the external report — conflating a raw `ERC20.balanceOf` reading with "available rewards" while ignoring accrued-but-unpaid obligations — exists in `RewardsDistributor._transferRewardIfEnoughTokens` (contracts/RewardsDistributor.sol:248-256). The distributor accrues obligations into `tokensAccruedOf` purely as a function of time × `tokenSpeeds` (lines 197-212, 261-266), completely decoupled from the contract's actual reward-token funding. When claims are executed, each account's payout is checked against the entire raw balance with no subtraction of the sum of all other accounts' outstanding `tokensAccruedOf`. Payout is first-come-first-served, so once cumulative accrual exceeds the funded balance, earlier claimants drain the contract and later users' accrued yield is stranded forever (their `tokensAccruedOf` stays positive but `_transferRewardIfEnoughTokens` silently does nothing and doesn't even clear or queue the debt beyond storage).

### Finding Description
- `_updateTokensAccruedOf` / `_calculateTokenIndex` grow `tokensAccruedOf[account]` at `tokenSpeeds[token]` per second (weighted by `token_.balanceOf(account_) / token_.totalSupply()`), regardless of whether the distributor holds enough `rewardToken` (contracts/RewardsDistributor.sol:197-231).
- `claimRewards(address[] accounts_, IERC20[] tokens_)` is public and `nonReentrant`; for each account it calls `_transferRewardIfEnoughTokens(account, tokensAccruedOf[account])` (lines 150-168).
- `_transferRewardIfEnoughTokens` only checks `amount_ <= rewardToken.balanceOf(address(this))` and transfers; if the check fails it does nothing — the accrued amount remains claimable in storage but is unpayable because earlier claims consumed the balance. There is no accounting like `totalAccrued` or `balance - Σaccrued` — exactly the raw-`balanceOf`-vs-accrued-obligations mismatch flagged in the report.

Attack/failure path: normal protocol operation (deposit/borrow activity triggers `updateBeforeMintOrBurn`/`updateBeforeTransfer` from `DepositToken`/`DebtToken`) accrues `tokensAccruedOf` for many users. Any unprivileged user can call `claimRewards` for themselves (or for any account, since `accounts_` is arbitrary). As soon as `Σ tokensAccruedOf > rewardToken.balanceOf(distributor)`, the first N claimants are paid in full and everyone else receives zero despite positive accrued balances — effectively forfeiting their earned yield unless governance happens to refund, since accrual keeps accruing new debt faster than funding arrives.

### Impact Explanation
Permanent freezing/loss of unclaimed yield for late claimants. Users' `tokensAccruedOf` balances represent earned rewards, but the FCFS payout against an unreserved balance means a subset of claimants captures all funded tokens and the remainder's yield is unrecoverable through the contract. No privileged action is needed: accrual is automatic via token mint/burn/transfer hooks, and `claimRewards` is permissionless.

### Likelihood Explanation
Likelihood is moderate: it requires the distributor's cumulative accrual to exceed its funded `rewardToken` balance, which depends on funding cadence vs. `tokenSpeeds` set by governor/keeper. However nothing in the contract bounds accrual to funding, `syncTokenSpeed` derives speed from an external Vesper `rewardRate` × treasury position (lines 333-348) with no funding check, and any gap in topping up deterministically creates stranded claims. Once the condition exists, an unprivileged race to claim decides who gets paid — a griefing/extraction dynamic identical in spirit to the reported overestimation.

### Recommendation
Track total outstanding obligations (e.g., `totalTokensAccrued`) and either (a) revert/queue when `tokensAccruedOf[account] > rewardToken.balanceOf(this) - totalTokensAccruedOfOthers`, or (b) reserve per-account amounts so claims are pro-rata rather than FCFS. Minimally, compute availability as `balanceOf - Σ outstanding accrued` — the analog of the report's `getRewardBalance()` fix. Optionally emit an event or pause accrual when underfunded.

### Proof of Concept
Hardhat-style sketch against existing test scaffolding (`test/RewardDistributor.test.ts`):

```ts
// rewardToken (vsp) funds distributor with 30; speeds accrue 40 total
// alice and bob each accrue 20 (as in existing 'claimRewards' test)
await rewardDistributor['claimRewards(address)'](alice.address) // pays 20, balance = 10
await rewardDistributor['claimRewards(address)'](bob.address)   // pays 10 (only if amount<=balance);
// if bob.accrued == 20 > 10 balance: pays 0, tokensAccruedOf[bob] stays 20 forever
expect(await rewardDistributor.tokensAccruedOf(bob.address)).eq(parseEther('20'))
expect(await vsp.balanceOf(bob.address)).eq(0) // stranded yield
```

Uncertainty: I could not verify (iterations exhausted) whether `DebtToken.balanceOf` returns interest-inflated balances, which would widen the accrual-vs-funding gap further, nor whether deployment configs keep the distributor perpetually over-funded, which would reduce practical likelihood.
