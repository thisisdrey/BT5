I found a concrete analog of the GitLab "feature not activated but usable" bug class.

### Title
TVM `delegateResource`/`unDelegateResource` opcodes bypass the `ALLOW_UNFREEZE_DELAY` committee gate enforced on the equivalent broadcastable transactions - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java)

### Summary
`DelegateResourceActuator` and `UnDelegateResourceActuator` — the actuators that handle ordinary, broadcastable `DelegateResourceContract`/`UnDelegateResourceContract` transactions — both require two dynamic-property flags before allowing resource delegation: `supportDR()` and `supportUnfreezeDelay()` [1](#0-0) , [2](#0-1) . However, the TVM-reachable equivalents, `DelegateResourceProcessor.validate()` and `UnDelegateResourceProcessor.validate()`, which are invoked directly from Solidity via `Program.delegateResource`/`Program.unDelegateResource`, only check `supportDR()` and never call `supportUnfreezeDelay()` [3](#0-2) , [4](#0-3) .

### Finding Description
`supportUnfreezeDelay()` is a distinct, separately-activated committee flag gating "Delegate/unDelegate resource transaction, need to be opened by the committee." Both regular actuators enforce it in addition to `supportDR()`. The TVM native-contract processors that back the `delegateResource`/`unDelegateResource` opcodes reachable from any deployed smart contract skip this second check entirely, calling `processor.validate(param, repository)` which only tests `supportDR()` [5](#0-4) . This is architecturally identical to the reported GitLab bug class: a feature (resource delegation on the `ALLOW_UNFREEZE_DELAY`-gated code path) that is not yet activated for the primary interface can still be triggered through an alternate interface (here, TVM opcodes instead of a direct transaction) because the second interface's validation path omits the same guard.

### Impact Explanation
If `ALLOW_DELEGATE_RESOURCE` (`supportDR`) is enabled by governance while `ALLOW_UNFREEZE_DELAY` (`supportUnfreezeDelay`) has not yet been enacted — a legitimate intermediate chain state during phased feature rollout — any contract deployer can still perform resource delegation/undelegation via the TVM opcodes, even though ordinary users are blocked from doing so by the transaction-level actuators. This lets contracts manipulate delegated bandwidth/energy balances and receiver "acquired" balances ahead of the intended activation, potentially interacting with resource accounting (bandwidth/energy weight totals, delegated balances) in ways the network was not yet designed/tested to allow, causing inconsistent resource accounting or unauthorized resource delegation state changes.

### Likelihood Explanation
Reachable by any account that deploys a contract calling the TVM `delegateResource`/`unDelegateResource` precompiled opcodes — no special privilege is required beyond normal contract deployment and invocation, which is available to any unprivileged network participant. Exploitability depends purely on the two flags being in the specific unsynchronized state (`supportDR()==true`, `supportUnfreezeDelay()==false`); whether such a state is presently observable on mainnet/testnet is not verifiable from static code alone.

### Recommendation
Add the same `supportUnfreezeDelay()` check to `DelegateResourceProcessor.validate()` and `UnDelegateResourceProcessor.validate()` that already exists in `DelegateResourceActuator.validate()` / `UnDelegateResourceActuator.validate()`, so both entry points (transaction and TVM opcode) enforce identical activation gating.

### Proof of Concept
1. Assume governance enables `ALLOW_DELEGATE_RESOURCE` but has not yet enabled `ALLOW_UNFREEZE_DELAY` (a legitimate intermediate/staged rollout state).
2. A regular account attempts `DelegateResourceContract` via a transaction → `DelegateResourceActuator.validate()` throws `"Not support Delegate resource transaction, need to be opened by the committee"` [6](#0-5) .
3. The same account instead deploys/calls a contract invoking the `delegateResource(receiver, balance, resourceType)` TVM opcode, which calls `DelegateResourceProcessor.validate()` — this passes because only `supportDR()` is checked [3](#0-2) , and `processor.execute()` completes the delegation, bypassing the intended gate.

  public boolean delegateResource(
      DataWord receiverAddress, DataWord delegateBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,
        delegateBalance.longValue(), null,
        "delegateResourceOf" + convertResourceToString(resourceType), nonce, null);

    try {
      DelegateResourceParam param = new DelegateResourceParam();
      param.setOwnerAddress(owner);
      param.setReceiverAddress(receiver);
      param.setDelegateBalance(delegateBalance.sValue().longValueExact());
      param.setResourceType(parseResourceCodeV2(resourceType));

      DelegateResourceProcessor processor = new DelegateResourceProcessor();
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM DelegateResource: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM DelegateResource: balance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }
