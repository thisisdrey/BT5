### Title
Unprivileged dust-transfer griefing permanently locks a user's ability to open new collateral/debt positions via `MAX_TOKENS_PER_USER` - (File: contracts/Pool.sol)

### Summary
`Pool` keeps a per-account enumerable set of deposit and debt tokens capped at `MAX_TOKENS_PER_USER = 30`. Any addition (deposit into a new collateral, issuing a new debt type, or *receiving* a deposit-token transfer) calls `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, which revert with `UserReachedMaxTokens` once the combined count reaches 30. Because `DepositToken.transfer`/`transferFrom` are permissionless ERC-20 entry points that call `pool.addToDepositTokensOfAccount(recipient_)` on the *recipient*, an attacker can force-fill a victim's set with dust of every deposit token in the pool, after which all attempts by the victim to deposit a new collateral type, issue a new synth debt, or receive any new deposit token revert — a repeatable availability failure analogous to the InnoDB crash/hang class of CVE-2018-3079. ### Finding Description
`DepositToken.transfer` (line 348) → `_transfer` (line 498) → on first nonzero balance, `pool.addToDepositTokensOfAccount(recipient_)` (line 519). `addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (Pool.sol:143-148). The same check runs inside `_mint` (DepositToken.sol:486-488), so `deposit()`, `DebtToken.issue()`, `liquidate()` fee/incentive `seize()` transfers, and SmartFarmingManager flows all revert for a saturated account. The check is enforced even if `add` would be a no-op — wait, actually `add` is called after the length check, so a re-add of an existing token still hits the length guard first only via `addToDepositTokensOfAccount` being called; note `_transfer`/`_mint` only call it when balance was previously zero, so existing-token operations are unaffected. [5](#0-4) [6](#0-5) 

The attacker needs only small unlocked balances of each deposit token (obtainable by depositing dust into each supported collateral), then calls `transfer(victim, 1 wei)` for each distinct `DepositToken` until the victim's combined set length hits 30. Thereafter:

- `victim` cannot `deposit()` into any collateral they don't already hold — the mint reverts in `addToDepositTokensOfAccount`.
- `victim` cannot `issue()` any new synth — `DebtToken` mint triggers `addToDebtTokensOfAccount` which reverts (Pool.sol:204-208).
- Nobody can `transfer`/`seize` a new token type to the victim — including `Pool.liquidate` paying the liquidator/fee collector if that recipient's set is saturated.
- Recovery requires the victim to fully zero out dust balances of tokens they never wanted (transferring each dust balance away), at their own gas cost — and the attacker can re-fill the freed slots in the same block by front-running, since removal only happens when balance returns to zero. [7](#0-6) 

### Impact Explanation
Availability (DoS) — matches the CVE class (hang/crash → loss of function). A saturated victim is prevented from using the protocol's core functions: depositing new collateral and issuing new debt both permanently revert while the attack is maintained. Since the pool supports up to `MAX_TOKENS_PER_USER` deposit tokens (Pool.sol:703 allows `addDepositToken` until `depositTokens.length() >= 30`), an attacker on a pool with, say, 5 collaterals would need to also hold/transfer debt-token entries — practically, the attacker fills slots with a mix of deposit-token dust and issued dust debt (`DebtToken.issue` of 1 wei of each synth adds to `debtTokensOfAccount`). Once saturated, repeated `deposit`/`issue` calls by the victim always revert; it is a temporary freezing of the victim's position-management capability and forces the victim to spend gas cleaning attacker-planted dust entries. Existing balances remain withdrawable only for tokens already held. [8](#0-7) 

### Likelihood Explanation
Fully reachable by an unprivileged EOA through public `DepositToken.transfer`/`deposit` and `DebtToken.issue` with no privileged role, no oracle manipulation, and no unbounded loop. Cost is bounded by the number of registered tokens (≤30) and the collateral needed for dust deposits plus the debt floor for `issue`. The attack can be repeated indefinitely (re-fill freed slots), so liveness loss persists as long as the attacker wishes.

### Recommendation
- Skip the max-count guard when the token is already in the account's set (the current code already avoids calling `add` when balance > 0, so the residual risk is only re-adds — but the real fix is on the accounting model): allow removal of dust entries cheaply, or
- track token membership differently (e.g., don't revert on add — keep a counter and only bound iteration, or cap the number of *deposit* tokens counted against the user but let the victim's own operations evict zero-value attacker-forced entries), or
- make `transfer` to a saturated account not revert the whole op for new tokens (e.g., use a pull/claim model for unsolicited tokens), and provide a `sweepDust`/`exitToken` helper so victims can remove forced entries in one call.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {DebtToken} from "../contracts/DebtToken.sol";

contract MaxTokensGriefTest is Test {
    // Assume a deployed pool with N deposit tokens + M debt tokens, N+M >= 30
    // (pool.addDepositToken allows up to MAX_TOKENS_PER_USER deposit tokens).
    Pool pool;
    DepositToken[] depositTokens;
    DebtToken[] debtTokens;
    address attacker = address(0xA);
    address victim   = address(0xB);

    function testGrief() public {
        // 1) Attacker obtains dust of each deposit token (deposit 1 wei of each underlying)
        //    and issues 1 wei debt of each synth via DebtToken.issue().
        // 2) Attacker fills victim's token lists:
        for (uint i; i < depositTokens.length; ++i) {
            vm.prank(attacker);
            depositTokens[i].transfer(victim, 1); // adds depositToken to victim's set
        }
        // For debt tokens, attacker deposits collateral on behalf of victim is not needed;
        // instead attacker issues debt is per-account, so attacker instead relies on
        // dust deposit-token transfers across pools' many DepositTokens (pool allows 30).
        // (On pools with <30 deposit tokens, attacker also transfers dust debt-token
        //  balances is not transferable; the deposit-token side alone suffices when
        //  depositTokens.length == 30, which addDepositToken permits.)

        // 3) Victim now has 30 entries; any new-token op reverts:
        vm.prank(victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        depositTokens[0].deposit(100, victim); // a collateral victim doesn't hold yet

        // 4) Receiving any new token also reverts:
        DepositToken newToken = depositTokens[depositTokens.length - 1]; // victim holds none
        vm.prank(attacker);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newToken.transfer(victim, 1);

        // 5) Victim must burn gas transferring each dust balance fully away to free slots;
        //    attacker can re-fill a freed slot in the same block before victim deposits.
    }
}
```

Note: the attack's feasibility depends on the deployed pool having enough registered deposit tokens (up to 30 permitted by `addDepositToken`, Pool.sol:703). On pools with few collaterals, the attacker can additionally saturate `debtTokensOfAccount` only through their own positions — debt tokens are not transferable, so the practical version of this griefing vector requires a pool with many deposit tokens, or saturation limited to `depositTokensOfAccount` (which still blocks all new-collateral deposits for the victim, since the shared guard sums both sets).
