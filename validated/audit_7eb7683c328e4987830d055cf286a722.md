### Title
Dust-transfer griefing fills `feeCollector`'s per-account token list to `MAX_TOKENS_PER_USER`, bricking `Pool.liquidate` / `DepositToken.withdraw` / `deposit` for any collateral the collector does not yet hold - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The MySQL CVE is a remotely-triggerable availability failure (repeatable crash / hang → complete DoS). The Metronome analog is the `MAX_TOKENS_PER_USER` cap in `Pool`: every mint/transfer/seize of a `DepositToken` to an account holding zero of that token calls `pool.addToDepositTokensOfAccount(account)`, which reverts with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount` reaches 30. `DepositToken.transfer` is permissionless and pushes tokens *to* an arbitrary recipient, so an attacker can dust-fill any fixed, well-known protocol address — most critically `poolRegistry.feeCollector()` — making subsequent fees/seizes of *new* deposit-token types revert, freezing liquidations, withdrawals, and deposits for those markets.

### Finding Description
`DepositToken._transfer` and `_mint` unconditionally add the token to the recipient's per-account list on a 0→>0 balance change: [1](#0-0) [2](#0-1) 

`Pool.addToDepositTokensOfAccount` enforces the combined 30-token cap and reverts on overflow: [3](#0-2) [4](#0-3) 

Attack path (unprivileged EOA, no privileged role):
1. Attacker deposits dust amounts of each listed collateral and `transfer`s 1 wei of each `DepositToken` to `feeCollector` (a fixed protocol address read via `poolRegistry.feeCollector()`), plus dust debt-token-free, until `depositTokensOfAccount.length(feeCollector) + debtTokensOfAccount.length(feeCollector) == MAX_TOKENS_PER_USER` (30). Pools list many deposit tokens (the per-pool cap is separately enforced by `ReachedMaxDepositTokens`), so 30 entries are reachable.
2. From then on, for any `DepositToken` the collector does not already hold:
   - `Pool.liquidate` reverts at `depositToken_.seize(account_, feeCollector, _fee)` when `_fee > 0` — `seize` → `_transfer` → `addToDepositTokensOfAccount(feeCollector)` → `UserReachedMaxTokens`.
   - `DepositToken.withdraw` / `withdrawFrom` / `flashWithdraw` revert at `_transfer(account_, feeCollector, _fee)` in `_withdraw` when `withdrawFee > 0`.
   - `DepositToken.deposit` reverts at `_mint(feeCollector, _fee)` when `depositFee > 0`. [5](#0-4) [6](#0-5) [7](#0-6) 

The same technique works on any protocol-owned receiver that cannot easily eject dust (e.g. `SmartFarmingManager` contract receiving msdTOKEN during `leverage`), but `feeCollector` is the strongest fixed target because it sits on the liquidation path.

### Impact Explanation
Availability / liveness failure mirroring the CVE: every `liquidate` call for a collateral market whose fee share would go to a "new" token at the filled collector reverts, so unhealthy positions in those markets cannot be liquidated — bad debt accrues and protocol solvency degrades while the condition persists. Withdrawals and deposits for those same markets are also bricked (temporary freezing of user funds) for as long as the collector remains at the cap. Recovery requires the feeCollector (or governor operations) to proactively transfer dust out; until then the DoS persists across all users.

### Likelihood Explanation
Requires: (a) enough listed `DepositToken`/`DebtToken` types to fill 30 combined slots — Metronome pools list many collaterals and synthetics, and the attacker can also add entries across *multiple* pools? No — the list is per-pool, so the precondition is a pool with ≥30 listed token types, or fewer if the collector already holds several; each dust transfer costs only gas and 1 wei. (b) `protocolLiquidationFee`/`withdrawFee`/`depositFee` > 0 on the affected markets (standard config). Severity is Medium-like: temporary, recoverable DoS of liquidations and exits on a subset of markets, not permanent loss — matching the CVE's availability-only impact.

### Recommendation
- Exempt fee-protocol sinks from the cap: in `Pool.addToDepositTokensOfAccount`, skip the `onlyIfAdditionWillNotReachMaxTokens` check (or skip list tracking entirely) when `account_ == poolRegistry.feeCollector()`.
- Alternatively, make `DepositToken` sends to `feeCollector` use a dedicated non-enumerated path (e.g. a `seize`-like transfer that bypasses the per-account list), or raise/eliminate `MAX_TOKENS_PER_USER` for contracts rather than EOAs.
- As defense-in-depth, allow `sweep`/rescue of dust msdTOKEN balances held by protocol contracts.

### Proof of Concept
Hardhat sketch (mirroring existing `test/Pool.test.ts` fixtures):

```ts
// 1. Attacker dust-fills feeCollector's list
const collector = await poolRegistry.feeCollector();
const n = (await pool.MAX_TOKENS_PER_USER()).toNumber();
for (let i = 0; i < n; i++) {
  // for each listed deposit token i (or a fresh smock-faked one added by governor in a fork):
  await depositToken_i.connect(attacker).deposit(1, attacker.address); // or transferFrom
  await depositToken_i.connect(attacker).transfer(collector, 1);       // adds token to collector list
}
expect(await pool.getDepositTokensOfAccount(collector)).to.have.length(n);

// 2. Any liquidation paying a fee in a token the collector doesn't hold reverts
await masterOracle.updatePrice(met.address, toUSD('0.5'));          // make alice unhealthy
await feeProvider.updateProtocolLiquidationFee(parseEther('0.01')); // _fee > 0
const amountToRepay = await pool.quoteLiquidateMax(msEth.address, alice.address, msdNEW.address); // msdNEW not held by collector
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, amountToRepay, msdNEW.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3. Withdrawals with withdrawFee > 0 in msdNEW also revert
await expect(
  msdNEW.connect(bob).withdraw(amount, bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
