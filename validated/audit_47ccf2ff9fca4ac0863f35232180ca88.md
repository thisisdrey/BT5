### Title
Unliquidatable debt band: `debtFloorInUsd` combined with `maxLiquidable < 100%` permanently DoSes `Pool.liquidate`, trapping bad debt - (File: contracts/Pool.sol)

### Summary
The bug class of the external report is a repeatable denial of service (hang/crash). The strongest reachable analog in Metronome is a permanent DoS of `Pool.liquidate`: when `debtFloorInUsd > 0` and `maxLiquidable < 1e18`, every position whose debt `D` falls in the interval `debtFloorInUsd < D < 2 * debtFloorInUsd` can never be liquidated. Any `amountToRepay_` either exceeds `maxLiquidable` or leaves a remainder below the floor, so the call always reverts and the unhealthy position freezes in place, accruing interest until it becomes protocol bad debt.

### Finding Description
`Pool.initialize` sets `maxLiquidable = 0.5e18` (50%) [1](#0-0) . In `liquidate`, two sequential checks are applied to `amountToRepay_` against the account's debt balance `_debtTokenBalance`:

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts with `AmountGreaterThanMaxLiquidable`, so `amountToRepay_ <= 0.5 * D`. [2](#0-1) 
2. The post-repayment debt `_debtTokenBalance - amountToRepay_` must be either `0` or `>= debtFloorInUsd`, otherwise `RemainingDebtIsLowerThanTheFloor` reverts. [3](#0-2) 

For a successful call there must exist `r` with `r <= 0.5 * D` and `D - r >= floor` (since `r = D > 0.5 * D` is impossible). The largest legal remainder is achieved at `r = 0.5 * D`, leaving `D - r = 0.5 * D`. Therefore liquidation is possible only when `0.5 * D >= floor`, i.e. `D >= 2 * floor`. Whenever `floor < D < 2 * floor`, no value of `amountToRepay_` satisfies both checks, and every call to `liquidate` reverts for any liquidator, any `depositToken_`, and any point in time — a complete, permanent DoS of the liquidation path for that position.

An unprivileged attacker can manufacture such a position using only public entry points: `DepositToken.deposit(amount, attacker)` to post collateral [4](#0-3) , then `SyntheticToken.mint`/`DebtToken.issue` to open a debt sized inside the forbidden band (e.g. `D = 1.5 * floor`). The position drifts unhealthy through ordinary interest accrual in `DebtToken.accrueInterest` or a collateral price drop — no privileged action and no oracle manipulation is required. Once `_isHealthy == false`, `debtPositionOf` is satisfied [5](#0-4) , but the band logic guarantees every subsequent `liquidate` reverts.

### Impact Explanation
The liquidation liveness invariant breaks: a whole class of underwater positions is permanently unliquidatable. Because interest continues to accrue on the stuck debt while collateral cannot be seized, the position degrades into protocol insolvency (bad debt backed by insufficient collateral), exactly the "complete DOS" impact of the reference advisory translated to the lending-liquidation surface. It also directly contradicts the stated purpose of `debtFloorInUsd`, which exists to keep positions economically liquidatable [6](#0-5) .

### Likelihood Explanation
Only public, unprivileged calls are needed: deposit collateral, mint a synth debt in the `(floor, 2*floor)` band, and wait for the position to become unhealthy via interest accrual or any downward collateral move. The condition depends only on `debtFloorInUsd > 0` and `maxLiquidable < 1e18`, both of which are normal deployed configurations (`maxLiquidable` defaults to 50% at initialization [1](#0-0) ). `nonReentrant`, `whenNotShutdown`, and the token-existence modifiers do not mitigate the arithmetic deadlock. The one caveat is that `debtFloorInUsd` is governor-configured, so the finding applies on deployments where a nonzero floor is set (the intended production configuration of this feature).

### Recommendation
Resolve the floor check against `maxLiquidable` instead of rejecting the repayment outright. Two equivalent options:

- When `D <= 2 * floor` (or more precisely when `D - maxLiquidable * D < floor`), allow a full liquidation by relaxing the `maxLiquidable` cap, i.e. permit `amountToRepay_ == D` so the remainder is `0` and the floor check passes at `Pool.sol:571-578`.
- Alternatively clamp `amountToRepay_` so that the remaining debt is either `0` or `>= debtFloorInUsd`, and have `quoteLiquidateMax` return `D` whenever the capped remainder would violate the floor [7](#0-6) .

### Proof of Concept
Hardhat fork sketch (deployed `Pool`, `DepositToken`, `msUSD` debt token, `debtFloorInUsd = F > 0`, `maxLiquidable = 0.5e18`):

```solidity
// 1. Attacker deposits collateral and mints debt D with F < D < 2*F
depositToken.deposit(collateralAmount, attacker);
msUSD.mint(attacker, D); // D = 1.5 * F, position is near-limit

// 2. Position turns unhealthy (interest accrual or collateral price drop)
debtToken.accrueInterest();
(bool healthy,,,,) = pool.debtPositionOf(attacker);
assert(!healthy);

// 3. Every liquidation attempt reverts
vm.expectRevert(AmountGreaterThanMaxLiquidable.selector);
pool.liquidate(msUSD, attacker, D, depositToken);        // r > 0.5*D rejected

vm.expectRevert(RemainingDebtIsLowerThanTheFloor.selector);
pool.liquidate(msUSD, attacker, D / 2, depositToken);    // remainder 0.5*D < F rejected

vm.expectRevert(RemainingDebtIsLowerThanTheFloor.selector);
pool.liquidate(msUSD, attacker, 1, depositToken);        // any partial remainder < F rejected
// Position is permanently unliquidatable -> bad debt accrues.
```
