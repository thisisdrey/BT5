## Analysis

The mechanics of the postponed-receipt/self-privilege gap are real: `check_actor_permissions` in `runtime/runtime/src/actions.rs:739-785` gates `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, and `DeleteAccount` purely on `actor_id == account_id` — a check derived from the receipt's own `predecessor_id`/`receiver_id` fields (`runtime/runtime/src/lib.rs:855`, `actor_id = receipt.predecessor_id().clone()`), not from any signature or access-key check re-verified at execution time. A stored postponed receipt with `predecessor_id == receiver_id == X` (a "self" receipt) will satisfy `actor_id == account_id` unconditionally, regardless of which account object currently lives at `X` in the trie. [1](#0-0) [2](#0-1) 

`remove_account` (`core/store/src/utils/mod.rs:504-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` — it never touches `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId`, all of which are account-scoped columns (`core/primitives/src/trie_key.rs:89-102`, `COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, 12 total, only 4 cleared). [3](#0-2) [4](#0-3) 

`action_create_account` (`runtime/runtime/src/actions.rs:167-210`) confirms this: it only checks naming rules (top-level length/registrar, or sub-account-of-predecessor) and unconditionally overwrites `*account` with a fresh zero-balance `Account`. It performs no scan for leftover postponed/yield state under the same account id. [5](#0-4) 

However, the "unrelated Y" framing does not hold for named sub-accounts: `action_create_account` requires `account_id.is_sub_account_of(predecessor_id)` for non-top-level ids, so a genuinely unrelated `Y` cannot re-create a sub-account previously owned by `A` unless `Y` is literally the same parent account `A` used originally — i.e., not "unrelated" for that class of account id. [6](#0-5) 

The only case where a truly unrelated party can create the exact same account id is a **long top-level account name** (length ≥ `min_allowed_top_level_account_length`, default 32), which any predecessor may create. [7](#0-6) [8](#0-7) 

For implicit accounts (NEAR-implicit hex ids), account re-creation via transfer always re-derives the `FullAccess` key from the account id's own hex bytes (`action_implicit_account_creation_transfer`), so the original key-holder always regains full control on re-creation regardless of any postponed-receipt trick — this path is not a novel escalation, it's inherent to implicit-account design.

I was not able to fully trace, within the remaining budget, whether `validate_receipt`/`validate_action_receipt` or any other check at either receipt-creation time or delivery time independently blocks self-privileged actions (e.g. `AddKey`, `DeployContract`) sitting in a `PostponedReceipt`/`PromiseYieldReceipt` slot from executing after the underlying account has been deleted and recreated by an unrelated top-level creator — nor did I find a test exercising exactly this cross-deletion sequence, so I cannot confirm the full exploit chain compiles/executes as described without an actual runtime-test-loop run. The `remove_account` gap itself, and the actor-permission check being purely `predecessor_id == receiver_id`-based, are both confirmed facts in the code; the reachability specifically requires the target account id to be a **long top-level name** (not an arbitrary "unrelated Y can grab any X" scenario), which substantially narrows — but does not eliminate — the real-world scope.

Given the confirmed code-level gap (no cleanup of `PostponedReceipt`/`PromiseYieldReceipt` family on account deletion, combined with re-creation being possible for long top-level accounts by any party) and the concrete authorization-bypass mechanism (`actor_id == account_id` check trusting receipt fields, not current key ownership), this constitutes a legitimate finding, though scoped narrower than the prompt's "any unrelated attacker Y can grab any deleted named account" framing.

### Title
Stale self-privileged postponed/yield receipts survive `DeleteAccount` and execute with full self-authority against a re-created top-level account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` deletes only 4 of the 12 account-scoped trie columns (`Account`, `ContractCode`, `AccessKey`/gas keys, `ContractData`), leaving `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` intact. If the deleted account id is a long top-level account name, any other unrelated party can immediately recreate the same account id, and a previously-authorized self-privileged receipt (predecessor==receiver==X, containing actions like `AddKey`/`DeployContract`) can later be released by its missing input data and execute against the new owner's account, because `check_actor_permissions` only compares `actor_id == account_id` derived from the stale receipt's own fields — it never re-validates that the account is still the same one that authorized the pending action.

### Finding Description
1. Attacker `A` creates a long top-level account `X` (`action_create_account`, `runtime/runtime/src/actions.rs:167`) — permitted for any predecessor once `X.len() >= min_allowed_top_level_account_length` (default 32, `core/parameters/res/runtime_configs/parameters.yaml:31`).
2. `A` adds a full-access key to `X` and deploys/calls a contract on `X` that issues a self-receipt (`predecessor_id == receiver_id == X`) containing a privileged action such as `AddKey(A's public key, FullAccess)`, with an unmet `input_data_id` (e.g. a pending cross-contract callback or explicit `yield`). This gets persisted as `TrieKey::PostponedReceipt`/`PromiseYieldReceipt` plus `PendingDataCount`/`PostponedReceiptId` (`runtime/runtime/src/lib.rs:1593-1655`, `process_action_receipt`).
3. `A` deletes `X` (`DeleteAccountAction`, `runtime/runtime/src/actions.rs:314`, calling `remove_account`). `remove_account` (`core/store/src/utils/mod.rs:504`) removes the `Account`/`ContractCode`/keys/`ContractData` rows only — the postponed/yield receipt rows for `X` remain in the trie.
4. Unrelated `Y` creates the same top-level name `X` again (now absent from state) via `CreateAccount`, funds it, adds its own key.
5. `A` (who still controls the sending side of the pending cross-contract call/yield) delivers the missing `DataReceipt`/`PromiseResume`. `process_receipt` (`runtime/runtime/src/lib.rs:1367-1455`) finds the matching `PostponedReceiptId`, decrements `PendingDataCount` to 0, fetches the stale `PostponedReceipt` and executes it via `apply_action_receipt`.
6. Inside `apply_action_receipt`, `actor_id` is initialized straight from `receipt.predecessor_id()` (`runtime/runtime/src/lib.rs:855`), i.e., `X` itself (from the old receipt). `check_actor_permissions` (`runtime/runtime/src/actions.rs:739`) allows `AddKey`/`DeployContract`/etc. because `actor_id == account_id` trivially holds — with no re-check that this is the *same* logical account that authorized the receipt, nor any check against `Y`'s current keys or signature.
7. Result: `A`'s stale privileged action (e.g., adding `A`'s key with `FullAccess`) executes on `Y`'s freshly created and funded account `X`.

### Impact Explanation
This is an authorization-escalation-across-accounts bug: a stranger's newly created account inherits and executes a previous, unrelated owner's pending self-privileged receipt without any fresh signature or consent from the new owner. Concretely this can grant the original owner (`A`) a full-access key or arbitrary contract code on `Y`'s account, enabling theft of `Y`'s subsequently deposited funds — matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Exploitability is real but narrow: it requires (a) the target account id to be a long top-level name (≥ `min_allowed_top_level_account_length`), so it is creatable by anyone, and (b) precise timing — `A` must arrange for the postponed receipt to remain unresolved across the `DeleteAccount` action and only deliver the missing data after `Y` recreates the exact same name. For ordinary named sub-accounts (the vast majority of real accounts, e.g. `*.near`), `Y` cannot recreate `A`'s deleted sub-account unless `Y` is the same parent account, which defeats the "unrelated Y" premise. The attack is entirely self-inflicted by `A` targeting a specific top-level name and hoping/inducing `Y` to claim it — feasible as a griefing/targeted attack against a specific desirable top-level name, but not a general "any deleted account is unsafe to reuse" vulnerability.

### Recommendation
`remove_account` (or `action_delete_account`) should also purge all remaining account-scoped columns for the deleted `account_id` — `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` — mirroring the full `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` set, or alternatively make account re-creation always increment an epoch/generation counter that stale receipts are validated against before execution.

### Proof of Concept
Runtime/test-loop integration test:
1. Create top-level account `x` (length ≥ configured minimum) via `A`; add full access key for `A`.
2. From `x`, issue a self action-receipt with `input_data_ids = [d]` and an `AddKey` action for `A`'s alternate key; confirm it is stored as `TrieKey::PostponedReceipt`.
3. `A` deletes `x` (beneficiary `A`); assert `get_account(x)` is `None` but `get_postponed_receipt(x, receipt_id)` still returns `Some`.
4. `Y` (unrelated signer) creates `x` again, funds it, adds `Y`'s own key.
5. Deliver the `DataReceipt` for `d`.
6. Assert the postponed `AddKey` executes successfully against `x` and `A`'s key is now present with `FullAccess` on `Y`'s account — without any signature or approval from `Y`.
