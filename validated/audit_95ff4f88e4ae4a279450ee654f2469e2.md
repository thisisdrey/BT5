### Title
Partial state commitment in `liquidate-multi` leaves vault debt reduced while borrower's ledger and liquidator's collateral payout are never applied - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The reported Solana bug is a class of "operation partially executes and mutates protocol state even though the overall action is reported/treated as failed," leaving the system's bookkeeping (nonce) permanently desynchronized from reality. The same failure class exists in `liquidate-multi`, which explicitly does not propagate per-position failures to the outer transaction, allowing a debt-repayment side effect on the vault to persist while the corresponding borrower-ledger update and collateral payout are dropped.

### Finding Description
`liquidate-multi` calls `call-liquidate` for each position via `map`, and always returns `(ok (map call-liquidate positions))` regardless of whether individual `liquidate` invocations return `ok` or `err`: [1](#0-0) 

Inside `liquidate`, `vault-system-repay` (a cross-contract call to the debt vault) executes and commits — transferring the liquidator's debt tokens into the vault and reducing the vault's tracked outstanding debt/principal — *before* the borrower's on-chain obligation ledger is updated and before collateral is paid out: [2](#0-1) 

Because each `contract-call?` in Clarity is only rolled back if *that specific call* returns `(err ...)`, a successful `vault-system-repay` call's effects are committed to state as execution proceeds. If a subsequent step in the same `liquidate` invocation — `debt-remove-scaled` or `collateral-remove` on `.v0-market-vault` — fails and causes `liquidate` to short-circuit via `try!` and return `(err ...)`, only that failing sub-call's own writes are discarded. The `vault-system-repay` effect that already succeeded earlier in the same call is **not** undone, because `liquidate` is invoked directly (not via `contract-call?`) from `call-liquidate`, and the overall transaction (`liquidate-multi`) still returns `(ok ...)` at the top level, which is what ultimately determines whether the whole transaction commits.

The result: the vault's `total-borrowed`/`principal-scaled` is reduced (as if the debt was repaid), the liquidator's tokens are consumed, but `market-vault`'s per-borrower scaled-debt record is left untouched and no collateral is transferred to the liquidator for that "failed" position — exactly analogous to the reported bug where the withdrawal's real-world effect proceeds/fails independently of whether the counter that is supposed to track it (nonce in Solana; per-user debt ledger and vault total-borrowed here) gets updated in lockstep.

### Impact Explanation
This creates a permanent desynchronization between (a) the vault's tracked total-borrowed (reduced) and (b) the sum of `market-vault` per-user scaled debts (unchanged) for the affected borrower. This divergence:
- Permanently understates system-wide debt relative to the vault's real backing, which is a protocol-insolvency-class accounting corruption (Critical), since it can be repeated across `liquidate-multi` batches by any unprivileged caller who crafts a batch entry designed to succeed at the repay step and fail at the subsequent ledger-update step (e.g., by targeting a stale/insufficient collateral amount for `collateral-remove`, or a scaled-debt mismatch for `debt-remove-scaled`).
- Also results in the liquidator's funds being consumed by `vault-system-repay` without receiving any collateral in return for that specific position — a direct loss of user (liquidator) funds for that call.

### Likelihood Explanation
Reachable by any unprivileged principal by calling the public `liquidate-multi` entry point with a batch that includes at least one position engineered so that `vault-system-repay` succeeds but the following `debt-remove-scaled`/`collateral-remove` step fails (both are ordinary, reachable error conditions such as amount/collateral mismatches). No DAO compromise, oracle manipulation, or privileged access is required — only crafting of the `debt-amount`/`min-collateral-expected` inputs of one position in the batch.

### Recommendation
In `liquidate-multi`/`call-liquidate`, ensure each per-position liquidation is executed with true atomicity: either invoke each `liquidate` call through a mechanism that guarantees full rollback of all of its cross-contract effects on failure (e.g., by having `call-liquidate` call `liquidate` through an actual `contract-call?` boundary so a failing `liquidate` rolls back everything it did, including the `vault-system-repay` step), or reorder `liquidate`'s internal logic so all validations/ledger updates that can fail occur before any externally-committing `vault-system-repay` call, so a later failure cannot leave a dangling committed vault-side effect.

### Proof of Concept
Not directly executable without a live/local Clarinet environment; the mechanism is derivable purely from source and Clarity's `contract-call?` semantics (each cross-contract call commits its own state independently once it returns `ok`, and is only rolled back by a failure of that same call — not by a later failure elsewhere in the same top-level call, as long as the top-level transaction itself resolves to `ok`):
1. Attacker/liquidator crafts a `liquidate-multi` batch with one position where `debt-amount`/collateral values are chosen so `vault-system-repay` succeeds (valid debt asset/amount/ft) but `collateral-remove` on `.v0-market-vault` fails (e.g., collateral already reduced or removed by a preceding position in the same batch, or `min-collateral-expected`/mask state causing `remove-user-collateral`'s `ERR-INSUFFICIENT-COLLATERAL`).
2. Submit `liquidate-multi`; it returns `(ok (list ... (err ...) ...))` — a top-level success.
3. Observe on-chain: the debt vault's `total-borrowed`/`principal-scaled` decreased (debt repaid), the liquidator's debt-ft balance decreased, but `market-vault`'s scaled-debt entry for the borrower is unchanged and no collateral was transferred to the liquidator for that position. [2](#0-1) [1](#0-0) 

**Uncertainty note:** I could not run the Clarinet test suite to empirically confirm the exact Clarity `contract-call?` rollback granularity used above (i.e., that a successful nested `contract-call?`'s effects survive a later, unrelated `try!` failure within the same enclosing function as long as the top-level transaction returns `ok`). This is standard documented Clarity VM behavior, but the repo's own test suite (`local-testing/tests/security/*`) does not appear to contain a test specifically exercising this `liquidate-multi` partial-failure path, so this should be validated with a Clarinet-based PoC before treating it as conclusively confirmed.
