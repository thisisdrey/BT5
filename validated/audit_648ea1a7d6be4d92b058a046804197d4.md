### Title
Shared Static `PrecompiledContract` Singletons Retain Stale Per-Call Caller/Repository/Result Context Across Concurrent Transaction Executions - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts` declares its non-constant-call precompile instances (`RewardBalance`, `IsSrCandidate`, `VoteCount`, `ResourceV2`, `DelegatableResource`, `CheckUnDelegateResource`, `TotalResource`, `ValidateMultiSign`, `BatchValidateSign`, etc.) as `private static final` singletons that live for the whole process lifetime. Each invocation of a precompile mutates per-call state directly on that shared object (`callerAddress`, `deposit`/`Repository`, `result`, `isConstantCall`, `vmShouldEndInUs`) instead of using an isolated, per-execution object. This is the same root-cause pattern as the ViewComponent advisory: a reused, mutable "execution context holder" whose request/caller-scoped fields are set with plain setters and never isolated between invocations.

### Finding Description
`Program.callToPrecompiledAddress` resolves the precompile via `PrecompiledContracts.getContractForAddress(codeAddress)` and, for **non**-constant calls, receives the shared static singleton directly (only constant calls get a freshly reflective-instantiated copy via `getOptimizedContractForConstant`): [1](#0-0) 

Right before executing, the caller mutates the shared instance's fields in place: [2](#0-1) 

Those fields are declared as plain (non-thread-local, non-volatile) instance fields on the abstract base class shared by every singleton (`ecRecover`, `sha256`, `rewardBalance`, `resourceV2`, `delegatableResource`, `checkUnDelegateResource`, `validateMultiSign`, `batchValidateSign`, ...): [3](#0-2) [4](#0-3) 

Only the *constant-call* path clones a fresh instance per call: [5](#0-4) 

For real (state-changing, block/mempool-applied) `TriggerSmartContract` execution — reachable from any signed transaction broadcast by an unprivileged sender that calls a contract executing a `CALL`/`STATICCALL`/`DELEGATECALL` opcode against one of these precompile addresses — the process never gets a fresh instance; it always reuses the module-wide singleton and stomps its `callerAddress`, `deposit` and `result` fields. Root repository/VM per-transaction objects (`VMActuator`, `RepositoryImpl.createRoot`, `Program`) are correctly created fresh per transaction (see `ActuatorCreator.getActuatorByContract`, `VMActuator.validate`), but `PrecompiledContracts`'s static instances break that isolation for exactly the same reason the ViewComponent advisory describes: mutable "render/execution" state stored with plain setters (`||=`-equivalent overwrite) on an object whose lifetime spans many unrelated calls. [6](#0-5) [7](#0-6) 

If any two executions of the same precompiled address interleave on different threads (e.g., mempool/broadcast transaction processing thread vs. the SR block-generation thread, or two concurrently-processed transactions during pending-pool validation), one execution's `setCallerAddress`/`setRepository`/`setResult` calls can be overwritten by the other before `execute(data)` reads them, so a transaction can execute a resource/vote/delegation precompile using another transaction's caller address, `Repository` (deposit), or `ProgramResult` object.

### Impact Explanation
Because the affected precompiles read and write account-scoped resource/voting/delegation state directly through the injected `Repository` (`ResourceV2`, `DelegatableResource`, `CheckUnDelegateResource`, `TotalResource`, `RewardBalance`, `VoteCount`), a stale-context race can:
- Cause a precompile to answer resource/delegation/reward queries for the wrong address (the previous caller), letting a downstream contract make an incorrect authorization decision (e.g., approve an unfreeze/undelegate/withdraw based on another account's frozen balance), a concrete "unauthorized account operation" per policy.
- Cause `ProgramResult`/log data intended for one transaction to be written into another transaction's receipt object, corrupting transaction results/logs on the affected node.
- If the mutated `Repository` object itself is swapped mid-execution, subsequent `commit()`/`putAccountValue` calls in one transaction's execution could operate against a different transaction's cache, risking incorrect balance/resource bookkeeping (potential unbacked balance or lost/duplicated freeze accounting) on the node that hits the race.

This is Medium severity: it requires a specific concurrency window rather than being deterministically triggerable by a single request, matching the CVSS AC:H characteristic of the original advisory.

### Likelihood Explanation
Reachability itself is trivial and unprivileged: any signed `TriggerSmartContract` transaction that calls a contract invoking `CALL`/`STATICCALL` to one of the affected precompiled addresses (freeze v2 / vote / reward precompiles, `ValidateMultiSign`, `BatchValidateSign`) drives this code path — no special privilege needed. What I could **not** fully verify from the indexed code within the available searches is the exact mutual-exclusion guarantee between the different threads that can call `processTransaction` (block application vs. mempool/broadcast transaction handling vs. re-push loop) in `Manager`; `Manager.java` does use thread-pool/executor constructs, but I was unable to confirm within budget whether a single global lock always serializes every `processTransaction`/VM-execution call against every other one. If such serialization exists everywhere the shared precompile singletons can be reached, actual exploitability is reduced to any code path that is *not* covered by that lock (e.g., pending-pool re-validation running in parallel with block generation). This should be verified directly in the repository (locking around `pushTransaction`, `generateBlock`, and the re-push loop in `Manager`) before treating this as fully confirmed exploitable in production.

### Recommendation
- Stop sharing mutable `PrecompiledContract` instances for the non-constant-call path: construct a fresh instance per invocation (the same way `getOptimizedContractForConstant` already does for constant calls), or make `callerAddress`, `deposit`, `result`, `isConstantCall`, and `vmShouldEndInUs` per-call parameters passed into `execute(...)` instead of instance state set via setters.
- Alternatively, if the singletons must remain to avoid extra allocation, guard `getContractForAddress`'s returned instance so all per-call mutation and execution happens atomically (e.g., synchronize the setter+execute sequence per address, or store the per-call context in a `ThreadLocal`/parameter object) so concurrent executions can never observe each other's `callerAddress`/`deposit`/`result`.
- Add a concurrency test that concurrently drives two different callers through the same precompiled address (e.g., `ResourceV2`, `RewardBalance`) and asserts each execution only ever observes its own caller/repository/result, mirroring the "no pollution on thread reuse" tests already present elsewhere in the codebase (`JsonFormatInt64AsStringTest.noPollutionOnThreadReuse`, `VMConfigIsolationTest`).

### Proof of Concept
Root-cause code path (concrete file/method support):
1. `Program.callToPrecompiledAddress` fetches the *shared* singleton for non-constant calls and mutates it: `contract.setCallerAddress(...)`; `contract.setRepository(deposit)`; `contract.setResult(this.result)`; `contract.execute(data)` — `actuator/src/main/java/org/tron/core/vm/program/Program.java:1741-1758`.
2. `PrecompiledContracts` defines these targets as static final singletons for the whole JVM lifetime, e.g. `resourceV2`, `delegatableResource`, `checkUnDelegateResource`, `rewardBalance` — `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:109-131`.
3. `PrecompiledContract` base class stores `callerAddress`/`deposit`/`result` as plain mutable instance fields with public setters and no synchronization or per-call isolation — `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:440-467`.
4. Only the constant-call branch avoids this by cloning a fresh instance via reflection — `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:215-222` — confirming the maintainers already recognize per-call isolation is required for at least one call path, but did not apply it to the state-changing path.

Conceptual PoC (would need to be validated in a running node/test harness, which I could not execute here): deploy two contracts A and B that both call a resource/voting precompile address (e.g., `ResourceV2`/`RewardBalance`) for two different owner addresses; submit transaction A to the mempool (broadcast) while a block-production thread concurrently executes a block containing transaction B that hits the same precompile address; assert (via receipt logs / resulting state) that A's precompile output is derived from B's caller/repository (or vice versa) when the two `execute()` calls interleave around the setter calls in `Program.callToPrecompiledAddress`. I was not able to run this against the live codebase to capture actual interleaved output, so this PoC is derived analytically from the code paths cited above rather than an observed run.
