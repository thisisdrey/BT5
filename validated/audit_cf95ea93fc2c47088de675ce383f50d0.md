### Title
`debt-add-scaled` refreshes the oracle-frontrunning guard (`last-borrow-block`) on any nonzero `scaled-amount`, letting an attacker perpetually shield an unhealthy position from liquidation with dust borrows - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`debt-add-scaled` unconditionally sets `last-borrow-block: stacks-block-height` whenever `scaled-amount > u0`, with no minimum economically meaningful threshold. Because the liquidation path relies on `last-borrow-block` as an oracle-frontrunning guard, an attacker can call `borrow` with the smallest possible amount every block to keep `last-borrow-block` equal to the current block indefinitely, at a cost bounded only by gas and the negligible principal borrowed, blocking liquidation of a position while its debt (and the protocol's bad-debt exposure) grows via interest accrual.

### Finding Description
In `mainnet/contracts/market/v0-market-vault.clar`, `debt-add-scaled` (lines 442-471) builds `updated-entry` with:
```
(updated-entry (merge entry { mask: update-mask, last-update: stacks-block-time, last-borrow-block: stacks-block-height }))
```
and the only preconditions checked before `insert` commits this are `check-impl-auth`, the `debt-add` pause flag, and `(asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)`. There is no minimum-scaled-amount, no minimum-token-value, and no rate limiting tied to the size of the borrow. The comment at line 448 ("Oracle frontrunning protection: record current block when borrowing") confirms `last-borrow-block` exists specifically to gate liquidation logic elsewhere (in the market implementation, `v0-4-market.clar`, which references `last-borrow-block` six times) so that a liquidator cannot liquidate in the same block a borrow was made (protecting against stale-oracle sandwiching).

Because the guard is refreshed by *any* nonzero `scaled-amount` — including sub-index-precision dust that rounds to a token amount far smaller than the interest accruing on the shielded debt — an attacker holding a position that is marginally healthy (per the question's precondition: `is-healthy-with-mask` remains true after adding 1 scaled unit) can call `borrow(ft, u1, none)` (or the smallest amount the market's scaling accepts) once every block. Each such call re-executes `debt-add-scaled` and resets `last-borrow-block` to the current block, so the same-block-anti-frontrunning check in the liquidation path never sees a stale `last-borrow-block`, and the position can never be liquidated as long as the attacker keeps repeating the call.

Existing checks that would normally stop griefing (pause flags, `check-impl-auth`, `ERR-AMOUNT-ZERO`, health checks) do not address this because: pause flags are a DAO lever not tied to amount size; `check-impl-auth` only restricts the caller to the market impl (which any user can invoke through the public `borrow` entrypoint); `ERR-AMOUNT-ZERO` only rejects exactly zero, not dust; and the health check is satisfied by design since the position is intentionally kept marginally healthy at borrow time even though it may become unhealthy shortly after due to price movement or interest accrual before the next dust-borrow refresh.

### Impact Explanation
This falls under **Critical - protocol insolvency**. A position that should be liquidatable (interest/price moving it underwater) can be kept perpetually shielded from liquidation for the cost of gas plus a token amount that rounds to dust, while the protocol continues to accrue bad debt against the shielded principal. If the shielded debt is large, the eventual unrecoverable shortfall (uncollateralized debt that could never be repaid via liquidation because liquidators were blocked) directly threatens protocol solvency.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: an ordinary Stacks principal only needs (1) an already-open position with debt and collateral such that adding 1 scaled unit keeps `is-healthy-with-mask` true, and (2) funds to pay gas plus the negligible token amount for each `borrow` call. The attack is fully repeatable every block for as long as the attacker is willing to pay gas, and it requires no privileged role, no oracle control, and no DAO/authorized-contract access — matching the in-scope unprivileged-attacker model. The capital outlay (K dust borrows) is asymptotically far smaller than the interest that accrues on the debt being shielded over the same K blocks, which is exactly the imbalance the SOLVENCY invariant flags.

### Recommendation
Decouple the anti-frontrunning `last-borrow-block` refresh from the ability to indefinitely block liquidation. Options: (a) only refresh `last-borrow-block` when the borrowed amount exceeds a protocol-defined minimum meaningful threshold (in real token terms, not scaled dust); (b) cap the anti-frontrunning protection window to reject liquidation only within the exact same transaction/block as the triggering borrow rather than "any borrow no matter how small refreshes it", e.g., track the guard per obligation update in a way that a trivial re-borrow cannot cheaply extend it every block; (c) impose a minimum borrow amount (in underlying token units, post-scaling) enforced in `debt-add-scaled` or in the market's `borrow` wrapper, sized relative to protocol economics so dust-borrow griefing is no longer near-free relative to the debt it protects.

### Proof of Concept
Clarinet/vitest simnet test plan:
1. Set up a funded market with one collateral asset and one debt asset; open a position for `attacker` with collateral sized so that current debt plus `u1` additional scaled debt keeps `is-healthy-with-mask` true, but the position would fail liquidation health checks if price moves adversely or interest accrues without the shield.
2. Move the price (or accrue interest across blocks) so that, absent the guard, the position would be liquidatable at block `N`.
3. For `K` blocks starting before block `N`, have `attacker` call `borrow(ft, u1, none)` (or minimal accepted amount) once per block, asserting via `get-position`/`resolve` that `last-borrow-block` equals `stacks-block-height` after each call.
4. Attempt liquidation each block from an unprivileged `liquidator` account; assert it fails due to the same-block/anti-frontrunning guard reading the just-refreshed `last-borrow-block`.
5. Read `get-index`/`get-debt` deltas on the vault across the `K` blocks to compute interest accrued on the shielded principal, and compare it against the attacker's total token outlay (K × dust borrow amount + gas), asserting the outlay is orders of magnitude smaller than the interest accrued — demonstrating the SOLVENCY invariant violation.
