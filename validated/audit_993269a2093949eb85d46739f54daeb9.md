### Title
Unbounded full-table scan in `AssetIssueStore.getAllAssetIssues()` reachable via unauthenticated wallet asset-name query APIs - (File: `chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java`)

### Summary
The GitLab CVE describes an unauthenticated project-search query causing full statement timeouts due to unbounded/expensive database scans, enabling DOS. The java-tron analog is the asset-issue lookup-by-name/pagination path, which loads and sorts the *entire* asset-issue table on every call rather than doing an indexed point lookup.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` iterates the full underlying RocksDB/LevelDB store and materializes every `AssetIssueCapsule` into a `List` on each invocation: [1](#0-0) 

`getAssetIssuesPaginated(offset, limit)` — used to serve pagination requests — calls `getAllAssetIssues()` first (full scan and full materialization into memory) and then sorts the entire in-memory list with a `toStringUtf8()` comparator before slicing out the requested page: [2](#0-1) 

This store is exposed through unauthenticated, publicly reachable HTTP/gRPC endpoints such as `/wallet/getassetissuebyname`, `/wallet/getassetissuelistbyname`, `/wallet/getassetissuelist`, and `/wallet/getpaginatedassetissuelist`, wired in `FullNodeHttpApiService`: [3](#0-2) 

and via gRPC in `WalletSolidityApi`/`WalletApi`: [4](#0-3) 

Each such request forces a full table scan, deserialization of every asset-issue record, and an O(n log n) sort — cost that grows linearly (or worse) with the number of on-chain assets, which is itself attacker-inflatable since asset issuance is a permissionless, low-cost operation.

### Impact Explanation
Because no authentication or per-object cost-bounding exists, and because any account can create new asset issuances cheaply, an attacker can both grow the dataset being scanned and repeatedly invoke the paginated/by-name asset endpoints to consume CPU and I/O, degrading node responsiveness for legitimate API/RPC callers — a resource-exhaustion condition analogous to the GitLab statement-timeout DOS. There is a global/per-servlet rate limiter (`RateLimiterServlet`, `reference.conf`'s `rate.limiter` block) that could mitigate but does not eliminate the underlying algorithmic cost per call: [5](#0-4) 

### Likelihood Explanation
Moderate-to-high: these are public, unauthenticated read endpoints with no per-request cost limits beyond generic global QPS defaults (`global.api.qps = 1000`), and the underlying data set size is attacker-influenceable via asset issuance. [6](#0-5) 

### Recommendation
Replace the full-scan-then-sort pagination with an indexed/sorted key-range query (e.g., store assets under a sorted-by-name key or maintain a secondary sorted index) so lookups and pagination do not require materializing and sorting the entire asset-issue table on every call. Additionally, apply tighter per-endpoint rate limits (`GetAssetIssueListServlet`, `GetPaginatedAssetIssueListServlet`, `GetAssetIssueByNameServlet`, `GetAssetIssueListByNameServlet`) via the existing `rate.limiter` configuration.

### Proof of Concept
1. Issue a large number of low-cost asset issuances (each `AssetIssueContract` transaction) to inflate the `asset-issue` store size.
2. Repeatedly call `/wallet/getpaginatedassetissuelist` or `/wallet/getassetissuelistbyname` (or the gRPC equivalents `GetPaginatedAssetIssueList`/`GetAssetIssueListByName`).
3. Each call triggers `AssetIssueStore.getAllAssetIssues()` — a full scan and in-memory sort of the entire table — observably increasing node CPU/latency proportional to asset count, degrading service for all other API clients.

Note: I was not able to fully trace the `Wallet.java` wrapper methods (`getAssetIssueByName`, `getAssetIssueListByName`, `getAssetIssueList`) within the remaining tool budget to confirm whether they all funnel through `getAllAssetIssues()`/`getAssetIssuesPaginated()` or use a more targeted lookup for the exact-name case; this should be verified in a follow-up session with full file access.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
