### Title
Unbounded in-memory buffering of attacker-controlled `git ls-remote` output enables remote-response memory-exhaustion DoS - ([File: internal/gitaly/service/remote/find_remote_repository.go])

### Summary
The reported OmniPortal bug is a "return bomb" gas-griefing pattern: an attacker controls the *size* of untrusted response data that a privileged executor (the relayer) must load into memory, and the executor fails to bound that size before buffering it, so a small attacker cost inflates the executor's resource cost disproportionately. The closest concrete analog in Gitaly is `RemoteService.FindRemoteRepository`, which lets an ordinary RPC caller supply an arbitrary remote URL and then slurps the *entire* `git-ls-remote` response from that remote into an unbounded `bytes.Buffer` before Gitaly does any validation.

### Finding Description
`FindRemoteRepository` takes a caller-supplied `remote` string with no scheme/host restriction and runs `git ls-remote <remote> HEAD`, capturing all stdout into a plain `bytes.Buffer` with `gitcmd.WithStdout(&output)`: [1](#0-0) 

`cmd.Wait()` blocks until the subprocess fully exits, meaning the entire ref advertisement returned by the remote endpoint must be written into the in-process buffer before Gitaly performs any size check or the trivial `bytes.Cut` parsing that follows: [2](#0-1) 

Unlike other places in the codebase that explicitly cap buffered data (e.g. `stderrBuffer` limiting subprocess stderr to `maxStderrBytes`/`maxStderrLineLength`, or `ReadObjectWithLimit` bounding object reads), no equivalent cap exists here for stdout of `git ls-remote`: [3](#0-2) [4](#0-3) 

Because the caller fully controls the `remote` field, the caller can point it at a remote endpoint they operate and craft an oversized `ls-remote` advertisement (arbitrary number/size of ref lines), just as the OmniPortal attacker controlled the size of an XCall's return data to grief the relayer that must load it before applying any length check.

### Impact Explanation
Each concurrent call can force Gitaly to allocate memory proportional to whatever size the caller's own remote endpoint chooses to return, with no upper bound enforced by Gitaly before or during the read. Multiple concurrent invocations (or a single very large response) can drive excessive memory allocation and processing time on the Gitaly node, causing service degradation or crash for the storage/service instance — a resource-exhaustion DoS of a handler, analogous to the return-bomb griefing that made XMsg execution unprofitable/DoS'd the OmniPortal relayer.

### Likelihood Explanation
The RPC is reachable by any client with normal Gitaly access needed to call `RemoteService`, requires only a single crafted request with an attacker-supplied `remote` value, and needs no privileged access, leaked token, or third-party MITM — the caller need only stand up (or already control) the endpoint referenced by `remote`. This keeps the same trust boundary as an ordinary user's crafted RPC field, consistent with the accepted "remote URL handling" analog category.

### Recommendation
Bound the size of data read from the `git ls-remote` subprocess before allocating in memory, e.g., wrap `gitcmd.WithStdout` with a size-limited writer (similar in spirit to `stderrBuffer` or `ReadObjectWithLimit`) that fails fast once a byte threshold is exceeded, and/or apply a hard timeout and byte cap on the underlying `ls-remote` invocation. Consider validating/restricting the `remote` field or requiring an allow-list for outbound remote operations where feasible.

### Proof of Concept
1. Stand up a git server (or any HTTP endpoint understood by git's `ls-remote` transport) that responds to a ref-advertisement request with an extremely large payload (e.g., millions of fabricated ref lines or a slow/huge chunked body).
2. Call Gitaly's `RemoteService.FindRemoteRepository` RPC with `remote` set to that endpoint's URL.
3. Observe that Gitaly's `git ls-remote` subprocess output is fully captured into an unbounded `bytes.Buffer` in `internal/gitaly/service/remote/find_remote_repository.go` before any length validation, causing outsized memory allocation on the Gitaly host; repeating the call concurrently amplifies memory/CPU pressure on the node.

```go
func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
	if err != nil {
		return nil, structerr.NewInternal("error executing git command: %w", err)
	}

	if err := cmd.Wait(); err != nil {
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}

	// The output of git-ls-remote is expected to be of the format:
	//
	//	58fbff2e0d3b620f591a748c158799ead87b51cd	HEAD\n
	objectID, refname, ok := bytes.Cut(output.Bytes(), []byte("\t"))
	if !ok {
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}

	// We've asked for HEAD, so the refname should match that.
	if !bytes.Equal(refname, []byte("HEAD\n")) {
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}
```
