## Analysis

I traced the exact code path in `stackslib/src/net/api/postblock_v3.rs` and `stackslib/src/net/relay.rs`. The claimed equality holds — confirmed as a real vulnerability.

**Auth gate (`try_parse_request`)**: Authentication is only enforced when `broadcast=1` is present in the query string. With no `broadcast` param, `authenticated` stays `false`, `broadcast` stays `false`, and the request passes with no auth header at all. [1](#0-0) 

**Relay decision (`try_handle_request`)**: `self.broadcast.unwrap_or(false)` is passed into `process_new_nakamoto_block_ext` only as the `force_broadcast` argument, but the actual relay call afterward is gated *solely* on `data_resp.accepted`, which is derived from `accepted.is_accepted()` — completely independent of `self.broadcast`. [2](#0-1) 

**`force_broadcast` only affects the "already have this block" branch** — it makes `process_new_nakamoto_block_ext` return `Accepted` instead of `AlreadyStored` for a block the node already has, purely so a legitimate re-broadcast can be forced. [3](#0-2) 

For a genuinely *new* block, `force_broadcast` is never referenced again in the rest of the function — acceptance is determined purely by consensus validation (`NakamotoChainState::accept_block`), and `Accepted` is returned identically whether `force_broadcast` is `true` or `false`. [4](#0-3) 

So the equality is verified: `data_resp.accepted == true` unconditionally triggers `node.set_relay_message(...)`, regardless of `self.broadcast`/auth state. The `broadcast`+auth gate in `try_parse_request` does not actually gate the relay decision in `try_handle_request` — it is dead as an access-control mechanism for the relay side-effect.

However, the impact is bounded by the fact that `accepted == true` still requires the block to pass `NakamotoChainState::accept_block`, which performs full consensus validation including signer-signature verification (consensus block-validation internals, explicitly out of scope for forging analysis). An attacker cannot get an arbitrary/forged block accepted; they can only cause an already validly-signed Nakamoto block to be relayed network-wide through an endpoint whose documented contract (see `docs/rpc/openapi.yaml`, "Authentication only required when broadcast=1") says relay requires authentication. [5](#0-4) 

### Title
Unauthenticated `broadcast` gate bypass causes unconditional P2P relay in `RPCPostBlockRequestHandler::try_handle_request` - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
The `/v3/blocks/upload/` endpoint requires an `Authorization` header only when `broadcast=1` is set, intending that unauthenticated uploads are stored locally but never pushed onward to peers. In practice, the relay call `node.set_relay_message(...)` fires whenever `data_resp.accepted` is `true`, with no reference to `self.broadcast` or authentication state, so the auth-gated `broadcast` flag has no effect on whether the block is actually relayed.

### Finding Description
`try_parse_request` computes `broadcast`/`authenticated` and rejects the request with `401` only if `broadcast && !authenticated`; with no `broadcast=1` query param, no header is required at all. [1](#0-0) 

`try_handle_request` then calls `Relayer::process_new_nakamoto_block_ext(..., self.broadcast.unwrap_or(false))`, and unconditionally relays whenever `data_resp.accepted`:
```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
``` [6](#0-5) 

Inside `process_new_nakamoto_block_ext`, the `force_broadcast` parameter (fed by `self.broadcast`) is only consulted in the "we already have this block" short-circuit, to decide whether to report `Accepted` (enabling re-broadcast) versus `AlreadyStored`. For any block the node does *not* already have, `force_broadcast` is never read again; acceptance is decided purely by consensus checks (`static_check_problematic_relayed_nakamoto_block`, `NakamotoChainState::accept_block`), and `Accepted` is returned the same way regardless of the flag's value. [3](#0-2) [4](#0-3) 

Root cause: the auth-gated `broadcast` flag is threaded through only as `force_broadcast` (a dedup-override signal), not as an actual relay-authorization signal at the HTTP layer. `try_handle_request`'s relay decision should have been `if data_resp.accepted && self.broadcast.unwrap_or(false)`, matching the documented API contract in `docs/rpc/openapi.yaml`. [5](#0-4) 

### Impact Explanation
Any unprivileged remote party who can reach a node's RPC port and possesses a validly-signed `NakamotoBlock` (obtained by any means — e.g., overheard on the network, from a node's own storage, or a block deliberately withheld by its original holders) can force that node to push it to all of its P2P peers via `node.set_relay_message`, with zero authentication and no `broadcast=1` parameter. This is repeatable per distinct new block and defeats the node operator's intended access control that only credentialed callers may command relay. It matches the Critical category "unauthenticated/unauthorized ... network-wide propagation of ... data," since the relay authorization the API documents and the code superficially implements is not actually enforced.

### Likelihood Explanation
Preconditions: the target node has `self.auth = Some(password)` configured (RPC secret set) and exposes `/v3/blocks/upload/` (default enabled RPC endpoint). Attacker cost is a single unauthenticated HTTP POST with a valid, consensus-acceptable `NakamotoBlock` body — no password, no `broadcast` query param needed. This is fully remotely reachable and repeatable for every new block the attacker can supply.

### Recommendation
Gate the relay call in `try_handle_request` on `self.broadcast.unwrap_or(false)` in addition to `data_resp.accepted`, e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
This restores the intent that only authenticated callers requesting `broadcast=1` can trigger network-wide relay of an uploaded block.

### Proof of Concept
In `stackslib/src/net/api/tests/postblock_v3.rs`, extend `handle_req_accepted`-style test:
1. Configure `RPCPostBlockRequestHandler::new(Some("12345".to_string()))` (auth secret set).
2. Build `StacksHttpRequest::new_post_block_v3(addr.into(), &next_block)` (no `broadcast=1`, no `authorization` header) — confirm `try_parse_request` succeeds and `handler.broadcast == Some(false)`.
3. Run `try_handle_request` via `TestRPC` harness; assert response `accepted == true`.
4. Assert that `node.set_relay_message` was invoked (inspect the network's queued relay message / `StacksNodeState` after the call) with a `StacksMessageType::NakamotoBlocks` containing `next_block`, proving relay occurred despite `self.broadcast == Some(false)` and no auth header — i.e., the assertion `relay_message.is_some()` should fail if the gate is fixed, and currently succeeds, confirming the bypass.
