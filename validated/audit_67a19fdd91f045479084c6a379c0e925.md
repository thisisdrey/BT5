### Title
Unbounded client-streamed bundle data allows disk exhaustion via FetchBundle - (File: internal/gitaly/service/repository/fetch_bundle.go)

### Summary
`FetchBundle` reads an attacker-controlled client stream via `streamio.NewReader` and feeds it directly into `createTempBundle`'s `io.Copy(file, reader)` with no maximum size enforced anywhere in the call path, before any bundle-format or content validation occurs.

### Finding Description
`FetchBundle` (`internal/gitaly/service/repository/fetch_bundle.go:23-31`) builds a `streamio.Reader` closure that calls `stream.Recv()` repeatedly until EOF/error, with no byte-count tracking. This reader is passed to `repo.FetchBundle` (`internal/git/localrepo/bundle.go:155-193`), which calls `createTempBundle` (`internal/git/localrepo/bundle.go:198-223`). There, `io.Copy(file, reader)` (line 217) writes every byte received directly to a temp file under `repo.GetStorageName()`'s tempdir with no size cap. No `grpc.MaxRecvMsgSize` is configured (confirmed no matches for `MaxRecvMsgSize`/`MaxCallRecvMsgSize` in the codebase), and the concurrency `LimiterMiddleware` (`internal/grpc/middleware/limithandler/middleware.go:118-170`) only rate-limits *stream initiation* (checked once via `w.initial`), not per-stream byte volume. Bundle format validation via `git bundle list-heads`/`git-fetch` only happens after the entire stream has been drained to disk. The identical pattern exists in `CreateRepositoryFromBundle` (`internal/gitaly/service/repository/create_repository_from_bundle.go:27-38`).

### Impact Explanation
An authenticated, unprivileged user who can invoke `FetchBundle` on a repository they control can stream indefinitely, filling the storage shard's temp directory and exhausting disk space (ENOSPC), which affects other repositories/tenants co-located on the same storage shard — a shared-infrastructure denial of service.

### Likelihood Explanation
Requires only a client-streaming gRPC connection to a repository the attacker can already reach (no special role, no config bypass). Fully repeatable and automatable; feasibility is high since it needs no crafted git object content, just continuous `Data` chunks.

### Recommendation
Enforce a maximum cumulative byte count in the `streamio.NewReader` closure (or via a wrapping counting reader) for `FetchBundle` and `CreateRepositoryFromBundle`, rejecting the stream once a configurable bundle-size ceiling is exceeded; alternatively use `io.CopyN` in `createTempBundle` with a hard limit, and/or enforce request/stream deadlines and per-connection message-size limits at the gRPC server level.
