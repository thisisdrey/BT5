Based on my investigation, this reflects a genuine gap in address-binding validation.

### Title
Pingback handshake accepts self-claimed `HandshakeData.addrbytes`/`port` without binding them to the dialed pingback address, allowing a peer to register a forged victim-address-to-attacker-key frontier entry - (File: stackslib/src/net/neighbors/walk.rs)

### Summary
`pingback_handshakes_try_finish` validates a `HandshakeAcceptData` reply only via `check_handshake_pubkey_hash`, which checks the responder's public key hash against the `NeighborAddress` the pingback was sent to, but never checks that `data.handshake.addrbytes`/`data.handshake.port` (self-claimed, attacker-controlled fields inside the signed payload) match the address that was actually dialed (`naddr`). This self-claimed address is what gets persisted to the PeerDB frontier via `Neighbor::load_and_update` -> `NeighborKey::from_handshake`.

### Finding Description
In `stackslib/src/net/neighbors/walk.rs`, `pingback_handshakes_begin` dials out to `naddr` (a `NeighborAddress` learned from a prior *inbound* connection's self-reported handshake, recorded in `network_pingbacks`/`walk_pingbacks`) via `self.comms.neighbor_session_begin(network, &naddr)` [1](#0-0) .

When the reply comes back in `pingback_handshakes_try_finish`, the code extracts `data: &HandshakeAcceptData` and computes `peer_nk` from `data.handshake.addrbytes`/`data.handshake.port` (the *self-claimed* address embedded in the just-received, attacker-signed payload), then only checks the public-key hash: `Self::check_handshake_pubkey_hash(&peer_nk, data, &naddr)` [2](#0-1) . That function compares `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key)` against `naddr.public_key_hash` only — it never compares `data.handshake.addrbytes`/`port` against `naddr.addrbytes`/`port` (the actually-dialed address) [3](#0-2) .

The reply is then passed straight to `add_or_schedule_replace_neighbor(network, &message.preamble, &data.handshake, db_data, ...)` [4](#0-3) , which calls `Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)` [5](#0-4) . `Neighbor::load_and_update` derives the stored key purely from the handshake payload: `let addr = NeighborKey::from_handshake(peer_version, network_id, handshake_data);` [6](#0-5) , and `NeighborKey::from_handshake` copies `handshake_data.addrbytes`/`handshake_data.port` verbatim [7](#0-6) . This is then inserted/updated in the PeerDB via `PeerDB::try_insert_peer`/`PeerDB::update_peer` [8](#0-7) .

By contrast, the analogous outbound-walk handshake path (`handle_handshake_accept`, used for `cur_neighbor` handshakes) explicitly checks `neighbor_from_handshake.addr != self.cur_neighbor.addr` and rejects mismatched claims (except for private-IP substitution) [9](#0-8) . No equivalent check exists in `pingback_handshakes_try_finish`, nor in `handle_neighbor_handshake_accept` (the "neighbors-of-neighbor" handshake path) — both trust the self-claimed `handshake.addrbytes`/`port` for what gets stored.

**Exploit flow:** An attacker makes an inbound connection to the victim node and completes a normal handshake, causing the node to schedule a pingback to the attacker's own reachable address (`schedule_network_pingbacks` in `p2p.rs`, using `convo.to_handshake_neighbor_address()`) [10](#0-9) . The node then dials back to that (attacker-reachable) address for the pingback probe. When the attacker replies to this probe with a `HandshakeAccept`/`StackerDBHandshakeAccept`, it signs a payload whose `HandshakeData.addrbytes`/`port` claim an arbitrary third-party (victim) IP/port instead of the address actually dialed. Since `check_handshake_pubkey_hash` only checks the pubkey hash (which legitimately matches, since the attacker owns that key) and never checks the claimed address against the dialed address, `add_or_schedule_replace_neighbor` persists a `Neighbor` row keyed by the victim's IP/port bound to the attacker's public key.

### Impact Explanation
This is an unauthenticated write of a forged address-to-pubkey binding into the local node's frontier/PeerDB (`Neighbor.addr` = victim IP/port, `Neighbor.public_key` = attacker's key). This poisons the peer's view of the network topology: subsequent walks may treat the victim's address as belonging to the attacker, potentially causing the node to attempt connections believing a legitimate victim IP hosts the attacker's key, degrading peer discovery integrity and potentially enabling further confusion/relay-based attacks. This matches the "unauthenticated/unauthorized write to state" Critical category. It is fully repeatable — the attacker can requeue itself for further pingbacks or open new inbound connections to trigger `schedule_network_pingbacks` again.

### Likelihood Explanation
Preconditions are modest: attacker only needs to be able to (a) make an inbound P2P connection to the target node and complete a normal handshake so that a pingback gets scheduled to an address it controls, and (b) reply to the resulting pingback handshake request with a crafted `HandshakeAcceptData` whose `handshake.addrbytes`/`port` differ from the dialed address. Both are within the unprivileged remote-peer threat model (no secrets, no special role, no local access needed). This makes the likelihood high given the attacker fully controls both the inbound handshake and the pingback-handshake reply content.

### Recommendation
In `pingback_handshakes_try_finish` (and similarly `handle_neighbor_handshake_accept`), verify that `data.handshake.addrbytes`/`data.handshake.port` equal the actually-dialed `naddr.addrbytes`/`naddr.port` (or the real connected socket address) before calling `add_or_schedule_replace_neighbor`, mirroring the check already done in `handle_handshake_accept` for `cur_neighbor`. Reject/log mismatches instead of persisting them, with the same private-IP substitution allowance if desired.

### Proof of Concept
Rust test plan in `stackslib::net::neighbors::walk` (or a new test module driving `pingback_handshakes_try_finish`):
1. Construct a `NeighborWalk` in `PingbackHandshakesFinish` state with `network_pingbacks`/comms simulating a pingback sent to `naddr` = `(attacker_ip, attacker_port)` with `naddr.public_key_hash` = attacker's pubkey hash.
2. Simulate a reply message whose `StacksMessageType::HandshakeAccept(data)` has `data.handshake.node_public_key` = attacker's real key (so `check_handshake_pubkey_hash` passes) but `data.handshake.addrbytes`/`port` set to a third-party victim IP/port (e.g. `10.0.0.99:12345`, distinct from `naddr`).
3. Call `pingback_handshakes_try_finish(&mut network)`.
4. Assert that `PeerDB::get_peer(conn, network_id, &victim_ip, victim_port)` returns `Some(neighbor)` with `neighbor.public_key` equal to the attacker's key — i.e., the frontier was poisoned with the victim's address bound to the attacker's key, despite the pingback having been dialed to `attacker_ip:attacker_port`, not `victim_ip:victim_port`.

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }
