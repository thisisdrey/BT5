The scheduling algorithm is specifically designed to prevent the described race. `ThreadAwareAccountLocks::try_lock_accounts` computes `accounts_schedulable_threads` for every account, intersecting the schedulable thread sets across all read/write accounts, before ever calling `thread_selector` [1](#0-0) . For a write lock that's already outstanding, `write_schedulable_threads` (via `schedulable_threads::<true>`) returns only the single thread currently holding that write lock — never "any" thread — so a second transaction writing to the same account A can only ever be assigned to the same thread that already holds the lock, not to an arbitrary/independent thread [2](#0-1) .

Concretely: `try_lock_accounts` first computes `schedulable_threads` from `accounts_schedulable_threads`, which already excludes any thread that doesn't hold the existing write lock, intersects that with `allowed_threads`, and only afterward invokes `thread_selector` on the (already-conflict-free) `schedulable_threads` set [3](#0-2) . The `thread_selector` (`select_thread` in `greedy_scheduler.rs`) has no ability to pick a thread outside that restricted set, so "thread_selector picks threads independently per transaction" as hypothesized in the question is not actually true — selection is constrained by the already-computed `schedulable_threads` bitmask [4](#0-3) .

Additionally, `GreedyScheduler::schedule` processes transactions from the container serially in a single loop (`while ... let Some(id) = container.pop()`), calling `try_schedule_transaction` synchronously one at a time against the single shared `self.common.account_locks` — there is no concurrency in the scheduling path itself that could allow two threads to race on the lock state [5](#0-4) . The existing unit tests (`test_schedule_single_threaded_conflict`, `test_accounts_schedulable_threads_outstanding_mixed`, `test_schedule_scan_past_highest_priority`) already directly assert that conflicting writers are pinned to a single thread and that a transaction depending on locks held on two different threads becomes unschedulable rather than being dispatched to a third thread [6](#0-5) [7](#0-6) .

No exploitable path exists for an unstaked attacker to force two `ConsumeWork` batches on different threads to hold conflicting write locks on the same account simultaneously — this is exactly the invariant the lock/thread-selection design enforces by construction, not something requiring an external rate-limit or QoS guard.

    pub fn try_lock_accounts<'a>(
        &mut self,
        write_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        read_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        allowed_threads: ThreadSet,
        thread_selector: impl FnOnce(ThreadSet) -> ThreadId,
    ) -> Result<ThreadId, TryLockError> {
        let schedulable_threads = self
            .accounts_schedulable_threads(write_account_locks.clone(), read_account_locks.clone())
            .ok_or(TryLockError::MultipleConflicts)?;
        let schedulable_threads = schedulable_threads & allowed_threads;
        if schedulable_threads.is_empty() {
            return Err(TryLockError::ThreadNotAllowed);
        }

        let thread_id = thread_selector(schedulable_threads);
        self.lock_accounts(write_account_locks, read_account_locks, thread_id);
        Ok(thread_id)
    }

    /// Returns `ThreadSet` of schedulable threads.
    /// If there are no locks, then all threads are schedulable.
    /// If only write-locked, then only the thread holding the write lock is schedulable.
    /// If a mix of locks, then only the write thread is schedulable.
    /// If only read-locked, the only write-schedulable thread is if a single thread
    ///   holds all read locks. Otherwise, no threads are write-schedulable.
    /// If only read-locked, all threads are read-schedulable.
    fn schedulable_threads<const WRITE: bool>(&self, account: &Pubkey) -> ThreadSet {
        match self.locks.get(account) {
            None => ThreadSet::any(self.num_threads),
            Some(AccountLocks {
                write_locks: None,
                read_locks: Some(read_locks),
            }) => {
                if WRITE {
                    read_locks
                        .thread_set
                        .only_one_contained()
                        .map(ThreadSet::only)
                        .unwrap_or_else(ThreadSet::none)
                } else {
                    ThreadSet::any(self.num_threads)
                }
            }
            Some(AccountLocks {
                write_locks: Some(write_locks),
                read_locks: None,
            }) => ThreadSet::only(write_locks.thread_id),
            Some(AccountLocks {
                write_locks: Some(write_locks),
                read_locks: Some(read_locks),
            }) => {
                assert_eq!(
                    read_locks.thread_set.only_one_contained(),
                    Some(write_locks.thread_id)
                );
                read_locks.thread_set
            }
            Some(AccountLocks {
                write_locks: None,
                read_locks: None,
            }) => unreachable!(),
        }
    }
