### Title
Integer truncation of untrusted `aux` offset in `debug/elf` GNU version-need parsing causes negative-index slice panic on 32-bit platforms - (File: src/debug/elf/file.go)

### Summary
`(*File).dynamicVersionNeeds` and `(*File).dynamicVersions` in `src/debug/elf/file.go` compute a byte offset `j := i + int(aux)` from an attacker-controlled `uint32` field taken directly from the ELF `SHT_GNU_VERNEED`/`SHT_GNU_VERDEF` section data, then bound-check with `if j+16 > len(d) { break }` before slicing `d[j+4:j+6]` etc. On 32-bit Go builds (`GOARCH=386`/`arm`), converting a `uint32` value ≥ `0x80000000` to `int` yields a negative number, so `j` becomes negative; the subsequent bounds check `j+16 > len(d)` is a no-op for negative `j` (since a large-negative int compares less than any non-negative `len(d)`), and execution falls through to slice with a negative index, causing a runtime panic. This is the direct Go analog of CVE-2017-15931's `store_versioninfo_gnu_verneed()` bug in radare2, which is caused by the identical pattern: an unchecked, attacker-controlled offset added to an index becoming negative and causing invalid access.

### Finding Description
Attacker input is a crafted ELF file with a `SHT_GNU_VERNEED` (or `SHT_GNU_VERDEF`) section containing an entry whose `aux` field (the `vn_aux`/`vd_aux` offset, read via `f.ByteOrder.Uint32(d[i+8:i+12])`) is set to a value ≥ `0x80000000`. This file is parsed via the public API entry points `(*File).DynamicVersionNeeds()` / `(*File).DynamicSymbols()` / `(*File).DynamicVersions()`, which call `gnuVersionInit` → `dynamicVersionNeeds`/`dynamicVersions`: [1](#0-0) 
Here `j := i + int(aux)` truncates/reinterprets the `uint32` as a 32-bit signed `int` on 386/arm builds, producing a negative `j`. The guard `if j+16 > len(d) { break }` fails to reject this because a very negative `j+16` is never greater than a non-negative `len(d)`, so the loop proceeds to `d[j+4:j+6]`, `d[j+6:j+8]`, `d[j+8:j+12]`, `d[j+12:j+16]`, all of which panic with "slice bounds out of range" for negative indices. The equivalent construction exists in `dynamicVersions` (verdef) at: [2](#0-1) 

### Impact Explanation
The result is an unrecovered runtime panic (denial of service) when parsing an attacker-supplied ELF binary on 32-bit Go builds — any tool built for `GOARCH=386`/`arm` that uses `debug/elf` to inspect an untrusted binary (e.g., build tooling, binary-analysis utilities, `go tool nm`/`objdump`-style consumers) can be crashed by a malformed input file. This does not corrupt memory (Go's bounds checking converts the C-style invalid memory access into a panic), so it is a availability/DoS issue, not memory corruption or code execution, and would fall under Go's PUBLIC track as a parser-panic-on-malicious-input bug specific to 32-bit architectures, mirroring the original CVE's own "on 32bit systems" scope.

### Likelihood Explanation
The victim workflow is any normal use of `debug/elf` to parse a third-party or user-supplied ELF file (a common and expected use case for this package, e.g. binary inspection tools) on a 32-bit host/target. The attacker only needs to supply a malformed ELF file; no privileges, network access, or trusted position are required.

### Recommendation
Add an explicit sanity check that `aux`/`next` offsets do not cause `j` to become negative or to overflow `int`, e.g. reject `aux`/`next` values greater than `len(d)` before converting to `int`/adding to the index, or perform the arithmetic in `uint64`/`uint` and only convert to a bounded `int` after validating `j >= 0 && j <= len(d)`.

### Proof of Concept
```go
package elf

import "testing"

// Simulates a crafted SHT_GNU_VERNEED section whose entry's "aux" field
// is >= 0x80000000, which becomes negative when converted to a 32-bit int.
func TestVerneedNegativeIndexPanic(t *testing.T) {
	// vers=1 (uint16), cnt=1 (uint16), fileoff=0 (uint32),
	// aux=0x80000000 (uint32, becomes negative int on 32-bit), next=0 (uint32)
	d := []byte{
		1, 0, // vers = 1
		1, 0, // cnt = 1
		0, 0, 0, 0, // fileoff = 0
		0, 0, 0, 0x80, // aux = 0x80000000
		0, 0, 0, 0, // next = 0
	}
	f := &File{FileHeader: FileHeader{ByteOrder: littleEndianData()}}
	// On GOARCH=386/arm, int(uint32(0x80000000)) < 0, causing j to be
	// negative; the bounds check `j+16 > len(d)` fails to catch it and
	// slicing d[j+4:j+6] panics with "slice bounds out of range".
	defer func() {
		if r := recover(); r == nil {
			t.Fatal("expected panic due to negative slice index on 32-bit int overflow")
		}
	}()
	_ = f.dynamicVersionNeedsForTest(d, nil) // hypothetical exported test hook
}
```
Note: reproducing the panic requires building/running with `GOARCH=386` (or another platform where `int` is 32 bits), since on 64-bit platforms `int(uint32(...))` is always non-negative and the bug is not triggered — matching the "32bit systems" constraint in the original CVE description.
