### Title
Same-key signature weight double-counted in `ValidateMultiSign` precompile due to byte-level (not address-level) duplicate check - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract sums the weight of every signature that recovers to a key contained in an account's `Permission`, in order to decide whether a threshold of signing weight has been met. The de-duplication logic that is supposed to prevent one key from being counted more than once only rejects an *exact byte-for-byte* repeat of a previously seen signature, not a repeat of the same recovered address. This mirrors the report's bug class ("vote"/weight counted multiple times because the check keyed on the wrong identity rather than the true voter/signer identity"), except here the "voter" is a signing key and the "vote" is its weight contribution to a multisig threshold, reachable by any contract caller through the `validatemultisign` precompile.

### Finding Description
`ValidateMultiSign.execute` iterates over the caller-supplied signature array and, for each signature, recovers the signing address, then decides whether to count its weight: [1](#0-0) 

The relevant logic is:
```java
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```

The "already seen" check only `continue`s (skips) the current signature when the *exact* `sign` bytes (recoveredAddr merged with the raw signature bytes) were already recorded. If `recoveredAddr` is already present in `executedSignList` but the current `sign` bytes are different from any signature already recorded for that address, the code falls through, recomputes `weight = TransactionCapsule.getWeight(permission, recoveredAddr)`, and adds it to `totalWeight` again. This means a single private key can have its permission weight counted more than once as long as the attacker can produce two distinct valid signature encodings that both recover to the same address for the same `hash` (e.g., via ECDSA signature malleability, where `(r, s)` and `(r, n-s)` with the flipped recovery id both validly recover to the same address for a given message hash).

This is directly analogous to the report's root cause: the consensus vote-counting code recorded "the public key of the node that is voting... but it is not used to prevent the same node from voting multiple times." Here, `checkWeight` in `TransactionCapsule` (used for normal transaction/permission validation) correctly deduplicates by the recovered *address*: [2](#0-1)  — throwing `"has signed twice!"` if the same address appears twice. `ValidateMultiSign`, however, deduplicates by the raw signature bytes instead of the recovered address, reintroducing the same class of flaw that `checkWeight` was designed to prevent.

### Impact Explanation
`ValidateMultiSign` is used by smart contracts to check whether enough weighted co-signers of a multisig `Permission` have approved an off-chain-signed action (the precompile is invoked by any TVM contract via a `STATICCALL`/`CALL`, reachable from any unprivileged contract deployer or caller who can trigger the contract). If a single key's weight can be counted multiple times by supplying malleable/duplicate-recovering signature byte strings, an attacker holding just one key (with weight less than the permission's threshold) can forge apparent multi-party approval and pass the `totalWeight >= permission.getThreshold()` check that legitimately requires multiple distinct co-signers. Any contract that relies on this precompile as an authorization gate for fund transfers, withdrawals, or privileged actions could therefore have its multisig protection bypassed by one attacker, leading to unauthorized account operations / theft of funds contingent on the specific contract's use of the precompile's result.

### Likelihood Explanation
Exploitation requires only: (1) a deployed contract that calls `validatemultisign` for authorization, (2) an attacker-controlled key that is one of the permission's keys but individually below threshold, and (3) the ability to produce a second distinct signature encoding for the same key/hash that still recovers to the same address (canonical ECDSA malleability techniques). No special privilege, staking, or committee/witness role is needed — it is reachable purely through crafting transaction input data to the precompile from ordinary contract calls, matching the allowed "TVM opcodes/precompiles" attack surface.

### Recommendation
Change the de-duplication check in `ValidateMultiSign.execute` to key off the recovered address alone (not the raw signature bytes), rejecting/skipping any second occurrence of the same `recoveredAddr` regardless of whether the accompanying signature bytes differ — consistent with the address-based dedup already implemented in `TransactionCapsule.checkWeight`. Additionally consider enforcing canonical/low-s signature form to reject the second malleable encoding outright before recovery.

### Proof of Concept
Conceptually:
1. Create an account with an Active `Permission` containing `keyA` (weight 1) and `keyB` (weight 1), threshold 2, as constructed in `ValidateMultiSignContractTest.testDifferentCase` (`framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java`).
2. Attacker controls only `keyA`.
3. Attacker signs `hash` with `keyA` to get `sigA1`, then derives a second distinct valid signature `sigA2` for the same `hash`/`keyA` using ECDSA malleability (flip `s -> n-s`, flip recovery id) so that `recoverAddrBySign(sigA2, hash) == recoverAddrBySign(sigA1, hash) == keyA`.
4. Call `validatemultisign(address, permissionId, hash, [sigA1, sigA2])`.
5. In `execute`, iteration 1 adds `keyA`'s weight (1) to `totalWeight` and records `sign1`. Iteration 2: `recoveredAddr` (`keyA`) is already in `executedSignList`, but `merge(keyA, sigA2)` differs from `merge(keyA, sigA1)`, so the inner `continue` is skipped; weight (1) is added again, making `totalWeight = 2 >= threshold(2)`, returning `DATA_ONE` even though only one distinct key actually approved.
