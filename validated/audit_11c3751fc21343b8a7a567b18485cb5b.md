### Title
Missing trailing-data check in `unmarshalCertificateV2` allows attacker-appended bytes to be silently accepted - ([File: cert/cert_v2.go])

### Finding Description
`unmarshalCertificateV2` opens the outer certificate envelope with `input.ReadASN1(&input, asn1.SEQUENCE)` and then re-uses the same `input` variable for both the receiver and the destination, so the variable is overwritten with the SEQUENCE's inner content, and the original byte string's continuation (anything after the outer TLV) is discarded without ever being checked: [1](#0-0) 

After that, the function sequentially reads `rawDetails`, the optional `curve`, the optional `publicKey`, and finally the `rawSignature` field out of `input`: [2](#0-1) 

but never calls `input.Empty()` (or equivalent) afterward before building and returning the certificate: [3](#0-2) 

Because the outer SEQUENCE's ASN.1 length field can be crafted by the attacker to include arbitrary extra bytes after the valid `TagCertSignature` TLV, those trailing bytes remain in `input` and are simply dropped when the function returns success. This is confirmed purely by reading the code — there is no `input.Empty()` check anywhere between reading the signature (line 615) and returning `c, nil` (line 638), unlike the analogous checks used elsewhere in the same file (e.g. `unmarshalDetails` also lacks a final `Empty()` check after reading the issuer field, but that's a separate instance of the same pattern).

Critically, `Fingerprint()` and `CheckSignature()` are computed only from `rawDetails`, `curve`, `publicKey`, and `signature` — none of which include the trailing junk bytes: [4](#0-3) [5](#0-4) 

So a byte-for-byte different input (valid cert + trailing garbage) parses successfully, passes signature verification, and produces the exact same `Fingerprint()`/logical identity as the original certificate, while the raw bytes differ.

### Impact Explanation
This breaks the "unknown/trailing fields must be rejected" fail-closed parsing invariant. The scoped, concrete impact is format/identity ambiguity: two distinct byte sequences are treated as the same logical, validly-signed certificate. This does not appear to break signature/CA verification itself (the signature check is fine and still requires a valid signature over the real fields), and I could not find, within this file or the ones inspected, any code path where the discarded trailing bytes are used to smuggle a second payload elsewhere in the handshake processing — that would require checking how `unmarshalCertificateV2`'s caller-provided length bounds interact with the surrounding handshake message parser, which was not available in the indexed context. Given the audit scope (attacker-presented certificate, no CA/key access), the most defensible impact is a parsing-strictness / format-confusion bug rather than a full authentication or decryption bypass.

### Likelihood Explanation
Trivial to trigger: any attacker who can present a certificate to a node (e.g. during handshake) can append attacker-controlled bytes inside the outer SEQUENCE's declared length, after the signature TLV, and the certificate will still parse successfully. No privileges, keys, or CA control are required.

### Recommendation
After reading the signature field in `unmarshalCertificateV2`, add an explicit `if !input.Empty() { return nil, ErrBadFormat }` check before constructing and returning the certificate, mirroring the strict-parsing pattern used elsewhere for the SEQUENCE envelope opening. Apply the same fix to `unmarshalDetails` at the end of its field reads for consistency.

### Proof of Concept
Unit test in `cert/cert_v2_test.go`:
1. Build a valid, correctly-signed v2 certificate via the existing test helpers (`newTestCertificate`/`Sign` equivalent used in the file).
2. Marshal it to bytes via `Marshal()`.
3. Re-encode the outer SEQUENCE by hand (or splice) to extend its declared length to include N extra random bytes appended right after the `TagCertSignature` TLV, while keeping the SEQUENCE tag/length consistent with the new total size.
4. Call `unmarshalCertificateV2(taintedBytes, nil, curve)`.
5. Assert: expected `ErrBadFormat`, actual: certificate parses successfully with `err == nil` and `Fingerprint()` identical to the fingerprint of the original untampered blob — demonstrating the missing trailing-data check.

```go
func (c *certificateV2) Fingerprint() (string, error) {
	if len(c.rawDetails) == 0 {
		return "", ErrMissingDetails
	}

	copy(b[len(c.rawDetails)+1:], c.publicKey)

	return hex.EncodeToString(sum[:]), nil
}
```

```go
func (c *certificateV2) CheckSignature(key []byte) bool {
	if len(c.rawDetails) == 0 {
		return false
	}
	b := make([]byte, len(c.rawDetails)+1+len(c.publicKey))
	copy(b, c.rawDetails)
	b[len(c.rawDetails)] = byte(c.curve)
	copy(b[len(c.rawDetails)+1:], c.publicKey)

	switch c.curve {
	case Curve_CURVE25519:
		if len(key) != ed25519.PublicKeySize {
			return false //avoids a panic internal to ed25519
		}
		return ed25519.Verify(key, b, c.signature)
	case Curve_P256:
		pubKey, err := ecdsa.ParseUncompressedPublicKey(elliptic.P256(), key)
		if err != nil {
			return false
		}
		hashed := sha256.Sum256(b)
		return ecdsa.VerifyASN1(pubKey, hashed[:], c.signature)
	default:
		return false
	}
}
```
