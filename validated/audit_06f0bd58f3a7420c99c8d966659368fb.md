### Title
`try_forward` clamps oversized receipt size for admission/deduction but pushes the full-size receipt, causing outgoing-bytes accounting drift - ([File: runtime/runtime/src/congestion_control.rs])

### Finding Description
`ReceiptSink::try_forward` receives a `size` parameter computed via `receipt_size`, and when `size > max_receipt_size` it clamps `size = max_receipt_size` purely "to avoid receipts getting stuck," per the comment referencing issue #12606 [1](#0-0) . The clamped `size` is used for the admission check against `forward_limit.size` and to decrement `forward_limit.size -= size` [2](#0-1) , but the original, unclamped `receipt` (whose real borsh-encoded size exceeds `max_receipt_size`) is what gets pushed into `outgoing_receipts` [3](#0-2) . This produces a real gap between the metered/decremented byte budget and the actual bytes placed into `outgoing_receipts`, which back the chunk's `source_receipt_proofs`.

Oversized receipts reaching this path are a known, currently-reachable condition: the test suite `test-loop-tests/src/tests/max_receipt_size.rs` explicitly demonstrates receipts exceeding `max_receipt_size` via `promise_return` (`test_max_receipt_size_promise_return`) and `value_return` (`test_max_receipt_size_value_return`) DAG constructions, both annotated as being possible "because of a bug (See https://github.com/near/nearcore/issues/12606)" [4](#0-3) , and both tests assert an oversized receipt did occur via `assert_oversized_receipt_occurred` [5](#0-4) . Separately, `test_max_receipt_size_yield_resume` shows that the yield/resume path is explicitly gated with a strict `ReceiptSizeExceeded` validation error before reaching congestion control [6](#0-5) , so yield/resume is not a viable oversized-receipt vector — only the promise-combinator (`promise_return`/`value_return`) paths bypass the strict gate.

However, this is not a novel finding: the code contains an explicit inline comment citing GitHub issue #12606, describing precisely this behavior as a known, already-tracked bug, with the design rationale stated directly in the source ("Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck") [7](#0-6) .

### Impact Explanation
The gap between clamped-and-decremented `size` and the real oversized receipt bytes means a shard's outgoing-limit accounting (`forward_limit.size`, and consequently `own_congestion_info` byte tracking) understates true outgoing bytes by `real_size - max_receipt_size` per oversized receipt forwarded. Repeated across many oversized receipts within a chunk height, this could inflate `source_receipt_proofs` for the chunk witness beyond the intended budget. That said, this is the exact scenario already tracked upstream in issue #12606, and the repository's own test suite documents it as an existing, acknowledged limitation rather than an unknown vulnerability — it does not constitute a new finding requiring separate disclosure.

### Likelihood Explanation
Reachable preconditions (funded account, deployed contract producing a promise-combinator receipt via `value_return`/`promise_return` whose actual size exceeds `max_receipt_size`) are demonstrated as achievable by the existing test suite. This is not gated by validator/node/network privilege — an ordinary contract deployer can trigger it.

### Recommendation
This is already tracked in the upstream issue referenced in the code comment (near/nearcore#12606); the fix belongs to that existing issue's resolution (e.g., properly rejecting/clamping receipts at creation time via the strict validation path, or accounting with the real un-clamped size while still avoiding stuck-receipt starvation, e.g. by tracking a "debt" separately).

### Proof of Concept
Not applicable as a new PoC requirement — the existing tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` already reproduce and assert the oversized-receipt condition referenced by this question.

fn test_max_receipt_size_yield_resume() {
    init_test_logger();

    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(

        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(50));

    let max_receipt_size = 4_194_304;

    // Perform a yield which creates a receipt that is larger than the max_receipt_size.
    // It should be rejected because of the receipt size limit.
    let yield_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "yield_with_large_args".into(),
        format!("{{\"args_size\": {}}}", max_receipt_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    let yield_receipt_res =
        env.rpc_runner().execute_tx(yield_receipt_tx, Duration::seconds(10)).unwrap();

    let expected_size = 4194504;
    let expected_yield_status =
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            index: Some(0),
            kind: ActionErrorKind::NewReceiptValidationError(
                ReceiptValidationError::ReceiptSizeExceeded {
                    size: expected_size,
                    limit: max_receipt_size,
                },
            ),
        }));
    assert_eq!(yield_receipt_res.status, expected_yield_status);
