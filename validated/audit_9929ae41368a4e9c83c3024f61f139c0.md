### Title
Unchecked `ByteArray.subArray` slicing of attacker-controlled event log data in shielded TRC-20 note scanning causes unhandled `ArrayIndexOutOfBoundsException` DoS - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getNoteTxFromLogListByOvk` and `Wallet.getNoteTxFromLogListByIvk`, which back the `scanShieldedTRC20NotesByOvk`/`scanShieldedTRC20NotesByIvk` gRPC and HTTP APIs, slice a smart-contract event log's `data` field at fixed offsets (up to byte 788) using `ByteArray.subArray` without first checking that the log data is long enough. An attacker who deploys an arbitrary contract that emits a log with a topic matching one of the shielded-TRC20 leaf-event signatures, but with a `data` payload shorter than the expected 788 bytes, causes an unhandled `ArrayIndexOutOfBoundsException` when any client subsequently scans that contract address for notes.

### Finding Description
The `queryTRC20NoteByIvk`/`scanShieldedTRC20NotesByOvk` code path classifies each transaction log by comparing its topic hash to fixed shielded-TRC20 event signatures via `getShieldedTRC20LogType`, which only checks the log's `address` and `topics`, never `data`: [1](#0-0) 

For log types 1–3 (`MintNewLeaf`, `TransferNewLeaf`, `BurnNewLeaf`), `getNoteTxFromLogListByIvk` only checks `!ArrayUtils.isEmpty(logData)` (i.e., non-empty) before slicing fixed offsets up to byte 708: [2](#0-1) 

Similarly, `getNoteTxFromLogListByOvk` slices the same log data up to byte 788 with no explicit length check for types 1–3, whereas the type-4 (`TokenBurn`) branch does explicitly guard with `logData.length < 64 + BURN_CIPHER_RECORD_SIZE` before slicing: [3](#0-2) [4](#0-3) 

`ByteArray.subArray` performs an unchecked `System.arraycopy` and will throw `ArrayIndexOutOfBoundsException` if `input.length < end`: [5](#0-4) 

This is a structurally identical bug class to the reported Go issue: a fixed-length slice is taken from attacker-influenced decoded bytes without validating the decoded length first, causing an unchecked runtime exception mid-request.

`shieldedTRC20ContractAddress` is a caller-supplied parameter to `scanShieldedTRC20NotesByOvk`/`scanShieldedTRC20NotesByIvk`, exposed through HTTP servlets (`ScanShieldedTRC20NotesByIvkServlet`, `ScanShieldedTRC20NotesByOvkServlet`) and gRPC (`RpcApiService`). Anyone can:
1. Deploy an ordinary smart contract (no special permission needed beyond normal contract deployment/energy payment).
2. Have that contract emit a log whose topic equals `sha3("MintNewLeaf(uint256,bytes32,bytes32,bytes32,bytes32[21])")` (or the Transfer/Burn-leaf variants) with `data` shorter than 708/788 bytes (even a single byte suffices to pass the `!isEmpty` check).
3. Call `scanShieldedTRC20NotesByOvk`/`ByIvk` for the block range containing that transaction and that contract address as `shieldedTRC20ContractAddress`.

This triggers `ArrayIndexOutOfBoundsException` inside `Wallet`, an exception type that is not declared/caught by the surrounding `ZksnarkException`/`ContractExeException`/`BadItemException` catches.

### Impact Explanation
The exception is unhandled by the specific catch blocks in this code path; whether it ultimately turns into a generic 500-style API error (soft DoS limited to that request) depends on outer HTTP/gRPC exception-handling wrappers not confirmed here, but at minimum this is a reliably triggerable unhandled runtime exception in a read-only query API reachable by anyone who deploys a contract and calls a public scan endpoint — a legitimate "API the node can no longer serve" instance for the shielded TRC-20 scan feature, analogous in severity/class to the reported Go advisory (which was also rated only as causing per-request panics recovered by the framework, not a full process crash).

### Likelihood Explanation
High likelihood of triggering: deploying a contract that emits a short-data log with a matching topic hash requires no special permission—any account able to deploy a contract and pay energy can do it, and the scan APIs are unauthenticated/open query endpoints that accept an arbitrary contract address parameter.

### Recommendation
Add explicit minimum-length checks on `logData` before slicing for log types 1–3 in both `getNoteTxFromLogListByIvk` and `getNoteTxFromLogListByOvk`, mirroring the existing guard used for the type-4 `TokenBurn` branch (`logData.length < 64 + NoteEncryption.Encryption.BURN_CIPHER_RECORD_SIZE`). Specifically:
- In `getNoteTxFromLogListByIvk`, require `logData.length >= 708` before doing any `ByteArray.subArray` call, returning `Optional.empty()` otherwise.
- In `getNoteTxFromLogListByOvk`, require `logData.length >= 788` before slicing for types 1–3.
- Consider hardening `ByteArray.subArray` itself to throw a descriptive checked/validated exception instead of relying on the raw `ArrayIndexOutOfBoundsException` from `System.arraycopy`.

### Proof of Concept
1. Deploy a contract with a function that executes:
   `emit MintNewLeaf(0, bytes32(0), bytes32(0), bytes32(0), [bytes32(0) x21])` is the expected ABI, but instead craft raw log emission (e.g., via low-level `LOG` opcodes/inline assembly) so the topic equals `keccak256("MintNewLeaf(uint256,bytes32,bytes32,bytes32,bytes32[21])")` while `data` is only 1 byte long.
2. Call `scanShieldedTRC20NotesByIvk`/`scanShieldedTRC20NotesByOvk` (HTTP: `/wallet/scanshieldedtrc20notesbyivk` or `/wallet/scanshieldedtrc20notesbyovk`) with `shieldedTRC20ContractAddress` set to the deployed contract and a block range covering the emitting transaction.
3. Observe `ArrayIndexOutOfBoundsException` thrown from `ByteArray.subArray` inside `Wallet.getNoteTxFromLogListByIvk`/`getNoteTxFromLogListByOvk`, uncaught by the method's declared exception types.

  private int getShieldedTRC20LogType(TransactionInfo.Log log, byte[] contractAddress)
      throws ZksnarkException {
    byte[] logAddress = log.getAddress().toByteArray();
    byte[] addressWithoutPrefix = new byte[20];
    if (ArrayUtils.isEmpty(contractAddress) || contractAddress.length != 21) {
      throw new ZksnarkException("invalid contract address");
    }
    System.arraycopy(contractAddress, 1, addressWithoutPrefix, 0, 20);
    if (Arrays.equals(logAddress, addressWithoutPrefix)) {
      List<ByteString> logTopicsList = log.getTopicsList();
      byte[] topicsBytes = new byte[0];
      for (ByteString bs : logTopicsList) {
        topicsBytes = ByteUtil.merge(topicsBytes, bs.toByteArray());
      }
      if (Arrays.equals(topicsBytes, SHIELDED_TRC20_LOG_TOPICS_MINT)) {
        return 1;
      } else if (Arrays.equals(topicsBytes, SHIELDED_TRC20_LOG_TOPICS_TRANSFER)) {
        return 2;
      } else if (Arrays.equals(topicsBytes, SHIELDED_TRC20_LOG_TOPICS_BURN_LEAF)) {
        return 3;
      } else if (Arrays.equals(topicsBytes, SHIELDED_TRC20_LOG_TOPICS_BURN_TOKEN)) {
        return 4;
      } else if (Arrays.equals(topicsBytes, SHIELDED_TRC20_LOG_TOPICS_NOTE_SPENT)) {
        return 5;
      }
    }
    return 0;
  }

  public static byte[] subArray(byte[] input, int start, int end) {
    byte[] result = new byte[end - start];
    System.arraycopy(input, start, result, 0, end - start);
