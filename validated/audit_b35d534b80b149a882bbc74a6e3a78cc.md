Confirmed: Nebula supports multiple concurrent UDP reader routines (`listen.routines` / `routines` config, `main.go` lines 162-180), each independently calling into the per-tunnel `ConnectionState.Decrypt` path for inbound data packets. This confirms the race is reachable across concurrently-running goroutines processing packets for the *same* `HostInfo`/`ConnectionState`, not just theoretically.

### Title
Replay-window check-then-act race allows duplicate delivery of replayed/duplicate data packets - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` (and its relay counterpart `VerifyRelay`) implements the anti-replay defense as two separate, independently-locked operations — `window.Check` and `window.Update` — with AEAD decryption sandwiched in between and no lock held across the whole sequence. This reproduces the exact bug class from the external report: a multi-step, security-critical operation (check window → do the expensive/effectful work → commit window state) that is not atomic, so two concurrent invocations for the same message counter can both pass the "check" step before either "commits" the corresponding state update.

### Finding Description
In `connection_state.go`: [1](#0-0) 

`Decrypt` acquires `decryptLock`, calls `cs.window.Check(l, messageCounter)`, releases the lock, performs `cs.dKey.DecryptDanger(...)` (the actual AEAD decryption, which does not consult or mutate the window at all), then re-acquires the lock to call `cs.window.Update(...)` which finally marks the counter as seen. The same check-decrypt-update pattern, with the same lock-release gap, is repeated in `VerifyRelay`: [2](#0-1) 

Because `AllowUnknownVpnAddr`/routines dispatch inbound UDP packets to a pool of reader goroutines when `listen.routines` > 1 (`main.go`), multiple goroutines can concurrently process the *same* ciphertext frame (i.e., an attacker duplicating a captured UDP packet and sending it twice, or network duplication) for the same `HostInfo`/`ConnectionState`: [3](#0-2) 

Sequence:
1. Goroutine A calls `Check(l, i)` → true (not yet marked).
2. Goroutine B (processing a duplicate/replayed copy of the same packet) calls `Check(l, i)` → also true, because A hasn't called `Update` yet.
3. Both A and B independently call `DecryptDanger` on the same ciphertext/counter — decryption is stateless with respect to the window, so both succeed and both produce plaintext.
4. Both A and B call `Update(l, i)`; only one will actually flip the bit and get `true`, but by that point **both plaintexts have already been produced and, in the caller path, already delivered/written to the TUN device** — the anti-replay window's job is to prevent exactly this outcome, and the check-then-act gap defeats it.

This is structurally identical to the reported "transaction ordering" class of bug: a security invariant (per-counter uniqueness/replay protection) is enforced via a non-atomic check-then-commit sequence, and an attacker who can cause two concurrent processing paths to race the gap can force both to observe the "not yet consumed" state and complete the protected operation twice.

### Impact Explanation
A successful race results in a replayed/duplicated encrypted data packet being decrypted and delivered to the TUN device (or, for `VerifyRelay`, re-forwarded through a relay) more than once, defeating Nebula's stated anti-replay guarantee for the data plane. This is a concrete instance of "traffic decryption/forgery/replay" impact explicitly listed as acceptable in the validation rules — it is a replay-protection bypass, not merely a duplicate log line, since the plaintext is handed to the overlay device (or relay-forwarded) on both racing paths before the window state is reconciled.

### Likelihood Explanation
Exploitability requires:
- `listen.routines` (config `listen.routines`) set greater than 1, which enables genuinely parallel packet dispatch across reader goroutines (a supported, documented performance configuration, not a test-only path).
- The attacker (a network-path attacker with no valid Nebula certificate — this only requires capturing/duplicating already-observed UDP ciphertext, which is trivial for any on-path or off-path spoofing attacker on UDP) to send (or cause network duplication of) two copies of the same captured ciphertext frame in close temporal proximity so they land in different reader goroutines' hot paths concurrently.

This is a timing-dependent race, so reliability depends on scheduler behavior and network jitter, but it is deterministically reachable by design (the check/decrypt/update sequence always has an unlocked window), so a patient/persistent attacker sending many duplicate bursts can eventually win the race. This does not require possession of a CA-signed certificate — decryption of a previously captured ciphertext with the correct symmetric key does not depend on presenting any certificate.

### Recommendation
Make the check-decrypt-update sequence atomic with respect to a given message counter: hold `decryptLock` (or a per-counter/token mechanism) across the full `Check → Decrypt → Update` sequence, or restructure so that `Update` reserves the slot *before* decryption is attempted (i.e., do a combined "claim-if-not-seen" operation first, then decrypt, and roll back the claim only on decryption failure). This closes the window during which two concurrent packets carrying the same counter can both pass the replay check.

### Proof of Concept
1. Configure a node with `listen.routines: 2` (or more) so that inbound UDP handling runs across multiple concurrent reader goroutines.
2. Establish a tunnel between two nodes and capture one inbound encrypted data-plane message (`header.Message`) addressed to the victim, noting its message counter `i`.
3. As a network attacker, replay the exact captured UDP datagram twice back-to-back (e.g., via a raw-socket duplicate send or a busy loop firing at maximum rate) so that with `routines > 1` the two copies are picked up by two different reader goroutines nearly simultaneously.
4. Instrument (or repeat many times to statistically observe) `ConnectionState.Decrypt`: because `Check` and `Update` are called as separate locked sections with `DecryptDanger` executed unlocked in between, both goroutines can observe `Check` returning `true` before either has called `Update`, causing the payload to be decrypted and delivered to the TUN device (or relay-forwarded) twice despite the anti-replay window nominally rejecting duplicates.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
