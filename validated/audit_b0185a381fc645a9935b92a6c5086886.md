### Title
Missing recipient validation in `DepositToken.withdraw` allows collateral to be sent to protocol contracts and permanently locked - (File: contracts/DepositToken.sol)

### Summary
`DepositToken.withdraw(uint256 amount_, address to_)` lets the caller pick an arbitrary recipient for the withdrawn underlying collateral. The only validation is `to_ != address(0)`. If `to_` is set to a protocol contract that cannot move ERC20 tokens — e.g. the `Treasury` itself or the `Pool` — the user's deposit-token balance is burned while the underlying is transferred to (or simply left inside) a contract from which it can never be withdrawn. This is the same bug class as the PrimitiveEngine `withdraw` finding: missing input validation on the withdrawal recipient leads to permanently stuck funds.

### Finding Description
The withdrawal flow is:

- `DepositToken.withdraw` at `contracts/DepositToken.sol:406-412` only checks `if (to_ == address(0)) revert RecipientIsNull()` before calling `_withdraw`. [1](#0-0) 
- `_withdraw` burns the caller's msdTOKEN and calls `_pool.treasury().pull(to_, _withdrawn)` at `contracts/DepositToken.sol:550-551`. [2](#0-1) 
- `Treasury.pull` at `contracts/Treasury.sol:66-72` again only checks `to_ != address(0)` and then does `underlying.safeTransfer(to_, amount_)`. [3](#0-2) 
- Critically, `Treasury` does **not** inherit `TokenHolder` — its inheritance list at `contracts/Treasury.sol:25` is `Initializable, ReentrancyGuardDeprecated, ReentrancyGuardTransient, Manageable, TreasuryStorageV1`, so it exposes no `sweep()` recovery for arbitrary tokens it should not hold. [4](#0-3) 

Consequences per bad recipient:

- `to_ == address(treasury)`: `pull` transfers the underlying back to the treasury contract. The transfer "succeeds" (balance unchanged), but the user's msdTOKEN is burned. The collateral stays in the treasury with no corresponding claim — the user has irreversibly forfeited it; there is no user-level function to reclaim it and `Treasury` has no `sweep`.
- `to_ == address(pool)` or `to_ == address(depositToken)` (i.e. `address(this)`): the underlying ERC20 is transferred to a contract that never custodies raw underlying. `DepositToken`/`Pool` do inherit `TokenHolder`, but `sweep()` is gated by `_requireCanSweep()` → `onlyGovernor` (`contracts/DepositToken.sol:492-493`), so trustless recovery by the user is impossible. [5](#0-4) 

No modifier stops this: `withdraw` is permissionless, `whenNotShutdown`/`nonReentrant`/`onlyIfDepositTokenExists` do not inspect `to_`, and `_revertIfLocked` only bounds `amount_`.

### Impact Explanation
Permanent freezing/loss of user funds. A user who supplies a protocol contract address as `to_` burns their deposit tokens while the underlying is delivered to an address that can never return it to them (Treasury/Pool have no user-callable recovery; the governor-gated `sweep` on `DepositToken` exists only where inherited and cannot be relied on). The accounting invariant "burned msdTOKEN ⇒ underlying leaves protocol custody to a user-controlled address" is broken.

### Likelihood Explanation
The same class of mistake as in the referenced audit: integrations, multicall/operator batching (`Operator.execute` routes arbitrary calls with `to_` supplied via calldata), and UI/wallet misconfiguration can all plausibly pass a well-known protocol address (Treasury, Pool, the deposit token) as recipient. Any user doing so loses the full withdrawn amount.

### Recommendation
Short term: in `DepositToken.withdraw` (or `Treasury.pull`), revert when `to_` equals `address(this)`, `address(pool.treasury())`, or `address(pool)` — i.e. blacklist protocol-internal addresses, mirroring the recommended `recipient != engine` check.

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// Fork mainnet, pick a registered Pool and its msDepositToken for e.g. WETH
IDepositToken msWETH = pool.depositTokenOf(WETH);
address treasury = address(pool.treasury());

// user deposits, then withdraws to the Treasury address
msWETH.deposit(amount, user);
vm.prank(user);
msWETH.withdraw(amount, treasury);   // succeeds — only zero-address is checked

// assertions:
assertEq(msWETH.balanceOf(user), 0);                // deposit tokens burned
assertEq(WETH.balanceOf(treasury), treasuryBefore); // collateral never left
// user has no function to recover; Treasury has no sweep()
```

With `to_ = address(pool)`, `WETH.balanceOf(pool)` increases and the funds are only recoverable via the governor-only `sweep`, not by the user.
