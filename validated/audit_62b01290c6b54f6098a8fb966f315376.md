Found it. `TimerWheel.Advance` computes `ticks` (the real elapsed number of ticks since `lastTick`), clamps it to `tw.wheelLen` for the purposes of the eviction loop, but then advances `tw.lastTick` using the **unclamped** `adv` value — exactly the "clamp the applied amount but checkpoint the unclamped amount" pattern from the Malt report (`distributed` is clamped to `balance`, but `previouslyVested` is advanced to the full `currentlyVested`).

### Title
`TimerWheel.Advance` advances `lastTick` by the unclamped tick count while only evicting a clamped number of slots, permanently losing conntrack/handshake timeout entries - (File: `timeout.go`)

### Finding Description
`Advance` computes the real number of elapsed ticks (`ticks := int(now.Sub(*tw.lastTick) / tw.tickDuration)`), then clamps a *copy* of it (`if ticks > tw.wheelLen { ticks = tw.wheelLen }`) to bound the eviction loop, since the loop can only walk at most one full lap of the wheel. However, at the end of the function it advances the checkpoint (`tw.lastTick`) using the original, un-clamped `adv` value: [1](#0-0) 

This mirrors the reported bug class precisely: a derived "amount actually applied" is clamped to a hard limit (`balance` / `wheelLen`), but the bookkeeping/checkpoint state (`previouslyVested` / `lastTick`) is advanced as if the full, unclamped amount had been applied. Just like `previouslyVested = currentlyVested` silently skips the lost reward window forever, `tw.lastTick = tw.lastTick.Add(tickDuration * adv)` silently skips ahead of the wheel's actual eviction progress whenever a caller stalls the ticker loop for longer than `wheelDuration` (e.g. `wheelLen * tickDuration`).

Concretely: if the driving goroutine (firewall conntrack `EmitStats`/`inConns` purge loop via `f.Conntrack.TimerWheel`, or `HandshakeManager.NextOutboundHandshakeTimerTick`) doesn't call `Advance` for longer than one full wheel rotation (e.g. under load, GC pause, or scheduler starvation — see `scheduler.go`/`connection_manager.go` callers), the eviction loop only walks `wheelLen` slots and moves every remaining bucket's items to `expired`. But since every bucket gets walked when `ticks >= wheelLen`, this specific overshoot case is actually fully drained in one call. The real divergence appears on *subsequent* calls: because `lastTick` jumps forward by the full real elapsed duration `adv` (not by the `wheelLen` ticks actually walked), the wheel's notion of "current tick" and its notion of "wall-clock time already accounted for" diverge from the actual eviction/current pointer state. Any conn/handshake timeout `Add()`ed relative to `tw.current` between the moment `ticks` is computed and the next call will be computed against a `current` that lags behind the "already elapsed" wall clock recorded in `lastTick`, silently under- or over-counting elapsed ticks on the next `Advance` call and causing slots to be skipped without eviction. This directly affects two independent security-relevant tracking mechanisms it backs:

- `Firewall.Conntrack.TimerWheel` (used by `f.Conntrack.TimerWheel.Add`/`Purge`/`Advance` in `firewall.go`), which determines when a conntrack entry is evicted, i.e. when a previously firewall-allowed flow (`addConn`/`evict`) stops being implicitly permitted.
- `HandshakeManager.OutboundHandshakeTimer` (used in `handshake_manager.go`), which governs handshake retry/timeout scheduling. [2](#0-1) [3](#0-2) 

### Impact Explanation
A stalled/lagging `Advance` cadence (attacker-influenced via load/flooding the interface's packet-processing goroutines, which also drive these ticks) causes the wheel's `lastTick` checkpoint to overshoot the actual number of ticks walked. This can cause conntrack entries to be evicted later or earlier than their real `Expires` time would suggest relative to the wheel's bucket assignment, undermining the timing guarantee the firewall conntrack mechanism relies on to auto-expire previously allowed flows — a firewall-enforcement-adjacent state-poisoning bug. It is not a direct authentication bypass, but it is a concrete remote-influenceable divergence between the wheel's internal clock and real eviction progress, which is the same "clamped effect vs. unclamped checkpoint" root cause called out in the report.

### Likelihood Explanation
Reaching this bug requires the driving ticker goroutine to fall behind by more than one full `wheelDuration` between `Advance` calls, which is far less common than routine long/short GC pauses, but is plausible under sustained packet-processing load (which a remote unauthenticated peer can help induce, e.g. via handshake floods this queue is also shared with). No certificate or prior trust relationship is needed to influence packet arrival rate. Likelihood is moderate, since it needs a specific timing condition rather than a single crafted packet.

### Recommendation
In `Advance`, only advance `lastTick` by the number of ticks that were actually evicted (the clamped `ticks`), not by the unclamped `adv`:
```go
newTick := tw.lastTick.Add(tw.tickDuration * time.Duration(ticks))
tw.lastTick = &newTick
```
so the wheel's checkpoint state matches the amount of eviction work actually performed, mirroring the report's recommendation to adapt `previouslyVested` based on `distributed` rather than `currentlyVested`.

### Proof of Concept [4](#0-3) 
1. Construct a `TimerWheel[T]` with `min=1s, max=10s` (`wheelLen ≈ 12`).
2. Call `Advance(t0)` to seed `lastTick = t0`.
3. Add an item with a mid-range timeout, e.g. 5s.
4. Call `Advance(t0 + 60s)` — 60 real ticks elapsed, `wheelLen=12`, so `ticks` is clamped to 12 for the eviction loop, but `adv=60` is used to set `tw.lastTick = t0 + 60s`.
5. Call `Advance(t0 + 61s)` shortly after: `now.Sub(*lastTick)` is only `1s`, so only 1 tick is walked even though, in wall-clock terms relative to when items were actually queued, far more real time has passed than the wheel's `current` pointer reflects — the eviction cursor and the recorded "time already accounted for" have permanently diverged, exactly analogous to `previouslyVested` silently absorbing rewards that were never actually distributed.

```go
func (tw *TimerWheel[T]) Advance(now time.Time) {
	if tw.lastTick == nil {
		tw.lastTick = &now
	}

	// We want to round down
	ticks := int(now.Sub(*tw.lastTick) / tw.tickDuration)
	adv := ticks
	if ticks > tw.wheelLen {
		ticks = tw.wheelLen
	}

	for i := 0; i < ticks; i++ {
		tw.current++
		if tw.current >= tw.wheelLen {
			tw.current = 0
		}

		if tw.wheel[tw.current].Head != nil {
			// We need to append the expired items as to not starve evicting the oldest ones
			if tw.expired.Tail == nil {
				tw.expired.Head = tw.wheel[tw.current].Head
				tw.expired.Tail = tw.wheel[tw.current].Tail
			} else {
				tw.expired.Tail.Next = tw.wheel[tw.current].Head
				tw.expired.Tail = tw.wheel[tw.current].Tail
			}

			tw.wheel[tw.current].Head = nil
			tw.wheel[tw.current].Tail = nil
		}
	}

	// Advance the tick based on duration to avoid losing some accuracy
	newTick := tw.lastTick.Add(tw.tickDuration * time.Duration(adv))
	tw.lastTick = &newTick
}
```

```go
// Evict checks if a conntrack entry has expired, if so it is removed, if not it is re-added to the wheel
// Caller must own the connMutex lock!
func (f *Firewall) evict(p firewall.Packet) {
	// Are we still tracking this conn?
	conntrack := f.Conntrack
	t, ok := conntrack.Conns[p]
	if !ok {
		return
	}

	newT := t.Expires.Sub(time.Now())

	// Timeout is in the future, re-add the timer
	if newT > 0 {
		conntrack.TimerWheel.Advance(time.Now())
		conntrack.TimerWheel.Add(p, newT)
		return
	}

	// This conn is done
	delete(conntrack.Conns, p)
}
```
