### Title
StackerDB push-chunk handler advertises an accepted chunk version before it is actually committed to storage, allowing advertised inventory to diverge from stored state - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` optimistically patches and immediately transmits a `StackerDBChunkInv` acknowledging that the node now holds a newly-pushed chunk version, before the chunk is actually written to the StackerDB. The real, authoritative write happens later and asynchronously, in the relayer's `process_stacker_db_chunks`/`process_pushed_stacker_db_chunks`, via `StackerDBTx::try_replace_chunk`, which re-validates against the DB state *at commit time* and can reject the chunk (e.g. `StaleChunk`) if another write for the same slot lands first. This is the same class of bug as the report: bookkeeping/accounting (here, the advertised slot-version inventory) is updated from the *input/claimed* value rather than the *actual* outcome of the operation, so the acknowledged/advertised state can be higher/different than what is truly persisted.

### Finding Description
`make_StackerDBChunksInv_or_Nack` builds the reply inventory from `self.stackerdbs.get_slot_versions(contract_id)` — i.e., the currently *stored* versions at the moment of the call. [1](#0-0) 

`handle_unsolicited_StackerDBPushChunk` then runs `validate_received_chunk` against that in-memory snapshot (`data.slot_versions`), and if the incoming pushed chunk's version and signature check out, it directly mutates the in-memory `StackerDBChunkInvData` to claim the *new* pushed version, before any chunk write has occurred: [2](#0-1) 

This patched inventory is then signed and sent back to the peer over the wire immediately, in the same synchronous p2p call: [3](#0-2) 

The function's own return value `(false, true)` signals "forward to relayer" — the actual, authoritative storage attempt happens later, out-of-band, in `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`: [4](#0-3) 

`try_replace_chunk` re-checks chunk size, signer, and (critically) freshness against the *actual* stored `slot_validation.version` at commit time, and returns `StaleChunk` if a competing write already advanced the slot past the version being stored: [5](#0-4) 

When this happens, the chunk is silently dropped (logged at `debug!`) and no event is emitted: [6](#0-5) 

Because the validation snapshot used to decide whether to *acknowledge/advertise* acceptance is taken before the deferred, asynchronous commit, a remote peer can race two pushes to the same slot (e.g., versions N and N+1 arriving close together, processed by the p2p thread before either is committed by the relayer). Both can pass `validate_received_chunk` against the same stale snapshot and both get an immediate "accepted" `StackerDBChunkInv` reply patched to their respective claimed versions — but only one of them is actually persisted by the time `try_replace_chunk` runs; the other is dropped as `StaleChunk`. The result: this node's outgoing inventory (sent to the pusher and, via subsequent `StackerDBChunkInv` gossip, to other peers who query it) claims possession of a specific chunk version/content that the node never actually stored.

### Impact Explanation
This breaks the "advertised inventory equals actual stored data" equality that the StackerDB inventory/sync protocol depends on (analogous to "served vs. committed" mismatches). Downstream effects:
- Peers that trust our `StackerDBChunkInv` (used to drive rarest-first / newest-first download scheduling) will believe we hold data we do not have, and may deprioritize re-fetching it from other sources.
- Since StackerDBs are used by the signer set to relay block-commit/decision artifacts, false inventory can delay propagation of legitimate chunks to other replicas, since the true committed content is never surfaced to peers that rely on our (already-sent) claim.
This aligns with the High-severity category "steering a node off the tip via false inventory" / serving non-canonical (here: not-actually-stored) state as canonical, since it's a remote, unprivileged, protocol-driven race rather than requiring any secret key or admin role.

### Likelihood Explanation
Any two legitimate StackerDB writers/relayers (or a single writer's chunk racing against a normal StackerDB-sync download of the same slot) pushing/pulling in close succession can trigger this, since the acknowledgment path is fully asynchronous from the actual commit path. No special timing precision or privileged access is required — it only needs ordinary unsolicited `StackerDBPushChunk` messages arriving close together, which is expected, normal StackerDB traffic.

### Recommendation
Do not patch/send the `StackerDBChunkInv` acknowledgment as "accepted" until after the chunk has actually been committed via `try_replace_chunk`. Either move the ack decision to after the relayer's synchronous replace attempt, or make `handle_unsolicited_StackerDBPushChunk` perform the actual DB write itself (transactionally) before advertising updated inventory, so the acknowledged version always matches the truly persisted `slot_validation.version`.

### Proof of Concept
1. Two signers (or a signer and a stale download-sync source) send `StackerDBPushChunk` messages for the same `slot_id` with versions `N` and `N+1` to a victim node in close succession, both signed correctly.
2. The victim's p2p thread handles both via `handle_unsolicited_StackerDBPushChunk` before the relayer processes either: `make_StackerDBChunksInv_or_Nack` snapshots the DB at version `N-1` for both, `validate_received_chunk` passes for both against that stale snapshot, and both trigger an optimistic `slot_version` patch + immediate signed `StackerDBChunkInv` ack sent back to each sender [7](#0-6) .
3. The relayer later processes both pushes in one transaction via `try_replace_chunk`; whichever is applied second (per DB order) is rejected as `StaleChunk` and silently dropped [8](#0-7) [6](#0-5) .
4. The node has already told the sender of the dropped chunk (and will propagate via subsequent inventory gossip) that it possesses that specific chunk version, even though it was never stored — an inventory/state mismatch reachable by any two remote, unprivileged StackerDB writers.
