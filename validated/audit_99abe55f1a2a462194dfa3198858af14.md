### Title
Stake-weighted stream throttling in QUIC streamer can be evaded by splitting traffic across multiple connections - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
The stake-weighted QoS (`SwQos`) throttles the number of streams a staked peer may open per throttling interval, computing that cap as the peer's proportional share of stake-weighted bandwidth. However, this cap is enforced independently on a **per-connection** basis via each connection's own `ConnectionStreamCounter`, while a single staked identity is allowed to hold up to `max_connections_per_staked_peer` concurrent connections. This mirrors the "LargeBet" pattern in the external report: a limit intended to bound a peer's aggregate share of a shared resource is checked in isolation per-unit (per connection) instead of in aggregate (per peer), so it can be trivially "gamed" by splitting load across multiple connections from the same staked identity.

### Finding Description
`SwQos::cache_new_connection` computes a per-connection uni-stream cap `max_uni_streams` using `compute_max_allowed_uni_streams_with_rtt`, seeded from the peer's stake ratio [1](#0-0) . Independently, `on_new_stream` throttles each stream against a per-connection budget derived from `max_streams_per_throttling_interval`, which calls `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration(peer_type, total_stake)` [2](#0-1) , and enforces it via `throttle_stream` against that connection's own `ConnectionStreamCounter` [3](#0-2) .

`available_load_capacity_in_throttling_duration` computes the allowed stream budget for **one connection** as `max_staked_load_in_throttling_window * stake / total_stake` (clamped to at least `max_unstaked_load_in_throttling_window + 1`) [4](#0-3) . This value is meant to represent the peer's proportional share of the cluster-wide staked stream budget, but nothing sums usage across a peer's multiple simultaneous connections — each connection independently gets its own token/stream counter and its own full stake-proportional allowance.

Because `try_add_connection`/`cache_new_connection` allow a single staked pubkey to hold up to `max_connections_per_staked_peer` connections at once (bounded by `ConnectionTable` keyed by `ConnectionTableKey::new(ip, pubkey)` and `max_connections_per_peer`) [5](#0-4) , a staked client can open N connections and receive N× the intended per-peer-per-interval stream allowance, since each connection's throttle counter and budget are computed and enforced completely independently, with no per-pubkey or per-IP aggregate accounting of consumed stream/token budget across connections.

This is analogous to the reported bug: the check ("does this connection/bet exceed its allowed share") is correct in isolation but doesn't hold for the actual protected invariant (total stake-weighted bandwidth per peer across all its connections), so splitting the traffic into multiple smaller units (connections) defeats the intended protection.

### Impact Explanation
This is a QoS-evasion bug explicitly in scope per the validation rules. A staked (or even low-stake) peer opening multiple concurrent QUIC connections up to `max_connections_per_staked_peer` can multiply its effective transaction/packet ingestion rate at the streamer beyond what the stake-weighted fairness model intends, unfairly consuming a disproportionate share of the leader's stream-processing capacity relative to its stake and crowding out other staked/unstaked peers. This undermines the fairness guarantee that stake-weighted QoS is designed to provide (medium impact — it breaks an invariant/gives false sense of fairness, but does not itself crash the node or corrupt consensus state).

### Likelihood Explanation
Medium: any staked validator client is already permitted (by design) to open multiple concurrent connections (bounded by `max_connections_per_staked_peer`), so no attacker capability beyond normal protocol usage is required — simply opening more connections than one and spreading traffic across them achieves the multiplier. There is limited direct financial incentive to do so, similar to the original report's likelihood rationale, but it is trivial to exploit and requires no special access.

### Recommendation
Change the throttling accounting so the stake-weighted stream budget (`available_load_capacity_in_throttling_duration`) is tracked and enforced per staked identity (pubkey) in aggregate across all of that peer's concurrent connections, rather than per individual connection. This could be done by keying the `ConnectionStreamCounter` (or an additional shared counter) by remote pubkey/IP inside `SwQos`/`ConnectionTable`, so that stream consumption from all connections opened by the same staked peer is summed against a single stake-proportional budget, consistent with how `cost_tracker.rs` correctly aggregates transaction costs against block/account-wide limits in [6](#0-5) .

### Proof of Concept
1. A staked node with total stake `s` connects to the QUIC streamer and opens `max_connections_per_staked_peer` connections instead of 1 (allowed by `try_add_connection`) [5](#0-4) .
2. For each connection, `on_new_stream` independently calls `max_streams_per_throttling_interval`, which returns the same stake-proportional budget `B` for each connection (since it's computed from the peer's fixed stake ratio, not remaining aggregate usage) [2](#0-1) .
3. The client evenly distributes its transaction/packet stream traffic across its `N` connections, sending up to `B` streams per connection per throttling interval, for a total of `N * B` streams — exceeding the single stake-proportional share `B` that the mechanism was designed to allow for that peer.

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
