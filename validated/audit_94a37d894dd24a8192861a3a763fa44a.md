### Title
Stale replica-consistency cache entries can be written after a Postgres disconnect/reconnect, causing outdated storages to be treated as consistent - ([File: internal/praefect/datastore/storage_provider.go])

### Summary
`CachingConsistentStoragesGetter` caches which physical storages hold the up-to-date generation of a repository, invalidating entries only via Postgres `LISTEN`/`NOTIFY` payloads delivered to `Notified()` [1](#0-0) . Like the Hats `changeHatToggle()` bug, this is a case where switching between two sources of truth (live DB query vs. locally cached value) can cause a stale value to become authoritative again without first being reconciled with the latest state.

### Finding Description
The cache is only trustworthy while the Postgres notification channel is connected: `Connected()` re-enables the cache and `Disconnected()` disables it and purges all entries, since a lost connection means missed invalidation notifications [2](#0-1) . However, `GetConsistentStorages` captures a local reference to the per-virtual-storage `cache` object at the start of the call, before doing a (possibly slow) DB query via `c.csg.GetConsistentStorages`, and only then unconditionally repopulates it with `cache.replicaInfoCache.Add(...)`, without re-checking `isCacheEnabled()` after the query completes [3](#0-2) .

If a `Disconnected()`/purge event happens concurrently with an in-flight `GetConsistentStorages` call that started while caching was enabled, the in-flight call can still write its (now possibly outdated) result into the cache after the purge, and before or without any subsequent `Notified()` invalidation for repositories that changed during the outage window. Once `Connected()` re-enables the cache, this leftover entry is served as valid (`isCacheEnabled()` true, `cache.replicaInfoCache.Get` hit) even though it reflects the pre-outage generation state — mirroring the toggle bug where switching sources of truth resurrects a previously-cached value instead of forcing a fresh read.

### Impact Explanation
`GetConsistentStorages` results are used by Praefect's routing/generation logic to determine which storages are considered "up to date" for a repository (per the `virtual_storage.md` consistency model, generations, and secondaries selection) [4](#0-3) . If a stale "consistent storages" set is served after a reconnect, reads or replication decisions could be made against a set of storages that no longer accurately reflects which nodes actually hold the latest generation, risking serving stale repository data to ordinary read/fetch RPCs or misrouting transaction participation for pushes shortly after any Praefect-to-Postgres connectivity interruption. This is a data-consistency/correctness issue reachable through ordinary fetch/push traffic combined with a naturally occurring (not attacker-controlled) DB reconnect event.

### Likelihood Explanation
Requires a specific timing window: a `GetConsistentStorages` cache-miss lookup in flight exactly when `Disconnected()`/`Connected()` toggle occurs, plus a relevant repository state change occurring in that same window that isn't later re-observed. Postgres connection blips are common in production HA deployments, and Praefect handles concurrent RPC traffic continuously, so the race window is plausible but narrow and self-heals once further mutations trigger fresh `Notified()` invalidations or additional cache misses naturally repopulate the entry with current data. I was not able to fully trace how `server_factory.go`/`glsql/postgres.go` wires `Connected`/`Disconnected` callbacks to the actual listener reconnect logic within my remaining exploration budget, so the exact reconnect-to-callback timing (and whether a full resync/purge-then-refetch is performed elsewhere) is not fully confirmed.

### Recommendation
In `GetConsistentStorages`, re-check `c.isCacheEnabled()` (or capture and compare a "generation"/epoch counter that increments on each `Disconnected()`) immediately before writing the result back with `cache.replicaInfoCache.Add(...)`, and skip the write if caching was disabled/reset at any point during the query. This ensures the cache is never repopulated with a value that predates a disconnect-triggered purge, analogous to calling `checkHatToggle()` before trusting a switched source of truth.

### Proof of Concept
1. Praefect is running with the disk-cache-backed `CachingConsistentStoragesGetter` and caching enabled.
2. Client A issues a read RPC that triggers `GetConsistentStorages(ctx, vs, path)` for a repository not yet cached; the call proceeds to `c.csg.GetConsistentStorages(...)` (a DB query) which is slow due to load.
3. Concurrently, the Postgres connection drops: `Disconnected()` fires, setting `access=0` and purging `cache.replicaInfoCache`.
4. During the outage, a mutator elsewhere changes the repository's generation/consistent-storages set on disk (e.g., a write completes on a subset of nodes), but the corresponding `NOTIFY`/`Notified()` invalidation is missed because the listener is down.
5. Postgres reconnects; `Connected()` sets `access=1`.
6. Client A's original DB query from step 2 returns (with data reflecting the state either just-before or racing with the outage) and unconditionally calls `cache.replicaInfoCache.Add(relativePath, cachedReplicaInfo{...})`, populating the now-active cache with a value that never accounted for the missed invalidation.
7. Subsequent calls to `GetConsistentStorages` for that `relativePath` return the cached, unreconciled result (`isCacheEnabled()` true, cache hit), until a later invalidation event happens to touch that same key.

// Notified handles notifications by invalidating cache entries of updated repositories.
func (c *CachingConsistentStoragesGetter) Notified(n glsql.Notification) {
	var changes []notificationEntry
	if err := json.NewDecoder(strings.NewReader(n.Payload)).Decode(&changes); err != nil {
		c.disableCaching() // as we can't update cache properly we should disable it
		c.callbackLogger.WithError(err).WithField("channel", n.Channel).Error("received payload can't be processed, cache disabled")
		return
	}

	for _, entry := range changes {
		cache, found := c.caches[entry.VirtualStorage]
		if !found {
			c.callbackLogger.WithError(errNotExistingVirtualStorage).WithField("virtual_storage", entry.VirtualStorage).Error("cache not found")
			continue
		}

		for _, relativePath := range entry.RelativePaths {
			cache.replicaInfoCache.Remove(relativePath)
		}
	}
}

// GetConsistentStorages returns the replica path and the set of up to date storages for the given repository keyed by virtual storage and relative path.
func (c *CachingConsistentStoragesGetter) GetConsistentStorages(ctx context.Context, virtualStorage, relativePath string) (string, *datastructure.Set[string], error) {
	cache, hasCache := c.caches[virtualStorage]
	if hasCache && c.isCacheEnabled() {
		if replicaInfo, found := cache.replicaInfoCache.Get(relativePath); found {
			c.cacheAccessTotal.WithLabelValues(virtualStorage, "hit").Inc()
			return replicaInfo.replicaPath, replicaInfo.storages, nil
		}

		// Synchronise concurrent attempts to update the cache for the same relative path.
		// This will cause us to wait for any ongoing calls, but also locks out other new
		// callers so that we can racelessly populate the cache. The deferred call will then
		// unlock other callers again once we're done with the lookup.
		defer cache.syncer.await(relativePath)()

		// We re-try whether the cache has been populated now via any concurrent Goroutine.
		// If so, we return the newly populated entry.
		if replicaInfo, found := cache.replicaInfoCache.Get(relativePath); found {
			c.cacheAccessTotal.WithLabelValues(virtualStorage, "hit").Inc()
			return replicaInfo.replicaPath, replicaInfo.storages, nil
		}
	} else {
		// Unset the cache so that we don't try to populate it when it is disabled.
		cache = nil
	}

	c.cacheAccessTotal.WithLabelValues(virtualStorage, "miss").Inc()

	replicaPath, storages, err := c.csg.GetConsistentStorages(ctx, virtualStorage, relativePath)
	if err != nil {
		return "", nil, err
	}
	if cache != nil {
		c.cacheAccessTotal.WithLabelValues(virtualStorage, "populate").Inc()
		cache.replicaInfoCache.Add(relativePath, cachedReplicaInfo{replicaPath: replicaPath, storages: storages})
	}

	return replicaPath, storages, err
}
