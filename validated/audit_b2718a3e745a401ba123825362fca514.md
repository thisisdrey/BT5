## Title
Unbounded per-connection goroutines and missing handshake/idle timeout in `SSHServer.run` allow resource exhaustion via stalled SSH connections - (File: sshd/server.go)

### Summary
`SSHServer.run` accepts every TCP connection and spawns a goroutine that calls `ssh.NewServerConn(c, s.config)` with no per-connection read/write deadline and no cap on concurrently outstanding handshakes. An attacker who opens many TCP connections and never completes (or only partially writes) the SSH handshake causes each corresponding goroutine to block indefinitely inside `ssh.NewServerConn`, since the only teardown path is cancellation of the whole listener's parent context, not a per-connection idle/handshake timeout.

### Finding Description
In `sshd/server.go`, `SSHServer.run` (`sshd/server.go:210`) loops on `listener.Accept()` and, for every accepted connection, launches a goroutine: [1](#0-0) 

The goroutine derives `sessionContext` from the run-level `ctx` and starts a watcher that closes the socket `<-sessionContext.Done()`, but `sessionContext` is only cancelled by (a) `sessionCancel()` being called after a completed/failed handshake, or (b) the entire server's `ctx` (from `Control.Stop`/reload) being cancelled — there is no independent per-connection timer. `ssh.NewServerConn` itself performs blocking reads on `c` with no deadline ever set via `c.SetDeadline`/`SetReadDeadline` anywhere in this file. Consequently, a peer that opens a TCP connection and sends a partial handshake (or nothing at all) causes the spawned goroutine, and the underlying file descriptor, to remain alive for the lifetime of the server run, not for any bounded idle period.

There is also no limit on the number of concurrent in-flight (unauthenticated) connections/goroutines that `run` will spawn; every `Accept()` immediately produces a new goroutine regardless of how many prior ones are still stuck in `NewServerConn`. The invariant expected by the question — "idle and half-open connections are timed out and total concurrency is bounded" — does not hold anywhere in this code path.

### Impact Explanation
An attacker with only network reachability to the SSH admin listener (no credentials, no CA certificate) can open many TCP connections and withhold/partially send handshake bytes. Each such connection pins one goroutine and one file descriptor indefinitely. Given enough concurrent stalled connections, the process can exhaust file descriptors or goroutine/memory headroom, which is a real denial-of-service vector against the node's control surface (the SSH admin console). This matches the "Denial of service against the node's control/DNS surface" impact class named in the question, scoped to resource exhaustion rather than a crash of the whole node.

### Likelihood Explanation
Exploitation requires only TCP reachability to the configured SSH listener address and no authentication material, making it feasible for any locally-reachable, unprivileged network attacker. It is trivially repeatable (e.g., opening N sockets and never writing/only partially writing the SSH banner/handshake) and does not depend on any race condition or timing quirk — the missing deadline and missing concurrency cap are unconditional code properties.

### Recommendation
- Set a bounded I/O deadline on the accepted `net.Conn` before calling `ssh.NewServerConn` (e.g., `c.SetDeadline(time.Now().Add(handshakeTimeout))`), and clear/reset it once the handshake completes and a session begins.
- Add an explicit cap on the number of concurrent unauthenticated/in-handshake connections (e.g., a semaphore or worker pool) so `run` stops accepting/handling new connections past a configured limit until slots free up.
- Consider closing connections that make no progress within a short idle window even after a session starts, independent of the parent context cancellation.

### Proof of Concept
Integration test plan for `sshd/server.go`:
1. Start `SSHServer.Run` on a test address with a valid host key and at least one trusted CA/key configured.
2. Open `N` (e.g., 200) raw TCP connections to the listener and, for each, write only a partial/incomplete SSH version banner (or nothing), then keep the socket open without closing it.
3. Concurrently, open one legitimate SSH client connection (with a valid key) and attempt a full handshake plus a trivial command execution.
4. Assert that the legitimate client's handshake completes and returns within a short bounded time (e.g., a few seconds) — currently, no timeout exists, so under FD/goroutine pressure this can stall or fail once system limits are approached, demonstrating the absence of the timeout/bound invariant.
5. Additionally assert (via runtime.NumGoroutine() or netstat/lsof counts) that the number of goroutines/FDs tied to stalled connections grows unboundedly and is never reclaimed absent a full server `Stop()`, confirming there is no idle timeout enforcement.
