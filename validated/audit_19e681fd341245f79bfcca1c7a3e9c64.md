Based on the investigation, I found a concrete analog: `handleCreateRelayRequest` in `relay_manager.go` trusts the peer-declared `RelayFromAddr` field from the `NebulaControl` message as the identity of the node the relay is being established "from," without validating it against `h.vpnAddrs` — the cryptographically-authenticated identity of the actual sender of the packet (`h *HostInfo`, whose identity was established during the Noise handshake and cert verification). This is the same bug class as the report: one field (`apiData.tokenFrom`) is checked/authorized, while a second, related field (`swapData`'s actual token) drives the real action, and the two are never cross-validated.

### Title
Unvalidated `RelayFromAddr` in `handleCreateRelayRequest` allows relay-identity spoofing - (`relay_manager.go`)

### Summary
`handleCreateRelayRequest` derives `from` solely from the attacker-controlled `NebulaControl.RelayFromAddr`/`OldRelayFromAddr` field embedded in the control message payload, rather than from the authenticated peer identity (`h.vpnAddrs`, derived from the verified certificate bound to the Noise session that delivered the message). The only checks performed are "is `from` == me" and "is `target` == me" [1](#0-0) . Nothing ties `from` to the certificate-verified `h.vpnAddrs[0]` of the peer that actually sent the authenticated packet.

### Finding Description
The handshake/cert machinery (`handshake/machine.go` `validateCert`) and `HandshakeManager.validatePeerCert`/`beginHandshake` establish a strong binding between a `HostInfo`'s `vpnAddrs` and its verified certificate, and this identity is what the firewall and hostmap rely on elsewhere (e.g. `outside.go`'s `handleOutsideRelayPacket`, and firewall spoofing tests such as `TestFirewall_ConntrackSourceSpoofingAcrossPeers` and `TestFirewall_DropIPSpoofing` in `firewall_test.go`, which explicitly guard against a peer claiming an overlay identity that isn't theirs) [2](#0-1) [3](#0-2) .

However, `relay_manager.go`'s `handleCreateRelayRequest` breaks this pattern: it reads `from := protoAddrToNetAddr(m.RelayFromAddr)` directly out of the Control message body — a field fully controlled by the sending peer — and uses it as the key for `AddRelay`, `QueryRelayForByIp`, and subsequent relay-state bookkeeping (`h.relayState.QueryRelayForByIp(from)`), instead of validating that `from` equals (or is consistent with) `h.vpnAddrs[0]`, the identity already verified for `h` via its certificate [4](#0-3) . The only self-consistency checks that exist are "is `from` == my own address" and "is `target` == my own address"; there is no check that `from` matches the sender `h`'s own certified identity.

This exactly mirrors the reported bug class: two data items describing "who this operation is for" (the authenticated `HostInfo`/cert identity vs. the declared `RelayFromAddr` field inside the message) are never cross-checked before the relay's internal state and indexes are built and used to route/forward encrypted traffic.

### Impact Explanation
An authenticated-but-malicious peer `h` (who has a valid cert and an established tunnel to a relay node, but is not the vpnAddr it claims via `RelayFromAddr`) can request the relay to set up `TerminalType`/`ForwardingType` relay state keyed to an arbitrary `from` address that isn't `h`'s own verified vpnAddr. Because `handleOutsideRelayPacket`'s forwarding logic (`outside.go:176-247`) subsequently looks up forwarding targets purely by relay index/`PeerAddr` bookkeeping populated from this unverified `from` value, this can let an attacker poison relay routing state, effectively impersonating another VPN node for relay purposes — a form of remote state poisoning affecting message forwarding trust in the mesh, distinct from ordinary firewall IP-spoofing protections (which only guard TUN-layer packet fields, not the relay control-plane identity fields).

### Likelihood Explanation
The `NebulaControl` `CreateRelayRequest` message is a normal, in-protocol control message processed automatically for any peer that has a valid handshake with a relay-capable node (`relay: am_relay: true`); no special conditions or races are needed to trigger `handleCreateRelayRequest` — any peer able to complete a handshake can send it with an arbitrary `RelayFromAddr`.

### Recommendation
In `handleCreateRelayRequest`, validate that the declared `from`/`RelayFromAddr` corresponds to the authenticated sender's own certificate-verified identity (`h.vpnAddrs`) before creating or updating any relay state, mirroring the self-consistency checks already used elsewhere (e.g. `validatePeerCert`, `TestFirewall_ConntrackSourceSpoofingAcrossPeers`). Reject the request if `from` is not contained in `h.vpnAddrs`.

### Proof of Concept
Not independently reproduced against a running instance in this investigation (no execution environment available). Based on static analysis: a peer `h` with a legitimate handshake to a relay-capable node could send a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <arbitrary_addr>, RelayToAddr: <target>}`; `handleCreateRelayRequest` would process it using `from = <arbitrary_addr>` without ever checking it against `h.vpnAddrs[0]` [1](#0-0) , since no such check exists in the visible code path.

// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
}
