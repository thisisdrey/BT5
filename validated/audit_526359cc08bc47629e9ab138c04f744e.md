### Title
Reward Arbitrage via Vote-Timing Around DPoS Maintenance Cycle Boundary — ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
An unprivileged account can cast a `VoteWitnessContract` transaction immediately before a maintenance cycle boundary, get its vote weight permanently baked into the witness's locked-in vote count for the *entire next cycle*, and then immediately reallocate/withdraw its vote right after the boundary — all without holding the position for any meaningful duration. Because per-cycle reward-per-vote (`Vi`) is computed using the vote-count snapshot fixed at maintenance time rather than a time-weighted measure, the arbitrager collects a full cycle's proportional reward while diluting the payout owed to voters who genuinely held their position the entire cycle. This is the DPoS-voting analog of the "stake right before rebase, unstake right after" arbitrage described in the Yieldy report.

### Finding Description
Vote weight is not locked or time-weighted within a cycle — it can be changed at any time via `VoteWitnessActuator.countVoteAccount`, which unconditionally clears and rewrites the caller's votes on every call with no minimum holding period: [1](#0-0) 

The witness's total vote count used for reward accrual is only re-tallied once per maintenance cycle and then locked in for the *entire upcoming cycle* via `setWitnessVote(nextCycle, ...)`: [2](#0-1) [3](#0-2) 

Reward-per-vote (`Vi`) for a cycle is calculated by dividing that cycle's total reward by the vote count that was locked in at the prior maintenance run — it does not account for how long within the cycle a given voter actually held their vote: [4](#0-3) 

A user's individual reward is then computed purely from the delta of `Vi` between the cycle boundaries multiplied by their recorded vote weight, with no adjustment for the timing of when the vote was cast relative to the boundary: [5](#0-4) 

Because `countVoteAccount` calls `mortgageService.withdrawReward(ownerAddress)` before mutating votes, the snapshot of "last known votes" is captured and stored via `setAccountVote`, which is exactly what the reward-claim logic later reads back to compute the "last cycle" reward — even if the account has already withdrawn its vote by the time it calls `withdrawReward`/`queryReward`: [6](#0-5) 

An attacker flow:
1. Freeze balance ahead of time to obtain TRON Power (freezing itself is not the attack window).
2. Just before the maintenance boundary of cycle `N`, submit `VoteWitnessContract` allocating full TRON Power to a target SR. `countVoteAccount` records this as a net new vote in `VotesStore`.
3. When maintenance for cycle `N` executes, `countVote` tallies this vote into the witness's `voteCount`, and `setWitnessVote(N+1, ...)` locks that inflated total in for cycle `N+1`.
4. Immediately after the boundary (first block of cycle `N+1`), the attacker calls `VoteWitnessContract` again with a different/zero allocation, removing themselves from consideration for cycle `N+2`'s vote-count tally.
5. Despite having withdrawn their vote at the very start of cycle `N+1`, the attacker's vote weight was already baked into cycle `N+1`'s locked vote-count denominator and their own `AccountVote` snapshot, so when they call `withdrawReward`/`queryReward` afterward, they still receive the full cycle `N+1` reward share as if they had voted for the entire cycle.

### Impact Explanation
This lets a transaction sender extract disproportionate SR voting rewards without bearing the corresponding holding-time/opportunity cost, at the expense of genuine long-term voters, since the fixed per-cycle reward pool is now divided among a vote-count total that includes a voter who was only present for a single block. This is a fund-redistribution/dilution exploit reachable by any account holder capable of submitting `VoteWitnessContract` transactions and requires no special privilege — matching the reported bug class of profiting from timing a stake/unstake around a reward-snapshot boundary.

### Likelihood Explanation
The maintenance interval (default 6 hours) is public and deterministic (`getNextMaintenanceTime`), so timing a transaction just before/after the boundary is trivial for any actor watching the chain. No lock-up period is required to cast or reallocate a vote (only actual unfreezing of principal has a delay), so the attack is a pure vote-timing play requiring only two ordinary transactions.

### Recommendation
Tie reward eligibility to a minimum holding duration within the cycle (e.g., require the vote to exist across the full snapshot boundary before crediting reward for that cycle), or use a time-weighted average vote count for `Vi` computation instead of the single point-in-time snapshot taken at maintenance. Alternatively, delay vote-count updates so that a vote only becomes reward-eligible starting the cycle *after* it has been continuously held through a full maintenance cycle without modification.

### Proof of Concept
1. Freeze balance to obtain TRON Power for account `A`.
2. Track `getNextMaintenanceTime()` (exposed via `Wallet`/API) and submit `VoteWitnessContract(A -> SR1, full power)` in the last block before that timestamp.
3. Observe `MaintenanceManager.doMaintenance()` execute, locking `A`'s vote weight into `delegationStore.setWitnessVote(nextCycle, SR1, updatedTotal)`.
4. In the first block of the new cycle, submit `VoteWitnessContract(A -> SR2 or empty)`, removing `A` from the vote tally used in the *next* maintenance run.
5. After the cycle completes, call `withdrawReward`/`queryReward` for `A` and confirm it receives a full cycle's proportional reward computed from `MortgageService.computeReward`, despite having held the vote for effectively one block.

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  private void accumulateWitnessVi(long cycle, byte[] address) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long voteCount = getWitnessVote(cycle, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
