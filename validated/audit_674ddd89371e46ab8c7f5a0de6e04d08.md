### Title
Unbounded blocking on `future.get()` in `VerifyTransferProof` precompile bypasses CPU-time deadline, allowing transaction-triggered DoS — (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiled contract `VerifyTransferProof` (invoked when a smart contract calls the shielded-transfer proof-verification precompile, gated by `allowShieldedTRC20Transaction`) offloads zk-SNARK verification work to a small, static, fixed-size thread pool and waits on a `CountDownLatch` with the transaction's remaining CPU-time budget. The result of that timed wait is discarded, and the code then calls `Future.get()` on every submitted task with **no timeout**, exactly the DoS pattern described in the advisory for `node-worker-threads-pool` (`StaticPool` tasks executed with no enforced timeout).

### Finding Description
In `VerifyTransferProof.execute`: [1](#0-0) 

- Up to 5 tasks (`SaplingCheckSpendTask`, `SaplingCheckOutputTask`, `SaplingCheckBingdingSig`) are submitted to a **static, shared, fixed 5-thread pool** (`workersInConstantCall` / `workersInNonConstantCall`), each performing native JNI calls into `librustzcash`. [2](#0-1) 
- `countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` is called and its result stored in `withNoTimeout`, but **that boolean is never checked**.
- The code unconditionally proceeds to `future.get()` for each future, which is an **unbounded blocking call** — no `future.get(timeout, unit)` is used, no `future.cancel()` is attempted if the deadline was already exceeded.
- The task methods (`SaplingCheckSpendTask.call()`, etc.) call into native code (`JLibrustzcash.librustzcashSaplingCheckSpendNew`, etc.) inside a `finally { countDownLatch.countDown(); }`, so the latch and the eventual future completion depend entirely on the native call returning. [3](#0-2) 

Because the thread pool is shared across all shielded-transfer verifications (constant and non-constant call each have their own pool of exactly 5 threads), and each verification transaction can occupy up to 5 of those threads simultaneously (`spendCount(≤2) + receiveCount(≤2) + 1`), an attacker who can keep submitting shielded-transfer transactions can saturate the pool. Once the pool is saturated, the JVM `future.get()` call executed on the block-processing / VM thread has no timeout and will block indefinitely — completely bypassing the `checkCPUTimeLimit`/`OutOfTimeException` machinery that governs every other TVM opcode via `Program.checkCPUTimeLimit`. [4](#0-3) 

This is the same root-cause class as CVE-2021-29057: a worker-pool task is executed and awaited without an enforced timeout, so a slow/never-returning task can starve the pool and block the caller forever.

### Impact Explanation
Unlike ordinary TVM opcode execution — which is bounded per-opcode by `program.checkCPUTimeLimit(opName)` inside `VM.play` — this precompile's blocking wait on `future.get()` has no such bound once the latch timeout has already elapsed. If the shared, statically-sized 5-thread pool is saturated (by concurrently submitted shielded transactions, each consuming up to 5 threads) or a native `librustzcash` call stalls, the thread executing `VMActuator`/block application blocks indefinitely. Because transaction execution during block application happens on the node's core processing path (`Manager` block application via `VMActuator`), this can stall the node's ability to apply further transactions/blocks — a node hang / DoS reachable from a single crafted transaction stream, without needing SR/witness privileges.

### Likelihood Explanation
Reaching this code only requires the ability to broadcast a `TriggerSmartContract` (or shielded-transfer) transaction whose data triggers the `VerifyTransferProof` precompile once `allowShieldedTRC20Transaction` is enabled (a live, standard java-tron proposal flag on mainnet). No special privileges are required — any transaction broadcaster can submit shielded-transfer proof-verification calls repeatedly to hold the pool's 5 threads occupied, at which point subsequent VM threads calling into this precompile block on `future.get()` past the intended CPU deadline.

### Recommendation
- Check the `withNoTimeout` (or renamed) result from `countDownLatch.await(...)`; if `false`, immediately cancel/interrupt the outstanding futures and raise the same `OutOfTimeException`/`notEnoughTime` path used elsewhere in the VM instead of falling through to unconditional `future.get()`.
- Replace `future.get()` with a bounded `future.get(remainingTimeoutNanos, TimeUnit.NANOSECONDS)` for every future in the loop, so the CPU-time budget is enforced consistently with the rest of `Program.checkCPUTimeLimit`.
- Consider sizing/isolating the `workersInConstantCall`/`workersInNonConstantCall` pools relative to concurrent-transaction concurrency limits so a burst of shielded transfers cannot starve verification threads for unrelated transactions.

### Proof of Concept
1. Enable/observe `allowShieldedTRC20Transaction` (already a live governance flag on mainnet).
2. From an unprivileged account, broadcast a `TriggerSmartContract` transaction whose call data reaches the shielded `VerifyTransferProof` precompile with `spendCount=2, receiveCount=2` (5 tasks submitted per call), repeated concurrently to fully occupy both the 5-thread `workersInConstantCall` and `workersInNonConstantCall` pools. [5](#0-4) 
3. Once the pools are saturated (e.g., by concurrent triggers or artificially slow native inputs), submit one more shielded-transfer transaction; its `countDownLatch.await(...)` will time out (`withNoTimeout=false`), but the code ignores this and calls `future.get()` unconditionally, blocking the executing thread (block-application / VM thread) indefinitely instead of throwing a timeout exception. [6](#0-5) 

Note: I was unable to further verify the exact fixed precompile address mapping or the runtime worst-case latency of the native `librustzcash` calls within the available index; a background Devin session with full repository/build access would be needed to confirm exact exploitation timing and the TVM address dispatch table for this precompile.
