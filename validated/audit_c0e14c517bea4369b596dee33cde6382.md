### Title
`handle_unsolicited_StackerDBPushChunk` advertises an unwritten `slot_version` in its `StackerDBChunkInv` reply, sent before the chunk is actually committed to the local StackerDB - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`handle_unsolicited_StackerDBPushChunk` builds its `StackerDBChunkInv` reply by calling `make_StackerDBChunksInv_or_Nack` (which reads the *current, on-disk* `slot_versions`) and then patches the in-memory `data.slot_versions[slot_id]` to the attacker-supplied `chunk_data.chunk_data.slot_version` after only `validate_received_chunk` (signature/size/monotonicity) passes — not after any actual storage write. The reply is then signed and sent immediately, while actual persistence of the chunk is deferred to the relayer/storage path (`Ok((false, true))`), which independently enforces write-frequency/max-writes limits. This creates a window where the node asserts a slot version in its outbound inventory that it has not yet — and may never — actually store.

### Finding Description
`make_StackerDBChunksInv_or_Nack` (stackslib/src/net/stackerdb/mod.rs:585-639) fetches `slot_versions` via `self.stackerdbs.get_slot_versions(contract_id)` — the authoritative, committed on-disk state. `handle_unsolicited_StackerDBPushChunk` (mod.rs:742-871) then runs `validate_received_chunk` (mod.rs:649-718), which only checks chunk size, slot-id bounds, signer authentication, and version monotonicity (`data.slot_version >= expected_version` and `<= config.max_writes`). Explicitly, per its own doc comment: "NOTE: does not check write frequency, since the caller has different ways of doing this" (mod.rs:644-648). After this check passes, the code unconditionally patches the in-memory inventory: `*slot_version = chunk_data.chunk_data.slot_version;` (mod.rs:807), then immediately signs and sends this `StackerDBChunkInv` back to the pushing peer (mod.rs:863-869) via `Ok((false, true))`, i.e., "don't buffer, forward to relayer" — meaning the actual DB commit of the chunk happens later, out-of-band, in the relayer/storage path where write-frequency (`write_freq`) and other storage-time checks are enforced.

Consequently, if the storage-time write-frequency/other checks reject the write (e.g., the slot was written too recently), the node has already broadcast an inventory entry claiming it holds `slot_version = chunk_data.chunk_data.slot_version`, while the actual on-disk value remains unchanged at the older version. Any peer relying on this specific reply's inventory content will believe the node has a chunk version it does not have.

### Impact Explanation
This causes divergence between the advertised `StackerDBChunkInv.slot_versions` entry and what `stackerdbs.get_slot_versions(...)` would return immediately after, for a slot the node has not actually written. Downstream sync logic ordinarily fetches inventories fresh via `make_StackerDBChunksInv_or_Nack` (which reads the DB directly) for routine inventory queries — this specific unsolicited-push acknowledgment path is the only one that patches a stale in-memory snapshot rather than re-querying the DB after the store attempt. The practical effect is a false/stale inventory advertisement returned to exactly one peer (the pusher), which could steer that peer into requesting a chunk version the node cannot serve, causing wasted round-trips or (until a later poll refreshes state) reflects state that was never canonically written to StackerDB. This is a narrower, retryable, best-effort DB inconsistency rather than a broadly-propagated forged/authenticated write, since the value only reaches the single reply message the pusher receives, and the underlying data write is still gated by the relayer's real checks.

### Likelihood Explanation
Triggering the race requires the attacker to have a legitimately-signed chunk for a slot they own, push it unsolicited, and have the storage-time check (e.g., write-frequency) reject the same chunk that passed `validate_received_chunk`'s weaker checks. I could not fully verify, within available tool budget, the exact code path/enforcement point for `write_freq`/`max_writes` at storage time in `stackslib/src/net/stackerdb/db.rs` or the relayer, so I cannot confirm with certainty how often or under what precise conditions the store is rejected after the ack is sent, nor whether other guards elsewhere close this window (e.g., re-validation before actual DB commit). This uncertainty limits confidence in the severity/likelihood classification.

### Recommendation
In `handle_unsolicited_StackerDBPushChunk`, do not patch and send the `StackerDBChunkInv` reply speculatively before the chunk is actually committed. Either (a) defer sending the reply until after the relayer/storage path confirms the write succeeded, re-reading `get_slot_versions` fresh at that point, or (b) only patch the advertised version if the write-frequency/storage-time checks are performed inline here before the ack is sent, so the acknowledgment never advertises a version not yet durably stored.
