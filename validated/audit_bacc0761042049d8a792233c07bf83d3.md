### Title
`liquidate()`'s `maxLiquidable` cap conflicts with `debtFloorInUsd` (and `quoteLiquidateMax` ignores the floor), creating unliquidatable positions and guaranteed bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate()` enforces two limits computed by different formulas: a repay fraction cap `amountToRepay_ <= balance * maxLiquidable` (line 567) and a dust-debt floor that forces the remaining debt to be either `0` or `>= debtFloorInUsd` (lines 571-579). These constraints are mutually exclusive whenever the position's debt satisfies `debt < debtFloorInUsd / (1 - maxLiquidable)`, i.e. `debt - maxLiquidable * debt < debtFloorInUsd < debt`. In that region, every partial repayment leaves dust below the floor (reverts with `RemainingDebtIsLowerThanTheFloor`), and a full repayment exceeds `maxLiquidable` (reverts with `AmountGreaterThanMaxLiquidable`). Additionally, the `quoteLiquidateMax()` view computes the max repayable amount using only `balance * maxLiquidable` and the collateral limit, completely ignoring the floor check, so it returns amounts that `liquidate()` will always revert on — the same "view vs. enforcement inconsistency" bug class as the reference report.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

Any `amountToRepay_` must satisfy **both**:
- `amountToRepay_ <= _debtTokenBalance * maxLiquidable` (with `maxLiquidable < 1e18`, full repayment is impossible since `wadDiv(balance, balance) = 1e18 > maxLiquidable`)
- `balance - amountToRepay_` must be `0` or `>= debtFloorInUsd` in USD terms

When `maxLiquidable < 1e18` and `debtFloorInUsd > 0`, the feasible set is empty for `debtUsd` in `(debtFloorInUsd, debtFloorInUsd / (1 - maxLiquidable))`. Positions can land in this dead zone without any user action: `DebtToken` balances grow via `accrueInterest()`, and oracle price changes shrink the USD value of debt. `DebtToken._mint` (contracts/DebtToken.sol:580-588) only prevents *minting* debt below the floor; it does not prevent drift into the dead zone afterward.

Meanwhile `quoteLiquidateMax` (contracts/Pool.sol:419-440) computes `_maxAmountToRepay = balance * maxLiquidable` capped by the collateral-value-equivalent repay, without modeling the floor at all — so the protocol's own quoter advertises repay amounts that the state-changing function will reject 100% of the time for dead-zone positions.

### Impact Explanation
A position in the dead zone cannot be liquidated by anyone, ever. If it is underwater (`_depositInUsd < _debtInUsd`), the pool permanently carries unrecoverable bad debt — synthetic tokens remain backed by less collateral than their face value, harming all holders of that synth and the protocol's solvency. The liveness failure applies to every liquidation attempt, not just an edge case: at 50% `maxLiquidable` and a $100 `debtFloorInUsd`, any position with debt between $100 and $200 is completely immune to liquidation.

### Likelihood Explanation
Likelihood depends on deployed configuration: both `debtFloorInUsd > 0` (it exists expressly to keep liquidator incentive, per `PoolStorageV1` docs) and `maxLiquidable < 1e18` must hold simultaneously — a configuration explicitly exercised in `test/Pool.test.ts` (50% close factor) and preserved across all `PoolUpgrader` versions. Once set, no attacker action is needed; interest accrual or normal price drift pushes borderline positions into the dead zone automatically. An attacker can also deliberately park a leveraged position near the threshold via `SmartFarmingManager.leverage`/`DebtToken.issue` to grief the pool. Note the floor check compares *only* that synth's debt USD value, so multi-debt positions don't escape it.

### Recommendation
When `amountToRepay_ == _debtTokenBalance` (full repayment), skip or relax the `maxLiquidable` check — i.e., allow `ratio <= maxLiquidable || amountToRepay_ == balance`. Alternatively, treat `remainingDebt < debtFloorInUsd` as permission for a full repay regardless of the cap. Update `quoteLiquidateMax` to apply the same rules as `liquidate`: if the capped amount would leave dust below the floor, return the full balance (or `0` when full repayment is also disallowed).

### Proof of Concept
Conceptual Hardhat fork/vector (matches `test/Pool.test.ts` setup):

```ts
// given: debtFloorInUsd = $100, maxLiquidable = 0.5e18, msUSD-like synth at $1
await pool.updateDebtFloor(parseEther('150'));   // $150
await pool.updateMaxLiquidable(parseEther('0.5')); // 50%

// alice mints ~$149 of msSynth against collateral; oracle price drops slightly
// so position is unhealthy with debt = $149 (in dead zone: 149 > 150? adjust so
// debt is e.g. $149 debt token units quoted at > floor, or accrue interest to reach it)

const debt = await msSynthDebtToken.balanceOf(alice.address); // debtUsd in (floor, floor/(1-M))

// any partial repay leaves dust < floor:
await expect(pool.connect(liq).liquidate(msSynth.address, alice.address, debt.div(2), msdToken.address))
  .revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// full repay exceeds maxLiquidable:
await expect(pool.connect(liq).liquidate(msSynth.address, alice.address, debt, msdToken.address))
  .revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// yet the quoter still advertises a "max" amount that always reverts:
expect(await pool.quoteLiquidateMax(msSynth.address, alice.address, msdToken.address)).gt(0);
```

Caveat: severity depends on the deployed `debtFloorInUsd` and `maxLiquidable` values, which I could not verify in the deployment artifacts within this analysis — both must be non-zero/sub-100% simultaneously for the dead zone to exist.
