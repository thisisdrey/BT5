### No vulnerability found for this question.

The behavior described is the intended, documented design of NEP-539 congestion control, not a bug. `CongestionControl::process_tx_limit` deliberately reduces the gas budget for converting new transactions to receipts as a shard's `incoming_congestion` rises, mixing between `max_tx_gas` and `min_tx_gas` based on `delayed_receipts_gas` relative to `max_congestion_incoming_gas` [1](#0-0) . This throttling applies fairly to all transactions destined for that shard, not selectively to any particular account, and is explicitly documented as intentional in the design rationale ("we heavily reduce the gas allocated for new transactions, in order to have more capacity to work on finishing the waiting receipts... This is why we added this feature") [2](#0-1) .

Any account, malicious or not, can raise `delayed_receipts_gas` on its own shard simply by submitting legitimate transactions/receipts — this is normal network usage, and the exact scenario (raising incoming congestion below `reject_tx_congestion_threshold` and observing reduced `process_tx_limit`) is already covered by an existing test, `measure_tx_limit`, in `test-loop-tests/src/tests/congestion_control_limits.rs` [3](#0-2) . There is a corresponding unit test, `test_incoming_congestion`, verifying `process_tx_limit()` degrades gradually with congestion level, confirming this is by-design behavior rather than an overlooked edge case [4](#0-3) .

This does not meet the bar for a valid finding under the stated rules: there is no theft or freezing of funds, no double-spend, no authorization escalation, no state-root divergence, and no shard-halting panic — only a throughput degradation that is a deliberate, protocol-level fairness/backpressure mechanism to protect the network from congestion collapse. Temporarily reduced tx throughput during high load (whether organic or attacker-induced) is the system working as designed, not a security vulnerability, and matches the excluded category of "speculative resource-hygiene claims with no reachable mainnet scenario" causing concrete fund loss or consensus failure.

        let mut info = CongestionInfo::default();

        info.add_delayed_receipt_gas(config.max_congestion_incoming_gas).unwrap();

            let control = CongestionControl::new(config, info, 0);
            assert_eq!(1.0, control.congestion_level());
            // fully congested, no more forwarding allowed
            assert_eq!(Gas::ZERO, control.outgoing_gas_limit(ShardId::new(1)));
            assert!(control.shard_accepts_transactions().is_no());
            // processing to other shards is restricted by own incoming congestion
            assert_eq!(config.min_tx_gas, control.process_tx_limit());
        }

        // Assert threshold is 80%. Change this number if the config changes
        assert_eq!(0.8, config.reject_tx_congestion_threshold);

        // reduce congestion to 80%
        info.remove_delayed_receipt_gas(config.max_congestion_incoming_gas.checked_div(5).unwrap())
            .unwrap();
        {
            let control = CongestionControl::new(config, info, 0);
            assert_eq!(0.8, control.congestion_level());
            assert_eq!(
                mix_gas(config.max_outgoing_gas, config.min_outgoing_gas, 0.8),
                control.outgoing_gas_limit(ShardId::new(1))
            );
            // at 80%, still no new transactions are allowed
            assert!(control.shard_accepts_transactions().is_no());
        }

        // reduce congestion to 10%
        info.remove_delayed_receipt_gas(

        .unwrap();
