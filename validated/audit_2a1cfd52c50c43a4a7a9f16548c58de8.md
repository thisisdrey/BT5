### Title
Unauthenticated `POST /v3/blocks/upload/` triggers network-wide relay of attacker-supplied Nakamoto block regardless of `broadcast` flag - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_handle_request` gates the call to `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` solely on `data_resp.accepted`, ignoring `self.broadcast`/authentication state entirely. An attacker can POST a block with no `broadcast` query parameter and no `authorization` header (which `try_parse_request` allows, since the 401 check only fires when `broadcast && !authenticated`), and if the block is independently accepted by `Relayer::process_new_nakamoto_block_ext`, the handler still queues it for network relay.

### Finding Description
In `try_parse_request` (lines 99-122), the `broadcast=1` requirement for authentication is enforced only via `if broadcast && !authenticated { return Err(...) }`. ` [1](#0-0) ` This means a request with `broadcast` unset (or `broadcast=0`) passes through unauthenticated, with `self.broadcast` set to `Some(false)`. ` [2](#0-1) `

In `try_handle_request`, the block is processed via `Relayer::process_new_nakamoto_block_ext` passing `self.broadcast.unwrap_or(false)` — presumably controlling internal handling — but the subsequent decision to call `node.set_relay_message(...)` is based purely on `data_resp.accepted`, not on `self.broadcast`: ` [3](#0-2) `. The stale comment `// should set to relay...` suggests the intended guard (checking `self.broadcast`) was never wired in.

`node.set_relay_message` stores the message on `StacksNodeState`, which is later retrieved via `take_relay_message()` in `ConversationHttp::handle_request` in `stackslib/src/net/rpc.rs` and returned as `Option<StacksMessageType>` up the call stack: ` [4](#0-3) ` and ` [5](#0-4) `. This return value is the mechanism by which HTTP-received data becomes a network-relayable `StacksMessageType`, and `NakamotoBlocks` is one of the message types explicitly handled by `PeerNetwork::dispatch_request`'s `NetworkRequest::Broadcast` arm, which samples peers and broadcasts the payload: ` [6](#0-5) `.

Thus, the equality claimed in the question holds: `set_relay_message` is invoked whenever `data_resp.accepted == true`, independent of `self.broadcast == Some(true)` and `authenticated == true`.

### Impact Explanation
Any unauthenticated remote peer that can reach the node's RPC port can submit a Nakamoto block without the RPC secret and without setting `broadcast=1`. If chainstate happens to accept it (e.g. because it is a well-formed, otherwise-valid block for a tenure/consensus hash the node already has, but the submitter is not the legitimate miner/relay path expects), the node still marks it for relay to the P2P network, propagating the block to its peers as if it had been legitimately broadcast. This defeats the auth gate's purpose and results in network propagation of data that should have required the secret, matching the "network-wide propagation of forged/unauthorized data" Critical category.

### Likelihood Explanation
The attacker needs only network reachability to the RPC port — no secret, no privileged peer role. The bar for `accepted` depends on `Relayer::process_new_nakamoto_block_ext`'s acceptance criteria, which is outside the direct code path examined here but is the same block-storage-acceptance logic exercised on any inbound block; the vulnerability is triggered whenever that acceptance succeeds, which is a routine and repeatable outcome (e.g., re-posting a block the node would accept anyway). This is repeatable per accepted block.

### Recommendation
Gate the `set_relay_message` call on the same authorization state used for `broadcast`, e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
Ensure `self.broadcast` can only be `true` when `try_parse_request` established `authenticated == true` (already the case), and require that condition before relaying.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postblock_v3.rs` (or extend existing `postblock_v3` test module) that:
1. Constructs an `RPCPostBlockRequestHandler` with `auth: Some("secret".to_string())`.
2. Builds a `StacksHttpRequest` via `StacksHttpRequest::new_post_block_v3` (no `broadcast` query arg, no `authorization` header) wrapping a block known to be accepted by the test chainstate fixture.
3. Calls `try_parse_request` then `try_handle_request` against a `StacksNodeState` built from a `TestPeer`'s chainstate where the block will be accepted.
4. Asserts `node.take_relay_message()` returns `None`.
5. Currently, this assertion fails because `set_relay_message` is called unconditionally on `accepted`, demonstrating the bug.
