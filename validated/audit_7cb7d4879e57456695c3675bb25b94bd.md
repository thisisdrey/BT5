### Title
Unbounded array allocation in `BatchValidateSign`/`ValidateMultiSign` TVM precompiles before size validation — memory-exhaustion DoS via a single crafted transaction - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` (precompile address `0x...09`) and `ValidateMultiSign` (`0x...0a`) precompiled contracts decode ABI-encoded array-length fields directly from attacker-controlled call data and use them to allocate Java arrays (`new byte[len][]`) **before** the `MAX_SIZE` bound is enforced on the legacy code path (`VMConfig.allowTvmSelfdestructRestriction()` == false), and unconditionally for the address array in `BatchValidateSign`. A tiny, cheaply-crafted call data payload can encode an array-length word close to `Integer.MAX_VALUE`, forcing the node to attempt a multi-gigabyte allocation for every execution of the precompile, analogous to the crafted-GIF decompression-bomb pattern in CVE-2023-3614 (small input → disproportionate resource consumption → node unresponsiveness).

### Finding Description
`extractBytesArray` and `extractBytes32Array` read the array length straight out of the call data with no upper bound before allocating: [1](#0-0) 

`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` only pre-check the array-length words against `MAX_SIZE` when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; on the legacy branch the extraction functions are called with the raw, unchecked length: [2](#0-1) 

Even when the guard is enabled, it is only applied to the *signature* array in `BatchValidateSign` for the branch that calls `extractSigArray`; the address array is extracted via `extractBytes32Array` in the same statement block, but only after (not before) the `addrArraySize > MAX_SIZE` check — while the equivalent unconditional call in `ValidateMultiSign` for `extractBytesArray`/`extractSigArray` has the same structural weakness for the legacy branch: [3](#0-2) 

The recently added `isValidAbiEncoding` check (gated by `VMConfig.allowTvmOsaka()`) only validates that the *total* call-data length is congruent to the expected header/item word shape; it does not validate the *value* of the length words used as `len` in `extractBytesArray`/`extractBytes32Array`, so a data blob of only a few hundred bytes can still pass this shape check while encoding a length word of up to `Integer.MAX_VALUE` at the position read by `words[offset].intValueSafe()`.

Because `intValueSafe()` converts an attacker-chosen 32-byte `DataWord` to a Java `int` (safely clamped, but still up to `Integer.MAX_VALUE`), `new byte[len][]` can be invoked with `len` near `2^31-1`, immediately requesting on the order of 16 GB of reference-array memory in a single allocation.

### Impact Explanation
This precompile is reachable by any account issuing a `TriggerSmartContract`/`TriggerConstantContract` transaction that performs a `CALL`/`STATICCALL` to the precompiled address (`0x...09` or `0x...0a`), or by any deployed contract forwarding a low-level `call` to that address — no special permission, stake, or prior state is required beyond enough bandwidth/energy to submit the transaction. Because the huge-length word does not need to be backed by real data (only the ABI "header" word at that offset needs the malicious value; the actual call-data byte length can be tiny), the attacker's cost is negligible compared with the multi-gigabyte allocation attempt forced on the validating/executing node. Repeated submissions can trigger sustained massive allocations/garbage-collection pressure on every full node that executes or re-validates the transaction, degrading throughput or making the node unresponsive — a resource-exhaustion Denial of Service directly analogous to the crafted-GIF CVE (tiny attacker input, outsized server-side resource cost).

### Likelihood Explanation
Exploitability depends on whether `VMConfig.allowTvmSelfdestructRestriction()` is active on the target network: when it is disabled (default on chains/environments where that specific hard fork has not yet activated, e.g. private/test networks or before mainnet activation), the vulnerable code path is fully unguarded and trivially reachable with a single transaction. Even where the flag is active, the guard construction (`extractBytes32Array` invoked without a preceding bound check within `BatchValidateSign`) leaves a structural weakness that a future refactor could easily reintroduce, and the shape-only `isValidAbiEncoding` check added for TIP-854 does not close this specific length-value gap. This makes it a Medium-severity, reachable, low-cost DoS analog.

### Recommendation
Enforce the `MAX_SIZE` bound on every length word (`words[offset].intValueSafe()`) unconditionally, *before* calling `extractBytesArray`, `extractSigArray`, or `extractBytes32Array`, regardless of `VMConfig.allowTvmSelfdestructRestriction()`. Additionally, validate that any offset/length word used for array sizing is within `[0, MAX_SIZE]` (and within the actual call-data bounds) inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves, so the fix is not dependent on caller discipline or feature-activation state.

### Proof of Concept
1. Craft `TriggerSmartContract` call data (or a helper contract that forwards a raw `CALL`) targeting precompile address `0x...0000000000000000000000000000000000000009` (`BatchValidateSign`) on a network/environment where `allowTvmSelfdestructRestriction` is not yet active.
2. Build call data of the minimal legal shape (`ABI_HEADER_WORDS=5` + at least one `ABI_ITEM_WORDS=6` block) so it passes `isValidAbiEncoding`, but set the word at the offset pointed to by `words[2]` (the addresses-array "length" slot) to `0x7FFFFFFF`.
3. Submit the transaction with enough energy to cover `getEnergyForData` (which is computed from `data.length`, not from the huge encoded length), so it passes the pre-execution energy check cheaply.
4. On execution, `extractBytes32Array` runs `new byte[0x7FFFFFFF][]`, attempting a multi-gigabyte allocation on every node that executes/validates the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
