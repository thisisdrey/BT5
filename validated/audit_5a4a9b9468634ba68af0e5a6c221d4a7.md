### Title
LinkRepositoryToObjectPool resolves object pool identity purely by path with no check that the pool is unchanged between validation and linking, permitting cross-repository object exposure via a recreated pool - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` and its helpers (`poolForRequest` → `objectpool.FromProto` → `objectpool.Link`) identify an object pool solely by its `StorageName`/`RelativePath`. There is no identity token (e.g. a pool generation ID, content hash, or lock held across the whole operation) that ties the pool validated at the start of the RPC to the pool that is actually linked at the end. This mirrors the `placeBid()` bug class: a mutable resource is referenced by a name/path that can be silently replaced between the time it is "checked" and the time it is "used".

### Finding Description
`LinkRepositoryToObjectPool` (`internal/gitaly/service/objectpool/link.go:10-28`) does:
1. `s.poolForRequest(ctx, req)` → `objectpool.FromProto` (`internal/git/objectpool/pool.go:48-91`), which resolves the pool's path via the locator and validates it's a git repository (`pool.IsValid(ctx)`), but performs no locking and captures no identity/version of the pool contents. [1](#0-0) 
2. `pool.Link(ctx, repo)` → `Link()` in `internal/git/objectpool/link.go:28-84`, which re-derives the pool's relative path (`getRelativeObjectPath`) and, if not already linked, writes that path into `objects/info/alternates`. [2](#0-1) 

Between step 1 (validation) and step 2 (write of the alternates file), the directory at that `RelativePath` can be entirely replaced: `DeleteObjectPool` has "no safety checks in place" and can remove a pool at any time, and a fresh `CreateObjectPool` can be immediately created at the exact same relative path (pool paths are deterministic, derived from the origin repository, e.g. `@pools/xx/yy/<hash>.git` per `internal/gitaly/storage/repository_path.go`). [3](#0-2) [4](#0-3) 

Because `Link()` never re-validates that the pool it is about to link against is the *same* pool that was checked (no pool generation counter, no content signature, no hold on a lock spanning both calls), a concurrent `DeleteObjectPool` + `CreateObjectPool` sequence against the same path — analogous to the auction "restart" in the external report — causes the RPC to complete against a semantically different pool than the caller intended, without any error.

### Impact Explanation
If a pool is deleted and recreated (from a different, unrelated origin repository) between validation and the alternates write, `LinkRepositoryToObjectPool` will link the caller's repository to the *new* pool instead of the one it validated. This can:
- Deduplicate/expose objects from an unrelated repository into the caller's repository via the alternates mechanism (`objects/info/alternates`), a cross-repository object access issue.
- Corrupt the caller's repository state if the new pool has an incompatible object hash/format or fewer objects, since the linking flow also strips the member's own packfile bitmaps (`removeMemberBitmaps`) based on stale assumptions about the pool's contents. [5](#0-4) 

This is comparable to the Medium-severity TOCTOU in the report: the caller commits to a decision based on stale state, and the actual operation silently completes against a different, unexpected resource, leading to unintended data exposure/corruption rather than an outright crash.

### Likelihood Explanation
`CreateObjectPool`/`DeleteObjectPool`/`LinkRepositoryToObjectPool` are part of the normal, user-triggered fork lifecycle (fork creation links a new fork's repository into the origin's object pool, as exercised by `TestCompleteForkCreationFlow`). [6](#0-5) 
Exploitation requires winning a race window — the pool must be deleted and recreated at the identical derived path between the `poolForRequest` validation and the `Link()` write — which is a narrow window in a single-node deployment, but is more plausible under concurrent fork/cleanup housekeeping load or via a malicious client deliberately racing `DeleteObjectPool`/`CreateObjectPool` calls against a target pool path it can predict deterministically from `DerivePoolPath`/`IsRailsPoolRepository`. [7](#0-6) 

### Recommendation
Bind the pool identity used at commit-time to the identity validated at request-time:
- Introduce a pool generation/version marker (or capture the pool's current HEAD/objects checksum) when `poolForRequest`/`objectpool.FromProto` validates the pool, and re-check that marker immediately before writing the alternates file in `Link()`, failing the RPC (similar to comparing `auction.startBlock`) if the pool was recreated in between.
- Alternatively, hold a repository lock (as already used elsewhere, e.g. `repoutil.Lock` in `internal/gitaly/repoutil/create.go`) across the pool-validation-and-link critical section so that a concurrent `DeleteObjectPool`/`CreateObjectPool` cannot interleave.
- Where transactions/WAL are enabled, ensure `LinkRepositoryToObjectPool` runs against a snapshot LSN so the pool's state is fixed for the duration of the RPC, consistent with how the transaction manager already prevents repository-deletion races for normal repositories (`ErrRepositoryConcurrentlyDeleted`). [8](#0-7) 

### Proof of Concept
1. Client A calls `CreateObjectPool` with `Origin = RepoX`, producing pool `P` at deterministic path `@pools/aa/bb/<hashX>.git`.
2. Client A begins `LinkRepositoryToObjectPool(Repository=RepoX, ObjectPool=P)`. The RPC calls `poolForRequest` → `FromProto`, which validates `P` exists and is a valid repository based on `RepoX`'s content.
3. Concurrently, an attacker (or a legitimate but racing housekeeping/cleanup process) calls `DeleteObjectPool(ObjectPool=P)` then immediately `CreateObjectPool(ObjectPool=P, Origin=RepoY)` — recreating the same on-disk path with a completely different repository's objects, since pool paths are deterministically derived and reusable once deleted.
4. Client A's still-in-flight `LinkRepositoryToObjectPool` call proceeds to `pool.Link(ctx, repo)`, which recomputes the relative alternates path purely from `P`'s path (now pointing at `RepoY`'s pool) and writes it into `RepoX`'s `objects/info/alternates`, without detecting the substitution.
5. `RepoX` now has `RepoY`'s objects available as alternates, and its previous bitmap files have been stripped based on the (now stale) validation — resulting in unintended cross-repository object exposure/corruption with no error returned to Client A.

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

func removeMemberBitmaps(ctx context.Context, pool *localrepo.Repo, repo *localrepo.Repo) error {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return err
	}

	poolBitmaps, err := getBitmaps(poolPath)
	if err != nil {
		return err
	}
	if len(poolBitmaps) == 0 {
		return nil
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return err
	}

	memberBitmaps, err := getBitmaps(repoPath)
	if err != nil {
		return err
	}
	if len(memberBitmaps) == 0 {
		return nil
	}

	for _, bitmap := range memberBitmaps {
		if err := os.Remove(bitmap); err != nil && !os.IsNotExist(err) {
			return err
		}
	}

	return nil
}

// DeriveReplicaPath derives a repository's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/repositories/ab/cd/<repository-id>.

	return deriveDiskPath(praefectRepositoryPathPrefix, repositoryID)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/pools/ab/cd/<repository-id>. The pools
// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository
// and avoid pruning them.
func DerivePoolPath(repositoryID int64) string {
