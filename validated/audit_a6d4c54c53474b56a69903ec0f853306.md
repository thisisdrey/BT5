### Title
`SwapFirstAssetTrader::refund_weight` performs an XCM fee-refund swap with **no slippage floor**, letting a sandwiched pool price zero out (or drastically reduce) the user's fee refund - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader` (used as an XCM `WeightTrader` on Asset Hub Westend/Rococo and Penpal, via `SwapFirstAssetTrader` in `xcm_config.rs`) swaps a user's non-native fee asset into the `Target` asset to pay XCM execution weight, and swaps back on refund of unused weight. The `buy_weight` path caps the swap input by the credit the user actually supplied, but the `refund_weight` path calls `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None`, explicitly disabling slippage protection on the refund leg.

### Finding Description
`refund_weight` extracts the unused portion of the previously collected `Target`-asset fee and swaps it back into the asset the user originally paid with: [1](#0-0) 

```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) {
    Ok(refund_in_target) => refund_in_target,
    ...
```

`None` is passed for `amount_out_min`, which for the concrete `pallet_asset_conversion::Pallet<T>` implementation of `SwapCredit` disables the minimum-output check entirely: `do_swap_exact_credit_tokens_for_tokens` only enforces `amount_out >= amount_out_min` when `amount_out_min` is `Some(_)`: [2](#0-1) 

By contrast, `buy_weight` uses `swap_tokens_for_exact_tokens` where the *entire* fee-asset credit provided by the user acts as an implicit cap on the input, so the user can never lose more than what they voluntarily supplied: [3](#0-2) 

The refund leg has no equivalent safeguard: whatever amount the AMM returns for the given `Target`-asset input at the *current* pool reserves is accepted unconditionally, no matter how far that is from a fair/expected price.

This is the exact broken invariant described in the external report: a swap executes trustlessly against a manipulable AMM price with zero minimum-acceptable-output enforcement, i.e. no slippage control on a live token swap path.

### Impact Explanation
`SwapFirstAssetTrader` is wired into the `Trader` config of Asset Hub Westend, Asset Hub Rococo, Penpal, and the staking-async parachain runtime XCM configs: [4](#0-3) [5](#0-4) 

Any unprivileged user who sends an XCM message that overpays execution weight in a non-native, pool-backed asset (a completely normal, public operation — `BuyExecution`/`PayFees` with any asset that has a pool with the native asset) triggers this refund path. If the underlying `AssetConversion` pool for that asset pair is thinly liquidated or its price is temporarily skewed at the moment the refund executes, the refund swap can return far less than fair value — in the extreme, close to zero — permanently transferring the difference to the pool's liquidity/arbitrageurs at the victim's expense. This is a direct value-conservation violation ("balances/assets...must conserve value and settle exactly once to the rightful beneficiary and amount") reachable purely through normal XCM usage, without any admin, governance, validator, or relayer involvement.

### Likelihood Explanation
Exploitation only requires the ability to move the relevant `AssetConversion` pool's reserves before and after the deterministic point in block execution where XCM messages (and their weight refunds) are processed — an ordinary swap transaction from any account, no privileged role required. Pools with lower liquidity for a given fee asset make this cheaper to execute, and the attacker's own manipulating trades can be reversed for profit within the same block, which is the classic sandwich pattern the original report describes for AMM swaps lacking a minimum-output check. This mirrors precisely the missing-guard pattern already fixed elsewhere in the same crate (`buy_weight`'s implicit input cap, and the explicit `amount_out_min`/`amount_in_max` parameters on all public `pallet-asset-conversion` extrinsics), showing the refund path was simply overlooked.

### Recommendation
Add a slippage floor to the refund swap, e.g. compute an `amount_out_min` from `QuotePrice::quote_price_exact_tokens_for_tokens` (already used elsewhere in this file for `quote_weight`) minus an acceptable tolerance, and pass `Some(min_amount)` instead of `None` to `SwapCredit::swap_exact_tokens_for_tokens` in `refund_weight`. If the realized output falls below that floor, prefer returning the refund credit in the `Target` asset (or holding it) over accepting an unbounded loss.

### Proof of Concept
1. Configure a runtime using `SwapFirstAssetTrader` (as Asset Hub Westend/Rococo/Penpal do) with a low-liquidity pool between `Target` (native) and asset `X`.
2. User sends an XCM message that pays execution fees in `X` via `BuyExecution`, overpaying weight so a nonzero refund is due; `buy_weight` swaps some `X` into `Target` (capped by user's supplied credit — no loss beyond authorization).
3. Before the refund is processed in the same block, attacker submits a large `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` on the `Target`/`X` pool to skew the price against `Target`→`X` conversions.
4. `refund_weight` executes `SwapCredit::swap_exact_tokens_for_tokens(vec![Target, X], refund, None)` at the skewed price — see [6](#0-5)  — returning far less `X` to the user than fair value, since no `amount_out_min` bound exists to reject the trade.
5. Attacker reverses the price-skewing trade afterward, pocketing the difference extracted from the victim's refund.
