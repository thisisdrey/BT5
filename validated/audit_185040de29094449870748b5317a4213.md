Based on my investigation, the strongest analog is in `PrecompiledContracts.java`'s array-extraction helpers used to decode precompiled-contract call data.

### Title
Uncontrolled memory allocation from unchecked declared array length in TVM precompiled-contract call data decoding - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The pypdf advisory describes an attacker crafting input where a *declared* size field is far larger than the *actual* backing data, causing a huge memory allocation before the mismatch is detected. The same pattern exists in java-tron's precompiled-contract input decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, which read a declared element count directly from attacker-controlled call data and immediately allocate an array of that size before validating it against the actual size of the supplied `data` buffer.

### Finding Description
`extractBytes32Array` reads `len` from `words[offset].intValueSafe()` and immediately does `new byte[len][]` before any check that `len` corresponds to the actual amount of data present: [1](#0-0) 

`extractBytesArray` and `extractSigArray` follow the same pattern — the only bound check performed is `offset > words.length - 1`, which validates that the *length word itself* is present, but not that `len` array elements actually exist in `data`: [2](#0-1) 

`DataWord.intValueSafe()` caps overflow values at `Integer.MAX_VALUE` rather than rejecting them, so a maliciously crafted call-data word decodes to `len = Integer.MAX_VALUE` (2,147,483,647) regardless of how small the actual `data` byte array is: [3](#0-2) 

The resulting `new byte[Integer.MAX_VALUE][]` allocation is a reference array (8 bytes per null slot on typical 64-bit JVMs), requesting roughly 16GB in a single allocation — an immediate large-memory-usage event caused entirely by an untrusted declared length that is not checked against the real size of the input before allocation, exactly mirroring the pypdf image-dimension bug class (CWE-789).

Similarly, `extractBytes32Array` performs no upper-bound check on `offset` before indexing `words[offset]`, but the memory-allocation issue is the primary concern here since it occurs unconditionally before any subsequent index access would throw.

### Impact Explanation
Because these helpers are called during `execute()` of TVM precompiled contracts, an attacker only needs to send a normal contract call (or trigger a `CALL`/`STATICCALL` from any deployed contract) to one of the precompiled contract addresses that uses these helpers, with call data whose relevant length word is set to a large value while the surrounding data buffer is small or empty. This can force a single JVM thread executing the transaction to attempt a very large heap allocation, which can throw `OutOfMemoryError` and potentially destabilize or crash the FullNode/SR process — a node crash/halt is the qualifying impact.

### Likelihood Explanation
Likelihood is high for any unprivileged party able to submit a `TriggerSmartContract` transaction or deploy a contract that calls the affected precompile address: no special privilege, signature, or witness/SR role is required, and the length field is fully attacker-controlled 32-byte call data, requiring no complex crafting beyond setting one word to `0xFFFFFFFF`-class values.

### Recommendation
Before allocating `bytes32Array`/`bytesArray`/`sigArray`, validate that the derived `len` is consistent with the actual remaining bytes in the `data`/`words` buffer (e.g., `len * elementSize <= data.length - currentOffset`), and reject with an execution failure (return `Pair.of(false, ...)`) when the declared count cannot be backed by the actual payload, mirroring the fix applied to `ContractEventParser.subBytes`, which already rejects lengths that exceed available source bytes.

### Proof of Concept
1. Identify a precompiled contract (reachable via `PrecompiledContracts.getContractForAddress`) whose `execute(byte[] data)` invokes `extractBytes32Array`, `extractBytesArray`, or `extractSigArray` with an offset pointing at attacker-supplied call data.
2. Craft `data` such that the length word at the referenced offset decodes (via `intValueSafe()`) to `Integer.MAX_VALUE`, while the actual `data` array is only a few words long.
3. Submit a `TriggerSmartContract` transaction (or have a deployed contract issue a `CALL`) invoking that precompile with the crafted payload.
4. Observe the JVM attempt to allocate a `byte[Integer.MAX_VALUE][]` array during `execute()`, producing large/failed memory allocation on the node processing the transaction.

Note: I could not fully confirm within the available search results which specific precompile address(es) currently call `extractBytesArray`/`extractSigArray` in this exact codebase version (the grep for their call sites only returned matches inside `PrecompiledContracts.java` itself, and I was not able to inspect the calling precompile classes further due to the iteration limit), so the exact reachable precompile name should be verified before treating this as fully confirmed.
