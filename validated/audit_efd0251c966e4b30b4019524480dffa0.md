### Title
Deposit crediting trusts the caller-supplied `amount` instead of the actual balance received, allowing fee-on-transfer NEP-141 tokens to mint uncollateralized internal balances - (File: contracts/defuse/src/contract/tokens/mod.rs)

### Summary
`Contract::deposit` credits an account's internal multi-token balance for the exact `amount` reported by the incoming transfer, without ever verifying that the Defuse contract's actual token balance increased by that same amount.

### Finding Description
When a NEP-141 token is transferred into Defuse via `ft_transfer_call`, `ft_on_transfer` receives `amount` as reported by the token contract and passes it straight into `self.deposit(...)`, which unconditionally adds `amount` to both `total_supplies` and the receiver's `token_balances`: [1](#0-0) [2](#0-1) 

The same pattern applies to `mt_on_transfer` for NEP-245 assets: [3](#0-2) 

For a NEP-141 token that implements fee-on-transfer or burn-on-transfer semantics (deducting a portion of the amount during its own internal `ft_transfer_call` bookkeeping while still invoking `ft_on_transfer` with the gross `amount`), Defuse's internal ledger (`total_supplies` / `token_balances`) will be credited for more than the quantity of real tokens actually escrowed by the Defuse contract. This breaks the core custody invariant that the sum of internally-tracked balances for a `TokenId` must equal the real token balance the contract holds for that asset — i.e. `credited_amount == tokens_actually_received`, which the code never checks.

Once minted, this uncollateralized internal balance is fully fungible within Defuse: the attacker can transfer it via intents (`Transfer`, `mt_transfer`), swap it against other users' deposits, or directly call `ft_withdraw`/`mt_withdraw` to redeem it for real tokens of any type held in the shared Defuse token pot, extracting value that was never actually deposited and is instead backed by other depositors' funds.

### Impact Explanation
This is a Critical-severity issue under the given rubric: it credits internal balances "without valid authorisation" over the real backing asset, and produces an unbalanced ledger — internal supply exceeds the actual custodied token balance for that `TokenId`. Because Defuse pools all users' tokens together and honors withdrawals from that shared pot, the deficit created by one fee-on-transfer deposit is ultimately paid for by other users' deposits of the same token, i.e. concrete value loss / insolvency of the pool for that asset.

### Likelihood Explanation
Exploitability only requires depositing an ERC20/NEP-141-style token that deducts a transfer fee or burns part of the amount on transfer while still reporting the gross intended `amount` to the receiver hook — a known and common token pattern (fee-on-transfer, deflationary/burn tokens). No privileged role, relayer, or victim key is required; any unprivileged account holding such a token can trigger it via a normal `ft_transfer_call`/`mt_transfer_call` deposit.

### Recommendation
Verify the actual balance delta of the Defuse contract for the deposited token (e.g., compare `ft_balance_of(current_account_id)` before/after the transfer, or require callers to only whitelist tokens known not to apply fees on transfer) before crediting `deposit()` with the reported `amount`, rather than trusting the value passed into `ft_on_transfer`/`mt_on_transfer`.

### Proof of Concept
1. Deploy/obtain a NEP-141 token `FEE` that burns/redirects 5% of every `ft_transfer`/`ft_transfer_call` amount internally but still calls `ft_on_transfer(sender_id, amount=100, msg)` on the receiver with the full intended amount.
2. Attacker calls `FEE.ft_transfer_call(defuse, 100, "")`. Defuse's real `FEE` balance only increases by 95, but `ft_on_transfer` → `deposit()` credits the attacker's `token_balances[FEE]` and `total_supplies[FEE]` by the full 100 (`contracts/defuse/src/contract/tokens/mod.rs:38-64`, `contracts/defuse/src/contract/tokens/nep141/deposit.rs:38-43`).
3. Attacker calls `ft_withdraw(token=FEE, receiver_id=attacker, amount=100)`. Defuse debits the attacker's internal balance by 100 and attempts `ft_transfer(attacker, 100)` from its real `FEE` balance, which only had 95 backing it plus whatever other depositors of `FEE` had contributed — draining real tokens belonging to other depositors to cover the phantom 5.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());
