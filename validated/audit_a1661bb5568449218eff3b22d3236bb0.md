## Title
Direct-transfer reserve-donation share dilution in `pallet-asset-conversion::do_add_liquidity` - (`substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`pallet-asset-conversion`'s liquidity-provider share (LP token) accounting is priced from live asset balances of the pool's sovereign account (`get_balance`/`get_reserves`), not from an internally tracked "total deposited" counter, while LP token minting for non-initial deposits is derived from `total_supply * amount / reserve` via `mul_div`. This is the same broken invariant the ERC4626 report describes: share price = pooled value / share supply, where "pooled value" can be moved by anyone independent of share issuance.

## Finding Description
The initial deposit into a pool takes the `total_supply.is_zero()` branch and mints shares from `calc_lp_amount_for_zero_supply(amount1, amount2) = sqrt(amount1*amount2) - MintMinLiquidity`, locking `MintMinLiquidity` LP tokens permanently to the pool account: [1](#0-0) 

Any subsequent depositor's share is computed purely from current on-chain reserve balances of the pool's sovereign account (`reserve1`, `reserve2` obtained via `get_balance`), not from any pallet-tracked "total value added by LPs": [2](#0-1) [3](#0-2) 

Because the pool account is a deterministic, publicly known `PalletId`/`PoolLocator`-derived `AccountId` and reserves are read directly off its live asset/native balance, anyone can inflate `reserve1`/`reserve2` by simply transferring `asset1`/`asset2` directly to that account (an ordinary `transfer` call, not `add_liquidity`), without minting any LP tokens for that donation. The pallet's only defense against a diluted mint is a *fixed, absolute* floor check, not a relative one: [4](#0-3) 

This mirrors exactly the Treehouse `TreehouseRouter.deposit()` fix cited in the report ("revert when no shares are minted") — but a fixed `MintMinLiquidity` floor only prevents the share count from rounding to literally zero; it does not prevent a victim's `mul_div(amount, total_supply, reserve)` computation from rounding down to a small-but-nonzero share that is worth far less than the value they contributed, once reserves have been artificially inflated relative to `total_supply` by a direct-transfer donation.

## Impact Explanation
An attacker who is first (or an early) LP in a freshly created pool can:
1. Add minimal liquidity via `add_liquidity` to make `total_supply` small and just above `MintMinLiquidity` (satisfying `lp_token_amount > MintMinLiquidity`).
2. Directly transfer a large amount of `asset1`/`asset2` to the pool's sovereign account (ordinary token transfer, no special privilege, no pool-related call), massively inflating `reserve1`/`reserve2` without touching `total_supply`.
3. Wait for a legitimate user to call `add_liquidity`. That user's `side1 = mul_div(amount1, total_supply, reserve1)` and `side2` are computed against the now-inflated reserves, so `lp_token_amount` rounds to a value that is tiny relative to the assets they deposited (but can still be `> MintMinLiquidity`, so the guard does not revert).
4. The attacker then calls `remove_liquidity`, redeeming their disproportionately large share of LP supply for a disproportionate share of total reserves (which now include the victim's freshly deposited assets), extracting value that rightfully belonged to the victim.

This is a direct theft of user funds via mis-priced share issuance in a public, unprivileged pathway (`add_liquidity`/`remove_liquidity` plus ordinary asset transfers) — matching the "theft or unbacked mint" and "wrong beneficiary or amount" impact categories.

## Likelihood Explanation
Likelihood is low-to-moderate: it requires a newly created (or currently low-liquidity) pool, an attacker willing to seed a small initial LP position and then donate assets to the pool account, and a subsequent depositor adding liquidity to that same pool before the attacker or other arbitrage activity normalizes the reserve/LP-supply ratio. It does not require a malicious validator, collator, governance actor, or mempool front-running — it is a standalone, repeatable setup an attacker can apply to any pool they can be first (or early) into, similar to the classical ERC4626/Uniswap V2 "first depositor donation" inflation attack.

## Recommendation
- Track pool reserves/"total value" internally (accounted at time of `add_liquidity`/`remove_liquidity`/swap) rather than deriving `reserve1`/`reserve2` purely from live balance queries, so uninvited direct transfers cannot be used to donate into the pricing denominator without corresponding share issuance.
- Alternatively/additionally, make the minimum-liquidity check proportional (e.g., ensure `lp_token_amount` respects a maximum allowed reserve-to-supply ratio, analogous to nomination-pools' `MaxPointsToBalance`/`ok_to_be_open` ratio guard) rather than a single fixed `MintMinLiquidity` floor, and/or reconcile any balance in the pool account that exceeds the pallet's tracked reserves (e.g., sweep/ignore untracked excess) before computing `mul_div`.
- Add regression tests that donate tokens directly to a pool's sovereign account between two `add_liquidity` calls and assert the second LP's minted share remains proportional to their contributed value.

## Proof of Concept
1. `create_pool(asset1, asset2)`.
2. Attacker (account A) calls `add_liquidity(asset1, asset2, amt1=X, amt2=X, ...)` with `X` just large enough that `lp_token_amount = sqrt(X*X) - MintMinLiquidity > MintMinLiquidity` succeeds; `total_supply` is now small (e.g., a few hundred units above `MintMinLiquidity`).
3. Attacker transfers a very large amount `D` of `asset1` and `asset2` directly to the pool's sovereign account (`T::PoolLocator::address(&pool_id)`) using ordinary `pallet-assets`/`pallet-balances` `transfer`, with no `add_liquidity` call — `reserve1`/`reserve2` jump from `X` to `X + D` while `total_supply` is unchanged.
4. Victim (account B) calls `add_liquidity(asset1, asset2, amt1=Y, amt2=Y, ...)` for a meaningful `Y`. `side1/side2 = mul_div(Y, total_supply, X+D)`, which, since `D >> X`, rounds down to a value only marginally above `MintMinLiquidity` — B receives LP tokens representing a tiny fraction of B's actual deposit's value.
5. Attacker A calls `remove_liquidity`, burning their (large relative) LP share and withdrawing a proportionate amount of the pool's `asset1`/`asset2`, which now includes B's freshly added `Y` — A recovers far more value than they contributed, at B's expense. [5](#0-4)

		/// Add liquidity to a pool.
		pub(crate) fn do_add_liquidity(
			who: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount1_desired: T::Balance,
			amount2_desired: T::Balance,
			amount1_min: T::Balance,
			amount2_min: T::Balance,
			mint_to: &T::AccountId,
		) -> Result<T::Balance, DispatchError> {
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			ensure!(
				amount1_desired > Zero::zero() && amount2_desired > Zero::zero(),
				Error::<T>::WrongDesiredAmount
			);

			let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;
			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			let reserve1 = Self::get_balance(&pool_account, asset1.clone());
			let reserve2 = Self::get_balance(&pool_account, asset2.clone());

			let amount1: T::Balance;
			let amount2: T::Balance;
			if reserve1.is_zero() || reserve2.is_zero() {
				amount1 = amount1_desired;
				amount2 = amount2_desired;
			} else {
				let amount2_optimal = Self::quote(&amount1_desired, &reserve1, &reserve2)?;

				if amount2_optimal <= amount2_desired {
					ensure!(
						amount2_optimal >= amount2_min,
						Error::<T>::AssetTwoDepositDidNotMeetMinimum
					);
					amount1 = amount1_desired;
					amount2 = amount2_optimal;
				} else {
					let amount1_optimal = Self::quote(&amount2_desired, &reserve2, &reserve1)?;
					ensure!(
						amount1_optimal <= amount1_desired,
						Error::<T>::OptimalAmountLessThanDesired
					);
					ensure!(
						amount1_optimal >= amount1_min,
						Error::<T>::AssetOneDepositDidNotMeetMinimum
					);
					amount1 = amount1_optimal;
					amount2 = amount2_desired;
				}
			}

			ensure!(
				amount1.saturating_add(reserve1) >= T::Assets::minimum_balance(asset1.clone()),
				Error::<T>::AmountOneLessThanMinimal
			);
			ensure!(
				amount2.saturating_add(reserve2) >= T::Assets::minimum_balance(asset2.clone()),
				Error::<T>::AmountTwoLessThanMinimal
			);

			T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
			T::Assets::transfer(asset2, who, &pool_account, amount2, Preserve)?;

			let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());

			let lp_token_amount: T::Balance;
			if total_supply.is_zero() {
				lp_token_amount = Self::calc_lp_amount_for_zero_supply(&amount1, &amount2)?;
				T::PoolAssets::mint_into(
					pool.lp_token.clone(),
					&pool_account,
					T::MintMinLiquidity::get(),
				)?;
			} else {
				let side1 = Self::mul_div(&amount1, &total_supply, &reserve1)?;
				let side2 = Self::mul_div(&amount2, &total_supply, &reserve2)?;
				lp_token_amount = side1.min(side2);
			}

			ensure!(
				lp_token_amount > T::MintMinLiquidity::get(),
				Error::<T>::InsufficientLiquidityMinted
			);

			T::PoolAssets::mint_into(pool.lp_token.clone(), mint_to, lp_token_amount)?;

			Self::deposit_event(Event::LiquidityAdded {
				who: who.clone(),
				mint_to: mint_to.clone(),
				pool_id,
				amount1_provided: amount1,
				amount2_provided: amount2,
				lp_token: pool.lp_token,
				lp_token_minted: lp_token_amount,
			});

			Ok(lp_token_amount)
		}
