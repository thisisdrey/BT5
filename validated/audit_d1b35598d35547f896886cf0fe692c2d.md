## Verdict: Valid finding (narrower than framed) — CREATE2 front-running griefs `SmartAccountFactory.deploySmartAccount`

### Title
Front-running `SAFE_PROXY_FACTORY.createProxyWithNonce` with a matching initializer permanently bricks a victim's `deploySmartAccount` nonce and desyncs `isDeployedSmartAccount` - ([File: tare-io__tare-contracts/contracts/SmartAccountFactory.sol])

### Summary
`deploySmartAccount` derives its Safe's CREATE2 salt purely from `keccak256(msg.sender, nonces[msg.sender])` and the `initializer` bytes are built purely from the caller-supplied config (delegates/currencies/owners/threshold/etc.), with no binding to `msg.sender` of the factory call itself [1](#0-0) . Since `SafeProxyFactory.createProxyWithNonce` is a public, permissionless entrypoint, anyone who can predict/observe the exact tuple `(delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold)` and the victim's current `nonces[victim]` value (a public mapping [2](#0-1) ) can precompute the identical `saltNonce` and `initializer`, and call `SAFE_PROXY_FACTORY.createProxyWithNonce` directly to deploy to that exact predetermined address first.

### Finding Description
Because the CREATE2 salt only depends on `(msg.sender-of-deploySmartAccount, deployerNonce)` and not on who actually submits the proxy-factory transaction, an attacker who front-runs with the same `initializer` bytes and the same `saltNonce` deploys a Safe at the exact address the victim's subsequent `deploySmartAccount` call would have produced. The `Safe.setup` delegatecall to `configureSmartAccount` runs regardless of who triggers deployment, so the resulting Safe is fully configured (module enabled, ERC20/NFT approvals set, delegates added, `TrustedSpender` allowances set) exactly as intended [3](#0-2) .

Two concrete, verifiable consequences follow when the victim's `deploySmartAccount` call subsequently executes:
1. `isDeployedSmartAccount[safeAddress]` is only ever set inside `deploySmartAccount` itself [4](#0-3) , so the attacker-deployed Safe — despite being correctly configured — never gets flagged in this registry.
2. `SAFE_PROXY_FACTORY.createProxyWithNonce` will attempt to deploy to an address that already has code (CREATE2 collision) and revert. Because `nonces[msg.sender]++` happens in the same transaction that reverts, the nonce increment is rolled back too [5](#0-4) . Every subsequent call by that same deployer recomputes the identical stuck `saltNonce` and reverts identically — the deployer's ability to ever call `deploySmartAccount` successfully again is permanently bricked.

I could not find any in-scope contract that actually reads `isDeployedSmartAccount` to gate funding, disbursement, or claim eligibility — it is only referenced in `SmartAccountFactory.sol`, its interface, and tests. So the premise that this flag is "relied upon by integrators/trustedRecipients to gate funding" is not substantiated by the current repository contents; it's a documented convenience for off-chain/external verification (per the NatSpec) [6](#0-5) , not an on-chain gating dependency within this codebase.

### Impact Explanation
The confirmed, in-scope impact is a permanent, unrecoverable denial-of-service on `deploySmartAccount` for the targeted deployer address (its nonce sequence can never advance past the squatted value), which blocks that user from onboarding a new smart account through the intended factory path. The Safe itself remains usable (correct owners/delegates/allowances), so there is no fund theft or loss of control over the Safe, and no confirmed on-chain consumer of `isDeployedSmartAccount` is corrupted in a way that changes fund flows. This is a griefing/DoS issue rather than a value-extraction or accounting-corruption issue.

### Likelihood Explanation
Requires the attacker to know or predict the exact `(delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold)` tuple and the victim's pending nonce, typically via mempool front-running of a pending `deploySmartAccount` transaction, or via predictable/templated role-account deployments (e.g., `cli/commands/create-role-accounts.ts`). This is plausible but requires public-mempool visibility and correctly copying all parameters before the victim's transaction lands.

### Recommendation
Bind the initializer/salt derivation to something the attacker cannot replicate independent of the legitimate caller (e.g., include `msg.sender` of `deploySmartAccount` inside the `initializer` itself, or have `deploySmartAccount` verify post-deployment that `Safe(safeAddress).isOwner(...)`/configuration matches expectations and otherwise treat a pre-existing contract at the predicted address as already-provisioned rather than reverting the whole nonce increment). At minimum, increment `nonces[msg.sender]` and record intent before attempting the CREATE2 deployment (e.g., using a two-step commit or a try/catch that still advances the nonce on collision) so a single front-run cannot permanently strand the deployer's nonce sequence.

### Proof of Concept
1. Observe (or predict) a pending `deploySmartAccount(delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold)` call from victim `V` with `nonces[V] == n`.
2. Compute `saltNonce = keccak256(abi.encodePacked(V, n))` and the identical `initializer` bytes via `_buildInitializer`.
3. Call `SAFE_PROXY_FACTORY.createProxyWithNonce(SAFE_SINGLETON, initializer, saltNonce)` directly, ahead of `V`'s transaction.
4. Confirm the resulting Safe address matches `factory.predictSmartAccountAddress(V, n, ...)` and that it is fully configured (delegates/allowances set), but `factory.isDeployedSmartAccount(safeAddress) == false`.
5. Submit/allow `V`'s original `deploySmartAccount` call to execute — observe it reverts on the CREATE2 collision, and `nonces[V]` remains `n` forever, permanently blocking `V` from any future successful `deploySmartAccount` call.

  /// @inheritdoc ISmartAccountFactory
  function configureSmartAccount(
    address[] memory delegates,
    address[] memory currencies,
    address[] memory nftCollections,
    address[] memory trustedRecipients,
    uint48 validUntil
  ) external {
    require(address(this) != _SELF, NotDelegateCall());
    _setConfigured();

    // 1. Enable TrustedCalls module
    IModuleManager(payable(address(this))).enableModule(TRUSTED_CALLS_MODULE);

    // 2. Approve currencies for TrustedSpender (standard ERC20 approvals)
    for (uint256 i = 0; i < currencies.length; ++i) {
      IERC20(currencies[i]).forceApprove(TRUSTED_SPENDER, type(uint256).max);
    }

    // 3. Approve NFT collections for TrustedSpender (blanket setApprovalForAll)
    for (uint256 i = 0; i < nftCollections.length; ++i) {
      IERC721(nftCollections[i]).setApprovalForAll(TRUSTED_SPENDER, true);
    }

    // 4. Add delegates to both TrustedCalls module and TrustedSpender contract
    for (uint256 i = 0; i < delegates.length; ++i) {
      // Add to TrustedCalls module
      ITrustedCalls(TRUSTED_CALLS_MODULE).addDelegate(address(this), delegates[i]);

      // Add to TrustedSpender contract
      ITrustedSpender(TRUSTED_SPENDER).addDelegate(address(this), delegates[i]);
    }

    // 5. Set ERC20 allowances for trusted recipients in TrustedSpender.
    //    NFT per-route allowances are set lazily via TrustedSpender.setNFTAllowance.
    for (uint256 i = 0; i < trustedRecipients.length; ++i) {
      for (uint256 j = 0; j < currencies.length; ++j) {
        ITrustedSpender(TRUSTED_SPENDER).setAllowance(
          currencies[j],
          address(this),
          trustedRecipients[i],
          type(uint208).max,
          validUntil
        );
      }
    }
  }
