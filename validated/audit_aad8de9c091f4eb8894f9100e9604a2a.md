### Title
Unauthenticated HTTP event listener lets any local network peer inject forged StackerDB chunk, block-validation, and burn-block events into a Stacks signer - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` is the HTTP server the `stacks-signer` binary runs to receive event pushes from its paired `stacks-node`. It accepts any POST to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` and feeds the deserialized JSON straight into the signer's event channel, with no authentication check whatsoever — unlike the node-side RPC endpoints in `stackslib/src/net/api/` (e.g. `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`), which all gate state-changing/sensitive requests behind an `authorization` header compared to a configured secret.

### Finding Description
`SignerEventReceiver::next_event` (`libsigner/src/events.rs:413-459`) only checks the HTTP method: [1](#0-0) 
It never inspects any `authorization` header or compares against a shared secret before calling `process_event::<T, StackerDBChunksEvent>`, `process_event::<T, BlockValidateResponse>`, or `process_event::<T, BurnBlockEvent>` (`libsigner/src/events.rs:519-542`), which simply JSON-deserialize the body and forward it to the signer runloop via `forward_event`.

By contrast, every state-changing/sensitive node-side RPC handler in this repo enforces a symmetric auth check against `connection_options.auth_token`, e.g. `postblock_proposal.rs:1136-1144`, `blockreplay.rs:575-583`, `blocksimulate.rs:153-161`, `txsimulate.rs:352-360`, and `postblock_v3.rs:104-111`: [2](#0-1) 

The documentation (`docs/signing.md:33-59`, `sample/conf/signer/mainnet-signer-conf.toml:45-50`) explicitly states that `auth_password` in the signer config "must match" the node's `auth_token`, implying the two processes are meant to mutually authenticate. However, that `auth_password`/`auth_token` pair is used only for the signer's *outbound* calls to the node's RPC (via `stacks-signer/src/client/stacks_client.rs`); it is never checked on the *inbound* side — the signer's own event-receiver socket that the node's `events_observer` posts to. This breaks the intended equality "only the paired node may push events to this signer" vs. the actual behavior "anyone who can reach this TCP port may push events."

This is structurally analogous to CVE-2019-10321: a state-affecting HTTP entry point that lacks any permission/CSRF check, allowing an unauthenticated party to drive internal logic with attacker-controlled input (the Jenkins plugin's unauthenticated form-validation callback vs. here, the unauthenticated event-push callback).

### Impact Explanation
Any host that can reach the signer's bound port (`endpoint`, e.g. `0.0.0.0:30000` per `sample/conf/signer/mainnet-signer-conf.toml:39` — several sample configs bind to `0.0.0.0`) can forge `StackerDBChunksEvent`, `BlockValidateResponse`, or `BurnBlockEvent` payloads and inject them directly into the signer's processing pipeline, without needing the node's `auth_token`/`auth_password`, the node's private key, or any StackerDB chunk signature at this layer (signature checks, if any, happen later inside signer-decision code, which is out of scope for this analog and not verified here). At minimum this allows an unauthenticated remote party to flood/desynchronize a signer's event stream (forged burn-block/tenure notifications, forged proposal-validation results) — a request-smuggling/spoofing-style issue at the transport boundary. Whether forged chunk/proposal data can influence actual signing decisions depends on downstream signature verification inside the (out-of-scope) signer decision logic, which was not evaluated here.

### Likelihood Explanation
Exploitability only requires network reachability to the signer's listening port and knowledge of the fixed set of URL paths (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`), all of which are public in this open-source code. No credentials, node key, or StackerDB slot ownership are needed to reach `process_event`. The primary mitigating factor — noted as a runtime warning in `stacks-signer/src/lib.rs:125-132` — is an operational recommendation to bind the receiver to a local/private network, not a code-level control.

### Recommendation
Add a shared-secret (or mTLS) check to `SignerEventReceiver::next_event`/`process_event` in `libsigner/src/events.rs`, symmetric to the `authorization` header check already used on the node's RPC handlers, so the event receiver verifies that inbound POSTs originate from the paired, authenticated node before deserializing and forwarding their contents.

### Proof of Concept
1. Start a `stacks-signer` configured per `sample/conf/signer/mainnet-signer-conf.toml`, with `endpoint = "0.0.0.0:30000"`.
2. From any host that can reach port 30000 (no `auth_token`/`auth_password` needed), send:
   ```
   POST /new_burn_block HTTP/1.1
   Host: <signer-ip>:30000
   Content-Type: application/json
   Content-Length: <n>

   { ...forged BurnBlockEvent JSON... }
   ```
3. Per `libsigner/src/events.rs:441-442,519-542`, the request is accepted, deserialized, and forwarded into the signer runloop via `forward_event` — no verification that this event came from the paired stacks-node.

Note: this repository's static index does not show whether the signer's downstream decision logic re-validates chunk signatures or proposal authenticity before acting on forwarded events (that logic is out of scope per the task rules); confirming the full exploit chain to a concrete signing-decision impact would require inspecting `stacks-signer` runloop/decision code, which was excluded.
