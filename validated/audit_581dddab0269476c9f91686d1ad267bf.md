### Title
Stale `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` state survives account deletion, causing orphaned receipts to execute against a same-named recreated account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (invoked by `action_delete_account` in `runtime/runtime/src/actions.rs`) only clears `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData`. It never removes `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` rows, all of which are keyed solely by the `AccountId` string with no binding to a specific account "generation." When the outstanding `DataReceipt` dependency later arrives, `process_receipt` in `runtime/runtime/src/lib.rs` looks these keys up purely by `account_id` and executes the postponed action receipt against whatever account currently occupies that name.

### Finding Description
`remove_account`, defined at `core/store/src/utils/mod.rs:504-575`, explicitly removes only: [1](#0-0) [2](#0-1) [3](#0-2) 

It performs no iteration/removal over `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` columns. `action_delete_account` in `runtime/runtime/src/actions.rs:314-390` calls `remove_account` unconditionally (subject only to a storage-usage cap that covers contract code/state, not postponed-receipt bookkeeping) and then sets `*account = None`: [4](#0-3) 

Meanwhile, `TrieKey::PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` are all defined with `receiver_id: AccountId` as their only account-identifying field, with no creation-nonce or generation counter: [5](#0-4) 

When the awaited `DataReceipt` eventually arrives, `process_receipt` resolves the postponed receipt purely by `account_id` string match, fetches it via `get_postponed_receipt`, and executes it via `apply_action_receipt` against the account object that is live in the trie *at that time* — with no check that it is the same logical account that originally created the postponed receipt: [6](#0-5) 

Exploit flow:
1. Attacker's account `A` issues an `ActionReceipt` targeting itself (`receiver_id = A`) with an unmet `input_data_id`, containing a self-targeted `DeployContract`/`Stake` action. This is stored via `process_action_receipt` as `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`: [7](#0-6) 
2. Attacker submits `DeleteAccount` on `A`. `action_delete_account` → `remove_account` clears the `Account`/`ContractCode`/`AccessKey`/`ContractData` rows but leaves the three postponed-receipt rows intact in the trie.
3. Some account is later (re)created under the same `AccountId` string `A` (subaccount creation requires the parent account's signature, or top-level accounts via the registrar contract; a naive party or a factory-mediated third party can end up with this reused name) and deploys its own contract.
4. The originally-pending `DataReceipt` (which the attacker fully controls the timing of, since they set up the dependency) is delivered. `process_receipt` finds the still-present `PostponedReceiptId`/`PendingDataCount` under `A`, decrements to zero, fetches the still-present `PostponedReceipt`, and executes it against the *new* account state living at `A` — silently redeploying the attacker's contract or altering stake on the new owner's account.

No existing check (nonce, access-key permission, signature, storage-staking) intervenes, because this path is not gated by any per-transaction authorization — it is an internal runtime resolution keyed only by account-id string equality, and `remove_account`'s cleanup scope simply omits these three column families.

### Impact Explanation
This is an authorization-escalation bug: an action (`DeployContract`/`Stake`) that was authorized only in the context of the original account owner gets executed against a different party's account without any new authorization check, matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
The attacker-side setup (crafting a self-postponed receipt then self-deleting) costs only ordinary transaction/contract-call fees and is fully repeatable. The limiting factor is getting the exact `AccountId` reused by an independent party: for direct subaccounts, only the parent account can issue the `CreateAccount` action for that name (so the "third party" would typically need to be a factory/registrar-style contract minting deterministic or attacker-influenced subaccount names, or the parent account itself acting later); for top-level `.near` names, reuse depends on the registrar's account-creation rules. This constrains real-world blast radius compared to an arbitrary victim, but the underlying state-hygiene defect in `remove_account` is unconditional and reachable by any unprivileged account performing a normal self-delete with a pending postponed receipt.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also iterate and remove all `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt` (and `ReceivedData`) rows scoped to `account_id` before/at account deletion, or reject `DeleteAccount` while the account has any outstanding postponed receipts. Alternatively, refuse to leave a `PostponedReceiptId`/`PostponedReceipt` for an account name that no longer exists at data-receipt-resolution time in `process_receipt`, e.g. by verifying the account entry still exists / matches an epoch/generation marker before applying the resolved receipt.

### Proof of Concept
Unit test plan for `core/store/src/utils/mod.rs::remove_account`:
1. Seed a `TrieUpdate` with `Account{A}`, `ContractCode{A}`, `AccessKey{A,...}`, `ContractData{A,...}`, plus `PostponedReceiptId{receiver_id:A,data_id}`, `PendingDataCount{receiver_id:A,receipt_id}`, `PostponedReceipt{receiver_id:A,receipt_id}` containing a `DeployContractAction`.
2. Call `remove_account(&mut state_update, &A)`.
3. Assert `Account`, `ContractCode`, `AccessKey`, `ContractData` are gone (already covered by existing tests), but assert `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt` for `A` are still present — demonstrating the cleared-set ⊊ written-set gap.

Integration/runtime-test-loop plan:
1. Account `A` sends itself an `ActionReceipt` with one `input_data_id` and a `DeployContract` action; confirm it is stored as postponed.
2. `A` submits `DeleteAccount`.
3. Recreate account `A` (e.g. via its parent) and deploy a legitimate contract, confirm `AccountContract::Local(new_hash)`.
4. Deliver the pending `DataReceipt` for the original `data_id`.
5. Assert the account's contract hash reverts to the attacker's `DeployContract` payload (or, for the `Stake` variant, assert unexpected validator-stake proposal), confirming the postponed receipt executed against the recreated account without their consent.
