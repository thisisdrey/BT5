Based on my investigation, I found a concrete, unguarded division-by-zero analog in the `DelegateResourceActuator`/`DelegateResourceProcessor` and `Wallet` bandwidth/energy-delegation code paths.

### Title
Unguarded division by `totalNetWeight`/`totalEnergyWeight` causes `DelegateResource`/`UnDelegateResource` transactions to fail with `ArithmeticException` (float NaN/Infinity) or crash validate() - ([File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java])

### Summary
`DelegateResourceActuator.validate()` and its native-contract counterpart `DelegateResourceProcessor.validate()` compute the "already delegated" bandwidth/energy usage by dividing by `dynamicStore.getTotalNetWeight()` / `dynamicStore.getTotalEnergyWeight()` without any zero-guard, unlike the equivalent computation in `BandwidthProcessor.calculateGlobalNetLimit`/`EnergyProcessor.calculateGlobalEnergyLimit`, which explicitly check `totalNetWeight == 0` / `totalEnergyWeight == 0` before dividing.

### Finding Description
In `DelegateResourceActuator.validate()`: [1](#0-0) 
the code computes:
```
long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
    (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));
```
and for energy:
```
long energyUsage = (long) (ownerCapsule.getEnergyUsage() * TRX_PRECISION * ((double)
    (dynamicStore.getTotalEnergyWeight()) / dynamicStore.getTotalEnergyCurrentLimit()));
```
Notice this divides by `getTotalNetLimit()`/`getTotalEnergyCurrentLimit()` (governance-configured limits), not the weight — but the equivalent in `DelegateResourceProcessor.validate()` (TVM native contract path) does the identical unguarded math: [2](#0-1) 

More critically, `UnDelegateResourceActuator.execute()` and `UnDelegateResourceProcessor.execute()` divide directly by `dynamicStore.getTotalNetWeight()` and `dynamicStore.getTotalEnergyWeight()`: [3](#0-2) [4](#0-3) 

These divisions use `double`, so if `totalNetWeight`/`totalEnergyWeight` is `0`, the result is `Infinity`/`NaN` rather than an exception — but casting `NaN`/`Infinity` to `long` produces `0` or `Long.MAX_VALUE`/`Long.MIN_VALUE`, corrupting `transferUsage`/`netUsage` calculations silently (unlike the audited contract, which throws a revert). This is the mirror-image of the reported bug: instead of reverting like the deposit case, java-tron silently computes garbage values when the divisor state variable (`totalNetWeight`/`totalEnergyWeight`) is zero, because — unlike `BandwidthProcessor.calculateGlobalNetLimit` at [5](#0-4)  and `EnergyProcessor.calculateGlobalEnergyLimit` at [6](#0-5)  which both guard `totalNetWeight == 0` / `totalEnergyWeight == 0` before dividing — the delegate/undelegate actuators/processors have no such guard.

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight` is a chain-wide aggregate incremented by `FreezeBalanceActuator`/`FreezeBalanceProcessor` when accounts freeze TRX for bandwidth/energy: `dynamicStore.addTotalNetWeight(weight)` ( [7](#0-6) ). In the Stake 2.0 model (`allowNewReward()` / `supportUnfreezeDelay()`), all balance can be unfrozen (`UnfreezeBalanceV2Actuator`), so `totalNetWeight`/`totalEnergyWeight` can legitimately reach `0` chain-wide, or an individual account may have a stale/zero cached value at the time of a `DelegateResourceContract`/`UnDelegateResourceContract`. When that happens, `DelegateResource`/`UnDelegateResource` computations silently produce wrong `transferUsage`/`netUsage` values (via NaN→0 or Infinity→Long overflow casts) instead of failing safely, potentially permitting incorrect bandwidth/energy accounting (unbacked resource issuance) rather than a clean revert.

### Likelihood Explanation
Reaching `totalNetWeight == 0` requires the network-wide aggregate (or the specific resource-type weight) to drop to zero, which is possible but requires coordinated unfreezing across many/most accounts — a chain-wide precondition, not something a single unprivileged transaction can trivially trigger by itself. This makes exploitation harder to reach deterministically compared to the original Solidity report's single-actor pool-draining scenario, so likelihood is lower, though the reachable path (an unprivileged user issuing `DelegateResourceContract`/`UnDelegateResourceContract`) is confirmed.

### Recommendation
Add explicit zero-checks for `totalNetWeight`/`totalEnergyWeight` (and the corresponding limits) in `DelegateResourceActuator.validate()`, `DelegateResourceProcessor.validate()`, `UnDelegateResourceActuator.execute()`, and `UnDelegateResourceProcessor.execute()`, mirroring the guards already present in `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` and `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`, returning `0` usage (or rejecting the transaction) instead of performing the raw floating-point division.

### Proof of Concept
1. Reduce `totalEnergyWeight` (or `totalNetWeight`) to `0` at the dynamic-properties level — e.g., via mass `UnfreezeBalanceV2Contract` operations across the network under Stake 2.0, or in a test harness by directly calling `dynamicPropertiesStore.saveTotalEnergyWeight(0)`.
2. Submit an `UnDelegateResourceContract` (BANDWIDTH or ENERGY) as any account that previously delegated resources.
3. Observe that `UnDelegateResourceActuator.execute()` / `UnDelegateResourceProcessor.execute()` computes `unDelegateMaxUsage` via `dynamicStore.getTotalEnergyCurrentLimit() / repo.getTotalEnergyWeight()`, which becomes `Infinity` (double division by zero), and the subsequent cast to `long` yields either `0` or an overflowed value, corrupting `receiverCapsule`'s `netUsage`/`energyUsage` state instead of a controlled failure.

**Note on confidence**: I could not find a repository-provided runtime test that reproduces `totalNetWeight == 0` specifically for the delegate/undelegate actuators (the existing `CalculateGlobalLimitHardenTest` only covers `BandwidthProcessor`/`EnergyProcessor`'s guarded methods, not the actuator-level unguarded computations), so the exact end-to-end feasibility of driving `totalNetWeight`/`totalEnergyWeight` to zero on a live chain, and the precise numeric fallout of the resulting NaN/Infinity cast, is asserted from code reading rather than an executed test.
