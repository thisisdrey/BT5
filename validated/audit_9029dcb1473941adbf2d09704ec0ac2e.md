### Title
Attacker can fill a victim's per-account token slots via dust `deposit(onBehalfOf_)`, DoS-ing new deposits and new debt issuance - ([File: contracts/Pool.sol])

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of an account's `debtTokensOfAccount` and `depositTokensOfAccount` lists. Any unprivileged user can add entries to a *victim's* list without the victim's consent by calling `DepositToken.deposit(amount_, onBehalfOf_ = victim)` with dust amounts on every registered deposit token. Once the victim's combined list reaches 30, any further `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, which makes all deposits of *new* collateral tokens and all issuance of *new* synth debt for that account revert — a "valid input causes the transaction to fail" availability analog of CVE-2024-50305.

### Finding Description
- The cap is enforced in the `onlyIfAdditionWillNotReachMaxTokens` modifier on `Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount`: `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` reverts [1](#0-0) [2](#0-1) 
- `addToDepositTokensOfAccount` is invoked by `DepositToken` when a balance goes from 0 to >0; the check applies to `account_` (the beneficiary), not the caller, so the attacker does not need the victim's cooperation [3](#0-2) 
- `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and mints the deposit token to them, so the attacker can force-add a slot to any account at the cost of a dust deposit [4](#0-3) 
- Symmetrically, `DebtToken._mint` triggers `addToDebtTokensOfAccount` when a debt balance goes 0→>0; once the cap is hit, `DebtToken.issue`/`SmartFarmingManager.leverage` for a synth the victim has never borrowed also reverts [5](#0-4) 
- No modifier stops this: `deposit` is `whenNotPaused` + `nonReentrant` + `onlyIfDepositTokenExists`, all of which pass in normal operation; `SynthContext._msgSender` indirection does not change the beneficiary parameter.

Attack trace:
1. Victim has, e.g., 2 deposit-token slots and 1 debt-token slot used (27 attacker-fillable slots remain).
2. Attacker loops over every registered deposit token and calls `deposit(1 wei-equivalent, victim)` (after seeding themselves via deposits of each underlying, or via `transfer` of dust msdTokens — `_transfer` also triggers `addToDepositTokensOfAccount` for the recipient).
3. Victim's combined list hits 30. From then on:
   - `DepositToken.deposit`/`transfer`/`seize` of any *new* deposit token to the victim reverts.
   - `DebtToken.issue`/`SmartFarmingManager.leverage` into any *new* synth reverts, since `_mint` → `addToDebtTokensOfAccount` reverts.

### Impact Explanation
Temporary freezing of funds / forced-liquidation griefing. A victim whose position turns unhealthy cannot deposit a collateral token they don't already hold a slot for — the rescue transaction reverts — so their position becomes liquidatable even though they own sufficient collateral of a different type. Liquidators then seize collateral at a discount via `Pool.liquidate` [6](#0-5) . The victim also cannot open new debt positions or receive new msdTokens (breaking SmartFarmingManager flows and any contract crediting new tokens to them). The DoS is temporary: the victim can free a slot by fully withdrawing one dust token (balance→0 triggers `removeFromDepositTokensOfAccount`), but doing so under liquidation pressure costs time and transactions the attacker can keep re-filling cheaply while deposit tokens remain un-held by the victim.

### Likelihood Explanation
- Cost: one dust deposit per free slot; number of slots needed is bounded by the number of registered deposit tokens in the pool (pool counts are small, well under 30), so on pools with many listed collaterals the attack is cheap and requires no privileged role, no oracle manipulation, and no victim interaction.
- Caveat reducing severity: it only blocks *new* token types; if the victim already holds the collateral they would use to deleverage, or repays debt directly, the attack has no effect. Impact is therefore situational — highest against multi-collateral users or smart-farming accounts that routinely touch new tokens. This is also a griefing/gas-economics tradeoff rather than guaranteed theft.

### Recommendation
- Make slot consumption consensual: only add to `depositTokensOfAccount`/`debtTokensOfAccount` when `account_ == _msgSender()` (i.e., self-initiated positions), or maintain the lists per `(account, initiatedBy)` and skip listing for unsolicited dust transfers/`onBehalfOf_` mints below a threshold.
- Alternatively, treat `onBehalfOf_` deposits differently: mint to the beneficiary without registering the token list entry until the beneficiary performs an action, or require a minimum first-deposit amount per token.
- Consider allowing victims to remove entries themselves (e.g., a `removeTokenOfAccount` escape hatch callable by the account) so slot recovery doesn't require a full withdrawal.

### Proof of Concept
Reproducible on a Hardhat fork of an existing deployment (e.g., `deployments/base/Pool.json`):

```ts
// fork base/mainnet; pool, msdXXX deposit tokens are registered
const depositTokens = await pool.getDepositTokens();

// attacker holds tiny amounts of each underlying (swap or already-held dust)
for (const dtAddr of depositTokens) {
  const dt = await ethers.getContractAt('DepositToken', dtAddr);
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  const dust = await underlying.balanceOf(attacker.address); // or a minimal unit
  if (dust.gt(0)) {
    await underlying.connect(attacker).approve(dt.address, dust);
    // force-adds dtAddr to victim's depositTokensOfAccount if not already present
    await dt.connect(attacker).deposit(dust, victim.address);
  }
}

// now victim's combined list == MAX_TOKENS_PER_USER (30)
expect(
  await pool.debtTokensOfAccountLength(victim.address) // via getDebtTokensOfAccount().length
    .add((await pool.getDepositTokensOfAccount(victim.address)).length)
).to.eq(30);

// 1) victim cannot deposit a collateral token they never held -> reverts
const newDt = await ethers.getContractAt('DepositToken', someTokenVictimNeverHeld);
await expect(
  newDt.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 2) victim cannot issue a synth they never borrowed -> reverts inside _mint -> addToDebtTokensOfAccount
await expect(
  newDebtToken.connect(victim).issue(someSynth, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Uncertain details (not fully verifiable in the index): the exact `_mint`/`_transfer` hook lines in `DepositToken.sol` that call `addToDepositTokensOfAccount` and the corresponding hook in `DebtToken` were inferred from the documented call direction (`Pool.sol` comments state these functions are "called from `DepositToken`/`DebtToken` when user's balance changes from 0"). A background agent should confirm those call sites and whether deployed pools expose enough distinct deposit tokens to reach the cap for a fresh victim.
