## Title
Relay manager trusts attacker-supplied `RelayFromAddr` instead of the authenticated tunnel identity, allowing relay-identity spoofing - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` derives the "who is this relay for" identity from the `RelayFromAddr` field inside an unauthenticated `NebulaControl` payload rather than from the cryptographically-verified peer identity (`h.vpnAddrs[0]`) of the tunnel the message arrived on. Any peer that can open a Nebula tunnel and send a `Control`/`CreateRelayRequest` message can set `RelayFromAddr` to an arbitrary VPN address that is not their own, causing the middle host to record relay state that associates that spoofed VPN address with the attacker's own tunnel. This mirrors the reported pattern of trusting a user-controlled identity field (`ownerAddress`) instead of the authenticated sender when making an authorization/routing decision.

### Finding Description
`HandleControlMsg` is dispatched for any `header.Control` packet received on an already-established, decrypted tunnel (`outside.go`, `f.relayManager.HandleControlMsg(hostinfo, out, f)` at [1](#0-0) ). It unmarshals attacker-controlled protobuf fields `RelayFromAddr`/`RelayToAddr` and only checks that they are non-nil, never that `RelayFromAddr` matches the sending peer's authenticated VPN address: [2](#0-1) 

`handleCreateRelayRequest` then uses the unverified `from := protoAddrToNetAddr(m.RelayFromAddr)` value directly as the identity being relayed, checking only whether `from`/`target` happen to equal *my own* VPN address, never whether `from` equals the actual sender `h.vpnAddrs[0]`: [3](#0-2) 

The relay state (`AddRelay(rm.l, h, f.hostMap, from, ...)`) is then attached to `h` — the HostInfo of the *attacker's own authenticated tunnel* — but keyed by the spoofed `from` address. Any future lookup of "who relays for VPN address `from`" (`QueryRelayForByIp`, `QueryVpnAddrsRelayFor`) will resolve to the attacker's tunnel `h`, not the legitimate owner of `from`. This is structurally identical to the reported bug: an authorization/identity decision (which peer is entitled to be treated as `from`) is taken from a self-declared payload field instead of the value bound to the authenticated channel (the peer's certificate-verified `vpnAddrs`).

### Impact Explanation
Because the relay's forwarding tables (`hostMap.QueryVpnAddrsRelayFor`, `relayState.relayForByAddr`) are populated using the spoofed identity, a peer can cause a shared relay to believe that the attacker's own tunnel is authorized to relay traffic on behalf of a VPN address it does not own. Subsequent `ForwardingType` relay traffic destined for that spoofed address can be misdirected into the attacker's tunnel, resulting in traffic interception/redirection and identity impersonation within the overlay network — a state-poisoning / spoofing impact within the same trust-boundary class as the referenced report (authorization decisions based on unauthenticated payload fields rather than verified identity).

### Likelihood Explanation
Any peer holding a valid tunnel that can act as a relay (`am_relay` enabled hosts, which are commonly deployed as generic mesh relays) is reachable by this path; the check that would prevent it (`from == h.vpnAddrs[0]`) is simply absent, so exploitation only requires sending one crafted `Control` message with an arbitrary `RelayFromAddr` — no race condition or timing dependency is needed.

### Recommendation
In `relayManager.handleCreateRelayRequest` (and `handleCreateRelayResponse`), validate that `RelayFromAddr` (or the appropriate compared field per message direction) equals one of the authenticated `h.vpnAddrs` for the connection the Control message arrived on, exactly as `handleHostUpdateNotification` in `lighthouse.go` already does for lighthouse updates ( [4](#0-3) ). Reject the message if the claimed identity doesn't match the authenticated tunnel's VPN address instead of trusting the payload-declared value.

### Proof of Concept
1. Attacker A establishes a normal Nebula tunnel to relay host M (valid handshake, `h.vpnAddrs[0] == A`).
2. A sends `header.Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = Y` (some other host's VPN address, not A) and `RelayToAddr = Z` (a legitimate third host).
3. `HandleControlMsg` -> `handleCreateRelayRequest` on M accepts it because it only checks `RelayFromAddr`/`RelayToAddr` are non-nil, and `from` (Y) isn't M's own address.
4. M calls `AddRelay(rm.l, h, f.hostMap, from=Y, ..., TerminalType, Established)`, associating VPN address `Y` with A's tunnel `h` in M's relay tables, without ever validating that A is actually `Y`.


Investigate `Lauraivanka/nebula--014/relay_manager.go`, function `handleCreateRelayRequest` (and `handleCreateRelayResponse`, `HandleControlMsg`), to confirm that the `RelayFromAddr` field taken from an inbound `NebulaControl` message is never checked against the authenticated sender's VPN address (`h.vpnAddrs[0]`, where `h *HostInfo` is passed into `HandleControlMsg` from `outside.go`'s `f.relayManager.HandleControlMsg(hostinfo, out, f)`).

Steps:
1. Confirm the vulnerability: trace `outside.go` -> `relay_manager.go:HandleControlMsg` -> `handleCreateRelayRequest`/`handleCreateRelayResponse`, and show that `from`/`target` (or `relayFrom`/`relayTo`) derived from `m.RelayFromAddr`/`m.RelayToAddr` are used to key relay state (`AddRelay`, `h.relayState`) without validating that the claimed "from" identity matches `h.vpnAddrs`.
2. Add validation in `HandleControlMsg` (or immediately at the top of `handleCreateRelayRequest`) for `NebulaControl_CreateRelayRequest`/`NebulaControl_CreateRelayResponse` messages: when the sending host itself is meant to be the "from" party of the relay (i.e., it's establishing a relay for itself, not on behalf of someone else), verify that the address claimed in the relevant field is contained in `h.vpnAddrs`. If it isn't, drop the message with a debug/error log, consistent with existing nil-check validation already present in `HandleControlMsg`.
3. Add unit tests in `relay_manager_test.go`/`control_test.go` covering: (a) a Control message where `RelayFromAddr` matches the sender's own vpnAddrs is still accepted, (b) a Control message where `RelayFromAddr` does not match the sender's vpnAddrs is rejected and logged, (c) verify no relay state (`h.relayState`) is created for the mismatched case.
4. Add/extend an e2e test (similar to `e2e/handshakes_test.go`'s wrong-responder tests) simulating a peer spoofing another peer's VPN address in a `CreateRelayRequest` to confirm the relay host now rejects it and no relay entry is created under the spoofed identity.
5. Update any relevant documentation/comments in `relay_manager.go` describing the trust model for relay identity fields.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}
