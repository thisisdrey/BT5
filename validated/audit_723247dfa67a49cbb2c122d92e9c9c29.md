## Title
StackerDB chunk signatures omit the destination contract, enabling cross-StackerDB chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The go-resolver bug lets an attacker present a validly-signed RRSIG for domain A as proof for domain B, because the RRSIG's owner name is never checked against the record it is asserted to authenticate. The analog in this repo is `SlotMetadata::auth_digest`, which is the payload a StackerDB signer's `MessageSignature` commits to: it hashes only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the `QualifiedContractIdentifier` (the specific StackerDB/"domain") the chunk is destined for. [1](#0-0) 

### Finding Description
`SlotMetadata::sign`/`verify` compute the digest solely from `(slot_id, slot_version, data_hash)`: [2](#0-1) 

Chunk validation and storage (`try_replace_chunk` / `validate_received_chunk`) look up the expected signer *per contract* (`get_slot_signer`/`get_slot_validation`) and then call `slot_desc.verify(&signer)`, but the equality being checked is only "does this signature recover to the address registered as owner of `slot_id` in *this* contract" — the contract identity itself is not part of what was signed: [3](#0-2) [4](#0-3) 

Consequently, if the same `StacksAddress` is registered as the signer of slot `N` in two (or more) different StackerDB smart contracts — which is a realistic configuration for the Nakamoto signer set, since the same signer set is replicated across multiple parallel "lane" contracts (e.g. per-message-type StackerDB instances keyed by `(reward_cycle, message_id)`) with the same slot ordering — a chunk that was validly signed and broadcast for contract A can be repackaged (by any relayer/observer, without the private key) inside a `StackerDBPushChunkData` naming contract B, or replayed during sync for contract B, and it will pass `validate_received_chunk`/`try_replace_chunk` as if the signer had authored it for contract B. The `contract_id` field that routes the chunk to a specific replica lives at the P2P message layer (`StackerDBPushChunkData::contract_id`) and is not covered by `sig`, so it is fully attacker-controlled/re-writable. [5](#0-4) 

This breaks the intended equality "signed-for-contract-A == stored-into-contract-A": the signature only proves "signed some (slot_id, slot_version, data) triple", not "signed for this specific StackerDB namespace," exactly mirroring the unvalidated-RRSIG-owner-name flaw where a signature scoped to one context is accepted as proof for a different context.

### Impact Explanation
An unprivileged network participant who observes one legitimately signed StackerDB chunk (chunks are broadcast/gossiped in the clear) can forge acceptance of that chunk's data into a *different* StackerDB replica that happens to share the same signer-address-to-slot-id mapping, without possessing any private key. This is an unauthorized write of attacker-chosen routing (cross-contract data injection/confusion) and forged-data propagation across the P2P network via `process_stacker_db_chunks`'s broadcast path, which matches the "unauthenticated/unauthorized write to StackerDB" / "network-wide propagation of forged data" High/Critical impact classes in scope.

### Likelihood Explanation
Exploitability depends on the operational fact of whether any two StackerDB contracts share identical `(slot_id → signer address)` assignments. Given that Nakamoto's signer-message StackerDB contracts are provisioned per reward cycle/message-id from the same underlying reward-set/signer list (`signer-<cycle>-<message_id>` naming was seen referenced in `libsigner/src/events.rs`), such overlap across lanes within the same reward cycle is plausible, making this a real, not purely theoretical, replay avenue for a remote unprivileged attacker. I was not able to fully trace the code that assigns `(address, slot_id)` pairs when each per-lane StackerDB contract is provisioned (that logic lives in the boot-contract/PoX signer-set assignment code, which I could not fully confirm within scope), so the exact set of contracts sharing slot assignments is not certain from the code inspected.

### Recommendation
Include the destination `QualifiedContractIdentifier` (or a contract-specific domain separator) in `SlotMetadata::auth_digest` so that a chunk signature is cryptographically bound to the specific StackerDB it was authored for, preventing cross-contract replay regardless of overlapping signer-to-slot assignments.

### Proof of Concept
1. Configure two StackerDB contracts, `contract-A` and `contract-B`, both registering `StacksAddress` derived from `privk` as the signer of `slot_id = 0`.
2. Signer with `privk` creates and signs `StackerDBChunkData { slot_id: 0, slot_version: 1, data: b"legit-for-A" }` and broadcasts it as a `StackerDBPushChunkData { contract_id: contract-A, chunk_data }`.
3. An attacker (no private key) observes this message on the wire, copies `chunk_data` unmodified, and re-broadcasts it wrapped in `StackerDBPushChunkData { contract_id: contract-B, chunk_data }`.
4. `validate_received_chunk`/`try_replace_chunk` for `contract-B` looks up the slot-0 signer (same address), calls `slot_metadata.verify(&addr)`, which succeeds because the digest never referenced `contract-A`/`contract-B` — the forged chunk is accepted and stored into `contract-B`'s slot 0, and then re-broadcast further by `process_stacker_db_chunks`, propagating the cross-context forgery network-wide.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
