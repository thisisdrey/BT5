### Title
GetAttachment RPC handler serves stored content without re-verifying it hashes to the requested `attachment_hash` - (File: stackslib/src/net/api/getattachment.rs)

### Summary
`RPCGetAttachmentRequestHandler::try_handle_request` parses and hex-decodes the requested `attachment_hash` from the URL, then calls `network.get_atlasdb().find_attachment(&attachment_hash)` and directly wraps whatever `Attachment` is returned into `GetAttachmentResponse` and serves it to the client. There is no re-computation of `Hash160::from_data(&attachment.content)` and comparison against the requested `attachment_hash` at this serving boundary.

### Finding Description
In `try_parse_request` (lines 58-84), the only validation performed is a regex match (`^/v2/attachments/(?P<attachment_hash>[0-9a-f]{40})$`) and `Hash160::from_hex` decoding of the path segment — this only confirms the *request* string is a well-formed 40-hex-char hash, it says nothing about the *stored* content's integrity.

In `try_handle_request` (lines 93-130), the code path is:
```
match network.get_atlasdb().find_attachment(&attachment_hash) {
    Ok(Some(attachment)) => Ok(GetAttachmentResponse { attachment }),
    _ => ... HttpNotFound ...
}
```
`Ok(Some(attachment))` is trusted verbatim and serialized straight into the JSON response body (line 109, 127-129) — there is no line anywhere in this function that recomputes `Hash160::from_data(&attachment.content)` and asserts it equals `attachment_hash` before returning `Ok`. The handler assumes the AtlasDB's `content`↔`hash` mapping is trustworthy by construction, and delegates all integrity guarantees to whatever wrote the row into the `attachments` table.

Given a precondition where a row in AtlasDB's `attachments` table is inserted with a `content` blob that does not hash to its stored `hash` key (a poisoning of the DB write path, as established separately for `db.rs`), this handler will unconditionally serve that mismatched pair back to any unprivileged remote client that requests the hash — since this endpoint requires no authentication, no RPC secret, and no privileged role, just a well-formed GET to `/v2/attachments/<hash>`.

### Impact Explanation
A remote unprivileged client (or any node relaying the attachment onward) would receive `Attachment.content` that does not correspond to the semantically canonical `attachment_hash` it requested, i.e., attachment/BNS data served that does not match its purported hash — this is the "attachment/BNS mismatch" category in the High severity bucket. This is fully repeatable per poisoned row and does not require any special peer state, only that the underlying AtlasDB actually contain such a mismatched row.

### Likelihood Explanation
This finding's real-world exploitability is entirely gated on the precondition that AtlasDB's write/insertion path can be made to store a `(hash, content)` pair where `content` does not hash to `hash` — i.e., it depends on the separately-scoped `db.rs` insertion vulnerability actually existing and being reachable by an unprivileged attacker. If that precondition holds, exploiting this endpoint costs a single unauthenticated GET request and is trivially repeatable. This specific file offers no independent guard (no hash re-verification) that would have otherwise blocked the poisoning from being served.

### Recommendation
In `RPCGetAttachmentRequestHandler::try_handle_request`, after obtaining `Ok(Some(attachment))` from `find_attachment`, recompute `Hash160::from_data(&attachment.content)` and compare it to `attachment_hash`; if they differ, log the integrity violation and return `HttpNotFound`/`HttpServerError` instead of serving the mismatched content. This closes the gap regardless of how the mismatch entered the database.

    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        captures: &Captures,
        query: Option<&str>,
        _body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        if preamble.get_content_length() != 0 {
            return Err(Error::DecodeError(
                "Invalid Http request: expected 0-length body".to_string(),
            ));
        }

        let attachment_hash_str = captures
            .name("attachment_hash")
            .ok_or(Error::DecodeError(
                "Failed to match path to attachment_hash group".to_string(),
            ))?
            .as_str();

        self.attachment_hash = Some(
            Hash160::from_hex(attachment_hash_str)
                .map_err(|_| Error::DecodeError("Failed to decode `attachment_hash`".into()))?,
        );

        Ok(HttpRequestContents::new().query_string(query))
    }

    fn try_handle_request(
        &mut self,
        preamble: HttpRequestPreamble,
        _contents: HttpRequestContents,
        node: &mut StacksNodeState,
    ) -> Result<(HttpResponsePreamble, HttpResponseContents), NetError> {
        let attachment_hash = self
            .attachment_hash
            .take()
            .ok_or(NetError::SendError("Missing `attachment_hash`".into()))?;

        let attachment_res = node.with_node_state(
            |network, _sortdb, _chainstate, _mempool, _rpc_args| match network
                .get_atlasdb()
                .find_attachment(&attachment_hash)
            {
                Ok(Some(attachment)) => Ok(GetAttachmentResponse { attachment }),
                _ => {
                    let msg = "Unable to find attachment".to_string();
                    warn!("{msg}");
                    Err(StacksHttpResponse::new_error(
                        &preamble,
                        &HttpNotFound::new(msg),
                    ))
                }
            },
        );
        let attachment = match attachment_res {
            Ok(attachment) => attachment,
            Err(response) => {
                return response.try_into_contents().map_err(NetError::from);
            }
        };

        let preamble = HttpResponsePreamble::ok_json(&preamble);
        let body = HttpResponseContents::try_from_json(&attachment)?;
        Ok((preamble, body))
    }
