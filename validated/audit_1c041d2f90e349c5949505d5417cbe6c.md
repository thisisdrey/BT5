### Title
Legacy `ExchangeProcessor` bonding-curve math uses lossy double-precision floating point, enabling committee-gated (proposal 66/`allowHardenExchangeCalculation`) but still-default-off exploitation of TRC10 exchange pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` path for TRON's built-in TRC10 "Bancor-style" exchange pools computes swap outputs via `ExchangeCapsule.transaction()`, which by default (unless the `allowHardenExchangeCalculation` dynamic parameter is turned on via committee proposal) uses the legacy `ExchangeProcessor` implementation instead of the newer `SafeExchangeProcessor`. [1](#0-0) [2](#0-1) 

### Finding Description
`ExchangeProcessor.exchangeToSupply()` and `exchangeFromSupply()` perform the Bancor relay-token pricing formula using native Java `double` arithmetic (`Maths.pow(...)`), then truncate the result to a `long` via a raw `(long)` cast: [3](#0-2) 

This is exactly the bug class in the SVT report: a floating-point/discretized bonding-curve price calculation that is not path-independent, so splitting a trade into multiple smaller calls (or performing sequences of buy/sell operations) against the same pool state within one transaction/flash-loan context can yield an aggregate result that diverges from a single large trade, extracting value that a correct AMM/bonding-curve should never allow. The project's own test suite for the safe path exists specifically because this defect was identified and "hardened" via `SafeExchangeProcessor`, which replaces `double`/`Maths.pow` with `BigDecimal` and exact overflow-checked arithmetic: [4](#0-3) 

Crucially, the hardened path is opt-in and controlled by the `allowHardenExchangeCalculation` dynamic property, exposed through the committee `ProposalUtil`/`ProposalService` proposal mechanism, not a hardfork forced on at genesis: [2](#0-1) 

Any unprivileged account can call `ExchangeTransactionContract` (via `ExchangeTransactionActuator`) repeatedly against a live TRC10 exchange pool. As long as `allowHardenExchangeCalculation` has not been switched on for the network, every trade is routed to the legacy floating-point `ExchangeProcessor`: [5](#0-4) 

### Impact Explanation
If the double-precision truncation systematically favors the trader in one direction (analogous to how the SVT pool's flawed calc allowed profitable buy/sell splitting), an attacker can repeatedly call `ExchangeTransactionActuator` to drain the counter-token reserve of any TRC10 exchange pool below its true bonded value, i.e., unbacked balance extraction / theft of pool funds — the reserves belong to the injecting user(s), and users' balances are directly debited/credited from `AccountStore` on every call. This maps to "unauthorized account operation, theft of funds" under the validation criteria.

### Likelihood Explanation
This requires only a single signed `ExchangeTransactionContract` broadcaster with TRX and/or TRC10 balance and access to some funded exchange pool — no special privilege. The actual exploitability depends on the precise sign/magnitude of the truncation bias across the specific `pow` exponents (0.0005 / 2000.0) used, which I could not fully re-derive analytically here; I could not confirm from the index whether `allowHardenExchangeCalculation` is enabled by default on mainnet (the `DynamicPropertiesStore` default-value initialization code was not retrievable within the available index — likely due to index size limits truncating that file). This is a meaningful gap: if the hardened calculation is already the default/mandatory state on the live chain, this analog is not practically exploitable today.

### Recommendation
- Confirm the default value of `allowHardenExchangeCalculation` in `DynamicPropertiesStore` (via a full checkout, since the index did not return its initializer) and whether it has already been activated on mainnet via committee proposal.
- If not yet default-on, prioritize activation of `allowHardenExchangeCalculation` and deprecate/remove the legacy `ExchangeProcessor` double-based path entirely, since `SafeExchangeProcessor` already exists as a drop-in, exact-arithmetic replacement.
- Add invariant checks in `ExchangeCapsule.transaction()` (independent of `hardenedCalc`) ensuring `buyTokenQuant` never exceeds the pool's real backing ratio, and that repeated trade splitting cannot produce better aggregate pricing than a single trade of equivalent total size.

### Proof of Concept
Not independently reproducible from the indexed code alone — I was unable to fully verify the numeric direction/magnitude of the float-truncation bias in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, nor confirm current mainnet activation state of `allowHardenExchangeCalculation`. This would require running the existing `ExchangeProcessorTest`/`ExchangeCapsuleTest` unit tests (which already probe legacy-vs-hardened divergence, e.g. `testTransactionLegacyVsHardenedProcessorSelection`) with a sequence of split trades to empirically demonstrate profit extraction, which I cannot execute in this read-only analysis.     logger.debug("balance: " + balance);
    long newBalance = balance + quant;

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

        ByteString.copyFromUtf8("owner"), 101L, 0L,
        "abc".getBytes(), "def".getBytes());

    long hardenedResult = hardened.transaction("abc".getBytes(), 1_000_000L, true, true);

    Assert.assertTrue("Both must return positive", legacyResult > 0 && hardenedResult > 0);

        hardenedResult <= 100_000_000L);
