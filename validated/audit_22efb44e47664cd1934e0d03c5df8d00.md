### Title
Fixed-window stream throttling allows ~2x burst of streams by straddling the `STREAM_THROTTLING_INTERVAL` boundary - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (non-sliding) window rate limiter: the stream counter is reset to 0 only when more than `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since the last reset. An attacker can send `max_streams_per_throttling_interval` streams right before a window reset and another full batch right after, achieving roughly double the intended stream rate within a short, attacker-chosen 100ms-ish span.

### Finding Description
`throttle_stream` calls `stream_counter.reset_throttling_params_if_needed()` [1](#0-0)  which only resets `stream_count` to 0 and moves `last_throttling_instant` forward when the elapsed time since the last reset exceeds `STREAM_THROTTLING_INTERVAL` [2](#0-1) . Because the window boundary is defined purely by wall-clock time since the last reset (not a rolling/sliding accounting of streams over the trailing `STREAM_THROTTLING_INTERVAL`), a client can open `max_streams_per_throttling_interval` streams at time `T - ε` (just before the next reset fires) and then open another `max_streams_per_throttling_interval` streams at `T + ε` (immediately after `stream_count` is zeroed). Since `throttle_stream` only checks `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` against the counter that was just reset [3](#0-2) , no throttling/backoff sleep is triggered for the second burst, so effectively `2 * max_streams_per_throttling_interval` streams from the same connection are processed within a window smaller than `STREAM_THROTTLING_INTERVAL`. This is a classic "fixed window counter" property, not a sliding-window rate limiter.

### Impact Explanation
This doubles the number of QUIC streams (and thus the packets/transactions read from an unstaked or low-staked single connection) that reach the streamer -> sigverify/banking pipeline within a short window, before per-transaction fees are collected, matching "grossly underpriced pre-fee work" for a single connection. The bound is still deterministic and finite per interval boundary (roughly 2x, not unbounded), and other layers (max unstaked connections, EMA-based staked throttling, sigverify cost limits, banking stage QoS) still apply afterward, so the practical impact is a bounded throughput amplification against the per-connection QUIC stream throttle rather than a full DoS or verification bypass.

### Likelihood Explanation
Fully feasible with a single unstaked QUIC connection and precise local timing of `open_uni()` calls around the 100ms window edge; no special privileges, staking, or multiple clients are required, and the behavior is deterministic given the fixed-window design, making it repeatable every ~100ms boundary.

### Recommendation
Replace the fixed-window reset in `ConnectionStreamCounter::reset_throttling_params_if_needed` with a sliding-window or token-bucket accounting scheme (e.g., track timestamps of recent streams, or decay the counter proportionally to elapsed time) so that no rolling `STREAM_THROTTLING_INTERVAL`-sized window can ever see more than `max_streams_per_throttling_interval` streams from a connection, regardless of when the internal reset boundary falls.

### Proof of Concept
Integration/unit test plan for `streamer/src/nonblocking/stream_throttle.rs`:
```rust
#[tokio::test]
async fn test_boundary_straddle_doubles_throughput() {
    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;

    // Burst 1: consume full quota just before reset.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Advance clock to just past STREAM_THROTTLING_INTERVAL to force reset.
    tokio::time::pause();
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst 2: immediately after reset, another full quota is allowed with no throttle sleep.
    let start = tokio::time::Instant::now();
    for _ in 0..max_streams {
        throttle_stream(
            &stats,
            ConnectionPeerType::Unstaked,
            "127.0.0.1:1234".parse().unwrap(),
            &counter,
            max_streams,
        ).await;
    }
    let elapsed = start.elapsed();

    // Assert: no throttling delay incurred for second burst even though
    // total streams (burst1 + burst2 = 2 * max_streams) occurred within
    // less than one full STREAM_THROTTLING_INTERVAL of wall-clock time.
    assert!(elapsed < STREAM_THROTTLING_INTERVAL);
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);
}
```
Expected (buggy) result: the second burst completes with zero throttling despite `2 * max_streams` streams occurring within one `STREAM_THROTTLING_INTERVAL`-sized sliding window, demonstrating the invariant violation described above.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
