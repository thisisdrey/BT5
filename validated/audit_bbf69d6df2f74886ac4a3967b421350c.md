## Title
Unchecked/fire-and-forget `Promise` transfers in the ETH-implicit Wallet Contract can silently lose user funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

## Summary
The near-wallet-contract (the "Wallet Contract" deployed on ETH-implicit accounts per NEP-518) creates low-level `Promise` transfer batches to pay relayers and refund callers, but never chains a callback to observe whether those transfers actually succeed. This is the direct on-chain analog of the reported LooksRare `call`-opcode issue: a value-bearing external call whose result is never checked, so a failure silently drops funds instead of triggering a compensating action.

## Finding Description
In `inner_rlp_execute`, when the wallet emulates an ETH base-token transfer or ERC-20 transfer with a non-zero relayer `fee`, the contract issues the fee payment as an independent, un-awaited promise batch: [1](#0-0) 

This `refund_promise` is created with `env::promise_batch_create` / `env::promise_batch_action_transfer` and is **not** `.then()`-chained to any callback — its result is never inspected anywhere in the contract (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`) via `env::promise_result`.

The same fire-and-forget pattern appears again in the failure branch of `rlp_execute_callback`, where the caller's attached deposit is supposed to be refunded if the main cross-contract call fails: [2](#0-1) 

Here again, `env::promise_batch_action_transfer` is invoked and the function immediately returns `ExecuteResponse { success: false, ... }` without waiting for or checking the refund promise's outcome.

This mirrors the LooksRare `_returnETHIfAny` bug exactly: a value transfer is dispatched but its completion is never verified, so the calling code (and the wallet's bookkeeping via `has_in_flight_tx`/`nonce`) proceeds as if the transfer always succeeds.

## Impact Explanation
If either of these unchecked transfers fails (e.g. the recipient account no longer exists, receives it in an invalid implicit-account format, or a gas/complexity limit is exceeded while processing that receipt), the deducted balance is not returned to the wallet contract and no error surfaces to the wallet owner or relayer:
- The relayer-fee transfer in `inner_rlp_execute` is deducted from the wallet's balance unconditionally and before the main action promise even resolves; if it fails, the user has effectively paid a fee for nothing and has no way to detect or recover it since the contract records success/failure based solely on the *other* promise chain.
- The caller-deposit refund in `rlp_execute_callback` is the compensating refund path for a *failed* action; if this refund itself fails, the user's attached deposit is permanently lost with the contract reporting only "Failed Near promise" and no indication that the refund also failed.

Both cases result in unrecoverable loss of user funds without any protocol-level or contract-level detection, matching the "confirmed, Medium severity, dust-level impact" classification of the original finding.

## Likelihood Explanation
Likelihood is low-to-moderate and bounded, similar to the original report's assessed severity: NEAR `Transfer` actions to existing accounts essentially always succeed, so failures are edge cases (e.g. transient/system-level receipt failures, or an account being deleted concurrently). The impact is also self-limited to the fee/refund amount per transaction (not the full transferred value), consistent with the "only dust is impacted" judgment in the original report.

## Recommendation
Chain both value transfers through the existing callback/promise-result system instead of firing them independently:
- Combine the relayer-fee transfer with the main action promise (or its own `.then()` callback) so `env::promise_result` can confirm success, and only mark the fee as "paid" (or retry/refund) based on that result.
- In `rlp_execute_callback`'s failure branch, chain the caller-deposit refund to a follow-up callback that checks `env::promise_result` for the refund itself, and surface a distinct error (or retry mechanism) if the refund transfer also fails, rather than assuming it always succeeds.

## Proof of Concept
1. Deploy the Wallet Contract on an ETH-implicit account and fund it.
2. Have the relayer submit an emulated ERC-20/base-token transfer transaction with a non-zero `fee` (per `EthEmulationKind::EOABaseTokenTransfer`/`ERC20Transfer`) via `rlp_execute`.
3. `inner_rlp_execute` fires `env::promise_batch_action_transfer(refund_promise, *fee)` unconditionally at [3](#0-2)  without ever chaining a result check.
4. If that transfer receipt fails for any reason (e.g. predecessor account state changes concurrently, or a transient shard/receipt failure), the `fee` amount is deducted from the wallet balance with no compensating action and no observable failure signal — the wallet's own accounting (`nonce`, `has_in_flight_tx`) proceeds as though the fee payment succeeded.
