## Title
Self-trade in `MarketSellAssetActuator` causes lost balance update due to aliased account state (analogous to src_reg==dst_reg aliasing bug) - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
The CVE describes a bug class where an in-place mutation of shared/aliased state (`src_reg == dst_reg`) causes a stale read of "the same" logical value through a second reference, producing incorrect derived state. The closest reachable analog in java-tron is `MarketSellAssetActuator`, which allows an account to match its own resting order (self-trade) and manages the taker and maker sides of the same underlying account as **two independently-loaded, independently-persisted `AccountCapsule` objects**, with a last-write-wins persistence order.

### Finding Description
In `execute()` [1](#0-0) , the taker account (`accountCapsule`) is loaded once, its sell-side balance is debited via `transferBalanceOrToken`, and then `matchOrder` is invoked with this in-memory object. Inside matching, `matchSingleOrder` calls two different code paths for crediting the buy-side token:
- For the taker, it reuses the passed-in `takerAccountCapsule` reference (in-memory only, not yet persisted): [2](#0-1) 
- For the maker, `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` performs a **fresh** `accountStore.get(...)` fetch, mutates it, and immediately `accountStore.put(...)`s it: [3](#0-2) 

There is no validation preventing the maker order owner and the taker owner from being the same address (no `Arrays.equals(ownerAddress, ...)` self-check exists in this actuator, unlike `TransferActuator`/`TransferAssetActuator`/`DelegateResourceActuator` which explicitly reject `to==from`). When an account's own new sell order matches its own existing resting order (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` self-trade path is handled explicitly at line 418: "// taker == maker" referring to quantity equality, but nothing prevents *account* equality), the sequence is:

1. Taker capsule object A is loaded and debited (sell token) in memory only.
2. During matching, the maker-side `addTrxOrToken` loads a **separate object B** for the same address from `accountStore`, credits the maker buy-token amount, and persists B immediately.
3. Back in taker-side matching, object A (still holding the pre-match state plus taker's own credit) is mutated in memory only.
4. At the end of `execute()`, `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` persists object A, **overwriting** the store with a version that never observed the maker-side credit written by object B in step 2.

This is structurally identical to the kernel bug's root cause: two references (`src_reg`/`dst_reg`, here "taker capsule"/"maker capsule") alias the *same* underlying state, one is mutated and persisted first, and the second reference's stale pre-mutation snapshot is used to compute/overwrite the final value, silently dropping the first mutation ("linked" delta lost).

### Impact Explanation
If exploitable, this results in silent loss of a self-trade's maker-side credit (unbacked-balance mismatch relative to what should have been received, or in other orderings a duplicated credit), i.e., non-deterministic loss/gain of TRC10 token or TRX balance purely from placing an order that matches one's own book entry. This falls into the "unbacked balance" / "permanent freezing/loss of funds" impact category from a single, unprivileged, self-issued transaction (`MarketSellAssetContract`), reachable by any account with two resting/crossing orders.

### Likelihood Explanation
Medium-High: any account can create two market orders on opposite sides of the same token pair and then submit a matching sell order to trigger self-matching; no special privileges are required. However, I was **not able to fully trace and confirm** the exact object lifecycle/final persisted values through `matchOrder`'s loop and the final `accountStore.put` in `execute()` with full certainty (e.g., whether other intermediate writes/reads inside `MarketUtils.updateOrderState` or repeated calls to `accountStore.get` inside the loop could re-synchronize state before the final taker `put`). This requires dynamic testing/tracing to confirm the exact net balance effect and directionality (loss vs. gain) for the maker-credit path, which I could not complete with the available static search tools.

### Recommendation
- Load the account object once per address within a single order-matching transaction and route all balance/asset mutations (taker and maker sides) through that single in-memory `AccountCapsule` reference before a single terminal `accountStore.put`, eliminating aliasing/last-write-wins races when taker and maker addresses coincide.
- Alternatively/additionally, explicitly detect self-trade (`Arrays.equals(takerOwnerAddress, makerOrderCapsule.getOwnerAddress().toByteArray())`) in `matchSingleOrder`/`matchOrder` and handle it as a single unified account update, consistent with the self-transfer/self-delegate guards already present elsewhere in the codebase (`TransferActuator`, `TransferAssetActuator`, `DelegateResourceActuator`).
- Add a regression test with two resting orders and a matching order all from the same account, asserting the post-execution balance equals the pre-trade balance minus/plus the correct net token deltas (no silent loss).

### Proof of Concept
Conceptual (not dynamically verified due to tool limitations):
1. Account `A` places order O1: sell TokenX 100 for TokenY 100 (added to order book).
2. Account `A` places order O2 (`MarketSellAssetContract`): sell TokenY 100 for TokenX 100, which matches O1 exactly (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch at line 418).
3. `execute()` debits `A`'s TokenY balance (in-memory object A1), then `matchOrder` → `matchSingleOrder` credits maker-side TokenX to a freshly-fetched object A2 for the same address and persists A2 immediately via `accountStore.put`.
4. The taker-side TokenX credit is applied to A1 in memory only; at the end of `execute()`, `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` persists A1, which does not include A2's already-persisted TokenX credit from step 3 — resulting in the final stored balance under-crediting (or over-crediting, depending on read timing) the TokenX amount that should have been received from the self-match.

Because I could not execute the actual matching engine to observe wire-level before/after balances, this should be validated with an integration test (e.g., extending `MarketSellAssetActuatorTest`) using a single account as both maker and taker before treating this as confirmed-exploitable, though the code-level aliasing pattern (two independently loaded/persisted `AccountCapsule` objects for the same address within one contract execution) is confirmed by direct file/line inspection above.
