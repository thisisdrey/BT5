### Title
Broken `ReliabilityReport::score()` lets an always-failing peer stay "most reliable" forever, causing `AttachmentsDownloader` to exhaust retries against a malicious source and permanently drop a resolvable attachment - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentRequest::get_url()` sends the `/v2/attachments/<hash>` request to only the single highest-scoring peer in `sources`, selected via `get_most_reliable_source()` [1](#0-0) . The scoring function `ReliabilityReport::score()` is mathematically broken: it grows with the total number of requests sent (`n`) regardless of the peer's actual success rate, so a peer that fails every request can permanently outrank an honest peer with a perfect but smaller request history. Combined with `AttachmentsDownloader::run`'s retry-exhaustion logic, which drops the batch after `max_attachment_retry_count` failed rounds without ever trying an alternate source in `sources` [2](#0-1) , this allows a malicious-but-legitimately-inventoried peer to make a real, on-chain-committed attachment permanently unresolvable.

### Finding Description
The claimed equality is: "attachment deemed unresolvable after `max_attachment_retry_count` retries" ⇒ "no reachable honest peer holds `content_hash`". This equality is broken because peer selection per retry is not diversified across `sources`, and worse, the underlying reliability metric used to pick that single source is itself unsound.

`get_prioritized_attachments_requests` correctly builds `sources: HashMap<UrlString, ReliabilityReport>` containing every peer whose inventory response claims to have the byte at `position_in_page` [3](#0-2) . However, `Requestable::get_url()` for `AttachmentRequest` collapses this set down to a single URL via `get_most_reliable_source()`, which picks `max_by_key(|(_, v)| v.score())` [4](#0-3) . Only that one peer is actually queried for the attachment bytes in a given round; the rest of `sources` is never contacted in that attempt.

The score formula is:
```
self.total_requests_success * 1000 / (n * 1000) + n
``` [5](#0-4) 
Because numerator and denominator share the `*1000` factor, this integer division reduces to `floor(success / n) + n`. Whenever `success < n` (i.e., any failure has ever occurred), `floor(success/n) == 0`, so `score == n` — the score is dominated purely by the volume of requests sent, not by the success ratio. A peer that fails 100% of the time but has been queried many times (e.g., because it "won" reliability selection early and kept being re-selected) will have `score = n`, which grows without bound and can exceed the score of an honest peer that has been queried fewer times even with a perfect success record (`score = n_honest`, since `floor(success/n)=1` only adds `+1`). This means the peer-selection algorithm intended to favor trustworthy peers instead favors *heavily-used* peers irrespective of their actual reliability, entrenching a malicious/always-failing source as "most reliable" across retries.

`bump_failed_requests()` and `bump_successful_requests()` both increment `total_requests_sent` [6](#0-5) , so every additional failed attempt against the malicious peer *increases* its `n` and therefore its score, rather than demoting it. Consequently, across successive `AttachmentsBatch` retries (`run()`'s re-enqueue path [7](#0-6) ), the same malicious peer keeps being reselected as the sole target for the content hash, keeps 404'ing/timing out, and the batch is dropped once `retry_count >= max_attachment_retry_count`, even though the `sources` map (rebuilt each round from fresh `/v2/attachments/inv` responses) may still contain one or more honest peers that also claimed to have the attachment.

### Impact Explanation
A remote, unprivileged peer that is part of a node's outbound sync-peer set can cause a specific, real, on-chain-committed attachment (identified by `content_hash`) to be treated as permanently unresolvable by the victim node, even though other reachable honest peers hold the actual bytes. This matches the "attachment/BNS mismatch" High-impact category: the node ends up treating valid committed state as absent/unresolvable due to attacker-controlled peer selection, not due to genuine unavailability. The effect is repeatable for any attachment whose inventory the attacker peer advertises, and does not require volumetric flooding — a handful of 404/timeout responses per retry round (bounded by `max_attachment_retry_count`) suffices once the attacker has built up a sufficiently high `total_requests_sent` count to dominate the score.

### Likelihood Explanation
- The attacker must be an outbound sync peer of the victim (`get_outbound_sync_peers`) with a reachable data URL — achievable by simply running a normal, non-privileged Stacks peer.
- The attacker must claim (via `/v2/attachments/inv`) to have the attachment in its inventory bitmap so it's included in `sources`.
- The attacker needs its `ReliabilityReport.total_requests_sent` (`n`) to exceed that of competing honest peers, which happens naturally over time simply by being queried repeatedly (including by its own prior failures, since every failed request still increments `n`) — no special timing or privileged conditions required beyond being an active, frequently-contacted peer.
- Once dominant, a small number of additional 404/timeout responses (bounded by `max_attachment_retry_count`, e.g. as low as 1–2 in constrained configs) is enough to exhaust retries for a given batch.

### Recommendation
Fix `ReliabilityReport::score()` so it reflects actual success ratio (e.g., `total_requests_success as f64 / total_requests_sent as f64`, with a tie-breaker on volume only when ratios are equal), rather than being dominated by `total_requests_sent`. Additionally, modify `AttachmentRequest`/`BatchedRequestsState` to fall back to the next-best source in `sources` within the same retry round when the top-ranked source fails or 404s, instead of only exhausting the whole batch via `max_attachment_retry_count` against a single dominant peer.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/tests.rs`:
1. Construct two `ReliabilityReport`s: `honest = ReliabilityReport::new(5, 5)` (5/5 success) and `malicious = ReliabilityReport::new(1000, 0)` (0/1000 success, simulating a peer that has been queried many times and always failed).
2. Assert `malicious.score() > honest.score()` (reproducing `score() = floor(0/1000) + 1000 = 1000` vs `honest.score() = floor(5/5) + 5 = 6`), demonstrating the broken comparator directly against the `ReliabilityReport::score` code at `stackslib/src/net/atlas/download.rs:1299-1306`.
3. Build an `AttachmentRequest` with `sources` containing both `honest_url -> honest` and `malicious_url -> malicious`; assert `request.get_most_reliable_source().0 == &malicious_url`, showing the malicious, always-failing peer is selected as the sole request target via `AttachmentRequest::get_url` (`download.rs:1104-1108`).
4. End-to-end: drive `AttachmentsDownloader::run` with `max_attachment_retry_count = 1` and a mocked network where the malicious peer's inventory response marks the target `content_hash` present but its `/v2/attachments/<hash>` requests always return 404, while an honest peer (present in `sources` but never actually queried because it's never top-ranked) holds the real bytes; assert the batch is dropped (`info!("Atlas: dropping batch ...")` path at `download.rs:199-204`) rather than resolved, confirming the false-negative resolution outcome.

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }
