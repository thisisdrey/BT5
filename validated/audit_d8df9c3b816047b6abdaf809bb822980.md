## Title
Exchange trade DOS via front-run griefing on `ExchangeTransactionActuator`'s stale-state amount checks - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeTransactionActuator` validates a submitted `ExchangeTransactionContract` against the exchange pool's *current* token balances (`balanceLimit` cap and the AMM-computed `anotherTokenQuant` vs. `tokenExpected`). Because any account can submit a competing trade against the same exchange pool before a pending transaction is packed into a block, an attacker can shift the shared pool state so that a previously-valid transaction's amount check fails at execution time, exactly mirroring the JUSDBank `liquidate(amount)` front-run-to-revert pattern described in the report, where a shared balance check is invalidated by a cheap front-run trade.

### Finding Description
`doValidate()` in `ExchangeTransactionActuator` computes the projected new pool balance and expected output using the exchange's current `firstTokenBalance`/`secondTokenBalance`, then reverts if the limit is exceeded or the swap output falls short of the caller's `tokenExpected`: [1](#0-0) 

These checks are all evaluated against `exchangeCapsule.getFirstTokenBalance()`/`getSecondTokenBalance()`, which is *shared, mutable state* that any other account can change by submitting their own `ExchangeTransactionContract` against the same `exchangeId` (or via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which similarly gate on `balanceLimit`): [2](#0-1) 

Execution mirrors validate and re-reads the pool state at commit time: [3](#0-2) 

This is structurally identical to the JUSDBank flaw: a validate-time bound (`liquidatedInfo.depositBalance[collateral]` vs. `amount`) is computed from mutable shared state that an adversary can cheaply perturb between transaction broadcast and block packing (front-running), causing a `ContractValidateException`/revert for the victim's otherwise legitimate transaction:
- `balanceLimit` check: attacker submits a small trade in the same direction just before the victim's large trade, pushing `newTokenBalance`/`newAnotherTokenBalance` over `dynamicStore.getExchangeBalanceLimit()`, reverting the victim's transaction with "token balance must less than ...".
- `tokenExpected` (slippage) check: attacker submits a trade that shifts the AMM ratio so `exchangeCapsule.transaction(...)` returns less than the victim's `tokenExpected`, reverting with "token required must greater than expected".

Both paths are reachable by any account holding TRX/TRC10 fee balance, requiring no special privilege — a normal signed `ExchangeTransactionContract`/`ExchangeInjectContract` transaction.

### Impact Explanation
An attacker can repeatedly and cheaply grief a specific victim's exchange trade, indefinitely preventing that trade from executing (denial of service on a specific market operation) by keeping the pool balance pinned near `balanceLimit` or by continuously moving the AMM price against the victim's expected-output guard. Because trade parameters (`quant`, `expected`, `exchangeId`) are fixed at signing time and the Exchange contract type has no slippage/near-miss recovery, a victim with time-sensitive intent (e.g., needing to complete a trade before a price move, similar to a liquidator racing a closing debt window) can be denied service block after block, unlike a normal AMM sandwich which merely worsens price but doesn't force a hard revert of the whole operation.

### Likelihood Explanation
The attack requires only observing pending transactions in the mempool (standard front-running capability) and paying trivial trade sizes to move the shared pool state; both `ExchangeTransactionActuator` and `ExchangeInjectActuator` are open to any account, with no ownership or permission gating.

### Recommendation
- Avoid using `expected`/`balanceLimit` hard exact-amount reverts for pool state that can be trivially manipulated between signing and execution; instead compute using a tolerance/range or make `expected` a lower bound applied to a partial-fill amount rather than an all-or-nothing revert.
- Consider adding commit-reveal or a minimum settlement window / anti-frontrunning ordering guarantee for `ExchangeTransactionContract`, or allow `amount`/`expected` to be automatically clamped to the maximum executable amount rather than reverting the whole transaction, analogous to the JUSDBank report's own recommendation to clamp instead of revert.

### Proof of Concept
1. Victim signs and broadcasts `ExchangeTransactionContract` with `exchangeId=E`, `tokenId=T`, `quant=Q`, `expected=Exp` (a large trade near `balanceLimit`).
2. Attacker observes the pending transaction and broadcasts a cheap `ExchangeTransactionContract` (or `ExchangeInjectContract`) on the same `exchangeId=E` and same `tokenId=T` with a small `quant`, packed in an earlier position in the same or a prior block.
3. This updates `exchangeCapsule`'s `firstTokenBalance`/`secondTokenBalance` via `Commons.putExchangeCapsule(...)`.
4. Victim's transaction now executes `doValidate()` against the new balances; `tokenBalance` (post-add) exceeds `balanceLimit` (see `ExchangeTransactionActuator.java:199-205`) or `anotherTokenQuant < tokenExpected` (see lines 217-221), throwing `ContractValidateException` and the whole transaction fails/reverts.
5. Attacker repeats this each time the victim resubmits, indefinitely blocking the victim's trade.
