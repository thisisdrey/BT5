### Title
Missing length validation when parsing shielded TRC20 event log data leads to DoS - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getNoteTxFromLogListByOvk` and the sibling `getNoteTxFromLogListByIvk` parse a `TransactionInfo.Log`'s raw `data` field at hard-coded byte offsets (up to offset 708) without first verifying that the log data is long enough, unlike the length-check that exists for the `logType == 4` branch a few lines below. A transaction/log crafted by any address that deploys a shielded-TRC20-like contract can emit a short log carrying the expected topics, causing an out-of-bounds slice and an uncaught exception when a client subsequently scans that block range via the shielded-note scanning API — mirroring the CVE-2021-25829 bug class of parsing binary/stream data at fixed offsets without validating the buffer size.

### Finding Description
In `getNoteTxFromLogListByOvk`: [1](#0-0) 
the code does:
```
byte[] logData = log.getData().toByteArray();
if (!ArrayUtils.isEmpty(logData)) {
  if (logType > 0 && logType < 4) {
    byte[] cm = ByteArray.subArray(logData, 32, 64);
    byte[] cv = ByteArray.subArray(logData, 64, 96);
    byte[] epk = ByteArray.subArray(logData, 96, 128);
    byte[] cenc = ByteArray.subArray(logData, 128, 708);
    byte[] coutText = ByteArray.subArray(logData, 708, 788);
```
No check exists that `logData.length >= 788` before these calls. Compare this with the `logType == 4` branch immediately below, which does perform an explicit length check before slicing: [2](#0-1) 

The same missing-length-check pattern exists in the IVK variant: [3](#0-2) 

`logType` is determined purely from topic-equality checks against a fixed set of well-known constants, not from any validated log-data length: [4](#0-3) 

Because `log.getAddress()` is only compared to the caller-supplied `contractAddress` argument (which the caller/attacker chooses when invoking the scan API) and the topics are compared to constant byte patterns, any account can:
1. Deploy an arbitrary contract.
2. Emit a `LOG` opcode whose topics match `SHIELDED_TRC20_LOG_TOPICS_MINT/TRANSFER/BURN_LEAF` but whose `data` payload is deliberately shorter than 788 bytes.
3. Have any client call `scanShieldedTRC20NotesByIvk`/`scanShieldedTRC20NotesByOvk` (or the equivalent HTTP/gRPC wallet endpoint) with that contract's address and a block range covering the crafted transaction.

`ByteArray.subArray` performs a raw `System.arraycopy`-based slice with no bounds validation (consistent with every other unchecked offset-parsing helper found across the codebase, e.g. `PrecompiledContracts` and `RLP` helpers that explicitly guard against this), so a request for `subArray(logData, 128, 708)` on data shorter than 708 bytes throws an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`-style runtime exception inside the note-scanning path, which is not wrapped in a defensive catch here.

### Impact Explanation
This crashes or errors the shielded-note scanning query path each time the crafted log is scanned, denying that API to legitimate users (an unprivileged API client cannot get results for any range containing the poisoned transaction), and depending on how the surrounding gRPC/HTTP service handles unchecked runtime exceptions, it can propagate and destabilize the serving thread/service — "an API the node can no longer serve," matching the accepted impact class for this analog.

### Likelihood Explanation
Likelihood is high: any account can deploy a contract and emit a log with attacker-chosen data at negligible cost, and the scanning API is reachable by any client supplying an `ivk`/`ovk` they themselves control together with the malicious contract's address — no privileged role or special permission is required.

### Recommendation
Add explicit length validation for `logData` before slicing in the `logType > 0 && logType < 4` branches of both `getNoteTxFromLogListByOvk` and `getNoteTxFromLogListByIvk` (analogous to the existing check performed for `logType == 4`), rejecting/returning `Optional.empty()` when `logData.length < 788` (or the minimum required size for the given logType) instead of allowing `ByteArray.subArray` to throw.

### Proof of Concept
1. Deploy a contract whose bytecode executes a `LOG` opcode with topics equal to `SHIELDED_TRC20_LOG_TOPICS_MINT` (or `_TRANSFER`/`_BURN_LEAF`) and a `data` payload shorter than 788 bytes (e.g., 32 bytes).
2. Call/trigger this contract from any unprivileged account so the log is recorded on-chain.
3. Invoke the wallet's `scanShieldedTRC20NotesByIvk` (or `...ByOvk`) API, passing the malicious contract's address as `shieldedTRC20ContractAddress` and a block range covering the triggering transaction, along with any (even self-generated) `ivk`.
4. Observe that `getNoteTxFromLogListByIvk`/`ByOvk` throws an unhandled exception when it attempts `ByteArray.subArray(logData, 128, 708)` on the undersized `logData`, failing the scan request.

Note: I was unable to fully trace the exact HTTP/gRPC servlet name that exposes `scanShieldedTRC20NotesByIvk`/`OvermnodesByOvk` to confirm the precise external endpoint wiring, nor did I retrieve the source of `ByteArray.subArray` directly to confirm it has zero bounds checking (inferred from the consistent unchecked-slice pattern used elsewhere in the codebase, and from the explicit length guard added only for the `logType == 4` case, implying the other branches were never guarded).

    if (Arrays.equals(logAddress, addressWithoutPrefix)) {

      byte[] topicsBytes = new byte[0];
      for (ByteString bs : logTopicsList) {
        topicsBytes = ByteUtil.merge(topicsBytes, bs.toByteArray());
      }
      if (Arrays.equals(topicsBytes, SHIELDED_TRC20_LOG_TOPICS_MINT)) {
        return 1;
      } else if (Arrays.equals(topicsBytes, SHIELDED_TRC20_LOG_TOPICS_TRANSFER)) {
        return 2;

        return 3;

        return 4;

        return 5;
