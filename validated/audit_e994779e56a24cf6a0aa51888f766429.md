Audit Report

## Title
Bounty claim silently loses payout funds when beneficiary transfer fails, since the result is only checked via `debug_assert!` - (File: `substrate/frame/bounties/src/lib.rs`)

## Summary
`claim_bounty` transfers the curator fee and beneficiary payout via `T::Currency::transfer`, but only checks the result with `debug_assert!(res.is_ok())`, a macro compiled out entirely in release builds. Regardless of whether the transfer to `beneficiary` actually succeeds, the code unconditionally deletes the bounty record and emits `Event::BountyClaimed` as if the payout definitely happened.

## Finding Description
In `claim_bounty` [1](#0-0) , the transfer to `beneficiary` is checked only with `debug_assert!`, which is a no-op in release builds. The underlying `Pallet::transfer` implementation delegates to `fungible::Mutate::transfer` [2](#0-1) , which will fail if the destination account doesn't exist and the transferred value is below the existential deposit (as evidenced by the ED enforcement logic present elsewhere in the same file, e.g. `deposit_creating`'s `ensure!(value >= ed || !is_new, ...)` at [3](#0-2) ).

The `beneficiary` account is freely chosen by the curator in `award_bounty` [4](#0-3) , an unprivileged role obtained merely by accepting curatorship via `accept_curator` [5](#0-4) . The curator also controls the bounty's `fee`, which determines `payout = balance.saturating_sub(fee)` computed in `claim_bounty` [6](#0-5) . By setting `fee` close to `value` and awarding to a never-funded account, `payout` can be forced below the existential deposit, guaranteeing the second transfer fails while the curator's own fee transfer succeeds.

`claim_bounty` is callable by any signed account (`ensure_signed(origin)?; // anyone can trigger claim`) [7](#0-6) . After the failed (but ignored) transfer, the bounty record is unconditionally removed (`*maybe_bounty = None`), descriptions are removed, and `BountyClaimed { payout, beneficiary }` is emitted [8](#0-7) , falsely reporting settlement. No later call path can reference the removed bounty to recover the stranded `payout` amount sitting in `bounty_account_id(bounty_id)`.

## Impact Explanation
This is a permanent fund lock: the bounty's payout amount becomes stranded in the bounty's sub-account with no remaining pallet call path able to reference or recover it, since `Bounties::<T,I>` no longer contains the entry (`award_bounty`, `close_bounty`, and `claim_bounty` all require `Bounties::<T,I>::get`/`try_mutate_exists` against an existing entry). On-chain state (the `BountyClaimed` event, and the removed bounty record) falsely reports the payout as settled, matching the required "duplicate settlement" / "permanent user-fund... lock" impact category, and the exact corrupted value is the `payout` amount transferred to `beneficiary`, which never leaves `bounty_account_id(bounty_id)` despite the ledger reporting settlement.

## Likelihood Explanation
The attack requires only an ordinary account becoming curator (via `propose_curator`/`accept_curator`, not requiring root/council powers over the destination choice) and any signed account (potentially the same curator) calling `claim_bounty` after the payout delay. No malicious validator, collator, leaked key, or governance abuse is needed — the curator role is an unprivileged position reachable through public extrinsics, and the bug can also trigger accidentally with a legitimately awarded but unfunded beneficiary whose payout share is below ED.

## Recommendation
Replace the `debug_assert!(res.is_ok())` checks in `claim_bounty` with `ensure!`/`?` propagation so a failed transfer aborts the extrinsic and leaves the bounty in `PendingPayout` state with funds intact in the bounty account, rather than silently deleting state and reporting false success. The same pattern should be checked in `substrate/frame/child-bounties/src/lib.rs::claim_child_bounty`.

## Proof of Concept
1. Deploy a chain with `ExistentialDeposit = E > 0`.
2. Propose and fund a bounty with `value = V`; have curator accepted via `accept_curator`.
3. Curator calls `award_bounty(bounty_id, beneficiary)` with a brand-new, never-funded `beneficiary` account, and a `fee` set (at proposal time, `fee <= value`) such that `payout = value - fee < E`.
4. Wait `BountyDepositPayoutDelay` blocks.
5. Any signed account calls `claim_bounty(bounty_id)`.
6. In a release build: the curator's fee transfer succeeds; the beneficiary payout transfer fails internally (`payout < E`, destination doesn't exist) but is silently discarded by `debug_assert!`; the bounty record is removed and `BountyClaimed` is emitted as if successful.
7. Verify `payout` remains stranded at `bounty_account_id(bounty_id)` with no pallet call path able to reference or recover it.

				};

			})?;
