### Title
Pushed microblocks anchored to non-canonical (`pox_valid=false`) sortitions are stored and relayed as canonical - (File: stackslib/src/net/relay.rs)

### Summary
`Relayer::preprocess_pushed_microblocks` resolves the `index_anchor_block` of a pushed `MicroblocksData` message to a `(consensus_hash, anchored_block_hash)` pair and looks up the corresponding sortition snapshot only to fetch `epoch_id`, never checking `block_snapshot.pox_valid`. Consequently, a microblock anchored to a block from a sortition on a non-canonical PoX fork is accepted by `chainstate.preprocess_streamed_microblock` and flagged `need_relay=true`, causing it to be stored and re-gossiped to peers as if it were on the canonical fork.

### Finding Description
In `preprocess_pushed_microblocks` (relay.rs:1480-1570), for each pushed microblock message the code does:

1. `chainstate.get_block_header_hashes(&mblock_data.index_anchor_block)` (relay.rs:1497) to recover `(consensus_hash, anchored_block_hash)` from the wire-supplied `index_anchor_block` (a `StacksBlockId`, fully attacker-controlled).
2. `SortitionDB::get_block_snapshot_consensus(sort_ic, &consensus_hash)` (relay.rs:1510) purely to obtain `block_snapshot.block_height`, which is then used only to fetch `epoch_id` (relay.rs:1512-1514).
3. It never inspects `block_snapshot.pox_valid` before proceeding to `chainstate.preprocess_streamed_microblock(&consensus_hash, &anchored_block_hash, mblock)` (relay.rs:1533).

If the anchored block referenced by the attacker's `index_anchor_block` sits on a sortition where `pox_valid == false` (a fork that has been PoX-invalidated / non-canonical), this code path still: (a) proceeds to determine `need_relay` via `has_descendant_microblock_indexed` (relay.rs:1529-1532), (b) calls `preprocess_streamed_microblock` which stores the microblock keyed by that `(consensus_hash, anchored_block_hash)` pair, and (c) on success inserts the microblock into `new_microblocks` keyed by `index_hash` for relay to peers (relay.rs:1538-1559). This breaks the invariant that microblocks stored/relayed via push should only be anchored to blocks on the currently-canonical PoX fork — the equivalent check is missing here even though such a check exists elsewhere for other message-processing code paths in the same file (other `pox_valid` references in relay.rs pertain to different code paths, e.g. block push processing, not this microblock push path).

The attacker's exact message is a `StacksMessageType::Microblocks(MicroblocksData)` where `index_anchor_block` is crafted to equal `StacksBlockHeader::make_index_block_hash(consensus_hash, anchored_block_hash)` for a `(consensus_hash, anchored_block_hash)` pair that the node has previously processed on a fork later invalidated by PoX (or that was never canonical), and `microblocks` contains a validly-formed microblock stream extending that anchored block.

### Impact Explanation
A remote, unprivileged peer can cause a node to store and re-gossip microblocks anchored to a block that is not part of the canonical PoX fork. This is a "serving non-canonical state as canonical" issue: other peers/clients querying unconfirmed microblock state for that anchored block will see attacker-supplied microblocks as if they were valid extensions of canonical chain state, and the node will propagate these forged/non-canonical microblocks network-wide via the `new_microblocks` relay mechanism. This matches the High severity category ("serving non-canonical state as canonical").

### Likelihood Explanation
The attacker needs no privileged role — any P2P peer can send a `MicroblocksData` push message. The only precondition is that the node has previously ingested (or can be made to ingest) a block header/snapshot for a `consensus_hash` whose sortition has `pox_valid=false` (e.g., a fork that was later invalidated), which is realistic in normal PoX-fork-switching operation. The attack is repeatable per non-canonical anchored block the attacker can reference, and is low-cost (a single crafted network message).

### Recommendation
In `preprocess_pushed_microblocks`, after resolving `block_snapshot` via `SortitionDB::get_block_snapshot_consensus`, check `block_snapshot.pox_valid` and skip/reject (and optionally penalize the sending neighbor) if it is `false`, mirroring the canonical-fork checks performed elsewhere in the codebase for block processing.

### Proof of Concept
1. Set up a `TestPeer`/`StacksChainState` fixture with two sortitions at the same or divergent heights: one canonical (`pox_valid=true`) and one where `pox_valid` is later flipped to `false` (simulate a PoX fork invalidation), each anchoring a distinct Stacks block.
2. Construct a `StacksMicroblock` extending the block on the `pox_valid=false` sortition, and build a `MicroblocksData { index_anchor_block: StacksBlockHeader::make_index_block_hash(non_canonical_consensus_hash, non_canonical_block_hash), microblocks: vec![mblock] }`.
3. Populate `NetworkResult::pushed_microblocks` with this message from a synthetic `neighbor_key`.
4. Call `Relayer::preprocess_pushed_microblocks(&sort_ic, &mut network_result, &mut chainstate)`.
5. Assert (per the question's proof idea) that the microblock is neither stored (`chainstate.has_descendant_microblock_indexed` / direct DB lookup for the mblock hash returns false) nor present in the returned `new_microblocks` relay list — the current code will fail this assertion because the microblock IS stored and IS added to `new_microblocks`, since `block_snapshot.pox_valid` is never checked at relay.rs:1509-1533.
