### Title
`VesperGateway.withdraw` calls Vesper `vToken.withdraw()` without a max-loss option, causing withdrawals to revert when the Vesper pool cannot pay the full amount - (File: contracts/VesperGateway.sol)

### Summary
In the source report, `withdrawFromSUSDVault()` invoked a Yearn vault `withdraw()` without specifying `max_loss`, so withdrawals reverted whenever the vault could not return the full requested amount — i.e., withdrawal unavailability. The Metronome analog is `VesperGateway.withdraw()` (`contracts/VesperGateway.sol:73-93`), the public path for users to exit a Synth collateral position into the Vesper pool's `underlying` token. It calls `vToken_.withdraw(_vTokenAmount)` unconditionally, with no way for the caller to accept a lossy withdrawal.

### Finding Description
`VesperGateway.withdraw` performs three steps: pull `msdTokens` from the caller, burn them via `_depositToken.withdraw(amount_, address(this))` to receive `vToken` shares, then call `vToken_.withdraw(_vTokenAmount)` and forward whatever `underlying` comes back (`contracts/VesperGateway.sol:80-92`).

Vesper `VPool.withdraw(shares)` (exposed here via `IVPool.withdraw`, `contracts/interfaces/external/IVPool.sol:12`) reverts when the pool does not hold enough liquid `underlying` to cover the shares' value — e.g., when funds are deployed into strategies (`AMO`'s own test suite shows `vamsETH.tokensHere()` drops to 0 after a strategy `rebalance()`, `test/E2E.mainnet.test.ts:871-884`) or when the pool reports a strategy loss. Unlike Yearn/Vesper's `withdraw(shares, maxLoss)` variants, the Metronome interface and gateway expose only the zero-loss-tolerant signature, and there is no strategist/governor-tunable max-loss parameter anywhere in the call path. The same unconditional call exists in `AMO._withdrawFromVesper` (`contracts/AMO.sol:145`), but that path is keeper/governor-gated; `VesperGateway.withdraw` is the user-facing one.

### Impact Explanation
Users who deposited `underlying` via `VesperGateway.deposit` cannot redeem back to `underlying` while the Vesper pool is illiquid or in loss: `vToken_.withdraw` reverts, and the whole transaction (including the already-pulled `msdTokens` and burned deposit position) rolls back. This is a temporary freezing of user funds lasting as long as the Vesper pool cannot cover the full withdrawal — matching the "unavailability of withdrawals" impact of the source bug. No modifier, pause flag, or health check prevents reaching the revert: `withdraw` is permissionless and only requires a registered pool (`contracts/VesperGateway.sol:73-74`).

### Likelihood Explanation
Vesper pools routinely move idle liquidity into strategies (Metronome's own E2E test relies on `rebalance()` leaving `tokensHere() == 0`). Any period of low pool liquidity, strategy utilization near 100%, or a strategy loss makes the full-amount `withdraw` revert. The trigger is external market/pool state, not a privileged actor, and any ordinary user hits it simply by calling `withdraw` during such a period. Severity is moderate: funds aren't stolen and users retain the option of withdrawing `vToken` shares directly via `DepositToken.withdraw` (they'd still hold the Vesper share position rather than `underlying`), so this is best classified as temporary freezing of funds / withdrawal unavailability.

### Recommendation
- Extend `IVPool`/`VesperGateway.withdraw` to support Vesper's loss-tolerant withdrawal variant (e.g., `withdraw(shares, maxLoss)` where available) and let the caller pass a `maxLoss_` parameter, defaulting to a sane bound.
- Alternatively, catch the revert or pre-check `vToken_.token()` liquidity (`tokensHere()`) and return the share-equivalent amount to the user, documenting that `underlying` redemption may be delayed when the pool is illiquid.

### Proof of Concept
Foundry fork test sketch (mainnet, existing `vamsETH`/vaUSDC Vesper pools):

```solidity
// 1. User deposits underlying through the gateway
vesperGateway.deposit(pool, vToken, amount);          // user receives msdTokens

// 2. Vesper strategy deploys/locks funds so tokensHere() < needed,
//    or simulate a strategy loss on the Vesper accountant.
vm.prank(vesperKeeper);
strategy.rebalance();                                 // tokensHere() -> 0

// 3. User tries to exit back to underlying
msdToken.approve(address(vesperGateway), amount);
vm.expectRevert();                                    // vToken.withdraw reverts (no maxLoss tolerated)
vesperGateway.withdraw(pool, vToken, amount);
```

The revert at `vToken_.withdraw(_vTokenAmount)` (`contracts/VesperGateway.sol:88`) demonstrates the withdrawal unavailability; a `maxLoss`-aware variant would succeed with a reduced `underlying` amount.
