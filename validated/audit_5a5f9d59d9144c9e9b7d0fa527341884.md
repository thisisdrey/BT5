Unauthenticated `RecvError` packet allows remote tunnel-state poisoning / teardown - (File: outside.go)

### Summary
`readOutsidePackets` dispatches `header.RecvError` packets in the "unencrypted packets" fast path, before any handshake completion check, index-ownership check, or AEAD decryption/authentication is performed. Any attacker who can send a UDP packet with a spoofed source address matching (or unknown-checked against) a victim's registered remote address can trigger tunnel teardown of an established, authenticated tunnel, purely by guessing/observing the `RemoteIndex` value.

`header.RecvError` is handled identically to `header.Handshake` — both are processed *before* the code reaches the `hostMap.QueryIndex`/AEAD-decrypt path that every other message type must pass through (lines 89–132). The handler is: [2](#0-1) 

The only gating checks are:
1. A rate-limit config (`f.acceptRecvErrorConfig.ShouldRecvError(addr)`) — a rate limiter, not an authentication check.
2. A lookup of the hostinfo by `h.RemoteIndex` via `QueryReverseIndex` — an attacker-supplied 32-bit index that can be brute-forced or observed on the wire (indices are transmitted in cleartext headers throughout the protocol).
3. A comparison of the source `netip.AddrPort` against `hostinfo.GetRemote()` — this is a plain address/port match, not a cryptographic proof of tunnel possession. Since UDP source addresses are trivially spoofable (no return-routability check, no signature, no counter/replay verification), this check offers no real authentication.

If these loose checks pass, `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` are called, unconditionally tearing down the tunnel — analogous to how the audited contract's `claimCompletedWithdrawals()` let an unauthenticated caller reset `_pendingWithdrawalAmount` to 0 and corrupt vault-wide accounting state without ever performing a real withdrawal. Here, an unauthenticated party can reset/corrupt the local peer's tunnel/hostinfo state without ever having participated in a valid handshake for that index.

This mirrors the report's root cause exactly: a state-mutating function reachable without proof of legitimate protocol participation, gated only by weak, spoofable checks (index guess + source-address match) rather than a cryptographic binding (e.g., a MAC over the RecvError payload, or verification via an authenticated channel).

### Impact Explanation
An off-path or spoofing attacker (no valid certificate, no completed handshake) can force closure of arbitrary active Nebula tunnels by sending crafted `RecvError` packets with guessed/observed `RemoteIndex` values and a spoofed source `AddrPort`. This is a remote state-poisoning / denial-of-service primitive against established, otherwise-secure tunnels — comparable in class to the reported vault-ratio corruption caused by an unauthenticated call resetting protected accounting state.

### Likelihood Explanation
`RemoteIndex` values are not secret — they are sent in cleartext in every packet header for a given tunnel, so an attacker who can observe any traffic on the path (or who is targeting a well-known lighthouse/relay index range) can obtain valid indices. Source-address spoofing over UDP is well-understood and commonly feasible unless additional network-layer protections (e.g., BCP38 filtering) are in place, which Nebula does not itself enforce for this packet type. The rate-limiting check (`ShouldRecvError`) mitigates volume but not exploitability by a single well-timed guess.

### Recommendation
Require some proof of tunnel knowledge before honoring a `RecvError` (e.g., authenticate it under the existing AEAD session, or require it to carry a value only derivable from the associated `ConnectionState`), rather than relying solely on `RemoteIndex` lookup plus a UDP source-address comparison. At minimum, treat `RecvError` handling with the same rigor changed for `claimCompletedWithdrawals` in the referenced remediation: ensure the acting party (source) is cryptographically tied to the specific tunnel/index before permitting the teardown/state-reset.

### Proof of Concept
1. Establish two Nebula peers `A` and `B` with an active tunnel (`hostinfo` on `A` referencing local index `idx`, remote `B`'s `AddrPort` as `bAddr`).
2. An attacker `M` who can spoof UDP packets with source `bAddr` sends `A` a raw packet: `header.Encode(..., header.RecvError, 0, idx, 0)` — exactly the format produced by `sendRecvError` at [3](#0-2)  — without ever performing a handshake or possessing any key material.
3. `A.readOutsidePackets` routes this straight to `handleRecvError` (bypassing decryption) at [4](#0-3) ; the address check at line 564 passes because `hr == bAddr` (spoofed), and `A` calls `closeTunnel`/`DeleteHostInfo`, tearing down the legitimate tunnel to `B`.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
