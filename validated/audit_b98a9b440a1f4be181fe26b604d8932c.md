### Title
`AtlasDB::insert_instantiated_attachment` stores attacker-supplied attachment content without enforcing `AtlasConfig.attachments_max_size` - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_instantiated_attachment` (stackslib/src/net/atlas/db.rs lines 576-592) writes `attachment.content` directly into the `attachments` table via `INSERT OR REPLACE` with no check against `self.atlas_config.attachments_max_size`. Attachment content that arrives from a `GetAttachmentResponse` (decoded in `StacksHttpResponse::decode_atlas_get_attachment`, stackslib/src/net/api/getattachment.rs lines 158-165) is stored unconditionally, so any peer serving a requested attachment can force storage growth beyond the configured cap.

### Finding Description
The equality that should hold is: bytes accepted into `attachments.content` ≤ `AtlasConfig.attachments_max_size`. Tracing the code:

- `insert_instantiated_attachment` [1](#0-0)  performs `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` using `attachment.content` verbatim, with no `content.len()` comparison against `self.atlas_config.attachments_max_size` anywhere in the function.
- The content originates from the network: `extend_with_attachments` in `stackslib/src/net/atlas/download.rs` (lines 530-558) takes the HTTP response, calls `response.decode_atlas_get_attachment()`, and inserts the resulting `Attachment` into `self.attachments` with **no validation of length or of the requested `content_hash`** before it is later passed to `insert_instantiated_attachment` in `AttachmentsDownloader::run` [2](#0-1) .
- `decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs` (lines 158-165) simply JSON-decodes the HTTP body into `GetAttachmentResponse` with no size cap tied to `attachments_max_size`; any size bound present is only the generic HTTP/JSON payload limit (`MAX_PAYLOAD_LEN`), which is unrelated to and typically much larger than the Atlas-specific `attachments_max_size` config value.

Because the attacker only needs to be selected as (or spoof itself as) the responding peer for an outstanding `AttachmentRequest`/`GetAttachment`, it can return an oversized `content` blob for a `content_hash` the local node is trying to resolve. The size is bounded only by the generic HTTP layer, not by the Atlas-specific `attachments_max_size` that the config is meant to enforce.

### Impact Explanation
A single malicious peer response can cause the node to write and persist attachment content into its local `attachments` sqlite table with a size not bounded by `AtlasConfig.attachments_max_size`, defeating the operator's configured storage bound for Atlas attachment caching. This is repeatable per attachment request/content_hash, allowing cumulative unauthenticated storage growth on the victim node, sourced from any peer the node happens to query for a given attachment.

### Likelihood Explanation
The attacker needs only to be reachable as one of the outbound sync peers/data URLs the victim queries for a missing attachment (`get_outbound_sync_peers`/`get_data_url` in `stackslib/src/net/atlas/download.rs`), which requires no special privilege, secret, or role — any peer that establishes a P2P/HTTP connection can be selected as a source when the node performs attachment inventory/discovery. No signature or additional authentication gates the attachment content itself before insertion, only the generic HTTP response parsing.

### Recommendation
In `insert_instantiated_attachment`, check `attachment.content.len() <= self.atlas_config.attachments_max_size` before executing the insert (and reject/log otherwise), and additionally verify `attachment.hash() == expected content_hash` from the corresponding `AttachmentRequest`/`AttachmentInstance` before accepting a downloaded attachment in `extend_with_attachments`/`AttachmentsDownloader::run`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AtlasConfig` with a small `attachments_max_size` (e.g., 1024 bytes).
2. Build an `Attachment` whose `content` is several megabytes.
3. Call `atlasdb.insert_instantiated_attachment(&attachment)` directly.
4. Assert the call succeeds (`Ok(())`) and that a subsequent `find_attachment(&attachment.hash())` returns the full oversized content — demonstrating the `attachments_max_size` bound is never enforced at the insertion boundary.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
