### Title
Missing/bypassable precision bounds check in `AssetIssueActuator` allows tokens with invalid decimal precision to be permanently stored - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
`AssetIssueActuator.validate()` is meant to enforce that a TRC10 asset's `precision` stays within `[0, 6]` (`ActuatorConstant.PRECISION_DECIMAL = 6`). The actual check is guarded by two extra conditions that make it possible for an unprivileged account to broadcast an `AssetIssueContract` transaction with an out-of-range (or negative) precision value that is never rejected and gets permanently persisted to the V1 `AssetIssueStore`.

### Finding Description
The precision validation in `validate()` is: [1](#0-0) 

```java
int precision = assetIssueContract.getPrecision();
if (precision != 0
    && dynamicStore.getAllowSameTokenName() != 0
    && (precision < 0 || precision > ActuatorConstant.PRECISION_DECIMAL)) {
  throw new ContractValidateException("precision cannot exceed 6");
}
```

The bounds check (`precision < 0 || precision > 6`) is only evaluated when **both** `precision != 0` and `dynamicStore.getAllowSameTokenName() != 0` hold. This means:

- When `AllowSameTokenName == 0`, the range check is skipped entirely regardless of the supplied `precision` value, including negative values or values far greater than 6.
- In `execute()`, when `AllowSameTokenName == 0`, only the **V2** capsule's precision is hard-coded to `0`; the **V1** capsule (`assetIssueCapsule`) keeps whatever unchecked `precision` value was supplied in the transaction and is written to `assetIssueStore`: [2](#0-1) 

```java
if (dynamicStore.getAllowSameTokenName() == 0) {
  assetIssueCapsuleV2.setPrecision(0);
  assetIssueStore
      .put(assetIssueCapsule.createDbKey(), assetIssueCapsule);
  assetIssueV2Store
      .put(assetIssueCapsuleV2.createDbV2Key(), assetIssueCapsuleV2);
} else {
  assetIssueV2Store
      .put(assetIssueCapsuleV2.createDbV2Key(), assetIssueCapsuleV2);
}
```

The `AssetIssueCapsule` simply stores whatever `precision` int is set on the protobuf without any additional clamping: [3](#0-2) 

This is precisely the missing-bounds-check bug class described in the external report (an asset field with a defined valid numeric range is only partially validated, allowing out-of-range values to be persisted as authoritative registry/token metadata).

### Impact Explanation
An unprivileged transaction broadcaster (any account funded to pay the asset-issue fee) can craft an `AssetIssueContract` with an arbitrary (including negative or >6) `precision` and have it permanently recorded in `AssetIssueStore` (V1) as long as `AllowSameTokenName == 0` at the time of the transaction (a network state that existed for a period of java-tron's history and is reachable in test/private networks or historical states). This corrupts asset metadata integrity relied upon by wallets, exchanges, explorers, and any downstream tooling/APIs that read `precision` from the V1 asset registry to interpret token amounts — a negative or oversized precision can cause incorrect amount scaling/display and integration errors for consumers of this on-chain data.

### Likelihood Explanation
The path is reachable with a single signed `AssetIssueContract` transaction from any account that can pay the token-issuance fee — no special privilege is required. The only precondition is that `dynamicStore.getAllowSameTokenName()` is `0`, a value fully controlled by chain configuration/history rather than by the caller, which somewhat limits the scenario to networks/time windows where that flag is still `0`.

### Recommendation
Remove the `dynamicStore.getAllowSameTokenName() != 0` and `precision != 0` gating from the bounds check so the `[0, PRECISION_DECIMAL]` range is always enforced regardless of the `AllowSameTokenName` state:

```java
int precision = assetIssueContract.getPrecision();
if (precision < 0 || precision > ActuatorConstant.PRECISION_DECIMAL) {
  throw new ContractValidateException("precision cannot exceed 6");
}
```

### Proof of Concept
1. On a chain/testnet where `AllowSameTokenName == 0`.
2. Broadcast an `AssetIssueContract` transaction from any funded account with `precision = -5` (or `precision = 18`).
3. `AssetIssueActuator.validate()` skips the bounds check because `dynamicStore.getAllowSameTokenName() != 0` is `false`.
4. `execute()` stores the V1 `AssetIssueCapsule` with the invalid precision into `assetIssueStore` (see [4](#0-3) ), permanently persisting an asset with out-of-spec decimal precision.
