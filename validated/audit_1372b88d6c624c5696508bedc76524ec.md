### Title
Uncaught RuntimeException in `ValidateMultiSign` precompile from malformed calldata propagates through `VM.play` and crashes block/transaction processing - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompiled contract parses ABI-encoded calldata without bounds validation before the `VMConfig.allowTvmOsaka()` hard-fork guard is active. A short/malformed `bytes` payload to this precompile (reachable via a plain `CALL` opcode from any deployed contract, triggerable by any unprivileged transaction that invokes it) causes `DataWord.parseArray` and subsequent array indexing to throw an uncaught `RuntimeException`/`ArrayIndexOutOfBoundsException` that is not contained by any try/catch in `execute()`, unlike its sibling `BatchValidateSign` which wraps everything in `try { doExecute(data) } catch (Throwable t)`.

### Finding Description
`ValidateMultiSign.execute()` [1](#0-0)  only applies the ABI-shape guard `isValidAbiEncoding` when `VMConfig.allowTvmOsaka()` is enabled (a hard-fork flag gated behind committee/network activation). When that flag is off (i.e., in the currently deployed/default network state), calldata goes straight to `DataWord.parseArray(rawData)` and is indexed at `words[0]`, `words[1]`, `words[2]`, `words[3]` with no length checks. The only `try/catch` in the method wraps just the signature-recovery/permission loop [2](#0-1) , not the initial parsing block, so a too-short `data` argument raises an unhandled exception from inside `execute()`.

This is explicitly documented in the codebase's own regression test: "this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode" [3](#0-2) .

The exception then propagates up through `Program.callToPrecompiledAddress`, where `contract.execute(data)` is called directly with no surrounding try/catch [4](#0-3) , and further up into `VM.play`'s opcode-execution loop, which only catches `RuntimeException` generically to spend energy/stop the program and then **rethrows** it [5](#0-4) . This matches the assertion-failure-triggers-process-exit pattern in CVE-2019-6473: invalid/malformed external input reaches an internal invariant check (array bounds) with no graceful validation path, and the resulting fault is not contained at the boundary meant to isolate untrusted input (the precompile execution boundary), unlike every other precompile that either wraps decoding in `try/catch(Throwable)` (`ECRecover`, `BatchValidateSign`, `P256Verify`) or validates length up front (`PairingCheck`, `P256Verify`) [6](#0-5) [7](#0-6) .

### Impact Explanation
Whether this results in node crash versus contained transaction failure depends on exception handling further up the call chain (`VMActuator.execute`, `TransactionTrace`, `Manager.processTransaction`/block application) which I could not fully trace to a terminal catch-all in the time available. If any layer between `VM.play` and the block-application loop in `Manager` lacks a catch for the specific runtime exception type thrown by array-index failures, this becomes a full node crash triggerable by a single crafted transaction calling `ValidateMultiSign` with truncated `bytes[]` calldata — a Medium/High severity DoS matching the CVE-2019-6473 class (unvalidated input → uncaught fault → process termination). At minimum, it is a clear code-quality/security regression relative to `BatchValidateSign`'s hardened equivalent, and the project's own TIP-854 test comments treat this as a known, still-unfixed "documented pre-activation failure mode" for `ValidateMultiSign`.

### Likelihood Explanation
High for reachability: any account can deploy a trivial contract that does a low-level `CALL` to the `ValidateMultiSign` precompile address with a truncated `bytes` payload (e.g., data shorter than 5 ABI header words), and broadcast that as an ordinary contract-call transaction. No special privileges, staking, or witness/SR status are required — only enough energy to pay for the call.

### Recommendation
Apply `isValidAbiEncoding` (or an equivalent length check) unconditionally in `ValidateMultiSign.execute()`, not only under the `VMConfig.allowTvmOsaka()` flag, and/or move the initial `DataWord.parseArray`/word-extraction block inside a `try/catch(Throwable)` that returns `Pair.of(true, DATA_FALSE)` on failure, mirroring `BatchValidateSign.execute()`'s wrapper. Additionally, verify that `VMActuator`, `TransactionTrace`, and `Manager`'s block-application path have a top-level catch for arbitrary `RuntimeException`/`Error` from TVM execution so that even latent bugs of this class cannot terminate the node process.

### Proof of Concept
1. Deploy a minimal contract whose fallback/function performs a low-level `call` to the `ValidateMultiSign` precompile address (`0x0000...0101` or equivalent per `PrecompiledContracts.getContractForAddress`), passing calldata shorter than `(5 + 5) * 32` bytes (fewer than the 5-word ABI header), e.g., 32 bytes of zero.
2. Ensure `allowTvmOsaka` is not yet activated on the target network (default/current state).
3. Broadcast a transaction invoking this contract function.
4. `ValidateMultiSign.execute()` calls `DataWord.parseArray(rawData)` and indexes `words[1]`/`words[2]`/`words[3]` beyond array bounds, throwing an uncaught `ArrayIndexOutOfBoundsException`, reproduced directly by `ValidateMultiSignContractTest.testTip854PreActivationNoOp` [8](#0-7) .
5. Observe whether the exception is caught gracefully by the transaction-processing pipeline or propagates to crash the block-application thread — this last step requires further tracing through `VMActuator.execute`/`TransactionTrace`/`Manager` which could not be completed within available tool calls.
