Confirmed: `ACC_SERVICER_FEE_PAYABLE`/`ACC_SERVICER_FEE_PAID` and `ACC_SERVICER_MISC_FEE_PAYABLE`/`ACC_SERVICER_MISC_FEE_PAID` balances are keyed only by `loanId`, not by servicer address [1](#0-0) , and `servicerWithdraw` always pays out the *current* `servicers[loanId]` regardless of who accrued the fee [2](#0-1) . `updateServicer` swaps `servicers[loanId]` with no check that outstanding servicer-payable balances are zero/withdrawn first [3](#0-2) .

### Title
Reassigning a loan's servicer without settling outstanding servicer fees diverts already-earned fees to the new servicer - (File: `contracts/Loans.sol`)

### Summary
This is the same bug class as Sherlock M-2: a role-update function (`CouncilMember.updateStream/updateTarget/updateID` there, `Loans.updateServicer` here) repoints who a claimable, already-accrued balance will be paid to, without first checking/forcing the withdrawal of the balance owed to the current recipient. In Tare, the servicer's earned-but-unwithdrawn fees are not tied to the servicer's address — they live in per-loan ledger accounts keyed only by `loanId`. Reassigning the servicer silently redirects the outgoing servicer's entire unclaimed fee balance to the incoming servicer.

### Finding Description
`servicerWithdraw` computes the amount owed using `_getNetPayable(loanId, ACC_SERVICER_FEE_PAYABLE, ACC_SERVICER_FEE_PAID)` and `_getNetPayable(loanId, ACC_SERVICER_MISC_FEE_PAYABLE, ACC_SERVICER_MISC_FEE_PAID)`, then transfers the sum to `servicerAddress`, which is derived from `servicers[loanId]` at call time [2](#0-1) . These payable balances accumulate over time via `applyWaterfall` allocations and are only reduced when `servicerWithdraw` (or `returnFunds`) is actually called — there is no automatic settlement.

`updateServicer` is guardian-gated and only checks that the loan is non-terminal and the new servicer is a registered/approved servicer; it does not check whether `_getNetPayable(loanId, ACC_SERVICER_FEE_PAYABLE, ACC_SERVICER_FEE_PAID)` (or the misc-fee equivalent) is zero before overwriting `servicers[loanId]` [3](#0-2) . Because the payable/paid ledger accounts are per-`loanId` global state, not per-address state, whatever fee balance the old servicer had accrued but not withdrawn becomes claimable by whichever address is `servicers[loanId]` at the time `servicerWithdraw` is finally called — i.e., the new servicer.

This mirrors the CouncilMember root cause precisely: an entity update (stream target/receiver in Sablier's case, `servicers[loanId]` here) happens on top of an unsettled claimable balance tracked in "current-holder-agnostic" storage, so the balance flows to whoever holds the role/position after the update rather than whoever earned it before.

### Impact Explanation
Whenever `updateServicer` is called while a loan carries an outstanding, unwithdrawn servicer fee or misc-fee balance, the previously-registered servicer permanently loses that entitlement — it is paid out instead to the new servicer on their next `servicerWithdraw`. This is a real, unrecoverable misdirection of value between two legitimate protocol participants (not just a privileged-role self-harm scenario): the outgoing servicer had a genuine, ledger-recorded claim on protocol cash that vanishes from their perspective and appears in the incoming servicer's payout. Given `SECURITY.md` already documents broad servicer discretion as a trust assumption but nowhere documents this specific loss-on-handoff behavior, and it is guardian-triggered rather than servicer-triggered, this sits outside the accepted "servicer is trusted" carve-out — the guardian performing a legitimate, intended servicer rotation causes the loss, not a malicious servicer.

### Likelihood Explanation
Servicer rotations are an expected operational event (servicer termination, migration, business changes) documented in the spec (`updateServicer`, guardian-only) [4](#0-3) . There is no requirement or tooling forcing `servicerWithdraw` to be called immediately before `updateServicer`, and nothing prevents `applyWaterfall`/fee accrual from continuing to build up payable balances between the last withdrawal and the rotation. Any real-world servicer transition where the outgoing servicer has not withdrawn very recently will trigger this loss.

### Recommendation
Before mutating `servicers[loanId]` in `updateServicer`, require that outstanding servicer-payable balances are settled: either (a) revert if `_getNetPayable(loanId, ACC_SERVICER_FEE_PAYABLE, ACC_SERVICER_FEE_PAID) > 0 || _getNetPayable(loanId, ACC_SERVICER_MISC_FEE_PAYABLE, ACC_SERVICER_MISC_FEE_PAID) > 0`, or (b) automatically flush the outstanding balance to the *old* servicer (via the same `_withdrawToAccount` primitive used by `servicerWithdraw`) as part of the `updateServicer` transaction before writing the new address.

### Proof of Concept
1. Loan is `Active`; `servicer = S1`. Over several `applyWaterfall(servicingFees=X, …)` calls, `ACC_SERVICER_FEE_PAYABLE` accrues `-100` (i.e., 100 owed) while `S1` never calls `servicerWithdraw`.
2. Guardian calls `updateServicer(loanId, S2)` — this succeeds unconditionally since `S2` is a registered servicer and the loan is non-terminal [3](#0-2) ; `servicers[loanId]` is now `S2`.
3. `S2` calls `servicerWithdraw([loanId], …)`. `_getNetPayable` still returns 100 (balance is per-loan, unaffected by the address change), so 100 currency is transferred to `S2` [5](#0-4) .
4. `S1` never receives the 100 it earned and has no on-chain path to reclaim it — the ledger entry that would have paid `S1` no longer references `S1` in any way.

  function updateServicer(
    uint64 loanId,
    address servicer
  ) external whenNotPaused onlyRole(GUARDIAN_ROLE) notTerminal(loanId) {
    require(servicer != address(0), ZeroAddress());
    require(isRegisteredForRole(address(this), Roles.Servicer, servicer), UnregisteredAddress(servicer));

    servicers[loanId] = servicer;
    data[loanId].updatedAt = uint48(block.timestamp);

    emit LoanServicerUpdated(loanId, servicer);
  }

  function servicerWithdraw(
    uint64[] calldata loanIds,
    uint48 timestamp,
    bytes32 ref
  ) external whenNotPaused nonReentrant returns (ServicerWithdrawalResult[] memory results) {
    uint256 numLoans = loanIds.length;
    results = new ServicerWithdrawalResult[](numLoans);

    int128 totalTransfer = 0;
    address servicerAddress;
    uint64 currentLoanCount = loanCount;

    for (uint256 i = 0; i < numLoans; ++i) {
      uint64 loanId = loanIds[i];

      require(loanId != 0 && loanId <= currentLoanCount, DoesNotExist());

      servicerAddress = _requireBatchCaller(servicers[loanId], i, servicerAddress);

      int128 servicingFee = _getNetPayable(loanId, ACC_SERVICER_FEE_PAYABLE, ACC_SERVICER_FEE_PAID);
      int128 miscFee = _getNetPayable(loanId, ACC_SERVICER_MISC_FEE_PAYABLE, ACC_SERVICER_MISC_FEE_PAID);

      totalTransfer += _withdrawToAccount(
        loanId,
        ACC_SERVICER_FEE_PAID,
        servicingFee,
        timestamp,
        ENTRY_SERVICER_FEE_WITHDRAWAL,
        ref
      );
      totalTransfer += _withdrawToAccount(
        loanId,
        ACC_SERVICER_MISC_FEE_PAID,
        miscFee,
        timestamp,
        ENTRY_MISC_FEE_WITHDRAWAL,
        ref
      );

      results[i] = ServicerWithdrawalResult({loanId: loanId, miscFee: miscFee, servicingFee: servicingFee});

      data[loanId].updatedAt = timestamp;
    }

    currency.safeTransfer(servicerAddress, uint256(int256(totalTransfer)));

### Update Servicer

The `updateServicer` function allows updating the servicer address for a loan.

```solidity
function updateServicer(uint64 loanId, address servicer) external onlyRole(GUARDIAN_ROLE)
```

**Validation:**

- Loan must exist and not be Cancelled or Closed
- Servicer address must be non-zero
- Servicer must be an approved servicer (registered for `Roles.Servicer` in the protocol address book)
- Caller must be a guardian

**Events:**

- Emits `LoanServicerUpdated(loanId, servicer)`
