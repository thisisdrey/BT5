### Title
Dust deposit-token transfers permanently fill a victim's per-account token list, blocking deposits, transfers and liquidations involving new collateral types - (File: contracts/Pool.sol)

### Summary
`Pool` tracks every deposit/debt token an account holds in `depositTokensOfAccount`/`debtTokensOfAccount` and enforces a hard cap of `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens`. Because `DepositToken._transfer` / `_mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero, any EOA can push arbitrary deposit tokens *into* a victim's list by transferring dust amounts. Once the combined list length reaches 30, every code path that would add a new token for that account reverts.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` [1](#0-0) 
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `recipient` balance goes 0→nonzero, and `transfer`/`transferFrom` are permissionless [2](#0-1) 
- `DepositToken._mint` does the same on deposits (`deposit(amount_, onBehalfOf_)` lets anyone mint to any `onBehalfOf_`), so `addToDepositTokensOfAccount` is reachable purely from attacker-chosen ERC-20 transfers [3](#0-2) 
- Attack: for each whitelisted `DepositToken` in the pool, the attacker deposits a dust amount of underlying (or obtains msdTOKEN), then `transfer(victim, 1 wei)`. Each transfer appends one entry to `depositTokensOfAccount[victim]`. Repeating with enough distinct deposit/debt tokens to reach 30 makes `addToDepositTokensOfAccount` revert for any token the victim does not already hold.

Consequences once the victim's list is saturated:

1. `DepositToken.deposit(amount, victim)` reverts for any collateral the victim doesn't already hold — the victim cannot add a *new* collateral type to rescue or grow a position.
2. `transfer`/`transferFrom`/`seize` **to** the victim of a not-yet-held msdTOKEN revert.
3. `Pool.liquidate` calls `depositToken_.seize(account_, liquidator/feeCollector, ...)`; if the protocol `feeCollector` (or liquidator) list is saturated and its balance of that msdTOKEN is zero, the fee-seize `_transfer` reverts, making `liquidate` revert — blocking liquidation of unhealthy positions until the collector clears an entry.
4. `DebtToken` mint paths (`issue`, `mint` via SmartFarmingManager) call `addToDebtTokensOfAccount` under the same shared cap, so a victim with a full list cannot take on a *new* debt token either [4](#0-3) 

### Impact Explanation
Analogous to CVE-2020-14861 (unauthenticated-reachable hang/DoS): an unprivileged attacker spends only dust collateral to grief a target's account state. The victim's ability to deposit new collateral, receive msdTOKENs, or open new debt positions is frozen until they manually transfer/burn the dust entries — a temporary freezing of funds and, for the `feeCollector` variant, a protocol-wide `liquidate`/`deposit` DoS for affected tokens, which can let unhealthy positions accrue bad debt while liquidations revert.

### Likelihood Explanation
Reachable entirely from public entry points (`DepositToken.deposit` with `onBehalfOf_`, `transfer`). Cost scales with the number of distinct pool deposit tokens and dust gas only. Mitigating factor: the victim (or fee collector) can recover by transferring/withdrawing dust entries, and the attack requires the pool to list enough deposit tokens to approach the 30-entry cap against a target holding few tokens. Hence Medium, matching the source advisory's severity.

### Recommendation
- In `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, return a bool instead of reverting, and have `_transfer`/`_mint`/`seize` skip the accounting-list insert (or the rewards hook) when at cap; or
- Make the cap apply only to debt tokens plus collateral actually counted toward `debtPositionOf`, or allow victims to permissionlessly evict entries; or
- Charge a minimum first-transfer/deposit amount so dust-filling is economically impractical.

### Proof of Concept
Reproducible on a Hardhat fork of a live deployment (e.g. `deployments/mainnet`):

```ts
// 1. Enumerate pool deposit tokens
const tokens = await pool.getDepositTokens(); // IDepositToken[]

// 2. For each token the victim doesn't hold, mint dust to attacker & transfer to victim
for (const t of tokens.slice(0, 30)) {
  const dt = await ethers.getContractAt('DepositToken', t);
  if ((await dt.balanceOf(victim.address)) == 0) {
    await underlying(t).approve(dt.address, DUST);
    await dt.deposit(DUST, attacker.address);          // mint msdTOKEN
    await dt.transfer(victim.address, 1);              // adds entry to victim's list
  }
}

// 3. Victim's list is now at MAX_TOKENS_PER_USER
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// 4. Any deposit of a not-yet-held collateral on behalf of victim reverts
await expect(newDepositToken.deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 5. Same for seize-to-feeCollector during liquidate when collector list is saturated
await expect(pool.liquidate(synth, unhealthyAcct, repayAmt, dt))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Key assertions: `addToDepositTokensOfAccount` reverts inside `_mint`/`_transfer` once combined list length hits 30, so `deposit(onBehalfOf_=victim)` and `liquidate` (seize to `feeCollector`) fail.
