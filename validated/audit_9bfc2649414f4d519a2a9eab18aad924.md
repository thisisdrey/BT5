### Title
Malicious peer can permanently poison Atlas attachment resolution, causing `/v2/attachments/inv` to report a genuinely committed `content_hash` as missing - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any successfully-decoded `GetAttachmentResponse` and inserts the delivered `Attachment` into the resolved set without verifying that the delivered content's hash matches the `content_hash` (`H`) that was actually requested. A malicious peer that is a valid inventory source for `H` can serve arbitrary bytes in response to the download request; those bytes get stored/counted as a "successful" resolution under their own (different) hash, while the real content for `H` is never written, leaving the local `attachment_instances` row for `H` permanently flagged `is_available` in its default "missing" state and served that way by `RPCGetAttachmentsInvRequestHandler`.

### Finding Description
The download pipeline in `stackslib/src/net/atlas/download.rs` builds `AttachmentRequest { content_hash, sources, ... }` from peers whose inventories claim to have `content_hash`. When a response comes back, `extend_with_attachments` (download.rs:530-558) does:

```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

There is no check comparing `response.attachment.hash()` against the `content_hash` that was actually requested (`request.content_hash`, from the same loop that built the queue at download.rs:460-478). This is the broken equality: the code assumes "response decoded successfully" implies "response corresponds to the requested hash `H`", but a remote, unprivileged peer that legitimately advertised `H` in its inventory can instead return an arbitrary, different attachment payload. `decode_atlas_get_attachment` only decodes the wire structure; it performs no cross-check against the specific hash that was requested.

Because the accepted-but-mismatched `Attachment` is keyed/stored by its own real hash (not `H`), the resolution logic never records success for `H`. The corresponding row for `H` in `attachment_instances` never gets its `is_available` bit cleared to the "resolved" state. `AtlasDB::get_attachments_missing_at_page_index` (db.rs:485-509) defaults every slot to `true` (missing) and only flips it when it finds a matching row with `is_available == 0`:

```rust
let mut bool_vector = vec![true; AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE as usize];
for (attachment_index, is_available) in rows.into_iter() {
    let index = attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
    let slot = bool_vector.get_mut(index as usize).ok_or(db_error::NotFoundError)?;
    *slot = is_available == 0;
}
``` [2](#0-1) 

`get_attachments_available_at_page_index` inverts this into the wire bit (`0` if missing, `1` if available) and `RPCGetAttachmentsInvRequestHandler::try_handle_request` serves this bitvector directly to any remote caller of `GET /v2/attachments/inv` without any additional cross-check against chain state:

```rust
match network.get_atlasdb().get_attachments_available_at_page_index(*page_index, &index_block_hash) {
    Ok(inventory) => Ok(AttachmentPage { inventory, index: *page_index }),
    ...
``` [3](#0-2) 

As long as the attacker's peer continues to be selected as a source for `H` (or is the only source), the node keeps re-requesting `H`, keeps receiving mismatched content, and keeps failing to ever populate the real `H`, so the "missing" bit for `H`'s slot is permanently served, even though the name operation committing to `H` is present on the canonical chain (the `attachment_instances` row itself, created at index time, proves `H` is canonical/committed - only its `is_available` resolution is corrupted).

### Impact Explanation
This breaks the invariant that the served attachment inventory bit reflects on-chain committed availability, i.e., it lets an unprivileged remote peer force other nodes to durably (not just transiently) report a real, chain-committed BNS/Atlas attachment as unavailable network-wide. This is an attachment/BNS mismatch matching the "High" impact category (serving non-canonical/incorrect state as canonical via false inventory). It does not crash the node or corrupt consensus state, but it degrades/denies attachment availability for specific, attacker-chosen `content_hash` values across any peer that queries the poisoned node's inventory, and can propagate as other peers treat "no one has it" as ground truth.

### Likelihood Explanation
- The attacker only needs to run a normal peer that advertises `H` in its Atlas inventory (any unprivileged node) and then answer attachment-content requests with mismatched bytes; no secret, no privileged role, no StackerDB slot ownership is needed.
- Reachability: the P2P/HTTP attachment-download path and the public `GET /v2/attachments/inv` RPC endpoint are both remotely reachable with no auth.
- Repeatability: the attacker can repeat this for every `content_hash` it wants to suppress and can keep doing so indefinitely, as the requesting node will keep retrying against the same malicious source if it remains the/an available source in inventory.
- Some non-determinism exists if multiple honest peers also serve the correct content concurrently (a race), but a well-positioned or Sybil'd attacker can dominate the source set for a given `H`, especially for freshly announced attachments.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558), verify `response.attachment.hash() == request.content_hash` before accepting the response as successful; on mismatch, treat it as a failed/faulty response (`report.bump_failed_requests()`, and optionally penalize/blacklist the peer) instead of inserting it into `self.attachments`. This restores the equality that a "successful" resolution for `H` can only occur when the delivered bytes actually hash to `H`.

### Proof of Concept
Rust test plan in `stackslib::net::atlas` (extending `download.rs`'s state machine tests) or `stackslib::net::api::getattachmentsinv`:
1. Insert an `AttachmentInstance` for hash `H` (a genuinely committed attachment index/row) into a test `AtlasDB`, un-instantiated.
2. Construct an `AttachmentsBatchStateContext` with a queued `AttachmentRequest { content_hash: H, sources: [malicious_peer], .. }`.
3. Simulate a `BatchedRequestsResult<AttachmentRequest>` where the malicious peer's response decodes successfully via `decode_atlas_get_attachment()` but contains an `Attachment` whose `.hash()` != `H`.
4. Call `extend_with_attachments` and assert: (a) `report.bump_successful_requests()` was called (no failure recorded) — showing the mismatch was silently accepted; (b) the returned context's `self.attachments` does **not** contain an entry resolving `H`.
5. Drive this through to DB persistence (wherever `self.attachments` is committed to `attachment_instances.is_available`), then call `RPCGetAttachmentsInvRequestHandler::try_handle_request` for the page containing `H`'s `attachment_index`, and assert `AttachmentPage.inventory` bit for that slot is `0` (missing) despite the underlying `attachment_instances` row for `H` existing (i.e., `H` is canonically committed).

Note: I could not fully verify the exact code path that writes `self.attachments` back into `AtlasDB`'s `is_available` column (in `stackslib/src/net/atlas/mod.rs`), nor confirm the internals of `decode_atlas_get_attachment`, within the available tool budget — a full reproduction should confirm that no hash check exists at that later write site either.
