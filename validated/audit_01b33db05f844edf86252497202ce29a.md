### Title
StackerDB config refresh fails open to a maximally-permissive `noop()` cap on transient contract-read failure - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`StackerDBConfig::noop()` — used whenever a StackerDB's on-chain config cannot be evaluated — has no meaningful caps at all (`chunk_size = STACKERDB_MAX_CHUNK_SIZE`, `max_writes = u32::MAX`, `write_freq = 0`). `create_or_reconfigure_stackerdbs` falls back to this config on *any* contract-read failure, and the fallback is silently retained in `PeerNetwork::stacker_db_configs` (via `refresh_stacker_db_configs`) without wiping/reconfiguring the underlying slot table, because the "should reconfigure" check is gated on `!new_config.signers.is_empty()`. This is the direct analog of the PoolTogether liquidity-cap finding: a value meant to bound a participant's "spend" against a fixed, contract-defined limit can silently balloon to an unbounded value, and downstream code (`try_replace_chunk`/`validate_received_chunk`) treats the *stale, unbounded* cap as authoritative for signers whose slot ownership persists across the failure.

### Finding Description
`StackerDBConfig::from_smart_contract` is expected to return the contract-defined bounds (`chunk-size`, `max-writes`, `write-freq`) that gate how much/how often a legitimate slot owner may write. When this read-only Clarity evaluation fails for any reason (e.g., contract briefly unparsable during a reorg, a transient DB/read error, a boot-code path not yet available), `create_or_reconfigure_stackerdbs` substitutes `StackerDBConfig::noop()`: [1](#0-0) 

`noop()` intentionally has no real caps: [2](#0-1) 

The code that decides whether to actually reconfigure (and thus wipe/reset) the on-disk slot table only fires when the new config differs from the old one *and* has non-empty signers, or when the signer count doesn't match the slot table: [3](#0-2) 

Because `noop().signers` is empty, the first branch (`new_config != stackerdb_config && !new_config.signers.is_empty()`) evaluates to `false` on the failing refresh, so `reconfigure_stackerdb` (which would drop the slot table's chunks) is **not** called. The on-disk `chunks` table — including the existing, real `(signer, slot_id)` bindings and any already-stored chunk data — is left completely intact. However, the returned `new_stackerdb_configs` map (containing the loose `noop()` config) is what gets stored into `PeerNetwork::stacker_db_configs`: [4](#0-3) 

That in-memory map is exactly what is used to open write transactions for the HTTP write path (`POST /v2/stackerdb/:principal/:contract/chunks`), which calls `network.stackerdbs_tx_begin(&contract_identifier)` and then `tx.try_replace_chunk(...)`. `try_replace_chunk`'s size/limits check is driven by `self.config.chunk_size` / `self.config.max_writes` — i.e. the config the transaction was opened with: [5](#0-4) 

Since the actual slot-to-signer bindings persist unchanged in the `chunks` table, any legitimate, already-registered slot signer (who never changed) can now write chunks up to `STACKERDB_MAX_CHUNK_SIZE` bytes at essentially unlimited version numbers (`max_writes = u32::MAX`) and with no write-frequency throttling (`write_freq = 0`), completely bypassing the smart contract's intended per-slot write budget/size/frequency caps — the exact equality the report calls out (the enforced cap silently diverges from the contract-committed cap while the underlying authorization state is unchanged). This state persists across refresh cycles for as long as the contract read keeps failing (or, on a subsequent refresh where `new_config == stackerdb_config` both being `noop()`, the second branch can trigger and wipe the table instead — a related availability hazard, but the cap-widening window itself requires no additional trigger beyond one failed contract read).

### Impact Explanation
This is a High-severity issue under the "serving non-canonical state as canonical" category: the in-memory `StackerDBConfig` used to gate writes stops reflecting the actual, contract-committed cap and instead serves the maximally permissive default while the real (unwiped) slot bindings remain valid. A legitimate signer can exploit this window to push oversized/high-frequency chunks that are then broadcast/gossiped network-wide via `StackerDBPushChunk` to all replicating peers (`node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))` in `poststackerdbchunk.rs`), amplifying storage/bandwidth consumption across the network beyond what the StackerDB contract's design intended, and undermining any protocol invariant (e.g. `.miners` / `.signers` StackerDBs) that depends on `max-writes`/`chunk-size` being enforced as configured on-chain.

### Likelihood Explanation
The failure path is reached by `StackerDBConfig::from_smart_contract` returning any `Err` — this can happen from ordinary conditions (contract not yet loaded at a given tip, `NoSuchStackerDB`, or any parsing/evaluation error), not just attacker-controlled ones, so it does not strictly require privileged access, only that a node's periodic config refresh (`refresh_stacker_db_configs`) observes a transient failure while it is peering with an already-registered signer that intends to abuse the widened bounds. Reproducibility only needs one failed evaluation followed by a write from an existing signer.

### Recommendation
- Do not let a config-read failure silently loosen enforcement: on `from_smart_contract` failure, retain the *previous* (last-known-good) `StackerDBConfig` instead of falling back to `noop()`, or fail closed (refuse writes) rather than fail open.
- Decouple the "should we reconfigure the slot table" decision from the "should we install this config for enforcement" decision — currently both hinge on the same buggy `!new_config.signers.is_empty()` gate, which was designed to avoid accidentally wiping slots but has the side effect of installing an unbounded cap.
- Consider bounding `noop()`'s caps to the tightest reasonable defaults (e.g. `max_writes = 0`, `chunk_size = 0`) rather than the loosest, so that failure-to-load never expands write capability.

### Proof of Concept
1. Register a StackerDB contract and let a node create a replica for it with real, restrictive `chunk-size`/`max-writes`/`write-freq` values via `create_or_reconfigure_stackerdbs`.
2. Force one refresh cycle where `StackerDBConfig::from_smart_contract` returns an `Err` (e.g. simulate `NoSuchStackerDB` or a transient chainstate read error at the tip used for evaluation) — this is the same code path exercised in `create_or_reconfigure_stackerdbs`:
   `stackslib/src/net/stackerdb/mod.rs:376-405`. Observe that `reconfigure_stackerdb` is *not* invoked (per the branch at `mod.rs:414-417`), so the `chunks` table's signer bindings survive unchanged, while `PeerNetwork::stacker_db_configs` for that contract becomes `StackerDBConfig::noop()`.
3. As an already-registered signer for a slot in that StackerDB, `POST /v2/stackerdb/:principal/:contract/chunks` with a chunk near `STACKERDB_MAX_CHUNK_SIZE` bytes and/or a slot version far beyond the contract's originally intended `max-writes`. Because `stackerdbs_tx_begin` opens the transaction with the now-`noop()` config, `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:398-438`) accepts it, bypassing the contract's real caps, and the node relays the (oversized/over-frequency) chunk to peers via `StackerDBPushChunk`.

    /// Config that does nothing
    pub fn noop() -> StackerDBConfig {
        StackerDBConfig {
            // Cap the chunk size at the protocol-wide maximum rather than u64::MAX.
            // `noop()` is used as a fallback whenever a replica's real config can't be
            // loaded (see `create_or_reconfigure_stackerdbs`), and it can transiently
            // overwrite a good in-memory config on a failed refresh. Since the DB slots

            // slots while `noop()` is active, so its chunk-size limit must never be
            // looser than `STACKERDB_MAX_CHUNK_SIZE`.

            write_freq: 0,
            max_writes: u32::MAX,
            hint_replicas: vec![],
            max_neighbors: 8,
            signers: vec![],
        }
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
