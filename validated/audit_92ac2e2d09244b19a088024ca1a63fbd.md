### Title
`add_gas_key` does not force `GasKeyInfo.balance` to zero, allowing attacker-supplied non-zero balance to be "burned" via immediate `DeleteKey` without any real deposit - ([File: runtime/runtime/src/access_keys.rs])

### Finding Description
`action_add_key` dispatches to `add_gas_key` whenever `add_key.access_key.gas_key_info()` is `Some` [1](#0-0) . Inside `add_gas_key`, the code explicitly zeroes the (unused) `nonce` field of the access key ("For gas keys, nonce stored on access key is not used and should always be zero") but performs **no equivalent normalization or validation on `gas_key_info.balance`** — it is taken verbatim from the attacker-supplied `AddKeyAction.access_key` and stored via `set_access_key` [2](#0-1) . Nothing in this function checks that `gas_key_info.balance == 0`, deducts `gas_key_info.balance` from `account.amount()`, or otherwise ties the stored balance to any real transfer.

Later, `delete_gas_key` trusts the persisted `gas_key_info.balance` as the amount to burn, only bounding it by `GasKeyInfo::MAX_BALANCE_TO_BURN`, then unconditionally adds it to `result.tokens_burnt`: `result.tokens_burnt = result.tokens_burnt.checked_add(gas_key_info.balance)...` [3](#0-2) . The only legitimate way `gas_key_info.balance` is supposed to become non-zero is via `action_transfer_to_gas_key`, which increments the stored balance and is the action that is meant to correspond to an actual transfer of value into the gas key [4](#0-3) . If `AddKey` itself can set a non-zero balance, an attacker can skip `TransferToGasKey` entirely: submit a single `ActionReceipt` with `actions = [AddKey(access_key = GasKeyFullAccess{ balance: B, num_nonces }), DeleteKey(same public_key)]`. `add_gas_key` stores `balance = B` with no funding, and the sibling `DeleteKey` in the same receipt calls `delete_gas_key`, which credits `tokens_burnt += B` even though no account balance was ever decremented anywhere in the transaction.

I was unable to fully confirm within the available context whether `runtime/runtime/src/action_validation.rs` (which references `GasKeyFullAccess`/`GasKeyInfo` in three places) contains a pre-execution check that rejects an `AddKeyAction` whose `GasKeyInfo.balance` is non-zero. If such a check exists there, it would fully close this issue before `action_add_key` is even reached; I could not retrieve the file's contents to verify this in the time available. The affected core logic (`add_gas_key`/`delete_gas_key`) in `access_keys.rs`, however, contains no such safeguard itself, which is the concrete code-level gap this report identifies.

### Impact Explanation
If reachable (i.e., if `action_validation.rs` does not reject non-zero-balance `GasKeyInfo` on `AddKey`), an unprivileged account could cause `tokens_burnt` to be incremented for value that was never deducted from any account. NEAR's runtime enforces a total-balance-conservation invariant across each chunk apply (burnt + final account balances + refunds must equal initial balances + minted); manufacturing burn out of nothing would either (a) corrupt aggregate burnt-supply/total-supply accounting if the conservation check does not catch this particular code path, or (b) trip the balance-conservation check and cause a deterministic panic/`BalanceMismatchError` during chunk application, which is a shard-halting condition since every validator applying the same receipt would hit the same failure. Either outcome is in-scope: token-supply accounting corruption or a shard-halting panic.

### Likelihood Explanation
Preconditions are minimal: an attacker only needs enough balance to cover the storage stake for one `AddKey` action (no `TransferToGasKey` deposit needed) and can craft the two-action receipt entirely with a standard signed transaction. The exploit is fully client-side (deposit + gas + action list), requiring no validator/node access. Feasibility hinges entirely on whether `action_validation.rs` already blocks non-zero `GasKeyInfo.balance` on `AddKey` — this must be verified directly in that file before treating the finding as confirmed exploitable.

### Recommendation
In `add_gas_key` (runtime/runtime/src/access_keys.rs), explicitly zero `gas_key_info.balance` (mirroring the existing `access_key.nonce = 0` treatment) before storing the access key, or reject the action if the attacker-supplied `GasKeyInfo.balance` is non-zero. Additionally, confirm and, if absent, add an explicit check in `action_validation.rs` that any `AddKeyAction` carrying `AccessKeyPermission::GasKeyFullAccess` must have `balance == 0`, so this invariant is enforced defense-in-depth at both validation and execution time.

### Proof of Concept
1. Unit test in `runtime/runtime/src/access_keys.rs` (alongside `test_add_gas_key`): construct an `AddKeyAction` with `access_key = AccessKey { permission: AccessKeyPermission::GasKeyFullAccess(GasKeyInfo { num_nonces: N, balance: Balance::from_yoctonear(1_000_000) }), .. }` directly (bypassing the `AccessKey::gas_key_full_access` helper which zeroes balance), call `action_add_key`, and assert whether the resulting stored `GasKeyInfo.balance` is forced to `0` or retains the attacker-supplied value.
2. If it retains the non-zero value, extend the test to immediately call `action_delete_key` with the same public key in the same mock `ActionResult`, and assert `result.tokens_burnt` — expected correct behavior is `tokens_burnt == 0` (nothing was ever deposited); a failing assertion (`tokens_burnt == 1_000_000`) confirms the bug.
3. Cross-check with an integration/test-loop test in `test-loop-tests/src/tests/gas_keys.rs` submitting a single transaction with `actions = [AddKey(gas_key, balance=B), DeleteKey(gas_key)]` and asserting post-apply that total supply / `tokens_burnt` reporting matches "no funds moved," and that chunk application does not panic on the balance-conservation check (or does panic, if that is the actual failure mode).

fn add_gas_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    // For gas keys, nonce stored on access key is not used and should always be zero
    let mut access_key = access_key.clone();
    access_key.nonce = 0;
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    // Set up nonces for gas key
    let num_nonces = gas_key_info.num_nonces;
    let nonce = initial_nonce_value(block_height);
    for i in 0..num_nonces {
        set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
    }

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(gas_key_storage_cost(fee_config, public_key, &access_key, num_nonces))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
