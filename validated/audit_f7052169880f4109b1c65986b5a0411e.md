### Title
Intra-batch account-lock conflicts are not detected, allowing simultaneous read and write locks on the same account within a single `try_lock_transaction_batch` call - (File: `accounts-db/src/account_locks.rs`)

### Summary
`AccountLocks::try_lock_transaction_batch` splits validation into two separate passes: a check pass that evaluates every transaction in the batch against the *pre-batch* lock state, and an apply pass that unconditionally grants locks to every transaction that passed the check. Because the check pass never sees the locks that sibling transactions in the same batch are about to acquire, a batch containing several read-locking transactions on account `K` followed by a write-locking transaction on `K` will have all of them pass validation and then all of them get their locks applied, producing simultaneous readonly and write locks on `K`.

### Finding Description
`try_lock_transaction_batch` at [1](#0-0)  works in two independent loops:

1. The first loop calls `self.can_lock_accounts(keys.clone())` (an immutable borrow, see [2](#0-1) ) for every transaction in the batch, comparing against the *current* `self.write_locks`/`self.readonly_locks` maps. This loop does not mutate state between transactions, so transaction N's check cannot see the pending lock request of transaction N-1 in the same batch.
2. The second loop then calls `self.lock_accounts(keys)` ( [3](#0-2) ) for every entry that came back `Ok`, unconditionally incrementing `write_locks`/`readonly_locks` counters with no re-check of conflicts.

`can_write_lock`/`can_read_lock` ( [4](#0-3) ) are the sole gatekeepers of the "no writable lock while a readonly/write lock is active" invariant, but they are only ever evaluated against pre-batch state in this function. Consequently, if a batch contains e.g. five readonly-locking transactions on key `K` followed by one write-locking transaction on `K`, all six pass the check phase (none of them conflict with state that existed *before* the batch), and all six get their locks applied in the apply phase — resulting in `is_locked_readonly(K) == true` and `is_locked_write(K) == true` at the same time. This directly violates the invariant documented at [5](#0-4)  ("Lock accounts for all transactions in a batch which don't conflict") and the fundamental purpose of `AccountLocks`.

Reachability: an unstaked client can send an arbitrary transaction batch to a leader's TPU; `banking_stage`'s `Consumer` groups received sanitized transactions into chunks and calls into `Accounts::lock_accounts`/`Bank::lock_accounts`, which ultimately calls `AccountLocks::try_lock_transaction_batch` for the chunk (see call sites in [6](#0-5)  and [7](#0-6) ). Nothing upstream of this function de-duplicates or reorders conflicting keys within a chunk before the locking call — the locking function itself is supposed to be the sole gate that serializes conflicting transactions, and it fails to do so intra-batch.

### Impact Explanation
Account locks are the mechanism that guarantees conflicting transactions inside a processing chunk are not both admitted for concurrent execution (chunks are processed with parallel iteration in later banking-stage/bank commit stages). If a readonly lock and a write lock on the same key are simultaneously "held" per this bug, the runtime's serialization guarantee for that chunk is broken: the writer and readers can be considered concurrently lock-granted even though their execution results are order-dependent. This can produce non-deterministic execution results for the same input transaction batch depending on scheduling, meaning the leader could record a block whose entry results do not correspond to a valid sequential execution order — an "invalid recorded block" / consensus-determinism class issue, matching Agave's critical-severity bounty category for correctness bugs in core validator paths.

### Likelihood Explanation
The precondition is simply constructing a packet/transaction batch (feasible for any unprivileged sender) where multiple sanitized transactions reference the same account key with mixed read/write locking, landing in the same call to `try_lock_transaction_batch` (i.e., same processing chunk under default banking-stage batching). No staked/gossip/config access is required — only ordinary transaction submission with attacker-chosen account key. This makes the flaw deterministically reproducible with a unit test directly against `AccountLocks`, independent of network conditions.

### Recommendation
Merge the check-and-lock phases into a single pass that checks and immediately applies each transaction's locks before moving to the next transaction, so that later transactions in the same batch see the lock state produced by earlier ones (i.e., `for each tx: if can_lock_accounts(tx) { lock_accounts(tx); Ok(()) } else { Err(AccountInUse) }`), preserving the intended two-phase-but-per-transaction sequential semantics that upstream Solana's account-lock design relies on.

#[test]
fn test_intra_batch_read_then_write_conflict_not_detected() {
    let mut locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    // Five readonly-locking transactions on `key`, followed by one
    // writable-locking transaction on the same `key`, all in a single
    // call to try_lock_transaction_batch (simulating one banking-stage chunk).
    let batch: Vec<TransactionResult<std::vec::IntoIter<(&Pubkey, bool)>>> = (0..5)
        .map(|_| Ok(vec![(&key, false)].into_iter()))
        .chain(std::iter::once(Ok(vec![(&key, true)].into_iter())))
        .collect();

    let results = locks.try_lock_transaction_batch(batch);

    // Invariant that SHOULD hold: the write-locking transaction must be
    // rejected with AccountInUse because readonly locks on `key` are
    // already active within this same batch.
    let write_tx_result = results.last().unwrap();
    assert!(
        write_tx_result.is_err(),
        "write tx must not succeed while readonly locks on the same key are held, \
         but got: {:?}",
        write_tx_result
    );

    // Demonstrates the actual (buggy) behavior:
    // both readonly and write locks end up simultaneously active.
    // assert!(locks.is_locked_readonly(&key) && locks.is_locked_write(&key));
}

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_readonly(&self, key: &Pubkey) -> bool {
        self.readonly_locks.get(key).is_some_and(|count| *count > 0)
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }
