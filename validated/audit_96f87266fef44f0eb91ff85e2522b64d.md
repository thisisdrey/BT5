### Title
Implicit Vote Counted Toward Timelock Override Threshold in `validate_multisig_transaction` Allows Timelock Bypass With One Fewer Explicit Approval Than Required — (`File: aptos-move/framework/aptos-framework/sources/multisig_account.move`)

---

### Summary

The `validate_multisig_transaction` prologue function in `multisig_account.move` passes `num_approvals` that includes the executing owner's implicit vote to `can_execute_with_timelock`. The override threshold — a security parameter explicitly required to be strictly greater than `num_signatures_required` — is therefore satisfiable with `override_threshold - 1` explicit approvals. An owner of a timelocked multisig account can bypass the timelock immediately after obtaining only `override_threshold - 1` explicit approvals from other owners, defeating the purpose of the override threshold entirely.

---

### Finding Description

**Root cause — the broken invariant:**

`upsert_timelock_internal` enforces at configuration time that `override_threshold > num_signatures_required`: [1](#0-0) 

The intent is that bypassing the timelock requires a *higher* bar of explicit consent than normal execution. However, `validate_multisig_transaction` (the VM prologue, lines 1348–1358) recomputes `num_approvals` by adding the executing owner's implicit vote, then passes that inflated count directly to `can_execute_with_timelock`: [2](#0-1) 

`can_execute_with_timelock` then checks `num_approvals >= override_threshold`: [3](#0-2) 

Because `num_approvals` already includes the executor's implicit +1, the override threshold is satisfied with only `override_threshold - 1` *explicit* approvals. The same logic is present in the `can_execute` view function used as the first gate: [4](#0-3) 

**The test suite explicitly demonstrates the bypass:** [5](#0-4) 

The test asserts `can_execute(owner_3)` returns `true` (timelock bypassed via implicit vote) while `can_be_executed` returns `false` (timelock not expired, explicit approvals below override threshold). This is the exact bypass path.

**Execution path:**

1. Attacker submits a `MultisigTransaction` as the executing owner.
2. The Rust VM calls `run_multisig_prologue` → `execute_function_bypass_visibility` on `validate_multisig_transaction`: [6](#0-5) 
3. Inside `validate_multisig_transaction`, `num_approvals` is incremented by the implicit vote (line 1350–1352), then passed to `can_execute_with_timelock` (line 1357).
4. If `explicit_approvals + 1 >= override_threshold`, the timelock is bypassed and the transaction executes immediately.

---

### Impact Explanation

The timelock override threshold is the only mechanism that allows early execution before the timelock period expires. Its invariant — that it requires strictly more approvals than the normal threshold — is broken at execution time. For a 3-owner multisig with `num_signatures_required = 2` and `override_threshold = 3` (unanimous override):

- **Expected**: all 3 owners must explicitly approve to bypass the 1-hour timelock.
- **Actual**: only 2 explicit approvals are needed; the executing owner provides the 3rd implicitly.

A malicious owner can execute a transaction that drains the multisig account's funds, changes ownership, or performs any other privileged operation immediately after obtaining only `override_threshold - 1` co-approvals, before the remaining owners have time to review and reject it. This directly enables unauthorized movement of assets held by timelocked multisig accounts on mainnet.

---

### Likelihood Explanation

Any owner of a multisig account that has configured a timelock with an override threshold can trigger this. No privileged keys, governance access, or external dependencies are required — only the ability to submit a normal `MultisigTransaction` as an owner. The `multisig_v2_enhancement_feature_enabled` feature flag must be active (it is the current mainnet path), and the `is_multisig_timelock_enabled` flag must be active for the timelock to exist. Both are production features.

---

### Recommendation

The override threshold check in `can_execute_with_timelock` must be evaluated against **explicit approvals only**, not the implicit-vote-inflated count. The fix is to pass the raw `num_approvals` (before adding the implicit vote) to `can_execute_with_timelock`, and only add the implicit vote for the normal quorum check:

```move
// In validate_multisig_transaction:
let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);

// Timelock override check uses ONLY explicit approvals.
assert!(
    can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
    error::invalid_state(ETIMELOCK_NOT_EXPIRED),
);

// Quorum check adds the implicit vote.
if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
    num_approvals += 1;
};
assert!(num_approvals >= num_signatures_required(multisig_account), ...);
```

The same correction must be applied to `can_execute` (the view function) so that it does not count the implicit vote toward the override threshold, preserving consistency between the view and the prologue.

---

### Proof of Concept

**Setup**: 3-owner multisig (`owner_1`, `owner_2`, `owner_3`), `num_signatures_required = 2`, `override_threshold = 3`, `timelock_period = 3600` seconds.

**Steps** (using the existing test framework in `multisig_account.move`):

```move
// 1. owner_1 creates a transaction (auto-approves → 1 explicit approval).
create_transaction(owner_1, multisig_account, PAYLOAD);

// 2. owner_2 approves → 2 explicit approvals. Timelock not expired.
approve_transaction(owner_2, multisig_account, 1);

// 3. Verify the timelock is NOT bypassed without the implicit vote.
assert!(!can_be_executed(multisig_account, 1));   // 2 < override(3), timelock active → false ✓

// 4. owner_3 has NOT voted. can_execute adds their implicit vote: 2+1=3 >= override(3).
assert!(can_execute(address_of(owner_3), multisig_account, 1));  // TRUE — bypass confirmed

// 5. owner_3 submits a MultisigTransaction. The prologue calls validate_multisig_transaction,
//    which passes num_approvals=3 (including implicit vote) to can_execute_with_timelock.
//    The timelock is bypassed. Transaction executes immediately, 0 seconds elapsed.
successful_transaction_execution_cleanup(address_of(owner_3), multisig_account, vector[]);
// Execution succeeds — timelock bypassed with only 2 explicit approvals instead of 3.
```

This matches the existing test `test_implicit_vote_counts_toward_override` at lines 3008–3027, which already asserts the bypass is reachable. The prologue path in `run_multisig_prologue` (Rust, `transaction_validation.rs` line 462) invokes the same `validate_multisig_transaction` logic, confirming the bypass is reachable from an unprivileged on-chain transaction.
