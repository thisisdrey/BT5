### Title
Global shielded-transaction pending cap is shared across all accounts, allowing one account to block others' shielded transactions from entering the mempool - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.pushTransaction()` enforces a cap on the number of pending shielded (`ShieldedTransferContract`) transactions using a single node-wide `AtomicInteger shieldedTransInPendingCounts`, compared against the global `shieldedTransInPendingMaxCounts` config value (default 10). This cap is not scoped per account/sender — any account's shielded transactions consume from the same shared counter, so a single account can fill the entire window and cause `pushTransaction` to reject shielded transactions submitted by any other, unrelated account until the counter resets (on the next block cycle via `PendingManager`) or the pending transactions are processed. This is analogous to the OpenClaw advisory where a pending-request cap was scoped per-channel (shared) rather than per-account, letting one account starve pairing for another.

### Finding Description
In `Manager.pushTransaction()`, before a shielded transaction is admitted to the pending pool, the code checks:
```java
if (isShieldedTransaction(trx.getInstance())
        && shieldedTransInPendingCounts.get() >= shieldedTransInPendingMaxCounts) {
  return false;
}
``` [1](#0-0) 

`shieldedTransInPendingCounts` is declared as a single shared `AtomicInteger` field on `Manager`, not keyed by sender address: [2](#0-1) 

This counter is reset to zero only once per block cycle, inside the `PendingManager` constructor: [3](#0-2) 

Because the check and the counter are node-wide rather than per-account, any single unprivileged account that can afford the `shieldedTransactionFee` can repeatedly broadcast valid shielded transactions (e.g., transparent-to-shielded transfers funded from its own balance) to saturate the shared window (default max 10) for the remainder of the current pending cycle. Once saturated, `pushTransaction` returns `false` for every other account's shielded transaction, and the broadcast/push path surfaces this as a rejected transaction via `Wallet.broadcastTransaction` → `dbManager.pushTransaction(trx)`. [4](#0-3) 

### Impact Explanation
This is a public, unauthenticated availability issue reachable by any account able to sign and broadcast a `ShieldedTransferContract` transaction (an ordinary broadcastable contract type). An attacker holding shielded/transparent balance can cheaply and repeatedly occupy the shared pending-shielded-transaction slots, denying other users' shielded transactions entry into the mempool. It does not permit unauthorized fund movement, cross-account approval, or data disclosure — it is an availability-only denial-of-service against a specific API path (shielded transaction submission), matching CWE-799 (Improper Control of Interaction Frequency) and the CVSS vector in the reference advisory (`C:N/I:N/A:L`).

### Likelihood Explanation
Likelihood is moderate-to-high: shielded transfers are a standard, publicly reachable transaction type (`ShieldedTransferActuator`), gated only by `supportShieldedTransaction`/`allowShieldedTransactionApi` flags and a fee (`getShieldedTransactionFee`) rather than any per-account throttling. [5](#0-4)  The default cap (`shieldedTransInPendingMaxCounts = 10`) is small, making it inexpensive for a single account to monopolize the window each block cycle. [6](#0-5) 

### Recommendation
Scope the shielded-transaction pending cap per sender/account (e.g., track pending shielded-transaction counts in a map keyed by the transparent/shielded sender identity, or derive an account-level quota from `shieldedTransInPendingMaxCounts`) instead of a single global `AtomicInteger`, so that one account's pending shielded transactions cannot starve the shared window for other accounts.

### Proof of Concept
1. Attacker account A holds enough ZEN/TRX balance to pay `shieldedTransactionFee` repeatedly.
2. A crafts and broadcasts `shieldedTransInPendingMaxCounts` (default 10) valid `ShieldedTransferContract` transactions (e.g., transparent→shielded transfers of trivial amounts) within the same pending cycle.
3. Each call reaches `Manager.pushTransaction()`, which increments the shared `shieldedTransInPendingCounts` up to the configured max: [1](#0-0) 
4. A legitimate, unrelated account B then broadcasts its own shielded transaction; `pushTransaction` returns `false` because `shieldedTransInPendingCounts.get() >= shieldedTransInPendingMaxCounts`, causing `broadcastTransaction` to fail for B until the next `PendingManager` reset cycle.
