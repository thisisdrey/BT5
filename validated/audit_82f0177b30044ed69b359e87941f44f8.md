### Title
Account type upgrade in `createContractImpl` fails to clear votes and frozen-resource state before converting a Normal account to a Contract account, leaving stale vote/witness accounting - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.createContractImpl` (CREATE/CREATE2) can target an address that already holds a `Normal` `AccountCapsule` (e.g. it previously received a transfer, was frozen for, or voted). When such an account is "promoted" to `AccountType.Contract`, only `existingAccount.clearDelegatedResource()` is invoked before `updateAccountType(AccountType.Contract)`; other pieces of account state tied to the "Normal account" role — most importantly outstanding witness votes (`getVotesList()`), and old TronPower/frozen accounting used by `MortgageService`/vote-reward bookkeeping — are not reset. This mirrors the CVE-2021-47194 bug class: switching an object's "type" without invoking the full cleanup path for the old type, leaving stale linked state (here, vote-count entries in the witness vote store and reward bookkeeping) referencing an account that is no longer a normal, votable account.

This is the exact "switch entity type without calling the corresponding stop/cleanup routine" pattern from the kernel bug (which failed to call `cfg80211_stop_ap()` when switching away from `NL80211_IFTYPE_P2P_GO`, leaving the account's `assigned_chanctx_list` in an inconsistent, still-linked state). Here, only resource-delegation data is cleared before the type flip; other subsystems that key off `AccountType.Normal` vs `Contract` and off list-like structures tied to the account (witness vote list, mortgage/reward bookkeeping in `MortgageService`, `VoteWitnessProcessor`/`VoteRewardUtil`) are not reset.

Concretely, an attacker can:
1. Fund an address `A` and cast votes for a witness via `VoteWitnessContract` (`VoteWitnessActuator`/`VoteWitnessProcessor`), populating `AccountCapsule`'s votes list and the witness's vote-count/vote-store bookkeeping used by `MortgageService` for reward computation.
2. From a contract, `CREATE2` a new contract whose predicted address equals `A` (fully attacker-controlled since `CREATE2` addresses are derived from sender/salt/initcode — this is a well known "address squatting" technique already exercised in this codebase's own tests, e.g. `FreezeTest.testCreate2SuicideToAccount`/`testCreate2SuicideToBlackHole`, which validate the analogous freeze/delegate cleanup path but not the vote path).
3. Deploy the contract to that address. `existingAccount` (the account that was voting) is non-null, `contractAlreadyExists` is false (no `ContractCapsule` yet stored there), so the branch at line 848-852 fires: the account's type flips to `Contract`, delegated resources are cleared, but the votes list is untouched.

The account is now type `Contract` while still carrying an old votes entry pointing at a witness. Because `Contract`-type accounts are not supposed to hold votes (votes are only ever added through `VoteWitnessActuator`/`VoteWitnessProcessor` under normal-account semantics), reward accounting (`MortgageService`, `VoteRewardUtil`) and any downstream witness-vote aggregation that trusts the votes list to represent legitimate voter state can now be exercised against a synthetic, contract-controlled account, i.e. a stale/dangling reference analogous to the corrupted `assigned_vifs` linked list in the CVE.

### Impact Explanation
If the vote-reward/mortgage accounting paths (`MortgageService`, `VoteRewardUtil`, `withdrawRewardAndCancelVote` in `Program.java`) do not independently re-validate account type before crediting/withdrawing rewards for entries in the votes list, an attacker can manufacture a contract account that still "votes," letting the contract siphon witness rewards it never legitimately earned as a normal voting account, or causing double counting/inconsistent total-vote bookkeeping used for witness ranking. This can translate into unbacked reward balance or persistent state inconsistency across the account/witness stores that is very difficult to detect and reconcile (a form of "unbacked balance" / permanent state corruption), which is the class of impact called for by this exercise.

### Likelihood Explanation
Requires only: (a) an unprivileged account that votes for a witness, and (b) a `CREATE2` deployment from a contract with an attacker-chosen salt/init-code so the predicted contract address equals the voting account's address — both fully within reach of any transaction broadcaster/contract deployer, no special privilege needed. The codebase already demonstrates (in tests) that developers are aware similar "account gets upgraded to Contract type" scenarios occur for delegated-resource and freeze state (hence the explicit `clearDelegatedResource()` call and comments in `UnDelegateResourceProcessor`), but the votes-list cleanup was evidently not extended to this path, indicating a genuine gap rather than a purely theoretical one.

### Recommendation
In `createContractImpl`, when promoting an existing `Normal` account to `Contract` type, also clear any outstanding witness votes (and settle/forfeit any pending vote rewards through the same code path used by `VoteWitnessActuator`/`MortgageService` withdrawal, similar to how `suicide2` calls `withdrawRewardAndCancelVote` before transferring balance) before calling `updateAccountType`. More generally, centralize "convert account to contract" cleanup in one method that clears delegated resources, votes, and any other Normal-account-only state, rather than clearing state piecemeal at each call site.

### Proof of Concept
1. Deploy a factory contract `F`.
2. From an unprivileged account `V`, cast a `VoteWitnessContract` vote for witness `W` (funds must be frozen/have TronPower per normal vote flow).
3. Compute `salt` such that `CREATE2` from `F` with some init-code produces address == `V`'s address (fully feasible since CREATE2 addresses are deterministic from sender, salt, and init-code hash, and `salt`/init-code are attacker-chosen).
4. Trigger `F` to `CREATE2` a contract at that address; `createContractImpl` finds `existingAccount != null`, `contractAlreadyExists == false`, executes the branch at `Program.java:848-852`, flipping `V` to `AccountType.Contract` while leaving its votes list for `W` intact.
5. Query the account (`GetAccount` via `Wallet`) and observe `AccountType.Contract` with a non-empty `votes` list still referencing `W`; then exercise witness reward withdrawal/vote-reward computation to observe reward accounting proceeding for this contract-turned-voter account. [2](#0-1)
