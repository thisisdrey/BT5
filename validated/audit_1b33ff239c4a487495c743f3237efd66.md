### Title
Relayer reward and message-delivery state are settled unconditionally, ignoring the `success` flag decoded from the Ethereum delivery receipt - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge outbound-queue-v2 pallet decodes an Ethereum `InboundMessageDispatched` event into a `DeliveryReceipt` that explicitly carries a `success: bool` field describing whether the message actually executed successfully on Ethereum. `process_delivery_receipt` never reads or checks this field before paying out the relayer reward and permanently removing the `PendingOrder`, exactly mirroring the ThorChain `TransferOut` bug where an event's payload (`to`) didn't reflect the true outcome of the underlying transfer, yet downstream logic (`GetTxInItem`) trusted it unconditionally.

### Finding Description
`DeliveryReceipt` is decoded from the Ethereum event log: [1](#0-0) 

The event explicitly encodes a `success` boolean indicating whether the dispatched message executed successfully on the Ethereum side. However, `process_delivery_receipt` in the pallet never inspects `receipt.success` before crediting the reward and clearing the pending order: [2](#0-1) 

The `PendingOrder` struct that tracks in-flight messages awaiting delivery does not even have a field to record delivery outcome — only `nonce`, `block_number`, and `fee`: [3](#0-2) 

This is the same class of bug as the ThorChain report: the contract/pallet emits or consumes an event whose payload can legitimately diverge from the real on-chain outcome (`to` bounced back vs. reported `to`; `success=false` dispatch vs. treating it as delivered), and the consuming logic (`GetTxInItem` / `process_delivery_receipt`) advances state and pays out funds purely on the presence of a validly-proven event, without checking the field that actually reflects success or failure.

### Impact Explanation
Once a valid Merkle/receipt proof is submitted for *any* `InboundMessageDispatched` event with the correct nonce and gateway — regardless of whether `success` is `true` or `false` — the relayer is paid the full fee out of `order.fee` via `T::RewardPayment::register_reward`, and the `PendingOrders` entry for that nonce is removed unconditionally. This means:
- Relayers are rewarded for message deliveries that reverted/failed on Ethereum, paying for work that did not actually complete.
- The `PendingOrder` (the only state that tracks "this message still needs to be delivered/retried") is permanently deleted even on failure, so there is no mechanism left in this pallet to detect or retry a failed dispatch — a form of permanent bridge-state loss for that nonce.
- Because `success` isn't part of the emitted `MessageDelivered` event either, on-chain observers cannot distinguish a genuinely successful delivery from a failed one.

### Likelihood Explanation
Any unprivileged relayer that already has an eligible proof for a real `InboundMessageDispatched` log (which is emitted by the Ethereum gateway regardless of whether the dispatched commands succeeded) can call the public extrinsic `submit_delivery_receipt` and have `process_delivery_receipt` unconditionally reward them and drop the pending order. No malicious relayer/validator collusion or privileged access is required — this is a straightforward consequence of the pallet ignoring a field it already decodes.

### Recommendation
Store and check the `success` flag before crediting the reward and removing the order:
- Only call `T::RewardPayment::register_reward` and remove the `PendingOrder` (or emit `MessageDelivered`) when `receipt.success == true`.
- On `success == false`, emit a distinct failure event (e.g. `MessageDeliveryFailed`) and either retain the `PendingOrder` for retry/resubmission or handle it through an explicit failure path, instead of silently treating it as delivered.

### Proof of Concept
1. A message with nonce `N` and fee `F` is committed via `process_message`, creating `PendingOrders[N] = { nonce: N, fee: F, block_number }` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-440`).
2. The relayer submits the message to the Ethereum gateway; execution of the commands reverts, so the gateway emits `InboundMessageDispatched(nonce=N, topic, success=false, reward_address)`.
3. The relayer obtains a valid Merkle/receipt proof for this event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the proof is valid), `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` never reads it: [4](#0-3) 
5. `order.fee` (`F`) is paid to the relayer via `register_reward`, `PendingOrders[N]` is removed, and `Event::MessageDelivered { nonce: N }` is emitted — identical to the successful path, even though the dispatch failed on Ethereum.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.

		) -> DispatchResult

			<T as frame_system::Config>::AccountId: From<[u8; 32]>,

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
