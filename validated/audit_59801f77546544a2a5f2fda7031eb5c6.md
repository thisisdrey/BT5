### Title
Oracle-priced synth swaps can be sandwiched around permissionless pull-oracle updates to mint unbacked synthetic tokens - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.swap()` prices every swap purely via `masterOracle().quote(...)` at the current oracle price, with no slippage check and no price-freshness bound relative to the trade. On deployments where `MasterOracle` reads a pull oracle (Pyth/RedStone), the price update (`updatePriceFeeds`/`updatePrice`) is permissionless — the E2E tests themselves update prices by directly calling the price provider, and `Operator.execute()` lets any EOA atomically batch arbitrary calls. An attacker can therefore execute, in a single transaction: swap synth A→B at stale price p1, push the already-known newer price p2 on-chain, then swap B→A at p2, pocketing the price gap each round trip. This is the same bug class as the report (repeatedly trading against two known oracle prices inside one validity window), reachable without any trusted actor.

### Finding Description
`Pool.swap` burns `syntheticTokenIn_` and mints `syntheticTokenOut_` at the instantaneous oracle quote with no min-amount-out parameter [1](#0-0) . The quote is a pure oracle conversion through `quoteSwapOut` → `masterOracle().quote` [2](#0-1) . Because swaps are mint/burn rather than AMM-driven, there is no price impact — the only cost is `feeProvider.swapFees`, which defaults to 0 per pair [3](#0-2) . `Operator.execute` is a public multicall that preserves `msg.sender` via transient storage, so the whole sequence (swap → `pyth.updatePriceFeeds` → swap back) is atomic and callable by any unprivileged account [4](#0-3) . The E2E tests confirm this exact pattern is intended usage — `updatePrice` is callable directly and via `operator.execute` [5](#0-4) .

### Impact Explanation
Each round trip mints more synth value than it burns, backed by nothing — the protocol mints unbacked synthetic supply. The attacker can accumulate excess msUSD/msETH, then redeem value through `liquidate` (seizing collateral at oracle prices) or bridge out via `ProxyOFT`, draining value from honest depositors and stakers. This is direct protocol insolvency / theft of user funds.

### Likelihood Explanation
Requires `isSwapActive == true` on the target pool and the price move between the stale and new oracle price to exceed the pair's `swapFee` (0 by default; deployed values could not be confirmed from deploy scripts). Pyth publishes signed price updates continuously, so stale-price windows occur every block; any keeper transaction or user `updatePriceFeeds` call can be front-run/back-run in the same block. No privileged role is needed.

### Recommendation
- Add `amountOutMin_`/`deadline` slippage parameters to `swap` (or bound `amountOut` within a confidence interval around both oracle prices).
- Charge a non-zero default swap fee sized above typical oracle deviation.
- Consider requiring the oracle price used for swaps to have been updated in a prior block (no same-block update + swap), or route swaps through a sequencer-style flow analogous to the report's mitigation.

### Proof of Concept
Hardhat fork sketch (mainnet, pull-oracle config as in `test/E2E.mainnet.next.test.ts:903-965`):

```ts
// alice holds msUSD. ETH price update pending: p1 -> p2 (p2 > p1)
const fee = await pyth.getUpdateFee([ETH_FEED_ID]);
const calls = [
  // 1. swap msUSD -> msETH at stale p1 (buys cheap ETH)
  { target: pool.address, value: 0,
    callData: pool.interface.encodeFunctionData('swap', [msUSD.address, msETH.address, amountIn]) },
  // 2. permissionlessly push new price p2
  { target: pyth.address, value: fee,
    callData: pyth.interface.encodeFunctionData('updatePriceFeeds', [updateData]) },
  // 3. swap msETH -> msUSD at p2 (sells expensive ETH)
  { target: pool.address, value: 0,
    callData: pool.interface.encodeFunctionData('swap', [msETH.address, msUSD.address, msEthReceived]) },
];
await operator.connect(attacker).execute(calls, { value: fee });
// attacker ends with more msUSD than started, whenever (p2/p1 - 1) > swapFee + fees
```

Uncertainty: I could not confirm the deployed `isSwapActive` flag or per-pair `swapFee` values for each chain from the deploy scripts within the iteration limit; the attack is profitable only where swaps are enabled and the fee is smaller than the oracle price move.

        ISyntheticToken syntheticTokenOut_,
        uint256 amountIn_

            amountIn_

        if (_swapFee > 0) {
            _fee = _amountOut.wadMul(_swapFee);
            _amountOut -= _fee;
        }
    }

    function swap(
        ISyntheticToken syntheticTokenIn_,
        ISyntheticToken syntheticTokenOut_,
        uint256 amountIn_
    )
        external
        override
        whenNotShutdown
        nonReentrant
        onlyIfSyntheticTokenExists(syntheticTokenIn_)
        onlyIfSyntheticTokenExists(syntheticTokenOut_)
        returns (uint256 _amountOut, uint256 _fee)
    {
        address _msgSender = _msgSender();

        if (!isSwapActive) revert SwapFeatureIsInactive();
        if (amountIn_ == 0 || amountIn_ > syntheticTokenIn_.balanceOf(_msgSender)) revert AmountInIsInvalid();

        syntheticTokenIn_.burn(_msgSender, amountIn_);

        (_amountOut, _fee) = quoteSwapOut(syntheticTokenIn_, syntheticTokenOut_, amountIn_);

        if (_fee > 0) {
            syntheticTokenOut_.mint(_poolRegistry.feeCollector(), _fee);
        }

        syntheticTokenOut_.mint(_msgSender, _amountOut);

        emit SyntheticTokenSwapped(_msgSender, syntheticTokenIn_, syntheticTokenOut_, amountIn_, _amountOut, _fee);
    }
