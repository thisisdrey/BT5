This is the critical finding: `PayAccountOnLocation::pay_reward` in `bridges/snowbridge/primitives/core/src/reward.rs` uses `ReserveAssetDeposited` on an XCM sent to AssetHub, minting a *foreign representation of Ether* on AssetHub for the beneficiary, without any real Ether ever leaving BridgeHub or being deducted from a real backing pot — the "reward" ledger entry (`Tips`/`PendingOrders.fee`/`RelayerRewards`) is the only accounting; the actual payout is a fresh mint of the reward asset on AssetHub. This confirms the claim's core assertion: the `amount` credited into `Tips`/`PendingOrders.fee` via `add_tip` is not merely "extracted from AMM pool liquidity" but is directly and fully honored later as unbacked-mint value via `ReserveAssetDeposited`, with no re-validation against real economic value. This matches the claim's stated impact category (theft/unbacked mint) in the Required Impacts gate.

Combined with the confirmed absence of `amount_out_min` protection in `swap_and_burn` (`bridges/snowbridge/pallets/system-frontend/src/lib.rs` lines 301-308, hard-coded `None`), and the fact that `pallet_asset_conversion::do_swap_exact_tokens_for_tokens` (`substrate/frame/asset-conversion/src/lib.rs` lines 987-1002) only enforces a minimum when the caller explicitly supplies one, the reported control flow is accurate:

- Attacker calls `add_tip` (or `register_token`) with a manipulable AMM pool for the tip asset.
- `swap_and_burn` swaps at spot price with zero floor, producing an inflated `ether_gained`.
- This value is forwarded unmodified via `build_add_tip_call`/`EthereumSystemCall::AddTip` to `AddTip::add_tip` on BridgeHub (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` L248-258 or outbound-queue-v2 L483-496), directly inflating `Tips`/`PendingOrders.fee`.
- That inflated total is paid via `register_reward` → `RelayerRewards` → `claim_rewards_to` → `PayAccountOnLocation::pay_reward`, which mints the corresponding Ether-denominated foreign asset on AssetHub for the beneficiary — a real, unbacked payout, not merely a redistribution of AMM pool liquidity.

This satisfies the "theft or unbacked mint" impact criterion in the Required Impacts gate, the exploit is reachable by any unprivileged signed account via the public `add_tip` extrinsic, and the only existing guard (fee_amount == 0 check, or unrelated origin checks) does not bound the swap output. This is a legitimate, in-scope, reachable vulnerability.

Audit Report

## Title
Unbounded relayer-reward inflation via unprotected AMM swap in `snowbridge-pallet-system-frontend::add_tip` - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`add_tip` lets any signed account swap an arbitrary asset for Ether through `pallet_asset_conversion` with `amount_out_min` hard-coded to `None`, then forwards the raw AMM output (`ether_gained`) as the exact reward amount credited on BridgeHub. Because the eventual relayer payout (`PayAccountOnLocation::pay_reward`) mints a fresh foreign Ether asset on AssetHub rather than transferring pre-existing backing funds, an attacker who transiently skews the tip-asset/Ether pool can cause a small nominal tip to be registered and paid out as an inflated, unbacked Ether reward.

## Finding Description
`add_tip` (`bridges/snowbridge/pallets/system-frontend/src/lib.rs` L261-273) is a public, unprivileged extrinsic that calls `swap_fee_asset_and_burn` → `swap_and_burn` (L290-317). `swap_and_burn` invokes `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)` (L301-308), where `None` disables the `amount_out_min` check inside `pallet_asset_conversion::do_swap_exact_tokens_for_tokens` (`substrate/frame/asset-conversion/src/lib.rs` L987-1002). The resulting `ether_gained` is burned locally and forwarded unmodified as `amount` in `EthereumSystemCall::AddTip` (L340-351) via XCM `Transact` to BridgeHub, where `AddTip::add_tip` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` L248-258, `outbound-queue-v2/src/lib.rs` L483-496) adds it directly into `Tips`/`PendingOrders.fee` with no independent validation of real economic value.

Critically, the eventual payout is not a conservative transfer from an existing backing pot: `PayAccountOnLocation::pay_reward` (`bridges/snowbridge/primitives/core/src/reward.rs` L127-151) sends an XCM to AssetHub containing `ReserveAssetDeposited` for the reward amount, which mints a new foreign-asset balance for the beneficiary. This means the inflated `amount` computed from a manipulated AMM spot price is directly honored as freshly minted value, with no downstream reconciliation against the real assets contributed by the tipper.

## Impact Explanation
This is a theft/unbacked-mint impact: an unprivileged attacker can register and subsequently claim (via `pallet_bridge_relayers::claim_rewards_to`) an Ether-denominated reward on AssetHub that exceeds the real economic value of the asset they supplied, because the swap price used to compute the reward was manipulated and unbounded. `Tips`/`PendingOrders.fee` and `RelayerRewards` do not conserve value under this flow.

## Likelihood Explanation
Exploitation requires only a signed account and capital to temporarily skew a thin `pallet_asset_conversion` pool (self-seeded or manipulated), executed atomically (e.g., via `utility.batch_all`). No validator, collator, relayer, or governance collusion is required. The absence of any `amount_out_min` or reference-price check removes the standard AMM manipulation defense.

## Recommendation
- Supply a real `min_amount_out` in `swap_and_burn`, derived from a trusted reference price (e.g., an oracle or `PricingParameters::exchange_rate`), instead of hard-coding `None`.
- Cap the maximum ether-equivalent tip/reward addable per call independent of raw AMM output.
- Consider reconciling reward mint amounts on AssetHub against the actual value burned/teleported from the source chain rather than trusting the frontend-computed `amount` unconditionally.

## Proof of Concept
1. Attacker seeds/skews a thin `pallet_asset_conversion` pool pairing a low-liquidity asset with `EthereumLocation` (Ether).
2. In one atomic batch, attacker unbalances the pool reserves, then calls `SnowbridgeSystemFrontend::add_tip(origin, message_id, Asset{ id: tip_asset, fun: Fungible(small_amount) })`.
3. `swap_and_burn` executes `swap_exact_tokens_for_tokens(..., None, ...)` against the skewed pool, returning `ether_gained` far above the fair value of `small_amount`.
4. The inflated amount is forwarded to BridgeHub's `AddTip::add_tip`, credited to `Tips`/`PendingOrders.fee`, then registered via `register_reward` into `RelayerRewards`.
5. Attacker (or accomplice) relayer calls `claim_rewards_to`, triggering `PayAccountOnLocation::pay_reward`, which mints the inflated Ether-equivalent foreign asset on AssetHub for the beneficiary — extracting more value than was contributed.
