## Finding: Heap out-of-bounds read while parsing untrusted ZIP/JAR central directory entries in `ijar`

### Title
Unbounded heap read when parsing ZIP central-directory entry metadata (file name / extra field / comment lengths) in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`, Bazel's bundled C++ tool for producing interface JARs (exposed to Starlark via `java_common.run_ijar` / `java_common.stamp_jar`, and used internally whenever a `.jar` produced by a `java_import`/`java_library`-style rule is stripped), mmaps an entire ZIP/JAR file and walks its central directory with `InputZipFile::ProcessCentralDirEntry`. Unlike the *local* file header parser (`ProcessLocalFileEntry`), which calls `EnsureRemaining()` before reading the file name and extra-field bytes, `ProcessCentralDirEntry` never validates that the attacker-controlled `file_name_length`, `extra_field_length`, or `file_comment_length` fields actually fit inside the mapped file before advancing the cursor and `memcpy`-ing from it. [1](#0-0) 

### Finding Description
`ProcessCentralDirEntry` reads the 16-bit length fields straight off the mmap'd buffer and immediately uses them: [2](#0-1) 

```
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
...
memcpy(reinterpret_cast<void*>(filename), p, len);
```

Nothing bounds `file_name_length`/`extra_field_length`/`file_comment_length` against the remaining bytes of the mmap'd input file (`input_file_->Length()`), the way `EnsureRemaining()` protects the equivalent local-header path: [3](#0-2) [4](#0-3) 

The subsequent extra-field scan loop is similarly unchecked and can walk `extra_p`/`p` arbitrarily far based on attacker-chosen `header_id`/`data_size` pairs, reading `get_u8le` values from beyond the mapped extra-field region: [5](#0-4) 

Because `central_dir_`/`p` point into an `mmap()`'d region sized exactly to the input file, a central directory record near the end of the file whose length fields claim more bytes than actually remain causes reads past the end of the mapping — a heap/mapping out-of-bounds read, directly analogous to the Samba `vfs_fruit` bug where attacker-supplied length fields in metadata (there, xattrs; here, ZIP central directory fields) are trusted without validating them against the buffer they are read from.

The over-read data (garbage/adjacent-memory bytes) is then: (1) copied into the fixed `filename[PATH_MAX]` buffer and used to construct output entry names in the generated interface jar (`processor->Accept/Process`), and (2) fed to `get_u8le(extra)` to derive `*offset`, which is later used verbatim by `ProcessNext()` to seek `p = zipdata_in_ + in_offset_ + offset` and read a "local file header" from that wild location — a second, attacker-influenced out-of-bounds read whose result (`compressed_size_`, `uncompressed_size_`, `file_name_`) flows into `ProcessFile`/`memcpy` calls that write file contents to disk.

### Impact Explanation
An attacker who controls the bytes of a `.jar`/`.zip` file that Bazel processes with `ijar` (e.g., a `java_import`/`aar_import` jar fetched via `http_jar`/`http_archive`/Maven-style external repository, or any target whose `.jar` output is run through `java_common.run_ijar`/`stamp_jar`) can craft a central directory record whose declared lengths exceed the remaining mapped file size. This yields out-of-bounds heap reads whose content can leak into the interface jar's file names, and can also be used to redirect the "local file header" pointer to attacker-chosen offsets, corrupting which bytes are treated as file content and written into the generated interface JAR. This is a real integrity/confidentiality violation of the extraction pipeline, not merely a crash: it violates the invariant that untrusted archive content must remain confined to its own declared boundaries. In the worst case it manifests as process crash (SIGSEGV) due to reading unmapped pages beyond the mmap region, but for typical corpora (contiguous mmap'd address space, guard-page-adjacent heap) it produces a genuine over-read of adjacent memory that is copied into observable output.

### Likelihood Explanation
Any repository that references a prebuilt `.jar` (via `java_import`, `aar_import`, or a Starlark rule calling `java_common.run_ijar`) processes attacker-controlled bytes through this exact code path with no checksum-independent validation of the internal ZIP structure — sha256/integrity on the `http_archive`/`http_jar` download only guarantees the *whole file* matches a hash the user pinned to a *specific* (potentially already-malicious) upstream artifact; it does nothing to prevent a malformed central directory inside an otherwise-hash-matching file from being mis-parsed. No sandboxing prevents this because it's a memory-safety bug in the parsing tool itself, not a Starlark/action-execution boundary issue.

### Recommendation
Add the same `EnsureRemaining()` bounds check used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, and `file_comment_length` bytes, and validate the extra-field scan loop (`header_id`/`data_size`) against the actual `extra_field_length` boundary (mirroring the checks already present in `src/tools/singlejar/zip_headers.h`'s `ExtraField::find`, which rejects fields whose declared size runs past the buffer end).

### Proof of Concept
A reproducible JUnit/`BuildIntegrationTestCase`-style PoC would:
1. Hand-craft a minimal ZIP file whose single central directory record sets `file_name_length`/`extra_field_length`/`file_comment_length` fields larger than the number of bytes actually remaining in the file (e.g., central directory record placed at the very end of the file, with `file_name_length = 0xFFFF`).
2. Feed the file to `ijar`/`InputZipFile::ProcessAll()` (or to `java_common.run_ijar` on a `java_import` jar built from this crafted file) under ASan.
3. Observe the ASan heap-buffer-overflow / SEGV report attributing the fault to `InputZipFile::ProcessCentralDirEntry`'s unchecked `memcpy`/`get_u2le`/`get_u8le` calls, contrasted with the same crafted lengths in a *local* header (protected by `EnsureRemaining`) correctly failing with a clean "Premature end of file" error instead of crashing/over-reading.

```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
```
