**Analysis:**

`lock_item_properties` dispatches to `do_lock_item_properties`, which performs the `Admin` role check and the `ItemConfigOf` mutation within a single atomic call using `has_role` (a live storage lookup against `CollectionRoleOf`) immediately followed by `ItemConfigOf::try_mutate`. [1](#0-0) 

There is no cached, precomputed, or persisted reference to "the current admin" or "the current owner" that is captured before a role/ownership change and then reused afterward — the permission check reads `CollectionRoleOf` fresh at call time via `has_role`: [2](#0-1) 

Role changes (`do_set_team`) atomically clear all old role entries with `clear_roles` before inserting new ones inside a single `try_mutate` on `Collection`, so there is no window where both an old and new role holder can be simultaneously valid or where a stale role reference outlives the transition: [3](#0-2) 

Ownership transfer (`do_transfer_ownership`) only updates `Collection.owner`, `CollectionAccount`, and the deposit — it does not touch `CollectionRoleOf` at all, so `Admin`/`Issuer`/`Freezer` roles are an entirely separate storage item unaffected by an ownership change: [4](#0-3) 

The lock itself only flips `ItemSetting::UnlockedMetadata`/`UnlockedAttributes` bits on `ItemConfigOf` for a specific `(collection, item)` — it does not store or reference any account/subject identifier at all, so there is no "subject" that could become stale. [5](#0-4) 

Since the permission check and the state mutation happen atomically within the same extrinsic call (no deferred authorization, no cached signer/owner snapshot reused in a later call), there is no window in which "one subject is replaced by another" while `lock_item_properties`'s effect still honors the old subject. This does not match the described exploit pattern.

		collection: T::CollectionId,
		new_owner: T::AccountId,
	) -> DispatchResult {
		// Check if the new owner is acceptable based on the collection's acceptance settings.
		let acceptable_collection = OwnershipAcceptance::<T, I>::get(&new_owner);
		ensure!(acceptable_collection.as_ref() == Some(&collection), Error::<T, I>::Unaccepted);

		// Try to retrieve and mutate the collection details.
		Collection::<T, I>::try_mutate(collection, |maybe_details| {
			let details = maybe_details.as_mut().ok_or(Error::<T, I>::UnknownCollection)?;
			// Check if the `origin` is the current owner of the collection.
			ensure!(origin == details.owner, Error::<T, I>::NoPermission);
			if details.owner == new_owner {
				return Ok(());
			}

			// Move the deposit to the new owner.
			T::Currency::repatriate_reserved(
				&details.owner,
				&new_owner,
				details.owner_deposit,
				Reserved,
			)?;

			// Update account ownership information.
			CollectionAccount::<T, I>::remove(&details.owner, &collection);
			CollectionAccount::<T, I>::insert(&new_owner, &collection, ());

			OwnershipAcceptance::<T, I>::remove(&new_owner);
			frame_system::Pallet::<T>::dec_consumers(&new_owner);

			// Emit `OwnerChanged` event.
			Self::deposit_event(Event::OwnerChanged { collection, new_owner });
			Ok(())
