Audit Report

## Title
Relayer reward is irrecoverably burned when the cross-chain `PayAccountOnLocation` reward XCM fails to execute on AssetHub - (File: `bridges/snowbridge/primitives/core/src/reward.rs`, `bridges/modules/relayers/src/lib.rs`)

## Summary
`pallet-bridge-relayers::do_claim_rewards` removes the relayer's accumulated reward from storage via `maybe_reward.take()` and then calls `T::PaymentProcedure::pay_reward`; for Snowbridge, `PayAccountOnLocation::pay_reward` only validates and delivers a fire-and-forget XCM to AssetHub and returns `Ok(())` once the message is queued, not once the remote `DepositAsset` actually succeeds. If the remote deposit fails, the reward is permanently lost with no compensation path.

## Finding Description
`do_claim_rewards` uses `RelayerRewards::<T, I>::try_mutate_exists` and calls `maybe_reward.take()` to remove the reward entry before invoking `T::PaymentProcedure::pay_reward`; the storage mutation only rolls back if the closure itself returns `Err` [1](#0-0) .

For Snowbridge, `pay_reward` is implemented by `PayAccountOnLocation`, which builds an XCM consisting of `UnpaidExecution`, `DescendOrigin(InboundQueueLocation)`, `UniversalOrigin(GlobalConsensus(Ethereum))`, `ReserveAssetDeposited`, and `DepositAsset { assets, beneficiary }`, then only `validate`s and `deliver`s the ticket, returning `Ok(())` as soon as delivery into the message queue succeeds — not once the remote instructions execute [2](#0-1) . No `SetAssetClaimer` instruction is present in this program, so if `DepositAsset` fails on AssetHub (e.g., beneficiary doesn't satisfy existential deposit for the newly minted foreign asset), the leftover holding is trapped via `DropAssets::drop_assets` and becomes unclaimable by the relayer or beneficiary, since the trap is keyed to the virtual `UniversalOrigin(GlobalConsensus(Ethereum))`/`DescendOrigin(InboundQueueLocation)` origin, which nobody can construct a matching signed origin for [3](#0-2) .

Meanwhile, on BridgeHub the `RelayerRewards` entry has already been irrevocably removed and `RewardPaid` has already fired before the remote outcome is known, violating the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."

## Impact Explanation
This is a permanent bridge-reward-fund lock: the accumulated reward is deleted from `RelayerRewards` before remote settlement is confirmed, and if the remote `DepositAsset` fails, funds are trapped under an unreachable virtual origin with no retry or re-credit mechanism, matching the "permanent user-fund or bridge-state lock" and "message queues ... must only advance after ... settlement succeed atomically" categories in the Polkadot SDK impact gate.

## Likelihood Explanation
`claim_rewards_to` is a public, unprivileged extrinsic reachable via `ensure_signed` [4](#0-3) , and the beneficiary `Location` is caller-supplied, so any relayer picking (deliberately or accidentally) an under-funded/unregistered beneficiary location deterministically triggers the loss once the remote `DepositAsset` fails. No malicious validator, governance, or leaked key is required — only ordinary operational conditions (fresh/unfunded beneficiary, foreign-asset registration edge cases, or remote congestion).

## Recommendation
Do not remove the `RelayerRewards` entry until remote settlement is confirmed. Preferable options:
- Move to a two-phase commit: mark the reward as "in-flight" and only finalize deletion after a confirmation is received back from AssetHub (mirroring the pending-order/delivery-receipt pattern in `process_delivery_receipt` [5](#0-4) ).
- Always include `SetAssetClaimer` in the `PayAccountOnLocation` XCM program, pinned to a real, relayer/beneficiary-controlled account, so a failed `DepositAsset` traps assets that remain claimable.
- Alternatively, re-credit `RelayerRewards` upon an observed remote failure notification (e.g., via XCM response/error reporting).

## Proof of Concept
1. Relayer accumulates a Snowbridge reward via `register_reward`, visible in `RelayerRewards::<T,I>::get`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(beneficiary))` where `beneficiary` has no existing entry (no ED) for the reward's foreign asset.
3. `do_claim_rewards` removes the reward entry and calls `PayAccountOnLocation::pay_reward`, which validates and delivers the XCM, returning `Ok(())`; `RewardPaid` fires and the storage entry is gone [6](#0-5) .
4. On AssetHub, `DepositAsset` fails because `beneficiary` doesn't meet ED for the minted asset; the holding is trapped under the Ethereum/InboundQueue-anchored virtual origin, which the relayer cannot match with a signed origin via `claim_assets`.
5. The reward is permanently gone: absent on BridgeHub (already removed) and unclaimable on AssetHub.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
