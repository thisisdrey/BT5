### Title
`GASLIMIT` opcode always returns a hardcoded zero instead of the actual block energy limit, breaking EVM compatibility - (File: `actuator/src/main/java/org/tron/core/vm/OperationActions.java`)

### Summary
The TVM's `GASLIMIT` opcode (`0x45`) is supposed to return the current block's gas/energy limit, matching EVM semantics. Instead, its implementation, `gasLimitAction`, unconditionally pushes `DataWord.ZERO()` onto the stack, discarding any notion of a real, dynamically configured block energy limit.

### Finding Description
The opcode handler is registered in `OperationRegistry.newBaseOperationSet()`, mapping `Op.GASLIMIT` to `OperationActions::gasLimitAction`: [1](#0-0) 

The action itself is implemented as a no-op that always returns zero, regardless of any real block energy limit configuration: [2](#0-1) 

This is confirmed by the existing unit test, which explicitly asserts the opcode returns `DataWord(0)`: [3](#0-2) 

For comparison, `GAS` (remaining transaction energy) correctly reads a real, contextual value via `program.getEnergyLimitLeft()`: [4](#0-3) 

TRON does maintain a real, per-block energy ceiling (`TOTAL_ENERGY_LIMIT`/dynamic energy limit machinery referenced across `DynamicPropertiesStore`, `EnergyProcessor`, `VMActuator`, and `VmConfig`), so a legitimate, non-zero block-level energy limit value does exist in the system and could in principle be exposed to the opcode. Instead of surfacing that value (or the per-transaction fee-limit-derived cap, as EVM-compatible chains typically do for `GASLIMIT`/`block.gaslimit`), the implementation hardcodes zero, which is neither the true value nor a meaningful semantic placeholder.

This differs from the reported minievm bug (which leaked the transaction's remaining gas as the block gas limit) in the specific wrong value chosen, but it is the same bug class: `GASLIMIT` fails to return the actual block gas limit, producing EVM-incompatible behavior that can break ported Solidity contracts.

### Impact Explanation
Any contract executed via a normal, unprivileged transaction can invoke `GASLIMIT` (opcode `0x45`). Contracts ported from Ethereum that use `block.gaslimit` for gas-based logic (e.g., checks such as `require(block.gaslimit > X)`, gas-based loops, gas-limit-derived fee/refund calculations, or legacy reentrancy-guard patterns) will silently receive `0` on TRON instead of a meaningful value. This can cause:
- Reverts or unexpected control-flow branches in ported contracts that assume a nonzero, realistic gas limit.
- Silent logic errors in financial/fee calculations that key off `block.gaslimit`, potentially leading to incorrect accounting or unintended contract states.

This is a functional correctness / EVM-compatibility issue reachable by any transaction sender or contract deployer without special privileges, and it can misbehave for any deployed contract relying on this opcode — this matches the class of "incompatibility with the EVM" bugs called out in the report, though it does not rise to fund theft by itself; the impact is contract logic/behavioral incorrectness.

### Likelihood Explanation
High likelihood of being triggered: any contract containing the `GASLIMIT`/`block.gaslimit` bytecode instruction, deployed and called by any address, will hit this incorrect behavior deterministically on every invocation — no special conditions or attacker capability beyond normal contract deployment/interaction are required.

### Recommendation
Update `gasLimitAction` in `actuator/src/main/java/org/tron/core/vm/OperationActions.java` to push the actual per-block energy limit (sourced from the same dynamic/config value used elsewhere for block-level energy accounting, e.g., via `DynamicPropertiesStore`/`ProgramInvoke`) instead of a hardcoded `DataWord.ZERO()`, and update the corresponding test in `framework/src/test/java/org/tron/common/runtime/vm/OperationsTest.java` accordingly.

### Proof of Concept
1. Deploy a Solidity contract containing `block.gaslimit` (compiles to opcode `0x45`).
2. Call the contract via a normal transaction.
3. Observe that `gasLimitAction` in `OperationActions.java` always pushes `DataWord.ZERO()`: [2](#0-1) 
4. Any contract logic depending on a realistic, nonzero `block.gaslimit` value will behave incorrectly or revert, confirmed by the existing test asserting the returned value is `0`: [3](#0-2)
