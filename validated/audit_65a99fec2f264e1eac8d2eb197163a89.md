The strongest analog found is in `HeuristicalOptimizationStrategy.ShouldRepackObjects`, where `stats.FullRepackTimestamp` explicitly returns the Go zero `time.Time{}` when a repository has never had a full repack, and this zero value flows directly into an elapsed-time computation used to decide whether to trigger a full repack.

### Title
Zero-valued `LastFullRepack` timestamp causes unconditional/oversized elapsed-time computation that forces disproportionate full repacks - (File: internal/git/housekeeping/optimization_strategy.go)

### Summary
`FullRepackTimestamp` returns the zero-value `time.Time{}` when the `.gitaly-full-repack-timestamp` marker file does not yet exist for a repository [1](#0-0) . This zero value is stored as `PackfilesInfo.LastFullRepack` and consumed by `HeuristicalOptimizationStrategy.ShouldRepackObjects` to compute `timeSinceLastFullRepack := time.Since(s.info.Packfiles.LastFullRepack)` [2](#0-1) . Exactly like the `ERC4626i.claimProtocolFees` bug — where a zeroed `feeRewardsLastClaimed[campaignId]` causes `elapsed = campaignData.end - 0` to be maximally (and unintentionally) large — this computation yields a duration on the order of decades (`time.Now() - year 1`) instead of a bounded, meaningful "time since last full repack."

### Finding Description
The heuristic that governs housekeeping cost gates full repacks behind a cooldown, `FullRepackCooldownPeriod`, intended to bound how frequently the (CPU/IO expensive) full-repack-with-cruft/unreachable strategy runs [3](#0-2) . The check is:

```go
if nonCruftPackfilesCount > 1 && timeSinceLastFullRepack > FullRepackCooldownPeriod {
    return true, fullRepackCfg
}
```

Because `LastFullRepack` defaults to the zero time whenever the timestamp file is absent (new repositories, repositories restored/imported without the marker file, repositories where the file was lost during a fork/pool link, or a fresh replica), `timeSinceLastFullRepack` is always far larger than any configured cooldown — the "elapsed" value is not floored to a sane baseline (e.g., repository creation time), mirroring the recommendation in the analog report to floor `lastUpdated` to `campaignData.start` instead of using the zero default.

### Impact Explanation
Any ordinary user action that causes multiple packfiles to accumulate in a repository without an existing `.gitaly-full-repack-timestamp` marker (e.g., repeated pushes/fetches into a freshly created repo, imports, or forks newly linked to an object pool via `gittest`-style `linkRepoToPool` flows exercised in tests [4](#0-3) ) will cause `ShouldRepackObjects` to unconditionally select the expensive `RepackObjectsStrategyFullWithCruft`/`FullWithUnreachable` strategy on essentially every optimization pass, bypassing the intended cooldown-based rate-limiting. Because full repacks are explicitly called out in the code comments as comparatively expensive and something the heuristic is designed to throttle [5](#0-4) , an attacker who can repeatedly trigger housekeeping on such repositories (via pushes, the `OptimizeRepository` RPC, or the write-count-driven middleware scheduler [6](#0-5) ) can force Gitaly to repeatedly perform full, resource-intensive repacks — a CPU/IO amplification and potential DoS vector on the housekeeping/optimization RPC path, well beyond what the cooldown heuristic intends to allow.

### Likelihood Explanation
The zero-timestamp condition is reachable through entirely unprivileged, ordinary flows: creating a repository, performing pushes that create multiple packfiles, or importing/forking a repository — none of which require special privileges or filesystem access. The `FullRepackTimestamp` zero-default behavior is explicit and documented in-code as "leave the timestamp at the zero date" [7](#0-6) , confirming this is a real, reachable code path rather than a hypothetical one.

### Recommendation
When `FullRepackTimestamp` returns the zero value (i.e., no full repack has ever happened), floor the elapsed-time computation to a meaningful baseline instead of the Unix/Go zero time — e.g., use the repository's creation time, or treat a zero `LastFullRepack` as "not yet due" until a minimum baseline age has passed, analogous to the report's recommendation to use `campaignData.start` instead of the zero default for `lastUpdated`.

### Proof of Concept
1. Create a new repository and push commits until it accumulates more than one non-cruft packfile (`nonCruftPackfilesCount > 1`), without ever running a full repack (so `.gitaly-full-repack-timestamp` never exists).
2. Call `OptimizeRepository` (or let the housekeeping middleware auto-schedule it via write-count thresholds [8](#0-7) ).
3. Observe `HeuristicalOptimizationStrategy.ShouldRepackObjects` compute `timeSinceLastFullRepack` from the zero time [2](#0-1) , which trivially exceeds `FullRepackCooldownPeriod`, causing a full (expensive) repack to run on essentially every optimization cycle instead of being throttled — repeatable by continuing to push new packfiles.

// FullRepackTimestamp reads the timestamp that indicates when a repository has last been fully
// repacked. If no such timestamp exists, the zero timestamp is returned without an error.
func FullRepackTimestamp(repoPath string) (time.Time, error) {
	stat, err := os.Stat(filepath.Join(repoPath, FullRepackTimestampFilename))
	if err != nil {
		if errors.Is(err, os.ErrNotExist) {
			// It's fine if the file doesn't exist. We just leave the timestamp at the
			// zero date in that case.
			return time.Time{}, nil
		}

		return time.Time{}, err
	}

	return stat.ModTime(), nil
}

// pendingOperations returns operations that have exceeded their RPC interval thresholds.
func (m *Middleware) pendingOperations(a *activity, force bool) []config.OperationType {
	var pending []config.OperationType

	for _, op := range allOperations {
		thresholds := m.getThresholds(op)
		lastRun := a.writeCountAtLastRun[op]
		writesSinceLastRun := a.writeCount - lastRun

		if force || writesSinceLastRun > thresholds.RPCInterval {
			pending = append(pending, op)
		}
	}

	return pending
}

func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++

	if a.active {
		return
	}

	pendingOps := m.pendingOperations(a, force)
	if len(pendingOps) == 0 {
		return
	}

	m.logger.WithFields(log.Fields{
		"forced":     force,
		"operations": pendingOps,
	}).InfoContext(ctx, "beginning scheduled housekeeping")

	// Mark that these operations are running at the current write count
	for _, op := range pendingOps {
		a.writeCountAtLastRun[op] = a.writeCount
	}

	m.markHousekeepingActive(key)

	m.wg.Add(1)
	go func() {
		// We need to call OptimizeRepository with a child context that's disowned from the parent's
		// cancellation signals we're executing it asynchronously. Providing the existing `ctx` would
		// cause it to fail, since `ctx` would be cancelled when this request completes. We still want
		// to be able to abort the worker when the middleware shuts down though, so we propagate
		// cancellation from the middleware's shutdown context.
		housekeepingCtx, housekeepingCancel := context.WithCancel(context.WithoutCancel(ctx))
		stopShutdownPropagation := context.AfterFunc(m.shutdownCtx, housekeepingCancel)

		defer func() {
			stopShutdownPropagation()
			m.markHousekeepingInactive(key)
			m.logger.InfoContext(housekeepingCtx, "ended scheduled housekeeping")
			housekeepingCancel()
			m.wg.Done()
		}()

		localRepo := m.localRepoFactory.Build(repo)
		if err := m.manager.OptimizeRepository(housekeepingCtx, localRepo,
			manager.WithOptimizationStrategyConstructor(
				func(info stats.RepositoryInfo) housekeeping.OptimizationStrategy {
					return housekeeping.NewSelectiveOptimizationStrategy(info, pendingOps)
				},
			),
			manager.WithMVCCGarbageCollection(),
		); err != nil {
			m.logger.WithError(err).ErrorContext(housekeepingCtx, "failed scheduled housekeeping")
		}
	}()
}
