### Title
Unprivileged `confidential_transfer_raw` Fills Recipient's `transfers_received` Counter, Griefing Key Rotation and Forcing Expensive ZK Proof Operations - (File: `aptos-move/framework/aptos-framework/sources/confidential_asset/confidential_asset.move`)

---

### Summary

Any unprivileged user can call `confidential_transfer_raw` (a `public entry fun`) to send micro-transfers to any registered recipient, incrementing the recipient's `transfers_received` counter. Once the counter reaches `MAX_TRANSFERS_BEFORE_ROLLOVER` (65,536), no further confidential transfers or deposits can be received. The victim is forced to call `rollover_pending_balance` followed by `normalize_raw` (which requires generating an expensive ZK proof) to recover. This is the direct Aptos analog of the Fenwick tree griefing attack: an unprivileged actor fills a bounded counter on behalf of another user, causing a denial-of-service on incoming transfers.

---

### Finding Description

The `ConfidentialStore` struct tracks a `transfers_received: u64` counter per `(user, asset_type)` pair: [1](#0-0) 

The constant bounding this counter is: [2](#0-1) 

Every call to `confidential_transfer` (reached via the public entry `confidential_transfer_raw`) increments the recipient's counter and then asserts it has not exceeded the limit: [3](#0-2) 

The entry point is fully public and unprivileged: [4](#0-3) 

An attacker who holds any confidential balance can send 65,536 dust transfers (each of 1 unit) to a victim's address. After the 65,536th transfer, `transfers_received == MAX_TRANSFERS_BEFORE_ROLLOVER`. The 65,537th attempt increments to 65,537, the assert fires, and the transaction aborts — leaving the counter permanently at 65,536 until the victim rolls over.

To recover, the victim must:
1. Call `rollover_pending_balance`, which resets `transfers_received = 0` but sets `normalized = false`: [5](#0-4) 

2. Call `normalize_raw` (a ZK withdrawal proof with `amount = 0`) to set `normalized = true` again before the next rollover is possible: [6](#0-5) 

The `deposit` function is similarly affected — it also increments `transfers_received` and checks the same limit: [7](#0-6) 

---

### Impact Explanation

- **Temporary DoS on incoming transfers**: Once `transfers_received` hits 65,536, the victim cannot receive any further confidential transfers or deposits until they roll over.
- **Forced expensive ZK proof generation**: After rollover, `normalized = false`. The victim must generate a Bulletproofs range proof + sigma protocol proof (via `normalize_raw`) to restore `normalized = true` before the next rollover cycle. This is computationally expensive for the victim.
- **Key rotation interference**: Key rotation requires `pending_balance.is_zero()` and `transfers_received == 0`. An attacker can repeatedly fill the counter to delay or disrupt a victim's key rotation workflow, though the victim can mitigate by calling `set_incoming_transfers_paused(true)` first. [8](#0-7) 

---

### Likelihood Explanation

The attacker must spend 65,536 transactions (each with gas) and 65,536 units of the confidential asset (which are transferred to the victim, not burned). This makes the attack expensive but not infeasible for a well-funded adversary targeting a high-value account. The attack can be repeated indefinitely as long as the victim does not pause incoming transfers.

---

### Recommendation

1. **Add a minimum transfer amount check** in `confidential_transfer` to raise the cost of dust-transfer griefing.
2. **Allow the recipient to set a minimum incoming transfer threshold** or require the sender to hold a minimum balance above a configurable floor.
3. **Consider allowing `rollover_pending_balance` to be called without requiring `normalized = true`**, or automatically normalize during rollover, to reduce the recovery burden on victims.
4. **Document clearly** that users who want to protect against this griefing should call `set_incoming_transfers_paused(true)` when not actively expecting transfers. [9](#0-8) 

---

### Proof of Concept

```
// Attacker setup: attacker has a confidential balance of >= 65536 units of asset_type
// Victim: registered at address `victim_addr` with transfers_received = 0

// Attacker calls confidential_transfer_raw 65,536 times, each sending 1 unit to victim_addr
// After 65,536 calls: victim.transfers_received == 65,536

// Now any further transfer to victim_addr aborts with E_PENDING_BALANCE_MUST_BE_ROLLED_OVER (code 6)
// confidential_transfer_raw(attacker, asset_type, victim_addr, ...) → ABORT

// Victim must:
// 1. rollover_pending_balance(victim, asset_type)  → transfers_received = 0, normalized = false
// 2. normalize_raw(victim, asset_type, ...)        → normalized = true  [requires ZK proof generation]
// Only then can victim receive transfers again.

// Attacker can immediately repeat the 65,536-transfer cycle.
```

The root cause is identical to the external report: `confidential_transfer_raw` is an unprivileged entry function that modifies a bounded counter on the recipient's store without any rate-limiting or sender-authorization check on the recipient side. [10](#0-9)

    /// Pauses or resumes incoming transfers. Pausing is required before key rotation.
    public entry fun set_incoming_transfers_paused(
        owner: &signer,
        asset_type: Object<fungible_asset::Metadata>,
        paused: bool
    ) acquires ConfidentialStore, GlobalConfig {
        assert!(!is_emergency_paused(), error::invalid_state(E_EMERGENCY_PAUSED));

        let ca_store = borrow_confidential_store_mut(signer::address_of(owner), asset_type);
        let old_paused = ca_store.pause_incoming;
        if (old_paused != paused) {
            ca_store.pause_incoming = paused;
            event::emit(IncomingTransfersPauseChanged::V1 { addr: signer::address_of(owner), asset_type, paused });
        }
    }
