## Analysis

The vulnerability class in the report — trusting an attacker-supplied identifier for an object without verifying that the invoking party actually owns/controls it — maps directly onto the relay-establishment control-plane handling in `relayManager.handleCreateRelayRequest`.

### Finding

In `relay_manager.go`, `handleCreateRelayRequest` extracts `from` directly from the peer-supplied `NebulaControl` message field `RelayFromAddr`/`OldRelayFromAddr`, with no verification that `from` is one of the sending `HostInfo`'s cryptographically-verified `vpnAddrs`: [1](#0-0)

`h` is the authenticated `HostInfo` for the actual sender of the control packet — the sender's real, certificate-verified identity is `h.vpnAddrs` (set from `validatePeerCert` during the handshake, see `handshake_manager.go`): [2](#0-1) 

But `handleCreateRelayRequest` never checks `from == one of h.vpnAddrs`. It blindly calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, which installs a `Relay{PeerAddr: from, ...}` on `h`'s relay state: [3](#0-2) 

This is the same class of bug as the audited Solana program: an object (`from`, the "relayed-for" VPN address) is accepted as-supplied by the invoker instead of being cross-checked against the invoker's verified identity (`h.vpnAddrs`, analogous to `stake_info.stake_owner`).

### Impact

Once installed, the forged relay mapping (`relay.PeerAddr = from`) is trusted for the lifetime of the tunnel. When a relayed data packet later arrives over that tunnel, the outer relay-index lookup resolves to this `Relay` object, and its `PeerAddr` is treated as an authenticated fact for terminal/forwarding relay logic (used by `handleOutsideRelayPacket` and `QueryVpnAddrsRelayFor`): [4](#0-3) 

This lets any authenticated-but-otherwise-unrelated peer register itself as "relaying for" a victim VPN address it does not own and was never certified for, poisoning the relay/hostmap state (`hm.Relays`, `h.relayState`) and enabling it to participate in the relay path under an identity claim it does not hold, without the target host having any way to detect the discrepancy from this message alone (there is no check tying `from` to `h`'s own certificate networks).

### Recommendation

In `handleCreateRelayRequest` (and symmetrically wherever `RelayFromAddr`/`RelayToAddr` values are trusted from a peer's control message), verify that the claimed `from` address is actually contained in the sending `HostInfo`'s certificate-verified `vpnAddrs`/`networks` (i.e., `h.vpnAddrs` or `h.networks`, populated by `buildNetworks`/`validatePeerCert`) before calling `AddRelay`. If it is not, reject the request the same way nil-address requests are already rejected in `HandleControlMsg`.
