## Confirmed: StackerDB chunk signatures are not bound to the contract they authorize

`SlotMetadata::auth_digest()` — the digest that `sign()`/`verify()` actually operate over — is computed only from `slot_id`, `slot_version`, and `data_hash`. It never includes the `QualifiedContractIdentifier` (the StackerDB contract/replica the chunk is meant for). [1](#0-0) 

`verify()` only checks that the recovered pubkey hash matches the `principal` passed in by the caller — it has no notion of "which StackerDB" the signature was scoped to. [2](#0-1) 

The write path, `StackerDBTx::try_replace_chunk`, resolves the expected signer purely from `(smart_contract, slot_desc.slot_id)` via `get_slot_validation`, and then calls `slot_desc.verify(&slot_validation.signer)` — the contract identifier is used only to select which signer address to check against, not as part of the signed material itself: [3](#0-2) 

The same lack of contract binding exists in the gossip validation path `PeerNetwork::validate_received_chunk`, which likewise only checks `(slot_id, slot_version, data_hash)` via `slot_metadata.verify(&addr)`: [4](#0-3) 

### Why this matters
If the same signer/stacker address is assigned the same `slot_id` in **two different StackerDB contracts** — which is common in this codebase, since Stacks signer sets are typically stable or overlapping across consecutive reward cycles and each reward cycle gets its own StackerDB contract (`signers-N-1`, `signers-N-2`, etc.) — then a `StackerDBChunkData` (slot_id, slot_version, sig, data) that was legitimately signed and broadcast for contract A can be **replayed verbatim by any unprivileged network peer against contract B**. Both the HTTP write endpoint (`/v2/stackerdb/:principal/:contract/chunks`, `RPCPostStackerDBChunkRequestHandler`) and the P2P gossip path only ever check the tuple `(slot_id, slot_version, data_hash)` under that contract's own current version counter — they never verify the signature was intended for *this* contract. As long as `slot_version` clears contract B's freshness check (`slot_version <= slot_validation.version` per `try_replace_chunk`), replay succeeds and overwrites arbitrary content into a different StackerDB replica than the signer intended.

This is a direct structural analog of the report's core defect: a signature that omits a scoping/context field ("to" contract equivalent) from what it authenticates, permitting cross-context replay with no interaction from the legitimate signer and no possession of any private key.

I could not fully verify from the index whether current reward-cycle signer sets are *guaranteed* to overlap on slot indices across contracts (this depends on runtime reward-set assignment logic which lives outside the files this scan is scoped to), so the practical likelihood depends on that overlap occurring, which the protocol does not prevent.

### Title
StackerDB chunk signatures omit the target contract, enabling cross-StackerDB signature replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` signs only `(slot_id, slot_version, data_hash)`, never the target `QualifiedContractIdentifier`. Both the HTTP chunk-write handler and the P2P `validate_received_chunk`/gossip path verify signatures using only this digest and the signer address resolved for the *local* contract, without checking that the signature was originally produced for that specific contract. Any relaying peer can therefore replay a previously-broadcast, validly-signed `StackerDBChunkData` from one StackerDB replica into a different StackerDB replica in which the same address happens to hold the same `slot_id`, causing an unauthorized write of stale/foreign data into that replica.

### Finding Description
The signing/verification contract is:
- `auth_digest()`: hashes `slot_id || slot_version || data_hash` only [1](#0-0) 
- `verify(principal)`: recovers the pubkey from that digest and compares its hash to `principal` [2](#0-1) 

`principal` (the expected signer) is looked up per-contract via `get_slot_validation`/`get_slot_signer`, but this lookup only determines *whose* signature is expected for slot N in contract C — it does not make the signed message itself contract-specific. So a signature that recovers correctly to address X's slot N in contract A will *also* verify successfully against contract B's slot N, provided address X also owns slot N there.

Both write paths rely solely on this insufficiently-scoped check:
- The write/insert path: `try_replace_chunk` checks signer, staleness (`slot_version <= slot_validation.version`), and max-writes — all keyed by `(contract, slot_id)`, but the signature itself carries no contract binding. [5](#0-4) 
- The gossip acceptance path: `validate_received_chunk` performs the same signer/version checks with the same digest. [6](#0-5) 
- The RPC endpoint deserializes attacker-supplied JSON directly into `StackerDBChunkData` and forwards it into `try_replace_chunk` for whatever `contract_identifier` is in the URL path, with no additional binding check. [7](#0-6) 

### Impact Explanation
This falls under "unauthenticated/unauthorized write to state or StackerDB" (Critical) and "network-wide propagation of forged data": an attacker with no keys and no privileged role can take a chunk they observed on the wire (broadcast legitimately for contract A) and submit it — via the public POST `/v2/stackerdb/.../chunks` RPC endpoint or via P2P `StackerDBPushChunk` gossip — to a different StackerDB contract B where it passes signature verification, causing contract B's slot to be overwritten with data that was never authorized for B. Depending on which StackerDB replicas overlap on signer/slot assignment (e.g., consecutive-reward-cycle signer contracts, or other StackerDBs sharing a signer set), this can corrupt data other nodes treat as canonical signer/miner coordination state.

### Likelihood Explanation
Exploitation requires no secret material — only observing one legitimate chunk broadcast and knowing/discovering a second StackerDB contract where the same address occupies the same `slot_id` with a lower stored version. Reward-cycle StackerDB contracts in this codebase are provisioned per-cycle with signer-to-slot assignments that can and often do overlap across adjacent cycles/contracts sharing similar signer sets, making the precondition realistic rather than purely theoretical. I could not confirm from the indexed files exactly how often slot-id assignments coincide across different StackerDB contracts at runtime (that logic sits in signer-set/reward-set computation outside this scan's scope), so likelihood is contingent on that overlap.

### Recommendation
Include the `QualifiedContractIdentifier` (or equivalently a unique StackerDB instance identifier) inside `SlotMetadata::auth_digest()` so that a signature is cryptographically bound to the specific StackerDB it was produced for. This mirrors the report's recommended fix of adding a distinguishing/nonce-like field to the signed payload to prevent cross-context replay.

### Proof of Concept
1. Set up two StackerDB contracts, A and B, where signer address `X` is assigned `slot_id = 0` in both (feasible when contracts share overlapping reward-cycle signer sets).
2. `X` legitimately signs and posts a `StackerDBChunkData{slot_id: 0, slot_version: 1, data, sig}` to contract A via `POST /v2/stackerdb/A/chunks`; it is accepted (`try_replace_chunk` succeeds) and relayed via gossip as `StackerDBPushChunk`.
3. An unprivileged attacker observing this chunk (from the HTTP response or P2P gossip) resubmits the exact same `StackerDBChunkData` (unmodified `slot_id`, `slot_version`, `sig`, `data`) to contract B: `POST /v2/stackerdb/B/chunks`.
4. In `try_replace_chunk`, `get_slot_validation(B, 0)` resolves signer `X` (assumed same assignment); `slot_desc.verify(&X)` succeeds because the digest never referenced contract A or B; if B's current stored version for slot 0 is `< 1`, the write succeeds, storing A's chunk data into B's slot 0 — an unauthorized cross-contract write the signer never approved for B.         let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(

            &self.signature,
