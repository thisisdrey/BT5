## Finding

**Title:** Relayer reward is marked paid and permanently unrecoverable if the remote `DepositAsset` on AssetHub fails (frozen/unqualified beneficiary) - (`bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`pallet-bridge-relayers`'s `do_claim_rewards`/`claim_rewards_to` removes the relayer's accrued reward from storage as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge, `pay_reward` is implemented by `PayAccountOnLocation::pay_reward`, which only guarantees that an XCM program was *sent* to AssetHub — not that the `DepositAsset` instruction inside it actually succeeds on AssetHub. If the beneficiary location cannot receive the deposit (frozen account, filtered asset, insufficient ED, etc. — the exact functional analog of "USDC blacklist"), the funds get trapped in the XCM holding register under an origin that the relayer generally cannot reconstruct or sign for, while the pallet has already deleted the claim record on BridgeHub. This mirrors the report's core defect: state is optimistically finalized on the "sending" side before the destination-side transfer is confirmed, and a receiver-side rejection permanently strands the funds.

### Finding Description
- `do_claim_rewards` in `bridges/modules/relayers/src/lib.rs` uses `try_mutate_exists` around a single call to `T::PaymentProcedure::pay_reward`; only an `Err` from `pay_reward` rolls back the reward-removal. [1](#0-0) 
- `PayAccountOnLocation::pay_reward` (used for `BridgeReward::Snowbridge`) builds an XCM ending in `DepositAsset { assets: AllCounted(1).into(), beneficiary }`, `validate_send`s it, charges delivery fees, and calls `XcmSender::deliver(ticket)`; it returns `Ok(())` the moment the message is handed to the router — the actual execution (and thus the `DepositAsset`) happens later, asynchronously, on AssetHub. [2](#0-1) 
- Crucially, unlike the inbound-queue-v2 message converter (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`), which explicitly sets `SetHints { hints: [AssetClaimer { location: message.claimer }] }` *before* placing bridged assets in holding so that any downstream failure traps funds under a claimer the recipient can reconstruct and sign for, [3](#0-2) 
the reward-payment XCM built in `reward.rs` never sets `SetHints`/`AssetClaimer`, and never issues `ClearOrigin`. If the `DepositAsset` on AssetHub fails, `post_process` traps the leftover holding under `self.asset_claimer.or(self.context.origin).unwrap_or(original_origin)` — i.e. the descended bridge/Ethereum-universal origin (`DescendOrigin(InboundQueueLocation) + UniversalOrigin(Ethereum)`), not the relayer's own account. [4](#0-3) 
- This is exactly the class of bug already remediated once in this codebase (PR fixing the fallback claimer's network so `claim_assets` could match the trap key), showing the project is aware that a mismatched/unreachable trap origin makes funds "effectively unrecoverable without a runtime upgrade." [5](#0-4) 
- The relayer reward storage entry, however, is already deleted by the time this trap happens (`do_claim_rewards` treats `deliver()` success as final settlement), so the relayer has no second avenue to re-claim.

### Impact Explanation
A relayer's earned bridge reward can be silently and permanently lost even though `claim_rewards_to` returned success and emitted `RewardPaid`. This is a fund-loss / permanent-lock bug (the reward tokens end up trapped under a system-level origin the relayer cannot reproduce with a signed origin) — it degrades the incentive mechanism that keeps Snowbridge message delivery running, aligning with the "permanent user-fund lock" and "duplicate settlement/payout" impact categories in scope.

### Likelihood Explanation
Medium: it requires the beneficiary location supplied to `claim_rewards_to` (an `AssetHubLocation`, freely chosen by the caller) to fail `DepositAsset` on AssetHub — e.g. a location resolving to a frozen/filtered account, an account below ED for the foreign WETH-derivative asset, or one rejected by `SafeCallFilter`/`Barrier` at the destination. Any relayer that mistypes or reuses a since-frozen/removed beneficiary triggers it without needing any privileged, malicious, or off-chain actor.

### Recommendation
- Mirror the inbound-queue-v2 pattern: add `SetHints { hints: [AssetClaimer { location: beneficiary.clone() }] }` (or the relayer's own account) to the reward-payment XCM in `PayAccountOnLocation::pay_reward` so that any deposit failure traps the reward under a location the relayer can sign for and reclaim via `pallet_xcm::claim_assets`.
- Alternatively/additionally, do not treat `deliver()` success as final settlement in `do_claim_rewards`; require an acknowledgement (e.g. via XCM query/response) before permanently deleting the `RelayerRewards` entry, or keep a recovery path (re-credit) if the remote execution is later observed to fail.

### Proof of Concept
1. Relayer accrues a reward via `register_reward` for `BridgeReward::Snowbridge`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(some_location))` where `some_location` resolves on AssetHub to an account that is frozen for the WETH-derivative asset (or otherwise fails `TransactAsset::deposit_asset`, e.g. below ED with no other qualifying asset in the same `DepositAsset`).
3. `do_claim_rewards` invokes `PayAccountOnLocation::pay_reward`, which builds and successfully `deliver()`s the XCM to AssetHub; `pay_reward` returns `Ok(())`, `RelayerRewards` entry is removed, `RewardPaid` event is emitted.
4. On AssetHub, the XCM executes: `ReserveAssetDeposited` succeeds, but `DepositAsset` to the frozen/disqualified beneficiary fails; since no `AssetClaimer` hint was set, `post_process` traps the reward asset under the descended `InboundQueueLocation`/`UniversalOrigin(Ethereum)` origin.
5. The relayer cannot construct a signed origin matching that trap key on AssetHub, so `pallet_xcm::claim_assets` cannot recover the funds — the reward is permanently lost despite `RewardPaid` having already fired on BridgeHub.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

title: 'Snowbridge: Set default asset claimer to local network'
doc:
- audience: Runtime Dev
  description: |-
    The inbound-queue v2 message converter falls back to the Snowbridge sovereign
    account on AssetHub as the asset claimer when no explicit claimer is supplied.
    Previously this fallback used `AccountId32 { network: None, .. }`, which did
    not match the location AssetHub's signed-origin converter produces (it sets
    `network: Some(LocalNetwork)`). The trap-key hash stored on `AssetsTrapped`
    therefore could not be matched by a signed `polkadotXcm.claim_assets` call,
    making default-claimer trapped funds effectively unrecoverable without a
    runtime upgrade.

    This PR sets `network: Some(LocalNetwork::get())` on the fallback claimer so
    its `Location` agrees with what `SignedToAccountId32<_, _, LocalNetwork>`
    yields on AssetHub, and adds a test covering the no-claimer-supplied path.
