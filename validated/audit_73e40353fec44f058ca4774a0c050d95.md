Audit Report

## Title
`ERC20Transactor` trusts nominal transfer amount instead of verified balance delta, allowing unbacked XCM asset credit from fee-on-transfer/deflationary tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls an ERC20-like contract's `transfer()` and, if it returns `true` without reverting, unconditionally credits `Erc20Credit(amount)` — the caller-specified nominal amount — into the XCM holding register, without ever checking the actual balance change on `TransfersCheckingAccount`. The companion `deposit_asset_with_surplus` has the symmetric flaw on withdrawal-out. Because `ERC20Matcher` accepts any `H160`/`AccountKey20` address as a valid fungible asset id, any unprivileged user can deploy a fee-on-transfer/deflationary ERC20-like contract via `pallet_revive` and mint unbacked XCM holding credit.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` moving `amount` from `who` to `TransfersCheckingAccount`, then, upon decoding a `true` boolean return (and no revert), mints `Erc20Credit(amount)` into holding using the nominal requested `amount`: [1](#0-0) [2](#0-1) 

`deposit_asset_with_surplus` has the symmetric issue: it transfers nominal `amount` out of the checking account and treats a decoded `true` as full success without checking that the beneficiary actually received `amount`: [3](#0-2) [4](#0-3) 

The matcher used by `ERC20Transactor` in the Asset Hub Westend runtime, `ERC20Matcher`, is defined generically to accept *any* local `AccountKey20` location as a valid fungible asset id, with no allow-list or registration check: [5](#0-4) 

and is wired directly into the runtime's `AssetTransactors`: [6](#0-5) 

Since `pallet_revive` contract instantiation is a public, permissionless extrinsic, any unprivileged user can deploy an ERC20-like contract whose `transfer()` implementation forwards `amount - fee` to the recipient while still returning `true`, and immediately use that contract's address as an `AccountKey20` asset id in an XCM program (via `pallet_xcm::execute` or similar). The existing revert/decode-failure guards only catch reverts and malformed non-bool returns — they do nothing to detect a contract that validly returns `true` while moving less value than requested, which is precisely the flaw class described.

## Impact Explanation
The XCM holding register is credited with `Erc20Credit(amount)` that is not fully backed by the real balance change on `TransfersCheckingAccount`. Because this credit lives in the same holding register used by subsequent XCM instructions in the same program (e.g. `ExchangeAsset` against a real liquidity pool, or `DepositAsset`/`InitiateReserveWithdraw`), the phantom credit can be converted into real backed value, constituting an unbacked-mint/theft primitive against pool liquidity or other real assets in the runtime's holding register — an impact aligned with the Polkadot SDK gate's "theft or unbacked mint" category.

## Likelihood Explanation
High. `pallet_revive` contract deployment is a public, unprivileged extrinsic, and `pallet_xcm::execute` is a public entry point on chains enabling `ERC20Transactor` (e.g., Asset Hub Westend). Writing a fee-on-transfer contract that returns `true` on `transfer()` while forwarding less than the requested `value` is a standard, trivial pattern requiring no special access, and the `ERC20Matcher` places no restriction on which contract addresses can be used as asset ids.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query the ERC20 `balanceOf` of the receiving account (`TransfersCheckingAccount` on withdraw, beneficiary on deposit) immediately before and after the `bare_call`, and credit/treat-as-transferred only the observed delta instead of the nominal requested `amount`. Reject or adjust the XCM operation when the delta does not match the requested amount.

## Proof of Concept
1. Deploy a PolkaVM/Solidity contract via `pallet_revive` implementing `IERC20` where `transfer(to, value)` moves `value - fee` to `to`, retains `fee`, and returns `true`.
2. Use this contract's address directly as an `AccountKey20` asset id — `ERC20Matcher`/`IsLocalAccountKey20` accepts it without any allow-list check (`cumulus/parachains/runtimes/assets/common/src/lib.rs:132-160`).
3. Submit `pallet_xcm::execute` with `WithdrawAsset((AccountKey20{key: attacker_token}, amount))` followed by `ExchangeAsset`/`DepositAsset`.
4. Observe `withdraw_asset_with_surplus` credit the full nominal `amount` into holding (`erc20_transactor.rs:195-203`) even though `TransfersCheckingAccount`'s real ERC20 balance only increased by `amount - fee`.
5. The subsequent instruction consumes the full nominal credit against real assets, extracting value never actually deposited.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
