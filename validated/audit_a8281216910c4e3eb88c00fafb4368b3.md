## Title
Vault-side scaled-debt reduction in `system-repay` uses a different rounding formula than the market's per-account scaled-debt reduction, causing aggregate vault debt to permanently drift above the sum of individual obligations - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every Zest vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` equivalents) tracks aggregate debt as `principal-scaled` and derives `total-debt()` via `calc-cumulative-debt`. Per-account debt is tracked separately in `v0-market-vault.clar` as scaled units computed via the standard `amount * INDEX-PRECISION / index` formula. On `borrow()` both layers use the identical rounding formula, so they stay in sync. On `repay()`, however, the vault computes the aggregate scaled-debt reduction with a *different* formula (`calc-principal-ratio-reduction`, a ratio of the repaid amount against the rounded‑up `total-debt()`) instead of reusing the standard `amount * INDEX-PRECISION / index` conversion that the market layer used to remove the account's own scaled debt. Because `total-debt()` is computed with `mul-div-up` (round up), the vault's ratio-based reduction is systematically **less than or equal to** the market's per-account reduction for every partial repayment, so the vault's aggregate `principal-scaled` drifts upward relative to the true sum of individually tracked obligations. This is the same class of bug as the referenced Mochi finding: two independent code paths incrementing/decrementing "debt" with formulas that are not mathematically identical, leaving a persistent, uncorrectable phantom balance.

### Finding Description
`borrow()` in the market computes the scaled debt added to a specific account using: [1](#0-0) 
and the vault's own `system-borrow` computes the aggregate scaled increase with the identical formula and the same cached index: [2](#0-1) 
so on the borrow path, aggregate and per-account scaled debt stay perfectly consistent.

On the repay path, the market computes the scaled amount to remove from the specific account with the same standard formula: [3](#0-2) 

But the vault's `system-repay` does **not** reduce its aggregate `principal-scaled` using that same formula. Instead it derives the reduction from a ratio against `total-debt()`: [4](#0-3) 

`calc-principal-ratio-reduction` and `calc-cumulative-debt` are defined as: [5](#0-4) 

`debt` = `total-debt()` = `mul-div-up(principal-scaled, idx, INDEX-PRECISION)` — rounded **up**. Consequently:

`scaled-principal / debt ≤ INDEX-PRECISION / idx`

with strict inequality whenever `principal-scaled * idx` is not exactly divisible by `INDEX-PRECISION` (which is virtually always true once interest has accrued, since `idx` grows by a compounding multiplier). Therefore, for the same token `amount` repaid:

`calc-principal-ratio-reduction(amount, scaled-principal, debt) = floor(amount * scaled-principal / debt) ≤ floor(amount * INDEX-PRECISION / idx)`

which is exactly the scaled amount the market removed from the specific account's ledger via `debt-remove-scaled`: [6](#0-5) 

So on every partial repayment, the vault's aggregate `principal-scaled` shrinks by an amount that is less than or equal to what the market ledger removed from the borrower's individual scaled debt. The gap is not refunded anywhere else in the system, so it accumulates call after call, across every borrower and every partial repayment on the vault.

### Impact Explanation
`total-debt()` (driven by the drifting `principal-scaled`) directly feeds:
- `utilization()` → `interest-rate()`, so all borrowers/depositors are charged interest against an inflated utilization figure over time: [7](#0-6) 
- `total-assets()`/`total-assets-preview()`, which value LP shares (zTokens) as `current-assets + max(0, debt - borrowed)`. Because `debt` never converges to the true sum of borrower obligations (it stays inflated) while `borrowed` and per-user `debt` in the market ledger do reach zero when users fully exit, the vault's reported `total-assets` becomes permanently and increasingly overstated relative to real backing assets: [8](#0-7) 
- `calc-treasury-lp-preview`/`accrue`, which mints treasury LP shares proportional to the (miscomputed) debt delta, further diluting/misallocating claims on vault assets: [9](#0-8) 

An overstated `total-assets` inflates the redemption value of every LP share. Early redeemers can extract more underlying than is actually backed by real, collectible interest, at the expense of depositors who redeem later — this is a temporary/permanent freezing of funds and a path to protocol insolvency for the vault's liquidity providers, entirely as a consequence of ordinary, unprivileged `repay()` calls.

### Likelihood Explanation
This requires no privileged access and no unusual conditions: any ordinary borrower calling `repay()` with a partial amount (i.e., not paying off their entire scaled debt in one transaction, which is a normal, common usage pattern) triggers the divergence. The drift is monotonic (never self-corrects) and compounds with every partial repayment across every borrower on every vault, so it will manifest under normal, expected protocol usage over time.

### Recommendation
Make the vault's aggregate scaled-debt reduction in `system-repay` mathematically identical to the conversion used by the market layer (and to the inverse of the `system-borrow` formula), e.g. compute `scaled-amount-removed = mul-div-down(capped-amount, INDEX-PRECISION, idx)` directly from the current index rather than via a ratio against the rounded `total-debt()`. Alternatively, have the market pass the already-computed `repaid-scaled-debt` (in scaled units) into `system-repay` so both ledgers are decremented by the exact same value, mirroring how `scaled-debt-added`/`scaled-amount` are kept consistent on the borrow path.

### Proof of Concept
1. A single account borrows an amount, producing `principal-scaled = P` in the vault and `account-scaled-debt = P` in `v0-market-vault`.
2. Time passes so the interest index `idx` grows to a value that is not an exact multiple relationship with `P` (the normal case, since `idx` compounds continuously) — this guarantees `total-debt() = mul-div-up(P, idx, INDEX-PRECISION)` rounds strictly upward, i.e. `debt = ceil(P*idx/INDEX-PRECISION) > P*idx/INDEX-PRECISION`.
3. The borrower calls `repay(ft, amount, none)` with `amount` smaller than their full owed debt (a partial repayment).
   - Market computes `scaled-debt-repayment = mul-div-down(amount, INDEX-PRECISION, idx)` and removes this from the account's ledger: [10](#0-9) 
   - The resulting `amount-to-repay` is forwarded to the vault's `system-repay`, which instead computes `principal-reduction = mul-div-down(amount-to-repay, P, debt)`: [11](#0-10) 
4. Because `P/debt < INDEX-PRECISION/idx` (from step 2), `principal-reduction < scaled-debt-repayment`, so the vault's `principal-scaled` decreases by strictly less than the market ledger's scaled debt for that account.
5. Repeat over many partial repayments/borrowers: the vault's `principal-scaled` (and `total-debt()`) permanently overstates the true sum of borrower obligations. `total-assets()` reported by the vault is inflated by this residual "phantom debt," inflating LP share redemption value and eventually causing insolvency for the vault's remaining depositors.
