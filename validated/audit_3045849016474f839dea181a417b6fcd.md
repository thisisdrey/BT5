### Title
Stale/uninitialized `accountIndexOf` treated as index `0` lets an existing holder harvest rewards equal to their full deposit balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The Chrome report is a use-after-free: code operates on an object whose backing state was freed/reset and then reuses the stale handle. The closest reachable analog in Metronome is in `RewardsDistributor._calculateTokenDelta`, which reads a per-account reward index that may never have been written (effectively "freed"/uninitialized storage, value `0`) and computes a reward delta against it. When a reward `TokenState` is freshly initialized to `INITIAL_INDEX` (`1e18`) — i.e., the token entry exists but the global index has not yet grown past it — the fallback that protects against index `0` does not fire, because the guard only substitutes `INITIAL_INDEX` when `_tokenIndex > INITIAL_INDEX`. [1](#0-0) 

### Finding Description
`_calculateTokenDelta` computes:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When `updateTokenSpeed`/`syncTokenSpeed` first activates a token, `_updateTokenSpeed` stores `TokenState({index: INITIAL_INDEX, timestamp: now})` and pushes the token — but it never initializes `accountIndexOf[token_]` for existing holders. [2](#0-1) 

In the window where `tokenStates[token_].index == INITIAL_INDEX` (i.e., `_deltaTimestamps == 0` — the same block/timestamp in which the speed was set, before any index growth), an account whose `accountIndexOf` is still `0` gets:

- `_accountIndex = 0` (the `> INITIAL_INDEX` guard fails, since `_tokenIndex == INITIAL_INDEX`)
- `_deltaIndex = 1e18 - 0 = 1e18`
- `_tokensDelta = balanceOf(account).wadMul(1e18) = balanceOf(account)`

So a holder's *entire* deposit/debt-token balance is credited as accrued reward on their very first index update — which happens automatically on any mint/burn/transfer via `updateBeforeMintOrBurn`/`updateBeforeTransfer` hooks in `DepositToken`/`DebtToken`, or even permissionlessly via `updateBeforeMintOrBurn` ("may be called by anyone to update stored indexes") or `claimRewards`. [3](#0-2) 

The accrued amount is then paid out in `rewardToken` up to the distributor's balance by `_transferRewardIfEnoughTokens`. [4](#0-3) 

### Impact Explanation
An attacker deposits (or already holds) a large deposit-token/debt-token balance before a reward speed is activated. In the same timestamp as the governor's `updateTokenSpeed`/`syncTokenSpeed` call that sets `index = INITIAL_INDEX`, the attacker triggers `_updateTokensAccruedOf` — e.g., by calling `claimRewards(attacker, [token])` or by performing a dust transfer. Their `tokensAccruedOf` jumps to their full token balance, and `claimRewards` immediately transfers `rewardToken` (e.g., MET/OP) equal to `min(balance, distributorBalance)`. This is direct theft of the reward pool's funds using only public entry points — an exact analog of using stale/freed state (index `0`) as if it were a valid initialized index. [5](#0-4) 

### Likelihood Explanation
The exploit window is narrow: it requires `tokenStates[token].index == INITIAL_INDEX` and `timestamp` unchanged, i.e., the same `block.timestamp` as the speed-setting transaction. On chains where the governor executes via a timelock/multisig whose tx lands in a predictable block, an attacker can bundle or back-run the governance tx (e.g., via a private relay or same-block MEV on L2s like Base/Optimism where Metronome is deployed) and trigger the accrual in the same timestamp. No privileged role is needed for the attack leg itself: depositing collateral and calling `claimRewards`/`updateBeforeMintOrBurn` are all unprivileged. Additionally, every *other* holder with `accountIndexOf == 0` whose balance updates in that window gets the same erroneous accrual, compounding the drain. Reward pools are routinely funded on deployed distributors, so the payoff is real.

Caveat: if the deployment never re-activates a reward token (all `tokenStates` already past `INITIAL_INDEX`), the bug is latent only — the fix should still be applied since `syncTokenSpeed` can re-initialize tokens whose index exists but whose accounts were never touched.

### Recommendation
In `_calculateTokenDelta`, treat any uninitialized `accountIndexOf` as the token's *initial* index unconditionally, not only when the global index has already advanced:

```solidity
if (_accountIndex == 0) {
    _accountIndex = INITIAL_INDEX; // or: _tokenIndex, to skip accrual entirely
}
```

Equivalently, initialize `accountIndexOf[token_][account_] = INITIAL_INDEX` lazily whenever `tokenStates[token_].index == INITIAL_INDEX`. Also consider having `_updateTokensAccruedOf` skip accrual when `_deltaIndex == 0` semantics can't be proven (i.e., `accountIndex` was just seeded). Re-run the reward-accounting invariant tests after the change.

### Proof of Concept
Hardhat sketch against `contracts/RewardsDistributor.sol`:

```ts
it('credits full balance as rewards when accountIndex is uninitialized', async () => {
  // Setup: alice deposits collateral -> holds msdMET balance
  await depositToken.connect(alice).deposit(parseEther('1000'), alice.address);
  await rewardToken.mint(distributor.address, parseEther('10000'));

  // Governor activates rewards for the deposit token (index = INITIAL_INDEX, timestamp = now)
  await distributor.updateTokenSpeed(depositToken.address, parseEther('1'));

  // Same block/timestamp: alice's accountIndexOf[token][alice] == 0
  // _tokenIndex == INITIAL_INDEX (1e18), guard `> INITIAL_INDEX` fails
  // _deltaIndex = 1e18 => _tokensDelta = 1000e18
  await distributor.connect(alice).claimRewards(alice.address, [depositToken.address]);

  // tokensAccruedOf[alice] == balanceOf(alice) == 1000e18, paid out in rewardToken
  expect(await rewardToken.balanceOf(alice.address)).to.eq(parseEther('1000'));
});
```

The key invariant break is reward-accrual correctness: a stale `accountIndexOf == 0` is interpreted as "account participated since index 0" instead of "account was never tracked," minting unearned claims equal to the user's full balance.
