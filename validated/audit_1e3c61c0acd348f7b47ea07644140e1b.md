### Title
Re-disabling `ALLOW_CHANGE_DELEGATION` after activation freezes already-accrued staker rewards - ([File: actuator/src/main/java/org/tron/core/utils/ProposalUtil.java])

### Summary
The `ALLOW_CHANGE_DELEGATION` chain parameter gates the "new" cycle-based delegation/reward-accounting algorithm used by `MortgageService`. Unlike almost every other feature-activation flag in `ProposalUtil` (which are hard-locked to only ever transition `0 -> 1`), `ALLOW_CHANGE_DELEGATION` is explicitly allowed to be set to either `0` or `1` at any time via a committee proposal, i.e. it can be turned back off after being turned on.

### Finding Description
`ProposalUtil.validator()` validates parameter changes proposed by Super Representatives/committee members. For most "allow" style flags the validation only permits `value == 1` (one-way activation), for example `ALLOW_DELEGATE_RESOURCE`, `ALLOW_MULTI_SIGN`, `ALLOW_NEW_RESOURCE_MODEL`, etc. `ALLOW_CHANGE_DELEGATION`, however, is validated with: [1](#0-0) 
allowing it to be toggled to `0` again after it was previously `1`.

This flag is read unconditionally, and with no fallback, at the very entry of the core reward-sync logic in `MortgageService`: [2](#0-1) [3](#0-2) 
When `allowChangeDelegation()` is `false`, both `withdrawReward()` and `queryReward()` return immediately without running `computeReward()`/`adjustAllowance()`/updating `beginCycle`/`endCycle`. These two methods are exactly the ones invoked by the publicly broadcastable `WithdrawBalanceContract`: [4](#0-3) [5](#0-4) 
so validation even blocks the withdrawal (`witnessAccount does not have any reward`) if `queryReward()` short-circuits to `0`/stale allowance while the newer, not-yet-synced cycle rewards computed with `delegationStore` Vi accounting sit unclaimed.

Additionally, the DPoS block-reward path `IncentiveManager.reward()` uses the *same* flag inverted as a gate for the old standby-witness payout logic: [6](#0-5) 
so flipping the flag also changes which reward-accounting path is executed during block application in `Manager`, meaning a governance toggle changes both the historical claim path and the ongoing accrual path simultaneously, exactly analogous to the reported oracle-disabling bug where an admin action makes historical reward math unreachable/inconsistent.

This is structurally the same bug class as the reported Middleware issue: a single mutable, governance-controlled switch that downstream reward-claim logic depends on unconditionally, and that (unlike its sibling flags) is *not* protected against being reverted after activation, so a later proposal can strand user rewards that were computed under the "on" state.

### Impact Explanation
While the flag is toggled to `0` after having been `1`, any staker/witness whose reward accrual for the current or a prior un-synced cycle depends on the new Vi-based algorithm cannot have that portion of their reward moved into `allowance`, and thus cannot withdraw it via `WithdrawBalanceContract`/`withdrawReward()` TVM opcode paths. Funds are not stolen but become temporarily/indefinitely unclaimable for as long as governance keeps the flag disabled — a funds-freezing condition reachable purely through the standard, unprivileged withdraw-balance transaction combined with a governance-level configuration change, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Low-to-medium: requires a committee-approved proposal to explicitly set `ALLOW_CHANGE_DELEGATION` back to `0` after it has been enabled (a coordinated/majority governance action, not a single malicious tx), so likelihood mirrors the "Low" likelihood rated in the source report for the analogous oracle-removal scenario.

### Recommendation
Treat `ALLOW_CHANGE_DELEGATION` like the other one-way activation flags in `ProposalUtil` (only allow `0 -> 1`, never `1 -> 0`), or, if a genuine "pause" capability is required, make `MortgageService`/`IncentiveManager` continue to correctly sync and expose already-accrued rewards for historical cycles regardless of the current flag value (e.g., only gate the switch of *newly accrued* cycles onto the algorithm, never gate withdrawal/query of already-computed rewards).

### Proof of Concept
1. Committee activates `ALLOW_CHANGE_DELEGATION` via a `ProposalCreateContract`/`ProposalApproveContract` (allowed since `value != 1 && value != 0` is the only check) — normal reward accrual/withdrawal proceeds through `MortgageService.withdrawReward`/`queryReward`.
2. A staker accumulates un-synced reward across multiple cycles (`beginCycle < currentCycle`) without withdrawing.
3. Committee submits/approves a new proposal setting `ALLOW_CHANGE_DELEGATION = 0` (permitted per `ProposalUtil.java:253-262`, unlike every other one-way flag).
4. The staker broadcasts a `WithdrawBalanceContract`; `WithdrawBalanceActuator.validate()` calls `mortgageService.queryReward()` which now returns immediately with `0`/stale allowance (`MortgageService.java:136-139`), so if `accountCapsule.getAllowance() <= 0` the transaction is rejected with "witnessAccount does not have any reward" even though real, computed-but-unsynced reward exists in `delegationStore`.
5. The staker's reward for the affected cycles remains frozen until/unless governance re-enables the flag, entirely outside the staker's control.
