### Title
Attacker-crafted `Operator.execute` payload drains victim's unlocked deposit collateral — ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` lets any caller run arbitrary `(target, value, callData)` calls while `SynthContext._msgSender()` resolves to the EOA that signed the transaction (stored in the `MSG_SENDER` transient slot). Because there is no allowlist on targets or calldata, an attacker can craft an `execute` batch — e.g. `DepositToken.transfer(attacker, unlockedBalance)` or `DepositToken.withdraw(amount, attacker)` — that silently moves the signer's funds. Any user tricked into broadcasting such a payload (the analog of clicking a crafted link) has their account credentials/identity used against them, matching the crafted-link → credential-misuse bug class.

### Finding Description
`Operator.execute` stores `msg.sender` in `MSG_SENDER_STORAGE` and then performs unrestricted external calls via `functionCallWithValue` [1](#0-0) . Every protocol contract resolves the effective sender through `SynthContext._msgSender()`, which returns the stored EOA whenever `msg.sender == operator` [2](#0-1) . 

`DepositToken.transfer` sends `_msgSender()`'s tokens to an arbitrary `to_` with only the `unlockedBalanceOf` check [3](#0-2) , and `withdraw` similarly burns the caller's shares and pays out to a chosen `to_` [4](#0-3) . Neither performs any additional authentication beyond `_msgSender()`, so an `execute` batch containing `transfer(attacker, unlockedBalanceOf(victim))` or `withdraw(amount, attacker)` executes as the victim.

The `nonReentrant` guard only prevents a callee from re-entering `execute`; it does not restrict which targets may be called, so the identity is legitimately forwarded to malicious payload choices.

### Impact Explanation
Direct theft of user funds: a victim who signs a single attacker-crafted `execute` transaction loses all unlocked deposit-token collateral (transferable or withdrawable underlying), any ETH sent, and can be made to perform arbitrary authenticated actions (e.g., `Pool.swap` at manipulated prices, `approve`, reward claims redirection via `RewardsDistributor.claimRewards`). Locked collateral is bounded by `unlockedBalanceOf`, but debt-free users lose their full balance.

### Likelihood Explanation
Requires user interaction — the victim must broadcast the crafted transaction — which matches the source bug class (crafted link requiring a user to follow it) and is a standard phishing vector for multicall/operator-style contracts. The Operator contract is deployed on all production chains and referenced by `SynthContext`, so the primitive is live. The risk is elevated because the batch is opaque calldata: a phishing dapp can present it as a routine "claim" or "deposit" action while embedding the drain calls.

### Recommendation
Restrict `execute` to an allowlisted set of targets/selectors (e.g., only registered Pool/gateway functions that are already user-initiated workflows), or require per-call user signatures (EIP-712) binding each call's intent. At minimum, block calls to `transfer`/`transferFrom`/`withdraw`/`approve` on `DepositToken`, `SyntheticToken`, and reward-claim functions when the resolved sender differs from the beneficiary, or surface a clearer signing payload in the UI so calldata intent is auditable.

### Proof of Concept
```solidity
// Foundry fork test — victim signs a tx crafted by attacker
function test_execute_drainsUnlockedCollateral() public {
    // victim has deposit tokens with no debt => fully unlocked
    uint256 amount = depositToken.unlockedBalanceOf(victim);
    assertGt(amount, 0);

    IOperator.Call[] memory calls = new IOperator.Call[](1);
    calls[0] = IOperator.Call({
        target: address(depositToken),
        value: 0,
        callData: abi.encodeCall(IERC20.transfer, (attacker, amount))
        // or: abi.encodeCall(IDepositToken.withdraw, (amount, attacker))
    });

    // victim is tricked into broadcasting this payload (crafted-link analog)
    vm.prank(victim);
    operator.execute(calls);

    assertEq(depositToken.balanceOf(attacker), amount);
    assertEq(depositToken.balanceOf(victim), 0);
}
```

        IPoolRegistry _poolRegistry = poolRegistry();
        if (address(_poolRegistry) != address(0)) {
            IOperator _operator = _poolRegistry.operator();
