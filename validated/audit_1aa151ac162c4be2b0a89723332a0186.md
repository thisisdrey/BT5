### Title
`VesperGateway.deposit()` reverts for fee-on-transfer underlying tokens, permanently blocking deposits for affected vTokens - ([File: contracts/VesperGateway.sol](https://github.com/Loderfordw/metronome-synth-public--015/blob/main/contracts/VesperGateway.sol#L44-L65))

### Summary
`VesperGateway.deposit()` pulls `amount_` of the vToken's underlying asset from the caller, then approves and calls `vToken_.deposit(amount_)` using the same nominal amount. With a fee-on-transfer underlying (e.g., PAXG, USDT-with-fee-enabled), the gateway receives `amount_ - fee`, so `vToken_.deposit(amount_)` reverts on its internal `transferFrom` / balance check. This is the same bug class as the Teller `CollateralManager._deposit()` report. Notably, `DepositToken.deposit()` already implements the correct balance-delta pattern (`balanceOf(treasury)` before/after at `DepositToken.sol:225-227`), as does `SmartFarmingManager._safeTransferFrom()` (`SmartFarmingManager.sol:257-261`) — `VesperGateway.deposit` is the remaining surface that does not.

### Finding Description
In `VesperGateway.deposit` (`contracts/VesperGateway.sol`):

```solidity
// 1. Get `underlying` asset
IERC20 _underlying = IERC20(vToken_.token());
_underlying.safeTransferFrom(_msgSender, address(this), amount_);

// 2. Deposit `underlying` to `VPool`
_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);
```

If `underlying` charges a transfer fee, the gateway's balance after step 1 is `< amount_`. Step 2 then approves `amount_` and calls `vToken_.deposit(amount_)`, which attempts to `transferFrom` the full `amount_` from the gateway and reverts (ERC20 insufficient balance). There is no balance-delta measurement of the underlying received — the `_balanceBefore`/`balanceOf` delta is only applied to the **vToken** side (lines 56-58), which is correct, but the upstream pull of `underlying` trusts the nominal `amount_`.

### Impact Explanation
Any whitelisted Vesper pool whose `token()` is (or becomes) a fee-on-transfer ERC20 can never be deposited through `VesperGateway.deposit` — every call reverts inside `vToken_.deposit()`. This is a permanent loss of the deposit functionality (liveness) for that collateral type through this gateway. No funds are stolen, but the flow is completely broken for the affected collateral. Severity matches the original Medium classification.

### Likelihood Explanation
- The path is reachable by any EOA: `VesperGateway.deposit` is permissionless, gated only by `isPoolRegistered(pool_)`, and `pool_.depositTokenOf(vToken_)` must be a registered deposit token.
- It requires a whitelisted collateral that is a Vesper vToken wrapping a fee-on-transfer underlying. This is conditional on a real-world token configuration (e.g., a Vesper pool over USDT if its fee is enabled, or STA/PAXG-like tokens), but that is exactly the precondition of the original report — the code is objectively non-functional for that token class.
- No governor/keeper action or oracle manipulation is needed to trigger the revert.

### Recommendation
Apply the same balance-delta pattern already used in `DepositToken.deposit` and `SmartFarmingManager._safeTransferFrom`:

```solidity
uint256 _underlyingBefore = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
amount_ = _underlying.balanceOf(address(this)) - _underlyingBefore;
```

Use the measured `amount_` for the approve and `vToken_.deposit(amount_)` calls. Alternatively, reuse a shared `_safeTransferFrom` helper consistent with `SmartFarmingManager`.

### Proof of Concept
Reproducible in the existing Hardhat test suite using `ERC20Mock`, which already supports a configurable transfer fee (`fee` scaled by `1e18` in `_transfer`, `contracts/mock/ERC20Mock.sol:73-80`) — the same mock used by the existing `DepositToken` fee-on-transfer test at `test/DepositToken.test.ts:433-449`.

```typescript
it('reverts when vToken underlying charges a transfer fee', async function () {
  // Setup: deploy ERC20Mock("TKN"), a mock VPool whose token() == TKN,
  // register a DepositToken for the vPool in the pool/registry.
  const erc20Factory = await ethers.getContractFactory('ERC20Mock')
  const tkn = await erc20Factory.deploy('Token', 'TKN', 18)

  // 10% transfer fee
  await tkn.updateFee(parseEther('0.1'))

  const amount = parseEther('100')
  await tkn.mint(alice.address, amount)
  await tkn.connect(alice).approve(vesperGateway.address, amount)

  // vPoolMock.token() == tkn.address ; depositTokenOf(vPool) registered
  const tx = vesperGateway.connect(alice).deposit(pool.address, vPoolMock.address, amount)

  // Gateway only received 90 TKN, but approves/calls vPool.deposit(100) -> revert
  await expect(tx).reverted // insufficient balance inside vToken.deposit's transferFrom
})
```

Steps:
1. `tkn.safeTransferFrom(alice, gateway, 100e18)` succeeds; gateway balance = 90e18.
2. `tkn.safeApprove(vPool, 100e18)` succeeds (approvals aren't balance-checked).
3. `vPool.deposit(100e18)` internally calls `tkn.transferFrom(gateway, vPool, 100e18)` → gateway holds only 90e18 → revert.

Uncertainty: `VPoolMock` in this repo would need its `token()`/`deposit()` wired to actually pull `amount_` via `transferFrom` to reproduce the revert faithfully; on a real fork against a live Vesper `VPool` (which performs `safeTransferFrom(msg.sender, address(this), amount)` internally), the revert occurs naturally.
