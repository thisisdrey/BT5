### Title
XOR-Based Repository Checksum Allows Reference-State Collisions Bypassing Concurrent-Modification and Replica-Consistency Checks - (File: internal/git/checksum.go)

### Summary
`git.Checksum` combines per-reference SHA-1 digests using **XOR** rather than a proper aggregate hash (e.g., feeding a sorted/ordered stream through a single hash function). Because XOR is linear and commutative over GF(2), the resulting "checksum" of a reference set is not collision-resistant against attacker-controlled inputs: different, non-equivalent sets of references can be engineered to XOR to the same value. This checksum is used as a security-relevant equality oracle in two places reachable via ordinary user actions: (1) `RewriteHistory`'s concurrent-modification guard, and (2) Praefect's replica-consistency verification/recovery logic. This mirrors the reported bug class where a linearly-combined "code" (`ownerPercent*DEMI + userPercent`) admits distinct inputs mapping to the same validation value, letting an adversary bypass a same-state check.

### Finding Description
`Checksum.Add`/`AddBytes` hash each allowed reference line (`name`, `target`) with SHA-1 and then XOR-fold them into a running `big.Int` sum: [1](#0-0) 

The test suite itself demonstrates the algebraic weakness: two identical reference entries cancel out under XOR, producing the exact same checksum as if those refs never existed: [2](#0-1) 

This is the direct analog of the reported vulnerability: just as `ownerPercent*DEMI + userPercent` is a linear combination where distinct `(ownerPercent, userPercent)` pairs collide to the same `code`, XOR-folded SHA-1 digests are a linear combination over GF(2) where distinct reference sets can collide to the same checksum. An attacker who controls ref names and target OIDs (any push access) can pick reference names/targets so that `H(refA) XOR H(refB) == H(refC) XOR H(refD)` for a completely different pair of refs, or so that adding/removing a crafted pair of refs leaves the aggregate checksum unchanged while the actual repository state differs.

This checksum is exposed via the `CalculateChecksum` RPC: [3](#0-2) 

and is relied upon as an authoritative "is the repository unchanged / is this replica in sync" signal in at least two security-relevant flows:

1. **RewriteHistory concurrent-modification guard** — `internal/gitaly/service/cleanup/rewrite_history.go` computes an `initialChecksum` before running `git-filter-repo`, and re-checks it against `validationChecksum` afterwards, aborting only if they differ: [4](#0-3) 
RewriteHistory is explicitly a sensitive operation intended to permanently strip blobs/redact content (e.g., to remove leaked secrets). If a repository owner or collaborator can push a crafted set of concurrent ref updates whose checksum collides with the pre-rewrite checksum, the abort safeguard is defeated, and the rewrite proceeds even though the source repository state actually changed mid-operation, risking incomplete removal or reintroduction of the very content the RPC was meant to purge.

2. **Praefect replica-consistency checks** — the same checksum is compared directly for equality to decide whether replicas are up to date, both during transaction recovery and general replication verification: [5](#0-4) [6](#0-5) 
A checksum collision here would let two genuinely divergent repository states be treated as identical, causing Praefect to mark an out-of-date replica as consistent (skipping replication) or to advance generation counters incorrectly, which is a repository-consistency/silent-corruption bypass.

### Impact Explanation
This maps to the "concrete storage escape / cross-repository object access / hook or quarantine bypass" family required by the validation rules, specifically as a **safety-check bypass via algorithmic collision**, analogous to the pool-code collision. Concretely:
- Bypassing the `RewriteHistory` concurrent-modification abort lets an attacker with ordinary push access defeat a data-scrubbing safeguard, undermining the guarantee that redacted/removed blobs are not silently reintroduced.
- Bypassing Praefect's checksum-equality gate can cause divergent replicas to be accepted as consistent, leading to silent data inconsistency across the cluster (a correctness/availability concern for a distributed VCS backend).

### Likelihood Explanation
Exploitation requires the attacker to fully control reference names and target OIDs of a repository they can push to — both are values an ordinary authenticated Gitaly user supplies routinely via `git push`. Constructing an actual SHA-1-based XOR collision is nontrivial (requires finding hash relations among attacker-chosen ref name/OID pairs), but it is a purely offline computational search against a public, deterministic combiner (XOR of SHA-1s) with no keying or salting, which is qualitatively weaker than the intended collision resistance of the mechanism it's meant to provide (detecting "the repository has not changed"). Likelihood is Low–Medium: the flaw is structurally real and reachable from an unprivileged pusher, but the concrete collision-finding cost is nontrivial (bounded by SHA-1 strength), so this is a design/robustness weakness rather than a trivially exploitable one like the original decimal-arithmetic collision.

### Recommendation
Replace the XOR-fold combiner with an order-independent but non-linear aggregation, e.g.:
- Sort all `(name, target)` hash outputs and feed them sequentially into a single SHA-256 hash (order-independence achieved by sorting rather than by algebraic cancellation), or
- Use a proper multiset/commutative cryptographic accumulator (e.g., hashing the sorted concatenation of all ref lines) instead of XOR-ing independent digests.

This removes the linear-algebra structure that allows attacker-chosen inputs to cancel out or collide, matching the reported fix recommendation of moving away from a reversible/collidable combination function (`keccak256` over the full, unambiguous serialization) toward one that binds the entire input set non-linearly.

### Proof of Concept
Conceptual (bounded by SHA-1 collision-search cost, not fully executed here — this is the algebraic structure exploited):
1. `Checksum.update` XORs `SHA1("<target> <name>")` for each allowed ref line into a running sum: `internal/git/checksum.go:48-56`.
2. Because XOR is commutative and self-inverse, for any four attacker-controlled ref lines `r1, r2, r3, r4` where `SHA1(r1) XOR SHA1(r2) == SHA1(r3) XOR SHA1(r4)`, pushing `{r1, r2}` and `{r3, r4}` as two different reference states yields an identical `CalculateChecksum` result despite the repository containing entirely different refs.
3. `internal/git/checksum_test.go:65-77` already proves the trivial degenerate case (duplicate refs canceling to zero contribution), confirming the combiner has no protection against engineered cancellation — only a stronger, non-linear combiner would prevent an attacker from generalizing this to non-trivial distinct ref sets.
4. Such a colliding pair, if injected as a concurrent ref update during `RewriteHistory`'s window (`internal/gitaly/service/cleanup/rewrite_history.go:119-142`) or presented to Praefect's replica-checksum comparison (`internal/praefect/recovery.go:93-105`), would defeat the "state unchanged"/"replicas match" checks that rely on checksum equality.

func (c *Checksum) Add(ref Reference) {
	if !refsAllowed.MatchString(ref.Name.String()) {
		return
	}

	h := sha1.New()
	// hash.Hash will never return an error.
	_, _ = fmt.Fprintf(h, "%s %s", ref.Target, ref.Name)

	c.update(h.Sum(nil))
}

func (c *Checksum) update(refSum []byte) {
	if c.sum.BitLen() == 0 {
		c.sum.SetBytes(refSum)
	} else {
		var hash big.Int
		hash.SetBytes(refSum)
		c.sum.Xor(&c.sum, &hash)
	}
}

func (s *server) CalculateChecksum(ctx context.Context, in *gitalypb.CalculateChecksumRequest) (*gitalypb.CalculateChecksumResponse, error) {
	repoProto := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repoProto); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repoProto)
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name: "show-ref",
		Flags: []gitcmd.Option{
			gitcmd.Flag{Name: "--head"},
		},
	}, gitcmd.WithSetupStdout())
	if err != nil {
		return nil, structerr.NewInternal("gitCommand: %w", err)
	}

	var checksum git.Checksum

	scanner := bufio.NewScanner(cmd)
	for scanner.Scan() {
		checksum.AddBytes(scanner.Bytes())
	}

	if err := scanner.Err(); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	if err := cmd.Wait(); checksum.IsZero() || err != nil {
		if s.isValidRepo(ctx, repo) {
			return &gitalypb.CalculateChecksumResponse{Checksum: git.ZeroChecksum}, nil
		}

		return nil, structerr.NewDataLoss("not a git repository '%s'", repoPath)
	}

	return &gitalypb.CalculateChecksumResponse{Checksum: hex.EncodeToString(checksum.Bytes())}, nil

func confirmChecksums(ctx context.Context, logger log.Logger, primaryClient, replicaClient gitalypb.RepositoryServiceClient, primary, replica *gitalypb.Repository) (bool, error) {
	g, gCtx := errgroup.WithContext(ctx)

	var primaryChecksum, replicaChecksum string

	g.Go(getChecksumFunc(gCtx, primaryClient, primary, &primaryChecksum))
	g.Go(getChecksumFunc(gCtx, replicaClient, replica, &replicaChecksum))

	if err := g.Wait(); err != nil {
		return false, err
	}

	logger.WithFields(log.Fields{
		"primary_checksum": primaryChecksum,
		"replica_checksum": replicaChecksum,
	}).Info("checksum comparison completed")

	return primaryChecksum == replicaChecksum, nil
}
