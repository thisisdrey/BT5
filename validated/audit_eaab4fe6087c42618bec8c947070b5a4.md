### Title
`remove_account` fails to clear postponed-receipt state (`PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`), letting a re-created account inherit privileged actions from before its deletion - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:504-575) only removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie rows for the account, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` rows keyed by `receiver_id == account_id`. Since `process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) and the Data-receipt branch of `process_receipt` (runtime/runtime/src/lib.rs:1386-1444) write exactly these four key types under the account's own `AccountId`, a postponed receipt created before deletion survives `DeleteAccount` and can execute against a later, unrelated account created with the same name.

### Finding Description
`process_action_receipt` stores an action receipt awaiting input data as `TrieKey::PostponedReceipt{receiver_id, receipt_id}` plus per-`data_id` `TrieKey::PostponedReceiptId{receiver_id, data_id}` and `TrieKey::PendingDataCount{receiver_id, receipt_id}` [1](#0-0) . When the corresponding data receipt later arrives at the same `receiver_id`, `process_receipt`'s Data-receipt branch looks up `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` purely by `receiver_id`/`receipt_id`/`data_id`, with no other binding to the account's identity/state (e.g., no check against `Account.storage_usage`, no nonce, no incarnation counter) [2](#0-1) .

`check_actor_permissions` treats `actor_id == account_id` as sufficient for `AddKey`, `DeployContract`, `DeleteKey`, `Stake`, etc. [3](#0-2) , and permits self `DeleteAccount` as long as `account.locked() == 0` [4](#0-3) . Neither check consults whether the account was re-created since the postponed receipt was queued — there is no "account epoch"/incarnation concept tying a postponed receipt to a specific account lifetime.

`remove_account`, which implements account deletion cleanup, only clears `Account`, `ContractCode`, access-key/gas-key rows, and `ContractData`: [5](#0-4) . It does not iterate or remove `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` rows, all of which are keyed by `receiver_id`/`account_id` per the `TrieKey` enum definitions [6](#0-5) .

Exploit flow:
1. `attacker.near` submits a function call that creates a callback action receipt to itself containing `AddKey(FullAccess)` with an `input_data_id` that is never satisfied at that time (postponed receipt persisted via `process_action_receipt`).
2. `attacker.near` submits `DeleteAccount` (self as actor, `locked == 0`, passes `check_actor_permissions`); `action_delete_account` calls `remove_account`, which deletes the account record and keys but leaves the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows intact.
3. A third party (or attacker via another path) `CreateAccount`s `attacker.near` again and funds it, believing it to be a fresh account.
4. The stale Data receipt satisfying `input_data_id` arrives (or attacker triggers it), `process_receipt`'s Data branch finds the leftover `PostponedReceiptId`/`PendingDataCount`, fetches the leftover `PostponedReceipt`, and executes it via `apply_action_receipt`, running `AddKey(FullAccess)` against the recreated account.
5. `check_actor_permissions` allows this because `actor_id (attacker.near, predecessor of the postponed receipt) == account_id (attacker.near)`, and there is no check that the account is the "same" account instance from before its deletion.

No existing check (signature/nonce/access-key permission/gas/storage-staking/size limits) intercepts this, because the entire path operates purely on trie state at the protocol level, not on transaction-level authorization primitives.

### Impact Explanation
This is an authorization-escalation bug: it lets `attacker.near` regain a full-access key on an account that a third party (funder) believes is newly created and under their trust assumptions, without the funder ever authorizing it. This matches the "authorization escalation across accounts or promises" bounty category. The severity depends on trust model — because the attacker is deleting and recreating an account under their own control (`attacker.near`), the practical loss is limited to funds a third party deposits into the account believing it's fresh; it is not a cross-account privilege escalation against an arbitrary victim account since the attacker must control the account name being deleted/recreated. It also represents state-hygiene corruption (residual state surviving deletion) which is a real dangling-reference bug in the protocol, but the exploitable financial impact is constrained to scenarios where a third party trusts a specific `account_id`'s freshness post-recreation and funds it — a real but narrower attack surface than a fully cross-account authorization break.

### Likelihood Explanation
The attack requires the attacker to fully control `attacker.near`'s lifecycle (create postponed receipt, self-delete, get itself recreated). Recreating a deleted named account requires a third party (not the attacker) to issue `CreateAccount` for that exact `account_id` and fund it — implicit accounts (64-hex) can't be intentionally "recreated" by others typically, but named accounts under a TLA can be recreated by any registrar-eligible party. This is a realistic scenario for marketplaces/registrars that recycle account names or re-issue subaccounts, or scenarios where users are led to believe a specific account name is safe to fund because it "looks new." The steps (function call, self-delete, wait for external CreateAccount) are all ordinary unprivileged transactions; the bug is fully reachable without any validator/node privilege.

### Recommendation
In `remove_account` (core/store/src/utils/mod.rs), before or alongside removing `Account`/`ContractCode`/`AccessKey`/`ContractData`, also iterate and remove any `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` rows keyed by the account being deleted (using the same prefix-iteration approach used for access keys and contract data). Alternatively, at the point where `DeleteAccount` is applied, generate delayed "cleanup" receipts that purge any postponed action receipts targeting the account, or reject `DeleteAccount` while any postponed receipt still targets the account (similar to how staking-lock prevents deletion). Any fix must account for the associated storage-usage/staking cost of these entries so deletion refunds remain correct.

### Proof of Concept

1. 2. Assert via direct trie inspection (`get_postponed_receipt`, `get` on `PostponedReceiptId`/`PendingDataCount`) that these rows exist.
3. Submit a `DeleteAccount` transaction signed by `attacker.near`'s key, beneficiary arbitrary, with `locked() == 0`; apply it through `apply_action_receipt`, and confirm `Account`/`AccessKey`/`ContractCode` are gone via `get_account`.
4. Assert via direct trie inspection that the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows for `attacker.near` still exist (demonstrating the bug).
5. Submit `CreateAccount` for `attacker.near` funded by a third-party account, and apply it.
6. Submit the Data receipt satisfying the stale `input_data_id` targeting `attacker.near`; apply via `apply_action_receipt`/`process_receipt`.
7. Assert that the recreated `attacker.near` account now has the `FullAccess` key from the old postponed `AddKey` action — i.e., `get_access_key(state_update, &attacker_id, &pubkey)` returns `Some(AccessKey{permission: FullAccess})` — proving the leftover postponed receipt executed against the newly created account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
