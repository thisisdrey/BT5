### Title
StackerDB chunk signatures are not bound to the target contract, enabling cross-replica replay of validly-signed chunks - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a StackerDB writer signs over `slot_id`, `slot_version`, and `data_hash` only — it never includes the target StackerDB's contract identifier (`QualifiedContractIdentifier`). Every verification path that accepts a chunk (`StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` and `PeerNetwork::validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`) looks up "who owns this slot *for this contract*" and then calls `SlotMetadata::verify(&addr)`, which only checks that the signature recovers to that address — it does not check that the signature was ever intended for *this* contract's replica. This is the same class of bug as the reported Rancher issue: a credential/signature that is valid and scoped for one destination (a downstream cluster / a specific StackerDB contract) is accepted by a different destination (the `local` cluster / a different StackerDB contract) because the verification step never binds the proof to the destination it is being presented to.

### Finding Description
The signed digest is defined as: [1](#0-0) 

Note it hashes only `slot_id`, `slot_version`, and `data_hash` — no contract/DB identifier, no chain ID, no domain separator identifying which StackerDB replica the chunk belongs to.

`SlotMetadata::verify()` only checks the recovered public key hash against the expected `principal`: [2](#0-1) 

Both storage paths look the signer address up per-contract, then call this same context-free `verify()`: [3](#0-2) [4](#0-3) 

Because the digest that is signed carries no information about *which* StackerDB contract the chunk is destined for, a chunk that a signer legitimately produced and signed for contract `A` (a specific `slot_id`/`slot_version`/`data_hash`) is a bit-for-bit valid, verifiable message for contract `B` as well, provided the same signing address happens to own that `slot_id` in `B`. The system conflates "signed by the correct principal" with "intended for this specific StackerDB instance" — exactly the equality violated in the Rancher analog (proof of authorization for one target accepted as proof of authorization for a different target).

If accepted, a replayed/cross-context chunk is not just stored locally — successful storage causes the node to treat the data as novel and rebroadcast it network-wide: [5](#0-4) 

This means a single cross-contract replay, once accepted by any node, propagates the (out-of-context) chunk data across the whole StackerDB gossip network as if it were legitimately produced for that replica.

### Impact Explanation
Multiple StackerDB contracts in this codebase (e.g. `signers-0-xxx.clar`, `signers-1-xxx.clar`) can have overlapping/deterministic slot assignment for the same signer set across contracts/reward cycles. Where such overlap exists, a signer's message intended for one StackerDB contract (e.g., one message type/cycle) is a valid, verifiable chunk for a *different* StackerDB contract's identical slot, without needing anyone else's key. Any node that receives it will store it (since it authenticates) and then automatically rebroadcast it to the whole peer network via `p2p.broadcast_message`, per `Relayer::process_stacker_db_chunks`. This can let a party inject/replay data intended for one operational context (e.g. block-signing/voting for one signer contract) into another semantically distinct contract's replica, and have the node infrastructure itself amplify that forged-context data network-wide — matching the "network-wide propagation of forged data" bar for Critical impact.

### Likelihood Explanation
The precondition (an authenticated slot owner producing a signature that happens to be replayable into a different contract's identically-numbered slot) depends on the concrete slot-assignment scheme used by the signer-related StackerDB configs, which I was not able to fully confirm from the indexed code before running out of investigation budget — I could not locate the exact slot-to-signer assignment routine to verify how often/whether the same address ends up owning the same `slot_id` across two live contracts simultaneously. The root-cause defect itself (missing contract binding in the signed digest) is confirmed directly in code, independent of that uncertainty, and is a latent replay/cross-context-confusion vulnerability regardless of the exact current deployment topology.

### Recommendation
Include the target `QualifiedContractIdentifier` (and ideally a chain-id / network domain separator) inside `SlotMetadata::auth_digest()`, so that a chunk signature is cryptographically bound to the specific StackerDB replica it is meant for. This closes the destination-confusion gap analogous to how Rancher's fix required binding session/kubeconfig credentials to the specific target cluster rather than validating only "is this a token this user legitimately holds."

### Proof of Concept
1. Configure/observe two StackerDB contracts, `A` and `B`, where the same signer address is assigned `slot_id = N` in both (this can occur when slot assignment is derived deterministically from the signer set, which can be identical or overlapping across contracts/cycles).
2. The signer legitimately signs `StackerDBChunkData { slot_id: N, slot_version: V, data: D }` for contract `A` via `StackerDBChunkData::sign()`, whose digest is `auth_digest() = H(slot_id || slot_version || data_hash)` (`libstackerdb/src/libstackerdb.rs:159-166`).
3. Replay the identical `(slot_id, slot_version, sig, data)` tuple as a `StackerDBPushChunkData` / `POST /v3/stackerdb` targeting contract `B` instead.
4. `validate_received_chunk`/`try_replace_chunk` fetch `B`'s slot owner for slot `N`, find it matches, call `SlotMetadata::verify(&addr)`, which succeeds because the digest never referenced contract `A` or `B`.
5. The chunk is stored under `B` and rebroadcast to the network by `Relayer::process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2445-2452`), propagating data outside its intended operational context.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
