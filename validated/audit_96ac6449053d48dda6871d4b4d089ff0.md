### Title
Unbounded memory allocation via `extractBytes32Array` in `BatchValidateSign` precompile - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `BatchValidateSign` TVM precompiled contract (address `0x9`, reachable via a normal `CALL`/`STATICCALL` opcode from any smart contract triggered by an unprivileged transaction) parses attacker-controlled ABI-encoded calldata and derives an array length directly from calldata words, then allocates a Java array of that length before any bound check is guaranteed to apply.

### Finding Description
In `doExecute()`, the address array is always extracted unconditionally via: [1](#0-0) 

`extractBytes32Array` allocates `new byte[len][]` where `len` comes straight from attacker calldata with no upper bound: [2](#0-1) 

The only size guard (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) is gated behind the `VMConfig.allowTvmSelfdestructRestriction()` feature flag: [3](#0-2) 

When that flag is not active (i.e., not yet activated on the relevant chain/network), `extractBytes32Array` is invoked with a completely attacker-controlled `len` (via `words[offset].intValueSafe()`) with no cap, so a crafted calldata word can request an array of up to `Integer.MAX_VALUE` `byte[]` references — an immediate multi-gigabyte allocation attempt — purely from parsing the "combination" of the two offset/length words in the ABI-style input. This is structurally analogous to CVE-2018-5744: a specific combination of two option/length fields in a parsed message triggers uncontrolled memory allocation/exhaustion before any real validation of the message contents occurs.

Note: I could not fully confirm from the available index whether `allowTvmSelfdestructRestriction` is enabled by default on current mainnet — its enablement is controlled by chain parameters/hard fork activation (`ProposalUtil.java`, `DynamicPropertiesStore.java`) which I was unable to fully trace within the available tool budget. If the fork has been activated on all live networks, the guard at lines 1165-1171 would neutralize this specific path; the vulnerability is only live where/when the flag is off.

### Impact Explanation
A successful trigger causes a large (up to multi-GB) array allocation attempt inside the TVM precompile execution path on the node processing/validating the transaction. This can:
- Throw `OutOfMemoryError`, which is caught by the enclosing `try { doExecute(data) } catch (Throwable t)` at lines 1145-1154, returning a benign result — but the JVM may already have triggered stop-the-world GC cycles or increased heap pressure before failing, which is exploitable repeatedly by broadcasting many such contract-invoking transactions to degrade or crash node availability (resource-exhaustion DoS against the query/execution path), consistent with the "High" severity, availability-only impact profile of CVE-2018-5744.

### Likelihood Explanation
Reachable by any unprivileged account that deploys or calls a contract invoking the precompile at address `0x...9` with crafted calldata; no special privileges, signatures, or SR/witness status required — only gas/energy to pay for the call. The `getEnergyForData` fee formula is based on calldata length, not on the derived array length, so the energy charged does not scale with the attacker-chosen allocation size, making the attack economically cheap relative to potential impact. This condition is easy to reach with a single crafted transaction.

### Recommendation
Move the `sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE` bound check (and equivalent checks in `ValidateMultiSign` and `extractBytesArray`/`extractSigArray`) outside the `allowTvmSelfdestructRestriction()` feature-flag gate so it always applies regardless of fork activation state. Additionally, validate the extracted `len` against `MAX_SIZE` (or a sane small bound) inside `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves before allocating the array, rather than relying on call-site checks that can be bypassed by unactivated config flags.

### Proof of Concept
1. Deploy or use any contract that performs a `CALL` to precompile address `0x0000...0009` (BatchValidateSign).
2. Craft the calldata such that `words[2]` (the addresses-array offset word) points to a word whose value (`intValueSafe()`) is a very large integer (e.g., close to `Integer.MAX_VALUE / 32`), while keeping the calldata otherwise minimally valid so `DataWord.parseArray` and `isValidAbiEncoding` (if the Osaka guard is inactive, this check is skipped entirely) do not reject it.
3. Submit this as a normal `TriggerSmartContract` transaction from any account.
4. Observe `extractBytes32Array` attempting `new byte[len][]` with the attacker-supplied `len`, causing a large/failed allocation and associated GC pressure on the executing node, repeatable at low cost per transaction. [2](#0-1) [4](#0-3)
