### Title
Missing `supportUnfreezeDelay` feature-gate check allows TVM-triggered `WithdrawExpireUnfreeze` even when the feature has not been enabled by committee - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`)

### Summary
The `WithdrawExpireUnfreezeContract` transaction path enforces a committee-controlled feature toggle (`dynamicStore.supportUnfreezeDelay()`), which gates whether the entire "withdraw expired unfreeze" feature is allowed to execute at all. The corresponding TVM native-contract path, which any unprivileged account can reach through a smart-contract call using the `withdrawExpireUnfreeze` opcode, omits this same gate — mirroring the reported bug class where one code path enforces a protocol-wide guard (`whenNotPaused`) while a sibling privileged/alternate path does not.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly checks the feature flag before allowing a normal transaction to withdraw expired unfrozen balance: [1](#0-0) 

However, the TVM-reachable equivalent, `WithdrawExpireUnfreezeProcessor.validate()` — invoked from the `withdrawExpireUnfreeze` opcode handler in `OperationActions.withdrawExpireUnfreezeAction()` — performs account/address/overflow checks but never checks `dynamicStore.supportUnfreezeDelay()`: [2](#0-1) [3](#0-2) 

This is directly analogous to the reported issue: the guard (`whenNotPaused` in the external report; `supportUnfreezeDelay()` here) is present on one code path that performs the sensitive fund-release operation but is absent from a second, independently reachable code path that performs the same operation.

### Impact Explanation
`supportUnfreezeDelay` is a chain-wide feature switch intended to be turned on only via committee proposal (`FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, `DelegateResourceActuator`, `UnDelegateResourceActuator` all consult this flag) [4](#0-3) . If the flag is not yet enabled (or intentionally disabled), any contract able to trigger the `withdrawExpireUnfreeze` TVM opcode can still bypass the feature gate and release "expired unfreeze" balances back to account balance, moving funds through a code path the protocol did not intend to be active — an unauthorized state transition analogous to bypassing a pause.

### Likelihood Explanation
The opcode is reachable by any address that can call/deploy a contract invoking `withdrawExpireUnfreeze` (a standard `TriggerSmartContractContract`), requiring no special privilege — only that the account has an `UnFreezeV2` entry with an elapsed expiration time, which is set up through normal `unfreezeBalanceV2` flows. No malicious-SR/witness/peer/node conditions are required.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check (throwing `ContractValidateException` when disabled, mirroring `WithdrawExpireUnfreezeActuator`) to `WithdrawExpireUnfreezeProcessor.validate()` so the TVM-triggered path enforces the identical feature gate as the transaction-actuator path.

### Proof of Concept
1. Deploy/observe a network state where `supportUnfreezeDelay` proposal has not been enabled (flag = 0/off) but where an account nonetheless holds `UnFreezeV2` entries with `unfreezeExpireTime <= now` (e.g., produced before the flag was toggled off, or via any state where such entries exist).
2. From an unprivileged EOA, deploy or call a smart contract that invokes the `withdrawExpireUnfreeze` native TVM opcode (`OperationActions.withdrawExpireUnfreezeAction` → `Program.withdrawExpireUnfreeze()` → `WithdrawExpireUnfreezeProcessor`).
3. Observe that `WithdrawExpireUnfreezeProcessor.validate()` succeeds and `execute()` moves the expired-unfreeze balance into the account's spendable balance, even though the equivalent `WithdrawExpireUnfreezeContract` broadcast transaction would be rejected by `WithdrawExpireUnfreezeActuator.validate()` with `"Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee"`.

Note: I was unable to fully trace `Program.java`'s `withdrawExpireUnfreeze()` method body in this pass (only confirmed via grep that it exists and calls into the processor) to rule out an additional feature check at that layer; a Devin session with full file access should verify this call site directly before finalizing the fix.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }

    if (accountCapsule.hasInvalidDelegatedV2()) {
      MUtil.checkCPUTimeForInvalidDelegatedV2Balance();
    }
  }
