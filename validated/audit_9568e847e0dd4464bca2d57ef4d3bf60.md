### Title
Dust `DepositToken` deposits fill a victim's per-account token set, permanently blocking new collateral types for accounts with locked debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the OpenVPN memory-leak DoS (repeated small allocations from crafted packets exhaust a resource), `Pool.depositTokensOfAccount` / `debtTokensOfAccount` are bounded per-account sets capped at `MAX_TOKENS_PER_USER = 30` [1](#0-0) . An unprivileged attacker can allocate victim-owned set entries by calling `DepositToken.deposit(amount_, onBehalfOf_ = victim)` or `transfer(victim, dust)` — no victim action or privileged role is required. Once the combined count reaches 30, every first-time receipt of a new deposit or debt token by the victim reverts with `UserReachedMaxTokens` [2](#0-1) .

### Finding Description
`Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` enforce the cap via `onlyIfAdditionWillNotReachMaxTokens` on the combined length of both sets [3](#0-2) . Entries are added whenever a balance goes `0 → >0` inside `DepositToken._mint` and `DepositToken._transfer` [4](#0-3) , and are only removed when the balance returns to exactly zero [5](#0-4) .

Attack path:
1. Attacker deposits (or transfers) a dust amount of each registered `DepositToken` with `onBehalfOf_ = victim`, filling `depositTokensOfAccount[victim]` up to the cap (bounded by the number of registered deposit tokens, itself capped at 30 [6](#0-5) ).
2. Thereafter, any `deposit`/`transfer`/`seize` that would give the victim a *new* deposit-token type reverts, and the victim cannot open a position in a new debt token either if the combined cap is hit.
3. For a victim holding locked debt, the dust cannot be cleaned up: `transfer`/`withdraw` are gated by `_revertIfLocked` → `unlockedBalanceOf`, which returns 0 when the position is fully locked [7](#0-6) , so the filler entries persist until the victim repays debt — which itself may require acquiring new collateral types that are now blocked.

### Impact Explanation
Temporary/partial freezing of funds and liveness denial: a victim with a debt position is permanently prevented (until full repayment) from receiving any new collateral token type, from being deposited-to by third parties (e.g., `NativeTokenGateway.deposit`/`VesperGateway` flows that mint new token types), and potentially from borrowing new synthetics. This breaks the liveness invariant that a user can always add collateral to rescue an unhealthy position, mirroring the advisory's "flood of crafted packets → resource exhaustion → DoS" shape.

### Likelihood Explanation
- Fully unprivileged: `deposit` and `transfer` are public; `issue()` cannot be abused since debt is minted to the caller [8](#0-7) .
- Cost is bounded: attacker needs net `>0` minted per token (deposit fee must not eat the whole dust amount) across all listed deposit tokens.
- Limitation: impact requires enough registered deposit tokens (plus the victim's own debt tokens) to reach 30, and victims with no locked balance can self-clean by transferring/withdrawing the dust. No modifier, cap, pause flag, or reentrancy guard stops the fill itself.

### Recommendation
- Reject `onBehalfOf_` minting that would create a new set entry for a different account, or require the beneficiary to opt in.
- Alternatively, let the account itself purge entries (e.g., a `Pool`-level `removeFromDepositTokensOfAccount` callable when `balanceOf == 0`, or a minimum-deposit threshold so dust cannot occupy slots).

// Hardhat fork test (pseudocode against deployed Pool + DepositTokens)
// given: victim has an open debt position (locked) and 0 token slots used
const tokens = await pool.getDepositTokens(); // N listed deposit tokens
for (let i = 0; i < 30 && i < tokens.length; i++) {
  const dt = await ethers.getContractAt('DepositToken', tokens[i]);
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(whale).transfer(attacker.address, 1n);
  await underlying.connect(attacker).approve(dt.address, 1n);
  // crafted "packet": 1-wei deposit mints a slot for the victim
  await dt.connect(attacker).deposit(1n, victim.address);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).length(30);

// victim can no longer receive a NEW deposit token type (e.g. via deposit or transfer)
await expect(newDt.connect(attacker).deposit(1n, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot clean slots while collateral is locked:
await expect(dt.connect(victim).transfer(attacker.address, 1n))
  .revertedWithCustomError(dt, 'NotEnoughFreeBalance');
