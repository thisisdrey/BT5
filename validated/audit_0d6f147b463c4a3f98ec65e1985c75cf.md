### Title
Unbounded `AssetIssueStore` growth via unrestricted `AssetIssueContract` creation causes full-iteration DoS in `Wallet.getAssetIssueList()` - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
Any account can create a new token via `AssetIssueActuator` by paying the asset-issue fee, and every issued asset is permanently stored in `AssetIssueStore`/`AssetIssueV2Store` with no mechanism to prune or bound its size. `Wallet.getAssetIssueList()` — the handler behind the un-paginated HTTP endpoint `/wallet/getassetissuelist` and the gRPC `GetAssetIssueList` RPC — loads and iterates the entire store on every call, running `BandwidthProcessor.updateUsage()` per entry, with no cap on the number of records processed or returned.

### Finding Description
`AssetIssueActuator.execute()` persists every newly issued asset into `AssetIssueStore`/`AssetIssueV2Store` and never removes entries: [1](#0-0) 

The only guard on this operation is a fixed TRX fee taken from the caller's balance and burned/sent to the blackhole address: [2](#0-1) 

There is no restriction on how many distinct assets can exist in total, nor any way to remove old/expired entries from `AssetIssueStore`. `AssetIssueStore.getAllAssetIssues()` performs a full-store scan: [3](#0-2) 

`Wallet.getAssetIssueList()` — the unbounded, non-paginated variant — calls `getAllAssetIssues()` and then iterates the full result set, invoking `BandwidthProcessor.updateUsage()` on every single asset before returning them all in one response: [4](#0-3) 

This method is reachable without authentication through both the HTTP JSON-RPC-style endpoint: [5](#0-4) 

and the gRPC API: [6](#0-5) 

A bounded/paginated sibling API (`getAssetIssueList(offset, limit)` / `getPaginatedAssetIssueList`) exists, but the legacy unbounded endpoint remains active and publicly exposed, exactly mirroring the reported analog: an ever-growing collection created by unrestricted user action, with no emptying/pruning mechanism, that is fully iterated by a reachable entry point without any cap.

### Impact Explanation
As the number of issued tokens grows (each creation only costs a fixed, moderate TRX fee — an attacker with sufficient TRX, or many colluding low-cost accounts, can create arbitrarily many assets over time), every call to `/wallet/getassetissuelist` or gRPC `GetAssetIssueList` becomes proportionally more expensive: it must deserialize every stored `AssetIssueCapsule`, run bandwidth-usage accounting on each, and marshal them all into a single response. This can degrade or exhaust node resources (CPU, memory for the in-memory result list, and response payload size) on every fullnode/solidity node serving this API, making the query path unable to serve legitimate clients — a concrete, reachable "API the node can no longer serve" condition on any fullnode exposing HTTP/gRPC APIs.

### Likelihood Explanation
Likelihood is moderate-to-high: creating an asset issue only requires a normal signed transaction and payment of the fixed `AssetIssueFee` (a network-wide constant, not scaling with existing asset count), so a well-funded attacker (or protocol abuse over a long period) can inflate the store size significantly with no on-chain restriction. Once inflated, every unauthenticated caller of the un-paginated endpoint pays the same growing cost, and the affected endpoint requires no special privileges to invoke.

### Recommendation
Deprecate or remove the unbounded `getAssetIssueList()` no-argument API path (or force callers through pagination with an enforced default/maximum limit, similar to `ASSET_ISSUE_COUNT_LIMIT_MAX` already used in `getAssetIssuesPaginated`), and cap the response size of `/wallet/getassetissuelist` and `GetAssetIssueList` regardless of client input.

### Proof of Concept
1. Repeatedly submit `AssetIssueContract` transactions from one or more funded accounts, each paying `dynamicStore.getAssetIssueFee()`, to create N (e.g. tens of thousands) of distinct assets — nothing in `AssetIssueActuator.validate()`/`execute()` caps the total number of assets in `AssetIssueStore`. [7](#0-6) 
2. Call `GET /wallet/getassetissuelist` (or gRPC `GetAssetIssueList`) repeatedly; each call performs a full scan of `AssetIssueStore`/`AssetIssueV2Store` (`getAllAssetIssues()`) and per-entry bandwidth processing in `Wallet.getAssetIssueList()`. [4](#0-3) 
3. As N grows, response construction time and memory usage grow linearly/unbounded per call, degrading availability of this API path for the whole node.

  public AssetIssueList getAssetIssueList() {
    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();

    getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
        chainBaseManager.getAssetIssueStore(),
        chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues()
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }
