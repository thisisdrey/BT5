### Title
Unpermissioned `DisconnectGitAlternates` snapshot/connectivity-check race can permanently corrupt or DoS an object-pool member repository - ([File: internal/git/objectpool/disconnect.go])

### Summary
The reported PartyDAO bug is a DOS pattern where an unpermissioned finalize-style call (`buy`) computes a critical downstream threshold (`totalVotingPower`) from mutable, attacker-influenceable state captured only at call time (`settledPrice`, inflated by a donation), with no re-validation against the "real" contribution total — permanently softlocking governance. The closest reachable analog in Gitaly is `objectpool.Disconnect` (exposed as the `DisconnectGitAlternates` RPC), which similarly performs a snapshot of shared, mutable, unprivileged-writable state (the object pool's alternate object directory) and then commits an irreversible action (removing `objects/info/alternates`) based on a connectivity check computed from that stale snapshot, all without any additional gating tied to whether the snapshot is still valid at commit time.

### Finding Description
`Disconnect` (called by the unprivileged, repo-scoped `DisconnectGitAlternates` RPC, gated only by normal `target_repository` validation, not by any special permission) is documented as "dangerous": [1](#0-0) 

It works by:
1. Enumerating the pool's alternate object files at a single point in time via `findObjectFiles`, which walks the alternate object directory and returns a list of file paths present *at that moment*. [2](#0-1) 
2. Hard-linking exactly that enumerated snapshot of objects into the member repository. [3](#0-2) 
3. Renaming away `objects/info/alternates` and then validating completeness with a connectivity walk (`git rev-list --objects --all --quiet`) over the *current* ref state of the repository, which is evaluated well after the snapshot was taken. [4](#0-3) 

Because object pools are shared, mutable resources — other pool members can push (an ordinary, unprivileged operation) causing `FetchIntoObjectPool` housekeeping to prune stale/dangling references in the pool concurrently with `Disconnect`'s snapshot-and-migrate sequence — there is a window between the object-file enumeration and the final connectivity check during which the pool's contents (and hence which objects are "linkable") can shift. The pool's own documentation explicitly acknowledges this fundamental race: "there is no point in time where it's safe to delete objects from the object pool... we cannot determine all references of all repositories at once in a race-free manner." [5](#0-4) 

If the connectivity check fails, the code attempts to roll back by restoring the alternates file, but the code's own comment states that during the entire operation "probably **all concurrent RPC calls to the repo will fail**", and if Gitaly crashes mid-operation the repository is left in a broken state requiring manual admin intervention: [1](#0-0) 

This mirrors the reported bug class: an unprivileged, unpermissioned action finalizes an irreversible state transition based on a stale/racy snapshot of externally-mutable shared data, with no mechanism to atomically pin or re-validate that snapshot against concurrent legitimate activity, leading to a DoS/corruption condition on a repository other users depend on.

### Impact Explanation
A successful race (or a crash mid-operation) can leave a pool member repository without its `objects/info/alternates` link and without a superset of the objects it needs, or leave it in the documented "broken state until an administrator intervenes." This is a Denial-of-Service against normal git operations (fetch/clone/read) on that repository — comparable in class to the softlocked Party in the original report, though the exact reachability and severity of a genuine data-loss window (versus admin-recoverable backup file restoration) could not be fully confirmed from static analysis alone; a live concurrency test against `Disconnect` running in parallel with `FetchIntoObjectPool`/pruning on the same pool would be needed to prove exploitability with certainty.

### Likelihood Explanation
`DisconnectGitAlternates` is a MUTATOR RPC scoped only by `target_repository`, callable by any actor authorized to mutate the target repository — no gatekeeper/host-style permission is layered on top the way the report recommends for `buy()`. Since object pools are inherently shared across forks, and pool housekeeping (`FetchIntoObjectPool`) is a routine, frequently-triggered operation, the timing window required to race the snapshot against pool mutation is plausible under normal load and does not require compromising any credentials or a malicious peer — matching the required "ordinary user" reachability constraint.

### Recommendation
Perform the alternate-object enumeration, hard-link migration, and final connectivity check within a single atomic transaction/lock that also serializes against concurrent `FetchIntoObjectPool`/pruning operations on the same pool, rather than relying on independent snapshot-then-verify steps separated by unguarded time. Alternatively, re-enumerate and re-validate the alternate object directory immediately before removing `objects/info/alternates` (as close as possible to the connectivity check) and treat any pool-side change since the initial snapshot as a hard failure requiring restart of the whole operation, not just a partial rollback.

### Proof of Concept
A concrete PoC requires setting up a live Gitaly deployment with an object pool and at least two members: while a `DisconnectGitAlternates` RPC is executing `Disconnect` on member A (after `findObjectFiles` snapshot but before the final `rev-list` connectivity check), trigger `FetchIntoObjectPool` from member B to run pool housekeeping/pruning concurrently, then observe whether member A's repository becomes unreadable/broken or requires the backup-alternates file to be manually restored. This dynamic race could not be executed or verified in this static, read-only analysis; it should be exercised in a live Devin session with access to a running Gitaly cluster.
