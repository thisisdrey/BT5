### Title
Nullifier derivation wrapper always reports success, letting a failed native computation produce an unvalidated/zero-filled Sapling nullifier - (File: chainbase/src/main/java/org/tron/common/zksnark/JLibrustzcash.java)

### Summary
`JLibrustzcash.librustzcashComputeNf` calls the native `librustzcashSaplingComputeNf` (a `void` JNI call) and then hardcodes `return true;`, discarding any actual success/failure signal from the native Rust nullifier derivation. [1](#0-0) 
Every caller — `Note.nullifier(...)` in `framework/src/main/java/org/tron/core/zen/note/Note.java`, `Wallet.createShieldNullifier` and `Wallet.getShieldedTRC20Nullifier` in `framework/src/main/java/org/tron/core/Wallet.java`, and `ShieldedTRC20ParametersBuilder.generateSpendProof` — treats the boolean return as an authoritative failure signal to decide whether to trust the pre-allocated 32-byte `result` buffer. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
Compare with the sibling API `librustzcashComputeCm`, which correctly forwards the native boolean result: [5](#0-4) 
`librustzcashComputeNf`, however, is written to always claim success:
```java
public static boolean librustzcashComputeNf(ComputeNfParams params) {
    INSTANCE.librustzcashSaplingComputeNf(params.getD(), params.getPkD(), params.getValue(),
        params.getR(), params.getAk(), params.getNk(), params.getPosition(), params.getResult());
    return true;
}
```
This mirrors the reported bug class exactly: an operation that writes into a caller-supplied output buffer (pre-zeroed with `new byte[32]`) can fail internally (e.g., invalid curve point from a malformed `pkD`/`ak`/`nk`/diversifier combination supplied by an untrusted note/spending-key input), yet the wrapper unconditionally signals success. Any downstream code that gates "is this nullifier trustworthy" on the boolean — as `Note.nullifier()`, `Wallet.createShieldNullifier`, and `Wallet.getShieldedTRC20Nullifier` all do — can never detect the failure and will accept a nullifier value that may be all-zero or otherwise not cryptographically bound to the spend inputs.

### Impact Explanation
The Sapling nullifier is the sole mechanism preventing a shielded note from being spent twice: `ShieldedTransferActuator.validate()`/`executeShielded()` reject a transaction only if its nullifier already exists in `NullifierStore`. [6](#0-5) [7](#0-6) 
If the underlying native derivation ever fails on attacker-influenced inputs while `librustzcashComputeNf` still reports success, the produced nullifier is not a trustworthy binding to the specific note — it could collide, be predictable, or otherwise fail to uniquely and correctly identify the spent note, undermining the double-spend protection at the core of the shielded pool (a concrete path to unauthorized spend / unbacked balance in the shielded token pool). It also mirrors the underlying CWE-330 (Use of Insufficiently Random/Trustworthy Value) class from the report: a value that must be treated as untrustworthy on failure is instead always trusted.

### Likelihood Explanation
Reachability requires the shielded transaction feature to be enabled (`AllowShieldedTransaction`), which is a supported, non-privileged, broadcastable path (`ShieldedTransferContract`) available to any TRX/asset holder, and the gRPC/HTTP-exposed `Wallet.createShieldNullifier`/`getShieldedTRC20Nullifier` APIs are directly reachable by any anonymous API client with no privilege required. [8](#0-7) 
Triggering the actual native failure requires crafting inputs (diversifier/`pkD`/`ak`/`nk`) that cause the underlying Rust curve arithmetic to fail — this is plausible given similar sibling functions (`librustzcashComputeCm`, `librustzcashSaplingSpendSig`, `librustzcashSaplingBindingSig`) are documented/tested to return `false` on invalid inputs, confirming failure paths exist in the same native library; only the nullifier wrapper fails to propagate them.

### Recommendation
Change `librustzcashComputeNf` to return the actual boolean result from `INSTANCE.librustzcashSaplingComputeNf(...)` instead of the hardcoded `true`, matching the pattern already used by `librustzcashComputeCm` and other wrappers, so that all callers' existing `if (!JLibrustzcash.librustzcashComputeNf(...)) { ...fail... }` checks become effective.

### Proof of Concept
1. Call `Wallet.createShieldNullifier` (or invoke a `ShieldedTransferActuator` spend) with a `PaymentAddress`/`ak`/`nk` combination engineered so the underlying native `librustzcashSaplingComputeNf` computation fails internally (e.g., an invalid/edge-case elliptic-curve point derived from the diversifier or key material).
2. Because `librustzcashComputeNf` at `chainbase/src/main/java/org/tron/common/zksnark/JLibrustzcash.java:65-69` ignores the native failure and always returns `true`, `Note.nullifier()` / `Wallet.getShieldedTRC20Nullifier()` return the pre-allocated `result` buffer (potentially still zero-filled or otherwise not properly bound to the note) as if it were a valid nullifier.
3. This untrustworthy nullifier is embedded in the `SpendDescription` and accepted by `ShieldedTransferActuator.validate()`'s nullifier-uniqueness check, since the actuator has no independent way to detect that the nullifier computation actually failed.
