### Title
Cross-repository/cross-transaction quarantine directory access via basename-only `isTransactionQuarantineDir` check - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath` (used directly by the client-facing `GetObjectDirectorySize` RPC) is supposed to verify that a request-supplied `GitObjectDirectory` path either resolves inside the repository itself or is a legitimate quarantine directory belonging to *that specific repository/transaction*. Instead of validating actual ownership, it uses a purely syntactic shortcut — matching on the directory's basename (`"quarantine"`/`tmp_objdir*`) — and when that shortcut matches it skips the real ownership check entirely, analogous to the reported bug where an intersection/validity check was performed against the wrong, overly broad set instead of the specific set that should have been used.

### Finding Description
`ObjectDirectoryPath` (`internal/git/localrepo/paths.go:21-83`) is called with a client-supplied `*gitalypb.Repository`, whose `GitObjectDirectory` field is taken verbatim from the RPC request [1](#0-0) .

The function first performs a storage-root escape check: [2](#0-1) 

This only ensures the path stays inside the *storage*, not inside the caller's repository or a specific transaction. It then computes a heuristic flag based solely on the path's basename/parent name: [3](#0-2) 

If that heuristic is true, the block that actually verifies the path belongs to *this* repository (either as a normal in-repo relative path, or — if not — as a quarantine directory whose prefix is derived from a SHA1 hash of the repository's own relative path, see `storage.QuarantineDirectoryPrefix`) is skipped entirely: [4](#0-3) 

The correct, ownership-verifying check exists (`expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))`) but is bypassed for any path whose basename happens to literally be `quarantine` (or `tmp_objdir*` under a `quarantine` parent) — this is precisely the pattern in the referenced report: a condition is evaluated against the wrong/too-broad scope (any directory named "quarantine" anywhere in storage) instead of the one that actually matters (whether the path is this repository's/transaction's own quarantine, verified via `expectedQuarantinePrefix`).

Transaction-manager quarantine directories are created at `filepath.Join(txn.stagingDirectory, "quarantine")` [5](#0-4)  — a storage-wide staging area, not scoped per caller. Because the basename is always literally `"quarantine"`, an attacker who can compute or guess another concurrent transaction's staging directory path (paths derived from transaction/partition IDs, which are sequential/discoverable) can set `Repository.GitObjectDirectory` to that path. The only remaining barrier is the storage-root escape check, which any such path satisfies since it is within the same storage.

### Impact Explanation
`GetObjectDirectorySize` will walk and sum the size of whatever directory is supplied, as long as it satisfies the weak basename heuristic and resides under the storage root [6](#0-5) . This allows an authenticated gRPC client to read size/metadata for another repository's or another concurrent push's in-flight quarantine directory — objects that have been pushed but not yet authorized/merged into the target repository. This is a cross-repository/cross-transaction quarantine-boundary violation and information disclosure (directory sizes, existence, and indirectly the fact that a specific push is in flight), and depending on other consumers of `ObjectDirectoryPath` in the future, could be extended into deeper cross-tenant object access.

### Likelihood Explanation
Exploitability requires only an ordinary authenticated Gitaly client able to invoke `GetObjectDirectorySize` with a crafted `Repository` proto (a normal, unprivileged RPC call) — no special access or server compromise needed. The main practical constraint is guessing/knowing another concurrent transaction's staging path, which is derived from internal, sequential/deterministic identifiers rather than being cryptographically random, reducing the difficulty of a successful attack in a busy multi-repo/multi-tenant Gitaly node.

### Recommendation
Remove the basename-based shortcut (`isTransactionQuarantineDir`) as the sole gate for skipping verification. Always require that any quarantine-like object directory path be validated against an ownership-derived prefix (as already done via `storage.QuarantineDirectoryPrefix`/`expectedQuarantinePrefix`) — for transaction-manager quarantine directories, this means verifying the path is under the staging directory that was actually allocated to the current transaction/repository, not merely that its basename matches `"quarantine"`.

### Proof of Concept
1. Client A starts a push to repo A; Gitaly's `TransactionManager.Begin` allocates a quarantine directory at `storage/staging/<txnA>/quarantine`.
2. A concurrent, unrelated attacker client sends `GetObjectDirectorySize` for repo A/B they legitimately have access to, but sets `Repository.GitObjectDirectory` to a relative path that resolves to `storage/staging/<txnA>/quarantine` (guessed or enumerated staging directory).
3. In `ObjectDirectoryPath`, `storage.ValidateRelativePath(storagePath, ...)` succeeds because the target is within the storage root; `filepath.Base(relativeObjectDirectoryPath) == "quarantine"` makes `isTransactionQuarantineDir` true, so the ownership/prefix check block is skipped entirely.
4. `os.Stat` finds the directory exists, and `GetObjectDirectorySize` walks and returns its size — leaking information about transaction A's in-flight (not-yet-authorized) push, despite the attacker having no relationship to that transaction or repository.
