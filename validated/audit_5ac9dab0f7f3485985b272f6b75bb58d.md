Audit Report

## Title
Broken `value.is_zero()`/`gas_limit` heuristic grants full `AllowReentry` (instead of restricted `AllowNext`) for the common non-zero-value `.transfer()`/`.send()` stipend case in the EVM-compat CALL handler - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

## Summary
`run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` decides reentrancy protection via a match on `(value.is_zero(), gas_limit == CALL_STIPEND)` whose first arm `(false, _) => (true, ReentrancyProtection::AllowReentry)` fires for any non-zero-value call regardless of `gas_limit`. Since solc emits `gas_limit = 0` (relying on the EVM's implicit 2300 stipend) for the standard `.transfer(amount)`/`.send(amount)` idiom, this is exactly the case that should receive the restricted `AllowNext` protection but instead receives unrestricted `AllowReentry`, while still only being allotted stipend-scale gas via `add_stipend = true`. This defeats the runtime's own explicit stipend-reentrancy guard described in `exec.rs`, whose doc comment states this enforcement exists precisely because Ethereum's stipend-gas-implies-no-reentrancy guarantee "does not automatically hold in revive."

## Finding Description
The code exactly matches the reported logic: [1](#0-0) 

Because the tuple match is evaluated with `value.is_zero()` first and `(false, _)` unconditionally maps to `AllowReentry`, any call with `value > 0` — including the case `gas_limit == 0` that solc uses for `.transfer()`/`.send()` per the project's own documented gas table — never reaches the `(_, true) => AllowNext` arm. Only the rare zero-value stipend calls (`transfer(0)`, `send(0)`, where solc explicitly emits `gas_limit = 2300`) get the intended restricted protection: [2](#0-1) 

`ReentrancyProtection::AllowNext` exists specifically to close this gap, as documented in its own definition: [3](#0-2) 

`AllowReentry` disables reentrancy protection entirely, permitting unrestricted recursive callbacks, whereas `AllowNext` restricts the callee to at most one level of same-contract reentry. The heuristic bug means the common, non-zero-value stipend-style transfer — which still only receives stipend-scale gas via `add_stipend = true` in the `(false, _)` arm — is executed with no reentrancy restriction at all, even though the code's own rationale (gas-scale differences between Ethereum and revive) is precisely why this class of call needs `AllowNext` enforcement. This is independently corroborated by a separate prdoc describing current (this) behavior as reachable: [4](#0-3) 

## Impact Explanation
This is a runtime logic bug that compromises the intended reentrancy-protection behavior for the single most common Solidity reentrancy-mitigation idiom (`.transfer()`/`.send()`), silently downgrading it from `AllowNext` to `AllowReentry`. That said, the concrete downstream state-corruption effect tracked separately in `prdoc/pr_12267.prdoc` (same-contract reentry double-counting `ContractInfo.storage_items`/`storage_bytes`/`storage_*_deposit`) is explicitly documented in-repo as **Low severity**, with no over-refund or fund theft possible: `Diff::update_contract`'s `.min(FixedU128::from_u32(1))` clamp prevents over-refund, and `do_terminate`'s `refund_all` reads actual on-hold balance rather than the inflated counters, so under-refund is the only effect and it is recoverable on termination. [5](#0-4) 

Taken on its own, the reentrancy-heuristic bug weakens intended runtime behavior (the reentrancy guard for stipend-style calls) but the only concretely documented, reachable exploitation of this gap in this repository produces an under-refund of storage deposit accounting — not theft, unbacked mint, duplicate settlement, or fund lock — and is already rated Low severity by the project itself.

## Likelihood Explanation
High reachability for triggering the mis-classification: any unprivileged account can deploy an EVM-compiled contract using `.transfer()`/`.send()` (the default solc idiom) and invoke it via ordinary `call` extrinsics, which reliably hits the buggy `(false, _)` arm since `value > 0` and `gas_limit == 0` is exactly what solc emits for this idiom.

## Recommendation
Fix the match logic in `run_call` so `AllowNext` is selected whenever the call is stipend-scale, independent of `value`: treat "stipend call" as `gas_limit == CALL_STIPEND` OR (`value > 0` AND `gas_limit == 0`, i.e., the EVM-implicit-stipend case for `.transfer()`/`.send()`), reserving `AllowReentry` only for calls that genuinely forward non-stipend gas (e.g., `.call{value: v}("")`). This should be landed together with the storage-accounting fix in `prdoc/pr_12267.prdoc` to ensure consistency.

3. Confirm via `run_call`'s `(false, _) => (true, AllowReentry)` arm that this transfer executes under `ReentrancyProtection::AllowReentry` rather than the intended `AllowNext`, using a debug assertion or test hook on `reentracy`.
