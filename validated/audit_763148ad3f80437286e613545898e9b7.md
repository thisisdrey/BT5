### Title
Cross-StackerDB replay of chunk signatures due to missing "audience" (contract) binding in `SlotMetadata` auth digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest over only `slot_id`, `slot_version`, and `data_hash` — it does not bind the signature to the specific StackerDB (`QualifiedContractIdentifier`) the chunk is intended for. This is structurally analogous to the SAML "missing audience verification" bug: a signed artifact that is valid in one context (one Service Provider / one StackerDB contract) can be replayed in a different context (another Service Provider / another StackerDB contract) if the recipient side does not itself bind the check to the intended context.

### Finding Description
`SlotMetadata::auth_digest()` is defined as: [1](#0-0) 

This digest — and therefore the signature produced by `SlotMetadata::sign` / verified by `SlotMetadata::verify` — commits only to `(slot_id, slot_version, data_hash)`: [2](#0-1) 

Verification of a received/pushed chunk is performed by `StackerDBSync::validate_received_chunk`, which looks up the expected signer *per contract* via `get_slot_signer(smart_contract_id, slot_id)`, then calls `slot_metadata.verify(&addr)`: [3](#0-2) 

Because the signature itself carries no reference to `smart_contract_id`, the "audience" (which StackerDB the chunk is authorized for) is enforced only by the verifier's out-of-band lookup of `get_slot_signer` for that specific contract — not by anything cryptographically bound into the signed payload. If the same signer public key hash (`StacksAddress`) is configured as the owner of the same `slot_id` in two different StackerDB contracts (which is plausible in practice, e.g. the signer set's own key reused across multiple different application-specific StackerDB contracts, or across `.signers-N` / miscellaneous stacker contracts), a signature and chunk produced for slot X, version V, data hash H in contract A is *also* a valid signature for slot X, version V, hash H in contract B, since `auth_digest` is identical. This is confirmed by the unit test suite, which only exercises wrong-signer and corrupted-metadata rejection, never rejection based on cross-database replay of an otherwise correctly-signed chunk: [4](#0-3) [5](#0-4) 

The HTTP POST endpoint (`RPCPostStackerDBChunkRequestHandler`) parses the contract identifier from the URL path and the chunk (with `slot_id`, `slot_version`, `sig`, `data`) from the JSON body independently — the contract is never mixed into the signed digest at the wire-format level either: [6](#0-5) 

`try_replace_chunk` (in `stackslib/src/net/stackerdb/db.rs`) is the storage-layer entry point invoked from this handler and from the sync path; based on the tests, it performs exactly the same class of check — signer lookup scoped by `smart_contract` id, then `SlotMetadata::verify` against that per-contract signer — again relying purely on the out-of-band DB lookup rather than an in-band audience binding.

### Impact Explanation
This breaks the intended equality "a signature authorizes a chunk for *this* StackerDB slot" into the weaker "a signature authorizes a chunk for *any* StackerDB slot with the same `(slot_id, slot_version, data_hash)` owned by the same signer." Where a signer key is reused as slot-owner across multiple StackerDB smart contracts (a configuration decision made by the contract deployer/operator, not defended against by the protocol), an attacker who observes one valid signed chunk broadcast on the network can rebroadcast/replay it as a `StackerDBChunkData`/`StackerDBPushChunkData` for a *different* StackerDB instance and have it accepted as authentic and stored/propagated there — an unauthorized write to state / forged-data propagation for that second StackerDB, without ever holding the signer's private key. This matches the report's underlying bug class (an authentication artifact validated in the wrong context because the intended "audience" was never verified) as opposed to the report's specific mechanism.

### Likelihood Explanation
Exploitability is conditioned on operational configuration: it requires a signer's public key hash to be registered as the owner of the same `slot_id` in more than one StackerDB contract that a node replicates, and requires reachable data reuse (identical `data_hash`) between the two, or an attacker's ability to get the same signer to sign the exact same content once and reuse the resulting signature elsewhere. This is a plausible but non-default configuration, and I could not fully verify from the indexed code whether any deployed/expected StackerDB configurations (e.g. `.signers`, `.miners`) actually reuse the same key across multiple concurrently-active StackerDB contract instances. This uncertainty should be resolved by a deeper audit of contract-side slot-owner sets, which is out of scope for static analysis of `stackslib/src/net/**`.

### Recommendation
Bind the target StackerDB's `QualifiedContractIdentifier` (and ideally the reward-cycle/consensus context, mirroring how `StackerDBHandshakeData.rc_consensus_hash` is already checked) into `SlotMetadata::auth_digest()`, so the signed digest becomes a function of `(smart_contract_id, slot_id, slot_version, data_hash)`. This requires a coordinated protocol/version change to `libstackerdb::SlotMetadata` and all callers (`StackerDBChunkData::sign`/`verify`, `db::try_replace_chunk`, `mod::validate_received_chunk`), since it changes the wire-verifiable message format.

### Proof of Concept
1. Operator configures two distinct StackerDB smart contracts, A and B, both listing the same `StacksAddress` (derived from signer key `K`) as the owner of `slot_id = 0`.
2. Signer `K` signs a legitimate `StackerDBChunkData { slot_id: 0, slot_version: 1, data: D }` for contract A; `sig` recovers to `K`'s address via `SlotMetadata::verify`, as in `auth_digest()` at `libstackerdb/src/libstackerdb.rs:159-166`.
3. Attacker (with no access to `K`'s private key) intercepts this chunk from the network, and re-submits the identical `StackerDBChunkData` (same `slot_id`, `slot_version`, `sig`, `data`) to contract B's slot 0 via `POST /v2/stackerdb/:address/:contract/chunks` (handled by `RPCPostStackerDBChunkRequestHandler` in `stackslib/src/net/api/poststackerdbchunk.rs`), or via the p2p `StackerDBPushChunkData` gossip path validated by `PeerNetwork::handle_unsolicited_StackerDBPushChunk` / `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs:649-717`.
4. Because `get_slot_signer(B, 0)` also returns `K`'s address, and `slot_metadata.verify(&addr)` only checks `(slot_id, slot_version, data_hash)` against `K`'s signature — with no contract-id binding — the chunk is accepted into contract B's replica as if legitimately authored for B, even though `K` never authorized data for B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

/// Decode the HTTP request
impl HttpRequest for RPCPostStackerDBChunkRequestHandler {
    fn verb(&self) -> &'static str {
        "POST"
    }

    fn path_regex(&self) -> Regex {
        Regex::new(&format!(
            r#"^/v2/stackerdb/(?P<address>{})/(?P<contract>{})/chunks$"#,
            *STANDARD_PRINCIPAL_REGEX_STRING, *CONTRACT_NAME_REGEX_STRING
        ))
        .unwrap()
    }

    fn metrics_identifier(&self) -> &str {
        "/v2/stackerdb/:principal/:contract_name/chunks"
    }

    /// Try to decode this request.
    /// There's nothing to load here, so just make sure the request is well-formed.
    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        captures: &Captures,
        query: Option<&str>,
        body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        if preamble.get_content_length() == 0 {
            return Err(Error::DecodeError(
                "Invalid Http request: expected non-empty body".to_string(),
            ));
        }

        if preamble.get_content_length() > MAX_MESSAGE_LEN {
            return Err(Error::DecodeError(
                "Invalid Http request: PostStackerDBChunk body is too big".to_string(),
            ));
        }

        let contract_identifier = request::get_contract_address(captures, "address", "contract")?;
        let chunk: StackerDBChunkData = serde_json::from_slice(body).map_err(Error::JsonError)?;

        self.contract_identifier = Some(contract_identifier);
        self.chunk = Some(chunk);

        Ok(HttpRequestContents::new().query_string(query))
    }
