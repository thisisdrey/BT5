Audit Report

## Title
Hardcoded per-command gas budgets in Snowbridge `ConstantGasMeter` can permanently strand unlocked/minted funds when the Ethereum recipient needs more gas - (File: `bridges/snowbridge/primitives/outbound-queue/src/v1/message.rs`)

## Summary
`ConstantGasMeter::maximum_dispatch_gas_used_at_most` assigns a fixed gas budget per outbound command (e.g., `UnlockNativeToken => 200_000`, `MintForeignToken => 100_000`) that is baked into `CommittedMessage.max_dispatch_gas` and used by the Ethereum Gateway to bound the value-transferring call for that command [1](#0-0) . Since the Substrate side already withdraws/burns the corresponding value when the message is committed and the nonce is consumed one-shot, any command whose real Ethereum-side execution needs more gas than the hardcoded constant reverts on Ethereum while the value is already gone on Substrate, with no retry mechanism in the V1 pipeline.

## Finding Description
Any unprivileged user can trigger `Command::UnlockNativeToken` via a standard reserve-asset-withdraw XCM on AssetHub; `XcmConverter::make_unlock_native_token_command` performs no origin check beyond a well-formed XCM shape [2](#0-1) . `do_process_message` commits the message with `max_dispatch_gas` fixed by `T::GasMeter::maximum_dispatch_gas_used_at_most`, increments the channel `Nonce`, and appends the message/leaf — all irreversibly, before any Ethereum-side execution occurs [3](#0-2) . The `CommittedMessage.max_dispatch_gas` field is committed as consensus data and used by the Gateway contract to bound the call [4](#0-3) .

Crucially, the V1 outbound-queue pallet has no delivery-receipt or success-tracking mechanism at all — `grep_search` over `bridges/snowbridge/**/v1/**` found no `InboundMessageDispatched`/`DeliveryReceipt`/`success` handling outside of test converters, unlike the V2 pipeline which does track a `DeliveryReceipt.success` bool via the `InboundMessageDispatched` event [5](#0-4) . This confirms V1 is fire-and-forget: once the nonce is consumed and burn/withdraw event is emitted (confirmed by the emulated test showing `Balances::Withdraw` from the Ethereum sovereign account as part of message construction) [6](#0-5) , there is no path to detect or compensate an Ethereum-side out-of-gas revert.

This is not hypothetical: PR #8259 raised the `TransferToken`/`UnlockNativeToken` gas budget from 100,000 to 200,000 specifically because the LDO token needed 140,000 gas against the then-current 100,000 budget [7](#0-6) , proving the hardcoded-constant model has already failed in practice for a real ERC20 token, with no systemic guard preventing recurrence for other tokens or complex recipients. Even in the V2 pipeline, which does track `success`, `process_delivery_receipt` pays the relayer reward based only on `order.fee > 0`, without branching on `receipt.success`, and there is no refund/reissue of the already-committed value if the Ethereum dispatch failed [8](#0-7) .

## Impact Explanation
When the constant gas budget for `UnlockNativeToken`/`MintForeignToken`/legacy `AgentExecute::TransferToken` is insufficient for a given token's transfer logic or a complex recipient contract, the Ethereum-side call reverts due to out-of-gas while the corresponding Substrate-side value has already been irrevocably withdrawn/burned and the nonce consumed. This matches the "permanent user-fund or bridge-state lock" impact gate: user funds are debited on Substrate with no successful unlock/mint counterpart on Ethereum, and V1 provides no automated retry or compensation path.

## Likelihood Explanation
This is demonstrated, not speculative — PR #8259 documents a real ERC20 (LDO) that exceeded the then-current gas budget for exactly this command family. Any unprivileged user can trigger the vulnerable code path simply by initiating a reserve-transfer of a token (existing or newly listed) whose transfer/hook logic, or whose recipient contract's fallback logic, exceeds the current hardcoded constant, with no relayer collusion, governance action, or privileged access required.

## Recommendation
- Do not treat message commitment/nonce consumption as final settlement on the Substrate side; only release/finalize burned value after on-chain proof that the paired Ethereum-side call succeeded, not merely that it was delivered.
- Replace the single hardcoded constant per command with a validated, per-token/per-command gas allowance (or forward a caller-supplied/estimated gas requirement with a safety margin), and add monitoring so underestimation is caught before user funds are affected.
- Provide a governed recovery/retry path (e.g., re-issue keyed by the original XCM message id) for commands whose Ethereum-side execution reverted due to gas exhaustion, and make `process_delivery_receipt`/reward payout in V2 explicitly branch on `receipt.success`.

## Proof of Concept
1. A user reserve-transfers an ERC20 token whose `transferFrom`/hook logic requires more gas than the current `UnlockNativeToken` budget (200,000) or `MintForeignToken` budget (100,000) — mirroring the already-observed LDO case that needed 140,000 gas against a 100,000 budget.
2. The XCM is converted into `Command::UnlockNativeToken`/`MintForeignToken` via `XcmConverter` with no origin restriction beyond XCM well-formedness.
3. `do_process_message` commits the message with `max_dispatch_gas` fixed by `ConstantGasMeter`, increments the nonce, and the corresponding value is already withdrawn from the sovereign/reserve account on the Substrate side.
4. On Ethereum, the Gateway's bounded-gas call to the token/recipient reverts due to insufficient gas.
5. The nonce is consumed and cannot be resubmitted in V1; the withdrawn/burned Substrate-side value has no corresponding successful unlock/mint on Ethereum, resulting in a stranded-fund state.

```rust
		/// Process a message delivered by the MessageQueue pallet
		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			ensure!(
				MessageLeaves::<T>::decode_len().unwrap_or(0) <
					T::MaxMessagesPerBlock::get() as usize,
				Yield
			);

			// Decode bytes into versioned message
			let versioned_queued_message: VersionedQueuedMessage =
				VersionedQueuedMessage::decode(&mut message).map_err(|_| Corrupt)?;

			// Convert versioned message into latest supported message version
			let queued_message: QueuedMessage =
				versioned_queued_message.try_into().map_err(|_| Unsupported)?;

			// Obtain next nonce
			let nonce = <Nonce<T>>::try_mutate(
				queued_message.channel_id,
				|nonce| -> Result<u64, ProcessMessageError> {
					*nonce = nonce.checked_add(1).ok_or(Unsupported)?;
					Ok(*nonce)
				},
			)?;

			let pricing_params = T::PricingParameters::get();
			let command = queued_message.command.index();
			let params = queued_message.command.abi_encode();
			let max_dispatch_gas =
				T::GasMeter::maximum_dispatch_gas_used_at_most(&queued_message.command);
			let reward = pricing_params.rewards.remote;

			// Construct the final committed message
			let message = CommittedMessage {
				channel_id: queued_message.channel_id,
				nonce,
				command,
				params,
				max_dispatch_gas,
				max_fee_per_gas: pricing_params
					.fee_per_gas
					.try_into()
					.defensive_unwrap_or(u128::MAX),
				reward: reward.try_into().defensive_unwrap_or(u128::MAX),
				id: queued_message.id,
			};
```

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
