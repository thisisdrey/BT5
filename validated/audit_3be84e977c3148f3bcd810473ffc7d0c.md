### Title
Index-invalidation during in-place removal loop causes stale duplicate replication jobs to escape cleanup - (File: internal/praefect/datastore/memory.go)

### Summary
`memoryReplicationEventQueue.Acknowledge()` contains a loop that removes duplicate queue entries by index while iterating forward, but the iteration index is not adjusted after a removal shrinks the backing slice. This causes the very next candidate entry to be skipped and never evaluated for cleanup, mirroring the reported bug class where a function uses one index to check/complete an item and a different, unadjusted index to mutate the underlying collection.

### Finding Description
`Acknowledge()` locates the queued event matching an acknowledged `id` at index `i`, and, when the new state is `JobStateCompleted`, scans forward from `i+1` to prune other queued entries that represent the same job and were created before the just-acknowledged job's `dequeuedAt`: [1](#0-0) 

```go
for j := i + 1; j < len(s.queued); j++ {
    if dequeuedAt.Before(s.queued[j].CreatedAt) {
        break
    }
    sameJobData, err := json.Marshal(s.queued[j].Job)
    ...
    if bytes.Equal(ackJobData, sameJobData) {
        s.remove(j)
    }
}
```

`remove()` deletes the slice element in place via `append(s.queued[:i], s.queued[i+1:]...)`: [2](#0-1) 

Each call to `s.remove(j)` shifts every element after `j` down by one position, so what used to be at `j+1` is now at `j`. The loop, however, increments `j` unconditionally on the next iteration, so it advances to what is now the *following* element and never (re-)inspects the element that just shifted into slot `j`. That element is silently skipped from the duplicate-pruning pass — the exact class of bug described in the report, where the code advances/removes using one index while the "current" item to evaluate has effectively moved to a different index.

### Impact Explanation
When several replication events targeting the same virtual-storage/target-storage/repository destination are queued back-to-back (which routinely happens for ordinary user pushes/fetches that Praefect replicates to secondary Gitaly nodes), acknowledging one of them as `JobStateCompleted` is supposed to prune the now-redundant duplicate entries queued right after it. Due to the index-shift bug, one of the duplicates in each run of 3+ same-destination entries is skipped and left behind in `s.queued` in its original (`Ready`/`Failed`) state. This entry is not lost from correctness in terms of crashing, but it defeats the purpose of the deduplication pass: a redundant replication job that should have been pruned survives and will be dequeued and replicated again later, needlessly repeating replication work and consuming worker cycles for every burst of same-destination writes. This is a resource-hygiene / minor DoS issue for the in-memory replication queue (`Praefect` with `memory_queue_enabled = true`), not a hard failure like the reported ETH-locking bug, since `Dequeue()` still finds and processes the skipped entry on a subsequent pass instead of being permanently stuck.

### Likelihood Explanation
The `memoryReplicationEventQueue` is a real, config-selectable production code path (`conf.MemoryQueueEnabled`) wired up in `internal/cli/praefect/serve.go`, not test-only code. Any ordinary user push/fetch to a virtual storage triggers Praefect to enqueue replication `ReplicationEvent`s for each secondary node, and multiple close-in-time writes to the same repository/destination are common (e.g., rapid successive pushes, CI-driven pipelines). Triggering three or more overlapping same-destination events queued in sequence is a routine operational scenario when this queue backend is enabled, making the bug easily reachable without any special privilege.

### Recommendation
Do not increment `j` after a successful in-place removal; instead, re-evaluate the same index (`j` should stay the same, or the loop should decrement/adjust after `s.remove(j)`), or bound the loop over a stable snapshot of candidate entries (e.g., collect matching indices first, then remove them in reverse order) so that no candidate for pruning is skipped due to slice-index invalidation.

### Proof of Concept
Given `s.queued` containing four events for the same destination `[i, i+1(A), i+2(B), i+3(C)]`, where `A`, `B`, `C` are duplicate jobs created before `dequeuedAt`:
1. `Acknowledge` marks event `i` as `JobStateCompleted` and starts the inner loop at `j = i+1`.
2. `j = i+1` matches `A`; `s.remove(i+1)` shifts `B` into slot `i+1` and `C` into slot `i+2`.
3. Loop increments to `j = i+2`, which is now `C` (originally at `i+3`); `B` (now sitting at `i+1`) is never inspected again in this pass and is left in the queue even though it should have been pruned as a duplicate.
4. `B` remains queued in its original `Ready`/`Failed` state and is later re-dequeued and replicated redundantly instead of being pruned as intended.
