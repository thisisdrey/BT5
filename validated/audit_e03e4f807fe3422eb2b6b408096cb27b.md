## Analysis: Unchecked `liquidatee_accounts` / `liquidator_accounts` lengths in `lending_account_liquidate`

The Gearbox `CreditFilter.sol` bug is about missing validation that array-length parameters match the actual arrays. The closest analog I found in marginfi-v2 is the `liquidatee_accounts` / `liquidator_accounts` `u8` counters passed into the permissionless `lending_account_liquidate` instruction, which are used to slice `ctx.remaining_accounts` without any check that they add up to the actual number of remaining accounts supplied.

### Finding Description
`lending_account_liquidate` takes two caller-supplied `u8` counts, `liquidatee_accounts` and `liquidator_accounts`, describing how many trailing remaining-account entries belong to the liquidatee and liquidator observation lists, per the documented schema `[liab_mint_ai?, asset_oracle_ai, liab_oracle_ai, liquidator_observation_ais..., liquidatee_observation_ais...]`. [1](#0-0) 

The instruction uses these counts to compute slice boundaries via plain subtraction, with no check that `liquidatee_accounts + liquidator_accounts + fixed_oracle_accounts == ctx.remaining_accounts.len()`:
```
let init_liquidatee_remaining_len = liquidatee_accounts as usize;
let liquidatee_accounts_starting_pos =
    ctx.remaining_accounts.len() - init_liquidatee_remaining_len;
let liquidatee_remaining_accounts = &ctx.remaining_accounts[liquidatee_accounts_starting_pos..];
...
let liquidator_remaining_acc_len = liquidator_accounts as usize;
let liquidator_accounts_starting_pos =
    liquidatee_accounts_starting_pos - liquidator_remaining_acc_len;
let liquidator_remaining_accounts =
    &ctx.remaining_accounts[liquidator_accounts_starting_pos..liquidatee_accounts_starting_pos];
``` [2](#0-1) [3](#0-2) 

Additionally, `fetch_asset_price_for_bank_low_bias` and the insurance-fee SPL transfer use `ctx.remaining_accounts` directly (the full unsliced array) rather than a bank-specific slice bounded by the declared counts. [4](#0-3) [5](#0-4) 

### Impact Explanation
If `liquidatee_accounts` or `liquidator_accounts` do not match the actual number of remaining accounts truly belonging to each side (e.g., an attacker-liquidator supplies a `liquidator_accounts` value smaller or larger than the real observation account count, or supplies overlapping/duplicate account slices), the resulting `liquidatee_remaining_accounts` / `liquidator_remaining_accounts` slices used for `check_pre_liquidation_condition_and_get_account_health`, `check_post_liquidation_condition_and_get_account_health`, and `check_account_init_health` would not correspond to the correct set of bank/oracle accounts for that account. Since health checks are the sole gate preventing over-liquidation and preventing the liquidator from ending up in an unhealthy/undercollateralized state, a mismatch could let a health check operate on a wrong/partial account list (e.g., omitting a large liability, or including manipulated oracle data belonging to a different bank slice), causing the health check to pass when it should fail. Underflow in the subtractions (`ctx.remaining_accounts.len() - liquidatee_accounts`, `liquidatee_accounts_starting_pos - liquidator_accounts`) if the counts exceed the actual remaining-accounts length would panic (an availability/DoS impact only), but a crafted count within bounds that simply mis-assigns which accounts belong to which "side" is the more concerning path for the health-check-bypass class of issue this bug report is analogous to.

### Likelihood Explanation
This is a permissionless instruction (no privileged signer required for the counts) reachable by any liquidator, matching the "unprivileged-user" scope. However, I was not able to conclusively prove within this pass that a specific mis-sized/mis-assigned `liquidatee_accounts`/`liquidator_accounts` value actually causes `check_pre_liquidation_condition_and_get_account_health`, `check_post_liquidation_condition_and_get_account_health`, or `check_account_init_health` to accept an account list that omits a real liability/asset or substitutes a manipulated one, rather than simply causing a deterministic panic (transaction revert) on any mismatch. The downstream health-check functions (`get_remaining_accounts_per_bank`, `check_pre_liquidation_condition_and_get_account_health`, etc.) may perform their own internal per-balance account-count validation that would reject a malformed/undersized slice before it could be exploited for a health bypass — I did not fully trace that code path in the available time. Given the uncertainty about whether a concrete bypass (versus a benign panic/DoS) is achievable, I cannot assert with confidence that this rises to concrete theft/insolvency/unauthorized-state-change without further code tracing (specifically into `get_remaining_accounts_per_bank` and the health-check implementations in `state/marginfi_account.rs`), which was not fully explored in this session.

### Recommendation
Add an explicit assertion in `lending_account_liquidate` that `liquidatee_accounts as usize + liquidator_accounts as usize + <fixed oracle/mint account count>` equals `ctx.remaining_accounts.len()` before performing any slicing, and use checked (non-panicking, explicit-error) arithmetic instead of raw `usize` subtraction when computing `liquidatee_accounts_starting_pos` and `liquidator_accounts_starting_pos`, returning a descriptive `MarginfiError` on mismatch rather than allowing either an underflow panic or a silently mis-sliced account list.

### Proof of Concept
Not constructed — building a working PoC requires deeper verification of whether `check_pre_liquidation_condition_and_get_account_health` / `check_account_init_health` independently validate that the supplied remaining-account slice length matches the number of active balances in the account (via `get_remaining_accounts_per_bank`), which would determine whether a mismatched `liquidatee_accounts`/`liquidator_accounts` count is exploitable beyond causing a revert. I was unable to complete this trace within the available tool budget.
