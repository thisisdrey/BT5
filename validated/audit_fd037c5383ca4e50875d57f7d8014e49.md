### Title
Missing zero-address check on `depositTokenOf` causes permanent loss of user ETH - ([File: contracts/NativeTokenGateway.sol](contracts/NativeTokenGateway.sol))

### Summary
The Apache null-pointer-dereference bug class maps to dereferencing an uninitialized/null reference. In `NativeTokenGateway.deposit`/`withdraw` and `VesperGateway.deposit`/`withdraw`, the contract resolves `pool_.depositTokenOf(underlying)` and immediately calls `safeApprove`, `deposit`, `safeTransferFrom`, and `withdraw` on the returned address without checking it is non-zero. When the queried mapping entry does not exist, `depositTokenOf` returns `address(0)`. Low-level calls to `address(0)` through `SafeERC20`/`Address` succeed silently (empty returndata is treated as `true`), so the transaction does not revert while the user's real assets have already been pulled in.

### Finding Description
In `NativeTokenGateway.deposit` (contracts/NativeTokenGateway.sol:46-54):

```solidity
nativeToken.deposit{value: msg.value}();                        // ETH already wrapped into WETH
IDepositToken _depositToken = pool_.depositTokenOf(nativeToken); // address(0) if WETH not listed in pool_
nativeToken.safeApprove(address(_depositToken), msg.value);     // no-op success on address(0)
_depositToken.deposit(msg.value, _msgSender());                  // no-op success on address(0)
```

The only guard is `_poolRegistry.isPoolRegistered(address(pool_))`, which checks the *pool*, not that `nativeToken` is a collateral of that pool. Metronome supports multiple registered pools; a pool that does not list WETH returns `address(0)` from `depositTokenOf`. The caller's ETH is converted to WETH and left in the gateway, recoverable only via governor `sweep` (`TokenHolder`). The same pattern exists in `withdraw` (line 65: `safeTransferFrom` on `address(0)` succeeds, then `withdraw` reverts on empty returndata decode — self-revert only) and in `VesperGateway.deposit`/`withdraw` (contracts/VesperGateway.sol:61,79), where an arbitrary `vToken_` whose underlying has no deposit token strands the freshly minted vTokens in the gateway.

### Impact Explanation
Permanent loss of user funds: the caller's ETH/vToken-underlying is pulled into the gateway contract while the crediting leg (`DepositToken.deposit`) is a silent no-op on `address(0)`. The funds sit in the gateway and can only be moved by governor `sweep`, i.e., they are effectively seized/stuck. This matches the "null pointer dereference" class: an unchecked null reference is dereferenced mid-transaction after the state-changing asset intake already happened.

### Likelihood Explanation
Reachable by any unprivileged caller calling `NativeTokenGateway.deposit{value: X}(pool)` on a registered pool lacking a WETH deposit token, or `VesperGateway.deposit(pool, vToken, amount)` for a vToken with no registered deposit token. No privileged role, oracle manipulation, or front-running is required; the flaw is the missing `AddressIsNull`-style check on `depositTokenOf` results (the codebase uses `AddressIsNull`/`UnderlyingAssetIsNull` errors elsewhere but not here).

### Recommendation
Revert when `pool_.depositTokenOf(underlying)` returns `address(0)` in `NativeTokenGateway.deposit`, `NativeTokenGateway.withdraw`, `VesperGateway.deposit`, and `VesperGateway.withdraw` before performing any token pull/approve. Prefer routing through `Pool.deposit`/`Pool.withdraw`, which validate the collateral internally.

### Proof of Concept
```solidity
// Foundry fork test sketch
function testNullDepositTokenLoss() public {
    // poolB is a *registered* Pool but WETH was never added as collateral
    assertTrue(poolRegistry.isPoolRegistered(address(poolB)));
    assertEq(address(poolB.depositTokenOf(address(weth))), address(0));

    uint256 balBefore = address(gateway).balance;
    vm.deal(user, 1 ether);
    vm.prank(user);
    gateway.deposit{value: 1 ether}(poolB); // succeeds — no revert

    // User received no deposit tokens; 1 ether of WETH is stuck in the gateway
    assertEq(weth.balanceOf(address(gateway)), 1 ether);
    assertEq(IDepositToken(address(0)).balanceOf(user), 0);
}
```

Note: `withdraw` variants self-revert on the returndata decode, so the exploitable legs are the two `deposit` functions; the stranded assets are only recoverable via the governor's `TokenHolder.sweep`.
