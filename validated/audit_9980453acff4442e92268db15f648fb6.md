### Title
Wallet Contract pays relayer fee for emulated ERC-20 transfers even when the target contract does not correctly implement NEP-141, causing unconditional loss of user funds - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The eth-implicit Wallet Contract's `rlp_execute` flow emulates Ethereum ERC-20 `transfer` calls by translating them into NEP-141 `ft_transfer` calls, assuming the target contract behaves like a standard NEP-141 token (implements `storage_balance_of`, `storage_deposit`, `ft_transfer` correctly). If the target token contract does not actually conform to this assumed interface — analogous to an ERC-777 token that does not implement ERC-20's `transfer` — the transfer promise chain fails, but the relayer fee has already been paid out unconditionally before that chain even starts, resulting in a permanent loss of the fee for the user with no corresponding action performed.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , whenever the parsed transaction kind is `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the wallet contract immediately creates a standalone promise batch and transfers the fee to the relayer (`predecessor_account_id`) via `env::promise_batch_action_transfer`. This happens synchronously, in the same host-function calls as nonce incrementing, before the actual token-transfer promise is even constructed.

The actual attempt to perform the emulated ERC-20 transfer happens later and independently, in a separate promise chain: first `storage_balance_of` is called on the target token contract [2](#0-1) , then (depending on the result) `storage_deposit` + the actual `ft_transfer`-equivalent function call are dispatched in `nep_141_storage_balance_callback` [3](#0-2) , with final success/failure resolved in `rlp_execute_callback` [4](#0-3) .

Because the fee-payment promise and the transfer-attempt promise chain are entirely disjoint (the fee promise is not `.then()`-chained to, or contingent on, the transfer succeeding), any failure in the transfer chain — e.g. because the `target` account does not actually implement the NEP-141 interface the way the wallet contract assumes (mirrors the ERC-777/ERC-20 mismatch in the external report), or because `storage_balance_of`/`ft_transfer` panics, returns unexpected data, or is simply absent — still results in the relayer being paid. The only remediation on failure is refunding `caller_deposit` (the attached $NEAR deposit from an external, non-owner caller) in `rlp_execute_callback`; the relayer fee itself is never clawed back regardless of outcome.

### Impact Explanation
Because the emulated ERC20Transfer's nonce is incremented and the fee is paid out before it is known whether the underlying NEP-141-style call chain will succeed, a target contract that does not conform to the expected NEP-141 interface (whether by design, bug, or simply not existing/being incompatible) causes: (1) the user's fee funds to be permanently transferred to the relayer for no delivered service, and (2) the intended token transfer to silently fail with no way to retry (the nonce was already consumed). This is a concrete, permanent loss of user funds triggered purely by interacting with a real but non-compliant/incompatible token contract, exactly analogous to the ERC-777/ERC-20 root cause in the external report where an assumed interface function does not exist on the target token.

### Likelihood Explanation
This is reachable by any ordinary wallet-contract user attempting to emulate an ERC-20 transfer of a token that is not implemented as a byte-for-byte standard NEP-141 contract (e.g., a token missing `storage_balance_of`, changing its return-value shape, or failing for other legitimate reasons), which is a realistic and common occurrence given the wide variety of token implementations, and requires no special privileges from the relayer or user beyond normal use of `rlp_execute`.

### Recommendation
Chain the relayer-fee transfer to the outcome of the actual transfer promise (e.g., only pay the fee inside `rlp_execute_callback` after confirming `PromiseResult::Successful`), rather than firing it unconditionally at the start of `inner_rlp_execute`. Alternatively, refund the fee back to the user (or re-credit the nonce so the user can retry) whenever the downstream transfer promise chain resolves as `Failed`.

### Proof of Concept
1. User signs an Ethereum-style transaction via the Wallet Contract representing an emulated ERC-20 `transfer` to `target` = some deployed contract account that is not a standards-compliant NEP-141 token (e.g., it lacks a `storage_balance_of` method, or its `ft_transfer`-equivalent panics), with a non-zero `fee` for the relayer.
2. Relayer submits this transaction via `rlp_execute` per `inner_rlp_execute` [5](#0-4) : nonce is incremented and the fee promise batch transfer to the relayer executes immediately.
3. The promise chain then calls `storage_balance_of` on `target`; since `target` does not implement this method, `PromiseResult::Failed` propagates to `nep_141_storage_balance_callback`/`rlp_execute_callback`, and the ExecuteResponse reports `success: false`.
4. Result: the relayer has already received the fee (step 2), the user's nonce has been consumed so the transaction cannot be resubmitted, and the intended token transfer never happened — a permanent loss of the fee amount for the user with no compensating transfer.

    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
