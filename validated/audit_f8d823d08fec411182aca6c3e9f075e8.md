### Title
Anti-replay guard on handshake completion relies on peer-supplied `lastHandshakeTime`, which can diverge from the local clock and be manipulated to win the `CheckAndComplete` race - ([File: handshake_manager.go])

### Summary
The report describes a bug class where two independently-updated timestamps that are supposed to stay in lock-step (`lastPriceTimestamp` in `LeveragedPool` and `lastUpdate` in `SMAOracle`) can diverge because one side is fed by an open, unauthenticated update path while the other is gated by a permissioned process. When the two diverge beyond a safety margin, an attacker can use the "stale" value to win a race and force a favorable outcome. The Nebula analog is `hostinfo.lastHandshakeTime`, a value used specifically "to avoid an attack where a handshake packet is replayed after some time" [1](#0-0) , but whose only source of truth is the unauthenticated `Time` field carried inside the handshake payload, set by whichever peer builds the message with `p.Time = uint64(time.Now().UnixNano())` [2](#0-1) .

### Finding Description
`lastHandshakeTime` exists purely as an anti-replay control comparing a "new" incoming handshake against the "existing" hostinfo for the same VPN address:

```go
// Is this a newer handshake?
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}
``` [3](#0-2) 

This value is populated from `Result.HandshakeTime`, which in turn comes straight from the peer-supplied `payload.Time` field with no server-side clock check, monotonicity check against previous handshakes for that peer, or bound against local time:

```go
m.result.RemoteIndex = remoteIndex
m.result.HandshakeTime = payload.Time
m.payloadSet = true
``` [4](#0-3) 

The value written into that field on the sending side is simply `time.Now().UnixNano()` taken from the sender's own clock at message-build time:
```go
p.Time = uint64(time.Now().UnixNano())
``` [5](#0-4) 

Because `Time` is attacker-controlled wire data (it is not authenticated by, or bound to, anything the receiver can independently verify — it is simply carried in the AEAD-protected but otherwise arbitrary payload), an attacker who can complete a handshake (which does not require possessing a CA-signed certificate for the *victim's* identity, since the value is set before any peer certificate/identity binding is enforced on this field) can choose an arbitrarily large `Time` value for a first handshake, then replay-or-force a legitimately newer handshake to be rejected as "too old":

```go
case ErrExistingHostInfo:
    f.l.Info("Handshake too old", ... "oldHandshakeTime", existing.lastHandshakeTime, "newHandshakeTime", hostinfo.lastHandshakeTime, ...)
``` [6](#0-5) 

This is structurally the same bug class as the report: a value meant to be a tamper-resistant, monotonically-increasing synchronization point between two independently-computed states (here: the "existing" hostinfo state vs a "new" incoming handshake state) is instead sourced from an unauthenticated, freely-chosen input, allowing the two comparison points to diverge in a way that benefits whichever party controls the larger reported value.

### Impact Explanation
An attacker who can reach the handshake responder path (any UDP peer allowed by `remote_allow_list`, which does not require a signed certificate of its own identity to submit a first-stage handshake to a target) can poison the anti-replay ordering used by `CheckAndComplete`. By supplying an inflated `Time` value in the handshake payload, the attacker's stale/rogue handshake can permanently or temporarily block a legitimate peer's newer, correct handshake for the same `vpnAddr` from being accepted, since `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` will be evaluated using the attacker's forged timestamp rather than a value verified against the local clock or a monotonic session counter. This is a remote state-poisoning / denial-of-tunnel-establishment impact directly analogous to a front-running/priority-manipulation impact, achieved purely by exploiting divergence between an authenticated state (existing tunnel) and an attacker-influenced state (new handshake's claimed time).

### Likelihood Explanation
The `Time` field is read and used in the `CheckAndComplete` comparison for every completed handshake without any bound checking against the receiver's own clock or previous values for that peer, so the field is reachable on every handshake attempt an attacker can initiate. The only friction is the `remote_allow_list` gate on `HandleIncoming`, which restricts source *addresses*, not the handshake payload contents, so it does not mitigate a forged `Time` value.

### Recommendation
Do not trust the wire-supplied `Time` field as the sole ordering key for the anti-replay/"is this handshake newer" decision. Either (a) bind `lastHandshakeTime` to the receiver's own clock at receipt time rather than the peer-supplied value, or (b) validate the peer-supplied `Time` against a reasonable window of the receiver's local clock and reject values that are implausibly far in the future, and/or (c) use a monotonic per-tunnel handshake/session counter that the receiver itself maintains instead of relying on an unauthenticated timestamp claimed by the remote peer.

### Proof of Concept
1. Attacker (or any peer allowed by `remote_allow_list`) crafts/sends a stage-1 handshake to victim `V` for `vpnAddr A`, with the handshake machine setting `p.Time = uint64(time.Now().UnixNano())` far in the future (attacker controls the local clock/machine building the packet, e.g. by running a modified client) — this becomes `existingHostInfo.lastHandshakeTime` once the tunnel completes.
2. The legitimate owner of `A` later performs a normal re-handshake (e.g., after roaming or restart) with a real, smaller/current `Time` value.
3. In `CheckAndComplete`, `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` evaluates true (attacker's forged time is larger), so the legitimate handshake is rejected with `ErrExistingHostInfo`, and the victim cannot re-establish the tunnel until the connection manager independently tears down the attacker's stale tunnel — reproducing the "diverged synchronization timestamp exploited for a favorable outcome" bug class from the report. Full confirmation requires instrumenting `handshake/machine.go`'s `marshalOutgoing` to inject an artificially large `Time` and observing `handleCheckAndCompleteError`'s `ErrExistingHostInfo` branch fire against a legitimate concurrent handshake in the e2e test harness (e.g., extending `handshake_manager_test.go`); this was not run/verified in a live environment as part of this analysis.
