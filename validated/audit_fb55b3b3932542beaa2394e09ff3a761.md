### Title
Liquidation can permanently strand bad debt by leaving collateral below the amount needed to repay the debt floor - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces `debtFloorInUsd` only against the debt remaining after liquidation, but it does not ensure that the collateral remaining afterward is sufficient to complete a later liquidation. An attacker can therefore liquidate their own unhealthy position from a second account, reduce the debt exactly to the floor, and leave less collateral than the amount required to seize when repaying that remaining debt.

### Finding Description
`Pool.liquidate` permits any account other than `account_` to repay an unhealthy position and seize collateral. [1](#0-0)  Before collateral is transferred, the function rejects a nonzero remaining debt below `debtFloorInUsd`, but it does not require the post-liquidation collateral balance to remain sufficient for a subsequent liquidation. [2](#0-1)  The liquidation quote adds the liquidator incentive and protocol fee to the collateral amount, so repaying the full remaining debt requires more collateral than the debt's nominal value. [3](#0-2) 

For example, assume:

- collateral factor = 70%
- liquidator incentive = 10%
- protocol liquidation fee = 0%
- `debtFloorInUsd = $100`
- `maxLiquidable = 50%`

The attacker deposits collateral worth `$300` and issues `$200` of debt, which is initially healthy because the issuable limit is `$210`. After a legitimate collateral price decline to `$200`, the position is unhealthy because the limit is now `$140`. The attacker transfers their synthetic tokens to a second EOA and liquidates their own account by repaying `$100`, which is permitted because self-liquidation is blocked only when liquidator and debtor are the same address. The liquidation seizes `$110` of collateral, leaving `$100` of debt and `$90` of collateral.

The resulting position is still unhealthy, but it cannot be liquidated:

- Repaying any amount below `$100` leaves nonzero debt below `$100` and reverts with `RemainingDebtIsLowerThanTheFloor`.
- Repaying the full `$100` requires seizing `$110`, exceeding the `$90` collateral balance and reverting with `AmountIsTooHigh`.

This breaks the debt floor's intended liquidation-incentive property: the stored debt remains at or above the floor, but the remaining collateral is insufficient to pay for clearing it. [4](#0-3) 

### Impact Explanation
An unprivileged user can intentionally create a permanently unliquidatable underwater position. The protocol retains bad debt while the associated collateral cannot be seized through `Pool.liquidate`, causing a direct protocol-insolvency condition. The attacker can also receive the normal liquidation incentive through the second account while constructing the stuck state.

### Likelihood Explanation
The attack requires an unhealthy position, a nonzero debt floor, and enough collateral to perform the intermediate liquidation. `CanNotLiquidateOwnPosition` compares only the liquidator and account addresses, so the attacker can use a second EOA or attacker-controlled contract holding the previously issued synthetic tokens. [5](#0-4)  The default `maxLiquidable` initialization of 50% permits the example's repayment of half the outstanding debt. [6](#0-5) 

### Recommendation
During liquidation, enforce that either:

1. the remaining debt is zero, or
2. the remaining collateral is sufficient to seize `quoteLiquidateOut(remainingDebt)`.

Alternatively, when a liquidation would leave collateral below the minimum profitable liquidation amount, require the liquidator to repay all remaining debt or move the residual collateral into an escrowed balance excluded from account health but still available for bad-debt resolution.

### Proof of Concept
A Hardhat test can reproduce the state using the existing mock deployment flow:

```ts
it('creates an unliquidatable dust-collateral debt position', async function () {
  // Initial fixture state:
  // - MET collateral factor = 70%
  // - liquidator incentive = 10%
  // - protocol liquidation fee = 0
  // - pool.debtFloorInUsd() = $100
  // - alice has $300 of msdMET collateral
  // - alice has $200 of msDebt

  const debtToken = msDebtToken
  const synth = msToken
  const collateral = msdMET

  // Move collateral price so Alice has $200 collateral and $200 debt.
  // Issuable limit = $200 * 70% = $140, so the position is unhealthy.
  await masterOracle.updatePrice(met.address, parseEther('0.666666666666666667'))

  expect((await pool.debtPositionOf(alice.address))._isHealthy).false

  const debtBefore = await debtToken.balanceOf(alice.address) // $200
  const repayAmount = debtBefore.div(2)                      // $100

  // Alice previously received the minted synthetic tokens and sends them
  // to another account she controls.
  await synth.connect(alice).transfer(attacker.address, repayAmount)

  // Liquidating through another address bypasses the same-address check.
  await pool
    .connect(attacker)
    .liquidate(synth.address, alice.address, repayAmount, collateral.address)

  // Debt is exactly the floor, while collateral is only $90 because
  // repaying $100 seized $110 at a 10% incentive.
  const debtAfter = await debtToken.balanceOf(alice.address)
  const collateralAfter = await collateral.balanceOf(alice.address)

  expect(debtAfter).eq(await tokenAmountForUsd(synth, parseEther('100')))
  expect(await usdValueOf(collateral, collateralAfter)).eq(parseEther('90'))

  // Partial liquidation leaves a nonzero debt below the floor.
  await expect(
    pool
      .connect(liquidator)
      .liquidate(synth.address, alice.address, debtAfter.sub(1), collateral.address)
  ).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

  // Full liquidation requires seizing $110 but only $90 remains.
  await expect(
    pool
      .connect(liquidator)
      .liquidate(synth.address, alice.address, debtAfter, collateral.address)
  ).revertedWithCustomError(pool, 'AmountIsTooHigh')
})
```
