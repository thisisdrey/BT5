### Title
Stale PendingDataCount/PostponedReceipt rows survive `remove_account`, allowing a postponed receipt to execute against a recreated account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only removes the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for an account; it never scans or removes `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::ReceivedData`, or the `PromiseYield*`/`YieldIdToDataId` families. If an account is deleted while it has an unresolved multi-input promise (`promise_and`), the leftover bookkeeping rows persist in the trie under the account's key prefix and can later be manipulated when the same account ID is recreated.

### Finding Description
`remove_account` ( [1](#0-0) ) removes exactly four categories of state:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- Access keys and gas key nonces (via `get_raw_prefix_for_access_keys` iteration)
- `TrieKey::ContractData` (via `get_raw_prefix_for_contract_data` iteration)

It does **not** iterate or clear `PENDING_DATA_COUNT` (col 5), `POSTPONED_RECEIPT` (col 6), `POSTPONED_RECEIPT_ID` (col 4), `RECEIVED_DATA` (col 3), `PROMISE_YIELD_RECEIPT`/`PROMISE_YIELD_STATUS`, or `YIELD_ID_TO_DATA_ID`/`DATA_ID_TO_YIELD_ID`, all of which are listed as account-keyed columns in `core/primitives/src/trie_key.rs` (`col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`) ( [2](#0-1) ).

An attacker fully controls the exploit setup from an ordinary account: submit a contract call that issues `promise_and` with two dependent receipts targeting itself, wait for exactly one `DataReceipt` to be delivered (which decrements `PendingDataCount` from 2 to 1 and leaves the `PostponedReceipt` stored), then submit a `DeleteAccount` action. `remove_account` runs but leaves the `PendingDataCount{receiver_id, receipt_id}` and `PostponedReceipt{receiver_id, receipt_id}` rows intact in the trie. The attacker (or anyone) then submits `CreateAccount` for the same `account_id`. When the second `DataReceipt` is later delivered (it is a receipt already in flight in the network/shard queue and cannot be intercepted or cancelled by the account owner), the runtime decrements the stale `PendingDataCount` to zero and triggers execution of the orphaned `PostponedReceipt` — now running against the newly created account's balance/code/state, which the new owner never authorized to receive that action set.

### Impact Explanation
This falls under authorization escalation across accounts/promises and potential fund theft or unintended privileged action execution: a receipt constructed and paid for under the old account's context can execute against the new account's post-recreation trie state without the new owner's consent. Depending on the actions embedded in the postponed receipt (e.g., `FunctionCall`, `Transfer`, `DeleteKey`, `AddKey`), this could result in state changes or fund movement the new account owner did not authorize.

### Likelihood Explanation
The precondition requires: (1) an account issuing a `promise_and` with ≥2 data dependencies, (2) at least one dependency resolved before deletion, (3) `DeleteAccount` executed while the count is still nonzero, and (4) the account ID being reused via `CreateAccount` before the remaining `DataReceipt` arrives. All of these are actions available to an ordinary unprivileged account and require no validator/node access. The attack is fully reproducible by the account owner alone (self-targeted) and does not require tricking a third party, though the described "new owner" variant (a third party claiming the deleted name) depends on account-ID squatting timing, which is feasible but adds some non-determinism (the new owner must claim the name before the pending data arrives).

### Recommendation
Extend `remove_account` to also scan and delete the `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` prefixes for the account, mirroring the existing access-key/contract-data iteration pattern, before allowing `DeleteAccount` to complete (or reject `DeleteAccount` outright while any of these rows exist for the account).

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or an integration/runtime test):
1. Construct a `TrieUpdate` and `set` a `TrieKey::PendingDataCount{receiver_id, receipt_id}` value (e.g. `1u32`) and a corresponding `TrieKey::PostponedReceipt{receiver_id, receipt_id}`.
2. Call `remove_account(&mut state_update, &account_id)`.
3. Assert `get::<u32>(&state_update, &TrieKey::PendingDataCount{receiver_id, receipt_id})` returns `Some(_)` (currently true — the bug), and likewise `get_postponed_receipt(...)` still returns `Some(_)`.
4. Extend to a full `test-loop`/runtime integration test: create account A, issue `promise_and` with two `DataReceipt` dependencies to itself, deliver one, delete A, recreate A, deliver the second `DataReceipt`, and assert the postponed receipt's actions executed against the recreated account's state despite no `PromiseYield`/`promise_and` authorization existing for the new account incarnation.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
