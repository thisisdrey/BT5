### Title
Unchecked `Currency::transfer` in `claim_bounty`/`claim_child_bounty` lets funds get permanently stranded while the bounty state is deleted as "paid" - ([File: substrate/frame/bounties/src/lib.rs])

### Summary
`pallet-bounties::claim_bounty` and `pallet-child-bounties::claim_child_bounty` push funds from the bounty's sub-account to the `curator` and `beneficiary` via `T::Currency::transfer(..., AllowDeath)`, but the result of that transfer is only checked with `debug_assert!`, which compiles to a no-op in release builds. Regardless of whether the transfer actually succeeds, the code unconditionally deletes the bounty record and emits `BountyClaimed`. This is the same broken invariant as the tbtc `purchaseSignerBondsAtAuction` bug: a push payment to an attacker-influenced/arbitrary account is treated as authoritative for state progression, but the transfer can legitimately fail (there, `.transfer()` reverting; here, `Currency::transfer` returning `Err` due to the destination not meeting the `ExistentialDeposit`), and the code does not handle that failure safely.

### Finding Description
In `claim_bounty`: [1](#0-0) 

```rust
let final_fee = fee.saturating_sub(children_fee);
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());

*maybe_bounty = None;
```

`curator` and `beneficiary` are both externally chosen (curator accepts the role via `accept_curator`, and `award_bounty` lets the curator freely set `beneficiary` to any lookup account). If `payout` (or `final_fee`) ends up below `ExistentialDeposit` for a brand-new/zero-balance destination account, `pallet_balances`'s `do_transfer` returns `TokenError::BelowMinimum`/`Err`, since `AllowDeath` only affects whether the *source* account is permitted to die, not whether the *destination* must clear the ED. There is no ED-aware guard (`grep` for `ExistentialDeposit`/`keep_alive`/`BelowMinimum` in this file returns nothing) and no fallback (e.g., `deposit_creating`, rounding, or minimum-payout check) before the transfer is attempted.

Because the transfer's `Result` is discarded (only `debug_assert!`, a no-op in release), the surrounding code proceeds exactly as if payment had succeeded: it removes the `Bounties` storage entry (`*maybe_bounty = None`), removes the description, notifies `T::ChildBountyManager::bounty_removed`, and emits `Event::BountyClaimed { payout, beneficiary, .. }`. The `bounty_account` funds that failed to move are left in that sub-account with no bounty record referencing them anymore — there is no sweep, retry, or reclaim path for a deleted bounty ID, so those funds are permanently stranded.

The exact same pattern exists in `pallet-child-bounties::claim_child_bounty`: [2](#0-1) 

This mirrors the tbtc root cause precisely: a mandatory push-transfer to an externally-influenced account is not verified, and the function's state-machine advances (bounty "claimed"/finalized) independent of whether the transfer actually succeeded — corrupting the invariant that settlement state should only advance after the transfer atomically succeeds.

### Impact Explanation
This directly violates the "conserve value and settle exactly once to the rightful beneficiary and amount" pivot for treasury/bounty payouts. The observable effect: `BountyClaimed`/`Claimed` events and total on-chain accounting suggest a payout occurred, but the actual DOT/asset remains locked forever in an orphaned `bounty_account`/`child_bounty_account` with no code path to recover it, i.e. permanent user-fund lock and inconsistent settlement accounting. Any bounty whose remaining payout (after curator fee deduction) is small relative to the chain's `ExistentialDeposit`, combined with a fresh beneficiary account, triggers this silently.

### Likelihood Explanation
No validator, relayer, prover, admin, or governance abuse is required as root cause — the trigger is purely a code-level omission (ignored `Result` on a `Currency::transfer`). Any curator (an unprivileged signed account once appointed/self-accepted for a bounty) can pick an arbitrary, brand-new `beneficiary` account in `award_bounty`, and any signed caller can later call `claim_bounty` ("anyone can trigger claim", per the code comment) once the payout delay elapses. Low/dust-value bounties (or bounties whose fee consumes most of the value, leaving a sub-ED remainder for the beneficiary) make this straightforward to hit; it does not depend on front-running or privileged actors.

### Recommendation
- Propagate the transfer results with `?` instead of `debug_assert!`, so a failed payout aborts the extrinsic (leaving the bounty in `PendingPayout` for retry) rather than silently deleting the bounty record.
- Alternatively, enforce a minimum payout/fee ≥ `ExistentialDeposit` at `award_bounty`/`propose_bounty` time, or use an ED-tolerant payment method (e.g., `deposit_creating`) so sub-ED dust is not lost.
- Apply the same fix to `pallet-child-bounties::claim_child_bounty`.

### Proof of Concept
1. Propose and fund a bounty whose value, after curator fee, leaves `payout < ExistentialDeposit` (e.g. a small bounty with the maximum permitted `CuratorFee`).
2. Curator calls `accept_curator`, then `award_bounty` with `beneficiary` set to a freshly generated account with zero prior balance.
3. Wait for `BountyDepositPayoutDelay`, then anyone calls `claim_bounty(bounty_id)`.
4. `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::BelowMinimum)` (or similar) in a release build; `debug_assert!` is compiled out and the error is discarded.
5. `Bounties::<T,I>::remove` deletes the bounty entry, `BountyClaimed` is emitted with the nominal `payout`, but `beneficiary`'s balance never increased — the funds remain locked in `bounty_account`, unreachable through any pallet call since the bounty ID no longer exists.
