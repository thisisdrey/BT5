### Title
Permanent loss of voter reward dust due to per-cycle floor-division in Vi reward accumulator - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
The reported bug class ("loss of fees due to rounding down" from an `accFeePerShareForToken * SCALE_FACTOR / liquidity` accumulator) maps directly onto java-tron's DPoS voter-reward-per-vote ("Vi") accumulator. Both patterns compute a per-unit accrual value as `numerator * SCALE / denominator` using integer division, and both silently truncate to `0` when the denominator (liquidity, or total vote count) is large relative to `numerator * SCALE`. In java-tron this happens once per maintenance cycle for every stored Vi delta, and the truncated remainder is never carried forward or reconciled, so it is permanently lost rather than merely delayed.

### Finding Description
The core Vi accumulation logic appears in three near-identical places: [1](#0-0) [2](#0-1) 

Each cycle, `deltaVi = reward * DECIMAL_OF_VI_REWARD / voteCount` is computed with `BigInteger` division, which floors toward zero. This value is stored as the sole representation of that cycle's per-vote reward (`setWitnessVi`), and there is no mechanism that tracks or carries forward the truncated remainder `(reward * DECIMAL_OF_VI_REWARD) % voteCount` into the next cycle's calculation. When `reward` is small (a single block/standby/fee reward split across a witness's total vote count) and `voteCount` is large (a popular SR can easily accumulate vote counts far larger than `DECIMAL_OF_VI_REWARD`), `deltaVi` rounds down to `0` for that entire cycle, and the corresponding fraction of the witness's paid-out reward becomes unclaimable by any voter — structurally identical to the `FarmKeeper` `_collectFees` issue where `amount * SCALE_FACTOR / liquidity` rounds to zero when `liquidity` is large.

This value later flows into voter reward computation, which multiplies the stored deltaVi by the individual voter's vote count and divides by the same `DECIMAL_OF_VI_REWARD`: [3](#0-2) [4](#0-3) 

Any cycle where the on-chain Vi delta rounds to `0` (because voteCount for the witness exceeded `reward * DECIMAL_OF_VI_REWARD`) causes every voter's `computeReward` for that cycle to compute `0` reward, with no possibility of recovery since the underlying stored `Vi` value never reflects the truncated fraction.

This computation runs unconditionally every maintenance cycle for every standby/active witness as part of normal DPoS block reward accounting, and is also directly reachable and observable by any account calling `withdrawReward`/`queryReward` (`MortgageService`) or the TVM `vote`/reward precompile path (`VoteRewardUtil`), both of which are unprivileged, permissionless entry points reachable from ordinary signed transactions or contract calls.

### Impact Explanation
Reward dust is permanently and silently discarded from voters' accrued balances whenever a witness's vote total is large relative to `reward * DECIMAL_OF_VI_REWARD` for a cycle. This constitutes a permanent freezing/loss of legitimately earned reward funds for ordinary token holders who voted for standby/active SRs, with no way for affected users to reclaim the lost value — mirroring the "fees collected when liquidity is high will be permanently lost and unclaimable by users" impact from the source report. Because this occurs deterministically as a floor-division artifact of consensus-level reward accounting (not user error), and there is no remainder-carry mechanism, losses compound over many cycles for high-vote-count SRs.

### Likelihood Explanation
The condition (`voteCount` large relative to `reward * DECIMAL_OF_VI_REWARD`) occurs naturally for any high-vote-count Super Representative with periods of relatively low per-cycle reward (e.g., low block/fee income cycles, or SRs receiving only the smaller standby-witness pay), which is common in production given TRX's large circulating supply and vote counts. No attacker action beyond normal voting/withdrawal is needed to observe the truncated result; it is a systemic rounding defect rather than an exploit requiring a malicious actor, making it Medium-to-High likelihood over the chain's operating lifetime.

### Recommendation
Track and carry forward the truncated remainder of each cycle's `reward * DECIMAL_OF_VI_REWARD % voteCount` into the next cycle's Vi computation (accumulate the remainder as "pending reward" added to the next `reward` term), or increase `DECIMAL_OF_VI_REWARD`'s precision sufficiently (analogous to the report's suggestion to raise `SCALE_FACTOR`) so that floor-division loss per cycle is economically negligible relative to realistic vote-count/reward ratios. Apply the same remainder-carrying fix consistently across `DelegationStore.accumulateWitnessVi`, `RewardViCalService.accumulateWitnessVi`, and the downstream `computeReward` methods in `MortgageService` and `VoteRewardUtil` that consume the stored Vi deltas.

### Proof of Concept
1. A Super Representative `SR_A` accumulates `voteCount = 5_000_000_000_000` (5 trillion) sun-equivalent votes.
2. In a given maintenance cycle, `SR_A` receives a modest reward, e.g. `reward = 1000` sun (from `payTransactionFeeReward`/`payBlockReward`), routed via `MortgageService.payReward` → `delegationStore.addReward(cycle, witnessAddress, value)`.
3. `RewardViCalService.accumulateWitnessVi` (or `DelegationStore.accumulateWitnessVi`) computes `deltaVi = BigInteger.valueOf(1000).multiply(DECIMAL_OF_VI_REWARD).divide(BigInteger.valueOf(5_000_000_000_000))`. If `DECIMAL_OF_VI_REWARD` is not large enough relative to this ratio, `deltaVi` truncates to `0`.
4. `setWitnessVi` stores `preVi` unchanged (no increment) for that cycle.
5. Any voter calling `withdrawReward`/`queryReward` (`MortgageService`) computes `deltaVi = endVi.subtract(beginVi)` across that cycle, obtains `0` (or less than expected), and their share of the 1000-sun reward is permanently lost — it is not credited to any account and cannot be recovered in a later cycle since the Vi ledger never recorded it.   public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
