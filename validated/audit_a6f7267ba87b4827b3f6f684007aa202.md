Based on the code, this is **not exploitable**. The relevant safeguard is that all receipts processed within a single chunk apply share the *same* `TrieUpdate` (`state_update`), applied sequentially, not in parallel or as isolated/deferred batches.

Key evidence:

1. `validate_delegate_action_key` reads the current access-key nonce via `get_access_key(state_update, ...)` and, if the delegate nonce is valid, immediately calls `set_access_key(state_update, ...)` to persist the bumped nonce into the same `TrieUpdate`, before returning: [1](#0-0) [2](#0-1) 

2. `Runtime::apply` uses a single `ApplyProcessingReceiptState.state_update: TrieUpdate` for the entire chunk, and `process_local_receipts` / `process_delayed_receipts` / `process_incoming_receipts` iterate receipts **sequentially** (`for receipt in &local_receipts { ... self.process_receipt_and_instant_receipts(...) }`), each call mutating and reading from that same shared `state_update`: [3](#0-2) [4](#0-3) 

3. There is no batching/deferral of the nonce write until the whole chunk is finalized — the write happens synchronously inside the very same function call that validated the nonce, and is visible to the next receipt's `get_access_key` read immediately (in-memory `TrieUpdate`, not disk-committed but already recorded).

4. This exact scenario — calling `validate_delegate_action_key` twice against the same `state_update` with the identical (unbumped) delegate nonce — is already covered by an existing unit test, which asserts the second call fails with `ActionErrorKind::DelegateActionInvalidNonce`: [5](#0-4) 

Since both duplicate wrapped `SignedDelegateAction` receipts — regardless of which shard/tx envelope carried them — must ultimately be validated against the access key that lives on `sender_id`'s account (which resides on exactly one shard), both receipts land on that single shard and are processed sequentially within the same `Runtime::apply`/`process_receipts` call (or, if split across blocks, the first block's nonce bump is committed to the persistent trie via `state_update.finalize()` before the next block is applied). Either way, the second occurrence necessarily observes the already-bumped nonce and is rejected with `DelegateActionInvalidNonce`. There is no window where two receipts carrying the same delegate nonce can both read the pre-bump nonce concurrently, because there is no concurrent/parallel receipt execution in the runtime apply path — it's fully sequential.
