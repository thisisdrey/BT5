### Title
Out-of-Bounds Heap Read via Unchecked Attribute Index in `Zip64ExtraField::attr64` During Jar Merging - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar`'s `Zip64ExtraField::attr64(int index)` accessor performs no bounds check against the field's own declared `attr_count()`. Callers in `LH`/`CDH` (`compressed_file_size()`, `uncompressed_file_size()`, `local_header_offset()`) compute the attribute index purely from which 32-bit size/offset fields are flagged `0xFFFFFFFF`, assuming the accompanying Zip64 extra field contains that many 64-bit slots — without verifying it actually does. A crafted (but otherwise well-formed) input jar/zip processed by `OutputJar`/`Concatenator` can trigger a read past the end of the extra-field payload, into adjacent heap memory.

### Finding Description
`Zip64ExtraField` stores a variable number of 64-bit attributes, with `attr_count()` computed from `payload_size()`: [1](#0-0) 

`attr64()` indexes directly into `attr_[]` with no check that `index < attr_count()`: [2](#0-1) 

Consumers determine which index to read purely from the 32-bit fields, not from the field's real size. For example, `LH::compressed_file_size()` unconditionally reads `attr64(1)` whenever `compressed_file_size32() == 0xFFFFFFFF`, assuming the Zip64 field holds both the uncompressed (`index 0`) and compressed (`index 1`) 64-bit values per spec: [3](#0-2) 

Similarly, `CDH::local_header_offset()` computes `attr_no` by summing flags on `uncompressed_file_size32()` and `compressed_file_size32()` and then reads `attr64(attr_no)`: [4](#0-3) 

The lookup helper `ExtraField::find`/`Zip64ExtraField::find` only validates that the *declared* field (`header + payload_size`) fits inside the `extra_fields` buffer — it says nothing about whether `payload_size` is large enough for the number of 64-bit slots the caller intends to read: [5](#0-4) 

The existing "malformed extra field" guard in `OutputJar::WriteEntry` (added, per the existing regression test, to reject fields whose declared size overruns the extra-fields buffer) checks the same invariant — total field size within bounds — and therefore does **not** catch a Zip64 field whose `payload_size` is smaller than the number of attributes implied by the 32-bit flags: [6](#0-5) [7](#0-6) 

These size accessors are invoked directly on attacker-controlled `LH`/`CDH` structures while merging/copying entries, e.g. in `Concatenator`/`OutputJar` bulk-copy paths and decompression: [8](#0-7) [9](#0-8) 

An attacker who publishes a malicious jar at a dependency URL (e.g., an unpinned/attacker-served `http_jar`/`http_file`/third-party artifact consumed as a `--sources` input to `singlejar`, which underlies `java_binary`/`java_import`-style deploy-jar merging) can craft an `LH`/`CDH` where a 32-bit size or offset field is `0xFFFFFFFF` (indicating "value is in Zip64 extra field") but the accompanying Zip64 extra field's `payload_size` is smaller than required for the implied index (e.g., only one 8-byte attribute present when the code expects `attr64(1)`). This field still passes the existing "size fits in `extra_fields` buffer" check because it is internally well-formed and short — it just doesn't contain enough attributes for the flags asserted elsewhere in the header. The subsequent `attr64(index)` call then reads 8 bytes past the field's own allocated extent, which can extend past the whole `extra_fields`/entry buffer (heap-mapped or `malloc`'d), disclosing adjacent heap bytes into computed sizes/offsets used for further pointer arithmetic (e.g., `data()`, `WriteBytes` length calculations), which can crash the process or leak/misuse heap memory content.

### Impact Explanation
This is an out-of-bounds heap read reachable purely from attacker-supplied jar/zip bytes processed by a build-time tool (`singlejar`), analogous to the reported BSON CodeWScope OOB read: an unchecked size value is trusted for pointer arithmetic across data derived from an external, attacker-controlled input. Consequences are a build-worker crash (denial of build) or disclosure of adjacent heap memory into size/offset fields that further drive read/write operations (potential secondary corruption via inconsistent size computations feeding into `WriteBytes`/`memcpy` lengths).

### Likelihood Explanation
Any Bazel target that runs `singlejar` (deploy jars, `java_import`, jar merging actions) over a jar that ultimately originates from an external, attacker-influenced source — a compromised/malicious third-party artifact URL without a verified checksum, or a dependency built from an untrusted branch — can trigger this. Crafting the malicious `LH`/`CDH` bytes is straightforward and requires no special privileges; it's a standard binary-format-manipulation attack on a self-describing structure.

### Recommendation
In `Zip64ExtraField::attr64(int index) const`, validate `index < attr_count()` (derived from `payload_size()`) before indexing `attr_[]`, and have callers (`LH::compressed_file_size`, `LH::uncompressed_file_size`, `CDH::compressed_file_size`, `CDH::uncompressed_file_size`, `CDH::local_header_offset`) treat an out-of-range index as a malformed-input error (`diag_errx`), consistent with the existing "malformed extra field" handling in `output_jar.cc`.

### Proof of Concept
Extend the existing malformed-extra-field regression harness in `src/tools/singlejar/output_jar_simple_test.cc` (which already builds a synthetic zip with `CreateZipWithMalformedExtraField`) with a new helper that:
1. Builds an `LH`/`CDH` pair where `compressed_file_size32` (and/or `uncompressed_file_size32`/`local_header_offset32`) is set to `0xFFFFFFFF`.
2. Attaches a `Zip64ExtraField` extra field whose `payload_size` is set to `8` (one attribute) instead of the `16`/`24` bytes required for the indices implied by the flags above, placed such that the field ends exactly at the boundary of the heap allocation backing the entry/extra-fields buffer (e.g., last bytes of a tightly-sized `malloc`'d buffer, as ASan would flag).
3. Runs this crafted jar through `OutputJar::Doit()` (as `--sources`) under AddressSanitizer.

Expected result without the fix: ASan reports a heap-buffer-overflow read inside `Zip64ExtraField::attr64` (called transitively from `LH::compressed_file_size`/`CDH::local_header_offset`), rather than the controlled `diag_errx("malformed extra field...")` abort produced by the existing, narrower bounds check.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
