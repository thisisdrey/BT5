### Title
Unbounded, fee-free creation of DelegatedResource records enables database-growth DoS - (File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java)

### Summary
`DelegateResourceActuator` (the `DelegateResourceContract` handler reachable from any signed transaction) charges no fee (`calcFee()` returns `0`) and enforces no cap on how many distinct delegation records or distinct receiver addresses an account may create, unlike sibling creation actuators (`AccountCreateContract`, `AssetIssueContract`, `ExchangeCreateContract`, `WitnessCreateContract`) which all charge a nontrivial system fee for every new persistent record they create.

### Finding Description
`DelegateResourceActuator.validate()` only checks that the delegated amount is at least 1 TRX (`TRX_PRECISION`) and that the owner has sufficient frozen V2 balance for bandwidth/energy — there is no check on the number of distinct receiver addresses the owner has already delegated to, nor any limit on the total number of `DelegatedResourceCapsule` records that may exist for one owner. `execute()`/`delegateResource()` unconditionally creates (or updates) a new key in `DelegatedResourceStore` for every distinct `(owner, receiver, lock)` tuple, and separately mutates `DelegatedResourceAccountIndexStore` to append new "from"/"to" index entries. Because `calcFee()` returns `0`, no TRX fee is burned for creating these entries — the only "cost" is that 1 TRX must be frozen and re-delegatable in each call, but the same 1 TRX-worth of frozen balance can be delegated, undelegated, and redelegated to a fresh receiver address repeatedly (each call is a distinct signed transaction with the minimum bandwidth/energy cost of a normal transaction, not tied to storage growth). An attacker controlling one funded account (with the minimum freeze of ~1 TRX) can therefore mint an unbounded number of new `(owner, uniqueReceiver)` pairs — each requiring only a fresh unfunded receiver address (which itself is free to reference, no receiver account creation is required beyond it existing) — permanently growing `DelegatedResourceStore` and the account index lists in `DelegatedResourceAccountIndexStore`, unlike other creation-type actuators that all require paying an escalating system fee per created record.

### Impact Explanation
Every accepted `DelegateResourceContract` transaction leaves a permanent (until manually undelegated) row in `DelegatedResourceStore` and grows list-typed index entries in `DelegatedResourceAccountIndexStore` for both the owner and the receiver. Because creation is not fee-gated, an attacker can flood these two stores with a very large number of entries using only the minimum transaction fee/bandwidth budget, which can bloat the state database, slow down `getDelegatedResourceAccountIndex`/`getDelegatedResourceV2` RPC/HTTP query paths on `Wallet`, and increase snapshot/sync and full-node storage costs — a denial-of-service surface analogous to CVE-2016-8611's unbounded Glance `/images` POST table saturation.

### Likelihood Explanation
Any ordinary (non-witness, non-committee) account can call this repeatedly as long as they have at least 1 TRX frozen for bandwidth or energy (a very low bar, reachable via a normal `FreezeBalanceV2Contract`), and the feature is gated only by the `supportDR`/`supportUnfreezeDelay` chain parameters (which are enabled on mainnet), making the path straightforward for a single unprivileged actor to exploit repeatedly over time.

### Recommendation
Introduce an explicit non-zero `calcFee()` for `DelegateResourceContract` (mirroring `AccountCreateContract`/`ExchangeCreateContract`), and/or add a validated upper bound on the number of distinct receiver addresses (or total `DelegatedResourceCapsule` records) a single owner account may create, similar to the `MAX_ACTIVE_ORDER_NUM` cap already enforced in `MarketSellAssetActuator`.

### Proof of Concept
1. Fund an account and freeze the minimum 1 TRX for bandwidth via `FreezeBalanceV2Contract` (`supportUnfreezeDelay` chain param enabled).
2. Repeatedly submit `DelegateResourceContract` transactions from that account, each with `balance = 1_000_000` (1 TRX) and a freshly generated, previously-unused `receiverAddress`.
3. After each delegation, submit an `UnDelegateResourceContract` to reclaim the 1 TRX frozen balance, then delegate again to yet another new receiver.
4. Observe that `DelegatedResourceStore` and `DelegatedResourceAccountIndexStore` grow by one new persistent entry per iteration, with `calcFee()` always returning `0` (see `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java` lines 277-280), imposing no monetary cost proportional to the number of records created.
