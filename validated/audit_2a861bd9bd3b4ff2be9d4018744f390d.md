### Title
Replay-window check-then-act race allows duplicate decryption of a replayed packet - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the replay-window "is this counter new" check and the "mark this counter as seen" update into two separate, independently-locked critical sections, with the actual AEAD decryption performed in between while the lock is released. This is the same class of bug described in the external report: a value is read once (window bit state), consulted, then re-checked/committed later, but the authoritative state can change (or be raced) in the gap between the read and the write, letting a stale/duplicate "already seen" decision slip through the protection that is supposed to be atomic.

### Finding Description
`Decrypt` performs:
1. `decryptLock.Lock(); result := cs.window.Check(...); decryptLock.Unlock()` [1](#0-0) 
2. AEAD decryption `cs.dKey.DecryptDanger(...)` performed **without holding `decryptLock`** [2](#0-1) 
3. `decryptLock.Lock(); result = cs.window.Update(...); decryptLock.Unlock()` [3](#0-2) 

`VerifyRelay` has the identical structure: `Check` under lock, unlocked AEAD verification, then `Update` under lock. [4](#0-3) 

Because `Check` (read) and `Update` (commit) are not performed atomically with the decryption in between, two goroutines processing two copies of the *same* ciphertext packet (a captured-and-replayed UDP datagram) concurrently on the same `ConnectionState` can both pass `Check` before either calls `Update`. Both will then independently decrypt the packet successfully (it is valid ciphertext for that `messageCounter`), and both will proceed to deliver/act on the plaintext before the second `Update` call has a chance to reject it as already seen. This mirrors the reported mvkv pattern exactly: a cached/checked value (`window.Check` result) is treated as authoritative for the remainder of the operation, but a concurrent path (the second goroutine reading the same not-yet-updated window state) observes a stale view and is allowed to proceed as if the counter were still fresh.

Nebula's own `CHANGELOG.md` documents that `window.Update` corruption from concurrent readers was previously fixed by adding locking (`Lock replay window updates so concurrent readers can't corrupt it. (#1802)`), but that fix only protects the internal `Bits` structure from data races - it does not make the `Check` → decrypt → `Update` sequence atomic. [5](#0-4) 

### Impact Explanation
This allows a network attacker with no certificate at all - simply someone who can observe and re-inject UDP packets between two already-established Nebula peers - to cause a replayed packet to be decrypted and forwarded a second time if it is processed concurrently with a duplicate delivery (e.g., attacker duplicates the datagram at the network layer, or `listen.routines` > 1 causes concurrent reads that race on delivery of a duplicate). The security guarantee that the replay window is supposed to provide (each `messageCounter` decrypted/accepted exactly once) can be violated, resulting in traffic replay into the tun device or through the relay path.

### Likelihood Explanation
Exploitation requires the attacker to get two copies of the same ciphertext processed concurrently by the receiver, which is more likely when `listen.routines` is configured >1 (multiple UDP reader goroutines) or when packet duplication/reordering naturally occurs on the underlay network. This is a narrow race window, not a deterministic bypass, so likelihood is lower than a straightforward logic bug, but the primitive (attacker-observable ciphertext replay against an unauthenticated race window) requires no possession of any cert or key material.

### Recommendation
Make the check-decrypt-commit sequence atomic with respect to the replay window, e.g., hold `decryptLock` across the entire `Check` → `DecryptDanger` → `Update` sequence (or perform the window `Update` optimistically/atomically as part of a single locked operation and roll back only if decryption fails), so no other goroutine can observe the same "not yet marked" state for the same counter while decryption of a duplicate is in flight.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes (`A` and `B`).
2. Attacker captures one valid encrypted data packet with `messageCounter = N` from `A` to `B`.
3. Configure/observe `B` with `listen.routines > 1`, or otherwise deliver two copies of the captured packet to `B`'s UDP socket in quick succession so two reader goroutines call `ConnectionState.Decrypt` concurrently with the same `messageCounter`.
4. Both goroutines call `window.Check(N)` before either calls `window.Update(N)`; both succeed and both decrypt the packet, resulting in the same plaintext being processed/forwarded twice, corresponding to [6](#0-5) .

```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
```

```go
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
```
