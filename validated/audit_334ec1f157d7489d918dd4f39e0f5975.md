### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule` lets an attacker DoS a victim's delegation index and its public query APIs - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceContract` (and its native/TVM counterpart) let any account freeze as little as 1 TRX and delegate the resulting bandwidth/energy to an arbitrary `receiverAddress`, with no permission check on the receiver and no cap on how many distinct delegators can point at the same receiver. Under the legacy (non-optimized) index model, each such delegation appends the delegator's address to a single, unbounded protobuf list stored in the receiver's `DelegatedResourceAccountIndexCapsule`, and this same growable structure is read back in full by public wallet/gRPC/HTTP query endpoints.

### Finding Description
`FreezeBalanceActuator.validate()` only requires `frozenBalance >= TRX_PRECISION` (1 TRX) and performs no check that the caller is authorized to delegate resources to `receiverAddress`: [1](#0-0) 

In `delegateResource()` (invoked from `execute()`), when the legacy index model is active (`!dynamicPropertiesStore.supportAllowDelegateOptimization()`), the receiver's index capsule accumulates the delegator's address into an in-memory `fromAccountsList` with only a "does it already contain this owner" de-dup check — there is no maximum size enforced anywhere: [2](#0-1) 

The underlying capsule simply appends to a protobuf-backed list with no bound: [3](#0-2) [4](#0-3) 

A test in the repo explicitly demonstrates that a single index capsule can be grown to at least 100+ entries by repeated 1-TRX delegations from freshly generated addresses, confirming there is no cap: [5](#0-4) 

This bloated, single-key capsule is then read back and fully materialized (and re-sorted/merged) by `DelegatedResourceAccountIndexStore.getIndex()` / `getV2Index()` (the V2/new-model equivalent similarly does a `prefixQuery` scan and sorts all matching entries in memory), which backs the public wallet query API `getDelegatedResourceAccountIndex` / `getDelegatedResourceAccountIndexV2` exposed over gRPC (`RpcApiService`) for both full node, solidity node, and PBFT node: [6](#0-5) [7](#0-6) 

This mirrors the vePeg `create_lock_for()` bug class: an unprivileged caller can perform low-cost, repeated operations targeting an arbitrary victim address that accumulate unbounded state attributable to the victim, with no minimum/maximum guard rail on the number of distinct counterparties, and that state is subsequently consumed by code paths (here, public query RPCs) without any pagination or size limit.

### Impact Explanation
An attacker can drive a victim's `DelegatedResourceAccountIndex` entry to an arbitrarily large size by repeatedly freezing the minimum 1 TRX from many disposable accounts and delegating to the victim's address. Because the entire list is stored under one DB key and fully deserialized/rebuilt (`getIndex`/`getV2Index` do a full scan + sort + rebuild via `setAllToAccounts`/`setAllFromAccounts`) on every subsequent read or write touching that account's delegation index, this can degrade or exhaust node resources when serving the public `getDelegatedResourceAccountIndex(V2)` API for that account, and increases CPU/memory cost for every future legitimate freeze/unfreeze/delegate operation involving the victim (each of which re-reads and re-writes the same growing capsule). In the worst case this is a resource-exhaustion vector against a query path the node must serve to any client, and it permanently pollutes the victim's on-chain delegation index (the entries cannot be removed by the victim, since only unfreezing by the original delegator removes them).

### Likelihood Explanation
Likelihood is medium: the attack is cheap per unit (1 TRX per fake delegator account, refundable via `withdraw`/`unfreeze` after the minimum freeze duration) and requires no special privilege, matching the "unprivileged transaction broadcaster" threat model. It is bounded only by the attacker's willingness to create many throwaway accounts and pay minor bandwidth/energy fees for each `FreezeBalanceContract` transaction; there is no on-chain rate limit or per-victim cap preventing it.

### Recommendation
1. Enforce a maximum number of distinct entries in `DelegatedResourceAccountIndexCapsule.fromAccountsList` / `toAccountsList` (and in the V2 prefix-scan result), rejecting further delegation attempts once the receiver's index length exceeds a sane bound.
2. Alternatively/additionally, raise the minimum delegable balance so that filling the index to an impactful size is prohibitively expensive.
3. Paginate the `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` wallet APIs instead of returning/deserializing the full list in one call.

### Proof of Concept
Conceptually mirroring the vePeg POC:
1. Attacker generates N throwaway accounts, each funded with slightly more than 1 TRX (as shown feasible in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which programmatically constructs 100+ distinct delegator addresses). [8](#0-7) 
2. From each account, broadcast a `FreezeBalanceContract` with `frozenBalance = 1_000_000` (1 TRX) and `receiverAddress = VICTIM`, passing `FreezeBalanceActuator.validate()`'s only balance check. [1](#0-0) 
3. Each transaction appends to `VICTIM`'s `DelegatedResourceAccountIndexCapsule.fromAccountsList` without bound. [9](#0-8) 
4. Repeat at scale (thousands of accounts); subsequent calls to the public `getDelegatedResourceAccountIndex`/`V2` RPC for `VICTIM`, and every future freeze/delegate/unfreeze operation touching `VICTIM`'s index, must deserialize and rebuild the now-huge list.

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
