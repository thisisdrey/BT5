## Title
Exchange (AMM) Liquidity Injection Lacks Slippage/Minimum-Output Protection, Enabling Frontrunning Losses - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` (the java-tron on-chain equivalent of a DEX "add liquidity" / `buyShares` call) computes the paired-token amount required for a liquidity injection strictly from the exchange pool's *current* on-chain reserve ratio at execution time, and exposes no user-supplied minimum/maximum bound (slippage parameter) that the actuator validates against. This mirrors the DODO `buyShares` frontrunning issue: a broadcaster who signs an `ExchangeInjectContract` cannot protect themselves against reserve-ratio manipulation that occurs between transaction signing and execution.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field, unlike its sibling `ExchangeTransactionContract`, which does carry an `expected` field: [1](#0-0) 

In `ExchangeInjectActuator.execute`, the paired-token amount (`anotherTokenQuant`) is derived purely from the pool's live `firstTokenBalance`/`secondTokenBalance` ratio at execution time: [2](#0-1) 

`doValidate` re-derives the same ratio-based `anotherTokenQuant` using `BigInteger` math, but the only checks performed are that the value is `> 0` and that the account has sufficient balance — there is no check comparing it against any caller-specified bound: [3](#0-2) 

By contrast, `ExchangeTransactionActuator` (a simple swap) does enforce a minimum-output check via the `expected` field: [4](#0-3) 

This asymmetry means the liquidity-injection path — the one most analogous to the vulnerable `buyShares` function in the report — has *no* slippage enforcement at all, not even a weak one. A liquidity provider signs an `ExchangeInjectContract` expecting the pool ratio observed when they built the transaction to still hold when it executes. Because Tron transactions can sit in the pending pool and be reordered/frontrun by other broadcasters (e.g., someone submitting an `ExchangeTransactionContract` swap against the same `exchange_id` first), the ratio used to compute `anotherTokenQuant` can be manipulated before the victim's `ExchangeInjectContract` executes.

### Impact Explanation
An attacker who observes a pending, large `ExchangeInjectContract` in the mempool can:
1. Submit (and get ordered before) a large `ExchangeTransactionContract` swap against the same exchange to skew `firstTokenBalance`/`secondTokenBalance`.
2. Let the victim's injection execute against the skewed ratio, forcing the victim to contribute an amount of the paired token that is worth more than intended relative to the pre-manipulation ratio (or reject the tx entirely if their `token balance is not enough` check fails, but if it succeeds, the victim overpays into the pool).
3. Reverse the swap (sell back) afterward, extracting the excess value that was effectively transferred to the pool (and to other participants) by the victim's mis-priced injection.

Since exchange balances directly back withdrawable value (`ExchangeWithdrawActuator` computes withdrawal amounts from these same balances), this results in real, quantifiable fund loss for the victim and value extraction by the attacker — satisfying the "theft of funds" bar.

### Likelihood Explanation
Any unprivileged account can broadcast `ExchangeInjectContract` and `ExchangeTransactionContract` transactions; no special privileges are required. The attack only requires observing a pending injection transaction and being able to get a swap ordered ahead of it, which is a standard mempool-frontrunning/MEV pattern applicable to any chain with a visible transaction pool. Given `ExchangeInjectActuator` provides zero protection (not even the partial protection `ExchangeTransactionActuator` has), the likelihood of executing this against any sizable liquidity injection is high whenever an economically motivated actor is monitoring the network.

### Recommendation
Add a caller-specified bound field to `ExchangeInjectContract` (e.g., `expected_another_token_quant_min`/`max`, analogous to `expected` in `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator.doValidate`/`execute` by rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller's tolerance. This closes the gap between `ExchangeInjectActuator` and `ExchangeTransactionActuator`'s existing (if still return-value-based) slippage handling.

### Proof of Concept
1. Attacker observes victim's pending `ExchangeInjectContract` for `exchange_id=X`, `token_id=firstToken`, `quant=Q` (computed by victim assuming current ratio `firstTokenBalance0/secondTokenBalance0`).
2. Attacker broadcasts and gets included first an `ExchangeTransactionContract` swap on the same `exchange_id` that shifts `firstTokenBalance`/`secondTokenBalance` significantly (per `ExchangeCapsule.transaction` pricing curve in `ExchangeProcessor`) — see reserve update logic used identically by inject: [5](#0-4) .
3. Victim's `ExchangeInjectContract` then executes against the manipulated ratio in `ExchangeInjectActuator.execute` (lines 71-83 above), computing `anotherTokenQuant` from the skewed balances with no bound check.
4. Attacker reverses their initial swap, restoring the ratio and capturing the mispriced value contributed by the victim's injection.

package org.tron.core.capsule;

import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.Maths;

@Slf4j(topic = "capsule")
public class ExchangeProcessor implements ExchangeCapsule.Processor {

  private long supply;
  private final boolean useStrictMath;

  public ExchangeProcessor(long supply, boolean useStrictMath) {
    this.supply = supply;
    this.useStrictMath = useStrictMath;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
