### Title
Anti-Replay Window Check-then-Update Race in `ConnectionState.Decrypt` Allows Replayed Packet Bypass - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` in `connection_state.go` releases `decryptLock` between the anti-replay `Check` and the state-mutating `Update`, performing the expensive AEAD decrypt operation in between while holding no lock. This mirrors the CEI violation in the reference report: a "check" is read, an "external"/expensive operation is interleaved unprotected, and the "effect" (marking the counter as seen) is applied only afterward — leaving a window where concurrent execution paths can both pass the check before either commits its effect.

### Finding Description
`Decrypt` does:
1. Lock, `window.Check(messageCounter)`, unlock.
2. `dKey.DecryptDanger(...)` — the AEAD decrypt, run entirely without holding `decryptLock`.
3. Lock, `window.Update(messageCounter)`, unlock. [4](#0-3) 

Because Nebula runs `f.routines` independent reader goroutines that each call `f.readOutsidePackets` concurrently, and dispatch is based solely on the packet's `RemoteIndex` header field via `f.hostMap.QueryIndex` (not on the underlying UDP source tuple), two duplicate copies of the exact same previously-observed ciphertext (a captured, replayed packet) can be steered to different reader routines and processed concurrently against the same `HostInfo`/`ConnectionState`. [1](#0-0) [2](#0-1) [3](#0-2) 

If both goroutines call `Check` for the same `messageCounter` before either calls `Update`, both `Check` calls can independently return true (since `Bits.Check` only tests, it does not mutate state), both proceed to successfully decrypt the same valid ciphertext with the correct key/nonce, and only afterward do they serialize on `Update` — by which point decryption (and any state built from the decrypted plaintext, e.g. delivery to the tun device or triggering roaming/relay logic) has already happened for both copies. This is the anti-replay analog of the report's CEI violation: the authoritative state mutation (`Update`, i.e., marking the nonce "spent") is deferred past the "external interaction" (decrypt + downstream side effects), rather than being committed atomically with the check.

`VerifyRelay` has the identical structure: `Check` → unlock → `DecryptDanger` → lock → `Update`. [5](#0-4) 

### Impact Explanation
A network-level attacker who can capture and duplicate/replay Nebula UDP ciphertext (no valid CA-signed certificate is required — replay only requires observing/duplicating wire traffic) can cause a single legitimate encrypted packet to be accepted and processed twice by the receiving node's data plane before the anti-replay window is updated, defeating the intended nonce/replay protection guarantee for that race window. Depending on payload, this can cause duplicate delivery to the tun device, duplicate roaming/connection-manager side effects, or duplicate relay/control message processing — a concrete traffic replay/state-poisoning impact.

### Likelihood Explanation
Exploitation requires winning a narrow race between two decrypt operations completing before either `Update` call lands, and requires getting duplicate copies of the same ciphertext dispatched to two different reader routines (only relevant when `routines > 1`, e.g. Linux with multi-queue/SO_REUSEPORT enabled). This is a real but timing-dependent condition, not a trivially reliable bypass, so likelihood is moderate rather than high.

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence (or perform an atomic "check-and-reserve" of the counter before decrypting, releasing/rolling back the reservation only on decrypt failure) so no other goroutine can observe the counter as unclaimed while a decrypt for it is in flight.

### Proof of Concept
1. Establish a tunnel between attacker-observable node A and victim B with `routines > 1` on the victim.
2. Capture one valid encrypted `Message` packet P (counter N) sent from A to B.
3. Rapidly replay two copies of P to B such that platform-level multi-queue steering (e.g., differing source port via NAT/spoof, or kernel RSS behavior) delivers the copies to two different `listenOut` reader goroutines nearly simultaneously.
4. Both goroutines resolve the same `HostInfo` via `QueryIndex`, both call `Decrypt`, both pass `window.Check(N)` before either calls `window.Update(N)`, both successfully decrypt and process P's payload, resulting in duplicate acceptance of a replayed packet.
