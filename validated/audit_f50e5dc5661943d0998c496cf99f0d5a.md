Based on my research, I found a strong local analog to the Gearbox "approve any token" pattern: an unrestricted matcher that accepts *any* address as a legitimate ERC20 asset, causing a privileged system account to interact with arbitrary attacker-supplied contracts.

### Title
`IsLocalAccountKey20` accepts any 20-byte address as a valid ERC20 asset, letting XCM messages force the `TransfersCheckingAccount` to call arbitrary attacker-deployed contracts - ([File: cumulus/parachains/runtimes/assets/common/src/lib.rs])

### Summary
The Gearbox bug is that `CreditManager` lets a user pick an arbitrary `token` address to be approved/acted upon, with no check that the token belongs to an allowed/trusted set. The direct analog here is `ERC20Matcher`, used by `ERC20Transactor` to decide which XCM `Asset` ids are legitimate ERC-20 tokens for asset transacting. Its `Contains<Location>` gate, `IsLocalAccountKey20`, accepts **any** local `AccountKey20` junction as a valid token — there is no allowlist of registered/trusted ERC-20 contracts.

### Finding Description
`ERC20Matcher` is defined as: [1](#0-0) 

Its gating predicate is `IsLocalAccountKey20`: [2](#0-1) 

This `Contains` impl returns `true` for *every* `Location` of the shape `(0, [AccountKey20 { .. }])` — i.e. every possible 20-byte EVM address, with no registry or allowlist check that the address corresponds to an actually deployed/trusted ERC-20 contract. `MatchedConvertedConcreteId::matches_fungibles` only calls this `Contains` check before converting and accepting the id: [3](#0-2) 

The matched `H160` is then used directly as the target contract address for a privileged `bare_call`. Crucially, in `deposit_asset_with_surplus`, the call is signed by `TransfersCheckingAccount` — a system-controlled account, not the end user: [4](#0-3) 

Because the matcher imposes no restriction on which address is a legitimate token, any XCM `Asset` whose id resolves to an `AccountKey20` location — including an address hosting attacker-controlled bytecode deployed via `pallet_revive`/`pallet_contracts` — is accepted as "the asset" to transact. The runtime then unconditionally executes `transferCall` against that address using the checking account as the signed origin. This is exactly the missing-allowlist pattern from the Gearbox report: the caller effectively "picks the token," and the protocol dispatches privileged calls to it without verifying the token is a known, trusted contract.

### Impact Explanation
The `TransfersCheckingAccount` is a shared, privileged pallet-controlled account used across all ERC-20 asset transactions. Letting an attacker force it to execute code they authored breaks the intended trust boundary: the checking account's calls are supposed to only ever hit genuine, registered ERC-20 tokens whose `transfer` semantics are well-understood. Instead, an attacker can deploy a malicious contract at an address, construct or trigger an XCM `Asset` referencing that address, and have the runtime invoke arbitrary logic "as" the checking account (e.g. a contract that fails from certain callers only, mis-reports return values, reenters other pallet-revive contracts, or manipulates its own state to desynchronize the checking account's expected balances across subsequent transfers). This can corrupt the checking-account-based settlement invariant that XCM asset transfers are supposed to preserve atomically.

### Likelihood Explanation
No malicious peer, validator, collator, or governance actor is required — any unprivileged party able to deploy a contract and construct/trigger an XCM message with an `Asset` id pointing at that contract (e.g. via a reserve-asset transfer program) can exercise this path solely through public dispatch entry points.

### Recommendation
Restrict `ERC20Matcher`'s gate to a maintained allowlist/registry of trusted ERC-20 token addresses (analogous to how `TrustBackedAssetsConvertedConcreteId`/`ForeignAssetsConvertedConcreteId` restrict by pallet instance and registered asset id) rather than accepting any `AccountKey20` junction. Only addresses that have been explicitly registered as legitimate tokens should be eligible for `TransfersCheckingAccount`-signed transfer calls.

### Proof of Concept
1. Deploy an arbitrary contract `Evil` via `pallet_revive` at address `0xEVIL...`, implementing `transfer(address,uint256)` with attacker-chosen logic (e.g., always returns `true` but performs reentrant/side-effecting logic, or behaves differently based on caller).
2. Construct/trigger an XCM program whose `Asset.id` resolves to `Location::new(0, [AccountKey20 { key: 0xEVIL..., network: None }])` with some `Fungible(amount)`.
3. Route this asset through `deposit_asset_with_surplus` (e.g. via a reserve transfer landing on this chain naming `Evil` as the asset).
4. Observe `ERC20Matcher::matches_fungibles` accepts the id (no allowlist check) and `pallet_revive::Pallet::<T>::bare_call` executes `Evil::transfer` signed by `RuntimeOrigin::signed(TransfersCheckingAccount::get())`, demonstrating the checking account executing attacker-supplied code chosen purely by XCM message content.
