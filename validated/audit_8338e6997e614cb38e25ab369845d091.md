### Title
Protocol treasury reward is silently discarded (never credited to any account) when the treasury account is also an active validator - ([File: chain/epoch-manager/src/reward_calculator.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`RewardCalculator::calculate_reward` pre-inserts the treasury's inflation share into the `res` map and then, inside the per-validator loop, unconditionally `res.insert()`s each validator's own block/chunk-production reward — overwriting (not summing with) the treasury's entry whenever the treasury account is itself an active validator. `epoch_actual_reward` (the `minted_amount` credited to `total_supply`) still includes the treasury share, but the `validator_rewards` map handed to `Runtime::update_validator_accounts` no longer contains it, and the "treasury already handled above" special case at `lib.rs:1728-1755` additionally guarantees no fallback credit path exists. The result is a permanent value-conservation violation: `total_supply` grows by `epoch_protocol_treasury` yet no account balance/locked amount reflects it.

### Finding Description
In `calculate_reward` (`chain/epoch-manager/src/reward_calculator.rs`):
- Line 84: `res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);` seeds the treasury's share into the rewards map.
- Line 90: `epoch_actual_reward` is initialized to `epoch_protocol_treasury`.
- Lines 94-144: for every validator in `validator_block_chunk_stats`, a `reward` is computed and `res.insert(account_id, reward)` is executed at line 142, then `epoch_actual_reward = epoch_actual_reward.checked_add(reward)` at line 143.

`HashMap::insert` overwrites any existing entry for the same key. If the protocol treasury account is itself one of the epoch's active validators (i.e. it appears in `validator_block_chunk_stats`, which happens whenever the treasury account has staked and been selected into the validator set), the loop's `res.insert(account_id, reward)` for that account replaces the treasury's `epoch_protocol_treasury` entry with just its own block/chunk-production `reward`. `epoch_actual_reward`, however, still accumulates both the initial `epoch_protocol_treasury` (line 90) and the treasury-as-validator's `reward` (line 143), so the *minted* amount used for `total_supply` is correct, but the *distributable* `res` map (returned as `validator_reward`, later exposed via `EpochManager::compute_stake_return_info` and passed into `ValidatorAccountsUpdate::validator_rewards`) has lost the `epoch_protocol_treasury` portion entirely.

Downstream, `Runtime::update_validator_accounts` (`runtime/runtime/src/lib.rs:1663-1759`) consumes this same collided map:
- Lines 1668-1716: because the treasury account is in `stake_info` (it staked), the loop adds only the corrupted `reward` value (`validator_rewards.get(account_id)`) to `account.locked()`.
- Lines 1728-1755: the treasury-specific credit branch is explicitly skipped because `stake_info.contains_key(account_id)` is true ("If protocol treasury stakes, then the rewards was already distributed above").

Both this comment's assumption and the actual data are wrong: the "already distributed" reward is not the full treasury reward, it's only the treasury's own validator-production reward with `epoch_protocol_treasury` silently dropped by the HashMap collision. No code path ever credits `epoch_protocol_treasury` to any account's `amount()` or `locked()` once this collision occurs, yet the epoch's `minted_amount` (which increases `total_supply` via `core/primitives/src/block.rs`) already includes it.

This is not stopped by any existing check: there is no signature/access-key/gas/storage-staking check relevant to this internal epoch-boundary bookkeeping path, and no invariant check catches the missing funds because `update_validator_accounts`'s only invariant assertion (`account.locked() < max_of_stakes`) does not verify total minted vs. total credited amounts.

### Impact Explanation
This is a token supply/ledger inconsistency: `total_supply` is inflated by `epoch_protocol_treasury` at the epoch boundary block, but that amount never appears in `account.amount()` or `account.locked()` of any account. This matches the "token inflation or loss" bounty category — funds are conjured into `total_supply` accounting but never actually exist in any spendable/stakable account, producing an unrecoverable ledger/total-supply mismatch (state-root/economic invariant divergence from the documented reward-distribution model).

### Likelihood Explanation
This requires only that the account configured as `protocol_treasury_account` (e.g. `near` on mainnet, set in genesis config) also be selected as an active validator for an epoch — a condition reachable via an ordinary `Stake` action signed by whoever controls that account's keys, with no other privilege needed. Once triggered, the bug reproduces deterministically every epoch in which the treasury account remains an active validator, since the `HashMap::insert` collision at `reward_calculator.rs:142` is unconditional whenever `account_id == protocol_treasury_account`. The precondition (treasury account controlling a validator key and staking) is the limiting factor; it is not something a fully unprivileged attacker without control of the specific treasury account can normally trigger, but it does not require any node/validator/network-operator privilege beyond a normal signed `Stake` transaction from that account.

### Recommendation
In `RewardCalculator::calculate_reward`, avoid unconditional overwrite of `res` entries — use `res.entry(account_id).and_modify(|r| *r = r.checked_add(reward).unwrap()).or_insert(reward)` (or equivalent explicit merge logic) so a validator that happens to be the protocol treasury account accumulates both its production reward and its treasury share in the returned map. Additionally, `update_validator_accounts` in `runtime/runtime/src/lib.rs` should not assume the treasury reward is "already distributed" purely based on `stake_info.contains_key`; instead it should explicitly account for and credit the treasury's inflation share independent of whether the treasury account is also staking.

### Proof of Concept
Add a unit test in `chain/epoch-manager/src/reward_calculator.rs` where `validator_block_chunk_stats`/`validator_stake` include an entry keyed by `reward_calculator.protocol_treasury_account` (simulating the treasury account being an active, block-producing validator) with nonzero stake and full uptime. Assert:
1. `result.0.get(&protocol_treasury_account)` equals only the validator-production reward component, not `epoch_protocol_treasury + production_reward`.
2. `result.1` (`epoch_actual_reward`/minted amount) equals `epoch_protocol_treasury + production_reward` (i.e., strictly greater than `result.0.get(&protocol_treasury_account)`), demonstrating the discrepancy.

Complement with a runtime/test-loop integration test extending `test_validator_reward_in_get_validator_info` (`test-loop-tests/src/tests/stake_nodes.rs:598`): configure the protocol treasury account to also be one of the staked validators, run through an epoch boundary, and assert `sum(all account balances + locked)` after the boundary block is less than `new_total_supply` by exactly `epoch_protocol_treasury`.     fn update_validator_accounts(
        &self,
        state_update: &mut TrieUpdate,
        validator_accounts_update: &ValidatorAccountsUpdate,
    ) -> Result<(), RuntimeError> {
        for (account_id, max_of_stakes) in &validator_accounts_update.stake_info {
            if let Some(mut account) = get_account(state_update, account_id)? {
                if let Some(reward) = validator_accounts_update.validator_rewards.get(account_id) {
                    tracing::debug!(target: "runtime", %account_id, %reward, locked = %account.locked(), "account adding reward to stake");
                    let locked = account.locked().checked_add(*reward).ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow("update_validator_accounts".into())
                    })?;
                    account.set_locked(locked).or_inconsistent_state(account_id)?;
                }

                tracing::debug!(target: "runtime",
                       %account_id, locked = %account.locked(), %max_of_stakes,
                       "account stake and max of stakes"
                );
                if account.locked() < *max_of_stakes {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. \
                         Account stake {} is less than maximum of stakes {} in the past three epochs",
                        account.locked(),
                        max_of_stakes)).into());
                }
                let last_proposal = *validator_accounts_update
                    .last_proposals
                    .get(account_id)
                    .unwrap_or(&Balance::ZERO);
                let return_stake = account
                    .locked()
                    .checked_sub(max(*max_of_stakes, last_proposal))
                    .ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - return stake".into(),
                        )
                    })?;
                tracing::debug!(target: "runtime", %account_id, %return_stake, "account return stake");
                let locked = account.locked().checked_sub(return_stake).ok_or_else(|| {
                    RuntimeError::UnexpectedIntegerOverflow(
                        "update_validator_accounts - set_locked".into(),
                    )
                })?;
                account.set_locked(locked).or_inconsistent_state(account_id)?;
                account.set_amount(account.amount().checked_add(return_stake).ok_or_else(
                    || {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - set_amount".into(),
                        )
                    },
                )?);

                set_account(state_update, account_id.clone(), &account);
            } else if *max_of_stakes > Balance::ZERO {
                // if max_of_stakes > 0, it means that the account must have locked balance
                // and therefore must exist
                return Err(StorageError::StorageInconsistentState(format!(
                    "Account {} with max of stakes {} is not found",
                    account_id, max_of_stakes
                ))
                .into());
            }
        }

        if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
            // If protocol treasury stakes, then the rewards was already distributed above.
            if !validator_accounts_update.stake_info.contains_key(account_id) {
                let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
                    StorageError::StorageInconsistentState(format!(
                        "Protocol treasury account {} is not found",
                        account_id
                    ))
                })?;
                let treasury_reward = *validator_accounts_update
                    .validator_rewards
                    .get(account_id)
                    .ok_or_else(|| {
                        StorageError::StorageInconsistentState(format!(
                            "Validator reward for the protocol treasury account {} is not found",
                            account_id
                        ))
                    })?;
                account.set_amount(account.amount().checked_add(treasury_reward).ok_or_else(
                    || {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - treasure_reward".into(),
                        )
                    },
                )?);
                set_account(state_update, account_id.clone(), &account);
            }
        }
        state_update.commit(StateChangeCause::ValidatorAccountsUpdate);

        Ok(())
    }
