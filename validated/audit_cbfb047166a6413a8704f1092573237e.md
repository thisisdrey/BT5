### Title
Unauthenticated event-injection endpoint on the signer's HTTP receiver allows forging node events (StackerDB chunks, block-validation responses, burn/Stacks blocks) - (File: `libsigner/src/events.rs`)

### Summary
`SignerEventReceiver`, the HTTP server the `stacks-signer` binary runs to receive events pushed by a `stacks-node` (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`), performs no authentication, origin check, or source verification on inbound POST requests before decoding them into trusted `SignerEvent`s and forwarding them to the signer runloop.

### Finding Description
The documentation and node config make an explicit trust-channel claim: the `auth_token`/`auth_password` pair "secures the communication channel between this node and a connected `stacks-signer` instance" [1](#0-0) . In practice that token is only checked on requests flowing from the signer to the node (e.g. `/v3/block_proposal`, `/v2/blocks?broadcast=1`); it is never consulted on the reverse channel, where the node pushes `events_observer` payloads to the signer's bound HTTP endpoint.

`SignerEventReceiver::bind` simply opens a plain `HttpServer` on the configured socket [2](#0-1) , and `next_event` dispatches purely on the URL path with no credential check whatsoever: [3](#0-2) 

`process_event` then just reads the body and deserializes it into the expected event type, with no signature, HMAC, or auth-header verification: [4](#0-3) 

The reference/sample configuration for this exact binary tells operators to bind on `0.0.0.0:30000`: [5](#0-4) 

This breaks the "authenticated vs. stored/acted-upon" equality that the rest of the system assumes for signer↔node traffic: any host that can reach the bound port (network segment, container network, misconfigured firewall, or literally `0.0.0.0`) can POST a JSON body to `/proposal_response`, `/new_burn_block`, `/new_block`, or `/stackerdb_chunks` and have it accepted and forwarded into the signer's event stream as if it originated from the paired, trusted node — with no cryptographic or shared-secret gate at the one place (the receiver) where the trust boundary is supposed to be enforced.

### Impact Explanation
Because the receiver treats any POST to these paths as an authentic node event, an unauthenticated network peer can inject forged `BlockValidateResponse`, `BurnBlockEvent`, or `StacksBlockEvent` data into the signer's processing pipeline. `StackerDBChunksEvent` chunks are later re-checked for a valid slot signature further downstream (`libstackerdb`/`stackerdb` verification), which limits forgeability of that specific path, but the receiver itself performs zero filtering before enqueueing any of the four event kinds — the auth gate simply doesn't exist at the transport layer that is supposed to demarcate "trusted node" from "the network." This is an auth-gate-fails-open condition on unprivileged input, matching the report's core bug class (any party able to reach the endpoint can talk to it and have its data trusted, regardless of same-origin/ACL expectations).

### Likelihood Explanation
Likelihood is high in any deployment that follows the shipped reference config (`endpoint = "0.0.0.0:30000"`) or otherwise exposes the signer's event port beyond loopback (containers, k8s pods, VPS with permissive security groups). No credentials, node private key, or prior access are required — only network reachability to the bound TCP port.

### Recommendation
Add authentication to the node→signer direction of the channel: require the signer's `SignerEventReceiver` to validate an `Authorization`/shared-secret header (reusing the existing `auth_token`/`auth_password` mechanism, but enforced on receipt, not just on the signer's outbound requests) before accepting `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` POSTs, and reject/drop unauthenticated requests instead of processing them.

### Proof of Concept
Given a signer bound on `0.0.0.0:30000` (as shown in the shipped `sample/conf/signer/mainnet-signer-conf.toml`), from any host that can reach that port:
```
curl -X POST http://<signer-host>:30000/proposal_response \
  -H "Content-Type: application/json" \
  -d '{ ... forged BlockValidateOk/BlockValidateReject JSON ... }'
```
`process_event::<T, BlockValidateResponse>` in `libsigner/src/events.rs` will deserialize this body and forward it to the signer runloop with no check that it actually came from the paired `stacks-node`, exactly mirroring the transport-layer trust bypass described in the external report (any party able to reach the endpoint is treated as authorized).

Note: I could not fully trace how `BlockValidateResponse`/`BurnBlockEvent` forgeries are consumed inside `stacks-signer/src/v0/signer.rs` (that decision logic is explicitly out of scope for this analysis), so the exact downstream consequence (e.g., whether it can cause a bad co-signature) is not verified here — the finding is scoped strictly to the missing authentication at the transport layer in `libsigner/src/events.rs`.

    fn next_event(&mut self) -> Result<SignerEvent<T>, EventError> {
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)
            } else if request.url() == "/new_block" {
                process_event::<T, StacksBlockEvent>(request)
            } else {
                let url = request.url().to_string();
                debug!(

                    event_receiver.local_addr,
                    url
                );
                ack_dispatcher(request);
                Err(EventError::UnrecognizedEvent(url))
            }
        })?

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
```
