### Title
Hardcoded, unverified `eth_wallet_global_contract_hash` mainnet/testnet constants can permanently brick ETH-implicit accounts - (File: `runtime/near-wallet-contract/src/lib.rs`)

### Summary
`eth_wallet_global_contract_hash()` returns hand-written `CryptoHash` byte-array literals for `MAINNET`/`TESTNET`/`MOCKNET`, instead of deriving the hash from the embedded wallet-contract WASM the way the `LOCALNET` branch does. This is the same bug class as the reported `_INIT_CODE_HASH` issue: a manually hardcoded hash used to identify/derive an on-chain artifact, which can silently diverge from the artifact it is supposed to represent, causing address/identity resolution to point at nothing (or the wrong thing).

### Finding Description
`eth_wallet_global_contract_hash` computes the `AccountContract::Global` code hash that every newly created ETH-implicit account is initialized with: [1](#0-0) 

Note the asymmetry: for `MAINNET`/`TESTNET` the function returns hardcoded literal byte arrays (manually transcribed, with only a base58 comment as a cross-check), whereas for every other chain id (including `LOCALNET`) it computes the hash directly from the embedded WASM via `*LOCALNET.read_contract().hash()`. The hardcoded constants are never checked at runtime against the actual embedded `MAINNET`/`TESTNET` wallet-contract bytes; the only guard is a unit test that asserts the constants equal themselves in base58 form: [2](#0-1) 

This hash is consumed directly at ETH-implicit account creation: [3](#0-2) 

and again when resolving which code to execute for a `FunctionCall` on an existing account: [4](#0-3) 

If the hardcoded literal ever diverges from the hash of the wallet-contract WASM that is actually deployed as the global contract on-chain (e.g. a transcription mistake when the constant was added, or the embedded `res/wallet_contract_mainnet.wasm` / `res/wallet_contract_testnet.wasm` is updated without regenerating this constant), every newly created ETH-implicit account is stamped with `AccountContract::Global(code_hash)` for a code hash that has no corresponding `TrieKey::GlobalContractCode` entry in state.

### Impact Explanation
An ETH-implicit account can only ever be operated through the wallet contract's `rlp_execute` entry point — it has no regular access key, cannot be given one via `AddKey` (rejected because there is no existing access key to authorize it), and cannot be deleted: [5](#0-4) 

If the global contract code hash baked into such an account does not resolve to any stored code, every `FunctionCall` to it (including `rlp_execute`) fails — `RuntimeContractIdentifier` would carry a `code_hash` for which `GlobalContractAccessExt::code` returns `None`. Because the account can never regain a usable access key or be deleted, any NEAR balance sent to it becomes **permanently frozen**, matching the "permanent freezing of funds" impact bar. This is analogous to the reported bug where an incorrect hardcoded init-code hash caused pool-address computation to point at the wrong/non-existent address, breaking all downstream operations against it.

### Likelihood Explanation
Under the current, checked-in constants the mainnet/testnet values appear self-consistent with their base58 comments, so there is no active exploit today. The vulnerability is the structural one: unlike `LOCALNET`, the mainnet/testnet path is not derived from the actual embedded contract bytes, so any future edit to `res/wallet_contract_mainnet.wasm`/`res/wallet_contract_testnet.wasm` (bug fix, protocol upgrade) without a matching, verified update to the hardcoded `eth_wallet_global_contract_hash` bytes — or any transcription slip when the literal was authored — silently breaks all ETH-implicit accounts created after the change, with no compiler or runtime check to catch the mismatch before deployment.

### Recommendation
Derive the mainnet/testnet global contract hash the same way `LOCALNET` does — from `MAINNET.read_contract().hash()` / `TESTNET.read_contract().hash()` — rather than duplicating it as a separate hardcoded literal, or at minimum add a compile-time/test-time assertion that the hardcoded constants equal the hash of the currently embedded WASM files, so any future WASM update that isn't accompanied by an updated constant fails CI instead of bricking newly created ETH-implicit accounts in production.

### Proof of Concept
Conceptual (not exploitable against the current, self-consistent constants, but demonstrating the failure mode):
1. A future PR updates `res/wallet_contract_mainnet.wasm` (e.g., a wallet-contract bugfix) but the author forgets to recompute and update the `CryptoHash` literal in `eth_wallet_global_contract_hash` for `chains::MAINNET`.
2. `action_implicit_account_creation_transfer` creates new ETH-implicit accounts with `AccountContract::Global(stale_hash)` [6](#0-5) , while the actually-deployed global contract (from `deploy_global_contract`) is keyed under the new WASM's real hash.
3. Any transfer creating such an account funds an account whose global code hash has no matching `GlobalContractCode` entry in the trie; `RuntimeContractIdentifier::resolve`/`code` resolution fails for every subsequent `FunctionCall` (including `rlp_execute`), and since the account has no access key and cannot be deleted, the transferred funds are permanently unreachable.
