## Analog Found

### Title
Snowbridge relayer reward payout allows an attacker-chosen, `Unlimited`-weight destination-side XCM execution that is never charged for — analog of the Gelato "uncapped payment-stage execution" bug ([File: bridges/snowbridge/primitives/core/src/reward.rs])

### Summary
The Gelato bug's core defect is: a fee/gas amount is measured over a scope that ends *before* the actual payment/settlement step, and that settlement step is then executed with **no cap on the computation it can trigger**, because it hands control to attacker-influenced code. `Snowbridge`'s `PayAccountOnLocation::pay_reward` reproduces this pattern: the relayer (an unprivileged, permissionless actor) supplies an arbitrary destination `beneficiary: Location` for the reward-mint XCM, and that XCM is sent with `weight_limit: Unlimited` and `UnpaidExecution`, meaning the actual execution cost on the receiving chain (AssetHub) is neither bounded to what was paid for nor charged to the relayer at all.

For Snowbridge rewards this resolves to `BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation)` and is passed straight through to `Location::try_from(account_location)` with no structural validation, then into `PayAccountOnLocation::pay_reward`: [2](#0-1) 

`PayAccountOnLocation::pay_reward` builds and sends the following XCM to AssetHub, using the caller-controlled `beneficiary` verbatim and an **unbounded** weight limit: [3](#0-2) 

Note the sequence:
- `UnpaidExecution { weight_limit: Unlimited, check_origin: None }` — the receiving side is instructed to permit execution regardless of actual weight consumed, and with no fee owed for it.
- `DepositAsset { assets: AllCounted(1).into(), beneficiary }` — `beneficiary` is the caller-supplied `Location`, unvalidated.
- The only cost actually charged on BridgeHub is the **XCMP delivery fee** (`XcmExecutor::charge_fees(relayer.clone(), fee)`), which reflects transport cost, not the cost of executing `DepositAsset` against an attacker-chosen `Location` on AssetHub.

This mirrors the Gelato defect precisely: the "fee" is computed and settled (delivery fee) at a point *before* the actual state-changing step (`DepositAsset` resolution against an attacker-supplied beneficiary) executes, and that later step is deliberately granted `Unlimited` weight and zero required payment, i.e., there is no equivalent of the "hard gas cap" that the Gelato team added as a fix.

### Impact Explanation
Because `weight_limit: Unlimited` combined with `UnpaidExecution` removes any fee-based bound on the destination-side execution, and the `beneficiary` `Location` is fully attacker-controlled and unvalidated, a malicious relayer can repeatedly call `claim_rewards_to` (once per accumulated reward entry, and rewards accumulate from ordinary message processing which any relayer can trigger cheaply) supplying `Location` values engineered to maximize resolution/deposit cost on AssetHub, while paying only the fixed, small `claim_rewards_to` weight and the XCMP delivery fee on BridgeHub. This is exactly the "public underpriced work that degrades block production or stalls bridge processing" category: cheap local cost, disproportionate/uncharged destination-side execution cost.

### Likelihood Explanation
No privileged role, governance action, or malicious relayer/node/validator collusion assumption beyond "an ordinary permissionless relayer calls a public extrinsic" is required — `claim_rewards_to` is callable by any signed account holding an accumulated reward, and the destination `beneficiary` is accepted without validating its structural complexity or resolvability cost. The `Unlimited`/`UnpaidExecution` pairing is present in the shipped code with no accompanying gas/weight hard-cap check on the destination side, unlike the Gelato post-fix design.

### Recommendation
Bound the destination-side execution the same way the Gelato fix bounded the fee-transfer step: replace `weight_limit: Unlimited` with a concrete, pre-computed weight limit sized for a single `DepositAsset` to a simple account, reject/normalize `beneficiary` locations that are not a plain, shallow account-style `Location` before constructing the XCM, and/or charge (or otherwise budget) for the destination-side weight rather than only the XCMP delivery fee.

### Proof of Concept
1. Relayer processes any Snowbridge inbound message (even with a minimal `relayer_fee`/tip) to accrue a reward via `RewardLedger::register_reward`.
2. Relayer calls `pallet_bridge_relayers::claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(location))` where `location` is crafted to be maximally expensive to resolve/deposit-into on AssetHub (e.g., maximal junction depth allowed by `Location`).
3. `BridgeRewardPayer::pay_reward` → `PayAccountOnLocation::pay_reward` sends the XCM shown above to AssetHub with `Unlimited` weight and `UnpaidExecution`; only the XCMP delivery fee is charged on BridgeHub.
4. AssetHub executes the message and pays the full (uncapped, uncharged) cost of resolving/depositing to the attacker-chosen `beneficiary`, while the relayer's on-chain cost was the fixed `claim_rewards_to` weight plus a small delivery fee — repeatable per accrued reward. [4](#0-3)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
