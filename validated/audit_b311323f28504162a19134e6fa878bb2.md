## Title
DoS via unchecked slice-index arithmetic when parsing reftable ref blocks - (File: internal/git/reftable/reftable.go)

### Summary
The external report concerns unchecked/unsafe arithmetic (raw multiplication) in `RubiconMarket.sol` that can overflow and corrupt accounting state. The closest reachable analog in Gitaly is not a numeric-overflow issue (Go's fixed-width unsigned arithmetic wraps rather than reverting, and the sizes involved are bounded by file layouts), but an equivalent "unsafe arithmetic used directly as slice bounds without validation" pattern in the reftable block/ref parser, `Table.getRefsFromBlock` and `Table.parseRefBlock` in `internal/git/reftable/reftable.go`. Attacker-influenced length fields decoded from the file are used directly as slice indices/arithmetic operands with no bounds checking against the underlying buffer, unlike the parallel `internal/git/mvcc/manifest.go` parser and `internal/git/packfile/bitmap.go`, which both defensively bound-check decoded sizes before using them.

### Finding Description
`getRefsFromBlock` (reftable.go L221-301) decodes `prefixLength`, `suffixLength`, and `extra` via `getVarInt` and then performs:

```go
refname := prefix[:prefixLength] + string(src[idx:idx+suffixLength])
idx = idx + suffixLength
``` [1](#0-0) 

Neither `prefixLength` (bounded against `len(prefix)`) nor `suffixLength`/`idx+suffixLength` (bounded against `len(src)`) is validated before being used as a slice bound. `getVarInt` itself only checks that the *byte offset* used while decoding the varint stays within `blockEnd` [2](#0-1) ; it never constrains the *decoded value* itself, so a crafted table can produce a `suffixLength` or `prefixLength` far larger than any real buffer size.

Similarly, `parseRefBlock` computes:
```go
b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)
``` [3](#0-2) 
using unsigned (`uint`) arithmetic on values (`currentBS`, `b.RestartCount`) taken directly from file content. If `currentBS < 2+3*RestartCount`, the subtraction underflows (wraps to a huge `uint`), producing an out-of-range `RestartStart` that is then used as a loop bound and slice index in `getRefsFromBlock`.

This mirrors the reported bug class: raw arithmetic (subtraction/addition used as an implicit multiplier/offset) performed on attacker-influenced integers without the defensive bounds-checking pattern that the codebase already uses elsewhere (e.g. `ReadEWAH`'s explicit `> math.MaxInt32` checks in `internal/git/packfile/bitmap.go` L192-208, and the manifest chunk bounds checks in `internal/git/mvcc/manifest.go` L280-320), which the report's mitigation recommendation ("use the guarded/safe operation already available in the codebase") directly parallels.

### Impact Explanation
Because `src[idx : idx+suffixLength]` and `prefix[:prefixLength]` are unchecked, a malformed/crafted reftable causes a Go runtime panic (slice bounds out of range) inside `GetReferences`/ref-listing code paths. Since Gitaly uses reftables as its reference backend, a repository containing (or having been made to contain, e.g., via replication of a corrupted/adversarial source, or a repository restored from an untrusted backup/import) a corrupted `.ref` table file can crash the RPC handler that lists references (`ListRefs` and related services depend on `Table.GetReferences`). Depending on panic-recovery middleware, this is a per-RPC or per-connection denial of service against an unprivileged, ordinary ref-listing operation.

### Likelihood Explanation
Reftable files are normally written only by Git/Gitaly itself, so triggering this from a fully "ordinary" client push is not directly demonstrated by the available code paths (I could not confirm from the indexed code whether an ordinary user-controlled push can force write of adversarial byte sequences into a reftable's ref-block content, e.g., via crafted ref names of a specific length composition). It is more clearly reachable via replication/backup-restore/import flows that read a reftable file whose provenance is not guaranteed to be well-formed (e.g., corrupted during replication, restored from backup, or copied from a partially-written state). Because of this uncertainty about a direct "ordinary user's push" trigger, likelihood is assessed as moderate rather than high.

### Recommendation
- In `getVarInt`, `getRefsFromBlock`, and `parseRefBlock`, validate every decoded length/offset against the actual buffer/`blockEnd` bounds before using it as a slice index or in further arithmetic (mirroring the explicit bounds checks already used in `internal/git/mvcc/manifest.go`'s `parseChunks` and `internal/git/packfile/bitmap.go`'s `ReadEWAH`).
- Reject `prefixLength > len(prefix)`, `idx+suffixLength > blockEnd`/`len(src)`, and `currentBS < 2+3*RestartCount` (to prevent unsigned-underflow of `RestartStart`) with explicit errors instead of allowing panics or wrapped-arithmetic values to propagate into slicing operations.
- Add fuzz/unit tests feeding malformed reftable blocks (oversized varints, truncated blocks, corrupt restart counts) to confirm graceful error returns rather than panics.

### Proof of Concept
Not independently reproduced against a running Gitaly instance; the above is derived from static analysis of `internal/git/reftable/reftable.go`. A conceptual PoC: construct a `.ref` file whose ref-block encodes a `suffix_length` varint value larger than the remaining bytes in the block (or a `restart_count` such that `2 + 3*restart_count > block_len`), then call `Table.GetReferences()` (reachable via ref-listing RPCs backed by reftable storage) to trigger an out-of-range slice panic.

func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}
