### Title
Missing buffer between borrowing limit and liquidation threshold allows immediate and repeated liquidations - (`contracts/Pool.sol`)

### Summary
Metronome uses each collateral’s `collateralFactor` both as the maximum borrowing limit and as the liquidation threshold. A borrower who mints at the maximum permitted debt becomes liquidatable after only a minimal increase in debt or decrease in collateral value, and each successful liquidation can leave the account unhealthy and exposed to further liquidations. [1](#0-0) [2](#0-1) 

### Finding Description
`DebtToken.issue()` calculates `_issuableInUsd` through `Pool.debtPositionOf()` and allows minting until debt equals that limit. [3](#0-2) 

`Pool.depositOf()` derives `_issuableLimitInUsd` as the sum of collateral USD value multiplied by `collateralFactor`. [4](#0-3) 

`Pool.debtPositionOf()` treats a position as healthy whenever `_debtInUsd <= _issuableLimitInUsd`, meaning the liquidation threshold is exactly the maximum borrowing limit rather than a higher collateralization boundary. [1](#0-0) 

During liquidation, `Pool.liquidate()` merely checks that same `_isHealthy` flag, then allows any third-party caller to burn synthetic assets, burn the borrower’s debt, and seize collateral plus liquidation incentives. [2](#0-1) [5](#0-4) 

Production deployment scripts configure collateral factors as high as 75%, while the default initialization sets `maxLiquidable` to 50%. [6](#0-5) [7](#0-6) 

The default liquidation economics additionally seize 10% for the liquidator and 8% for the protocol, so a minimally breached position can immediately lose collateral exceeding the debt repaid. [8](#0-7) 

### Impact Explanation
A borrower at the borrowing limit has no operational buffer against interest accrual, oracle updates, or minor price movement. [1](#0-0) 

Once `_debtInUsd` exceeds `_issuableLimitInUsd` by any amount, an unprivileged liquidator can call `Pool.liquidate()` and receive collateral worth more than the repaid debt through the liquidation incentive. [2](#0-1) [9](#0-8) 

Because `liquidate()` performs no post-liquidation health requirement, a repayment below the recovery amount can leave the borrower unhealthy and available for repeated liquidation. [10](#0-9) 

The repository’s own liquidation helper derives the repayment needed to restore `D == LIMIT`, explicitly showing that smaller repayments do not restore health. [11](#0-10) 

The existing test suite confirms this behavior: after liquidating half of the minimum recovery amount, `isHealthyAfter` remains false and the borrower’s remaining collateral is fully locked. [12](#0-11) 

This produces direct collateral loss to borrowers through liquidation penalties and allows liquidation calls to continue while the account remains unhealthy. [2](#0-1) [13](#0-12) 

### Likelihood Explanation
Borrowing at the configured maximum is an explicitly permitted public action because `issue()` only reverts when the requested debt exceeds the full issuable limit. [3](#0-2) 

No privileged actor is required to trigger liquidation: any account holding the relevant synthetic token can call `liquidate()` once the account is unhealthy. [14](#0-13) [5](#0-4) 

Interest-bearing debt can cross the threshold without any malicious oracle input because `liquidate()` calls `accrueInterest()` before evaluating health. [15](#0-14) [16](#0-15) 

Liquidation incentives make immediate monitoring and liquidation economically attractive for unprivileged bots. [8](#0-7) [13](#0-12) 

### Recommendation
Introduce a separate per-collateral liquidation threshold that is strictly higher than its borrowing `collateralFactor`. [17](#0-16) 

Use the borrowing factor for `issue()` capacity and the higher liquidation factor for health checks, so a position borrowing at maximum LTV remains healthy until the configured safety buffer is consumed. [1](#0-0) 

Alternatively, keep `collateralFactor` as the liquidation threshold and introduce a lower `borrowFactor` for issuance. [4](#0-3) 

Validate every configured factor such that `0 < borrowFactor < liquidationFactor < 1e18`, and extend `depositOf()`/`debtPositionOf()` to expose both limits. [18](#0-17) [19](#0-18) 

### Proof of Concept
The following Hardhat fork sequence demonstrates the reachable path on a production `Pool` with a nonzero-interest `DebtToken` and a collateral configured at maximum borrow capacity. [16](#0-15) [3](#0-2) 

```ts
// Assumes Hardhat mainnet fork and deployed Pool/DepositToken instances.
const pool = await ethers.getContractAt('Pool', POOL_ADDRESS)
const depositToken = await ethers.getContractAt('DepositToken', DEPOSIT_TOKEN_ADDRESS)
const underlying = await ethers.getContractAt('IERC20', await depositToken.underlying())

// Select a production debt token with a nonzero interest rate.
for (const debtTokenAddress of await pool.getDebtTokens()) {
  const debtToken = await ethers.getContractAt('DebtToken', debtTokenAddress)
  if ((await debtToken.interestRate()).gt(0)) {
    const synth = await ethers.getContractAt(
      'SyntheticToken',
      await debtToken.syntheticToken()
    )

    // Victim deposits collateral and mints exactly the maximum debt.
    await deal(underlying, victim.address, collateralAmount)
    await underlying.connect(victim).approve(depositToken.address, collateralAmount)
    await depositToken.connect(victim).deposit(collateralAmount, victim.address)

    const position = await pool.debtPositionOf(victim.address)
    const maxDebt = await pool.masterOracle().then(oracle =>
      oracle.quoteUsdToToken(synth.address, position._issuableInUsd)
    )
    await debtToken.connect(victim).issue(maxDebt, victim.address)

    // Interest accrual makes debt marginally greater than the same limit
    // used as the liquidation threshold.
    await time.increase(1)
    expect((await pool.debtPositionOf(victim.address))._isHealthy).to.eq(false)

    // An unprivileged liquidator holding synth liquidates the position.
    const repayAmount = await pool.quoteLiquidateMax(
      synth.address,
      victim.address,
      depositToken.address
    )
    await pool.connect(liquidator).liquidate(
      synth.address,
      victim.address,
      repayAmount,
      depositToken.address
    )

    break
  }
}
```

The same flow can be reproduced without relying on manipulated oracle data: borrowing reaches the maximum through `issue()`, interest accrual increases debt, and `liquidate()` uses the identical collateral-factor-derived limit to determine eligibility. [19](#0-18) [20](#0-19) 

A smaller repayment can also be selected with `getMinLiquidationAmountInUsd()`, which returns the amount needed to restore `debt == limit`; repaying half that amount leaves the position unhealthy, as demonstrated by the repository’s test. [11](#0-10) [21](#0-20)
