### Title
Accrued Commission Redirected to New Beneficiary Due to Missing `synchronize_delegation_pool` in `set_beneficiary_for_operator` — (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary

`delegation_pool::set_beneficiary_for_operator` changes the commission beneficiary address without first calling `synchronize_delegation_pool` to commit already-accrued but uncommitted commission rewards. The next time any stake-management operation triggers `synchronize_delegation_pool`, all previously accrued commission is paid to the **new** beneficiary instead of the **old** one. An operator can exploit this to steal accrued commission from the current beneficiary by switching the beneficiary to themselves before the rewards are committed.

### Finding Description

Every stake-management entry point in `delegation_pool.move` (`add_stake`, `unlock`, `reactivate_stake`, `withdraw`, `set_operator`, `update_commission_percentage`, `vote`) calls `synchronize_delegation_pool` as its first action to commit pending rewards before any state change. [1](#0-0) 

`synchronize_delegation_pool` distributes accrued commission by calling `buy_in_active_shares` and `buy_in_pending_inactive_shares` with the **current** value of `beneficiary_for_operator` at the time of the call: [2](#0-1) 

`set_beneficiary_for_operator`, however, does **not** call `synchronize_delegation_pool` before mutating the beneficiary address. It simply overwrites the stored address: [3](#0-2) 

The code's own comment acknowledges this gap but treats it as a caller responsibility rather than an enforced invariant: [4](#0-3) 

Compare with `set_operator`, which correctly calls `synchronize_delegation_pool` first to ensure the old operator is paid before the operator address changes: [5](#0-4) 

The same pattern exists in `staking_contract::set_beneficiary_for_operator`, which also omits the required `distribute` call: [6](#0-5) 

### Impact Explanation

An operator who has previously set a third-party beneficiary (address B) can:

1. Allow multiple epochs to pass so that commission rewards accrue in the stake pool but remain uncommitted (not yet passed through `synchronize_delegation_pool`).
2. Call `set_beneficiary_for_operator(operator_self)` — no sync occurs, the beneficiary pointer is silently redirected.
3. The next stake-management operation by any delegator triggers `synchronize_delegation_pool`, which calls `buy_in_active_shares(..., beneficiary_for_operator(...), commission_active)` — now resolving to `operator_self`.
4. All commission that accrued while B was the beneficiary is credited to `operator_self`. B receives nothing.

This is a direct theft of staking commission balances from the old beneficiary. The old beneficiary has no on-chain mechanism to prevent or detect this before it occurs.

### Likelihood Explanation

- The entry point `set_beneficiary_for_operator` is a public, unprivileged transaction callable by any operator on mainnet.
- No special conditions are required beyond having accrued commission (i.e., any active validator with a non-self beneficiary).
- The attack is silent: the old beneficiary only discovers the loss after the next sync, which may be triggered by an unrelated delegator action.
- The identical pattern exists in both `delegation_pool` and `staking_contract`, doubling the attack surface.

### Recommendation

**Short term:** Add a `synchronize_delegation_pool` call at the top of `set_beneficiary_for_operator` in `delegation_pool.move`, mirroring the pattern used in `set_operator`. For `staking_contract::set_beneficiary_for_operator`, call `request_commission_internal` (or `distribute_internal`) before updating the beneficiary address.

**Long term:** Enforce the invariant that any function mutating reward-routing state (operator, beneficiary, commission rate) must atomically commit all accrued rewards under the old routing before applying the new one. This should be a checked precondition, not a documentation note.

### Proof of Concept

```
// Epoch 0: operator sets beneficiary to B
set_beneficiary_for_operator(operator, B);

// Epochs 1–N: rewards accrue; synchronize_delegation_pool is never called
// commission_active grows with each epoch but is NOT committed to B

// Epoch N+1: operator silently redirects beneficiary to self
set_beneficiary_for_operator(operator, operator_self);
// No synchronize_delegation_pool call → B's accrued commission is NOT committed

// Any delegator calls add_stake / unlock / etc.
// → synchronize_delegation_pool fires
// → buy_in_active_shares(pool, beneficiary_for_operator(operator), commission_active)
//   resolves to operator_self, not B
// → All N epochs of accrued commission go to operator_self
// → B receives 0
```

The root cause maps exactly to the external report: `synchronize_delegation_pool` (the "charge" equivalent) is assumed to have been called before `set_beneficiary_for_operator` (the "redistribute" equivalent), but this is not enforced, allowing stale beneficiary state to misdirect accrued staking balances.

    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
