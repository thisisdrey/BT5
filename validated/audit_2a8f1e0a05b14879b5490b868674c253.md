### Title
Unprivileged user can force-insert tokens into a victim's per-account lists and exhaust `MAX_TOKENS_PER_USER`, blocking the victim's deposits and borrows - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The reference bug class is a state-changing action that can be triggered without authorization from the affected party (CSRF). The on-chain analog in Metronome is that `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are invoked by token contracts for *any* recipient account, and a permissionless `DepositToken.transfer` of dust to a victim mutates the victim's `depositTokensOfAccount` set without the victim's consent. An attacker can fill the victim's combined deposit+debt token list up to `MAX_TOKENS_PER_USER`, after which `onlyIfAdditionWillNotReachMaxTokens` reverts every subsequent list insertion for that account.

### Finding Description
`Pool` tracks each account's deposit and debt positions in bounded enumerable sets guarded by `MAX_TOKENS_PER_USER` [1](#0-0) . `addToDepositTokensOfAccount` is callable by any registered `DepositToken` and inserts `account_` (the token recipient) into the set [2](#0-1) . The same applies for debt tokens [3](#0-2) . Per the contract comments, the DepositToken calls this whenever an account's balance transitions from `0` — i.e., on every ERC20 `transfer`/`transferFrom`/`seize`/mint to a fresh holder. There is no check that the token movement was initiated or authorized by the receiving account. An attacker therefore mints (or buys) one wei of each of the protocol's deposit tokens and `transfer`s dust to the victim; each transfer inserts a new entry until `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == MAX_TOKENS_PER_USER`, after which every future `addTo*` for the victim reverts.

Note on confidence: the exact DepositToken hook (`_beforeTokenTransfer`/`_afterTokenTransfer` calling `addToDepositTokensOfAccount` unconditionally on 0→nonzero transitions) could not be fully read within tool limits; the Pool comments at lines 200–213 describe this call pattern explicitly. If the hook were gated by an opt-in flag the attack would not work — this should be verified in `DepositToken.sol`.

### Impact Explanation
Once the victim's list is saturated, any action that requires adding a new token to either set reverts: depositing a not-yet-held collateral type (deposit mint → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), issuing a new synth debt type, and receiving deposit tokens via `seize` during liquidation (the seize leg targeting the victim's counterparty also inserts into the recipient's set). A victim who needs to deposit new collateral to restore an unhealthy position is blocked, so their position can be liquidated while remediation is impossible — temporary freezing of the ability to manage funds, and in edge cases forced liquidation losses. The victim can recover by transferring the dust balances out (0-balance transitions trigger `removeFromDepositTokensOfAccount` [4](#0-3) ), so this is temporary freezing / forced-liquidation griefing rather than permanent theft — consistent with the "account list / freeze griefing" surface in the bug map.

### Likelihood Explanation
Fully permissionless: requires only an EOA, dust amounts of each listed deposit token, and gas for one transfer per token. No privileged role, oracle manipulation, or victim signature is needed — the victim's consent is never checked, exactly matching the CSRF shape of the reference report. Cost scales with the number of listed collaterals; the attacker's dust is not burned and can be reclaimed afterward, so cost is low.

### Recommendation
Verify the recipient's consent before mutating per-account lists, or decouple list membership from unsolicited balance changes: e.g., only call `addToDepositTokensOfAccount` from `DepositToken.deposit` (an action the account performs itself) rather than from generic ERC20 transfer hooks, or require `account_ == tx-authorized sender` for insertion. Alternatively, raise/remove the per-account cap or let `removeFrom*` be callable when a balance is zero regardless of consent (it already is), and document the self-healing path.

### Proof of Concept
Hardhat fork sketch against a deployed pool:

```ts
const victim = "0xVICTIM";
const depositTokens: string[] = await pool.getDepositTokens();

// Attacker obtains dust of each collateral and deposits via each DepositToken
for (const dt of depositTokens) {
  const dep = await ethers.getContractAt("DepositToken", dt);
  const underlying = await ethers.getContractAt("IERC20", await dep.underlying());
  await underlying.approve(dt, dust);
  await dep.deposit(dust, attacker.address);      // mint attacker deposit tokens
  await dep.transfer(victim, 1);                  // 0 -> nonzero: adds victim to list
}

// Victim's list is now full
expect(await pool.debtTokensOfAccountLen(victim) +
        (await pool.getDepositTokensOfAccount(victim)).length)
  .to.equal(MAX_TOKENS_PER_USER);

// Victim cannot deposit a collateral type they don't already hold
await expect(dep.connect(victimSigner).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// Victim cannot issue a new synth debt type either
await expect(newDebtToken.connect(victimSigner).issue(amount))
  .to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// If victim's position is unhealthy, a liquidator can still seize existing
// collateral while the victim is blocked from adding new collateral.
```
