### Title
Unvalidated Contract type index causes IndexOutOfBoundsException in multisig permission-bitmap check - ([File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java])

### Summary
`WalletUtil.checkPermissionOperations` (and its duplicate `TransactionUtil.checkPermissionOperations`) computes a bit index into a fixed 32-byte permission-operations bitmap using `contract.getTypeValue()` directly, without validating that the value is within the legal `ContractType` enum range (0–59). This mirrors the ksmbd bug class: an attacker-controlled value is used as an array/bitmap index without bounds checking against the actual backing storage size.

### Finding Description
`checkPermissionOperations` reads the raw protobuf enum value for the contract type and uses it, unchecked, to compute both a byte offset and a bit offset into a 32-byte (256-bit) `ByteString`: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException(...);
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`contract.getTypeValue()` returns the *raw* protobuf-wire int32 stored for the `ContractType type = 1` field [2](#0-1) . Protobuf's generated `getXxxValue()` accessor for an enum field always returns the wire-level integer, even for values that don't correspond to any declared enum constant ("unrecognized" values are preserved this way, unlike `getType()` which would collapse them to `UNRECOGNIZED`). This means a transaction crafted at the wire/byte level (not necessarily through the Java setter API) can set `Contract.type` to any int32 — including negative numbers or values far outside the declared range 0–59.

Given `contractType/8` (and, for negative values, Java's truncating integer division/remainder semantics), the computed index can fall well outside `[0, 31]`, the valid index range for the 32-byte `operations` `ByteString`. `ByteString.byteAt()` performs its own bounds check and throws `IndexOutOfBoundsException` rather than allowing true out-of-bounds memory access (Java's memory safety prevents the literal OOB read seen in the kernel CVE), but the *root cause* — an untrusted integer derived from user-controlled data used to index a fixed-size backing store without prior range validation — is directly analogous to the missing `KSMBD_EVENT_MAX` bound-check in `ksmbd_nl_policy`.

The identical unguarded pattern also exists in the second copy of this logic: [3](#0-2) 

This routine is invoked as part of the multisig permission verification flow that runs for every transaction carrying a `Permission_id`, i.e., it is on the standard signature/permission-validation path exercised for any broadcast transaction using account permissions.

### Impact Explanation
An unhandled `IndexOutOfBoundsException` thrown mid-way through permission/signature validation for a broadcast transaction is not caught as a `PermissionException`/`ContractValidateException` by this method's declared checked-exception contract, so it will propagate as an unexpected `RuntimeException` to its caller. Depending on how deep in the transaction-processing/validation pipeline this propagates without a generic `catch (Exception)` guard, this can abort processing of the transaction pool/validation thread, producing a denial-of-service condition for the node handling the crafted transaction (an unhandled exception thrown during core transaction validation service, reachable from any unprivileged HTTP/gRPC transaction broadcaster).

### Likelihood Explanation
High: any account with a permission configured (owner/active/witness with `Permission_id`) can be targeted by crafting a transaction whose `Contract.type` field is set to an out-of-range wire value. This does not require any special privilege, key material beyond an already-existing account, or race condition — a single malformed but well-signed (or attacker-broadcast) transaction is sufficient to trigger the code path.

### Recommendation
Bound-check `contractType` against the valid `ContractType` enum range (e.g., `0 <= contractType && contractType < ContractType.values().length` or explicitly `< 32*8`) before using it to index into the `operations` bitmap, and reject the transaction with a normal validation error (`ContractValidateException`/`PermissionException`) instead of allowing an uncaught runtime exception. Apply the same fix to both copies of the logic in `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`.

### Proof of Concept
1. Construct a `Transaction` whose `raw_data.contract[0].type` field is serialized at the protobuf wire level with an int32 value outside `[0, 255]`'s valid mapped enum range (e.g., `100000` or a negative varint), while other fields (permission id, signatures) are set up to route through the multisig/permission check.
2. Broadcast the transaction to a java-tron node via the standard transaction submission API.
3. When `checkPermissionOperations` runs `operations.byteAt(contractType / 8)` with `contractType = 100000`, the index `12500` (out of range for the 32-byte operations blob) causes `ByteString.byteAt` to throw `IndexOutOfBoundsException`, propagating an unhandled runtime exception during transaction validation.
