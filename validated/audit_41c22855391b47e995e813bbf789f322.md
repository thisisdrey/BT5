### Title
Unbounded ref accumulation in `FindRefsByOID` unary RPC enables memory-exhaustion DoS - (File: internal/gitaly/service/ref/find_refs_by_oid.go)

### Summary
`FindRefsByOID` is a **unary** RPC (single request → single response) that loops over every reference in a repository matching the caller-supplied `Oid`/`RefPatterns` and appends each one to an in-memory `[]string` before returning it as one gRPC message. There is no default cap: the request's `Limit` field is optional and defaults to `0`, meaning "no limit." An ordinary user who controls the number of refs pointing at a given object (e.g., by pushing many tags/branches to the same commit) can force the handler to build and return an arbitrarily large response, exhausting Gitaly's memory or violating gRPC constraints.

### Finding Description
The handler builds the result set with an unbounded accumulation loop: [1](#0-0) 

```go
forEachRefIter := gitpipe.ForEachRef(
    ctx, repo, patterns,
    gitpipe.WithSortField(in.GetSortField()),
    gitpipe.WithPointsAt(in.GetOid()),
    gitpipe.WithCount(int(in.GetLimit())),
)

var refs []string
for forEachRefIter.Next() {
    refs = append(refs, string(forEachRefIter.Result().ObjectName))
}
```

`gitpipe.WithCount` only forwards `--count` to `git for-each-ref` when `in.GetLimit()` is non-zero, per the proto contract: [2](#0-1) 

```proto
message FindRefsByOIDRequest {
  ...
  // limit limits the amount of results returned. 0 means no limit.
  uint32 limit = 5;
}
```

Because `FindRefsByOID` is unary rather than streamed, the entire `refs` slice must be materialized in memory and marshaled into a single `FindRefsByOIDResponse` before it can be sent, unlike `ListRefs`, which streams and paginates results: [3](#0-2) 

The project's own RPC-development guidance states this pattern must be avoided: "**Stream unbounded or oversized payloads.** Use a `stream` when the result is an unbounded sequence (a `repeated` collection that can grow without limit)..." [4](#0-3) 

No `MaxSendMsgSize` is configured anywhere in the codebase, so grpc-go's default (effectively unbounded send size) applies, meaning the server will attempt to allocate and transmit the full response regardless of size before any transport-level limit intervenes.

### Impact Explanation
A repository with a large number of references pointing at the same object (achievable via normal, unprivileged push/tag operations — no special access required) turns `FindRefsByOID` into a resource-exhaustion vector: a single call with `Limit=0` forces Gitaly to enumerate and hold every matching ref name in memory and marshal them into one gRPC message. Repeated or concurrent calls against such a repository can drive up memory usage on the Gitaly node significantly, degrading or crashing the process and impacting all repositories/tenants served by that node (a shared, unauthenticated-resource DoS within the RPC-handler resource-limit category).

### Likelihood Explanation
Likelihood is moderate-to-high: creating many refs (tags/branches) pointing at one commit is an ordinary, unprivileged Git operation, and the request field enabling the unbounded path (`Limit=0`, the default) requires no special crafting — it's simply omitting the optional limit. No authentication bypass or elevated privilege is needed; only push access to a repository and the ability to invoke `FindRefsByOID` (a standard, non-privileged RPC) are required.

### Recommendation
- Enforce a hard, server-side maximum on the number of refs (and/or serialized bytes) that `FindRefsByOID` will accumulate, independent of the caller-provided `Limit`.
- Convert `FindRefsByOID` to a streaming RPC (matching the pattern already used by `ListRefs`) so results are paginated/chunked rather than buffered entirely in memory before being sent.
- Configure explicit `MaxSendMsgSize`/`MaxRecvMsgSize` bounds on the gRPC server as defense in depth.

### Proof of Concept
1. As an ordinary user with push access, create a large number of tags (e.g., tens of thousands) all pointing at the same commit `<oid>` in a repository.
2. Call `FindRefsByOID` with `Repository: <repo>`, `Oid: <oid>`, and `Limit` left unset (`0`).
3. Observe the handler's loop in `find_refs_by_oid.go` accumulate every matching ref into `refs` and attempt to marshal/send the entire set in a single unary response, causing elevated memory consumption proportional to the number of refs and, at scale, resource exhaustion on the Gitaly node.

  string oid = 2;

  // Providing more than one pattern will yield refs that match any of the given patterns.
  // If left empty, defaults to "refs/heads/" and "refs/tags/"

  // If left empty, defaults to "refname" (lexicographic refname order)
  string sort_field = 4;
  // limit limits the amount of results returned. 0 means no limit.
  uint32 limit = 5;
}
