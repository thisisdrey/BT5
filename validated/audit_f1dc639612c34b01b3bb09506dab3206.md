### Title
Unbounded ASN.1 DER signature parsing enables node crash via crafted transaction signature bytes - (File: crypto/src/main/java/org/tron/common/crypto/sm2/SM2.java)

### Summary
When java-tron is configured to use the SM2 signature scheme (`CommonParameter.isECKeyCryptoEngine() == false`), every signature attached to a broadcast transaction or block header is decoded from raw, attacker-controlled bytes using Bouncy Castle's low-level `ASN1InputStream` before any cryptographic sanity check is applied.

### Finding Description
`SM2.SM2Signature.decodeFromDER` feeds the raw signature bytes directly into `org.bouncycastle.asn1.ASN1InputStream` and calls `decoder.readObject()` / `seq.getObjectAt(...)` to materialize an `ASN1Integer`: [1](#0-0) 

This method is reached from `SM2.verify(byte[], byte[], byte[])` and `SM2.verifyMessage(...)`, which are the entry points exposed through `SignUtils.signatureToAddress(...)` when the node's crypto engine flag selects SM2 instead of secp256k1: [2](#0-1) 

The signature bytes decoded here are taken verbatim from the `Transaction.signature` field of any broadcast transaction (via `TransactionCapsule.validatePubSignature` → `validateSignature`) or from the block header witness signature (`BlockCapsule.validateSignature`), both of which are attacker/peer-controlled inputs processed before any authorization check succeeds: [3](#0-2) [4](#0-3) 

The referenced CVE-2026-13506 describes a bug in Bouncy Castle's lazy ASN.1 sequence handling where "forcing" (materializing) a lazily-parsed sequence resets the library's internal nesting-depth guard, allowing a crafted, deeply nested DER structure to bypass the depth limit that is supposed to prevent unbounded recursion during parsing. Because `SM2Signature.decodeFromDER` performs exactly this pattern — constructing an `ASN1InputStream` over fully attacker-controlled bytes and then forcing resolution of the sequence's elements (`getObjectAt`) — a vulnerable Bouncy Castle version bundled by java-tron would allow the depth guard to be bypassed here, leading to uncontrolled recursion (stack exhaustion / `StackOverflowError`) during signature decoding.

### Impact Explanation
A `StackOverflowError` thrown deep inside Bouncy Castle's ASN.1 parser during `decoder.readObject()` is not a checked `IOException`; it is an `Error`, which is not caught by the surrounding `catch (IOException e)` block in `decodeFromDER`, nor by the `catch (SignatureException | PermissionException | SignatureFormatException e)` in `validatePubSignature`. An uncaught `Error` propagating out of transaction/block signature validation can crash or corrupt the validating thread, resulting in denial of service for the node processing the crafted transaction or block — reachable by any unprivileged transaction broadcaster or peer once bundled to a vulnerable Bouncy Castle release.

### Likelihood Explanation
Exploitability depends entirely on: (1) the node's Bouncy Castle dependency version being within the vulnerable range described in CVE-2026-13506, and (2) the node being configured to use the SM2 signature engine (`isECKeyCryptoEngine() == false`), since the `secp256k1`/`ECKey` path in this codebase does not use raw `ASN1InputStream` decoding of untrusted bytes for the standard R/S/V signature format. I could not verify the exact Bouncy Castle version pinned in this repository's build files, so likelihood of practical exploitability cannot be confirmed without that check.

### Recommendation
- Confirm and, if needed, upgrade the Bouncy Castle dependency to the patched versions (>=1.85 core, >=2.73.12 LTS, or the corresponding FIPS fixes) referenced in the advisory.
- In `SM2.SM2Signature.decodeFromDER`, wrap the ASN.1 decoding in a broader safety boundary (e.g., catch `Throwable`/`Error` in addition to `IOException`) and/or pre-validate signature length/structure before invoking `ASN1InputStream`, to prevent an uncaught `Error` from crashing the validation thread regardless of underlying library bugs.

### Proof of Concept
Conceptual (cannot be fully executed without confirming the bundled Bouncy Castle version): an attacker configures the SM2 signature field of a broadcast `Transaction` (or a block header's witness signature) to contain a crafted DER byte sequence with deeply nested ASN.1 constructs designed to trigger the lazy-sequence-forcing nesting-depth bypass described in CVE-2026-13506. When the node calls `TransactionCapsule.validatePubSignature` → `SignUtils.signatureToAddress` → `SM2.signatureToAddress` → `SM2Signature.decodeFromDER`, the crafted bytes are parsed via `ASN1InputStream`, potentially triggering uncontrolled recursion and a `StackOverflowError` that is not caught by the existing exception handlers.
