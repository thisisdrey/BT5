### Title
Unbounded memory allocation in `run_http_request` before StackerDB chunk-size check - (File: libsigner/src/http.rs, libsigner/src/session.rs)

### Summary
`StackerDBSession::get_latest_chunks` (and every other RPC call routed through `rpc_request`) relies on `run_http_request` to fetch the HTTP response, but `run_http_request` calls `sock.read_to_end(&mut buf)` with no size cap whatsoever before any chunk-size validation occurs. A malicious or compromised StackerDB host (a peer that a signer connects to for chunk retrieval) can send an HTTP response with an arbitrarily large body, forcing the requesting signer to buffer the entire payload in memory before the `body_bytes.len() > limit` check in `get_latest_chunks` ever runs.

### Finding Description
The broken invariant: the intended guarantee is that a signer only ever stores/uses `body_bytes` bounded by `SIGNERS_STACKERDB_CHUNK_SIZE` (for signer contracts) or `STACKERDB_MAX_CHUNK_SIZE` otherwise, per `libsigner/src/session.rs` lines 230-262. In reality, the actual memory allocated during the read is unbounded by that limit.

- `run_http_request` in `libsigner/src/http.rs` writes the request, then does:
```
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
```
`Read::read_to_end` has no size cap and will keep growing `buf` (reallocating) for as long as the peer keeps sending bytes (bounded only by connection close or the `socket_timeout` set on the socket, which is a *time* bound, not a *size* bound) [1](#0-0) .
- After the full body is buffered, `decode_http_response` parses headers, and `decode_http_body` is called: for the non-chunked case it does `buf.to_vec()` — again with no length limit [2](#0-1) . Only the chunked-transfer-encoding path enforces `MAX_MESSAGE_LEN` via `HttpChunkedTransferReader`.
- The resulting `Vec<u8>` is returned up through `rpc_request` to `get_latest_chunks`, which only *then* checks `body_bytes.len() > limit` and discards it if oversized [3](#0-2) .

So the size check is entirely post-hoc: the full oversized body has already been read into process memory by the time it is evaluated. A StackerDB host that a signer polls (any node advertised in the signer set as a StackerDB replica, or a rogue node the signer is configured/tricked into contacting) can respond with a non-chunked `Content-Length`-free (or arbitrarily large `Content-Length`) body and force the signer to allocate memory proportional to whatever the attacker chooses to send, limited only by the attacker's willingness to keep the TCP connection open within the configured `socket_timeout`.

### Impact Explanation
A single StackerDB host response can force a signer process to allocate an attacker-chosen amount of memory (bounded only by available system memory and the read timeout), which can exhaust process memory and crash/OOM the signer or degrade it enough to stall signing operations. This is repeatable on every `get_chunks`/`get_latest_chunks`/`list_chunks`/`put_chunk` RPC call the signer makes to that host. This matches the "Critical - remote crash/unauthenticated DoS from few messages" category since it requires no authentication and can be triggered by a single crafted HTTP response.

### Likelihood Explanation
- No privileged role, secret, or signature is required — the attacker only needs to run/control a host that the signer's `StackerDBSession` connects to (e.g., a malicious replica or a peer the signer is configured to poll).
- The exploit is a single HTTP response with a large body; cost to the attacker is minimal (just holding a socket open long enough to send the payload, within the client's `socket_timeout`, or amortizing over an oversized `Content-Length` claim/actual body).
- Reachable and repeatable on every RPC call the signer issues to that host.

### Recommendation
Enforce a hard cap on the number of bytes read in `run_http_request` (e.g., wrap `sock` in a limited reader, or read incrementally and abort once bytes read exceed a max threshold such as `SIGNERS_STACKERDB_CHUNK_SIZE`/`STACKERDB_MAX_CHUNK_SIZE` plus header/framing overhead) instead of calling `sock.read_to_end` unconditionally. Additionally honor/validate `Content-Length` against the expected chunk-size limit before reading the body, and apply the same cap to the non-chunked path in `decode_http_body` that is currently only enforced for chunked transfer encoding via `MAX_MESSAGE_LEN`.

### Proof of Concept
```rust
// libsigner/src/session.rs (test module) or a new test file
#[test]
fn oversized_stackerdb_response_causes_unbounded_read() {
    use std::io::Write;
    use std::net::TcpListener;
    use std::thread;

    let listener = TcpListener::bind("127.0.0.1:0").unwrap();
    let addr = listener.local_addr().unwrap();

    thread::spawn(move || {
        if let Ok((mut stream, _)) = listener.accept() {
            // consume the request
            let mut tmp = [0u8; 1024];
            let _ = stream.read(&mut tmp);
            // Reply with headers claiming a huge body, then actually stream
            // far more bytes than SIGNERS_STACKERDB_CHUNK_SIZE before the
            // client's read_to_end ever returns.
            stream.write_all(b"HTTP/1.1 200 OK\r\nConnection: close\r\n\r\n").unwrap();
            let oversized = vec![b'A'; 500 * 1024 * 1024]; // 500MB, >> SIGNERS_STACKERDB_CHUNK_SIZE
            let _ = stream.write_all(&oversized);
        }
    });

    let contract_id = QualifiedContractIdentifier::parse(
        "SP000000000000000000002Q6VF78.signer-1-2",
    ).unwrap();
    let mut session = StackerDBSession::new(&addr.to_string(), contract_id, Duration::from_secs(30));
    session.connect_or_reconnect().unwrap();

    // Assertion: memory usage during this call spikes to ~500MB before
    // get_latest_chunks discards the value, demonstrating read_to_end
    // buffers the full oversized body prior to the len() > limit check
    // in session.rs::get_latest_chunks.
    let _ = session.get_latest_chunks(&[0]);
}
```

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
