### Title
Unprivileged dust-transfer stuffing of `MAX_TOKENS_PER_USER` list causes deposit/transfer/liquidation DoS for victim - (File: contracts/DepositToken.sol)

### Summary
CVE-2020-2774 is an availability bug (complete DoS). The reachable Metronome analog is the per-account token-list cap: `Pool` tracks each account's deposit/debt tokens in bounded enumerable sets (`MAX_TOKENS_PER_USER` in `Pool.sol` / `PoolStorage.sol`), and any action that would add a new token to a full set reverts. An unprivileged attacker can fill a victim's `depositTokensOfAccount` set with dust, without the victim's consent, blocking subsequent deposits, transfers, and liquidations that would introduce a new collateral type.

### Finding Description
Two unprivileged vectors let an attacker add entries to a victim's deposit-token set:

1. `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` mints the deposit receipt token to an arbitrary `onBehalfOf_` address — there is no opt-in. An attacker deposits 1 wei of each listed collateral `onBehalfOf_` the victim. [1](#0-0) 
2. `DepositToken.transfer`/`transferFrom` only check the *sender's* locked balance via `_revertIfLocked(_msgSender, amount_)`; the recipient's set is updated unconditionally. Dust transfers of each distinct `DepositToken` to the victim achieve the same fill at lower cost. [2](#0-1) 

Once the victim holds `MAX_TOKENS_PER_USER` distinct deposit tokens, any operation that would register an additional token — `deposit` of a new collateral, inbound `transfer`/`transferFrom`, or `seize` to an account at cap during `Pool.liquidate` — reverts at the set-insert/cap check. 

Note: I was unable to read the exact cap-enforcement lines in `Pool.sol`/`PoolStorage.sol` within the available iterations; the grep index confirms `MAX_TOKENS_PER_USER` and the `depositTokensOfAccount`/`addToDepositTokensOfAccount` machinery exist there, but the precise revert condition and whether removal-on-zero-balance is correctly paired should be confirmed before a PoC is finalized.

### Impact Explanation
Liveness impact, consistent with the bug class: the victim is temporarily unable to (a) deposit any collateral type they do not already hold, (b) receive `DepositToken` transfers of new types, and (c) be a beneficiary of seizure into a capped account. The victim can recover by withdrawing dust balances to zero (which triggers `removeFromDepositTokensOfAccount`), so this is temporary freezing of functionality/funds rather than permanent loss — but it is caused entirely by an unprivileged third party, and the recovery costs the victim gas across up to `MAX_TOKENS_PER_USER` tokens.

### Likelihood Explanation
- Attacker is a plain EOA using only public entry points (`deposit`, `transfer`); no governor/guardian/keeper/oracle involvement.
- Cost is bounded: at most `MAX_TOKENS_PER_USER` dust deposits/transfers of cheapest-unit collateral.
- No modifier stops it: `deposit` is only `whenNotPaused nonReentrant onlyIfDepositTokenExists`, and `transfer` only checks the sender's own lock — neither validates the recipient's consent or remaining list capacity upfront in a way the victim controls.

### Recommendation
- Require opt-in for crediting a *new* token to an account: either revert `deposit` when `onBehalfOf_ != _msgSender()` and the beneficiary is already at the cap, or add an allowlist/acknowledgement step for third-party deposits.
- Do not add a token to `depositTokensOfAccount` below a dust threshold, or allow set insert beyond cap when the amount is trivially small and auto-sweepable.
- Ensure `seize` during `Pool.liquidate` cannot revert solely because the beneficiary's list is full (route seized dust to the liquidator's chosen address or Treasury instead).

### Proof of Concept
Conceptual Hardhat outline (exact revert assertion pending confirmation of the cap-check site):

```ts
// setup: pool with N registered DepositTokens where N == MAX_TOKENS_PER_USER,
// plus one extra listed token (extraDepositToken). victim holds none.
for (const dt of allDepositTokens.slice(0, N)) {
  await dt.connect(attacker).deposit(1n, victim.address); // or transfer dust
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(N);

// victim's own deposit of a new collateral type now reverts
await underlyingExtra.mint(victim.address, amount);
await underlyingExtra.connect(victim).approve(extraDepositToken.address, amount);
await expect(
  extraDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.reverted; // cap reached: cannot add N+1-th token
```

If the cap check lives in `Pool.addToDepositTokensOfAccount`, the same PoC holds with `deposit(1n, victim)` replaced by `transfer(victim, 1n)` calls.
