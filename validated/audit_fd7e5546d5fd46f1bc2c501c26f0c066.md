## Analog Vulnerability Found

### Title
Unvalidated client-supplied `git_object_directory`/`git_alternate_object_directories` fields allow arbitrary filesystem path injection into Git commands - ([File: internal/git/gitcmd/command_factory.go])

### Summary
Every gRPC `Repository` message accepted by Gitaly carries optional `git_object_directory` and `git_alternate_object_directories` fields that are meant to describe a Git object quarantine directory set up during a push (`git-receive-pack(1)`) and looped back through GitLab Rails' access checks. `ExecCommandFactory.newCommand` consumes these fields directly, with no path validation whatsoever, when constructing the environment for every Git invocation against a repository.

### Finding Description
When building the environment for a Git command, the command factory does: [1](#0-0) 

which calls `alternates.Env`: [2](#0-1) 

`alternates.Env` simply does `filepath.Join(repoPath, dir)` for whatever the caller placed in `GetGitObjectDirectory()`/`GetGitAlternateObjectDirectories()`, and exports it as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES`. There is no call to `storage.ValidateRelativePath`, no check that the resolved path stays inside the repository's storage root, and no verification that it corresponds to a legitimate quarantine directory created by Gitaly itself.

This is in stark contrast to the dedicated validation path used elsewhere in the codebase, `Repo.ObjectDirectoryPath`, which explicitly checks that the path is either inside the repository or matches an expected, repo-specific quarantine-directory prefix before use: [3](#0-2) 

The storage-manager middleware is aware that these two fields are trust-sensitive: it explicitly blocks *mutator* RPCs from having them set (`ErrQuarantineConfiguredOnMutator`), but explicitly *permits* accessor RPCs to carry them, assuming they only ever originate from Rails' internal access-check loop-back: [4](#0-3) 

The code comment even acknowledges the exact "trust the caller" risk pattern from the LiFi report — relying on an untrusted/loosely-coupled caller (Rails/API) to only ever send well-formed values, while conceding the check is bypassable and left unaddressed: [5](#0-4) 

However, nothing on the wire enforces that only Rails can populate these fields — they are plain proto fields on `Repository`, settable by any gRPC caller that can reach an accessor RPC taking a `Repository` message. Because `newCommand` (used for essentially every Git invocation, including read-only ones like `TreeEntry`, `LastCommitForPath`, `GetBlob`, etc.) never funnels these fields through `ObjectDirectoryPath`'s validation before injecting them into the process environment, a caller can set `git_alternate_object_directories` to an absolute path or a `../`-relative path that escapes the storage root or points into a sibling repository's real object directory (not a quarantine), and Git will read/traverse objects from that arbitrary directory.

### Impact Explanation
This breaks the storage/repository isolation model that the rest of the codebase carefully enforces (see the `ValidateRelativePath`/quarantine-prefix checks in `paths.go`, `dirs.go`, and `objectpool/link.go`). It allows an ordinary caller of an accessor RPC to make Gitaly read Git objects from any directory the Gitaly process user can access (cross-repository object disclosure), or from files outside any repository entirely, defeating storage-path containment guarantees relied upon elsewhere (object pool isolation, alternates validation, snapshot boundaries).

### Likelihood Explanation
High: it requires no privileged access — any RPC caller that can issue an ordinary accessor RPC (e.g. `TreeEntry`, `GetBlob`, `LastCommitForPath`) with a crafted `Repository.git_alternate_object_directories`/`git_object_directory` field reaches this code path directly, since the middleware only restricts *mutators*, not accessors, and `newCommand` performs no path validation at all before exporting the values as environment variables for `git`.

### Recommendation
Route `repo.GetGitObjectDirectory()` / `repo.GetGitAlternateObjectDirectories()` through the same validation as `Repo.ObjectDirectoryPath` (via `storage.ValidateRelativePath` plus the repo-specific quarantine-prefix check) before constructing the environment in `ExecCommandFactory.newCommand`/`alternates.Env`, for both accessor and mutator RPCs, rather than trusting the caller-supplied strings.

### Proof of Concept
1. As an ordinary client, call any accessor RPC that accepts a `Repository` message (e.g. `TreeEntry`) against a legitimate, accessible repository `A`.
2. Set `Repository.git_alternate_object_directories = ["../../B/objects"]` (or an absolute path) pointing at a sibling repository `B`'s real object directory, or outside the storage root entirely.
3. Because middleware only blocks this for mutator RPCs (`beginTransactionForRepository`), the accessor request proceeds to `s.localRepoFactory.Build(...)` → `ExecCommandFactory.newCommand`, which calls `alternates.Env(repoPath, "", [".../B/objects"])` unchecked, setting `GIT_ALTERNATE_OBJECT_DIRECTORIES` to the traversal path.
4. The subsequent `git cat-file`/`git log` invocation for RPC `A` can now resolve and return objects that physically reside in repository `B` (or elsewhere on disk), even though the caller was only authorized/using RPC on `A`.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
