### Title
Unvalidated attacker-supplied `Attachment.content` from `AttachmentRequest` peer responses is stored via `insert_instantiated_attachment` without hash or size verification against the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When resolving an `AttachmentRequest`, `AttachmentsBatchStateContext::extend_with_attachments` decodes the peer's `GetAttachmentResponse` via `decode_atlas_get_attachment` and inserts the returned `Attachment` into `self.attachments` without ever checking that its content hashes to the `content_hash` that was actually requested. In the `Done` state, `insert_instantiated_attachment` is called unconditionally for every attachment returned, regardless of whether any matching `attachment_instances` were found for its hash, and regardless of `attachments_max_size`/`AtlasConfig` checks (which are only applied elsewhere, e.g. `posttransaction.rs`, not in the download path). Any peer selected as a source for an `AttachmentRequest` can therefore return content up to the HTTP body limit and have it persisted to the Atlas DB on every batch retry cycle.

### Finding Description
The equality that should hold is: *bytes persisted for hash H == bytes committed on-chain for H* (i.e., `attachment.hash() == request.content_hash`, and `content.len() <= atlas_config.attachments_max_size`). Neither is checked in the download path:

- `AttachmentRequest.content_hash` is the hash the node actually needs [1](#0-0) , and the peer is queried via `GET /v2/attachments/{content_hash}` [2](#0-1) .
- The response is decoded purely as JSON/hex with no verification that the returned content actually hashes to the requested `content_hash`: [3](#0-2)  and [4](#0-3) .
- `extend_with_attachments` inserts whatever `Attachment` was decoded into `self.attachments` (a `HashSet<Attachment>`), again with no hash/size check against the request: [5](#0-4) .
- In the `Done` state, for every attachment drained, `insert_instantiated_attachment` is called unconditionally, before or regardless of whether `find_all_attachment_instances(&attachment.hash())` found any actual pending instance for that (self-consistent) hash: [6](#0-5) .
- `insert_instantiated_attachment` itself performs a raw `INSERT OR REPLACE` with no size cap check at all: [7](#0-6) .
- The only place `attachments_max_size` is enforced is `AtlasDB::should_keep_attachment`, which is used by the transaction/mempool ingestion path (`posttransaction.rs`), not by the attachment download/`insert_instantiated_attachment` path.
- Because `resolve_attachment` is invoked with `attachment.hash()` (the hash of the attacker's garbage), not the originally requested `content_hash`, the legitimate pending instance for `content_hash` is never actually resolved and remains in the retry queue — so the batch is re-queued and the malicious peer can repeat the attack on every retry cycle (`bump_retry_count`/`max_attachment_retry_count`), each time inserting up to an HTTP-body-sized blob.

Existing guards that do NOT stop this: the HTTP body size limit (`MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN` in `httpcore.rs`) bounds a single response but is far larger than any real BNS zonefile attachment; there is no Atlas-specific per-attachment cap or hash-equality check anywhere in this reachable code path.

### Impact Explanation
A remote, unprivileged peer that is included as a `source` in an `AttachmentRequest` (which happens automatically for any peer that advertises the relevant attachment in its inventory response — no special privilege needed, just answering `/v2/attachments/inv` and `/v2/attachments/:hash` truthfully-looking) can cause the victim node to write attacker-chosen bytes, up to the HTTP body limit, into its local `attachments` SQLite table via `insert_instantiated_attachment`, repeatedly across retry cycles, disproportionate to the small size actually implied by real BNS commitments. This is a disk/storage-exhaustion issue scoped to the Atlas attachment cache; it does not forge canonical on-chain state (the garbage attachment is never associated with a real `attachment_instance`, since its self-computed hash won't match any pending commitment), but it does allow unbounded, unauthenticated growth of local storage state through legitimate P2P/RPC interaction. This matches the "High" scoped-impact category (attachment/BNS mismatch, storage abuse tied to a commitment that never authorized that content/size).

### Likelihood Explanation
- Precondition: the victim node must have at least one pending/unresolved `attachment_instance` (any real BNS zonefile commitment triggers this) and the attacker's peer must be selected as a `source` for that request — which happens automatically once the attacker answers `/v2/attachments/inv` claiming to have the attachment.
- No secrets, admin roles, or slot ownership required — this is a plain P2P/RPC HTTP responder role that any peer can assume.
- Attacker cost is trivial: run a normal node/peer and answer HTTP GET requests with crafted JSON.
- Repeatable: every batch retry (`bump_retry_count`, up to `max_attachment_retry_count`) re-triggers the same request/response/insert cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), after `decode_atlas_get_attachment`, verify `response.attachment.hash() == request.content_hash` and `response.attachment.content.len() as u32 <= connection_options`/`atlas_config.attachments_max_size` before inserting into `self.attachments`; reject and treat as a failed request (bump `report.bump_failed_requests()`) otherwise. Additionally, in the `Done` branch of `AttachmentsDownloader::run`, only call `insert_instantiated_attachment` when `find_all_attachment_instances` returns a non-empty match, or otherwise gate storage on an explicit size/hash check mirroring `AtlasDB::should_keep_attachment`.

```rust
// stackslib/src/net/atlas/download.rs (test module)
#[test]
fn test_extend_with_attachments_accepts_hash_mismatched_oversized_content() {
    // Build an AttachmentRequest expecting content_hash = H (small legitimate commitment)
    let expected_hash = Hash160([0x11; 20]);
    let request = AttachmentRequest {
        content_hash: expected_hash,
        sources: /* one peer url -> ReliabilityReport */,
        stacks_block_height: 1,
        canonical_stacks_tip_height: None,
    };

    // Craft a malicious GetAttachmentResponse with oversized content whose hash != expected_hash
    let malicious_content = vec![0xAA; MAX_ALLOWED_HTTP_BODY_SIZE]; // near HTTP body cap
    let malicious_attachment = Attachment::new(malicious_content);
    assert_ne!(malicious_attachment.hash(), expected_hash); // proves mismatch

    // Simulate response.decode_atlas_get_attachment() succeeding with this attachment
    let mut results = BatchedRequestsResult::new(HashMap::new());
    results.succeeded.insert(request.clone(), Some(fake_response_with(malicious_attachment.clone())));

    let ctx = AttachmentsBatchStateContext::new(/* batch */, /* peers incl. url */, &ConnectionOptions::default());
    let ctx = ctx.extend_with_attachments(&mut results);

    // Assert: no hash-equality check exists — attacker's mismatched, oversized content is accepted
    assert!(ctx.attachments.contains(&malicious_attachment));

    // Simulate the Done-state insertion path to show it persists unconditionally:
    let mut atlasdb = AtlasDB::connect_memory(AtlasConfig::new(false)).unwrap();
    let instances = atlasdb.find_all_attachment_instances(&malicious_attachment.hash()).unwrap();
    assert!(instances.is_empty()); // no real commitment ever specified this content
    atlasdb.insert_instantiated_attachment(&malicious_attachment).unwrap(); // persists anyway - no guard
    let stored = atlasdb.find_attachment(&malicious_attachment.hash()).unwrap();
    assert!(stored.is_some()); // oversized, uncommitted attacker content is now stored
}
```
This demonstrates the fault: `insert_instantiated_attachment` persists attacker content unconditionally even when `find_all_attachment_instances` proves no legitimate commitment ever referenced that hash/size, and `extend_with_attachments` never checks `attachment.hash() == request.content_hash` before accepting the payload.

```rust
    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
```

```rust
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
```

```rust
    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
```
