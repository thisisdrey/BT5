### Title
Any unprivileged account can create a TRC10/TRX exchange pool with an arbitrarily skewed price via `ExchangeCreateContract`, enabling arbitrage against later traders - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
The reported LooksRare bug lets an unprivileged user permanently fix a wrong ERC20/ERC721 price for a future round by being the first depositor, which later victims are forced to trade against. The same bug class exists in java-tron's built-in bancor-style TRC10 Exchange feature: `ExchangeCreateActuator` lets any single account create a new exchange pool between any two tokens (or TRX) with an arbitrary, attacker-chosen balance ratio, permanently fixing the pool's initial exchange rate with no relation to real-market prices or any minimum-liquidity/oracle safeguard.

### Finding Description
`ExchangeCreateActuator.execute()` creates a new `ExchangeCapsule` and sets its `firstTokenBalance`/`secondTokenBalance` directly from the caller-supplied `ExchangeCreateContract.firstTokenBalance` / `secondTokenBalance` fields: [1](#0-0) [2](#0-1) 

The validation logic only checks that both balances are `> 0`, do not exceed a global `balanceLimit`, and that the creator actually owns that amount of tokens/TRX — there is no check that the implied ratio between the two token balances bears any relation to real market value: [3](#0-2) 

This is architecturally identical to the reported bug class: a single unprivileged transaction fixes a price (here, the exchange-pool token ratio) that other, unrelated participants are later forced to trade against via `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`, whose swap math (`ExchangeCapsule.transaction`, bancor-relay `ExchangeProcessor`/`SafeExchangeProcessor`) derives entirely from the balances set at creation time: [4](#0-3) [5](#0-4) 

Because there is no oracle check, no minimum liquidity lock, and no restriction on who can create a pool or at what ratio, an attacker can:
1. Create an exchange pool pairing TRX (or a liquid TRC10) against a target TRC10 token, depositing a tiny amount of the target token against a large amount of TRX/other token (or vice versa), fixing a wildly mispriced rate.
2. Wait for legitimate users to discover the pool (it is indistinguishable on-chain from a fairly-priced pool created moments after real market conditions) and trade against it via `ExchangeTransactionContract`, or
3. Directly arbitrage it themselves: buy the underpriced token cheaply from the pool, or inject additional liquidity via `ExchangeInjectContract` (whose exchange rate for `anotherTokenQuant` is derived from the attacker-fixed ratio) to extract value from any TRX/asset already routed toward that pool.

### Impact Explanation
Unrelated accounts trading, injecting, or withdrawing against a maliciously mispriced exchange pool can lose real TRX/TRC10 value to the attacker at a rate far from fair market price — this is direct theft of funds from any account that unknowingly interacts with a manipulated pool, matching the "unauthorized... theft of funds" acceptance criterion.

### Likelihood Explanation
`ExchangeCreateContract` is a normal, fee-only user-facing transaction type reachable by any account with sufficient TRX/TRC10 balance to pay `getExchangeCreateFee()` and cover the token balances supplied — no special privilege is required, and the attack requires only a single broadcast transaction plus later interaction (by the attacker or an unsuspecting counterparty) via the standard Exchange APIs.

### Recommendation
Require exchange-pool creation to be permissioned/whitelisted, or enforce a minimum-liquidity/price-deviation check against a trusted price reference, and/or lock a portion of the initial liquidity (Uniswap-style) so a single account cannot unilaterally fix an arbitrary, unchecked initial price ratio for a tradable pool that other accounts will later interact with.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` with `firstTokenId = TRX`, `firstTokenBalance = 1` (1 sun), `secondTokenId = <TargetTRC10>`, `secondTokenBalance = 1_000_000` — this passes all `doValidate()` checks (both `>0`, both under `balanceLimit`, attacker owns the tiny amounts) and creates a pool implying 1,000,000 TargetTRC10 == 1 sun of TRX.
2. `ExchangeCreateActuator.execute()` stores this skewed ratio directly into `ExchangeCapsule`/`ExchangeV2Store` with no sanity check against real market price.
3. Any victim who subsequently calls `ExchangeTransactionContract` to sell TargetTRC10 into this pool (e.g., believing it reflects fair pricing, or routed via tooling that queries exchanges by ID) receives an amount of TRX computed by `ExchangeCapsule.transaction()`/`ExchangeProcessor` off the attacker-fixed balances, resulting in the victim receiving far less value than the real market rate, while the attacker (or anyone front-running) can extract the mispriced side via `ExchangeInjectContract`/`ExchangeTransactionContract` for profit.
