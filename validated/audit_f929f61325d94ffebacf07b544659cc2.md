## Title
Exchange (Bancor-style AMM) inject/withdraw price math relies on instantaneous, single-block reserve ratio with no TWAP/oracle check, enabling spot-price manipulation to mis-price LP-like inject/withdraw operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
java-tron's native `Exchange` contract type implements a Bancor-style two-token AMM. Trading (`ExchangeTransactionContract`) is open to any account and moves the pool's `firstTokenBalance`/`secondTokenBalance` instantaneously through a bonding-curve formula. `ExchangeInjectContract`/`ExchangeWithdrawContract` (restricted to the pool's creator) compute the amount of the paired token to move using only the *current* on-chain reserve ratio at execution time — there is no time-weighted average or oracle-based check, and no protection against the ratio having just been pushed by a large trade in the same or an adjacent transaction. This is structurally the same bug class as the Float Protocol incident: an actuator that mints/redeems value based on a manipulable instantaneous price rather than a robust price reference.

### Finding Description
`ExchangeTransactionActuator.execute` lets any signed transaction swap against a pool via `ExchangeCapsule.transaction`, which directly mutates `firstTokenBalance`/`secondTokenBalance` based on the Bancor formula in `ExchangeProcessor.exchange` [1](#0-0) . This reserve state is the sole "spot price" for the pool — analogous to Uniswap V3's `slot0`.

`ExchangeInjectActuator` (restricted to the exchange creator) computes the counter-asset amount to accept purely from the current instantaneous ratio of `firstTokenBalance`/`secondTokenBalance`, with no staleness/TWAP check: [2](#0-1) 

`ExchangeWithdrawActuator` performs the symmetric calculation when redeeming, again from the live reserve ratio: [3](#0-2) 

Both operations are gated only by a creator-address check [4](#0-3)  and [5](#0-4)  — not by any TWAP/oracle/slippage-vs-external-price validation. Since `ExchangeCreateContract` is permissionless (any account can become the "creator" of a new pair) [6](#0-5) , an attacker can create a pool, then use ordinary `ExchangeTransactionContract` trades (from any account, including their own) to push the reserve ratio away from a fair/external market rate, and immediately inject or withdraw at the skewed ratio to extract more value than deposited, before trading back to restore the ratio. This mirrors the Float Protocol root cause: a critical value-transfer function that trusts a freshly-manipulable on-chain price with no TWAP or slippage-vs-oracle protection.

### Impact Explanation
An attacker (as pool creator) can extract real TRX/TRC10 value from a pool they control through a sequence of ordinary, permissionless transactions (large swap → inject/withdraw → reverse swap), profiting at the expense of whichever token balances remain in the pool or other liquidity that later interacts with it. This is unauthorized value extraction / mispriced settlement, matching the "unbacked balance / theft of funds" impact class, though scoped to whatever the specific exchange pool holds.

### Likelihood Explanation
All required operations — pool creation, trading, inject, withdraw — are reachable via a single signed transaction each, from an unprivileged account, using only public `ExchangeCreateContract`, `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` messages. No special privilege beyond being the pool's own creator (self-assigned at creation) is required.

### Recommendation
Introduce a TWAP or minimum-elapsed-time check before allowing `ExchangeInjectContract`/`ExchangeWithdrawContract` to use the current reserve ratio, or require the ratio to be validated against a longer observation window (multiple blocks) rather than the instantaneous post-trade balances. Alternatively, apply a maximum allowed deviation between the ratio used for inject/withdraw and a recent moving-average ratio, similar to slippage bounds already present in `ExchangeTransactionContract`'s `expected` field.

### Proof of Concept
1. Attacker account A calls `ExchangeCreateContract` to create a pool with tokens X/Y, becoming `creatorAddress` [7](#0-6) .
2. Attacker (or a colluding account) submits a large `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` far from the pool's fair ratio via `ExchangeCapsule.transaction` [1](#0-0) .
3. Attacker A immediately submits `ExchangeInjectContract`, whose `anotherTokenQuant` is computed from the now-skewed ratio [2](#0-1) , letting A acquire a disproportionate share of the pool cheaply.
4. Attacker reverses the initial swap (or lets normal trading restore the ratio) and then issues `ExchangeWithdrawContract`, again priced off the live ratio [3](#0-2) , redeeming more value than originally injected.
