### Title
Uncaught `IndexOutOfBoundsException` in permission-operation bitmap check crashes transaction validation - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
The Samba CVE (ALPINE-CVE-2021-20254) is an out-of-bounds array read caused by trusting an unvalidated index (from a cache/lookup) when indexing a fixed-size mapping array, which then feeds a security decision (group/permission membership). The analogous pattern in java-tron is `TransactionUtil.checkPermissionOperations()`, which indexes a fixed 32-byte `operations` bitmap using an attacker-controlled index derived from the transaction's contract type value, without bounds checking.

### Finding Description
`checkPermissionOperations` computes a byte offset into a permission's 32-byte `operations` bitmap using `contract.getTypeValue()`: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException("operations size must be 32");
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`Contract.type` is a proto3 `enum ContractType`, but `getTypeValue()` returns the raw wire-encoded int32, which is fully attacker-controlled and not limited to the declared enum range (proto3 preserves out-of-range enum values via the value accessor). If `contractType` is large (or negative), `contractType / 8` can be far outside `[0, 31]`, and `ByteString.byteAt(index)` throws an unguarded `IndexOutOfBoundsException`.

This function is reached from `TransactionCapsule.checkPermission()` [2](#0-1)  which is called from `validateSignature()` whenever `permissionId != 0`: [3](#0-2) 

Critically, for an account that does not yet exist on-chain, `permissionId == 2` triggers the fallback `createDefaultActivePermission()`, which any address can obtain without prior multisig setup: [4](#0-3) 

`validatePubSignature()`, which is the entry point invoked during transaction broadcast/validation, only catches `SignatureException | PermissionException | SignatureFormatException` — not `IndexOutOfBoundsException`: [5](#0-4) 

So a crafted `IndexOutOfBoundsException` from `checkPermissionOperations` is not caught here and propagates as an unchecked `RuntimeException`.

### Impact Explanation
Any unprivileged party can broadcast a transaction from a not-yet-activated address, set `Contract.permission_id = 2` (the always-available default active permission), and set the raw contract type value (via the wire-level int, bypassing enum validation) to an out-of-range value. This makes `checkPermissionOperations` throw `IndexOutOfBoundsException` outside of the expected `PermissionException`/`SignatureException` catch clauses in `validatePubSignature`. Depending on where this uncaught exception is caught upstream (broadcast path in `Wallet` vs. deeper in block application/`Manager`), this can manifest as an uncaught exception during transaction processing — a potential node crash/DoS or service disruption for the affected code path. This matches the report's threat class of an out-of-bounds read on a fixed-size mapping triggered via an unvalidated index reaching security-relevant logic.

### Likelihood Explanation
The trigger requires only crafting and broadcasting a single signed transaction with `permission_id = 2` and an out-of-range raw enum value for the contract type — both fields are directly attacker-controlled at the protobuf wire level, and the default active permission path (`createDefaultActivePermission`) requires no prior on-chain setup. This is reachable from the standard transaction broadcast API used by any unprivileged client.

### Recommendation
Validate `contractType` bounds (e.g., `contractType >= 0 && contractType < operations.size() * 8`) before indexing into `operations` in `checkPermissionOperations`, returning `false`/throwing `PermissionException` for out-of-range values, and ensure `validatePubSignature` and related callers (`getTransactionSignWeight`, `getTransactionApprovedList`) catch a broader exception type (or the specific bounds-check exception) around permission/signature validation so malformed input cannot escape as an uncaught runtime exception.

### Proof of Concept
1. Choose an address `A` that has never been activated on-chain (no `AccountCapsule` in `AccountStore`).
2. Construct a `Transaction` whose `raw.contract[0]` has:
   - `type` field encoded on the wire as an out-of-range int (e.g., 100000) rather than a valid `ContractType` enum value — achievable by directly crafting the serialized protobuf bytes since the field is a varint at the wire level.
   - `Permission_id = 2`.
   - `provider`/`owner_address` referencing `A`.
3. Sign the transaction with `A`'s private key (satisfies `createDefaultActivePermission`'s threshold of 1).
4. Broadcast the transaction via the node's broadcast API.
5. During `TransactionCapsule.validateSignature()` → `checkPermission()` → `checkPermissionOperations()`, `contract.getTypeValue()` returns 100000, `operations.byteAt(100000/8)` is called on a 32-byte `ByteString`, throwing `IndexOutOfBoundsException`, which is not caught by `validatePubSignature`'s catch clauses.

Note: I was not able to fully trace, within the available indexing, the exact top-level exception handler (in `Manager`/block-application code) that would ultimately catch or fail to catch this propagated `IndexOutOfBoundsException` at the broadcast/block-processing boundary — this would need to be confirmed in a full source checkout (e.g., via a Devin session) to determine whether the failure mode is a rejected transaction, an HTTP 500, or a node-level crash.

      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));

        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

      throws ValidateSignatureException {

      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
