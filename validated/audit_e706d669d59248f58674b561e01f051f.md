### Title
Unprivileged attacker fills a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER` via dust transfers and dust issuances, permanently reverting all first-time deposits, borrows, transfers, and liquidations that would add a new token to the victim's position - ([File: contracts/DepositToken.sol])

### Summary
Analogous to the Passenger bug (an unprivileged request that poisons shared state and turns subsequent legitimate requests into persistent reverts), `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` the first time any recipient touches a deposit token, and `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the per-account list reaches `MAX_TOKENS_PER_USER`. An EOA can transfer 1 wei of every listed `DepositToken` to a victim (and, if `DebtToken.issue` mints on behalf, issue dust debt) until the victim's shared list is full, after which every operation that would insert a new token reverts.

### Finding Description [1](#0-0) 
In `contracts/DepositToken.sol:498-526`, `_transfer` (reachable from public `transfer`, `transferFrom`, `seize`, and the fee path in `_withdraw`) calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero. The same happens in `_mint` at `contracts/DepositToken.sol:485-488`, so `deposit(amount_, onBehalfOf_=victim)` also inserts into the victim's list (`contracts/DepositToken.sol:234`). On the Pool side, `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (`contracts/Pool.sol`, confirmed by `test/Pool.test.ts:1491-1521`) add to a `MappedEnumerableSet` capped by `MAX_TOKENS_PER_USER` and revert with `UserReachedMaxTokens` when full — the test itself shows the cap is shared across both lists (max/2 deposit + max/2 debt tokens saturates it). Because `_transfer`/`_mint` are called inside every deposit, withdraw fee path, seize/liquidation, and user transfer, once the victim's list is full:

- `DepositToken.deposit(amount, onBehalfOf=victim)` for any collateral the victim doesn't yet hold reverts.
- `transfer`/`transferFrom` of any deposit token the victim doesn't hold reverts.
- `DebtToken.issue`/mint flows that would add a new debt token revert (`contracts/DebtToken.sol` calls `pool.addToDebtTokensOfAccount` on first issuance).
- `Pool.liquidate` → `depositToken_.seize(account_, _msgSender, ...)` (`contracts/Pool.sol:589-593`) reverts for a liquidator whose own list is saturated — an attacker can saturate their own account is irrelevant, but saturating a *known active liquidator/MEV bot* account degrades liquidation liveness.

Recovery exists but is costly and asymmetric: the victim must burn a dust balance to zero (`withdraw`) to free a slot, while the attacker only paid dust; for debt tokens the victim may be unable to repay a dust issuance at all if `debtFloorInUsd` (`contracts/Pool.sol:571-578`) reverts `RemainingDebtIsLowerThanTheFloor` on small debts, making the debt slot permanently occupied and the block irreversible without governance intervention.

### Impact Explanation
Liveness/DoS on legitimate protocol operations, matching the "reachable denial of service" impact class: the victim is denied deposits of new collateral types, cannot open debt positions in new synthetics, and cannot receive new deposit tokens; if dust debt is issued below `debtFloorInUsd`, the blocked slot can become effectively permanent, freezing the victim's ability to expand or refinance positions indefinitely. This is not an unbounded-loop gas issue — it is a hard `UserReachedMaxTokens` revert on a bounded list, triggered by state the attacker wrote against the victim.

### Likelihood Explanation
Fully unprivileged: `transfer`/`deposit`/`issue` are public entry points; `SynthContext._msgSender` does not restrict recipients; no pause flag, health check, or cap protects the *recipient's* list — the cap check happens at insertion, not per-sender. Cost to the attacker is dust amounts of each listed deposit token (and any minimum issue amounts for debt tokens). Uncertainty: the exact `MAX_TOKENS_PER_USER` value and whether `DebtToken.issue` allows arbitrary `onBehalfOf_` without a debt floor at issuance were not fully verified from the indexed snippets; the shared-cap behavior itself is confirmed by `test/Pool.test.ts:1491-1521`.

### Recommendation
Only track tokens in the per-account list on credit events that the account actually wants (e.g., only on `deposit`/`issue`, not on `transfer`/`seize` receipt), or skip `addToDepositTokensOfAccount` in `_transfer` when the recipient is not the transaction initiator's own position. Alternatively, raise/remove the `MAX_TOKENS_PER_USER` cap or make `addTo*` return instead of revert when full and fall back to scanning `depositTokens`/`debtTokens` in `debtPositionOf`. Ensure `DebtToken.issue` enforces `debtFloorInUsd` at issuance so dust debts cannot occupy slots.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {Pool} from "../contracts/Pool.sol";

// Fork an in-scope deployment (e.g. mainnet Pool + listed DepositTokens).
contract MaxTokensGriefingTest is Test {
    Pool pool = Pool(POOL_ADDR);
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    function test_griefVictimTokenList() public {
        uint256 max = pool.MAX_TOKENS_PER_USER();
        address[] memory dt = pool.getDepositTokens(); // all listed deposit tokens

        // Attacker deposits dust into every listed collateral and transfers
        // 1 wei to the victim, plus issues dust debt where possible,
        // until victim's combined list hits MAX_TOKENS_PER_USER.
        for (uint256 i; i < dt.length && pool.getDepositTokensOfAccount(victim).length < max; ++i) {
            DepositToken d = DepositToken(dt[i]);
            deal(address(d.underlying()), attacker, 2);
            vm.startPrank(attacker);
            d.underlying().approve(address(d), 2);
            d.deposit(2, attacker);          // mint dust msdTOKEN
            d.transfer(victim, 1);           // -> addToDepositTokensOfAccount(victim)
            vm.stopPrank();
        }

        // Victim can no longer receive a first-time deposit of any NEW token:
        vm.expectRevert(); // UserReachedMaxTokens
        vm.prank(attacker);
        DepositToken(dt[0]).transfer(victim, 1); // any token not yet held reverts

        // deposit(onBehalfOf = victim) on a new collateral reverts inside _mint.
        vm.expectRevert();
        DepositToken(dt[0]).deposit(1, victim);
    }
}
```

Run on a mainnet/Base fork of the deployed `Pool`; the second and third calls revert with `UserReachedMaxTokens` because `depositTokensOfAccount`/`debtTokensOfAccount` is saturated by the attacker's dust transfers.
