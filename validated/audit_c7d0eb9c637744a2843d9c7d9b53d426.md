### Title
Front-running public pull-oracle price updates to mint synths at stale prices and leave bad debt - ([File: contracts/Pool.sol])

### Summary
The external report's bug class is *observing a pending outcome-reveal transaction and front-running an exit/claim before the protocol state reflects the revealed information*. Metronome has no VRF, but it has a direct analog: the protocol prices all collateral, debt, and swaps through `IMasterOracle`, and on deployments that use pull oracles (Pyth on mainnet, Redstone on Hemi — see `test/E2E.mainnet.test.ts:1057-1073` and `test/E2E.hemi.pullOracle.test.ts:116-121`), the price-update transaction (`Pyth.updatePriceFeeds`, `pullPriceProvider.updatePrice`) is a public, permissionless mempool transaction. An attacker who sees a pending price update that will lower a collateral's USD value can front-run it with `DebtToken.issue` / `Pool.swap` / `DepositToken.withdraw`, all of which evaluate health at the stale (pre-update) price. When the update lands, the attacker's position is underwater beyond `maxLiquidable`/collateral coverage, minted synth value was already extracted, and the residual is protocol bad debt.

### Finding Description
- `Pool.debtPositionOf` computes health purely from `masterOracle().quoteTokenToUsd(...)` over the user's deposit and debt token balances (`contracts/Pool.sol:248-266`). `depositOf` applies the collateral factor to oracle-quoted value (`contracts/Pool.sol:274-288`). There is no staleness-window guard beyond the oracle's own expiry, no lock between "price becomes stale/queued for update" and protocol state-changing calls, and no two-block or commit scheme.
- `DebtToken.issue` lets any user mint synths up to `issuableInUsd` computed at the current oracle price. `Pool.swap` converts synth A→B at `masterOracle().quote(...)` (mint/burn at oracle rates, only `swapFees` skimmed). `DepositToken.withdraw` permits withdrawal of `unlockedBalanceOf` while the post-withdraw position is healthy at the current oracle price.
- Attack trace (unprivileged EOA):
  1. Deposit collateral C (e.g., WETH via `msdWETH.deposit`), `DebtToken.issue` synths up to the limit.
  2. Observe a pending `Pyth.updatePriceFeeds` (or Redstone pull `updatePrice`) tx that cuts C's price.
  3. Front-run it: `issue` additional synths to the stale-price limit and/or `Pool.swap` existing synths into the synth whose price is about to fall (or away from one about to rise), and `withdraw` any collateral still unlocked at stale valuation.
  4. The oracle update lands in the same block right after. Position is now deeply unhealthy; `Pool.liquidate` (`contracts/Pool.sol:581-595`) can only seize `depositToken` balance, capped by `maxLiquidable` (`0.5e18`, `contracts/Pool.sol:181`) per call and by total collateral. Minted synths already extracted exceed post-update collateral backing → bad debt.

### Impact Explanation
Direct value extraction at stale prices: the attacker walks away with synthetic assets whose issuance was collateralized at a price the pending mempool transaction was about to invalidate. The protocol is left with an undercollateralized debt position — liquidation recovers at most the remaining collateral, so the difference is socialized as protocol insolvency / loss for other synth holders and depositors. This mirrors the Infiltration report: a publicly observable pending state-transition (VRF fulfill there; oracle update here) is front-run to exit before the loss is priced in.

### Likelihood Explanation
- Pull-oracle updates are by design public and mempool-visible before inclusion (Pyth `updatePriceFeeds`, Redstone `updatePrice` are permissionless — the tests themselves call them directly and via `Operator.execute` with arbitrary calldata, confirming no access control on the update path).
- No modifier blocks this: `swap`/`issue`/`withdraw` only check pause/shutdown flags, caps, and health at the *current* oracle read. `SynthContext`/`Operator` batching actually helps the attacker (oracle update + action can be atomically ordered).
- Constraints: profit is limited by collateral factor, swap fees, `maxLiquidable` pacing, and requires a large enough pending price move; on Chainlink-push deployments the window is smaller since updates come from the operator's tx (still front-runnable on some chains, but weaker).

### Recommendation
- Add a staleness/deviation guard: reject issuance/swaps/withdrawals when the oracle's publish time is older than a short threshold, or when a queued update deviates beyond a bound (Chainlink-style "freshness per action," not just expiry).
- Alternatively require oracle freshness as a precondition inside `issue`/`withdraw`/`swap` (e.g., force a same-tx `updatePriceFeeds` pull through `Operator`) so no actor can act on a stale price while a newer price is already public.

### Proof of Concept
Foundry fork sketch (mirrors `test/foundry/poc/TBY.t.sol` setup which already forks mainnet against the real `Pool`/`MasterOracle`):

```solidity
// 1. Attacker deposits WETH into msdWETH and issues msUSD up to the limit.
weth.approve(address(msdWETH), amount);
msdWETH.deposit(amount, attacker);
msUsdDebt.issue(issuableNow, attacker); // at stale ETH price P0

// 2. Attacker sees pending Pyth.updatePriceFeeds dropping ETH to P1 < P0.
//    Front-run: issue the remaining issuableInUsd computed at P0 and/or
//    swap msUSD -> msETH at stale quote.
pool.swap(address(msUSD), address(msETH), msUsdBalance);

// 3. Include the oracle update (attacker can even call it themselves).
pyth.updatePriceFeeds{value: fee}(updateData); // ETH now priced at P1

// 4. Assert: position is underwater beyond collateral recovery.
(bool healthy, uint256 depUsd, uint256 debtUsd,,) = pool.debtPositionOf(attacker);
assert(!healthy && debtUsd > depUsd); // bad debt; liquidate() seizes only depUsd-worth
```

Invariant broken: solvency — debt issued is bounded by oracle-priced collateral only at call time, so a front-run between "price publicly known" and "price applied on-chain" mints unbacked synths. Uncertainty: exact profitability depends on deployed collateral factors, swap fees, and oracle deviation thresholds on each chain; the core stale-window (no freshness check inside state-changing calls) is confirmed by `debtPositionOf`/`depositOf` reading `masterOracle` directly with no freshness precondition.
