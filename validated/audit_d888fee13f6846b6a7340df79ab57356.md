Audit Report

## Title
Reentrant `instantiate` targeting the same deterministic address bypasses the `DuplicateContract` collision guard in legacy `pallet-contracts`, unlike the fixed equivalent in `pallet-revive` - (File: `substrate/frame/contracts/src/exec.rs`, `substrate/frame/contracts/src/storage.rs`)

## Finding Description
`pallet-contracts` derives a new contract's address deterministically and nonce-independently, exactly like CREATE2: `DefaultAddressGenerator::contract_address` hashes `deploying_address ++ code_hash ++ input_data ++ salt` with no dependency on the account nonce [1](#0-0) . The collision guard against re-instantiation lives in `ContractInfo::new`, which only checks `ContractInfoOf::<T>::contains_key(account)` in storage [2](#0-1) .

Crucially, `Stack::push_frame` explicitly skips writing `ContractInfoOf` for the currently executing frame when it is a `Constructor`: the persist-on-push logic only inserts storage `if let (CachedContract::Cached(contract), ExportedFunction::Call) = (&frame.contract_info, frame.entry_point)`, with the comment "We do not store on instantiate because we do not allow to call into a contract from its own constructor" [3](#0-2) . This means while a `Constructor` frame for address `X` is on the stack, `ContractInfoOf::<T>::contains_key(X)` remains `false` in storage.

`new_frame` (used both for the first frame and for every `push_frame` call) derives `account_id` via `Contracts::<T>::contract_address(&sender, code_hash, input_data, salt)` and then calls `ContractInfo::new(&account_id, nonce, code_hash)`, which performs only the storage-based `contains_key` check [4](#0-3) . If a `Constructor` for account `X` re-enters (directly or via a call chain) `Pallet::instantiate`/`Ext::instantiate` with the identical `sender`, `code_hash`, `input_data`, and `salt`, the derived address is again `X`, and the `contains_key(X)` check in `ContractInfo::new` still returns `false` because the outer frame's `ContractInfo` was never persisted mid-construction. `push_frame` contains no equivalent to `pallet-revive`'s in-stack `Constructor`/`account_id` collision check [5](#0-4) , whereas `pallet-revive`'s `push_frame` explicitly walks `self.frames()` looking for an existing `Constructor` frame with the same `account_id` and rejects with `DuplicateContract` before this exact race can be exploited [6](#0-5) . The only reentrancy guards present in `pallet-contracts::exec.rs` (`is_recursive`/`allows_reentry`) govern `Call`-type reentry into already-materialized contracts, not the constructor-collision path [7](#0-6) . As a result, two `Constructor` frames for the same account `X` (with different `nonce` values feeding into different `trie_id`s, since address derivation is nonce-independent while `trie_id` derivation is not) can run concurrently on the call stack, and whichever's `ContractInfo` is persisted last at frame-pop silently overwrites/orphans the other's state, leaking the other's storage deposit and consumer/code refcount.

## Impact Explanation
This is a genuine reentrancy/duplicate-settlement class bug: a single contract account `X` can end up with two competing `ContractInfo` records (each with its own `trie_id`), one of which becomes permanently orphaned when the surviving frame's `ContractInfo` is written to `ContractInfoOf` at teardown. This matches the "permanent user-fund lock" impact criterion — the orphaned trie's storage deposit becomes stranded and the code reference count for the orphaned constructor's code hash is never properly decremented, corrupting the code-reference accounting used elsewhere in the pallet. This mirrors precisely the flaw that was identified and patched in `pallet-revive` via `prdoc/pr_12645.prdoc`, confirming the vulnerability class is real and previously acknowledged as security-relevant by the codebase's own maintainers, just left unfixed in the still-shipped legacy `pallet-contracts`.

## Likelihood Explanation
The attack requires only an unprivileged user to deploy an ordinary contract whose constructor re-enters `pallet_contracts::Pallet::instantiate` (or the `seal_instantiate` host function) with the same `code_hash`+`salt`+`input_data` as the outer, in-progress instantiation. No governance, validator, or off-chain privilege is needed — the primitive is identical to the one `pallet-revive`'s regression test `reentrant_instantiate_at_same_address_is_rejected` was written to guard against. `pallet-contracts` is still compiled and available in this repository and has received no equivalent fix, so the same attacker-controlled contract pattern applies directly.

## Recommendation
Port the `pallet-revive` fix into `pallet-contracts::exec.rs`: before pushing a new `Constructor` frame in `push_frame`/`new_frame`, walk `self.frames()` for an existing `Constructor` frame with a matching `account_id` and reject with `Error::<T>::DuplicateContract` if found, mirroring `substrate/frame/revive/src/exec.rs` lines 1238-1246.

## Proof of Concept
1. Deploy contract `A` with `code_hash = H`, `salt = S`, `input_data = D` from sender `S0`; `Contracts::<T>::contract_address(S0, H, D, S)` deterministically derives address `X` (nonce-independent, per `substrate/frame/contracts/src/address.rs`).
2. In `A`'s constructor (running as the `Constructor` frame for `X`), before returning, call back into `Pallet::instantiate` (or `seal_instantiate`) with the identical `sender = S0`, `code_hash = H`, `salt = S`, `input_data = D`.
3. Because `push_frame` never inserted `ContractInfoOf::<T>` for `X` while its `Constructor` frame is open (`exec.rs` lines 922-931), `ContractInfo::new`'s `contains_key(X)` check in `storage.rs` returns `false`, and a second `Constructor` frame for account `X` is pushed and executed alongside the first.
4. Both frames' `ContractInfo` (with different `trie_id`s due to differing `nonce`) race to be persisted at frame-pop; the losing frame's storage deposit and code refcount are orphaned. No test analogous to `pallet-revive`'s `reentrant_instantiate_at_same_address_is_rejected` exists for `pallet-contracts`, confirming the gap.

	/// Formula: `hash("contract_addr_v1" ++ deploying_address ++ code_hash ++ input_data ++ salt)`
	fn contract_address(
		deploying_address: &T::AccountId,
		code_hash: &CodeHash<T>,
		input_data: &[u8],
		salt: &[u8],

			.using_encoded(T::Hashing::hash);
		Decode::decode(&mut TrailingZeroInput::new(entropy.as_ref()))
			.expect("infinite length input; no invalid inputs for type; qed")
	}

	/// Create a subsequent nested frame.
	fn push_frame(
		&mut self,
		frame_args: FrameArgs<T, E>,
		value_transferred: BalanceOf<T>,
		gas_limit: Weight,
		deposit_limit: BalanceOf<T>,
		read_only: bool,
	) -> Result<E, ExecError> {
		if self.frames.len() == T::CallStack::size() {
			return Err(Error::<T>::MaxCallDepthReached.into());
		}

		// We need to make sure that changes made to the contract info are not discarded.
		// See the `in_memory_changes_not_discarded` test for more information.
		// We do not store on instantiate because we do not allow to call into a contract
		// from its own constructor.
		let frame = self.top_frame();
		if let (CachedContract::Cached(contract), ExportedFunction::Call) =
			(&frame.contract_info, frame.entry_point)
		{
			<ContractInfoOf<T>>::insert(frame.account_id.clone(), contract.clone());
		}

		let frame = top_frame_mut!(self);
		let nested_gas = &mut frame.nested_gas;
		let nested_storage = &mut frame.nested_storage;
		let (frame, executable, _) = Self::new_frame(
			frame_args,
			value_transferred,
			nested_gas,
			gas_limit,
			nested_storage,
			deposit_limit,
			self.determinism,
			read_only,
		)?;
		self.frames.push(frame);
		Ok(executable)
	}
