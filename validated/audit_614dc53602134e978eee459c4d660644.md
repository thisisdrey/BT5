### Title
Unsafe raw-double resource-usage math in `UnDelegateResourceActuator.execute()` allows an attacker to under-charge bandwidth/energy usage and free resource capacity from a peer account - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.execute()` computes the amount of bandwidth/energy usage to transfer back from a delegation receiver using raw, unchecked `double`/`long` arithmetic instead of the "hardened" safe-math (`BigInteger`/`*Exact`) helpers that the rest of the resource-accounting code (`ResourceProcessor`, `EnergyProcessor`, `BandwidthProcessor`) uses when `allowHardenResourceCalculation`/`allowHardenExchangeCalculation` is enabled. The inputs to this computation (`unDelegateBalance`, receiver's live usage/frozen counters) are attacker-influenced through a plain signed `UnDelegateResourceContract` transaction, matching the reported bug class of "unvalidated params with unsafe math."

### Finding Description
In `execute()`:
```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
``` [1](#0-0) 

and symmetrically for `ENERGY`: [2](#0-1) 

This is unlike the parallel `RepositoryImpl`/`ResourceProcessor`/`EnergyProcessor` code paths in the same codebase, which explicitly guard the same class of computation with a "hardened" BigInteger implementation to avoid precision loss and silent overflow, e.g.: [3](#0-2) [4](#0-3) 
The presence of these `hardenCalculation()`/`disableJavaLangMath()` branches elsewhere shows the project is aware that this exact pattern (`long * ((double) a / b)`) is unsafe — silently losing precision and able to overflow/wrap when `unDelegateBalance`, `getNetUsage()`, or `getAllFrozenBalanceForBandwidth()` are large (TRX amounts are `long` values that can be user-inflated up to `Long.MAX_VALUE` scale by freezing/delegating large TRX amounts) — yet `UnDelegateResourceActuator` (and its TVM-precompile counterpart `UnDelegateResourceProcessor`) still perform the computation with plain `double`/`long` math and no `*Exact` calls or `ArithmeticException` handling.

`unDelegateBalance` comes directly from the transaction (`unDelegateResourceContract.getBalance()`), and `validate()` only bounds it against the aggregate delegated balance (`delegateBalance < unDelegateBalance` check), not against the specific arithmetic performed in `execute()`: [5](#0-4) 
There is no re-validation of `transferUsage` before it is subtracted from the receiver's live `NetUsage`/`EnergyUsage` counters:
```java
long newNetUsage = receiverCapsule.getNetUsage() - transferUsage;
receiverCapsule.setNetUsage(newNetUsage);
``` [6](#0-5) 
Because double-precision division/multiplication can round differently (and, for sufficiently large frozen/usage values, truncate/overflow silently as a `long` cast of a `double` that exceeds `Long.MAX_VALUE` clamps rather than throwing), an attacker who controls `unDelegateBalance` (bounded only loosely by the delegated-balance check) and who controls timing of their own resource usage on the receiver side (self-delegation loops, or via a colluding/contract-suicide receiver as explicitly called out in the surrounding code comments — "A TVM contract suicide, re-create will produce this situation") can cause `transferUsage`/`unDelegateMaxUsage` to be computed incorrectly, resulting in the owner's or receiver's bandwidth/energy usage window being desynchronized from the actual frozen collateral backing it.

### Impact Explanation
Bandwidth/Energy usage counters directly gate how much free TVM execution (`Energy`) and free transaction throughput (`Bandwidth`) an account can consume without paying TRX. An incorrect/manipulable `transferUsage` value lets an attacker desynchronize the usage-to-collateral ratio for the delegation pair, effectively obtaining unbacked resource capacity (spending TVM energy / bandwidth without the collateral that is supposed to back it) or corrupting the receiver's accounting window (`newWindowSize`) used by later resource recovery calculations elsewhere in `ResourceProcessor`. This falls into the "unbacked balance" / resource-accounting integrity category referenced in the validation rules, since energy/bandwidth is the on-chain analog of a spendable resource balance.

### Likelihood Explanation
The `UnDelegateResourceContract` is a standard broadcastable transaction type reachable by any account holder once resource delegation (`supportDR`/`supportUnfreezeDelay`) is enabled on the network — this is production functionality on java-tron mainnet/testnets today. No special privilege is required beyond having previously delegated/received resources, which an attacker fully controls by delegating to their own second address. Triggering the specific numeric edge cases (very large delegated/frozen balances or usage right at recovery boundaries) requires some setup but is within reach of a single account without validator/witness cooperation.

### Recommendation
Replace the raw `double`/`long` arithmetic in `UnDelegateResourceActuator.execute()` (and the identical pattern in `UnDelegateResourceProcessor.execute()` and `DelegateResourceActuator.validate()`) with the same hardened `BigInteger`-based, exact-math approach already used in `ResourceProcessor`/`EnergyProcessor`/`RepositoryImpl` (`hardenCalculation()` / `disableJavaLangMath()` gated `BigInteger.multiply().divide().longValueExact()`), so that overflow is detected via `ArithmeticException` rather than silently truncated/mis-rounded, and so `transferUsage`/`unDelegateMaxUsage` are always computed consistently regardless of the magnitude of `unDelegateBalance` or the receiver's usage/frozen values.

### Proof of Concept
Not independently executable from static analysis alone — reproducing the numeric divergence requires driving `unDelegateBalance`, `receiverCapsule.getNetUsage()`/`getEnergyUsage()`, and `receiverCapsule.getAllFrozenBalanceForBandwidth()`/`getAllFrozenBalanceForEnergy()` to values where `double` precision loss (values > 2^53) or the plain `(long)` cast of an out-of-range `double` diverges from the exact `BigInteger` result used elsewhere in the codebase (the project's own `CalculateGlobalLimitHardenTest`/`RepositoryImplHardenTest` unit tests, e.g. `testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss` and `testUsageToBalanceOverflowDetectedWithHardening`, demonstrate exactly this divergence pattern for the sibling code paths that *do* have the hardening applied): [7](#0-6) [8](#0-7)
