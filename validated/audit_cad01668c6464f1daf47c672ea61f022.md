### Title
Wallet Contract `has_in_flight_tx` flag can be permanently stuck to `true`, freezing the account - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract` (used to give ETH-implicit accounts a NEAR-native wallet) uses a boolean flag `has_in_flight_tx` to guarantee that only one Ethereum-style transaction is "in flight" (i.e. has an outstanding cross-contract promise) at a time, preserving nonce ordering. `rlp_execute` sets the flag to `true` and only the terminal callbacks (`rlp_execute_callback`, `ban_relayer`) reset it back to `false`. This is structurally the same pattern flagged in the external report: a "callback flag" is set when an operation is registered, and nothing guarantees that the corresponding callback actually runs to completion and clears it. [1](#0-0) 

### Finding Description
`rlp_execute` refuses to start a new transaction whenever `has_in_flight_tx` is `true`, and every code path that returns a `Promise` sets it to `true` before returning: [2](#0-1) 

The flag is only cleared inside the private callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), as the *first statement* of each function: [3](#0-2) [4](#0-3) 

On NEAR, a `FunctionCall` action's state changes are only committed if the WASM execution returns successfully; if the callback function panics or aborts for *any* reason (host error, gas exceeded, guest panic, etc.) partway through, its entire receipt fails and **all state changes made during that call — including the earlier `self.has_in_flight_tx = false;` statement — are rolled back** by `TrieUpdate`. This atomicity/rollback behavior is explicitly documented: [5](#0-4) [6](#0-5) 

The terminal callback `rlp_execute_callback` is always dispatched with a **fixed, static gas budget** `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, independent of the size of the data it needs to process: [7](#0-6) [8](#0-7) 

Inside `rlp_execute_callback`, the very first thing after clearing the flag is to read the result of the *previous* cross-contract call via `env::promise_result(0)`: [9](#0-8) 

For the default/`ERC20Transfer`/base-token paths, the preceding promise calls a `target` account that is **fully attacker/user controlled** (the `target` argument of `rlp_execute`, or the NEP-141 token contract). A malicious or compromised target contract can return an arbitrarily large `SuccessValue` (up to the protocol's max return-value size) from its method call. Copying/decoding that large blob inside `rlp_execute_callback` costs gas proportional to its size; because the callback's prepaid gas is the small fixed constant (5 Tgas) rather than being sized to the potential payload, a sufficiently large returned value can exhaust the callback's gas budget, causing a `GasExceeded`/`HostError` abort of the callback receipt. Because of NEAR's per-receipt atomicity, this abort reverts the `has_in_flight_tx = false` write that had already executed at the top of the function, leaving the flag stuck at `true` forever.

Once stuck, `rlp_execute` will unconditionally short-circuit on every future call with `"transaction already in progress, please try again later"` and never create a new promise, so the flag can never be cleared through the normal flow: [10](#0-9) 

No admin/reset method exists elsewhere in the contract to unstick this flag (the only writers found are the four methods above, all of which require a promise callback to run to completion — which is exactly the precondition that fails).

This is a direct analog of the BaseVault.sol issue: an operation sets a "callback expected" flag before dispatch, but nothing enforces/guarantees that the callback actually completes and clears the flag, and once it fails to do so, all subsequent legitimate operations are permanently blocked.

### Impact Explanation
If triggered, the wallet contract becomes permanently unusable: `rlp_execute` (the sole entry point for the user to move funds or interact with contracts from their ETH-implicit account) will reject every future transaction, regardless of relayer or signer. Since this is the account's only mechanism for spending its NEAR balance and interacting with contracts, this constitutes a **permanent freezing of user funds** held by the wallet-contract account (all $NEAR balance and any assets manageable only through this contract become inaccessible).

### Likelihood Explanation
The attack is reachable by an ordinary, unprivileged actor: any account named as `target` in an `rlp_execute` call (e.g. a token contract the user or relayer chooses to interact with, or one the relayer is tricked into using) can return an oversized successful value from its exposed method to trigger this condition. No special node/network privileges, consensus manipulation, or protocol bug are required — only a target/token contract controlled or influenced by an attacker, which is a realistic scenario for wallets designed to interact with arbitrary third-party contracts/tokens. The exact gas margin needed (whether normal contract sizes practically allow exceeding 5 Tgas from a large return value) could not be fully verified from the code alone (this would require empirically measuring the gas cost of `promise_result`/register-read for large payloads plus WASM loading costs against the 5 Tgas ceiling), so the precise minimum payload size to trigger this is unconfirmed.

### Recommendation
- Do not rely on a state flag that is only cleared inside a subsequent callback which may fail to fully execute. Instead, add a mechanism to detect and recover from the case where a scheduled callback never completes (e.g. rely on a value that is guaranteed to be set/incremented regardless of the outer function's success, or use a robust timeout/self-heal path).
- Size the static gas allocated to `rlp_execute_callback` based on worst-case payload sizes it might need to read (e.g., cap and pre-charge for the maximum possible `PromiseResult` value length before it's copied), or bound how much of the `PromiseResult` payload is processed rather than assuming the fixed `RLP_EXECUTE_CALLBACK_GAS` constant is always sufficient.
- Consider structuring `rlp_execute_callback` so the `has_in_flight_tx = false` reset is guaranteed even if downstream processing panics — e.g., splitting "clear flag" into its own minimal, low-gas first receipt/action that cannot be starved by large payloads from later actions in the same call.

### Proof of Concept
1. Deploy `WalletContract` for an eth-implicit account and give the relayer a function-call access key for `rlp_execute`.
2. Deploy an attacker-controlled contract as `target` (or reuse a NEP-141 token contract with a huge padded response) whose invoked method returns success with a payload sized close to the max allowed return-value length.
3. Submit an RLP-encoded transaction via `rlp_execute` addressed to this `target`.
4. The action promise resolves successfully but the chained `rlp_execute_callback` (dispatched with only `RLP_EXECUTE_CALLBACK_GAS` = 5 Tgas) fails while decoding/copying the large `PromiseResult::Successful` value via `env::promise_result(0)`, aborting with a gas-related `HostError`.
5. Because the receipt fails, the `has_in_flight_tx = false` write is rolled back; `has_in_flight_tx` remains `true`.
6. Any subsequent call to `rlp_execute` (by the legitimate user or any relayer) immediately returns `"Error: transaction already in progress, please try again later."` and never resets the flag, permanently freezing the account.

Note: verifying the exact payload size needed to exceed the 5 Tgas budget requires empirical gas-cost measurement of `promise_result`/register copy for large blobs, which was not directly confirmed in the indexed code; this is flagged as an area needing hands-on testing/benchmarking to fully validate feasibility.

                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }

                ExecuteResponse { success: true, success_value: Some(value), error: None }
