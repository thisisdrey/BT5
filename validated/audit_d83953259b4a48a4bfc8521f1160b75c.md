### Title
Fixed-window stream throttle allows near-2x burst of streams across `STREAM_THROTTLING_INTERVAL` boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a lazy, per-connection *fixed* window counter: `stream_count` is reset to `0` only when `Instant::now() - last_throttling_instant > STREAM_THROTTLING_INTERVAL`, and the window boundary is anchored to whenever the attacker's connection/counter was created or last reset. [1](#0-0) 

`throttle_stream` only sleeps a peer once `streams_read_in_throttle_interval >= max_streams_per_throttling_interval`; until that threshold is hit, every new stream is admitted immediately with no smoothing. [2](#0-1) 

`on_new_stream` in the SwQoS controller invokes `throttle_stream` on every new QUIC stream a remote peer (staked or unstaked) opens, before `on_stream_accepted` increments `stream_count`. [3](#0-2) [4](#0-3) 

Because the window is a fixed (non-sliding) window anchored to the attacker-controlled connection's own clock, an attacker can:
1. Open `max_streams_per_throttling_interval - 1` streams just before the window's end (all admitted, since count stays `< max`).
2. Immediately after `reset_throttling_params_if_needed` resets `stream_count` to `0` (triggered lazily by the next stream's throttle check once `STREAM_THROTTLING_INTERVAL` has elapsed), open another `max_streams_per_throttling_interval` streams.

Both bursts are individually compliant with the per-window cap, but together they deliver close to `2 * max_streams_per_throttling_interval - 1` streams within a short, effectively negligible wall-clock span straddling the boundary — a classic fixed-window-counter burst-doubling effect. This is exploitable by a fully unstaked/unprivileged QUIC client since throttling and window anchoring are purely local, per-connection, and timer-based (no cross-connection synchronization or randomized jitter on window boundaries).

### Impact Explanation
This is a QoS evasion: an attacker can transiently double their effective stream ingestion rate relative to the configured `max_streams_per_throttling_interval` for both unstaked and (low-stake) staked connections, by timing bursts around interval boundaries. It does not cause a panic, memory-safety, or consensus issue — the effect is bounded to roughly one extra `max_streams_per_throttling_interval` worth of streams per attack cycle, momentarily exceeding configured per-connection throughput.

### Likelihood Explanation
The attacker only needs to control the timing of stream opens on their own connection and does not need any elevated privileges, staking, or validator control — a plain unstaked QUIC client to the leader's TPU port is sufficient. Precise boundary alignment requires estimating `last_throttling_instant`, which is anchored to the connection/stream-counter creation time under the attacker's control, making the timing largely predictable modulo network jitter. This is repeatable at every window boundary, though each individual burst gain is capped at roughly one extra window's worth of streams — it does not compound into unbounded, sustained overshoot beyond ~2x for a single interval.

### Recommendation
Replace or augment the fixed-window counter with a token-bucket or sliding-window rate limiter (e.g., decrement fractional tokens continuously, or track a rolling window of timestamps) so that no wall-clock window boundary allows admitting more than `max_streams_per_throttling_interval` streams within any rolling `STREAM_THROTTLING_INTERVAL`-sized window, not just fixed, attacker-anchored windows.

// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_fixed_window_boundary_burst() {
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max = 10u64;

    // Burst 1: send max-1 streams just before window end.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL - Duration::from_millis(1)).await;
    for _ in 0..max - 1 {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);

    // Cross the boundary -> lazy reset triggers on next call.
    tokio::time::advance(Duration::from_millis(2)).await;

    // Burst 2: send another `max` streams right after reset.
    let mut admitted_in_burst2 = 0;
    for _ in 0..max {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
        admitted_in_burst2 += 1;
    }

    // Assert: total streams admitted across the narrow window spanning both bursts
    // exceeds max_streams_per_throttling_interval, demonstrating the ~2x boundary burst.
    let total_admitted = (max - 1) + admitted_in_burst2;
    assert!(
        total_admitted > max,
        "expected boundary burst to exceed configured max_streams_per_throttling_interval, got {total_admitted}"
    );
}

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
