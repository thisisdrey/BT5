### Title
Single unstaked attacker can starve staked TPU connections by sustaining ~2,500 stalled QUIC handshakes/sec, since the per-IP connection rate limiter is never charged for connections that never complete the handshake - (File: streamer/src/nonblocking/quic.rs)

### Summary
The QUIC accept loop in `run_server`/`setup_connection` bounds each half-open connection to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) and caps concurrent slots via `ClientConnectionTracker::new(..., qos.max_concurrent_connections())`, but the per-IP `ConnectionRateLimiter` is only debited in `register_connection`, which is called from `setup_connection` **after** a successful handshake. An attacker who never completes the handshake (Initial sent, Handshake withheld) never triggers `register_connection`, so `rate_limiter.is_allowed()` keeps returning `true` for that IP indefinitely. The only remaining gate is the coarse global `overall_connection_rate_limiter` (2,500/s sustained, burst 1,000), which is high enough to continuously refill all `max_concurrent_connections` slots (default 5,000, recycled every 2s) from a single source.

### Finding Description
In `streamer/src/nonblocking/quic.rs::run_server`, each incoming QUIC attempt goes through:
1. Global rate check: `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
2. Per-IP pre-check: `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) 
3. Slot acquisition: `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` [3](#0-2) 
4. `setup_connection` is spawned, which waits `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` (2 seconds), decrementing `outstanding_incoming_connection_attempts` regardless of outcome. [4](#0-3) 

Critically, `ConnectionRateLimiter::is_allowed` only checks an *existing* token-bucket record for the IP and defaults to `true` if none exists — it never consumes a token: [5](#0-4) . The bucket is only actually charged in `register_connection`, and its own doc-comment confirms this design assumption: "we should only modify server state once source IP is verified" [6](#0-5) . `register_connection` is invoked only inside `setup_connection` **after** the handshake future resolves `Ok`: [7](#0-6) .

Consequently, if the attacker's `connecting` future never resolves (stalls until the 2s timeout fires and returns `Err` at line 538-542), `register_connection` is never reached, so the per-IP bucket for that IP is never touched and `is_allowed` continues returning `true` forever for that same IP. The per-IP defense (`max_connections_per_ipaddr_per_min`, default 8/min, burst 80) is thus completely bypassed for this exact attack pattern, leaving only the single global `overall_connection_rate_limiter` (`TOTAL_CONNECTIONS_PER_SECOND` = 2500, `MAX_CONNECTION_BURST` = 1000) as protection: [8](#0-7) [9](#0-8) .

`max_concurrent_connections()` for the production `SwQos` is `(max_staked_connections + max_unstaked_connections) * 5 / 4`, which with defaults `DEFAULT_MAX_STAKED_CONNECTIONS`=2000 and `DEFAULT_MAX_UNSTAKED_CONNECTIONS`=2000 equals 5000 slots: [10](#0-9) [11](#0-10) . Each slot is held for up to 2 seconds (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) before `ClientConnectionTracker::drop` frees it: [12](#0-11) . To keep all 5000 slots perpetually occupied, an attacker only needs a sustained inflow of `5000 slots / 2s = 2500 attempts/sec` — which exactly matches `TOTAL_CONNECTIONS_PER_SECOND`, the global limiter's steady-state cap. A single unprivileged client generating tiny UDP QUIC Initial packets (no CPU-expensive crypto completion required, since it never finishes the handshake) can sustain this rate indefinitely from one machine/IP, since the per-IP gate never engages against it.

While `ClientConnectionTracker::new` correctly returns `Err` and increments `refused_connections_too_many_open_connections` once slots are full (bounding memory, not causing unbounded growth or panic) [13](#0-12) , the attacker can keep the pool saturated continuously, meaning legitimate staked clients attempting to connect during the attack window are refused via `incoming.refuse()` at the same rate: [3](#0-2) .

### Impact Explanation
This is a TPU accept-path Denial of Service against staked/legitimate traffic (QoS evasion / connection starvation category). A single unstaked attacker can occupy essentially all of a leader's available QUIC connection slots by sending never-completing handshake attempts at a rate matching the leader's own global rate-limit ceiling, causing genuine stake-weighted transaction submitters to be refused connections (`refused_connections_too_many_open_connections`) for the duration of the attack, degrading or halting transaction ingress at that leader.

### Likelihood Explanation
Feasible with modest resources: the attacker needs only to send QUIC Initial packets and never respond to/complete the Handshake, which is cheap (no TLS handshake completion, no valid stake, no special network position, works from a single IP). Sustaining ~2500 attempts/sec of tiny UDP packets is well within reach of a single unprivileged client and does not require IP spoofing (spoofing may even improve robustness, but is not required, since the per-IP limiter is never charged in this incomplete-handshake path). The attack is fully repeatable and requires no privileged/staked identity, matching the preconditions of the audited threat model.

### Recommendation
Charge (or at least provisionally reserve) the per-IP `ConnectionRateLimiter` token at connection-attempt time (before/at `ClientConnectionTracker::new`) rather than only after a successful handshake, so that an IP that repeatedly starts but never completes handshakes is throttled the same as one that fails handshakes for other reasons. Alternatively, track outstanding (unconfirmed) attempts per source IP with a strict cap independent of the global counter, and/or reduce `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` / `TOTAL_CONNECTIONS_PER_SECOND` so the sustainable attack rate is no longer within reach of a single client, and reserve a portion of `max_concurrent_connections` slots exclusively for connections that present a valid stake-weighted identity as early as possible.

### Proof of Concept
Integration test plan (extending existing tests like `test_quic_server_unstaked_node_connect_failure` in `streamer/src/nonblocking/quic.rs`):
1. Spawn a QUIC streamer with default `SwQosConfig` (max_staked=2000, max_unstaked=2000 → `max_concurrent_connections()` = 5000) and default `QuicStreamerConfig`.
2. From a single test-controlled `IpAddr` (or a small pool that never varies within the attack loop), repeatedly call `endpoint.connect(...)` to the server but intentionally drop/never poll the resulting `Connecting` future to completion (or wrap it so it never sends the final handshake completion flight), at a sustained rate of ~`TOTAL_CONNECTIONS_PER_SECOND` (2500/s) for several multiples of `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (e.g., 10 seconds).
3. Concurrently, from a second, legitimate staked keypair/client, attempt to connect once per handshake-timeout window.
4. Assert:
   - `stats.open_connections` stays near `max_concurrent_connections()` throughout the attack (bounded, as expected).
   - `stats.refused_connections_too_many_open_connections` increases specifically when the legitimate staked client attempts to connect during the attack window, i.e., the staked client fails/times out to connect within one or more `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` cycles.
   - After stopping the attack, the staked client connects successfully within one handshake-timeout cycle, confirming recovery — demonstrating the "bounded but effectively 100%-occupied-by-a-single-unstaked-IP" starvation window, not merely an expected/bounded refusal under overall load.
   - Instrument `ConnectionRateLimiter::is_allowed`/`register_connection` call counts to show `register_connection` for the attacking IP is never invoked (0 times) despite thousands of attempts, confirming the per-IP limiter bypass.

impl Drop for ClientConnectionTracker {
    /// When this is dropped, reduce the open connection count.
    fn drop(&mut self) {
        self.stats.open_connections.fetch_sub(1, Ordering::Relaxed);
    }
}

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
