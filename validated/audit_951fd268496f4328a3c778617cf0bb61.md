## Title
Non-constant-time comparison of RPC bearer-token authorization header allows remote timing side-channel to recover the admin password - (File: `stackslib/src/net/api/blockreplay.rs`, `blocksimulate.rs`, `postblock_v3.rs`, `postblock_proposal.rs`, `fastcallreadonly.rs`, `txsimulate.rs`)

### Summary
Six privileged Nakamoto/mining RPC endpoints authenticate callers by comparing the client-supplied `Authorization` header against the operator-configured password using Rust's default `!=` string comparison. This comparison is not constant-time, so an unauthenticated network attacker can use response-timing measurements to incrementally recover the password byte-by-byte, then use it to gain full unauthorized access to sensitive/destructive node RPCs (block posting/broadcast, block/tx simulation, block replay, fast-call-read).

### Finding Description
The advisory hints at a bug class: a secret (Applitools API key) that should remain confidential is instead exposed/handled insecurely, undermining "credential confidentiality." The closest reachable analog in this repo's in-scope network code is not display of the secret, but recoverability of it: several stacks-node RPC handlers gate access with a shared-secret bearer token compared via plain equality: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Each handler stores `auth: Option<String>` and performs `if auth_header != password { return Err(...401...) }`. Rust's derived/`str`/`String` `PartialEq` performs an early-exit byte-wise comparison — it returns as soon as the first mismatching byte is found. This means the time taken to reject an incorrect header is a function of how many leading bytes match the true secret. A remote attacker who can send many HTTP requests to `/v3/blocks/upload/`, `/v3/blocks/simulate/:id`, `/v3/blocks/replay/:id`, `/v3/block_proposal`, `/v3/contracts/fast-call-read/...`, or the transaction-simulate endpoint can perform a classic byte-at-a-time timing side-channel attack against the `authorization` header value to recover the password, without ever needing to know it or hold "another party's key" up front — the entire point of the attack is to obtain that credential remotely.

This breaks the intended equality "supplied credential == stored credential" being an atomic, timing-independent decision — the same class of "authenticated vs. stored" boundary called out as in-scope.

### Impact Explanation
Once the shared password is recovered, an unauthenticated remote attacker gains authorization to:
- POST/broadcast attacker-controlled Nakamoto blocks via `postblock_v3.rs` (`RPCPostBlockRequestHandler`), influencing block relay/propagation state (`try_handle_request` calls `Relayer::process_new_nakamoto_block_ext` and can set a relay message) [6](#0-5) 
- Submit block proposals for validation via `postblock_proposal.rs`.
- Trigger block/tx simulation and block replay endpoints, potentially causing bounded compute DoS on a read endpoint or exposing internal chain data.

This matches the "High" impact bucket (bounded compute DoS on a read endpoint; unauthenticated write path reachable once the secret is exfiltrated) and edges toward "Critical" for the post-block endpoint since it is an unauthenticated-write-once-armed vector reachable purely from the network side.

### Likelihood Explanation
Exploitation requires the attacker to send a large but automatable number of HTTP requests and perform statistical timing analysis — a well-established technique (Boneh/Brumley-style timing attacks against string comparisons). It requires no prior knowledge of the secret or privileged access, only network reachability to the RPC endpoint, satisfying the "remote, unprivileged" requirement. Real-world exploitability depends on network jitter, but the endpoints run synchronous per-byte comparisons with no artificial delay or rate limiting on this code path, making the channel measurable, especially over a low-latency or repeated-request LAN/co-located adversary.

### Recommendation
Replace the `!=`/`==` `String` comparisons on the `authorization` header value with a constant-time comparison (e.g., `subtle::ConstantTimeEq`) in all affected handlers (`blockreplay.rs`, `blocksimulate.rs`, `postblock_v3.rs`, `postblock_proposal.rs`, `fastcallreadonly.rs`, `txsimulate.rs`), and consider rate-limiting/backoff on repeated authentication failures for these endpoints.

### Proof of Concept
1. Configure a stacks-node with an `authorization` password for the v3 RPC endpoints (e.g., `postblock_v3`).
2. From a remote client, send many crafted `Authorization` header guesses to an endpoint such as `POST /v3/blocks/upload/`, incrementing one byte at a time and measuring response latency to the 401 rejection at `postblock_v3.rs:104-111` (`if auth_header != password { return Err(Error::Http(401, ...)) }`).
3. Statistically, guesses whose prefix matches more of the true password take marginally longer to reject because the `PartialEq` comparison scans further before finding a mismatch.
4. Iterate per-byte to reconstruct the full password, then use it to authenticate to the privileged endpoint (e.g., broadcast an attacker block via `broadcast=1` on `/v3/blocks/upload/`).
