### Title
Unvalidated length/offset in precompile ABI-decoding causes uncaught exception denial-of-service - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The reported CVE-2025-13151 is a stack-based buffer overflow in libtasn1's `asn1_expend_octet_string`, caused by trusting an attacker-supplied length field to size/copy a buffer without validating it against actual available data. The closest reachable analog in java-tron is in `PrecompiledContracts.extractBytes`/`extractBytesArray`/`extractSigArray`, which extract variable-length byte slices from ABI-encoded precompile input using attacker-controlled offset/length words without validating them against the actual `data` array bounds before calling `Arrays.copyOfRange`.

### Finding Description
`extractBytesArray` and `extractSigArray` read a length word from the caller-supplied `DataWord[] words` and compute `bytesOffset`/`bytesLen` directly from attacker-controlled ABI-encoded input: [1](#0-0) 

These values are passed unchecked into `extractBytes`, which calls `Arrays.copyOfRange(data, offset, offset + len)` with no validation that `offset >= 0`, `len >= 0`, or `offset + len <= data.length`: [2](#0-1) 

Because `offset` and `len` are derived from `DataWord.intValueSafe()` on fully attacker-controlled ABI words (via a TVM contract call to a precompile that uses these array extraction helpers), a crafted call can drive `offset + len` far outside the bounds of `data`, or negative, triggering `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`/`IllegalArgumentException` from `Arrays.copyOfRange` rather than a validated rejection. This mirrors the libtasn1 root cause: length/offset values taken from untrusted input are used to size a copy operation without a bounds check against the real underlying buffer.

Unlike C, Java's bounds-checked arrays prevent this from becoming actual memory corruption/RCE — the practical effect is an uncaught runtime exception during precompile execution instead of a buffer overflow.

### Impact Explanation
If the exception thrown by `extractBytes` is not caught somewhere up the call chain in the specific precompiled contract's `execute()` method (I was not able to fully confirm exception handling for every precompile that calls `extractBytesArray`/`extractSigArray` due to iteration limits), an unhandled exception during TVM execution of a contract call could disrupt transaction processing for that call, at minimum causing that specific call to fail/revert unexpectedly, and at worst — if propagated up through block application in a way that isn't caught — impacting node processing of the transaction/block. This is bounded to a denial-of-service-class issue reachable by any account able to invoke the relevant precompiled contract via a normal contract call; it does not lead to memory corruption, fund theft, or key disclosure given JVM's memory safety guarantees.

### Likelihood Explanation
Reaching these helper methods only requires a transaction/contract call to a TRON precompiled contract that uses `extractBytesArray` or `extractSigArray` for multi-signature/array-based ABI parameters (e.g., batch signature validation). The attacker fully controls the ABI-encoded call data used to derive `offset`/`len`, so triggering out-of-bounds values requires no privilege beyond normal contract-call broadcasting.

### Recommendation
Add explicit bounds validation in `extractBytes` (and callers `extractBytesArray`/`extractSigArray`) before calling `Arrays.copyOfRange`: reject when `offset < 0`, `len < 0`, or `offset + len > data.length` (guarding against integer overflow), returning a failure/empty result instead of allowing an uncaught exception to escape from precompile execution.

### Proof of Concept
I was unable to fully trace which specific precompiled contract(s) invoke `extractBytesArray`/`extractSigArray` and whether their `execute()` implementations wrap calls in a try/catch that would neutralize the resulting exception before it reaches the TVM's transaction-processing loop — this requires further investigation of the concrete precompile classes (e.g., batch signature verification precompile) and the TVM's exception handling around `PrecompiledContract.execute()` calls, which I could not complete within the available tool iterations.
