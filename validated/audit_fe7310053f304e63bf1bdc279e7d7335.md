## Analog Bug Found

### Title
GRANDPA bridge pallet permanently halts when the bridged chain's legitimate authority set exceeds the hardcoded `MAX_AUTHORITIES_COUNT`, freezing header import - ([File: bridges/modules/grandpa/src/storage_types.rs])

### Summary
The Gravity Bridge report describes a hardcoded, fixed-size assumption (5000 blocks / implicit ~10MB log limit) that breaks down once validator-set-driven data legitimately grows past that assumption, causing the relay/oracle loops to error forever with no fallback, freezing the bridge. The Substrate GRANDPA bridge pallet has the same class of hardcoded, unbounded-growth assumption: it stores the bridged chain's authority set in a `BoundedVec` sized by the constant `MAX_AUTHORITIES_COUNT`. If the bridged chain's own (legitimate) governance grows its validator set beyond that constant, the bounded conversion fails and the header/authority-set update is permanently rejected, with no chunking/retry/resize path — halting further finality tracking exactly as described in the report's core "hardcoded byte/size limit + validator-set growth = perpetual freeze" pattern.

### Finding Description
The pallet documents this exact hazard itself: [1](#0-0) 

`MAX_AUTHORITIES_COUNT` is enforced as a hard, non-negotiable bound via `StoredAuthorityListLimit`, which backs a `BoundedVec`: [2](#0-1) 

The conversion from an unbounded `AuthorityList` (decoded from the bridged chain's header digest/justification) into this `StoredAuthoritySet` fails outright — with `Error::TooManyAuthoritiesInSet` — if the actual authority set exceeds the configured maximum: [3](#0-2) 

This is invoked from `try_enact_authority_change`/`submit_finality_proof_ex` every time the bridged chain schedules an authority-set change (a "mandatory" header). The pallet's own `ChainWithGrandpa` trait explicitly documents `MAX_AUTHORITIES_COUNT` as: "This is a strict constant. If bridged chain will have more authorities than that, the GRANDPA bridge pallet may halt." Once this bound is exceeded on the bridged chain, `submit_finality_proof_ex` fails on every attempt to import the mandatory header, and since mandatory headers *must* be imported before any later header can be verified (the pallet only accepts justifications signed by the currently known authority set), the pallet permanently stops accepting new finalized headers. Concrete deployed values are set very conservatively (`MAX_AUTHORITIES_COUNT: u32 = 1_256` for Polkadot-like chains), while GRANDPA `MaxAuthorities` on relay chains is configured far higher (documented as up to `100_000`) — meaning the bridge-side constant is deliberately a much smaller "real-world value" estimate rather than a protocol-enforced cap: [4](#0-3) 

This is structurally identical to the Gravity Bridge issue: a hardcoded size/count assumption baked into client/pallet logic (5000-block window assumption vs. 300-validator log size in Gravity; `MAX_AUTHORITIES_COUNT` vs. actual validator count here) that, once exceeded by legitimate protocol growth (more validators, not an attacker), causes the relaying/verification pipeline to error perpetually with no fallback path (no re-chunking of the authority list, no incremental acceptance, no governance-independent recovery) — freezing bridge processing.

### Impact Explanation
If a bridged chain's authority set organically grows past `MAX_AUTHORITIES_COUNT` (a chain-level decision made by that chain's own validators/governance, not an admin action on the bridge chain itself), every subsequent `submit_finality_proof_ex` call carrying the new mandatory header will fail with `TooManyAuthoritiesInSet`. Because mandatory headers gate all future header imports, this permanently locks the bridge's on-chain light client at the last authority set it could store — a hard "permanent bridge-state lock" matching the required-impact category "permanent user-fund or bridge-state lock" (it can stall any dependent bridge messaging, e.g. `pallet-bridge-messages`, that relies on the GRANDPA light client for header inclusion, and requires a runtime upgrade to raise the constant and manually reinitialize the pallet to recover).

### Likelihood Explanation
Likelihood is low-to-moderate and tied to the bridged chain's own validator-count trajectory rather than any attacker action, which mirrors the original report (Cosmos Hub raising validators to 300). Current configured constants (`1_256` for Polkadot-like chains) provide a large safety margin versus current live validator counts, but the constant is a fixed value hardcoded per-chain-pair in the runtime and is not automatically kept in sync with the bridged chain's actual `MaxAuthorities` runtime parameter, so any future governance-driven increase on the bridged chain that is not matched by a corresponding runtime upgrade on the bridge chain reproduces exactly this freeze, with no on-chain fallback.

### Recommendation
Add either (a) a chunked/partial encoding path so authority sets larger than `MaxBridgedAuthorities` can still be accepted (analogous to the recommended "chunk the search and combine results" fix for Gravity), or (b) an explicit monitoring/alerting and safe-halt-with-governance-recovery mechanism so this failure mode is detected before authority sets approach the hardcoded bound, and ensure the constant is kept comfortably above the bridged chain's actual configured `MaxAuthorities`, not just its current observed size.

### Proof of Concept
1. Deploy the GRANDPA bridge pallet bridging to a chain X with `MAX_AUTHORITIES_COUNT = N`.
2. On chain X, through its own legitimate governance, increase `pallet_grandpa::Config::MaxAuthorities`/actual validator count to `> N`.
3. When chain X's authority set changes (a "mandatory" header with a `ScheduledChange` digest is produced with `> N` authorities), a relayer submits it via `submit_finality_proof_ex`.
4. `try_enact_authority_change` calls `StoredAuthoritySet::try_new`, which returns `Error::TooManyAuthoritiesInSet` because the authority list no longer fits into `StoredAuthorityListLimit`'s bound.
5. Every subsequent attempt to import this or any later mandatory header fails identically; the pallet is permanently unable to progress finality tracking for chain X without a runtime upgrade increasing `MAX_AUTHORITIES_COUNT` and manual reinitialization.
