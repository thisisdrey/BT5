### Title
Wnear `storage_deposit` leg debited by `withdraw()` is never refunded when `near_withdraw` fails, permanently destroying user funds - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`internal_ft_withdraw` atomically debits both the FT amount and the wnear `storage_deposit` amount from the signer's ledger balance in a single `withdraw()` call, but only the FT leg is ever re-credited on failure via `ft_resolve_withdraw`. If `near_withdraw` fails, `do_ft_withdraw` panics before scheduling any wnear-specific resolver, so the debited wnear amount is never restored anywhere in the promise chain.

### Finding Description
The claimed binding is:
`(ft_amount_debited + storage_deposit_debited) == (ft_delivered_or_refunded) + (storage_deposit_delivered_or_refunded)`, evaluated per `TokenId` (`Nep141TokenId::new(token)` vs `Nep141TokenId::new(wnear_id)`).

In `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:54-74`), a single call to `self.withdraw(...)` subtracts **both** legs atomically from the signer's ledger: [1](#0-0) 

The promise chain is `near_withdraw()` → `do_ft_withdraw()` → `ft_resolve_withdraw()`. Inside `do_ft_withdraw`, if `near_withdraw` failed, the function panics via `require!` before ever constructing the `storage_deposit` promise or any wnear-specific callback: [2](#0-1) 

Because `do_ft_withdraw` panics, the receipt for that call fails as a whole. The next callback, `ft_resolve_withdraw`, still executes (per NEAR's `.then()` semantics) and reads `promise_result_checked_void(0)`/`promise_result_checked_json(0)` against the failed `do_ft_withdraw` result, resulting in `used = 0` and a full refund — but only for the **FT `token`**, never for the wnear leg: [3](#0-2) 

There is no other code path in this file, in `ft_resolve_withdraw`, or elsewhere that re-credits `Nep141TokenId::new(wnear_id)` for the amount that was subtracted as `withdraw.storage_deposit`. The ledger subtraction happens in `Contract::withdraw` (`contracts/defuse/src/contract/tokens/mod.rs:76-128`), which treats all `(TokenId, amount)` pairs from the chained iterator uniformly and permanently decrements `owner.token_balances` for each — there is no rollback mechanism tied to promise outcomes; refunding is entirely the responsibility of the resolver callbacks, and none exists for the wnear leg of `ft_withdraw`.

Physically, since `near_withdraw` failed, the wnear tokens were never unwrapped/transferred out of the Defuse contract's wNEAR balance — the contract still custodies them — but the internal accounting no longer attributes them to any user, since the signer's ledger entry was already decremented and never restored. This is a real ledger/physical-asset divergence: the Verifier's actual wNEAR balance held on the wnear contract remains, but no account can claim it, i.e., a real "orphaned" surplus with a corresponding permanent loss to the specific signer whose withdrawal failed.

Attacker/user flow: sign `FtWithdraw{token, storage_deposit: Some(x), receiver_id, amount, ...}` where the target FT contract requires `min_gas` etc., but force `near_withdraw` to fail — e.g. by having insufficient wNEAR registered/backing on the wnear contract side, or by using `min_gas`/gas starvation causing `near_withdraw` to run out of gas or the wnear contract to reject the withdrawal for its own reasons (e.g. insufficient storage balance on wnear side for the receiver in some wnear implementations, or amount exceeding held wNEAR due to a race). Any user can trigger this against their own account (self-inflicted), and it does not require any privileged role — it is exploitable by any signer via `Contract::withdraw`/`ft_withdraw` (or via `execute_intents` executing an `FtWithdraw` intent) simply by choosing a `storage_deposit` value that makes `near_withdraw` fail, while the ft_transfer_call/ft_transfer itself may or may not succeed (it doesn't matter — the wnear leg is lost regardless of the FT leg's outcome).

### Impact Explanation
The signer's internal wNEAR-token ledger balance is decremented by `storage_deposit` and never restored on `near_withdraw` failure, while the underlying wNEAR asset remains custodied by the contract, unclaimed by anyone. This is a permanent loss/freeze of user funds specific to the signer who issued the withdrawal — matching the "user funds permanently frozen" Critical category. It is repeatable per withdrawal attempt and per account, and the amount lost equals the attacker-chosen (or victim's) `storage_deposit` value, which can be made arbitrarily large up to their wnear-equivalent balance.

### Likelihood Explanation
Preconditions: the signer must have both a `token` balance and enough wnear-equivalent balance to fund `storage_deposit`. The only additional requirement is a scenario where `near_withdraw` fails after the ledger debit has already occurred — e.g., a mismatch between the wnear contract's registered/liquid NEAR balance for the Defuse contract's account (e.g. if the Defuse account's own wNEAR balance held on the wNEAR contract is less than the requested `storage_deposit`, or the wNEAR contract enforces a minimum registration balance that would be violated by fully withdrawing). This is plausible without any special privileges — the attacker fully controls the `storage_deposit` parameter of their own signed intent, and can pick a value that is known to fail (e.g., larger than the Defuse contract's actual liquid wNEAR balance on the wnear contract, if such a mismatch can arise, or exploiting timing/race with concurrent withdrawals draining the contract's wNEAR reserve). The exact trigger condition depends on the wNEAR contract's implementation and the Defuse contract's actual wNEAR reserve at call time, which I could not fully verify from the indexed code (I did not have access to the `defuse-wnear` crate's `near_withdraw` implementation to confirm exact failure conditions). This uncertainty affects only the ease of triggering `near_withdraw` failure, not the core logic flaw: **whenever** `near_withdraw` fails for any reason, the wnear leg is unconditionally and permanently lost with no refund path.

### Recommendation
Track the wnear `storage_deposit` leg separately through the promise chain and refund it if `near_withdraw` (or the subsequent `storage_deposit` call) fails, symmetric to how `ft_resolve_withdraw` refunds the FT leg. Concretely: have `do_ft_withdraw` propagate the `near_withdraw` failure information (rather than or in addition to panicking outright), or add a dedicated resolver stage that inspects the `near_withdraw` promise result and calls `self.deposit(sender_id, [(Nep141TokenId::new(wnear_id), storage_deposit)], ...)` when `near_withdraw` did not succeed, mirroring the existing FT refund logic in `ft_resolve_withdraw`.

    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),

            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
