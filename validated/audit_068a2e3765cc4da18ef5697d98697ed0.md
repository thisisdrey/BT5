Audit Report

## Title
Fee-calculation truncation lets `calculate_fee` return a zero remote fee for non-zero, validated `PricingParameters` — public underpriced bridge work - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::calculate_fee` in the Snowbridge outbound-queue pallet converts the Ethereum-side remote fee (computed in wei, 18 decimals) into the chain's native `Balance` via `convert_from_ether_decimals`, which performs an integer division by `10^(18-Decimals)`. For realistic, fully non-zero `PricingParameters` that pass `validate()`, this division can silently truncate the remote fee component to `0`, meaning the message sender is charged nothing for the relayer's Ethereum-side gas/reward cost. The pallet's own regression test confirms this exact scenario with `fee_per_gas=1`, `rewards.remote=1`.

## Finding Description
`PricingParameters::validate()` in `bridges/snowbridge/primitives/core/src/pricing.rs` only checks that `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` are each individually non-zero. It performs no check relating these values to the truncation denominator used later in fee conversion.

`Pallet::calculate_fee` (`bridges/snowbridge/pallets/outbound-queue/src/lib.rs`) computes `calculate_remote_fee(gas_used, fee_per_gas, reward)`, casts to `u128`, applies the `multiplier`/`exchange_rate` via `FixedU128` arithmetic, and finally calls `convert_from_ether_decimals`, which does `value.checked_div(10^(18-Decimals))`. For a 10-decimal chain, this divisor is `10^8`; any computed value below that threshold is truncated to exactly `0` with no error path, floor, or non-zero-result assertion — unlike the `expect("divisor is non-zero; qed")` guard, which only protects against a zero divisor, not a zero result.

The pallet's test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` demonstrates this with fully valid, `validate()`-passing parameters, and its own comment states the resulting zero fee "should be avoided."

Additionally, `do_process_message` populates `CommittedMessage.reward` from the raw, unconverted `pricing_params.rewards.remote` value, which is what the Ethereum gateway contract uses to pay the relayer — while the balance actually collected from the user for that promised reward is computed through the lossy `convert_from_ether_decimals` path in `calculate_fee`. This creates a divergence between the fee charged on-chain and the reward promised/paid on Ethereum.

## Impact Explanation
When `calculate_fee`'s remote component truncates to zero (or under-collects relative to the promised Ethereum-side `reward`), relayers submitting messages to Ethereum are not compensated from the user-paid fee for that leg of the relay. Since relaying is a permissionless, incentive-driven service, systematically zero/underpriced remote fees remove the economic incentive to relay messages, which can stall delivery of the outbound message queue to Ethereum. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category.

## Likelihood Explanation
Governance sets `PricingParameters` via the `set_pricing_parameters` extrinsic in the system pallet, gated only by `validate()`'s non-zero checks, which do not account for the truncation denominator introduced in `convert_from_ether_decimals`. Any combination where `fee_per_gas * gas_used + reward` falls below `10^(18-Decimals)` (e.g., ~`10^8` wei-equivalent for a 10-decimal chain) triggers this deterministically and repeatably; the pallet's own test uses trivially realistic values (`fee_per_gas=1`, `reward=1`) to demonstrate it. No malicious actor is required to trigger the underlying arithmetic bug — it is a straightforward integer-truncation flaw in the fee-computation path.

## Recommendation
In `calculate_fee`, after computing the truncated remote `Balance` fee, explicitly check whether the pre-truncation value was non-zero but the post-truncation value became zero, and either return an error/revert the extrinsic or enforce a minimum floor fee rather than silently accepting `0`. Ensure the value embedded in `CommittedMessage.reward` (used for on-Ethereum payout) is derived consistently from the same converted value actually charged to the user, rather than the raw pre-conversion `rewards.remote`. Consider extending `PricingParameters::validate()` (or adding a dedicated check invoked at parameter-update time) to reject parameter combinations that would produce a fully truncated (zero) fee given `Decimals` and expected gas-used ranges.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}
