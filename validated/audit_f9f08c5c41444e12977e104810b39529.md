## Title
Stale `PromiseYield`/`Resume` state (`PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, `YieldIdToDataId`/`DataIdToYieldId`) survives `DeleteAccount` and lets a scheduled self-call bypass `predecessor_id == receiver_id` internal-only gating on a recreated account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account()` — the function invoked by `action_delete_account` when a `DeleteAccount` action is processed — only removes the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie rows for the account. It never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout` queue entries, or the `TrieKey::YieldIdToDataId`/`TrieKey::DataIdToYieldId` rows created by an in-flight `promise_yield_create`/`promise_yield_create_with_id`. Because the account_id namespace can be recreated later (e.g. by the parent account handing the sub-account name to a new owner), the leftover yield state resolves into a self-call receipt (`predecessor_id == receiver_id == account_id`) executed against whatever code/owner now occupies that account_id.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only these columns: [1](#0-0) 

It never touches `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `PROMISE_YIELD_TIMEOUT`, `YIELD_ID_TO_DATA_ID`, or `DATA_ID_TO_YIELD_ID` (compare with the dedicated helper that would need to be called, `remove_yield_id_mappings`, which is never invoked from `action_delete_account`): [2](#0-1) 

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and then clears `*account = None`, with no reference to yield/resume state cleanup: [3](#0-2) 

When a yield is created, the yield callback receipt (the "yield_receipt") is always built as a **self-call**: `predecessor_id: account_id.clone()` and `receiver_id: receipt.receiver_id` (the same account), stored under `TrieKey::PromiseYieldReceipt{receiver_id, data_id}`: [4](#0-3) 

A timeout is also scheduled unconditionally at yield-creation time, independent of whether the account still exists later, via `enqueue_promise_yield_timeout`: [5](#0-4) 

When the timeout fires, `resolve_promise_yield_timeouts` checks only whether `PromiseYieldReceipt` is *still present in the trie* — it does not check whether the account currently existing at that id is the same account/owner that created the yield: [6](#0-5) 

The resulting `PromiseResume` receipt is delivered with `predecessor_id: queue_entry.account_id`, `receiver_id: queue_entry.account_id` — i.e. always a self-call to the account_id, regardless of who now controls it. On delivery, `apply_action_receipt` looks up `get_promise_yield_receipt(state_update, account_id, data_id)` purely by `(account_id, data_id)` and, if found, executes the yield_receipt's `FunctionCall` actions (chosen at yield-creation time by the original creator) against whatever code is currently deployed at `account_id`: [7](#0-6) [8](#0-7) 

**Exploit flow:**
1. Attacker deploys a contract to `child.attacker.near` with an "internal-only" method gated by `assert!(predecessor_id() == current_account_id())` (a standard self-callback authorization pattern).
2. Attacker calls `promise_yield_create`, targeting itself, choosing the callback method name and arguments to be executed later; this writes `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries keyed by `child.attacker.near`.
3. Attacker (or the account's own key) issues `DeleteAccount`. `remove_account` deletes the `Account`/keys/code/data but leaves the `PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout` and (if `promise_yield_create_with_id` was used) `YieldIdToDataId`/`DataIdToYieldId` rows intact.
4. The parent namespace (e.g. `attacker.near`) later recreates `child.attacker.near` — handing control (new full-access key, new deployed contract) to a different party. Nothing in `action_create_account`/`action_deploy_contract` purges the leftover yield state, since it lives under an unrelated column keyed by `AccountId` alone.
5. At the block height set at step 2 (`yield_timeout_length_in_blocks`, attacker-controlled indirectly since it just needs to exceed the recreation time), `resolve_promise_yield_timeouts` finds `PromiseYieldReceipt` still present and auto-generates a `PromiseResume` receipt with `predecessor_id == receiver_id == child.attacker.near`.
6. This drives execution of the original attacker-chosen `FunctionCall` (method name + args fixed in step 2) against the account's **current** (victim-controlled) contract code. Since `predecessor_id == receiver_id` (both `child.attacker.near`), any internal-only gate relying on that invariant is satisfied even though the call effectively originates from stale attacker-controlled state, not from the current contract's own logic.

No existing check re-validates that the account executing the leftover yield callback is "the same" account (by ownership/epoch/generation) that created the yield; account identity in NEAR is purely the `AccountId` string, and none of `check_actor_permissions`, `verify_and_charge_tx_ephemeral`, or the receipt-delivery path in `apply_action_receipt` differentiate between "this account_id as it existed before deletion" and "this account_id after recreation."

### Impact Explanation
This is an authorization-escalation bug: an attacker can plant a scheduled, guaranteed-to-fire, self-authenticated (`predecessor_id == receiver_id`) callback into any account_id they currently control, then have that account_id's identity reassigned to a different owner/contract, and have the callback execute against the new owner's code while still passing internal-only/self-call authorization checks. This directly matches the NEAR bounty category of "authorization escalation across accounts or promises." The practical severity depends on how common named-subaccount-reuse across ownership boundaries is in a given deployment (factories/marketplaces that delete and reassign subaccounts), but the underlying state-hygiene defect (yield/resume trie rows not purged on `DeleteAccount`) is unconditionally present and reachable by an ordinary, unprivileged account.

### Likelihood Explanation
- Cost to attacker: minimal — one `promise_yield_create` call, one `DeleteAccount` action, both ordinary transactions signed with the attacker's own keys.
- No validator, node, or protocol privilege required; purely a sequence of standard actions available to any account with a full-access key on the account and its parent namespace.
- Repeatable: the attacker fully controls the timeout length (`yield_timeout_length_in_blocks`) and the callback method/args at creation time.
- Precondition that limits blast radius: the account_id must actually be reassigned to a different owner's contract that also implements a `predecessor_id == receiver_id` self-call gate for a privileged method — this is a common pattern (used for guarding promise-then callbacks) but requires the specific subaccount-recycling scenario described. The root state-cleanup bug itself, however, is unconditional and demonstrable regardless of that downstream contract pattern.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`) and/or `action_delete_account` (`runtime/runtime/src/actions.rs`), iterate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, pending `PromiseYieldTimeout` queue entries, and `YieldIdToDataId`/`DataIdToYieldId` rows scoped to the account being deleted before clearing the account record (mirroring the existing `remove_yield_id_mappings` helper, plus new iteration over the `PROMISE_YIELD_RECEIPT`/`PROMISE_YIELD_STATUS` prefixes for that account and removal of matching entries from the global `PromiseYieldTimeout` queue, or alternatively tag/invalidate them so `resolve_promise_yield_timeouts`/the `PromiseResume` handler treat them as expired once the owning account has been deleted).

### Proof of Concept
Integration test plan (extending the existing test-loop harness used in `test-loop-tests/src/tests/yield_resume.rs` and `test-loop-tests/src/tests/create_delete_account.rs`):
1. Deploy contract A to `child.alice.near` exposing a method `internal_only()` that asserts `predecessor_account_id() == current_account_id()` and, if passed, performs an observable side effect (e.g. writes a "PWNED" storage value) — analogous to `check_promise_result_write_status` in `runtime/near-test-contracts/test-contract-rs/src/lib.rs`.
2. Call `promise_yield_create` (or `_with_id`) on `child.alice.near`, targeting `internal_only()` with attacker-chosen args, with a small `yield_timeout_length_in_blocks`.
3. Submit `DeleteAccount{beneficiary_id: alice.near}` from `child.alice.near`.
4. From `alice.near` (parent), submit `CreateAccount` + `DeployContract` for `child.alice.near` deploying contract B (a different, "victim" contract) that has no knowledge of contract A's yield.
5. Advance blocks past the yield timeout height.
6. Assert: a `PromiseResume` receipt is auto-generated and delivered to `child.alice.near`; assert the "PWNED" storage marker from contract A's `internal_only()` now exists under the account now running contract B's code, proving the stale self-call callback executed against the recreated account and passed the `predecessor_id == receiver_id` gate despite the account having been deleted and given entirely different code/ownership in between.
