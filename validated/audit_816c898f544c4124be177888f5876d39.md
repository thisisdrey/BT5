### Title
Unauthenticated peer-identity overwrite via neighbor-of-neighbor `HandshakeAccept` with attacker-chosen `addrbytes`/`port` - ([File: stackslib/src/net/neighbors/walk.rs -> fn handle_neighbor_handshake_accept])

### Summary
The exact scenario asked about (a raw inbound `Handshake` self-signed with a fresh keypair, claiming a victim's `NeighborKey`, silently overwriting that victim's `PeerDB` row) is **not** exploitable as described, because `validate_handshake`'s address check and the `stats.outbound` gate in `handle_handshake` prevent direct DB writes from unauthenticated inbound handshakes. However, a materially equivalent bug exists in the neighbor-walk "neighbor-of-neighbor" handshake path: `handle_neighbor_handshake_accept` in `stackslib/src/net/neighbors/walk.rs` writes to `PeerDB` keyed by the attacker-controlled `HandshakeAcceptData.handshake.addrbytes`/`port` fields instead of the actually-dialed address, with no binding check comparable to the one used for `pingback` or `cur_neighbor` handshakes.

### Finding Description
`validate_handshake` (`stackslib/src/net/chat.rs:1047-1127`) only checks that the payload is self-signed by its own embedded `node_public_key`; it never binds that key to the actual TCP peer identity. The claimed exploit path in the question — inbound Handshake forcing a `PeerDB` overwrite via `Neighbor::load_and_update`/`insert_or_replace_peer` — is blocked by two guards:
- `handle_handshake` (`chat.rs:1214-1296`) only performs the `Neighbor::load_and_update` + `save_update` write `if updated && self.stats.outbound` (line 1275), i.e. never for an unauthenticated inbound connection an attacker initiates.
- For re-key on already-known outbound connections, `validate_handshake`'s `Some(_)` branch (lines 1072-1091) rejects handshake data whose `addrbytes`/`port` don't match the dialed peer address (unless "anynet").

The equivalent broken equality does exist, however, in the neighbor-walk "GetNeighbors → handshake with neighbors-of-neighbors" flow:
- `neighbor_handshakes_begin` (`walk.rs:979-1089`) dials out to addresses `na` gossiped by `cur_neighbor` (a `NeighborAddress`, i.e., an address + claimed pubkey-hash reported by some other peer — this is attacker-controllable content since anyone can be `cur_neighbor` or appear in its `GetNeighbors` response).
- When the reply comes back, `neighbor_handshakes_try_finish` (`walk.rs:1133-1230`) calls `handle_neighbor_handshake_accept(network, naddr, preamble, data, db_data)` (`walk.rs:1092-1124`), which immediately calls `self.neighbor_db.add_or_schedule_replace_neighbor(network, preamble, &data.handshake, db_data, ...)` — **without ever comparing `data.handshake.addrbytes`/`port` (attacker-controlled fields inside the self-signed `HandshakeAcceptData`) to `naddr`/`nk` (the address actually dialed)**.
- `add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs:368-426`) calls `Neighbor::load_and_update(&tx, ..., handshake)` (`chat.rs:475-516`), which derives the DB key via `NeighborKey::from_handshake(peer_version, network_id, handshake_data)` — using the attacker-supplied `addrbytes`/`port`, not the dialed socket address. If a `PeerDB` row already exists at that `(network_id, addrbytes, port)` (`was_present == true`), it calls `neighbor.save_update(&tx, ...)` → `PeerDB::update_peer` (`stackslib/src/net/db.rs:1285-1334`), which executes `UPDATE frontier SET ... public_key = ?2 ... WHERE network_id = ?12 AND addrbytes = ?13 AND port = ?14` using the attacker's claimed address as the WHERE clause and the attacker's freshly-generated `node_public_key` as the new value — silently overwriting the legitimate victim's stored public key.

This differs from the two other reply-handling paths that *do* enforce the address/key binding:
- `handle_handshake_accept` (`walk.rs:669-737`) for `cur_neighbor` rejects mismatched `neighbor_from_handshake.addr != self.cur_neighbor.addr` for outbound walks (line 705) *before* any DB write.
- `pingback_handshakes_try_finish` (`walk.rs:1683-1742`) calls `check_handshake_pubkey_hash` (line 1714) to require the reply's key hash to equal the previously-authenticated inbound peer's `public_key_hash` before calling `add_or_schedule_replace_neighbor`.

`handle_neighbor_handshake_accept` has no such check, so the attack proceeds as:
1. Attacker runs a reachable P2P node and gets discovered/listed as a "neighbor" by any honest peer already in the victim's frontier (trivial — legitimately handshake with any node so it appears in its `GetNeighbors` responses).
2. Victim's neighbor walk dials attacker's real IP as a "neighbor-of-neighbor" candidate.
3. Attacker replies with a self-signed `HandshakeAccept`/`StackerDBHandshakeAccept` whose `handshake.addrbytes`/`handshake.port` are set to some other, already-known-good peer's `NeighborKey`, and `node_public_key` is a freshly generated attacker key.
4. `handle_neighbor_handshake_accept` → `add_or_schedule_replace_neighbor` → `Neighbor::load_and_update` + `save_update`/`PeerDB::update_peer` silently rewrites that victim `NeighborKey`'s stored `public_key` to the attacker's key.

### Impact Explanation
The victim node's `PeerDB` `frontier` table entry for a legitimate peer's `(network_id, addrbytes, port)` is silently corrupted with an attacker-chosen public key, breaking the invariant that `PeerDB.public_key` for that address equals the key actually controlling that peer. Consequences: the corrupted entry's `public_key_hash` will subsequently be gossiped in `NeighborAddress` records (`GetNeighborsData`/`NeighborAddress::from_neighbor`), causing other peers who rely on `check_handshake_pubkey_hash`/`Neighbor::load_by_address` to distrust/refuse the legitimate peer at that address, and existing `stackerdb_peers` associations for that slot get dropped (`update_peer` drops StackerDB replicas on key change). This is repeatable per victim entry and per walk cycle, propagates forged identity data through gossip, and constitutes unauthenticated write to network state — matching the "Critical: unauthenticated/unauthorized write to state... network-wide propagation of forged data" category.

### Likelihood Explanation
Preconditions are modest: the attacker only needs to run a reachable P2P listener and get itself gossiped into any honest node's `GetNeighbors` responses (a normal, unprivileged action any peer can perform by handshaking once with any node). No secrets, no privileged role, no physical/local access, and no IP spoofing are required — the attacker relies purely on the fields inside its own self-signed `HandshakeAcceptData` payload, not on the actual TCP source. The attack is repeatable against any victim entry the attacker can name, as long as the walking node reaches out to the attacker as a "neighbor-of-neighbor" candidate, which happens routinely during normal neighbor-walk operation.

### Recommendation
In `handle_neighbor_handshake_accept` (`stackslib/src/net/neighbors/walk.rs`), before calling `add_or_schedule_replace_neighbor`, verify that `data.handshake.addrbytes`/`data.handshake.port` match the actually-dialed `naddr`/`nk` (as is already done for `cur_neighbor` in `handle_handshake_accept`), and/or verify `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key) == naddr.public_key_hash` (as already done in `pingback_handshakes_try_finish` via `check_handshake_pubkey_hash`) before allowing any `PeerDB` write. Reject/discard replies that fail this check instead of writing them into `PeerDB`.

### Proof of Concept
Rust test plan (in `stackslib/src/net/tests/neighbors.rs` or a new walk-focused test):
1. Set up three `TestPeer`s: `victim` (the walker), `honest_relay` (gossips attacker as a neighbor), `attacker` (malicious listener), and pre-populate `victim`'s `PeerDB` with a legitimate `Neighbor` entry for a fourth address `known_good_addr` with `known_good_pubkey`.
2. Have `victim` walk to `honest_relay`, which advertises `attacker`'s real address via `GetNeighborsData`.
3. When `victim` handshakes with `attacker`, have `attacker`'s conversation logic build and sign (with a fresh random `Secp256k1PrivateKey`) a `HandshakeAcceptData` whose `handshake.addrbytes`/`handshake.port` equal `known_good_addr`'s fields (not attacker's own dialed address).
4. Drive `victim.network`'s walk state machine through `GetHandshakesBegin`/`GetHandshakesFinish` so `handle_neighbor_handshake_accept` processes the crafted `HandshakeAccept`.
5. Assert: `PeerDB::get_peer(victim.network.peerdb.conn(), network_id, &known_good_addr.addrbytes, known_good_addr.port).unwrap().unwrap().public_key != known_good_pubkey` and instead equals the attacker's freshly generated public key — demonstrating the silent overwrite at `stackslib/src/net/db.rs:1311-1313` (`PeerDB::update_peer`'s `UPDATE frontier ... WHERE addrbytes = ?13 AND port = ?14`).
