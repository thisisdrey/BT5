### Title
Unhealthy positions can be made permanently unliquidatable via the `maxLiquidable`/`debtFloorInUsd` interaction — a liveness panic in `Pool.liquidate` (contracts/Pool.sol)

### Summary
The external report describes a panic (RUSTSEC-2024-0399) reachable by unprivileged network input in a liveness-critical path (`Acceptor::accept`), permanently crashing the connection handler. The Metronome analog is a liveness panic of the same class in the liquidation path: for a range of unhealthy positions, **every** call to `Pool.liquidate` unconditionally reverts — repaying the full debt violates `maxLiquidable`, while repaying up to `maxLiquidable` leaves residual debt below `debtFloorInUsd`. The position can never be liquidated, and bad debt accrues to the protocol.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:541-596):

- Line 567-569: `if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert AmountGreaterThanMaxLiquidable();` — caps any single repayment to a fraction of total debt (deployed configs use values < 1e18, e.g. 50%).
- Lines 571-579: if `debtFloorInUsd > 0`, any repayment that leaves `_debtTokenBalance - amountToRepay_` worth less than the floor (but > 0) reverts with `RemainingDebtIsLowerThanTheFloor`.

So for a position whose total debt `D` (in USD) satisfies `debtFloorInUsd > D·(1 - maxLiquidable)`, the two checks are mutually exclusive:

- `amountToRepay_ == D` (the only repayment that clears the floor check by leaving `_newDebtInUsd == 0`) → `D.wadDiv(D) = 1e18 > maxLiquidable` → reverts.
- `amountToRepay_ <= D·maxLiquidable` → `D - amountToRepay_ ≥ D·(1 - maxLiquidable) > 0` and (for `D < debtFloorInUsd / (1 - maxLiquidable)` … precisely `D - amountToRepay_ < debtFloorInUsd` whenever `amountToRepay_ > D - debtFloorInUsd`) → reverts.

Concretely: with `debtFloorInUsd = $3,000` and `maxLiquidable = 0.5e18`, any position with debt between $3,000 and $6,000 cannot be liquidated at all — full repay trips the cap, partial repay trips the floor. The tests confirm each revert independently (`test/Pool.test.ts:409-421`, `:439-451`) but never test their simultaneous application. `DebtToken.repay` has the same floor check (contracts/DebtToken.sol:442-451), so third-party repayment cannot rescue the position either; the position's collateral cannot be seized by anyone.

### Impact Explanation
Liquidation is the solvency invariant for the protocol. An attacker deliberately opens a position sized into the dead zone (debt between the floor and `floor/(1-maxLiquidable)`), waits for normal price movement or contributes to the position going underwater, and the protocol has no mechanism to recover the collateral — the position becomes permanently unseizable bad debt. Once collateral value < debt, the shortfall is socialized across depositors/synthetic holders. Every `liquidate` call against such a position panics identically and unconditionally — the same "reachable panic kills the liveness-critical handler" structure as the rustls report. Additionally, `depositToken_.seize` inside `liquidate` transfers to the liquidator via `_transfer`, which calls `addToDepositTokensOfAccount`; a victim/liquidator whose token list is at `MAX_TOKENS_PER_USER` causes a second unconditional revert vector on the same function.

### Likelihood Explanation
- Reachable entirely by an unprivileged attacker: `deposit` + `issue` are public; the attacker picks debt size freely at open time.
- Requires only that governance set both `debtFloorInUsd > 0` and `maxLiquidable < 1e18` — both are deployed configurations on Optimism/Mainnet pools (`updateDebtFloor`/`updateMaxLiquidable` exist precisely because they are used).
- The trigger is ordinary price decay; same-transaction oracle manipulation is not required.
- The flaw is in protocol code logic (missing "allow full repay when capped repay would leave sub-floor dust" branch), not in a parameter choice itself.

### Recommendation
In `Pool.liquidate` (and equivalently in the `DebtToken.repay` floor check), permit the full-repayment escape: when `maxLiquidable`-capped repayment would leave residual debt below the floor, allow repaying the entire debt in one call. E.g. compute the cap as `min(amountToRepay_, debtBalance)` first, then only apply the floor check to genuinely partial repayments — or treat `_newDebtInUsd == 0` as satisfying both constraints by checking the cap against `min(1e18, floor/(D - floor))`. Alternatively, enforce at `issue`/`mint` time that `debt ≥ debtFloorInUsd / (1 - maxLiquidable)` so the dead zone is unreachable.

### Proof of Concept
Hardhat sketch (extends `test/Pool.test.ts` "liquidate" fixture):

```ts
// given: alice deposited MET, issued msETH; position is now unhealthy
await pool.updateMaxLiquidable(parseEther('0.5'))       // 50%
await pool.updateDebtFloor(toUSD('3000'))              // $3,000
// alice's debt ≈ $4,000 (1 msETH) → dead zone: $3,000 < $4,000 < $6,000
await masterOracle.updatePrice(met.address, toUSD('1')) // push position underwater

const debt = await msEthDebtToken.balanceOf(alice.address)

// full repay → capped
await expect(pool.connect(liquidator).liquidate(msEth.address, alice.address, debt, msdMET.address))
  .revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

// max-allowed repay → dust below floor
await expect(pool.connect(liquidator).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address))
  .revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

// No amount in (0, debt] clears both checks → position is permanently unliquidatable
```

A fork PoC can additionally show repeated calls over time failing while `accrueInterest` grows `balanceOf(alice)` — bad debt compounds, mirroring the unrecoverable panic-per-request behavior of the rustls `Acceptor` bug.
