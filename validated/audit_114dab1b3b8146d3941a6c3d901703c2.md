### Title
Unvalidated attachment content hash in `AttachmentsBatchStateContext::extend_with_attachments` lets a lying peer be treated as a successful, high-reliability source, starving honest peers and causing permanent BNS attachment resolution failure - (File: stackslib/src/net/atlas/download.rs)

### Summary
`get_prioritized_attachments_requests` (download.rs:404-478) admits any peer whose `/v2/attachments/inv` response has bit `1` at `(page_index, position_in_page)` as a `source` for a given `content_hash`, with no verification that the peer actually holds byte-matching data. When the actual `/v2/attachments/{content_hash}` fetch is performed, `extend_with_attachments` (download.rs:530-558) accepts any syntactically valid JSON response and bumps the peer's reliability score without ever checking `response.attachment.hash() == request.content_hash`. Because `AttachmentRequest::get_url()`/`get_most_reliable_source()` (download.rs:1073-1108) sends the request to only the single highest-scoring peer in `sources`, a malicious peer that repeatedly lies about having the attachment can inflate its own reliability score every round (fake "success"), be perpetually selected over an honest peer that actually has the data, and never deliver correct content — causing the batch to exhaust `max_attachment_retry_count` and be permanently dropped, per `stackslib/src/net/atlas/mod.rs`'s use of `AttachmentsBatch::bump_retry_count`/drop logic in `download.rs:187-205`.

### Finding Description
The claimed equality — "`inventory_bit(peer, page, index)==1` iff `peer.attachments[index].hash()==content_hash`" — is never enforced anywhere in the client:

- `get_prioritized_attachments_requests` (download.rs:434-458) only checks `search_page.inventory.get(position_in_page) == Some(&1)`, taken verbatim from `RPCGetAttachmentsInvRequestHandler::try_handle_request`'s peer-supplied `AttachmentPage.inventory`. It never fetches or verifies the actual bytes before adding the peer URL+`ReliabilityReport` to `sources` of the resulting `AttachmentRequest` (download.rs:467-472).
- The download step, `Requestable::get_url()` for `AttachmentRequest` (download.rs:1104-1108) and `get_most_reliable_source` (download.rs:1073-1080), only queries `.max_by_key(|(_, v)| v.score())` — i.e., a single URL, the peer currently believed most reliable — per round. Other sources in `sources` are never contacted in that round.
- Crucially, `extend_with_attachments` (download.rs:530-558) decodes the HTTP response via `decode_atlas_get_attachment()` and, on success, does:
  ```rust
  if let Ok(response) = response.decode_atlas_get_attachment() {
      self.attachments.insert(response.attachment);
      report.bump_successful_requests();
  } else {
      report.bump_failed_requests();
  }
  ```
  There is **no check that `response.attachment.hash() == request.content_hash`**. Any syntactically valid `GetAttachmentResponse` JSON — regardless of content — is treated as a "successful" request and rewards the responding peer's `ReliabilityReport` (`bump_successful_requests`).
- Only later, in the `Done` branch of `AttachmentsDownloadScheduler::make_progress` (download.rs:153-169), is `attachment.hash()` computed and used to look up matching `AttachmentInstance`s via `find_all_attachment_instances(&attachment.hash())` and to call `attachments_batch.resolve_attachment(&attachment.hash())`. If the malicious peer's payload doesn't hash to the originally-requested `content_hash`, no instance matches, so the batch entry for that `content_hash` is simply left unresolved for another retry round — but the malicious peer's reliability score has already been boosted by the bogus "success."

Exploit flow:
1. Attacker runs an ordinary, unprivileged P2P peer that an honest node includes in its Atlas peer set.
2. Attacker's node responds to `GET /v2/attachments/inv` (handled by `RPCGetAttachmentsInvRequestHandler::try_handle_request`) with an `AttachmentPage.inventory` bit of `1` at the position for the target `content_hash`, despite not holding the actual data.
3. The victim's `get_prioritized_attachments_requests` adds the attacker as a `source`.
4. When `AttachmentRequest`'s round picks the attacker (initially by luck, or by having contributed a fabricated favorable `ReliabilityReport` history), the attacker's server for `GET /v2/attachments/{content_hash}` returns arbitrary well-formed JSON (`{"attachment": {"content": "..."}}`) with content that does **not** hash to `content_hash`.
5. `extend_with_attachments` blindly calls `bump_successful_requests()` for the attacker, inflating its score, while the batch entry remains unresolved.
6. On every retry round, the attacker (now with an inflated score relative to the honest peer, which may have a normal or degraded score due to network jitter/latency) keeps being selected as `get_most_reliable_source`, repeating steps 4-5.
7. After `connection_options.max_attachment_retry_count` retries, `AttachmentsDownloadScheduler::make_progress` (download.rs:187-205) drops the batch permanently — even though a byte-correct attachment was available the whole time on another, honest peer that was never queried because it never won `get_most_reliable_source`.

### Impact Explanation
This is a denial-of-service against BNS zonefile/attachment resolution for a confirmed, on-chain name operation: nodes that rely on the Atlas subsystem to fetch zonefiles will never resolve the attachment, serving no data for a valid, committed transaction even though a fully honest, byte-correct copy of the data exists elsewhere on the network. Repeated per round with zero cost (attacker just returns fabricated JSON), and the false "successful request" credit means the attacker's `ReliabilityReport` — which directly orders both the `AttachmentsInventoryRequest` priority queue and `AttachmentRequest::get_most_reliable_source` (download.rs:1088-1096) — keeps winning selection over honest peers, making the starvation self-reinforcing rather than probabilistic. This matches the "High" category: serving no data (a denial) for a confirmed name operation, and steering resolution away from canonical/correct data via forged/false inventory claims that the codebase never independently verifies.

### Likelihood Explanation
No privileged role, secret, or config value is required: any peer that can complete a normal P2P/RPC handshake and respond to `/v2/attachments/inv` and `/v2/attachments/{hash}` requests can mount this attack. It requires only that the victim's peer set include the attacker's URL (a default and expected part of Atlas discovery) and that an honest peer's `ReliabilityReport` score not permanently dominate the attacker's (achievable over multiple rounds by the attacker cheaply farming fake "successes"). The precondition "when the honest attachment is unavailable elsewhere" as literally stated in the question is not required — the flaw is broader: even when the honest attachment IS available elsewhere, this bug allows the attacker to be preferentially and repeatedly selected instead, due to unchecked reliability inflation, which is a stronger and more directly demonstrable finding than the literal question's framing.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558), after `decode_atlas_get_attachment()` succeeds, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments` and before calling `report.bump_successful_requests()`; on mismatch, treat it as a `bump_failed_requests()` (or a stronger penalty / disconnect / blocklist for the offending peer, since a hash mismatch is a stronger integrity violation than a mere failed request). Additionally, consider having `AttachmentRequest` fall over to the next-most-reliable source within the same round when the top pick returns a hash-mismatched or otherwise invalid payload, rather than waiting for a full batch retry cycle.

### Proof of Concept
Add a Rust test in `stackslib/src/net/atlas/tests.rs` alongside `test_downloader_context_attachment_requests`:
1. Build an `AttachmentsBatchStateContext` with two peers, `honest` and `malicious`, and one missing `AttachmentInstance` with `content_hash = attachment_1.hash()`.
2. Use `new_attachments_inventory_response` to have both peers report bit `1` for `attachment_1`'s index (both become `sources`).
3. Call `get_prioritized_attachments_requests()`; confirm both peers are present in `request.sources`, and (since malicious hasn't had score bumped yet) note which one `get_most_reliable_source()` would return — force `malicious`'s `ReliabilityReport` via `new_peers` to have a higher `(req_sent, req_success)` ratio than `honest`.
4. Simulate `BatchedRequestsResult::succeeded.insert(request, Some(fake_response))` where `fake_response` decodes via `decode_atlas_get_attachment()` to an `Attachment` whose `.hash()` does **not** equal `attachment_1.hash()` (e.g., a different byte string).
5. Call `context.extend_with_attachments(&mut results)` and assert (a) `context.peers.get(&malicious_url).unwrap()` shows `bump_successful_requests` was applied (score increased) — demonstrating the missing-hash-check bug directly — and (b) that `attachments_batch.resolve_attachment(&attachment_1.hash())` was never triggered for this content hash, i.e. the instance remains in `attachments_batch.attachments_instances`, proving no re-verification against a second (honest) source occurred and the false "success" credit was still granted to the lying peer.
