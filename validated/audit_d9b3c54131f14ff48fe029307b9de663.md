### Title
Attacker can fill a victim's per-account token list with dust deposit tokens, DoS-ing new collateral deposits and debt issuance (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across the combined `debtTokensOfAccount` + `depositTokensOfAccount` sets (`contracts/Pool.sol:79`, `contracts/Pool.sol:143-148`). Both sets are populated as a side effect of balance changes: `DepositToken._mint` calls `pool.addToDepositTokensOfAccount` on a first-ever balance (`contracts/DepositToken.sol:485-488`) and `DepositToken._transfer` does the same for the recipient (`contracts/DepositToken.sol` `_transfer`). Because `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` (`contracts/DepositToken.sol:211-237`) and deposit tokens are freely transferable (`transfer`/`transferFrom`, only gated by `_revertIfLocked` on the *sender*), any unprivileged attacker can push up to 30 distinct dust deposit tokens onto a victim's account list. Once the list is full, `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`, which bubbles up and reverts `DepositToken.deposit`, `DepositToken.transfer`, `DebtToken.issue`, and `DebtToken.mint` (`contracts/DebtToken.sol:597-600`) whenever they would create a *new* token entry for that account.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokens + depositTokens >= 30` for the account (`contracts/Pool.sol:143-148`, `204-220`).
- An attacker can (a) call `depositToken.deposit(dustAmount, victim)` — `onBehalfOf_` is attacker-chosen and there is no opt-in or minimum-amount check, or (b) `depositToken.transfer(victim, 1)` — the recipient is never consulted. Both paths invoke `pool.addToDepositTokensOfAccount(victim)` on first balance.
- After 30 such insertions, the victim cannot: mint any new synthetic debt (`DebtToken._mint` → `addToDebtTokensOfAccount` reverts → `issue`/`mint` revert), deposit a collateral type they don't already hold, or receive transfers of a deposit token they don't already hold.
- The account-list entries are only removed when a balance returns to zero (`contracts/DepositToken.sol:459-462`, `contracts/DebtToken.sol:539-542`), so the victim must notice the griefing and send the dust away to recover.

### Impact Explanation
Availability/DoS analog to the MySQL Optimizer crash class: an unprivileged attacker cheaply and repeatedly breaks core protocol functionality for a targeted account. Concretely, the victim's ability to open or increase a debt position (`issue`, `SmartFarmingManager.leverage` via `DebtToken.mint`) is frozen, and top-up deposits of a not-yet-held collateral revert — temporarily freezing that collateral path. This is most damaging when the victim is a smart contract (vault, zap, leverage integrator) that cannot arbitrarily transfer the dust out, in which case the freeze can be effectively permanent. Attack cost is 30 dust deposits/transfers.

### Likelihood Explanation
Fully permissionless: `deposit(..., onBehalfOf_)` and `transfer` are public entry points reachable by any EOA (directly or via `Operator.execute`/gateways). No privileged role, oracle manipulation, or governance parameter is needed. The only prerequisites are that the pool lists enough distinct deposit tokens and that `isSwapActive`/pause flags don't matter (deposits and transfers are not gated by swap state). The check is a deliberate cap, but there is no consent mechanism or minimum deposit to prevent strangers from occupying slots.

### Recommendation
Make account-list membership opt-in or dust-resistant, e.g.:
- Require a minimum first-deposit amount in `DepositToken._mint`/`_transfer` before adding to `depositTokensOfAccount` (or add the entry lazily on `issue`/health-relevant paths only).
- Alternatively, only count tokens above a USD threshold in `debtPositionOf`/`depositOf` and cap *meaningful* positions, or track deposit/debt tokens in separate caps so dust collateral can't block debt issuance.
- At minimum, allow `deposit(..., onBehalfOf_)` to skip list insertion for zero-value-dust amounts and let recipients reject unsolicited transfers.

### Proof of Concept
Hardhat test sketch (run against the repo's existing `test/Pool.test.ts` harness where `pool`, `depositToken` list, and signers are already wired):

```ts
// attacker fills victim's account list with dust deposit tokens
const victim = bob.address;
const depositTokens = await pool.getDepositTokens(); // assume >= 30 listed collaterals
for (const dt of depositTokens.slice(0, 30)) {
  const token = await ethers.getContractAt('DepositToken', dt);
  await token.connect(attacker).deposit(1n, victim); // or transfer(victim, 1n) if attacker holds balance
}
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30);

// 1) victim cannot issue any new synthetic debt
await expect(
  msUsdDebtToken.connect(bob).issue(parseEther('1'), bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 2) victim cannot deposit a collateral type they don't already hold
const newDepositToken = /* any deposit token not in victim's dust set or re-check */
await expect(
  newDepositToken.connect(bob).deposit(parseEther('1'), bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Recovery is only possible if the victim (or a contract they control) can `transfer` the dust balances back to zero to trigger `removeFromDepositTokensOfAccount`.
