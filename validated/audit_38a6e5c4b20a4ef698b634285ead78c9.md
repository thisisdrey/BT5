### Title
Floating-point division-by-zero/overflow in unhardened Bancor exchange math silently mis-prices trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The CVE describes a floating-point exception in GPAC's Opus header parser caused by an unchecked denominator derived from untrusted input. `ExchangeProcessor` (the legacy/default Bancor-relay math used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`) performs the analogous unguarded floating-point division and `pow()` calls on values fully derived from an unprivileged user's transaction, with no validation that the denominators are non-zero or that intermediate results stay finite before being cast to `long`.

### Finding Description
`ExchangeProcessor.exchangeToSupply` computes `(double) quant / newBalance` where `newBalance = balance + quant`, and `ExchangeProcessor.exchangeFromSupply` computes `(double) supplyQuant / supply` after `supply -= supplyQuant`: [1](#0-0) 

Neither denominator is checked for zero, and neither the resulting `double` (which can become `Infinity`/`NaN`) nor the `(long)` cast of it is validated before being written back into exchange/account state: [2](#0-1) 

This is invoked from `ExchangeCapsule.transaction()`, which is reachable directly from an unprivileged, unpermissioned trader via `ExchangeTransactionActuator.execute`/`doValidate`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`: [3](#0-2) [4](#0-3) 

Critically, `ExchangeCapsule.transaction()` only rejects a negative resulting token balance when the newer `hardenedCalc` flag is enabled; the default/legacy path performs no such check: [5](#0-4) 

The project's own test suite confirms this exact bug class exists and had to be patched by a separate `SafeExchangeProcessor`, which explicitly guards against divide-by-zero (`BigDecimal` divide throws `ArithmeticException`) and overflow (`StrictMathWrapper.addExact`): [6](#0-5) [7](#0-6) 

`SafeExchangeProcessor` is only used when `allowHarden()`/`AllowHardenExchangeCalculation` is enabled via a network parameter proposal (`ProposalUtil`/`DynamicPropertiesStore`), i.e. it is an opt-in hardening added after the fact — the plain `ExchangeProcessor` (unguarded `double` math) remains the code path exercised whenever this proposal has not been activated on a given chain/testnet, exactly the situation the CVE's "unchecked denominator from crafted input" bug class targets.

### Impact Explanation
Unlike C's `SIGFPE`, Java integer division by zero throws, but *floating-point* division by zero does not — it silently yields `Infinity`/`NaN`. Casting such a value to `long` yields `Long.MAX_VALUE`/`Long.MIN_VALUE`/`0` with no exception raised. Because these values are then written directly into `ExchangeCapsule`/`AccountCapsule` balances (`anotherTokenQuant`), a trade that manages to drive `newBalance` (or `supply`) to (or through) zero can mint an attacker-controlled, effectively unbacked amount of TRX or TRC10 tokens, or corrupt the exchange pool's balances such that other unrelated node computations (any subsequent trade against the same pool) behave unpredictably. This maps to the "unbacked balance" / "theft of funds" impact class in scope.

### Likelihood Explanation
`firstTokenBalance`/`secondTokenBalance` are validated to be non-zero and the request quant must be `> 0`, so hitting `newBalance == 0` requires that a token balance in the exchange has first been driven negative by an earlier trade — something the legacy (non-hardened) path does not prevent, since the negative-balance guard in `ExchangeCapsule.transaction()` is gated behind `hardenedCalc`. Reaching the precise zero/overflow boundary requires careful selection of quant/balance ratios and is not a trivial single-transaction PoC to fully validate without live execution; this is flagged as the main open uncertainty. Reachability of the vulnerable arithmetic itself (any signed, ordinary trader can call `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`) is confirmed and requires no special privilege.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based, exact-overflow-checked) the unconditional exchange math implementation instead of an opt-in hardening flag, or add explicit zero/finite checks in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` before performing the division and before casting the result to `long`, and enforce the non-negative-balance invariant in `ExchangeCapsule.transaction()` regardless of the `hardenedCalc` flag.

### Proof of Concept
Not fully reproduced end-to-end; conceptual PoC based on code inspection:
1. Issue two tokens and create an `Exchange` pair via `ExchangeCreateActuator`.
2. Using the legacy (non-hardened) path (`AllowHardenExchangeCalculation` not activated), submit a sequence of `ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions crafted so that the computed `anotherTokenQuant` (via `ExchangeProcessor`, unguarded `double` math) exceeds the counterpart token balance, driving one side of `ExchangeCapsule`'s balance negative (`ExchangeCapsule.java:140-162`, no check outside `hardenedCalc`).
3. Submit a further trade selecting the token whose balance is now negative with a `quant` equal in magnitude, forcing `newBalance = balance + quant == 0` in `ExchangeProcessor.exchangeToSupply` (`ExchangeProcessor.java:19-23`), producing `Infinity`/`NaN` and a `(long)` cast result that credits an attacker-controlled amount of the paired asset.

This last step could not be verified with a concrete numeric example within the available static analysis; a Devin session with test execution capability would be needed to confirm the exact quant/balance values that trigger the zero denominator and observe the resulting balance corruption in the JVM.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
