### Title
Unattributed storage growth: dust `DepositToken` transfers permanently fill a victim's `depositTokensOfAccount` list and freeze their ability to add collateral - ([File: contracts/Pool.sol])

### Summary
Analogous to CVE-2022-0742 (repeated cheap allocations of non-freeable resources leading to resource exhaustion), any unprivileged account can force entries into another account's `depositTokensOfAccount` set by transferring dust amounts of `DepositToken`s. `Pool.addToDepositTokensOfAccount` reverts once the combined `debtTokensOfAccount + depositTokensOfAccount` count reaches `MAX_TOKENS_PER_USER = 30`, so a victim whose set is filled cannot deposit new collateral, cannot receive deposit tokens (including via liquidation `seize` proceeds or `NativeTokenGateway.deposit` on their behalf), and — critically — cannot remove the dust entries while they carry debt because `_revertIfLocked`/`unlockedBalanceOf` blocks transferring out collateral locked against their position.

### Finding Description
`DepositToken._transfer` (also reached by `transfer`, `transferFrom`, `seize`, `deposit`→`_mint`) calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is 0. The recipient never consents — anyone holding an unlocked positive balance can send 1 wei of each `DepositToken` to the victim. [1](#0-0) [2](#0-1) [3](#0-2) 

Removal is only possible if the victim zeroes the balance (`_burn`/`_transfer` → `removeFromDepositTokensOfAccount`), but every outbound `transfer`/`withdraw` goes through `_revertIfLocked`, which consults `unlockedBalanceOf`. For a victim with `debtInUsd > 0`, unlocked balance is capped by `issuableInUsd / collateralFactor`; if the position is fully utilized the unlocked balance is ~0, so the dust cannot be moved out and the slots cannot be freed while the debt exists. [4](#0-3) [5](#0-4) 

The attacker can also continuously refill freed slots by front-running (dust transfers cost only gas + negligible underlying), making the exhaustion persistent rather than one-shot — matching the "tiny repeated allocations the victim cannot free" structure of the ICMPv6 memory leak.

### Impact Explanation
Temporary-to-indefinite freezing of the victim's ability to increase collateral. Concretely:
- Victim near liquidation cannot `deposit` additional collateral to restore health → forced liquidation and loss of the liquidation fee / collateral discount.
- No one can deposit `onBehalfOf_` the victim or send them `DepositToken`s (any mint/transfer reverting inside `addToDepositTokensOfAccount` reverts the whole call).
- If the victim's debt makes their dust balance fully locked, the freeze persists until they repay debt — they cannot clear it themselves. This is a liveness break of the deposit/collateral-addition path, i.e., temporary freezing of funds/freeze of an account capability, with an economic loss path via forced liquidation.

### Likelihood Explanation
Requires only EOA-level actions: the attacker needs dust balances of each `DepositToken` in the pool (obtained by depositing minimal underlying themselves, possibly via `NativeTokenGateway.deposit` for the native-token wrapper) and then calls `transfer(victim, 1)` per token. Cost is bounded by the number of `DepositToken`s in the pool (≤ 30) and gas for ~30 cheap calls; the victim can be targeted repeatedly. No privileged role, oracle manipulation, or governance action is needed.

### Recommendation
Bound or make consensual the per-account set growth: e.g., only auto-add on `deposit`/`_mint` and require an opt-in flag (or skip `addToDepositTokensOfAccount` in `_transfer`/`seize` when recipient did not self-initiate), or let an account purge zero-value/dust entries via a permissionless `removeFromDepositTokensOfAccount` when balance is below a threshold. Alternatively raise the accounting granularity: track collateral in a fixed-size bitmap/allowlist of pool-registered tokens rather than a per-user enumerable set, so dust cannot exhaust the slot budget.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test sketch
// Attacker exhausts victim's token slots so victim can no longer deposit collateral.

function test_DustTransferFillsAccountSlots() public {
    // victim has an open debt position, fully utilizing collateral so
    // unlockedBalanceOf(victim) == 0 for all deposit tokens
    // (deposit collateral, mint max synth debt beforehand)

    address[] memory dTokens = pool.getDepositTokens(); // N deposit tokens in pool
    uint256 slotsNeeded = pool.MAX_TOKENS_PER_USER()
        - pool.getDebtTokensOfAccount(victim).length
        - pool.getDepositTokensOfAccount(victim).length;

    for (uint256 i; i < slotsNeeded && i < dTokens.length; ++i) {
        DepositToken dt = DepositToken(dTokens[i]);
        // attacker deposits dust of underlying to obtain a balance
        deal(address(dt.underlying()), attacker, 1);
        vm.startPrank(attacker);
        dt.underlying().approve(address(dt), 1);
        dt.deposit(1, attacker);
        // force an entry into victim's set
        dt.transfer(victim, 1);
        vm.stopPrank();
    }

    assertGe(
        pool.getDepositTokensOfAccount(victim).length
            + pool.getDebtTokensOfAccount(victim).length,
        pool.MAX_TOKENS_PER_USER()
    );

    // victim tries to deposit more collateral -> whole tx reverts
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    DepositToken(dTokens[0]).deposit(1e18, victim);

    // victim cannot remove dust entries: transfer reverts NotEnoughFreeBalance
    vm.prank(victim);
    vm.expectRevert(DepositToken.NotEnoughFreeBalance.selector);
    DepositToken(dTokens[0]).transfer(attacker, 1);
}
```
Steps: fork a chain with a live `Pool` (e.g., mainnet deployment), create victim position at max borrow, loop over registered deposit tokens depositing 1 wei and transferring to victim, then show `deposit` reverts with `UserReachedMaxTokens` and cleanup reverts with `NotEnoughFreeBalance`, demonstrating sustained resource exhaustion the victim cannot reclaim.
