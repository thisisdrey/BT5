### Title
DoS of `ExchangeWithdrawActuator` via Front-Run Balance-Ratio Manipulation in `ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator.doValidate()` computes the counter-asset amount to return to the pool creator using the *current* on-chain reserves of the `ExchangeCapsule` (`firstTokenBalance`/`secondTokenBalance`) and then enforces a strict precision check ("Not precise enough") comparing that freshly computed value against the creator-supplied `quant`. Because any unprivileged account can shift those same reserves in the same block via `ExchangeTransactionActuator` (a `broadcastable` `ExchangeTransactionContract`), an attacker can front-run a pending `ExchangeWithdrawContract` to alter the pool ratio just enough to make the precision check fail, reverting the creator's withdraw transaction. This mirrors the reported Sherlock issue where `LibTWAPOracle::setPool` reads live pool reserves and reverts on a strict invariant (`_reserve0 == _reserve1`) that an unprivileged actor can violate by front-running.

### Finding Description
`doValidate()` reads the exchange's live reserves and recomputes `anotherTokenQuant` from them: [1](#0-0) 
It then enforces a tight tolerance check against that same value: [2](#0-1) 
Because `firstTokenBalance`/`secondTokenBalance` are mutated by `ExchangeTransactionActuator.execute()` — which any account can invoke without being the pool creator — a griefer can submit an `ExchangeTransactionContract` immediately before a known/mempool-visible `ExchangeWithdrawContract` from the pool creator, shifting the ratio so the recomputed `anotherTokenQuant` no longer matches within the 0.01% tolerance encoded in the `Not precise enough` check, forcing the creator's withdraw to revert: [3](#0-2) 
This is analogous to the reported bug class: a state-changing, reserve-dependent invariant check that is evaluated against live state which any unprivileged transaction can manipulate ahead of the target transaction, causing repeated denial of service against a legitimate, otherwise-valid operation.

### Impact Explanation
A malicious actor who repeatedly front-runs the pool creator's `ExchangeWithdrawContract` with cheap `ExchangeTransactionContract` trades can indefinitely block the creator from withdrawing their liquidity from the exchange pool, effectively freezing the creator's funds inside the `ExchangeCapsule` for as long as the attacker is willing to pay trading fees to keep re-unbalancing the pool. Unlike a simple "insufficient balance" revert, this is a state derived from adversarial, attacker-controlled action rather than the victim's own mistake, and it can be sustained transaction after transaction.

### Likelihood Explanation
Exchange trading (`ExchangeTransactionContract`) is permissionless and cheap, requiring only ownership of one of the pool's two assets and payment of a small fee, so any attacker who wants to grief a specific pool creator's withdraw can watch the mempool for `ExchangeWithdrawContract` transactions referencing that pool and submit a counter-trade in the same block to desynchronize the ratio just enough to trip the 0.01% precision check.

### Recommendation
Avoid deriving the pass/fail invariant purely from state that is mutable by unprivileged third parties in the same block window. Options include: allowing the withdraw actuator to accept a caller-specified acceptable slippage/minimum-out parameter (similar to DEX `min_amount_out` patterns) rather than a fixed tight tolerance against a live-computed value, or widening/removing the "Not precise enough" precision requirement so minor pool-ratio changes caused by intervening trades do not cause deterministic reverts.

### Proof of Concept
1. Pool creator C holds an exchange with `firstTokenBalance = X`, `secondTokenBalance = Y`.
2. C broadcasts `ExchangeWithdrawContract(tokenId=first, quant=q)` computed off the currently observed ratio `X/Y`.
3. Attacker observes C's pending transaction and broadcasts `ExchangeTransactionContract` trading against the same pool with higher priority/gas ordering in the same block, shifting the pool to `X'`, `Y'`.
4. When C's withdraw executes, `doValidate()` recomputes `anotherTokenQuant` from `X'`, `Y'` instead of `X`, `Y` [4](#0-3) 
and the recomputed value diverges from C's original expectation beyond the 0.01% tolerance, causing `ContractValidateException("Not precise enough")` and reverting C's withdrawal, while the attacker's trade succeeds and can be repeated on every subsequent retry by C.

Note: I could not fully verify real-world economic feasibility (i.e., the exact quant of counter-trade needed to reliably trip the 0.01% band for arbitrary pool sizes) without running the actual arithmetic/fees in a live environment; a Devin session with test execution capability would be needed to confirm the precise numeric conditions and reproduce this end-to-end with a unit test similar to the existing `ExchangeWithdrawActuatorTest` suite.
