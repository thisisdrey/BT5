### Title
Attacker fills a victim's `depositTokensOfAccount`/`debtTokensOfAccount` set to `MAX_TOKENS_PER_USER` via dust deposits/transfers, blocking the victim from adding new collateral or debt positions - (File: contracts/Pool.sol)

### Summary
The bug class of CVE-2024-21134 is a low-privileged, easily-exploitable partial denial of service. The reachable analog in Metronome is the per-account token-set cap in `Pool`: `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` revert once `debt + deposit` token count reaches `MAX_TOKENS_PER_USER = 30`. [1](#0-0)  Because tokens are added to a *recipient's* set whenever they receive a balance for the first time — with no minimum amount — any unprivileged user can grief an arbitrary account by pushing dust of every pool deposit token into the victim's set until the cap is hit.

### Finding Description
Two unprivileged paths add entries to a victim's set:

1. `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary. `_mint(onBehalfOf_, _deposited)` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance is `0`, with `amount_ > 0` — a 1-wei underlying dust deposit suffices. [2](#0-1) [3](#0-2) 
2. `DepositToken.transfer`/`transferFrom`/`seize` do the same via `_transfer`, which adds the token to the recipient's set on a `0 → >0` balance change. [4](#0-3) 

Both paths funnel into `Pool.addToDepositTokensOfAccount`, gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens()` once the combined count hits 30. [5](#0-4)  There is no dust threshold, no opt-in, and the check counts `debt + deposit` tokens together, so filling deposit slots also blocks future `DebtToken.issue`/`mint` for the victim (which add to `debtTokensOfAccount`). The same technique applied to `feeCollector` as `onBehalfOf_`/recipient can push the fee collector toward the cap, after which any `deposit()` charging a nonzero `depositFee` reverts inside `_mint(_pool.feeCollector(), _fee)`. [6](#0-5) 

### Impact Explanation
Once the victim's set is full: (a) any `deposit()` of a collateral type the victim doesn't already hold reverts, (b) any incoming `transfer`/`seize` of a new deposit token to the victim reverts, and (c) issuing a *new* debt token reverts. The victim cannot diversify collateral or open new debt positions; if their position is unhealthy and their only held collateral is insufficient, they cannot add a different collateral to restore health and will be liquidated. The invariant broken is liveness/availability of core protocol functions for a targeted account — matching the CVE's "partial DOS" availability impact. The attack is fully unprivileged: the attacker only needs dust amounts of each listed underlying and standard `deposit`/`transfer` calls.

### Likelihood Explanation
Feasibility depends on the deployed pool listing enough deposit + debt tokens for the attacker to approach 30 distinct entries; with few listed collaterals the cap can't be reached. Attack cost is only dust of each underlying plus gas. Mitigating factors: the victim can recover by transferring dust balances out (each `0` balance triggers `removeFromDepositTokensOfAccount`), so the freeze is temporary, and existing collateral remains withdrawable. No privileged role, oracle manipulation, or governance action is required on the attacker's side; `whenNotPaused`, `nonReentrant`, and `SynthContext` checks do not prevent it.

### Recommendation
Enforce a minimum first-deposit/transfer amount before registering a token in `depositTokensOfAccount`/`debtTokensOfAccount`, or only add tokens on `deposit`/`issue` initiated by the account owner (or via `SynthContext._msgSender()`), not on permissionless inbound transfers/`onBehalfOf_` deposits. Alternatively, cap `MAX_TOKENS_PER_USER` accounting to tokens the account explicitly opted into, and exempt the `feeCollector` from the per-account cap since it is force-fed fee mints on every deposit.

  // path A: deposit dust on behalf of victim
  await dt.connect(attacker).deposit(1, victim.address);

await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address) // or attacker depositing on behalf
