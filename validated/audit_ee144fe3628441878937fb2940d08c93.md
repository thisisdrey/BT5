### Title
Atlas attachment downloader stores peer-supplied attachment content without verifying it matches the requested content hash - (File: stackslib/src/net/atlas/download.rs)

### Summary
The Ollama advisory is about accepting a caller-supplied digest without validating its format/length before using it to address a resource, letting the caller substitute wrong or malicious content for what should be identified by a specific, verified digest. The Atlas attachment sync pipeline in this repo has the same class of flaw: the code fetches an `Attachment` from a remote peer keyed by a specific requested `content_hash` (a `Hash160`), but never checks that the returned data actually hashes to that requested value before accepting and persisting it.

### Finding Description
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest` carrying an expected `content_hash` [1](#0-0) . When the response comes back, `extend_with_attachments` decodes it and inserts the returned `Attachment` into `self.attachments` with **no comparison against the `content_hash` that was originally requested**: [2](#0-1) 

Later, in the `Done` state of `run()`, every attachment collected this way is looked up and persisted using `attachment.hash()` — i.e., the hash of whatever bytes the peer actually sent — rather than the hash that was requested: [3](#0-2) 

This breaks the intended equality "served content digest == requested/expected content digest." A malicious or compromised peer that is asked for attachment `X` (hash `H`) can instead return arbitrary content `Y` (hash `H' != H`). The code accepts `Y`, computes its own `H'`, and calls `atlasdb.insert_instantiated_attachment(&attachment)` unconditionally, writing `Y` into local persistent state — without ever verifying it corresponds to the `AttachmentInstance`/content hash that triggered the download in the first place. The downstream `/v2/attachments/{hash}` handler [4](#0-3)  only enforces a syntactic hex-length regex on the *query* hash, and AtlasDB storage/retrieval both key strictly by `content_hash` — but nothing prevents an unrelated, attacker-chosen blob from being unauthenticated-ly written into `AtlasDB` in the first place via this download path, since no check ties the stored bytes back to any legitimate on-chain `AttachmentInstance.content_hash`.

### Impact Explanation
This allows any remote, unprivileged peer serving Atlas attachment content to cause a node to write arbitrary attacker-controlled data into its `AtlasDB` (unauthenticated write to state) whenever the node requests an attachment. This falls into the "Critical - unauthenticated/unauthorized write to state" category defined by the validation rules.

### Likelihood Explanation
Any node that runs Atlas sync and requests attachments from a set of peers (as determined by `get_prioritized_attachments_requests`) is subject to this; an attacker only needs to answer an outbound attachment-fetch HTTP request with mismatched content, which requires no authentication, no signature, and no special privilege — merely acting as (or spoofing) one of the `hint_replicas`/discovered peers serving `/v2/attachments/{hash}`.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; reject and treat as a failed/faulty peer response otherwise. Also enforce `AtlasConfig::attachments_max_size` on the downloaded content size before accepting it.

### Proof of Concept
1. Node N processes a block establishing an `AttachmentInstance` with `content_hash = H` for a BNS zonefile.
2. N enqueues an `AttachmentRequest{content_hash: H, ...}` and sends `GET /v2/attachments/{H}` to a peer P (which could be any peer returned by `get_outbound_sync_peers`/`hint_replicas`).
3. Malicious P responds 200 OK with `Attachment{content: Y}` where `Hash160::from_data(Y) = H' != H`.
4. `extend_with_attachments` inserts `Attachment{content: Y}` into `context.attachments` without checking `H' == H` [5](#0-4) .
5. In `run()`'s `Done` branch, `network.atlasdb.insert_instantiated_attachment(&attachment)` is called unconditionally, persisting `Y` in `AtlasDB` keyed by `H'` — content that was never authenticated by, nor tied to, any chain-confirmed `AttachmentInstance` [6](#0-5) .

Note: I was unable to inspect the full `download.rs` file (truncated beyond line 1000) or `insert_instantiated_attachment`'s implementation in `atlas/db.rs`, so I could not fully confirm whether any size cap (`attachments_max_size`) is enforced elsewhere on this exact path; a Devin session with full file access would be needed to double check that detail before finalizing a fix.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

/// Decode the HTTP request
impl HttpRequest for RPCGetAttachmentRequestHandler {
    fn verb(&self) -> &'static str {
        "GET"
    }

    fn path_regex(&self) -> Regex {
        Regex::new(r#"^/v2/attachments/(?P<attachment_hash>[0-9a-f]{40})$"#).unwrap()
    }

    fn metrics_identifier(&self) -> &str {
        "/v2/attachments/:hash"
    }

    /// Try to decode this request.
    /// There's nothing to load here, so just make sure the request is well-formed.
    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        captures: &Captures,
        query: Option<&str>,
        _body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        if preamble.get_content_length() != 0 {
            return Err(Error::DecodeError(
                "Invalid Http request: expected 0-length body".to_string(),
            ));
        }

        let attachment_hash_str = captures
            .name("attachment_hash")
            .ok_or(Error::DecodeError(
                "Failed to match path to attachment_hash group".to_string(),
            ))?
            .as_str();

        self.attachment_hash = Some(
            Hash160::from_hex(attachment_hash_str)
                .map_err(|_| Error::DecodeError("Failed to decode `attachment_hash`".into()))?,
        );

        Ok(HttpRequestContents::new().query_string(query))
    }
