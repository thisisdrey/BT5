Audit Report

## Title
`pallet_identity::set_username_for` signature has no chain/instance binding, enabling cross-chain signature replay — ([File: substrate/frame/identity/src/lib.rs])

## Summary
`set_username_for` verifies a pre-signed username authorization via `Self::validate_signature(&bounded_username[..], &s, &who)`, where the signed payload is only the raw `username.suffix` bytes with no genesis hash, chain ID, or pallet-instance discriminator. Because `pallet-identity` is deployed on multiple chains (e.g. `people-westend`, `people-kusama`) with independently-derived `AccountId`s, a signature a user creates to authorize a username grant on one chain can be replayed by any authority holding a matching suffix on a different chain/instance.

## Finding Description
In `set_username_for`, the caller (an authority) supplies `who`, `username`, and an optional `signature`. When present, the code verifies the signature against `bounded_username[..]` and the target account `who`, then immediately calls `Self::insert_username`, binding the username without further consent checks: [1](#0-0) 

The suffix is authority-specific and baked into the signed bytes (`username.suffix`), but nothing in the signed message binds it to a specific chain's genesis hash, a specific pallet instance, or the specific authority account executing the call — only `sender == properties.account_id` for that suffix is checked via `AuthorityOf::<T>::try_mutate`, which is a per-chain storage item, not a cryptographically bound value in the signature itself. Since `AccountId32` derivation from a public key is chain-independent, and `pallet-identity` with `set_username_for` is deployed identically (or near-identically) across multiple runtimes, the identical signed message + signer public key pair validates true on any deployment where an authority happens to hold the same suffix string. This is confirmed directly in the code: the only inputs to `validate_signature` are the username bytes and the target account, with no domain separator akin to EIP-712's `chainId`/`verifyingContract` used elsewhere in this repo's `permit` pallet: [2](#0-1) 

## Impact Explanation
This allows an authority on chain B to consume a signature intended for chain A's authority and unilaterally bind a username to the victim account on chain B, without the victim's chain-B-specific consent. This is unauthorized state mutation via a mis-bound signature acceptance, and fits the "forged or mis-bound proof or state acceptance" impact category. The impact is bounded to identity/username binding state (not fund theft or consensus safety), and removal requires authority/root action (`unbind_username`/`kill_username`), making it a persistent unwanted state change for the victim, though it does not directly cause loss of funds or take down a chain.

## Likelihood Explanation
Exploitation requires an attacker to both know a target's off-chain username signature (plausible since these are shared publicly to authorities for countersigning) and control an authority slot for a matching suffix on a different chain/instance — a role reachable by any ordinary participant able to register a suffix, not a privileged governance action. No validator/relayer compromise or leaked key is required.

## Recommendation
Bind the signed payload to chain-specific and authority-specific context — e.g., include the genesis hash (`frame_system::Pallet::<T>::block_hash(0)`), a pallet instance identifier, and/or the specific authority `AccountId` in the message that gets hashed and signed, similar to how the `permit` pallet folds `chainId` and `verifying_contract` into its EIP-712 domain separator.

## Proof of Concept
1. User signs `username_to_sign = b"alice.kyc"` off-chain, intending it for Authority A1 on chain A (suffix `kyc`).
2. Attacker controls Authority A2, also registered for suffix `kyc`, on chain B — a separate `pallet-identity` deployment with the same `AccountId32` derivation.
3. Attacker calls `set_username_for(origin = A2, who = alice, username = b"alice.kyc", signature = Some(sig), use_allocation)` on chain B.
4. `Self::validate_signature(&bounded_username[..], &s, &who)` succeeds — [3](#0-2)  — because the signed bytes and signer match exactly, with no chain-binding value ever included in the message, resulting in `insert_username` binding the username to Alice's account on chain B without her chain-B-specific consent.
