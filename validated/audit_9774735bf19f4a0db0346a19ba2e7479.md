### Title
Handshake identity re-keying without proof of ownership of the new public key - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_handshake` only verifies the handshake's signature against the claimed `node_public_key` when the conversation does not yet have a public key (`self.connection.get_public_key() == None`). Once a peer already has an established public key `X`, a second `Handshake` message on the same connection is accepted as long as it is signed by `X` (i.e. `authenticated` via the existing key), but the `node_public_key` field inside the payload — which can be set to an arbitrary key `Y` the attacker does not own — is never checked against the message's actual signer. `update_from_handshake_data` then unconditionally calls `self.connection.set_public_key(Some(Y))`, and for outbound conversations the change is persisted into `PeerDB` via `Neighbor::load_and_update`/`save_update`, re-keying the neighbor entry to a key never proven to be controlled by the attacker.

### Finding Description
The broken invariant is: *"the public key bound to a `NeighborKey` (addrbytes, port) must be the key that most recently proved knowledge of the corresponding private key."*

Trace:
1. `validate_handshake` (stackslib/src/net/chat.rs:1047-1127):
   - `None` branch (first handshake): calls `message.verify_secp256k1(&handshake_data.node_public_key)`, so `Y` must actually sign the message the first time.
   - `Some(_)` branch (already-established key `X`): only checks outbound address/port equality — `message.verify_secp256k1` is **never called against `handshake_data.node_public_key`** here. The message only needs to satisfy whatever generic `authenticated` signature check exists at the higher-level message dispatch, which is checked against the *current* known key `X`, not against the new key `Y` embedded in the payload.
2. `handle_handshake` (stackslib/src/net/chat.rs:1214-1333) calls `validate_handshake`, then unconditionally calls `self.update_from_handshake_data(&message.preamble, &handshake_data)`.
3. `update_from_handshake_data` (stackslib/src/net/chat.rs:1131-1167) computes `pubk` from the **unverified** payload field `handshake_data.node_public_key`, compares to `cur_pubk` (`X`), sets `updated = true` if different, and unconditionally calls `self.connection.set_public_key(Some(pubk.clone()))` — with no proof that the attacker controls the private key for `pubk` (`Y`).
4. If `self.stats.outbound` is true, `handle_handshake` (stackslib/src/net/chat.rs:1275-1295) persists this into `PeerDB`: `Neighbor::load_and_update(...)` followed by `neighbor.save_update(&tx, None)`, re-keying the stored neighbor record for that `NeighborKey` to `Y`.

Attacker's exact message: after completing a legitimate handshake as `X` (owning `X`'s private key), the attacker sends a second `Handshake` message on the same TCP connection, still signed by `X` (so it passes whatever session-level authentication gate exists), but with the `HandshakeData.node_public_key` field set to an arbitrary `Y` for which the attacker need not know the private key at all. Because the `Some(_)` branch of `validate_handshake` never checks the signature against the newly-claimed key, this forged identity is accepted, and the connection/PeerDB record is silently re-keyed to `Y`.

Existing guards fail because the code assumes that once a key is established, revalidation is unnecessary beyond an address check, but it never re-derives which key actually signed the *specific* payload field being adopted.

### Impact Explanation
This allows an attacker to hijack the recorded on-disk identity (`PeerDB` neighbor entry keyed by `NeighborKey`) of a peer they control the network address for, re-keying it to an arbitrary public key without proving ownership of that key's private key. This breaks the peer-identity invariant used throughout the P2P layer (peer authentication, StackerDB replication trust, and neighbor-walk logic that treats `(addr,port) -> pubkey` as authenticated). This is an unauthenticated write to persisted network state (PeerDB) and corrupts the node's view of peer identity, matching the "unauthenticated/unauthorized write to state" Critical category.

### Likelihood Explanation
Preconditions: attacker must first complete a legitimate handshake with the target as key `X` (trivial — a normal, unprivileged handshake, no secret required), then send a second `Handshake` message on the same connection. This requires only the ability to connect and send arbitrary P2P bytes — no privileged role, no config secret. It is repeatable per-connection and per-neighbor. For outbound conversations (the target dialed this peer), the persistence to `PeerDB` also triggers.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, always verify `message.verify_secp256k1(&handshake_data.node_public_key)` regardless of whether a current key is already set, so that any claimed `node_public_key` (old or new) must be proven by the message's own signature before `update_from_handshake_data` is allowed to treat it as authoritative. Only allow re-keying if the new key actually produced the signature on the re-key message.

### Proof of Concept
Rust net test in `stackslib/src/net/chat.rs` tests module:
1. Set up a `ConversationP2P` between two `LocalPeer`s using `Secp256k1PrivateKey` `k1` for peer `X`.
2. Perform `convo_handshake` (or equivalent helper) so `self.connection.get_public_key() == Some(X)`.
3. Craft a second `StacksMessage` with `StacksMessageType::Handshake(HandshakeData { node_public_key: Y_pub, .. })` where `Y_pub` corresponds to a *different* `Secp256k1PrivateKey` `k2`, but **sign the message with `k1`** (i.e., call `sign_message`/`sign_p2p` using `k1`, not `k2`).
4. Feed the message into `validate_handshake` / `handle_handshake`, and assert it returns `Ok(...)` without error (no `net_error::InvalidMessage` for unverified `Y_pub`).
5. Assert `self.connection.get_public_key() == Some(Y_pub)` after `update_from_handshake_data`, proving the connection was re-keyed to a key never proven to be controlled by the attacker.
6. For the outbound persistence path, assert via `PeerDB`/`Neighbor::load_and_update` that the neighbor record for the `NeighborKey` now stores `Y_pub` instead of `X_pub`.
