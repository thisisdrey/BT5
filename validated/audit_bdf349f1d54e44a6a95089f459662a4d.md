### Title
`RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` can drive global resource-weight totals negative, corrupting global bandwidth/energy accounting - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
The Sherlock report describes `FlatcoinVault.settleFundingFees()` allowing `marginDepositedTotal`, a value that must always stay non-negative, to be pushed negative and mis-cast, corrupting a core global accounting invariant used throughout the protocol. The java-tron analog is the pair of code paths that update the same persisted global counters (`TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, `TOTAL_TRON_POWER_WEIGHT`) used to compute every account's bandwidth/energy limits: one path (legacy actuators via `DynamicPropertiesStore`) clamps the result to `0`, while the other path (TVM native-contract/precompile freeze/unfreeze/cancel-unfreeze processors via `RepositoryImpl`) does not, allowing the shared global counters to go negative and corrupt resource-limit math for every account on the chain.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` (used by the classic `FreezeBalanceActuator`/`UnfreezeBalanceActuator` path) explicitly guards against negative totals: [1](#0-0) 

However `RepositoryImpl` — which is the `Repository` implementation used by the TVM native-contract processors reachable from smart-contract precompile calls (`freezeBalanceV2`, `unfreezeBalanceV2`, `cancelAllUnfreezeV2`, legacy `freezeBalance`/`unfreezeBalance` opcodes) — implements the exact same methods with **no clamping at all**: [2](#0-1) 

Both code paths read and write the *same* underlying persisted keys (`TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, `TOTAL_TRON_POWER_WEIGHT`), so the invariant "total weight ≥ 0" that one path tries to enforce can be bypassed by driving the counter down through the other, unguarded path. This mirrors the root cause in the Sherlock report: a shared, security-critical global accounting field is decremented on one path with proper bounds checking and on another path without it.

These processors are directly reachable from TVM opcode execution triggered by any contract call (see `OperationActions`/`Program` native-contract dispatch for `freezeBalanceV2Action`, `unfreezeBalanceV2Action`, `cancelAllUnfreezeV2Action`), i.e. by any unprivileged transaction that invokes a smart contract performing these operations: [3](#0-2) [4](#0-3) [5](#0-4) 

The downstream consumer of these totals, `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`, divides by `totalEnergyWeight`/`totalNetWeight` and only asserts (a no-op in production JVMs, which run without `-ea`) that the value is positive: [6](#0-5) [7](#0-6) 

If the shared total is negative, this division produces negative or otherwise corrupted resource-limit values for every account whose bandwidth/energy limit is calculated from it — a chain-wide accounting corruption, not an isolated per-account bug.

### Impact Explanation
Because `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT`/`TOTAL_TRON_POWER_WEIGHT` feed directly into `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`, which determine how much free bandwidth/energy every account on the network is entitled to, corrupting this single global value has network-wide effect: a negative divisor flips the sign of every account's computed resource limit, which can grant unbounded (or negative/zero) energy and bandwidth allowances depending on how the corrupted value propagates through `getAccountLeftEnergyFromFreeze`/`BandwidthProcessor`, effectively breaking the resource-accounting invariant the whole staking/freeze system relies on. This is analogous in class and severity to the original report: a single global accounting field that must stay non-negative is silently corrupted through an unguarded arithmetic path, breaking core protocol accounting used by every subsequent transaction.

### Likelihood Explanation
Both code paths are reachable by ordinary users: the legacy path via `FreezeBalanceContract`/`UnfreezeBalanceContract` transactions, and the unguarded path via TVM smart-contract calls to the `freezeBalanceV2`/`unfreezeBalanceV2`/`cancelAllUnfreezeV2` native-contract opcodes (available to any deployed contract). No special privileges are required — only sufficient TRX to freeze/unfreeze and a contract making the calls repeatedly to accumulate rounding/negative deltas against the shared global counter.

### Recommendation
Apply the same `max(0, total, disableJavaLangMath())` (or equivalent) clamp used in `DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` to the corresponding methods in `RepositoryImpl` (`actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java` lines 1196-1217), and in `ContractState.java` if it implements the same interface, so that both code paths enforce the "total weight ≥ 0" invariant identically regardless of whether the freeze/unfreeze operation originated from a normal transaction or from a TVM contract call.

### Proof of Concept
1. An attacker deploys a contract that calls the TVM native precompile for `unfreezeBalanceV2`/`cancelAllUnfreezeV2` in a sequence (freeze small amounts across many accounts/cycles, then unfreeze) so that `RepositoryImpl.addTotalNetWeight(newNetWeight - oldNetWeight)` is invoked with a net negative delta that is not clamped (unlike the actuator path).
2. Because `RepositoryImpl.addTotalNetWeight` (`actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java:1196-1202`) performs `totalNetWeight += amount; saveTotalNetWeight(totalNetWeight);` with no floor at `0`, repeated calls can drive the persisted `TOTAL_NET_WEIGHT` value negative.
3. Subsequent calls to `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` for any account divide by this now-negative shared total, producing corrupted (negative or wildly incorrect) resource limits for every account on the network, since `assert totalEnergyWeight > 0` is compiled out in production builds.

*Note: I was not able to fully trace every intermediate weight-delta computation across all freeze/unfreeze/delegate call combinations to confirm the exact minimal sequence of calls that produces a net-negative aggregate delta; this would require dynamic testing/fuzzing of the freeze/unfreeze/delegate state machine, which is beyond static code review, to establish the precise minimal PoC sequence.*

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        Common.ResourceCode freezeType,
                                        long unfreezeBalance,
                                        Repository repo) {
    switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        repo.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        repo.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;
    }
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
