Audit Report

## Title
Bridge close/reopen with a reused deterministic `LaneId` resets message nonces, allowing duplicate dispatch of an already-settled XCM message - (File: `bridges/modules/xcm-bridge-hub/src/lib.rs`)

## Summary
`pallet_xcm_bridge_hub::close_bridge` fully purges `InboundLaneData`/`OutboundLaneData` once queued messages are pruned and removes the `Bridges`/`LaneToBridge` entries. Since `LaneId` is deterministically derived from the two bridge endpoint locations and documented to "never change," a later `open_bridge`/`do_open_bridge` between the same endpoints recreates the lane at the identical `LaneId` with fresh, zeroed nonce counters via `LanesManager::create_inbound_lane`, resetting `last_delivered_nonce` to `0`.

## Finding Description
`close_bridge` in `bridges/modules/xcm-bridge-hub/src/lib.rs` (L408-412) calls `inbound_lane.purge()` / `outbound_lane.purge()` once the outbound queue is fully pruned, deleting the `InboundLanes`/`OutboundLanes` storage for that `LaneId` and removing `Bridges`/`LaneToBridge` entries. `LaneId` is calculated purely from the two endpoint locations (`bridges/modules/xcm-bridge-hub/src/lib.rs` L39-43), so `do_open_bridge` on a subsequent `open_bridge` between the same endpoints recreates the lane at the same `LaneId` via `LanesManager::create_inbound_lane`/`create_outbound_lane` (`bridges/modules/messages/src/lanes_manager.rs` L68-101), producing `InboundLaneData::default()` with `last_delivered_nonce = 0`. `InboundLane::receive_message` (`bridges/modules/messages/src/inbound_lane.rs` L186-212) only checks `Some(nonce) == data.last_delivered_nonce().checked_add(1)` per-lane, with no independent permanent replay ledger. ## Impact Explanation
This is a genuine design gap: the messages pallet has no cross-lifecycle replay protection beyond the per-lane `last_delivered_nonce`, and closing/reopening a bridge on the same `LaneId` legitimately resets that counter to zero, which could in principle allow re-acceptance of a message payload with a nonce that was already dispatched in a prior bridge lifetime.

However, I could not fully verify feasibility within this investigation. Successful exploitation requires the relayer to produce a valid storage/finality proof of the *old* delivered message anchored to a header that the target chain's finality pallet (e.g. GRANDPA/BEEFY bridge) still accepts as verifiable. Bridge finality pallets typically retain only a bounded/pruned set of recently-imported headers, and the source chain's outbound message storage for an already-confirmed message is itself pruned after delivery confirmation (via `receive_messages_delivery_proof`), meaning a fresh storage proof against current chain state would not reflect the stale message. I was not able to inspect `receive_messages_delivery_proof`, `pallet_bridge_grandpa`/`pallet_bridge_beefy` header-pruning logic, or `do_open_bridge`'s full body in this session to confirm whether a stale-but-still-importable header/proof window realistically exists, nor whether `close_bridge`/`open_bridge` are reachable by a genuinely unprivileged origin versus requiring bridge-owner-level XCM origin (`T::OpenBridgeOrigin`/`bridge_locations_from_origin`), which the pallet's own doc comments describe as "owner of this side of the bridge."

## Likelihood Explanation
Unresolved. The root trigger (`close_bridge` + `open_bridge`) is gated by an origin check (`bridge_locations_from_origin`) that I was unable to fully inspect in the time available; if this restricts the action to the bridge's own owning chain/origin (a self-governance action rather than an attacker-controlled path), the scenario may fall under "privileged governance/administrative action as root cause," which the rules require rejecting. Additionally, whether an unprivileged relayer can practically resubmit a stale delivery proof after such a reset depends on finality-pallet header retention and source-chain outbound-queue pruning behavior that I could not confirm from the files reviewed.

## Recommendation
N/A — could not confirm this rises to a validated, reachable exploit within the scope and time available; further investigation of `pallet_bridge_grandpa`/`pallet_bridge_beefy` header pruning, `receive_messages_delivery_proof` outbound pruning, and the exact origin requirements for `close_bridge`/`open_bridge` is needed before concluding this is exploitable by an unprivileged actor.

## Proof of Concept
Not confirmed — the proof-of-concept described in the claim assumes the relayer can still produce a valid finality/storage proof for a header from before bridge closure at the time of replay, which was not verified against the finality pallet's header-retention/pruning logic in this repository during this investigation.
