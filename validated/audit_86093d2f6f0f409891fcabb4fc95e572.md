### Title
Attacker can dust-fill a victim's per-account token list up to `MAX_TOKENS_PER_USER`, permanently/repeatedly reverting all future deposits, mints, and transfers of new collateral or debt token types for that account - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to CVE-2026-50251 (where an unprivileged attacker pushes a defensive counter to `unwanted-reply-threshold` to repeatedly trigger a defensive resource flush at will), an unprivileged attacker can push a victim's `debtTokensOfAccount + depositTokensOfAccount` counter to the hard `MAX_TOKENS_PER_USER = 30` threshold in `Pool.sol`. Once the limit is hit, `onlyIfAdditionWillNotReachMaxTokens` reverts (`UserReachedMaxTokens`) inside `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, which are called during any first receipt of a token. Every subsequent deposit, mint, transfer, seize, or debt issuance involving a token type the victim does not already hold reverts — a repeatable, low-cost liveness denial driven entirely by attacker-chosen inputs.

### Finding Description
`Pool.sol` maintains per-account enumerable sets (`MappedEnumerableSet`) of deposit and debt tokens and caps their combined size at `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`). The modifier `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:143-148`), and it guards `addToDepositTokensOfAccount` (`Pool.sol:216-220`) and `addToDebtTokensOfAccount` (`Pool.sol:204-208`).

`DepositToken._transfer` adds the token to the *recipient's* list whenever `balanceOf[recipient_] == 0 && amount_ > 0` (`DepositToken.sol:517-520`), and `DepositToken._mint` does the same on deposits (`DepositToken.sol:485-488`). Both are reachable by an unprivileged attacker:

- `deposit(amount_, onBehalfOf_)` is public, permissionless, and credits `onBehalfOf_` — the attacker can deposit 1-wei dust of each listed collateral directly into the victim's account (`DepositToken.sol:211-237`).
- Alternatively, `transfer(to_, amount_)` only checks the *sender's* unlocked balance (`DepositToken.sol:348-354`), so the attacker can deposit to themselves and push 1-wei dust transfers of every deposit-token type to the victim.

Each dust credit consumes one of the victim's 30 slots. Once the counter reaches the threshold:

- `deposit()` of any new collateral type reverts in `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.
- `transfer()` / `transferFrom()` of any token the victim doesn't already hold reverts the same way, so nobody can send the victim new collateral types.
- `DebtToken` issuance of a new synthetic (which calls `addToDebtTokensOfAccount`) reverts, blocking new debt positions.
- `seize()` during liquidation reverts if the seized token would be a new entry for the liquidator — self-inflicted, but the same revert path.

Like the CVE, the attacker only spends negligible resources (dust deposits/transfers of their own tokens), the counter increments are caused by attacker-controlled events the protocol misattributes as legitimate state growth, and the denial can be re-applied indefinitely: whenever the victim frees a slot (transferring a dust balance to zero triggers `removeFromDepositTokensOfAccount`, `DepositToken.sol:522-525`), the attacker refills it in the same or next transaction.

### Impact Explanation
Temporary freezing of funds / liveness denial on a per-victim basis:

- A victim whose position approaches liquidation cannot add collateral of a token type not already in their list — a realistic scenario when the victim's existing collateral type depreciates or they simply hold a different asset. Their deposits revert, forcing liquidation of otherwise rescuable positions.
- The victim cannot open a debt position in any new synthetic token.
- Incoming transfers of new deposit-token types revert, which can break integrations (zaps, SmartFarmingManager flows) targeting the victim.
- The victim can only recover by burning gas to zero-out a dust slot, and the attacker can immediately refill it — mirroring the CVE's "counter resets, attack loops forever" property.

No modifier stops this: `deposit`/`transfer` are unauthenticated, `whenNotPaused`/`nonReentrant` don't apply to the list accounting, `SynthContext` sender resolution doesn't change the recipient parameter, and `onlyIfAdditionWillNotReachMaxTokens` reverts the *whole* deposit/transfer rather than skipping the accounting — so the protective cap itself is the DoS mechanism.

### Likelihood Explanation
Feasibility depends on the deployed pool having enough listed tokens for an attacker to fill the victim's slots. On mainnet `Pool` there are many deposit tokens (WETH, WBTC, MET, msUSD, msETH, vaETH/vaBTC/vaUSDC family, OP, frxETH, etc. per `deployments/mainnet/`), and slots the victim already occupies (existing deposits + debt tokens) count toward the 30, reducing the attacker's required coverage. Cost per slot is a single dust deposit or transfer; with ~30 tokens the attack is dozens of cheap transactions, repeatable forever at gas cost only. Requires no privileged role, oracle manipulation, or spoofing — matching the unprivileged-attacker model. Success requires the victim to hold fewer than 30 distinct tokens (true for essentially all accounts).

### Recommendation
- Make list insertion non-reverting at the cap for *recipient-side* paths: e.g., in `_transfer`/`seize`, skip `addToDepositTokensOfAccount` when the recipient is at cap (the recipient can't be health-checked anyway without it, but dust balances are economically irrelevant), or move the revert to only the sender's own `deposit` call so a forced `onBehalfOf_` credit doesn't poison the victim.
- Alternatively, add an opt-in (account-level allowlist or `onBehalfOf_ == msg.sender` restriction in `deposit`) so third parties cannot force-credit new token types.
- Provide a public `removeFromDepositTokensOfAccount`/`removeFromDebtTokensOfAccount` escape allowing an account to purge zero-balance entries.

### Proof of Concept
```solidity
// Foundry fork test against deployed mainnet Pool/DepositTokens
function testDustFillVictimTokenList() public {
    IPool pool = IPool(POOL_ADDRESS);
    address victim = makeAddr("victim");
    IERC20 weth = IERC20(WETH);

    IDepositToken[] memory dts = allDepositTokensOf(pool); // enumerated from deployments/

    // Attacker fills victim's slots: for each deposit token,
    // deposit 1 wei on behalf of victim (or deposit to self then transfer dust).
    for (uint256 i; i < dts.length; ++i) {
        IERC20 underlying = dts[i].underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dts[i]), 1);
        dts[i].deposit(1, victim); // mints dust, adds to victim's list
        vm.stopPrank();
    }

    // Victim's list is now at MAX_TOKENS_PER_USER (30)
    // Any deposit of a token type not already in the list reverts:
    vm.startPrank(victim);
    deal(WETH, victim, 1 ether);
    weth.approve(address(wethDepositToken), 1 ether);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    wethDepositToken.deposit(1 ether, victim); // only if WETH token wasn't among the filled ones

    // Transfers of new token types to victim also revert:
    vm.startPrank(attacker);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newTypeDepositToken.transfer(victim, 1);
    vm.stopPrank();

    // Victim frees one slot by zeroing a dust balance...
    vm.prank(victim);
    dts[0].transfer(attacker, 1);
    // ...attacker immediately refills it
    vm.prank(attacker);
    dts[0].transfer(victim, 1);
}
```

Note: exact feasibility per chain depends on each pool's count of registered deposit tokens; on pools with fewer than 30 total token types the cap cannot be reached by deposits alone and this reduces to a non-issue there. This was verified against `Pool.sol:79,143-148,204-220` and `DepositToken.sol:348-354,485-488,517-525`; deployment token counts should be confirmed per target pool when writing the fork PoC.
