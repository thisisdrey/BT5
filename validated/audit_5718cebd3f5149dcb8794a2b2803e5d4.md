### Title
Unauthorized Permanent Freeze (and Upgrade) of Victim's Package via Ungated Object Transfer — (`aptos-move/framework/aptos-framework/sources/object_code_deployment.move`)

### Summary
`object_code_deployment::publish` creates a code object with `allow_ungated_transfer = true` and stores no `TransferRef`-based guard. Any third party can call `object::transfer` to seize ownership, then call `freeze_code_object` to irreversibly set `upgrade_policy = immutable` on every package in the victim's `PackageRegistry`, permanently stripping the original publisher of the ability to patch their own modules.

### Finding Description
`object_code_deployment::publish` calls `object::create_named_object`, which internally calls `create_object_internal` and initialises `ObjectCore.allow_ungated_transfer = true`. [5](#0-4) 

The `publish` function never calls `object::disable_ungated_transfer` or `object::set_untransferable`, so the code object remains freely transferable by anyone who holds it. [6](#0-5) 

`code::freeze_code_object` authorises the caller solely by checking `object::is_owner` against the **current** owner: [7](#0-6) 

Once the attacker transfers the object to themselves, they satisfy this check and the loop unconditionally overwrites every package's policy: [8](#0-7) 

The same ownership-only check in `object_code_deployment::upgrade` means the attacker can also replace the victim's bytecode with arbitrary code before or instead of freezing. [9](#0-8) 

### Impact Explanation
The `upgrade_policy` field in `PackageRegistry.packages` is a user-controlled on-chain asset. Setting it to `immutable` is explicitly irreversible (`EUPGRADE_IMMUTABLE` aborts any subsequent upgrade attempt). The victim permanently loses the ability to patch security vulnerabilities in their deployed modules. The secondary path — attacker calling `upgrade` with malicious bytecode — allows direct replacement of the victim's live module logic, which can affect every user and contract that depends on it.

### Likelihood Explanation
The precondition (`allow_ungated_transfer == true`) is the **default** for every object created by `object_code_deployment::publish`. No special configuration is required from the victim. The attacker needs only to know the code object address (derivable deterministically from the publisher address and sequence number) and submit two transactions: `object::transfer_call` then `object_code_deployment::freeze_code_object`.

### Recommendation
In `object_code_deployment::publish`, immediately disable ungated transfer on the newly created code object:

```move
let transfer_ref = constructor_ref.generate_transfer_ref();
object::disable_ungated_transfer(&transfer_ref);
// store transfer_ref in ManagingRefs if re-enabling is ever needed
```

Alternatively, store the original publisher address in `ManagingRefs` and add an explicit check in both `freeze_code_object` and `upgrade` that `signer::address_of(publisher)` matches the stored original publisher, not merely the current `ObjectCore.owner`.

### Proof of Concept
```
1. victim calls object_code_deployment::publish(victim_signer, metadata, code)
   → code_object created at deterministic address, allow_ungated_transfer = true

2. attacker calls object::transfer_call(attacker_signer, code_object_addr, attacker_addr)
   → verify_ungated_and_descendant passes (allow_ungated_transfer = true)
   → ObjectCore.owner = attacker_addr

3. attacker calls object_code_deployment::freeze_code_object(attacker_signer, code_object)
   → code::freeze_code_object: object::is_owner(code_object, attacker_addr) == true ✓
   → all packages.upgrade_policy set to immutable (policy = 2)

4. victim calls object_code_deployment::upgrade(victim_signer, new_metadata, new_code, code_object)
   → object::is_owner(code_object, victim_addr) == false → ENOT_CODE_OBJECT_OWNER abort
   (even if victim re-acquires ownership, check_upgradability aborts with EUPGRADE_IMMUTABLE)

Result: victim's package is permanently frozen; security patches are impossible.
```
