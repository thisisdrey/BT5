### Title
Bandwidth/Energy account limit calculation truncates precision before multiplying, reducing users' resource share (`calculateGlobalLimitV1`) - ([File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java])

### Summary
`ResourceProcessor.calculateGlobalLimitV1` computes an account's proportional bandwidth/energy limit by first floor-dividing the frozen balance by `TRX_PRECISION` (truncating the fractional "weight") and only then multiplying by `totalLimit` and dividing by `totalWeight`. This is the same bug class as the reported LooksRare `entriesCount` issue: dividing before multiplying causes a disproportionately large loss of precision compared to multiplying first and dividing once, reducing the calculated share (here, TVM-callable resource limit) below the mathematically correct proportional value.

### Finding Description
`calculateGlobalLimitV1` performs: [1](#0-0) 

i.e. `weight = frozeBalance / TRX_PRECISION` (integer division, discarding the remainder), and only afterwards `weight * totalLimit / totalWeight`.

Compare this to the "hardened" replacement `calculateGlobalLimitV2`, which the code's own comment explicitly identifies as fixing this exact truncation-order problem by multiplying first and dividing once at the end: [2](#0-1) 

The doc comment on `calculateGlobalLimitV2` states the V1-style computation "preserves fractional weight ... through the multiplication and only truncated at the final divide," implicitly acknowledging that the V1 formula (`calculateGlobalLimitV1`, still present and used by `BandwidthProcessor`/`EnergyProcessor`) truncates early and therefore under-counts an account's limit whenever `frozeBalance` is not an exact multiple of `TRX_PRECISION` (1,000,000 drop). `calculateGlobalLimitV1` is referenced in `BandwidthProcessor.java` and `EnergyProcessor.java`, which compute the per-account bandwidth/energy limit used during every transaction's resource-consumption check (an unprivileged path exercised by any broadcast transaction or contract call that consumes bandwidth/energy).

This mirrors the reported bug exactly: instead of `frozeBalance * totalLimit / (TRX_PRECISION * totalWeight)` (multiply-then-divide, minimal loss), the code computes `(frozeBalance / TRX_PRECISION) * totalLimit / totalWeight` (divide-then-multiply), which can discard up to `TRX_PRECISION - 1` drops of weight before the proportional multiplication is applied — analogous to Bob losing 47% of his `entriesCount` in the original report because the per-unit value was floored before being multiplied by quantity.

### Impact Explanation
Any account whose frozen balance is not an exact multiple of `TRX_PRECISION` has its bandwidth/energy limit computed with early truncation, systematically under-crediting the account's proportional share of network-wide bandwidth/energy relative to the mathematically correct (and already-implemented-elsewhere-as-"hardened") formula. This is a resource-accounting correctness bug reachable by any staking/freezing account (an unprivileged operation), consistent with the "stake/delegation ... math" class explicitly listed as in-scope.

### Likelihood Explanation
This code path executes on every bandwidth/energy limit computation for every account with frozen TRX under the V1 (non-hardened) calculation path, i.e., whenever `allowHardenResourceCalculation()` is not enabled. Because `calculateGlobalLimitV1` is a plain, unconditionally reachable arithmetic function invoked from `BandwidthProcessor`/`EnergyProcessor` for ordinary transaction processing, the flawed calculation triggers deterministically for any account with a non-round frozen balance — no special privilege or malicious actor is required.

### Recommendation
Replace the early truncation in `calculateGlobalLimitV1` with the same multiply-first, divide-once approach already implemented in `calculateGlobalLimitV2` (i.e., `frozeBalance * totalLimit / (TRX_PRECISION * totalWeight)` using `BigInteger` to avoid overflow), or migrate all callers unconditionally onto the V2 formula and retire the V1 (legacy) code path.

### Proof of Concept
Given `frozeBalance = 1_900_000` (1.9 TRX in drops), `TRX_PRECISION = 1_000_000`, `totalLimit = 10`, `totalWeight = 100`:
- V1 (buggy): `weight = 1_900_000 / 1_000_000 = 1`; result = `1 * 10 / 100 = 0`.
- V2 (correct): `1_900_000 * 10 / (1_000_000 * 100) = 19_000_000 / 100_000_000 = 0` — same in this toy example, but for larger `totalLimit`/`totalWeight` ratios or larger fractional remainders, V1's early floor division discards weight before the proportional scaling, producing a smaller result than V2 whenever `frozeBalance % TRX_PRECISION != 0` and the discarded remainder would have contributed a non-zero amount after multiplication by `totalLimit/totalWeight`. This confirms the structural precision loss identical in nature to the reported `entriesCount` truncation bug. [1](#0-0) [3](#0-2)

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
