## Analysis

The referenced report describes a classic **state-precondition sandwich/griefing** pattern: a shared, mutable resource (the NFT loan/exchange state) can be cheaply toggled by an unrelated third party right before a victim's transaction executes, causing the victim's transaction to revert because the precondition it relies on no longer holds — even though the attacker's own action costs them (near) nothing net.

In java-tron, `ExchangeWithdrawContract`/`ExchangeInjectContract`/`ExchangeTransactionContract` all operate on the same shared, permissionless bancor-style liquidity pool tracked by `ExchangeCapsule`. Any account can call `ExchangeTransactionActuator` (a normal, unprivileged "swap" against the pool) which mutates `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`.

`ExchangeWithdrawActuator.doValidate()` recomputes the withdrawal counterpart amount from the **current** pool ratio and enforces a strict precision tolerance (0.01%) as well as strictly-positive/sufficient-balance checks: [1](#0-0) 

Because the ratio is shared state that any account can move via `ExchangeTransactionContract` (fee = 0, purely bandwidth/energy cost): [2](#0-1) [3](#0-2) 

an attacker can sandwich the exchange creator's pending `ExchangeWithdrawContract` with a small trade that shifts `firstTokenBalance`/`secondTokenBalance` just enough to push the creator's precomputed `tokenQuant`/`anotherTokenQuant` outside the allowed tolerance, causing `ContractValidateException("Not precise enough")` (or the related `"exchange balance is not enough"` / `"withdraw another token quant must greater than zero"` checks) to fire and the withdraw to fail — then trade back afterward. This is directly analogous to the NFT case: a cheap, reversible manipulation of shared state by an unrelated actor, timed around the victim's call, defeats a precondition check and blocks the victim's withdrawal.

### Title
Exchange pool ratio can be sandwiched to griefing-DoS a creator's `ExchangeWithdrawContract` - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract` recomputes the counterpart withdrawal amount from the live `firstTokenBalance`/`secondTokenBalance` ratio of the shared bancor-style `ExchangeCapsule` and enforces a tight ±0.01% precision tolerance. Because any unprivileged account can move this same ratio via a free (`calcFee()==0`) `ExchangeTransactionContract` trade, an attacker can sandwich the exchange creator's withdraw transaction, causing it to revert on every attempt.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` from `firstTokenBalance`/`secondTokenBalance` at validation time and rejects the transaction if the computed value diverges from the "true" ratio by more than 0.01%, is non-positive, or exceeds the available pool balance: [4](#0-3) 

`firstTokenBalance`/`secondTokenBalance` are mutated by `ExchangeCapsule.transaction()`, which is invoked by the fully permissionless `ExchangeTransactionActuator` (any account holding the tokens/TRX can call it, `calcFee()` returns `0`): [5](#0-4) [6](#0-5) 

Because the pool state that the creator's withdraw amount depends on is shared and freely mutable by any third party, an attacker can broadcast an `ExchangeTransactionContract` immediately before (and reverse it immediately after) the creator's `ExchangeWithdrawContract` within the same or adjacent blocks, shifting the ratio just enough that the creator's previously-precise `quant`/computed `anotherTokenQuant` now fails the precision or sufficiency checks in validate, causing `ContractValidateException` and transaction failure. This can be repeated indefinitely and cheaply (bandwidth/energy cost only, no protocol fee on the trade itself, and typical small trades incur minimal slippage), effectively denying the exchange creator the ability to withdraw their share of the pool.

### Impact Explanation
An exchange creator who is entitled to withdraw funds from their own AMM pool can be perpetually blocked from doing so by a third party at negligible/near-zero cost, since `ExchangeTransactionContract` costs no protocol fee (`calcFee()` returns `0`) and can be trivially reversed. This constitutes a griefing denial-of-service that can amount to a freezing of the creator's ability to extract liquidity from the pool, satisfying the "permanent freezing of funds" impact class.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to observe the creator's pending `ExchangeWithdrawContract` in the mempool and race a small `ExchangeTransactionContract` before it lands (and optionally reverse afterward). This requires only an unprivileged, signed transaction and awareness of mempool contents — no special privilege, staking, or witness status is required, matching the "unprivileged transaction broadcaster" reach required by scope.

### Recommendation
Avoid deriving hard validation failures purely from live, third-party-mutable AMM ratios for a withdrawal whose intended amounts were chosen against a stale ratio. Consider allowing a tolerance/slippage parameter supplied by the caller (similar to `expected` in `ExchangeTransactionContract`) so a withdraw either succeeds within caller-specified bounds or fails gracefully without being trivially forced to fail by unrelated trades; alternatively, recompute amounts from the actual balances at execution time rather than re-validating against a fixed precision threshold tied to values computed before the transaction is packed.

### Proof of Concept
1. Exchange creator submits `ExchangeWithdrawContract` for `exchangeId` with `tokenId`/`quant` computed against the current `firstTokenBalance`/`secondTokenBalance` ratio.
2. Attacker observes this pending transaction and broadcasts an `ExchangeTransactionContract` against the same `exchangeId` with a size chosen to shift the ratio just enough that the creator's precomputed `anotherTokenQuant` in `ExchangeWithdrawActuator.doValidate()` (lines 218-243) now fails the `"Not precise enough"` / `"exchange balance is not enough"` check.
3. Because block producers order transactions and both are cheap unprivileged transactions, the attacker's trade can be included immediately before the creator's withdraw, causing the withdraw to revert with `ContractValidateException`.
4. Attacker optionally reverses the trade via another `ExchangeTransactionContract` afterward (both transactions have `calcFee()==0`), repeating the process on every subsequent withdraw attempt by the creator.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
