Audit Report

## Title
Irreversible fund burn in `add_tip` before validating that the target message is still tippable - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

## Summary
`Pallet::add_tip` on AssetHub calls `swap_fee_asset_and_burn`, which permanently withdraws and burns the caller's tip asset via `burn_for_teleport`, before the corresponding `EthereumSystemCall::AddTip` `Transact` is even dispatched to BridgeHub. [1](#0-0)  The `Transact` is sent as `UnpaidExecution`, a one-way fire-and-forget message with no acknowledgment or rollback path if BridgeHub's `AddTip::add_tip` rejects it. [2](#0-1) 

## Finding Description
`add_tip` is a public, permissionless, signed extrinsic. [1](#0-0)  It calls `swap_fee_asset_and_burn`, which either swaps the tip asset for Ether and burns the proceeds (`swap_and_burn` → `burn_for_teleport`) or, if the asset is already Ether, burns it directly. [3](#0-2)  `burn_for_teleport` performs `can_check_out`, `check_out`, and `withdraw_asset` — an irreversible withdrawal of the asset from the user's account. [4](#0-3) 

Only after this burn does `add_tip` build and send the `AddTip` call to BridgeHub via `send_transact_call`, using `UnpaidExecution` + `Transact`, which is asynchronous and has no built-in success/failure feedback loop back to AssetHub. [5](#0-4) 

On BridgeHub, `AddTip::add_tip` in `snowbridge-pallet-inbound-queue-v2` only accepts the tip if the message's nonce is not yet consumed: `ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed)`. [6](#0-5)  The nonce is marked consumed in `process_message` *before* the tip is drained via `Tips::<T>::take(nonce)`, and `process_message` is triggered independently by relayers calling `submit`. [7](#0-6) 

I confirmed there is no pre-check in `system-frontend::add_tip` (or anywhere in the burn path) that queries whether the message/nonce has already been processed before burning. A runtime API `is_message_relayed` exists in `InboundQueueV2Api` [8](#0-7)  and is referenced in the BridgeHub Westend runtime, but this is a runtime API for off-chain/RPC queries — it is not, and cannot be, invoked synchronously by the `add_tip` extrinsic on AssetHub (a different chain) prior to burning, since runtime APIs are not accessible cross-chain within a single transaction. Thus no guard exists to prevent burning against an already-processed message.

Because relaying (`submit`/`process_message` on BridgeHub) and tipping (`add_tip` on AssetHub → XCM `Transact`) are two independent, asynchronous flows with no shared lock or synchronization, a user's asset can be burned on AssetHub for a tip that BridgeHub subsequently rejects with `AddTipError::NonceConsumed`, with no compensating refund, mint-back, or trap-and-claim path defined anywhere in `system-frontend`, `system-v2`, or `inbound-queue-v2`.

## Impact Explanation
This matches the "permanent user-fund lock" impact category: an unprivileged user calling a public extrinsic (`add_tip`) can have their fee asset irreversibly burned via `burn_for_teleport` with no reward or refund if the underlying message has already been relayed by the time the cross-chain `Transact` executes. The corrupted/lost value is the burned tip `amount` credited nowhere — it is destroyed on AssetHub without any corresponding benefit or recovery, a real fund-loss condition rather than a griefing-only issue.

## Likelihood Explanation
This requires no malicious actor — normal, independent relayer activity (calling `submit` for a message) racing against a user's ordinary `add_tip` call is sufficient. Given the inherent multi-block latency of XCM `Transact` delivery between AssetHub and BridgeHub, and that relaying is driven by off-chain relayers on their own schedule, a user tipping a message that gets relayed before (or concurrently with) the tip's `Transact` arrival is a realistic and repeatable occurrence, not a contrived edge case.

## Recommendation
- Do not burn the tip asset on AssetHub until confirmation that the corresponding nonce is still unprocessed on BridgeHub (e.g., via a synchronous check where feasible, or a two-phase reserve/commit pattern).
- Alternatively, switch to a paid/acknowledged XCM pattern (e.g., XCM query-response) so a failed `AddTip::add_tip` call on BridgeHub can trigger a refund or mint-back on AssetHub.
- Add a settlement/trap-and-claim mechanism analogous to existing `claimer`-based trapped-asset recovery patterns used elsewhere in the bridge, specifically for this failure mode.

## Proof of Concept
1. A message with nonce `N` is bridged from Ethereum and pending relay (unconsumed) on BridgeHub.
2. A user calls `add_tip(message_id = N, asset)` on AssetHub; `swap_fee_asset_and_burn` swaps/burns the asset via `burn_for_teleport`, then dispatches `Transact(EthereumSystemCall::AddTip{ sender, message_id: N, amount })` as `UnpaidExecution` to BridgeHub. [1](#0-0) 
3. Before the `Transact` executes on BridgeHub, a relayer calls `submit` for nonce `N`; `process_message` sets `Nonce::<T>::set(N)` and drains `Tips::<T>::take(N)` (none registered yet). [7](#0-6) 
4. The delayed `Transact` for `AddTip` executes; `AddTip::add_tip` sees `Nonce::<T>::get(N) == true` and returns `AddTipError::NonceConsumed`, so no tip is registered. [6](#0-5) 
5. The user's burned asset on AssetHub is permanently lost with no refund, mint-back, or trap-and-claim path in any of the involved pallets.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
	}
