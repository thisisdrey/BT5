### Title
Unbounded, unthrottled compute-cost read requests (`GetPoxInv`/`GetBlocksInv`/`GetNakamotoInv`/`StackerDBGetChunkInv`/`StackerDBGetChunk`) enable bounded compute DoS on an authenticated peer connection - (File: stackslib/src/net/chat.rs)

### Summary
The Sui commit fixes a DoS gap where "gasless" transactions (zero cost to the sender) were not counted by the traffic controller, letting an attacker flood the node for free. The stacks-core P2P layer has the same class of gap: every *data-bearing push* message (`Blocks`, `Microblocks`, `Transaction`, `StackerDBChunk`/`StackerDBPushChunk`, `NakamotoBlocks`) is metered through a per-neighbor bandwidth accounting/throttle (`validate_*_push` + `NeighborStats::add_*_push`) that NACKs the sender with `Throttled` once a configured bytes/sec cap is exceeded. In contrast, the *request* message types that trigger chainstate/sortdb reads and cryptographic signing on the receiving node — `GetPoxInv`, `GetBlocksInv`, `GetNakamotoInv`, `StackerDBGetChunkInv`, `StackerDBGetChunk` — have no equivalent accounting or throttle at all. Since these requests are essentially free for the sender (no data payload, no fee, no proof-of-work), an already-handshaked peer can issue them back-to-back with no rate limit, forcing the node to repeatedly perform unbounded DB/computation work per request.

### Finding Description
`ConversationP2P::handle_authenticated_data_message` (in `stackslib/src/net/chat.rs`) dispatches inbound authenticated data-plane messages. For each of the *push* types, it first calls a dedicated `validate_*_push` method that increments per-neighbor bandwidth counters and returns a `Throttled` NACK if a configured rate is exceeded: [1](#0-0) 

Each push type is metered via a helper such as: [2](#0-1) 

which is backed by `NeighborStats::add_stackerdb_push` / `get_stackerdb_push_bandwidth` and a configurable `max_stackerdb_push_bandwidth`: [3](#0-2) [4](#0-3) 

By contrast, the *request* types in the same dispatch table are routed directly to handlers with no bandwidth/rate accounting whatsoever: [5](#0-4) [6](#0-5) 

`handle_getnakamotoinv` and `handle_getblocksinv` each trigger a chainstate/sortdb query and a full-message signing round-trip on every call, with no gate on how many times per second an authenticated peer may issue them: [7](#0-6) [8](#0-7) 

This is structurally the same fault as the Sui report: a category of inbound message that costs the sender essentially nothing (a small, unsigned/no-fee request) is not fed into the traffic-control/throttle accounting that protects the node from bandwidth/compute exhaustion, even though every other data/compute-costing message type is.

### Impact Explanation
Any already-handshaked (but otherwise unprivileged) peer can repeatedly send `GetPoxInv`, `GetBlocksInv`, `GetNakamotoInv`, `StackerDBGetChunkInv`, or `StackerDBGetChunk` requests as fast as the connection allows. Each triggers bounded-but-nonzero sortdb/chainstate lookups (e.g., `make_tenure_bitvector`, `get_slot_signer`, on-disk chunk reads) and a signed reply, with zero per-peer throttling comparable to the `Throttled` NACK path used for pushed data. This matches the "bounded compute DoS on a read endpoint" High-impact category: repeated invocation degrades node responsiveness for legitimate peers without requiring any meaningful investment (bandwidth, fee, or proof-of-work) from the attacker, unlike the deliberately-throttled push paths.

### Likelihood Explanation
High likelihood of triggerability: any peer that can complete a handshake (a cheap, unauthenticated action) can immediately begin issuing these requests. No signature validation failure, chain-state precondition, or fee is required to reach the vulnerable handlers — they are reached directly from `handle_authenticated_data_message` for any authenticated connection.

### Recommendation
Extend the existing bandwidth/rate-accounting infrastructure (`NeighborStats`, `validate_*_push`, `ConnectionOptions::max_*_push_bandwidth`) to also cover request-class messages that incur node-side compute cost: `GetPoxInv`, `GetBlocksInv`, `GetNakamotoInv`, `StackerDBGetChunkInv`, and `StackerDBGetChunk`. Add per-neighbor request-rate counters (e.g., requests/sec or a token-bucket) and reply with `NackErrorCodes::Throttled` once a peer exceeds a configurable request rate, mirroring the existing `validate_stackerdb_push`/`validate_nakamoto_block_push` pattern.

### Proof of Concept
Not independently reproducible from static analysis alone (would require a running two-node testnet), but the code path is directly demonstrable:
1. Two nodes complete a handshake (`handle_handshake`/`handle_handshake_accept`).
2. The authenticated peer sends a tight loop of `StacksMessageType::GetNakamotoInv(GetNakamotoInvData { consensus_hash })` (or `GetBlocksInv`/`StackerDBGetChunk`) messages.
3. Each is routed via `handle_authenticated_data_message` → `handle_getnakamotoinv`/`handle_getblocksinv`/`handle_stacker_db_getchunk*` (`stackslib/src/net/chat.rs:2288-2355`) with no counter increment or bandwidth check, unlike the `Blocks`/`Transaction`/`StackerDBChunk` arms in the same match block which call `validate_*_push` first (`stackslib/src/net/chat.rs:2303-2381`).
4. Existing unit tests such as `test_validate_stackerdb_push`/`test_validate_transaction_push` (`stackslib/src/net/chat.rs:7307-7432`) demonstrate the throttle exists for push types; no analogous test exists for the request types, confirming the asymmetry.

Note: I was not able to locate the exact source lines for `handle_getpoxinv`, `handle_stacker_db_getchunkinv`, and `handle_stacker_db_getchunk` function bodies within the indexed content (only their call sites in the dispatch table were retrievable), so their internal compute cost could not be fully quantified from the index. Given the size limits on the codebase index, some file contents may not be available; if you need to confirm the exact compute cost of these handlers, a Devin session with full repository access would be able to open `stackslib/src/net/chat.rs` and `stackslib/src/net/stackerdb/mod.rs` directly to inspect them in full.

    /// Returns a reply handle to the generated message (possibly a nack)
    fn handle_getblocksinv(
        &mut self,
        network: &mut PeerNetwork,
        sortdb: &SortitionDB,
        chainstate: &mut StacksChainState,
        preamble: &Preamble,
        get_blocks_inv: &GetBlocksInv,
    ) -> Result<ReplyHandleP2P, net_error> {
        monitoring::increment_msg_counter("p2p_get_blocks_inv".to_string());

        let mut response = ConversationP2P::make_getblocksinv_response(
            network,
            sortdb,
            chainstate,
            get_blocks_inv,
        )?;

        if let StacksMessageType::BlocksInv(ref mut blocks_inv_data) = &mut response {
            debug!(
                "{:?}: Handled GetBlocksInv. Reply {:?} to request {:?}",
                &network.get_local_peer(),
                &blocks_inv_data,
                get_blocks_inv
            );

            if self.connection.options.disable_inv_chat {
                // never reply that we have blocks
                debug!(
                    "{:?}: Disable inv chat -- pretend like we have nothing",
                    network.get_local_peer()
                );
                for entry in blocks_inv_data.block_bitvec.iter_mut() {
                    *entry = 0;
                }
                for entry in blocks_inv_data.microblocks_bitvec.iter_mut() {
                    *entry = 0;
                }
            }
        }

        self.sign_and_reply(
            network.get_local_peer(),
            network.get_chain_view(),
            preamble,
            response,
        )
    }

    /// Handle an inbound GetNakamotoInv request.
    /// Returns a reply handle to the generated message (possibly a nack)
    /// Only returns up to $reward_cycle_length bits
    pub fn make_getnakamotoinv_response(
        network: &mut PeerNetwork,
        sortdb: &SortitionDB,
        chainstate: &StacksChainState,
        get_nakamoto_inv: &GetNakamotoInvData,
    ) -> Result<StacksMessageType, net_error> {
        let _local_peer = network.get_local_peer();

        let base_snapshot_or_nack = Self::validate_consensus_hash_reward_cycle_start(
            _local_peer,
            sortdb,
            &get_nakamoto_inv.consensus_hash,
        )?;
        let base_snapshot = match base_snapshot_or_nack {
            Ok(sn) => sn,
            Err(msg) => {
                return Ok(msg);
            }
        };

        let tip = SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())?;
        let reward_cycle = sortdb
            .pox_constants
            .block_height_to_reward_cycle(sortdb.first_block_height, base_snapshot.block_height)
            .ok_or(net_error::InvalidMessage)?;

        let bitvec_bools = network.nakamoto_inv_generator.make_tenure_bitvector(
            &tip,
            sortdb,
            chainstate,
            &network.stacks_tip.consensus_hash,
            &network.stacks_tip.block_hash,
            reward_cycle,
        )?;
        let nakamoto_inv = NakamotoInvData::try_from(&bitvec_bools).inspect_err(|e| {
            warn!("Failed to create a NakamotoInv response to {get_nakamoto_inv:?}: {e:?}")
        })?;

        debug!(
            "Reply NakamotoInv for {} (rc {}): {:?}",
            &get_nakamoto_inv.consensus_hash, reward_cycle, &nakamoto_inv
        );

        Ok(StacksMessageType::NakamotoInv(nakamoto_inv))
    }

    /// Validate a pushed stackerdb chunk.
    /// Update bandwidth accounting, but forward the stackerdb chunk along if we can accept it.
    /// Possibly return a reply handle for a NACK if we throttle the remote sender
    fn validate_stackerdb_push(
        &mut self,
        network: &PeerNetwork,
        preamble: &Preamble,
        relayers: Vec<RelayData>,
    ) -> Result<Option<ReplyHandleP2P>, net_error> {
        assert!(preamble.payload_len > 1); // don't count 1-byte type prefix

        let local_peer = network.get_local_peer();
        let chain_view = network.get_chain_view();

        if !self.process_relayers(local_peer, preamble, &relayers) {
            warn!(
                "Drop pushed stackerdb chunk -- invalid relayers {:?}",
                &relayers
            );
            self.stats.msgs_err += 1;
            return Err(net_error::InvalidMessage);
        }

        self.stats
            .add_stackerdb_push((preamble.payload_len as u64) - 1);

        if self.connection.options.max_stackerdb_push_bandwidth > 0
            && self.stats.get_stackerdb_push_bandwidth()
                > (self.connection.options.max_stackerdb_push_bandwidth as f64)
        {
            debug!("{:?}: Neighbor {:?} exceeded max stackerdb-push bandwidth of {} bytes/sec (currently at {})", self, &self.to_neighbor_key(), self.connection.options.max_stackerdb_push_bandwidth, self.stats.get_stackerdb_push_bandwidth());
            return self
                .reply_nack(local_peer, chain_view, preamble, NackErrorCodes::Throttled)
                .map(Some);
        }

        Ok(None)
    }
