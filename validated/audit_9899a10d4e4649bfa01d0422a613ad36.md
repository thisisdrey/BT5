### Title
Missing content-hash verification in `AttachmentsBatchStateContext::extend_with_attachments` allows a malicious peer to poison the attachments store with mismatched data - (File: stackslib/src/net/atlas/download.rs)

### Summary
`extend_with_attachments` accepts any `GetAttachmentResponse` returned by a peer for an `AttachmentRequest` and inserts `response.attachment` into `self.attachments` without ever comparing `response.attachment.hash()` to the `AttachmentRequest.content_hash` that was actually requested. The unverified attachment is subsequently persisted via `network.atlasdb.insert_instantiated_attachment(&attachment)` in `AttachmentsDownloader::run`.

### Finding Description
The expected invariant is `served_bytes.hash() == requested_content_hash`. In `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558), each `(request, response)` pair from `results.succeeded` is processed: the response is decoded via `response.decode_atlas_get_attachment()` (stackslib/src/net/api/getattachment.rs:159-165), which merely hex-decodes the JSON string into an `Attachment` — it never checks the decoded content's hash against `request.content_hash`. The resulting `Attachment` is inserted directly into `self.attachments` (`self.attachments.insert(response.attachment)`, line 548) with no equality check at all.

Later, in `AttachmentsDownloader::run` (stackslib/src/net/atlas/download.rs:154-169), every attachment drained from `context.attachments` is looked up by its own (self-reported) hash — `network.atlasdb.find_all_attachment_instances(&attachment.hash())` — and then unconditionally written with `network.atlasdb.insert_instantiated_attachment(&attachment)` regardless of whether any matching `AttachmentInstance` was found. A remote, unprivileged peer serving `GET /v2/attachments/{H}` can return content `C'` whose hash `H' = hash(C') != H`; that content is still queued, decoded, and stored — reachable purely from an HTTP response to a node-initiated attachment-sync request.

### Impact Explanation
Because storage is keyed by the peer-supplied content's own hash (`attachment.hash()`), and `AttachmentInstance.content_hash` is the value bound to a confirmed on-chain BNS operation, a mismatched attachment stored under `H'` is *not* actually linked to the instance that requested `H` (the `resolve_attachment(&attachment.hash())` call uses `H'`, so it won't resolve the pending instance keyed at `H`). The practical, confirmed impact is therefore attachment-store pollution/exhaustion: attacker-controlled peers can cause the victim node to fetch, decode, and permanently persist (`insert_instantiated_attachment`) arbitrary attacker-chosen blobs that are not tied to any confirmed name/zonefile operation, consuming `uninstantiated`/`instantiated` attachment storage and DB rows. This is repeatable per attachment request the victim issues, for any peer the victim queries. A full BNS zonefile-resolution mismatch (serving `H`'s zonefile as attacker content) would additionally require the instance lookup itself to be spoofable, which the code prevents by keying the resolution/lookup on the attachment's own real hash rather than trusting the peer's claimed hash — so the worst confirmed outcome is unauthenticated storage pollution, not a BNS content swap.

### Likelihood Explanation
No privileges are required: any peer the victim queries for attachments (chosen from `network.get_outbound_sync_peers()` / advertised inventories) can simply serve arbitrary hex content on `GET /v2/attachments/{hash}` and it will be decoded and stored without any hash-equality check in `extend_with_attachments`. The precondition is that the victim node is actively running Atlas attachment sync (default for boot nodes tracking BNS) and has issued a request to the attacker-controlled/malicious peer, which is a normal, expected condition, not one requiring special timing or races. Cost to the attacker is a single crafted HTTP response.

### Recommendation
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs:547-549), after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; if the hash doesn't match, treat it as a failed request (`report.bump_failed_requests()`) and optionally penalize/deregister the peer. This restores the `served_bytes.hash() == requested_content_hash` invariant before any data reaches `atlasdb.insert_instantiated_attachment`.

### Proof of Concept
Rust test in `stackslib::net::atlas::download` (or `tests.rs`):
1. Construct an `AttachmentsBatchStateContext` with a `priority_queue`/`attachments_batch` containing an `AttachmentInstance` with `content_hash = H` (e.g., via `new_attachment_instance_from`).
2. Build an `AttachmentRequest { content_hash: H, .. }` and a `BatchedRequestsResult` whose `succeeded` map pairs that request with a fake `StacksHttpResponse` (or directly a `GetAttachmentResponse`) built from bytes `C'` such that `Hash160::from_data(&C') != H`.
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert `context.attachments` contains an `Attachment` whose `.hash()` equals `H'` (not `H`), i.e., `context.attachments.iter().any(|a| a.hash() != H)` is true — demonstrating the missing equality check.
5. Optionally continue to `AttachmentsDownloader::run`-equivalent logic and assert `atlasdb.find_attachment(&H')` returns `Some`, confirming the mismatched content is persisted, while `atlasdb.find_attachment(&H)` (the originally requested hash) remains `None`/unresolved.     pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
