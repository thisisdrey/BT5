### Title
Unprivileged dust transfers fill `MAX_TOKENS_PER_USER` account list and DoS victim's deposits, mints, and liquidations — (`contracts/Pool.sol`)

### Summary
Metronome tracks, per account, the set of `DepositToken`s and `DebtToken`s it holds in `depositTokensOfAccount`/`debtTokensOfAccount` (`contracts/storage/PoolStorage.sol`), and enforces a hard cap of `MAX_TOKENS_PER_USER = 30` combined (`contracts/Pool.sol:79`, `contracts/Pool.sol:143-148`). Any holder of a msdTOKEN can call `DepositToken.transfer(victim, 1 wei)`, which unconditionally registers that token in the victim's set via `pool.addToDepositTokensOfAccount(recipient_)` (`contracts/DepositToken.sol:517-520`). There is no opt-in or minimum amount: the recipient cannot refuse the listing. This is the same bug class as the OpenQ `TOKEN_ADDRESS_LIMIT` report — an attacker-controlled bounded set is filled with dust to block legitimate usage.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's pool-level set whenever the recipient's prior balance is 0 and `amount_ > 0` (`contracts/DepositToken.sol:518-520`). `transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked`), never the recipient's list size (`contracts/DepositToken.sol:348-376`).
- `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_`, also registering the token on the victim (`contracts/DepositToken.sol:211-237`, `_mint` at `contracts/DepositToken.sol:485-488`) — so even without holding msdTOKENs, an attacker can deposit dust collateral directly on behalf of the victim.
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`, `204-220`).
- The same check fires on the *mint* path: `DebtToken` minting (issue/flashIssue during `Pool.mint`, leverage, swaps) calls `addToDebtTokensOfAccount`, so the victim cannot open debt in a new synthetic either.
- A pool supports at most 30 deposit tokens (`ReachedMaxDepositTokens`, `contracts/Pool.sol:703`), so an attacker needs at most ~30 dust transfers/deposits — cheap, atomic, and front-runnable against a victim's first deposit.

Invariant broken: liveness — the victim cannot register any new collateral or debt token, so `deposit()` of any collateral type not already in their set, `mint()` of any new synthetic, `Pool.swap` outputs, and SmartFarmingManager leverage all revert.

### Impact Explanation
- A fresh account can be permanently prevented (until they manually clear slots) from depositing collateral and using the protocol: attacker front-runs the first deposit and fills all 30 slots.
- An underwater or near-unhealthy victim who needs to deposit a *different* collateral type to restore health is blocked and can be forced into liquidation — attacker profits by liquidating.
- Legitimate msdTOKEN senders to the victim revert, DoSing transfers.
- Mitigation exists (victim can `transfer` the full dust balance of each token to burn slots, costing gas per token), so impact is temporary freezing of funds/functionality and forced-liquidation griefing rather than permanent loss — consistent with Medium severity.

### Likelihood Explanation
- Fully unprivileged: requires only an EOA with dust amounts of underlying collateral or msdTOKENs; no privileged role, oracle manipulation, or governance action.
- Cost is bounded (~30 dust deposits/transfers), targetable, and front-runnable.
- Caveat I could not fully verify within the iteration budget: whether `Pool.liquidate`'s fee split seizes to a `feeCollector`/`to_` whose own list could be attacker-filled to brick liquidations protocol-wide; if `seize` credits a fixed fee-collector via `_transfer`, filling that account's list would escalate this to a liquidation DoS — worth confirming in the PoC.

### Recommendation
- Do not register tokens in the recipient's account set on `transfer`/`transferFrom`; instead require the recipient to opt in (e.g., a `claim`/`accept` pattern or registering only on `deposit`/`mint` where the caller and beneficiary are the same or explicitly authorized).
- Alternatively, enforce a minimum meaningful amount or track positions by balance > 0 only at accounting time rather than via a capped enumerable set, and bound loops (`debtOf`, `depositOf`, `debtPositionOf`) accordingly.

### Proof of Concept
Hardhat fork sketch (against deployed `Pool` + any listed `DepositToken`):

```ts
// attacker deposits dust of every listed deposit token directly on behalf of victim
const dTokens = await pool.getDepositTokens();
for (const addr of dTokens) {
  const dt = await ethers.getContractAt('DepositToken', addr);
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, victim.address); // fills victim's set
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(MAX);

// victim's own deposit of a new collateral type now reverts
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot mint a new synthetic either (addToDebtTokensOfAccount reverts)
await expect(
  pool.connect(victim).mint(newSynthetic, amount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Also assert the same effect via `depositToken.connect(attacker).transfer(victim.address, 1)` for each token, and test whether `pool.liquidate(...)` reverts when the fee recipient's set is saturated.
