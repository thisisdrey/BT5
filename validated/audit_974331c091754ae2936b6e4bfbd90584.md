### Title
`native_withdraw` debits signer's wNEAR unconditionally but `do_native_withdraw`'s final `Promise::new(receiver_id).transfer(amount)` has no resolve/refund callback, permanently losing signer funds if the transfer fails - (File: `contracts/defuse/src/contract/tokens/nep141/native.rs`, `contracts/defuse/src/contract/intents/state.rs`)

### Summary
`Contract::native_withdraw` debits the signer's internal wNEAR balance and unwraps wNEAR to real NEAR via `near_withdraw`, then schedules `do_native_withdraw` which fires `Promise::new(receiver_id).transfer(amount)` and immediately `.detach()`es the whole chain with no subsequent `resolve_*` callback. Every other withdraw path (`ft_withdraw`, and by the same pattern `nft_withdraw`/`mt_withdraw`) attaches a `*_resolve_withdraw` callback that inspects the transfer's promise result and calls `self.deposit(...)` to refund the sender on failure; `native_withdraw` has no equivalent, so a failed final `Transfer` action leaves the signer's internal ledger permanently short by `amount` with no path to recovery.

### Finding Description
Binding that should hold: `signer_wnear_debited == amount_delivered_to(receiver_id)`.

Trace:
- `Contract::native_withdraw` (contracts/defuse/src/contract/intents/state.rs:212-240) calls `self.withdraw(owner_id, [(wnear_token_id, amount)], ...)`, which invokes `internal_sub_balance` and permanently decrements the signer's internal wNEAR ledger entry before any promise executes.
- It then calls `ext_wnear::near_withdraw` and chains `.then(do_native_withdraw(withdraw))`, and finally `.detach()`s the whole promise (line 237) — there is no `.then(Self::ext(...).resolve_native_withdraw(...))` step anywhere in this chain.
- `do_native_withdraw` (contracts/defuse/src/contract/tokens/nep141/native.rs:11-19) only asserts that `near_withdraw` (promise index 0) succeeded, then unconditionally returns `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)`. This returned `Promise` is the *last* promise in the chain (the original chain was already `.detach()`ed by the caller), so its outcome is never inspected by any contract logic.
- If `receiver_id` does not exist when this `Transfer` action is processed (e.g., the attacker self-destructs their own controlled account via a `delete_account` receipt scheduled earlier in the same batch, racing the ~2-hop `near_withdraw -> do_native_withdraw` callback chain), the NEAR runtime fails the `Transfer` action and refunds the deposit back to the *predecessor* of that receipt — i.e., back onto the Defuse contract's own account balance, not into any internal ledger entry.
- Compare this to `internal_ft_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs:96-105), which always chains a `ft_resolve_withdraw` callback that reads `promise_result_checked_void(0)`/`promise_result_checked_json`, computes `refund = amount - used`, and calls `self.deposit(sender_id, ..., refund)` to restore the sender's internal balance on failure. `native_withdraw` has no analogous resolver.

Because of this asymmetry, the equality `signer_wnear_debited == amount_delivered_to(receiver_id)` is violated whenever the final native transfer fails: the left side is decremented unconditionally and irreversibly at the start of `native_withdraw`, while the right side can be zero, and there is no code path to reconcile the difference.

### Impact Explanation
The signer's wNEAR balance inside the Defuse Verifier is permanently reduced by `amount` while zero NEAR is delivered to `receiver_id`; the underlying NEAR ends up stuck on the Defuse contract's own account balance with no internal accounting record tying it back to the signer, i.e. it is unrecoverable through any exposed contract method. This is repeatable per signer per withdraw call and matches the Critical category "user funds permanently frozen" — value (the signer's own funds) leaves their control with no refund path, unlike every other withdraw type in this codebase which implements a resolve/refund callback.

### Likelihood Explanation
Preconditions are fully attacker-controlled: the attacker only needs their own wNEAR balance inside the Verifier (`>= amount`), and to control an account they can delete (`receiver_id`, which they deploy and can self-destruct via `Promise::new(receiver_id).delete_account(beneficiary)`). The attack requires timing the `delete_account` receipt to land before the `do_native_withdraw` receipt executes — feasible because `native_withdraw` -> `near_withdraw` -> `do_native_withdraw` -> final `Transfer` is at least two to three cross-contract hops, giving ample scheduling room for a receipt from the attacker's own account/contract to execute first. No privileged role, relayer key, or victim key is required — purely self-inflicted account deletion timed against one's own withdraw call. This is directly reproducible in a `near-workspaces` sandbox test.

### Recommendation
Add a `resolve_native_withdraw` (and equivalent for `storage_deposit`'s NEAR-unwrap path) private callback attached after the `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw`, mirroring `ft_resolve_withdraw`: inspect `promise_result_checked_void` on the transfer result, and on failure call `self.deposit(owner_id, [(wnear_token_id, amount)], Some(REFUND_MEMO))` to re-credit the signer's internal wNEAR balance so the debit and delivery stay balanced.

### Proof of Concept
`cargo test` plan using `near-workspaces` sandbox (crate under `crates/testing/sandbox`, test file added under `tests/src/tests/defuse/intents/native_withdraw.rs`):
1. Deploy Defuse contract and wNEAR contract; fund a signer account with wNEAR deposited into the Verifier (internal wNEAR balance `>= amount`).
2. Attacker (signer) deploys their own account `receiver_id` with a minimal contract.
3. Signer submits a `MultiPayload` batch (via `execute_intents`) containing: (a) `NativeWithdraw{ receiver_id, amount }` intent, and (b) in the same transaction/batch, a function call on `receiver_id`'s own contract that calls `Promise::new(env::current_account_id()).delete_account(beneficiary)` to self-destruct `receiver_id`, scheduled so its receipt resolves before the `do_native_withdraw` receipt (e.g., by adding artificial gas-heavy delay to the `near_withdraw`->`do_native_withdraw` chain, or simply deleting the account directly before the batch, since receipt ordering in sandbox is deterministic enough to reproduce the same end effect: `receiver_id` does not exist when the final `Transfer` executes).
4. After the sandbox settles all receipts, assert:
   - `defuse_contract.balance_of(signer_id, wnear_token_id)` decreased by exactly `amount` (LHS of the binding — debited).
   - `receiver_id` account's NEAR balance delta == 0 (RHS of the binding — nothing delivered).
   - No `Deposit`/refund event or internal balance increase for `signer_id` was emitted (confirming no resolve/refund path exists).
   - This demonstrates `signer_wnear_debited (amount) != amount_delivered_to(receiver_id) (0)` with no reconciling refund, proving the fund-freezing vulnerability.
