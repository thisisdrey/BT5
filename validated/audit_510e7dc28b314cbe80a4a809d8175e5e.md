### Title
Integer-underflow bypass of `EnsureRemaining` bounds check in ijar's ZIP central-directory parsing allows out-of-bounds read of untrusted archive/heap data - (File: `third_party/ijar/zip.cc`)

### Summary

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads the per-entry `offset` field directly from the untrusted central directory with no bounds validation: [1](#0-0) 
That `offset` (an attacker-controlled 32-/64-bit value from a crafted ZIP/JAR) is later used unvalidated to reposition the read cursor: [2](#0-1) 
`EnsureRemaining` is the only guard against reading past the end of the mmap'd input buffer: [3](#0-2) 
`in_offset` and `remaining` are `size_t` (unsigned). If the attacker-controlled `offset` pushes `p` beyond `zipdata_in_ + input_file_->Length()`, then `in_offset > input_file_->Length()`, and `remaining = input_file_->Length() - in_offset` **underflows** to a huge value near `SIZE_MAX`. The subsequent check `n > remaining` then always passes, silently defeating the bounds check for every following read (`get_u4le`, `get_u2le`, and ultimately the `memcpy` of `file_name_length_` bytes into the fixed `filename[PATH_MAX]` buffer and the `p += compressed_size_`/`ProcessFile` data copy). The parser then dereferences and copies memory at attacker-influenced addresses far outside the mapped file into the interface-jar/output file via `processor->Process(filename, attr, file_data, uncompressed_size_)`: [4](#0-3) [5](#0-4) 

This is the direct structural analog of CVE-2016-1977: a native (C++) parser trusts attacker-supplied length/offset fields from a "smart" binary container format (Graphite font vs. ZIP/JAR central directory) without validating them against the actual buffer bounds, and an integer-arithmetic bug in the would-be bounds check lets crafted input corrupt/over-read memory during parsing of untrusted content that a victim's build consumes (a downloaded `.jar`/`.zip`/`.aar` processed by the `ijar` tool, e.g. via `http_jar`, `http_archive`, or `java_import` interface-jar generation).

### Impact Explanation
An attacker who serves a crafted `.jar`/`.zip` archive (fetched by a victim's build, e.g. as a Maven/HTTP dependency subsequently run through `ijar` to produce an interface jar) can craft a central-directory `offset` value that underflows the `EnsureRemaining` bounds check. This turns what should be a hard read-boundary check into a no-op, allowing the parser to read heap/mmap memory outside the archive's mapped region and copy it into the generated interface jar (information disclosure of process memory into a build artifact) or crash the `ijar`/Bazel process (memory-safety violation, potential segfault). This is a genuine memory-corruption-class bug in native code parsing untrusted, non-BUILD/.bzl binary content — not a checksum, credential, or cache-key issue and not simply resource exhaustion, since the primitive is an out-of-bounds *read* driven by an integer-underflow logic bug in a bounds check, structurally identical to the Graphite CVE's mis-validated buffer-bound arithmetic.

### Likelihood Explanation
Reaching this code requires a build to run `ijar` over an attacker-supplied ZIP/JAR (a plausible, unprivileged supply-chain scenario: a malicious `http_jar`/`http_archive` target, dependency mirror, or unpinned/untrusted registry artifact). No checksum on the *bytes fed into ijar's parsing routine* protects against a maliciously-structured (but potentially still sha256-matching, if the victim didn't pin, or served post-verification through a compromised mirror inconsistent with an already-recorded but not yet enforced digest) archive — the vulnerability is in structural parsing of the archive's own metadata (central directory), which sha256 verification of the outer file does not semantically validate. This is a real, if narrow, path: it requires the target's build to invoke `ijar` against attacker-influenced ZIP bytes.

### Recommendation
In `EnsureRemaining` (and everywhere else in `third_party/ijar/zip.cc` that advances `p` using untrusted length/offset fields), explicitly validate that `p` is within `[zipdata_in_, zipdata_in_ + input_file_->Length()]` **before** computing `in_offset`/`remaining`, and reject the file if `p` is already out of range instead of computing an unsigned subtraction that can underflow. Apply the same explicit range check to the central-directory `offset` field immediately after it is read in `ProcessCentralDirEntry`, and to the extra-field loop's `data_size`-driven advancement of `extra_p`.

### Proof of Concept
A `BuildIntegrationTestCase`/native unit test (in `third_party/ijar` test suite, e.g. `zip_test.cc`) constructing a minimal ZIP: valid EOCD + a single central-directory entry whose `offset` field is set to a value close to `SIZE_MAX` (or otherwise larger than the mapped file length) would demonstrate that `EnsureRemaining` incorrectly returns success (no error), and that `get_u4le(p)`/subsequent reads dereference memory outside the input mapping — observable via a crash (ASan heap-buffer-overflow/SEGV) or via inspecting the bytes copied into `filename`/`file_data`. Building this as an `ijar_test` case with ASan enabled would reproduce and confirm the OOB read deterministically.
