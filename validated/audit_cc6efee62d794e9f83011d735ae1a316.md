This confirms the mechanism fully. The `congestion_seed = apply_state.block_height.wrapping_add(shard_seed)` at [1](#0-0)  is deterministic and derived purely from block height and shard index — it does not depend on which sender shard is congesting the receiver or how much congestion traffic exists. `get_new_allowed_shard` (`core/primitives/src/congestion_info.rs:370`) does `congestion_seed.checked_rem(all_shards.len())` to round-robin the `allowed_shard` across every shard in `all_shards`, advancing by one shard index per block height [2](#0-1) .

### Conclusion

#No vulnerability found for this question.

**Reasoning:** The attack scenario described (mass cheap-tx flood keeping a receiver shard at `reject_tx_congestion_threshold`/fully congested) does not actually block the honest receipt indefinitely:

1. `allowed_shard` selection is a **pure round-robin function of `(block_height + shard_index) mod num_shards`**, entirely independent of which shards are sending congestion-inducing traffic [3](#0-2) . An attacker cannot bias or exclude the honest sender's shard from ever becoming `allowed_shard` — it cycles through every shard deterministically, guaranteeing the sender shard becomes `allowed_shard` at least once every `num_shards` blocks regardless of congestion level.

2. When the honest sender's shard becomes `allowed_shard`, `outgoing_gas_limit` grants it `config.allowed_shard_outgoing_gas` (not zero) even under full congestion [4](#0-3) .

3. `try_forward`'s `ClampOutgoingGasAdmission` (active at PV 85+, and the repo's stable protocol version is 86, i.e., unconditionally active) clamps the *admission* gas check to `min(receipt_gas, allowed_shard_outgoing_gas)` [5](#0-4) , so a single large/expensive buffered receipt cannot be perpetually stuck behind the gas-limit check once its shard is the allowed shard — this is an explicit fix for issue #12606 documented in the spec [6](#0-5) .

4. Attached to this, `forward_from_buffer_to_shard` drains buffered receipts in FIFO order every chunk whenever the shard is allowed to send any gas at all [7](#0-6) , so the buffered receipt is not skipped in favor of newer ones.

Therefore the described "OutgoingLimit.gas stays at Gas::ZERO for all non-allowed_shard senders indefinitely" precondition is self-limiting: the attacker cannot make any *specific* other shard's `OutgoingLimit.gas` stay zero forever, since the allowed-shard designation is not congestion-attacker-controllable and rotates deterministically with block height. This directly satisfies the bounded-liveness property the question's own "proof idea" asks to test, and the repo's spec explicitly documents this as an intentional invariant ("Bounded incoming work" / red-light guarantee) [8](#0-7) . There is no code path by which an unprivileged attacker can influence or extend the allowed-shard rotation, so permanent freezing of the honest receipt is not achievable through this mechanism.

        &mut self,
        buffer_shard_id: ShardId,
        state_update: &mut TrieUpdate,

        shard_layout: &ShardLayout,

        let mut outgoing_metadatas_updates: Vec<(ByteSize, Gas)> = Vec::new();
        for receipt_result in
            self.outgoing_buffers.to_shard(buffer_shard_id).iter(&state_update.trie, true)
        {
            let receipt = receipt_result?;
            let gas = receipt_congestion_gas(&receipt, &apply_state.config)?;
            let size = receipt_size(&receipt)?;
            let should_update_outgoing_metadatas = receipt.should_update_outgoing_metadatas();

                receipt,
                gas,

                target_shard_id,

                &mut self.outgoing_receipts,
                apply_state,
                &mut self.stats,

                    num_forwarded += 1;

                    break;
                }
            }

                buffer_shard_id,
                size,
                gas,
                state_update,

        }
        Ok(())
    }
