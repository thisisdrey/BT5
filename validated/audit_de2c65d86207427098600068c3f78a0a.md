### Title
Exchange pool reserve can be driven to exactly zero, permanently freezing all tokens locked in the pool - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
The `Exchange`/`ExchangeV2` Bancor-relay pools in java-tron use the same defensive pattern DODO GSP does — a hard `balance == 0` guard that is meant to detect a "closed" pool — but nothing prevents a legitimate `ExchangeTransactionContract` from computing a `buyTokenQuant` that drives one side of the pool's balance to *exactly* zero. Once that happens, the same `balance == 0` check is enforced identically in `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`, and `ExchangeInjectActuator`, so the pool becomes permanently unusable: it cannot be traded against, cannot be withdrawn from, and — critically — cannot be refilled via inject either, since inject uses the very same guard.

### Finding Description
`ExchangeCapsule.transaction()` computes the counter-token amount via `ExchangeProcessor`/`SafeExchangeProcessor` (a Bancor-formula relay) and then updates the two token balances with a simple subtraction, only rejecting the trade if a balance goes **negative**, not if it lands on **zero**: [1](#0-0) 

`ExchangeTransactionActuator.execute()` persists whatever balances `transaction()` returns with no additional floor check: [2](#0-1) 

The only protection against a zero reserve is a pre-trade check in `doValidate()`, which rejects new trades once a balance is *already* zero, but does nothing to prevent a trade from *creating* that zero balance: [3](#0-2) 

The identical `firstTokenBalance == 0 || secondTokenBalance == 0` → `"the exchange has been closed"` guard is also present in `ExchangeWithdrawActuator`: [4](#0-3) 

and in `ExchangeInjectActuator`, as confirmed by its dedicated test `SameTokenNameCloseTokenBalanceZero`: [5](#0-4) 

Because **all three** entry points (trade, withdraw, inject) reject once any side of the pool balance is zero, there is no recovery path once a legitimate `ExchangeTransactionContract` results in a balance of exactly zero — this mirrors the DODO GSP root cause where a reserve hitting zero makes `buyShares`/`sellQuote` unusable with no way to refill, except here java-tron additionally blocks the "refill" (`ExchangeInject`) path too, making the freeze permanent rather than just DOS'd until an external actor sells back.

### Impact Explanation
Any TRX/TRC-10 held in an `Exchange`/`ExchangeV2` pool whose balance reaches zero on one side becomes permanently locked in the contract-equivalent store: no further `ExchangeTransactionContract`, `ExchangeWithdrawContract`, or `ExchangeInjectContract` against that exchange ID can succeed, since all three actuators independently short-circuit on the same zero-balance condition. This is a permanent freezing-of-funds condition reachable by an unprivileged, single signed transaction from any account (the pool creator or any trader), satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Reaching a balance of exactly zero requires a trader to select a `quant` for `ExchangeTransactionContract` whose computed `anotherTokenQuant` from the Bancor relay formula exactly equals the remaining reserve of the opposite token (or to do so via repeated trades that whittle the reserve down and then finish it off exactly). This requires deliberate calculation but no special privilege — the amounts are fully attacker-controlled and can be computed off-chain against the current pool state (the pool state, `firstTokenBalance`/`secondTokenBalance`, is public), and `ExchangeCapsule.transaction()` is exposed to any account willing to pay the trade fee. There is no minimum-reserve floor, unlike the negative-balance guard that exists in the hardened path.

### Recommendation
Add an explicit floor check (e.g., `newFirstTokenBalance <= 0 || newSecondTokenBalance <= 0`) in `ExchangeCapsule.transaction()`/the actuators' `doValidate()`/`execute()` methods to reject trades that would drive either reserve to zero, mirroring but strengthening the existing negative-balance check. Alternatively, allow `ExchangeInjectActuator` to bypass or specially handle the `balance == 0` case so that a zeroed-out pool can always be refilled and reopened rather than being permanently bricked.

### Proof of Concept
1. Create an `Exchange`/`ExchangeV2` between tokens A and B with small reserves (e.g. via `ExchangeCreateContract`).
2. Compute, using the public Bancor relay formula in `ExchangeProcessor`/`SafeExchangeProcessor` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java` and `SafeExchangeProcessor.java`), a sell `quant` of token A such that the resulting `anotherTokenQuant` (token B payout) exactly equals the current `secondTokenBalance`.
3. Submit `ExchangeTransactionContract` with that `quant`; `ExchangeTransactionActuator.execute()` accepts it because `newSecondTokenBalance == 0` passes the only guard (`< 0` check in hardened mode, no check at all in legacy mode) — see `ExchangeCapsule.transaction()` lines 160-162.
4. Any subsequent `ExchangeTransactionContract`, `ExchangeWithdrawContract`, or `ExchangeInjectContract` against this exchange ID now fails validation with `"Token balance in exchange is equal with 0, the exchange has been closed"`, permanently locking the remaining token A balance in the pool with no way to reopen it.
