### Title
Unvalidated remote URL scheme allows `ext::`/local-command Git transport execution via FetchRemote/CreateRepositoryFromURL/UpdateRemoteMirror - (File: internal/gitaly/service/repository/fetch_remote.go, internal/gitaly/service/repository/create_repository_from_url.go)

### Summary
`FetchRemoteRequest.RemoteParams.Url`, `CreateRepositoryFromURLRequest.Url`, and `UpdateRemoteMirrorRequest.Remote.Url` are passed to `git fetch`/`git clone` as `remote.<name>.url` / clone arguments without any scheme allowlist, so a URL such as `ext::sh -c ...` reaches Git's URL parser as a transport-helper invocation instead of a network address, causing Gitaly to execute an arbitrary local command as the Gitaly process user.

### Finding Description
In `buildCommandOpts` (`internal/gitaly/service/repository/fetch_remote.go:260-304`), `remoteURL := req.GetRemoteParams().GetUrl()` is taken verbatim from the request and only mutated if `resolved_address` is set (via `gitcmd.GetURLAndResolveConfig`, `internal/git/gitcmd/command_resolve.go:27-49`). It is then stored directly as `remote.inmemory.url` config and used by `quarantineRepo.FetchRemote(ctx, "inmemory", opts)`, which invokes `git fetch` (`internal/gitaly/service/repository/fetch_remote.go:104`). `validateFetchRemoteRequest` (`internal/gitaly/service/repository/fetch_remote.go:306-320`) only checks that the URL is non-empty — no scheme allowlist (http/https/git/ssh) is enforced.

Similarly, `cloneFromURLCommand` (`internal/gitaly/service/repository/create_repository_from_url.go:21-85`) does `u, err := url.Parse(repoURL)` and passes `u.String()` straight into `gitcmd.Command{Name: "clone", ..., Args: []string{urlString, repositoryFullPath}}` (lines 77-84). `url.Parse` happily accepts `ext::<command>` as a URL with scheme `ext`; there is no check restricting `u.Scheme` to a safe set. `validateCreateRepositoryFromURLRequest` (lines 149-159) only checks for a non-empty URL.

`GetURLAndResolveConfig` (`internal/git/gitcmd/command_resolve.go:27-49`) is only invoked when `resolved_address` is supplied and its switch only recognizes `http://`, `https://`, `git://`, `ssh://` prefixes explicitly — any other value (including `ext::...`) falls through to the SCP-style branch (`getURLAndResolveConfigForSCP`), which does not reject or sanitize `ext::` syntax; and when `resolved_address` is empty (an optional field), this function is skipped entirely, leaving the raw attacker-supplied string untouched.

Git's `ext::` transport (and, depending on build/config, `file::`) executes an arbitrary shell command specified in the URL as the transport helper. Since Gitaly's execution environment does not set `GIT_ALLOW_PROTOCOL`/`GIT_PROTOCOL_FROM_USER=0` or configure `protocol.ext.allow=never` (verified absent from `setupGitExecutionEnvironments` in `internal/git/gitcmd/command_factory.go:221-236` and from `GlobalConfiguration` in the same file, lines 649-722), Git's default policy (`protocol.ext.allow=user`) permits the `ext::` helper to run when it originates from a "user"-supplied value, which is exactly the case here.

None of the existing defenses (`storage.ValidateRelativePath`, `git.ValidateRevision`, the `gitcmd` option/flag allowlists in `command_description.go`) validate the *value* of a URL argument — they only guard revision/path/flag shapes, not scheme.

### Impact Explanation
If the URL reaches Gitaly unfiltered, this results in arbitrary command execution on the Gitaly host under the Gitaly process's OS user, which can read/write any file the process can access, exfiltrate credentials, pivot to other repositories/storages, or pursue further privilege escalation — a critical RCE impact.

### Likelihood Explanation
Exploitability entirely depends on whether GitLab Rails' `Gitlab::UrlBlocker` (or equivalent caller-side allowlisting) filters the URL scheme before invoking `FetchRemote` / `CreateRepositoryFromURL` / `UpdateRemoteMirror`. That validation happens outside Gitaly, in GitLab Rails, which is explicitly out of scope per the audit rules ("reject anything ... a bug in GitLab Rails/git itself rather than a bug in Gitaly"). Within Gitaly's own code, there is no independent scheme allowlist, so if any caller (Rails feature, direct RPC caller, or a future/alternate caller path) forwards an unsanitized URL, Gitaly will execute it without complaint. This constitutes a missing defense-in-depth control in Gitaly rather than a directly attacker-triggerable RCE from an unprivileged, no-special-role GitLab user through the documented product flow, since Rails is expected to block non-http(s)/git/ssh schemes before the RPC is issued.

### Recommendation
Add an explicit scheme allowlist in Gitaly itself (defense in depth, independent of Rails) at the entry points that accept remote URLs — `validateFetchRemoteRequest`, `validateCreateRepositoryFromURLRequest`, and the `UpdateRemoteMirror` request handling — rejecting any URL whose scheme is not one of `http`, `https`, `git`, `ssh`, or a bare SCP-style `user@host:path` form. Additionally, set `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (or equivalent `protocol.*.allow=never` config for `ext`/`file`) in the shared Git execution environment (`internal/git/gitcmd/command_factory.go:setupGitExecutionEnvironments`) so that even if a disallowed URL slips through, Git itself refuses to invoke the `ext::`/`file::` transports.

### Proof of Concept
```go
func TestFetchRemote_extProtocolRCE(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)
    repoProto, _ := gittest.CreateRepository(t, ctx, cfg)

    marker := filepath.Join(testhelper.TempDir(t), "pwned")
    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.Remote{
            Url: fmt.Sprintf("ext::sh -c 'touch %s'", marker),
        },
    })
    // Expected (vulnerable): err reflects fetch failure but marker file exists,
    // proving the shell command executed on the Gitaly host.
    require.FileExists(t, marker)
}
```
