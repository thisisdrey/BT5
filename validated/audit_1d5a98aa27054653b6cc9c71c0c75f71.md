### Title
`mt_resolve_withdraw` refunds the full batch on a mis-sized (but `Ok`) `mt_batch_transfer_call` result, crediting `sender_id` for tokens that were actually transferred out - (File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs)

### Summary
`mt_resolve_withdraw` treats any successfully-returned (`Ok`) promise result whose `Vec<U128>` length does not exactly match `amounts.len()` as "zero tokens used," refunding the entire withdrawn batch back into `sender_id`'s internal balance. Because the `token` contract address in `mt_withdraw`/`mt_force_withdraw` is fully attacker-controlled, an attacker can deploy a `token` contract whose `mt_batch_transfer_call` genuinely completes the transfer to `receiver_id` on its own ledger while intentionally returning a wrong-length array, causing Defuse to both let the transfer succeed externally and refund the sender internally.

### Finding Description
The broken binding is:
`amount_debited_from_sender_id_per_token_id == amount_actually_transferred_to_receiver_id + amount_recredited_to_sender_id`

In `internal_mt_withdraw` (contracts/defuse/src/contract/tokens/nep245/withdraw.rs, lines 60-87), the sender's internal `token_balances[Nep245TokenId(token, token_id)]` is decremented for every `(token_id, amount)` pair via `self.withdraw(...)` before any external call is made: [1](#0-0) 

`do_mt_withdraw` then issues `ext_mt_core::ext_on(p).mt_batch_transfer_call(receiver_id, token_ids, amounts, ...)` against the attacker-supplied `token` account: [2](#0-1) 

The callback `mt_resolve_withdraw` interprets the promise result: [3](#0-2) 

The `Ok(_) => vec![U128(0); amounts.len()]` branch is reached whenever the `token` contract's `mt_batch_transfer_call` returns a value that deserializes as JSON `Ok` but whose array length differs from `amounts.len()`. This is treated identically to "receiver refused everything," and `used` becomes all zero. `self.deposit(sender_id, ...)` then computes `refund = amount.0 - used.0 = amount.0` for every `token_id`, fully re-crediting `sender_id`'s balance: [4](#0-3) 

Since `token` is an arbitrary `AccountId` chosen by the withdrawer (see `mt_withdraw` / `mt_force_withdraw` signatures), the attacker deploys their own `token` contract that: (1) implements `mt_batch_transfer_call` to actually record the incoming batch against `receiver_id` (also attacker-controlled) in its own MT ledger, and (2) returns a `Vec<U128>` of the wrong length (e.g. empty) instead of the NEP-245-compliant per-item "unused amount" array. No code in `mt_resolve_withdraw` or upstream validates that the `token` contract's response actually matches on-chain reality — the mismatched-length case is conflated with "nothing was used," which is only safe if a mismatched length reliably means the transfer did not happen, an assumption that does not hold for a malicious or non-compliant `token` contract that the attacker fully controls.

Existing guards do not catch this: `require!(token_ids.len() == amounts.len() && !amounts.is_empty(), ...)` only checks the withdraw's own input arrays, not the promise result; `#[private]` only restricts the callback to be invoked by the contract itself as a scheduled callback (which is exactly the exploited path); there is no `checked_*`/invariant check tying the refund to the token contract's actual custody state.

### Impact Explanation
This breaks the invariant that a resolver refund must correspond to tokens that failed to settle. The attacker can repeatedly deposit self-issued NEP-245 "tokens" from their own contract into Defuse, then withdraw them through this path: the malicious `token` contract completes the transfer to `receiver_id` (attacker-controlled) on its own ledger, while Defuse's internal `token_balances` for `sender_id` is fully restored via `self.deposit`. This mints duplicate, unbacked internal balance for that `Nep245TokenId` inside Defuse's ledger — the ledger claims custody it no longer has. That inflated balance is a first-class asset within Defuse's `Verifier`/intents accounting and can subsequently be used in signed swap intents against other counterparties' genuine holdings, i.e. the Verifier's bookkeeping for that token type no longer matches what it actually custodies. This matches the Critical category "a refund or resolver credit that does not match what failed to settle" / "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies." The attack is fully repeatable per token/account/batch at negligible cost (deploy one malicious contract, then deposit/withdraw in a loop).

### Likelihood Explanation
Preconditions are entirely attacker-controlled: no privileged role, relayer key, or victim key is required. The attacker needs only to (1) deploy a `token`-style AccountId contract implementing `mt_batch_transfer_call` to return a malformed-length success value while completing the internal transfer, (2) deposit MT balance tagged with that contract into Defuse via the normal deposit flow to establish `token_balances[Nep245TokenId(token, id)]`, and (3) call `mt_withdraw` with `msg` set (to hit the `is_call` branch) targeting their own `receiver_id`. This is fully repeatable and requires only ordinary transaction gas costs — no race conditions, no third-party cooperation.

### Recommendation
In `mt_resolve_withdraw`, do not treat an `Ok` result with mismatched length as "zero used." Instead, treat a length mismatch the same as a malformed/untrusted response and refuse to refund optimistically — e.g., fall back to the same conservative branch used for `Err(_)` (assume nothing failed / no refund) rather than assuming a full refund, or explicitly reject/ignore malformed responses and keep the debit in place, requiring the `token` contract to prove compliant behavior before any refund is issued. At minimum, do not credit `sender_id` more than would be consistent with `token_ids`/`amounts` actually reported back verifiably by a spec-compliant contract.
