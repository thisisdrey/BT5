### Title
Heap buffer over-read in singlejar's Zip entry processing via unvalidated central-directory-derived local header pointer and size fields - (File: `src/tools/singlejar/input_jar.h`, `src/tools/singlejar/transient_bytes.h`)

### Summary
Like CVE-2017-6802, where `DecompressRTF()` trusted an attacker-controlled length field from an untrusted stream and read past the end of the source buffer, Bazel's `singlejar` tool (used to merge/process Java jar entries, including dependency jars pulled into the build) computes pointers and read lengths from attacker-controlled Zip Central Directory Header (CDH) and Local Header (LH) fields without validating them against the actual size of the memory-mapped input file.

### Finding Description
`InputJar::NextEntry()` advances the CDH cursor and validates that the *next CDH* pointer lies inside the mapped file via `mapped_file_.mapped(new_cdr)` [1](#0-0) . However, the companion `LocalHeader()` accessor computes the LH pointer directly from the untrusted `cdh->local_header_offset()` field (a 32/64-bit attacker-controlled value read straight from the archive) with **no equivalent bounds check** before dereferencing it: [2](#0-1) 

Once an LH pointer (potentially outside the mapped region, or inside it but with a header whose declared `file_name_length_`/`extra_fields_length_`/`compressed_file_size_`/`uncompressed_file_size_` fields are inflated) is obtained, callers such as `Concatenator::Merge()` use it to read entry contents via `TransientBytes::ReadEntryContents()` / `TransientBytes::DecompressEntryContents()` in `src/tools/singlejar/transient_bytes.h`. These functions compute `in_bytes`/`out_bytes` from the CDH/LH size fields and immediately call `Append(lh->data(), uncompressed_file_size)` or feed `lh->data()` to zlib's `inflater->DataToInflate(data, in_bytes_chunk)` with no verification that `data + in_bytes`/`data + out_bytes` stays within the bounds of the memory-mapped archive: [3](#0-2) 

This mirrors the ytnef bug class exactly: a length/offset value taken from attacker-supplied compressed-stream metadata (here, Zip CDH/LH fields) is used to drive a buffer read without first confirming it fits inside the actual allocated/mapped source buffer.

### Impact Explanation
`singlejar` is invoked by Bazel's Java build actions to merge jar files, including jars that originate from external dependencies (e.g., fetched via `http_jar`/`http_archive`/Maven-style rules) or from source control. A malicious jar with a crafted CDH `local_header_offset` and/or oversized `compressed_file_size`/`uncompressed_file_size` fields can cause `singlejar` to read heap memory beyond the mapped input file. Because the (over-)read bytes are subsequently copied/inflated into the constructed output jar, this could leak adjacent process heap memory into build artifacts, or crash the build process (heap over-read/segfault), constituting a memory-safety violation reachable purely by supplying a malformed archive.

### Likelihood Explanation
Reachability is straightforward: any external jar/zip dependency consumed by a Bazel Java build passes through `singlejar`'s `InputJar`/`Concatenator` path. An attacker only needs control over the bytes of an archive the victim's build fetches or accepts (e.g., a compromised/malicious mirror publishing a "valid" but structurally malformed jar, or an untrusted CI branch/build input). SHA256/checksum verification of the download (if present) does not protect against this bug, because the archive can be self-consistent from a hashing standpoint while still containing malformed internal Zip structure (bad `local_header_offset`, oversized size fields) — the checksum only guarantees byte-for-byte integrity of the file that was intentionally crafted this way.

### Recommendation
- In `InputJar::LocalHeader()`, validate that the computed LH pointer and the full local header (including `file_name_length()`/`extra_fields_length()`) lie within `mapped_file_` bounds before returning it, mirroring the existing check done for CDH advancement in `NextEntry()`.
- In `TransientBytes::ReadEntryContents()`/`DecompressEntryContents()`, validate that `lh->data() + in_bytes` (and `+ out_bytes`) do not exceed the mapped file's end before calling `Append()`/`DataToInflate()`.
- Add fuzz/unit tests feeding crafted CDH entries with out-of-range `local_header_offset` and inflated size fields to `InputJar`/`Concatenator` and assert graceful error handling rather than an out-of-bounds read.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Construct a minimal Zip file with one CDH entry whose `local_header_offset32` points near the end of the mapped file (e.g., `mapped_file_size - 4`), and/or whose `uncompressed_file_size`/`compressed_file_size` fields are set to a large value (e.g., `0xFFFFFF`) while the actual local header + data present in the file is only a few bytes.
2. Run `singlejar --output out.jar --sources crafted.jar` (or trigger it via a `java_library`/`java_binary` build depending on `crafted.jar` as a resource/dep jar).
3. Under a memory-sanitized build (ASan), observe a heap-buffer-overflow (over-read) report inside `TransientBytes::ReadEntryContents`/`DecompressEntryContents` or in `LH` field accessors reached from `InputJar::LocalHeader()`, confirming the read extends past the mapped input file.

Note: I was not able to fully inspect `src/tools/singlejar/mapped_file.h` (the `MappedFile::address()`/`mapped()` implementation) within this session to confirm whether it performs any implicit bounds clamping; this should be verified as part of remediation to confirm the exact point where the missing check needs to be added.
