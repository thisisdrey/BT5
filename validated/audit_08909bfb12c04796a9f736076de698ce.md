## Title
Malicious actors can DoS a legitimate large TRC10 crowdsale purchase by front-running it with a dust `ParticipateAssetIssueContract` - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
`ParticipateAssetIssueActuator.validate()` hard-requires that the issuer's (`toAddress`) remaining TRC10 balance be *strictly sufficient* to cover the exact `exchangeAmount` computed from a buyer's `amount`, with no fallback to a partial fill. Because this check is evaluated against the issuer's current on-chain balance at the moment the transaction is validated/executed (either during `pushTransaction` mempool admission or during `generateBlock`/`processBlock`), an attacker can submit a trivial dust `ParticipateAssetIssueContract` targeting the same asset issue that lands before a victim's large, near-cap purchase, causing the victim's transaction to fail and effectively be dropped.

### Finding Description
In `validate()`, the check that gates whether a participate-transaction can proceed is: [1](#0-0) 

This computes `exchangeAmount` from the buyer's TRX `amount` and requires `toAccount.assetBalanceEnoughV2(assetName, exchangeAmount, dynamicStore)` to be true, i.e. the issuer must still hold at least `exchangeAmount` of the token. There is no minimum-fill / partial-fill option — if the issuer's remaining token balance drops even by 1 unit below what the buyer requested, `validate()` throws `ContractValidateException("Asset balance is not enough !")` and the whole buy fails.

The same "all-or-nothing" pattern is repeated at execution time: [2](#0-1) 

An attacker who is monitoring the mempool (or simply racing a broadcaster's own submission) can send a minimal `ParticipateAssetIssueContract` (buying, e.g., the smallest possible amount) targeting the same crowdsale/asset, timed to be processed before the victim's near-cap purchase. This is directly analogous to the reported `AuctionRebalanceModuleV1` bug: a strict "requested amount ≤ remaining amount" check with no partial-fill fallback lets a cheap dust order grief a large order for the same finite pool of "remaining quantity."

The effect of a failing `validate()` is significant in java-tron's transaction pipeline:
- At mempool admission time, `pushTransaction` runs `processTransaction` inside a session and any `ContractValidateException` propagates back to the broadcaster/`Wallet.broadcastTransaction`, i.e. the victim's transaction is rejected outright rather than queued: [3](#0-2) [4](#0-3) 
- During block packing, each pending transaction is polled off the queue and attempted once; if it throws, it is simply logged and dropped rather than re-queued: [5](#0-4) 

So a dust `ParticipateAssetIssueContract` that shaves the issuer's remaining balance below what the victim requested can cause the victim's transaction to be rejected at broadcast time, or silently dropped during block production, requiring the victim to resubmit — and the attacker can repeat this cheaply every time.

### Impact Explanation
This is a Medium-severity griefing/DoS: it doesn't steal funds directly, but it lets an unprivileged actor reliably block other users from completing large purchases of a token crowdsale near its remaining supply, force repeated retries at the victim's cost (bandwidth/energy for each failed attempt still may be considered, and definitely wasted time/opportunity), and can be used to manipulate who is able to acquire the final chunk of a limited TRC10 issuance. It maps to the "no valid partial-fill / off-by-dust revert" bug class from the report, reachable purely through the public `ParticipateAssetIssueContract` transaction type available to any account.

### Likelihood Explanation
Likelihood is high for popular/limited asset issues: the attack requires only enough TRX to pay the tiny purchase amount plus fee, is fully permissionless, and can be repeated indefinitely against any target transaction that buys near the remaining token balance of an ongoing `AssetIssueContract` sale.

### Recommendation
Support partial fills in `ParticipateAssetIssueActuator`: when the requested `exchangeAmount` exceeds the issuer's remaining token balance, either cap the purchase to the available remaining amount (returning the excess TRX) or provide the buyer with a "minimum acceptable amount" parameter (slippage-style protection) so their transaction succeeds with a partial amount instead of unconditionally reverting on any change to the issuer's balance.

### Proof of Concept
1. Issuer `T` creates an ongoing TRC10 crowdsale via `AssetIssueContract` with a large but finite remaining balance.
2. Victim `Alice` broadcasts a `ParticipateAssetIssueContract` requesting an `amount` that converts (via `trxNum`/`num`) to nearly all of `T`'s remaining token balance.
3. Attacker `Bob`, watching the mempool, broadcasts his own `ParticipateAssetIssueContract` for a dust `amount` (e.g. smallest unit) targeting the same `toAddress`/asset, timed/prioritized to be processed first.
4. When `Bob`'s transaction executes first, `toAccount`'s asset balance in `AccountCapsule` (checked in `assetBalanceEnoughV2`, `reduceAssetAmountV2`) drops below what Alice requested. [6](#0-5) 
5. Alice's transaction now fails `validate()` with `"Asset balance is not enough !"`, either being rejected at broadcast (`Wallet.broadcastTransaction`) or dropped during block packing without being retried automatically. [5](#0-4) 
6. Bob repeats this against every retry Alice makes, indefinitely blocking her purchase at negligible cost to himself.
