### Title
Denial of Service via unbounded array allocation in `ValidateMultiSign`/`BatchValidateSign` precompiled contracts before length validation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` helper methods in `PrecompiledContracts.java` allocate a `byte[][]` array whose size is taken directly from attacker-controlled calldata (`words[offset].intValueSafe()`) before any bound is enforced against that value. The `MAX_SIZE` (16) sanity check that limits this value is only executed when the `VMConfig.allowTvmSelfdestructRestriction()` hard-fork flag is active; the vulnerable code path that skips the check is retained for backward compatibility and is directly reachable by any smart-contract call to the `ValidateMultiSign` / `BatchValidateSign` precompiles.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a length word straight from calldata and immediately allocate an array of that size: [1](#0-0) 

In `ValidateMultiSign.execute`, the `MAX_SIZE` bound check on the array-size word is gated behind a config flag, and the fallback path calls `extractBytesArray` unconditionally, before any size check: [2](#0-1) 

The same pattern repeats in `BatchValidateSign.doExecute`: [3](#0-2) 

This is structurally identical to the Spring Data Commons bug class described in the report: an untrusted, attacker-supplied numeric field is used directly to size a memory allocation before validation, letting a caller force the process to attempt allocating an outsized data structure. Here the length word comes from a `DataWord` (256-bit) parsed from EVM calldata and passed through `intValueSafe()`; when `VMConfig.allowTvmSelfdestructRestriction()` is disabled (or on chains/heights where that hard-fork flag hasn't been activated), an attacker can set this word to a very large value and reach `extractBytesArray`/`extractBytes32Array` without any prior bound check, causing `new byte[len][]` to be executed with an oversized `len`.

### Impact Explanation
Because these precompiled contracts execute as part of ordinary contract execution (reachable from any TVM `CALL`/`STATICCALL` to the precompile addresses used by `ValidateMultiSign`/`BatchValidateSign`), every full node that validates the block containing such a transaction performs the same allocation attempt. A successful trigger produces an `OutOfMemoryError`/excessive GC pressure on all validating nodes simultaneously, which can crash node processes or severely degrade throughput — a deterministic, network-wide Denial of Service consistent with the CWE-400 classification of the reference advisory, and touching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Reachability requires only a signed transaction that triggers a smart contract call to the `ValidateMultiSign` or `BatchValidateSign` precompile address with crafted calldata — something any unprivileged contract caller can construct. The severity depends on whether `VMConfig.allowTvmSelfdestructRestriction()` is enabled on the target network/height; where it is disabled the `MAX_SIZE` guard never executes and the vulnerable path is directly hit. I was not able to fully confirm from the available index whether this flag is active by default on current mainnet at the analyzed commit, or whether `intValueSafe()` clamps to a value still large enough to cause practical OOM (e.g., `Integer.MAX_VALUE`); this should be verified in a live environment/Devin session before treating this as unconditionally exploitable.

### Recommendation
Move the `MAX_SIZE` bound check on the array-length word so it is unconditionally enforced in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves — before performing the array allocation — rather than depending on the caller to have applied a hard-fork-gated pre-check. Additionally validate that the length is consistent with the remaining calldata size before allocating, mirroring the `verifyLength`/`isValidAbiEncoding` bounds checks already used elsewhere in this file.

### Proof of Concept
1. Deploy or call an existing contract that performs a `STATICCALL`/`CALL` to the `ValidateMultiSign` (or `BatchValidateSign`) precompile address.
2. Craft the ABI-encoded calldata so the array-length word inside the array-offset location (`words[offset]`) — normally the count of provided signatures/addresses — is a very large value (e.g., close to `Integer.MAX_VALUE`).
3. On a network/height where `VMConfig.allowTvmSelfdestructRestriction()` is not active, submit the transaction; execution reaches `extractBytesArray`/`extractBytes32Array` and allocates `new byte[len][]` with the attacker-supplied `len`, forcing an excessive memory-allocation attempt on every node that executes/validates the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
