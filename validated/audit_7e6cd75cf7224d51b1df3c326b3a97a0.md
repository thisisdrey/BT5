### Title
Unbounded array allocation in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles allows an unprivileged contract call to OOM-crash a node - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `lib-net` report describes an attacker who controls a length field read off the wire and uses it to force an oversized allocation before any bound is checked, exhausting memory and crashing the process (OOM-reaper kill). The java-tron analog is in the TVM precompiled-contract layer: the `ValidateMultiSign` and `BatchValidateSign` precompiles read an attacker-supplied 32-byte word from the transaction/contract call data and use it directly as an array length for `new byte[len][]`, with no bound check unless a specific chain-parameter guard (`allowTvmSelfdestructRestriction`) has been activated by governance.

### Finding Description
`extractBytesArray` and `extractBytes32Array` take the array length straight from the caller-controlled ABI-encoded data and allocate without validation: [1](#0-0) 

`ValidateMultiSign.execute` only bounds `sigArraySize` before calling the extractor **when** `VMConfig.allowTvmSelfdestructRestriction()` is enabled; on the legacy branch (flag disabled) it calls `extractBytesArray` with the raw, unchecked length: [2](#0-1) 

`BatchValidateSign.doExecute` has the same pattern: the `sigArraySize`/`addrArraySize` bound check only runs inside the `allowTvmSelfdestructRestriction()` branch, but the extraction calls (`extractBytesArray`/`extractSigArray`/`extractBytes32Array`) are unconditional: [3](#0-2) 

Both precompiles are reachable from ordinary TVM `CALL`/`STATICCALL` opcodes to addresses `0x...09` (BatchValidateSign) and `0x...0a` (ValidateMultiSign), gated only by `VMConfig.allowTvmSolidity059()`: [4](#0-3) 

Any unprivileged account can deploy or call a contract that performs this `CALL`, supplying an offset word whose `intValueSafe()` yields a huge value (close to `Integer.MAX_VALUE`), triggering `new byte[len][]` — an immediate multi-gigabyte allocation attempt.

### Impact Explanation
When `allowTvmSelfdestructRestriction` is not yet activated on a given chain (it is a governable chain parameter defaulting to inactive until turned on by proposal, per `DynamicPropertiesStore`), this legacy code path is live in the current codebase and reachable by any transaction executing a contract call to these precompile addresses. The resulting massive array allocation can throw `OutOfMemoryError`. In `BatchValidateSign.execute`, the outer wrapper catches `Throwable` and returns gracefully, but `ValidateMultiSign.execute` performs the extraction call outside any try/catch, so the `OutOfMemoryError` propagates out of the precompile directly into the TVM call stack. Repeated/parallel invocation (a single crafted transaction, or many, since this is cheap to construct and callable by anyone) can destabilize or crash node JVM processes, degrading or halting transaction processing — analogous to the reported "network not being able to confirm new transactions" impact, though scoped by the JVM heap ceiling rather than raw OS memory as in the original Rust report.

### Likelihood Explanation
Reachable by any account via a simple smart-contract `CALL` to a public precompile address; no special privileges required. Exploitability is contingent on the `allowTvmSelfdestructRestriction` governance flag being inactive on the target network, which is the historical/legacy default until the corresponding TIP is activated by super representatives.

### Recommendation
Move the `sigArraySize`/`addrArraySize` (and general array-length) bound checks unconditionally, before any call to `extractBytesArray`, `extractSigArray`, or `extractBytes32Array`, regardless of the `allowTvmSelfdestructRestriction` flag state, so the legacy code path can no longer allocate an unbounded array. Additionally wrap the extraction calls in `ValidateMultiSign.execute` with the same defensive `catch (Throwable)` pattern already used in `BatchValidateSign.execute`, and consider imposing a hard maximum length check inside `extractBytesArray`/`extractBytes32Array` themselves as a defense-in-depth measure independent of any TIP activation flag.

### Proof of Concept
1. Craft ABI calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign(...)`) where the offset word pointed to by the `bytes[]` parameter is set so that `words[offset].intValueSafe()` returns a value close to `Integer.MAX_VALUE` (e.g., `0x7fffffff`).
2. Deploy a trivial contract that performs a `CALL` to precompile address `0x...0a` with this calldata (requires `allowTvmSolidity059` active, which is standard).
3. Submit the transaction as any funded account, on a network where `allowTvmSelfdestructRestriction` has not been activated.
4. Observe `ValidateMultiSign.execute` invoking `extractBytesArray(words, offset, rawData)` which executes `new byte[len][]` with `len ≈ Integer.MAX_VALUE`, throwing `OutOfMemoryError`, uncaught within the precompile, propagating into the TVM interpreter and potentially destabilizing the node process handling the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
