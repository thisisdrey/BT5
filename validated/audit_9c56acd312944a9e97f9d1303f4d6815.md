## Title
Fixed callback gas budgeting in `nep_141_storage_balance_callback` / `address_check_callback` lets an attacker permanently strand the eth-implicit `WalletContract` in the "in-flight" state - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` gates all future execution on a single boolean, `has_in_flight_tx`, which is set to `true` right before scheduling a promise chain and is only cleared inside the asynchronous callbacks that resolve that chain [1](#0-0) . Exactly like the Wenwin `RNSourceController` bug (where a reverted external call left `lastRequestFulfilled` stuck at `false` with no automatic recovery), a caller who controls the gas attached to `rlp_execute` can make an intermediate callback receipt fail (out-of-gas), which rolls back the `has_in_flight_tx = false` write together with the rest of that receipt's state changes, leaving the flag permanently `true`.

### Finding Description
`rlp_execute` immediately rejects any call while `has_in_flight_tx` is `true`, and otherwise sets it `true` right before returning the scheduled `Promise` [2](#0-1) . The flag is only ever reset to `false` inside the private callbacks `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer`, at the very start of each function body [3](#0-2) [4](#0-3) [5](#0-4) .

For a `ERC20Transfer`, the gas given to the intermediate callback is computed as a fixed base plus the user-controlled action gas: `let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());` [6](#0-5) . Inside `nep_141_storage_balance_callback`, the code path taken depends on the *result* of the first cross-contract call: if the receiver is unregistered, the callback must additionally schedule **two more** `function_call`s (`storage_deposit` + the transfer) plus the final `rlp_execute_callback` hop, which is materially more gas-expensive than the "already registered" branch that only needs one extra hop [7](#0-6) . `address_check_callback` has the analogous shape for `EOABaseTokenTransfer` [8](#0-7) .

Because NEAR receipt execution is atomic (a receipt that fails, e.g. via `GasExceeded`, discards *all* of its state writes — as documented for this runtime: "When a receipt fails, its state changes are rolled back using `TrieUpdate`" [9](#0-8) ), if the caller attaches just enough gas for the "cheap" branch of the callback but the runtime resolves into the "expensive" branch (extra `storage_deposit` hop), the callback receipt exceeds its `callback_gas` budget mid-execution. This is functionally identical to the Solidity report's `try{}catch{}` gas-starvation: an externally controllable gas parameter causes a specific step of a multi-hop asynchronous flow to fail, and the "clear the in-progress flag" write performed earlier in that same execution is never actually committed because the whole receipt (including the `self.has_in_flight_tx = false;` write at line 202) is rolled back. The persisted value of `has_in_flight_tx` reverts to `true` (the value it was set to when the *first* hop of the promise chain was scheduled in `rlp_execute`/scheduled promise), permanently blocking the invariant check at the top of `rlp_execute` [10](#0-9) .

Unlike the Wenwin lottery (which at least has a `retry()`/`maxRequestDelay` recovery path and an owner-controlled `swapSource()` escape hatch), `WalletContract` has **no timeout, retry, or admin override** for `has_in_flight_tx` at all — once stuck `true`, `rlp_execute` will reject every future call forever, with no code path capable of clearing it (only the private callbacks can, and no new callback will ever be scheduled since `rlp_execute` refuses to proceed).

### Impact Explanation
This causes permanent freezing of the eth-implicit account: `rlp_execute` is the sole intended entry point for authorizing NEAR actions (transfers, function calls, key management) from that account, and it will unconditionally short-circuit once `has_in_flight_tx` is stuck `true` [11](#0-10) . Any $NEAR balance or NEP-141 tokens held by/routable through that account become permanently inaccessible through this mechanism, satisfying the "permanent freezing of funds" impact bar. Any unprivileged relayer submitting the outer NEAR transaction controls the attached gas, and the gas required by each callback branch is a function of runtime state (whether the receiver is already registered with the token contract), making the failure trivially triggerable without any special privilege.

### Likelihood Explanation
Likelihood is high: relayers are by design unprivileged/untrusted parties (the contract explicitly anticipates "faulty relayer" behavior with `ban_relayer`), any relayer picks the attached gas for the outer transaction, and simply choosing a gas value that comfortably covers the "receiver already registered" branch but not the "receiver needs `storage_deposit`" branch reliably drives the callback receipt into an out-of-gas failure at the specific point after the state has logically progressed but before the write is committed.

### Recommendation
Do not rely on state written earlier in the same (possibly-failing) receipt to represent durable progress. Structure `has_in_flight_tx` reset so that it is guaranteed to be committed independent of whether subsequent promise scheduling in the same callback succeeds — e.g., clear the flag and persist that single state change before attempting any further gas-metered work, or use a dedicated cheap final callback (with a fixed, conservatively-sized gas reservation not derived from user input) solely responsible for clearing the flag, so an out-of-gas failure later in the chain cannot roll back the flag reset. Also consider adding a fallback/timeout so a wallet cannot be locked indefinitely.

### Proof of Concept
1. Relayer submits an RLP-encoded `ERC20Transfer` to `rlp_execute` where `receiver_id` is *not yet* registered with the NEP-141 token's storage standard.
2. Relayer attaches attached-gas/`action.gas()` sized just above what `NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()` needs for the "receiver already registered" branch (single extra hop), but insufficient for the "receiver not registered" branch, which needs `storage_deposit` + transfer + `rlp_execute_callback` (three chained actions) [12](#0-11) .
3. `rlp_execute` sets `has_in_flight_tx = true` and schedules `storage_balance_of(...).then(nep_141_storage_balance_callback(...))` [13](#0-12) .
4. `storage_balance_of` returns `None` (unregistered), so `nep_141_storage_balance_callback` enters the expensive branch and runs out of its allotted `callback_gas` while scheduling the multi-action promise.
5. The `nep_141_storage_balance_callback` receipt fails (`GasExceeded`); its `self.has_in_flight_tx = false;` write (line 202) is rolled back along with the rest of the receipt's state changes.
6. Persisted `has_in_flight_tx` remains `true` forever; all future `rlp_execute` calls for this account immediately return the "transaction already in progress" error with no way to recover.
