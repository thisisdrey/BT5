### Title
Unbounded central-directory offset lets `InputZipFile::ProcessNext` seek/read outside the mapped zip file — ([File: third_party/ijar/zip.cc])

### Summary
This is the same bug class as the ALSA report: a value taken directly from attacker-controlled data is turned into a pointer/offset with no upper-bound check against the object it indexes into, and the "remaining bytes" guard that should catch this is defeated by unsigned-integer wraparound, so the code goes on to dereference memory outside the buffer.

### Finding Description
`InputZipFile::ProcessNext` (`third_party/ijar/zip.cc:302-330`) reads the per-entry `offset` field straight out of the central directory (and, for zip64 entries, out of the extra field, via `ProcessCentralDirEntry`, `third_party/ijar/zip.cc:493-545`, lines 515 and 538-540 `*offset = get_u4le(p)` / `*offset = get_u8le(extra)`), both fully attacker-controlled 32/64-bit values embedded in the zip file being parsed. It then computes:

```
p = zipdata_in_ + in_offset_ + offset;
``` [1](#0-0) 

with no check that `offset` (or `in_offset_ + offset`) stays within the bounds of the mmap'd input file (`zipdata_in_`, sized to `input_file_->Length()`). Immediately after, `EnsureRemaining(4, "signature")` is supposed to be the bounds guard:

```
int EnsureRemaining(size_t n, const char *state) {
  size_t in_offset = p - zipdata_in_;
  size_t remaining = input_file_->Length() - in_offset;
  if (n > remaining) { ... return error(...); }
  return 0;
}
``` [2](#0-1) 

Because `in_offset` and `remaining` are `size_t` (unsigned), an `offset` large enough to push `p` past `zipdata_in_ + input_file_->Length()` makes `remaining = Length() - in_offset` underflow to a huge value, so `n > remaining` is false and the check silently passes. `get_u4le(p)` at `third_party/ijar/zip.cc:319` and the subsequent `ProcessLocalFileEntry` parsing then read from an out-of-bounds address, exactly mirroring the pattern in the kernel report: an attacker-supplied offset with "no bound of any kind" that lets a fault handler (here, a parser) walk off the end of the backing object.

This is the ijar/zipper zip reader that Bazel uses to parse zip/jar archives it consumes (e.g., stripping interface jars from precompiled `.jar` dependencies, and general zip/jar extraction via the `zipper`/`ijar` binaries). The bytes being parsed are exactly the bytes an external origin (a `http_jar`/`http_file`/`http_archive` source, or any archive on an untrusted branch that CI builds) serves; a checksum on the whole archive only guarantees the *outer* bytes match what was requested, it does nothing to constrain the *internal* zip metadata (offsets, sizes) from being self-inconsistent/malicious.

### Impact Explanation
An attacker who controls the content served at an archive URL (or a malicious `.jar`/`.zip` published as a dependency) can craft a central-directory entry with a huge `offset`/zip64 offset. When Bazel's ijar/zipper tooling processes that archive during a build, the unsigned-underflow in `EnsureRemaining` defeats the bounds check and the code reads out-of-bounds memory relative to the mmap'd file. Depending on the offset chosen, this can crash the build tool (denial of service on the specific invocation) or read adjacent heap/mapped memory content into the parser state (e.g., filenames/sizes copied out via `memcpy` in `ProcessCentralDirEntry`), which can leak into build outputs or error messages. This is a genuine memory-safety violation triggered purely by untrusted archive content, matching the report's "no bound of any kind" bug class and the requirement that a hostile origin's bytes defeat an invariant (here, the "stay within extracted/mapped object" containment invariant) that the code appears to enforce but doesn't due to the underflow.

### Likelihood Explanation
High. Any code path that parses a zip/jar with `ijar`'s `zip.cc` reader (`third_party/ijar` is used both by the `ijar` interface-jar tool and the standalone `zipper`) will call `InputZipFile::ProcessNext`/`ProcessCentralDirEntry` on every entry of an attacker-supplied archive. Constructing a zip with a bogus local-header offset (or a zip64 extra-field offset field) is trivial and requires no special privileges — the attacker only needs to be the origin of a dependency archive that a victim's build fetches and processes.

### Recommendation
In `EnsureRemaining`/`ProcessNext`, validate `offset` (and `in_offset_ + offset`) against `input_file_->Length()` *before* computing `p`, using overflow-safe arithmetic (e.g., check `offset > Length() - in_offset_` first, or use bounds-checked addition), and reject the entry with an error rather than allowing `p` to advance past the end of the mapped buffer. Apply the same fix to all places in `zip.cc` that derive a pointer from an attacker-supplied offset/size (e.g., `ProcessCentralDirEntry`'s extra-field walking loop, and `FindZip64CentralDirectory`).

### Proof of Concept
A `BuildIntegrationTestCase`/shell-style reproduction, analogous to `third_party/ijar/test/zip_test.sh`'s existing `test_no_path_traversal` test:
1. Programmatically build a minimal valid zip with one entry, then patch the central-directory "relative offset of local header" field (and, for a zip64 variant, the zip64 extra-field 8-byte offset) to a very large value (e.g., `0xFFFFFF00` or `2^63`) that is larger than the file length.
2. Run the `ijar`/`zipper` binary (or invoke `ZipExtractor::Create`+`ProcessAll` directly in a C++ test, as done in `third_party/ijar/zip_test.cc`-style tests) against this crafted archive.
3. Observe a crash (SIGSEGV) or an out-of-bounds read instead of a clean `"local file header signature ... not found"` error, demonstrating that `EnsureRemaining`'s unsigned-subtraction guard is bypassed by the unbounded attacker-controlled offset.
