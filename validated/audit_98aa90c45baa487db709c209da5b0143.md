### Title
Stale `PostponedReceipt` entries survive `remove_account`, allowing pre-deletion receipts (including `DeleteKey`) to execute against a re-created account of the same name - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` purges `TrieKey::Account`, `TrieKey::ContractCode`, all access keys/gas-key nonces, and `TrieKey::ContractData`, but it never enumerates or removes `TrieKey::PostponedReceipt` (nor the associated `PostponedReceiptId`/pending-data-count bookkeeping) that was written for that `account_id` as `receiver_id` by `set_postponed_receipt`. Because NEAR allows an account name to be deleted and later re-created, a postponed receipt that was pending against the old account instance can resolve later and execute its actions against the unrelated, re-created account.

### Finding Description
`set_postponed_receipt` stores a not-yet-runnable `ActionReceipt` keyed purely by `{receiver_id, receipt_id}`: [1](#0-0) 

Such postponed receipts are created whenever a receipt's `input_data_ids` are not all resolved yet (e.g. a `.then()`-style callback receipt whose parent promise has not returned data). The receipt (which can contain arbitrary actions, including `DeleteKey`, targeting the receiver account) sits in the trie until a matching `ReceivedData` arrives and the pending-data counter reaches zero, at which point it is promoted and executed against whatever account currently exists under that `receiver_id`.

`remove_account` is the single clear/cleanup routine invoked from `DeleteAccount` action processing (`runtime/runtime/src/actions.rs`) and only removes: [2](#0-1) 
access keys / gas-key nonces: [3](#0-2) 
and contract data: [4](#0-3) 

It never calls `remove_postponed_receipt` (defined a few lines above) nor iterates a `PostponedReceipt`/`PostponedReceiptId` prefix for the account: [5](#0-4) 

**Exploit flow (unprivileged attacker, sub-account scenario):**
1. Attacker owns account `A` (e.g. `sub.parent.near`) and deploys a contract.
2. Attacker's contract creates a promise chain: `P1` (a call whose result won't be delivered immediately, e.g. cross-shard/cross-contract call) `.then(promise_batch_action_delete_key(pk))` targeting itself (`receiver_id = A`). Because `P1`'s data hasn't arrived, this callback receipt is stored via `set_postponed_receipt` under `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}`.
3. Before the data for `P1` arrives, attacker submits `DeleteAccount { beneficiary_id }` for `A`. `remove_account` wipes the account, code, keys, and data — but the postponed `DeleteKey` receipt row remains in the trie, orphaned.
4. Account name `A` is later re-created (e.g. by the parent account, a legitimate different owner) via `CreateAccount`, and the new owner adds a full-access key `pk`.
5. The attacker (who still controls timing/content of `P1`'s completion, since they authored it) triggers delivery of the `ReceivedData` for `P1`'s data id. The runtime finds the still-present `PostponedReceipt{receiver_id: A, receipt_id}`, decrements the pending count to zero, and executes it against the *current* state of `A` — the re-created account.
6. If the hard-coded target public key in the postponed `DeleteKey` action matches the key added by the new owner, that full-access key is deleted without any authorization from the new owner.

No existing check re-validates that the receiver account is the "same" logical account instance (there is no account epoch/generation tag in `TrieKey::PostponedReceipt`), so nothing in the resolution path detects the intervening delete+recreate cycle.

### Impact Explanation
This is an authorization-exactness violation: actions authorized/queued under one account "incarnation" execute against a different, unrelated incarnation of the same name after deletion and recreation, with no re-validation of the new owner's consent. In the specific `DeleteKey` case this can strip the new owner's full-access key (permanent loss of access, matching the "authorization escalation across accounts" bounty category). Even outside the exact-`DeleteKey`-target scenario, the same structural gap means the stale receipt (whatever actions it carries) still executes against the reincarnated account, which is itself the audited invariant violation.

### Likelihood Explanation
The precondition that most limits real-world impact is that the attacker's `DeleteKey` action must target the exact public key later added to the recreated account — the attacker cannot query or steer the new owner's future key choice at receipt-creation time. This is realistic in scenarios where key material is deterministic/reused (common HD-wallet or custodial re-provisioning flows) or where the "new owner" is effectively the same operator/organization recreating the sub-account with a known/fixed key. Constructing the postponed receipt itself is trivial and fully within attacker capability (no validator/node access needed) — it only requires a self-call promise chain plus a `DeleteAccount` transaction, all of which an ordinary funded account can submit to a public RPC. The underlying code defect (missing cleanup in `remove_account`) is unconditionally reproducible independent of the key-guessing constraint.

### Recommendation
`remove_account` should enumerate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and related pending-data-count entries keyed by the account as `receiver_id` before/while deleting the account, mirroring the existing prefix-iteration pattern already used for access keys and contract data. Alternatively, tie postponed-receipt resolution to an account generation/incarnation identifier so a receipt created against an old incarnation cannot resolve against a newer one.

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or a runtime integration test):
1. Build a `TrieUpdate`, call `set_account` for `account_id`, then call `set_postponed_receipt` with a `Receipt` whose `receiver_id() == account_id` (and, for completeness, populate matching `PostponedReceiptId`/pending-data-count rows using the same helpers used by `runtime/runtime/src/lib.rs`).
2. Call `remove_account(&mut state_update, &account_id)`.
3. Assert `get_postponed_receipt(&state_update, &account_id, receipt_id).unwrap().is_none()` — this assertion fails today because `remove_account` never removes the `PostponedReceipt` row.
4. (Integration-level extension) Drive the full scenario through `runtime/runtime/src/lib.rs`'s receipt-processing test harness: create account, submit a `.then()` `DeleteKey` receipt that is postponed, `DeleteAccount`, `CreateAccount` + `AddKey` with the same public key used in the postponed action, deliver the missing `ReceivedData`, and observe the full-access key being deleted from the re-created account without any transaction signed by the new owner authorizing it.

pub fn set_postponed_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    assert!(matches!(receipt.versioned_receipt(), VersionedReceiptEnum::Action(_)));
    let key = TrieKey::PostponedReceipt {
        receiver_id: receipt.receiver_id().clone(),
        receipt_id: *receipt.receipt_id(),
    };
    set(state_update, key, receipt);
}
