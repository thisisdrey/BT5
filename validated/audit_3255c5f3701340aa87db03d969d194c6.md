### Title
Unhandled `NullPointerException` from `protobuf.parseFrom(null)` in Market/Exchange capsule constructors reachable from `MarketCancelOrderActuator`/`MarketSellAssetActuator`/Exchange actuators — ([File: chainbase/src/main/java/org/tron/core/capsule/MarketOrderIdListCapsule.java])

### Summary
Multiple `TronStoreWithRevoking`-backed stores (`MarketOrderStore`, `MarketPairPriceToOrderStore`, `ExchangeStore`, `ProposalStore`) construct their capsule objects directly from the raw bytes returned by `revokingDB.get(key)`:

```java
// MarketPairPriceToOrderStore
public MarketOrderIdListCapsule get(byte[] key) throws ItemNotFoundException {
  byte[] value = revokingDB.get(key);
  return new MarketOrderIdListCapsule(value);
}
``` [1](#0-0) 

The capsule constructors only guard against a malformed-but-non-null byte array:
```java
public MarketOrderIdListCapsule(final byte[] data) {
  try {
    this.orderIdList = MarketOrderIdList.parseFrom(data);
  } catch (InvalidProtocolBufferException e) {
    logger.debug(e.getMessage(), e);
  }
}
``` [2](#0-1) 

`com.google.protobuf.AbstractParser.parseFrom(byte[])` throws a `NullPointerException` (not `InvalidProtocolBufferException`) when the input array is `null`. That NPE is **not caught** by the constructor's `catch (InvalidProtocolBufferException e)` block, so it propagates straight out of the store's `get()` call. This is the same bug class as CVE-2019-8382: a lookup helper (`AP4_List::Find`) that can fail to produce a valid object, and the caller uses the result without validating it — here the "lookup" is `revokingDB.get(key)` returning `null` for a missing/inconsistent key, and the capsule wrapper mishandles that null, producing an uncaught NPE instead of the declared checked exception.

### Finding Description
The vulnerable pattern is used identically in several market/exchange stores:
- `MarketOrderStore.get()` → `new MarketOrderCapsule(value)` [3](#0-2) 
- `MarketPairPriceToOrderStore.get()` → `new MarketOrderIdListCapsule(value)` [1](#0-0) 
- `ExchangeStore.get()` → `new ExchangeCapsule(value)` [4](#0-3) 
- `ProposalStore.get()` → `new ProposalCapsule(value)` [5](#0-4) 

All the corresponding capsule constructors (`MarketOrderCapsule(byte[])`, `MarketOrderIdListCapsule(byte[])`, `ExchangeCapsule(byte[])`) only catch `InvalidProtocolBufferException`, never `NullPointerException`, e.g.: [6](#0-5) [7](#0-6) 

These `get()` methods are invoked directly inside broadcastable-contract actuators without any null-guard on the returned capsule before use, e.g. `MarketCancelOrderActuator.execute()`:
```java
byte[] orderId = contract.getOrderId().toByteArray();
MarketOrderCapsule orderCapsule = orderStore.get(orderId);
...
MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);
orderIdListCapsule.removeOrder(orderCapsule, orderStore, pairPriceKey, pairPriceToOrderStore);
``` [8](#0-7) 

and `MarketSellAssetActuator.matchOrder()`:
```java
MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);
...
MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);
matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);
``` [9](#0-8) 

If `revokingDB.get(key)` returns `null` for a key that is referenced by market/exchange linked-list metadata but whose value has been deleted or is otherwise absent from the underlying store (e.g. through inconsistent revoke/flush timing, corrupted DB state, or a race introduced by future data-model changes), the capsule constructor throws an unguarded `NullPointerException`. Because `execute()`/`validate()` in these actuators only declare `catch (ItemNotFoundException | InvalidProtocolBufferException | ...)`, this NPE is **not** one of the checked/caught exception types and propagates out of the actuator into `RuntimeImpl.execute()` / `TransactionTrace`, i.e., out of the normal error-handling path for contract execution.

### Impact Explanation
An uncaught `RuntimeException` (here `NullPointerException`) escaping actuator execution during block application is a node-crash/halt class issue: it is not one of the exceptions the transaction-processing pipeline is designed to convert into a failed-but-recoverable transaction result. Depending on where exactly it surfaces (broadcast-time TX validation vs. block-application inside `Manager`), it can cause:
- A crash/unhandled exception when processing a transaction during `pushTransaction`, or
- Worse, if it occurs during block application (SR node building a block that includes such a transaction, or any node re-executing a block), it can produce inconsistent processing between nodes or an unhandled exception that halts block application — a potential chain-halt / DoS condition, analogous to the Bento4 NPE causing a crash of `mp4dump`.

This matches the CVE's core impact (Denial of Service / crash via unchecked null dereference reachable from processing untrusted/attacker-influenced input).

### Likelihood Explanation
I was **not able to fully confirm** that `revokingDB.get(key)` can actually return `null` (as opposed to throwing `ItemNotFoundException` itself, which would make this path unreachable in practice) within the time available — `revokingDB.get()`'s exact contract lives in the `TronStoreWithRevoking`/underlying `Chainbase`/`RevokingDB` layer, which I did not get to inspect. If `revokingDB.get()` always throws `ItemNotFoundException` on a missing key and never returns `null`, this specific NPE path would not be reachable through the "key not found" case, and the analog would only materialize from other rare null-byte scenarios (e.g., empty stored value, or a bug in DB compaction/revoke pointer handling). This is a real gap in the analysis and should be verified by a background agent before treating this as a confirmed, exploitable bug.

### Recommendation
1. Verify (in `chainbase/src/main/java/org/tron/core/db/TronStoreWithRevoking.java` and the revoking DB implementation) whether `revokingDB.get(key)` can return `null` for a missing key, or whether it always throws `ItemNotFoundException`.
2. Regardless, harden all capsule constructors that call `XXX.parseFrom(data)` (`MarketOrderCapsule`, `MarketOrderIdListCapsule`, `ExchangeCapsule`, `ProposalCapsule`, and any other capsule with the same pattern) to explicitly null-check `data` before calling `parseFrom`, and to throw/propagate a well-defined, caught exception (e.g., `ItemNotFoundException`/`BadItemException`) instead of allowing an uncaught `NullPointerException`.
3. Add defensive null checks immediately after every `orderStore.get(...)`, `pairPriceToOrderStore.get(...)`, `exchangeStore.get(...)` call in actuator `execute()`/`validate()` paths before the result is dereferenced, mirroring the pattern already used for `AccountStore.get()` (`if (x == null) throw new ContractValidateException(...)`).
4. Add unit tests that simulate a missing/inconsistent underlying key at execute-time (not just validate-time) for `MarketCancelOrderActuator`, `MarketSellAssetActuator`, `ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator` to ensure no unguarded NPE can escape.

### Proof of Concept
A concrete, deterministic PoC requires access to the `TronStoreWithRevoking`/`RevokingDB` implementation to force `revokingDB.get(key)` to return `null` bytes (or an environment where flush/revoke ordering allows a referenced key, e.g. a `pairPriceKey` still linked from `pairToPriceStore`, to be missing from `pairPriceToOrderStore` at execute time). Conceptually:
1. Create a market sell order pair such that a `pairPriceKey` exists in `pairToPriceStore`/`pairPriceToOrderStore`.
2. Through crafted/adversarial ordering of transactions in the same block (cancel + concurrent match, or a revert/flush timing issue), cause the `MarketOrderIdListCapsule` value for that `pairPriceKey` to be absent from the underlying DB while still being referenced.
3. Submit a `MarketCancelOrderContract` or `MarketSellAssetContract` transaction that triggers `pairPriceToOrderStore.get(pairPriceKey)` in `execute()`.
4. If `revokingDB.get()` returns `null` bytes for that key, `new MarketOrderIdListCapsule(null)` throws an uncaught `NullPointerException` inside `MarketOrderIdList.parseFrom(null)`, escaping the actuator's `catch` clauses.

Because step 2 could not be fully validated against the actual `RevokingDB`/`Chainbase` implementation in the time available, this PoC is provisional — a background agent with full codebase/test-harness access should confirm whether `revokingDB.get()` ever returns `null` for a missing key before treating this as a fully proven, exploitable DoS.
