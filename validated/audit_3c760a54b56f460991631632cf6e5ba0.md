### Title
Non-atomic repository partition assignment allows front-running of repository/fork/pool creation - (File: internal/gitaly/storage/storagemgr/partition_assigner.go)

### Summary
Gitaly assigns every repository's relative path to a storage partition the first time it is accessed, and this assignment is persisted permanently in the key-value store. For repository-creating RPCs, Gitaly deliberately allows a partition to be assigned for a relative path *before* the repository itself is created, so the write transaction that will create it has somewhere to go. This assignment step is not atomic with the actual authorized repository-creation logic (which is responsible for correctly grouping a fork/pool member with its object pool's partition). An ordinary client can race a repository-creating RPC against the same relative path ahead of the legitimate creation flow and thereby dictate/"claim" the partition assignment for that path, exactly mirroring the reported bug class: a security-relevant binding (mintHook / here, partition-to-pool binding) that should be set atomically at creation time can instead be front-run by an unprivileged caller because the gate is applied lazily and separately from the privileged operation.

### Finding Description
`beginTransactionForRepository` marks certain RPCs (`repositoryCreatingRPCs`, e.g. `CreateRepository`, `CreateFork`, `CreateObjectPool`, `ReplicateRepository`) with `AllowPartitionAssignmentWithoutRepository: isRepositoryCreation` when beginning a transaction: [1](#0-0) 

This flag lets `getPartitionIDRecursive` create and persist a partition assignment for a relative path that does not exist on disk yet, purely because the RPC is classified as a creation RPC — with no verification that the *caller* attempting to squat the path is actually the one who will legitimately create it there: [2](#0-1) 

The assignment is written to the embedded key-value store immediately via `setPartitionID`, independent of and prior to the write-ahead-logged transaction that actually creates the repository: [3](#0-2) 

Gitaly's own documentation acknowledges this is not atomic and can leave stale/incorrect assignments: [4](#0-3) [5](#0-4) 

Partitioning is meant to guarantee that a fork (or any repository about to be linked to an object pool) lands in the *same* partition as its pool, so that transaction ordering keeps the fork and the pool's objects consistent: [6](#0-5) 

Because the assignment for a not-yet-existing path can be created by *any* repository-creating RPC racing for that same relative path — not necessarily the one that will end up performing the "real"/intended creation with the correct alternate/pool hint — a client can pre-empt the assignment (e.g., issue a plain `CreateRepository`/`ReplicateRepository` for a path that a fork or object-pool operation is about to target) and force that path into an arbitrary partition before the legitimate, alternate-aware creation logic runs. This is directly analogous to the reported "front-run the mintHook" bug: the security-relevant binding (here, "this repository belongs in the same partition as its pool") is supposed to be established atomically by the privileged/legitimate creation flow, but the underlying resource (partition assignment) is left open to being set by an ordinary, unprivileged create request that gets there first.

### Impact Explanation
If an unprivileged caller wins the race and assigns a fork's or pool member's target relative path to the wrong partition before the legitimate fork/pool-linking RPC runs, the invariant that a repository and its object pool must share a partition is broken. Per Gitaly's own documentation, this can cause "updating a reference in a fork before the objects are written into the pool" and other consistency issues within the transactional/WAL guarantees, since transactions cannot be ordered across partitions. Additionally, because assignments are permanent (never deleted, even if the repository creation fails or the repository is later deleted), a squatted/incorrect assignment persists and cannot be self-healed by legitimate follow-up requests, producing a lasting integrity defect for that relative path — a form of denial-of-service/data-consistency corruption reachable purely through ordinary repository-creation RPCs.

### Likelihood Explanation
Exploitation requires an attacker capable of issuing repository-creating RPCs (any authenticated Gitaly client, including a client only supposed to create their own repositories/forks) to race a chosen relative path against a legitimate creation/fork/pool-linking RPC for the same path. Gitaly's maintainers already flag this exact non-atomicity as an open, tracked issue (referenced inline as gitlab-org/gitaly#5957), which corroborates that the race window and its consequences are real and currently unresolved, making this a credible, concretely reachable path rather than a theoretical scenario.

### Recommendation
Make partition assignment atomic with the repository-creation transaction that establishes the pool/alternate relationship, rather than allowing any repository-creating RPC to pre-assign a partition for an arbitrary not-yet-existing relative path. Concretely: only allow `AllowPartitionAssignmentWithoutRepository` when the RPC also supplies (and the assigner verifies) the correct alternate/origin hint up front, and/or defer persisting the assignment until the repository-creation write-ahead-log entry that actually creates the repository (and its alternates file, if any) is committed, rolling back the assignment if creation fails. This closes the same class of window the mint-front-running finding describes: an unprivileged actor should not be able to fix the outcome of a privileged/atomic setup step before the legitimate operation completes.

### Proof of Concept
1. Attacker (or any client with repository-creation access on a shared storage) determines/predicts the relative path `P` that will shortly be used as the target of a legitimate `CreateFork`/`CreateObjectPool` call (paths are often deterministic, e.g. hashed by project ID).
2. Attacker issues a `CreateRepository` (or any other `repositoryCreatingRPCs` member) targeting `P` without any alternate/pool hint. This calls `beginTransactionForRepository` → `Begin` with `AllowPartitionAssignmentWithoutRepository: true`, which reaches `getPartitionIDRecursive` and immediately persists a partition assignment for `P` via `assignPartitionID`/`setPartitionID` — see [7](#0-6) .
3. Shortly after, the legitimate `CreateFork`/`CreateObjectPool` RPC for `P` runs; per `getPartitionID`, since `P` already has a stored assignment, the "hint" logic in lines 156-190 of `partition_assigner.go` must match the attacker-established partition or the request fails with `ErrRepositoriesAreInDifferentPartitions` — either breaking the intended fork/pool grouping or forcing an operational failure, both of which are unavailable to the legitimate caller to prevent because the assignment was already fixed by the attacker's earlier, unrelated request.

```go
func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}

		// With the repository under lock, verify it is a Git directory before we assign it into a partition.
		// It's okay if the repository doesn't yet exist as this transaction may be about to create it.
		if err := storage.ValidateGitDirectory(filepath.Join(pa.storagePath, relativePath)); err != nil {
			if errors.Is(err, fs.ErrNotExist) {
				if !isRepositoryCreation {
					return 0, relativePathNotFoundError(relativePath)
				}

				// Repository creations are allowed to target non-existing repositories. They create the partition
				// where the repository is to be created.
			} else {
				return 0, fmt.Errorf("validate git directory: %w", err)
			}
		}

		ptnID, err = pa.assignPartitionID(ctx, relativePath, recursiveCall, partitionHint)
		if err != nil {
			return 0, fmt.Errorf("assign partition ID: %w", err)
		}
	}

	return ptnID, nil
}

func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}
```

```markdown
Gitaly automatically assigns repositories to partitions when they are first accessed:

- Object pools and all repositories connected to the object pool are placed in the same partition. Repositories that are about to be connected to an object pool, such as newly created forks, are also placed in the same partition with the object pool they are about to be connected.
  - Assigning pools and their connected repositories into the same partition ensures transactions can guarantee consistency between them. If pools were in different partitions, transaction ordering could cause issues, for example updating a reference in a fork before the objects are written into the pool.
- Repositories that are not connected (nor about to be connected) to an object pool are placed in their own partitions.

Whether repository is, or is about to be connected to an object pool, is determined from multiple sources:

- If it has an `info/alternates` file, the repository is currently connected to a pool.
- If it is an RPC that contains an additional repository in the request, the repository is about to be connected.
  - For example, `CreateFork` contains the origin repository as an additional repository. We place the fork in the same partition as an objet pool might be created, and the fork and the origin connected to it.
  - `CreateObjectPool` will similarly place the object pool into the same partition as the source repository since it will generally be connected to it.

Partitioning is handled in the `StorageManager` component. This component handles routing transactions to the correct partitions, and starting and stopping partitions as needed. The partition assignments are retrieved or created at
[this location in the codebase](https://gitlab.com/gitlab-org/gitaly/-/blob/7c0f925b3df33c77de8c124b5f89447a13da3059/internal/gitaly/storage/storagemgr/partition_manager.go#L331) when a transaction is began against a repository for the first time. The assignment handling is fairly crude at the moment. The assignments are created before the repository is even created, and assignments are not deleted even if the repository is deleted.
```
