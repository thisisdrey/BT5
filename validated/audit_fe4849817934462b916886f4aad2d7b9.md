### Title
Unbounded prefix-scan and in-memory sort in `DelegatedResourceAccountIndexStore.getV2Index` allows attacker-inflatable DoS via `GetDelegatedResourceAccountIndexV2` API - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
The `getV2Index`/`getWithPrefix` method backing the `GetDelegatedResourceAccountIndexV2` HTTP/gRPC endpoint performs an unbounded key-prefix scan and an in-memory sort over every delegation record ever created for a given address, with no cap on the number of entries. Because creating a new delegation-index entry only costs an unprivileged `DelegateResourceContract` transaction (minimum 1 TRX, no limit on number of distinct receiver/sender addresses), an attacker can cheaply inflate the number of entries under a single address to a very large number and then repeatedly query that address via the public read API, forcing the node to do large unbounded work per request.

### Finding Description
`DelegateResourceActuator.delegateResource` calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, timestamp)` for every delegation, unconditionally writing two new keys keyed by `V2_FROM_PREFIX + owner + receiver` and `V2_TO_PREFIX + receiver + owner`: [1](#0-0) [2](#0-1) 

There is no limit anywhere in `validate()` on the number of distinct receiver addresses an owner can delegate to (only a per-pair balance/lock check), so an attacker who owns one frozen-balance account can repeatedly delegate the minimum 1 TRX to N distinct freshly-created/activated receiver accounts, creating N `V2_FROM_PREFIX` entries under their own address key space: [3](#0-2) 

When the address is later queried via `getV2Index`, the store performs a `prefixQuery` (a full linear scan/collection of every key sharing the prefix) for both the FROM and TO directions, converts the results into a `List`, and sorts the entire list by timestamp in memory before returning it: [4](#0-3) 

`prefixQuery` itself iterates the underlying RocksDB/LevelDB from the seek point until the prefix no longer matches, materializing every matching key/value pair into a `HashMap` before returning: [5](#0-4) 

This is reachable directly by any anonymous API client via the fullnode/solidity/PBFT HTTP servlet `GetDelegatedResourceAccountIndexV2Servlet`, which forwards straight to `wallet.getDelegatedResourceAccountIndexV2(address)` with no size cap or pagination: [6](#0-5) 

This mirrors the reported bug class exactly: an unrestricted, attacker-inflatable array (here, delegation-index entries per address) is fully iterated and sorted with no bound, inside a read path reachable by any unprivileged caller — the only difference from the Solidity example is that the "array" is grown by prior cheap transactions rather than passed directly as a parameter, but the effect (unbounded O(N log N) work triggerable per query, with N attacker-controlled) is the same.

### Impact Explanation
Each call to `GetDelegatedResourceAccountIndexV2` for an attacker-inflated address performs O(N) DB scanning plus O(N log N) sorting, where N is fully controlled by the attacker's prior (cheap) delegate transactions. Repeated invocation of this read-only, rate-limited-but-not-size-limited endpoint against such an address can consume disproportionate CPU/I/O on full nodes, SolidityNode and PBFT-serving nodes that expose this API, degrading or denying service to legitimate API clients (a concrete "node ... can no longer serve" condition for this API path).

### Likelihood Explanation
Likelihood is moderate-to-high: the precondition (creating many delegation-index entries) requires only minimum 1 TRX delegation transactions to N distinct existing, non-contract receiver accounts — well within reach of a single funded, unprivileged account issuing many low-cost transactions over time. The query endpoint is unauthenticated and requires only knowledge of the target address (which is public, e.g. the attacker's own).

### Recommendation
- Cap the number of delegation-index entries returned/scanned per address (e.g., cap `prefixQuery` results or add a max-entries guard in `getWithPrefix`), or paginate `GetDelegatedResourceAccountIndexV2` similarly to `getPaginatedNowWitnessList`/`getAssetIssuesPaginated`.
- Consider bounding, at the actuator level, how many distinct delegation index records (`FROM`/`TO`) can be created per address, or enforce a maximum via `getCanDelegatedMaxSize`-style checks that apply globally rather than per-pair.
- Alternatively, avoid full in-memory sort by timestamp on every read; store entries pre-ordered or limit sort cost with a bounded working set.

### Proof of Concept
1. Attacker account A freezes balance for bandwidth/energy (`FreezeBalanceV2Contract`), then repeatedly sends `DelegateResourceContract` transactions delegating the minimum 1 TRX to N distinct receiver addresses B1..BN (each Bi only needs to be an existing non-contract account) — each such transaction is accepted per `DelegateResourceActuator.validate()`/`execute()` with no cap on N.
2. Each call appends a new `V2_FROM_PREFIX + A + Bi` key via `delegatedResourceAccountIndexStore.delegateV2`.
3. Attacker (or anyone) repeatedly calls `GET /wallet/getdelegatedresourceaccountindexv2?value=<A>` (or the gRPC/JSON-RPC equivalent).
4. Each call triggers `getV2Index(A)` → `getWithPrefix` → `prefixQuery(V2_FROM_PREFIX+A)` scanning and materializing all N entries, then sorting them in memory — cost scales with N, which the attacker fully controls and can grow indefinitely at low cost.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  @Override
  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    resetDbLock.readLock().lock();
    try (final ReadOptions readOptions = getReadOptions();
         final RocksIterator iterator = getRocksIterator(readOptions)) {
      Map<WrappedByteArray, byte[]> result = new HashMap<>();
      for (iterator.seek(key); iterator.isValid(); iterator.next()) {
        if (Bytes.indexOf(iterator.key(), key) == 0) {
          result.put(WrappedByteArray.of(iterator.key()), iterator.value());
        } else {
          return result;
        }
      }
      return result;
    } finally {
      resetDbLock.readLock().unlock();
    }
  }
