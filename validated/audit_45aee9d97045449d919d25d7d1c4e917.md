### Title
Reference-counter leak when all proc-receive updates are rejected — `PostReceive` API call is skipped, permanently incrementing the "active push" counter - ([File: internal/gitaly/hook/receivepack/receive_pack.go])

### Summary
This is a structural analog of the reported bug class: an accounting side-effect (the `PostReceive`/reference-counter decrement) is only executed on one outcome branch of a request (successful reference updates) but not on the other (all updates rejected), even though the corresponding increment (`PreReceive`) is applied unconditionally whenever the pre-receive hook runs. Exactly like the burn-fee that is only paid on wins and not losses, the reference counter here is only decremented on "wins" (accepted updates) and never on "losses" (all updates rejected), leaving persistent unbalanced state.

### Finding Description
GitLab's push reference-counter is incremented in `preReceiveHook` via `m.gitlabClient.PreReceive(ctx, repo.GetGlRepository())` [1](#0-0)  every time the pre-receive hook is invoked for the primary node, regardless of whether the push's reference updates ultimately succeed or are rejected.

The corresponding decrement is performed by `PostReceiveHook` → `postReceiveHook` → `m.gitlabClient.PostReceive(...)` [2](#0-1) . However, in the `git-receive-pack` proc-receive execution path, the post-receive hook is only invoked conditionally:

```go
// The post-receive hook only executes if there are successful updates.
if len(acceptedUpdates) > 0 {
    ...
    hookManager.PostReceiveHook(...)
}
``` [3](#0-2) 

In the non-atomic branch, each reference update is attempted individually; if the associated `update` hook returns a `CustomHookError`, the update is added to `rejectedUpdates` instead of `acceptedUpdates` [4](#0-3) . If every requested reference update in a push is rejected this way (or the atomic path fails), `acceptedUpdates` remains empty, and the guarded call to `PostReceiveHook` — and consequently `gitlabClient.PostReceive` — is never made. The `PreReceive` increment made earlier in the same push, however, was already committed unconditionally. This creates a permanent asymmetry: the counter is incremented but never decremented for that push.

Per the hooks documentation, this counter tracks "how many pushes are active at the same time," and repository-move/mirror-style operations wait for it to reach zero before proceeding: "If the reference counter is not at 0, there are active pushes happening." [5](#0-4) 

### Impact Explanation
Any unprivileged user who can push to a repository and trigger a custom `update` hook rejection (or otherwise cause all proc-receive updates to be rejected) can leave the GitLab-side per-repository push reference counter permanently incremented. This is a straightforward, repeatable DoS vector against repository lifecycle operations gated on that counter (e.g., repository storage moves), since the counter never returns to zero for the affected repository after such a push, blocking these operations indefinitely without requiring any privileged access.

### Likelihood Explanation
Likelihood is high: triggering an `update` hook rejection is trivial for any user with push access when server-side custom hooks are configured to reject certain refs/commits (a common configuration, e.g. branch/commit policy enforcement), or when the non-atomic proc-receive path is exercised with multiple refs where all are rejected. No special privileges, timing races, or malicious peers are required — this is exercised purely through ordinary push RPC handling (`git-receive-pack` proc-receive flow).

### Recommendation
Ensure the `PostReceive` (reference-counter decrement) call is made unconditionally whenever `PreReceive` was called for the same push, independent of whether any reference updates were accepted. For example, restructure `procReceiveHook` so that the counter-decrementing call happens regardless of `len(acceptedUpdates)`, while keeping the *messages/custom-hook* execution logic conditioned on accepted updates if desired:

```diff
-	// The post-receive hook only executes if there are successful updates.
-	if len(acceptedUpdates) > 0 {
+	// The reference counter must always be decremented to match the unconditional
+	// increment performed in the pre-receive hook, even if no updates were accepted.
+	{
 		hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.PostReceiveHook)
 		...
 	}
```
More precisely, decouple the reference-counter accounting call (`gitlabClient.PostReceive`) from the "print messages / run custom hooks" logic so the counter is always balanced with the pre-receive increment, even when `acceptedUpdates` is empty.

### Proof of Concept
1. Configure a custom `update` server hook on a repository that unconditionally rejects updates (returns non-zero / writes to stderr) for at least one pushed reference.
2. As an ordinary user with push access, push a change using a client/path that exercises the proc-receive flow (`git-receive-pack` with proc-receive hook enabled), including one or more reference updates, such that every reference update is rejected by the `update` hook.
3. Observe that `preReceiveHook` already called `gitlabClient.PreReceive` and incremented GitLab's reference counter for the repository before the update hook ran [1](#0-0) .
4. Because `acceptedUpdates` is empty (all updates were rejected in `receivePackReferenceUpdates`/proc-receive loop) [4](#0-3) , the `if len(acceptedUpdates) > 0` guard prevents `PostReceiveHook` from running at all [3](#0-2) , so `gitlabClient.PostReceive` is never called and the counter is never decremented.
5. Repeat step 2 for the same repository; each such rejected push further increments the counter without ever decrementing it, permanently blocking any GitLab-side operation gated on the "active pushes" counter reaching zero for that repository.
