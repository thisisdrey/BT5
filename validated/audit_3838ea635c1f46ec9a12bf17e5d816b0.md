### Title
Heap-based buffer over-read parsing malicious ZIP/JAR Central Directory entries in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in Bazel's `ijar` tool parses each Central Directory Header (CDH) of a ZIP/JAR file entirely without bounds validation, unlike its sibling `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every field read. A crafted JAR whose CDH declares oversized `file_name_length`/`extra_field_length`/`file_comment_length` (or a corrupt Zip64 extra-field `data_size`) drives the parsing cursor `p`/`extra_p` past the end of the memory-mapped input buffer, causing subsequent `get_u2le`/`get_u4le`/`get_u8le` reads on out-of-bounds heap memory — the same "unchecked length field advances read cursor past buffer" bug class as CVE-2019-7574 in SDL's `IMA_ADPCM_decode`.

### Finding Description
`ijar`'s `InputZipFile` mmaps the input archive and walks its Central Directory with `ProcessCentralDirEntry`: [1](#0-0) 

Note the total absence of `EnsureRemaining()` calls here, even though the file has just skipped forward by attacker-controlled `file_name_length`, `extra_field_length`, and `file_comment_length` values (each up to `0xFFFF`) with no check that these lengths actually fit inside the mapped buffer. Compare this to `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` for every variable-length field: [2](#0-1) 

Inside the Zip64 extra-field loop of `ProcessCentralDirEntry`, `extra_p` is advanced by an attacker-controlled `data_size` with no check that `extra_p + data_size` stays within `p`: [3](#0-2) 

If `data_size`/`extra_field_length`/`file_comment_length` push `p` past the mapped region, the *next* iteration of the calling loop (`InputZipFile::ProcessNext` or `InputZipFile::CalculateOutputLength`) calls `ProcessCentralDirEntry` again with `p` already out of bounds, immediately dereferencing `get_u4le(p)` and further fields on unmapped/out-of-bounds heap memory: [4](#0-3) [5](#0-4) 

The code comment claiming safety ("the central directory is always followed by another data structure that has a signature, so parsing it this way is safe") only holds if every declared length field is itself validated against the actual buffer size — which it is not.

### Impact Explanation
`ijar` is invoked by Bazel's Java build rules (e.g., `java_import`/interface-jar generation) to process `.jar` files, including externally fetched dependencies. Even though `http_jar`/`http_archive`/module-registry fetches are checksum-pinned, the checksum only proves the bytes are unmodified in transit — it does nothing to prevent a hostile-but-legitimately-hashed JAR (published by the attacker and referenced with its own correct `sha256`/`integrity`) from containing a malformed Central Directory. Feeding such a JAR to `ijar` causes the parser to read past the end of its mmap'd input buffer, which can crash the process (SIGSEGV) or, when the buffer is contiguous with adjacent mapped data (e.g., an archive embedded in a larger self-extracting binary as done in `PartialZipExtractor`/`archive_utils.cc`), read unintended memory and feed corrupted length/offset values into subsequent processing.

### Likelihood Explanation
Any Bazel build that fetches a `.jar`/`.zip`/`.aar` from an external source and passes it through `ijar` (routine for `java_import`, prebuilt jar rules, and many `maven`/`http_jar` based dependency setups) can trigger this by simply hosting or publishing a malformed archive with the described oversized length fields. No MITM, credential access, or trusted-repo Starlark control is required — only that the victim's build consumes attacker-published bytes, which is the standard `http_jar`/`http_archive` threat model.

### Recommendation
Add the same `EnsureRemaining()` bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` for every fixed-size skip and for `file_name_length`, `extra_field_length`, `file_comment_length`, and to the inner Zip64 extra-field loop's `data_size`-driven advance of `extra_p`, rejecting the archive when any declared length would exceed the remaining mapped buffer.

### Proof of Concept
1. Build a minimal ZIP/JAR file containing one valid entry, then hand-patch its Central Directory Header so that `extra_field_length` (or `file_comment_length`) is set to a large value (e.g., `0xFFFF`) that extends past the actual end of the file/mapped buffer, while keeping the End-Of-Central-Directory record's reported `cen_size`/`cen_offset` internally consistent so `LocateCentralDirectory` still accepts the file.
2. Run `ijar`'s extractor (or `ProcessAll()`/`CalculateOutputLength()` as exercised by `third_party/ijar/zip_main.cc` or `PartialZipExtractor` in `src/main/cpp/archive_utils.cc`) against this file.
3. Observe a crash (ASan: heap-buffer-overflow READ, or SIGSEGV) inside `InputZipFile::ProcessCentralDirEntry`/`get_u4le` when the corrupted `p` pointer is dereferenced on the next central-directory iteration — add this as a new `third_party/ijar/zip_test.cc`/`zip_test.sh` regression case analogous to the existing `test_no_path_traversal` shell test in `third_party/ijar/test/zip_test.sh`.

  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
