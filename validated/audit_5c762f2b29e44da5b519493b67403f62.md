Audit Report

## Title
Unbacked value creation in `ERC20Transactor::withdraw_asset_with_surplus` via ERC20 tokens with non-standard transfer semantics (fee-on-transfer/rebasing/deflationary) - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits the XCM `AssetsInHolding` register with the requested `amount` whenever the ERC20 `transfer()` call returns `true`, without verifying that the checking account's actual token balance increased by that amount. Combined with `ERC20Matcher`/`IsLocalAccountKey20` accepting any `(0, [AccountKey20{..}])` location with no allow-list, and `pallet-revive` contract deployment being permissionless, an attacker can deploy a fee-on-transfer/deflationary ERC20 to mint phantom XCM holding value.

## Finding Description
`withdraw_asset_with_surplus` invokes `IERC20::transferCall { to: checking_address, value: amount }` via `pallet_revive::Pallet::<T>::bare_call`, and on a decoded `true` return constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))`, where `Erc20Credit(amount).amount()` simply returns the hardcoded `amount` value with no relation to any measured balance delta [1](#0-0) [2](#0-1) . There is no `balanceOf` check before/after the call. Symmetrically, `deposit_asset_with_surplus` transfers from the checking account and treats a `true` return as fully successful regardless of actual balance movement [3](#0-2) .

`ERC20Matcher` is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, and `IsLocalAccountKey20::contains` matches any `(0, [AccountKey20{..}])` location unconditionally — there is no allow-list of vetted contract addresses [4](#0-3) . This matcher is wired directly into `ERC20Transactor`, which is part of the live `AssetTransactors` tuple used by Asset Hub Westend's XCM executor [5](#0-4) .

Because contract deployment on `pallet-revive` is permissionless, an attacker can deploy a fee-on-transfer/deflationary ERC20 contract whose `transfer()` moves less than `value` while still returning `true`. Submitting an XCM program that withdraws such a token credits the executor's holding register with the full requested amount even though the checking account received less, creating unbacked value that can subsequently be deposited to any beneficiary via `deposit_asset_with_surplus`, draining the real backing held by `ERC20TransfersCheckingAccount`.

## Impact Explanation
This is theft/unbacked-value creation reachable from an unprivileged public entrypoint (XCM execution over a user-deployed `pallet-revive` contract), matching the "theft or unbacked mint" impact category. Repeated exploitation drains real token balance held by the checking account while the attacker's XCM holding reflects a phantom balance that can be moved to other accounts or bridged further.

## Likelihood Explanation
Likelihood is high: contract deployment via `pallet-revive` is permissionless, `ERC20Matcher`/`IsLocalAccountKey20` perform no allow-listing of contract addresses, and writing a Solidity `transfer()` that returns `true` while moving less than `value` (fee-on-transfer/deflationary pattern) is trivial and mirrors real-world token designs (e.g., USDT-style fee tokens).

## Recommendation
- Measure the actual `balanceOf` delta of the checking account (for withdraw) or beneficiary (for deposit) before/after the `transferCall`, and credit/consume exactly that delta rather than the requested `amount`.
- Alternatively, maintain a governance-controlled allow-list of vetted ERC20 contract addresses permitted for use with `ERC20Transactor`, rejecting any unvetted contract.
- Add integration tests using fee-on-transfer and rebasing mock ERC20 contracts to confirm the transactor cannot create unbacked value.

## Proof of Concept
1. Deploy `EvilERC20` via `pallet_revive::instantiate` whose `transfer(to, value)` moves only `value - fee` to `to` but returns `true`.
2. Fund attacker's account with `X` units of `EvilERC20`.
3. Attacker submits `pallet_xcm::execute` with `WithdrawAsset(Asset{ id: EvilERC20 location, fun: Fungible(X) })` followed by `DepositAsset { assets: All, beneficiary: attacker_or_other }`.
4. `withdraw_asset_with_surplus` calls `transfer(checking_account, X)`, which returns `true` but only moves `X - fee` to the checking account [6](#0-5) .
5. `AssetsInHolding` is nonetheless credited with the full `X`, and `deposit_asset_with_surplus` transfers `X` out of the checking account to the beneficiary, exceeding what the checking account actually received — demonstrating unbacked value creation.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
