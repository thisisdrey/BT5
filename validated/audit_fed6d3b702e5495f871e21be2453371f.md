Audit Report

## Title
Snowbridge relayer rewards can be permanently trapped on AssetHub because the reward-payment XCM omits an `AssetClaimer` hint - (File: bridges/snowbridge/primitives/core/src/reward.rs)

## Summary
`PayAccountOnLocation::pay_reward` in `bridges/snowbridge/primitives/core/src/reward.rs` builds and sends an XCM to AssetHub that performs `ReserveAssetDeposited` + `DepositAsset` into the relayer's beneficiary location, but never sets a `SetHints { hints: [AssetClaimer{..}] }` instruction, unlike the sibling inbound-message converter (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`) which explicitly adds this exact protection. `pallet_bridge_relayers::do_claim_rewards` (`bridges/modules/relayers/src/lib.rs`) clears the `RelayerRewards` storage entry and emits `RewardPaid` as soon as `pay_reward` returns `Ok(())`, which only confirms local XCM validation/delivery, not that the remote `DepositAsset` on AssetHub succeeded.

## Finding Description
`pay_reward` (`bridges/snowbridge/primitives/core/src/reward.rs` L127-151) constructs:
```
UnpaidExecution, DescendOrigin(InboundQueueLocation), UniversalOrigin(GlobalConsensus(Ethereum)),
ReserveAssetDeposited(assets), DepositAsset { assets: AllCounted(1), beneficiary }
```
with no `AssetClaimer` hint set for the beneficiary. If `DepositAsset` fails on AssetHub (e.g., beneficiary below existential deposit, asset not registered at the reanchored location), the assets fall into holding and get trapped via `PolkadotXcm::AssetsTrapped` under the technical bridge origin (`DescendOrigin`+`UniversalOrigin`), which the relayer cannot construct or authenticate as — making the trapped funds effectively unclaimable by the relayer.

Meanwhile `do_claim_rewards` (`bridges/modules/relayers/src/lib.rs` L263-301) calls `T::PaymentProcedure::pay_reward`, and on `Ok(())` immediately clears the `RelayerRewards` entry (via `try_mutate_exists`/`take()`) and emits `Event::RewardPaid` — this happens purely based on successful XCM *validation and delivery into the queue*, not on confirmation that the remote deposit executed. This is confirmed by the contrast with `converter.rs` (L386-394), which explicitly documents and implements the `AssetClaimer` mitigation for the analogous inbound-asset path ("Set claimer before PayFees, in case the fees are not enough... claimer will be able to claim the funds still"), and by the `invalid_xcm_traps_funds_on_ah` / `fallback_claimer_*` tests demonstrating the codebase already treats AssetHub-side XCM execution failure as a real, reachable outcome for this exact bridge.

## Impact Explanation
Any relayer claiming a Snowbridge reward whose beneficiary/location fails `DepositAsset` on AssetHub for ordinary reasons (uninitialized/under-ED account, unregistered asset at reanchored location) will have the reward balance irreversibly cleared from `RelayerRewards` on BridgeHub while the actual asset value is trapped on AssetHub under an origin the relayer cannot claim from. This is a direct, unbacked and unrecoverable loss of relayer funds, matching the "permanent user-fund or bridge-state lock" and "duplicate settlement or payout state advancing before execution/settlement succeeds" impact categories.

## Likelihood Explanation
No privileged, malicious, or off-repo actor is required — a relayer simply calling the public `claim_rewards_to` extrinsic with a beneficiary location that fails deposit conditions on AssetHub (a normal, reachable condition, not attacker-controlled maliciousness) triggers the loss. This is a self-inflicted-but-unrecoverable outcome reachable through ordinary use of scoped public extrinsics.

## Recommendation
Add a `SetHints { hints: [AssetClaimer { location: beneficiary }] }` instruction to the XCM program built in `PayAccountOnLocation::pay_reward`, placed before `DepositAsset` (mirroring the inbound converter's placement before `PayFees`), so that if the deposit fails, the relayer/beneficiary itself is the claimable origin for `pallet_xcm::claim_assets` on AssetHub, rather than the unreachable technical bridge origin.

## Proof of Concept
1. Register a relayer and accrue a Snowbridge reward via `register_relayer_reward` with `BridgeReward::Snowbridge`.
2. Call `claim_rewards_to` with a beneficiary AccountId32 location that does not exist / lacks existential deposit on AssetHub for the deposited asset.
3. On BridgeHub: `pay_reward` returns `Ok(())` (ticket delivered), `RelayerRewards` entry cleared, `RewardPaid` emitted.
4. On AssetHub: `DepositAsset` fails, `PolkadotXcm::AssetsTrapped` fires with origin equal to the descended/universal bridge-technical location.
5. Attempt `claim_assets` as the relayer/beneficiary — fails since the trap origin does not match any location the relayer can authenticate as, analogous to `fallback_claimer_trap_cannot_be_claimed_by_other_account`. The reward is permanently lost. [1](#0-0) [2](#0-1) [3](#0-2)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
