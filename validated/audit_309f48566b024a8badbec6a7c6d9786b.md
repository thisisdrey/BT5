Audit Report

## Title
`submit_delivery_receipt` pays the full relayer fee regardless of message delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The Snowbridge V2 outbound queue's `process_delivery_receipt` credits a relayer with the full `order.fee` via `T::RewardPayment::register_reward` and permanently removes the `PendingOrder` based solely on the existence of a matching nonce, without ever inspecting `receipt.success`. Since `DeliveryReceipt::success` faithfully reflects the real `InboundMessageDispatched(nonce, topic, success, reward_address)` Ethereum event [3](#0-2) , a genuine but failed delivery (`success = false`) still results in full payout and irreversible order removal.

## Finding Description
`submit_delivery_receipt` is a public, unprivileged extrinsic (`ensure_signed` only, no allowlist) that verifies the Ethereum event log via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` (which carries `success`), and forwards it directly to `process_delivery_receipt`: [4](#0-3) .

`process_delivery_receipt` looks up the `PendingOrder` by `receipt.nonce`, and if `order.fee > 0`, unconditionally calls `T::RewardPayment::register_reward` for the reward account before removing the order from `PendingOrders`. The `receipt.success` field is never read: [5](#0-4) .

The module documentation explicitly states the intended flow requires the message to be "verified **and executed**" before the reward is paid [6](#0-5) , confirming this is a missing check rather than intended behavior. The only guards present — `T::GatewayAddress::get() == receipt.gateway` and `PendingOrders::get(nonce)` — verify origin/nonce validity but do nothing to verify successful execution, so they are insufficient to prevent payout on failed delivery.

## Impact Explanation
This is a duplicate/incorrect-settlement bug: the relayer reward (funded from user message fees) is paid in full for messages that did not actually execute successfully on Ethereum, and the `PendingOrder` is irrecoverably deleted — there's no retry or reconciliation path for the failed nonce. This falls under "duplicate settlement or payout" / bridge-state advancing without successful execution, matching the required impact gate for message queues, bridge markers, receipts, and payout state needing to advance atomically only after decode, dispatch, execution, and settlement succeed.

## Likelihood Explanation
`submit_delivery_receipt` is fully public and permissionless; any account holding a valid Merkle/receipt proof for a genuine (but failed) `InboundMessageDispatched` event can trigger the full payout. `success = false` is a normal, achievable outcome of Ethereum-side command execution (e.g., insufficient gas or a revertible failure path), requiring no collusion with governance, validators, or the bridge operator.

## Recommendation
Check `receipt.success` in `process_delivery_receipt` before crediting the reward. On `success == false`, withhold or reduce the reward (or route to a distinct failure-handling/retry path) instead of unconditionally calling `register_reward` and removing the order as if delivery succeeded.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { fee, block_number }` [7](#0-6) .
2. On Ethereum, the corresponding command execution reverts/fails, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any account submits `submit_delivery_receipt` with a valid proof for this real `success=false` event.
4. `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false`, but `process_delivery_receipt` never checks it, so `order.fee` is paid via `register_reward` and `PendingOrders::remove(nonce)` deletes the order permanently [8](#0-7) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
