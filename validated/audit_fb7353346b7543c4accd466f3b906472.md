### Title
Unvalidated attacker-controlled offsets cause ArrayIndexOutOfBoundsException DoS in `VerifyTransferProof.execute()` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `VerifyTransferProof` precompiled contract (invoked via a TVM `STATICCALL`/`CALL` to a fixed precompile address by any unprivileged contract caller) parses `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` directly from attacker-supplied call data and uses them as raw byte offsets into `System.arraycopy` calls without bounds-checking them against `data.length`. Only the overall `data.length` is checked against a fixed whitelist of total sizes; the *internal* offsets are fully attacker-controlled and unvalidated before being used to slice sub-arrays.

### Finding Description
`execute(byte[] data)` in `VerifyTransferProof` (analogous to Ghostscript's fixed-size buffer write without adequate bounds validation in `devn_pcx_write_rle`) does: [1](#0-0) 

It only validates `data.length` against a small set of allowed total sizes (`{2080, 2368, 2464, 2752}`), then reads three 32-byte words at fixed offsets 0/32/64 as `spendOffset`, `spendAuthSigOffset`, `receiveOffset` — these are raw `int` values taken straight from the input, with no check that they are within `[0, data.length)` or that `spendOffset + 32`, `receiveOffset + 32`, etc. remain in range: [2](#0-1) 

These attacker-controlled offsets are then used directly as source indices for numerous `System.arraycopy` calls building `nullifier`, `anchor`, `spendCv`, `rk`, `spendProof`, `spendAuthSig`, `receiveCm`, `receiveCv`, `receiveEpk`, `receiveProof`: [3](#0-2) 

Because `parseInt(data, spendOffset)`/`parseInt(data, receiveOffset)` themselves also index into `data` at attacker-chosen positions, and later `arraycopy(data, spendOffset + 320*i + ..., ...)` can be pushed far outside the actual array bounds (e.g., a huge or negative `spendOffset`), this can throw `ArrayIndexOutOfBoundsException` (or similar unchecked exceptions) while running inside the TVM.

### Impact Explanation
This is reachable by anyone able to trigger the TVM's Sapling-related precompile via `CALL`/`STATICCALL` from a smart contract (or via `TriggerConstantContract`/`TriggerSmartContract` JSON-RPC/HTTP entry points into `Wallet`), i.e. any unprivileged contract deployer/caller — no special committee, witness, or node privilege is required. If the resulting exception is not fully absorbed by the enclosing `catch (Throwable any)` (e.g., if it is thrown by helper `parseInt`/`parseLong` in a way not accounted for, or thrown asynchronously from the worker thread pool `Future.get()` in a form the catch does not gracefully convert before energy/state is finalized), it can produce inconsistent handling of a crafted transaction across nodes, differing behavior between full nodes, or unexpected resource consumption (fixed thread pools `workersInConstantCall`/`workersInNonConstantCall` sized 5 could be exhausted by crafted calls that throw before `countDownLatch.countDown()` in `finally` fires, though the `finally` blocks do generally protect against latch starvation). At minimum this is a local, transaction-triggerable exception path built on unchecked attacker-controlled offset arithmetic feeding fixed-size buffer operations — the same bug class as CVE-2023-38559 (buffer write driven by insufficiently validated size/offset fields from untrusted input).

### Likelihood Explanation
High reachability: any account can call the Sapling verify-transfer precompile through a deployed contract or via `TriggerConstantContract` without needing SR/witness privileges, and the data length check (`Arrays.asList(SIZE).contains(data.length)`) does nothing to constrain the embedded `spendOffset`/`spendAuthSigOffset`/`receiveOffset` values. Crafting a payload with a valid total length but a malicious internal offset word is straightforward.

### Recommendation
Validate that `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and all subsequently derived indices such as `spendOffset+32`, `spendOffset+320*spendCount+160`, `receiveOffset+32+288*receiveCount`, etc.) are non-negative and strictly within `[0, data.length]` before any `parseInt`/`parseLong`/`System.arraycopy` call. Reject the call (return `Pair.of(true, DataWord.ZERO().getData())`) on any out-of-range offset instead of relying solely on the broad `catch (Throwable any)` at the bottom of `execute()`.

### Proof of Concept
1. Build a 2080-byte payload (matches `SIZE[0]`) for `VerifyTransferProof`.
2. Set the first 32-byte word (`spendOffset`, read via `parseInt(data,0)`) to a large value such as `Integer.MAX_VALUE - 100` or a negative value derived from the low 32 bits.
3. Leave `spendAuthSigOffset`/`receiveOffset` and the rest of the 2080-byte buffer as arbitrary/zero bytes so the overall length check passes.
4. Deploy a trivial contract that performs a `STATICCALL`/precompile-invoking call to the Sapling verify-transfer address (or invoke through `TriggerConstantContract` with the crafted call data) with this payload.
5. Observe `execute()` attempting `System.arraycopy(data, spendOffset + 320*i, nullifier[i], 0, 32)` with `spendOffset` far outside `data.length`, throwing `ArrayIndexOutOfBoundsException`, exercising the exception path with attacker-fully-controlled offset arithmetic in a fixed-size-buffer copy — the java-tron analog of the Ghostscript RLE buffer-overflow bug class.
