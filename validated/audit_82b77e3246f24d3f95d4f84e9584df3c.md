## Analog Found

### Title
Active-permission key holders can rewrite the Owner permission via `AccountPermissionUpdateContract`, permanently locking the account - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
The reported bug lets a lower-privileged "trusted" actor unilaterally overwrite the top-level trust state (`isTrusted`) of any account, including its own, causing an irrecoverable lockout. In java-tron, an analogous privilege-escalation/lockout path exists in the account multisig permission system: a non-Owner "Active" permission key can be authorized to submit `AccountPermissionUpdateContract` transactions, and that actuator will overwrite the account's `Owner` permission unconditionally, without ever confirming the transaction was actually signed under the Owner permission.

### Finding Description
Signature/permission enforcement for a broadcast transaction is generic and only checks that the signer's chosen `permission_id` allows the specific `ContractType` being submitted, via the `operations` bitmap on that permission: [1](#0-0) 

This same check is used both when adding a signature and when validating the fully signed transaction: [2](#0-1) 

Nothing in this generic path (or in `WalletUtil.checkPermissionOperations`) special-cases `AccountPermissionUpdateContract` to require `permission_id == 0` (Owner): [3](#0-2) 

Meanwhile, `AccountPermissionUpdateActuator.execute()` looks up the account purely by the `owner_address` field embedded in the contract body and unconditionally overwrites the Owner permission, Witness permission, and Active permissions with whatever the transaction specifies — it never inspects which permission id was used to sign the transaction that reached it: [4](#0-3) [5](#0-4) 

`validate()`/`checkPermission()` in the actuator only sanity-check the *shape* of the new permissions (key counts, weights, thresholds, valid contract-type bits), not who is allowed to submit them: [6](#0-5) 

As a result, if an account owner ever grants an Active permission an `operations` bitmap that includes the bit for `AccountPermissionUpdateContract` (type 46), any co-signer holding that Active key can single-handedly submit an `AccountPermissionUpdateContract` that replaces the account's Owner permission with keys it controls (or with an unsatisfiable threshold/keys nobody controls), removes the legitimate owner and other active keys, and permanently locks the account — exactly the "faulty trusted actor changes trust state of others / locks the contract forever" pattern from the report, just applied to on-chain account permissions instead of a Solidity mapping.

### Impact Explanation
This allows unauthorized escalation from an Active-tier key to full Owner-tier control of an account, and can be used to permanently freeze funds/assets held by that account (no key can ever satisfy the rewritten Owner permission threshold, and TRX/TRC10/TRC20 balances, votes, and resources become unrecoverable). This matches the "permanent freezing of funds" / "unauthorized account operation" acceptance criteria.

### Likelihood Explanation
This requires the account owner to have configured an Active permission whose `operations` bitmap includes `AccountPermissionUpdateContract`. This is not blocked by `checkPermission()` (which only verifies the bit maps to *some* valid, enabled `ContractType`, not that it's a safe one to delegate) so it is a plausible real-world misconfiguration, especially for exchange/custodial-style multisig setups that grant broad Active permissions to a bot/co-signer. Once granted, exploitation is a single, always-reachable transaction from that co-signer.

### Recommendation
Explicitly forbid `AccountPermissionUpdateContract` (and other high-impact "self-privilege-management" contract types) from being included in the settable bits of an `Active` permission's `operations` field during `checkPermission()`/`checkPermissionOperations()`, or require that `AccountPermissionUpdateContract` be signed strictly under `permission_id == 0` (Owner) regardless of the `operations` bitmap of any Active permission.

### Proof of Concept
1. Account `A` sets up multisig via `AccountPermissionUpdateContract`: Owner permission = {A}, and an Active permission (id 2) = {A, B} with `operations` bitmap bit 46 (`AccountPermissionUpdateContract`) enabled — this passes `checkPermission()` validation since 46 is presumably an "available" contract type.
2. Key `B` alone (weight sufficient to meet the Active threshold) constructs and signs a new `AccountPermissionUpdateContract` transaction with `permission_id = 2`, setting the new Owner permission to a key `C` that `B` controls (or to an unreachable threshold/key set).
3. `TransactionCapsule.checkPermission`/`WalletUtil.checkPermissionOperations` pass because bit 46 is set in `B`'s Active permission.
4. `AccountPermissionUpdateActuator.execute()` overwrites Owner permission on account `A` using `account.updatePermissions(...)` without checking that the submitting permission was Owner-tier.
5. Account `A`'s original owner key can no longer authorize any Owner-only operation, and if `C` is unusable/unknown, the account is permanently locked, mirroring the `setIsTrusted` DoS/lockout scenario in the source report.

*(Confidence note: I could not fully verify at what default value `DynamicPropertiesStore.getAvailableContractType()` initializes the "available contract types" bitmap, or whether `AccountPermissionUpdateContract`'s bit is excluded by default from that whitelist — the store's source lookup did not return the initialization logic within available tool calls. If the default whitelist already excludes bit 46, real-world exploitability would depend entirely on the account owner manually re-enabling it via a committee/governance-controlled parameter or a custom permission setup, which would lower likelihood.)*

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      throw new ContractValidateException(e.getMessage());

      throw new ContractValidateException("invalidate ownerAddress");

      throw new ContractValidateException("ownerAddress account does not exist");

      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }

        throw new ContractValidateException("account isn't witness can't set witness permission");
      }

      throw new ContractValidateException("active permission is missed");

    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    checkPermission(owner);

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
