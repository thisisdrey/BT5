### Title
Unbacked/negative Bancor-exchange pool balances via unchecked arithmetic in default (non-hardened) `ExchangeCapsule.transaction` - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The TRC10 Bancor-style `Exchange` mechanism tracks two token pool balances (`firstTokenBalance`/`secondTokenBalance`) that are supposed to always stay non-negative, analogous to the reported vault's `assetDepositNet` accounting invariant. The default (non-hardened) execution path performs unchecked `long` subtraction/addition rather than the checked, exception-throwing arithmetic used in the newly-added "hardened" mode, so the invariant can be silently violated in production.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances using either a checked path (`hardenedCalc == true`, using `StrictMathWrapper.addExact/subtractExact` and an explicit `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard that throws `ContractValidateException`) or the legacy default path, which just does `firstTokenBalance - buyTokenQuant` / `secondTokenBalance - buyTokenQuant` with plain Java `long` operators and **no negative-balance check at all** [3](#0-2) .

`hardenedCalc` is only `true` when `allowHardenExchangeCalculation()` returns true, which is gated by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` dynamic property [4](#0-3) . This property defaults to `0` and requires committee approval and a specific fork version to change, confirmed by the test asserting "current value is 0 (default)" [5](#0-4)  and by `getAllowHardenExchangeCalculation()`'s `orElse(0L)` default [6](#0-5) .

`ExchangeWithdrawActuator.doValidate()` does check `firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant` before executing withdrawals [7](#0-6) , but `ExchangeTransactionActuator.doValidate()` performs no such sufficiency check on the pool balances before calling `exchangeCapsule.transaction(...)` in non-hardened mode [8](#0-7) . This mirrors the STBL report's core defect: an unprivileged, single-transaction-reachable operation (`ExchangeTransactionContract`, broadcastable by any account via `ExchangeTransactionActuator`) can update accounting state using unchecked subtraction where the resulting balance is not guaranteed to remain non-negative, because the Bancor formula's rounding/precision and repeated small trades near-depleted pools can (in edge cases, e.g. with extreme quantities or precision loss in `ExchangeProcessor`) produce a `buyTokenQuant` that exceeds the remaining pool balance without the validate-path catching it, since validate re-runs the same non-hardened `transaction()` call and only checks `anotherTokenQuant < tokenExpected`, not against actual balance sufficiency.

### Impact Explanation
If a pool balance underflows to a negative `long` value, the corrupted `Exchange`/`ExchangeV2` capsule is persisted to the store via `Commons.putExchangeCapsule` [9](#0-8) . A negative token balance breaks the Bancor pricing formula for all subsequent trades against that pair (denominators/proportions become nonsensical), and can be leveraged to mint disproportionate `anotherTokenQuant` outputs for other traders — i.e., unbacked token issuance out of the exchange pool, or a permanent denial-of-service for that trading pair since further calculations against a negative balance are undefined/exploitable. This matches the report's "unbacked balance" / "permanent freezing of funds" criteria.

### Likelihood Explanation
Reaching this code path requires only a normal signed `ExchangeTransactionContract` broadcast by any account — no special privilege is needed, matching the "asset issuer/order placer/unprivileged broadcaster" reachability bar. However, exploitability depends on whether the Bancor `ExchangeProcessor.exchange()` calculation (non-hardened, using `BigInteger`/rounding) can actually be driven to produce a `buyTokenQuant` greater than the current pool's opposite-side balance without failing an earlier `> 0`/`balanceLimit` check; the report did not provide a concrete PoC for this specific pool-underflow scenario, and validate/execute both invoke the same non-hardened math, so consistent results are somewhat likely to prevent naive triggering. This is a plausible but not proven-exploitable path given available code; likelihood is assessed as Medium given the default-disabled hardening explicitly exists to fix exactly this unchecked-arithmetic class of bug.

### Recommendation
Enable `ALLOW_HARDEN_EXCHANGE_CALCULATION` by default (or make the checked/guarded arithmetic path in `ExchangeCapsule.transaction()` unconditional rather than opt-in), and add an explicit non-negative-balance guard in `ExchangeTransactionActuator.doValidate()`/`execute()` for the non-hardened path, consistent with the check already present in `ExchangeWithdrawActuator`.

### Proof of Concept
Not independently verified with a working end-to-end numeric trigger within the scope of this review; the analog is grounded in the confirmed default-disabled state of `ALLOW_HARDEN_EXCHANGE_CALCULATION` [5](#0-4)  and the unchecked-subtraction code path in `ExchangeCapsule.transaction()` [2](#0-1) , combined with the absence of a pool-sufficiency check in `ExchangeTransactionActuator` [8](#0-7) . A concrete numeric PoC (specific pool balances/quant sequence causing underflow) would need to be constructed and tested against `ExchangeProcessor`'s exact rounding behavior, which was not available in this ask-only review.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

    this.put(ALLOW_HARDEN_EXCHANGE_CALCULATION, new BytesCapsule(ByteArray.fromLong(value)));
