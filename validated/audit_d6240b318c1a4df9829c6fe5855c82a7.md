### Title
Sequential WAL apply enforcement can permanently deadlock a partition's `TransactionManager` on a failing log entry - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
Gitaly's WAL-based `TransactionManager` mirrors the same architectural pattern as the reported `BridgedGovernor` bug: log entries (transactions) must be applied strictly in ascending LSN order, and the manager offers no mechanism to skip or discard an entry that fails to apply. If `applyLogEntry` ever fails deterministically for a given LSN, the entire partition (and every repository routed to it) becomes permanently unable to process any further transaction, requiring manual operator intervention with an offline CLI tool.

### Finding Description
The `run` loop of `TransactionManager` enforces strict, gapless LSN ordering when applying committed log entries to disk: [1](#0-0) 

If `mgr.applyLogEntry(ctx, lsn)` returns an error for any reason, `run()` immediately returns that error, which terminates the manager goroutine entirely: [2](#0-1) 

The applied LSN is only ever advanced by `storeAppliedLSN`, which is called strictly after a successful `applyOperations` call inside `applyLogEntry`; there is no path that allows the manager to skip a bad LSN and move to `lsn+1`. When the owning `partition_manager.go` detects that `mgr.Run()` has returned, it deletes the partition from the active map so that a *new* `TransactionManager` instance will be created lazily on the next request: [3](#0-2) 

On restart, `initialize()` re-reads `appliedLSN` from the database and resumes applying from `appliedLSN+1` — i.e., the exact same failing LSN is retried: [4](#0-3) 

If the failure is deterministic (the same operations, same filesystem state, same manifest bytes are replayed every time), the manager will fail again immediately after every restart attempt, in an infinite crash loop — exactly the "irrecoverable state" pattern from the reference report, just realized as a WAL apply loop instead of a LayerZero nonce check.

This is explicitly acknowledged as an unrecoverable condition by Gitaly's own recovery tooling comment in the offline `recovery replay` CLI command, which is the only way to remove a malformed/stuck entry — and even that tool states the partition may be "broken completely" if this doesn't work: [5](#0-4) 

The apply step (`applyOperations`) performs raw filesystem hardlink/mkdir/remove/key-value operations based on the manifest recorded at commit time: [6](#0-5) 

Unlike the commit-time verification path (`verifyObjectsExist`, `verifyFileSystemOperations`, `verifyKeyValueOperations`), which runs against a snapshot before the log entry is durably appended, `applyOperations` runs later, against the live repository, and is not repeatable/idempotent for anything other than the specific "already exists"/"already removed" cases explicitly whitelisted (`fs.ErrExist`, `fs.ErrNotExist`). Any other deterministic failure — e.g., a hard-link `os.Link` failing because the destination directory hierarchy was concurrently altered, denied by filesystem quota/permission changes, encountering a name collision from a case-insensitive or overlong path, or a source object file being pruned/corrupted between verification and apply — will cause `applyOperations` to return a non-nil, non-whitelisted error every single time it is retried, since the operations and paths are byte-for-byte identical on every retry.

### Impact Explanation
Because Gitaly routes a repository to a single partition and a single `TransactionManager` per partition, any repository-scoped RPC that needs to read the latest state or issue new writes for that repository blocks indefinitely or errors with `storage.ErrTransactionProcessingStopped` once the manager is permanently down. This is a Denial-of-Service against every git operation (push, fetch that requires up-to-date refs, RPC-driven housekeeping, etc.) for all repositories sharing that partition, with no online recovery path — recovery requires taking Gitaly offline and running the `gitaly recovery replay` CLI tool, which itself may need to delete the malformed WAL entry and accept a "partition ... broken completely" outcome per its own inline documentation.

### Likelihood Explanation
Reaching `applyLogEntry` requires a transaction to have already passed all normal admission checks (reference verification, object-dependency verification, and file-system conflict verification), so triggering the deterministic-apply-failure condition is not as trivial as sending one malformed RPC field. However, the reachable path is entirely from ordinary user-driven Git operations (push/fetch/housekeeping) that end up producing a `LogEntry`/manifest with filesystem operations (`CreateHardLink`, `CreateDirectory`, `RemoveDirectoryEntry`) that is committed to the WAL, and the actual apply step operates on the live filesystem without re-validating anything beyond the two whitelisted error classes. Since the codebase's own test suite exercises "crash before/after apply" scenarios and the recovery tooling has dedicated language for "the partition is always in a broken state" and "there is nothing this tool can do to resolve the situation automatically," this is a known, designed-for risk class rather than a purely theoretical one — it is rated as a design-level gap rather than a proven one-shot exploit, since a precise, reliably reproducible trigger from a single crafted RPC was not confirmed in this analysis.

### Recommendation
- Make `applyLogEntry` operations idempotent/retry-safe beyond the two whitelisted error classes, or add a bounded-retry-then-quarantine mechanism that moves a persistently failing log entry out of the critical path (e.g., into a "poison" state) instead of looping forever.
- Provide an online, safe mechanism (analogous to an "application-level" recovery step) to skip or repair a single corrupted/undecodable log entry without requiring the offline `recovery replay` tool and full partition outage.
- Add alerting/circuit-breaking so that a partition stuck in a crash-loop due to `applyLogEntry` failure is surfaced immediately rather than silently respawning and failing indefinitely.

### Proof of Concept
A concrete, minimal reproduction from a single crafted RPC could not be fully constructed from static analysis alone; the following describes the structural conditions that were confirmed and the gap that a Devin session with test/execution access would need to validate empirically:

Commit a transaction whose manifest includes a `CreateHardLink` (or `CreateDirectory`/`RemoveDirectoryEntry`) operation that passes `verifyFileSystemOperations`/`verifyObjectsExist` at commit time (e.g., because the destination directory or filesystem state changes between verification and apply, or a resource limit like a quota is hit only during `os.Link`).
2. `appendLogEntry` persists this manifest to the WAL, per [7](#0-6) .
3. On the next `run()` iteration, `applyLogEntry` calls `applyOperations`, which hits the non-whitelisted error and returns non-nil, per [8](#0-7) .
4. `run()` returns the error, terminating the manager; `partition_manager.go` respawns a fresh manager which re-reads the same `appliedLSN` and retries the exact same operation, reproducing the same error indefinitely, per [4](#0-3)  and [3](#0-2) .

```go
// appendLogEntry appends a log entry of a transaction to the write-ahead log. After the log entry is appended to WAL,
// the corresponding snapshot lock and in-memory reference for the latest appended LSN is created.
func (mgr *TransactionManager) appendLogEntry(ctx context.Context, objectDependencies map[git.ObjectID]struct{}, logEntry *gitalypb.LogEntry, logEntryPath string) error {
	defer trace.StartRegion(ctx, "appendLogEntry").End()

	// After this latch block, the transaction is committed and all subsequent transactions
	// are guaranteed to read it.
	appendedLSN, err := mgr.logManager.AppendLogEntry(logEntryPath)
	if err != nil {
		return fmt.Errorf("append log entry: %w", err)
	}

	mgr.mutex.Lock()
	mgr.committedEntries.PushBack(&committedEntry{
		lsn:                appendedLSN,
		entry:              logEntry,
		objectDependencies: objectDependencies,
	})
	mgr.mutex.Unlock()

	return nil
}
```

```go
// applyLogEntry reads a log entry at the given LSN and applies it to the repository.
func (mgr *TransactionManager) applyLogEntry(ctx context.Context, lsn storage.LSN) error {
	defer trace.StartRegion(ctx, "applyLogEntry").End()

	defer prometheus.NewTimer(mgr.metrics.transactionApplicationDurationSeconds).ObserveDuration()

	manifest, err := wal.ReadManifest(mgr.logManager.GetEntryPath(lsn))
	if err != nil {
		return fmt.Errorf("read log entry: %w", err)
	}

	// Ensure all snapshotters have finished snapshotting the previous state before we apply
	// the new state to the repository. No new snapshotters can arrive at this point. All
	// new transactions would be waiting for the committed log entry we are about to apply.
	previousLSN := lsn - 1

	mgr.mutex.Lock()
	previousLock := mgr.snapshotLocks[previousLSN]
	mgr.mutex.Unlock()

	// This might take a while, it should better wait out side of mutex lock.
	previousLock.activeSnapshotters.Wait()

	mgr.mutex.Lock()
	delete(mgr.snapshotLocks, previousLSN)
	mgr.mutex.Unlock()

	mgr.testHooks.beforeApplyLogEntry(lsn)

	if err := mgr.db.Update(func(tx keyvalue.ReadWriter) error {
		if err := applyOperations(ctx, safe.NewSyncer().Sync, mgr.storagePath, mgr.logManager.GetEntryPath(lsn), manifest.GetOperations(), tx); err != nil {
			return fmt.Errorf("apply operations: %w", err)
		}

		return nil
	}); err != nil {
		return fmt.Errorf("update: %w", err)
	}

	if err := mgr.storeAppliedLSN(lsn); err != nil {
		return fmt.Errorf("set applied LSN: %w", err)
	}
	mgr.snapshotManager.SetLSN(lsn)

	// Notify the transactions waiting for this log entry to be applied prior to take their
	// snapshot.
	mgr.mutex.Lock()
	mgr.createSnapshotLockIfNeeded(lsn)
	close(mgr.snapshotLocks[lsn].applied)
	mgr.mutex.Unlock()

	return nil
}
```

```go
func applyOperations(ctx context.Context, sync func(context.Context, string) error, storageRoot, walEntryDirectory string, operations []*gitalypb.LogEntry_Operation, db keyvalue.ReadWriter) error {
	// dirtyDirectories holds all directories that have been dirtied by the operations.
	// As files have already been synced to the disk when the log entry was written, we
	// only need to sync the operations on directories.
	dirtyDirectories := map[string]struct{}{}
	for _, wrappedOp := range operations {
		switch wrapper := wrappedOp.GetOperation().(type) {
		case *gitalypb.LogEntry_Operation_CreateHardLink_:
			op := wrapper.CreateHardLink

			basePath := walEntryDirectory
			if op.GetSourceInStorage() {
				basePath = storageRoot
			}

			destinationPath := string(op.GetDestinationPath())
			if err := os.Link(
				filepath.Join(basePath, string(op.GetSourcePath())),
				filepath.Join(storageRoot, destinationPath),
			); err != nil && !errors.Is(err, fs.ErrExist) {
				return fmt.Errorf("link: %w", err)
			}

			// Sync the parent directory of the newly created directory entry.
			dirtyDirectories[filepath.Dir(destinationPath)] = struct{}{}
		case *gitalypb.LogEntry_Operation_CreateDirectory_:
			op := wrapper.CreateDirectory

			path := string(op.GetPath())
			if err := os.Mkdir(filepath.Join(storageRoot, path), fs.FileMode(op.GetMode())); err != nil && !errors.Is(err, fs.ErrExist) {
				return fmt.Errorf("mkdir: %w", err)
			}

			// Sync the newly created directory itself.
			dirtyDirectories[path] = struct{}{}
			// Sync the parent directory where the new directory's directory entry was created.
			dirtyDirectories[filepath.Dir(path)] = struct{}{}
		case *gitalypb.LogEntry_Operation_RemoveDirectoryEntry_:
			op := wrapper.RemoveDirectoryEntry

			path := string(op.GetPath())
			if err := os.Remove(filepath.Join(storageRoot, path)); err != nil && !errors.Is(err, fs.ErrNotExist) {
				return fmt.Errorf("remove: %w", err)
			}

			// Remove the dirty marker from the removed directory entry if it exists. There's
			// no need to sync it anymore as it doesn't exist.
			delete(dirtyDirectories, path)
			// Sync the parent directory where directory entry was removed from.
			dirtyDirectories[filepath.Dir(path)] = struct{}{}
		case *gitalypb.LogEntry_Operation_SetKey_:
			op := wrapper.SetKey

			if err := db.Set(op.GetKey(), op.GetValue()); err != nil {
				return fmt.Errorf("set key: %w", err)
			}
		case *gitalypb.LogEntry_Operation_DeleteKey_:
			op := wrapper.DeleteKey

			if err := db.Delete(op.GetKey()); err != nil {
				return fmt.Errorf("delete key: %w", err)
			}
		default:
			return fmt.Errorf("unhandled operation type: %T", wrappedOp)
		}
	}
```
