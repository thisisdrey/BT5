### Title
Liquidations become permanently blocked when an oracle price legitimately resolves to zero - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-resolve`, the core oracle-resolution helper used throughout `v0-4-market.clar` (including inside `liquidate`), enforces `oracle-price-legal` which requires the resolved price to be strictly greater than zero, reverting with `ERR-ORACLE-INVARIANT` otherwise. If any collateral or debt asset's underlying Pyth/DIA feed genuinely reports (or normalizes to) zero, every code path that must resolve that asset's price — including `liquidate` — reverts, making positions using that asset permanently unliquidatable while debt/losses continue to accrue.

### Finding Description
`price-resolve` is the single oracle-price entry point used by `market.clar` / `v0-4-market.clar` for both position valuation and liquidation: [1](#0-0) 

`oracle-price-legal` strictly requires `p > u0`, and `price-resolve` asserts this condition, reverting with `ERR-ORACLE-INVARIANT` if it fails: [2](#0-1) [3](#0-2) 

`liquidate` depends on this same resolution mechanism at multiple points: it calls `get-notional-evaluation`/`get-assets` (which internally batch-resolve prices via `price-multi-resolve`/`price-resolve`) to compute `total-collateral-usd`/`total-debt-usd`, and it also calls `price-resolve` directly for disabled collateral assets that are not already in the enabled asset list: [4](#0-3) [5](#0-4) 

`price-multi-resolve`/`iter-price-multi` propagate any single-asset resolution failure as an overall failure (`ERR-ORACLE-MULTI`), so a zero price for even one asset in the position's mask aborts the whole `liquidate` call: [6](#0-5) 

Because both the Pyth (`resolve-pyth`) and DIA (`resolve-dia`) feed resolvers pass raw feed values straight into `oracle-price-legal` without any floor/sentinel-value substitution, a legitimate price collapse to (or normalization toward) zero for any single asset used by a borrower's position causes `liquidate` to revert unconditionally for that borrower, mirroring the GMX `M-20` root cause of treating zero as strictly invalid everywhere prices are consumed.

### Impact Explanation
If a collateral or debt asset's price genuinely reaches zero (e.g., a depegged/failed stablecoin or a token whose market value truly goes to zero), the position that holds/owes that asset can never be liquidated through `liquidate`, because every price resolution required by that call path reverts. Debt keeps accruing, no collateral is seized, and the protocol accumulates uncollateralized bad debt with no on-chain path to intervene via the normal liquidation flow — this is a protocol insolvency risk (Critical impact class), matching the exact root cause and impact class in the referenced GMX finding.

### Likelihood Explanation
Likelihood is low but non-zero — it requires an asset's price to genuinely hit zero (not just staleness or outage), which is an extreme but real market event (e.g., total depeg or de-listing of a token used as collateral/debt in the egroup). Given the protocol supports multiple assets/pools indefinitely, the probability over the system's lifetime is non-trivial, consistent with the "unlikely but should not break liquidations" judgment reached in the original Sherlock discussion.

### Recommendation
Do not treat a resolved price of exactly zero as an unconditional oracle failure inside the liquidation path. Either: (1) allow `price-resolve` to return a minimum sentinel value (e.g., 1 wei-equivalent) instead of reverting when the raw price is zero specifically for the liquidation code path, so liquidations remain executable, or (2) add an explicit manual/permissionless "emergency settle" mechanism that lets positions with zero-priced assets be resolved/liquidated using a floor price, separate from the normal fresh-price invariant enforced elsewhere (borrow/withdraw) which can safely continue to reject zero prices.

### Proof of Concept
1. A registered asset's Pyth/DIA feed price collapses to (or normalizes via `normalize-pyth`/`resolve-callcode` to) `0`.
2. A borrower has an open position using this asset as collateral or debt, with `current-ltv >= ltv-liq-partial` (i.e., objectively liquidatable).
3. A liquidator calls `liquidate` (`mainnet/contracts/market/v0-4-market.clar` lines 1382+); `get-notional-evaluation`/`price-multi-resolve` internally calls `price-resolve` for the zero-priced asset.
4. `oracle-price-legal` evaluates `(> 0 u0)` → `false`, the `asserts!` in `price-resolve` fires, and the whole transaction reverts with `ERR-ORACLE-INVARIANT`/`ERR-ORACLE-MULTI`.
5. No liquidator can ever successfully call `liquidate` for this borrower's position while the price remains zero, even though the position is deeply undercollateralized — debt/bad-debt grows unchecked.

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
