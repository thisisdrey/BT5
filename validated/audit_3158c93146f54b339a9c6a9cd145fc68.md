### Title
Denial of Service via unbounded array-length in TVM precompiled contract ABI decoding - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiled-contract helpers `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read an attacker-controlled 256-bit "array length" word from calldata and immediately use it to allocate a Java array (`new byte[len][]`) before any bound check against the actual size of the decoded `words`/`data` buffer. This is the same bug class as the seroval advisory: a declared/encoded length is trusted for allocation instead of being derived from (or validated against) the real available data, allowing a single request to trigger an outsized allocation.

### Finding Description
`extractBytesArray` and `extractSigArray` read the length field directly from `DataWord[] words`: [1](#0-0) 

and `extractBytes32Array` does the same without even the `offset > words.length - 1` guard: [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`. `intValueSafe()` only caps the value at `Integer.MAX_VALUE` when the word doesn't fit in 4 bytes — it does not check the value against the real number of remaining words/bytes in the actual calldata: [3](#0-2) 

So an attacker can craft ABI-encoded calldata whose "length" header word is set to `0x7fffffff` while the actual buffer is tiny (a handful of bytes). `new byte[len][]` (i.e. `new byte[2147483647][]`) is evaluated eagerly at that statement, before the subsequent loop ever touches the out-of-range indices, so the process attempts to allocate on the order of gigabytes of reference-array memory (8 bytes per element on 64-bit JVMs ⇒ ~16 GB for `Integer.MAX_VALUE` elements) in a single call. This throws `OutOfMemoryError`/consumes huge amounts of heap, exactly analogous to seroval trusting an encoded array length instead of deriving it from the actual payload (CWE-770).

These extraction helpers back TVM precompiled contracts reachable from ordinary smart-contract execution. The dispatcher in `getContractForAddress` maps fixed precompile addresses (e.g., `0x9`, `0xa`) to contracts gated only by chain-parameter feature flags such as `allowTvmSolidity059()`: [4](#0-3) 

Any account can broadcast a `TriggerSmartContract` transaction whose bytecode issues a `CALL`/`STATICCALL` to one of these precompile addresses with attacker-controlled `data`, causing this code path to execute inside `PrecompiledContract.execute(byte[] data)` on the node processing/validating the transaction.

### Impact Explanation
A crafted, cheaply-sized transaction can force the executing node (and every full node/witness that re-executes the block/transaction) to attempt an extremely large heap allocation, causing `OutOfMemoryError` and process instability/crash. Because block validation requires re-executing transactions, a single malicious transaction accepted into a block can crash multiple nodes that replay it — a broad availability/DoS impact consistent with CVSS `AV:N/AC:L/PR:N/UI:N/A:H` from the source advisory.

### Likelihood Explanation
Likelihood is high: the attack requires only crafting calldata for a normal `TriggerSmartContract` call to a fixed precompile address, no special privileges, no cooperation from other participants, and no prior on-chain state — reachable by any anonymous transaction broadcaster once the relevant TVM feature flag (e.g. `allowTvmSolidity059`) is enabled, which it is on production networks supporting these opcodes.

### Recommendation
Before allocating `new byte[len][]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual bounds of `words`/`data` (e.g., ensure `offset + len` does not exceed `words.length`, and reject if `len` exceeds the maximum number of items the given `data.length` could possibly encode) and throw/return an empty result instead of allocating an unbounded array. Additionally, cap `len` to a sane maximum independent of `intValueSafe()`'s `Integer.MAX_VALUE` ceiling.

### Proof of Concept
1. Deploy or use any contract that performs `staticcall`/`call` to precompile address `0x...9` (BatchValidateSign) or `0x...a` (ValidateMultiSign) forwarding raw calldata.
2. Construct calldata where the length header word (the word at the array-length offset consumed by `extractBytesArray`/`extractSigArray`) is set to `0x000000000000000000000000000000000000000000000000000000007fffffff`, while the remainder of the calldata contains only a few real words (far fewer than implied by the length).
3. Broadcast a `TriggerSmartContract` transaction invoking this call.
4. When the node executes the transaction, `extractBytesArray`/`extractSigArray` reads `len = 0x7fffffff` and executes `new byte[len][]`, attempting a multi-gigabyte allocation and causing `OutOfMemoryError`/node instability during transaction execution or block validation.
