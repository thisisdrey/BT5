## Title
Witness brokerage-fee change bypasses any notice period before affecting the very next reward cycle - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
The reported Solana stake-pool bug allowed a pool manager to raise a withdrawal fee right at the end of an epoch and have it apply almost immediately at the start of the next epoch, giving depositors no time to react. Java-tron has a structurally identical mechanism for witness "brokerage" (the cut of block/vote rewards a Super Representative keeps from its voters): `UpdateBrokerageContract` lets any registered witness change its brokerage rate at any time with no minimum notice, and the change is committed to take effect starting the very next reward cycle at the next maintenance boundary.

### Finding Description
`UpdateBrokerageActuator.execute` immediately persists the new rate to a "pending" slot (cycle `-1`, i.e. `DelegationStore.REMARK`) with no delay or cooldown check: [1](#0-0) 

That pending value is stored/read via the cycle-less overloads: [2](#0-1) 

At every maintenance boundary, `MaintenanceManager.doMaintenance()` reads whatever pending value is currently stored and commits it as the effective rate for `nextCycle = currentCycle + 1` — i.e., the reward cycle that begins immediately: [3](#0-2) 

`MaintenanceManager.applyBlock` triggers `doMaintenance()` as soon as a block's timestamp crosses `nextMaintenanceTime`: [4](#0-3) 

Because there is no check tying the `UpdateBrokerageContract` submission time to a required minimum number of cycles before it can take effect (unlike the referenced patch which blocks a fee for at least one full epoch), a witness can broadcast the brokerage update in the last block before the maintenance switch and have the new (higher) rate lock in for the very next cycle, with zero notice to voters who delegated votes expecting the previous rate. The actual reward split uses whatever rate was committed for the current cycle: [5](#0-4) 

### Impact Explanation
Voters (delegators) who voted for a witness under one brokerage assumption can have their share of block/standby rewards silently reduced starting the very next cycle (as short as one maintenance interval, default 6 hours), since there is no mandated waiting/notice period analogous to the stake-pool fix. This diverts reward funds from voters to the witness operator without giving voters realistic time to un-vote, matching the "theft of funds via bypassed fee-delay" pattern from the report.

### Likelihood Explanation
Any account that has registered as a witness (a permissionless, fee-paid action via `WitnessCreateContract`) can broadcast an `UpdateBrokerageContract` transaction at will, including in the block immediately preceding a maintenance-cycle rollover. No special privilege beyond being a witness is required, and timing the transaction to the maintenance boundary is straightforward since `getNextMaintenanceTime()` is a public, queryable value.

### Recommendation
Mirror the referenced patch: require that a brokerage change only take effect after at least one full completed cycle from the time it is submitted (e.g., apply the change to `nextCycle + 1` instead of `nextCycle`, or reject/queue updates submitted within some minimum window before `getNextMaintenanceTime()`), so voters have a guaranteed notice period before a new rate applies.

### Proof of Concept
1. Register as a witness (`WitnessCreateContract`) and accumulate votes from delegators under the default brokerage rate (`DelegationStore.DEFAULT_BROKERAGE`, 20%).
2. Monitor `getNextMaintenanceTime()` via `DynamicPropertiesStore`/API.
3. Just before the block whose timestamp will cross `nextMaintenanceTime`, broadcast an `UpdateBrokerageContract` setting `brokerage` to the maximum allowed (100), which is only checked against `[0,100]` in `UpdateBrokerageActuator.validate` (no rate-of-change or notice-period restriction).
4. When the maintenance block is applied, `MaintenanceManager.doMaintenance()` commits this new brokerage for `nextCycle`, which begins immediately — voters who already delegated votes under the old, favorable rate now receive a much smaller reward share with no opportunity to react.
