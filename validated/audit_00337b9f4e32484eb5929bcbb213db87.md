Confirmed: `add_tip()` on `AssetHub` (`pallet_snowbridge_system_frontend`) actually withdraws/burns the user's real asset (swapped to Ether and burned for teleport) *before* the tip is forwarded via XCM to `BridgeHub`. On `BridgeHub`, `pallet_snowbridge_system_v2::add_tip()` tries to credit that value into the `Inbound`/`OutboundQueue`'s per-nonce `Tips` map, but if the nonce was already consumed (message already processed) or unknown, the value is instead pushed into `LostTips<T>` — a storage map that is only ever written to, never read back out by any dispatchable, closely mirroring the "can add but not remove/recover" defect from the external report.

### Title
Burned relayer-tip funds recorded in `LostTips` are permanently unclaimable - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
`pallet-snowbridge-system-frontend::add_tip` burns the user's real tip asset on AssetHub and forwards only the numeric amount via XCM to `pallet-snowbridge-system-v2::add_tip` on BridgeHub. If crediting the tip to the target queue pallet fails (nonce already processed, or unknown message), the amount is added to `LostTips<T>` instead of being refunded, and there is no extrinsic, hook, or governance call anywhere in the codebase that reads or drains `LostTips`, leaving the burned value permanently locked in on-chain bookkeeping with no path to recovery.

### Finding Description
The tip flow spans two chains:

1. On AssetHub, `add_tip` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` (lines 261-273) calls `swap_fee_asset_and_burn`, which either swaps the supplied asset to Ether or, if it's already Ether, calls `burn_for_teleport` directly — i.e. the user's real funds are irreversibly destroyed/withdrawn at this point: [1](#0-0) [2](#0-1) 

2. The resulting `ether_gained` amount is packaged into an `EthereumSystemCall::AddTip` XCM `Transact` and sent unpaid (`UnpaidExecution`) to BridgeHub: [3](#0-2) 

3. On BridgeHub, `pallet_snowbridge_system_v2::add_tip` attempts to register that amount against a specific `Inbound`/`Outbound` message nonce. If `T::InboundQueue::add_tip` or `T::OutboundQueue::add_tip` returns an error (e.g. `AddTipError::NonceConsumed` or `UnknownMessage`, defined in `bridges/snowbridge/primitives/core/src/reward.rs` lines 32-37), the code does **not** attempt to refund or teleport anything back — it silently accumulates the lost amount into `LostTips<T>`: [4](#0-3) [5](#0-4) 

The storage doc comment itself acknowledges the gap: *"Capturing the lost tips here supports implementing a recovery method in the future"* — but no such recovery method exists in the current pallet: there is no `claim_lost_tips`, no governance call, and no automatic sweep found anywhere referencing `LostTips` besides the write path and tests. This is the exact shape of the referenced report: a value can be *added* to a tracking structure (safe-list membership there, burned-tip credit here) but the pallet provides no complementary function to remove/redeem it, leaving the state (and here, real economic value) stuck.

The window for triggering `NonceConsumed`/`UnknownMessage` is entirely reachable by an ordinary, unprivileged user: since `add_tip` on AssetHub is signed-origin only (`ensure_signed(origin)?`) with no check that the referenced message is still pending, any user can race their own `add_tip` against the relayer's `process_message`/message-delivery call for the same nonce (or simply typo/guess a nonce), causing the tip to land in `LostTips` after their funds have already been burned.

### Impact Explanation
This satisfies the "permanent user-fund ... lock" impact category: real Ether-denominated value is burned on AssetHub as part of the tip flow, but if the BridgeHub-side crediting fails for a benign, easily reachable reason (timing race with message processing, or a bad/late nonce), the value becomes permanently unrecoverable — there's no code path that reads `LostTips` back into a payable state. This is a direct, unprivileged loss of user funds in the Snowbridge delivery/reward flow, not a governance or admin misconfiguration issue.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `add_tip` and `process_message`/message delivery are two independent transactions that can be submitted concurrently by different actors (the tipper and the relayer). Any user who tips a message that gets processed in the same or an earlier block, or who tips a nonce that doesn't yet exist/was already consumed, will hit this path. No malicious relayer or validator behavior is required — this can happen from completely honest, uncoordinated user activity, and is exactly the kind of "underpriced/mis-costed public work with fund-lock" scenario the impact gate calls out for Snowbridge delivery flow.

### Recommendation
Add a `claim_lost_tips` (or `withdraw_lost_tips`) extrinsic that allows the original `sender` recorded in `LostTips<T>` to redeem their balance — either by minting/teleporting the equivalent Ether back to their account on the origin chain via XCM, or by crediting a local balance they can later bridge back. Alternatively, and more robustly, refactor `add_tip` on system-frontend to defer the burn/withdrawal until BridgeHub confirms successful crediting (e.g., via an XCM query-response pattern) instead of irrevocably burning funds before the destination side validates the nonce.

### Proof of Concept
1. User A calls AssetHub `pallet_snowbridge_system_frontend::add_tip(message_id: Inbound(N), asset: Asset{Ether, amount})`. Their asset is swapped/burned immediately in `swap_fee_asset_and_burn`.
2. Concurrently (or just before this XCM lands), the relayer submits `InboundQueue::submit`/`process_message` for nonce `N`, which calls `Nonce::<T>::set(nonce)` marking it processed (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` lines 219-225).
3. The XCM `Transact` carrying `EthereumSystemCall::AddTip { sender: A, message_id: Inbound(N), amount }` executes on BridgeHub, calling `InboundQueue::add_tip(N, amount)`.
4. Inside the inbound-queue's `AddTip` implementation (via `AddTipError::NonceConsumed`, `bridges/snowbridge/primitives/core/src/reward.rs` lines 32-37), the call fails because nonce `N` is already processed.
5. `pallet_snowbridge_system_v2::add_tip` catches the `Err`, and instead of refunding, executes `LostTips::<T>::mutate(&sender, |lost_tip| *lost_tip = lost_tip.saturating_add(amount))` (lines 266-271 of `bridges/snowbridge/pallets/system-v2/src/lib.rs`).
6. User A's burned Ether value is now only reflected as a number in `LostTips<T>` storage with no extrinsic in the pallet's `#[pallet::call]` block (only `upgrade`, `set_operating_mode`, `register_token`, `add_tip`) to ever move it back to them — the funds are permanently lost.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		#[pallet::call_index(3)]

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
