### Title
Bancor-exchange `transaction()` allows draining a reserve to exactly zero, breaking the pool invariant - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()`, which implements TRON's on-chain Bancor-style AMM (`ExchangeTransactionContract`), only rejects a post-trade reserve balance that is strictly negative. It never rejects a resulting reserve balance of exactly `0`, even though the actuators explicitly treat `firstTokenBalance == 0 || secondTokenBalance == 0` as an invalid/closed pool state everywhere else. This is the same bug class as the reported issue: the trading function is checked against the wrong boundary condition, so a swap that drains one side of the pool down to its boundary value (0) is silently accepted instead of being rejected, corrupting the invariant for all future trades on that exchange.

### Finding Description
The `doValidate()` methods of `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all guard against operating on a pool whose balances are already zero: [1](#0-0) 

This shows the protocol's own invariant: a reserve of `0` is considered a "closed"/invalid exchange state that must never be produced. However, the actual state transition performed by a trade, `ExchangeCapsule.transaction()`, only checks for a *negative* resulting balance in its "hardened" branch, not a zero one: [2](#0-1) 

Specifically: [3](#0-2) 

`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` permits `== 0` to pass unimpeded. In the legacy (non-hardened) branch there is no bound check at all — the subtraction is a plain `long` subtraction that can even go negative without detection: [4](#0-3) 

The Bancor curve implemented by `ExchangeProcessor`/`SafeExchangeProcessor` computes the amount bought as a supply-relay based on `pow(1+quant/newBalance, 0.0005)` then `pow(1+supplyQuant/supply, 2000)`: [5](#0-4) 

For a sufficiently large `sellTokenQuant` (bounded only by the seller's own asset/TRX balance, not by the pool's opposite-side reserve — the `ExchangeTransactionActuator.doValidate()` only enforces `balanceLimit` on the *sell* side, see lines 199-205 of that file, and enforces `tokenExpected` as a lower, not upper, bound), the computed `buyTokenQuant` can equal (or, in the legacy path, exceed) the entire opposite-side reserve. Once it equals the reserve exactly, `transaction()` accepts the trade and sets the reserve to `0`, which the codebase elsewhere defines as a broken/closed pool state, but this path never enforces that invariant on the way in.

### Impact Explanation
Once a reserve hits exactly zero (or goes negative in the legacy math path), the Bancor invariant used by `ExchangeProcessor`/`SafeExchangeProcessor` becomes degenerate: subsequent `exchangeToSupply`/`exchangeFromSupply` calls using a `0` (or negative) balance produce division-by-zero, `NaN`/`Infinity` doubles, or `ArithmeticException`s that are caught and simply converted to failed transactions in `ExchangeTransactionActuator.execute()` — but the pool is now permanently unusable (funds effectively frozen and unrecoverable through normal exchange operations) or, depending on rounding behavior of the Bancor curve, can be exploited by a follow-up attacker to extract further value while the pool state is inconsistent with the "no side may be zero" invariant the rest of the actuators assume. This matches the reported bug class ("wrong invariant at bounds ... allowing to steal all pool reserves") applied to TRON's on-chain exchange.

### Likelihood Explanation
This is reachable by any account holding TRX or the traded TRC10 asset simply by submitting an `ExchangeTransactionContract` with a very large `quant` value against a low-liquidity exchange pool (e.g. one just created via `ExchangeCreateActuator` with attacker-controlled `firstTokenBalance`/`secondTokenBalance`, since an attacker can create their own exchange pair). No special privileges (SR/witness/committee) are required — it is a pure user-facing, single-transaction actuator (`ExchangeTransactionActuator`) exposed through normal transaction broadcast / wallet RPC paths.

### Recommendation
In `ExchangeCapsule.transaction()`, reject any trade whose resulting `newFirstTokenBalance` or `newSecondTokenBalance` is `<= 0` (not just `< 0`), and apply this check unconditionally (not only when `hardenedCalc` is true). Additionally, enforce this check in `ExchangeTransactionActuator.doValidate()` before allowing the trade, mirroring the existing pre-trade `firstTokenBalance == 0 || secondTokenBalance == 0` guard so the invariant is validated both before and after the trade.

### Proof of Concept
1. Attacker calls `ExchangeCreateActuator` to create a low-liquidity pool, e.g. `firstTokenBalance = 100`, `secondTokenBalance = 100` (small TRC10 amounts), becoming the pool creator.
2. Attacker (or any other account holding the sell-side asset) submits an `ExchangeTransactionContract` selling a very large `tokenQuant` of the first token such that the Bancor curve in `ExchangeProcessor.exchange()`/`SafeExchangeProcessor.exchange()` computes `buyTokenQuant == secondTokenBalance` (draining the second reserve to `0`) or, in the non-hardened path, `buyTokenQuant > secondTokenBalance` (driving it negative).
3. `ExchangeCapsule.transaction()` at [3](#0-2)  only rejects `< 0`; a result of exactly `0` is accepted and persisted via `Commons.putExchangeCapsule(...)` in `ExchangeTransactionActuator.execute()`.
4. Any subsequent trade against this exchange now operates on a zero reserve, producing division-by-zero/degenerate Bancor math and permanently breaking the pool.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
