### Title
Path traversal / absolute-path write during snapshot extraction via unsanitized `tar -C` subprocess - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`server.untar` pipes an attacker-influenced HTTP response body directly into a raw `tar -C <repoPath> -xvf -` subprocess without any per-entry path validation, unlike the hardened `extractTarToDirectory` used by `ReplicateRepository`, which explicitly checks that every extracted path, symlink target, and hard-link target stays within `targetDir` via `strings.HasPrefix` checks. [1](#0-0) [2](#0-1)  A tar archive containing an absolute path entry (e.g. `/etc/evil`) or a relative traversal entry (e.g. `../../evil`) served from `in.GetHttpUrl()` can therefore cause GNU `tar` to write files outside the freshly-created repository directory.

### Finding Description
`CreateRepositoryFromSnapshot` calls `repoutil.Create` with a callback that invokes `s.untar(ctx, path, in)`, where `path` is the freshly-created repository's directory. `untar` performs an HTTP GET to `in.GetHttpUrl()` (optionally with `in.GetHttpAuth()` as a bearer/basic header) and streams the response body as stdin into `tar -C path -xvf -`. [3](#0-2)  No entry name is inspected in Go — the extraction logic is fully delegated to the system `tar` binary, which honors absolute paths and `../` traversal in the same manner as any tar implementation. Note that the code contains an explicit developer acknowledgment of this limitation ("NOTE: The received archive is trusted *a lot*. Before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening"), confirming that the endpoint is designed to only accept a fully-trusted/administrator-controlled `HttpUrl`, not attacker-supplied input. [4](#0-3) 

By contrast, `ReplicateRepository`'s `extractSnapshot` → `extractTarToDirectory` (used for internal Gitaly-to-Gitaly replication of an existing repository via `GetSnapshot`) validates every path with `filepath.Join` + `strings.HasPrefix(targetPath, targetDir+separator)` for regular files/dirs, and additionally validates symlink and hard-link targets, rejecting anything that escapes the target directory. [2](#0-1) [5](#0-4) 

However, I could not find any reachable path in this codebase by which an unprivileged GitLab user directly controls `CreateRepositoryFromSnapshotRequest.HttpUrl`/`HttpAuth` end-to-end through a project fork or import flow. This RPC is a low-level Gitaly primitive; GitLab Rails historically invokes it only in specific internal/administrative Geo or repository-migration contexts where the `HttpUrl` is derived from GitLab's own internal snapshot endpoint (an authenticated Rails-controlled URL), not a URL supplied verbatim by an unprivileged user. The security-relevant `resolved_address` field and `newResolvedHTTPClient` (DNS-rebinding protection) further indicate this RPC is designed for internal service-to-service snapshot transfer, not arbitrary user-supplied URLs. [6](#0-5)  I was unable to locate, within the indexed Gitaly repository alone, concrete evidence of an unprivileged-user-reachable RPC/API path that lets an attacker set an arbitrary attacker-hosted `HttpUrl` for this specific RPC — that wiring lives in GitLab Rails, which is out of scope for this repo's index and was explicitly excluded per the rules ("Reject anything requiring... a bug in GitLab Rails... rather than in Gitaly").

### Impact Explanation
If reachable with attacker-controlled `HttpUrl` content, the impact would be a genuine storage-path escape: arbitrary file write/overwrite outside the new repository (e.g., clobbering sibling repository files, planting a custom hook, or overwriting arbitrary paths reachable by the Gitaly process user). This matches the "archive extraction escape" / "storage-path escape" bounty impact class explicitly listed in scope.

### Likelihood Explanation
The vulnerable code and lack of Go-side validation are real and confirmed in this file, and the difference in rigor from `extractTarToDirectory` is a legitimate hardening gap. However, per the rules, a valid finding requires tracing "the exact reachable path from attacker input ... into the affected function," and confirming the attacker is unprivileged with no reliance on non-default configuration or components outside Gitaly. I could not confirm, using only this repository's context, that an unprivileged user's fork/import action lets them set `HttpUrl`/`HttpAuth` on this specific RPC — this wiring is owned by GitLab Rails and is out of scope for a Gitaly-only code audit. The developer comment in the code itself indicates the intended trust model is that `HttpUrl` is *not* attacker-controlled in the current deployment.

### Recommendation
Regardless of current reachability, harden `untar` to reuse (or share) the same tar-entry validation logic as `extractTarToDirectory` (reject absolute paths, verify `filepath.Join(path, header.Name)` stays within `path` via prefix check, validate symlink/hardlink targets) instead of invoking a bare `tar -C ... -xvf -` subprocess, so that this RPC is safe even if it were ever fed a less-trusted or attacker-influenced `HttpUrl`.

// newResolvedHTTPClient is a modified version of the httpClient variable but here we resolve the
// URL to predefined IP:PORT. This is to avoid DNS rebinding.
func newResolvedHTTPClient(httpAddress, resolvedAddress string) (*http.Client, error) {
	url, err := url.ParseRequestURI(httpAddress)
	if err != nil {
		return nil, structerr.NewInvalidArgument("parsing HTTP URL: %w", err)
	}

	port := url.Port()
	if port == "" {
		switch url.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		default:
			return nil, structerr.NewInvalidArgument("unsupported schema %q", url.Scheme)
		}
	}

	// Sanity-check whether the resolved address is a valid IP address.
	if net.ParseIP(resolvedAddress) == nil {
		return nil, structerr.NewInvalidArgument("invalid resolved address %q", resolvedAddress)
	}

	transport := httpTransport.Clone()
	transport.DialContext = func(ctx context.Context, network, _ string) (net.Conn, error) {
		return httpTransport.DialContext(ctx, network, fmt.Sprintf("%s:%s", resolvedAddress, port))
	}

	return &http.Client{
		Transport: correlation.NewInstrumentedRoundTripper(otelhttp.NewTransport(transport)),
		// Here we directly return the `ErrUseLastResponse` to prevent redirects
		CheckRedirect: func(*http.Request, []*http.Request) error {
			return http.ErrUseLastResponse
		},
	}, nil
}
