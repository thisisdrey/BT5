### Title
Unauthenticated write of unverified content to AtlasDB via missing hash-match check in `extend_with_attachments` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachment` HTTP response and stores the returned `Attachment` bytes without ever checking that the content actually hashes to the `content_hash` that was requested (`AttachmentRequest::content_hash`). The caller in `AttachmentsDownloader::run` then unconditionally calls `AtlasDB::insert_instantiated_attachment` for every attachment collected, persisting attacker-chosen content keyed by a hash computed locally from that same attacker-chosen content.

### Finding Description
The download pipeline works as follows: `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest` whose `content_hash` field is a Hash160 value taken from a real, on-chain-committed `AttachmentInstance` [1](#0-0) . That request is sent to a peer chosen from `network.get_outbound_sync_peers()` — a peer set that an attacker can join simply by running their own Stacks peer that the victim node dials out to for Atlas syncing, requiring no privileged role or secret [2](#0-1) .

When the HTTP response comes back, `extend_with_attachments` only checks that the response decodes successfully via `decode_atlas_get_attachment()`; it never compares the decoded `Attachment`'s actual hash against `request.content_hash` (the value the request was keyed on) before inserting it into `self.attachments`: [3](#0-2) 

Then in `AttachmentsDownloader::run`, every attachment collected this way is committed to disk unconditionally, regardless of whether any `AttachmentInstance` actually references its (self-computed) hash: [4](#0-3) 

`insert_instantiated_attachment` performs `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` using `attachment.hash()` (Hash160 of the attacker-supplied bytes) as the key, with no check that this hash is bound to any on-chain-committed `attachment_instances.content_hash` row [5](#0-4) .

Because the hash stored is derived from the attacker's own bytes rather than validated against the requested `content_hash`, a malicious peer answering a legitimate `GetAttachment` request can substitute arbitrary content. Each distinct payload produces a distinct Hash160, so repeated malicious responses (across retries of unresolved batches, or across different real content_hash requests the malicious peer is selected to serve) create new, unrelated rows in `attachments` whose `hash` never corresponds to a confirmed `attachment_instances.content_hash`. This breaks the invariant that every row in `attachments` should correspond to a hash referenced by a confirmed on-chain `AttachmentInstance`.

### Impact Explanation
This is an unauthenticated write to persistent node state: an attacker-controlled remote peer can cause the victim node's `AtlasDB` `attachments` table to be populated with content the attacker chose, keyed under a hash the attacker also chose, with no cryptographic tie-back to any confirmed on-chain commitment. This affects any node that syncs Atlas attachments with an attacker-controlled or attacker-influenced outbound peer, is repeatable across every attachment request/retry cycle, and results in disk-state pollution decoupled from consensus-committed data (`attachment_instances`). The instance resolution logic (`context.attachments_batch.resolve_attachment(&attachment.hash())`) is also derived from the unverified hash, so the intended `content_hash` may not actually be resolved by this bogus response, further corrupting sync-state bookkeeping.

### Likelihood Explanation
An attacker needs only to run an ordinary Stacks peer, be selected by the victim as an outbound Atlas-sync peer (a routine, unprivileged occurrence), and respond to the victim's `GetAttachment` requests with arbitrary bytes instead of the correct content. No secret, signature, or special role is required — this is reachable via the normal Atlas HTTP attachment-download flow. The growth rate is bounded by the number of legitimate pending `AttachmentRequest`s (real committed instances) times the retry budget (`max_attachment_retry_count`) per batch, rather than being purely unbounded per message, but each malicious response is a low-cost, guaranteed successful write.

### Recommendation
In `extend_with_attachments`, verify that `Hash160(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; discard and treat as a failed/faulty response (bump `report.bump_failed_requests()` or mark the peer faulty) otherwise. This restores the invariant that only attachments matching a request's expected `content_hash` are ever persisted via `insert_instantiated_attachment`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/download.rs` (or a new test module under `stackslib::net::atlas`) that:
1. Constructs an `AttachmentsBatchStateContext` with one pending `AttachmentRequest { content_hash: H, .. }`.
2. Builds a `BatchedRequestsResult` whose `succeeded` map pairs that request with a crafted `StacksHttpResponse` encoding a `GetAttachmentResponse` containing content `C` such that `Hash160(C) != H`.
3. Calls `context.extend_with_attachments(&mut result)` and observes `context.attachments` now contains the mismatched `Attachment`.
4. Feeds this context through `AttachmentsDownloader::run`'s `Done` branch (or directly calls `atlasdb.insert_instantiated_attachment(&attachment)`), then asserts `AtlasDB` now has a row in `attachments` with `hash = Hash160(C)`, while `find_all_attachment_instances(&Hash160(C))` returns empty and no `attachment_instances` row references `Hash160(C)` — demonstrating the row exists with no corresponding confirmed `AttachmentInstance.content_hash`.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
