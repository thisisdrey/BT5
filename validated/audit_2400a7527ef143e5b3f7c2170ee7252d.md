### Title
Unvalidated array-length field in TVM `ValidateMultiSign`/`BatchValidateSign` precompile ABI decoding leads to uncaught `ArrayIndexOutOfBoundsException` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts decode an attacker-controlled calldata blob into a `DataWord[]` and then read a length field (`sigArraySize`/`addrArraySize`) directly from that data to drive array allocation and iteration in `extractBytesArray`/`extractSigArray`/`extractBytes32Array`. The bounds check on that length field against the actual decoded word count is **only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled**; when that flag is off (or for `ValidateMultiSign` prior to reaching that branch), the extraction helpers index into the `words` array using offsets derived purely from the untrusted length field with no check against `words.length`. This mirrors the ESP-NOW bug class exactly: the "count" field (`addrs_num` analog) is not checked against the actual buffer/array size while a *different* field (offset/data pointer, analog of `addrs_list`) is checked, producing an out-of-bounds array access.

### Finding Description
`extractBytesArray` / `extractSigArray` (used by `ValidateMultiSign`) and `extractBytes32Array` (used by `BatchValidateSign`) read a `len` value straight from decoded calldata and loop `len` times, indexing `words[offset + i + 1]` with no bound check against `words.length`: [1](#0-0) 

In `ValidateMultiSign.execute`, the size-bound check (`sigArraySize > MAX_SIZE`) is only executed inside `if (VMConfig.allowTvmSelfdestructRestriction())`. The subsequent call to `extractBytesArray`/`extractSigArray` — which actually performs the unchecked indexing — sits **outside** the `try { ... } catch (Throwable t)` block that wraps the rest of the method: [2](#0-1) 

So if `allowTvmSelfdestructRestriction()` is disabled (a real, reachable network configuration state, since this is a feature-gated hardfork flag), an attacker can craft a `sigArraySize`-controlling word larger than the actual remaining `words` array, causing `words[offset + i + 1]` in `extractBytesArray`/`extractSigArray` to throw `ArrayIndexOutOfBoundsException`. This exception is **not caught** by the inner `try/catch(Throwable)` (that block only wraps the permission-weight loop, which is never reached), so it propagates out of `PrecompiledContract.execute()` uncaught.

By contrast, `BatchValidateSign.execute` wraps its entire body (`doExecute`) in a top-level `catch (Throwable t)`, so the same class of exception there is safely absorbed: [3](#0-2) 
This asymmetry confirms `ValidateMultiSign` is the vulnerable path — its author evidently intended similar protection but placed the try/catch too narrowly, leaving the unchecked-length array indexing exposed.

### Impact Explanation
An unprivileged contract deployer/caller can invoke the `ValidateMultiSign` precompile (reachable from any TVM contract call, e.g., via a `CALL` to the precompile address) with crafted calldata whose signature/address-array length word exceeds the actual decoded word count. This raises an uncaught `ArrayIndexOutOfBoundsException` inside precompile execution. Depending on how the TVM's opcode dispatch (`Program.callToPrecompiledAddress`) handles unexpected `RuntimeException`s bubbling out of a precompile (rather than the expected TVM-specific exceptions), this can either abnormally terminate the enclosing VM run in an unhandled way or propagate further up into block/transaction processing, since — unlike `BatchValidateSign` — there is no catch-all guard around the vulnerable extraction call. Because this occurs deterministically for every node applying the same transaction/block, it is a reachable denial-of-service vector against transaction processing/block application rather than a memory-safety bug (Java has no true OOB memory corruption), but it matches the same missing-count-validation root cause as the reported CVE.

### Likelihood Explanation
The `allowTvmSelfdestructRestriction()`-gated check demonstrates the java-tron team already recognized the need to bound this length field, but the fix was incomplete: it protects only against `sigArraySize > MAX_SIZE`, is conditioned on a config flag, and does not add a general bounds check inside `extractBytesArray`/`extractSigArray`/`extractBytes32Array` themselves. Any transaction broadcaster can trigger this by calling the precompile address with malformed data; no privileged role is required.

### Recommendation
- Add an unconditional bounds check inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` verifying `offset + len` (and all derived offsets) do not exceed `words.length`/`data.length` before indexing, independent of the `allowTvmSelfdestructRestriction()` flag.
- Move the `extractBytesArray`/`extractSigArray` calls inside `ValidateMultiSign.execute` into the existing `try { } catch (Throwable t)` block, matching `BatchValidateSign`'s defensive pattern, so malformed input safely falls through to `Pair.of(true, DATA_FALSE)` instead of propagating an uncaught exception.

### Proof of Concept
1. Craft calldata for `ValidateMultiSign` (address, permissionId, data-offset word, then a signature-array header) where the `sigArraySize` word (read at `words[words[3].intValueSafe()/WORD_SIZE]`) is set to a very large value (e.g. `0x7fffffff`) while the actual calldata contains only a few 32-byte words.
2. Deploy/invoke a contract that performs a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address with this calldata, in a network configuration where `allowTvmSelfdestructRestriction()` is not yet active (or before this feature flag activation on the corresponding chain).
3. `extractBytesArray(words, offset, rawData)` will iterate up to `sigArraySize` times, and `words[offset + i + 1]` will index past the actual array bounds, throwing `ArrayIndexOutOfBoundsException` that is not caught by the narrow inner `try/catch` in `ValidateMultiSign.execute`.

Note: I was not able to fully trace, within the remaining investigation budget, exactly how `Program.callToPrecompiledAddress` (the caller of `PrecompiledContract.execute()`) handles an arbitrary uncaught `RuntimeException` bubbling out of a precompile — i.e., whether it is caught generically at that layer (downgrading impact to a reverted transaction) or propagates further into block application (which would upgrade this to a node-halting issue). This should be verified directly in `actuator/src/main/java/org/tron/core/vm/program/Program.java` before final severity is confirmed.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
