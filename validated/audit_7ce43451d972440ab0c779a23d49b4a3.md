### Title
DoS via unbounded in-memory patch buffering before `MaxPatchBytes`/`MaxBytes` enforcement in the CommitDiff/RawDiff parser - (File: internal/gitaly/diff/diff.go)

### Summary
`Parser.Parse()` (`internal/gitaly/diff/diff.go`) only enforces the configured size limits (`MaxPatchBytes`, `MaxBytes`, `MaxLines`, `MaxFiles`) *after* an entire file's patch has already been read into memory via `readNextDiff`/`consumeChunkLine`. Because the check happens after the value it is meant to bound has already been fully computed/mutated, a single crafted diff (e.g. one huge line or one file with a very large hunk) can be buffered in full before the enforcement/prune logic ever runs, mirroring the reported class of bug: a threshold check that is evaluated before, not after, the operation that grows/mutates the checked quantity.

### Finding Description
`readNextDiff` (`internal/gitaly/diff/diff.go:234-276`) calls `consumeChunkLine` for every content line (`-`, `+`, ` `, `\`, `Binary`, etc.) of the current file's patch, and `consumeChunkLine` (`internal/gitaly/diff/diff.go:472-510`) unconditionally appends each line to `diff.Patch`: [1](#0-0) 

Inside `consumeChunkLine`, when a single line is longer than the `bufio.Reader`'s internal buffer, `reader.ReadSlice('\n')` returns `bufio.ErrBufferFull` and the loop simply keeps reading and appending more of the same line (`for done := false; !done`), with **no check against `MaxPatchBytes` or `MaxBytes` during this loop**: [2](#0-1) 

Only once `readNextDiff` fully returns (i.e., the entire file's patch — potentially including one arbitrarily long line, or many lines forming one huge hunk — has been buffered into `diff.Patch`) does `Parser.Parse()` check the limits and prune: [3](#0-2) 

This is the same bug class as the WooFi report: a protective threshold (`srcInfos.minBridgeAmount` / here `MaxPatchBytes`/`MaxBytes`) is checked, but the quantity it is supposed to bound (`bridgeAmount` after fee deduction / here `diff.Patch` after continued line accumulation) can still grow past that bound between the point where accumulation happens and the point where the check is actually applied. In both cases the fix is to perform the check incrementally, during accumulation, rather than only once after the value has already been fully constructed.

### Impact Explanation
`CommitDiff`/`RawDiff`-style RPCs (`internal/gitaly/service/diff`) accept revisions supplied by an ordinary, unprivileged caller (e.g. a fork/MR diff view, or any client invoking the diff service against a repository the caller can push to). By pushing a commit that changes a single line to be extremely large (a common technique — e.g. a huge minified/one-line file, or a giant hunk with no embedded newlines for a long stretch) an attacker can force the Gitaly worker to buffer that entire line/hunk into `diff.Patch` in memory before any `MaxPatchBytes`/`MaxBytes` limit is applied, effectively defeating the purpose of the size limits and creating a memory-exhaustion / DoS vector on the Gitaly node handling the request, independent of what limit the client (e.g. GitLab Workhorse/Rails) requested.

### Likelihood Explanation
Likelihood is moderate-to-high in the sense that the trigger only requires an ordinary user to push a commit with a large single line/patch and then request a diff of it (e.g. via merge request diff view, which is a very common, unprivileged, always-reachable code path). No special privileges, tokens, or MITM position are required — only the ability to push a commit and request its diff, both of which are standard user capabilities.

### Recommendation
Enforce `MaxPatchBytes` (and ideally `MaxBytes`) incrementally inside `consumeChunkLine`'s accumulation loop (and/or inside the `bufio.ErrBufferFull` branch of `readNextDiff`), aborting/pruning the patch as soon as the running byte count for the current file exceeds the limit, instead of only checking `len(parser.currentDiff.Patch)` once the whole file's patch has already been fully read into `diff.Patch`. This avoids unbounded memory growth for any single file/line regardless of the configured cap.

### Proof of Concept
1. As an ordinary authorized user, push a commit that modifies one text file to contain a single line of many hundreds of megabytes (no embedded `\n` for the bulk of the line), e.g. via `git commit` a file with `python -c "print('a'*500_000_000)" > big.txt`.
2. Request `CommitDiffRequest`/`RawDiffRequest` for that commit against the repository, with the caller-provided (or default) `MaxPatchBytes`/`MaxBytes` set to a small value (e.g. 500 KB, well below the actual line size), as in the existing test `TestCommitDiff_limits` (`internal/gitaly/service/diff/commit_diff_test.go`) which exercises `MaxPatchBytes`.
3. Observe that `consumeChunkLine` (`internal/gitaly/diff/diff.go:472-502`) keeps looping and appending to `diff.Patch` on `bufio.ErrBufferFull` until the entire ~500 MB line has been read and stored in memory, and only after `readNextDiff` returns does `Parser.Parse()` (`internal/gitaly/diff/diff.go:203-209`) detect `maxPatchBytesExceeded` and prune — by which point the full oversized buffer has already been allocated, defeating the intended memory/size protection.
