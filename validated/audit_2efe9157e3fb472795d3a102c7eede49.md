### Title
Remote address entries admitted under a permissive `remote_allow_list` are never re-validated after the list is tightened, letting a peer that front-runs a config reload retain an untrusted address indefinitely - ([File: remote_list.go])

### Summary
The Sherlock report describes a class of bug where a boolean/mode toggle (whitelist off → on) is checked only at admission time, so an entity that gets itself admitted while the gate is open keeps the privilege that was supposed to be revoked, and the owner is forced to briefly re-grant the privileged status just to remove it. In Nebula, the closest reachable analog for an attacker without a CA-signed certificate is the `lighthouse.remote_allow_list` gate on learned/reported remote addresses: it is enforced only when an address is first inserted into a peer's `RemoteList` cache, never re-checked when the list is rebuilt from that cache, and never re-checked when the operator tightens the allow-list config.

### Finding Description
`RemoteList.shouldAdd`-style callbacks (`lh.unlockedShouldAddV4`, `lh.unlockedShouldAddV6`, `lh.shouldAdd`) call `lh.GetRemoteAllowList().Allow(...)` and are only consulted at the point new addresses are inserted into the cache (`unlockedSetV4`/`unlockedSetV6`/`unlockedPrependV6`, invoked from lighthouse gossip and handshake handling) [1](#0-0) .

Once an address has been accepted into `RemoteList.cache[ownerVpnIp]` as `learned` or `reported`, the periodic/on-demand rebuild path `unlockedCollect()` re-derives the exposed `addrs` slice straight from that cache without ever re-invoking `shouldAdd`/the allow list - it only filters via `unlockedIsBad`, which is unrelated to the allow-list gate. The allow-list based `shouldAdd` filter is applied a second time only for freshly resolved DNS addresses (`dnsAddrs`), not for the previously cached `learned`/`reported` entries [2](#0-1) .

This means the acceptance decision is made once, at insertion time, and is never revisited. If an operator narrows `lighthouse.remote_allow_list` (e.g. to exclude a previously-allowed CIDR/IP that was actually controlled by an attacker), any address that a malicious peer already got learned/reported into a victim's `RemoteList` before the tightening remains in the collected/sorted address set and continues to be used for handshakes and packet routing after the reload - the exact "toggle a gate closed but the already-admitted entity keeps its status" pattern from the referenced report, translated from an on-chain whitelist to Nebula's remote-address trust cache.

### Impact Explanation
An attacker who is not yet excluded by the current `remote_allow_list` can get one of its addresses learned into a target's `RemoteList` (via lighthouse reports or handshake-time `RefreshFromHandshake`) while the list is still permissive. After the operator restricts the allow list to lock the attacker out, the cached entry survives the rebuild and Nebula will keep attempting/sending handshakes and traffic to that now-disallowed address, defeating the intent of the tightened `remote_allow_list` and preserving the attacker's addressing foothold on the tunnel.

### Likelihood Explanation
Reaching this path does not require a CA-signed certificate for the initial admission step in all cases (lighthouse reports of remote addresses flow through `shouldAdd` at insertion), and the exploit only needs the attacker to be un-blocked at some point in time before an operator narrows the config, then have the operator perform a routine hot-reload of `lighthouse.remote_allow_list` - a realistic operational sequence (e.g., revoking a compromised segment's IP range). Likelihood is moderate: it depends on timing relative to a config reload, similar to the front-running window in the original report.

### Recommendation
Re-validate cached `learned`/`reported` addresses in `RemoteList.unlockedCollect()` against the current `remote_allow_list` (`shouldAdd`) on every rebuild, not just for freshly resolved DNS addresses, and drop/evict cache entries that no longer pass the allow list when the lighthouse's allow list is reloaded, mirroring how the firewall's `inConns` re-validates conntrack entries against a bumped `rulesVersion` after a reload [3](#0-2) .

### Proof of Concept
Not applicable/not verified end-to-end - this is a code-review-based analog derived from the report's bug class; a concrete PoC would require exercising `unlockedSetV4`/`RefreshFromHandshake` to seed a cache entry, then reloading `lighthouse.remote_allow_list` and confirming the stale entry persists in `unlockedCollect()`'s output, which was not executed in this analysis.

// unlockedShouldAddV4 checks if to is allowed by our allow list
func (lh *LightHouse) unlockedShouldAddV4(vpnAddr netip.Addr, to *V4AddrPort) bool {
	udpAddr := protoV4AddrPortToNetAddrPort(to)
	allow := lh.GetRemoteAllowList().Allow(vpnAddr, udpAddr.Addr())
	if lh.l.Enabled(context.Background(), logging.LevelTrace) {
		lh.l.Log(context.Background(), logging.LevelTrace, "remoteAllowList.Allow",
			"vpnAddr", vpnAddr,
			"udpAddr", udpAddr,
			"allow", allow,
		)
	}

	if !allow {
		return false
	}

	if lh.myVpnNetworksTable.Contains(udpAddr.Addr()) {
		return false
	}

	return true
}

func (r *RemoteList) unlockedCollect() {
	addrs := r.addrs[:0]
	relays := r.relays[:0]

	for _, c := range r.cache {
		if c.v4 != nil {
			if c.v4.learned != nil {
				u := protoV4AddrPortToNetAddrPort(c.v4.learned)
				if !r.unlockedIsBad(u) {
					addrs = append(addrs, u)
				}
			}

			for _, v := range c.v4.reported {
				if v == nil {
					continue
				}
				u := protoV4AddrPortToNetAddrPort(v)
				if !r.unlockedIsBad(u) {
					addrs = append(addrs, u)
				}
			}
		}

		if c.v6 != nil {
			if c.v6.learned != nil {
				u := protoV6AddrPortToNetAddrPort(c.v6.learned)
				if !r.unlockedIsBad(u) {
					addrs = append(addrs, u)
				}
			}

			for _, v := range c.v6.reported {
				if v == nil {
					continue
				}
				u := protoV6AddrPortToNetAddrPort(v)
				if !r.unlockedIsBad(u) {
					addrs = append(addrs, u)
				}
			}
		}

		if c.relay != nil {
			for _, v := range c.relay.relay {
				relays = append(relays, v)
			}
		}
	}

	dnsAddrs := r.hr.GetAddrs()
	for _, addr := range dnsAddrs {
		if r.shouldAdd == nil || r.shouldAdd(r.vpnAddrs, addr.Addr()) {
			if !r.unlockedIsBad(addr) {
				addrs = append(addrs, addr)
			}
		}
	}

	r.addrs = addrs
	r.relays = relays

}
