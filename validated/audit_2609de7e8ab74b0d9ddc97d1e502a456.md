Found a strong analog. The `CostPacer::scheduling_budget` mechanism in `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs` mirrors the exact bug class from the RBS finding: a monotonically-increasing time-based budget that keeps expanding regardless of whether the underlying condition it was meant to gate (actual block fill/cost usage) still holds, and it is only recomputed when the leader slot changes — not when a stale/slow bank is still being processed well past its expected timeline.

### Title
Cost-pacing budget grows unboundedly stale once `detection_time` is set, allowing full-block-cost admission of transactions before real usage justifies it - (File: core/src/banking_stage/transaction_scheduler/scheduler_controller.rs)

### Summary
`CostPacer` computes a `scheduling_budget` by linearly interpolating from `0` to `block_limit` over `fill_time`, anchored to a single `detection_time` timestamp captured once when a new leader slot is detected [1](#0-0) . This is structurally the same pattern as the RBS bug: a threshold/allowance is derived purely from elapsed wall-clock time since a state transition, with no re-check of the actual underlying condition (real cost consumption) before granting more allowance.

### Finding Description
`detection_time` is captured only once, at the moment `most_recent_leader_slot` changes [2](#0-1) . `CostPacer::scheduling_budget` then computes `target` purely as a function of `current_time - detection_time` versus `fill_time`, subtracting only `shared_block_cost.load()` (actual cost consumed so far) [3](#0-2) . Because the target term is driven by elapsed time alone (not by observed throughput or delays), any stall between detecting the leader slot and actually being able to schedule/consume transactions (e.g., a slow `decision_maker`, GC pause, lock contention, or a bank that becomes the working bank late) causes the time-based `target` to keep climbing toward `block_limit` even though no real transactions have been processed yet. When scheduling resumes, the pacer immediately grants a scheduling budget close to `block_limit` in one shot instead of the intended gradual ramp, admitting transactions with the same "grossly underpriced pre-fee work" pattern the pacer exists to prevent (favoring low-fee-rate transactions to fill blocks early, ahead of higher-fee transactions that would legitimately arrive later in the fill window).

This differs from the intended "gradual pacing" invariant in the same way the RBS regen counter differed from its intended "price must return inside the wall" invariant: the gating value (`lastActive`/`detection_time`) is frozen at a past instant and the subsequent time-based check assumes forward progress that may not have actually happened.

### Impact Explanation
If exploited/triggered (deliberately or by incidental scheduler stalls), this allows admission of a large batch of low-priority-fee transactions in a burst once the stale time budget is finally consumed, defeating the pacing mechanism's purpose of reserving late-slot capacity for higher-fee transactions. This is a QoS-evasion-class effect (grossly underpriced pre-fee work displacing fee-paying work) rather than a fund-loss bug, but it is the closest structural analog to the RBS pattern within the allowed scope.

### Likelihood Explanation
Requires the scheduler loop to be delayed between leader-slot detection and the first `process_transactions` call for that slot (e.g., decision-maker/lock contention, GC/CPU stalls, or slow `receive_completed`), which is plausible under load but not attacker-controlled directly; likelihood is therefore low-to-moderate and mostly incidental rather than an unprivileged-user-triggerable exploit.

### Recommendation
Anchor `detection_time` to when scheduling actually starts consuming budget (or re-derive the target from `shared_block_cost` growth rate rather than pure wall-clock elapsed time), so that a stall between slot-detection and first scheduling does not manufacture unearned budget.

### Proof of Concept
1. `most_recent_leader_slot` changes, `cost_pacer.detection_time = now` is set [1](#0-0) .
2. Introduce a delay before the next `process_transactions(&decision, cost_pacer.as_ref(), &now)` call is reached with a fresh `now` (e.g. slow `receive_completed`/`decision_maker` iteration).
3. When `scheduling_budget(now)` is finally invoked, `time_since = now - detection_time` is already large relative to `fill_time`, so `target` is close to or equal to `block_limit` [3](#0-2) , granting a large one-shot budget instead of the intended gradual ramp.

Note: this is a plausible but not fully proven-in-production analog; confidence is moderate given the difficulty of directly attacker-triggering the scheduler-loop stall from an unprivileged network path.

impl CostPacer {
    fn scheduling_budget(&self, current_time: &Instant) -> u64 {
        let target = if let Some(fill_time) = &self.fill_time {
            let time_since = current_time.saturating_duration_since(self.detection_time);
            if time_since >= *fill_time {
                self.block_limit
            } else {
                // on millisecond granularity, pace the cost linearly.
                let allocation_per_milli = self.block_limit / fill_time.as_millis() as u64;
                let millis_since_detection = time_since.as_millis() as u64;
                allocation_per_milli * millis_since_detection
            }
        } else {
            self.block_limit
        };

        target.saturating_sub(self.shared_block_cost.load())
    }
