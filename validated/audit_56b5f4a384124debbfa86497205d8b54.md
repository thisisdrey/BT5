Attacker can force-fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via unconsented `deposit(onBehalfOf)` / `transfer`, permanently blocking new deposits and debt issuance for that account - (File: contracts/Pool.sol)

### Summary
`DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer/transferFrom` mint or move `msdToken` to an arbitrary recipient and, whenever the recipient's balance goes from `0` to `>0`, call `pool.addToDepositTokensOfAccount(recipient)`. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER`. An unprivileged attacker can therefore "register" every listed deposit token on a victim's account without the victim's consent — exactly the bug class of the reference report, where a public "pay/buy to arbitrary `to`" entrypoint forces tokens onto an address that never opted in, bypassing the intended restriction and DoS-ing a subsequent flow.

### Finding Description [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

1. `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` (only `!= address(0)` is checked) and mints `msdToken` to it. `transfer`/`transferFrom` credit an arbitrary `recipient_`. Neither requires consent from the recipient.
2. Both `_mint` and `_transfer` invoke `pool.addToDepositTokensOfAccount(account)` on the 0→>0 transition, and `DebtToken._mint` does the same via `addToDebtTokensOfAccount`.
3. `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` when the combined list length reaches `MAX_TOKENS_PER_USER`.

Attack path (unprivileged, public entrypoints only):
- Attacker calls `depositToken_i.deposit(1 wei equivalent, victim)` for every `depositToken` registered in the pool (they must source dust of each underlying, which is cheap for low-value collateral), filling `depositTokensOfAccount[victim]` up to `MAX_TOKENS_PER_USER` (any pre-existing victim entries count toward the cap, reducing attacker cost).
- From then on, for the victim:
  - `depositToken_j.deposit(amount, victim)` reverts for any `j` the victim didn't already hold (the `_mint` → `addToDepositTokensOfAccount` path reverts).
  - `transfer`/`transferFrom`/`seize` of a new deposit token to the victim reverts.
  - `debtToken.issue(amount, to)` reverts when it would register a *new* debt token for the victim (`_mint` → `addToDebtTokensOfAccount`), so the victim cannot open a position in a synthetic they don't already owe.

Critical timing: when the victim's position turns unhealthy, a natural defense is depositing additional collateral of a different (whitelisted) type. If the attacker has pre-filled the list, every such rescue `deposit` reverts unless the collateral token is one already in the victim's list, enabling the attacker to sandwich the victim's liquidation. The donated dust also marginally *increases* the victim's collateral value (`unlockedBalanceOf`/`depositOf` counts it), so the attacker is partially gifting value — but the list-capacity griefing is the exploitable primitive.

### Impact Explanation
Temporary denial of service / freezing of the victim's position-management ability: the victim cannot receive new collateral types (by deposit or transfer) and cannot issue new debt types while the list is saturated. This can be timed to coincide with liquidation so a rescue deposit reverts and the victim is liquidated, suffering the liquidation penalty. It is recoverable — the victim can `withdraw`/`transfer` the dust entries to trigger `removeFromDepositTokensOfAccount` and free slots — so the freeze is temporary rather than permanent, and requires a separate cleanup transaction that itself can be re-griefed by a persistent attacker.

### Likelihood Explanation
Medium-low. The attacker must hold dust of each whitelisted underlying to deposit on the victim's behalf; this is real but small cost, and any tokens the victim already holds reduce the work. All entrypoints used (`deposit`, `transfer`) are permissionless and unrestricted — `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` do not stop it, and `SynthContext._msgSender`/Operator paths change nothing. The main mitigation is that the victim can always unbrick themselves by moving the dust out, so the attack's window is bounded and it degrades to a griefing/liquidation-sandwich rather than outright theft.

### Recommendation
Only register an account in `depositTokensOfAccount`/`debtTokensOfAccount` when the account itself initiated the operation, or exempt consent-less pushes: e.g., in `DepositToken.deposit`/`transfer` call `addToDepositTokensOfAccount` only when `onBehalfOf_ == _msgSender()` / `recipient_ == _msgSender()`, or relax `onlyIfAdditionWillNotReachMaxTokens` for list-additions caused by inbound transfers and instead enforce the cap on outbound/issuance paths where the actor benefits. Alternatively let anyone call a `removeFrom*` cleanup for accounts they don't own, or skip list insertion for dust below a threshold.
