### Title
Signature Malleability Allows Duplicate Weight Counting in `ValidateMultiSign` TVM Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract, reachable by any contract that calls it during a `TriggerSmartContract`, deduplicates signer weight contributions by comparing the raw signature bytes rather than solely by the recovered signer address. Because ECDSA (secp256k1) signatures are malleable (a valid `(r, s)` can be transformed into another valid `(r, n-s)` that recovers to the same address), a single private key can produce two distinct signatures that both pass verification and both add weight to the multisig threshold calculation, effectively doubling the weight of one key.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()`: [1](#0-0) 
the loop recovers `recoveredAddr` for each supplied signature, then checks:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
The `continue` (skip) only triggers when the *exact same signature bytes* have already been seen for that address. If the same key produces a second, differently-encoded but still valid signature over the same hash (e.g., via ECDSA `s`-malleability, producing `n - s` with the corresponding `v` flipped), `recoveredAddr` is identical but `sign` differs, so the code does **not** skip — it proceeds to add that key's `weight` to `totalWeight` a second time. This lets an attacker holding a single low-weight key inflate `totalWeight` past `permission.getThreshold()` without collecting real approvals from other required signers.

By contrast, the account-level authentication path in `TransactionCapsule.checkWeight()` (used for validating on-chain transaction signatures) explicitly de-duplicates by recovered address/base64-encoded value via `addMap.containsKey(base64)` and throws `"has signed twice!"` if attempted, which is the correct anti-malleability pattern: [2](#0-1) 
The TVM precompile does not apply the same protection, making it inconsistent and exploitable specifically through smart-contract-triggered calls to the multisig-validation precompile.

### Impact Explanation
Any smart contract on TRON that relies on `ValidateMultiSign` (address `0x66` precompile) to gate privileged operations — for example custom multisig wallets, DAO-style approval logic, or asset-custody contracts — can be bypassed by a single colluding/compromised key holder who crafts a malleated duplicate signature. This allows an attacker controlling one authorized key (with weight below threshold) to have their operations (fund transfers, withdrawals, contract state changes) falsely treated as fully authorized by the required threshold, resulting in unauthorized account/contract operations and potential theft of funds held by contracts that depend on this precompile for authorization.

### Likelihood Explanation
The precompile is directly reachable by any contract deployer or caller through a normal `TriggerSmartContract`/`CreateSmartContract` transaction invoking address `0x66` (`ValidateMultiSign`) — no special privileges, no consensus/SR access, and no dependency on p2p/mocked paths are required. Constructing an ECDSA signature malleation (`s' = n - s`, `v' = v XOR 1`) is a well-known and trivial cryptographic operation, so any attacker who possesses one valid signature over the given hash can derive the second one without additional information. The only prerequisite is that a deployed contract actually uses this precompile for threshold-based authorization, which is a documented and intended use case of `ValidateMultiSign`.

### Recommendation
In `ValidateMultiSign.execute()` (and equally review `BatchValidateSign.execute()` for the same pattern), deduplicate strictly by `recoveredAddr` regardless of the exact signature bytes — i.e., skip weight accumulation whenever the address has already contributed, instead of only skipping on byte-identical signature duplicates. This mirrors the safe pattern already used in `TransactionCapsule.checkWeight()`.

### Proof of Concept
1. Attacker holds one key `K` that is a member of a contract-controlled `Permission` with `threshold` requiring, e.g., weight 2, while `K` alone only carries weight 1.
2. Attacker signs `hash` with `K`, producing `sig1 = (r, s, v)`.
3. Attacker derives the malleated signature `sig2 = (r, n - s, v XOR 1)`, which is also a cryptographically valid ECDSA signature for the same message and recovers to the same address as `sig1`.
4. Attacker calls the target contract, passing `[sig1, sig2]` into `ValidateMultiSign` (or a contract wrapping it).
5. In `execute()`, the first iteration adds `sig1`/`recoveredAddr` to `executedSignList` and adds `weight` (1) to `totalWeight`. On the second iteration, `recoveredAddr` is found in `executedSignList`, but `sign` (`sig2`, merged with address) is not found, so the `continue` is skipped; `weight` (1) is added again, making `totalWeight = 2`.
6. `totalWeight >= permission.getThreshold()` now evaluates true, and the precompile returns success (`dataOne()`), even though only a single distinct key actually authorized the operation. [3](#0-2)
