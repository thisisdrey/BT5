### Title
Dust deposits to arbitrary `onBehalfOf` fill a victim's token list to `MAX_TOKENS_PER_USER`, blocking all new collateral deposits and debt issuance - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken.deposit(uint256 amount_, address onBehalfOf_)` lets any caller mint the deposit token to an arbitrary account for any nonzero amount. On the victim's first-time receipt of each token, `_mint` calls `pool.addToDepositTokensOfAccount(account_)`, which reverts with `UserReachedMaxTokens` once the account holds `MAX_TOKENS_PER_USER = 30` entries across `depositTokensOfAccount` + `debtTokensOfAccount`. An unprivileged attacker can deposit 1 wei of each pool collateral into a victim, filling the list and griefing the victim's ability to add any new collateral type or take on any new debt type — an availability / temporary-freezing-of-funds analog of the advisory's low-privilege DoS class.

### Finding Description
- `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and any `amount_ > 0` (only `AmountIsZero`/`BeneficiaryIsNull` are rejected). There is no minimum deposit and no opt-in by the beneficiary. `contracts/DepositToken.sol:211-237`
- `_mint` adds the token to the victim's per-account list when their prior balance is zero: `if (_balanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(account_); }` `contracts/DepositToken.sol:486-488`
- `Pool.addToDepositTokensOfAccount` enforces the cap via `onlyIfAdditionWillNotReachMaxTokens`: once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` it reverts `UserReachedMaxTokens`. `contracts/Pool.sol:143-148, 216-220`
- The same modifier guards `addToDebtTokensOfAccount`, so once filled the victim also cannot mint a new kind of `DebtToken` (`_mint` → `addToDebtTokensOfAccount`, `contracts/DebtToken.sol:597-600`) nor deposit into a new collateral.
- The attacker funds the dust deposits themselves (`safeTransferFrom(_msgSender, _treasury, amount_)`), so the attack is fully unprivileged and repeatable: after the victim clears slots, the attacker can re-fill them.

### Impact Explanation
Temporary freezing of funds / griefing DoS. Until the victim withdraws or transfers out the dust positions (each removal costs the victim a transaction per token and may require interacting with tokens they never wanted), every action that would add a new token to their list reverts: depositing a new collateral type (`deposit`, `NativeTokenGateway`/`VesperGateway` wraps), and issuing any new synthetic debt. For a leveraged user being liquidated or needing to add a different collateral to restore health, this can delay remediation. Because the attack is repeatable and front-runnable, the freeze can be extended indefinitely as long as the attacker spends gas.

### Likelihood Explanation
Requires only an EOA calling the public `deposit` with dust amounts of each registered `DepositToken` — no privileged role, no oracle manipulation, no flash loan needed. The attacker's cost is bounded by gas plus the dust value for up to 30 distinct collateral types. Caveat lowering severity: impact is temporary rather than permanent — the victim can un-do each dust entry themselves via `withdraw`/`transfer` (their balance is unlocked while they have no debt), so funds are never permanently locked and no value is stolen; it is a griefing/availability issue consistent with the Medium severity of the reference advisory.

### Recommendation
- Require deposits on behalf of others to meet a minimum minted amount, or route beneficiary mints through an allowlist/consent mechanism (e.g., only add to `depositTokensOfAccount` when `onBehalfOf_ == _msgSender()` or when the beneficiary has opted in).
- Alternatively, skip `addToDepositTokensOfAccount` for below-threshold dust balances, or let users permissionlessly remove entries for tokens they hold (e.g., an `sweepDust(account, token)` that transfers negligible balances out).

### Proof of Concept
Hardhat-style sketch against deployed pool fixtures:

```ts
// Victim starts with an empty token list.
const MAX = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30
const depositTokens = await pool.getDepositTokens();       // registered collaterals

// Attacker deposits 1 wei of each distinct collateral to the victim.
for (let i = 0; i < MAX && i < depositTokens.length; i++) {
  const dt = await ethers.getContractAt('DepositToken', depositTokens[i]);
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, victim.address); // fills a slot
}
// (If fewer than 30 deposit tokens exist, attacker additionally
//  transfers dust of their own msdTOKEN balances to the victim via
//  dt.transfer(victim, 1), which also calls addToDepositTokensOfAccount.)

// Victim's list is now full.
expect((await pool.getDepositTokensOfAccount(victim.address)).length
  + (await pool.getDebtTokensOfAccount(victim.address)).length).to.eq(MAX);

// Victim attempts to deposit a collateral type they don't yet hold -> DoS.
const newDt = await ethers.getContractAt('DepositToken', someTokenNotInList);
await underlying.connect(victim).approve(newDt.address, amount);
await expect(newDt.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim attempts to issue a new synthetic debt type -> DoS.
await expect(debtToken.connect(victim).issue(issueAmount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
