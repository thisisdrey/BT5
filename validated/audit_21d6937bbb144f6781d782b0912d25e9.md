### Title
Old-style FreezeBalance re-locks already-expired (unlockable) frozen TRX by resetting a single shared expire time - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
`FreezeBalanceActuator` (and its TVM equivalent `FreezeBalanceProcessor`) stores bandwidth/energy freeze balance as a single aggregated amount with a single `expireTime` field rather than per-freeze entries with independent expiry. When a user calls `FreezeBalance` again, the actuator adds the new amount to *all* currently recorded frozen balance — including any portion whose lock period has already elapsed but has not yet been explicitly unfrozen — and overwrites the expire time with a new, later value. This mirrors the FlatMoney `PointsModule._setMintUnlockTime` bug: a fresh mint/freeze recalculates a single unlock timestamp that applies to previously-unlocked funds as well.

### Finding Description
In `FreezeBalanceActuator.execute`, for the bandwidth case: [1](#0-0) 

`accountCapsule.getFrozenBalance()` sums whatever is currently in the account's `Frozen` list, regardless of whether that entry's `expireTime` has already passed. The old, already-unlockable amount is combined with the newly frozen amount and re-stored via `setFrozenForBandwidth(newFrozenBalanceForBandwidth, expireTime)`, which sets a single `expireTime` for the *whole* combined balance: [2](#0-1) 

The same pattern exists in the TVM-callable native contract path used by smart contracts (`freezeBalance` opcode/precompile): [3](#0-2) 

Crucially, an account's previously-frozen balance is only removed from the `Frozen` list when the user *explicitly* calls `UnfreezeBalance`, which filters entries by `expireTime <= now`: [4](#0-3) [5](#0-4) 

This means between the moment a freeze period naturally expires and the moment `UnfreezeBalance` is actually called, the expired-but-still-recorded frozen balance remains part of `getFrozenBalance()`. If the account (or a contract account, since `FreezeBalanceProcessor` is reachable from TVM) issues a new `FreezeBalance`/`freezeBalance` call in that window, the already-expired amount gets folded into the new frozen total and is assigned the new, later `expireTime` — exactly the "unlocked points can be locked up again" pattern from the report.

### Impact Explanation
A user's TRX that has completed its freeze period (and is thus eligible to be unfrozen and spent) can be silently re-locked for a full new freeze duration (3 days for bandwidth/energy, 3 days for TRON Power under legacy rules) simply by issuing another `FreezeBalanceContract` for the same resource type before calling `UnfreezeBalance`. This is a temporary/permanent-until-re-triggered freezing of funds: the user loses access to already-vested TRX for an additional lock period, which can be triggered even unintentionally (e.g., automated freezing bots, or a malicious actor front-running/griefing by freezing on behalf of themselves is not applicable since it's owner-only, but the owner's own funds can be inadvertently or repeatedly re-locked, and any tooling/dApp performing routine re-freezing can trigger this each cycle). This qualifies as unintended/unauthorized freezing of funds reachable from a single signed `FreezeBalanceContract` transaction or TVM `freezeBalance` call.

### Likelihood Explanation
Both `FreezeBalanceActuator.execute` (BANDWIDTH and ENERGY, and TRON_POWER) and `FreezeBalanceProcessor.execute` combine `frozenBalance + accountCapsule.getFrozenBalance()` (or the energy-resource equivalent) without excluding already-expired frozen entries, and always overwrite the expire time. Any account/contract with an expired-but-unwithdrawn frozen balance that calls freeze again for the same resource on the same account (very common usage pattern, since users regularly top up frozen amounts for bandwidth/energy) will trigger this behavior. No special privilege is required — it is reachable by any account owner via a normal signed transaction or a deployed contract invoking the `freezeBalance` native contract.

### Recommendation
Before merging the new freeze amount into the existing frozen total, first settle/expire any already-matured `Frozen` entries (as `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` do) and return that matured balance to the account's spendable balance, or otherwise track freeze entries independently with their own expiry rather than a single aggregated amount+expireTime pair. At minimum, `FreezeBalanceActuator`/`FreezeBalanceProcessor` should call the equivalent of `unfreezeExpire`-style logic on existing frozen balance for that resource type prior to computing `newFrozenBalanceForBandwidth`/`newFrozenBalanceForEnergy`.

### Proof of Concept
1. Account A calls `FreezeBalance(amount=X, duration=3 days, resource=BANDWIDTH)`. `Frozen{frozenBalance=X, expireTime=T0+3d}` is stored via `setFrozenForBandwidth`. [6](#0-5) 
2. Time passes; block timestamp now > T0+3d. Account A does not call `UnfreezeBalance`, so `Frozen` list still holds `{X, T0+3d}` (expired but not withdrawn) — confirmed by `UnfreezeBalanceActuator` only removing entries when explicitly invoked. [7](#0-6) 
3. Account A calls `FreezeBalance(amount=Y, duration=3 days, resource=BANDWIDTH)` again. `newFrozenBalanceForBandwidth = Y + getFrozenBalance() = Y + X`, and `setFrozenForBandwidth(Y+X, now+3d)` overwrites the single frozen entry, resetting the expire time for the entire `X+Y` to `now+3d`. [8](#0-7) 
4. The amount `X`, which had already completed its lock period and was eligible for `UnfreezeBalance`, is now locked again for another 3 days.
