### Title
Premature destruction of a shared Object Pool while member repositories still depend on it via alternates - ([File: internal/gitaly/service/objectpool/delete.go])

### Summary
Gitaly's `ObjectPoolService.DeleteObjectPool` RPC unconditionally deletes an object pool repository from disk without verifying that no member repository still references it through the Git `alternates` mechanism. This mirrors the PoolFactory bug class: a shared, depended-upon resource (the ACL owner / the object pool's object database) can be destroyed while other components still rely on it, permanently corrupting all dependents.

### Finding Description
An object pool is a bare repository whose objects are shared by many "member" repositories through the Git `objects/info/alternates` file [1](#0-0) . Members are attached via `LinkRepositoryToObjectPool`, which writes the pool's relative object path into the member's alternates file [2](#0-1) , and are only safely detached via `DisconnectGitAlternates`, which hard-links pool objects into the member and runs a connectivity check before removing the alternates link [3](#0-2) .

However, `DeleteObjectPool` performs none of these safety steps. It simply resolves the pool and calls `repoutil.Remove` to delete the pool directory from disk: [4](#0-3) 

The proto definition explicitly documents this gap as intentional, placing the entire safety burden on the caller: [5](#0-4) [6](#0-5) 

Nowhere in `DeleteObjectPool` is there a check against `PoolStore.ListPoolMembers` (which does exist as an interface capability, see `internal/gitaly/storage/relational/pool_store.go`) or any equivalent alternates-membership check before the pool is removed. As a result, if `DeleteObjectPool` is invoked (whether through a race with `LinkRepositoryToObjectPool`, an out-of-order orchestration call, or a directly crafted RPC) while member repositories are still linked to the pool via alternates, all of those member repositories immediately become permanently and irrecoverably corrupted — their alternate object directory disappears and their history/objects become unreachable, exactly analogous to the ACL contract being left ownerless after PoolFactory's self-destruct.

### Impact Explanation
This falls squarely into the "object-pool and alternates isolation" bug class. Any member repository still relying on the deleted pool for deduplicated objects will fail Git operations that need those objects (clone, fetch, fsck, etc.), and there is no automatic recovery path — unlike `DisconnectGitAlternates`, which keeps a backup and performs a connectivity check, `DeleteObjectPool` performs an outright deletion with no rollback. Depending on how many repositories are linked to the pool (potentially all forks of a project), this can cause widespread, cross-repository data-availability loss/corruption from a single RPC call.

### Likelihood Explanation
The RPC is a normal `MUTATOR` operation reachable with the standard Gitaly RPC authentication used by all client-facing services (Rails/Workhorse/gitlab-shell/Praefect), the same trust boundary as any other object-pool RPC, so no elevated internal privilege beyond ordinary RPC access is required. The precondition — the pool still having members — is easily reached in normal operation (e.g., pool deletion racing with fork housekeeping, replayed/duplicate RPCs during Praefect coordination, or a caller that fails to first disconnect all members as required by the documented but unenforced contract).

### Recommendation
Before physically removing the pool repository in `DeleteObjectPool`, verify that no repository is still linked to it (e.g., via `PoolStore.ListPoolMembers`/`ForEachPoolByStorage` or by scanning for repositories whose alternates reference the pool) and reject the deletion (or force disconnection first) if any members remain, mirroring the recommendation from the PoolFactory report: never remove a shared, referenced resource while dependents still exist. At minimum, add a warning-free hard error path analogous to `ContractUpgrader.destroy()`'s `RootSelfDestroyException` check.

### Proof of Concept
1. Create an object pool from repository A: `CreateObjectPool(origin=A)`.
2. Link repository B to the pool: `LinkRepositoryToObjectPool(pool, B)` — B's `objects/info/alternates` now points at the pool.
3. Call `DeleteObjectPool(pool)` — the pool directory is deleted immediately with no membership check [4](#0-3) .
4. Any Git operation against B that needs pool-only objects (e.g. `git fsck`, `git cat-file`) now fails because the alternates path no longer exists — B is permanently corrupted, with no built-in recovery.

# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
```

// Disconnect disconnects the specified repository from its object pool. If the repository does not
// utilize an alternate object database, no error is returned. For repositories that depend on
// alternate objects, the following steps are performed:
//   - Alternate objects are hard-linked to the main repository.
//   - The repository's Git alternates file is backed up and object pool disconnected.

func (s *server) DeleteObjectPool(ctx context.Context, in *gitalypb.DeleteObjectPoolRequest) (*gitalypb.DeleteObjectPoolResponse, error) {
	pool, err := s.poolForRequest(ctx, in)
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			// TODO: we really should return an error in case we're trying to delete an
			// object pool that does not exist.
			return &gitalypb.DeleteObjectPoolResponse{}, nil
		}

		return nil, err
	}

	if err := repoutil.Remove(ctx, s.logger, s.locator, nil, s.repositoryCounter, pool); err != nil {
		return nil, fmt.Errorf("remove: %w", err)
	}
```
