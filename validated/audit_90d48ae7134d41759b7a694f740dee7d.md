## Analysis

The external report's core broken invariant: **a rate that only decreases *dynamically* (without a stored snapshot of already-accrued value at the old rate) causes stale accrued value to be re-computed at the new, lower rate, and the differential is misallocated to the wrong party.**

This repository already discovered and *partially* patched exactly this bug class in `pallet-nomination-pools`. `prdoc/pr_12397.prdoc` documents that `set_commission_max` force-lowers `commission.current` via `try_update_max`, and if `update_records` (the reward-pool snapshot) isn't called *first*, rewards accrued at the higher rate get re-rated at the new lower rate on the next `update_records`, crediting the differential to pool members instead of the commission payee. [1](#0-0) 

The fix applied snapshots the reward pool via `update_records` immediately before `try_update_max` is allowed to force-lower `current`, mirroring the ordering already used in `set_commission`: [2](#0-1) 

However, the *effective* commission rate is **not solely** determined by `commission.current`. It is dynamically clamped against `GlobalMaxCommission` on every read:

```rust
fn current(&self) -> Perbill {
    self.current
        .as_ref()
        .map_or(Perbill::zero(), |(c, _)| *c)
        .min(GlobalMaxCommission::<T>::get().unwrap_or(Bounded::max_value()))
}
``` [3](#0-2) 

Every caller of `current_reward_counter`/`update_records` (via `claim_payout`, `claim_payout_other`, `bond_extra`, `unbond`, `join`, `set_commission`, `set_commission_max`) reads `bonded_pool.commission.current()` at call time and feeds it straight into `current_reward_counter`, which re-rates the *entire unrated payout balance since the last snapshot* at whatever commission value is passed in: [4](#0-3) [5](#0-4) 

Unlike `set_commission_max`, there is no call site that snapshots every pool's reward pool (via `update_records`) at the moment `GlobalMaxCommission` is lowered. The clamp in `current()` is applied lazily/globally and retroactively to *all* pools' un-snapshotted accrued rewards, the exact same failure mode the authors just fixed for the single-pool `set_commission_max` path, but left open at the global level.

### Title
Lazy global-commission-max clamp re-rates un-snapshotted rewards, diverting commission payee funds to members - (`substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`BondedPool::commission.current()` clamps the stored per-pool commission rate against `GlobalMaxCommission` on every read instead of at the point the global maximum is lowered. When the global max is reduced, every pool's un-snapshotted accrued-but-unclaimed reward balance since its last `update_records` call gets re-rated at the new lower commission on the very next `claim_payout`, `bond_extra`, `unbond`, or `join` — a permissionless action by any ordinary pool member — silently moving the commission differential from the commission payee to pool members, contradicting the exact fix the maintainers already applied to `set_commission_max`.

### Finding Description
`RewardPool::current_reward_counter` computes `current_payout_balance` as everything accrued since `last_recorded_total_payouts`, then splits it into commission vs. member reward using whatever `commission: Perbill` is passed in at call time: [6](#0-5) 

`commission.current()` does not return a durable, previously-agreed rate — it re-derives the effective rate on every call by taking `min(stored_current, GlobalMaxCommission::get())`. The stored `current` value is untouched; only the *observed* rate changes the instant `GlobalMaxCommission` is lowered by governance/root. There is no code path that iterates `BondedPools`/`RewardPools` and calls `update_records` to snapshot every pool's accrued rewards at the *old* effective rate before (or as part of) lowering `GlobalMaxCommission`.

Consequently, rewards that accrued between a pool's last snapshot and the moment `GlobalMaxCommission` drops are, on the very next unprivileged action that triggers `update_records`/`current_reward_counter` (e.g., `claim_payout` by any member, `bond_extra`, `join`, `unbond`), rated at the *new* lower commission rather than the rate that was actually in effect while they accrued. This is structurally identical to the bug the maintainers fixed in `set_commission_max`, where the fix was to snapshot with `update_records` at the *old* rate before applying the reduction — that snapshot-before-lower discipline is absent for the global-max path.

### Impact Explanation
This is a value-conservation/wrong-beneficiary bug in the treasury/reward-payout category: the commission differential the payee is entitled to is instead credited to pool members, who can extract it via ordinary `claim_payout`/`unbond`/`withdraw_unbonded` calls. The commission payee (often the pool operator/root, sometimes a third party) permanently loses funds it had already earned; no admin abuse or malicious actor is required — an ordinary, unprivileged pool member simply calling `claim_payout` after a legitimate `GlobalMaxCommission` reduction is enough to trigger the misallocation.

### Likelihood Explanation
`GlobalMaxCommission` is a normal runtime-configurable/root-settable parameter intended to be adjustable to cap all pools network-wide; each time it decreases, every pool with `current > new_max` is affected. The trigger condition (any member action causing `update_records`/`current_reward_counter` to run) is routine and happens continuously (deposits, joins, unbonds, claims), so the misallocation window is realistically exploitable and not a rare edge case — it is the default behavior anytime the global cap is lowered while unclaimed rewards exist.

### Recommendation
Apply the same discipline used for `set_commission_max`: whenever `GlobalMaxCommission` is reduced, iterate all `BondedPools`/`RewardPools` (or lazily snapshot on next touch, gated by a stored "effective rate at last snapshot" rather than a live re-derived clamp) and call `update_records` with each pool's *pre-reduction* effective commission before the new global max takes effect for reward-counter purposes. Alternatively, stop clamping `current()` dynamically for reward-accounting purposes and only apply the global cap at the point `try_update_current`/`try_update_max` mutate the stored `current`, always preceded by an `update_records` snapshot, consistent with the pattern already fixed for the per-pool path.

### Proof of Concept
1. Root sets `GlobalMaxCommission = 50%`. Pool `1`'s commission is set to `50%` via `set_commission` (snapshots reward pool at the time, per existing fix).
2. `100` units of reward accrue in pool `1` with no intervening claim/bond/unbond (no snapshot occurs).
3. Root lowers `GlobalMaxCommission` to `20%` (no per-pool snapshot occurs anywhere, since this path is not covered like `set_commission_max`).
4. Any member calls `claim_payout`, which calls `do_reward_payout` → `reward_pool.current_reward_counter(..., bonded_pool.commission.current())`, where `commission.current()` now returns `20%` (clamped) instead of the `50%` that was actually in force while the `100` accrued.
5. The full `100` is split `20/80` instead of `50/50`; the payee only receives `20` (or less, since already-claimed shares reduce the payee's future claimable amount) instead of the `50` they earned, and the extra `30` is credited to member reward shares — reproducing, at the global level, the exact loss pattern the `set_commission_max` fix (`prdoc/pr_12397.prdoc`) was written to prevent at the per-pool level.
