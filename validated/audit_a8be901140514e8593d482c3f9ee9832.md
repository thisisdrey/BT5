### Title
Missing verification that claimed `RelayFromAddr`/`RelayToAddr` in `CreateRelayRequest`/`CreateRelayResponse` matches the authenticated sender's identity - ([File: relay_manager.go])

### Summary
The Sherlock report's root cause is that `Depositor#withdrawFromGauge` and `DepositReciept#burn` trust an NFT id without verifying it was minted by (i.e., "belongs to") the caller's own contract instance, letting one user manipulate another user's deposit/reward state. The closest reachable analog in Nebula's relay subsystem is `relayManager.HandleControlMsg` → `handleCreateRelayRequest`/`handleCreateRelayResponse` in `relay_manager.go`, which process attacker-suppliable `RelayFromAddr`/`RelayToAddr` (or the legacy `OldRelayFromAddr`/`OldRelayToAddr`) fields taken directly from the `NebulaControl` protobuf payload, rather than deriving the "from" identity strictly from the already-authenticated `HostInfo h` that carried the control message.

### Finding Description
`relayManager.HandleControlMsg` [1](#0-0)  unmarshals a `NebulaControl` message and, for `CreateRelayRequest`/`CreateRelayResponse`, only checks that `RelayFromAddr`/`RelayToAddr` are non-nil [2](#0-1)  before dispatching to `handleCreateRelayRequest`/`handleCreateRelayResponse`. Inside `handleCreateRelayRequest`, the `from` address used to build and index relay state (`h.relayState.QueryRelayForByIp(from)`, `AddRelay(rm.l, h, f.hostMap, from, ...)`) is taken from `msg.RelayFromAddr` — attacker-controlled payload data — rather than being cross-checked against `h.vpnAddrs` (the cryptographically verified identity of the peer that actually sent this authenticated control message over its Noise-protected tunnel) [3](#0-2) . The only identity checks performed are "is the source of the relay me" and "is the target of the relay me" [4](#0-3) , neither of which validates that the claimed `from` corresponds to the sender `h`. This mirrors the Sherlock finding's root cause: an operation is bound to an identifier taken from caller-supplied data instead of being enforced against the entity that actually owns/authenticated the associated state (in Isomorph, "the depositor that minted the NFT"; here, "the HostInfo that authenticated the connection").

### Impact Explanation
If `from` in a relay control message does not have to match the authenticated sender's own `vpnAddrs`, a malicious authenticated peer (or a peer that itself has an established Nebula tunnel, i.e., not a stranger, but not the actual party the relay is being created for) could register itself as a relay-hop or relay-terminus for a `from` address it does not own. This would let the attacker insert its own `HostInfo`/relay index into another node's relay path, potentially poisoning remote relay state (`Relay.PeerAddr`, `RelayState`), hijacking or intercepting traffic meant for the real owner of that `vpnAddr`, or creating relay-index bindings that cause traffic to be forwarded to/through the attacker instead of the legitimate peer — a direct analog to "stealing" another party's traffic/relay relationship, similar in spirit to stealing another user's staked rewards by manipulating shared identifier state.

### Likelihood Explanation
Exploitability requires only that the attacker holds any authenticated Nebula tunnel to the target relay/terminal node (already reachable without a CA-signed cert being needed for the attacker's own claim, since the manipulated field is the payload-level `from`, not the connection's certificate identity) and sends a crafted `NebulaControl` message with a `RelayFromAddr` that is not its own address. This is a realistic "malicious authenticated peer supplies forged control-plane metadata" scenario rather than a stranger-with-no-cert scenario, so it sits right at the edge of the rules (reachable via header/control-message parsing and hostmap/relay address trust, which is explicitly in-scope).

### Recommendation
In `handleCreateRelayRequest` and `handleCreateRelayResponse`, require that the claimed `RelayFromAddr` (or `OldRelayFromAddr`) equals one of `h.vpnAddrs` before using it to index or mutate `RelayState`; reject the message otherwise. This enforces that relay state can only be created/modified using the identity that was actually authenticated for the `HostInfo h` carrying the message, closing the analogous "operate on someone else's identifier" gap identified in the Isomorph report.

### Proof of Concept
Conceptual PoC (not verified end-to-end due to tool-call limitations on the final iteration):
1. Attacker `A` establishes a legitimate, certificate-authenticated tunnel to relay/terminal node `T` (`HostInfo h` for `A` exists on `T`).
2. `A` sends `T` a `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to victim `B`'s `vpnAddr` (not `A`'s own) instead of its real address.
3. `handleCreateRelayRequest` on `T` processes the message using `h` (bound to `A`'s real, authenticated tunnel) but derives `from := protoAddrToNetAddr(m.RelayFromAddr)` = `B`, then calls `h.relayState.QueryRelayForByIp(from)` / `AddRelay(rm.l, h, f.hostMap, from, ...)`, associating relay state for `B` with `A`'s `HostInfo`.
4. Because no check enforces `from == h.vpnAddrs[0]`, `T` believes `A` is authorized to be the relay-from party for `B`, letting `A` insert itself into `B`'s relay path/state.

**Uncertainty:** I was unable to re-open `relay_manager.go` lines 1-78 or the `RelayState`/`InsertRelay`/`QueryRelayForByIp` implementations in `hostmap.go` in the final iteration to confirm there is no earlier, upstream check (e.g., in `HandleControlMsg` or in how `h` is resolved) that already ties `from` to `h.vpnAddrs`. This should be verified directly before treating this as a confirmed vulnerability — a Devin session with full file access should re-read `relay_manager.go:1-78`, `hostmap.go` relay-state methods, and `outside.go`'s control-message dispatch path (where `h` is resolved from `h.RemoteIndex` before `HandleControlMsg` is invoked) to confirm whether `from` is ever cross-validated against the authenticated peer identity.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.

						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
