### Title
Bridged-in synthetic tokens burned via `DebtToken.repay`/liquidation permanently inflate `totalBridgedIn`, DoSing all future bridge-ins - ([File: contracts/SyntheticToken.sol])

### Summary
`SyntheticToken` tracks cross-chain conservation with two asymmetric counters: `totalBridgedIn` is incremented only when `proxyOFT` is the minter, and `totalBridgedOut` only when `proxyOFT` is the burner. Synthetic tokens that entered the chain through the bridge but are later burned through a different controller (`DebtToken.repay`, `Pool.liquidate`, `DebtToken.repayAll`, seize-and-burn flows) reduce `totalSupply` but never decrement `totalBridgedIn`. Once enough bridged-in tokens are destroyed via non-bridge burn paths, `bridgedInSupply()` exceeds `maxBridgedInSupply` and every subsequent `ProxyOFT._creditTo` → `syntheticToken.mint` reverts, blocking all inbound bridging and leaving in-flight cross-chain transfers failing/retrying until governance manually raises the cap.

### Finding Description
In `SyntheticToken._mint`, the bridged-supply accounting is keyed on the caller:

```solidity
if (_isMsgSenderProxyOFT(_msgSender)) {
    totalBridgedIn += amount_;
    if (bridgedInSupply() > maxBridgedInSupply) revert SurpassMaxBridgingSupply();
}
```

`contracts/SyntheticToken.sol:338-340`

In `SyntheticToken._burn`, only a `proxyOFT` burn increments `totalBridgedOut`:

```solidity
if (_isMsgSenderProxyOFT(_msgSender)) {
    totalBridgedOut += amount_;
    if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
}
```

`contracts/SyntheticToken.sol:275-277`

`bridgedInSupply()` computes `max(totalBridgedIn - totalBridgedOut, 0)` (`contracts/SyntheticToken.sol:160-167`), so it is meant to represent the *current* amount of bridged-in supply outstanding on this chain. But burning is routed by caller identity, not by token provenance:

- `DebtToken.repay` and `repayAll` call `_syntheticToken.burn(_msgSender, _repaid)` where `msg.sender` to `SyntheticToken` is the `DebtToken` (`contracts/DebtToken.sol:453`, `contracts/DebtToken.sol:491`).
- `DebtToken.flashIssue`/seize flows and `Pool.liquidate` burns go through the `DebtToken`/`Pool` caller path as well.
- None of these decrement `totalBridgedIn`.

This is the same bug class as CVE-2025-22011: two controllers (the `ProxyOFT` bridging path and the `DebtToken`/`Pool` burn paths) both mutate the same logical resource (outstanding bridged-in supply), but only one of them updates the shared accounting. Mixed use leaves the state inconsistent and the resource fails to "resume" — bridge-in mints permanently revert once the phantom `bridgedInSupply()` exceeds `maxBridgedInSupply`.

### Impact Explanation
Broken invariant: bridge conservation (`bridgedInSupply()` should equal actual outstanding bridged-in tokens). Every synthetic token that was minted by `ProxyOFT` and later destroyed through `repay`, `repayAll`, or liquidation leaves `totalBridgedIn` overstated forever — there is no code path that decrements it other than bridging back out, and the tokens no longer exist to be bridged out.

Once `bridgedInSupply() > maxBridgedInSupply`, all inbound cross-chain mints revert in `SyntheticToken._mint` inside `ProxyOFT._creditTo` (`contracts/ProxyOFT.sol:86-93`), so LayerZero receive calls fail and users' bridged funds are stuck in the retry queue. The protocol's only recovery is governor calling `updateMaxBridgedInSupply` — i.e., temporary freezing of bridged funds plus permanent cap drift.

### Likelihood Explanation
- Reachable by an unprivileged attacker: bridge in synths to this chain (normal `sendFrom` on the source chain — attacker supplies their own tokens), then call `DebtToken.repay(attacker, amount)` or `repayAll` to burn them via the `DebtToken` caller path. `totalBridgedIn` stays inflated; repeat until the cap is exceeded.
- It also happens organically without an attacker: any ordinary user repaying debt with tokens that were originally bridged in inflates `bridgedInSupply()`, so the cap is gradually consumed by phantom supply in normal operation.
- No modifier stops it: `repay`/`repayAll` are public `whenNotShutdown`/`nonReentrant` entry points (`contracts/DebtToken.sol:418-495`), and `burn` only requires `onlyIfCanBurn`, which any registered `DebtToken` satisfies (`contracts/SyntheticToken.sol:83-92`, `313-320`).
- Cost to the attacker equals the amount of bridged supply they must destroy to exceed the cap (real synth value burned), so this is griefing-class; the organic drift makes the cap mismatch occur regardless.

### Recommendation
Make the bridge-supply accounting symmetric with actual outstanding supply. Options: (a) in `_burn`, when the burned tokens reduce `totalSupply` below what the bridge counters imply, decrement `totalBridgedIn` (e.g., `totalBridgedIn = min(totalBridgedIn, totalSupply)` or subtract on any non-proxyOFT burn up to `totalBridgedIn`); or (b) treat `totalBridgedIn`/`totalBridgedOut` as running totals and compare the *delta of circulating supply*, not net counters, against caps. At minimum, decrement `totalBridgedIn` when tokens are burned through `DebtToken`/`Pool` paths.

### Proof of Concept
Foundry-style fork test sketch:

```solidity
function testBridgedInSupplyInflatedByRepay() public {
    // Deployed config: maxBridgedInSupply > 0
    uint256 cap = syntheticToken.maxBridgedInSupply();

    // Attacker bridges in `cap` synths from source chain.
    // Simulate _creditTo: prank ProxyOFT to mint to attacker.
    vm.prank(address(proxyOFT));
    syntheticToken.mint(attacker, cap);
    assertEq(syntheticToken.bridgedInSupply(), cap);

    // Attacker opens a position and repays it using the bridged-in synths,
    // so burn() is invoked with msg.sender == DebtToken.
    depositToken.deposit(collateral, cap * 2);
    debtToken.issue(amount, attacker);           // attacker has debt
    debtToken.repayAll(attacker);                // burns synths via DebtToken path

    // bridgedInSupply() still reports `cap` even though those tokens are burned
    assertEq(syntheticToken.bridgedInSupply(), cap);
    assertLt(syntheticToken.totalSupply(), cap);

    // Any further bridge-in reverts -> inbound bridging DoS
    vm.prank(address(proxyOFT));
    vm.expectRevert(SurpassMaxBridgingSupply.selector);
    syntheticToken.mint(victim, 1);
}
```

Note: exact harness wiring (registered `DebtToken`, `ProxyOFT` address, and the deployed `maxBridgedInSupply` values per chain in `deployments/*/`) should be confirmed against the target deployment; the counter asymmetry itself is unconditional in the code.
