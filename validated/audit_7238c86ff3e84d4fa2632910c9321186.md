Audit Report

## Title
Permanent fund lock in `claim_child_bounty`: payout transfer failures are ignored via `debug_assert!` and bounty state is unconditionally destroyed - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`claim_child_bounty` transfers the curator fee and beneficiary payout from `child_bounty_account_id` using `T::Currency::transfer(..., AllowDeath)`, but only checks the results with `debug_assert!`, which compiles to a no-op in release builds. [1](#0-0)  Regardless of whether the transfer to the beneficiary actually succeeds, the code unconditionally decrements `ParentChildBounties`, removes `ChildBountyDescriptionsV1`, and sets `*maybe_child_bounty = None`, permanently deleting the only on-chain record referencing `child_bounty_account_id`. [2](#0-1) 

## Finding Description
In `claim_child_bounty`, after computing `curator_fee` and `payout` from the child bounty account's `free_balance`, the pallet performs two `AllowDeath` transfers and discards their `Result` via `debug_assert!(fee_transfer_result.is_ok())` and `debug_assert!(payout_transfer_result.is_ok())`. [1](#0-0)  Neither result is propagated with `?`. Debug assertions are stripped in production/release builds (the default for real chains), so a failed transfer produces no error and does not abort the extrinsic.

Immediately afterward, the code emits the `Claimed` event and unconditionally tears down all bookkeeping: it decrements `ParentChildBounties`, removes the `ChildBountyDescriptionsV1` entry, and sets the `ChildBounties` storage entry to `None`. [3](#0-2)  This happens irrespective of whether the transfer above actually moved funds out of `child_bounty_account_id`.

`claim_child_bounty` is callable by any signed account once `unlock_at` has elapsed — there is no beneficiary-only restriction. [4](#0-3)  Once the `ChildBounties` entry for `(parent_bounty_id, child_bounty_id)` is removed, any subsequent call referencing that index (including a retry of `claim_child_bounty`) fails with `BountiesError::<T>::InvalidIndex`, since the lookup depends on `maybe_child_bounty.as_mut().ok_or(...)`. [5](#0-4)  There is no `reclaim_child_bounty_funds`-style extrinsic in the child-bounties pallet analogous to the one that exists in `pallet-bounties` (confirmed via search: `substrate/frame/bounties/src/lib.rs` contains such a reclaim path added by `prdoc/pr_11045.prdoc`, whereas `substrate/frame/child-bounties/src/lib.rs` has no equivalent public function to recover stranded balances). [6](#0-5) 

The failure mode requiring no privileged action: `award_child_bounty` lets the curator specify an arbitrary `beneficiary: AccountIdLookupOf<T>` with no existence or existential-deposit check performed at award time. [7](#0-6)  If `payout = balance - curator_fee` ends up below the chain's existential deposit and the beneficiary account has never been created, `Currency::transfer(..., AllowDeath)` returns an error (e.g., `TokenError::CannotCreate`), yet execution proceeds as described above.

## Impact Explanation
This is a permanent fund lock: the payout amount remains stranded in `child_bounty_account_id`, which is no longer referenced by any live storage entry after `ChildBounties` is cleared, so no dispatchable call in the pallet can recover it. This matches the "permanent user-fund or bridge-state lock" category in the impact gate, since the corrupted/lost value is the balance held at `child_bounty_account_id` for the given `(parent_bounty_id, child_bounty_id)` pair, and no governance, admin, or permissionless mechanism exists in this pallet to sweep it back.

## Likelihood Explanation
The trigger condition — a beneficiary account that does not exist and a payout below the existential deposit — is plausible without any malicious/privileged actor: it can arise from an ordinary misconfiguration (curator sets a fee close to the bounty value, or specifies a fresh/unfunded beneficiary address), and `claim_child_bounty` can then be called by any unprivileged signed account once `unlock_at` passes. No attacker needs elevated permissions; they only need to observe or induce this state and submit a normal signed extrinsic.

## Recommendation
- Propagate `fee_transfer_result` and `payout_transfer_result` with `?` (or explicit `map_err`) instead of `debug_assert!`, and only proceed with clearing `ChildBounties`, `ParentChildBounties`, and `ChildBountyDescriptionsV1` after both transfers succeed.
- Add a permissionless reclaim path (mirroring `pallet_bounties`'s reclaim mechanism) so that if a child bounty's escrow account still holds a balance, it can be recovered even after the record is removed, or avoid removing the record until settlement is confirmed.
- Validate that the beneficiary can receive the intended payout (existence/ED check) at `award_child_bounty` time rather than deferring failure to `claim_child_bounty`.

## Proof of Concept
1. Create a parent bounty and a child bounty with `value` slightly above the existential deposit (ED) and a curator `fee` such that `payout = value - fee < ED`.
2. Curator calls `award_child_bounty` with `beneficiary` set to a brand-new, never-funded account.
3. After `unlock_at`, any signed account calls `claim_child_bounty(parent_bounty_id, child_bounty_id)`.
4. `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)` returns `Err(TokenError::CannotCreate)`; `debug_assert!` is compiled out in release builds, so execution continues.
5. `Claimed` event is emitted (falsely signaling success), `ParentChildBounties` is decremented, `ChildBountyDescriptionsV1` is removed, and `ChildBounties` entry is set to `None`.
6. The `payout` balance remains in `child_bounty_account_id` with no storage entry left to reference or reclaim it — a permanent fund lock, reproducible as a Rust unit test in `substrate/frame/child-bounties/src/tests.rs` asserting non-zero `free_balance(child_bounty_account_id)` after the storage removal and a failed transfer.
