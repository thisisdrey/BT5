### Title
Unbounded growth of `DelegatedResourceAccountIndex` per address enables DoS of resource-delegation query APIs - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegateResourceContract` is a fully permissionless, unprivileged transaction any account can broadcast to delegate frozen bandwidth/energy to an arbitrary receiver address. Each delegation adds a new entry to a per-address index (`toAccounts`/`fromAccounts`) with **no maximum-count check** anywhere in `DelegateResourceActuator`/`FreezeBalanceActuator` validate/execute paths. An attacker can therefore make the delegation-index list for any victim address (or their own address) grow without bound, at the cost of many cheap freeze+delegate transactions from throwaway accounts. This index is later read in full and sorted by `DelegatedResourceAccountIndexStore.getWithPrefix()`, which backs the `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` Wallet methods exposed via unauthenticated HTTP/gRPC query endpoints (`GetDelegatedResourceAccountIndexServlet`, `GetDelegatedResourceAccountIndexV2Servlet`, and the RPC equivalents). This mirrors the reported bug class: a permissionless action inflates a shared/queryable array without limit, and a later "normal" operation (in this case, a query) must iterate/sort the full unbounded list.

### Finding Description
- `DelegateResourceActuator.execute()` (actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java) and `FreezeBalanceActuator.delegateResource()` add an entry to `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` (or write a new key under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` namespace via `DelegatedResourceAccountIndexStore.delegateV2`) for every distinct `(owner, receiver)` pair. [1](#0-0) [2](#0-1) 
- Neither `validate()` method enforces any cap on the number of distinct receivers/senders an account can accumulate; the only check is deduplication against the same address (`if (!toAccountsList.contains(...))`), so the list length is bounded only by how many distinct addresses/transactions the attacker is willing to pay for. [3](#0-2) 
- A test in the codebase confirms this is trivially exploitable at scale (100+ entries added with no rejection), demonstrating the unbounded nature of the list. [4](#0-3) 
- The query path `DelegatedResourceAccountIndexStore.getWithPrefix()` performs a full `prefixQuery` over all entries for the target address and then sorts the entire result set in memory for both the "to" and "from" directions, with no pagination or size limit. [5](#0-4) 
- This is reachable through `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`, which are exposed via unauthenticated HTTP servlets (and equivalent gRPC/JSON-RPC handlers) that any external API client can call without any rate/size limiting beyond a generic rate limiter. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who inflates the delegation index of a target address (or their own address, to be queried by others, e.g., exchanges/wallets that look up delegation state) forces every subsequent query for that address to perform an unbounded LevelDB/RocksDB prefix scan plus an in-memory sort over the full, attacker-controlled-size result set. At sufficient scale this degrades or blocks the servicing thread for that API, and because these HTTP/RPC servlets typically run on a shared thread pool, sustained abuse can degrade the node's ability to serve this and other API requests — matching the accepted impact category of "an API the node can no longer serve." Unlike the original Paladin report (which blocked swaps for all users of a pool), the blast radius here is scoped to queries against the targeted address(es), so the severity is Medium rather than Critical/High.

### Likelihood Explanation
Likelihood is Medium: exploitation requires no special privileges — only ordinary `FreezeBalanceV2Contract`/`DelegateResourceContract` transactions from many funded accounts, each of which is cheap (small frozen balance suffices). No admin flag, hard-fork gate, or governance proposal blocks this path in the current, active `DelegateResourceContract`/V2 delegation flow. The cost to the attacker (transaction fees/bandwidth for many small delegations) is the main limiting factor, similar to the original report's requirement to pay for LP-token deployments.

### Recommendation
Enforce a maximum number of distinct delegation relationships (`toAccounts`/`fromAccounts` entries) per address in `DelegateResourceActuator.validate()`/`FreezeBalanceActuator.validate()`, rejecting new delegations once the cap is reached. Additionally, add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix()` (and the corresponding Wallet/HTTP/RPC methods) so a single query cannot force an unbounded scan and sort.

### Proof of Concept
1. Attacker funds N throwaway accounts, each freezing a minimal amount of TRX for bandwidth/energy via `FreezeBalanceV2Contract`.
2. From each throwaway account, attacker broadcasts a `DelegateResourceContract` delegating a minimal balance to a single victim receiver address (or, symmetrically, delegates from a single owner account to N distinct throwaway receiver addresses to inflate the owner's `toAccounts` list).
3. Repeat until the victim's/owner's delegation index (`toAccounts`/`fromAccounts`, or the V2 prefixed entries) contains a very large number of entries — no on-chain check prevents this, as shown by `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth` accepting 100 entries with no cap.
4. Any subsequent call to `GetDelegatedResourceAccountIndexServlet`/`GetDelegatedResourceAccountIndexV2Servlet` (or the gRPC/JSON-RPC equivalent) for the victim address triggers `DelegatedResourceAccountIndexStore.getWithPrefix()`, which performs a full prefix scan and sort over the inflated entry set, consuming disproportionate CPU/time on the serving node for that request.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndexV2(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule = chainBaseManager
        .getDelegatedResourceAccountIndexStore().getV2Index(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
