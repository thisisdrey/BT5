### Title
Quadratic CPU rescan of the accumulated preamble buffer in `StacksHttp::read_preamble` allows slow-drip RPC connections to cause bounded but wasteful O(n²) CPU work - (File: stackslib/src/net/httpcore.rs)

### Summary
`StacksHttp::read_preamble` is invoked by `ConnectionInbox::consume_preamble` with the *cumulative* preamble buffer (`self.buf` in `connection.rs`), which grows by however many bytes the peer trickles in on each socket read. Each invocation re-runs the `for i in 0..=buf.len()` CRLFCRLF search over the *entire* buffer from index 0, even though earlier bytes were already scanned in previous calls. An attacker who sends the preamble one byte (or a few bytes) at a time without ever completing `\r\n\r\n` forces this full rescan on every call, producing O(n²) total comparisons for n bytes sent, bounded only by `HTTP_PREAMBLE_MAX_ENCODED_SIZE`.

### Finding Description
`consume_preamble` in `stackslib/src/net/connection.rs` calls `buffer_preamble_bytes` to append newly-arrived bytes into `ConnectionInbox.buf` (an accumulator that is never truncated until a full preamble is parsed), then calls `protocol.read_preamble(&self.buf)` [1](#0-0) . Because `self.buf` holds all bytes received so far for this preamble (up to the size hint), `read_preamble` is handed a buffer that grows across calls.

Inside `StacksHttp::read_preamble`, when `self.body_start` is still `None`, the loop `for i in 0..=buf.len() { ... self.body_start_search_window(i, buf) ... }` scans the *whole* `buf` slice from the start on every call, looking for `\r\n\r\n` [2](#0-1) . The struct fields `num_preamble_bytes` and `last_four_preamble_bytes` are updated as bookkeeping for offset computation (`self.body_start = Some(self.num_preamble_bytes + i)`), but they are never used to *skip* re-scanning bytes already scanned in prior calls — they only affect the reported offset, not the scan range. Consequently, if a remote peer trickles the HTTP preamble in tiny increments (e.g., 1 byte per TCP segment/read event) and never completes the header terminator, each of the up-to-`HTTP_PREAMBLE_MAX_ENCODED_SIZE` calls to `read_preamble` rescans a buffer of increasing length, yielding a sum of 1+2+...+N ≈ N²/2 byte comparisons for N total bytes sent, instead of the intended O(N) linear scan.

This is reachable purely via the RPC HTTP port with no authentication and no special peer/config state — any TCP client that can complete a connection and trickle bytes below `HTTP_PREAMBLE_MAX_ENCODED_SIZE` can trigger it repeatedly (open the connection, drip a byte, wait, drip another, etc., resetting/reopening as desired).

### Impact Explanation
Each triggered read-preamble cycle wastes CPU proportional to the square of the bytes sent (bounded by `HTTP_PREAMBLE_MAX_ENCODED_SIZE`), rather than linear time, on the node's connection-processing/read loop for RPC connections. This matches the "bounded compute DoS on a read endpoint" category (High): no crash, no state corruption, and the total work per connection is capped by the preamble size limit, but the algorithm is needlessly quadratic instead of linear within that bound, and it is trivially repeatable by reopening/continuing slow-drip connections.

### Likelihood Explanation
- No privileges, secrets, or peer relationship required — any remote TCP client can open an RPC connection.
- The attacker only needs to control the pacing/segmentation of bytes sent (e.g., writing 1 byte at a time with small delays), which is straightforward with standard sockets.
- The bug is deterministic and reproducible on every slow-drip connection that never completes `\r\n\r\n` within `HTTP_PREAMBLE_MAX_ENCODED_SIZE` bytes.
- Impact per single connection is bounded by the preamble size cap, so this is not an unbounded/critical DoS, but the wasted CPU work is quadratic rather than linear, and cost to the attacker is minimal (a handful of small packets) versus the node's repeated full-buffer rescans.

### Recommendation
Change `read_preamble` to only scan the newly-appended bytes (using `self.last_four_preamble_bytes` as the carried-over window context) rather than re-scanning the full cumulative buffer on every call, restoring intended O(1)-per-byte / O(n) total behavior. Concretely, the search loop should operate over the incremental slice appended since the last call, using `last_four_preamble_bytes` only to bridge the boundary, rather than iterating `0..=buf.len()` against the whole accumulated buffer each time.

### Proof of Concept
Add a test in `stackslib/src/net/tests/httpcore.rs` that:
1. Constructs a `StacksHttp` instance.
2. Feeds a valid-looking HTTP request preamble byte-by-byte (never sending the final `\r\n\r\n` until the very last call, and staying under `HTTP_PREAMBLE_MAX_ENCODED_SIZE`), calling `read_preamble` after each single-byte append (mirroring how `consume_preamble` grows `self.buf` and calls `protocol.read_preamble(&self.buf)`).
3. Instruments/count the total number of byte comparisons performed inside `body_start_search_window` (e.g., via a counter, or by timing), asserting the total work scales linearly (O(n)) rather than quadratically (O(n²)) in the number of bytes fed — i.e., assert total comparisons ≈ C·n rather than C·n²/2 for n approaching `HTTP_PREAMBLE_MAX_ENCODED_SIZE - 1`.

        if self.body_start.is_none() {

                let window = self.body_start_search_window(i, buf);
