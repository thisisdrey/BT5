### Title
Missing Handshake Identity Check Lets a Neighbor-of-Neighbor Poison the Peer Database with a Forged Identity - (File: `stackslib/src/net/neighbors/walk.rs`)

### Summary
When a Stacks node performs neighbor-walk discovery, it asks a peer (`cur_neighbor`) for its neighbors, then handshakes directly with each reported `NeighborAddress` to confirm it is real and to learn its long-term identity (public key). The reply path used for this step, `handle_neighbor_handshake_accept`, persists the responding peer's self-reported `HandshakeData` into the local `PeerDB`/frontier **without verifying that the reported public key matches the public-key hash the walk was expecting for that `NeighborAddress`**. A sibling code path in the same file (`pingback_handshakes_try_finish`) performs exactly this check via `check_handshake_pubkey_hash` before storing a neighbor, showing that the check is a deliberate anti-spoofing control that was simply omitted on this path.

### Finding Description
The relevant call chain:

- `getneighbors_neighbors_begin`/`neighbor_handshakes_try_finish` connect to and handshake with each `NeighborAddress` obtained from `cur_neighbor`'s `Neighbors` reply. [1](#0-0) 

- On receiving a `HandshakeAccept`/`StackerDBHandshakeAccept`, the code immediately calls `self.handle_neighbor_handshake_accept(network, naddr, &message.preamble, data, db_data)` — **no identity check is performed between `naddr` (the address/pubkey-hash we expected to be talking to) and `data.handshake` (the identity the remote peer claims in its payload)**. [2](#0-1) 

- `handle_neighbor_handshake_accept` takes `data.handshake` at face value and persists it via `add_or_schedule_replace_neighbor`, inserting the (attacker-controlled) neighbor record into both the in-memory frontier and the on-disk `PeerDB`: [3](#0-2) 

- `add_or_schedule_replace_neighbor` calls `Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)` and then `.save()`/`.save_update()`, writing the claimed address/public key straight into the peer database: [4](#0-3) 

Contrast this with the **other** handshake-completion path in the same struct, `pingback_handshakes_try_finish`, which explicitly guards the same call with `check_handshake_pubkey_hash(&peer_nk, data, &naddr)` before calling `add_or_schedule_replace_neighbor`, and skips storage if the check fails: [5](#0-4) [6](#0-5) 

The equality that should hold — "the identity we dialed/expected (`naddr.public_key_hash`) equals the identity the peer claims in its handshake payload (`data.handshake.node_public_key`)" — is enforced on the pingback path but not on the neighbor-of-neighbor handshake path. This lets any peer that is a "neighbor of a neighbor" (i.e., any remote node reachable via the normal crawl, requiring no privileges) return a `HandshakeAccept`/`StackerDBHandshakeAccept` whose `HandshakeData` claims an arbitrary IP/port/public key — that forged tuple is stored as a legitimate peer in the crawler's frontier and `PeerDB`.

### Impact Explanation
This breaks "authenticated vs. stored" for peer-discovery data: unauthenticated/unverified identity claims are written into persistent peer-selection state (`PeerDB`) and the in-memory `new_frontier`/`frontier`, which subsequently drive future connection attempts, neighbor advertisement (`GetNeighbors` replies), and StackerDB replica selection (`StackerDBHandshakeAccept` also carries `db_data.smart_contracts`). This is a form of forged-gossip propagation: a single malicious node reachable via the walk can poison a victim's neighbor table with fabricated `(addr, port, pubkey)` triples, potentially directing the victim (and, transitively, anyone who later crawls the victim and receives these entries via `GetNeighbors`) into connecting to attacker-chosen or victim-targeted IP:port pairs, wasting connection slots/bandwidth on invented peers, and network-wide spreading of forged peer records — a High/Critical-class impact per the given classification ("network-wide propagation of forged data").

### Likelihood Explanation
The trigger requires nothing more than being reachable during a normal walk (being reported as a neighbor by some other neighbor, or otherwise being dialed as a `naddr`) and responding to the resulting handshake with a crafted `HandshakeAcceptData`. No node secret, signer key, or admin role is required; this is a standard, unauthenticated remote-response path in the neighbor-walk protocol, so the likelihood of triggering is high for any attacker who can get a node to attempt to handshake with them (e.g., by having a colluding/attacker-controlled peer report the attacker's own address in a `Neighbors` reply, or by directly answering discovery attempts).

### Recommendation
Add the same `check_handshake_pubkey_hash(&naddr's expected key, data, &naddr)` (or equivalent addr/pubkey-hash consistency check) inside `handle_neighbor_handshake_accept`, mirroring `pingback_handshakes_try_finish`, before calling `add_or_schedule_replace_neighbor`. Reject/drop handshake replies whose claimed identity does not match the `NeighborAddress` that was dialed.

### Proof of Concept
1. Attacker operates node `M`. Attacker also controls (or colludes with) node `N`, which is a legitimate first-hop neighbor of the victim `V`.
2. When `V` performs a neighbor-walk step and asks `N` for its neighbors (`GetNeighbors`), `N` reports `M`'s `NeighborAddress` (real IP:port with `M`'s real `public_key_hash`) as one of its neighbors — this is the normal, sanctioned path (`getneighbors_try_finish` → `getneighbors_neighbors_begin`).
3. `V` connects to and handshakes with `naddr = M`. `M` instead sends back a `HandshakeAccept` whose `HandshakeData.node_public_key`/`addrbytes`/`port` correspond to an arbitrary forged identity `F` (e.g., a victim's own address, or a nonexistent one), which does not match `naddr.public_key_hash`.
4. On the `getneighbors_neighbors_begin`/`neighbor_handshakes_try_finish` path, `V` calls `handle_neighbor_handshake_accept` directly with this data — since no `check_handshake_pubkey_hash` call exists here (unlike `pingback_handshakes_try_finish`), `V` stores forged identity `F` into its `PeerDB` and frontier via `add_or_schedule_replace_neighbor` / `Neighbor::load_and_update`/`save`.
5. `V` may subsequently advertise `F` to other crawlers via `handle_getneighbors`, propagating the forged record further.

Note: I was unable to execute this end-to-end in a live environment; the finding is based on static code-path analysis contrasting the two structurally identical handshake-completion routines in the same file, one of which enforces the identity check and the other of which does not.

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }

    fn add_or_schedule_replace_neighbor(
        &self,
        network: &mut PeerNetwork,
        preamble: &Preamble,
        handshake: &HandshakeData,
        db_data: Option<&StackerDBHandshakeData>,
        replacements: &mut NeighborReplacements,
    ) -> Result<(bool, Neighbor), net_error> {
        let local_peer_str = format!("{:?}", network.get_local_peer());
        let tx = network.peerdb_tx_begin()?;
        let (mut neighbor_from_handshake, was_present) =
            Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)?;

        if was_present {
            test_debug!(
                "{}: already know about neighbor {:?}",
                &local_peer_str,
                &neighbor_from_handshake.addr
            );
            neighbor_from_handshake
                .save_update(&tx, db_data.map(|x| x.smart_contracts.as_slice()))?;
            tx.commit()?;

            // seen this neighbor before
            return Ok((false, neighbor_from_handshake));
        }

        debug!(
            "{}: new neighbor {:?}",
            &local_peer_str, &neighbor_from_handshake.addr
        );

        // didn't know about this neighbor yet. Try to add it.
        let added =
            neighbor_from_handshake.save(&tx, db_data.map(|x| x.smart_contracts.as_slice()))?;

        if added {
            // neighbor was new, and we had space to add it.
            tx.commit()?;
            return Ok((true, neighbor_from_handshake));
        }

        // neighbor was new, but we don't have space to insert it.
        // find and record a neighbor it would replace.
        let replaced_neighbor_slot_opt =
            Self::find_replaced_neighbor_slot(&tx, &neighbor_from_handshake.addr)?;
        if let Some(slot) = replaced_neighbor_slot_opt {
            replacements.add_neighbor(
                NeighborAddress::from_neighbor(&neighbor_from_handshake),
                neighbor_from_handshake.clone(),
                slot,
            );
        }

        tx.commit()?;

        // neighbor was new
        Ok((true, neighbor_from_handshake))
    }
