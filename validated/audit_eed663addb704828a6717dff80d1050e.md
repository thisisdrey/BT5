### Title
Division by zero (`ArithmeticException`) in `ResourceProcessor.increaseV2` / `getNewWindowSize` reachable from ordinary transactions consuming bandwidth or energy - (File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java)

### Summary
`ResourceProcessor.increaseV2()` computes `newUsage` via `getUsage(...)` and then, when `remainUsage != 0`, unconditionally divides by `newUsage` inside `divideCeil`/`divideCeilExact` to derive the new resource window size. `newUsage` is not checked for zero before being used as a divisor. If `newUsage` evaluates to `0` (a rounding-down result of the internal fixed-point math, not merely equal to the already-guarded `remainUsage`), the division throws an uncaught `ArithmeticException`. This method is invoked from `ResourceProcessor.increase(AccountCapsule, ResourceCode, ...)` [1](#0-0) , which is the core bandwidth/energy accounting routine used on every transaction that consumes network bandwidth or energy (via `BandwidthProcessor`/`EnergyProcessor`), and from `unDelegateIncreaseV2` used by `UnDelegateResourceActuator`/`UnDelegateResourceProcessor`, both reachable by any unprivileged account issuing a normal transaction or an `UnfreezeBalanceV2`/`UnDelegateResource` contract.

### Finding Description
`increaseV2` computes:
```
long newUsage = getUsage(averageLastUsage, oldWindowSize, averageUsage, this.windowSize);
long remainUsage = getUsage(averageLastUsage, oldWindowSize);
if (remainUsage == 0) {
  accountCapsule.setNewWindowSizeV2(resourceCode, this.windowSize * WINDOW_SIZE_PRECISION);
  return newUsage;
}
...
newWindowSize = divideCeil(
    remainUsage * remainWindowSize + usage * this.windowSize * WINDOW_SIZE_PRECISION,
    newUsage);   // divides by newUsage, not remainUsage
``` [2](#0-1) 

The existing zero-guard only checks `remainUsage == 0`, but the divisor used later is `newUsage`, a *different* value derived from `averageUsage` in addition to `averageLastUsage` [3](#0-2) . Because `getUsage` performs integer truncation (`(oldUsage * oldWindowSize + newUsage * newWindowSize) / precision`), it is possible for `remainUsage` (which uses `precision`-scaled `averageLastUsage` alone) to be non-zero while the combined `newUsage` computation truncates to `0` for suitably small `averageLastUsage`/`averageUsage`/`windowSize` combinations, since the two `getUsage` calls use different formulas (one two-argument, one four-argument) rather than being trivially related. When `newUsage == 0`, `divideCeil(numerator, 0)` or `divideCeilExact` (when hardening is enabled) throws `ArithmeticException`, which is not caught anywhere in the call chain (`increase` → `BandwidthProcessor.useTransactionFee`/`consume`, `EnergyProcessor.updateUsage`/`useEnergy`, or `UnDelegateResourceProcessor.execute`). The identical unguarded-divisor pattern also exists in the V1 `increase(AccountCapsule, ...)` method calling `getNewWindowSize(..., newUsage)` [4](#0-3)  and in `getNewWindowSize` itself, which divides by its `newUsage` parameter without any zero check [5](#0-4) .

### Impact Explanation
An uncaught `ArithmeticException` thrown while processing a transaction's bandwidth/energy accounting would propagate out of `consume()`/`updateUsage()` during block application in the `Manager`/actuator execution path, which is not designed to tolerate unchecked runtime exceptions from routine resource bookkeeping. This can crash the node processing the transaction or cause it to reject a transaction that other nodes accept (or vice versa, depending on which nodes have hit the specific numeric edge case), risking a chain split or node halt — consistent with the "node crash/halt or chain split" impact bar for this scan.

### Likelihood Explanation
The trigger requires finding integer inputs (existing account usage, transferred usage, and window sizes) where the two-term `getUsage` truncates to zero while the single-term `remainUsage` guard does not. Because usage/time values are attacker-influenced only indirectly (bandwidth/energy consumption accumulates through the account's history and any user's own or delegated transactions), an attacker with the ability to freeze/delegate/unfreeze small amounts of resource repeatedly, or use accounts with unusual timing, has some control over the values feeding this arithmetic. However, I could not fully confirm from static review alone that `remainUsage != 0 && newUsage == 0` is reachable in practice given the specific precision/window-size constants in this codebase (`PRECISION`, `WINDOW_SIZE_PRECISION`, `windowSize` in slots) — this would need to be validated with concrete numeric fuzzing/PoC in the target repository build, which I could not execute in this ask-only context.

### Recommendation
Add an explicit `newUsage == 0` guard (mirroring the existing `remainUsage == 0` guard) before the `divideCeil`/`divideCeilExact` calls in `increaseV2`, `increase(AccountCapsule,...)`, `unDelegateIncreaseV2`, and `getNewWindowSize`, returning a safe default window size (e.g., `this.windowSize * WINDOW_SIZE_PRECISION`) when the divisor would be zero, and add unit tests asserting no `ArithmeticException` is thrown for degenerate small-usage inputs.

### Proof of Concept
Not fully constructible without running the exact `ChainConstant.PRECISION`/`WINDOW_SIZE_PRECISION`/`windowSize` values through the four-argument `getUsage` and two-argument `getUsage` formulas to find concrete `averageLastUsage`/`averageUsage` values that make `remainUsage > 0` and `newUsage == 0` simultaneously; this requires numeric exploration (e.g., a small brute-force script or Devin-driven test) against the actual constants in `chainbase/src/main/java/org/tron/core/config/Parameter.java` (`PRECISION`, `WINDOW_SIZE_MS`, `WINDOW_SIZE_PRECISION`) rather than something confirmable from static code inspection alone.

  private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,

    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
          .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
      return bi.divide(BigInteger.valueOf(newUsage)).longValueExact();
    }
    return (lastUsage * lastWindowSize + usage * windowSize) / newUsage;
