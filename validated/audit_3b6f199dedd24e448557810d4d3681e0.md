### Title
Improper Authorization: `ValidateMultiSign` precompile omits `operations` bitmask enforcement, letting any Active permission be used as an unrestricted signer-weight oracle - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `security-role-ref`-style bug class in the Tomcat advisory is: a permission/role artifact that is defined for one specific, scoped purpose gets reused in a different code path without the accompanying scope restriction, causing broader authorization than intended. In java-tron, `Permission.operations` is the scope restriction attached to an `Active` permission — it restricts that key-set/threshold combination to only certain `ContractType`s. Every transaction-broadcast path enforces this restriction, but the `ValidateMultiSign` TVM precompile, which any deployed contract can invoke to authenticate off-chain signatures against an account's on-chain permission, does not.

### Finding Description
`ValidateMultiSign.execute()` at [1](#0-0)  takes an attacker-supplied `address` and `permissionId`, fetches `Permission permission = account.getPermissionById(permissionId)`, and directly computes signer weight via `TransactionCapsule.getWeight(permission, recoveredAddr)` against `permission.getThreshold()` — it never checks `permission.getOperations()` against any contract-type context, unlike the transaction-signing/approval paths.

Compare with the transaction-broadcast/approval paths, which all gate non-owner permissions by their `operations` bitmask:
- `TransactionCapsule.checkPermission` calls `checkPermissionOperations(permission, contract)` before accepting a signature for a given `Contract.ContractType`: [2](#0-1) 
- `TransactionUtil.getTransactionSignWeight` performs the same check: [3](#0-2) 
- `Wallet.getTransactionApprovedList` performs the same check via `WalletUtil.checkPermissionOperations`: [4](#0-3) 

The `operations` bitmask is defined and validated by `AccountPermissionUpdateActuator.checkPermission`, explicitly to scope an Active permission's authority to specific `ContractType`s (e.g., a "low-risk" Active permission with keys authorized only for `TransferAssetContract`, not `AccountPermissionUpdateContract` or `WitnessCreateContract`): [5](#0-4) 

Because `ValidateMultiSign` treats every `Active` permission (any `permissionId` 2-9) as an unrestricted "is this address/threshold combination authorized" oracle without consulting `operations`, a smart contract can use it to validate signatures collected for a narrowly-scoped Active permission (e.g. one restricted to asset transfers) and treat that validation as authorization for arbitrary in-contract logic that has nothing to do with the permission's intended scope — mirroring the Tomcat flaw where a role-ref intended for a narrow `isUserInRole()` check was reused as a general Realm-level role alias.

### Impact Explanation
Any TRC-20/TRC-721 style contract, DAO, multisig wallet, or exchange contract built on top of `ValidateMultiSign` (documented, intended use per the TIP that introduced this precompile) to gate on-chain actions by off-chain-collected signatures cannot rely on the permission's `operations` scoping to limit what the collected signatures may authorize. An account owner who created a narrowly-scoped Active permission (believing it can only ever authorize specific TRON-native contract types) has no protection against that permission's key-set/threshold being reused by a third-party contract to authorize unrelated value-moving operations (e.g., withdrawal from a vault contract), because the precompile silently drops the scope check that the rest of the system enforces uniformly. This can lead to unauthorized fund movement in any dApp that trusted the permission-scoping guarantee.

### Likelihood Explanation
`ValidateMultiSign` is reachable by any deployed contract and any unprivileged contract caller — no special privilege is required, only that a target account has created an Active permission via `AccountPermissionUpdateActuator` (a normal, common multisig-setup transaction) and that some contract in the ecosystem uses `ValidateMultiSign` to check signatures against that permission for a purpose outside the permission's configured `operations` scope. This is directly triggerable by a single TVM call, matching the "unprivileged transaction broadcaster / contract deployer" reachability bar.

### Recommendation
Either (a) document explicitly that `ValidateMultiSign` performs pure signature-weight/threshold validation and deliberately ignores `operations` scoping, so integrators do not rely on the bitmask when using it outside of transaction-broadcast contexts, or (b) require callers to pass the intended `ContractType`/context and enforce `checkPermissionOperations`-equivalent scoping inside the precompile when the referenced permission is of type `Active`, mirroring `TransactionCapsule.checkPermission`.

### Proof of Concept
1. Account `A` creates an Active permission (id=2) with `operations` scoped only to `TransferAssetContract`, via `AccountPermissionUpdateContract`.
2. A third-party contract `C` (e.g., a vault) is written to authorize withdrawals by calling `validatemultisign(A, 2, hash, sigs)` and trusting a `true` result as sufficient authorization for withdrawal, on the assumption that permission id=2's scoping protects against misuse.
3. Any holder of the keys in permission id=2 (who was only meant to be able to co-sign asset transfers) can produce `sigs` over an arbitrary `hash`/context chosen by contract `C`'s caller and get `ValidateMultiSign` to return `true`, since `operations` is never consulted at [6](#0-5) , allowing withdrawal from `C` despite the permission never being intended to authorize anything beyond `TransferAssetContract`.
