### Title
Reference backend detection trusts the repository's own `refstorage` config value without validating it against the actual on-disk reference layout, enabling MVCC-binary confusion / cross-backend corruption - ([File: internal/git/gitcmd/reference_backend.go])

### Summary
`DetectReferenceBackend` reads the `extensions.refstorage` value straight out of a repository's `config` file and uses it, unvalidated, to decide which bundled Git binary (`files`, `reftable`, or the divergent `mvcc` fork) must serve that repository. The "type" of the repository (its reference-storage format) is never checked against the repository's actual on-disk structure before that type is trusted to select the binary — directly analogous to the Astaria finding where a component's declared type is trusted without validating it actually conforms to that type.

### Finding Description
`DetectReferenceBackend` (`internal/git/gitcmd/reference_backend.go:39-81`) explicitly documents that it "doesn't validate the configuration": it scans the `[extensions]` section for `refstorage` and maps the raw string via `git.ReferenceBackendByName` [1](#0-0) . The only check performed is that the *name* is one of the three known strings; there is no verification that the repository's on-disk layout (`refs/` directory vs `reftable/` directory vs MVCC manifest structures) actually matches the declared value.

This detected backend is then placed into the request context via `ContextWithReferenceBackend` and used by `ExecCommandFactory.newCommand` and the `BundledGitEnvironmentConstructor.isEnabled` closure to select the actual Git binary that will operate on the repository [2](#0-1) . The comment on the `BundledGitEnvironmentConstructor.ReferenceBackend` field states the strict invariant this mechanism is supposed to guarantee: "This environment is used if and only if the repository uses the named backend" and "it must never be used for any other repository" [3](#0-2) .

Crucially, `isMvccReferenceBackend` in the gRPC middleware calls this same unvalidated detector on every incoming RPC to decide whether to enable the MVCC caching layer for a repository [4](#0-3) . Since `config` is an ordinary file inside the repository's git directory, its content is reachable through normal repository-management operations (e.g. replication/fork flows that copy configuration, or any path that writes to the repository's `config` file) without any independent verification that the repository's `refs`/`reftable` state matches the declared `refstorage` value.

If the declared backend and the actual on-disk state diverge — e.g., a repository whose config claims `files` but whose refs are laid out as `reftable`, or vice versa, or a non-MVCC repository whose config is manipulated to claim `mvcc` — Gitaly will select the wrong bundled Git binary to operate on it. Because the MVCC binary "diverges from upstream Git" and only that binary is capable of correctly reading/writing MVCC-formatted refs, running the mismatched binary against a repository has a strong likelihood of producing reference corruption, unreadable ref state, or a crash of the invoked Git process, since none of the three binaries are designed to gracefully handle a foreign backend's on-disk format.

### Impact Explanation
A repository whose declared `refstorage` does not match its actual layout causes Gitaly to invoke the wrong specialized Git binary against it. This can corrupt reference data (loss of user data), cause Git subprocess crashes (denial of service against that repository/RPC handler), or place the repository into an unreadable/inconsistent state that is difficult to recover from — mirroring the "loss of user funds / re-deployment expense" severity class of the original finding, translated to "loss of repository data / need for repository restoration."

### Likelihood Explanation
The `config` file is a normal part of a bare repository and is reachable via internal repository management flows (fork/replicate) that copy or write repository configuration, and `DetectReferenceBackend` is invoked on effectively every RPC via the MVCC middleware interceptor. The mismatch does not require exploiting a memory-safety bug — it only requires the on-disk ref layout to diverge from the declared `refstorage` value, which can happen through partial/failed migrations, incomplete replication, or other legitimate-looking but crafted repository states. However, I could not fully verify (given the available index) whether an ordinary, unprivileged user can single-handedly write to a repository's `config` file through a public-facing RPC (as opposed to only internal Gitaly-to-Gitaly flows like `ReplicateRepository`), so likelihood should be treated as moderate rather than confirmed high.

### Recommendation
Before trusting a repository's declared `refstorage`/reference-backend value to select the Git binary, verify that the on-disk structure is consistent with the declared backend (e.g., presence/absence of `refs/heads`, `reftable/tables.list`, or MVCC manifest markers as appropriate) and reject or quarantine the RPC with a clear error if it is not. This detection and validation should happen at repository-boundary transition points (post-replication, post-fork, post-repository-write) rather than only being consumed lazily and implicitly by the command factory on every git invocation.

### Proof of Concept
Not independently reproduced in this analysis (no execution environment available). The theoretical PoC: manually edit `objects/../config`'s `[extensions] refstorage = reftable` value inside a repository that is actually a `files`-backend repository (or vice versa, or set `refstorage = mvcc` for a non-MVCC repo), as demonstrated by the existing unit test harness which shows `DetectReferenceBackend` accepting arbitrary declared values without checking the repository's real layout [5](#0-4) ; then trigger any git operation against that repository and observe the command factory select the Git binary matching the declared (not actual) backend [6](#0-5) .

// DetectReferenceBackend detects the reference backend used by the repository.
// It plucks out the first refstorage configuration value from the repository's configuration
// file and doesn't validate the configuration.
//
// Note: It is recommended to use localrepo.ReferenceBackend since that value is
// cached for a given repository.
func DetectReferenceBackend(ctx context.Context, repoPath string) (_ git.ReferenceBackend, returnedErr error) {
	configFile, err := os.Open(filepath.Join(repoPath, "config"))
	if err != nil {
		return git.ReferenceBackend{}, fmt.Errorf("open: %w", err)
	}
	defer func() {
		if err := configFile.Close(); err != nil {
			returnedErr = errors.Join(returnedErr, fmt.Errorf("close: %w", err))
		}
	}()

	// We default to the files backend and override it with the first refstorage value found in
	// the configuration. Only the reference backend is relevant here, as it alone determines
	// which bundled Git binary is able to read the repository. We deliberately do not inspect the
	// object storage extension: a repository using the MVCC reference backend must be served by
	// the MVCC binary regardless of how its objects are stored.
	refStorage := git.ReferenceBackendFiles.Name

func (m *CacheInterceptor) isMvccReferenceBackend(ctx context.Context, repo *gitalypb.Repository) bool {
	repoPath, err := m.locator.GetRepoPath(ctx, repo)
	if err != nil {
		return false
	}
	backend, err := gitcmd.DetectReferenceBackend(ctx, repoPath)
	if err != nil {
		return false
	}
	return git.ReferenceBackendMVCC.Name == backend.Name
}
