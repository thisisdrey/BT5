## Verdict: Vulnerability confirmed (extends beyond what the question described)

### Title
Unauthenticated eviction of another peer's StackerDB registrations via unvalidated self-reported address in neighbor-of-neighbor handshake responses - (`stackslib/src/net/neighbors/walk.rs`, `stackslib/src/net/neighbors/db.rs`, `stackslib/src/net/db.rs`)

### Summary
`PeerDB::update_peer` (db.rs:1286-1334) correctly implements "drop StackerDB registrations only when the slot's authenticated public key changes," but the *slot identity* it keys off — `(network_id, addrbytes, port)` — is populated from the **handshake payload's self-declared address** (`handshake_data.addrbytes/port`) rather than any verified network fact. In the main neighbor-crawl path (`handle_neighbor_handshake_accept` → `add_or_schedule_replace_neighbor`), no code checks that this self-declared address matches the address that was actually dialed, nor that the responder's key matches an expected public-key hash. A remote peer that is legitimately discoverable as someone's neighbor can therefore answer a handshake with a spoofed `addrbytes/port` belonging to a victim peer and its own (different) key, causing `update_peer` to detect a "re-key" and call `PeerDB::drop_stacker_dbs` for the victim's slot.

### Finding Description
`PeerDB::try_insert_peer` (db.rs:1452-1488) and `PeerDB::update_peer` (db.rs:1286-1334) operate purely on the `Neighbor.addr = (network_id, addrbytes, port)` fields supplied in the `Neighbor` struct passed to them; when `old_peer.public_key != neighbor.public_key` for an existing slot, `PeerDB::drop_stacker_dbs(tx, slot)` (db.rs:1329) is invoked unconditionally [1](#0-0) .

The `Neighbor` object fed into this path during a routine neighbor walk comes from `NeighborKey::from_handshake`, which is built entirely from the **handshake payload's self-reported** `addrbytes`/`port` [2](#0-1) , and `Neighbor::load_and_update` uses this claimed address as the lookup/storage key without any cross-check against the actually-contacted socket [3](#0-2) .

During a normal walk, when the crawling node asks `cur_neighbor` for its neighbors and then handshakes with each reported `NeighborAddress`, replies are processed by `handle_neighbor_handshake_accept`, which calls `add_or_schedule_replace_neighbor` directly with **no verification that `data.handshake.addrbytes/port` matches the dialed `naddr`, and no public-key-hash check**: [4](#0-3) 

`add_or_schedule_replace_neighbor` then loads/updates the peer keyed by the self-declared address and calls `save_update` (→ `PeerDB::update_peer`) when the address is already occupied: [5](#0-4) 

By contrast, the developers clearly recognized this class of risk and added a `check_handshake_pubkey_hash` guard for the *pingback* flow (`pingback_handshakes_try_finish`) that verifies the reported key hash before saving [6](#0-5) [7](#0-6) . The same protection is applied for the first-hop `cur_neighbor` handshake in `handle_handshake_accept` (walk.rs), which rejects a mismatch between the self-reported address and the address of the neighbor actually dialed [8](#0-7) . **No equivalent check exists in `handle_neighbor_handshake_accept` / `add_or_schedule_replace_neighbor`**, which is the code path used for every "neighbor of neighbor" discovered during normal crawling.

**Exploit flow:** An attacker runs an ordinary Stacks peer (fully unprivileged, no secrets needed) and lets itself be discovered normally (e.g. it is a genuine neighbor of some third node, or it advertises itself). When any crawling node dials the attacker as part of resolving a `GetNeighbors` list, the attacker's `HandshakeAccept`/`StackerDBHandshakeAccept` reply declares `handshake_data.addrbytes/port` = victim's real `(network_id, addrbytes, port)`, signed under the attacker's own key (a valid signature, since `verify_secp256k1` only checks the message is signed by whatever key is embedded in the payload — it says nothing about whose address that is). Because the victim's slot is already occupied with a different (legitimate) public key, `update_peer` treats this as the address's owner re-keying and calls `PeerDB::drop_stacker_dbs` on the victim's slot, deleting the victim's real StackerDB contract registrations.

### Impact Explanation
This is an unauthenticated write (deletion) of another party's PeerDB/StackerDB state: `stackerdb_peers` rows for the victim's slot are removed, causing the victim to stop being treated as a replicant for its StackerDB contracts network-wide from the crawling node's perspective, and potentially triggering repeated churn/removal as other nodes independently crawl and hit the same attacker-controlled response. This matches the "unauthenticated/unauthorized write to state or StackerDB" Critical category. The attack is repeatable at will and does not require the victim's key, the node's RPC secret, or any privileged role — only that the attacker's own peer be discoverable and dialed during normal crawling, which is the P2P protocol's ordinary operation.

### Likelihood Explanation
Preconditions: the victim must already hold an occupied PeerDB slot for `(network_id, addrbytes, port)` (true for any known/contacted peer with StackerDB registrations); the attacker must be discoverable and get dialed as a "neighbor of a neighbor" during a walk (a routine, automatic occurrence — no special positioning required beyond running a normal reachable node). Attacker cost is minimal: run one Stacks peer, wait to be crawled, and answer with a crafted (but validly self-signed) handshake payload. Fully remote, requires no privileged access, and repeatable each crawl cycle.

### Recommendation
In `handle_neighbor_handshake_accept` (and generally anywhere `add_or_schedule_replace_neighbor`/`Neighbor::load_and_update` is invoked on a handshake response), validate that the self-reported `handshake_data.addrbytes/port` matches the address that was actually dialed (`naddr`), and/or verify the responder's public key hash against the expected `naddr.public_key_hash` before persisting — mirroring the existing `check_handshake_pubkey_hash` guard used in `pingback_handshakes_try_finish` and the address-match guard in `handle_handshake_accept`. Additionally, `PeerDB::update_peer`/`try_insert_peer` should not key exclusively on attacker-suppliable `(network_id, addrbytes, port)` without some proof of address ownership before allowing a re-key-triggered `drop_stacker_dbs`.

### Proof of Concept
Rust test plan (in `stackslib/src/net/neighbors/db.rs` or `walk.rs` test module):
1. Set up a `PeerDB` and insert a legitimate `Neighbor` "victim" at `(network_id, addrbytes=X, port=P)` with `insert_or_replace_stacker_dbs` registering contract IDs, via `PeerDB::try_insert_peer`.
2. Construct a `Preamble`/`HandshakeData` where `node_public_key` = attacker's key (different from victim's), but `handshake_data.addrbytes = X`, `handshake_data.port = P` (i.e., spoofing victim's slot identity), correctly signed by the attacker's own private key.
3. Call `NeighborWalkDB::add_or_schedule_replace_neighbor` (or the higher-level `handle_neighbor_handshake_accept`) with this crafted `handshake`/`preamble`, simulating that this reply came from a dialed `naddr` that is NOT `X:P`.
4. Assert `PeerDB::get_stacker_dbs_by_slot`/`static_get_peer_stacker_dbs` for the victim's slot now returns empty, confirming the victim's StackerDB registrations were dropped by an unrelated, unauthenticated third party.
