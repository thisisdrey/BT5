## Title
Uncontrolled regex complexity via `FindCommitsRequest.MessageRegex` passed unsanitized to `git log --grep` - ([File: internal/gitaly/service/commit/find_commits.go])

### Summary
`CommitService.FindCommits` accepts a client-supplied `message_regex` field and forwards it verbatim as the pattern argument to native `git log --grep=<pattern> --regexp-ignore-case`. No length limit, complexity check, or safe-regex validation is applied to the value before it is handed to Git's own regex engine, giving any caller of this RPC (an ordinary, unprivileged Gitaly client) the ability to submit a pathological pattern that causes catastrophic/polynomial backtracking inside the spawned `git log` process, tying up a Gitaly worker and its CPU for a controllable, attacker-chosen amount of time.

### Finding Description
The RPC handler builds the `git log` subcommand in `getLogCommandSubCmd`: [1](#0-0) 

The only validation performed on the incoming `FindCommitsRequest` is `validateFindCommitsRequest`, which checks the repository and the revision, but never inspects `MessageRegex` at all: [2](#0-1) 

Because `--grep` is passed straight through to Git's native pattern matcher (POSIX extended regex by default, or PCRE if configured), a caller can supply a pattern exhibiting well-known catastrophic-backtracking shapes (e.g. nested/overlapping quantifiers such as `(a+)+$`, `(a|a)*b`, or wide-repetition patterns similar to the reported `is-my-json-valid` `style` format issue) combined with a large/adversarial commit-message corpus (or even just very long input lines) to blow up matching time super-linearly. This is the same bug class as the reported `is-my-json-valid` ReDoS: an externally controlled regex/format string evaluated by a backtracking-capable engine against attacker-influenced input, with no bound on evaluation cost.

Unlike `internal/git/localrepo/config.go`'s `UnsetMatchingConfig`, which also forwards a caller-controlled `regex` string to `git config --get-regex`, `FindCommits` is reachable by any client with read access to a repository and requires no special repo-mutation privileges — it's a plain read/list RPC, making it a lower-barrier trigger.

### Impact Explanation
A malicious or careless caller can cause the `git log` child process spawned by Gitaly to consume excessive CPU while evaluating the crafted `--grep` pattern against the repository's commit history, for as long as the client keeps the stream open (bounded only by any surrounding RPC/command timeout). Because this ties up a Gitaly worker's CPU and the underlying `git log` subprocess, repeated concurrent invocations can degrade Gitaly's ability to serve other RPCs against the same repository or node, constituting a denial-of-service condition. This matches "DoS of a handler" from the validation criteria.

### Likelihood Explanation
Likelihood is high for any environment where `FindCommits` is exposed to semi-trusted or external callers (e.g., via GitLab's commit search / log APIs), since triggering it requires only a single gRPC call with a crafted `message_regex` value — no write access, no special permissions, and no additional preconditions beyond read access to a repository.

### Recommendation
- Bound the complexity/length of `MessageRegex` before forwarding it to Git (e.g., enforce a maximum pattern length, reject patterns with known pathological repetition-of-repetition constructs, or run pattern validation through a safe-regex checker).
- Alternatively/additionally, run the `git log --grep` invocation under a bounded CPU/wall-clock timeout independent of client-controlled context cancellation, so a single crafted pattern cannot monopolize a Gitaly worker indefinitely.
- Consider disallowing extended regex features (e.g., forcing `--fixed-strings` unless explicitly requested) or documenting/enforcing that `MessageRegex` must not contain nested quantifiers.

### Proof of Concept
1. Populate a repository with a moderately sized commit history where at least one commit message is long (e.g., thousands of repeated characters) or where many commit messages exist.
2. Call `FindCommits` with:
   ```
   FindCommitsRequest{
     Repository: repo,
     Revision: []byte("HEAD"),
     MessageRegex: "(a+)+$",   // or another catastrophic-backtracking pattern
     Limit: 9000,
   }
   ```
3. Observe that the spawned `git log --grep='(a+)+$' --regexp-ignore-case` process consumes disproportionate CPU time relative to input size, scaling super-linearly with the length of matched commit-message content, while the RPC handler performs no validation of the pattern per `validateFindCommitsRequest` and `getLogCommandSubCmd` at [2](#0-1)  and [1](#0-0) .

		return err

	}
