Audit Report

## Title
`Crowdloan::refund` permanently deadlocks all remaining contributor refunds if any single transfer errors mid-loop - ([File: polkadot/runtime/common/src/crowdloan/mod.rs])

## Summary
`pallet-crowdloan`'s `refund` extrinsic iterates over a child-trie of contributors and calls `CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;` inside the loop, propagating any single transfer failure via `?` out of the dispatchable. Because all `#[pallet::call]` dispatchables are automatically wrapped in `with_storage_layer`, an error causes a full rollback of every storage mutation performed in that call, including `contribution_kill` and `fund.raised` updates for contributors processed earlier in the same call, and since the child-trie iteration order is deterministic, this failure recurs identically on every retry, permanently blocking refunds for the poisoned contributor and everyone after them.

## Finding Description
The `refund` extrinsic is confirmed exactly as described: [1](#0-0) 

```rust
pub fn refund(origin: OriginFor<T>, #[pallet::compact] index: ParaId) -> DispatchResultWithPostInfo {
    ensure_signed(origin)?;
    ...
    for (who, (balance, _)) in contributions {
        if refund_count >= T::RemoveKeysLimit::get() { all_refunded = false; break; }
        CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;
        CurrencyOf::<T>::reactivate(balance);
        Self::contribution_kill(fund.fund_index, &who);
        fund.raised = fund.raised.saturating_sub(balance);
        refund_count += 1;
    }
    Funds::<T>::insert(index, &fund);
    ...
}
```

The `?` on `transfer` returns `Err`, and every `#[pallet::call]` dispatchable is auto-wrapped by the `#[pallet::call]` macro expansion in `with_storage_layer`, which commits on `Ok` and rolls back all storage changes on `Err`, confirmed at: [2](#0-1)  and the underlying transactional semantics at [3](#0-2) . This means a mid-loop transfer failure discards every `contribution_kill`/`fund.raised` update made earlier in that same call, and because `contribution_iterator` walks the child trie deterministically, the same contributor is hit at the same point on every subsequent call, making the failure permanent and irrecoverable via this dispatchable.

## Impact Explanation
This matches the Impact Gate's "permanent user-fund or bridge-state lock" category: an unprivileged, permissionless call (`refund`, callable by anyone per its doc comment) can be made to fail deterministically and permanently for an entire crowdloan fund, blocking refunds for every contributor at or after the poisoned entry in iteration order, and preventing the fund from reaching a zero-`raised` state required for `dissolve`.

## Likelihood Explanation
The trigger condition requires a contributor account that cannot receive a re-created balance below `ExistentialDeposit` via `AllowDeath` transfer (e.g., a reaped account with a small refundable balance). No privileged actor, malicious relayer, or governance action is needed — any signed account can call `refund`, and the failure is deterministic and reproducible given the described account state, matching the required "unprivileged external attacker using public extrinsics" criterion.

## Recommendation
Do not propagate individual-transfer errors with `?` inside the refund loop. Capture the `Result` per contributor and on failure skip/continue (leaving that contributor's entry intact for a fallback pull-based `claim_refund`), emit a `RefundFailed` event, and proceed with the remaining contributors so a single bad account cannot block the batch.

## Proof of Concept
1. Create a crowdloan fund via `Crowdloan::create`.
2. Have several accounts contribute, including account `X`, then have `X` fully drain and lose its provider reference so it is reaped (zero providers/balance) before the crowdloan ends.
3. Let the crowdloan end (`ensure_crowdloan_ended` passes).
4. Call `Crowdloan::refund(origin, index)`.
5. Iteration reaches `X`; `transfer(&fund_account, &X, balance, AllowDeath)` fails with an existential-deposit error since re-creating `X` below `ExistentialDeposit` is disallowed.
6. The `?` propagates the error; `with_storage_layer` rolls back the entire call, including any `contribution_kill`/`fund.raised` updates for contributors processed earlier in this call.
7. Every subsequent `refund` call for this fund hits `X` at the same iteration position and fails identically, permanently blocking refunds for `X` and all contributors after it, and blocking `dissolve` (which requires `fund.raised.is_zero()`). [1](#0-0)

pub fn with_storage_layer<T, E, F>(f: F) -> Result<T, E>
where
	E: From<DispatchError>,
	F: FnOnce() -> Result<T, E>,
{
	with_transaction(|| {
		let r = f();
		if r.is_ok() {
			TransactionOutcome::Commit(r)
		} else {
			TransactionOutcome::Rollback(r)
		}
	})
}
