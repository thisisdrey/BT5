### Title
Non-monotonic Bancor-style exchange curve in `ExchangeProcessor` can be exploited to extract more tokens than a single equivalent trade, enabling TRC10 exchange pool drain — ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Rubicon report describes a short-leverage position whose size is not a smooth, monotonic function of the leverage input, because the borrow amount is computed by two different formula branches around the `1.0x` boundary. The `TRC10` exchange pricing curve in `ExchangeProcessor` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`) has an analogous defect: it converts the sell quantity to an intermediate "relay" (virtual supply) using floating-point `Math.pow` with tiny fractional exponents (`0.0005` and `2000.0`), and the two conversions are not algebraically inverse at `double` precision. This breaks the expected property of a bonding-curve AMM that a single larger trade should always yield an output at least as good as (and never worse than) executing the same total quantity as multiple smaller trades against the same pool.

### Finding Description
`ExchangeCapsule.transaction()` (chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:124-169) is reachable by any account through `ExchangeTransactionActuator` (actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:38-107), an unprivileged, broadcastable transaction type. When `hardenedCalc` is false (the default, non-hardened path), it uses `ExchangeProcessor`: [1](#0-0) 

`exchangeToSupply` computes `-supply * (1.0 - pow(1.0 + quant/newBalance, 0.0005))`, and `exchangeFromSupply` computes `balance * (pow(1.0 + supplyQuant/supply, 2000.0) - 1.0)`. Because `0.0005 * 2000 = 1`, these are meant to be exact inverses of a constant-product-style curve, but at IEEE-754 double precision the subtraction of two nearly-equal quantities (`1.0 - pow(...)`) suffers catastrophic cancellation for small `quant/newBalance` ratios, and the result is truncated to a `long` (`(long) issuedSupply`, `(long) exchangeBalance`). This is the same class of defect as the reported issue: the output curve as a function of the traded quantity is not smooth/monotonic near certain input ratios, so two different ways of expressing "the same" trade (one big trade vs. several smaller ones summing to the same quantity) can yield different total outputs, and a user can obtain a better cumulative price than the mathematically fair curve should allow — exactly the "curve is not smooth" failure mode described in the report, just manifesting in the TRC10 Bancor exchange rather than a leverage-position calculator.

The severity of this rounding/precision issue is acknowledged elsewhere in the codebase: a `SafeExchangeProcessor` using `BigDecimal` was later added as a "hardened" alternative (chainbase/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java:1-45), gated by `allowHarden()`/`hardenedCalc` in `ExchangeCapsule.transaction` and `AbstractExchangeActuator`, confirming the original floating-point path was recognized as imprecise. However, unless the corresponding hard fork switch (`allowHarden`) is activated on a given network, `ExchangeTransactionActuator` and `ExchangeInjectActuator`/`ExchangeWithdrawActuator` still route through the legacy, non-monotonic `ExchangeProcessor`.

### Impact Explanation
An attacker can repeatedly call `ExchangeTransactionActuator` (unprivileged, any account with tokens in the exchange pair) with a sequence of smaller trade sizes instead of one large trade, exploiting floating-point cancellation error to extract cumulatively more of the counter-token from the pool than a fair constant-product curve would allow, or vice versa force other traders' larger trades to receive less than expected. Because `ExchangeCapsule.transaction` directly mutates on-chain token balances (`firstTokenBalance`/`secondTokenBalance`) and the actuator immediately credits the account (`ExchangeTransactionActuator.java:86-91`), this is a real value-transfer path, not merely a cosmetic UI issue — it can result in draining value from a TRC10 exchange pool (theft of funds / unbacked balance for other liquidity participants), the same "unintended larger position" harm the original report flags for leveraged positions.

### Likelihood Explanation
Reachable by any unprivileged account that can hold the relevant TRC10 tokens and submit `ExchangeTransactionContract` transactions — no special permission is required. Exploitation only requires performing multiple exchange transactions with carefully chosen quantities near ratio boundaries where floating point precision loss is maximal, which is straightforward to script and repeat.

### Recommendation
Migrate all `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` code paths to always use the `BigDecimal`-based `SafeExchangeProcessor` (removing dependence on the `allowHarden()`/`hardenedCalc` hard-fork gate), or otherwise replace the `double`/`Math.pow` computation in `ExchangeProcessor` with a fixed-point/BigDecimal implementation that guarantees monotonicity: splitting any trade into a sequence of smaller trades summing to the same input must never yield strictly more output than a single trade of the summed quantity.

### Proof of Concept
Conceptual reproduction path (mirrors the report's PoC style):
1. Create an `Exchange` pair with token balances `A` and `B` via `ExchangeCreateActuator`.
2. Using `ExchangeTransactionActuator`, call `ExchangeCapsule.transaction()` once with `sellTokenQuant = Q` (non-hardened path) and record output `O1`.
3. Reset pool state and call `ExchangeCapsule.transaction()` twice with `sellTokenQuant = Q/2` each, summing outputs `O2a + O2b`.
4. Compare `O1` vs `O2a + O2b`: due to the `Math.pow`/cancellation behavior in `exchangeToSupply`/`exchangeFromSupply` (chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:17-39), for certain `Q`/balance ratios these differ, demonstrating the curve is not smooth/monotonic — analogous to the `x1`/`x1.7` leverage collision in the original report.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
