Audit Report

## Title
`process_delivery_receipt` pays relayer reward and closes pending orders without checking the decoded `success` flag of the delivery receipt - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt`, decoded from a Merkle/event-proved Ethereum `InboundMessageDispatched` log, carries a `success: bool` field recording whether the message actually executed on the Gateway contract. `Pallet::process_delivery_receipt` validates the gateway address and pending-order nonce but never inspects `receipt.success` before calling `T::RewardPayment::register_reward` and removing the `PendingOrder`, so a genuinely proved but failed (`success == false`) dispatch still results in full relayer payout and permanent order closure.

## Finding Description
The `submit_delivery_receipt` extrinsic is reachable by any signed account (`ensure_signed(origin)?`), verifies the event log's authenticity via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` (which faithfully copies the on-chain `success` field per `TryFrom<&Log>`), and forwards it unmodified to `process_delivery_receipt`. That function only checks `T::GatewayAddress::get() == receipt.gateway` and that a `PendingOrder` exists for `receipt.nonce`; it then unconditionally pays `order.fee` as a reward and removes the order via `<PendingOrders<T>>::remove(nonce)`, regardless of the value of `receipt.success`. The module's own doc-header states the intended flow is that reward is paid "when the message has been verified and executed," but the actual check only verifies proof authenticity and gateway/nonce matching — not the recorded execution outcome. No other check in the pallet, in `do_process_message`, or in the call path references `success`.

## Impact Explanation
Since any account holding a legitimately provable Merkle/event proof for a `success == false` `InboundMessageDispatched` log (a normal, expected occurrence whenever the Gateway contract's dispatched command reverts, e.g. due to gas exhaustion) can still collect the full relayer reward and cause the `PendingOrder` to be permanently removed, this results in payout for underpriced/failed work and improper settlement of bridge delivery state — matching the "public underpriced work" and duplicate/incorrect settlement categories in the impact gate. Rewards intended to compensate successful delivery are paid for failed executions, and the bookkeeping used to track outstanding deliveries is silently and irreversibly closed out even though the corresponding action never completed successfully on Ethereum.

## Likelihood Explanation
The path requires no privileged origin, relayer allowlist, or compromised infrastructure — only a signed account and a valid Merkle/event proof for a real Ethereum log where the dispatched command failed, which is an ordinary occurrence in cross-chain messaging when Gateway execution reverts. This makes the issue highly reachable and repeatable by any unprivileged party who observes such a failure on Ethereum.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only pay `T::RewardPayment::register_reward` and treat the order as successfully settled when `success == true`. When `success == false`, avoid paying the full reward (or apply reduced/no fee), and handle the pending order's lifecycle explicitly (e.g., emit a distinct `MessageExecutionFailed` event and decide on refund/retry semantics) rather than treating failed execution identically to successful delivery.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating a `PendingOrder` with `fee > 0` at a given `nonce` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 426-436).
2. The message is delivered to the Ethereum Gateway, but the dispatched command reverts, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account submits this genuine, provable log via `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the log is authentic) and `DeliveryReceipt::try_from` decodes `success: false` correctly.
5. `process_delivery_receipt` checks only `gateway` and `PendingOrders::get(nonce)`; since `order.fee > 0`, it calls `register_reward` and removes the order regardless of `success` being `false`, confirmed at `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 445-480.
6. A unit test asserting that a `DeliveryReceipt { success: false, .. }` still results in `MessageDelivered` being emitted and the reward being paid would demonstrate the bug.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
