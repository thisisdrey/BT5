### Title
Uncapped gas subtraction after clamped admission check allows a single receipt to zero a shard's outgoing gas budget - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
In `ReceiptSinkV2::try_forward`, the admission check clamps the compared gas value (`admission_gas`) to `allowed_shard_outgoing_gas` under `ProtocolFeature::ClampOutgoingGasAdmission`, but the subsequent budget decrement uses the full, unclamped `gas` value via `forward_limit.gas.saturating_sub(gas)`. This mismatch lets one cheaply-admitted, high-gas receipt collapse the entire per-sender-shard outgoing gas budget for the chunk instead of being charged only the clamped amount.

### Finding Description
`try_forward` (`runtime/runtime/src/congestion_control.rs:403-463`) computes `admission_gas` by clamping the receipt's congestion gas to `allowed_shard_outgoing_gas` when `ClampOutgoingGasAdmission` is active: [1](#0-0) 

The forwarding decision compares `forward_limit.gas >= admission_gas` (the clamped value), but on success the code decrements `forward_limit.gas` by the full, uncapped `gas`: [2](#0-1) 

The receipt's congestion gas (`gas`) for a `FunctionCall` action includes the attached prepaid gas via `action_receipt_congestion_gas`, which an unprivileged attacker fully controls by attaching a large amount of gas (bounded only by the per-transaction/per-receipt gas limit, e.g. up to `max_gas_burnt`/attached gas ceiling, which is far larger than `allowed_shard_outgoing_gas`). `forward_limit` for the receiver shard is initialized per chunk from `outgoing_gas_limit(sender_shard)` on the receiving shard's `CongestionControl`, which for a partially congested shard (`0 < congestion_level < 1`) is `mix_gas(max_outgoing_gas, min_outgoing_gas, congestion_level)` — a modest, non-`Gas::MAX` value. Because `forward_limit.gas` only needs to exceed the *clamped* `admission_gas` (≤ `allowed_shard_outgoing_gas`) to pass, but the *full* attacker-chosen `gas` is then subtracted with `saturating_sub`, a single attacker receipt with `gas` far exceeding `forward_limit.gas` will pass admission and then zero out (`saturating_sub` floors at 0) the entire remaining budget in one step. Any subsequent legitimate receipt in the same chunk targeting the same shard will fail the `forward_limit.gas >= admission_gas` check and be pushed to `NotForwarded`/buffered via `buffer_receipt` (`:466`), even though a fair, congestion-proportional allocation would have allowed it.

None of the existing checks (signature, nonce, access-key, gas metering, size limits) block this: gas metering only limits gas burnt during execution, not the attacker's ability to attach large prepaid gas to a `FunctionCall` receipt destined for cross-shard forwarding, and the size clamp (`:417-427`, issue #12606 workaround) is an unrelated, separate mitigation for receipt size, not gas.

### Impact Explanation
This is a liveness/fair-flow-control violation, not a fund-theft bug: a single attacker-crafted `FunctionCall` receipt with outsized prepaid gas can cause a moderately congested victim shard's per-sender `OutgoingLimit.gas` to collapse to zero for the remainder of the chunk, causing legitimate concurrent receipts from the same sender shard to be denied forwarding and instead buffered, delaying their execution. This matches a "denial of service / degraded liveness for cross-shard receipt delivery" category rather than fund loss, consensus divergence, or a shard halt — repeated buffering does not corrupt state, since buffered receipts are eventually retried in later chunks, but it does allow one cheap-to-admit attacker receipt to unfairly starve other users' cross-shard messages to the same shard for that chunk.

### Likelihood Explanation
This requires only unprivileged capabilities: fund an account, and submit one `FunctionCall` receipt with prepaid gas set far above `allowed_shard_outgoing_gas` targeting an account on a moderately congested shard. It is fully repeatable per chunk (the attacker can resend such a receipt every chunk as long as the victim shard remains partially congested), and costs the attacker only the gas price for that one receipt (paid as normal, no privileged relationship needed). The precondition of `0 < congestion_level < 1` on the victim shard is a normal operating condition, not a rare edge case, making this practically reachable on mainnet where `ClampOutgoingGasAdmission` (PV ≥ 85) is active.

### Recommendation
Charge the budget by the same clamped value used for admission (`admission_gas`) instead of the raw `gas`, i.e., change `forward_limit.gas = forward_limit.gas.saturating_sub(gas)` to subtract `admission_gas`, so the deduction is proportional to what was actually checked against the limit, preventing a single receipt from consuming more of the budget than the admission gate intended to allow.

### Proof of Concept
Unit test in `runtime/runtime/src/congestion_control.rs` (or its test module) directly exercising `ReceiptSinkV2::try_forward`:
1. Construct an `ApplyState` with `current_protocol_version` ≥ 85 (`ClampOutgoingGasAdmission` enabled) and `congestion_control_config.allowed_shard_outgoing_gas = 50`.
2. Initialize `outgoing_limit` map with `OutgoingLimit { gas: 500, size: <large> }` for the target shard (simulating a `mix_gas` result for partial congestion).
3. Call `try_forward` with a `FunctionCall` receipt whose congestion gas `= 100_000` (attacker receipt). Assert:
   - Result is `ReceiptForwarding::Forwarded` (admission passes because `admission_gas = min(100_000, 50) = 50 <= 500`).
   - After the call, `outgoing_limit[shard].gas == 0` (due to `saturating_sub(100_000)` on 500).
4. Call `try_forward` again with a second, normal receipt whose congestion gas `= 200` (≤ original 500 budget). Assert:
   - Result is `ReceiptForwarding::NotForwarded(_)`, demonstrating the legitimate receipt is denied forwarding even though a fair proportional budget (500 minus a properly clamped 50) would have admitted it.
