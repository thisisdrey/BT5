Audit Report

## Title
Unbound MMR leaf position allows mis-bound `parent_number_and_hash` to be recorded for an unrelated block number - (File: `bridges/modules/beefy/src/lib.rs`)

## Summary
`Pallet::submit_commitment` in `bridges/modules/beefy/src/lib.rs` verifies a signed BEEFY commitment and independently verifies that a supplied `mmr_leaf`/`mmr_proof` pair is included in that commitment's MMR root via `utils::verify_beefy_mmr_leaf`, but never checks that the proof's `leaf_indices` (i.e., the proven leaf's position) actually corresponds to `commitment.commitment.block_number`. [1](#0-0)  Since MMR roots are cumulative, any earlier genuine leaf can be proven against a later root, allowing an unrelated block's `parent_number_and_hash` to be stored under the current commitment's `block_number` key in `ImportedCommitments`.

## Finding Description
`verify_commitment` only validates the validator set, signatures, and extracts the MMR root from the commitment payload — it never touches the leaf or its position. [2](#0-1) 

`verify_beefy_mmr_leaf` only proves `mmr_leaf` is included in `mmr_root` at whatever position `mmr_proof.leaf_indices` specifies; it performs no check that this index equals the expected leaf index for `commitment.commitment.block_number`. [3](#0-2) 

The underlying `verify_leaves_proof` is purely structural: it maps `proof.leaf_indices` to tree positions (via `mmr_lib::leaf_index_to_pos`) and checks the merkle path against `root`, with `proof.leaf_count` only affecting the tree "size" parameter used for path reconstruction — it never derives or enforces which leaf index *should* correspond to the externally-claimed block number. [4](#0-3) 

The test helper in `mock_chain.rs` confirms the intended convention that leaf index should equal `header.number() - 1` and `leaf_count` should equal `header.number()` — a convention that is enforced only by the test's own construction, not by any on-chain check in `submit_commitment` or `verify_beefy_mmr_leaf`. [5](#0-4) 

Because MMR roots accumulate all historical leaves, any leaf `L_M` from an earlier block `M` remains provable against any later root `R_N` (`N > M`) using the correct `leaf_count = N` and a valid Merkle path — this is not a proof forgery but a legitimate historical-inclusion proof against the wrong claimed context. `submit_commitment` accepts such a proof and unconditionally writes `ImportedCommitment { parent_number_and_hash: mmr_leaf.parent_number_and_hash, mmr_root }` under key `commitment.commitment.block_number`, binding block `N`'s storage entry to an unrelated block `M`'s parent hash/number. [6](#0-5) 

Existing tests only cover cases where the leaf content is tampered with (which breaks the leaf hash and fails verification) or the proof items/root are corrupted — they do not cover substituting a genuine, unmodified older leaf+proof pair against a newer, otherwise-valid commitment, so this gap is not caught by current guards. [7](#0-6) 

## Impact Explanation
`ImportedCommitments` is the on-chain BEEFY light-client state that downstream bridge pallets rely on to validate header-based proofs for the bridged chain. Poisoning the `parent_number_and_hash` value recorded for a given `block_number` corrupts the light client's ancestry record, matching the "forged or mis-bound proof or state acceptance" impact category for the Polkadot SDK bridge scope. This is a state-integrity bug in a public extrinsic (`submit_commitment`) rather than a privileged-actor issue.

## Likelihood Explanation
`submit_commitment` requires only `ensure_signed(origin)` — any account can call it. [8](#0-7)  The attacker needs only one legitimately signed BEEFY commitment for a new block (public gossip data) and any older leaf+proof pair reconstructable from the same public MMR — no malicious validator, relayer compromise, or privileged access is required, making this a repeatable, unprivileged attack path.

## Recommendation
Derive the expected leaf index from `commitment.commitment.block_number` (following the `leaf index = block_number - 1` convention already used elsewhere) and assert that `mmr_proof.leaf_indices == [expected_index]` (and that `mmr_proof.leaf_count` is consistent with `block_number`) inside `verify_beefy_mmr_leaf` or `submit_commitment`, rejecting the call otherwise.

## Proof of Concept
1. Observe a legitimate signed BEEFY commitment for block `N` with MMR root `R_N` (public gossip).
2. From the historical/reconstructable MMR, obtain an earlier leaf `L_M` (`M < N-1`) with a valid inclusion proof against `R_N` (valid `leaf_count = N`, correct Merkle path) — such a proof exists because `R_N` accumulates all past leaves.
3. Call `submit_commitment(origin, commitment_for_N, validator_set, Box::new(L_M), proof_of_L_M_against_R_N)` from any signed account.
4. `verify_commitment` succeeds (unrelated to the leaf); `verify_beefy_mmr_leaf` succeeds since `L_M` is genuinely included in `R_N` at the claimed position.
5. `ImportedCommitments::<T, I>::get(N)` now returns `parent_number_and_hash = L_M.parent_number_and_hash`, i.e., block `M`'s parent hash/number recorded under block `N`'s key — as shown by the code path in `bridges/modules/beefy/src/lib.rs:242-248`.

```rust
pub(crate) fn verify_commitment<T: Config<I>, I: 'static>(
	commitment: &BridgedBeefySignedCommitment<T, I>,
	authority_set_info: &BridgedBeefyAuthoritySetInfo<T, I>,
	authority_set: &BridgedBeefyAuthoritySet<T, I>,
) -> Result<BridgedMmrHash<T, I>, Error<T, I>> {
	// Ensure that the commitment is signed by the best known BEEFY validator set.
	ensure!(
		commitment.commitment.validator_set_id == authority_set_info.id,
		Error::<T, I>::InvalidCommitmentValidatorSetId
	);
	ensure!(
		commitment.signatures.len() == authority_set_info.len as usize,
		Error::<T, I>::InvalidCommitmentSignaturesLen
	);

	verify_authority_set(authority_set_info, authority_set)?;
	verify_signatures(commitment, authority_set)?;

	extract_mmr_root(commitment)
}
```

```rust
/// Verify MMR proof of given leaf.
pub(crate) fn verify_beefy_mmr_leaf<T: Config<I>, I: 'static>(
	mmr_leaf: &BridgedBeefyMmrLeaf<T, I>,
	mmr_proof: BridgedMmrProof<T, I>,
	mmr_root: BridgedMmrHash<T, I>,
) -> Result<(), Error<T, I>> {
	let mmr_proof_leaf_count = mmr_proof.leaf_count;
	let mmr_proof_length = mmr_proof.items.len();

	// Verify the mmr proof for the provided leaf.
	let mmr_leaf_hash = BridgedMmrHashing::<T, I>::hash(&mmr_leaf.encode());
	verify_mmr_leaves_proof(
		mmr_root,
		vec![BridgedMmrDataOrHash::<T, I>::Hash(mmr_leaf_hash)],
		mmr_proof,
	)
	.map_err(|e| {
		tracing::error!(
			target: LOG_TARGET,
			error=?e,
			?mmr_leaf_hash,
			root=?mmr_root,
			leaf_count=%mmr_proof_leaf_count,
			len=%mmr_proof_length,
			"MMR proof of leaf verification has failed"
		);

		Error::<T, I>::MmrProofVerificationFailed
	})
}
```

```rust
pub fn verify_leaves_proof<H, L>(
	root: H::Output,
	leaves: Vec<Node<H, L>>,
	proof: LeafProof<H::Output>,
) -> Result<bool, Error>
where
	H: Hash,
	L: FullLeaf,
{
	let size = NodesUtils::new(proof.leaf_count).size();

	if leaves.len() != proof.leaf_indices.len() {
		return Err(Error::Verify.log_debug("Proof leaf_indices not same length with leaves"));
	}

	let leaves_and_position_data = proof
		.leaf_indices
		.into_iter()
		.map(|index| mmr_lib::leaf_index_to_pos(index))
		.zip(leaves.into_iter())
		.collect();

	let p = mmr_lib::MerkleProof::<Node<H, L>, Hasher<H, L>>::new(
		size,
		proof.items.into_iter().map(Node::Hash).collect(),
	);
	p.verify(Node::Hash(root), leaves_and_position_data)
		.map_err(|e| Error::Verify.log_debug(e))
}
```
