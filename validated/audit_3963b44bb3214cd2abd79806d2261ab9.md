## Title
Squash-induced sibling-node trie reads are recorded into the chunk's storage-proof size only during the deferred, whole-chunk `TrieUpdate::finalize()` pass, bypassing both the per-receipt `EnforcePerReceiptStorageProofLimit` hard limit and the chunk-wide soft limit check, and are never gas-charged - (File: core/store/src/trie/ops/squash.rs)

### Summary
`GenericTrieUpdateSquash::extend_child` (via `squash_node`) calls `ensure_updated` on the surviving sibling of a two-child branch when the other child is deleted, and this sibling read is recorded by `TrieRecorder` into `recorded_storage_size_upper_bound()`. However, real trie mutation (insert/delete/squash) never happens during action execution — `TrieUpdate::set`/`remove` only buffer into `prospective`/`committed` maps, and the actual `trie.update()` walk that performs squashing is deferred to a single `TrieUpdate::finalize()` call executed once for the *entire chunk*, after all receipts have already been processed and their `EnforcePerReceiptStorageProofLimit` checks have passed.

### Finding Description
The per-receipt hard storage-proof limit is enforced in `apply_action_receipt` by snapshotting `recorded_storage_size_upper_bound()` before the receipt's action loop and comparing it to the value after each action: [1](#0-0) [2](#0-1) 

This is the only place `EnforcePerReceiptStorageProofLimit`-gated accounting happens, and it runs entirely inside `apply_action_receipt`, i.e. before `state_update.finalize()`.

`storage_remove`/`storage_write` (via `TrieUpdate::remove`/`set`) do not touch the actual trie structure at all — they only buffer changes: [3](#0-2) 

Real trie mutation, including the branch→extension squash logic (`squash_node`/`extend_child`), only happens once, when `TrieUpdate::finalize()` calls `trie.update(committed…)`: [4](#0-3) 

And `Runtime::apply` calls `state_update.finalize()` exactly once, for the whole chunk, at the very end of `validate_apply_state_update` — well after step 3 ("process receipts") has fully completed: [5](#0-4) [6](#0-5) 

Inside that single deferred `finalize()`/`trie.update()` pass, `squash_node`'s `extend_child` reads the surviving sibling via `ensure_updated`, exactly as documented: [7](#0-6) [8](#0-7) 

That sibling read is recorded by `TrieRecorder` via `convert_existing_to_updated`/`nodes_tracker.record(...)`, adding to `upper_bound_size` — the same counter used for `recorded_storage_size_upper_bound()`: [9](#0-8) 

Because this happens only during the deferred, chunk-wide `finalize()` call:
1. It cannot be captured by the per-receipt "before/after action" delta check in `apply_action_receipt`, since that check's window closes long before `finalize()` runs — the bytes literally don't exist yet at check time.
2. It also is not visible to the chunk-wide soft limit (`main_storage_proof_size_soft_limit`), which is checked via `trie.check_proof_size_limit_exceed()` *between* receipts, during the receipt-processing loop — also before `finalize()` runs.
3. `TrieUpdate::finalize()` uses `AccessOptions::DEFAULT`, not the `contract_runtime` tracker used for `storage_remove`/`storage_read`, so no TTN ("touching trie node") gas is charged for this sibling read either — it's genuinely gas-free.

The only place this growth is ever observed is the post-hoc metric taken right after `finalize()`: [10](#0-9) 
which is purely informational (a Prometheus histogram), not an enforcement point.

### Impact Explanation
An unprivileged account can deploy a contract and, across many receipts within a single chunk, repeatedly create two-child branches (one child being a large-ish sibling subtree node, e.g. a full 16-way branch/extension) and delete the small sibling. Each such deletion triggers one `extend_child`/`ensure_updated` sibling-node read at `finalize()` time that: (a) counts toward the chunk's real recorded storage proof (and thus `ChunkStateWitness` size), (b) is invisible to and unbounded by the 4MB per-receipt hard limit (`EnforcePerReceiptStorageProofLimit`) and the chunk-wide soft limit checked during the receipt loop, and (c) costs the attacker no gas (TTN accounting is bypassed since `finalize()` uses `AccessOptions::DEFAULT`). This lets an attacker cheaply grow the chunk's real witness size beyond what the size-limit mechanisms described in `docs/misc/state_witness_size_limits.md` intend to guarantee, undermining the "keep `ChunkStateWitness` under ~21MiB" invariant the limits are designed to enforce. This is a metering/accounting-totality bug with a concrete, low-cost, repeatable mainnet-reachable trigger.

### Likelihood Explanation
Preconditions are minimal: an unprivileged, funded account that deploys its own contract and issues ordinary `FunctionCall` transactions to write/delete storage keys forming branch/sibling structures (standard trie key insertion patterns, no special permissions needed). Each squash event contributes only on the order of one serialized `RawTrieNode` (roughly hundreds of bytes for a branch with several children), so a meaningful chunk-wide effect requires many such deletions packed into one chunk — feasible since storage removals are comparatively cheap gas operations and thousands can fit within a chunk's gas budget. The attack is fully repeatable across chunks/blocks with no special timing or validator cooperation required.

### Recommendation
Charge the storage-proof bytes recorded during `TrieUpdate::finalize()`'s squash pass back to the originating receipt(s), or move squash/insert-delete trie mutation to happen eagerly per receipt (before commit) rather than deferring it to a single end-of-chunk `finalize()`, so that `recorded_storage_size_upper_bound()` snapshots taken by `EnforcePerReceiptStorageProofLimit` and the chunk-wide soft-limit check actually observe squash-induced reads before the chunk is deemed complete. At minimum, re-run the per-receipt and chunk-wide proof-size checks after `finalize()` and fail/re-delay the chunk (or attribute/charge gas) if squash-only growth pushes totals over the limits.

### Proof of Concept
Integration test plan (extending `integration-tests/src/tests/features/storage_proof_size_limit.rs` / `runtime/runtime/src/tests/apply.rs::test_per_receipt_storage_proof_size_limit` patterns):
1. Deploy a contract; write keys forming N two-child branch nodes where one child of each branch is itself a multi-child branch/extension (the "large sibling"), and the other is a short leaf.
2. Submit a receipt (or many receipts within one chunk) that deletes only the leaf sibling of each branch via `storage_remove`.
3. Record `state_update.trie.recorded_storage_size_upper_bound()` immediately after `apply_action_receipt` returns for the deleting receipt(s) (this is what `EnforcePerReceiptStorageProofLimit` used), and separately record it again after the full `Runtime::apply` (post `state_update.finalize()`, i.e. via `apply_result.trie_changes`/the recorder used to build `ApplyResult`).
4. Assert: (a) the deleting receipt(s) succeed with gas well under what `per_receipt_storage_proof_size_limit` would imply, (b) the post-`finalize()` recorded proof size is measurably larger than the pre-`finalize()` snapshot by an amount attributable to the sibling reads (matches `N * (bytes per sibling RawTrieNode)`), and (c) no `ReceiptStorageProofSizeExceeded`/proof-limit error is raised for the deleting receipt even though total proof growth (if repeated at scale) would exceed `main_storage_proof_size_soft_limit`/`per_receipt_storage_proof_size_limit` had it been measured before `finalize()`.
