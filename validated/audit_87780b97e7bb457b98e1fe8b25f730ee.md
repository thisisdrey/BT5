### Title
Stale signer authorization retained when a StackerDB contract's signer set is reconfigured to empty - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to update a locally-replicated StackerDB's signer/slot ownership table by comparing the freshly-evaluated contract config against the previously cached one. The reconfiguration is deliberately skipped whenever the newly loaded signer list is empty, which means the on-disk (and thus authoritative-for-validation) mapping of `slot_id -> signer address` can remain stuck on a superseded signer set indefinitely. Any peer still holding the private key for a previously-authorized slot can continue to produce validly-signed chunks that stale nodes will accept and re-gossip, even though the controlling contract no longer authorizes that signer for that slot — the same "compare against a value that can go stale after an on-chain update" bug class as the reported `WITHDRAWAL_ADDRESS`/`CSVerifier` issue.

### Finding Description
`StackerDBConfig::from_smart_contract` re-evaluates a StackerDB's owning contract (via `stackerdb-get-signer-slots`/`stackerdb-get-config`) to obtain the current `signers: Vec<(StacksAddress, u32)>` mapping [1](#0-0) . This new config is compared against the currently cached one and, only if different, `reconfigure_stackerdb` is invoked to update the on-disk `signer` column for each slot:

```
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len()
            != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    // only reconfigure if the config has changed ...
    if let Err(e) = self.reconfigure_stackerdb(&stackerdb_contract_id, &new_config) { ... }
}
``` [2](#0-1) 

The `!new_config.signers.is_empty()` guard means that when the contract now reports an empty signer list (e.g. governance revokes/rotates the signer set to a state where the freshly loaded config comes back with zero entries), the local replica's `signer_validation.signer` mapping is **not** updated and keeps the previous (now-superseded) address for every slot. `validate_received_chunk` and `StackerDBTx::try_replace_chunk` both authorize incoming chunks purely by comparing the message's recovered public key hash against this on-disk `signer` value [3](#0-2) [4](#0-3) . Because this value is never refreshed once the "empty signers" branch is hit, the equality check `slot_metadata.verify(&addr)` keeps succeeding for the old, no-longer-authorized signer indefinitely on any node that experiences this code path — exactly mirroring the `WITHDRAWAL_ADDRESS` staleness pattern where an immutable, cached identifier is checked for equality against a value that can silently change on-chain.

### Impact Explanation
Chunks accepted under a stale signer identity are further relayed to peers via `handle_unsolicited_StackerDBPushChunk` and inventory gossip [5](#0-4) , so a revoked signer's messages can continue propagating network-wide as if still authoritative. For contracts such as `.signers-*` (consumed by `stacks-signer` for block acceptance/rejection voting) this could let a stale/removed signer's messages keep being treated as legitimate signer traffic by nodes stuck with the old config, which is a "network-wide propagation of forged/unauthorized data" class issue.

### Likelihood Explanation
The trigger condition — the reconfigured contract state evaluating to an empty signer list — is not attacker-controlled directly; it depends on the specific on-chain signer-set contract deliberately or transiently reporting zero signers (which the code's own comment shows was already a source of a related historical bug, #5142, about a StackerDB "never shrinking"). This limits likelihood compared to a fully attacker-triggerable primitive, but once hit, exploitation by any previously-authorized keyholder is straightforward and requires no privileged access to the node.

### Recommendation
Do not gate reconfiguration purely on `!new_config.signers.is_empty()`. Distinguish "config eval genuinely failed / fell back to noop" from "the contract now legitimately reports zero signers," and in the latter case still wipe/reconfigure the local slot-to-signer mapping so stale signer authorizations cannot persist. Track the contract's own versioning/epoch for the signer set rather than only comparing the resulting tuple equality.

### Proof of Concept
Not independently reproduced beyond static code analysis of the `create_or_reconfigure_stackerdbs`, `reconfigure_stackerdb`, and `validate_received_chunk` control flow cited above; a concrete PoC would require driving a `.signers-*` (or custom) StackerDB contract to a state where `eval_signer_slots` returns an empty vector for one reconfiguration pass, then observing that a node continues to accept and re-broadcast chunks signed by the previous signer for slots that existed before that pass.
