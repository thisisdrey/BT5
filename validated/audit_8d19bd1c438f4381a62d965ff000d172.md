### Title
Unrestricted `FindRemoteRepository`/`FindRemoteRootRef` accept fully user-controlled remote strings passed directly to `git ls-remote`/`git remote show`, unlike the SSRF/rebinding protections used elsewhere - (File: internal/gitaly/service/remote/find_remote_repository.go)

### Summary
`FindRemoteRepository` takes an arbitrary, attacker-supplied `Remote` string and passes it verbatim as an argument to `git-ls-remote(1)`, with none of the mitigations that Gitaly applies to functionally equivalent RPCs (`FetchRemote`, `CreateRepositoryFromURL`, `FindRemoteRootRef`) — no scheme allowlisting, no `resolved_address`/DNS-rebinding pinning, and no `transfer.bundleURI=false` hardening.

### Finding Description
The external report's bug class is "an unprivileged caller supplies attacker-controlled data that is fed into a call whose target/interpretation is fully controlled by that data, letting the caller redirect trusted execution somewhere unintended." In gitaly, git itself acts as the "arbitrary call" surface: a `remote`/URL string handed to git can select non-HTTP transports (`ext::`, `file://`, `fd::`, local paths) or point at internal/loopback addresses, and Gitaly's own code elsewhere treats this as a serious concern.

Contrast the RPCs:
- `CreateRepositoryFromURL` explicitly resolves DNS-rebinding via `resolved_address`/`GetURLAndResolveConfig` and disables `transfer.bundleURI` "to prevent attack vectors that could abuse this mechanism" [1](#0-0) .
- `FetchRemote`/`buildCommandOpts` and `FindRemoteRootRef` also support `resolved_address` pinning via `gitcmd.GetURLAndResolveConfig` [2](#0-1) [3](#0-2) .

By contrast, `FindRemoteRepository` only checks the `Remote` field is non-empty and then runs `git ls-remote <remote> HEAD` with the raw string, with no scheme validation, no `resolved_address` support, and no bundle-URI hardening: [4](#0-3) 

Because `git-ls-remote(1)` interprets its first positional argument the same way `git-fetch`/`git-clone` do, a caller can supply values such as `ext::sh -c ...` (if the `ext` helper is permitted by the runtime's git build/environment) or point the command at `http://169.254.169.254/...`, `http://localhost:<internal-port>/...`, or a local filesystem path (`file:///var/...` or a bare path) that the Gitaly process can read, all under the identity/network context of the Gitaly server process rather than the caller.

### Impact Explanation
An unprivileged/ordinary caller of the `RemoteService.FindRemoteRepository` RPC (and similarly `FindRemoteRootRef`, which also lacks `transfer.bundleURI` hardening even though it does support `resolved_address`) can cause the Gitaly host to issue arbitrary outbound git-protocol requests, enabling SSRF against internal services/metadata endpoints reachable from the Gitaly node, or to interact with local filesystem paths reachable by git's local transport. This maps to the "SSRF or credential disclosure" acceptance category, since the RPC has no scheme allowlist and no IP-pinning defense that its sibling RPCs already implement.

### Likelihood Explanation
`FindRemoteRepository` requires only a valid `Remote` string and a `StorageName`; there is no repository ownership check on the remote target itself (it is not fetching into a repository, just probing). Any client with access to invoke `RemoteService` RPCs (e.g., through GitLab's application layer proxying user-triggered "check remote" style actions, or any caller with gRPC access) can trigger this with a single call, making it straightforward to reach.

### Recommendation
Apply the same defenses used by `CreateRepositoryFromURL`/`FetchRemote` to `FindRemoteRepository` (and audit `FindRemoteRootRef` for the missing `transfer.bundleURI=false` hardening):
- Validate/allowlist the URL scheme (e.g., restrict to `http`/`https`/`git`/`ssh`) before invoking `git-ls-remote`.
- Support and require (or default-apply) `resolved_address`-based DNS-rebinding protection via `gitcmd.GetURLAndResolveConfig`, consistent with `FetchRemote`/`CreateRepositoryFromURL`.
- Explicitly disable `transfer.bundleURI` on the ad-hoc command, matching the mitigation already applied in `cloneFromURLCommand`.

### Proof of Concept
1. As an unprivileged caller with access to `RemoteService`, invoke:
```
FindRemoteRepository(Remote: "http://169.254.169.254/latest/meta-data/", StorageName: "<storage>")
```
2. Gitaly runs `git ls-remote http://169.254.169.254/latest/meta-data/ HEAD` from the server host, as shown in the unmitigated code path [5](#0-4) , with no scheme allowlist or IP-pinning check applied, unlike the equivalent `CreateRepositoryFromURL`/`FetchRemote` code paths.
3. Because there is no `resolved_address` support here, an attacker cannot even be forced into a pinned IP the way `FetchRemote`/`CreateRepositoryFromURL` callers can be — the request goes wherever DNS/the string resolves at request time, which is a strictly weaker posture than the RPCs GitLab already hardened for this exact concern.

Note: I could not verify from the available index whether the Gitaly-bundled Git binary is compiled with the `ext::` transport helper enabled or whether an outer allowlist (e.g., `GIT_ALLOW_PROTOCOL`/`protocol.*.allow`) is set process-wide; no such configuration was found in `command_factory.go`'s `setupGitExecutionEnvironments`/`GlobalConfiguration`. This affects whether full command execution via `ext::` is reachable versus "only" SSRF via `http(s)://`/`git://`. A Devin session with full repository/build access would be needed to confirm the compiled Git's allowed transports and any wrapper-level protocol restrictions.

```go
func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
	if err != nil {
		return nil, structerr.NewInternal("error executing git command: %w", err)
	}
```
