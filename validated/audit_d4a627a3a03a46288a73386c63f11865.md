### Title
Reference counter incremented by pre-receive hook is permanently leaked when quarantine migration or ref update fails after pre-receive succeeds - (File: internal/gitaly/hook/updateref/update_with_hooks.go)

### Summary
`UpdaterWithHooks.UpdateReference` increments GitLab's per-repository push reference counter via the pre-receive hook, but returns early — without invoking the post-receive hook that decrements it — on any failure occurring in quarantine migration, the update hook, or the reference-transaction prepare/commit steps. This leaves the counter permanently incremented for legitimate, attacker-triggerable failure conditions.

### Finding Description
`PreReceiveHook` calls `m.gitlabClient.PreReceive(ctx, repo.GetGlRepository())` which increments Rails' internal per-repository reference counter (documented as tracking "how many pushes are active at the same time") [1](#0-0) . This counter is only ever decremented by `PostReceiveHook`'s call to `m.gitlabClient.PostReceive` [3](#0-2) .

In `UpdaterWithHooks.UpdateReference`, after `PreReceiveHook` succeeds, several steps must all succeed before `PostReceiveHook` is ever called: quarantine object migration, the update hook, and the reference-transaction preparing/prepared/commit sequence [4](#0-3) . Each of these returns an error immediately, exiting the function before line 309's `PostReceiveHook` call is reached [5](#0-4) .

Several of these failure conditions are reachable by an ordinary authenticated user through crafted RPC input to `OperationService` RPCs that use `UpdaterWithHooks` (e.g. `UserCreateTag`, `UserUpdateBranch`, etc.):
- A concurrent/conflicting reference state can cause `updater.Prepare()` or `updater.Commit()` to fail (returned as `Error{...}`) after `PreReceiveHook` already incremented the counter.
- A custom `update` hook installed by an administrator that exits non-zero causes `UpdateHook` to fail.
- `quarantineDir.Migrate` can fail on filesystem-level errors.

None of these cause `PostReceiveHook` to run, so the counter is left elevated forever, with no automatic recovery mechanism — exactly analogous to the reported `Curves` bug where fees taken from one accounting bucket are never forwarded/reconciled under specific conditional branches.

### Impact Explanation
Per `doc/hooks.md`, the reference counter is used by GitLab Rails to determine when a repository is safe to move ("If the reference counter is not at 0, there are active pushes happening") [6](#0-5) . A permanently stuck non-zero counter means Rails will indefinitely believe there is an active push to that repository, which can block legitimate repository relocation/storage-migration operations — a persistent denial of service on repository management for the affected repository, triggerable repeatedly by an ordinary user via normal ref-update RPCs that race against or fail update/reference-transaction hooks.

### Likelihood Explanation
Reachable from an unprivileged, authenticated user simply by causing routine reference-update conflicts (e.g., pushing racing updates causing `updater.Commit()` compare-and-swap failures) or by triggering an administrator-installed custom `update` hook to fail, both of which are ordinary occurrences in the reference-update path — no special privileges, MITM, or malicious peer required.

### Recommendation
Ensure `PostReceiveHook` (or an equivalent counter-decrement call) is always invoked once `PreReceiveHook` has successfully incremented the counter, regardless of whether later steps (quarantine migration, update hook, reference-transaction hook, ref commit) succeed or fail — for example by using a `defer` that unconditionally calls the post-receive/decrement logic after a successful pre-receive, mirroring how `git-receive-pack` always executes `post-receive` after `pre-receive` succeeds regardless of per-ref failures.

### Proof of Concept
1. As an authenticated user with write access, call an `OperationService` RPC that routes through `UpdaterWithHooks.UpdateReference` (e.g. `UserCreateTag`) targeting a reference.
2. Concurrently issue a second conflicting reference update (or install/trigger a custom `update` hook that exits non-zero) so that `updater.Prepare()`/`updater.Commit()` or `UpdateHook` fails after `PreReceiveHook` has already succeeded and incremented Rails' reference counter.
3. Observe that the RPC returns an error without `PostReceiveHook` ever being invoked (confirm via the `/internal/post_receive` endpoint never being called and the `/internal/pre_receive` counter remaining incremented).
4. Repeat to accumulate an ever-increasing stuck counter for the target repository, preventing Rails from ever treating the repository as push-idle.
