### Title
DepositToken supply cap blocks collateral top-ups, enabling forced liquidations - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._mint()` enforces the governor-set `maxTotalSupply` cap and reverts with `SurpassMaxDepositSupply()` whenever a deposit would push `totalSupply` above it. This is the same bug class as the Size finding: a protocol-level cap check reverts a `deposit()` call unconditionally, including when a borrower is trying to add collateral to rescue an underwater position. An unprivileged attacker can deliberately fill the cap so that other users' deposits revert and their positions become liquidatable.

### Finding Description
`DepositToken.deposit()` pulls underlying into the `Treasury` and calls `_mint(onBehalfOf_, _deposited)` [1](#0-0) . `_mint` enforces the cap:

```solidity
totalSupply += amount_;
if (totalSupply > maxTotalSupply) revert SurpassMaxDepositSupply();
``` [2](#0-1) 

The revert happens after the underlying was already transferred, so the whole transaction reverts and no collateral is credited. There is no bypass: no "rescue deposit" path, no capping of the minted amount, no exemption for deposits that improve account health. `Pool.liquidate`/`seize` move existing `msdTOKEN` balances via `_transfer` and do not mint, so liquidations themselves are unaffected by the cap — only the defensive deposit path is blocked. The unit test confirms the revert behavior directly [3](#0-2) .

Notably, the codebase already acknowledges this failure mode elsewhere: `DebtToken.accrueInterest` wraps `syntheticToken.mint` in try/catch because "minting will fail (e.g. ... it reached max supply)" [4](#0-3) , and `docs/cross-chain.md` admits stuck cross-chain transactions where "the protocol governor must act in order to unstuck transactions (e.g., increase caps)" — yet `deposit()` has no such graceful handling.

### Impact Explanation
- A borrower whose position is near the liquidation threshold attempts `deposit(amount, onBehalfOf)` to restore health. If `totalSupply + deposited > maxTotalSupply`, the call reverts and the position remains liquidatable; a liquidator then seizes collateral at a discount, causing direct loss of user funds.
- Worse, an unprivileged attacker can force this state: deposit underlying up to `maxTotalSupply` (deposits are permissionless and the cap counts raw supply, not per-user), then any victim whose only available collateral is that underlying cannot top up. The attacker can combine this with a same-transaction oracle price move (e.g., an AMM trade pushing the collateral price down) to push the victim below the liquidation threshold, block the rescue deposit, and liquidate them — extracting the liquidation bonus/seized collateral.

### Likelihood Explanation
- Requires no privileged role: `deposit` is a public entry point reachable directly or via `Operator.execute`/`NativeTokenGateway`/`VesperGateway`.
- Preconditions: the deposit token's `maxTotalSupply` is close to exhausted (or fillable by the attacker within their capital budget — deposits can be withdrawn later, so cost is temporary capital plus fees), and a victim position that is near-liquidatable and relies on that specific collateral.
- Mitigations that reduce but don't eliminate it: the victim could repay debt or deposit a different collateral type if they hold one; the governor can raise the cap, but not within the same block. Since the attacker controls when the cap is hit, the attack window is attacker-chosen.

### Recommendation
Do not revert on cap breach during deposit. Options consistent with the codebase:
- Cap the minted deposit at `maxTotalSupply - totalSupply` and refund/leave the excess underlying in the `Treasury` (or pull only the accepted amount by computing the allowed amount before `safeTransferFrom` using `quoteDepositIn`-style math plus the Treasury balance-delta pattern already used for fee-on-transfer tokens).
- Alternatively, exempt deposits that decrease the account's projected liquidatable state, or track per-`underlying` TVL caps outside the mint path (mirroring the report's recommendation to control debt emission rather than collateral intake — i.e., keep the cap on `DebtToken.issue`/`mint`/`flashIssue` where it already exists via `SurpassMaxDebtSupply`-style checks, not on collateral deposits).

### Proof of Concept
Foundry/Hardhat fork outline (matches `test/DepositToken.test.ts` setup):

```solidity
// setup: pool with metDepositToken (msdMET), MET underlying, healthy victim alice
// who is near the liquidation threshold on an msUSD debt position.

// 1. Governor-set cap is nearly reached (or attacker fills it):
uint256 cap = metDepositToken.maxTotalSupply();
uint256 headroom = cap - metDepositToken.totalSupply();

// 2. Attacker (EOA) fills remaining headroom:
met.approve(address(metDepositToken), type(uint256).max);
metDepositToken.deposit(headroom, attacker);

// 3. Price of MET drops (or attacker's AMM trade moves MasterOracle quote),
//    making alice liquidatable. Alice tries to rescue:
vm.prank(alice);
vm.expectRevert(DepositToken.SurpassMaxDepositSupply.selector);
metDepositToken.deposit(topUpAmount, alice);

// 4. Liquidator seizes alice's collateral:
pool.liquidate(alice, address(metDebtToken), debtToCover, address(metDepositToken));
// alice loses collateral at liquidation discount despite holding MET to deposit.
```

The revert is confirmed by the existing unit test `should revert if surpass max supply in usd` [3](#0-2) .

*Uncertainty:* I was unable to fully read `Pool.liquidate`/`maxLiquidable` internals before the iteration limit, so the exact seize/fee math is not cited; the deposit-side revert — the core of the analog — is confirmed directly in `DepositToken._mint` and its test.

    function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
