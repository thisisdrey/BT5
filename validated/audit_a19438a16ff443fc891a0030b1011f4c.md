### Title
Unprivileged attacker can brick deposits, withdrawals, and liquidations by filling a target's per-account token list to `MAX_TOKENS_PER_USER` with dust - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks every deposit token and debt token a user holds in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`), and `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once the combined count reaches 30. Anyone can force entries onto an arbitrary account's list: `DepositToken.transfer`/`transferFrom`/`seize` and `deposit(amount_, onBehalfOf_)` all end in `_transfer`/`_mint`, which call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero. A dust transfer of 1 wei of each deposit token to a victim (or to the `feeCollector`) permanently inflates their list. Once a victim is at 30 entries, every path that would add a new token type to their account reverts. Filling the `feeCollector`'s list is worse: protocol fee collection reverts inside `deposit`, `withdraw`, `repay`, and `liquidate`, freezing those functions for all users.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's list when `_recipientBalanceBefore == 0` — there is no opt-in, no minimum amount, and no way for the recipient to refuse. [1](#0-0) 
- `DepositToken.deposit` mints to `onBehalfOf_`, which is attacker-chosen, reaching the same `addToDepositTokensOfAccount` via `_mint`. [2](#0-1) 
- `Pool.onlyIfAdditionWillNotReachMaxTokens` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30 → revert UserReachedMaxTokens`. [3](#0-2) 
- `DepositToken._withdraw` first transfers the fee to `pool.feeCollector()` via `_transfer`, which triggers `addToDepositTokensOfAccount(feeCollector)` if the collector had a zero balance of that token; the call reverts once the collector is at 30. [4](#0-3) 
- `Pool.liquidate` seizes `_fee` to `feeCollector()` through `depositToken_.seize` → `_transfer`, so liquidations with a nonzero protocol fee also revert. [5](#0-4) 
- For an individual victim at the cap: `deposit(onBehalfOf = victim)` reverts (`_mint` → add), `DebtToken.issue`/`mint` reverts when the debt token is new to them (`_mint` → `addToDebtTokensOfAccount`), and any `transfer`/`seize` of a token they don't already hold reverts. [6](#0-5) 

### Impact Explanation
Availability/insolvency. If the attacker saturates `feeCollector`'s list, all `withdraw` calls that charge a `withdrawFee` revert → temporary freezing of user collateral; all `liquidate` calls with `protocolFee > 0` revert → underwater positions cannot be liquidated, which can accrue bad debt and push the pool toward insolvency. If a user is saturated, they cannot open new collateral/debt positions and cannot receive liquidation-seized tokens they don't already hold. The denial persists until the target reduces a balance to zero (which itself requires a successful transfer/withdraw — the feeCollector can sweep/transfer dust out, and a user can still repay and withdraw existing positions, so it is a temporary rather than permanent freeze).

### Likelihood Explanation
The attack is fully unprivileged: any EOA holding small amounts of each registered deposit token calls `transfer(victim, 1)`. The constraint is that only deposit tokens actually registered in the pool can be dusted (debt tokens are non-transferable), so the attacker needs the pool's deposit-token count plus the target's existing entries to reach 30 — or must rely on governance adding tokens over time while the dust sits inert. Filling the `feeCollector` additionally requires a nonzero fee on the bricked path to matter. Cost is dust amounts of each underlying plus gas. No privileged actor, oracle manipulation, or governance misconfiguration is required.

### Recommendation
Remove the forced-list-add on transfers/deposits, or decouple it from a hard revert: e.g., skip adding (or use a try/catch / soft-fail) when the recipient is at `MAX_TOKENS_PER_USER`, and have `debtPositionOf`/rewards treat unlisted balances appropriately. At minimum, exempt `feeCollector` (and other protocol addresses) from the cap, or let fee accounting rely on internal balances rather than the enumerable set. Alternatively cap by checking only on `issue`/position-affecting paths instead of plain ERC20 transfers.

//    - liquidate(...) with protocolFee > 0 reverts with UserReachedMaxTokens
//      (seize(account, feeCollector, fee) reverts), leaving an unhealthy
//      position unliquidatable -> bad debt.
//    - For a saturated victim: deposit(amount, victim) and issue() of a new
//      debt token revert with UserReachedMaxTokens.
//
// Root cause references:
//   Pool.onlyIfAdditionWillNotReachMaxTokens  (Pool.sol:143-148)

Uncertainty to note: the exact feasibility depends on the deployed pool's number of registered deposit tokens (`ReachedMaxDepositTokens` bound) and the target's current token count; on a fork this must be checked against live state before claiming full bricking of `feeCollector`. The victim-blocking variant (blocking deposits/new debt issuance for a chosen account) is reproducible whenever the victim is within `N` slots of the cap.
