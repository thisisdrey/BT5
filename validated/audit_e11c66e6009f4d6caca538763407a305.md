### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract ABI decoding causes OOM/DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The private helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` decode dynamic arrays out of precompiled-contract call data by reading a length word directly from attacker-supplied `DataWord[]` and using it, unchecked, to size a Java array allocation. This is the same bug class as the reported `rardecode` CVE: a size/length field taken from untrusted input controls a memory allocation with no upper bound, enabling an Out-Of-Memory crash.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read `len` via `words[offset].intValueSafe()` and immediately allocate `new byte[len][]` before any bound is enforced: [1](#0-0) [2](#0-1) 
`extractSigArray` follows the same unchecked pattern for signature arrays: [3](#0-2) 

`intValueSafe()` clamps to `Integer.MAX_VALUE` rather than to a sane protocol-defined maximum, so a crafted 32-byte length word (e.g. `0x7fffffff`) yields an attempt to allocate an array of that many `byte[]` references (~16GB of object-array overhead alone, before any element bytes are populated), which throws `OutOfMemoryError`. This is directly analogous to the RAR advisory: the RAR decoder trusted an embedded dictionary-size field without capping it, whereas here the TVM ABI decoder trusts an embedded array-length word without capping it. Contrast this with the sibling `ModExp` precompile in the same file, which explicitly enforces `UPPER_BOUND = 1024` on attacker-supplied lengths before use: [4](#0-3) 
No equivalent bound exists for the array-length fields consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`.

These helpers are used by the shielded/multi-signature precompiled contracts (addresses `0x9`/`0xa` and the shielded-proof precompiles) that are directly reachable by any account: a smart contract can invoke them via a plain `STATICCALL`/`CALL` opcode with attacker-chosen call data, and the `data` byte array passed to `execute()` is the raw calldata the caller supplied to the precompile address.

### Impact Explanation
An `OutOfMemoryError` thrown inside VM execution while processing a transaction can degrade or crash the full node process (or at minimum abort the executing thread/transaction unpredictably depending on how the executor and JVM heap are shared), which matches the CWE-789/DoS class described in the advisory ("node crash or halt"). This is reachable by any account able to deploy or call a contract that forwards crafted calldata to the affected precompiled-contract addresses — no special privilege is required.

### Likelihood Explanation
The attack requires only a normal signed transaction invoking a contract that performs a `CALL`/`STATICCALL` to one of the precompiled addresses (e.g. `0x9`/`0xa`) with calldata containing a maliciously large length word at the offset consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`. Because `intValueSafe()` only clamps to `Integer.MAX_VALUE` and there is no bounds check comparable to `ModExp.UPPER_BOUND` prior to allocation, the trigger condition is simple to construct. I was not able to fully confirm, within the indexed context available, whether the energy (gas) charged for these specific precompiles (`BatchValidateSign`/`ValidateMultiSign`) scales with the same length field before the allocation occurs — I could not retrieve the full `getEnergyForData`/`execute` bodies of those two classes in this pass, so it is not fully proven whether an attacker can trigger the huge allocation cheaply or must pay proportional gas first. This uncertainty should be resolved by reviewing those two classes directly, since their energy accounting is not fully covered by the indexed snippets I retrieved.

### Recommendation
Add an explicit upper bound (mirroring `ModExp.UPPER_BOUND`) on the `len` value read in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating `new byte[len][]`, rejecting (returning a failed/false execution result) whenever `len` exceeds a small protocol-defined maximum consistent with the maximum practical size of these arrays (e.g., max signer/signature count). Additionally, verify that any energy cost function for `BatchValidateSign`/`ValidateMultiSign` charges proportionally to the same length field prior to allocation, so gas cost cannot be decoupled from allocation size.

### Proof of Concept
1. Deploy a contract that performs a `staticcall`/`call` to precompiled address `0x9` (`BatchValidateSign`) or `0xa` (`ValidateMultiSign`).
2. Construct calldata such that the 32-byte word read by `words[offset].intValueSafe()` (the array length prefix consumed by `extractBytesArray`/`extractSigArray`) is set to a very large value (e.g. `0x7fffffff`).
3. Broadcast a transaction invoking this contract call.
4. During TVM execution, `PrecompiledContracts.extractBytesArray`/`extractSigArray` allocates `new byte[len][]`, causing an `OutOfMemoryError` inside the node process handling the transaction. [5](#0-4)

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
