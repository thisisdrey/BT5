### Title
Dust-mint griefing fills `depositTokensOfAccount` of the feeCollector/SmartFarmingManager, reverting all subsequent `DepositToken.deposit` mints — (File: contracts/DepositToken.sol)

### Summary
`DepositToken._mint` and `_transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient)` whenever a recipient's balance goes from 0 to >0. That call enforces `MAX_TOKENS_PER_USER` via `onlyIfAdditionWillNotReachMaxTokens` and reverts once the recipient's per-account set is full. Because `deposit(amount_, onBehalfOf_)` lets any caller mint msdTOKENs to an arbitrary beneficiary, an unprivileged attacker can fill the `depositTokensOfAccount` sets of privileged receivers — most importantly `pool.feeCollector()`, which receives a `_fee` mint inside every `deposit` when `depositFee() > 0` — causing deposits of any collateral type not already in the fee collector's list to permanently revert.

### Finding Description
Relevant code paths:

- `DepositToken.deposit` mints fees to the pool's fee collector and the net amount to `onBehalfOf_`:

```solidity
// contracts/DepositToken.sol
(_deposited, _fee) = quoteDepositOut(amount_);
if (_fee > 0) {
    _mint(_pool.feeCollector(), _fee);
}
_mint(onBehalfOf_, _deposited);
```

- `_mint` (and `_transfer`/`seize`) registers the token on the recipient when their balance was zero:

```solidity
// contracts/DepositToken.sol
if (_balanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(account_);
}
```

- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)` and reverts when the account's `MappedEnumerableSet` is at `MAX_TOKENS_PER_USER`:

```solidity
// contracts/Pool.sol
function addToDepositTokensOfAccount(address account_) external onlyIfAdditionWillNotReachMaxTokens(account_) {
    address _depositToken = _msgSender();
    _revertIfSenderIsNotDepositToken(_depositToken);
    if (!depositTokensOfAccount.add(account_, _depositToken)) revert DepositTokenAlreadyExists();
}
```

Attack sequence (unprivileged EOA, no privileged role needed):

1. For every registered `DepositToken` in the pool, attacker calls `deposit(dust, onBehalfOf_ = feeCollector)` (or `transfer(feeCollector, 1)` after depositing to themselves) until `depositTokensOfAccount.length(feeCollector) == MAX_TOKENS_PER_USER`. Cost is dust-sized underlying amounts.
2. Any subsequent `deposit`/`_mint` involving a deposit token not already in the fee collector's set reverts inside `addToDepositTokensOfAccount` — before this, the whole transaction reverts and no depositor can use that collateral type.
3. The identical attack applies to `SmartFarmingManager`, which receives `flashWithdraw`/`withdrawFrom` mints and leverage deposits on behalf of users; and to any individual victim, whose ability to receive a new collateral type via `transfer`, `seize` (liquidation payout), or `deposit` is blocked while their list is full.

Modifiers do not prevent this: `deposit` is `nonReentrant`/`whenNotPaused` only, `onlyIfDepositTokenExists` checks the token not the beneficiary, and there is no opt-in mechanism for receiving msdTOKENs. `TreasuryCanNotDeposit` only blocks the treasury as sender, not as beneficiary.

### Impact Explanation
When `depositFee() > 0`, depositing into any collateral type whose msdTOKEN is absent from the fee collector's set always reverts — a protocol-wide denial of service for that collateral. Against `SmartFarmingManager`, new leverage/deposit flows for collateral types it does not already hold revert, blocking user position management. For individual victims, inbound `seize` proceeds during liquidation can be forced to fail for collateral types outside their set. If the targeted recipient is a contract without a path to reduce a dust balance to zero (`_transfer`/`_burn` to empty the slot), the freeze is permanent; if it is an EOA/multisig that can transfer the dust out, it is a temporary freeze requiring manual intervention. This maps to the CVE's class: an open/public entry point (unrestricted beneficiary registration) that crashes core functionality.

### Likelihood Explanation
Requires only dust amounts of each underlying across the pool's registered deposit tokens (bounded by `MAX_TOKENS_PER_USER`), a standard deposit fee > 0 configuration, and no privileged role. The attacker is a plain EOA calling `deposit`. Exploitability depends on the deployed `depositFee` and `MAX_TOKENS_PER_USER` values and on whether `feeCollector`/`SmartFarmingManager` can empty a dust balance — I was unable to confirm those deployed configuration values or a sweep/transfer path on `SmartFarmingManager` within the indexed code, which determines whether the freeze is temporary or permanent.

### Recommendation
- Track per-account token-list membership only for accounts that opt in, or decouple collateral accounting from the enumerable set so mints/transfers cannot be made to revert by a full set.
- Skip `addToDepositTokensOfAccount` for fee-collector mints, or allow set membership to exceed the cap for protocol-internal recipients.
- Add a permissionless "remove token from my set" escape hatch so a griefed account (including contracts) can always free slots by zeroing a balance.

### Proof of Concept
Hardhat-style reproduction outline (requires a fork or fixture pool with `depositFee > 0` and at least two deposit tokens):

```ts
// Setup: pool with depositTokens [msdA, msdB, ...], depositFee > 0,
// feeCollector = await pool.feeCollector()
// Attacker fills the feeCollector's per-account set:
for (const dt of allDepositTokens) {
  const underlying = await ethers.getContractAt("IERC20", await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, DUST_GROSS);
  // deposit() measures received amount by treasury balance delta and mints to onBehalfOf_
  await dt.connect(attacker).deposit(DUST, feeCollector);
}
assert(
  (await pool.depositTokensOfAccount(feeCollector)).length ===
  (await pool.MAX_TOKENS_PER_USER()) // conceptual: set is now full
);

// A deposit token NOT yet in feeCollector's set (or a newly added collateral)
// now reverts for every depositor:
await expect(
  msdNew.connect(victim).deposit(amount, victim.address)
).to.be.reverted; // addToDepositTokensOfAccount -> MaxTokensPerUserReached

// Same attack against SmartFarmingManager:
for (const dt of allDepositTokens) {
  await dt.connect(attacker).deposit(DUST, smartFarmingManager.address);
}
// subsequent leverage/flashRepay deposits into tokens SFM didn't already hold revert.
```

Equivalent variant via `transfer(victim, 1)` dust fills any victim's set so that `deposit` into a new collateral type, `seize` proceeds, and `transfer` receipts all revert until a slot is freed.

A fork test against a live deployment should additionally assert `feeProvider.depositFee() > 0`, read the real `MAX_TOKENS_PER_USER` cap, and verify whether `feeCollector`/`SmartFarmingManager` can clear a dust slot (determines permanent vs. temporary freeze).
