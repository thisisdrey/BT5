### Title
Unauthenticated `RecvError` message allows any off-path attacker to force-close and evict an established tunnel - (File: outside.go)

### Summary
`RecvError` is processed as an unencrypted, pre-authentication packet type. `Interface.handleRecvError` tears down an active, established tunnel (`closeTunnel` + `handshakeManager.DeleteHostInfo`) based solely on a 32-bit index taken from the cleartext packet header and a source-address heuristic — with no certificate, no CA verification, and no cryptographic proof that the sender is the actual remote peer. This mirrors the `assertGovernanceApproved` bug class: a function that has real, destructive side effects on another party's state is reachable by anyone without access control, because the only "authorization" check is easily bypassed or simply absent.

### Finding Description
In `outside.go`, `readOutsidePackets` routes `header.RecvError` directly to `f.handleRecvError` before any hostinfo/ConnectionState lookup or decryption is required: [1](#0-0) 

`handleRecvError` then does the following: [2](#0-1) 

The only gating checks are:
1. `f.acceptRecvErrorConfig.ShouldRecvError(addr)` — an address-based allow/deny policy, not a cryptographic authentication check.
2. `hr.IsValid() && hr != addr` — this only rejects the spoofed `RecvError` if the target hostinfo already has a *known* remote address that differs from the spoofed source. If `hr` is not yet valid (e.g., a fresh/roaming tunnel), or if the attacker sends the packet with the source address matching (or spoofs) the real peer's `hr`, the check is bypassed entirely.

Crucially, `h.RemoteIndex` (the 32-bit index used to look up the victim's hostinfo via `hostMap.QueryReverseIndex`) travels in the cleartext header of every packet on the wire (see `header.Encode`/`header.H`), so any attacker capable of observing traffic between two nebula nodes — or simply guessing/brute-forcing the 32-bit index — can learn or forge it without ever possessing a CA-signed certificate or completing a handshake. Combined with UDP's lack of source-address authentication, an attacker can spoof the source UDP address to match the real peer's known remote, defeating the `hr != addr` check, and force `closeTunnel` to tear down a fully established, encrypted tunnel between two legitimate peers.

This is structurally the same defect pattern as the reported bug: a state-mutating function (`closeTunnel`/`DeleteHostInfo`, analogous to the fund-locking `assertGovernanceApproved`) is invoked based on attacker-supplied, unauthenticated input (`sender`/`target` in the original; `RemoteIndex`/spoofed source address here) with no proper access control tying the caller to the actual party who should be allowed to trigger it.

### Impact Explanation
An attacker with no valid certificate can force termination of any active nebula tunnel they can identify by (spoofed source address, remote index), causing:
- Repeated denial-of-service against arbitrary tunnels (the tunnel is deleted from both the main hostmap and the pending handshake map, forcing a full re-handshake).
- Amplified impact if the attacker can send `RecvError` at scale/on-path, effectively locking legitimate peers out of their sessions repeatedly, similar in nature to how the original report caused funds to be "locked" against the victim's will with no interaction required from the victim.
- If the attacker is on-path (can observe the cleartext header), no cert or handshake participation is needed at all to learn the exact `RemoteIndex`, making the attack trivially reliable.

### Likelihood Explanation
- `RecvError` handling is reachable by any UDP sender, unauthenticated, since it is processed prior to any hostinfo/ConnectionState/cert check in `readOutsidePackets`.
- `RemoteIndex` is unencrypted in every packet header, so any on-path observer trivially obtains valid indices for active tunnels.
- The `hr != addr` guard is bypassable when `hr` is not yet set or when the source address is spoofed to match the legitimate remote (UDP has no source-address authentication).
- The remaining protection, `acceptRecvErrorConfig.ShouldRecvError`, is a configurable network/CIDR policy, not an identity/cert-based check, and per the CHANGELOG this control exists purely to bound information disclosure/DoS risk, not to authenticate the sender.

### Recommendation
- Do not allow `RecvError` to trigger `closeTunnel`/`DeleteHostInfo` based on unauthenticated data alone. At minimum, require the `hr.IsValid()` case to be mandatory (never allow a bypass on a "unset remote" hostinfo), and prefer requiring a matching packet counter/nonce or a MAC binding the `RecvError` to a value only the real peer’s key material could produce.
- Consider signing/authenticating `RecvError` similarly to how encrypted `Message`/`Test` packets are handled, or gating destructive actions on it behind stronger correlation (e.g., only accept `RecvError` shortly after we sent an outbound packet to that exact `(addr, index)` tuple, and rate-limit/back off per source).
- Treat any state-mutating handler reachable pre-authentication with the same suspicion as an unauthenticated `transferFrom`: verify the caller/sender is cryptographically tied to the object being mutated before acting.

### Proof of Concept
1. Alice and Bob establish a nebula tunnel; Alice's UDP `remoteIndexId` for the tunnel with Bob is visible in the cleartext header of every packet Bob sends her (`h.RemoteIndex`).
2. Attacker Mallory, positioned to observe (or infer) this traffic, crafts a `RecvError` packet: `header.Encode(..., header.RecvError, 0, aliceRemoteIndexForBob, 0)` and sends it to Alice's UDP endpoint, spoofing the source address as Bob's known address (or timing the attack for a tunnel state where `hr` is not yet set, e.g., right after a roam).
3. `readOutsidePackets` routes this straight to `f.handleRecvError(via.UdpAddr, h)` without requiring any certificate or handshake.
4. `handleRecvError` finds Alice's hostinfo via `QueryReverseIndex`, the `hr != addr` check passes (spoofed or unset), and it calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the legitimate Alice↔Bob tunnel without either party's consent. [2](#0-1)

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
