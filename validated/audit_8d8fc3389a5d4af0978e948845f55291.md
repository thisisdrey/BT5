Based on extensive investigation, this Solidity report's root cause—accepting a caller-declared "amount"/value without verifying it against what was actually transferred, allowing surplus theft or shortfall loss—does not have a matching unguarded analog in this Go repository. Every place in `net/http` (and HTTP/2) where a declared length (Content-Length) could diverge from actual bytes transferred is explicitly checked and rejected:

- Server writes: `response.write` rejects writes exceeding the declared `contentLength` with `ErrContentLength` [1](#0-0) , and the same invariant is enforced for `ReadFrom`/sendfile paths [2](#0-1) .
- HTTP/2 server response writer rejects writes beyond `sentContentLen` [3](#0-2) .
- Client-side request/response body writer (`transferWriter.writeBody`) verifies the actual copied byte count equals the declared `ContentLength` and errors otherwise [4](#0-3) .
- HTTP/2 server request-body ingestion (`processData`) explicitly checks the sum of DATA frame bytes against the declared Content-Length both mid-stream and at stream end, closing the body with an error on mismatch in either direction [5](#0-4) [6](#0-5) .
- `transferReader.determineBodyLength` treats Transfer-Encoding/Content-Length ambiguity as a hard error specifically to prevent request-smuggling-class issues, which is the closest conceptual analog to "declared amount not matching actual value" [7](#0-6) .

There is no equivalent code path in scope where a declared quantity is silently trusted, forwarded, and acted upon without validation against the actual data/value received — the pattern the Solidity report describes. I did not find a reachable, unguarded analog to report.
