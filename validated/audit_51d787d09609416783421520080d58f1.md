### Title
Signature Malleability Enables Multisig Weight Double-Counting in `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x…0a`) computes a permission's total signing weight by iterating over caller-supplied signatures, recovering each signer's address via `SignUtils.signatureToAddress`/`ECKey.recoverPubBytesFromSignature`, and summing per-key weights until the permission threshold is reached. The de-duplication logic that is supposed to prevent one key from being counted more than once keys off the exact raw signature bytes (`address‖rawSig`) instead of the recovered address alone. Because `ECKey.ECDSASignature.validateComponents()` does not enforce the canonical low-S form (it only checks `1 ≤ r,s < SECP256K1N`, unlike `toCanonicalised()` which exists but is never invoked in the verification path), any valid signature `(r, s)` has a second, distinct-byte, equally-valid signature `(r, n-s)` for the exact same message and signer, recoverable to the same address. This lets a single authorized key contribute its weight more than once toward the multisig threshold. [1](#0-0) [2](#0-1) 

### Finding Description
`ValidateMultiSign.execute()` loops over the supplied signature array, recovers each signer address, and only skips weight accumulation when the *exact* `(recoveredAddr, rawSignature)` pair was already seen — if the address was seen before but the raw signature bytes differ, it falls through to `TransactionCapsule.getWeight(...)` and adds the weight again instead of skipping: [3](#0-2) 

The address recovery relies on `recoverAddrBySign`, which builds the signature via `SignUtils.fromComponents` and only gates on `signature.validateComponents()`: [4](#0-3) 

`validateComponents()` is the java-tron analog of the external report's `crypto.SigToPub`/`Ecrecover` path — it recovers a public key/address from a signature but does not reject the malleable high-S counterpart before use: [1](#0-0) 

Given one legitimately obtained valid signature `sigA = (r, s, v)` from an authorized key, anyone (not just the key holder) can locally compute the malleable variant `sigB = (r, n-s, v')` — this only needs public curve parameters, no private key material. `sigA` and `sigB` are two different byte strings that both recover to the *same* address for the *same* message hash. Submitting both to `ValidateMultiSign` causes the per-key weight to be added twice, since the dedup check only short-circuits on exact raw-signature match, not on recovered-address match.

### Impact Explanation
`ValidateMultiSign` is a public, permission-checking precompile that any TVM contract (custom multisig wallets, exchange/withdrawal contracts, DAO/governance contracts built on TRON) can call to gate privileged operations behind an N-of-M threshold. By exploiting the malleability gap, an attacker who controls a single authorized key (whose weight alone is below the required threshold) can synthesize a second "distinct" valid signature for that same key and have the precompile report the threshold as satisfied, even though only one real distinct signer actually participated. Any contract logic that trusts `ValidateMultiSign`'s boolean result as proof of multi-party authorization can be bypassed, leading to unauthorized execution of the gated account operation (e.g., unauthorized fund transfer or privileged state change) — a concrete unauthorized-account-operation / theft-of-funds scenario for contracts relying on this on-chain multisig primitive.

### Likelihood Explanation
Reachable by any contract deployer or caller since `ValidateMultiSign` is invoked directly at a fixed precompile address with attacker-controlled `rawData` (address, permissionId, data, and the signature array). No special privilege is needed beyond already possessing one authorized signature over the message being validated — the malleable counterpart is derivable purely from public parameters (`n - s`), not from any secret. This is Medium-High likelihood for any smart contract that leans on `ValidateMultiSign` for threshold-based authorization.

### Recommendation
1. Fix the de-duplication logic in `ValidateMultiSign` (and the analogous `BatchValidateSign`) to key strictly on the **recovered address**, not on `(address, rawSignature)` — i.e., `continue`/skip weight accumulation whenever `recoveredAddr` has already been counted, regardless of whether the raw signature bytes differ.
2. Additionally, enforce canonical (low-S) signatures in `ECKey.ECDSASignature.validateComponents()` (or invoke `toCanonicalised()` and reject non-canonical inputs) before using a signature for any weight/permission decision, mirroring the external report's recommendation to validate signature "minimal standards" prior to public-key/address recovery.

### Proof of Concept
1. Generate `key1` with weight `W1 < threshold` in an account's Active permission (e.g., `threshold=2`, `key1.weight=1`, `key2.weight=1`, as in the existing `ValidateMultiSignContractTest`).
2. Sign the message hash once with `key1` to obtain `sigA = (r, s, v)`.
3. Compute the malleable counterpart `sigB = (r, CURVE.getN().subtract(s), v')` (flip `v` parity accordingly) — no private key needed, only public curve order `n`.
4. Call the `ValidateMultiSign` precompile with `signatures = [sigA, sigB]` (never providing `key2`'s signature).
5. Because `recoverAddrBySign(sigA, hash)` and `recoverAddrBySign(sigB, hash)` both recover `key1`'s address, but the exact-byte dedup check (`ByteArray.matrixContains(executedSignList, sign)`) fails to match (different raw bytes), the loop adds `key1`'s weight twice, `totalWeight` reaches `threshold=2`, and the precompile returns `DataWord.ONE()` (success) despite only one real distinct authorized signer having participated.   private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
