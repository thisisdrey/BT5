## Analysis: Unbounded array allocation in `ValidateMultiSign` precompile (`extractBytesArray`) [1](#0-0) 

### Title
Uncontrolled Resource Consumption via attacker-controlled array allocation in `ValidateMultiSign` precompiled contract - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract parses an attacker-supplied ABI word as an array length and immediately allocates a Java array of that size before any bound is enforced, mirroring the `nimiq-network-libp2p` Discovery-message pattern where an unvalidated peer-supplied length field drives an unbounded allocation.

### Finding Description
`ValidateMultiSign.execute()` reads the signature-array offset word from call data and, when `VMConfig.allowTvmSelfdestructRestriction()` is **not** active, calls `extractBytesArray` directly with no size check: [2](#0-1) 

`extractBytesArray` takes `len = words[offset].intValueSafe()` — a value fully controlled by the caller's call data — and allocates `new byte[len][]` before doing any range/size validation: [1](#0-0) 

`intValueSafe()` clamps only to `int` range, so `len` can be crafted up to `Integer.MAX_VALUE` (~2.1 billion). Allocating a `byte[][]` of that size allocates ~8–17 GB of reference slots on a 64-bit JVM (4 or 8 bytes per null reference depending on compressed-oops), which can trigger an immediate `OutOfMemoryError` on the node executing the transaction.

The size guard (`MAX_SIZE = 5`) that would normally reject an oversized signature array is only applied on the newer code path that calls `extractSigArray`, gated behind `VMConfig.allowTvmSelfdestructRestriction()`: [3](#0-2) 

When that hard-fork flag is disabled (e.g., on networks/chains where this proposal hasn't been activated, or during any period before activation), the legacy `extractBytesArray` branch is reached with no equivalent pre-allocation check — the length is used to size the array immediately, exactly like the CVE's unbounded `Discovery` buffer allocation from an untrusted peer-supplied length.

Additionally, the ABI-encoding sanity check (`isValidAbiEncoding`) that could catch malformed/oversized inputs is itself gated behind `VMConfig.allowTvmOsaka()`: [4](#0-3) 

so on any chain configuration lacking that later feature flag, no upstream validation limits the crafted length before it reaches `extractBytesArray`.

### Impact Explanation
Any account (unprivileged) can construct a smart contract call whose calldata invokes the `ValidateMultiSign` precompile with a crafted word specifying an enormous array length. The resulting single-transaction call can force the node's TVM executor to attempt an outsized array allocation, throwing `OutOfMemoryError`/triggering GC pressure and potentially crashing or stalling the JVM node process — a node availability/DoS impact reachable from ordinary contract execution, consistent with "node crash or halt" in the accepted impact categories.

### Likelihood Explanation
Exploitability requires only deploying/calling a contract (or crafting a raw `TriggerSmartContract`) that performs a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address with attacker-chosen calldata — no special privileges, keys, or SR/witness status needed. Whether this is exploitable in the currently deployed network configuration depends entirely on whether `allowTvmSelfdestructRestriction` (and separately `allowTvmOsaka`) is enabled on that chain/fork; on any deployment where that flag is off, the vulnerable path is directly reachable.

### Recommendation
Move the `MAX_SIZE` (and general non-negative/bounded) check on the parsed array length ahead of the `extractBytesArray`/`extractSigArray` call regardless of the `allowTvmSelfdestructRestriction` flag, and add an explicit upper bound check inside `extractBytesArray` and `extractBytes32Array` before allocating `new byte[len][]`, rejecting the call (returning `Pair.of(false/true, DATA_FALSE)`) when `len` exceeds a small sane constant (e.g., `MAX_SIZE`) or when `len` would exceed the remaining `words.length`.

### Proof of Concept
1. Craft calldata for the `ValidateMultiSign` precompile (`address`, `permissionId`, `data` hash-input, and a signature-array offset word) such that the word at the computed array-offset slot encodes a very large 32-byte integer (e.g., `0x7FFFFFFF`).
2. Submit a `TriggerSmartContract` transaction (or a contract that internally calls the precompile) invoking this precompile with the crafted calldata, on a network/build where `allowTvmSelfdestructRestriction` (and/or `allowTvmOsaka`) is not enabled.
3. `ValidateMultiSign.execute()` reaches `extractBytesArray(words, offset, rawData)`, which executes `byte[][] bytesArray = new byte[len][]` with the attacker-supplied `len`, causing excessive memory allocation on the executing node. [5](#0-4)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
