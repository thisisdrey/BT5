Based on my research, the closest reachable analog to this ImageMagick heap-buffer-over-read (a length/offset field taken from untrusted input and used to index a buffer without validating it stays within bounds) is the ABI array-extraction helpers in the TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign`, reachable directly from a signed transaction's contract call.

### Title
Unvalidated ABI offset/length fields in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` allow out-of-bounds array access from TVM contract calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` compute `bytesOffset`/`bytesLen` directly from attacker-supplied `DataWord` words in the calldata sent to the `ValidateMultiSign` (address `0x66...`) and `BatchValidateSign` precompiles, and pass them straight into `extractBytes`, which does `Arrays.copyOfRange(data, offset, offset + len)` with no bound check against `data.length`. [1](#0-0) 

### Finding Description
`extractBytesArray`/`extractSigArray` derive `bytesOffset` and `bytesLen` from `words[offset + i + 1].intValueSafe()` — fully attacker-controlled 256-bit words truncated to `int` — and then call `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)`, which performs `Arrays.copyOfRange(data, offset, offset + len)` with no check that `offset >= 0`, `len >= 0`, or `offset + len <= data.length`. [1](#0-0) 

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` before either method's inner `try { ... } catch (Throwable t)` block is entered — the extraction call happens at the top of `execute()`, and the surrounding try/catch only wraps the later permission-weight logic, so an `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` thrown by `Arrays.copyOfRange` during extraction is not caught inside these actuator methods. [2](#0-1) [3](#0-2) 

There is a partial fix path guarded by `VMConfig.allowTvmOsaka()`: when that TIP-854 hard-fork flag is active, `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` rejects malformed calldata shapes up front and returns `(false, EMPTY_BYTE_ARRAY)` instead of reaching the vulnerable extraction path. [4](#0-3) [5](#0-4) 

However, the test suite explicitly documents that before `allowTvmOsaka` activation the legacy decoder path is left unguarded and can throw an uncaught `RuntimeException` — this is called out as "the existing behaviour" that TIP-854 "explicitly preserves" for the pre-activation case, meaning any deployment/chain state where this hard fork bit is not yet turned on remains exposed to attacker-triggered `Arrays.copyOfRange` bound violations from raw ABI words. [6](#0-5) 

### Impact Explanation
If the exception thrown by `extractBytes`'s `Arrays.copyOfRange` during precompile execution is not caught anywhere higher in the TVM call/opcode dispatch chain (e.g., in `OperationActions.java` / `Program.java`), a single crafted transaction calling `ValidateMultiSign` or `BatchValidateSign` with out-of-range offset/length words can propagate an uncaught runtime exception out of contract execution, on both full nodes and SRs that must all execute the same transaction deterministically — i.e., a potential node crash/halt or, if execution differs between constant-call and block-application/thread-pool contexts (`BatchValidateSign` executes signature recovery through an `ExecutorService`), a possible chain-processing inconsistency. I was **not able to fully verify** whether the TVM call opcode implementation (`OperationActions.java`/`Program.java`) wraps precompiled-contract `execute()` invocations in a catch-all `Throwable`/`RuntimeException` handler that would downgrade this to a normal REVERT rather than an unhandled crash — my search located only single references to `PrecompiledContract`/`callToPrecompiledAddress`-equivalent code in these files but I ran out of iterations before reading their contents. This uncertainty should be resolved before treating impact as confirmed at "node crash" severity; if such a catch-all exists, the practical impact is limited to a reverted transaction (low severity, out of scope per the rules), not a crash.

### Likelihood Explanation
Both precompiles are reachable by any account issuing a normal signed `TriggerSmartContract` transaction that calls the fixed precompile addresses with crafted calldata — no special privilege, SR/witness role, or network position is required. Constructing calldata with an out-of-range offset/length word is straightforward arithmetic (as demonstrated by the existing `TIP-854`-focused unit tests that already probe malformed-length edge cases in this exact code). [7](#0-6) 

### Recommendation
Apply the same `isValidAbiEncoding` (or equivalent explicit bounds validation on every `bytesOffset`/`bytesLen` derived from calldata) unconditionally in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` (or in `extractBytes` itself), rather than gating it behind `VMConfig.allowTvmOsaka()`/`allowTvmSelfdestructRestriction()`, so pre-activation nodes are not exposed. Additionally, verify and, if missing, add a catch-all boundary around precompiled-contract `execute()` invocation in the TVM call opcode handling so any residual parsing exception degrades to a REVERT instead of an unhandled exception.

### Proof of Concept
1. Issue a `TriggerSmartContract` transaction whose `data` targets the `ValidateMultiSign` precompile address.
2. Encode the calldata so that `words[3]` (the offset word for the signature array) decodes, after `/WORD_SIZE`, to a value such that `words[offset+1]` (the declared array length) combined with the computed `bytesOffset`/`bytesLen` for an element makes `(bytesOffset + offset + 2) * WORD_SIZE + bytesLen` exceed `rawData.length`, or makes `bytesLen` negative.
3. Send the transaction; on a node where `allowTvmOsaka` (TIP-854) is not yet activated, `extractBytesArray`/`extractBytes` is reached at [8](#0-7) 
before the actuator's own try/catch, and `Arrays.copyOfRange(data, offset, offset + len)` throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` uncaught within `execute()`. [9](#0-8) 

**Note on confidence**: I could not confirm within the available tool budget whether this exception is ultimately caught by a higher-level TVM dispatch handler (in `OperationActions.java`/`Program.java`), which would reduce this to a simple revert rather than a node-impacting crash. This should be verified directly in those files before treating the "node crash/halt" impact rating as confirmed.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,

    }
