### Title
`LinkRepositoryToObjectPool` performs no verification that the object pool actually belongs to the target repository's fork network, allowing cross-repository object disclosure — ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The bug class in the ZeroLend report is a missing ownership/relationship check: `split()` lets a caller supply an arbitrary `tokenId` belonging to someone else and mint themselves a token carrying that token's value, because the contract never verifies `msg.sender` actually owns the `tokenId`. The Gitaly analog is `ObjectPoolService.LinkRepositoryToObjectPool`, which lets a caller supply an arbitrary, unrelated `object_pool` and have Gitaly link it as a Git alternate to the caller-controlled `repository`, without verifying that the pool was ever derived from (or has any relationship to) that repository.

### Finding Description
`LinkRepositoryToObjectPoolRequest` carries two independent repository references — `repository` (annotated `target_repository`) and `object_pool` (annotated `additional_repository`) — see [1](#0-0) . The RPC handler `LinkRepositoryToObjectPool` only validates that `repository` is a well-formed repository and that the pool exists/is valid; it never checks that `object_pool` was created from `repository` or is otherwise associated with it: [2](#0-1) 

The pool-resolution helper `poolForRequest` → `objectpool.FromProto` only confirms the pool directory is a syntactically valid pool path and a valid git repository — it performs no linkage/ownership check against the caller's target repository: [3](#0-2) [4](#0-3) 

`ObjectPool.Link` / `Link()` then simply writes the pool's `objects` directory into the target repository's `info/alternates` file (unless something is already linked to a *different* pool, in which case it errors out, but that is only a consistency check, not an authorization check): [5](#0-4) 

Once linked, every object stored in the object pool becomes transparently readable through the target repository via Git's alternates mechanism (any `git cat-file`/`git clone`/`git fetch` against the target repo can resolve objects that physically live only in the pool). Gitaly's storage-path/locator layer (`ValidateRepository`, `GetRepoPath`) validates that both `repository` and `object_pool` are legitimate repositories *somewhere* in the same storage, but does nothing to verify they are the same fork network — this is exactly the same shape of vulnerability as the `split()` bug: an operation whose safety implicitly assumes the caller has a right to the "other side" of the transaction (owns `tokenId` / owns or forked from `object_pool`), but the code performs no such check at the layer where the sensitive linkage is created.

### Impact Explanation
If an attacker can get Gitaly to execute `LinkRepositoryToObjectPool` with `repository` = a repository the attacker controls and `object_pool` = an arbitrary pool repository (e.g., one they can guess/enumerate the relative path of, since pool paths are derived from content hashes and follow a fixed `@pools/xx/yy/<hash>.git` naming scheme, or one they otherwise learn), all objects contained in that pool — potentially all objects reachable from a private, unrelated repository that was the pool's origin — become directly fetchable from the attacker's own repository. This is a cross-repository object-disclosure primitive: private commits, blobs, and trees from someone else's repository could be exfiltrated by linking to its object pool from an attacker-owned repo and then cloning/fetching it. This matches the "cross-repository object access" acceptance criterion in the validation rules.

### Likelihood Explanation
Exploitability depends on whether an ordinary, unprivileged caller can invoke this RPC with a `object_pool` value they do not otherwise have legitimate access to. In the normal GitLab flow, this RPC is only called internally by GitLab Rails during fork creation with a pool it just derived/knows to be associated with the source project, so exploitation requires either (a) direct/unauthenticated or improperly-scoped access to the Gitaly gRPC endpoint bypassing Rails-level authorization, or (b) an application-level bug in Rails that lets a user supply/influence the `object_pool` relative path for a repository they do not own (e.g., through an IDOR in fork-related endpoints). Because Gitaly itself performs no ownership check and treats this as purely an internal-trust boundary, any weakness upstream (or any direct-gRPC access, e.g. via Praefect's routing which only rewrites paths and does not re-validate the pool relationship, as seen in `internal/praefect/coordinator_test.go`) converts into full cross-repo object disclosure. Given the strict "reject privileged-actor" instruction, this analog is only valid to the extent the RPC is reachable via a crafted RPC field rather than requiring a fully privileged operator — which is the case here since the vulnerable code path itself has zero authorization logic and relies entirely on external correctness.

### Recommendation
Add an explicit relationship check inside `LinkRepositoryToObjectPool` (and ideally `objectpool.Link`) that verifies the object pool being linked was actually created from (or is a recognized member of the fork network of) the target `repository` before writing the alternates file — for example by recording/verifying the pool's origin repository at `CreateObjectPool` time and checking it against the `repository` argument at link time, rather than only checking pool path well-formedness and validity.

### Proof of Concept
Conceptual PoC (cannot be executed without a running Gitaly test environment, but derivable directly from the code paths cited above):
1. Attacker creates repository `A` (owned by them).
2. Attacker learns/guesses the relative path of an object pool `P` created from a *different*, unrelated repository `B` (pool paths are deterministic hash-based paths under `@pools/...`, not access-controlled by relation to `B`).
3. Attacker calls `LinkRepositoryToObjectPool(repository=A, object_pool=P)`. Per `internal/gitaly/service/objectpool/link.go` and `internal/git/objectpool/link.go`, no check is made that `P` originated from `A`; the call succeeds and `A/objects/info/alternates` now points at `P`'s object directory.
4. Attacker runs `git fetch`/`git cat-file` against repository `A`; all objects present in pool `P` (i.e., all objects from repository `B`, since pools contain a full history of their origin repo) are now resolvable and can be exfiltrated through `A`.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

	if err := transaction.CommitLockedFile(ctx, txManager, alternatesWriter); err != nil {
		return fmt.Errorf("committing alternates: %w", err)
	}

	if tx := storage.ExtractTransaction(ctx); tx != nil {
		alternatesRelativePath, err := filepath.Rel(tx.FS().Root(), altPath)
		if err != nil {
			return fmt.Errorf("rel alternates file: %w", err)
		}

		if err := tx.FS().RecordFile(alternatesRelativePath); err != nil {
			return fmt.Errorf("record alternates file")
		}
	}

	return removeMemberBitmaps(ctx, pool, repo)
