### Title
Multi-sig weight double-counting via ECDSA signature malleability in `ValidateMultiSign` precompile allows single-key forgery of multi-party consent - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The external report concerns a MetaMask Snap that could be induced to sign/authorize critical actions without genuine, verifiable multi-party consent. The closest reachable analog in java-tron is the `ValidateMultiSign` TVM precompile, which any smart contract can call (via `STATICCALL`) to check whether a supplied set of signatures meets an account permission's signing threshold. Its de-duplication logic can be bypassed with ECDSA signature malleability, letting a single key-holder's weight be counted multiple times, forging the appearance of independent multi-signer consent.

### Finding Description
`ValidateMultiSign.execute` iterates over the caller-supplied signature array, recovers the signer address for each signature, and accumulates `totalWeight` from the account's `Permission`: [1](#0-0) 

The de-duplication check is flawed: when a `recoveredAddr` has already been seen (`matrixContains(executedSignList, recoveredAddr)` is true), the code only `continue`s (skips adding weight again) if the *exact same encoded signature bytes* (`merge(recoveredAddr, sign)`) were already seen. If the signature bytes differ but recover to the *same address* — which is trivially achievable via ECDSA signature malleability (the pair `(r, s)` and `(r, n-s)` with a flipped recovery id both validly recover to the same public key/address for the same message hash) — the code merely calls `MUtil.checkCPUTime()` and then falls through to add the weight for that address **again**: [2](#0-1) 

`matrixContains` performs a plain byte-array equality check with no semantic awareness of "same signer, different signature encoding": [3](#0-2) 

Because a single private key can trivially generate multiple distinct, valid signatures over the same fixed message hash (the hash is `sha256(address || permissionId || data)`, constant for a given call, see lines 1057-1064), an attacker holding just one signer's key can submit up to `MAX_SIZE` (5) malleated variants of their own signature in the `signatures` array. Each variant recovers to the same address but is treated as an independent signer contribution, so `totalWeight` accumulates multiple times for the same key: [4](#0-3) 

If `totalWeight >= permission.getThreshold()`, the precompile returns "true" (`dataOne()`), signaling that the multi-signature threshold has been satisfied — even though only one real key-holder actually authorized the action: [5](#0-4) 

This mirrors the reported bug class exactly: a critical authorization decision ("does this account's multi-party permission approve this action?") is granted without genuine, independently verifiable consent from the required number of distinct parties — a single party's signature is fraudulently multiplied to simulate consensus.

### Impact Explanation
`ValidateMultiSign` is a general-purpose precompile intended for on-chain smart contracts implementing multisig-wallet, DAO, escrow, or exchange logic that gate privileged operations (e.g., releasing held TRX/TRC10/TRC20 funds, approving withdrawals, executing governance actions) on threshold approval from an account's `Permission` keys. Any contract that relies on this precompile's boolean result to authorize a fund transfer or privileged state change can be tricked by an attacker controlling only one authorized key (e.g., an insider, or an attacker who compromised one of several signer keys) into believing the full threshold of independent signers approved the action. This can lead to unauthorized withdrawal/movement of funds held by such a contract — a concrete theft-of-funds scenario reachable from a single crafted transaction/contract call, satisfying the "unauthorized account operation / theft of funds" bar.

### Likelihood Explanation
The precompile is reachable by any unprivileged account that can deploy or call a smart contract using the corresponding precompiled-contract address — no special privilege, SR/witness role, or network position is required. ECDSA signature malleability is a well-known, deterministic, and computationally trivial operation (flip `s` to `n-s`, flip recovery id) requiring no additional secret material beyond the one valid signature the attacker already possesses. The only "mitigation" present, `MUtil.checkCPUTime()`, is a CPU/time budget guard unrelated to authorization correctness and does not prevent the weight double-count. The `signatures.length <= MAX_SIZE (5)` cap limits the maximum inflation factor to 5×, but for many practical low-threshold multisig configurations (e.g., 1-of-2, 2-of-3, or weighted setups where one key's weight is a large fraction of the threshold) this is sufficient to forge threshold satisfaction.

### Recommendation
Deduplicate accumulated signer weight strictly by `recoveredAddr` (i.e., once an address has contributed weight, unconditionally skip it regardless of the raw signature bytes), rather than by the combination of address + raw signature. Concretely, in `ValidateMultiSign.execute`, when `matrixContains(executedSignList, recoveredAddr)` is true, always `continue` without adding weight again, removing the branch that permits a second, differently-encoded signature from the same address to add weight.

### Proof of Concept
1. Deploy or use an existing smart contract that calls the `ValidateMultiSign` precompile to gate a privileged action for an account whose `Permission` has, e.g., a 2-of-3 (or weighted) key configuration where the attacker controls one key with sufficient weight.
2. The attacker computes `hash = sha256(address || permissionId || data)` per [6](#0-5) .
3. Using their single private key, the attacker signs `hash` and derives a second valid signature via ECDSA malleability (`s' = n - s`, recovery id flipped), producing two distinct 65-byte signatures that both `recoverAddrBySign` to the same address.
4. The attacker submits both signatures (padded to fit within `MAX_SIZE`) as the `signatures` array argument to `ValidateMultiSign`.
5. Per the loop at [1](#0-0) , the second signature is not deduplicated (different raw bytes), so `totalWeight` is credited twice for the same key.
6. If `2 * weight(key) >= permission.getThreshold()`, the precompile returns `true`, and the calling contract executes the privileged/fund-moving action believing that independent multi-party consent was obtained, when in reality only one key ever signed.

(Note: exact byte offsets of the recovery-id field within the 65-byte signature and the specific `recoverAddrBySign` implementation were not fully retrievable from the indexed context; the malleability argument relies on standard secp256k1 ECDSA properties used throughout java-tron's `SignUtils`/`ECKey` signature-recovery code. A live PoC transaction would be needed to confirm the exact byte layout expected by `extractSigArray`/`extractBytesArray`.)
