### Title
StackerDB write-frequency (`write_freq`) rate limit is never enforced on the authenticated write path - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBTx::try_replace_chunk` — the sole function that actually commits a chunk write to a StackerDB slot — validates chunk size, slot existence, signer authenticity, staleness, and `max_writes`, but never checks the contract-configured `write_freq` (minimum wall-clock interval between writes to a slot). This is the exact function invoked by the unauthenticated-but-signed `POST /v2/stackerdb/.../chunks` RPC handler (`poststackerdbchunk.rs`) and by the P2P chunk-storage path (`process_stacker_db_chunks` in `relay.rs`), so any party holding a slot's private key can write to that slot at unlimited frequency regardless of the smart-contract-declared rate limit.

### Finding Description
`StackerDBConfig::write_freq` is populated straight from the StackerDB smart contract's `write-freq` field [1](#0-0) , and is intended to bound how often a slot signer may push a new chunk version — the wire-level analog of "excessive attempts" throttling.

The only place `write_freq` is actually consulted is `StackerDBSync::find_new_chunks`, which uses it purely as a client-side heuristic to decide whether to *fetch* a chunk during a sync round: `if self.write_freq > 0 && write_ts + self.write_freq > now { continue; }` [2](#0-1) . This only skips out-bound fetches; it does nothing to gate what the node accepts when writing.

The actual write/commit function, `StackerDBTx::try_replace_chunk`, performs these checks in order — chunk size, slot existence, signer verification, staleness, `max_writes` — with no `write_freq`/`write_time` comparison anywhere in the function body: [3](#0-2) . The underlying `insert_chunk` helper explicitly documents that authentication and clock-ordering "will not be checked" by it (they are the caller's responsibility), reinforcing that `try_replace_chunk` is supposed to be the complete gate, yet it omits `write_freq` [4](#0-3) .

`validate_received_chunk` (used for downloaded/pushed chunks prior to storage) has an explicit code comment acknowledging the omission: "NOTE: does not check write frequency, since the caller has different ways of doing this" [5](#0-4) . But tracing the "other ways" leads only to the client-side sync throttle above — there is no server-side enforcement at the point of commit.

Both realistic remote write entry points funnel into `try_replace_chunk` without any `write_freq` gate:
- The HTTP RPC handler for a directly-submitted, signed chunk calls `tx.try_replace_chunk` directly [6](#0-5) .
- The P2P relay path that stores chunks obtained from StackerDB sync results also calls `tx.try_replace_chunk` per chunk [7](#0-6) .

A test comment in `tests/db.rs` documents the intended invariant ("verifies that they cannot exceed the config-given wall-clock write frequency") [8](#0-7) , but the accompanying test body only exercises `StaleChunk`, `TooManySlotWrites`, and `BadSlotSigner` errors against `try_replace_chunk` — it never triggers or asserts a `write_freq`-based rejection, because no such error path exists [9](#0-8) . This is consistent with the code inspected: there is no `WriteTooFrequent`/similar variant used by `try_replace_chunk`.

### Impact Explanation
This breaks the equality "committed write rate ≤ contract-declared `write_freq`". A slot owner (a normal, non-privileged StackerDB participant such as a signer in the signer-set StackerDB) can flood a slot with new chunk versions far faster than the contract intends, as long as `slot_version` increases and stays within `max_writes`. Depending on how the StackerDB contents are consumed downstream (e.g., signer coordination messages, miner data), this could be leveraged to spam gossip/broadcast (`process_stacker_db_chunks` re-broadcasts every accepted chunk over `p2p.broadcast_message`) or to exhaust a `max_writes` budget faster than the protocol design assumes, potentially forcing premature StackerDB rotation/exhaustion. Because it only requires bypassing a rate-limit invariant (not forging any signature or writing to another owner's slot), and remains bounded by `max_writes`, this is a bounded compute/bandwidth amplification and protocol-invariant violation on a read/write path reachable by any unprivileged, already-provisioned slot signer — matching the "bounded compute DoS on a read/write endpoint" tier rather than a critical write-authorization bypass.

### Likelihood Explanation
High likelihood of triggerability: the attacker only needs to be a legitimate StackerDB slot owner (e.g., any registered signer, which is not a privileged administrative role) and simply needs to submit chunks with monotonically increasing `slot_version` back-to-back via the standard signed RPC endpoint or P2P chunk push — no cryptographic bypass or race condition is required, since the check is simply absent.

### Recommendation
Add a `write_freq` check in `StackerDBTx::try_replace_chunk` (or in a shared pre-write validation used by all write paths) that compares `now - slot_validation.write_time` against `self.config.write_freq` and rejects (e.g., with a new `WriteTooFrequent` error) writes that arrive before the configured interval has elapsed, mirroring the client-side heuristic already implemented in `StackerDBSync::find_new_chunks`.

### Proof of Concept
1. Configure/observe a StackerDB contract with `write-freq > 0` (e.g., 120 seconds) and `max-writes` large enough (e.g., signer-set StackerDBs).
2. As the legitimate owner of slot `N`, sign and submit chunk version `v` via `POST /v2/stackerdb/<contract>/chunks` (handled by `poststackerdbchunk.rs`, which calls `tx.try_replace_chunk`).
3. Immediately (well under the 120s `write_freq` window) sign and submit chunk version `v+1` for the same slot.
4. Observe that the second write succeeds and is accepted/broadcast, because `try_replace_chunk` (stackslib/src/net/stackerdb/db.rs:398-438) never checks `write_time` against `config.write_freq`; it is rejected only if it is stale, exceeds `max_writes`, or fails signature verification — none of which apply here.
5. Repeat as fast as the network/RPC layer allows (bounded only by `max_writes` and chunk size), confirming the contract's declared write-frequency limit is not enforced.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
