### Title
Unbounded 1-yoctoNEAR "subsidized" balance minting via repeated zero-balance `promise_batch_action_function_call_weight` calls - ([File: runtime/near-vm-runner/src/logic/logic.rs])

### Summary
`promise_batch_action_function_call_weight` allows a contract with `account_balance == 0` to attach exactly 1 yoctoNEAR to an outgoing `FunctionCall` action without deducting it from its balance (`skip_deduct`), instead crediting it to `result_state.subsidized_amount`. The check only inspects the *current* balance and never tracks how many times this subsidy has been granted, and because the balance is never actually decremented when `skip_deduct` fires, the zero-balance precondition remains true for every subsequent call in the same execution, letting an attacker repeat the subsidy across many outgoing promise actions within one receipt.

### Finding Description
In `runtime/near-vm-runner/src/logic/logic.rs`:
```
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self.result_state.subsidized_amount
        .checked_add(amount).expect("subsidized_amount overflow");
} else {
    self.result_state.deduct_balance(amount)?;
}
``` [1](#0-0) 

Because the "else" branch (`deduct_balance`) is the only place the account balance is ever reduced by this function, and it is skipped whenever `skip_deduct` is true, `current_account_balance` stays at zero across the entire lifetime of the guest execution once the precondition is first met. This means the same attacker contract can call `promise_batch_action_function_call_weight` (or the wrapper `promise_batch_action_function_call`) repeatedly against many different `promise_batch_create` targets in a single `FunctionCall` receipt, each time attaching `amount = 1` and each time re-triggering `skip_deduct`, since the zero-balance condition never changes. Each invocation increments `subsidized_amount` by 1 yoctoNEAR, and the resulting outgoing action still carries `amount = 1` which will be credited to the receiver account upon receipt execution, effectively creating value that was never deducted from the sender. The accumulated `subsidized_amount` is propagated back up through `execute_function_call` → `action_function_call` in `runtime/runtime/src/function_call.rs`:
```
result.subsidized_amount = safe_add_balance(result.subsidized_amount, outcome.subsidized_amount)?;
``` [2](#0-1) 

The number of times this can be repeated in one receipt is not bounded by any explicit "use this subsidy once" counter — it is only indirectly limited by generic resource limits (gas cost of `function_call_base`/`function_call_byte`, `max_actions_per_receipt`, `max_promises_per_function_call_action`, and prepaid gas). Those generic limits were designed to bound the number of *actions*, not to bound a token-minting side channel, so the number of "free" 1-yoctoNEAR credits scales with however many function-call actions the attacker can pack into gas/action limits (potentially hundreds), not with a fixed "1 credit per zero-balance account" invariant that the comment implies.

### Impact Explanation
This falls under token inflation / value-conservation violation: an attacker-controlled zero-balance contract can generate an outgoing deposit-bearing action for every "subsidized" call without ever paying for it, and `subsidized_amount` — which is meant to represent a bounded, deliberate protocol subsidy — grows linearly with the number of promise actions the attacker chooses to create in a single receipt, rather than being capped. If `subsidized_amount` is later reconciled against total supply accounting (as its propagation up through `ActionResult`/`chain/chain/src/runtime/mod.rs` suggests), this allows unbacked yoctoNEAR credits to be minted proportional to attacker-chosen action count, not to a fixed per-account/per-call allowance.

### Likelihood Explanation
Preconditions are attacker-reachable with no privileged access: any account can spend its balance down to exactly zero (trivial, e.g., transferring away all NEAR) and then deploy/call its own contract that loops over `promise_batch_create` + `promise_batch_action_function_call_weight(amount=1)` for as many actions as gas and `max_actions_per_receipt`/`max_promises_per_function_call_action` allow. This requires `config.one_yocto_on_promise` to be enabled (a runtime config parameter). The action is fully repeatable across receipts/transactions, and cost to the attacker is only the gas for issuing many function-call actions, not the balance itself, since no NEAR is actually deducted for the subsidized calls.

### Recommendation
Track and enforce a single, protocol-defined limit on how many times the zero-balance one-yocto subsidy may be granted per account/receipt/execution (e.g., a one-shot flag consumed on first use, or accounting the subsidy against a fixed global-config cap), rather than re-evaluating `current_account_balance.is_zero()` on every call without ever decrementing it. Alternatively, deduct the 1 yoctoNEAR from a virtual/subsidy ledger that is itself bounded, or only allow the subsidy once per receipt/execution context.

### Proof of Concept
Integration test (in the vm-logic promise test suite, e.g. `runtime/near-vm-runner/src/logic/tests/promises.rs`):
1. Deploy a contract with `account_balance = 0` and `config.one_yocto_on_promise = true`.
2. In a single `FunctionCall`, loop `N = max_promises_per_function_call_action` (or however many fit under `max_actions_per_receipt`/prepaid gas) times, each iteration calling `promise_batch_create(victim_account)` then `promise_batch_action_function_call_weight(..., amount=1, ...)`.
3. Assert that `outcome.subsidized_amount == N` (i.e., unbounded growth with N) rather than being capped at a fixed protocol-intended value (e.g., `1`).
4. Cross-check against `RuntimeGroup`'s global balance invariant (`runtime/runtime/src/tests/apply.rs` uses `subsidized_amount`) to show total system balance increases by `N` yoctoNEAR with no corresponding deduction anywhere, violating conservation.
