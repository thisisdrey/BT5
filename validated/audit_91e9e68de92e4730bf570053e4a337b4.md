### Title
Failed batched `storage_deposit` on a malicious FT permanently strands unwrapped wNEAR with no re-credit path - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
When `FtWithdraw.storage_deposit` is set, `internal_ft_withdraw` debits the signer's wNEAR balance for the storage deposit and unwraps it to raw NEAR, then attaches it to a `storage_deposit` action batched in the *same receipt* as the `ft_transfer`/`ft_transfer_call` action targeting the attacker-controlled `withdraw.token`. If `storage_deposit` panics, the whole receipt fails atomically, the unwrapped NEAR is refunded by the NEAR runtime to the Defuse contract's own account balance (not to the signer), and `ft_resolve_withdraw` only ever re-credits the FT `amount` — never the wNEAR `storage_deposit` amount — permanently losing the signer's wNEAR from the ledger.

### Finding Description
The broken binding: wNEAR debited from signer's `token_balances` for `storage_deposit` should equal NEAR either delivered into `withdraw.token`'s storage balance or re-credited to the signer on failure. In the exploit, debited = `storage_deposit` (e.g. 1 NEAR), delivered = 0, re-credited = 0.

Code path:
- `internal_ft_withdraw` ( [1](#0-0) ) debits both the FT `amount` and the wNEAR `storage_deposit` amount from the signer up front via `self.withdraw(...)`, unconditionally of what happens downstream.
- It then calls `near_withdraw` to unwrap wNEAR into raw NEAR and, via `.then()`, invokes `do_ft_withdraw` ( [2](#0-1) ).
- `do_ft_withdraw` builds the `storage_deposit` call on `withdraw.token` and chains `ft_transfer`/`ft_transfer_call` onto the *same* `Promise` object via `ext_ft_core::ext_on(p)` ( [3](#0-2) ). `ext_on` appends actions to the existing promise/receipt rather than creating an independent async callback — this same pattern is explicitly documented elsewhere in the repo as running "in the same receipt" ( [4](#0-3) ). Consequently `storage_deposit` and `ft_transfer(_call)` are batched actions in one receipt sent to the attacker's FT contract.
- Per NEAR runtime semantics, if any action within a receipt fails (a panicking `storage_deposit`), the entire receipt fails atomically: `ft_transfer`/`ft_transfer_call` never executes, and the NEAR attached to the failed `storage_deposit` action (line 127, `.with_attached_deposit(storage_deposit)`) is refunded by the protocol back to the predecessor — the Defuse contract's own account — not to the signer's Verifier balance.
- `ft_resolve_withdraw` only inspects promise index 0's aggregate result and only ever re-credits the FT `token`/`amount` ( [5](#0-4) ); there is no code path anywhere that re-credits `storage_deposit`/wNEAR regardless of whether the batched receipt succeeded or failed.

Attacker's exact payload: sign `FtWithdraw { token: <attacker-controlled FT with panicking storage_deposit>, receiver_id, amount, storage_deposit: Some(NearToken::from_near(1)), msg: None, min_gas: None }` and submit via `execute_intents`, holding `amount` of that FT and ≥1 NEAR of wNEAR in the Verifier beforehand.

Existing guards do not prevent this: `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")` only checks that `near_withdraw` itself succeeded before attempting `storage_deposit`; it does nothing to protect against `storage_deposit`'s own failure. `ft_resolve_withdraw`'s refund logic is scoped only to the FT `amount`/`token`, never to wNEAR.

### Impact Explanation
The signer's own wNEAR balance inside the Verifier is permanently and irrecoverably reduced by the `storage_deposit` amount, while the corresponding raw NEAR ends up stuck in the Defuse contract's own account balance, invisible to the internal `token_balances` ledger and unreachable by any user-facing recovery path. This matches the "user funds permanently frozen" Critical impact category. The bug is repeatable per withdrawal against any FT contract whose `storage_deposit` fails (deliberately by an attacker's own contract, or accidentally against any real FT that rejects the deposit, e.g., already-registered accounts or minimum-balance mismatches), and scales with however much `storage_deposit` is set. Because `FtWithdraw` only allows withdrawing the signer's own authorized balance, the funds lost belong to whoever signs the withdrawal — this is not a mechanism to steal a third party's funds, but it is a genuine, code-level permanent loss of the caller's own assets that the protocol design (refund-on-failure) fails to honor.

### Likelihood Explanation
Trivial to trigger: any account holding wNEAR and any FT balance can deploy a one-function malicious FT contract whose `storage_deposit` panics unconditionally, then submit a single self-signed `FtWithdraw` intent. No special roles, relayer keys, or victim cooperation needed. The same defect can also be hit unintentionally by ordinary users against legitimate but non-conforming FT contracts, so it is not purely a deliberate self-harm scenario — it's a systemic missing-refund bug in the withdraw flow.

### Recommendation
Track the `storage_deposit` promise result independently (e.g., split it into its own receipt/callback rather than batching it into the same receipt as `ft_transfer`), and have `ft_resolve_withdraw` (or a dedicated resolver) re-credit the signer's wNEAR balance whenever the `storage_deposit` action did not succeed, mirroring the existing FT `amount` refund logic.

    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }

    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
