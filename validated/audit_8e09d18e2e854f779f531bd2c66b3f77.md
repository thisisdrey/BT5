Audit Report

## Title
Stale child-bounty curator fee is never reverted from the parent bounty's aggregate fee pot after `unassign_curator` - (File: substrate/frame/child-bounties/src/lib.rs)

## Summary
`propose_curator` unconditionally commits a curator fee into the parent bounty's cumulative `ChildrenCuratorFees` ledger before the proposed child curator accepts the role. When `unassign_curator` is called on a `CuratorProposed` (not-yet-accepted) child bounty, it resets the status back to `Added` but never decrements `ChildrenCuratorFees` nor resets `child_bounty.fee`, so a subsequent `propose_curator` call adds a new fee on top of the stale, uncleaned one.

## Finding Description
`propose_curator` writes `fee` into `ChildrenCuratorFees::<T>` via `saturating_add` and sets `child_bounty.fee = fee` as soon as it's called, requiring only that `child_bounty.status == ChildBountyStatus::Added`: [1](#0-0) 

`unassign_curator`'s `CuratorProposed` match arm only performs an authorization check and then falls through to reset the status, without touching `child_bounty.fee` or `ChildrenCuratorFees`: [2](#0-1) 

The status is then unconditionally reset to `Added` for all branches, again without any fee reversal: [3](#0-2) 

This is inconsistent with `impl_close_child_bounty`, which correctly reverts the fee from the ledger via `ChildrenCuratorFees::<T>::mutate(parent_bounty_id, |value| { *value = value.saturating_sub(child_bounty.fee) })` before removing the child bounty: [4](#0-3) 

Since `propose_curator` only requires `status == Added` (which `unassign_curator` restores) and always does `saturating_add(fee)` without first subtracting any prior contribution for that same child-bounty slot, calling `propose_curator` → `unassign_curator` → `propose_curator` again causes `ChildrenCuratorFees` to accumulate `F1 + F2` even though only `F2` will ever be paid out to an accepting curator. The accumulated total is read and cleared exactly once, when the parent bounty is claimed, via `children_curator_fees`, and subtracted from the parent curator's award in `pallet-bounties`: [5](#0-4) 

## Impact Explanation
This corrupts the `ChildrenCuratorFees` storage value for a parent bounty — the exact value used to reduce the parent bounty curator's payout upon claim. The stale fee portion (`F1`) is deducted from the parent curator's award with no corresponding recipient (no curator ever accepted or was paid that stale fee), constituting an unbacked fund loss in the treasury-funded bounty accounting path.

## Likelihood Explanation
Reachable via ordinary signed calls to the public extrinsics `propose_curator` and `unassign_curator`, both callable by the parent bounty curator alone (a normal signed account, no governance/root privilege required beyond being the existing curator of an active parent bounty), in a simple propose → unassign → propose sequence.

## Recommendation
In `unassign_curator`, when transitioning out of `ChildBountyStatus::CuratorProposed { .. }`, decrement `ChildrenCuratorFees::<T>::mutate(parent_bounty_id, |v| *v = v.saturating_sub(child_bounty.fee))` and reset `child_bounty.fee = Zero::zero()`, mirroring `impl_close_child_bounty`'s reversal logic.

## Proof of Concept
1. Parent bounty curator `C` creates child bounty `#0` with value `V` via `add_child_bounty`.
2. `C` calls `propose_curator(parent, 0, X, fee=F1)` → `child_bounty.fee = F1`, `ChildrenCuratorFees[parent] += F1`.
3. Before `X` accepts, `C` calls `unassign_curator(parent, 0)` → status resets to `Added`; `ChildrenCuratorFees[parent]` remains `F1`.
4. `C` calls `propose_curator(parent, 0, Y, fee=F2)` → `child_bounty.fee = F2`, `ChildrenCuratorFees[parent] += F2`, total = `F1 + F2`.
5. `Y` accepts and is paid `F2` normally from the child bounty account.
6. When the parent bounty is claimed, `children_curator_fees(parent)` returns `F1 + F2`, deducted in full from `C`'s parent-bounty payout, even though only `F2` was ever paid to an accepting curator.
