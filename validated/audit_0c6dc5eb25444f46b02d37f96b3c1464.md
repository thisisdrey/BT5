### Title
Fractionalized asset admin role is bound to the pallet's un-keyed sovereign account, permanently disabling freeze/thaw/force-status control - (File: `substrate/frame/nft-fractionalization/src/lib.rs`)

### Summary
This mirrors the TermMax bug exactly: a higher-level module (`TermMaxVault` / here, `pallet-nft-fractionalization`) programmatically creates a sub-object (an `Order` / here, a `pallet-assets` asset class) and assigns the sub-object's privileged role (`Owner` / here, `admin`) to *itself* — a contract/pallet account that exposes no pass-through call to exercise that role. As a result, admin-gated safety operations on the created object (`pause`/`unpause` / here, `freeze`/`thaw`/`force_asset_status`) become permanently uncallable by anyone.

### Finding Description
`Pallet::fractionalize` locks a user's NFT and creates a brand-new `pallet-assets` asset to represent fractional ownership. It calls: [1](#0-0) 

which invokes `Self::do_create_asset(asset_id.clone(), pallet_account.clone())`, i.e. `admin` is set to the **pallet's own sovereign/derived account**: [2](#0-1) [3](#0-2) 

The `admin` slot in `pallet-assets` is not a passive metadata field — it is the origin required to call the asset's protective/administrative extrinsics such as `freeze`, `thaw`, `freeze_asset`/`thaw_asset`, and `force_asset_status`-style operations that gate transfers of a specific account or the whole asset class. These calls all `ensure_signed(origin)` and then check `origin == details.admin` inside `pallet-assets`.

Just like the Solidity report — where `Vault` becomes `Owner` of the `Order` but has no `pause()`/`unpause()` wrapper, so the order's pause protection is unreachable — here `pallet-nft-fractionalization`'s pallet account (a `PalletId`-derived `AccountId`, `T::PalletId::get().into_account_truncating()`) becomes `admin` of the asset but the pallet exposes **no dispatchable** that lets any user or governance origin drive `pallet-assets::freeze`/`thaw`/`force_asset_status` as that pallet account. The pallet account has no private key and is never used as a signed origin elsewhere in the pallet, so every admin-gated safety control on the fractionalized asset is permanently orphaned the moment the asset is created — for the entire lifetime of that asset (until `unify`/`start_destroy`, and even the pending destroy path bypasses `admin` entirely rather than restoring control).

### Impact Explanation
Any account (owner) that fractionalizes an NFT via `fractionalize` creates an asset whose admin-only freeze/thaw/force-status controls can never be exercised. Concretely:
- If a fractionalized asset is later found to be involved in fraud, minting error, or needs an emergency freeze of a malicious holder's balance, there is no path to invoke it — the admin account cannot sign transactions.
- This is a permanent, protocol-level loss of intended protective functionality for every asset created through this pallet, not a one-off admin mistake: it is baked into `do_create_asset`'s hardcoded `pallet_account` argument, so it affects 100% of fractionalized assets by design.
- This matches the required impact class of "runtime bugs that compromise intended behavior" and "permanent ... state lock" since the admin-restricted mitigation surface for these assets is unconditionally and irreversibly disabled.

### Likelihood Explanation
This triggers on every single call to `fractionalize` — there is no attacker action required beyond calling the pallet's normal, permissionless entrypoint (any NFT owner may fractionalize). The broken invariant (an admin capability bound to an unreachable, keyless account) is deterministic and 100% reproducible, not conditional on a race or privileged step.

### Recommendation
Do not assign asset `admin` to the pallet's own unkeyed sovereign account. Either:
- Expose dedicated pallet extrinsics (gated by an appropriate origin, e.g. the NFT/asset creator or a configurable `AdminOrigin`) that forward `freeze`/`thaw`/`force_asset_status` calls to `pallet-assets` on behalf of the pallet account, or
- Set `admin` to a real, controllable account (e.g. the original NFT owner or a governance-controlled origin) at asset-creation time, consistent with how `issuer`/`freezer`/`owner` roles are handled elsewhere in `pallet-assets`.

### Proof of Concept
1. Alice owns an NFT in `pallet-nfts` and calls `pallet_nft_fractionalization::fractionalize(nft_collection_id, nft_id, asset_id, beneficiary, fractions)`.
2. Internally, `do_create_asset(asset_id, pallet_account)` runs `T::Assets::create(asset_id, pallet_account, false, One::one())`, setting `admin = pallet_account` in the new `pallet-assets` asset record.
3. Assume abusive behavior is later detected on this asset (e.g. a compromised beneficiary draining or manipulating balances) and someone attempts to call `pallet_assets::freeze`/`thaw`/`force_asset_status` to mitigate it — this requires `ensure_signed(origin)` to equal `pallet_account`.
4. Because `pallet_account` is a `PalletId`-derived account with no corresponding private key, and `pallet-nft-fractionalization` never dispatches any call as that account nor exposes a wrapper extrinsic to do so, the freeze/thaw/force-status controls on this asset can never be invoked by anyone — confirming the permanent loss of the intended admin safety mechanism.
