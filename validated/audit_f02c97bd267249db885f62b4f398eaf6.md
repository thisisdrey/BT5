### Title
StackerDB chunk signatures omit the smart-contract identifier, enabling cross-contract signature replay when a signer's slot is reset - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` (the digest a signer signs via `sign()`/`verify()`) only commits to `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the target StackerDB smart-contract identifier or to a reward cycle. Combined with `StackerDBTx::reconfigure_stackerdb()`'s behavior of resetting a slot's version to `NO_VERSION` (0) whenever the signer assigned to that slot ID changes, this omission is analogous to the reported "missing nonce" bug: a signature that was valid for one authenticated context (a given contract/slot/version) can be replayed into a different context that shares the same signer key, slot ID, but a freshly-reset (lower) version.

### Finding Description
`SlotMetadata::auth_digest()` at `libstackerdb/src/libstackerdb.rs` (lines 159-166) computes:
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
``` [1](#0-0) 

No domain separator (contract ID, reward cycle, chain ID) is included. `sign()`/`verify()` operate solely on this digest. [2](#0-1) 

The write-path validation in `StackerDBTx::try_replace_chunk()` only checks: chunk size, `slot_desc.verify(&slot_validation.signer)` (a pure signature check against the digest above — no contract binding), monotonic `slot_version`, and `max_writes`. It never verifies that the signature's digest is scoped to the specific `smart_contract` being written to: [3](#0-2) 

Separately, `StackerDBTx::reconfigure_stackerdb()` resets a slot to `version = NO_VERSION` (0) whenever the signer principal assigned to that `slot_id` changes across a reconfiguration (e.g., a signer-set update at a reward cycle boundary): [4](#0-3) 

Because the signature never commits to the contract identifier, if the *same signer key* is ever re-assigned to the *same slot_id* in another StackerDB instance/contract that it can also legitimately write to (or the same contract after a slot reset lowers `slot_validation.version` below a previously-produced version), a previously broadcast, validly-signed `StackerDBChunkData` (data + `sig`) can be resubmitted there. Since `try_replace_chunk` and `validate_received_chunk` check only `slot_version > stored_version` and "signature recovers to the expected signer for this slot", a stale (data, sig) pair remains fully valid input as long as those two conditions hold — there is nothing in the cryptographic commitment that ties it to the original contract or cycle context.

`PeerNetwork::validate_received_chunk()` (used for both `StackerDBSync` downloads and unsolicited `StackerDBPushChunk` gossip) performs the identical checks — signer verification then freshness-by-version — with the same absence of contract binding in the signed digest: [5](#0-4) 

### Impact Explanation
If a signer's slot is reset to version 0 by `reconfigure_stackerdb` (a normal event on signer-set changes), an attacker who has observed and stored a signer's older, validly signed chunk for that slot — from before the reset, or from another StackerDB contract instance where the signer occupies the same slot ID — can replay it verbatim to `try_replace_chunk`/`validate_received_chunk`. This is an unauthenticated/unauthorized write of stale application data into current StackerDB state (e.g., stale block-response or state-machine-update data attributed to a live signer), which downstream consumers (`stackerdb_listener.rs`, `monitor_signers.rs`, block validation waiting on signer signatures) would treat as fresh, potentially misleading miner/coordinator logic about signer state. This maps to the "unauthenticated/unauthorized write to state" (Critical) and "steering a node off tip via false [signer] state" (High) impact categories.

### Likelihood Explanation
Exploitability requires: (1) an attacker capturing a previously valid, signed chunk (trivial — StackerDB chunks are broadcast/gossiped publicly), and (2) a target slot whose stored `version` has been reset/lowered below the captured chunk's `slot_version`, which the codebase's own `reconfigure_stackerdb` logic demonstrates does happen on signer set changes. Whether a signer key is realistically re-assigned to the identical `slot_id` across reconfigurations, and whether real deployments trigger `reconfigure_stackerdb` (versus always calling `create_stackerdb`) for the relevant `.signers-N-xxx` contracts, could not be fully confirmed from the available index — I was not able to trace, within tool-call limits, the exact call site in `stackslib/src/net/stackerdb/mod.rs` that decides between `create_stackerdb` and `reconfigure_stackerdb` on a reward-cycle rotation, nor confirm slot-ID stability guarantees for the same signer across `.signers-0-xxx`/`.signers-1-xxx` rotations. This uncertainty means the likelihood is moderate/unconfirmed rather than proven end-to-end.

### Recommendation
Bind the StackerDB chunk signature to the smart-contract identifier (and ideally a reward-cycle/version epoch marker) by including it in `SlotMetadata::auth_digest()`, e.g.:
```rust
hasher.update(smart_contract_id.serialize_to_vec());
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```
This requires threading the contract ID into `sign()`/`verify()` (and thus `StackerDBChunkData`, `try_replace_chunk`, `validate_received_chunk`), ensuring a chunk signed for one StackerDB contract instance cannot be replayed into another, and that a version reset in `reconfigure_stackerdb` cannot be bypassed by an old signature for the same (now-reset) slot.

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
