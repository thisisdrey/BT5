Audit Report

## Title
Post-expiry pool interaction corrupts `PoolInfo.last_update_block`, permanently bricking stake/unstake and locking staked funds - (`substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`update_pool_rewards` unconditionally stamps `last_update_block` with the raw current block number rather than the same expiry-capped value (`last_block_reward_applicable(expiry_block)`) used by `reward_per_token` for reward accounting. Once any post-expiry `stake` or `unstake` call is persisted, `last_update_block` exceeds `expiry_block`, causing the checked subtraction in `reward_per_token` to underflow on every subsequent call, permanently blocking `stake`, `unstake`, `harvest_rewards`, and the admin repair functions that also rely on `reward_per_token`.

## Finding Description
`reward_per_token` computes `rewardable_blocks_elapsed` as `last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)?`, where `last_block_reward_applicable` clamps to `min(now, expiry_block)`. [1](#0-0) [2](#0-1) 

`update_pool_rewards`, called by every state-mutating path via `update_pool_and_staker_rewards`, sets `last_update_block` to the uncapped current block number instead of the same capped value: [3](#0-2) 

`unstake` is explicitly permissionless once `now > pool_info.expiry_block`, and persists the resulting (corrupted) `pool_info`: [4](#0-3) [5](#0-4) 

`stake` has no expiry guard at all and likewise persists `pool_info` after calling `update_pool_and_staker_rewards`: [6](#0-5) 

Once `last_update_block > expiry_block` is committed, every future `reward_per_token` call (invoked from `stake`, `unstake`, `harvest_rewards` via `update_pool_and_staker_rewards`, and from `set_pool_reward_rate_per_block`/`set_pool_expiry_block`) computes `expiry_block.ensure_sub(last_update_block)`, which underflows and returns a `DispatchError`, aborting the call before any repair logic runs: [7](#0-6) 

The admin's own repair entry points call `reward_per_token` on the already-corrupted `pool_info` before applying any change, so they fail identically: [8](#0-7) [9](#0-8) 

The only unaffected path, `cleanup_pool`, requires an empty `PoolStakers` map, which can never be reached because every unstake attempt after the first corrupting call reverts: [10](#0-9) 

The only escape is the `reward_per_token` early return for `total_tokens_staked.is_zero()` — reachable only if the very first post-expiry interaction fully unstakes all remaining stake across all stakers in one call, which is not the general case.

## Impact Explanation
Once `last_update_block` exceeds `expiry_block` for a pool with nonzero `total_tokens_staked` remaining, no further `unstake` (the only path calling `T::AssetsFreezer::decrease_frozen`) or `harvest_rewards` can succeed, and the admin cannot fix the pool through `set_pool_expiry_block` or `set_pool_reward_rate_per_block` since both re-invoke the same broken `reward_per_token` first. This permanently locks the frozen staked assets and any accrued but unharvested rewards for every remaining staker in that pool, matching the "permanent user-fund ... lock" impact category.

## Likelihood Explanation
High. `unstake` is deliberately designed to be callable by anyone once `now > pool_info.expiry_block`, so the corrupting call is an intended, expected usage pattern rather than an edge case, and requires no privileged actor or special conditions — a single ordinary post-expiry transaction triggers it whenever the pool still has stakers.

## Recommendation
In `update_pool_rewards`, set `new_pool_info.last_update_block` to `Self::last_block_reward_applicable(pool_info.expiry_block)` instead of the raw current block number, keeping it bounded by `expiry_block` so `reward_per_token` never underflows post-expiry. Consider also rejecting `stake` calls against an already-expired pool.

## Proof of Concept
1. Create a pool with `expiry_block = 100`; `last_update_block = 0`.
2. Staker `A` stakes at block 10 → `last_update_block = 10`.
3. At block 150 (post-expiry), `A` calls `unstake` for part of their stake: succeeds (`reward_per_token` uses `last_block_reward_applicable(100)=100` minus `10` = 90, no underflow), but `update_pool_rewards` now sets `last_update_block = 150 > expiry_block(100)` and persists it.
4. At block 160, any further `unstake`/`stake`/`harvest_rewards`/`set_pool_expiry_block`/`set_pool_reward_rate_per_block` call triggers `reward_per_token` computing `100.ensure_sub(150)`, which underflows and returns `Err`, aborting the extrinsic.
5. Remaining staked tokens stay frozen indefinitely since `total_tokens_staked` never reaches zero and `cleanup_pool` requires an empty staker set.

		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}
