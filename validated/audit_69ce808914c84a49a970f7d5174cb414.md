### Title
Uninitialized `accountIndexOf` falls back to 0 (not `INITIAL_INDEX`) when token index equals `INITIAL_INDEX`, letting a first-touch user accrue reward tokens equal to their entire token balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` treats a missing per-account index as `INITIAL_INDEX` only when the global token index is strictly greater than `INITIAL_INDEX`. When the token index is exactly `INITIAL_INDEX` (i.e., a newly reward-enabled token before any index update has accrued), the missing account index stays `0`, so `_deltaIndex = 1e18` and the account accrues `balance * 1e18 / 1e18 = balance` reward tokens in a single call. This is the Solidity analog of prototype pollution: an absent per-account key silently "inherits" a global/default value, and the guard that was meant to apply the safe default fails at the boundary.

### Finding Description
The bug lives in `contracts/RewardsDistributor.sol`: [1](#0-0) 

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a token is first added via `_updateTokenSpeed`, its state is set to `{index: INITIAL_INDEX, timestamp: now}` (`INITIAL_INDEX = 1e18`, lines 296–299). Until a subsequent `_updateTokenIndex` produces `_newIndex > INITIAL_INDEX` (requires `deltaTimestamps > 0` and non-zero accrued ratio, lines 200–212), any call path that reaches `_updateTokensAccruedOf` computes:

- `_tokenIndex = 1e18`
- `_accountIndex = 0` (attacker never touched the index), and `1e18 > 1e18` is false, so the fallback does not apply
- `_deltaIndex = 1e18`
- `_tokensDelta = balanceOf(attacker).wadMul(1e18) = balanceOf(attacker)`

Reachable, attacker-controlled entry points (all public, no privileged modifier):

- `claimRewards(accounts_, tokens_)` — `nonReentrant` only, lines 150–168
- `updateBeforeMintOrBurn(token_, account_)` — explicitly "may be called by anyone", lines 175–180
- `updateBeforeTransfer(token_, from_, to_)`, lines 186–192
- Indirectly via `DepositToken` mint/transfer hooks

Attack path:
1. Attacker deposits underlying and holds a large `DepositToken` balance `B` (or flash-mints/holds `DebtToken` principal) ahead of time.
2. Attacker front-runs (or back-runs in the same block as) the governor's `updateTokenSpeed(depositToken, speed)` that first sets `tokenStates[token] = {INITIAL_INDEX, now}`.
3. Same block (`deltaTimestamps == 0`, so `_calculateTokenIndex` returns `(0,0)` and the index stays `INITIAL_INDEX`), attacker calls `claimRewards([attacker], [depositToken])` or `updateBeforeMintOrBurn`.
4. `tokensAccruedOf[attacker] += B`, and `_transferRewardIfEnoughTokens` pays out `B` reward tokens if the distributor balance covers it (lines 248–256).

### Impact Explanation
Theft of unclaimed yield / reward-token funds. The attacker receives `rewardToken` equal to their full `DepositToken`/`DebtToken` balance — an amount never accrued legitimately — draining the `RewardsDistributor`'s balance and denying other depositors/borrowers their accrued rewards. This is a direct, reproducible loss of protocol-held reward funds triggered entirely by an unprivileged EOA.

### Likelihood Explanation
The exploit requires the token index to equal `INITIAL_INDEX` when the attacker acts. This occurs deterministically in the block in which a governor first enables rewards for a token (`tokenStates[token_].index` transitions 0 → `INITIAL_INDEX`), and persists while `_calculateTokenIndex` produces no positive ratio (e.g., zero elapsed time, or `delta*speed/totalSupply` rounding to 0 in `wadDiv`). Since reward tokens are added over time via governance and attacker transactions can be ordered around the governor's transaction (front-run/back-run), the condition is practically reachable for each newly added reward token. No privileged role, oracle manipulation, or bridge assumption is needed.

### Recommendation
Change the fallback condition in `_calculateTokenDelta` to apply whenever the stored account index is `0`, e.g.:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

or more simply initialize `_accountIndex = _tokenIndex` when `accountIndexOf[token_][account_] == 0`, so a first-touch account accrues zero delta. Add a regression test where `claimRewards` is called in the same block a token's speed is first set, asserting `tokensAccruedOf` remains 0.

### Proof of Concept
Hardhat sketch (assumes existing fixtures for `pool`, `depositToken`, `rewardsDistributor`, `rewardToken`):

```ts
it('accrues full balance when token index equals INITIAL_INDEX', async () => {
  const {governor, alice, depositToken, rewardsDistributor, rewardToken} = await loadFixture(fixture)

  // 1. Attacker holds a depositToken balance
  const B = parseEther('1000')
  await deposit(depositToken, alice, B) // alice deposits underlying

  // 2. Fund distributor with rewards
  await rewardToken.mint(rewardsDistributor.address, parseEther('100000'))

  // 3. Governor enables rewards for the token (sets index = INITIAL_INDEX)
  await rewardsDistributor.connect(governor).updateTokenSpeed(depositToken.address, parseEther('1'))

  // 4. Same block: index still INITIAL_INDEX, attacker claims
  await rewardsDistributor.claimRewards([alice.address], [depositToken.address])

  // Bug: alice receives B reward tokens despite accruing nothing
  expect(await rewardToken.balanceOf(alice.address)).to.eq(B)
})
```

    function _calculateTokenDelta(
        TokenState memory _tokenState,
        IERC20 token_,
        address account_
    ) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
        _tokenIndex = _tokenState.index;
        uint256 _accountIndex = accountIndexOf[token_][account_];

        if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
            _accountIndex = INITIAL_INDEX;
        }

        uint256 _deltaIndex = _tokenIndex - _accountIndex;
        _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
    }
