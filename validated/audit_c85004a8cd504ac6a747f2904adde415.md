### Title
Malicious/mutable Token-2022 Transfer Hook can permanently freeze withdrawals from a bank - (File: `programs/marginfi/src/state/bank.rs`, `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`)

### Summary
`Bank::withdraw_spl_transfer` (and the equivalent deposit/borrow/repay transfer paths) performs the token move via `spl_token_2022::onchain::invoke_transfer_checked`, which for Token-2022 mints automatically resolves and CPIs into the mint's `TransferHook` program if the extension is present. This is the same bug class as the report: an untrusted external call is made from within a critical fund-movement function, and that external program controls how much of the transaction's execution budget it consumes.

### Finding Description
`withdraw_spl_transfer` in [1](#0-0)  calls `spl_token_2022::onchain::invoke_transfer_checked` for any mint routed through `maybe_bank_mint` (Token-2022 path), which transparently invokes the mint's transfer-hook program via CPI if the extension is set. `utils::has_transfer_hook` in [2](#0-1)  shows the protocol is aware transfer hooks can be attached to a bank's mint, and it is explicitly *rejected* for the emissions-deposit path in [3](#0-2) , but no equivalent guard exists on `lending_account_withdraw`/`lending_account_borrow`/deposit/repay, which is exactly where user funds move. Test-utils confirm production support for transfer hooks in normal deposit/borrow flows (`#[cfg(feature = "transfer-hook")]` blocks resolving `add_extra_account_metas_for_execute`), e.g. [4](#0-3) .

Because Solana enforces a hard per-transaction compute-unit ceiling, a transfer-hook program that is (or becomes, via a later hook-authority upgrade) malicious can deliberately consume all available compute units (e.g. a busy loop or repeated expensive syscalls) every time it is invoked. Since the hook CPI happens unconditionally inside the same atomic transaction as `lending_account_withdraw`, this forces every withdrawal transaction against that bank to fail with a compute-budget exceeded error — there is no gas/compute stipend limiting how much of the budget the external hook program may consume, mirroring the report's "no gas stipend on the external call" root cause.

### Impact Explanation
If a bank's underlying Token-2022 mint has a mutable `TransferHook` extension whose authority can update the hook program (or if the hook program itself is later closed/frozen or made to burn all compute), the hook authority (a third party external to marginfi's own admin roles) can indefinitely block all withdrawals, repayments-via-transfer, and borrows from that bank, permanently locking depositors' funds in the bank's liquidity vault. This satisfies "permanent lock/freeze" of user funds without requiring any marginfi-privileged action — the bank's group admin only chose to onboard the mint; the actual attack is executed by the mint's external transfer-hook authority at any later time.

### Likelihood Explanation
Likelihood depends on whether a group admin lists a Token-2022 mint with an upgradable/malicious transfer hook as a bank's asset. Given marginfi explicitly builds and tests transfer-hook support for deposits/withdraws (not just a theoretical SPL edge case), and Token-2022 hook programs are commonly upgradable by a hook authority independent of marginfi, this is a realistic supply-chain/asset-listing risk rather than a purely theoretical one — analogous to a bank being created for a token whose hook authority later "rug pulls" liquidity by bricking withdrawals.

### Recommendation
Apply the same defensive check used in `lending_pool_emissions_deposit` (`utils::has_transfer_hook`) to reject transfer-hook-enabled mints at bank creation/whitelisting time, or wrap the hook CPI with a bounded compute budget (Solana's CPI does not support a "gas stipend" directly, but the protocol can require callers to pre-fund a dedicated compute allotment and treat hook failure/OOC as a recoverable, non-blocking condition), and/or provide an emergency migration path (e.g., an admin-gated "force withdraw without hook" fallback for banks whose mint hook is confirmed malicious) so that funds are not irrecoverably frozen.

### Proof of Concept
1. Group admin creates a bank for a Token-2022 mint that currently has a benign transfer hook (passes any due-diligence at listing time).
2. Users deposit into the bank normally; `lending_account_deposit`/`lending_account_withdraw` succeed while the hook is cheap.
3. The mint's `TransferHook` authority upgrades the hook program to one that intentionally spins until it exhausts the transaction's compute budget (e.g., an unbounded loop or repeated `sol_log`/hashing calls).
4. Any subsequent `lending_account_withdraw` (or `lending_account_borrow`, `lending_account_repay`) for that bank now CPIs into the malicious hook via `withdraw_spl_transfer` → `invoke_transfer_checked`, which exhausts the compute budget and causes the whole transaction (and Solana transaction compute ceiling of 1.4M CU) to fail every time, regardless of the compute-budget instruction the user attaches, up to the program-configurable maximum.
5. All depositors of that bank are permanently unable to withdraw their tokens, matching the report's "controller can indefinitely lock users' tokens" bug class.

Note: I was not able to fully trace whether `LendingPoolAddBank`/`LendingPoolAddBankWithSeed` (bank-creation instructions) perform any mint-extension validation that might already reject transfer-hook mints outright; the `has_transfer_hook` check I found is only wired into `lending_pool_emissions_deposit`, not into bank creation or the core deposit/withdraw/borrow/repay paths. If bank creation does reject Token-2022 mints with an active transfer hook, this finding would be substantially mitigated — this should be confirmed against the full `add_pool`/`add_bank` instruction source.

```rust
/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
```
