### Title
Liquidation can degrade account health by seizing high-collateral-factor deposit tokens, leaving persistent bad debt - (`contracts/Pool.sol:537`)

### Summary
`Pool.liquidate` lets any caller freely choose which `IDepositToken` to seize. Because each `DepositToken` has its own `collateralFactor`, seizing a high-CF collateral removes more issuable power per USD of debt repaid than seizing a low-CF one. A liquidator can therefore repay debt against an unhealthy account while making `debtPositionOf` *less* healthy (or never restoring health), forcing repeated partial liquidations under the `maxLiquidable` cap and leaving bad debt on the protocol longer. This is the same bug class as the Arcadia report: liquidation is not health-aware and collateral selection is unrestricted.

### Finding Description
Health in Metronome is computed in `debtPositionOf` as `_isHealthy = _debtInUsd <= _issuableLimitInUsd`, where `_issuableLimitInUsd` is the sum of each deposit's USD value weighted by `depositToken.collateralFactor()` (`contracts/Pool.sol:248-288`). `collateralFactor` is per-asset (`contracts/DepositToken.sol:163-164`).

In `liquidate` (`contracts/Pool.sol:537-596`), the liquidator passes `depositToken_` as an arbitrary argument restricted only by `onlyIfDepositTokenExists`. The seized amount `quoteLiquidateOut` is priced purely in USD terms via `masterOracle().quote(...)` plus `liquidatorIncentive`/`protocolFee` (`contracts/Pool.sol:451-472`) — the `collateralFactor` of the chosen collateral is never consulted. Only bounds checked are:

- `amountToRepay_` ≤ `maxLiquidable` × debt balance (default 50%, `contracts/Pool.sol:181,567`)
- `debtFloorInUsd` (`contracts/Pool.sol:571-579`)
- seized amount ≤ account balance (`contracts/Pool.sol:583`)

There is no check that the post-liquidation position is healthier, nor any ordering/priority on which collateral is seized.

Concrete numerics mirroring the original report: victim has debt `D = 1000 USD` of msUSD, collateral `msdETH` worth `600 USD` with `CF = 0.9` and `msdBTC` worth `400 USD` with `CF = 0.5`. `issuableLimit = 540 + 200 = 740`, unhealthy (740 < 1000).

- Liquidator calls `liquidate(msUSD, victim, 500e18, msdBTC)` repaying ~500 USD and seizing ~525 USD of BTC: `L' = 540 + 400-262.5... ` — with low-CF collateral removed, `L' ≈ 540 + (400-525·CF... )`; properly: seize `~525 USD` of BTC → `L' = 540 + 0.5·(400-525) = 540 - 62.5 = 477.5`? No — BTC only has 400 USD, cap at balance. Seize ≤ balance enforced. Use `amountToRepay` that seizes 300 USD of BTC: `L' = 540 + 0.5·100 = 590`, `D' = 1000 - ~286 = 714`. Health gap went from 260 to 124 — improved.
- Instead, liquidator calls `liquidate(msUSD, victim, amountToRepay_, msdETH)` seizing the same USD value of the CF-0.9 token: `L' = 0.9·(600-315) + 200 = 256.5 + 200 = 456.5`, `D' = 714`. Health gap went from 260 to 257.5 — barely improved, and proportionally the issuable limit dropped far more per USD repaid.

With the 50% `maxLiquidable` cap, full liquidation in one call is impossible; a liquidator selecting the highest-CF collateral each round maximizes the number of liquidation rounds (collecting `liquidatorIncentive` each time) while the account remains unhealthy — and the portion of debt backed by remaining collateral shrinks toward insolvency. The liquidator is paid the same USD-denominated bonus regardless of which collateral is picked, so choosing high-CF collateral is the dominant strategy for prolonging liquidation.

### Impact Explanation
- **Protocol insolvency / bad debt persistence:** an unhealthy account can be kept unhealthy (or made relatively worse in issuable-limit terms) across successive liquidations, extending the window in which collateral value may fall below debt — directly the bad-debt scenario the mechanism is supposed to clear.
- **Victim harm:** the victim loses the same USD of collateral but retains strictly less borrowing capacity than if low-CF collateral were seized first; their position is weakened more than necessary per repayment.
- **Misaligned incentives:** `liquidatorIncentive` is paid on every partial liquidation, so repeat high-CF liquidations are profitable to the caller while degrading the very health metric the pool uses.

### Likelihood Explanation
Any EOA holding (or flash-borrowed/leveraged via `SmartFarmingManager`) synthetic tokens can call `liquidate` on any unhealthy account with any registered `depositToken_`. No privileged role, oracle fault, or governance action is required — pools routinely list collaterals with heterogeneous collateral factors (the enforced range is `0 < CF < 1e18`, `DepositToken.sol:163-164`). The only precondition is a multi-collateral unhealthy account, which is normal operation. `nonReentrant`/`whenNotShutdown`/`SynthContext` do not mitigate this.

### Recommendation
Make liquidation health-aware. Options:

1. Compute post-liquidation `debtPositionOf` and revert if `_issuableLimitInUsd` decreased relative to `debt` reduction (i.e., require the position's health ratio to improve or the debt to be fully repaid).
2. Restrict `depositToken_` to the lowest-`collateralFactor` collateral among the account's deposits, or sort seizure in ascending-CF order inside `liquidate`.
3. Scale the seized amount by the collateral's CF so that high-CF seizures cost proportionally more debt repayment to justify the larger issuable-limit reduction.

### Proof of Concept
Hardhat sketch (consistent with existing `test/Pool.test.ts` fixtures: `masterOracle`, `msdMET`/`msdXXX` deposit tokens, `msEth`/`msEthDebtToken`, `liquidator` signer):

// setup: two deposit tokens, high CF and low CF, registered in `pool`
// msdHigh.underlying = HIGH (e.g. blue-chip, CF = 0.9)
// msdLow.underlying  = LOW  (CF = 0.5)
// victim deposits $600 HIGH and $400 LOW, issues $1000 msUSD-equivalent debt -> unhealthy

await feeProvider.updateProtocolLiquidationFee(0);
// debt floor disabled, maxLiquidable = 50%

const before = await pool.debtPositionOf(victim.address);
const gapBefore = before._debtInUsd.sub(before._issuableLimitInUsd);

// liquidator selects the HIGH-CF collateral instead of LOW-CF

    function liquidate(
        ISyntheticToken syntheticToken_,
        address account_,
        uint256 amountToRepay_,
        IDepositToken depositToken_
    )
        external
        override
        whenNotShutdown
        nonReentrant
        onlyIfSyntheticTokenExists(syntheticToken_)
        onlyIfDepositTokenExists(depositToken_)
        returns (uint256 _totalSeized, uint256 _toLiquidator, uint256 _fee)
    {
        address _msgSender = _msgSender();

        if (amountToRepay_ == 0) revert AmountIsZero();
        if (_msgSender == account_) revert CanNotLiquidateOwnPosition();

        IDebtToken _debtToken = debtTokenOf[syntheticToken_];
        _debtToken.accrueInterest();

        (bool _isHealthy, , , , ) = debtPositionOf(account_);

        if (_isHealthy) {
            revert PositionIsHealthy();
        }

        uint256 _debtTokenBalance = _debtToken.balanceOf(account_);

        if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
            revert AmountGreaterThanMaxLiquidable();
        }

        if (debtFloorInUsd > 0) {
            uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
                address(syntheticToken_),
                _debtTokenBalance - amountToRepay_
            );
            if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
                revert RemainingDebtIsLowerThanTheFloor();
            }
        }

        (_totalSeized, _toLiquidator, _fee) = quoteLiquidateOut(syntheticToken_, amountToRepay_, depositToken_);

        if (_totalSeized > depositToken_.balanceOf(account_)) {
            revert AmountIsTooHigh();
        }

        syntheticToken_.burn(_msgSender, amountToRepay_);
        _debtToken.burn(account_, amountToRepay_);
        depositToken_.seize(account_, _msgSender, _toLiquidator);

        if (_fee > 0) {
            depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee);
        }

        emit PositionLiquidated(_msgSender, account_, syntheticToken_, amountToRepay_, _totalSeized, _fee);
    }
