### Title
Missing precision-consistency check in `ExchangeInjectActuator` allows exchange creator to skew pool reserves via floor-division rounding - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` computes the counterpart token amount for a liquidity injection using integer (floor) division and never verifies that the result is free of rounding loss, unlike the sibling `ExchangeWithdrawActuator`, which explicitly rejects any operation whose rounding error exceeds 0.01% with a dedicated "Not precise enough" check.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` with `BigDecimal` and then explicitly bounds the rounding error against the computed value, rejecting the transaction if the remainder is too large: [1](#0-0) 

`ExchangeInjectActuator.doValidate()` performs the analogous cross-token ratio computation but only guards against non-positive results — it never checks whether `divide()` lost precision: [2](#0-1) 

The same unguarded floor-division is repeated in `execute()`, where `anotherTokenQuant` is computed via `floorDiv(multiplyExact(...), ...)` and directly used to update the constant-product pool balances that price all subsequent trades through `ExchangeTransactionActuator`: [3](#0-2) 

Because only the exchange creator can call `ExchangeInjectContract` (enforced at line 175-177), this is still an unprivileged, permissionlessly-reachable operation — any account can create an exchange (`ExchangeCreateActuator`) and then repeatedly call `ExchangeInject` on their own pool: [4](#0-3) 

Each floor-division rounds `anotherTokenQuant` down, meaning the creator contributes strictly less than the mathematically proportional amount of the counterpart token while the pool balances (and thus the implied exchange rate used by `ExchangeTransactionActuator`/`ExchangeCapsule.transaction`) are updated as if the contribution were exact: [5](#0-4) 

Repeated small injections can therefore be used to incrementally skew the pool's reserve ratio away from its true price without contributing proportional value, at the expense of counterparties who subsequently trade against the manipulated reserves.

### Impact Explanation
The pool balances maintained by `ExchangeCapsule` back all trades executed via `ExchangeTransactionActuator` and `ExchangeWithdrawActuator`. Allowing the pool's price to be skewed for free (via unchecked rounding) lets the exchange creator extract value from other traders interacting with the same exchange pool, which constitutes a fund-safety issue analogous to the reported "missing consistency check" pattern — one actuator (`Withdraw`) enforces precision, the paired actuator (`Inject`) does not.

### Likelihood Explanation
Any account can create an exchange via `ExchangeCreateActuator` and become its creator, then call `ExchangeInjectContract` with token quantities deliberately chosen to trigger unfavorable-for-counterparty rounding, repeated arbitrarily many times at negligible cost (fee is 0, per `calcFee()` in `ExchangeInjectActuator`, line 268-270).

### Recommendation
Add the same BigDecimal-based rounding-error bound used in `ExchangeWithdrawActuator` (or an equivalent exact-division check) to `ExchangeInjectActuator.doValidate()`, rejecting injections whose implied counterpart amount cannot be represented without loss of precision.

### Proof of Concept
1. Account A creates an exchange pool with `firstTokenBalance = 100_000_000`, `secondTokenBalance = 100_000_000` via `ExchangeCreateActuator`.
2. Account A repeatedly calls `ExchangeInjectContract` with small `tokenQuant` values chosen so that `secondTokenBalance * tokenQuant` is not evenly divisible by `firstTokenBalance`, e.g. `tokenQuant = 3` on a 100,000,000/100,000,001 pool.
3. `doValidate()`/`execute()` compute `anotherTokenQuant` via floor division with no precision check, silently truncating the fractional counterpart contribution — see `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java` lines 217-227 and 73-83.
4. Over many repetitions the pool ratio drifts in favor of Account A, and subsequent traders using `ExchangeTransactionActuator` execute against the skewed reserves.
