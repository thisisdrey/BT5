### Title
`SyntheticToken._burn` does not decrease `totalBridgedIn` / `amoSupply` when bridged-in or AMO-minted synths are burned through `DebtToken.repay`, permanently consuming the `maxBridgedInSupply` / `maxAmoSupply` caps - (`contracts/SyntheticToken.sol`)

### Summary
Analogous to the Party `burn`/`totalVotingPower` bug, Metronome's `SyntheticToken._burn` reduces `balanceOf`/`totalSupply` but only adjusts the directional supply trackers (`totalBridgedOut`, `amoSupply`) for specific privileged callers. When a user burns synths via `DebtToken.repay` (or `Pool`-initiated burns), tokens that were originally minted via `ProxyOFT._creditTo` (`totalBridgedIn += amount`) or via the AMO (`amoSupply += amount`) are destroyed without decrementing `totalBridgedIn`/`amoSupply`. `bridgedInSupply()` (`MAX(totalBridgedIn - totalBridgedOut, 0)`) therefore permanently overstates the net bridged-in circulating supply, and the `maxBridgedInSupply` cap enforced in `_mint` is consumed forever.

### Finding Description
- `contracts/SyntheticToken.sol:338-344` — `_mint` increments `totalBridgedIn` when caller is `proxyOFT`, and `amoSupply` when caller is `amo`, enforcing `maxBridgedInSupply` / `maxAmoSupply`.
- `contracts/SyntheticToken.sol:271-294` — `_burn` increments `totalBridgedOut` only when caller is `proxyOFT`, and decrements `amoSupply` only when caller is `amo`. Burns by a registered `Pool` or `DebtToken` (`onlyIfCanBurn`, lines 83-92; `_isMsgSenderDebtToken`, lines 313-320) touch neither tracker.
- `contracts/DebtToken.sol:453-454` — public `repay(onBehalfOf_, amount_)` calls `_syntheticToken.burn(_msgSender, _repaid)`, destroying synths from the payer's balance with no provenance tracking.
- `contracts/ProxyOFT.sol:86-93` — `_creditTo` mints via `syntheticToken.mint`, so every bridge-in permanently raises `totalBridgedIn`.

Attack cycle (per iteration, attacker recovers their collateral):
1. Attacker deposits collateral and calls `DebtToken.issue`, minting synth `S` against debt `S`; sells `S`.
2. Attacker bridges `S` of the same synth in from another chain (where they hold it): `ProxyOFT._creditTo` → `mint` → `totalBridgedIn += S`.
3. Attacker calls `DebtToken.repay(attacker, S)`: the bridged-in `S` is burned and their debt cleared. `totalBridgedIn` is NOT decremented.

Result: `bridgedInSupply()` remains inflated by `S` even though zero bridged tokens circulate. Repeating cycles the `bridgedInSupply` up to `maxBridgedInSupply`, after which every `_creditTo` bridge-in reverts with `SurpassMaxBridgingSupply` — a denial of service on inbound bridging. The identical pattern applies to `amoSupply`/`maxAmoSupply`: buying AMO-minted synths on the market and repaying debt with them permanently consumes the AMO cap (AMO itself cannot reduce `amoSupply` for tokens burned by other actors).

The invariant broken is bridge conservation: `bridgedInSupply()` is documented as "net bridged-in circulating supply" but conflates cumulative receipts with current circulation. Inbound bridging is frozen until governance raises the cap (`updateMaxBridgedInSupply`), and the same inflated accounting also relaxes the `maxBridgedOutSupply` check on this chain.

### Impact Explanation
Permanent (until governor intervention) freezing of cross-chain transferability for the synth: all inbound OFT receives revert once the cap is saturated, stranding users' tokens on remote chains. The AMO cap variant freezes AMO minting capacity.

### Likelihood Explanation
Requires no privileges — `repay` and `sendFrom` are public. The attacker needs real capital (collateral to issue debt, synths on a remote chain), but repaying their own debt recovers the collateral; per-cycle cost is bridge fees + repay/issue fees. The impact scales to whatever `maxBridgedInSupply` is set to. Whether this is considered intended cumulative accounting is uncertain — the natspec claims net-circulating semantics, which the code violates, so this is best judged as a liveness/DoS analog rather than direct theft.

### Recommendation
Track provenance or decrement `totalBridgedIn`/`amoSupply` when tokens attributable to those sources are burned by non-OFT/non-AMO callers. Simplest: reduce `bridgedInSupply` contribution on any burn while `totalBridgedIn > totalBridgedOut` (i.e., burn settles the outstanding bridged balance first), or cap `bridgedInSupply` by `min(totalBridgedIn - totalBridgedOut, circulatingShare)`. Alternatively accept that these counters are cumulative and enforce caps only at mint time against `totalSupply` growth attributable to bridging.

### Proof of Concept
Foundry/Hardhat fork on a deployed chain (e.g. base):

```solidity
// setup: attacker deposits collateral, issues S synth (debt S)
debtToken.issue(S, attacker);

// bridge S in from remote chain (or simulate _creditTo via prank on proxyOFT)
vm.prank(address(proxyOFT));
synth.mint(attacker, S);            // totalBridgedIn += S, cap checked

assertEq(synth.bridgedInSupply(), prevBridgedIn + S);

// burn bridged-in synths by repaying own debt
debtToken.repay(attacker, S);       // synth.burn(attacker, S) — totalBridgedIn unchanged

// invariant violation: circulating bridged supply is 0, but counter still reads S
assertEq(synth.bridgedInSupply(), prevBridgedIn + S); // BUG: should be prevBridgedIn

// repeat until bridgedInSupply() == maxBridgedInSupply, then:
vm.prank(address(proxyOFT));
vm.expectRevert(SurpassMaxBridgingSupply.selector);
synth.mint(victim, 1);              // all bridge-ins now revert → DoS
```
