### Title
Cross-contract signature replay in `ValidateMultiSign` precompiled contract due to missing caller-contract binding - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (address `0x...0a`) constructs the message hash that off-chain signers actually sign from only three components: the target TRON account address, the permission id, and an arbitrary `data` blob supplied by the calling smart contract. It never mixes in the address/identity of the calling contract itself, so the exact same `(address, permissionId, data)` triple — and therefore the exact same valid signature set — can be replayed by any other smart contract on the chain that also calls this precompile with matching parameters.

### Finding Description
`ValidateMultiSign.execute` builds the signed hash like this: [1](#0-0) 

`combine` is only `address || permissionId || data`. There is no notion of "which contract asked for this validation" (no `msg.sender`/`this` binding, no chain id, no nonce enforced by the precompile itself). The precompile then recovers signer addresses from this hash and checks accumulated weight against the account's permission threshold: [2](#0-1) 

This is structurally the same root cause as the referenced `Project.sol#updateProjectHash` finding: the signed payload omits a binding to the specific contract instance that is meant to consume the authorization. Any DApp that follows the natural/expected usage pattern of `validatemultisign(address, permissionId, hash(dataStruct))` — where `dataStruct` does not itself embed the verifying contract's address — is vulnerable to having a legitimately-obtained user/owner signature replayed against a *different* contract that happens to request validation for the same account, permission id, and same `data` (e.g., a re-deployed or sibling instance of the same DApp, or any other contract that reuses the same encoding convention for `data`, such as a common `(action, nonce)` tuple).

Uniqueness is left entirely to whatever the calling contract puts into `data`; the precompile provides no protection by itself, unlike raw EVM/TVM patterns (e.g. EIP-712) where a domain separator including the verifying contract address is a standard mitigation baked into the signing convention, not an accidental omission at the primitive level.

### Impact Explanation
If a DApp built on top of `ValidateMultiSign` uses `data` that is not already scoped to the specific consuming contract (a very natural mistake, matching exactly the audited pattern in the original report), a signature authorizing an action on one contract can be replayed to authorize the same action on a different contract sharing the same account/permission and `data`/nonce space. Depending on what the consuming DApp gates behind this check (fund transfers, task/state updates, governance actions), this can lead to unauthorized account operations or theft of funds in the affected DApp's contracts once the same nonce/data value recurs across the different contract instances.

### Likelihood Explanation
Reaching this code path requires only a normal TVM `CALL`/`STATICCALL` from any contract or an off-chain signature that the attacker can obtain (e.g., by tricking a user into signing an authorization for contract A, then replaying it against contract B). No special privilege, validator/SR role, or node-level access is required — any deployer/contract author or transaction sender that interacts with an already-deployed vulnerable DApp using this precompile can trigger the replay. The likelihood of an actually-affected downstream contract existing depends on DApp-level encoding practices, but the precompile itself provides no guardrail, which is exactly the gap flagged in the original report.

### Recommendation
Document explicitly (and consider enforcing at the precompile level) that `data` passed to `ValidateMultiSign`/`BatchValidateSign` MUST include the verifying/calling contract's own address (e.g., via `address(this)`) as part of the signed payload, or add a mandatory domain-separation parameter (chain id + calling contract address) that the precompile itself mixes into `combine` before hashing, so that a valid signature cannot be replayed across differing verifying contracts even when they share the same target account, permission id, and application-level `data`/nonce.

### Proof of Concept
1. Off-chain user signs `sha256(sha256(ownerAddress || permissionId || data))` where `data` encodes only `(action, nonce)` without any contract-specific salt, intending to authorize DApp A's contract at address `X`.
2. DApp B (a different, unrelated contract at address `Y`) also calls the `validatemultisign(address,uint256,bytes32,bytes[])` precompile with the same `ownerAddress`, `permissionId`, and computes the same `data`/`hash` for its own `(action, nonce)` combination (plausible if both DApps use a common encoding library or if B is a clone/fork of A).
3. The attacker submits the previously-collected signature to DApp B's contract; `ValidateMultiSign` returns success because `combine`/`hash` matches, even though the user never intended to authorize DApp B.
4. DApp B executes the privileged action gated by this check, using a signature that was never meant for it — an instance of the same signature-replay-across-instances bug class as `Project.sol#updateProjectHash`.
