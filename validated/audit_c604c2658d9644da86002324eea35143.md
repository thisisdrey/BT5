### Title
Ambiguous delimiter-based archive cache key allows cache-key collisions across distinct `GetArchive` requests - (File: `internal/gitaly/service/repository/archive.go`)

### Summary
`GetArchive`'s response cache key is built by joining `args` and `pathspecs` with a plain `","` separator and hashing the concatenation, with no length-prefixing or escaping. Because pathspecs/exclude entries are attacker-controlled repository paths that are not restricted from containing literal comma characters, two semantically different requests (different path/exclude lists) can serialize to the identical byte string before hashing, producing the same cache key. This is analogous to the reported LineaRollup issue where a hash key was computed over data that omitted or failed to guarantee per-item uniqueness, allowing distinct inputs to collide under the same key used for storage/lookup gating.

### Finding Description
`createArchiveCacheKey` computes the cache key as: [1](#0-0) 

`args` and `pathspecs` are built directly from client-supplied `GetArchiveRequest` fields (`CommitId`, `Path`, `Exclude`), only validated against path traversal via `storage.ValidateRelativePath`, not against delimiter characters: [2](#0-1) 

Because the pathspecs slice is joined with a bare comma before hashing, a single pathspec entry containing a literal comma (e.g. exclude path `"a,b"`) serializes identically to two separate pathspec entries `"a"` and `"b"`. These represent different `git archive` invocations (excluding one path vs. excluding two different paths) yet produce the same `cacheKeyHash` input and therefore the same cache key used to key `s.archiveCache.Fetch`: [3](#0-2) 

The codebase demonstrates that the maintainers are aware of exactly this ambiguous-concatenation class of bug and defend against it elsewhere with an explicit length-prefix encoding (`prefixLen`) in the disk-cache keyer used for `InfoRefsUploadPack` caching: [4](#0-3) 

`createArchiveCacheKey` does not apply this (or any other unambiguous encoding, e.g. length-prefixing or a non-occurring separator/escaping) to `args`/`pathspecs`, so it remains vulnerable to the same class of collision that `prefixLen` was introduced to prevent in the sibling cache implementation.

### Impact Explanation
If two clients (or the same client with two crafted requests) race a colliding cache key, `s.archiveCache.Fetch` will serve one client's `git archive` output to the other. Since `pathspecs` directly controls which paths/exclusions are archived, a collision can cause a requester whose intended pathspec was `["a,b"]` to receive an archive generated from `["a", "b"]` (or vice versa) — i.e., the client can receive archive content generated for a different exclude/path scope than the one it explicitly requested, within the same repository/commit. This is a content-integrity /cache-poisoning issue reachable from an ordinary authenticated caller of `GetArchive` via crafted `Exclude`/`Path` fields; it does not require a privileged actor, leaked token, or a malicious peer.

### Likelihood Explanation
Exploitability requires only that an attacker control the `Exclude`/`Path` fields of `GetArchiveRequest`, which are ordinary RPC inputs available to any client permitted to call `GetArchive`. No cryptographic collision is needed — the collision is a deterministic construction ambiguity, not a hash break, so it is trivially reproducible by choosing pathspecs containing a comma character. The main precondition is that filesystem/relative-path validation (`storage.ValidateRelativePath`) does not reject commas in path components, which is standard on POSIX filesystems.

### Recommendation
Encode `args` and `pathspecs` unambiguously before hashing in `createArchiveCacheKey`, e.g. reuse the existing `prefixLen`-style length-prefixing scheme from `internal/cache/keyer.go`, or hash each element separately (e.g., `Write(len(item))` then `Write(item)` for every slice element) instead of joining with a plain delimiter that can appear in the data itself.

### Proof of Concept
1. Repository contains files/directories at paths `a` and `b`, and also (or alternatively) a differently-named path that literally contains a comma, e.g. a directory named `a,b`.
2. Client A calls `GetArchive` with `Exclude = ["a,b"]` (excluding the single path literally named `a,b`).
3. Client B calls `GetArchive` with `Exclude = ["a", "b"]` (excluding the two separate paths `a` and `b`).
4. Both requests, after pathspec construction (`":(exclude)a,b"` vs `":(exclude)a", ":(exclude)b"`), joined with `","` in `createArchiveCacheKey`, hash to the same `cacheKeyHash` value given identical `args` (same commit ID) and `gitLabProjectPath`.
5. Whichever request reaches `s.archiveCache.Fetch` first populates the cache entry; the second request receives the first request's cached archive content instead of the archive corresponding to its own exclude list — i.e., Client B may receive an archive that unexpectedly still contains `a` and `b`, or Client A may receive one where directory `a,b` was not excluded as requested.

Note: I was unable to fully verify from the index whether `storage.ValidateRelativePath` imposes any additional character restrictions beyond traversal checks, and I could not inspect `s.archiveCache`'s underlying `Fetch`/locking semantics (e.g., whether it dedupes truly-concurrent identical-key requests or also affects sequential get requests after first population) within the available context. A Devin session with full repository access would be needed to confirm these two points precisely (`internal/gitaly/storage/locator.go`'s `ValidateRelativePath` implementation and the `streamcache`/`archiveCache` `Fetch` semantics referenced in `internal/gitaly/service/repository/server.go`).

```go
func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}
```

```go
// prefixLen reduces the risk of collisions due to different combinations of
// concatenated strings producing the same content.
// e.g. f+oobar and foo+bar concatenate to the same thing: foobar
func prefixLen(s string) []byte {
	return []byte(fmt.Sprintf("%08x%s", len(s), s))
}
```
