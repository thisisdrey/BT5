### Title
Gas-key nonce prefetch cache is never updated within a chunk, allowing nonce replay/double-spend across sequential gas-key transactions in the same chunk - (File: runtime/runtime/src/lib.rs)

### Summary
The transaction-processing loop resolves the "current nonce" for gas-key transactions from an immutable prefetch map `gas_key_nonces` populated before the loop starts, copying out the value (`*n`) rather than obtaining a mutable handle into the map. Because regular accounts/access-keys are looked up with `.get_mut()` (whose mutations persist in-place for later iterations of the same loop), but gas-key nonces are looked up with `.get()` and no write-back is performed afterward, two gas-key transactions targeting the same `(signer_id, pubkey, nonce_index)` in the same chunk both see the same stale `current_nonce`.

### Finding Description
In `process_transactions`/`verify_and_charge_transaction` loop in `runtime/runtime/src/lib.rs`, for gas-key transactions the code does: [1](#0-0) 
it fetches `nonce_entry = gas_key_nonces.get(&(signer_id, pubkey, nonce_index))` and copies out `*n` as `current_nonce`, then passes this plain value into `verify_and_charge_gas_key_tx_ephemeral`. This contrasts with the account and access-key lookups just above it, which use `.get_mut()` on their respective prefetch maps: [2](#0-1) 
so that in-place mutation of `account`/`access_key` state is visible to later transactions processed in the same loop iteration set. The gas-key nonce path has no equivalent mutable back-reference or explicit re-insert into `gas_key_nonces` after a transaction succeeds — the verdict-handling block that follows (building the outcome, receipt, and burnt-gas accounting) contains no call updating the `gas_key_nonces` map: [3](#0-2) 
Since gas-key nonces are deliberately stored outside the `AccessKey` struct (the access key's own `nonce` field is fixed at 0 for gas keys, per `add_gas_key`), the only place the "current nonce" is tracked during in-loop processing is this prefetch map: [4](#0-3) 
If this map is not refreshed between transactions in the same chunk, both `tx1(nonce_index=0, nonce=K+1)` and `tx2(nonce_index=0, nonce=K+2)` would be verified against the same stale `current_nonce = K`, both satisfying `tx_nonce > current_nonce`, and both would be converted into receipts / charged as if independently valid — a double-spend of the gas key's balance and duplicate execution of the attached actions.

I was not able to fully inspect `runtime/runtime/src/verifier.rs`'s `verify_and_charge_gas_key_tx_ephemeral` and `verify_nonce` implementations, or confirm definitively whether a write-back to `gas_key_nonces` occurs elsewhere in the loop (e.g., via a helper not captured in the reviewed line ranges) before the next transaction in the same list is processed. This is a real gap in my verification and should be checked directly in `runtime/runtime/src/verifier.rs` and the full body of the transaction loop before treating this as confirmed exploitable in production.

### Impact Explanation
If confirmed, this allows an attacker (an ordinary account owner with a funded gas key) to submit two or more transactions using incrementing nonces against the same gas-key nonce slot within a single chunk and have all of them accepted and converted to receipts, each independently debiting the gas key's balance and dispatching its attached actions — a double-spend/double-execution of gas-key-funded transactions, falling under double-spend/replay and token-inflation/loss-of-funds impact categories.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: any account can add a gas key with `num_nonces >= 1` via a normal `AddKey` action, fund it via `TransferToGasKey`, and then submit two ordinary signed transactions using the same `nonce_index` with sequential nonces to the public RPC, timed to land in the same chunk. No validator or node privilege is required — only normal transaction submission — making this trivially repeatable if the underlying prefetch-staleness is real.

### Recommendation
Update the gas-key nonce tracking to mirror the account/access-key pattern: either store `gas_key_nonces` as a map of mutable cells (e.g., `RefCell<Nonce>` or similar) that `verify_and_charge_gas_key_tx_ephemeral` updates in place upon success, or explicitly re-insert the new nonce into `gas_key_nonces` immediately after each successful (or deposit-failed-but-nonce-advancing) gas-key transaction, before the next transaction in the loop is processed. Add an assertion/test that a second same-nonce-index transaction in the same chunk is rejected with `InvalidNonce`.

### Proof of Concept
Runtime integration test (in `runtime/runtime/src/tests/apply.rs` or `test-loop-tests/src/tests/gas_keys.rs` style):
1. Set up an account with a gas key having `num_nonces = 1`, funded with sufficient balance, at initial nonce `K` (via `initial_nonce_value`).
2. Build two signed transactions `tx1` (nonce_index=0, nonce=K+1, small transfer/deposit) and `tx2` (nonce_index=0, nonce=K+2, small transfer/deposit) from the same gas key.
3. Submit both transactions in the same chunk/apply call (`apply_transactions` or the runtime test harness applying a `SignedTransaction` list in one call).
4. Assert: only one of the two transactions succeeds (produces a receipt / debits balance), and the other fails with `InvalidNonce`/`InvalidTxError` referencing the now-updated nonce — i.e., `tx2`'s effective `current_nonce` must reflect `tx1`'s just-applied nonce (`K+1`), not the stale prefetch value `K`.
5. Additionally assert total gas-key balance debited equals exactly one transaction's cost, not two, to directly capture the double-spend impact.
