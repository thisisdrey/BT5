Based on the investigation, I found a genuine analog to the reported bug class: **an authorization check enforced on one code path but silently skipped on a structurally-equivalent code path performing the same trust decision.**

### Title
Initiator-side handshake completion (`continueHandshake`) skips the lighthouse remote-allow-list check that the responder-side path (`beginHandshake`/`validatePeerCert`) enforces - ([File: handshake_manager.go])

### Summary
In the Centrifuge report, `transferTrancheTokens()` enforces a restriction-manager check when called through `CentrifugeRouter`, but the same logical operation on `PoolManager` omits the check, letting a frozen actor bypass a control that should apply uniformly to the action. The same class of "check present on one path, missing on the structurally-parallel path" exists in Nebula's handshake completion code.

### Finding Description
`HandshakeManager.validatePeerCert()` — used by the **responder** path (`beginHandshake`, at [1](#0-0) ) — derives `vpnAddrs` from the peer's just-verified certificate and then calls: [2](#0-1) 

i.e. it checks `f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr())` against the certificate-derived VPN addresses before the handshake is allowed to complete.

The **initiator** path, `continueHandshake` (processing the responder's stage-2 message), performs the analogous self-check ("Refusing to handshake with myself") inline, and comments that this "mirrors the responder-side check in `validatePeerCert`" ( [3](#0-2) ), but it never calls `AllowAll` against the certificate-derived `vpnAddrs` it just computed. The only remote-allow-list check in this path happens earlier, before the handshake even starts, against `hostinfo.vpnAddrs` — the initiator's originally *intended* target address ( [4](#0-3) ). Once the certificate is verified and the final `vpnAddrs` list is built at lines 892-921, that list is used directly to set `hostinfo.vpnAddrs = vpnAddrs` and complete the tunnel (`hm.Complete(hostinfo, f)`) with no second `AllowAll` check against the certificate's actual (possibly multi-network) address set ( [5](#0-4) ).

This mirrors the report's root cause exactly: the same authorization primitive (remote-allow-list / restriction check) is invoked in one code path that builds/derives a resource identity from a certificate (`validatePeerCert`, analogous to `CentrifugeRouter`'s hook-triggered check), but is missing on the parallel path that performs the equivalent identity resolution and trust decision (`continueHandshake`, analogous to `PoolManager.transferTrancheTokens()`).

### Impact Explanation
Nebula's `lighthouse.remote_allow_list` is a deployment-configured trust/segmentation control that restricts which real-world (UDP) addresses are permitted to be associated with which peers/subnets. Because a v2 certificate can carry multiple `netip.Prefix` networks (see certificate handling in `cert/`), an attacker holding a certificate whose primary/first network address passes the pre-handshake `AllowAll` check, but whose certificate also carries an additional network/address not permitted by `remote_allow_list`, can complete a handshake and have that additional address accepted into `hostinfo.vpnAddrs` without the allow-list ever validating it against the actual UDP source. This effectively bypasses the operator's IP/address-based trust segmentation for the initiator side, undermining a security boundary the operator explicitly configured, even though the exact same boundary is enforced for the responder side.

### Likelihood Explanation
This path is reachable by any peer that can complete a Noise IX handshake as a responder to a locally initiated connection — it does not require an already-established, blocklist-cleared long-term relationship beyond presenting a certificate the local CA pool accepts as far as `cert.CheckSignature`/expiry (the same certificate trust prerequisites apply to both paths, so this is not a "valid-certificate-holder-only" edge case beyond what the responder path also requires). The asymmetry is deterministic and code-path-inherent, not dependent on timing or race conditions, so it will trigger any time a peer's certificate includes an address that is unauthorized-but-not-checked on the initiator side.

### Recommendation
Apply the same `f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr())` check in `continueHandshake` against the certificate-derived `vpnAddrs` (the same list used in `validatePeerCert`), before calling `hm.Complete(hostinfo, f)` — mirroring the check already performed in `validatePeerCert` for the responder path, so both handshake completion paths enforce identical remote-allow-list authorization on the certificate-resolved address set.

### Proof of Concept
Conceptual PoC (not runnable without harness access):
1. Configure `lighthouse.remote_allow_list` to permit UDP address `A` for network `10.0.0.1/24` but deny it for network `10.0.0.5/24`.
2. Issue a certificate to a peer covering both `10.0.0.1/24` and `10.0.0.5/24`.
3. From address `A`, have that peer respond (as responder) to a locally-initiated handshake targeting `10.0.0.1`.
4. Observe that `continueHandshake` completes the tunnel and sets `hostinfo.vpnAddrs` to include `10.0.0.5`, without ever calling `AllowAll` against `10.0.0.5` — whereas if the roles were reversed (this peer as responder receiving an inbound handshake), `validatePeerCert` would call `AllowAll` on the full `vpnAddrs` set including `10.0.0.5` and could reject it.

**Uncertainty note:** I could not execute this against a live Nebula deployment to empirically confirm runtime behavior; the finding is based on static code-path comparison between `validatePeerCert` (responder) and `continueHandshake` (initiator completion) in `handshake_manager.go`. I also could not fully verify whether some other layer (e.g., firewall rule matching at packet time via `h.networks`/`buildNetworks`) independently re-validates `remote_allow_list` for addresses beyond the primary one — that would need confirmation via a live test or deeper trace through `firewall.go`'s `match`/`buildNetworks` before treating this as a confirmed exploitable bypass rather than a code-path inconsistency.

```go
// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
```
