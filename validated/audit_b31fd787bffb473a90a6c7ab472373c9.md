### Title
No L2 sequencer uptime check allows unfair liquidations immediately after sequencer recovery - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` allows any unprivileged liquidator to liquidate an unhealthy position, but there is no check on the L2 sequencer status nor any grace period after a sequencer outage. Metronome Synth is deployed on Optimism and Base (`deployments/base`, `deployments/optimism`), both sequencer-based L2s. A `grep` over the codebase shows zero references to a sequencer uptime feed, `latestRoundData` started-at checks, or any grace period (`sequencer|Sequencer|gracePeriod` — no matches). If the sequencer goes down, positions cannot be topped up or repaid; if collateral prices move adversely during the outage, the moment the sequencer resumes a liquidator can seize collateral in the very first blocks before the victim's recovery transaction can be included.

### Finding Description
`Pool.liquidate` at `contracts/Pool.sol:537-596` performs the following checks only: `whenNotShutdown`, `nonReentrant`, token-existence checks, `PositionIsHealthy` via `debtPositionOf`, `maxLiquidable` bound, `debtFloorInUsd`, and solvency bounds on `_totalSeized`. None of these gate liquidation on sequencer uptime:

```solidity
(bool _isHealthy, , , , ) = debtPositionOf(account_);
if (_isHealthy) {
    revert PositionIsHealthy();
}
```

`debtPositionOf` prices collateral/debt through `masterOracle()` (`Pool.sol:601-603`), an external oracle aggregator. A Chainlink feed's `updatedAt`/`startedAt` timestamps become stale during a sequencer outage, but the standard mitigation — reading the L2 sequencer uptime feed (`0xFdB...F492` on OP-stack chains) and enforcing a grace period after `status` flips back to up — is absent both in `Pool.sol` and anywhere else in the repo. Users have no mechanism (deposit, repay, swap) that becomes usable faster than `liquidate`, so the first-sequence race is won by the liquidator who submits the liquidation call immediately.

The analogous FlatMoney issue required the same observation: a permissionless `liquidate` with no sequencer check. Here the identical structure exists in `Pool.liquidate`, and the protocol is actively deployed on OP Mainnet and Base where this bug class applies.

### Impact Explanation
Direct loss of user funds: a borrower whose position would have remained healthy absent the outage (or who would have added collateral/repait during normal operation) loses collateral plus the `liquidatorIncentive` bonus computed by `quoteLiquidateOut`. During a long outage with large price movement, positions can be pushed deep underwater, and liquidation extracts the seized collateral at post-move prices with no opportunity for the victim to cure. This is loss of user collateral caused by the liquidation path itself, not by incorrect oracle data.

### Likelihood Explanation
L2 sequencer outages are a known recurring event on OP-stack chains (OP Mainnet and Base have both experienced multi-minute-to-hour outages). Any attacker/keeper bot monitoring `Pool.liquidate` can front-run or out-sequence victim recovery transactions the moment the sequencer accepts transactions again; liquidations are permissionless and profitable by design (`liquidatorIncentive`). No privileged role is needed — `liquidate` only reverts if `_msgSender == account_` or if the position is healthy.

### Recommendation
Integrate the Chainlink L2 sequencer uptime feed on OP/Base deployments: before executing `liquidate` (and ideally `debtPositionOf`-dependent mutating paths), require `sequencerUptimeFeed.latestRoundData().answer == 0` (up) and `block.timestamp - startedAt > GRACE_PERIOD` (e.g., 3600s), so users get a window to restore collateral ratios after the sequencer comes back. On chains without a sequencer feed (mainnet), skip the check.

### Proof of Concept
Hardhat fork on Optimism or Base:

```ts
it('liquidates immediately after sequencer resume, no grace period', async () => {
  // fork optimism at block N; alice deposits collateral + issues msETH (healthy)
  await msdWETH.deposit(parseEther('10'), alice.address);
  await msETHDebt.issue(amount, alice.address);

  // simulate outage effect: price moves against alice while she cannot act
  // (on fork: push oracle price update / warp into stale-then-fresh state)
  await masterOracle.updatePrice(weth.address, droppedPrice); // position now unhealthy

  // attacker liquidates in the same block the sequencer accepts txs again
  const tx = pool.connect(liquidator).liquidate(
    msETH.address, alice.address, amountToRepay, msdWETH.address
  );
  await expect(tx).to.emit(pool, 'PositionLiquidated'); // succeeds with no uptime/grace check
});
```

Key assertion: `liquidate` succeeds unconditionally once `debtPositionOf` reports unhealthy — there is no timestamp or sequencer-state gate anywhere in `Pool.sol` (grep for `sequencer|gracePeriod` returns no matches).
