### Title
`ProcReceiveHook` RPC trusts a client-supplied `TransactionID` without verifying the caller is the actual hook process for that transaction - ([File: internal/gitaly/service/hook/proc_receive.go])

### Summary
`HookServiceServer.ProcReceiveHook` accepts a `ProcReceiveHandler` built entirely from client-supplied stream data (environment variables containing a `TransactionID`, plus a pkt-line stream of ref updates) and immediately transmits it to whichever RPC (`UserFFBranch`, `PostReceivePack`, `SSHReceivePack`, etc.) is currently waiting on that same `TransactionID` in `ProcReceiveRegistry`. The only gate is "does a waiter exist for this ID" — there is no check that the caller invoking `ProcReceiveHook` is the same `gitaly-hooks` child process that git-receive-pack spawned for that specific transaction.

### Finding Description
`ProcReceiveRegistry.RegisterWaiter`/`Transmit` matches purely on `storage.TransactionID`, an integer extracted from the hook payload environment variable that any caller can present: [1](#0-0) 

The gRPC endpoint that accepts this data does no additional authorization beyond parsing the client-supplied environment/stdin and calling `Transmit`: [2](#0-1) 

Compare this to `SignalPostReceiveReady`, a structurally similar "internal coordination" RPC, which explicitly requires the call to originate from Praefect's backchannel and documents this as a deliberate anti-abuse measure: [3](#0-2) 

`ProcReceiveHook` has no equivalent check. Its authorization boundary is the generic Gitaly auth token used by every hook RPC (the `InternalSocketToken` embedded in `HooksPayload`), which is the same credential handed to *every* `gitaly-hooks` invocation for *every* push, not a credential scoped to one specific transaction: [4](#0-3) 

Because the token is not transaction-specific, any process capable of invoking a hook (i.e., any push that legitimately triggers `gitaly-hooks`) holds a credential that is accepted for *all* `HookService` RPCs, including `ProcReceiveHook`. This is directly analogous to the reported bug class: `onlyAcceptedCallers` verifies "is a generally accepted caller" but not "is specifically the loan contract this operation concerns." Here, Gitaly verifies "is a generally accepted internal caller" but not "is specifically the git-receive-pack/gitaly-hooks process spawned for transaction ID N." A caller that knows or predicts another concurrent push's `TransactionID` can craft its own `ProcReceiveHookRequest` (its own environment variables plus an arbitrary pkt-line ref-update stream) and have `Transmit` deliver it to the registered waiter for that other transaction, in place of the real git-receive-pack process's proc-receive hook.

The consumer of the resulting handler (`procReceiveHook` in `internal/gitaly/hook/receivepack/receive_pack.go`) trusts the handler's `ReferenceUpdates()`, `Atomic()`, and `PushOptions()` verbatim and drives real ref updates and hook execution (`UpdateHook`, `PostReceiveHook`, `updater.Commit()`) from that data: [5](#0-4) 

This mirrors the Gondi bug precisely: a component that is supposed to only be reachable from a specific trusted intermediary (the loan contract / the spawned git-receive-pack process) can instead be driven directly by a lower-trust actor because the access check validates "is an accepted caller" rather than "is the specific expected caller for this operation," letting it bypass the real proc-receive protocol (git's own ref safety checks, ancestor/quorum semantics enforced by the actual receive-pack) and inject arbitrary reference updates into someone else's push transaction.

### Impact Explanation
If exploited, an attacker who can trigger any push (thus obtaining a valid `InternalSocketToken`) and who can determine or race a victim's in-flight `TransactionID` could impersonate that victim's proc-receive hook, submitting attacker-chosen ref updates that get committed via `updater.Commit()` under the victim's repository and transaction context, and trigger `PostReceiveHook` with the attacker's fabricated changes. This could corrupt refs, spoof push notifications, or desynchronize replicas — comparable in nature to the "skip storage/state accounting checks by impersonating a trusted internal caller" impact in the source report.

### Likelihood Explanation
Exploitability hinges on: (1) whether `storage.TransactionID` values are predictable/enumerable (I was not able to fully confirm the allocation strategy — the grep for the ID-generation function did not return conclusive results due to a tool error, so this is unverified), and (2) whether an attacker's own push can be timed to race a legitimate concurrent push's transaction window. Given that `RegisterWaiter`/`Transmit` operate over a small, likely monotonically-increasing integer space shared process-wide, guessing or brute-forcing a concurrently active ID during periods of active traffic is plausible but not proven. This uncertainty should be resolved by inspecting `internal/gitaly/storage/storagemgr/transaction_registry.go` (not fully reviewed here) to see how transaction IDs are generated and scoped.

### Recommendation
Bind the `ProcReceiveHook` RPC's accepted `TransactionID` to the actual peer/session that registered the waiter — e.g., have `RegisterProcReceiveHook` generate and embed a per-invocation, unpredictable secret (nonce) in the `HooksPayload` alongside the `TransactionID`, and require `ProcReceiveHook`/`Transmit` to validate that secret before delivering the handler, similar to how `SignalPostReceiveReady` restricts itself to the Praefect backchannel. At minimum, ensure `storage.TransactionID` values are not predictable and are single-use per registration, and add a check that only a genuine hook invocation for that repository/transaction can transmit.

### Proof of Concept
Conceptual PoC (unverified against a running Gitaly cluster due to lack of a live environment for this analog):
1. Attacker issues an authenticated push (e.g., `SSHReceivePack`) which is required to call `RegisterProcReceiveHook`, giving the attacker a legitimate `InternalSocketToken` and observing the transaction-ID allocation pattern from their own `TransactionID`.
2. In parallel, a victim's push registers a waiter for `TransactionID = N+1` (or another nearby/observable value) via `RegisterProcReceiveHook`.
3. Before the victim's real `gitaly-hooks` process calls `ProcReceiveHook` with `TransactionID = N+1`, the attacker opens their own `ProcReceiveHook` gRPC stream, sets `HooksPayload.TransactionID = N+1` in the environment variables it sends, and supplies a crafted pkt-line stream describing attacker-chosen ref updates.
4. `ProcReceiveRegistry.Transmit` matches on `TransactionID` alone and delivers the attacker's handler to the victim's waiting `RegisterProcReceiveHook` goroutine, which then calls `procReceiveHook` and commits the attacker-supplied ref updates as if they came from the victim's push.

This PoC requires confirming: exact `TransactionID` value predictability/race window, and that `HookService`'s auth (internal socket token) does not otherwise scope a caller to one specific transaction — both of which I could not fully verify within the available tool budget.

func (r *ProcReceiveRegistry) RegisterWaiter(id storage.TransactionID) (<-chan ProcReceiveHandler, func(), error) {
	r.m.Lock()
	defer r.m.Unlock()

	if _, ok := r.waiters[id]; ok {
		return nil, nil, fmt.Errorf("cannot register id: %d again", id)
	}

	ch := make(chan ProcReceiveHandler)
	r.waiters[id] = ch

	cleanup := func() {
		r.m.Lock()
		defer r.m.Unlock()

		delete(r.waiters, id)
	}

	return ch, cleanup, nil
}

// Transmit transmits a handler to its waiter.
func (r *ProcReceiveRegistry) Transmit(ctx context.Context, handler ProcReceiveHandler) error {
	r.m.Lock()
	ch, ok := r.waiters[handler.TransactionID()]
	r.m.Unlock()

	if !ok {
		return fmt.Errorf("no waiters for id: %d", handler.TransactionID())
	}

	// It is possible that the RPC (waiter) returned because receive-pack
	// returned an error. In such scenarios, we don't want to block indefinitely.
	select {
	case <-ctx.Done():
		return ctx.Err()
	case ch <- handler:
	}

	return nil
}

func (s *server) ProcReceiveHook(stream gitalypb.HookService_ProcReceiveHookServer) error {
	ctx := stream.Context()

	firstRequest, err := stream.Recv()
	if err != nil {
		return structerr.NewInternal("receiving first request: %w", err)
	}

	stdin := streamio.NewReader(func() ([]byte, error) {
		req, err := stream.Recv()
		return req.GetStdin(), err
	})

	var m sync.Mutex
	stdout := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stdout: p})
	})

	stderr := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stderr: p})
	})

	handler, doneCh, err := gitalyhook.NewProcReceiveHandler(
		firstRequest.GetEnvironmentVariables(), stdin, stdout, stderr,
	)
	if err != nil {
		return structerr.NewInternal("creating handler: %w", err)
	}

	registry := s.manager.ProcReceiveRegistry()
	if err := registry.Transmit(ctx, handler); err != nil {
		return sendProcReceiveHookResponse(stream, 1, fmt.Sprintf("transmitting handler: %s", err))
	}

	if err := <-doneCh; err != nil {
		return sendProcReceiveHookResponse(stream, 1, fmt.Sprintf("handler finished: %s", err.Error()))
	}

	return sendProcReceiveHookResponse(stream, 0, "")
}

func procReceiveHook(
	ctx context.Context,
	logger log.Logger,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	tx storage.Transaction,
	handler hook.ProcReceiveHandler,
) (returnedErr error) {
	var acceptedUpdates []hook.ReferenceUpdate
	rejectedUpdates := make(map[git.ReferenceName]string)

	defer func() {
		if err := handler.Close(returnedErr); err != nil && returnedErr == nil {
			returnedErr = err
		}
	}()

	if handler.Atomic() {
		// Atomic reference updates are all or nothing. If this fails for any reason, return an error.
		err := receivePackReferenceUpdates(
			ctx, cfg, req, repo, hookManager, handler.ReferenceUpdates(), handler, handler,
		)
		if err != nil {
			return fmt.Errorf("updating references atomically: %w", err)
		}

		// There is no need to track rejected reference updates because we fail early if any updates
		// are not successful.
		acceptedUpdates = handler.ReferenceUpdates()
	} else {
		// Non-atomic reference updates are performed one at a time. Errors due to an update hook
		// failing are expected and should signal to the client it was rejected instead of
		// completely failing.
		for _, update := range handler.ReferenceUpdates() {
			if err := receivePackReferenceUpdates(
				ctx, cfg, req, repo, hookManager, []hook.ReferenceUpdate{update}, handler, handler,
			); err != nil {
				var (
					reason    string
					hookErr   hook.CustomHookError
					updateErr updateError
				)
				switch {
				case errors.As(err, &hookErr):
					reason = "update hook failed"
				case errors.As(err, &updateErr):
					reason = updateErr.Error()
				default:
					return fmt.Errorf("updating reference: %w", err)
				}

				rejectedUpdates[update.Ref] = reason
			} else {
				acceptedUpdates = append(acceptedUpdates, update)
			}
		}
	}

	commitLSN, err := tx.Commit(ctx)
	if err != nil {
		return fmt.Errorf("committing transaction: %w", err)
	}

	storage.LogTransactionCommit(ctx, logger, commitLSN, "proc-receive")

	for _, update := range handler.ReferenceUpdates() {
		if reason, rejected := rejectedUpdates[update.Ref]; rejected {
			if err := handler.RejectUpdate(update.Ref, reason); err != nil {
				return fmt.Errorf("rejecting update: %w", err)
			}
		} else {
			if err := handler.AcceptUpdate(update.Ref); err != nil {
				return fmt.Errorf("accepting update: %w", err)
			}
		}
	}
