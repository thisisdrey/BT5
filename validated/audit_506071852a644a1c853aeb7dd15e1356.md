### Title
Out-of-bounds read parsing attacker-controlled ZIP/JAR central directory entries in ijar - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar parses the ZIP/JAR central directory of an archive that Bazel treats as untrusted input (e.g. a `.jar` downloaded via `http_jar`/`http_archive`, or any jar consumed by `ijar` when generating interface jars). Unlike the local-file-header parser, which validates remaining bytes via `EnsureRemaining` before every read, the central-directory parser advances its cursor by attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) with no bound checking against the mapped file size, allowing the read cursor to run past the end of the `mmap`'d input file.

### Finding Description
`ProcessLocalFileEntry` carefully calls `EnsureRemaining()` before every variable-length read: [1](#0-0) 

In contrast, `ProcessCentralDirEntry`, which is the function that walks each entry of the central directory, never calls `EnsureRemaining`. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly off the wire and advances the raw pointer `p` by these fully attacker-controlled 16-bit values before the next iteration reads a new signature at the (potentially out-of-bounds) location: [2](#0-1)  and the tail of the function: [3](#0-2) 

The comment directly above the function acknowledges this design assumption but it is not actually enforced against a malicious/corrupted archive: [4](#0-3) 

The only containment check performed anywhere is a sanity check when locating the central directory from the End-Of-Central-Directory record, which bounds the *declared* central directory block against total file length but does nothing to prevent a single malformed entry's length fields from causing the cursor to run past that block or past the file: [5](#0-4) 

Because `file_name_length`, `extra_field_length`, and `file_comment_length` are each independent `u2` values (up to 65535 each) fully controlled by the archive author, a single crafted entry near the end of the mapped region can push `p` (and the subsequent `extra_p` walk over "extra fields", which also lacks a length check: [6](#0-5) ) far beyond the `mmap`'d file boundary, then dereference it (`get_u4le`, `get_u2le`, `memcpy` reading from `p`) — a direct out-of-bounds read, exactly analogous to the CVE-2018-7182 class of unchecked-length-driven OOB reads in a length-prefixed record parser.

### Impact Explanation
An out-of-bounds read here can crash the Bazel build (SIGSEGV reading unmapped pages beyond the file) or, in the read-into-buffer path via `memcpy(filename, p, len)`, potentially disclose adjacent process memory contents into the interface-jar filename buffer, which the build error/log could subsequently expose. This is triggered purely by ijar consuming a jar whose bytes are supplied by an untrusted/attacker-controlled origin (e.g. a poisoned or corrupted third-party jar dependency), matching the required "hostile origin server" premise, since ijar operates on jars used for compilation and does not perform any checksum-independent structural validation before parsing the central directory.

### Likelihood Explanation
Any build that runs `ijar` over an externally-fetched jar (a very common path for Java targets, e.g. `java_import`, jars from `http_jar`/`http_archive`/Maven-style external repos) is potentially affected as soon as the jar's bytes are attacker-influenced (e.g. a compromised mirror serving bytes that still match a declared checksum via a hash-collision, or more realistically a case where the checksum is not present/enforced, or a malformed jar the checksum-verified download itself contains). The bug is purely deterministic and low-effort to trigger — no special build-time features are required, only a crafted central-directory entry.

### Recommendation
Add `EnsureRemaining`-style bounds validation inside `ProcessCentralDirEntry` before reading `file_name_length` bytes, `extra_field_length` bytes, and `file_comment_length` bytes (and before the `extra_p` sub-field walk), so parsing fails safely with a diagnostic instead of advancing the cursor past the mapped file. Additionally, validate that each entry's cumulative advance stays within the previously-validated `central_dir_offset + central_dir_size` region.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`- or `src/test/shell/bazel`-style reproduction would:
1. Hand-craft a minimal valid ZIP/JAR containing a correct EOCD record (so `FindZipCentralDirectory` succeeds) with one central-directory entry near the end of the file.
2. Set that entry's `file_name_length` (and/or `extra_field_length`/`file_comment_length`) to `0xFFFF`, far exceeding the actual remaining bytes in the mapped file.
3. Feed this archive to `ijar`'s `ZipExtractor::Create`/`ProcessAll` (or to a Bazel build target relying on ijar to build an interface jar from this "dependency" jar).
4. Observe a crash (SIGSEGV) or a read of memory beyond the file's `mmap` region, confirming the out-of-bounds read.
