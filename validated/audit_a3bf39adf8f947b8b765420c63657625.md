### Title
Improper Authentication via Non-Constant-Time Token Comparison Enabling Unrestricted Brute-Force of Privileged RPC Endpoints - (File: `stackslib/src/net/api/postblock_proposal.rs`, also `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`)

### Summary
Six privileged Stacks node RPC endpoints (`/v3/block_proposal`, `/v3/blocks/replay/:id`, `/v3/blocks/simulate/:id`, `/v3/contracts/fast-call-read/...`, `/v3/transactions/simulate`, and the `broadcast=1` path of `POST /v3/blocks`) gate access with a single shared-secret `authorization` header compared against the configured token using plain Rust string inequality (`!=`), which is not constant-time. There is no rate limiting, attempt counting, or lockout on these comparisons anywhere in `stackslib/src/net/server.rs` or the surrounding HTTP peer code. This mirrors CWE-307 (Improper Restriction of Excessive Authentication Attempts) from the reported Lin-CMS advisory: an unauthenticated remote attacker can send unlimited guesses at the token, and can additionally exploit the non-constant-time comparison as a timing side-channel to recover the token byte-by-byte far faster than blind brute force.

### Finding Description
Each of the six handlers implements the identical pattern: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

`auth_header != password` uses `String`'s derived `PartialEq`, which internally calls `str::eq`, a byte-wise comparison that returns as soon as a mismatch is found (and also short-circuits on length mismatch). This is the standard, well-known timing side-channel in token/password comparisons — the amount of time taken leaks how many leading bytes of the guess match the true secret. No `subtle::ConstantTimeEq` or equivalent constant-time comparison is used anywhere in this codebase (confirmed via search — zero hits for `ct_eq`/`subtle::`/`constant_time`).

Compounding this, there is no failed-attempt tracking, exponential backoff, or IP-based lockout anywhere in the HTTP server path (`stackslib/src/net/server.rs`); the `openapi.yaml` documentation itself states the auth token is a "Plain-text secret value that must exactly equal" the configured password, confirming the design intent is a simple equality check with no additional hardening: [5](#0-4) 

An unauthenticated remote attacker connected to the node's RPC port can therefore:
1. Send unlimited authentication attempts with no throttling (classic brute force, matching the reported CWE-307/CVE-2020-18698 pattern), and
2. Use response-timing measurements against the byte-wise comparison to prune the search space per byte, dramatically reducing the number of guesses needed to recover the token — a capability strictly worse than the original report's plain brute-force weakness.

Once the token is recovered, the attacker gains write access to `/v3/block_proposal` (feeds block proposals into signer/miner logic) and authenticated `broadcast=1` block submission on `/v3/blocks`, i.e., privileged write paths that are supposed to be restricted to trusted operators/signers.

### Impact Explanation
This qualifies as Critical under the given impact criteria: it is an unauthenticated/unauthorized write path once the shared secret is recovered (`/v3/block_proposal`, authenticated `postblock_v3` broadcast), reachable by a remote, unprivileged attacker requiring only network access to the RPC port — no node secret or admin role is needed a priori, since the whole point of the flaw is that the "secret" itself is recoverable through the flawed comparison plus unlimited attempts.

### Likelihood Explanation
Likelihood is high for tokens of realistic length under active timing measurement, and the complete absence of throttling means classic brute force is also unrestricted regardless of network jitter — an attacker can simply run enough trials to average out noise. The vulnerability requires no special access; any TCP client that can reach the node's RPC listener can attempt it.

### Recommendation
- Replace all six `auth_header != password` checks with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or first comparing SHA-256/HMAC digests of both values).
- Add attempt-based rate limiting / exponential backoff / temporary lockout per source IP for failed `authorization` header checks on these endpoints, tracked in `HttpPeer`/`stackslib/src/net/server.rs`.
- Consider replacing the static shared-secret model with a signed/HMAC-based challenge or short-lived token to reduce the value of any single leaked comparison.

### Proof of Concept
1. Configure a stacks-node with `connection_options.auth_token` set (enabling `/v3/block_proposal`).
2. From a remote unprivileged client, repeatedly `POST /v3/block_proposal` with an `authorization` header value being a candidate token, incrementally lengthening the correct-prefix guess.
3. Measure round-trip response time for the 401 response for each candidate; because `!=` on `String` compares byte-by-byte and returns on first mismatch, candidates sharing a longer correct prefix take measurably longer to reject (extra byte comparisons) versus a random guess, letting the attacker recover the token character-by-character.
4. Repeat until the full token is recovered, then issue an authenticated request to `/v3/block_proposal` or `POST /v3/blocks?broadcast=1` to demonstrate unauthorized write access.
