Based on my investigation, the closest analog to the iccDEV `CIccFileIO::Read8()` bug class (unchecked read producing an out-of-bounds access) that is reachable by an unprivileged, single-transaction actor is the unchecked offset/length arithmetic in `PrecompiledContracts.extractSigArray()` / `extractBytesArray()` in java-tron.

### Title
Unchecked attacker-controlled offset/length arithmetic in `PrecompiledContracts.extractBytes()`/`extractSigArray()` allows crafted TVM call data to trigger out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`extractSigArray()` and `extractBytesArray()` decode attacker-supplied ABI call data for the batch-signature-validation precompiled contract without validating that the derived `bytesOffset`/`len`/`SIG_LENGTH` values stay within the bounds of the supplied `data` array before calling `extractBytes()`, which performs `Arrays.copyOfRange(data, offset, offset + len)` [1](#0-0) . This mirrors the iccDEV bug class where a length/offset value taken directly from untrusted file data is used in a read/copy operation without first checking it against the buffer's actual bounds.

### Finding Description
`extractSigArray(DataWord[] words, int offset, byte[] data)` reads `len` from `words[offset].intValueSafe()` and, for each signature slot `i`, computes `bytesOffset` from `words[offset + i + 1].intValueSafe() / WORD_SIZE`, then calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, SIG_LENGTH)` [2](#0-1) . `extractBytesArray` has the analogous pattern but also derives `bytesLen` from attacker data [3](#0-2) . Neither function bounds-checks the resulting `offset`/`offset+len` against `data.length` before calling `extractBytes`, which does a raw `Arrays.copyOfRange(data, offset, offset + len)` [4](#0-3) . Since `words[...]` values are fully attacker-controlled (32-byte words from the TVM call data passed to the batch-validate-sign precompile), a crafted `bytesOffset` or `len` can drive `offset` negative or far beyond `data.length`, or make `offset + len` overflow/underflow, causing `Arrays.copyOfRange` to throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`/`IllegalArgumentException` at runtime rather than being rejected as invalid input up front. This is analogous to `CIccFileIO::Read8()` trusting a length value read from untrusted profile data and using it directly in a buffer operation without validating it against the actual buffer size.

### Impact Explanation
In Java, an out-of-bounds `Arrays.copyOfRange` call does not corrupt heap memory the way a C/C++ buffer overflow does; it throws a runtime exception. The concrete impact is therefore constrained to how that exception propagates: if it is not caught by the TVM interpreter's opcode/precompile dispatch and results in an unhandled exception escaping transaction execution, it could crash the node process or abort block/transaction processing, denying service. I was not able to fully trace, within the available index, whether the top-level TVM `CALL`/precompile-dispatch path wraps `execute()` calls in a catch-all that converts such exceptions into a normal "revert" versus letting them propagate as uncaught errors — this needs direct verification of the calling opcode handler (`Program`/`PrecompiledContracts.execute` dispatch) before confirming node-crash severity.

### Likelihood Explanation
Any unprivileged account can invoke the batch-validate-sign precompiled contract via a normal Solidity `CALL`/`STATICCALL` with crafted ABI-encoded arguments, so the reachability is trivial — a single crafted transaction suffices to drive `words[...]` and `data` into the vulnerable arithmetic.

### Recommendation
Add explicit bounds validation in `extractSigArray`, `extractBytesArray`, and `extractBytes` (verify `offset >= 0`, `len >= 0`, and `offset + len <= data.length`) before performing `Arrays.copyOfRange`, returning an empty/invalid result instead of allowing the exception to propagate, consistent with the bounds checks already used elsewhere (e.g., `RLP.verifyLength()` at [5](#0-4)  and `ContractEventParser.subBytes()` at [6](#0-5) ).

### Proof of Concept
Craft a transaction that invokes the batch-validate-sign precompiled contract (address configured via `VMConfig`) with ABI-encoded call data where the "signatures" array length word at `words[offset]` is a large value and/or the per-entry offset word at `words[offset + i + 1]` encodes a negative or out-of-range byte offset (e.g., `0xFFFFFFFF...` word), causing `bytesOffset` to be negative or huge; when `extractSigArray` calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, SIG_LENGTH)`, the resulting `offset` argument to `Arrays.copyOfRange` falls outside `[0, data.length]`, throwing an unchecked exception during precompile execution [1](#0-0) .

**Caveat**: I could not verify within the indexed code whether the TVM's precompile dispatch/opcode execution path catches this exception and safely reverts the transaction, or whether it propagates uncaught. This distinction determines whether the issue is a benign-revert (no real impact) or a genuine DoS/crash — full confirmation requires reading the `Program`/opcode CALL-dispatch code that invokes `PrecompiledContract.execute()`, which was not available in the index for this pass. A Devin session with full repository access would be needed to trace that call chain conclusively.
