### Title
Missing bounds validation of untrusted CDH/LH size fields in singlejar's ZIP entry iteration allows out-of-bounds reads - (File: `src/tools/singlejar/output_jar.cc`, `third_party/ijar/zip_headers.h`)

### Summary
The CVE-2023-28448 analog is: `Versionize::deserialize` trusted a length field from an untrusted serialized header to index into a flexible array without checking it matched the actual allocated/available bytes, causing OOB access. In Bazel's singlejar (which merges JAR files produced from external Maven/Java dependencies pulled by `java_import`/`rules_jvm_external` etc. into a single deploy jar), the same bug class appears in how Central Directory Header (`CDH`) and Local Header (`LH`) records are walked: fields like `file_name_length()`, `extra_fields_length()`, and `comment_length()` are read directly from attacker-controlled bytes inside a dependency JAR and used to compute `size()`/pointer offsets (`zip_headers.h:301-311`, `zip_headers.h:502-505`) without first checking these lengths against the remaining bytes actually mapped from the file.

### Finding Description
`LH::size()` and `CDH::size()` in `third_party/ijar/zip_headers.h` (and the very similar structures in `src/tools/singlejar/zip_headers.h`) compute the record length purely from the two/three 16-bit length fields embedded in the header itself: [1](#0-0) 
and [2](#0-1) 

These lengths (`file_name_length_`, `extra_fields_length_`, `comment_length_`) come straight from bytes of a JAR file that Bazel is asked to merge/repackage — i.e., a file published by an unprivileged, untrusted third party (a Maven artifact, a genrule output from an external repo, etc.), not something the root repository author controls. `output_jar.cc`'s `AppendToDirectoryBuffer`/`WriteEntry` code walks the "extra fields" chain using `ExtraField::next()`, which itself advances by `size()` derived from an attacker-controlled `payload_size_` field: [3](#0-2) 

While some call sites (e.g. `OutputJar::WriteEntry`, `AppendToDirectoryBuffer`) do bound the *extra field* iteration against a previously computed `ef_end`, that `ef_end` itself is derived from the *stated* `extra_fields_length()`/`file_name_length()` fields taken from the header, which is only trustworthy if those stated lengths are already known to fit inside the mapped file. The `TransientBytes::ReadEntryContents`/`DecompressEntryContents` helpers used by `Log4J2PluginDatCombiner::Merge` and others compute `uncompressed_file_size`/`compressed_file_size` purely from the LH/CDH header fields and then call `Append(lh->data(), uncompressed_file_size)`, reading `uncompressed_file_size` bytes starting at `lh->data()` without any check that this range lies within the memory-mapped input file: [4](#0-3) 

This mirrors the `FamStructWrapper` bug precisely: a struct whose "flexible array" region size is dictated by an attacker-supplied header field, consumed by code that trusts the field to bound the array without cross-checking it against the buffer that was actually mapped/read.

### Impact Explanation
If an unvalidated length field (`file_name_length`, `extra_fields_length`, `comment_length`, or the derived `uncompressed_file_size`/`compressed_file_size`) is larger than what actually remains in the memory-mapped JAR file, `LH::data()`/`extra_fields()`/`ExtraField::next()` pointer arithmetic will point past the end of the mapped region, and subsequent `memcpy`/`Append` calls will read out-of-bounds heap/mmap memory into the combined output JAR (an information disclosure of adjacent process memory embedded into build outputs) or crash the `singlejar` process (denial of availability during the build). This matches CWE-125 (out-of-bounds read) in the same "header length trusted, buffer length unchecked" pattern as the advisory.

### Likelihood Explanation
I could not fully confirm exploitability within the available read-only inspection. `third_party/ijar/zip.cc`'s `InputZipFile::ProcessLocalFileEntry` (used by `ijar`, a different consumer) does call `EnsureRemaining()` before trusting `file_name_length_`/`extra_field_length_`: [5](#0-4) 
and `src/tools/singlejar/output_jar.cc`'s extra-field walkers do check `ef->size()` against a computed `lh_ef_end`/`ef_end`: [6](#0-5) 

I was not able to locate, within the indexed portion of the repo, the specific call site in `src/tools/singlejar` that computes `lh_ef_end`/entry sizes for `LH`/`CDH` records *before* these existing checks run, to confirm whether that upstream computation itself validates the header lengths against the mapped file bounds (analogous to `input_jar.cc`'s `LocateCentralDirectory`, which does perform such validation for the central-directory-level fields `cen_offset32()`/`cen_size32()`). Because `LocateCentralDirectory` shows Bazel authors are aware of, and do implement, this exact class of check at the central-directory level, it is plausible equivalent validation also exists (or is expected) at the per-entry `LH`/`CDH` level and I could not rule it out with certainty from the code surfaced by search.

### Recommendation
Given the uncertainty above and the "no vulnerability without concrete verified bypass" bar required by the rules, I do not have sufficient evidence to assert a *confirmed*, currently-unmitigated OOB bypass in singlejar's per-entry header handling — only a structurally similar risky pattern (trusting a header-embedded length to bound access without an evidenced remaining-bytes check at that exact call site). A background engineer should audit every `LH`/`CDH`/`ExtraField` consumer in `src/tools/singlejar/` and `third_party/ijar/` to ensure each header length (`file_name_length`, `extra_fields_length`, `comment_length`, `compressed_file_size`, `uncompressed_file_size`) is validated against the actual remaining mapped-file bytes before being used in pointer arithmetic or `memcpy`, mirroring the fix pattern already present in `InputJar::LocateCentralDirectory` and `InputZipFile::ProcessLocalFileEntry`'s `EnsureRemaining`.

### Proof of Concept
Not established — I could not construct and verify a concrete reproduction (e.g., a crafted JAR with `extra_fields_length` exceeding the mapped file size fed through `singlejar --sources bad.jar`) that survives all existing checks, given the constraints of this analysis. This finding should be treated as an audit lead rather than a confirmed vulnerability.
