### Title
Defuse blindly trusts the caller-reported `amount` in `ft_on_transfer`/`mt_on_transfer` for fee-on-transfer/deflationary tokens, letting depositors mint uncollateralized internal balance - (File: `contracts/defuse/src/contract/tokens/nep141/deposit.rs`)

### Summary
The Defuse contract credits a user's internal multi-token ledger with exactly the `amount` value reported in the `ft_on_transfer`/`mt_on_transfer` callback arguments, without ever checking that the contract's own custodied balance of the underlying token actually increased by that amount. This is the same trust-boundary defect described in the Polkaswap report: the system accepts an externally-controlled token's self-reported transfer amount as ground truth for internal accounting, with no mechanism to detect or reject tokens whose transfer semantics deduct value (deflationary/fee-on-transfer/upgraded tokens) before it reaches the recipient.

### Finding Description
`ft_on_transfer` takes the `amount` parameter supplied by the calling NEP-141 contract and passes it straight into `Contract::deposit`, which increments both `total_supplies` and the receiver's `token_balances` by that exact figure: [1](#0-0) 

`deposit()` performs no comparison against the contract's actual token balance on the underlying NEP-141 contract - it just adds `amount` to `total_supplies` and to the owner's `token_balances`: [2](#0-1) 

The same pattern repeats for `mt_on_transfer` (`contracts/defuse/src/contract/tokens/nep245/deposit.rs`) and `nft_on_transfer`, and for the withdrawal-refund path (`ft_resolve_withdraw`) which similarly trusts the promise-returned "used" amount from the token contract rather than verifying actual balance movement: [3](#0-2) 

Because any `AccountId` can be used as the NEP-141 predecessor to mint a `TokenId::Nep141` inside Defuse (there is no allow-list or verified-balance check gating which tokens can be deposited), a token whose `ft_transfer_call` implementation burns or redirects a fraction of the transferred amount before invoking `ft_on_transfer` (a deflationary/tax token, or a proxy token upgraded to add such behavior) will cause Defuse to credit the *pre-fee* amount while only the *post-fee* amount is actually received into Defuse's custodied balance on that token contract.

Binding broken: `internal ledger credit (amount reported by ft_on_transfer)` should equal `actual increase in Defuse's held balance of that token`. After an attacker deposits N units of a deflationary token, Defuse's internal `total_supplies`/`token_balances` record N, but the real balance held by the Defuse account on the token contract is `N - fee`. The deficit is socialized against every other holder of that same `TokenId`, and the attacker (or any subsequent withdrawer racing to withdraw first) can withdraw up to N, i.e., more than what is actually custodied for that token, at the expense of other depositors of the same asset.

### Impact Explanation
This crosses the "value debited versus value delivered" ledger-conservation boundary: Defuse credits internal balance based on the sender-reported transfer amount instead of the amount actually received into its own custody. This directly enables credited/withdrawable balances that are not backed by real custodied tokens, which is a form of over-crediting without valid backing - qualifying as Critical impact (tokens credited without them actually having been transferred in full, ultimately allowing later withdrawals to exceed the real custodied balance for that token, at other depositors' expense).

### Likelihood Explanation
Exploitability requires only that the attacker control (or find and use) a NEP-141/NEP-245 token contract with non-1:1 transfer semantics (fee-on-transfer, deflationary, or upgraded proxy token) and call `ft_transfer_call`/`mt_transfer_call` into Defuse - no privileged role, relayer key, or DAO action is needed. The main constraint is finding or deploying such a token that other users are also willing to hold/trade inside Defuse under the same `TokenId`, since the loss is realized only when total withdrawals exceed the real custodied balance.

### Recommendation
Verify actual balance delta on deposit (e.g., query `ft_balance_of`/`mt_balance_of` for Defuse's own account before and after accepting the transfer, or otherwise reconcile total internal supply against the real custodied balance periodically) rather than trusting the caller-supplied `amount` argument. Alternatively/additionally, maintain an explicit allow-list of supported token contracts vetted for standard-compliant, non-deflationary transfer semantics, and require re-approval before accepting deposits from a token that has changed its code (e.g., via an upgradeable proxy).

### Proof of Concept
1. Deploy a NEP-141 token `evil.near` whose `ft_transfer_call` implementation burns 10% of the transferred amount before invoking `ft_on_transfer` on the receiver (functionally identical to what an upgraded/deflationary ERC20-style proxy would do).
2. Attacker calls `evil.near::ft_transfer_call(defuse, amount=1000, msg=<self-deposit>)`. Defuse's actual token balance on `evil.near` increases by only 900, but `ft_on_transfer` reports `amount=1000` to `contracts/defuse/src/contract/tokens/nep141/deposit.rs`, which calls `Contract::deposit` and credits the attacker's `mt` balance for `nep141:evil.near` with the full 1000.
3. Attacker (or any other holder of the same `TokenId`) now can withdraw funds against a 1000-unit internal ledger balance backed by only 900 real custodied tokens, causing the last withdrawer(s) of that token to be unable to redeem, while the attacker who exploited the desync exits with more value than actually deposited.

    fn ft_on_transfer(
        &mut self,

        require!(amount.0 > 0, "zero amount");

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {

        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
