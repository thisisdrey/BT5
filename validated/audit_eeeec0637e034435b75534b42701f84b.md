### Title
Overlapping-validity-window replay lets an attacker indefinitely re-bind a personhood identity/alias between two accounts using two pre-collected proofs - (File: `substrate/frame/people/src/extension.rs`)

### Summary
The external report's core broken invariant is: a signed artifact (oracle price) remains valid for a whole validity window, and an attacker who collects two such artifacts (p1, p2) can replay them arbitrarily inside that window to flip system state back and forth, extracting value from the flip. The `pallet-people` transaction extension `AsPerson` reproduces the identical primitive: a signed personhood proof binds an `account` to a `PersonalAlias`/`PersonalIdentity` via `set_alias_account`/`set_personal_id_account`, and that proof stays "replayable" for the whole `account_setup_time_tolerance` window relative to `call_valid_at`. If two such proofs (for two different target accounts) are collected with overlapping validity windows, both remain replayable and the caller can toggle the identity binding between the two accounts indefinitely for the duration of the overlap — the exact "known signed data + validity window + repeated flip" primitive from the oracle report.

### Finding Description
In `AsPerson::validate` ( [1](#0-0) ), for `AsPersonInfo::AsPersonalAliasWithProof`, the only staleness/replay check is:
- `now < call_valid_at` → `Future`
- `now > call_valid_at + account_setup_time_tolerance` → `Stale`
- replay is rejected **only** if the target `account` is already the one currently stored for that alias (`AccountToAlias::<T>::get(account) == stored_rev_ca`).

The identical pattern exists for `AsPersonInfo::AsPersonalIdentityWithProof` targeting `set_personal_id_account` ( [2](#0-1) ).

The type documents this exact weakness itself: [3](#0-2) 

This means: an attacker with a valid personhood commitment can pre-generate two signed proofs, at `call_valid_at = t0` binding to account A, and at `call_valid_at = t1` binding to account B, chosen so `[t0, t0+tolerance]` and `[t1, t1+tolerance]` overlap. Inside the overlap, the attacker can submit `set_alias_account(A, t0)` then `set_personal_id_account`/`set_alias_account(B, t1)` then back to A, then back to B, etc. — each call only fails if it re-targets the account currently already bound (the "no-op" replay), but flipping A→B→A→B is never rejected because the stored comparison only blocks the exact previous target, not the previously-used proof itself. Nonce-based replay protection (`CheckNonce`) is not the guard here, since the "None"-origin proof path builds validity from `provides`/`Stale` checks on stored account state, not nonces — this is functionally the same weakness as the oracle attack: a signed artifact remains "usable" for its entire validity window and can be alternated with a second signed artifact to move state back and forth.

### Impact Explanation
`Origin::PersonalAlias`/`Origin::PersonalIdentity` is the sybil-resistance/uniqueness primitive pallet-people exists to provide: exactly one account should be authoritatively bound to a given proven personhood/alias at any time so that downstream pallets relying on "one alias == one account, settled once" (e.g. quotas, one-time claims, voting weight, meritocratic payouts) can trust the binding. The documented indefinite-replay window means the "settle exactly once" guarantee is violated for the duration of `account_setup_time_tolerance`: any downstream logic that reads the current `AccountToAlias`/`AccountToPersonalId` mapping and gates a one-per-personhood action (e.g. a claim, salary payout, or governance right) can be triggered from account A, then the binding flipped to B and the same action triggered again from B, and so on — the attacker effectively obtains multiple executions of a personhood-gated action from the same underlying proof of personhood within one tolerance window. This is a runtime bug that compromises the intended one-account-per-identity invariant (aligned with "runtime bugs that compromise intended behavior" and "duplicate settlement or payout" in the impact gate), without requiring any privileged, governance, validator, or relayer role — the attacker only needs their own two proofs and unprivileged extrinsic submission.

### Likelihood Explanation
The condition needed (two proofs with overlapping `call_valid_at` + `account_setup_time_tolerance` windows) is entirely attacker-controlled: the attacker chooses `call_valid_at` for both proofs and submits both inside the current tolerance window, which the pallet explicitly documents as achievable ("If 2 transactions that set 2 different accounts are sent for an overlapping validity period, then those 2 transactions can be replayed indefinitely for the duration of the overlapping period"). No malicious peer, validator, collator, or leaked key is required, matching the bug class from the oracle report (attacker collecting two already-known valid signed prices and swapping between them repeatedly).

### Recommendation
Bind replay-protection to the specific proof/signature (or a monotonically increasing setup sequence number per alias/identity) rather than only to the currently-stored target account, so that once a given proof has been consumed it cannot be reused to move the binding to a different account within the same tolerance window. Alternatively, shrink `account_setup_time_tolerance` to the minimum necessary for practical inclusion, and/or require any overlapping re-bind to also be rejected until the previous bind's own tolerance window has fully elapsed, closing the flip-flop window entirely.

### Proof of Concept
1. Attacker generates proof P1 for `ring_index=R`, valid at `call_valid_at=t0`, targeting `set_alias_account(account=A, call_valid_at=t0)`.
2. Attacker generates proof P2 for the same ring/personhood, valid at `call_valid_at=t1` where `t1 <= t0 + account_setup_time_tolerance` (i.e., overlapping window), targeting `set_alias_account(account=B, call_valid_at=t1)`.
3. At block `t1` (inside both tolerance windows), submit the extrinsic with `AsPersonInfo::AsPersonalAliasWithProof(P1, R, ctx)` calling `set_alias_account(A, t0)` → succeeds, binds alias to A (`AccountToAlias[A] = rev_ca`).
4. Any downstream personhood-gated action executable from account A is triggered.
5. Still inside the overlap, submit with `AsPersonInfo::AsPersonalAliasWithProof(P2, R, ctx)` calling `set_alias_account(B, t1)` → succeeds because `AccountToAlias::get(B)` does not equal `rev_ca` yet (the stale-check only blocks re-targeting the *same* account already bound) — binds alias to B.
6. Downstream action re-triggered from account B.
7. Re-submit step 3's extrinsic again (still inside `[t0, t0+tolerance]`): `AccountToAlias::get(A)` currently equals `rev_ca` for B's binding logic check on... wait — the stale check compares against the account being targeted, so re-targeting A again succeeds because A is not currently the bound account. Binding flips back to A.
8. Repeat steps 3–7 as many times as fit within the overlapping tolerance window, each flip potentially re-triggering any single-per-personhood downstream logic keyed by the currently-bound account. [4](#0-3) [5](#0-4)

					return Err(InvalidTransaction::Call.into());
				};

				let now = frame_system::Pallet::<T>::block_number();
				if now < *call_valid_at {
					return Err(InvalidTransaction::Future.into());
				}
				let time_tolerance = Pallet::<T>::account_setup_time_tolerance();
				if now > call_valid_at.saturating_add(time_tolerance) {
					return Err(InvalidTransaction::Stale.into());
				}

				let key = People::<T>::get(index)
					.map(|record| record.key)
					.ok_or(InvalidTransaction::BadSigner)?;

				let msg = inherited_implication.using_encoded(sp_io::hashing::blake2_256);

				if !T::Crypto::verify_signature(signature, &msg[..], &key) {
					return Err(InvalidTransaction::BadProof.into());
				}

				// This protects again replay attack.
				if People::<T>::get(index).is_some_and(|record| {
					record.account.is_some_and(|stored_account| stored_account == *account)
				}) {
					return Err(InvalidTransaction::Stale.into());
				}

				// The extrinsic provides the setup of the account for the personal id.
				let provides = twox_64(&("setup", index, &account).encode()[..]);
				let valid_transaction =
					ValidTransaction::with_tag_prefix("Ppl:Id").and_provides(provides).into();

				// We transmute the origin.
				let local_origin = Origin::PersonalIdentity(*index);
				let mut origin = origin;
				origin.set_caller_from(local_origin);

				Ok((valid_transaction, Val::UsingProof, origin))
