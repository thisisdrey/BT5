## Analysis

The Zebra CVE's root cause is a verification shortcut: a *partial* identifier (the ZIP-244 `txid`, which deliberately excludes authorization/signature data) is used as a proxy for "this data has already been fully verified," so a node accepts differing actual content that happens to share that partial identifier.

Gitaly has a structurally analogous pattern in its cross-node consistency/consensus mechanism: `CalculateChecksum`.

### Root cause

`internal/git/checksum.go` computes a repository "checksum" by running `git show-ref --head`, filtering to a fixed set of ref namespaces, and XOR-combining the SHA1 of each `"<oid> <name>"` line: [1](#0-0) [2](#0-1) 

Critically, this "checksum" only covers **reference name → target OID pairs**. It never reads, walks, or validates the actual object graph (commits/trees/blobs) that those OIDs point to: [3](#0-2) 

This checksum is then treated as ground truth for consensus/replication decisions in Praefect:

- `internal/praefect/recovery.go`'s `recoverPendingTransaction` calls `repoChecksum()` (which invokes `CalculateChecksum`) on the primary and every expected voter, and if a secondary's checksum equals the primary's, it is classified as `updated` and its generation is advanced via `IncrementGeneration`; only checksum-mismatched nodes get queued for replication: [4](#0-3) 

- The same pattern is used in replication confirmation (`confirmChecksums`) and in `RepositoryReplicas` reporting.

### Why this is analogous to CVE-2026-34377

Just as Zebra's cache treated "same `txid`" as "same fully-verified transaction" while `txid` excludes signature/proof data, Gitaly's checksum treats "same ref-name/OID set" as "same repository state" while excluding the actual object content. An OID normally binds cryptographically to its object, but this checksum mechanism never confirms the referenced objects are even present, complete, or uncorrupted on the storage being checksummed — `git show-ref` only reads the ref pointer files/tables, not object files. A test comment in the codebase explicitly acknowledges this class of ambiguity: [5](#0-4) 

An ordinary user driving pushes/fetches that trigger partial or interrupted replication (e.g., timing a repack/prune, a crafted set of ref updates, or exploiting a window where `ReplicateRepository` has copied refs metadata but not yet completed transferring all pack objects) can cause a secondary's refs to match the primary's checksum while the secondary is actually missing or has corrupted underlying objects for those refs. Praefect's recovery/consistency logic would then mark that secondary as `updated`/consistent and advance its generation — meaning it can be selected to serve reads (or as a replication source) despite not actually holding valid data for those refs, all without a proper replication ever having verified object completeness.

Additionally, using per-ref-line SHA1 values combined via **XOR** (rather than a proper accumulating hash such as HMAC-chained or ordered SHA of the full serialized ref list) is an algebraically weak construction: XOR is commutative, order-independent, and self-cancelling, which further weakens the checksum's ability to detect certain classes of divergence (e.g., two refs swapping OIDs, or duplicate cancelling pairs) compared to a real content hash of the reachable object graph.

### Assessment against scope rules

This finding involves object-pool/replication consistency logic reachable via ordinary push/fetch/replication flows (no privileged actor, no malicious peer/MITM assumption, no leaked token) and results in a genuine storage/consensus-integrity gap: Praefect can consider a replica "verified"/"up to date" without any confirmation that the underlying git objects for its refs actually exist or are intact. I'm treating this as a valid analog because the mechanism (identifier-based verification shortcut that omits full-content verification, used for cluster-wide consensus decisions) directly mirrors the reported bug class.

### Title
Praefect/Gitaly Consensus Relies on Ref-Only Checksum That Never Verifies Underlying Object Data — ([File: internal/git/checksum.go])

### Summary
`CalculateChecksum` (used by Praefect for replication consistency checks, crash recovery via `RecoverPendingTransactions`, and replica reporting) computes a checksum solely from `git show-ref` output — reference names and their target OIDs — via an XOR-combined SHA1. It never verifies that the objects those OIDs reference are actually present, complete, or valid on the storage being checksummed. Praefect treats a checksum match as proof of full data consistency and uses it to advance generation numbers (marking nodes as up-to-date and read-eligible) and to decide which nodes need replication.

### Finding Description
- `internal/git/checksum.go`'s `Checksum` type is built by XOR-ing SHA1 hashes of individual `"<oid> <name>"` lines pulled from `git show-ref --head` output, filtered to a fixed ref-namespace allowlist.
- `CalculateChecksum` in `internal/gitaly/service/repository/calculate_checksum.go` exposes this as an RPC, and does not perform `git-fsck`/object-walk verification of the referenced objects.
- `internal/praefect/recovery.go`'s `recoverPendingTransaction` uses checksum equality between the primary and each secondary as the sole criterion for classifying a node as `updated` (generation advanced, no replication scheduled) versus `outdated` (replication scheduled).
- This mirrors the CVE-2026-34377 pattern: a partial identifier (ref name + target OID set) is used as a stand-in for full verification of the underlying data (object graph), and mismatches between the two are not detected by the mechanism, allowing divergent underlying data to be accepted as consistent.

### Impact Explanation
If a secondary's ref pointers match the primary but the underlying git objects are missing, incomplete, or corrupted (e.g., due to an interrupted or racing replication job, concurrent housekeeping, or storage partial failure), Praefect's recovery logic will mark that secondary as fully replicated and eligible to serve as an authoritative/read source, without ever scheduling the replication needed to fix it. This is a consistency/consensus integrity gap in the clustered storage layer: the system of record (Praefect's generation tracking) can silently diverge from physical reality, analogous to the consensus-split described in the CVE, though localized to Gitaly's own cluster-consistency guarantees rather than the whole distributed network.

### Likelihood Explanation
Requires a specific timing/administrative window (crash recovery racing with in-flight object replication, or repository housekeeping mutating objects between ref-checksum reads) rather than a single crafted RPC field, so exploitability by an ordinary user is indirect and depends on triggering such races. The underlying weakness (checksum validates refs only, not the reachable object graph) is a permanent design gap independent of any specific race, however.

### Recommendation
Extend the consistency check used for generation advancement to verify presence/integrity of the objects reachable from the ref set (e.g., incorporate `git rev-list --objects --all | git cat-file --batch-check` completeness, or leverage `git-fsck`-style connectivity checks) rather than relying solely on ref-name/OID checksums. Replace the XOR-combination with an order-sensitive accumulating hash of the full sorted ref list to remove the self-cancelling algebraic weakness.

### Proof of Concept
Conceptual reproduction path (requires access to trigger replication/recovery timing, not a single RPC):
1. Trigger a `ReplicateRepository` job from primary to secondary.
2. Interrupt or race the job so that ref updates (packed-refs/reftables) land on the secondary before all referenced pack objects finish copying.
3. Trigger Praefect's crash/pending-transaction recovery path (`RecoverPendingTransactions`) while in this state.
4. `repoChecksum()` on the secondary returns the same value as the primary (refs match) even though objects are incomplete; `IncrementGeneration` marks the secondary consistent, and no replication event is queued to fix the missing objects.

var refsAllowed = regexp.MustCompile(`HEAD|(refs/(heads|tags|keep-around|merge-requests|environments|notes)/)`)

// Checksum is a hash representation of all references in a repository.
// Checksum must not be copied after first use.
type Checksum struct {
	sum big.Int
}

// AddBytes adds a reference to the checksum that is a line in the output format of `git-show-ref`.
func (c *Checksum) AddBytes(line []byte) {
	if !refsAllowed.Match(line) {
		return
	}

	h := sha1.New()
	// hash.Hash will never return an error.
	_, _ = h.Write(line)

	c.update(h.Sum(nil))
}

// Add adds a reference to the checksum.
func (c *Checksum) Add(ref Reference) {
	if !refsAllowed.MatchString(ref.Name.String()) {
		return
	}

	h := sha1.New()
	// hash.Hash will never return an error.
	_, _ = fmt.Fprintf(h, "%s %s", ref.Target, ref.Name)

	c.update(h.Sum(nil))
}

func (c *Checksum) update(refSum []byte) {
	if c.sum.BitLen() == 0 {
		c.sum.SetBytes(refSum)
	} else {
		var hash big.Int
		hash.SetBytes(refSum)
		c.sum.Xor(&c.sum, &hash)
	}
}

	repoProto := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repoProto); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repoProto)
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name: "show-ref",
		Flags: []gitcmd.Option{
			gitcmd.Flag{Name: "--head"},
		},
	}, gitcmd.WithSetupStdout())
	if err != nil {
		return nil, structerr.NewInternal("gitCommand: %w", err)
	}

	var checksum git.Checksum

	scanner := bufio.NewScanner(cmd)
	for scanner.Scan() {
		checksum.AddBytes(scanner.Bytes())
	}

	if err := scanner.Err(); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

		}

		return nil, structerr.NewDataLoss("not a git repository '%s'", repoPath)
	}

	return &gitalypb.CalculateChecksumResponse{Checksum: hex.EncodeToString(checksum.Bytes())}, nil
