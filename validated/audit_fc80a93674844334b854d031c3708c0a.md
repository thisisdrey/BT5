### Title
Users lose fractional TRX during `ParticipateAssetIssueContract` due to floor-division rounding when converting TRX to asset-token units - (File: actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java)

### Summary
`ParticipateAssetIssueActuator` (reachable via a normal signed `ParticipateAssetIssueContract` transaction, i.e. buying a TRC10 token with TRX) deducts the caller's full TRX `amount` but converts it to the purchased token quantity using integer floor division of `amount * num / trxNum`. When `amount * num` is not an exact multiple of `trxNum`, the fractional remainder is silently discarded: the full TRX cost is taken from the buyer but the corresponding fractional token value is never credited to them nor refunded. This is the same rounding/decimal-conversion loss-of-funds bug class as the reported `SolverVaults.deposit` issue (collateral amount fully debited while the minted amount is floor-rounded to fewer units).

### Finding Description
In `execute()`:
```java
long cost = participateAssetIssueContract.getAmount();
...
long balance = subtractExact(ownerAccount.getBalance(), cost);   // full cost debited
...
long exchangeAmount = multiplyExact(cost, assetIssueCapsule.getNum());
exchangeAmount = floorDiv(exchangeAmount, assetIssueCapsule.getTrxNum());  // floor-rounded
ownerAccount.addAssetAmountV2(key, exchangeAmount, dynamicStore, assetIssueStore);
``` [1](#0-0) 

The `validate()` method only guards against the exchange resolving to zero or less:
```java
long exchangeAmount = multiplyExact(amount, num);
exchangeAmount = floorDiv(exchangeAmount, trxNum);
if (exchangeAmount <= 0) {
  throw new ContractValidateException("Can not process the exchange!");
}
``` [2](#0-1) 

It does **not** check that `amount * num` is exactly divisible by `trxNum` — it only rejects the degenerate case where the buyer would receive literally 0 tokens. As soon as `exchangeAmount >= 1`, any remainder from `floorDiv` is dropped, yet the buyer still pays the *entire* `cost` in TRX (not a reduced, exactly-divisible amount). This is functionally identical to the SolverVault bug: an amount expressed in one unit (TRX "drops") is converted via truncating integer division into another unit (asset-issue token units defined by `trx_num`/`num`, an arbitrary exchange ratio that is explicitly allowed to not be 1:1) and the truncated remainder value is lost by the paying user rather than refunded or otherwise accounted for.

The existing regression test confirms this rounding is intentional/accepted current behavior rather than something the code protects against:
```java
Assert.assertEquals(owner.getAssetMapForTest().get(ASSET_NAME).longValue(),
    (999L * NUM) / TRX_NUM);
``` [3](#0-2) 
This is integer division in the test itself (`999L * NUM / TRX_NUM`), confirming any remainder of the 999 TRX spent is simply not represented as tokens received, while the full 999 TRX is deducted from the buyer's balance.

### Impact Explanation
Any TRC10 asset issuer can set `trx_num`/`num` (the `AssetIssueContract.trx_num` / `num` fields) to an arbitrary ratio (the only functional constraint enforced elsewhere is the `precision` field bound for the token's own decimal display, not on `trx_num`/`num`) so that `num/trxNum` is not an integer multiple relationship. [4](#0-3)  Any buyer sending TRX amounts that don't divide evenly by `trxNum/num` permanently loses the fractional TRX value with no possibility of recovery — the TRX is transferred to the issuer's `toAccount` in full (`toAccount.setBalance(addExact(toAccount.getBalance(), cost))`) while the buyer's minted asset amount is truncated down. [5](#0-4)  Because this can be repeated across many transactions and asset issuers, it results in cumulative unauthorized-in-effect loss of user TRX (paid but not converted into represented value), matching the Medium-severity classification of the original report (small-value loss per operation, accruing over many transactions).

### Likelihood Explanation
This is triggerable by any unprivileged account simply calling `participateAssetIssue` with an `amount` that is not an exact multiple of `trxNum/gcd`. Given `trx_num`/`num` are attacker/issuer-controllable at asset-issue time (no restriction requiring `num` to evenly divide typical purchase amounts), and buyers commonly send arbitrary TRX amounts, non-divisible inputs are the common case rather than an edge case, making likelihood high whenever an asset uses a non-trivial exchange ratio.

### Recommendation
Either (a) reject the transaction in `validate()`/`execute()` when `amount * num` is not exactly divisible by `trxNum` (i.e., require `(amount * num) % trxNum == 0`), or (b) compute the exact TRX cost that corresponds to the truncated `exchangeAmount` (`actualCost = exchangeAmount * trxNum / num`) and only debit/transfer `actualCost` from the buyer, refunding the remainder difference back to the buyer instead of transferring the full requested `amount`.

### Proof of Concept
1. Asset issuer creates a TRC10 asset with `trx_num = 3`, `num = 1` (i.e., 3 TRX buys 1 token unit), via `AssetIssueActuator`.
2. Buyer calls `ParticipateAssetIssueContract` with `amount = 998` TRX drops.
3. `exchangeAmount = floorDiv(998 * 1, 3) = 332` (since `998 * 1 / 3 = 332.67`).
4. `validate()` passes because `exchangeAmount (332) > 0`.
5. `execute()` debits the buyer's full `998` TRX and credits the issuer the full `998` TRX, while the buyer only receives `332` token units (representing exactly `996` TRX worth) — the remaining `2` TRX of value is permanently lost by the buyer with no refund and no corresponding token issued.
