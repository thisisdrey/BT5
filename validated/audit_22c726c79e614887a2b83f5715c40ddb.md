### Title
Unchecked `page_index * ATTACHMENTS_INV_PAGE_SIZE` arithmetic in `AtlasDB::get_attachments_available_at_page_index` reachable via unauthenticated `GET /v2/attachments/inv` - ([File: stackslib/src/net/api/getattachmentsinv.rs])

### Summary
The `GET /v2/attachments/inv` handler only bounds the *count* of requested page indexes (`MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`), never the *value* of each `u32` page index parsed from the query string. Each raw, attacker-chosen `u32` is passed straight into `AtlasDB::get_attachments_available_at_page_index`, which computes offsets by multiplying the page index by `AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE`, an operation that is not visibly guarded with `checked_mul`/`checked_add` in the handler layer.

### Finding Description
In `try_parse_request` [1](#0-0) , each comma-separated entry of `pages_indexes` is parsed with `entry.parse::<u32>()` and inserted into a `HashSet<u32>` with no upper-bound validation — any value up to `u32::MAX` is accepted. In `try_handle_request`, the only check performed on the collected list is on its length (`page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`) [2](#0-1) ; the individual `u32` values are never range-checked before being forwarded to `network.get_atlasdb().get_attachments_available_at_page_index(*page_index, &index_block_hash)` [3](#0-2) . The `index_block_hash` itself only needs to parse as a valid 64-hex `StacksBlockId`, with no requirement that it correspond to a known/canonical block.

I was not able to fully inspect the body of `AtlasDB::get_attachments_available_at_page_index` in `stackslib/src/net/atlas/db.rs` within the available tool budget (only grep hit counts confirming its use of `ATTACHMENTS_INV_PAGE_SIZE` and `page_index` were retrieved, not the exact arithmetic lines), so I cannot state with certainty whether the multiplication there uses checked arithmetic or whether the crate's release profile enables `overflow-checks`. This is a material gap: whether this reaches a genuine remote panic (Critical) depends on (a) the exact arithmetic in `db.rs`, and (b) the `Cargo.toml` `[profile.release]` `overflow-checks` setting, neither of which I was able to confirm before running out of iterations.

### Impact Explanation
If the downstream multiplication is unchecked and `overflow-checks` is enabled in the release profile (or the node runs a debug build), a single crafted request with a boundary `page_index` (e.g., near `u32::MAX / ATTACHMENTS_INV_PAGE_SIZE`) would panic the thread handling the RPC request, producing an unauthenticated remote crash/DoS on a read endpoint — matching the Critical category. If `overflow-checks` is disabled in release (Rust's default), the multiplication instead wraps silently, at worst causing the endpoint to compute/serve an incorrect attachment bit-range rather than crash, which is a much lower-severity correctness bug rather than a crash.

### Likelihood Explanation
The RPC port requires no authentication or special role, and the crafted query string is a single GET request with no preconditions other than a syntactically valid 64-hex `index_block_hash`. The confirmed gap in the RPC layer (no per-value bound on `page_index`) is definite; whether it translates into a crash depends on unverified details of `db.rs` and the build's overflow-check configuration.

### Recommendation
Regardless of downstream behavior, add explicit validation in `getattachmentsinv.rs`'s `try_parse_request`/`try_handle_request` to reject `page_index` values that would overflow when multiplied by `AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE` (e.g., `page_index.checked_mul(ATTACHMENTS_INV_PAGE_SIZE).ok_or(...)`), and ensure `AtlasDB::get_attachments_available_at_page_index` itself uses `checked_mul`/`checked_add` and returns a bounds error rather than performing raw arithmetic on attacker-supplied `u32` values.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/tests.rs` calling `atlasdb.get_attachments_available_at_page_index(u32::MAX, &StacksBlockId([0;32]))` directly and assert it returns `Err(..)` rather than panicking; additionally, an integration-level test can send `GET /v2/attachments/inv?pages_indexes=4294967295&index_block_hash=<64 hex zeros>` to a running RPC handler and assert a graceful `400`/`404` response instead of a connection-terminating panic. I was unable to construct the exact crash-triggering value or confirm panic reproduction because the precise arithmetic in `db.rs` and the crate's overflow-check build settings were not verified within my available tool calls.
