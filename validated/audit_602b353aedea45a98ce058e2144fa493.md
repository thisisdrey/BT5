## Title
`max_receipt_size` cap is not enforced when a receipt is mutated after validation (`output_data_receivers` / value-return) - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/congestion_control.rs`)

## Summary
This is the closest reachable analog in nearcore to the `OmoVault` bug: a documented state variable (`max_receipt_size`, a `LimitConfig` field) is checked in one code path (`validate_receipt` at receipt-creation time) but the check is not re-applied after the receipt is later mutated (when `output_data_receivers` are appended or a large value is returned via `promise_return`), so receipts can end up **larger than the configured cap** while the "SUPPLY_CAP_EXCEEDED"-equivalent check is silently skipped for that path — exactly mirroring the OmoVault pattern of "the cap exists and is enforced somewhere, but not on every code path that can grow the tracked quantity."

## Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces `receipt_size <= limit_config.max_receipt_size` only for `ValidateReceiptMode::NewReceipt` [1](#0-0) . This check runs once, right after a receipt is created inside `apply_action` in `runtime/runtime/src/lib.rs` [2](#0-1) .

However, a receipt's `output_data_receivers` list can be appended to **after** that validation point (e.g. `promise_return`/`promise_batch_then`), and a large value can be attached via value-return, both of which grow the receipt's serialized size past `max_receipt_size` without re-triggering `validate_receipt`. The codebase's own comments and tests confirm this: `ValidateReceiptMode::ExistingReceipt` is explicitly documented as more lenient "because... there is a bug which allows to create receipts that are above the size limit," citing the tracked issue directly in the source [3](#0-2) . Downstream, `try_forward` in the congestion-control forwarding path has to work around this by pretending the receipt is only `max_receipt_size` bytes for accounting/limit-comparison purposes, while the *actual* oversized receipt is still pushed into `outgoing_receipts` [4](#0-3) [5](#0-4) .

This is structurally identical to the OmoVault flaw: a cap variable/config value exists (`supplyCap` / `max_receipt_size`), it is enforced in the "normal" entry point (`deposit`/`mint` claim to check it in comments vs. `validate_receipt` at creation time), but a secondary mutation path (`mint` bypassing the check entirely vs. `output_data_receivers`/value-return mutating the receipt post-validation) allows the tracked quantity to exceed the cap.

## Impact Explanation
Receipts exceeding `max_receipt_size` violate an invariant relied on elsewhere: congestion-control size accounting, bandwidth-scheduler grants, and per-shard memory bounds are all sized around `max_receipt_size`. The workaround in `try_forward` (clamping the *accounted* size to `max_receipt_size` while forwarding the *real*, larger receipt) means the actual bytes transmitted/buffered can exceed what the bandwidth/congestion model assumes was granted, undermining the size-limit guarantees the cross-shard congestion-control system depends on. Under NearCore's own severity/likelihood framing (mirroring the M-16 report), the reachable outcome is a config/invariant-violation issue (Low impact) rather than direct fund loss, but it does defeat the size cap that other subsystems assume holds — a "cap not enforced in every path" class bug, consistent with the accepted answer format.

## Likelihood Explanation
This is reachable by an ordinary contract deployed by any unprivileged account: a contract using `promise_return`/`promise_then` with large output data, or returning a large value, can build a receipt whose size grows past `max_receipt_size` after the one-time `validate_receipt` check. The nearcore test suite itself demonstrates this is trivially triggerable and already tracked as a known, reproducible bug (not merely theoretical) via `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` [6](#0-5) .

## Recommendation
Re-validate `max_receipt_size` (or otherwise account for post-mutation growth) at every point where a receipt's serialized form can grow after initial validation — specifically after `output_data_receivers` are appended (`promise_batch_then`/`promise_return`) and after value-return payloads are attached — mirroring the fix pattern of moving/duplicating the cap check to cover every mutation path, the same recommendation as in the OmoVault report for `deposit`/`mint`. Alternatively, remove the special-casing in `try_forward`'s size clamp and enforce the true cap end-to-end so oversized receipts cannot enter the outgoing/buffered receipt pipeline at all.

## Proof of Concept
Existing in-repo tests already reproduce the condition (not fully "fixed", explicitly labeled as bug-reproducing tests):
- `test_max_receipt_size_promise_return`: builds a promise DAG where `output_data_receivers` are added to an already-max-sized receipt, pushing it over `max_receipt_size`, and asserts (via `assert_oversized_receipt_occurred`) that an oversized receipt appears on-chain despite the configured limit [7](#0-6) .
- `test_max_receipt_size_value_return`: returns a value equal to `max_receipt_size`, which is wrapped into a `Data` receipt exceeding the size limit, again confirmed via `assert_oversized_receipt_occurred` [8](#0-7) .

**Uncertainty note:** I was not able to fully trace the exact runtime call sites where `output_data_receivers` are appended post-validation (e.g., inside `receipt_manager.rs`/`function_call.rs`) within the available iterations, so the precise line numbers for that mutation are not cited here — only the validation entry point, the documented workaround, and the confirming tests. The impact is bounded to invariant/congestion-accounting violation as tracked by nearcore issue #12606, referenced directly in `runtime/runtime/src/verifier.rs` and `runtime/runtime/src/congestion_control.rs` [9](#0-8) [10](#0-9) ; I did not find evidence it escalates to fund theft, double-spend, or a shard-halting panic within the code I was able to inspect.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
