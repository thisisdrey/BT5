### Title
Cross-contract StackerDB chunk replay due to missing contract_id binding in chunk signature - ([File: libstackerdb/src/libstackerdb.rs], [File: stackslib/src/net/stackerdb/db.rs], [File: stackslib/src/net/api/poststackerdbchunk.rs])

### Summary
`StackerDBChunkData`/`SlotMetadata::auth_digest` only commits to `slot_id`, `slot_version`, and `data_hash` — never to the `contract_id`/`smart_contract` the chunk is destined for. Because `StackerDBTx::try_replace_chunk` verifies the signature purely against the slot owner recorded for the *target* contract without checking that the signer intended that specific contract, a validly-signed chunk observed for contract A can be replayed verbatim into contract B whenever the same `StacksAddress` owns the same `slot_id` in B.

### Finding Description
`SlotMetadata::auth_digest` in [1](#0-0)  hashes only `slot_id`, `slot_version`, and `data_hash` — `contract_id` is never part of the signed material. `StackerDBChunkData::sign`/`verify` reuse this digest [2](#0-1) .

The authoritative write path is `StackerDBTx::try_replace_chunk` in `db.rs`, which looks up the slot's owner **for the contract passed in by the caller** and verifies the signature against that owner only — it never checks contract identity against anything embedded in the signed bytes: [3](#0-2) .

This function is reachable directly from the unauthenticated (no RPC secret required) HTTP handler `RPCPostStackerDBChunkRequestHandler::try_handle_request`, which takes the target contract from the URL path and the chunk (with its self-contained signature) from the POST body, then calls `tx.try_replace_chunk(&contract_identifier, &stackerdb_chunk.get_slot_metadata(), &stackerdb_chunk.data)`: [4](#0-3) . On success it also re-gossips the chunk to the P2P network under contract B's identity via `node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))`: [5](#0-4) .

The same gap exists on the P2P push path: `PeerNetwork::validate_received_chunk` resolves the signer via `get_slot_signer(smart_contract_id, data.slot_id)` for whichever `contract_id` is embedded in the attacker-supplied `StackerDBPushChunkData`, then verifies the chunk against that owner — again with no cross-check that the chunk was actually signed with that contract in mind: [6](#0-5) .

Exploit flow:
1. Attacker observes (StackerDB data/signatures are public) a validly-signed `StackerDBChunkData` for contract A, slot K, signed by address X.
2. Attacker sends that exact JSON body via `POST /v2/stackerdb/<address-B>/<contract-B>/chunks` to a victim node that replicates contract B, where slot K in B also happens to be owned by X (plausible when the same signer set participates in multiple StackerDB contracts, e.g. per-cycle `signers-N-M` contracts using consistent slot-to-signer-index mapping).
3. `try_replace_chunk` succeeds because the signature verifies against B's slot-K owner (X), even though X never signed anything referencing contract B.
4. The node persists the chunk into contract B's slot K and relays it as a fresh `StackerDBPushChunkData` for contract B to its peers, propagating the cross-namespace write network-wide.

Existing guards (chunk size cap, version/staleness check, max-writes check) do not address this because none of them bind the signature to the contract — only `slot_id`, `slot_version`, `data_hash` are checked, per `validate_received_chunk`/`try_replace_chunk`.

### Impact Explanation
An unprivileged remote party can cause a node to accept and persist a chunk into a StackerDB namespace (contract) that the signing key never authorized, and then have the node re-broadcast it network-wide as if it were a legitimate write to that contract. This is an unauthenticated/unauthorized write to StackerDB state and network-wide propagation of misattributed data — matching the Critical impact category. It is fully repeatable for any signer address that happens to share slot numbering across two StackerDB contracts replicated by the same node.

### Likelihood Explanation
Preconditions: (1) the victim node replicates the target contract B, (2) slot K in contract B is owned by the same `StacksAddress` as slot K in the source contract A. This is plausible in real signer-set deployments where the same address is assigned identical slot indices across parallel StackerDB contracts (e.g., successive reward-cycle "signers" contracts). The attacker needs no privileged role, no RPC secret, and no key compromise — only the ability to observe one legitimately signed chunk (StackerDB data is public) and issue an HTTP POST or P2P push to the target node. Attack cost is a single crafted message per replay.

### Recommendation
Include the fully-qualified `contract_id` (or a domain-separation tag derived from it) inside `SlotMetadata::auth_digest`/`StackerDBChunkData` signing material, so a signature is only valid for the specific contract it was produced for. This requires a protocol/wire-format change (bumping StackerDB chunk versioning) and must be rolled out with backward-compatibility handling for existing signed chunks.

### Proof of Concept
Rust test in `stackslib/src/net/stackerdb/tests/db.rs`:
1. Create two independent StackerDB contracts, A and B, each via `StackerDBTx::create_stackerdb`, both assigning slot 0 to the same `StacksAddress` (derived from the same private key `pk`).
2. Build one `StackerDBChunkData { slot_id: 0, slot_version: 1, data: ... }`, sign it once with `pk` (`chunk_data.sign(&pk)`).
3. Call `tx.try_replace_chunk(&contract_a, &chunk_data.get_slot_metadata(), &chunk_data.data)` — expect `Ok(())`.
4. Call `tx.try_replace_chunk(&contract_b, &chunk_data.get_slot_metadata(), &chunk_data.data)` with the identical signed `chunk_data` — assert this **also** returns `Ok(())`, proving the signature intended for contract A is accepted verbatim as a valid write into contract B.
5. Optionally extend with an HTTP-level test hitting `RPCPostStackerDBChunkRequestHandler` at `/v2/stackerdb/<addr-B>/<contract-B>/chunks` with the JSON body of the chunk signed for contract A, asserting `accepted: true` in the `StackerDBChunkAckData` response.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
