### Title
Missing bypass for `ALLOW_MARKET_TRANSACTION` disablement permanently freezes escrowed order funds in `MarketSellAssetActuator`/`MarketCancelOrderActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java`)

### Summary
`MarketSellAssetActuator` escrows a user's sell-side tokens (TRX or TRC10) into the account balance ledger the moment an order is created — the tokens are simply subtracted from the owner's balance via `transferBalanceOrToken()`, and the corresponding `MarketOrderCapsule` is persisted in `MarketOrderStore`/`MarketPairPriceToOrderStore` with no separate escrow contract to "unwind" from. The only two paths that can ever release these escrowed tokens are (1) a matching taker order via `MarketSellAssetActuator.execute()` → `matchOrder()`, or (2) `MarketCancelOrderActuator.execute()`. Both of these actuators gate their entire `validate()` on the single dynamic property `supportAllowMarketTransaction()`. [1](#0-0) [2](#0-1) 

### Finding Description
When a sell order is placed, the seller's tokens/TRX are debited immediately at order-creation time: [3](#0-2) 

This mirrors exactly the pattern in the external report: a privileged flag (`sellable` in the report, `ALLOW_MARKET_TRANSACTION` here) gates the entry point that escrows/locks value, but the exit/completion path that should release that value is checked against the *same* flag rather than being independent of it. In the SecondSwap report, `listVesting()` checked `sellable` but `completePurchase()` forgot to recheck it, letting a purchase go through after the flag flipped to false. In java-tron, the analogous defect is inverted but structurally identical: both the "lock" operation (`MarketSellAssetActuator`, which also performs matching/unlocking as a side effect of `matchOrder()`) and the dedicated "unlock" operation (`MarketCancelOrderActuator`) require the *same* committee-controlled flag `supportAllowMarketTransaction()` to be true, with no independent code path that lets a user withdraw already-escrowed funds once that flag is turned off. [4](#0-3) 

Because `matchOrder()`/`matchSingleOrder()` are only reachable from inside `MarketSellAssetActuator.execute()` — itself gated by the same `validate()` check — once the committee (via a `Proposal`, see `ProposalUtil.java` references to `supportAllowMarketTransaction`) disables market transactions, **no unprivileged user (order placer) can ever again cancel or have matched any order that was already resting in the order book**, even though their tokens have already been debited from their spendable balance and are only "logically" represented by the `MarketOrderCapsule` record. [5](#0-4) 

### Impact Explanation
Any account that has an active (unmatched or partially unmatched) market order at the moment `ALLOW_MARKET_TRANSACTION` is turned off has its escrowed TRX/TRC10 permanently frozen with no code path to recover it — neither by cancellation nor by having the order match. This is a direct, unbacked, permanent freezing of user funds triggered purely by a governance parameter change, with zero remediation path built into the actuators themselves (no "cancel-even-when-disabled" carve-out exists, unlike, e.g., how some systems allow withdrawals during a pause but block new deposits).

### Likelihood Explanation
This requires no attacker action beyond having placed a normal, unprivileged `MarketSellAssetContract` order (available to any account with TRX/TRC10 balance) at some point before the committee disables the market-transaction feature via the standard proposal mechanism (a normal, expected operational lever already present in `DynamicPropertiesStore`/`ProposalUtil`). Given the feature toggle exists specifically so it can be exercised, and any user could plausibly have a resting order at that time, the likelihood of triggering the freeze is high in any deployment where the toggle is ever exercised, and the loss is total and unrecoverable for affected orders.

### Recommendation
Decouple the "release escrowed funds" path from the `supportAllowMarketTransaction()` gate:
- Remove (or make conditional/bypassable) the `supportAllowMarketTransaction()` check inside `MarketCancelOrderActuator.validate()` so that order owners can always retrieve their escrowed tokens/TRX, regardless of whether new order creation/matching is currently disabled.
- Alternatively, introduce a distinct property (e.g., `ALLOW_MARKET_CANCEL`) that is independent of `ALLOW_MARKET_TRANSACTION`, ensuring the "unlock" operation is never blocked by disabling the "lock/match" operation.

### Proof of Concept
1. Committee/SR passes a proposal that sets `ALLOW_MARKET_TRANSACTION` to `1` (enabled) initially.
2. Alice, an ordinary account, submits `MarketSellAssetContract` selling 100 TRX for token X. `MarketSellAssetActuator.execute()` immediately debits 100 TRX from Alice's balance via `transferBalanceOrToken()` and stores the order (`createAndSaveOrder`) in `MarketOrderStore`; suppose it does not fully match and remains resting in the order book (`saveRemainOrder`).
3. Committee/SR passes a subsequent proposal setting `ALLOW_MARKET_TRANSACTION` to `0`.
4. Alice attempts `MarketCancelOrderContract` to recover her 100 TRX. `MarketCancelOrderActuator.validate()` throws `"Not support Market Transaction, need to be opened by the committee"` because `dynamicStore.supportAllowMarketTransaction()` is now `false`.
5. No other taker can match Alice's order either, since any new `MarketSellAssetContract` (the only path into `matchOrder()`) is blocked by the identical check in `MarketSellAssetActuator.validate()`.
6. Alice's 100 TRX is now permanently unrecoverable until/unless the committee re-enables the flag — and even then, only if the flag is later re-enabled, which is not guaranteed and not enforced by any protocol invariant.
