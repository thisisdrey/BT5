### Title
Stale postponed `Stake` action survives `DeleteAccount`/`CreateAccount` and re-fires against the recreated account's balance - ([File: runtime/runtime/src/actions.rs], [File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) deletes an `Account`, its keys, code and contract data, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, or `TrieKey::ReceivedData` entries keyed by that `account_id`. If an account had a postponed `ActionReceipt` (e.g. containing `Action::Stake`) waiting on an unresolved `input_data_id` at the moment it is deleted, that postponed receipt survives in state under the same `receiver_id` string. When the account name is later recreated and the outstanding data dependency finally resolves, `process_receipt`'s `Data` arm (`runtime/runtime/src/lib.rs:1386-1474`) pulls the stale receipt out of state and executes it via `apply_action_receipt` against whatever `Account` currently occupies that name — including a freshly recreated account funded by an unrelated new owner.

### Finding Description
- `check_actor_permissions` for `Action::DeleteAccount` (`runtime/runtime/src/actions.rs:761-776`) only checks `account.locked().is_zero()` at the moment of deletion. A `Stake` action buried inside a postponed receipt has not yet mutated `locked`/`amount` (postponement happens in `process_action_receipt`, `runtime/runtime/src/lib.rs:1593-1658`, before the receipt's actions ever run), so the guard is trivially satisfied even though a `Stake` action is "in flight" for that account.
- `remove_account` (`core/store/src/utils/mod.rs:505-575`) removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData`. It does **not** enumerate or remove `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, or `TrieKey::ReceivedData` records for the account, all of which are keyed purely by the `account_id` string (`receiver_id`), independent of any specific `Account` "identity" or creation nonce.
- `action_stake` (`runtime/runtime/src/actions.rs:59-110`) operates on the `&mut Account` reference and `account_id` it is given; it has no way to know or check that the `Account` object is a "new" account distinct from the one that originally spawned the receipt. It simply computes `increment`, checks balances, sets `locked`, and pushes a `ValidatorStake` proposal using whatever `Account`/`account_id` combination `apply_action_receipt` looked up via `get_account(state_update, account_id)` (`runtime/runtime/src/lib.rs:853`).
- `apply_action_receipt`'s only actor-authorization check for `Stake` is `check_actor_permissions`, which compares `actor_id` (initialized from `receipt.predecessor_id()`) to `account_id` (both are just `AccountId` strings) — it never checks that the account backing `account_id` is the same account (by key/owner) that existed when the receipt was created.
- Exploit flow: an unprivileged attacker deploys a contract on `sub.attacker.near` (or similar) that issues a promise batch containing `promise_batch_action_stake` chained after (`.then`) a cross-contract call whose result is not yet available — this creates a receipt with an `input_data_ids` entry, so it is stored as a **postponed receipt** (`runtime/runtime/src/lib.rs:1642-1655`, `set_postponed_receipt`). Before the dependent data ever arrives, the attacker submits `DeleteAccount` on `sub.attacker.near` (passes `DeleteAccountStaking` because `locked == 0`). The account is removed, but the postponed `Stake` receipt, its `PendingDataCount`, and `PostponedReceiptId` link remain in the trie under the name `sub.attacker.near`. Later, the account name is recreated (e.g. a dapp/name-provisioning flow re-issues `sub.attacker.near` to a new customer with a fresh key and a funded balance via `CreateAccount` + `Transfer`/`AddKey`). Once the attacker-controlled dependency finally resolves (attacker fully controls the timing of the corresponding `Data` receipt), `process_receipt`'s `Data` arm finds the still-pending `PostponedReceiptId`, decrements `PendingDataCount` to zero, fetches and removes the postponed receipt, and calls `apply_action_receipt` — which now operates on the **new owner's account**, moving their `amount` into `locked` and emitting a `ValidatorStake` proposal for the attacker's chosen validator public key.
- Existing checks that fail to catch this: nonce/signature verification (irrelevant — this is a receipt, not a signed tx, replayed from state), `DeleteAccountStaking` (checks only current `locked`, not pending postponed stake actions), `check_actor_permissions` (string-equality only, no account-identity binding), and `pipelining.rs`'s same-chunk code-identity blocking (`runtime/runtime/src/pipelining.rs:173-191`), which only protects `FunctionCall` contract-identity resolution within a single chunk and does nothing for cross-chunk postponed `Data`-receipt resolution of non-`FunctionCall` actions like `Stake`.

### Impact Explanation
This allows freezing (locking) of a new/unrelated account owner's `amount` into `locked` state without that owner ever submitting a `Stake` action, and generates a `ValidatorStake` proposal carrying the attacker's chosen public key for the epoch manager, i.e., authorization escalation across accounts (an action authored before account replacement is executed with authority over funds it was never entitled to) and freezing of user funds — both explicitly in-scope impact categories (freezing/locking of funds, authorization escalation across accounts).

### Likelihood Explanation
Preconditions are all within reach of an ordinary account holder: deploying a contract, calling `promise_batch_action_stake` in a promise chain with an unresolved dependency, and submitting a normal `DeleteAccount` transaction (which nothing currently prevents while a postponed action is outstanding, since `locked() == 0` holds pre-execution). The remaining precondition — someone else recreating the exact same account name with fresh funds — is scenario-dependent (most naturally a namespace/subaccount-provisioning service where the attacker itself is the parent account handing out subaccounts, or a purchased/recycled account name); this narrows real-world likelihood but does not eliminate it, since attacker fully controls both when to delete and when to resolve the dangling data dependency, giving them arbitrary timing control over the trap.

### Recommendation
When `action_delete_account` removes an account, also purge all outstanding `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries keyed to that `account_id` (and ideally `ReceivedData`), or fail/queue-drain them safely (e.g., convert to failed outcomes) instead of leaving them dangling for a future, unrelated occupant of the same name. Alternatively, bind postponed receipts to an account-identity/generation counter that is invalidated on `DeleteAccount`, so `process_receipt`'s `Data` arm can detect and drop stale postponed receipts whose target account has since been deleted and recreated.

### Proof of Concept
1. Unit/integration test using `runtime/runtime/src/tests/apply.rs` harness (as in `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`, `runtime/runtime/src/tests/apply.rs:4877-4954`, but spanning two `apply()` calls / chunks):
   - Chunk 1: submit an `ActionReceipt` to `child` account with `actions: [Stake(stake_action)]` and `input_data_ids: [data_id]` (unresolved) — assert it is stored as a postponed receipt (`get_postponed_receipt` returns `Some`), and `child.locked() == 0`.
   - Chunk 2: submit `DeleteAccount` receipt for `child` (self-receipt, passes since `locked() == 0`); assert `get_account(child)` is `None` afterward, but `get_postponed_receipt(state, child, receipt_id)` and the `PendingDataCount`/`PostponedReceiptId` trie entries still return `Some`.
   - Chunk 3: submit `CreateAccount` + `Transfer(fresh_balance)` receipt for `child` from a different predecessor/new owner; assert account now exists with fresh balance and `locked() == 0`.
   - Chunk 4: submit the `Data` receipt satisfying `data_id`; assert this triggers execution of the previously postponed `Stake` receipt (via `apply_action_receipt`), and assert `child.locked() > 0` afterward and a `ValidatorStake` proposal for the attacker's public key appears in `validator_proposals`, despite the new owner never authoring a `Stake` action.
2. Expected (buggy) result: `locked` changes and a stake proposal is emitted for the new owner's account without their consent, confirming the vulnerability. Expected (fixed) result: the postponed receipt is purged on `DeleteAccount`, and step 4 either fails validation or produces no effect on the recreated account.
