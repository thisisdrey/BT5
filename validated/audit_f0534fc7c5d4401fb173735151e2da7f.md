### Title
Reward accrual in `pallet-asset-rewards` is computed as a fixed emission schedule independent of the pool's actual reward-asset balance, breaking accounting for elastic-supply/rebasable reward assets - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes staker entitlements purely from `reward_rate_per_block * blocks_elapsed`, accumulated into `reward_per_token_stored`, with no cross-check against the actual `fungibles` balance held by the pool account. This is the same broken invariant flagged in the 1inch `FarmAccounting.sol` report: distributed/accrued amounts are tracked as a strict internal counter while the underlying token balance can float independently of that counter (rebase, external mint/burn, elastic supply, bridged wrapped assets). The pallet even documents this caveat in prose ("Care should be taken by the pool operator to keep pool accounts adequately funded with the reward asset") but enforces nothing in code.

### Finding Description
`reward_per_token` accrues rewards on a purely time/rate basis: [1](#0-0) 

This value feeds `derive_rewards`/`update_pool_and_staker_rewards`, which set `staker_info.rewards` without ever comparing against `T::Assets::reducible_balance` of the pool account: [2](#0-1) 

`harvest_rewards` then unconditionally transfers the accrued (internally tracked) amount out of the pool account: [3](#0-2) 

`T::Assets` is a generic `fungibles::Inspect + Mutate` registry keyed by `T::AssetId`, so `reward_asset_id` can be any registered asset — including elastic-supply, rebasing, or externally-bridged wrapped assets (e.g. a Snowbridge-originated wrapped ERC-20 whose backing supply can change independent of on-chain transfers into the pool account). Because the pallet's `reward_per_token_stored`/`staker_info.rewards` accounting assumes the pool's balance moves in lockstep with the declared `reward_rate_per_block`, any divergence between the actual token balance and the internally accrued total desyncs entitlements from real holdings — exactly the FarmAccounting.sol failure mode. The pallet doc's own admission ("pool operator must keep pool adequately funded") confirms there is no on-chain guard; the recommendation in the original report ("warn developers not to use rebasable tokens as reward tokens") is not present anywhere in this pallet's config, docs-as-code, or call-time validation.

### Impact Explanation
When the reward asset's real balance is lower than the internally accrued `staker_info.rewards` (rebase down, external burn, or simply many stakers accruing against a pool whose real balance the admin failed to keep in sync), `harvest_rewards`'s `T::Assets::transfer` will fail for later claimants with `NotEnoughTokens`/`FundsUnavailable`-class errors, permanently locking their already-accrued reward entitlement (their `staker_info.rewards` counter is only cleared on a successful transfer, but they can never successfully harvest if the pool never catches up). Conversely, if the asset rebases up, `cleanup_pool` sweeps the pool's entire `reducible_balance` to the admin, meaning any float above the tracked, staker-attributable amount is not reconciled against individual entitlements at all — value simply flows to whichever party acts on it, breaking exact, once-only settlement to the rightful beneficiary. This is a direct instance of "permanent user-fund lock" / failure to "conserve value and settle exactly once to the rightful beneficiary and amount" from the required impact set.

### Likelihood Explanation
No privileged action, malicious validator/collator, or governance abuse is required. The pool creator (via `T::CreatePoolOrigin`, which per the pallet's own docs is expected to eventually become permissionless) merely needs to configure a `reward_asset_id` whose supply is not rigidly 1:1 backed by deposits into the pool account (a rebasing token, interest-bearing wrapped asset, or an asset governed by another pallet/bridge with independent mint/burn semantics). Any ordinary staker who then stakes, waits, and calls `harvest_rewards` can hit the desync — no attacker collusion, no off-chain infrastructure, and no need to front-run anyone.

### Recommendation
Do not rely solely on the time-based accrual counter for entitlement; before crediting/transferring rewards, cap `staker_info.rewards`/transfer amount by the pool account's actual `reducible_balance` of `reward_asset_id`, and reconcile any shortfall/surplus explicitly (e.g. pro-rata reduction, or an explicit "insolvent pool" state) rather than allowing `harvest_rewards` to unconditionally attempt a transfer against an internally-tracked figure. At minimum, document and enforce (via a `Config` trait bound or asset property check) that `reward_asset_id` must be a fixed-supply asset whose balance in the pool account can only change through `deposit_reward_tokens`/`harvest_rewards`/`cleanup_pool`.

### Proof of Concept
1. Create a pool via `create_pool` with `reward_asset_id` set to an asset ID that is a wrapped/rebasing representation of an external token (any asset registered in the runtime's `fungibles` registry works from the pallet's perspective — it performs no restriction on `reward_asset_id` characteristics, see `create_pool`'s parameters at [4](#0-3) ).
2. Fund the pool via `deposit_reward_tokens`; the reward asset's backing subsequently rebases downward (e.g., an external event reduces the wrapped token's redeemable value, or another pallet/bridge burns from the pool account through a mechanism outside `deposit_reward_tokens`/`harvest_rewards`).
3. Multiple stakers `stake`, accrue rewards through normal `update_pool_and_staker_rewards` calls over several blocks (pure `reward_rate_per_block * blocks_elapsed` accrual, unrelated to the pool's real balance).
4. The first staker(s) to call `harvest_rewards` successfully drain the now-insufficient real balance; subsequent stakers' `harvest_rewards` calls fail at the `T::Assets::transfer` step because `pool_info.account`'s `reducible_balance` is less than their tracked `staker_info.rewards`, permanently locking their entitlement with no path to recovery in the pallet's call surface.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
