### Title
Repository Left Permanently Broken and Locked if `DisconnectGitAlternates` Fails Mid-Operation Due to Resource Exhaustion - ([File: internal/git/objectpool/disconnect.go])

### Summary
`DisconnectGitAlternates` performs a two-phase operation—hard-linking pool objects into the member repository, then renaming away `objects/info/alternates` to run a connectivity check—that is documented by Gitaly's own authors as "dangerous." If the hard-linking phase fails partway through (e.g., due to disk space exhaustion while linking a large object pool into a member repository, an ordinary user-triggered path via forking/detaching), or if the process crashes between the rename and the connectivity check, the repository is left in a corrupt, unusable state that only an administrator can manually repair, with no automated recovery path—mirroring the "processed but not completed, resource frozen" bug class from the external report.

### Finding Description
`Disconnect` in [1](#0-0)  explicitly documents the risk: alternate objects are hard-linked into the repository, then the alternates file is temporarily renamed away and a connectivity check (`git rev-list --objects --all`) is run to validate the repository is self-sufficient. The hard-linking loop in [2](#0-1)  can fail partway (e.g., `ENOSPC` from `storage.Link`/`MkdirAll` when the pool has accumulated many objects/packs on a nearly-full storage volume), leaving some objects linked and others not, with no rollback of already-completed hard-links.

Worse, in `removeAlternatesIfOk` ( [3](#0-2) ), the alternates file is renamed away *before* the connectivity check runs. The function's own comment states: "if the repo is not connected for whatever reason, then until this function returns, probably **all concurrent RPC calls to the repo will fail**. Also, if Gitaly crashes in the middle of this function, the repo is left in a broken state." The deferred rollback ( [4](#0-3)  ) only executes if the Go process survives to run the deferred closure—a crash, OOM kill (plausible if hard-linking a large pool concurrently strains resources), or `os.Rename`/`os.Link` failure during rollback due to the same resource exhaustion that caused the original fault leaves `objects/info/alternates` permanently missing, with only a timestamped backup file (`newBackupFile`, [5](#0-4) ) sitting on disk that requires manual administrator restoration.

This is directly analogous to the reported bug class: an operation is irreversibly "processed" (alternates removed) before the "completion" check (connectivity/fsck) can be guaranteed to succeed or be rolled back, and insufficient resources (disk space, memory) at the critical juncture leaves the resource (the repository) frozen/unusable with no self-service recovery — only administrator intervention, exactly as in the original funds-frozen report.

### Impact Explanation
A single ordinary RPC call (`DisconnectGitAlternates`, invoked e.g. when a forked repository member is detached from its pool such as when it becomes private) can leave the target repository completely inaccessible for all Git operations until an administrator manually restores `objects/info/alternates` from the backup file. This is a denial of service against a specific repository triggered by ordinary storage pressure or process instability, not a privileged-actor or malicious-peer scenario.

### Likelihood Explanation
Triggering requires only disk space (or memory) pressure and calling the pre-existing, unprivileged `DisconnectGitAlternates` RPC on a repository with a sizable linked object pool — a realistic operational condition (e.g., large fork networks nearing storage capacity, or a Gitaly process constrained enough to OOM during hard-linking/rev-list of a huge pool). The code path and its danger are already acknowledged in the comments as a known risk, but there is no automated recovery/self-healing.

### Recommendation
- Make the hard-linking and alternates-swap steps atomic/idempotent (e.g., stage into a temporary location and use a single atomic rename, or persist a durable "pending disconnect" marker that a startup/reconciliation routine can detect and either complete or roll back automatically).
- Add a Gitaly startup/healthcheck routine that scans for orphaned alternates backup files (`objects/info/alternates.<timestamp>.<rand>`) and automatically restores them if the corresponding `objects/info/alternates` is missing and the repo fails connectivity checks, removing the dependency on manual administrator action.
- Verify sufficient free disk space before beginning the hard-link phase to reduce the likelihood of a mid-operation `ENOSPC` failure.

### Proof of Concept
1. Create a repository forked from / linked to a large object pool via `CreateObjectPool` + `LinkRepositoryToObjectPool`.
2. Constrain the storage backing the Gitaly node to have only slightly more free space than the size of the member repository's own unique objects (not enough for the full deduplicated pool content to be hard-linked in, or induce a Gitaly process crash/OOM kill during the hard-link loop, e.g. via `SIGKILL`).
3. Call `DisconnectGitAlternates` on the member repository.
4. Observe the hard-link loop ( [2](#0-1) ) fails with `ENOSPC`, or the process is killed after `removeAlternatesIfOk` has renamed `objects/info/alternates` away ( [6](#0-5) ) but before the deferred rollback executes.
5. Restart Gitaly and attempt any Git operation against the repository — it now fails as "not connected"/missing objects, with only the manually-restorable timestamped backup file left on disk, requiring administrator intervention.

// Disconnect disconnects the specified repository from its object pool. If the repository does not
// utilize an alternate object database, no error is returned. For repositories that depend on
// alternate objects, the following steps are performed:
//   - Alternate objects are hard-linked to the main repository.
//   - The repository's Git alternates file is backed up and object pool disconnected.
//   - A connectivity check is performed to ensure the repository is complete. If this check fails,
//     the repository is reconnected to the object pool via the backup and an error returned.
//
// This operation carries some risk. If the repository is in a broken state, it will not be restored
// until after the connectivity check completes. If Gitaly crashes before the backup is restored,
// the repository may be in a broken state until an administrator intervenes and restores the backed
// up copy of objects/info/alternates.
