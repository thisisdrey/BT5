### Title
`socialize-debt` omits the accrue step before computing `old-total-assets`, causing bad-debt write-downs to understate real losses - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Finding Description
`socialize-debt` (lines 944-984) computes `old-total-assets` via `(total-assets)` at line 950, which is a read-only helper backed by `(var-get index)` — the *last checkpointed* index, not a freshly-recomputed value that includes interest accrued since the last checkpoint. Every other state-mutating vault entrypoint that touches debt/interest math (`system-borrow`, `system-repay`, `flashloan`) begins its `let` with `(u (try! (accrue)))` to first checkpoint `index`/`lindex` up to the current block before doing any arithmetic: [1](#0-0) 
`socialize-debt` conspicuously lacks this call: [2](#0-1) 
Since `new-lindex` is derived as `current-lindex * (old-total-assets - debt-reduction) / old-total-assets` (lines 956-958), any stale `index` at the moment of socialization directly understates the real loss baked into `lindex`, which is the share-price checkpoint used across redemptions.

### Impact Explanation
This falls in the Critical bucket (protocol insolvency / theft of funds at rest): if `lindex` is written down less than the true loss, remaining `zft` holders' shares are marked at an inflated value, so early redeemers after a bad-debt event can extract more underlying per share than their fair post-loss entitlement, leaving later redeemers unable to redeem at par — a direct insolvency/fund-extraction pattern.

### Likelihood Explanation
Exploitability hinges entirely on whether the actual call chain from an attacker-triggered liquidation (`liquidate-multi` on the market) invokes this vault's own `accrue` before it invokes `socialize-debt` in the same transaction. All sibling debt-mutating functions in this same vault file explicitly guard against this exact staleness by calling `accrue` first, which is strong internal evidence that `socialize-debt`'s omission is inconsistent with the codebase's own established invariant. However, I could not retrieve and verify the market contract's (`v0-4-market.clar`) `liquidate-multi` → bad-debt-socialization call sequence within the available tool budget, so I cannot confirm with certainty whether the market layer independently calls this vault's `accrue` (e.g., via a `get-debt`/`total-debt` read that itself triggers accrual, or an explicit accrue call) immediately before dispatching to `socialize-debt`. If the market does call the vault's `accrue` beforehand as part of computing bad debt to socialize, the staleness window collapses to zero and this finding would not be exploitable. If it does not, the bug is real and trivially triggerable by any attacker who can trigger a bad-debt liquidation after a period of inactivity (no vault-level `system-borrow`/`system-repay`/`accrue` calls), which is a normal, low-cost, repeatable precondition (just letting time pass).

### Recommendation
Add `(u (try! (accrue)))` as the first binding in `socialize-debt`'s `let`, mirroring `system-borrow`/`system-repay`/`flashloan`, so `old-total-assets` and `idx` reflect interest accrued up to the current block before the write-down is computed.

### Proof of Concept
Not able to finalize a concrete Clarinet/vitest PoC because confirming the exploitable path requires reading `v0-4-market.clar`'s `liquidate-multi` and bad-debt dispatch logic to establish whether `accrue` is already called on the vault before `socialize-debt`, which was not completed within the investigation. A PoC would need to: (1) supply funds, (2) borrow to create debt, (3) let significant time pass with no vault-level accrue-triggering call, (4) trigger `liquidate-multi` to cause bad debt requiring `socialize-debt`, (5) compare the resulting `lindex` against a control run where an explicit `accrue` is forced immediately before the same `socialize-debt` scaled-amount and time gap, and (6) assert the two diverge and that immediate redemption after the no-accrue path extracts more underlying per share than the accrue-first path.

  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))

                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
