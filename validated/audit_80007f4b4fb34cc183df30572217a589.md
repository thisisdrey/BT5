### Title
StackerDB chunk signatures do not bind to the contract/slot "epoch", enabling replay of stale signed chunks after slot reassignment - (File: `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/db.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB contract instance or to any notion of "which assignment of that slot" produced it. Combined with `StackerDBTx::reconfigure_stackerdb`, which resets a slot's stored version to `NO_VERSION`/0 whenever the signer address for that slot_id changes (but leaves it untouched when the signer is unchanged), this allows an unprivileged remote peer to replay a previously valid, captured `(data, signature)` chunk into the same slot after the slot has cycled away from and back to the original signer, since the freshness check (`slot_version > stored_version`) trivially passes against the reset version 0.

### Finding Description
The chunk-authentication digest is computed purely from local, re-derivable fields: [1](#0-0) 

This digest carries no reference to the `QualifiedContractIdentifier` (which StackerDB replica/contract the chunk belongs to) or to any monotonically-increasing "assignment epoch" for the slot. `SlotMetadata::verify` and `StackerDBChunkData::verify`/`recover_pk` reuse this same digest to check the signer: [2](#0-1) 

The write path (`StackerDBTx::try_replace_chunk`, used both for local writes via HTTP `POST /stackerdb_chunk` and for chunks accepted from gossip/sync) only requires:
1. Chunk not oversized.
2. `slot_desc.verify(&slot_validation.signer)` succeeds (i.e., some valid signature over `slot_id || slot_version || data_hash` recovers to the currently-configured signer for that slot).
3. `slot_desc.slot_version > slot_validation.version` (freshness).
4. `slot_version <= config.max_writes`. [3](#0-2) 

Crucially, the per-slot version baseline is reset to `NO_VERSION` whenever `reconfigure_stackerdb` observes that the slot's current signer differs from the new configured signer for that slot_id — but is left completely unchanged (`continue`) if the new configured signer is the same as the one currently on file: [4](#0-3) 

Because the authentication digest does not include the contract identifier or any binding to "this particular tenure of ownership over the slot," the following sequence is possible for any StackerDB whose slot assignment can change over time (e.g., the `.signers-{0,1}-N` contracts, which are reconfigured every reward cycle via `create_or_reconfigure_stackerdbs`/`NakamotoSigners::update_signers`, and whose slot list can shrink/grow/reorder based on the computed reward set):

1. Signer `A` legitimately owns slot `k` and signs and gossips chunk `C = (slot_id=k, slot_version=v, data, sig)`. This is observed/stored by any and all peers (a normal, unprivileged network observer can capture this).
2. In a later reconfiguration (reward-cycle rollover), a different signer `B` is assigned slot `k` (e.g., stake changes cause slot reordering). `reconfigure_stackerdb` sees `existing_validation.signer != B` and resets the row: `version = NO_VERSION` (0), `data = []`, `signature = empty`.
3. In a subsequent reconfiguration, signer `A` is reassigned back to slot `k` (this is a realistic occurrence given the reward-set computation can reorder signers cycle to cycle, and previous stakers frequently re-stake). `reconfigure_stackerdb` again sees `existing_validation.signer != A` (it's currently `B`), so it again resets `version` to 0.
4. Any unprivileged remote peer — with no knowledge of `A`'s private key, simply having observed step 1's gossip — resubmits the exact same captured chunk `C` (unmodified `data` and `sig`) to a node via `PUT /stackerdb_chunk`, or pushes it via `StackerDBPushChunk` gossip.
5. `try_replace_chunk` validates: `slot_desc.verify(&A)` succeeds (the signature is still valid — nothing about it changed), and `v > 0` (the reset baseline) passes the freshness check. The stale chunk is accepted and stored as the "current" chunk for slot `k`, and is then eligible for further propagation to the rest of the network by that node's StackerDB sync/gossip logic (`validate_received_chunk`, `handle_unsolicited_StackerDBPushChunk`). [5](#0-4) [6](#0-5) 

This is the direct structural analog of the report's bug class: an "authentication" value (here, the chunk signature over `slot_id/slot_version/data_hash`) is treated by the storage/validation layer as sufficient proof of "current, freshly-authored data for this specific StackerDB context," when in fact it only proves "at some point A validly signed this triple" — it does not commit to the contract instance or to the particular tenure of slot ownership. The equality that silently breaks is: *"signature verifies for signer X" (which the code checks) vs. "this data was authored during the current assignment epoch of slot k to X"* (which the code assumes but never checks).

### Impact Explanation
An unauthenticated/unprivileged remote peer who has merely observed prior legitimate gossip traffic can, without any signing key, force stale/forged signer-authored content (e.g. an old `BlockResponse::Accepted`/`BlockRejection`, `BlockPreCommit`, or `StateMachineUpdate` message) to reappear as the "current" chunk for a slot in an active `.signers-*` StackerDB, and have it propagate to the rest of the network via normal StackerDB chunk-inventory gossip. Consumers of this data (miners' `StackerDBListener`, other signers' block-response aggregation logic) read chunk contents keyed by slot_id under the assumption that a validly-signed, fresher-than-previously-seen chunk reflects the signer's current intent. Replaying an old, stale-but-validly-signed acceptance/rejection or state-machine-update message can mislead these consumers (e.g., resurrecting a stale `BlockAccepted` for a block that is no longer the tip, or resurrecting an old `StateMachineUpdate`) — a case of non-canonical/stale signer state being served and propagated as canonical/current. This maps to the "network-wide propagation of forged data" / "steering a node off the tip via false inventory" impact tier.

### Likelihood Explanation
The primitive itself (capture a validly-signed chunk from public gossip, then resubmit it later) requires no privileged access and is trivial to execute remotely. The precondition — that a given signer address is reassigned away from and then back to the same `slot_id` in the same signer-set StackerDB contract across reward cycles — depends on how the reward-set/slot ordering algorithm assigns positions cycle to cycle; this is plausible but not guaranteed on every cycle, since slot assignment appears deterministic based on the reward-set computation (e.g., sorted by signing key in some contracts) rather than being sticky to "last known slot." The exact stickiness/ordering behavior of slot assignment for the live `.signers-*` contracts could not be fully confirmed from the indexed context (the reward-set → slot assignment mapping function was only partially inspected), so likelihood is assessed as data-dependent rather than guaranteed-on-every-cycle.

### Recommendation
Bind the signed digest to the specific StackerDB context and to the current slot-assignment epoch, not just to the raw `(slot_id, slot_version, data_hash)` triple:
- Include the `QualifiedContractIdentifier` (or a per-DB fixed salt/ID) in `SlotMetadata::auth_digest()`, and/or
- Introduce a monotonically increasing "slot epoch" counter that is bumped (and included in the digest, or used as an additional freshness gate) every time `reconfigure_stackerdb` reassigns a slot's signer, so that replays of pre-reassignment chunks are rejected even though the raw signature still recovers to the correct address.
- As a narrower fix, when `reconfigure_stackerdb` resets a slot back to a previously-seen signer, ensure the new baseline version can never be satisfied by a previously observed `(data, sig, version)` tuple — e.g., persist the "last version ever seen for (contract, slot_id, signer)" across reassignments instead of unconditionally resetting to `NO_VERSION`.

### Proof of Concept
1. Configure a StackerDB contract with slot 0 owned by signer `A`.
2. `A` signs and submits chunk `C0 = StackerDBChunkData{ slot_id: 0, slot_version: 5, data: D, sig: sig_A }` via `StackerDBTx::try_replace_chunk`; it is accepted (per the existing test `test_stackerdb_insert_query_chunks`, this path is proven to work: [7](#0-6) ). An attacker with no keys simply records `C0` bytes from network traffic.
3. Call `StackerDBTx::reconfigure_stackerdb(&sc, &[(B, 1)])` — slot 0's signer changes from `A` to `B`; the row is reset to `version = NO_VERSION`, `sig = empty` (per `reconfigure_stackerdb` logic at `stackslib/src/net/stackerdb/db.rs:298-333`, and demonstrated by the existing test `test_reconfigure_stackerdb` showing reset behavior on signer change: [8](#0-7) ).
4. Call `StackerDBTx::reconfigure_stackerdb(&sc, &[(A, 1)])` again — slot 0 reverts to `A`; because the currently-stored signer (`B`) differs from the new one (`A`), the row is reset again to `version = NO_VERSION`.
5. Attacker (no private key required) resubmits the previously captured `C0` (`slot_version: 5`, `sig_A`) via `try_replace_chunk`. `slot_desc.verify(&A)` succeeds (signature unaffected by resets), and `5 > 0` passes the freshness check — the stale chunk is accepted and becomes the "current" data for the slot, ready to be redistributed to peers via `validate_received_chunk`/gossip.

This chain cannot be fully executed end-to-end against the live `.signers` boot contract from the indexed context alone (the reward-set slot-assignment stickiness across cycles was not fully verified), so this PoC is expressed against the underlying `StackerDBTx` primitives, which are directly reachable from the same `reconfigure_stackerdb`/`try_replace_chunk` code paths used by the live network sync and HTTP chunk-ingestion logic.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }

        config: &StackerDBConfig,

    ) -> Result<bool, net_error> {

                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }

            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr

            return Ok(false);
