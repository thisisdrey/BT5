### Title
Race between `window.Check`/`window.Update` and unlocked `DecryptDanger` allows duplicate acceptance of a replayed messageCounter - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` checks the anti-replay window, releases the lock, performs decryption unlocked, and only then re-locks to mark the counter as used. Two concurrent `Decrypt` calls carrying the same `messageCounter`/ciphertext can both pass `window.Check` before either has called `window.Update`, letting both decrypt and both return successfully, violating the single-use invariant for a given (key, nonce) pair.

### Finding Description
`Decrypt` in `connection_state.go` splits the check-then-mark replay protection into two separately locked critical sections with the actual AEAD operation performed outside the lock: [1](#0-0) 

Because `cs.decryptLock` is released between the `window.Check` call and the `window.Update` call, if two goroutines call `Decrypt` with the same `messageCounter` at roughly the same time, both can observe `window.Check` returning `true` (since neither has updated the bitmap yet), both proceed to call `cs.dKey.DecryptDanger` with the same key/nonce/ciphertext, and both succeed, each returning `nil` error. Only after both decryptions complete does one of the two calls to `window.Update` (in `bits.go`, via `updateSlow`'s duplicate check) fail for the second caller — but by that point the decrypted plaintext has already been produced and returned to the caller for both invocations.

This is reachable purely from attacker-controlled UDP packets: nothing prevents a remote peer/attacker from sending duplicate UDP datagrams (or an on-path attacker replaying a captured datagram) that race with the original packet's processing goroutine, since Nebula's UDP receive loop can dispatch to worker goroutines that call `Decrypt` concurrently for the same tunnel.

### Impact Explanation
Successfully decrypting the same nonce/ciphertext twice does not itself leak new plaintext (AEAD decryption is deterministic on the same inputs), but it breaks the anti-replay invariant that "each key/nonce pair is used at most once" and causes the tunnel to process/deliver the same packet twice to the upper layer (double delivery), which can manifest as traffic duplication, double firewall-state mutation, or double delivery to the TUN device — a state-poisoning/replay-bypass class issue rather than a full decryption/key-recovery break. It weakens replay protection guarantees relied upon elsewhere in the codebase.

### Likelihood Explanation
This requires no privileges beyond sending UDP packets to an established tunnel and relies on a narrow race window between the unlocked decrypt call and the second locked update — it is timing-dependent and requires the receive path to actually process two packets with the same counter concurrently (i.e., duplicate packets arriving close enough in time to be scheduled on different goroutines). It is feasible to trigger with a controlled test harness (spawning two goroutines that call `Decrypt` simultaneously), which is a reasonable proxy for two duplicate UDP packets processed concurrently in production.

### Recommendation
Perform the replay check, decrypt, and window update as a single atomic operation with respect to `cs.decryptLock` — e.g., hold `decryptLock` across `window.Check`, `DecryptDanger`, and `window.Update`, or restructure to do the tentative window update (reserve the slot) before decrypting and roll back on decryption failure, ensuring no other goroutine can observe the counter as "available" while a decrypt for that counter is in flight.

### Proof of Concept
Unit test in `connection_state_test.go`: construct a `ConnectionState` with a real cipher, encrypt a single packet using `eKey`/`messageCounter`, then call `cs.Decrypt` twice concurrently (via two goroutines with a `sync.WaitGroup`) with the same `messageCounter`, `packet`, and fresh `out`/`nb` buffers. Assert that only one of the two calls returns `(plaintext, nil)` and the other returns `ErrAlreadySeen`; currently, due to the lock/unlock/lock pattern in `Decrypt`, both calls can return `nil` error with decrypted plaintext, demonstrating the double-acceptance bug.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
