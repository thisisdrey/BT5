### Title
Dust-transfer griefing fills a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER`, causing a partial DoS of deposits, transfers, and issuance - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a per-account cap of `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount` + `debtTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens` ( [1](#0-0) ). Because `DepositToken` is a freely transferable ERC-20 and every first-time receipt registers the token in the recipient's list (`DepositToken._transfer` → `pool.addToDepositTokensOfAccount(recipient_)` at [2](#0-1) ), an unprivileged attacker can dust-transfer tiny amounts of many distinct registered deposit tokens to a victim, filling their combined list to 30. Once saturated, `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` ( [3](#0-2) ), so the victim cannot receive any new deposit token (deposit, incoming transfer, liquidation seizure proceeds routed as deposits) nor mint a new debt token type — a partial denial of service analogous to CVE-2019-2977's limited availability impact.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30` bounds the per-account enumerable sets ( [4](#0-3) ).
- The cap modifier counts both sets: `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` reverts.
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked` on `sender_`, [5](#0-4) ); there is no opt-in or minimum-amount check for the recipient. Any nonzero transfer to an account with `balanceOf[recipient_] == 0` permanently registers that token until the recipient fully zeroes it.
- `DebtToken._mint` similarly registers each new debt token via `addToDebtTokensOfAccount`, so saturated accounts also revert inside `DebtToken.issue`/`mint` for new synths, and inside `DepositToken._mint` for new collateral deposits.

Attack path: attacker deposits small amounts of each listed collateral, then calls `depositToken_i.transfer(victim, 1 wei)` for N distinct deposit tokens. Once the victim's combined count hits 30, `victim` cannot: deposit a collateral type they don't already hold (`deposit` → `_mint` → `addToDepositTokensOfAccount` reverts), receive transfers/seizures of new tokens, or issue a new synthetic asset (`issue` → `_mint` → `addToDebtTokensOfAccount` reverts). No modifier stops this: `addToDepositTokensOfAccount` is permissionless-gated only on `msg.sender` being a registered deposit token, which it is.

### Impact Explanation
Partial denial of service of the victim's position management. The victim cannot add new collateral types or open debt in new synthetics, which can leave them unable to improve health during adverse price movement (they can only deposit collateral types already in their list). Recovery requires the victim to fully transfer out the dusted tokens (balance → 0 triggers `removeFromDepositTokensOfAccount`), which costs gas per token and requires the dust to be *unlocked* — but `_revertIfLocked` only restricts the attacker, and a victim with existing debt may have locked balances that prevent clearing some entries, extending the freeze. This maps to the CVE's unauthorized partial-availability impact on an unauthenticated remote attacker.

### Likelihood Explanation
Requires the pool to list multiple deposit tokens (deployed configs do list several collaterals per pool) and the attacker to hold dust of each — obtainable by depositing minimal amounts. Cost is bounded by gas and dust value; no privileged role, oracle manipulation, or reentrancy needed. Moderate likelihood: impact is a recoverable but disruptive freeze rather than fund theft.

### Recommendation
- Exclude zero-or-dust "slots" from the cap by tracking the cap against tokens with meaningful balance (e.g., only count a token toward `MAX_TOKENS_PER_USER` once, and make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` a no-op instead of reverting when the token is already registered — it already reverts `DepositTokenAlreadyExists` after the cap check, but the cap check runs first).
- Prefer: reorder so `add()` is attempted and only revert `UserReachedMaxTokens` if it's a genuinely new entry; even better, make the add functions silently skip when already present so saturation only blocks *new* token types rather than reverting all flows.
- Alternatively, allow recipients to forcibly clear entries (e.g., a `burn`/`sweepDust` on `DepositToken` callable by the balance holder regardless of lock state), or add a minimum-dust threshold for first-time registration.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {DepositToken} from "contracts/DepositToken.sol";

contract DustGriefingTest is Test {
    Pool pool;
    DepositToken[] depositTokens; // all deposit tokens registered in pool
    address victim = address(0xBEEF);
    address attacker = address(0xA77AC);

    function testDustGriefing() public {
        uint256 max = pool.MAX_TOKENS_PER_USER(); // 30

        // Attacker deposits 1 unit of underlying per deposit token, then dusts victim
        for (uint256 i; i < depositTokens.length && pool.getDepositTokensOfAccount(victim).length < max; ++i) {
            DepositToken dt = depositTokens[i];
            // attacker holds unlocked dust (no debt -> fully unlocked)
            vm.prank(attacker);
            dt.transfer(victim, 1);
        }

        // Victim's list is now saturated with attacker-chosen tokens
        assertEq(
            pool.getDepositTokensOfAccount(victim).length +
                pool.getDebtTokensOfAccount(victim).length,
            max
        );

        // Victim cannot deposit a collateral type not already in their list
        DepositToken newToken = depositTokens[depositTokens.length - 1]; // not yet held by victim
        deal(address(newToken.underlying()), victim, 1e18);
        vm.startPrank(victim);
        newToken.underlying().approve(address(newToken), 1e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newToken.deposit(1e18, victim);

        // Incoming dust/transfers of any not-yet-registered token also revert
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newToken.transfer(victim, 1);
        vm.stopPrank();
    }
}
```

Notes for fork reproduction: run against a forked pool with ≥2 listed deposit tokens; attacker seeds dust via `deposit()` then `transfer(victim, 1)`. Each successful dust transfer adds one slot; after 30 combined slots, any `deposit`/`transfer`/`issue` that would register a new token for the victim reverts with `UserReachedMaxTokens`.
