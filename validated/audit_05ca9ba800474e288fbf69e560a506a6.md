## Title
Unhandled `ItemNotFoundException`/`BadItemException` from `MarketOrderIdListCapsule` construction crashes the OSPF-style lookup path in `MarketCancelOrderActuator.execute()` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java`)

### Summary
`MarketPairPriceToOrderStore.get()` looks up a `MarketOrderIdListCapsule` by a price-pair key that is *derived at execute time* from the order's current sell/buy quantities, not validated to exist during `validate()`. `MarketCancelOrderActuator.validate()` (lines 189–216) only checks that the order exists, is active, and belongs to the owner — it never confirms that the corresponding `pairPriceToOrderStore` entry for the order's *current* price key is present. This is structurally the same bug class as CVE-2024-34088: a lookup function (`get_edge()` in FRR, `pairPriceToOrderStore.get()` here) can fail to find the expected record, and the calling code dereferences the result without checking. [1](#0-0) 

### Finding Description
In `execute()`, the actuator recomputes the price key from the order's live fields and fetches the order-id list directly: [2](#0-1) 

`pairPriceToOrderStore.get(pairPriceKey)` is declared to throw `ItemNotFoundException`, which the actuator does catch generically: [3](#0-2) 

However, `MarketOrderIdListCapsule`'s underlying construction path can also throw `BadItemException` (uncaught here) if the stored bytes are malformed/empty in ways that don't trigger `ItemNotFoundException`, and more importantly `validate()` never asserts that a `pairPriceToOrderStore` entry exists for the *exact* pairPriceKey that `execute()` will compute. Because the pairPriceKey is a function of `orderCapsule.getSellTokenQuantity()`/`getBuyTokenQuantity()` (the original order price, immutable per order) combined with token IDs, any state where this list entry is missing or has been concurrently removed by a preceding order/match in the same block (e.g., another `MarketSellAssetActuator` match emptied and deleted the list via `pairPriceToOrderStore.delete(pairPriceKey)` in `matchOrder()`) causes `execute()` to throw an uncaught runtime exception instead of a handled `ContractValidateException`/`ContractExeException`, aborting block application in `Manager`.

This mirrors the OSPF `get_edge()` bug class: a store/lookup function whose failure mode (missing key) is not defensively checked by the caller before dereferencing the returned object (`orderIdListCapsule.removeOrder(...)`, `orderIdListCapsule.isOrderEmpty()`). [4](#0-3) 

### Impact Explanation
If reachable, an uncaught exception thrown while applying a transaction inside block processing (rather than being converted into a normal `ContractExeException`/failed receipt) can propagate up through `Manager`'s transaction processing and crash block application, i.e., a denial-of-service against the node processing that block — analogous to the FRR OSPF daemon crash from an unhandled NULL. This would satisfy the "node crash or halt" acceptance criterion if reproducible.

### Likelihood Explanation
I was **not able to fully confirm** that this state (order exists and belongs to caller, but its `pairPriceToOrderStore` entry is missing) is reachable through the normal order lifecycle in this codebase within the tool budget available. `MarketSellAssetActuator.matchOrder()` does delete `pairPriceToOrderStore` entries when an order list becomes empty, and orders are only removed from `orderIdListCapsule` — not directly from `pairPriceToOrderStore` — through `removeOrder`, which itself calls back into `pairPriceToOrderStore`. Establishing a definitive interleaving where `MarketCancelOrderActuator.execute()` observes a stale `pairPriceKey` with no backing list entry requires deeper trace of `MarketOrderIdListCapsule.removeOrder()` and confirming whether `MarketPairToPriceStore`'s counters and `pairPriceToOrderStore` deletions can ever get out of sync with an order's `active` state within a single block or across blocks (e.g., due to reentrant matching, partial fills, or same-block cancel-after-match ordering). This was not verified with certainty, so likelihood is **uncertain/unconfirmed** rather than proven.

### Recommendation
- In `MarketCancelOrderActuator.execute()`, treat a null/exceptional result from `pairPriceToOrderStore.get(pairPriceKey)` as expected and convert it into a `ContractExeException`/failed transaction result rather than letting any non-`ItemNotFoundException`/`InvalidProtocolBufferException`/`BalanceInsufficientException` exception (e.g., `BadItemException`) propagate uncaught.
- Add symmetry checks in `validate()` mirroring the exact pairPriceKey the executor will use, verifying the entry's existence before committing to `execute()`.
- Broaden or add a catch-all in the actuator dispatch layer (wherever actuators are invoked during block application) so any unexpected `RuntimeException` from an actuator's `execute()` is converted to a rejected transaction rather than crashing block processing — this would harden against this specific bug class and any other unchecked-store-lookup analog uniformly.

### Proof of Concept
Not independently reproducible from static analysis alone within the available scope — I could not construct a confirmed sequence of transactions (e.g., market sell + partial match + cancel within the same block) that leaves the order active while removing its `pairPriceToOrderStore` list entry, nor could I rule out that `MarketOrderIdListCapsule.removeOrder`/`MarketUtils.updateOrderState` always keep these two data structures consistent. A background agent with test-execution capability should attempt: (1) create two orders with the same sell/buy token pair and quantities so they share a `pairPriceKey`; (2) fully match/cancel one such that the shared list is deleted via `pairPriceToOrderStore.delete(pairPriceKey)`; (3) attempt to cancel the second, still-active order referencing the same derived pairPriceKey, and observe whether `execute()` throws an unhandled exception instead of a clean `ContractExeException`.
