### Title
Shielded wallet key-derivation GET servlets accept raw spending/viewing key material as URL query parameters, causing key disclosure via logs/history - (File: framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java)

### Summary
Several full-node HTTP API servlets that derive shielded-address key material (spending keys, authorizing keys, nullifier keys, viewing keys) accept the raw secret key bytes as a plain HTTP GET query-string parameter (`value`, `ak`, `nk`, etc.) instead of requiring the caller to use POST with a request body. This is directly analogous to CVE-2019-3803, where Concourse placed a sensitive access token in a URL, allowing it to leak via browser history, proxy logs, or web-server access logs.

### Finding Description
`GetExpandedSpendingKeyServlet.doGet` reads the caller's spending key straight from `request.getParameter("value")` and returns the derived expanded spending key: [1](#0-0) 

The same pattern exists in `GetAkFromAskServlet.doGet` (takes the `ask` authorizing-spend-key value via `value` parameter): [2](#0-1) 

and in `GetNkFromNskServlet.doGet` (nullifier-deriving key `nsk` passed as `value`): [3](#0-2) 

and in `GetIncomingViewingKeyServlet.doGet`, which takes `ak`/`nk` key components via query parameters: [4](#0-3) 

Because all of these are `GET` handlers reading `HttpServletRequest.getParameter`, the secret key material becomes part of the URL query string for any client (browser, curl with shell history, corporate proxy, load balancer, or any intermediary that logs full request URIs) that invokes them exactly as CVE-2019-3803 describes for Concourse's access token. Unlike a POST body, GET query strings are routinely persisted in:
- Web/reverse-proxy access logs
- Browser history and autocomplete caches (if invoked via a browser or embedded webview)
- HTTP `Referer` headers if a resulting page follows an outbound link
- Shell history / process listings if invoked via `curl <url>`

None of these servlets require authentication; any client with network access to the exposed HTTP API port can either supply key material to derive dependent keys, and in doing so leaks that key material to any log-collection or intermediary infrastructure the operator has in place. This is a `RateLimiterServlet`-derived class with no additional access control: [5](#0-4) 

### Impact Explanation
Exposure of a spending key (`sk`), authorizing key (`ask`), or nullifier/viewing key material through logs constitutes key disclosure, which the scope explicitly recognizes as impactful: an attacker who recovers such logs (proxy/CDN/reverse-proxy access logs, browser history on a shared/compromised machine, SIEM ingestion of URLs) can reconstruct a user's shielded spending authority and spend/steal their shielded TRC-20/TRX funds. This matches the CVE's core bug class — sensitive secrets placed in a URL and thus persisted outside the transport-layer encryption boundary once logged.

### Likelihood Explanation
These endpoints exist specifically to support shielded-transaction workflows in wallet-cli / third-party wallet integrations that call the FullNode HTTP API directly; the code paths are reachable by any HTTP client and none of them enforce POST-only usage — `doGet` is implemented and wired identically to `doPost`. Whether these particular shielded endpoints are enabled depends on the `allowShieldedTransactionApi` configuration flag guarding `Wallet`'s shielded methods, which I could not fully confirm is disabled by default from the indexed configuration files (the reference.conf grep returned no default entry, so I cannot state with certainty whether the flag defaults to enabled or disabled — this should be verified directly in the deployed node configuration rather than assumed).

### Recommendation
- Remove or deprecate the `doGet` handlers on all shielded key-derivation servlets (`GetExpandedSpendingKeyServlet`, `GetAkFromAskServlet`, `GetNkFromNskServlet`, `GetIncomingViewingKeyServlet`, and any sibling servlet accepting raw key material) and require POST with a JSON body instead.
- If GET must be retained for backward compatibility, mark it deprecated, emit warnings, and ensure operators are advised in documentation that these endpoints should never be exposed behind logging proxies/CDNs.
- Ensure `Util.getRequestValue`/`PostParams` based POST paths are the sole supported entry points for any endpoint that receives private key material, consistent with the existing `checkBodySize`/`getVisiblePost` helpers already used elsewhere: [6](#0-5) 

### Proof of Concept
1. Enable the full node HTTP API and the shielded transaction API (`allowShieldedTransactionApi = true`).
2. As an anonymous network client, issue: `curl "http://<node>:8090/wallet/getexpandedspendingkey?value=<sk_hex>"`.
3. The secret `sk_hex` is now embedded in the URL, and will be captured verbatim by:
   - Any reverse proxy or load balancer access log (`GET /wallet/getexpandedspendingkey?value=<sk_hex> HTTP/1.1`)
   - The requester's shell history if `curl` was invoked interactively
   - Browser history if the same URL is opened in a browser tab
4. Any party with read access to those logs/history can extract `sk_hex` and derive the full shielded spending authority, matching the disclosure mechanism described in CVE-2019-3803.
