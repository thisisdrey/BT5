### Title
Dust DepositToken transfers fill a victim's account token list (MAX_TOKENS_PER_USER), blocking the victim from adding new collateral types — ([File: contracts/DepositToken.sol](contracts/DepositToken.sol) / [File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2017-13721 — where an authenticated X client could corrupt/abort the *shared segments of other clients in the same session* — any unprivileged account can write into another account's per-user token list. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance goes from zero to nonzero, and `transfer()`/`transferFrom()` only check the *sender's* unlocked balance. An attacker can therefore spam 1-wei transfers of every `DepositToken` in a `Pool` to a victim, filling the victim's `MappedEnumerableSet` up to `MAX_TOKENS_PER_USER` without the victim's consent.

### Finding Description
- `DepositToken.transfer()` only validates `_revertIfLocked(_msgSender, amount_)` on the sender side before calling `_transfer` (`contracts/DepositToken.sol:348-354`).
- `_transfer` adds the token to the recipient's account list whenever the recipient previously had a zero balance (`contracts/DepositToken.sol:517-520`).
- `_mint` does the same on deposits (`contracts/DepositToken.sol:485-488`), so `deposit(amount, onBehalfOf)` is another vector that writes into an arbitrary `onBehalfOf_` account's list.
- The recipient has no opt-in/opt-out: the account-list entry is created purely by the caller's action. The list is bounded (`MAX_TOKENS_PER_USER` via `MappedEnumerableSet` in `contracts/storage/PoolStorage.sol`), and `addToDepositTokensOfAccount` reverts once the set is full — meaning every subsequent operation that would register a *new* deposit token for the victim reverts.
- The same pattern exists for debt positions via `addToDebtTokensOfAccount` on `_mint` (`contracts/DebtToken.sol:597-600`), though minting debt on a victim requires the SmartFarmingManager, so the deposit-token path is the reachable surface.

Attack path (all unprivileged, public entry points):
1. Attacker deposits dust amounts of each of the pool's N collaterals to themselves (or uses `deposit(amount, victim)` directly), obtaining N distinct `msdX` tokens.
2. Attacker calls `msdX_i.transfer(victim, 1)` for each token, or `transferFrom` after self-approval — each call adds `msdX_i` to `depositTokensOfAccount(victim)` until the set hits `MAX_TOKENS_PER_USER`.
3. Any later legitimate deposit of a *new* collateral type to the victim (`deposit(..., victim)` from anyone, or a transfer of a token the victim doesn't hold) reverts inside `addToDepositTokensOfAccount`, because the victim's set is already full.

### Impact Explanation
The invariant broken is per-account state isolation: one user's transaction mutates another user's bounded account list. Consequences:
- The victim is temporarily unable to add new collateral types. If the victim has an open debt position deteriorating toward liquidation, they cannot top up with a different collateral asset — their position can be liquidated while the rescue deposit reverts (temporary freezing of the collateral-addition path, forced loss via liquidation).
- Recovery requires the victim to spend gas transferring/burning each dust token to clear set slots, and if the victim's position is unhealthy the attacker can re-fill slots faster than the victim clears them.

### Likelihood Explanation
High reachability: `transfer`, `transferFrom`, and `deposit(amount_, onBehalfOf_)` are all public, unprivileged, and only gated by `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` — none of which stop this. Cost is N dust transfers plus negligible underlying. The constraint is that impact requires either a capped set small enough to fill cheaply, or a victim whose rescue depends on a new collateral type; damage is bounded (griefing / forced liquidation path rather than direct theft).

### Recommendation
- In `Pool.addToDepositTokensOfAccount`, treat "set full" as a no-op for tokens added via incoming `transfer`/`deposit` to `onBehalfOf_`, or charge the sender rather than accounting against the recipient's bounded set.
- Alternatively, require recipients to opt in (e.g., only add to the account list on `deposit`/`withdraw`-initiated mints and liquidations, not on plain ERC20 `transfer`/`transferFrom`), or let `debtPositionOf` iterate a sender-managed list instead of an attacker-writable one.
- Add a regression test: fill `victim`'s list to `MAX_TOKENS_PER_USER` via dust `transfer`s, then assert `deposit(newCollateral, victim)` behavior is the intended one.

### Proof of Concept
```solidity
// Foundry fork test sketch — mainnet fork with deployed Pool/DepositTokens
function testFillVictimTokenList() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    IPool pool = IPool(POOL);
    // assume MAX_TOKENS_PER_USER distinct DepositTokens exist
    IDepositToken[] memory tokens = getAllDepositTokens(pool);

    for (uint256 i; i < tokens.length; ++i) {
        IERC20 underlying = tokens[i].underlying();
        deal(address(underlying), attacker, 10);
        vm.startPrank(attacker);
        underlying.approve(address(tokens[i]), 10);
        tokens[i].deposit(10, attacker);      // attacker holds dust msdX_i
        tokens[i].transfer(victim, 1);        // adds msdX_i to victim's set
        vm.stopPrank();
    }

    // victim's account list is now at MAX_TOKENS_PER_USER
    // any deposit of a NEW collateral type to victim reverts:
    IDepositToken newToken = getNewDepositToken(pool);
    IERC20 newUnderlying = newToken.underlying();
    deal(address(newUnderlying), attacker, 1e18);
    vm.startPrank(attacker);
    newUnderlying.approve(address(newToken), 1e18);
    vm.expectRevert(); // addToDepositTokensOfAccount: set full
    newToken.deposit(1e18, victim);
    vm.stopPrank();
}
```

Uncertainty note: the exact revert/append behavior inside `Pool.addToDepositTokensOfAccount` and the `MAX_TOKENS_PER_USER` constant could not be re-verified line-by-line within this pass (only match counts were retrieved for `contracts/Pool.sol`). The finding stands on the confirmed writes in `DepositToken.sol` (`_mint`/`_transfer` → `addToDepositTokensOfAccount`, lines 485–488 and 517–520) and the bounded `MappedEnumerableSet` account list in `contracts/storage/PoolStorage.sol`; if the Pool implementation silently ignores overflow instead of reverting, the impact downgrades to reward-index/list inconsistency rather than a revert-based freeze and should be revalidated against the full `Pool.sol` source.
