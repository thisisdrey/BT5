### Title
Uncontrolled attacker-supplied length used for array pre-allocation in `PrecompiledContracts.extractSigArray` causes asymmetric memory consumption - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractSigArray` reads a signature-count field directly from smart-contract call data and immediately allocates a two-dimensional array sized by that untrusted value, before validating it against the actual size of the supplied `data` buffer. This mirrors the go-git advisory's root cause: a length field taken from untrusted input is used to size an in-memory structure ahead of any bound check against the real payload size, producing wildly asymmetric memory consumption relative to the small amount of attacker-supplied bytes.

### Finding Description
`extractSigArray` computes `len` from a caller-controlled `DataWord` and uses it directly to allocate `bytesArray`: [1](#0-0) 

`words[offset].intValueSafe()` converts an arbitrary 256-bit word from calldata into a Java `int`, and that value is used unchecked as the size of `new byte[len][]`. There is no comparison of `len` against `words.length`, the number of actual signature words present in `data`, or any protocol-defined maximum before the allocation happens — the bounds check inside the following loop (`words[offset + i + 1]`) would only fail *after* the array has already been allocated, and a sufficiently large `len` alone (independent of whether the subsequent loop ever completes) is enough to force a large heap allocation attempt. This is the same bug class as the go-git `.idx` issue: a compact/small crafted input encodes a large declared size, and the parser allocates memory proportional to the declared size rather than the actual input size, producing asymmetric memory consumption (CWE-770/CWE-191 class issue).

### Impact Explanation
Because `extractSigArray` is invoked from a precompiled contract's `execute(byte[] data)` path that any address can call by sending a transaction that triggers a `CALL`/contract invocation to that precompile, an attacker only needs to submit a small transaction whose calldata encodes a very large signature-count word. This forces the JVM to attempt allocating a correspondingly large `Object[]` (`byte[][]`), which can exhaust node heap memory and crash or stall the executing full node/validator process — a resource-exhaustion Denial-of-Service condition reachable from a single unprivileged transaction, consistent with the "Reject... no-impact analogs" bar of accepting node crash/halt as valid impact.

### Likelihood Explanation
Exploitation only requires crafting and broadcasting a single transaction that invokes the relevant precompiled contract with attacker-chosen calldata bytes, with no special privileges beyond being able to submit a transaction/contract call, matching the "unprivileged transaction broadcaster / contract deployer" reachability requirement. The `intValueSafe()` conversion and unchecked allocation are unconditionally executed on the attacker-supplied `offset` word before any structural validation of `data`'s real length occurs.

### Recommendation
Before allocating `bytesArray` in `extractSigArray`, validate `len` against the actual remaining size of `data`/`words` (e.g., `len >= 0 && (offset + 1 + len) <= words.length` and `len` below a small protocol-defined maximum signature count) and reject with a fast failure otherwise, so the size of any allocation is bounded by the size of the actual supplied calldata rather than by an attacker-chosen 256-bit value.

### Proof of Concept
1. Construct calldata for the precompiled contract path that calls `extractSigArray`, with the word at `offset` set to a very large value (e.g., close to `Integer.MAX_VALUE / 32`, the maximum representable via `intValueSafe()`), while providing minimal actual signature data after it.
2. Submit a transaction invoking the precompile with this calldata.
3. Observe that `new byte[len][]` at [2](#0-1) 
attempts to allocate an array with millions of null-reference slots from only a few hundred bytes of calldata, driving heap pressure and potentially causing an `OutOfMemoryError` or long GC pauses on the processing node — all before energy/execution-time checks in the surrounding execute loop have a chance to bound the cost of the operation.

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
