Based on `mainnet/contracts/market/v0-market-vault.clar`, this vulnerability class is real and confirmed at the vault level, though I was unable to fully verify whether `v0-4-market.clar` (the `impl` contract that gates access via `check-impl-auth`) has a reentrancy lock that would block the described call sequence before it reaches the vault.

### Title
Stale `entry`-snapshot commit in `collateral-add`/`collateral-remove`/`debt-add-scaled`/`debt-remove-scaled` allows reentrant calls to silently overwrite registry `mask`, desynchronizing it from the `debt`/`collateral` maps - (File: mainnet/contracts/market/v0-market-vault.clar)

### Summary
Each of `collateral-add`, `collateral-remove`, `debt-add-scaled`, and `debt-remove-scaled` captures the account's `registry` `entry` (and its `mask`) in a `let` at function entry, computes `updated-mask`/`updated-entry` from that stale snapshot, performs a token transfer to an attacker-controlled `<ft-trait>` mid-function, and only afterward calls `(insert updated-entry)` which unconditionally overwrites the whole `registry` row. [1](#0-0) [2](#0-1)  If a reentrant call for a different asset commits its own `insert` in between, the outer call's later `insert` clobbers that update, desynchronizing `mask` from the true non-zero rows of `debt`/`collateral`.

### Finding Description
`mask-update` in each public function operates on a `mask` value read once via `(get mask entry)` at `let`-binding time, not re-read at commit time [3](#0-2) . `insert` performs an unconditional `map-set registry id params`, replacing the entire row rather than merging bit-by-bit [4](#0-3) .

In `collateral-add`, the order is: snapshot `entry`/`mask` → compute `updated-mask`/`updated-entry` → `check-impl-auth`/pause/amount checks → `(try! (receive-tokens ft amount account))` (an external `contract-call?` into the attacker-supplied `<ft-trait>`) → only then `(insert updated-entry)` [1](#0-0) . `debt-remove-scaled`/`collateral-remove` follow the same "compute-then-transfer/insert" ordering, and `debt-add-scaled` computes and inserts without an intervening external call for that asset, but is itself vulnerable to being the *inner* call that gets clobbered by an outer, still-pending `collateral-add`/`collateral-remove`/`debt-remove-scaled` transfer.

Exploit flow: attacker deploys a malicious `<ft-trait>` contract and calls the market's deposit/withdraw path so that `collateral-add`/`collateral-remove` is invoked for asset Y on the attacker's own account. Inside `receive-tokens`/`send-tokens`, the malicious token's `transfer` implementation calls back (through the legitimate `impl` contract, so `check-impl-auth` still passes since `contract-caller` is the impl contract, not the token) into `debt-add-scaled` for asset X on the same account. That reentrant call reads the still-unmodified `registry` row (mask without Y's bit), sets X's bit, and commits via its own `insert` — this is written to state immediately. Control then returns to the outer `collateral-add`, which resumes with its own stale `updated-entry` (computed before the reentrant call ran, containing only Y's bit) and calls `(insert updated-entry)`, overwriting the registry row and erasing the X debt bit that was just committed. The `debt` map row for asset X, however, was written directly by `add-user-scaled-debt` and is untouched by this overwrite [5](#0-4) . Consequently `(get-debt id X)` is non-zero, but `mask` no longer has X's debt bit set, so `get-position`'s `(lookup-debt user-id mask MAX-U128)` — which only iterates bits present in `mask` via `mask-to-list-debt` — never visits asset X and omits it from the returned `debt` list [6](#0-5) .

None of the existing checks stop this: `check-impl-auth` only validates that the immediate caller is the `impl` contract, which remains true during reentrancy since the call is proxied through the legitimate market implementation; pause states, amount-zero checks, and the `ERR-INSUFFICIENT-*` underflow guards in `remove-user-collateral`/`remove-user-scaled-debt` are unrelated to this ordering bug.

### Impact Explanation
Any health-check, liquidation, or risk-calculation logic that relies on `get-position` to enumerate a user's non-zero debt/collateral rows (rather than iterating the `debt`/`collateral` maps directly) will silently ignore real, non-zero debt that still exists in the `debt` map. This allows an attacker to accumulate real, uncollateralized debt that is invisible to solvency checks and liquidators, directly enabling protocol insolvency — matching the Critical impact category (protocol insolvency) defined in scope.

### Likelihood Explanation
Preconditions are attacker-controlled and inexpensive: deploy one malicious `<ft-trait>` contract, hold a small amount of any accepted asset to open a `collateral-add`/`collateral-remove` position, and trigger a second in-block call to `debt-add-scaled`/`debt-remove-scaled`/`collateral-add` on the same account from within the token's `transfer` callback. The attack is fully repeatable per account and does not require any privileged role, oracle input, or DAO action. The main open uncertainty is whether `v0-4-market.clar` (the `impl` contract gating `check-impl-auth`) imposes a reentrancy lock around its calls into `v0-market-vault.clar`; I was not able to confirm the presence or absence of such a guard within the available context, so the exact reachability of the reentrant call through the impl contract's public entry points remains unverified.

### Recommendation
Re-derive `mask` from a fresh `map-get?` on `registry` immediately before each `insert`, or perform `mask-update` and `insert` atomically without any external `contract-call?` in between (e.g., move `receive-tokens`/`send-tokens` before the mask computation, or merge only the changed field via a scoped `map-set` rather than replacing the whole row from a stale snapshot). Additionally, verify whether `v0-4-market.clar` enforces a reentrancy lock across calls into `v0-market-vault.clar`, and add one if absent.

### Proof of Concept
Clarinet/vitest simnet plan (local fork):
1. Deploy a mock `<ft-trait>` contract whose `transfer` function, when called, invokes the market's `debt-add-scaled` path (through the `impl`/market contract) for a second asset-id on the same account before returning.
2. As the attacker account, call the market path that triggers `v0-market-vault.collateral-add` for asset Y using the malicious token as `ft`.
3. Assert that after the transaction: `(get-debt id X)` returns a non-zero `scaled` value, while `(get-position account MAX-U128)`'s returned `debt` list does not contain an entry with `aid: X`.
4. This demonstrates the mask/`debt`-map divergence described, satisfying the stated invariant violation.

        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
