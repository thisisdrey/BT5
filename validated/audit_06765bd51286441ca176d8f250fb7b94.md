### Title
Unhandled `ArrayIndexOutOfBoundsException` in `ValidateMultiSign` precompile via attacker-controlled offset word - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign.execute()` parses `rawData` as an ABI-style array of 32-byte words and then indexes into that array using an offset value taken directly from the calldata (`words[3]`), without ever validating that the resulting index (and the subsequent indices derived from it in `extractSigArray`/`extractBytesArray`) stay within the bounds of the parsed `words` array. This is analogous to the reported kernel bug class: a length/offset field taken from an untrusted payload is used to index further into the payload without checking that the remaining buffer actually has that many words, producing out-of-bounds access.

### Finding Description
`ValidateMultiSign.execute()` computes: [1](#0-0) 

Key issues:
1. `words[3].intValueSafe() / WORD_SIZE` is fully attacker-controlled (any 32-byte value from calldata) and used directly as an array index into `words` at line 1067 (`words[words[3].intValueSafe() / WORD_SIZE]`). There is no bounds check before this dereference.
2. `extractSigArray`/`extractBytesArray` only check the *entry* offset (`if (offset > words.length - 1) return new byte[0][];`) but the subsequent loop reads `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` for `i` up to an attacker-controlled `len`, with no check that `offset + i + 1 < words.length`: [2](#0-1) 
3. The `VMConfig.allowTvmOsaka()` guard added via `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` only validates that `rawData.length` is 32-byte aligned and its length matches a `header + n*item` shape: [3](#0-2) 
   This check says nothing about the *values* of offset words embedded in the data, so a data blob of exactly the "valid" shape can still contain an offset word pointing far outside `words.length`, triggering `ArrayIndexOutOfBoundsException`.
4. Critically, this offset-computation/array-extraction code path (lines 1066–1074) sits **outside** the `try { ... } catch (Throwable t)` block that wraps only the permission-weight-verification loop (lines 1082–1117). Contrast this with `BatchValidateSign`, which wraps its *entire* body in `execute()` via `try { return doExecute(data); } catch (Throwable t) { ... }`: [4](#0-3) 
   The project's own regression test explicitly documents that outer-frame containment ("leave the outer frame free of any propagated exception") is required for both `ValidateMultiSign` and `BatchValidateSign`, but only exercises the "too few words" early-reject path, not the "correct length, malicious offset" path that still reaches the unguarded array indexing: [5](#0-4) 

An uncaught exception thrown by `contract.execute(data)` propagates directly out of `Program.callToPrecompiledAddress`, since that call site has no surrounding try/catch: [6](#0-5) 

### Impact Explanation
Any smart contract can invoke the `ValidateMultiSign` precompiled contract (reachable via `CALL`/`STATICCALL`/`DELEGATECALL` to its precompile address) with attacker-crafted calldata whose length passes the Osaka ABI-shape check but whose embedded offset word (`words[3]`) is out of range. This throws an unhandled `ArrayIndexOutOfBoundsException` from inside a precompiled-contract call, which is not contained the way `BatchValidateSign` explicitly contains it. This is a broadly reachable, single-transaction trigger (any contract deployer/caller can invoke it), and the maintainers' own test/comment for TIP-854 frames uncontained precompile exceptions as a containment requirement for the outer CALL frame — implying the failure mode this leaves open (for ValidateMultiSign's offset path) can corrupt/derail the enclosing execution frame rather than degrading gracefully to a revert, which is the java-tron project's own stated concern for this exact bug class.

### Likelihood Explanation
High likelihood of reachability: `ValidateMultiSign` is a public precompiled contract callable by any TVM contract with attacker-chosen calldata; no privileged role or special contract state is required. Crafting calldata that satisfies the word-count/alignment check while pointing the offset field out of bounds is trivial.

### Recommendation
Apply the same containment/validation pattern used in `BatchValidateSign.execute()` to `ValidateMultiSign.execute()`: wrap the entire method body (including the offset lookups at line 1067 and the `extractSigArray`/`extractBytesArray` calls at lines 1072–1074) in a `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` (excluding rethrow of timeout exceptions, matching existing convention), and additionally validate that every offset/length word used to index `words[]` is within `[0, words.length)` before use, rather than relying solely on the aggregate length check in `isValidAbiEncoding`.

### Proof of Concept
1. Construct `rawData` of exactly `(5 + 5) * 32` bytes (10 words) so it passes `isValidAbiEncoding(rawData, 5, 5)`.
2. Set word[0] = arbitrary address, word[1] = permission id, word[2] = arbitrary hash-input word.
3. Set word[3] (the offset field, in bytes) to a large value, e.g. `0x00000000000000000000000000000000000000000000000000000000001000` (4096), so `words[3].intValueSafe() / WORD_SIZE` = 128, far beyond `words.length` (10).
4. Deploy a contract that performs `staticcall`/`call` to the `ValidateMultiSign` precompile address with this `rawData`.
5. Execution reaches `words[words[3].intValueSafe() / WORD_SIZE]` at line 1067 (or the equivalent lookup inside `extractSigArray`/`extractBytesArray`), throwing `ArrayIndexOutOfBoundsException`, which is not caught anywhere in `ValidateMultiSign.execute()` and propagates out through `Program.callToPrecompiledAddress` uncontained.

    if (offset > words.length - 1) {

    int len = words[offset].intValueSafe();
