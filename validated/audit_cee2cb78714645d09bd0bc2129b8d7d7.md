Confirmed: the client-side response decoding (`decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs`) performs no hash validation at all — it simply JSON-parses the body into `GetAttachmentResponse { attachment }` without comparing anything to the originally requested `content_hash`. The comparison never happens anywhere in the call chain.

### Title
`AttachmentsBatchStateContext::extend_with_attachments` accepts unverified attachment content, allowing hash-mismatched data injection and reliability-score poisoning - (File: stackslib/src/net/atlas/download.rs)

### Summary
When a victim node requests an attachment by `Hash160` content hash from a peer it selected via `get_prioritized_attachments_requests`, the response handler `extend_with_attachments` inserts the returned `Attachment` bytes into `self.attachments` and calls `report.bump_successful_requests()` without ever checking that `response.attachment.hash()` equals the `AttachmentRequest.content_hash` that was actually requested. A malicious peer can therefore return arbitrary bytes for any requested hash.

### Finding Description
The equality that must hold — served attachment bytes' `hash()` == `AttachmentRequest.content_hash` — is never checked. In `extend_with_attachments`: [1](#0-0) 

the response is decoded via `response.decode_atlas_get_attachment()`, which itself is a pure JSON-parse with no hash validation: [2](#0-1) 

The decoded `attachment` is inserted into `self.attachments: HashSet<Attachment>` and the peer's `ReliabilityReport::bump_successful_requests()` is called unconditionally — with no linkage back to the `request.content_hash` that triggered the fetch. Later, in `AttachmentsDownloader::run`, the `Done` state drains `context.attachments` and calls `attachment.hash()` to look up matching `AttachmentInstance`s and to call `attachments_batch.resolve_attachment(&attachment.hash())`: [3](#0-2) 

Because resolution is keyed off the hash of whatever bytes the attacker sent (not the hash originally requested), a forged attachment whose real hash doesn't match any pending instance is simply inserted into the atlas DB as an "instantiated" but unlinked attachment (`insert_instantiated_attachment`) and does not resolve the pending `AttachmentInstance` for the real `content_hash`. Meanwhile the peer's reliability score is inflated as if it correctly served the request, making the node keep preferring this peer for future requests (since `get_prioritized_attachments_requests`/report selection favors higher-reliability sources), while the real content is never fetched from the batch's other candidate peers within that same batch pass.

### Impact Explanation
This matches the "attachment/BNS mismatch" High-impact category: a node can be made to serve/store data that does not correspond to the on-chain-committed hash for a given BNS name-update, and the attacker's identity is favored for future lookups due to falsely inflated reliability, degrading resolution reliability for legitimately committed attachments. No crash or unauthenticated write of consensus state occurs, so it does not reach the Critical thresholds defined (no memory disclosure, no forged data relayed to other peers, no request smuggling/auth bypass) — the forged attachment is stored locally in the victim's own atlas DB but not propagated as canonical replacing existing state; it's an additional unlinked entry.

### Likelihood Explanation
Preconditions are attacker-cheap: the victim must have a pending `AttachmentInstance` (any BNS name-update creates one) and have selected the attacker's peer URL as one of the `sources` in `AttachmentRequest` (requires only advertising a matching inventory bit for the missing page, which the attacker fully controls in `GetAttachmentsInvResponse`). The attacker peer just answers the plain `GET /v2/attachments/<hash>` RPC with any JSON body decodable as `GetAttachmentResponse`. This is fully remote, requires no secret/privileged role, and is trivially repeatable per attachment fetch cycle.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it against `request.content_hash`. Only insert into `self.attachments` and call `report.bump_successful_requests()` if they match; otherwise call `report.bump_failed_requests()` (and optionally mark the peer as faulty/deregister the event) to prevent reliability-score poisoning from forged content.

### Proof of Concept
Add a unit test in `stackslib::net::atlas::download` tests module:
1. Construct an `AttachmentsBatchStateContext` with a `peers` map containing one `UrlString` -> `ReliabilityReport::empty()`.
2. Build an `AttachmentRequest` with `content_hash = Hash160::from_data(b"expected")`.
3. Build a `BatchedRequestsResult` whose `succeeded` map has `(request.clone(), Some(mock_response))`, where `mock_response` is a `StacksHttpResponse` wrapping a `GetAttachmentResponse { attachment: Attachment::new(b"attacker-controlled-bytes".to_vec()) }` (hash of these bytes ≠ `expected`).
4. Call `context.extend_with_attachments(&mut results)`.
5. Assert: `context.peers.get(&url).unwrap().n_successful_requests` incremented (reliability poisoned) — demonstrating `bump_successful_requests` was called with mismatched content — and separately assert that `context.attachments` contains an `Attachment` whose `.hash()` differs from `request.content_hash`, showing the forged attachment is stored under the wrong key and would never satisfy `attachments_batch.resolve_attachment(&request.content_hash)`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
