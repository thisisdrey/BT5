### Title
Treasury `check_status` treats an inconclusive `PaymentStatus::Unknown` result as a successful payout, permanently discarding unpaid spends - (File: `substrate/frame/treasury/src/lib.rs`)

### Summary
The external report's core defect is that a state machine advances to a "settled" state even when the underlying transfer's success was never confirmed. The local analog is `pallet-treasury::Pallet::check_status`, which maps both `PaymentStatus::Success` and `PaymentStatus::Unknown` to the same "spend processed / removed" branch, without ever verifying the payment actually completed.

### Finding Description
`Treasury::payout` calls `T::Paymaster::pay(...)` and stores the returned payment id under `PaymentState::Attempted { id }` [1](#0-0) .

The follow-up dispatchable `check_status` is the only path that reconciles this attempted state with the real payment outcome. It matches on `T::Paymaster::check_payment(payment_id)`: [2](#0-1) 

`Status::Success | Status::Unknown` are handled identically: the `Spends` entry is removed and `Event::SpendProcessed` is emitted, with `Pays::No` (fee refunded), exactly as if the beneficiary had definitively received the funds. Only `Status::Failure` preserves the spend for retry via `PaymentState::Failed`, and `Status::InProgress` defers with an error.

The `PaymentStatus` enum's own semantics distinguish `Unknown` from `Success` — `Unknown` means the paymaster could not determine the outcome (e.g., the payment id is stale, the backend lost track of it, or an implementation returns `Unknown` on internal error) — yet the pallet's accounting collapses this ambiguous case into "paid." Once `Spends::remove(index)` executes, there is no stored state left to retry or audit the payout: the spend record — the only proof that a beneficiary is owed funds — is destroyed regardless of whether the transfer actually succeeded.

This is structurally the same failure mode as the referenced report: a payout attempt whose completion was never proven is nonetheless recorded as settled, and the accounting state (the `Spends` map) advances irreversibly on that unproven assumption.

### Impact Explanation
If any configured `T::Paymaster` implementation can legitimately return `PaymentStatus::Unknown` for a payment that in fact failed or never executed (which the type explicitly allows for), the beneficiary permanently loses the payout: the spend is deleted, so `payout` can never be called again for that index (`Error::InvalidIndex`), and no compensating mechanism exists. This is a treasury/reward fund-loss bug — value is not conserved and does not settle to the rightful beneficiary — matching the "permanent user-fund lock" / "duplicate settlement or payout" impact category. It is reachable by any signed account (the dispatchable only requires `ensure_signed`), so an ordinary user completing the two-step payout/check_status flow triggers the loss without needing any privileged or malicious actor.

### Likelihood Explanation
Likelihood is bounded by the specific `Paymaster` trait implementation configured for a given runtime: default/local implementations (mint-based) tend not to return `Unknown` for failed payments, but any implementation backed by asynchronous or off-chain settlement (e.g., cross-chain/XCM-based paymasters as used with `pallet-treasury` asset spends) can plausibly report `Unknown` for payments that are lost, dropped, or indeterminate — which is exactly the scenario the enum variant exists for. Given that `check_status` is a normal, expected part of the payout retry flow (as shown by `check_status_works`, which explicitly exercises the `Unknown` branch), the mis-handling is triggered by ordinary operation, not by attacker-crafted edge cases.

### Recommendation
Do not treat `PaymentStatus::Unknown` as equivalent to `Success`. At minimum, keep the `Spends` entry (similar to the `Failure` branch) when the status is `Unknown`, allow retry via `payout`, and/or require an explicit administrative resolution path before removing the record. Only remove the entry and mark it processed when `PaymentStatus::Success` is unambiguously returned.

### Proof of Concept
1. `Treasury::spend(...)` creates spend `index = 0`.
2. `Treasury::payout(origin, 0)` calls `T::Paymaster::pay` and stores `PaymentState::Attempted { id }` [3](#0-2) .
3. Suppose the configured paymaster's backend loses track of the payment (e.g., cross-chain settlement failure) so `T::Paymaster::check_payment(id)` returns `PaymentStatus::Unknown` — the actual transfer to the beneficiary never happened.
4. Any signed account calls `Treasury::check_status(origin, 0)`. Execution enters the `Status::Success | Status::Unknown` arm [4](#0-3) , removing the spend and emitting `SpendProcessed`.
5. The beneficiary never received funds, but `Spends::get(0)` is now `None`; calling `payout` again yields `Error::InvalidIndex`. The funds allocated for that spend are permanently unaccounted for and unclaimable — the treasury's internal ledger falsely records the payout as completed.

Existing tests (`check_status_works`) exercise this exact branch with `PaymentStatus::Unknown` and assert `SpendProcessed` is emitted [5](#0-4) , confirming this behavior is intentional-but-unguarded rather than a hypothetical code path.

				Status::Failure => {
					spend.status = PaymentState::Failed;
					Spends::<T, I>::insert(index, spend);
					Self::deposit_event(Event::<T, I>::PaymentFailed { index, payment_id });
