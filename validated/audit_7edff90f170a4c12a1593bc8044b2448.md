### Title
DoS via unbounded PCRE query in `SearchFilesByContent` enabling ReDoS-style catastrophic backtracking - ([File: internal/gitaly/service/repository/search_files.go])

### Summary
`SearchFilesByContent` passes the client-supplied `Query` field directly to `git grep --perl-regexp -e <query>` with no length or complexity bound, unlike the sibling `Filter` field used in `SearchFilesByName`, which is explicitly capped to prevent "excessive resource usage." An ordinary user with read access to a repository can submit a single RPC with a pathological PCRE pattern that triggers catastrophic backtracking in PCRE's backtracking engine, causing the `git grep` subprocess (and thus the RPC handler) to run for a disproportionately long time relative to the size of the request — mirroring the "very slow execution from a small crafted input" bug class in the referenced report.

### Finding Description
`validateSearchFilesRequest` only checks that `Query` is non-empty and that `Ref` is set; it applies no length or pattern-complexity restriction to `Query`: [1](#0-0) 

That unbounded `Query` is fed straight into `--perl-regexp -e <query>` for `git grep`: [2](#0-1) 

By contrast, the codebase explicitly recognizes this exact risk class and mitigates it for the `Filter` field in `SearchFilesByName`, which is compiled with Go's linear-time RE2 engine (`regexp.Compile`) and is still capped at `searchFilesFilterMaxLength = 1000`: [3](#0-2) [4](#0-3) 

`git grep --perl-regexp` uses a backtracking PCRE engine (not RE2), so unlike `Filter`, the `Query` field is exposed to classic ReDoS patterns (e.g., nested quantifiers like `(a+)+$` or alternation-based blowups) with no upper bound on pattern length or repetition depth. This is directly analogous to the referenced Besu issue, where a crafted, unbounded input parameter caused disproportionate computational cost in an otherwise ordinary code path.

### Impact Explanation
Because `SearchFilesByContent` is reachable by any user who has read access to a repository (e.g., via GitLab's code search feature), a single crafted `Query` can pin a `git grep` process — and the gRPC handler goroutine blocked on it — for an extended, potentially unbounded period against arbitrarily sized repository content. Since Gitaly's concurrency/queueing protections (`internal/gitaly/service/hook/pack_objects.go`'s limiter machinery) target pack-objects specifically, and there is no evident length/complexity cap analogous to `Filter`'s cap applied to `SearchFilesByContent`, repeated or concurrent requests with such patterns can exhaust worker/goroutine capacity and CPU on the Gitaly node, degrading service for other tenants on the same storage shard. This fits "DoS of a handler" under the accepted impact categories.

### Likelihood Explanation
Likelihood is moderate-to-high: the RPC is reachable by any authenticated user with read access to a repository, requires no special privileges, no MITM, and no dependency on a malicious peer — only a crafted request field, matching the "ordinary user's ... crafted RPC field" validation bar. The only precondition is that at least one file/ref match the search scope so `git grep` actually scans content, which is trivially satisfied in any non-empty repository.

### Recommendation
Apply the same defensive posture used for `SearchFilesByName`'s `Filter` field to `SearchFilesByContent`'s `Query`:
- Enforce a maximum length on `Query` (e.g., reuse or extend `searchFilesFilterMaxLength`) in `validateSearchFilesRequest`.
- Consider rejecting or normalizing patterns with known-dangerous PCRE constructs (nested quantifiers, unbounded backreferences), or apply a wall-clock/CPU timeout on the spawned `git grep` process specific to this RPC so a pathological pattern cannot block the handler indefinitely.
- Alternatively, evaluate replacing `--perl-regexp` with `--extended-regexp`/`--basic-regexp` (POSIX engines with bounded worst-case behavior) when the query doesn't require PCRE-only features, or route the timeout through the existing command execution context so it is bounded regardless of RPC deadline.

### Proof of Concept
1. As an ordinary user with read access to a repository containing at least one line of text on `HEAD` (or any valid ref), call `SearchFilesByContent` with:
   - `Repository`: the target repo
   - `Ref`: `"HEAD"`
   - `Query`: a classic PCRE catastrophic-backtracking pattern, e.g. `"(a+)+$"` combined with matching content containing a long run of `a` characters followed by a non-matching character (e.g., a file whose content is `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!"`).
2. Observe that the underlying `git grep --perl-regexp -e '(a+)+$'` process against that content takes disproportionately long (exponential in the length of the `a` run) compared to normal queries of similar byte size, while `validateSearchFilesRequest` performs no rejection based on pattern complexity or length.
3. Repeat concurrently to demonstrate handler-level resource exhaustion, since no per-request timeout or length cap analogous to `searchFilesFilterMaxLength` exists for this code path.

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
