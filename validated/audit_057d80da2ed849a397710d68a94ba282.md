### Title
`has_in_flight_tx` can be permanently stuck at `true` if the `ban_relayer` promise's `FunctionCall` action fails, freezing the wallet - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`create_ban_relayer_promise` batches `delete_key(pk)` and `function_call_weight("ban_relayer", ..., static_gas=1 TGas, GasWeight(1))` as two actions on a single receipt with no `.then()` callback attached. `rlp_execute` sets `self.has_in_flight_tx = true` in its own (separate, already-committed) receipt before this promise resolves, but the only code path that resets the flag back to `false` is the `self.has_in_flight_tx = false;` line inside `ban_relayer` itself. If the `ban_relayer` `FunctionCall` action fails (e.g., insufficient gas), the whole ban-relayer receipt is rolled back atomically per the runtime's documented "failed receipt atomicity" behavior, so the flag reset is never persisted, permanently stuck at `true`.

### Finding Description
`rlp_execute` (`lib.rs:89-128`) checks `has_in_flight_tx` up front and no-ops if `true`. On `Err(Error::Relayer(_))` with `env::signer_account_id() == current_account_id`, it calls `create_ban_relayer_promise` and then unconditionally sets `self.has_in_flight_tx = true` (`lib.rs:121-124`) before the created promise/receipt is even processed — these are two independent receipts. [1](#0-0) 

`create_ban_relayer_promise` builds a single receipt with two batched actions on `current_account_id` — `delete_key(pk)` then `function_call_weight("ban_relayer", ..., Gas::from_tgas(1), GasWeight(1))` — with no `.then()` chained to catch a failure: [2](#0-1) 

The only reset of `has_in_flight_tx` for this path lives inside `ban_relayer` itself: [3](#0-2) 

Per the runtime execution model, multi-action receipts execute actions in order and are atomic: any action failure causes `state_update.rollback()`, discarding **all** state changes from that receipt — this would also discard the `has_in_flight_tx = false` write inside `ban_relayer` if that action fails to complete (e.g., runs out of its allotted gas): [4](#0-3) [5](#0-4) 

Notably, every other internal self-call in this same contract (`rlp_execute_callback`, `address_check_callback` via `RLP_EXECUTE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`) reserves 5 TGas as static gas for calling back into itself, while `create_ban_relayer_promise` reserves only 1 TGas: [6](#0-5) 

An attacker who holds a Function-Call access key on the wallet-contract account (`env::signer_account_id() == current_account_id`, e.g. a limited-scope automation key granted by the true owner) can submit a malformed/relayer-error-triggering RLP transaction directly via `rlp_execute` while attaching just enough total gas to (a) satisfy the minimum static-gas reservation so `rlp_execute` itself succeeds and commits `has_in_flight_tx = true`, but (b) leave the `GasWeight(1)`-based leftover-gas share for the `ban_relayer` `FunctionCall` action at or near zero, so only the guaranteed 1 TGas static allocation is available for it. If that 1 TGas is insufficient to cover wasm contract loading/compilation plus execution (a materially tighter budget than the 5 TGas the contract's own authors use elsewhere for equivalent self-calls), `ban_relayer`'s action fails, the whole receipt rolls back (undoing both `delete_key` and the flag reset), and `has_in_flight_tx` is left permanently `true`. Every subsequent call to `rlp_execute` then immediately no-ops at line 97-105, permanently freezing the account.

### Impact Explanation
Once stuck, `rlp_execute` (the sole entry point for spending/transferring NEAR or NEP-141 tokens out of this eth-implicit wallet-contract account) always short-circuits with an error and never issues further promises, permanently freezing all NEAR and NEP-141 assets held by the account. Because the attacker in this scenario need only hold a scoped Function-Call access key (not full ownership), this also functions as an authorization escalation: a party intended to have limited, method-scoped permissions can inflict total, permanent denial-of-service on the account owner's funds, exceeding their granted scope. This matches the "permanent freezing of user funds" / DoS bounty category.

### Likelihood Explanation
The attacker must control a Function-Call access key registered on the target wallet-contract account (self, or a limited-permission delegate) and be able to craft an RLP-encoded transaction that deterministically triggers a `Relayer` error (trivial — several existing tests already show garbage/invalid data reliably triggers `Error::Relayer`), while precisely tuning the attached NEAR gas so the leftover unweighted gas available to the `ban_relayer` `FunctionCall` action is minimized. Exploitability hinges on whether 1 TGas static gas is genuinely insufficient for `ban_relayer`'s execution (including wasm loading) under worst-case leftover-gas conditions — this could not be conclusively confirmed from the available index data (exact wasm size/compilation cost figures were not found), but the stark inconsistency with the 5 TGas budget used elsewhere in the same contract for equivalent self-calls is a strong signal of an under-provisioned gas reservation. Repeatable: any account owner or delegate can retry deterministically by resubmitting a relayer-error transaction with the tuned gas amount.

### Recommendation
- Attach a `.then()` callback to the `ban_relayer` promise (mirroring `rlp_execute_callback`/`address_check_callback`) that unconditionally resets `has_in_flight_tx = false` regardless of the promise's success/failure, so the flag reset does not depend on `ban_relayer`'s own action succeeding within the same atomic receipt.
- Increase the static gas reserved for the `ban_relayer` `FunctionCall` action (currently `Gas::from_tgas(1)`) to match the 5 TGas convention used elsewhere in this contract, and/or verify empirically that 1 TGas is always sufficient even under worst-case `GasWeight` starvation.
- Add an invariant test that forces the `ban_relayer` action to run out of gas (or otherwise fail) and asserts `has_in_flight_tx` is still reset to `false` (or that the contract provides an alternative recovery path), not just on the happy path.

### Proof of Concept
1. Deploy the `WalletContract` in a sandbox test (following patterns in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs`).
2. Register a Function-Call access key for the wallet's own `current_account_id` (self-signer).
3. Call `rlp_execute` with malformed `tx_bytes_b64` (as in `test_relayer_invalid_tx_data`) signed by that key, attaching a total gas amount tuned so that after `rlp_execute`'s own execution and the guaranteed static-gas reservations, the `GasWeight(1)`-allocated leftover for `ban_relayer` is minimal (attach only the minimum gas needed to enter the `Err(Error::Relayer(_))` branch and satisfy static reservations).
4. Assert the outer `rlp_execute` call's receipt for `ban_relayer` fails with an out-of-gas error.
5. Query `has_in_flight_tx` via a view method/state inspection and assert it is stuck at `true`.
6. Call `rlp_execute` again with a valid, well-formed transaction and assert it is rejected with "transaction already in progress" indefinitely, demonstrating permanent freeze.

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
