## Analysis

The Zest market contract implements a two-tier oracle design: base price feeds (Pyth/DIA) go through `price-resolve`, which enforces both a positivity check (`oracle-price-legal`) and a timestamp-freshness check (`oracle-timestamp-fresh`) against a per-asset `max-staleness` before the price is trusted [1](#0-0) . However, the stSTX staking ratio — which is multiplied into the price of `stSTX` and `zstSTX` via the `CALLCODE-STSTX`/`CALLCODE-ZSTSTX` transforms — is fetched by a completely separate path, `call-ststx-ratio`, which returns only a raw `uint` ratio with no timestamp field at all [2](#0-1) , and this value is applied in `resolve-ststx` with zero freshness or sanity validation [3](#0-2) .

### Title
Missing staleness/freshness validation on the stSTX ratio callcode used in collateral pricing - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`resolve-ststx` multiplies the base STX price by a staking ratio obtained from `call-ststx-ratio` (an external `block-info-nakamoto-ststx-ratio-v2` contract call) with no timestamp, no staleness bound, and no deviation check, unlike every other price component that flows through `price-resolve`'s `oracle-timestamp-fresh` check. This is the direct analog of the audited stETH/ETH heartbeat/deviation issue: a secondary price-affecting oracle value is trusted and folded into a critical valuation without the same freshness guarantees applied to the primary feed, allowing a stale or lagging ratio to corrupt collateral valuation for `stSTX` and `zstSTX` positions used throughout health checks, borrowing, and liquidation.

### Finding Description
`price-resolve` fetches a base price via `resolve-price-feed` (Pyth/DIA), which returns `{value, timestamp}`, and validates `timestamp` for freshness with `oracle-timestamp-fresh` before returning the final price [1](#0-0) . The callcode transformation (`resolve-callcode`) is applied to that base price inside this same flow, so for `CALLCODE-STSTX`/`CALLCODE-ZSTSTX` the *staking ratio* injected by `resolve-ststx` is never itself timestamp-checked — only the underlying STX/USD feed's timestamp is validated [4](#0-3) . The ratio source, `call-ststx-ratio`, simply forwards whatever `block-info-nakamoto-ststx-ratio-v2::get-ststx-ratio-v3` returns, with no returned timestamp, no staleness threshold, and no bound on deviation from the previous value [5](#0-4) .

This final blended price (`STX price × ststx ratio`, and further `× liquidity index` for `zstSTX`) feeds directly into `get-assets`/`get-notional-evaluation`, which computes `total-collateral-usd` and `total-debt-usd` used for LTV, borrow capacity, and the liquidation health check (`current-ltv >= ltv-liq-partial`) [6](#0-5) . Because the ratio itself is unchecked, if the external ratio provider lags in updating (analogous to a long "heartbeat") or diverges from the true stSTX/STX exchange rate before being refreshed on-chain (analogous to a large "deviation threshold"), the market will compute collateral/debt values off of a stale ratio with no protocol-level safeguard, exactly mirroring the root cause of the referenced report: a secondary price-affecting oracle component lacking the same freshness enforcement as the primary feed, unfairly affecting borrowers/liquidatees.

### Impact Explanation
An unfairly stale-low ratio undervalues `stSTX`/`zstSTX` collateral, pushing healthy positions above the partial/full liquidation LTV thresholds and causing unwarranted liquidation penalties against borrowers — theft of user funds via the liquidation bonus paid to liquidators. An unfairly stale-high ratio overvalues that collateral, letting users borrow beyond their real collateral value and leaving the protocol under-collateralized once the ratio corrects, i.e., protocol insolvency / bad debt. Both map to in-scope Critical/High impact categories (theft of funds at rest, protocol insolvency).

### Likelihood Explanation
No attacker action is required to trigger the divergence — it occurs naturally whenever the external ratio contract's own update cadence lags real staking-reward accrual (or any transient reporting anomaly), and the market has zero code-level defense (no timestamp check, no deviation cap) comparable to the check applied to Pyth/DIA feeds in the same `price-resolve`/`resolve-callcode` pipeline. Any ordinary principal opening a `stSTX`/`zstSTX`-collateralized position, or any liquidator calling `liquidate`, exercises this unguarded path.

### Recommendation
Have `call-ststx-ratio` (or the wrapping `resolve-ststx`) return/track a timestamp alongside the ratio value, and validate it through the same `oracle-timestamp-fresh`/`max-staleness` mechanism already used for Pyth/DIA feeds in `price-resolve`, plus consider bounding the maximum allowed ratio deviation between consecutive reads, matching the fix pattern recommended in the referenced report (tighter heartbeat/deviation enforcement on any oracle input that flows into collateral valuation).

### Proof of Concept
1. `resolve-ststx` is invoked whenever any account holds `stSTX` or `zstSTX` collateral/debt and any borrow, withdraw, or liquidate call triggers `get-assets` → `price-multi-resolve` → `resolve-callcode` → `resolve-ststx` [3](#0-2) .
2. `resolve-ststx` calls `call-ststx-ratio`, which returns the raw ratio from the external Nakamoto contract with no timestamp and no staleness assertion [5](#0-4) .
3. Because `oracle-timestamp-fresh` in `price-resolve` only ever checks the timestamp returned by `resolve-price-feed` (the STX/USD Pyth feed), the ratio applied on top of that price can be arbitrarily lagged/stale without failing any assertion [7](#0-6) .
4. A borrower with `stSTX`/`zstSTX` collateral is then health-checked/liquidated in `liquidate` using this unguarded valuation [6](#0-5) , exposing them to liquidation (or the protocol to bad debt) purely from the ratio's lag/deviation, with no on-chain check to prevent it.

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
