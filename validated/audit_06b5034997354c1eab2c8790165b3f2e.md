### Title
Front-runnable Contract-Creation DoS via Pre-existing Account at Deterministic Contract Address - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.create()` computes the new contract's account address deterministically from the transaction hash and owner address, then unconditionally rejects deployment if any account (even a plain TRX-holding EOA created by an unrelated transfer) already exists at that address. Because the deploy transaction's hash is fixed and visible before it is included in a block, any observer can pre-create an account at the same address and permanently block the legitimate contract deployment — the same "pre-create account at a deterministically-derived address to block init" class of bug described in the external report for `bonding_curve_token_account`.

### Finding Description
When a `CreateSmartContract` transaction executes, `create()` computes the target contract address as `sha3omit12(txId || ownerAddress)` via `WalletUtil.generateContractAddress`: [1](#0-0) 

and then validates that no account already exists at that address, throwing a hard `ContractValidateException` if it does: [2](#0-1) 

The transaction id (`txId`) used in the address derivation is the hash of the raw transaction bytes (`ref_block`, `expiration`, `contract` payload, `fee_limit`, etc.), which is fully determined the moment the transaction is signed/broadcast and is visible in the mempool prior to inclusion in a block. Any network participant (an unprivileged transaction broadcaster with normal node/mempool visibility) can therefore:
1. Observe the pending `CreateSmartContract` transaction and compute the exact `contractAddress` that will be checked at line 360.
2. Broadcast a plain `TransferContract` (or any account-creating operation) sending a trivial amount of TRX to that address with a higher priority, which implicitly creates an `AccountCapsule` at that address before the target deployment transaction is processed.
3. When the original deployment transaction is later applied, `rootRepository.getAccount(contractAddress) != null` is now true, so `create()` throws `ContractValidateException`, and the deployment is rejected — permanently, since the deployer cannot change the deterministic address for that same transaction/nonce combination.

This mirrors the reported Solana pattern: `bonding_curve_token_account` uses `init` on a PDA whose address is derivable in advance, and an attacker pre-creates the account to make the legitimate `init` call fail forever. Here, `create()` similarly uses a strict "must not already exist" check (`getAccount(contractAddress) != null` -> throw) against a deterministically-derivable address, instead of tolerating (or safely absorbing) a pre-existing non-contract account, analogous to the recommended `init_if_needed` fix.

### Impact Explanation
A malicious actor can deny a specific user's contract deployment indefinitely by racing to fund the precomputed contract address before the deployment transaction lands, forcing the deployer to lose the transaction fee/energy and preventing the intended contract from ever being deployed at that address for that transaction. This is a targeted, repeatable denial-of-service against the `TVM` contract-creation path reachable by any address that can observe the mempool and issue ordinary transfers — no special privilege required.

### Likelihood Explanation
Likelihood is bounded by the requirement that the attacker observe the pending deployment transaction (or its transaction id) before it is confirmed and race a competing transaction ahead of it, which is a realistic capability for any node operator or mempool-monitoring actor on a public chain, but requires timing/ordering luck to land the pre-creation transaction first.

### Recommendation
In `VMActuator.create()`, do not unconditionally reject deployment when an account already exists at the computed `contractAddress`. Instead, mirror the collision-handling logic already used for `CREATE2` in `Program.createContractImpl` (checking whether the existing account is already a contract via `isContractExist`, and only rejecting when it truly is a deployed contract, while safely upgrading a plain EOA/balance-holding account in place): [3](#0-2) 

This removes the ability to grief specific deployments by pre-funding the deterministic target address.

### Proof of Concept
1. Attacker monitors the network/mempool and sees a pending `CreateSmartContract` transaction from victim `V`.
2. Attacker computes `contractAddress = sha3omit12(txId(V's tx) || V's ownerAddress)` using the same logic as `WalletUtil.generateContractAddress`.
3. Attacker broadcasts a `TransferContract` sending 1 sun to `contractAddress`, getting it confirmed before V's deployment transaction.
4. V's deployment transaction is later processed; `create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException("Trying to create a contract with existing contract address...")`, permanently failing that deployment.

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
