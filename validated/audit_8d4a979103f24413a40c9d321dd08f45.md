### Title
GetAttachmentsInvResponse block_id is not validated against the requested index_block_hash before being stored - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`extend_with_inventories` decodes a `GetAttachmentsInvResponse` and stores it in `self.inventories` keyed by `request.key()` (derived from the request that was sent), rather than validating that the `block_id` field in the response actually matches the `index_block_hash` that was requested via `AttachmentsInventoryRequest::make_request_type`. A malicious peer that receives a legitimate `AttachmentsInventoryRequest` for block A can reply with inventory data (bitvector of attachment presence) that is actually for a different, unrelated block B, and the node will index/use that inventory as if it correctly described block A.

### Finding Description
The `AttachmentsInventoryRequest` is built against a specific `index_block_hash` (the tip of `AttachmentsBatch`), and the resulting `StacksHttpRequest` is sent to a peer's data URL. When the response comes back, `extend_with_inventories` calls `response.decode_atlas_attachments_inv_response()` to parse the body into a `GetAttachmentsInvResponse`, which itself carries a `block_id` field asserting which block the inventory bitvector belongs to. The code then does `self.inventories.entry(request.key())...` to store the resulting per-peer inventory, using the *request's* key (which encodes the block/page that was asked for) rather than cross-checking `response.block_id == request.index_block_hash`. Because HTTP correlates request/response per-connection but says nothing about the semantic correctness of the payload, a byzantine peer is free to fill in any `block_id` value in the JSON payload it returns — the parser only checks structural validity (JSON shape, page/bitlen bounds), not that the claimed block matches what was actually asked. This breaks the invariant "inventory response block_id == requested index_block_hash" and lets attacker-controlled inventory content for an unrelated block get filed under the correct block's key.

### Impact Explanation
Attachment inventory data drives which attachments the node considers as needing to be fetched/resolved for a given block (BNS name-registration attachments, etc.). If a peer can inject a bitvector for the wrong block under the key of the block that was actually requested, the downloader can be steered into believing the wrong set of attachments is present/absent for that block, causing it to skip fetching attachments it should fetch, or attempt fetches based on the wrong page state. This matches the "High - attachment/BNS mismatch" category: state (attachment resolution decisions) is derived from inventory data that was never validated as pertaining to the block it's filed under.

### Likelihood Explanation
This requires only an unprivileged peer that: (1) is selected as an outbound sync peer / has a reachable data URL, and (2) receives an `AttachmentsInventoryRequest` from the victim node (which happens routinely as part of normal Atlas attachment sync). No secret, signature, or privileged role is needed — any peer answering the HTTP GET can return a forged `block_id` in its JSON response body. This is repeatable on every attachment inventory poll cycle.

### Recommendation
In `extend_with_inventories`, after `decode_atlas_attachments_inv_response()` succeeds, explicitly verify `response.block_id == request.index_block_hash` (and page number matches the request's requested page) before inserting into `self.inventories`; reject and treat as an unreliable-peer response (penalize via `ReliabilityReport`) if the fields don't match.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AttachmentsInventoryRequest` for `index_block_hash = A` (block A) via `AttachmentsBatch`/`AttachmentsBatchStateMachine`.
2. Have the mock/test HTTP responder return a `GetAttachmentsInvResponse { block_id: B, pages: [...] }` where `B != A`.
3. Call `extend_with_inventories` (or the state machine step that invokes it) with this response.
4. Assert that `self.inventories` now contains an entry keyed by `request.key()` (associated with block A) holding the inventory data that was actually declared for block B — demonstrating the missing `response.block_id == request.index_block_hash` check.
