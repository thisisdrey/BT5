### Title
Inconsistent conversion-factor sources between DelegateResourceActuator/Wallet and UnDelegateResourceProcessor for resource-usage scaling - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
Analogous to the RToken bug (where `transfer` and `transferFrom` derive the "underlying ⇄ scaled" conversion factor from two different sources — a live `getNormalizedIncome()` call versus a stored `_liquidityIndex`), java-tron's resource-delegation logic computes the bandwidth/energy "usage ⇄ frozen-balance" conversion ratio (`TotalNetWeight` / `TotalNetLimit`, `TotalEnergyWeight` / `TotalEnergyCurrentLimit`) from two different accessor sources depending on the code path: the system-contract path (`DelegateResourceActuator`, `Wallet.calcCanDelegatedBandWidthMaxSize/EnergyMaxSize`) reads both numerator and denominator from the same `DynamicPropertiesStore` instance, while the TVM native-contract path (`UnDelegateResourceProcessor`) mixes `dynamicStore.getTotalNetLimit()`/`getTotalEnergyCurrentLimit()` with `repo.getTotalNetWeight()`/`repo.getTotalEnergyWeight()` — a distinct accessor going through the `Repository` layer.

### Finding Description
The delegate-resource conversion formula appears twice with the same intent: convert a TRX balance to the bandwidth/energy "usage" it represents, using the ratio `TotalWeight / TotalLimit` (or its inverse).

In `DelegateResourceActuator.doValidate()`, both the numerator and denominator come from the same `dynamicStore` object: [1](#0-0) 

The same single-source pattern is used in `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`: [2](#0-1) 

However, in `UnDelegateResourceProcessor.execute()` — reachable when a smart contract invokes the `unDelegateResource` native precompile from within a transaction — the same ratio is computed by mixing `dynamicStore.getTotalNetLimit()` with `repo.getTotalNetWeight()` (and analogously `dynamicStore.getTotalEnergyCurrentLimit()` with `repo.getTotalEnergyWeight()`): [3](#0-2) [4](#0-3) 

`repo` here is a `Repository`/`RepositoryImpl` instance, a caching/overlay layer used during TVM execution that is distinct from directly reading `DynamicPropertiesStore`: [5](#0-4) 

This mirrors the RToken root cause exactly: the same conceptual conversion factor (`TotalWeight`/`TotalLimit`) is sourced from two different objects (`DynamicPropertiesStore` directly vs. the `Repository` overlay) within the same undelegate formula, instead of consistently pulling both operands from one source as the sibling `DelegateResourceActuator`/`Wallet` code does.

### Impact Explanation
If `Repository.getTotalNetWeight()`/`getTotalEnergyWeight()` ever returns a value that differs from `DynamicPropertiesStore.getTotalNetWeight()`/`getTotalEnergyWeight()` at the moment `UnDelegateResourceProcessor` runs (e.g., because other resource-affecting operations occurred earlier in the same transaction/VM call chain and were only reflected in the repository overlay, not yet flushed to the store, or vice versa), the computed `unDelegateMaxUsage` would be calculated from a numerator/denominator pair that is inconsistent with the ratio used everywhere else (`DelegateResourceActuator`, `Wallet`). This would cause `transferUsage` for the receiver's bandwidth/energy accounting to be wrong, letting a contract caller under- or over-credit resource usage during undelegation — a concrete accounting/resource-integrity bug reachable by any account that can trigger the `unDelegateResource` native contract via a TVM call.

### Likelihood Explanation
This is reachable by any unprivileged account issuing a `TriggerSmartContract` transaction that invokes the `unDelegateResource` precompile (part of the standard TVM freeze-v2/delegation feature set), so the attack surface is broad and requires no special privilege. However, I could not fully verify within the available index whether `RepositoryImpl.getTotalNetWeight()`/`getTotalEnergyWeight()` actually diverges from the underlying `DynamicPropertiesStore` value in practice (its exact implementation body was not retrieved) — if `RepositoryImpl` simply forwards to `getDynamicPropertiesStore().getTotalNetWeight()` with no independent caching/staleness, the two accessors are always numerically identical and this is a benign code-style inconsistency rather than an exploitable divergence.

### Recommendation
Standardize `UnDelegateResourceProcessor` (and `DelegateResourceProcessor`, if it exhibits the same pattern) to source both the weight and the limit for a given ratio from the same object — either always through `repo.getDynamicPropertiesStore()` or always through the same `Repository` accessor — matching the pattern already used in `DelegateResourceActuator` and `Wallet`. Additionally, verify `RepositoryImpl.getTotalNetWeight()`/`getTotalEnergyWeight()` to confirm whether any transaction-local caching/staleness can cause it to diverge from `DynamicPropertiesStore`'s live value; if so, that divergence must be resolved before it is used together with a value from a different source in the same formula.

### Proof of Concept
Not independently confirmed with a runnable exploit in this analysis — the finding is based on static code review showing the mixed-source formula in `UnDelegateResourceProcessor.java:116-117,140-141` versus the single-source formula in `DelegateResourceActuator.java:162-163` and `Wallet.java:1010-1011`. Concrete exploitation would require verifying that `RepositoryImpl.getTotalNetWeight()`/`getTotalEnergyWeight()` can return a value different from the current `DynamicPropertiesStore` value at the time `UnDelegateResourceProcessor.execute()` runs, which was not fully confirmed with the available tooling.
