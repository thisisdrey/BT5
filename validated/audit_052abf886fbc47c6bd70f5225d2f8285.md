## Analysis: TRC10 Exchange Precision-Loss Analog Found

The reported bug class — burning/consuming a user's full input amount while crediting them a division-truncated (smaller) output amount, silently destroying the fractional difference — has a direct analog in java-tron's `ParticipateAssetIssueActuator`.

### Title
Integer Division Truncation in `ParticipateAssetIssueActuator` Causes Permanent Loss of Purchased Token Value - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
When a user participates in a TRC10 asset issuance (`ParticipateAssetIssueContract`), the actuator deducts the user's full TRX `cost` but computes the token amount received using integer floor-division (`num`/`trxNum` exchange ratio). Any fractional remainder from that division is neither credited to the buyer nor returned to the buyer as TRX — it is silently lost, exactly mirroring the `WithdrawRequest.amount` precision-loss pattern in the reference report (full input consumed, truncated output credited).

### Finding Description
In `execute()`, the actuator subtracts the caller's TRX `cost` in full: [1](#0-0) 

It then computes the amount of TRC10 tokens to credit using integer multiplication followed by `floorDiv`, which truncates any remainder: [2](#0-1) 

The same truncating formula is duplicated in `validate()`: [3](#0-2) 

Because `cost * num` is not generally a multiple of `trxNum`, `floorDiv` drops the remainder permanently: the buyer's full TRX payment is transferred to the asset issuer (`toAccount.setBalance(addExact(toAccount.getBalance(), cost))`), but the buyer receives fewer TRC10 tokens than the exact `cost * num / trxNum` ratio implies, and the corresponding fractional token value is never issued to anyone (it stays locked in the issuer's remaining asset balance, is not returned to the buyer, and is not compensated in TRX). This is functionally identical to the reported `SolverVaultToken` bug: full input burned/consumed, truncated output credited, and the delta silently vanishing from the user's equity.

This behavior is directly reachable by any unprivileged account broadcasting a `ParticipateAssetIssueContract` transaction — no special privilege is required.

### Impact Explanation
Each call can lose up to `trxNum - 1` "sun"-equivalent fractional units of the target TRC10 token to the caller. While a single transaction's loss is bounded and small, this is the same accumulation dynamic the reference report flags as High severity: it can be repeated arbitrarily (each `ParticipateAssetIssueContract` call is a cheap, unprivileged, broadcastable transaction), so an attacker or unaware users interacting frequently with an asset issuance with an unfavorable `trxNum`/`num` ratio (e.g., large `trxNum`, small `num`) systematically lose token value with every purchase, which is a real loss-of-equity/unbacked-accounting condition for the buyer.

### Likelihood Explanation
High. `ParticipateAssetIssueContract` is a standard user-facing, unprivileged transaction type; asset issuers freely set `trxNum`/`num` (bounded only by int32 range and no strict "1:1"-style ratio requirement enforced), so many existing/future TRC10 offerings can have ratios that produce non-trivial truncation on typical purchase amounts.

### Recommendation
- Require the exchange to be evenly divisible (reject the participate call, as is already partly done via the `exchangeAmount <= 0` check) whenever `cost * num % trxNum != 0`, or refund/return the truncated TRX remainder to the buyer.
- Alternatively, use a higher-precision intermediate representation (e.g., track remainders and settle them, or restrict `cost` to multiples of `trxNum`) so that no value is destroyed on either the TRX or token leg of the exchange.

### Proof of Concept
Given an asset issuance with `trxNum = 3`, `num = 1` (i.e., 1 token per 3 sun), a buyer sending `cost = 5` sun:
- `exchangeAmount = floorDiv(5 * 1, 3) = 1` token credited.
- The buyer pays the full 5 sun (which is transferred to the issuer as balance), but only receives value equivalent to 3 sun worth of tokens (1 token) — the value of the remaining 2 sun is lost, never returned nor otherwise credited to the buyer or issuer's token supply. Repeating such calls accumulates loss proportionally to the frequency of participation, mirroring the referenced `requestWithdraw` truncation issue. [4](#0-3)
