Audit Report

## Title
PSM `internal_to_external` decimal-scaling division truncates redemption output to zero for small amounts, unlike a slippage-protected swap - (File: `substrate/frame/psm/src/lib.rs`)

## Summary
The PSM pallet's `internal_to_external` function performs a floor-division by `10^diff` when converting an internal-asset amount into external-asset units on redemption, with no minimum-output check or `min_amount_out` guard. When the internal/external decimal gap is large, any redemption amount smaller than `10^diff` truncates to exactly zero external output, while the internal asset is still burned.

## Finding Description
`internal_to_external` scales down when the external asset has fewer decimals than the internal asset by dividing the input amount by `factor = 10^diff` via `checked_div`, falling back to zero on failure and otherwise returning the floored quotient directly, with no check that the result is non-zero for a non-zero input: [1](#0-0) 

The scaling factor itself is computed by `pow10`, which simply raises 10 to the configured decimal-difference exponent: [2](#0-1) 

The pallet's own unit tests document and accept this truncation behavior for the sibling function `external_to_internal`, confirming floor-division-to-truncation is the intended (but unguarded) behavior of the scaling logic: [3](#0-2) 

No minimum-output enforcement, rounding-up option, or caller-supplied slippage/`min_amount_out` parameter exists in this conversion path, so for any internal/external decimal pair with a large gap (e.g., 18 vs 2, `diff = 16`), redeeming an amount below `10^diff` internal units yields `0` external units while the internal asset is still burned/debited.

## Impact Explanation
This is a genuine value-conservation defect in a settlement/conversion path: burning internal asset without paying out the corresponding external asset breaks the invariant that balances must conserve value and settle exactly once to the rightful beneficiary and amount, as required by the Polkadot SDK Pivots. The destroyed value is not stolen by an attacker but is unrecoverably lost by the user performing a normal redemption, which is a real (if configuration-dependent) fund-loss bug in scoped pallet code.

## Likelihood Explanation
Exploitability requires only a normal user calling the redemption path with a small enough amount against a PSM instance configured with a sufficiently large internal/external decimal gap; no privileged actor, governance action, or malicious peer is needed. Likelihood is Medium since it depends on the specific decimal pairs registered via `add_external_asset` for a given runtime instance — if all configured external assets have decimals close to the internal asset's decimals, the truncation window is narrow, but for any pair with a large gap this is trivially and repeatably triggerable.

## Recommendation
- Add a check after scaling in `internal_to_external` that rejects (returns an error) or rounds in the user's favor when a non-zero input amount scales down to zero output.
- Alternatively, add a caller-supplied minimum-output parameter to the redeem dispatchable so the extrinsic reverts rather than silently paying out less (including zero) than expected.
- Consider disallowing registration of external assets whose decimal gap could produce a zero-output redemption below a configured minimum redemption size, or carry the truncated remainder as a credit rather than discarding it.

## Proof of Concept
1. Register a PSM instance with `internal_decimals = 18` and an external asset with `ext_decimals = 2`, giving `diff = 16` and `factor = 10^16` in `pow10`.
2. Call the redeem path with an internal amount of `9_999_999_999_999_999` (just under `10^16`).
3. `internal_to_external` executes `amount.checked_div(&factor)` at `substrate/frame/psm/src/lib.rs:1616`, yielding `0`.
4. The internal asset burn/debit for the user proceeds while the external payout is `0`, producing an unrecoverable, repeatable loss of the redeemed value for any user under this decimal configuration.

			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
			}
		}
