Audit Report

## Title
`process_delivery_receipt` ignores the `success` field of the Ethereum delivery receipt, paying relayer rewards regardless of actual message execution outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The `DeliveryReceipt` struct decoded from the Ethereum `InboundMessageDispatched` event log carries a `success: bool` field indicating whether the dispatched commands actually executed successfully on the Gateway contract [1](#0-0) . `process_delivery_receipt` decodes this receipt but never inspects `receipt.success` before paying out the relayer reward from the `PendingOrder` and removing the order [2](#0-1) .

## Finding Description
When an outbound message is enqueued, a `PendingOrder { nonce, fee, block_number }` is stored keyed by `nonce` [3](#0-2) . The public extrinsic `submit_delivery_receipt` verifies the event proof via `T::Verifier::verify`, decodes the `DeliveryReceipt` from the log, and forwards it to `process_delivery_receipt` [4](#0-3) . Inside `process_delivery_receipt`, only `receipt.gateway` (must match `T::GatewayAddress`) and the existence of a `PendingOrder` for `receipt.nonce` are checked; the function then unconditionally calls `T::RewardPayment::register_reward` whenever `order.fee > 0`, regardless of `receipt.success`, and removes the order [5](#0-4) . The `success` field is populated from the on-chain `InboundMessageDispatched` event's `success` parameter during decode [6](#0-5)  but is never referenced anywhere else in the pallet — confirmed via search across `bridges/snowbridge/pallets/outbound-queue-v2` showing no other usage of `success`. This breaks the invariant that payout state must only advance after execution and settlement succeed, since a receipt proving a *failed* dispatch (a legitimately, cryptographically verified event log from the real Gateway contract) is treated identically to a successful one.

## Impact Explanation
This allows a legitimate, cryptographically-proven `success: false` receipt to still trigger full reward payment via `T::RewardPayment::register_reward` for `order.fee`, and the `PendingOrder` is deleted so the failed message can never be retried or reconciled. This matches the required "Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" invariant and constitutes underpriced/incorrect payout settlement independent of actual bridge work performed, degrading the intended incentive alignment of the outbound relayer reward mechanism.

## Likelihood Explanation
No privileged or malicious-node/relayer assumption is required beyond normal operation: any relayer submitting a legitimately verified receipt for a message whose Ethereum-side command execution failed (a routine, expected failure mode, not an attack) will still be paid in full. The extrinsic `submit_delivery_receipt` is public and unprivileged, gated only by `ensure_signed`, valid Merkle/beacon proof verification, and gateway/nonce matching — none of which depend on `success`. This is directly and repeatably reachable whenever any dispatched command reverts on Ethereum.

## Recommendation
Add an explicit branch on `receipt.success` in `process_delivery_receipt`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, emit a distinct event (e.g., `MessageDispatchFailed { nonce }`) and define explicit protocol semantics for the failed order (e.g., retry, refund fee payer, or partial/no reward) rather than silently paying the full fee and discarding the order.

## Proof of Concept
1. Queue an outbound message with `fee > 0`, producing `PendingOrders[nonce] = PendingOrder { nonce, fee, block_number }` per `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 426-436.
2. Construct (or have Ethereum emit) an `InboundMessageDispatched` event log with `success = false` for that `nonce` from the real Gateway address, and obtain a valid Merkle/BEEFY proof for it — this is the normal failure path when command execution reverts on Ethereum, not a forged proof.
3. Call `submit_delivery_receipt(origin, event)`; `T::Verifier::verify` succeeds (proof is valid), `DeliveryReceipt::try_from` decodes `success: false`.
4. `process_delivery_receipt` reaches `order.fee > 0` and calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` unconditionally, then removes the `PendingOrder` — the relayer is rewarded despite `receipt.success == false`.
5. Add a unit test in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` asserting `register_reward` is NOT called (or is called with 0/reduced amount) when a `DeliveryReceipt { success: false, .. }` is processed for an existing `PendingOrder` with non-zero `fee`.

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
