### Title
Unvalidated `onBehalfOf_` deposits / dust transfers let an attacker fill a victim's token list and block all borrowing - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol), [File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`DepositToken.deposit(uint256 amount_, address onBehalfOf_)` and `DepositToken.transfer`/`transferFrom` push the token onto the recipient's per-account list via `Pool.addToDepositTokensOfAccount` with no minimum-amount check and no recipient consent. The list is capped at `MAX_TOKENS_PER_USER = 30` entries shared between deposit and debt tokens, and any addition beyond that reverts with `UserReachedMaxTokens`. An unprivileged attacker can dust-fill a victim's list, after which `DebtToken.mint` (which calls `Pool.addToDebtTokensOfAccount`) reverts for any new debt token, DoS-ing the victim's ability to open a borrow position.

### Finding Description
- `DepositToken.deposit` accepts any `onBehalfOf_` address and only requires `amount_ != 0` and `onBehalfOf_ != 0` [1](#0-0) .
- `_mint` and `_transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes from 0 to non-zero — a dust amount (e.g. 1 wei) suffices [2](#0-1) , [3](#0-2) .
- `Pool.addToDepositTokensOfAccount` is protected only by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [4](#0-3) , [5](#0-4) .
- `DebtToken.mint`/`issue` symmetrically call `addToDebtTokensOfAccount`, which reverts under the same modifier [6](#0-5) . There is no opt-in, minimum amount, or cooldown — the same missing-input-validation bug class as `settleFundingFees`.

### Impact Explanation
Temporary freezing of victim funds / protocol functionality. Once a victim's list holds 30 entries, every call that would add a new token to their list reverts: `DebtToken.mint` for any debt token they don't already hold, `deposit`/`transfer` of any deposit token they don't already hold, and liquidation seizures of new collateral types (`seize` → `_transfer` → `addToDepositTokensOfAccount` also reverts for a new token, though seize to a *new* account is what liquidations target). A fresh victim who has never interacted can be permanently blocked from borrowing until they burn gas transferring dust back out — and the attacker can re-fill the list in the same block, front-running the cleanup.

### Likelihood Explanation
High. The attacker needs only dust balances of each registered deposit token's underlying (or can use `deposit(1, victim)` directly since `onBehalfOf_` is unauthenticated). Cost is bounded by ~30 dust deposits. No privileged role, flash loan, or oracle manipulation is required — all calls are public entry points on `DepositToken` reachable directly or via `Operator.execute`. Neither `nonReentrant`, `whenNotPaused`, `SynthContext` sender checks, nor supply caps mitigate it.

### Recommendation
- Revert when `onBehalfOf_` differs from `_msgSender()` unless explicitly allowed, or require a minimum deposit amount.
- Count per-account tokens only above a meaningful balance threshold, or replace the revert in `onlyIfAdditionWillNotReachMaxTokens` with a check that only applies to the account's own actions (debt issuance), not unsolicited incoming transfers.
- Alternatively, make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` no-op (rather than revert) when the list is full and let the account opt in later.

### Proof of Concept
Foundry fork sketch (mainnet pool):

```solidity
// assume pool has N registered deposit tokens; list them via getDepositTokens()
address victim = makeAddr("victim");
address[] memory dts = pool.getDepositTokens();

// Attacker: dust-deposit each deposit token on behalf of victim
for (uint256 i; i < dts.length; ++i) {
    DepositToken dt = DepositToken(dts[i]);
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, 1);
    vm.startPrank(attacker);
    underlying.approve(address(dt), 1);
    dt.deposit(1, victim); // adds dts[i] to victim's list
    vm.stopPrank();
}
// If fewer than 30 deposit tokens exist, attacker additionally
// transfers dust of synthetic/debt-tracking tokens is not needed —
// repeat with multiple collaterals until list length == 30.
assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

// Victim now tries to borrow: mint msUSD via DebtToken
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
debtToken.mint(victim, 1e18); // reverts: addToDebtTokensOfAccount blocked
```

The revert persists until the victim transfers out at least one dust position (or a token is removed by governance), and the attacker can re-fill the freed slot in the same transaction, making the DoS effectively continuous.
