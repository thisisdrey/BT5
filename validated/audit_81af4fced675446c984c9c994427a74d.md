### Title
Uninitialized `treasury` causes `DepositToken.deposit` to revert, blocking all collateral deposits — (File: contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
`Pool.initialize()` never sets `treasury` (nor `feeProvider`/`smartFarmingManager`), yet `DepositToken.deposit` unconditionally pulls collateral to `pool.treasury()`. On a pool where the governor has not yet called `updateTreasury`, `treasury` is `address(0)` and `deposit` reverts — the same bug class as the Astaria report (uninitialized config variable reverts a core user path). For underlying tokens that do not revert on zero-address transfers, the deposited collateral is burned outright.

### Finding Description
`Pool.initialize` only sets `_poolRegistry`, `isSwapActive`, and `maxLiquidable` — `treasury` remains `address(0)` with no check anywhere. [1](#0-0) 

`DepositToken.deposit` resolves `treasury` and transfers the underlying to it: [2](#0-1) 

The `TreasuryCanNotDeposit` guard only compares `msg.sender == treasury`, which passes when `treasury == address(0)` since no real sender is the zero address. `IERC20.safeTransferFrom(sender, address(0), amount)` then reverts in OpenZeppelin-standard tokens (`transfer to the zero address`), so every deposit reverts. The analogous `feeCollector` path is also uninitialized-by-default: `deposit` mints fees to `_pool.feeCollector()` sourced from `PoolRegistry`, and a zero fee collector would revert `_mint` when `depositFee > 0`. [3](#0-2) 

`updateTreasury` exists as a governor setter but is not invoked by any initializer, so nothing forces initialization before users interact. [4](#0-3) 

### Impact Explanation
- All `DepositToken.deposit` calls (and `NativeTokenGateway.deposit`, which routes through it) revert while `treasury == address(0)` → temporary freezing of funds / broken liveness of the core deposit→borrow flow, matching the Astaria impact.
- For an underlying ERC20 that tolerates zero-address transfers, collateral is sent to `address(0)` and lost while `msdTOKEN` is still minted → direct theft/loss of user funds and protocol insolvency (minted shares backed by nothing redeemable).

### Likelihood Explanation
Triggering requires a deployment window where a deposit token is registered before `updateTreasury` is called — a plausible operational ordering since `addDepositToken` does not check `treasury`. Any unprivileged user calling `deposit` hits the revert (or burns funds). No modifier, cap, or SynthContext check prevents it.

### Recommendation
- Reject `address(0)` treasury: revert in `addDepositToken`/`deposit` if `treasury == address(0)`, or require a non-null `treasury_` parameter in `Pool.initialize` (mirroring the Astaria recommendation to initialize the variables up front).
- Similarly guard `feeCollector` in `PoolRegistry` before allowing non-zero fees.

Caveat: I verified `Pool.initialize` and `DepositToken.deposit` directly; I did not exhaustively confirm whether deployed configs already have `treasury` set (deployments indicate pools are configured post-deploy by governance), but the uninitialized-by-default code path and revert are confirmed in the in-scope contracts.

```text
    function updateTreasury(ITreasury newTreasury_) external onlyGovernor {
        if (address(newTreasury_) == address(0)) revert AddressIsNull();
        ITreasury _currentTreasury = treasury;
        if (newTreasury_ == _currentTreasury) revert NewValueIsSameAsCurrent();

        if (address(_currentTreasury) != address(0)) {
            _currentTreasury.migrateTo(address(newTreasury_));
        }

        emit TreasuryUpdated(_currentTreasury, newTreasury_);
        treasury = newTreasury_;
    }
```
