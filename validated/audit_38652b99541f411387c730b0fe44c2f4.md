### Title
`Pool.liquidate` can never succeed for positions whose debt is near/below `debtFloorInUsd` — `maxLiquidable` cap and floor check make the position permanently unliquidatable - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two mutually exclusive bounds: `amountToRepay_` cannot exceed `maxLiquidable` (default 50%) of the account's debt, and the post-liquidation debt must be either `0` or `>= debtFloorInUsd`. For any position whose debt `D` satisfies `D * (1 - maxLiquidable) < debtFloorInUsd` (in particular, any `D < debtFloorInUsd` when `maxLiquidable < 100%`), no value of `amountToRepay_` satisfies both constraints, so every liquidation attempt reverts. An unprivileged attacker can deliberately open such a position; once it turns unhealthy (e.g. via collateral depreciation or interest accrual pushing it over its collateral factor), the protocol can never seize the collateral and is forced to absorb bad debt.

### Finding Description
In `Pool.liquidate` the repayment amount is validated by two independent checks: [1](#0-0) 

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` → `AmountGreaterThanMaxLiquidable`. With the deployed default `maxLiquidable = 0.5e18` (set in `initialize`), a full repayment `amountToRepay_ = D` always reverts.
2. If `debtFloorInUsd > 0`, any repayment leaving `0 < D - amountToRepay_ < debtFloorInUsd` reverts with `RemainingDebtIsLowerThanTheFloor`.

The admissible set is therefore `amountToRepay_ <= D * maxLiquidable` **and** (`D - amountToRepay_ == 0` or `>= debtFloorInUsd`). When `D * (1 - maxLiquidable) < debtFloorInUsd`:

- Any `amountToRepay_ < D` leaves `D - amountToRepay_ < debtFloorInUsd` → reverts.
- `amountToRepay_ = D` exceeds `D * maxLiquidable` → reverts.

`quoteLiquidateMax` also ignores the floor: it caps at `balanceOf(account_) * maxLiquidable`, so even protocol-suggested amounts revert on-chain. Neither `depositToken_.seize` nor any other path can recover the collateral, because the user's `unlockedBalanceOf` is `0` while unhealthy and `withdraw`/`transfer`/`transferFrom` all funnel through `_revertIfLocked` (`DepositToken.sol:180-182, 350, 362, 409, 424`).

### Impact Explanation
Permanent liveness failure of liquidations for a deliberately craftable position class, leading to protocol insolvency: the attacker mints `D` synthetic tokens (extracting real value, e.g. swapping them via `Pool.swap` or selling externally), then the position becomes unliquidatable forever. The locked collateral may be worth less than the outstanding debt — the deficit is bad debt borne by the protocol/synthetic holders, mirroring the "complete DOS" availability impact class of the reference report against the liquidation function itself.

### Likelihood Explanation
- `debtFloorInUsd` is a live governance-set parameter (`updateDebtFloor`, `Pool.sol:768`) whose documented purpose is exactly this liquidation economics; the code path is active in the deployed configuration whenever it is non-zero.
- An unprivileged attacker needs only a normal `DepositToken.deposit` + `DebtToken.issue` to create debt in the dead zone `[debtFloorInUsd * X, debtFloorInUsd / (1 - maxLiquidable))` — or even `D < debtFloorInUsd`, which is unliquidatable under any `maxLiquidable < 1`.
- No privileged role, oracle manipulation, or protocol pause is required; interest accrual via `accrueInterest` alone can push a borderline position over the health threshold, and any collateral price decline does so too.
- Cost to the attacker is bounded (collateral stays locked), and profit is the minted synthetic value minus the collateral loss — positive whenever the position drifts underwater.

### Recommendation
Allow full liquidation when a partial one is impossible. E.g. in `Pool.liquidate`, skip the `maxLiquidable` check when `D * (1 - maxLiquidable) < debtFloorInUsd`, or clamp `amountToRepay_` to `D` in that case, so that a position can always be fully closed. Alternatively enforce `debtFloorInUsd`-aware minimum mint sizes in `DebtToken.issue`/`mint` so that debt below the floor can never be created, and add the floor check to `quoteLiquidateMax` so off-chain liquidators are steered to a valid (full-repay) amount.

### Proof of Concept
Hardhat test (repo framework, smock/fixtures as in `test/Pool.test.ts`):

```ts
it('position with debt below floor is permanently unliquidatable', async function () {
  // Setup: standard fixture, alice deposits MET collateral and mints msETH.
  // governor sets a debt floor; maxLiquidable is 50% (initialize default).
  await pool.updateDebtFloor(parseEther('3000')) // $3,000

  // Attacker opens a position whose debt D satisfies D*(1-0.5) < floor,
  // e.g. D = 1 msETH at $4,000 -> remaining debt after 50% repay = $2,000 < floor
  // (or simply any D < floor).

  // Position becomes unhealthy (lower collateral price or accrued interest):
  await masterOracle.updatePrice(met.address, toUSD('1.5'))

  const debt = await msEthDebtToken.balanceOf(alice.address)

  // 1) Partial repay at the max allowed (50%) -> leaves debt < floor
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address)
  ).to.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

  // 2) Full repay -> exceeds maxLiquidable
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, debt, msdMET.address)
  ).to.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

  // 3) Protocol's own quote also reverts on-chain
  const max = await pool.quoteLiquidateMax(msEth.address, alice.address, msdMET.address)
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, max, msdMET.address)
  ).to.be.reverted // RemainingDebtIsLowerThanTheFloor

  // Position is now frozen: collateral cannot be withdrawn (unhealthy) nor seized.
  expect((await pool.debtPositionOf(alice.address))._isHealthy).to.be.false
  await expect(msdMET.connect(alice).withdraw(1, alice.address))
    .to.revertedWithCustomError(msdMET, 'NotEnoughFreeBalance')
})
```

This matches the existing test scaffolding: the repo's own tests already confirm each revert independently (`test/Pool.test.ts:408-451`) but never test their conjunction, which is the dead zone shown above.
