This is the closest verified analog to the DSWarp report's core bug class ("attacker-controlled time-like value influences a security-critical decision, with no independent authority check"). Nebula's handshake protocol carries an unauthenticated `Time` field (`handshake.Payload.Time`) that the sender fills in and the receiver trusts verbatim as `lastHandshakeTime`, which then gates whether an incoming handshake is allowed to replace an existing tunnel.

### Title
Attacker-controlled handshake `Time` field allows tunnel-replacement / anti-replay bypass in `CheckAndComplete` - (File: `handshake_manager.go`)

### Summary
`handshake.Payload.Time` is a value chosen by the sender of a handshake message and is copied into `HostInfo.lastHandshakeTime` without any independent validation against wall-clock time or monotonicity guarantees tied to the certificate/session. This value is later used as the sole tie-breaker for whether a new handshake is allowed to supersede an existing, established tunnel for the same VPN address.

### Finding Description
In `handshake/machine.go`, `processPayload` reads `payload.Time` directly off the wire and stores it into `m.result.HandshakeTime` with no bound checking beyond nonzero-index validation: [1](#0-0) 

This flows into `HostInfo.lastHandshakeTime`, whose doc comment explicitly says its purpose is anti-replay protection: [2](#0-1) 

The value is set from the handshake result on both the responder path (`beginHandshake`) and the initiator-continuation path (`continueHandshake`): [3](#0-2) [4](#0-3) 

`CheckAndComplete` then uses this attacker-suppliable field as the decisive comparison for whether a new handshake is allowed to take over an existing hostinfo entry: [5](#0-4) 

This mirrors the DSWarp pattern precisely: a value that is supposed to represent "when this happened" and is used for a security decision (which side wins a race / whether a state transition is "stale") is taken from an unauthenticated field controlled by the remote peer, the same peer whose access is being gated by the very decision. Because there is no cross-check against an authenticated wall-clock (there is no equivalent of `time.Now()` bound-checking here), the "time" comparisons are effectively unprotected in the DSWarp sense — the field is attacker's choice, not attacker's cert-bound identity, and it directly drives trust decisions in the hostmap.

### Impact Explanation
An attacker who can present handshake packets that pass Noise/cert validation (any peer holding a valid certificate under the network's CA, or in cross-linked/relay handshake races, an off-path attacker capturing/replaying/racing legitimate stage-1/stage-2 packets) can manipulate `lastHandshakeTime` to always compare as "newer" than a legitimate handshake, forcing repeated or unwanted tunnel replacement (`ErrExistingHostInfo` bypass), or conversely stamp a very high value to make a legitimate future handshake always appear "older" and get rejected (`Handshake too old` log path), effectively denying re-handshakes for a given VPN address. This is a remote state-poisoning / DoS vector on hostmap tunnel selection, analogous to the report's concern about attacker-controlled "time" corrupting a security-relevant computation.

### Likelihood Explanation
Likelihood is difficulty **Low-to-Medium**: the code comment acknowledges this exact threat class ("used to avoid an attack where a handshake packet is replayed after some time") but the mitigation only prevents *exact* packet replay via `HandshakePacket` byte comparison (`ErrAlreadySeen`), not manipulation of the `Time` field's magnitude in a *fresh, otherwise-valid* handshake from a legitimately certificate-holding peer, or during genuine handshake races (`TestStage1Race`, `TestRaceRegression` in the test suite show the race path is a supported/expected condition, not a hardened one against a malicious value).

### Recommendation
Do not trust the peer-supplied `Time` field as an absolute ordering value for tunnel-replacement decisions. Either (a) bind the comparison to a monotonic, locally-observed sequence (e.g., local receipt order or a locally-generated nonce/counter that the responder controls) rather than a value the initiator freely picks, or (b) treat `lastHandshakeTime` purely as a diagnostic/logging field and use `localIndexId`/`remoteIndexId` allocation order plus certificate freshness (`NotBefore`) for tie-breaking, as those are anchored to values the attacker cannot arbitrarily choose without a CA-signed certificate binding them to an identity and lifetime.

### Proof of Concept
1. Attacker holds a certificate signed by the network CA for identity `them` (satisfies "handshake authentication" but is otherwise a low-privilege, adversarial peer wanting to disrupt other tunnels/perform DoS).
2. Attacker completes a normal handshake with `me`, but crafts the handshake payload's `Time` field to be `math.MaxUint64` (or any value far exceeding real time) via the `NebulaHandshakeDetails.Time` protobuf field before it is processed at `handshake/machine.go:313-329`.
3. `me` stores this value into `hostinfo.lastHandshakeTime` and installs it in the hostmap through `CheckAndComplete` (`handshake_manager.go:446-452`).
4. Any subsequent legitimate re-handshake attempt from `them` (e.g., after a real certificate renewal or roam) will have a normal, lower `Time` value and will be rejected via `ErrExistingHostInfo` ("Handshake too old"), permanently pinning `me`'s tunnel to the attacker-poisoned hostinfo until connection-manager-driven teardown occurs — reproducible against the `TestRehandshakingLoser`/`CheckAndComplete` code paths cited above.
