### Title
Dust-transfer griefing fills a victim's deposit-token list up to `MAX_TOKENS_PER_USER`, blocking new collateral deposits and forcing avoidable liquidations - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The CVE-2018-14767 bug class is "missing input validation on a crafted message causes a crash / denial of service." The Metronome analog is the unconditional `pool.addToDepositTokensOfAccount(recipient_)` executed inside `DepositToken._transfer` whenever a recipient goes from zero to non-zero balance. Because the per-account list is capped (`MAX_TOKENS_PER_USER`, enforced in `Pool.addToDepositTokensOfAccount` / `MappedEnumerableSet`), an unprivileged attacker can permanently poison a victim's slot capacity by sending dust amounts of every `DepositToken` in the pool to the victim. Once the list is full, every subsequent first-time receipt of a new collateral type reverts — including the victim's own `deposit()` of a new collateral, which mints via `_mint` → `addToDepositTokensOfAccount`.

### Finding Description
- `DepositToken.transfer`/`transferFrom` only check the sender's unlocked balance (`_revertIfLocked`); there is no opt-in or whitelist on the recipient side. Any holder of a `DepositToken` may push it to any address. [1](#0-0) 
- `_transfer` adds the token to the recipient's tracked list whenever `_recipientBalanceBefore == 0 && amount_ > 0`. [2](#0-1) 
- `_mint` applies the same rule on deposit, so a victim who wants to deposit a *new* collateral type also hits `pool.addToDepositTokensOfAccount`, which reverts once the account's set is at capacity. [3](#0-2) 
- Removal only happens when a balance goes exactly to zero, and only the victim can empty their own slots — the attacker chooses dust amounts and there is no way for the victim to reject or eject entries without transferring the dust out themselves for each token (and `_revertIfLocked` may block even that when the victim has debt). [4](#0-3) 
- There is no validation equivalent to the missing "To"-header check in Kamailio: the recipient list insertion is performed with zero validation of whether the recipient wants/needs the entry, and a revert inside `addToDepositTokensOfAccount` propagates and crashes the whole call — the direct analog of the SIP-parser segfault.

### Impact Explanation
A victim whose `depositTokensOfAccount` set is saturated cannot:
- receive any new `DepositToken` type via `transfer`/`transferFrom`/liquidation `seize` (all hit the same `addToDepositTokensOfAccount` path),
- `deposit()` a new collateral type to improve health (`_mint` reverts).

If the victim has open debt and their existing collateral falls in price, they cannot add a different collateral to restore health; `Pool.liquidate` becomes the only outcome — a liveness break that converts directly into loss of funds through liquidation penalties. Even absent debt, the victim's ability to onboard any additional collateral asset is bricked until they manually spend gas emptying each dust slot — temporary freezing of the deposit functionality (liveness invariant), which persists because the attacker can front-run the cleanup with a fresh dust transfer of another token.

### Likelihood Explanation
Cost scales with the number of distinct `DepositToken`s in a pool: the attacker must hold a non-zero balance of each (one real `deposit` each, since minting requires actual collateral transferred to `Treasury`). For a pool with N collateral types the attacker deposits N dust amounts once, then pushes each to the victim in N cheap transfers. No privileged role, oracle manipulation, or timing window is needed; `transfer` is permissionless, `nonReentrant` does not apply to plain `transfer` (and `transferFrom`'s guard is irrelevant to single calls), and `updateRewardsBeforeTransfer` only iterates the pool's reward distributors. The attack is only worth it against a victim carrying debt near the liquidation threshold, but front-running a victim's `deposit(newCollateral)` transaction with the dust transfer that fills the last slot is a zero-cost denial for that specific rescue attempt, repeatable indefinitely.

### Recommendation
- Allow the recipient to opt out: track the account list only on `deposit()` (mint path), not on `transfer`/`seize` receipts, or
- exempt `addToDepositTokensOfAccount` failures on plain transfers (try/catch or skip list tracking for unsolicited receipts), and/or
- raise/remove `MAX_TOKENS_PER_USER` by iterating lazily, or let `debtPositionOf` iterate only tokens that can actually carry debt-relevant value.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";

/// @notice Fork test against a deployed Pool with >= 2 DepositTokens.
/// Attacker fills victim's depositTokensOfAccount set to MAX_TOKENS_PER_USER,
/// then victim's deposit of a new collateral type reverts.
contract DustListGriefingTest is Test {
    IPool pool = IPool(POOL);
    DepositToken[] collaterals; // all DepositTokens registered in the pool
    DepositToken newToken;      // one the victim has never held
    address victim = address(0xVIC);
    address attacker = address(0xBAD);

    function test_listSaturationBlocksNewDeposit() external {
        // 1. Attacker deposits dust into each collateral type
        for (uint256 i; i < collaterals.length; ++i) {
            DepositToken dt = collaterals[i];
            deal(address(dt.underlying()), attacker, 1);
            vm.startPrank(attacker);
            dt.underlying().approve(address(dt), 1);
            dt.deposit(1, attacker);            // attacker mints dust
            dt.transfer(victim, 1);             // fills victim's list entry
            vm.stopPrank();
        }
        // victim's list is now at MAX_TOKENS_PER_USER

        // 2. Victim tries to deposit a brand-new collateral to save position
        deal(address(newToken.underlying()), victim, 1e18);
        vm.startPrank(victim);
        newToken.underlying().approve(address(newToken), 1e18);
        vm.expectRevert(); // revert inside pool.addToDepositTokensOfAccount
        newToken.deposit(1e18, victim);
        vm.stopPrank();

        // 3. Same revert hits unsolicited transfers of a new token
        deal(address(newToken.underlying()), attacker, 1);
        vm.startPrank(attacker);
        newToken.underlying().approve(address(newToken), 1);
        newToken.deposit(1, attacker);
        vm.expectRevert();
        newToken.transfer(victim, 1);
        vm.stopPrank();
    }
}
```

Note: the exact revert error and the `MAX_TOKENS_PER_USER` constant live in `Pool.addToDepositTokensOfAccount` / `MappedEnumerableSet` (`contracts/Pool.sol`, `contracts/lib/MappedEnumerableSet.sol`); I verified the call sites in `DepositToken` but did not read the cap-enforcement lines themselves within the available iterations, so the PoC's `expectRevert` should be bound to that specific error selector once confirmed.
