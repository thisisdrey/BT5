### Title
Multi-signature threshold bypass via ECDSA signature malleability in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (invoked by any deployed smart contract to verify TRON account permission signatures, e.g. bridge/custody contracts that gate withdrawals on multisig approval) contains flawed de-duplication logic that allows a single private key's signature to be counted multiple times toward the required signing weight, via ECDSA signature malleability, effectively bypassing the intended multi-signer threshold.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute` [1](#0-0) , for every provided signature the code recovers a signer address via `recoverAddrBySign(sign, hash)`, then checks whether that address was already used:

```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```

The `continue` (skip re-counting) only fires when the *exact same signature bytes* for an address have already been seen. If the same address recovers from a *different* signature byte string, the code falls through and adds the weight again, appending a second entry for the same address. Because ECDSA signatures are malleable — for any valid `(r, s)` signature, `(r, n-s)` (where `n` is the curve order) also validates and recovers the same address — an attacker in possession of a single valid signature can trivially derive a second, byte-different signature from the same key, submit both, and have the same key's weight counted twice (or more, up to `MAX_SIZE` = 5 entries) toward `permission.getThreshold()`. No check exists elsewhere in this precompile enforcing "one signature per distinct signer".

This differs from the standard on-chain transaction signature-weight logic in `TransactionCapsule.checkWeight` [2](#0-1) , which de-duplicates strictly by *recovered address* (`addMap.containsKey(base64)` keyed on address, throwing `"has signed twice!"`), correctly preventing weight duplication regardless of malleable signature encoding. The `ValidateMultiSign` precompile diverges from this safe pattern and keys de-duplication on the raw signature bytes instead of the address, reintroducing the malleability weakness.

### Impact Explanation
Any smart contract (bridge custody wallets, multisig vaults, DAO treasuries, exchange hot-wallet contracts) that relies on `ValidateMultiSign` to authorize fund release based on an N-of-M or weighted TRON account permission can be tricked into approving an operation with fewer genuinely-authorizing keys than intended — in the worst case with a single compromised or complicit signer's key duplicated via signature malleability to satisfy the full threshold. This maps directly to the reported incident class (a bridge's hot-wallet processing unauthorized outflows), since contracts of this shape are exactly what this precompile is designed to protect. The result is unauthorized approval of fund transfers, i.e. direct theft of funds guarded by multisig logic.

### Likelihood Explanation
The attacker only needs one valid signature share and standard elliptic-curve arithmetic to derive its malleable counterpart (`s' = n - s`), which is a well-known, cheap, offline operation requiring no additional key material. The precompile is reachable by any contract deployer/caller via `TriggerSmartContract`/`CreateSmartContract`, i.e. by an unprivileged transaction broadcaster, with no special permissions needed to invoke it once a vulnerable contract has been deployed that uses `ValidateMultiSign` for authorization.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute` from the merged `sign` bytes to the `recoveredAddr` alone (mirroring `TransactionCapsule.checkWeight`), rejecting or skipping any second signature that recovers to an already-counted address regardless of its byte encoding, and consider canonicalizing/rejecting non-low-S signatures at `recoverAddrBySign` to close the malleability vector outright.

### Proof of Concept
1. Deploy a contract that calls the `ValidateMultiSign` precompile to authorize a withdrawal, requiring e.g. a threshold weight satisfied by 2 keys of weight 1 each out of a 2-of-2 permission.
2. Attacker controls only 1 of the 2 keys. Attacker signs the `hash` with that key to get signature `(r, s, v)`.
3. Attacker computes the malleable counterpart `(r, n-s, v')` — a distinct but still valid signature recovering to the same address.
4. Attacker submits both signatures as the `signatures` array to the precompile call.
5. Because the two signatures differ in bytes, the `ByteArray.matrixContains(executedSignList, sign)` check fails to treat them as duplicates; both add `weight` for the same address, doubling `totalWeight`, satisfying `permission.getThreshold()` with only one real signer.
6. The dependent contract treats the multisig check as passed and releases funds with only one legitimate signer's authorization. [3](#0-2) [4](#0-3)
