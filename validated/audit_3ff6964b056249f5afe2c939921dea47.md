## Analysis

`LoansNFT.lock()` deliberately broadens ERC-5753 authorization beyond owner/operator to include ordinary per-token `approve`d addresses, specifically to support integrators such as `LoansExchange` locking a listed loan with a narrow approval instead of `setApprovalForAll`: [1](#0-0) 

Once locked, only the stored `unlocker` (`msg.sender == _unlockers[id]`) may call `unlock()`, and `_update` bypasses the standard authorization check whenever the token is locked, requiring `auth == unlocker` for any transfer to succeed: [2](#0-1) 

Critically, the guardian-only rescue path `forceTransfer` explicitly refuses to act on a locked token (`require(_unlockers[tokenId] == address(0), TokenLocked())`), so even a privileged guardian cannot recover a token once it is locked to an uncooperative or malicious unlocker: [3](#0-2) 

Because the `approve()` override itself is blocked once locked (`require(_unlockers[tokenId] == address(0), TokenLocked())`), the true owner cannot even re-approve or revoke access after the token is locked: [4](#0-3) 

## Assessment against scope

The scenario requires an **owner-granted per-token approval** to an unprivileged third party (no admin/guardian/servicer power needed). That approved party — which under normal ERC721 semantics would only be able to *transfer* the token, an action the owner can revoke at any time via `approve(address(0), id)` — can instead call `lock(selfOrAttackerContract, id)` and simply never call `unlock()`. This is a genuine privilege escalation: a capability intended only for "transfer" is silently upgraded to "permanent, owner-unrevocable lock," and the one designed rescue mechanism (`forceTransfer`) is explicitly disabled for locked tokens. The result is a durable, unrecoverable freeze of the true owner's loan NFT and its cashflow rights — harming a different user (the owner) than the attacker, and matching the "Permanent or practically unrecoverable lock of ... loan NFTs caused by an unprivileged path" impact category.

The `ownershipNonce` framing in the question is a red herring: lock/unlock do not change `ownerOf`, so no nonce bump is expected or missing there; the real defect is the lock/authorization/rescue interaction, not nonce bookkeeping.

### Title
Approved (non-owner) address can permanently and irrecoverably lock another user's loan NFT via `lock()`, with no guardian rescue - (File: contracts/LoansNFT.sol)

### Summary
`lock()` accepts any ERC721-`approve`d address (not just owner/operator) as an authorized caller and lets that caller name an arbitrary `unlocker`. Only the `unlocker` can subsequently `unlock()` or transfer the token, `approve()` is blocked while locked, and `forceTransfer` (the only privileged rescue path) explicitly refuses to touch locked tokens.

### Finding Description
An owner who grants a narrow, single-token `approve()` (a normal, expected ERC721 action, e.g. for a marketplace flow) to a counterparty gives that counterparty far more power than plain ERC721 approval implies: the approved address can call `lock(attackerAddr, tokenId)` naming itself or any address it controls as `unlocker`. From that point:
- The owner cannot revoke the approval (`approve()` reverts with `TokenLocked` while locked).
- The owner cannot transfer the token (transfer requires `auth == unlocker`).
- Guardian's `forceTransfer` cannot rescue it (`require(_unlockers[tokenId] == address(0))`).
The token, and the loan cashflow rights it represents, are frozen indefinitely unless the malicious/uncooperative unlocker chooses to act.

### Impact Explanation
This is a durable, unrecoverable lock of a loan NFT and its associated cashflow entitlement, caused entirely through an unprivileged, ordinary NFT interaction (per-token `approve` + `lock`). It matches the in-scope impact "Permanent or practically unrecoverable lock of ... loan NFTs caused by an unprivileged path," and harms a user other than the attacker (the token owner), not just the attacker's own position.

### Likelihood Explanation
Requires the owner to grant a single-token approval to a counterparty who then acts maliciously instead of using the approval for its intended purpose (e.g., listing/transfer). This is a realistic scenario for OTC/escrow-style loan-NFT transfers or third-party marketplace integrations not vetted as trusted as `LoansExchange`.

### Recommendation
Restrict `lock()` authorization back to owner/operator (`setApprovalForAll`) only, or, if per-token-approved lockers must remain supported for integrators, require the `unlocker` to equal `msg.sender` (preventing an approved caller from designating an arbitrary third-party address), and/or allow guardian `forceTransfer` to also clear an existing lock (treat lock as owner-revocable state that guardians can override for recovery, subject to appropriate access control).

### Proof of Concept
1. Owner mints/holds loan NFT `id`, calls `approve(bob, id)` intending Bob to eventually transfer or list it.
2. Bob (unprivileged) calls `lock(bob, id)` — passes `_isAuthorized` check since he's the approved address.
3. Bob never calls `unlock(id)`.
4. Owner attempts `approve(...)`, `transferFrom(...)` — both revert (`TokenLocked`/authorization failure since `auth != unlocker`).
5. Guardian attempts `forceTransfer(owner, rescueAddr, id)` — reverts with `TokenLocked()`.
6. Token and its cashflow rights are permanently stuck; only Bob can ever move it. [5](#0-4) [6](#0-5)

  /**
   * @inheritdoc ILockable
   * @dev Authorization is intentionally broader than the ERC-5753 reference
   *      implementation (owner or operator): per-token approved addresses may also
   *      lock. This lets integrators such as `LoansExchange` lock listed loans with
   *      narrow per-token approvals instead of requiring `setApprovalForAll`.
   */
  function lock(address unlocker, uint256 id) external {
    address tokenOwner = ownerOf(id);

    require(unlocker != address(0), InvalidUnlocker());
    require(_unlockers[id] == address(0), AlreadyLocked());
    require(_isAuthorized(tokenOwner, msg.sender, id), Unauthorized());

    // Clear approval
    _approve(address(0), id, address(0), false);
    _unlockers[id] = unlocker;

    emit Lock(unlocker, id);
  }

  function _update(address to, uint256 tokenId, address auth) internal override returns (address previousOwner) {
    address unlocker = _unlockers[tokenId];
    address from = _ownerOf(tokenId);

    bool isLocked = from != address(0) && unlocker != address(0);
    if (isLocked && auth != unlocker) {
      revert TokenLocked();
    }

    // Bump per-address ownership nonce so external integrators can detect any
    // change to the NFT ownership set of a given address. The zero address is
    // skipped (mint's `from`, burn's `to`) because no consumer reads that slot.
    unchecked {
      if (from != address(0)) ++ownershipNonce[from];
      if (to != address(0)) ++ownershipNonce[to];
    }

    // When the unlocker is transferring a locked token, bypass the standard
    // ERC-721 approval check (pass address(0) as auth) because the unlocker
    // is not set via the normal approve() storage slot.
    previousOwner = super._update(to, tokenId, isLocked ? address(0) : auth);

    if (previousOwner != address(0) && unlocker != address(0)) {
      delete _unlockers[tokenId];
      emit Unlock(tokenId);
    }
  }
