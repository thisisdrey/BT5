### Title
`UpdateReferences` RPC commits raceless ref updates without invoking pre-receive/update/reference-transaction hooks, bypassing GitLab access-control enforcement - (File: internal/gitaly/service/ref/update_references.go)

### Summary
### Finding Description
The external report describes `LensV2Migration.batchMigrateFollows` reaching `FollowNFT.tryMigrate`, a state-mutating path that skips the "is this actor allowed to do this" check (`isBlocked`) that the normal `follow()` path enforces. The analogous pattern in gitaly is an RPC that performs a real, durable state mutation (a reference update) through a code path that structurally omits the hook invocations Gitaly normally uses to let GitLab (Rails) enforce authorization.

`Server.UpdateReferences` builds a plain `updateref.Updater` via `updateref.New(ctx, repo)` and calls `updater.Start()` / `updater.Update()` / `updater.Commit()` directly: [1](#0-0) [2](#0-1) 

This is structurally different from the normal push/update path used by `receive-pack` and by other operations-service RPCs (`UserUpdateSubmodule`, etc.), which go through `UpdaterWithHooks.UpdateReference`. That path explicitly runs `PreReceiveHook`, `UpdateHook`, the `ReferenceTransactionHook`, and `PostReceiveHook` before/around the actual `git-update-ref` commit: [3](#0-2) [4](#0-3) [5](#0-4) 

In GitLab's architecture, `PreReceiveHook`/`UpdateHook` are the mechanism by which Gitaly calls back into GitLab Rails to authorize the specific reference change (protected branch rules, force-push restrictions, blocked/banned user checks, etc. — this is documented as the purpose of the hooks payload's "Information about the user who triggered the hook. This is required for access checks."): [6](#0-5) 

`UpdateReferences`, however, is a plain gRPC `MUTATOR` RPC (`proto/ref.proto`) that any client capable of invoking Gitaly RPCs can call directly with arbitrary reference names/old-new object IDs, and it commits the update with zero hook invocations — no `PreReceiveHook`, no `UpdateHook`, no `ReferenceTransactionHook`. The only checks performed are reference-name format validation and object-ID hex validation: [7](#0-6) 

This mirrors the reported bug class precisely: a reachable, unprivileged-looking mutation path (`tryMigrate`/`UpdateReferences`) that performs the same fundamental effect as the "protected" path (`follow`/`receive-pack`) but omits the authorization gate (`isBlocked`/pre-receive+update hooks) that the protected path relies on.

### Impact Explanation
If any GitLab-facing feature or API surface allows an authenticated-but-unprivileged user to trigger `UpdateReferences` (directly, or indirectly through a Rails feature that forwards a user-controlled reference/target to this RPC instead of the hook-guarded `receive-pack`/operations paths), that user can force-update or delete arbitrary references — including protected branches/tags — without any of the pre-receive/update hook checks GitLab relies on for branch protection, push rule enforcement, or blocked-user checks. This is a Gitaly-level authorization bypass with the same shape as the reported "bypass isBlocked/isAllowed check via an alternate mutation entrypoint" bug class: the mutation is performed, but the gate that the "normal" mutation path enforces is never consulted.

### Likelihood Explanation
Likelihood depends entirely on whether GitLab's Rails layer exposes any user-triggerable code path that calls `UpdateReferences` with a caller-influenced repository/reference/object-ID rather than always going through hook-guarded RPCs (`receive-pack`, `UserUpdateSubmodule`, `OperationsService` RPCs). Gitaly itself performs no additional per-caller authorization for this RPC beyond the standard gRPC/Gitaly transport auth token, so the security boundary is pushed entirely onto callers correctly avoiding this RPC for user-initiated writes. I was not able to find, within the indexed code, any Rails-side caller list showing this RPC is invoked from an unprivileged/user-facing flow; this must be verified against the calling application (GitLab Rails) to determine actual reachability by an unprivileged user, since gitaly itself doesn't record RPC callers.

### Recommendation
- Have `UpdateReferences` (and any other raw `updateref`-based mutator RPC) explicitly document and enforce that it must only be called for repository paths/flows that have already been authorized upstream (e.g., internal/system callers), and/or add a required "hooks-disabled acknowledged" flag plus caller identity metadata so misuse is auditable.
- Where end-user-influenced reference/object data can reach this RPC, route the update through `UpdaterWithHooks.UpdateReference` (or equivalent) so `PreReceiveHook`/`UpdateHook` access checks are always evaluated, rather than through the bare `updateref.Updater`.
- Add integration tests asserting that any RPC accepting user-controlled reference names/targets invokes the pre-receive/update hook chain, to prevent regressions where a "fast path" mutation silently drops the authorization hooks (the same class of oversight as `tryMigrate` omitting the `isBlocked` check that `follow` performs).

### Proof of Concept
Conceptual (cannot be executed here without the running GitLab/Gitaly stack and knowledge of a concrete Rails-facing caller):
1. Identify (or hypothesize) a GitLab Rails/API code path that resolves a repository and reference name from user input and invokes the `UpdateReferences` gRPC RPC directly (rather than through `receive-pack` or the `OperationsService`).
2. As an unprivileged user without push access to a protected branch, submit a request through that path targeting `refs/heads/<protected-branch>` with a new object ID.
3. Observe that `internal/gitaly/service/ref/update_references.go` accepts and commits the update via `updateref.Updater.Commit()` without ever invoking `PreReceiveHook`/`UpdateHook`, i.e., without GitLab's branch-protection authorization being consulted — analogous to the PoC in the report where `batchMigrateFollows` → `tryMigrate` completes a follow relationship without the `isBlocked` check that `follow()` enforces.
