### Title
FindCommits accepts a negative `limit` that disables `git log --max-count`, allowing unbounded history dumps - (File: internal/gitaly/service/commit/find_commits.go)

### Summary
`FindCommitsRequest.Limit` is passed straight into `git log --max-count=%d` without ever being checked for a negative value, unlike sibling RPCs in the same package (`TreeEntry`, `ListLastCommitsForTree`) which explicitly reject negative `Limit`/`Offset`. This mirrors the Teku `BlobSidecarsByRange` class of bug: a numeric range/count parameter supplied by an ordinary caller is forwarded to the backend without bounds validation, letting the caller force an unbounded/expensive operation instead of the limited one the RPC contract implies.

### Finding Description
`validateFindCommitsRequest` only validates the repository and the revision: [1](#0-0) 

There is no check on `req.GetLimit()` (nor `req.GetOffset()`) anywhere in the request validation or in `FindCommits`/`findCommits`: [2](#0-1) 

The unchecked `Limit` value is used to build the `--max-count` flag for `git log`: [3](#0-2) 

`git log --max-count=<N>` treats a negative `N` as "no limit" (git ignores/ ​overrides a negative max-count and walks the full history), so a caller can send `Limit: -1` (or any negative number) to force gitaly to run an unconstrained `git log` over the full history of the referenced revision, streaming every commit back to the client and consuming full git-log CPU/memory/I/O for the whole ancestry graph instead of the small page the RPC is meant to bound.

This is inconsistent with other pagination-bearing RPCs in the very same service package that do validate negative values defensively:
- `TreeEntry` explicitly rejects `Limit < 0` with `"negative Limit"` [4](#0-3) 
- `ListLastCommitsForTree` explicitly rejects negative `Offset`/`Limit` [5](#0-4) 

`FindCommits` has no equivalent guard, and its own test suite exercises `Limit: 0` and `Limit: 9000` but never a negative value [6](#0-5) , indicating the negative-limit path is untested and unguarded.

### Impact Explanation
An ordinary, authenticated RPC caller (any client permitted to call `CommitService/FindCommits`, which requires no special repository privileges beyond read access) can pass a negative `limit` to force `git log` to walk and stream a repository's entire commit history instead of the bounded page the request implies. For large repositories with deep history this multiplies CPU time, memory usage, and network/streaming cost per request, and can be issued repeatedly and cheaply to degrade or exhaust gitaly resources — a reachable, unprivileged DoS vector analogous to the unvalidated `count`/range fields in the Teku `BlobSidecarsByRange` report.

### Likelihood Explanation
High likelihood of reachability: `FindCommits` is a standard read RPC exposed to any client with repository read access (e.g. via GitLab web/API proxy paths), and the `Limit` field is a plain client-controlled `int32` with no validation. No privileged actor, leaked token, or malicious peer is required — any caller who can invoke `FindCommits` can set a negative `Limit`.

### Recommendation
Add explicit validation to `validateFindCommitsRequest` that rejects `req.GetLimit() < 0` (and similarly validate `req.GetOffset() < 0`), consistent with the guards already present in `TreeEntry` and `ListLastCommitsForTree`. This prevents negative values from ever reaching the `--max-count` flag construction in `getLogCommandSubCmd`.

### Proof of Concept
1. Create/identify a repository with a large commit history reachable by gitaly.
2. Send `FindCommitsRequest{ Repository: <repo>, Revision: <ref>, Limit: -1 }` to the `CommitService/FindCommits` RPC as an ordinary client.
3. Observe that `getLogCommandSubCmd` builds `git log --format=%H --max-count=-1 <ref>` [7](#0-6) , which git executes as an unbounded walk of the full ancestry, streaming every commit rather than being capped, unlike the intended pagination-limited behavior.

func (s *server) FindCommits(req *gitalypb.FindCommitsRequest, stream gitalypb.CommitService_FindCommitsServer) error {
	ctx := stream.Context()

	if err := validateFindCommitsRequest(ctx, s.locator, req); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(req.GetRepository())

	// Use Gitaly's default branch lookup function because that is already
	// migrated.
	if revision := req.GetRevision(); len(revision) == 0 && !req.GetAll() {
		defaultBranch, err := repo.GetDefaultBranch(ctx)
		if err != nil {
			return structerr.NewInternal("defaultBranchName: %w", err)
		}
		req.Revision = []byte(defaultBranch)
	}
	// Clients might send empty paths. That is an error
	for _, path := range req.GetPaths() {
		if len(path) == 0 {
			return structerr.NewInvalidArgument("path is empty string")
		}
	}

	if err := s.findCommits(ctx, req, stream); err != nil {
		return structerr.NewInternal("%w", err)
	}

	return nil
}
