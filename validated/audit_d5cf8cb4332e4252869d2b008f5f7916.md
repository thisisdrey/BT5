### Title
`LinkRepositoryToObjectPool` allows linking a repository to an arbitrary caller-chosen "pool" repository, enabling cross-repository object disclosure - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` writes an unauthenticated, caller-supplied `ObjectPool.Repository` path into the target repository's `objects/info/alternates` file, with no verification that the "pool" repository was actually created via `CreateObjectPool` from (or is otherwise related to) the target repository. Any RPC caller (e.g., the GitLab Rails/gitlab-shell client acting on behalf of an ordinary user performing a fork or similar workflow) that can invoke this RPC and knows the storage name and relative path of another repository on the same storage can link their own repository to it as an "object pool," making all of that other repository's Git objects transparently readable through the attacker's own repository (e.g., via `GetBlob`, `GetCommit`, archive, or clone), independent of the original repository's access controls.

### Finding Description
The `LinkRepositoryToObjectPool` handler only validates that `repository` (the target) is a valid, existing repository, then resolves the object pool via `poolForRequest`/`objectpool.FromProto`, and finally calls `pool.Link(ctx, repo)`: [1](#0-0) 

`poolForRequest` merely builds an `ObjectPool` object from the caller-supplied `req.GetObjectPool()` proto and confirms the path is a valid git repository — it does not check that this repository is derived from, forked from, or otherwise entitled to be linked with the target repository: [2](#0-1) 

The underlying `Link` function computes the relative path from the target repository to the "pool" and unconditionally writes it into `objects/info/alternates` (unless an alternates file with different content already exists), with the only defensive check being whether an *existing* alternates entry differs from what git-alternates format expects — there is no check that the "pool" and "repo" are legitimately related (e.g., sharing history, or that the pool was created by `CreateObjectPool` from this exact repo): [3](#0-2) 

`CreateObjectPool` only requires that the "pool" path matches the internal pool-path naming convention (`storage.IsPoolRepository`) — it does not bind the created pool cryptographically or by ACL to the origin repository that seeded it: [4](#0-3) 

Consequently, `LinkRepositoryToObjectPool` will happily link a target repository to *any* existing, valid git repository at a caller-controlled `StorageName`/`RelativePath`, whether or not it is a real "pool" that was ever associated with the target. Once linked, Git's alternates mechanism makes every object (blobs, trees, commits) in the "pool" repository directly readable from the target repository — the same class of bug as the Tempus report, where supplying an arbitrary/fake trusted object (`tempusAMM`) to a function that blindly trusts its self-reported state let an attacker redirect asset flow to themselves. Here, supplying an arbitrary repository as the "pool" redirects **object read access** to the attacker.

### Impact Explanation
This is a cross-repository object access / confidentiality bypass. An attacker who controls a repository that they can request to be linked (directly via the `ObjectPoolService.LinkRepositoryToObjectPool` RPC, or indirectly through any consumer of this RPC, such as Rails' fork-linking flow) can gain read access to the full object database of an unrelated, potentially private repository on the same storage/partition, bypassing GitLab's access-control layer entirely (Gitaly has no concept of repository authorization once it has the storage name + relative path). This matches "cross-repository object access" explicitly called out as an acceptable class of finding.

### Likelihood Explanation
Reachability depends on whether the RPC is exposed to a level of caller that does not already have full, pre-vetted control over both repositories in the request. In stock GitLab, `LinkRepositoryToObjectPool` is invoked internally by Rails as part of fork creation with a pool it itself created and validated at the application layer (Rails maintains the pool ⇄ repository association authoritatively), and Gitaly's own transaction middleware additionally requires the target and "additional" (pool) repository to reside in the same storage/partition (`internal/gitaly/storage/storagemgr/middleware.go`). Whether Rails validates that the caller-supplied pool actually corresponds to a project the user is authorized to associate their fork with is outside the scope of the Gitaly repository and could not be confirmed from this codebase alone. Within Gitaly itself, there is no defense-in-depth check preventing arbitrary pool linkage, so if any calling layer forwards attacker-influenced pool coordinates (e.g., a project ID/path an attacker can somewhat control at fork time), the vulnerability is directly exploitable.

### Recommendation
Add a Gitaly-side invariant that a repository can only be linked to an object pool that was created with that repository (or one of its already-verified relatives) as `origin`, e.g., by persisting/verifying a pool-to-origin binding (similar to the confirmed Tempus fix of adding a whitelist/registry) rather than trusting the RPC caller's `ObjectPool.Repository` value at face value. At minimum, require that the target repository share ancestry/objects with the pool (e.g., verify a known common commit) before writing the alternates link, and audit all callers (Rails, gitlab-shell) to ensure the pool repository path is derived from validated, access-controlled server-side state rather than client input.

### Proof of Concept
1. Attacker-controlled repository `A` exists on storage `default`.
2. Attacker discovers (or is otherwise able to influence) the storage name and relative path of victim repository `V` (private) on the same storage.
3. Attacker (or a compromised/overly-trusting caller of the RPC) issues:
```
LinkRepositoryToObjectPool(
  repository:  { storage_name: "default", relative_path: "A.git" },
  object_pool: { repository: { storage_name: "default", relative_path: "V.git" } }
)
```
4. Gitaly's `pool.Link` writes `../../V.git/objects` into `A.git/objects/info/alternates` without verifying any relationship between `A` and `V`: [5](#0-4) 
5. Attacker now fetches/reads any known or brute-forced object ID from `V` via RPCs on repository `A` (e.g., `GetBlob`, `GetCommit`, `GetArchive`), since Git transparently resolves objects through alternates.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

	if err := transaction.CommitLockedFile(ctx, txManager, alternatesWriter); err != nil {
		return fmt.Errorf("committing alternates: %w", err)
	}

	if tx := storage.ExtractTransaction(ctx); tx != nil {
		alternatesRelativePath, err := filepath.Rel(tx.FS().Root(), altPath)
		if err != nil {
			return fmt.Errorf("rel alternates file: %w", err)
		}

		if err := tx.FS().RecordFile(alternatesRelativePath); err != nil {
			return fmt.Errorf("record alternates file")
		}
	}

	return removeMemberBitmaps(ctx, pool, repo)
}

func (s *server) CreateObjectPool(ctx context.Context, in *gitalypb.CreateObjectPoolRequest) (*gitalypb.CreateObjectPoolResponse, error) {
	if in.GetOrigin() == nil {
		return nil, errMissingOriginRepository
	}

	poolRepo := in.GetObjectPool().GetRepository()
	if poolRepo == nil {
		return nil, errMissingPool
	}

	if !storage.IsPoolRepository(poolRepo) {
		return nil, errInvalidPoolDir
	}

	// repoutil.Create creates the repositories in a temporary directory. This means the repository is not created in the location
	// expected by the transaction manager. This makes sense without transactions, but with transactions, there's no real point in
	// doing so given a failed transaction's state is anyway removed. Creating the repository in a temporary directory is problematic
	// as the reference transaction hook is invoked for the repository from unexpected location, causing the transaction to fail to
	// associate the reference updates with the repository.
	//
	// Run the repository creation without the transaction in the context. The transactions reads the created repository's state from
	// the disk when committing it, so it's not necessary to capture the updates from the reference-transaction hook. This avoids the
	// problem for now, and later with transactions enabled by default we can stop creating repositories in unexpected locations.
	ctxWithoutTransaction := storage.ContextWithTransactionID(ctx, 0)
	if err := repoutil.Create(ctxWithoutTransaction, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, poolRepo, func(poolRepo *gitalypb.Repository) error {
		if _, err := objectpool.Create(
			ctxWithoutTransaction,
			s.logger,
			s.locator,
			s.gitCmdFactory,
			s.catfileCache,
			s.txManager,
			s.housekeepingManager,
			&gitalypb.ObjectPool{
				Repository: poolRepo,
			},
			s.localRepoFactory.Build(in.GetOrigin()),
		); err != nil {
			return err
		}

		return nil
	}, repoutil.WithSkipInit()); err != nil {
		return nil, structerr.New("creating object pool: %w", err)
	}
