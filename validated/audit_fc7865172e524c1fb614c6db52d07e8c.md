## Title
Hardcoded EVM `CHAIN_ID` Shared By All Non-Mainnet/Testnet Networks Enables Cross-Chain Replay of ETH-Implicit Wallet Contract Transactions - (File: `runtime/near-wallet-contract/build.rs`, `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`, `runtime/near-wallet-contract/src/lib.rs`)

### Summary
The ETH-implicit account "Wallet Contract" embeds an EIP-155 `CHAIN_ID` value at compile time to bind a signed Ethereum-style transaction to a specific NEAR network. Only two values are network-specific (`mainnet`=397, `testnet`=398); every other NEAR network — any new chain deployed from this codebase — is built with, and at runtime resolved to, the exact same `wallet_contract_localnet.wasm` binary carrying a single hardcoded `CHAIN_ID=399` [1](#0-0) . This mirrors the reported bug class: a value that should be derived per-network (a real, network-specific chain identifier) is instead a fixed constant baked into shared, non-network-specific code, breaking isolation between distinct deployments.

### Finding Description
The Wallet Contract validates every relayed Ethereum-style transaction against a compile-time constant: [2](#0-1) 
```
pub const CHAIN_ID: u64 = std::include!("CHAIN_ID");
```
and rejects only transactions whose `chain_id` field doesn't equal this constant: [3](#0-2) 

`build.rs` compiles exactly three wasm variants and assigns chain-id constants for `mainnet` (397), `testnet` (398), and a catch-all `localnet` (399) [4](#0-3) . At runtime, `eth_wallet_global_contract_hash`/`wallet_contract_magic_bytes` route every chain whose `chain_id` string is not exactly `mainnet`/`testnet`(/`mocknet`) to this same `localnet` build: [5](#0-4) 

This value is then what `action_implicit_account_creation_transfer` uses to attach the global Wallet Contract to every newly created ETH-implicit account: [6](#0-5) 

Because the ETH-implicit account ID (and therefore its private key ownership) is derived purely from the user's Secp256K1 public key and is independent of any NEAR network [7](#0-6) , the *same* account can be created on any number of independently-operated NEAR networks that are not literally `mainnet`/`testnet` (e.g. two different permissioned/enterprise/custom chains, or `mocknet`/forknet-style deployments). All of these networks deploy the identical Wallet Contract wasm with the identical `CHAIN_ID = 399` baked in. The `EIP-155`-style `chain_id` check inside the contract is therefore never actually chain-specific for any of these networks — it is a single global constant shared by every "other" network, defeating its purpose of preventing cross-chain replay.

### Impact Explanation
An Ethereum-style transaction signed once by a user's Secp256K1 key, authorizing an action (`Transfer`, `FunctionCall`, `AddKey`, etc.) via `rlp_execute` on one non-mainnet/non-testnet NEAR network, remains fully valid and byte-for-byte replayable on any other non-mainnet/non-testnet NEAR network where the user's ETH-implicit account (same address, since it's derived only from the public key) has also been funded — because both networks run the same wasm with `CHAIN_ID=399` and the contract performs no other network-binding check (only sender address, `chain_id`, nonce, target, gas) [8](#0-7) . A malicious or compromised relayer (or anyone who intercepts the base64 RLP transaction, which is not secret once submitted) can resubmit it on a second chain to drain the account there too, or vice-versa. This is a concrete cross-network signature-replay vulnerability leading to theft of funds from ETH-implicit accounts, which matches the accepted "double-spend/replay" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the same user to control ETH-implicit accounts (same keypair) with a nonzero balance on two or more distinct NEAR-based networks that both fall outside the `mainnet`/`testnet` special-cased chain IDs — a realistic scenario for testnets/devnets/enterprise chains, migration/fork scenarios, or any ecosystem running multiple independent chains from this same nearcore codebase (which is explicitly one of its supported deployment patterns, as evidenced by `LOCALNET`/`benchmarknet`/custom `chain_id` handling throughout genesis/config code). No node/validator misbehavior is required — an ordinary relayer or any party who observes the base64-encoded transaction can trigger the replay.

### Recommendation
Do not hardcode a single shared EVM chain id for "every network that isn't mainnet or testnet." Instead, derive the Wallet Contract's chain-id check from a value that is unique per NEAR network — e.g., pass/derive it from the network's own `chain_id` (hash of the NEAR `chain_id` string, or a value supplied at genesis/global-contract-deployment time) rather than compiling one shared constant into a single `localnet` binary reused by all non-mainnet/testnet chains. This mirrors the recommended fix for the analogous `GENESIS_SHNARF` bug: compute the network-binding value from network-specific input rather than hardcoding it.

### Proof of Concept
1. Deploy the standard `wallet_contract_localnet.wasm` (or the current global-contract equivalent selected by `eth_wallet_global_contract_hash` for a non-mainnet/testnet `chain_id`) on two independent NEAR networks, "Chain A" and "Chain B", both with `chain_id` strings other than `mainnet`/`testnet` (e.g. `chain-a`, `chain-b`).
2. Generate a Secp256K1 keypair; derive the ETH-implicit account id `0x...` (same on both chains, since derivation is public-key-only).
3. Fund the ETH-implicit account on both Chain A and Chain B, deploying the Wallet Contract (same wasm, same `CHAIN_ID=399`) to each via the standard implicit-account-creation-transfer path [6](#0-5) .
4. Sign one EIP-2930/legacy Ethereum transaction (e.g. `Transfer` to an attacker-controlled address) with `chain_id = 399`.
5. Submit this exact transaction via `rlp_execute` to the Wallet Contract on Chain A — it succeeds since `tx.chain_id == CHAIN_ID (399)` and nonce/sender/target checks pass [9](#0-8) .
6. Submit the identical transaction bytes via `rlp_execute` to the Wallet Contract on Chain B — it also succeeds for the identical reason, draining the account there as well, even though the user never intended or authorized an action on Chain B.

fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

    let nonce = if tx.nonce <= U64_MAX {
        tx.nonce.low_u64()
    } else {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    };
    if nonce != expected_nonce {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    }

    // Relayers must attach at least as much gas as the user requested.
    let gas_limit = if tx.gas_limit < U64_MAX { tx.gas_limit.as_u64() } else { u64::MAX };
    if env::prepaid_gas().as_gas() < gas_limit.saturating_mul(GAS_MULTIPLIER) {
        return Err(Error::Relayer(RelayerError::InsufficientGas));
    }

    Ok(target_kind)
}

### ETH-implicit account ID

The account ID is derived from a Secp256K1 public key using the following formula: `'0x' + keccak256(public_key)[12:32].hex()`.
