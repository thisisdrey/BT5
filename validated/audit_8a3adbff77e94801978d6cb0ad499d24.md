### Title
Unchecked boolean return of `reduceAssetAmountV2`/`addAssetAmountV2` in `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` — silent asset accounting mismatch on failure - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeTransactionActuator.execute` and `ExchangeWithdrawActuator.execute` call `AccountCapsule.reduceAssetAmountV2(...)` and `AccountCapsule.addAssetAmountV2(...)` to debit/credit a user's TRC10 asset balances during a bazaar/exchange trade, but discard the boolean return value that signals whether the operation actually succeeded. This mirrors the reported "ERC20 with no revert on failure" bug class: a token-balance mutation that can fail (return `false`) is treated as unconditionally successful because its result is never checked.

### Finding Description
`Commons.adjustAssetBalanceV2` and `TransferAssetActuator.execute` both correctly check the boolean result of `reduceAssetAmountV2`/`addAssetAmountV2` and throw a `BalanceInsufficientException`/`ContractExeException` on failure: [1](#0-0) [2](#0-1) 

In contrast, `ExchangeTransactionActuator.execute` calls the same asset-mutation methods but ignores the returned boolean entirely: [3](#0-2) 

And `ExchangeWithdrawActuator.execute` does the same for both the withdrawn token and the paired token: [4](#0-3) 

If `reduceAssetAmountV2`/`addAssetAmountV2` return `false` (e.g., because of an internal overflow guard, asset-store lookup miss, or amount inconsistency not otherwise caught by `validate()`), the actuator still proceeds to `accountStore.put(...)`, `Commons.putExchangeCapsule(...)`, and sets `ret.setStatus(fee, code.SUCESS)` — recording the trade as successful even though the underlying asset ledger update silently failed, exactly analogous to the ERC20 `transfer()` returning `false` without being checked in `FootiumPrizeDistributor`.

### Impact Explanation
If the unchecked mutation fails silently, the exchange pool (`ExchangeCapsule`) balances get updated (via `Commons.putExchangeCapsule`) while the corresponding user account's asset balance does not (or updates only partially/incorrectly), producing an inconsistency between the exchange's internal accounting and real per-account token balances. This is a fund-accounting/integrity issue: assets could be recorded as transferred to/from an account when they were not, resulting in unbacked balances or loss of funds for the counterparties of the exchange pool. This is reachable by any unprivileged account issuing an `ExchangeTransactionContract` or `ExchangeWithdrawContract` transaction (an order-placer on TRON's built-in Bancor-style exchange).

### Likelihood Explanation
The likelihood depends entirely on whether `reduceAssetAmountV2`/`addAssetAmountV2` can actually return `false` in a state reachable after `validate()` passes — I was unable to fully confirm the exact conditions under which these methods return `false` because the `AccountCapsule.java` method bodies were not found within the indexed content available to me (only call sites were located, and a direct `grep_search` for the method implementations in `AccountCapsule.java` returned no matches, likely due to index size limits truncating that file). The two actuators' `validate()` paths perform some manual balance/overflow checks before `execute()`, which may or may not fully cover every internal failure branch of `reduceAssetAmountV2`/`addAssetAmountV2` — this gap is the crux of the risk and needs direct code confirmation.

### Recommendation
In `ExchangeTransactionActuator.execute` and `ExchangeWithdrawActuator.execute`, check the boolean return values of `reduceAssetAmountV2`/`addAssetAmountV2` and throw a `ContractExeException` (mirroring `TransferAssetActuator` and `Commons.adjustAssetBalanceV2`) if either call returns `false`, ensuring the transaction result is not marked `SUCESS` and the exchange capsule is not persisted when the underlying balance mutation failed.

### Proof of Concept
Due to indexing limits I could not retrieve the full body of `AccountCapsule.reduceAssetAmountV2`/`addAssetAmountV2` to construct a concrete failing input; a Devin session with full repository access would be needed to inspect `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` and confirm a reachable `false`-return path (e.g., an overflow check in `addAssetAmountV2` when the destination balance plus amount exceeds `Long.MAX_VALUE`, which `validate()`'s `addExact` check may not perfectly mirror across both branches of `ExchangeTransactionActuator`/`ExchangeWithdrawActuator`).
