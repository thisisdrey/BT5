## Title
Unbounded array allocation in `BatchValidateSign` precompile from attacker-controlled calldata length causes OutOfMemoryError node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` TVM precompiled contract parses its calldata into `DataWord[]` words and derives array lengths directly from attacker-supplied 32-byte words in transaction data. When the `allowTvmSelfdestructRestriction` chain parameter is not active, the length bound check is skipped and `extractBytesArray`/`extractBytes32Array` allocate `byte[len][]` reference arrays sized by that unchecked value before any sanity check occurs, letting a single crafted smart-contract call trigger excessive heap allocation and crash the executing node — the same "attacker-controlled size drives premature bulk allocation before validation" bug class as the reported TIFF decoder OOM.

### Finding Description
`BatchValidateSign.doExecute` only enforces a maximum signature-count bound (`MAX_SIZE = 16`) inside a feature-gated branch: [1](#0-0) 

If `VMConfig.allowTvmSelfdestructRestriction()` is false, the `sigArraySize`/`addrArraySize` bound check is entirely skipped, and execution falls straight to:
```java
byte[][] signatures = ... extractBytesArray(words, words[1].intValueSafe() / WORD_SIZE, data);
byte[][] addresses = extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE);
```
Both helpers read an `int len` directly from a caller-controlled `DataWord` and immediately allocate an array of that length **before any check against `MAX_SIZE`**: [2](#0-1) 

The `cnt > MAX_SIZE` rejection only happens after this allocation has already succeeded or already thrown an `OutOfMemoryError`: [3](#0-2) 

`DataWord.intValueSafe()` returns a value clamped only to the `int` range (up to `Integer.MAX_VALUE`), so an attacker can encode a `len` field of hundreds of millions. `new byte[len][]` for a reference array of that size (4–8 bytes per null reference on a 64-bit JVM) can request gigabytes of heap in a single allocation, well before the loop that would populate it even runs.

### Impact Explanation
An `OutOfMemoryError` thrown mid-allocation inside the TVM interpreter thread is only caught as `Throwable t` in the outer `execute()` wrapper, but by the time the JVM throws `OutOfMemoryError` the heap is typically already exhausted/thrashing; other concurrent threads (block processing, consensus, RPC, DB writes) on the same node process can fail or the JVM can be killed by the OS OOM-killer. This is a remotely triggerable node crash/DoS from a single transaction that calls the `BatchValidateSign` precompile, satisfying the "node crash or halt" impact bar.

### Likelihood Explanation
Likelihood depends entirely on whether `allowTvmSelfdestructRestriction` is active on the target network. On current public mainnet this parameter is expected to be enabled (it long ago passed as a committee-activated hard fork), which would make the length check active and this path unreachable there. However, any network where that specific hard-fork bit has not yet been activated — e.g. non-fully-upgraded private/test chains, newly bootstrapped chains, or networks that intentionally keep older TVM behavior — remains fully exposed, and the vulnerable code path (`extractBytesArray`/`extractBytes32Array` allocating before validating) exists unconditionally in the source regardless of config state. Any account able to broadcast a contract call (no special privilege) can reach it via a single crafted transaction.

### Recommendation
Move the length/bounds validation (`sigArraySize > MAX_SIZE`, `addrArraySize > MAX_SIZE`, and generally `len < 0 || len > MAX_SIZE`) to unconditionally execute inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves (or immediately before calling them) regardless of the `allowTvmSelfdestructRestriction` flag, so that no array allocation sized by untrusted calldata occurs before the length is checked against `MAX_SIZE`.

### Proof of Concept
1. Deploy/call a contract that invokes the `BatchValidateSign` precompile (fixed address) with calldata where:
   - word[0] = arbitrary hash
   - word[1] = offset pointing to a "signatures array" whose length word is set to a very large value (e.g. `0x0FFFFFFF`)
   - word[2] = offset pointing to an "addresses array" similarly configured
2. On a node/chain where `allowTvmSelfdestructRestriction` is not activated, `extractBytesArray`/`extractBytes32Array` will execute `new byte[0x0FFFFFFF][]` before the `cnt > MAX_SIZE` check is ever reached, driving the JVM heap allocation far beyond the configured node heap and crashing the process or making it unresponsive.
3. Repeat via low-cost transactions to reliably deny service to the target node(s).

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
