This confirms the analog: `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` at [1](#0-0)  computes each voter's share of a witness's per-cycle reward pool using floating-point division (`voteRate = (double) userVote / totalVote`) and multiplies by the fixed `totalReward` read from `delegationStore.getReward(cycle, srAddress)`. This pool value is never decremented as individual voters withdraw, so every voter for the same witness/cycle independently computes `voteRate * totalReward` using IEEE-754 doubles, and per-voter rounding can push the computed share up rather than down. Summed across all voters, the total credited (via `adjustAllowance`) can exceed the single fixed `totalReward` that was actually reserved for that witness/cycle — the same class of rounding-driven overestimation described in the report (per-party independent share computation with floating-point/rounding error that in aggregate exceeds the funded pool).

### Title
Reward pool over-distribution via floating-point vote-rate rounding in old-cycle reward computation — ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` splits a fixed, non-decrementing per-witness/per-cycle reward pool (`delegationStore.getReward(cycle, srAddress)`) among all voters for that witness using floating-point arithmetic (`double voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;`). Because each voter's share is computed independently with double-precision rounding rather than via a single integer division of the pool, the sum of all individually credited shares can exceed the actual `totalReward` reserved for that witness/cycle.

### Finding Description
The vote-reward pool for a witness in a given cycle is set once via `MortgageService.payReward` (`delegationStore.addReward(cycle, witnessAddress, value)`) [2](#0-1) . This `totalReward` value is never reduced as individual voters claim their portion — it is only ever read, never decremented, in `computeReward` [1](#0-0) .

Each voter who staked for that witness in that cycle independently calls (through `WithdrawBalanceActuator.execute` → `MortgageService.withdrawReward` → `computeReward(beginCycle, endCycle, accountCapsule)` → `getOldReward` → `computeReward(cycle, votes)`) and computes:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
Because `voteRate` is a double and is then multiplied by `totalReward` and implicitly truncated to `long` on accumulation, the rounding behavior of each voter's individual query is independent of every other voter's. Unlike a single atomic decrement-from-pool model (where the pool is reduced by the exact amount paid out, guaranteeing the sum of payouts never exceeds the pool), here `sum_over_voters(voteRate_i * totalReward)` is not constrained to equal `totalReward`; due to floating point rounding it can be strictly greater than `totalReward` for certain vote-count distributions (e.g., many voters with vote counts that produce repeating/irrational binary fractions when divided by `totalVote`). This is architecturally the same bug class as the reported issue: multiple independent claimants each compute their proportional share of a shared pool via floating point/rounding math instead of via a decrement from the pool, so the aggregate claimed can exceed what was actually funded.

The reward computed here flows directly into `MortgageService.adjustAllowance` which increases `AccountCapsule.allowance` [3](#0-2) , and this allowance is later converted 1:1 into spendable TRX balance by `WithdrawBalanceActuator.execute` [4](#0-3)  or by the TVM-reachable `WithdrawRewardProcessor.execute` native contract [5](#0-4) , which is reachable by any account issuing a `WithdrawBalanceContract` transaction or calling the corresponding TVM native/precompiled withdraw-reward path — i.e. by an unprivileged transaction broadcaster.

### Impact Explanation
If the aggregate reward claimed across all voters of a witness for a given old-algorithm cycle exceeds the `totalReward` that was actually funded for that witness/cycle (via `payReward`/`addReward`), the protocol effectively mints/credits TRX allowance beyond what was reserved for distribution. This constitutes unbacked balance creation: `WithdrawBalanceActuator`/`WithdrawRewardProcessor` will convert this over-credited allowance into real, transferable account balance, which can then be moved/spent — an economic overstatement of protocol-controlled value, matching the "protocol insolvency"/overestimated-fee-value impact class in the report.

### Likelihood Explanation
This code path is only used for cycles prior to `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()` (`beginCycle < newAlgorithmCycle`) and only when `allowOldRewardOpt()` is not enabled — the newer path uses exact `BigInteger`-based Vi-index accounting (`computeReward(long, long, AccountCapsule)` at lines 199-230) which avoids floating point. On networks/cycles still running the legacy per-cycle `computeReward(cycle, votes)` double-based algorithm, any voter can trigger the computation simply by voting and calling `WithdrawBalanceContract`/`withdrawReward`; no special privileges are required. The magnitude of overestimation per withdrawal is small (sub-unit rounding), so exploitation requires many voters/cycles to accumulate a material discrepancy, and it is not reachable at all on networks where the legacy algorithm window has passed or `allowOldRewardOpt` is enabled.

### Recommendation
Replace the floating-point `voteRate * totalReward` computation in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` with exact integer arithmetic (e.g., `BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote))`), consistent with the precise `BigInteger`-based approach already used in the newer Vi-index algorithm at [6](#0-5) . Alternatively, decrement `delegationStore`'s stored `totalReward` by the exact amount paid out to each voter so that the sum of payouts is structurally capped by the funded pool.

### Proof of Concept
Because this is a legacy-algorithm, cycle-based accumulation bug, a concrete PoC requires simulating multiple voters sharing one witness reward pool across an old-algorithm cycle and comparing the sum of computed rewards to the stored pool value:
1. Set `dynamicPropertiesStore.saveNewRewardAlgorithmEffectiveCycle()` to a value greater than the test cycle, and disable `allowOldRewardOpt` so `computeReward(cycle, votes)` (double-based) is used.
2. Fund a witness's cycle reward: `delegationStore.setWitnessVote(cycle, sr, totalVote)`; `delegationStore.addReward(cycle, sr, totalReward)` with `totalVote` and `totalReward` values chosen such that `userVote/totalVote` does not have an exact binary fraction representation (e.g., `totalVote = 3`, `totalReward` a large value, with many distinct voters each holding `userVote = 1`).
3. Create `N` voter accounts each with `vote.getVoteCount() = 1` for `sr`, and call `mortgageService.withdrawReward(voterAddress)` for each.
4. Sum the resulting `AccountCapsule.getAllowance()` across all `N` voters and compare to `totalReward`; demonstrate the sum can exceed `totalReward` due to independent double-rounding of `voteRate * totalReward` per voter (analogous to the referenced `ComputeRewardTest`/`DelegationServiceTest` test harnesses at [7](#0-6)  which already exercise this exact `computeReward` path).

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
