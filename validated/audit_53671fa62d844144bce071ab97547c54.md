### Title
CREATE/CREATE2 silently converts a colliding EOA into a contract, preserving attacker-influenced control at the collided address - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
Both `Router.sol`'s callback check and java-tron's `Program.createContractImpl` rely on a 160-bit (20-byte) truncated hash to uniquely identify an address, without an authoritative check that the collision cannot occur or is handled safely. In java-tron, when `CREATE`/`CREATE2` computes a new contract address that happens to already be occupied by an existing externally-owned account (EOA), the code takes that pre-existing account and silently promotes it to `AccountType.Contract`, preserving its balance, instead of treating the situation as a fatal collision.

### Finding Description
`createContractImpl` fetches any existing account at the computed address and, in the post-Constantinople path, only compares against `isContractExist` (i.e., whether the account already has *code*) to decide whether a "true" collision exists: [1](#0-0) 

If the account exists but has no code yet (a plain EOA that has simply received TRX, or been created by any prior transfer), `contractAlreadyExists` evaluates to `false`, and the code takes the `else if (!contractAlreadyExists)` branch: it mutates the *existing* `AccountCapsule` in place — flipping its type to `Contract` and clearing its delegated resources — while keeping its balance. The deployer-controlled bytecode is then written and executed at that same address: [2](#0-1) 

The address itself is computed with a truncated 256-bit hash exactly like the Kyber Router.sol pool address (`sha3omit12`/`generateContractAddress2`), giving the same ~160-bit collision-resistance ceiling the Kyber report describes: [3](#0-2) 

The legacy (pre-Constantinople) branch is worse: it unconditionally calls `deposit.createAccount(...)` and only afterwards preserves any balance already sitting at the address — with a comment acknowledging the exact risk ("In case of hashing collisions, check for any balance before createAccount()") but still proceeding to overwrite the account's type without any circuit breaker: [4](#0-3) 

This is the same root-cause class as the Kyber bug: the system treats "the hash matches this 20-byte value" as sufficient proof of identity/ownership, without verifying through an authoritative registry (e.g., "does this account have a private key controlled by someone else, or was it credited by an unrelated transfer") that reusing the address is safe. If an attacker can find (or has already funded/received TRX at) an EOA whose address collides with a future CREATE2 target — analogous to brute-forcing the ~2^80 search space described in the Kyber report — the existing account is absorbed into the attacker's deployed contract, and any balance or resource state that had accumulated at that address (from unrelated third parties transferring to what they believed was a plain EOA) becomes subject to the newly-installed contract's logic.

### Impact Explanation
Successful exploitation would let a broadcaster of a `CREATE2` (or `CREATE`) contract-creation transaction take over an account that other, unrelated users had already funded or interacted with, converting it into an attacker-controlled contract while retaining its balance and clearing its delegated-resource records. This satisfies "unauthorized account operation" and "theft of funds" categories, since the account's economic state and administrative type are altered without consent of whoever controls (or should control) that address.

### Likelihood Explanation
Likelihood mirrors the Kyber judgment: finding a genuine EOA/CREATE2-target collision within the 160-bit truncated hash space requires substantial but not infeasible compute (the same ~2^80–2^82 hash-generation math cited in the external report applies identically here, since java-tron's contract-address derivation truncates a Keccak/SHA3 hash to 20 bytes exactly like Ethereum). Sherlock's own judgment on the referenced issue treated this class as a valid Medium given the immutability of the vulnerable logic and decreasing cost of compute/storage over time; the same reasoning applies to this core protocol code, which likewise cannot be trivially "patched around" once deployed since it is consensus-critical VM behavior, not an upgradeable dapp.

### Recommendation
Do not silently absorb a pre-existing, non-contract account into a `CREATE`/`CREATE2` target. Treat any address collision — whether or not the existing account currently has code — as a hard failure of contract creation (push zero / revert), rather than converting the account type in place. At minimum, require verification that the target address has zero balance and zero nonce/history before permitting reuse, consistent with the intent already partially expressed by the "check for any balance" comment in the legacy branch.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC would require: (1) brute-forcing an EOA address that collides with a `WalletUtil.generateContractAddress`/`generateContractAddress2` output for a chosen deployer+salt+bytecode combination (search space ~2^80, per the cited external report's methodology), (2) getting any balance credited to that EOA via an ordinary TRX/TRC10 transfer, and (3) broadcasting the `CREATE2` transaction that targets the same address, then observing via `AccountCapsule`/`ContractStore` state that the account's type flips to `Contract` while its balance is preserved, per the code paths cited above. This is analogous to the coded PoC referenced in the original Kyber report demonstrating that 20-byte hash collisions are practically achievable at moderate scale.

  public static byte[] generateContractAddress2(byte[] address, byte[] salt, byte[] code) {
    byte[] mergedData = ByteUtil.merge(address, salt, Hash.sha3(code));
    return Hash.sha3omit12(mergedData);
