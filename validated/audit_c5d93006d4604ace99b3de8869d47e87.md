### Title
Stale PromiseYield receipt survives account deletion/recreation and executes attacker-chosen actions against a later account incarnation - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (invoked by `Action::DeleteAccount`) only clears `Account`, `ContractCode`, access/gas keys, and `ContractData`; it never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`, or `YieldId`↔`data_id` mappings for the deleted account. Since these keys are addressed purely by `account_id` (with no incarnation/generation tag), a `PromiseYield` receipt created before deletion remains parked in the trie and is later delivered (via timeout or explicit resume) against whatever account currently occupies that `account_id`, executing the originally-embedded actions/signer_id verbatim.

### Finding Description
`is_instant_receipt` (`core/primitives/src/receipt.rs:474`) marks `PromiseYield` receipts as instant, single-account receipts. On creation, `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200`) stores the full receipt (including `actions` and `signer_id`) under `TrieKey::PromiseYieldReceipt { receiver_id, data_id }`, and `create_promise_yield_receipt`/`create_promise_yield_receipt_with_id` in `runtime/runtime/src/ext.rs:353-400` set `TrieKey::PromiseYieldStatus` and enqueue a `TrieKey::PromiseYieldTimeout` entry (`function_call.rs:161-169`), all keyed only by `account_id`/`data_id`.

`Action::DeleteAccount` calls `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`), which calls `remove_account` (`core/store/src/utils/mod.rs:505-575`). That function removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` only [1](#0-0) . It never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, or `PromiseYieldTimeout` entries [2](#0-1) , and `MAX_ACCOUNT_DELETION_STORAGE_USAGE` gating (`actions.rs:348-353`) is based on `account.storage_usage()`, which doesn't count these system trie keys, so deletion is not blocked by a pending yield.

Later, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) walks the `PromiseYieldTimeout` queue purely by `expires_at`, and for each entry checks only `state_update.contains_key(&promise_yield_key)` — i.e., whether the `PromiseYieldReceipt` trie entry still exists — with no check that the account itself still exists or is the "same" account that created the yield [3](#0-2) . If it exists, a `PromiseResume` receipt is synthesized and forwarded to the same account id [4](#0-3) .

When the resume arrives, `process_receipt` (`runtime/runtime/src/lib.rs:1500-1562`) fetches the parked yield receipt via `get_promise_yield_receipt` and, if found, executes it verbatim via `apply_action_receipt` [5](#0-4) , using the `actions`, `signer_id`, and `signer_public_key` that were captured at yield-creation time (`function_call.rs:172-180`). No re-validation occurs against the current account's existence, identity, or incarnation — only against `account_id` as a string. Consequently:

1. Account `A` (incarnation 1) calls `promise_yield_create`, embedding an action batch (e.g. `FunctionCall`, `Transfer`, `AddKey`) to run on itself later.
2. `A` is deleted (`DeleteAccount`); `remove_account` clears the account/keys/code/data but leaves the `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries in the trie.
3. `A` is recreated (incarnation 2) — possibly by a different logical owner (e.g. a parent account recreating a sub-account, or anyone re-registering a previously-deleted top-level name via the registrar) with a new contract/keys.
4. `A` is deleted and recreated again (incarnation 3), repeating step 2-3.
5. The original timeout (or an explicit resume, since `data_id` is derivable from the original receipt id/action hash and not secret to whoever created it) fires; `resolve_promise_yield_timeouts`/`process_receipt` find the still-present `PromiseYieldReceipt` entry and execute incarnation-1's actions against incarnation-3's account state, storage, and balance.

This breaks the implicit assumption that a `PromiseYield` receipt is "confined to a single account" in the sense of a single *live* account instance — confinement is only by name, not by identity/incarnation, and the receipt's content (actions/signer_id) is trusted without re-validating that the account is still the one that created it.

### Impact Explanation
This is an authorization-escalation bug: actions chosen and queued by one owner/contract of an account name execute later against a completely different owner/contract that now controls the same account name, without any consent from the new owner. Depending on the embedded actions (e.g. `Transfer`, `FunctionCall` draining balance/state, `AddKey`), this can move or drain funds or otherwise mutate state of the new incarnation using stale authorization from a prior, unrelated incarnation — matching the "authorization escalation across accounts or promises" bounty category. It compounds across multiple delete/recreate cycles as the question specifies, since nothing in the code path is sensitive to how many times the name has cycled.

### Likelihood Explanation
Preconditions are fully within reach of an unprivileged account: any ordinary account can deploy a contract that calls `promise_yield_create`, then issue a `DeleteAccount` action on itself (subject to the existing `MAX_ACCOUNT_DELETION_STORAGE_USAGE` and gas-key-balance checks, which are unrelated to the yield state and don't block deletion). Recreation of the same account name is possible for sub-accounts (by the parent) or for top-level names once vacated (subject to registrar rules) — an attacker who controls both the original deletion and a later recreation (e.g. an account they resurrect themselves, or a griefing scenario against a sub-account namespace they will reuse) can reliably reproduce this. The default yield timeout (`yield_timeout_length_in_blocks`) bounds how long the attacker must wait, and no validator/node privilege or race condition is required — everything is driven by ordinary signed transactions.

### Recommendation
Have `remove_account` (or `action_delete_account`) also iterate and remove any outstanding `PromiseYieldReceipt`, `PromiseYieldStatus`, and pending `PromiseYieldTimeout`/yield-id-mapping entries scoped to the account being deleted before the account is torn down, and/or bind these entries to an account "incarnation" identifier that changes on every `CreateAccount`, so `resolve_promise_yield_timeouts`/`process_receipt` refuse to resume against a mismatched incarnation.

### Proof of Concept
Integration test (test-loop, modeled on `test-loop-tests/src/tests/yield_timeouts.rs` and `test-loop-tests/src/tests/yield_resume.rs`):
1. Deploy the yield-test contract on account `A`; call `call_yield_create_return_promise` to create a `PromiseYield` receipt with a distinguishable payload/action (e.g. one that writes a marker value into contract storage on resume).
2. Before the timeout fires, submit `DeleteAccount` from `A` to a beneficiary.
3. Recreate `A` (incarnation 2) with a fresh contract/keys via `CreateAccount`+`DeployContract`.
4. Delete `A` again, then recreate it a third time (incarnation 3) with different contract state/keys.
5. Advance blocks until `yield_timeout_length_in_blocks` elapses; assert that the runtime still produces the `PromiseResume` receipt (`find_promise_resume_receipt_ids_from_latest_block`-style helper) and that it executes against incarnation 3, asserting the marker/action from incarnation 1 lands in incarnation 3's state/storage (e.g. via `store.get_ser` on the recreated account's contract data or balance delta), even though incarnation 3 never called `promise_yield_create` or `promise_yield_resume` and has no relation to incarnation 1's signer/contract.
