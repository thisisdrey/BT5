### Title
Unbounded array allocation from attacker-controlled length field in `BatchValidateSign`/`ValidateMultiSign` precompiles enables per-call resource-consumption DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`extractBytes32Array` and `extractBytesArray`/`extractSigArray` in `PrecompiledContracts.java` allocate `byte[len][]` arrays where `len` is read directly from attacker-supplied call data via `words[offset].intValueSafe()`, before that length is checked against any bound or against the actual amount of data available.

### Finding Description
`extractBytes32Array` reads a length word and immediately allocates an array of that size with no upper bound check at all: [1](#0-0) 

`extractBytesArray` checks only that `offset` is in range, but not that `len` (also attacker-controlled) is bounded before allocating `new byte[len][]`: [2](#0-1) 

These helpers are invoked from `BatchValidateSign.doExecute` (precompile address `0x9`) and `ValidateMultiSign.execute` (address `0xa`): [3](#0-2) [4](#0-3) 

The bound check (`sigArraySize > MAX_SIZE`) is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and is derived from a *different* word than the one actually consumed to size the allocation in the unrestricted branch (`extractBytesArray`), which performs no size check at all: [5](#0-4) 

Energy charged for the call is computed purely from the physical `data.length` of the call data, not from the decoded `len` value embedded inside it: [6](#0-5) 

This is analogous to CVE-2017-11140's root cause: a resource (pixel cache in GraphicsMagick; here a large Java object array) is allocated based on an untrusted size field before that field is validated against the actually-available/legitimate data, letting a small, cheaply-priced input trigger a disproportionately large allocation attempt.

### Impact Explanation
A caller can craft calldata to `BatchValidateSign`/`ValidateMultiSign` whose actual byte length is small (and thus cheap in energy) but which embeds a huge 256-bit "array length" value (up to `Integer.MAX_VALUE` via `intValueSafe()`) at the offset consumed by `extractBytesArray`/`extractBytes32Array`. This triggers an attempted allocation of an array with billions of references (`new byte[len][]`), which can throw `OutOfMemoryError`/`NegativeArraySizeException` or cause severe GC pressure on the JVM shared by the whole node process. Because the outer `execute()` wraps this in `catch (Throwable t)`, the error does not crash the node outright, but the attempted allocation and associated GC churn is a resource-consumption vector — matching the "node crash/halt" and "resource consumption" impact classes of the referenced CVE, reachable from a single, ordinary signed transaction that deploys a contract calling this precompile (no special privilege required).

### Likelihood Explanation
High reachability: `BatchValidateSign`/`ValidateMultiSign` are reachable by any account via a normal contract `CALL`/`STATICCALL` to precompiled address `0x9`/`0xa` once `VMConfig.allowTvmSolidity059()` is active, which is a long-since-activated mainnet feature. Crafting the calldata requires only basic ABI knowledge (control over one length word independent of the actual byte-length paid for in energy). No special account privileges are required.

### Recommendation
In `extractBytes32Array` and `extractBytesArray`/`extractSigArray`, validate `len` against both an application-level cap (`MAX_SIZE`) and the amount of data actually present in `words`/`data` (e.g., ensure `offset + len` doesn't exceed `words.length`) before allocating any array, independent of the `allowTvmSelfdestructRestriction` feature flag. Apply the same bound uniformly to both the restricted and unrestricted code paths so array allocation size can never exceed the bound implied by the actual submitted calldata length.

### Proof of Concept
Construct calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the `bytes[]` offset word (`words[1]`) points to a slot whose value is set to `0x7fffffff` instead of a small real array length, while keeping the total calldata length minimal (few words) so `getEnergyForData` charges very little energy. When `VMConfig.allowTvmSelfdestructRestriction()` is not yet active for the transaction's execution context, `extractBytesArray`/`extractBytes32Array` will attempt `new byte[2147483647][]`, causing an immediate `OutOfMemoryError`/large allocation spike per invocation, for the cost of a handful of `1500`-energy units.   private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
