### Title
Attachment fetch reliability score is bumped on successful HTTP decode without verifying the returned bytes hash to the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
In `AttachmentsBatchStateContext::extend_with_attachments`, a peer's `ReliabilityReport` is bumped as successful the moment `response.decode_atlas_get_attachment()` succeeds, with no comparison of the decoded attachment's hash against the `AttachmentRequest::content_hash` that was actually requested. An attacker-controlled peer can therefore return any well-formed-but-wrong attachment body and still be credited with a successful request, inflating its reliability score used by `get_most_reliable_source`/`make_request_type` to prioritize future attachment fetches.

### Finding Description
The claimed fault ("reliability bumped == request succeeded is asserted before bytes-vs-hash equality is checked") is confirmed in the code: [1](#0-0) 

```rust
pub fn extend_with_attachments(...) -> AttachmentsBatchStateContext {
    for (request, response) in results.succeeded.drain() {
        let report = self.peers.get_mut(request.get_url())...;
        let response = if let Some(r) = response { r } else { report.bump_failed_requests(); continue; };
        if let Ok(response) = response.decode_atlas_get_attachment() {
            self.attachments.insert(response.attachment);
            report.bump_successful_requests();          // <-- bumped here, no hash check
        } else {
            report.bump_failed_requests();
        }
    }
    ...
}
```

`request` here is the `AttachmentRequest` carrying `content_hash` (the hash the fetch was actually for), but `request.content_hash` is never compared to `response.attachment.hash()` at this point. The hash of the decoded attachment is only ever used later, in the `Done` branch of `run()`, purely as a lookup key into pending instances: [2](#0-1) 

```rust
AttachmentsBatchStateMachine::Done(ref mut context) => {
    for attachment in context.attachments.drain() {
        let attachments_instances = network.atlasdb
            .find_all_attachment_instances(&attachment.hash())?;
        network.atlasdb.insert_instantiated_attachment(&attachment)?;
        for attachment_instance in attachments_instances.into_iter() {
            resolved_attachments.push((attachment_instance, attachment.clone()));
        }
        context.attachments_batch.resolve_attachment(&attachment.hash())
    }
    ...
    for (peer_url, report) in context.peers.drain() {
        self.reliability_reports.insert(peer_url, report);   // score already inflated
    }
```

If the attacker returns garbage bytes that merely decode successfully (`decode_atlas_get_attachment` only parses/validates the HTTP payload shape, not the requested hash), `attachment.hash()` will not match any pending `AttachmentInstance`, so `find_all_attachment_instances` returns empty and the batch's original `content_hash` entry is never resolved — the legitimate content is never obtained from this exchange. But by this point `report.bump_successful_requests()` has already executed unconditionally back in `extend_with_attachments`, and that inflated `ReliabilityReport` is persisted into `self.reliability_reports` for the attacker's URL.

`ReliabilityReport::score()` and the `Ord`/`PartialOrd` impls used by `AttachmentRequest::get_most_reliable_source` (download.rs:1073-1079) and by `AttachmentsInventoryRequest`'s ordering select peers purely by this score: [3](#0-2) 

Repeating this (send bogus 200 responses with decodable-but-wrong-hash bodies), the attacker climbs the ranking used by `get_most_reliable_source`/`make_request_type` (download.rs:1104-1119), making it preferentially chosen as the URL for subsequent genuine attachment fetches, ahead of honest peers who might legitimately fail occasionally.

### Impact Explanation
No content-hash forgery/collision is required or claimed — the achievable impact is degradation of the peer-selection/reliability mechanism: an attacker can cause a node to prefer the attacker's URL for BNS/Atlas attachment retrieval over honest peers, since success accounting does not require serving the actually-requested content. This matches the "attachment/BNS mismatch" bounded-impact category (High): genuine attachment resolution for a `content_hash` is repeatedly starved/delayed (the batch is bumped and retried via `bump_retry_count`, eventually dropped if `max_attachment_retry_count` is exceeded — download.rs:187-205), while the attacker's reliability metric is inflated at no real cost. This is a read-endpoint/availability degradation on Atlas attachment sync, not a memory-safety or consensus-state-corruption bug.

### Likelihood Explanation
Any remote peer that is included in `network.get_outbound_sync_peers()` and offers a data URL can be selected for attachment requests. It only needs to respond to `/v2/attachments/<hash>` with an HTTP 200 whose body successfully decodes as an `Attachment` payload (no content match needed) to get `bump_successful_requests()` called every single time — a very low-cost, remotely repeatable action, no privileged role, no secret required.

### Recommendation
In `extend_with_attachments`, verify the decoded attachment's hash equals `request.content_hash` before crediting the peer with a success; only call `report.bump_successful_requests()` when `response.attachment.hash() == request.content_hash`, and call `report.bump_failed_requests()` (or a distinct "served wrong content" penalty) otherwise.

### Proof of Concept
A Rust unit test in `stackslib/src/net/atlas/tests.rs` (parallel to existing `test_downloader_context_attachment_requests`):
1. Build an `AttachmentsBatchStateContext` with one `AttachmentRequest` for `content_hash = H(attachment_A)`.
2. Construct a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains that request mapped to `Some(response)` where the response's `Attachment` payload decodes fine but is `attachment_B` (`attachment_B.hash() != content_hash`).
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert that the peer's `ReliabilityReport.total_requests_success` was incremented (`bump_successful_requests` fired) even though `attachment_B.hash() != content_hash`, demonstrating the missing equality check before the reliability bump.
