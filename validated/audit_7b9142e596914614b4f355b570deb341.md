Audit Report

## Title
`pallet-revive` derives contract address and storage `trie_id` from a reapable account nonce, enabling address/trie-id reuse after account dusting - (File: `substrate/frame/revive/src/exec.rs`, `substrate/frame/revive/src/storage.rs`)

## Summary
`pallet-revive`'s CREATE1 address and the contract's storage `trie_id` are both derived from `System::account_nonce(&sender)` rather than from a dedicated monotonic counter. [1](#0-0)  Because `frame_system::Account` (including `nonce`) is deleted once `providers == 0 && consumers == 0 && sufficients == 0`, and restored at `0` upon refunding, a deployer that drains and later refunds its own account can reproduce an identical CREATE1 address and identical `trie_id` for a new contract as one it deployed and terminated earlier at the same nonce value. [2](#0-1) [3](#0-2) 

## Finding Description
`new_frame`'s `FrameArgs::Instantiate` branch computes the CREATE1 address via `address::create1(&deployer, account_nonce)` and immediately calls `ContractInfo::new(&address, System::account_nonce(&sender), code_hash)`, which hashes `("bcontract_trie_v1", address, nonce)` to build `trie_id`. [1](#0-0) [4](#0-3) 

`ContractInfo::new` guards only against two conditions: (1) the target address currently being an occupied contract (`is_contract` check), and (2) unflushed `NativeDepositOf` rows for the address's fallback account. [5](#0-4)  Neither check inspects whether the computed `trie_id` value itself has been used by a previously terminated contract; the code only prevents redeploying to an address that is *currently* a live contract, and separately blocks reuse while a specific deposit-cleanup queue (`NativeDepositOf`) is non-empty. This is a narrower and different guard than a check on `trie_id` uniqueness across the contract's full lifetime.

Meanwhile, `frame_system::dec_providers`/`dec_sufficients` fully remove `Account<T>` (including `nonce`) once all reference counters hit zero, and tests explicitly confirm the nonce resets to `0` after this reaping (`dust_account_removal_should_work`, `provider_ref_handover_to_self_sufficient_ref_works`). [6](#0-5) [7](#0-6) [3](#0-2) 

By contrast, `pallet-contracts` explicitly avoids using the account nonce for this purpose, maintaining a dedicated, never-decremented `Nonce<T>` storage item whose doc comment states exactly this risk: creating, terminating, and immediately recreating a contract with the same account could collide in storage because trie deletion is lazy, and hence a value that can repeat (like an account nonce after reset) must not be used. [8](#0-7)  A regression test (`instantiate_unique_trie_id`) specifically enforces that trie ids never repeat after termination in `pallet-contracts`. [9](#0-8)  `pallet-revive` has no equivalent dedicated counter — it derives `trie_id` from the general-purpose, reapable `System::account_nonce`.

I was unable to fully verify within available tool iterations whether `pallet-revive`'s termination path (`terminate` in `exec.rs`) removes the `AccountInfoOf` entry for the address such that the address becomes available for reuse, and whether the `NativeDepositOf` guard added in `storage.rs` (lines 205-212) was specifically introduced to close all or part of this exact gap (it addresses "unflushed `NativeDepositOf` rows," which appears related to native-token deposit accounting rather than general child-trie/contract-storage residue). This distinction matters for the precise scope of what stale state could survive: the existing guard may already block a meaningful subset of the described attack (deposit-related state), while leaving other child-trie contract storage unprotected by any address/trie_id-reuse check tied to `trie_id` values themselves, only to the address's "is a contract" status and its deposit-queue status.

## Impact Explanation
If confirmed exploitable end-to-end (i.e., if child-trie storage cleanup on termination is genuinely lazy/deferred and the address-becomes-available-again + nonce-resets-to-zero + NativeDepositOf-guard-passes conditions can all be satisfied by an ordinary user), this would violate the storage-isolation invariant between successive contract instantiations at the same trie_id, potentially exposing stale key/value state from a destroyed contract to a newly instantiated one. This falls under "runtime bugs that compromise intended behavior" in the Polkadot SDK impact gate, as it involves corruption of contract storage state (the exact wrong value being a reused `trie_id`) reachable purely through unprivileged, ordinary extrinsics (balance transfers to drain/refund an account, followed by `instantiate`/`instantiate_with_code`).

## Likelihood Explanation
The prerequisite chain — draining a deployer account below existential deposit to trigger full reaping (providers/consumers/sufficients all zero), refunding it, and calling `instantiate` without a salt — uses only standard, permissionless extrinsics available to any account holder. The `NativeDepositOf` check added at `storage.rs:210-212` is an existing guard whose precise scope of protection (whether it fully closes this gap for all contract storage residue, or only for native-deposit-specific state) I could not fully determine from the code read within available iterations; this affects the actual current exploitability and residual risk, which should be verified further (e.g., by tracing the `terminate` function and `DeletionQueue`/`on_idle` drain logic in `exec.rs` and `lib.rs`) before treating this as a confirmed, currently-exploitable bug versus a partially-mitigated one.

## Recommendation
Do not derive `trie_id` from `System::account_nonce`. Introduce a dedicated, monotonic, never-decremented counter analogous to `pallet-contracts::Nonce<T>` for use specifically in `trie_id` computation, retaining `account_nonce` only for CREATE1 address derivation where Ethereum-compatible semantics require it. Additionally, audit whether the existing `NativeDepositOf`-based guard in `ContractInfo::new` fully covers all forms of stale-storage inheritance, or only deposit-accounting-specific state, and extend the check to cover trie-id uniqueness directly if it does not.

## Proof of Concept
1. Deploy a contract from account `A` at `account_nonce(A) == 0` without a salt; record address `X` and the resulting `trie_id`. [1](#0-0) 
2. Terminate the contract at `X` (verify what `terminate` does to `AccountInfoOf::<T>` and `NativeDepositOf` — not fully confirmed in this review).
3. Drain account `A`'s balance/providers/consumers/sufficients to zero so `frame_system::Account::<T>` is removed. [6](#0-5) 
4. Refund `A`; confirm `account_nonce(A)` is `0` again, per the pattern shown in `dust_account_removal_should_work`. [3](#0-2) 
5. Call `instantiate` again from `A` without a salt and verify whether the resulting `trie_id` matches the one from step 1, and whether any residual storage from the terminated contract is observable — this final verification step (whether stale storage is actually observable, given the `NativeDepositOf` guard and actual termination/deletion-queue behavior) was not completed in this review and should be the focus of a dedicated integration test in `substrate/frame/revive/src/tests/`.

#[test]
fn provider_ref_handover_to_self_sufficient_ref_works() {
	new_test_ext().execute_with(|| {
		assert_eq!(System::inc_providers(&0), IncRefStatus::Created);
		System::inc_account_nonce(&0);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// a second reference coming and going doesn't change anything.
		assert_eq!(System::inc_sufficients(&0), IncRefStatus::Existed);
		assert_eq!(System::dec_sufficients(&0), DecRefStatus::Exists);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// a provider reference coming and going doesn't change anything.
		assert_eq!(System::inc_providers(&0), IncRefStatus::Existed);
		assert_eq!(System::dec_providers(&0).unwrap(), DecRefStatus::Exists);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// decreasing the providers with a self-sufficient present should not delete the account
		assert_eq!(System::inc_sufficients(&0), IncRefStatus::Existed);
		assert_eq!(System::dec_providers(&0).unwrap(), DecRefStatus::Exists);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// decreasing the sufficients should delete the account
		assert_eq!(System::dec_sufficients(&0), DecRefStatus::Reaped);
		assert_eq!(System::account_nonce(&0), 0u64.into());
	});
}

	/// This is a **monotonic** counter incremented on contract instantiation.
	///
	/// This is used in order to generate unique trie ids for contracts.
	/// The trie id of a new contract is calculated from hash(account_id, nonce).
	/// The nonce is required because otherwise the following sequence would lead to
	/// a possible collision of storage:
	///
	/// 1. Create a new contract.
	/// 2. Terminate the contract.
	/// 3. Immediately recreate the contract with the same account_id.
	///
	/// This is bad because the contents of a trie are deleted lazily and there might be
	/// storage of the old instantiation still in it when the new contract is created. Please
	/// note that we can't replace the counter by the block number because the sequence above
	/// can happen in the same block. We also can't keep the account counter in memory only
	/// because storage is the only way to communicate across different extrinsics in the
	/// same block.
	///
	/// # Note
	///
	/// Do not use it to determine the number of contracts. It won't be decremented if
	/// a contract is destroyed.
	#[pallet::storage]
	pub(crate) type Nonce<T: Config> = StorageValue<_, u64, ValueQuery>;

fn instantiate_unique_trie_id() {
	let (wasm, code_hash) = compile_module::<Test>("self_destruct").unwrap();

	ExtBuilder::default().existential_deposit(500).build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 1_000_000);
		Contracts::upload_code(RuntimeOrigin::signed(ALICE), wasm, None, Determinism::Enforced)
			.unwrap();

		// Instantiate the contract and store its trie id for later comparison.
		let addr =
			builder::bare_instantiate(Code::Existing(code_hash)).build_and_unwrap_account_id();
		let trie_id = get_contract(&addr).trie_id;

		// Try to instantiate it again without termination should yield an error.
		assert_err_ignore_postinfo!(
			builder::instantiate(code_hash).build(),
			<Error<Test>>::DuplicateContract,
		);

		// Terminate the contract.
		assert_ok!(builder::call(addr.clone()).build());

		// Re-Instantiate after termination.
		assert_ok!(builder::instantiate(code_hash).build());

		// Trie ids shouldn't match or we might have a collision
		assert_ne!(trie_id, get_contract(&addr).trie_id);
	});
