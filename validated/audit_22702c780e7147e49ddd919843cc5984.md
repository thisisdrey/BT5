### Title
Attacker can permanently DoS a victim's ability to deposit collateral, receive deposit tokens, or issue new debt by dust-filling the per-account token list to `MAX_TOKENS_PER_USER` - (File: contracts/Pool.sol)

### Summary
`Pool` tracks the deposit tokens and debt tokens an account interacts with in `MappedEnumerableSet.AddressSet` lists (`depositTokensOfAccount`, `debtTokensOfAccount`) and enforces a hard cap of `MAX_TOKENS_PER_USER = 30` combined entries via `onlyIfAdditionWillNotReachMaxTokens` ( [1](#0-0) , [2](#0-1) ). Any holder of a `DepositToken` can push a victim's list to the cap with dust `transfer`s; `DebtToken` is non-transferable so debt-side entries can't be forced, but deposit-side alone is sufficient. Once the combined list hits 30, every action that would add a *new* token to the victim's lists reverts with `UserReachedMaxTokens`. This is the on-chain analog of the CVE-2024-57649 class: a crafted, unprivileged input sequence causes a persistent denial of service against a chosen target.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 → non-zero ( [3](#0-2) ).
- `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < 30` and reverts otherwise ( [4](#0-3) , [1](#0-0) ).
- `DebtToken._mint` symmetrically adds to `debtTokensOfAccount` on first borrow ( [5](#0-4) ), and `DepositToken._mint` does the same for deposits ( [6](#0-5) ).

Attack steps (all unprivileged):
1. Attacker deposits dust amounts of each listed collateral into each `DepositToken` (up to the number of registered deposit tokens; pools commonly have ~10+ collaterals, and the cap counts debt tokens too, so an attacker can also self-issue dust debt on their own account is irrelevant — only deposit tokens are needed if the pool lists ≥30 deposit tokens; otherwise the attacker fills the remainder by dust-depositing onBehalf via `deposit(amount_, onBehalfOf_ = victim)` which also mints to the victim, see [7](#0-6) ).
2. For each `DepositToken`, attacker calls `transfer(victim, 1 wei)` — or, more cheaply, calls `deposit(dust, victim)` directly, since `deposit` mints to `onBehalfOf_` with no victim consent.
3. The victim's combined list reaches 30.

After that, for the victim:
- `DepositToken.deposit(..., onBehalfOf_=victim)` for any collateral the victim doesn't already hold reverts (in `_mint` → `addToDepositTokensOfAccount`).
- `transfer`/`transferFrom`/`seize` of any deposit token the victim doesn't already hold reverts.
- `DebtToken.issue`/`mint` for any synthetic the victim doesn't already owe reverts in `_mint` → `addToDebtTokensOfAccount` ( [8](#0-7) , [9](#0-8) ).
- `SmartFarmingManager.leverage` for the victim reverts at the mint/deposit steps (both `_mint` paths run under `onlyIfAdditionWillNotReachMaxTokens`).

Cleanup requires the victim to transfer the dust entries away one-by-one (`_transfer` removes entries on zero balance, [10](#0-9) ), but `transfer` is gated by `_revertIfLocked`/`unlockedBalanceOf`, which queries `pool.debtPositionOf` ( [11](#0-10) , [12](#0-11) ). A dust amount is usually within `unlockedBalanceOf`, so self-recovery is possible — but the attacker can re-fill freed slots in the same block (or by sandwiching the victim's deposit tx), making the DoS persistent for as long as the attacker wishes.

### Impact Explanation
Liveness/funds-availability impact: the victim is denied service for (a) depositing any new collateral type, (b) receiving any new `DepositToken` (including via third-party `deposit(onBehalfOf)` and liquidation proceeds directed at them), and (c) opening debt in any new synthetic. If the victim has an open unhealthy position whose rescue requires topping up a *new* collateral type or issuing a different synthetic, the griefing can delay remediation and indirectly cause a liquidation that would otherwise have been avoidable — a temporary freezing/DoS of funds flows rather than a one-tx gas exhaustion. No privileged role, oracle manipulation, or malicious endpoint is required; only public `deposit`/`transfer` calls and dust collateral.

### Likelihood Explanation
- Cost per occupied slot is a dust deposit/transfer of an already-whitelisted collateral; no supply cap or fee prevents it.
- A pool with N deposit tokens allows N attacker-forced entries (debt tokens can't be pushed since `DebtToken` reverts on transfer — [13](#0-12) ); if a pool has fewer than 30 deposit tokens total, the attack only fully saturates when victim's own existing entries + deposit-token count ≥ 30, which lowers applicability on small pools but is realistic on the multi-collateral Metronome deployments.
- No modifier stops it: `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists` all pass; the cap check is exactly what the attacker exploits.

### Recommendation
- Count slots per-account only for tokens with economically meaningful balances (e.g. require a minimum first-mint amount above a USD floor in `addToDepositTokensOfAccount`, similar to `debtFloorInUsd`), or
- Move the max-tokens check out of the add path so transfers/deposits never revert on the recipient's list size — instead cap only positions that contribute to `debtPositionOf` iteration cost, or raise/decouple the cap per list rather than the combined count, or
- Let any account evict zero-value dust entries permissionlessly (e.g. a `sweepDust(account, token)` helper callable when balance < floor) so grief entries are trivially and atomically removable within the victim's transaction.

### Proof of Concept
Hardhat (fork or fixture-based) sketch:

```ts
// Setup: pool with >= 2 deposit tokens (msdA, msdB) and a debt token (dSYN).
// victim has a normal position; attacker is a fresh EOA.

it('griefs victim token list to MAX_TOKENS_PER_USER', async () => {
  const depositTokens = await pool.getDepositTokens(); // all registered
  const victimCount =
    (await pool.getDepositTokensOfAccount(victim.address)).length +
    (await pool.getDebtTokensOfAccount(victim.address)).length;

  // Attacker pushes victim's deposit list until combined length == 30.
  for (let i = 0; victimCount + i < 30 && i < depositTokens.length; i++) {
    const dt = await ethers.getContractAt('DepositToken', depositTokens[i]);
    const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
    await underlying.connect(attacker).approve(dt.address, 1);
    await dt.connect(attacker).deposit(1, victim.address); // mints dust to victim
  }

  // Victim cannot deposit a collateral type not already in its list
  const dtNew = await ethers.getContractAt('DepositToken', depositTokens[0]);
  const uNew = await ethers.getContractAt('IERC20', await dtNew.underlying());
  await uNew.connect(victim).approve(dtNew.address, parseEther('1'));
  await expect(
    dtNew.connect(victim).deposit(parseEther('1'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // Victim cannot receive a new deposit token type
  await expect(
    msdOther.connect(attacker).transfer(victim.address, 1)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // Victim cannot issue a new synthetic debt type
  await expect(
    debtToken.connect(victim_issue_call) // issue(amount, to) on a synthetic victim doesn't owe
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Reproduction notes: on a mainnet fork use the deployed `Pool`, enumerate `pool.getDepositTokens()`, acquire dust of each underlying, and loop `deposit(1, victim)` (or `transfer(victim, 1)` after self-depositing) until `getDepositTokensOfAccount(victim).length + getDebtTokensOfAccount(victim).length == 30`; then show `deposit`/`transfer`/`issue` of new token types revert while pre-existing positions still function — matching the persistent, input-crafted DoS pattern of CVE-2024-57649.
