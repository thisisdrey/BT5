### Title
Floating-point precision flaw in the legacy Bancor-style AMM calculation allows arbitrage draining of `Exchange`/`ExchangeV2` pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The `ExchangeTransactionActuator`, reachable by any account via a signed `ExchangeTransactionContract`, resolves swap amounts through `ExchangeCapsule.transaction()`, which by default uses `ExchangeProcessor` — a `double`/`Math.pow`-based reimplementation of the Bancor relay-token formula. [1](#0-0)  Because the formula is computed with IEEE-754 doubles instead of exact arithmetic, repeated small swaps can be crafted so that rounding/precision error systematically favors the caller, similar in spirit to the Polkatrain incident where an unbounded, imprecisely-tracked rebate let an attacker repeatedly call `swap` to extract more value than was deposited.

### Finding Description
`ExchangeProcessor.exchangeToSupply()` and `exchangeFromSupply()` perform the core AMM math with `double` and `Maths.pow(...)`, converting the result back to `long` via a narrowing cast (`(long) issuedSupply`, `(long) exchangeBalance`). [2](#0-1)  This is the path used whenever `hardenedCalc` (the `allowHardenExchangeCalculation` committee parameter) is not enabled — `ExchangeCapsule.transaction()` explicitly falls back to `new ExchangeProcessor(supply, useStrictMath)` in that case. [3](#0-2)  A hardened, `BigDecimal`-based `SafeExchangeProcessor` exists as an alternative, and `ExchangeTransactionActuator` passes `allowHarden()` (which just reads the dynamic property) to select between them, meaning the vulnerable path is still compiled in and only avoided if/when that specific proposal parameter is active on the network. [4](#0-3) [5](#0-4) 

`ExchangeTransactionActuator.execute()` then unconditionally applies whatever `anotherTokenQuant` the processor returns to both the pool balances (`exchangeCapsule`) and the caller's real TRX/TRC10 balance, with no invariant check (e.g. constant-product/relay-supply consistency) verifying that the pool's economic value is preserved. [6](#0-5)  The only guard in `doValidate()` is `anotherTokenQuant < tokenExpected` — a slippage floor supplied by the caller, not a soundness check on the AMM math itself. [7](#0-6)  Because a caller fully controls `tokenQuant` and can issue many sequential small `ExchangeTransactionContract` transactions, any systematic favorable rounding bias in the double-precision formula (which is inherent to floating point `pow`/division at small supply deltas) can be repeatedly harvested, draining real, backed TRX/TRC10 liquidity from the pool in exchange for negligible-cost fractional swaps — structurally the same "no cap / no consumption bound, repeatedly callable exchange primitive" pattern SlowMist identified in Polkatrain's `_update`/`swap` rebate.

### Impact Explanation
Successful exploitation lets an attacker extract real backed asset value (TRX or TRC10 tokens) from `Exchange`/`ExchangeV2` liquidity pools beyond what they deposit, at the expense of other liquidity providers — a direct theft-of-funds / unbacked-balance condition reachable from ordinary signed transactions, without any special privilege.

### Likelihood Explanation
Exploitability depends on the network having `allowHardenExchangeCalculation` (and the newer `SafeExchangeProcessor` hardened path) inactive; on chains/environments where that proposal has not been activated, the double-precision `ExchangeProcessor` remains live for every `ExchangeTransactionContract`, and pool balances/token IDs (needed to target skewed ratios) are all public on-chain data, so an attacker can script repeated swaps cheaply.

### Recommendation
Ensure `allowHardenExchangeCalculation` (routing all exchanges through `SafeExchangeProcessor`) is permanently enabled network-wide and remove or hard-disable the floating point `ExchangeProcessor` fallback so it can never again become reachable; additionally add an explicit pool-invariant check (e.g. verifying the relay-supply/product before and after a swap is non-decreasing beyond fee tolerance) in `ExchangeTransactionActuator.execute()` as defense in depth.

### Proof of Concept
1. Attacker identifies (or creates) an `Exchange` pool where `firstTokenBalance`/`secondTokenBalance` produce a swap size for which `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`'s double-precision `pow` rounding yields an output truncated in the attacker's favor (verifiable offline by simulating `ExchangeProcessor.exchange()` with candidate `sellTokenQuant` values).
2. Attacker repeatedly submits `ExchangeTransactionContract` transactions with that `tokenQuant`/`tokenId`/`exchangeId`, each processed by `ExchangeTransactionActuator.execute()` calling `exchangeCapsule.transaction(...)`. [8](#0-7) 
3. Each iteration nets the attacker a small excess of the counter-asset relative to true fair value; repeated at scale this drains the pool's real backing while the attacker's added asset is comparatively worthless, mirroring the Polkatrain uncapped-rebate arbitrage drain.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
