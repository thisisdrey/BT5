### Title
NULL pointer dereference in `UnDelegateResourceActuator.execute` on unlocked `DelegatedResourceCapsule` - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.execute` fetches the "unlock" `DelegatedResourceCapsule` for a given owner/receiver pair and immediately calls a mutator method on it (`addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`) without checking whether the lookup returned `null`. `validate()` does not guarantee this specific object is non-null — it only guarantees that *at least one* of the "unlock" or "lock" resource records exists. A transaction can pass `validate()` while only the "lock" resource exists, causing `execute()` to dereference a null `unlockResource`, analogous to CVE-2021-20196 where an ioport handler dereferenced an uninitialized (unchecked) block-device object.

### Finding Description
In `validate()`:
```java
// actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java:256-263
DelegatedResourceCapsule unlockResourceCapsule = delegatedResourceStore.get(key);
byte[] lockKey = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, true);
DelegatedResourceCapsule lockResourceCapsule = delegatedResourceStore.get(lockKey);
if (unlockResourceCapsule == null && lockResourceCapsule == null) {
  throw new ContractValidateException("delegated Resource does not exist");
}
```
This check only rejects the transaction when *both* records are absent. If only the "lock" resource exists (a common state produced by TIP delegation with lock time, e.g. `DelegateResourceContract` with `lock=true`), `unlockResourceCapsule` is `null` but validation still succeeds.

In `execute()` the same lookup is repeated, and the result is used unconditionally:
```java
// actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java:128-137
byte[] unlockKey = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, false);
DelegatedResourceCapsule unlockResource = delegatedResourceStore.get(unlockKey);
...
AccountCapsule ownerCapsule = accountStore.get(ownerAddress);
switch (unDelegateResourceContract.getResource()) {
  case BANDWIDTH: {
    unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);   // NPE if unlockResource == null
```
The same pattern repeats for the `ENERGY` branch (`unlockResource.addFrozenBalanceForEnergy(...)`). None of this code inside `execute()` is wrapped in a try/catch — only the earlier `any.unpack(...)` call is guarded (`actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java:51-57`). A `NullPointerException` here is an unchecked `RuntimeException` that will propagate straight out of `Actuator.execute()`.

### Impact Explanation
Any unprivileged account holder can trigger this: delegate resources with `lock=true` (creating only a "lock" `DelegatedResourceCapsule`, no "unlock" record), then broadcast an `UnDelegateResourceContract` for that same owner/receiver/resource pair before the lock naturally expires (or exploit boundary conditions where only the lock record persists). `validate()` passes because the lock record exists, but `execute()` unconditionally dereferences the null unlock record and throws an uncaught `NullPointerException`. Since actuator execution for on-chain transactions occurs during block application (`Manager.processTransaction` → actuator execute path), an unhandled runtime exception at this stage is a denial-of-service vector affecting transaction/block processing on any node applying that transaction — potentially blocking further chain progress on that node until manual intervention, which is the same "privileged internal operation on unchecked object → crash" bug class as CVE-2021-20196's floppy NULL pointer dereference (unchecked block device before an ioport read/write).

### Likelihood Explanation
Medium-High. The precondition (only a "lock" delegated resource existing without a matching "unlock" record) is a normal, reachable on-chain state reachable via a single standard `DelegateResourceContract` with `lock=true`, and requires no special privileges — any transaction broadcaster can set this state up and then send the crashing `UnDelegateResourceContract`. The bug is purely in first-party actuator logic, not a mocked/test-only path, and it sits directly in the mainline actuator execute flow used for every incoming resource-undelegation transaction.

### Recommendation
Add an explicit null check on `unlockResource` in `execute()` before dereferencing it, mirroring the defensive style used elsewhere in the same file (e.g., the `receiverCapsule != null` guard), or tighten `validate()` to require that the specific resource type actually has redeemable balance in the record that `execute()` will use (as opposed to allowing either lock or unlock record to satisfy the existence check). At minimum, wrap the `execute()` logic in a broader try/catch that converts unexpected runtime exceptions into a `ContractExeException` with a `FAILED` status rather than letting the exception propagate unhandled through block application.

### Proof of Concept
1. Owner account delegates resources to a receiver using `DelegateResourceContract` with `lock=true` for `BANDWIDTH` (or `ENERGY`). This creates only a "lock" `DelegatedResourceCapsule` (key built with `createDbKeyV2(owner, receiver, true)`); no "unlock" record (`createDbKeyV2(owner, receiver, false)`) is created.
2. Owner immediately broadcasts an `UnDelegateResourceContract` for the same owner/receiver/resource with `balance <= lockResourceCapsule.getFrozenBalanceForBandwidth()`.
3. `UnDelegateResourceActuator.validate()` succeeds because `lockResourceCapsule != null` (the `unlockResourceCapsule == null && lockResourceCapsule == null` check passes since only one side is null).
4. `UnDelegateResourceActuator.execute()` looks up `unlockResource = delegatedResourceStore.get(unlockKey)`, which returns `null` (no unlock record exists).
5. Execution reaches `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);` and throws `NullPointerException`, which is not caught anywhere in `execute()`, propagating out of the actuator during transaction/block processing.
