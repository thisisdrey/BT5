### Title
Non-constant-time comparison of the HTTP `authorization` bearer token allows timing-based token recovery - (File: `stackslib/src/net/api/postblock_proposal.rs`, and identically in `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_v3.rs`, `txsimulate.rs`)

### Summary
Multiple `stackslib/src/net/api/*` HTTP request handlers authenticate remote requests by comparing the `authorization` header value against the node-configured secret (`connection_options.auth_token`) using Rust's standard `!=` string comparison, which is not constant-time. This is the same bug class as the reported `Crypto::do_decrypt` HMAC timing side-channel: a secret-bearing comparison is done byte-by-byte with early exit, letting an attacker recover the secret via timing analysis.

### Finding Description
Each of the affected handlers implements `try_parse_request` and performs:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) [2](#0-1) 

The same pattern (`auth_header != password`) recurs verbatim in `blocksimulate.rs`, `fastcallreadonly.rs`, and is used analogously in `postblock_v3.rs` (`auth_header != password`) to gate `broadcast=1` and in `postblock_proposal.rs` to gate the `/v3/block_proposal` endpoint. This token protects the RPC channel between `stacks-node` and `stacks-signer` / miner, as documented in `stackslib/src/config/mod.rs`: "This token is used in the Authorization header for certain requests... It is also used to authenticate requests to `/v2/blocks?broadcast=1`" and gates `/v3/block_proposal`. [3](#0-2) 

Rust's `PartialEq` for `String`/`&str` (used via `!=`) delegates to slice `==` which compares byte-by-byte and returns as soon as a mismatch is found (via `memcmp`-like semantics), so the time taken is correlated with the number of matching leading bytes. An attacker who can query these HTTP endpoints repeatedly (no prior authentication needed — the whole point is that the header is being checked) can use timing statistics to incrementally recover the correct `auth_token` byte by byte, exactly as described in the reference report for the HMAC comparison.

### Impact Explanation
`auth_token` is the primary gate for privileged operations, including:
- Broadcasting non-canonical/attacker-controlled blocks via `/v2/blocks?broadcast=1` (`postblock_v3.rs`).
- Submitting block proposals via `/v3/block_proposal` (`postblock_proposal.rs`), which is the interface a miner/attacker uses to get a signer to validate/sign a block.
- Read endpoints like block-replay/simulate/fastcall, which can leak chain state or consume compute.

Recovering the token would let an attacker impersonate the miner/signer relationship, submitting forged block proposals or triggering privileged broadcasts — i.e., an authentication bypass leading to unauthorized write/forged-data submission on a security-critical RPC surface. This aligns with the "auth bypass" and "unauthenticated write to state" Critical/High impact categories in scope.

### Likelihood Explanation
Difficulty is nontrivial (timing attacks require many samples over network, and jitter reduces signal), matching the "Medium" difficulty rating in the original report. However this is a real, remotely reachable design flaw: the comparison is on the direct network hot path of an HTTP handler with no rate limiting or constant-time enforcement, and repeated requests to a local/low-latency node RPC (as would exist between a miner and its own or a partner's signer, or across the open node RPC port if reachable) make statistical extraction feasible over time.

### Recommendation
Replace the `!=`/`==` plaintext comparisons of `auth_header` vs. the configured secret in all of `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, and `txsimulate.rs` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or by comparing SHA-256 digests of both header value and secret with a constant-time digest compare). Centralize this into a single shared helper (e.g., in `crate::net::httpcore`) used by every handler in `stackslib/src/net/api/` that checks `self.auth`, so the fix is applied consistently and future endpoints inherit constant-time behavior by default.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`, exposing `/v3/transactions/simulate`, `/v3/blocks/replay/...`, or `/v3/block_proposal`.
2. From a network position with low-jitter access to the node's RPC port, send repeated requests with the `authorization` header set to candidate strings that share progressively longer correct prefixes of the secret (byte-by-byte brute force per position).
3. Measure round-trip response times for the 401 rejection path across many trials; statistically, guesses whose prefix matches more bytes of the real secret take marginally longer in the comparison (`auth_header != password`) due to more bytes being compared before the mismatch is found.
4. Repeat per byte position across the alphabet to reconstruct `auth_token` character-by-character, then use it to authenticate to `/v3/block_proposal` or `/v2/blocks?broadcast=1` as if privileged.
