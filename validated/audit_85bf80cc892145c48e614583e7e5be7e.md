Based on my research, I found a valid analog vulnerability. The SSL-verification bug class ("the endpoint's caller identity/authenticity is never actually checked, so any party can impersonate a trusted peer") maps to `libsigner/src/events.rs`, where the signer's local HTTP event listener has no request-level authentication, and one of the two payload branches performs *no* signature check at all before treating unauthenticated data as trusted miner state.

### Title
Signer Event HTTP Endpoint Accepts Unauthenticated Miner Messages With No Signature Verification - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver` binds a plain, unauthenticated HTTP server (`tiny_http`) that the Stacks node is expected to POST events to. [1](#0-0)  Any client that can reach this listening socket can POST arbitrary JSON to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block`, and it will be parsed and forwarded to the signer runloop with no verification that the request actually originated from the trusted local node. [2](#0-1)  The `stacks-signer` code itself acknowledges this exposure risk in a startup warning. [3](#0-2) 

### Finding Description
Within `TryFrom<StackerDBChunksEvent> for SignerEvent<T>`, chunks destined for the `MINERS_NAME` boot contract are deserialized and forwarded as `SignerEvent::MinerMessages` with **zero signature or ownership verification** — `T::consensus_deserialize` is called directly on `chunk.data` with no call to `chunk.recover_pk()` or any equivalent authenticity check: [4](#0-3) 

This is in stark contrast to the adjacent `SIGNERS_NAME` branch just below it, which at least recovers a public key from the chunk's signature before accepting the message: [5](#0-4) 

Normally, chunk signatures are validated against the true slot owner before being stored/broadcast by the node itself, in `stackslib/src/net/stackerdb/mod.rs::validate_received_chunk`, which explicitly checks `slot_metadata.verify(&addr)` against the on-chain-configured slot signer. [6](#0-5)  However, that validation happens on the **node** side, not in the **event-delivery path** that feeds the signer. The `SignerEventReceiver` HTTP listener performs no equivalent check on the HTTP request itself, and the `MinerMessages` conversion path performs no equivalent check on the chunk payload either. The implicit "authenticated because it came from localhost/the trusted node" assumption is never enforced in code — it is only a documented operational expectation. [7](#0-6) 

This exactly mirrors the CVE-2012-5825 bug class: a trust decision ("this data came from the legitimate counterparty") is made without any cryptographic check to enforce it, so any party capable of reaching the channel can impersonate the trusted source.

### Impact Explanation
An attacker who can reach the signer's bound event port (which is a configurable `SocketAddr`, not hardcoded to loopback) can POST a forged `StackerDBChunksEvent` JSON body containing an arbitrary `MinerMessages` payload with a garbage or empty signature, since the `MINERS_NAME` branch performs no signature check whatsoever. This is unauthenticated write of forged state into the signer's internal event stream and runloop, potentially steering signer behavior/decisions based on fabricated miner messages — a direct case of "forged gossip relayed" and "unauthenticated/unauthorized write to state" reachable without any node secret or privileged role, satisfying the Critical impact bar in the rules.

### Likelihood Explanation
Likelihood depends entirely on network exposure of the signer's event-receiver port. If bound to `0.0.0.0` or any non-loopback interface (which the code allows and the startup warning explicitly anticipates as a real-world configuration), the endpoint is remotely reachable with no authentication, no TLS, and no shared secret — trivially exploitable by any unprivileged network peer that can send an HTTP POST.

### Recommendation
Require an authenticated channel between the node and the signer's event receiver (e.g., a shared bearer token/HMAC on the HTTP request, or restrict listener to loopback with a documented enforced check rather than a warning). Additionally, apply the same `recover_pk`/signature-verification discipline used in the `SIGNERS_NAME` branch to the `MINERS_NAME` branch in `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` so that miner chunk data is never accepted without proof of authorship, mirroring the node-side `validate_received_chunk` guarantee.

### Proof of Concept
1. Start a `stacks-signer` instance configured to bind its event receiver to a non-loopback address (a supported and warned-about configuration per `stacks-signer/src/lib.rs`).
2. From a remote unprivileged host, craft an HTTP POST to `http://<signer-ip>:<port>/stackerdb_chunks` with a JSON body matching `StackerDBChunksEvent`, where `contract_id` names the boot `MINERS_NAME` contract and `modified_slots` contains a `StackerDBChunkData` whose `data` field is an arbitrary serialized miner message and whose `sig` field is left empty/garbage.
3. Observe that `process_event::<T, StackerDBChunksEvent>` successfully parses the request and `TryFrom` yields `SignerEvent::MinerMessages` containing the forged message with no signature check, which is then forwarded to the signer's runloop via `forward_event`. [8](#0-7) 

Note: I could not fully verify within the tool budget whether the downstream consumer in `stacks-signer/src/v0/signer.rs` performs any additional re-validation of `MinerMessages` content before acting on it; if such a check exists it may reduce (but does not eliminate, since it doesn't change the events.rs contract) the practical severity. This should be confirmed by a follow-up review of `stacks-signer/src/v0/signer.rs`'s handling of `SignerEvent::MinerMessages`.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
