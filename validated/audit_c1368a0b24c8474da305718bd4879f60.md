Audit Report

## Title
`ERC20Transactor` performs unconditional external ERC-20 `transfer()` calls without a zero-amount guard, letting a revert-on-zero-value token DoS XCM asset withdrawal/deposit - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` extract `amount` from the XCM `Asset`/`AssetsInHolding` via `Matcher::matches_fungibles` and unconditionally invoke `pallet_revive::Pallet::<T>::bare_call` with `IERC20::transferCall { value: EU256::from(amount), .. }`, with no `amount == 0` short-circuit [1](#0-0) [2](#0-1) . A revert-on-zero ERC-20 contract registered as a foreign asset behind this transactor turns any zero-value leg of an XCM program into a hard `FailedToTransactAsset` failure.

## Finding Description
The XCM executor's `process_instruction` for `WithdrawAsset` iterates every asset in the instruction and calls `Config::AssetTransactor::withdraw_asset_with_surplus` per-asset without any amount filtering [3](#0-2) ; similarly, `deposit_assets_with_retry` calls `deposit_asset_with_surplus` per asset from holding without filtering zero amounts [4](#0-3) . `Matcher::matches_fungibles` (the `MatchesFungibles` trait) performs only asset-id/type matching and returns whatever `amount` a caller supplies — it does not reject zero [5](#0-4) . `ERC20Transactor` is wired directly into the live `AssetTransactors` tuple used by Asset Hub Westend's `XcmConfig` [6](#0-5) , confirming it is reachable from externally-triggerable XCM execution (including bridged/Snowbridge flows), consistent with the transactor's original PR intent to support ERC20s referenced by their smart-contract address in XCM [7](#0-6) .

The codebase has already needed to fix an analogous zero-amount-in-holding hazard: `SwapFirstAssetTrader::buy_weight` previously wrapped an exact-trade zero-amount credit unconditionally into `AssetsInHolding`, causing an undecodable `AssetsTrapped { Fungible(0) }` event, and the fix explicitly guards against putting a zero value into holding [8](#0-7) . `pallet-revive`'s own internal `transfer` helper documents and implements exactly the guard that is missing here ("This is a no-op for zero `value`...") [9](#0-8) . `ERC20Transactor` has no equivalent check, so a zero-value fungible instance of an ERC20 asset flowing through `WithdrawAsset`/`DepositAsset` reaches `bare_call` → `transfer(_, 0)` on the target contract. For a spec-legal ERC-20 that reverts on zero-value transfers, `did_revert()` is `true`, causing `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))` to propagate: on withdraw, the whole XCM program instruction fails before assets are pulled into holding; on deposit, the failure is surfaced per-asset via `deposit_asset_with_surplus`'s `Err((what, ...))`, and — since `deposit_assets_with_retry` processes each asset in `into_per_asset_holdings()` independently — a failing zero-amount deposit for this asset does not doom unrelated non-zero assets in the same call (they are retried/deposited separately), but it does cause that specific transactor's deposit to fail, propagating an `XcmError` for that leg and leaving the corresponding holding entry to be trapped via `AssetsTrapped` at `post_process` rather than delivered to the beneficiary [10](#0-9) .

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" / "permanent user-fund lock" impact category: any permissionless XCM sender able to route a `Fungible(0)` instance of an ERC20-backed asset through `WithdrawAsset` or `DepositAsset` can force `FailedToTransactAsset` for that asset leg. The failed leg's assets are trapped via `AssetsTrapped` (requiring manual claim) rather than settling to the rightful beneficiary in one atomic step, and the failure aborts execution of the enclosing `TransactionalProcessor::process` block for that instruction, degrading normal processing of otherwise-valid XCM programs that happen to include a zero-value leg of a revert-on-zero ERC20 asset.

## Likelihood Explanation
Exploitability requires only that at least one ERC20 contract registered/reachable via `ERC20Transactor`'s `Matcher` implements the (fully spec-compliant) `require(value > 0)` pattern on `transfer`. Given this, the attack requires no privileged access — any XCM sender (including an Ethereum-origin Snowbridge message or any account able to construct an XCM program with a `Fungible(0)` asset entry) can trigger it repeatedly, at will, since `Fungible(0)` legs are trivial to construct.

## Recommendation
Add an explicit `amount.is_zero()` short-circuit in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, returning `Ok((AssetsInHolding::new(), Weight::zero()))` / `Ok(Weight::zero())` respectively and skipping the `bare_call` entirely when the amount is zero, mirroring the pattern used in `pallet_revive::exec::transfer` and the `SwapFirstAssetTrader` zero-amount fix (`pr_11389`).

## Proof of Concept
1. Deploy an ERC-20 contract via `pallet-revive` whose `transfer` reverts when `value == 0`, registered as a foreign asset matched by `ERC20Transactor`'s `Matcher`.
2. Construct an XCM program executed against `AssetHubWestend`'s `XcmConfig` containing `WithdrawAsset` (or a `DepositAsset` from holding) with `Fungible(0)` for that asset's `AssetId`.
3. Observe `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` invoke `bare_call` → `transfer(_, 0)` → contract reverts → `XcmError::FailedToTransactAsset("ERC20 contract reverted")`, failing the instruction and causing the associated holding entry to be trapped via `AssetsTrapped` rather than delivered.

			match Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
