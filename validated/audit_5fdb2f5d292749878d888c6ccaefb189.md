### Title
Unprivileged attacker can fill a victim's per-account token lists via dust `DepositToken` transfers, permanently reverting new collateral onboarding and debt issuance for that account — ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken._transfer` unconditionally calls `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to positive. `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount` hits `MAX_TOKENS_PER_USER`. Any user with an unlocked `msdTOKEN` balance can `transfer()` dust of every supported collateral token to a victim, filling the victim's list until every subsequent first-time deposit, transfer-in, `seize`, or debt issuance to that account reverts.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's list on any 0→positive balance change, with no opt-in or minimum amount. From `contracts/DepositToken.sol` (lines 517-525):
```solidity
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```
- `Pool.addToDepositTokensOfAccount` enforces the combined cap in `contracts/Pool.sol` (lines 143-148, 216-220):
```solidity
if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
    revert UserReachedMaxTokens();
}
```
- The same cap gates `addToDebtTokensOfAccount` (`contracts/Pool.sol` line 204), which is invoked from `DebtToken` when a balance first becomes positive, so `issue`, `leverage`, and any transfer that pushes a debt token balance above zero also revert.
- Attack path (all public, unprivileged):
  1. Attacker deposits a minimal amount of each listed collateral via `DepositToken.deposit(amount, attacker)` — or just acquires dust.
  2. For each `DepositToken` the victim does not already hold, attacker calls `msdToken.transfer(victim, 1 wei)`. Each call hits `addToDepositTokensOfAccount(victim)` (the dust is unlocked since the attacker has no debt against it, so `_revertIfLocked` passes — `contracts/DepositToken.sol` lines 348-353).
  3. Once the victim's combined list length reaches `MAX_TOKENS_PER_USER`, any `deposit`/`transfer`/`seize` of a deposit token the victim doesn't already hold reverts in `_transfer` → the transaction fails atomically.
  4. By also issuing synths to themselves and swapping/donating, the attacker can push debt-token entries toward the cap as well where reachable; the deposit-token side alone is sufficient for the DoS.

### Impact Explanation
The victim is denial-of-serviced at the state-transition level, analogous to the crafted-content process crash in CVE-2025-43425:
- `DepositToken.deposit`, `transfer`, `transferFrom`, and `DepositToken.seize` all revert for any collateral type not already in the victim's list — the victim cannot onboard new collateral or be seized into a new `msdTOKEN` position.
- `DebtToken` minting paths (`issue`, `leverage`, `SmartFarmingManager.leverage`) revert for new synth types, blocking position management.
- While not permanent loss, this is a temporary freezing of funds/positions: a victim approaching liquidation cannot add a new collateral type to rescue their position, and the attacker can re-fill entries each time the victim clears dust (persistent griefing at low cost — the dust itself is near-free to the attacker since it stays transferable).

### Likelihood Explanation
- Only requires an EOA and public entry points; no privileged role, oracle manipulation, or trusted-remote compromise.
- Cost scales with the number of listed deposit tokens not already held by the victim; per the deployed configuration the cap `MAX_TOKENS_PER_USER` is a bounded constant and the pool's listed deposit tokens are few, so filling the list is cheap. (Exact `MAX_TOKENS_PER_USER` value was not confirmed from indexed source — the modifier logic in `Pool.sol:143-148` is what matters.)
- Mitigating factor: the victim can unstick themselves by transferring the dust back out (0-balance triggers `removeFromDepositTokensOfAccount`), so severity is medium-low — but recovery costs the victim gas per token and can be repeated by the attacker.

### Recommendation
- Only call `addToDepositTokensOfAccount` from state-changing paths the recipient controls (e.g., `deposit`), or track membership lazily: treat "is in list" as `balanceOf > 0` instead of maintaining enumerable sets, or make `debtPositionOf`/`depositOf` iterate over the global `depositTokens` list filtered by nonzero balance.
- Alternatively, require a minimum transfer amount, or allow `seize`/liquidation paths to bypass the cap so liquidations of the victim cannot be bricked.

### Proof of Concept
Hardhat sketch (against existing test fixtures such as `E2E.base.test.ts`):

```ts
// setup: pool with deposit tokens msdWETH, msdUSDC, ... and alice as victim
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber()

// attacker deposits dust in each supported collateral
for (const dToken of allDepositTokens) {
  await underlying.connect(attacker).approve(dToken.address, MaxUint256)
  await dToken.connect(attacker).deposit(1, attacker.address)
}

// grief: fill victim's depositTokensOfAccount
for (const dToken of allDepositTokens) {
  if ((await dToken.balanceOf(victim.address)).isZero()) {
    await dToken.connect(attacker).transfer(victim.address, 1)
  }
}

// victim can no longer deposit a collateral type they don't already hold
await expect(
  newDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// and first-time issuance of any new debt token reverts identically
await expect(
  newDebtToken.connect(victim).issue(1, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Caveat: the exact `MAX_TOKENS_PER_USER` constant and the deployed count of deposit/debt tokens were not confirmed in the indexed source; the PoC assumes filling to the cap is economically feasible given the pool's listed tokens.
