### Title
RewardsDistributor index math is broken for interest-bearing DebtTokens: rewards are credited on the interest-inflated balance retroactively, letting borrowers over-claim at other users' expense - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor` advertises (via `onlyIfTokenExists`) that it supports both `DepositToken` and `DebtToken` reward markets [1](#0-0) . The accrual model assumes a token's `balanceOf` only changes via mint/burn/transfer callbacks that checkpoint `accountIndexOf` — true for `DepositToken`, but false for `DebtToken`, whose `balanceOf` grows continuously with interest accrual without any callback [2](#0-1) . Analogous to the OpenQ `solvent()` issue, a function that purports to work for all supported token types silently produces incorrect results for one of them.

### Finding Description
The per-account reward delta is computed as:

```solidity
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

`contracts/RewardsDistributor.sol:229-230` — the *current* `balanceOf` is multiplied by the entire index delta since the user's last checkpoint. For `DepositToken` this is correct because `_transfer`/`_mint`/`_burn` always invoke `updateBeforeTransfer`/`updateBeforeMintOrBurn` before any balance changes [3](#0-2) .

For `DebtToken`, `balanceOf(account)` returns `principalOf[account] * currentDebtIndex / debtIndexOf[account]` [4](#0-3) , where `currentDebtIndex` grows every second via `_calculateInterestAccrual` [5](#0-4) . This balance growth produces no `updateBeforeMintOrBurn` call — only `issue`, `mint`, `repay`, `repayAll`, and `burn` trigger the modifier [6](#0-5) .

Consequence: when a borrower's rewards are finally updated (at their next repay/burn/claim), the accrued reward delta `deltaIndex` — which accumulated over a period when their balance was *smaller* — is applied to their *interest-inflated* current balance. They are retroactively credited rewards on debt they did not hold during most of the accrual window.

### Impact Explanation
The reward index `_tokensAccrued / totalSupply` distributes a fixed per-token reward pool [7](#0-6) . Over-crediting a borrower therefore depletes `rewardToken` held by the distributor, and `_transferRewardIfEnoughTokens` silently pays nothing when the balance is insufficient [8](#0-7)  — so earlier over-claimers steal unclaimed yield owed to later claimers. This is theft of unclaimed yield, an accepted impact class.

### Likelihood Explanation
Requires a `RewardsDistributor` with nonzero `tokenSpeeds[debtToken]` (borrower incentives) on an interest-bearing market (`interestRate > 0`). An unprivileged attacker calls `debtToken.issue()` to open a debt position, waits for interest to accrue, then calls `repay()` or `claimRewards(account, [debtToken])`. The `_burn` path checkpoints `accountIndexOf` *before* the burn, crediting `balanceOf` — which includes all accrued interest — against the full `deltaIndex`. The larger the interest rate and the longer since the last checkpoint, the larger the over-credit. No privileged role, oracle manipulation, or timing beyond normal block production is needed; the attacker can amplify by maximizing time between their checkpoints while their balance grows.

Caveat: since all debt holders' balances grow at the same `debtIndex` rate, the per-account inflation factor is similar across borrowers; the asymmetry is realized mainly by borrowers who checkpoint *late* relative to when their balance grew, versus depositors/early claimers whose deltas were computed at lower balances. A fork PoC should quantify the divergence against a fair time-weighted baseline.

### Recommendation
Either restrict `onlyIfTokenExists` to deposit tokens (drop DebtToken reward markets), or make reward accrual for debt tokens interest-aware — e.g., snapshot `principalOf`/`debtIndexOf` at each checkpoint and compute the delta on the principal at the *old* index, or call `updateBeforeMintOrBurn` inside `DebtToken.accrueInterest` for accounts being touched. At minimum, document that borrower rewards are computed on interest-adjusted balances.

### Proof of Concept
Hardhat outline (requires a configured RewardsDistributor with speed on the msETH DebtToken and funded rewardToken):

```ts
// 1. alice issues debt at t0 (checkpoints accountIndexOf at balance B0)
await msEthDebtToken.connect(alice).issue(amount, alice.address)

// 2. advance time; interest accrues: balanceOf(alice) = B0 * (1 + r*t)
await time.increase(365 * 24 * 3600)

// 3. trigger an update via repay/claim; deltaIndex covers the whole year
//    but is multiplied by the year-end inflated balance
await msEthDebtToken.connect(alice).repay(alice.address, dust)

// 4. compare tokensAccruedOf[alice] vs fair value sum_i B(t_i)*dIndex_i
//    (approximate by a second account issuing the same amount and claiming
//    every block — alice's accrual exceeds the frequently-checkpointed account's)
const accrued = await rewardsDistributor.tokensAccruedOf(alice.address)
// assert accrued > fairBaseline
```

The assertion gap equals approximately `B0 * deltaIndex * (debtIndexGrowth - 1)`, demonstrating retroactive rewards on non-existent debt.
