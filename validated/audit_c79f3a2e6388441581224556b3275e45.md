Ephemeral Merkle-Leaf Storage in Snowbridge Outbound Queue Makes Bridge Message Delivery Dependent on Unrecoverable Off-Chain Data, Enabling Permanent Fund Lock - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
The Snowbridge outbound queue pallets (`snowbridge-pallet-outbound-queue` and its v2 successor) commit only a Merkle **root** of outbound messages to the parachain header digest at `on_finalize`. The full message contents and leaf hashes needed to reconstruct the Merkle proof required to relay a message to Ethereum are stored in `Messages` and `MessageLeaves`, both of which are explicitly killed one block later in `on_initialize`. This mirrors the reported Linea defect: the chain publishes a commitment (root / offsets) but not the data needed to independently reconstruct the proof, making delivery dependent on a relayer or archive-node operator having captured the ephemeral data in time.

### Finding Description
In `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`:

- `Messages` and `MessageLeaves` are declared `#[pallet::unbounded]` storage values with the explicit design note: "Is never read in the runtime, only by offchain message relayers... it will never go into the PoV of a block." [1](#0-0) 
- `on_initialize` unconditionally kills both storages from the previous block, and `on_finalize` calls `commit()`, which builds the Merkle root from `MessageLeaves` and only pushes the **root** into the header digest via `SnowbridgeDigestItem`. [2](#0-1) 
- The only mechanism to reconstruct a Merkle proof for a given leaf is the `prove_message` runtime API, which reads directly from the live `MessageLeaves` storage. [3](#0-2) 

Because `MessageLeaves`/`Messages` are killed at the very next block's `on_initialize`, the underlying leaf data backing the committed root exists in *current* chain state for exactly one block. After that, the data is only available by querying **historical state** at the exact block hash where it was committed — which requires either (a) the relayer capturing it within that one-block window, or (b) a full/archive node that has not pruned that historical state. Full nodes by default prune old state after a limited number of blocks, so once pruned, nobody — not even other willing relayers or the message's own beneficiary — can reconstruct the Merkle proof from on-chain data alone. Unlike the actual message payload, root commitments themselves give no way to rebuild the leaf set; the ordering and full content of every other message committed in that same block must be known to reconstruct the tree and generate a valid inclusion proof.

This exactly parallels the reported invariant break: a commitment (root / `l2MessagingBlocksOffsets`) is published on-chain, but the data required to build the proof for claiming/delivering the message is not persisted or otherwise verifiably reconstructable, so message delivery becomes dependent on the cooperation/availability of an off-chain party (relayer or archive-node operator) rather than being self-contained and trustless.

### Impact Explanation
If the ephemeral leaf data is lost — because no relayer queried `prove_message` before the next block's `on_initialize`, or because all queryable nodes have pruned that historical state — the corresponding `PendingOrder` entry in `PendingOrders` (keyed by `nonce`, holding the user's prepaid `fee`) can never be fulfilled: no proof can be generated to submit the message to the Ethereum Gateway, so the on-chain event that would trigger `submit_delivery_receipt` and pay out the relayer/settle the order never occurs. The user's fee remains permanently locked in `PendingOrders` (never reaped by any extrinsic in this pallet), and any cross-chain action gated on that message (e.g., unlocking assets on Ethereum) is unrecoverable. This is a permanent bridge-state/fund lock rooted in the pallet's own storage-lifecycle design rather than any malicious relayer/validator action, satisfying the "public underpriced work / permanent user-fund or bridge-state lock" impact category.

### Likelihood Explanation
This does not require any malicious actor. It occurs naturally whenever no relayer happens to fetch `prove_message` for a given leaf within the single block before `Messages`/`MessageLeaves` are killed (e.g., relayer downtime, network partition, high message volume causing a relayer to miss specific leaves in a busy block, or simply a lack of financial incentive to capture data for a low-value message alongside others in the same block). Because default node state pruning windows are far shorter than realistic relayer-recovery timeframes, the window to recover from a missed capture is effectively limited to one block unless an archive node happened to retain that exact state.

### Recommendation
- Persist committed message payloads (or at minimum, enough data to regenerate the leaf set: origin, nonce, topic, commands) for a bounded but non-trivial retention window (e.g., N blocks) instead of killing them at the very next block, or emit them fully via events so any observer can reconstruct the tree without relying on live storage.
- Alternatively/additionally, provide the full ordered leaf set (or a compact proof) as part of the commitment itself so proof reconstruction does not require reading transient runtime storage tied to a single block's lifetime.
- Add a permissionless "reap stuck order" or fee-refund path so that `PendingOrders` entries whose underlying leaf data has become unreconstructable are not indefinitely locked.

### Proof of Concept
1. Multiple messages are enqueued and processed into a single block; `do_process_message` appends to `Messages`/`MessageLeaves` and creates a `PendingOrder` per nonce. [4](#0-3) 
2. `on_finalize` runs `commit()`, publishing only the Merkle root to the header digest. [5](#0-4) 
3. In the very next block, `on_initialize` kills `Messages` and `MessageLeaves`. [6](#0-5) 
4. Any relayer that did not call `prove_message` (`bridges/snowbridge/pallets/outbound-queue-v2/src/api.rs`) against the exact prior block hash before this point permanently loses the ability to reconstruct a proof for any leaf committed in that block, once historical state for that block is pruned by all reachable nodes — leaving the corresponding `PendingOrders` entries and prepaid fees stuck indefinitely with no extrinsic to recover them.

		/// Process a message delivered by the MessageQueue pallet.
		/// IMPORTANT!! This method does not roll back storage changes on error.
		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			let current_len = MessageLeaves::<T>::decode_len().unwrap_or(0);
			if current_len >= T::MaxMessagesPerBlock::get() as usize {
				Self::deposit_event(Event::MessagePostponed {
					payload: message.to_vec(),
					reason: Yield,
				});
				return Err(Yield);
			}

			// Decode bytes into Message
			let Message { origin, id, fee, commands } =
				Message::decode(&mut message).map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: None,
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?;

			// Convert it to OutboundMessage and save into Messages storage
			let commands: Vec<OutboundCommandWrapper> = commands
				.into_iter()
				.map(|command| OutboundCommandWrapper {
					kind: command.index(),
					gas: T::GasMeter::maximum_dispatch_gas_used_at_most(&command),
					payload: command.abi_encode(),
				})
				.collect();

			let nonce = <Nonce<T>>::get().checked_add(1).ok_or_else(|| {
				Self::deposit_event(Event::MessageRejected {
					id: None,
					payload: message.to_vec(),
					error: Unsupported,
				});
				Unsupported
			})?;

			let outbound_message = OutboundMessage {
				origin,
				nonce,
				topic: id,
				commands: commands.clone().try_into().map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: Some(id),
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?,
			};
			Messages::<T>::append(outbound_message);

			// Convert it to an OutboundMessageWrapper (in ABI format), hash it using Keccak256 to
			// generate a committed hash, and store it in MessageLeaves storage which can be
			// verified on Ethereum later.
			let abi_commands: Vec<CommandWrapper> = commands
				.into_iter()
				.map(|command| CommandWrapper {
					kind: command.kind,
					gas: command.gas,
					payload: Bytes::from(command.payload),
				})
				.collect();
			let committed_message = OutboundMessageWrapper {
				origin: FixedBytes::from(origin.as_fixed_bytes()),
				nonce,
				topic: FixedBytes::from(id.as_fixed_bytes()),
				commands: abi_commands,
			};
			let message_abi_encoded_hash =
				<T as Config>::Hashing::hash(&committed_message.abi_encode());
			MessageLeaves::<T>::append(message_abi_encoded_hash);

			// Generate `PendingOrder` with fee attached in the message, stored
			// into the `PendingOrders` map storage, with assigned nonce as the key.
			// When the message is processed on ethereum side, the relayer will send the nonce
			// back with delivery proof, only after that the order can
			// be resolved and the fee will be rewarded to the relayer.
			let order = PendingOrder {
				nonce,
				fee,
				block_number: frame_system::Pallet::<T>::current_block_number(),
			};
			<PendingOrders<T>>::insert(nonce, order);

			<Nonce<T>>::set(nonce);

			Self::deposit_event(Event::MessageAccepted { id, nonce });

//! Helpers for implementing runtime api

use crate::{Config, MessageLeaves};
use frame_support::storage::StorageStreamIter;
use snowbridge_merkle_tree::{merkle_proof, MerkleProof};

pub fn prove_message<T>(leaf_index: u64) -> Option<MerkleProof>
where
	T: Config,
{
	if !MessageLeaves::<T>::exists() {
		return None;
	}
	let proof =
		merkle_proof::<<T as Config>::Hashing, _>(MessageLeaves::<T>::stream_iter(), leaf_index);
	Some(proof)
}
