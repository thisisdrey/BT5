Based on my investigation, I found a concrete analog in the NEAR ETH-implicit **Wallet Contract**, which is one of the explicitly in-scope areas. The relevant bug class is different in mechanism from Solidity's synchronous reentrancy (NEAR's promise/receipt model makes classic same-call-stack reentrancy structurally impossible), but the same *root cause pattern* — a state "lock"/guard flag whose write can be silently discarded by a later failure inside the same guarded execution path — reproduces the theft/freeze impact class the report is about.

### Title
Wallet Contract's `has_in_flight_tx` guard is not panic-safe against callback failures caused by untrusted cross-contract calls, permanently freezing ETH-implicit account funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` uses a single boolean flag, `has_in_flight_tx`, as a reentrancy-style guard to serialize `rlp_execute` calls while a multi-step promise chain is outstanding. [1](#0-0) 
The flag is reset to `false` as the first statement inside each `#[private]` callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`). [2](#0-1) [3](#0-2) 
However, under `near-sdk`/nearcore's execution model, contract state is only persisted back to the trie if the method returns successfully; if the method call fails partway (e.g. due to `GasExceeded`), the entire receipt's state changes — including any in-memory field mutation already made — are discarded (per the runtime invariant that a failing action receipt causes a full rollback of that receipt's state changes). [4](#0-3) [5](#0-4) 

### Finding Description
`nep_141_storage_balance_callback` and `address_check_callback` each deserialize a `PromiseResult::Successful(value)` returned by an **externally chosen, untrusted contract** — the ERC-20 emulation path lets an attacker-deployed token contract's `storage_balance_of` response reach `serde_json::from_slice(&value)` in the wallet contract's callback: [6](#0-5) 
The gas allotted to this callback is a small, fixed static amount (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`) computed independently of the size of the value the external contract may return: [7](#0-6) 
Because the token/target contract in `ERC20Transfer` emulation is attacker-controllable (any account the user's/relayer's parsed target resolves to), a malicious contract can return an oversized or gas-expensive payload so that reading/deserializing it inside the callback exhausts the statically reserved gas, causing the callback's WASM execution to abort (`GasExceeded`/`GasLimitExceeded`) before it can return successfully. Since `self.has_in_flight_tx = false` is only an in-memory field mutation that is committed to the account's persisted state solely on a successful method return, an abort at this point means the persisted `has_in_flight_tx` value from before the callback ran (`true`, set by the earlier `rlp_execute`/callback-scheduling call) is never overwritten. This effectively "un-does" the guard reset the same way an unprotected reentrant external call in the `mergeTranches()` report can leave loan/tranche accounting inconsistent — a downstream failure in a called-into contract corrupts state that the guard was supposed to make consistent.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true` in persisted state, every future `rlp_execute` call on that ETH-implicit account short-circuits and returns the "transaction already in progress" error without ever creating a new promise: [8](#0-7) 
Because `rlp_execute` is the sole entry point for interacting with an ETH-implicit account (such accounts cannot receive a full-access key and cannot be deleted, per the protocol's ETH-implicit account design), this permanently freezes all funds ($NEAR balance and any assets reachable only via actions from this account) held by that wallet. This satisfies the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood depends on whether the fixed callback gas budget can realistically be exceeded by a return value from an untrusted external contract; the callback path that is reachable by an ordinary externally-owned attacker (deploying/controlling the ERC-20-emulated target contract that any wallet-contract user might transact with) is `nep_141_storage_balance_callback`, since `target`/`token_id` for `ERC20Transfer` emulation is resolved from the RLP transaction and not restricted to known-good contracts. This requires the attacker to control the target token contract's `storage_balance_of` response but requires no privileged NEAR role — it's reachable by any account able to deploy a contract and get a wallet-contract user (or the relayer acting on their behalf) to interact with it via `rlp_execute`.

### Recommendation
- Bound the size of promise results consumed by these callbacks before attempting deserialization (e.g., check `value.len()` against a safe limit before calling `serde_json::from_slice`), and/or increase callback gas to a size-scaled amount with a hard ceiling and reject overly large results early with an `Err` (not a panic).
- More fundamentally, persist the `has_in_flight_tx = false` reset independently of the rest of the callback's success path — e.g., using a low-level `storage_write` for just that flag before doing any risky work with external, size-unbounded input, so a later panic in the same call cannot revert the guard release.
- Add explicit gas-budget guards (`env::used_gas()` checks) before/after deserializing untrusted payloads so the contract can fail gracefully (returning an `Err` value) rather than aborting via `GasExceeded`.

### Proof of Concept
1. Attacker deploys a NEP-141-shaped contract `EvilToken` whose `storage_balance_of` view method returns a maximal-size JSON payload (e.g., near the `ReturnedValueLengthExceeded` limit).
2. Victim (or their relayer) calls `rlp_execute` on their ETH-implicit account with an RLP-encoded Ethereum tx that emulates an `ERC20Transfer` targeting `EvilToken`.
3. `inner_rlp_execute` sets `has_in_flight_tx = true`, schedules `storage_balance_of` on `EvilToken`, then `.then()`s `nep_141_storage_balance_callback` with `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` static gas. [9](#0-8) 
4. `EvilToken::storage_balance_of` returns the oversized payload; `nep_141_storage_balance_callback` begins executing, sets `self.has_in_flight_tx = false` in memory, then attempts `serde_json::from_slice(&value)` on the huge payload, exhausting the callback's remaining gas and aborting with `GasExceeded` before the method returns.
5. Because the callback receipt failed, near-sdk's state-persist step is never reached; the account's on-chain `has_in_flight_tx` remains `true` from step 3.
6. All subsequent `rlp_execute` calls on the victim's account now short-circuit with "transaction already in progress," permanently locking the account and its funds.
