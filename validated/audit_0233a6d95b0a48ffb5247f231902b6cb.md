### Title
`close_account` omits `ACCOUNT_IN_DELEVERAGE`/`ACCOUNT_IN_ORDER_EXECUTION` flag checks that the sibling `admin_close_account` explicitly enforces - (File: `programs/marginfi/src/instructions/marginfi_account/close.rs`)

### Summary
`close_account` only validates `ACCOUNT_FROZEN`, `liquidation_record == default`, `active_orders == 0`, and `can_be_closed()` before closing an account, whereas the sibling permissionless closing path `admin_close_account` performs `can_be_closed()` **plus** explicit checks that `ACCOUNT_IN_DELEVERAGE` and `ACCOUNT_IN_ORDER_EXECUTION` are not set. This asymmetry suggests `close_account` can close an account while it is mid-way through a deleverage or order-execution state transition that a sibling flow expects to complete against a live account.

### Finding Description
`close_account` (owner-invoked, permissionless with respect to protocol admin) performs: [1](#0-0) 

It checks `ACCOUNT_FROZEN`, `liquidation_record`, `active_orders`, and `can_be_closed()`, then closes the account via Anchor's `close = fee_payer` constraint on `MarginfiAccountClose`: [2](#0-1) 

By contrast, `admin_close_account` — described in its own doc comment as a "permissionless instruction to close legacy or new accounts that are empty and inactive" — performs `can_be_closed() && is_inactive`, then **additionally** requires that `ACCOUNT_IN_DELEVERAGE` and `ACCOUNT_IN_ORDER_EXECUTION` flags are clear, on top of `active_orders == 0` and `liquidation_record == default`: [3](#0-2) 

The fact that `admin_close_account` re-checks `ACCOUNT_IN_DELEVERAGE`/`ACCOUNT_IN_ORDER_EXECUTION` as separate conditions, in addition to `can_be_closed()`, strongly implies these flags are not already covered by `can_be_closed()` — otherwise this would be dead/redundant code. If that's the case, `close_account` is missing a precondition that a sibling code path considers mandatory for safely closing an account: an account flagged `ACCOUNT_IN_DELEVERAGE` or `ACCOUNT_IN_ORDER_EXECUTION` represents a partially-completed state transition (a deleverage operation or order-execution flow that expects to finalize against a still-existing account). Closing the account mid-transition via `close_account` would strand that in-flight process's expectations or allow the account container (and any escrowed/pending state tied to that flag) to be released while the flag still marks it as "securing a live position/transition."

I was unable to confirm the exact body of `can_be_closed()` (in `programs/marginfi/src/state/marginfi_account.rs`) in this session due to tool constraints, so I cannot rule out that it internally already rejects these flag states. This must be verified directly against the source before treating the finding as fully confirmed.

### Impact Explanation
If `can_be_closed()` does not already gate on `ACCOUNT_IN_DELEVERAGE`/`ACCOUNT_IN_ORDER_EXECUTION`, an account owner could close their account via `close_account` while a deleverage or order-execution transition is still in flight, permanently destroying the account object that the in-flight process depends on. Depending on how deleverage/order-execution state is tracked (e.g., whether counterparty state, escrowed balances, or admin bookkeeping references the account), this could strand value or create a hidden exposure — matching the "High: permanent lock or hidden exposure with real financial effect" impact tier.

### Likelihood Explanation
The precondition (an account with `ACCOUNT_IN_DELEVERAGE` or `ACCOUNT_IN_ORDER_EXECUTION` set, but `can_be_closed()` still returning true) needs confirmation via direct inspection of `can_be_closed()`. If `can_be_closed()` already checks `get_flag` bits comprehensively, this finding is a false positive. Given the explicit, seemingly redundant re-check in `admin_close_account`, there's a reasonable chance the flags are not covered, but this cannot be asserted with full confidence without reading `can_be_closed()`'s source.

### Recommendation
Read and verify `can_be_closed()`'s implementation in `programs/marginfi/src/state/marginfi_account.rs`. If it does not check `ACCOUNT_IN_DELEVERAGE` and `ACCOUNT_IN_ORDER_EXECUTION`, add the same explicit checks used in `admin_close_account` to `close_account`, or better, fold these flag checks into `can_be_closed()` itself so all closing paths share one authoritative precondition function.

```rust
pub fn close_account(ctx: Context<MarginfiAccountClose>) -> MarginfiResult {
    let marginfi_account = &ctx.accounts.marginfi_account.load()?;

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return err!(MarginfiError::AccountFrozen);
    }

    check!(
        marginfi_account.liquidation_record == Pubkey::default(),
        MarginfiError::IllegalAction,
        "Close liquidation record before closing account"
    );

    check!(
        marginfi_account.active_orders == 0,
        MarginfiError::IllegalAction,
        "Close all active orders before closing account"
    );

    check!(
        marginfi_account.can_be_closed(),
        MarginfiError::IllegalAction,
        "Account cannot be closed"
    );

    Ok(())
```

```rust
pub fn admin_close_account(ctx: Context<AdminCloseAccount>) -> MarginfiResult {
    let marginfi_account = ctx.accounts.marginfi_account.load()?;
    let clock = Clock::get()?;
    let elapsed = clock
        .unix_timestamp
        .saturating_sub(marginfi_account.last_update as i64);
    let is_inactive = elapsed > 60 * SECONDS_PER_DAY;

    check!(
        marginfi_account.can_be_closed() && is_inactive,
        MarginfiError::IllegalAction,
        "Account is not eligible for close (not empty or active within 60d)"
    );

    check!(
        !marginfi_account.get_flag(ACCOUNT_IN_DELEVERAGE)
            && !marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION)
            && marginfi_account.active_orders == 0
            && marginfi_account.liquidation_record == Pubkey::default(),
        MarginfiError::IllegalAction,
        "Account cannot be closed"
    );
```
