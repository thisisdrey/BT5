### Title
Weight double-counting via ECDSA signature malleability in `ValidateMultiSign` precompile bypasses multisig threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract, which any deployed smart contract can invoke to authorize privileged, high-value actions (custody release, treasury withdrawal, bridge/vault approval, etc.) by checking that a set of signatures reaches an account's `Permission.threshold`, deduplicates signers only by exact raw signature bytes rather than by recovered signer address before weight is accumulated. Because ECDSA signatures are malleable (a single private key can produce multiple distinct valid `(r,s,v)` byte sequences over the same message hash), a caller controlling a single low-weight key can submit two or more distinct-but-valid signatures from that one key and have its weight added to `totalWeight` multiple times, artificially reaching the multisig `threshold` without collecting signatures from the required number of independent keys.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute` [1](#0-0) , for each submitted signature the code recovers the signer address, then checks whether that address has already been counted:

```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```

The `continue` (skip) path is only taken when the *exact same signature bytes* were already seen for that address. If the same address recurs with a *different* signature encoding (trivially producible from one private key by flipping `s`/recovery id, i.e. the canonical ECDSA malleability trick), the code falls through, calls `MUtil.checkCPUTime()` (a CPU-time budget check, not a dedup guard), and then adds `weight` for that address again into `totalWeight`. This is in contrast to the transaction-level signature weighting logic in `TransactionCapsule.checkWeight` [2](#0-1) , which (post fork `VERSION_4_7_1`) keys its dedup map by the recovered *address*, correctly preventing any signer from being counted more than once. `ValidateMultiSign` lacks this per-address one-time-counting guarantee.

Because `ValidateMultiSign` is exposed as a general-purpose builtin usable from arbitrary TVM contracts (not just the protocol's own transaction broadcast path), any unprivileged contract deployer can write a contract that relies on this precompile to gate a sensitive action (this is exactly the documented intended use case — on-chain verification of a TRON account's multisig `Permission` for contract-level authorization, functionally analogous to how bridge contracts like Multichain verify multi-party approval before releasing custody of funds).

### Impact Explanation
Any contract that uses `ValidateMultiSign` to gate withdrawal/authorization logic (custom multisig wallets, vault/bridge-style contracts holding TRC10/TRC20/TRX, DAO treasuries) can have its multisig protection defeated: an attacker holding (or having compromised) a single signer's private key can inflate `totalWeight` past `permission.getThreshold()` using only malleable-signature duplicates of that one key, without ever obtaining approval from the other required signers. This directly enables unauthorized approval/withdrawal of funds from any such contract, mirroring the underlying failure class in the Multichain incident (broken/insufficiently-independent signature verification gating custody release).

### Likelihood Explanation
Exploitation requires only: (1) deploying or interacting with a contract that uses `ValidateMultiSign` for authorization (a common, documented pattern), and (2) possessing one valid private key that is part of the target `Permission`'s key set with nonzero weight. Producing a second, distinct valid signature from the same key over the same hash is a standard, well-known ECDSA malleability operation requiring no special access. The `MAX_SIZE = 5` cap on signature array length still permits up to 5 malleable duplicates, enough to satisfy most realistic thresholds using a single compromised key. No special network or SR privilege is needed — this is reachable from any TVM contract call, i.e., by any unprivileged transaction broadcaster.

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute`, deduplicate purely by `recoveredAddr` (skip/`continue` immediately whenever the address has already been counted, regardless of the exact signature bytes), matching the address-keyed dedup already used in `TransactionCapsule.checkWeight` post `VERSION_4_7_1`. The `MUtil.checkCPUTime()` call for repeated addresses should be replaced with a hard skip of weight accumulation for any address seen more than once.

### Proof of Concept
1. Create/target an on-chain account with an `Active` `Permission` containing keys `K1` (weight 1) and `K2` (weight 1), `threshold = 2` — deploy a contract that gates a fund-release function on `ValidateMultiSign(address, permissionId, dataHash, signatures) == 1`.
2. As an attacker controlling only `K1`, compute `hash` per the precompile's combine/sha256 scheme [3](#0-2) .
3. Sign `hash` with `K1` to get signature `S1 = (r, s, v)`. Derive the malleable counterpart `S1' = (r, n-s, 1-v)` — both recover to `K1`'s address but are byte-distinct.
4. Call the precompile with `signatures = [S1, S1']`.
5. In the loop: first iteration adds `K1`'s weight (1) to `totalWeight` and records `(K1, S1)`. Second iteration recognizes `K1` already in `executedSignList` but `S1'` (different bytes) is not, so it does not `continue`; it calls `checkCPUTime()` and adds `K1`'s weight (1) again, making `totalWeight = 2 >= threshold`.
6. The precompile returns `DATA_ONE` (success), and the gated contract releases funds using only a single compromised/attacker-controlled key, without `K2`'s approval.

      long weight = getWeight(permission, address);
