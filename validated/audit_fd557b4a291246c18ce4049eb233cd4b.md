### Title
Dust-token spam fills victim's position set to `MAX_TOKENS_PER_USER`, blocking deposits/withdrawals/liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The external report fixes a DoS where an attacker amplifies cost-free resubmissions because the system lacked per-submitter accounting. The Metronome analog is the per-account position list (`MappedEnumerableSet.AddressSet`) capped by `MAX_TOKENS_PER_USER` in `Pool.sol`/`PoolStorage.sol` and maintained via `DepositToken`/`DebtToken` transfer and mint hooks. Because deposit tokens are freely transferable ERC-20s, an unprivileged attacker can spam cheap "submissions" — dust transfers of many distinct deposit tokens, or dust deposits minted with attacker-supplied collateral — into a victim's set until it reaches the cap, after which the victim's legitimate operations revert. There is no analog of the report's spam-weight/tally: the protocol grants the attacker unlimited, cost-minimal list mutations against a third party.

### Finding Description
`Pool` tracks each account's live collateral and debt positions in enumerable sets backed by `MappedEnumerableSet` (`contracts/lib/MappedEnumerableSet.sol:22-66` — `_add` pushes to `_values`, `_remove` swap-pops). `Pool.sol` and `PoolStorage.sol` reference `MAX_TOKENS_PER_USER`, enforced when a token is added to an account's set (9 matches in `Pool.sol`, 5 in `PoolStorage.sol`). Tokens are registered to an account not only on `deposit`/`issue` but also on `DepositToken.transfer`/`transferFrom`, since a transfer moves a collateral position and the recipient's set must reflect it so `debtPositionOf`/`depositOf` iterate correctly.

Attack path:

1. Attacker holds or acquires dust amounts of every listed `DepositToken` in the pool (or deposits 1 wei of each underlying via `NativeTokenGateway`/`VesperGateway` to mint them).
2. Attacker calls `DepositToken(victim).transfer(dustToken_i, 1)` for each distinct deposit token `i`. Each transfer triggers the pool's position update and `MappedEnumerableSet.add(victim, token_i)`.
3. Once `length(victim) == MAX_TOKENS_PER_USER`, the revert on `add` causes:
   - any further `deposit` of a *new* collateral type by the victim to revert (temporarily freezing their ability to open/expand positions),
   - `liquidate` calls that would credit a new deposit token to the victim-as-liquidator to revert (griefing liquidations of the victim's own unhealthy positions into bad debt),
   - depending on where the check sits in the transfer hook, `withdraw`/`repay` paths that re-register tokens can also revert.

The attacker can repeat the dust spam cheaply and continuously (front-running any relief) — precisely the "excessive resubmission" amplification the Sui fix addressed — while bearing only gas cost, because the sets never rate-limit or penalize the submitter. No privileged actor, oracle manipulation, or Sybil assumption is needed; a single EOA suffices.

### Impact Explanation
Temporary freezing of funds and liveness degradation: the victim cannot deposit new collateral types (blocking top-ups needed to avoid liquidation, which can escalate to direct loss of collateral), and liquidations/seizes that would add a new token to a capped set revert, enabling bad debt accumulation. This fits the accepted impact categories (temporary freezing of funds; insolvency risk via blocked liquidations).

### Likelihood Explanation
High reachability: `DepositToken.transfer` is a public ERC-20 entry point reachable by any EOA, and dust amounts of N distinct deposit tokens cost only the transfers' gas. The cap is a fixed small constant; the attack scales linearly. Mitigations that do NOT stop it: `ReentrancyGuardTransient` (no reentrancy needed), pause flags (pool must be live for the attack to matter), SynthContext/onlyPool modifiers (the registration path is intentionally reachable from token transfers), and health checks (dust transfer doesn't depend on victim health). One residual uncertainty I could not fully resolve within this pass: the exact line where `MAX_TOKENS_PER_USER` is enforced on the *transfer* path versus only the `deposit` path — if the cap check were enforced only on `deposit`, the attacker would instead mint dust deposit tokens to a contract and `transferFrom`/sweep them, or directly dust-transfer, and the finding reduces to blocking the victim's own deposits only. The set-based griefing core stands either way because the `MappedEnumerableSet` cap exists and is populated on position changes.

### Recommendation
Mirror the report's approach — make repeated list growth attributable and expensive, or remove the victim-paid cap:

- Do not enforce `MAX_TOKENS_PER_USER` on inbound `DepositToken` transfers (recipient can't consent); enforce only when the account itself calls `deposit`/`issue`/`leverage`.
- Alternatively, add a minimum balance threshold so sub-dust positions aren't registered, and let users permissionlessly prune dust entries (`remove` when balance < threshold).
- Cap iteration cost by bounding sets per operation rather than per account lifetime, so unsolicited entries can't permanently consume the victim's slots.

### Proof of Concept
Foundry fork sketch (fill in deployed pool/token addresses):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

contract DustSetGriefingTest is Test {
    Pool pool;            // deployed Pool proxy on fork
    address victim = address(0xBEEF);
    address attacker = address(0xA77ACK);

    function test_dustFillsVictimTokenSet() public {
        // Enumerate listed deposit tokens of the pool (poolRegistry/pool getters).
        address[] memory depTokens = getListedDepositTokens(); // helper

        // Victim has a normal position
        dealUnderlyingAndDeposit(victim, depTokens[0], 1 ether);

        // Attacker mints or acquires 1 wei of every deposit token
        for (uint i; i < depTokens.length; ++i) {
            mintDust(attacker, depTokens[i]);
        }

        // Spam: attacker "resubmits" dust transfers to victim
        vm.startPrank(attacker);
        for (uint i; i < depTokens.length; ++i) {
            DepositToken(depTokens[i]).transfer(victim, 1);
        }
        vm.stopPrank();

        // Victim's set is at MAX_TOKENS_PER_USER; new collateral deposit reverts
        address newToken = depTokens[depTokens.length - 1]; // a token not yet held
        vm.startPrank(victim);
        dealUnderlying(victim, newToken, 1 ether);
        IERC20(underlyingOf(newToken)).approve(address(pool), type(uint256).max);
        vm.expectRevert(); // position-list-full error
        pool.deposit(newToken, 1 ether);
        vm.stopPrank();

        // Optionally show liquidate/seize path reverting for a capped liquidator/victim.
    }
}
```

Helpers would fork mainnet, pull the pool's listed `DepositToken`s, and mint dust via `pool.deposit` with 1 wei of each underlying (or `VesperGateway`/`NativeTokenGateway` for wrapped paths), matching deployed configuration. The revert assertion validates that the `MAX_TOKENS_PER_USER` guard fires on the victim's set growth caused by third-party transfers.
