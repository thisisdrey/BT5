### Title
Attacker-controlled attachment size unbounded by `AtlasConfig::attachments_max_size` in `AttachmentsBatchStateMachine` download path - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) accepts any `Attachment` returned by a remote peer for a `GetAttachment` request and inserts it into `self.attachments` without checking `attachment.content.len()` against `AtlasConfig::attachments_max_size`, and without re-verifying that `attachment.hash()` matches the originally requested `content_hash`. The `Done` arm of `AttachmentsBatchStateMachine::try_proceed` (via `AttachmentsDownloader::run`, `stackslib/src/net/atlas/download.rs:153-169`) then calls `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) unconditionally, storing the attachment content in the `attachments` SQLite table with no size bound at that call site.

### Finding Description
The equality the system is supposed to maintain is: any attachment byte blob accepted into `AtlasDB` must satisfy `content.len() <= AtlasConfig::attachments_max_size`. Tracing the download path in `stackslib/src/net/atlas/download.rs`:

- `AttachmentsBatchStateContext::get_prioritized_attachments_requests` (`download.rs:404-478`) builds `AttachmentRequest{content_hash, sources, ...}` from `attachments_batch.attachments_instances`, which is populated from on-chain `AttachmentInstance` commitments (via `check_attachment_instances`, `download.rs:227-286`).
- The request is sent to whichever peer claims (via its self-reported inventory) to have the attachment; this peer is an arbitrary, unprivileged remote party (any outbound sync peer).
- The response is parsed by `response.decode_atlas_get_attachment()` and handed to `extend_with_attachments` (`download.rs:530-558`), which does:
  ```rust
  if let Ok(response) = response.decode_atlas_get_attachment() {
      self.attachments.insert(response.attachment);
      report.bump_successful_requests();
  }
  ```
  There is no check here that `response.attachment.hash() == request.content_hash`, nor any check of `response.attachment.content.len()` against `attachments_max_size`.
- In the `Done` arm of `AttachmentsDownloader::run` (`download.rs:153-169`), every attachment drained from `context.attachments` is passed straight to `network.atlasdb.insert_instantiated_attachment(&attachment)`, which performs a raw SQL `INSERT OR REPLACE` of `attachment.content` with no size validation (`db.rs:576-592`).

Because the on-chain commitment only records a `Hash160` content hash (32 bytes' worth of state, effectively), a malicious peer can craft an `Attachment` whose SHA/Hash160 preimage is large (megabytes) but whose hash still matches the tracked `content_hash` for some `AttachmentInstance`. This response is accepted at both the `check_attachment_instances` fast-path (`atlas_db.find_uninstantiated_attachment` then `insert_instantiated_attachment` at `download.rs:255-262`) and the download/`Done`-arm path, in neither of which is `attachments_max_size` consulted before writing to the DB. The only place `attachments_max_size` is referenced elsewhere in the codebase is unrelated to this write path (e.g., config parsing/other RPC ingestion), so it does not gate this code.

### Impact Explanation
A single malicious/compromised outbound peer that legitimately owns (or fabricates) a valid `content_hash`-matching attachment blob can cause the victim node to store an arbitrarily large blob in its local `AtlasDB` `attachments` table, unconstrained by the configured `attachments_max_size`. Because `insert_instantiated_attachment` uses `INSERT OR REPLACE`, and there is no size cap enforced along this call path, repeated attachment instances (from repeated block processing or new contracts publishing attachment instances) allow unbounded growth of local storage — a storage-exhaustion condition tied to a consensus commitment that itself constrains nothing about the size of the smuggled payload. This matches the "High" impact category of attachment/BNS-adjacent state being served/stored that is inconsistent with what the on-chain commitment actually constrains (size-wise).

### Likelihood Explanation
Preconditions are modest: the attacker must be one of the node's outbound sync peers serving data over the Atlas HTTP data-plane (a normal, unprivileged peer relationship), and must know or construct content whose `Hash160` matches a `content_hash` the victim is actively trying to resolve (attacker can trivially satisfy this by advertising/serving content for their own contract's attachment instances, which they control). No secrets, admin roles, or privileged state are required. The attack is repeatable per-instance/per-contract each time the victim requests an unresolved attachment.

### Recommendation
Enforce `attachments_max_size` at the point attachments are ingested into the download pipeline: reject/drop responses in `extend_with_attachments` (and in `check_attachment_instances`'s inboxed/uninstantiated-attachment paths) whose `attachment.content.len()` exceeds `context.connection_options`/`AtlasConfig::attachments_max_size`, and additionally verify `attachment.hash() == request.content_hash` before accepting the attachment at all. Also add a guard inside `AtlasDB::insert_instantiated_attachment` (and `insert_uninstantiated_attachment`) to reject oversized content as defense in depth.

### Proof of Concept
In `stackslib::net::atlas::tests`, construct an `AttachmentsBatchStateContext` with a tracked `AttachmentInstance` whose `content_hash` is the `Hash160` of an oversized (e.g., 10MB) byte blob. Simulate a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains that oversized `Attachment` for the request. Call `context.extend_with_attachments(&mut results)` and then feed the resulting context through the `Done` arm logic (or directly call `atlasdb.insert_instantiated_attachment`) with an `AtlasConfig::attachments_max_size` set to a small value (e.g., 1MB). Assert that `atlasdb.find_attachment(&content_hash)` returns the full 10MB content and that no error/rejection occurred, proving the size cap is not enforced at this call site (`content.len() > attachments_max_size`, yet the row is stored).
