## Analog Found: Unbacked relayer-reward inflation via `snowbridge_pallet_system_v2::add_tip`

### Title
Public `add_tip` extrinsic inflates Snowbridge relayer rewards without charging the caller, enabling unbacked reward mint - ([File: bridges/snowbridge/pallets/system-v2/src/lib.rs])

### Summary
The GMX report's core broken invariant is: a public "fee top-up" path mutates fee/reward-bearing state without the guarded economic checks that back the original fee amount. The local analog is `pallet_snowbridge_system_v2::Pallet::add_tip`, which increases a `PendingOrder.fee` (the amount later paid out to relayers) but never withdraws, reserves, or debits any balance from the caller for the `amount` it adds.

### Finding Description
`add_tip` only authenticates the caller via `T::FrontendOrigin::ensure_origin(origin)` and then forwards an attacker-supplied `amount` straight into the reward-queue mutation, with no balance transfer step in this pallet: [1](#0-0) 

The `sender: AccountIdOf<T>` parameter is only used for bookkeeping (`LostTips`) and event emission — it is never checked against the transaction signer, nor is it charged. The call simply forwards to whichever queue's `AddTip` implementation: [2](#0-1) 

On the outbound side, `AddTip::add_tip` unconditionally increases `PendingOrders[nonce].fee` by the requested amount with no upper bound and no corresponding debit: [3](#0-2) 

That inflated `fee` is later paid out in full to the relayer via `T::RewardPayment::register_reward` when the delivery receipt is processed: [4](#0-3) 

Relayer rewards registered this way are ultimately settled by minting a reserve asset deposit via XCM to the beneficiary on AssetHub (`ReserveAssetDeposited` + `DepositAsset`), with no burn/backing on the sender's side inside this code path: [5](#0-4) 

Because `FrontendOrigin` only proves the XCM origin identity (e.g. that a message came from a particular parachain/location), and this pallet performs no `withdraw`/`hold` of `amount` from any account before crediting the reward, any caller able to satisfy `FrontendOrigin` can call `add_tip` repeatedly with large `amount` values for an existing valid nonce (obtained from a normal, cheap message it sent itself) and cause the bridge to mint/pay out rewards that were never backed by any deposited fee. This mirrors the GMX bug class precisely: the guard that is supposed to keep a "fee update" path bounded/paid-for is missing, letting an attacker manipulate fee-bearing state through a public wrapper that was designed only for legitimate top-ups.

### Impact Explanation
This directly violates the required invariant that "bridge rewards ... must conserve value and settle exactly once to the rightful beneficiary and amount." An attacker can mint unbacked relayer rewards (paid out as WETH on AssetHub) by tipping their own low-fee messages, extracting value from the bridge's reward pool/sovereign account without any real payment — a theft/unbacked-mint condition with direct chain/bridge fund-safety impact.

### Likelihood Explanation
The only gate is `FrontendOrigin`, which authenticates *where* the call came from, not that funds were provided. If `FrontendOrigin` is satisfiable by any account able to reach AssetHub's frontend pallet (e.g. a signed extrinsic proxied via a permissionless "send tip" call, or any parachain able to XCM into this origin), the attack requires no privileged access, malicious validator, or governance compromise — an ordinary user submits one cheap message plus repeated `add_tip` calls.

### Recommendation
Before forwarding to `AddTip::add_tip`, `pallet_snowbridge_system_v2::add_tip` (and its `system-frontend` counterpart, which I could not fully inspect in this pass) must actually withdraw/hold `amount` from the real transaction signer (not an attacker-supplied `sender` field) in the same atomic call, and only credit the `PendingOrder.fee` if that withdrawal succeeds — mirroring how `ChargeTransactionPayment`/`OnChargeAssetTransaction` in `substrate/frame/transaction-payment` withdraw funds before adjusting fee state. Verify the full round trip from `system-frontend` (AssetHub) through XCM to `system-v2::add_tip` (BridgeHub) to confirm whether fee-charging happens upstream; if it does, ensure it cannot be bypassed by calling `system-v2::add_tip` directly or via a spoofed/lower-cost XCM path.

### Proof of Concept
1. Attacker sends any cheap outbound message via the normal `SendMessage` flow, creating a `PendingOrder { nonce, fee: tiny, .. }` in `outbound-queue-v2::PendingOrders`.
2. Attacker (satisfying `FrontendOrigin`, e.g. from their own parachain/sovereign location) calls `snowbridge_pallet_system_v2::add_tip(sender = attacker, message_id = Outbound(nonce), amount = LARGE)` repeatedly.
3. Each call increases `PendingOrders[nonce].fee` by `LARGE` with no balance debited anywhere in this code path (`outbound-queue-v2::lib.rs` `add_tip` impl, lines 483-496).
4. Attacker (or a colluding relayer) submits the delivery receipt; `process_delivery_receipt` pays `order.fee` (now inflated) to the reward account via `RewardPayment::register_reward`, ultimately minted as WETH to the beneficiary on AssetHub through `PayAccountOnLocation::pay_reward`.
5. Net effect: reward paid out exceeds any amount ever paid into the bridge — unbacked mint.

Note: I was not able to inspect `bridges/snowbridge/pallets/system-frontend/src/lib.rs` in this session due to tool-call limits; it is possible (but not confirmed from the code reviewed) that fee-charging occurs there before the XCM reaches `system-v2::add_tip`. This should be verified directly to confirm whether the missing charge is fully exploitable end-to-end or mitigated upstream.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
				match maybe_order {
					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
						Ok(())
					},
					None => Err(AddTipError::UnknownMessage),
				}
			})
		}
