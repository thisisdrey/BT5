## Analysis

**Binding claimed to hold:** `fees_credited_to_fee_collector == Σ over all negative TokenDiff deltas of Pips::fee_ceil(protocol_fee, |delta|)` for every unit of value the signer moves out of a token balance.

**Actual code behavior traced:**

`TokenDiff::execute_intent` computes the fee **per intent execution, per token leg**, not per account-lifetime or per-batch aggregate: [1](#0-0) 

The fee rate itself is determined by `TokenDiff::token_fee`, which explicitly zeroes the fee for `Imt`/`Nep245` token classes whenever the **per-intent** magnitude is `<= 1`: [2](#0-1) 

`Imt` tokens are mintable by any unprivileged caller to any receiver via `ImtMint`, namespaced only by the signer as minter authority (`imt:<minter_id>:<token_id>`), with no role/permission gate: [3](#0-2) [4](#0-3) 

The batch-level invariant enforced by `TransferMatcher::finalize` only checks that deposits/withdrawals net to zero across the batch — it contains **no fee-related check** and does not aggregate the magnitude of same-token legs for fee-classification purposes: [5](#0-4) 

**Exploit path:** An attacker mints an `Imt` token to themselves (or a second account they control) with balance `N > 1` via `ImtMint`. To move the full `N`-unit balance out fee-free, instead of submitting one `TokenDiff` with `delta = -N` (which would incur `Pips::fee_ceil(fee, N) > 0` since `amount > 1`), the attacker submits `N` separate signed `TokenDiff` intents (distinct nonces), each with `delta = -1` on the same token, matched against `N` corresponding `+1` deposits (e.g. on a second attacker-controlled account) within the same `MultiPayload` batch so `TransferMatcher::finalize` nets to zero. Each individual `execute_intent` call sees `amount.unsigned_abs() == 1`, hits `TokenIdType::Imt` in the `match` with `amount > 1` false, and returns `Pips::ZERO`, so `fees_collected` is never incremented for that leg. This is repeatable for any `N` and for `Nep245` tokens as well, and costs the attacker only the gas of packing `N` intents into one (or a few) transactions plus the trivial mint cost — no counterparty funds or privileged role are needed.

This is a genuine divergence between the two sides of the fee-equality binding: a single `TokenDiff(-N)` intent yields `fee_collected = Pips::fee_ceil(fee, N)`, while `N` chained `TokenDiff(-1)` intents transferring the identical aggregate value yield `fee_collected = 0`. Nothing in `MultiPayload::verify`, nonce handling, `Lock`, or `TransferMatcher::finalize` prevents or detects this structuring, because the `amount > 1` gate in `token_fee` is evaluated strictly per single-intent delta with no session/account-lifetime or batch-wide aggregation.

### Title
Fee bypass on `Imt`/`Nep245` balances via unit-splitting of `TokenDiff` deltas - (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives fees on `Imt`/`Nep245` legs whenever a single intent's delta magnitude is `<= 1`, but this check is evaluated per-intent rather than against the total value moved. An attacker can mint an arbitrary-balance `Imt` token to themselves and then move the entire balance fee-free by splitting it into N signed `TokenDiff` intents of `delta = ±1` each, bypassing `Pips::fee_ceil` entirely.

### Finding Description
The broken equality: `fee_collected(T) == Pips::fee_ceil(protocol_fee, total_amount_moved(T))`. In code, `TokenDiff::execute_intent` computes `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` per intent using only that intent's own `delta.unsigned_abs()` (`contracts/defuse/core/src/intents/token_diff.rs:69-78`), and `token_fee` returns `Pips::ZERO` for `Imt`/`Nep245` when `amount <= 1` (`contracts/defuse/core/src/intents/token_diff.rs:206-216`). Any unprivileged account can mint `Imt` balances of arbitrary size via `ImtMint`/`State::imt_mint` (`contracts/defuse/core/src/intents/imt.rs:42-72`, `contracts/defuse/core/src/engine/state/mod.rs:144-172`), then submit `N` separate `TokenDiff` intents each moving `1` unit (paired with matching `+1` legs on a second attacker-controlled account so `TransferMatcher::finalize` — which only enforces net-zero balance, not fee correctness (`contracts/defuse/core/src/engine/state/deltas.rs:267-283`) — accepts the batch). Every leg independently evaluates `amount == 1`, so `fee_collected` stays `Pips::ZERO` for the whole transfer, whereas an equivalent single `delta = -N` intent would have paid `Pips::fee_ceil(fee, N)`.

### Impact Explanation
Protocol fees are systematically bypassed/under-collected on `Imt` and `Nep245` token volume, denying revenue to `fee_collector` for any amount of value the attacker chooses to move, scaling with `N` at negligible marginal cost (extra nonces/gas within a batch). This matches the explicit Critical category "protocol fees bypassed or over-collected." The attack is fully repeatable across accounts, tokens, and batches, and requires no victim funds or privileged role.

### Likelihood Explanation
Preconditions are trivial: any account can call `ImtMint` to create its own `Imt` balance, and can sign as many `TokenDiff` intents with distinct nonces as needed within one `execute_intents`/`MultiPayload` call (bounded only by gas limits, which can be worked around by splitting into a few transactions for very large `N`). No role, relayer key, or counterparty cooperation beyond the attacker's own second account is required, making this highly feasible and cheap relative to the fee saved on large transfers.

### Recommendation
Base the `amount > 1` fee-exemption check on the actual net transfer amount after `TransferMatcher::finalize` (i.e., the matched transfer size between sender and receiver) rather than on the raw per-intent delta, or remove/restrict the exemption to token classes that are structurally incapable of representing fungible quantities (e.g., true NFTs where amount is always exactly 1), applying it consistently for `Nep245`/`Imt` only when the token's semantics guarantee unit-only balances.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox, `contracts/defuse` / `tests` crate context — note: implementation of the actual test file is out of scope per rules since `tests/**` is excluded, but the scenario to prove is):
1. Attacker mints `Imt` token `T` with balance `N` (e.g. `N = 100`) to account `A` via `ImtMint`.
2. Set `protocol_fee = Pips::ONE_PERCENT` (or similar `> 0`).
3. Baseline: execute one `TokenDiff` intent on `A` with `delta = -N` for `T` matched against a `+N` intent on account `B`; assert `fee_collector` balance of `T` increases by `Pips::fee_ceil(fee, N)` (`> 0`).
4. Exploit: reset state, instead execute `N` separate `TokenDiff` intents on `A`, each `delta = -1` for `T`, matched against `N` separate `TokenDiff` intents on `B`, each `delta = +1`, all within one `execute_intents` batch (or several batches).
5. Assert cumulative `fee_collector` balance of `T` after step 4 is `0`, while `B`'s final balance of `T` equals `N` — demonstrating the same aggregate value transfer that cost `Pips::fee_ceil(fee, N)` in step 3 costs `0` fee when structured into unit legs.

    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {

            }

            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });

    }
