### Title
Personal-ID account-binding signature is replayable within the setup tolerance window, allowing an attacker to revert a personhood account link to a stale/compromised account - (`File: substrate/frame/people/src/extension.rs`, `substrate/frame/people/src/lib.rs`)

### Summary

### Finding Description
The People pallet lets a `PersonalIdentity` bind an `AccountId` to its personhood via `set_personal_id_account(account, call_valid_at)`, authorized off-chain by a signature over `(extension_version, call, other_tx_ext)` using the personal identity's ring key [1](#0-0) . Just like the reported bug, the signature does not bind to a unique, single-use intention — it only signs over the call payload plus a `call_valid_at` block number, and validity is bounded by `account_setup_time_tolerance`. Replay protection only rejects the exact `(index, account)` pair if it is *currently* the stored value: `People::<T>::get(index).is_some_and(|record| record.account.is_some_and(|stored_account| stored_account == *account))` [2](#0-1) .

This means once a person has signed two different `set_personal_id_account` messages (e.g., account A then account B) both within the tolerance window, anyone holding either signed transaction can replay it to flip the on-chain binding back and forth between A and B for as long as both remain inside the tolerance period — the pallet's own doc comment on `AsPersonInfo::AsPersonalIdentityWithProof` explicitly acknowledges this: "If 2 transaction that set 2 different account are sent for an overlapping validity period, then those 2 transactions can be replayed indefinitely for the duration of the overlapping period." [3](#0-2) 

`set_personal_id_account` itself performs no additional freshness/nonce check tying the assignment to a specific target permanently — it just re-links the storage each time it is (re-)dispatched: `AccountToPersonalId::<T>::remove(&old_account)`, then `record.account = Some(account.clone()); AccountToPersonalId::<T>::insert(&account, id);` [4](#0-3) .

The pallet's own test suite (`replay_protection_for_identity`) demonstrates this exact behavior: after Alice moves her personal ID from account `10` to `11`, replaying the *original* signed transaction for account `10` succeeds again, and then replaying the account-`11` transaction succeeds once more — the account is repeatedly flipped back and forth as long as both signed messages are within the tolerance window [5](#0-4) .

### Impact Explanation
The account linked via `AccountToPersonalId` is not cosmetic: it is the origin-authorizing binding used by `AsPersonalIdentityWithAccount` to let that specific `AccountId` dispatch calls as the `PersonalIdentity` origin using ordinary signed transactions with a nonce, and the pallet also tracks "sufficients" for the bound account (`inc_sufficients`/`dec_sufficients`) as part of granting free personhood-authenticated transactions [6](#0-5) [7](#0-6) . If a user rotates away from an account they believe is compromised or no longer trusted (directly analogous to the wallet-key-rotation scenario in the report), anyone who has retained the old signed `set_personal_id_account` message can replay it — within the tolerance window — to re-bind the personhood identity (and its associated fee-free dispatch privilege and origin) back to the old/stale account, causing unauthorized execution under the `PersonalIdentity` origin and defeating the user's intended account rotation. This matches the "unauthorized execution or origin escalation" impact class in the gate.

### Likelihood Explanation
The attacker needs no privileged role, node access, or governance power — only possession of a previously broadcast/signed `set_personal_id_account` transaction (visible in the transaction pool or block history, since the payload and signature are public once submitted) and to submit it again before `account_setup_time_tolerance` elapses relative to its `call_valid_at`. This is a purely public, unprivileged extrinsic-replay path, exactly matching the "public underpriced work"/"unauthorized execution" scope allowed by the impact gate, and requires no malicious peer/validator/relayer/admin assumption.

### Recommendation
Bind the signed payload (or the on-chain acceptance check) to a single-use nonce/generation counter per `PersonalId` rather than only to `call_valid_at` + best-effort "is this already the current account" check. Concretely: include a strictly-increasing per-identity "account generation" counter in the signed message and in `Record`, and reject any `set_personal_id_account` call whose generation is not exactly `current_generation + 1`, incrementing the stored generation on success. This eliminates the ability to replay a superseded signed message even within the tolerance window, mirroring the report's own recommendation of binding a signature to the specific intended state rather than to reusable nonce/timestamp/call data alone.

### Proof of Concept
Use `substrate/frame/people/src/tests.rs::replay_protection_for_identity` as the concrete PoC already present in the repo [8](#0-7) :
1. Alice signs and submits `set_personal_id_account(account: 10, call_valid_at: N)` → `People[alice_index].account == 10`.
2. Alice later signs and submits `set_personal_id_account(account: 11, call_valid_at: N + tolerance)` → `People[alice_index].account == 11`.
3. An attacker (or observer) replays Alice's *first* signed transaction (account 10) — it succeeds again because it is still within its own tolerance window, resetting `People[alice_index].account` back to `10`.
4. The attacker then replays the second transaction again, flipping it back to `11`.
5. This flip can repeat indefinitely as long as both signed messages remain inside their respective `call_valid_at + account_setup_time_tolerance` windows, with no way for Alice to invalidate a previously signed-but-superseded message.

#[test]
fn replay_protection_for_identity() {
	new_test_ext().execute_with(|| {
		const EXTENSION_VERSION: u8 = 0;
		// Setup alice as a member.
		let alice_sec = Simple::new_secret([1u8; 32]);
		let alice_pub = Simple::member_from_secret(&alice_sec);
		let alice_index = PeoplePallet::reserve_new_id();
		PeoplePallet::recognize_personhood(alice_index, Some(alice_pub)).unwrap();
		let generate_setup_account_tx_ext_for_call = |call: RuntimeCall| {
			let other_tx_ext = (frame_system::CheckNonce::<Test>::from(0),);
			// Here we simply ignore implicit as they are null.
			let msg = (&EXTENSION_VERSION, &call, &other_tx_ext)
				.using_encoded(sp_io::hashing::blake2_256);
			let signature = Simple::sign(&alice_sec, &msg).unwrap();
			(
				AsPerson::<Test>::new(Some(AsPersonInfo::AsPersonalIdentityWithProof(
					signature,
					alice_index,
				))),
				other_tx_ext.0,
			)
		};
		// Transaction 1: Alice sets its personal id account to 10.
		let call = RuntimeCall::PeoplePallet(crate::Call::set_personal_id_account {
			account: 10,
			call_valid_at: System::block_number(),
		});
		let tx_ext = generate_setup_account_tx_ext_for_call(call.clone());
		assert_ok!(exec_tx(None, tx_ext.clone(), call.clone()));
		assert_eq!(crate::People::<Test>::get(alice_index).unwrap().account, Some(10));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(10), Some(alice_index));
		// Somebody tries to replay the transaction, it must fail, replay is protected.
		assert_noop!(exec_tx(None, tx_ext.clone(), call.clone()), InvalidTransaction::Stale);
		// Transaction 2: Alice sets its personal id account to 11, with call valid only in the
		// future.
		let call_2 = RuntimeCall::PeoplePallet(crate::Call::set_personal_id_account {
			account: 11,
			call_valid_at: System::block_number() + 1,
		});
		let tx_ext_2 = generate_setup_account_tx_ext_for_call(call_2.clone());
		// Transaction 2 is not valid yet.
		assert_noop!(exec_tx(None, tx_ext_2.clone(), call_2.clone()), InvalidTransaction::Future);
		assert_eq!(crate::People::<Test>::get(alice_index).unwrap().account, Some(10));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(10), Some(alice_index));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(11), None);
		// Advance some time. Transaction 1 is still valid, transaction 2 becomes valid.
		mock::advance_to(System::block_number() + PeoplePallet::account_setup_time_tolerance());
		// Transaction 2 is now valid.
		assert_ok!(exec_tx(None, tx_ext_2.clone(), call_2.clone()));
		assert_eq!(crate::People::<Test>::get(alice_index).unwrap().account, Some(11));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(11), Some(alice_index));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(10), None);
		// Somebody replays the transaction 1, it must succeed. It is within time tolerance.
		assert_ok!(exec_tx(None, tx_ext.clone(), call.clone()));
		assert_eq!(crate::People::<Test>::get(alice_index).unwrap().account, Some(10));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(10), Some(alice_index));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(11), None);
		// Replay the transaction 2.
		assert_ok!(exec_tx(None, tx_ext_2.clone(), call_2.clone()));
		assert_eq!(crate::People::<Test>::get(alice_index).unwrap().account, Some(11));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(11), Some(alice_index));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(10), None);
		// Advance some time, Now time tolerance is exceeded for transaction 1.
		mock::advance_to(System::block_number() + 1);
		// Somebody replays the first transaction, it is invalid.
		assert_noop!(exec_tx(None, tx_ext, call), InvalidTransaction::Stale);
		assert_eq!(crate::People::<Test>::get(alice_index).unwrap().account, Some(11));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(11), Some(alice_index));
		assert_eq!(crate::AccountToPersonalId::<Test>::get(10), None);
	});
}
