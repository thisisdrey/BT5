### Title
Signer Event-Receiver HTTP Server Accepts Unauthenticated POSTs, Allowing Forged StackerDB/Block-Validation/Burn-Block Events to Be Injected into the Signer Runloop - ([File: libsigner/src/events.rs])

### Summary
The `stacks-signer` binary listens on an HTTP port (`SignerEventReceiver`, meant to receive events only from its paired `stacks-node`). This receiver never checks any authentication token on incoming requests, even though the node/signer pairing is documented as being secured by a shared `auth_token`/`auth_password`. Any host that can reach the signer's listening port can POST a forged `StackerDBChunksEvent`, `BlockValidateResponse`, `BurnBlockEvent`, or `StacksBlockEvent` payload and have it injected into the signer's local event queue exactly as if it had come from the trusted node.

### Finding Description
`SignerEventReceiver::next_event` dispatches based solely on URL path and HTTP method, with no credential check at all: [1](#0-0) 

`process_event` simply deserializes the raw JSON body into the target type and converts it into a `SignerEvent`, again with no authentication or provenance check: [2](#0-1) 

On the node side, the event dispatcher that is supposed to be the *only* legitimate sender to this port builds the outbound HTTP request without ever attaching any `auth_token`/`Authorization` header — it only sets `Connection: close`: [3](#0-2) 

Meanwhile, the documentation explicitly describes `auth_token` (node) / `auth_password` (signer) as a security pairing that "must match" between node and signer: [4](#0-3) 

and the sample signer config even suggests binding the listener to all interfaces: [5](#0-4) 

In reality, `auth_token`/`auth_password` is only consulted by the *node's own* HTTP RPC handlers (e.g. `RPCBlockProposalRequestHandler`, `RPCPostBlockRequestHandler`), which correctly gate their endpoints on a matching `Authorization` header: [6](#0-5) 

It is never wired into the signer's own inbound listener. This is exactly the "auth-gate that fails open" pattern called out in the report: a security control that is documented/advertised (matching secrets between two parties) but is not actually enforced at the point that receives untrusted network input — analogous to Glances' CORS wildcard being applied indiscriminately regardless of the caller's legitimacy. Here the equality being broken is "trusted node-originated event" vs. "any POST reaching the signer's socket" — the receiver treats the two as equivalent.

### Impact Explanation
This breaks the assumption that only the paired `stacks-node` can feed the signer's event stream. Depending on the signer's binding (the sample config uses `0.0.0.0:<port>`), a remote, unauthenticated attacker on the same network/interface can:
- Inject forged `/stackerdb_chunks` events (`StackerDBChunksEvent`), causing the signer to process attacker-supplied StackerDB chunk payloads that never actually reached (or passed validation on) the signer's paired node's StackerDB replica.
- Inject forged `/proposal_response` (`BlockValidateResponse`) events, i.e., synthetic "block validation" verdicts that never resulted from the node's actual chainstate validation.
- Inject forged `/new_burn_block` / `/new_block` events to desynchronize the signer's view of chain/burnchain state.
- Trigger `/shutdown` remotely, since that path also requires no authentication and directly sets the stop signal, terminating the signer's event loop (unauthenticated DoS).

This is a network-reachable, unauthenticated write into a component whose entire purpose is to gate block validity signing — i.e., "unauthenticated/unauthorized write to state" feeding directly into the signer runloop, and a trivial unauthenticated DoS via `/shutdown`. I was not able to fully trace, within the remaining budget, exactly how far downstream signer logic (`stacks-signer/src/v0/signer.rs`) re-validates these injected events against independently-verified node state before acting on them (e.g., whether `BlockValidateResponse` is cross-checked against the signer's own record of an outstanding proposal, or whether StackerDB chunk contents are still signature-checked against the known signer set before being trusted). That downstream decision logic is explicitly out of scope for this analog per the rules, but the transport-layer failure itself — a completely unauthenticated listener despite an advertised shared-secret pairing — is squarely in scope (`libstackerdb`/`libsigner` transport files) and is independently exploitable at minimum as remote unauthenticated DoS via `/shutdown`.

### Likelihood Explanation
High. No credentials, keys, or races are required — a bare TCP connection and a well-formed HTTP POST/GET to a known, well-documented set of paths (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`, `/shutdown`, `/status`) is sufficient. The sample/reference configuration shipped in this repository even directs operators to bind the listener on `0.0.0.0`, increasing real-world exposure whenever the signer host is not otherwise firewalled.

### Recommendation
Require the signer's `SignerEventReceiver` to validate an `Authorization`/shared-secret header against the configured `auth_password` before processing any POST (mirroring the check already implemented in `stackslib/src/net/api/postblock_proposal.rs` / `postblock_v3.rs`), and have `stacks-node`'s event dispatcher (`stacks-node/src/event_dispatcher/worker.rs::make_http_request`) attach the configured `auth_token` as an `Authorization` header on every request to observer endpoints that expect it. At minimum, gate `/shutdown` and `/stackerdb_chunks`/`/proposal_response` behind this check, and default-bind the signer's listener to loopback unless explicitly overridden.

### Proof of Concept
Given a running `stacks-signer` bound to `0.0.0.0:30000` (per the shipped sample config), from any reachable host:
```
curl -X POST http://TARGET_SIGNER_IP:30000/shutdown
```
This immediately sets the internal stop signal via the unauthenticated dispatch path: [7](#0-6) 
terminating the signer's event-receiver loop with no credentials of any kind — a complete, remote, unauthenticated denial of service against the signer process. The same lack of a credential check applies to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block`, allowing arbitrary attacker-controlled JSON bodies matching `StackerDBChunksEvent`/`BlockValidateResponse`/`BurnBlockEvent`/`StacksBlockEvent` to be forwarded into the signer's runloop as legitimate node-originated events.

        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)

                process_event::<T, StacksBlockEvent>(request)

                    url
                );

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
