### Title
Downloaded Atlas attachments bypass `AtlasConfig.attachments_max_size` and are persisted unchecked - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`StacksHttpResponse::decode_atlas_get_attachment` decodes a peer-supplied JSON body into a `GetAttachmentResponse`/`Attachment` with no size validation against `AtlasConfig.attachments_max_size`, and the resulting `Attachment` is inserted into `self.attachments` by `extend_with_attachments` and later persisted via `AtlasDB::insert_instantiated_attachment` with no size check performed anywhere on that path.

### Finding Description
`RPCGetAttachmentRequestHandler`/`StacksHttpResponse::decode_atlas_get_attachment` parses the HTTP response body as JSON and deserializes it directly into `GetAttachmentResponse` via `serde_json::from_value`, with no length check against `ATTACHMENTS_MAX_SIZE_MIN` or the configured `attachments_max_size` visible in that function [1](#0-0) . The decoded `Attachment` is then inserted straight into `self.attachments: HashSet<Attachment>` by `extend_with_attachments`, again with no size validation [2](#0-1) . When the batch state machine reaches `Done`, every attachment in that set is persisted directly via `network.atlasdb.insert_instantiated_attachment(&attachment)` with no size check performed in that code path either [3](#0-2) . The only `attachments_max_size` reference I could locate in `stackslib/src/net/atlas/db.rs` appears to guard a different insertion function (used for the "uninstantiated"/gossip attachment path, e.g. `insert_uninstantiated_attachment`), not the `insert_instantiated_attachment` call used by the downloader's `Done` branch above — I was not able to fully confirm this before running out of tool calls, so this should be independently re-verified.

### Impact Explanation
If confirmed, a malicious peer serving `GET /v2/attachments/<hash>` can return an oversized hex-encoded attachment body that decodes to an `Attachment.content` larger than `ATTACHMENTS_MAX_SIZE_MIN` (1,048,576 bytes) or any configured `attachments_max_size`, and have it accepted and written to the node's Atlas SQLite database unconditionally, since `insert_instantiated_attachment` is called without a preceding size check in this path. Repeated across many `AttachmentInstance`s/hashes this could grow the on-disk Atlas database well beyond the configured bound, i.e., attachment storage exhaustion bypassing the configured size bound — matching the "bounded compute DoS on a read endpoint"/resource-exhaustion category claimed by the question.

### Likelihood Explanation
The attacker only needs to be a normal outbound sync peer providing a `data_url` that the victim node queries for attachments it doesn't yet have (a routine, unprivileged scenario in Atlas sync) [4](#0-3) . No secret, signature, or privileged role is required — only that the victim has an outstanding `AttachmentInstance` referencing content the attacker's peer claims to have in its inventory. This is repeatable per attachment-request round.

### Recommendation
Enforce `attachment.content.len() <= AtlasConfig.attachments_max_size` (or `ATTACHMENTS_MAX_SIZE_MIN` at minimum) inside `decode_atlas_get_attachment` (or immediately after, before insertion into `self.attachments`), and add a redundant check inside `insert_instantiated_attachment` itself so the DB layer never persists an oversized attachment regardless of caller.

### Proof of Concept
Rust test plan: construct a `StacksHttpResponse` whose JSON body is `{"attachment":{"content":"<hex string > 2*1_048_576 chars>"}}`; call `.decode_atlas_get_attachment()` and assert it succeeds with `attachment.content.len() > ATTACHMENTS_MAX_SIZE_MIN`; feed the result through `AttachmentsBatchStateContext::extend_with_attachments` with a `BatchedRequestsResult` containing this response as `succeeded`, and assert the oversized `Attachment` lands in `context.attachments`; finally simulate the `Done` branch of `AttachmentsDownloader::run` and assert `atlasdb.insert_instantiated_attachment(&attachment)` succeeds without any size-based `Err`.

**Caveat:** I was not able to fully confirm within the available tool budget (a) the exact HTTP-layer maximum body size that bounds how large a single response can be before this code is even reached, and (b) whether `insert_instantiated_attachment` in `stackslib/src/net/atlas/db.rs` performs its own size check (only one match for `attachments_max_size` was found in that file, and I could not read its surrounding function body). These two points should be verified directly in the repository before treating this as fully confirmed.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
