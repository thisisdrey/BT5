### Title
Unchecked incoherent liquidity-relay math in `ExchangeProcessor.exchange()` can violate pool balance invariants - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The default (non-hardened) TRC10 bancor-style exchange math in `ExchangeProcessor` computes swap outputs via floating-point `pow()` operations without validating that the result is coherent (non-negative, bounded by the counter-token reserve, or consistent with the pool invariant), analogous to the Kyber `estimateIncrementalLiquidity`/`getSmallerRootOfQuadEqn` bug where an unchecked mathematical solution can silently produce a value that does not satisfy the underlying equation.

### Finding Description
`ExchangeProcessor.exchange()` implements the continuous-relay/bancor formula for the TRC10 built-in exchange pools: [1](#0-0) 

It calls `exchangeToSupply` and `exchangeFromSupply`, which perform `double`-based `Maths.pow(...)` computations and cast the result to `long` with no sanity/bounds check on the returned amount — no check that the output is non-negative, no check that it does not exceed the counter-token balance, and no check that the underlying invariant (`x*y=k`-style relation for the bancor curve) actually holds after the swap, mirroring exactly the class of bug in the external report: a numerical solving routine (there, `getSmallerRootOfQuadEqn`; here, floating-point `pow`) whose result is used unconditionally even though the domain/solvability of the formula was never verified.

This unchecked result is consumed directly by `ExchangeCapsule.transaction()`, which updates the pool's on-chain token balances using the raw processor output: [2](#0-1) 

In the non-hardened path (`hardenedCalc == false`, which is the historical/default behavior gated by `dynamicStore.getAllowHardenExchangeCalculation()`), there is no `>= 0` guard on `newFirstTokenBalance`/`newSecondTokenBalance`, and `buyTokenQuant` is not checked against the actual counter-token reserve before use in `ExchangeTransactionActuator.execute()`: [3](#0-2) 

The codebase's own remediation confirms this is a recognized bug class: a `SafeExchangeProcessor` was introduced that uses `BigDecimal` and explicitly validates results (rejecting overflow, requiring `result >= 0`, requiring `result <= buyBalance`), but this hardened path is only active when `allowHardenExchangeCalculation` is enabled via governance proposal: [4](#0-3) [5](#0-4) 

### Impact Explanation
If floating-point precision loss, extreme reserve ratios, or edge-case inputs (e.g., very large `supply`/`quant` ratios feeding `Math.pow`) cause `exchangeToSupply`/`exchangeFromSupply` to return an incoherent value (negative, NaN-derived cast, or a value inconsistent with the bancor invariant) while the non-hardened path is active, the exchange pool's on-chain token balances (`ExchangeCapsule.firstTokenBalance`/`secondTokenBalance`) can be corrupted — this can result in an account receiving more tokens than the pool invariant permits (theft from the pool) or the pool's tracked balance no longer matching real backing (unbacked balance), exactly the impact class described in the source report ("Accountability of the pool will be broken... LP trying to withdraw more than is available in balance").

### Likelihood Explanation
Reachability is straightforward: any account can invoke `ExchangeTransactionContract` via `ExchangeTransactionActuator`, an ordinary broadcastable transaction, to trigger `ExchangeCapsule.transaction()` → `ExchangeProcessor.exchange()`. Whether an attacker can practically craft inputs producing a genuinely incoherent (`negative`/out-of-range) result depends on the precise numerical behavior of the bancor `pow` formula across the full input domain, which I could not fully verify from static reading of the code alone (unlike the Kyber report, which mathematically proved discriminant negativity is reachable). The presence of the dedicated `SafeExchangeProcessor` hardening effort and associated tests strongly suggests the java-tron team already identified and is actively mitigating this exact class of issue for the non-hardened path.

### Recommendation
Require `allowHardenExchangeCalculation` (i.e., the `SafeExchangeProcessor` bounds/overflow-checked math) to be the sole calculation path, deprecating the legacy `ExchangeProcessor`/`useStrictMath` double-based path entirely, and add explicit invariant checks in `ExchangeCapsule.transaction()` (e.g., `buyTokenQuant >= 0`, `buyTokenQuant < counterTokenBalance`, resulting balances non-negative) regardless of the hardened flag, so that any future incoherent output from the swap-math routine reverts the transaction instead of corrupting pool state.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC would require constructing `sellBalance`/`buyBalance`/`sellQuant` values under the non-hardened path that drive `Maths.pow` in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [6](#0-5)  to a value that violates `0 <= result <= buyBalance`, then submitting that via `ExchangeTransactionContract`. The existing test suite's dedicated overflow/negative-result checks in `SafeExchangeProcessor` tests (`testHardenedOverflowDetection`, `testSafeProcessorNoOvershootForTypicalInputs`) demonstrate the team has already exercised boundary conditions where the naive/legacy math needs correction, but I did not find a test proving the legacy non-hardened `ExchangeProcessor` itself produces an out-of-bounds result in production, so this should be treated as an unverified analog requiring further fuzzing/property-testing to confirm exploitability.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
