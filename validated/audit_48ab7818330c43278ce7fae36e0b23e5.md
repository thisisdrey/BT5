### Title
Non-atomic Check-then-Update on the anti-replay window lets a raced/duplicated packet bypass replay protection - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt()` and `ConnectionState.VerifyRelay()` split the anti-replay-window operation into two separately-locked steps — `window.Check()` then, after the expensive AEAD decrypt runs *unlocked*, `window.Update()` — instead of performing the check-and-mark atomically. This mirrors the reported `updatePool()` bug class: state is read, an external/attacker-influenced operation is interleaved, then the state is written back without re-validating it hasn't changed in between, letting concurrent processing of the same replay counter race the window.

### Finding Description
The replay window is a `Bits` structure guarded by `cs.decryptLock` [1](#0-0) . `Decrypt()` takes the lock only for the `Check()` call, releases it, performs `DecryptDanger` unlocked, then re-acquires the lock to call `Update()`: [2](#0-1) 

Nebula processes inbound UDP packets across multiple reader routines/batches (`listen.batch`/`recvmmsg`, `tun.routines`), so two goroutines can concurrently receive the exact same (or an attacker-replayed) ciphertext carrying the same `messageCounter` for one `ConnectionState`. Because the window bit for that counter is not set until `Update()` runs — which happens only *after* the (unlocked, comparatively expensive) AEAD decrypt — both goroutines can pass `Check()` before either calls `Update()`. This is the same "read current state, allow an external operation to occur, then write state without validating it is still consistent" pattern as the `updatePool()` bug: the atomic guarantee the replay window is supposed to provide (one-shot acceptance per counter) is broken by splitting check and commit across an unlocked, attacker-triggerable operation.

`VerifyRelay()` has the identical pattern for relayed traffic: `Check()` under lock, unlocked AEAD verify, then `Update()` under lock [3](#0-2) .

### Impact Explanation
The anti-replay window's entire purpose is to guarantee that a given `messageCounter` is accepted at most once (`bits.go` implements this bookkeeping) [4](#0-3) . Splitting the check and the update across an unlocked decrypt operation reintroduces a TOCTOU race on that guarantee: a captured/replayed ciphertext raced against legitimate traffic sharing the same counter can be decrypted concurrently by two goroutines before the window is actually marked, undermining the deterministic single-acceptance property the design relies on (the project's own changelog documents prior, related replay-window race fixes: "Advance the replay window on relayed packets..." and "Lock replay window updates so concurrent readers can't corrupt it" [5](#0-4) , showing this exact class of bug has recurred here). This is a remote, network-attacker-reachable weakening of replay/nonce handling that does not require the attacker to hold a CA-signed certificate — only the ability to observe/replay a ciphertext on the wire.

### Likelihood Explanation
Likelihood is Medium: it requires (a) multi-routine packet processing to be enabled (a common, often default, deployment configuration via `listen.batch`/`tun.routines`), and (b) the attacker to race a replayed or duplicated ciphertext against genuine traffic sharing the same counter within the narrow unlocked decrypt window. This is a timing-dependent race rather than a deterministic bypass, but it is directly analogous to the reported sandwich-attack bug class: non-atomic read-then-write of security-critical state around an externally triggerable operation.

### Recommendation
Perform the replay-window check-and-mark as a single atomic operation under one lock acquisition spanning the check, and mark the counter as consumed *before* releasing the lock and performing the decrypt — or restructure `Update`/`Check` into one locked "reserve" call so no other goroutine can observe the same unclaimed counter while decryption is in flight. If a counter's reservation must be rolled back after a decrypt failure, do so explicitly rather than leaving the window unmarked for the duration of the decrypt.

### Proof of Concept
Conceptual PoC (based on the exposed code path, not independently executed):
1. Establish a tunnel with `listen.batch > 1` or multiple reader routines so inbound packets can be processed concurrently.
2. Capture one legitimate ciphertext (`packet`) with a given `messageCounter` between two already-handshaked peers.
3. Simultaneously deliver two copies of this exact ciphertext (or race it against the genuine packet) to the receiver so two goroutines call `ConnectionState.Decrypt()` concurrently.
4. Both goroutines call `cs.window.Check()` under lock, both find the counter not yet marked, both proceed to unlocked `DecryptDanger`, and only after decrypting does either call `cs.window.Update()` — demonstrating the check/commit is not atomic across the decrypt operation, unlike what the anti-replay design intends. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
