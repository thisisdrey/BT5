Audit Report

## Title
Relayer reward is paid and `PendingOrder` removed on Snowbridge outbound delivery receipt regardless of `receipt.success` value - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::<T>::process_delivery_receipt` decodes a `DeliveryReceipt` (derived from the Ethereum `InboundMessageDispatched` event) that carries an explicit `success: bool` field indicating whether the message's execution on the Ethereum Gateway succeeded, but the function pays the relayer reward and permanently removes the corresponding `PendingOrder` unconditionally, never inspecting `receipt.success`. This allows a relayer to be rewarded for messages whose Ethereum-side execution actually failed/reverted, and permanently discards the order so it cannot be retried.

## Finding Description
`process_delivery_receipt` verifies the gateway address, resolves the reward account, fetches the `PendingOrder` by nonce, and if `order.fee > 0` calls `T::RewardPayment::register_reward` before unconditionally removing the order from `PendingOrders` and emitting `Event::MessageDelivered`: [1](#0-0) 

The `DeliveryReceipt` type is constructed from the on-chain Ethereum log for the `InboundMessageDispatched` event, which explicitly encodes a `success` boolean alongside `nonce`, `topic`, and `reward_address`, confirming that `success` reflects whether dispatch/execution on the Ethereum side succeeded: [2](#0-1) 

No guard such as `ensure!(receipt.success, ...)` exists anywhere in `process_delivery_receipt`; the field is decoded from a cryptographically verified proof but its value is discarded before the reward-and-removal side effects execute. The doc comment for the module even describes the intended flow as "Fetch the pending order by nonce ... pay reward" without conditioning on success, confirming this is the actual (flawed) implemented behavior rather than a misunderstanding of intent.

## Impact Explanation
This falls within the "duplicate settlement or payout" / "theft or unbacked mint or unlock" impact category for bridge relayer rewards. An unprivileged relayer can obtain a valid Merkle/receipt proof of a message whose Ethereum-side dispatch reverted or otherwise failed (`success: false`) and submit it via the public `submit_delivery_receipt` extrinsic. `process_delivery_receipt` will still pay the full `order.fee` reward to the `reward_account` and remove the `PendingOrder` from storage, which is an incorrect/unbacked payout not tied to actual successful delivery, and also permanently loses the ability to retry or reconcile the failed order.

## Likelihood Explanation
Any unprivileged relayer with a valid Ethereum inclusion proof for the `InboundMessageDispatched` event can trigger this — no malicious validator, governance, or leaked-key assumption is required. A failed/reverted dispatch on the Ethereum Gateway is a normal outcome that can occur outside the relayer's control (e.g. due to gas issues or destination-side XCM execution failure), and the relayer only needs to submit the resulting proof, which they can legitimately obtain.

## Recommendation
Gate the reward payment (and ideally the order removal, or replace it with retry/slash logic) on `receipt.success`:
```rust
ensure!(receipt.success, Error::<T>::DeliveryFailed);
```
For the `false` branch, consider emitting a distinct event (e.g. `MessageDeliveryFailed`) and defining explicit handling (retry, refund, or removal without reward) instead of silently crediting the reward and discarding the order.

## Proof of Concept
1. A message is queued via `submit`, creating `PendingOrder { nonce, fee, .. }` with `fee > 0`: [3](#0-2) 
2. On Ethereum, the Gateway's dispatch of the inbound message fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`, provable via Merkle proof of transaction receipt inclusion.
3. Relayer calls the pallet's `submit_delivery_receipt` extrinsic with a `DeliveryReceipt { nonce, success: false, .. }` and valid proof.
4. `process_delivery_receipt` fetches `order`, sees `order.fee > 0`, calls `T::RewardPayment::register_reward` unconditionally, then removes `PendingOrders(nonce)` — paying reward for a failed delivery and permanently clearing the order: [4](#0-3) 
5. A unit test analogous to the existing test harness, but setting `success: false` in the constructed `DeliveryReceipt` and asserting the reward is still registered and the order is still removed, reproduces the issue (existing tests only cover the `success: true` case, per the emulated test at `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs` lines 408-419).

				);

			Self::deposit_event(Event::MessageDelivered { nonce });

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
