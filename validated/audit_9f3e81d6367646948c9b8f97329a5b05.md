### Title
ValidateMultiSign precompile double-counts a single signer's weight via ECDSA signature malleability, bypassing multisig threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x66`) is invoked by any smart contract to check whether a set of caller-supplied signatures satisfies an on-chain account's `Permission` threshold. Its de-duplication logic keys on the raw signature bytes instead of the recovered signer address, so a single real signature can be turned into two "different" signatures (via standard ECDSA malleability) that both recover to the same address and are each counted toward the threshold. This lets one signer's weight be counted twice (or more, bounded by `MAX_SIZE`), letting an attacker satisfy a multisig threshold that should require multiple independent approvers, using only one leaked/observed signature.

### Finding Description
`ValidateMultiSign.execute` iterates over the caller-supplied signature array, recovers each signer address, and accumulates `weight` per signature: [1](#0-0) 

The de-duplication check is:
```
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
This only skips counting a signature when the *exact byte sequence* `merge(recoveredAddr, sign)` has already been seen. If `recoveredAddr` has already been credited but the raw signature bytes differ (even though they recover to the same address), the code falls through past the `continue`, calls `MUtil.checkCPUTime()` (a CPU-budget check only, not a security gate), and then adds `weight` again for the same address — double-counting.

Standard ECDSA signature malleability lets anyone, without the private key, derive a second valid signature `(r, n-s, v')` from any known valid `(r, s, v)` for the same message/pubkey (`n` is the curve order). Given one leaked or observed 65-byte signature that recovers to signer `A`, an attacker can compute this malleable twin, which has different raw bytes but recovers to the same address `A`. Submitting both the original and its malleable twin in the `signatures` array causes `A`'s weight to be counted twice.

This contrasts with the correct pattern used elsewhere in the codebase, `TransactionCapsule.checkWeight`, which de-duplicates by the *recovered address* (`encode58Check(address)`), not by raw signature bytes, and explicitly rejects a repeat signer with "has signed twice!": [2](#0-1) 

The precompile is reachable by any unprivileged contract-caller: any smart contract can call this precompile with attacker-controlled `data` (address, permissionId, message, signature array), as exercised in the test harness that drives it directly with arbitrary signature lists: [3](#0-2) 

### Impact Explanation
On-chain contracts (custodial wallets, escrow, exchange/withdrawal contracts, DAOs) that rely on `ValidateMultiSign` to authorize an action gated by an account's multisig `Permission.threshold` can be tricked into approving an action with fewer independent signers than the threshold requires — e.g., a 2-of-2 or N-of-M permission can be satisfied by a single compromised/observed signature plus its malleable twin. This is a real authorization bypass leading to unauthorized account operations (fund transfers, permission changes acted upon by the calling contract) — a concrete "unauthorized account operation" per the validation criteria.

### Likelihood Explanation
High. No privileged access is required: any address can deploy or call a smart contract that invokes precompile `0x66` with arbitrary calldata, as this is a standard TVM precompile exposed to all TriggerSmartContract callers. Computing the ECDSA malleable counterpart of an already-known signature (e.g., one observed on-chain, in a prior authorized call, or leaked off-chain) is a pure arithmetic operation requiring no secret key material.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute` from the raw signature bytes to the recovered address only (mirroring `TransactionCapsule.checkWeight`), so that once an address has contributed weight, any further signature recovering to that same address — malleable or not — is skipped rather than falling through to `MUtil.checkCPUTime()` and re-adding weight.

### Proof of Concept
1. Deploy a contract that calls precompile `0x66` (`ValidateMultiSign`) with an account whose Active permission has threshold 2 and two keys, `key1` (weight 1) and `key2` (weight 1) — i.e. requires 2 independent signers.
2. Obtain (observe/leak) one valid signature `sig1 = key1.sign(hash)`.
3. Compute the ECDSA-malleable twin `sig1' = (r, n-s, 1-recId)` from `sig1` — this recovers to the same address as `sig1` but has different raw bytes.
4. Submit `signatures = [sig1, sig1']` to the precompile.
5. Per the loop logic at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1088-1106`, the first signature adds `key1`'s weight (1) and is recorded; the second recovers the same address but has different raw bytes, so `matrixContains(executedSignList, sign)` is false, the `continue` is skipped, and `key1`'s weight (1) is added again — `totalWeight` reaches 2, meeting the threshold of 2 using a single real signer's credential, without any signature from `key2`.
