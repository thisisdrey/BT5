### Title
Unbounded blocking body read in `JsonRpcServlet` allows slow-POST thread exhaustion, denying the HTTP/JSON-RPC API - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java`)

### Summary
`JsonRpcServlet.doPost` reads the entire request body by looping on `InputStream.read()` until EOF before doing any JSON-RPC processing. This loop has no read-timeout and no minimum throughput requirement, so it blocks the Jetty worker thread for as long as the client trickles bytes (or stops sending bytes without closing the socket). This is the same bug class as the referenced iperf advisory: a client sending less data than expected (or sending it arbitrarily slowly) causes the server-side handler to hang indefinitely waiting for the remainder, tying up server resources and preventing the server from servicing other requests.

### Finding Description
`readBody` is implemented as: [1](#0-0) 

It is invoked unconditionally at the top of `doPost` before any request validation: [2](#0-1) 

`JsonRpcServlet` runs on a plain Jetty `Server` created via `new Server(this.port)` with no explicit connector/idle-timeout configuration and only a maximum-size guard (`SizeLimitHandler`), not a rate/timeout guard: [3](#0-2) 

A search of the codebase found no `setIdleTimeout`/`idleTimeout` configuration anywhere, meaning the connector's default behavior applies and nothing in the servlet layer bounds how long `readBody`'s `while ((n = in.read(tmp)) != -1)` loop may block. An attacker can open a POST to `/jsonrpc` with a `Content-Length` (or chunked transfer) indicating a body larger than what is actually sent, and then send only a trickle of bytes (e.g., one byte every few seconds) or stop sending entirely while keeping the TCP connection open. The servlet thread executing `doPost` will remain blocked inside `readBody` for the entire duration, since the read loop only terminates on EOF (`-1`) or an I/O exception — neither of which occurs while the connection is idle-but-open.

This is structurally identical to the iperf bug: "a malicious or malfunctioning client can send less than the expected amount of data ... which can cause the server to hang indefinitely waiting for the remainder or until the connection gets closed... prevent[ing] other connections."

### Impact Explanation
Each such slow/partial POST occupies one Jetty request-handling thread indefinitely (bounded only by whatever default socket/idle timeout Jetty applies, which is not overridden and can be trivially reset by trickling a few bytes periodically — a classic Slowloris pattern). Because the standard Jetty thread pool is finite, a modest number of concurrent slow connections to the JSON-RPC endpoint can exhaust all available worker threads, making the node unable to serve legitimate JSON-RPC (and, if the pool is shared, other HTTP API) requests — i.e., "an API the node can no longer serve," one of the explicitly accepted impact categories. This does not require authentication, a signed transaction, or any special privilege — only network reachability to the JSON-RPC HTTP port.

### Likelihood Explanation
The JSON-RPC HTTP endpoint is typically exposed for wallet/dApp/exchange integrations and is reachable by any anonymous network client per the report's threat model ("API client"). No authentication or precondition beyond opening a TCP connection and issuing a partial/slow POST is required, making exploitation straightforward and repeatable (High likelihood for a Medium-severity availability issue), matching the CVSS vector of the source advisory (AV:N/AC:L/PR:N/UI:N/A:L).

### Recommendation
- Configure an explicit Jetty connector idle timeout (and/or a dedicated read timeout for request bodies) short enough to bound worst-case body read time, and ensure it cannot be indefinitely reset by trickling single bytes without an overall maximum body-read duration.
- Replace `readBody`'s unbounded blocking loop with a bounded-time / bounded-throughput read (e.g., using `Request.setAsyncTimeout`, `HttpConfiguration#setBlockingTimeout`, or Jetty's `getMinRequestDataRate`/`setMinRequestDataRate` to enforce a minimum request body arrival rate and reject slow bodies with `408 Request Timeout`).
- Apply the same protection to other servlets that block on `request.getReader()`/`getInputStream()` (e.g., `Util.getRequestValue`, and the many `doPost` handlers using `request.getReader().lines().collect(...)`), since they share the same unbounded-read pattern.

### Proof of Concept
1. Start a java-tron node with the JSON-RPC HTTP API enabled.
2. From an unauthenticated client, open a raw TCP connection to the JSON-RPC port and send:
   ```
   POST /jsonrpc HTTP/1.1
   Host: <node>
   Content-Type: application/json
   Content-Length: 1000000

   {"jsonrpc":"2.0","method":"eth_blockNumber","params":[]...
   ```
   but only send a few bytes of the declared 1,000,000-byte body, then send one additional byte every few seconds (or simply stop sending) while keeping the socket open.
3. Repeat this concurrently from a handful of connections.
4. Observe that the node's JSON-RPC worker threads become pinned inside `readBody` (`framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java:268-276`), and subsequent legitimate JSON-RPC/HTTP requests time out or are refused because the thread pool is exhausted.

**Uncertainty note:** I could not confirm the exact default idle-timeout value Jetty applies to the `new Server(port)` construction used in `HttpService.initServer()` (no explicit `setIdleTimeout` call exists anywhere in the indexed codebase), nor the exact size of the underlying Jetty thread pool, since these are runtime/library defaults not present in the repository source. Confirming the precise number of concurrent slow connections needed to exhaust the pool, and whether any Jetty default (e.g., `minRequestDataRate`) already partially mitigates this, would require runtime testing or reviewing the specific Jetty version's defaults, which is outside what the indexed repository content can confirm.

  private byte[] readBody(InputStream in) throws IOException {
    ByteArrayOutputStream buffer = new ByteArrayOutputStream();
    byte[] tmp = new byte[4096];
