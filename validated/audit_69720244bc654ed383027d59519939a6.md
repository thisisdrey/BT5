### Title
Protocol fee bypass on Imt/Nep245 tokens by splitting a multi-unit transfer across multiple TokenDiff intents - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives fees on `Nep245`/`Imt` tokens whenever the *per-intent* `amount <= 1`, but `TokenDiff::execute_intent` computes and collects this fee independently for each `TokenDiff` intent rather than on the aggregate negative delta for a token across the whole batch. An attacker can split a `-2` (or larger) delta on an Imt/Nep245 token into multiple `TokenDiff` intents each with `delta = -1`, causing the fee guard `amount > 1` to evaluate false on every intent and the total fee to be zero instead of `Pips::fee_ceil(protocol_fee, 2)`.

### Finding Description
The broken binding: fee credited to `fee_collector` for token `T` should equal `Pips::fee_ceil(protocol_fee, |Σ negative deltas of T across the batch|)`, but the code actually computes `Σ over intents of Pips::fee_ceil(protocol_fee, |delta_i|)` where each `delta_i` is evaluated in isolation.

In `contracts/defuse/core/src/intents/token_diff.rs`, `TokenDiff::execute_intent` iterates `self.diff` (a single `TokenDiff`'s own `BTreeMap<TokenId, i128>`) and for negative deltas computes: [1](#0-0) 
calling `Self::token_fee(token_id, amount, protocol_fee)`, whose guard is: [2](#0-1) 
`TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}` else `return Pips::ZERO`. This decision is made per `TokenDiff` intent, using only that intent's own delta for the token — not any batch-wide aggregate.

The engine dispatches intents one at a time with no cross-intent aggregation before fee computation: `Engine::execute_signed_intent` extracts the `DefuseIntents` and calls `intents.execute_intent`, which iterates `Vec<Intent>` and calls each intent's `execute_intent` independently: [3](#0-2) 
And across signed payloads in a batch, `execute_signed_intents` simply loops: [4](#0-3) 
Balances are only reconciled globally at `finalize()` for invariant checking, which happens after all fees have already been (under-)collected — it does not re-derive or correct fees.

Exploit: attacker holds ≥2 units of an Imt/Nep245 token in the Verifier. They construct a `MultiPayload` batch (or even a single signed `DefuseIntents` with multiple `TokenDiff` entries in its `intents: Vec<Intent>`) containing two `TokenDiff` intents, each with `diff = {imt_token: -1, other_token: +x}`. Each is executed by a separate call to `TokenDiff::execute_intent`, each sees `delta = -1`, `amount = 1`, and `Self::token_fee` returns `Pips::ZERO` both times (guard `amount > 1` is false). The aggregate effect on the Verifier's balance for that token is `-2`, but total fee collected is `0`, whereas a single `TokenDiff` with `delta = -2` would have hit the `amount > 1` branch and paid `fee_ceil(protocol_fee, 2)`.

None of the existing guards prevent this: `MultiPayload::verify`, nonce/salt checks, and `has_public_key` only validate authenticity and replay protection, not fee aggregation; `Deltas::finalize` only checks that overall balance changes are internally consistent (sum of all deltas across signer and fee_collector nets to what's actually moved), which is still satisfied even with zero fee — it's a balance-conservation check, not a fee-correctness check.

### Impact Explanation
This directly under-collects protocol fees owed to `fee_collector` on Imt/Nep245 token trades, matching the "protocol fees bypassed or over-collected" Critical category. Any account holding multiple units of an Imt/Nep245 token can repeatedly fragment their `TokenDiff` intents into `delta = -1` chunks to move arbitrarily large quantities of that token type while paying zero fee, at no cost beyond one extra intent (and, if desired, a couple of extra NEAR transactions/signatures) per unit. This is repeatable indefinitely across any Imt/Nep245 token and any account, systematically starving the fee collector on this token class.

### Likelihood Explanation
Preconditions are trivial and fully within an unprivileged attacker's control: they only need to hold ≥2 units of some Imt or Nep245 token in the Verifier (self-mintable/depositable via their own MT contract) and sign multiple ordinary `TokenDiff` intents — no privileged role, relayer key, or victim key is required. The attack is cheap (bounded by transaction/signature overhead, which is explicitly excluded from scope as a cost concern) and trivially repeatable.

### Recommendation
Aggregate net deltas per `TokenId` across all `TokenDiff` intents within the same `DefuseIntents`/signer-execution scope (and ideally across the whole batch for the same signer) before evaluating `token_fee`'s `amount > 1` guard, so the fee is computed on the true consolidated negative delta rather than on each individual intent's delta in isolation.

### Proof of Concept
`cargo test` (or `near-workspaces` sandbox) plan in the `contracts/defuse` test suite:
1. Deploy Verifier, deploy an MT contract, mint/deposit ≥2 units of an Imt/Nep245 token id `T` to attacker's Verifier balance, and set `protocol_fee` to a nonzero `Pips` value.
2. Sign a `DefuseIntents` (or two separate `MultiPayload`s) with two `TokenDiff` intents: `diff = {T: -1, other: +x}` each (using two distinct nonces if using separate payloads).
3. Call `execute_intents` with the batch.
4. Assert: `fee_collector`'s balance for `T` after execution is `0`.
5. Compare against expectation: `Pips::fee_ceil(protocol_fee, 2)` (nonzero for `protocol_fee > 0`), demonstrating `0 != Pips::fee_ceil(protocol_fee, 2)` — the fee-conservation equality is violated even though the attacker's net token movement of `-2` on `T` matches what a single `TokenDiff{T: -2}` would have produced (which *would* have paid the fee).
