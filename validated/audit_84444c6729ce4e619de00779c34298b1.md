## Finding: Legacy (non-hardened) Exchange AMM path can drive a Bancor-relay pool balance negative, creating an unbacked/insolvent exchange market

### Title
Non-hardened `ExchangeCapsule.transaction()` path allows negative/unbacked pool reserves due to floating-point AMM math with no solvency check - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
java-tron's `Exchange`/`ExchangeV2` feature is an on-chain bancor-relay AMM where users can swap between two listed tokens (or TRX) via `ExchangeTransactionContract`. The reserve balances (`firstTokenBalance`/`secondTokenBalance`) represent the pool's backing, analogous to Holdefi's collateral pool. The legacy (default, non-hardened) code path computes the swap output using floating-point `double` math and never verifies that the resulting reserve balances stay non-negative, unlike the "hardened" path which is gated behind an on/off dynamic property.

### Finding Description
`ExchangeCapsule.transaction()` computes the swap output via either the legacy `ExchangeProcessor` (double-based Bancor-relay formula using `Math.pow`) or the "hardened" `SafeExchangeProcessor` (BigDecimal-based, deterministic rounding), selected by the `hardenedCalc` flag: [1](#0-0) 

Critically, the invariant check that the new reserve balances must remain non-negative is only performed when `hardenedCalc` is `true`:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

Whether the hardened path is used is controlled by a chain-wide dynamic property `allowHardenExchangeCalculation()`, checked via `allowHarden()` in `AbstractExchangeActuator`: [3](#0-2) 

`ExchangeTransactionActuator.execute()` passes this flag straight through: [4](#0-3) 

The legacy `ExchangeProcessor` performs the Bancor-relay math with raw `double` arithmetic and truncation to `long`: [5](#0-4) 

The project's own test suite demonstrates that the legacy/double-based path and the hardened/BigDecimal path produce *different* results for the same inputs (`testStrictMath` explicitly asserts `assertNotEquals(anotherTokenQuant, result)` between the two math modes), confirming that floating-point rounding drift is real and non-trivial: [6](#0-5) 

Neither the actuator's `validate()` nor `execute()` bounds `anotherTokenQuant` against the actual `secondTokenBalance`/`firstTokenBalance` on the legacy path — only a lower bound (`tokenExpected`) is checked: [7](#0-6) 

If floating-point rounding in `exchangeToSupply`/`exchangeFromSupply` ever computes an output that exceeds the true remaining reserve (e.g., under extreme reserve-ratio imbalance, as exercised by the very asymmetric `sellBalance`/`buyBalance` values used in the project's own tests, such as `128L * 1024 * 1024 * 1024` vs `100_000_000_000000L`), the resulting `newFirstTokenBalance`/`newSecondTokenBalance` can go negative on the legacy path without being rejected, since the `hardenedCalc && (...)` guard is short-circuited to `false` when hardening is disabled.

### Impact Explanation
A negative/overdrawn reserve balance means the exchange pool's on-chain accounting no longer matches the tokens it actually holds — i.e., the market becomes "insolvent" in the same sense as the Holdefi report: later participants (injectors, withdrawers, or subsequent swappers) can no longer redeem their proportional share, and the earliest actor to exploit the rounding drift effectively extracts value that isn't backed by real reserves. This is a concrete unbacked-balance / fund-loss condition for other exchange participants, not merely a theoretical risk.

### Likelihood Explanation
Exploitability depends on: (1) `allowHardenExchangeCalculation` not yet being activated on the relevant chain (a real, plausible state prior to/absent the corresponding hard fork proposal), and (2) the reserve ratio and swap sizes being extreme enough to trigger floating-point rounding that flips the sign or magnitude of the computed reserve delta. The severity is bounded by these preconditions, making this a medium-likelihood, high-impact issue rather than a trivially/always-exploitable one. I could not fully verify from static inspection alone whether a concrete sellQuant/reserve combination reliably produces an overdraw beyond the visible rounding-drift test evidence — this would need targeted numeric fuzzing of `ExchangeProcessor.exchange()` against `SafeExchangeProcessor.exchange()` across extreme reserve ratios to confirm an actual sign-flip/overdraw case, which is beyond what can be conclusively proven through code reading alone.

### Recommendation
Enforce the non-negative reserve invariant unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, so the legacy path cannot commit an overdrawn/negative balance. Consider deprecating/removing the double-based `ExchangeProcessor` path entirely in favor of always using `SafeExchangeProcessor`, and add fuzz/differential tests comparing both processors across a wide range of skewed reserve ratios to detect any remaining rounding-driven overdraw before removing the legacy path.

### Proof of Concept
Conceptual reproduction (requires numeric confirmation via fuzzing, as noted above):
1. Create an `Exchange` with a highly asymmetric reserve ratio (e.g., `firstTokenBalance = 100_000_000_000000L`, `secondTokenBalance = 128L*1024*1024*1024`), mirroring `ExchangeProcessorTest.testExchange`.
2. On a chain where `allowHardenExchangeCalculation` is disabled (legacy default), repeatedly broadcast `ExchangeTransactionContract` swaps sized to probe the boundary where `Maths.pow`-based truncation in `ExchangeProcessor.exchangeFromSupply` rounds the output up relative to the true bonding-curve value.
3. If any swap's computed `buyTokenQuant` exceeds the actual remaining opposite-side reserve, `ExchangeCapsule.transaction()` will silently persist a negative `secondTokenBalance`/`firstTokenBalance` (since the `hardenedCalc` guard is skipped), leaving the pool under-collateralized for subsequent participants.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
```
