### Title
Unliquidatable "dead-band" debt positions from `debtFloorInUsd` × `maxLiquidable` contradiction — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two independent constraints that cannot be satisfied simultaneously for a class of positions: (1) `amountToRepay_` must be ≤ `debt * maxLiquidable` (a fraction < 100%), and (2) the remaining debt after repayment must be either exactly `0` or ≥ `debtFloorInUsd`. When `maxLiquidable < 1e18` and `debtFloorInUsd > 0` — the deployed configuration — any position whose debt is in `[floor, floor / (1 - maxLiquidable))` can never be liquidated: full repayment exceeds `maxLiquidable`, and every permitted partial repayment leaves a sub-floor remainder that reverts. Analogous to CVE-2016-8635, the attacker confines a value into a small subgroup (here, a dead band of debt sizes) from which the intended recovery mechanism (liquidation) cannot operate.

### Finding Description
In `Pool.liquidate`:

```solidity
// contracts/Pool.sol:567-579
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_), _debtTokenBalance - amountToRepay_);
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
``` [1](#0-0) 

With e.g. `maxLiquidable = 0.5e18` and `debtFloorInUsd = $100`, any liquidation repays at most 50% of the debt, so at least 50% always remains. If total debt is below `$200`, the remainder is necessarily `< $100` and non-zero, so `liquidate` always reverts — the position is permanently unliquidatable. `quoteLiquidateMax` dutifully returns the capped max, which still cannot satisfy the floor check.

Meanwhile, `DebtToken._mint` only requires the *total* debt to be ≥ `debtFloorInUsd` — it never enforces `debt ≥ floor / (1 - maxLiquidable)`: [2](#0-1) 

So an unprivileged user can open a position with debt anywhere in `(floor, floor/(1-maxLiquidable))` via the public `DebtToken.issue` entry point: [3](#0-2) 

The same contradiction exists in `DebtToken.repay` (partial repayment below floor reverts, though `repayAll` sidesteps it), so even the borrower can only exit in full — but the critical victim is the protocol/liquidators.

### Impact Explanation
Once such a position becomes unhealthy (collateral price decline), it is permanently unliquidatable: every possible `amountToRepay_` reverts. The underwater debt continues accruing interest and can never be removed through `Pool.liquidate`, producing bad debt that the protocol must absorb — the invariant "every unhealthy position is liquidatable" is broken. An attacker can cheaply open many such positions (Sybil accounts, each with minimal collateral and debt just above the floor) to scale the unrecoverable bad debt. This qualifies as protocol insolvency / permanent liveness failure of liquidation for a reachable class of positions.

### Likelihood Explanation
- Requires `maxLiquidable < 100%` and `debtFloorInUsd > 0`, which is the intended deployed configuration (both are governor-set parameters with dedicated tests exercising exactly these values).
- Attacker needs no privileged role: `issue` is permissionless; they only need collateral worth more than `floor / (1 - maxLiquidable)` of debt.
- The position becoming unhealthy requires collateral depreciation or debt growth via interest — inevitable for any marginal position; the attacker can mint maximally against the collateral factor to sit near the liquidation threshold.
- No modifier, reentrancy guard, pause flag, or `SynthContext` check prevents it; `liquidate` reverts on `PositionIsHealthy`, `AmountGreaterThanMaxLiquidable`, or `RemainingDebtIsLowerThanTheFloor` for every possible input.

### Recommendation
Reconcile the two constraints, e.g.:
- Allow full liquidation regardless of `maxLiquidable` when `debt - maxAllowed < debtFloorInUsd` (i.e., waive the cap when capping would strand sub-floor dust), or
- Enforce at mint time in `DebtToken._mint` that new debt satisfies `debtUsd ≥ debtFloorInUsd / (1e18 - maxLiquidable)`-equivalent bound (`remaining debt after a max liquidation is 0 or ≥ floor`), and/or
- In `liquidate`, treat a remainder `< debtFloorInUsd` as permission to repay the full balance rather than reverting.

### Proof of Concept
Hardhat-style, following existing test scaffolding in `test/Pool.test.ts`:

```ts
it('dead-band position can never be liquidated', async function () {
  // given: floor $3,000, maxLiquidable 50%
  await pool.updateDebtFloor(parseEther('3000'));
  await pool.updateMaxLiquidable(parseEther('0.5'));

  // attacker opens position with debt in dead band: $3,000 < debt < $6,000
  // (issue() only enforces debt >= floor; $4,000 debt passes _mint check)
  const debtBefore = await msEthDebtToken.balanceOf(alice.address);
  expect(debtBefore).eq(parseEther('1')); // $4,000 at ethPrice

  // collateral price drops -> position unhealthy
  await masterOracle.updatePrice(met.address, newMetPrice /* makes position unhealthy */);
  const { _isHealthy } = await pool.debtPositionOf(alice.address);
  expect(_isHealthy).false;

  // full repay exceeds maxLiquidable -> AmountGreaterThanMaxLiquidable
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, debtBefore, msdMET.address)
  ).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

  // max allowed repay (50%) leaves $2,000 < $3,000 floor -> RemainingDebtIsLowerThanTheFloor
  const maxRepay = debtBefore.wadMul ? debtBefore.div(2) : debtBefore.div(2);
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, maxRepay, msdMET.address)
  ).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

  // no valid amountToRepay exists -> position is permanently unliquidatable
});
```

Both test fixtures (`updateDebtFloor(3000)` and `updateMaxLiquidable(0.5e18)`) are already exercised separately in `test/Pool.test.ts:408-451`; combining them demonstrates the contradiction directly.
