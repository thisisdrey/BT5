### Title
Ethereum-side relayer reward silently truncates to zero for cheap commands, letting anyone submit real bridge-committed messages while underpaying the reward component of `Fee` - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
The BlueBerry `borrow()` bug lets an attacker repeatedly extract real value while the accompanying accounting term (`debtShare`) that should track the extraction rounds down to zero, because there is no check that the derived quantity is non-zero. The exact same "compute derived value via integer division, never check it isn't zero, then let the caller repeat the action for free" pattern exists in Snowbridge's outbound-queue fee calculation: `calculate_fee` derives the relayer-reward portion of the message fee via `checked_div` by the ETH/DOT `exchange_rate` and then truncates decimals, and this can legitimately compute to `0` even though every individual `PricingParameters` field (`fee_per_gas`, `rewards.remote`, `exchange_rate`, `multiplier`) is validated to be non-zero by `PricingParameters::validate`. Nothing in `validate()` (the `SendMessage` entry point used by every message submission, including ordinary XCM asset transfers) checks that the *computed* `Fee` is non-zero or above some floor, so an attacker can keep the reward component of `RemoteFeeAdjusted` at zero while still getting real commands committed into `Messages`/`MessageLeaves` for relaying to Ethereum.

### Finding Description
`calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`: [1](#0-0) 

computes:
```
fee = calculate_remote_fee(gas_used_at_most, fee_per_gas, reward)   // in wei
fee = FixedU128::from_inner(fee).saturating_mul(multiplier).checked_div(&exchange_rate).unwrap().into_inner()
fee = convert_from_ether_decimals(fee)   // integer division by 10^(18 - Decimals)
```

`convert_from_ether_decimals` does a plain integer `checked_div` truncation from 18-decimal wei precision down to the chain's native decimals (10 or 12): [2](#0-1) 

This is a floor-division rounding step with no "result must be non-zero" guard, structurally identical to the BlueBerry `share = (amount*totalShare).div(totalDebt)` step that produced `newShare == 0`. The test file already demonstrates the exact failure mode with realistic parameters: [3](#0-2) 

Note the test's own comment: *"Though none zero pricing params the remote fee calculated here is invalid which should be avoided"* — i.e., the maintainers were aware this can happen but the pallet ships without a guard against it.

`PricingParameters::validate()` only checks that the *inputs* are non-zero, never the *output* of `calculate_fee`: [4](#0-3) 

The fee computed here flows directly, unmodified and unchecked, into the `SendMessage::validate` entry point that every outbound message (including the primary path from ordinary user XCM transfers via `EthereumBlobExporter::deliver` and governance/system messages) uses to determine what the caller must pay: [5](#0-4) 

`deliver()` then unconditionally enqueues the message for commitment (Merkle-rooted into the header and relayed to Ethereum) regardless of what fee was actually charged upstream: [6](#0-5) 

Because governance can only tune the *raw* `PricingParameters` (`fee_per_gas`, `multiplier`, `exchange_rate`, `rewards.remote`) and not the derived, decimals-truncated result, any parameter set that happens to produce `fee.remote == 0` for a given `gas_used_at_most` band (as the existing test proves is reachable with entirely valid, non-zero inputs) means every message whose command falls in that gas band is committed to Ethereum with zero relayer-reward compensation baked into `CommittedMessage.reward`. `commit()` and `do_process_message()` never re-check the fee either — they just serialize whatever `reward` was computed and merkle-root it: [7](#0-6) 

### Impact Explanation
This falls squarely under the accepted "public underpriced work that degrades block production or stalls bridge processing" impact category. An unprivileged, ordinary user (any account that can send an XCM message that gets exported to Ethereum, i.e. normal asset-transfer traffic, no admin/governance/relayer/validator role needed) can repeatedly submit messages whose local weight fee is paid (so it isn't literally free block space) but whose **cross-chain relayer reward** — the actual economic incentive that funds delivery of the message to Ethereum — is zero. Since relayers are only compensated per the `reward` field embedded in `CommittedMessage`/consumed on the Ethereum gateway side, spamming such messages produces a growing backlog of committed messages that carry no incentive for any relayer to deliver, which can stall the bridge's outbound processing pipeline (message backlog grows unboundedly since `MaxMessagesPerBlock` still admits them) without any relayer volunteering to pay gas to deliver worthless-reward messages. This is analogous to draining a "reward vault" (the relayer incentive pool) for free by keeping the accounted reward at zero while the real committed work (and its downstream Ethereum gas cost obligation) proceeds anyway.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no attacker-controlled or malicious infrastructure (no malicious relayer/validator/collator/governance abuse) — only ordinary, permissionless message submission with a gas-used value that lands in the exact-truncation band, and the test suite already proves such a parameter combination is a normal, reachable, "valid" configuration, not a contrived edge case requiring governance misconfiguration.

### Recommendation
Add an explicit invariant check in `calculate_fee` (or immediately after it, in `validate()`), asserting `fee.remote != 0` (returning `SendError`/rejecting the message) whenever `PricingParameters::rewards.remote` and `fee_per_gas` are non-zero. Equivalently, apply `Rounding::Up` (as used elsewhere in the codebase, e.g. `sp_arithmetic::MultiplyRational`) for the `checked_div`/decimal-truncation step so that a nonzero pre-truncation value can never collapse to zero, or floor the minimum computed remote fee to `1` unit whenever the pre-truncation quantity is nonzero.

### Proof of Concept
The existing unit test already constitutes a proof of concept that the rounding-to-zero path is reachable with fully "valid" (per `PricingParameters::validate`) inputs: [3](#0-2) 
Given `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local:1, remote:1}`, `multiplier = 1/1`, and `gas_used = 250000`, `calculate_fee` returns `fee.remote == 0`. In production this occurs whenever the ETH/DOT `exchange_rate` × decimals-adjustment truncates the reward component below one native-currency unit for a given message's `gas_used_at_most`; an attacker submits repeated messages (e.g. cheap XCM commands) whose `GasMeter::maximum_gas_used_at_most` keeps them in that band, each of which is accepted by `validate()`, enqueued by `deliver()`, and committed by `do_process_message`/`commit()` with `reward = 0` recorded in `CommittedMessage`, at no incremental compensation cost to the attacker beyond the (unrelated) local weight fee.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {

			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}

			return Err(InvalidPricingParameters);
		}
		if self.rewards.remote.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);
