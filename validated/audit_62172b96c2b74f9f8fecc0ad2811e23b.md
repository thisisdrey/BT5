## Title
`DeleteAccount` with a non-existent `beneficiary_id` permanently burns the account's entire balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
The reported Gearbox bug is a missing validation on a fund-recipient parameter (`to`/beneficiary) that lets a caller irreversibly destroy their own funds by mistake. NEAR's `DeleteAccountAction` has the same structural flaw: `beneficiary_id` is only checked for *account-id format* validity, never for *existence*, and the resulting balance-refund receipt is a "refund" receipt whose failure mode is to burn the funds rather than fail the original transaction or bounce back.

### Finding Description
`action_delete_account` pays out the deleted account's remaining balance by pushing a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` — a system-predecessor "refund" receipt containing a single `Transfer` action to whatever `beneficiary_id` was supplied: [1](#0-0) 

`beneficiary_id` is only validated for syntactic correctness (a well-formed `AccountId`); nothing checks that the account actually exists.

When this refund receipt is later executed, `apply_action` computes `is_refund = receipt.predecessor_id().is_system()` and `implicit_account_creation_eligible = is_the_only_action && !is_refund`, which is **always `false` for refund receipts** — this is a deliberate anti-abuse design ("refunds don't automatically create accounts"): [2](#0-1) 

Because `implicit_account_creation_eligible` is `false`, `check_transfer_to_nonexisting_account` always falls into the error branch for any `beneficiary_id` that doesn't already exist as an account — even a syntactically valid NEAR-implicit or ETH-implicit account id: [3](#0-2) 

Finally, when a system-predecessor (refund) receipt's execution fails, the deposit is not returned to anyone — it is unconditionally added to `other_burnt_amount`: [4](#0-3) 

This exact behavior is documented as intentional in the refunds spec: *"If the execution of a refund fails, the refund amount is burnt."* [5](#0-4) 

So an ordinary signer who submits a `DeleteAccount` action (directly, or via a signed meta-transaction/`DelegateAction`) with a `beneficiary_id` that does not correspond to an existing account (e.g. a typo'd account name, or any not-yet-created account) permanently and irrecoverably burns their entire remaining account balance — precisely mirroring the Gearbox `to = address(0)` mistake, just without an equivalent "guard rail" check (`beneficiary_id must exist` / `beneficiary_id != account_id-that-cannot-receive`).

### Impact Explanation
This is a concrete, permanent loss of funds for the account owner: the entire remaining NEAR balance of the deleted account is burned (removed from circulation) rather than transferred or refunded to anyone. There is no recovery path once the `DeleteAccount` receipt and its refund receipt have executed. This satisfies the "permanent freezing/loss of funds" impact bar.

### Likelihood Explanation
The path is reachable by any ordinary, unprivileged account holder using a standard, documented action (`DeleteAccountAction`) — no special privileges, validator status, or malicious node/peer behavior are required. The mistake is easy to make (typo in beneficiary, using an account that was never created, or a relayer-submitted meta-transaction where the user only inspected the wrong field), and the protocol provides no warning, no dry-run existence check, and no fallback (e.g., refund to self/predecessor) — it silently burns funds on receipt failure.

### Recommendation
Add a beneficiary-existence check before allowing `DeleteAccountAction` to execute (or before generating the refund receipt), analogous to the report's suggested `to != address(0)` guard:
- Validate that `beneficiary_id` corresponds to an existing account (or is eligible for implicit-account creation even from a refund context) at the point `action_delete_account` is processed, and reject the action with a clear error (e.g. `BeneficiaryDoesNotExist`) instead of generating a refund receipt doomed to fail.
- Alternatively, change the failure semantics of the beneficiary refund receipt so that on `AccountDoesNotExist`, the balance is returned to the deleted account's actor/predecessor rather than burned, consistent with how ordinary deposit refunds behave for failed non-refund receipts.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance.
2. Sign and submit a transaction from `alice.near` containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent123.near" })`, where `nonexistent123.near` is a syntactically valid but never-created account.
3. `action_delete_account` removes `alice.near` and enqueues `Receipt::new_balance_refund("nonexistent123.near", alice_balance)`.
4. When that refund receipt executes, `check_account_existence`/`check_transfer_to_nonexisting_account` reject it with `AccountDoesNotExist` because `implicit_account_creation_eligible` is `false` for refund receipts.
5. Because the receipt's predecessor is `system` (a refund) and it failed, `alice_balance` is added to `other_burnt_amount` and permanently lost — confirmed by the existing test pattern for `test_delete_account_no_account`/`test_refund_on_send_money_to_non_existent_account` showing `AccountDoesNotExist` on transfers to non-existent accounts: [6](#0-5)

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
