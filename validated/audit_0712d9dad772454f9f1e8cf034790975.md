### Title
Permissionless dust deposits can exhaust a victim's `MAX_TOKENS_PER_USER` slots, blocking collateral top-ups and forcing liquidation - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol), [File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the OpenClaw report (unauthenticated sockets consuming a bounded resource before any validation), `DepositToken.deposit()` lets any EOA credit an arbitrary `onBehalfOf_` account before the account-level resource check happens. Every first-time deposit adds the token to `Pool.depositTokensOfAccount[victim]`, and `Pool.addToDepositTokensOfAccount` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` shared across deposit and debt tokens. An attacker can therefore fill a victim's slots with dust across all registered deposit tokens, after which every deposit or `msdTOKEN` transfer into a *new* token for that victim reverts.

### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` is permissionless and only requires `amount_ > 0`; it calls `_mint(onBehalfOf_, _deposited)` [1](#0-0) .
- `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance was previously zero [2](#0-1) .
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount >= 30` [3](#0-2) [4](#0-3) .
- `_transfer` applies the same add on first receipt, so plain `msdTOKEN` transfers to the victim also revert once saturated [5](#0-4) .
- A slot is only released when the token balance reaches exactly zero (`removeFromDepositTokensOfAccount`) [6](#0-5) . A victim whose position is partially locked by debt (`_revertIfLocked` / `unlockedBalanceOf`) cannot fully withdraw, so the slots cannot be freed while the position is undercollateralized [7](#0-6) .
- Debt tokens count toward the same cap: `DebtToken._mint` adds to `debtTokensOfAccount`, and leverage via `SmartFarmingManager`/`DebtToken.mint` also reverts once saturated [8](#0-7) .

The resource accounting happens *after* the state-consuming mint, exactly the same ordering flaw as the advisory: the "connection" (a list slot) is allocated before the cap check can reject it cheaply for the victim's benefit — the revert protects the set, not the victim.

### Impact Explanation
Temporary freezing of funds leading to loss via forced liquidation. Once saturated:
1. Neither the victim nor a third party can deposit collateral into a new deposit token on the victim's behalf (`deposit(..., victim)` reverts).
2. The victim cannot receive `msdTOKEN` transfers or open debt positions in new synthetics.
3. If the victim's health factor deteriorates, no one can top up collateral with a fresh deposit token; the victim's own existing-token balances are locked by debt, so slots cannot be freed. The position becomes liquidatable with no defense path — a direct availability/insolvency-adjacent loss to the victim and profit to the attacker acting as liquidator.

### Likelihood Explanation
- Attacker needs only dust amounts of each underlying registered in the pool and pays only gas + dust; underlying is returned to the victim's position (it even marginally improves their collateral), so cost is near zero.
- Feasibility depends on the deployed pool having enough distinct deposit tokens (plus any debt tokens the victim holds) to reach 30. Metronome deployments register multiple deposit tokens per pool; if `len(depositTokens) + len(victim's debt tokens) >= 30`, the attack is fully executable. If fewer tokens exist, the attacker can only partially fill the cap — still griefing, but not fully blocking. This is the main uncertainty: I could not confirm the exact registered-token count per live pool from the repo.
- No privileged role, oracle manipulation, or governance action is required; `deposit` is `whenNotPaused nonReentrant` only.

### Recommendation
Make the slot allocation opt-in or beneficiary-controlled:
- Only add to `depositTokensOfAccount` when `onBehalfOf_ == _msgSender()`, or require a per-account allowlist/`acceptDeposit` flag for first-time tokens; alternatively let any account call `removeFromDepositTokensOfAccount` for tokens with zero *locked* balance while keeping dust.
- Alternatively, allow `unlockedBalanceOf == 0`-with-debt accounts to evict zero-value slots, or exempt top-up deposits from the cap when they improve health (check the cap only for the initiator, not the beneficiary).

### Proof of Concept
Reproducible Hardhat sketch (against a fork with `N >= 30` registered deposit tokens):

```ts
// Attacker fills victim's slots with 1-wei deposits of each deposit token
const depositTokens: DepositToken[] = await getAllDepositTokens(pool); // >= 30
for (const dt of depositTokens.slice(0, 30)) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, victim.address); // dust, credited to victim
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// Any subsequent deposit of a *new* token to the victim reverts
const newDt = depositTokens[30];
await expect(newDt.connect(helper).deposit(parseEther('10'), victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim cannot free a slot while collateral is locked by debt:
await expect(depositTokens[0].connect(victim).withdraw(victimBalance, victim.address))
  .revertedWithCustomError(depositTokens[0], 'NotEnoughFreeBalance');

// Price moves down → victim is unhealthy → pool.liquidate(...) succeeds for attacker;
// no collateral top-up was possible meanwhile.
```

Note: the PoC's completeness depends on the target pool registering enough deposit tokens to reach the 30-slot cap; if the deployed set is smaller, combine with the victim's existing debt-token entries or reduce the effective cap accordingly.
