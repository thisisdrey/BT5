### Title
Unvalidated attacker-controlled array size in `ValidateMultiSign`/`BatchValidateSign` precompile input parsing can throw an uncaught `OutOfMemoryError`/`NegativeArraySizeException` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The go-bitfield advisory describes a DoS where a `size` parameter taken directly from untrusted input is used to allocate a bit array without validating it is non-negative/well-formed, causing an unhandled panic. The same bug class exists in java-tron's `PrecompiledContracts.extractBytesArray` / `extractBytes32Array` / `extractSigArray` helpers: an attacker-controlled length word from the precompile call data is used directly as an array-allocation size (`new byte[len][]`) with no upper bound in the legacy (non-`allowTvmSelfdestructRestriction`) code path, and no check at all against negative values in either path.

### Finding Description
`extractBytesArray` reads a length directly from the ABI-decoded `DataWord[] words` array and uses it, unchecked, to allocate a 2-D array: [1](#0-0) 
Likewise `extractBytes32Array` does the same for the address list: [2](#0-1) 

These are called from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. Bound checking on `sigArraySize`/`addrArraySize` (`> MAX_SIZE`) is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [3](#0-2) 
and [4](#0-3) 

In the legacy branch (`allowTvmSelfdestructRestriction()` disabled — the default/older behavior gated by hard fork configuration), `extractBytesArray` is invoked with a completely attacker-supplied `len = words[offset].intValueSafe()` before any size check, i.e. `new byte[len][]` is allocated first and only afterward is `signatures.length > MAX_SIZE` checked — but the allocation itself already happened by then. `intValueSafe()` clamps to `Integer` range but does not prevent negative values (if the underlying `DataWord` encodes a negative two's-complement value) or extremely large positive values (up to `Integer.MAX_VALUE`), both of which are exactly the class of "unusual/exceptional" size values the go-bitfield advisory calls out.

`ValidateMultiSign.execute` has no enclosing `try/catch` around the `extractBytesArray`/`extractSigArray` call site at all — only the later account/permission logic is wrapped in `try { ... } catch (Throwable t)`. A `NegativeArraySizeException` or `OutOfMemoryError` thrown from array allocation during argument parsing therefore propagates out of `execute()` uncaught by the precompile itself.

### Impact Explanation
If the exception thrown by the oversized/negative array allocation is not caught somewhere further up the TVM call stack (e.g., in the generic precompiled-contract invocation wrapper), it will surface as an unhandled exception during transaction execution, which can crash the node's transaction-processing thread or otherwise interrupt block application — a node crash/halt DoS reachable by any account able to submit a transaction that triggers a `CALL` to the `ValidateMultiSign` precompiled address. Even if partially caught elsewhere, allocating a huge back array (`new byte[Integer.MAX_VALUE][]`, ~16GB of references on 64-bit JVMs, or similar) is a resource-exhaustion primitive that can degrade or crash the node via `OutOfMemoryError`, which per the JVM's default behavior is often not safely recoverable and can bring down the entire process (all threads), not just the calling one.

### Likelihood Explanation
Reaching this code only requires an unprivileged account to submit or trigger a smart-contract `CALL` to the `ValidateMultiSign` precompile address with crafted calldata that sets the signature-array length word to a very large or negative 32-byte value — this is directly reachable from any TVM contract invocation, i.e., from any transaction a broadcaster can submit. The severity is somewhat mitigated by the fact that newer builds gate the safer path behind `allowTvmSelfdestructRestriction()`; if that flag is enabled network-wide, the size is checked before the vulnerable allocation only for the sigArraySize (BatchValidateSign checks both, ValidateMultiSign path via `extractSigArray` is safer since it doesn't allocate an array of variable per-signature length). However, whether `allowTvmSelfdestructRestriction()` is active by default on the current live chain configuration could not be confirmed from the available code/index, so the exact current-network exploitability is uncertain.

### Recommendation
Validate the parsed array length (`len`) in `extractBytesArray` and `extractBytes32Array` against a sane upper bound (matching `MAX_SIZE`) and against negativity, before allocating any array, regardless of the `allowTvmSelfdestructRestriction()` flag. Additionally wrap the full precompile `execute()` bodies (including argument-parsing helpers) in a `try/catch (Throwable)` that safely returns a failure result rather than letting `NegativeArraySizeException`/`OutOfMemoryError` propagate out of the precompiled-contract execution path, consistent with the defensive pattern already used elsewhere in the same file (e.g., `BatchValidateSign.execute`'s `try { return doExecute(data); } catch (Throwable t) { ... }` wrapper).

### Proof of Concept
Construct calldata for a `CALL` to the `ValidateMultiSign` precompiled contract address where:
1. `words[3]` (the offset word to the signatures array) points to a slot,
2. That slot's `DataWord` value encodes either a negative number (e.g., all `0xFF` bytes) or a very large positive number close to `Integer.MAX_VALUE / 32`.

With `allowTvmSelfdestructRestriction()` disabled, this value flows unchecked into `extractBytesArray(words, offset, rawData)`: [1](#0-0) 
`new byte[len][]` at line 404 either throws `NegativeArraySizeException` (negative `len`) or attempts a multi-gigabyte allocation (large `len`), both outside any local `try/catch` in `ValidateMultiSign.execute`, allowing the exception/OOM to propagate out of precompile execution.
