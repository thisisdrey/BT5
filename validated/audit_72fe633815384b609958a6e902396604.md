### Title
Unvalidated `level` parameter in `MerkleHash` precompile passed unchecked into native `librustzcashMerkleHash`, causing out-of-bounds read in the JNI/native layer - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `MerkleHash` precompiled contract, reachable from any TVM contract call, parses a `level` value directly from attacker-controlled calldata and forwards it—without any range or bounds validation—to the native `librustzcashMerkleHash` JNI call. This mirrors the root cause of CVE-2026-32882 in libheif: an index/stride value taken from untrusted input is used to address a fixed-size internal buffer/table without validating it against the buffer's real bounds, resulting in an out-of-bounds read across the trust boundary (there, C++ pixel planes; here, the native Rust/C++ librustzcash Merkle-hash internals invoked over JNI, which is not protected by the JVM's array bounds checking).

### Finding Description
`MerkleHash.execute()` computes `level` purely from user-supplied `data` via `parseInt(data)` (which just reads the first 32 bytes and calls `intValueSafe()`), and passes it straight into `JLibrustzcash.librustzcashMerkleHash(new MerkleHashParams(level, left, right, hash))` with no upper- or lower-bound check: [1](#0-0) 

Compare this to the same underlying primitive `librustzcashMerkleHash` used inside `VerifyProof.insertLeaves()`/static initializer, where `level` is always constrained to `0..32` by the surrounding Java loop bounds: [2](#0-1) [3](#0-2) 

The `MerkleHash` precompile is the only call site that lets an unprivileged caller supply the `level`/`depth` value directly with no clamping. The JNI wrapper (`JLibrustzcash.librustzcashMerkleHash`) forwards the raw depth to native code: [4](#0-3) 

Java's own bounds checking only protects the `byte[]` arguments (`left`, `right`, `hash`, each fixed at 32 bytes) that are copied via `System.arraycopy`—these are safe. The vulnerability is in the `depth`/`level` integer itself: this value is documented and used elsewhere (e.g., the 32-level `UNCOMMITTED` Merkle tree construction) as an index into fixed-size internal tables (in-tree "empty root" tables typically sized 32–62 entries in the native Zcash Merkle-hash implementation). Once execution crosses into native code via JNI, out-of-bounds indexing is not caught by the JVM and can read (or in some native implementations, write) adjacent native heap memory — exactly the same bug class as the libheif report: use of an untrusted/unvalidated index or stride against a buffer whose true bounds differ from what the index assumes.

### Impact Explanation
Because the `MerkleHash` precompile is directly reachable by any contract deployer or unprivileged transaction sender via a single TVM `CALL` (no special permissions/whitelisting required, unlike some other Sapling precompiles gated behind `checkAllowShieldedTransactionApi` at the Wallet layer — this precompile is invoked purely through TVM opcode dispatch), an attacker can supply an arbitrary 32-byte `level` value (e.g., a huge or negative integer) with each invocation. If the underlying native implementation does not itself re-validate `depth` before indexing its internal constant tables, this results in an out-of-bounds heap read in the node's native memory space. Depending on the native implementation's behavior, this can:
- Crash the node process (denial of service / potential chain halt across nodes that receive and execute the same contract call), or
- Leak adjacent native heap bytes into the returned hash output, which becomes part of the precompile's return data and can be embedded in transaction execution results/logs — an information disclosure vector.

This qualifies as a High-severity, reachable analog: an anonymous contract caller can trigger it with a single deployed contract and one `CALL`, no consensus/witness privilege needed.

### Likelihood Explanation
High. No authentication or special permission is required to invoke a TVM precompile; any address can deploy a small contract that performs a low-level `STATICCALL`/`CALL` to the `MerkleHash` precompile address with crafted calldata setting `level` to an out-of-range value (e.g. `0xFFFFFFFF` or a large positive int like `1000000`). The precompile performs no validation before invoking native code, so the vulnerable path is trivially and repeatably reachable from mainnet by any user, unlike the Sapling proof precompiles which require the shielded-transaction feature switch and structurally-larger payloads with more argument checks.

### Recommendation
Add explicit bounds validation of `level` in `MerkleHash.execute()` before calling into native code — mirroring the `0 <= level < 32` (or whatever the native table's real bound is) constraint already enforced implicitly by the loop-bounded call sites in `VerifyProof`. Reject out-of-range values by returning a failure/zero result rather than forwarding untrusted integers into the JNI boundary. Additionally, audit all other `JLibrustzcash` call sites and the native `librustzcashMerkleHash` implementation itself to ensure defense-in-depth validation of `depth` server-side (native), not just relying on Java call-site invariants.

### Proof of Concept
1. Deploy a minimal contract (or use an existing generic proxy-call contract) that performs a `STATICCALL`/`CALL` to the `MerkleHash` precompile's fixed address.
2. Craft calldata: first 32 bytes = a large/negative `level` (e.g. `0x00000000000000000000000000000000000000000000000000000000FFFFFF` or a negative two's-complement value), followed by 32 bytes for `left` and 32 bytes for `right`.
3. Broadcast the transaction (any account with minimal TRX for energy can do this — no special permission needed).
4. Observe: `PrecompiledContracts.MerkleHash.execute()` at [5](#0-4)  calls `JLibrustzcash.librustzcashMerkleHash` with the attacker-chosen `level` unchecked; depending on native table bounds this either crashes the node (energy-metered execution reaching into native code with no Java-side safety net) or returns a hash value derived from out-of-bounds native memory, which is then returned as the precompile's output and can be inspected via the transaction's execution result.

Note: I was unable to inspect the native (Rust/C++) implementation of `librustzcashMerkleHash` itself (native library source is outside this repository's indexed Java sources), so I cannot confirm from first principles the exact internal table size or whether the native code performs its own bounds check. This is stated as an assumption based on: (a) the value's use as a depth/level index into a fixed Merkle-tree table elsewhere in the codebase (bounded to 32), and (b) the complete absence of any bounds check specific to this one reachable call site. A Devin session with access to the native library sources (if vendored) or the ability to build/run the node would be needed to fully confirm exploitability.

    @Override
    public Pair<Boolean, byte[]> execute(byte[] data) {
      byte[] left = new byte[32];
      byte[] right = new byte[32];
      byte[] hash = new byte[32];
      boolean res = true;
      try {
        int level = parseInt(data);
        System.arraycopy(data, 32, left, 0, 32);
        System.arraycopy(data, 64, right, 0, 32);
        JLibrustzcash.librustzcashMerkleHash(
            new LibrustzcashParam.MerkleHashParams(level, left, right, hash));
      } catch (Throwable any) {
        res = false;
        logger.info("Compute MerkleHash failed:{}", any.getMessage());
      }
      if (res) {
        return Pair.of(true, hash);
      } else {
        return Pair.of(false, EMPTY_BYTE_ARRAY);
      }
    }

    private int parseInt(byte[] data) {
      byte[] bytes = parseBytes(data, 0, 32);
      return new DataWord(bytes).intValueSafe();
    }
  }
