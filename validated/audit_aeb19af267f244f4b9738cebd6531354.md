### Title
Uncontrolled injection of token entries into a victim's position set via dust `DepositToken` transfers lets an attacker block the victim's deposits, borrows and withdrawals — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The JS prototype-pollution bug class is "attacker writes attacker-chosen keys into an object/map the victim relies on, thereby corrupting its behavior". Metronome's analog is `MappedEnumerableSet`: `Pool` tracks, per account, the set of deposit/debt tokens in `depositTokensOf[account]` / `debtTokensOf[account]`, and iterates that set when computing `debtPositionOf`, when enforcing `MAX_TOKENS_PER_USER`, and on deposit/withdraw/swap/liquidate paths. Because `DepositToken.transfer`/`transferFrom` call `Pool` to add the token to the *recipient's* set, an attacker can "pollute" a victim's per-account object with keys the victim never chose — exactly like `obj[k]=v` with a user-controlled `k`. [1](#0-0) 

### Finding Description
- `MappedEnumerableSet._add` appends a token to `set._ofAddress[_key]._values` under the account key. The key is derived from the *recipient* of a `DepositToken` transfer, while the *value* (which token) is attacker-controlled — the attacker can hold dust positions in every deposit token the pool lists. [2](#0-1) 
- `Pool` caps the number of tokens a user may hold (`MAX_TOKENS_PER_USER`) and iterates the user's token sets in position/debt accounting (`Pool.debtPositionOf`, `depositOf`, `debtOf` and every mint/burn/withdraw/swap path that snapshots or updates the position). Once the set is full, any subsequent action that would add a *new* token reverts. [3](#0-2) 
- Attack path (pure EOA, no privileged role):
  1. Attacker deposits a dust amount of collateral into `Pool.deposit` for each of the N whitelisted `DepositToken`s (or receives them freely — deposit tokens are transferable).
  2. Attacker calls `depositToken.transfer(victim, 1 wei)` for each token, causing `Pool` to `_add` each token to `depositTokensOf[victim]` until the set reaches `MAX_TOKENS_PER_USER`.
  3. Victim's calls to `deposit`/`mint`/any path that registers a new token now revert; loops over the polluted set also run with inflated gas. The dust entries only disappear via swap-and-pop when the victim withdraws the dust balance — i.e., the victim must first identify and unwind attacker-injected entries. [4](#0-3) 
- No guard stops this: `SynthContext._msgSender` correctly resolves the EOA through `Operator.execute`, transfers are permissionless, `onlyIfCanMint`-style modifiers gate the *action* not the set-write, and neither `ReentrancyGuardTransient` nor pause flags (unless fully shut down) prevent plain ERC20-style transfers of deposit shares. [5](#0-4) 

### Impact Explanation
Temporary freezing of the victim's funds: once the victim's token set is saturated with attacker-chosen dust entries, deposits of new collateral, new borrows and (on pools where withdraw iterates/validates the full position) withdrawals revert until the victim manually removes the injected tokens. The attacker spends only dust × N and gas; every user of the pool can be targeted, and the attack is repeatable after cleanup.

### Likelihood Explanation
High feasibility: deposit tokens are freely transferable by design, dust costs are negligible, and no authorization is required to credit tokens to another account's set. The limiting factor is whether `MAX_TOKENS_PER_USER` is configured low enough to be reached cheaply and whether withdrawal paths remain usable for cleanup — I could not fully confirm the exact cap value and every revert site in `Pool.sol` within the indexed source, so the precise blast radius (which functions revert vs. merely cost more gas) should be confirmed on a fork.

### Recommendation
- Only add a token to an account's set when the *account itself* initiated the position (i.e., on deposit/mint paths), not on incoming `transfer`/`transferFrom`, or require opt-in registration.
- Alternatively, keep a separate "transferred-in" balance that does not count toward `MAX_TOKENS_PER_USER`, or allow set entries to be removed by anyone once the balance is zero.
- At minimum, ensure `withdraw`/`seize` cleanup paths never iterate the unbounded set in a way that can be pushed over gas limits.

### Proof of Concept
Hardhat/Foundry fork outline:
```solidity
// fork mainnet, use deployed Pool + DepositTokens
address victim = makeAddr("victim");
// 1. seed attacker with one wei of each depositToken share
for (uint i; i < pool.getDepositTokens().length; ++i) {
    IDepositToken dt = pool.getDepositTokens()[i];
    vm.prank(attacker);
    dt.transfer(victim, 1); // attacker previously deposited dust for each
}
// 2. victim's next deposit of a NEW token reverts (set at MAX_TOKENS_PER_USER)
vm.prank(victim);
underlying.approve(address(pool), amount);
vm.expectRevert(); // "max-tokens-per-user"-style revert
pool.deposit(newDepositToken, amount);
```
Note: the exact revert condition and whether `withdraw` remains functional for cleanup must be verified against the deployed `Pool` implementation on a fork, since the capped-iteration details in `Pool.sol` were only partially visible in the index.

```text
    function _remove(AddressSet storage set, address _key, address value) private returns (bool) {
        // We read and store the value's index to prevent multiple reads from the same storage slot
        uint256 valueIndex = set._ofAddress[_key]._indexes[value];

        if (valueIndex != 0) {
            // Equivalent to contains(set, value)
            // To delete an element from the _values array in O(1), we swap the element to delete with the last one in
            // the array, and then remove the last element (sometimes called as 'swap and pop').
            // This modifies the order of the array, as noted in {at}.

            uint256 toDeleteIndex = valueIndex - 1;
            uint256 lastIndex = set._ofAddress[_key]._values.length - 1;

            if (lastIndex != toDeleteIndex) {
                address lastvalue = set._ofAddress[_key]._values[lastIndex];

                // Move the last value to the index where the value to delete is
                set._ofAddress[_key]._values[toDeleteIndex] = lastvalue;
                // Update the index for the moved value
                set._ofAddress[_key]._indexes[lastvalue] = valueIndex; // Replace lastvalue's index to valueIndex
            }

            // Delete the slot where the moved value was stored
            set._ofAddress[_key]._values.pop();

            // Delete the index for the deleted slot
            delete set._ofAddress[_key]._indexes[value];
```
