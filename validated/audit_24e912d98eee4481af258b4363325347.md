### Title
Unprivileged DoS via dust deposit-token transfers filling `MAX_TOKENS_PER_USER`, blocking victim from opening new collateral or debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The original report (CVE-2020-14453) is a denial of service caused by unrestricted read/socket operations. The Metronome analog is a permissionless griefing vector that denies a victim the ability to open new positions: `Pool` tracks each account's deposit tokens and debt tokens in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30`, and any addition beyond that reverts with `UserReachedMaxTokens` (`Pool.sol:143-148`). Because `DepositToken._transfer` and `DepositToken._mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` when a recipient's balance moves from zero (`DepositToken.sol:486-488`, `DepositToken.sol:518-520`), an attacker can force-fill a victim's 30 slots — at dust cost — via `transfer()` of the pool's deposit tokens or `deposit(amount, onBehalfOf_=victim)`. Once the victim's combined `debtTokensOfAccount.length + depositTokensOfAccount.length` reaches 30, every subsequent `DebtToken` mint/issue (which calls `addToDebtTokensOfAccount`) and every `deposit`/`transfer` into a *new* collateral type reverts, freezing the victim's ability to add new collateral or mint new synthetics.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` enforces `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) < 30` on both `addToDebtTokensOfAccount` and `addToDepositTokensOfAccount` (`Pool.sol:143-148`, `Pool.sol:204-220`).
- `DepositToken._transfer` adds the token to the recipient's account list whenever `balanceOf[recipient] == 0`, with no opt-in and no minimum amount (`DepositToken.sol:498-525`).
- `DepositToken.deposit(amount, onBehalfOf)` allows depositing for an arbitrary `onBehalfOf_`, minting deposit tokens to the victim and triggering the same list insertion (`DepositToken.sol:211-237`, `DepositToken.sol:469-488`).
- Therefore an attacker holding/buying tiny amounts of each deposit token in a pool can push dust to the victim until the cap is hit. There is no `minimum` check, no consent mechanism, and the removal path (`removeFromDepositTokensOfAccount`) only fires when the balance reaches exactly zero, so the victim must actively send the dust away slot-by-slot to recover — and the attacker can re-grief.
- Debt issuance is equally blocked: `DebtToken.issue/mint` calls `pool.addToDebtTokensOfAccount(account_)` when the account's debt balance transitions from 0 (`DebtToken.sol`), which reverts once the combined list is full.

### Impact Explanation
Liveness/temporary freezing of funds: the victim cannot deposit additional collateral types nor mint/issue any new synthetic debt token while their list is saturated. If the victim is approaching liquidation, they cannot add a *new* collateral to heal their position — only existing listed tokens — so an attacker can force-liquidate positions that could otherwise have been saved, or permanently block a fresh account from ever opening a position in that pool. Recovery requires the victim to spend gas clearing each dusted slot (transfer/withdraw to zero), and the attacker can cheaply re-fill slots, making the freeze effectively persistent for as long as the attacker is willing to spend dust.

### Likelihood Explanation
- Fully unprivileged: any EOA calls `DepositToken.transfer`/`deposit(onBehalfOf_)` — public entry points.
- Cost is negligible: dust amounts (1 wei of each deposit token) across at most 30 tokens; flash-funded if desired.
- No privileged role, oracle manipulation, or timing assumption required. The cap and the unconditional `addToDepositTokensOfAccount` call are both present in the deployed implementation.
- Limitation: it does not steal funds directly; it blocks new position actions and can prevent adding new collateral during liquidation risk (temporary freezing / forced liquidation enabler).

### Recommendation
- Do not add a deposit token to the recipient's account list on `transfer`/`seize` for balances the recipient never opted into, or track "position tokens" (debt + collateral the account deposited itself) separately from transferable balance.
- Alternatively, exempt zero-value/dust additions, require a minimum amount for list insertion, or allow the account to remove entries itself (a public `removeMyToken(address token)` that verifies `balanceOf == 0`/opt-out semantics).
- Consider making `deposit` to `onBehalfOf_` skip list insertion when `onBehalfOf_ != msg.sender`, or handle health checks lazily so unsolicited tokens don't count against `MAX_TOKENS_PER_USER`.

### Proof of Concept
Hardhat sketch (fork against deployed `Pool` + `DepositToken`s):

```ts
// pool: deployed Pool; depositTokens: >=1 deposit token(s) registered in pool
const victim = await ethers.Wallet.createRandom().connect(provider)
// ensure victim has no position yet
expect(await pool.getDepositTokensOfAccount(victim.address)).to.be.empty

// Attacker deposits a tiny amount of each collateral for itself, then
// transfers 1 wei of each msdTOKEN to the victim (or deposits directly
// with onBehalfOf_ = victim) until the victim hits MAX_TOKENS_PER_USER.
const max = await pool.MAX_TOKENS_PER_USER() // 30
for (const dt of depositTokenList) {
  await underlying.approve(dt.address, amount)
  await dt.deposit(amount, attacker.address)      // mint dust to attacker
  await dt.transfer(victim.address, 1)            // forces addToDepositTokensOfAccount(victim)
}
// combine debt tokens too if fewer than 30 deposit tokens exist
const tokensOf = (await pool.getDepositTokensOfAccount(victim.address)).length
             + (await pool.getDebtTokensOfAccount(victim.address)).length
expect(tokensOf).to.eq(max)

// Victim can no longer open a new collateral position in an unused token:
await expect(newDepositToken.deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// Nor mint/issue a new synthetic debt:
await expect(newDebtToken.issue(amount, victim.address)) // via Pool path
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Key assertions: the attacker's 1-wei `transfer` triggers `addToDepositTokensOfAccount` (`DepositToken.sol:518-520`), the cap check reverts (`Pool.sol:143-148`), and the victim's `issue`/`deposit` on any token not already in their list permanently reverts until slots are manually cleared.
