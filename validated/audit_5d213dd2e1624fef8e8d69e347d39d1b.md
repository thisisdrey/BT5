### Title
Redundant recomputation of `total_prepaid_send_fees` over the whole `action_receipt.actions()` inside `apply_delegate_action` over-burns gas when a receipt contains multiple `Delegate`/`DelegateV2` actions - ([File: runtime/runtime/src/actions.rs])

### Summary
`apply_delegate_action` computes `prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())` using the *entire* outer receipt's action list rather than only the send fees attributable to the specific `Delegate` action currently being processed. `total_prepaid_send_fees` sums the inner send fees of every `Delegate`/`DelegateV2` entry found in that list, so if the receipt contains more than one delegate action, this same aggregate sum is recomputed and burnt again on every invocation of `apply_delegate_action` for that receipt.

### Finding Description [1](#0-0) 

`total_prepaid_send_fees` in `config.rs` iterates over the given `actions` slice and, for every `Delegate`/`DelegateV2` entry found, adds the send fees of that delegate's *inner* actions; non-delegate entries contribute `ParameterCost::ZERO`: [2](#0-1) 

In `apply_delegate_action`, this function is called with `action_receipt.actions()` - the full action list of the *outer* receipt being applied - not the single `Delegate` action currently being processed. Since a chunk's `apply_action` loop dispatches to `apply_delegate_action` separately for each `Delegate`/`DelegateV2` entry in that same action list, if the receipt contains N delegate actions (`D1..Dn`), each with own inner-action send-fee cost `c1..cn`, then every one of the N invocations recomputes `c1+c2+...+cn` and adds the *entire sum* to `result.gas_burnt`/`result.gas_used`, rather than only its own `ci`. The result is that the receipt burns `N*(c1+...+cn)` gas for send fees instead of the correct `(c1+...+cn)` that was actually purchased/reserved when the outer transaction was converted to a receipt via `tx_cost`/`calculate_tx_cost`, which computes this same total exactly once.

This breaks the value-conservation invariant: `result.gas_burnt` accumulated across the receipt's action processing can exceed the gas that was reserved for the receipt at conversion time, which is used later for refund computation.

### Impact Explanation
If reachable, this causes the relayer's `gas_burnt` for the receipt to diverge from the gas that was actually purchased from its balance at transaction conversion, which corresponds to the "double-charged (fund freeze)" scenario named in the question: gas beyond what was reserved gets burnt, and downstream refund arithmetic that assumes `gas_burnt <= prepaid` gas could hit a checked-subtraction/overflow error. That class of error is treated as a `RuntimeError` in the runtime, which is a candidate for a shard-halting panic under the project's severity categories, not merely economic loss.

### Likelihood Explanation
This is only exploitable if a single receipt/transaction can legally contain more than one `Delegate`/`DelegateV2` action at the top level (nested delegates are excluded by the `NonDelegateAction` typing of a `DelegateAction`'s own `actions` field, so this cannot be triggered by nesting). I was not able to confirm within the available tool budget whether `action_validation.rs` enforces "at most one Delegate action per receipt/transaction." I found strong indications that this file contains substantial delegate-specific validation logic (60 matches for delegate-related terms) but could not read its contents before running out of iterations. **This precondition is unverified** and is essential to determining exploitability: if the validation layer already restricts a transaction/receipt to a single `Delegate` action, this finding does not produce any observable divergence (N=1, so the "sum over the list" and "sum for this delegate" coincide) and the bug is latent/non-exploitable.

### Recommendation
Regardless of whether the precondition is currently blocked, the code should not rely on an implicit invariant (single Delegate action per receipt) that isn't visibly enforced at the call site. `apply_delegate_action` should compute prepaid send fees only for the specific `delegate_action` it is applying (e.g., using `delegate_action.get_actions()` and `delegate_action.receiver_id()` directly, mirroring how `total_prepaid_send_fees`'s recursive-per-delegate logic already isolates a single delegate's cost), instead of re-deriving the aggregate over the whole `action_receipt.actions()` on every invocation. This makes the accounting correct independent of whether multiple delegates in one receipt are otherwise permitted, and removes reliance on an unstated cross-module invariant.

### Proof of Concept
Not provided - I could not confirm within this investigation whether the runtime's action/receipt validation permits multiple `Delegate`/`DelegateV2` actions in a single outer `ActionReceipt`. A definitive Rust unit/integration test would need to:
1. Check `runtime/runtime/src/action_validation.rs` for any check limiting the number/position of `Delegate` actions per receipt/transaction.
2. If unrestricted, construct a transaction with actions `[Delegate(A), Delegate(B)]` from two independently signed `SignedDelegateAction`s, submit it, and assert `result.gas_burnt` for the receipt equals `c_A + c_B` (the correct single-count sum) rather than `2*(c_A + c_B)`, and compare the relayer's pre/post balance delta against the expected reserved amount from `tx_cost`.

Given the unresolved precondition, I cannot assert this as a confirmed, exploitable vulnerability without further verification of `action_validation.rs`.

pub fn total_prepaid_send_fees(
    config: &RuntimeConfig,
    actions: &[Action],
) -> Result<ParameterCost, IntegerOverflowError> {
    let mut result = ParameterCost::ZERO;
    for action in actions {
        use Action::*;
        let delta = match action {
            Delegate(signed_delegate_action) => {
                let delegate_action = &signed_delegate_action.delegate_action;
                let sender_is_receiver = delegate_action.sender_id == delegate_action.receiver_id;

                total_send_fees(
                    config,
                    sender_is_receiver,
                    &delegate_action.get_actions(),
                    &delegate_action.receiver_id,
                )?
            }
            DelegateV2(signed_delegate_action) => {
                let delegate_action =
                    VersionedDelegateActionRef::from(&signed_delegate_action.delegate_action);
                let sender_is_receiver =
                    delegate_action.sender_id() == delegate_action.receiver_id();

                total_send_fees(
                    config,
                    sender_is_receiver,
                    &delegate_action.get_actions(),
                    delegate_action.receiver_id(),
                )?
            }
            _ => ParameterCost::ZERO,
        };
        result = result.checked_add_result(delta)?;
    }
    Ok(result)
}
