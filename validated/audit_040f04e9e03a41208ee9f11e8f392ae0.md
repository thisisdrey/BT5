### Title
Gateways wrap and strand user funds when `Pool.depositTokenOf` returns `address(0)` — missing zero-address check silently no-ops the final deposit - ([File: contracts/NativeTokenGateway.sol], also `contracts/VesperGateway.sol`)

### Summary
Both user-facing gateways look up a `DepositToken` from an attacker/user-supplied `pool_` via `pool_.depositTokenOf(underlying)` and never verify the returned address is non-zero. In Solidity, a high-level call to an address with no code succeeds silently, so `deposit()` on `address(0)` is a no-op. The wrapped/minted collateral remains trapped inside the gateway contract with no user-facing recovery path — the same bug class as CVE-2024-36953 (unchecked `kvm_get_vcpu_by_id()` NULL result driving invalid behavior on attacker-supplied input).

### Finding Description
`NativeTokenGateway.deposit` checks only that `pool_` is registered, then wraps the caller's native asset and resolves the deposit token without validation: [1](#0-0) 

```solidity
nativeToken.deposit{value: msg.value}();
IDepositToken _depositToken = pool_.depositTokenOf(nativeToken);
nativeToken.safeApprove(address(_depositToken), 0);
nativeToken.safeApprove(address(_depositToken), msg.value);
_depositToken.deposit(msg.value, _msgSender()); // no-op if _depositToken == address(0)
```

`depositTokenOf` is a plain mapping keyed by `underlying` (set in `addDepositToken`, deleted in `removeDepositToken`), so any underlying that isn't a listed collateral returns `address(0)`: [2](#0-1) 

There is no `DepositTokenDoesNotExist`-style check here (unlike `Pool.liquidate`/`swap`, which validate token parameters via `onlyIfDepositTokenExists`/`onlyIfSyntheticTokenExists`): [3](#0-2) 

The identical pattern exists in `VesperGateway.deposit` (line 61–64) and `VesperGateway.withdraw` (line 79–83), where `vToken_` is fully attacker/user-chosen: [4](#0-3) 

### Impact Explanation
Any caller of `NativeTokenGateway.deposit` on a registered pool that does **not** list `nativeToken` (WETH/etc.) as collateral will have their native tokens wrapped and permanently stranded in the gateway: the approve targets `address(0)` and the final `deposit()` call to `address(0)` (an EOA) returns success, so the transaction does not revert. The funds are not credited to any position (`depositTokensOfAccount` never updates), and the only escape is a governor `TokenHolder.sweep` — i.e., permanent freezing of user funds absent governance rescue. In `VesperGateway`, the same applies to minted vTokens for any non-listed `vToken_`.

### Likelihood Explanation
Reachable by any unprivileged EOA or contract through public entry points (direct call or via `Operator.execute` meta-transactions, since the gateway uses `SynthContext._msgSender()`). It requires only that the user selects a registered pool missing that collateral — e.g., a newly added pool without the WETH listing, a pool after `removeDepositToken` (which only requires `totalSupply == 0`), or a wrong `vToken_` argument. No privileged actor, oracle manipulation, or timing is needed; the transaction itself succeeds and the loss is immediate.

### Recommendation
After `pool_.depositTokenOf(...)` in `NativeTokenGateway.deposit`/`withdraw` and `VesperGateway.deposit`/`withdraw`, revert if the result is `address(0)` (e.g., `if (address(_depositToken) == address(0)) revert DepositTokenDoesNotExist();`), or reuse the pool's existing `onlyIfDepositTokenExists`-style validation before pulling user funds — mirroring the upstream fix that added a NULL check after `kvm_get_vcpu_by_id()`.

### Proof of Concept (Foundry sketch)
```solidity
// PoolRegistry registers `pool` (a real Pool with no WETH deposit token added).
NativeTokenGateway gw = new NativeTokenGateway(poolRegistry, weth);
assertTrue(poolRegistry.isPoolRegistered(address(pool)));
assertEq(address(pool.depositTokenOf(weth)), address(0));

address alice = makeAddr("alice");
vm.deal(alice, 10 ether);
vm.prank(alice);
gw.deposit{value: 10 ether}(pool); // succeeds, does NOT revert

// Alice's 10 ETH is now WETH sitting in the gateway, credited to nobody:
assertEq(weth.balanceOf(address(gw)), 10 ether);
assertEq(alice.balance, 0);
// No msdToken minted; no user-side recovery function exists.
```
Equivalent PoC for `VesperGateway.deposit`: pass a registered pool plus a valid `IVPool` that is not a listed underlying; the freshly minted vTokens remain in the gateway while `_depositToken.deposit(_vTokenAmount, msgSender)` no-ops against `address(0)`.

Caveat: the loss path requires the caller to supply a pool/collateral combination whose `depositTokenOf` is unset, so exploitation is self-inflicted rather than direct theft from a third party — I was unable to enumerate every `SmartFarmingManager`/`Operator` path within the iteration limit, and a stronger variant affecting other users' funds cannot be ruled out there.

        address _msgSender = _msgSender();

        // 1. Get `underlying` asset
        IERC20 _underlying = IERC20(vToken_.token());
        _underlying.safeTransferFrom(_msgSender, address(this), amount_);

        // 2. Deposit `underlying` to `VPool`
        _underlying.safeApprove(address(vToken_), 0);
        _underlying.safeApprove(address(vToken_), amount_);
        uint256 _balanceBefore = vToken_.balanceOf(address(this));
        vToken_.deposit(amount_);
        uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;

        // 3. Deposit `VPool` to `Synth` and send `msdTokens` to the `_msgSender()`

        vToken_.safeApprove(address(_depositToken), 0);
        vToken_.safeApprove(address(_depositToken), _vTokenAmount);
        _depositToken.deposit(_vTokenAmount, _msgSender);
    }
