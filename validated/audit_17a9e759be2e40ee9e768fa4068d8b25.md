## Title
Out-of-bounds heap read when parsing Central Directory entries in ijar's ZIP parser — (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the Central Directory Header (CDH) of a ZIP/JAR file with **no bounds checking at all**, unlike the sibling local-file-header parser which calls `EnsureRemaining()` before every read. A crafted archive can set arbitrarily large `file_name_length`, `extra_field_length`, or `file_comment_length` fields, or a bogus `offset`/Zip64 offset field, and drive the cursor `p`/`extra_p` past the end of the mmap'd input buffer. The bytes read from beyond the mapped region are then copied via `memcpy` into the `filename` buffer and flow into `processor->Accept()`/`Process()`, which for the primary consumer (`OutputZipFile`, used to build interface jars) writes them straight into the generated output artifact.

### Finding Description
`ProcessCentralDirEntry` reads six size/offset fields and copies `file_name_length` bytes with no validation: [1](#0-0) 

Compare this to `ProcessLocalFileEntry`, which validates every variable-length read against the remaining bytes in the mapped file via `EnsureRemaining()`: [2](#0-1) 

`EnsureRemaining` itself is not safe against an attacker-chosen `offset` field either. In `ProcessNext`, the cursor is repositioned using the *attacker-controlled* CDH `offset` (which can be extended to a full 64-bit value via the Zip64 extra field, see lines 531–540): [3](#0-2) 

`EnsureRemaining` computes:
```
size_t in_offset = p - zipdata_in_;
size_t remaining = input_file_->Length() - in_offset;
``` [4](#0-3) 

If `offset` pushes `p` beyond `zipdata_in_ + input_file_->Length()`, `in_offset` exceeds `Length()` and the unsigned subtraction underflows to a huge value, so the `n > remaining` guard never fires. Any subsequent `get_u2le`/`get_u4le`/`memcpy` therefore reads from memory outside the mmap'd archive.

The invariant that should hold — "all reads of attacker-supplied ZIP metadata are bounds-checked against the mapped file length" — is broken specifically for the Central Directory walk (`ProcessCentralDirEntry`, used by both `ProcessNext` and `CalculateOutputLength`), and is bypassable for local-file-header entries too because the offset used to seek `p` is unchecked before the `EnsureRemaining` arithmetic itself.

### Impact Explanation
Out-of-bounds bytes read from beyond the mapped input file can be copied into the `filename` buffer and subsequently be written by `OutputZipFile` into the interface-jar/output artifact that the build produces, or into diagnostic output. This is a heap out-of-bounds read whose content (adjacent process memory) can leak into a build artifact consumed later — directly analogous to CVE-2019-5881's disclosure of process memory via a crafted input. It can also crash the process (SIGSEGV) when the wild pointer lands on an unmapped page, but the disclosure path is the qualifying impact here.

### Likelihood Explanation
Any Bazel build step that runs ijar over an externally supplied `.jar`/`.zip` (e.g., pre-built jars brought in as dependencies for interface-jar generation) triggers this code path. A sha256/integrity check on the *download* does not protect against this: the attacker can legitimately publish a byte-for-byte fixed archive whose sha256 matches, while its internal ZIP Central Directory structure is malformed in the way described. No MITM, cache poisoning, or credential compromise is required — only a hostile origin serving a crafted, checksum-matching jar/zip.

### Recommendation
Add bounds checking to `ProcessCentralDirEntry` (mirroring `EnsureRemaining` in `ProcessLocalFileEntry`) before every variable-length field read (`file_name_length`, `extra_field_length`, `file_comment_length`, and the extra-field walk). Additionally, validate the CDH `offset` (and its Zip64 override) against `input_file_->Length()` before it is used to reposition `p` in `ProcessNext`, so `EnsureRemaining`'s subtraction cannot underflow.

### Proof of Concept
Construct a minimal ZIP/JAR with one Central Directory Header entry where `file_name_length` (or `extra_field_length`) is set to a large value (e.g. 0xFFFF) while the mmap'd file is only a few hundred bytes long, and/or set the local-header `offset` field to a large value exceeding the file length. Feed this file to the `ijar` binary (`third_party/ijar/zip_main.cc`) or any Bazel build path that invokes ijar interface-jar generation on the archive. A reproducible JUnit/`BuildIntegrationTestCase` test would: 1) build such a crafted jar byte array, 2) invoke `InputZipFile::Open()`/`ProcessNext()` (or the higher-level ijar entry point) on it, 3) assert the process either reads bytes beyond the known file length into `filename`/output, or crashes with a SIGSEGV/ASAN "heap-buffer-overflow READ" report, demonstrating the missing bounds check.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
