#No vulnerability found for this question.

The scenario described matches explicitly documented, intended protocol behavior rather than a bug. `create_deterministic_account` in `runtime/runtime/src/deterministic_account_id.rs:96-112` is called from `action_implicit_account_creation_transfer`'s `NearDeterministicAccount` branch [1](#0-0) , creating a funded account with `AccountContract::None` and no state — this is the well-documented "`nonexist` -> `uninit`" transition explicitly called out in code comments [2](#0-1)  and in `docs/DataStructures/Account.md:174-186`, which states plainly that a bare Transfer "will not be usable... until the `DeterministicStateInitAction` is also executed" [3](#0-2) .

This is self-inflicted by construction: the only way to derive a `'0s...'` id is to compute `keccak256(borsh(state_init))` yourself [4](#0-3) , meaning whoever can produce a syntactically valid `'0s...'` id inherently knows (or can trivially reconstruct) the matching `DeterministicAccountStateInit` needed to submit `DeterministicStateInitAction` and unlock the account, since `validate_deterministic_state_init` only requires the hash of the *known* state_init to match the receiver [5](#0-4) . An attacker who "guesses" a random `'0s...'` string without knowing its preimage is functionally in the same position as anyone sending funds to a random address for which nobody holds the private key/preimage — there is no reachable mainnet scenario where a third party's funds are affected, no consensus divergence, and no authorization escalation. The freezing (if the attacker deliberately discards their own state_init) is purely self-inflicted and matches intended, spec'd behavior, not a coding defect. This is out of scope per the rules excluding "speculative... claims with no reachable mainnet scenario" and findings that don't demonstrate concrete loss/freezing of *other* users' funds or consensus impact.

```markdown
### Deterministic account creation

Deterministic accounts cannot be created with a `CreateAccount` nor with a `Transfer` action.
A special action, `DeterministicStateInitAction`, is required.
This action validates that the account id matches its initial state.

As with all account types, you have to attach a large enough deposit to cover for the account storage. If the code and
initial state is small enough to fit below the zero-balance limit, no balance is required. The
`DeterministicStateInitAction` has a field to include a balance specifically to cover storage. Anything above the
required amount to cover storage requirements is refunded.

A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable,
however, until the `DeterministicStateInitAction` is also executed.
```

```rust
/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
```

```rust
fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }
```
