### Title
Precompiled contract array-length fields taken directly from unvalidated calldata allow unbounded memory allocation (OOM DoS) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.java` contains three helper methods — `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` — that read an array-length value directly out of attacker-supplied TVM call data (`words[offset].intValueSafe()`) and immediately use it to allocate a Java array (`new byte[len][]`) with no upper-bound validation before the allocation happens. [1](#0-0) 

### Finding Description
Each of these helpers decodes an ABI-style dynamic array by first reading the declared element count from the call data as a `DataWord`, converting it with `intValueSafe()`, and then allocating a two-dimensional byte array sized to that count:

This is the same bug class as CVE-2026-9538: a size field taken from attacker-controlled input (the tar entry header / here, the TVM call-data word designating an array length) is used to size a memory allocation with no sanity/upper-bound check before the allocation is performed. In `Archive::Tar`, the 12-byte size field could declare gigabytes and Perl would attempt to allocate a scalar of that size; here, `intValueSafe()` only prevents an integer-overflow crash when converting the 256-bit `DataWord` to a Java `int` — it does not impose any semantic limit on the returned value, so `len` can be as large as `Integer.MAX_VALUE` (or any value up to that). `new byte[len][]` then attempts to allocate an array of up to ~2.1 billion object references (8+ GB of reference-array memory alone, before the inner elements are even populated), independent of the true size of the submitted call data.

Because `len` is read from the *content* of the call data (a single word interpreted as a count) rather than derived from `data.length`, the actual call-data payload delivered by the caller can be tiny, while the declared count encoded in that payload can be enormous — mirroring the tar bug where the physical size of the malicious archive stream is unrelated to the declared (and unbounded) entry size.

I was not able to confirm from the available index which specific `PrecompiledContract.execute()` implementation invokes these three helpers, nor the exact energy-cost path guarding this precompiled contract call (the `SIG_LENGTH`-related naming of `extractSigArray` suggests a batch signature-verification precompile). This should be verified directly in the repository before treating this as fully confirmed, since some callers may additionally validate `len` against `words.length` or a fixed cap before invoking these helpers, which would mitigate the issue.

### Impact Explanation
If reachable with an unbounded `len` before any subsequent bounds check against `words.length`, an unprivileged caller (any account submitting a TVM `CALL`/`STATICCALL` transaction that invokes this precompiled contract with crafted call data) can force the node to attempt a multi-gigabyte array allocation. This can throw `OutOfMemoryError` on the validating/executing node, potentially crashing or destabilizing the node process during transaction execution or block validation — a node crash / denial-of-service impact.

### Likelihood Explanation
Likelihood cannot be rated with full confidence without confirming (a) which precompiled contract dispatches to these helpers, (b) whether `getEnergyForData` for that contract scales energy cost with the declared `len` before execution, and (c) whether the caller validates `offset > words.length - 1` type checks *before* reading `len` in a way that bounds it. The `extractBytes32Array` variant notably has no such offset/bounds guard at all before reading `len`, which is the most likely candidate to be directly exploitable if invoked with attacker-influenced `offset`/`words`.

### Recommendation
Add an explicit upper bound on `len` in all three helpers (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) before allocating, e.g., reject if `len` exceeds a small sane maximum (matching the maximum plausible number of elements given the call-data size, similar to `isValidAbiEncoding`'s bound checks already used elsewhere in this file), and/or validate `len * elementSize` does not exceed `data.length` prior to allocation.

### Proof of Concept
Not fully reproducible from the indexed code alone because the exact precompiled-contract entry point calling these helpers, and its energy-cost gating, could not be located in this pass. A concrete PoC would require identifying the `execute()` method that calls `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, then crafting a TVM `CALL` to that precompile address with a call-data word (at the offset the function reads as `len`) set to a large value (e.g., `0x7FFFFFFF`) while keeping the actual call-data payload small, and observing whether the node allocates a correspondingly oversized array before further validation.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
