### Title
`apply_action_receipt` skips the per-receipt storage-proof limit for non-`FunctionCall` actions when `EnforceStorageProofLimitForAllActions` is not enabled - (File: `runtime/runtime/src/lib.rs`)

### Summary
In `apply_action_receipt`, the per-receipt storage-proof size check is only performed when *both* `ProtocolFeature::EnforcePerReceiptStorageProofLimit` and `ProtocolFeature::EnforceStorageProofLimitForAllActions` are enabled for the current protocol version. If only the former is active, the enforcement loop's guard (`Some(size_before), Some(limit)`) never matches, so a receipt whose actions are exclusively non-`FunctionCall` (e.g. `Transfer`, `AddKey`, `DeleteKey`, `Stake`, `DeleteAccount`) can generate unbounded trie storage-proof growth relative to `per_receipt_storage_proof_size_limit` without ever raising `ActionErrorKind::ReceiptStorageProofSizeExceeded`.

### Finding Description
`apply_action_receipt` computes `storage_proof_size_before_receipt` gated solely by `EnforcePerReceiptStorageProofLimit`, and separately computes `storage_proof_limit_for_all_actions` gated solely by `EnforceStorageProofLimitForAllActions`: [1](#0-0) 

The per-action enforcement after `apply_action` only runs the size check when *both* values are `Some`: [2](#0-1) 

The comment directly above the feature gate makes the root cause explicit: "The in-VM `RecordedStorageCounter` only bounds `FunctionCall` actions" — meaning the VM-internal metering mechanism (`RuntimeExt::storage_proof_size_before_receipt` / `get_recorded_storage_size` in `runtime/runtime/src/ext.rs`) only applies during contract execution and has no visibility into storage effects of non-`FunctionCall` actions such as `AddKey`/`DeleteKey`/`Transfer`, which can still cause trie removals/insertions (e.g. removing access-key entries) that grow the recorded storage proof. [3](#0-2) 

An attacker crafts a transaction/receipt whose action list contains only non-`FunctionCall` actions (e.g. many `AddKey` followed by `DeleteKey` actions, exploiting deep/rebalancing trie paths) so the receipt drives many trie removals. As long as protocol version has `EnforcePerReceiptStorageProofLimit` on but `EnforceStorageProofLimitForAllActions` off, `storage_proof_limit_for_all_actions` is `None` for every action iteration, so the `if let (true, Some(_), Some(_))` guard at line 928 never evaluates true, and no `ReceiptStorageProofSizeExceeded` error is ever produced — regardless of how much `recorded_by_receipt` (computed at line 933-936) actually grows.

### Impact Explanation
This is a metering-totality gap: the receipt-level storage-proof cap (designed as an independent belt-and-suspenders bound beyond gas costs, to protect state-witness size for stateless validation) is silently disabled for any receipt without `FunctionCall` actions during this specific protocol-version window. The growth is still bounded indirectly by gas costs (each trie touch charges `touching_trie_node`/`read_cached_trie_node`, capped by per-receipt gas), so this is not an unbounded resource-exhaustion vector; it degrades the receipt-level storage-proof-size guarantee back to only what the coarser gas-based bound allows, rather than causing literal unbounded proof size. It does not directly correspond to loss/freezing of funds, double-spend, or authorization escalation.

### Likelihood Explanation
This requires a specific, narrow protocol-version configuration state (`EnforcePerReceiptStorageProofLimit` stabilized while `EnforceStorageProofLimitForAllActions` is not), which is a rollout/versioning precondition rather than something the attacker controls directly. Whether such an intermediate state is ever reachable on a live network depends on the stabilization schedule recorded in `core/primitives-core/src/version.rs`, which I was not able to fully confirm within the available iterations — it's possible both features are always stabilized together in practice, in which case this gap is not reachable on mainnet.

### Recommendation
Decouple the size-before-receipt tracking from the enforcement-for-all-actions flag so that whenever `EnforcePerReceiptStorageProofLimit` is enabled, the receipt-level cap is enforced for all actions unconditionally (or make `EnforceStorageProofLimitForAllActions` a strict superset/dependency of `EnforcePerReceiptStorageProofLimit` so they cannot be independently toggled in a way that disables enforcement for non-`FunctionCall` actions).

### Proof of Concept
Add a unit test in `runtime/runtime/src/tests/apply.rs` (or a dedicated test module) that:
1. Constructs `RuntimeConfig` with `EnforcePerReceiptStorageProofLimit` enabled and `EnforceStorageProofLimitForAllActions` disabled (protocol version selection matching this exact gate).
2. Sets `per_receipt_storage_proof_size_limit` to a small value.
3. Pre-populates trie state with many access keys / large records under one account.
4. Submits an action receipt consisting only of `DeleteKey`/`AddKey`/`Transfer` actions (no `FunctionCall`) that collectively force trie removals whose recorded storage proof upper bound exceeds the configured limit.
5. Executes via `apply_action_receipt` and asserts the resulting `ExecutionOutcome` result is `Ok` (no `ActionErrorKind::ReceiptStorageProofSizeExceeded`), while independently verifying via `state_update.trie.recorded_storage_size_upper_bound()` that the growth exceeded `per_receipt_storage_proof_size_limit`.

    fn get_recorded_storage_size(&self) -> usize {
        // `recorded_storage_size()` doesn't provide the exact size of storage proof
        // as it doesn't cover some corner cases (see https://github.com/near/nearcore/issues/10890),
        // so we use the `upper_bound` version to estimate how much storage proof
        // could've been generated by the receipt. As long as upper bound is
        // under the limit we can be sure that the actual value is also under the limit.
        self.trie_update.trie().recorded_storage_size_upper_bound()
    }

    fn storage_proof_size_before_receipt(&self) -> usize {
        self.storage_proof_size_before_receipt.unwrap_or_else(|| self.get_recorded_storage_size())
    }
