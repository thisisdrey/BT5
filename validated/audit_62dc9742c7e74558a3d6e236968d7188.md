### Title
GetAttachmentResponse content is inserted into AtlasDB with no `attachments_max_size` size check and no hash verification against the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When `AttachmentsDownloader` processes a peer's response to an `AttachmentRequest`, `AttachmentsBatchStateContext::extend_with_attachments` decodes the JSON body via `StacksHttpResponse::decode_atlas_get_attachment` and inserts `response.attachment` directly into `self.attachments` with no check that its length is within `AtlasConfig.attachments_max_size`, and no check that `Attachment::hash()` (i.e. `Hash160(content)`) equals the `content_hash` that was actually requested from that peer. `AttachmentsDownloader::run` then persists every entry from `context.attachments` via `atlasdb.insert_instantiated_attachment` unconditionally.

### Finding Description
The exploit path is:
1. A malicious peer receives an `AttachmentRequest` for some `content_hash` (`RPCGetAttachmentRequestHandler` / `/v2/attachments/:hash`) as tracked in `AttachmentRequest.content_hash` [1](#0-0) .
2. The peer replies with an HTTP 200 body containing an arbitrary hex-encoded JSON `GetAttachmentResponse`, decoded via `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs` lines 158-165), which just does `serde_json::from_value` with no size validation.
3. In `AttachmentsBatchStateContext::extend_with_attachments`, the decoded response is accepted with no checks at all beyond `Ok(response)`: [2](#0-1) 
   Note that `response.attachment` is inserted into `self.attachments` without ever comparing `response.attachment.hash()` to `request.content_hash`, and without checking `response.attachment.content.len()` against `AtlasConfig.attachments_max_size`.
4. `AttachmentsDownloader::run` then unconditionally persists every attachment in `context.attachments` to the DB: [3](#0-2) 
   `insert_instantiated_attachment` is called with no upstream length gate tied to `attachments_max_size`.

The `MAX_MESSAGE_LEN`/HTTP body-length limits bound the overall message but are unrelated to (and typically much larger than) `AtlasConfig.attachments_max_size`, so a peer can return content that satisfies the outer transport limit yet violates the configured attachment cap. Additionally, because there is no hash comparison against the `content_hash` that was requested, a malicious peer can also substitute arbitrary content unrelated to the on-chain-committed hash for a given request, though the id-side of the exploit (storage exhaustion via oversized content) is the one directly asked about here.

### Impact Explanation
A malicious peer answering `AttachmentRequest`s can force victim nodes to store oversized attachment blobs in their `AtlasDB`, bypassing the operator-configured `attachments_max_size` cap, whichI is meant to bound storage per row. This is repeatable per attachment request, and since Atlas periodically re-requests unresolved instances from multiple peers, an attacker acting as one of the outbound sync peers can repeatedly feed oversized payloads, degrading node storage guarantees. This matches the "High" impact category described (attachment storage exhaustion via rows that violate the configured cap).

### Likelihood Explanation
Preconditions: the attacker only needs to run a normal p2p/RPC-reachable Stacks node that a victim considers an "outbound sync peer" and gets included as one of the `peers` a `AttachmentsInventoryRequest`/`AttachmentRequest` is sent to (`network.get_outbound_sync_peers()` in `AttachmentsDownloader::run`, `stackslib/src/net/atlas/download.rs` lines 115-124). No special privilege, secret, or slot ownership is required — any remote peer that responds to attachment inventory/attachment requests can serve the payload. Attacker cost is a single crafted HTTP response per attachment request, and the attack is trivially repeatable.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), before inserting `response.attachment`:
- Verify `response.attachment.hash() == request.content_hash` (reject and treat as a faulty peer otherwise).
- Verify `response.attachment.content.len() <= connection_options`/`AtlasConfig.attachments_max_size` (or an equivalent config field reachable from this context), rejecting/penalizing peers that exceed it, before it ever reaches `insert_instantiated_attachment`.
- Consider likewise capping/validating the decode step itself in `getattachment.rs`'s `try_parse_response`/`decode_atlas_get_attachment` so oversized bodies are rejected as early as possible.

### Proof of Concept
Rust net test plan (in `stackslib/src/net/atlas/tests.rs` or a new test module):
1. Construct an `AtlasConfig` with a small `attachments_max_size` (e.g., 10 bytes).
2. Build an `AttachmentRequest` for a known `content_hash`.
3. Simulate a `StacksHttpResponse` whose JSON body is `{"attachment":{"content":"<hex of e.g. 1000 bytes>"}}` (mirroring `GetAttachmentResponse`'s wire format), decoded by `StacksHttpResponse::decode_atlas_get_attachment`.
4. Feed this response through `AttachmentsBatchStateContext::extend_with_attachments` and then through `AttachmentsDownloader::run`'s persistence path (or directly call `atlasdb.insert_instantiated_attachment`).
5. Assert: `attachment.content.len() > atlas_config.attachments_max_size` yet `atlasdb.find_attachment(&content_hash)` (or the hash of the injected bogus content) succeeds post-insert, and/or assert `response.attachment.hash() != request.content_hash` was never checked/rejected — confirming no size or hash validation gate exists before storage.

            let missing_attachments = match self

                .attachments_instances

                None => continue,
                Some(missing_attachments) => missing_attachments,

                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page

                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
