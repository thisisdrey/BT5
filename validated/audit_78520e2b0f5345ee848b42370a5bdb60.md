Based on my research, I found a directly analogous bug class in java-tron: **unvalidated attacker-controlled length fields used to size array allocations before any bounds/sanity check**, which is exactly the root cause described in CVE-2017-6349 (`u_read_undo` trusting an on-disk length field to size an allocation).

### Title
Unvalidated attacker-controlled length used for array allocation in TVM precompiled-contract calldata parsing — Denial-of-Service via uncontrolled memory allocation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` read a 256-bit word directly from precompile calldata and use it, unchecked, as the size of a newly allocated array, mirroring the `u_read_undo` pattern where a length value read from untrusted input is used directly in an allocation without verifying it against the size of the remaining input.

### Finding Description
Both helper methods take the "array length" word verbatim from the ABI-encoded call data supplied by the caller of a TVM precompiled contract, then allocate an array of that size before validating that the value is sane relative to the actual size of `data`: [1](#0-0) 

```
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    ...
}

private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    ...
}
```
`len` comes straight from `words[offset].intValueSafe()`, a value fully controlled by the transaction/call data sent to the precompile — no comparison is made against `words.length`, `data.length`, or any sane upper bound before `new byte[len][]` is executed. This is analogous to the vim bug: a length field taken from an untrusted source is used to size an allocation without validating it is consistent with the actual amount of remaining data.

`extractSigArray` has the identical pattern: [2](#0-1) 

Because Java is memory-safe, this cannot produce a classic buffer overflow / RCE like the original vim bug. Instead, an attacker-controlled `len` close to `Integer.MAX_VALUE` (or a negative value that the `intValueSafe()` conversion may not fully guard against) causes either a `NegativeArraySizeException` or an attempted allocation of an enormous object-array reference table (`Integer.MAX_VALUE` references ≈ 8–16GB), which throws `OutOfMemoryError`.

### Impact Explanation
`OutOfMemoryError` is a JVM `Error`, not an `Exception`. Precompile execution paths that only `catch (Exception e)` (as seen elsewhere in `PrecompiledContracts.execute()`, e.g. the shielded-transfer precompile) will not catch it, so it propagates up through the TVM execution stack. Depending on where it surfaces (inside block/transaction processing in `Manager`), this can crash or destabilize the node process, denying service to the network — this satisfies the "node crash or halt" impact bar.

### Likelihood Explanation
Reachability depends on confirming which precompiled contract(s) actually invoke `extractBytesArray`/`extractSigArray` with attacker-supplied offsets from a `CALL`/`STATICCALL` to a precompile address; my searches located the helper methods themselves and confirmed 8 call sites in `PrecompiledContracts.java`, but I was not able to fully retrieve the exact precompile method body dispatching into them before running out of tool budget. If these helpers back a directly-callable precompiled contract (e.g., a batch-signature-verification precompile), then any contract deployer or caller can trigger this with a single crafted transaction, making likelihood high. This part of the analysis carries residual uncertainty and should be verified by reading the full call sites in `PrecompiledContracts.java` around the `extractBytesArray`/`extractSigArray` usages.

### Recommendation
Before allocating `new byte[len][]`, validate `len`:
- Reject if `len < 0`.
- Reject if `len` exceeds a sane bound derived from `words.length` / `data.length` (e.g., `len` cannot exceed `(data.length - offset*WORD_SIZE) / WORD_SIZE`), similar to the `verifyLength` bound check already used in `RLP.java` (`framework/src/main/java/org/tron/core/capsule/utils/RLP.java:612`).
- Apply the same bound check consistently to `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`.

### Proof of Concept
Craft calldata for the affected precompiled contract where the "array length" word (at the offset consumed by `extractBytesArray`/`extractSigArray`) is set to a very large value (e.g., `0x7FFFFFFF`) while the remainder of the calldata is short/empty. Invoke the precompile via a normal smart-contract `CALL`/`STATICCALL`. The precompile execution will attempt `new byte[0x7FFFFFFF][]`, triggering `OutOfMemoryError` (uncaught by `catch (Exception e)` handlers), destabilizing the node executing the transaction.

**Note on confidence**: I was unable to fully confirm, within the available tool budget, the exact precompiled-contract method(s) that call `extractBytesArray`/`extractSigArray` with attacker-controlled offsets end-to-end from a transaction. The root-cause pattern (unchecked length-driven allocation) is confirmed in the code, but full reachability/PoC validation requires reading the complete call chain in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`.
