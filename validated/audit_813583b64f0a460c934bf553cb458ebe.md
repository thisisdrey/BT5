### Title
Permission-operations bitmap not checked in `ValidateMultiSign` TVM precompile, allowing bypass of multi-sig operation restrictions - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign` (address `0x0a`) lets any contract check whether a supplied signature set meets an account's permission threshold for an arbitrary `permissionId`. It only checks `TransactionCapsule.getWeight`/threshold and skips the `operations` bitmap check (`checkPermissionOperations`) that every other permission-verification path enforces.

### Finding Description
Every legitimate path that validates a multi-sig `Permission` against a specific action enforces two things: (1) that the signer weight meets the permission's threshold, and (2) that the permission's 32-byte `operations` bitmap allows the specific `ContractType` being authorized — see `TransactionCapsule.checkPermission` [1](#0-0) , used by both `validateSignature` and `addSign`, and duplicated in `TransactionUtil.getTransactionSignWeight` [2](#0-1)  and `Wallet.getTransactionApprovedList` [3](#0-2) .

The `ValidateMultiSign` precompile, reachable by any contract via the standard `validateMultiSign(address,uint256,bytes32,bytes[])` TVM builtin, instead only computes signer weight and compares it to `permission.getThreshold()`: [4](#0-3) . It never calls `checkPermissionOperations`/`WalletUtil.checkPermissionOperations`. This is functionally identical to the Deno flaw: a permission gate (the operations allow-list) exists and is enforced on the "normal" API surface but is missing on a parallel, built-in code path (a TVM precompiled contract) that reaches the same underlying capability.

### Impact Explanation
`validateMultiSign` is meant to let on-chain contracts (e.g., multisig wallet contracts, custody logic) verify that a proposed set of signatures satisfies an account's configured permission before releasing funds or performing an action gated by that permission. Because the `operations` bitmap is not checked, a permission whose `operations` bitmap disallows a given `ContractType`/capability (e.g., a limited "Active" key intentionally restricted from authorizing transfers or other sensitive operations) will still be reported as "sufficiently authorized" by this precompile as long as the raw signature weight meets the threshold. Any contract-based access-control scheme built on top of `validateMultiSign` that relies on the operations restriction is silently bypassed, enabling unauthorized account operations by holders of restricted keys.

### Likelihood Explanation
This is trivially reachable by any contract deployer or caller: `validateMultiSign` is a plain TVM opcode-level precompile at a fixed address, requires no special privilege, and is enabled whenever `VMConfig.allowTvmSolidity059()` is on (mainnet feature). Exploitation only requires signatures from keys that are legitimately part of the permission's key list but whose `operations` bitmap was meant to exclude the specific capability being gated.

### Recommendation
Add an `checkPermissionOperations`-equivalent check in `ValidateMultiSign.execute` (and `BatchValidateSign` if it has the same gap) mirroring `TransactionCapsule.checkPermission`, requiring the caller to supply (or the precompile to derive) the intended `ContractType`/capability being authorized, and rejecting when the permission's operations bitmap disallows it — consistent with all other permission-verification call sites.

### Proof of Concept
1. Account `A` sets an `Active` permission (id=2) with `threshold=1`, keys `[K1]`, and an `operations` bitmap that has the bit cleared for the sensitive `ContractType` (e.g., `TransferContract`), analogous to `ValidateMultiSignContractTest.testDifferentCase` setup: [5](#0-4) .
2. A custody/multisig contract calls the `validateMultiSign(A, 2, hash, [sig_by_K1])` precompile to gate release of funds/authority normally reserved for permissions that allow that operation type.
3. `ValidateMultiSign.execute` computes `totalWeight` via `TransactionCapsule.getWeight` and compares only to `permission.getThreshold()` [6](#0-5) , returning success even though `checkPermissionOperations` would have rejected `K1` for this action type, since the bit for the target `ContractType` is not set in `operations`.
4. The calling contract proceeds to authorize the restricted action, believing it validated against the account's intended, operation-scoped permission.
