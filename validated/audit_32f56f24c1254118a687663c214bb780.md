## Finding [1](#0-0) 

### Title
Bancor-relay exchange rate manipulation via floating-point precision loss in `ExchangeProcessor` - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Rari Capital incident stemmed from relying on a manipulable, formula-derived exchange rate for a lending/AMM-style pool, allowing an attacker to skew the rate and extract value in a single interaction sequence. java-tron's TRC10 Bancor-style exchange (`ExchangeCreateContract`/`ExchangeTransactionContract`) computes trade output using the same class of "relay-token bonding curve" math, but by default does so with native Java `double`/`Math.pow` arithmetic rather than an exact decimal method, making the computed exchange rate susceptible to precision-based skew that a caller can trigger directly through a signed transaction.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines depending on the `allowHarden()` gate (a chain-parameter/proposal controlled flag): the default `ExchangeProcessor`, which performs the Bancor relay math with plain doubles, and the newer `SafeExchangeProcessor`, which uses `BigDecimal` at 18-digit precision. [2](#0-1) 

The default `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` methods compute `Maths.pow(...)` in double precision and then truncate the result via `(long) issuedSupply` / `(long) exchangeBalance`, discarding fractional value in each direction of a two-leg trade (sell-token → virtual "relay supply" → buy-token). [1](#0-0) 

This code path is reachable directly by any unprivileged account broadcasting an `ExchangeTransactionContract`: `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, and unless the `AllowHardenExchangeCalculation` proposal has been activated by SRs, `allowHarden()` is false and the double-precision path is used for every trade against every TRC10 Bancor pool on chain. [3](#0-2) 

Because the pricing state (`firstTokenBalance`/`secondTokenBalance`) is mutated in-place after every trade and persisted via `Commons.putExchangeCapsule`, repeated small trades against the same pool compound the double-precision rounding at each step, letting a caller iteratively bias the realized rate away from the theoretically correct Bancor curve output in their favor over many transactions, without needing any counter-party cooperation, similar to how manipulable spot-computed exchange rates were abused in the Rari/Alpha Homora incident to extract value from a pool through a mispriced conversion.

### Impact Explanation
An attacker who repeatedly trades in and out of a TRC10 Bancor exchange pool can accumulate value extracted from the pool's reserves beyond what the intended bonding-curve formula allows, at the expense of the pool's liquidity provider(s)/other traders — a direct, unauthorized transfer of value (theft of pool funds) reachable purely by transaction broadcast, matching the "Critical" unbacked-balance/fund-theft class named in scope.

### Likelihood Explanation
Exploitation requires only the ability to submit ordinary, unprivileged `ExchangeCreateContract`/`ExchangeTransactionContract` transactions and does not require any special permission, SR/witness role, or network position. It is gated only by whether `AllowHardenExchangeCalculation` has been activated on the network; since it is a governance-toggled parameter (not guaranteed enabled), the vulnerable double-precision path remains reachable on any deployment where the hardening proposal has not been passed. The per-trade profit from rounding is small, so realistic exploitation requires many repeated transactions (bounded by TRX fees/energy), which somewhat limits — but does not eliminate — practical impact.

### Recommendation
Make `SafeExchangeProcessor` (the exact `BigDecimal`-based implementation) the default and only pricing engine for `ExchangeCapsule.transaction()`, removing the double-precision `ExchangeProcessor` path entirely (or requiring the hardened path unconditionally rather than behind an optional proposal), and add invariant checks (e.g., constant-product/constant-relay-supply monotonicity assertions) after every trade to reject any state transition that would let a caller extract more value than the theoretical curve permits.

### Proof of Concept
1. On a chain/testnet where `AllowHardenExchangeCalculation` has not been activated, create a Bancor exchange pool via `ExchangeCreateContract` (`ExchangeCreateActuator`).
2. Submit a sequence of small `ExchangeTransactionContract` trades alternating sell direction against the pool, using `ExchangeTransactionActuator`, which internally calls `ExchangeCapsule.transaction(..., allowHarden()=false)` and thus `ExchangeProcessor.exchange()`. [3](#0-2) 
3. Track cumulative first/second token balances returned in `ExchangeTransactionActuatorTest`-style assertions (e.g. as in `testSellAndBuy2` in `ExchangeProcessorTest.java`, which already demonstrates round-trip trades not returning exactly the same quantities due to double rounding) to quantify the compounding discrepancy versus the exact Bancor formula. [4](#0-3) 
4. Repeat the round-trip trade pattern to demonstrate net extraction of pool reserve value over the exact BigDecimal-computed baseline.
