### Title
Unguarded `assert totalEnergyWeight > 0` allows division-by-zero / undefined energy-limit calculation reachable from a normal TVM call - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` (the global TRON-wide energy-freeze weight) after only guarding the invariant with a Java `assert`, which is a no-op in production JVMs (assertions are disabled unless `-ea` is passed). This mirrors the YoloV2 bug class: code assumes an aggregate/global counter (there, "total entries"; here, "total energy weight") can never be zero at the point of division, but the guard enforcing that assumption is not real production-enforced logic — it is either bypassable (YoloV2: reachable via free/zero deposits) or, here, literally disabled at runtime (`assert`).

### Finding Description
In `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`: [1](#0-0) 
```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

`EnergyProcessor` at least has an explicit `if (totalEnergyWeight <= 0) return 0;` fallback (guarded by feature flags), and a fully-guarded V2 code path for the delegated-resource unfreeze model. `RepositoryImpl.calculateGlobalEnergyLimit`, which is the version consulted from inside TVM execution during smart-contract calls, has **no such explicit zero-check at all** — only the disabled `assert`.

`RepositoryImpl.calculateGlobalEnergyLimit` is invoked from `VMActuator.getAccountEnergyLimitWithFloatRatio`, which is on the hot path for every triggered smart-contract transaction that goes through the "float ratio" consume-user-resource-percent branch: [3](#0-2)

This is reachable from a single, unprivileged `TriggerSmartContractContract` transaction whenever `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` for the calling/creator account. If, at that moment, the global `totalEnergyWeight` dynamic property is `0` (or negative due to accounting drift across the legacy `FreezeBalance`/new `FreezeBalanceV2`/`UnfreezeBalanceV2` unfreeze-delay bookkeeping paths, which independently add/subtract this counter via `addTotalEnergyWeight`/`saveTotalEnergyWeight`), the call reaches either:
- `BigInteger.divide(BigInteger.ZERO)` → uncaught `ArithmeticException: / by zero` when `allowHardenResourceCalculation()` (`hardenResourceCalculation()`) is enabled, or
- `(double) totalEnergyLimit / 0` → `Infinity`/`NaN`, silently cast `(long)` to `Long.MAX_VALUE`/`0`, corrupting the caller's computed available energy in the non-hardened legacy path.

This is directly analogous to the YoloV2 finding: an assumed-nonzero global aggregate (`currentEntryIndex` there, `totalEnergyWeight` here) is used as a divisor/modulus with no enforced runtime guard, and the aggregate's zero-state is reachable through ordinary, permission-less transactions manipulating global counters (freeze/unfreeze), not through any privileged path.

### Impact Explanation
- **Uncaught `ArithmeticException`** during TVM execution of a normal `TriggerSmartContract` transaction can propagate out of `VMActuator`/`getAccountEnergyLimitWithFloatRatio` during block application. Depending on where it is caught (or not) in `Manager`'s transaction-processing pipeline, this can cause the node to fail applying an otherwise valid block, resulting in a chain-halt/consensus failure for the block containing that transaction, since the divergence is deterministic given the shared global state (`totalEnergyWeight`), meaning all full nodes would hit it identically — a High severity liveness/availability issue for the network.
- Alternatively, in the non-hardened legacy arithmetic path, silent `Infinity`/`NaN` → cast-to-`long` corruption of the computed energy limit can grant an account effectively unlimited/undefined energy for a transaction, letting them bypass energy accounting (a resource-accounting integrity issue analogous to "unbacked" resource allocation).

### Likelihood Explanation
Requires the network's `totalEnergyWeight` dynamic property to reach `0` (or a non-positive drift value) while at least one account still has `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` and subsequently triggers a smart contract via the float-ratio energy path (`getAccountEnergyLimitWithFloatRatio`, i.e., when `consumeUserResourcePercent` triggers that branch). This can plausibly occur transiently in edge cases of the legacy Freeze/UnfreezeV1↔V2 migration bookkeeping (multiple code paths independently mutate this counter: `addTotalEnergyWeight`, `saveTotalEnergyWeight`), or in private/low-participation networks/testnets. Because the check is compiled to a no-op `assert` (JVMs run without `-ea` by default in production), there is no runtime safety net once the precondition is violated — unlike `EnergyProcessor`'s equivalent method, which does check explicitly. Given the reliance on an internal invariant that isn't demonstrably always true across all freeze/unfreeze code paths, and given the disabled assertion providing zero real protection, I rate likelihood as Medium.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check mirroring `EnergyProcessor.calculateGlobalEnergyLimitV2`:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```
Additionally, audit all other `assert` statements guarding divisors/moduli across the resource-accounting code (`RepositoryImpl`, `EnergyProcessor`, `BandwidthProcessor`) to ensure none of them are relied upon as the sole protection against division by zero in production, since Java assertions are disabled by default.

### Proof of Concept
Cannot be fully constructed without live-network state manipulation across multiple blocks/maintenance cycles to force `totalEnergyWeight` to `0`/negative while an account retains `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` — this requires deeper testing of the Freeze/FreezeV2/Unfreeze/UnfreezeV2 interplay with `addTotalEnergyWeight`/`saveTotalEnergyWeight`, which was not verified end-to-end within the scope of this analysis. This is flagged as an open question for the engineering team to confirm reachability empirically (e.g., via a modified `CalculateGlobalLimitHardenTest`/`FreezeBalanceActuatorTest` scenario setting `dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(0)` while an account has frozen energy balance, then invoking `VMActuator.getAccountEnergyLimitWithFloatRatio` or `RepositoryImpl.calculateGlobalEnergyLimit` directly) before treating this as confirmed-exploitable rather than a latent defensive-coding gap.
