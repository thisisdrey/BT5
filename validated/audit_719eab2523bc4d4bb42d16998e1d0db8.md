### Title
Out-of-bounds read via unchecked Zip64 extra-field attribute indexing in `CDH`/`LH` size accessors - ([File: src/tools/singlejar/zip_headers.h])

### Summary
`singlejar` (invoked by Bazel's Java rules to merge/process jars, and structurally identical to the parsing pattern used by `ijar`'s `zip.cc`) parses ZIP Central Directory Headers (`CDH`) and Local Headers (`LH`) from attacker-controlled archive bytes. When a 32-bit size/offset field is `0xFFFFFFFF`, the code treats this as "value is stored in the Zip64 extra field" and unconditionally indexes into `Zip64ExtraField::attr64(index)` based on *which* 32-bit fields are flagged as extended, without verifying that the extra field's declared `payload_size()` (and hence `attr_count()`) actually contains that many 8-byte slots.

### Finding Description
`Zip64ExtraField::attr64(int index)` performs a raw, unchecked array read: [1](#0-0) 

Callers compute `index` purely from which of `uncompressed_file_size32()`, `compressed_file_size32()`, `local_header_offset32()` equal `0xFFFFFFFF` — never from `attr_count()`: [2](#0-1) [3](#0-2) [4](#0-3) 

For example, a malicious archive entry can set `uncompressed_file_size32_ = 0xFFFFFFFF`, `compressed_file_size32_ = 0xFFFFFFFF`, and `local_header_offset32_ = 0xFFFFFFFF`, but supply a Zip64 extra field whose `payload_size()` covers only one 8-byte attribute (`attr_count() == 1`). `local_header_offset()` will then compute `attr_no = 2` and call `z64->attr64(2)`, reading 8 bytes starting 16 bytes past the actual end of the declared attribute array — i.e., past the end of the parsed extra-field payload, and potentially past the end of the entire memory-mapped/heap-allocated archive buffer (`InputJar`/`MappedFile` in `src/tools/singlejar/input_jar.h`).

The bounds check that *does* exist, `ExtraField::find`, only validates that the extra-field *header and declared payload* fit within `extra_fields_length()` — it does not, and cannot, prevent a caller from indexing beyond `payload_size()/8` attributes once a valid (but short) Zip64 field has been located: [5](#0-4) 

This is structurally analogous to the reported Linux kernel `x25_bind` OOB flaw: a bounds/length field supplied by an unprivileged data producer (there, `sockaddr_x25.sx25_addr.x25_addr[]` bounds; here, `payload_size()`/`attr_count()`) is not checked against the actual index computed at the point of access, so a crafted length triggers a read past the intended buffer.

### Impact Explanation
The attacker is the publisher of a ZIP/JAR archive that a build fetches and that `singlejar` processes (e.g., via `java_import`, `deploy_jar` merging, or any target that runs `singlejar`/`AddJar` over an externally-supplied jar). The OOB read can:
- Crash the `singlejar` worker process (denial of service for that build action) if it walks off the mapped region, or
- Read adjacent heap/mmap memory and incorporate the garbage 64-bit value into `uncompressed_file_size`, `compressed_file_size`, or `local_header_offset`, which are then used to locate/copy "file data" out of the mapped input — potentially copying unrelated process memory content into the merged output jar, an information-disclosure primitive (leaking adjacent memory contents into a build artifact).

This satisfies the "read outside the repository / exec root / output base" / info-leak class: the read is not confined to the archive's own declared data.

### Likelihood Explanation
Reaching this path only requires supplying a syntactically valid CDH/LH with three specific 32-bit fields set to `0xFFFFFFFF` and an accompanying Zip64 extra field with a `payload_size` shorter than what the combination of flags implies (e.g., `payload_size = 8` while both size fields and the offset are all `0xFFFFFFFF`, which per spec would need `payload_size = 24`). No credentials, containment bypass, or privileged access is needed — only that the attacker controls bytes of an archive (dependency, jar) that reaches `singlejar`/`ijar` parsing. There is an existing project test, `MalformedExtraField` (`output_jar_simple_test.cc`), that engineers a related malformed-extra-field scenario and expects a `LOG(FATAL)`-style abort with message "malformed extra field" — indicating the project is aware of and defends against *some* malformed extra-field shapes, but that existing check targets extra-field iteration (`ExtraField::find`) bounds, not the `attr64(index)` bounds-vs-`attr_count()` mismatch described above. [6](#0-5) 

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site in `CDH`/`LH`), validate `index < attr_count()` before dereferencing `attr_[index]`; if the requested attribute is absent, treat the record as malformed and abort/error (consistent with the existing "malformed extra field" diagnostic) rather than performing the unchecked read.

### Proof of Concept
Construct a CDH (or LH) with:
- `uncompressed_file_size32_ = 0xFFFFFFFF`
- `compressed_file_size32_ = 0xFFFFFFFF`
- `local_header_offset32_ = 0xFFFFFFFF`
- A Zip64 extra field (tag `0x0001`) with `payload_size = 8` (one 8-byte attribute only, i.e. `attr_count() == 1`)

Feed this into `singlejar`'s `OutputJar::Doit()` (as the existing `MalformedExtraField` test in `output_jar_simple_test.cc` does for a different malformed-extra-field shape) and observe that `CDH::local_header_offset()` calls `z64->attr64(2)`, reading 16 bytes beyond the declared attribute payload — verifiable with AddressSanitizer showing a heap-buffer-overflow read, or (unsanitized) a wild `local_header_offset`/size value derived from adjacent memory. A JUnit/`gtest`-based unit test extending `zip_headers_test.cc` can directly construct a `Zip64ExtraField` with `payload_size(8)` and call `CDH::local_header_offset()` after setting all three 32-bit fields to `0xFFFFFFFF`, then run under ASan to confirm the OOB read.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}

TEST_F(OutputJarSimpleTest, MalformedExtraField) {
  string out_path = OutputFilePath("out.jar");
