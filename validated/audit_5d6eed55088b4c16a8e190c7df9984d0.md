### Title
Out-of-bounds array index in `ValidateMultiSign` precompile from unvalidated ABI offset field - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x66`, callable by any TVM contract via `TriggerSmartContract`) parses its raw call data into a `DataWord[]` array and then uses a 32-bit value taken directly from that call data — `words[3].intValueSafe() / WORD_SIZE` — as an index into the same `words` array, without checking it against `words.length`. This mirrors the Zephyr PTP bug class: an attacker-controlled "type/offset" value is used to index a fixed-size table before any upper-bound validation, causing an out-of-bounds read.

### Finding Description
`ValidateMultiSign.execute()` builds `words` via `DataWord.parseArray(rawData)`, whose length is determined purely by the caller-supplied `rawData` length [1](#0-0) . It then computes an index from `words[3]`, an attacker-controlled word, and immediately uses it to index into `words` twice: [2](#0-1) 

The only guard against a malformed/oversized offset is `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)`, and that check is gated behind `VMConfig.allowTvmOsaka()`: [3](#0-2) 

When `allowTvmOsaka()` is not active (older/other hard-fork configurations, or any deployment where this flag has not been enabled), there is no bound check at all before `words[words[3].intValueSafe() / WORD_SIZE]` is evaluated. Because `words[3]` is a raw attacker-supplied 32-byte word truncated to an int (`intValueSafe()`), the computed index can trivially exceed `words.length - 1`, producing an `ArrayIndexOutOfBoundsException`. Critically, this indexing occurs *outside* the `try { ... } catch (Throwable t)` block that wraps only the later signature-verification loop [4](#0-3) , so the exception is not locally handled by `ValidateMultiSign` itself and propagates out of `execute()`.

### Impact Explanation
This is reachable by any account that can broadcast a `TriggerSmartContractContract` targeting a contract that calls the precompile at address `0x66` (or directly if the precompile is dispatchable without a deployed contract, per the TVM's precompiled-contract routing) — no special privileges required. Exploitation induces an uncaught `ArrayIndexOutOfBoundsException` during opcode execution inside `VM.play()`/`op.execute(program)`, i.e., a runtime exception path that the interpreter does not specifically anticipate for this precompile. At minimum this causes transaction execution to fail unexpectedly outside the normal “revert due to insufficient energy/logic” handling; because the same deterministic input is processed identically by every full node validating the block, this is a reliable, reproducible fault rather than a leak of sensitive memory (the `DataWord[]` only contains data already derived from the caller's own supplied bytes, so there is no cross-tenant information disclosure). The primary practical impact is denial-of-service style disruption of a normally-servable code path, analogous to the “crash/fault” outcome the CVE describes for Zephyr's PTP indexing bug, rather than fund theft or ledger corruption.

### Likelihood Explanation
Likelihood is high for triggering the code path: crafting `rawData` for a `TriggerSmartContract` call to the `ValidateMultiSign` precompile with a large `words[3]` value is trivial and requires only a single signed transaction from any account with enough energy/bandwidth. The condition depends on the `allowTvmOsaka` hard-fork flag not being active for the guard to be entirely absent; where it is active, `isValidAbiEncoding` is expected to reject malformed offsets before the indexing occurs (this repo's exact validation logic for `isValidAbiEncoding` could not be fully retrieved in this session, so its coverage of this specific offset field is not independently confirmed).

### Recommendation
Before using `words[3].intValueSafe() / WORD_SIZE` (or any derived index) to access `words`, validate that the computed index is within `[0, words.length)` and reject (return `Pair.of(false, EMPTY_BYTE_ARRAY)`) otherwise — independent of the `allowTvmOsaka` flag, so the fix applies unconditionally rather than only under a hard-fork switch. Apply the same bound check inside `extractSigArray`/`extractBytesArray` wherever they index `words` using offsets derived from call data.

### Proof of Concept
1. Build TVM call data for the precompile at address `0x66` with the standard header words: `address` (word 0), `permissionId` (word 1), `data` (word 2).
2. Set word 3 (the byte-array/signature-array offset field) to a large value, e.g. `0x00000000000000000000000000000000000000000000000000000000FFFFFF00`, so that `intValueSafe() / WORD_SIZE` yields an index far beyond the actual `words.length` produced by a short `rawData` payload.
3. Trigger the precompile via a `TriggerSmartContractContract` transaction (through any deployed contract that performs the equivalent of a static/precompiled call to `0x66`) with this crafted payload as call data.
4. Observe that `words[words[3].intValueSafe() / WORD_SIZE]` at [5](#0-4)  throws `ArrayIndexOutOfBoundsException`, uncaught by the local `try/catch` (which only wraps the later loop), propagating out of `execute()`.
