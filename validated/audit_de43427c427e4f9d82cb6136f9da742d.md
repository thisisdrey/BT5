### Title
`SmartFarmingManager.leverage`/`flashRepay` execute AMM swaps with hardcoded `amountOutMin_ = 0`, allowing sandwich attacks that steal user collateral - (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage()` and `flashRepay()` route collateral↔synth swaps through the external `Swapper`, but hardcode `amountOutMin_ = 0` on every internal `_swap()` call. The only protections are an optional user-supplied `depositAmountMin_`/`swapAmountOutMin_` and a post-swap health check that constrains losses only to "still above liquidation" — not to "fair price". An unprivileged attacker can sandwich a victim's `leverage` call on the AMM (flash-loan the pool, let the victim's zero-min-out swap execute at a manipulated price, restore the price) and extract the difference, leaving the victim with a nearly-maximal-LTV position. This is the same bug class as the Derby `claimTokens` finding: a protocol-initiated swap whose acceptable output is implicitly the manipulated spot quote, with no effective slippage floor enforced by the protocol.

### Finding Description
In `leverage`, the tokenIn→collateral swap and the synth→collateral swap are both invoked with `amountOutMin_ = 0`: [1](#0-0) 

The comment explicitly states "slippage will be checked later on", but the only later checks are `if (_depositAmount < depositAmountMin_)` (line 198) and the `PositionIsNotHealthy` check (lines 207-208). `_debtToken.flashIssue` mints debt sized via `masterOracle().quote(...)` (lines 189-192, `_calculateLeverageDebtAmount` at lines 228-240), i.e., the debt is fixed at oracle price while the collateral actually acquired depends on the manipulable AMM execution price.

`flashRepay` has the same pattern: the collateral→synth swap uses `amountOutMin_ = 0` (line 125), and `swapAmountOutMin_` is only checked after the fact — a caller passing `0` (as all in-repo tests do, e.g. `test/SmartFarmingManager.test.ts:296`) has zero protection.

The generic `_swap` helper forwards `amountOutMin_` verbatim to `swapper_.swapExactInput` (lines 293-306), so nothing enforces a minimum internally.

### Impact Explanation
Direct theft of user funds. Consider a victim calling `leverage(tokenIn, depositToken, msToken, amountIn, leverage, depositAmountMin_ = 0)`:

1. Attacker flash-borrows and dumps the synth on the AMM pool used by `Swapper`, collapsing the synth→collateral rate.
2. Victim's tx executes: debt `D` is minted at oracle price, but the swap of `_issued` synth returns far less collateral than the oracle-implied value. The position still passes `debtPositionOf` as long as `collateral * collateralFactor >= D` — i.e., the attacker can steal up to roughly `(1 - collateralFactor)` fraction of the swapped value, or everything above the health bound if `depositAmountMin_ = 0`.
3. Attacker restores the pool price and pockets the extracted value; the victim is left with a position at (or just inside) the liquidation threshold.

The invariant broken is fair-value exchange: the protocol mints debt at oracle price but acquires the backing collateral at manipulated spot price, transferring the difference to the sandwicher. `swapAmountOutMin_`/`depositAmountMin_` are caller-controlled and default to `0` in practice, and the health check caps loss at the liquidation boundary rather than at a fair rate — it does not prevent the theft.

### Likelihood Explanation
- `leverage` and `flashRepay` are permissionless, `whenNotShutdown` entry points reachable by any EOA or via `Operator.execute`; `nonReentrant` does not help because the manipulation happens across separate transactions on the external AMM, not via reentrancy.
- The synth↔collateral routes on the `Swapper` (e.g., msUSD↔USDC, msETH↔WETH) trade on DEX pools that can be thin; flash loans make the required capital free.
- No privileged role, oracle failure, or incorrect third-party data is needed — only ordinary AMM trades in the same block(s) around the victim's transaction.

### Recommendation
Enforce a protocol-side slippage floor instead of `amountOutMin_ = 0` on internal swaps: compute `amountOutMin` from `masterOracle().quote(tokenIn, tokenOut, amountIn) * (1 - maxSlippage)` and require user-supplied minimums to be non-zero, or revert when the oracle-implied and executed rates deviate beyond a bound. Treat the oracle quote as the reference rate for the swap, not only for sizing the debt.

### Proof of Concept
Hardhat fork outline (mirroring `test/SmartFarmingManager.test.ts`):

```ts
// victim deposits vaDAI and calls leverage with depositAmountMin = 0 (as existing tests do)
await smartFarmingManager.connect(victim)
  .leverage(vaDAI.address, msdVaDAI.address, msUSD.address, amountIn, parseEther('1.9'), 0);

// attacker sandwich (on a mainnet/base fork where Swapper routes via a real AMM):
// 1. flash-loan USDC, buy msUSD in the AMM pool -> msUSD price spikes / collateral out drops
// 2. victim.leverage(...) executes; _swap(swapper, msUSD, collateral, _issued, 0)
//    accepts the manipulated rate because amountOutMin_ == 0
// 3. debt D minted at oracle price; collateral received << D * (1/cf)
//    -> position is still healthy (cf-bound) => PositionIsNotHealthy does not revert
// 4. attacker sells msUSD back / repays flash loan, pockets the difference
// assert: victim._depositInUsd * cf - victim._debtInUsd ~= 0 while
//         attacker profit > 0, victim net equity < amountIn
```

Reproducibility: fork mainnet/Base at a block with deployed `PoolRegistry`, `Pool`, `SmartFarmingManager`, and `Swapper`; impersonate or fund a victim; manipulate the AMM pool via a flash-loan swap; call `leverage` with `depositAmountMin_ = 0`; unwind; show attacker profit equals victim's equity loss while `debtPositionOf` still reports healthy.
