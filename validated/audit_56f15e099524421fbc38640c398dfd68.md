## Finding: Missing slippage protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` enables sandwich attacks against TRC10 Bancor-style exchange pools

### Title
Missing minimum/maximum output protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables sandwich-attack losses - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's built-in Bancor-style TRC10 exchange pool supports three user-facing operations: inject liquidity, withdraw liquidity, and trade (`ExchangeTransactionContract`). Only the trade operation includes a caller-supplied `expected` slippage-protection field that is validated against the pool's live ratio at execution time. The inject and withdraw operations compute the paired-token amount purely from the pool's current reserve ratio at the time the transaction is packed into a block, with no way for the caller to bound the acceptable ratio, mirroring the exact bug class described in the reference report (state-dependent output calculated without user-controlled slippage bound).

### Finding Description
`ExchangeTransactionContract` carries an `expected` field used to enforce a minimum acceptable output: [1](#0-0) 

`ExchangeTransactionActuator.doValidate()` enforces this bound against the exchange's live-computed output: [2](#0-1) 

In contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/minimum bound field: [3](#0-2) 

`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` — the amount of the paired token that will simultaneously be deducted from (inject) the user's account — purely from the live pool ratio (`firstTokenBalance`/`secondTokenBalance`) at execution time, with no check against any user-supplied bound: [4](#0-3) 

Likewise, `ExchangeWithdrawActuator.execute()` computes the paired-token payout `anotherTokenQuant` from the live ratio with no user-supplied bound: [5](#0-4) 

Because any account can freely submit `ExchangeTransactionContract` trades that shift `firstTokenBalance`/`secondTokenBalance` (subject only to `dynamicStore.getExchangeBalanceLimit()`), an attacker who observes a pending `ExchangeInjectContract` or `ExchangeWithdrawContract` in the mempool can front-run it with a trade that skews the ratio, let the victim's inject/withdraw execute against the skewed ratio, then back-run with an opposite trade to restore the ratio and capture the difference — a classic sandwich attack. This exactly matches the report's bug class: state-dependent AMM/pool math executed without a user-enforced minimum/maximum bound.

### Impact Explanation
A victim calling `ExchangeInjectContract` can be forced to contribute a disproportionate amount of the paired token relative to fair value, and a victim calling `ExchangeWithdrawContract` can receive a paired-token payout below fair value — both silently, since the actuators never reject execution based on an economic bound the caller controls. Since both operations move real TRX/TRC10 balances between the user's account and the exchange pool, this results in a concrete, unauthorized transfer of value from ordinary users to an attacker capable of transaction ordering (e.g., via mempool observation and same-block trade submission), i.e. financial loss to users — a Medium/High severity issue depending on pool liquidity depth and attacker capital.

### Likelihood Explanation
Any unprivileged account can submit `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` transactions; no special permission is required beyond normal signature/balance checks in `AbstractExchangeActuator`/`ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator`. An attacker only needs to observe a target's pending inject/withdraw transaction and have sufficient balance to move the pool ratio, which is a standard MEV/sandwich pattern already directly enabled for the trade path (hence why `expected` exists there) but left unmitigated for inject/withdraw.

### Recommendation
Add an `expected`/bound field (minimum `anotherTokenQuant` for inject deduction cap, minimum `anotherTokenQuant` for withdraw payout) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` analogous to the existing check in `ExchangeTransactionActuator.doValidate()` (`anotherTokenQuant < tokenExpected` → reject).

### Proof of Concept
1. Attacker monitors mempool and sees victim's `ExchangeInjectContract` (or `ExchangeWithdrawContract`) targeting exchange pool `P` with tokens A/B.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of A into `P`, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for a subsequent inject (or withdraw) of A.
3. Victim's inject/withdraw transaction executes against the skewed ratio computed in `ExchangeInjectActuator.execute()` / `ExchangeWithdrawActuator.execute()` (lines cited above), causing the victim to contribute more B than fair value (inject) or receive less B than fair value (withdraw).
4. Attacker submits a reverse `ExchangeTransactionContract` trade to restore the ratio, realizing profit extracted from the victim's inject/withdraw, since no `expected` bound field exists to make the victim's transaction revert under `ContractValidateException` when the ratio is unfavorable.
