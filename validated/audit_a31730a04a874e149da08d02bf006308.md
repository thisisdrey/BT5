### Title
Unbounded TCP connection acceptance on the gRPC API server allows file-descriptor exhaustion and full node crash - (File: framework/src/main/java/org/tron/common/application/RpcService.java)

### Summary
`RpcService.initServerBuilder()` builds the FullNode/Solidity/PBFT gRPC listener (ports 50051/50061/50071) with `NettyServerBuilder`, configuring only per-connection limits — `maxConcurrentCallsPerConnection`, `flowControlWindow`, `maxConnectionIdle`, `maxConnectionAge`, `maxInboundMessageSize`, `maxHeaderListSize` [1](#0-0) . There is no cap anywhere on the total number of concurrently accepted TCP connections/channels for this server. By contrast, the sibling `HttpService` (used for the JSON HTTP and JSON-RPC APIs) explicitly guards against exactly this class of bug by installing a Jetty `ConnectionLimit` bean bounded by `node.maxHttpConnectNumber` (default 50) [2](#0-1) . The gRPC path has no analogous protection: `RateLimiterInterceptor` only throttles at the gRPC-call level after a connection/stream is already accepted [3](#0-2) , and `GrpcNettyMaxConcurrentStreamsLimiter` only bounds streams *within* a connection, not the number of connections [4](#0-3) .

### Finding Description
An unauthenticated remote client can open a very large number of raw TCP connections to the gRPC port and simply hold them open (never completing the HTTP/2 preface, or completing it and issuing no/low-rate calls). Because `RpcService` never sets any Netty-level limit on the number of accepted connections/channels (no boss/worker backlog cap, no connection counting interceptor, no analog of the HTTP `ConnectionLimit` bean), Netty's NIO event loop will keep accepting and allocating a file descriptor for every incoming socket. On a node with a bounded `ulimit -n`, this drives the process toward file-descriptor exhaustion, at which point subsequent `accept()`/`open()` calls throw `IOException: Too many open files` inside Netty's event loop. This mirrors CVE-2016-7072 in PowerDNS, where the web server ran out of file descriptors from many TCP connections and the resulting exception terminated the whole process, rather than just the offending connection.

### Impact Explanation
If the resulting `IOException` propagates uncaught out of a Netty I/O thread (rather than being confined to the single failing channel), the entire gRPC event loop/service — and potentially the whole FullNode JVM process, since other subsystems (P2P, block application, HTTP) may also be starved of file descriptors — can crash or hang. This is a remotely triggerable denial of service against a core JSON-RPC/gRPC query and broadcast surface with no authentication or transaction cost required, causing the node to stop serving `Wallet` gRPC APIs (including `BroadcastTransaction`) until manually restarted.

### Likelihood Explanation
Likelihood is high in unhardened deployments: default `node.rpc` configuration does not set any total-connection cap, `maxConnectionIdleInMillis` and `maxConnectionAgeInMillis` default to `0` → `Long.MAX_VALUE` (no forced disconnects) as shown in `postProcess()` [5](#0-4) , and reference/example configs ship the same unbounded defaults [6](#0-5) . Any anonymous internet client with a socket library can reach the exposed gRPC port and hold many slow/idle connections open indefinitely; no signed transaction, stake, or special privilege is needed.

### Recommendation
Add a total-connection cap to the gRPC server analogous to the existing HTTP `ConnectionLimit`, e.g. by tracking connection counts via a `ServerTransportFilter`/channel-count `ServerInterceptor` that rejects new transports once a configurable `maxRpcConnectNumber` is exceeded, and/or bound the underlying Netty boss/worker `EventLoopGroup` accept behavior with a connection-limiting `ChannelHandler`. Additionally, ensure a sane non-zero default for `maxConnectionIdleInMillis`/`maxConnectionAgeInMillis` so idle/slow-loris style connections are proactively reclaimed, and confirm any I/O exception from `accept()`/`open()` in the Netty pipeline is caught and logged per-channel rather than being allowed to propagate to and crash the whole JVM.

### Proof of Concept
```python
# Open thousands of raw TCP connections to the gRPC port and hold them idle.
import socket, time

TARGET = ("<fullnode-ip>", 50051)
socks = []
try:
    for i in range(20000):
        s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        s.settimeout(5)
        s.connect(TARGET)
        socks.append(s)  # never send the HTTP/2 client preface; just hold the FD
except Exception as e:
    print(f"stopped after {len(socks)} connections: {e}")

time.sleep(600)  # observe node logs / process for FD exhaustion and crash
```
Run concurrently from several source hosts/IPs to defeat any coarse per-IP peer limiting (which in this codebase only applies to the P2P listener via `maxConnectionsWithSameIp`, not the gRPC listener) [7](#0-6) , and monitor for `Too many open files` in node logs and eventual process termination or unresponsiveness on the gRPC/HTTP/P2P ports.

      this.executorService = ExecutorServiceManager.newFixedThreadPool(
          this.executorName, parameter.getRpcThreadNum());
      serverBuilder = serverBuilder.executor(this.executorService);
    }
    // Set configs from config.conf or default value
    serverBuilder = GrpcNettyMaxConcurrentStreamsLimiter.configurePlaintext(
        serverBuilder, parameter.getMaxConcurrentCallsPerConnection());
    serverBuilder
        .flowControlWindow(parameter.getFlowControlWindow())
        .maxConnectionIdle(parameter.getMaxConnectionIdleInMillis(), TimeUnit.MILLISECONDS)
        .maxConnectionAge(parameter.getMaxConnectionAgeInMillis(), TimeUnit.MILLISECONDS)
        .maxInboundMessageSize(parameter.getMaxMessageSize())
        .maxHeaderListSize(parameter.getMaxHeaderListSize());
    if (parameter.getRpcMaxRstStream() > 0 && parameter.getRpcSecondsPerWindow() > 0) {
      serverBuilder.maxRstFramesPerWindow(
          parameter.getRpcMaxRstStream(), parameter.getRpcSecondsPerWindow());
    }

    if (parameter.isRpcReflectionServiceEnable()) {
      serverBuilder.addService(ProtoReflectionService.newInstance());
    }
    return serverBuilder;
  }

  @Override
  public <ReqT, RespT> Listener<ReqT> interceptCall(ServerCall<ReqT, RespT> call, Metadata headers,
      ServerCallHandler<ReqT, RespT> next) {

    String methodMeterName = MetricsKey.NET_API_DETAIL_QPS
        + call.getMethodDescriptor().getFullMethodName();
    MetricsUtil.meterMark(MetricsKey.NET_API_QPS);
    MetricsUtil.meterMark(methodMeterName);

    IRateLimiter rateLimiter = container
        .get(KEY_PREFIX_RPC, call.getMethodDescriptor().getFullMethodName());

    Listener<ReqT> listener = new ServerCall.Listener<ReqT>() {};

    RuntimeData runtimeData = new RuntimeData(call);
    // Check per-endpoint first to avoid consuming global IP/QPS quota for requests
    // that would be rejected by the per-endpoint limiter anyway. acquirePermit()
    // chooses blocking or non-blocking semantics based on rate.limiter.apiNonBlocking.
    boolean perEndpointAcquired = rateLimiter == null || rateLimiter.acquirePermit(runtimeData);
    boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);

    if (!acquireResource) {
      // Release the per-endpoint permit when global rejected, to avoid semaphore leak.
      if (rateLimiter instanceof IPreemptibleRateLimiter && perEndpointAcquired) {
        ((IPreemptibleRateLimiter) rateLimiter).release();
      }
      call.close(Status.fromCode(Code.RESOURCE_EXHAUSTED), new Metadata());
      return listener;
    }

  static NettyServerBuilder configurePlaintext(
      NettyServerBuilder builder, int maxConcurrentStreams) {
    checkNotNull(builder, "builder");
    checkArgument(maxConcurrentStreams > 0, "maxConcurrentStreams must be positive");
    builder.maxConcurrentCallsPerConnection(maxConcurrentStreams);
    // TODO: Remove this shim after https://github.com/grpc/grpc-java/issues/12930 is fixed.
    return builder.protocolNegotiator(newPlaintextNegotiator(maxConcurrentStreams));
  }

  static InternalProtocolNegotiator.ProtocolNegotiator newPlaintextNegotiator(
      int maxConcurrentStreams) {
    checkArgument(maxConcurrentStreams > 0, "maxConcurrentStreams must be positive");
    return new EnforcingProtocolNegotiator(
        InternalProtocolNegotiators.serverPlaintext(), maxConcurrentStreams);
  }
