Based on my investigation, the strongest local analog is in the Snowbridge `system-v2`/`system-frontend`/`inbound-queue-v2` tip-registration flow, where the amount recorded as a relayer reward on BridgeHub is fully trusted from an XCM `Transact` message carrying a plain `u128 amount`, with no on-chain proof that real Ether backing was ever burned/withdrawn on the sending side for that exact amount.

### Title
Unbacked relayer reward inflation via trusted `amount` in cross-chain `AddTip`/`RegisterToken` XCM `Transact` calls - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`, `bridges/snowbridge/pallets/system-v2/src/lib.rs`, `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

### Summary
`pallet_snowbridge_system_frontend::add_tip` on AssetHub swaps/burns a user's tip asset for Ether and then encodes the *resulting* `ether_gained` amount into an XCM `Transact` call (`EthereumSystemCall::AddTip { sender, message_id, amount }`) sent to BridgeHub. On BridgeHub, `pallet_snowbridge_system_v2::add_tip` [1](#0-0)  takes this `amount` at face value and forwards it straight into `InboundQueue::add_tip`/`OutboundQueue::add_tip`, which unconditionally records it as an owed reward with no cross-check against any escrowed/locked balance on BridgeHub itself [2](#0-1) . This mirrors the `VestingEscrowSimple` bug class: a contract/pallet records a promised payout amount purely from a caller-supplied parameter, without verifying (at the point of recording) that the underlying value was actually deposited/locked in the account/pallet that will eventually pay it out.

### Finding Description
The flow is:
1. On AssetHub, `SystemFrontend::add_tip` burns the swapped ether via `burn_for_teleport` and computes `ether_gained` [3](#0-2) .
2. It builds an `EthereumSystemCall::AddTip { sender, message_id, amount: ether_gained }` and ships it as an **unpaid** `Transact` XCM to BridgeHub [4](#0-3) .
3. On BridgeHub, the `EthereumSystemV2::add_tip` extrinsic only checks the origin is `FrontendOrigin` (i.e., "this XCM genuinely came from the AssetHub frontend pallet's location") — it performs **no independent verification of the amount** against any locked/escrowed value on BridgeHub [1](#0-0) .
4. `InboundQueue::add_tip` (and `OutboundQueue::add_tip`) simply insert/accumulate `amount` into the `Tips`/`PendingOrders` storage as owed reward, with the only checks being amount-nonzero and nonce/order-not-yet-consumed [2](#0-1) .
5. Later, `process_message` reads back this recorded `tip` and adds it to `relayer_fee`, then calls `T::RewardPayment::register_reward(&relayer, ..., total_tip)` [5](#0-4) , which is exactly `pallet-bridge-relayers`' `register_relayer_reward`, crediting a claimable balance that is later paid out via `T::PaymentProcedure::pay_reward` in `claim_rewards`/`claim_rewards_to` [6](#0-5) .

The entire chain trusts the `amount` field carried in the cross-chain message rather than re-deriving or verifying it against value that was actually moved/escrowed on the paying chain (BridgeHub). This is structurally identical to the `VestingEscrowSimple` flaw: the payout ledger (`Tips`/`RelayerRewards`) is populated from a caller/message-supplied number rather than from an on-chain-verified transfer of backing value at the point of crediting.

### Impact Explanation
If any code path can cause `amount` in the `AddTip`/message_id-forwarded XCM to diverge from the ether actually burned/escrowed (e.g., a bug in `swap_and_burn`/`burn_for_teleport` that under-burns but still returns a larger `ether_gained`, or any other origin able to construct/replay the `Transact` with an inflated `amount`), the relayer reward ledger on BridgeHub becomes unbacked. Rewards would then be paid out via `pay_reward`/XCM `Deposit` to relayers exceeding what was actually collected/burned on AssetHub, i.e., unbacked mint/theft of bridge funds paid from the reward pot. Even absent an exploitable bug in the burn step itself, this is a load-bearing trust boundary that the vulnerability class targets: nowhere in the `add_tip` extrinsic on BridgeHub is the `amount` cross-checked against a proof of real value transfer.

### Likelihood Explanation
The origin check (`FrontendOrigin::ensure_origin`) restricts the caller to the specific pallet-derived XCM location, which limits this to a bug/edge-case in the swap-and-burn accounting rather than an arbitrary unprivileged attacker directly forging the message. This significantly lowers likelihood versus a directly attacker-triggerable primitive, and I was not able to fully verify (within available tooling/index) whether `swap_and_burn`'s `T::Swap::swap_exact_tokens_for_tokens` and `burn_for_teleport` guarantee `ether_gained` always equals real burned value under all code paths (e.g., rounding, slippage with `None` minimum-amount, or partial burn failures swallowed as success). This is the key uncertainty limiting confidence in exploitability.

### Recommendation
- On BridgeHub, before crediting `Tips`/`PendingOrders`/`RelayerRewards`, verify the tip `amount` against an accompanying cryptographic/asset proof of the actual value burned/escrowed on the sending chain (e.g., include a receipt of the specific burn amount rather than trusting a bare `u128`), or route real fungible value cross-chain (teleport/reserve-transfer the ether alongside the `Transact`) instead of only sending a number.
- Add a defensive invariant/try-state check that the sum of all outstanding `Tips`/`RelayerRewards` recorded from cross-chain messages never exceeds cumulative burned/escrowed value tracked on BridgeHub.
- Audit `swap_and_burn`/`burn_for_teleport` for any path where `ether_gained` (the reported amount) can exceed the amount actually irreversibly burned (e.g., `None` slippage tolerance in `swap_exact_tokens_for_tokens`).

### Proof of Concept
Not independently reproducible from the index alone: exploitability hinges on confirming a concrete divergence between `ether_gained` returned by `swap_and_burn`/`burn_for_teleport` [7](#0-6)  and the value truly removed from circulation, which I could not fully verify in this pass. A Devin session with repo access and test execution (`bridges/snowbridge/pallets/system-frontend/src/tests.rs`, `bridges/snowbridge/pallets/system-v2/src/tests.rs`) would be needed to construct a concrete PoC demonstrating `amount` inflation through the swap/burn step, or to confirm no such divergence is possible, before this can be escalated with certainty.

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
	}

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
