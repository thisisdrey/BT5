### Title
Non-monotonic, floating-point exchange-rate calculation in TRC10 Bancor-style Exchange allows pool drainage via `ExchangeTransactionActuator` - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeTransactionActuator` derives the amount of tokens a caller receives from a mutable, self-referential "price" value — the exchange pool's own `firstTokenBalance`/`secondTokenBalance` state — the same class of bug as the ibBTC `pricePerShare` finding: a value used to compute transfer amounts is trusted without a sanity/monotonicity check, and when the calculation path is imprecise it can silently under- or over-credit a party, draining the pool. Here, by default (`allowHardenExchangeCalculation` disabled) the amount is computed with the legacy `ExchangeProcessor`, which uses `double` floating-point arithmetic for the Bancor-relay formula, instead of the `BigDecimal`-based `SafeExchangeProcessor` that was added later as a hardening fix.

### Finding Description
`ExchangeTransactionActuator.execute` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` to compute `anotherTokenQuant`, the amount of the counter-token to credit to the caller and debit from the pool. [1](#0-0) 

Inside `ExchangeCapsule.transaction`, the processor used to compute this amount is selected by the `hardenedCalc` flag, which is controlled by `allowHarden()` — a chain parameter (`allowHardenExchangeCalculation`) that must be turned on via governance proposal: [2](#0-1) [3](#0-2) 

When not hardened, `ExchangeProcessor` performs the Bancor "relay" calculation entirely in `double` precision: [4](#0-3) 

This is the exact analog of the ibBTC bug class: a derived exchange rate/price (here, the implicit spot price encoded by `firstTokenBalance`/`secondTokenBalance` and processed through a lossy `double` power function) is used directly to move value between the pool and the caller, with no sanity check that:
- the computed output never exceeds what a correct (precise) calculation would allow, and
- repeated small transactions cannot accumulate rounding bias in the caller's favor.

The project's own test suite demonstrates the divergence: `testStrictMath` explicitly asserts that the legacy double-based result and the hardened BigDecimal result differ (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the legacy path is measurably imprecise relative to the "correct" value: [5](#0-4) 

Because the legacy path is the *default* (hardening is opt-in via `ALLOW_HARDEN_EXCHANGE_CALCULATION`), any unprivileged account can submit repeated `ExchangeTransactionContract` transactions against a TRC10/TRX Bancor pool and have the pool balance state (the "price") updated using this imprecise, non-validated formula. There is no check anywhere in `ExchangeTransactionActuator` comparing the legacy result against a reference/expected value beyond the caller-supplied `expected` floor: [6](#0-5) 
That check only protects the caller from getting less than they want — it does nothing to prevent the pool from being systematically shorted across many small trades due to floating-point drift, unlike the `Not precise enough` sanity check that `ExchangeInjectActuator`/`ExchangeWithdrawActuator` apply to their own ratio-based calculations only in hardened mode. [7](#0-6) 

### Impact Explanation
If the floating-point relay computation in `ExchangeProcessor` diverges from the true bonding-curve value (as the codebase's own tests prove it does), an attacker can structure a sequence of `ExchangeTransactionContract` calls to repeatedly extract more counter-token than they should, gradually draining the pool's `firstTokenBalance`/`secondTokenBalance` reserves — directly analogous to the ibBTC report's "drainage of wibbtc from Curve pool" impact, but here draining TRC10/TRX liquidity pools created via `ExchangeCreateContract`. This is a theft-of-funds / unbacked-balance class impact reachable purely via ordinary signed transactions from any account, with no special privilege required.

### Likelihood Explanation
Likelihood is bounded by: (1) whether `allowHardenExchangeCalculation` is enabled on the target network (if enabled, the vulnerable `ExchangeProcessor` path is bypassed entirely in favor of `SafeExchangeProcessor`), and (2) the actual magnitude of floating-point drift for realistic pool sizes/trade quantities, which I could not fully quantify from the available context. The existence of a dedicated hardening mechanism (`SafeExchangeProcessor`, `allowHarden()`, and precision-check code paths added to Inject/Withdraw actuators) strongly suggests the java-tron team already recognized precision issues in the legacy Exchange arithmetic as a real concern; whether it has been enabled by default in production is not verifiable from this index alone.

### Recommendation
- Make hardened (`SafeExchangeProcessor`/BigDecimal) calculation the mandatory, non-optional code path for `ExchangeTransactionActuator`, removing the legacy `double`-based `ExchangeProcessor` entirely, rather than gating it behind an opt-in proposal.
- Add an explicit sanity/consistency check in `ExchangeCapsule.transaction` analogous to the "Not precise enough" check already present in `ExchangeWithdrawActuator`, verifying the computed `buyTokenQuant` does not exceed what an exact/BigDecimal-based computation would yield, before mutating pool balances.
- Add invariant checks that the product `firstTokenBalance * secondTokenBalance` (the constant-product/relay invariant) does not decrease across a transaction in a way that benefits the caller beyond expected fees/slippage.

### Proof of Concept
Not independently executable from the indexed context (no access to a live network/hardfork state to confirm whether `allowHardenExchangeCalculation` is active by default). The codebase's own regression test demonstrates the underlying precision divergence that enables the exploit path: [8](#0-7) 
An attacker would call `ExchangeTransactionContract` repeatedly with small `quant` values against a pool while `allowHardenExchangeCalculation == 0`, relying on the `double`-based `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` rounding to extract a cumulative surplus of the counter-token relative to what the exact bonding-curve formula would yield, as shown by `ExchangeTransactionActuator.execute` crediting `anotherTokenQuant` directly from that computation with no independent precision check. [9](#0-8)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
