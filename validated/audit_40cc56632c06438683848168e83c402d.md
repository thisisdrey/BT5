Audit Report

## Title
Stale `ChildBountiesValuePerParent` accounting on child-bounty payout permanently under-pays the parent bounty - (File: `substrate/frame/multi-asset-bounties/src/lib.rs`)

## Summary
`pallet-multi-asset-bounties` tracks the value reserved for child bounties in `ChildBountiesValuePerParent`, which `calculate_payout()` uses to compute the parent bounty's payout as `value.saturating_sub(children_value)`. The `remove_bounty()` function's `Some(child_bounty_id)` branch (invoked from the `PayoutAttempted` success arm) never decrements `ChildBountiesValuePerParent`, while the `RefundAttempted` success arm explicitly decrements it before calling `remove_bounty`; only the parent-removal (`None`) branch clears the map entirely. This means once a child bounty is paid out, its value stays permanently "reserved" against the parent, causing the parent's eventual payout to be under-paid by the sum of all previously paid-out child bounties.

## Finding Description
`remove_bounty()`'s `Some(child_bounty_id)` branch only removes the `ChildBounties` entry and decrements `ChildBountiesPerParent`; it does not touch `ChildBountiesValuePerParent`: [1](#0-0) 

The `PayoutAttempted` success arm calls `remove_bounty(parent_bounty_id, child_bounty_id, metadata)` for a paid-out child bounty without any preceding decrement of `ChildBountiesValuePerParent`: [2](#0-1) 

In contrast, the `RefundAttempted` success arm explicitly subtracts the child's value from `ChildBountiesValuePerParent` before calling the same `remove_bounty`: [3](#0-2) 

`calculate_payout()` reads `ChildBountiesValuePerParent` to size the parent's own payout, subtracting it from the parent's total value: [4](#0-3) 

Only the parent-removal (`None`) branch of `remove_bounty` clears `ChildBountiesValuePerParent` entirely (via `remove`), which happens when the parent itself is finally cleaned up — too late to affect the (already computed) payout amount, and irrelevant to the mid-lifecycle accounting problem: [5](#0-4) 

This confirms the previously flagged "open verification gap": `remove_bounty()` does **not** generically decrement the counter for the child-payout path, so the asymmetry between the refund and payout arms is a real, unaddressed bug — the same accounting-counter class of defect that PR #11425 previously fixed for the destructive-read variant.

## Impact Explanation
Because `ChildBountiesValuePerParent` is never decremented when a child bounty is paid out (only when refunded), it permanently overstates the value "still reserved for children" that no longer exist once paid. When the parent bounty is later awarded and paid via `calculate_payout(parent_bounty_id, None, value)`, the payout is reduced by `children_value`, which still includes every already-settled child bounty's value. This permanently locks a portion of the parent bounty's funds — they are never paid to the parent's rightful beneficiary and are not recoverable through any subsequent path, since the storage is fully cleared only when the parent bounty itself is removed. This matches the "permanent user-fund lock" and "duplicate settlement"/incorrect-payout categories of the impact gate: value that was already correctly paid to child beneficiaries is now double-counted as a deduction against the parent, causing conserved value to be permanently stuck/unaccounted rather than paid.

## Likelihood Explanation
No privileged or malicious action is required. This triggers under the normal, expected flow: create a parent bounty, create and successfully pay out any child bounty via the standard extrinsics/`check_status()` processing, and later award and pay out the parent bounty. Every combination of "create child bounty → pay it out → later pay out parent" reproduces the fund lock deterministically and repeatably, using only public extrinsics.

## Recommendation
Decrement `ChildBountiesValuePerParent` by the child bounty's value inside `remove_bounty()`'s `Some(child_bounty_id)` branch unconditionally (covering both the payout and refund paths), and remove the now-duplicate explicit decrement in the `RefundAttempted` success arm to avoid double-subtraction. Add a regression test verifying that after a child bounty is paid out (not refunded) and removed, `ChildBountiesValuePerParent::<T, I>::get(parent_bounty_id)` returns `0`, and that the subsequent parent bounty payout's `BountyPayoutProcessed` event reports the full remaining `value`.

## Proof of Concept
1. Create a parent bounty with `value = V`.
2. Create a child bounty with `child_value = C`, setting `ChildBountiesValuePerParent::<T,I>::get(parent) = C`.
3. Award and drive the child bounty through `check_status()` to a successful `PayoutAttempted` outcome, triggering `remove_bounty(parent, Some(child_id), metadata)`.
4. Assert `ChildBountiesValuePerParent::<T,I>::get(parent)` still equals `C` (not `0`) — confirms the stale counter.
5. Award and pay out the parent bounty; observe the `BountyPayoutProcessed` event reports `value = V - C` instead of `V`, confirming `C` worth of the parent bounty's funds are permanently unpaid/locked.
