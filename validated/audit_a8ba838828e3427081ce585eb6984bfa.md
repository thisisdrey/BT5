## Title
Unchecked `reduceAssetAmountV2` Return Value in `ExchangeTransactionActuator.execute` Can Allow Free Token Withdrawal from Exchange Pool - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeTransactionActuator.execute()` calls `AccountCapsule.reduceAssetAmountV2(...)` to debit the trader's TRC10 token but ignores its boolean return value, mirroring the reported "unchecked transfer" pattern where a token-moving call's success/failure is never checked before the surrounding logic proceeds as if it succeeded.

### Finding Description
`reduceAssetAmountV2` returns `false` instead of throwing when the account's tracked balance is insufficient for the requested amount, and its caller is expected to check that value and abort on failure. This exact contract is honored elsewhere in the codebase: `TransferAssetActuator.execute()` checks the return value and throws `ContractExeException("reduceAssetAmount failed !")` if it is `false` [1](#0-0) , and `ParticipateAssetIssueActuator.execute()` similarly checks `reduceAssetAmountV2`'s sibling `reduceAssetAmountV2` on the counterparty side [2](#0-1) . `Commons.adjustAssetBalanceV2` also enforces this by throwing `BalanceInsufficientException` when the reduce call fails [3](#0-2) .

`ExchangeTransactionActuator.execute()` breaks this pattern: it invokes `accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);` for the non-TRX debit leg without checking or using the returned boolean [4](#0-3) . Immediately afterward, regardless of whether the debit actually succeeded, the actuator unconditionally credits the counterpart token via `addAssetAmountV2`, persists the mutated account, commits the already-mutated exchange pool balances (mutated earlier by `exchangeCapsule.transaction(...)`), and reports success [5](#0-4) .

`validate()` does check `assetBalanceEnoughV2` before execution [6](#0-5) , but `reduceAssetAmountV2`'s internal branching depends on `dynamicPropertiesStore.getAllowSameTokenName()` and asset-key resolution logic that differs from the simpler `assetBalanceEnoughV2` check, and both re-derive state independently at execute time [7](#0-6) . Because the two checks are not guaranteed to be perfectly consistent (e.g., across the `AllowSameTokenName`/asset-migration code paths, or divergence introduced by future changes to either method), a caller can end up in a state where `reduceAssetAmountV2` silently fails (returns `false`, balance not actually decremented) while the actuator still credits the exchanged token and commits an updated exchange pool state as if the debit succeeded.

### Impact Explanation
If the debit silently fails while the rest of the trade completes, the calling account receives the purchased token without ever paying the sold token, while the exchange pool's balances are still updated to reflect a completed trade. This produces an unbacked token balance for the caller and depletes/mis-accounts the exchange pool's TRC10 liquidity — a direct theft-of-funds / unbacked-balance condition reachable by any account that can submit an `ExchangeTransactionContract` (i.e., any unprivileged transaction broadcaster).

### Likelihood Explanation
Exploitability depends on finding a state where `assetBalanceEnoughV2` (used in `validate()`) and `reduceAssetAmountV2` (used in `execute()`) disagree about balance sufficiency — for example due to the `AllowSameTokenName` migration path or asset-key import edge cases in `importAsset`/`reduceAssetAmountV2`. This is a narrower window than the audited `topUp` case, but the code pattern itself — ignoring the boolean success signal of a balance-mutating call before committing dependent state — is the same root cause flagged in the report, and the surrounding code in this very file demonstrates the correct pattern is well known but was not applied here.

### Recommendation
Check the return value of `reduceAssetAmountV2` in `ExchangeTransactionActuator.execute()` and throw a `ContractExeException` (or equivalent) if it returns `false`, exactly as done in `TransferAssetActuator` and `ParticipateAssetIssueActuator`, before crediting the counterpart token or committing the exchange pool state.

### Proof of Concept
1. Craft an `ExchangeTransactionContract` where `assetBalanceEnoughV2` (validate-time check) passes but the equivalent internal state consulted by `reduceAssetAmountV2` at execute-time reports insufficient/absent balance for the token being sold (e.g., by racing an `AllowSameTokenName` transition or an asset-key resolution edge case that differs between the two methods).
2. Submit the transaction; `validate()` passes.
3. In `execute()`, `reduceAssetAmountV2` returns `false` and the account's sold-token balance is left unchanged, but the code proceeds to call `addAssetAmountV2` for the bought token, persist the account, and commit the updated exchange pool via `Commons.putExchangeCapsule`.
4. The result is `ret.setStatus(fee, code.SUCESS)` — the trader received tokens without paying, and the exchange pool balances no longer match actual TRC10 backing.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
