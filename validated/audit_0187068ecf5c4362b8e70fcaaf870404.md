### Title
Unbounded memory allocation from attacker-controlled length fields in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE describes ImageMagick's `ReadVIPSImage` allocating memory based on an attacker-supplied length field that is disconnected from the actual amount of data present, letting a crafted file trigger unbounded memory consumption. java-tron's `ValidateMultiSign` and `BatchValidateSign` precompiled contracts contain the same bug class: array-length and per-item byte-length values are read directly from ABI-encoded calldata and used to size allocations, without validating that they are consistent with the real size of the `data` buffer.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` decode a nested ABI array of "signatures" using `extractBytesArray`: [1](#0-0) 

`extractBytesArray` reads `len` (array item count) and, for each item, `bytesLen` (an individual byte-length) straight out of `words`, then calls `extractBytes`: [2](#0-1) 

`extractBytes` performs `Arrays.copyOfRange(data, offset, offset + len)`. `Arrays.copyOfRange` does not require `offset + len <= data.length`; when the requested end exceeds the source array length, Java silently zero-pads the result up to the requested size instead of throwing. Because `bytesLen`/`len` are decoded via `DataWord.intValueSafe()` from attacker-controlled words, an attacker can set this length field to a huge value (up to `Integer.MAX_VALUE`) while sending only a small amount of actual calldata — exactly analogous to ImageMagick trusting a length header that doesn't match the real payload.

The call sites in `ValidateMultiSign`: [3](#0-2) 
and `BatchValidateSign`: [4](#0-3) 
only bound the declared array size (`sigArraySize`/`addrArraySize` vs. `MAX_SIZE`) when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then only guard the `extractSigArray` path (which uses a fixed `SIG_LENGTH`, not attacker data). When that hard-fork switch is disabled, execution falls through to `extractBytesArray`, whose inner per-item `bytesLen` is never validated against `MAX_SIZE`, `data.length`, or any other bound in either code path.

Energy metering does not compensate for this: `getEnergyForData` charges strictly proportional to `data.length / WORD_SIZE`: [5](#0-4) 
so a small, cheap calldata payload can still declare an enormous `bytesLen`, decoupling the energy paid from the memory actually allocated during `execute()` — the same root-cause pattern as CVE-2017-14684, where a length header drove `ResizeMagickMemory` allocation independent of the real input size.

### Impact Explanation
Any account can invoke `ValidateMultiSign`/`BatchValidateSign` at their precompile addresses via a normal `TriggerSmartContract` (CALL/STATICCALL to the fixed precompile address from any contract), reachable from a single signed transaction with no special privileges. By crafting `data` such that a nested length word decodes to a very large value while keeping the outer calldata small (and thus cheap in energy/bandwidth), an attacker can force allocation of very large zero-padded byte arrays inside `extractBytes`/`extractBytesArray`. Repeated or parallel invocation (e.g., via multiple transactions, or the multi-item loop in `BatchValidateSign`, which even spins up a thread pool per signature) can drive excessive heap consumption and pressure the JVM toward `OutOfMemoryError`, degrading or crashing full nodes — a memory-consumption denial of service consistent with the "node crash or halt" impact category in the validation rules.

### Likelihood Explanation
Likelihood is conditional: the bounded (`extractSigArray`) path is only reachable when `VMConfig.allowTvmSelfdestructRestriction()` is active, and that same flag also gates the `sigArraySize > MAX_SIZE` check that precedes the vulnerable `extractBytesArray` call. On networks/chains where this hard-fork bit has not been activated (private/test chains, or chains lagging behind the corresponding TIP), the vulnerable `extractBytesArray` branch is used with no size validation whatsoever, and the bug is trivially and repeatably reachable by any address able to broadcast a transaction. On mainnet where the flag is on, the array-count bound partially mitigates this but does not validate the per-item `bytesLen` against `data.length`, so the extent of exploitability there needs confirmation against current mainnet parameter state (not verifiable purely from static code review).

### Recommendation
- In `extractBytes`, validate `offset >= 0 && len >= 0 && offset + len <= data.length` before calling `Arrays.copyOfRange`, rejecting (returning false/failure) rather than zero-padding oversized ranges.
- In `extractBytesArray`, bound both `len` (item count) and each `bytesLen` against `MAX_SIZE`/a fixed maximum item length and against the real remaining length of `data`, independent of the `allowTvmSelfdestructRestriction` flag, so the guard applies unconditionally rather than only in the newer code path.
- Ensure `getEnergyForData` cannot be bypassed for expensive-to-allocate calldata: either charge energy based on declared array/byte lengths after validating them, or reject requests whose declared lengths exceed the actual `data.length`.

### Proof of Concept
1. Deploy or reuse any contract that can issue an EVM `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address with attacker-controlled calldata (e.g., via `abi.encodeWithSelector`/raw call from Solidity, or directly via `TriggerSmartContract` calldata against the precompile if reachable).
2. Construct `rawData` such that:
   - `words[3]` points to an offset for the "signature array" header.
   - The word at that offset (`len`, the declared array length) is set to a small number (e.g., 1) to pass the `MAX_SIZE` check trivially, or, if `allowTvmSelfdestructRestriction` is disabled, skip that check entirely.
   - The per-item `bytesOffset`/`bytesLen` word for item 0 is set to a very large value (e.g., `0x7FFFFFFF`), while the actual `rawData` byte array is kept short (a few hundred bytes) to minimize energy cost.
3. Send the transaction with sufficient `feeLimit` to cover the small `getEnergyForData` cost (proportional only to the small `data.length`).
4. Observe that `extractBytesArray` → `extractBytes` → `Arrays.copyOfRange(data, offset, offset + bytesLen)` allocates a byte array sized by the huge declared `bytesLen` (backed by zero-padding), consuming disproportionate heap relative to the actual transaction size/cost — repeatable across multiple transactions to accumulate memory pressure on the executing full node.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
