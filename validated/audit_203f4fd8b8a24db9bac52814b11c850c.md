### Title
Post-validation mutation of `output_data_receivers` allows receipts to exceed `max_receipt_size` after passing `NewReceipt` validation - ([File: runtime/runtime/src/verifier.rs])

### Summary
When a contract creates a promise DAG such as `A -then-> B` where `A` calls `promise_return` on a freshly created receipt `C`, receipt `C` is validated once at creation time under `ValidateReceiptMode::NewReceipt` (enforcing `max_receipt_size`), but is later mutated by having `output_data_receivers` appended to it when the DAG is resolved. This mutation happens after the strict size check and is never re-validated under `NewReceipt` mode, so the persisted/forwarded receipt can exceed `max_receipt_size`. This is a confirmed, reproducible bug tracked upstream as [nearcore#12606](https://github.com/near/nearcore/issues/12606) and directly demonstrated by the in-repo test `test_max_receipt_size_promise_return`.

### Finding Description
`runtime/runtime/src/verifier.rs` exposes `ValidateReceiptMode::NewReceipt` vs `ExistingReceipt`, used by `action_validation.rs`/`lib.rs` to decide how strictly to enforce `max_receipt_size` (and related limits) depending on whether a receipt is freshly created in this apply or is one already accepted into the chain. Freshly created receipts get the strict check; receipts that already exist (i.e., previously accepted, presumably already-validated) get the relaxed treatment, on the assumption that a receipt validated once at creation cannot grow afterward.

That assumption is violated by the `promise_return`/DAG-then mechanism. The test-loop test `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs:129-208`) constructs exactly the scenario in the prompt:
- User calls a contract method that builds DAG `A -then-> B`.
- When `A` executes, it creates a new receipt `C` and issues `promise_return`, rewriting the DAG to `C -then-> B`.
- Receipt `C` is created with a size right at `max_receipt_size` and passes `NewReceipt` validation at creation.
- The runtime then appends `output_data_receivers` to `C`'s already-materialized `ActionReceipt` (via the promise-then linkage logic that wires `B`'s input data dependency into `C`'s outputs), growing `C` above `max_receipt_size`.
- The test's own comment states explicitly: *"the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently isn't because of a bug (See https://github.com/near/nearcore/issues/12606)"*.
- The helper `assert_oversized_receipt_occurred` at the end of the test scans block/chunk incoming receipts and asserts that an oversized receipt (`receipt_size > max_receipt_size`) is indeed found in the persisted chain data — proving the mutated receipt is never re-checked with `NewReceipt` and is forwarded/persisted as-is.

The root cause is architectural: `output_data_receivers` mutation occurs downstream of the point where `ValidateReceiptMode::NewReceipt` validation runs, and there is no re-validation pass over receipts whose data dependencies get patched in after the fact (this differs from a truly "existing" receipt coming from another shard, which was validated once and is immutable thereafter — `C` is mutated locally after its own validation).

### Impact Explanation
This matches the "shard-halting panic / consensus divergence" and protocol-limit-bypass category: chunk producers can legitimately (not maliciously — this happens under ordinary contract logic) emit receipts above the documented `max_receipt_size` cap. Because such receipts are outside the documented invariant, any downstream consumer, witness size accounting, or chunk-validator logic that assumes `receipt_size <= max_receipt_size` must special-case them under `ExistingReceipt`/relaxed treatment indefinitely, growing effective witness/receipt-transport size past the documented cap. If tolerance logic for `ExistingReceipt` diverges even slightly between producer and validator, this creates disagreement about whether the receipt is acceptable, which is a state-validity divergence risk. It does not directly let an attacker steal or freeze funds by itself, but it breaks a hard protocol invariant ("every receipt leaving a chunk passed the strict size check at creation") using unprivileged, ordinary contract calls with no need for validator/node privileges.

### Likelihood Explanation
Fully unprivileged and trivially reproducible: an ordinary account deploys a WASM contract that implements the A/B/C promise-then/`promise_return` pattern (available today in the repo's own `near-test-contracts` test contract, methods `max_receipt_size_promise_return_method1`/`assert_test_completed`), then calls it once. No special permissions, no validator access, no race condition — this is a deterministic runtime code path executed by regular `FunctionCall` actions and `promise_batch_then`/`promise_return` host calls. The existing repo test `test_max_receipt_size_promise_return` (and the analogous `test_max_receipt_size_value_return`) already reproduces and asserts the oversized receipt is present in the chain.

### Recommendation
Re-validate receipts under `ValidateReceiptMode::NewReceipt` (or an equivalent strict check) after any post-creation mutation such as appending `output_data_receivers` during DAG resolution/`promise_return` handling, before the receipt is persisted or queued for cross-shard forwarding. Alternatively, reserve size headroom for the maximum possible `output_data_receivers` growth when validating a receipt that may still receive additional output-data receivers, so the final mutated size can never exceed `max_receipt_size`.

### Proof of Concept
Use the existing `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs`:
1. Deploy the test contract; compute `base_receipt_size` for a template `ActionReceipt` and set `args_size = max_receipt_size - base_receipt_size` so receipt `C` is created at exactly `max_receipt_size`.
2. Call `max_receipt_size_promise_return_method1` to build DAG `A -then-> B`, where `A` creates `C` and does `promise_return`.
3. After execution, call `assert_test_completed` to confirm `B` executed (i.e., the oversized receipt was still forwarded/processed rather than rejected).
4. Assert via `assert_oversized_receipt_occurred` that a receipt with `borsh::object_length(receipt) > max_receipt_size` exists among persisted/forwarded receipts in the chain — expected assertion: this check currently **passes** (finds an oversized receipt), demonstrating the bug; a fixed implementation should cause the transaction to fail with `ReceiptValidationError::ReceiptSizeExceeded` instead, and `assert_oversized_receipt_occurred` should find no such receipt (panic "Didn't find receipt with size above max_receipt_size!").
