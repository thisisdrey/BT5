Based on my analysis, I found the closest analog to the OnionShare check-then-act rate-limiting bypass in java-tron's transaction admission path.

### Title
Denial of Service via Non-Atomic "Too Many Pending" Check in `broadcastTransaction`/`pushTransaction` Allows Unbounded Concurrent Mempool Flooding - ([File: framework/src/main/java/org/tron/core/Wallet.java], [File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
`Wallet.broadcastTransaction` gates admission into the mempool with a single, non-atomic `dbManager.isTooManyPending()` check before calling `dbManager.pushTransaction(trx)`. `isTooManyPending()` and the subsequent enqueue into `pushTransactionQueue` are two separate, unsynchronized operations, exactly mirroring the OnionShare flaw where a per-second directory-count guard was checked once but not enforced atomically against concurrent writers, letting a burst of parallel requests race past the limit.

### Finding Description
`Wallet.broadcastTransaction` performs the admission check as follows: [1](#0-0) 

This check calls `Manager.isTooManyPending()`, defined as a size comparison with no lock held across the check-then-act window: [2](#0-1) 

Immediately after the check passes, `Wallet.broadcastTransaction` calls `dbManager.pushTransaction(trx)`, which unconditionally appends to the unbounded `pushTransactionQueue` (a plain `LinkedBlockingQueue` with no capacity bound) before doing any expensive work: [3](#0-2) 

Because the check (`isTooManyPending`) and the act (`pushTransactionQueue.add(trx)`) are not protected by a common lock or CAS, any number of concurrent gRPC/HTTP `broadcastTransaction` callers can simultaneously observe `isTooManyPending() == false` and all proceed to enqueue, each additionally triggering full signature validation and `processTransaction` (VM execution, `revokingStore` session build/merge) inside the subsequent `synchronized(this)` block: [4](#0-3) 

This is structurally identical to the OnionShare bug class: a fixed threshold check that is not atomically coupled to the resource-consuming operation it is meant to gate, so an attacker who issues a burst of concurrent requests (trivially scriptable, exactly as in the report's `parallel`+`curl` PoC) can push far more transactions into the pending/queued state than `maxTransactionPendingSize` intends to allow, at the cost of one signature verification and one `processTransaction`/DB-session cycle per accepted transaction.

### Impact Explanation
An unauthenticated, unprivileged client (any gRPC/HTTP API caller reaching `Wallet.broadcastTransaction`) can send a large burst of concurrent broadcast requests. Because the pending-size guard is TOCTOU-racy and `pushTransactionQueue` is unbounded, all of them can bypass the intended cap simultaneously, each consuming CPU for `validateSignature`/`processTransaction` and creating/merging a `revokingStore` session under the global `Manager` monitor lock (`synchronized(this)`). Since block production (`generateBlock`) and block application (`pushBlock`/`processBlock`) also require this same lock and iterate the growing `pendingTransactions`/`pushTransactionQueue`, sustained flooding can starve legitimate transaction processing and block production/consensus threads, degrading the node to the point that it can no longer serve transaction broadcast and block-production duties in a timely manner — i.e., an API/node the node can no longer effectively serve.

### Likelihood Explanation
The `broadcastTransaction` RPC/HTTP endpoint is reachable by any client without special permission (only bounded by the generic `GlobalRateLimiter`/QPS defaults, which are far above what's needed to build a burst that races the check, similar to how OnionShare's fixed per-second cap was easily overrun with thousands of parallel connections). No cryptographic secrets or privileged roles are required — only network access to the node's public API, exactly matching the reachable-path constraint (unprivileged transaction broadcaster).

### Recommendation
- Make the pending-size admission check atomic with the enqueue: hold a single lock (or use an atomic counter with compare-and-increment) across both the `isTooManyPending()` read and the `pushTransactionQueue.add`/`pendingTransactions.add` write in `Manager`, rejecting once the bound is exceeded instead of only checking beforehand.
- Bound `pushTransactionQueue` itself (e.g., construct it with a fixed capacity derived from `maxTransactionPendingSize`) so that `offer()` fails fast once full, rather than relying solely on the advisory `isTooManyPending()` check performed by the caller.
- Consider moving the admission check inside the same `synchronized` block that performs `pendingTransactions.add(trx)` in `pushTransaction`, so concurrent callers are serialized against the shared counter before doing expensive signature/VM work.

### Proof of Concept
1. Configure a node with a small `maxTransactionPendingSize` (e.g., 200) as in `common/src/main/resources/reference.conf`.
2. From a single unprivileged client, fire a large number (e.g., 5,000–10,000) of well-formed, distinct `broadcastTransaction` gRPC/HTTP calls concurrently (e.g., using a thread pool or a tool such as GNU `parallel` + `grpcurl`/`curl`, analogous to the report's PoC script), each with a unique valid transaction.
3. Observe via the `tron:manager_queue_size` metric (`MetricLabels.Gauge.QUEUE_QUEUED`/`QUEUE_PENDING`) or `Manager.getCachedTransactionSize()` that the combined queue size significantly exceeds `maxTransactionPendingSize`, because many callers passed `isTooManyPending()` before any of their enqueues were reflected in the size.
4. Observe increased CPU usage and possible processing delays for block generation/application caused by the burst of concurrent `validateSignature`/`processTransaction`/`revokingStore` session work performed under the shared `Manager` lock.
