### Title
Active-Permission Keys Can Escalate to Full Owner Control via `AccountPermissionUpdateContract` — ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateContract` — the transaction type used to reconfigure an account's Owner/Witness/Active permission structure — is not restricted to being authorized only by the account's Owner permission (`permission_id = 0`). Because the contract type is not excluded from the set of operations that can legally be assigned to an `Active` permission, and the signature-verification path treats any permission whose bitmap contains this contract type as sufficient authorization to execute it, a lower-trust, delegated "Active" key can rewrite the account's Owner permission entirely, seizing full control of the account and locking out the legitimate owner — structurally the same class of bug as the EC-CUBE finding, where a security-configuration endpoint could be reached and overwritten without passing through the higher-trust gate that was supposed to protect it.

### Finding Description
Tron's multisig model has three permission tiers: Owner (id 0, full control including permission management), Witness (id 1), and Active (id ≥2, restricted to a whitelist of contract types encoded as a 256-bit `operations` bitmap on the `Permission` message) [1](#0-0) .

When a transaction is signed and verified, `TransactionCapsule.checkPermission` only enforces that, for a non-zero `permissionId`, the permission type must be `Active` and that `checkPermissionOperations` confirms the specific contract type's bit is set in that permission's operations bitmap — there is no special case forbidding `AccountPermissionUpdateContract` from being included in that bitmap: [2](#0-1) 

`AccountPermissionUpdateActuator.checkPermission` (the validator invoked when the *contents* of the new permission set are checked) only rejects operation bits that are not in `dynamicStore.getAvailableContractType()`; the test `checkAvailableContractTypeCorrespondingToCode` shows that the only contract types excluded from the "available" bitmap are `UNRECOGNIZED`, `ClearABIContract`, and `UpdateBrokerageContract` — `AccountPermissionUpdateContract` (type 46) is *not* excluded, so it is a legal bit to set in an Active permission's operations: [3](#0-2) [4](#0-3) 

Finally, `AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's Owner permission (and Witness/Active permissions) from the contract's fields, with no re-check of which permission signed the transaction: [5](#0-4) [6](#0-5) 

Consequently, if an account's Owner ever creates (or is induced to accept, e.g. via a wallet/dapp default template) an Active permission whose `operations` bitmap includes bit 46 (`AccountPermissionUpdateContract`), any key holding that Active permission can sign and broadcast an `AccountPermissionUpdateContract` transaction with `permission_id` set to that Active permission's id. It will pass `checkPermission`/`checkPermissionOperations` (Active permission legally authorizes this contract type) and `AccountPermissionUpdateActuator.validate()` (which never inspects which permission signed the transaction), and `execute()` will replace the account's Owner permission with keys entirely controlled by the attacker.

This mirrors the EC-CUBE root cause precisely: a security-critical reconfiguration action (`/admin/two_factor_auth/set` in EC-CUBE, `AccountPermissionUpdateContract` here) is reachable and fully executable using a lower-trust credential (an unauthenticated-but-password-holding session in EC-CUBE, an Active-tier key here) instead of being gated behind the highest trust tier (2FA-verified session / Owner permission).

### Impact Explanation
An attacker who compromises (or is legitimately delegated, e.g. an exchange hot-wallet automation key, a dapp service key, or any third-party integration key) an Active-permission key whose operations bitmap includes `AccountPermissionUpdateContract` can:
- Overwrite the account's Owner permission with attacker-controlled keys, permanently locking out the legitimate owner.
- Subsequently exercise full control over the account, including its balance, TRC10/TRC20 asset operations, staking/voting, and any smart-contract-owning capabilities tied to that account — constituting unauthorized account takeover and potential permanent freezing/theft of funds.

This is a privilege-escalation vulnerability reachable purely by broadcasting a single signed transaction from an account holder who is only supposed to have restricted "Active" capability, not full Owner capability.

### Likelihood Explanation
Exploitability depends on whether an Active permission with the `AccountPermissionUpdateContract` bit set exists on the target account. Because the actuator's validator does not exclude this contract type from the allowed operations set, nothing on-chain prevents an account owner (or a wallet/tool that pre-fills default operations) from creating such an over-privileged Active permission, and there is no on-chain warning or restriction communicated to the user at permission-creation time. Given the sensitivity of this specific contract type (it is the sole mechanism for permission/ownership management), the lack of an explicit carve-out is a design gap rather than a purely theoretical one — analogous to EC-CUBE's oversight of leaving the 2FA-config route out of its auth-exclusion list.

### Recommendation
- In `AccountPermissionUpdateActuator.checkPermission`/`validate()`, explicitly reject `AccountPermissionUpdateContract` (and ideally `WitnessUpdateContract`/other identity-critical contract types) from being settable in an `Active` permission's `operations` bitmap, mirroring the existing exclusion already applied to `UpdateBrokerageContract` and `ClearABIContract`.
- Alternatively/additionally, enforce in `TransactionCapsule.checkPermission` / `AccountPermissionUpdateActuator.validate()` that transactions of type `AccountPermissionUpdateContract` must be signed using `permission_id == 0` (Owner) regardless of what the account's stored Active permission operations bitmap allows.

### Proof of Concept
1. Account `A` (Owner key `K_owner`) creates an Active permission `P_active` (id=2) for a secondary key `K_active`, using the framework's `createDefaultActivePermission` helper or a custom operations bitmap that includes bit 46 (`AccountPermissionUpdateContract`) — this is achievable without any additional restriction check in `checkPermission`.
2. Attacker obtains `K_active` (e.g., via a compromised integration/service).
3. Attacker crafts an `AccountPermissionUpdateContract` transaction for account `A`, sets `Transaction.Contract.Permission_id = 2`, and sets `owner` field to a new `Permission` whose `keys` list contains only attacker-controlled addresses.
4. Attacker signs with `K_active` and broadcasts.
5. `TransactionCapsule.validateSignature` → `checkPermission(2, P_active, contract)` succeeds because `P_active.getType() == Active` and `checkPermissionOperations` finds bit 46 set.
6. `AccountPermissionUpdateActuator.validate()` passes (all structural checks on the new permission are satisfied).
7. `AccountPermissionUpdateActuator.execute()` overwrites `A`'s Owner permission with the attacker's keys via `AccountCapsule.updatePermissions` — full account takeover completed using only an Active-tier key.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
