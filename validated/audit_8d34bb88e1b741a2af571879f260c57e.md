Audit Report

## Title
Snowbridge relayer reward payout on BridgeHub advances to "paid" state on XCM dispatch acceptance rather than confirmed AssetHub-side execution, permanently losing rewards on destination-side `DepositAsset` failure - (File: `bridges/modules/relayers/src/lib.rs`, `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`pallet-bridge-relayers::do_claim_rewards` deletes the relayer's `RelayerRewards` ledger entry and emits `Event::RewardPaid` as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For `BridgeReward::Snowbridge`, `pay_reward` is `PayAccountOnLocation::pay_reward`, which only validates and enqueues an XCM to AssetHub via `XcmSender::deliver` — it never waits for or confirms that the destination-side `DepositAsset` into the relayer-supplied `beneficiary` actually succeeds. If AssetHub-side execution fails, the assets are trapped there while BridgeHub has already irreversibly erased the reward record and reported success.

## Finding Description
`do_claim_rewards` takes the reward out of storage, calls `T::PaymentProcedure::pay_reward`, and only restores/aborts on an `Err` return; on `Ok`, the storage entry stays cleared and `RewardPaid` is emitted unconditionally: [1](#0-0) 

For the Snowbridge reward kind, `pay_reward` is `PayAccountOnLocation::pay_reward`, which builds an XCM containing `DescendOrigin(InboundQueueLocation)`, `UniversalOrigin(GlobalConsensus(EthereumNetwork))`, `ReserveAssetDeposited`, and `DepositAsset { assets, beneficiary }` targeting `AssetHubLocation`, calls `validate_send`, charges local fees via `XcmExecutor::charge_fees`, and calls `XcmSender::deliver(ticket)`. It returns `Ok(())` the instant delivery is accepted into the outbound queue, with no confirmation of AssetHub-side execution or the `DepositAsset` outcome: [2](#0-1) 

The `beneficiary` for the `AssetHubLocation` variant is an arbitrary `Location` chosen by the relayer at call time via the public `claim_rewards_to` extrinsic, as shown in the integration test's use of `BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::V5(relayer_location))`: [3](#0-2) 

If that `DepositAsset` fails on AssetHub (unregistered asset for the beneficiary, beneficiary below existential deposit, bad location, etc.), the remaining holding-register assets get trapped under the composed origin produced by the `DescendOrigin`+`UniversalOrigin` instructions — a virtual, non-signed origin that no ordinary account can reproduce via `pallet_xcm::claim_assets`. This is the same trap-origin-mismatch bug class the codebase already fixed once for the *inbound message default claimer* path via `pr_11919` (which corrected a fallback claimer `Location` mismatch that made trapped funds unrecoverable): [4](#0-3)  — but this equivalent fix was never applied to the reward-payment path. The existing negative test in the repo (`claim_snowbridge_rewards_to_local_account_fails`) only demonstrates that `pay_reward` fails cleanly for a `LocalAccount` beneficiary (an unsupported variant, rejected at construction, before any XCM is sent), which is a different, benign failure mode; it does not cover the case of a valid-looking `AssetHubLocation` beneficiary whose deposit fails downstream after dispatch succeeds: [5](#0-4) 

No mechanism in `do_claim_rewards` or `pay_reward` re-credits `RelayerRewards` or exposes a rescue path if the dispatched XCM later fails execution on AssetHub.

## Impact Explanation
This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Marking a reward as paid and deleting the ledger entry based solely on successful XCM *dispatch* (not *execution*) can permanently destroy a relayer's legitimately earned reward with no retry path (ledger entry gone) and generally no accessible claim path (the AssetHub-side trap origin is not reproducible by a signed account). This matches the allowed impact category of "permanent user-fund ... lock" / "duplicate settlement or payout" for the relayer's own funds.

## Likelihood Explanation
The trigger is reachable through the public, unprivileged `claim_rewards_to` extrinsic with a `BridgeRewardBeneficiaries::AssetHubLocation` value that fails `DepositAsset` checks on AssetHub (unregistered foreign asset for that account, below-ED account, or malformed location) — no governance, admin, or malicious-actor assumption is required, and it can occur from an honest relayer's configuration mistake or a transient AssetHub-side registration/ED issue. Once triggered, it is irreversible because the ledger entry is erased on BridgeHub before AssetHub confirms anything.

## Recommendation
Do not clear `RelayerRewards` / emit `RewardPaid` until AssetHub-side execution success is confirmed (e.g., via a receipt/acknowledgement mechanism back to BridgeHub), or make the reward-claim flow reversible by only removing the ledger entry once execution confirmation is received. Alternatively, apply the same fix pattern used for the inbound-queue default-claimer trap (`pr_11919`) to this path: ensure the deposit target/claimer used in the reward XCM maps to a location the relayer can reproduce with a signed `claim_assets` call if `DepositAsset` fails.

## Proof of Concept
1. Relayer accrues a Snowbridge reward via `register_reward` on BridgeHub.
2. Relayer calls `pallet_bridge_relayers::claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(some_location))` where `some_location` will fail AssetHub's `DepositAsset` check (e.g., unregistered foreign asset for that account, or an account below ED).
3. On BridgeHub: `validate_send` + `deliver` succeed; `do_claim_rewards` deletes the `RelayerRewards` entry and emits `RewardPaid` per [1](#0-0)  and [6](#0-5) .
4. On AssetHub, the XCM executes and `DepositAsset` fails; remaining holding assets are trapped under the `DescendOrigin`+`UniversalOrigin` composed origin.
5. Relayer has no reward record on BridgeHub to retry and no signed-origin path to reclaim the trapped assets on AssetHub — funds are permanently lost. A unit/integration test extending `claim_rewards_works` in `snowbridge_v2_rewards.rs` with a beneficiary location that AssetHub rejects at deposit time (rather than at construction time) would reproduce this.

```rust
	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
```

```text
title: 'Snowbridge: Set default asset claimer to local network'
doc:
- audience: Runtime Dev
  description: |-
    The inbound-queue v2 message converter falls back to the Snowbridge sovereign
    account on AssetHub as the asset claimer when no explicit claimer is supplied.
    Previously this fallback used `AccountId32 { network: None, .. }`, which did
    not match the location AssetHub's signed-origin converter produces (it sets
    `network: Some(LocalNetwork)`). The trap-key hash stored on `AssetsTrapped`
    therefore could not be matched by a signed `polkadotXcm.claim_assets` call,
    making default-claimer trapped funds effectively unrecoverable without a
    runtime upgrade.

    This PR sets `network: Some(LocalNetwork::get())` on the fallback claimer so
    its `Location` agrees with what `SignedToAccountId32<_, _, LocalNetwork>`
    yields on AssetHub, and adds a test covering the no-claimer-supplied path.
```
