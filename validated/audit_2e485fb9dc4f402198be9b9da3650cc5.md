### Title
Unprivileged Caller Can Unfreeze a Victim's Frozen Fungible Asset Store via `migrate_coin_store_to_fungible_store` — (`aptos-move/framework/aptos-framework/sources/coin.move`)

---

### Summary

`migrate_coin_store_to_fungible_store` is a permissionless `public entry fun` that accepts an arbitrary `vector<address>`. When a victim holds an **unfrozen** `CoinStore<CoinType>` with a non-zero balance alongside a **frozen** primary `FungibleStore`, the migration logic unconditionally overwrites the FA store's `frozen` flag with the CoinStore's `frozen` value (`false`), effectively unfreezing the FA store without any authorization check.

---

### Finding Description

`migrate_coin_store_to_fungible_store` requires no signer for the victim accounts: [1](#0-0) 

It delegates to `maybe_convert_to_fungible_store`, which destructures the victim's `CoinStore` and reads its `frozen` field: [2](#0-1) 

After migrating the coin balance into the primary FA store, it synchronizes the frozen flag: [3](#0-2) 

The condition `frozen != fungible_asset::is_frozen(store)` is symmetric. The developer comment only describes the intended direction (frozen CoinStore → freeze FA store), but the code also fires in the **reverse** direction: if `CoinStore.frozen = false` and `FA store.frozen = true`, the branch executes `set_frozen_flag_internal(store, false)`.

`set_frozen_flag_internal` is `public(friend)` and performs **no authorization check** — it directly mutates the store's frozen bit: [4](#0-3) 

The legitimate freeze path (`set_frozen_flag`) requires a `TransferRef` whose metadata matches the store: [5](#0-4) 

The migration path bypasses this entirely.

---

### Impact Explanation

A coin issuer that freezes a user's primary FA store (e.g., for compliance or sanctions enforcement) via `primary_fungible_store::set_frozen_flag` loses that enforcement guarantee. Any unprivileged third party can call `migrate_coin_store_to_fungible_store<CoinType>([victim])` to silently unfreeze the store, re-enabling deposits and withdrawals that the issuer explicitly blocked. This constitutes unauthorized reversal of a freeze — a direct asset-control bypass.

---

### Likelihood Explanation

The preconditions are realistic and commonly satisfied during the coin-to-FA migration period:

1. Victim has a `CoinStore<CoinType>` with `coin.value > 0` and `frozen = false` (the default state for most users).
2. The coin issuer has frozen the victim's primary FA store via `TransferRef`.
3. The attacker submits a single transaction with no special privileges.

All three conditions can coexist naturally during the migration window, and the entry point is publicly callable by anyone.

---

### Recommendation

The freeze-synchronization logic should only propagate the CoinStore's frozen state **onto** the FA store when the CoinStore is frozen (i.e., only freeze, never unfreeze via migration). Replace the symmetric check with a one-directional guard:

```move
// Only freeze the FA store if the CoinStore was frozen; never unfreeze via migration.
if (frozen && !fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, true);
};
```

This preserves the intended semantic (a frozen CoinStore propagates its freeze to the FA store) while preventing migration from overriding an issuer-imposed freeze on the FA store.

---

        store: Object<T>, frozen: bool
