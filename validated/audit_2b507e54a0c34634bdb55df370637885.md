### Title
`DepositToken.transfer`/`transferFrom` become unusable when `MasterOracle` reverts, freezing user collateral tokens — (File: contracts/DepositToken.sol)

### Summary
The external report describes a token whose `transfer`/`transferFrom` paths internally call an oracle (`pricePerShare()`), so an oracle outage freezes user funds. Metronome's `DepositToken` exhibits the same bug class: every `transfer` and `transferFrom` calls `_revertIfLocked`, which calls `unlockedBalanceOf`, which unconditionally calls `Pool.debtPositionOf`, which queries `masterOracle().quoteTokenToUsd(...)` for every deposit and debt token of the account. If any underlying oracle feed reverts (e.g., a stale/invalid Chainlink round), the whole transfer path reverts and users cannot move their `msdTOKEN` collateral positions.

### Finding Description
- `DepositToken.transfer` calls `_revertIfLocked(_msgSender, amount_)` before `_transfer` [1](#0-0) 
- `DepositToken.transferFrom` calls `_revertIfLocked(sender_, amount_)` [2](#0-1) 
- `_revertIfLocked` enforces `amount_ <= unlockedBalanceOf(account)`, and `unlockedBalanceOf` always calls `pool.debtPositionOf(account_)` first [3](#0-2) 
- `Pool.debtPositionOf` calls `debtOf` and `depositOf`, both of which loop over the account's tokens and call `masterOracle().quoteTokenToUsd(...)` [4](#0-3) [5](#0-4) 

Because `depositOf` quotes the USD value of the deposit token itself via the oracle, even an account with zero debt hits the oracle on every transfer — the `_debtInUsd == 0` early return in `unlockedBalanceOf` only happens *after* `debtPositionOf` (and therefore all oracle calls) completes. There is no cached price fallback, unlike the `WrappedIbbtcEth` behavior in the external report.

### Impact Explanation
Temporary freezing of funds: while any oracle feed used by `MasterOracle` for the account's collateral or synthetic tokens is reverting (stale round, aggregator update failure, sequencer outage on L2s where uptime checks revert, etc.), all `transfer`, `transferFrom`, `withdraw`, `withdrawFrom`, and liquidation-adjacent `seize`-style flows that route through `_revertIfLocked`/`debtPositionOf` will revert. Users cannot exit positions or move collateral tokens until the oracle recovers. Note `seize` itself bypasses the lock check (`onlyIfCanSeize` → `_transfer` directly), so liquidations still work — the freeze is asymmetric and harms only the user.

### Likelihood Explanation
This requires no attacker action — it triggers whenever a configured oracle reverts, which is a real-world occurrence (Chainlink feed staleness, L2 sequencer downtime grace-period reverts, upstream vault `pricePerShare` failures for vault-share collateral). Any EOA can reproduce it trivially by calling `transfer` on a `DepositToken` while the oracle is in a reverting state; no privileged role is needed to observe the freeze.

### Recommendation
Decouple the ERC-20 transfer path from liveness-critical oracle calls. Options:
- Let `transfer`/`transferFrom` skip the lock check when the oracle call fails (e.g., wrap `debtPositionOf` in a try/catch and, on failure, allow transfers but still block `withdraw`, since withdrawals reduce collateral backing debt while transfers do not change aggregate collateralization).
- Alternatively, only consult the oracle when the account actually has debt: pre-check `debtTokensOfAccount.length(account) == 0` cheaply and skip `debtPositionOf`, and consider try/catch around `depositOf` for the debt-free case.
- Ensure `withdraw` keeps the strict check since it removes collateral from the system.
