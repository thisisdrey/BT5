### Title
Attacker can force-fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `deposit(onBehalfOf)` / `transfer`, permanently blocking new collateral deposits and debt positions for that account - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of `depositTokensOfAccount` and `debtTokensOfAccount`. Entries are added automatically whenever an account's `DepositToken` or `DebtToken` balance goes from 0 to positive — with no opt-in from the account. An unprivileged attacker can therefore fill a victim's list with dust positions (via `DepositToken.deposit(amount, victim)` or `DepositToken.transfer(victim, 1)`), after which every path that would add a new token to the victim's list reverts with `UserReachedMaxTokens`.

### Finding Description
`Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (Pool.sol:143-148). It guards `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount`, which are invoked from token contracts, not by the account itself:

- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `balanceBefore == 0` (DepositToken.sol:486-488). `deposit(amount_, onBehalfOf_)` mints directly to an arbitrary `onBehalfOf_` with no consent required (DepositToken.sol:211-237).
- `DepositToken._transfer` does the same for any first-time recipient (DepositToken.sol:517-520), so `transfer`/`transferFrom` of dust also fills the victim's set.
- `DebtToken` mints (borrow/issue) add entries to `debtTokensOfAccount` through the same capped path, so the attack also blocks the victim from opening debt in any new synthetic.

There is no bounded-ness check on *whose* set gets filled; the only requirement is that the transferred/minted amount is nonzero. Entries are only removed when the account's balance of that token returns to zero (`removeFromDepositTokensOfAccount`, DepositToken.sol:523-525). While a victim with no debt can self-cleanse by transferring dust out, a victim with outstanding debt may have `unlockedBalanceOf` equal to zero on the dust tokens (`_revertIfLocked`, DepositToken.sol:180-182, 383-398), making the slots non-removable while the debt exists — precisely when the victim most needs to add collateral.

### Impact Explanation
- Any `deposit`, `transfer`, `seize`, or `issue`/`mint` that would introduce a new token into the victim's sets reverts. The victim cannot deposit into a new collateral type and cannot borrow a new synthetic.
- Combined with a deteriorating position (issuable → 0, dust locked), the victim cannot free the occupied slots and cannot add any new collateral to restore health — the position is forced into liquidation. This is a temporary freezing of funds / forced-liquidation griefing inflicted entirely through public entry points.
- The grief applies to any account, including SmartFarmingManager-held positions and liquidators targeted via `seize` (a liquidator can switch addresses, but a victim position owner cannot).

### Likelihood Explanation
- Cost is dust amounts of each listed collateral; no privileged role needed (`deposit` is `whenNotPaused`/`nonReentrant` only, `onlyIfDepositTokenExists`).
- Full lockout requires the pool's deposit+debt token offerings to reach the victim's remaining slots; where fewer than 30 tokens exist, the attacker can still occupy all existing slots and front-run additions of new tokens to maintain the cap.
- No modifier (`onlyIfAdditionWillNotReachMaxTokens` is itself the only check) or guard prevents unsolicited set entries; consentless `onBehalfOf` deposits make the attack trivially reachable.

### Recommendation
- Charge the max-tokens accounting to the *payer/initiator*, or let accounts opt out: e.g., only add to `depositTokensOfAccount` when `onBehalfOf_ == _msgSender()` on `deposit`, and/or require recipient consent for first-time transfers.
- Alternatively, exempt removals from the lock check so a victim can always purge dust tokens (`transfer` of a token contributing zero collateral value could bypass `_revertIfLocked`), or skip adding tokens below a minimum-balance threshold.

### Proof of Concept
```solidity
// Foundry fork test against deployed Pool/DepositTokens
function test_fillVictimTokenSet() public {
    address victim = address(0xBEEF);
    address[] memory depositTokens = pool.getDepositTokens(); // registered collaterals

    // Attacker deposits 1 wei of each collateral on behalf of the victim
    for (uint256 i; i < depositTokens.length; ++i) {
        IDepositToken dt = IDepositToken(depositTokens[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), address(this), 10);
        underlying.approve(address(dt), 10);
        dt.deposit(1, victim); // mints dust to victim -> addToDepositTokensOfAccount(victim)
    }
    // Top up remaining slots toward 30 via debt tokens the attacker repays/mints,
    // or by waiting for/griefing newly added tokens.

    // Victim can no longer deposit any collateral token they don't already hold:
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDepositToken.deposit(1e18, victim);

    // Victim cannot borrow a new synthetic either (DebtToken mint hits the same cap).
}
```
