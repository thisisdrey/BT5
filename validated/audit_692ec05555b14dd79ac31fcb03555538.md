### Title
Transactional object packing commits unvalidated Git objects into repository storage without fsck verification - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
Gitaly's write-ahead-log (WAL) based transaction manager packs objects from a client-supplied quarantine directory directly into the committed repository state without ever verifying object validity (equivalent to `git fsck`/`git index-pack --strict`). The function's own documentation acknowledges this gap. Because this pack becomes part of the durable, replicated repository state, a single malformed push can permanently corrupt objects that every subsequent reader/writer of the repository — not just the pusher — must contend with, closely mirroring the reported bug class where unvalidated attacker-controlled data is committed into shared state and breaks future honest participants.

### Finding Description
`packObjects` walks new reference tips together with the objects a client wrote into its object quarantine directory, then packs and indexes them via `git pack-objects` / `git index-pack --stdin --rev-index`, staging the resulting `.pack`/`.idx`/`.rev` files to be logged into the transaction's WAL entry and ultimately committed into the partition: [1](#0-0) 

The function's own doc comment states plainly that no validation happens: [2](#0-1) 

`index-pack` is invoked without `--strict`/`--fsck-objects`, so it only performs structural pack decoding, not object-content validation (bad tree entries, malformed commit/tag headers, etc. are not caught): [3](#0-2) 

This differs from the classic `git-receive-pack` code path, where Gitaly explicitly configures `transfer.fsckObjects`/`receive.fsckObjects` to reject malformed objects up front: [4](#0-3) 

However, the WAL transaction manager's `packObjects` path is a separate, lower-level mechanism used whenever a transaction has a quarantine and reference updates to apply (e.g. via RPCs that write into quarantine directories such as `FetchRemote`, `FetchSourceBranch`, and other mutator RPCs going through the transactional storage layer), and it does not re-derive or enforce the fsck guarantee at the point objects are actually packed and persisted into the log. The objects it packs are taken straight from whatever the client/quarantine populated, with no re-validation before they are written into the authoritative WAL-backed pack.

The nearby quarantine-directory validation code (`ObjectDirectoryPath`, `QuarantineDirectoryPrefix`) only defends against *path*-level attacks (directory traversal, cross-repository quarantine confusion) — it says nothing about the *content* of the objects inside a legitimately-scoped quarantine directory: [5](#0-4) [6](#0-5) 

### Impact Explanation
Once malformed objects are packed and logged via the WAL, they become part of the durable, replicated repository object database for every node/replica applying that log entry — not merely a rejected, quarantined push. Subsequent operations (git operations by other users, replication, housekeeping/repack, `git fsck`, or Rails-driven Gitaly RPCs) that touch these objects can fail or behave in undefined ways, potentially halting repository access for all users of that repository (denial of service), analogous to the reported scenario where a single malicious actor's unvalidated data locks out all future honest participants. This is an explicitly acknowledged design gap tracked as gitlab-org/gitaly issue #5779, referenced directly in the source comment.

### Likelihood Explanation
Likelihood is bounded by how reachable the `packObjects` path is from ordinary (non-privileged) actions. It is invoked for any transaction that touches a repository with a quarantine and pending reference updates in the transactional (WAL) storage backend, which is exercised by normal internal RPCs such as `FetchRemote`/`FetchSourceBranch` and other mutator flows that stage objects via quarantine before committing reference updates. An ordinary user triggering a fetch/import/mirror-update RPC that introduces attacker-influenced object content (e.g., objects fetched from a source repository the user controls) can reach this path. The severity is mitigated somewhat because most user-facing pushes still go through `git-receive-pack` with fsck enabled first, but the transaction manager's packing step itself provides no independent, defense-in-depth validation — matching the report's finding that a single unvalidated code path is sufficient to corrupt shared state.

### Recommendation
- Enable `git index-pack --strict` (or run `git-fsck` against the assembled pack/quarantine objects) before the objects are logged into the WAL entry in `packObjects`, so no unvalidated object is ever admitted to durable transaction state.
- Ensure this validation is enforced uniformly across every mutator RPC path that stages objects into a quarantine directory ahead of the transaction manager, not only the classic `git-receive-pack` push path.
- Track resolution against the already-filed gitlab-org/gitaly#5779 to close this acknowledged gap.

Not applicable — the vulnerability is evidenced directly by the shipped source code and its own doc comment acknowledging that packed objects are not validated: [1](#0-0)

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
