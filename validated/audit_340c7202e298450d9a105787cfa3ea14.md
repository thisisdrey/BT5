### Title
Receivership liquidation `start_liquidation`/`start_deleverage` compute health checks using stale bank interest state - ([File: programs/marginfi/src/instructions/marginfi_account/liquidate_start.rs])

### Summary
`start_receivership()` — the shared logic behind `start_liquidation` and `start_deleverage` — calls `check_pre_liquidation_condition_and_get_account_health()` to decide whether an account is liquidatable, but it never calls `Bank::accrue_interest()` on the account's banks beforehand. Unlike the classic `lending_account_liquidate` path, which explicitly accrues interest on both the asset and liability banks before running the liquidatability check, the receivership entrypoint evaluates health using whatever interest/exchange-rate state the banks happen to have from their last accrual.

### Finding Description
In `lending_account_liquidate()`, the correct ordering is followed: interest is accrued on `asset_bank` and `liab_bank` immediately before `check_pre_liquidation_condition_and_get_account_health()` is invoked. [1](#0-0) 

In contrast, `start_liquidation()` / `start_deleverage()` call `start_receivership()`, which runs the liquidatability/health check directly against the loaded `MarginfiAccount` and the banks referenced by its remaining accounts — with no `accrue_interest()` call anywhere in this function or its callers before the check: [2](#0-1) 

The health/liquidatability computation relies on `Bank::get_asset_amount`/`get_liability_amount`, which are derived from `asset_share_value`/`liability_share_value` — values only updated by `accrue_interest()`: [3](#0-2) [4](#0-3) 

Per the receivership liquidation rules, only `ComputeBudgetProgram` and Kamino-refresh instructions are allowed before `start_liquidation`/`start_deleverage`, and validated via `validate_instructions`/`validate_ix_first`: [5](#0-4) 

This means there is no mechanism, within or before the `start_liquidation` transaction, to force interest accrual on the liquidatee's banks prior to the liquidatability check — the check is performed strictly against stale interest state (in the sense of the GMX-analog bug class: liquidation-decision checks run before global interest/fee state is refreshed).

### Impact Explanation
If a liability bank has accumulated enough unaccrued interest since its `last_update` that the position is unhealthy only after that interest is applied, `check_pre_liquidation_condition_and_get_account_health()` in `start_receivership()` (called with `ignore_healthy = false` for `start_liquidation`) will see the account as healthy and revert with `MarginfiError::HealthyAccount`, blocking a legitimate liquidation attempt in that block/transaction. This is a delayed-liquidation issue: an account that should be liquidatable is not, letting its debt/collateral ratio worsen further before it can actually be liquidated (once some other transaction accrues interest on the relevant bank), which can increase realized bad debt/insurance-fund losses — consistent with the accepted impact class of insolvency/bad debt.

Note: unlike `end_receivership`, where post-health uses `HealthPriceMode::Cached` (recomputed against the live-priced/health-cached values written at `start_receivership`), the initial gate at `start_receivership` is the only chance to correctly classify the account as liquidatable at that moment; if it is wrong due to stale interest, the liquidation cannot even begin.

### Likelihood Explanation
Interest accrual on marginfi is generally permissionless and can be triggered by anyone via `lending_pool_accrue_bank_interest`, so in most cases a liquidator could work around this by simply also submitting an accrue-interest instruction — but not within the same protected liquidation transaction, since only `ComputeBudgetProgram` and Kamino refresh ixs are permitted before `start_liquidation`. The liquidator would need to accrue interest in a prior transaction, which is subject to being front-run/sandwiched or simply delayed by one slot, reproducing the "delayed liquidation" impact described in the original GMX report. The likelihood is moderate: it requires a bank whose interest hasn't been accrued recently and where accrual would flip the account from healthy to unhealthy — a realistic but not universal scenario, especially for low-traffic banks.

### Recommendation
Call `Bank::accrue_interest()` on every bank referenced by the liquidatee's active balances (the banks backing `remaining_ais`) inside `start_receivership()`, before invoking `check_pre_liquidation_condition_and_get_account_health()` — mirroring the pattern already used in `lending_account_liquidate()`.

### Proof of Concept
1. User deposits collateral in Bank A and borrows against Bank B; Bank B has not had `lending_pool_accrue_bank_interest` called for a long period, so `last_update` is stale.
2. Time passes such that, once interest is properly accrued on Bank B, the user's health would drop below zero (liquidatable), but the on-chain `liability_share_value` for Bank B is still stale/lower, keeping the computed health above zero.
3. A liquidator submits `start_liquidation` (with only the allowed preceding Kamino-refresh/ComputeBudget ixs) targeting this account.
4. `start_receivership()` → `check_pre_liquidation_condition_and_get_account_health()` computes health using the stale `liability_share_value`, finds `account_health > 0`, and reverts with `MarginfiError::HealthyAccount`, blocking the liquidation in that transaction despite the account actually being unhealthy once interest is applied. pub fn start_receivership<'info>(
    marginfi_account: &mut MarginfiAccount,
    liq_record: &mut LiquidationRecord,
    remaining_ais: &'info [AccountInfo<'info>],
    ignore_healthy: bool,
) -> MarginfiResult {
    // Note: the receiver can use the health cache state after this ix concludes to plan their
    // liquidation/deleverage strategy.
    let mut health_cache = HealthCache::zeroed();
    let mut liq_price_cache = LiquidationPriceCache::default();
    let (_pre_health, assets, liabs) = check_pre_liquidation_condition_and_get_account_health(
        marginfi_account,
        remaining_ais,
        None,
        &mut Some(&mut health_cache),
        HealthPriceMode::Live {
            liq_cache: Some(&mut liq_price_cache),
        },
        ignore_healthy,
    )?;
