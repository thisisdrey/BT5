### Title
Attachment content-hash is never verified against served bytes / peer inventory claims are trusted, allowing attachment/BNS-hash mismatch - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` selects which peer(s) to fetch an attachment from purely based on the unauthenticated inventory bit reported by that peer in a `GetAttachmentsInvResponse`, with no cross-check against actual content. `extend_with_attachments` then unconditionally inserts whatever bytes the chosen peer returns into `self.attachments` without recomputing/comparing the content hash of the received bytes against the `content_hash` that was requested. This lets a single colluding, unauthenticated peer both fabricate availability for an attachment and supply arbitrary bytes for it, with no verification anywhere in this path that peer-claimed-inventory equals actually-served-bytes-hash.

### Finding Description
In `get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs:404-478), for each `content_hash` the code iterates `peers_responses` and includes a peer as a `source` solely if `search_page.inventory.get(position_in_page)` reports `1` [1](#0-0) . This inventory data comes from `AttachmentsInventoryRequest`/`GetAttachmentsInvResponse` sent by peers in `self.peers`, which is populated from `network.get_outbound_sync_peers()` — an unauthenticated peer set. If `sources` ends up non-empty, an `AttachmentRequest{content_hash, sources, ...}` is queued and dispatched to those peer(s) [2](#0-1) . If a colluding peer is the only one claiming to have the content, the request goes to it exclusively.

When the response comes back, `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558) decodes the HTTP response via `decode_atlas_get_attachment()` and does:
```
self.attachments.insert(response.attachment);
``` [3](#0-2) 
There is no step here that recomputes the hash of `response.attachment`'s content and compares it to `request.content_hash` (the value the request was keyed on). The function only checks whether decoding succeeded/failed for reliability-report bookkeeping — it never rejects a syntactically valid but content-mismatched attachment at this stage.

Root cause: the entire selection-and-fetch pipeline treats "peer claims bit=1 in inventory" and "peer returned decodable bytes" as sufficient proof of correctness, but never actually binds the returned bytes' hash to the `content_hash` key that drove the request.

### Impact Explanation
A single unauthenticated peer can force a node to accept and route an `AttachmentRequest` for a given `content_hash` to itself by lying in its self-reported `GetAttachmentsInvResponse.pages[].inventory`, and then respond with arbitrary bytes that do not hash to `content_hash`. `extend_with_attachments` stores that mismatched `Attachment` into the batch state's `attachments` set without ever validating it against the requested hash. This is an attachment/BNS-mismatch class issue (serving/propagating attachment content that does not match the on-chain-committed `content_hash`), which is explicitly listed as a High-severity impact category. Repeatable per attachment/content_hash, and requires no privileged role — only running an ordinary outbound-reachable peer.

### Likelihood Explanation
Preconditions: the attacker must be selected as an (ideally sole) source for a given `content_hash`, achievable simply by being the only peer (or colluding to be the only responding peer) claiming inventory bit=1 for that position/page. This requires no secret, no StackerDB slot, no special role — just running a peer that the target node includes in `network.get_outbound_sync_peers()`. Cost is low and the attack is repeatable across content hashes/batches.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, recompute the hash of `response.attachment`'s content bytes and compare it to `request.content_hash` before inserting into `self.attachments`; reject (and penalize the peer's reliability report) on mismatch. Additionally, downstream consumers of `self.attachments` (e.g., the code building `resolved_attachments` for storage) should independently verify hash equality before writing to the Atlas attachments table.

### Proof of Concept
Rust test plan (stackslib/src/net/atlas/download.rs test module):
1. Construct an `AttachmentsBatchStateContext` with a single mocked peer URL in `self.peers` and reliability report.
2. Populate `self.attachments_batch.attachments_instances` with one `(contract_id, {attachment_index: content_hash})` entry for a known `content_hash` (e.g., hash of `b"real data"`).
3. Populate `self.inventories` with a `GetAttachmentsInvResponse` from that mocked peer whose `pages[].inventory[position_in_page] == 1`, even though the peer has no matching data.
4. Call `get_prioritized_attachments_requests()` and assert the returned queue contains an `AttachmentRequest{content_hash, sources: {peer_url}}` — proving the false inventory claim alone drove request issuance (asserting `sources.is_empty()` did not trigger the skip at line 461-464).
5. Simulate the peer's HTTP response containing an `Attachment` whose content is `b"garbage"` (hash != `content_hash`), wrapped in a `BatchedRequestsResult::succeeded` for that request.
6. Call `extend_with_attachments(&mut results)` and assert `self.attachments` now contains the garbage `Attachment`, and that `Hash160::from_data(&garbage_attachment.content) != content_hash` — demonstrating the mismatch survives unrejected through this stage of the pipeline.
