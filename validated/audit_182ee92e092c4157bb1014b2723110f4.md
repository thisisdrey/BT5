### Title
`FindRefsByOID`'s unbounded `ref_patterns` field allows unary-RPC resource-exhaustion DoS - (File: internal/gitaly/service/ref/find_refs_by_oid.go)

### Summary
`FindRefsByOID` is a unary (non-streaming) accessor RPC whose `FindRefsByOIDRequest.ref_patterns` field is a `repeated string` with no upper bound, analogous to the unbounded `Addresses` field in the `eth_getLogs` finding. Every pattern the client supplies is forwarded as a literal `git for-each-ref` argument and every matching result is accumulated into an in-memory slice before a single response is returned, so a large request directly inflates both git's argument-processing cost and Gitaly's memory/CPU usage on a single call.

### Finding Description
The handler takes `in.GetRefPatterns()` unmodified and passes it straight through as the `Args` of `git for-each-ref` via `gitpipe.ForEachRef`: [1](#0-0) 

`validateFindRefsReq` only checks that `Oid` is non-empty — it never checks the size or count of `ref_patterns`: [2](#0-1) 

`gitpipe.ForEachRef` places `patterns` directly into `gitcmd.Command{Name: "for-each-ref", ..., Args: patterns}`: [3](#0-2) 

Unlike `Topics` in the reported `eth_getLogs` bug (capped at `maxTopics = 4`), and unlike other RPCs in this repo that impose `limit`/`max_count` bounds on similarly unbounded lists (e.g. `GetTagSignatures`, `ListBlobs`, `ObjectsSize`, `ListCommits`), `FindRefsByOID` has no analogous cap on the number of `ref_patterns` a caller can supply. Because it is a **unary** RPC (not streamed), the entire result set is also buffered in memory (`var refs []string`) before the single response is sent back, compounding the cost of a large pattern list with a large unbounded result buffer.

### Impact Explanation
An unauthenticated (from Gitaly's perspective, any client with repo access) caller can send a single `FindRefsByOID` request with a very large `ref_patterns` array (bounded only by gRPC's default 4MB message-size limit, which can hold well over 50,000 short string patterns). This forces Gitaly to spawn `git for-each-ref` with an enormous argument list, consuming CPU while git parses/matches each pattern, and to buffer all resulting reference names in memory before responding. Because Gitaly's concurrency-limiting mechanism only limits the *number of in-flight requests* per RPC/repository — not the cost of an individual request — a small number of such requests can occupy worker resources for a long duration and degrade or halt the service for other repository accessors, mirroring the `eth_getLogs` DoS pattern (unbounded per-request cost, cheap for the attacker, expensive for the server).

### Likelihood Explanation
This is trivially reachable by any client authorized to call `FindRefsByOID` (a normal read-only RPC used e.g. by GitLab's `find_commits_by_oid`-like features) — no special privileges, malicious peer, or leaked token needed. The request only requires knowledge of the target repository and standard gRPC access, matching the "ordinary user issues a crafted RPC field" class called out in the validation rules.

### Recommendation
Enforce a maximum size on `ref_patterns` (and consider bounding the resulting `refs` slice / streaming the response), analogous to the `maxTopics` bound recommended for `Addresses` in the referenced report:
- Reject requests where `len(in.GetRefPatterns())` exceeds a small constant (e.g. tens, similar to how `GetTagSignatures`/`ListCommits` bound other repeated inputs) in `validateFindRefsReq`.
- Alternatively/additionally, convert `FindRefsByOID` to a streaming RPC so results are flushed incrementally rather than fully buffered, reducing worst-case memory pressure.

### Proof of Concept
1. Create/target any accessible repository via `FindRefsByOIDRequest{Repository: repo, Oid: "<any existing oid prefix>"}`.
2. Populate `RefPatterns` with tens of thousands of distinct pattern strings (e.g. `"refs/heads/pattern-0"`..`"refs/heads/pattern-N"`), staying under gRPC's default message size limit.
3. Issue the RPC and measure server-side latency/CPU consumption of the spawned `git for-each-ref` process as `N` grows — analogous to the `Test_GetLogs` PoC in the referenced report, request latency scales with the (unbounded) number of patterns supplied, with no server-side rejection at any size below the gRPC message-size ceiling.

```go
func (s *server) FindRefsByOID(ctx context.Context, in *gitalypb.FindRefsByOIDRequest) (*gitalypb.FindRefsByOIDResponse, error) {
	if err := validateFindRefsReq(ctx, s.locator, in); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(in.GetRepository())

	patterns := in.GetRefPatterns()
	if len(patterns) == 0 {
		patterns = []string{"refs/tags/", "refs/heads/"}
	}

	forEachRefIter := gitpipe.ForEachRef(
		ctx,
		repo,
		patterns,
		gitpipe.WithSortField(in.GetSortField()),
		gitpipe.WithPointsAt(in.GetOid()),
		gitpipe.WithCount(int(in.GetLimit())),
	)

	var refs []string
	for forEachRefIter.Next() {
		refs = append(refs, string(forEachRefIter.Result().ObjectName))
	}
```

```go
func validateFindRefsReq(ctx context.Context, locator storage.Locator, in *gitalypb.FindRefsByOIDRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}

	if in.GetOid() == "" {
		return errors.New("empty Oid")
	}

	return nil
}
```
