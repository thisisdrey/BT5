### Title
Ineffective `assert` allows division-by-zero (`ArithmeticException`) in `EnergyProcessor.calculateGlobalEnergyLimit` when `totalEnergyWeight` is non-positive - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
The reported Sherlock issue is that `_isQuoteAssetExcessOrAtTarget` fails to guard against a zero denominator before calling `approximatelyEquals`, causing an unconditional revert of core protocol functions. The closest analog in java-tron is `EnergyProcessor.calculateGlobalEnergyLimit`, which relies on a Java `assert` statement (a no-op in production JVMs, since assertions are disabled by default unless `-ea` is passed) as its only guard against `totalEnergyWeight` being non-positive before dividing by it.

### Finding Description
In `calculateGlobalEnergyLimit`: [1](#0-0) 

the code only short-circuits to `return 0` when `dynamicPropertiesStore.allowNewReward()` is `true` **and** `totalEnergyWeight <= 0`. If `allowNewReward()` is `false` (legacy resource-model chain state) while `totalEnergyWeight` is `0` or negative, execution falls through to:

```java
} else {
  assert totalEnergyWeight > 0;
}
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
```

The `assert` statement provides no runtime protection in a standard production deployment because Java assertions are disabled by default. When `hardenCalculation()` is enabled, `calculateGlobalLimitV1` (in `ResourceProcessor.java`) performs a `BigInteger` division by `totalWeight`: [2](#0-1) 

`BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException: BigInteger divide by zero`, exactly mirroring the reported bug class: a math helper is invoked without validating the denominator is non-zero, and the only defense is a check that does not actually execute at runtime (an `assert` here, versus a missing check entirely in the audited report).

This method is reachable from a single unprivileged, broadcastable `TriggerSmartContract` transaction through `useEnergy()`: [3](#0-2) 

and through `RepositoryImpl.getAccountLeftEnergyFromFreeze`, used during energy-limit computation in `VMActuator.getTotalEnergyLimitWithFloatRatio`: [4](#0-3) [5](#0-4) 

Note the code's own V2 (new resource model) counterpart, `calculateGlobalEnergyLimitV2`, correctly guards unconditionally with `if (totalEnergyWeight == 0) { return 0; }` regardless of `allowNewReward()`: [6](#0-5) 

confirming that the V1/legacy path's reliance on an `assert` (rather than an explicit `if`) is an inconsistency/oversight relative to the hardened V2 logic.

### Impact Explanation
If `totalEnergyWeight` reaches zero or a negative value while `allowNewReward()` is not active and `hardenCalculation()`/`allowHardenResourceCalculation()` is enabled, every subsequent call to `calculateGlobalEnergyLimit` for any account (triggered by ordinary smart-contract calls) throws an uncaught `ArithmeticException`. Because energy accounting is invoked for essentially all `TriggerSmartContract` transactions, this could disrupt transaction processing/energy metering broadly, which is an "API/critical path the node can no longer serve" class of impact analogous to the audited bug (reverting core protocol functions such as `bid`/`unlock`).

### Likelihood Explanation
This code path is gated behind two conditions that are not the default/expected production configuration: (1) `allowNewReward()` being disabled (a legacy proposal state) and (2) `totalEnergyWeight` becoming non-positive, which would require essentially all network energy-freeze weight to be withdrawn — an unlikely but not impossible condition on a low-activity/private/test network. On mainnet with `allowNewReward()` and `supportUnfreezeDelay()` already activated, the safer `calculateGlobalEnergyLimitV2` path is used instead, which is not vulnerable. This significantly limits real-world exploitability but the underlying code defect (relying on `assert` instead of an explicit runtime check) remains present and is a valid low-likelihood/high-impact latent bug on any chain configuration where these legacy flags are not yet activated.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` statement with an explicit runtime check (e.g., `if (totalEnergyWeight <= 0) { return 0; }`) unconditional on `allowNewReward()`, matching the pattern already used correctly in `calculateGlobalEnergyLimitV2`, so that a zero/negative `totalEnergyWeight` cannot reach the `BigInteger` division in `calculateGlobalLimitV1`.

### Proof of Concept
Not independently reproducible from static analysis alone — reaching the vulnerable branch requires a chain state where `allowNewReward()` is disabled, `allowHardenResourceCalculation()` (`hardenCalculation()`) is enabled, and `totalEnergyWeight` is driven to `<= 0`, which could not be confirmed as achievable on current mainnet parameters from the code alone. This is noted as an area of uncertainty; a Devin session with access to the full chain configuration/test harness would be needed to confirm whether these preconditions are jointly reachable in practice.

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }
