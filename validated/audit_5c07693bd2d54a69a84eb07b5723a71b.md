### Title
Non-constant-time authorization comparison enables timing side-channel attack on `/v3/contracts/fast-call-read` - (File: stackslib/src/net/api/fastcallreadonly.rs)

### Summary
`RPCFastCallReadOnlyRequestHandler::try_parse_request` compares the client-supplied `authorization` header directly against the configured secret using Rust's standard `!=` operator on `String`/`&str`, which performs a byte-wise comparison that returns as soon as a mismatch is found. A remote attacker without the secret can measure response timing across repeated requests to incrementally recover the correct prefix of `password` byte by byte.

### Finding Description
In `try_parse_request`, after confirming `self.auth` is configured, the code does: [1](#0-0) 
`auth_header != password` invokes the derived `PartialEq` for `String`, which internally compares underlying byte slices. Rust/LLVM slice equality is not specified to run in constant time and in practice a mismatched byte terminates the comparison early (a length check followed by a linear byte scan that stops at the first differing byte). This means a header value that shares a longer correct prefix with the real secret takes measurably longer to reject than one that diverges at the first byte. An attacker who can send arbitrary bytes to the node's RPC port (this endpoint requires no other privilege, since the whole point of `self.auth` is to gate exactly this) can iterate byte-by-byte: try all 256 values for the next header byte, keep the one that yields a distinguishable timing delay, and repeat until the full secret is reconstructed — a classic timing side-channel that breaks the intended equality "authenticated secret == secret only the operator knows."

The same insecure pattern (`header != password`/similar) is reused verbatim across other admin-gated endpoints in this codebase, e.g. `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, confirming this is a systemic, non-constant-time secret comparison rather than an isolated typo. ### Impact Explanation
If exploitable, this would allow an unauthenticated remote attacker to eventually recover the `fast-call-read` bearer secret and gain unauthorized access to the gated Clarity read-only execution endpoint, matching the "auth bypass on a gated endpoint" Critical category described in the prompt. The endpoint itself only exposes read-only contract-call execution (no state mutation), so the direct additional impact beyond recovering the secret is bounded to unauthorized read access to this specific RPC surface.

### Likelihood Explanation
Exploiting a network-level timing side-channel against a single-byte comparison loop over a real TCP/HTTP round trip is extremely difficult in practice: network jitter, OS scheduling noise, and TLS/HTTP framing overhead dominate the sub-microsecond timing differences created by an early-exit byte comparison, especially since the comparison itself is a tiny fraction of total request-handling latency (JSON parsing, regex matching, Clarity environment setup all happen after or around it). No proof-of-concept in this codebase or associated tests demonstrates a statistically reliable extraction over a real network path, and the prompt's own proof idea only asks for an in-process timing measurement, not a demonstrated remote extraction. This is a real code-quality/hardening gap (the fix — constant-time comparison — is cheap and standard), but remotely exploiting it to fully recover a secret over the network is not demonstrated to be practical here.

### Recommendation
Replace the direct `!=` comparison with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` (`auth_header.as_bytes().ct_eq(password.as_bytes())`) or a manual XOR-accumulate comparison over fixed-length byte slices, applied consistently across all endpoints in `stackslib/src/net/api/` that gate on a shared secret (`fastcallreadonly.rs`, `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`).

### Proof of Concept
A Rust unit test in `stackslib/src/net/api/fastcallreadonly.rs` tests module could construct a `HttpRequestPreamble` with an `authorization` header value sharing an increasing correct-prefix length against a fixed configured `auth` secret, call `try_parse_request` in a loop while measuring `std::time::Instant` elapsed nanoseconds for each candidate, and assert whether mean timing for longer-correct-prefix candidates is statistically distinguishable from shorter ones. However, this only demonstrates a theoretical in-process signal (consistent with the question's own proof idea) and does not by itself establish that the side channel is exploitable over the actual remote RPC network path given realistic noise.
