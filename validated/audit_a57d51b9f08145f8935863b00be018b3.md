### Title
`try_lock_transaction_batch` fails to detect intra-batch write-write account conflicts, allowing two conflicting transactions to both receive `Ok(())` locks - ([File: accounts-db/src/account_locks.rs])

### Finding Description
`AccountLocks::try_lock_transaction_batch` splits validation and locking into two separate full passes over the batch instead of interleaving check-then-lock per transaction: [1](#0-0) 

The first pass (`validated_batch_keys.iter_mut().for_each`) calls `can_lock_accounts` (a `&self`, non-mutating read) for every entry in the batch, comparing each transaction's account keys only against the locks that existed *before* the batch call started [2](#0-1) . Because this pass never mutates `self.write_locks`/`self.readonly_locks`, two (or more) transactions within the same batch that write-lock the same account both observe `can_write_lock(key) == true` and are both marked `Ok`.

The second pass then unconditionally calls `self.lock_accounts(keys)` for every entry that remained `Ok`, incrementing the write-lock counter for each one without re-checking for conflicts against locks acquired earlier in the same pass [3](#0-2)  and [4](#0-3) . As a result, both conflicting transactions end up in `write_locks[A] == 2` and both are reported as `Ok(())` to the caller, i.e. both are considered successfully locked and eligible for concurrent execution — violating the core invariant that conflicting transactions never execute concurrently.

This is a functional regression relative to the correct approach of validating and locking each transaction sequentially (check-then-commit per transaction), which would make later transactions in the batch see earlier transactions' just-acquired locks.

### Impact Explanation
Two transactions writing to the same account within a single locked batch can both be granted write locks simultaneously. If the caller (bank/transaction execution) trusts `try_lock_transaction_batch`'s result to guarantee mutual exclusion for concurrent execution, this allows concurrent mutation of the same account state by two transactions — an invalid recorded block / state-correctness bug, matching Agave's "invalid recorded block" / consensus-safety bounty category rather than a mere availability issue.

### Likelihood Explanation
No special ordering trick, `TooManyAccountLocks` failure, or privileged access is required — simply constructing a batch containing two transactions that write to the same account is sufficient to trigger the flaw at the `AccountLocks` level, since the check pass never accounts for other entries in the same call. Whether this is reachable end-to-end from an unprivileged remote client depends on whether the higher-level batch-construction code (banking stage / scheduler) already filters out same-account write conflicts before calling `lock_accounts`/`try_lock_transaction_batch`; I was unable to confirm this within the available tool calls (the caller in `accounts-db/src/accounts.rs` was not fully inspected due to iteration limits). Based purely on the `AccountLocks` unit itself, the vulnerability is real and deterministically reproducible.

### Recommendation
Restore per-transaction interleaved check-and-lock semantics: for each transaction in the batch, in order, call `can_lock_accounts` against the *current* (already-mutated-by-earlier-entries-in-this-batch) state and, if `Ok`, immediately call `lock_accounts` before moving to the next transaction, rather than doing one full validation pass followed by one full locking pass.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test module)
#[test]
fn test_try_lock_transaction_batch_detects_intra_batch_write_conflict() {
    let mut locks = AccountLocks::default();
    let account_a = Pubkey::new_unique();

    // Two transactions in the SAME batch call, both writing account_a.
    let tx1_keys: Vec<(&Pubkey, bool)> = vec![(&account_a, true)];
    let tx2_keys: Vec<(&Pubkey, bool)> = vec![(&account_a, true)];

    let batch = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // Invariant: two write-conflicting transactions must not both succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both conflicting write-lock transactions were granted Ok(()) simultaneously: {:?}",
        results
    );
}
```
Running this against the current implementation fails: both entries return `Ok(())`, and `write_locks[account_a]` ends at `2`, demonstrating that the function grants concurrent write access to the same account within one batch.

```rust
    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }
```
