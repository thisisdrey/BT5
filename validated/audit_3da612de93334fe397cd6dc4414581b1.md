### Title
`init_global_fee_state` allows front-running: unprivileged attacker can permissionlessly seize the global fee admin role - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The `init_global_fee_state` instruction initializes the program-wide `FeeState` singleton PDA. The PDA address is fully deterministic (derived only from the fixed `FEE_STATE_SEED`, with no per-caller entropy), and the instruction's `Accounts` struct places no constraint on who may call it — any signer with enough SOL to pay rent can invoke it and pass themselves in as `admin_key`/`fee_wallet`. This is the classic "initializer can be front-run" bug class: whoever's transaction lands first (whether the legitimate deployer or an attacker racing them) permanently becomes the `global_fee_admin`.

### Finding Description
The instruction handler simply trusts its caller-supplied `admin_key` argument and writes it into the newly created account with no authorization check: [1](#0-0) 

The corresponding `Accounts` validation struct only requires `payer` to be *a* signer — there is no `address = ...` constraint pinning `payer` (or any other account) to a known/expected deployer key, and the PDA seeds contain no per-deployer or per-transaction component that would make the address unpredictable or claimable only by the intended party: [2](#0-1) 

Because Anchor's `init` constraint on a PDA simply fails if the account already exists, the *first* transaction to land wins. Since the PDA address `[FEE_STATE_SEED]` is publicly derivable and the instruction is dispatched permissionlessly from `lib.rs`: [3](#0-2) 

an attacker who observes the pending deployment (or simply calls it first, since nothing gates it) can submit their own `init_global_fee_state` call with themselves as `admin_key` and their own `fee_wallet`, permanently taking over the `global_fee_admin` role for the entire protocol, before the legitimate admin's call executes.

The newly-added `init_global_fee_state_v2` instruction has the identical pattern — a PDA derived only from a fixed seed, initialized by an unconstrained `payer` signer: [4](#0-3) 

### Impact Explanation
`global_fee_admin` is the highest-privilege role in the fee subsystem: it is authorized (via `edit_global_fee_state`) to change `admin`, `fee_wallet`, program fee rates/fixed fees, liquidation/order fee maximums, and the `pause_delegate_admin`. An attacker who wins this race can redirect all future protocol-fee flows to their own wallet, set fees to extract maximum value from every bank in every group (since `FeeState` values are cached into every `MarginfiGroup` on `marginfi_group_initialize` per `fee_state_cache`), and grant themselves pause-delegate control. Because the account is a `FEE_STATE_SEED`-only PDA, the protocol cannot simply "retry" at a new address — recovery would require a program upgrade to point at a new seed/PDA, i.e., in the report's own words, "in the best case force a re-deployment."

### Likelihood Explanation
This requires the instruction to be called exactly once, on program deployment/upgrade, before any legitimate `init_global_fee_state` transaction has landed. On Solana, unconfirmed transactions are visible in the mempool/gossip before confirmation, and the required accounts (a fixed PDA plus a signer) are fully known in advance. Any actor monitoring for this deployment can race it with a higher-priority-fee transaction. This is a one-time deployment-window risk rather than a continuously exploitable path, but the impact if it succeeds is severe and irreversible without a redeploy.

### Recommendation
Add an explicit authorization check to `InitFeeState` (and `InitFeeStateV2`) restricting `payer`/`admin` to a hardcoded, trusted deployer/upgrade-authority key (e.g., via an `address = ...` constraint or a `require_keys_eq!` against a known constant, or by checking against the program's upgrade authority account). Alternatively, perform the fee-state initialization atomically within the same deployment transaction/script as the program deploy so no window exists for a competing transaction to land first.

### Proof of Concept
1. Program is deployed; `FEE_STATE_SEED` PDA does not yet exist.
2. Attacker derives the same PDA address (`Pubkey::find_program_address(&[FEE_STATE_SEED.as_bytes()], &marginfi::ID)`), which is public and deterministic.
3. Attacker submits `init_global_fee_state(admin: attacker_key, fee_wallet: attacker_wallet, ...)` with a higher priority fee than the legitimate deployment transaction, as shown constructible in the test helper: [5](#0-4) 
4. If the attacker's transaction confirms first, `fee_state.global_fee_admin = attacker_key` is set permanently; the legitimate `init_global_fee_state` call from the real admin now fails (`init` on an already-initialized PDA), and every subsequently created `MarginfiGroup` inherits fee parameters controlled by the attacker via `edit_global_fee_state`.
