### Title
Permanent freeze of eth-implicit wallet via un-resettable `has_in_flight_tx` reentrancy lock - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `WalletContract` (eth-implicit wallet, NEP-title "Wallet Contract") implements a reentrancy-style lock, `has_in_flight_tx`, to serialize execution of a single Ethereum-emulated transaction across a chain of async NEAR promises/callbacks. This is the intentional analog of a `nonReentrant` guard. Unlike `RaffleMintV1.withdrawNonRaffleProceeds()`, which failed to update state *before* an external call, this contract does clear its guard at the *start* of every callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) before making any further external call — the "set-before-call" pattern that the original report recommends. However, because NEAR rolls back **all** state changes of a receipt on failure/panic (including the initial `self.has_in_flight_tx = false;`), any panic or gas-exhaustion inside one of these `#[private]` callback functions leaves the guard permanently `true`. Since `rlp_execute` unconditionally rejects any further calls while `has_in_flight_tx == true` (`lib.rs:97-105`), and there is no non-`#[private]` (externally-callable) function that can reset the flag, the wallet becomes permanently unusable — a lock analogous to the reentrancy guard "stuck open" failure mode.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) checks and only proceeds if `!self.has_in_flight_tx`, then sets `self.has_in_flight_tx = true` before returning a `Promise` to the caller [1](#0-0) . The flag is only ever reset back to `false` inside `#[private]` callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), each of which sets it to `false` as their very first statement [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) .

These callback functions then perform potentially gas-intensive, attacker-influenceable work after clearing the flag — e.g. `serde_json::from_slice(&value)` on a cross-contract response body in `nep_141_storage_balance_callback` (`lib.rs:203-221`) and `address_check_callback` (`lib.rs:141-159`), and further promise construction (`action_to_promise(...).then(...)`) that depends on the statically-sized gas budgets `RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (`lib.rs:34-41`). In the NEAR runtime, a failed/panicking receipt execution has all of its state changes rolled back via `state_update.rollback()` (per `runtime/runtime/src/lib.rs` receipt-processing flow, documented at `runtime/runtime/AGENTS.md:64` — "When a receipt fails, its state changes are rolled back using `TrieUpdate`"). This means that if any of these callback functions panics or exhausts its allotted gas *after* the initial `has_in_flight_tx = false` line but before the receipt completes successfully, the flag reset is discarded along with everything else, and the contract's persisted state still shows `has_in_flight_tx == true`.

Because `rlp_execute` is the only public entry point that can drive a new transaction, and it unconditionally refuses to proceed while the flag is `true`, and no public (non-`#[private]`) recovery function exists to clear it, the wallet becomes permanently unable to process any further Ethereum-emulated transactions.

### Impact Explanation
This is a permanent freezing of the wallet contract's transaction capability. The account's NEAR balance is not directly drained, but the eth-implicit account (and all funds/authorizations routed exclusively through it) can never execute another Near action again once the lock is stuck — a permanent denial of service analogous to funds/authorization "freezing." Given `near-wallet-contract` is explicitly called out as one of the few in-scope unprivileged-signer analog surfaces, and the impact is a hard, irrecoverable freeze rather than a soft failure, this is a meaningful integrity issue for any account relying on this mechanism.

### Likelihood Explanation
Triggering it requires driving one of the `#[private]` callbacks into a panic or out-of-gas condition after the guard has already been cleared in-memory but before the receipt finishes successfully. The most plausible vector is `nep_141_storage_balance_callback`/`address_check_callback` processing a large or malformed response from an external contract (attacker- or third-party-controlled token/registrar contract) via `serde_json::from_slice`, or the fixed downstream `.then()` gas budgets (`RLP_EXECUTE_CALLBACK_GAS` = 5 Tgas, etc.) being insufficient for the subsequent action, causing an out-of-gas panic mid-callback. Exploitability depends on whether an adversary (e.g., a malicious ERC-20 "target" token contract or a malicious/compromised relayer supplying such a target) can reliably force this condition, which I could not fully confirm from static review alone — dynamic/gas-profiling verification would be needed to establish a guaranteed trigger versus edge-case fragility. This uncertainty should be noted; the failure mode exists structurally in the code, but the practical exploitability threshold (exact gas margins, and whether `target`/`token_id` in the ERC-20 path can be attacker-chosen outside of the true key holder's control) was not conclusively established from the available context.

### Recommendation
Do not rely on state mutations inside a callback that can itself fail/panic to release the reentrancy-style lock. Instead:
- Reset `has_in_flight_tx` in a way that is guaranteed to commit even if the "main" logic of the callback fails, e.g., by structuring the callback so the guard-reset is the only unconditional state write, with all fallible/gas-sensitive logic occurring only after it is confirmed to have committed (this is inherently hard in a single receipt because NEAR rolls back atomically on panic).
- Alternatively, add a public recovery path (e.g., a timeout-based "unstick" method) that permits the account owner to reset `has_in_flight_tx` if no callback resolves within a bounded time/block height, mirroring the yield/resume timeout pattern already used elsewhere in the runtime (`docs/RuntimeSpec/...` / promise-yield timeouts).
- Ensure callback gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) are sized with sufficient margin above worst-case deserialization/processing costs of externally supplied response payloads, or bound the size of data processed from cross-contract responses before use.

### Proof of Concept
Not independently executed; based on static code review:
1. Owner submits an RLP-encoded ERC-20 transfer transaction via `rlp_execute`, causing `nep_141_storage_balance_callback` to be scheduled as a `.then()` callback with a statically fixed gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) [6](#0-5) .
2. `has_in_flight_tx` is set to `true` before the promise is returned [7](#0-6) .
3. The target token contract's `storage_balance_of` response is sized/crafted (or conditions occur) such that `nep_141_storage_balance_callback`'s deserialization or subsequent promise construction exceeds its allotted gas, causing the callback receipt to panic after having already executed `self.has_in_flight_tx = false;` in-memory [8](#0-7) .
4. Because the receipt fails, all its state changes (including the flag reset) are rolled back, leaving `has_in_flight_tx == true` permanently in persisted state.
5. Any subsequent call to `rlp_execute` is rejected with `"transaction already in progress"` forever [9](#0-8) , and no public function exists to clear the flag.

Note: I was not able to conclusively confirm within the available context whether the exact gas margins in production make this trigger reliably or only under contrived conditions; this would require dynamic gas-profiling of the callback paths against worst-case attacker-supplied cross-contract response sizes to fully validate exploitability.
