### Title
StackerDB chunk signatures lack domain separation across StackerDB contract instances, enabling cross-contract chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The `SlotMetadata`/`StackerDBChunkData` signature scheme in `libstackerdb` binds only `(slot_id, slot_version, data_hash)` into the signed digest, but never binds the identity of the StackerDB smart contract (or the network's chain view) the chunk is destined for. Any node that accepts and stores a chunk verifies the recovered signer only against the *locally configured* slot owner for the target contract — it never checks that the signature was produced *for that specific StackerDB instance*. This is the same class of bug as the reported `uniTransferFrom` issue: the code assumes a parameter (which "database"/"domain" the signed authorization applies to) is implicitly fixed, but it is actually attacker-controlled, and the equality "signed-for X" vs. "stored-into Y" is never enforced.

### Finding Description
`SlotMetadata::auth_digest` computes the digest that gets signed and later verified: [1](#0-0) 

```
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```

Note that the smart contract identifier (`QualifiedContractIdentifier`) of the StackerDB the chunk belongs to is **not** part of the digest. `SlotMetadata::verify` only recovers the public key from this digest and checks it against a `principal: &StacksAddress` that is passed in by the caller: [2](#0-1) 

That caller-supplied `principal` comes from `get_slot_signer`/`get_slot_validation`, which is scoped to whichever `smart_contract` the caller happens to be checking against, e.g. in `StackerDBTx::try_replace_chunk`: [3](#0-2) 

and in `PeerNetwork::validate_received_chunk`: [4](#0-3) 

Both the HTTP write path (`RPCPostStackerDBChunkRequestHandler::try_handle_request`, which calls `tx.try_replace_chunk`) and the gossip/push path (`PeerNetwork::handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk`) perform this "look up the owner *for this contract*, then verify signature" check — but since the signed bytes never include the contract identifier, a signature that is valid for slot `N` in StackerDB contract `A` is byte-for-byte equally valid for slot `N` in StackerDB contract `B`, provided the same signer address happens to own slot `N` in both. The `StackerDBPushChunkData` envelope even carries a `contract_id` and `rc_consensus_hash` alongside the chunk, but neither of those fields is covered by `chunk_data.sig`: [5](#0-4) 

This is structurally identical to the reported bug: the function trusts an implicit binding between the authenticated data and the context it's applied in ("chunk signed for slot N" is trusted to mean "chunk signed for slot N in *this* database"), but that binding is never actually checked.

### Impact Explanation
A holder of a valid signer key for slot `N` in one StackerDB contract (e.g., an old `.signers-<cycle>-<idx>` reward-cycle contract, or a `.miners`/other lower-privilege replicated DB) can take a previously and validly signed `StackerDBChunkData` and resubmit it — via the unauthenticated `POST /v2/stackerdb/{principal}/{contract}/chunks` RPC endpoint or via unsolicited `StackerDBPushChunk` gossip — against a *different* StackerDB contract where that same address is assigned to the same slot index. Because `try_replace_chunk`/`validate_received_chunk` only check the signature against the locally resolved slot owner for the target contract (not against the contract the signature was actually produced for), the replayed chunk is accepted as authentic, stored, and then rebroadcast network-wide via `broadcast_message` in `Relayer::process_stacker_db_chunks`. This is an unauthorized write into a StackerDB replica coupled with network-wide propagation of data that was never actually authorized for that database/round — matching the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact categories.

### Likelihood Explanation
Exploitation requires only: (1) possession of a legitimately-signed chunk for some slot the attacker (or anyone) controls in any StackerDB contract, and (2) that address also owning the same slot index in a second StackerDB contract that the target node also replicates. Signer sets in the Stacks signer protocol are frequently persistent or overlapping across successive reward-cycle StackerDB contracts, so this precondition is realistically satisfiable without any privileged access, the node's secret key, or another party's private key — the attacker only reuses their own, already-valid signature bytes in a new context. No brute force or heavy traffic volume is needed; a single crafted POST or push message suffices.

### Recommendation
Bind the target StackerDB's identity (and ideally a chain-view/round-specific value such as `rc_consensus_hash`) into the signed digest in `SlotMetadata::auth_digest`, e.g. by hashing in the `QualifiedContractIdentifier` bytes before `slot_id`/`slot_version`/`data_hash`. This requires a coordinated protocol version bump since it changes the wire-signed payload, but it closes the domain-separation gap and makes a chunk's signature verifiable as authentic for one specific StackerDB instance only.

### Proof of Concept
1. Configure/observe two StackerDB contracts, `A` and `B`, on a target node such that signer address `S` (controlled by the attacker) owns slot `3` in both `A` and `B` (a realistic condition, since Stacks signer StackerDB contracts across reward cycles often reuse the same signer set/slot assignment).
2. As `S`, sign a `StackerDBChunkData` for slot `3`, version `10`, with arbitrary `data` intended only for contract `A` (using `StackerDBChunkData::sign`, per [6](#0-5) ).
3. Submit this exact `StackerDBChunkData` (unmodified `slot_id`, `slot_version`, `sig`, `data`) to the target node via `POST /v2/stackerdb/{B's-principal}/{B's-contract}/chunks`, per the request handler at [7](#0-6) , or embed it in a `StackerDBPushChunk` message with `contract_id = B`.
4. The node resolves the slot-3 owner for contract `B` (which is `S`), calls `SlotMetadata::verify(&S)` — which succeeds because the digest never referenced contract `A` or `B` — and accepts/stores the chunk into `B`'s replica, then rebroadcasts it via `Relayer::process_stacker_db_chunks` ( [8](#0-7) ), even though this data was never signed for `B`.

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

                slot_validation.signer,
