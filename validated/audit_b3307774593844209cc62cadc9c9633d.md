## Title
Replay Window TOCTOU Race Permits Duplicate Acceptance of Replayed Traffic — ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` checks the replay window (`window.Check`), decrypts the AEAD payload, and only *afterwards* marks the counter as consumed (`window.Update`) — as two separate, independently-locked critical sections rather than one atomic operation. When Nebula is configured with more than one reader routine (`tun.routines`/`listen.batch` > 1, `SO_REUSEPORT`), multiple goroutines can process inbound UDP datagrams for the same tunnel concurrently. Exactly like the EigenPod report — where a state-consuming operation (`_processWithdrawalBeforeRestaking`) and the boundary check that guards future re-processing (`proofIsForValidTimestamp`) were not applied atomically to the same event, letting one instance of state "slip between" the two steps — here the "consume" step (`Update`) is decoupled from the "check" step (`Check`), letting a captured/duplicated packet slip through the gap and be accepted twice.

### Finding Description
`Decrypt` in `connection_state.go` does:
1. `cs.decryptLock.Lock(); result := cs.window.Check(l, messageCounter); cs.decryptLock.Unlock()`
2. `cs.dKey.DecryptDanger(...)` (no lock held)
3. `cs.decryptLock.Lock(); result = cs.window.Update(l, messageCounter); cs.decryptLock.Unlock()` [1](#0-0) 

`Check` only tests whether the counter has already been marked; it does not mark it. Marking only happens in `Update`, which is a distinct, separately-acquired critical section: [2](#0-1) [3](#0-2) 

Because step 1 and step 3 are not part of one atomic transaction, two goroutines that receive the exact same ciphertext packet (e.g., because an attacker retransmits it while it is still in flight, or a NIC/queue duplicates a datagram) can both execute `Check` and both see "not yet seen," both successfully `DecryptDanger`, and both then call `Update` — the second `Update` call will report `false`/duplicate only after the payload has *already* been decrypted and handed back to the caller once already (and, in a race, possibly delivered to the tun device twice, or duplicate-processed by relay logic). Nebula supports exactly this concurrent-reader configuration: [4](#0-3) [5](#0-4) 

This is the same bug class as the EigenPod report: a two-phase "consume-then-gate" pattern where the gate (boundary check) and the consuming action are not executed as a single atomic step, so a legitimate/adversarial event that lands exactly in that gap escapes the intended one-time-only guarantee — in EigenPod's case causing state loss, here causing state re-acceptance (replay).

### Impact Explanation
An attacker who can observe/capture even a single legitimate ciphertext packet on the wire (no valid certificate or key material required — Nebula's threat model already assumes on-path attackers can see UDP datagrams) can attempt to have that packet processed twice by racing it against itself across reader routines. Successful exploitation defeats the AEAD replay window's core security guarantee (each counter processed exactly once) and could result in duplicate delivery of decrypted traffic to the tun device or duplicate relay forwarding, i.e., a replay-protection bypass on the data plane.

### Likelihood Explanation
This requires the affected node to run with multiple reader routines (`tun.routines > 1`, multi-reader UDP sockets), which is an explicitly supported, documented configuration for higher throughput, and requires the attacker to win a narrow race window between the `Check` and `Update` lock sections on two concurrently-processed instances of the same packet. This makes it a real but timing-sensitive vulnerability rather than a trivially reliable one.

### Recommendation
Make the check-decrypt-mark sequence atomic with respect to a given `messageCounter`: hold `decryptLock` (or an equivalent per-counter guard) across the entire `Check` → `Decrypt` → `Update` sequence, or perform an atomic "check-and-reserve" of the counter before decrypting and only finalize/rollback the reservation after decryption succeeds or fails, so no two concurrent goroutines can ever observe the same counter as "unclaimed" simultaneously.

### Proof of Concept
1. Configure Nebula with `listen.batch` > 1 and `tun.routines` > 1 so `f.readOutsidePackets` runs concurrently across queues (`interface.go` `run()`/`listenOut`).
2. Capture one legitimate Message packet with counter `N` destined for an established tunnel.
3. Inject two (or more) copies of that exact packet onto the wire simultaneously so they are picked up by different reader goroutines at nearly the same time.
4. Both goroutines call `cs.window.Check(l, N)` before either calls `cs.window.Update(l, N)`; both succeed and proceed to `DecryptDanger`, resulting in the same counter being decrypted/accepted more than once, in violation of the replay window's single-acceptance guarantee. [1](#0-0) [2](#0-1)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
