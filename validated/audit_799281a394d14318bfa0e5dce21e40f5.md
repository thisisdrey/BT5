### Title
Check-then-Decrypt-then-Update race in the anti-replay window allows a single wire-observed ciphertext to be decrypted multiple times, bypassing intended one-shot replay semantics - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt()` (and the analogous `VerifyRelay()`) makes its replay decision the same way OracleMaker priced trades: it evaluates the anti-replay window state *before* the current operation completes, releases the lock, performs the expensive AEAD operation unlocked, and only afterward commits the state update under a fresh lock acquisition. Because the "is this counter allowed" check and the "commit this counter as seen" update are two separate, unlocked-in-between critical sections, an attacker who can duplicate a single observed on-wire UDP packet (no certificate needed — this is pure packet replay on the wire) can race two (or more) copies of it through `Check()` before either has reached `Update()`, exactly as Alice could race two opposite orders through the OracleMaker before either updated the Maker's tracked position.

### Finding Description
`Decrypt()` in `connection_state.go`:
```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)   // 1. read current window state
	cs.decryptLock.Unlock()
	...
	out, err = cs.dKey.DecryptDanger(...)          // 2. expensive AEAD op, NOT holding the lock
	...
	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)   // 3. commit new window state
	cs.decryptLock.Unlock()
	...
}
``` [1](#0-0) 

This mirrors the OracleMaker root cause precisely: the gating decision (`Check`) is made against the state that exists *right now*, without accounting for the in-flight effect of the operation currently being processed (the pending `Decrypt`/`Update` of a same-counter packet already admitted by `Check`). Just as OracleMaker let a trader split one trade into two smaller ones to reset the Maker's tracked position between price evaluations, an attacker can send the same on-wire ciphertext twice in quick succession (a trivial UDP replay, requiring no valid certificate or session key — the attacker never needs to decrypt anything, only duplicate bytes already observed passing over the network) so that both copies pass `window.Check()` while the window still shows the counter as unseen, because neither goroutine has reached `window.Update()` yet.

`Bits.Check()` and `Bits.Update()` themselves implement the correct sliding-window replay semantics in isolation [2](#0-1) [3](#0-2) , but `Decrypt()`'s two-phase locking pattern (check under lock A, unlock, do work, lock B, update) reintroduces a TOCTOU window between phase 1 and phase 3 that the `Bits` data structure was never designed to tolerate concurrently for the *same* counter.

### Impact Explanation
The forged/duplicated packet's second instance will still ultimately fail at `Update()` (since the first successful `Update()` marks the bit, and the second call to `Update()` on the same counter returns `false`, yielding `ErrAlreadySeen`), so the plaintext from the raced duplicate is discarded by the caller in `outside.go` [4](#0-3) . This means the direct data-plane impact is bounded: it does not currently look like it lets a stale packet's plaintext be delivered to the TUN device twice. However, it does mean:
- The AEAD `Open()` operation on the shared `cs.dKey` cipher object is invoked concurrently, unsynchronized, for the *same* nonce/counter from two goroutines — `CipherStateAESGCM.DecryptDanger` performs no locking of its own and mutates the shared `nb` nonce-scratch buffer and calls into the underlying `cipher.AEAD.Open` concurrently [5](#0-4) . Nebula only serializes writes via `writeLock`/`EncryptLockNeeded`, but read-side `dKey` is never protected by a data-race-safe lock across the full decrypt call; only the window bookkeeping is locked in short critical sections, leaving the actual `Open()` call unsynchronized between racing goroutines that both passed `Check()`.
- More broadly, this pattern degrades the intended guarantee that "a given message counter is admitted and processed at most once" into "may be decrypted more than once, but only committed once" — a wasted-CPU amplification vector (an attacker can force redundant expensive AEAD decrypt work per duplicated UDP datagram) and a concurrency-safety concern for the underlying cipher object, both stemming from the same root cause identified in the OracleMaker report: gating a stateful decision on a snapshot of state that does not yet reflect concurrently in-flight state-changing operations for the same input.

### Likelihood Explanation
Likelihood is moderate-to-high for the racing pattern (any attacker that can capture/observe a valid ciphertext packet on the wire can immediately re-send a duplicate copy with negligible timing skew — no cryptographic material or CA-signed certificate is required, exactly like the OracleMaker exploit required no special protocol access, only quick order submission). The receiving Nebula instance's UDP reader loop(s) run concurrently across multiple queues/goroutines, making it plausible that duplicate packets for the same counter land on different reader goroutines and interleave through `Decrypt()` before the first `Update()` commits.

### Recommendation
Collapse the check-decrypt-update sequence into a single atomic critical section held under `decryptLock` (or use a compare-and-commit primitive) so that no second caller can observe the "not yet seen" state for the same counter while a first caller's decrypt/update is still in flight — i.e., reserve the counter slot (tentatively mark it) at `Check()` time under the same lock that is only released once `Update()` (or a rollback on decrypt failure) has completed, closing the analogous "gap between decision and settlement" that made OracleMaker's spread bypassable.

### Proof of Concept
Conceptual sequence (not executed, since only static analysis was available):
1. Attacker observes one valid data-plane UDP packet `P` (header + ciphertext) sent to a Nebula node for message counter `N`, e.g. by passive network observation — no certificate or key material required.
2. Attacker immediately sends two copies of `P` to the target's UDP listener queues (or forces the OS to deliver duplicates), timed so both are read by separate goroutines before either completes `ConnectionState.Decrypt`.
3. Goroutine A calls `window.Check(N)` → true, releases `decryptLock`.
4. Before goroutine A calls `window.Update(N)`, goroutine B also calls `window.Check(N)` → still true (bit unset), releases `decryptLock`.
5. Both A and B now call `cs.dKey.DecryptDanger(..., N, ...)` concurrently on the shared `dKey` object with the same nonce/counter — a decrypt operation is executed twice for one otherwise-single-use counter, and the two calls are unsynchronized with respect to each other. Only whichever of A/B reaches `window.Update(N)` first will have its result accepted; the other gets `ErrAlreadySeen`, but the duplicate `Open()` call has already executed against the shared cipher state. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (s *CipherStateAESGCM) DecryptDanger(out, ad, ciphertext []byte, n uint64, nb []byte) ([]byte, error) {
	if s == nil {
		return []byte{}, nil
	}
	nb[0] = 0
	nb[1] = 0
	nb[2] = 0
	nb[3] = 0
	binary.BigEndian.PutUint64(nb[4:], n)
	return s.c.Open(out, nb, ciphertext, ad)
