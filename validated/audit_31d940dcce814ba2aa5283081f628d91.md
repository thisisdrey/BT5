### Title
Non-Constant-Time Authorization Token Comparison Enables Timing Side-Channel Auth-Token Recovery - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
Multiple privileged RPC endpoints in `stackslib/src/net/api/` compare the client-supplied `authorization` header against the node's configured secret token using the standard `!=` operator on `String`/`&str`, instead of a constant-time comparison. This is the same bug class as the FileBrowser report: a secret-bearing comparison whose execution time leaks information that lets a remote, unauthenticated attacker recover the secret byte-by-byte.

### Finding Description
Each of the following handlers gates a sensitive endpoint with the identical pattern:

```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

This exact code appears in:
- `postblock_proposal.rs` (`/v3/block_proposal`) [1](#0-0) 
- `postblock_v3.rs` (`/v3/blocks?broadcast=1`) [2](#0-1) 
- `blockreplay.rs` (`/v3/blocks/replay/:id`) [3](#0-2) 
- `blocksimulate.rs` (`/v3/blocks/simulate/:id`) [4](#0-3) 
- `fastcallreadonly.rs` (`/v3/contracts/fast-call-read/...`) [5](#0-4) 
- `txsimulate.rs` (`/v3/transactions/simulate`) [6](#0-5) 

The equality check is `auth_header != password`, where both sides are `String`/`&String`. Rust's `PartialEq` for `str`/`String` compares length first, then delegates to a byte-slice comparison (`memcmp`-style) that in the general case terminates at the first mismatched byte rather than running in constant time. The `auth_token`/`password` value is a single secret configured via `connection_options.auth_token` [7](#0-6)  and is threaded into each handler's `self.auth: Option<String>` field, which is compared identically against attacker-controlled input on every request with no rate limiting or delay.

This exactly matches the reported bug class: a request comparing an attacker-supplied credential (`authenticated` value) against a `stored` secret without constant-time semantics, where the comparison's timing leaks how many leading bytes matched — breaking the "authenticated vs. stored" equality invariant that the token comparison is supposed to enforce opaquely.

### Impact Explanation
An unauthenticated, remote attacker can mount a byte-at-a-time timing attack against `auth_header != password` to incrementally recover the full `auth_token` value, without needing the node operator's or signer's private key. Once recovered, the attacker gains the privileges these endpoints authenticate:
- Submit block proposals via `/v3/block_proposal`, impersonating the signer's coordination channel with the miner.
- Broadcast arbitrary Stacks blocks via `/v3/blocks?broadcast=1`, since successful authentication sets `broadcast = true` in `postblock_v3.rs`.
- Access debug endpoints (`/v3/blocks/replay`, `/v3/blocks/simulate`, `/v3/transactions/simulate`, `/v3/contracts/fast-call-read`) that are otherwise gated behind this same secret.

This is an authentication-bypass primitive that grants unauthorized write access to node/network-facing state (block broadcast, block-proposal submission), matching the "Critical: unauthenticated/unauthorized write to state... auth bypass" impact bucket.

### Likelihood Explanation
Exploitability depends on how measurable the byte-comparison timing signal is over the network versus local noise, similar to the referenced report where a ~40–50 ms bcrypt delay was measured against a ~1–4 ms baseline. Here the signal-to-noise ratio is much smaller (a `memcmp`-scale operation vs. bcrypt), so many more samples/statistical averaging would likely be required to distinguish a matching-prefix length increment from network jitter, especially over a real network path rather than localhost. It is a real weakness (CWE-208) but practically harder to exploit remotely than the bcrypt-based original; likelihood is Medium given the small timing delta and requirement for extensive statistical sampling to overcome network noise.

### Recommendation
Replace the plain `!=` comparisons with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or hashing both sides with a keyed MAC and comparing the MACs) in all six locations: `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, and `txsimulate.rs`. Centralize the check into a single shared helper (e.g., in `httpcore.rs`, which already stores `auth_token` [8](#0-7) ) so future endpoints inherit constant-time behavior by default.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. For a target endpoint (e.g., `/v3/block_proposal`), send repeated POST requests with an `authorization` header guessing one additional correct leading byte at a time (e.g., `"a"`, `"aa"`, `"aab"`, ...), each followed by many random trailing bytes.
3. Measure response latency for each guess over many trials (as in the report's PoC script) and compare against a baseline built from fully incorrect tokens.
4. A guess whose measured latency statistically exceeds the baseline (indicating the byte-compare loop advanced further before mismatching) is treated as the correct next byte; repeat until the full `auth_token` is reconstructed, then use it to authenticate to `/v3/block_proposal` or `/v3/blocks?broadcast=1`.
