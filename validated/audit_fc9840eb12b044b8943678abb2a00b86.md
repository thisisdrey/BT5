### Title
Non-hardened `ExchangeProcessor` truncates trade output with plain `(long)` casts, letting repeated small `ExchangeTransactionContract` trades drain a Bancor-style TRC10 exchange pool - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeProcessor.exchangeToSupply()`/`exchangeFromSupply()` compute Bancor-formula swap amounts in `double` and truncate the result to `long` with a bare `(long)` cast (equivalent to floor/truncation toward zero), exactly the same rounding-truncation defect described in the Mento `TradingLimits::update()` report, where only the "exactly 0" edge case is special-cased and any other rounding loss is silently accepted [1](#0-0) . This code path is reached directly from `ExchangeCapsule.transaction()` when `hardenedCalc` is false (the default, non-hardened path), which is invoked by any unprivileged user via `ExchangeTransactionActuator.execute()` processing a broadcast `ExchangeTransactionContract` [2](#0-1) [3](#0-2) .

### Finding Description
The exchange amount is derived from a floating-point Bancor "relay supply" model:
```
double issuedSupply = -supply * (1.0 - pow(1.0 + quant/newBalance, 0.0005));
long out = (long) issuedSupply;   // truncation, not rounding, no floor-safety check
...
double exchangeBalance = balance * (pow(1.0 + supplyQuant/supply, 2000.0) - 1.0);
return (long) exchangeBalance;    // truncation again
``` [1](#0-0) 

Unlike `TradingLimits::update()`, which at least rounds up when the result becomes exactly `0`, this code has **no rounding-up safeguard whatsoever** — every trade truncates twice (once converting sell token → "virtual supply", once converting supply → buy token), and both truncations are always in the same direction (toward the caller's benefit relative to the true irrational Bancor curve value), because `(long)` cast on a positive double always rounds toward zero. Both `exchangeToSupply` and `exchangeFromSupply` mutate `this.supply` as a side effect, so per-transaction truncation error accumulates into the exchange's internal invariant state, not just the output amount. The direct AMM balance-mutation code in `ExchangeCapsule.transaction()` then applies the truncated `buyTokenQuant` to update `firstTokenBalance`/`secondTokenBalance` without any invariant check when `hardenedCalc` is false [4](#0-3) .

A hardened alternative, `SafeExchangeProcessor`, does exist and uses `BigDecimal` with 18-digit precision and `RoundingMode.HALF_UP`/`DOWN` [5](#0-4) , but it is only used when `hardenedCalc` (gated by the `allowHarden()` proposal flag) is enabled [6](#0-5) . On any deployment where this proposal has not been activated by the SR committee, the vulnerable double-precision, unguarded-truncation `ExchangeProcessor` remains the live code path for every `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` execution.

### Impact Explanation
An unprivileged transaction broadcaster can call `ExchangeTransactionContract` (`ExchangeTransactionActuator`) repeatedly with small `quant` values chosen to maximize the fraction of true curve output lost to truncation on each hop, or conversely to systematically extract slightly more `buyTokenQuant` than the true Bancor value implies, because the truncation direction is deterministic and the accumulated `supply` state compounds the drift over many trades. This is directly analogous to the "swap 2-by-2" attack path in the report, where repeated small operations exploit deterministic rounding to bypass an invariant — here, the invariant being violated is the TRC10 AMM's token-conservation guarantee (`firstTokenBalance * secondTokenBalance` constant-ish curve), leading to gradual, then material, drain of the pool's reserves (an unbacked-balance condition for the exchange pool, at the expense of other liquidity participants).

### Likelihood Explanation
Any account can create/fund an old-style TRC10 `Exchange` and issue arbitrarily many `ExchangeTransactionContract` transactions against it at low fee cost (`calcFee()` is a fixed system fee, not proportional to exploit gain) [7](#0-6) . The exploit requires no special privileges, only the `hardenedCalc` proposal being inactive, which is the default/legacy behavior preserved for backward compatibility.

### Recommendation
Make the hardened, BigDecimal-based `SafeExchangeProcessor` path (or an equivalent fixed-point implementation with explicit round-up/round-down policy consistent with pool solvency) the unconditional default for `ExchangeCapsule.transaction()`, removing dependence on the `allowHarden()` proposal switch, and add an explicit invariant check (e.g., verifying the post-trade product of balances does not decrease beyond the rounding tolerance) before committing state in `ExchangeCapsule.transaction()`.

### Proof of Concept
1. Create an `Exchange` with `firstTokenBalance` and `secondTokenBalance` values chosen so that the Bancor exponentiation in `exchangeToSupply`/`exchangeFromSupply` produces fractional results close to an integer boundary.
2. Repeatedly submit `ExchangeTransactionContract` transactions with small `quant` amounts via `ExchangeTransactionActuator`, which calls `exchangeCapsule.transaction(...)` → `ExchangeProcessor.exchange(...)` on the non-hardened path [3](#0-2) .
3. Because both `exchangeToSupply` and `exchangeFromSupply` truncate via `(long)` cast without a compensating round-up (unlike even the flawed `deltaFlowUnits == 0` special case in the reference report), each trade's truncation error accumulates in the mutated `supply` field and pool balances, letting the attacker extract more total value across many trades than a single equivalent large trade would yield, gradually depleting the counter-party token reserve.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

      newSecondTokenBalance = hardenedCalc

          : secondTokenBalance - buyTokenQuant;

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
