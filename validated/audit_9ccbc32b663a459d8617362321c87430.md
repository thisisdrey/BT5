## Analog Found: `pallet-psm` (Peg Stability Module) — redemption insolvency for rebasing external assets

### Title
PSM redeem/mint accounting assumes a static, non-rebasing external asset balance, allowing rebase-driven reserve shortfall to permanently lock later redeemers — (`File: substrate/frame/psm/src/lib.rs`)

### Summary
The Cork Protocol report's core broken invariant is: the protocol tracks `Ra`/`Pa` balances in internal state variables assuming a fixed 1:1 relationship with the actual token balance held by the contract, but rebasing tokens change balance independently of transfers, desynchronizing tracked accounting from real holdings. `pallet-psm` in this repository has the exact same structural assumption: `PsmDebt` is a state-tracked value meant to represent the amount of external asset owed 1:1 (via decimal conversion) against whatever the reserve account (`psm_account`) actually holds, but the reserve amount itself is read live from `T::Fungibles::balance` rather than being reconciled against any exchange-rate or rebase mechanism.

### Finding Description
`PsmDebt<T>` records, per `(internal_asset, external_asset)`, the internal-asset-denominated amount that must remain redeemable 1:1 (adjusted only for decimals) against the external asset held in the reserve account: [1](#0-0) 

`mint` increases `PsmDebt` by the internal-equivalent of the external deposit and transfers the external asset into the reserve: [2](#0-1) 

`redeem` computes `external_out` purely from the decimal conversion of `internal_net` (`internal_to_external`), checks that `PsmDebt >= effective_internal_net`, and only then reads the *live* reserve balance via `get_reserve` to confirm liquidity: [3](#0-2) 

The pallet only guards against **internal**-asset decimal/metadata drift (`DecimalsMismatch`), verified by `ensure_decimals_match`, and has an explicit test proving this protection exists solely for the internal side: [4](#0-3) 

There is no analogous protection, exchange-rate mechanism, or balance-sync step for the **external** asset. If a PSM admin approves an external asset whose balance in `psm_account` can change independently of `T::Fungibles::transfer` calls (a rebasing token, e.g. a `stETH`-style asset that auto-accrues or auto-slashes balance in the holder's account), the reserve balance and `PsmDebt` diverge exactly as in the Cork report:
- Positive rebase → reserve balance silently grows beyond tracked debt (matches "stuck yield accrual" in the original report); the pallet's own `do_try_state` invariant tolerates this by design (`reserve >= debt_as_external` only, not equality), and there is no way to withdraw or credit the surplus, so it is trapped in the pallet account permanently.
- Negative rebase (balance shrinks, e.g. yield-bearing token unwinding or a slashing-style rebase) → reserve balance falls below `PsmDebt`'s decimal-converted requirement. The invariant check in `do_try_state` would then fail: [5](#0-4) 
and in live operation the `redeem` extrinsic's defensive check trips for the users who redeem after the shortfall materializes: [6](#0-5) 
This means the first redeemers to act after a negative rebase succeed (because `PsmDebt` decreases faster than the real backing, effectively front-running the shortfall against later users), while remaining internal-asset holders end up permanently unable to redeem their 1:1-pegged claim — a permanent user-fund lock triggered without any admin, governance, or privileged action; the PSM admin only needs to have approved the (rebasing) external asset once via `add_external_asset`, an ordinary, in-scope configuration action, not the root cause exploit itself.

### Impact Explanation
This breaks the core invariant that PSM debt and reserve conservation must settle exactly once per unit of internal asset, matching the "Balances, assets ... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot. It produces either a permanent value lock (negative rebase case, unrecoverable stuck funds for a subset of internal-asset holders) or permanently stranded assets (positive rebase case, matching the seed report's "stuck yield accrual" impact) — both squarely inside the accepted impact classes for asset accounting.

### Likelihood Explanation
The only precondition is that a PSM instance has an approved external asset whose live balance in the reserve account is not solely a function of pallet-initiated transfers (i.e., a rebasing or auto-compounding asset). Approving an external asset is a normal, documented, non-privileged-abuse workflow (`add_external_asset`) exercised as part of the pallet's intended configuration surface, not a governance/admin compromise; the vulnerability is in the pallet's silent lack of any rebase/exchange-rate handling, which the code and tests confirm is absent for the external side, mirroring exactly what the seed report flags as "won't fix" in Cork but which here manifests as a fund-lock condition rather than a merely cosmetic one, because `PsmDebt`-vs-`reserve` ordering directly gates the `redeem` extrinsic.

### Recommendation
- Document and enforce (at `add_external_asset` time or via a runtime-level `Config` constraint) that external assets must be non-rebasing / balance must equal cumulative net transfers.
- Alternatively, replace the fixed decimal-only `internal_to_external`/`external_to_internal` conversion with a live exchange-rate query so `PsmDebt` and `get_reserve` stay reconciled, and add a runtime check that reverts `add_external_asset` for asset kinds flagged as rebasing.
- Add a periodic or pre-redeem reconciliation that fails closed (halts the specific external's circuit breaker) rather than only defensively erroring per-transaction, once `reserve < debt_as_external` is detected, so that stuck users are not selected by transaction ordering.

### Proof of Concept
1. Admin registers a PSM instance for `internal_asset` and calls `add_external_asset(internal_asset, rebasing_asset)`, where `rebasing_asset`'s `T::Fungibles::balance` for a given account can increase/decrease without any `transfer`/`mint_into`/`burn_from` call against it (simulating a rebasing token via a custom `Fungibles` impl or a wrapped asset whose issuance floats).
2. Multiple users call `Psm::mint` depositing `rebasing_asset`, populating `PsmDebt::<T>::get(internal_asset, rebasing_asset)` and the reserve in `psm_account`.
3. Simulate a negative rebase event that reduces the live balance of `psm_account` for `rebasing_asset` (external to any pallet call), e.g. as would occur naturally with a rebasing token's negative-yield epoch.
4. Have one user call `Psm::redeem`: `PsmDebt >= effective_internal_net` still holds (unaffected by the rebase), but `get_reserve` now returns less than before; if the shortfall hasn't yet caused `reserve < external_out` for this particular redemption size, it succeeds, further depleting the now-insufficient reserve.
5. Have a subsequent user attempt `Psm::redeem` for their full internal-asset holding: `get_reserve` returns a balance now less than `external_out`, triggering `defensive!("PSM reserve is less than expected output amount")` and `Error::<T>::Unexpected`, permanently blocking that user's redemption while their internal-asset balance and non-zero `PsmDebt` claim remain unbacked, reproducible via `Psm::do_try_state()` failing the `"PSM reserve is less than tracked debt for an asset"` assertion at [7](#0-6) .
