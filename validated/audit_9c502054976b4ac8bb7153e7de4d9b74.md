Based on my investigation of `substrate/frame/psm/src/lib.rs`, I found a concrete local analog to the reported bug class — a scaling/decimals value that one code path validates against live state, while a sibling path trusts a stale snapshot without re-validation, exactly the "the code comments/setters imply one thing, but the consumer assumes different scaling" pattern from the Opyn report.

### Title
PSM `redeem` skips the live-decimals revalidation that `mint` performs, allowing stale decimals snapshots to corrupt internal/external conversion math - (File: substrate/frame/psm/src/lib.rs)

### Summary
`pallet-psm` normalizes swaps between an `internal` stablecoin and externally supplied assets using a decimals-scaling factor `10^diff` computed from a `decimals` value snapshotted at `add_external_asset` time [1](#0-0) . The `mint` extrinsic explicitly re-validates that live metadata decimals still match the registration snapshot before doing any conversion, via `Self::ensure_decimals_match(...)` [2](#0-1) . The `redeem` extrinsic, however, reads the snapshotted `external.decimals` and `info.internal_decimals` directly and performs the same scaling conversions without calling `ensure_decimals_match` or any equivalent live-metadata check [3](#0-2) .

### Finding Description
The PR history shows this pallet was specifically designed around the invariant that "the internal asset's live decimals must still match the snapshot in `PsmInfo`" and that a "Runtime drift guard: `mint`/`redeem` return `DecimalsMismatch` if live metadata diverges from the registration snapshot" [4](#0-3) . This documents the intended invariant that **both** `mint` and `redeem` must check live decimals before scaling.

In the actual `mint` implementation, this guard is enforced: [5](#0-4) 

In `redeem`, the analogous guard call is absent — the function pulls `ext_decimals`/`internal_decimals` straight from the stored `PsmInfo`/`ExternalAssets` snapshot and immediately proceeds to `internal_to_external` / `external_to_internal` conversions and fund transfers: [6](#0-5) 

Since external assets are ordinary `Fungibles` assets (e.g. `pallet-assets`), decimals are exposed as mutable metadata that the asset's own owner can typically update independently of PSM's `full_admin`/`emergency_admin` roles (PSM only snapshots the value at `add_external_asset` time) [7](#0-6) . If live decimals for a registered external asset drift from the snapshot used in `PsmInfo`/`ExternalAssets` — through any metadata update outside PSM's own governance actions — `mint` will correctly reject the operation with `DecimalsMismatch`, but `redeem` will silently continue to scale by the stale factor `10^diff`, computed in `external_to_internal`/`internal_to_external` [8](#0-7) .

### Impact Explanation
Because `redeem` burns the caller's internal asset and pays out external asset from the PSM reserve account using the (now-incorrect) scaling factor, an attacker who can cause the effective decimals mismatch (or who registers/administers an external asset whose decimals metadata is independently mutable) can force `redeem` to compute a wildly wrong `external_out` relative to `internal_net` burned. Depending on the direction of the drift this either drains the PSM reserve disproportionately to the internal amount burned (fund loss analogous to seizing the `MarginPool`'s funds in the source report) or corrupts `PsmDebt` accounting relative to the real reserve, breaking the "value conserved and settled exactly once" invariant required for asset accounting pallets.

### Likelihood Explanation
This does not require a malicious PSM admin, governance actor, validator, or relayer — the only actor needed is whoever controls metadata of the already-approved external asset, or any mechanism causing decimals of that asset to diverge post-registration, which `mint`'s own defensive check confirms is an anticipated real-world condition (hence `DecimalsMismatch` exists at all). The asymmetry between `mint` and `redeem` means the mitigation intended by the pallet author (per the prdoc) is only half-implemented, so likelihood of exploitation is high whenever such drift occurs, since normal usage of `redeem` provides no independent decimals check to fall back on.

### Recommendation
Call the same `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?` guard (or equivalent live-metadata comparison) at the start of `redeem`, exactly as is done in `mint`, before computing `internal_to_external`/`external_to_internal`. This restores the documented invariant that both mint and redeem halt on decimals drift rather than only one of the two paths.

### Proof of Concept
1. Admin registers external asset `X` with `add_external_asset`, snapshotting `decimals = 18` in `ExternalAssets` and `PsmInfo::internal_decimals = 6`.
2. The asset `X`'s owner (an ordinary account, not the PSM admin) later updates `X`'s live metadata decimals to `0` via the underlying `Fungibles`/`pallet-assets` `set_metadata` (or any process that changes reported decimals independent of PSM).
3. Calling `Psm::mint` now correctly fails with `Error::DecimalsMismatch` (validated at line 717).
4. Calling `Psm::redeem(internal_asset, X, internal_amount, max_fee)` proceeds without any decimals check, using the stale `ext_decimals = 18` to compute `external_out = internal_to_external(internal_net, 18, 6)`, scaling up by `10^12` instead of the correct (now `10^0`) factor — paying out an amount of `X` from the reserve many orders of magnitude larger than intended for the internal amount burned, up to the limit of `PsmDebt`/reserve balance checks, which do not detect the metadata drift.

Note: I was not able to fully trace `ensure_decimals_match`'s exact implementation body or confirm whether some out-of-band mechanism additionally restricts who can alter a registered external asset's live decimals (e.g., whether PSM requires the external asset's owner account to equal the PSM admin at registration time). This should be verified directly in `substrate/frame/psm/src/lib.rs` (search for `fn ensure_decimals_match`) before treating this as a confirmed exploit path, as the index truncated some regex/search attempts.

		/// Convert an amount denominated in external-asset units into internal units.
		///
		/// Scales by `10^(ext_decimals - internal_decimals)` — multiplies up when internal has more
		/// decimals, floor-divides when it has fewer. Returns [`Error::ConversionOverflow`] if
		/// the scaling factor or the product does not fit in the balance type.
		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}

		/// Convert an amount denominated in internal units into external-asset units.
		///
		/// Inverse of [`Self::external_to_internal`]. Floor-divides when internal has more
		/// decimals, multiplies up when it has fewer.
		pub(crate) fn internal_to_external(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {

- audience: Runtime Dev
  description: |-
    Previously pallet-psm rejected any external stablecoin whose decimals did
    not match pUSD. This change normalizes to pUSD units internally so the PSM
    can approve assets with arbitrary decimal precision within a safe range.

    Core changes:
    - New storage: per-asset `AssetDecimals` snapshot and pallet-wide
      `StableDecimals` snapshot. Storage version bumped to 2.
    - Conversion helpers `external_to_pusd` / `pusd_to_external` with checked

    - `mint` and `redeem` use round-trip rounding. Truncation dust stays in the
      caller's wallet on both paths (symmetric behavior), no value is trapped
      in the reserve and no hidden dust is routed to the fee destination.
    - `PsmDebt` now denominates in pUSD units so aggregate ceilings and issuance
      checks are meaningful across mixed-decimal assets.
    - Runtime drift guard: `mint`/`redeem` return `DecimalsMismatch` if live
      metadata diverges from the registration snapshot; that asset halts until
      governance intervenes.

### Asset Onboarding Requirements

Before calling `add_external_asset(internal_asset, asset_id)`:

- A PSM must already be registered for `internal_asset`
- The external `asset_id` must already exist in the `Fungibles` implementation
- The internal asset's live decimals must still match the snapshot in `PsmInfo`
- `|external_decimals − internal_decimals|` must be within `MAX_DECIMALS_DIFF`
- The PSM must still be below `MaxExternals`

After `add_external_asset`, the external starts with an `AssetCeilingWeight` of `0%`, so its
per-external ceiling is zero and **minting is disabled**. Before the first mint, call
`set_asset_ceiling_weight(internal_asset, asset_id, weight)` with a non-zero weight (and
optionally `set_minting_fee` / `set_redemption_fee`, which otherwise default to 0.5%).
Skipping this step makes the first mint fail with `ExceedsMaxPsmDebt`.
