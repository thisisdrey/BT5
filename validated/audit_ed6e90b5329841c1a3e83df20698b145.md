### Title
Unauthenticated `RelayFromAddr` spoofing in `handleCreateRelayRequest` allows relay-state poisoning for arbitrary vpnAddrs - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` accepts a `RelayFromAddr` field taken directly from the `CreateRelayRequest` control message body and uses it as the identity for which relay state is created, without verifying that this claimed address actually belongs to the authenticated sender `h`. This mirrors the C4 finding's root cause: a component (`Pool.mintSynth`) trusted a caller-supplied reference (`synthOut`) without checking it actually corresponds to the caller's own context (its underlying token), enabling cross-context abuse.

### Finding Description
In `relay_manager.go`, `handleCreateRelayRequest` is invoked from `HandleControlMsg`, which is called after the peer `h` has already completed a valid Noise handshake — so `h`'s own certificate/identity is authenticated [1](#0-0) . However, the function then derives `from` purely from the attacker-controlled message body:

```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(from) {
    logMsg.Error("Discarding relay request from myself", "myIP", from)
    return
}
``` [2](#0-1) 

There is no check anywhere in this path that `from == h.vpnAddrs[0]` (i.e., that the claimed relay-from address actually matches the identity of the peer `h` that sent the authenticated control message). The only validation performed elsewhere is a nil-check on the `RelayFromAddr`/`RelayToAddr` fields in `HandleControlMsg`, not an identity/ownership check [3](#0-2) .

Because `from` is trusted, the code proceeds to record/complete relay state (`AddRelay`, `h.relayState.QueryRelayForByIp(from)`, `CompleteRelayByIP`) and eventually replies with a `CreateRelayResponse` addressed using this attacker-chosen `from` value [4](#0-3) . This is structurally the same bug class as the Synth report: the vulnerable function accepts an object/identity reference (`synthOut` / `RelayFromAddr`) from the caller and performs privileged bookkeeping (mint/burn / relay-state establishment) keyed on that reference without validating that it corresponds to the calling entity's own verified context (underlying token / authenticated vpnAddr).

### Impact Explanation
An authenticated-but-malicious peer can send `CreateRelayRequest` messages claiming an arbitrary `RelayFromAddr` that is not its own vpnAddr. Since the relay target host processes this as if the claimed address were the true relay-from identity, this can poison relay state (`h.relayState`) for a vpnAddr the attacker does not own, potentially causing:
- Relay-state confusion/corruption for a legitimate third host (the one whose address was spoofed), since a `Requested`/`Established` relay entry keyed on that address gets created on the responder without that host's knowledge or participation.
- The responder issuing `CreateRelayResponse` messages that reference the spoofed address, which downstream relay-migration and completion logic (`EstablishRelay`, `migrateRelayUsed`) uses to route/forward traffic, potentially enabling traffic redirection or established-relay hijack for the spoofed identity.

This is comparable in class (though narrower in blast radius, since attacker must be an authenticated tunnel peer, not a fully open network attacker) to the original report's arbitrage/confused-deputy pattern: trusting a caller-provided reference without validating it matches the caller's own authenticated context.

### Likelihood Explanation
Requires the attacker to already be an authenticated Nebula peer capable of establishing a tunnel and sending Control-type messages to a relay-capable host (`am_relay` node), which is a normal capability for any peer holding a valid certificate signed by an in-scope CA — no additional privilege escalation needed beyond being a legitimate but malicious member of the mesh. This keeps it reachable under the "no CA-signed certificate attacker" framing is *not* strictly satisfied by a fully unauthenticated attacker, but is reachable by anyone who is a normal certificate holder in the mesh, which is the closest reachable analog to the multi-actor arbitrage scenario in the original report (which also required a certificate-holding participant in the protocol, just abusing legitimate access across trust boundaries).

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`/`EstablishRelay`), validate that the claimed `RelayFromAddr` actually corresponds to the authenticated sender `h`'s own vpnAddrs (i.e., `slices.Contains(h.vpnAddrs, from)`) before creating or completing any relay state, analogous to the recommended fix of checking `iSYNTH(synthOut).LayerONE() == TOKEN` in the original report — i.e., verify the referenced identity matches the caller's own verified identity before performing any state-changing operation keyed on it.

### Proof of Concept
Conceptual (Go, based on `relay_manager.go` control-message handling):
```go
// Attacker "h" has a valid cert for vpnAddr A, but crafts:
msg := NebulaControl{
    Type:                NebulaControl_CreateRelayRequest,
    InitiatorRelayIndex: idx,
    RelayFromAddr:       netAddrToProtoAddr(victimVpnAddr), // NOT attacker's own address
    RelayToAddr:         netAddrToProtoAddr(targetVpnAddr),
}
// Send via authenticated tunnel to a relay-capable peer.
// handleCreateRelayRequest only checks:
//   f.myVpnAddrsTable.Contains(from)  -> false, passes
// and never checks from == h.vpnAddrs[0], so relay state for `victimVpnAddr`
// is created/keyed based entirely on attacker-controlled data.
```
I was unable to fully trace `AddRelay`/`hostmap.go`'s internal relay-state structures (`RelayState`, `QueryRelayForByIp`, `CompleteRelayByIP`) within the available search budget, so the exact downstream data-corruption/traffic-hijack mechanics could not be fully confirmed against the source; this should be verified directly in `hostmap.go` before treating the impact as fully proven.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}
