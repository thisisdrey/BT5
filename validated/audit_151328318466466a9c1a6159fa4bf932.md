### Title
Gossip vote sigverify bypass: `run_gossip_task` forwards `transaction` unconditionally after `ed25519_verify_serial` - ([File: core/src/sigverify.rs])

### Summary
`SigVerifyWorkerPool::run_gossip_task` calls `sigverify::ed25519_verify_serial(&mut work.batch, true, false)` to authenticate a gossip vote's packet, but it never inspects the resulting discard/verify flags on `work.batch` before sending `GossipVerifiedVoteBatch { transaction: work.transaction, packet_batch: work.batch }` downstream. The return value of `send` is only used for error logging, and the function always returns `true` regardless of verification outcome.

### Finding Description
In `core/src/sigverify.rs`, `run_gossip_task` is: [1](#0-0) 

The verification call `sigverify::ed25519_verify_serial(&mut work.batch, true, false)` marks packets in `work.batch` as discarded when the signature check fails (this is the same primitive used in `run_transaction_task`, which does check `num_valid_packets == 0` before proceeding, at lines 332-344 of the same file). However, `run_gossip_task` has no equivalent check: it does not call `sigverify::count_valid_packets` on `work.batch`, nor does it inspect `packet.meta().discard()` before constructing and sending `GossipVerifiedVoteBatch`. The `transaction` field is the original, independently-deserialized `Transaction` struct provided by the caller (`GossipSigVerifier::send_votes_to_worker_pool`, lines 96-127), not something derived from the verified packet bytes. Because `transaction` and `batch` are separate values joined only by the `GossipVerifyTask`/`GossipVerifiedVoteBatch` structs, there is no code-level tie between the discard state set on the packet in `work.batch` and whether `work.transaction` is forwarded — the send happens unconditionally.

An attacker who can push/pull a gossip vote message reaching `GossipSigVerifier::send_votes_to_worker_pool` (lines 96-127) can craft a `Transaction` whose outer structure parses but whose signature is invalid; `ed25519_verify_serial` will mark the packet in `batch` as discarded, but the raw `transaction` value is still forwarded to `gossip_verified_vote_sender`.

### Impact Explanation
This matches Agave's "signature verification bypass" bounty category: an unauthenticated vote transaction can reach `ClusterInfoVoteListener` (the consumer of `GossipVerifiedVoteBatch`) unless that consumer independently re-checks the `packet_batch` discard state before trusting `transaction`. I was unable to fully confirm from available context whether `ClusterInfoVoteListener` performs this discard check before consuming `transaction` — the file `core/src/cluster_info_vote_listener.rs` does reference `GossipVerifiedVoteBatch` and packet/discard-related terms, but I could not verify the exact ordering/guard logic within the iteration budget available.

### Likelihood Explanation
Preconditions are met by an unstaked/unprivileged remote peer able to submit gossip push/pull vote messages that reach `send_votes_to_worker_pool`. The code path from `GossipSigVerifier::send_votes_to_worker_pool` through `run_gossip_task` to the `gossip_verified_vote_sender` channel is unconditional and does not require staked status, and is reproducible deterministically with a crafted invalid-signature vote packet.

### Recommendation
In `run_gossip_task`, after calling `ed25519_verify_serial`, check `sigverify::count_valid_packets(std::iter::once(&work.batch)) == 0` (mirroring `run_transaction_task`) and drop/skip sending `GossipVerifiedVoteBatch` when the packet was discarded, or verify `work.batch` packet's `meta().discard()` state directly before forwarding `work.transaction`.
