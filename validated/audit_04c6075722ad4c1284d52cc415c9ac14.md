### Title
Remote Code Execution via unsanitized `remote` URL in Bzlmod registry `git_repository` sources - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
A `source.json` file served by any configured Bazel module registry can declare `"type": "git_repository"` and directly forward a `remote` field into Bazel's `git_repository` repo rule [1](#0-0) . That `remote` value is passed, unsanitized, as a `git remote add origin <remote>` argument and subsequently used in `git fetch origin`, with no protocol allowlisting configured. Because Git supports the `ext::` remote-helper transport, which executes an arbitrary shell command supplied in the URL, a malicious or compromised registry can achieve remote code execution on any machine that resolves this module.

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` drives the clone/update flow used by both `git_repository` and (per the registry doc) the Bzlmod `git_repository`-typed `source.json` entries. It calls `add_origin(ctx, git_repo, ctx.attr.remote)`, which invokes: [2](#0-1) 

`_git()` and the low-level `_execute()` build the actual argv and pass it straight to `ctx.execute`, without any escaping, protocol restriction, or allowlist of git transports: [3](#0-2) 

`fetch()` then runs `git fetch origin ...` against the configured `origin` remote: [4](#0-3) 

Nowhere in `_execute`, `_git`, or `_git_maybe_shallow` is `protocol.allow`/`GIT_ALLOW_PROTOCOL` set to restrict git to safe transports (`http`, `https`, `ssh`, `git`); only unrelated `GIT_*` environment variables are cleared for hygiene/isolation reasons [5](#0-4) . Modern Git ships an `ext::` transport helper that runs an arbitrary command supplied inline in the URL (e.g. `ext::sh -c "..."`). Because the `remote` value here is fed straight into `git remote add`/`git fetch` without validating the URL scheme, any caller-supplied `remote` that resolves to `ext::<command>` results in that command being executed by the `git` subprocess spawned by Bazel.

The registry documentation confirms that for `source.json` files of `"type": "git_repository"`, the `remote`, `commit`, `tag`, `branch`, etc. fields are "directly forwarded to the underlying `git_repository` repo rule" [1](#0-0) . Unlike the default `archive` type, which is bound by a mandatory `integrity` (sha256) checksum of the downloaded artifact [6](#0-5) , the `git_repository` type has no equivalent verification of the `remote` field itself — only the resulting `commit` acts as a content pin, and it does nothing to constrain what transport/URL scheme is used to reach that commit.

This satisfies the "hostile registry" exception in scope: any of the `--registry` entries Bazel is configured to consult (including third-party/internal registries or a compromised mirror of the Bazel Central Registry) is fully trusted to supply this `remote` value with no sha256/integrity check standing in the way, unlike the archive path.

Note: I could not locate the Java-side code that parses `source.json` and converts a `git_repository`-typed entry into the actual `git_repository()` repository-rule invocation (likely excluded by index size limits), so I can't 100% rule out an additional validation layer there. However, the Starlark implementation that actually executes the git command (`git_worker.bzl`) is the code path of record for this rule regardless of how the attributes are populated, and it performs no such validation.

### Impact Explanation
A single malicious/compromised registry entry (reachable via any of the module registries configured with `--registry`, including a compromised mirror or MITM'd non-TLS registry) causes arbitrary command execution on the machine performing the Bazel build/fetch, with the privileges of the Bazel user. This is a full remote code execution primitive from a build-time dependency source that is not gated by any checksum, matching CVE-2025-47286's bug class (an insufficiently escaped/validated externally-controlled value flowing into a command that a privileged/build process executes).

### Likelihood Explanation
Exploitation requires only that Bazel resolve a module whose `source.json` declares `"type": "git_repository"` with a `remote` set to an `ext::` URL, from any of the registries configured for the build (default BCR, or any additional/internal `--registry` the project uses). No user interaction beyond running `bazel build`/`bazel fetch` is required, and no credentials or prior access are needed by the attacker — they only need to control (or intercept) content served by one of the consulted registries.

### Recommendation
- Enforce an allowlist of safe git transports (e.g., set `protocol.allow=never` globally with explicit `protocol.<scheme>.allow=always` only for `http`, `https`, `git`, `ssh`, `file` as appropriate) before invoking any `git` subprocess in `git_worker.bzl`'s `_execute`.
- Reject `remote` (and any other user/registry-controlled string forwarded into `git` argv) that begins with `-` or matches the `ext::`/`fd::` helper syntax before calling `ctx.execute`.
- Require the same kind of integrity binding for `git_repository`-typed `source.json` entries as for `archive` entries (e.g., pin `commit` and validate resulting tree hash), and treat registry-controlled `remote` values as data that must be transport-restricted, not fully trusted.

### Proof of Concept
1. Stand up (or compromise/MITM) a Bazel module registry and add, for some module `evil@1.0`, a `source.json`:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c \"touch /tmp/pwned\"",
  "commit": "0000000000000000000000000000000000000000"
}
```
2. In a victim project's `MODULE.bazel`, add `bazel_dep(name = "evil", version = "1.0")` and configure `--registry=<attacker registry>` (or rely on this registry being one of the configured mirrors).
3. Run `bazel build //...` (or any command that triggers resolution/fetch of `evil@1.0`).
4. Bazel's `git_repository` machinery (`tools/build_defs/repo/git_worker.bzl`, `add_origin`/`fetch`) executes `git remote add origin ext::sh -c "touch /tmp/pwned"` followed by `git fetch origin`, causing Git to invoke the `ext::` helper and execute the attacker's shell command on the build machine — observable via creation of `/tmp/pwned`.

A JUnit/`BuildIntegrationTestCase` or `src/test/shell/bazel` reproduction would set up a local file-based registry serving the above `source.json`, point `--registry` at it, and assert that the sentinel file is created after a `bazel build` invocation that depends on the malicious module — analogous to the existing git repository shell tests in `src/test/shell/bazel/starlark_git_repository_test.sh` [7](#0-6) .

```text
def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)
```

```text
def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
```
