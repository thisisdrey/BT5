### Title
Unauthenticated `RecvError` packet allows remote attackers to forcibly tear down a live Nebula tunnel - (File: `outside.go`)

### Summary
The HyVM report describes a destructive primitive (`callcode` → `selfdestruct`) that is reachable *before* any real access control, letting anyone destroy the shared state that other parties depend on. Nebula's `header.RecvError` handling is analogous: `readOutsidePackets` dispatches `RecvError` packets in the "Unencrypted packets" branch, before any AEAD authentication or certificate verification takes place, and the handler can unilaterally destroy an established tunnel's state.

### Finding Description
In `outside.go`, incoming UDP packets are parsed and, for `header.RecvError`, routed directly to `f.handleRecvError` without decryption or certificate validation: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely by the cleartext `RemoteIndex` field carried in the packet header, and if found, tears the tunnel down: [2](#0-1) 

The only anti-spoofing check present is comparing the packet's source `netip.AddrPort` against the hostinfo's currently known remote address (`hr != addr`). Because Nebula runs over UDP, this "authentication" is just a source-address match on unauthenticated transport data — it does not involve the Noise handshake state, AEAD keys, or the peer certificate at all. Anyone who can (a) observe or guess a victim's `RemoteIndex` (a 32-bit value transmitted unencrypted in the header of every packet on that tunnel) and (b) spoof or send from the matching UDP source address can trigger `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying the tunnel state on the receiving node — with no certificate, no handshake, and no possession of any cryptographic material.

This mirrors the HyVM issue's core defect class: a state-destroying operation reachable through an unrestricted/unauthenticated code path, with impact amplified when other logic (e.g., liquidation-sensitive or availability-sensitive traffic, analogous to the "Nested wallet" scenario) depends on the destroyed state remaining intact.

### Impact Explanation
An attacker who can spoof the UDP source address (trivial for off-path attackers unless the underlying network deploys BCP38, and easy for on-path/adjacent attackers) and who has observed a `RemoteIndex` value from any packet on the target tunnel can force-close that tunnel at will. This is a remote availability/DoS impact: repeated `RecvError` injection can prevent a Nebula tunnel between two hosts from ever stabilizing, causing traffic loss, forced re-handshakes, and potential downstream failures for anything relying on tunnel continuity (e.g., time-sensitive control traffic), analogous to the exploit scenario in the report where destruction of shared state at an inopportune moment causes real-world harm.

### Likelihood Explanation
Reachability requires no CA-signed certificate and no valid Noise session — only knowledge of a `RemoteIndex` (observable from any single captured/relayed packet on the tunnel, since it's sent in cleartext) and the ability to spoof/send from the correct UDP source address. Nebula does have a configurable mitigation (`f.acceptRecvErrorConfig`, tied to `listen.send_recv_error`/accept settings per the CHANGELOG entry for v1.6.0 security fix), but the mechanism's default trust model still evaluates only the source `AddrPort`, not any cryptographic proof, so likelihood is elevated for attackers capable of basic UDP spoofing or already positioned on the network path.

### Recommendation
- Short term: Require `RecvError` handling to additionally validate against something derived from the current cryptographic session for the target hostinfo (e.g., only actionable after the peer has proven possession of the current cipher state, or rate-limit/ignore `RecvError` from addresses that haven't completed a fresh handshake), rather than relying on a UDP source-address string match alone.
- Long term: Treat all pre-authentication packet types (`Handshake`, `RecvError`) as adversarial input by default; audit every code path reachable prior to AEAD decryption for destructive side effects (tunnel teardown, hostinfo deletion) and gate them behind proof-of-possession of relevant secret material wherever feasible.

### Proof of Concept
1. Establish a tunnel between hosts `A` and `B`; capture one packet from `B` to `A` to learn the `RemoteIndex` A uses for B's hostinfo (or note it via any packet in the flow).
2. Craft a UDP packet with `header.RecvError` type/`RemoteIndex` set to the observed value, sourced (spoofed) from `B`'s currently known `UdpAddr`.
3. Send it to `A`. Per `handleRecvError`, `A` finds the hostinfo via `QueryReverseIndex`, the address check passes because the spoofed source matches the recorded remote, and `A` calls `f.closeTunnel(hostinfo)` plus `DeleteHostInfo`, destroying the tunnel state — without ever possessing Noise keys or a valid certificate. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
