### Title
Off-by-one boundary in `RewardsDistributor._calculateTokenDelta` lets a fresh account's index be read as `0` instead of `INITIAL_INDEX`, inflating reward accrual - (File: contracts/RewardsDistributor.sol)

### Summary
When a reward token is first enabled, `tokenStates[token].index` is initialized to `INITIAL_INDEX` (1e18). In `_calculateTokenDelta`, the fallback that assigns a never-seen account a starting index only fires when the token index is **strictly greater** than `INITIAL_INDEX` (`_tokenIndex > INITIAL_INDEX`). During the window where the index is exactly `INITIAL_INDEX` (no timestamp has elapsed yet since the speed was set), `_accountIndex` stays `0`, so `_deltaIndex = INITIAL_INDEX - 0 = 1e18` and the account is credited `balance × 1` reward tokens — as if it had accrued rewards since index zero. [1](#0-0) [2](#0-1) 

### Finding Description
`_calculateTokenDelta` is the reward-accrual analog of the reported bug class: a boundary condition causes a read to fall outside the intended range (index `0` instead of `INITIAL_INDEX`). The vulnerable window opens whenever `tokenStates[token_].index == INITIAL_INDEX`, i.e., from the block where `updateTokenSpeed`/`syncTokenSpeed` first sets a nonzero speed until `block.timestamp` advances so `_updateTokenIndex` pushes the index past `INITIAL_INDEX`. Any public trigger that calls `_updateTokensAccruedOf` during that window — `claimRewards`, `updateBeforeMintOrBurn`, or `updateBeforeTransfer` — settles the inflated delta into `tokensAccruedOf`. The claim path is fully permissionless: `claimRewards(account_, tokens_)` accepts any account and any token whose `tokenStates[_token].index > 0`. [3](#0-2) [4](#0-3) 

### Impact Explanation
Theft of unclaimed yield. The attacker is credited `depositToken.balanceOf(attacker)` (or `debtToken.balanceOf`) worth of the reward token, capped only by the distributor's balance (`_transferRewardIfEnoughTokens` pays out when `amount_ <= _balance`). Using a flash loan, the attacker deposits a large amount of underlying via `Pool.deposit`, calls `claimRewards(attacker, [depositToken])`, withdraws (no debt, so health checks pass), and repays the loan — draining up to the flash-loanable balance of the reward token held by the distributor. [5](#0-4) 

### Likelihood Explanation
The window is narrow but real and repeats: it exists in every block between a reward token's index initialization (governor `updateTokenSpeed` or keeper `syncTokenSpeed` setting a nonzero speed for a token with `index == 0`) and the first subsequent block where `speed > 0`. An attacker monitoring the mempool can back-run the speed-setting transaction in the same block. No privileged role, oracle manipulation, or special configuration is required beyond a live rewards distributor — which is the deployed configuration.

### Recommendation
Change the fallback condition so a missing account index defaults to `INITIAL_INDEX` (or to the current index) whenever `tokenIndex >= INITIAL_INDEX`, not strictly `>`. Equivalently, treat `_accountIndex == 0` as "initialize to `_tokenIndex`" so `_deltaIndex` is `0` for first-time accounts. Alternatively, initialize `accountIndexOf` to `INITIAL_INDEX` at the moment the token's index is created. Add a fork test covering a claim made in the same block as `updateTokenSpeed`.

### Proof of Concept
Foundry fork sketch:

```solidity
// contracts/RewardsDistributor.sol boundary test
function test_claimInSameBlockAsSpeedInit() public {
    // 1. Governor enables rewards for depositToken in this block
    vm.prank(governor);
    distributor.updateTokenSpeed(IERC20(address(depositToken)), 1e18);
    // tokenStates[depositToken].index == INITIAL_INDEX (1e18)

    // 2. Attacker flash-deposits, claims, withdraws in the same block
    uint256 amount = 1_000_000e18;
    deal(address(underlying), attacker, amount);
    vm.startPrank(attacker);
    underlying.approve(address(pool), amount);
    pool.deposit(address(depositToken), amount); // mints depositToken to attacker

    IERC20[] memory toks = new IERC20[](1);
    toks[0] = IERC20(address(depositToken));
    distributor.claimRewards(attacker, toks); // credits balance * INITIAL_INDEX delta

    uint256 stolen = rewardToken.balanceOf(attacker);
    assertGt(stolen, 0); // attacker received ~ deposit balance of rewardToken
    pool.withdraw(address(depositToken), amount);
    vm.stopPrank();
}
```

Caveat: this analysis is based on the indexed source; I verified the index logic in `RewardsDistributor.sol` directly, but did not fully trace `Pool.deposit`/`withdraw` lock semantics (`_revertIfLocked`) to confirm the same-transaction deposit/withdraw is unblocked — the attack also works across consecutive blocks as long as the index is still `INITIAL_INDEX`, which only requires the speed-setting transaction to be the most recent timestamp.
