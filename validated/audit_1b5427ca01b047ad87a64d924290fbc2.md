### Title
Segment-Index-Based `disabledApi` Bypass via Ambiguous/Duplicate Path Separators in `HttpApiAccessFilter` - (File: `framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java`)

### Summary
`HttpApiAccessFilter.isDisabled()` extracts the API method name to check against `node.disabledApi` by taking a fixed array index after splitting the endpoint string on `/`, rather than by matching against the actual routed servlet. This is structurally the same bug class as the rou3 double-slash issue: a mismatch between how the routing layer (Jetty servlet dispatch) resolves a request to a handler and how the security-gate layer re-derives the "logical" endpoint name from the raw path string. Any path variation that shifts segment positions (extra/empty segments, encoded slashes, etc.) can make the index-based extraction silently return the wrong (or empty) token, which will never match an entry in `disabledApiList`, bypassing the disable check while the underlying servlet may still be invoked.

### Finding Description
`isDisabled(String endpoint)` does:
```java
endpoint = URI.create(endpoint).normalize().toString();
...
disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
``` [1](#0-0) 

Two structural weaknesses mirror the rou3 advisory's root cause (a router that silently collapses/normalizes empty path segments differently than the security-gate code expects):

1. `java.net.URI.normalize()` only resolves `.`/`..` dot-segments per RFC 3986 §5.2.4; it does **not** collapse empty segments produced by repeated slashes (`//`). So `endpoint.split("/")` on a path containing `//` produces an extra empty string in the array, shifting the fixed index `[2]` away from the actual method name (e.g. `/wallet//getnowblock` → `["", "wallet", "", "getnowblock"]`, index `2` = `""`, not `getnowblock`).
2. The filter derives `endpoint` from `contextPath + request.getServletPath()` [2](#0-1) , i.e. it trusts the Jetty-resolved servlet path. Because the FullNode/PBFT/Solidity HTTP servlets are registered with **exact** path specs (e.g. `"/wallet/getnowblock"`) [3](#0-2) , any discrepancy between how Jetty's URI/path-compliance layer resolves an incoming request URI (which may tolerate or normalize ambiguous separators depending on Jetty's `UriCompliance`/path-canonicalization behavior) and how this filter's naive string-splitting re-derives the method name from that same path creates exactly the router-vs-app-layer normalization mismatch the rou3 advisory describes.

The project's own regression test only exercises `.`/`..` dot-segment collapsing (`/wallet/a/../b/../getnowblock`) [4](#0-3) , confirming the developers were aware that path-normalization games against this specific index-based check are a real concern class, but no equivalent test/handling exists for duplicate/ambiguous slash segments — the exact bug class in the external report.

The same fragile "split-by-`/`-and-take-fixed-index" pattern is duplicated for gRPC in `RpcApiAccessInterceptor.isDisabled()` (`endpoint.split("/")[1]`) [5](#0-4) , though gRPC method names come from the protobuf `MethodDescriptor` rather than a user-controlled URL, so it is not attacker-reachable in the same way.

### Impact Explanation
If an attacker can reach the FullNode/Solidity/PBFT HTTP listener with a path containing an ambiguous separator sequence that (a) still dispatches to the intended exact-path-mapped servlet via Jetty's own path resolution/compliance handling, while (b) `getServletPath()`/the reconstructed `endpoint` string retains the extra separator, the `disabledApiList.contains(...)` check computed on the wrong split index will evaluate to `false`, and `HttpApiAccessFilter.doFilter()` will call `chain.doFilter(...)` to invoke the disabled servlet anyway [6](#0-5) . This would let an operator's `node.disabledApi` hardening (used to hide sensitive endpoints such as `getaccount`, wallet-mutation endpoints, etc., from public exposure) be bypassed by an unprivileged remote HTTP client, re-exposing an endpoint the operator explicitly intended to disable.

### Likelihood Explanation
Exploitability is contingent on the exact Jetty version/`HttpURI` path-canonicalization behavior in use (whether Jetty's servlet-path resolution for exact-match `ServletHolder` path specs tolerates/normalizes `//` the same way while leaving `getServletPath()` un-collapsed). I was unable to confirm the concrete Jetty version/URI-compliance configuration from the indexed files (build.gradle dependency resolution details were not available in the index), so I cannot fully verify end-to-end reachability of a live bypass versus a 404 from Jetty's own routing before this filter even executes. This is a real, demonstrable logic flaw in the disabled-API check's parsing regardless (proven statically and by the existing dot-segment test), but confirming a working double-slash bypass requires live testing against the actual Jetty version, which is outside what static indexing can confirm.

### Recommendation
Replace the fragile `split("/")[fixed-index]` parsing in `HttpApiAccessFilter.isDisabled()` (and the analogous logic in `RpcApiAccessInterceptor`) with matching against the actual registered servlet path/method name (e.g., derive the disabled-check key from the `HttpServletRequest`'s resolved `Servlet`/`ServletHolder` name, or from `request.getPathInfo()`/last non-empty path segment after explicitly collapsing repeated `/` characters) rather than a positional array index on a loosely-normalized string. Additionally, explicitly collapse consecutive slashes (`endpoint.replaceAll("/+", "/")`) before splitting, in addition to the existing `URI.normalize()` dot-segment handling, to align this layer's notion of "the requested API name" with however Jetty ultimately routes the request.

### Proof of Concept
Static PoC (parsing-level, demonstrating the index-shift root cause independent of Jetty routing behavior):
```java
String endpoint = "/wallet//getnowblock";
endpoint = URI.create(endpoint).normalize().toString(); // "/wallet//getnowblock" (unchanged, no slash collapsing)
String[] parts = endpoint.split("/");
// parts = ["", "wallet", "", "getnowblock"]
String checked = parts[2].toLowerCase(Locale.ROOT); // "" -- NOT "getnowblock"
// disabledApiList.contains("") is false even though disabledApiList contains "getnowblock"
```
This can be reproduced directly against `HttpApiAccessFilterTest#testIsDisabled` by adding a case:
```java
CommonParameter.getInstance().setDisabledApiList(Collections.singletonList("getnowblock"));
boolean f = (boolean) privateMethod.invoke(httpApiAccessFilter, "/wallet//getnowblock");
// Currently returns false — the check is bypassed for this input
```
A full network-level PoC (confirming Jetty still dispatches `GET /wallet//getnowblock HTTP/1.1` to `GetNowBlockServlet` despite the double slash) would require live testing against the deployed Jetty version, which I could not execute or verify from the static index.
