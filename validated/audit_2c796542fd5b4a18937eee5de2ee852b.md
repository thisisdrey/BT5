### Title
Unvalidated `new_authority` parameter in `TransferToNewAccount`/`TransferToNewAccountPda` allows permanent freeze of account funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `transfer_to_new_account` and `transfer_to_new_account_pda` instruction handlers accept a caller-supplied `new_authority` account that is used, unchecked, as the sole authority of a freshly created `MarginfiAccount` that inherits the old account's full `LendingAccount` (deposits/borrows). The account itself is explicitly annotated as unchecked (`/// CHECK: WARN: New authority is completely unchecked`), and there is no guard against `Pubkey::default()` or any other unusable/invalid address, matching the bug class in the external report (missing validation of an address parameter before it is used to gate future access).

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` both declare: [1](#0-0) [2](#0-1) 

`new_authority` is an `UncheckedAccount` with no `constraint` requiring it to be non-default or otherwise valid. The handler uses `ctx.accounts.new_authority.key()` directly as the authority of the new account: [3](#0-2) 

`initialize_migrated_account` sets the new account's authority to this value and copies over the old account's entire `lending_account` (i.e., all deposit/borrow balances): [4](#0-3) 

The old account is then irreversibly disabled and its `lending_account` is zeroed, and `migrated_to`/`migrated_from` are set, which is also checked to prevent re-migration: [5](#0-4) [6](#0-5) 

If `new_authority` is `Pubkey::default()` (or any other address that cannot produce a valid signature, e.g. a PDA with no corresponding program logic to sign for it), the newly created account — which now holds all the migrated deposit/borrow positions — becomes permanently unusable: no `Signer` can ever match `new_authority`, so no withdraw/repay/close/liquidate-trigger instruction requiring `authority` as signer can succeed for that account. Because the old account is simultaneously disabled and zeroed (`ACCOUNT_DISABLED` flag set, `lending_account` zeroed, `migrated_to` set so it can't be reused), there is no fallback path to recover the funds.

This is the direct analog of the reported bug class: a caller-supplied address is used in an access-control-relevant field (`authority`) without any validation, and an invalid/zero value can permanently block the contract (here, a specific margin account and its funds) from working correctly.

### Impact Explanation
If `new_authority` is left as, or manipulated to be, `Pubkey::default()` (e.g., through a client bug, a malicious/compromised front-end, or a crafted third-party integration that assembles the transaction on the user's behalf and the user blind-signs it), the account's entire collateral and debt position becomes permanently frozen — unrecoverable by any party, since the old account is simultaneously disabled and its balances zeroed. This is a permanent lock/freeze of user funds within the core account-migration path.

### Likelihood Explanation
The instructions are permissionless in the sense that any account authority can invoke them; the only gating is that `authority` must be the legitimate signer of the old account (`is_signer_authorized`) and the account must not be frozen. There is no additional confirmation step or on-chain sanity check on `new_authority`, so a single mistake (wrong/blank keypair, malformed integration, or malicious front-end substituting the destination) is sufficient to trigger the freeze. The explicit `/// CHECK: WARN: New authority is completely unchecked` comment in the code confirms this was a known, unaddressed risk area.

### Recommendation
Add a constraint (or explicit `require!`) in both `TransferToNewAccount` and `TransferToNewAccountPda` handlers to reject `new_authority == Pubkey::default()`, and consider requiring `new_authority` to be a `Signer` (or otherwise proven to be capable of signing) so migrations cannot target an unusable address.

### Proof of Concept
1. User owns a `MarginfiAccount` with deposits/borrows.
2. User (or a compromised/buggy client acting on the user's behalf) submits `transfer_to_new_account_pda` with `new_authority = Pubkey::default()`.
3. The instruction succeeds: the new account is created with `authority = Pubkey::default()` and inherits the full `lending_account` from the old account.
4. The old account is disabled (`ACCOUNT_DISABLED`) and zeroed (`lending_account = LendingAccount::zeroed()`), and `migrated_to` prevents any re-migration.
5. No transaction can ever be signed by `Pubkey::default()`, so the new account's deposits/borrows are permanently frozen with no recovery path.

fn initialize_migrated_account(
    new_account: &mut MarginfiAccount,
    old_account: &MarginfiAccount,
    new_authority: Pubkey,
    current_timestamp: u64,
    old_account_key: Pubkey,
) {
    new_account.initialize(old_account.group, new_authority, current_timestamp);
    new_account.lending_account = old_account.lending_account;
    new_account.emissions_destination_account = old_account.emissions_destination_account;
    new_account.account_flags = old_account.account_flags;
    new_account.migrated_from = old_account_key;
    new_account.indexer_flags = old_account.indexer_flags;
    new_account.sync_indexer_flags();
}

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);

}
