### Title
Unauthenticated dust transfers/deposits fill a victim's per-account token list, bricking all future first-time deposits, issuance and inbound transfers for that account - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount` + `depositTokensOfAccount` (`Pool.sol:79`, `Pool.sol:143-148`). The list is populated not only on deposits/issues but also on plain `DepositToken._transfer` / `DepositToken._mint` to any recipient (`DepositToken.sol:486-488`, `DepositToken.sol:518-520`), and `deposit(amount_, onBehalfOf_)` lets anyone mint a deposit-token position to an arbitrary account (`DepositToken.sol:211-237`). An attacker can therefore force entries into a victim's list without consent. Once the combined length hits 30, `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` (`Pool.sol:204-219`), and every code path that would add a new token type to that account DoS-reverts.

### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` mints `msdTOKEN` to `onBehalfOf_`, an arbitrary address chosen by the caller (`DepositToken.sol:211-237`). On a `0 → >0` balance change, `_mint` calls `pool.addToDepositTokensOfAccount(onBehalfOf_)` (`DepositToken.sol:486-488`).
- `DepositToken.transfer` / `transferFrom` are permissionless ERC20 paths; `_transfer` also calls `pool.addToDepositTokensOfAccount(recipient_)` on first receipt (`DepositToken.sol:498-526`), gated only by `_revertIfLocked` on the *sender* (`DepositToken.sol:348-376`).
- `Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` revert when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (`Pool.sol:143-148`, `Pool.sol:204-219`). The cap counts debt tokens too, so a mixed dusting also blocks `DebtToken.mint`'s `0 → >0` path during `issue`.

Concrete attack: the attacker deposits a minimal amount of each deposit token of the pool with `onBehalfOf_ = victim` (or dust-`transfer`s tokens it already holds) until the victim's combined list reaches 30. After that, for the victim:

- `deposit(anyAmount, victim)` for any collateral type the victim doesn't already hold reverts — nobody can top up the victim's collateral with a new asset.
- `DebtToken.issue` reverts when it would mint a debt token the victim doesn't already hold (`addToDebtTokensOfAccount` reverts).
- Any `transfer`/`transferFrom`/`seize` sending a not-yet-held deposit token to the victim reverts (`_transfer` → `addToDepositTokensOfAccount`).
- Entries are only removed when a balance returns to exactly zero (`DepositToken.sol:460-462`, `523-525`), so the victim must spend gas to `withdraw`/transfer out up to 30 dust positions before normal account functionality is restored.

### Impact Explanation
Liveness/freezing impact on a per-account basis: all first-time-token operations for the victim revert. The victim cannot receive new collateral types, cannot open debt in new synthetics, and cannot be the recipient of new deposit tokens (including via `seize` and `deposit onBehalf`). This is a temporary freezing of the victim's position-management functionality; the victim retains withdrawal of existing tokens, but only after an unforced, attacker-imposed cleanup cost of emptying dust balances. If the victim is a contract/integration (e.g., a router, vault or the SmartFarmingManager flow holding transient first-time balances) that cannot itself burn the dust tokens, the freeze is effectively permanent for the affected token types. The bug class matches the CVE: a resource bound meant to protect the protocol (bounded per-account iteration) is weaponized by an unprivileged user exceeding it against someone else's account.

### Likelihood Explanation
Requires no privileged role, no oracle manipulation and no flash liquidity — only dust amounts of the pool's deposit tokens (attacker can mint them itself via `deposit`). Cost scales linearly with the number of registered collateral/debt tokens in the target pool and is highest where many collaterals are listed; on pools with few tokens the attack is limited by the number of distinct tokens available, but combined deposit+debt token counting widens the surface. Fully reproducible on a fork with public `deposit`/`transfer` calls.

### Recommendation
Do not mutate the per-account list on behalf of accounts that did not initiate the action. Options:
- Only call `addToDepositTokensOfAccount` when the recipient is `_msgSender()` / the position owner initiating the call, and track unsolicited balances in a separate non-enumerated structure; or
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` non-reverting-at-cap (e.g., return a boolean and let `debtPositionOf` skip unlisted tokens, or store list membership outside the bounded `MappedEnumerableSet`); or
- Let any account purge its own list entries regardless of balance (opt-out removal), so victims can cheaply eject dust without zeroing balances.

### Proof of Concept
Hardhat sketch (forked deployment, `pool` with ≥2 deposit tokens `dtA`, `dtB`, …, attacker EOA `atk`, `victim`):

```solidity
// Attacker fills victim's list to MAX_TOKENS_PER_USER (30)
for (uint256 i; i < depositTokens.length && pool.depositTokensOfAccountLength(victim) < 30; ++i) {
    underlying[i].approve(address(depositTokens[i]), DUST);
    depositTokens[i].deposit(DUST, victim); // onBehalfOf_ = victim, adds token to victim's list
    // or: depositTokens[i].transfer(victim, DUST) using attacker's own msdTOKEN balance
}
assertEq(pool.depositTokensOfAccountLength(victim) + pool.debtTokensOfAccountLength(victim), 30);

// 1) New collateral deposit to victim reverts
underlyingNew.approve(address(dtNew), 1e18);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
dtNew.deposit(1e18, victim);

// 2) Inbound transfer of a not-yet-held deposit token reverts
dtNew.deposit(1e18, attacker); // attacker's own list unaffected
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
dtNew.transfer(victim, 1);

// 3) Issuing a synth whose debt token victim doesn't hold reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDebtToken.issue(1e18, victim);

// Victim must burn each dust balance to zero (removeFromDepositTokensOfAccount)
// before any of the above works again — unforced cleanup cost imposed by attacker.
```

Note: severity is bounded by the number of distinct deposit+debt tokens registered in the target pool and by the victim's ability to self-clean via `withdraw`/`transfer`; on pools with few listed tokens, the combined-list accounting (debt tokens count too) is what preserves reachability to the 30-entry cap.
