Audit Report

## Title
Snowbridge v2 outbound queue pays relayer rewards for failed Ethereum executions - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` registers a relayer reward and deletes the corresponding `PendingOrder` for any structurally valid delivery receipt, regardless of the `success` flag carried in the receipt. Since the `success` field — decoded from the Ethereum `InboundMessageDispatched` event — is never inspected, a relayer who submits proof of a *reverted* Ethereum execution is paid the full message fee exactly as if the message had succeeded.

## Finding Description
The Ethereum gateway contract emits `InboundMessageDispatched(nonce, topic, success, reward_address)`, explicitly recording execution outcome on-chain. This is decoded into `DeliveryReceipt.success` in `TryFrom<&Log> for DeliveryReceipt` (`bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs`, lines 38-51). The public, unprivileged extrinsic `submit_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, lines 298-317) verifies the log/proof pair via `T::Verifier::verify`, builds the `DeliveryReceipt`, and passes it straight to `process_delivery_receipt`.

`process_delivery_receipt` (lines 446-480) performs exactly two checks: that `receipt.gateway` matches `T::GatewayAddress::get()`, and that a `PendingOrder` exists for `receipt.nonce`. It then unconditionally calls `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` when `order.fee > 0`, and removes the `PendingOrders` entry. `receipt.success` is not referenced anywhere in the function body. Consequently a receipt proving a reverted/failed Ethereum-side execution is processed identically to a receipt proving success — the reward is paid and the order is consumed (removed) either way, so there is no retry or alternate handling path for failed messages.

## Impact Explanation
This allows an unbacked/duplicate-value payout from the bridge reward pool: relayers can be rewarded for message deliveries that did not achieve their intended effect on Ethereum, draining reward funds and creating a perverse incentive to relay or manufacture failing traffic. This matches the Polkadot SDK impact gate categories "theft or unbacked mint or unlock" and "duplicate settlement or payout" in bridge reward flows, since the exact corrupted value is the reward payout keyed to `order.fee`/`PendingOrders` state, which is settled without verifying execution success (`receipt.success`).

## Likelihood Explanation
The path is fully public and unprivileged — any signed account can call `submit_delivery_receipt` with a valid proof of a real (but failed) `InboundMessageDispatched` event. No malicious relayer collusion, node compromise, or governance action is required; only observation and relaying of a genuine but failed Ethereum execution log. The nonce-based `PendingOrders` check prevents double-claiming the same nonce, but does not prevent the first (and only) claim for a failed message.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before calling `register_reward`. On `success == false`, skip (or reduce) the reward while still removing/resolving the `PendingOrder`, or take an alternate remediation action (e.g., emit a distinct "delivery failed" event, allow retry, or route fee differently). If paying for delivery attempts regardless of on-chain execution outcome is intentional, the `success` field should be removed from consideration and this behavior explicitly documented as intended, since currently the field is decoded but silently dropped.

## Proof of Concept
1. A Snowbridge v2 outbound message with nonce `N` and fee `F > 0` is dispatched and accepted into `PendingOrders` via `do_process_message`.
2. On Ethereum, the corresponding inbound call reverts, so the gateway emits `InboundMessageDispatched(nonce=N, topic=..., success=false, reward_address=...)`.
3. Any relayer builds an `EventProof` for this log and calls `submit_delivery_receipt(origin, Box::new(event_proof))`.
4. `T::Verifier::verify` succeeds (real, valid proof), `DeliveryReceipt::try_from` decodes `success: false`.
5. `process_delivery_receipt` checks gateway address and `PendingOrders::get(N)`, both pass; it calls `register_reward(&reward_account, DefaultRewardKind, F)` and removes `PendingOrders[N]`, ignoring `success == false`.
6. The relayer subsequently calls `claim_rewards` and receives fee `F` despite the underlying message execution having failed on Ethereum.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
