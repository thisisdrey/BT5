### Title
Attacker can fill a victim's 30-token account list with dust transfers, blocking deposits of new collateral types and new-debt issuance (`Pool.addToDepositTokensOfAccount` / `onlyIfAdditionWillNotReachMaxTokens`) — (File: contracts/Pool.sol)

### Summary
CVE-2025-50089 is an availability bug class (a reachable call path deterministically hangs/crashes the service). The reachable analog in Metronome is the per-account token-list cap: `Pool` enforces `MAX_TOKENS_PER_USER = 30` combined deposit + debt tokens, and any action that would add a new token to an account's list reverts. Because `DepositToken._transfer` registers the *recipient's* balance going `0 → >0` via `pool.addToDepositTokensOfAccount(recipient_)`, any unprivileged EOA can dust-transfer deposit tokens to a victim until the victim's combined list hits 30. From then on, every operation that would add a *new* token type to the victim's lists reverts with `UserReachedMaxTokens()`, so the victim cannot deposit a different collateral nor mint a new debt type — an attacker-driven denial of service on that account, including freezing their ability to add collateral to rescue an unhealthy position.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`), and both `addToDebtTokensOfAccount` (`contracts/Pool.sol:204`) and `addToDepositTokensOfAccount` (`contracts/Pool.sol:216`) are gated by it.
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance transitions from zero (`contracts/DepositToken.sol:518-520`). `transfer`/`transferFrom` only check that the *sender's* amount is unlocked (`_revertIfLocked`), so an attacker holding dust balances can push new token entries onto any victim's list (`contracts/DepositToken.sol:348-376`).
- `DepositToken._mint` does the same on `deposit(amount_, onBehalfOf_)` for the beneficiary (`contracts/DepositToken.sol:234, 486-488`), so once the list is full, the victim cannot deposit into any collateral they do not already hold, and `DebtToken._mint` similarly blocks issuing any new debt type (`contracts/DebtToken.sol:598-600`).
- The invariant that breaks is liveness of the account: public entry points reachable by an unprivileged attacker (`DepositToken.transfer`, or `deposit` with `onBehalfOf_ = victim`) force the victim's state into a configuration where subsequent legitimate transactions deterministically revert — mirroring the CVE's "frequently repeatable crash" on the processing path.
- No guard stops this: `transfer` is not behind `whenNotPaused`-restricted admin paths, there is no minimum transfer amount, no opt-in for receiving deposit tokens, and `SynthContext`/`Operator` meta-sender paths do not change the outcome.

### Impact Explanation
Temporary freezing of funds / denial of service per victim:
- The victim cannot deposit any *new* collateral type — `deposit` reverts in `_mint → addToDepositTokensOfAccount` (`contracts/DepositToken.sol:486-488`). If their position drifts toward liquidation and the collateral they already hold is insufficient or they want to diversify, they are blocked from topping up, so their position can be liquidated while the rescue path reverts.
- The victim cannot receive new deposit-token types (`transfer`, `seize` to them, `SmartFarmingManager.leverage`/`flashRepay` flows that mint or transfer a new collateral to them) and cannot issue a new debt type — all revert.
- Recovery exists (the victim can transfer each dust balance back out, which pops the entry via `removeFromDepositTokensOfAccount` when their balance hits zero, `contracts/DepositToken.sol:523-525`), making this a temporary rather than permanent freeze — matching the CVE's medium severity.

### Likelihood Explanation
- Requirements: the pool must have enough distinct whitelisted deposit/debt tokens that the combined count can reach `MAX_TOKENS_PER_USER` (30), and the attacker must hold a dust balance in each one. Attack cost is ~30 dust deposits + 30 transfers — trivial. No privileged role, oracle manipulation, or timing dependence is needed; the revert is deterministic on every subsequent add-path call.
- Limitations: on deployments with fewer than ~30 listed tokens total, the cap may be unreachable; the victim can self-recover by sweeping the dust, and cannot be permanently locked. This keeps impact at medium/low rather than high.

### Recommendation
- Do not revert when the account list is full; either raise/remove the per-account cap or make the cap apply only to tokens the account *added itself* (e.g., track "self-registered" vs. "received" entries, or skip registering the recipient on plain `transfer`/`seize` and lazily count tokens at `debtPositionOf` time).
- Alternatively, add a minimum meaningful amount before registering a token in `depositTokensOfAccount` (dust below a USD threshold does not create an entry), and/or allow anyone to force-remove zero-value entries.

### Proof of Concept
Hardhat (fork or local deploy) sketch:

```ts
// Setup: pool with >=30 whitelisted DepositTokens (or a mix of deposit+debt tokens
// such that combined count can reach MAX_TOKENS_PER_USER = 30).
const victim = alice.address;

// Attacker deposits 1 wei of underlying into each deposit token
// and transfers 1 wei of the msdTOKEN to the victim.
for (const dt of depositTokens) {
  await underlyingOf(dt).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, attacker.address);
  await dt.connect(attacker).transfer(victim, 1); // adds entry to victim's list
}

// Sanity: victim's combined token list is now at the cap
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30);

// 1) Victim cannot deposit into a collateral they don't already hold:
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 2) Victim cannot receive a new deposit token type:
await expect(
  newDepositToken.connect(attacker).transfer(victim, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) Victim cannot issue a new debt type (DebtToken._mint -> addToDebtTokensOfAccount):
await expect(
  newDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Each call deterministically reverts inside `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`), demonstrating the repeatable-crash/availability analog to the CVE's bug class.
