### Title
Unvalidated array-length taken from calldata used to allocate `byte[][]` in TVM precompile ABI decoding, enabling attacker-triggered `OutOfMemoryError`/crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes an unchecked `num_elements` count coming from an untrusted caller being used directly to allocate/iterate an array, causing an out-of-bounds heap access and crash. The same pattern of an untrusted "element count" word being used to size an array without any upper-bound validation exists in java-tron's precompiled-contract ABI-decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`.

### Finding Description
`extractBytes32Array` reads a length word directly out of the caller-controlled `DataWord[] words` (parsed from the precompile's raw `data` input) and immediately uses it, unchecked, to allocate a two-dimensional byte array and drive a loop: [1](#0-0) 

`extractBytesArray` and `extractSigArray` follow the identical pattern — they only bound-check `offset` against `words.length`, but the `len` value itself (`words[offset].intValueSafe()`) is never checked against any sane maximum or against the actual size of `data` before being used to size a `byte[len][]` array and to index into `data` with attacker-controlled offsets: [2](#0-1) 

Because `DataWord.intValueSafe()` derives an `int` from an arbitrary 256-bit word supplied by the caller inside a smart-contract `CALL` to a precompiled address, an attacker who deploys or triggers a contract that invokes one of these ABI-decoding precompiles can supply a `len` value close to `Integer.MAX_VALUE`. This causes `new byte[len][]` to attempt an allocation of billions of array-header slots, exhausting heap memory (`OutOfMemoryError`), or, for smaller-but-still-oversized `len` values relative to the actual `data` length, causes `extractBytes` (`Arrays.copyOfRange(data, offset, offset + len)`) to be called with out-of-bounds offsets/lengths, throwing unchecked `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` deep inside the precompile execution path: [3](#0-2) 

This mirrors the root cause of CVE-2017-5994 exactly: a size/count field taken from untrusted input is used to allocate/iterate a data structure with no upper-bound or consistency check against the actual backing buffer.

### Impact Explanation
An `OutOfMemoryError` or unhandled runtime exception thrown while a full node is processing a transaction that calls one of these precompiles can crash or destabilize the JVM process handling block/transaction execution, since `Error` types are generally not caught by the surrounding `Exception`-only catch blocks used elsewhere in `PrecompiledContracts`. If nodes crash inconsistently (depending on available heap at the time), this can also cause consensus-relevant divergence between nodes if some nodes process the transaction successfully and others crash, risking a chain halt for affected nodes. This qualifies as a node crash/denial-of-service.

### Likelihood Explanation
Reaching this code only requires deploying a trivial contract that calls the affected precompiled contract address with crafted calldata containing an artificially large length word at the expected offset — no special privilege, stake, or witness/SR status is required, only enough energy/fee to cover the call. This makes the likelihood high for any attacker capable of broadcasting a signed transaction.

### Recommendation
Add explicit upper-bound validation on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` — e.g., reject if `len < 0`, if `len` exceeds a reasonable maximum (bounded by `data.length / WORD_SIZE` or a fixed small constant appropriate to the precompile's semantics), and verify that `bytesOffset`/`bytesLen`/`SIG_LENGTH`-derived read ranges stay within `data.length` before allocating or copying. Wrap the precompile decode path so that any resulting `Error`/`RuntimeException` is caught and converted into a normal "execution failed" result rather than propagating and potentially destabilizing the node process.

### Proof of Concept
1. Deploy or use an existing contract that performs a `CALL`/`STATICCALL` to the precompiled contract address whose `execute(byte[] data)` implementation eventually invokes `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (one of the ABI-array-decoding precompiles in `PrecompiledContracts.java`).
2. Craft the calldata so that the 32-byte word at the expected "array length" offset encodes a very large positive integer (e.g., `0x7FFFFFFF`).
3. Broadcast the transaction triggering the call; `words[offset].intValueSafe()` returns the large value, `new byte[len][]` is allocated (or `extractBytes` is called with an out-of-range `offset+len`), causing an `OutOfMemoryError` or unhandled `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` during transaction execution on any full node that processes the transaction.

Note: I could not fully confirm from the indexed code which specific precompiled-contract address(es) invoke `extractBytes32Array`/`extractBytesArray`/`extractSigArray` at runtime (the call sites were not resolvable within the available index), so the exact externally-callable entry point should be confirmed by a Devin session with full repository access before remediation.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
