Audit Report

## Title
`claim_bounty` and `claim_child_bounty` unconditionally delete bounty state and emit success events even when the reward-token `Currency::transfer` calls fail - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`pallet-bounties::claim_bounty` and `pallet-child-bounties::claim_child_bounty` push-transfer bounty fee and payout amounts via `T::Currency::transfer(..., AllowDeath)` and only guard the result with `debug_assert!(res.is_ok())`, which compiles to a no-op in release/production runtimes. Regardless of whether the transfer actually succeeds, execution falls through to unconditionally deleting the bounty (or child-bounty) storage record and emitting `BountyClaimed`/`Claimed` success events.

## Finding Description
In `claim_bounty`, after computing `final_fee` and `payout`, the code performs two currency transfers out of the bounty sub-account and checks each result only via `debug_assert!`: [1](#0-0) 
Immediately afterward, regardless of the (discarded in release) transfer outcome, the bounty is deleted and a success event is emitted: [2](#0-1) 

The identical pattern exists in `claim_child_bounty`, where both the curator-fee transfer and the beneficiary payout transfer are guarded only by `debug_assert!`, followed by unconditional removal of the child-bounty description and storage entry, and emission of the `Claimed` event: [3](#0-2) 

Because `debug_assert!` is stripped in release builds — the only builds used on-chain — a failed `T::Currency::transfer` (e.g., due to the destination account being frozen/blocked at the currency-implementation level, or any other transfer failure condition) is silently ignored. There is no `?`, `ensure!`, or state rollback tied to the transfer result. The settlement state (bounty/child-bounty existence and status) is deleted unconditionally, and a `BountyClaimed`/`Claimed` event falsely asserts the payout succeeded, violating the invariant that payout state must only advance after the underlying settlement actually succeeds.

## Impact Explanation
If a transfer fails, the corresponding funds remain in the (now-orphaned) `bounty_account`/`child_bounty_account` sub-account with no surviving storage record referencing them and no retry extrinsic, since `*maybe_bounty = None` / `*maybe_child_bounty = None` unconditionally destroys the only state that could be used to reattempt payout. This is a permanent lock of treasury-derived funds, combined with a public event that misreports the outcome. It matches the repository's allowed impact bucket of "permanent user-fund lock" and violates the settlement invariant that payout state may only advance after settlement succeeds atomically.

## Likelihood Explanation
This requires `T::Currency` for `pallet-bounties`/`pallet-child-bounties` to be configured (by the runtime, not by an attacker) such that transfers to specific accounts can fail — for instance an adapter around an asset type supporting account freezing/blocking, or any other legitimate `Currency` implementation returning `Err` from `transfer`. No privileged or malicious actor is required to trigger the bug once such a configuration and a blocked/frozen beneficiary or curator exist; any signed account can call `claim_bounty`/`claim_child_bounty` to trigger the loss, since these calls are open to "anyone" as noted in the code comments and docs.

## Recommendation
Replace both `debug_assert!(res.is_ok())` checks in `claim_bounty` and `claim_child_bounty` with proper error propagation (e.g., `res?`) so that a failed transfer aborts the extrinsic and reverts all storage mutations via `try_mutate_exists` before the bounty/child-bounty record is deleted. Alternatively, adopt the asynchronous payment/retry state machine already used in `pallet-multi-asset-bounties` (`check_status`/`retry_payment`) so that a failed transfer leaves the bounty in a recoverable state instead of unconditionally deleting it.

## Proof of Concept
1. In a mock runtime for `pallet-bounties` or `pallet-child-bounties`, implement/wrap a `Currency` type whose `transfer` returns `Err` for a designated "blocked" beneficiary/curator account.
2. Create, fund, and award a bounty (or child bounty) to the blocked beneficiary account, awaiting the `PendingPayout` unlock period.
3. Call `claim_bounty` (or `claim_child_bounty`) after the unlock delay.
4. Observe that despite `T::Currency::transfer` returning `Err`, the call returns `Ok(())`, `BountyClaimed`/`Claimed` is emitted, and the bounty/child-bounty storage entry is removed — while the funds remain stranded in the bounty sub-account with no further pallet call able to recover them.
