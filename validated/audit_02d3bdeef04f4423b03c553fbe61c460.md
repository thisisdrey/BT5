### Title
`remove_account` fails to purge postponed-receipt state (`PendingDataCount`/`PostponedReceipt`/`PostponedReceiptId`), letting stale privileged actions execute against a re-created account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`), invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`), only clears `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows for the deleted account. It leaves `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries untouched, so a postponed self-targeted `ActionReceipt` created before deletion survives account deletion and later executes against whatever account subsequently occupies that same `AccountId`.

### Finding Description
When a `FunctionCall` on account `A` schedules a promise chain to itself with an unresolved `input_data_id`, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) persists:
- `TrieKey::PostponedReceiptId{receiver_id: A, data_id}` → `receipt_id`
- `TrieKey::PendingDataCount{receiver_id: A, receipt_id}` → count
- `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}` → the full `ActionReceipt` [1](#0-0) 

If `A` then submits `DeleteAccountAction`, `action_delete_account` calls `remove_account`, which only removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows: [2](#0-1) [3](#0-2) 

The `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` rows keyed by `receiver_id: A` are never removed by this function. This is corroborated by the resharding boundary-key enumeration test, which explicitly lists these as separate account-keyed columns (`col::POSTPONED_RECEIPT_ID`, `col::PENDING_DATA_COUNT`, `col::POSTPONED_RECEIPT`) distinct from the ones `remove_account` clears. [4](#0-3) 

Once `A` is deleted and later recreated via a `CreateAccountAction` from any funder, and the outstanding `DataReceipt` for the original `data_id` is delivered, `process_receipt`'s `Data` arm (`runtime/runtime/src/lib.rs:1367-1474`) finds the still-present `PostponedReceiptId` link, decrements `PendingDataCount`, and once it reaches zero, fetches and executes the stale `PostponedReceipt` via `apply_action_receipt`: [5](#0-4) 

This stale `ActionReceipt` was authorized under the old account's execution context (predecessor/receiver both equal to the old `A`), but its actions (`FunctionCall`, `AddKeyAction`, `TransferAction`, etc.) execute against the newly created account occupying the same `AccountId`, without any re-validation tying the action to the new account owner's consent. No existing check in `action_delete_account` (storage-usage limit, gas-key balance limit) inspects or blocks deletion in the presence of outstanding postponed/pending-data state for the account.

### Impact Explanation
This is an authorization-escalation bug: actions queued by the original owner of an account name execute against a distinct, newly created account with the same name, potentially adding attacker-controlled access keys (`AddKeyAction`), transferring funds, or invoking arbitrary contract methods (`FunctionCall`) on behalf of a party that never authorized it in the new account's lifetime. This falls under "authorization escalation across accounts or promises" in the bounty scope, since the recreated account's state (its funds, deployed contract, and keys) can be manipulated by a receipt whose privileges were derived from the deleted predecessor account, not the new one.

### Likelihood Explanation
Preconditions are attacker-controlled and require no privileged access: a funded ordinary account can (1) deploy/call a contract that issues a self-targeted `promise_then` producing an unresolved `input_data_id`, (2) submit `DeleteAccountAction` on itself, and (3) have any third party (or itself, via a relayed meta-transaction) recreate the same `AccountId`. Delivery of the original pending `DataReceipt` is guaranteed eventually by normal receipt processing since it isn't cleaned up on deletion. The attack is fully reproducible and repeatable at negligible cost (storage-staking deposits and gas fees only), limited only by whether a third party can be induced to recreate the exact same account name before the outstanding data resolves — a scenario plausible for accounts intentionally "freed" and immediately relisted/reused.

### Recommendation
Extend `remove_account` to also enumerate and remove `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, `TrieKey::ReceivedData`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` rows for the account being deleted (mirroring the full `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` set), or alternatively reject `DeleteAccountAction` while any such outstanding entries exist for the account.

### Proof of Concept
Runtime integration test plan (test-loop or `runtime/runtime/src/tests/apply.rs` style):
1. Create account `A` with funds; have `A` execute a `FunctionCall` that issues `promise_then` targeting itself, leaving an unresolved `input_data_id` (e.g., via a cross-shard style delayed data receipt).
2. Assert state contains `TrieKey::PostponedReceiptId{A,..}`, `TrieKey::PendingDataCount{A,..}`, `TrieKey::PostponedReceipt{A,..}`.
3. Apply `DeleteAccountAction` for `A` (beneficiary arbitrary); assert `Account{A}`, `AccessKey{A,*}`, `ContractCode{A}`, `ContractData{A,*}` are gone, but assert the three postponed-receipt keys above are still present (proving asymmetric cleanup — the "strict superset" claim).
4. Apply `CreateAccountAction` for `A` from a distinct funder, establishing a fresh `Account{A}` with zero prior relationship to the deleted one.
5. Deliver the outstanding `DataReceipt` for the original `data_id`; assert the postponed `ActionReceipt`'s actions (e.g., `AddKeyAction`) execute successfully against the newly created `A`, verified by checking the new account now has the access key/added balance/mutated contract state dictated by the stale receipt, despite the new account owner never authorizing it.

pub fn remove_account(
