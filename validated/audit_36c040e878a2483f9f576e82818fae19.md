### Title
Unbounded-exponent `BigDecimal` parsing in HTTP JSON parameter parsing enables unauthenticated node DoS - (File: `framework/src/main/java/org/tron/core/services/http/Util.java`)

### Summary
The `feeLimit`/numeric parameter parsing path used by java-tron's public HTTP API (`getJsonLongValue`) converts a client-supplied JSON string into a `BigDecimal` via `TypeUtils.castToBigDecimal` and then immediately calls `longValueExact()` on it. `TypeUtils.castToBigDecimal` only bounds the *string length* (65535 chars) before calling `new BigDecimal(strVal)`, but places no bound on the parsed exponent. A short string such as `"1e2000000000"` (well under the 65535-char limit) produces a `BigDecimal` with `unscaledValue=1` and `scale=-2000000000`. Calling `longValueExact()`/`toBigIntegerExact()` on such a value forces the JVM to internally compute `BigInteger.TEN.pow(2000000000)`, allocating a multi-gigabyte `BigInteger` in a single call — the same "unbounded exponent → out-of-memory" bug class described in the `decimal` (Elixir) advisory (GHSA-rhv4-8758-jx7v), just realized through Java's `BigDecimal` instead of the Elixir `Decimal` library.

### Finding Description
`TypeUtils.castToBigDecimal` (common/src/main/java/org/tron/json/TypeUtils.java:150-184) is: [1](#0-0) 
which only checks `strVal.length() > 65535` before calling `new BigDecimal(strVal)` — it never bounds the magnitude of the exponent, only the raw character count of the input string. A crafted string like `"1e2000000000"` passes this check trivially (13 characters) yet encodes a scale of roughly `-2×10^9`.

This value is retrieved by `JSONObject.getBigDecimal` (common/src/main/java/org/tron/json/JSONObject.java:104-106): [2](#0-1) 

and consumed by the HTTP servlet helper `Util.getJsonLongValue`, which immediately forces materialization via `longValueExact()`: [3](#0-2) 

`BigDecimal.longValueExact()` internally calls `toBigIntegerExact()`, and for a negative scale this computes `unscaledValue.multiply(BigInteger.TEN.pow(-scale))` — i.e., it builds a `BigInteger` with on the order of `10^9` decimal digits in one allocation. This is functionally identical to the reported `decimal` library flaw: the parser itself is cheap, but any consumer that performs arithmetic/coercion on the parsed value (`add`, `round`, `to_integer` in the advisory; here `longValueExact()`/any `BigDecimal` arithmetic) explodes memory proportional to the exponent.

`Util.getJsonLongValue` is wired into public, unauthenticated HTTP endpoints that accept a `fee_limit`/numeric JSON field, e.g. `DeployContractServlet` and `TriggerSmartContractServlet`: [4](#0-3) [5](#0-4) 
These are exactly the "HTTP/gRPC/JSON-RPC query paths into Wallet" reachable by any anonymous API client per the in-scope surface for this analog.

### Impact Explanation
A single unauthenticated HTTP request to `wallet/deploycontract`, `wallet/triggersmartcontract`, or any other endpoint that reads a numeric field (e.g., `fee_limit`, `call_value`) through `Util.getJsonLongValue` can supply a scientific-notation string with a huge negative exponent (e.g. `"1e2000000000"`). The resulting `longValueExact()` call attempts to allocate a `BigInteger` of billions of digits, consuming multiple gigabytes of heap and either triggering an `OutOfMemoryError` that kills the JVM/node process or causing severe GC pressure/hang that makes the HTTP API — and potentially the whole node — unresponsive. This is a remote, unauthenticated, single-request denial of service against a production java-tron full node/API node.

### Likelihood Explanation
High. No authentication, signature, or on-chain state is required — the attacker only needs to send a normal HTTP POST to a public wallet endpoint with a crafted numeric string in a JSON body. The length check in `TypeUtils.castToBigDecimal` gives a false sense of safety since it bounds character count, not exponent magnitude, so the guard does not stop this input at all.

### Recommendation
- In `TypeUtils.castToBigDecimal` (common/src/main/java/org/tron/json/TypeUtils.java), after parsing, reject `BigDecimal` values whose `scale()` (positive or negative) exceeds a small sane bound (e.g., ±1000), before returning the value to any caller.
- Alternatively/additionally, in `Util.getJsonLongValue` (framework/src/main/java/org/tron/core/services/http/Util.java:507-513), validate `bigDecimal.scale()` / `bigDecimal.precision()` bounds before calling `longValueExact()`, or wrap the arithmetic with a bound check that rejects unscaled values requiring impractically large intermediate `BigInteger`s.
- Apply the same exponent-bound check anywhere else user-supplied JSON numeric strings are coerced to `BigDecimal` and later used in arithmetic (`castToInt`/`castToLong` fallbacks that go through `BigDecimal`).

### Proof of Concept
Send an HTTP request to a wallet API endpoint that parses a numeric field through `Util.getJsonLongValue` (e.g., `wallet/deploycontract`) with the `fee_limit` field set to a scientific-notation string with a huge exponent:
```
POST /wallet/deploycontract
Content-Type: application/json

{
  ...
  "fee_limit": "1e2000000000",
  ...
}
```
`Util.getJsonLongValue` → `JSONObject.getBigDecimal("fee_limit")` → `TypeUtils.castToBigDecimal("1e2000000000")` returns a `BigDecimal` with `scale=-2000000000` (the 65535-char length guard does not stop a 13-character input). The subsequent `bigDecimal.longValueExact()` call forces `BigInteger.TEN.pow(2000000000)`, causing an OutOfMemoryError / multi-gigabyte allocation on a single unauthenticated request.
