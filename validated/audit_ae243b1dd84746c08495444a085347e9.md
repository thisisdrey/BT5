### Title
Stream throttle check-then-act race allows momentary over-admission beyond `max_streams_per_throttling_interval` - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`throttle_stream` decides whether to admit or delay a new QUIC stream by reading `stream_counter.stream_count` and comparing it to `max_streams_per_throttling_interval`, but the function never atomically reserves a slot as part of that check — the actual counter increment happens outside this check, in the caller. Multiple concurrently-handled streams on the same connection can therefore all observe a stream count below the limit and be admitted in the same window, most severely right after `reset_throttling_params_if_needed` resets `stream_count` to 0 at an interval boundary.

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` uses a correct read-then-write double-checked lock to decide *when* to reset `stream_count` to 0 and roll `last_throttling_instant` forward — the second check inside the write-lock branch correctly prevents two threads from both performing the reset. [1](#0-0) 

However, the actual admission decision in `throttle_stream` is a separate, non-atomic check: it loads `stream_count` with `Ordering::Relaxed` and compares it to `max_streams_per_throttling_interval`; if below the limit, it does nothing (i.e., the stream is admitted) and returns without ever incrementing `stream_count` itself. [2](#0-1) 

Because the check (`load`) and the eventual increment (performed by the caller after `throttle_stream` returns, not inside this function/lock) are two separate, non-atomic operations, any number of concurrently-processed streams on the same connection can race between the check and the increment. Each one independently observes `streams_read_in_throttle_interval < max_streams_per_throttling_interval` before any of the others has recorded its admission, so none of them throttles. The race window is maximized exactly at throttling-interval boundaries: immediately after `reset_throttling_params_if_needed` zeroes `stream_count`, an attacker who opens many QUIC streams simultaneously on one connection can have all of them pass the check while the counter is still (or close to) zero, admitting a burst larger than `max_streams_per_throttling_interval` in that interval. This is a classic TOCTOU (check-then-act) gap: the limit-check and the state-mutation that should make the check meaningful are not combined into a single atomic operation (e.g., `fetch_add` + compare, or a CAS loop), and no lock guards this check/act pair against concurrent access.

### Impact Explanation
This is a QoS/rate-limit evasion: an unstaked, unprivileged attacker can obtain more admitted streams per `STREAM_THROTTLING_INTERVAL_MS` (100ms) window than `max_streams_per_throttling_interval` is meant to allow, by opening many concurrent streams on a single connection timed around interval resets. The impact is scoped and repeatable every 100ms boundary, giving sustained unfair capacity capture rather than unbounded memory/DoS, matching the "QoS evasion" bounty category explicitly listed as in-scope.

### Likelihood Explanation
The attacker only needs to open a normal QUIC connection to the TPU port and fire many uni-directional streams concurrently — no stake, keys, or validator control required. The race window is small (microseconds) but is naturally realigned every 100ms at each throttling-interval reset, making it trivially repeatable indefinitely for as long as the attacker maintains the connection, so exploitation does not require rare timing luck — it can be retried every interval.

### Recommendation
Make the check-and-admit operation atomic with respect to the counter update: reserve the slot inside `throttle_stream` itself, e.g. use `stream_count.fetch_add(1, Ordering::Relaxed)` and compare the *previous* value against `max_streams_per_throttling_interval` (or a CAS loop) so that each concurrent caller's admission decision is based on a value that reflects all prior admissions in the same interval, closing the gap between "read count" and "increment count".

### Proof of Concept
Rust concurrency test in `streamer/src/nonblocking/stream_throttle.rs`:
```rust
#[tokio::test]
async fn test_throttle_stream_race_over_admits() {
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 5u64;
    let admitted = Arc::new(AtomicU64::new(0));

    // Simulate the caller pattern: check via throttle_stream, then increment
    // (mirrors the real call site, where increment happens after throttle_stream returns).
    let mut handles = vec![];
    for _ in 0..50 {
        let stats = stats.clone();
        let counter = counter.clone();
        let admitted = admitted.clone();
        handles.push(tokio::spawn(async move {
            throttle_stream(
                &stats,
                ConnectionPeerType::Unstaked,
                "127.0.0.1:0".parse().unwrap(),
                &counter,
                max_streams,
            ).await;
            // Increment happens only after the check returns — mirrors real caller.
            counter.stream_count.fetch_add(1, Ordering::Relaxed);
            admitted.fetch_add(1, Ordering::Relaxed);
        }));
    }
    futures::future::join_all(handles).await;

    // Expect: within one interval, admitted streams should never exceed max_streams_per_throttling_interval
    // without any of them being throttled. This assertion is expected to FAIL, demonstrating the race.
    assert!(
        counter.stream_count.load(Ordering::Relaxed) <= max_streams,
        "over-admitted {} streams, limit was {}",
        counter.stream_count.load(Ordering::Relaxed),
        max_streams
    );
}
```
Expected result: because `throttle_stream`'s check and the counter increment are decoupled, many/all of the 50 concurrently-spawned tasks observe `stream_count < max_streams` before any increment lands, so the assertion fails, confirming over-admission beyond `max_streams_per_throttling_interval`.
