The reported CVE-2026-62309 concerns CoreDNS's `plugin/pkg/proxyproto` package (a separate project), where `PacketConn.ReadFrom` mishandles a PROXY v2 header with non-UDP transport, reassigns `addr` to nil after `parseProxyProtocol` fails, and then calls `addr.String()` before `ServeDNS`'s panic recovery applies. This code does not exist in `ThankGodontt/go--004`, which is the Go standard library/toolchain repository, not CoreDNS.

I searched for analogous patterns in the Go standard library's own packet-oriented networking code, since the bug class is "parse untrusted network header → nil address → dereference before recovery." The relevant `net` package implementations consistently guard against this exact failure mode:

- `UDPConn.ReadFrom` explicitly checks `if addr == nil` before returning, specifically to avoid returning `Addr(*UDPConn(nil))`: [1](#0-0) 
- `IPConn.ReadFrom` performs the same nil-check pattern: [2](#0-1) 
- `UnixConn.ReadFrom` also nil-checks `addr` before returning it: [3](#0-2) 
- The low-level `udpsock_posix.go` `readFrom` explicitly sets `addr = nil` on error rather than leaving a stale/garbage address: [4](#0-3) 

No production `golang/go` code path parses an attacker-controlled proxy-protocol-style header and then dereferences a potentially nil `Addr` in a logging/warning call prior to panic recovery, so there is no matching analog to prove reachability against.

	if !c.ok() {
		return 0, nil, syscall.EINVAL
	}

		err = &OpError{Op: "read", Net: c.fd.net, Source: c.fd.laddr, Addr: c.fd.raddr, Err: err}

		return n, nil, err
	}
	return n, addr, err
