### Title
Unbounded allocation from attacker-controlled length in `extractBytesArray`/`extractBytes32Array` used by `BatchValidateSign`/`ValidateMultiSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE describes an allocation failure DoS in `quicktime_read_info` caused by trusting a crafted length field to size an allocation. The same bug class exists in java-tron's TVM precompiled-contract helpers `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, which allocate a `byte[][]` sized directly from a caller-supplied word in the precompile calldata, before any bound check is applied.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read a length directly from the ABI-encoded input words and use it to size an array with no upper bound: [1](#0-0) 

`len` comes from `words[offset].intValueSafe()`, which converts an attacker-controlled 256-bit `DataWord` from calldata into a (safely clamped, but still attacker-chosen up to `Integer.MAX_VALUE`) `int`. `extractBytesArray` and `extractBytes32Array` then execute `new byte[len][]` before any comparison against the real size of `words`, `data`, or a maximum item count.

These helpers are invoked from the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts (TVM addresses `0x...a` and `0x...9`), which are reachable by any TVM contract call: [2](#0-1) [3](#0-2) 

The size guard (`sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE`) that would reject an oversized length is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [4](#0-3) 

When that config flag is not active (legacy/older activated-feature configuration), `extractBytesArray`/`extractBytes32Array` are called with a completely unchecked `len`, so `new byte[len][]` executes first, and the `signatures.length > MAX_SIZE` check at line 1076/1179 only runs *after* the allocation attempt has already occurred — too late to prevent the allocation from being attempted with an attacker-chosen size.

### Impact Explanation
An attacker can craft a smart-contract call to `ValidateMultiSign` (`0x...0a`) or `BatchValidateSign` (`0x...09`) with a length word set to a very large value. This forces the JVM to attempt allocating an array with millions/billions of elements (`new byte[len][]`), which can throw `OutOfMemoryError` or consume excessive heap on the node processing the transaction. Because `BatchValidateSign`/`ValidateMultiSign` execution happens inside transaction/contract execution paths reachable by any account issuing a TVM `CALL`, this can be triggered by an unprivileged transaction broadcaster or contract caller, potentially causing node instability or crash (denial of service) for full nodes/SRs executing the block, which is the same "allocation failure via crafted input causes DoS" bug class as CVE-2017-12143.

### Likelihood Explanation
Reachability requires only building calldata for the precompile and issuing a normal `CALL`/`triggerContract` transaction — no special privilege needed. The magnitude of impact depends on the runtime configuration (`allowTvmSelfdestructRestriction` on/off) and JVM heap limits; on paths where the modern guard is disabled, the length is fully attacker-controlled before allocation.

### Recommendation
Move the `MAX_SIZE` (and any general sanity/length) bound checks in `ValidateMultiSign`/`BatchValidateSign` before calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, and make `extractBytesArray`/`extractBytes32Array` themselves validate `len` against a reasonable maximum (and against the actual size of `words`) prior to allocating, independent of the `allowTvmSelfdestructRestriction` feature flag.

### Proof of Concept
Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign(...)`) where the length word encoding the `bytes[]`/`address[]` array size is set to a very large 256-bit value (e.g. `0xFFFFFFFF`), and issue a `TriggerSmartContract` transaction calling this precompile with `allowTvmSelfdestructRestriction` disabled. `words[offset].intValueSafe()` yields a huge `len`, causing `new byte[len][]` in `extractBytesArray`/`extractBytes32Array` to allocate excessively before the size guard downstream is checked, consistent with the pattern of unvalidated pre-allocation length exercised by the existing `testTip854RejectsMalformedCalldata` test only for the Osaka-guarded path: [5](#0-4) , which does not cover the legacy (non-Osaka, non-selfdestruct-restriction) code path where the unbounded allocation is reachable.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  @Test
  public void testTip854RejectsMalformedCalldata() {
    contract.setVmShouldEndInUs(System.nanoTime() / 1000 + 2_000_000);
    VMConfig.initAllowTvmOsaka(1);
    try {
      // Bucket 1: 32-aligned head + sub-word trailing bytes (r=1, r=31).
      for (int r : new int[]{1, 31}) {
        byte[] data = new byte[(5 + 6) * 32 + r];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("non-32-aligned len=" + data.length, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 2: fewer than the static head's 5 words.
      for (int bytes : new int[]{0, 32, 64, 96, 128}) {
        Pair<Boolean, byte[]> ret = contract.execute(new byte[bytes]);
        Assert.assertFalse("len=" + bytes + " < 5 words", ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 3: 32-aligned but tail not a multiple of I=6 words (k = 1..5).

        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("aligned bad-tail k=" + k, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Null calldata: explicit spec clause.
      Pair<Boolean, byte[]> ret = contract.execute(null);
      Assert.assertFalse("null calldata", ret.getLeft());
