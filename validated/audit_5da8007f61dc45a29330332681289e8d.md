Audit Report

## Title
Silent tip loss when BridgeHub `add_tip` fails after asset is already burned on AssetHub - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`snowbridge-pallet-system-frontend::add_tip` unconditionally withdraws and burns the user's tip asset via `swap_fee_asset_and_burn` before any confirmation that the tip will actually be applied on BridgeHub, then dispatches a `Transact` XCM to `snowbridge-pallet-system-v2::add_tip`. That extrinsic swallows the underlying `AddTipError` (e.g. `UnknownMessage`, `NonceConsumed`) from the inbound/outbound queue and always returns `Ok(())`, permanently diverting already-burned funds into an unrecoverable `LostTips` counter with no consumer anywhere in the codebase.

## Finding Description
On AssetHub, `Pallet::add_tip` calls `Self::swap_fee_asset_and_burn(who.clone().into(), asset)?`, which either swaps the tip asset for Ether via `T::Swap::swap_exact_tokens_for_tokens` or burns it directly via `burn_for_teleport::<T::AssetTransactor>` [1](#0-0) . This debits the user's real balance immediately, unconditionally, and irreversibly (see `swap_fee_asset_and_burn` and `swap_and_burn`) [2](#0-1) [3](#0-2) .

The resulting `ether_gained` is packaged into an `EthereumSystemCall::AddTip { sender, message_id, amount }` sent via `UnpaidExecution`/`Transact` to BridgeHub [4](#0-3) .

On BridgeHub, `snowbridge_pallet_system_v2::Pallet::add_tip` forwards to the queue's `AddTip::add_tip(nonce, amount)`, but if this fails, the function does not propagate the error — it records the amount into `LostTips::<T>` and still returns `Ok(())`: [5](#0-4) .

The outbound queue's `AddTip` implementation confirms the failure mode: if `PendingOrders::<T>::get(nonce)` is `None` (e.g., already removed by `submit_delivery_receipt`), it returns `Err(AddTipError::UnknownMessage)` [6](#0-5) . The `AddTipError` enum defines `NonceConsumed`, `UnknownMessage`, and `AmountZero` as the possible failure modes [7](#0-6) .

The `LostTips` storage map's own doc comment concedes there is no recovery mechanism yet ("Capturing the lost tips here supports implementing a recovery method in the future") [8](#0-7) . A codebase-wide search confirms `LostTips` is only ever written to (in `add_tip`) and referenced in tests — there is no extrinsic, hook, or XCM callback anywhere that reads it and refunds or re-credits the user.

## Impact Explanation
Because `submit_delivery_receipt` removes `PendingOrders[nonce]` as part of normal relayer operation (and the inbound queue similarly advances its nonce state upon message processing), there is an inherent, non-adversarial race between a user's `add_tip` call on AssetHub and the relayer's delivery-receipt submission or message processing on BridgeHub. If the tip's `Transact` execution reaches BridgeHub after the order/nonce is already consumed, the user's Ether — already burned on AssetHub — is irrecoverably lost, with no relayer reward increase and no refund path. This matches the "permanent user-fund lock"/funds-loss impact category, since the corrupted value is the user's swapped/burned Ether balance, which is destroyed with no corresponding credit anywhere in state.

## Likelihood Explanation
No privileged actor or malicious behavior is required. Any signed AssetHub account can call `add_tip`, and the failure condition (nonce/order already consumed) is a normal outcome of the message-relaying lifecycle that the tipping feature is explicitly designed to interact with, making the vulnerable path readily and repeatably reachable in ordinary operation.

## Recommendation
Either (1) make `system-v2::add_tip` propagate the queue's `AddTipError` so the `Transact` fails, combined with restructuring the AssetHub-side flow to defer or reverse the burn until BridgeHub confirms acceptance (e.g., two-phase reserve/commit or an XCM response callback prior to burning), or (2) implement a real recovery mechanism for `LostTips` — an extrinsic allowing the recorded sender to reclaim the lost amount (in Ether/PNA form) rather than leaving it as a permanently stranded, unconsumed counter.

## Proof of Concept
1. Relayer calls `submit_delivery_receipt` for outbound nonce `N`, removing `PendingOrders[N]` at `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:475`.
2. Concurrently or shortly after, a user on AssetHub calls `EthereumSystemFrontend::add_tip(origin, MessageId::Outbound(N), asset)`.
3. `swap_fee_asset_and_burn` executes, burning/swapping the user's asset for Ether immediately (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:372-404`).
4. The `Transact` reaches BridgeHub; `snowbridge_pallet_system_v2::add_tip` calls `OutboundQueue::add_tip(N, amount)`, which returns `Err(AddTipError::UnknownMessage)` since the order was removed.
5. `system-v2::add_tip` swallows this error, credits `amount` to `LostTips::<T>::get(sender)`, emits `TipProcessed { success: false }`, and returns `Ok(())` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:251-281`).
6. The user's burned Ether is permanently gone; no code path anywhere reads or consumes `LostTips` to refund it.

			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether

			let who = T::AccountIdConverter::convert_location(&origin)

				true,
			)?;

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
