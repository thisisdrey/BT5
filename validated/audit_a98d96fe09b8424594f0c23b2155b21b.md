### Title
Fixed-window stream throttling in `throttle_stream`/`ConnectionStreamCounter::reset_throttling_params_if_needed` allows a boundary-straddling burst of up to ~2x `max_streams_per_throttling_interval` streams per connection - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (tumbling) window rate limiter keyed on `last_throttling_instant`, rather than a sliding window. An unprivileged remote client controlling the timing of its own stream opens on a single QUIC connection can send up to `max_streams_per_throttling_interval` streams just before a window reset and another full quota immediately after the reset, resulting in roughly double the intended per-interval stream budget within a short span straddling the `STREAM_THROTTLING_INTERVAL` boundary.

### Finding Description
`reset_throttling_params_if_needed` only resets `stream_count` to `0` when `Instant::now().duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL`, and it stores the new reset instant as `Instant::now()` at that moment [1](#0-0) . `throttle_stream` then compares the current `stream_count` against `max_streams_per_throttling_interval` and only sleeps the caller if the count in the *current* fixed window has already reached the cap [2](#0-1) .

Because the window boundary is anchored to `last_throttling_instant` (effectively connection creation time plus subsequent reset events) rather than being evaluated as a rolling/sliding window over the last `STREAM_THROTTLING_INTERVAL`, an attacker who knows or can infer roughly when the window will roll over can:
1. Send up to `max_streams_per_throttling_interval - 1` streams at the very end of window N (right before the boundary), none of which get throttled since `stream_count` has not yet reached the cap.
2. Immediately after the boundary crosses (window N+1 begins, `stream_count` reset to 0), send another `max_streams_per_throttling_interval` streams, again none of which get throttled.

Within a short interval straddling the reset boundary (bounded by network RTT/scheduling jitter), the connection can push close to `2 * max_streams_per_throttling_interval` streams to the validator, exceeding the intended bounded-per-connection-stream-rate invariant that a sliding `STREAM_THROTTLING_INTERVAL` window would enforce.

### Impact Explanation
This is a per-connection QoS/rate-limit evasion: an unstaked/unprivileged attacker can transiently double the number of streams (and therefore transactions/packets) it pushes into the QUIC ingestion pipeline relative to the intended `max_streams_per_throttling_interval` budget, consuming extra receive-thread and packet-batch capacity that should be evenly shared. This matches the described bounty category of unfairly capturing per-connection/stream QoS limits and starving legitimate senders. The impact is bounded and self-correcting, however: only one doubling occurs per boundary crossing (it does not compound across multiple windows), and it is still constrained by other independent controls, such as `StakedStreamLoadEMA`'s stake-weighted capacity function [3](#0-2) , per-IP/connection count limits, and QUIC's own max concurrent stream transport parameters. So the practical effect is a bounded, transient burst rather than an unbounded resource exhaustion.

### Likelihood Explanation
Exploitability requires only an unprivileged client that can open a QUIC connection to the leader's TPU port and time its stream opens relative to wall-clock, which is fully within reach of a remote unstaked attacker (no special stake, keys, or config needed). The precise timing of `last_throttling_instant` per connection is not exposed directly to the client, but it can be inferred by observing when previously-throttled streams stop being delayed, making the attack feasible with modest probing, and repeatable once per boundary crossing (every 100ms) for the life of the connection.

### Recommendation
Replace the fixed/tumbling window counter in `ConnectionStreamCounter` with a true sliding-window or token-bucket algorithm (e.g., track timestamps of recent stream opens and evict those older than `STREAM_THROTTLING_INTERVAL`, or use a leaky/token bucket with continuous refill) so that the invariant "no more than `max_streams_per_throttling_interval` streams accepted in any `STREAM_THROTTLING_INTERVAL`-length window" holds for all sliding windows, not just windows aligned to the last reset instant.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (new test)
#[tokio::test(start_paused = true)]
async fn test_boundary_straddle_doubles_accepted_streams() {
    use std::sync::atomic::Ordering;

    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 100u64;

    // Simulate max_streams-1 stream opens right before the interval boundary.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Just before STREAM_THROTTLING_INTERVAL elapses, no reset should occur.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL - Duration::from_millis(1)).await;
    let before_reset_count = counter.stream_count.load(Ordering::Relaxed);
    assert_eq!(before_reset_count, max_streams);

    // Cross the boundary.
    tokio::time::advance(Duration::from_millis(2)).await;
    throttle_stream(
        &stats,
        ConnectionPeerType::Unstaked,
        "127.0.0.1:0".parse().unwrap(),
        &counter,
        max_streams,
    ).await; // triggers reset_throttling_params_if_needed -> stream_count reset to 0

    // Immediately after reset, attacker sends another full quota.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }

    // Total accepted streams within a STREAM_THROTTLING_INTERVAL-wide sliding
    // window centered on the boundary is ~2x max_streams, violating the
    // intended per-connection bound.
    let total_in_sliding_window = before_reset_count + counter.stream_count.load(Ordering::Relaxed);
    assert!(
        total_in_sliding_window > max_streams,
        "expected sliding-window violation, got {total_in_sliding_window}"
    );
}
```
Expected result: the assertion demonstrates that the sliding-window invariant (`accepted streams in any STREAM_THROTTLING_INTERVAL window <= max_streams_per_throttling_interval`) is violated by the fixed-window implementation, confirming the boundary-straddling burst.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
