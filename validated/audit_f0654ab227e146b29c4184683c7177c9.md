Audit Report

## Title
Hard-coded ERC20 transfer weight limit in `ERC20Transactor` permanently fails and locks funds for ERC20 tokens whose `transfer` exceeds the fixed gas budget - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` execute an ERC20 contract's `transfer` via `pallet_revive::bare_call` using a single, globally fixed `WeightLimit` (`ERC20TransferGasLimit`), with no per-token override. Because `ERC20Matcher` matches any `AccountKey20` location without any registration/permission gate, any deployed contract can participate in this flow, and if its `transfer` legitimately (or deliberately) exceeds the fixed weight budget, deposits fail deterministically and — since `check_in`/`check_out` are `Unimplemented` and reclaiming a trapped asset re-runs the identical under-provisioned call — the token balance already moved into the shared `TransfersCheckingAccount` becomes permanently stuck.

## Finding Description
`ERC20Transactor` is wired into `AssetTransactors` on Asset Hub Westend and handles XCM `WithdrawAsset`/`DepositAsset` for any asset matched by `ERC20Matcher` [1](#0-0) . `ERC20Matcher` is purely a location-pattern matcher (`AccountKey20` under `IsLocalAccountKey20`) with no asset-registry or governance gate, unlike the Snowbridge foreign-token flow, which requires an explicit `register_token` call [2](#0-1) . This means any contract deployed via pallet-revive's public `instantiate`/`call` extrinsics can be referenced immediately as an XCM-transactable asset.

Both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke `IERC20::transfer` through `bare_call` with a single fixed `weight_limit = WeightLimit::get()` [3](#0-2) [4](#0-3) , bound to `ERC20TransferGasLimit` on Asset Hub Westend [5](#0-4) . On failure, both functions hit the same fallback branch, whose own comment states there is no way for a user to remedy the failure via the XCM itself [6](#0-5) .

`check_in`/`check_out` both explicitly return/do `Unimplemented`, so there is no teleport-style reclamation path [7](#0-6) . Any attempt to reclaim a trapped `Erc20Credit` asset re-invokes `deposit_asset_with_surplus` with the identical fixed weight limit, so if the transfer genuinely requires more weight, every retry fails identically.

## Impact Explanation
`TransfersCheckingAccount` is a single shared account holding the pooled real ERC20 balance for all users of a given token contract that has been withdrawn via `withdraw_asset_with_surplus` [8](#0-7) . If `deposit_asset_with_surplus` for that token contract ever fails due to insufficient weight (whether from a legitimately heavier `transfer` implementation or one deliberately crafted to exceed the budget only when invoked from the checking account), the abstract `Erc20Credit` held in `AssetsInHolding` is trapped by the XCM executor while the real balance remains locked in `TransfersCheckingAccount`, with no working exit path since reclaiming re-executes the same call under the same fixed limit. This satisfies the "permanent user-fund lock" impact category, and because `ERC20Matcher` requires no registration, the exposure is not limited to a curated/vetted set of tokens.

## Likelihood Explanation
Reachability requires only unprivileged, public actions: deploying an ERC20 contract via pallet-revive and initiating an ordinary XCM asset transfer through the registered `ERC20Transactor` path — no governance or registry step is needed given `ERC20Matcher`'s permissive location matching. The likelihood for accidental triggering by a legitimate but unusual ERC20 (fee-on-transfer, rebasing, hooked, proxy/delegatecall-heavy) depends on how tight `ERC20TransferGasLimit` actually is relative to real-world transfer costs; the report does not include a concrete measurement or benchmark proving the current constant (500_000_000_000 ref-time / 10MiB proof) is insufficient for any specific real ERC20 pattern — this part of the claim is plausible by analogy to the Snowbridge `ConstantGasMeter` history but not directly demonstrated in this codebase. However, an adversarial contract deployer can trivially and deterministically engineer a contract whose `transfer` consumes more weight specifically when called by the checking-account address, guaranteeing the failure and lock for any counterparty who moves that token through XCM.

## Recommendation
Replace the single hardcoded `WeightLimit` with a per-asset configurable weight/gas budget determined at first use or asset registration, or perform a dry-run/weight probe before committing to a two-step withdraw/deposit sequence. Ensure failure paths do not leave real ERC20 balances stranded in `TransfersCheckingAccount` with no viable exit — e.g., support a recovery/refund mechanism independent of the same fixed-weight `transfer` call, or make `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` atomic/reversible on failure.

## Proof of Concept
1. Deploy an ERC20 contract via pallet-revive whose `transfer` function consumes materially more weight when called from a specific address (e.g., check `msg.sender == TransfersCheckingAccount` and perform extra storage writes/loops in that branch), while consuming normal weight for other callers.
2. This contract is immediately usable as an XCM asset via `ERC20Matcher` without any registration step [1](#0-0) .
3. A user submits an XCM `WithdrawAsset`/`DepositAsset` moving this token; `withdraw_asset_with_surplus` succeeds, moving the real balance into `TransfersCheckingAccount` [9](#0-8) .
4. `deposit_asset_with_surplus` calls `transfer` from `TransfersCheckingAccount`, which now exceeds `weight_limit`, and hits the `FailedToTransactAsset("ERC20 contract execution errored")` branch [6](#0-5) .
5. Any subsequent `ClaimAsset`/reclaim attempt re-executes step 4 identically and fails identically, leaving the token balance permanently stuck in `TransfersCheckingAccount`.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
