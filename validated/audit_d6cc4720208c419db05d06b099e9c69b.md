### Title
FIFO (oldest-first) eviction in `EvictingSender` lets cheap valid transactions displace higher-fee transactions from the sigverify→banking-stage channel - (File: core/src/sigverify.rs, streamer/src/evicting_sender.rs)

### Summary
The bounded channel between sigverify workers and the banking stage (`SigVerifyWorkerState::banking_stage_sender`) uses `EvictingSender`, which evicts the *oldest* queued batch on overflow rather than the lowest-priority one. An unprivileged attacker who floods the TPU with a sustained stream of signature-valid but arbitrarily-low-fee transactions can keep this channel saturated so that legitimate higher-fee batches sitting in the queue (waiting for the banking stage to drain them) get evicted purely because they arrived earlier, not because they are lower-value.

### Finding Description
`SigVerifyWorkerPool::run_transaction_task` sends each verified batch to the banking stage via `state.banking_stage_sender.send(banking_packet_batch.clone())` at [1](#0-0)  only after signature verification and (optionally) a priority-floor pre-filter, but with no fee/priority consideration for the send/eviction itself. The underlying `TracedSender::send` forwards to `EvictingSender::try_send` [2](#0-1) , whose implementation evicts strictly by insertion order:

```
TrySendError::Full(msg) => match self.receiver.try_recv() {
    Ok(older) => { ... Err(TrySendError::Full(older)) }
``` [3](#0-2) 

`try_recv` on a crossbeam bounded channel always returns the oldest enqueued item — there is no comparison of fee/priority between `older` and the new `msg`. The channel (`NON_VOTE_CHANNEL_CAPACITY = 1024 * 16`, defined at [4](#0-3) ) sits between sigverify output and the banking-stage scheduler's own priority queue; batches queued here have not yet entered the scheduler's priority-ordered structure, so nothing downstream re-protects them once they're evicted here.

The only fee-aware defense in this path is the `priority_floor` check in `run_transaction_task`, applied via `apply_priority_floor_to_batch` before sigverify [5](#0-4) . That mechanism only rejects *newly arriving* packets whose priority is at-or-below the scheduler's last-published queue-min floor; it does nothing to protect a legitimate batch that is already sitting in the `banking_stage_sender` channel waiting to be drained, and the floor value necessarily lags real-time channel occupancy. Sigverify itself performs no fee check at all — only a valid signature is required (`sigverify::ed25519_verify_serial`) — so an attacker with ordinary, unstaked funded keypairs can generate a continuous stream of cheap-but-valid transactions (varying nonce/memo/blockhash to avoid the `Deduper`) fast enough to keep the channel full. Whenever the attacker's batch arrives while the channel is at capacity, it evicts whatever batch is oldest in the queue — which may be a legitimate, much higher-fee transaction still waiting for the banking stage to consume it — via `eviction_drops` accounting at [6](#0-5) .

### Impact Explanation
This allows grossly underpriced attacker work (near-zero fee, signature-only cost) to selectively discard already-verified, higher-value legitimate transactions from the leader's ingress pipeline purely based on arrival-order collision with a full channel, rather than fee/priority. This is a QoS-evasion / fee-market-bypass class issue: legitimate high-fee traffic can be starved of block inclusion by cheap spam without the attacker ever paying commensurate fees, degrading the leader's effective throughput and fee-market guarantees below intended cost, matching the "vastly exceeds fees collected" bounty scope for the sigverify/dedup/scheduling/buffering ingress path.

### Likelihood Explanation
Feasible for a fully unprivileged remote client: no stake, no special config, and no exploitation of a memory-safety bug — only sustained submission of valid, low-fee transactions timed against normal cluster/network jitter to coincide with channel-full windows. It requires precise timing (attacker traffic overlapping the exact moments the channel is at capacity and a target high-fee batch is the oldest entry) and sustained throughput exceeding banking-stage consumption capacity, which is plausible during any period of high TPS load or under an attacker-induced sustained flood in the non-vote channel (capacity 16384 batches). Repeatable and inexpensive to sustain since fees for the spam do not need to be collected/executed for the eviction to occur — sigverify does not check fee/balance, only the signature.

### Recommendation
Change `EvictingSender`'s eviction policy so that it never evicts an entry whose fee/priority is higher than the incoming message when the channel is full; e.g., inspect and compare priority before evicting (peek instead of unconditional `try_recv`), or maintain a min-priority-ordered structure so the *lowest*-priority buffered item is evicted rather than the oldest. Alternatively, apply the scheduler's `SchedulerPriorityFloor` (or an equivalent per-send priority comparison) directly at the `EvictingSender::try_send` boundary rather than only pre-sigverify, so eviction is priority-consistent end-to-end.

### Proof of Concept
```rust
// streamer/src/evicting_sender.rs (new unit test)
#[test]
fn test_eviction_is_not_priority_consistent() {
    // Priority-tagged payload wrapper
    #[derive(Clone)]
    struct PrioritizedMsg { priority: u64, id: u32 }

    let (sender, _receiver) = EvictingSender::<PrioritizedMsg>::new_bounded(2);

    // Fill channel with legitimate high-priority (high-fee) messages.
    sender.try_send(PrioritizedMsg { priority: 1_000_000, id: 1 }).unwrap();
    sender.try_send(PrioritizedMsg { priority: 1_000_000, id: 2 }).unwrap();

    // Attacker sends a low-priority (near-zero fee) message; channel is full.
    let evicted = sender.try_send(PrioritizedMsg { priority: 1, id: 3 });

    // Current (buggy) behavior: evicts the OLDEST message (id: 1, priority 1_000_000),
    // even though the attacker's message (priority 1) is far lower priority.
    match evicted {
        Err(crossbeam_channel::TrySendError::Full(evicted_msg)) => {
            assert!(
                evicted_msg.priority >= 1, // attacker priority
                "evicted message must never be higher priority than incoming message; \
                 evicted id={} priority={}, incoming priority=1",
                evicted_msg.id, evicted_msg.priority
            );
            // This assertion FAILS today: evicted_msg has priority 1_000_000 (id 1),
            // demonstrating that a cheap attacker message displaced a high-fee legitimate one.
        }
        other => panic!("expected Full eviction, got {other:?}"),
    }
}
```
Expected: the assertion fails against current `EvictingSender::try_send`, proving that the oldest (not lowest-priority) entry is evicted, confirming the vulnerability. A fixed implementation should make this test pass by refusing to evict entries with priority higher than the incoming message (or by evicting the lowest-priority entry instead of the oldest).

    fn try_send(&self, msg: T) -> std::result::Result<(), TrySendError<T>> {
        let Err(e) = self.sender.try_send(msg) else {
            return Ok(());
        };

        match e {
            // Prefer newer messages over older messages.
            TrySendError::Full(msg) => match self.receiver.try_recv() {
                Ok(older) => {
                    // Attempt to requeue the newer message.
                    // NB: if multiple senders are used, and another sender is faster than us to send() after we've popped `older`,
                    // our try_send() will fail with Full(msg), in which case we drop the new message.
                    self.sender.try_send(msg)?;
                    // Propagate the error _with the older message_.
                    Err(TrySendError::Full(older))
                }
                // Unlikely race condition -- it was just indicated that the channel is full.
                // Attempt to requeue the message.
                Err(TryRecvError::Empty) => self.sender.try_send(msg),
                // Unreachable in practice since we maintain a reference to both the sender and receiver.
                Err(TryRecvError::Disconnected) => unreachable!(),
            },
            // Unreachable in practice since we maintain a reference to both the sender and receiver.
            TrySendError::Disconnected(_) => unreachable!(),
        }
    }
