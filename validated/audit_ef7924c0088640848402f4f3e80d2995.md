### Title
Handshake replay with spoofed source address triggers roam of established tunnel via `SetRemoteIfPreferred` - ([File: handshake_manager.go])

### Finding Description
`HandshakeManager.HandleIncoming` routes any inbound packet with `h.MessageCounter == 1` and `h.RemoteIndex == 0` into `beginHandshake`, regardless of whether a tunnel for that peer already exists [1](#0-0) . `beginHandshake` builds a fresh responder `handshake.Machine`, feeds it the raw packet, and — because a byte-for-byte replay of a previously valid stage-0 message decrypts deterministically the same way — successfully re-derives the same `RemoteCert`/result and calls `hm.CheckAndComplete` [2](#0-1) .

`CheckAndComplete` looks up any existing hostinfo for the same vpn address and, if the new packet's stored `HandshakePacket[handshakePacketStage0]` bytes exactly match a previously seen packet, returns `ErrAlreadySeen` with the existing (established) hostinfo — this check is purely a `bytes.Equal` comparison, with no association to the address the original packet came from [3](#0-2) .

`handleCheckAndCompleteError`'s `ErrAlreadySeen` branch then calls `existing.SetRemoteIfPreferred(f.hostMap, via)`, where `via` carries the UDP source address of the just-received (replayed) packet, not the address that produced the original packet [4](#0-3) . If that spoofed address falls within `preferredRanges`, the established `HostInfo.remote` is updated to point at the attacker-chosen address (this repo's `hostmap.go` content for `SetRemoteIfPreferred`/`SetRemote` could not be retrieved via the index in this session, so its exact preferred-range gating logic is not directly confirmed here, but its use and naming in `handshake_manager.go` and `connection_state.go` matches this behavior).

The root cause is that "already seen" is determined solely by packet-content equality, not by any cryptographic binding to the sender's network address; an attacker who has captured one legitimate stage-0 packet (e.g. via passive observation, since it is UDP and unencrypted at the transport/address layer) can replay it from a spoofed source and cause a roam decision without ever proving ownership of a valid session or address.

### Impact Explanation
This does not defeat the Noise handshake crypto, decrypt traffic, or forge a new authenticated session — the attacker has no session keys, so no data-plane traffic can be exchanged from the spoofed address. The concrete impact is remote-state poisoning of an already-established tunnel: `hostinfo.remote` can be redirected to an attacker-chosen address (constrained to `preferredRanges`), causing the local node's traffic for that peer to attempt delivery to the wrong destination until legitimate traffic (or a fresh handshake) restores it, effectively black-holing/disrupting the tunnel — a localized denial-of-service / traffic-misdirection condition, not authentication or confidentiality bypass.

### Likelihood Explanation
Exploitability requires: (1) the attacker to have captured an exact copy of a legitimate stage-0 handshake packet (via passive network observation, not decryption), (2) the ability to spoof/inject a UDP packet with an arbitrary source address reaching the victim's listener, and (3) that spoofed address falling inside the victim's configured `preferredRanges` (commonly a private/underlay CIDR). These are non-trivial but realistic preconditions for an on-path or same-broadcast-domain attacker; no CA key, credential, or privileged access is required, consistent with the rules' scope of "attacker-sent UDP packets ... spoofed source addresses."

### Recommendation
Do not let `ErrAlreadySeen` alone authorize a remote-address change. Either (a) drop the roam entirely for `ErrAlreadySeen` and rely only on `sendHandshakeResponse` retransmission, or (b) require additional proof that the new source can complete a fresh round trip (e.g., only roam after a successful `header.Test`/keepalive response is *received back* from the new address, rather than merely sending one speculatively) before mutating `hostinfo.remote`.

### Proof of Concept
Integration test plan:
1. Establish a real tunnel between two simulated nodes A and B; capture the exact stage-0 packet bytes A→B on the wire.
2. After the tunnel is fully established (`hostinfo.remote == A`'s real address), have a third party replay the identical stage-0 bytes to B's listener with a spoofed source `netip.AddrPort` C that lies inside B's `preferredRanges`.
3. Drive the packet through `HandshakeManager.HandleIncoming` → `beginHandshake` → `CheckAndComplete` (expect `ErrAlreadySeen`) → `handleCheckAndCompleteError`.
4. Assert that `existing.remote` (the hostinfo for A) is unexpectedly updated to `C`, and that no cryptographic exchange with `C` occurred (no valid session bound to `C`), demonstrating the roam happened purely off packet-content replay rather than any freshly-verified session proof from `C`.
