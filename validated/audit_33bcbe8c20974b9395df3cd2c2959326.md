### Title
Liquidation Avoidance via `transfer_to_new_account`/`transfer_to_new_account_pda` Lacking a Health/Liquidatability Check - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
Marginfi's account-migration instructions (`transfer_to_new_account` and `transfer_to_new_account_pda`) let an account's current `authority` move an entire position (all balances, flags, etc.) to a brand-new `MarginfiAccount` under an arbitrary, unchecked `new_authority`, at any time, with no check on the account's health/liquidatability. This mirrors the Gearbox v2.0 issue where `transferAccountOwnership()` could be front-run against `liquidateCreditAccount()` because liquidation targeted the borrower rather than an immutable account identity.

### Finding Description
`transfer_to_new_account` validates only a narrow set of guards before moving `lending_account`, flags, and indexer state to a freshly-initialized account and disabling the old one: [1](#0-0) 

None of these checks reference account health or liquidatability — only `ACCOUNT_IN_FLASHLOAN`, `ACCOUNT_IN_RECEIVERSHIP`, `ACCOUNT_IN_ORDER_EXECUTION`, `active_orders == 0`, and "not already migrated" are enforced. The `TransferToNewAccount` account constraints likewise only check that the group isn't paused, that the account isn't frozen for this authority, and that the caller is the authorized signer — never health: [2](#0-1) 

Critically, `new_authority` is completely unchecked (`/// CHECK: WARN: New authority is completely unchecked`): [3](#0-2) 

Compare this to the atomic liquidation path `lending_account_liquidate`, which operates against a *specific* `liquidatee_marginfi_account` pubkey and a specific `liab_bank` position, looking up the exact balance entry by bank key: [4](#0-3) 

If a user's account becomes liquidatable (maintenance health < 0), and a liquidator submits `lending_account_liquidate` referencing the old account address, the borrower can front-run it with `transfer_to_new_account`/`transfer_to_new_account_pda`. This zeroes out the old account's `lending_account` (moving it wholesale to a new account/address) and sets `ACCOUNT_DISABLED`: [5](#0-4) 

The pending liquidation transaction, still pointing at the old account, will then fail (`LendingAccountBalanceNotFound` since the target liability balance is gone, or the empty-account path would report the account healthy) — exactly analogous to the Gearbox bug where `liquidateCreditAccount()` failed after ownership/identity changed underneath it. The documentation confirms liquidation eligibility is a purely state-based property (`Unhealthy` → `Is account frozen?` → `Is signer == authority?`) with no special-case blocking transfers of unhealthy accounts: [6](#0-5) [7](#0-6) 

Unlike the Gearbox case, the transfer moves the debt and collateral together (health ratio nominally preserved at the instant of transfer), so this isn't an instantaneous asset-drain. However it still constitutes a functional liquidation-avoidance/DoS: the liquidator's specific in-flight transaction is invalidated and must be rediscovered against the new (attacker-chosen) account/authority, which can be repeated indefinitely as prices continue to move against the position — allowing bad debt to accumulate beyond what collateral/insurance can cover, ultimately socialized onto lenders via bankruptcy handling. It also allows sending the disabled position's replacement to an authority the attacker doesn't even control (since `new_authority` is unchecked), potentially permanently locking the position from any further liquidator interaction if the new authority can never sign further transactions (though the position remains liquidatable by anyone able to reference the new account key once discovered).

### Impact Explanation
This enables liquidation avoidance/delay for an already-unhealthy account, analogous to the reported Gearbox class: front-running a targeted liquidation call and shifting the account's identity, forcing liquidators to restart discovery while the position (and market prices) can continue to move unfavorably. Repeated abuse (a "shell game" of hopping to new accounts each time a liquidation attempt appears in the mempool/pending queue) can grow bad debt beyond what a single/partial liquidation would have captured, and that shortfall is ultimately borne by lenders/insurance fund via `HandleBankruptcy`. This is an unauthorized-state-change / insolvency-risk class issue reachable by any unprivileged, already-unhealthy account owner — no admin privilege required.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an account to actually be in an unhealthy/liquidatable state, and (b) the attacker to detect and front-run a specific liquidation transaction (feasible on low-fee/fast/permissionless mempools or via priority fees), similar to the conditions described in the original Gearbox report. The instruction itself (`transfer_to_new_account`) is permissionless for the account authority, requires only a flat SOL fee, and has no cooldown or health gate, so exploitation is technically straightforward once the precondition (unhealthy + visible pending liquidation) is met.

### Recommendation
Add a liquidatability/health check to `transfer_to_new_account` and `transfer_to_new_account_pda` (mirroring `check_pre_liquidation_condition_and_get_account_health`) and reject the transfer if the account's maintenance health is below zero, analogous to Gearbox's fix of reverting `transferAccountOwnership()` for accounts with health factor < 0. Alternatively/additionally, require that `liquidatee_marginfi_account`-style checks resolve to the *current* account (post any migration) via `migrated_to` chase-through, so liquidators can always follow migrations to the account currently holding the debt, closing the front-running window entirely.

### Proof of Concept
1. Attacker's `MarginfiAccount` A drops below maintenance health (liquidatable) due to price movement.
2. A liquidator submits `lending_account_liquidate` targeting account A's specific `liab_bank` balance (see check at `programs/marginfi/src/state/marginfi_account.rs:916-932`).
3. Attacker observes the pending liquidation transaction (mempool/priority) and immediately submits `transfer_to_new_account` (or `_pda`), which only checks flashloan/receivership/order-execution/active-orders/already-migrated flags (`transfer_account.rs:61-89`) — no health check — and moves all balances to new account B under an attacker-chosen `new_authority` (unchecked, `transfer_account.rs:158-159`), while disabling and zeroing account A (`transfer_account.rs:39-49`).
4. The liquidator's transaction against account A now fails (`LendingAccountBalanceNotFound`), forcing rediscovery of account B.
5. Attacker repeats steps 1–4 each time a new liquidation attempt is detected, delaying resolution of an underwater position while the market continues to move against it, increasing eventual bad debt.

## Authorization Logic

When a user operation is attempted, the protocol checks authorization in this order:

1. **KilledByBankruptcy**: If the bank is killed, the operation is blocked regardless of who calls it.
2. **Receivership**: If the account is in receivership and the operation allows it, any signer is
   authorized.
3. **Frozen**: If the account is frozen, only the group admin is authorized.
4. **Normal**: The signer must match the account's `authority`.

```
Is account in receivership? ──Yes──> Any signer OK (for allowed operations)
         │
         No
         │
Is account frozen? ──Yes──> Only group admin OK
         │
         No
         │
Is signer == authority? ──Yes──> OK
         │
         No
         │
    Unauthorized
```
