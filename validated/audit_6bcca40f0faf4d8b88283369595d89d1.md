### Title
Unprivileged attacker can exhaust `SyntheticToken` bridged-supply caps to permanently (until governor intervention) block all bridging for a synth — (File: `contracts/SyntheticToken.sol`)

### Summary
`SyntheticToken` enforces two global, cumulative bridging caps — `maxBridgedInSupply` and `maxBridgedOutSupply` — as net counters (`totalBridgedIn` / `totalBridgedOut`). Any EOA can unilaterally drive either counter to its cap using public `ProxyOFT.sendFrom` calls with their own legitimately obtained synths. Once a cap is reached, every subsequent bridge mint/burn for that synth reverts with `SurpassMaxBridgingSupply`, blocking all users' bridge transfers (and any pending cross-chain messages that mint on this chain) until the governor raises the cap — exactly the "shared global limit manipulated to grief users until owner intervenes" bug class.

### Finding Description
In `SyntheticToken._mint`, when the caller is the `proxyOFT` (i.e., a LayerZero bridge-in), the contract does:

```solidity
totalBridgedIn += amount_;
if (bridgedInSupply() > maxBridgedInSupply) revert SurpassMaxBridgingSupply();
```

and symmetrically in `_burn` for bridge-outs:

```solidity
totalBridgedOut += amount_;
if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
```

`bridgedInSupply() = max(totalBridgedIn - totalBridgedOut, 0)` and `bridgedOutSupply() = max(totalBridgedOut - totalBridgedIn, 0)` (lines 160–180).

Attack paths (no privileged role needed):

1. **Bridged-out cap exhaustion (direct, single chain).** Attacker obtains msUSD/msETH (mint via `DebtToken.issue`/`Pool`, or buy on a DEX) and repeatedly calls `ProxyOFT.sendFrom(...)` to a supported destination. Each call burns on source and increases `totalBridgedOut`. Once `bridgedOutSupply() == maxBridgedOutSupply`, every subsequent `sendFrom` for that synth reverts — no other user can bridge out. Attacker's funds sit on the destination chain (recoverable by selling there), but only a governor `updateMaxBridgedOutSupply` call or a bridge-in can unblock the cap.

2. **Bridged-in cap exhaustion (griefs in-flight transfers).** Attacker bridges their own synths *into* this chain, raising `totalBridgedIn` until `bridgedInSupply()` hits `maxBridgedInSupply`. All subsequent inbound LayerZero mints for that synth revert inside `nonblockingLzReceive`, so other users' in-flight `sendFrom` deliveries are cached as failed messages and their funds remain burned on the source chain until retry succeeds — which requires the governor to raise the cap or someone to bridge out. This is a temporary freeze of *other users'* funds, not just a feature block.

Nothing prevents this: `sendFrom` is public and only checks `SenderIsNotTheOwner`, `isBridgingActive`, and the destination-chain allowlist; the cap check is the only gate, and raising `totalBridgedIn`/`totalBridgedOut` is exactly what a normal bridge transfer does — there is no per-user or per-day sub-limit, so one attacker consumes the entire shared budget.

### Impact Explanation
Temporary freezing of funds / DoS of the bridging feature for a synthetic asset. Path 2 freezes in-flight bridged funds of unrelated users (their messages fail at `_mint` and must be retried after cap increase). Path 1 blocks all users from moving their synths cross-chain, including unwinding cross-chain leverage/flash-repay flows. Both states persist until the governor intervenes (`updateMaxBridgedIn/OutSupply`), matching the report's "undesired state until owner intervention" severity model.

### Likelihood Explanation
Requires capital proportional to the remaining cap headroom, but the attacker does not lose the funds (they hold the synths on the other side and can sell or, for path 2, eventually bridge back after the governor raises the cap — recouping everything). Caps are intentionally set near current volumes, so headroom can be small. No timing, oracle, or privileged assumption needed; executable in a single block via a contract.

### Recommendation
Make the caps time-windowed or per-message/per-account rather than purely cumulative (e.g., daily rolling bridge volume like the reference design intended but implemented correctly), or add rate-limited refilling. At minimum, inbound mints (path 2) should not be allowed to permanently wedge: consider making `totalBridgedIn`/`totalBridgedOut` accounting ignore the failed case or adding a sanctioned "cap relief" queue, and monitor/alert on cap utilization approaching the limit.

### Proof of Concept
Hardhat fork sketch (mainnet msUSD):

```ts
// Attacker: acquire msUSD on mainnet (swap or issue), then:
const oft = await ethers.getContractAt('ProxyOFT', PROXY_OFT_ADDR);
const synth = await ethers.getContractAt('SyntheticToken', MSUSD_ADDR);
const headroom = (await synth.maxBridgedOutSupply()).sub(await synth.bridgedOutSupply());
await synth.approve(oft.address, headroom);
// one call suffices; LZ fee quoted via oft.estimateSendFee
await oft['sendFrom(address,uint16,address,uint256)'](
  attacker.address, DST_LZ_CHAIN_ID, attacker.address, headroom, {value: fee});
// now bridgedOutSupply() == maxBridgedOutSupply
await expect(
  oft['sendFrom(address,uint16,address,uint256)'](victim.address, DST_LZ_CHAIN_ID, victim.address, 1, {value: fee})
).revertedWithCustomError(synth, 'SurpassMaxBridgingSupply');
// all bridge-outs for msUSD blocked until governor raises cap
```

For path 2, on the destination chain the attacker calls `sendFrom` to this chain; the delivered `_lzReceive` → `SyntheticToken.mint` reverts in `_mint` once `bridgedInSupply() > maxBridgedInSupply`, caching the message as failed (`CallOFTReceivedFailure` path) and leaving the victim's tokens burned on the source chain until the cap is raised or the attacker bridges out.
