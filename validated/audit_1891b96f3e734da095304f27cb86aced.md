### Title
Unchecked null `DelegatedResourceCapsule` dereference in `UnDelegateResourceActuator.execute` can crash block processing - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.execute()` fetches the "unlock" `DelegatedResourceCapsule` from `DelegatedResourceStore` and immediately calls mutator methods on it without a null check, mirroring the CVE-2024-53115 bug class (a store/lookup helper that can legitimately return `NULL`/`null` is dereferenced without validation).

### Finding Description
In `execute()`: [1](#0-0) 
the code calls `delegatedResourceStore.unLockExpireResource(...)` and then reads the "unlock" key with `delegatedResourceStore.get(unlockKey)` into `unlockResource`, followed directly by `unlockResource.addFrozenBalanceForBandwidth(...)` / `unlockResource.addFrozenBalanceForEnergy(...)` at lines 137 and 152 — with no `null` check on `unlockResource` before dereferencing it, unlike every other `AccountCapsule`/`DelegatedResourceCapsule` lookup in this same class (e.g. `receiverCapsule` is null-checked at line 68, `lockResource` is null-checked at line 182).

`validate()` only guarantees that *either* the unlock-key resource *or* the lock-key resource is non-null and that their combined (unlock + expired-lock) balance covers `unDelegateBalance`: [2](#0-1) 
It is possible for `unlockResourceCapsule` (unlock key) to be `null` at validate-time while `lockResourceCapsule` (lock key, already expired) is non-null and alone satisfies the balance check — validation succeeds even though the unlock-key record does not exist yet.

`execute()` then relies on the side effect of `delegatedResourceStore.unLockExpireResource(...)` to have materialized/created the unlock-key record before it calls `delegatedResourceStore.get(unlockKey)` again and dereferences it unconditionally. I was not able to fully verify the internal implementation of `DelegatedResourceStore.unLockExpireResource` within the available tool budget (its body in `chainbase/src/main/java/org/tron/core/store/DelegatedResourceStore.java` was located but not read to completion), so I cannot conclusively confirm every edge case (e.g., resource type mismatch such as validating with `ENERGY` while only bandwidth balance is delegated, expiry-timestamp boundary conditions, or a lock resource whose `getFrozenBalanceForBandwidth()`/`getFrozenBalanceForEnergy()` for the *requested* resource type is zero while the other resource type carries the balance) that could leave `unlockResource` `null` at line 130 after the call. This is the primary uncertainty in this analog.

### Impact Explanation
If any code path allows `unlockResource` to remain `null` after `unLockExpireResource()` (e.g., a mismatch between the resource type validated in `validate()` and what `unLockExpireResource` actually promotes, or an edge case in expiry timing), the resulting `NullPointerException` is thrown deep inside `execute()`, which is invoked from `Manager` during transaction processing for every applied `UnDelegateResourceContract`. An uncaught runtime exception here is not one of the actuator's declared checked exceptions (`ContractExeException`), so it would propagate as an unchecked `NullPointerException` through block application, which can crash or halt the node's block-processing path — a node-crash/halt impact within scope.

### Likelihood Explanation
Reachability is high: `UnDelegateResourceContract` is a standard broadcastable contract type that any account holding delegated resources can submit, requiring no special privileges beyond having a delegation relationship. However, likelihood of actually *triggering* the null dereference is uncertain because it depends on `DelegatedResourceStore.unLockExpireResource`'s exact contract (whether it always creates/updates the unlock-key record whenever `lockResourceCapsule` satisfied the balance check in `validate()`). Because I could not fully verify this store method in the time available, I rate confidence as medium — the missing defensive null check is a definite code smell directly analogous to the CVE, but full end-to-end exploitability through a specific transaction sequence is unconfirmed.

### Recommendation
Add an explicit null check on `unlockResource` immediately after `delegatedResourceStore.get(unlockKey)` in `execute()` (lines 130-131), mirroring the existing pattern used for `receiverCapsule` and `lockResource` in the same method — e.g., construct a fresh, zero-balance `DelegatedResourceCapsule` when `unlockResource == null` before entering the `switch` block, so the `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` calls are always safe regardless of `unLockExpireResource`'s internal behavior.

### Proof of Concept
A definitive transaction-level PoC could not be constructed without confirming the exact semantics of `DelegatedResourceStore.unLockExpireResource` (unread in this session). Conceptually: an attacker/account owner delegates resources, lets the lock period expire, and submits an `UnDelegateResourceContract` for a resource type/amount where `validate()`'s combined-balance check is satisfied solely by the (now-expired) lock-key record while the unlock-key record does not yet exist for that resource type; if `unLockExpireResource()` does not create the unlock record for that exact case, `execute()` at line 137/152 throws `NullPointerException`.
