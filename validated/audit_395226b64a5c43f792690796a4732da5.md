## Title
Broken `value.is_zero()`/`gas_limit` heuristic grants full `AllowReentry` (instead of restricted `AllowNext`) for exactly the common non-zero-value `.transfer()`/`.send()` stipend case in the EVM-compat CALL handler - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

### Summary
`pallet-revive`'s EVM-compatibility interpreter tries to recreate Solidity's 2300-gas-stipend reentrancy guard (the very mechanism the external report is about — code relying on a fixed, tiny gas allowance passed with a value transfer). The local re-implementation of this guard mis-detects which calls are "stipend" calls, so the case that actually matters most — a non-zero-value `.transfer(amount)`/`.send(amount)` — gets the *weakest* protection level instead of the restricted one, defeating the very defense the mechanism was added for.

### Finding Description
`run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` decides the reentrancy level using this heuristic: [1](#0-0) 

```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        // Heuristic: detect when solc passes `gas_limit = 2300` (the call stipend).
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

Per the project's own gas table (`prdoc/stable2603/pr_11227.prdoc`), solc emits `gas_limit = 0` for **non-zero-value** `transfer`/`send` (the EVM adds the 2300 stipend implicitly), and only emits `gas_limit = 2300` explicitly for the **zero-value** variants: [2](#0-1) 

Because the match is ordered `(value.is_zero(), gas_limit == CALL_STIPEND)` and the first arm `(false, _)` fires whenever `value` is non-zero — regardless of `gas_limit` — every ordinary `.transfer(amount)`/`.send(amount)` call (value > 0, gas_limit = 0) is routed to `ReentrancyProtection::AllowReentry`, the unrestricted mode, while `add_stipend` is still set to `true` so it still receives only the tiny stipend weight. Only the rare zero-value stipend calls (`transfer(0)`, `send(0)`) reach the intended `AllowNext` branch.

`exec.rs`'s own doc comment explains why `AllowNext` exists at all: [3](#0-2) 

i.e., in Ethereum the 2300-gas stipend by itself is enough to stop a callee from making another call; "due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here." That explicit enforcement is `AllowNext`. The heuristic bug means this explicit enforcement is skipped precisely in the scenario the comment says needs it most — non-zero-value transfers, i.e. real ETH-analog transfers guarded by the classic `.transfer()`/`.send()` reentrancy idiom.

This exact reachability gap is independently confirmed in a later fix's prdoc, which documents the current (unpatched-here) state of the code: [4](#0-3) 

> "In EVM mode, `CALL`/`STATICCALL` default to `ReentrancyProtection::AllowReentry` for non-zero-value calls and for zero-value calls without the 2300-gas Solidity stipend (`vm/evm/instructions/contract.rs:193-203`)."

That prdoc goes on to describe an actual storage-accounting corruption bug (`same_contract_reentry_does_not_double_count_storage`) that is only reachable because non-zero-value transfers default to `AllowReentry` — i.e., this exact heuristic gap is the root cause enabling a same-contract reentrancy path that corrupts `ContractInfo` storage-deposit accounting (`storage_items`/`storage_bytes`/`storage_*_deposit` inflated via double-counted diffs, per `RawMeter`/`Frame::pop_frame` in `exec.rs`).

### Impact Explanation
Any Solidity contract deployed on `pallet-revive` that relies on the standard `.transfer(amount)`/`.send(amount)` idiom to prevent reentrancy (the de-facto standard mitigation pattern, and exactly the pattern this task's seed report is about) does **not** get the reentrancy protection its developer/auditor expects at the runtime level. Combined with the confirmed downstream effect in `pr_12267.prdoc`, this allows a same-contract (or transitive) reentrant call during a value transfer to corrupt persisted per-contract storage-deposit accounting state (`insert_contract`), which under-refunds `clear_storage` operations later — a runtime bug that compromises intended value/deposit accounting for the underlying, permissionless `call` extrinsic path (`Pallet::call` / `bare_call` in `substrate/frame/revive/src/lib.rs`).

### Likelihood Explanation
High reachability: any unprivileged account can deploy an EVM-compiled (solc) contract and drive a value-bearing call to a receiver contract whose `receive()`/`fallback()` reenters — this requires no relayer, validator, governance, or leaked key, only ordinary `eth_call`/`call` extrinsics. The condition (`value > 0`, `gas_limit == 0`) is the default bytecode solc emits for `.transfer()`/`.send()`, so it is hit by essentially every contract using this common idiom, not an edge case.

### Recommendation
Fix the match ordering/logic in `run_call` so that `AllowNext` (restricted reentry, "next frame only") is applied whenever the call is stipend-scale, independent of whether `value` is zero — i.e. detect "stipend call" as `gas_limit == CALL_STIPEND` OR ("value > 0" AND "gas_limit == 0", meaning the EVM-implicit-stipend case), and only use `AllowReentry` for calls that genuinely forward non-stipend gas (e.g. `.call{value: v}("")`). Cross-check against the fix path already tracked in `prdoc/pr_12267.prdoc` (storage double-count fix) to ensure the reentrancy-level correction and the storage-accounting fix are consistent and both land together.

### Proof of Concept
Using the existing `Stipends.sol` fixture already in the repo (`substrate/frame/revive/fixtures/contracts/Stipends.sol`):
1. Deploy `StipendTest`; its constructor creates a `ReentrancyAttacker` whose `receive()` calls back into `msg.sender.attemptTransfer(...)`.
2. Call `testTransferReentrancy()` with `msg.value > 0`. This invokes `this.attemptTransfer(payable(reentrancyAttacker), amount)`, which performs `to.transfer(amount)` — a **non-zero-value** transfer, so `gas_limit == 0` at the EVM CALL opcode.
3. Per `run_call`'s first match arm `(false, _) => (true, AllowReentry)`, this transfer is executed with `ReentrancyProtection::AllowReentry`, not `AllowNext`, even though the fixture and `pr_11151.prdoc`/`pr_11227.prdoc` intend this call to be reentrancy-guarded like Ethereum's stipend.
4. Combine with the `same_contract_reentry_does_not_double_count_storage` scenario from `prdoc/pr_12267.prdoc` (self-reentrant `write→call-self→write`) using a value-bearing call in place of the zero-value path used there, to reproduce persisted `ContractInfo` storage counter inflation exploitable by any depositor interacting with the contract.
