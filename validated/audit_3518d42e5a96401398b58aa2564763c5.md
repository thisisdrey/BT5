## Title
Front-running poisoned transaction can lock out a legitimate broadcast via stale `transactionIdCache` entry (incomplete cleanup) - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`Wallet.broadcastTransaction()` inserts a transaction's ID into `Manager.transactionIdCache` to short-circuit duplicate broadcasts, but it does so *before* the transaction has been fully validated (signature correctness, TAPOS, expiration, execution). If the subsequent `pushTransaction()` call fails for any reason, the ID is never evicted from the cache. Because the transaction ID is derived only from `rawData` (not the signature), an attacker who knows or predicts the `rawData` of a transaction that a legitimate user is about to broadcast can pre-submit a copy with a garbage-but-correctly-sized signature. This poisons the cache with the shared ID, causing the victim's later, correctly-signed broadcast of the same transaction to be rejected as `DUP_TRANSACTION_ERROR` for up to the cache's 1-hour TTL — mirroring the reported Zebra `SentHashes`/`KnownBlock` incomplete-cleanup bug class (CWE-459), but reached here via the anonymous `broadcastTransaction` RPC/HTTP path.

### Finding Description
In `Wallet.broadcastTransaction()`: [1](#0-0) 

Only signature *length* is checked before the transaction ID is registered: [2](#0-1) 

`getTransactionIdCache()` is populated eagerly at this point, well before `dbManager.pushTransaction(trx)` performs real signature/TAPOS/expiration/execution validation: [3](#0-2) 

If `pushTransaction` subsequently throws (e.g. `ValidateSignatureException`, `ContractValidateException`, `TaposException`, `TransactionExpirationException`, etc.), the corresponding `catch` blocks only build an error response — none of them remove the ID from `transactionIdCache`: [4](#0-3) 

The cache itself is a 1-hour TTL cache defined on `Manager`: [5](#0-4) 

Critically, the Transaction ID (`Sha256Hash`) used as the cache key is computed only from `rawData`, independent of the signature bytes (this is standard protobuf tx-id design, but it means the signature does not affect the key). Consequently, an attacker who can predict/observe a target `rawData` (owner, contract, amount, ref block, expiration, fee limit) can submit a transaction sharing the same ID with an arbitrary (but length-valid) signature. This bogus submission fails `ValidateSignatureException` and returns `SIGERROR` to the attacker, but the ID stays cached. When the legitimate signer then broadcasts the real, correctly-signed transaction, `broadcastTransaction` hits the stale cache entry at line 559 and immediately returns `DUP_TRANSACTION_ERROR` — the honest transaction is never pushed, validated, or gossiped.

### Impact Explanation
This is a targeted, unauthenticated denial-of-service against a specific victim transaction: the legitimate, fully-valid transaction is rejected outright by the broadcasting node for up to the cache TTL (1 hour), delaying or effectively blocking a time-sensitive transfer/contract call without the victim being aware their transaction was even attempted server-side (they just see `DUP_TRANSACTION_ERROR`). This matches the "incomplete cleanup of a sent/known marker causing legitimate items to be treated as already handled" bug class from the reference advisory, reachable here through the fully in-scope `broadcastTransaction` API used by any anonymous transaction broadcaster.

### Likelihood Explanation
Exploitability depends on the attacker's ability to predict or observe the exact `rawData` of a not-yet-broadcast transaction (e.g. deterministic transfer parameters, or observing a transaction the moment it appears in relay/mempool from another node before it reaches the target node). Where this is possible — for example, a wallet or dApp that constructs deterministic transactions before signing/broadcasting, or a race where the attacker beats the honest broadcast to the same node — the attack requires no special privileges, only the ability to call the public `broadcastTransaction` RPC/HTTP endpoint with a garbage signature of correct length.

### Recommendation
Do not insert into `transactionIdCache` until the transaction has passed full validation (signature, TAPOS, expiration) inside `pushTransaction`, or remove/rollback the cache entry in every failure path of `broadcastTransaction` (mirroring how `Request::KnownBlock` was patched in the referenced advisory to drain rejected entries before consulting the "known" set).

### Proof of Concept
1. Determine (or observe) the exact `rawData` bytes of a transaction Victim intends to broadcast (owner, contract, ref block, expiration, fee limit).
2. Attacker builds a `Transaction` with identical `rawData` but attaches an arbitrary signature of valid byte length, and calls `broadcastTransaction` on the target node. The call reaches line 564 and inserts `txID` into `transactionIdCache`, then fails signature validation inside `pushTransaction`, returning `SIGERROR` to the attacker.
3. Victim subsequently calls `broadcastTransaction` with the same `rawData` and a correct signature. At line 559 the node finds `txID` already present in `transactionIdCache` and immediately returns `DUP_TRANSACTION_ERROR`, without ever validating or propagating the honest transaction.
4. The lockout persists until the 1-hour TTL expires or the cache entry is evicted by size pressure.
