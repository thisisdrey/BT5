### Title
Non-atomic order matching in `MarketSellAssetActuator` permits partially-committed trades and unbacked order-book entries when the `MAX_MATCH_NUM` guard aborts mid-loop - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
The external report describes a class of bug where a contract irreversibly commits state (`self.status = Resume`, liquidity removed from the pool) before an external, potentially-failing operation completes, and the failure path (`afterDepositCancellation`) does not undo the earlier state change — leaving the vault in an inconsistent state that can neither proceed nor be reverted, permanently locking funds. The structurally equivalent pattern exists in java-tron's on-chain order-matching actuator: `MarketSellAssetActuator` persists several irreversible store writes (new order creation, maker-side balance credits, order-book removals) *before* it evaluates a failure condition (`MAX_MATCH_NUM` exceeded) that aborts the transaction as `FAILED`, and none of the already-applied writes are rolled back when that abort happens.

### Finding Description
`MarketSellAssetActuator.execute()` performs several steps that write directly to persistent, revoking-backed stores rather than to a per-transaction scratch/child repository that can be discarded on failure (contrast this with TVM execution, where `Program.callToAddress` uses a child `Repository deposit` and only calls `deposit.commit()` on success [1](#0-0) , discarding it otherwise [2](#0-1) ).

In `MarketSellAssetActuator`, `createAndSaveOrder` immediately persists the taker's new order into `orderStore` and `marketAccountStore`: [3](#0-2) 

The subsequent `matchOrder`/`matchSingleOrder` calls directly commit maker-side state changes — reducing/zeroing a maker's `sellTokenQuantityRemain`, persisting the updated maker order via `orderStore.put`, crediting the maker's account balance via `addTrxOrToken` (which itself calls `accountStore.put`), and removing the maker order from the order book: [4](#0-3) [5](#0-4) [6](#0-5) 

Critically, the loop's `MAX_MATCH_NUM` guard is only checked *after* `matchSingleOrder` (and its persisted side effects) have already run for that iteration: [7](#0-6) 

When this guard fires, it throws `ContractValidateException("Too many matches...")`, which is caught by the outer `try/catch` in `execute()`. This sets the transaction result to `FAILED` and re-throws a `ContractExeException`, aborting the transaction: [8](#0-7) 

The taker's own compensating writes — the fee/token debit applied to the in-memory `accountCapsule` and the final persistence of the (possibly reduced) taker order — only occur at the very end of `execute()`, at lines 147–148, and are skipped entirely when the exception is thrown mid-loop: [9](#0-8) 

The net effect: an order that was already persisted to the on-chain order book at the *original* (un-debited) quantity (from `createAndSaveOrder`), combined with real, already-committed reductions/credits on the maker side of the trade, is not undone when the overall transaction is marked `FAILED`. There is no actuator-scoped rollback mechanism analogous to the TVM's `Repository` child/commit pattern to undo these writes, mirroring the GMX report's root cause: state committed before a failure path is triggered, with no correct recovery of that state on the failure branch.

### Impact Explanation
An attacker-controlled taker can craft a `MarketSellAssetContract` designed to match more than `MAX_MATCH_NUM` (20) qualifying maker orders in the order book at once. Because the taker's own order was already persisted to `orderStore`/`marketAccountStore` at full quantity before the guard fires, and the transaction's own balance-debiting write is skipped due to the abort, the taker ends up with a phantom order representing tokens/TRX they were never actually debited for. This order can subsequently be cancelled via `MarketCancelOrderActuator`, which calls `MarketUtils.returnSellTokenRemain` to credit the (never-actually-spent) `sellTokenQuantityRemain` back to the attacker's account: [10](#0-9) 

This produces an unbacked balance increase (tokens/TRX materialized without a corresponding debit), while up to 20 legitimate maker accounts have already had real balance credits and order-quantity reductions applied and persisted. This satisfies the "unbacked balance / theft of funds" bar because value can be created from nothing and/or extracted from counterpart makers whose orders were consumed against a taker order that was never actually funded.

### Likelihood Explanation
Reaching this path only requires broadcasting a single, unprivileged `MarketSellAssetContract` transaction (reachable by any account owner via the standard actuator/transaction path) against an order book that already has ≥`MAX_MATCH_NUM`+1 matching maker orders at the qualifying price — the attacker can themselves create the requisite maker orders beforehand with a separate account, making this fully self-triggerable without relying on a third party's on-chain activity or any special permission.

### Recommendation
Make `MarketSellAssetActuator`'s order creation, matching, and persistence atomic with respect to a single transaction: move the `MAX_MATCH_NUM` bound check to occur strictly before any store-mutating call in a given match iteration (or pre-validate that a match will not exceed the bound before invoking `matchSingleOrder`), and/or perform all store writes (`orderStore.put`, `accountStore.put`, `pairPriceToOrderStore` mutations) through a per-transaction child repository that is only committed on full success and discarded on any exception, matching the pattern already used for TVM contract execution in `Program.java`.

### Proof of Concept
1. Attacker (or colluding accounts) creates more than `MAX_MATCH_NUM` (20) small maker sell orders at a matching price for a token pair (A→B), using `MarketSellAssetActuator` normally.
2. Attacker submits a taker `MarketSellAssetContract` (B→A) sized to match against all of these ≥21 maker orders in a single transaction.
3. `MarketSellAssetActuator.execute()` runs `createAndSaveOrder` (persisting the taker's order at full un-debited quantity), then `matchOrder` begins consuming maker orders one by one, calling `matchSingleOrder` which directly persists maker-side quantity reductions and balance credits for each of the first 21 matches.
4. On the 21st match, `matchOrderCount > MAX_MATCH_NUM` triggers `ContractValidateException("Too many matches...")`, which is caught in `execute()`'s outer try/catch, setting the transaction result to `FAILED` and skipping the final `accountStore.put(accountCapsule...)` for the taker (lines 147–148).
5. The taker's phantom order (persisted in step 3, never actually debited) remains in `orderStore`/`marketAccountStore`; the attacker calls `MarketCancelOrderActuator` to cancel it, receiving a credit via `MarketUtils.returnSellTokenRemain` for tokens they never paid, while the 20+ maker accounts have already had real, persisted balance/order changes applied.

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
