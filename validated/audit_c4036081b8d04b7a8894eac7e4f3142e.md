### Title
Division by zero (uncaught `ArithmeticException`) in `RepositoryImpl.calculateGlobalEnergyLimit` when `totalEnergyWeight` is 0 - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)`, which is invoked on the hot path of every TVM contract call to compute an account's frozen-energy limit, guards against a zero `totalEnergyWeight` divisor only with a Java `assert` statement. Assertions are disabled by default in production JVMs (`-ea` is not set), so the guard is a no-op at runtime. When the hardened resource-calculation path is active, the method performs a `BigInteger.divide(BigInteger.valueOf(totalEnergyWeight))`, which throws `ArithmeticException: BigInteger divide by zero` if `totalEnergyWeight` is 0.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

The `assert` is the only check on `totalEnergyWeight`, and unlike other similar helpers in the codebase, there is no explicit `if (totalEnergyWeight == 0) return 0;` fallback. Compare this with the analogous bandwidth helper, which does contain an explicit zero-check before its own hardened division: [2](#0-1) 

`calculateGlobalEnergyLimit` is reached from `getAccountLeftEnergyFromFreeze`, which is executed for every account involved in TVM execution (energy metering): [3](#0-2) 

This is wired into contract invocation via `VMActuator`/`ContractState` (`Repository.calculateGlobalEnergyLimit`), i.e. it runs whenever any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` participates in a `TriggerSmartContract`/`CreateSmartContract` transaction — a fully unprivileged, broadcastable operation: [4](#0-3) 

`getTotalEnergyWeight()` is a global chain state value that is decremented on unfreeze/undelegate operations and is not permanently pinned above zero; on chains or test/private networks with low freeze activity, or transiently as accounts unfreeze energy, this value can legitimately reach 0. The "hardened" BigInteger path (`hardenResourceCalculation()` / `allowHardenResourceCalculation`) is a real, activatable chain parameter (confirmed by test fixtures toggling `saveAllowHardenResourceCalculation(1)`), so this is not a dead code path.

### Impact Explanation
If `totalEnergyWeight` becomes 0 while the hardened resource-calculation feature is enabled, any subsequent smart-contract call by any account that has frozen balance for energy will throw an unhandled `ArithmeticException` deep in transaction/energy processing. Because this executes during transaction application (inside `VMActuator`), an uncaught runtime exception at this point can abort block processing for that transaction/block, causing a denial-of-service crash or halt of the node executing it — a direct availability impact on the network in line with the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Reaching `totalEnergyWeight == 0` requires an unusual but reachable global state (e.g., a network state where all energy-frozen balances have been unfrozen, or genesis/private-network configurations with the hardened calculation flag on). Once that state exists, the trigger is trivial: any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` submitting an ordinary `TriggerSmartContract` transaction hits the vulnerable code path — no special privileges are required. The likelihood is Medium: it depends on the chain parameter and total-weight state, but the trigger itself is a single ordinary transaction.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `calculateGlobalEnergyLimit` with an explicit runtime check, matching the pattern already used in `BandwidthProcessor`:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
placed before the `hardenResourceCalculation()` branch, so the BigInteger division is never attempted with a zero divisor regardless of JVM assertion settings.

### Proof of Concept
1. Configure/drive the chain into a state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns 0 (e.g., via unfreezing all energy-frozen balances network-wide) and enable `allowHardenResourceCalculation` (hardened path).
2. From any account holding `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`, broadcast an ordinary `TriggerSmartContract` transaction.
3. During execution, `VMActuator` invokes `Repository.getAccountLeftEnergyFromFreeze` → `RepositoryImpl.calculateGlobalEnergyLimit`, which executes `BigInteger.valueOf(totalEnergyWeight)` as divisor = 0, since the guarding `assert` is compiled out in a production JVM (no `-ea`), throwing `java.lang.ArithmeticException: BigInteger divide by zero` and aborting transaction/block processing on that node.
