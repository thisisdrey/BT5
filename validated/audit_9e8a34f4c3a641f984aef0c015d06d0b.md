## Analog Found

### Title
Cross-repository object disclosure via unconditional hard-linking of pool contents in `DisconnectGitAlternates` - (File: `internal/git/objectpool/disconnect.go`)

### Summary
The external report describes a Nouns Builder bug where `_transferFrom()` moves accounted state (delegated votes) directly between two entities without re-resolving it through the correct level of indirection (the actual delegate), letting a user accumulate more voting power than they are entitled to by repeatedly transferring and re-delegating. The Gitaly analog is in the object-pool "alternates" subsystem: when a repository is disassociated from its object pool, Gitaly does not re-derive which objects the *disconnecting repository* is actually entitled to (i.e. what is reachable from its own refs); instead it indiscriminately copies the *entire* pool's object store into the repository, permanently granting it objects that originated from other, unrelated pool members.

### Finding Description
Repositories that are forks share objects through an object pool via `objects/info/alternates`, as documented in [1](#0-0) . When a member wants to leave the pool, `Disconnect()` first "rehydrates" the repository by hard-linking every object found in the alternate directory into the repository's own object store, then removes the alternates file, and finally validates connectivity with `git rev-list`: [2](#0-1) 

Critically, `findObjectFiles()` walks the **entire** pool object directory tree and returns every packfile/loose object present, without any filtering based on what is actually reachable from the disconnecting repository's own references: [3](#0-2) 

An object pool accumulates objects from *all* of its members over time via `FetchIntoObjectPool`, including objects that only exist because of another (potentially private) fork's history, and it deliberately keeps "dangling" objects alive indefinitely because "any other member of the pool may still use any of those unreferenced objects" — see the explicit acknowledgment in the docs: [4](#0-3) 

Because `Disconnect()` hard-links the pool's *entire* object set rather than only the objects reachable by the disconnecting repository, once disconnected, that repository permanently and physically possesses copies of objects it never had reachable references to — including content pushed only to sibling forks. This is the direct structural analog of the reported bug: state (object/vote availability) is copied wholesale between two entities (pool → member) without re-deriving what the *true* delegated/owned subset should be, and once copied it can never be "taken back," since the objects are now loose/packed files in the recipient's own object database.

### Impact Explanation
`DisconnectGitAlternates` is exactly the RPC GitLab Rails invokes on ordinary, user-triggered actions — most notably when a fork's project visibility is changed to private, or when a fork is "unlinked" from its source, per the documented RPC lifecycle: [5](#0-4) 

An attacker who forks a public/shared repository (or who is a member of a pool alongside other forks whose maintainers pushed sensitive/unmerged content that ended up cached in the shared pool as dangling objects) can trigger disconnection of their own fork from the pool and thereby obtain durable, local copies of objects that were never reachable from their fork's own refs — a cross-repository object disclosure. Because the pool retains dangling objects from all historical members indefinitely (by design, to avoid corrupting other members), the blast radius grows over the pool's lifetime.

### Likelihood Explanation
This does not require any privileged access, leaked token, MITM, or malicious peer — it only requires being able to trigger a normal, supported lifecycle operation (a fork leaving its object pool), which is exposed to ordinary GitLab user actions (e.g., toggling fork visibility). The vulnerable code path (`findObjectFiles` walking the whole alternate directory, `Disconnect` hard-linking everything found) is unconditionally executed on every disconnect and is directly reachable without any special condition or race.

### Recommendation
`Disconnect()` should only rehydrate objects that are actually reachable from the disconnecting repository's own references (e.g., by computing the set of objects reachable via `git rev-list --objects --all` scoped to the repository prior to unlinking, and hard-linking only that subset), analogous to how the ERC721 fix requires resolving through the true delegate before moving voting weight. Alternatively, perform a `git repack`/`git prune-packed`-style extraction that only pulls in objects actually referenced by the repository's own ref namespace, rather than copying the pool's raw file listing indiscriminately.

### Proof of Concept
1. Create repository `A`, create an object pool `P` from `A`, and link `A` to `P` (`CreateObjectPool` + `LinkRepositoryToObjectPool`).
2. Fork `A` into repository `B`; link `B` to the same pool `P`.
3. In `B`, push a private branch/commit that only exists in `B`. Trigger `FetchIntoObjectPool` from `B` into `P` (a normal housekeeping operation), causing `B`'s private commit objects to be copied into the shared pool `P`.
4. Later, `B`'s branch is deleted/rewritten (force-push) so the object becomes "dangling" in `P` but is kept alive by the pool's dangling-object retention logic, per [6](#0-5) .
5. As the attacker controlling repository `A` (or any other pool member), call `DisconnectGitAlternates` on `A`. `Disconnect()`'s `findObjectFiles(altObjectDir)` walks the whole pool object tree and hard-links every object — including `B`'s private dangling commit — into `A`'s own object store, per [2](#0-1) .
6. After disconnection, the attacker can read `B`'s previously-private object directly from `A`'s now-local object database (e.g. via `CatFile`/`GetCommit` RPCs), even though it was never reachable through `A`'s own refs.

func findObjectFiles(altDir string) ([]string, error) {
	var objectFiles []string
	if walkErr := filepath.Walk(altDir, func(path string, info os.FileInfo, err error) error {
		if err != nil {
			return err
		}

		rel, err := filepath.Rel(altDir, path)
		if err != nil {
			return err
		}

		if strings.HasPrefix(rel, "info/") {
			return nil
		}

		if info.IsDir() {
			return nil
		}

		objectFiles = append(objectFiles, rel)

		return nil
	}); walkErr != nil {
		return nil, walkErr
	}

	sort.Sort(objectPaths(objectFiles))

	return objectFiles, nil
}
