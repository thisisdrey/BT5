### Title
Unbounded array-length field from precompiled-contract calldata triggers uncontrolled memory allocation / OutOfMemoryError - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray` and `extractBytes32Array` read a 32-byte "length" word directly out of attacker-supplied precompile calldata and immediately allocate a Java array sized by that value, with no upper bound or sanity check before the allocation happens.

### Finding Description
`extractBytes32Array` and `extractBytesArray` take the count of elements straight from a `DataWord` in the caller-controlled input and use it to size a `byte[][]` allocation before any content is copied or validated: [1](#0-0) [2](#0-1) 

`len = words[offset].intValueSafe()` converts an attacker-controlled 256-bit word into a 32-bit int (clamped to `Integer.MAX_VALUE` by `intValueSafe()`), and this value is used directly as the size of a reference array (`new byte[len][]`). A `byte[][]` of size close to `Integer.MAX_VALUE` requires several gigabytes just for the object-reference backing array (4–8 bytes per null slot), independent of any subsequent per-element gas metering — the allocation attempt happens *before* the per-element loop that could otherwise fail fast. This is the same bug class as the reported Bouncy Castle CVE-2019-17359: a small, cheaply crafted input contains a large length field that is trusted at face value and used to drive a memory allocation, producing an `OutOfMemoryError` from a tiny amount of attacker effort.

This is analogous to the hardened pattern already present elsewhere in the codebase (e.g. `RLP.decode`/`RLP.verifyLength` explicitly bounds supplied lengths against available data before allocating, and catches `OutOfMemoryError` defensively): [3](#0-2) 
No equivalent bound exists for `extractBytesArray`/`extractBytes32Array` in `PrecompiledContracts.java`.

### Impact Explanation
If reachable from a precompiled contract's `execute(byte[] data)` entry point that is invoked via a normal `CALL`/`STATICCALL` TVM opcode to a precompile address, any unprivileged contract caller could submit calldata whose length word is set to a very large value (e.g., `0xffffffff`), causing the executing full node to attempt a multi-gigabyte array allocation on a single transaction. Depending on JVM heap configuration this can throw `OutOfMemoryError`, which — unless caught at every level of the VM execution path — can crash or destabilize the node process, i.e., "node crash or halt" impact.

### Likelihood Explanation
Likelihood depends on which precompiled-contract `execute()` method calls `extractBytesArray`/`extractBytes32Array` and at what point in that method's control flow (before or after any energy/size pre-check). I located 5 usages of these two methods within `PrecompiledContracts.java` but was not able to enumerate and confirm each call site's surrounding validation within the tool budget available for this session. Without that confirmation, I cannot assert with full certainty that no length check precedes every call site.

### Recommendation
Add an explicit upper bound / sanity check on the "count" word read from calldata before using it to size any array in `extractBytesArray` and `extractBytes32Array` (e.g., compare against the remaining bytes in `data`, similar to `RLP.verifyLength`), and reject with a controlled error instead of attempting the allocation.
