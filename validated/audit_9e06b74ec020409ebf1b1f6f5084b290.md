Confirmed: `gas_cost` (the actual gas expenditure) is charged directly from `gas_key_info.balance` for a gas-key transaction, while `deposit_cost` is charged from `account.amount()`. Only the *gas* portion is real money held in the gas key's `balance` field, and only that portion is what a subsequent gas-refund receipt (`Receipt::new_gas_refund`) is meant to restore.

### Title
Stale access-key-kind refund routing lets a gas-key gas refund be misdirected into account balance and access-key allowance simultaneously - (File: `runtime/runtime/src/lib.rs`)

### Summary
`action_transfer_or_implicit_account_creation` decides how to apply a gas refund receipt purely by inspecting the *current* access key stored under the refund's `signer_public_key`, not by any record of what kind of key actually paid for the original transaction. If the account owner deletes a gas key and re-adds a `FunctionCall`-permission access key reusing the same public key before the outstanding gas refund receipt executes, the runtime treats the refund as an ordinary allowance refund: it credits the deposit into `account.amount()` via `action_transfer` **and** separately increases the `FunctionCallPermission.allowance` by the same amount via `try_refund_allowance`.

### Finding Description
For a gas-key transaction, `gas_cost` is debited straight from `access_key.gas_key_info().balance` (`runtime/runtime/src/verifier.rs:440-447`), which is real, independently-held token value distinct from `account.amount()`. The refund path in `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1230-1365`) always emits a `Receipt::new_gas_refund` carrying only the original `signer_public_key` — it carries no information about whether that key was a gas key or a regular key at charge time [1](#0-0) .

When that refund receipt is later applied, `action_transfer_or_implicit_account_creation` re-derives the routing decision from the **current** state of the access key: [2](#0-1) 
```
let is_gas_refund = is_refund && action_receipt.signer_id() == receipt.receiver_id();
if is_gas_refund && try_refund_gas_key_balance(...) { return Ok(()); }
action_transfer(account, deposit)?;
if is_gas_refund { try_refund_allowance(...)?; }
```
`try_refund_gas_key_balance` (`runtime/runtime/src/actions.rs:112-132`) only succeeds if the access key currently present under `signer_public_key` is *still* a gas key. If the user has since deleted that gas key and added a new `FunctionCall`-permission key with the same public key, `try_refund_gas_key_balance` returns `false`, and control falls through to `action_transfer(account, deposit)` — crediting the refund into `account.amount()` — followed unconditionally by `try_refund_allowance` (`runtime/runtime/src/actions.rs:134-158`), which adds the same `deposit` amount to `FunctionCallPermission.allowance`.

This is the same root-cause shape as the reported bug: the system uses one piece of persistent state (the current access-key record) as an implicit "kind" flag paired with a value that must be updated consistently with it (the location where refunded value is credited), but the kind flag can be mutated out from under the pending refund between when the debt is incurred and when it is settled, causing the two credit paths (real balance vs. allowance bookkeeping) to be applied inconsistently. Whereas for a genuinely FunctionCall-charged transaction the account balance and the allowance both represent the *same* underlying debit (so crediting both back is correct and non-inflationary), for a gas-key-charged transaction the `gas_cost` was never subtracted from `account.amount()` nor from any `FunctionCallPermission.allowance` at charge time — it came solely out of `gas_key_info.balance`. Crediting it into `account.amount()` *and* into a newly-created key's `allowance` therefore does not merely misplace funds within the account; it also inflates the new key's spendable allowance ledger by an amount that was never actually reserved against that key, while the account's real balance also grows by the refund. Net effect: the account's total token balance is still correctly increased once (no double real-money mint), but the FunctionCall key's allowance counter is bumped by an amount it never paid, over-crediting a purely internal spending-limit counter that gates how much of the account's *real* balance that key is allowed to spend later — i.e. it grants the new key spending headroom that was not backed by any actual charge against it, up to the size of the outstanding gas refund.

### Impact Explanation
The affected account is the sole beneficiary/victim, so there is no cross-account theft. The concrete effect is a bookkeeping-consistency violation in `FunctionCallPermission.allowance` that does not correspond to any real balance previously reserved against that key: the allowance can be inflated by up to the outstanding gas-refund amount for every gas-key-to-FunctionCall-key transition performed while a refund is in flight, letting the new key spend more of the account's real balance than the intended per-key allowance model allows. This is an authorization/limit-bypass on the access-key allowance mechanism, analogous in class (though smaller in blast radius) to the original reward-debt accounting bug, since it stems from the identical "paired state not kept consistent across a kind-change reset" pattern. It does not, however, on its own produce protocol-wide fund theft, double-spend across accounts, or state-root divergence between honest nodes (since all nodes apply the same deterministic receipt-processing logic), so it is best characterized as a fund-accounting/limit-integrity flaw for the affected account rather than a network-wide critical bug.

### Likelihood Explanation
Triggering requires precise attacker-controlled sequencing purely by the account owner (no cross-account trust boundary is crossed): submit a gas-key transaction that leaves an unspent-gas refund pending, then before that refund receipt executes, submit `DeleteKey` for the gas key and `AddKey` reusing the identical public key with a `FunctionCall` permission and a chosen allowance. Since refund receipts are processed by the same shard/account in the following chunk(s), a user controlling their own transaction ordering can realistically arrange this within a couple of blocks.

### Recommendation
Do not re-derive the refund-routing "kind" from the live access-key state at refund-execution time. Either (a) encode into the refund receipt itself (or into per-tx pending-refund state) whether the paying key was a gas key at charge time and route strictly by that recorded kind, refusing/burning-and-logging a mismatch rather than falling through to the allowance path, or (b) when `try_refund_gas_key_balance` fails because the key is no longer a gas key, skip `try_refund_allowance` entirely for what was originally a gas-key charge (only apply `action_transfer` to restore the real balance, without touching any `FunctionCallPermission.allowance`, since that allowance was never charged in the first place).

### Proof of Concept
1. Account `A` adds a gas key `pk` with `num_nonces` and funds it via `TransferToGasKey`.
2. `A` submits a `FunctionCall` transaction signed with `pk` using the gas-key nonce with generous `prepaid_gas`, causing gas to be charged from `gas_key_info.balance` (`verifier.rs:447`) and a large unused-gas refund to be scheduled (`lib.rs:1354-1362`).
3. Before the resulting gas-refund receipt (`predecessor_id == "system"`, `signer_id == receiver_id == A`, `signer_public_key == pk`) executes, `A` submits, in the same or an earlier-processed transaction: `DeleteKey(pk)` then `AddKey(pk, FunctionCall{ allowance: Some(X), ... })`.
4. When the gas-refund receipt executes, `try_refund_gas_key_balance` fails (key `pk` is no longer a gas key) (`actions.rs:121-126`), so `action_transfer` credits `account.amount()` with the refund, and `try_refund_allowance` (`actions.rs:140-155`) additionally adds the refund amount to the new key's `allowance`, even though that key's allowance was never debited for the original transaction's gas cost.
5. Compare `pk`'s allowance before step 3 (`X`) to its allowance after the refund lands: it will be `X + refund_amount`, an increase not backed by any prior charge against that key — confirming the inconsistent paired-state update.
