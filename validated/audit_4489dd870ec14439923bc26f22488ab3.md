Audit Report

## Title
Unbounded slippage in `SwapFirstAssetTrader::refund_weight` lets an attacker sandwich XCM fee refunds and drain refunded value via the AssetConversion pool - (File: cumulus/primitives/utility/src/lib.rs)

## Summary
`SwapFirstAssetTrader::refund_weight` swaps the unused portion of collected `Target`-asset fees back into the user's original payment asset by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, disabling the minimum-output check that this same trait's implementation otherwise enforces. [1](#0-0) 

## Finding Description
`buy_weight` withdraws the user's non-target payment asset and swaps it for the `Target` asset via `SwapCredit::swap_tokens_for_exact_tokens`, requesting an exact `fee` amount with no minimum-input laxity issue because it targets exact output. [2](#0-1) 

`refund_weight` extracts the unused `Target`-asset credit and swaps it back into `refund_swap_asset` using `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)`, passing `None` for `amount_out_min`. [3](#0-2) 

The `SwapCredit::swap_exact_tokens_for_tokens` trait definition explicitly documents that `amount_out_min` is optional and, when provided, causes an error if the swap can't achieve at least that amount — implying that when `None` is passed, no minimum is enforced. [4](#0-3)  The concrete pallet implementation of `Pallet::swap_exact_tokens_for_tokens` (the `Swap` trait, used by the dispatchable) forwards to `do_swap_exact_tokens_for_tokens`, which only checks `amount_out >= amount_out_min` when `amount_out_min` is `Some(_)` — when `None`, the check is skipped entirely. [5](#0-4)  The `SwapCredit` implementation used by `refund_weight` calls the analogous `do_swap_exact_credit_tokens_for_tokens`, which follows the same optional-check pattern. [6](#0-5) 

This trader type is instantiated in the live XCM `Trader` configuration of Asset Hub Rococo, Asset Hub Westend, Penpal, and the staking-async parachain runtime, confirmed by direct references to `SwapFirstAssetTrader` in each runtime's `xcm_config.rs`. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)  The pool used for this swap is the same public, permissionlessly tradable AssetConversion pool that any account can swap against via the public dispatchable `swap_exact_tokens_for_tokens`, which correctly enforces `amount_out_min` for ordinary users. [11](#0-10) 

By contrast, the analogous refund path in the transaction-payment asset-conversion adapter always quotes a price and passes `Some(refund_asset_amount)` before swapping back a refund, demonstrating that the codebase's own pattern for safe refund swaps is to bound the output — a pattern `refund_weight` omits. [12](#0-11) 

An attacker who can observe an in-flight XCM message that will trigger a fee refund can move the pool price against the refund swap via the public swap dispatchables immediately before `refund_weight` executes, and reverse it afterward, capturing the difference between the fair and manipulated refund amount.

## Impact Explanation
The corrupted value is the amount of the original fee-payment asset credited back to the user upon refund. Because the swap-back accepts any nonzero output, a manipulated pool price transfers value from the intended refund recipient to whoever manipulated the pool immediately before the refund executed. This matches the "public underpriced work" / value non-conservation category under the impact gate: intended fee-refund behavior is degraded on a public, permissionless AMM pool without any privileged actor involved.

## Likelihood Explanation
This requires only ordinary transaction-ordering ability against public, permissionless `AssetConversion` dispatchables (`swap_exact_tokens_for_tokens` / `swap_tokens_for_exact_tokens`), which are open to any unprivileged account. Fee overestimation causing refunds is a routine consequence of XCM weight accounting, so the precondition (a non-trivial `refund_amount` in `refund_weight`) is not rare. No governance, validator, or relayer privilege is required — only observability of pending XCM execution and the ability to race transactions within the same or adjacent blocks.

## Recommendation
Compute a bound before the swap-back in `refund_weight`, e.g., using `QuotePrice::quote_price_exact_tokens_for_tokens(Target::get(), refund_swap_asset, refund_amount, true)` and pass `Some(quoted_min)` (with a small tolerance) as `amount_out_min` to `SwapCredit::swap_exact_tokens_for_tokens`, mirroring the pattern already used in the asset-conversion transaction-payment adapter. On swap failure, retain the credit in `total_fee` as the existing error branch already does.

## Proof of Concept
1. Deploy a runtime using `SwapFirstAssetTrader` as the XCM `Trader` (as in `asset-hub-rococo`, `asset-hub-westend`, `penpal`, or the staking-async parachain), with an `AssetConversion` pool between `Target` and a foreign/local asset.
2. Attacker monitors for an incoming XCM message that overpays fees in a swappable non-target asset (routine due to conservative fee estimation).
3. Immediately before the message executes, the attacker calls the public `swap_tokens_for_exact_tokens` dispatchable to skew the pool's `Target`→foreign-asset price unfavorably.
4. The XCM message executes; `buy_weight` swaps in the exact fee; unused weight triggers `refund_weight`, which calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target, foreign], refund, None)`, accepting whatever (unfavorable) output the skewed pool returns. [3](#0-2) 
5. Attacker reverses the initial swap, restoring the pool and capturing the spread extracted from the undervalued refund.

Unverified/uncertain: exact profitability under specific `LPFee`/pool-depth parameters of the shipped runtimes was not quantified, and it was not independently confirmed whether any wrapping code outside `refund_weight` (e.g., at the XCM executor call site) imposes a compensating check; a deeper runtime-specific analysis would be needed to bound expected attacker profit precisely.

	fn swap_exact_tokens_for_tokens(
		path: Vec<Self::AssetKind>,
		credit_in: Self::Credit,
		amount_out_min: Option<Self::Balance>,
	) -> Result<Self::Credit, (Self::Credit, DispatchError)> {
		let credit_asset = credit_in.asset();
		with_transaction(|| -> TransactionOutcome<Result<_, DispatchError>> {
			let res = Self::do_swap_exact_credit_tokens_for_tokens(path, credit_in, amount_out_min);
			match &res {
				Ok(_) => TransactionOutcome::Commit(Ok(res)),
				// wrapping `res` with `Ok`, since our `Err` doesn't satisfy the
				// `From<DispatchError>` bound of the `with_transaction` function.
				Err(_) => TransactionOutcome::Rollback(Ok(res)),
			}
		})
		// should never map an error since `with_transaction` above never returns it.
		.map_err(|_| (Self::Credit::zero(credit_asset), DispatchError::Corruption))?
	}
