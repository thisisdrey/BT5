### Title
Stale `PostponedReceiptId`/`PostponedReceipt` state survives `remove_account`, allowing a self-call-authorized receipt to execute against a re-created account - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` clears `TrieKey::Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` for an account, but never removes `TrieKey::PostponedReceiptId`, `TrieKey::PostponedReceipt`, `TrieKey::ReceivedData`, or `TrieKey::PendingDataCount` entries keyed by that account. An attacker who owns an account can leave a postponed self-call receipt outstanding, delete the account, let a victim re-register the same account name, and then deliver the missing input data to trigger execution of the stale receipt against the new account.

### Finding Description
`remove_account` in [1](#0-0)  only removes the `Account`, `ContractCode`, access-key/gas-key entries, and `ContractData` rows for `account_id`. It does not touch `TrieKey::PostponedReceiptId{receiver_id, data_id}`, `TrieKey::PostponedReceipt{receiver_id, receipt_id}`, `TrieKey::ReceivedData{receiver_id, data_id}`, or `TrieKey::PendingDataCount`, all of which are written by `set_postponed_receipt` / the input-data-arrival path defined alongside it in the same file (`set_postponed_receipt`, `remove_postponed_receipt`, `get_postponed_receipt`, see [2](#0-1) ). These columns are documented as tracking outstanding cross-contract-call data dependencies in `core/primitives/src/trie_key.rs` (`col::POSTPONED_RECEIPT_ID`, `col::POSTPONED_RECEIPT`) [3](#0-2) .

Exploit flow:
1. Attacker creates account `A` and deploys a contract they control.
2. From `A`, the attacker schedules a self-directed promise batch (e.g. `AddKey`/`DeployContract`/`Transfer` actions) whose receipt has `predecessor_id == receiver_id == A`, with `input_data_ids` referencing a result to be returned later by a second attacker-controlled contract `B`. Because `B` never returns, this receipt is postponed: the runtime writes `PostponedReceipt{receiver_id: A, receipt_id: R}`, `PostponedReceiptId{receiver_id: A, data_id: D}` and a `PendingDataCount` entry.
3. Attacker submits `DeleteAccount` on `A`. `remove_account` wipes the account/keys/contract/data but leaves the postponed-receipt bookkeeping rows in the trie untouched.
4. The account name `A` becomes available; a victim registers a new account named `A` with their own keys/contract.
5. The attacker triggers `B` to finally return its result, producing the `DataReceipt` for `data_id = D` targeting `A`. The runtime looks up the surviving `PostponedReceiptId{receiver_id: A, data_id: D}`, resolves it to receipt `R`, decrements pending-data count to zero, and executes the surviving `PostponedReceipt{receiver_id: A, receipt_id: R}` — now against the victim's freshly created account.
6. Because the stored receipt's `predecessor_id` equals its `receiver_id` (`A`), any self-call-only actions in it (e.g. `AddKey`, `DeployContract`) pass `check_actor_permissions`'s self-call authorization, even though the entity currently controlling `A` is the victim, not the attacker who originally authorized the actions.

Existing checks do not stop this because signature/nonce/access-key validation and self-call authorization are evaluated against the string `account_id`, not against a generation counter or storage-epoch identifier that would distinguish the old (attacker-owned) incarnation of `A` from the new (victim-owned) one. `DeleteAccount` has no requirement that postponed/received-data state for the account be empty before allowing deletion.

### Impact Explanation
This is an authorization-escalation bug: a receipt whose self-call actions were only ever valid against the attacker's original account instance is later executed with full self-call trust against a different party's account of the same name. Depending on the actions embedded in the postponed receipt, this can grant the attacker an access key on the victim's account, replace the victim's contract code, or transfer/drain balance the victim deposited into the new account — i.e., theft of funds or account takeover, matching NEAR's "authorization escalation across accounts" bounty category.

### Likelihood Explanation
The attacker needs only ordinary unprivileged capabilities: create two accounts, deploy contracts, submit transactions and cross-contract calls, and delete their own account — all reachable via a public RPC endpoint with no validator/node privileges. The main precondition is that the account name become available and be re-registered by a third party before the attacker chooses to resolve the pending data (which the attacker controls, since postponed receipts can remain pending indefinitely). This introduces some non-determinism (whether/when a victim re-registers the exact freed name), which lowers real-world likelihood somewhat, but the underlying state-cleanup gap is fully attacker-triggerable and repeatable on any account the attacker owns.

### Recommendation
Extend `remove_account` (or the `DeleteAccount` action handler in `runtime/runtime/src/actions.rs`) to also iterate and remove all `PostponedReceiptId`, `PostponedReceipt`, `PendingDataCount`, and `ReceivedData` trie entries prefixed by the deleted `account_id`, mirroring the existing access-key/contract-data cleanup loops. Alternatively/additionally, reject `DeleteAccount` when such pending entries exist for the account, forcing them to resolve or be explicitly purged first.

### Proof of Concept
Integration test (runtime test-loop) plan:
1. Create account `A` with a contract that issues a self-targeted promise batch (`AddFullAccessKey`) with one `input_data_id` sourced from a call to contract `B`.
2. Drive execution until `PostponedReceiptId{receiver_id: A, data_id: D}` and `PostponedReceipt{receiver_id: A, receipt_id: R}` exist in state (dump state records, confirm non-empty `POSTPONED_RECEIPT_ID`/`POSTPONED_RECEIPT` entries for `A`).
3. Submit `DeleteAccount` for `A`; dump state records again and assert the `POSTPONED_RECEIPT_ID`/`POSTPONED_RECEIPT` entries for `A` are still present (proving the gap).
4. Recreate account `A` with a fresh, victim-controlled key set.
5. Trigger `B` to return its result, producing the `DataReceipt` for `D` targeting `A`.
6. Assert that the new `A`'s access key set now contains the attacker's injected full-access key (or that the injected action otherwise executed), demonstrating unauthorized self-call action execution against the re-created account.

pub fn set_postponed_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    assert!(matches!(receipt.versioned_receipt(), VersionedReceiptEnum::Action(_)));
    let key = TrieKey::PostponedReceipt {
        receiver_id: receipt.receiver_id().clone(),
        receipt_id: *receipt.receipt_id(),
    };
    set(state_update, key, receipt);
}

pub fn remove_postponed_receipt(
    state_update: &mut TrieUpdate,
    receiver_id: &AccountId,
    receipt_id: CryptoHash,
) {
    state_update.remove(TrieKey::PostponedReceipt { receiver_id: receiver_id.clone(), receipt_id });
}

pub fn get_postponed_receipt(
    trie: &dyn TrieAccess,
    receiver_id: &AccountId,
    receipt_id: CryptoHash,
) -> Result<Option<Receipt>, StorageError> {
    get(trie, &TrieKey::PostponedReceipt { receiver_id: receiver_id.clone(), receipt_id })
}

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
