## Title
Shielded Key Material (Spending Key / `ask` / `nsk`) Accepted via GET Query Parameters in Wallet HTTP API — Plaintext Leakage in Access Logs — (File: `framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java`)

## Summary
Several full-node HTTP API endpoints that derive Sapling shielded-transaction key material accept the raw secret key as a `GET` query-string parameter (`?value=...`) instead of requiring it in a POST body. Because HTTP GET request lines (including query strings) are routinely captured verbatim by web/reverse-proxy access logs, application logs, browser history, and `Referer` headers, any deployment that fronts the node's HTTP API with a standard reverse proxy (nginx, HAProxy, load balancers) or enables request logging will persist the caller's `sk` (spending key), `ask` (spend authorizing key) or `nsk` (nullifier deriving key) in plaintext logs. This mirrors the reported bug class: sensitive secret material that should be redacted/never logged ends up embedded in log output because of how the API is designed to accept it.

## Finding Description
`GetExpandedSpendingKeyServlet.doGet` reads the caller-supplied spending key straight from the query string and passes it to `wallet.getExpandedSpendingKey`: [1](#0-0) 

`GetAkFromAskServlet.doGet` and `GetNkFromNskServlet.doGet` follow the identical pattern for `ask` and `nsk` respectively: [2](#0-1) [3](#0-2) 

All three routes are registered and reachable by any anonymous HTTP client that can reach the node's `wallet` HTTP API (no authentication is enforced by these servlets): [4](#0-3) 

Unlike POST bodies, GET query strings are:
- Logged verbatim by common reverse proxies/load balancers placed in front of the FullNode HTTP API (a standard production topology for java-tron nodes).
- Recorded in browser history / bookmarks if a wallet UI is used interactively.
- Leaked via the `Referer` header to any third-party resource loaded from the same page.

The node's own logging stack only desensitizes IP addresses in log lines via `DesensitizedConverter`, it does not redact URL query parameters or request lines: [5](#0-4) 

so nothing in-process protects this data either if any component logs the incoming request URI.

This is architecturally analogous to the reported CVE: secret material (there, `SUPABASE_API_KEY`/`TOKEN`; here, shielded spending/authorizing keys) is handled in a code path (HTTP GET parameter binding) that predictably surfaces it, unredacted, in logs outside the application's direct control.

## Impact Explanation
`sk`, `ask`, and `nsk` are the core secrets protecting Sapling shielded balances. Anyone who obtains one of these values from an access log, proxy log, or browser history can derive the full spending authority for the corresponding shielded note(s) and steal the underlying funds — an unauthorized account operation / theft of funds impact from key disclosure via a completely legitimate, unprivileged API usage pattern (no exploit of a bug in cryptography, purely an insecure transport choice for secret input).

## Likelihood Explanation
Any client (wallet software, dApp back end, integrator) that follows the documented API (`GET /wallet/getexpandedspendingkey?value=<sk>`, `GET /wallet/getakfromask?value=<ask>`, `GET /wallet/getnkfromnsk?value=<nsk>`) will place secret material in a URL. Because these are full node HTTP endpoints commonly placed behind reverse proxies/CDNs/API gateways in real deployments, and default web-server/proxy configurations log the full request line, the exposure occurs through completely normal operational practices rather than requiring an attacker-controlled state.

## Recommendation
- Remove or deprecate the `doGet` handlers for `GetExpandedSpendingKeyServlet`, `GetAkFromAskServlet`, and `GetNkFromNskServlet` (and any other shielded-key-accepting servlet using GET), forcing callers to use the existing POST variants that carry the secret in the request body.
- Add documentation/warnings that shielded key material must never be sent as URL parameters.
- Where feasible, mark these endpoints so that any node-side logging middleware excludes their request lines/query strings.

## Proof of Concept
1. Deploy a java-tron FullNode with the standard HTTP API enabled and place a reverse proxy (e.g., nginx with default access-log format `$request`) in front of it, as is common in production.
2. An unprivileged client calls:
   `GET /wallet/getexpandedspendingkey?value=<hex-encoded spending key>`
3. The reverse proxy's access log now contains the full spending key in plaintext, e.g.:
   `"GET /wallet/getexpandedspendingkey?value=1a2b3c...ff HTTP/1.1" 200 ...`
4. Anyone with read access to that log (ops staff, log aggregation SaaS, a compromised log-shipping pipeline) can extract the spending key and derive full control over the associated shielded funds.
