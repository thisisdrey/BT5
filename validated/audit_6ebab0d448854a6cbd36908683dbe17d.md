### Title
Unsigned Integer Underflow in Reftable Block Parsing Causes Out-of-Bounds Slice Panic - ([File: internal/git/reftable/reftable.go])

### Summary
`Table.parseRefBlock` and its helpers `getBlockRange`/`getVarInt`/`getRefsFromBlock` compute buffer offsets by subtracting values parsed from an on-disk reftable file without validating that the subtrahends are smaller than the minuends. Because all of these offsets are typed as unsigned `uint`, a malformed/crafted reftable causes the subtraction to wrap around to a very large value, which is then used to slice `src`, producing an out-of-bounds slice panic. This mirrors the reported "curve not monotonically increasing" bug class: a downstream computation assumes an on-disk/attacker-influenced value is well-ordered/bounded relative to another value and performs unchecked subtraction, causing an overflow/underflow instead of a proper validation error.

### Finding Description
`extractBlockLen` reads a 3-byte, attacker/file-controlled block length (`currentBS`) straight out of the reftable bytes with no lower bound check: [1](#0-0) 

That value then flows into `parseRefBlock`, which performs: [2](#0-1) 

Specifically:
- `src[blockStart+currentBS-2:]` — if `currentBS` is 0 or 1 (a valid `uint24` value the parser never rejects), `blockStart+currentBS-2` underflows the unsigned `uint`, producing a value near `math.MaxUint`, which panics when used as a slice index.
- `b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)` — `RestartCount` is a `uint16` read directly from the file footer of the block; if `3*RestartCount` exceeds `blockStart+currentBS-2`, the subtraction again underflows to a huge `uint`, which is later used as a loop bound and slice index in `getRefsFromBlock`: [3](#0-2) 

None of these values are checked to be monotonically consistent (e.g., `currentBS >= 2`, `3*RestartCount <= currentBS-2`) before being subtracted, exactly analogous to the reported curve values not being validated as monotonically increasing before `curve[n+1] - curve[n]` is computed.

### Impact Explanation
A malformed reftable file reaching `reftable.ParseTable`/`Table.GetReferences` triggers an unsigned-integer wraparound followed by an out-of-bounds slice access, which panics in Go. Reftable files are read by Gitaly's storage/housekeeping code paths (`internal/gitaly/storage/storagemgr/partition/reftable.go`, `transaction_manager_housekeeping.go`, `internal/git/stats/repository_info.go`) whenever the reftable ref backend is used. If reftable data can be introduced into a repository directory that Gitaly subsequently reads (e.g., via repository import/replication/bundle-based creation flows that place files into `.git/reftable/`), a crafted file can cause a panic in whatever goroutine performs the parse. Depending on whether that call path is wrapped by gRPC panic-recovery middleware, this results in either an RPC failing with an internal error (localized DoS) or, if it occurs in a background/maintenance goroutine without a recover(), a full process crash — a broader denial of service across the storage/partition.

### Likelihood Explanation
Reftable files are normally only written by Gitaly/Git itself via valid `git` commands, so the most straightforward attacker foothold requires a path where externally-influenced repository content (imported repository, replicated repository, or a bundle-derived repository) can populate `.git/reftable/*.ref` with attacker-chosen bytes before Gitaly's own reftable parser reads them back for reference listing or housekeeping. Given the values involved (`currentBS`, `RestartCount`) are compact and simple to control if raw file placement is achievable, exploitation of the parser itself is straightforward once such a file is reachable; the main uncertainty is confirming an existing import/replication code path that allows attacker control over raw file bytes placed into a repository's `reftable` directory rather than through validated `git` commands.

### Recommendation
Before performing any subtraction on values derived from the reftable file, validate that they satisfy the invariants the format assumes:
- Reject blocks where `currentBS < 2` (or below whatever the documented minimum block size is) in `parseRefBlock`.
- Validate `3*uint(b.RestartCount) <= (currentBS - 2)` before computing `RestartStart`, returning a parse error otherwise.
- Add an explicit bounds/underflow check (e.g., using `math/bits.Sub` or comparing operands first) anywhere a `uint` subtraction is performed on values sourced from `getVarInt`, `extractBlockLen`, or `RestartCount`, mirroring the guard already present in `getBlockRange` for the `offset >= t.footerOffset` case.
- Ensure any goroutine invoking the reftable parser (`ParseTable`, `GetReferences`) is wrapped with panic recovery so a malformed file cannot crash the process, in addition to fixing the root-cause validation.

### Proof of Concept
1. Construct a reftable file with a valid header/footer (magic `REFT`, valid version, valid HashID, correct CRC32 in the footer) so that `ParseTable` succeeds.
2. In the first ref block (`'r'` type block), set the 3-byte block length field (parsed by `extractBlockLen`) to `0x000000` or `0x000001`.
3. Call `Table.GetReferences()` (reachable via `internal/gitaly/storage/storagemgr/partition/reftable.go` / `internal/git/stats/repository_info.go` code paths that read reftables from a repository directory).
4. In `parseRefBlock`, `blockStart+currentBS-2` underflows (`uint` wraps to near `MaxUint`), and `src[blockStart+currentBS-2:]` panics with `runtime error: slice bounds out of range`, crashing the parsing goroutine.

```go
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
```
