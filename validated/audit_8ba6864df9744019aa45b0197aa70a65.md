### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule` from/to-account lists enables unbounded-loop DoS during legacy-index migration - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource` (legacy resource-delegation path) appends to an account's `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` with no size limit, and later, the one-time migration routine `DelegatedResourceAccountIndexStore.convert()` iterates the entire list synchronously inside a single transaction's `execute()`. An attacker can grow this list arbitrarily large across many cheap, fee-free transactions, then trigger `convert()` to force an unbounded loop to execute within one transaction, degrading block-processing performance for every node that applies that block — the same bug class as the reported `UXDController.assetList` / `UXDRouter._depositoriesForAsset` unbounded loops.

### Finding Description
When `FreezeBalanceContract` delegates resources to a `receiverAddress` and `dynamicStore.supportAllowDelegateOptimization()` is false, `FreezeBalanceActuator.delegateResource` unconditionally appends new entries to the owner's/receiver's `DelegatedResourceAccountIndexCapsule` lists with no upper bound check: [1](#0-0) 

`addToAccount`/`addFromAccount` simply append protobuf list entries with no cap: [2](#0-1) 

Both `FreezeBalanceActuator.calcFee()` and `DelegateResourceActuator.calcFee()` return `0`, meaning list growth costs nothing beyond bandwidth for repeated small-value freeze/delegate transactions to a large number of distinct receiver addresses: [3](#0-2) 

Later, once the committee activates `supportAllowDelegateOptimization`, the very next `delegateResource()` call involving that same address calls `DelegatedResourceAccountIndexStore.convert(address)`, which reads the entire legacy `toList`/`fromList` and, for every element, performs a full `delegate()` call (two additional store `put()`s each) — an unbounded loop executed synchronously inside a single transaction's `execute()`: [4](#0-3) [5](#0-4) 

Because Actuator execution (unlike TVM opcode execution) is not metered by per-step energy/gas, there is no mechanism to bound or charge for the cost of this loop proportional to its size, so an attacker-inflated list directly translates into unbounded synchronous work performed while every full node applies the block containing the triggering transaction.

### Impact Explanation
An attacker can pre-build an arbitrarily large `toAccountsList`/`fromAccountsList` for an account under their control via many cheap `FreezeBalanceContract` (delegate) transactions before or while `supportAllowDelegateOptimization` is disabled, at effectively zero protocol fee. When the network subsequently enables `supportAllowDelegateOptimization` (an eventual, planned upgrade path), the attacker (or anyone interacting with that address via delegate/freeze) can trigger `convert()`, forcing every full node to perform the full O(n) migration synchronously while applying that single block. With a sufficiently large N this can significantly slow down or stall block processing for the entire network — a node availability / consensus-liveness impact consistent with the "Medium" unbounded-loop class in the source report.

### Likelihood Explanation
Reachability requires only unprivileged, ordinary `FreezeBalanceContract` transactions (broadcastable by any account holder) to inflate the list, and a single subsequent delegate/freeze transaction to trigger the migration. The only external dependency is that the committee-controlled `supportAllowDelegateOptimization` parameter transitions to enabled — a normal, expected chain-upgrade event, not an attacker privilege. The lack of any cap on list growth, combined with zero delegation fee, makes the precondition (an oversized list) trivially attainable in advance.

### Recommendation
Enforce a maximum size for `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` in `FreezeBalanceActuator.delegateResource` (rejecting further delegation once the limit is reached), and/or change `DelegatedResourceAccountIndexStore.convert()` to migrate entries incrementally (e.g., lazily on lookup, or batched across multiple blocks/transactions) rather than in a single unbounded loop performed inside one transaction's execution.

### Proof of Concept
1. Attacker controls address `A` with minimal TRX balance.
2. While `supportAllowDelegateOptimization` is disabled, submit N `FreezeBalanceContract` transactions from `A`, each freezing a minimal amount of BANDWIDTH/ENERGY and delegating to a distinct freshly-generated `receiverAddress_i` (i = 1..N). Each call appends one entry to `A`'s `toAccountsList` via `FreezeBalanceActuator.delegateResource` (lines 328–332) with no size check, and each corresponding receiver gets one `fromAccountsList` entry — cost is only bandwidth, since `calcFee()` returns 0.
3. Repeat over enough blocks to build N into the hundreds of thousands.
4. Once the committee proposal enabling `supportAllowDelegateOptimization` activates, submit one more `FreezeBalanceContract`/`DelegateResourceContract` transaction involving address `A`.
5. `FreezeBalanceActuator.delegateResource` calls `delegatedResourceAccountIndexStore.convert(A)`, which iterates all N stored entries and performs 2×N `put()` operations synchronously inside `execute()` for this single transaction, causing significant processing delay for all nodes validating/applying the containing block.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
