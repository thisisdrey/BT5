## Analysis

The Shim CVE-2023-40551 bug class is: a binary parser trusts an attacker-controlled length/offset field taken from the file and uses it to index into a buffer without checking that the resulting index stays inside the buffer, causing an out-of-bounds read.

The closest reachable analog in java-tron is the "dynamic bytes array" decoder used by the `ValidateMultiSign` / `BatchValidateSign` TVM precompiles, which parse attacker-controlled `bytes[]` ABI parameters out of a `DataWord[]` array built directly from the raw call data.

### Title
Out-of-bounds `DataWord[]` read when decoding attacker-controlled offset/length fields in `PrecompiledContracts.extractBytesArray`/`extractSigArray` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign` (precompile address `0x0a`) and `BatchValidateSign` (`0x09`) decode a `bytes[]` ABI parameter from the raw TVM call-data by parsing it into a `DataWord[]` array and then following an attacker-supplied "array length" word to iterate over further attacker-supplied "offset"/"length" words. The bounds check that exists only validates the *initial* array-header offset, not the derived indices used inside the decoding loop, so a crafted transaction can drive `words[offset + i + 1]` past the end of the `DataWord[]` array.

### Finding Description
`extractBytesArray` and `extractSigArray` are used to decode the `bytes[] signatures` parameter for these precompiles: [1](#0-0) 

```
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  for (int i = 0; i < len; i++) {
    int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
    int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
    bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen);
  }
  return bytesArray;
}
```

The only bound check performed is on the initial `offset` value (`offset > words.length - 1`). The subsequent `len` value is read from `words[offset]` and is fully attacker controlled (it is the "array length" word of the ABI encoding). The loop then indexes `words[offset + i + 1]` for `i` up to `len - 1` with **no check that `offset + len` stays within `words.length`**. `extractSigArray` has the identical pattern: [2](#0-1) 

Both are invoked from `ValidateMultiSign.execute()`: [3](#0-2) 

Note that this call happens **before** the only `try { ... } catch (Throwable t) { ... }` block in the method (which only wraps the later permission/weight logic), so an `ArrayIndexOutOfBoundsException` thrown inside `extractBytesArray`/`extractSigArray` propagates directly out of `execute()`.

The `isValidAbiEncoding` guard that was added (apparently as part of the TIP-854 hardening visible in the test suite) only validates that the **overall byte length** of the call data is congruent with `headerWords + n*itemWords` words: [4](#0-3) 

This check constrains the *total size* of the data, but it does **not** constrain the *value* of the length word read at `words[offset]` inside `extractBytesArray`, nor does it force the dynamic array's declared length to match the actual number of words available after `offset`. An attacker can therefore submit call data that is "shape-valid" (passes `isValidAbiEncoding`) but whose `bytes[]` header word encodes an arbitrarily large `len`, driving the decode loop to read past the end of the `DataWord[] words` array.

### Impact Explanation
Any account can trigger this by issuing a `TriggerSmartContract` transaction (or having any contract perform a `CALL`/`STATICCALL`) to the `validatemultisign`/`batchvalidatesign` precompile addresses with crafted call data. The resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` is thrown from inside `PrecompiledContract.execute()` outside of any local catch in `ValidateMultiSign`, so its containment depends entirely on the generic exception handling in the VM interpreter loop (`VM.play`) and `Program.callToPrecompiledAddress`. If that generic handling does not fully absorb it for this specific call path, the failure surfaces as an uncontrolled runtime exception during block/transaction application in `Manager`, which is the java-tron analog of the Shim OOB-read leading to a crash during a security-critical processing phase. At minimum this is a reliable, cheap DoS/crash primitive reachable by any unprivileged transaction broadcaster or contract deployer; at worst (if any code path executes this during block application without full containment) it can affect node availability/consensus.

### Likelihood Explanation
High: the input is fully attacker-controlled TVM call data, no special privilege or timing is required, and the vulnerable code is on the hot path for two precompiles that any signed transaction (a `TriggerSmartContract` calling a helper contract that does `CALL`) can reach. The recently added `isValidAbiEncoding` guard (TIP-854) demonstrates the authors are aware of and actively hardening this exact decoding surface for shape-level malformed input, but the length-word/offset-value bound gap in `extractBytesArray`/`extractSigArray` themselves appears unaddressed by that guard.

### Recommendation
In `extractBytesArray` and `extractSigArray`, after reading `len = words[offset].intValueSafe()`, validate that `offset + len < words.length` (and that `len >= 0`) before allocating `bytesArray` or entering the loop, and similarly bound-check `offset + bytesOffset + 1` before dereferencing `words[...]` in each iteration. Return `new byte[0][]` (as already done for the initial `offset` case) whenever any derived index would exceed `words.length`.

### Proof of Concept
1. Craft ABI call data for `validatemultisign(address,uint256,bytes32,bytes[])` such that:
   - The static head (`address`, `permissionId`, `hash`, dynamic-offset word) is well-formed and `words[3]` points to a valid in-bounds header word `offset`.
   - `words[offset]` (the declared `bytes[]` length) is set to a large value, e.g. `0x7fffffff`, while the actual call data only contains a few trailing words.
   - The total byte length of the call data is kept congruent with `(5 + n*5)*32` for some small `n` so it passes `isValidAbiEncoding`, while `n` (declared) at `words[offset]` is set independently to a large value larger than `words.length`.
2. Send this data via a `TriggerSmartContract` transaction (or a contract that `CALL`s address `0x...a`).
3. During `extractBytesArray`'s loop, `words[offset + i + 1]` will be accessed once `i` exceeds the real array bounds, throwing `ArrayIndexOutOfBoundsException` out of `ValidateMultiSign.execute()`, uncaught by any local handler in that method.

  private static boolean isValidAbiEncoding(byte[] data, int headerWords, int itemWords) {
    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));
    return tail > 0 && tail % multiplyExact(itemWords, WORD_SIZE) == 0;
  }
