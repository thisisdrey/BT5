### Title
`simulate_intents` returns a non-throwing "success" result for batches that `execute_intents` will always panic on — ([File: contracts/defuse/src/contract/intents/mod.rs])

### Summary
`simulate_intents` and `execute_intents` do not treat `DefuseError::InvariantViolated` the same way: `execute_intents` always panics (aborting the whole transaction) on any `Err`, while `simulate_intents` explicitly swallows `InvariantViolated` and returns it as a normal, non-throwing `SimulationOutput` value. A caller that treats "the view call returned/did not throw" as "this batch is executable" (rather than inspecting the `invariant_violated` field) will be misled about whether `execute_intents` will succeed for the identical batch.

### Finding Description
The binding under test is: *for the same batch and block, the outcome `simulate_intents` reports == the outcome `execute_intents` produces*.

`execute_intents` unconditionally panics on any engine error: [1](#0-0) 

`simulate_intents`, however, special-cases exactly one error variant, `DefuseError::InvariantViolated`, and returns it as ordinary struct data instead of panicking, while every other error still panics identically to `execute_intents`: [2](#0-1) 

`InvariantViolated` is produced by `TransferMatcher::finalize()` inside `Deltas::finalize()` whenever the accumulated deltas from `TokenDiff`/transfer intents in the batch do not net to zero (unmatched deposits/withdrawals or overflow): [3](#0-2) [4](#0-3) 

An attacker/solver can construct a probe batch (e.g., a single-sided `TokenDiff` intent that is not matched by any opposite leg) against a victim account that has no stored entry yet. Because `simulate_intents` runs on `self.cached()` (a `CachedState` wrapper) rather than directly on `Contract`, and lazily materializes accounts via `get_or_create` in `internal_sub_balance`/`internal_add_balance` instead of the direct `Contract::internal_sub_balance`, which returns `DefuseError::AccountNotFound` for a non-existent account: [5](#0-4) [6](#0-5) 

the two state implementations do not fail through identical error paths for a fresh account, and — more importantly for the "success" divergence — `simulate_intents` returns a normally-constructed `SimulationOutput` (function call succeeds, no panic) with `invariant_violated: Some(...)` for a batch that `execute_intents` will unconditionally panic (and thus fully revert) on. From the point of view of any caller that only checks "did the RPC view call throw," these two outcomes diverge: `simulate_intents` "succeeds," `execute_intents` reverts.

### Impact Explanation
Because NEAR reverts all state changes on a contract panic, `execute_intents` panicking on an unmatched/invariant-violating batch cannot itself move any custodied funds — no partial execution occurs. The actual exposure is therefore not a direct on-chain fund transfer bug, but a false-quote scenario: a relayer or counter-party solver who calls `simulate_intents` and only checks for a thrown error (rather than the `invariant_violated` field) can be led to believe a batch will settle, take real-world/off-chain action (e.g., releasing assets, quoting a price, committing capital) on that belief, and then find that `execute_intents` reverts entirely for the identical batch. This matches the rules' High-severity category: "`simulate_intents` reporting an outcome `execute_intents` does not produce when a party settles on that report." It is repeatable for any batch/account combination that produces unmatched deltas, and costs the attacker nothing (a single `simulate_intents` view call).

### Likelihood Explanation
No privileged role is required; any unprivileged party can call `simulate_intents` with an arbitrary `MultiPayload` batch including a single unmatched `TokenDiff`/transfer intent against a fresh victim account. The precondition (victim has no stored account entry) is trivial to satisfy and not even strictly necessary — any unmatched-delta batch triggers the divergence. The cost is one view call; the "harm" materializes only if a downstream party's tooling treats a non-throwing `simulate_intents` result as proof of executability without inspecting `invariant_violated`.

### Recommendation
Make `simulate_intents`'s success/failure signaling consistent with `execute_intents`: either (a) document/enforce that any consumer MUST treat `invariant_violated.is_some()` as equivalent to a would-be panic (i.e., "not executable"), or (b) have `simulate_intents` also fail loudly (e.g., return a `Result`/explicit error field with an unmistakable non-success discriminant, or panic in a distinguishable simulation-only error mode) so that naive "did the call throw" checks by relayers/solvers cannot mistake an unmatched batch for a settleable one. Additionally, align `CachedState`'s balance-mutation account creation semantics with `Contract`'s `AccountNotFound` behavior for non-existent accounts so error surfaces match between the two code paths.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let account = self
            .accounts
            .get_or_create(owner_id.to_owned(), |owner_id| {
                self.view.is_account_locked(owner_id)
            })
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;
        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            if account.token_amounts.get(&token_id).is_none() {
                account
                    .token_amounts
                    .add(token_id.clone(), self.view.balance_of(owner_id, &token_id))
                    .ok_or(DefuseError::BalanceOverflow)?;
            }
            account
                .token_amounts
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }
        Ok(())
    }
