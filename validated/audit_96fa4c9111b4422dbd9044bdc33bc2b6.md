Audit Report

## Title
Snowbridge relayer reward is irreversibly cleared on successful XCM *send* rather than confirmed settlement on AssetHub - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`pallet_bridge_relayers::do_claim_rewards` deletes a relayer's `RelayerRewards` entry via `try_mutate_exists`/`maybe_reward.take()` as soon as `T::PaymentProcedure::pay_reward` returns `Ok(())`. For `BridgeReward::Snowbridge`, that implementation (`PayAccountOnLocation::pay_reward`) never transfers value locally — it only validates, charges local delivery fees, and hands an `UnpaidExecution` XCM to the outbound queue, returning `Ok(())` on successful *send*, not on confirmed *execution/settlement* on AssetHub.

## Finding Description
`do_claim_rewards` takes the reward balance out of storage and treats a successful `pay_reward` call as final proof of payout, permanently deleting the record on `Ok(())`: [1](#0-0) . For the Snowbridge reward kind, `pay_reward` builds an XCM containing `UnpaidExecution`, `DescendOrigin`, `UniversalOrigin(GlobalConsensus(Ethereum))`, `ReserveAssetDeposited`, and `DepositAsset`, then calls `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver` — success here means only "accepted by the local XCM sender for delivery," not "executed and credited on AssetHub": [2](#0-1) . There is no message id, receipt, or query-based confirmation retained on BridgeHub to verify or roll back settlement if the destination-side execution fails (e.g., barrier rejection of `UnpaidExecution` for that origin, a malformed `beneficiary` `Location` that traps the deposit, or reserve-trust misconfiguration on AssetHub). The `try_mutate_exists` guard only protects against synchronous local failures (captured by `Err` from `pay_reward`); it structurally cannot detect or compensate for asynchronous remote failures, since the local call has already returned `Ok(())` by the time delivery to AssetHub happens.

## Impact Explanation
This matches the allowed impact class "duplicate settlement or payout, permanent user-fund or bridge-state lock." The relayer's earned reward, recorded in `RelayerRewards`, can be permanently erased without the beneficiary ever being credited on AssetHub, and there is no recovery path (`NoRewardForRelayer` is returned on any subsequent claim attempt) — a genuine architectural violation of the "advance payout state only after execution/settlement succeeds atomically" pivot.

## Likelihood Explanation
No privileged actor or compromised infrastructure is required. Any unprivileged relayer calling the permissionless `claim_rewards_to` extrinsic combined with any ordinary post-send failure condition on the AssetHub side (barrier/config drift, malformed-but-valid-looking beneficiary, reserve-trust misalignment) triggers the loss — an architectural gap between "send success" and "settlement success," not attacker-controlled exploitation of privileged code.

## Recommendation
Do not treat `deliver()` success as final settlement. Retain the reward entry (or a pending/receipt marker) until an explicit execution confirmation/callback from AssetHub is received (e.g., using a two-phase `PayOverXcm`-style `check_payment`/query-id pattern), with a compensating path to re-credit `RelayerRewards` if the remote message is dropped, trapped, or fails execution.

## Proof of Concept
1. Relayer accrues reward for `BridgeReward::Snowbridge` via `register_reward`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(some_location))`.
3. `PayAccountOnLocation::pay_reward` validates/charges fees/delivers the XCM and returns `Ok(())`; `do_claim_rewards` deletes the `RelayerRewards` entry: [3](#0-2) .
4. On AssetHub, `UnpaidExecution`/`ReserveAssetDeposited`/`DepositAsset` fails to execute (barrier disallows unpaid execution for that origin, or `some_location` doesn't decode to a depositable beneficiary), so no funds are ever credited.
5. Relayer calls `claim_rewards_to` again and receives `Error::NoRewardForRelayer` — the reward is permanently lost with no funds delivered, consistent with the existing test showing that `claim_rewards_to` failures are only caught for local/synchronous conditions, confirming send and settlement are decoupled and unguarded: [4](#0-3) .

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
