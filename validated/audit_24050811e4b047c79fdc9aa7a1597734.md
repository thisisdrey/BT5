Based on the evidence gathered, I found a concrete conservation-invariant break analogous to the report's "aggregate accounting never updated on one path" bug class.

### Title
`total_supplies` is never updated when balances change via intent execution (`internal_add_balance`/`internal_sub_balance`/`mint`/`burn`), breaking the supply-vs-balances invariant and permanently corrupting NFT deposit-guard and `mt_supply` accounting - (File: `contracts/defuse/src/contract/intents/state.rs`)

### Summary
The Verifier tracks a per-token `total_supplies` ledger in `ContractState` [1](#0-0) , which is correctly incremented/decremented only in the raw `deposit`/`withdraw` helpers [2](#0-1) [3](#0-2) . However, the `State` trait implementation used during intent execution (`internal_sub_balance`, and by symmetry `internal_add_balance`) in `contracts/defuse/src/contract/intents/state.rs` only mutates the owner's `token_balances` and never touches `self.storage.state.total_supplies`: [4](#0-3) .

### Finding Description
`ft_withdraw`/`nft_withdraw`/`mt_withdraw`/`native_withdraw`/`TokenDiff`/`mint`/`burn`/`imt_mint`/`imt_burn` intents all route through the `State` trait's `internal_add_balance`/`internal_sub_balance` methods (see the `Deltas<S>` wrapper forwarding to the underlying state at [5](#0-4) , and the concrete contract-level implementation at `contracts/defuse/src/contract/intents/state.rs:171-195`). That implementation adjusts only the account's `token_balances` map and never calls `self.storage.state.total_supplies.add`/`.sub`, unlike the separate `deposit`/`withdraw` contract methods in `contracts/defuse/src/contract/tokens/mod.rs` which do keep `total_supplies` in sync [6](#0-5) .

This breaks the invariant: `sum(token_balances for token X across accounts) == total_supplies[X]`. Concretely:
- `mt_supply`/`mt_batch_supply` read directly from `total_supplies` [7](#0-6) , so they will silently diverge from real aggregate balances once any `ft_withdraw`/`TokenDiff`/`mint`/`burn` intent executes without a corresponding `total_supplies` change.
- The NFT single-deposit guard in `deposit()` relies on `total_supply > 1` to reject double-deposits of a NEP-171 NFT [8](#0-7) . Because `total_supplies` is never decremented when an NFT balance is removed via intent-driven `nft_withdraw`/`burn`/`mint`(transfer)-style operations that go through `contract/intents/state.rs`, this guard's tracked value stays stale/inflated relative to actual custody, corrupting the deposit-uniqueness bookkeeping for that `TokenId`.

This is the same bug class as the FairSide finding: an aggregate/global accounting counter (`fscAddress`'s conviction score / here, `total_supplies`) is updated on only one code path (deposit/withdraw contract calls) but not the other (intent-driven internal balance mutations), causing the aggregate ledger to permanently diverge from the sum of individual balances.

### Impact Explanation
This does not directly move funds, but it corrupts a value that other logic depends on for correctness (`mt_supply` reporting and the NFT re-deposit guard). A corrupted, monotonically-diverging `total_supplies` for NEP-171 tokens can incorrectly permit or block re-deposits of the "same" NFT `token_id`, and `mt_supply`/`mt_batch_supply` (part of the public NEP-245 view API relied upon by integrators/relayers) will report incorrect aggregate figures indefinitely, since there is no mechanism to resynchronize `total_supplies` with actual balances once it diverges.

### Likelihood Explanation
High likelihood of being triggered: `internal_sub_balance`/`internal_add_balance` in `contracts/defuse/src/contract/intents/state.rs` are the standard path invoked by essentially every intent (`FtWithdraw`, `NftWithdraw`, `MtWithdraw`, `NativeWithdraw`, `TokenDiff`, `Mint`/`Burn`, `ImtMint`/`ImtBurn`) executed via `execute_intents`/`simulate_intents`, so divergence begins on the very first non-`deposit`/`withdraw`-helper-based state change performed by any user.

### Recommendation
Update `contracts/defuse/src/contract/intents/state.rs`'s `internal_add_balance`/`internal_sub_balance` (and any `mint`/`burn` implementations that don't route through `deposit`/`withdraw`) to also apply the corresponding delta to `self.storage.state.total_supplies`, mirroring what `contracts/defuse/src/contract/tokens/mod.rs`'s `deposit`/`withdraw` already do, so `total_supplies` always equals the sum of individual account balances for every token.

### Proof of Concept
1. A user deposits an NFT via `nft_on_transfer`, going through `deposit()`, which sets `total_supplies[nft_token_id] = 1` [9](#0-8) .
2. The user signs and executes an `NftWithdraw` intent, which is handled via `State::nft_withdraw` → `internal_sub_balance` in `contracts/defuse/src/contract/intents/state.rs:171-195`, which decrements the owner's `token_balances` but leaves `total_supplies[nft_token_id]` at `1`.
3. `mt_supply`/`mt_batch_supply` for that token id still report `1`, even though no account holds the NFT anymore, and any future `deposit()` call on the same `token_id` will see the pre-existing `total_supply` value (now already `1` before the add), causing `total_supply > 1` and the `NftAlreadyDeposited` guard to incorrectly fire despite the token having been fully withdrawn — an unintended, permanent denial of legitimate re-deposit for that `TokenId`, while `mt_supply` remains permanently wrong for every token routed only through intent execution.

mod imt;

use super::Contract;
use defuse_core::{DefuseError, Lock, Result, token_id::TokenId};
use defuse_near_utils::{REFUND_MEMO, promise_result_checked_json_with_len};
use defuse_nep245::{MtBurnEvent, MtEvent, MtMintEvent};
use itertools::{Either, Itertools};
use near_sdk::{AccountId, AccountIdRef, FunctionError, Gas, env, json_types::U128};
use std::borrow::Cow;

pub const STORAGE_DEPOSIT_GAS: Gas = Gas::from_tgas(10);

impl Contract {
    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        if !mint_event.amounts.is_empty() {
            MtEvent::MtMint([mint_event].as_slice().into())
                .check_refund()?
                .emit();
        }

        Ok(())
    }

    pub(crate) fn withdraw(
        &mut self,
        owner_id: &AccountIdRef,
        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<impl Into<String>>,
        force: bool,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        // Schedule to emit `mt_burn` events only in the end of tx
        // to avoid confusion when `mt_burn` occurs before relevant
        // `mt_transfer` arrives. This can happen due to postponed
        // delta-matching during intents execution.
        if !burn_event.amounts.is_empty() {
            self.runtime.postponed_burns.mt_burn(burn_event);
        }

        Ok(())
    }
}

    fn internal_add_balance(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        for (token_id, amount) in tokens {
            self.state
                .internal_add_balance(owner_id.clone(), [(token_id.clone(), amount)])?;
            if !self.deltas.deposit(owner_id.clone(), token_id, amount) {
                return Err(DefuseError::BalanceOverflow);
            }
        }
        Ok(())
    }

        &mut self,
        owner_id: &AccountIdRef,

    ) -> Result<()> {

            self.state
                .internal_sub_balance(owner_id, [(token_id.clone(), amount)])?;
