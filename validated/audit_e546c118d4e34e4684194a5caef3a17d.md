### Title
Deleted-and-recreated account inherits attacker-controlled postponed receipts, causing authorization escalation across accounts - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for an account, but never clears any `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries scoped to that `account_id`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) relies exclusively on `remove_account` for cleanup before nulling out the `Account` object, so a receipt that was postponed on the account before deletion survives the deletion untouched.

### Finding Description
When a contract issues a promise with multiple input data dependencies targeting itself, the runtime persists the pending `ActionReceipt` under `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`, all keyed only by `receiver_id` (the account id) and `receipt_id`/`data_id`, with no notion of "account generation" (`runtime/runtime/src/lib.rs:1398-1455`).

If the account is deleted via `DeleteAccountAction` while one of the two data dependencies is still outstanding, `action_delete_account` calls `remove_account` (`runtime/runtime/src/actions.rs:371`), which deletes `Account`, `ContractCode`, `AccessKey`/gas-key entries, and `ContractData`, but does not touch `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` (`core/store/src/utils/mod.rs:509-573`). The account object is then set to `None` (`runtime/runtime/src/actions.rs:388`), but the postponed receipt and its bookkeeping remain live in the trie under the same `AccountId` prefix.

If an unprivileged party then submits `CreateAccountAction` for the exact same `AccountId`, a fresh `Account` record is created at that trie prefix — but the leftover `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries from the old owner are not part of the newly-created account's state and are not cleared by account creation either. When the withheld `DataReceipt` for that `data_id` eventually arrives, `process_receipt` looks up `TrieKey::PostponedReceiptId` by `receiver_id`+`data_id` (`runtime/runtime/src/lib.rs:1398-1410`), finds the stale entry, decrements `PendingDataCount` to zero, fetches the original postponed `ActionReceipt` via `get_postponed_receipt` (`runtime/runtime/src/lib.rs:1430-1437`), and executes it via `apply_action_receipt` against the account that now belongs to a different owner (`runtime/runtime/src/lib.rs:1442-1455`).

Because the postponed `ActionReceipt`'s actions (e.g. `AddKey`, `FunctionCall`, `Transfer`) were authored by the original account/contract before deletion, they now execute with `receiver_id` bound to the new account's state, without any check that the promise's original context still matches the account that currently occupies that `AccountId`. This is an authorization escalation: the resumed receipt was never authorized by the new account owner, yet the runtime applies actions from it against the new account's state, root, and balances.

### Impact Explanation
This is an authorization escalation across accounts: a postponed receipt created by the old owner of an `AccountId` executes against a re-created account controlled by an unrelated party, potentially allowing the original owner (or an attacker who colludes with the deletion path) to add access keys or transfer funds into/out of the new account's context. This falls under "authorization escalation across accounts or promises," matching the corresponding NEAR bounty category for privilege-boundary violations across account identities.

### Likelihood Explanation
The preconditions require: a funded account with a contract capable of issuing a two-dependency self-promise, delivering one `DataReceipt` while withholding the other, then deleting the account before the second data item arrives, and having a third party recreate the identical `AccountId`. All of these steps are reachable by an unprivileged actor using ordinary transactions (`FunctionCall`, `DeleteAccount`, `CreateAccount`) with no special permissions. One aspect that could not be fully confirmed from the available context is whether `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` check in `action_delete_account` (`runtime/runtime/src/actions.rs:326-353`) would block deletion if the postponed receipt materially inflates `account.storage_usage()`; since the attacker fully controls the size/content of the postponed receipt, they can keep it minimal to stay under this threshold, but this interaction was not independently verified against the storage-usage accounting code for postponed receipts.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also iterate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries scoped to the deleted `account_id` (mirroring the existing access-key/contract-data iteration and removal pattern), so that no postponed cross-shard state survives account deletion. Alternatively, disallow `DeleteAccountAction` from succeeding while any postponed receipt or pending data count exists for that account, forcing settlement of all outstanding promises before deletion is permitted.

### Proof of Concept
Runtime integration test (test-loop or `runtime/runtime/src/tests/apply.rs` style):
1. Deploy a contract to `victim.near` that, on call, creates a promise-with-2-input-data-ids receipt targeting itself, with an action list containing e.g. `AddKey(full_access_key)`.
2. Execute the call so the `ActionReceipt` is stored via `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`; deliver exactly one of the two `DataReceipt`s, leaving `PendingDataCount == 1`.
3. Submit a `DeleteAccountAction` on `victim.near` with `beneficiary_id = attacker.near`, and apply it; assert the account is removed but assert (via raw trie inspection) that `TrieKey::PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries for `victim.near` still exist in the state.
4. Submit `CreateAccountAction` for `victim.near` funded by an unrelated party (`new_owner.near`), transferring in fresh balance and setting a new access key.
5. Deliver the second, previously withheld `DataReceipt` for the pending `data_id`.
6. Assert that the postponed receipt executes against the newly created `victim.near` account — e.g., assert that the `AddKey` action from the stale postponed receipt succeeds and a full access key now exists on `new_owner`'s freshly created `victim.near` account, despite `new_owner` never having authorized it. This confirms authorization escalation across the account boundary caused by the incomplete cleanup in `remove_account`.
