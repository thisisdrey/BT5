### Title
Check/Update TOCTOU race in `ConnectionState.Decrypt` allows accepted replay of a packet counter during the unlocked `DecryptDanger` gap - ([File: connection_state.go])

### Summary
`Decrypt` releases `decryptLock` between `window.Check` and `window.Update`, and the release is also present around `DecryptDanger` itself. Two packets `i` and `i+1` can race so that `Update(i+1)` (a jump-path update) commits and clears the bit for `i` before `Update(i)` commits, momentarily marking slot `i` as unset even though packet `i`'s decrypt is already in flight. A duplicate/replayed copy of packet `i` arriving in that narrow window sees `Check(i)` return true and is accepted a second time.

### Finding Description
`ConnectionState.Decrypt` does: `Check` under `decryptLock` → unlock → `DecryptDanger` (no lock) → lock → `Update` → unlock [1](#0-0) . `Bits.Update`'s jump path (`updateSlow`) clears the range between the previous `current` and the new `i`, marking any bit in that span as "lost" unless explicitly set, then sets only the final index and advances `current` [2](#0-1) . If two concurrent `Decrypt` calls for counters `i` and `i+1` interleave such that `Update(i+1)` runs as a jump (because `current` is still `i-1` when it executes) before `Update(i)` commits, `clearRange` clears the slot for `i` and `Update(i)`'s own eventual call will re-set it and return `true` — i.e. `Update(i)` behaves as if `i` were a fresh arrival regardless of order. Crucially, during the gap between `Update(i+1)`'s commit (bit `i` cleared, `current = i+1`) and `Update(i)`'s commit (bit `i` re-set), `Bits.Check(l, i)` — called by any other concurrently-arriving packet claiming counter `i` — sees `strictlyWithinWindow(i)` true and `get(i)` false, so it returns `true`, treating a duplicate of `i` as new/unset. If a duplicate ciphertext for counter `i` (a captured/replayed copy of the legitimate packet) arrives in that window, it passes `Check`, passes `DecryptDanger` (since it's byte-identical to a validly-authenticated packet), and is delivered as new payload data a second time.

### Impact Explanation
This is a bounded replay: it does not break AEAD authentication or allow forging arbitrary content (the attacker still needs a byte-identical previously-valid ciphertext for counter `i`, which requires either observing genuine traffic or reusing a packet an attacker under this threat model would already need cryptographic material for). The exploitable outcome is duplicate delivery/acceptance of a single already-authenticated packet during a narrow concurrency window, i.e., an anti-replay-window bypass for one packet, not a full decryption/forgery oracle. This matches a "traffic replay" style impact but is limited in blast radius (single duplicate delivery per race, not a systemic decrypt bypass).

### Likelihood Explanation
Exploitation requires: (1) the attacker to possess a genuine, previously-authenticated ciphertext for a specific counter `i` (i.e., prior observation of traffic, since no keys are available), (2) precise timing to get worker goroutines to process `i` and `i+1` such that `Update(i+1)`'s jump-path commits before `Update(i)`'s update commits, and (3) injecting the duplicate of `i` inside that narrow window between the two `Update` calls. This is a genuine, code-verifiable race (the lock is provably released around `DecryptDanger`), but the window is small (bounded by one AEAD decrypt's duration) and requires favorable goroutine scheduling plus prior packet capture, making real-world exploitation difficult but not theoretically impossible under the stated concurrency-stress-test PoC.

### Recommendation
Do not release `decryptLock` between `Check` and `Update` for the same packet, or restructure so that the replay-window commit for counter `i` (i.e., reserving/marking `i` as "in flight") happens atomically with `Check`, with `Update` only finalizing/rolling back on decrypt failure — e.g., mark the bit optimistically at `Check` time under the lock (treating it as consumed) and only clear it back out if `DecryptDanger` fails, rather than deferring the set until after decrypt completes.

### Proof of Concept
Concurrency stress test in `bits_test.go`/`connection_state_test.go`:
1. Spawn goroutines calling `ConnectionState.Decrypt` (or directly `window.Check`/`window.Update`) for counters `i`, `i+1`, and a duplicate of `i`, with an artificial delay inserted between `Check` and `Update` for counter `i` to simulate the `DecryptDanger` gap.
2. Release counter `i+1`'s goroutine to run its full `Check`→`Update` cycle first (jump path), then release the duplicate `i` goroutine's `Check` call before the original `i` goroutine's `Update(i)` commits.
3. Assert that the duplicate `i`'s `Check` call returns `false` (rejected as replay) in a correct implementation; the current implementation returns `true`, and both the original and duplicate `Update(i)` calls return `true`, proving two acceptances of the same counter — run with `go test -race` to also confirm the interleaving is a genuine data race across goroutines rather than serialized access.

func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}
