### Title
Unbounded git-clone in CreateRepositoryFromURL enables indefinite handler hang and resource exhaustion - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`CreateRepositoryFromURL` clones from a caller-supplied URL via `git clone` with no internally-enforced timeout, unlike the sibling `FetchRemote` RPC which explicitly bounds execution via a `timeout` request field [1](#0-0) . If the remote endpoint accepts a TCP/HTTP connection but never completes the Git protocol handshake or response, the spawned `git clone` process and the RPC handler can block indefinitely, since the only bound on the operation is whatever deadline (if any) the calling client happens to set on the gRPC context.

### Finding Description
`CreateRepositoryFromURL` builds a `git clone` command via `cloneFromURLCommand` using `req.GetUrl()` verbatim (or via a resolved-address override) and executes it with `s.gitCmdFactory.NewWithoutRepo(ctx, ...)`, then waits with `cmd.Wait()` [2](#0-1) . No timeout is derived from the request, and the underlying `CreateRepositoryFromURLRequest` proto message has no `timeout` field at all, unlike `FetchRemoteRequest` which does [3](#0-2) [4](#0-3) .

Execution flows through `repoutil.Create`, which first creates a temporary repository directory, then invokes the seeding callback (the clone), and only afterward takes an exclusive repository-path lock via `repoutil.Lock` before moving the repository into place [5](#0-4) [6](#0-5) . Because the clone (the seeding step) runs before the lock is taken, a stalled clone alone does not block other creations of the *same* repository path, but it does hold open: a git subprocess, its stdio pipes, a temporary on-disk directory under the storage (tempdir.NewRepository), and one in-flight gRPC handler goroutine, for as long as the remote party chooses to stall the connection.

This mirrors the reported bug class exactly: an outbound network call made by an RPC handler (analogous to the DAClient's unbounded `client.Start` call to Celestia) has no independent timeout, and instead depends entirely on whether an external caller (Rails/Workhorse/Praefect) happens to impose a deadline on the gRPC context. If any caller in the chain invokes this RPC with `context.Background()` or a very long/no deadline (which is common for admin/import tooling, and is exactly the kind of caller behavior Gitaly itself cannot control or verify), the handler can hang indefinitely.

### Impact Explanation
An ordinary user who can trigger a "repository import from URL" project creation (a standard, unprivileged GitLab feature backed by this RPC) can point the URL at an attacker-controlled or slow-loris-style endpoint that accepts the TCP/HTTP connection but never responds with valid Git smart-HTTP data. This ties up a Gitaly-side git subprocess and gRPC handler goroutine for an unbounded duration, contributing to resource exhaustion (file descriptors, temp directories, goroutines, subprocess table entries) if repeated, degrading Gitaly's liveliness — a DoS of the handler consistent with the accepted "DoS of a handler" impact class.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the calling layer to not itself impose a strict deadline on this specific RPC invocation, and (b) an attacker-reachable import-from-URL feature, both of which are plausible in real deployments since Gitaly has no independent enforcement and the proto contract offers no `timeout` parameter for callers to even opt into bounding this RPC the way they can with `FetchRemote`.

### Recommendation
Add a bounded, Gitaly-enforced timeout for `CreateRepositoryFromURL`'s clone step, analogous to `FetchRemote`'s `req.GetTimeout()` handling — either by adding a `timeout` field to `CreateRepositoryFromURLRequest` and wrapping the context with `context.WithTimeout` before calling `cloneFromURLCommand`, or by applying a sane default upper bound server-side (e.g., via Gitaly configuration) so the handler cannot hang indefinitely regardless of caller behavior. Additionally consider applying HTTP transport-level timeouts (dial/response-header timeouts) analogous to the `httpTransport` used in `create_repository_from_snapshot.go` [7](#0-6)  for HTTP(S) clone URLs.

### Proof of Concept
1. Stand up a TCP listener on an attacker-controlled host that accepts connections on port 80/443 but never writes any HTTP response bytes (a classic slow-loris stub).
2. Trigger `CreateRepositoryFromURL` (e.g., via a "New project from URL" import in GitLab, or directly via a Gitaly gRPC client) with `Url` pointing at that listener, using a context with no deadline (`context.Background()`), mirroring how internal callers that don't explicitly set one would behave.
3. Observe that the RPC handler blocks in `cmd.Wait()` (`internal/gitaly/service/repository/create_repository_from_url.go:112`) indefinitely, holding a subprocess and temp directory open; repeating this concurrently exhausts subprocess/FD resources without any Gitaly-side circuit breaker specific to this RPC.

func Lock(ctx context.Context, logger log.Logger, locator storage.Locator, repository storage.Repository) (func(), error) {
	path, err := locator.GetRepoPath(ctx, repository, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	// Create the parent directory in case it doesn't exist yet.
	if err := os.MkdirAll(filepath.Dir(path), mode.Directory); err != nil {
		return nil, structerr.NewInternal("create directories: %w", err)
	}

	// We're somewhat abusing this file writer given that we simply want to assert that
	// the target directory doesn't exist and isn't created while we want to move the
	// new repository into place. We thus only use the locking semantics of the writer,
	// but will never commit it.
	locker, err := safe.NewLockingFileWriter(path)
	if err != nil {
		return nil, err
	}

	unlock := func() {
		if err := locker.Close(); err != nil {
			logger.WithError(err).ErrorContext(ctx, "closing repository locker failed")
		}
	}

	if err := locker.Lock(); err != nil {
		unlock()

		return nil, err
	}

	return unlock, nil
}
