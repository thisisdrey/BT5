### Title
Empty account name bypasses the one-time account-naming lock in `UpdateAccountActuator`, enabling account-name-index poisoning/hijacking - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateAccountActuator.java`)

### Summary
The `UpdateAccountActuator`, reachable by any account holder via a signed `AccountUpdateContract` transaction, is supposed to allow an account to set its human-readable name only once (unless the `ALLOW_UPDATE_ACCOUNT_NAME` chain parameter is enabled). The "already named" gate is implemented by checking whether the account's *current* `accountName` field is non-empty [1](#0-0) . This is structurally identical to the ERC20Facet bug: initialization state is inferred from whether a string field is empty, and the setter that writes that field does not forbid writing an empty string back into it, so the "initialized" flag can be reset.

### Finding Description
`UpdateAccountActuator.validate()` only checks that the *incoming* name passes `TransactionUtil.validAccountName(accountName)` [2](#0-1) . That helper is implemented as:

```java
public static boolean validAccountName(byte[] accountName) {
  return validBytes(accountName, MAX_ACCOUNT_NAME_LEN, true);
}
private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
  if (ArrayUtils.isEmpty(bytes)) {
    return allowEmpty;
  }
  return bytes.length <= maxLength;
}
``` [3](#0-2) 

Because `allowEmpty` is passed as `true`, an empty `account_name` (`ByteString.EMPTY`) is treated as *valid*. The one-time-name lock, however, is implemented purely on the stored state:

```java
if (account.getAccountName() != null && !account.getAccountName().isEmpty()
    && chainBaseManager.getDynamicPropertiesStore().getAllowUpdateAccountName() == 0) {
  throw new ContractValidateException("This account name is already existed");
}
``` [1](#0-0) 

Since `validAccountName` now accepts an empty name, an account owner who has already named their account can submit a second `AccountUpdateContract` with an empty `account_name`. This passes validation (the empty-name check no longer rejects it) and `execute()` unconditionally writes it: `account.setAccountName(accountUpdateContract.getAccountName().toByteArray())` [4](#0-3) , and `AccountCapsule.setAccountName` performs no validation at all [5](#0-4) . This resets `account.getAccountName()` to empty, which re-opens the `!account.getAccountName().isEmpty()` gate. The account owner can then submit a third transaction with a brand-new name, bypassing the "one name change only" invariant that `ALLOW_UPDATE_ACCOUNT_NAME == 0` (the Mainnet default, per the proto comment "ALLOW_UPDATE_ACCOUNT_NAME is not enabled on Mainnet, so account names are currently unique" [6](#0-5) ) is meant to enforce.

This also lets the attacker repeatedly `put()` into the global, address-independent `AccountIndexStore`, which is keyed solely by name (`put(accountCapsule.getAccountName().toByteArray(), ...)` [7](#0-6) ) with no uniqueness enforcement on the empty key, and to repeatedly re-attempt names that were `has()`-checked before their own reset. In effect the "unique name" invariant guaranteed to dApps/exchanges that rely on `AccountIndexStore`/`getAccountByName`-style lookups for account identification is broken by any ordinary account holder.

The existing unit test `UpdateAccountActuatorTest.invalidName()` explicitly expects an empty name to be rejected with `"Invalid accountName"` [8](#0-7) , confirming that `validAccountName` returning `true` for empty bytes is a regression/injected defect relative to the actuator's intended contract, and is directly analogous to the missing "empty string" guard flagged in the ERC20Facet finding.

### Impact Explanation
Any regular signed account (no special privilege needed) can:
1. Set its name once (locking the name per the `AllowUpdateAccountName==0` policy).
2. Send a second `AccountUpdateContract` with an empty name, which the buggy `validAccountName` now accepts, resetting the on-chain "named" state to empty.
3. Send further `AccountUpdateContract`s with arbitrary new names indefinitely, defeating the intended one-time-naming/uniqueness guarantee and repeatedly mutating `AccountIndexStore` name→address mappings.

This breaks a chain-enforced identity/uniqueness invariant relied upon by exchanges, wallets, and any service that resolves accounts by name (analogous to how the ERC20Facet bug let anyone re-run `initialize()` after "uninitializing" the token). It does not directly enable minting or fund theft in java-tron, but it does allow account-name squatting/hijacking and index corruption that downstream systems trust as unique, which is a state-integrity violation deterministically reproducible by any user, warranting Medium severity per the standard for broken uniqueness/initialization guarantees.

### Likelihood Explanation
High likelihood of exploitation: it requires only two ordinary transactions signed by the attacker's own key (`AccountUpdateContract` with empty name, then with a new name), no special permissions, no race condition, and no reliance on other actors' actions.

### Recommendation
In `TransactionUtil.validAccountName`, reject empty account names (pass `allowEmpty=false`, or add an explicit `ArrayUtils.isEmpty(accountName)` check in `UpdateAccountActuator.validate()`), matching the recommended mitigation from the referenced report of adding explicit empty-string checks so the one-time naming state cannot be "uninitialized."

### Proof of Concept
1. Ensure `AllowUpdateAccountName == 0` (Mainnet default).
2. Attacker broadcasts `AccountUpdateContract{ owner_address = A, account_name = "alice" }` → succeeds, `AccountIndexStore["alice"] = A`.
3. Attacker broadcasts `AccountUpdateContract{ owner_address = A, account_name = "" }` → currently **succeeds** because `TransactionUtil.validAccountName(empty)` returns `true`; `account.accountName` is reset to empty.
4. Attacker broadcasts `AccountUpdateContract{ owner_address = A, account_name = "bob" }` → the `!account.getAccountName().isEmpty()` gate is now false, so this **succeeds** again, even though `AllowUpdateAccountName == 0`, contradicting the intended one-time-rename policy and repeatedly mutating `AccountIndexStore`.
