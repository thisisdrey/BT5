### Title
`StopTransaction` releases the repo write-lock but leaves the transaction entry in `Manager.transactions`, mirroring the `queuedTransactions` cleanup gap - ([File: internal/praefect/transactions/manager.go])

### Summary
`Manager.StopTransaction` is the Gitaly analog of the audited `cancel()` function: it is meant to gracefully terminate an in-flight reference transaction, but — like the Solidity finding where `cancel()` fails to purge the entry from `queuedTransactions` — it never removes the transaction from the manager's authoritative tracking map `mgr.transactions`. Only the separate `cancelTransaction` path (invoked via the `CancelFunc` returned by `RegisterTransaction`) performs the `delete(mgr.transactions, transaction.ID())`.

### Finding Description
`RegisterTransaction` inserts a transaction into `mgr.transactions` and hands back a `CancelFunc` whose sole purpose is to remove that entry: [1](#0-0) 

The actual deletion only happens in `cancelTransaction`: [2](#0-1) 

`StopTransaction`, however, is a *different* code path, reachable directly via the `RefTransactionServer.StopTransaction` gRPC method. It releases the repo write-lock (`mgr.releaseRepoLock`) and calls `transaction.stop()`, but it never touches `mgr.transactions`: [3](#0-2) 

This is corroborated by the test authors' own comment, which explicitly documents the gap: [4](#0-3) 

The gRPC handler exposes `StopTransaction` as an independent RPC that callers can invoke repeatedly ("It is fine to call this RPC multiple times on the same transaction"), decoupled from the `CancelFunc` closure that would actually clean up the map entry: [5](#0-4) 

This is structurally identical to the FrankenDAO bug class: the "stop/cancel" verb releases the resource that guards concurrent access (lock / queuedTransactions eta) but the bookkeeping map (`queuedTransactions` / `mgr.transactions`) retains a stale entry that a caller must remember to clean up through a separate call.

### Impact Explanation
If any caller (a Gitaly node participating in a transaction, or a coordinator-side code path) invokes `StopTransaction` without also invoking the `CancelFunc` returned by `RegisterTransaction` for that same transaction ID, the entry in `mgr.transactions` is leaked permanently. Since `mgr.idSequence` only increases and the map is never bounded or garbage-collected outside of `cancelTransaction`, repeated occurrences of this pattern under sustained push/vote traffic against Praefect cause unbounded growth of the in-memory `Manager.transactions` map — a memory-exhaustion DoS vector against the Praefect process handling reference-transaction RPCs for ordinary pushes. It also leaves a `*transaction` object reachable via `voteTransaction`'s lookup (`mgr.transactions[transactionID]`) in a "stopped" state indefinitely, which is at minimum a resource leak in a core RPC-handler path.

### Likelihood Explanation
The likelihood depends on whether every internal call site that invokes `StopTransaction` reliably also invokes the transaction's `CancelFunc`. This repository's test suite shows the two are already treated as separate obligations ("StopTransaction doesn't delete the txn from the in-memory map, so we still need to call the cancel closure at the end to clean it up"), which indicates the invariant is fragile and depends on every caller remembering the second call. I was not able to fully enumerate every production caller of `StopTransaction` versus `CancelFunc` before running out of iterations, so I cannot confirm with certainty that a production path exists where `StopTransaction` is called without a subsequent `CancelFunc` call — this is the main open uncertainty in this analog.

### Recommendation
Make `StopTransaction` remove the entry from `mgr.transactions` (or otherwise unify cleanup so that "stop" and "cancel" converge on a single deletion path), rather than relying on every caller to separately invoke the `CancelFunc` closure. At minimum, add a size-bounded eviction/expiry mechanism for `mgr.transactions` and/or metrics on map size so a leak of this kind is observable in production, and audit all call sites of `StopTransaction` to confirm each is paired with a `CancelFunc` invocation.

### Proof of Concept
1. Call `RegisterTransaction` to create transaction `N`, obtaining `CancelFunc`.
2. Call `StopTransaction(ctx, N)` via the `RefTransactionServer.StopTransaction` RPC (or through internal Praefect logic that stops a transaction on node failure) without ever invoking the `CancelFunc`.
3. Observe that `mgr.transactions[N]` still exists (as shown by the `TestPraefectWriteSerialization_StopTransactionReleasesLock` test needing an explicit `defer cancelTxn1Reg()` to clean up) — the transaction remains in the map indefinitely, only reclaimed if some other code path eventually calls `CancelFunc`. func (mgr *Manager) cancelTransaction(ctx context.Context, transaction *transaction) error {
```go
	mgr.lock.Lock()
	defer mgr.lock.Unlock()

	delete(mgr.transactions, transaction.ID())
	// Release while holding mgr.lock so a concurrent voteTransaction can't
	// re-acquire the repo lock between delete and cancel.
	mgr.releaseRepoLock(transaction.ID())
	transaction.cancel()
	mgr.subtransactionsMetric.Observe(float64(transaction.CountSubtransactions()))
```

```go
// StopTransaction will gracefully stop a transaction.
func (mgr *Manager) StopTransaction(ctx context.Context, transactionID uint64) error {
	mgr.lock.Lock()
	transaction, ok := mgr.transactions[transactionID]
	if ok {
		// Release while holding mgr.lock so a concurrent voteTransaction
		// can't acquire a fresh repo lock between this release and stop.
		mgr.releaseRepoLock(transactionID)
	}
	mgr.lock.Unlock()

	if !ok {
		return fmt.Errorf("%w: %d", ErrNotFound, transactionID)
	}
	if err := transaction.stop(); err != nil {
		return err
	}

	mgr.logger.WithFields(log.Fields{
		"transaction.id": transactionID,
	}).DebugContext(ctx, "VoteTransaction: transaction stopped")
	mgr.counterMetric.WithLabelValues("stopped").Inc()

	return nil
}
```

```go
// StopTransaction is called by a client who wants to gracefully stop a
// transaction. All voters waiting for quorum will be stopped and new votes
// will not get accepted anymore. It is fine to call this RPC multiple times on
// the same transaction.
func (s *Server) StopTransaction(ctx context.Context, in *gitalypb.StopTransactionRequest) (*gitalypb.StopTransactionResponse, error) {
	if err := s.txMgr.StopTransaction(ctx, in.GetTransactionId()); err != nil {
		switch {
		case errors.Is(err, transactions.ErrNotFound):
			return nil, structerr.NewNotFound("%w", err)
		case errors.Is(err, transactions.ErrTransactionCanceled):
			return nil, structerr.NewCanceled("%w", err)
		case errors.Is(err, transactions.ErrTransactionStopped):
			return &gitalypb.StopTransactionResponse{}, nil
		default:
			return nil, structerr.NewInternal("%w", err)
		}
	}

	return &gitalypb.StopTransactionResponse{}, nil
```
