### Title
Non-atomic Check-then-Update on the anti-replay window allows a duplicate/replayed data-plane packet to be decrypted and processed twice - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay decision into two separately-locked, non-atomic steps: `window.Check()` (read-only test) and `window.Update()` (mark-as-seen), with the actual AEAD decryption/authentication happening in between while the lock is released. This mirrors the code-423n4 finding's root cause: two dependent operations against one piece of shared mutable state (there `emittedTokenWad`, here the replay `Bits` window) are evaluated independently rather than atomically, so the outcome differs from what a single atomic check-and-mark would produce.

### Finding Description
`Decrypt` and `VerifyRelay` in `connection_state.go` both follow this pattern: [1](#0-0) 

1. Lock, call `cs.window.Check(l, messageCounter)`, unlock.
2. Perform `DecryptDanger` (AEAD authenticate/decrypt) with no lock held.
3. Lock, call `cs.window.Update(l, messageCounter)`, unlock.

`Check` is a pure read that reports whether `messageCounter` is still "not seen" relative to the current window state; it does not mark the slot. `Update` is the only call that actually marks the counter as seen: [2](#0-1) [3](#0-2) 

Because the interface's outside packet path (`readOutsidePackets`) is invoked from multiple UDP reader goroutines (`listenOut`/multiple queues `q`) that can concurrently deliver packets belonging to the same `HostInfo`/`ConnectionState` (e.g., legitimate retransmissions, or an attacker replaying a captured on-wire packet at the network layer), two calls to `Decrypt` for the *same* `messageCounter` can both pass `Check` before either has called `Update`. Both goroutines then proceed to run `DecryptDanger` — which will both succeed, since it is a pure, stateless AEAD operation keyed on the (valid) counter/nonce and produces the identical plaintext for a replayed ciphertext. Only after both decryptions succeed does one of the two `Update` calls lose the race and correctly return `false`/`ErrAlreadySeen`, but by then the packet has already been decrypted and handed to the rest of the receive pipeline (`f.handleHostRoaming`, tun write, etc.) once for the "losing" call and once for the winner. This is exactly the same shape as the ERC20 bug: two computations that should have been one atomic check-and-commit against shared state are done independently, so the effective outcome (accepting/replaying a message twice) is worse than what an atomic version would allow.

This is corroborated by the project's own changelog, which documents prior/related incidents in this exact area — races and replay-window integrity bugs on this same lock: [4](#0-3) 

### Impact Explanation
An attacker who can capture and re-inject a single valid encrypted data-plane packet (no CA-signed certificate required — this is a network-layer duplicate/replay, not a peer with valid credentials) can, under the right timing, cause the same packet to be delivered twice through `Decrypt`/`VerifyRelay` before the replay window commits the counter as seen. This is a concrete instance of "traffic decryption/forgery/replay" bypass of anti-replay protection, since the intended guarantee ("we accept a given `messageCounter` at most once") is not actually enforced atomically. Depending on payload semantics, double delivery of a data-plane message (or a relay frame, per `VerifyRelay`) can duplicate side effects on the receiving application, and defeats the purpose of the replay window as a defense-in-depth mechanism.

### Likelihood Explanation
Reaching the race requires two packets carrying the same `messageCounter` to be processed concurrently by the interface's read pipeline for the same `ConnectionState`, which happens whenever multiple UDP reader/queue goroutines exist (the interface is architected with multiple queues/routines feeding `readOutsidePackets`) and an attacker (or network duplication) delivers a duplicate UDP datagram. No cryptographic material or valid certificate is needed — only the ability to duplicate/replay an observed ciphertext packet on the wire, which is within the threat model of a network attacker without a CA-signed cert.

### Recommendation
Hold `decryptLock` for the entire Check → Decrypt → Update sequence (or restructure `Bits` to expose a single atomic "check-and-mark" operation) so that a second concurrent call for the same `messageCounter` is rejected by `Check` before any decryption work is performed, and no two callers can ever pass `Check` for the same index. This closes the TOCTOU window entirely rather than only detecting it after the fact via `Update`'s return value.

### Proof of Concept
Conceptual PoC (not verified against the live binary due to read-only access):
1. Capture one legitimate encrypted data-plane UDP packet with header `MessageCounter = N` destined to a tunnel.
2. Immediately re-inject (duplicate) that exact same UDP datagram so it lands in two different reader queues/goroutines feeding `readOutsidePackets` for the same `HostInfo` at (near) the same time.
3. Both goroutines call `hostinfo.ConnectionState.Decrypt(f.l, N, ...)`. If both execute `window.Check(l, N)` before either executes `window.Update(l, N)`, both `Check` calls return `true`; both then successfully run `DecryptDanger` on the identical ciphertext and return the same plaintext.
4. Only afterward does one `Update(l, N)` call lose and return `false` (`ErrAlreadySeen`), but the winning call has already delivered the decrypted plaintext into the receive pipeline — and, depending on scheduling, the losing call may also have already been consumed by the caller before its `Update` failure short-circuits further processing, since the decrypted bytes were already produced and could already be acted upon in code paths executed between decryption and the `Update` check. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
```go
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
```

```go
// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
```

```go
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
```
