### Title
Out-of-bounds read in `InputZipFile::ProcessCentralDirEntry` while parsing an attacker-supplied zip/jar central directory - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s zip reader parses the central directory of a zip/jar file that Bazel treats as untrusted input (e.g. a jar fetched via `http_jar`/`http_archive` and then processed by the `ijar`/`zipper` tool to build an interface jar or to extract/inspect entries). Unlike the local-file-header parser in the same file, the central-directory parser performs no bounds checks before reading attacker-controlled length fields and copying/scanning memory based on them, allowing reads past the end of the memory-mapped file.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` (third_party/ijar/zip.cc:332-364) is careful: before reading each variable-length field it calls `EnsureRemaining(n, "state")` (defined at third_party/ijar/zip.cc:161-170), which validates that `n` bytes remain within the mmap'd input before the cursor `p` is advanced or dereferenced: [1](#0-0) 

`InputZipFile::ProcessCentralDirEntry` (third_party/ijar/zip.cc:493-545), however, reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and then unconditionally advances `p`/`extra_p` and dereferences memory according to those lengths — with **no equivalent `EnsureRemaining`/bounds check against the mapped file's end**: [2](#0-1) 

Specifically:
- `memcpy(reinterpret_cast<void*>(filename), p, len)` copies from `p` for up to `file_name_length` bytes with no check that `p + len` is within the mapped region. [3](#0-2) 
- The subsequent `while (extra_p != p)` loop reads a `header_id`/`data_size` pair via `get_u2le` and advances `extra_p += data_size`, again with no bound check that `extra_p` stays inside the mmap region; a crafted `extra_field_length`/`data_size` can walk the cursor arbitrarily far past the buffer end while continuing to dereference memory. [4](#0-3) 

Since the whole file is accessed via `MappedInputFile`/mmap (see `InputJar`/`InputZipFile` bounds logic in `input_jar.cc` and `zip.cc`), reading past the mapped extent is a genuine out-of-bounds memory read: it can read adjacent unmapped pages (crash) or adjacent mapped memory (disclosure of adjacent heap/mmap bytes into `filename`, which is later used in diagnostics/processing) — directly analogous to the CVE-2018-5683 pattern of "improper memory address validation" causing an out-of-bounds read while parsing attacker-controlled structured data (there, VGA text buffer offsets; here, zip central-directory field lengths).

This is reachable purely from content that an unprivileged outside party controls: a jar/zip fetched through Bazel's dependency-fetch mechanisms (e.g. `http_jar`, `http_archive` producing a `.jar`/`.zip` consumed via `java_import`, or any path that runs a downloaded archive through the `ijar`/`zipper` (`zip_main.cc`) tools) is exactly the "central directory" bytes parsed here. A declared `sha256`/integrity hash on the download only proves the bytes are exactly what the attacker published — it does nothing to stop malicious *structure* within those correctly-hashed bytes from triggering the OOB read once `ijar`/`zipper` parses it.

### Impact Explanation
An attacker who controls the content of a jar/zip that a victim's build fetches (with a matching, attacker-chosen sha256/integrity value, which is trivial since the attacker controls the artifact from the start) can craft central-directory length fields that drive `ProcessCentralDirEntry`'s pointer past the mapped file. This causes an out-of-bounds read, which can crash the `ijar`/`zipper` build tool process (denial of service for that action) and, depending on adjacent memory layout, could copy adjacent process memory into the `filename` buffer, which is subsequently used in `processor->Accept`/`processor->Process` calls and error messages — a data-confusion / potential-disclosure primitive rather than pure crash.

### Likelihood Explanation
High for reachability: this code path executes on every entry of every jar/zip that Bazel's `ijar`/`zipper` tooling processes, and any dependency delivered as a prebuilt jar (common for `java_import`/Maven-style deps) goes through it. Crafting a zip with an inflated `file_name_length`/`extra_field_length`/`data_size` near the end of the mapped file is straightforward and requires no special privileges — only the ability to publish/serve the artifact that the victim's build fetches.

### Recommendation
Add the same bounds validation used in `ProcessLocalFileEntry` (i.e., call an `EnsureRemaining`-equivalent check, or explicitly bound `p`/`extra_p` against `mapped_file_`/`zipdata_in_ + input_file_->Length()`) before each read and pointer advance in `ProcessCentralDirEntry`, including inside the extra-field scanning loop, and reject the entry with an error rather than dereferencing past the mapped file when the computed lengths would exceed the remaining file size.

### Proof of Concept
A reproducible test can be added similarly to `output_jar_simple_test.cc`'s `MalformedExtraField` test (third_party/singlejar/output_jar_simple_test.cc:1227-1236), but targeting `ijar`'s `zip.cc` reader: [5](#0-4) 
1. Construct a minimal valid zip file consisting of a valid EOCD/central-directory-header signature.
2. Set the central directory entry's `file_name_length` (or `extra_field_length`) to a value that extends several kilobytes past the actual mapped file size (e.g., file is 200 bytes, `file_name_length = 0xFFFF`).
3. Invoke the `zipper`/`ijar` extraction path (`devtools_ijar::extract`, `zip_main.cc:498`) on this file, e.g. via `bazel-bin/third_party/ijar/zipper x -d out malicious.zip` or through `InputZipFile::Open`/`ProcessNext` directly in a unit test.
4. Observe a crash (SIGSEGV from reading unmapped pages) or, under ASan, an out-of-bounds-read report inside `InputZipFile::ProcessCentralDirEntry` at the `memcpy`/`get_u2le` calls at third_party/ijar/zip.cc:520 and :527-528.
