### Title
Expired CA certificates are added to the trusted CA pool before the expiry check runs, allowing an expired root to remain usable for certificate verification - ([File: cert/ca_pool.go])

### Summary
`CAPool.AddCA` inserts the CA into the trusted pool (`ncp.CAs[sum] = cc`) before it checks whether the CA is expired. This mirrors the dHEDGE bug class: an invariant-preserving check ("this CA must not be expired") is evaluated *after* the state mutation that the check is supposed to gate, instead of before it (or, symmetrically to the report's fix, the mutation should not be committed until the check has passed). Because the pool entry is made durable regardless of the outcome of the expiry check, any code path that treats a non-nil error from `AddCA`/`AddCAFromPEM` as "this CA was not added" is wrong, and the expired CA remains resolvable via `GetCAForCert`/`ncp.CAs`.

### Finding Description
In `cert/ca_pool.go`: [1](#0-0) 

```go
func (ncp *CAPool) AddCA(c Certificate) error {
	if !c.IsCA() {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotCA)
	}

	if !c.CheckSignature(c.PublicKey()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotSelfSigned)
	}

	sum, err := c.Fingerprint()
	if err != nil {
		return fmt.Errorf(...)
	}

	cc := &CachedCertificate{...}
	...
	ncp.CAs[sum] = cc          // <-- state mutation happens here

	if c.Expired(time.Now()) { // <-- invariant check happens AFTER the mutation
		return fmt.Errorf("%s: %w", c.Name(), ErrExpired)
	}

	return nil
}
```

The signature-validity and "is a CA" checks correctly gate the mutation (they `return` before `ncp.CAs[sum] = cc`), but the expiry check does not: the certificate is committed to the trusted pool `ncp.CAs` unconditionally, and only afterward is an error returned if it happens to be expired. This is structurally identical to the report's root cause: an assertion/invariant check that is supposed to prevent an inconsistent state from being observed is placed on the wrong side of the state update, so the "bad" state (an expired CA sitting in the trusted pool) is committed regardless of whether the check fails.

This matters because `ncp.CAs` is the map consulted by `GetCAForCert`/`verify` for the lifetime of the process (`CAPool` is loaded once at startup and via config reload, see `pki.go`'s `NewCAPoolFromPEMReader` / `AddCAFromPEM` chain). If any caller merges CA bundles by calling `AddCA` in a loop and, similar to `cmd/nebula-cert/verify.go`'s handling of `cert.ErrExpired` from `NewCAPoolFromPEMReader`, tolerates/ignores an `ErrExpired` return (treating it as "added, but stale" rather than "not added"), the expired CA is fully present in the pool from that point on and every subsequent host-cert verification calls `signer.Certificate.Expired(now)` as a second, independent check.

The mitigating factor: `verify()` does re-check `signer.Certificate.Expired(now)` on every verification (`cert/ca_pool.go` line ~224), so a currently-expired CA cannot itself be used to mint fresh verifications through the normal `VerifyCertificate` path today. The residual risk is limited to any place that treats `AddCA`'s error as fatal-and-non-committing and is surprised that the CA is already resident in `ncp.CAs`, or any future/alternate code path that consults `ncp.CAs` directly without re-checking expiry (e.g. `GetCAForCert`, `GetFingerprints`, blocklist/group bookkeeping) — the ordering bug means the pool's invariant ("CAs is exactly the set of currently valid CAs, or callers can rely on a non-nil `AddCA` error meaning nothing was mutated") does not hold.

### Impact Explanation
If a consumer of `AddCA`/`AddCAFromPEM` relies on the returned error to decide whether a CA was actually incorporated into the trust store (a reasonable and common assumption for an "Add" function), it will be wrong: the expired CA is unconditionally inserted into `ncp.CAs` before the error is returned. Any downstream logic that enumerates or trusts entries in `ncp.CAs` without independently re-validating expiry (unlike the redundant check inside `verify()`) would treat an expired root as trusted, which is a certificate-verification/trust-boundary bypass in the CA-pool invariant. This is a defense-in-depth / invariant-integrity flaw analogous to the dHEDGE finding: the safety net (the state consistency check) is rendered ineffective because it doesn't run before the state is committed.

### Likelihood Explanation
Reachable without a CA-signed certificate: this code runs whenever CA bundles are (re)loaded, e.g. during config reload of `pki.go`'s CA pool, or CLI verification tooling (`cmd/nebula-cert/verify.go`) that explicitly tolerates `cert.ErrExpired`. An attacker who can influence which CA certs get merged (e.g. supply an additional/rotated CA bundle that includes an expired CA) benefits from this ordering bug the moment any caller doesn't strictly abort on `AddCA` error. Likelihood of the ordering itself being hit is high (any expired CA in an input PEM triggers it every time); the exploitability further depends on whether a consuming call path skips the redundant expiry re-check in `verify()`, which is not confirmed on the currently-reachable primary path.

### Recommendation
Move the `c.Expired(time.Now())` check in `AddCA` above the `ncp.CAs[sum] = cc` assignment (or otherwise defer the mutation until all validity checks, including expiry, have passed), mirroring the report's fix of relocating the invariant check to after all the relevant state changes that it must reflect — here, that means gating the mutation on the check rather than the reverse. This restores the invariant that a non-nil error from `AddCA` implies the pool state was not changed.

### Proof of Concept
1. Build (or take) a self-signed CA certificate `caExpired` whose `NotAfter` is in the past (`cert_test.NewTestCaCert` can produce one with `NotAfter` before `time.Now()`), that otherwise passes `IsCA()` and `CheckSignature()`.
2. Call `pool := cert.NewCAPool(); err := pool.AddCA(caExpired)`.
3. Observe `err` is a non-nil `ErrExpired`, exactly as documented — but also observe that `pool.CAs[fingerprint(caExpired)]` is already populated (e.g. via `pool.GetFingerprints()` or `pool.GetCAForCert(...)` against a cert issued by `caExpired`), demonstrating the CA was committed to the pool despite the reported error.
4. Any caller of `AddCA`/`AddCAFromPEM` (e.g. `cmd/nebula-cert/verify.go`, which explicitly special-cases and swallows `cert.ErrExpired` from `NewCAPoolFromPEMReader`) that continues execution treating the pool as "CA not added" is instead operating with the expired CA already resident and reachable via `GetCAForCert`.

```go
// AddCA verifies a Nebula CA certificate and adds it to the pool.
func (ncp *CAPool) AddCA(c Certificate) error {
	if !c.IsCA() {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotCA)
	}

	if !c.CheckSignature(c.PublicKey()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotSelfSigned)
	}

	sum, err := c.Fingerprint()
	if err != nil {
		return fmt.Errorf("could not calculate fingerprint for provided CA; error: %w; %s", err, c.Name())
	}

	cc := &CachedCertificate{
		Certificate:    c,
		Fingerprint:    sum,
		InvertedGroups: make(map[string]struct{}),
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	ncp.CAs[sum] = cc

	if c.Expired(time.Now()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrExpired)
	}

	return nil
}
```
