### Title
Permissionless `lending_pool_emissions_deposit` allows first-depositor share-value inflation, trapping later depositors via rounding — analogous to the ElasticSwap LP donation attack ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
`lending_pool_emissions_deposit` lets *anyone* donate tokens directly into a bank's `liquidity_vault` and have that donation immediately re-priced into `asset_share_value` without minting any new `total_asset_shares`. [1](#0-0)  This is structurally identical to the ElasticSwap bug: a user who controls (or reduces) the outstanding share supply to a tiny value can inflate the per-share value via a "donation," causing subsequent depositors' share-conversion math to round their minted shares down to zero while their underlying tokens are still pulled into the vault.

### Finding Description
Marginfi's bank accounting uses a shares model: `asset_amount = asset_shares * asset_share_value`, and conversely `asset_shares = asset_amount / asset_share_value` [2](#0-1) . When a user deposits, the new share amount is computed by dividing the deposited value by the *current* `asset_share_value`, and credited without any minimum-share-output check: [3](#0-2) 

`lending_pool_emissions_deposit` is explicitly documented and implemented as permissionless ("Permissionlessly deposit same-mint emissions directly into the bank liquidity vault, increasing depositor value through asset share value") [1](#0-0) . Its only gating condition is `total_asset_shares > 0` [4](#0-3) , after which it directly recomputes `asset_share_value` as `(total_assets + donated_amount) / total_asset_shares` — with no new shares minted for the donation: [5](#0-4) 

This mirrors the ElasticSwap root cause exactly: the ElasticSwap attacker mints/burns nearly all LP tokens down to `1 Wei`, then transfers ("donates") base token directly to the pool to inflate the implied value-per-share, after which any legitimate depositor's share-mint calculation (`_quoteTokenQty * totalSupply / _quoteTokenReserveBalance`) rounds down to zero for realistic deposit sizes. In marginfi's case, an attacker who is the sole/first depositor of a bank can:
1. Deposit a small amount to become the only shareholder.
2. Withdraw nearly all of it via normal `lending_account_withdraw`, leaving `total_asset_shares` at a minimal (e.g., near-dust) value while still satisfying `total_asset_shares > 0`.
3. Call the permissionless `lending_pool_emissions_deposit` with a "donation" to spike `asset_share_value` to an arbitrarily large number.
4. Any subsequent depositor whose deposited value, divided by the now-inflated `asset_share_value`, floors to zero shares still has their tokens transferred into the vault but is credited zero (or a negligible number of) `asset_shares` — because `get_asset_shares`/`increase_balance_internal` perform no minimum-output check [3](#0-2) .

### Impact Explanation
A victim who deposits after this manipulation can have their underlying tokens absorbed into the bank's liquidity vault while receiving disproportionately few (or zero) `asset_shares`, effectively donating value to the existing shareholder(s) — the same "protocol becomes a trap that takes a cut from future liquidity providers" impact described in the ElasticSwap report. This is an unauthorized value transfer/dilution within the core deposit accounting path, reachable by any unprivileged user with a normal deposit/withdraw/emissions-deposit sequence, no admin privilege required.

### Likelihood Explanation
Likelihood is comparable to the original finding: it requires the attacker to be the dominant/sole shareholder of a specific bank at the time of attack (e.g., a freshly created bank, or one where an attacker can temporarily reduce `total_asset_shares` to a very small value), then to profitably front-run future depositors with a donation. Deposit limits, minimum deposit-limit-capacity math, and the fact that a bank typically already has real depositors reduce practical likelihood, but the mechanism itself — permissionless donation directly re-pricing shares without a minted counterpart — is present and unguarded by any minimum-shares or dust threshold in the codebase we could confirm.

### Recommendation
- Enforce a minimum outstanding `total_asset_shares` (or a "dead shares" floor, akin to Uniswap V2's `MINIMUM_LIQUIDITY`) below which withdrawals cannot fully drain a bank, preventing an attacker from single-handedly controlling the entire share supply.
- In `lending_pool_emissions_deposit`, require `total_asset_shares` to exceed some meaningful floor (not just `> 0`) before allowing a share-value-inflating donation, or cap the maximum single-call increase to `asset_share_value`.
- Reject deposits whose computed `asset_shares_increase` rounds to zero (revert instead of crediting zero shares while still transferring tokens), closing the "dust trap" precision-loss path across all deposit entry points.

### Proof of Concept
Conceptual sequence within the existing instruction set (no new capability required beyond calling public instructions in order):
1. Attacker deposits a small amount into a newly-created (or currently near-empty) bank via `lending_account_deposit`, becoming (effectively) the sole shareholder, so `bank.total_asset_shares` and `bank.asset_share_value` both reflect a tiny state.
2. Attacker withdraws almost all of their balance via `lending_account_withdraw`, leaving `total_asset_shares` positive but minimal (satisfying the `EmissionsUpdateError` check) [4](#0-3) .
3. Attacker calls `lending_pool_emissions_deposit` with a sizeable donation amount, causing `asset_share_value` to jump by `updated_total_assets / total_asset_shares` [5](#0-4)  — no new shares are minted for this value.
4. A victim later calls `lending_account_deposit` with a normal deposit amount; `bank.get_asset_shares(value)` divides by the inflated `asset_share_value` [6](#0-5) , and if the result floors to (near) zero, `increase_balance_internal` credits that (near) zero share amount to the victim while their tokens have already moved into the vault [3](#0-2) , transferring value from the victim to the attacker's remaining shares.

This exact scenario is not covered by any existing test file we were able to locate (e.g., `tests/specs/basic/18_emissionsDeposit.spec.ts` could not be retrieved in this session due to tool limitations), so we could not empirically confirm the exact numeric magnitude of loss achievable on-chain; this should be validated with a live/bankrun reproduction before treating severity as final — consistent with the original ElasticSwap judgment, this issue class is best considered **Medium** severity pending confirmation of concrete achievable magnitude in marginfi's specific `I80F48` fixed-point precision (which is significantly higher-precision than typical ERC-20 `uint256`/`sqrt` LP math, potentially limiting practical exploitability).
