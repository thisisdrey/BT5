Audit Report

## Title
Snowbridge outbound-queue-v2 settles pending orders and pays relayer rewards without checking delivery `success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` from the Ethereum `InboundMessageDispatched` event that includes a `success` flag, but never reads or branches on it. The relayer reward is paid via `T::RewardPayment::register_reward` and the `PendingOrder` is permanently removed from `PendingOrders` based solely on `order.fee > 0` and gateway/nonce validity, regardless of whether the dispatched command actually executed successfully on Ethereum.

## Finding Description
The pallet's documentation states the intended flow at [2](#0-1)  as fetching the pending order and paying the reward, with no mention of gating on outcome. The `process_delivery_receipt` function at [1](#0-0)  checks only `T::GatewayAddress::get() == receipt.gateway` and that a `PendingOrder` exists for `receipt.nonce`; the `receipt.success` field is never inspected. Since `Command::CallContract` permits the message sender to specify an arbitrary `gas` value that becomes the committed `max_dispatch_gas` via `ConstantGasMeter::maximum_dispatch_gas_used_at_most`, an underpriced `gas` value can cause the command to fail on Ethereum while the source-chain settlement (reward payout + order removal) proceeds unconditionally as if delivery succeeded.

## Impact Explanation
This is public underpriced/incorrect settlement: relayer rewards are paid and `PendingOrders` state is destroyed for commands that did not achieve their intended effect on Ethereum, with no retry or dispute mechanism, violating the invariant that settlement state should only advance after execution actually succeeds.

## Likelihood Explanation
No privileged or malicious actor is required — any user constructing a v2 XCM message with `Command::CallContract` and an insufficient `gas` value causes this path; an honest relayer merely submits the resulting event (with `success=false`) via the public `submit_delivery_receipt` extrinsic, and the existing code pays out and clears the order regardless.

## Recommendation
`process_delivery_receipt` should branch on `receipt.success`, only paying the reward and clearing the order on success; on failure, retain the order for retry or transition to an explicit failure-handling path.

## Proof of Concept
1. Submit a v2 XCM message with `Command::CallContract { gas: <too_low>, .. }`.
2. `do_process_message` commits the command with the caller-supplied `gas` and creates a `PendingOrder`.
3. On Ethereum, execution fails due to underpriced gas; Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
4. A relayer submits this via `submit_delivery_receipt`; `process_delivery_receipt` ignores `success`, pays the reward, and removes the order.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
