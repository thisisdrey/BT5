## Analysis

The reported bug class is a state-machine defect: a contract enters a "pending resolution" phase (`has_in_flight_tx` acting like the Voting contract's un-finalized poll) with no timeout or fallback path to force resolution if the expected resolving call never successfully completes. The strongest reachable analog in this nearcore tree is in the **eth-implicit Wallet Contract** (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`), which is explicitly in scope.

### Title
Wallet Contract `has_in_flight_tx` lock has no timeout/reset path, permitting permanent freezing of an ETH-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` sets `has_in_flight_tx = true` before dispatching a cross-contract promise chain, and every subsequent `rlp_execute` call is unconditionally rejected while the flag is `true` [1](#0-0) . The flag is only ever cleared inside the `#[private]` callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) . There is no timeout, no owner/relayer "force-unlock" method, and no alternate code path to reset the flag if the resolving callback receipt itself fails to commit its state changes (e.g. via panic/out-of-gas). This directly mirrors the report's bug class: an action that is supposed to "resolve" a pending state can simply never happen, and the contract provides no time-bounded fallback.

### Finding Description
`rlp_execute` dispatches a promise chain and attaches a fixed, small static gas budget to the terminal callback that clears the lock — e.g. `RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)` [6](#0-5) . `rlp_execute_callback` copies an arbitrary-size `PromiseResult::Successful(value)` (returned by whatever `target` contract the user's transaction calls) into `ExecuteResponse.success_value` [7](#0-6) , and `self.has_in_flight_tx = false` is written at the top of the function body [8](#0-7) . In the NEAR runtime, a contract's state changes for a call are only persisted if the entire host-function execution completes without panicking; if the call later exhausts its attached gas (e.g. while serializing/copying an oversized `success_value` for the return value), the whole receipt fails and **all** state writes from that receipt — including the `has_in_flight_tx = false` write — are discarded (see the runtime's commit/rollback discipline for action receipts: `apply_action_receipt`, `runtime/runtime/src/lib.rs:961-970`, "success commits ... failure calls `state_update.rollback()`"). Because the only way to ever clear `has_in_flight_tx` is for one of these fixed-gas callbacks to fully succeed, and because a called `target` contract's return payload size and computation cost are outside the wallet contract's control, an attacker-influenced/malicious `target` contract can force the terminal callback to run out of gas and panic, permanently leaving `has_in_flight_tx == true`. From that point, `rlp_execute` immediately and unconditionally short-circuits with `"transaction already in progress"` for every future call, with no other method available to reset the flag [9](#0-8) .

### Impact Explanation
Since ETH-implicit accounts can only be acted upon through the Wallet Contract's `rlp_execute` entry point — they cannot have a full access key added and cannot be deleted [10](#0-9)  — permanently locking `has_in_flight_tx` permanently freezes all of that account's funds (native NEAR balance and any assets/permissions reachable only via that account). This satisfies the "permanent freezing of funds" impact bar.

### Likelihood Explanation
The likelihood is dependent on the specific gas accounting of the `.then()` callback relative to attacker-controlled response payload sizes/target contract cost, which was not independently verified with a concrete numeric proof-of-concept in this analysis — the callback logic itself (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`) does not panic on ordinary error paths (it gracefully handles `PromiseResult::Failed` and malformed data), so the only trigger is genuine gas exhaustion or another unexpected panic inside the fixed-gas callback. This requires the account owner (or a relayer acting on their behalf) to route a call through a hostile or buggy `target` contract designed/able to return an oversized value or otherwise make the callback exceed its statically attached gas.

### Recommendation
Add a defensive, time/height-bounded escape hatch: record the block height (or a receipt/promise id) when `has_in_flight_tx` is set, and allow the wallet owner (or anyone, after a fixed timeout window analogous to the reported recommendation) to call a "force-reset" method that clears `has_in_flight_tx` if the pending transaction has not resolved within that timeout. Additionally, bound the callback's gas budget to scale safely with worst-case return-value size, or truncate/avoid echoing arbitrary-size promise results back through contract state-mutating code paths.

### Proof of Concept
Not independently reproduced/measured in this analysis; a full PoC would require constructing a `target` contract that returns a maximal-size successful response (or otherwise inflates gas cost) precisely calibrated to exceed `RLP_EXECUTE_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS` when `rlp_execute_callback` attempts to serialize it, then confirming the resulting receipt panics and `has_in_flight_tx` remains `true` in the post-state.
