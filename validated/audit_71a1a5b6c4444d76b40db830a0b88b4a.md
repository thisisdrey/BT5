### Title
`insert_uninstantiated_attachment` stores attachment content with no check against `attachments_max_size` - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_uninstantiated_attachment` enforces a cap on the *number* of uninstantiated attachments via `max_uninstantiated_attachments` (evicting oldest entries), but never checks `attachment.content.len()` against `self.atlas_config.attachments_max_size` before writing the row. `AtlasConfig::validate()` only validates that the *configured* value of `attachments_max_size` is not below a minimum, it does not enforce anything against attachments actually written to the DB. This means the intended storage bound "stored content length <= attachments_max_size" is not enforced at the point of insertion.

### Finding Description
`insert_uninstantiated_attachment` (stackslib/src/net/atlas/db.rs) only bounds the count of pending attachments: [1](#0-0) 
It computes `uninstantiated_attachments` and evicts the oldest ones if the count reaches `max_uninstantiated_attachments`, then unconditionally runs `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at)` with `attachment.content` as-is — there is no comparison of `attachment.content.len()` to `self.atlas_config.attachments_max_size` anywhere in this function.

`AtlasConfig::validate()` (stackslib/src/net/atlas/mod.rs) only checks that the *configured value* of `attachments_max_size` is at least `ATTACHMENTS_MAX_SIZE_MIN` (1 MiB); it never inspects the actual size of attachments being inserted: [2](#0-1) 

So the per-item size cap that the config name implies exists only as a documented intent, not an enforced invariant inside `AtlasDB`.

However, per the audit rules, the impact must trace back to a remote, unprivileged attacker actually reaching this function with oversized content. The only non-test caller of `insert_uninstantiated_attachment` found in the codebase is in `stackslib/src/net/api/posttransaction.rs` (the unauthenticated `POST /v2/transactions` RPC handler, which accepts an optional hex-encoded `attachment` field). I was **not able to fully verify**, within the remaining tool budget, whether `posttransaction.rs` (or any intermediate relay/mempool code) performs its own size check against `atlas_config.attachments_max_size` before calling into `AtlasDB`, nor whether the download path (`stackslib/src/net/atlas/download.rs`, which does reference `content.len()`) enforces this bound when attachments arrive from peer-to-peer `GetAttachment` responses. Without confirming that caller-side gap, I cannot conclusively state that a remote, unprivileged attacker's oversized `Attachment` reaches `insert_uninstantiated_attachment` unchecked end-to-end — only that the function itself, in isolation, contains no such check.

### Impact Explanation
If an unprivileged caller can indeed reach `insert_uninstantiated_attachment` with content exceeding `attachments_max_size` (e.g., via the `POST /v2/transactions` attachment field, or via a crafted `GetAttachment`/`AttachmentsInv` response accepted by `AttachmentsDownloader`), each accepted oversized attachment consumes disk space beyond the configured per-item limit. Because the eviction logic only bounds the *count* of uninstantiated rows (`max_uninstantiated_attachments`), the effective storage ceiling `max_uninstantiated_attachments * attachments_max_size` would no longer hold, and worst-case disk usage becomes `max_uninstantiated_attachments * (attacker-chosen size)`. This matches "storage exhaustion" style High impact, contingent on confirming the unauthenticated reachability described above.

### Likelihood Explanation
Preconditions/uncertainty: requires confirming (not yet verified here) that `posttransaction.rs` or the atlas P2P download path forwards attacker-controlled `Attachment.content` to `insert_uninstantiated_attachment` without first checking its length against `attachments_max_size`. The database function itself provides no defense-in-depth against this, so if any caller omits the check, the bound breaks. Given the size of the codebase and the tool-call budget exhausted, this caller-side check could not be conclusively ruled in or out.

### Recommendation
Add an explicit size check inside `insert_uninstantiated_attachment` itself (defense in depth, not relying on callers):
```rust
if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
    return Err(db_error::Overflow); // or a dedicated error variant
}
```
This makes the per-item bound an invariant of the storage layer regardless of caller behavior, removing the need to audit every call site.

```rust
    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
```
