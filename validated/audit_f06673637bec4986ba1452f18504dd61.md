### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule` account-index lists via low-cost `FreezeBalanceContract` delegation - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
When the legacy (pre-optimization) delegated-resource indexing path is active, `FreezeBalanceActuator.delegateResource()` appends the receiver/owner address into a single, unbounded `List<ByteString>` stored inside one `DelegatedResourceAccountIndexCapsule` object per account, with no cap on the number of entries and no fee proportional to list size.

### Finding Description
`FreezeBalanceActuator.delegateResource()` maintains legacy delegation indices when `dynamicPropertiesStore.supportAllowDelegateOptimization()` is false: [1](#0-0) 

For every `FreezeBalanceContract` that delegates resources to a `receiverAddress`, the code:
1. Loads the *entire* `DelegatedResourceAccountIndexCapsule` for the owner (`toAccountsList`) and for the receiver (`fromAccountsList`).
2. Performs an O(n) `List.contains()` scan to check for duplicates.
3. Appends the new address with `addToAccount`/`addFromAccount`, growing the list.
4. Writes the whole, now-larger, capsule back to the key-value store.

`calcFee()` for this actuator returns a flat `0`, unrelated to the resulting list size: [2](#0-1) 

Because `receiverAddress` is attacker-controlled and does not require the receiver's consent, an attacker can repeatedly issue `FreezeBalanceContract` transactions (freezing only the network minimum, e.g., 1 SUN, which is later recoverable via unfreeze) from many different owner addresses, all targeting the *same* victim receiver address. Each such transaction grows the victim's `fromAccountsList` inside a single serialized protobuf object stored under the victim's key in `DelegatedResourceAccountIndexStore`: [3](#0-2) 

This list is unbounded — unlike the newer `UnfreezeBalanceV2Actuator`/`unfrozenV2List`, which enforces a hard cap of `UNFREEZE_MAX_TIMES = 32`: [4](#0-3) 

The legacy delegated-resource index has no equivalent limit. Once the list is large:
- Any subsequent `FreezeBalanceContract`/`UnfreezeBalanceActuator` operation touching the victim's index must deserialize, linear-scan, and re-serialize the entire bloated object (O(n) work per transaction), increasing the cost of block processing for validators without a corresponding fee.
- The unbounded list is also served in full to any external caller through the read-only query API `Wallet.getDelegatedResourceAccountIndex` / gRPC and HTTP endpoints (`RpcApiService`, `GetDelegatedResourceAccountIndexServlet`), meaning a bloated index degrades or can exhaust resources for that specific API path.

### Impact Explanation
This matches the report's bug class: cheap, repeated actions build a list that grows without bound and is later processed in full, degrading or breaking normal function for the affected account/API rather than the attacker's own account. Concretely: (1) every future `FreezeBalanceContract`/`UnfreezeBalanceActuator` operation involving the victim account becomes progressively more expensive to execute for the same fixed committed fee (potential resource/time exhaustion during block application for validators, i.e., partial denial of service for the affected account's transactions), and (2) the `getDelegatedResourceAccountIndex` query API returns the unbounded list, which a malicious caller can force to grow arbitrarily, degrading that API's serving cost for the target account. This is a resource-exhaustion / DoS-class issue rather than a direct fund theft.

### Likelihood Explanation
Exploitability depends on the chain-wide dynamic parameter `ALLOW_DELEGATE_OPTIMIZATION` being disabled (`supportAllowDelegateOptimization() == false`), which is the default unless the committee has enabled it via proposal. I was not able to confirm from the code alone what the current on-chain/mainnet value of this parameter is; if it has already been permanently enabled network-wide, this specific legacy code path is dead and the issue is not exploitable today. This is a material uncertainty I could not resolve with the tools available.

### Recommendation
- Enforce a maximum entry count (mirroring `UNFREEZE_MAX_TIMES`) on `toAccountsList`/`fromAccountsList` in the legacy `DelegatedResourceAccountIndexCapsule` path, or fully retire the non-optimized code path.
- Charge a fee proportional to the list size for `FreezeBalanceActuator` when it must append to these legacy index lists, or reject the delegation once a cap is reached.
- Confirm and, if necessary, force-enable `ALLOW_DELEGATE_OPTIMIZATION` network-wide so the O(1)-per-key `delegateV2`/`unDelegateV2` indexing scheme (which avoids single-object unbounded growth) is always used.

### Proof of Concept
Not independently reproduced in a running node; based on static code review:
1. Ensure `supportAllowDelegateOptimization()` returns `false` (default/unset dynamic parameter).
2. From N distinct attacker-controlled accounts, each holding at least the minimum freezable balance, submit `FreezeBalanceContract` transactions with `resource=BANDWIDTH` (or `ENERGY`) and `receiver_address` = victim's address, freezing a minimal amount.
3. Each transaction executes `FreezeBalanceActuator.delegateResource()`, appending the attacker's address into the victim's `fromAccountsList` via `DelegatedResourceAccountIndexStore.get`/`put` on the victim's key [5](#0-4) , with no fee scaling and no cap.
4. Repeat for large N; subsequent `FreezeBalanceContract`/`UnfreezeBalanceActuator` calls touching the victim, and calls to `Wallet.getDelegatedResourceAccountIndex` for the victim, must load/process the entire bloated list.
