### Title
Unprotected atomic `fetch_sub` on `CostTracker::block_cost` can underflow and stall block production - (File: cost-model/src/cost_tracker.rs)

### Summary
`CostTracker` mixes two different arithmetic-safety strategies for the same logical quantities: per-field counters (`transaction_count`, `allocated_accounts_data_size`, signature counts) are typed as `std::num::Saturating<u64>`, so their `-=` operators are safe. However, the block-level `block_cost` field is a `SharedBlockCost` wrapper around a raw `AtomicU64`, and its decrement path uses `AtomicU64::fetch_sub`, which wraps on underflow instead of saturating [1](#0-0) . This is the exact bug class described in the external report: unprotected math operators used where a safe/saturating equivalent exists elsewhere in the same struct.

### Finding Description
`sub_transaction_execution_cost` decrements both the per-account cost map (via `saturating_sub`) and the shared block cost (via raw `fetch_sub`): [2](#0-1) 

This is invoked from `remove_transaction_cost`, which is the backing implementation of the public `CostTracker::remove()` API used to reverse a transaction's previously-added cost: [3](#0-2) [4](#0-3) 

`remove()` is called from banking-stage's `Consumer::remove_added_transaction_costs`, which walks a per-batch vector of `Option<TransactionCost>` and removes every `Some` entry from the tracker whenever a batch of transactions fails to be recorded into PoH (e.g. `PohRecorderError::MaxHeightReached`): [5](#0-4) [6](#0-5) 

The invariant that `remove()` is only ever called exactly once per `try_add()` that actually mutated `block_cost` is maintained by hand across several code paths (`try_add_processed_transaction_costs`'s all-or-nothing/partial-batch rollback branches, plus the explicit `remove_added_transaction_costs` call on record failure) rather than being enforced by the type system. Unlike the per-account map (protected via `saturating_sub` and explicit zero-check/removal) and the scalar counters (protected via the `Saturating<u64>` wrapper type), `block_cost` has no such protection: any double-removal, removal for a cost that was rejected/never applied, or any future refactor that re-triggers a rollback path twice will cause `AtomicU64::fetch_sub` to wrap `block_cost` to a value near `u64::MAX`.

### Impact Explanation
`block_cost` is read by two safety-critical scheduling gates that assume it is monotonically bounded by `limits.block_cost`:
- `CostTracker::try_add` rejects further transactions once `block_cost.saturating_add(cost) > limits.block_cost` — an underflowed (near `u64::MAX`) `block_cost` would make every subsequent transaction fail this check for the rest of the slot, effectively halting block production/transaction inclusion by the leader for that bank.
- The banking-stage cost pacer and progress tracker read `shared_block_cost.load()` directly to compute remaining scheduling budget (`target.saturating_sub(self.shared_block_cost.load())` and `limit.saturating_sub(shared_block_cost.load())`), both of which would clamp to `0` once `block_cost` is corrupted: [7](#0-6) [8](#0-7) 

The practical effect is a leader that silently stops packing transactions for the remainder of the affected bank/slot — a concrete, unprivileged-user-reachable denial-of-service against block production, without any panic or crash (the corruption is purely logical, via wraparound, and persists until the next bank/slot resets the tracker via `new_from_parent_limits`).

### Likelihood Explanation
I was not able to fully verify, within the available tool budget, whether any current call path in `consumer.rs` can trigger `remove()` twice for the same transaction cost (i.e., prove a concrete double-decrement trigger under adversarial transaction sequencing/timing in the record-failure and all-or-nothing rollback branches). The invariant "one `remove()` per successful `try_add()`" is maintained manually across multiple branches (`try_add_processed_transaction_costs`, `remove_added_transaction_costs`, cost-tracker rollback), which is exactly the kind of manually-tracked invariant that is fragile to refactors and edge cases (e.g., interaction between the all-or-nothing rollback loop that already calls `cost_tracker.remove()` on a prefix, and a subsequent record failure that calls `remove_added_transaction_costs` on the same `transaction_costs` vector). Given this uncertainty, likelihood is assessed as **possible but unconfirmed** — the root architectural issue (unprotected `fetch_sub` on a value with no independent invariant enforcement, unlike its sibling fields in the same struct) is confirmed by direct code reading, but a concrete unprivileged-user-triggerable double-remove sequence was not proven end-to-end in this session.

### Recommendation
Make `block_cost`'s decrement path consistent with the rest of `CostTracker`'s already-safe fields: use `fetch_update`/`saturating_sub`-style compare-and-swap semantics (or store `block_cost` as `Saturating<u64>` behind a lock, mirroring `transaction_count`/`allocated_accounts_data_size`) instead of raw `AtomicU64::fetch_sub`, and add a debug assertion that the pre-subtraction value is `>= adjustment` to surface any invariant violation in tests before it manifests as silent wraparound in production. Additionally, audit and document (or assert) that `try_add`/`remove` pairs cannot be invoked more than once per transaction cost object across all banking-stage code paths.

### Proof of Concept
Not independently constructed/verified in this session — a full PoC would require driving the banking-stage record-failure path (`PohRecorderError::MaxHeightReached`) concurrently with an all-or-nothing batch rollback so that `remove()`/`sub_transaction_execution_cost` is invoked more than once for the same `TransactionCost`, then observing `CostTracker::block_cost()` wrap to a near-`u64::MAX` value and subsequent `try_add()` calls failing with `WouldExceedBlockMaxLimit` for the remainder of the bank.

    fn sub_transaction_execution_cost(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
        adjustment: u64,
    ) {
        for account_key in tx_cost.writable_accounts() {
            let account_cost = self
                .cost_by_writable_accounts
                .entry(*account_key)
                .or_insert(0);
            *account_cost = account_cost.saturating_sub(adjustment);
        }
        self.block_cost.fetch_sub(adjustment);
    }

pub struct SharedBlockCost(Arc<AtomicU64>);

        self.0.fetch_sub(value, Ordering::Release)
    }

    pub fn load(&self) -> u64 {
        self.0.load(Ordering::Acquire)

impl CostPacer {
    fn scheduling_budget(&self, current_time: &Instant) -> u64 {
        let target = if let Some(fill_time) = &self.fill_time {
            let time_since = current_time.saturating_duration_since(self.detection_time);
            if time_since >= *fill_time {
                self.block_limit
            } else {
                // on millisecond granularity, pace the cost linearly.
                let allocation_per_milli = self.block_limit / fill_time.as_millis() as u64;
                let millis_since_detection = time_since.as_millis() as u64;
                allocation_per_milli * millis_since_detection
            }
        } else {
            self.block_limit
        };

        target.saturating_sub(self.shared_block_cost.load())
    }
