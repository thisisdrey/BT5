### Title
Unchecked SIP-010 `transfer` boolean result in vault `receive-underlying`/`send-underlying` can cause silent share/asset accounting desync - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Every vault's `receive-underlying`/`send-underlying` helpers call the underlying SIP-010 token's `transfer` and only wrap the call in `try!`, which aborts on `(err ...)` but does nothing to validate that the inner boolean of an `(ok bool)` response is `true`. This mirrors the referenced Zerem `_sendFunds` bug class (ERC20 `transfer` returning `false` on failure instead of reverting): here the Clarity analog is a SIP-010 token whose `transfer` returns `(ok false)` on failure rather than an `(err ...)`. Because `try!` treats `(ok false)` the same as `(ok true)`, the vault proceeds as if the transfer succeeded even though no tokens moved.

### Finding Description
In `v0-vault-stx.clar`, `receive-underlying` and `send-underlying` are implemented as: [1](#0-0) 
and analogous code exists in every other vault: [2](#0-1) [3](#0-2) [4](#0-3) 

These helpers are invoked directly from the unprivileged `deposit`/`redeem` entry points: [5](#0-4) 

In Clarity, `try!` only aborts execution when the wrapped expression evaluates to a `(err ...)` response; it passes through `(ok anything)`, including `(ok false)`. SIP-010's `transfer` is specced to return `(response bool uint)`, so a token implementation that returns `(ok false)` on a failed transfer (e.g., due to an internal balance/allowlist check that doesn't want to hard-fail the whole call) is not distinguished from a real success by this code, because the inner boolean is never inspected — this is the exact "unsafe transfer" root cause described in the referenced report, adapted to SIP-010/Clarity's response-with-boolean pattern instead of Solidity's ERC20 `bool` return.

### Impact Explanation
- On `redeem`: shares are burned via `ft-burn?` before `send-underlying` is called, and `assets` is decremented immediately after in the same transaction regardless of whether `send-underlying`'s inner boolean was `true`. If the underlying token returns `(ok false)`, the user's shares are destroyed and vault accounting is decremented, but the user never receives the underlying tokens — a permanent freezing/loss of the user's unclaimed funds.
- On `deposit`, the same unchecked-boolean pattern in `receive-underlying` means shares could be minted to a depositor and `assets` incremented even though the vault never actually received the underlying tokens, understating the vault's real backing and diluting/desyncing share accounting for all other depositors (protocol insolvency risk for the pool).

Both outcomes map to in-scope impact classes: temporary/permanent freezing of user funds (redeem path) and protocol insolvency via broken vault share/asset accounting (deposit path), matching the "vault share math and interest accrual" and "market entry points" categories permitted by the rules.

### Likelihood Explanation
Exploitability depends on the underlying token contract returning `(ok false)` instead of erroring on a failed transfer — this requires a non-standard SIP-010 implementation among the assets the market/vault integrates with (analogous to the ZRX-style non-reverting ERC20 called out in the source report). Given Zest integrates with multiple external token contracts (`wstx`, `usdcx`, `usdh-token-v1`, `sbtc-token`, `ststx-token`, `ststxbtc-token-v2`) whose full source/behavior on failure is not guaranteed to be controlled by Zest, this is a plausible but token-dependent (Medium) likelihood, consistent with the Medium severity assigned in the original report.

### Recommendation
After every `contract-call? <token> transfer ...`, explicitly check the inner boolean of the `(ok bool)` response and abort with an error if it is `false`, e.g.:
```clarity
(asserts! (try! (contract-call? .wstx transfer amt tx-sender account none)) ERR-TRANSFER-FAILED)
```
instead of merely `(try! (contract-call? .wstx transfer amt tx-sender account none))`. Apply this fix uniformly across `receive-underlying`/`send-underlying` in all vault contracts and in `dao-treasury.clar`'s `withdraw`.

### Proof of Concept
1. A vault's underlying token (hypothetically a non-standard SIP-010 implementation) has an edge case where `transfer` returns `(ok false)` instead of `(err ...)` on failure (e.g. paused token, denylist, or a bug in the token contract).
2. A user calls `redeem` on, e.g., `v0-vault-stx.clar`.
3. `ft-burn?` succeeds, burning the user's zSTX shares. [6](#0-5) 
4. `send-underlying` calls the token's `transfer`, which returns `(ok false)`; `try!` does not abort because the response is `ok`. [7](#0-6) 
5. `assets` is decremented and the function returns `(ok inkind)` as if successful. [8](#0-7) 
6. The user's shares are gone, no underlying tokens were received — funds are permanently lost/frozen for that user, while the vault's internal `assets` bookkeeping no longer matches its real token balance.
