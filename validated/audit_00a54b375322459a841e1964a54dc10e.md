### Title
`Fee(Message)` charged from users can round its Ethereum-side `remote` component to zero, causing Snowbridge relayers to deliver messages unrewarded and letting bridge processing stall - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`pallet_outbound_queue::Pallet::calculate_fee` computes the total DOT fee charged to a user for delivering an XCM message to Ethereum. The fee is split into a `local` component (native weight fee) and a `remote` component that is supposed to fund the relayer's gas refund and reward on the Ethereum side. The `remote` component is derived from `U256` wei math and then truncated into native-currency decimals via integer division in `convert_from_ether_decimals`. With governance-set but plausible pricing parameters (e.g. a very low `exchange_rate`, low `fee_per_gas`/`reward`, low `multiplier`), this integer division can floor the `remote` fee to `0`, while the message is still accepted, queued, and delivered to Ethereum. This is the same "small-decimal rounds fee to zero" bug class as the referenced EURS report, but here the corrupted value is the bridge relayer-reward/gas-refund component of the delivery fee rather than a token-transfer fee.

### Finding Description
`calculate_fee` in [1](#0-0)  computes:
```
fee = calculate_remote_fee(gas_used_at_most, fee_per_gas, reward)      // U256, wei
fee = fee * multiplier / exchange_rate                                 // FixedU128 math, still ether-scale inner value
fee = convert_from_ether_decimals(fee)                                 // integer division by 10^(18-Decimals)
```
`convert_from_ether_decimals` performs a plain `checked_div` by `10u128.saturating_pow(decimals)` [2](#0-1) , with no minimum-fee floor and no rejection of a zero result. The pallet's own test explicitly demonstrates this: with valid, non-zero pricing parameters, `fee.remote` is computed as `0`: [3](#0-2) 

`PricingParameters::validate()` only checks that `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` are individually non-zero [4](#0-3) ; it does not simulate `calculate_fee` for a representative `gas_used_at_most` to guarantee the *derived* `remote` fee (after the exchange-rate division and decimal truncation) stays non-zero. Because the multiplication/division order is `fee_per_gas*gas + reward` → `* multiplier / exchange_rate` → `/ 10^(18-Decimals)`, a governance-set `exchange_rate` that is small (favorable DOT/ETH ratio) combined with a low `multiplier` can still pass `validate()` while yielding `fee.remote == 0` for realistic gas amounts.

`SendMessage::validate` in the outbound queue calls `calculate_fee` and returns the `(ticket, fee)` pair unconditionally — there is no check that `fee.remote` (or `fee.local`) is non-zero before accepting the ticket [5](#0-4) . The caller (XCM exporter / system pallet) charges the computed `Fee` and proceeds to `deliver()`, which unconditionally enqueues the message regardless of whether `remote` was zero.

By contrast, the codebase's own transaction-payment pallets explicitly guard against this exact failure mode for fee conversions: `FungiblesAdapter::withdraw_fee` enforces `min_converted_fee = 1` when the native fee is non-zero [6](#0-5) , and `SwapAssetAdapter`/`quote_price_tokens_for_exact_tokens` reject zero-quoted conversions via `.filter(|asset_fee| !asset_fee.is_zero())` [7](#0-6) . `pallet-psm` similarly rejects redemptions whose external-asset output truncates to zero via `AmountTooSmallAfterConversion` [8](#0-7) . No equivalent floor/rejection exists for Snowbridge's `remote` fee component.

### Impact Explanation
The `remote` fee funds `Min(GasPrice, Message.MaxFeePerGas) * GasUsed() + Message.Reward` paid to relayers on the Ethereum gateway contract, as documented in the pallet's own module docs [9](#0-8) . If `remote` is silently truncated to zero while the message is still committed and merkle-rooted for delivery, the system publicly accepts underpriced (here, entirely free) relaying work: messages are queued and require Ethereum-side execution and gas expenditure by relayers, but the escrowed/forwarded reward is zero. This degrades the economic incentive for honest relayers to submit messages, which can stall processing of the outbound queue to Ethereum — directly matching the "public underpriced work that ... stalls bridge processing" impact category. It does not require a malicious relayer, governance abuse, or leaked keys — it is purely a rounding defect reachable by any user who submits a message when pricing parameters and gas estimates combine unfavorably (or is triggerable by governance setting parameters that individually pass `validate()` but yield a zero derived fee).

### Likelihood Explanation
`PricingParameters::validate()` does not simulate the actual `calculate_fee` computation, so a governance update that passes validation can still produce a zero `remote` fee for typical `gas_used_at_most` values, as proven directly by the pallet's own test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` [3](#0-2) . Because Ethereum gas costs and ETH/DOT exchange rates are volatile, and Decimals is fixed at 10 or 12 [10](#0-9) , drift in `exchange_rate` toward favorable DOT valuation naturally pushes the derived remote fee toward the truncation boundary over time, without any additional guard to catch it before messages are queued.

### Recommendation
- In `calculate_fee`, after computing the truncated `remote` fee, enforce a minimum non-zero fee (mirroring `min_converted_fee` in `pallet-transaction-payment` asset adapters) whenever the pre-truncation remote fee was non-zero, or reject/round up instead of flooring.
- Extend `PricingParameters::validate` (or add a runtime integrity check) to simulate `calculate_fee` for a representative `gas_used_at_most` and reject parameter updates that would produce a zero `remote` component.
- In `SendMessage::validate` (`send_message_impl.rs`), explicitly reject tickets whose `fee.remote` is zero, rather than silently accepting and queuing the message.

### Proof of Concept
The existing unit test in the repository already demonstrates the corrupted value directly: [3](#0-2) 
With `exchange_rate = FixedU128::from_rational(1, 1)`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = FixedU128::from_rational(1,1)` — all individually non-zero and passing `PricingParameters::validate()` — `OutboundQueue::calculate_fee(250_000, price_params)` yields `fee.remote == 0` while `fee.local == 698_000_000`. Feeding this `Fee` through `SendMessage::validate`/`deliver` (`send_message_impl.rs` lines 41-88) would enqueue and commit the message for Ethereum delivery with zero relayer compensation, since neither function checks `fee.remote` for zero before proceeding.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
