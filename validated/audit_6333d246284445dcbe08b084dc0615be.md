### Title
Archive extraction path traversal via untar of unvalidated tar stream - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`server.untar` in `create_repository_from_snapshot.go` pipes the raw HTTP response body directly into `tar -C path -xvf -` with no path/entry validation, and the code comment itself acknowledges the archive is "trusted *a lot*" and "should undergo a lot of hardening" before pointing this RPC at endpoints not under Gitaly's control. Since `HttpUrl` is a caller-supplied field of `CreateRepositoryFromSnapshotRequest`, an attacker who controls the server behind that URL can serve a tar stream with `../` traversal entries or symlink entries that `tar` will happily extract, writing files outside the target repository directory.

### Finding Description
`CreateRepositoryFromSnapshot` (internal/gitaly/service/repository/create_repository_from_snapshot.go:123) creates a new repository at `path` via `repoutil.Create` and then calls `s.untar(ctx, path, in)` (line 142) to populate it. `untar` (line 87) issues an HTTP GET to `in.GetHttpUrl()`, and on success streams `rsp.Body` straight into `command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))` (lines 105–120). There is no call to `archive.TarEntries` or any other archive-entry inspection before extraction — that helper exists in the codebase (`internal/archive/tar_entries.go`) and is used only in the RPC's own test file (`generateTarFile` in create_repository_from_snapshot_test.go:58–70) to enumerate the trusted, self-generated tar for assertions, not to sanitize an attacker-supplied stream at runtime.

Because GNU `tar` by default extracts absolute paths and `../`-relative paths as given (subject only to normal filesystem permissions of the Gitaly process), a malicious tar containing entries such as `../../../etc/cron.d/x` or a symlink entry pointing outside `path` followed by a regular file written through that symlink can escape the intended repository storage directory. The RPC performs no allowlist/denylist filtering of entry names, no rejection of `..` components, and no rejection of symlink/hardlink header types before invoking `tar`.

The comment at lines 140–141 explicitly documents this as a known, unresolved trust issue: "the received archive is trusted *a lot*. Before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening."

### Impact Explanation
An attacker who can cause Gitaly to fetch a hostile tar via `HttpUrl` can write arbitrary files anywhere the Gitaly process user has filesystem permissions, outside the newly created repository's storage root. This is an archive-extraction/path-confinement escape (PATH_CONFINEMENT invariant violation) that can lead to file overwrite/planting outside the repo storage tree (e.g., dropping cron jobs, hook scripts, or corrupting other repositories/configuration files reachable by the process), which is significantly more severe than the intended blast radius of "create one repository from a snapshot."

### Likelihood Explanation
Exploitability depends entirely on whether GitLab Rails (or another caller of Gitaly) allows an unprivileged, attacker-controlled `HttpUrl`/`ResolvedAddress` to reach this RPC. If GitLab exposes a repository-import-by-URL / project-snapshot feature that lets a low-privileged user supply an arbitrary or self-hosted HTTP endpoint for this RPC (as implied by the audit's threat scenario), the attack is fully within reach: no admin role, no shell access, no leaked secret is required — only the ability to host an HTTP server and trigger the RPC with that URL. Within Gitaly's own code and tests, there is no gating that would prevent an already-reachable call from carrying a malicious tar; the only server-side control is HTTP auth to fetch the tar body, and status-code checking, neither of which constrains the tar's *content*. I could not, from this repo's context alone, confirm the exact Rails-side authorization/allowlisting for who may set `HttpUrl` on this RPC, so the real-world reachability by an unprivileged user should be verified independently; based purely on the audit's stated precondition ("attacker controls the HTTP server responding to HttpUrl"), the Gitaly-side code has no defense once that precondition holds.

### Recommendation
Do not pipe the HTTP response directly into `tar -xvf -`. Instead:
- Read/validate the tar stream in Go using `archive/tar` before or during extraction, applying `archive.TarEntries`-style checks (already present in the codebase) to reject entries with `..` path segments, absolute paths, or paths that resolve outside `path` after `filepath.Clean`/`filepath.Join`.
- Reject or strip symlink (`TypeSymlink`) and hardlink (`TypeLink`) tar entries, or verify their targets stay within the destination directory.
- Alternatively, extract into a temporary isolated directory and then move only expected, validated files into the final repository path, or use `tar --strip-components`/`--one-top-level` plus explicit `-C` confinement combined with pre-validated entry lists so `tar` itself never sees unsanitized untrusted paths directly from the network stream.

### Proof of Concept
```go
func TestCreateRepositoryFromSnapshot_pathTraversal(t *testing.T) {
	ctx := testhelper.Context(t)
	cfg, client := setupRepositoryService(t)

	// Build a malicious tar with a path-traversal entry.
	var buf bytes.Buffer
	tw := tar.NewWriter(&buf)
	evilContent := []byte("pwned")
	require.NoError(t, tw.WriteHeader(&tar.Header{
		Name: "../../../tmp/gitaly-evil-file",
		Mode: 0o644,
		Size: int64(len(evilContent)),
	}))
	_, err := tw.Write(evilContent)
	require.NoError(t, err)
	require.NoError(t, tw.Close())

	srv := httptest.NewServer(&tarTesthandler{tarData: bytes.NewReader(buf.Bytes()), secret: secret})
	defer srv.Close()

	repo := &gitalypb.Repository{
		StorageName:  cfg.Storages[0].Name,
		RelativePath: gittest.NewRepositoryName(t),
	}

	_, err = client.CreateRepositoryFromSnapshot(ctx, &gitalypb.CreateRepositoryFromSnapshotRequest{
		Repository: repo,
		HttpUrl:    srv.URL + tarPath,
		HttpAuth:   secret,
	})
	require.NoError(t, err)

	// Assert the traversal file landed outside the repository storage root.
	require.FileExists(t, "/tmp/gitaly-evil-file")
}
```
Expected: with the current implementation, `/tmp/gitaly-evil-file` is created outside the repository's storage directory, confirming the path traversal escape. After applying entry validation (rejecting `..`/absolute paths and symlink entries before extraction), this assertion should fail (`require.NoFileExists`) and the RPC should reject the malicious archive.
