### Title
Divergent rounding between per-account scaled debt (`market-vault`) and aggregate vault `principal-scaled` in `repay`/`system-repay` causes systemic insolvency drift - ([File: mainnet/contracts/market/v0-4-market.clar], [File: mainnet/contracts/vault/v0-vault-usdh.clar])

### Summary
This is a direct analog of the FutureCash `tradeLiquidityToken` rounding bug: a token amount is derived once via one division formula and used to update one ledger, while a second, independently-derived value (via a *different* division formula) is used to update a second ledger that is supposed to stay perfectly in sync with the first. Because Clarity integer division truncates, the two ledgers diverge, and the divergence compounds with every `repay`/`system-repay` call.

### Finding Description
In `market.clar`'s `repay`, the amount a specific account owes is converted to scaled units using the borrow index: [1](#0-0) 

`repaid-scaled-debt` is the value subtracted from the borrower's individual scaled-debt entry via `debt-remove-scaled` in `v0-market-vault.clar`, and `amount-to-repay` (rounded *up*, `mul-div-up`) is the token amount actually pulled and forwarded to the vault: [2](#0-1) 

The vault, however, receives only the raw token `amount` (`amount-to-repay`) and independently recomputes how much of *its own* aggregate `principal-scaled` to reduce — using a completely different formula, a straight proportional ratio against the vault's aggregate debt, not the per-user `INDEX-PRECISION`/`borrow-index` conversion used by the market: [3](#0-2) 

```
(define-private (calc-principal-ratio-reduction (amount uint) (scaled-principal uint) (debt-amount uint))
  (mul-div-down amount scaled-principal debt-amount))
``` [4](#0-3) 

The protocol's invariant requires `vault.principal-scaled` (aggregate) to always equal the sum of every individual account's `scaled` debt entry tracked in `market-vault`'s `debt` map, since both represent the same underlying obligations valued at the same shared `index`. But:
- `market.clar`'s per-account reduction (`repaid-scaled-debt`) is derived from `amount → scaled` via `mul-div-down(amount, INDEX-PRECISION, borrow-index)`, then re-derived back to `amount-to-repay` via `mul-div-up`.
- `vault`'s aggregate reduction (`principal-reduction`) is derived from the *token amount* via `mul-div-down(amount, scaled-principal, debt)` — a ratio against current aggregate state, not a conversion through the shared index at all.

These two formulas round differently on essentially every call (the FutureCash bug's exact mechanism: `tokensToRemove = f(collateralRequired)` vs `collateral = g(tokensToRemove)` using different ratios). Just as `totalCollateral` diverged from the true `currencyBalance` in FutureCash, here `vault.principal-scaled` (which underlies `total-debt()`, `get-available-assets()`, utilization/interest-rate calculation, and the debt cap check) will systematically drift away from the true sum of borrowers' individually-tracked scaled debt in `market-vault`. The same divergence pattern also exists on the borrow side: `system-borrow` computes its own `scaled-amount = mul-div-up(amount, INDEX-PRECISION, idx)` added to the vault's aggregate `principal-scaled`, which is a third independent computation path from whatever the market layer records for the specific account's debt increase.

### Impact Explanation
`total-debt()` (built from `principal-scaled`) directly drives `get-available-assets()`, which gates `redeem`, `system-borrow` liquidity checks, and the debt cap. If the vault's aggregate `principal-scaled` under-tracks debt relative to the true sum of per-account obligations (rounding down more often via `mul-div-down` ratio reduction than the per-account ledger which uses `mul-div-up` on the way back to tokens), `get-available-assets()` will overstate liquidity, allowing withdrawals/borrows that the vault cannot ultimately honor once every account's real debt is collected — this is a path to protocol insolvency and permanent freezing of funds for the last redeemers, since the drift compounds with every repay across every market and vault (`v0-vault-usdh`, `v0-vault-usdc`, `v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc` all share this pattern). This lands on the in-scope **Critical** impact class (protocol insolvency / permanent freezing of funds).

### Likelihood Explanation
This triggers on ordinary, unprivileged `repay` calls — no special permissions, no DAO action, and no flashloan trickery required. Every repay of every borrower on every asset hits this divergence; it does not need to be deliberately engineered by an attacker to occur, though an attacker can amplify it by performing many small repayments (each truncation event) to accelerate the drift between the vault's aggregate state and the true per-account sum.

### Recommendation
Do not let `market.clar` and the vault independently re-derive scaled-principal deltas via different formulas from the same nominal repayment/borrow event. Either:
1. Have `market.clar` pass the already-computed `repaid-scaled-debt` (in `INDEX-PRECISION` scaled units, using the shared `borrow-index`) directly to the vault's `system-repay`, and have the vault subtract that scaled amount directly from `principal-scaled` (mirroring how `socialize-debt-asset` already "passes scaled directly to avoid rounding" as noted in the code's own comment), instead of independently recomputing a ratio-based `principal-reduction`; or
2. Make the vault return the actual scaled-principal delta it applied, and force `market.clar` to use that returned value (not its own precomputed `repaid-scaled-debt`) for the per-account `debt-remove-scaled` call — exactly as the original report recommends uncommenting and using `_settleLiquidityToken`'s returned value instead of the pre-computed `collateralRequired`.

### Proof of Concept
1. Borrower A borrows via `system-borrow`; vault records `principal-scaled += scaled-amount = mul-div-up(amount, INDEX-PRECISION, idx)`, and `market.clar`/`market-vault` records the account's own scaled debt via the market's own conversion path.
2. Borrower A repays partially via `repay`. `market.clar` computes `repaid-scaled-debt = mul-div-down(safe-amount, INDEX-PRECISION, borrow-index)` and `amount-to-repay = mul-div-up(repaid-scaled-debt, borrow-index, INDEX-PRECISION)`; this exact `repaid-scaled-debt` is subtracted from the account's individual debt entry in `market-vault`.
3. The vault's `system-repay(amount-to-repay)` independently computes `principal-reduction = mul-div-down(amount-to-repay, scaled-principal, debt)` and subtracts that from `principal-scaled` — a value computed via a wholly different ratio, not tied to `borrow-index`/`INDEX-PRECISION` at all.
4. Because these two reductions use different truncating formulas, `principal-reduction != repaid-scaled-debt` in general. Repeat steps 1–3 across many borrowers/repayments (as happens continuously in production); the aggregate `vault.principal-scaled` (and therefore `total-debt()`/`get-available-assets()`) diverges from the true sum of all individually tracked account debts in `market-vault`, exactly as `totalCollateral` diverged from `currencyBalance` in the referenced FutureCash bug.
