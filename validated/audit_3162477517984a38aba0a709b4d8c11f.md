### Title
Refund receipt to nonexistent account is not permanently frozen — it is burnt, not lost or looping - ([File: runtime/runtime/src/lib.rs])

### Summary
The described scenario — a self-calling contract that redirects `refund_to_account_id` to a deleted/nonexistent account and then fails a `FunctionCall`, hoping the deposit refund becomes permanently undeliverable — does not create a freeze. NEAR's refund-receipt handling explicitly treats this case: refund receipts (`predecessor_id == "system"`) that fail to execute (e.g., because the target account doesn't exist) have their deposit amount burnt, not looped or left in limbo.

### Finding Description
`promise_set_refund_to` lets a predecessor override the refund recipient of a receipt it creates [1](#0-0) , storing it via `ReceiptManager::set_refund_to` [2](#0-1) . When that receipt's execution fails (e.g., an intentional panic in `promise_batch_action_function_call_weight`'s target), `refund_unspent_gas_and_deposits` builds a `Receipt::new_balance_refund` addressed to `receipt.balance_refund_receiver()`, which resolves to the overridden `refund_to` if set, or the predecessor otherwise [3](#0-2) .

This refund receipt itself is a plain `ActionReceipt` with `predecessor_id == "system"` [4](#0-3) . When the runtime processes it and the destination account does not exist, `apply_action` for a `Transfer` action against a nonexistent account fails with `AccountDoesNotExist` (transfers can only implicitly create accounts, and implicit account creation is explicitly disabled for refunds) [5](#0-4) . Critically, the runtime special-cases refund failures: if `receipt.predecessor_id().is_system()` and `result.result.is_err()`, the deposit amount is added to `stats.balance.other_burnt_amount` — it is burnt, not requeued, retried, or left dangling [6](#0-5) . This matches the documented invariant: "If the execution of a refund fails, the refund amount is burnt" [4](#0-3) .

So the attacker's flow (self-call with attached deposit + `promise_set_refund_to` pointed at a deleted account + guaranteed panic) does not "freeze" funds indefinitely or produce an undeliverable/looping receipt. It results in the deposit being burnt (removed from circulating supply, credited to `other_burnt_amount`, which reduces `total_supply` per the standard burn accounting) — a deliberate, self-inflicted loss of the attacker's own attached deposit, not a freeze exploitable against a victim, and not value creation or double-spend.

### Impact Explanation
There is no freezing bug and no reachable path to lock funds indefinitely, cause consensus divergence, or affect any other user's balance. The worst outcome is the attacker burning their own deposit, which is standard, accounted-for economic burn behavior (`other_burnt_amount`), not a vulnerability. No NEAR bounty category (theft, freezing of others' funds, inflation, double-spend, authorization escalation, consensus divergence, shard halt) applies.

### Likelihood Explanation
Not applicable — the "bug" as described does not exist; the runtime's design already accounts for and burns deposits that cannot be refunded to a dead/invalid account, by design and by test coverage in `test_refund_to` and refund/burn tests.

### Recommendation
No fix required. If desired for clarity, documentation could more explicitly state (as `docs/RuntimeSpec/Refunds.md` already does) that redirecting refunds to a nonexistent account results in the deposit being burnt rather than lost/frozen in an unrecoverable pending state, to avoid confusion for contract authors using `promise_set_refund_to`.

### Proof of Concept
Not applicable given no vulnerability. For confirmation, `runtime/runtime/tests/test_async_calls.rs::test_refund_to` already demonstrates the redirect mechanism [7](#0-6) ; an analogous test pointing `refund_to` at a deleted/nonexistent account would show the refund receipt executes, fails with `AccountDoesNotExist`, and the deposit is accounted into `other_burnt_amount`/burnt supply rather than persisting as an undeliverable or looping receipt, per `runtime/runtime/src/lib.rs:993-1000`.

fn test_refund_to() {

            },

        },
        {
            "action_function_call": {

                "method_name": "non_existing_function",
                "arguments": [],

                "gas": GAS_2,
            },
            "id": 0
        },
        {
            "set_refund_to": {
                "promise_index": 0,
                "beneficiary_id": "near_3"
            }, "id": 0
        }
    ]);

    let signed_transaction = SignedTransaction::from_actions(
        1,
        signer_sender.get_account_id(),
        signer_receiver.get_account_id(),
        &signer_sender,
        vec![Action::FunctionCall(Box::new(FunctionCallAction {

            args: serde_json::to_vec(&data).unwrap(),
            gas: GAS_1,
            deposit,
        }))],
        CryptoHash::default(),
    );

    let handles = RuntimeGroup::start_runtimes(group.clone(), vec![signed_transaction.clone()]);
    for h in handles {
        h.join().unwrap();
    }

    println!("{:?}", group.executed_receipts);

    use near_primitives::transaction::*;
    let [r0] = &*assert_receipts!(group, signed_transaction) else {
        panic!("Incorrect number of produced receipts")
    };

    let receipts = &*assert_receipts!(group, "near_0" => r0 @ "near_1",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),

        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_1);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "call_promise");
        }
    );
    let [r1, refunds @ ..] = &receipts else { panic!("Incorrect number of produced receipts") };
    group.assert_gas_refunds(&refunds[..]);
