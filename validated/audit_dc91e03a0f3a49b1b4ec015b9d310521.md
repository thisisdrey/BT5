### Title
Missing fallback for uninitialized `accountIndexOf` when token index equals `INITIAL_INDEX` lets holders drain reward tokens - (File: contracts/RewardsDistributor.sol)

### Summary
The Linux bug class is "a struct field left uninitialized and later read" (`fattr->mdsthreshold`). The Metronome analog is `RewardsDistributor._calculateTokenDelta()`: it reads `accountIndexOf[token_][account_]`, which is `0` for any account that held a balance before reward tracking began. The code guards this with a fallback to `INITIAL_INDEX`, but only when `_tokenIndex > INITIAL_INDEX`. During the window where `tokenStates[token_].index == INITIAL_INDEX` (i.e., the same block `tokenSpeeds` is first set), the uninitialized `accountIndex` of `0` is used directly, producing `_deltaIndex = 1e18` and crediting the account `balanceOf(account)` reward tokens — even though zero time elapsed and zero rewards were actually earned.

### Finding Description
`_calculateTokenDelta` at `contracts/RewardsDistributor.sol:217-231`:

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback assumes the supply index has already grown past `INITIAL_INDEX`. But when a token's speed is first set in `_updateTokenSpeed`, `tokenStates[token_]` is initialized to `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (`contracts/RewardsDistributor.sol:298`). In that same block, `_calculateTokenIndex` computes `_deltaTimestamps = 0` and returns `_newIndex = 0`, so `_updateTokenIndex` leaves the index at exactly `INITIAL_INDEX` (`contracts/RewardsDistributor.sol:202-212`).

Any account whose balance was set while `index == 0` (all pre-existing depositors/borrowers, since `updateBeforeMintOrBurn`/`updateBeforeTransfer` no-op when `tokenStates[token_].index == 0`, lines 175-192) has `accountIndexOf == 0`. In the same block the speed is enabled, `_deltaIndex = 1e18 - 0 = 1e18`, and `tokensDelta = balance.wadMul(1e18) = balance` is credited to `tokensAccruedOf[account]` (`contracts/RewardsDistributor.sol:261-265`). `claimRewards` then pays out via `_transferRewardIfEnoughTokens` (lines 248-256).

### Impact Explanation
Every pre-existing holder of a DepositToken/DebtToken is credited `tokensAccruedOf` equal to their entire token balance in `rewardToken` units the instant rewards are enabled, despite earning nothing. `claimRewards` is permissionless and pays out as long as the distributor holds enough `rewardToken`, draining funds reserved for other users' legitimate yield — direct theft of unclaimed yield/protocol reward funds. Multiple accounts can claim until the distributor balance is exhausted.

### Likelihood Explanation
The exploit window is the same block the governor enables a nonzero `tokenSpeed` (one block later, `index > INITIAL_INDEX` and the fallback engages). An unprivileged attacker can watch the mempool for `updateTokenSpeed`/`updateTokenSpeeds`/`syncTokenSpeed`, hold (or flash-acquire) a DepositToken/DebtToken balance beforehand so `accountIndexOf == 0`, and call `claimRewards` in the same block. Note `syncTokenSpeed` is callable by a permissioned keeper, not a fully public path, but the governor paths are public transactions observable in the mempool. No modifiers, health checks, or reentrancy guards prevent the claim; `nonReentrant` is irrelevant to the arithmetic flaw. Likelihood is moderate: it depends on sandwiching the single speed-enabling transaction, which occurs once per token per distributor.

### Recommendation
In `_calculateTokenDelta`, apply the fallback whenever the account index is uninitialized and a nonzero supply index exists, not only when it exceeds `INITIAL_INDEX`:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Equivalently, initialize `accountIndexOf` to `INITIAL_INDEX` in `_updateTokensAccruedOf`/`updateBefore*` for first-touch accounts, or treat `_accountIndex == 0` as `_tokenIndex` (zero delta) instead of `0`.

### Proof of Concept
Hardhat fork sketch:

```ts
// Setup: msUSD/mETH pool live, depositToken (e.g. vaUSDC) registered,
// RewardsDistributor registered on Pool, funded with rewardToken (e.g. MET).

// 1. Attacker (or existing user) holds depositToken balance before rewards exist.
//    depositToken.balanceOf(attacker) = B; accountIndexOf[token][attacker] == 0.
await depositToken.connect(attacker).deposit(B);

// 2. Governor enables speed; in the SAME block attacker front-runs/sandwiches.
await rewardsDistributor.connect(governor).updateTokenSpeed(depositToken.address, speed);

// 3. Same block: index == INITIAL_INDEX, timestamp == block.timestamp.
await rewardsDistributor.connect(attacker).claimRewards(attacker.address, [depositToken.address]);

// tokensAccruedOf[attacker] == B (reward-token units), and rewardToken
// was transferred to attacker despite zero elapsed accrual time.
expect(await rewardToken.balanceOf(attacker.address)).to.be.gt(0);
```

Key assertions: `tokenStates[depositToken].index == 1e18`, `accountIndexOf[depositToken][attacker] == 0` before the claim, `_deltaIndex == 1e18`, and `tokensAccruedOf[attacker]` is set to `B.wadMul(1e18)` then paid out by `_transferRewardIfEnoughTokens`.
