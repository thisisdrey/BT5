## Title
Authorization token compared with non-constant-time `!=` on privileged block-write RPC endpoints — timing side-channel enables token recovery ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
Three RPC handlers that gate privileged, state-mutating write paths compare the client-supplied `authorization` header against the node's secret `auth_token` using the standard `!=` string comparison operator instead of a constant-time comparison. This is the exact bug class described in the CodeIgniter/Kohana advisory (CVE-2014-8684): using ordinary string-equality operators to compare a security-critical secret leaks timing information proportional to the length of the matching prefix, letting a remote, unauthenticated attacker recover the secret byte-by-byte and then forge valid `Authorization` headers.

### Finding Description
`RPCPostBlockRequestHandler::try_parse_request` (guards `POST /v2/blocks?broadcast=1`), `RPCBlockProposalRequestHandler::try_parse_request` (guards `POST /v3/block_proposal`), and `RPCNakamotoBlockReplayRequestHandler::try_parse_request` (guards `GET /v3/blocks/replay/:block_id`) all perform the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `auth_header != password` is a plain `String`/`str` comparison. Rust's `str`/`[u8]` equality first checks length, then performs a byte-wise comparison that returns as soon as a mismatch is found — it is not designed to be constant-time. An attacker who can measure response latency with sufficient precision (over many repeated requests, which is standard practice for network timing attacks against secret comparisons) can incrementally recover `auth_token` one byte/prefix at a time, exactly analogous to the session-cookie/HMAC comparison flaw in the referenced advisory.

`auth_token` is the shared secret between a `stacks-node` and its `stacks-signer`, documented as securing both the signer's block-proposal channel and the `/v2/blocks?broadcast=1` write path: [4](#0-3) 

### Impact Explanation
Recovering `auth_token` via this timing side-channel allows a remote, unauthenticated attacker to:
- Submit forged block proposals to `/v3/block_proposal` as if it were the trusted signer, or
- Force a broadcast of an arbitrary Stacks block via `/v2/blocks?broadcast=1`, or
- Access the internal block-replay/profiler debug endpoint.

This is an unauthorized write/auth-bypass on state-affecting node endpoints, matching the "Critical: unauthenticated/unauthorized write to state ... auth bypass" impact category.

### Likelihood Explanation
Exploitation requires the operator to have configured `auth_token` (it is off by default) and requires an attacker to perform many timed requests against the same secret to statistically distinguish prefix-length matches from network jitter — a nontrivial but well-established technique (as demonstrated by the CVE-2014-8684 research referenced in the advisory). No node secret or privileged role is needed to begin the attack; only network reachability to the RPC endpoint is required.

### Recommendation
Replace the plain `!=` comparisons in `postblock_v3.rs`, `postblock_proposal.rs`, and `blockreplay.rs` (and `blocksimulate.rs`, which follows the same pattern) with a constant-time comparison (e.g., `subtle::ConstantTimeEq` or a manual XOR-accumulate comparison over the full byte length regardless of early mismatches) when checking the `authorization` header against the configured secret.

### Proof of Concept
1. Configure `auth_token = "<secret>"` on a node exposing `/v3/block_proposal`.
2. From a remote unauthenticated client, repeatedly send `POST /v3/block_proposal` with `Authorization` headers of varying candidate prefixes, measuring response latency for the `auth_header != password` check at line 1142 of `postblock_proposal.rs`.
3. Statistically distinguish latency for candidates whose prefix matches more bytes of the true secret vs. those that mismatch earlier, and iteratively extend the guessed prefix until the full `auth_token` is recovered.
4. Use the recovered token to submit a forged block proposal or broadcast an arbitrary block via `/v2/blocks?broadcast=1`.
