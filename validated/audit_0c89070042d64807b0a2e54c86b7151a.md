### Title
`mt_resolve_withdraw` treats a length-mismatched but successful `mt_batch_transfer_call` result as total failure, causing a full double-credit refund - (File: `contracts/defuse/src/contract/tokens/nep245/withdraw.rs`)

### Summary
`mt_resolve_withdraw` only accepts the `used` amounts array returned by `mt_batch_transfer_call` when `used.len() == amounts.len()`; any other successfully-deserialized array (including a valid JSON array of the wrong length) is silently treated as `used = vec![U128(0); amounts.len()]`, i.e. "nothing was transferred." Because the length check is not enforced by the JSON-size guard (`promise_result_checked_json_with_len` only caps the byte size, it does not enforce array length), an attacker's own MT `token` contract can legitimately transfer all the tokens to `receiver_id` yet return a success array one element short, forcing the Verifier to refund the *entire* withdrawn batch back to the withdrawer even though the tokens already left custody.

### Finding Description
Broken binding: for every `token_id` in the batch, `amount_debited == amount_delivered_to_receiver + amount_recredited` should hold. The exploit breaks it into `amount_debited == amount_delivered_to_receiver + amount_debited` (full double credit), because `amount_recredited` is computed from a `used` array that the code discards on any length mismatch rather than on genuine transfer failure.

Code path:
- `internal_mt_withdraw` debits the caller's balance via `self.withdraw(...)` for every `(token_id, amount)` pair before any cross-contract call happens: [1](#0-0) 
- It then schedules `do_mt_withdraw` -> `mt_batch_transfer_call` on the attacker-controlled `token` contract, followed by `mt_resolve_withdraw` as the resolving callback: [2](#0-1) 
- `do_mt_withdraw` invokes `mt_batch_transfer_call` on the externally-controlled `token` contract: [3](#0-2) 
- `mt_resolve_withdraw` deserializes the promise result and only accepts it when the returned length matches; any other successfully-parsed result (e.g. `amounts.len()-1` elements) is treated identically to a malformed/failed call, i.e. zero tokens used: [4](#0-3) 
- The subsequent refund computation then re-credits the *full* amount for every `token_id`, because `used.0` is `0` for all entries: [5](#0-4) 
- Confirming that the length-check helper does not itself enforce exact array length (it only bounds the serialized byte size for gas/stack safety, and `serde_json::from_slice` will happily deserialize a shorter `Vec<U128>`): [6](#0-5) 

Root cause: the `Ok(_) => vec![U128(0); amounts.len()]` branch conflates "malformed/short response" with "nothing was transferred." Since the attacker controls the `token` contract's `mt_batch_transfer_call` implementation entirely (per the unprivileged-attacker profile, which explicitly allows deploying and controlling one's own MT contract), they can genuinely deliver all tokens to `receiver_id` and still return an array shorter by one element, triggering the full-refund branch for the entire batch. None of `MultiPayload::verify`, `has_public_key`, nonce/salt checks, `assert_one_yocto`, or `#[private]` on `mt_resolve_withdraw` prevent this — those guard the *authorization* of the withdraw intent (which the attacker withdraws for themselves) and the callback's caller (`env::current_account_id()`), not the semantic correctness of the cross-contract JSON payload it acts upon.

Exploit flow: attacker deposits into Defuse tokens of their own MT contract (`token`), then calls `mt_withdraw` with `msg` set (so `is_call = true`) targeting `receiver_id` (their own account/second contract). Their `token` contract's `mt_batch_transfer_call` genuinely moves the assets to `receiver_id` but returns `Vec<U128>` of length `amounts.len()-1`. `mt_resolve_withdraw` falls into the `Ok(_)` mismatched-length branch, sets `used = [0; N]`, and re-credits the attacker's Defuse balance for every `token_id` in the batch by the full withdrawn amount — while the tokens have already left custody to `receiver_id`.

### Impact Explanation
The attacker ends up holding both: (1) the tokens physically delivered outside Defuse to `receiver_id`, and (2) a fully restored internal Verifier ledger balance for the same `token_id`s, which they can now trade/swap against real counterparties via `execute_intents`, or withdraw again. This inflates the Verifier's internal ledger beyond what is actually custodied for that `token`, matching the Critical category "a refund or resolver credit that does not match what failed to settle" / "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies." The exploit is repeatable per batch and per token contract the attacker controls, and the fabricated ledger balance can subsequently be used to extract genuine value from other users through matched swap intents.

### Likelihood Explanation
Fully attacker-controlled: they only need to deploy their own NEP-245 MT contract implementing `mt_batch_transfer_call` to intentionally return a mis-sized array, deposit some of that token into Defuse, and call `mt_withdraw` with a `msg`. No privileged role, relayer key, or victim key is required. Cost is limited to gas and storage deposit for their own contracts. It is deterministically reproducible in a sandbox test.

### Recommendation
In `mt_resolve_withdraw`, distinguish "malformed/wrong-length response" from "confirmed zero transferred." A length mismatch should either be treated as a hard failure (panic, since the callback's own promise contract violated the interface, similar to `Err(_) => amounts.clone()` which conservatively assumes nothing was refunded is wrong direction) — but the safer minimal fix is: on any length mismatch, do **not** refund (`used = amounts.clone()`, matching the "insufficient gas" comment's conservative philosophy of not compounding lost funds through spurious refunds), or reject/require the exact length and let the promise fail loudly rather than silently defaulting to `vec![U128(0); amounts.len()]`.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox):
1. Deploy the Defuse contract and a malicious MT `token` contract whose `mt_batch_transfer_call` always transfers the requested amounts of all `token_ids` to `receiver_id` (updating the mock's own internal balances) but returns a `Vec<U128>` of length `amounts.len() - 1`.
2. As the unprivileged attacker account, deposit N distinct `token_id`s of that MT contract into Defuse (via `mt_on_transfer`), recording `balance_before = defuse.mt_balance_of(attacker, token_id)` for each.
3. Call `mt_withdraw(token, receiver_id, token_ids, amounts, memo, msg=Some(...))` with `assert_one_yocto` deposit.
4. Assert on both sides of the broken binding:
   - `mock_token.mt_balance_of(receiver_id, token_id) == amounts[i]` for every `token_id` (tokens genuinely delivered).
   - `defuse.mt_balance_of(attacker, token_id) == balance_before[i]` for every `token_id` (full refund happened despite genuine delivery) — proving `amount_debited == amount_delivered + amount_recredited_full` instead of `amount_recredited == 0`.
5. This demonstrates the Verifier's ledger for that `token` is now inflated by the full withdrawn batch beyond what is actually custodied.

pub fn promise_result_checked_json_with_len<T: MaxJsonLength<Args = (usize, ())>>(
    result_idx: u64,
    length: usize,
) -> PromiseJsonResult<T> {
    let max_len = T::max_json_length_root((length, ()));
    let value = env::promise_result_checked(result_idx, max_len)?;
    Ok(serde_json::from_slice::<T>(&value))
}
