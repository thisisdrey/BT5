### Title
Global unstaked-blind `overall_connection_rate_limiter` allows IP-diverse unstaked attacker to starve staked-peer TPU connections - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC connection admission pipeline in `run_server`/`setup_connection` gates all new connections — staked and unstaked alike — behind a single global `TokenBucket` (`overall_connection_rate_limiter`) sized at `MAX_CONNECTION_BURST`=1000 tokens refilling at `TOTAL_CONNECTIONS_PER_SECOND`=2500/s, with no stake-aware reservation or priority lane. Since stake is only known *after* the QUIC handshake completes, an unstaked attacker who can originate genuine completed handshakes from many distinct source IPs can continuously drain this shared bucket, causing `incoming.ignore()`/`close(CONNECTION_CLOSE_CODE_DISALLOWED)` to be issued against subsequently arriving connections regardless of their stake.

### Finding Description
In `run_server` [1](#0-0)  a single `overall_connection_rate_limiter` `TokenBucket` is created and shared across the entire endpoint, independent of any per-stake logic. On each incoming connection, the accept loop first peeks this global bucket: [2](#0-1) 

and only afterwards performs the per-IP `rate_limiter.is_allowed` check [3](#0-2) . Neither of these gates has any notion of stake — stake can only be resolved after TLS/QUIC handshake completes and the remote pubkey is extracted (`get_connection_stake`, called later in the per-connection setup after `qos.build_connection_context`) [4](#0-3) . The actual token consumption for the global bucket happens in `setup_connection` after a successful handshake: [5](#0-4) 

Because `TokenBucket` is a flat, unweighted structure (see `net-utils/src/token_bucket.rs`, `consume_tokens`) with no per-key/per-stake partition, any successfully-completed connection — whether from a staked validator or an anonymous unstaked client — draws from the identical shared pool of 1000 burst / 2500-per-second admission slots. The code comment above the checks explicitly documents the trade-off ("shed fast and bound resource consumption... before a peer has asserted control over their ip address") but does not include any stake-based carve-out or reserved allocation for staked identities once handshakes do complete. Consequently, a client controlling many distinct source IPs (no stake, no special config required — matching the "unprivileged/unstaked remote client" threat model) can sustain a stream of real completed QUIC handshakes exceeding 2500/s, keeping `overall_connection_rate_limiter.current_tokens()` at or near 0. Any staked peer whose connection attempt arrives during that window is rejected at line 347 (`incoming.ignore()`) purely due to global exhaustion — before its own per-IP or per-stake accounting is ever consulted.

### Impact Explanation
This is a TPU-wide connection-admission starvation: unstaked/unprivileged traffic can unfairly capture the global connection-rate budget and deny staked/legitimate senders' new connections, directly matching the described bounty category "An unprivileged, unstaked client can bypass or unfairly capture connection, stream, or per-IP QoS limits and starve legitimate senders of TPU capacity." The blast radius is scoped to new-connection admission (existing/keep-alive connections from staked peers already established are unaffected), but during sustained attack, staked nodes attempting to (re)connect (e.g., after routine QUIC connection churn, rotated client endpoints, or restarts) would be denied entry to the leader's TPU regardless of their stake weight.

### Likelihood Explanation
Exploitation requires the attacker to complete real QUIC handshakes (QUIC's address-validation/Retry mechanism as referenced in the code comment prevents pure IP spoofing from consuming this budget) from a sufficiently large and diverse pool of source IPs sustained above 2500 handshakes/sec — feasible for an attacker with a botnet, cloud-based IP rotation, or an IPv6 /64 allocation, none of which require stake or validator identity. This is a purely volumetric/distributed-IP precondition, consistent with the question's stated preconditions, and does not require any privileged, staked, or gossip-participant capability.

### Recommendation
Introduce a stake-aware reservation in the global connection admission path: e.g., split `overall_connection_rate_limiter` into a fast-path reserved bucket for previously-seen-staked source IP/pubkey pairs (using cached stake-table lookups keyed by IP prior to full handshake, where feasible) or weight/reserve a minimum fraction of `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND` capacity exclusively for staked identities post-handshake, so unstaked volumetric admission attempts cannot fully saturate the shared token pool.
