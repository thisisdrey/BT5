Audit Report

## Title
Snowbridge relayer reward is irreversibly cleared on successful XCM *send* rather than confirmed settlement on AssetHub — (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`pallet_bridge_relayers::do_claim_rewards` deletes a relayer's `RelayerRewards` entry as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For the Snowbridge reward kind, `PayAccountOnLocation::pay_reward` only validates, charges local delivery fees, and enqueues an `UnpaidExecution`/`ReserveAssetDeposited`/`DepositAsset` XCM to AssetHub — success means only "handed to the local outbound queue," not "executed and settled on AssetHub."

## Finding Description
`do_claim_rewards` uses `RelayerRewards::<T, I>::try_mutate_exists` to atomically `take()` the reward balance and invoke `T::PaymentProcedure::pay_reward`; the record is permanently removed once `pay_reward` returns `Ok(())`, regardless of what happens afterward on the destination chain [1](#0-0) .

For `BridgeReward::Snowbridge`, `pay_reward` is implemented as `PayAccountOnLocation::pay_reward`, which builds a fire-and-forget XCM (`UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, `DepositAsset`), calls `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver`, and returns `Ok(())` as soon as delivery to the outbound queue succeeds — with no message id, receipt, or callback retained to confirm remote execution [2](#0-1) .

The only error paths modeled and tested are strictly local/synchronous: XCM validation failure, fee-charging failure, and delivery failure at the sender queue — as shown by the unit tests `pay_reward_fails_on_xcm_validate_xcm`, `pay_reward_fails_on_charge_fees`, and `pay_reward_fails_on_delivery` [3](#0-2) . None of these tests (nor the production code) verify or wait for confirmation that AssetHub actually executed the `ReserveAssetDeposited`/`DepositAsset` sequence and credited the `beneficiary`. Once `deliver()` succeeds, `do_claim_rewards`'s `try_mutate_exists` guard considers the operation successful and the storage mutation (deleting the reward entry) is committed — there is no mechanism to detect or roll back on asynchronous remote failure (e.g., AssetHub `Barrier` rejecting the `UnpaidExecution` for that origin, a malformed `beneficiary` causing the deposit to trap, or reserve-trust misconfiguration for the `UniversalOrigin(GlobalConsensus(Ethereum))` path).

## Impact Explanation
If the destination-side XCM execution fails post-delivery, the relayer's reward is permanently and irrecoverably erased from `RelayerRewards` with no funds ever credited to the beneficiary — a broken settlement-atomicity condition matching "duplicate settlement or payout, permanent user-fund or bridge-state lock" in the accepted impact set. The exact corrupted state is the `RelayerRewards<T, I>` double-map entry for `(relayer, BridgeReward::Snowbridge)`, which is deleted based on local delivery success rather than confirmed remote settlement.

## Likelihood Explanation
The path is reachable via the permissionless, signed extrinsic `claim_rewards_to` [4](#0-3) , requiring no privileged actor or compromised infrastructure — only a normal relayer claim combined with any destination-side condition causing the XCM to fail after being accepted for delivery (barrier/config drift, an ill-formed but well-formed-looking beneficiary `Location`, or reserve-trust misalignment). This is an architectural gap between local "send success" and remote "settlement success," not a contrived multi-step attack.

## Recommendation
Do not treat `XcmSender::deliver()` success as final settlement. Retain the reward record (or a pending/receipt marker) until confirmed execution feedback from AssetHub is received — e.g., adopt a two-phase pattern analogous to `PayOverXcm`'s query-id/`check_payment` mechanism — and only clear `RelayerRewards` after explicit settlement confirmation, with a recovery path to re-credit the reward if the remote message fails or the deposited assets are trapped.

## Proof of Concept
1. Relayer accrues a reward for `BridgeReward::Snowbridge` via `register_reward`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))`.
3. `do_claim_rewards` calls `RelayerRewards::try_mutate_exists`, takes the reward balance, and invokes `PayAccountOnLocation::pay_reward`, which succeeds through `validate_send`/`charge_fees`/`deliver` and returns `Ok(())` [5](#0-4) [6](#0-5) ; the `RelayerRewards` entry is deleted (`maybe_reward.take()`).
4. On AssetHub, execution of the `UnpaidExecution`/`ReserveAssetDeposited`/`DepositAsset` sequence fails (barrier rejection, trap on bad beneficiary, or reserve-trust misconfiguration), so no asset is ever credited to the beneficiary.
5. Relayer calls `claim_rewards_to` again and receives `Error::NoRewardForRelayer` — the reward is permanently gone with no funds delivered. Existing unit tests in `bridges/snowbridge/primitives/core/src/reward.rs` (`pay_reward_fails_on_xcm_validate_xcm`, `pay_reward_fails_on_charge_fees`, `pay_reward_fails_on_delivery`) confirm that only local/synchronous failures are modeled, and none simulate or check for remote execution failure, demonstrating that send success and settlement success are unguarded and decoupled [7](#0-6) .

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
