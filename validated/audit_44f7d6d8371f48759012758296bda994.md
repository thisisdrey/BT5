### Title
Non-constant-time bearer-token comparison enables timing side-channel to recover the `auth_token` on privileged RPC endpoints - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
Several `/v3/*` HTTP RPC handlers gate privileged operations (block proposal submission, authenticated block broadcast, fast-call-read, block/tx replay and simulate) behind a single shared-secret string compared with Rust's built-in `!=` operator on `String`/`&str`. This comparison is not constant-time, and an unauthenticated remote attacker can exploit the timing differential to recover the secret byte-by-byte, exactly the exploitation technique used in the referenced Apache Archiva CVE-2020-9495 advisory (timing-based extraction of secret data from an authentication check).

### Finding Description
`RPCPostBlockRequestHandler::try_parse_request` reads the `authorization` header and compares it directly against the configured secret: [1](#0-0) 

```
if let Some(password) = &self.auth {
    if let Some(auth_header) = preamble.headers.get("authorization") {
        if auth_header != password {
            return Err(Error::Http(401, "Unauthorized".into()));
        }
        authenticated = true;
    }
}
```

The identical pattern (`auth_header != password`) is used to gate the block-proposal validation endpoint: [2](#0-1) 

Both `auth_token`/`password` are HTTP-facing shared secrets configured in `[connection_options]` (`auth_token`) and used to authenticate the `stacks-signer` and to authorize `/v2/blocks?broadcast=1` and `/v3/block_proposal` requests, per its own documentation: [3](#0-2) 

`grep` confirms the exact same `auth_header`-based check (2 occurrences: header lookup + inequality comparison) is repeated verbatim in `stackslib/src/net/api/fastcallreadonly.rs`, `stackslib/src/net/api/blockreplay.rs`, `stackslib/src/net/api/blocksimulate.rs`, and `stackslib/src/net/api/txsimulate.rs`, all guarding privileged, state-mutating or compute-heavy endpoints with the same shared token.

Rust's `PartialEq` for `str`/`String` performs a length check followed by a byte-wise comparison that returns as soon as a difference is found — it is not designed or guaranteed to run in constant time. This breaks the intended equality "presented header == configured secret" into an information channel: the more leading bytes an attacker's guess shares with the real secret, the (on average, statistically) longer the comparison takes before it fails. Over many network requests with statistical averaging, this allows incremental byte-by-byte recovery of the secret — the same "measure response time to leak protected data" bug class as the reported Archiva LDAP timing attack, but here targeting a bearer-token authentication gate on the node's own privileged Nakamoto-era RPC surface rather than an LDAP filter.

### Impact Explanation
Recovering the `auth_token` grants an unauthenticated remote attacker the ability to:
- POST fabricated Nakamoto blocks to `/v3/blocks/upload/?broadcast=1`, forcing the node to relay attacker-supplied block data network-wide (`stackslib/src/net/api/postblock_v3.rs`),
- submit arbitrary block proposals to `/v3/block_proposal`, impersonating the trusted `stacks-signer` channel (`stackslib/src/net/api/postblock_proposal.rs`),
- invoke fast-call-read, block/tx replay and simulate endpoints intended to be gated behind this secret.

This is an authentication-bypass vector on network-facing endpoints that mediate block propagation/validation trust, matching the "auth bypass" / "network-wide propagation of forged data" Critical impact tier in the report's rubric — provided the timing signal is measurable and averaged over sufficient samples (network jitter reduces but does not eliminate practical exploitability of such timing side channels, as demonstrated by the cited CVE).

### Likelihood Explanation
The comparison is reachable by any unauthenticated network peer that can send HTTP requests to the node's RPC endpoint — no prior credentials, connection state, or privileged role is required. Exploitation requires statistical timing measurement across repeated requests (mitigated somewhat by network noise and secret length), so likelihood is lower than a deterministic bypass but non-trivial given the endpoints are always network-reachable when `auth_token` is configured.

### Recommendation
Replace the direct `!=` string comparison with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or hashing both sides with a fixed-time MAC comparison) in all affected handlers: `postblock_v3.rs`, `postblock_proposal.rs`, `fastcallreadonly.rs`, `blockreplay.rs`, `blocksimulate.rs`, and `txsimulate.rs`. Centralize the auth-token check in one helper function to avoid divergence and ensure any future endpoint reusing this pattern also gets the constant-time comparison.

### Proof of Concept
1. Configure a node with `auth_token = "<secret>"` and start the RPC service exposing `/v3/blocks/upload/?broadcast=1`.
2. From a remote unauthenticated host, repeatedly send POST requests with an `authorization` header containing incrementally-guessed prefixes (`"a"`, `"aa"`, `"ab"`, ... ), measuring response latency for each guess.
3. Average many samples per candidate prefix to filter network jitter; the prefix yielding a statistically longer average rejection time indicates a correct partial match, since the underlying byte-wise comparison performs more work before failing.
4. Iterate this per-character search until the full `auth_token` is recovered, then use it to gain `authenticated = true` in `postblock_v3.rs`/`postblock_proposal.rs`, bypassing the intended access control.
