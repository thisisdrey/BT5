### Title
Origination Fee Rounds Down to Zero on Small Borrows, Allowing Fee-Free Looping/Borrowing - (File: `programs/marginfi/src/instructions/marginfi_account/borrow.rs`)

### Summary
`lending_account_borrow` computes the origination fee by truncating (flooring) an `I80F48` fixed-point value to `u64` instead of rounding up, unlike the repay-side/bankruptcy accounting in this codebase which explicitly rounds up ("ceil") origination fees. This lets an unprivileged borrower split a large borrow into many small borrows, each individually small enough that the computed fee truncates to zero, extracting a fee-free (or under-fee) loan overall — the same rounding/fee-bypass bug class described in the external Riz report.

### Finding Description
In `lending_account_borrow`, the origination fee is derived from the bank's `protocol_origination_fee` rate and the pre-fee borrow amount, then converted to `u64` via `checked_to_num()`, which truncates toward zero rather than rounding up: [1](#0-0) 

```
let (origination_fee_u64, share_amount): (u64, I80F48);
if !origination_fee_rate.is_zero() {
    origination_fee = I80F48::from_num(amount_pre_fee)
        .checked_mul(origination_fee_rate)
        .ok_or_else(math_error!())?;
    origination_fee_u64 = origination_fee.checked_to_num().ok_or_else(math_error!())?;
    ...
```

For any `amount_pre_fee` such that `amount_pre_fee * origination_fee_rate < 1` native unit, `origination_fee_u64` truncates to `0`. Since a bank's `protocol_origination_fee` is a per-bank rate a group admin can legitimately set to a nonzero value (the codebase's own tests configure `1%` origination fees, e.g. in `tests/specs/basic/08_borrow.spec.ts` and `programs/marginfi/tests/user_actions/borrow.rs`), any user can borrow in a sequence of small increments (each below the "1 fee-unit" threshold for the configured rate) to accumulate a large total borrowed principal while paying zero (or near-zero) cumulative origination fee, versus the fee that would be charged for a single equivalent-size borrow.

This is the same root cause pattern as the external Riz report: a fee computed as `amount * rate` and floored to an integer can be driven to zero by controlling `amount` to be small, and repeating the operation many times to reach the desired total notional. Notably, this codebase demonstrates awareness of the correct fix elsewhere — repay-side fee expectations round up: [2](#0-1) 

```
let origination_fee: I80F48 =
    I80F48::from_num(native!(borrow_amount, debt_bank.mint.mint.decimals, f64))
        .checked_mul(origination_fee_rate)
        .unwrap()
        .ceil(); // Round up when repaying
```

and the same "round up" comment/pattern appears in `programs/marginfi/tests/admin_actions/bankruptcy.rs` (lines 470-474), confirming the intended behavior is to round the origination fee up, which the actual `lending_account_borrow` instruction does not do.

### Impact Explanation
Origination fees accrue to `collected_group_fees_outstanding` and `collected_program_fees_outstanding` on the bank [3](#0-2) , which are later paid out to the group admin and program fee wallet via `LendingPoolCollectBankFees`/`LendingPoolWithdrawFees`. By truncating the fee to zero on sufficiently small per-transaction borrow amounts, a user can accumulate a large debt position while systematically depriving the protocol/group of legitimately owed origination fee revenue — this is a fee-bypass / protocol-revenue-theft primitive, directly reachable by any unprivileged borrower with no special permissions, in the core borrow accounting path.

### Likelihood Explanation
Exploitability depends on the group admin having configured a nonzero `protocol_origination_fee`. The project's own documentation states origination fees have "always been zero" in production as of November 2025 [4](#0-3) , so the bug is currently latent/dormant rather than actively exploitable against the live fee configuration. However, the origination fee is a first-class, admin-configurable bank parameter (validated and exercised extensively in tests with nonzero values, e.g. 1%), so any bank where an admin enables this fee becomes immediately exploitable by any borrower, with low cost given Solana's low per-transaction fees (matching the report's observation that this is "more potent in networks that have a lower gas fee").

### Recommendation
Round the origination fee up (ceiling) instead of truncating in `lending_account_borrow`, consistent with the rounding convention already used in the repay/bankruptcy test expectations:
```rust
origination_fee_u64 = origination_fee.ceil().checked_to_num().ok_or_else(math_error!())?;
```
Ensure the actual on-chain accrual (not just tests) mirrors this rounding so that fee liability strictly reflects the borrowed amount and cannot be driven to zero by amount-splitting.

### Proof of Concept
1. Group admin configures a bank with a nonzero `protocol_origination_fee` (e.g., 1%, as done in existing tests).
2. An attacker calls `lending_account_borrow` repeatedly with `amount_pre_fee` values small enough that `amount_pre_fee * 0.01 < 1` native unit (e.g., borrowing 99 native units at a time for a 1% fee rate).
3. Each call computes `origination_fee = 99 * 0.01 = 0.99`, which truncates via `checked_to_num()` to `0`, so `origination_fee_u64 = 0` and no fee is added to `collected_group_fees_outstanding`/`collected_program_fees_outstanding` (see `borrow.rs` lines 117-131, 173-201).
4. Repeating this N times accumulates a total borrowed principal of `99*N` native units with zero cumulative origination fee, versus the `~1%` fee that a single equivalent borrow of `99*N` would have incurred — reproducing the fee bypass described in the external report within marginfi's borrow instruction.
