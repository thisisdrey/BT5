### Title
Heap buffer over-read in `singlejar`'s Zip64 extra-field parsing via unchecked `attr64()` index access - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` parses zip/jar Local Headers (`LH`) and Central Directory Headers (`CDH`) from attacker-influenced input archives (e.g. third-party `.jar` dependencies fetched by the build). When a 32-bit size field is `0xFFFFFFFF`, the code looks up the corresponding `Zip64ExtraField` and blindly calls `attr64(index)` to fetch the 64-bit replacement value, without verifying that the field's declared `payload_size()`/`attr_count()` actually contains that many 64-bit slots. This mirrors the ImageMagick CVE-2019-13391 class of bug: a component computes an offset/index into a buffer from header-derived values and reads through it (`GetCacheViewVirtualPixels` in the analog, `Zip64ExtraField::attr64` here) without validating that the read stays inside the actual allocated/mapped extent, because the "size" implied by the surrounding metadata does not match the true buffer bounds.

### Finding Description
`Zip64ExtraField::attr64(int index)` at [1](#0-0)  performs an unchecked array access `attr_[index]` on a C99 flexible array member; the only validation of the field is done in `ExtraField::find`, which ensures the field's own declared `size()` (header + `payload_size()`) fits between `start` and `end` [2](#0-1) . Nothing enforces that `payload_size()` is large enough to contain the specific `attr64` index that callers subsequently request.

`LH::compressed_file_size()` unconditionally calls `z64->attr64(1)` whenever `compressed_file_size32()` is `0xFFFFFFFF`, relying only on a *comment* that the ZIP spec "MUST" have both uncompressed and compressed sizes present in the Local Header's Zip64 field — a property that is not enforced by any code in this file: [3](#0-2) 

If an attacker crafts a Local Header where `compressed_file_size32_ == 0xFFFFFFFF` but the accompanying Zip64 extra field has `payload_size() == 8` (i.e., only one 8-byte attribute present, `attr_count() == 1`), `ExtraField::find` will accept the field (its own declared 12-byte size fits inside the entry's extra-fields region), but the subsequent `attr64(1)` read dereferences `attr_[1]`, which lies 8 bytes past the field's actual declared payload. That memory is outside the range that was validated to exist.

The equivalent `CDH` accessor is more careful — it computes the index from whether `uncompressed_file_size32()` itself needs ext64 [4](#0-3)  — showing the codebase is aware attacker-supplied entries can decouple which of the two size fields overflow, yet the `LH` path (used when reading `Local Header`s while iterating archive entries with `InputJar::NextEntry`/`OutputJar::AddJar`, see [5](#0-4) ) does not apply the same defensive computation.

The archive bytes reaching this code are not necessarily trusted: `singlejar` is invoked by Bazel's Java rules to merge dependency jars, and jars fetched from external registries/mirrors via `http_jar`/`http_archive`/Maven rules are exactly this kind of attacker-influenced content (a hostile origin serving a byte-for-byte crafted jar; a `sha256`/`integrity` mismatch would stop a *different* archive but not stop a byte-identical malicious jar published under a checksum the victim pins to that malicious content in the first place — the checksum verifies "this is the file I intended to trust", it does not validate the *internal structural correctness* of the zip format inside it).

### Impact Explanation
A successfully triggered out-of-bounds read in `attr_[index]` reads adjacent heap/mmap memory as if it were a 64-bit size value. Depending on layout, this can:
- Produce an incorrect (attacker-uncontrolled but non-deterministic) `compressed_file_size()`, which is subsequently used to drive `WriteBytes`/copy-length computations in `OutputJar::AddJar` (see the surrounding copy logic at [5](#0-4) ), potentially causing further out-of-bounds reads of the mapped input file or incorrect output artifact contents.
- If the `Zip64ExtraField` happens to sit at the very end of the mapped input buffer (e.g., a crafted jar where the LH's extra fields are the last bytes of the mapped region), the extra 8-byte read for `attr_[1]` can run past the end of the `mmap`'d file entirely, causing a crash (SIGSEGV) or, depending on `mmap` allocation granularity, a benign but still incorrect read of unrelated heap contents.

This does not directly grant memory disclosure to the attacker (there is no channel back to the attacker for the misread bytes), so the practical worst case is denial of service (crash of the singlejar merging step) or corruption of build outputs — not attacker-controlled arbitrary read/write.

### Likelihood Explanation
Reaching this code requires an attacker to control the bytes of a `.jar`/`.zip` file that is fed into `singlejar` as one of the merged input jars. This is realistic in a Bazel build that consumes third-party `.jar` artifacts (e.g. via Maven/`http_jar`) from an attacker-influenced mirror or registry, since the pinned digest for that jar was computed over the attacker's own (malicious) bytes, and a fixed sha256/integrity check on that specific file does nothing to stop internal structural inconsistencies engineered by whoever produced the file being pinned. However, crafting a Local Header/Zip64 field combination that lands the resulting over-read on an interesting/observable byte range (rather than harmless adjacent header bytes) requires precise control over the file's memory layout, which is possible but not trivial, and the observable effect is most often a crash rather than useful memory disclosure.

### Recommendation
- In `LH::compressed_file_size()` (and any similar accessor), do not assume the Zip64 extra field always contains both attributes. Compute the correct index the same way `CDH::compressed_file_size()` already does, and additionally validate `z64->attr_count()` is large enough for the requested index before calling `attr64()`; if not, treat the entry as malformed and fail closed (as other malformed-extra-field cases in this file already do via `diag_errx`).
- Add a bounds check inside `Zip64ExtraField::attr64()` itself (or a safe accessor) that asserts `index < attr_count()`, turning an OOB read into a deterministic parse error.

### Proof of Concept
A JUnit/C++ gtest analogous to the existing `output_jar_simple_test.cc::CreateZipWithMalformedExtraField` helper [6](#0-5)  can be extended to build a Local Header where:
1. `compressed_file_size32_` is set to `0xFFFFFFFF`.
2. The accompanying extra field has tag `0x0001` (Zip64) with `payload_size = 8` (a single 8-byte attribute, i.e., only the uncompressed size is present, no compressed size slot).
3. Place this Local Header + extra field at (or very near) the end of the mapped test buffer so that `attr_[1]` read by `attr64(1)` falls outside the allocated/mapped region.
4. Feed this buffer through `InputJar::Open(path, data, length)` and call `lh->compressed_file_size()` (or run it through `OutputJar::AddJar`), and observe the out-of-bounds read (detectable under ASan as `heap-buffer-overflow READ` or a crash), where a correctly-guarded implementation would instead reject the entry with a parse error.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
