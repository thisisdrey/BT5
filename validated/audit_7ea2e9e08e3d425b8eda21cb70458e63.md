### Title
Unvalidated attacker-controlled offset/length arithmetic in `ValidateMultiSign` precompile causes uncaught out-of-bounds exception reachable via a plain `CALL` opcode - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` and its helpers `extractBytesArray`/`extractSigArray`/`extractBytes32Array` compute array offsets and lengths directly from attacker-supplied `DataWord` values in the raw calldata, with no bound check against the actual `rawData`/`words` array size before use, unless a not-yet-default-activated feature flag (`VMConfig.allowTvmOsaka()`, TIP-854) is enabled. [1](#0-0) [2](#0-1) 

### Finding Description
`ValidateMultiSign.execute(byte[] rawData)` only guards malformed calldata shape when `VMConfig.allowTvmOsaka()` is enabled:
```
if (VMConfig.allowTvmOsaka() && !isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
  return Pair.of(false, EMPTY_BYTE_ARRAY);
}
``` [3](#0-2) 

When that flag is off (the documented "pre-activation" state, per the test explicitly named `testTip854PreActivationNoOp`), execution falls straight into `DataWord.parseArray(rawData)` and then `extractBytesArray`/`extractSigArray`, which derive `bytesOffset`, `bytesLen`, and array sizes purely from attacker-controlled words and index into `words[]`/`rawData` without checking against actual array bounds:
```
int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen);
``` [4](#0-3) 
`extractBytes` then performs `Arrays.copyOfRange(data, offset, offset + len)` with these unchecked values, which throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` when offset/len exceed `data.length` or are negative. [5](#0-4) 

Critically, these calls (`words[3].intValueSafe()`, `extractSigArray`/`extractBytesArray`) at lines 1067-1074 sit *outside* the method's only `try { ... } catch (Throwable t)` block, which wraps only the later account/permission-check logic (lines 1082-1117). This means any exception thrown while decoding the signature array is **not caught inside the precompile at all**. [6](#0-5) [7](#0-6) 

The exception then propagates to `Program.callToPrecompiledAddress`, where `contract.execute(data)` is invoked with **no surrounding try/catch** for the `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL` path that dispatches to a precompiled address:
```
Pair<Boolean, byte[]> out = contract.execute(data);
``` [8](#0-7) 

This is the direct Java analog of the UPX CVE's root cause: pointer/index arithmetic computed from untrusted, attacker-supplied length/offset fields is used to access a buffer without validating it stays within bounds, causing an out-of-bounds access instead of a controlled rejection.

Note: `BatchValidateSign` (which also calls `extractBytesArray`/`extractSigArray`/`extractBytes32Array`) is *not* similarly exposed because its `execute()` wraps the whole `doExecute()` call in `try { ... } catch (Throwable t) { return Pair.of(true, new byte[WORD_SIZE]); }`, so it does not exhibit the uncaught-exception path. [9](#0-8) 

### Impact Explanation
Any transaction broadcaster / contract deployer can craft a smart contract (or a raw contract-triggering transaction) that issues a `CALL` to the fixed `ValidateMultiSign` precompile address with malformed calldata (e.g. an out-of-range `words[3]` offset or a signature-array length that makes `bytesOffset`/`bytesLen` point outside `rawData`). This is reachable by anyone submitting a `TriggerSmartContract`, i.e. by an unprivileged actuator/TVM caller. The uncaught `RuntimeException` propagates out of the normal energy-metered execution path in `Program.callToPrecompiledAddress`, bypassing the state-refund/`stackPushZero()` handling that every other failure path in that method uses. I was not able to fully trace, within the remaining tool budget, whether the top-level `Runtime`/`VMActuator` execution loop catches this generically as a reverted transaction or whether it can escape further up the call stack; this is the main remaining uncertainty. At minimum it is a confirmed uncontrolled-crash/DoS class bug for the single transaction's execution path, deviating from the "always push 0 on precompile failure" invariant enforced everywhere else in `callToPrecompiledAddress`.

### Likelihood Explanation
High — the vulnerable code path is the *default* behavior today, since the fix (TIP-854/`allowTvmOsaka`) is explicitly modeled as "pre-activation" in the codebase's own tests (`testTip854PreActivationNoOp`, `testTip854RejectsMalformedCalldata`) and is gated behind a chain parameter that is not unconditionally on. Any account can call the `ValidateMultiSign` precompile address directly from a contract with attacker-chosen calldata, at negligible cost (a single `CALL`). [10](#0-9) 

### Recommendation
Move the `isValidAbiEncoding` check (or an unconditional bounds check) in `ValidateMultiSign.execute()` outside the `allowTvmOsaka()` gate so malformed calldata is always rejected, and wrap the offset/length decoding calls (`words[3]...`, `extractSigArray`/`extractBytesArray`) in the same defensive `try/catch` that already protects the permission-check block, mirroring `BatchValidateSign.execute()`'s outer `catch (Throwable t)`. Additionally, add a defensive `try/catch` (or bounds validation) around `contract.execute(data)` in `Program.callToPrecompiledAddress` so no precompile implementation can throw an uncaught exception out of the metered CALL path.

### Proof of Concept
1. Deploy any contract, or craft a raw `TriggerSmartContract` transaction whose `CALL`/`DELEGATECALL` target is the `ValidateMultiSign` precompile address with `allowTvmOsaka` not activated (default network state).
2. Build calldata mimicking `validatemultisign(address,uint256,bytes32,bytes[])` where the 4th head word (`words[3]`) encodes an offset that, after `/ WORD_SIZE`, plus `i + 1`, indexes past the actual `words[]` array length, or where the decoded `bytesLen`/`bytesOffset` combination exceeds `rawData.length`.
3. Because this code path executes before the guarded `try/catch` block in `ValidateMultiSign.execute()`, the resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` is thrown uncaught through `contract.execute(data)` in `Program.callToPrecompiledAddress`, which has no exception handling for this call, unlike every other failure branch in that method.
