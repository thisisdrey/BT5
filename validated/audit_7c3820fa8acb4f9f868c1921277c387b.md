## Analysis

The Cooler Factory bug is about a permissionless, unbounded on-chain array that grows with every user call and is later iterated in full by contracts/queries, allowing a spam-based DoS. The closest reachable analog in java-tron is the TRC10 legacy `Exchange` (bancor-style) subsystem.

**Root cause chain:**

1. `ExchangeCreateActuator` lets *any* account create a new exchange pair by submitting an `ExchangeCreateContract` transaction. The only gates are a fixed create fee and having enough balance/token balance — there is no cap on the total number of exchanges that can exist. [1](#0-0) 

2. Each successful call increments `dynamicStore.getLatestExchangeNum()`/`saveLatestExchangeNum(id)` and persists a new record into `ExchangeStore`/`ExchangeV2Store`, with no upper bound on the counter. [1](#0-0) 

3. `ExchangeStore.getAllExchanges()` reads the **entire** underlying LevelDB store into memory via `Streams.stream(iterator())` and sorts it, with no limit at all — unlike the paginated/limited counterparts (`getPaginatedExchangeList` capped by `EXCHANGE_COUNT_LIMIT_MAX`, or `getMarketPairList` capped by `MARKET_COUNT_LIMIT_MAX`). [2](#0-1) 

4. `Wallet.getExchangeList()` calls this unbounded method directly. [3](#0-2) 

5. This is exposed as a public, unauthenticated node API via HTTP (`ListExchangesServlet`, and its PBFT variant) and gRPC (`RpcApiService.listExchanges` / `getWalletSolidityApi().listExchanges`), reachable by any anonymous client. [4](#0-3) [5](#0-4) 

### Title
Unbounded `ExchangeStore.getAllExchanges()` iteration exposed via public `listExchanges` API enables state/CPU DoS through permissionless exchange creation - (File: chainbase/src/main/java/org/tron/core/store/ExchangeStore.java)

### Summary
`ExchangeCreateActuator` allows any funded account to permissionlessly create new TRC10 `Exchange` records with no cap on the total count. `ExchangeStore.getAllExchanges()`, used by `Wallet.getExchangeList()` and exposed through the public `listExchanges` HTTP/gRPC API (full node, solidity node, and PBFT node), loads and sorts every single exchange record in the store on every call, with no pagination or size limit, unlike the corresponding paginated/limited APIs elsewhere in the codebase (`getPaginatedExchangeList`, `getMarketPairList`).

### Finding Description
`ExchangeCreateActuator.execute()` persists a new `ExchangeCapsule` keyed by a monotonically increasing `id` (`dynamicStore.getLatestExchangeNum()+1`) with no maximum bound on the number of exchanges that can be created — the only cost is the fixed `calcFee()` and providing non-zero token balances for both sides of the pair. [6](#0-5) 

`ExchangeStore.getAllExchanges()` then does an unbounded full-store scan and in-memory sort:
```java
public List<ExchangeCapsule> getAllExchanges() {
  return Streams.stream(iterator())
      .map(Map.Entry::getValue)
      .sorted(...)
      .collect(Collectors.toList());
}
``` [2](#0-1) 

`Wallet.getExchangeList()` calls this method directly and builds a full-size protobuf response with no truncation. [3](#0-2) 

This is reachable through the public, unauthenticated `listExchanges` endpoints on HTTP (`ListExchangesServlet`, `ListExchangesOnPBFTServlet`) and gRPC (`RpcApiService`, `RpcApiServiceOnPBFT`, and the solidity wallet equivalent), meaning any anonymous API client can trigger the full-store read/sort/serialize on demand. [7](#0-6) [8](#0-7) 

This is a direct parallel to the Cooler `Factory.sol` pattern: a permissionless append-only array/store, unbounded in size, that is later fully iterated by an accessible read path — except here the iteration also involves an in-memory sort and full protobuf serialization of every record, which is more expensive per element than a simple array read. Other similar list-producing endpoints in the same codebase (`getPaginatedExchangeList`, `getMarketPairList`, `getPaginatedProposalList`) explicitly cap iteration via `EXCHANGE_COUNT_LIMIT_MAX` / `MARKET_COUNT_LIMIT_MAX` / `PROPOSAL_COUNT_LIMIT_MAX`, confirming this is a missing-bound bug rather than intended design. [9](#0-8) 

### Impact Explanation
An attacker who repeatedly submits `ExchangeCreateContract` transactions (each requiring only the fixed exchange-create fee and minimal token balances) can grow the `Exchange`/`ExchangeV2` store to a very large number of entries. Every subsequent call to the public `listExchanges` API (HTTP/gRPC, on full, solidity, and PBFT nodes) will then read, sort, and serialize the entire store, consuming CPU and memory proportional to the attacker-controlled store size on every single request. Because this endpoint is unauthenticated and can be called repeatedly and concurrently, this can degrade or crash the API-serving node process (an API the node can no longer serve), impacting availability for legitimate wallet/API clients.

### Likelihood Explanation
Likelihood is moderate: creating each exchange costs a fixed TRX fee plus locking token balances, so an attacker needs capital, but there's no upper bound preventing them from creating an arbitrarily large number of exchange pairs over time using low-value TRC10 tokens they mint themselves cheaply relative to the ongoing DoS potential. Once the store is large, the amplification (unbounded reads triggered by cheap unauthenticated API calls) is straightforward to exploit repeatedly at near-zero marginal cost to the attacker.

### Recommendation
Bound `getExchangeList()`/`ExchangeStore.getAllExchanges()` the same way `getPaginatedExchangeList` and `getMarketPairList` are bounded — either remove the unbounded `listExchanges` API entirely in favor of the paginated variant, or enforce a hard cap (e.g. `EXCHANGE_COUNT_LIMIT_MAX`) on the number of records read/sorted/returned per call.

### Proof of Concept
1. Repeatedly submit `ExchangeCreateContract` transactions from one or more funded accounts, each creating a new TRC10-TRC10 or TRC10-TRX exchange pair (paying the fixed fee via `ExchangeCreateActuator`). [6](#0-5) 
2. After accumulating a very large number of exchange entries, call the public `listExchanges` HTTP endpoint (`/wallet/listexchanges`) or gRPC `listExchanges` RPC repeatedly. [4](#0-3) 
3. Each call forces the node to execute `ExchangeStore.getAllExchanges()`, fully iterating, sorting, and serializing every stored exchange, causing high CPU/memory usage proportional to the attacker-inflated store size. [2](#0-1)

  public List<ExchangeCapsule> getAllExchanges() {
    return Streams.stream(iterator())
        .map(Map.Entry::getValue)
        .sorted(
            (ExchangeCapsule a, ExchangeCapsule b) -> a.getCreateTime() <= b.getCreateTime() ? 1

    if (limit < 0 || offset < 0) {
      return null;

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
