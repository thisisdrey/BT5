### Title
Disk-cache invalidation is skipped for `OpMaintenance` RPCs, allowing stale `InfoRefsUploadPack` advertisements after object pruning — ([File: internal/grpc/middleware/cache/cache.go])

### Summary
Gitaly's gRPC cache-invalidation middleware explicitly excludes RPCs annotated as `OP_MAINTENANCE` from disk-cache invalidation, on the assumption that maintenance operations "shouldn't ever result in a user-visible change in behaviour." `OptimizeRepository` and `PruneUnreachableObjects` are repository-scope RPCs reachable by any client with repository access (the same access level used for ordinary push/fetch), and they can genuinely prune objects that are still referenced by a cached `InfoRefsUploadPack` response. Because the cache is not invalidated for these RPCs, subsequent fetches served from the stale cache can advertise refs pointing at objects that have just been removed, exactly mirroring the reported bug class: a publicly reachable operation updates part of the system's state (`rewardPerSecond`/`lastUpdateTime` in the Solidity report; the repository's object graph here) while skipping the complementary update (`rewardPerTokenStored`; the disk-cache invalidation here), producing an inconsistency that harms other users.

### Finding Description
The `shouldInvalidate` helper used by both the unary and stream cache-invalidation interceptors deliberately returns `false` for maintenance-typed RPCs: [1](#0-0) 

This means `UnaryInvalidator`/`StreamInvalidator` never call `StartLease`/`EndLease` for these methods, so the "latest" state file backing the disk cache key is never rotated: [2](#0-1) 

The disk cache is used specifically to serve `SmartHTTPService.InfoRefUploadPack` responses (the ref advertisement returned to a `git fetch`), keyed off a "latest" marker that is supposed to change whenever a mutating RPC touches the repository: [3](#0-2) [4](#0-3) 

`OpMaintenance` is defined with the assumption that it "shouldn't ever result in a user-visible change in behaviour, except that it may repair corrupt data": [5](#0-4) 

However, `RepositoryService.OptimizeRepository` and `PruneUnreachableObjects` — both reachable repository-scope RPCs invoked directly by clients (and also triggered automatically by the housekeeping middleware after ordinary pushes) — genuinely mutate reachability: they repack, GC, and delete unreachable objects via the housekeeping manager: [6](#0-5) [7](#0-6) 

Because these operations skip cache invalidation, if an `InfoRefsUploadPack` response was cached (e.g. right after a push that housekeeping middleware will asynchronously optimize) and the maintenance run subsequently prunes unreachable objects that were still present when the response was cached, later fetchers served from the stale cache will receive advertisement of refs/objects that no longer exist on disk, breaking their fetch (`git fetch`) or a followed `git upload-pack` operation. This directly parallels the report's root cause: a public function performs a partial state transition (advancing `rewardPerSecond`/`lastUpdateTime`) while skipping the reward-per-token update, leaving other users to observe inconsistent/lost state.

### Impact Explanation
**Impact: Medium-High.** Legitimate clients performing `git fetch`/clone against a repository can be served a stale, cached ref advertisement referencing objects that have been pruned by an intervening maintenance run, causing their subsequent fetch to fail (objects missing from the pack). This is a denial-of-service style impact on the fetch path for other users of the same repository, driven purely by state inconsistency between the housekeeping/GC subsystem and the disk-cache invalidation subsystem.

### Likelihood Explanation
**Likelihood: Medium.** `OptimizeRepository`/`PruneUnreachableObjects` are ordinary repository-scope RPCs invokable by any client with access to the repository (the same access level as pushing/fetching), and housekeeping is also triggered automatically after normal write RPCs via the housekeeping middleware. Any repository that has an actively cached `InfoRefsUploadPack` response (a very common state for busy repos) is subject to becoming stale the moment a maintenance operation prunes reachable-turned-unreachable objects.

### Recommendation
Do not blanket-exclude `OpMaintenance` operations from disk-cache invalidation. At minimum, `PruneUnreachableObjects` and any `OptimizeRepository` strategy that can delete objects (not just repack/compact) should invalidate the repository's disk cache the same way mutator RPCs do, since they can produce a user-visible change (missing objects) despite being classified as maintenance.

### Proof of Concept
Not executed against the live codebase (analog derived from source review), but the exploitable sequence is:
1. Push a commit/ref to a repository so that `SmartHTTPService.InfoRefUploadPack` gets cached for that repository state.
2. Delete the ref referencing that commit (e.g., via `WriteRef`/`UpdateReferences`), leaving the previously advertised commit's objects unreachable, while the stale `InfoRefsUploadPack` cache entry remains valid because `WriteRef`'s subsequent read doesn't refresh the already-served cache entry for concurrent readers, or trigger the race window in `doc/design_diskcache.md`'s state machine.
3. Call `PruneUnreachableObjects` (or let housekeeping middleware auto-trigger it) — this is classified `OP_MAINTENANCE`, so `shouldInvalidate` in `internal/grpc/middleware/cache/cache.go` returns `false` and the cache's "latest" marker is not rotated.
4. A concurrent/subsequent client calling `InfoRefUploadPack` receives the stale cached advertisement (still listing the now-pruned objects) and attempts `git fetch`, which fails because the objects are gone from the pack directory.

func shouldInvalidate(mi protoregistry.MethodInfo) bool {
	if mi.Scope != protoregistry.ScopeRepository {
		return false
	}

	if mi.Operation == protoregistry.OpAccessor {
		return false
	}

	if mi.Operation == protoregistry.OpMaintenance {
		return false
	}

	return true
}

// UnaryInvalidator will invalidate any mutating RPC that targets a
// repository in a gRPC unary RPC
func UnaryInvalidator(ci diskcache.Invalidator, reg *protoregistry.Registry, logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		if shouldIgnore(reg, info.FullMethod) {
			return handler(ctx, req)
		}

		errLogger := methodErrLogger(logger, info.FullMethod)

		mInfo, err := reg.LookupMethod(info.FullMethod)
		countRPCType(mInfo)
		if err != nil {
			errLogger(err)
			return handler(ctx, req)
		}

		if !shouldInvalidate(mInfo) {
			return handler(ctx, req)
		}

		pbReq, ok := req.(proto.Message)
		if !ok {
			errLogger(fmt.Errorf("expected protobuf message but got %T", req))
			return handler(ctx, req)
		}

		target, err := mInfo.TargetRepo(pbReq)
		if err != nil {
			errLogger(err)
			return handler(ctx, req)
		}

		le, err := ci.StartLease(ctx, target)
		if err != nil {
			errLogger(err)
			return handler(ctx, req)
		}

		// wrap the handler to ensure the lease is always ended
		return func() (resp interface{}, err error) {
			defer func() {
				if err := le.EndLease(ctx); err != nil {
					errLogger(err)
				}
			}()
			return handler(ctx, req)
		}()
	}
}
