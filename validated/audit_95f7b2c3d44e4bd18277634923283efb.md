### Title
Operator.execute exposes the delegated `MSG_SENDER` identity to every contract invoked inside the call batch, allowing identity hijack and theft of victim funds - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` stores the caller's address in a transient slot for the entire duration of the multicall and clears it only after the last sub-call returns. Any external contract that gains execution during the batch (e.g., a malicious token, swap router, pool, or callback target included in `calls_`, or reached transitively via `SmartFarmingManager.leverage` / `NativeTokenGateway` / `VesperGateway` swapper calls) can call back into Metronome contracts and be treated as the victim by `SynthContext._msgSender`. This is the direct analog of the Tang race: for a bounded window, a privileged secret (the authenticated sender) is readable by "other processes" (arbitrary code in the call tree). [1](#0-0) 

### Finding Description
`setMsgSender` writes `msg.sender` to `MSG_SENDER_STORAGE` (TSTORE), runs the whole `calls_` loop via `Address.functionCallWithValue`, and only then writes `address(0)` [2](#0-1) . `SynthContext._msgSender` resolves the privileged identity by checking `msg.sender == operator` and reading that transient slot [3](#0-2) . All privileged flows built on `SynthContext` — `DepositToken.withdraw`/`transfer`/`transferFrom` (`_revertIfLocked` protects only via the resolved sender's own position), `Pool` mint/withdraw/swap entry points, `ProxyOFT.sendFrom`, and `VesperGateway` — therefore trust whichever address is in the slot at the moment they execute.

The `nonReentrant` guard on `execute` only blocks re-entering `Operator` itself; it does not prevent a contract invoked mid-batch from calling `Pool`, `DepositToken`, `SyntheticToken`, or `ProxyOFT` directly, where `_msgSender()` still resolves to the victim because the slot is not yet cleared.

Attack path:
1. Victim calls `Operator.execute` with a batch that (perhaps unknowingly, e.g. through a swap/leverage zap with attacker-controlled call data, an ERC-777/ERC-1363 callback token, or an attacker-owned DEX pool contract) transfers execution to `AttackerContract` while `MSG_SENDER == victim`.
2. Inside its callback, `AttackerContract` calls `DepositToken.transferFrom`/`transfer` or `Pool.withdraw`/`Pool.swap`/`ProxyOFT.sendFrom`. `msg.sender` seen by those contracts is `Operator`, so `SynthContext._msgSender()` returns the victim.
3. The attacker drains the victim's unlocked deposit-token balance / synths / initiates a bridge debit in the victim's name, all within the same transaction.

### Impact Explanation
Direct theft of user funds: any unlocked `DepositToken` collateral, synthetic token balance, or bridgeable `msToken`/`ProxyOFT` balance of the victim can be moved by the attacker while the identity window is open. The identity invariant of `SynthContext` — that `_msgSender()` equals the EOA that initiated `execute` — is broken for every frame inside the batch.

### Likelihood Explanation
Requires the victim's `execute` batch to include a call path reaching attacker-controlled code. This is realistic: `SmartFarmingManager` leverage/flashRepay and gateway swaps route through arbitrary external swappers/tokens, and operators multicalls are precisely designed to chain third-party protocols. Front-runners or malicious zap builders can craft calldata; a poisoned token or pool contract is enough. No privileged role needed — only unprivileged EOA interaction.

### Recommendation
Reset `MSG_SENDER_STORAGE` to `address(0)` around each individual sub-call (set → call → clear inside the loop) rather than once for the whole batch, or hash the approved call list into the transient context and verify it in `getActualMsgSender`. Additionally, have `SynthContext`-aware contracts reject execution when `getActualMsgSender` was not established by a direct `execute` entry (e.g., require a per-call nonce).

### Proof of Concept
Hardhat sketch:

```solidity
// AttackerToken: a contract the victim's batch touches
contract AttackerToken {
    function exploit(IPool pool, IDepositToken dt, address victim) external {
        // called mid-execute; MSG_SENDER still == victim
        dt.transferFrom(victim, address(this), dt.unlockedBalanceOf(victim));
        // or pool.swap / withdraw / ProxyOFT.sendFrom as victim
    }
}

// test
await depositToken.approve(address(operator), type(uint256).max); // or transfer path
IOperator.Call[] memory calls = new IOperator.Call[](1);
calls[0] = IOperator.Call({
    target: address(attackerToken), // reached directly or via swapper inside a legit zap
    value: 0,
    callData: abi.encodeCall(AttackerToken.exploit, (pool, depositToken, victim))
});
await operator.execute(calls); // attacker drains victim's unlocked collateral
```

The assertion `depositToken.balanceOf(attacker) == victimUnlockedBalance` holds because `_msgSender()` inside `transferFrom` resolves to `victim` via `getActualMsgSender` while the slot is still populated.

    /// @notice Get actual `msg.sender` that is executing the call
    /// @dev It reverts if read outside of a call context
    function getActualMsgSender() external view returns (address _actualMsgSender) {
        _actualMsgSender = MSG_SENDER_STORAGE.asAddress().tload();
        require(_actualMsgSender != address(0), "not-authenticated");
    }

    /// @notice Execute calls on sender's behalf
    function execute(
        Call[] calldata calls_
    ) external payable override nonReentrant setMsgSender returns (bytes[] memory _returnData) {
        uint256 _length = calls_.length;
        _returnData = new bytes[](_length);

        uint256 _sumOfValues;
        Call calldata _call;
        for (uint256 i; i < _length; ) {
            _call = calls_[i];
            uint256 _value = _call.value;
            unchecked {
                _sumOfValues += _value;
            }
            _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
            unchecked {
                ++i;
            }
        }

        require(msg.value == _sumOfValues, "value-mismatch");
    }
