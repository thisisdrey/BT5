### Title
Floating-Point Precision Loss in `ExchangeWithdrawActuator` Legacy Precision Check Allows Bypass of "Not Precise Enough" Safeguard - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator.doValidate()` contains two code paths for validating that a bancor-exchange withdrawal ratio is "precise enough" before allowing execution. The hardened path (`allowHarden()==true`) uses exact `BigDecimal` arithmetic, but the legacy path (`allowHarden()==false`, the default unless the `AllowHardenExchangeCalculation` dynamic parameter has been enabled) converts a `BigDecimal` ratio to a Java `double` via `.doubleValue()` before comparing it against the actually truncated `anotherTokenQuant` computed with exact `BigInteger`/`BigDecimal` math in the same method and in `execute()`. This is precisely the bug class described in the external report (floating-point arithmetic used where fixed-point/exact arithmetic is required for financial calculations), applied here to TRON's on-chain Bancor-style token exchange pools. [1](#0-0) 

### Finding Description
In `doValidate()`, `anotherTokenQuant` is first computed exactly using `BigDecimal.divideToIntegralValue` (floor-truncated integer division), matching the value that will be minted to the withdrawer in `execute()` via `BigInteger.divide()` (also floor truncation for positive operands): [2](#0-1) [3](#0-2) 

The "precise enough" safeguard is meant to reject withdrawals where the truncation error introduced by integer division would exceed 0.01% of `anotherTokenQuant` (i.e. protect the pool's reserve ratio invariant from being distorted by an imprecise creator withdrawal). In the *hardened* branch this comparison is done entirely in `BigDecimal`: [4](#0-3) 

But in the *non-hardened* (legacy/default) branch, the same ratio is converted to a primitive `double` before the remainder is computed and compared:

```java
double remainder = bigSecondTokenBalance.multiply(bigTokenQuant)
    .divide(bigFirstTokenBalance, 4, BigDecimal.ROUND_HALF_UP).doubleValue()
    - anotherTokenQuant;
if (remainder / anotherTokenQuant > 0.0001) {
  throw new ContractValidateException("Not precise enough");
}
``` [1](#0-0) [5](#0-4) 

`double` only guarantees exact representation of integers up to 2^53 (~9.0e15). Token/TRX pool balances and quantities in exchange contracts are `int64` (up to `Long.MAX_VALUE` ≈ 9.2e18), and `firstTokenBalance`/`secondTokenBalance` for TRX-denominated pools (measured in SUN, 1 TRX = 1e6 SUN, with total TRX supply on the order of 1e17 SUN) routinely produce intermediate ratio values above the 2^53 exact-integer boundary once scaled to 4 decimal places for the `BigDecimal.divide(..., 4, ...)` call. Converting such a value to `double` silently discards low-order bits, meaning the computed `remainder` no longer reflects the true truncation error that `execute()` will actually apply. This creates two problems:
1. The tooling that developed the `SafeExchangeProcessor`/`allowHarden` machinery in this codebase explicitly documents that legacy `double`-based formulas differ from BigInteger-exact ones (see the "Hardened replacement of legacy...formula" comment elsewhere in the codebase, confirming this class of bug is a recognized, real concern for this project) [6](#0-5) .
2. A user who is the creator of an exchange (the only party permitted to call `ExchangeWithdrawContract`, enforced at line 181-183) can select `tokenQuant` and pool balances (indirectly, through prior `ExchangeInjectContract`/`ExchangeCreateContract` calls they control since they are the creator) such that the true fixed-point remainder exceeds the 0.0001 threshold (and would be rejected in the hardened path) while the `double`-degraded remainder computed here falls under the threshold, allowing the "Not precise enough" check to be bypassed.

### Impact Explanation
Bypassing this check lets the exchange creator execute withdrawals whose reserve-ratio truncation error exceeds the protocol's own designed tolerance. Because `execute()` unconditionally applies the (larger, unvalidated) truncation, this systematically distorts the AMM pool's `firstTokenBalance`/`secondTokenBalance` ratio away from the economically fair value. Since the *same* exchange pool is later used by unrelated market participants via `ExchangeTransactionActuator` (buy/sell against the pool, using the constant-product/Bancor `SafeExchangeProcessor`/`ExchangeProcessor` formula), a ratio distorted through repeated exploitation of this floating-point bypass directly changes the price other traders receive, allowing the creator to extract value from the pool (and, transitively, from counterparties trading against it) beyond what the precision safeguard was designed to permit. This is a concrete instance of unauthorized/incorrect value extraction rooted in floating-point precision loss in a financial calculation reachable from a single signed transaction (`ExchangeWithdrawContract`), matching the report's bug class and impact category (inaccurate/exploitable price/ratio calculation leading to fund loss).

### Likelihood Explanation
The vulnerable branch is the **default/legacy** code path — it is only replaced by the exact `BigDecimal` computation when the `AllowHardenExchangeCalculation` dynamic property has been enabled on-chain via governance proposal (`allowHarden()`), which is not guaranteed to be enabled on all networks/at all times. Any account can become the "creator" of an exchange by calling `ExchangeCreateActuator`, and only that creator needs to call `ExchangeWithdrawContract` to trigger the vulnerable check — no special privilege beyond owning an exchange is required, and no cooperation from other parties or witnesses is needed. The attacker fully controls the inputs (`tokenQuant`, and indirectly the pool balances via prior inject calls), making crafting an exploitative case for the `double` conversion feasible with off-chain computation.

### Recommendation
Remove the non-hardened `double`-based comparison entirely (or force `allowHarden()` to always be `true`), and perform the precision/remainder check using only exact `BigDecimal`/`BigInteger` arithmetic, consistent with the already-implemented hardened path:
```java
BigDecimal remainder = bigSecondTokenBalance.multiply(bigTokenQuant)
    .divide(bigFirstTokenBalance, 4, RoundingMode.HALF_UP)
    .subtract(BigDecimal.valueOf(anotherTokenQuant));
if (remainder.compareTo(
    BigDecimal.valueOf(anotherTokenQuant).multiply(new BigDecimal("0.0001"))) > 0) {
  throw new ContractValidateException("Not precise enough");
}
```
Additionally, consider deprecating/removing the legacy `double` branch altogether so that no chain configuration state permits the imprecise code path to be reachable in production.

### Proof of Concept
1. Attacker calls `ExchangeCreateActuator` to create an exchange pool, becoming its `creatorAddress` (satisfying the `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check in `ExchangeWithdrawActuator.doValidate()`) [7](#0-6) .
2. Attacker uses `ExchangeInjectContract` calls to grow `firstTokenBalance`/`secondTokenBalance` to values whose product with a chosen `tokenQuant`, once divided and scaled to 4 decimal places, exceeds `2^53` — realistic for TRX-denominated pools given TRX's total supply expressed in SUN (up to ~1e17).
3. Attacker computes off-chain (using exact `BigDecimal` arithmetic mirroring the contract) a `tokenQuant` for which:
   - The true (hardened) remainder ratio would exceed `0.0001` (i.e., would be rejected by the hardened check), but
   - The `double`-degraded remainder ratio computed by `bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance, 4, ROUND_HALF_UP).doubleValue()` rounds to a value that produces `remainder / anotherTokenQuant <= 0.0001`.
4. Attacker submits `ExchangeWithdrawContract` with this crafted `tokenQuant` while the network has *not* enabled `AllowHardenExchangeCalculation` (the default legacy state). The check at lines 236-243 (or 264-271) passes despite exceeding the intended tolerance, and `execute()` applies the exact `BigInteger`-truncated `anotherTokenQuant`, distorting the pool's reserve ratio in the attacker's favor.
5. Attacker (or any subsequent trader) then interacts with `ExchangeTransactionActuator` against the now-distorted pool to realize value extracted from the mispriced ratio.

Note: I was unable to execute this PoC or run the actual `double` vs `BigDecimal` divergence numerically inside this environment (no code execution tools available); the finding is based on static analysis of the confirmed source code and the documented precision-loss concern already present elsewhere in the codebase (`ResourceProcessor.calculateGlobalLimitV2` comment) confirming this is a recognized bug class for this project. A background engineering session with test execution capability should validate the exact `tokenQuant`/balance combination needed to trigger the divergence in practice.

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
