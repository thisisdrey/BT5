### Title
Unbounded `offset`/`limit` in paginated list HTTP/gRPC APIs enables memory-exhaustion DoS - (File: `framework/src/main/java/org/tron/core/services/http/GetPaginatedAssetIssueListServlet.java`)

### Summary
Several public, unauthenticated Full Node HTTP endpoints (`/wallet/getpaginatedassetissuelist`, `/wallet/getpaginatedexchangelist`, `/wallet/getpaginatedproposallist`, `/wallet/getpaginatednowwitnesslist`) accept attacker-controlled `offset`/`limit` values as raw `long`s and pass them directly into `Wallet` list-building calls with no upper bound, unlike the analogous block-range endpoints which explicitly cap the requested range.

### Finding Description
`GetPaginatedAssetIssueListServlet`, `GetPaginatedExchangeListServlet`, `GetPaginatedProposalListServlet`, and `GetPaginatedNowWitnessListServlet` all parse `offset` and `limit` as `long` from the HTTP request (GET query parameters or POST JSON body) and forward them unchecked to `Wallet.getAssetIssueList(offset, limit)`, `Wallet.getPaginatedExchangeList(offset, limit)`, `Wallet.getPaginatedProposalList(offset, limit)`, and `Wallet.getPaginatedNowWitnessList(offset, limit)` respectively: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

This is a direct architectural inconsistency with the block-range servlets in the same package, which explicitly reject any `endNum - startNum` exceeding a hard-coded `BLOCK_LIMIT_NUM = 100` cap before invoking `wallet.getBlocksByLimitNext(...)`: [5](#0-4) [6](#0-5) 

The Jenkins advisory's bug class — a server that renders/builds a response object whose size is proportional to an unconstrained, client-supplied numeric parameter, with no upper limit enforced before the (potentially large) allocation — maps to this pattern: `offset`/`limit` (analogous to Jenkins graph width/height) flow straight into `Wallet` methods that build a `List`/protobuf message, with no equivalent of the `BLOCK_LIMIT_NUM` clamp present on the sibling block-range servlets.

**Uncertainty:** I was unable to fully inspect the bodies of `Wallet.getAssetIssueList(long, long)`, `Wallet.getPaginatedExchangeList`, `Wallet.getPaginatedProposalList`, and `Wallet.getPaginatedNowWitnessList` within the tool budget available, so I cannot rule out that these methods internally clamp `limit` against the actual store size or another constant before allocating. This is the missing piece needed to fully confirm exploitability; only the servlet-layer absence of a bound (in contrast to the block servlets) is confirmed.

### Impact Explanation
If `Wallet`'s paginated-list methods do not internally cap `limit`, a remote unauthenticated caller can request an arbitrarily large `limit` (e.g. `Long.MAX_VALUE`), forcing the node to allocate and serialize a correspondingly large in-memory list/protobuf response for every request, exhausting heap memory and causing the Full Node (and any other services hosted in the same JVM) to crash or become unresponsive — a node-crash/halt denial of service, matching the accepted impact criteria.

### Likelihood Explanation
The endpoints are unauthenticated HTTP/JSON-RPC style Wallet APIs reachable by any anonymous client with network access to the Full Node's HTTP port; no signed transaction or special privilege is required, only an HTTP GET or POST request with a large `limit` value, making exploitation trivial to attempt. The severity in practice depends on whether the unconfirmed internal clamp exists in `Wallet.java`.

### Recommendation
Enforce an explicit maximum `limit` (analogous to `BLOCK_LIMIT_NUM` in `GetBlockByLimitNextServlet`) at the servlet layer for `GetPaginatedAssetIssueListServlet`, `GetPaginatedExchangeListServlet`, `GetPaginatedProposalListServlet`, and `GetPaginatedNowWitnessListServlet` before invoking the corresponding `Wallet` methods, rejecting or truncating requests whose `limit` exceeds the configured maximum, and additionally validate that `offset`/`limit` are non-negative to avoid related edge-case exceptions.

### Proof of Concept
```
POST /wallet/getpaginatedassetissuelist HTTP/1.1
Content-Type: application/json

{"offset": 0, "limit": 9223372036854775807}
```
Repeat against `/wallet/getpaginatedexchangelist`, `/wallet/getpaginatedproposallist`, and `/wallet/getpaginatednowwitnesslist` with the same oversized `limit`; if `Wallet` does not clamp internally, each request drives disproportionate memory allocation relative to normal usage.
