### Title
Atomic, unverified owner-permission replacement in `AccountPermissionUpdateContract` can permanently lock an account out of its own funds - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` lets any account atomically overwrite its entire `Owner` permission (and `Active`/`Witness` permissions) in a single, one-shot transaction, exactly like the Y2K `Timelock.changeOwner()` pattern flagged in the external report. There is no two-step "propose/accept" confirmation, and the contract only checks address format validity, not that the submitter actually controls the private key(s) being installed as the new owner.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unpacks the `AccountPermissionUpdateContract` and immediately calls `account.updatePermissions(...)`, replacing the stored owner/witness/active `Permission` objects in one atomic step: [1](#0-0) 

The actual mutation is performed unconditionally by `AccountCapsule.updatePermissions`, which simply overwrites `ownerPermission`, `witnessPermission` and clears/re-adds `activePermission`: [2](#0-1) 

`validate()` only checks structural correctness of the new permissions (key count, threshold, weight sum, address format via `DecodeUtil.addressValid`) — it never verifies that the addresses supplied as new owner keys are addresses the caller actually controls: [3](#0-2) [4](#0-3) 

Because the owner permission is the top-level authority for the account (required for most privileged operations, further `AccountPermissionUpdateContract` calls, and this actuator's own `calcFee()`-gated update), a mistaken address (typo, wrong key, or unreachable multisig threshold) in the new owner permission is irreversible: there is no fallback path or recovery mechanism, unlike a two-step accept-based transfer.

### Impact Explanation
If an account owner submits an `AccountPermissionUpdateContract` with an incorrect owner-permission key set (e.g., typo'd address, unreachable threshold, or keys the sender does not actually hold), the account permanently loses the ability to authorize any further owner-level transaction, including a corrective `AccountPermissionUpdateContract`. This permanently freezes the account's assets and any privileged capability tied to that account (multisig-controlled TRX/TRC10 balances, staked/delegated resources, and any contracts controlled by that address), matching the "permanent freezing of funds" impact class.

### Likelihood Explanation
Any account holder with `AllowMultiSign` enabled can trigger this by broadcasting a single, ordinary signed `AccountPermissionUpdateContract` transaction — no privileged role or malicious actor is required, only user/operational error, exactly as described in the source report for `Timelock.changeOwner()`.

### Recommendation
Introduce a two-step confirmation for owner-permission changes: require the new owner permission's keys to explicitly co-sign/accept the change (analogous to `Ownable2Step.acceptOwnership()`) before it takes effect, or add a time-delayed/pending-permission staging mechanism so an erroneous update can be reverted before finalization.

### Proof of Concept
1. Account `A` has `AllowMultiSign` enabled and a valid owner permission.
2. `A` submits `AccountPermissionUpdateContract` with `owner_address = A`, and `owner` permission containing a mistyped key address (or a threshold unreachable by keys `A` actually controls).
3. `AccountPermissionUpdateActuator.validate()` passes all structural checks (address format valid, weight sum ≥ threshold using the *stated* keys), and `execute()` calls `AccountCapsule.updatePermissions(...)`, overwriting the owner permission in the same block.
4. `A` can no longer produce a valid owner-permission signature for any future transaction, including a corrective `AccountPermissionUpdateContract`, permanently freezing all funds and privileges tied to account `A`.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
