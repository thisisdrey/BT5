### Title
Unbounded exchange/asset creation combined with un-paginated `listExchanges`/`getAssetIssueList` query APIs enables state-growth Denial of Service - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The Sherlock report describes a DoS pattern where an unprivileged user can repeatedly invoke a cheap contract entry point (`increasePosition` with `amount == 1`) to grow an internal collection unboundedly, degrading a globally-serialized operation. The java-tron analog is the unbounded growth of the `Exchange`/`AssetIssue` stores via unrestricted, repeatable actuators, combined with un-paginated read APIs that fully materialize those stores on every call.

### Finding Description
`ExchangeCreateActuator.execute()` lets any account with sufficient balance create a new `Exchange` entry, incrementing `dynamicStore.getLatestExchangeNum()` with no upper bound on the total number of exchanges that can exist in the chain state. [1](#0-0) 

There is no cap enforced anywhere in `doValidate()` on the total count of exchanges — only per-transaction balance/fee checks are performed. [2](#0-1) 

`ExchangeStore.getAllExchanges()` and `Wallet.getExchangeList()` load and serialize the *entire* store on every call, without pagination, sorting the full result set in memory each time: [3](#0-2) [4](#0-3) 

This unbounded, non-paginated read is directly reachable from unauthenticated gRPC and HTTP endpoints: [5](#0-4) [6](#0-5) 

The same pattern exists for asset issuance: `Wallet.getAssetIssueList()` iterates `getAllAssetIssues()` (all rows) with no bound and updates bandwidth usage for every single entry on every call, and this is likewise exposed unauthenticated over gRPC. [7](#0-6) [8](#0-7) 

Paginated variants exist (`getPaginatedExchangeList`, `getAssetIssueList(offset, limit)`), but the un-paginated `listExchanges`/`getAssetIssueList()` endpoints remain fully exposed and are not deprecated or access-limited. [9](#0-8) 

### Impact Explanation
An attacker who repeatedly submits `ExchangeCreateContract` (or `AssetIssueContract`) transactions — each a normal, fee-paying, unprivileged transaction — permanently grows the `ExchangeStore`/`AssetIssueStore` state. Because these stores are never pruned and the un-paginated list APIs (`listExchanges`, `getAssetIssueList()`) always materialize and sort/iterate the *entire* store on each request, the CPU and memory cost of serving these specific, unauthenticated API calls grows linearly (or worse, with the `O(n log n)` sort in `getAllExchanges`) with the number of exchanges/assets ever created. Once the store is large enough, each call to these endpoints can consume excessive CPU/heap on the serving node, degrading or denying that API path for all clients — a resource-exhaustion DoS of node query services reachable purely through normal, unprivileged transactions and public API calls, echoing the underlying bug class in the report (cheap, repeatable, unprivileged operations bloating unbounded state that another code path must fully process).

### Likelihood Explanation
Likelihood is moderate: creating an exchange or asset issuance requires paying a configurable creation fee (not literally "dust" as in the original report), so the attack has an ongoing TRX cost, unlike the 1e6 USDC dust example. This raises the bar compared to the original report but does not eliminate the risk, since the fee is fixed and modest relative to potential state-bloat and API-degradation impact, and the store growth is permanent and cumulative across the chain's lifetime (all historical exchanges/assets remain forever). No rate limiting on the number of exchanges/assets an account (or many accounts) may create was found in the validated code paths.

### Recommendation
- Deprecate or restrict the un-paginated `listExchanges` / `getAssetIssueList()` (no-offset) endpoints, forcing clients to use the paginated variants (`getPaginatedExchangeList`, `getAssetIssueList(offset, limit)`), which already exist and cap `limit` via `EXCHANGE_COUNT_LIMIT_MAX` / `ASSET_ISSUE_COUNT_LIMIT_MAX`.
- Alternatively, add the same limit enforcement to `getAllExchanges()`/`getAllAssetIssues()` call sites used by the un-paginated APIs, or return an error/require pagination once the store exceeds a threshold size.
- Consider adding rate limiting or per-account/global caps on exchange/asset creation.

### Proof of Concept
1. Attacker repeatedly broadcasts `ExchangeCreateContract` transactions (each pays `getExchangeCreateFee()`), incrementing `dynamicStore.getLatestExchangeNum()` indefinitely — this succeeds as validated purely by balance checks in `ExchangeCreateActuator.doValidate()` [10](#0-9) .
2. Once the `ExchangeStore` contains a very large number of entries, any client calls the unauthenticated `listExchanges` gRPC method or the `/wallet/listexchanges` HTTP endpoint.
3. `Wallet.getExchangeList()` invokes `ExchangeStore.getAllExchanges()`, which streams, maps, and sorts every stored `ExchangeCapsule` on every single request [11](#0-10) , causing high CPU/memory usage proportional to the attacker-inflated store size, degrading the API's responsiveness for all callers.

Note: I was unable to fully verify the exact configured default value of `getExchangeCreateFee()`/asset issuance fee within the time available (it is read from `DynamicPropertiesStore` but the constant/default was not located in the indexed files), so the precise economic cost-per-entry of this attack could not be confirmed with certainty.

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;

    ExchangeList.Builder builder = ExchangeList.newBuilder();
    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ExchangeCapsule::calculateDbKey).map(key -> {
      try {
        return getExchangeStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getExchangeStore(),
            chainBaseManager.getExchangeV2Store()).get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(exchangeCapsule -> builder
            .addExchanges(exchangeCapsule.getInstance()));
    return builder.build();

  }
