### Title
Remote-address (roaming) state can be poisoned by an unauthenticated on-path attacker via UDP source-address spoofing - (File: outside.go, hostmap.go)

### Summary
The external report describes a share-price/accounting manipulation where an attacker can influence a protocol's internal state (`totalAssets()`) through a channel that bypasses the intended, validated update path (a direct token transfer instead of the official `depositLRT()` bookkeeping), corrupting a calculation that other users rely on. The closest reachable analog in Nebula is `Interface.handleHostRoaming` / `HostInfo.SetRemoteIfPreferred`, which updates a peer's trusted "current remote address" using the **UDP source address of the received packet** — a value that is never authenticated by the Noise/cert layer and is fully attacker-controllable by any on-path party capable of spoofing UDP packets, without needing a valid Nebula certificate at all.

### Finding Description
When a data-plane packet arrives, `readOutsidePackets` looks up the `HostInfo` by index and decrypts the packet's AEAD payload, then immediately calls `f.handleHostRoaming(hostinfo, via)`: [1](#0-0) 

`handleHostRoaming` compares `via.UdpAddr` (the packet's *outer* UDP source address, taken straight from the socket read, never bound cryptographically to the Noise session) against the host's currently trusted remote, and if it differs and isn't suppressed, calls `hostinfo.SetRemote(via.UdpAddr)`: [2](#0-1) 
The relevant "roaming" logic lives here — it trusts `via.UdpAddr` derived purely from the received packet's L3/L4 header, and updates `hostinfo.remote` for all future traffic: [3](#0-2) 

Only two soft gates exist before the trust update occurs — `remote_allow_list` and a short roam-suppression window — neither of which authenticates the *source address itself*; both operate on values controlled by the packet's IP/UDP header, not by anything the certificate or Noise handshake attests to. The AEAD decrypt step only proves that *some* valid ciphertext for that host's session arrived; it says nothing about who actually sent the UDP datagram or from where, because UDP source addresses are unauthenticated and spoofable. This is architecturally analogous to the `Aggregator.totalAssets()` bug: a value that should only be updated through a validated/authenticated path (the completed Noise handshake and certificate-verified peer identity) is instead derived from an untrusted external input (`via.UdpAddr`) and used to update shared state (`hostinfo.remote`, the "trusted return address" for all future sends) that affects the correctness/security of subsequent traffic for a legitimate peer.

### Impact Explanation
An attacker positioned on the network path (able to observe an in-flight encrypted Nebula packet and race/replay it with a spoofed UDP source address before or in place of the genuine packet) can cause the receiving node to silently switch `hostinfo.remote` to an address the attacker controls. Because `SetRemote`/`handleHostRoaming` require no certificate, no handshake, and no additional cryptographic proof of the new source address, this can redirect where the victim sends all subsequent outbound encrypted traffic for that tunnel — enabling traffic redirection/MITM positioning or a denial-of-service (blackholing outbound traffic to an attacker-chosen or nonexistent address), all without the attacker ever possessing a CA-signed certificate.

### Likelihood Explanation
Exploitation requires an attacker with on-path/spoofing capability (e.g., able to inject UDP packets with a forged source address into the path between the two legitimate peers, and race the legitimate packet) — this is a meaningfully harder position than a fully remote, unauthenticated internet attacker, but it needs no valid certificate, no CA trust, and no participation in the Noise handshake, which matches the "no CA-signed certificate" reachability bar in the rules. Likelihood is Medium: it requires network positioning (MITM/on-path or forged-source capability, common in untrusted Wi-Fi/cloud-hop scenarios that Nebula is explicitly designed to operate over) but not cryptographic compromise.

### Recommendation
Do not update `hostinfo.remote` purely from the unauthenticated outer UDP source address of a decrypted packet. Consider binding roaming acceptance to a freshly authenticated in-band assertion (e.g., require a signed/keyed confirmation of the new source, such as a re-verified `Test`/heartbeat round-trip using the session cipher before committing to the new remote), or rate/quorum-gate roam switches so a single spoofed/raced packet cannot flip the trusted remote.

### Proof of Concept
Conceptual (not executable without network-level spoofing tooling):
1. Attacker sits on-path between Host A and Host B and observes an in-flight, validly encrypted Nebula UDP packet from A to B.
2. Attacker crafts a UDP packet with identical payload/ciphertext but a forged source `IP:port` (`AttackerAddr`), and races it to arrive at B before/instead of the genuine packet.
3. B's `Decrypt` succeeds (ciphertext/nonce are valid and unused), so `handleHostRoaming` runs and, since `AttackerAddr` differs from B's current remote for A and isn't suppressed, calls `SetRemote(AttackerAddr)`.
4. B now sends all subsequent traffic destined for A to `AttackerAddr` instead of A's real address — traffic redirection/DoS achieved without the attacker ever holding a CA-signed certificate.

**Note:** This scenario is plausible from the code paths inspected (`outside.go` lines 126-136, `hostmap.go` lines 777-823), but I was not able to fully verify from the indexed code whether `remote_allow_list`/roam-suppression or replay-window timing in practice make this materially harder to exploit than described; a full assessment (including reviewing `AllowAll` semantics and typical `RoamingSuppressSeconds` defaults) would benefit from a live Devin session with complete repository access.

func (i *HostInfo) SetRemote(remote netip.AddrPort) {
	// We copy here because we likely got this remote from a source that reuses the object
	if i.GetRemote() != remote {
		i.remote.Store(&remote)
		i.remotes.LearnRemote(i.vpnAddrs[0], remote)
	}
}

// SetRemoteIfPreferred returns true if the remote was changed. The lastRoam
// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}
