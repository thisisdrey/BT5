### Title
Forged asset-conversion pool reserves via direct balance transfer bypass `Pools` registry, enabling underpriced/fake fee quotes - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet_asset_conversion::Pallet::get_reserves()` infers pool "liquidity" purely from the raw asset balances held at a *deterministically-derived* pool account, without ever checking the `Pools` storage map that records whether the pool was officially created. This is the same broken invariant as the Dodo `_existsPairPool()` bug: existence/liquidity is inferred from incidental `balanceOf()`-style state rather than an authoritative registry, so an attacker can fabricate a "pool" for any asset pair simply by transferring tokens to the computed address.

### Finding Description
`Pools` is explicitly documented as the source of truth for pool existence: [1](#0-0) 

which states pools are "officially created rather than people sending tokens directly to a pool's public account." Dispatchable calls such as swaps correctly enforce this by checking the map, e.g. in the ops migration path: [2](#0-1) 

However, the pallet's `get_reserves()` view function — used by both the public precompile and the fee-quoting logic — never consults `Pools`. It only derives the pool address and reads raw balances: [3](#0-2) 

`quote_price_exact_tokens_for_tokens` and `quote_price_tokens_for_exact_tokens` build directly on this unverified result to compute swap quotes: [4](#0-3) [5](#0-4) 

Because `T::PoolLocator::pool_address(&asset1, &asset2)` is a pure deterministic function of the two asset identifiers, any unprivileged account can compute this address off-chain and transfer arbitrary amounts of `asset1`/`asset2` into it *without ever calling `create_pool`*. The `Pools` map entry — the only authoritative existence check — is never inserted, yet `get_reserves()`/`quote_price_*` will treat the pair as a fully liquid pool and return a price ratio entirely controlled by the attacker's chosen deposit amounts.

This exactly mirrors the external report's root cause: "This logic never verifies that `pool` has deployed contract code... it thus treats any stray token balances at that address as liquidity." Here, the corrupted value is the `(balance1, balance2)` tuple returned by `get_reserves()` / consumed by `quote_price_*`, which is accepted as real reserve data despite `Pools::<T>::contains_key(pool_id)` being `false`.

### Impact Explanation
`quote_price_tokens_for_exact_tokens` / `quote_price_exact_tokens_for_tokens` are the exact primitives used by `pallet-asset-conversion-tx-payment`'s `ChargeAssetTxPayment` extension to convert transaction fees into an alternate asset (confirmed by the fee-quoting test file directly calling `AssetConversion::quote_price_tokens_for_exact_tokens` for fee conversion): [6](#0-5) 

Because the reserve ratio for a non-existent, self-forged "pool" is entirely attacker-controlled (they choose how much of each asset to deposit at the computed address), an attacker can set an extreme ratio (e.g., 1 unit of a worthless asset priced against a large amount of the fee asset) and then submit transactions paying fees in that worthless asset. `ChargeAssetTxPayment` will accept the quote and withdraw only a negligible amount, letting the attacker consume block space/weight for near-zero real cost — a public underpriced-work condition that degrades fee-market integrity and can be used to spam block production cheaply. It also independently causes the same DoS class described in the source report: any caller of `get_reserves`/the asset-conversion precompile can be given false "pool exists with liquidity X" data for a pair that has no real, registered pool, while actual swap extrinsics (`swap_exact_tokens_for_tokens`, `add_liquidity`, etc.) still correctly gate on `Pools`, so subsequent real operations relying on the false quote will revert.

### Likelihood Explanation
No privileged role, relayer, validator, or governance action is required. Any unprivileged account can: (1) deterministically compute the pool address for any asset pair via the public `PoolLocator`, (2) transfer small amounts of both assets to that address (ordinary `transfer`/`mint`), and (3) immediately have `get_reserves`/`quote_price_*` treat the pair as a liquid, "existing" pool. This is a pure public-entrypoint, unprivileged-attacker path with no front-running or malicious-infrastructure precondition, matching the accept criteria (public underpriced work / false state acceptance).

### Recommendation
`get_reserves()` (and by extension `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens`) must first verify `Pools::<T>::get(&pool_id)` (or equivalent registration check) and return `Error::<T>::PoolNotFound` if the pool was never officially created, before reading any balances from the derived pool account — mirroring the guard already used by the dispatchable swap/liquidity calls.

### Proof of Concept
1. Attacker picks `asset_junk` (an asset they fully control/mint) and the native fee asset.
2. Attacker computes `pool_account = PoolLocator::pool_address(&Native, &asset_junk)` off-chain (pure function, no on-chain state needed) — note `create_pool` is never called, so `Pools::<T>::get(pool_id) == None`.
3. Attacker transfers `1` unit of `asset_junk` and a very large amount of native currency they temporarily control into `pool_account` (ordinary `balances::transfer` / `assets::transfer`, no privilege required).
4. Attacker calls (or the runtime's tx-payment extension calls) `AssetConversion::quote_price_tokens_for_exact_tokens(asset_junk, Native, fee_amount, true)`. Since `get_reserves()` never checks `Pools`, it returns `Ok((1, large_amount))`, yielding an extremely favorable quote (e.g., paying a fraction of `asset_junk` for the full native fee).
5. Attacker submits a transaction using `ChargeAssetTxPayment` with `asset_junk` as the fee asset; the extension withdraws only the manipulated tiny amount, letting the attacker pay negligible real value for block space/weight consumption — while the pool the quote is based on was never actually created via `create_pool` and holds no genuine liquidity.

			asset1: T::AssetKind,
			asset2: T::AssetKind,
		) -> Result<(T::Balance, T::Balance), Error<T>> {
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			let balance1 = Self::get_balance(&pool_account, asset1);
			let balance2 = Self::get_balance(&pool_account, asset2);

			if balance1.is_zero() || balance2.is_zero() {
				Err(Error::<T>::PoolEmpty)?;
			}

			Ok((balance1, balance2))
		}

		///
		/// If `include_fee` is true, the quote will include the liquidity provider fee.
		/// If the pool does not exist or has no liquidity, `None` is returned.
		/// Note that the price may have changed by the time the transaction is executed.
		/// (Use `amount_out_min` to control slippage.)
		/// Returns `Some(quoted_amount)` on success.
		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
		}
