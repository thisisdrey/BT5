Audit Report

## Title
Stranded funds in closed child-bounty accounts have no reclaim path - (File: substrate/frame/child-bounties/src/lib.rs)

## Summary
`pallet-child-bounties` derives a per-child-bounty sub-account (`child_bounty_account_id`) that holds funds transferred out of the parent bounty for the child bounty's lifetime, but unlike the sibling `pallet-bounties`, it has no permissionless sweep extrinsic keyed on the absence of the `ChildBounties` storage entry. Once a child bounty is closed or fully claimed and its `ChildBounties` entry is removed, any balance later sent (accidentally or otherwise) to that now-orphaned sub-account is permanently unreachable by any dispatchable in the pallet.

## Finding Description
`pallet-bounties` previously had this exact defect: a bounty's derived account could receive stray transfers that became stranded once the bounty closed and its storage entry was removed, since no call referenced the account afterward. This was fixed in PR 11045 by adding `reclaim_bounty_funds`, gated on `!Bounties::<T, I>::contains_key(bounty_id)`, which permissionlessly transfers any remaining balance from `Self::bounty_account_id(bounty_id)` to the treasury. `pallet-child-bounties` has the architecturally identical pattern — a `child_bounty_account_id` sub-account funded during the child bounty's active lifecycle via `add_child_bounty`, drained during `award_child_bounty`/`claim_child_bounty`/`close_child_bounty`, and then dropped from `ChildBounties` storage — but no analogous `reclaim_child_bounty_funds`-style call exists. A grep of `substrate/frame/child-bounties/src/lib.rs` for `reclaim`/sweep-style functionality confirms no such dispatchable is present; the pallet's documented dispatchable list only covers `add_child_bounty`, `propose_curator`, `accept_curator`, `award_child_bounty`, `claim_child_bounty`, `unassign_curator`, and `close_child_bounty`, none of which reference a closed child bounty's account after its storage key is removed.

## Impact Explanation
Any balance sent to a closed child bounty's derived account — whether through an accidental transfer, asset dust, or delayed settlement — becomes permanently locked with no recovery path for treasury, governance, curator, or beneficiary. This matches the "permanent user-fund lock" impact class.

## Likelihood Explanation
No privileged action is required. Any unprivileged account can transfer tokens to the deterministically-derived (`AccountIdConversion`) child-bounty account after closure, exactly as demonstrated for the parent pallet's now-fixed `reclaim_bounty_funds_works_after_accidental_refund` test scenario. The precondition — a closed child bounty followed by an ordinary transfer — is trivially reachable through the pallet's normal lifecycle.

## Recommendation
Add a permissionless `reclaim_child_bounty_funds` extrinsic to `pallet-child-bounties`, gated on the child bounty no longer existing in `ChildBounties` storage, that transfers any residual balance from `child_bounty_account_id(parent_bounty_id, child_bounty_id)` to the parent bounty account or treasury, mirroring `pallet-bounties::reclaim_bounty_funds`.

## Proof of Concept
1. Create a parent bounty and add a child bounty; fund it normally.
2. Complete the child bounty lifecycle via `claim_child_bounty` or `close_child_bounty`, which removes the `ChildBounties` entry.
3. Transfer native currency directly to the child bounty's derived account (`child_bounty_account_id`).
4. Observe no extant call in `pallet-child-bounties` can move this balance — it is permanently stranded, reproducing the pattern that `reclaim_bounty_funds_works_after_accidental_refund` demonstrates was fixed for the parent pallet, but left unaddressed for child bounties.

```rust
		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
```
