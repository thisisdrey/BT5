### Title
Unbounded stderr capture in `sshReceivePack` allows attacker-driven memory growth via hook/ref-rejection output - (File: internal/gitaly/service/ssh/receive_pack.go)

### Summary
`sshReceivePack` captures the entire stderr stream of `git-receive-pack(1)` into an unbounded `strings.Builder` via `io.MultiWriter(&stderrBuilder, stderr)` for the whole duration of the RPC. An attacker who pushes a pack producing large volumes of pre-receive/update hook rejection messages or per-ref error output can force this buffer to grow proportionally to that output, since there is no size cap on `stderrBuilder`.

### Finding Description
In `sshReceivePack` [1](#0-0) , stderr from the spawned `git-receive-pack` process is written to both the gRPC stream (`stderr`) and locally accumulated in `stderrBuilder strings.Builder`, with no size limit applied. The only consumer of `stderrBuilder` afterward is a single exact-string comparison against `"fatal: the remote end hung up unexpectedly\n"` [2](#0-1) , meaning the full accumulation serves no functional purpose beyond that narrow check, yet consumes memory linear to total attacker-influenced stderr output. Notably, the codebase already contains a bounded stderr capture utility, `stderrBuffer`, in `internal/command/stderrbuffer.go` [3](#0-2) , which enforces both `bufLimit` and `lineLimit`, but this bounded mechanism is used elsewhere in `internal/command/command.go` for other purposes and is not used by `sshReceivePack`'s local `stderrBuilder`. An attacker who pushes a large number of ref updates that fail hook/update validation (e.g., malformed ref names, protected-branch rejections) can cause `git-receive-pack` to emit one rejection line per ref, and with enough ref updates in a single push, the resulting stderr text accumulated in `stderrBuilder` scales with attacker-controlled input size, unbounded by any Gitaly-side limit.

### Impact Explanation
This is a memory-based denial-of-service concern local to the Gitaly process handling the RPC: an attacker-controlled push with a very large number of doomed ref updates increases per-request memory retained in `stderrBuilder` for the duration of the RPC, on top of the data already streamed to the client. This matches a resource-exhaustion/DoS impact class scoped to a single RPC handler, rather than a broader compromise (no cross-repo access, no command injection, no auth bypass).

### Likelihood Explanation
An unprivileged user with push access to their own repository can trigger this by crafting a push containing thousands of ref updates designed to fail (e.g., invalid ref names or protected ref violations), a repeatable action requiring no special privilege beyond ordinary push rights. The overall severity is bounded by how much stderr git-receive-pack and its hooks can realistically emit per push and by request/stream size limits enforced elsewhere in the RPC pipeline (e.g., pack size limits), which likely constrain the practical amplification factor; this reduces (but does not eliminate) the practical impact.

### Recommendation
Replace the unbounded `strings.Builder` in `sshReceivePack` with a bounded writer (e.g., reuse or wrap the existing `stderrBuffer` from `internal/command/stderrbuffer.go`, or a `io.LimitWriter`-equivalent) capped at a small size (e.g., a few KB) sufficient to detect known sentinel messages like the "remote end hung up unexpectedly" string, while still streaming the full stderr to the client unbounded via the existing `stderr` writer.

// stderrBuffer implements io.Writer and buffers outputs with limited buffer
// size and line length.
// Bytes will be truncated if `bufLimit` and `lineLimit` exceeded. It will
// always return the full len of input and nil on writes.
type stderrBuffer struct {
	buf       []byte
	bufLimit  int
	lineLimit int
	lineSep   []byte

	currentLineLength int
}

func newStderrBuffer(bufLimit, lineLimit int, lineSep []byte) (*stderrBuffer, error) {
	if bufLimit < 0 || lineLimit < 0 {
		return nil, fmt.Errorf("invalid limit")
	}
	res := &stderrBuffer{
		bufLimit:  bufLimit,
		lineLimit: lineLimit,
		lineSep:   lineSep,
	}
	if len(res.lineSep) == 0 {
		// use default '\n' for linesep if not specified
		res.lineSep = []byte{'\n'}
	}
	res.buf = make([]byte, 0, res.lineLimit)
	return res, nil
}
