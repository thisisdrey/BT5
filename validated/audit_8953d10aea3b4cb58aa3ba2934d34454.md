### Title
Precompiled-contract endowment transfer is applied outside the atomic call/rollback path in `callToPrecompiledAddress` - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress()` moves TRX/TRC10 value ("endowment") between the caller and the precompiled contract's context address *before* the precompiled contract logic actually runs, and the code explicitly flags this transfer with the comment "Charge for endowment - is not reversible by rollback". This mirrors the reported MultiInvoker pattern where collateral is moved before the operation that can fail is executed.

### Finding Description
In `callToPrecompiledAddress`, the endowment (TRX or TRC10 token value attached to a `CALL`/`STATICCALL`/`DELEGATECALL` targeting a precompiled address) is transferred via `MUtil.transfer(...)` / `deposit.addTokenBalance(...)` at lines 1712-1732, prior to `contract.execute(data)` being invoked at line 1752: [1](#0-0) 

Only on success (`out.getLeft()==true`) is `deposit.commit()` called to persist the child repository's state to its parent (line 1758). On failure, the method just pushes zero and, if an exception was recorded, re-throws it (lines 1759-1766): [2](#0-1) 

Because `deposit` is a child `RepositoryImpl` created via `newRepositoryChild()` and mutations are buffered in per-repository caches (`accountCache`, `dynamicPropertiesCache`, etc.) that are only flushed to the parent by `commit()`, the design intent is that an uncommitted child's changes should be discarded on failure. This is corroborated by `RepositoryImpl.commit()`/`commitAccountCache()` mechanics: dirty entries are only pushed to the parent repository inside `commit()`. [3](#0-2) [4](#0-3) 

The explicit source comment "Charge for endowment - is not reversible by rollback" at line 1712, however, signals that the developers themselves flagged this transfer path as *not* guaranteed to be rolled back by the normal child-repository discard mechanism, which is the exact bug class described in the external report: value movement performed outside/ahead of the atomic operation whose success determines whether the movement should have happened at all.

I was not able to fully confirm within the available tool budget whether `AccountCapsule` objects returned by a child repository's `getAccount()` are deep-copied or are the same mutable object reference as the parent/root cached instance (i.e., whether `addBalance`/`addTokenBalance` on the child's `AccountCapsule` could mutate an object that is still referenced by the parent cache, causing the balance change to leak into parent state even though `commit()` is never called). This is precisely the sharp edge that the "not reversible by rollback" comment appears to warn about, and it could not be verified from the `RepositoryImpl` accessor code retrieved in this session (`getAccount`/cache-lookup implementation was not located in time). This uncertainty should be resolved by direct inspection of `RepositoryImpl.getAccount()`/`getAccountCapsule()` and any interaction with the `accountCache` `Value<Account>` wrapper (whether `Value.create`/cache lookups perform copy-on-read).

### Impact Explanation
If the endowment transfer performed on lines 1712-1732 is not fully reversible when the precompiled contract call subsequently fails (`out.getLeft() == false`) or throws an exception that propagates out of `callToPrecompiledAddress`, an attacker could craft a `CALL`/`DELEGATECALL` to a precompiled address with a nonzero `value`/`tokenValue` designed to make the precompiled contract logic fail deterministically after the transfer state has already been mutated on the child repository whose eventual discard does not fully undo the balance/token mutation (e.g., due to object aliasing rather than value copying). This would allow unauthorized movement or loss of TRX/TRC10 balances — a direct "unbacked balance" / "theft or permanent freezing of funds" outcome reachable purely from a signed `TriggerSmartContract` transaction executed by any external account, with no special privileges required.

### Likelihood Explanation
Reaching this code path only requires deploying/calling a contract that issues a `CALL`/`STATICCALL`/`DELEGATECALL` with a nonzero endowment against one of the registered precompiled contract addresses (`PrecompiledContracts.getContractForAddress`) — trivially reachable by any transaction broadcaster. The severity therefore hinges entirely on whether the "not reversible by rollback" comment reflects a real, exploitable aliasing/commit gap in `RepositoryImpl`'s account-cache semantics, which I could not conclusively verify or refute with the tools available in this session.

### Recommendation
1. Verify whether `RepositoryImpl.getAccount()`/related accessors return copies (not shared mutable references) for accounts inherited from the parent repository, so that uncommitted child mutations can never leak into the parent/root state.
2. If aliasing is confirmed, ensure the endowment transfer in `callToPrecompiledAddress` is deep-copied onto the child's own cache entry before mutation, or restructure the method so the transfer happens after a successful `contract.execute(data)` (mirroring the pattern already used at commit time), rather than before, consistent with how `callToAddress` handles ordinary contract calls.
3. Add regression tests analogous to `RuntimeTransferComplexTest` but specifically targeting failing precompiled-contract calls with nonzero TRX/TRC10 endowment, asserting balances are unchanged after failure — closing the gap flagged by the "not reversible by rollback" comment.

### Proof of Concept
Conceptual PoC (pending confirmation of the aliasing issue):
1. Deploy a contract that issues `staticcall`/`call` with `value > 0` (or `callTokenValue > 0`) to a known precompiled contract address, with call data engineered so `contract.getEnergyForData(data)` and/or `contract.execute(data)` fails deterministically (`out.getLeft() == false`), e.g., malformed input to a precompile that validates strictly and returns failure without throwing.
2. Observe whether the caller's/target's TRX or TRC10 balance is nevertheless mutated because `deposit`'s `addBalance`/`addTokenBalance` mutated an `AccountCapsule` object shared with the parent repository, despite `deposit.commit()` never being invoked.
3. If balances change, the endowment is effectively stolen or duplicated depending on transaction direction, confirming exploitability. This step could not be executed/confirmed in this analysis due to lack of access to `RepositoryImpl.getAccount()` internals within the session's tool budget.
