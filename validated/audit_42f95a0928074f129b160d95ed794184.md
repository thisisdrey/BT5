Based on the investigation, I found an analog: the same class of bug — a state-transition guard (pause/restriction) that is enforced in only one code path but not the other, allowing bypass — exists around `ExchangeTransactionContract` handling in java-tron.

### Title
Exchange Transaction rejection is enforced only in the mempool gate, not in the actuator or block-application path - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
Similar to IronBank's `liquidate()`, which only checks `isMarketSeizable` on the collateral market and forgets to check the borrow market's pause state, java-tron's rejection of `ExchangeTransactionContract` is implemented as a one-sided guard: it exists only in `Manager.pushTransaction()`, the entry point used when a transaction is first submitted to the node's pending pool, but is absent from `ExchangeTransactionActuator`'s own `validate()`/`execute()` logic, which is the code that actually runs during block application.

### Finding Description
`Manager.pushTransaction()` contains an explicit guard: [1](#0-0) 
This check throws if the incoming transaction is an `ExchangeTransactionContract`, effectively disabling the legacy TRC10 "Exchange" trading feature at the point a transaction is first pushed into the node's pending-transaction pipeline (i.e., the path reached from `TronJsonRpcImpl`/`Wallet`'s broadcast RPC).

However, this restriction is not mirrored inside `ExchangeTransactionActuator`, which is the actual actuator invoked when a transaction contained in a block is applied to state: [2](#0-1) 
Unlike the newer `MarketSellAssetActuator` and `MarketCancelOrderActuator`, which each independently re-check `dynamicStore.supportAllowMarketTransaction()` inside their own `validate()` methods: [3](#0-2) [4](#0-3) 
`ExchangeTransactionActuator.doValidate()` contains no analogous check referencing the "rejected"/disabled state at all — the restriction lives solely in `Manager.pushTransaction`, outside the actuator layer that is exercised for every transaction included in a block, regardless of how that block was produced or received (e.g., via sync from a peer, or reconstructed by another path that does not funnel through `pushTransaction`).

This mirrors the IronBank root cause exactly: a critical restriction (pause/rejection) is checked in one entry point (`liquidate()`'s collateral-market-only pause check / java-tron's mempool-only reject check) but is not enforced at the authoritative execution layer (the borrow market's pause / the actuator's own validate-execute), so any path that reaches execution without going through the guarded entry point bypasses the restriction entirely.

### Impact Explanation
If `ExchangeTransactionContract` was intended to be permanently disabled (the hardcoded rejection message strongly implies this legacy AMM-style feature is deprecated/dangerous, likely superseded by the Market actuators which do carry a committee-controlled `supportAllowMarketTransaction` flag), any transaction of this type that reaches `ExchangeTransactionActuator.execute()` without passing through `Manager.pushTransaction()` will still mutate `ExchangeCapsule` balances and account asset/TRX balances using the old, unguarded math path. This could let an attacker manipulate legacy Exchange-pair balances or account balances outside the flag-controlled system that all other market operations were migrated to.

### Likelihood Explanation
The likelihood depends on whether any block-processing path (e.g., applying a block received from the network, or a path used during chain sync/re-application) invokes `ExchangeTransactionActuator` without first passing the transaction through `Manager.pushTransaction()`'s gate. My analysis could not fully confirm this due to indexing/iteration limits — I was unable to trace the complete definition of `Manager.processTransaction`/block-application flow to conclusively verify whether it re-invokes the `isExchangeTransaction` rejection check for transactions already embedded in a block. This is a structural inconsistency worth verifying with full source access.

### Recommendation
Move the `ExchangeTransactionContract` rejection check (or an equivalent flag such as `supportAllowMarketTransaction` used by the newer Market actuators) into `ExchangeTransactionActuator.validate()` itself, so the restriction is enforced uniformly regardless of which path (mempool submission vs. direct block application) triggers execution — consistent with how `MarketSellAssetActuator` and `MarketCancelOrderActuator` already do it.

### Proof of Concept
Not independently reproducible from the indexed context alone; would require confirming in the full source whether `Manager`'s block-application path (used for blocks received via sync or already-produced blocks) calls the actuator directly without re-running the `isExchangeTransaction` check performed in `pushTransaction`. I recommend starting a full Devin session with complete file access to trace `Manager.processBlock` → transaction execution flow and confirm whether this bypass is concretely reachable.
