### Title
Per-IP and global QUIC connection rate limiters never throttle attackers who intentionally fail the handshake, allowing unbounded-rate CPU-bound TLS handshake DoS - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC accept path in `run_server`/`setup_connection` gates admission using non-consuming reads (`overall_connection_rate_limiter.current_tokens() == 0` and `rate_limiter.is_allowed(ip)`), but the actual token spend (`rate_limiter.register_connection` and `overall_connection_rate_limiter.consume_tokens`) only happens on the success branch after the crypto handshake completes. An attacker who sends Initial/ClientHello packets crafted to be accepted by `incoming.accept()` but to fail or time out during the expensive TLS handshake never causes any tokens to be consumed, so neither limiter ever throttles them, and the only remaining bound is the concurrency cap `ClientConnectionTracker`/`qos.max_concurrent_connections()` combined with the 2-second `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.

### Finding Description
In `run_server` [1](#0-0) , every accepted `Incoming` is admitted to spawn a handshake task if two cheap read-only checks pass:
- `overall_connection_rate_limiter.current_tokens() == 0` (global bucket, read-only) [2](#0-1) 
- `rate_limiter.is_allowed(&ip)` (per-IP bucket, read-only) [3](#0-2) 

`ConnectionRateLimiter::is_allowed` explicitly returns `true` for any IP it has not previously "registered" [4](#0-3) , so first-time (or spoofed) source IPs always pass. After passing these gates, `ClientConnectionTracker::new` only enforces a *concurrency* cap (`open_connections >= max_concurrent_connections`) [5](#0-4) , then `setup_connection` is spawned and performs the actual, CPU-expensive TLS/QUIC handshake via `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` [6](#0-5) .

Critically, both rate limiters are only *charged* inside the success branch of the match on the handshake result:
```
Ok(new_connection) => {
    ... rate_limiter.register_connection(&from.ip()) ...
    ... overall_connection_rate_limiter.consume_tokens(1) ...
}
Err(e) => handle_connection_error(e, &stats, from),   // no token consumption
```
and the timeout branch (`else { stats.connection_setup_timeout... }`) also never touches either limiter [7](#0-6) . This means that any handshake attempt an attacker causes to fail or time out (e.g., malformed/garbage-but-Initial-framed QUIC packets, or a valid ClientHello with an invalid Finished/transport-parameter designed to force server-side crypto work then failure) is completely free from the perspective of both the per-IP and global token buckets. The code comment at lines 331-340 documents an intentional "shed fast" design that defers per-IP charging until "control-asserted" IP (post-handshake) to avoid enabling IP-spoofing reflection — but this design has the side effect that the CPU cost of the handshake itself (which happens before the charge) is not gated by anything proportional to that cost; it is bounded only by `max_concurrent_connections` and the fixed 2-second timeout, not by a rate proportional to CPU spent.

### Impact Explanation
An unstaked/unprivileged remote attacker can continuously fill the `max_concurrent_connections` (staked+unstaked capacity, e.g. `DEFAULT_MAX_STAKED_CONNECTIONS`/`DEFAULT_MAX_UNSTAKED_CONNECTIONS`) [8](#0-7)  slot budget with handshakes that are engineered to be cryptographically expensive but always fail, cycling every `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) [9](#0-8) . Because neither the per-IP nor the global `overall_connection_rate_limiter` ever decrement for these failures, the intended `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) admission-shaping comment/intent [10](#0-9)  provides no effective ceiling against this failure-mode traffic; the sustained handshake-attempt rate is instead governed purely by concurrency slots ÷ timeout duration, and the server's tokio handshake-processing threads can be kept continuously saturated doing TLS crypto work for connections that will never legitimately register. This starves legitimate TPU connection setup — matching the "CPU exhaustion on the QUIC handshake path" scoped impact in the question, falling under Agave's DoS / underpriced-pre-fee-work bounty category.

### Likelihood Explanation
Fully reachable by a single unprivileged remote UDP client with no stake, no gossip presence, and no special access — only the public TPU QUIC port. It requires no more than the ability to construct QUIC Initial packets whose ClientHello reaches the crypto-processing stage of the TLS handshake but is crafted to fail deterministically (e.g., invalid key confirmation), which is straightforward with a custom or modified QUIC client library. The attack is trivially repeatable and can be amplified by rotating source ports/IPs (real or via NAT) since `is_allowed` defaults to `true` for unseen IPs.

### Recommendation
Charge (or partially charge) the rate limiters for handshake *attempts*, not just successes — e.g., consume a token from `overall_connection_rate_limiter` and reserve/charge the per-IP bucket at admission time (before `incoming.accept()`/spawn), refunding on success if desired, rather than only spending on the `Ok(new_connection)` branch. Alternatively, enable QUIC stateless Retry (address validation) for unstaked/unverified peers so that expensive TLS crypto work is deferred until the source address is validated via a cheap, stateless token round trip, which is the standard QUIC anti-amplification/DoS mitigation and is not currently configured in `configure_server` in `streamer/src/quic.rs`.

### Proof of Concept
Integration/fuzz test plan (Rust, `streamer` crate):
1. Spin up the QUIC server via `setup_quic_server` (as used in `streamer/src/nonblocking/quic.rs` tests / `tpu-client-next/tests/connection_workers_scheduler_test.rs`) with default `QuicStreamerConfig`.
2. From a raw UDP socket (bypassing quinn's client API), craft N QUIC Initial packets per unique spoofed source port/IP that: (a) parse as valid Initial packets so `incoming.accept()` in `run_server` succeeds and `total_incoming_connection_attempts`/`outstanding_incoming_connection_attempts` increment, but (b) contain a ClientHello that forces rustls/quinn to perform key-exchange computation and then fail (e.g. invalid transport parameters or a bad Finished digest).
3. Assert via `StreamerStats`:
   - `stats.connection_setup_error` (or `connection_setup_timeout`) increases at a rate exceeding `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) sustained over several seconds.
   - `stats.connection_rate_limited_across_all` and `stats.connection_rate_limited_per_ipaddr` remain at 0 (or near 0) throughout, proving the limiters never engaged despite the sustained attack rate.
   - Measure wall-clock/CPU time of the tokio runtime handshake worker threads during the flood vs. baseline, and measure successful legitimate connection establishment rate (via a concurrently-running legitimate `make_client_endpoint` client) dropping to near zero, demonstrating starvation.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
