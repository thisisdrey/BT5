### Title
Cross-Contract StackerDB Chunk Signature Replay via Missing Contract Binding in `SlotMetadata` Digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a signer signs to authenticate a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash` [1](#0-0)  — it never binds the signature to the target smart-contract identifier (the specific StackerDB instance) or to a chain/network identifier. Because the Stacks signer boot contract (`signers.clar`) assigns the *same* signer→slot-id mapping to every `.signers-(0|1)-xxx` lane contract sharing the same reward-cycle parity [2](#0-1) , a validly-signed chunk captured from one StackerDB contract (e.g. the `BlockResponse` lane) can be replayed verbatim into a different StackerDB contract (e.g. the `Transactions` lane, or the same lane in a different reward cycle of matching parity) where the same signer owns the same `slot_id`, as long as the target slot's stored version has not yet reached the replayed `slot_version`. This is the same bug class as the reported `ApprovedCallsPolicy` issue: a signed message not bound to "the verifying address" (here, the verifying contract) can be replayed across independent instances that happen to share signer roles.

### Finding Description
The signature-verification path in the StackerDB replica logic (`try_replace_chunk` and `validate_received_chunk`) authenticates a chunk purely by checking that `slot_desc.verify(&slot_validation.signer)` succeeds for the locally-configured signer of that `slot_id` in *that* contract [3](#0-2) [4](#0-3) . The signature itself is over `auth_digest()`, which hashes only `(slot_id, slot_version, data_hash)` — never the `smart_contract` identifier being written to [1](#0-0) .

Because the boot contract `signers.clar` stores exactly one signer-slot list per reward-cycle parity (`stackerdb-signer-slots-0`/`-1`) and every message-lane contract (`BlockResponse`, `Transactions`, `BlockPreCommit`, etc., for a given cycle parity) reads the *same* list via `stackerdb-get-signer-slots-page` [5](#0-4) , a given signer address is assigned the identical `slot_id` across all of those distinct StackerDB contract instances. Each new StackerDB contract instance also initializes its per-slot version to `NO_VERSION` (0) at creation time [6](#0-5) .

Consequently, any unprivileged network observer who captures a broadcast `StackerDBChunkData` (slot_id, slot_version, sig, data) from one lane contract can resubmit that exact same tuple to a *different* lane contract (or the corresponding contract of a future reward cycle with matching parity) where:
1. the same signer address owns the same `slot_id`, and
2. the target slot's currently stored version is still below the replayed `slot_version` (trivially true for a freshly-instantiated contract, since versions restart at 0).

`try_replace_chunk`/`validate_received_chunk` will accept it as a fully authentic, freshly-signed chunk for the wrong contract, because nothing in the digest distinguishes contracts. The chunk is then stored and relayed onward to peers exactly as legitimate first-party data (`handle_unsolicited_StackerDBPushChunk` → inventory update → broadcast) [7](#0-6) .

### Impact Explanation
This allows network-wide propagation of forged/misattributed data: a message legitimately produced by a signer for one purpose/lane (e.g. a `BlockPreCommit` payload) can be replayed by any third party as if it were a fresh, validly authenticated chunk in an unrelated StackerDB instance for that same signer/slot. The payload-type/lane sanity check (`signer_message_payload_matches_lane`) exists only in the higher-level `libsigner` event-consumption path [8](#0-7) , not in the StackerDB storage/replication layer itself, so the chunk is durably stored and gossiped by every replica node regardless of whether it semantically belongs there. This matches the "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data" Critical-impact categories, since the write succeeds without a signature that was ever intended to authorize writes to that specific contract.

### Likelihood Explanation
StackerDB chunks are broadcast in the clear over the P2P network and are also queryable via read APIs, so any observer can trivially capture a `(slot_id, slot_version, sig, data)` tuple. No private key or privileged role is needed — only the ability to relay an HTTP POST or P2P push message to a target replica for a *different* StackerDB contract that shares a signer/slot mapping and has not yet advanced past the replayed version (guaranteed at contract creation, or opportunistically for any lane that lags behind).

### Recommendation
Include the target `QualifiedContractIdentifier` (and ideally the chain ID / network identifier) as part of the signed digest in `SlotMetadata::auth_digest()`, so a chunk signature is cryptographically bound to the specific StackerDB instance it is meant for, e.g.:
```rust
hasher.update(smart_contract.to_string().as_bytes());
hasher.update(chain_id.to_be_bytes());
```
This requires plumbing the contract identifier into `sign()`/`verify()` call sites (`try_replace_chunk`, `validate_received_chunk`, `StackerDBChunkData::sign`) so the digest can no longer be reused across differing contracts or reward-cycle instances.

### Proof of Concept
1. Signer `S` (owning `slot_id=k` in both `signers-0-<transactions>` and `signers-0-<blockresponse>` per `signers.clar`'s shared per-parity slot list) signs and pushes a `StackerDBChunkData{slot_id:k, slot_version:0, data:D}` to the `Transactions` lane contract for reward cycle `N`.
2. An unprivileged observer captures this chunk from the network (via P2P relay or the chunk-fetch RPC).
3. The observer resubmits the identical `(slot_id, slot_version, sig, data)` tuple as a `StackerDBPushChunk`/`POST /stackerdb_chunks` to the `BlockResponse` lane contract for reward cycle `N` (or the same `Transactions` lane contract for reward cycle `N+2`, same parity), whose slot `k` is also owned by `S` and whose stored version is still `< 0`/at genesis.
4. `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) verifies `slot_desc.verify(&slot_validation.signer)` successfully (since the digest never referenced the contract) and stores the chunk, which the node then relays to the whole network as legitimate data for that unrelated contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
