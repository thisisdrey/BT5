## Analysis

The Mattermost bug class is: attacker-controlled input size drives unbounded memory allocation during parsing, crashing the server (CWE-400). Searching java-tron for equivalent "attacker picks a length field, we allocate based on it without validating it against real bounds" patterns turned up multiple defended cases (RLP length checks, `Memory.extend` checked allocation, ModExp `UPPER_BOUND`, ABI string/bytes length checks in `ContractEventParser`, asset URL/description length caps, JSON nesting-depth guard). One place, however, still allocates a Java array whose size is taken directly from an attacker-supplied 32-byte word with no upper bound: the sig/bytes-array extraction helpers used by the `ValidateMultiSign` / `BatchValidateSign` TVM precompiles. ### Title
Unbounded array allocation from attacker-controlled length in ValidateMultiSign/BatchValidateSign precompiles can crash the node - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read an array-length field directly from TVM-precompile calldata (`words[offset].intValueSafe()`) and immediately allocate a Java array of that size (`new byte[len][]`), without validating `len` against the actual amount of data present or any sane upper bound. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
These helpers back the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, which are reachable from any contract via a `CALL`/`STATICCALL` TVM opcode to their fixed addresses. Any account that can broadcast a `TriggerSmartContract` transaction (or call a contract that internally calls these precompiles) fully controls the calldata bytes, including the word at `offset` that becomes `len`. Because `len` is only bounds-checked implicitly by later `Arrays.copyOfRange`/index accesses on the `data` array (which throw ordinary exceptions for out-of-range *content* reads), the array-length itself is unconstrained before the `new byte[len][]` allocation executes. A crafted value close to `Integer.MAX_VALUE` for this length word causes the JVM to attempt to allocate an object-reference array many gigabytes in size, which throws `OutOfMemoryError` — an `Error`, not a `RuntimeException`.

The existing exception handling around precompile execution and the VM interpreter loop only catches `RuntimeException` (and specific known exception types), not `Error`: [5](#0-4) 
An `OutOfMemoryError` thrown mid-allocation is uncaught by this layer and propagates outward through `Program.callToPrecompiledAddress` / `VMActuator`, unlike the deliberate `RuntimeException` containment added for TIP-854 malformed-calldata handling (which only guards against calldata *shorter* than the required head-word count, not against an oversized embedded length field): [6](#0-5) 
This is structurally the same bug class as the Mattermost advisory: a single attacker-supplied size field drives unbounded resource (memory) consumption during parsing/decoding of untrusted input, with no cap, leading to resource exhaustion / crash.

### Impact Explanation
An `OutOfMemoryError` thrown inside the JVM heap allocator can destabilize the whole process — other threads performing unrelated allocations may also fail, and in the worst case the node process crashes or becomes unresponsive, halting block production/serving for that node. This matches the "node crash or halt" / "API the node can no longer serve" impact criteria for this analog.

### Likelihood Explanation
Reaching this code only requires broadcasting an ordinary `TriggerSmartContract` transaction (or an `eth_call`/`triggerconstantcontract` JSON-RPC/gRPC request) whose calldata invokes the `ValidateMultiSign` or `BatchValidateSign` precompile address with a crafted length word. No special privileges, signatures beyond the caller's own, or witness/SR status are required — this is directly reachable by any unprivileged transaction broadcaster or anonymous constant-call API client, satisfying the "single signed transaction / contract call / API request" bar.

### Recommendation
Validate the extracted `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` against a sane upper bound (e.g., derived from `data.length / WORD_SIZE` or a fixed maximum signature-array size) before allocating `new byte[len][]`, rejecting (returning a failure `Pair`) rather than allocating when the length is inconsistent with the available calldata. This should be applied consistently with the same style of guard already used elsewhere in the file (`isValidAbiEncoding`) and in `ContractEventParser.subBytes`, which already reject oversized/negative lengths before performing allocation or copies.

### Proof of Concept
1. Deploy or use any existing contract, or call directly via `TriggerSmartContract` with `contract_address` set to the `ValidateMultiSign` (or `BatchValidateSign`) precompile address.
2. Construct calldata containing at least the minimum head-word count expected by the guard (so the short-data guard is not triggered), but set the array-length word (`words[offset]`) that becomes `len` in `extractSigArray`/`extractBytesArray` to a large value such as `0x7FFFFFFF`.
3. Broadcast the transaction (or send it via `triggerconstantcontract`/`eth_call`). Execution reaches `extractSigArray`/`extractBytesArray`, which executes `new byte[len][]`, attempting to allocate an oversized array and throwing `OutOfMemoryError`.
4. Because `OutOfMemoryError` is not caught by the `catch (RuntimeException e)` blocks in `VM.play` or the precompile call path, it propagates uncaught, risking process-wide memory pressure/crash on the node handling the transaction or constant call.

**Note on confidence**: I was unable to trace every call site into `extractBytesArray`/`extractSigArray`/`extractBytes32Array` (e.g., whether some outer wrapper in `PrecompiledContracts.java` bounds `len` against `data.length` before calling these helpers) due to the limited scope of code retrieved. The line ranges shown are the exact locations where the unbounded allocation occurs; confirming there is truly no upstream length check would require reading the full `ValidateMultiSign`/`BatchValidateSign` `execute()` methods in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`, which is recommended before treating this as fully validated.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
