### Title
Storage-backed `DataWord` values are not defensively copied, allowing in-place TVM arithmetic ops to corrupt cached/persisted contract storage - (`actuator/src/main/java/org/tron/core/vm/program/Storage.java`)

### Summary
`Storage.getValue()` and `Storage.put()` hand out and store raw 32-byte arrays without cloning. `DataWord`'s constructor also skips copying when the input is already 32 bytes long. Several TVM opcode handlers then mutate a `DataWord`'s backing array *in place*. Because of the missing copies, a `DataWord` produced from `SLOAD` (or passed to `SSTORE`) can be the exact same array object that is cached inside `StorageRowCapsule.rowValue` and later persisted by `Storage.commit()`. Any bytecode that performs an in-place mutating opcode on such a value corrupts the cached/persisted storage slot silently, without going through `StorageRowCapsule.setValue()`/`markDirty()`. This is the same root-cause class as the TensorFlow advisory: a buffer that callers assume is immutable/private is written to in place because the "clone on hand-off" boundary is missing.

### Finding Description
- `Storage.getValue(DataWord key)` returns `new DataWord(rowCache.get(key).getValue())` [1](#0-0) . `StorageRowCapsule.getValue()`/`getData()`/`getInstance()` return the live `rowValue` field, not a copy [2](#0-1) .
- The `DataWord(byte[] data)` constructor only copies when `data.length != WORD_SIZE`; for the common 32-byte case it directly aliases the caller-supplied array: `this.data = data;` [3](#0-2) .
- `Storage.put(DataWord key, DataWord value)` stores `value.getData()` directly into the `StorageRowCapsule` (new row or via `setValue`), again with no clone [4](#0-3) .
- Multiple opcode handlers mutate the popped `DataWord`'s backing array in place instead of allocating a new array: e.g. `ltAction`/`gtAction`/`sltAction`/`sgtAction`/`eqAction`/`isZeroAction` write `word1.getData()[31] = 1` and call `word1.and(DataWord.ZERO)` [5](#0-4) ; `byteAction` writes into `word2.getData()[31]` [6](#0-5) ; and `DataWord.and/or/xor` themselves mutate `this.data[i]` in place rather than returning a new array [7](#0-6) .

Because `SLOAD`/`SSTORE` values flow through `Storage.getValue`/`put` without a defensive copy, and are 32 bytes (the standard EVM word size), any subsequent in-place-mutating opcode applied to a value that was just loaded from or stored to storage mutates the exact array cached in `rowCache`/`StorageRowCapsule.rowValue`. If that row is (or later becomes) `dirty`, `Storage.commit()` persists the corrupted bytes to `StorageRowStore` [8](#0-7) , meaning the value actually written to chain state differs from the value the contract explicitly `SSTORE`'d. Even without a persisted write, a re-`SLOAD` of the same key within the same execution context returns the now-corrupted value, since `rowCache.get(key).getValue()` is the same mutated array.

### Impact Explanation
This lets a contract deployer/caller cause silent, unauthorized corruption of contract storage values during a single transaction's execution — either (a) persisting storage content that differs from what was explicitly `SSTORE`'d, or (b) causing subsequent `SLOAD`s in the same call/transaction to observe corrupted values. Either outcome can be leveraged inside a malicious contract to desynchronize balance/allowance/permission bookkeeping that legitimate contract logic relies on being stable between reads, potentially enabling unbacked balances or bypassed checks within a single crafted contract's own storage. This matches the "unbacked balance / permanent freezing / unauthorized account operation" impact bar, scoped to storage owned by the calling contract, reachable purely through TVM opcodes executed by any unprivileged contract deployer.

### Likelihood Explanation
Reachable by any transaction that deploys and calls a smart contract containing a crafted sequence of `SLOAD`/`SSTORE` followed by in-place-mutating opcodes (`AND`, `OR`, `XOR`, `LT`, `GT`, `SLT`, `SGT`, `EQ`, `ISZERO`, `BYTE`). No special permissions, precompiles, or network position are required — only ordinary contract-deployment and contract-call capability that every account already has.

### Recommendation
Enforce defensive copying at the storage/VM boundary:
- Have `Storage.getValue()`/`Storage.put()` clone the byte array before wrapping/storing it (e.g. `Arrays.copyOf`), matching the intended "each `DataWord` owns a private buffer" invariant.
- Alternatively/also, make `DataWord` always clone its input array in the constructor (remove the `data.length == WORD_SIZE` no-copy fast path), and make `and`/`or`/`xor` and friends allocate new result arrays instead of mutating `this.data` in place, consistent with how `add()` already does (`byte[] result = new byte[WORD_SIZE]; ... this.data = result;`) [9](#0-8) .

### Proof of Concept
Conceptual bytecode sequence for a deployed contract (exact opcode encoding omitted, semantics shown):
```
SSTORE(slot=0, value=V1)      ; Storage.put -> row.rowValue == V1 array (dirty=true)
v = SLOAD(slot=0)             ; Storage.getValue -> new DataWord aliasing row.rowValue (same array)
v2 = AND(v, mask)             ; DataWord.and mutates v.data (== row.rowValue) in place
; no further SSTORE is issued
```
After execution, `Storage.commit()` persists the row because `dirty == true`, writing the array that was mutated by `AND` rather than the originally `SSTORE`'d `V1`, without any explicit second `SSTORE` call — i.e., the persisted/observed storage value diverges from the value the contract logic intended to write/read, purely due to the missing copy at the `DataWord`/`StorageRowCapsule` boundary.

  public DataWord(byte[] data) {
    if (data == null) {
      this.data = ByteUtil.EMPTY_BYTE_ARRAY;
    } else if (data.length == WORD_SIZE) {
      this.data = data;
    } else if (data.length < WORD_SIZE) {
      System.arraycopy(data, 0, this.data, WORD_SIZE - data.length, data.length);
    } else {
      throw new RuntimeException("Data word can't exceed 32 bytes: " + ByteArray.toHexString(data));
    }
  }
