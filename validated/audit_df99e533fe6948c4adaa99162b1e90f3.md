### Title
Unbounded attacker-controlled offsets in `ValidateMultiSign`/`BatchValidateSign` precompile decoders cause out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
Similar to the iosm MUX decoder, which trusted device-supplied table/datagram offsets and only checked one of them for non-zero, `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` decode ABI-encoded call data by following attacker-supplied word offsets (`words[3]`, `words[1]`, `words[2]`) into the `words[]`/`rawData` arrays without validating that the resulting index/length stays within bounds of the actually-allocated buffers.

### Finding Description
`ValidateMultiSign.execute()` parses `rawData` into a fixed-size `DataWord[] words` array via `DataWord.parseArray(rawData)`, then computes an arbitrary offset from attacker data: [1](#0-0) 
`words[3].intValueSafe() / WORD_SIZE` can be any value derived from a 256-bit attacker-controlled word (bounded only by `intValueSafe`, not by `words.length`). This is used directly to index into `words[]` (`words[words[3]...]`) and passed into `extractSigArray`/`extractBytesArray`, which further index `words[offset + i + 1]` and copy from `rawData` at `(bytesOffset + offset + 2) * WORD_SIZE`: [2](#0-1) 
`extractBytes` performs `Arrays.copyOfRange(data, offset, offset + len)` with no bounds check against `data.length`, and no check that `offset` is non-negative — exactly the pattern flagged in the CVE (device/attacker-supplied offset and length used to index into a buffer with no bound against the real buffer size).

The `VMConfig.allowTvmOsaka()` guard, `isValidAbiEncoding()`, only validates that the *total* calldata length matches a fixed `(headerWords + n*itemWords)` shape: [3](#0-2) 
It does not validate that the specific offset fields (`words[3]`, `words[1]`, `words[2]`, and the per-item `bytesOffset`/`bytesLen`) point within the buffer — analogous to the kernel bug where only `first_table_index` non-zero was checked while every other offset/length in the chain was left unvalidated.

Crucially, in `ValidateMultiSign.execute()`, the offset computation and `extractSigArray`/`extractBytesArray` calls (lines 1066–1074) sit **outside** any try/catch block — the `try` only starts around the later permission-weight logic: [4](#0-3) 
A crafted `words[3]` value that resolves to an out-of-range index throws `ArrayIndexOutOfBoundsException` (from `words[offset...]`) or `NegativeArraySizeException`/`IndexOutOfBoundsException` (from `Arrays.copyOfRange` with a negative or oversized offset/len) that propagates uncaught out of `execute()`.

### Impact Explanation
An uncaught runtime exception thrown out of a precompiled contract's `execute()` is not the graceful, energy-consuming failure path (`Pair.of(true/false, DATA_FALSE)`) that the rest of the codebase relies on; it is an unexpected exception type that the TVM's precompile-call dispatch path may not model as a normal execution failure. This can manifest as inconsistent transaction execution/receipt behavior across nodes (some catching generically, some not) or, in the worst case, an unhandled exception bubbling up through block application in a way that halts transaction processing for that node — a chain-halt/DoS class impact reachable by any account that can send a transaction invoking the `validatemultisign` precompile (address `0x...0a`) with crafted calldata. `BatchValidateSign` mitigates this with an outer `try { doExecute(data) } catch (Throwable t)`, but `ValidateMultiSign` does not wrap the offset-computation/extraction step.

### Likelihood Explanation
Likelihood is high: reaching this precompile requires only building calldata for a `CALL` to address `0x0a` (`validatemultisign(address,uint256,bytes32,bytes[])`), which any account or contract can do without special permissions. Crafting `words[3]` to be an out-of-range multiple of `WORD_SIZE` relative to the actual `words.length` is trivial and does not require passing the `isValidAbiEncoding` shape check (that check only constrains total length, not the offset field's value).

### Recommendation
Bound-check every offset and length derived from calldata against the actual buffer sizes before use:
- Validate `words[3].intValueSafe() / WORD_SIZE` (and the equivalent in `BatchValidateSign` for `words[1]`/`words[2]`) is within `[0, words.length)` before indexing `words[]`.
- In `extractBytesArray`/`extractSigArray`, validate `bytesOffset`, `bytesLen`, and the final `(bytesOffset + offset + 2) * WORD_SIZE (+ len)` against `data.length` before calling `extractBytes`, replacing the raw `Arrays.copyOfRange` with a bounds-checked copy that fails safe (returns `DATA_FALSE`) instead of throwing.
- Wrap the offset-resolution and extraction logic in `ValidateMultiSign.execute()` in the same defensive try/catch (or bounds-check-then-fail pattern) already used in `BatchValidateSign.execute()`, so malformed calldata cannot produce an uncaught exception from `execute()`.

### Proof of Concept
Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the 4th static parameter (offset field for the dynamic `bytes[]`, i.e. `words[3]`) is set to an extremely large value (e.g., `0xFFFFFFFF` or a value like `(rawData.length/32) * 32 + 1000000`) instead of a valid in-bounds byte offset, while keeping total calldata length consistent with `isValidAbiEncoding`'s `(5 + n*5)*32` shape check (e.g., `n=1`). When `CALL`ed to precompile address `0x...0a`:
1. `words[3].intValueSafe() / WORD_SIZE` evaluates to an index far beyond `words.length`.
2. `words[words[3].intValueSafe() / WORD_SIZE]` at line 1067 (when `allowTvmSelfdestructRestriction` is active) or the `extractBytesArray`/`extractSigArray` call at line 1072–1074 throws `ArrayIndexOutOfBoundsException`.
3. Because this occurs before the method's own `try` block, the exception propagates out of `PrecompiledContract.execute()` uncaught by `ValidateMultiSign`, differing from the intended `(true, DATA_FALSE)` failure path used elsewhere in the same class.
