Audit Report

## Title
Nomination-pools uses `pallet-staking`'s `CurrentEra` (planned era) instead of `ActiveEra` for unbonding/withdrawal accounting, causing points-dissolved-but-funds-not-released fund traps - (File: `substrate/frame/nomination-pools/src/adapter.rs`)

## Summary
`pallet-nomination-pools`'s `unbond()` and `withdraw_unbonded()` extrinsics both key their unlock-era bookkeeping off `T::StakeAdapter::current_era()`, which is documented to return the active era but, for the legacy `pallet-staking` backend, actually forwards to `StakingInterface::current_era()` returning `CurrentEra::<T>::get()` — the "latest planned era" which can run ahead of `ActiveEra` during an in-flight election. This causes the pool's internal accounting to conclude an unbonding chunk is releasable one era earlier than the real staking ledger considers it withdrawable, dissolving pool points and firing `Withdrawn`/`MemberRemoved` events while the underlying `T::StakeAdapter::withdraw_unbonded()` call may not yet release the equivalent balance.

## Finding Description
`StakeStrategy::current_era()` in `substrate/frame/nomination-pools/src/adapter.rs` is documented as "returns active era which should be used for all non-election staking logic," but the implementation blindly forwards to `Self::CoreStaking::current_era()`. For the still-default legacy `pallet-staking` backend, `StakingInterface::current_era()` is implemented as `CurrentEra::<T>::get().unwrap_or(Zero::zero())` in `substrate/frame/staking/src/pallet/impls.rs:1994-1996`, and `CurrentEra` is explicitly documented in `substrate/frame/staking/src/pallet/mod.rs:494-499` as "the latest planned era, depending on how the Session pallet queues the validator set, it might be active or not" — a distinct storage item from `ActiveEra` at line 506.

By contrast, `pallet-staking-async`'s `StakingInterface::current_era()` (`substrate/frame/staking-async/src/pallet/impls.rs:1890-1894`) was patched to return `Rotator::<T>::active_era()`, with an explicit comment that "Active era should be used for all non-election staking logic." The prdoc for this patch, `prdoc/stable2512-2/pr_10986.prdoc`, bumps only `pallet-nomination-pools` and `pallet-staking-async` — legacy `pallet-staking` was never updated.

Nomination-pools' `unbond()` (`substrate/frame/nomination-pools/src/lib.rs:2290-2323`) computes `unbond_era = bonding_duration + current_era()` and inserts the unbonding balance into `sub_pools.with_era[unbond_era]`. `withdraw_unbonded()` (`substrate/frame/nomination-pools/src/lib.rs:2408-2513`) then reads `active_era = T::StakeAdapter::current_era()` and calls `member.withdraw_unlocked(active_era)`, which determines which chunks are releasable and unconditionally dissolves the corresponding sub-pool points, decrements `PoolMembers`, and emits `Withdrawn`/possibly `MemberRemoved`, before/independently of whether `T::StakeAdapter::withdraw_unbonded()`'s call into the real staking ledger has actually released the funds (since the ledger's own unlocking-chunk release logic is keyed to the true `ActiveEra`, not the planned `CurrentEra`). This exact failure mode — "points were dissolved but the held funds weren't released" — is documented as a real, previously-occurring incident in `prdoc/stable2512-3/pr_11018.prdoc`, remediated only via a bespoke one-time migration for a single affected pool member, not a systemic fix to the era source.

## Impact Explanation
This matches the "permanent user-fund lock" and "runtime bugs that compromise intended behavior" categories in the impact gate. Nomination-pools' internal accounting (`PoolMembers::unbonding_eras`, `SubPoolsStorage`) can settle a withdrawal — burning points, decrementing bonded balances, emitting `Withdrawn` — out of sync with the real unlock state of the underlying staking ledger, because it relies on `T::StakeAdapter::current_era()`, which for the still-default legacy `pallet-staking` backend returns the planned `CurrentEra`, not the genuinely active era. This is not theoretical: it is the identical root cause behind a prior real incident that required a one-time on-chain migration (`pr_11018`) to unlock one victim's stranded balance, and that root-cause fix was applied only to `pallet-staking-async`, leaving the legacy backend — the backend used by the overwhelming majority of production nomination-pool deployments — still exposed.

## Likelihood Explanation
No privileged action, malicious relayer, or off-chain assumption is required. Any nomination-pool member calling the public, permissionless `unbond` or `withdraw_unbonded` extrinsics during the multi-block window where `CurrentEra > ActiveEra` (the interval between an election being triggered and the era actually rotating, which recurs every era under normal `pallet-staking` operation) is exposed to the mismatch. This is a naturally recurring timing condition, not a rare edge case, making the issue highly likely to manifest in ordinary operation.

## Recommendation
Apply the same fix used for `pallet-staking-async`'s `StakingInterface::current_era()` to legacy `pallet-staking`: change `substrate/frame/staking/src/pallet/impls.rs`'s `current_era()` implementation to return the genuinely active era (e.g., derived from `ActiveEra::<T>::get()`) rather than `CurrentEra::<T>::get()`, or introduce a distinct `active_era()` method on `StakingInterface`/`StakeStrategy` that `pallet-nomination-pools`' `unbond()` and `withdraw_unbonded()` are required to use instead of `current_era()`. Additionally, add a try-state/integrity check asserting `T::StakeAdapter::current_era()` never exceeds the true active era for whichever staking backend is configured.

## Proof of Concept
1. Configure a runtime with `pallet-nomination-pools` backed by legacy `pallet-staking` (`T::StakeAdapter` wraps `pallet-staking`'s `StakingInterface`).
2. Advance the chain so that `CurrentEra::<T>::get() == ActiveEra::<T>::get().index + 1` (a state that persists for multiple blocks during every ordinary election-and-era-rotation cycle).
3. Have a pool member call `unbond()`; observe `unbond_era` computed via `T::StakeAdapter::current_era()` (`substrate/frame/nomination-pools/src/lib.rs:2290-2291`), which resolves to the ahead-by-one planned era.
4. Once nomination-pools' `bonding_duration` eras have elapsed by this ahead-of-real reckoning (but the staking ledger's real `ActiveEra` is still one behind), the member calls `withdraw_unbonded()`. Observe `active_era = T::StakeAdapter::current_era()` (`substrate/frame/nomination-pools/src/lib.rs:2410`) again yields the ahead value, so `member.withdraw_unlocked(active_era)` reports the chunk unlockable; pool points are dissolved and `Withdrawn` is emitted (`substrate/frame/nomination-pools/src/lib.rs:2436-2513`), while `T::StakeAdapter::withdraw_unbonded()`'s underlying ledger call — keyed to the real, still-behind `ActiveEra` — does not yet release the equivalent balance.
5. Result reproduces the trapped-balance condition previously fixed only via the one-time migration in `pr_11018`: verify via unit test in `substrate/frame/nomination-pools/src/tests.rs` that constructs a mock `StakeAdapter` where `current_era()` is decoupled from the mock staking ledger's real unlock-eligibility state, and assert that `withdraw_unbonded` dissolves points/emits `Withdrawn` even though the mock ledger's corresponding unlocking chunk has not yet matured.
