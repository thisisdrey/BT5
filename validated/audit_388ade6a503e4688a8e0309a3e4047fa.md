### Title
`AttachmentsBatchStateMachine::try_proceed`'s `Done` handler stores every downloaded attachment blob unconditionally, even when no `AttachmentInstance` in `attachments_instances` references its hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
In the `Done` branch of `AttachmentsDownloader::run`, the loop over `context.attachments` calls `network.atlasdb.insert_instantiated_attachment(&attachment)` for every attachment regardless of whether `find_all_attachment_instances(&attachment.hash())` returned any rows. This means a peer that answers an `AttachmentRequest` with content that doesn't match the requested/on-chain `content_hash` still gets its blob permanently written into the local `attachments` table.

### Finding Description
The invariant the codebase intends to hold is: every row persisted via `insert_instantiated_attachment` should correspond to some `AttachmentInstance.content_hash` that was committed on-chain (i.e., is present in `attachments_instances`). The `Done`-state loop breaks this: [1](#0-0) 

```rust
for attachment in context.attachments.drain() {
    let attachments_instances = network
        .atlasdb
        .find_all_attachment_instances(&attachment.hash())
        .map_err(net_error::DBError)?;
    network
        .atlasdb
        .insert_instantiated_attachment(&attachment)
        .map_err(net_error::DBError)?;
    for attachment_instance in attachments_instances.into_iter() {
        resolved_attachments.push((attachment_instance, attachment.clone()));
    }
    ...
}
```

`find_all_attachment_instances` is queried purely to build the `resolved_attachments` output list; its result length is never checked before `insert_instantiated_attachment` runs. Even if `attachments_instances` is empty (no on-chain commitment references this hash), the blob is still inserted into local storage.

`context.attachments` is populated in `extend_with_attachments`, which simply decodes whatever bytes a peer returns for an `AttachmentRequest` and inserts them into the set without validating that the decoded attachment's hash equals the `content_hash` that was actually requested: [2](#0-1) 

The `AttachmentRequest` itself is built from `content_hash` values sourced from `attachments_instances` (on-chain-derived), [3](#0-2) , but nothing in the visible request/response path (`decode_atlas_get_attachment`, `extend_with_attachments`, or the `Done` loop) re-verifies that the attachment bytes returned by the remote peer actually hash to the `content_hash` that was requested. A remote peer that a node is syncing attachments from (an outbound sync peer, reachable without any privileged role) can therefore respond to a legitimate `GetAttachment` request with arbitrary attachment bytes of its choosing, and those bytes will be persisted into the node's `attachments` table via `insert_instantiated_attachment` with no corresponding on-chain `AttachmentInstance`.

The only bound on this storage growth is `evict_expired_uninstantiated_attachments`, run once per state-machine `Done` cycle [4](#0-3) , which is a time/expiry-based sweep, not a hash-correctness check, and provides no guarantee against continual resupply of new unlinked blobs by a hostile peer across many polling cycles.

### Impact Explanation
A remote peer that a victim node treats as an outbound sync source for Atlas (no admin role or secret required, simply being selected via `get_outbound_sync_peers`/`get_data_url`) can cause the victim to durably store arbitrary attacker-chosen blobs in its Atlas database with zero corresponding on-chain `AttachmentInstance` commitment. This is repeatable per attachment request/response round and is bounded only by periodic, best-effort expiry eviction rather than any hash-correctness gate, resulting in unbounded storage of peer-supplied data disconnected from chain state (High: storing/serving data with no canonical commitment).

### Likelihood Explanation
Preconditions are modest: the attacker must be selected as (or run) an outbound Atlas sync peer that the victim queries for attachment inventories/content — something any peer participating in gossip can arrange without special privilege, secrets, or admin access. The attacker only needs to answer a `GetAttachment` HTTP request with a decodable `Attachment` payload of their choosing; no signature or additional secret gates this response. This can be repeated for every batch cycle the node processes.

### Recommendation
Before calling `insert_instantiated_attachment`, verify that `attachments_instances` returned by `find_all_attachment_instances(&attachment.hash())` is non-empty (i.e., some on-chain `AttachmentInstance.content_hash` actually references this hash) — skip/drop and penalize the peer otherwise. Additionally, in `extend_with_attachments`, validate that the decoded attachment's hash equals the `content_hash` of the specific `AttachmentRequest` that produced it before adding it to `context.attachments`, rejecting mismatched responses immediately.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/download.rs` (or an integration test using `PeerNetwork`/`AtlasDB`):
1. Construct an `AtlasDB` with an empty `attachments_instances` table (no instance referencing a chosen hash `H`).
2. Construct an `Attachment` with content whose `hash()` equals `H`.
3. Build an `AttachmentsBatchStateContext` and manually insert this `Attachment` into `context.attachments` (simulating a malicious/mismatched peer response via `extend_with_attachments`).
4. Drive `AttachmentsBatchStateMachine::try_proceed` (or directly execute the `Done` branch logic in `AttachmentsDownloader::run`) with `network.atlasdb` referencing the DB from step 1.
5. Assert `network.atlasdb.find_all_attachment_instances(&H)` is empty before the call, then assert that `network.atlasdb` now contains the attachment (e.g. via a lookup on the `attachments` table / `find_uninstantiated_attachment` or equivalent), proving `insert_instantiated_attachment` persisted a blob with no matching on-chain commitment — confirming the code path at [5](#0-4)  stores the attachment unconditionally.
