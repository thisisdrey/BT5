Found a concrete local analog matching the report's bug class: user funds taken and burned by the contract/pallet, with no path to return them when the downstream operation cannot use them.

### Title
`snowbridge_pallet_system_frontend::add_tip` burns the user's tip asset before send, and on remote rejection the value is permanently lost (only tracked in `LostTips`, never refunded) - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
Analogous to the Sense report's pattern (contract pulls in more value than the operation ultimately consumes, and doesn't return the unused portion to the sender), `Pallet::add_tip` in `snowbridge-pallet-system-frontend` irrevocably withdraws and burns the user's tip asset locally (via `swap_fee_asset_and_burn` → `burn_for_teleport`) *before* it is known whether the remote `add_tip` call on BridgeHub will actually succeed. If the remote pallet rejects the tip (unknown/consumed nonce), the burned value is not returned to the user — it is only recorded in `LostTips` for bookkeeping.

### Finding Description
`add_tip` at [1](#0-0)  executes in this order:
1. `swap_fee_asset_and_burn(who, asset)` — this swaps the tip asset for Ether and calls `burn_for_teleport`, which withdraws/burns the asset from the user's account on AssetHub [2](#0-1) .
2. The resulting `ether_gained` amount is packaged into an `AddTip` transact call and sent via XCM to BridgeHub's `snowbridge-pallet-system-v2`.

On BridgeHub, `EthereumSystemV2::add_tip` forwards the call to the inbound or outbound queue's `AddTip::add_tip`, which can fail with `AddTipError::UnknownMessage` (outbound: no `PendingOrder` for that nonce) or `AddTipError::NonceConsumed` (inbound: message already processed) [3](#0-2) . When that happens, `EthereumSystemV2::add_tip` does **not** propagate a failed dispatch back that would let the value be recovered — it simply records the loss: [4](#0-3) 

The value was already destroyed on the source chain (AssetHub) in step 1, at the time `add_tip` was called on AssetHub — well before the destination pallet on BridgeHub even attempts to apply the tip. There is no mechanism anywhere in this path (`system-frontend`, `system-v2`, `inbound-queue-v2`, `outbound-queue-v2`) that returns the burned Ether/asset to the sender when the remote application of the tip fails; `LostTips` is purely an accounting map with no corresponding claim/refund extrinsic found in these pallets.

This exactly mirrors the reported bug class: value is taken from the user (via `_transferFrom`/burn) based on an unverified assumption that the full amount will be consumed downstream, and the excess/unused amount is not returned to the rightful beneficiary — it is destroyed and only "tracked," not restored.

### Impact Explanation
Any unprivileged AssetHub user who calls `add_tip` targeting a nonce that is not (yet, or no longer) a valid pending outbound order or an already-consumed inbound nonce permanently loses the swapped/burned tip amount. This is a direct, permanent user-fund loss caused by normal pallet logic (no malicious relayer, validator, or governance actor required) — it falls squarely within the "permanent user-fund lock/loss" and "duplicate settlement/payout — wrong beneficiary or amount" impact categories for the live Snowbridge scope. Because `MessageId::Outbound`/`Inbound(nonce)` values are provided directly by the caller with no ownership check tying the caller to that nonce's original message, any user (not just the original message sender) can trigger this loss against themselves or, more importantly, the burn happens unconditionally regardless of whether the nonce is valid — an attacker gains nothing directly, but the design guarantees fund destruction for any invalid nonce, including via off-by-one/race conditions where a nonce is consumed between fee-swap and remote processing (submit vs. add_tip race).

### Likelihood Explanation
High. Triggering the vulnerable path requires no privileged access — a signed AssetHub user need only call the public `add_tip` extrinsic with any `MessageId` that does not correspond to a currently pending order (trivial to do accidentally, e.g., racing against message finalization, or the message being processed between the time the tip is composed and when the XCM lands on BridgeHub). The existing test `tip_to_invalid_nonce_is_added_to_lost_tips` [5](#0-4)  confirms this exact scenario occurs in normal operation and is treated as expected/passing behavior rather than a bug — i.e., there's no code path guarding against it.

### Recommendation
Do not burn/destroy the tip asset on AssetHub until confirmation that the remote tip application succeeded. Options:
- Hold the swapped Ether in escrow (e.g., under a `HoldReason`) on AssetHub until a delivery-confirmation/ack XCM message from BridgeHub confirms the tip was applied; refund the hold if the remote call reports failure.
- Alternatively, validate nonce validity synchronously (e.g., via a state proof or a two-phase commit) before burning, or provide a `claim_lost_tip` extrinsic that lets the sender reclaim value tracked in `LostTips` by minting/refunding an equivalent amount rather than treating it purely as a write-off ledger.

### Proof of Concept
1. On AssetHub, a user calls `SnowbridgeSystemFrontend::add_tip(origin, MessageId::Outbound(N), asset)` where `N` is a nonce with no corresponding `PendingOrder` on BridgeHub (e.g., already delivered/removed, or never created) — as reproduced in `tip_to_invalid_nonce_is_added_to_lost_tips` [6](#0-5) .
2. `swap_fee_asset_and_burn` executes first and unconditionally burns the swapped Ether via `burn_for_teleport` [2](#0-1) .
3. The XCM `Transact` call reaches BridgeHub; `OutboundQueue::add_tip` returns `AddTipError::UnknownMessage` since `PendingOrders` has no entry [3](#0-2) .
4. `EthereumSystemV2::add_tip` catches the `Err`, increments `LostTips[sender]` by `amount`, and emits `TipProcessed { success: false }` [7](#0-6) .
5. The user's burned Ether is never returned — `LostTips` has no associated claim/refund call, confirming permanent loss of the burned amount for a fully unprivileged, easily-triggered action.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
