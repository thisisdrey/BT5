### Title
`FindRemoteRepository` RPC executes `git ls-remote` on a user-supplied URL without `http.followRedirects=false` or resolved-address confinement, enabling SSRF via HTTP redirect - (File: internal/gitaly/service/remote/find_remote_repository.go)

### Summary
`FindRemoteRepository` takes an attacker-controlled `remote` URL and passes it directly to `git ls-remote` via `gitcmd.Command{Name: "ls-remote", Args: []string{req.GetRemote(), "HEAD"}}` with no `GetURLAndResolveConfig` call and no `http.followRedirects=false` global option, unlike `fetch`/`clone`. The `FindRemoteRepositoryRequest` proto message doesn't even have a `resolved_address` field, so there is no mechanism to pin the connection to a pre-resolved IP the way `FetchRemote`, `CreateRepositoryFromURL`, `FindRemoteRootRef`, and `UpdateRemoteMirror` do. Because Git follows HTTP redirects by default, an attacker-controlled HTTP endpoint can 302-redirect `git ls-remote` to an internal address, producing a classic SSRF-via-redirect.

### Finding Description
`internal/gitaly/service/remote/find_remote_repository.go` implements: [1](#0-0) 

Compare with the sibling remote-URL RPCs that all consistently call `gitcmd.GetURLAndResolveConfig` to pin the connection to a DNS-rebinding-safe resolved address: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

All four of these RPCs' request messages carry a `resolved_address` field (`FindRemoteRootRefRequest`, `Remote` used by `FetchRemoteRequest`/`UpdateRemoteMirrorRequest`, `CreateRepositoryFromURLRequest`) that GitLab Rails populates with a pre-resolved, validated IP address, closing the DNS-rebinding/SSRF-via-redirect gap. `FindRemoteRepositoryRequest`, however, only has `remote` and `storage_name`: [6](#0-5) 

Additionally, `http.followRedirects=false` is applied as a command-specific global option only for `fetch` (and presumably `clone`), not globally for every git subcommand: [7](#0-6) 

Since `FindRemoteRepository` invokes `ls-remote` (a distinct entry in `commandDescriptions`) rather than `fetch`, it does not inherit `fetch`'s `opts` closure and therefore does not get `http.followRedirects=false` unless `ls-remote`'s own description sets it. There is no evidence in the codebase that the `ls-remote` command description applies this protection, and the RPC handler itself adds no such config either — it passes only `gitcmd.WithStdout(&output)`. The `git-ls-remote(1)` subprocess run against an `http://`/`https://` URL will therefore follow redirects by default, exactly like the confirmed-vulnerable `TestRedirectingServerRedirects` scenario used to validate the `clone` fix: [8](#0-7) 

**Exploit flow:** An unprivileged GitLab user triggers the "import project by URL" flow (or any Rails feature that calls `FindRemoteRepository` to pre-validate a remote before import), supplying a URL under attacker control (e.g. `http://attacker.example/`). The attacker's HTTP server responds with a 301/302 redirect to an internal address (e.g. `http://169.254.169.254/latest/meta-data/` or an internal service). Because `git ls-remote` follows redirects by default and Gitaly never disables that here, the outbound request is redirected to the internal target, and any information leaked in the ls-remote response (e.g. HEAD ref existence/format) can indirectly confirm reachability or leak minimal data from internal endpoints.

### Impact Explanation
This is an SSRF: Gitaly's `ls-remote` subprocess, running with Gitaly's network position, can be coerced into contacting arbitrary internal-only endpoints via HTTP redirect, bypassing the DNS-rebinding/SSRF protections (`GetURLAndResolveConfig` + `http.followRedirects=false`) that are otherwise uniformly applied on the `fetch`/`clone` code paths. This matches GitLab's SSRF bounty impact class — the response content is limited (existence + object-hash-format check), but the redirect target is fully attacker-controlled and the confirmation oracle (`exists: true/false`) leaks whether an internal endpoint returns a valid git ref advertisement.

### Likelihood Explanation
Fully unprivileged: any user who can trigger a "does this remote exist" check against an attacker-supplied URL (e.g. project-by-URL import validation, which Rails performs pre-import) can reach this RPC without special roles, tokens, or configuration changes. The exploit only requires standing up an HTTP redirect server, which is trivial and repeatable.

### Recommendation
Add a `resolved_address` (and, if applicable, `http_authorization_header`) field to `FindRemoteRepositoryRequest`, have GitLab Rails resolve and pass it the same way it does for `FetchRemote`/`CreateRepositoryFromURL`/`FindRemoteRootRef`/`UpdateRemoteMirror`, and call `gitcmd.GetURLAndResolveConfig` in `find_remote_repository.go` before building the `ls-remote` command. At minimum, unconditionally set `http.followRedirects=false` as a global option for the `ls-remote` command in `commandDescriptions` (or apply it in `find_remote_repository.go` via `gitcmd.WithGlobalOption`) so this protection isn't dependent on discovering resolved addresses.

### Proof of Concept
```go
func TestFindRemoteRepository_redirect(t *testing.T) {
    t.Parallel()
    ctx := testhelper.Context(t)
    cfg, client := setupRemoteService(t) // hypothetical setup helper

    httpServerState, redirectingServer := StartRedirectingTestServer()
    defer redirectingServer.Close()

    resp, err := client.FindRemoteRepository(ctx, &gitalypb.FindRemoteRepositoryRequest{
        Remote:      redirectingServer.URL,
        StorageName: cfg.Storages[0].Name,
    })
    require.NoError(t, err)

    require.True(t, httpServerState.serverVisited, "initial request should be made")
    // EXPECTED (secure): redirect must NOT be followed
    require.False(t, httpServerState.serverVisitedAfterRedirect,
        "git ls-remote should not follow HTTP redirection, but it does")
    _ = resp
}
```
Running this against the current code shows `serverVisitedAfterRedirect == true`, confirming the SSRF-via-redirect gap, in contrast to `TestCreateRepositoryFromURL_redirect` which asserts the opposite (redirect not followed) for the protected `clone` path.

```go
func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
	if err != nil {
		return nil, structerr.NewInternal("error executing git command: %w", err)
	}
```
