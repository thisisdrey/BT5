### Title
Unbounded array allocation from attacker-controlled length field in `PrecompiledContracts.extractBytesArray`/`extractSigArray` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign` and `BatchValidateSign` (TVM precompiles reachable via any `CALL`/`STATICCALL` from a contract, i.e. by any transaction broadcaster) decode a length field directly out of caller-supplied `data` and use it to size a Java array before any upper bound is enforced, unless the `allowTvmSelfdestructRestriction` hard-fork flag is active.

### Finding Description
`extractBytesArray` and `extractSigArray` read the array length straight from the untrusted calldata and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

In `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, the `MAX_SIZE` bound on this length is only checked when `VMConfig.allowTvmSelfdestructRestriction()` is true; the array-extraction helper itself is called with no independent bound when that flag is disabled: [3](#0-2) [4](#0-3) 

This mirrors the CVE bug class (`handle_keywordonly_args` trusting an attacker-influenced count without validating it against buffer bounds before indexing/allocating): a length value taken from untrusted, structured input is used to size a data structure with no upper limit, producing either an out-of-bounds read (in the `words[offset + i + 1]` walk, since only the *starting* offset is range-checked, not every subsequent index) or an unbounded allocation that throws `NegativeArraySizeException`/`OutOfMemoryError`.

### Impact Explanation
`OutOfMemoryError` is a JVM `Error`, not a `RuntimeException`. The general safety nets that contain malformed opcode/precompile behavior in the interpreter only catch `RuntimeException`: [5](#0-4) 
An `Error` thrown from `contract.execute(data)` (via `Program.callToPrecompiledAddress`) would not be caught by these handlers and would propagate out of transaction/block execution, which can destabilize or crash the executing thread/node — a node-halt condition rather than a contained, per-transaction revert.

### Likelihood Explanation
Reachability depends entirely on the chain-level `allowTvmSelfdestructRestriction` flag being disabled. This is a hard-fork-style proposal flag defined in `VMConfig`/`ProposalUtil`/`DynamicPropertiesStore`. On the current TRON mainnet this proposal has very likely already been activated for a long time, which would mean the guarded branch (`extractSigArray` with the pre-checked `MAX_SIZE`) is the one actually exercised in production today, making the unguarded branch effectively dead code on mainnet. I was not able to confirm from the index whether any deployment (private/enterprise fork, testnet, or a chain that has not yet activated this specific proposal) still executes the unguarded branch, nor could I fully verify the exact clamping behavior of `DataWord.intValueSafe()` (whether it can return values large enough to force an immediate `OutOfMemoryError` versus a smaller/negative value that only yields a contained `RuntimeException`). This uncertainty, combined with the extensive existing hardening in this file (`isValidAbiEncoding` TIP‑854 guards, `MAX_SIZE` checks, outer try/catch in `BatchValidateSign.execute`, and dedicated `OuterFrameContainment` tests), makes it unclear this is an exploitable, unmitigated path on a live, current deployment rather than dead legacy code.

### Recommendation
Enforce the `MAX_SIZE` (and general non-negative, bounded) check on the decoded length unconditionally in `extractBytesArray`/`extractSigArray` themselves, rather than only in the caller and only when `allowTvmSelfdestructRestriction` is active, and validate every derived index (`offset + i + 1`, `offset + bytesOffset + 1`) against `words.length` before dereferencing.

### Proof of Concept
Not produced — could not be validated end-to-end given the uncertainty above (activation status of `allowTvmSelfdestructRestriction` on the target deployment, and the exact numeric range of `DataWord.intValueSafe()`), so no concrete malicious-transaction PoC is asserted.
