Audit Report

## Title
PSM `internal_to_external` decimal-scaling division truncates redemption output to zero for small amounts, with no minimum-output or slippage guard - (File: `substrate/frame/psm/src/lib.rs`)

## Summary
`Pallet::internal_to_external` in the PSM pallet converts a burnt internal-asset amount into the external-asset amount owed on redemption by floor-dividing by `10^(internal_decimals - ext_decimals)` with no minimum-output check and no caller-supplied slippage/`min_amount_out` guard. [1](#0-0) 
When the decimal gap between internal and external assets is large, any redeemed amount smaller than the scaling factor `10^diff` floors to zero external output while the internal asset burn still proceeds, destroying value instead of settling it to the redeeming user.

## Finding Description
The conversion logic is exactly as described: for the `Less` branch (external asset has fewer decimals than internal), the function computes `factor = 10^diff` via `pow10` and does `amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero)` with no post-division floor/minimum check. [2](#0-1) 
`pow10` itself only guards against `u128`/`BalanceOf` overflow, not against the resulting factor being large relative to the input amount. [3](#0-2) 
The pallet's own documentation confirms this function is the redemption-path conversion ("Redemption: Burn internal asset → receive external asset (minus fee)"), and that internal debt/burn and external payout are two separate steps in the flow. [4](#0-3) 
The pallet's own unit tests explicitly document that the inverse conversion (`external_to_internal`) truncates via floor-division, corroborating that `internal_to_external` behaves the same way for its `Less` branch: [5](#0-4) 

I was able to directly confirm the `internal_to_external`/`pow10` implementation matches the claim verbatim, and that it contains no minimum-output or slippage check. I was not able to fully trace the exact `redeem` dispatchable call site within the available tool budget to confirm line-by-line how the zero result is handled downstream (e.g., whether it is transferred as zero or whether some other guard silently rejects zero-value transfers elsewhere in the runtime). This limits full end-to-end exploit confirmation, though the truncation behavior of the conversion function itself, which is the core of the claim, is directly verified in code.

## Impact Explanation
If reachable from the public `redeem` extrinsic without a minimum-output guard, this breaks the settlement invariant that burnt/debited internal value must be conserved and paid out to the rightful beneficiary in full (or fail atomically) — a user could have their internal asset burned while receiving zero external asset, a real fund-loss scenario matching the "theft/unbacked... duplicate settlement" class of impacts in the gate. However, without confirming the call site, it's not fully verified that `redeem` doesn't independently reject a zero-output computation before executing the burn (e.g., via an explicit check elsewhere in the dispatchable body) — this residual uncertainty affects confidence in end-to-end exploitability, though the underlying conversion logic itself is confirmed unsafe as described.

## Likelihood Explanation
Any unprivileged user can call `redeem` with a small amount against a PSM instance whose external asset has significantly fewer decimals than the internal asset (a configuration set by `add_external_asset`, not by the attacker) — no privileged role or malicious peer/relayer is required. Exploitability is conditioned on runtime configuration (large decimal gaps), consistent with the original claim's own likelihood framing.

## Recommendation
Add a check in `internal_to_external` (and any dispatchable path relying on it) that rejects or rounds in the user's favor when a non-zero input amount would scale to zero output, and/or accept a caller-supplied `min_amount_out` parameter enforced before burning the internal asset, ensuring the burn and payout are atomic and either both succeed with correct value or both fail.

## Proof of Concept
1. Configure a PSM instance with `internal_decimals = 18` and an external asset with `ext_decimals = 2` (`diff = 16`, `factor = 10^16`).
2. Call the public `redeem` extrinsic burning `9_999_999_999_999_999` internal units (just under `10^16`).
3. `internal_to_external` computes `amount.checked_div(&10^16)` → `0` per [2](#0-1) , matching the pallet's own truncation test pattern in `tests.rs`.
4. Verify (in a full trace of the `redeem` dispatchable, not completed here due to tool budget) whether the internal burn executes unconditionally despite the zero external payout — this final confirmation step is the one part of the PoC not directly verified in this session.

		pub(crate) fn internal_to_external(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
			}
		}
