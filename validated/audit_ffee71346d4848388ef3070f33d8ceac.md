### Title
Unprivileged dust-transfer griefing fills a victim's per-account token list and blocks all new deposits/mints - (File: contracts/Pool.sol)

### Summary
Metronome tracks every deposit token and debt token an account touches in `depositTokensOfAccount` / `debtTokensOfAccount`, capped by `MAX_TOKENS_PER_USER = 30` in `contracts/Pool.sol:79`. Any addition past the cap reverts in `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`). Because `DepositToken` shares are freely transferable and `deposit(amount_, onBehalfOf_)` credits an arbitrary beneficiary (`contracts/DepositToken.sol:211-237`), an unprivileged attacker can forcibly push dust balances of up to 30 distinct whitelisted deposit tokens onto a victim's list, analogous to the NATS bug where an unauthenticated peer bricks the server by sending repeated messages before session setup. Once the victim's list is full, every call path that would add a new token (deposits into a new collateral, minting a new synthetic, transfers of a new msdTOKEN to the victim) reverts.

### Finding Description
- `DepositToken._mint` and `DepositToken._transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance moves from zero (`contracts/DepositToken.sol:486-488`, `contracts/DepositToken.sol:518-520`). There is no opt-in or approval; the recipient cannot refuse a token list entry.
- `Pool.addToDepositTokensOfAccount` is externally callable only by a registered deposit token, but the *attacker* controls when the deposit token calls it simply by transferring dust to the victim or calling `deposit(1 wei, victim)` (`contracts/Pool.sol:216-220`).
- `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` when `debtTokensOfAccount + depositTokensOfAccount >= 30` (`contracts/Pool.sol:143-148`). The revert happens inside the mint/transfer, so the entire victim-facing operation fails atomically.
- Minting debt similarly triggers `addToDebtTokensOfAccount`, so once the list is full the victim cannot open a borrow position in a synthetic asset they do not already hold — the count is shared across both lists.

### Impact Explanation
Temporary freezing of funds / liveness denial. A victim whose list is saturated cannot deposit new collateral types, cannot mint new synthetic debt, and cannot receive new msdTOKEN transfers (including seized collateral routed through `DepositToken.seize`/`_transfer` to a liquidator address the liquidator controls). Their already-held positions remain withdrawable and they can clear slots by transferring or withdrawing dust balances to zero (which calls `removeFromDepositTokensOfAccount`), so the freeze is temporary and costs the victim only gas and inconvenience — but it is fully attacker-induced and repeatable at low cost (30 dust transfers, one per whitelisted collateral, front-runnable against the victim's own deposit transactions). No modifier (`whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`) prevents it because the deposit-token caller is legitimate.

### Likelihood Explanation
Unprivileged and cheap: the attacker needs only dust amounts of each whitelisted underlying (or already-held msdTOKEN) and 30 transactions. `MAX_TOKENS_PER_USER` is a hard constant of 30, and pools with several whitelisted collaterals make saturation easy. The attack must be repeated if the victim clears slots, but the attacker can re-fill for the same dust cost and can monitor mempool to front-run the victim's legitimate deposits.

### Recommendation
- Make token-list additions consent-based, or charge them to the sender/initiator rather than the recipient (e.g., only track tokens on self-initiated `deposit`/`mint`, not on `transfer`/seizure receipts).
- Alternatively, raise/remove the per-account cap, or make `transfer`/`seize` skip `addToDepositTokensOfAccount` when the recipient is at the cap (handling untracked balances in `depositOf`).

### Proof of Concept
```solidity
// Foundry fork-style PoC against a deployed Pool with >= 1 whitelisted DepositToken
// Assume `depositTokens` = array of whitelisted IDepositToken, `underlyings` = their ERC20s,
// `victim` = target account, `pool` = Pool instance.

function test_griefFillTokenList() public {
    address victim = makeAddr("victim");

    // Attacker fills victim's depositTokensOfAccount to MAX_TOKENS_PER_USER
    uint256 max = pool.MAX_TOKENS_PER_USER(); // 30
    uint256 slots = max - pool.getDepositTokensOfAccount(victim).length
                        - pool.getDebtTokensOfAccount(victim).length;

    for (uint256 i = 0; i < slots; ++i) {
        IDepositToken dt = depositTokens[i % depositTokens.length];
        // rotate through whitelisted collateral; deposit 1 wei on behalf of victim
        deal(address(dt.underlying()), attacker, 1);
        vm.prank(attacker);
        dt.underlying().approve(address(dt), 1);
        vm.prank(attacker);
        dt.deposit(1, victim); // _mint -> pool.addToDepositTokensOfAccount(victim)
    }

    // Victim can no longer deposit a new collateral type or receive new msdTOKEN
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    depositTokens[depositTokens.length - 1].deposit(1e18, victim);

    // Victim also cannot mint a synthetic they don't already hold
    // (DebtToken._mint -> pool.addToDebtTokensOfAccount(victim) -> same revert)
}
```

**Known limitation / uncertainty:** I verified the deposit-token path end-to-end (`DepositToken.deposit` → `_mint` → `pool.addToDepositTokensOfAccount` → `onlyIfAdditionWillNotReachMaxTokens` revert); I did not fully trace `DebtToken._mint` internals, but it uses the same `addToDebtTokensOfAccount` guard per `contracts/Pool.sol:204-208`. The impact is bounded to temporary freezing — the victim retains the ability to clear slots — so severity is griefing-level rather than fund theft.
