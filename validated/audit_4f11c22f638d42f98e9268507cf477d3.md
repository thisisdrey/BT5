### Title
Stale non-accrued `convert-to-shares`/`convert-to-assets` quotes cause legitimate `deposit`/`redeem` calls to revert via slippage check - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Each Zest vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) exposes a public, non-accruing conversion view (`convert-to-assets`/`convert-to-shares`, exposed cross-contract e.g. via `protocol-data.clar`'s `get-all-vault-ratios` and `get-vault-underlying-balance`) that any principal or composing contract can call to estimate the shares/assets they will receive from `deposit`/`redeem`. However, the actual `deposit` and `redeem` entry points first run `accrue`, which advances the interest index and mints new treasury-LP shares, changing the total-supply/total-assets ratio used for the real conversion (`convert-to-shares-preview`/`convert-to-assets-preview`). A caller that reads the quote before submitting the transaction and uses it to populate the `min-out` slippage parameter will have their transaction revert with `ERR-SLIPPAGE`, mirroring the “Vault.maxWithdraw returns asset amount too big for Vault.withdraw” bug class: a quoting/max function omits a state change (fee/accrual) applied inside the real operation.

### Finding Description
`deposit` and `redeem` both call `(accrue)` before computing the executed conversion: [1](#0-0) 

`accrue` advances `index`/`lindex` and can mint treasury-LP shares to `.dao-treasury`, which dilutes `total-supply` and changes `total-assets` relative to the pre-accrual state: [2](#0-1) 

The actual amount of shares minted on deposit is computed with `convert-to-shares-preview`, which uses `total-assets-preview` — a value that already incorporates pending interest accrued since the last update via `debt-preview`/`next-index`: [3](#0-2) 

This preview total-assets value is strictly `>=` the “current” (non-preview) total-assets that a caller would observe by querying the vault's own state or via `protocol-data.clar`'s cross-vault helpers (`get-vault-underlying-balance`, `get-all-vault-ratios`) prior to submitting a transaction: [4](#0-3) [5](#0-4) 

Because `convert-to-shares-preview = amount * total-supply / total-assets-preview`, and `total-assets-preview` grows with every block due to compounding interest (`debt-preview` uses `next-index`, which is always `>=` the currently stored `index`), any pre-flight quote taken before submitting `deposit` understates the future denominator and thus overstates the shares a caller expects to receive. If that stale quote is used to populate the `min-out` slippage-protection parameter, the on-chain check reverts: [6](#0-5) 

This is directly analogous to the reported issue: an ERC4626-style “what will I receive” view function does not account for a state change (fee accrual in Popcorn; interest/treasury-LP dilution here) that is unconditionally applied inside the corresponding mutating call, so composing/automated callers relying on the view for slippage-bound parameters see their otherwise-valid transactions revert.

### Impact Explanation
Any ordinary depositor or redeemer — or, more significantly, any automated/composing contract that reads a vault's conversion rate to construct a `min-out` bound before calling `deposit`/`redeem` — is exposed to spurious, protocol-induced reverts purely because interest accrues (and treasury-LP is minted) between the time of the quote and the time of execution, which happens on essentially every block. This causes temporary freezing of user funds/transactions: legitimate deposit/redeem operations fail with `ERR-SLIPPAGE` even though the user supplied fair market parameters, until they retry with a looser or re-fetched bound. This matches the in-scope "temporary freezing of funds" impact category, since a user's assets are locked in their own wallet (deposit blocked) or stuck as vault shares (redeem blocked) pending a successful retry, and third-party integrators building automated flows on top of the vault's own quoting functions face repeated failures.

### Likelihood Explanation
The mismatch is essentially guaranteed to occur, not merely theoretically possible: any nonzero time delta since the last `accrue()` call causes `debt-preview`/`next-index` to differ from the stored `index`, growing `total-assets-preview` relative to what an off-chain or on-chain query observed moments earlier. Since interest accrual is time-based (`stacks-block-time`) and every `deposit`/`redeem`/`accrue`-triggering call updates state, virtually every transaction that uses a pre-fetched quote for slippage protection will experience this drift, especially in low-liquidity or infrequently-touched vaults where more time (hence more interest) has elapsed between the quote and the transaction.

### Recommendation
Provide (and have callers use) a “preview” conversion function that mirrors the exact state the real `deposit`/`redeem` will execute against — i.e., expose `convert-to-shares-preview`/`convert-to-assets-preview` (or an equivalent that first simulates `accrue`) as the public quoting interface instead of, or in addition to, the non-accruing `convert-to-shares`/`convert-to-assets`, so that any principal or contract computing `min-out` bounds off-chain gets a value consistent with what the mutating call will actually produce. Alternatively, document and enforce that consumers always add a buffer/tolerance to quotes proportional to the maximum possible interest accrual since the last update, rather than using exact-equality or tight slippage bounds derived from the raw (stale) conversion view.

### Proof of Concept
1. At time T0, a caller (user or integrator contract) queries `.v0-vault-sbtc convert-to-assets`/`convert-to-shares` (or `protocol-data.clar`'s `get-vault-underlying-balance`/`get-all-vault-ratios`) to determine the expected shares for a planned deposit of `amount`.
2. The caller submits `deposit(amount, min-out, recipient)` with `min-out` set to the value observed in step 1.
3. Time has passed (even one block, due to `stacks-block-time`-based accrual), so `accrue()` inside `deposit` advances `index`/`lindex` and may mint treasury-LP shares, increasing `total-assets-preview` used by `convert-to-shares-preview`.
4. `inkind = convert-to-shares-preview(amount)` is now strictly less than the value quoted in step 1.
5. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` in the `deposit` function fails, reverting the transaction: [7](#0-6) .

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
