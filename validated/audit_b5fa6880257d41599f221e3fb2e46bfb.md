### Title
Duplicate/malleable-signature double-counting bypasses multisig threshold in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract accumulates permission-key voting weight from a list of caller-supplied ECDSA signatures without ensuring each signature is a distinct, non-malleable proof from a distinct signer. Because deduplication is done by exact byte-comparison of the *signature bytes* (merged with the recovered address) rather than by the recovered *signer address* alone, an attacker can submit two or more distinct-but-valid signatures that all recover to the same key and have that single key's weight counted multiple times, exactly mirroring the SEDA `Secp256k1ProverV1.postBatch` root cause (accumulating voting power without uniqueness tracking per signer).

### Finding Description
`ValidateMultiSign.execute` loops over up to `MAX_SIZE` (5) attacker-supplied signatures, recovers a signer address for each, and sums `TransactionCapsule.getWeight(permission, recoveredAddr)` into `totalWeight`: [1](#0-0) 

The de-duplication logic only skips counting when the recovered address AND the exact signature bytes were already seen: [2](#0-1) 

and the check itself is implemented as an exact-byte-match search: [3](#0-2) 

Because secp256k1 ECDSA is malleable (for any valid signature `(r, s, v)` over a hash, `(r, n-s mod n, 1-v)` is also a valid signature recovering to the same address), or because a signer can simply re-sign the same hash with a different nonce to obtain a different valid `(r, s)` pair, an attacker who possesses (or can derive from) a single valid signature by a permission key can trivially construct a second, byte-distinct signature that recovers to the *same* address. When this second signature is submitted, `matrixContains(executedSignList, recoveredAddr)` is `true` but `matrixContains(executedSignList, sign)` is `false` (because the signature bytes differ), so the `continue` is skipped, `MUtil.checkCPUTime()` runs (a resource-metering guard only), and the same key's weight is added to `totalWeight` a second time. This can be repeated up to `MAX_SIZE` times.

This is the same root cause pattern as the SEDA report: voting/weight is accumulated per submitted proof/signature instead of per unique validator/signer identity, with no set-of-signers uniqueness enforcement.

Contrast this with the correct pattern already used elsewhere in the codebase — `TransactionCapsule.checkWeight`, used for on-chain transaction multi-sig verification, explicitly tracks signer identity (not signature bytes) via a map keyed by recovered address and rejects "has signed twice": [4](#0-3) 

The `ValidateMultiSign` precompile does not follow this same-address-uniqueness rule; it only rejects exact signature-byte duplicates.

### Impact Explanation
`ValidateMultiSign` is a TVM precompiled contract callable by any smart contract (and therefore reachable by any unprivileged transaction that triggers a contract call), used by dApps to verify that a TRON account's multisig permission threshold has been met before authorizing an on-chain action (e.g., releasing funds, approving withdrawals, custody/multisig wallet logic built on top of TRON's native permission system). By exploiting the malleable/duplicate-signature weight double-counting, an attacker controlling (or having obtained) just one signature from a single key with partial weight can synthesize additional valid signatures for that same key and satisfy a permission threshold that was supposed to require multiple independent co-signers. This directly undermines the security guarantee of on-chain multisig verification and can lead to unauthorized approval of privileged actions performed by any contract that relies on `ValidateMultiSign` to gate fund transfers or other privileged operations — a concrete path to theft/unauthorized account operations analogous to the SEDA consensus-threshold bypass.

### Likelihood Explanation
The precompile is reachable by any account via a plain smart-contract call (`STATICCALL`/`CALL` to the precompile address), requiring no special privilege, validator status, or node compromise — matching the "unprivileged transaction broadcaster/contract caller" reachable-path criteria. Generating a malleable counterpart signature `(r, n-s, 1-v)` from an existing valid `(r, s, v)` is a well-known, computationally trivial operation requiring no access to the private key, and simply re-signing with a different nonce is available to any cooperating/compromised signer. The only friction is the energy cost per signature (`ENGERYPERSIGN` = 1500 each) and the `MAX_SIZE` cap of 5 signatures, which bounds but does not prevent the multiplier (up to 5x weight for a single key).

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute` (and the analogous `BatchValidateSign` logic if it has similar semantics) from the merged `(recoveredAddr, signature)` bytes to the recovered address alone, matching the pattern already used in `TransactionCapsule.checkWeight`: maintain a set of already-counted signer addresses, and skip (or reject) any subsequent signature that recovers to an address already present in that set, regardless of whether the signature bytes differ.

### Proof of Concept
1. Create an account with an `Active` permission containing key `A` with weight `w` and threshold `T > w` (so `A` alone cannot satisfy the threshold), following the setup in `ValidateMultiSignContractTest.testDifferentCase`: [5](#0-4) 
2. Compute `hash = sha256(address || permissionId || data)` as done by the precompile: [6](#0-5) 
3. Sign `hash` with key `A`'s private key to get signature `sig1 = (r, s, v)`.
4. Derive a malleable counterpart `sig2 = (r, n - s mod n, 1 - v)` — a valid signature recovering to the same address `A`, but byte-distinct from `sig1`.
5. Call the `validatemultisign(address,uint256,bytes32,bytes[])` precompile with `signatures = [sig1, sig2]`.
6. In `ValidateMultiSign.execute`, the loop counts weight for `sig1` (adds `w`), then for `sig2` the `recoveredAddr` matches (`matrixContains(executedSignList, recoveredAddr)` is true) but `sign` bytes differ so `matrixContains(executedSignList, sign)` is false — the `continue` is skipped and weight `w` is added again, yielding `totalWeight = 2w`, which can now exceed threshold `T` despite only one real key having signed. See the vulnerable accumulation loop: [7](#0-6)
