### Title
Legacy `ExchangeProcessor` uses double-precision floating point instead of arbitrary-precision arithmetic for Bancor-formula swap calculations, causing precision loss and incorrect settlement of TRC10/TRX exchange trades - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The default (non-hardened) code path used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` to settle TRC10↔TRX bonding-curve swaps relies on `ExchangeProcessor`, which performs the Bancor relay-token math with native `double` arithmetic instead of arbitrary/high-precision arithmetic. This mirrors the reported StableSwap issue: intermediate calculation precision is insufficient for the range of legitimate on-chain values, producing inaccurate or unreliable swap outputs.

### Finding Description
`ExchangeCapsule.transaction()` selects `ExchangeProcessor` as the swap engine unless the optional `allowHardenExchangeCalculation` dynamic parameter is enabled, in which case `SafeExchangeProcessor` (BigDecimal-based) is used instead: [1](#0-0) 

The default `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the constant-relay-supply Bancor curve entirely with `double`: [2](#0-1) 

`double` has only ~15-17 significant decimal digits of precision, while TRX/TRC10 balances are `long` values that can range up to `Long.MAX_VALUE` (~9.2×10^18, 19 digits) and exchange pools are explicitly allowed to grow up to a governance-configured `exchangeBalanceLimit`: [3](#0-2) 

This is the exact bug class described in the report: using a numerically insufficient intermediate type (`double`, analogous to `Uint256`) for a bonding-curve/AMM-style calculation that must support realistic large-magnitude token amounts. Just as the StableSwap `Uint256` intermediate overflowed for 1M-token pools with 18 decimals, `double`'s limited mantissa silently loses precision for large TRX/TRC10 balances near the top of the `long` range, and the loss compounds because `exchangeToSupply` and `exchangeFromSupply` are chained (the output of one feeds directly into the other), amplifying rounding error before the final result is truncated back to `long` via `(long) issuedSupply` / `(long) exchangeBalance`.

Unlike the StableSwap case (which reverted with an explicit overflow error), here the double-precision computation does not throw — it silently returns a numerically wrong result, which is then compared against the user's `tokenExpected` slippage check in `ExchangeTransactionActuator.doValidate()`: [4](#0-3)  and directly credited to accounts via `addAssetAmountV2`/`setBalance` in `execute()`: [5](#0-4) 

The repository's own test suite acknowledges the resulting drift between the legacy `double` path and the arbitrary-precision hardened path is only accepted within "±1" tolerance for modest values, and that hardened tests are needed to validate large-balance behavior — implying the legacy path's accuracy is not proven for large-value swaps: [6](#0-5) 

### Impact Explanation
Any unprivileged account can create an exchange pool via `ExchangeCreateActuator` and drive it (via `ExchangeInjectActuator`) toward the `exchangeBalanceLimit`, then repeatedly call `ExchangeTransactionActuator` to trade. Because `double` truncates/rounds differently than the exact rational value the Bancor curve should produce, an attacker can craft trade sequences at scale (large pool balances, tokens with maximum decimal-equivalent magnitude) that:
- extract more of the counter-asset than the true invariant should allow (small favorable rounding repeated across many trades, i.e., value leakage from the pool at the expense of other liquidity/withdrawers), or
- cause legitimate trades by other users to fail or settle at an incorrect, unexpected amount, since `anotherTokenQuant` silently diverges from the mathematically correct value.

Either outcome constitutes an unbacked/incorrect balance change credited to real accounts through a standard, permissionless transaction type (`ExchangeTransactionContract`), which is a fund-integrity issue at Medium-to-High severity, matching the reported bug class's "insufficient intermediate precision breaking reliability of swap settlement."

### Likelihood Explanation
Reachable by any account with TRX to pay the network fee — no special permission, contract deployment, or SR/witness status required. Only ordinary `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract` transactions are needed, all of which are exposed at the actuator level to any signed transaction. The optional hardened path is opt-in via a still-off-by-default dynamic parameter (`allowHardenExchangeCalculation`), so the vulnerable `double`-based `ExchangeProcessor` remains the effective default engine for exchange pools.

### Recommendation
Make `SafeExchangeProcessor` (or an equivalent BigInteger/BigDecimal high-precision implementation) the default and only swap engine for `ExchangeCapsule.transaction()`, removing the `double`-based `ExchangeProcessor` from the settlement path entirely, and add a dedicated regression test suite exercising exchange pools at/near `exchangeBalanceLimit` and edge-case decimal ratios to verify the pool consistently produces results within the intended invariant (no value leakage, no unexpected failures) — mirroring the recommended mitigation of upgrading intermediate precision (`Uint256`→`Uint512`) in the original report, applied here as `double`→arbitrary-precision arithmetic used unconditionally.

### Proof of Concept
Not independently executable here (no test harness access in ask-only mode), but the divergence is directly demonstrable using the existing repository test harness pattern: instantiate `ExchangeCapsule` with balances approaching `dynamicPropertiesStore.getExchangeBalanceLimit()` (e.g., balances in the range of 10^17–10^18 sun, comparable in magnitude to the 18-decimal token amounts in the original PoC), call `capsule.transaction(sellTokenId, sellQuant, useStrictMath=true, hardenedCalc=false)` via the legacy `ExchangeProcessor`, and compare the result against `capsule.transaction(..., hardenedCalc=true)` (`SafeExchangeProcessor`). The existing test `testTransactionLegacyVsHardenedProcessorSelection` only asserts a "±1" tolerance at modest balances (100,000,000L) [7](#0-6) ; repeating this comparison at balances near `Long.MAX_VALUE`/`exchangeBalanceLimit` is expected to show a growing, non-trivial divergence between the two engines, confirming the `double` path's precision breaks down exactly as `Uint256` did in the original StableSwap report.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Test
  public void testTransactionLegacyVsHardenedProcessorSelection() throws Exception {
    // Same input produces deterministic results in both modes.
    ExchangeCapsule legacy = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 100L, 0L,
        "abc".getBytes(), "def".getBytes());
    legacy.setBalance(100_000_000L, 100_000_000L);
    long legacyResult = legacy.transaction("abc".getBytes(), 1_000_000L, true, false);

    ExchangeCapsule hardened = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 101L, 0L,
        "abc".getBytes(), "def".getBytes());
    hardened.setBalance(100_000_000L, 100_000_000L);
    long hardenedResult = hardened.transaction("abc".getBytes(), 1_000_000L, true, true);

    Assert.assertTrue("Both must return positive", legacyResult > 0 && hardenedResult > 0);
    Assert.assertTrue("Hardened must not exceed pool",
        hardenedResult <= 100_000_000L);
    // Allow ±1 difference due to BigDecimal vs double precision
    Assert.assertTrue("Results should be within 1 unit",
        StrictMathWrapper.abs(legacyResult - hardenedResult) <= 1);
  }
