### Title
Integer overflow in ZIP central-directory bounds check leads to out-of-bounds pointer arithmetic - ([File: third_party/ijar/zip.cc])

### Summary
`FindZipCentralDirectory` in `third_party/ijar/zip.cc` validates the central-directory location of a (interface-)jar by computing `cd.central_dir_offset + cd.central_dir_size` and comparing it to the mapped file length. Both fields are read as 32-bit `u4` values [1](#0-0) , and the addition is performed at 32-bit width before the (size_t) comparison, mirroring the classic "integer overflow" bug class in the referenced CVE.

### Finding Description
`FindZipCentralDirectory` reads `central_dir_offset` and `central_dir_size` directly from the untrusted end-of-central-directory record via `get_u4le`, both typed as `u4` (`uint32_t`) [2](#0-1) . It then checks:
```
if (cd.central_dir_offset + cd.central_dir_size > in_length) { ... reject ... }
``` [3](#0-2) 
Because both operands are `uint32_t`, the addition is performed with 32-bit wraparound semantics before the result is (implicitly) widened for comparison against `in_length` (a `size_t`). An attacker who controls the ZIP/jar bytes can choose `central_dir_offset` and `central_dir_size` such that their true sum exceeds the file length but their 32-bit-wrapped sum does not (e.g. `offset = 0xFFFFFFF0`, `size = 0x20` wraps to `0x10`), causing the bounds check to pass incorrectly.

Once the check is bypassed, the code computes:
```
*central_dir = end_of_central_dir - cd.central_dir_size;
``` [4](#0-3) 
With an attacker-chosen huge `central_dir_size`, this pointer arithmetic drives `central_dir` far outside the bounds of the memory-mapped input file. Subsequent parsing (`ProcessCentralDirEntry`, `CalculateOutputLength`, or the actual jar-stripping pass) dereferences this out-of-bounds pointer [5](#0-4) , reading (and potentially further miscomputing sizes/offsets from) memory outside the mapped region.

The `u4`/`u8` mismatch that this class of headers otherwise handles carefully (e.g. `ziph::zfield_has_ext64` promoting 32-bit fields to 64-bit ZIP64 extensions) is not applied here for the EOCD offset/size sum — this one validation path stays at 32-bit width.

### Impact Explanation
ijar (`zip.cc`) is bazel's in-tree implementation used to read/parse jar archives, including archives fetched from external, attacker-served locations (e.g., prebuilt/third-party jars pulled in as dependencies) as part of interface-jar generation. A crafted jar whose EOCD fields are set to cause the 32-bit wraparound will not be rejected by the sanity check, and the resulting out-of-bounds pointer is dereferenced during central-directory parsing. This is a memory-safety violation (out-of-bounds read, potentially crashing the build or leaking adjacent process memory) triggered purely by attacker-controlled file bytes that a victim's build consumes — the checksum pinning a dependency's hash does not protect against this because the hash simply confirms the attacker's malicious bytes are the ones being processed, not that the bytes are well-formed.

### Likelihood Explanation
Moderate-to-high: any attacker who can get a victim to reference their crafted jar (a common supply-chain vector for prebuilt/third-party jar dependencies) can trigger this by constructing valid-looking EOCD/ZIP64 fields whose 32-bit sum wraps. No special privileges, credentials, or MITM are required — the malicious jar is served as-is and matches whatever checksum the victim pinned for it.

### Recommendation
Perform the bounds check using 64-bit (`u8`) arithmetic before comparing to `in_length`, e.g.:
```
if ((u8)cd.central_dir_offset + (u8)cd.central_dir_size > in_length) { ... }
```
and validate `cd.central_dir_size <= (size_t)(end_of_central_dir - bytes)` before computing `*central_dir = end_of_central_dir - cd.central_dir_size`, rejecting any value that would place the pointer before `bytes` or the offset/size sum beyond `in_length`, consistent with the ZIP64 handling elsewhere in the file (`ziph::zfield_has_ext64`/`zfield_needs_ext64`) [6](#0-5) .

### Proof of Concept
A JUnit/shell test analogous to the existing ijar zip tests (`src/tools/singlejar/zip_headers_test.cc`, `third_party/ijar` test harness) can construct a minimal ZIP file whose End-Of-Central-Directory record sets:
- `central_dir_offset = 0xFFFFFFF0`
- `central_dir_size = 0x20`

so that `central_dir_offset + central_dir_size` wraps to `0x10` (well under `in_length`), passing the check in `FindZipCentralDirectory` [3](#0-2) . Running `ijar` (or any bazel path that reads this jar, e.g. interface-jar generation) on this file then computes `central_dir = end_of_central_dir - 0x20`, an address far outside the mapped file, and dereferencing it in `ProcessCentralDirEntry` demonstrates the out-of-bounds read/crash.
