This is a real design gap: `TrieKey::PostponedReceipt` entries are keyed only by `(receiver_id, receipt_id)` and are never invalidated or cleaned up when the receiver account is deleted.

### Title
Stale postponed receipt's `DeleteKeyAction` can survive `DeleteAccount` and later strip the access key of a recreated/implicit account at the same account_id - ([File: runtime/runtime/src/lib.rs])

### Summary
A postponed `ActionReceipt` (one whose `input_data_ids` are not yet all received) is persisted under `TrieKey::PostponedReceipt{receiver_id, receipt_id}` independently of the receiver account's lifecycle. If that receiver account is deleted via `DeleteAccountAction` while the postponed receipt is still pending, and the account_id is later recreated (trivially the case for a NEAR-implicit account, whose access key is deterministically derived from the account_id), the stale receipt will still fire once its awaited data arrives and execute its `DeleteKeyAction` against the freshly (re)created account, deleting the newly added key.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an incoming action receipt as a postponed receipt keyed only by `receiver_id`/`receipt_id` when any `input_data_id` is missing (`set_postponed_receipt`, `core/store/src/utils/mod.rs:120-127`), together with a `PendingDataCount` and `PostponedReceiptId` index. None of these trie entries reference the account's current "generation"/existence at storage time.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and clears the account record, storage, keys, etc., but does not touch `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries scoped to that `receiver_id`. There is no code path that scans for or cancels postponed receipts belonging to a deleted account.

When the missing data finally arrives (`process_receipt`, `runtime/runtime/src/lib.rs:1367` handling `VersionedReceiptEnum::Data`), the runtime decrements `PendingDataCount`; once it hits zero it fetches the postponed receipt via `get_postponed_receipt`, removes it from state, and calls `apply_action_receipt` (`runtime/runtime/src/lib.rs:1430-1454`). Crucially, `apply_action_receipt` re-fetches the account fresh at execution time: `let mut account = get_account(state_update, account_id)?;` (`runtime/runtime/src/lib.rs:853`) — it is not tied to the account state that existed when the receipt was postponed.

For the `DeleteKeyAction` within that receipt, `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-760`) only checks `actor_id == account_id` (both AccountIds, not tied to any specific key generation) — trivially satisfied because the original receipt's predecessor was the account itself. `check_account_existence` (`runtime/runtime/src/actions.rs:787-855`) only requires the account to currently exist. `action_delete_key` (`runtime/runtime/src/access_keys.rs:52-91`) simply looks up `get_access_key(state_update, account_id, &delete_key.public_key)` and removes it if present — with no check that this is the "same" account instance that existed when the receipt was created.

For a NEAR-implicit account, `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:212-244`) always derives the same FullAccess key from `PublicKey::from_near_implicit_account(account_id)` — i.e., the recreated account's key is fully deterministic and known in advance to anyone (including the original attacker who owned/deleted the account).

Exploit flow:
1. Attacker controls NEAR-implicit account `A` (account_id = hex of its own ed25519 pubkey).
2. Attacker sends itself (as `receiver_id = A`) an `ActionReceipt` containing `DeleteKeyAction{public_key: <A's implicit pubkey>}` with a non-empty `input_data_ids` (e.g. via a cross-contract promise `.then()` callback) so it becomes a `PostponedReceipt` under key `(A, receipt_id)`.
3. Before that data resolves, attacker submits `DeleteAccountAction` on `A` (permitted, `actor_id == account_id`), refunding balance to a beneficiary and calling `remove_account` — the postponed receipt entry is left untouched in the trie.
4. `A` is later recreated — trivially, since anyone (attacker or an unwitting third party) sending a `Transfer` to implicit account_id `A` recreates it with the same deterministic FullAccess key (`action_implicit_account_creation_transfer`).
5. When the originally-awaited data receipt finally arrives (a normal, inevitable event — the async callback the attacker set up simply completes), the stale postponed `DeleteKeyAction` executes against the newly created account and deletes its only access key.

### Impact Explanation
This causes permanent freezing of funds: the recreated account's sole access key is silently removed by a receipt the current owner has no knowledge of and cannot see or cancel, with no way to regain access. This matches the "permanent freezing of user funds" bounty category. It is worth noting the practical exploitation is easiest against the attacker's own former implicit account_id (self-inflicted, low direct value) or as a "poisoned address" trap where the attacker publishes/sells the (believed-fresh) implicit account_id or relies on a third party independently generating and funding the same address before the stale trap resolves — the latter requires the third party to pick exactly that key, which is not attacker-controlled and thus low probability in practice, but the underlying mechanism (stale postponed receipts surviving account deletion/recreation) is a genuine protocol invariant violation regardless of who benefits.

### Likelihood Explanation
Low-to-moderate likelihood in practice: the mechanism is fully reachable by an unprivileged user (self-receipts, promises, `DeleteAccountAction` are ordinary transaction actions), and costs only the gas/fees of a few actions plus the deposit needed to survive until callback resolution. However, meaningfully weaponizing it against a *victim* (rather than one's own account) requires the victim to reuse a specific attacker-chosen account_id/key before the stale receipt resolves, which is only trivially satisfiable for NEAR-implicit accounts (deterministic key) and requires either social engineering to get a victim to reuse that exact implicit address, or the attacker being the one who "loses" access to their own account (self-DoS, not useful as an attack on others). The core defect — postponed receipts outliving `DeleteAccount` — is reproducible deterministically every time.

### Recommendation
Invalidate/clean up postponed receipts (and associated `PendingDataCount`/`PostponedReceiptId` entries) for an account when it is deleted via `action_delete_account`, or alternatively bind `DeleteKeyAction`/action execution in `apply_action_receipt` to an account-lifecycle-scoped identifier (e.g. reject/no-op stale actions if the account did not exist continuously since the receipt was postponed). At minimum, `check_account_existence`/`apply_action_receipt` should detect that the account was deleted and recreated since the receipt was postponed and fail such actions rather than silently applying them to the new account instance.

### Proof of Concept
Integration/test-loop test plan:
1. Create a NEAR-implicit account `A` via `Transfer` (deterministic FullAccess key `pk_A` derived from `account_id`).
2. From `A`, deploy a helper contract or use a cross-contract call chain so that `A` sends itself an `ActionReceipt` with action `DeleteKey{public_key: pk_A}` and a non-empty `input_data_ids` (e.g., call another contract with `.then(self.some_callback)`), causing it to be stored as `PostponedReceipt`. Do not yet deliver the dependent data receipt.
3. Submit `DeleteAccountAction` from `A` (beneficiary = some other account); assert account `A` no longer exists (`get_account` returns `None`) but `get_postponed_receipt(state_update, &A, receipt_id)` still returns `Some(..)`.
4. Recreate `A` via a fresh `Transfer` to the implicit account_id `A` (or `AddKey(pk_A, FullAccess)` after `CreateAccount`, if applicable) — assert `get_access_key(state_update, &A, &pk_A)` is `Some`.
5. Deliver the pending data receipt that completes the callback dependency; run `Runtime::apply`/`process_receipt`.
6. Assert: (a) the postponed receipt was executed (`get_postponed_receipt` now returns `None`), and (b) `get_access_key(state_update, &A, &pk_A)` returns `None` — the key added in step 4 has been silently removed, demonstrating permanent lockout of the recreated account.
