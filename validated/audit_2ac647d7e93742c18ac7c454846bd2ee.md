### Title
Unchecked `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` allows permanent loss of margin account control - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`TransferToNewAccount` and `TransferToNewAccountPda` perform an irrevocable, single-step transfer of a marginfi account's authority to `new_authority`, which is explicitly documented as unchecked and is never validated against `Pubkey::default()` (the zero address) or against the current `authority`. This mirrors the reported bug class: a critical, non-recoverable ownership-changing operation done in one step with no validation, allowing a user to accidentally (or via a malicious front-end/typo) set the new authority to an unusable/zero address and permanently lose control of the account and its funds.

### Finding Description
The instruction handler moves `old_account`'s lending position into a brand-new `MarginfiAccount` owned by `new_authority`, then permanently disables the old account: [1](#0-0) 

`new_authority` is declared as a completely unchecked account with no on-chain validation of its value: [2](#0-1) 

`initialize_migrated_account` simply assigns whatever `new_authority.key()` is passed into the new account's `authority` field, without checking it is non-zero or different from the old authority: [3](#0-2) 

Once this executes, the old account is irreversibly disabled (`ACCOUNT_DISABLED` flag set, `lending_account` zeroed, `migrated_to` set) and can never be un-migrated: [4](#0-3) 

The identical unchecked pattern exists in the PDA variant of the instruction: [5](#0-4) 

Notably, the off-chain CLI tooling recognizes this exact risk and defends against it client-side, but this validation is absent from the on-chain program itself: [6](#0-5) 

This confirms the on-chain instruction is the enforcement gap — any caller bypassing the CLI (a custom client, a bug in a different front-end, or a user directly building the transaction) can submit `new_authority = Pubkey::default()` and the program will accept it.

### Impact Explanation
If `new_authority` is `Pubkey::default()` (or any address the user does not control, e.g., a typo/wrong keypair), the new `MarginfiAccount` is created with that authority, and the old account is atomically and permanently disabled in the same instruction — there is no two-step "propose/accept" flow and no possibility of reversal. Since `is_signer_authorized` gates only who may *initiate* the transfer (the current authority/delegate) and not the value being transferred to, and the account holds real deposited/borrowed collateral (`lending_account`), this results in a **permanent freeze/lock of the user's funds** inside a marginfi account nobody can ever again produce a valid signer for. This is a fund-loss impact directly analogous to the reported `VotingEscrow.transfer_ownership` issue, but reachable by an ordinary unprivileged user through a core account-management path rather than an admin-only function.

### Likelihood Explanation
Likelihood is moderate: the instruction is user-callable and unprivileged (protected only by group-pause and normal signer/frozen checks), so any account holder invoking it directly (bypassing or misusing a UI/CLI, or via a buggy/malicious frontend, or simple copy-paste error) can trigger the zero-address/self-mistake scenario described in the report. The official CLI already treats this as dangerous enough to hard-fail on `Pubkey::default()`, which supports that this is a realistic, foreseen failure mode rather than a purely theoretical one.

### Recommendation
Add on-chain validation in `transfer_to_new_account` and `transfer_to_new_account_pda`: reject `new_authority == Pubkey::default()` and consider requiring `new_authority != old authority` and/or a signed acknowledgment from `new_authority` (or a claim/accept step) before finalizing the migration, following a two-step "propose new authority, then have new authority accept" pattern rather than an atomic single-instruction irrevocable transfer.

### Proof of Concept
1. Create a marginfi account with `authority = A`, deposit collateral.
2. Directly construct and submit a `TransferToNewAccount` (or `TransferToNewAccountPda`) transaction with `new_authority = Pubkey::default()` (bypassing the CLI's `bail!` guard shown in `p0-cli/src/processor/account.rs`), signed by `A`.
3. The instruction succeeds: `initialize_migrated_account` sets the new account's `authority` to `Pubkey::default()`, and `finalize_migrated_old_account` sets `ACCOUNT_DISABLED` and zeroes `old_account.lending_account`, permanently retiring the old account.
4. No signer can ever satisfy `authority == Pubkey::default()`/`is_signer_authorized` for the new account, so the migrated collateral/position becomes permanently inaccessible.

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,

    old_account.migrated_to = new_account_key;
