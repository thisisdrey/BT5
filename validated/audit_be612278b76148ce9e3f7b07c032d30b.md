Confirmed: no code path in `outbound-queue-v2` reads or branches on `receipt.success` anywhere in the pallet.

Audit Report

## Title
Relayer reward is registered on `process_delivery_receipt` without checking `DeliveryReceipt.success` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::<T>::process_delivery_receipt` pays the full relayer reward (`order.fee`) for a pending order whenever a validly-verified `DeliveryReceipt` references an existing `PendingOrders` entry with the correct `GatewayAddress`, but it never reads or branches on `receipt.success` before calling `T::RewardPayment::register_reward`. [1](#0-0)  The `DeliveryReceipt` type explicitly carries a `success: bool` field decoded from the Ethereum `InboundMessageDispatched` event log, so the information is available but simply unused. [2](#0-1) 

## Finding Description
`submit_delivery_receipt` verifies the Merkle/event proof via `T::Verifier::verify`, decodes the log into a `DeliveryReceipt` (which includes `success`), and forwards it to `process_delivery_receipt` unchanged. [3](#0-2)  Inside `process_delivery_receipt`, the only checks performed are: (1) `receipt.gateway` matches `T::GatewayAddress::get()`, and (2) a `PendingOrder` exists for `receipt.nonce`. [4](#0-3)  If those pass, the full `order.fee` is unconditionally registered via `T::RewardPayment::register_reward`, the pending order is removed, and `MessageDelivered` is emitted — none of this depends on `receipt.success`. [5](#0-4)  A grep across the entire `outbound-queue-v2` pallet confirms `receipt.success` (or any `.success` reference) is never consulted anywhere in the pallet's logic. This means a genuinely failed/reverted delivery on Ethereum (event log with `success: false`) results in exactly the same reward payout and same `MessageDelivered` event as a successful delivery, decoupling the reward side effect from the outcome the `success` field is meant to represent.

## Impact Explanation
This matches the "duplicate settlement or payout" / "public underpriced work" impact category: relayer rewards are settled from the bridge's relayer reward pot without being conditioned on the actual delivery/execution outcome that the receipt is supposed to encode. Since `order.fee` is fully paid regardless of `success`, a failed delivery is rewarded identically to a successful one, meaning the bridge can pay out for outcomes it should not be paying (or should be paying at a different rate) for, given that the codebase deliberately models and decodes a `success` flag but discards it functionally. [6](#0-5) 

## Likelihood Explanation
This is reachable by any unprivileged, signed relayer submitting a proof through the public `submit_delivery_receipt` extrinsic. [3](#0-2)  The relayer does not need to forge or fabricate the `success` value — it need only relay a real, verifier-validated event log for a message whose on-chain Ethereum execution reverted (`success: false`), which is a normal, expected occurrence (e.g., due to insufficient gas provided by the command, a reentrancy guard, or an application-level revert on the Gateway contract), not an attacker-controlled forgery. No admin, governance, or compromised-relayer/prover assumption is required — this is the intended, permissionless proof-submission path, and the only gating in code (`InvalidGateway`, `InvalidPendingNonce`) is satisfied by any correctly-proven receipt regardless of `success`.

## Recommendation
Branch on `receipt.success` inside `process_delivery_receipt` before calling `T::RewardPayment::register_reward`. If failed deliveries should still compensate relayers for proof-submission costs, implement that as an explicit, smaller, clearly-labeled reward path (and/or a distinct event) rather than paying the full `order.fee` indistinguishably from a successful delivery.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders::<T>::get(nonce) == PendingOrder { nonce, fee, .. }`. [7](#0-6) 
2. The message is relayed to Ethereum's Gateway contract, but its execution reverts, producing an `InboundMessageDispatched` event log with `success: false`.
3. A relayer submits this real event log with a valid Merkle/verifier proof via `submit_delivery_receipt`. `T::Verifier::verify` succeeds (the log is real), and `DeliveryReceipt::try_from` decodes `success: false` correctly. [8](#0-7) [9](#0-8) 
4. `process_delivery_receipt` checks only `gateway` match and `PendingOrders` existence — both pass — and never inspects `success`. [4](#0-3) 
5. `T::RewardPayment::register_reward` is called with the full `order.fee`, `PendingOrders::<T>::remove(nonce)` fires, and `Event::MessageDelivered { nonce }` is emitted — identical to the successful-delivery case demonstrated in the existing emulated test that constructs a receipt and asserts `RewardRegistered` fires, irrespective of the `success` field's value. [5](#0-4)

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
