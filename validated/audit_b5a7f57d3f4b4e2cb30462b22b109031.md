Audit Report

## Title
Delivery-receipt `success` flag is decoded but never checked, so relayer rewards are paid even for failed Ethereum-side message execution - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs` decodes the `success: bool` field from the `InboundMessageDispatched` Ethereum event log, but `Pallet::process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` never reads this field before paying out the relayer reward and removing the `PendingOrder`. As a result, the reward is paid identically whether the corresponding message execution succeeded or failed on the Ethereum Gateway contract.

## Finding Description
The `DeliveryReceipt` struct decodes `success` directly from the ABI-encoded log at [1](#0-0) . The public extrinsic `submit_delivery_receipt` verifies the proof, decodes the receipt, and forwards it to `process_delivery_receipt` at [2](#0-1) .

`process_delivery_receipt` checks only `receipt.gateway` and `order.fee`, then unconditionally calls `T::RewardPayment::register_reward` and removes the `PendingOrder`, never inspecting `receipt.success`: [3](#0-2) . A repository-wide search confirms `.success` is never referenced anywhere in `bridges/snowbridge/pallets/outbound-queue-v2/**`, so the decoded field is genuinely dead data on the critical payout path.

The `PendingOrder` is originally created with a nonzero `fee` in `do_process_message` at [4](#0-3) , and this fee is paid out regardless of whether the message's commands actually executed successfully on Ethereum.

## Impact Explanation
This breaks the invariant that settlement (reward payout + order removal) must only advance after successful execution. Any signed account can submit a proof of an `InboundMessageDispatched` event with `success = false` (a normal, non-adversarial Ethereum outcome such as a reverted command) and still receive the full relayer reward from the fee pool, while the `PendingOrder` is permanently removed with no retry or penalty. This is an unbacked payout — value leaves the bridge's fee-paying account without the corresponding successful service being rendered — and matches the "theft or unbacked mint/unlock" and "duplicate settlement or payout"/"public underpriced work" category of the impact gate, since rewards are dispensed for work whose completion was never verified.

## Likelihood Explanation
No privileged or compromised-relayer assumption is required. Any signed account holding a valid execution proof for a real `InboundMessageDispatched` log (success or failure) can call `submit_delivery_receipt`. Ethereum transactions can fail for mundane reasons (e.g., insufficient forwarded gas at the Gateway execution step) independent of any malicious behavior, making this a routinely reachable condition rather than a contrived attack.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before calling `T::RewardPayment::register_reward`: on `false`, withhold or reduce the reward, emit a distinct event (e.g. `MessageDeliveryFailed`), and consider retaining the `PendingOrder` for retry rather than unconditionally removing it.

## Proof of Concept
1. `do_process_message` creates a `PendingOrder{nonce, fee>0, ..}` for a queued message (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-436`).
2. On Ethereum, the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` because command execution reverted.
3. Any signed account builds the proof and calls `submit_delivery_receipt(origin, event)`; `T::Verifier::verify` succeeds since the proof is genuinely valid, and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` never inspects `receipt.success`; since `order.fee > 0`, `T::RewardPayment::register_reward` pays out the full reward and `PendingOrders::remove(nonce)` executes, exactly as it would for `success: true`, matching the emulated test assertions in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs:793-811` which never assert on `success`.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
