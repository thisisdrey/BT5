### Title
Unsigned integer underflow in reftable block parsing causes out-of-bounds panic - ([File: internal/git/reftable/reftable.go])

### Summary
`Table.parseRefBlock` in `internal/git/reftable/reftable.go` performs unsigned (`uint`) subtraction on an attacker/corruption-influenced block-length value (`currentBS`) without validating that it is large enough for the subtraction to stay non-negative, mirroring the H-5 pattern of performing subtraction on unsigned values *before* any bounds check, causing wraparound instead of a controlled error.

### Finding Description
`extractBlockLen` reads a 3-byte, fully attacker/file-controlled length field directly out of the reftable block bytes with no minimum-value validation: [1](#0-0) 

`parseRefBlock` then uses this unchecked value (`currentBS`) in unsigned arithmetic: [2](#0-1) 

Both `src[blockStart+currentBS-2:]` and `b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)` are `uint` computations. If `currentBS < 2` (a value fully controlled by the bytes of the parsed table), `blockStart+currentBS-2` wraps to a value near `math.MaxUint`, producing a slice expression that panics with "slice bounds out of range" instead of returning an error. Likewise, if `b.RestartCount` (also read directly from the block, as a `uint16`) is large enough that `3*uint(b.RestartCount)` exceeds `blockStart+currentBS-2`, `RestartStart` also wraps to a huge value, which is then used as a loop bound in `getRefsFromBlock`, causing further out-of-bounds slice panics.

This is the same bug class as the Solidity report: subtraction is performed on unsigned integers *before* any bounds/sign check, so an adversarial or corrupted low value flips into an enormous positive value rather than being rejected. Contrast this with `getVarInt` in the same file, which does perform an explicit `start > blockEnd` bounds check before indexing — `parseRefBlock` lacks the analogous guard for `currentBS`/`RestartCount`.

### Impact Explanation
A malformed or maliciously crafted `.ref` (reftable) file causes `parseRefBlock`/`getRefsFromBlock` to panic on out-of-range slice access when Gitaly parses it via `Table.GetReferences()`. This function is invoked wherever reftables are read: reference listing, transaction manager housekeeping/compaction and resequencing of newly written tables (`internal/gitaly/storage/storagemgr/partition/reftable.go`), and repository backup/restore (`internal/backup/repository.go`). A panic here denies service to the RPC handling that repository (and, absent a top-level recover, can crash the serving goroutine/process), representing a DoS of a handler that processes repository data.

### Likelihood Explanation
Likelihood depends on how easily a client-influenced or corrupted reftable file can reach these parsing paths. Reftable files are normally written by `git` itself and are not directly accepted as raw client input over standard push/fetch RPCs, so exploitation from an *ordinary* user push/fetch is not immediately evident from what I found. However, paths that ingest raw file bytes for an existing repository — such as backup restore (`internal/backup/repository.go`) or replication/transaction resequencing of table files (`internal/gitaly/storage/storagemgr/partition/reftable.go`) — read and reparse `.ref` files without validating internal block-length invariants, so any corruption (disk corruption, incomplete backup, or a maliciously supplied backup archive) can trigger the panic.

I was not able to fully confirm, within the available investigation, an end-to-end path from an *unprivileged* user-supplied push/fetch/import RPC field directly into these bytes without git's own reftable writer sanitizing them first. This should be verified further (e.g., via a Devin session with full repo/tool access) before treating this as a definitively externally-triggerable vulnerability versus a robustness/DoS-on-corruption issue.

### Recommendation
Add explicit bounds validation before performing the subtractions in `parseRefBlock`, mirroring the pattern already used in `getVarInt`:
- Reject blocks where `currentBS < 2` before computing `blockStart+currentBS-2`.
- Validate `3*uint(b.RestartCount) <= blockStart+currentBS-2` before computing `RestartStart`, returning a parse error otherwise.
- Consider using signed (`int64`) arithmetic for these offset calculations with explicit range checks, then converting to `uint` only after validation, analogous to fixing the Solidity issue by casting operands to a signed type before subtracting rather than after.

### Proof of Concept
Conceptual reproduction (would need to be validated in a live Gitaly checkout):
1. Take a valid reftable `.ref` file produced by `git pack-refs`/`git update-ref` with the reftable backend enabled.
2. Overwrite the 3-byte block-length field read by `extractBlockLen` (offset `blockStart+1` .. `blockStart+4`) inside a `r`-type (ref) block with a value `< 2`.
3. Call `reftable.ParseTable(path)` followed by `table.GetReferences()` (as exercised in `internal/git/reftable/reftable_test.go`'s `TestParseTable`/`TestParseTable_validation` harness).
4. Expect a panic from the out-of-range slice expression `src[blockStart+currentBS-2:]` in `parseRefBlock`, rather than a returned `error`, because `blockStart+currentBS-2` wraps around under `uint` arithmetic. [3](#0-2)

// getBlockRange provides the abs block range if the block is smaller

func (t *Table) getBlockRange(offset, size uint) (uint, uint) {
	if offset >= t.footerOffset {
		return 0, 0
	}

	if offset+size > t.footerOffset {
		size = t.footerOffset - offset
	}

	return offset, offset + size
}

// extractBlockLen extracts the block length from a given location.
func (t *Table) extractBlockLen(src []byte, blockStart uint) uint {
	return uint(big.NewInt(0).SetBytes(src[blockStart+1 : blockStart+4]).Uint64())
}

// getVarInt parses a variable int and increases the index.
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
