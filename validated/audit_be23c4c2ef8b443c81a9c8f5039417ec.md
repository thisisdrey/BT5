### Title
Unprivileged caller can unfreeze any victim's frozen primary FA store via `migrate_coin_store_to_fungible_store` — (`aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`coin::migrate_coin_store_to_fungible_store` is a permissionless `public entry fun` that accepts an arbitrary `vector<address>`. When it migrates a victim's `CoinStore<CoinType>`, it synchronizes the CoinStore's `frozen` flag onto the victim's primary FA store via `set_frozen_flag_internal`. If the victim holds an **unfrozen** CoinStore with `coin.value > 0` alongside a **frozen** primary FA store, any third party can call this function to force the FA store's frozen flag to `false`, bypassing the issuer's `TransferRef`/`FreezeCapability` entirely.

### Finding Description
`migrate_coin_store_to_fungible_store<CoinType>(accounts: vector<address>)` has no authorization check. It iterates over the supplied addresses and calls `maybe_convert_to_fungible_store<CoinType>(account)` for each.

Inside `maybe_convert_to_fungible_store`:
1. The `CoinStore<CoinType>` is destructured, extracting its `frozen` field (line 674).
2. The condition `coin.value > 0` is checked (line 676) — if true, the primary FA store is obtained via `ensure_primary_store_exists`.
3. At lines 712–713, if `frozen != fungible_asset::is_frozen(store)`, `set_frozen_flag_internal(store, frozen)` is called.

There is no check that the caller holds the `TransferRef` or `FreezeCapability` for the asset. The FA store's frozen flag is overwritten with whatever the CoinStore says.

**Attack precondition:**
- Victim has `CoinStore<CoinType>` with `frozen = false` and `coin.value > 0`.
- Victim's primary FA store for the paired metadata exists and has `frozen = true` (set by the issuer).

**Attack:** Attacker submits a transaction calling `migrate_coin_store_to_fungible_store<CoinType>(vector[victim_addr])`. The function reads `frozen=false` from the CoinStore, sees it differs from the FA store's `frozen=true`, and calls `set_frozen_flag_internal(store, false)`, permanently unfreezing the FA store.

### Impact Explanation
The issuer's freeze on a user's FA store is silently and permanently removed by an unprivileged third party. Any asset whose issuer relies on the freeze mechanism for compliance, sanctions enforcement, or protocol-level access control is compromised. The victim can now freely transfer assets that were supposed to be frozen. This constitutes unauthorized state transition and bypass of issuer-controlled asset freeze — a direct impact on fungible asset integrity.

### Likelihood Explanation
The entry function is public and permissionless. The precondition (unfrozen CoinStore + frozen FA store) is a realistic state during the coin-to-FA migration period, especially for regulated assets where issuers freeze FA stores while users still hold legacy CoinStore balances. Any attacker can trigger this with a single transaction at zero cost.

### Recommendation
Before calling `set_frozen_flag_internal`, check whether the FA store is already frozen by a source other than the CoinStore migration (i.e., do not overwrite a frozen FA store with `false` unless the CoinStore itself was frozen). A minimal fix: only propagate `frozen=true` from CoinStore to FA store, never `frozen=false`. Alternatively, skip the freeze-sync entirely if the FA store is already frozen:

```move
// Only freeze the FA store if the CoinStore was frozen; never unfreeze it here.
if (frozen && !fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, true);
};
```

#[test(aptos_framework = @aptos_framework, issuer = @0x1234, victim = @0x5678, attacker = @0x9999)]
fun test_unfreeze_bypass(aptos_framework: &signer, issuer: &signer, victim: &signer, attacker: &signer) {
