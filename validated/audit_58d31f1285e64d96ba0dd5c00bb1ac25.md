## Finding

### Title
Cross-StackerDB chunk signature replay due to missing contract-identity binding in `SlotMetadata` digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` binds a signed StackerDB chunk only to `slot_id`, `slot_version`, and `data_hash`. It never binds the digest to the target StackerDB contract (`QualifiedContractIdentifier`). Consequently, a chunk that a signer validly authored and signed for StackerDB contract A can be replayed byte-for-byte by any unprivileged network peer into a different StackerDB contract B, and will pass all server-side checks (`try_replace_chunk` / `validate_received_chunk`) as long as the same signer address happens to own the same `slot_id` in contract B. This is the direct structural analog of the reported Aptos DKG bug, where `AggregatedSubtranscript` signatures were not bound to `dealer_epoch`, letting a valid multisig from epoch N be replayed into epoch N+1.

### Finding Description
The signing/verification digest is: [1](#0-0) 

```rust
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```

No `contract_id` (or any other DB-identifying value) is folded into the signed message. `verify()` recovers the pubkey from this same domain-less digest and only checks it against the caller-supplied `principal` address: [2](#0-1) 

On the storage path, `StackerDBTx::try_replace_chunk` looks up the expected signer *for that particular contract's slot* and checks the signature/version, but never checks that the chunk was originally destined for this contract: [3](#0-2) 

The same gap exists in the P2P validation path used for both pushed and downloaded chunks: [4](#0-3) 

Because the digest is contract-agnostic, whenever the same `StacksAddress` is registered as the signer for the same `slot_id` in two different StackerDB contracts (e.g. two different `.signers-<cycle>-<n>` reward-cycle contracts, which is common because signer sets and their relative ordering are frequently stable across cycles), a previously observed, validly-signed `StackerDBChunkData` (slot_id, slot_version, data, sig) from contract A can be resubmitted verbatim — via the unauthenticated `POST /v2/stackerdb/.../chunks` HTTP endpoint or via unsolicited P2P `StackerDBPushChunk` — against contract B. `try_replace_chunk`/`validate_received_chunk` will accept it as if it were freshly authored for contract B, provided only that the target slot's stored version is lower than the replayed `slot_version` and it fits `chunk_size`. Both are attacker-controllable/observable properties, not secrets.

This breaks the "authenticated for DB A" vs "stored as authenticated for DB B" equality: the signature is treated as proof of authorship for whichever contract queries it, when it was only ever a commitment to `(slot_id, slot_version, data_hash)`.

### Impact Explanation
This allows an unprivileged network participant who has observed one legitimately signed chunk to inject/propagate that same signed payload into an unrelated StackerDB replica's namespace, without any private key access. Depending on which StackerDB contract is targeted (e.g. signer coordination contracts), this can cause stale or out-of-context signer data to be accepted as canonical for a different reward cycle/contract, misleading downstream consumers of that DB (event observers, other nodes syncing the DB) about what was actually authored for that context — a "non-canonical data served as canonical" condition reachable by any remote, unauthenticated peer.

### Likelihood Explanation
Exploitation requires: (1) observing a validly signed chunk (trivial — StackerDB chunks are broadcast/gossiped and served on request), and (2) the same signer address owning the same `slot_id` in the target contract. Slot-to-signer assignment for `.signers-*` StackerDB contracts is derived from the reward-set ordering, which is often stable or only partially reshuffled between adjacent cycles, making address/slot_id collisions realistic rather than purely theoretical. No secret key, admin role, or node-internal state is needed.

### Recommendation
Bind the contract identity into `SlotMetadata::auth_digest()` (e.g., hash the `QualifiedContractIdentifier` bytes alongside `slot_id`, `slot_version`, and `data_hash`), and version this change so old signatures aren't misinterpreted. Alternatively, have `try_replace_chunk`/`validate_received_chunk` require an additional out-of-band binding (e.g. verify the signature against a digest that already incorporates `smart_contract`), consistent with the domain-separation fix applied upstream for `AggregatedSubtranscript`.

### Proof of Concept
1. Signer key `S` legitimately signs and posts `StackerDBChunkData { slot_id: 3, slot_version: 5, sig, data }` to StackerDB contract `A` (`.signers-10-1`), where `S` owns slot 3 in `A`. This is observed by any peer (chunk is gossiped / retrievable via `StackerDBGetChunk`).
2. Attacker (no keys) determines that StackerDB contract `B` (`.signers-11-1`) also lists `S` as owner of slot 3 (common due to stable reward-set ordering), and that `B`'s stored version for slot 3 is `< 5`.
3. Attacker issues `POST /v2/stackerdb/<B-address>/<B-contract>/chunks` with the *exact same* `slot_id=3, slot_version=5, sig, data` captured from `A`.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` calls `tx.try_replace_chunk` for contract `B`; `slot_desc.verify(&slot_validation.signer)` succeeds (digest doesn't encode contract), version check passes (5 > B's current version) — chunk is stored and relayed as authentic data for `B`, even though `S` never authored it for `B`.

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
