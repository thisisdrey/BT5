### Title
Reliability scoring counts hash-mismatched attachment responses as successes, letting a malicious peer dominate `get_most_reliable_source()` and `Ord` for `AttachmentRequest` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` bumps a peer's `ReliabilityReport` success counter purely based on whether `decode_atlas_get_attachment()` parsed the HTTP response, without ever comparing `Hash160::from_data(&attachment.content)` to the requested `content_hash`. A peer that always returns syntactically valid but content-mismatched attachments therefore accumulates the same "successful" score as an honest peer, which lets it win `AttachmentRequest`'s `Ord`/`get_most_reliable_source()` selection for future rounds.

### Finding Description
In `extend_with_attachments`: [1](#0-0) 
the response is decoded and unconditionally inserted with `self.attachments.insert(response.attachment)`, then `report.bump_successful_requests()` is called with no check that the returned content's hash equals `request.content_hash`. The only failure paths are "no response" or "decode error" (`bump_failed_requests()`), not "wrong content".

Peer selection for subsequent requests relies entirely on this report: [2](#0-1) 
`get_most_reliable_source` picks the source with the highest `report.score()`, and `Ord for AttachmentRequest` breaks ties using the same comparison. `Requestable::get_url` for `AttachmentRequest` also routes future HTTP requests to `get_most_reliable_source()`'s URL: [3](#0-2) 

So the invariant the question posits — "`reported_success_count == count of responses whose hash matched the requested content_hash`" — does not hold in the code: `reported_success_count` is actually `count of responses that decoded successfully`, regardless of content correctness. A peer serving wrong-hash content on every request will have its `bump_successful_requests()` invoked exactly as often as an honest peer, and if the honest peer additionally experiences ordinary network failures, the malicious peer's score can exceed it.

### Impact Explanation
This does not directly cause the wrong attachment to be accepted as canonical (any final acceptance of `Attachment` into `AtlasDB`/instance resolution would need to separately verify against the expected `content_hash`, a step outside this function and not exercised here). The demonstrable, in-scope impact is entirely within the download scheduler: `AttachmentsDownloader`'s prioritization/URL-selection logic (`get_prioritized_attachments_requests`, `get_most_reliable_source`, `Ord for AttachmentRequest`) can be made to consistently prefer a peer that never supplies usable data. This entrenches resolution failures for the affected attachments/BNS zonefiles — retries keep going to the same unhelpful peer while assigning it an artificially high reliability score — degrading availability of attachment resolution for the node. This is a bounded, repeatable availability degradation confined to the Atlas attachment-download subsystem, not a state-corruption or forged-data-acceptance bug, since I could not confirm within this file that a hash-mismatched `Attachment` is ever treated as the resolved instance without a downstream hash check.

### Likelihood Explanation
Any remote peer that is included among a batch's `AttachmentsInventoryRequest`/`AttachmentRequest` sources (i.e., any peer this node treats as an outbound sync peer with a data URL, and which advertises the missing attachment in its inventory) can trigger this by simply returning HTTP 200 responses with any well-formed but wrong-content-hash attachment payload to every `/v2/attachments/<hash>` GET. No secret, signature, or privileged role is required — this matches the "unprivileged remote peer" threat model. The attacker only needs to keep answering with parseable garbage; cost is low and the behavior is fully repeatable across retries/batches since reports persist in `AttachmentsDownloader::reliability_reports`.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before calling `report.bump_successful_requests()`; call `report.bump_failed_requests()` (or a distinct "bad content" penalty) on mismatch instead, and avoid inserting the mismatched attachment into `self.attachments`.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/tests.rs` (or a new test module) that:
1. Constructs an `AttachmentsBatchStateContext` with two peers, `honest_url` and `malicious_url`, each with an initial empty `ReliabilityReport`.
2. Builds a `BatchedRequestsResult<AttachmentRequest>` where `malicious_url`'s N responses all decode successfully via `decode_atlas_get_attachment()` but carry `Attachment { content: b"wrong".to_vec() }` while the request's `content_hash` is `Hash160::from_data(b"correct")`; `honest_url`'s responses return the correct content but M of them are `None` (simulating failures).
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert that `context.peers[&malicious_url].score() > context.peers[&honest_url].score()` even though zero of the malicious peer's responses had `Hash160::from_data(content) == content_hash`, and separately assert (by re-deriving the hash check the code lacks) that all N malicious responses are hash-mismatched — proving `bump_successful_requests` was called N times despite 0 real matches.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}
