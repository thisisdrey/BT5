### Title
Stale Postponed Action Receipts Survive Account Deletion and Execute Against a Recreated Account - ([File: runtime/runtime/src/actions.rs], [File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`action_delete_account` / `remove_account` delete the `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData` for an account, but never clean up `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries keyed by that account's `receiver_id`. When the awaited `DataReceipt` later arrives, `process_receipt`'s `Data` arm resolves and executes the stale postponed `ActionReceipt` purely by `receiver_id`/`data_id`/`receipt_id` lookup, with no check that the account was deleted and recreated in the interim.

### Finding Description
`action_create_account`/self-call flows let a contract on account `A` build a self-addressed `ActionReceipt` (`receiver_id == predecessor_id == A`) containing `input_data_ids` from a `Promise::then` callback. When such a receipt arrives and its data is not yet available, `process_action_receipt` stores it as postponed: [1](#0-0) 

`remove_account`, invoked from `action_delete_account`, only clears `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [2](#0-1) 

`action_delete_account` itself performs no check for outstanding postponed receipts, `PendingDataCount`, or `PostponedReceiptId` entries tied to the account before wiping it and setting `*account = None`: [3](#0-2) 

When the corresponding `DataReceipt` eventually arrives, `process_receipt`'s `Data` arm looks up `PostponedReceiptId{receiver_id, data_id}` and `PendingDataCount{receiver_id, receipt_id}` purely by these keys — with no verification that the account backing `receiver_id` is the same account instance that originally created the postponed receipt: [4](#0-3) 

Because the stale receipt has `predecessor_id == receiver_id == A`, `check_actor_permissions` treats it as a self/owner action (actor_id initialized from `predecessor_id`, matching `account_id`) for privileged actions such as `AddKey`, `Stake`, or `DeployContract`, and `check_account_existence` only requires that some account currently exists at `A` — it does not verify it is the *same* account: [5](#0-4) 

Exploit flow:
1. Attacker deploys a contract on account `A`, triggers a cross-contract callback creating a postponed self-receipt on `A` containing e.g. `AddKey(FullAccess, K_attacker)`, with input data pending.
2. Attacker submits `DeleteAccount{beneficiary_id: attacker}` for `A` (small storage usage, zero locked stake) — succeeds; `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` survive in trie state.
3. Account name `A` is later reused — either by the same attacker (self-directed re-init) or, more critically, by an unrelated third party who independently registers the now-available account id `A` with their own keys/contract/funds.
4. Attacker (who controls delivery of the original cross-contract callback / knows the deterministic `data_id`) causes the `DataReceipt` to be delivered.
5. `process_receipt` finds the stale `PostponedReceiptId`/`PendingDataCount` entries still keyed to `A`, fetches and executes the stale `ActionReceipt` against the *new* account state, and `check_actor_permissions` passes it as an owner action with no signature from the new account's actual key holder.

### Impact Explanation
This is an authorization escalation across account recreation: privileged self-actions (`AddKey FullAccess`, `Stake`, `DeployContract`) queued by a previous account occupant execute against a freshly (re)created account without any signature or consent from its new owner. If a third party re-registers the deleted account name and funds it before the attacker triggers the residual receipt, the attacker can inject a full-access key or replace the contract on that new account, leading to theft of the new owner's funds/control — matching the "authorization escalation across accounts" and "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions: an ordinary unprivileged account, ability to deploy a wasm contract, trigger a cross-contract Promise callback to itself, and control account deletion/timing — all within a single attacker-controlled account's normal capabilities and standard NEAR transaction fees. No validator, node-operator, or privileged access is required. The main friction is that a distinct victim must independently re-register the exact same account_id before the attacker replays the pending `DataReceipt`; this is fully feasible for attacker-chosen/short or otherwise desirable account names, and the state entries persist indefinitely (no expiry) until consumed, so the attacker can wait arbitrarily long for the collision. The attack is repeatable per deleted/recreated account name.

### Recommendation
Either (a) reject `DeleteAccount` when the account has any outstanding `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries (require callbacks to resolve or be explicitly cancelled first), or (b) have `remove_account` iterate and purge all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie entries for the account being deleted, or (c) bind postponed receipts to an account "incarnation"/generation counter that is bumped on `CreateAccount`, and have `process_receipt`'s data-arm and postponed-receipt execution verify the generation matches before applying, dropping (and refunding/erroring) stale receipts whose generation no longer matches.

### Proof of Concept
Runtime integration test (test-loop or `runtime/runtime` apply-chain test):
1. Create account `A` with a contract that, on call, issues a `Promise::then` callback to itself producing an `ActionReceipt{receiver_id: A, predecessor_id: A, actions: [AddKey(FullAccess, K1)], input_data_ids: [d1]}` before the callback data is available; assert `TrieKey::PostponedReceipt{A, receipt_id}` and `TrieKey::PendingDataCount{A, receipt_id}` exist in state.
2. Submit `DeleteAccount{account_id: A, beneficiary_id: attacker}` from `A`; assert account `A` no longer exists but the postponed-receipt trie keys above are still present.
3. Submit `CreateAccount` for `A` with a fresh key `K2` (and optionally deploy a different contract), simulating a new/unrelated owner.
4. Deliver the pending `DataReceipt{receiver_id: A, data_id: d1}`.
5. Assert the resumed `ActionReceipt` executes successfully against the new account and that `K1` (attacker's key, not signed by the new owner) is now a `FullAccess` key on account `A`'s access-key set — demonstrating the stale receipt's actions applied to the recreated account rather than being dropped or rejected.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            } else {
                if account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts) {
                    // If the account doesn't exist and it's implicit, then you
                    // should only be able to create it using single transfer action.
                    // Because you should not be able to add another access key to the account in
                    // the same transaction.
                    // Otherwise you can hijack an account without having the private key for the
                    // public key. We've decided to make it an invalid transaction to have any other
                    // actions on the implicit hex accounts.
                    // The easiest way is to reject the `CreateAccount` action.
                    // See https://github.com/nearprotocol/NEPs/pull/71
                    return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                        account_id: account_id.clone(),
                    }
                    .into());
                }
            }
        }
        Action::Transfer(_) => {
            if account.is_none() {
                return check_transfer_to_nonexisting_account(
                    config,
                    account_id,
                    implicit_account_creation_eligible,
                );
            }
        }
        Action::DeterministicStateInit(_) => {
            // Existing and non existing is valid for DeterministicStateInit.
            // Does not exist => The account will be created by the action.
            // Does exist => Nothing happens but the receipt is not aborted to
            // allow optional init before other actions.
        }
        Action::DeployContract(_)
        | Action::FunctionCall(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeleteAccount(_)
        | Action::Delegate(_)
        | Action::DelegateV2(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::TransferToGasKey(_)
        | Action::WithdrawFromGasKey(_) => {
            if account.is_none() {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
    };
    Ok(())
}
