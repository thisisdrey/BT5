Audit Report

## Title
Integer-division truncation in `OutboundQueue::calculate_fee` lets the remote (Ethereum-side) delivery fee round down to zero, causing underpriced bridge work - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::calculate_fee` converts an 18-decimal, ether-denominated remote fee into the chain's native decimals via plain integer division in `convert_from_ether_decimals`, with no rounding-up or minimum-fee floor. When `gas_used_at_most * fee_per_gas + reward` scaled by `multiplier`/`exchange_rate` is small relative to the decimal-conversion divisor (`10^(ETHER_DECIMALS - T::Decimals)`), the result truncates to zero, so a sender is charged `fee.remote = 0` even though all `PricingParameters` pass `validate()`.

## Finding Description
`calculate_fee` computes the remote fee in wei via `calculate_remote_fee`, scales it by `multiplier`/`exchange_rate` using `FixedU128`, and then calls `convert_from_ether_decimals`, which does `value.checked_div(denom)` with no rounding or floor logic. `PricingParameters::validate` only rejects exact-zero fields, not truncated-to-zero derived fees, so it does not catch this case. Meanwhile, `do_process_message` constructs the `CommittedMessage` sent to Ethereum using the raw `pricing_params.rewards.remote` and `fee_per_gas` values directly (unaffected by the local truncation), so the bridge still commits to paying relayers the full reward/gas refund on Ethereum even though `Fee::total()` (used by callers like the XCM exporter to withdraw payment) collected `local + 0` from the sender.

## Impact Explanation
Any unprivileged user invoking `SendMessage::validate` (e.g., via `pallet_xcm::execute`/`send`) under `PricingParameters` where the remote-fee computation rounds to zero pays nothing toward the Ethereum-side relayer reward/gas, while the queued message still promises that reward on delivery. Repeated exploitation drains the pool funding relayer rewards without collecting matching fees, degrading relayer incentives and potentially stalling bridge message processing, matching the "public underpriced work that degrades block production or stalls bridge processing" impact category.

## Likelihood Explanation
The vulnerability depends on the relationship between `PricingParameters` (`exchange_rate`, `fee_per_gas`, `rewards.remote`, `multiplier`) and `T::Decimals`, which are periodically adjusted by governance rather than attacker-controlled directly. However, once such a parameter combination is live, exploitation requires no special privilege — any ordinary user's bridge message triggers the truncation. The maintainers' own test, `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, demonstrates this is a real, reproducible condition, not a contrived edge case, and `validate()` provides no defense against it.

## Recommendation
In `convert_from_ether_decimals` (and the decimal-scaling steps in `calculate_fee`), round up instead of truncating, or enforce a configurable minimum non-zero fee floor so any strictly-positive computed fee cannot collapse to zero after decimal conversion. Extend `PricingParameters::validate` or add a runtime check in `calculate_fee` to detect/reject parameter combinations that would yield `fee.remote == 0` for realistic `gas_used_at_most` values.

## Proof of Concept
The existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` in `bridges/snowbridge/pallets/outbound-queue/src/test.rs` (lines 303-319) reproduces this exactly: with `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local:1, remote:1}`, `multiplier = 1/1`, and `gas_used = 250000` (Test config `Decimals = 12`), `OutboundQueue::calculate_fee` returns `fee.local = 698000000` (nonzero) but `fee.remote = 0`, despite all `PricingParameters::validate()` checks passing.

			// Remote fee in ether
