### Title
Eligible user permanently loses reward if their address is blocked/blacklisted by the reward token — reward cannot be redirected to an alternative receiver - ([File: contracts/utils/RecurringAirdrop.sol](contracts/utils/RecurringAirdrop.sol), [File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RecurringAirdrop.claim` (and its deployed subclass `MetAirdrop`) hard-codes the merkle leaf account, the `claimed[]` accounting key, and the token recipient to `msg.sender`. Similarly, `RewardsDistributor.claimRewards` always pays accrued rewards to `account_` itself — there is no recipient parameter. If the distributed/reward token can block transfers to an address (blacklistable tokens such as USDC/USDT, or the esMET `lockFor` path reverting for a blocked beneficiary), the eligible user's claim always reverts and the reward is frozen in the contract forever. This is the same bug class as the Footium report: a `_to`-style recipient forced to equal the claiming account.

### Finding Description
In `RecurringAirdrop.claim` (`contracts/utils/RecurringAirdrop.sol:52-66`), the leaf is `keccak256(abi.encodePacked(msg.sender, amount_))`, `claimed[msg.sender]` is incremented, and `_transferReward(msg.sender, _claimable)` is invoked. The base implementation does `token.safeTransfer(to_, amount_)` (line 73-75). `MetAirdrop._transferReward` (`contracts/MetAirdrop.sol:31-48`) either `MET.safeTransfer(to_, ...)` or calls `ESMET.lockFor(to_, amount_, ...)`.

In `RewardsDistributor.claimRewards` (`contracts/RewardsDistributor.sol:150-168`), anyone can trigger claims for arbitrary `accounts_`, but `_transferRewardIfEnoughTokens(account_, ...)` sends `rewardToken` strictly to `account_` (line 248-256). `rewardToken` is set at `initialize` (line 103-109) and is not constrained — a pool distributor can be initialized with a blacklistable token (e.g., USDC).

If the token's `transfer`/`transferFrom` reverts for the beneficiary (blacklist) or `esMET.lockFor` rejects the beneficiary, the whole transaction reverts (before `claimed[]`/`tokensAccruedOf` are committed), so the user can never claim while blocked — and there is no alternative receiver parameter to route around the restriction.

### Impact Explanation
Permanent freezing of unclaimed yield: the user's accrued/allocated rewards remain locked in `RecurringAirdrop`/`MetAirdrop`/`RewardsDistributor` and are unclaimable by that user for as long as the token-level block holds. Because the merkle leaf binds `msg.sender`, no delegate or alternate address can claim on the blocked user's behalf either. In `RewardsDistributor`, a blocked account in a batched `claimRewards(accounts_, tokens_)` call also reverts the entire batch (minor, since callers choose the list). Rewards remain recoverable only via governor `sweep`, i.e., they depend on governance intervention.

### Likelihood Explanation
Medium-low. The code path is unconditionally reachable (`claim` is public, `nonReentrant` only), but impact requires the reward token to enforce a recipient-side restriction against the user. The deployed `MetRewardsDistributor`/`OpRewardsDistributor` use MET/OP, and `MetAirdrop` uses immutable MET — I could not confirm from in-repo code whether MET or the external esMET `lockFor` can block a beneficiary; `IESMET` is only an interface in `contracts/interfaces/external/IESMET.sol`. However, `RewardsDistributor.initialize` accepts an arbitrary `rewardToken` with no allowlist check, so any present or future distributor configured with a blacklistable reward token (USDC/USDT-class) is fully exposed, and the fork PoC is reproducible by deploying a blacklistable ERC20 as `token`/`rewardToken`.

### Recommendation
- `RecurringAirdrop`: include an explicit `to_` recipient in the leaf encoding or accept a `to_` parameter while keeping `claimed[]`/`proof` accounting keyed on `msg.sender`'s eligible allocation — e.g., leaf `[account, amount]` verified against `msg.sender`, then `_transferReward(to_, _claimable)`.
- `RewardsDistributor`: add `claimRewards(address account_, IERC20[] tokens_, address to_)` or let users set a claim-receiving delegate; continue accounting against `account_` but send tokens to `to_`. Alternatively, use a pull pattern where failure to transfer to a blocked receiver does not brick future claims.
- In `MetAirdrop._transferReward`, allow `lockFor`/`safeTransfer` target to differ from the merkle account for the same reason.

### Proof of Concept
Foundry (fork or local) sketch:

```solidity
contract BlacklistToken is ERC20 {
    mapping(address => bool) public blocked;
    constructor() ERC20("B", "B") { _mint(msg.sender, 1e24); }
    function block_(address a) external { blocked[a] = true; }
    function _update(address f, address t, uint256 v) internal override {
        require(!blocked[t], "blocked");
        super._update(f, t, v);
    }
}

function testBlacklistedUserCannotClaim() public {
    BlacklistToken tkn = new BlacklistToken();
    RecurringAirdropDrop airdrop = new RecurringAirdropDrop(IERC20(address(tkn)));
    tkn.transfer(address(airdrop), 1000e18);

    // build 1-leaf tree for alice
    bytes32 leaf = keccak256(abi.encodePacked(alice, uint256(100e18)));
    vm.prank(governor);
    airdrop.updateMerkleRoot(leaf, bytes32(uint256(1))); // single-leaf root, empty proof

    // alice claims successfully before blacklist
    vm.prank(alice);
    airdrop.claim(50e18, new bytes32[](0)); // partial? (leaf is cumulative; see note)

    // Now blacklist alice and attempt to claim remaining/newly allocated amount
    tkn.block_(alice);
    vm.prank(alice);
    vm.expectRevert(); // safeTransfer to alice reverts
    airdrop.claim(100e18, new bytes32[](0));
    // alice has no way to redirect the reward to another address -> funds frozen
}
```

Equivalent variant for `RewardsDistributor`: initialize with `BlacklistToken` as `rewardToken`, accrue rewards to alice via a deposit/debt token with nonzero speed, call `claimRewards(alice, tokens)` — it reverts once `blocked[alice] == true`, and no overload permits an alternate recipient. Note the leaf encodes cumulative `amount_`, so the PoC should use a second `updateMerkleRoot` round or a fresh allocation to demonstrate a positive `_claimable`.
