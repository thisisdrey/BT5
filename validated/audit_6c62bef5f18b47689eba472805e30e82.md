### Title
Unvalidated `GitObjectDirectory`/`GitAlternateObjectDirectories` Repository Fields Enable Object-Directory/Alternates Escape - ([File: internal/git/gitcmd/command_factory.go])

### Summary
Gitaly's `Repository` protobuf message carries client-settable `git_object_directory` and `git_alternate_object_directories` fields that are meant only to convey Git's object-quarantine paths back and forth between Gitaly and Rails during push access checks. When Gitaly spawns a Git subprocess, these fields are joined onto the repository path and exported as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` without ever being run through the same relative-path containment check (`storage.ValidateRelativePath`) that guards the dedicated `ObjectDirectoryPath()` accessor. This mirrors the Symmetry "buy_state_rebalance" bug: a downstream, security-critical operation (a CPI / here, a spawned `git` process) trusts caller-supplied "account"/path values instead of validating that they resolve to the intended, bounded targets.

### Finding Description
`internal/git/localrepo/paths.go`'s `ObjectDirectoryPath()` carefully validates the `GitObjectDirectory` field with `storage.ValidateRelativePath` and additional quarantine-prefix checks before it is used [1](#0-0) , and even guards against path traversal explicitly [2](#0-1) .

However, the actual code path used whenever Gitaly executes *any* Git command through the `ExecCommandFactory` does not go through this validated accessor. Instead, it takes the raw `GetGitObjectDirectory()`/`GetGitAlternateObjectDirectories()` values straight off the request-supplied `Repository` message and joins them onto the repo path unchecked: [3](#0-2) 

That joined value is turned directly into the `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables with no traversal check at all: [4](#0-3) 

The Gitaly codebase itself acknowledges that these two fields are effectively “remaining_accounts”-style trust boundaries that are not enforced: the transaction middleware only special-cases requests where these fields are non-empty and explicitly documents that manually setting them lets a caller "circumvent transaction management," calling this "unaddressed for now": [5](#0-4) 

For accessor RPCs, the middleware only requires that a `relative-path-bin` metadata header be present (`restoreSnapshotRelativePath`); it rewrites `RelativePath` but never validates or bounds `GitObjectDirectory`/`GitAlternateObjectDirectories` themselves: [6](#0-5) 

Tests confirm the field is deliberately consumed as-is and only later routines like `GetObjectDirectorySize` happen to reject traversal because they route through `ObjectDirectoryPath()` — while the generic `newCommand` git-spawning path (used by essentially every RPC that shells out to `git`) does not: [7](#0-6) 

### Impact Explanation
An RPC request whose `Repository.git_object_directory` / `git_alternate_object_directories` is crafted with `../` segments (or an absolute-looking join) can cause Gitaly to spawn Git subprocesses that read (and in some non-catfile flows, write) objects from directories outside of the intended repository/quarantine boundary. This is a cross-repository/cross-storage object-access primitive: exactly the class of bug flagged by the report — a downstream primitive (spawned Git process / CPI call) trusting caller-supplied "account" (object-directory path) data instead of the program validating it against an allow-listed pair of locations. Depending on the calling RPC this can leak objects from arbitrary repositories/storages into command output, or make private objects appear to belong to the wrong repository, undermining repository isolation and, for hook/push-time flows, potentially quarantine/access-check bypass.

### Likelihood Explanation
The two fields are ordinary, wire-visible fields on the `Repository` message used on essentially every RPC [8](#0-7) , and the only guard for accessor RPCs is presence of a metadata header, not validation of the field's contents [6](#0-5) . Any caller able to invoke Gitaly RPCs directly (as Rails does during push access checks, and as any component holding Gitaly's shared auth token can) can set these fields to arbitrary values; the containment logic that exists elsewhere (`ObjectDirectoryPath`) is not applied on the hot path used to actually spawn Git processes, and the maintainers' own comment confirms the gap is known and intentionally deferred.

### Recommendation
Route the object-directory/alternate-directory values used in `ExecCommandFactory.newCommand` (and anywhere else `alternates.Env` is called) through the same `storage.ValidateRelativePath`/quarantine-prefix validation performed in `localrepo.(*Repo).ObjectDirectoryPath`, rejecting any repository whose `GitObjectDirectory`/`GitAlternateObjectDirectories` resolve outside the repository's own storage root or an expected quarantine/transaction temp directory, before exporting `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES`.

### Proof of Concept
1. As a caller with the ability to invoke a Gitaly RPC that accepts a `Repository` message and eventually shells out to `git` (i.e., goes through `ExecCommandFactory.newCommand`), send a request where `git_alternate_object_directories` is set to a relative path such as `../../other-repo.git/objects`, alongside a valid `relative-path-bin` metadata header to satisfy the accessor-path check in `restoreSnapshotRelativePath`.
2. Gitaly computes `GIT_ALTERNATE_OBJECT_DIRECTORIES=<repoPath>/../../other-repo.git/objects` via `alternates.Env` and injects it into the spawned `git` process's environment [9](#0-8) .
3. The `git` subprocess resolves objects from the foreign repository's object directory, which is returned to the caller as if it belonged to the target repository, evidencing cross-repository object access outside the intended storage boundary.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}

func restoreSnapshotRelativePath(ctx context.Context, methodInfo protoregistry.MethodInfo, req proto.Message) (proto.Message, error) {
	// Rails sends RPCs from its access checks with quarantine applied. The quarantine paths are relative to the
	// snapshot repository of the original transaction. While the relative path of the request is the original relative
	// path of the repository before snapshotting, Rails sends the snapshot repository's path in a header. For the
	// quarantine paths to apply correctly, we must thus rewrite the request to point to the snapshot repository here.
	snapshotRelativePath := metadata.GetValue(ctx, MetadataKeySnapshotRelativePath)
	if snapshotRelativePath == "" {
		return nil, ErrQuarantineWithoutSnapshotRelativePath
	}

	rewrittenReq, targetRepo, err := rewritableRequest(methodInfo, req)
	if err != nil {
		return nil, fmt.Errorf("rewritable request: %w", err)
	}

	targetRepo.RelativePath = snapshotRelativePath

	return rewrittenReq, nil
}
