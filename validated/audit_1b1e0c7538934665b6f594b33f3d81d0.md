### Title
Out-of-bounds slice re-slice on malformed PNG tRNS chunk causes decoder panic - ([File: src/image/png/reader.go])

### Summary
`image/png`'s `parsetRNS` handles the `cbP1/cbP2/cbP4/cbP8` (paletted) branch by unconditionally growing `d.palette` with `d.palette = d.palette[:n]` whenever `len(d.palette) < n`, instead of validating that the palette actually has enough backing capacity. A PNG that declares a paletted `IHDR` color type but supplies a `tRNS` chunk before (or without) a valid `PLTE` chunk of sufficient size causes this re-slice to run on a `nil`/zero-capacity slice, triggering a runtime panic (`slice bounds out of range`). This is the same bug class as CVE-2014-0144: an image/container-format parser missing an input-validation check on a length-derived index into an internal table, taken from attacker-controlled header/chunk data.

### Finding Description
Untrusted PNG bytes reach `image.Decode`/`png.Decode`, which drives `(*decoder).decode` to read chunks sequentially and dispatch to per-chunk parsers such as `parseIHDR`, `parsePLTE`, and `parsetRNS`. `parseIHDR` sets `d.cb` (color mode) purely from header fields (bit depth + color type) without requiring that a `PLTE` chunk exists yet [1](#0-0) . In `parsePLTE`, when it does run, `d.palette` is allocated with capacity 256 and then sliced down to `np` entries [2](#0-1) .

The vulnerable sink is in `parsetRNS`'s paletted branch:
```go
case cbP1, cbP2, cbP4, cbP8:
    if length > 256 {
        return FormatError("bad tRNS length")
    }
    ...
    if len(d.palette) < n {
        d.palette = d.palette[:n]
    }
    for i := 0; i < n; i++ {
        rgba := d.palette[i].(color.RGBA)
        ...
``` [3](#0-2) 

If a crafted stream sets a paletted `IHDR` (`d.cb` = `cbP1/2/4/8`) and then sends a `tRNS` chunk before any `PLTE` chunk, `d.palette` is still its zero value (`nil`, length 0, capacity 0). The check `len(d.palette) < n` is true for any `n > 0`, and the code attempts `d.palette[:n]`, which panics because `n` exceeds the slice's capacity (Go slicing beyond capacity panics, it does not silently grow). Even if a `PLTE` chunk was previously parsed but declared fewer entries than `tRNS`'s `n` (still ≤ 256 due to the `d.palette` allocation always using a 256-capacity backing array, this particular re-slice happens to stay in bounds) — but the `nil`/no-PLTE case is unguarded and panics.

### Impact Explanation
A single crafted PNG file (or an image embedded in HTML/other document formats decoded via `image.Decode`) triggers an unrecovered panic in the standard library's `image/png` decoder when processed by any Go program that decodes untrusted images (web servers generating thumbnails, chat/upload services, image proxies, etc.). This is a parser-panic-on-malicious-input class issue, which qualifies as a real security-relevant bug under Go's vulnerability policy even without memory corruption, since it is a remote unauthenticated denial-of-service against any process that calls `png.Decode`/`image.Decode` on attacker-supplied bytes.

### Likelihood Explanation
The attacker only needs to supply a malformed PNG through any normal image-upload/image-fetch workflow — no privileges, no host/environment control, and no reliance on a malicious server or peer are required. The victim workflow is simply "decode an image received from an untrusted source," which is extremely common (image upload endpoints, avatar processing, thumbnailing, etc.).

### Recommendation
In `parsetRNS`'s `cbP1, cbP2, cbP4, cbP8` case, reject the chunk instead of blindly re-slicing: return a `FormatError` (e.g. "tRNS before PLTE" / "tRNS length exceeds palette size") whenever `n` exceeds the palette's actual populated length, and additionally verify `d.palette != nil` (i.e., that a `PLTE` chunk was already successfully parsed) before indexing into it.

        3,          // color type = paletted

    writeChunk(&buf, "tRNS", []byte{0xff})

}
