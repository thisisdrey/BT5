## Title
Unbounded `ContractType` value in permission-operations check causes uncaught index-out-of-bounds exception, bypassing the active-permission allowlist enforcement - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

## Summary
The active-permission "allowlist" that restricts which `ContractType`s a multisig sub-permission may execute is enforced by indexing a fixed 32-byte bitmap (`Permission.operations`) using the *raw, unvalidated* wire value of the contract's type field (`contract.getTypeValue()`), instead of the bounded enum (`contract.getType()`). This is the same bug class as the reported CVE: a request can supply a type "alias" (an out-of-range/unrecognized encoded form) that the allowlist matcher was never designed to reject cleanly, so instead of a clean deny it throws an uncaught exception during transaction/block processing.

## Finding Description
The permission-operations check exists in two duplicated implementations: [1](#0-0) [2](#0-1) 

Both do:
```java
int contractType = contract.getTypeValue();
boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
```
`operations` is a fixed 32-byte `ByteString` (256 valid bit positions, indices 0-31 for `byteAt`). `contract.getTypeValue()` returns the **raw protobuf int32** stored on the wire for the `type` field of `Transaction.Contract`, which — unlike `contract.getType()` — is *not* clamped to `UNRECOGNIZED` for out-of-range values. A transaction constructed with an arbitrary int32 in this field (e.g. an unrecognized "alias" value like `100000` or `-1`) will make `getTypeValue()` return that raw number, while `getType()` would report `UNRECOGNIZED`.

This unsafe index is reached from `TransactionCapsule.checkPermission`: [3](#0-2) 

which is only invoked when the transaction sets a non-default `permissionId` (i.e., it targets an `Active` multisig permission the account owner configured themselves — an ordinary, unprivileged operation via `AccountPermissionUpdateActuator`). It is called from both the signature-verification entry points used for every incoming/broadcast transaction and every transaction inside an applied block: [4](#0-3) [5](#0-4) 

and these are driven from `Manager.pushTransaction` (broadcast path) and `Manager.processTransaction` (block application path): [6](#0-5) [7](#0-6) 

Crucially, the catch block around signature/permission validation only expects `SignatureException`, `PermissionException`, and `SignatureFormatException`: [8](#0-7) 

An `IndexOutOfBoundsException`/`ArrayIndexOutOfBoundsException` thrown by `ByteString.byteAt()` when `contractType/8` is negative or ≥32 is **not** one of the caught types, so it propagates as an uncaught `RuntimeException` out of `validatePubSignature`/`validateSignature`, into `pushTransaction`/`processTransaction`.

This is exactly the CWE-184 pattern from the advisory: the allowlist check assumes all reachable "type" inputs fall in a bounded, recognized set, but the parser/deserializer (`getTypeValue()`) permits an alias/out-of-range encoding that the checker was not built to reject safely — turning what should be a deterministic "Permission denied" rejection into an unhandled exception. Notably, the codebase already has a *safe* pattern for this exact bitmap elsewhere — `AccountPermissionUpdateActuator.checkPermission` iterates a fixed `0..255` range when validating operations at permission-setup time: [9](#0-8) 
— confirming that the enforcement-time check in `WalletUtil`/`TransactionUtil` is the inconsistent, unsafe path.

## Impact Explanation
An uncaught runtime exception thrown while validating a transaction's signature/permission — reachable both when a single transaction is broadcast to a node (`pushTransaction`) and when the same transaction is included in a block being applied (`processTransaction`) — can disrupt transaction processing on any node that receives it (denial of service / processing halt for that code path), including deterministically during block application, which is the core state-transition logic shared by all full nodes. Depending on where the exception propagates to (uncaught exception in the block-application thread), this can result in inconsistent handling across the network or a hard failure in-block processing, which the "Validate" criteria classifies as node crash/halt.

## Likelihood Explanation
Reachable by a single, unprivileged, signed transaction: (1) the attacker creates/uses their own account and self-configures an `Active` permission via `AccountPermissionUpdateContract` (a normal, permissionless multisig setup feature, gated only by the network-wide `AllowMultiSign` flag, which is enabled on mainnet); (2) the attacker crafts a raw transaction (bypassing the normal `ContractType` enum-constrained builders) whose `Contract.type` wire field is set to an out-of-range int32 and whose `permission_id` references the configured Active permission; (3) the attacker signs and broadcasts it. No special network position, node compromise, or SR/witness role is required — it is directly reachable by any transaction broadcaster.

## Recommendation
Bound-check `contract.getTypeValue()` (or better, only accept `contract.getType()` and reject `UNRECOGNIZED`) before indexing into the 32-byte `operations` bitmap in both `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`, mirroring the safe `0..255` bounded iteration already used in `AccountPermissionUpdateActuator.checkPermission`. Additionally, widen the catch clauses around `validatePubSignature`/`checkPermission` call sites to convert any unexpected `RuntimeException` into a `PermissionException`/`ValidateSignatureException` so that malformed contract-type values are cleanly rejected rather than crashing transaction processing.

## Proof of Concept
1. Using an unprivileged account `A`, call `AccountPermissionUpdateContract` to add an `Active` permission (id 2) with a small `operations` bitmap and low threshold — standard multisig setup.
2. Construct a `Transaction` whose single `Contract` has:
   - `permission_id = 2` (referencing the configured Active permission),
   - the `type` field's wire varint set directly (via low-level protobuf byte manipulation, not through the generated `ContractType` enum builder) to an out-of-range value, e.g. `2000` (so `contractType/8 = 250`, which exceeds the 32-byte `operations` bound), or a negative value.
   - a valid `TransferContract`-shaped payload (or any contract payload) so downstream unpacking of `getOwner()` succeeds.
3. Sign the transaction with a key present in permission id 2, and broadcast it (or include it in a block being validated).
4. `TransactionCapsule.checkPermission` → `WalletUtil.checkPermissionOperations` executes `operations.byteAt(contractType / 8)` with an out-of-range index, throwing an uncaught `IndexOutOfBoundsException` that is not caught by the surrounding `catch (SignatureException | PermissionException | SignatureFormatException e)` block in `validatePubSignature`, propagating up through `Manager.pushTransaction`/`Manager.processTransaction`.
