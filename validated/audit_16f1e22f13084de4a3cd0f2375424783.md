### Title
Front-runnable PDA squatting via `transfer_to_new_account_pda`'s unchecked `new_authority` allows griefing of a victim's canonical marginfi account index - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `TransferToNewAccountPda` instruction derives the destination PDA from `[MARGINFI_ACCOUNT_SEED, group, new_authority, account_index, third_party_id]`, the exact same seed formula used by `MarginfiAccountInitializePda`, but `new_authority` is an `UncheckedAccount` that never needs to sign and is fully attacker-controlled. Any unprivileged holder of any unrelated marginfi account can name a victim's public key as `new_authority` and pre-create (squat) the victim's deterministic PDA before the victim submits their own `marginfi_account_initialize_pda` (or `transfer_to_new_account_pda`) call for that same `(account_index, third_party_id)` pair — an on-chain analog of the reported FraxLend hash-collision/front-running class, where an unauthenticated party blocks a specific deterministic deployment slot belonging to another user.

### Finding Description
`MarginfiAccountInitializePda` derives its PDA as: [1](#0-0) 

`TransferToNewAccountPda` derives its `new_marginfi_account` PDA with the identical seed scheme, but crucially the `new_authority` field used in the seeds is unchecked and not required to sign: [2](#0-1) 

The only caller-side gating on `transfer_to_new_account_pda` concerns the caller's own `old_marginfi_account` (must not be frozen, in flashloan, in receivership, in order execution, or already migrated, and the caller must be an authorized signer of that old account) — there is no check at all tying `new_authority` to any signature or relationship with the caller: [3](#0-2) 

Because both instructions use `init` on the same deterministically derived address, whichever transaction lands first wins; the second fails with "already in use" (the same class of collision demonstrated in the report's `_deploySecond`/`_deployFirst` uniqueness checks). Any user Eve — using any spare, non-frozen marginfi account she owns — can pass `new_authority = Alice's pubkey` with the exact `account_index`/`third_party_id` Alice is known (or expected, e.g. index `0`) to use, and submit `transfer_to_new_account_pda` first. This pre-creates Alice's canonical PDA slot with attacker-influenced initial contents (`migrated_from`, `account_flags`, `indexer_flags`, and `lending_account` copied from Eve's `old_account`, per `initialize_migrated_account`): [4](#0-3) 

Once this happens, Alice's own subsequent `marginfi_account_initialize_pda` call for that `(account_index, third_party_id)` will always fail because the account already exists, permanently denying her that specific deterministic address.

### Impact Explanation
This is a permanent, unauthenticated-vs-unprivileged-user front-running/squatting primitive:
- Alice permanently loses the ability to ever initialize her canonical PDA account at a specific `(group, account_index, third_party_id)` combination — any integrator or CPI caller relying on a well-known deterministic index (e.g., a default index used by a third-party protocol integration, similar to the `PDA_FREE_THRESHOLD`/restricted `third_party_id` scheme referenced in `lib.rs`) is denied that address forever.
- The account that does get created at that address, while its `authority` correctly resolves to Alice, is initialized with attacker-chosen `migrated_from`, `account_flags`, and `indexer_flags` state copied from the attacker's throwaway `old_marginfi_account`, rather than a clean, expected-by-Alice initial state — an unauthorized state change on an address Alice expected to control the initialization of.
- This qualifies as a permanent lock/griefing of a specific account-derivation slot and an unauthorized state change, matching the accepted impact categories.

### Likelihood Explanation
Both `marginfi_account_initialize_pda` and `transfer_to_new_account_pda` are fully permissionless/unprivileged-user instructions (no admin gating). The attacker only needs any unfrozen marginfi account they legitimately own (trivially obtainable via `marginfi_account_initialize`/`marginfi_account_initialize_pda`) and knowledge of the victim's pubkey plus the target `account_index`/`third_party_id` — the latter is either observable from the victim's pending (mempool-visible) transaction or simply a commonly-used default value (e.g. `0`). The only cost to the attacker is the nominal `ACCOUNT_TRANSFER_FEE`.

### Recommendation
Require `new_authority` to co-sign `transfer_to_new_account_pda` (or otherwise cryptographically authorize the recipient, e.g., via a pre-signed message/nonce scheme) so that only the intended recipient can cause a PDA to be created and initialized in their own address space. Alternatively, disallow `TransferToNewAccountPda` and `MarginfiAccountInitializePda` from sharing the exact same PDA seed derivation domain so migrations cannot pre-empt a user's own direct initialization path, or add a distinct namespace/tag bit into the seeds for transfer-created accounts vs. self-initialized accounts.

### Proof of Concept
1. Alice intends to call `marginfi_account_initialize_pda(account_index = 0, third_party_id = None)`, expecting her account to be created at PDA `P = find_program_address([MARGINFI_ACCOUNT_SEED, group, Alice, 0u16, 0u16])` as shown in `MarginfiAccount::derive_pda`: [5](#0-4) 
2. Eve creates (or already owns) any unfrozen marginfi account `old_marginfi_account` with no active orders and no pending migration.
3. Eve submits `transfer_to_new_account_pda` with `authority = Eve`, `old_marginfi_account = Eve's account`, `new_authority = Alice's pubkey`, `account_index = 0`, `third_party_id = None`, targeting the same PDA `P`.
4. Eve's transaction lands first (front-run), successfully `init`-ing `P` via `TransferToNewAccountPda`'s `init` constraint at: [6](#0-5) 
5. Alice's `marginfi_account_initialize_pda` transaction, using the identical seeds/`init` constraint: [1](#0-0) 
now fails on-chain with an "already in use" account error, permanently denying Alice her canonical `account_index = 0` PDA slot, and the account at `P` instead contains state (`migrated_from`, `account_flags`, `indexer_flags`) copied from Eve's throwaway account rather than a clean initialization.

fn initialize_migrated_account(
    new_account: &mut MarginfiAccount,
    old_account: &MarginfiAccount,
    new_authority: Pubkey,
    current_timestamp: u64,
    old_account_key: Pubkey,
) {
    new_account.initialize(old_account.group, new_authority, current_timestamp);
    new_account.lending_account = old_account.lending_account;
    new_account.emissions_destination_account = old_account.emissions_destination_account;
    new_account.account_flags = old_account.account_flags;
    new_account.migrated_from = old_account_key;
    new_account.indexer_flags = old_account.indexer_flags;
    new_account.sync_indexer_flags();
}

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
