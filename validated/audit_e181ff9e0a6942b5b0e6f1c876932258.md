### Title
Unprivileged attacker can brick deposits, issuance and liquidations by filling an account's token list to `MAX_TOKENS_PER_USER` via dust transfers - (File: contracts/Pool.sol)

### Summary
`Pool` tracks, per account, the set of deposit tokens and debt tokens it holds in `depositTokensOfAccount` / `debtTokensOfAccount`, and enforces a hard cap of `MAX_TOKENS_PER_USER = 30` in `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0) . Both `DepositToken._mint` and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 [2](#0-1) [3](#0-2) . Because `deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` [4](#0-3)  and `transfer`/`transferFrom` have no consent check on the recipient, any EOA can push dust deposit-token balances onto a victim (or onto `feeCollector`/a known liquidator) until the account hits the 30-token cap. Every subsequent call that would add a *new* token to that account then reverts with `UserReachedMaxTokens` — matching the CVE bug class: a benign-looking input (an ordinary deposit/transfer, analogous to a benign response header) deterministically DoSes the victim's protocol interactions.

### Finding Description
The attack requires only public entry points and dust amounts of each underlying collateral:

1. For each registered `DepositToken` in the pool, the attacker calls `depositToken.deposit(1 wei, victim)` (or buys dust `msdX` and calls `msdX.transfer(victim, 1)`).
2. Each call lands in `Pool.addToDepositTokensOfAccount(victim)` [5](#0-4) , which adds the token until `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`, after which the modifier reverts.
3. Once the victim is at the cap:
   - `DepositToken.deposit` of any collateral the victim doesn't already hold reverts inside `_mint` → `addToDepositTokensOfAccount` [6](#0-5) .
   - `DebtToken.issue`/`mint` of any synthetic the victim doesn't already owe reverts inside `_mint` → `addToDebtTokensOfAccount` [7](#0-6) .
   - Any `transfer`/`transferFrom` of a deposit token the victim doesn't hold reverts.
   - Critically, `Pool.liquidate` calls `depositToken_.seize(account_, _msgSender, _toLiquidator)` and `seize(account_, feeCollector, _fee)` [8](#0-7) . `seize` routes through `_transfer`, so if the liquidator (or `feeCollector` for the fee seize, when `protocolLiquidationFee > 0`) is at the cap and doesn't already hold that deposit token, the entire `liquidate` reverts.

Reachability of the cap requires the pool to expose ≥30 distinct deposit+debt tokens usable for stuffing (the attacker cannot create new deposit tokens — `addDepositToken` is `onlyGovernor` [9](#0-8) ). For `feeCollector` specifically, only deposit-token slots are fillable, so the liquidation-wide DoS requires ≥30 registered deposit tokens. For an ordinary victim who already holds several deposit and debt positions, fewer attacker-filled slots are needed.

### Impact Explanation
- **Temporary freezing of funds / liquidation DoS**: while a liquidator's or `feeCollector`'s list is saturated, `liquidate` reverts unconditionally (`UserReachedMaxTokens`), so unhealthy positions cannot be liquidated through that path — bad debt can accrue while the block is maintained (the attacker can re-dust after each sweep/removal).
- **Position-management lockout**: a saturated victim cannot deposit any new collateral type nor issue any new synthetic type, blocking the normal "add collateral / refinance debt" response to a deteriorating position, leaving them exposed to liquidation.
- Removal is possible (the victim/liquidator can `transfer` out each dust token so its balance hits 0 and `removeFromDepositTokensOfAccount` fires [10](#0-9) ), but costs gas per token and can be griefed continuously, so the DoS is temporary but repeatable.

### Likelihood Explanation
The attack needs no privileged role, no oracle manipulation, and only dust amounts of already-supported collateral. Its feasibility is gated by the number of distinct deposit/debt tokens in the deployed pool (must approach 30 to fully saturate an account, or saturate `feeCollector` for the liquidation-wide variant) and by `depositFee` (which slightly raises dust cost). It is not a gas/unbounded-loop issue — the revert is an explicit cap check reached by ordinary transfers.

### Recommendation
- Revert `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` gracefully (skip instead of `UserReachedMaxTokens`) when the caller is a transfer/seize, or only enforce the cap on user-initiated `deposit`/`issue` rather than on inbound transfers and seizes.
- Alternatively, do not add tokens to an account's list for unsolicited `transfer`/`deposit(onBehalfOf)` dust (e.g., minimum amount threshold), so third parties cannot consume a victim's slots.
- Consider exempting `feeCollector` (and `seize` transfers generally) from the cap so fee collection and liquidations can never be bricked.

### Proof of Concept
Reproducible on the existing Hardhat fixture (pattern from `test/Pool.test.ts`):

```ts
// given: pool with deposit tokens [msdA, msdB, ..., msdN]
// attacker deposits 1 wei of each underlying on behalf of the victim
for (const dToken of allDepositTokens) {
  const underlying = await dToken.underlying()
  await IERC20(underlying).connect(attacker).approve(dToken.address, 1)
  await dToken.connect(attacker).deposit(1, victim.address) // fills victim's list
}
// victim's combined list is now at MAX_TOKENS_PER_USER (30)
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30)

// 1) victim cannot deposit a collateral type it doesn't already hold:
await expect(msdNew.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 2) victim cannot issue a new synthetic (addToDebtTokensOfAccount reverts):
await expect(newDebtToken.connect(victim).issue(parseEther('1'), victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3) if the saturated account is the feeCollector (protocolLiquidationFee > 0)
//    or the liquidator, liquidate() reverts at seize():
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, amountToRepay, msdMET.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
