Based on the code and existing regression tests, this is a confirmed, already-acknowledged bug in the codebase (tracked as [nearcore#12606](https://github.com/near/nearcore/issues/12606)), and the exact exploit sequence described in the question is validated by the codebase's own test suite.

### Title
Oversized receipt bypasses bandwidth accounting via mismatched clamp in `try_forward` - (`runtime/runtime/src/congestion_control.rs`)

### Summary
`try_forward` clamps the local `size` variable to `max_receipt_size` for the purpose of comparing against `forward_limit.size` and decrementing it, but pushes the original, unclamped `Receipt` into `outgoing_receipts`. Because receipts can be constructed above `max_receipt_size` via the `output_data_receivers`-after-validation gap (also #12606), an attacker can get an oversized receipt forwarded cross-shard while only debiting the bandwidth grant by `max_receipt_size` bytes, not the true size.

### Finding Description
`ReceiptSinkV2WithInfo::forward_or_buffer_receipt` computes `size = compute_receipt_size(&receipt)?` (the true borsh size) and calls `ReceiptSinkV2::try_forward` [1](#0-0) . Inside `try_forward`, a workaround for issue #12606 clamps the local `size` to `max_receipt_size` before the admission check and before decrementing `forward_limit.size`, but the original `receipt` (still full, unclamped size) is what gets pushed into `outgoing_receipts`: [2](#0-1) 

The oversized receipt itself can be produced by an unprivileged contract because `output_data_receivers` is appended to a receipt's `ActionReceipt` *after* the receipt already passed `ValidateReceiptMode::NewReceipt` size validation, i.e., a `promise_then`/`promise_return` DAG can be sized so that the final receipt is exactly at `max_receipt_size` before data receivers are added, and grows past the limit afterward without being re-validated. This exact scenario is already reproduced by the existing regression test `test_max_receipt_size_promise_return`, whose comment explicitly states: "Size of this receipt will be equal to `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and the receipt's size will go above `max_receipt_size`. The receipt should be rejected, but currently isn't because of a bug" [3](#0-2) , and the test asserts that such an oversized receipt does end up in the incoming receipt proofs of another shard via `assert_oversized_receipt_occurred` [4](#0-3) .

Once this oversized receipt reaches `forward_or_buffer_receipt`/`try_forward`, the clamp comment itself acknowledges the size-limit workaround exists specifically "to avoid receipts getting stuck" [5](#0-4) , but the accounting bug (pushing the unclamped receipt while debiting only the clamped amount from `forward_limit.size`) is a direct, unaddressed side effect of that same workaround, confirmed by reading the code as-is — there is no re-clamping or re-checking of the pushed receipt's actual size anywhere in this path.

### Impact Explanation
Every byte of `forward_limit.size` corresponds to bandwidth explicitly granted by the bandwidth scheduler for a specific shard-to-shard link (`bandwidth_scheduler_output.granted_bandwidth`) [6](#0-5) . Under-debiting this limit by `(true_size - max_receipt_size)` bytes per oversized receipt causes `outgoing_receipts`' true borsh size to exceed what was granted for that shard pair, meaning the receiving shard's `source_receipt_proofs` (and hence witness) carries more bytes than validators budgeted for that link. This maps to a "shard-halting panic" / chunk-witness-oversize category if repeatedly exploited to push cumulative outgoing bytes for a shard pair far beyond the granted bandwidth, risking witness size blow-up beyond what receiving validators expect.

### Likelihood Explanation
The precondition (crafting a promise DAG whose final receipt sits at `max_receipt_size` before `output_data_receivers` is appended) is fully within reach of an unprivileged account: it only requires deploying a WASM contract and issuing `FunctionCall` transactions using `promise_then`/`promise_return`, exactly as done by the existing test contract method `max_receipt_size_promise_return_method1` used in `test_max_receipt_size_promise_return`. No validator, node-operator, or privileged access is needed. The overhang per receipt is bounded (bounded by how much `output_data_receivers` can grow a receipt beyond `max_receipt_size`, which itself is limited by protocol limits on the number of data receivers), so a single receipt causes a bounded amount of under-debiting; repeating the attack across chunks compounds the effect but each attempt costs ordinary gas/transaction fees.

### Recommendation
In `try_forward`, decrement `forward_limit.size` (and account into `outgoing_receipts`' effective total) using the **actual**, unclamped receipt size rather than the workaround-clamped value, or alternatively reject/re-route (buffer or fail) receipts whose true size exceeds `max_receipt_size` instead of forwarding them with an under-reported cost. More fundamentally, fix the root cause described in #12606: enforce `ValidateReceiptMode::NewReceipt`-equivalent size validation on the receipt *after* `output_data_receivers` (and any other post-validation mutation) is finalized, so receipts above `max_receipt_size` cannot be created in the first place.

### Proof of Concept
1. Reuse `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` as the base to generate a receipt whose true borsh size exceeds `max_receipt_size` after `output_data_receivers` is appended.
2. Add instrumentation/assertions around `ReceiptSinkV2::try_forward` (or a targeted unit test in `runtime/runtime/src/congestion_control.rs`) that:
   - Constructs a `Receipt` with `compute_receipt_size(&receipt) > max_receipt_size`.
   - Calls `try_forward` with a `forward_limit.size == max_receipt_size` (i.e., exactly the grant for that shard).
   - Asserts `ReceiptForwarding::Forwarded` is returned (confirming the oversized receipt was let through).
   - Asserts that the receipt actually pushed into `outgoing_receipts` has `compute_receipt_size(...) > forward_limit.size` that was granted before the call, and that `forward_limit.size` after the call is decremented only by `max_receipt_size`, not the true size — demonstrating a mismatch between debited bandwidth and actual bytes placed into `outgoing_receipts`/`source_receipt_proofs`.

    fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

            Ok(ReceiptForwarding::Forwarded)
        } else {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "not forwarding buffered receipt");
            Ok(ReceiptForwarding::NotForwarded(receipt))
        }
    }

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
