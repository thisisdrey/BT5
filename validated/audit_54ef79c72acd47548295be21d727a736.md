### Title
Panic-Level Out-of-Bounds Slice Access in Reftable Block Parsing via Unvalidated `prefixLength`/`suffixLength` Varints - (File: internal/git/reftable/reftable.go)

### Summary
`Table.getRefsFromBlock` in `internal/git/reftable/reftable.go` decodes ref records from a reftable block by reading varint-encoded `prefixLength` and `suffixLength` values directly from file bytes and using them, unchecked, to slice both a running `prefix` string and the block byte slice `src`. Analogous to the `Zero.sol` issue where `zeroi` (derived from address comparison) was used to index into a `results` array without validating it stayed within the array's actual bounds, here `prefixLength` and `suffixLength` are used to index into `prefix` and `src` without validating they fit within the actual remaining data, causing a runtime panic (index/slice bounds out of range) instead of a graceful error.

### Finding Description
In `getRefsFromBlock`: [1](#0-0) 
the code computes `prefixLength` and `suffixLength` via `getVarInt`, which only validates that the *cursor* stays within `blockEnd`/`FullBlockSize` — it never validates that the decoded length values themselves are consistent with the size of `prefix` or the remaining bytes in `src`: [2](#0-1) 

The refname is then built as:
```go
refname := prefix[:prefixLength] + string(src[idx:idx+suffixLength])
```
If a corrupted or maliciously crafted reftable block encodes `prefixLength > len(prefix)`, `prefix[:prefixLength]` panics with "slice bounds out of range". Similarly, `src[idx:idx+suffixLength]` can panic if `suffixLength` exceeds the remaining buffer. This is the same bug class as the external report: an index/length derived from untrusted/parsed input is used to slice a fixed-size buffer without bounds validation, and rather than the code returning an error, the runtime panics.

The same class of unchecked-length slicing recurs later in the function for peeled/symref hash and target parsing: [3](#0-2) 
where `hashSize` and the symref `size` are used to slice `src` without checking they remain within `b.FullBlockSize`/`len(src)`.

### Impact Explanation
`GetReferences`/`getRefsFromBlock` is invoked whenever Gitaly reads references from a reftable-backed repository (`GetReferences` → `parseRefBlock` → `getRefsFromBlock`), a path reachable through ordinary ref-listing RPCs against repositories using the reftable ref backend. A corrupted or crafted `.ref` table file (e.g., arriving through repository import/fork, replication, or a repository whose reftable data becomes corrupted/attacker-influenced) can trigger a panic during ref parsing. Unless recovered further up the call stack, this crashes the serving goroutine/handler, resulting in denial of service for that RPC (and potentially the whole `gitaly` process if not recovered by gRPC panic-recovery middleware). This mirrors the reported impact: a Medium-severity DoS due to unchecked bounds usage rather than memory corruption or privilege escalation.

### Likelihood Explanation
Reftable data is nominally produced by Git tooling itself, so under normal operation the lengths are well-formed. However, since Gitaly's reftable reader performs no defense against malformed values, any bit corruption, non-git-created reftable file, or future feature that allows writing/importing arbitrary reftable content (e.g. repository import/fork/replication where Gitaly copies files provided by another node) can trigger the panic deterministically. Because there are no cross-checks against `len(prefix)` or `len(src)`, this is a low-effort-to-trigger, high-certainty crash once reachable, similar in spirit to the "50/50, unnoticed until triggered" characterization in the reference report, except here it requires a corrupted/malformed reftable rather than a purely probabilistic address ordering.

### Recommendation
- In `getRefsFromBlock`, validate `prefixLength <= len(prefix)` and `idx+suffixLength <= b.RestartStart` (or the relevant block boundary) before slicing, returning a descriptive error instead of allowing a panic.
- Similarly bound-check `idx+hashSize` and `idx+size` (symref case) against `b.FullBlockSize`/`len(src)` before slicing.
- Add fuzz/unit tests feeding truncated or adversarially large length fields to `getRefsFromBlock`/`parseRefBlock` to ensure errors are returned rather than panics.
- Consider wrapping reftable parsing with `recover()` at the RPC boundary as defense-in-depth, in addition to fixing bounds validation at the source.

### Proof of Concept
Construct (or corrupt) a reftable ref block such that the varint-encoded `prefixLength` byte for the second ref record exceeds the length of the first record's `refname` (used as `prefix` in the next iteration), or such that `suffixLength` causes `idx+suffixLength` to exceed the block's data range. Feed this file into `Table.GetReferences()` (e.g., by placing it as a repository's reftable and invoking a ref-listing RPC). The call to `prefix[:prefixLength]` or `src[idx:idx+suffixLength]` in `getRefsFromBlock` panics with "slice bounds out of range" instead of returning an error, crashing the handling goroutine.

```go
// getVarInt parses a variable int and increases the index.
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}
```
