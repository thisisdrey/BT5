### Title
Anti-replay window Check/Update race allows a captured data-plane packet to be decrypted and delivered twice - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the check-effects-interactions pattern incorrectly: the replay-window "check" (peek) is performed and the lock released, the expensive AEAD decrypt ("interaction") runs unlocked, and only afterward is the window "effects" update performed under a freshly re-acquired lock. This mirrors the reentrancy root cause in the referenced report (state committed only after an external/expensive interaction, with the lock/critical section split across it), letting two concurrent invocations for the same message counter both pass the check before either commits the update.

### Finding Description
`Decrypt` at [1](#0-0)  and `VerifyRelay` at [2](#0-1)  both follow this shape:

```
decryptLock.Lock(); window.Check(counter); decryptLock.Unlock()
... DecryptDanger(...) // unlocked, no mutation of window state
decryptLock.Lock(); window.Update(counter); decryptLock.Unlock()
```

`window.Check` is a non-mutating peek that only tells the caller "this counter has not yet been marked seen." The actual state mutation that prevents replay (`window.Update`) happens only after the AEAD open completes, and the lock is dropped for the entire decrypt operation in between. This is the same class of bug as the external-report finding: an "interaction" (here, the AEAD decrypt, analogous to the ETH `call` in `_distributeETHRewardsToUserForToken`) is interleaved between the read of state and the write of state, with no guard preventing another invocation from observing the pre-update state.

If two goroutines call `Decrypt` (or `VerifyRelay`) concurrently for the same `ConnectionState` with the same `messageCounter` — which happens whenever the identical ciphertext packet is delivered twice to the data plane, e.g. duplicated by network-level retransmission, or replayed by an on-path/off-path attacker who captured a legitimate packet and re-injects it while the original is still in flight to the same node — both calls can pass `window.Check` before either calls `window.Update`, because the lock is released between the two operations. Both then independently perform a successful `DecryptDanger` and both packets get delivered up the stack (`readOutsidePackets` → `handleOutsideMessagePacket`/TUN write, or for relayed messages, forwarded again via `handleOutsideRelayPacket`).

This is directly reachable pre-authentication in the sense required by the rules: it is exploitable by a network-level attacker who has no CA-signed certificate of their own — they only need to capture and duplicate/replay a UDP datagram belonging to an already-established tunnel between two legitimate certificate holders (a classic nonce/replay handling weakness), not to be a certificate holder or malicious peer themselves.

### Impact Explanation
Nebula's replay protection (`window.Check`/`window.Update`, `ReplayWindow` in [3](#0-2) ) is meant to guarantee that any given AEAD nonce/counter is accepted exactly once, which is a core AEAD security invariant (nonce reuse tolerance is what protects confidentiality/integrity guarantees at the protocol layer, and also prevents replay of application-layer traffic). A race that allows the same ciphertext to be decrypted and delivered twice:
- Breaks the "accept-once" replay-protection guarantee entirely for concurrently-delivered duplicates.
- Can be leveraged to replay an inside TUN packet (e.g., a command, a stateful protocol message) to the destination application twice, causing state poisoning at the application layer behind the tunnel.
- For relay traffic (`VerifyRelay` / `handleOutsideRelayPacket`), a duplicated/rebroadcast relay frame could be forwarded twice through the relay path, amplifying traffic or duplicating relayed application data.

The severity is bounded by the fact that decryption itself still requires a valid AEAD tag (so it is not a full authentication bypass), but it does defeat the anti-replay/duplicate-suppression mechanism that the protocol explicitly implements, which is exactly the property `window.Update` exists to enforce.

### Likelihood Explanation
Exploitation likelihood depends on Nebula actually processing the outside path with real concurrency for the same `HostInfo`. The codebase does dispatch outside UDP reads across multiple reader routines/queues (`q` parameter through `readOutsidePackets`/`handleOutsideMessagePacket`), and `decryptLock` in `ConnectionState` was clearly added because concurrent access to the same connection state is expected. Given that duplicate UDP delivery is common on real networks (retransmits, multipath, NIC-level duplication) and trivially reproducible by an attacker replaying a captured packet at the right time, the race window (an entire AEAD `Open` operation) is non-trivial in duration, making the race practically triggerable rather than a purely theoretical one. I was not able to fully confirm within this session whether all reader routines dispatch to fully independent goroutines processing the same `HostInfo` concurrently (this would need deeper tracing of `interface.go`'s `listenOut`/worker dispatch), so likelihood should be treated as "plausible, pending confirmation of the exact concurrency model" rather than fully proven.

### Recommendation
Hold `decryptLock` for the entire `Check` → `DecryptDanger` → `Update` sequence (or otherwise make the check-and-mark atomic), so no other goroutine can observe the "not yet seen" state for the same counter while a decrypt is in flight. Concretely, in `connection_state.go`:
- Acquire `decryptLock` once before `window.Check`, keep it held across `DecryptDanger`, and only release it after `window.Update` succeeds (or fold check+update into a single atomic operation performed only after a successful decrypt, e.g. a compare-and-set-style "reserve" done under the lock before decrypting, with rollback if decrypt fails).
- Apply the same fix to both `Decrypt` and `VerifyRelay`.

### Proof of Concept
Conceptual PoC (not executed, reasoning from code structure):
1. Establish a tunnel between node A and node B normally.
2. Capture one valid outside-path ciphertext packet `P` (header + AEAD ciphertext) sent from A to B, with message counter `c`.
3. From two different sources/sockets (or by rapidly re-sending `P` twice in quick succession, exploiting typical multi-queue UDP receive on B), deliver `P` to B twice, arranging for the two deliveries to be processed by B's data plane concurrently (e.g., two different `q` reader routines).
4. Both concurrent calls into `ConnectionState.Decrypt` for the same `HostInfo`/counter `c` call `cs.window.Check(l, c)` before either has called `cs.window.Update(l, c)`, because the lock guarding `Check` is released before `DecryptDanger` runs: [1](#0-0) .
5. Both goroutines successfully `DecryptDanger` the identical ciphertext and proceed to deliver the plaintext twice (e.g., write to TUN twice, or in the relay case, forward twice), even though Nebula's design intends exactly one acceptance per message counter.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
