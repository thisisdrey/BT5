Audit Report

## Title
`process_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`process_delivery_receipt` in the `outbound-queue-v2` pallet looks up a `PendingOrder` solely by `nonce` and unconditionally pays `order.fee` to the reward account whenever a `PendingOrder` exists for that nonce, without ever inspecting `DeliveryReceipt.success`. The Ethereum Gateway's `InboundMessageDispatched` event carries a `success: bool` field precisely because dispatch can fail on the Ethereum side, but the pallet treats every verified receipt (success or failure) identically.

## Finding Description
`DeliveryReceipt` is decoded from the Ethereum `InboundMessageDispatched` log and explicitly includes `pub success: bool` [1](#0-0) , populated directly from the decoded event's `success` field [2](#0-1) .

The public extrinsic `submit_delivery_receipt` verifies the proof via `T::Verifier::verify`, decodes the log into `DeliveryReceipt`, and forwards it to `process_delivery_receipt` [3](#0-2) . `process_delivery_receipt` checks only the gateway address match and that a `PendingOrder` exists for `receipt.nonce`; it then unconditionally pays `order.fee` via `T::RewardPayment::register_reward` and removes the order — `receipt.success` is never read or branched on [4](#0-3) .

This matches the required invariant class "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here the receipt's own success attestation is ignored before settlement/payout occurs.

## Impact Explanation
Any legitimate `InboundMessageDispatched` event reporting `success = false` (Ethereum-side dispatch failure, which the Gateway emits by protocol design regardless of outcome) still results in full payment of `order.fee` to the relayer and irreversible removal of the `PendingOrder`. This is a duplicate/incorrect settlement of bridge reward funds: relayer reward payout — misallocating value from the parachain's fee pool and permanently discarding the pending-order record that would otherwise support correct accounting for a failed delivery.

## Likelihood Explanation
`submit_delivery_receipt` is a public, signed extrinsic reachable by any unprivileged account [3](#0-2) . The only gates are the light-client proof verification and gateway address equality, both of which are satisfied by a legitimate, correctly-proven Ethereum event that simply reports `success = false`. No malicious peer, validator, prover collusion, or privileged action is required — a normal relayer forwarding a real failed-dispatch receipt triggers the bug deterministically and repeatably for every such nonce.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` when `success == true`. When `success == false`, still remove the `PendingOrder` to prevent indefinite state accumulation, but skip the payout, and emit a distinct event (e.g., `MessageDeliveryFailed`) instead of `MessageDelivered` for monitoring/accounting purposes.

## Proof of Concept
1. A message is enqueued, producing `PendingOrder { nonce, fee > 0, .. }` in `PendingOrders` via `do_process_message` [5](#0-4) .
2. The message is delivered to the Ethereum Gateway but its dispatch fails; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this event and calls `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds, `DeliveryReceipt::try_from` decodes `success: false` [6](#0-5) .
5. `process_delivery_receipt` matches the gateway, finds the `PendingOrder`, and pays `order.fee` regardless of `success`, then removes the order [7](#0-6) .
6. Result: reward paid and order settled despite a failed on-chain delivery — confirmable by adding a unit test that constructs an event proof with `success = false` and asserting `RewardPayment::register_reward` is still invoked and `PendingOrders::get(nonce)` becomes `None`.

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
