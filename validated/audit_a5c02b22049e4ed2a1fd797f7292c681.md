## Timing side-channel on RPC auth-token comparison enables secret recovery and unauthorized writes - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
Several Stacks node RPC endpoints gate privileged/write-capable operations behind a shared secret (`connection_options.auth_token`) supplied via the `authorization` HTTP header. The comparison of the client-supplied header against the configured secret is done with Rust's built-in, non-constant-time `!=` operator on `String`/`str`, which short-circuits on the first differing byte (and on length). This is the same bug class as CVE-2018-6596 (Django-Anymail `WEBHOOK_AUTHORIZATION` timing attack): a remote, unauthenticated attacker can use repeated timed requests to incrementally recover the secret token byte-by-byte, then use it to forge authorized requests.

### Finding Description
The `auth_token` is intended to authenticate privileged requests to the node's RPC interface, as documented in `stackslib/src/config/mod.rs` (`auth_token: Option<String>` — "used in the `Authorization` header ... secures the communication channel between this node and a connected `stacks-signer` instance ... also used to authenticate requests to `/v2/blocks?broadcast=1`"). [1](#0-0) 

Every handler that checks this secret performs the comparison identically, with a plain, variable-time equality check:

```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

This exact pattern appears in multiple RPC request handlers reachable pre-auth over the network:
- `RPCNakamotoBlockReplayRequestHandler::try_parse_request` (`/v3/blocks/replay/:block_id`) [2](#0-1) 
- `RPCNakamotoBlockSimulateRequestHandler::try_parse_request` (`/v3/blocks/simulate/:block_id`) [3](#0-2) 
- `RPCFastCallReadOnlyRequestHandler::try_parse_request` (`/v3/contracts/fast-call-read/...`) [4](#0-3) 
- `RPCBlockProposalRequestHandler::try_parse_request` (`/v3/block_proposal`) [5](#0-4) 
- `RPCTransactionSimulateRequestHandler::try_parse_request` (`/v3/transactions/simulate`) [6](#0-5) 
- `RPCPostBlockRequestHandler::try_parse_request` (`/v2/blocks?broadcast=1`) [7](#0-6) 

Rust's `str`/`String` `PartialEq` implementation compares lengths first and then does a byte-wise `memcmp`-style comparison that returns as soon as a mismatch is found. This means the wall-clock time of the `auth_header != password` check leaks information about how many leading bytes of the attacker-supplied header match the true secret. By sending many requests and measuring response latency for the authorization check specifically (isolatable because it happens before any other expensive parsing/DB work in most of these handlers, e.g. before block-ID decoding or body parsing), a remote attacker can incrementally recover the `auth_token` one byte at a time — exactly the vulnerability class described in the external report for Django-Anymail's webhook secret check.

### Impact Explanation
Recovering the `auth_token` allows a remote, unauthenticated attacker to submit authenticated requests to security-sensitive endpoints, including:
- `/v3/block_proposal` — feeds block proposals into the signer's validation pipeline.
- `/v2/blocks?broadcast=1` — authenticates block broadcast requests.
- `/v3/blocks/simulate`, `/v3/transactions/simulate`, `/v3/contracts/fast-call-read` — trigger compute on the node under an authenticated identity.

This constitutes unauthorized access to authentication-gated write/compute endpoints on the node, matching the Critical-tier impact category ("unauthenticated/unauthorized write to state ... auth bypass").

### Likelihood Explanation
Exploitability depends on how much timing signal is present in this specific comparison relative to network jitter. Because the check happens early in `try_parse_request` (before heavier parsing for most of these handlers), the signal is not diluted by other significant work, which improves feasibility relative to a typical noisy network timing attack, though many trials/statistical averaging would still be required in practice. The bug is unambiguously present as a pattern (non-constant-time secret comparison) across every one of these handlers, matching the reported bug class precisely; only the practical difficulty of extracting a clean timing signal over a real network is uncertain.

### Recommendation
Replace `auth_header != password` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or Rust's `ring::constant_time::verify_slices_are_equal`) across all affected handlers: `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`, `txsimulate.rs`, and `postblock_v3.rs`. Additionally, ensure the length check itself does not leak length information trivially (constant-time libraries typically handle fixed-length comparisons; consider hashing both sides with a fixed-size MAC/HMAC before comparing to fully normalize timing).

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote unauthenticated client, repeatedly send POST requests to `/v3/block_proposal` (or any of the listed endpoints) with an `authorization` header guess, e.g. incrementally testing each byte position: `"A", "B", ..., "Aa", "Ab", ...` etc.
3. Measure round-trip time for the 401 rejection at `auth_header != password` (`stackslib/src/net/api/postblock_proposal.rs:1142`) across many trials to reduce jitter noise.
4. Because the comparison short-circuits at the first mismatching byte, correct-prefix guesses take measurably (statistically) longer than incorrect-prefix guesses, allowing incremental full recovery of `auth_token`.
