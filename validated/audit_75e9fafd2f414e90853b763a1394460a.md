## Finding Vulnerability class match: predictable/front-runnable sequential exchange IDs in `ExchangeCreateActuator`/`ExchangeTransactionActuator`

The Notional report's root cause — a purely sequential, content-independent ID that lets an attacker front-run and substitute the object a victim's transaction operates on — has a direct analog in java-tron's on-chain Bancor-style exchange market, which is reachable by any unprivileged account (no witness/SR/committee privilege required, unlike the `ProposalCreate`/`ProposalApprove` actuators which do require the caller to be a witness and are therefore out of scope).

### Title
Sequential, content-unbound `exchange_id` allows front-running substitution of exchange pairs, causing victims' trades to execute against attacker-controlled token pairs - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java)

### Summary
`ExchangeCreateActuator` assigns exchange IDs purely by incrementing `DynamicPropertiesStore.getLatestExchangeNum()`, with no binding between the ID and the exchange's actual token pair/content. `ExchangeTransactionActuator` later trusts whatever exchange currently occupies that ID when a user submits a trade referencing an `exchange_id`.

### Finding Description
In `ExchangeCreateActuator.execute`, the new exchange ID is computed as a simple counter increment, with no hash of the token pair or creator baked into the identifier: [1](#0-0) 

That ID is then persisted and the counter advanced: [2](#0-1) 

Creating an exchange requires only that the caller is an existing account with sufficient balance — no witness/committee privilege is checked, unlike `ProposalCreateActuator` which requires `witnessStore.has(ownerAddress)`: [3](#0-2) 

When a user later trades, `ExchangeTransactionActuator` looks up the exchange purely by the numeric `exchange_id` supplied in the contract, and validates only that the supplied `token_id` matches one of the two tokens *currently* stored under that ID — it never verifies that the exchange still corresponds to the pair the caller originally intended to trade against: [4](#0-3) 

The `expected` field only protects against price slippage for the chosen token pair, not against the pair itself being swapped out: [5](#0-4) 

### Impact Explanation
Exactly as in the Sherlock finding, an unprivileged attacker can watch the mempool for a pending `ExchangeCreateContract` (e.g., Bob creating exchange #N for TRX/USDT) and a subsequent `ExchangeTransactionContract` from a victim that references the *expected* future ID N (submitted optimistically before Bob's `ExchangeCreateContract` is confirmed, or resubmitted after a reorg). The attacker front-runs with their own `ExchangeCreateContract` (paying higher bandwidth/energy price to be prioritized), claiming ID N first but with a different token pair (e.g., TRX/WORTHLESS_TOKEN created by the attacker). Bob's original create transaction then either fails or claims ID N+1. The victim's `ExchangeTransactionContract{exchange_id=N, token_id=TRX}` still validates (TRX matches `firstTokenID` of the attacker's exchange) and executes against the attacker's malicious pair, causing the victim to receive `anotherTokenQuant` of the attacker's worthless token instead of USDT — a direct, irreversible loss of value for the victim, i.e., unauthorized draining/misdirection of the victim's TRX/asset balance.

### Likelihood Explanation
Any account holder can call `ExchangeCreateContract` and `ExchangeTransactionContract` via the standard transaction broadcast path (HTTP/gRPC `Wallet`/`RpcApiService` endpoints), with no special role required. The attack only requires observing the victim's pending transaction (mempool visibility) and paying a competitive fee/bandwidth to be included first — a standard front-running capability available to any network participant, matching the same likelihood profile as the original report.

### Recommendation
Bind the exchange identity to its content when validating trades: require callers to pass (and validate against) the expected `firstTokenId`/`secondTokenId` (or a commitment/hash of them) alongside `exchange_id` in `ExchangeTransactionContract`, and reject the trade in `ExchangeTransactionActuator.validate()` if the on-chain exchange's stored token pair does not match the caller's expectation. Alternatively, derive `exchange_id` deterministically from `(creator address, first_token_id, second_token_id, nonce)` so an attacker cannot cheaply produce a colliding ID with different backing tokens.

### Proof of Concept
1. Bob broadcasts `ExchangeCreateContract{owner=Bob, firstToken=TRX, secondToken=USDT}`, expecting to receive `exchange_id = N` (current `LatestExchangeNum + 1`).
2. Alice, anticipating exchange `N`, broadcasts `ExchangeTransactionContract{owner=Alice, exchange_id=N, token_id=TRX, quant=X}` intending to swap TRX for USDT.
3. Attacker observes both pending transactions, and broadcasts `ExchangeCreateContract{owner=Attacker, firstToken=TRX, secondToken=WORTHLESS}` with a higher fee/bandwidth priority, causing it to be included before Bob's transaction and claim `exchange_id = N` (see ID assignment at `ExchangeCreateActuator.java:78-79`).
4. Alice's `ExchangeTransactionContract{exchange_id=N, token_id=TRX}` still passes validation in `ExchangeTransactionActuator.validate()` (TRX matches `firstTokenID` of the attacker's exchange at `ExchangeTransactionActuator.java:182-184`) and executes, crediting Alice with `WORTHLESS` tokens instead of USDT, while the attacker's exchange retains Alice's TRX.
5. Bob's original `ExchangeCreateContract` now creates exchange `N+1` instead, completing the ID/content mismatch.
