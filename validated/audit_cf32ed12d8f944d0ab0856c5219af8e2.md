### Title
Terminal relay establishment trusts attacker-controlled `RelayFromAddr` instead of the authenticated peer's own VPN address, enabling traffic hijack of a third-party overlay IP - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` binds a relay's `PeerAddr` to the `RelayFromAddr` field taken directly from the `NebulaControl` message body, rather than to `h.vpnAddrs[0]`, the VPN address cryptographically bound to the already-authenticated tunnel peer `h` that actually sent the control message. This is the same root-cause pattern as the referenced Connext finding: a function that should act "on behalf of" the caller instead trusts a caller-supplied address parameter.

### Finding Description
In `relay_manager.go`, `HandleControlMsg` dispatches `CreateRelayRequest` messages to `handleCreateRelayRequest(v, h, f, msg)`, where `h` is the `*HostInfo` of the tunnel that delivered the (encrypted, authenticated) control message: [1](#0-0) 

Inside `handleCreateRelayRequest`, the "from" address is decoded purely from the message payload:

```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
``` [2](#0-1) 

When the local node is the intended terminal target of the relay (`f.myVpnAddrsTable.Contains(target)`), the code establishes relay state keyed on `from`, and adds it directly to `h.relayState`, without ever checking that `from == h.vpnAddrs[0]`:

```go
if f.myVpnAddrsTable.Contains(target) {
    existingRelay, ok := h.relayState.QueryRelayForByIp(from)
    ...
    } else {
        _, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
        ...
``` [3](#0-2) 

`AddRelay` unconditionally records `PeerAddr: vpnIp` (i.e., the attacker-chosen `from`) in `h.relayState.relayForByAddr[from]`: [4](#0-3) 

Only `target` (the relay's own address) is validated against `f.myVpnAddrsTable`; `from` — which represents "who this tunnel `h` is allowed to carry traffic for" — is never checked against `h`'s certificate-derived `vpnAddrs`. This is directly analogous to `addLiquidity(router, ...)` trusting a `router` parameter instead of `msg.sender`: here the relay trusts a `RelayFromAddr` parameter instead of binding to `h`'s verified identity (`h.vpnAddrs[0]`).

The consequence surfaces at forwarding time: when a `ForwardingType` relay receives traffic destined for `relay.PeerAddr` (i.e., the forged `from`), it looks up who is authorized to receive that traffic via `f.hostMap.QueryVpnAddrsRelayFor(hostinfo.vpnAddrs, relay.PeerAddr)` and forwards decrypted-relay-frame payloads to whichever `HostInfo` holds a relay entry keyed by that address: [5](#0-4) 

Because the terminal relay entry created above is keyed by the attacker-supplied `from` rather than the tunnel's real identity, a malicious peer `h` (any node holding a normal, validly-certified tunnel) can claim `RelayFromAddr` = a victim's real VPN address, causing the relay to bind future traffic addressed to that victim to attacker `h`'s tunnel.

### Impact Explanation
A fully authenticated peer (holding a valid CA-signed cert and completed Noise handshake — no CA-signed cert is required to be forged, only normal peer trust is abused) can hijack packets destined for another host's overlay VPN address by claiming that address as its own `RelayFromAddr` when requesting to be a relay target. This results in remote traffic redirection: legitimate traffic meant for the victim's `PeerAddr` can be routed to the attacker instead, a concrete instance of "remote state poisoning" of the hostmap/relay routing table by an authenticated-but-unauthorized peer.

### Likelihood Explanation
Any peer that can complete a normal handshake and send `Control`-type messages (which any connected peer can, once a tunnel is up) can trigger this path by sending a crafted `CreateRelayRequest` with a `RelayFromAddr` that does not match its own certificate address. No special privileges beyond being a legitimate but adversarial member of the mesh are required, and no additional handshake or cert forgery is needed—only manipulation of a control-plane message field.

### Recommendation
In `handleCreateRelayRequest` (and its symmetric handling in `handleCreateRelayResponse`/`EstablishRelay`), validate that `from` (`RelayFromAddr`) matches one of `h.vpnAddrs` (the certificate-verified addresses of the peer that actually sent the message) before calling `AddRelay`/binding relay state to that address. Reject the request (log and drop) if `from` is not contained in `h.vpnAddrs`, mirroring how `target` is already validated against `f.myVpnAddrsTable`.

### Proof of Concept
1. Establish a normal Nebula tunnel between attacker node `A` (valid cert for VPN address `A_ip`) and victim relay-capable node `R` (`relay.am_relay=true`), where `R` is also the terminal for the true victim `V_ip`.
2. From `A`, send a `NebulaControl` `CreateRelayRequest` over the established tunnel with `RelayFromAddr = V_ip` (the real victim's overlay address, not `A_ip`) and `RelayToAddr = R`'s own VPN address.
3. `R.handleCreateRelayRequest` sees `target == R` is itself, and — without checking `from == h.vpnAddrs[0]` — calls `AddRelay(rm.l, h /* = A's hostinfo */, f.hostMap, V_ip, ...)`, inserting `A`'s HostInfo relay state keyed by `V_ip`.
4. Any subsequent `ForwardingType` relay traffic on `R` destined for `V_ip` (`relay.PeerAddr == V_ip`) is now looked up via `hostMap.QueryVpnAddrsRelayFor` and delivered to `A`'s tunnel instead of the legitimate `V`, achieving traffic hijack of `V_ip`'s relayed data. [6](#0-5)

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}
