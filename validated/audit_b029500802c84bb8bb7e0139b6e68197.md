### Title
Unauthenticated attacker can permanently fill a victim's per-account token list via dust `deposit(onBehalfOf)`/`transfer`, DoS-ing all future deposits and borrows — (`contracts/Pool.sol`)

### Summary
`Pool` tracks each account's deposit and debt tokens in `MappedEnumerableSet` lists capped by `MAX_TOKENS_PER_USER = 30`. Any `DepositToken._mint`/`_transfer` to an address with a zero balance calls `pool.addToDepositTokensOfAccount(recipient_)`, which reverts once the combined list hits 30. Because `deposit()` accepts an arbitrary `onBehalfOf_` beneficiary and `transfer()` is permissionless, an unprivileged attacker can stuff a victim's list with dust amounts of every registered deposit token, after which the victim cannot mint any new deposit-token type (deposits revert) and cannot open a debt position in a new synthetic (`addToDebtTokensOfAccount` reverts inside `DebtToken` issuance) — a direct analog of the SAN-stuffing DoS: unauthenticated, repeated additions to a bounded per-victim list until the resource is unusable.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce `onlyIfAdditionWillNotReachMaxTokens`, reverting with `UserReachedMaxTokens` when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` (`contracts/Pool.sol:143-148, 204-208`).
- `DepositToken._mint` adds the token to the recipient's list whenever the prior balance was 0 (`contracts/DepositToken.sol:485-488`), and `deposit(amount_, onBehalfOf_)` lets anyone mint dust to an arbitrary victim (`contracts/DepositToken.sol:211-237`).
- `DepositToken._transfer` does the same on plain `transfer`/`transferFrom` (`contracts/DepositToken.sol:517-520`); `seize` during liquidation also routes through `_transfer`.
- A token is only removed when the holder's balance returns to 0 (`_burn`/`_transfer` at `contracts/DepositToken.sol:460-462, 523-525`). If the victim has outstanding debt, `unlockedBalanceOf` may return 0 (`contracts/DepositToken.sol:383-398`), so the victim cannot even transfer the dust out — the DoS is sticky.

### Impact Explanation
Temporary/permanent freezing of protocol functionality for the victim: with the list full, every `deposit` of a collateral type the victim doesn't already hold reverts, and every `DebtToken.issue` of a new synthetic reverts (the `addToDebtTokensOfAccount` call inside minting fails), so the victim cannot borrow at all. If the victim's dust balances are locked by existing debt (`_revertIfLocked` blocks `transfer`/`withdraw`), they cannot self-clean the list, making the freeze persist for the life of the debt. Existing collateral can't be seized by a liquidator into a new token either if it would push the liquidator over the cap, and a victim under water cannot add collateral of a new type to recover health — worsening bad-debt outcomes for the protocol.

### Likelihood Explanation
Fully unprivileged and cheap: the attacker needs only dust amounts of each underlying (or can chain `deposit` dust `onBehalfOf` the victim across all ~dozen registered deposit tokens, plus `transfer` of attacker-held msdTOKENs). No privileged role, oracle manipulation, or governance action is required — exactly the K3s pattern of an unauthenticated party forcing entries into a victim-scoped bounded list. The only mitigation is that a debt-free victim can transfer the dust away, but a victim with any debt may be unable to.

### Recommendation
Decouple list membership from the revert path: (a) make `addTo*TokensOfAccount` calls tolerant — e.g. skip adding instead of reverting when at cap, and have `debtPositionOf`/collateral calculations iterate token balances directly rather than relying solely on the enumerable list; or (b) restrict who can add to another account's list (only self/`onBehalfOf == msg.sender` deposits, or an opt-in flag); or (c) allow holders to "eject" unwanted tokens via a `removeFromDepositTokensOfAccount`-style escape that ignores `_revertIfLocked` when transferring dust to a burn/treasury address.

### Proof of Concept
Hardhat fork sketch (against deployed Pool/DepositTokens):
```ts
// attacker: for each registered deposit token d_i
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying())
  await underlying.approve(dt.address, DUST)
  // fills victim's depositTokensOfAccount without victim consent
  await dt.deposit(DUST, victim.address)
}
// after 30 distinct tokens:
await expect(dtNew.deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(pool.issue(synth, victim.address, amount))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
The revert propagates from `DepositToken._mint` → `pool.addToDepositTokensOfAccount` and from `DebtToken` issuance → `pool.addToDebtTokensOfAccount`, matching the guard at `contracts/Pool.sol:143-148`.
