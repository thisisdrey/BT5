### Title
Unbounded CreateRepositoryFromBundle data stream allows disk-exhaustion DoS - ([File: internal/gitaly/service/repository/create_repository_from_bundle.go])

### Summary
`CreateRepositoryFromBundle` streams client-supplied `Data` chunks directly into `bundleReader`, which is passed to `CloneBundle` → `createTempBundle`, whose `io.Copy` writes every byte received to a temp file on disk with no maximum size check anywhere in the path. An attacker who can invoke this RPC (e.g., via a repository import/fork flow) can send an effectively unbounded stream of `Data` frames and fill the shared storage before git ever validates the bundle content.

### Finding Description
The handler reads the first request, then wraps subsequent `stream.Recv()` calls in a `streamio.NewReader` closure with no byte-count tracking or limit: [1](#0-0) 
This reader is handed to `s.localRepoFactory.Build(repo).CloneBundle(ctx, bundleReader)`: [2](#0-1) 
`CloneBundle` calls `createTempBundle`, which does a plain `io.Copy(file, reader)` with no size cap, writing everything from the stream to `bundlePath` on the storage's temp directory before `git-clone` (which performs bundle validation) is even invoked: [3](#0-2) 
No request-size, gRPC message-size, or total-stream-size limit was found configured for this service (`MaxRecvMsgSize`/`MaxCallRecvMsgSize` are not set anywhere in the repo), so the attacker's `Data` chunks can be repeated indefinitely across the gRPC stream. Because `createTempBundle` uses `tempdir.New(ctx, repo.GetStorageName(), ...)`, the temp file lands on the same physical storage that hosts other tenants' repositories, so exhausting it denies service to every repository on that storage, not just the attacker's own.

### Impact Explanation
This is a storage-wide denial of service: an attacker with only repository-creation/import capability (a normal, unprivileged GitLab user permission) can drive disk usage on a shared Gitaly storage to 100%, which will cause write failures (pushes, commits, imports, WAL/transaction writes) for all repositories co-located on that storage. This matches GitLab's bounty "Denial of Service" impact class for a Gitaly RPC handler lacking resource bounding.

### Likelihood Explanation
The only precondition is the ability to reach the `CreateRepositoryFromBundle` RPC with attacker-controlled repository creation parameters and to stream arbitrary bytes as `Data` — both are available to an ordinary authenticated user through project import/bundle-based repository creation flows. The attack is trivially repeatable and requires no race conditions or special timing, only sustained upload bandwidth.

### Recommendation
Enforce a maximum cumulative size while reading `Data` chunks in the `bundleReader` closure (e.g., track bytes read and abort once a configured limit, such as the max blob/bundle size, is exceeded), and/or wrap the `io.Copy` in `createTempBundle` with an `io.LimitReader` sized to a sane maximum bundle size. Additionally consider checking available free space on the target storage before/while streaming and aborting early if a threshold is crossed.

### Proof of Concept
```go
func TestCreateRepositoryFromBundle_UnboundedDataDoS(t *testing.T) {
    cfg, repoClient := setupRepositoryService(t) // existing test harness
    ctx := testhelper.Context(t)

    stream, err := repoClient.CreateRepositoryFromBundle(ctx)
    require.NoError(t, err)

    repo := &gitalypb.Repository{StorageName: cfg.Storages[0].Name, RelativePath: "attacker-repo.git"}
    require.NoError(t, stream.Send(&gitalypb.CreateRepositoryFromBundleRequest{Repository: repo}))

    chunk := make([]byte, 4*1024*1024) // 4MB chunk, within any per-message gRPC default limit
    // Send far more data than any legitimate bundle would require, e.g. hundreds of GB worth of chunks,
    // and observe disk usage on cfg.Storages[0].Path grow unbounded until ENOSPC or storage-wide failure.
    for i := 0; i < N; i++ {
        require.NoError(t, stream.Send(&gitalypb.CreateRepositoryFromBundleRequest{Data: chunk}))
    }
    // Assert: server should reject once a maximum bundle size threshold is exceeded (currently it does not).
}
```
Expected (fixed) behavior: the server aborts the stream with an `InvalidArgument`/`ResourceExhausted` error once a configured maximum size is exceeded, instead of writing unbounded data via `io.Copy` in `createTempBundle` (`internal/git/localrepo/bundle.go:217`).

func (repo *Repo) createTempBundle(ctx context.Context, reader io.Reader) (bundlPath string, cleanup func(), returnErr error) {
	tmpDir, cleanup, err := tempdir.New(ctx, repo.GetStorageName(), repo.logger, repo.locator)
	if err != nil {
		return "", nil, fmt.Errorf("create temp bundle: %w", err)
	}

	bundlePath := filepath.Join(tmpDir.Path(), "repo.bundle")

	file, err := os.Create(bundlePath)
	if err != nil {
		cleanup() // Clean up if we fail after creating the temp directory
		return "", nil, fmt.Errorf("create temp bundle: %w", err)
	}
	defer func() {
		if err := file.Close(); err != nil && returnErr == nil {
			returnErr = fmt.Errorf("create temp bundle: %w", err)
		}
	}()

	if _, err = io.Copy(file, reader); err != nil {
		cleanup() // Clean up if we fail after creating the temp directory
		return "", nil, fmt.Errorf("create temp bundle: %w", err)
	}

	return bundlePath, cleanup, nil
}
