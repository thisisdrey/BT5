Audit Report

## Title
`harvest_rewards` never persists the recomputed pool checkpoint, letting anyone repeatedly double-count elapsed blocks and over-mint reward-per-token for a pool - (File: substrate/frame/asset-rewards/src/lib.rs)

## Summary
`harvest_rewards` computes an updated `pool_info` (with advanced `last_update_block` and `reward_per_token_stored`) via `update_pool_and_staker_rewards`, but unlike `stake` and `unstake`, it never calls `Pools::<T>::insert` to persist this update back to storage. As a result, the pool-level reward checkpoint remains stale after every harvest, causing subsequent calls to re-derive rewards over already-paid block ranges and over-distribute the pool's `reward_asset_id`.

## Finding Description
`update_pool_and_staker_rewards` ( [1](#0-0) ) calls `reward_per_token` ( [2](#0-1) ), which derives the pool's accumulated reward-per-token from `pool_info.last_update_block` and `pool_info.reward_per_token_stored`, then returns a new `pool_info` via `update_pool_rewards` that advances `last_update_block` to the current block. `stake` persists this via `Pools::<T>::insert(pool_id, pool_info)` at [3](#0-2) , and `unstake` does the same at [4](#0-3) . `harvest_rewards`, however, computes the identical updated `pool_info` at [5](#0-4)  and only uses it locally to authorize the `T::Assets::transfer` at [6](#0-5) ; it never writes it back with `Pools::<T>::insert`, only updating `PoolStakers` at [7](#0-6) . Consequently, `Pools::<T>::get(pool_id).last_update_block` and `.reward_per_token_stored` remain at their pre-harvest values in storage. The next call that reads the pool (another `stake`, `unstake`, or `harvest_rewards`, by any staker) recomputes `reward_per_token` over the interval since the *old* `last_update_block`, re-including the block range that was already paid out during the prior harvest, and adds it into `reward_per_token_stored` again.

## Impact Explanation
This allows an unprivileged staker to cause the pool to over-distribute its `reward_asset_id` beyond what `reward_rate_per_block × elapsed blocks` should allow, since rewards are paid via `T::Assets::transfer` from the pool's own account (`pool_info.account`). Repeated harvesting interleaved with other stake/unstake/harvest activity duplicates settlement of the same block interval across multiple reward-per-token accumulations, draining the pool's reward-asset balance faster than intended and starving later legitimate claimants — a duplicate settlement/over-mint of pool funds matching the impact gate's "theft or unbacked mint or unlock, duplicate settlement or payout" category.

## Likelihood Explanation
High. `harvest_rewards` is a normal public extrinsic callable by any staker with a nonzero stake once rewards have accrued; no privileged role, governance action, or adversarial timing is required — ordinary interleaving of `stake`/`unstake`/`harvest_rewards` by independent participants is sufficient to trigger repeated re-crediting of the same block window.

## Recommendation
Persist the pool-level checkpoint in `harvest_rewards` exactly as `stake`/`unstake` do: after computing `(pool_info, staker_info) = Self::update_pool_and_staker_rewards(...)`, call `Pools::<T>::insert(pool_id, pool_info)` so `last_update_block` and `reward_per_token_stored` are advanced in storage before/along with the transfer and `PoolStakers` update.

## Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R`, funded with reward tokens.
2. Staker A stakes `X` tokens at block `M`.
3. At block `N`, Staker A calls `harvest_rewards`; `update_pool_and_staker_rewards` computes `reward_per_token` using elapsed `N - M` and pays Staker A, updating `PoolStakers`, but `Pools::<T>::get(pool_id)` still shows `last_update_block = M` since no `Pools::insert` occurs in `harvest_rewards`.
4. At block `N2 > N`, Staker B calls `stake`; this reads the stale `Pools` entry and recomputes `reward_per_token` over `N2 - M` (not `N2 - N`), re-crediting the `[M, N]` interval already paid to Staker A into the pool-wide `reward_per_token_stored`.
5. Sum of all stakers' eventually harvestable rewards now exceeds `R × (N2 - M)`, over-draining the pool's reward-asset balance relative to what `reward_rate_per_block` was intended to emit — reproducible as a Rust unit test asserting `Pools::<T>::get(pool_id).last_update_block` is unchanged immediately after a `harvest_rewards` call, followed by a second `stake`/`unstake` call showing inflated `reward_per_token_stored` relative to the true elapsed-time formula.
