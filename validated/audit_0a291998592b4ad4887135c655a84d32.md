### Title
Witness rewards credited for a cycle with zero total votes are permanently unclaimable ("locked forever") - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java, chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
java-tron's DPoS reward accounting (`MortgageService`, `DelegationStore`, `RewardViCalService`) credits block/standby-witness rewards to a per-cycle, per-witness pool via `addReward`, then splits that pool among voters proportionally to their vote weight for that cycle, using either the legacy `totalVote`-ratio method or the newer cumulative "Vi" (value-per-share) method. Both methods explicitly special-case `totalVote == 0` by simply skipping distribution rather than deferring/rolling the reward forward to a future period with actual voters — the same root-cause pattern as the Zivoe `ZivoeRewards`/`ZivoeRewardsVesting` bug, where reward accrued during a zero-staker window is permanently lost instead of preserved for the next staker.

### Finding Description
When a witness earns a block reward or transaction-fee reward, `MortgageService.payReward` deposits it into the current cycle's reward pool for that witness: [1](#0-0) 

This crediting happens unconditionally for the current cycle regardless of whether the witness currently has any votes recorded for that cycle. Later, distribution to voters for a given cycle is computed by `computeReward(long cycle, List<Pair<byte[], Long>> votes)` (legacy path), which explicitly `continue`s (skips) whenever `totalVote == 0`, discarding that cycle's reward for the affected voter/witness pair rather than rolling it forward: [2](#0-1) 

The newer cumulative-rate ("Vi") algorithm has the same characteristic: `DelegationStore.accumulateWitnessVi` (and the equivalent in `RewardViCalService`) only accumulates a delta into the cumulative Vi value when both `reward != 0` and `voteCount != 0`; when `voteCount == 0`, it just forwards the previous Vi value unchanged, meaning any reward recorded for that cycle (via `getReward(cycle, address)`) is never converted into distributable Vi delta and is never paid to anyone, present or future: [3](#0-2) 

This accumulation is invoked automatically for every witness during `MaintenanceManager.doMaintenance`: [4](#0-3) 

Because vote totals for a witness can be driven to zero purely through unprivileged user actions (any voter can withdraw/change votes via the vote-related actuators/TVM `voteWitness`/`withdrawReward` opcodes reachable from `VoteRewardUtil.withdrawReward`), it is possible for a witness to have accrued a block reward within a cycle, and then have all voters clear their votes for that witness before the maintenance boundary that finalizes the cycle's vote totals. When that happens, the reward recorded via `addReward`/`delegationStore.getReward(cycle, address)` is never distributed to any voter, either under the old ratio-based algorithm (division and comparison against `totalVote == 0`, `MortgageService.java:180`) or the new Vi-based algorithm (`voteCount == 0` guard, `DelegationStore.java:136`). The funds are effectively minted/counted into a per-cycle pool that no future stakeholder can withdraw, matching the exact bug class described in the external report: rewards "distributed" against a zero-participant period become permanently stranded rather than deferred.

### Impact Explanation
The reward pool value recorded via `addReward` for a (cycle, witness) pair with zero total votes is never credited to any account's `allowance`, and no code path recovers or re-queues it for a later cycle. This constitutes a permanent, protocol-level freezing of value that was already accounted as owed to voters — unauthorized loss of rewards that should have gone to future/other stakers, matching the Medium-severity classification given to the analogous Zivoe finding.

### Likelihood Explanation
The condition (`totalVote == 0` for a witness in a cycle that still received a reward credit) requires a narrow timing window — all voters for a specific witness withdrawing/clearing their votes within the same cycle the reward was earned, before the maintenance cycle boundary recalculates `WitnessVote`/`Vi`. This is achievable purely through unprivileged voting/freeze/unfreeze transactions without any admin or validator collusion, but requires a specific and somewhat unlikely sequence of user actions (similar to how the original Sherlock finding was rated borderline Medium/Low due to low but nonzero probability).

### Recommendation
When `totalVote`/`voteCount` is zero for a witness at a given cycle, defer the already-recorded reward instead of discarding it — e.g., roll the un-distributed reward amount forward into the reward pool for the next cycle in which the witness has nonzero votes, mirroring the fix recommended for Zivoe (preserve funds for future stakers rather than silently treating the period as fully distributed).

### Proof of Concept
1. A witness receives a block reward for cycle `N` via `MortgageService.payBlockReward` → `payReward` → `delegationStore.addReward(N, witnessAddress, value)`.
2. Before the maintenance boundary finalizes cycle `N`'s `WitnessVote`, every voter who had voted for this witness withdraws/clears their vote (via ordinary `voteWitness`/`unfreezeBalance` unprivileged transactions), driving `getWitnessVote(N, witnessAddress)` to `0`.
3. At maintenance, `DelegationStore.accumulateWitnessVi(N, witnessAddress, 0)` sees `voteCount == 0` and only forwards the previous Vi, without emitting a delta for the reward recorded in step 1.
4. Any subsequent voter computing rewards for cycle `N` via `MortgageService.computeReward`/`VoteRewardUtil.computeReward` gets `deltaVi <= 0` for that cycle for this witness and therefore never receives that reward; the value credited in step 1 is unclaimable by anyone thereafter.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
