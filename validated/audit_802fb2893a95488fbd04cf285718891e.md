### Title
Path traversal via naive prefix comparison in ijar zip extraction (missing separator-boundary check) - (File: `third_party/ijar/zip_main.cc`)

### Summary
`UnzipProcessor::Process` in the ijar zip extractor validates that an extracted entry stays within the output directory by doing a raw string-prefix comparison, without checking for a path-separator boundary. This is structurally the same class of bug as the Starlette `StaticFiles` advisory: both use "does string A start with string B" as a containment check instead of verifying B is an actual ancestor directory of A, allowing a sibling path that merely shares a prefix (e.g. `output_root_evil` vs `output_root`) to be treated as "inside" the directory.

### Finding Description
In `Process()`, the destination path for a zip entry is built and validated like this: [1](#0-0) 

Specifically:
- `path` = `concat_path(output_root_, output_file_name)` (i.e. `output_root_ + "/" + entry_name`), and entry_name comes directly from the attacker-controlled zip's central directory filename.
- `normalized_root = normalize_path(output_root_)`
- `normalized = normalize_path(path)`
- The containment check is `normalized.compare(0, normalized_root.size(), normalized_root) != 0`.

This is a plain `std::string::compare` prefix check — it does **not** verify that the character immediately following the matched prefix in `normalized` is a path separator (`/`) or end-of-string. This is exactly the flaw `os.path.commonprefix` had in the Starlette advisory: a purely lexical prefix match instead of a path/ancestor-aware comparison (analogous to `os.path.commonpath`, or to `paths.bzl`'s `_starts_with`, which correctly checks `norm_a[len(norm_b)] == "/"` at [2](#0-1) ).

If an entry name inside the zip contains `../` segments that normalize to a sibling directory whose name has `output_root_`'s basename as a prefix (e.g. output dir `/tmp/output`, entry causing normalized path `/tmp/output_evil/pwned`), the `compare(0, len("/tmp/output"), "/tmp/output")` succeeds because `"/tmp/output_evil/pwned"` textually starts with `"/tmp/output"`, even though `/tmp/output_evil` is not a subdirectory of `/tmp/output` at all — it's a sibling. The write would then land outside the intended extraction directory.

The `third_party/ijar/test/zip_test.sh` `test_no_path_traversal` test only exercises the simple `../` escape case (`path_traversal_zip.jar`), which the direct `../` case already trips over `normalize_path` collapsing straight into a path with fewer leading components than the root — it does not cover the sibling-prefix case that this comparison is blind to.

### Impact Explanation
This zip extractor (`zipper`/`ijar` unzip tool) is used by Bazel's build machinery to unpack zip/jar archives, including `third_party/java` tooling and other build-time archive handling. A maliciously crafted zip/jar (e.g. served as a build dependency or supplied via an untrusted archive) could place entries that, after path normalization, land in a sibling directory of the intended output root, writing files outside the sandboxed extraction directory. This is a containment/path-traversal write, matching the class of impact called for (write outside the intended repository/extraction directory).

### Likelihood Explanation
Exploitability requires an entry name whose resolved (normalized) path is a prefix-colliding sibling of the output root — e.g., if `output_root_` is `.../foo`, an entry like `../foo_evil/x` resolves to `.../foo_evil/x`, which shares the literal prefix `.../foo` with the root without being a true descendant. This depends on predictable/attacker-controllable output-root naming and requires careful crafting, similar in spirit to the original Starlette PoC needing a sibling directory/file with a matching prefix name. Given the code's own regression test already anticipates `../` traversal (showing awareness of the general risk) but does not test the sibling-prefix scenario, the boundary check gap looks like a genuine unpatched edge case rather than a deliberately accepted risk.

### Recommendation
Replace the raw prefix `compare` with an ancestor-aware check that requires the byte immediately following the matched prefix to be a path separator or end-of-string (equivalent to using `os.path.commonpath`-style semantics, or mirroring the `_starts_with` boundary check already implemented correctly in `paths.bzl`). Concretely, after confirming `normalized.compare(0, normalized_root.size(), normalized_root) == 0`, additionally verify `normalized.size() == normalized_root.size() || normalized[normalized_root.size()] == '/'` before proceeding with extraction; otherwise reject the entry as escaping the output directory.

def _starts_with(path_a, path_b):
    """Returns True if and only if path_b is an ancestor of path_a.

    Does not handle OS dependent case-insensitivty."""
    if not path_b:
        # all paths start with the empty string
        return True
    norm_a = _normalize(path_a)
    norm_b = _normalize(path_b)
    if len(norm_b) > len(norm_a):
        return False
    if not norm_a.startswith(norm_b):
        return False
    return len(norm_a) == len(norm_b) or norm_a[len(norm_b)] == "/"
