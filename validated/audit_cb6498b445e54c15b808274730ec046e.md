### Title
Unauthenticated poisoning of the neighbor frontier DB via address/pubkey-hash decoupling in pingback handshake finish - (File: stackslib/src/net/neighbors/walk.rs)

### Summary
`check_handshake_pubkey_hash` in `pingback_handshakes_try_finish` only verifies that `Hash160(node_public_key)` matches the previously-recorded `NeighborAddress.public_key_hash`; it never checks that `HandshakeData.addrbytes`/`port` match the `naddr` that was pinged or the actual connection the reply came in on. The verified handshake, including attacker-chosen `addrbytes`/`port`, is then persisted unconditionally via `add_or_schedule_replace_neighbor`.

### Finding Description
`check_handshake_pubkey_hash` (`stackslib/src/net/neighbors/walk.rs:1663-1680`) computes:
```rust
let neighbor_pubkey_hash = Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
if neighbor_pubkey_hash != naddr.public_key_hash { return false; }
true
``` [1](#0-0) 
This is the *only* check performed before the peer's self-reported handshake is trusted. It binds the peer's claimed public key to the previously recorded `public_key_hash`, but does nothing to bind `data.handshake.addrbytes`/`port` to `naddr.addrbytes`/`naddr.port` or to the actual socket the reply arrived from.

In `pingback_handshakes_try_finish` (`stackslib/src/net/neighbors/walk.rs:1683-1725`), after this check passes, the code immediately calls:
```rust
self.neighbor_db.add_or_schedule_replace_neighbor(
    network, &message.preamble, &data.handshake, db_data, &mut self.neighbor_replacements,
)?;
``` [2](#0-1) 
which forwards `data.handshake` (containing attacker-controlled `addrbytes`/`port`) straight into `PeerDBNeighborWalk::add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs:368-426`), which calls `Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)` and then `.save()`/`.save_update()` to persist the record keyed on the handshake's address fields. [3](#0-2) 

An attacker who was previously advertised under `NeighborAddress` with `public_key_hash = H_attacker` can, when probed via pingback, reply with a `HandshakeAccept` whose `HandshakeData.node_public_key` hashes to `H_attacker` (trivial, since the attacker holds this key) but whose `addrbytes`/`port` point to an arbitrary victim address. `check_handshake_pubkey_hash` passes because it only checks the hash, and `add_or_schedule_replace_neighbor` persists the record with the victim's address associated with the attacker's key/identity into the frontier (peer) DB.

### Impact Explanation
This allows an unprivileged peer to write an address record into the node's frontier/peer DB that does not correspond to any address it actually controls, poisoning the neighbor database with a false address-to-key mapping. If a node later selects this record as a walk target or bootstrap candidate, it will attempt to dial the victim's `addrbytes:port` believing it to be reachable and associated with the (attacker-supplied) key material, i.e., an unauthenticated write of forged routing state into the peer DB. This matches the "unauthenticated/unauthorized write to state" Critical category — an attacker triggers persistent, repeatable false state without holding any privileged credential.

### Likelihood Explanation
Preconditions: the attacker must already be known to the node as some `NeighborAddress` (e.g., because it gossiped itself, or was discovered through some other peer's neighbor list) with a recorded `public_key_hash`, and the node must be running its neighbor-walk pingback logic (`PingbackHandshakesFinish` state) against that address, which is a routine, config-independent occurrence during normal peer discovery. The attacker's cost is trivial: run a single node with a key it controls, wait to be pinged back, and reply with a crafted `HandshakeAccept`. This is fully remote, requires no secret or privileged role, and can be repeated at will (each successful pingback round re-triggers `add_or_schedule_replace_neighbor` with attacker-chosen addresses).

### Recommendation
In `check_handshake_pubkey_hash` (or in `pingback_handshakes_try_finish` before calling `add_or_schedule_replace_neighbor`), also validate that `data.handshake.addrbytes`/`port` equal `naddr.addrbytes`/`naddr.port` (or the actual observed peer socket address for this pingback session), rejecting the handshake if they differ. Persisting the record should require both the pubkey-hash-to-naddr binding and an address binding to the naddr/actual connection that was pinged.

### Proof of Concept
Add a test in `stackslib/src/net/neighbors/walk.rs` (or a dedicated test module) that:
1. Registers `naddr` with `public_key_hash = H_attacker` in `self.network_pingbacks` (or equivalent pingback bookkeeping), simulating a prior advertisement from the attacker.
2. Constructs a `StacksMessage` whose `payload` is `StacksMessageType::HandshakeAccept(HandshakeAcceptData { handshake: HandshakeData { node_public_key: attacker_pubkey, addrbytes: victim_addrbytes, port: victim_port, .. }, .. })`, where `Hash160::from_node_public_key_buffer(&attacker_pubkey) == H_attacker`, but `victim_addrbytes/victim_port != naddr.addrbytes/naddr.port`.
3. Feeds this message through `comms.collect_replies` mock (or directly invokes the loop body of `pingback_handshakes_try_finish`) and calls `pingback_handshakes_try_finish`.
4. Asserts that `check_handshake_pubkey_hash` returns `true` (confirming the missing address check) and that after `add_or_schedule_replace_neighbor` runs, the peer DB (via `PeerDB::get_peer`) contains a record keyed by `victim_addrbytes:victim_port` associated with the attacker's public key — demonstrating the forged address write into the frontier DB.

    fn add_or_schedule_replace_neighbor(
        &self,
        network: &mut PeerNetwork,
        preamble: &Preamble,
        handshake: &HandshakeData,
        db_data: Option<&StackerDBHandshakeData>,
        replacements: &mut NeighborReplacements,
    ) -> Result<(bool, Neighbor), net_error> {
        let local_peer_str = format!("{:?}", network.get_local_peer());
        let tx = network.peerdb_tx_begin()?;
        let (mut neighbor_from_handshake, was_present) =
            Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)?;

        if was_present {
            test_debug!(
                "{}: already know about neighbor {:?}",
                &local_peer_str,
                &neighbor_from_handshake.addr
            );
            neighbor_from_handshake
                .save_update(&tx, db_data.map(|x| x.smart_contracts.as_slice()))?;
            tx.commit()?;

            // seen this neighbor before
            return Ok((false, neighbor_from_handshake));
        }

        debug!(
            "{}: new neighbor {:?}",
            &local_peer_str, &neighbor_from_handshake.addr
        );

        // didn't know about this neighbor yet. Try to add it.
        let added =
            neighbor_from_handshake.save(&tx, db_data.map(|x| x.smart_contracts.as_slice()))?;

        if added {
            // neighbor was new, and we had space to add it.
            tx.commit()?;
            return Ok((true, neighbor_from_handshake));
        }

        // neighbor was new, but we don't have space to insert it.
        // find and record a neighbor it would replace.
        let replaced_neighbor_slot_opt =
            Self::find_replaced_neighbor_slot(&tx, &neighbor_from_handshake.addr)?;
        if let Some(slot) = replaced_neighbor_slot_opt {
            replacements.add_neighbor(
                NeighborAddress::from_neighbor(&neighbor_from_handshake),
                neighbor_from_handshake.clone(),
                slot,
            );
        }

        tx.commit()?;

        // neighbor was new
        Ok((true, neighbor_from_handshake))
    }
