### Title
`git_repository`/`new_git_repository` force-enables `protocol.file.allow=always` for submodule fetches, allowing a hostile git remote to exfiltrate arbitrary local files via `.gitmodules` - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` unconditionally passes `-c protocol.file.allow=always` to every `git submodule update --init [--recursive] --checkout --force` invocation made by the Starlark `git_repository`/`new_git_repository` rules. [1](#0-0) 

### Finding Description
Git deliberately restricts the `file://` (and `ext::`) transports for *submodule* operations to the "user" protocol class, which is blocked by default when submodule fetches are performed non-interactively (as they are here, invoked programmatically by Bazel) — this is exactly the mitigation that closed CVE-2018-11235 (arbitrary local file/read via crafted `.gitmodules`). Bazel's `update_submodules` re-opens this hole for every `init_submodules`/`recursive_init_submodules` invocation by passing `protocol.file.allow=always` on the command line, per the comment referencing bazelbuild/bazel#17040.

`git_repository`'s `remote`, `commit`/`tag`/`branch` values are supplied by the trusted root module, but the actual tree content at that ref — including the `.gitmodules` file — is controlled by whoever can push to the fetched remote/ref (e.g., an upstream maintainer, a compromised mirror, or an attacker who lands a PR/branch that the build later fetches by branch name rather than a pinned commit). Because `protocol.file.allow=always` is forced, a `.gitmodules` entry such as:
```
[submodule "x"]
    path = x
    url = file:///etc/passwd
```
or pointing at any other locally-readable absolute path (SSH keys, `.netrc`, other checked-out repos, CI secrets mounted on disk) will be happily cloned by `git submodule update --init --recursive`, materializing that content inside the fetched repository directory under the Bazel output base. [2](#0-1) [3](#0-2) 

None of the existing checks in `git.bzl`/`git_worker.bzl` (strip_prefix containment checks, add_prefix escape checks) constrain what `git submodule update` itself pulls in from `.gitmodules` — those checks only validate paths *within* the already-cloned tree, not the source of a submodule fetch. There is no allowlisting of submodule URL schemes, no confirmation prompt, and no restriction tying `protocol.file.allow` to remotes that are themselves local paths.

### Impact Explanation
This breaks containment: content that should come only from the declared remote/ref can instead pull arbitrary local filesystem content into the fetched repository tree. Since the fetched repository's contents subsequently become inputs to `BUILD` files, `filegroup`s, or genrules in the workspace, this is a read outside of the intended repository/fetch scope — sensitive local files (credentials, other repos' source, CI secrets) can be exfiltrated into build outputs, uploaded as artifacts, or otherwise leaked to whoever/whatever consumes the build.

### Likelihood Explanation
Any project that uses `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` while fetching a `branch` (rather than a pinned commit) — a common, endorsed usage pattern — is affected whenever the upstream remote content is not fully trusted (forks, mirrors, third-party dependencies with submodules). No user interaction beyond a normal `bazel fetch`/`bazel build` is required, and the attacker only needs push/merge access to the fetched ref, matching an "unprivileged content publisher" threat model.

### Recommendation
Do not force `protocol.file.allow=always` globally. Scope submodule protocol overrides only to remotes verified to be local paths matching the top-level `remote` attribute (or otherwise trusted), and leave `file://`/`ext::` blocked for arbitrary submodule URLs discovered in `.gitmodules` from a fetched ref. At minimum, warn users and document the risk of `init_submodules`/`recursive_init_submodules` combined with unpinned refs, and consider validating/allowlisting submodule URL schemes before invoking `git submodule update`.

### Proof of Concept
Extend `src/test/shell/bazel/starlark_git_repository_test.sh` (which already sets up local bare git repos consumed via `git_repository`, see its existing `do_git_repository_test` helpers) as follows:

1. Create `secret_dir/secret.txt` containing a marker string (`TOP-SECRET`) outside of any repo Bazel is meant to fetch.
2. Create a "malicious upstream" git repo `evil_repo` with a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///absolute/path/to/secret_dir
   ```
   and commit it.
3. In `MODULE.bazel`, declare:
   ```
   git_repository(
       name = "evil",
       remote = "<path to evil_repo>",
       branch = "main",
       recursive_init_submodules = True,
   )
   ```
4. Run `bazel fetch @evil//...` and assert that `bazel-bin/external/+git_repository+evil/leak/secret.txt` (or the corresponding output-base path) exists and contains `TOP-SECRET`, proving that content from an arbitrary local path outside the intended repository was pulled in via the forced `protocol.file.allow=always` submodule override. def update_submodules(ctx, git_repo, recursive = False):
```text
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
