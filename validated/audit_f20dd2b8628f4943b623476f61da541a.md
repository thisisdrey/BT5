### Title
A single stale/or reverting collateral oracle freezes all of an account's withdrawals and transfers, and an attacker can force this state by dust-depositing that collateral to the victim - (File: contracts/DepositToken.sol)

### Summary
`Pool.depositOf()` iterates every deposit token ever credited to an account and calls `masterOracle().quoteTokenToUsd()` on each underlying with no error isolation. `DepositToken.deposit(amount_, onBehalfOf_)` performs no oracle or health check, so any EOA can deposit a dust amount of a collateral whose price feed is stale/reverting directly into a victim's account list. From then on, every `withdraw()`, `transfer()`, and `transferFrom()` for that account reverts inside `_revertIfLocked()` -> `unlockedBalanceOf()` -> `Pool.debtPositionOf()`, and the victim cannot remove the poisoned entry themselves because removing it requires a transfer or full burn, which reverts on the same path.

### Finding Description
- `DepositToken.deposit()` takes an arbitrary `onBehalfOf_`, pulls underlying from the caller, and mints msdTOKEN to that beneficiary without consulting the oracle. [1](#0-0) 
- `_mint()` calls `pool.addToDepositTokensOfAccount(account_)` the first time an account receives the token. [2](#0-1) 
- `Pool.depositOf()` loops over `depositTokensOfAccount` and calls `masterOracle().quoteTokenToUsd(underlying, balance)` for each entry; one reverting oracle reverts the whole call. [3](#0-2) 
- `debtPositionOf()` unconditionally calls `depositOf()`, even when the account has zero debt. [4](#0-3) 
- `withdraw()` and `transfer()`/`transferFrom()` all gate on `_revertIfLocked()`, which calls `unlockedBalanceOf()` -> `debtPositionOf()`; there is no try/catch or stale-price fallback. [5](#0-4) [6](#0-5) [7](#0-6) 

This mirrors the reported bug class: an offline oracle for one component asset bricks the exit path for the whole position. Metronome makes it worse because the poisoned collateral entry can be imposed on a victim via `onBehalfOf_` dust deposits.

### Impact Explanation
Temporary freezing of user funds. While any one collateral oracle in a victim's `depositTokensOfAccount` set reverts (Chainlink staleness, pull-oracle expiry such as `price-too-behind`/`invalid-token-price`, etc.), the victim cannot withdraw or transfer any deposit token, including fully healthy, correctly-priced collateral, and even with zero debt. The dust cannot be removed by the victim because both removal paths (transfer to zero out the balance, or `withdraw()` which burns to zero) hit the same reverting valuation loop. `Pool.liquidate()` also reverts at its `debtPositionOf()` check, blocking liquidations of the poisoned account during the outage. [8](#0-7) 

### Likelihood Explanation
Requires an external oracle to become stale/revert — the same precondition as the source finding, which was accepted as Medium for the analogous freeze. No privileged role is needed: the attacker only calls the public `deposit(amount_, victim)` with dust of the affected collateral. The protocol's own tests confirm expired prices cause `debtPositionOf` and `withdraw` to revert (`price-expired`, `invalid-token-price`). [9](#0-8) 

### Recommendation
Make per-collateral valuation failure non-fatal for exits: wrap `quoteTokenToUsd` per-token calls in `depositOf()`/`debtOf()` with try/catch and treat a reverting oracle as zero collateral value (conservative for issuance, still blocking new debt), or check locks only against the specific token being withdrawn/transferred. Alternatively, disallow `onBehalfOf_` deposits of collaterals whose oracle is currently reverting, and/or let users remove a zero-priced dust token from their set. Also consider skipping zero-value entries in `unlockedBalanceOf()` when `_debtInUsd == 0`.

### Proof of Concept
Foundry/Hardhat fork sketch (existing suites already wire `Pool`, `DepositToken`, and a stale-capable oracle):

```solidity
// Collaterals: msdWETH (healthy oracle), msdSTALE (oracle reverts, e.g. stale RedStone/Pyth feed)
// Victim holds only msdWETH, zero debt.

// 1) Attacker dust-deposits the stale-oracle collateral to the victim.
//    deposit() has no oracle check and calls _mint -> addToDepositTokensOfAccount(victim).
staleUnderlying.approve(msdSTALE, 1);
msdSTALE.deposit(1, victim);                 // attacker pays dust

// 2) Oracle for staleUnderlying is now stale (e.g. advance time past stale period).
vm.warp(block.timestamp + stalePeriod + 1);

// 3) Victim tries to withdraw WETH collateral -> reverts.
//    withdraw -> _revertIfLocked -> unlockedBalanceOf -> debtPositionOf
//    -> depositOf -> quoteTokenToUsd(staleUnderlying, ...) reverts.
vm.prank(victim);
vm.expectRevert();                            // e.g. "price-too-behind"
msdWETH.withdraw(victimWethBalance, victim);

// 4) Victim cannot shed the poisoned dust: transfer() hits the same check.
vm.prank(victim);
vm.expectRevert();
msdSTALE.transfer(attacker, 1);
```

`deposit()` is reachable by any EOA, `nonReentrant`/`whenNotShutdown` do not help, and `MAX_TOKENS_PER_USER` only caps the number of entries — one dust entry is enough. [1](#0-0) [10](#0-9) [3](#0-2)
