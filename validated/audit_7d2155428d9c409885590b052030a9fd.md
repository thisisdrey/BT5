### Title
Bridged synthetic tokens are permanently burned with no refund path when destination mint reverts - (File: contracts/ProxyOFT.sol)

### Summary
`ProxyOFT._debitFrom` burns the user's `SyntheticToken` on the source chain before dispatching the LayerZero message [1](#0-0) . On the destination chain, `OFTCoreUpgradeable._sendAck` calls `ProxyOFT._creditTo`, which unconditionally calls `syntheticToken.mint(to, amount)` [2](#0-1) . `SyntheticToken._mint` reverts under several reachable conditions: `SyntheticIsInactive`, `SurpassMaxBridgingSupply` (when `bridgedInSupply() > maxBridgedInSupply`), `SurpassMaxSynthSupply`, and `MintToTheZeroAddress` [3](#0-2) . When the mint reverts, `NonblockingLzAppUpgradeable._blockingLzReceive` catches the failure and stores it in `failedMessages` [4](#0-3) , but the only recovery is `retryMessage`, which replays the identical mint on the destination chain [5](#0-4) . There is no mechanism to refund/re-mint the burned tokens on the source chain, matching the ZetaChain bug class: debit succeeds, credit fails, funds frozen.

### Finding Description
1. User calls `ProxyOFT.sendFrom(from_, dstChainId_, to_, amount_)`, which routes to `OFTCoreUpgradeable._send` → `_debitFrom` → `syntheticToken.burn(from_, amount_)`. The tokens are burned atomically with the `_lzSend` dispatch [6](#0-5) .
2. On the destination, `lzReceive` → `_blockingLzReceive` → `_nonblockingLzReceive` → `_sendAck` → `_creditTo` → `SyntheticToken.mint`.
3. The mint reverts if:
   - the bridged-in cap is hit (`bridgedInSupply() > maxBridgedInSupply`). This is reachable by an unprivileged attacker: the attacker bridges a large amount of the same synth into the destination chain first, consuming `maxBridgedInSupply`, so that a victim's already-in-flight message fails; or it is reached organically by concurrent inbound bridges;
   - `totalSupply > maxTotalSupply` after the mint;
   - the synth is inactive (`isActive == false`);
   - `to_` is `address(0)` — note `sendFrom` accepts an arbitrary `to_`, and `MintToTheZeroAddress` makes the stored message permanently unretryable.
4. The failed message is stored; `retryMessage` re-executes the same payload and reverts again for as long as the condition holds. For `MintToTheZeroAddress` it reverts forever. There is no "send back / refund on source" flow anywhere in `ProxyOFT`, `OFTCoreUpgradeable`, or `SyntheticToken` — `sendFrom` only burns, and no function re-credits a burned outbound amount.
5. `sendAndCall` is disabled (`revert SendAndCallNotAllowed`), so the composable `retryOFTReceived`/`failedOFTReceivedMessages` path doesn't apply; only the plain `PT_SEND` path is live [7](#0-6) .

### Impact Explanation
Bridge conservation breaks: tokens are burned on the source chain but never minted on the destination. User funds are temporarily frozen (until `maxBridgedInSupply`/`maxTotalSupply` is raised, bridged-out volume offsets the net-in supply, or the synth is reactivated — all dependent on governance/third parties, analogous to reliance on TSS holders in the original report) or permanently frozen (zero-address recipient, or a persistent cap). An attacker can also deliberately saturate `maxBridgedInSupply` to grief inbound transfers.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `sendFrom` with `to_ = address(0)` (permanent freeze) or by bridging while `bridgedInSupply` is at/near `maxBridgedInSupply`. The caps are finite governance-set values observed in deployment configs, and net bridged-in supply grows with every inbound transfer, so cap exhaustion is a realistic steady-state condition rather than an edge case.

### Recommendation
Implement a source-chain refund path: store the burned amount keyed by LayerZero nonce/guid when the message fails, and provide a function (or a reverse "refund" packet type) that lets the sender re-mint the tokens on the source chain or redirect them to a valid destination address. Alternatively, on destination failure, automatically dispatch a compensating message back to the source chain to re-mint to the original sender.

### Proof of Concept
Foundry/Hardhat fork sketch:
1. Issue msUSD to `alice` on chain A; call `proxyOFT.sendFrom(alice, dstChainId, address(0), amount, {value: fee})` — succeeds; `synth.balanceOf(alice) == 0`, `totalBridgedOut += amount`.
2. Deliver the payload on chain B: `lzReceive` → mint reverts `MintToTheZeroAddress` → message stored in `failedMessages`; `synth.balanceOf(0) == 0` obviously and no tokens minted.
3. Call `retryMessage(...)` with the same payload → reverts again. No function exists to re-credit `alice` on chain A. Tokens are permanently burned.
   Alternatively: on chain B, an attacker first bridges in enough synth so `bridgedInSupply() == maxBridgedInSupply`; then `alice`'s inbound `sendFrom` message fails with `SurpassMaxBridgingSupply` and remains frozen until governance raises the cap or net supply decreases.

    function _mint(address account_, uint256 amount_) private onlyIfSyntheticTokenIsActive {
        if (account_ == address(0)) revert MintToTheZeroAddress();

        address _msgSender = _msgSender();

        if (_isMsgSenderProxyOFT(_msgSender)) {
            totalBridgedIn += amount_;
            if (bridgedInSupply() > maxBridgedInSupply) revert SurpassMaxBridgingSupply();
        } else if (_isMsgSenderAmo(_msgSender)) {
            amoSupply += amount_;
            if (amoSupply > maxAmoSupply) revert SurpassMaxAmoSupply();
        }

        totalSupply += amount_;
        if (totalSupply > maxTotalSupply) revert SurpassMaxSynthSupply();
        balanceOf[account_] += amount_;
        emit Transfer(address(0), account_, amount_);
    }

    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
    }
