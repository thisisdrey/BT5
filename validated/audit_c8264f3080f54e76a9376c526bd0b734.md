### Title
Attacker can permanently fill a victim's per-account token list via dust deposits/transfers, DoS-ing deposits of new collateral types and leverage flows - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount + depositTokensOfAccount`. Entries are added whenever a `DepositToken` balance goes from `0` to non-zero, and the add reverts with `UserReachedMaxTokens` once the cap is hit. Any unprivileged EOA can push entries into an arbitrary victim's list at dust cost — via `DepositToken.deposit(amount_, onBehalfOf_ = victim)` or `DepositToken.transfer(victim, dust)` — because neither requires the victim's consent. Once 30 entries exist, every mint/transfer of a *new* deposit token to the victim reverts, blocking the victim from depositing any collateral type not already in their list (and blocking SmartFarmingManager leverage paths that add tokens on a user's behalf).

### Finding Description
- `Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) .
- The check runs on the *account* argument, not the caller, and `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary with no opt-in [2](#0-1) .
- `deposit` mints `msdTOKEN` to `onBehalfOf_`; on a zero-balance account the mint path calls `pool.addToDepositTokensOfAccount(victim)`, inserting an entry the victim never requested.
- The same insertion happens on `transfer`/`transferFrom` when the recipient's balance is zero, so an attacker holding dust balances of many deposit tokens can also fill the list for free (no underlying needed beyond initial dust).
- Attack: for every registered `DepositToken` the victim doesn't already hold, the attacker deposits (or transfers) 1 wei to the victim until the combined list reaches 30.
- Afterwards: `deposit(newCollateral, victim)` reverts in `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`; `transfer` of any new `msdTOKEN` to the victim reverts; `Pool.liquidate` still works, but `depositToken_.seize(account, liquidator, ...)` will revert for a liquidator whose own list is full, and SmartFarmingManager `leverage` flows that mint a fresh deposit token to a position account revert.

### Impact Explanation
Temporary freezing / liveness loss for the targeted account: the victim cannot add new collateral types to their position. If the victim's position is approaching liquidation and the only collateral they hold off-protocol is a type not yet in their list, topping up is impossible — they are forced into liquidation, converting the DoS into direct loss of collateral (liquidator incentive + protocol fee). While the victim can eventually clear entries by fully withdrawing dust positions (each withdraw that zeroes a balance calls `removeFromDepositTokensOfAccount`), this requires multiple transactions, gas, and cannot be done atomically inside the same tx as the rescue deposit, so front-running liquidations remain exploitable during the window. Deposits of already-listed tokens still work because `add` is only invoked on a 0→non-zero transition.

### Likelihood Explanation
- Fully unprivileged: attacker needs only dust amounts of each registered collateral (or dust `msdTOKEN` balances to transfer). No governor/keeper/oracle cooperation required; `deposit` is `whenNotPaused nonReentrant` and permissionless.
- Reachability depends on deployed configuration: the pool must have enough distinct registered tokens (deposit + debt) that the victim doesn't already hold to reach 30 total. Pools with few collateral types are not exploitable; pools approaching 30 registered tokens are.
- No modifier stops it: `SynthContext`/`onlyIfAdditionWillNotReachMaxTokens` keys on `account_`, and `TreasuryCanNotDeposit`/pause flags are irrelevant.

### Recommendation
- Only add to `depositTokensOfAccount` on balance transitions where the account has effectively opted in, or make `add` idempotent-and-non-reverting and instead enforce the cap on operations that iterate the list (e.g., revert in `debtPositionOf` consumers), so third parties cannot fill the list.
- Alternatively, let the account itself prune: add a public `removeDepositTokenFromAccount(token)` for entries with `balanceOf == 0`, or skip zero-balance members during iteration.
- Require `onBehalfOf_` consent (allowlist/permit) or charge a minimum first-deposit so dust-filling is uneconomical.

### Proof of Concept
Hardhat/Foundry sketch (against a pool with ≥30 registered deposit/debt tokens not held by `victim`):

```solidity
// Assume depositTokens[0..29] registered in pool, victim holds none of them
for (uint256 i; i < 30; ++i) {
    IERC20 underlying = depositTokens[i].underlying();
    deal(address(underlying), attacker, 2);
    underlying.approve(address(depositTokens[i]), 2);
    depositTokens[i].deposit(1, victim); // mints dust msdToken to victim, adds entry
    // or: depositTokens[i].transfer(victim, 1) from attacker's dust balance
}
assertEq(pool.depositTokensOfAccount(victim).length + pool.debtTokensOfAccount(victim).length, 30);

// Victim's legitimate deposit of a new collateral now reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
depositTokens[30].deposit(1e18, victim); // reverts inside _mint -> addToDepositTokensOfAccount

// Consequence: victim near liquidation cannot add fresh collateral -> forced liquidation
pool.liquidate(synthToken, victim, repayAmount, depositTokens[0]); // succeeds, victim loses collateral
```

Uncertainty noted: I could not fully verify the exact `_mint`/`transfer` hook code paths (lines beyond the excerpted region) or the number of deposit tokens registered in the target production pool; the attack requires enough registered tokens to reach the 30-entry cap. If the deployed pool has fewer than 30 token entries reachable for the victim, this analog does not hold.

    function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
