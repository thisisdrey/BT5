Audit Report

## Title
Zero-slippage AMM swap in `swap_and_burn` allows sandwich attack that drains user tip/fee assets and underfunds Ethereum-side execution/reward accounting - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

## Summary
`Pallet::swap_and_burn`, invoked by both the public `register_token` and `add_tip` extrinsics via `swap_fee_asset_and_burn`, calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, disabling all slippage protection on the AMM trade that converts a user's fee/tip asset into Ether. Any unprivileged actor can sandwich this call against the underlying `pallet_asset_conversion` pool, and the resulting near-zero `ether_gained` is used verbatim as the authoritative fee/tip `amount` forwarded to BridgeHub's `EthereumSystem::register_token`/`add_tip`, causing the user's full input to be consumed while the recorded execution-fee/relayer-tip value is deflated.

## Finding Description
`swap_and_burn` performs:
```rust
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
``` [1](#0-0) 

There is no `amount_out_min` check anywhere in this call path. This is reachable from two public, permissionless entry points:
- `register_token` (non-`Root` origin) calls `swap_fee_asset_and_burn`, whose output feeds `build_register_token_call`'s `amount` field, dispatched as `EthereumSystemCall::RegisterToken{ amount, .. }` to BridgeHub. [2](#0-1) 
- `add_tip` (any signed account) calls `swap_fee_asset_and_burn` directly and forwards the result as the `amount` in `EthereumSystemCall::AddTip{ sender, message_id, amount }`, which is the relayer reward tip for a specific `message_id`. [3](#0-2) 

`swap_fee_asset_and_burn` routes non-Ether assets through `swap_and_burn` unconditionally whenever `fee_asset_location != ether_location`: [4](#0-3) 

The `Swap` trait's own signature explicitly supports a real minimum-output guard (`amount_out_min: Option<Balance>`), and `pallet_asset_conversion`'s own extrinsic implementation of `swap_exact_tokens_for_tokens` enforces it via `ProvidedMinimumNotSufficientForSwap` when `Some` is supplied — proving the protection mechanism exists and is simply not used here. This pallet is the only caller that deliberately passes `None`.

Because the swapped asset is drawn from the public, permissionless `pallet_asset_conversion` pool (the pallet's `type Swap` is generically wired to it in production configs), any account can submit adjacent extrinsics before and after a victim's `register_token`/`add_tip` call within the same block to move the pool price, extract the arbitrage, and leave the victim's `ether_gained` deflated to near-zero — a standard sandwich attack requiring only ordinary transaction submission rights, no privileged role, validator collusion, or off-chain infrastructure control.

## Impact Explanation
The deflated `ether_gained` is forwarded as the authoritative `amount` to BridgeHub's `EthereumSystem::register_token`/`add_tip`:
- For `add_tip`, the relayer reward tip recorded against `message_id` is minted/allocated far below what the user paid, while the user's full input asset has already been burned for teleport — an unbacked, underpriced-work condition directly in Snowbridge's reward/delivery accounting.
- For `register_token`, the on-chain execution-fee amount reported to Ethereum is deflated even though the full user-supplied asset was consumed, degrading the bridge's fee-funding guarantee for the corresponding Ethereum-side command.

This fits the "public underpriced work that degrades... bridge processing" and unbacked-value-loss impact categories for the Snowbridge reward/delivery pivot, since the exact corrupted value is the `amount`/`ether_gained` field passed into `EthereumSystemCall::RegisterToken`/`AddTip`.

## Likelihood Explanation
Exploitation requires only observing a pending `register_token`/`add_tip` transaction in the pool and submitting an ordinary front-run/back-run pair of swaps against the same `pallet_asset_conversion` pool leg — a standard MEV technique achievable by any unprivileged account with capital, bounded by pool liquidity depth. No malicious node, validator, relayer, or off-repo infrastructure control is required, satisfying the "unprivileged external attacker using public extrinsics" requirement.

## Recommendation
Add a real `amount_out_min` parameter to `register_token`/`add_tip` (or compute a conservative bound via `pallet_asset_conversion::quote_price_exact_tokens_for_tokens` at call time with an acceptable tolerance) and pass it into `T::Swap::swap_exact_tokens_for_tokens` instead of hardcoding `None`, so the swap — and the extrinsic — reverts if pool price has been manipulated beyond an acceptable slippage bound.

## Proof of Concept
1. Attacker observes a pending `add_tip(message_id, asset)` call with `asset = (tip_asset_location, 1000)` targeting the `tip_asset → ether` leg of the public `pallet_asset_conversion` pool.
2. Attacker submits a large `swap_exact_tokens_for_tokens(tip_asset → ether)` trade immediately before the victim's transaction in the same block, moving the pool price.
3. Victim's `add_tip` executes `swap_and_burn` → `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)`; the trade succeeds despite `ether_gained` being far below fair value, since no `amount_out_min` check exists (see `bridges/snowbridge/pallets/system-frontend/src/lib.rs:301-308`).
4. Attacker submits a reverse trade (`ether → tip_asset`) immediately after the victim's transaction, restoring the price and capturing the arbitrage profit.
5. The deflated `ether_gained` is burned via `burn_for_teleport` and forwarded as `amount` in `EthereumSystemCall::AddTip` to BridgeHub — the relayer reward recorded for `message_id` is far lower than intended, while the attacker extracted the difference from the pool. This can be reproduced as a Rust unit test by wiring a mock `Swap` implementation whose output varies with a simulated pool-price shift and asserting the forwarded `amount` is far below the fair-value expectation despite full input consumption.
