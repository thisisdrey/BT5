### Title
`RewardPool::current_reward_counter` reverts when `bonded_pool.points == 0`, permanently locking un-claimed pool reward/commission funds - (`substrate/frame/nomination-pools/src/lib.rs`)

### Summary
The TribalChief report describes a "total" denominator (`totalAllocPoint`) that can be driven to zero by ordinary `add`/`set` calls, after which `updatePool` unconditionally divides by it and reverts, permanently freezing funds. The nomination-pools pallet has the same broken invariant: `bonded_pool.points` is used as an unguarded denominator inside `RewardPool::current_reward_counter`, and it can legitimately reach zero (every member fully unbonds), after which any subsequent call that must run `update_records` reverts forever, locking the pool's residual reward-account balance (accrued but un-flushed commission/dust).

### Finding Description
`RewardPool::current_reward_counter` computes the pool's reward-per-point counter by dividing `new_pending_rewards` by `bonded_points`: [1](#0-0) 

Unlike the sibling helpers `balance_to_point`/`point_to_balance`, which explicitly special-case `current_points.is_zero()` before dividing: [2](#0-1) [3](#0-2) 

`current_reward_counter` has no such guard: it feeds `bonded_points` straight into `checked_from_rational(new_pending_rewards, bonded_points)`. When `bonded_points == 0` and `new_pending_rewards != 0` (there is unflushed reward-account balance not yet accounted for in `last_recorded_total_payouts` — e.g. pending commission or dust that accrued before the last member left), the rational conversion divides by zero, returns `None`, and the function converts that into `Error::<T>::OverflowRisk`, aborting the whole extrinsic: [4](#0-3) 

`bonded_pool.points` is exactly the "total" analog of `totalAllocPoint`: it is the sum of all members' active points and is decremented to zero by ordinary, unprivileged `unbond` calls as members leave (mirrored in `point_to_balance`/`balance_to_point`'s explicit zero handling, showing the pallet authors know 0 is a reachable state for this value).

`update_records` — the function that must run before *any* point or commission change is persisted — passes `bonded_pool.points` straight through without checking for zero: [5](#0-4) 

It is invoked as a mandatory precondition in multiple call paths that are not restricted to a state where points must be non-zero:
- `join` (blocked by pool state, but demonstrates the call site): [6](#0-5) 
- `set_commission`: [7](#0-6) 
- `set_commission_max`: [8](#0-7) 
- `do_claim_commission`: [9](#0-8) 

None of these call sites checks `bonded_pool.points.is_zero()` before calling `update_records`, so once the bonded pool's points reach zero while its reward account still holds an unflushed balance, every one of these entry points will unconditionally revert with `OverflowRisk`.

### Impact Explanation
This is a **permanent fund lock**, the same class as the TribalChief bug: once `bonded_pool.points == 0` with a non-zero unflushed reward-account balance, `set_commission`, `set_commission_max`, and `do_claim_commission` all revert forever via `update_records` → `current_reward_counter`. There is no code path that resets or bypasses this check, so any commission or leftover reward balance sitting in the pool's reward account becomes permanently unclaimable/unrecoverable — the funds are stuck in the reward account with no dispatchable able to move them out, since every mutating call to the reward pool state is gated by the now-always-failing `update_records`.

### Likelihood Explanation
The precondition (`bonded_pool.points` hitting exactly zero while the reward account still carries an un-recorded balance) is reachable through entirely permissionless, ordinary operations: members progressively `unbond` until the pool's total points are fully exhausted, while commission is enabled and reward deposits/commission accrual has produced a balance that has not yet been folded into `last_recorded_total_payouts` via an `update_records` call. No malicious peer, validator, relayer, or governance action is required — only ordinary member and pool-root actions in a specific but realistic ordering (e.g., commission set, rewards deposited, all members unbond before commission is claimed/flushed).

### Recommendation
Mirror the pattern already used in `balance_to_point`/`point_to_balance`: in `RewardPool::current_reward_counter`, explicitly special-case `bonded_points.is_zero()` (e.g., treat pending rewards as retained/carried over, or route the leftover balance to depositor/commission payee via a dedicated cleanup path) instead of relying on `checked_from_rational` to fail into `OverflowRisk`. Additionally, add an explicit `ensure!(!bonded_pool.points.is_zero(), ...)` guard (or equivalent zero-total handling) at the `update_records` call sites in `set_commission`, `set_commission_max`, and `do_claim_commission` so a zero-points pool cannot permanently brick access to its residual reward-account balance.

### Proof of Concept
1. Create a pool with a single depositor and set a non-zero commission via `set_commission`.
2. Deposit rewards into the reward account (`deposit_rewards`) so the reward account balance grows.
3. Have the depositor/members fully `unbond` such that `bonded_pool.points` becomes `0` (achievable once the pool transitions toward destroying and the last member unbonds), while some commission/dust remains un-flushed in the reward account (i.e., `current_payout_balance` in `current_reward_counter` is non-zero at that moment).
4. Call `Pools::set_commission`, `Pools::set_commission_max`, or `Pools::claim_commission` on that pool id.
5. Observe `update_records` → `current_reward_counter` compute `T::RewardCounter::checked_from_rational(new_pending_rewards, 0)` → `None` → `Error::<T>::OverflowRisk`, causing the extrinsic to revert every time it is retried, permanently locking the reward account's residual balance.
