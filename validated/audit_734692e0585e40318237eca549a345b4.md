Audit Report

## Title
Any staker can permanently zero out reward emission in `pallet-asset-rewards` via cheap per-block interactions, silently advancing `last_update_block` without crediting `reward_per_token_stored` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`reward_per_token` computes a per-block reward increment using integer division scaled only by `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) , and `update_pool_rewards` unconditionally advances `last_update_block` to the current block regardless of whether the computed `reward_per_token` actually changed [2](#0-1) . Any unprivileged staker can call the public `stake`, `unstake`, or `harvest_rewards` extrinsics every block with minimal amounts to keep the reward increment rounding down to zero while permanently consuming each block's reward-eligible window, denying rewards to all stakers and stranding the funded reward asset in the pool account.

## Finding Description
`reward_per_token` computes: `reward_per_token_stored + reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` [3](#0-2) . For `rewardable_blocks_elapsed = 1`, this rounds to zero whenever `total_tokens_staked > reward_rate_per_block * 4096`, which is trivially true for pools with realistic decimal-scaled staked amounts (e.g., 10^18) against modest reward rates.

Crucially, `update_pool_rewards` writes `last_update_block = now` and `reward_per_token_stored = reward_per_token` unconditionally, with no check for whether the increment was actually nonzero [2](#0-1) . This means that once the checkpoint advances, the "lost" block-window (whose reward rounded to 0) can never be recovered by a future call, since future calls only measure elapsed blocks from the newly advanced `last_update_block`.

This update path is reached by three fully public, unprivileged extrinsics before any other logic executes: `stake` [4](#0-3) , `unstake` [5](#0-4) , and `harvest_rewards` [6](#0-5) , all routing through `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards` [7](#0-6) . There is no minimum-interval guard, no minimum-stake requirement, and no check that the computed reward delta is nonzero before persisting the checkpoint. The pallet's own test suite acknowledges rounding errors exist but dismisses them as "insignificant" without considering the case where `total_tokens_staked` is large relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR`, which yields full (not off-by-one) zeroing per call [8](#0-7) .

An attacker can additionally keep the pool permanently non-empty (maintaining a nonzero stake) to block `cleanup_pool`, which requires the pool to have no stakers before an admin can reclaim leftover reward tokens [9](#0-8) , compounding the fund-lock effect.

## Impact Explanation
An attacker who repeatedly triggers `stake`/`unstake`/`harvest_rewards` every block with `total_tokens_staked > reward_rate_per_block * 4096` causes `reward_per_token_stored` to stop growing while `last_update_block` continuously advances, permanently discarding each block's reward-eligible window. This denies rewards to all stakers in the pool (not just the attacker) and leaves the reward-asset balance funded into `pool_info.account` unclaimable, matching the "permanent user-fund lock" and "runtime bug that compromises intended behavior" impact categories in the gate.

## Likelihood Explanation
The precondition `total_tokens_staked > reward_rate_per_block * 4096` is easily satisfied for any pool using realistic decimal-scaled staked assets. Calling `stake`/`unstake`/`harvest_rewards` every block costs only ordinary transaction fees — no economic barrier exists, and the attack is self-sustaining (attacker's own stake changes do not meaningfully change `total_tokens_staked`). No existing guard checks the computed reward delta before persisting the new checkpoint, so likelihood is high for any active pool with meaningful liquidity.

## Recommendation
- In `update_pool_rewards`/`reward_per_token`, avoid advancing `last_update_block` when the computed increment rounds to zero, or accumulate a fractional remainder using a higher-precision type (e.g., `FixedU128`/`Perquintill`) so rounding loss does not compound across repeated small-window updates — analogous to `pallet-nomination-pools`'s `RewardCounter`.
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g., to an 18-decimal-scale fixed point) to shrink the rounding-to-zero window for realistic stake sizes.

## Proof of Concept
1. `create_pool` with `reward_rate_per_block = 100`; have stakers deposit until `total_tokens_staked > 100 * 4096 = 409_600` (trivial with decimal-scaled assets, e.g. `total_staked = 10^18`).
2. Attacker calls `stake(pool_id, 1)`.
3. Every subsequent block, attacker calls `unstake(pool_id, 1, None)` then `stake(pool_id, 1)` (or repeatedly calls `harvest_rewards`), each triggering `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards`.
4. With `rewardable_blocks_elapsed = 1`, `100 * 1 * 4096 / 10^18` computes to `0` via integer division; `reward_per_token_stored` stays constant, but `last_update_block` advances to the current block each time via `update_pool_rewards` at `substrate/frame/asset-rewards/src/lib.rs:775-784`.
5. Repeating step 3–4 for the pool's full duration means `reward_per_token_stored` never meaningfully increases despite `reward_rate_per_block * elapsed_blocks` (the funded/intended distribution) being large and nonzero — that reward remains stuck in `pool_info.account`, unclaimable by any staker, and the attacker's continued stake blocks `cleanup_pool` from reclaiming it.

		///
		/// Origin must be the pool admin.

		/// Cleanup storage, release any associated storage cost and return the remaining reward
		/// tokens to the admin.
		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}
