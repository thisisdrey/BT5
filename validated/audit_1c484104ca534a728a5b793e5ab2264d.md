### Title
Unbounded merge of duplicate non-reserved HTTP headers via BTreeMap `push_str` - ([File: stackslib/src/net/http/request.rs])

### Summary
`HttpRequestPreamble::consensus_deserialize` only tracks `seen_headers` for the four reserved header names (`host`, `content-type`, `content-length`, `connection`); any other (non-reserved) header name is never inserted into `seen_headers`, so the "duplicate header" rejection at line 374-379 never fires for it. This lets an attacker send many same-named non-reserved headers that get merged with `entry.push_str(", ")` + `push_str(&value)` at lines 414-420, growing a single `String` value with no cap on the accumulated size — only the per-header `value.len()` is checked against `HTTP_PREAMBLE_MAX_ENCODED_SIZE` (line 366), not the resulting merged `entry`.

### Finding Description
The claimed equality break is confirmed: the per-header size guard at [1](#0-0) 
only validates the incoming `value` on each loop iteration, never the accumulated `entry` string that lives in the `BTreeMap`. The merge itself happens at [2](#0-1) 
where `.and_modify(|entry| { entry.push_str(", "); entry.push_str(&value); })` concatenates every occurrence of a duplicate key into one growing `String`, with no check on `entry.len()` before or after the push.

Critically, the "duplicate header" rejection that would normally stop an attacker from repeating a header name is scoped only to the reserved keys: [3](#0-2) 
`seen_headers.insert(key)` is only called inside the `host`/`content-type`/`content-length`/`connection` branches (lines 386, 391, 398, 410); the `else` branch handling arbitrary headers (lines 413-421) never inserts into `seen_headers`. Since `seen_headers.contains(&key)` is checked before branching (line 374), and non-reserved keys are never added to that set, an attacker can send the same non-reserved header name repeated across the entire header list without ever triggering the duplicate check.

The number of headers httparse will parse is bounded by the preamble's configured header-array capacity, so the total growth is bounded by (max header count) × (max value size), not unbounded — but it is not validated against any accumulated cap, and the per-header check at line 366 gives a false sense that header sizes are bounded.

### Impact Explanation
On each preamble parse, the attacker forces one or more `String` reallocations via repeated `push_str`, producing a merged header value bounded by (number of headers allowed) × `HTTP_PREAMBLE_MAX_ENCODED_SIZE`, stored in the resulting `HttpRequestPreamble.headers` map. This is a bounded, per-message compute/allocation cost increase on the RPC/P2P HTTP preamble parser — it does not crash the node, corrupt state, or forge canonical data. Per the audit's own severity categories, this most plausibly falls under "bounded compute DoS on a read endpoint," but the actual amplification is limited by the fixed maximum header count httparse/the preamble parser is configured with, and the resulting cost (single string growth to a few hundred KB at most) is well within what any HTTP preamble parser already allocates for headers of that count and size. It does not constitute an unbounded or amplifying DoS.

### Likelihood Explanation
Reachable by any unprivileged remote peer connecting to the P2P or RPC HTTP listener with no authentication, since it only requires sending a crafted preamble. Cost to the attacker is trivial (one HTTP request). However the achievable amplification is strictly bounded by the same header-count cap that already bounds normal use of this code path — there's no growth beyond what the parser would already accept from legitimate duplicate-ish header traffic within its configured limits.

### Recommendation
Track `seen_headers` (or an equivalent count) for all header keys, not just the reserved ones, and either reject duplicate non-reserved headers outright or cap the accumulated `entry.len()` after each `push_str` against `HTTP_PREAMBLE_MAX_ENCODED_SIZE`, returning `CodecError::DeserializeError` if exceeded.

### Proof of Concept
A Rust test in `stackslib/src/net/http/tests.rs` sending a preamble with N (bounded by httparse's max header count) distinct-case but same-lowercased non-reserved header names, each with a value near `HTTP_PREAMBLE_MAX_ENCODED_SIZE`, then asserting `HttpRequestPreamble::consensus_deserialize` either (a) rejects the request once the merged entry would exceed `HTTP_PREAMBLE_MAX_ENCODED_SIZE`, or (b) currently accepts it with a merged header value exceeding that constant — demonstrating the missing post-merge cap. Given the bound is small and fixed by the header-count cap, this should be treated as a hardening/defense-in-depth fix rather than a high-severity DoS.
