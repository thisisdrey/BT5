### Title
Per-account token-list congestion via dust `DepositToken.transfer` causes DoS on victim's deposits, borrows, and inbound transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The zae-limiter bug class is a per-entity shared bottleneck: all of one entity's buckets live on a single partition, so heavy write traffic against that entity throttles (denies) service for the whole entity. The Metronome analog is the per-account token registry: every account has a single bounded set (`debtTokensOfAccount` + `depositTokensOfAccount`, capped at `MAX_TOKENS_PER_USER = 30`) that is written on every first-touch of a deposit or debt token. An attacker can write into a victim's "partition" without the victim's consent by dust-transferring each registered `DepositToken`, filling the set to the cap. Once full, every code path that adds a new token reverts for that account.

### Finding Description
`Pool` enforces `onlyIfAdditionWillNotReachMaxTokens` on both list-addition entry points:

- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) [2](#0-1) [3](#0-2) 
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 — including plain ERC20 `transfer`/`transferFrom`, which any holder can call to any address [4](#0-3) [5](#0-4) 
- `DepositToken._mint` does the same for recipients of `deposit()`, `depositTo()`, and `depositOnBehalf` paths [6](#0-5) 
- `DebtToken.issue`/`mint` add the debt token to the caller's list via `Pool.addToDebtTokensOfAccount` when the position's debt balance goes from 0 to >0, so a filled list also blocks opening *new* debt types [7](#0-6) 

There is no sharding, no opt-in (an ERC721-style "recipient must accept"), and no way for the victim to reject an inbound dust transfer — mirroring the report's "no admission control before hitting the shared partition."

### Impact Explanation
Once the victim's combined list reaches 30:

- `transfer`/`transferFrom`/`seize`/`deposit` of any deposit token the victim doesn't already hold reverts. This breaks `Pool.liquidate` when the seized collateral is sent to a filled beneficiary, SmartFarming/Operator batched flows that deposit new collateral, and any contract (e.g., a strategy or multisig) that must receive an msdTOKEN.
- `DebtToken.issue` for any synthetic the victim doesn't already owe reverts, blocking new borrows/leverage for that account.
- The victim can free a slot by transferring a dust balance to zero, but the attacker can refill it permissionlessly in the same or next block, making the freeze effectively continuous while the attacker is active. Cost to the attacker is gas plus locked dust (recoverable).

This is a temporary freezing/griefing of funds flow against a targeted entity — the same "single entity's shared slot saturates and rejects all further writes" shape as the advisory.

### Likelihood Explanation
Bounded by deployment configuration: the attacker can only inject tokens that exist in the victim's pool, so the attack fully saturates the cap only if `registeredDepositTokens + registeredDebtTokens ≥ 30`, or if the victim already holds several tokens. On smaller pools the attacker can still occupy every currently-registered deposit token, which blocks all *new* collateral types as governance adds them. No privileged role, oracle, or keeper is required — only a funded EOA calling `DepositToken.transfer(victim, dust)` per token. Note this is partly a known design trade-off (the cap exists to bound `debtOf`/`depositOf` loop gas); the missing piece is consent on inbound entries.

### Recommendation
- Let `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` tolerate a saturated victim list for *recipient-side* additions (e.g., track balances in a mapping for reads and only enumerate a bounded "active" set), or let health/position reads iterate over global token lists filtered by `balanceOf > 0` instead of the per-account set.
- Alternatively, make inbound transfers that would add a new token opt-in, or allow the victim to force-remove zero-dust entries via a `sweep`/`removeToken(account, token)` helper callable on themselves.
- Exempt liquidation/`seize` paths from the cap by sending seized collateral to the liquidator rather than the beneficiary's list when the beneficiary list is full.

### Proof of Concept
Hardhat sketch (against deployed-style fixtures):

```ts
// attacker: for each registered deposit token the victim doesn't hold:
for (const dt of await pool.getDepositTokens()) {
  const dep = await ethers.getContractAt('DepositToken', dt);
  // attacker has balance (deposited earlier, or withdraws/re-deposits)
  await dep.transfer(victim.address, 1); // adds `dt` to victim's list
}
// repeat across debt tokens attacker can open + until combined length == 30
expect(await pool.getDepositTokensOfAccount(victim.address)).length
  .eq(30 - (await pool.getDebtTokensOfAccount(victim.address)).length);

// victim can no longer receive a new deposit token:
await expect(dep2.transfer(victim.address, 1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
// and cannot issue a new synthetic debt type:
await expect(debtToken.connect(victim).issue(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
// attacker refills any slot the victim clears → persistent while active
```
