### Title
Unauthenticated forgery of `SignerEvent::NewBurnBlock` (and `/new_block`, `/proposal_response`) via the signer's event-receiver HTTP port - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` dispatches any POST body on `/new_burn_block`, `/new_block`, and `/proposal_response` straight into `serde_json::from_slice` and then `TryInto<SignerEvent<T>>`, with no signature, token, or peer-identity check anywhere in the path. Any TCP client that can reach the signer's bound `endpoint` (which the shipped sample configs set to `0.0.0.0:30000`, i.e. all interfaces) can hand-craft a `BurnBlockEvent` JSON body and have the signer runloop treat it as a genuine node-observed burn block.

### Finding Description
`next_event` (`libsigner/src/events.rs:413-459`) routes based purely on URL path and HTTP method; it never checks any header, token, or source address before calling `process_event`. `process_event` (`libsigner/src/events.rs:519-542`) reads the raw body, deserializes it via `serde_json::from_slice::<E>`, and converts it with `E::try_into()`. For `BurnBlockEvent`, `TryFrom<BurnBlockEvent> for SignerEvent<T>` (`libsigner/src/events.rs:637-649`) copies `burn_block_height`, `burn_block_hash`, `consensus_hash`, and `parent_burn_block_hash` verbatim into `SignerEvent::NewBurnBlock` — there is no cryptographic binding proving these fields came from the configured node's chainstate. The `[connection_options] auth_token` mechanism documented across `docs/signing.md`, `sample/conf/mainnet-signer.toml`, etc., and in `stackslib/src/config/mod.rs:3799-3816`, only authenticates the *signer→node* direction (`/v3/block_proposal` and `/v2/blocks?broadcast=1`); it is never checked on the *node→signer* event-receiver side in `events.rs`. The code's own warning at `stacks-signer/src/lib.rs:125-132` acknowledges the receiver is unauthenticated and that "additional proper security checks" would be needed for anything but a purely local/trusted network path — but no such checks exist in this codebase. Sample configs (`sample/conf/signer/mainnet-signer-conf.toml:39`, `docs/signing.md:45`) even set `endpoint = "0.0.0.0:30000"`, binding on all interfaces.

### Impact Explanation
An attacker who can reach this port can POST a synthetic `BurnBlockEvent` and inject `SignerEvent::NewBurnBlock` carrying attacker-chosen `burn_height`, `consensus_hash`, and `parent_burn_block_hash` into the signer's runloop, which (per `stacks-signer/src/v0/signer_state.rs` and `stacks-signer/src/v0/signer.rs`) drives burn-block-tracking state used for tenure/reorg timing decisions in the signing protocol. This is a single-message, repeatable forgery of chain-state notifications the signer trusts as ground truth from its node — matching the "unauthenticated write to state" / "forged data" critical category, since it breaks the invariant "every burn-block observation the signer acts on == a burn block the configured node actually processed." The same lack of authentication applies identically to `/new_block` (`StacksBlockEvent`) and `/proposal_response` (`BlockValidateResponse`).

### Likelihood Explanation
No privileged role, secret, or key is required — only network reachability to the bound `endpoint` TCP port. The shipped reference configs bind this port on `0.0.0.0`, and the codebase's own comment flags external reachability as a real operational risk. The attack is a single crafted HTTP POST, fully repeatable, requiring no ordering or state assumptions ahead of it (only that the receiver be up).

### Recommendation
Authenticate node→signer event deliveries: require a shared-secret/HMAC or the same `auth_token` mechanism (checked via an `Authorization` header comparison) in `SignerEventReceiver::next_event`/`process_event` before accepting `/new_burn_block`, `/new_block`, and `/proposal_response` bodies, and/or bind the event receiver to loopback/mTLS-protected interfaces by default rather than `0.0.0.0`.

### Proof of Concept
In a Rust test analogous to `libsigner/src/tests/mod.rs::test_simple_signer`, spawn `SignerEventReceiver::bind` on `127.0.0.1:0`, then from a plain `TcpStream` (no `stacks-node` involved) send:
```
POST /new_burn_block HTTP/1.1\r\nHost: ...\r\nContent-Type: application/json\r\nContent-Length: N\r\n\r\n{"burn_block_hash":"0x...","burn_block_height":999999,"consensus_hash":"0x...","parent_burn_block_hash":"0x...", ...}
```
matching `BurnBlockEvent`'s field names/serde format, then assert that the value received on the `Sender<SignerEvent<T>>` channel via `forward_event` is `SignerEvent::NewBurnBlock { burn_height: 999999, .. }`, proving the forged values pass through unauthenticated.
