## Finding

The strongest analog to the reported "raw `ecrecover` without EIP-712 domain separation → cross-chain signature replay" bug class in java-tron is the `ValidateMultiSign` TVM precompiled contract.

### Title
Missing Domain Separation in `ValidateMultiSign` Precompile Enables Cross-Chain / Cross-Purpose Signature Replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompile (invoked via a TVM opcode/precompiled-contract call from any smart contract) recovers signer addresses from a hash built solely from `address || permissionId || data`, with no chain identifier, verifying-contract address, or other domain separator, mirroring exactly the vulnerable pattern in the external report (raw hash + `ecrecover`, no EIP-712 domain).

### Finding Description
`ValidateMultiSign.execute()` computes the message hash as: [1](#0-0) 

then recovers each signer via `recoverAddrBySign(sign, hash)` and checks the recovered addresses/weights against the target account's on-chain `Permission`: [2](#0-1) 

The hashed payload is only `(account address, permissionId, arbitrary caller-supplied data)`. There is no:
- chain/network identifier,
- verifying-contract address,
- reference to any TRON-specific replay-protection primitive (unlike ordinary transactions, whose signed hash is bound to `ref_block_hash`/`ref_block_bytes`/`expiration`, which tie a signature to a specific chain and time window: [3](#0-2) ).

This precompile exists specifically so that smart contracts can perform off-chain, "permit"-style authorization checks (the same "verify a user's off-chain signature and act on it" pattern as the `BatcherPaymentService.verifySignatureAndDecreaseBalance` in the report). Because the hash has no domain separator, any dApp built on top of it inherits the exact cross-chain/cross-context replay weakness described in the bug report — the protocol itself provides no EIP-712-equivalent binding for this signature-verification primitive.

### Impact Explanation
Any TVM contract relying on `ValidateMultiSign` for authorization (e.g., gasless/meta-transaction "permit" patterns, escrow release, multisig-gated transfers) is exposed to signature replay:
- **Cross-chain replay**: The same TRON address commonly exists with identical or similarly-configured `Permission`s across the mainnet and TRON-compatible test/fork networks (Nile, Shasta, private forks). A signature produced for one network can be resubmitted via a contract call on another network to pass the identical weight/threshold check, since nothing in the hashed payload differentiates networks.
- **Cross-contract/cross-purpose replay**: Since only `(address, permissionId, data)` is hashed and `data` is fully controlled by the calling contract, if two different contracts (or two different functions of the same contract) construct the same `data` blob for different intents, a signature meant to authorize one action can be reused to authorize another.

Either scenario can result in unauthorized execution of multisig-gated operations (e.g., unauthorized fund transfers) — a concrete unauthorized account operation / theft-of-funds impact reachable purely by an anonymous contract-calling actor supplying a previously-observed signature.

### Likelihood Explanation
`ValidateMultiSign` is a public TVM precompile reachable from any deployed contract triggered via ordinary `TriggerSmartContract` transactions — no special privilege is required. Exploitation only requires that a victim have signed a `(address, permissionId, data)` payload once (e.g., for a legitimate authorization on one network/contract) and that an attacker be able to observe that signature (broadcast transactions, contract events, or off-chain relaying, which is the whole point of this precompile) and resubmit it elsewhere. This makes the likelihood Medium: it depends on real-world dApp adoption patterns of `ValidateMultiSign` for off-chain authorization, but the protocol itself supplies no protection, unlike ordinary TRON transactions.

### Recommendation
Bind the `ValidateMultiSign` hash to a domain separator, e.g., include the chain identifier (a network-specific constant analogous to EVM `chainId`), and require/encourage callers to include the verifying contract's address and a purpose tag/nonce in `data`, so signatures cannot be replayed across networks, contracts, or unrelated actions — mirroring the EIP-712 style fix applied to `BatcherPaymentService`.

### Proof of Concept
1. On TRON mainnet, account `A` (with `Permission` P, threshold T) signs `hash = sha256(A || permissionId || data)` off-chain to authorize contract `C`'s function `foo(data)` (a common gasless-transaction/permit pattern using `ValidateMultiSign`).
2. Attacker observes this signature (from the mainnet transaction, an event log, or a relayer).
3. If account `A` also exists (or is later re-derived from the same key) on another TRON-compatible network (e.g., Nile testnet, a private fork, or after a future hard fork) with the same/similar `Permission` configuration, the attacker submits a `TriggerSmartContract` call to a contract there invoking `ValidateMultiSign` with the identical `(A, permissionId, data, signature)`. Because the recomputed `hash` at [4](#0-3)  is identical (no chain/contract binding), the precompile returns success, and the target contract executes the authorized action without a fresh signature from `A`.
