## Title
`reloadFirewall()` skips firewall rebuild when the certificate's assigned VPN networks change but `UnsafeNetworks()` stays the same, leaving `routableNetworks` stale - ([File: interface.go])

## Summary
Nebula's own firewall reload logic in `Interface.reloadFirewall` decides whether to rebuild `Firewall.routableNetworks` (the set used to validate that inbound packets' source/destination match the peer's certificate) purely by diffing `UnsafeNetworks()` between the old and new certificate. The routable set is actually built from **both** the certificate's assigned `Networks()` and its `UnsafeNetworks()`, but only the unsafe half is checked for drift. This mirrors the reported bug class: a piece of derived state (`routableNetworks`, analogous to the vault's fee-accrual timestamp) is only refreshed on some triggers, not on every input that feeds the calculation, so it can silently go stale relative to the current certificate.

## Finding Description
`NewFirewall` builds `routableNetworks` from two certificate-derived inputs: [1](#0-0) 

`Interface.reloadFirewall` only rebuilds the firewall (and thus `routableNetworks`) when the plain YAML `firewall` section changed, **or** when the certificate's `UnsafeNetworks()` differ from what's currently loaded: [2](#0-1) 

If a certificate rotation (via SIGHUP/`pki` reload, exercised in `TestCertUpgrade`/`TestCertDowngrade`/rehandshake tests) changes the assigned `Networks()` (e.g., a host gets reissued with a different or additional VPN address) while `UnsafeNetworks()` remains byte-for-byte identical, `certUnsafeChanged` evaluates to `false`, `c.HasChanged("firewall")` is also `false` (nothing in the YAML firewall block changed), and the entire rebuild is skipped. The `Firewall` object — and therefore `routableNetworks`/`assignedNetworks` — keeps referencing the **old** certificate's network set even though `PKI.reloadCerts` has already swapped in the new `CertState` for handshakes going forward.

This is exactly analogous to the reported `setManagementFeeBps()` issue: a config/state-changing operation (`setManagementFeeBps` / cert reload) updates one piece of state (the fee rate / the active certificate) but leaves a dependent, previously-computed value (`lastFeeCollectionTimestamp` / `routableNetworks`) untouched, so later logic computes against stale inputs.

`routableNetworks` directly gates whether a packet's local/remote address is treated as belonging to this node for firewall purposes — it's the same category of check that a prior real Nebula CVE addressed ("Nebula could incorrectly accept and process a packet from an erroneous source IP when the sender's certificate is configured with unsafe_routes ... or multiple IPs", fixed in 1.9.7, and further hardened by "Reload the firewall when the unsafe networks in the certificate change" in 1.11.0): [3](#0-2) [4](#0-3) 

The 1.11.0 fix only closed the gap for `UnsafeNetworks()` drift — it did not add an equivalent check for drift in the assigned `Networks()` half of the same computation, which is the same code path that builds `routableNetworks`.

## Impact Explanation
If exploitable, a stale `routableNetworks`/`assignedNetworks` set means the firewall keeps validating traffic against a VPN address set that no longer matches the active certificate. Depending on how `routableNetworks` is consumed downstream (address ownership / local-address matching in the data path), this can let packets tied to a since-revoked or since-changed VPN address continue to be accepted as locally-owned, or cause legitimate traffic under the new address to be misclassified — i.e., remote state poisoning of the firewall's address-trust model without requiring the attacker to hold a CA-signed certificate for the affected address. Severity is Medium: it requires the operator to actively rotate the local certificate's `Networks()` without altering `UnsafeNetworks()` or the firewall YAML, which is a plausible but not everyday operational sequence.

## Likelihood Explanation
Likelihood is Medium. It requires two things to line up: (1) an admin-driven PKI cert reload where `Networks()` changes but `UnsafeNetworks()` and the `firewall` config block do not, and (2) the resulting stale `routableNetworks` being consulted by a packet with a source/destination that only appears legitimate under the old (pre-reload) network set. The precondition is config-driven, not attacker-controlled directly, but the resulting window (stale firewall network trust) is externally observable/exploitable by any peer sending traffic during that window.

## Recommendation
In `Interface.reloadFirewall` (`interface.go`), extend the drift check beyond `UnsafeNetworks()` to also compare the certificate's assigned `Networks()` against `Firewall.assignedNetworks`, and force a firewall rebuild whenever either set has changed:
```go
certNetworksChanged := curCert != nil && (!slices.Equal(curCert.UnsafeNetworks(), f.firewall.unsafeNetworks) ||
    !slices.Equal(curCert.Networks(), f.firewall.assignedNetworks))

if !c.HasChanged("firewall") && !certNetworksChanged {
    ...
}
```
This keeps `routableNetworks` (and any other cert-derived firewall state) synchronized with every input it is actually computed from, not just one of them.

## Proof of Concept
Conceptual reproduction (extending the existing `TestReloadFirewall_CertUnsafeNetworksChanged` pattern in `interface_test.go`):
1. Build a `Firewall` via `NewFirewallFromConfig` using a certificate `c1` with `Networks() = [10.0.0.1/24]` and `UnsafeNetworks() = [198.51.100.0/24]`.
2. Swap in a new `CertState` whose certificate `c2` has `Networks() = [10.0.0.9/24]` (changed) but the same `UnsafeNetworks() = [198.51.100.0/24]`.
3. Reload the same YAML (`cfg.ReloadConfigString`) so `HasChanged("firewall")` is `false`.
4. Call `f.reloadFirewall(cfg)`.
5. Observe (as in `TestReloadFirewall_NoChange`) that `f.firewall` is left `Same` as before — the firewall/`routableNetworks` is never rebuilt — even though the certificate's assigned network changed, unlike the existing test `TestReloadFirewall_CertUnsafeNetworksChanged`, which only proves the *unsafe*-network path is monitored.

```go
func (f *Interface) reloadFirewall(c *config.C) {
	cs := f.pki.getCertState()
	curCert := cs.getCertificate(cert.Version2)
	if curCert == nil {
		curCert = cs.getCertificate(cert.Version1)
	}

	// The firewall builds its routableNetworks set from the certificate's UnsafeNetworks at construction.
	// Check to see if that set has changed, and if so, rebuild the firewall.
	certUnsafeChanged := curCert != nil && !slices.Equal(curCert.UnsafeNetworks(), f.firewall.unsafeNetworks)

	if !c.HasChanged("firewall") && !certUnsafeChanged {
		f.l.Debug("No firewall config change detected")
		return
	}

```
