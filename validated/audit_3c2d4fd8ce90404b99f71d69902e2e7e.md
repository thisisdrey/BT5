### Title
Unhandled NullPointerException in `UnDelegateResourceActuator.execute()` on legitimate transactions that only have a locked (unlocked-yet-expired) delegation record - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.validate()` treats an unfreeze/undelegate request as valid as long as the *combined* balance across the "unlocked" delegation record and an already-expired "locked" delegation record covers the requested amount — it does not require the unlocked record to exist. `execute()`, however, unconditionally fetches the unlocked record and calls a method on it without a null check, exactly mirroring the Kubernetes HPA bug class: a code path that validates an object as "acceptable" without guaranteeing a particular optional sub-structure is present, while a downstream consumer assumes that sub-structure is always populated and dereferences it directly.

### Finding Description
In `validate()` [1](#0-0) , the BANDWIDTH/ENERGY sufficiency check sums two independently-optional sources:
- `unlockResourceCapsule` (looked up via `createDbKeyV2(owner, receiver, false)`), which may legitimately be `null`.
- `lockResourceCapsule` (looked up via `createDbKeyV2(owner, receiver, true)`), counted only if it is non-null **and** already expired (`getExpireTimeForBandwidth() < now`).

The only hard failure condition is `unlockResourceCapsule == null && lockResourceCapsule == null` [2](#0-1) . Therefore a transaction where the caller has **only** an expired locked delegation (no unlocked record at all) and `lockResourceCapsule.getFrozenBalanceForBandwidth() >= unDelegateBalance` passes validation cleanly.

In `execute()`, the actuator re-fetches the unlocked record and immediately dereferences it without any null guard:
```java
DelegatedResourceCapsule unlockResource = delegatedResourceStore.get(unlockKey);
...
switch (unDelegateResourceContract.getResource()) {
  case BANDWIDTH: {
    unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);   // NPE if unlockResource == null
    ...
``` [3](#0-2) 

There is a `delegatedResourceStore.unLockExpireResource(...)` call right before this fetch [4](#0-3)  which is presumably intended to move the expired "locked" balance into the "unlocked" record so that `unlockResource` becomes non-null. However, `validate()` and `execute()` compute state independently, and validate()'s acceptance criteria do not guarantee that `unLockExpireResource` will always populate/return a non-null unlocked record for every combination that validate() accepted (e.g., store-key/version edge cases, or if `unLockExpireResource`'s migration logic diverges from the mixed-source sum used in validation). Any state where `unLockExpireResource` fails to materialize the unlocked record while `validate()` still accepted the request (because it summed the pre-migration locked balance) leads straight to a `NullPointerException` in the middle of `execute()`.

This is unlike the store-lookup methods seen elsewhere in the codebase (e.g. `MarketPairPriceToOrderStore.get()`, which throws `ItemNotFoundException` instead of returning null and is declared accordingly): `DelegatedResourceStore.get()` here is used as a null-returning lookup, and the surrounding code at lines 170-176 explicitly handles `unlockResource == null` semantics (`unlockResource = null;`) after the switch, showing the author was aware null is possible for this variable, but forgot to guard the dereference inside the switch itself.

### Impact Explanation
`NullPointerException` is an unchecked `RuntimeException`; unlike `ContractValidateException`/`ContractExeException`, it is not part of the actuator's expected checked-exception contract and is not caught by the `catch` blocks the rest of `execute()` relies on (there is no try/catch around lines 128-176 at all). Depending on how the caller in block/transaction processing handles uncaught runtime exceptions during `execute()`, this can:
- Abort processing of the transaction/block in an unexpected way, and if this occurs deterministically for a validly-signed transaction that different nodes process identically, it produces a **denial of service that repeats every time the transaction is (re)played** (e.g., during re-sync, historical replay, or re-broadcast), analogous to the KCM crash-loop in the reference advisory.
- If block-application code does not defensively catch `Throwable`/`RuntimeException` around actuator execution, the exception could propagate up through `Manager` and halt the node's block-application/consensus loop, effectively taking the node offline for that block until manually patched or the offending transaction is filtered — an availability/DoS impact on a chain node's ability to serve/produce blocks.

I was not able to fully confirm from the excerpts obtained whether the surrounding `Manager`/`TransactionTrace` execution path wraps `actuator.execute()` calls in a blanket `catch (Throwable e)`/`catch (Exception e)` that would down-grade the crash to a failed-transaction log entry instead of an unhandled propagation — this needs verification with a session that can inspect `framework/src/main/java/org/tron/core/db/Manager.java` and `actuator/src/main/java/org/tron/core/actuator/TransactionTrace.java` (or equivalent) in full.

### Likelihood Explanation
The triggering path — `UnDelegateResourceContract` — is directly reachable by any account holder who has previously delegated bandwidth/energy resources with a lock period (`DelegateResourceContract` with `lock=true`) and waits for the lock to expire before calling undelegate without ever creating an "unlocked" delegation entry for that owner/receiver pair. This requires only two ordinary, unprivileged signed transactions (delegate-locked, then undelegate after expiry) — no special permissions, no malicious validator/witness involvement, and no reliance on TVM contract internals. This satisfies the requirement of being reachable from "a single signed transaction" from a normal broadcaster.

### Recommendation
- Add an explicit null check on `unlockResource` before dereferencing it in the `BANDWIDTH`/`ENERGY` cases of `execute()`, mirroring the existing `if (unlockResource == null) { ... }` pattern already used later in the same method (lines 170-176), e.g. construct a fresh zero-balance `DelegatedResourceCapsule` when `unlockResource == null` before performing `addFrozenBalanceForXxx`.
- Align the acceptance logic in `validate()` and the state-mutation logic in `execute()` so that whenever `validate()` counts an already-expired lock balance toward sufficiency, `execute()` is guaranteed (not just expected) to have migrated that balance into a non-null unlocked record via `unLockExpireResource` before dereferencing it — add an assertion/defensive fallback rather than relying on migration side effects.
- Apply the same defensive-null-check review to `UnDelegateResourceProcessor` (the TVM-native-contract equivalent under `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`), whose `validate()`/`execute()` split at lines 61-66/160-165 follows a similar (though slightly different) unlock-only lookup pattern and should be checked for the same class of gap.
- Add a regression test that calls `undelegateresource` for an owner/receiver pair that has **only** an expired locked delegation and no unlocked delegation record, verifying `execute()` completes without throwing `NullPointerException`.

### Proof of Concept
1. Owner account calls `DelegateResourceContract` with `lock = true` and `lock_period > 0` for BANDWIDTH toward a receiver, creating only a locked (`createDbKeyV2(owner, receiver, true)`) `DelegatedResourceCapsule`; no unlocked (`createDbKeyV2(owner, receiver, false)`) record is ever created for this pair.
2. Wait for the lock period to expire (`lockResourceCapsule.getExpireTimeForBandwidth() < now`).
3. Broadcast an `UnDelegateResourceContract` transaction from the owner requesting `unDelegateBalance <= lockResourceCapsule.getFrozenBalanceForBandwidth()`.
4. `validate()` passes: `unlockResourceCapsule == null`, but `delegateBalance` (from the expired lock) is `>= unDelegateBalance`, so no `ContractValidateException` is thrown (see lines 269-284).
5. During `execute()`, if `delegatedResourceStore.unLockExpireResource(...)` does not create/return a corresponding unlocked record for `unlockKey` in this exact state, the subsequent `delegatedResourceStore.get(unlockKey)` returns `null`, and `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` throws `NullPointerException`, crashing/aborting execution of an otherwise validly-signed and validated transaction.

Note: I could not execute this against a running node in this session to confirm the exact runtime behavior of `unLockExpireResource` for every code path (it may in some versions always populate the unlocked record for any expired lock, which would mean the null path is unreachable in practice); this should be verified with a live/test-suite run of `UnDelegateResourceActuator` covering the "expired-lock-only, no-unlocked-record" scenario before treating this as fully confirmed exploitable.
