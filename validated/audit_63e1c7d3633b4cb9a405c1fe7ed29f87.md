### Title
StackerDB chunk signatures are not bound to the target smart contract, permitting cross-contract chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the message that gets signed/verified for a StackerDB chunk as `hash(slot_id, slot_version, data_hash)`. It does not include the StackerDB's smart contract identifier (the "domain"/context the chunk is written to). Consequently, a validly signed chunk broadcast for one StackerDB contract can be relayed by any unprivileged network peer as a `StackerDBPushChunk` for a *different* StackerDB contract and will pass signature validation, as long as the original signer occupies the same `slot_id` in the target contract. This is analogous to the OctoberCMS/Laravel bug where encrypted cookie values were not bound to the cookie's name, letting content generated for one context be replayed into another.

### Finding Description
The signed digest for a chunk is: [1](#0-0) 

which is verified against a per-(contract, slot) signer address via: [2](#0-1) 

The runtime validation path, `PeerNetwork::validate_received_chunk`, looks up the expected signer for `(smart_contract_id, slot_id)` and checks `slot_metadata.verify(&addr)` — but `smart_contract_id` is taken from the *outer, attacker-controlled message envelope* (`StackerDBPushChunkData::contract_id`), not from anything covered by the signature itself: [3](#0-2) 

This function is reachable directly from unsolicited, unauthenticated network input in `handle_unsolicited_StackerDBPushChunk`, which passes `&chunk_data.contract_id` (attacker-supplied) straight into `validate_received_chunk`: [4](#0-3) 

Because the smart-contract identifier is never part of the signed digest, the equality being checked is only "does this signature validate for signer X at this slot_id/version/hash" — not "was this chunk signed *for this particular StackerDB*." If the same signer address occupies the same `slot_id` in two different StackerDB contracts (which is the normal case for the `.signers-<cycle>-<message_id>` family of contracts, since all message-type contracts for a given reward cycle derive slot assignments from the same sorted signer list, as seen in `signers_tests.rs` and `signer_set.rs`/`signers.clar`), then a chunk that was legitimately signed and broadcast for contract A (e.g. `StateMachineUpdate`) is also a validly-signed chunk for contract B (e.g. `BlockResponse`) at the same slot. A completely unprivileged network observer can capture such a broadcast chunk (StackerDB data is not confidential — it is gossiped in the clear) and re-wrap it with a different `contract_id` field in a `StackerDBPushChunk` message and send it to any node.

The chunk that passes this check is then persisted via `try_replace_chunk` and re-broadcast network-wide in `Relayer::process_stacker_db_chunks` / `process_pushed_stacker_db_chunks`: [5](#0-4) 

### Impact Explanation
This breaks the intended equality "chunk stored under contract X was authorized for contract X" (analogous to "cookie value belongs to the cookie it was issued under" in the reference advisory). An attacker who has observed one legitimately-signed chunk from a signer can inject that exact same signed payload into an unrelated StackerDB slot/contract that the signer also occupies, causing the node to store and gossip signer-attributed data in the wrong DB/context (e.g., a `BlockPreCommit` payload accepted into the `StateMachineUpdate` slot, or vice versa). Depending on how downstream consumers key off `contract_id` when reading data out of the `chunks` events dispatcher (`StackerDBEventDispatcher::new_stackerdb_chunks`), this can corrupt whichever consensus/miner-coordination logic keys purely off `(contract_id, slot_id)` to interpret chunk contents, since a byte-identical, validly-signed payload for context A is now indistinguishable from an authentic payload deliberately produced for context B. This qualifies as unauthorized/forged-data propagation network-wide, reached by any unprivileged peer relaying previously-observed gossip traffic — no attacker key or admin role is required, only observation of one legitimate broadcast.

### Likelihood Explanation
Likelihood is bounded by two preconditions that both hold naturally in the current design: (1) StackerDB chunks are broadcast in the clear to all peers, so obtaining a legitimately signed chunk requires no privilege; (2) slot assignment for the `.signers-<cycle>-<n>` contract family is derived identically (same sorted signer list) across all message-type contracts in a reward cycle, so the same address occupies the same `slot_id` across contracts with high probability. The relay/validation code path performing the check (`validate_received_chunk`, `handle_unsolicited_StackerDBPushChunk`) is exercised directly on unauthenticated, unsolicited p2p input, making this reachable without prior connection state beyond a live conversation.

### Recommendation
Include the StackerDB's `smart_contract_id` (and possibly a protocol/domain-separation tag) inside `SlotMetadata::auth_digest()` so that a chunk signature is cryptographically bound to the specific StackerDB it was produced for, mirroring the fix applied for OctoberCMS/Laravel cookies (binding the encrypted value to the cookie name). This requires a signature-format/protocol version bump since it changes what gets hashed and signed.

### Proof of Concept
1. Reward cycle `R` has signer set `S`; signer `addr` is assigned `slot_id = k` in both `.signers-R-1` (BlockResponse) and `.signers-R-2` (StateMachineUpdate) contracts, per the shared sorted signer-list assignment.
2. `addr`'s operator signs and broadcasts a `StackerDBChunkData { slot_id: k, slot_version: v, data, sig }` for `.signers-R-1` via normal signer StackerDB operation.
3. An unprivileged network observer intercepts this broadcast `StackerDBPushChunk` (contract_id = `.signers-R-1`).
4. The observer re-sends the identical `chunk_data` (same `slot_id`, `slot_version`, `sig`, `data`) wrapped in a new `StackerDBPushChunkData { contract_id: .signers-R-2, ... }` to a victim node.
5. `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk(".signers-R-2", ..., data, ...)` looks up `get_slot_signer(".signers-R-2", k) == addr`, then `slot_metadata.verify(&addr)` succeeds because the digest never referenced `.signers-R-1` — the chunk is accepted and stored/broadcast under the wrong contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }
