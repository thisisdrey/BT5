### Title
`AuthCall` with attached deposit permanently debits user balance with no refund path if `near_withdraw` or `on_auth` fails - (File: contracts/defuse/src/contract/intents/state.rs)

### Summary
`auth_call()` in `contracts/defuse/src/contract/intents/state.rs` synchronously debits the signer's internal wNEAR balance, then asynchronously unwraps the wNEAR and forwards it to an arbitrary external `on_auth()` callee. Unlike every other value-moving flow in this contract (`ft_withdraw`, `nft_withdraw`, `mt_withdraw`, `mt_transfer_call`), this path has no resolver/refund callback: it is `.detach()`ed, so any failure downstream of the debit (failed `near_withdraw`, or a reverting/panicking `on_auth`) leaves the debited amount permanently lost, breaking the "value debited versus value delivered plus refunded" custody binding.

### Finding Description
`auth_call` executes as part of a signed `MultiPayload`/intent (`AuthCall` in `contracts/defuse/core/src/intents/auth.rs`), invoked via `Engine::execute_signed_intent` → `ExecutableIntent::execute_intent` → `State::auth_call`. [1](#0-0) 

When `attached_deposit` is non-zero, the implementation:
1. Synchronously calls `self.withdraw(signer_id, [(wnear_token, amount)], Some("withdraw"), false)`, which immediately subtracts the amount from the signer's internal ledger balance (this happens in the same receipt as `execute_intents`, so it is committed regardless of what happens afterward).
2. Fires an async promise chain: `near_withdraw()` (unwrap wNEAR into real NEAR held by the contract) `.then(do_auth_call(...))`, and finally `.detach()`s the whole chain — there is no `.then()` callback that inspects the outcome and could refund the signer.

`do_auth_call()` (contracts/defuse/src/contract/intents/auth_call.rs:17-24) does check that `near_withdraw` succeeded via `promise_result_checked_void(0)`, but if it didn't, it simply `require!`s and panics — the deposit is not refunded to the signer. Likewise, if `near_withdraw` succeeds but the receiving contract's `on_auth()` (an arbitrary, attacker/solver-controlled `contract_id`) panics or the receipt otherwise fails, nothing credits the amount back to the signer.

Compare this to every other outbound-value path in the same contract, which all use a paired resolver method to refund unused/failed amounts back to the owner:
- `ft_withdraw` → `ft_resolve_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs:154-195) explicitly re-`deposit()`s the unused amount back to `sender_id`.
- `nft_withdraw` → `nft_resolve_withdraw` similarly refunds on failure.
- `mt_withdraw` → `mt_resolve_withdraw` similarly refunds on failure.
- `mt_transfer_call` → `mt_resolve_transfer` (contracts/defuse/src/contract/tokens/nep245/resolver.rs) explicitly refunds unclaimed amounts, even handling the locked-receiver edge case.

`auth_call` has no analogous resolver. The debit made in `internal_sub_balance`/`withdraw` is unconditional and irreversible from the intent executor's perspective, while the actual value transfer downstream is best-effort and can fail for reasons entirely outside the signer's or the protocol's control (e.g., a malicious/broken `on_auth` callee, insufficient gas for `near_withdraw`, or the wNEAR contract rejecting the call).

### Impact Explanation
This breaks the conservation invariant "value debited versus value delivered plus refunded": the internal ledger is debited by `attached_deposit`, but on failure of `near_withdraw` or `on_auth`, no value is delivered to the callee and none is refunded to the signer — the funds are permanently and definitively lost from the user's perspective (destination is a state where the tokens exist nowhere: not in the user's defuse balance, not delivered to the callee, and not held as spendable NEAR by anyone). Any user (or a griefing/malicious `contract_id` chosen in the intent, including a third party front-running with an intentionally reverting `on_auth`) can trigger this, and because `AuthCall.contract_id` is attacker-supplied, an attacker who convinces (or is) a signer to route an `AuthCall` to a contract that reverts `on_auth` guarantees fund loss for that signer with no recovery mechanism, unlike identical flows elsewhere in the codebase.

### Likelihood Explanation
`AuthCall.contract_id` is fully attacker-supplied user input (it's part of a signed intent controlled entirely by the intent author), so triggering a reverting `on_auth()` or an out-of-gas `near_withdraw` is trivial and requires no privileged access — it is directly reachable by any unprivileged signer via `execute_intents`. The absence of the resolver step is a structural gap (not a rare edge case), so any real-world integration with a buggy, malicious, or simply out-of-gas `on_auth` callee will hit this permanently, unrecoverable loss path.

### Recommendation
Add a resolver callback (`auth_call_resolve` or similar) to the `near_withdraw().then(do_auth_call(...))` promise chain, mirroring the existing `ft_resolve_withdraw`/`mt_resolve_withdraw` pattern: check the result of `near_withdraw` and/or `on_auth`, and if either fails, re-credit `attached_deposit` back to `signer_id`'s wNEAR balance via `deposit()`, exactly as done in `ft_resolve_withdraw`.

### Proof of Concept
1. User signs an `AuthCall` intent with `attached_deposit > 0` and `contract_id` set to a contract whose `on_auth()` implementation unconditionally panics (or simply any account that doesn't implement `on_auth` at all, causing a `MethodNotFound`/execution failure).
2. Submit via `execute_intents`. `state.rs::auth_call()` synchronously calls `self.withdraw(...)`, debiting the user's internal wNEAR balance — this state change is part of the committed `execute_intents` receipt and is not rolled back by subsequent receipt failures.
3. The chained `near_withdraw().then(do_auth_call(...))` promise executes in a later receipt; `on_auth()` on the target contract panics, or `do_auth_call`'s `require!(promise_result_checked_void(0).is_ok(), ...)` panics if `near_withdraw` itself failed.
4. No compensating `deposit()` call exists anywhere in this code path (unlike `ft_resolve_withdraw`), so the user's `attached_deposit` amount of wNEAR is permanently gone from their balance, was never delivered to any account, and cannot be recovered.

Note: I was unable to execute this against a live sandbox to confirm receipt-level rollback semantics empirically; this analysis is based on the documented NEAR receipt model (parent receipt state changes commit independently of async child receipts) and the absence of a resolver, both of which are directly visible in the cited source.

```rust
    fn auth_call(&mut self, signer_id: &AccountIdRef, auth_call: AuthCall) -> Result<()> {
        if auth_call.attached_deposit.is_zero() {
            Self::do_auth_call(signer_id.to_owned(), auth_call)
        } else {
            // withdraw from signer's wNEAR balance
            self.withdraw(
                signer_id,
                [(
                    Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                    auth_call.attached_deposit.as_yoctonear(),
                )],
                Some("withdraw"),
                false,
            )?;

            ext_wnear::ext(self.wnear_id.clone())
                .with_attached_deposit(NearToken::from_yoctonear(1))
                .with_static_gas(NEAR_WITHDRAW_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .near_withdraw(U128(auth_call.attached_deposit.as_yoctonear()))
                .then(
                    // do_auth_call only after unwrapping NEAR
                    Self::ext(env::current_account_id())
                        .with_static_gas(
                            Self::auth_call_callback_gas(&auth_call)
                                .ok_or(DefuseError::GasOverflow)?,
                        )
                        .do_auth_call(signer_id.to_owned(), auth_call),
                )
        }
        .detach();

        Ok(())
    }
```
