## Title
Reward-per-token griefing via low `PRECISION_SCALING_FACTOR` permanently zeroes staker rewards in `pallet-asset-rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes `reward_per_token` by scaling `reward_rate_per_block * blocks_elapsed` by `PRECISION_SCALING_FACTOR = 4096` before dividing by `total_tokens_staked`. [1](#0-0) [2](#0-1)  Because `update_pool_rewards` unconditionally advances `last_update_block` and overwrites `reward_per_token_stored` with this computed value even when integer division rounds it to zero, any period where the per-token increment underflows to zero results in permanently lost reward accrual for that period. [3](#0-2) 

## Finding Description
`reward_per_token` is:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [2](#0-1) 

`PRECISION_SCALING_FACTOR` is a fixed `u16` constant of `4096`, far smaller than the `1e18`-scale precision used elsewhere in the runtime (e.g., nomination-pools uses wide `U256` arithmetic for its equivalent computation). [1](#0-0) [4](#0-3) 

`update_pool_rewards` unconditionally sets `last_update_block` to the current block and stores the (possibly zero-incremented) `reward_per_token`, with no accumulation of "dust" carried forward:
```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;

    Ok(new_pool_info)
}
``` [3](#0-2) 

`update_pool_and_staker_rewards` calls `reward_per_token` then `update_pool_rewards`, and is invoked unconditionally at the start of every `stake` and `unstake` extrinsic, both of which are callable by unprivileged signed accounts. [5](#0-4) [6](#0-5) [7](#0-6)  Because `blocks_elapsed` resets to (effectively) zero-to-small values whenever the update runs, an attacker who calls `stake`/`unstake` every block against a pool with sufficiently large `total_tokens_staked` relative to `reward_rate_per_block * 4096` can keep the numerator smaller than the denominator, causing `ensure_div` to floor to `0` on every call while `last_update_block` still advances — permanently discarding that period's reward accrual with no dust carryover mechanism.

I verified all cited code paths directly in the repository and confirm they match the claim exactly: the constant, the division-based computation, and the unconditional state advancement in `update_pool_rewards`, as well as the permissionless call sites in `stake`/`unstake`.

## Impact Explanation
This matches the "permanent user-fund lock" impact class: reward tokens deposited into the pool account remain unspendable by honest stakers because `reward_per_token_stored` (the exact corrupted value) never advances, so `derive_rewards` — which multiplies staker `amount` by the stored `reward_per_token` delta — always returns zero increments for affected periods. [8](#0-7)  Funds are only recoverable by the pool admin via `cleanup_pool`, and only once all stakers have exited, so honest stakers experience an unbacked loss of expected rewards despite the pool being funded.

## Likelihood Explanation
The exploit requires only an unprivileged signed account calling public `stake`/`unstake` extrinsics repeatedly, which is inexpensive (freeze/unfreeze of a small amount) and requires no special privileges, governance, or off-chain assumptions. [6](#0-5)  The precondition — `total_tokens_staked` large relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR` — is a normal configuration for pools pairing high-decimal staked assets against low-rate/low-decimal reward assets, making this readily triggerable rather than a contrived edge case.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to at least `10^18` and/or use wide (`U256`) intermediate arithmetic for the multiplication/division in `reward_per_token`, mirroring the approach used in nomination-pools' point-to-balance conversion. [4](#0-3)  Additionally, track and carry forward any undistributed remainder rather than silently discarding it when the computed increment rounds to zero, or rate-limit `last_update_block` advancement to require a nonzero per-token increment.

## Proof of Concept
1. Create a pool with an 18-decimal staked asset and a 6-decimal reward asset, with `reward_rate_per_block` set to a small value (e.g., ~12000 raw units per block) and `total_tokens_staked` reaching `1_000_000e18`.
2. An attacker account calls `stake(pool_id, 1)` every block. Each call triggers `update_pool_and_staker_rewards` → `reward_per_token()`, computing `12000 * 1 * 4096 / 1_000_000e18 ≈ 0` after integer division. [2](#0-1) 
3. `update_pool_rewards` still advances `last_update_block` to the current block, discarding that block's reward accrual permanently. [3](#0-2) 
4. Repeating every block over an extended period keeps `reward_per_token_stored` at its initial value; any honest staker calling `harvest_rewards` receives `staker_info.rewards = 0` despite the pool holding fully funded reward tokens.
