### Title
Unauthenticated `header.RecvError` packet with spoofed source + guessed `RemoteIndex` can force tunnel teardown - (File: outside.go)

### Summary
`Interface.readOutsidePackets` dispatches `header.RecvError` packets directly to `handleRecvError` before any AEAD/handshake authentication is performed. `handleRecvError` looks up the `HostInfo` via `hostMap.QueryReverseIndex(h.RemoteIndex)` and, if the source UDP address matches `hostinfo.remote`, calls `f.closeTunnel(hostinfo)`, tearing down a live session based solely on an unauthenticated packet plus an address-equality check.

### Finding Description
In `outside.go`, packet type dispatch happens immediately after `h.Parse(packet)` and basic header sanity checks (version/subtype), and *before* any per-hostinfo cryptographic verification: [1](#0-0) 

For `header.RecvError`, the packet is handled purely based on `h.RemoteIndex` (attacker-controlled, 32 bits) and the source address of the UDP datagram (spoofable), with no requirement that the sender have completed a Noise handshake or possess any session key. This is unlike the `header.Message`/`header.Test`/`header.CloseTunnel` types, which are only actioned after `hostinfo.ConnectionState.Decrypt` succeeds (see the encrypted-packet branch guarded by `Decrypt` at lines 126-132, versus the unauthenticated `RecvError` short-circuit at line 81-83). [2](#0-1) 

`handleRecvError` resolves the hostinfo using `hostMap.QueryReverseIndex(h.RemoteIndex)`: [3](#0-2) [4](#0-3) 

If the looked-up `hostinfo.remote` equals the (spoofable) source address of the packet, the code proceeds to `f.closeTunnel(hostinfo)`, tearing down session state and removing hostmap/index entries via `handshakeManager.DeleteHostInfo` — all without verifying any cryptographic proof that the sender is the actual remote peer. The only two barriers to exploitation are: (1) guessing/observing the victim's 32-bit `RemoteIndex`, and (2) the ability to spoof the source IP:port to match the victim's currently-known remote address for that tunnel.

### Impact Explanation
This allows an unauthenticated, off-path attacker who can spoof UDP source addresses (and who has observed or guessed the 32-bit reverse index — which is visible in every packet exchanged with that peer over the wire, so any attacker capable of packet-address spoofing along the path can also observe traffic and read `RemoteIndex` directly from headers) to force teardown of an established, legitimate Nebula tunnel. This forces a full re-handshake, causing a denial-of-service-style disruption and creating a window during which existing route/firewall state tied to the old `HostInfo` is invalidated, potentially causing packet loss or in-flight connection disruption for the victim. It does not, however, allow decryption, forgery of application data, or bypass of certificate/CA verification — impact is limited to unauthenticated session/state disruption (forced re-handshake / partial DoS).

### Likelihood Explanation
Exploitability requires the attacker to both know the 32-bit `RemoteIndex` for the target tunnel (trivially learned by observing any packet on that tunnel, since it's sent in cleartext in every header) and to be able to spoof UDP packets with a source address equal to the victim's current remote endpoint. Source-address spoofing is often blocked by network egress/ingress filtering (BCP38) but is feasible for attackers on-path, on shared broadcast networks, or behind ISPs without spoofing protections. Given these preconditions this is a real but conditionally-likely attack — not remotely exploitable from an arbitrary unprivileged internet host without spoofing capability.

### Recommendation
Do not act on `header.RecvError` based purely on `RemoteIndex` + source-address match. Options: require the `RecvError` packet to be authenticated (e.g., carry a MAC keyed with the session key, or be wrapped/verified similarly to how relay/message packets are authenticated before triggering `closeTunnel`), or at minimum require multiple corroborating signals (e.g., a matching outbound packet was recently sent and no reply/ack received) rather than tearing down the tunnel on a single unauthenticated packet.

### Proof of Concept
Unit test in `outside_test.go` (or equivalent):
1. Establish two `HostInfo` structures via a completed handshake between "host A" and "host B" so `f.hostMap` contains a valid reverse index mapping and `hostinfo.remote` is set to B's `netip.AddrPort`.
2. Without completing any additional handshake, construct a raw `header.RecvError` packet with `RemoteIndex` set to the known reverse index for A's `HostInfo` on B's tunnel.
3. Call `f.readOutsidePackets` (or `f.handleRecvError` directly) passing a `via.UdpAddr` spoofed to equal `hostinfo.remote` (B's real address) but from a different physical/logical sender in the test harness.
4. Assert that `f.closeTunnel` is invoked and the `HostInfo` is removed from `hostMap`/`handshakeManager` despite no AEAD/handshake proof having been presented by the caller — i.e., assert this happens even when the test never performs the corresponding Noise handshake step for the "attacker" identity, demonstrating that address equality alone (not authenticated proof) triggers teardown.
