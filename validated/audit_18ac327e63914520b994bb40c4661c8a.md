### Title
Unbounded/unlimited FindAllBranches and FindAllRemoteBranches allow DoS via git-for-each-ref over unbounded ref sets - (File: internal/gitaly/service/ref/find_all_branches.go, internal/gitaly/service/ref/find_all_remote_branches.go)

### Summary
`FindAllBranches` and `FindAllRemoteBranches` build `for-each-ref` options via `buildFindRefsOpts(ctx, nil)`, always passing a `nil` `PaginationParameter`. Unlike `FindLocalBranches`, `FindAllTags`, and `ListRefs`, these two RPCs give the caller no way to bound the number of results, and the server itself imposes no cap: the limit is fixed at `math.MaxInt32`.

### Finding Description
`findAllBranches` and `findAllRemoteBranches` call: [1](#0-0) [2](#0-1) 

`buildFindRefsOpts` derives its limit from `buildPaginationOpts`, which defaults to `math.MaxInt32` when the pagination parameter is `nil`: [3](#0-2) [4](#0-3) 

Because both handlers pass `nil` explicitly instead of forwarding a caller-supplied `PaginationParameter`, there is no client-side or server-side mechanism to bound the ref set being iterated — every reference under `refs/heads` and `refs/remotes` (for `FindAllBranches`), or under `refs/remotes/<name>` (for `FindAllRemoteBranches`), is walked. Contrast this with `FindLocalBranchesRequest`/`FindAllTagsRequest`/`ListRefsRequest`, whose protobuf definitions expose a `pagination_params` field that callers can use to cap `Limit`: [5](#0-4) [6](#0-5) 

`FindAllBranchesRequest` and `FindAllRemoteBranchesRequest` have no such field at all, so there is no protocol-level way to limit the response even if the server wanted to honor one.

For each matched reference, the response writer performs an additional `catfile` lookup to resolve the full commit object before it can be streamed: [7](#0-6) 

This means an ordinary, unprivileged client (any user with read access to a repository who can call the RPC) that has pushed a large number of branches/remote-tracking refs — for example, via a fork with thousands of remote-tracking branches or by pushing thousands of branches to a repository — can trigger a single request that forces gitaly to spawn `git-for-each-ref`, enumerate the entire (unbounded) ref namespace, and perform one `catfile` object resolution per ref, all without ever being able to specify a page size.

### Impact Explanation
This is a resource-exhaustion / denial-of-service vector: a repository with a very large number of branches or remote-tracking refs makes `FindAllBranches`/`FindAllRemoteBranches` consume proportionally large CPU, memory, and catfile-process time on the gitaly node servicing the request, with no limit the operator or caller can apply through the RPC surface. Repeated or concurrent calls against such a repository can degrade or block the RPC handler and the shared `catfileCache`/process pool used by other requests on the same node, affecting availability of the ref service more broadly. This matches the "unbounded iteration" bug class from the reference report (unbounded loop growth causing resource/gas-equivalent exhaustion), translated to a gitaly RPC-handler resource-limit issue.

### Likelihood Explanation
Likelihood is moderate: exploitation only requires an authenticated caller of the `RefService` (any client permitted to call read-only `ACCESSOR` RPCs against a repository, e.g. via GitLab pushing a large number of branches) and a repository with a large ref count, which is plausible in real-world large monorepos or heavily-forked repositories with many remote-tracking branches. No privileged access or protocol violation is required — this is reachable through ordinary accessor RPC calls.

### Recommendation
- Add a `pagination_params` field to `FindAllBranchesRequest` and `FindAllRemoteBranchesRequest` (mirroring `FindLocalBranchesRequest`/`ListRefsRequest`) and thread it through to `buildFindRefsOpts` instead of passing `nil`.
- Alternatively/additionally, enforce a server-side hard cap (independent of client input) on the number of refs processed per call, and/or require streaming pagination for these RPCs by default.
- Consider imposing a maximum on `ItemsPerMessage`-scaled work (i.e., total refs processed) irrespective of caller behavior, so a single request cannot force unbounded `for-each-ref` + per-ref `catfile` work.

### Proof of Concept
1. Create/push a repository with a very large number of branches or remote-tracking refs (e.g., tens of thousands of `refs/remotes/<remote>/*` entries), which is achievable by an ordinary user via normal `git push`/fetch operations that create remote-tracking refs.
2. Call `RefService.FindAllRemoteBranches` (or `FindAllBranches`) against that repository.
3. Observe that gitaly executes `git-for-each-ref` over the entire ref set with `Limit = math.MaxInt32` (per `buildPaginationOpts` defaulting when `nil` is passed at [2](#0-1) ) and performs one `catfile` object lookup per ref via `buildBranchWithCatfile`/`buildAllBranchesBranch` ( [7](#0-6) ), with no request-level way to bound the work, unlike sibling RPCs that accept `pagination_params`.

func newFindAllBranchesWriter(stream gitalypb.RefService_FindAllBranchesServer, objectReader catfile.ObjectContentReader) lines.Sender {
	return func(refs [][]byte, hasNextPage bool) error {
		var branches []*gitalypb.FindAllBranchesResponse_Branch
		ctx := stream.Context()

		for _, ref := range refs {
			elements, err := parseRef(ref, len(localBranchFormatFields))
			if err != nil {
				return err
			}
			branch, err := buildAllBranchesBranch(ctx, objectReader, elements)
			if err != nil {
				return err
			}
			branches = append(branches, branch)
		}
		return stream.Send(&gitalypb.FindAllBranchesResponse{Branches: branches})
	}
}

func buildPaginationOpts(ctx context.Context, p *gitalypb.PaginationParameter) *paginationOpts {
	opts := &paginationOpts{}
	opts.IsPageToken = func(_ []byte) bool { return true }
	opts.Limit = math.MaxInt32

	if p == nil {
		return opts
	}

	if p.GetLimit() >= 0 {
		opts.Limit = int(p.GetLimit())
	}
