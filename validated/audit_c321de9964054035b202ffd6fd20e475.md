### Title
Heap buffer over-read via unvalidated extra-field size in ijar's ZIP central-directory parser - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` walks the "extra fields" of a ZIP central-directory entry using an attacker-controlled 16-bit `data_size` with no bound check against the end of the extra-field region or the mmap'd input buffer, unlike the parallel, already-hardened implementation in `src/tools/singlejar/zip_headers.h`.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-supplied bytes with no `EnsureRemaining`-style validation (that check exists only in `InputZipFile::ProcessLocalFileEntry`, not in the central-directory reader): [1](#0-0) 

After computing `extra_p`/`p` purely from the unchecked `extra_field_length`, the loop advances `extra_p` by the attacker-controlled `data_size` on every iteration and dereferences `get_u8le(extra)` for a matching ZIP64 tag, without ever checking that `extra_p + data_size` stays within `[extra_p_start, p)` or within the underlying mmap'd file: [2](#0-1) 

This is structurally the same bug class as the JerryScript analog (`scanner_literal_is_created`): a size field taken from untrusted input drives a pointer/index without a bounds check, producing an out-of-bounds read. Bazel's own `singlejar` tool already recognizes and defends against exactly this ZIP-extra-field pattern — `ExtraField::find` explicitly checks `start + extra_field->size() > end` before dereferencing, and there's a regression test proving the fix: [3](#0-2) [4](#0-3) [5](#0-4) 

The ijar implementation of the same conceptual data structure never received this hardening.

### Impact Explanation
`ProcessCentralDirEntry` is on the path used every time ijar (interface-jar generation) or its callers parse a `.jar`/`.zip` originating from an untrusted source (e.g., a `java_import`/Maven artifact fetched from a hostile registry or mirror). A crafted central-directory entry with a short `extra_field_length` but an embedded extra-field record whose `data_size` overruns that region causes `get_u8le`/`get_u2le` reads past the mmap'd file buffer. Depending on layout this yields at minimum an out-of-bounds read (crash/ASan heap-buffer-overflow), and the OOB bytes are used to overwrite `*uncompressed_size`/`*compressed_size`/`*offset`, which downstream feed `EnsureRemaining`, `memcpy` sizing, and output-length calculations (`CalculateOutputLength`, `ProcessFile`/`UncompressFile`), meaning corrupted size/offset values derived from adjacent heap memory can propagate into further buffer arithmetic.

### Likelihood Explanation
Reachable purely from attacker-published archive bytes with no build-time integrity gap needed beyond normal `http_archive`/`maven_jar`-style fetch of a jar (checksums, if declared, verify the archive as a whole but do not prevent malformed-but-hash-matching-if-attacker-controls-origin content from containing this structure when the archive itself is the attacker's own hosted artifact). I could not fully trace every call site that invokes `ProcessCentralDirEntry`/`InputZipFile::Open` to confirm there is no additional outer bounds check on `central_dir_` size elsewhere in `zip.cc` that I did not view in this session (e.g., EOCD-driven overall length validation) — this is a residual uncertainty given tool-call limits, and it should be checked when reproducing.

### Recommendation
Port the same defensive bound check used in `ExtraField::find` (`src/tools/singlejar/zip_headers.h`) into `InputZipFile::ProcessCentralDirEntry`'s extra-field loop in `third_party/ijar/zip.cc`: before dereferencing `header_id`/`data_size` or advancing `extra_p`, verify `extra_p + sizeof(header) <= p` and `extra_p + total_entry_size <= p`, and fail cleanly (as singlejar does with "malformed extra field") rather than continuing to read.

### Proof of Concept
Construct a ZIP central-directory entry (following the pattern of `CreateZipWithMalformedExtraField()` in `src/tools/singlejar/output_jar_simple_test.cc`) where `extra_field_length` is small (e.g. 4 bytes) but the embedded extra record's `payload_size`/`data_size` is set to a large value (e.g. `0xF000`) with tag `1` (ZIP64), then feed this crafted jar as an input to the ijar binary (`third_party/ijar/zip_main.cc extract`/build path) or a Bazel rule that triggers ijar generation on this jar; run under ASan and observe a heap-buffer-overflow/over-read inside `InputZipFile::ProcessCentralDirEntry`, contrasted with the already-passing `OutputJarSimpleTest.MalformedExtraField` (`ASSERT_DEATH(..., "malformed extra field")`) which shows singlejar's parallel code path is protected while ijar's is not.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
