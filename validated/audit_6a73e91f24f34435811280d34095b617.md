Based on my investigation, the strongest local analog to the "blacklisted immutable payout address permanently locks funds" bug class is in `pallet-treasury`'s spend/payout flow, where the `beneficiary` recorded in a `Spend` is fixed at approval time and cannot be changed, and a failed payout (e.g. a blocked/frozen beneficiary account) leaves the spend retriable only to the *same* unreachable beneficiary, with no admin path to redirect funds.

### Title
Treasury spend funds can be permanently stuck when the recorded beneficiary becomes unable to receive the asset - (File: `substrate/frame/treasury/src/lib.rs`)

### Summary
`pallet-treasury::payout` pays out a `Spend` to the `beneficiary` address stored at spend-creation time via `T::Paymaster::pay(&spend.beneficiary, ...)` [1](#0-0) . This mirrors the reported bug class: a payout destination that is fixed/hardcoded per-spend and cannot be altered, so if the underlying asset implementation (e.g. `pallet-assets`, which supports `TokenError::Blocked`/`Frozen` semantics as shown in tests such as `transferring_to_blocked_account_should_not_work`) blocks that specific beneficiary, the transfer will keep failing forever [2](#0-1) [3](#0-2) .

### Finding Description
`payout()` looks up the `Spend` by index, validates timing/status, and then calls `T::Paymaster::pay(&spend.beneficiary, spend.asset_kind.clone(), spend.amount)`, storing the result as `PaymentState::Attempted { id }` [4](#0-3) . There is no dispatchable that allows changing `spend.beneficiary` after the spend has been approved/created. If the beneficiary later becomes blocked/frozen for the configured asset (analogous to a blacklisted `STADIUM_ADDRESS` in the external report), every subsequent retry through `check_status`/`payout` will target the same unreachable account, and the treasury-held funds allocated to that spend can never be delivered — exactly the "funds stuck in the contract forever" pattern from the report, just realized as a pallet-level design instead of a Solidity contract.

Unlike the external Solidity bug, this is not solved by an "admin can update the address" fix either, because there is intentionally no dispatchable to mutate `beneficiary` on an existing `Spend` once created — the same "immutable payout target + no recovery path" root cause.

### Impact Explanation
If a governance-approved treasury spend targets a beneficiary that is later frozen/blocked by the asset pallet (deliberately or via a compliance freeze), the earmarked treasury funds become permanently unretrievable through the normal payout flow, since `payout`/`check_status` always operate on the immutable `spend.beneficiary`. This is a fund-lock condition consistent with the "Impacts" gate's "permanent user-fund lock" category.

### Likelihood Explanation
This requires the beneficiary account to become blocked/frozen for the relevant asset after a spend is created but before/during payout — a scenario that is plausible for asset classes supporting freeze/block semantics (e.g. `pallet-assets`) but not for the native `Balances` pallet (which has no `Blocked` semantics). The likelihood is therefore asset/config-dependent rather than universally exploitable, and I could not fully verify from the index whether recent `check_status`/retry logic or the `Paymaster` trait implementations used in-tree runtimes include any redirect/void mechanism for permanently-failing spends — the treasury source beyond line ~758 was not retrievable in this session (tool access was cut off before I could inspect the `check_status` implementation and `SpendStatus`/`void_spend` logic in full).

### Recommendation
- Verify whether `pallet-treasury` already exposes a `void_spend`/admin-redirect path for spends whose beneficiary is permanently blocked; if not, add one gated by the same origin that approves spends.
- Ensure `check_status` distinguishes "temporarily failed" vs "permanently blocked" beneficiary errors and surfaces this distinctly so governance can react.
- Consider requiring `Paymaster::pay` implementations to surface a specific "beneficiary rejected" error class so treasury spends can be voided/reissued to a new beneficiary rather than infinitely retried.

### Proof of Concept
Not independently reproducible from the available index slice; the concrete PoC would need to: (1) create and approve a `Spend` to beneficiary `B` for an asset `A` in `pallet-assets`; (2) have origin with `Freezer`/admin authority `block`/`freeze` account `B` for asset `A` (as demonstrated by `transferring_to_blocked_account_should_not_work` in `substrate/frame/assets/src/tests.rs` [2](#0-1) ); (3) call `Treasury::payout(index)` and observe the transfer inside the configured `Paymaster` fail with `TokenError::Blocked`; (4) confirm no dispatchable exists to change `spend.beneficiary`, leaving the spend permanently retriable-but-failing.

Given the incomplete verification of the `check_status`/void-spend logic (session ended before I could read it), I present this with reduced confidence rather than as a fully proven exploit chain.

			ensure_signed(origin)?;
			let mut spend = Spends::<T, I>::get(index).ok_or(Error::<T, I>::InvalidIndex)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now >= spend.valid_from, Error::<T, I>::EarlyPayout);
			ensure!(spend.expire_at > now, Error::<T, I>::SpendExpired);
			ensure!(
				matches!(spend.status, PaymentState::Pending | PaymentState::Failed),
				Error::<T, I>::AlreadyAttempted
			);

			let id = T::Paymaster::pay(&spend.beneficiary, spend.asset_kind.clone(), spend.amount)
				.map_err(|_| Error::<T, I>::PayoutError)?;

			spend.status = PaymentState::Attempted { id };
			spend.expire_at = now.saturating_add(T::PayoutPeriod::get());
			Spends::<T, I>::insert(index, spend);

			Self::deposit_event(Event::<T, I>::Paid { index, payment_id: id });
