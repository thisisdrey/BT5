### Title
Unbounded `read_to_end` on HTTP RPC response allows a malicious StackerDB replica/node to OOM a signer client - (File: `libsigner/src/http.rs`)

### Summary
`StackerDBSession::rpc_request` (`libsigner/src/session.rs`) calls `run_http_request` (`libsigner/src/http.rs`) to talk to a Stacks node's StackerDB HTTP RPC endpoint. Unlike every other HTTP body-parsing path in this codebase, `run_http_request` reads the entire response with an **unbounded** `sock.read_to_end(&mut buf)` before any length checks are applied, so a malicious or compromised counterparty can force the signer to buffer an arbitrarily large amount of data into memory.

There is no cap analogous to `MAX_MESSAGE_LEN`, `BoundReader`, or `Content-Length`-based capping applied to this initial read — `buf` grows without limit for as long as the remote endpoint keeps sending bytes (or until the OS/process runs out of memory). Only *after* the full response has been buffered does the code call `decode_http_response` (which parses headers/status) and `decode_http_body` (which, for chunked bodies, does apply `MAX_MESSAGE_LEN` via `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())`): [2](#0-1) [3](#0-2) 

This is the same bug class as the report: the caller trusts a remote/less-trusted party to return a modest amount of data, but nothing bounds the actual bytes accepted before they are loaded into memory — a large response (chunked or not) increases the receiver's cost, or exhausts memory, before it is even parsed to see whether it's valid or oversized.

Compare with the rest of the P2P/HTTP stack, which is careful to bound every read:
- `stackslib/src/net/httpcore.rs`'s HTTP client path enforces `MAX_MESSAGE_LEN` and dispatches to bounded parsers (`parse_bytes`, `BoundReader`) for both known-length and chunked responses.
- `stackslib/src/net/connection.rs`'s `recv_bytes`/`buffer_message_bytes` enforces `inbox_maxlen` and `MAX_MESSAGE_LEN`-based `message_remaining` bounds before ever appending to an internal buffer.

`run_http_request` in `libsigner` (used by `StackerDBSession`, the signer's own HTTP client to a Stacks node's StackerDB RPC) breaks this pattern by reading to completion with no bound at all.

### Impact Explanation
This maps to the "bounded compute DoS on a read endpoint" class, but here it is worse — there's no bound at all applied to the initial socket read. Any Stacks node the signer is configured to talk to (or a man-in-the-middle/malicious peer masquerading as that node's TCP endpoint) can respond to a `list_chunks`/`get_chunks`/`put_chunk` RPC with an unbounded stream of bytes, forcing the signer process to allocate unbounded memory in `run_http_request`'s `buf`, causing memory exhaustion / crash (DoS) of the signer. The only mitigating factor is `sock.set_read_timeout` — bandwidth is still bounded by time, but there is no bound on *bytes*, so a fast/local or high-bandwidth malicious host can still push a large payload within the configured timeout window, and a slow-but-persistent attacker can send data indefinitely up to the timeout envelope on each read call, growing `buf` on every `read()` iteration inside `read_to_end`.

### Likelihood Explanation
The signer's `host` in `StackerDBSession` is configuration-driven, so exploitation normally requires the configured node (or something impersonating it on the network path, e.g. DNS/network-level attacker, or a compromised/malicious node an operator points a signer at) to return oversized data. This is a real, reachable code path in normal signer operation (every RPC round-trip goes through `run_http_request`), but it does depend on the counterparty (the "server" side of this client connection) being adversarial, which is a narrower attack surface than a fully open unauthenticated listener.

### Recommendation
Bound the initial socket read the same way the rest of the codebase bounds HTTP bodies: use a `BoundReader`/limited reader (e.g., capped at `MAX_MESSAGE_LEN` or a smaller, request-appropriate limit) instead of raw `sock.read_to_end(&mut buf)`, and fail the request if the limit is exceeded, mirroring the `MAX_MESSAGE_LEN` enforcement already used in `decode_http_body`/`stackslib/src/net/httpcore.rs`.

### Proof of Concept
1. Point a `StackerDBSession` at a malicious TCP endpoint (e.g. by MITM'ing the configured `host`, or standing up a rogue "node").
2. On accepting the connection, respond to any request with a valid HTTP status line/headers followed by an effectively endless stream of body bytes (either as a huge `Content-Length` body or as an endless series of chunked-encoding chunks), without closing the connection until the client's socket read timeout is imminent.
3. `run_http_request`'s `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) will keep appending to `buf` for the entire duration allowed by `socket_timeout`, consuming memory proportional to attacker-controlled bandwidth × timeout, before any length validation in `decode_http_response`/`decode_http_body` is ever reached.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
