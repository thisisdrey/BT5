### Title
Attacker can fill a victim's `MAX_TOKENS_PER_USER` slots with dust `DepositToken` transfers, DoS-ing deposits and collateral top-ups — (File: contracts/Pool.sol)

### Summary
`Pool` enforces a hard cap of 30 tracked tokens per account (`MAX_TOKENS_PER_USER`) shared across `depositTokensOfAccount` and `debtTokensOfAccount`. Any balance-changing `DepositToken` transfer (including `transfer`/`transferFrom` of dust, or `deposit(amount_, onBehalfOf_)`) calls `pool.addToDepositTokensOfAccount(recipient)`, which reverts with `UserReachedMaxTokens` once the recipient has 30 entries. An unprivileged attacker can deposit into every supported collateral and dust-transfer 1 wei of each `DepositToken` to a victim, permanently stuffing the victim's list. After that, any action that would add a *new* token to the victim's account — depositing a different collateral (`deposit` → `_mint` → `addToDepositTokensOfAccount`), receiving a new deposit token, or receiving seized collateral — reverts.

### Finding Description
- `Pool.sol:79` `MAX_TOKENS_PER_USER = 30`; `Pool.sol:143-148` `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount + depositTokensOfAccount >= 30`; `Pool.sol:216-220` `addToDepositTokensOfAccount` is gated by that modifier.
- `DepositToken.sol:498-526` `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was 0 — with no opt-out, no minimum amount, and no consent. Any holder (or `deposit`'s `onBehalfOf_`) can push an entry onto an arbitrary victim's list.
- Removal only happens when the victim's balance for that token returns to 0 (`DepositToken.sol:523-525` → `removeFromDepositTokensOfAccount`), which requires the victim to actively transfer each dust balance away.
- Consequence of a stuffed list: `DepositToken.deposit` of any collateral the victim does not already hold reverts in `_mint` → `addToDepositTokensOfAccount`; `Pool.liquidate` payouts via `DepositToken.seize` (same `_transfer` path) revert if the seized token is new to the account; `DebtToken` mints have the same cap. The victim cannot add new collateral to improve health while under water — a direct liveness break on the deposit path, matching the CVE's "hang / complete DoS of the component" class.

### Impact Explanation
Temporary denial of service of a core protocol function for the targeted account: all deposits into new collateral types, incoming transfers of new deposit tokens, and (for a victim with a stuffed list) liquidation seizure into fresh tokens revert unconditionally. A victim approaching liquidation can be prevented from topping up collateral with a new asset, making them liquidatable when they otherwise wouldn't be. The attacker cost is dust amounts of collateral (1 wei per token, ~30 tokens), while the victim must spend gas transferring each dust token out to a fresh address to recover — and if the victim's dust became locked (`_revertIfLocked` via `unlockedBalanceOf`), recovery can be further delayed.

### Likelihood Explanation
Fully permissionless: `DepositToken.transfer`/`transferFrom`/`deposit(onBehalfOf_)` are public entry points with no whitelist, no minimum amount, and no opt-in for list insertion. The attacker only needs tiny balances of each supported collateral. No governance, oracle manipulation, or privileged role required. Deployed pools with multiple collaterals (per `deployments/base/`) provide enough distinct `DepositToken`s to reach the cap.

### Recommendation
Make the per-account accounting opt-in or failure-tolerant:
- Bound the griefing: skip `addToDepositTokensOfAccount` for `transfer`s below a dust threshold, or track "manually added" tokens rather than every token ever received.
- Alternatively, remove the hard cap for *incoming* tokens and only enforce it on user-initiated deposits, or iterate health checks off a snapshot so a stuffed list cannot block `seize`/deposit.
- Add a `sweep`-style escape so a user can batch-clear unwanted dust entries in one transaction.

### Proof of Concept
Hardhat (repo already has Hardhat + smock setup, see `test/Pool.test.ts:1386-1416` exercising the revert):

```ts
it('griefs victim: fills MAX_TOKENS_PER_USER via dust transfers', async () => {
  const victim = bob.address;
  // attacker deposits 1 wei-equivalent of each supported collateral and transfers to victim
  for (const dt of depositTokens /* all pool DepositTokens */) {
    await dt.deposit(2, attacker.address);
    await dt.transfer(victim, 1); // adds dt to depositTokensOfAccount[victim]
  }
  // ...also issue debt tokens to reach 30 total entries if fewer collaterals exist
  expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30);

  // victim tries to deposit a new collateral -> reverts
  await expect(newDepositToken.connect(bob).deposit(amount, bob.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // incoming transfer of any new token also reverts
  await expect(newDepositToken.transfer(victim, 1))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```
