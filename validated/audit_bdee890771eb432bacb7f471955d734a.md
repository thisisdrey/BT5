### Title
Non-atomic replay-window check-and-update permits duplicate delivery of a replayed data packet - (File: connection_state.go)

### Summary
Nebula's per-tunnel anti-replay bookkeeping (`Bits`, used via `ConnectionState.window`) is checked and updated as two separate, independently-locked operations rather than one atomic "commit" step. `Decrypt` and `VerifyRelay` in `connection_state.go` call `window.Check` under `decryptLock`, release the lock, perform the AEAD decryption *without* holding the lock, and only then re-acquire the lock to call `window.Update`. This mirrors the reported bug class: an internal ledger (here, the replay bitmap) is consulted for eligibility but not atomically debited/credited together with the action it is meant to gate, so a party can obtain the benefit of the action (decrypted/delivered traffic) more than once for what the bookkeeping believes is a single, once-only unit.

### Finding Description
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`: [1](#0-0) [2](#0-1) 

The sequence is: `decryptLock.Lock(); window.Check(i); decryptLock.Unlock()` → AEAD `DecryptDanger`/`Open` (no lock held) → `decryptLock.Lock(); window.Update(i); decryptLock.Unlock()`.

With `routines > 1` (multi-queue UDP listeners), Nebula runs multiple reader goroutines that all call `readOutsidePackets` → `Decrypt`/`VerifyRelay` concurrently for packets belonging to the same tunnel/`ConnectionState`, since dispatch is per-socket-queue, not per-hostinfo: [3](#0-2) 

Because `Check` and `Update` are separated by the (unlocked, CPU-bound) decryption step, two threads that receive the *same* replayed ciphertext (attacker duplicates a captured on-wire UDP datagram and floods it in) can both:
1. call `Check(i)` while the bit for `i` is still unset — both return `true`,
2. both successfully decrypt the same valid ciphertext with the same counter `i` (decryption success does not depend on the window state),
3. proceed to hand the plaintext to the tun device / firewall / application path before either has called `Update`.

Only afterward does one of the two `Update(i)` calls actually win and mark the bit; the other returns `false` — but by that point the packet has already been delivered twice. The bitmap ("internal balance") is therefore not an accurate ledger of what has actually been processed at the time processing occurs, exactly analogous to the reported ERC20 issue where the internal balance was updated based on an assumption rather than atomically with the real, observable event.

The same relay-frame replay-window rationale is documented and tested for the *forwarding* relay path (`handleOutsideRelayPacket` / `VerifyRelay`), where the fix note explicitly states "Before the fix, handleOutsideRelayPacket authenticated the frame but never advanced the replay window, so every replay was re-forwarded": [4](#0-3) 

That test confirms that under multi-threaded processing, replay-window "authenticate first, book-keep later" designs in this codebase have historically enabled exactly the class of bug flagged in the external report; the current `Decrypt`/`VerifyRelay` split-lock structure retains the same non-atomic check→act→commit pattern for the terminal (non-relay) decryption path.

### Impact Explanation
An attacker with no CA-signed certificate — who only needs to capture and replay a single legitimate on-wire UDP datagram belonging to an established tunnel — can cause the receiving Nebula node to deliver the same application-layer packet to the tun device more than once under concurrent multi-routine processing. This is a traffic-integrity violation (duplicate delivery / partial replay bypass) of the exact security property the sliding-window anti-replay mechanism (`Bits`) is designed to enforce. Depending on the payload (e.g., a duplicated firewall-state-changing message, a duplicated financial/command packet on the overlay network, or a duplicated Nebula-internal control packet processed via `header.Control`/`header.LightHouse`), this can lead to state poisoning or duplicate processing of one-time operations on the receiving host.

### Likelihood Explanation
Exploitability requires: (a) `routines > 1` (multiple listener queues, a documented, common performance configuration mentioned in `main.go`), and (b) the ability to send two copies of a single captured legitimate ciphertext to the target UDP port at effectively the same time so they land on different queues/goroutines before either `Update` call commits. Both conditions are attacker-controllable without possessing a valid certificate — the attacker only needs raw UDP send access to the target and a captured packet. This is a race condition, so it is probabilistic rather than deterministic, which lowers likelihood somewhat, but it is trivially retriable (attacker can keep re-sending duplicate pairs for any captured packet) until it lands.

### Recommendation
Make the replay-window check-and-commit atomic with respect to the decrypt/authenticate step for a given counter, e.g.:
- Hold `decryptLock` across `Check` and the corresponding `Update` (not just each individually), or
- Reserve the slot optimistically before decrypting (mark as "in-flight") and only finalize/rollback after decrypt succeeds/fails, ensuring no second thread can pass `Check` for the same counter while the first is still processing, or
- Serialize replay-window operations for a given `ConnectionState` so that decryption of counter `i` and the corresponding window update happen as one critical section, closing the TOCTOU gap between "check eligibility" and "commit the receipt" — mirroring the report's suggested mitigation of updating internal bookkeeping strictly in lockstep with the real, verified event rather than trusting an intermediate assumption.

### Proof of Concept
1. Configure a Nebula node with `routines` > 1 (multiple UDP listener queues).
2. Establish a tunnel and capture one legitimate encrypted data-plane UDP packet (`header.Message`) destined for the node, noting its `MessageCounter`.
3. From an external, uncertificated attacker position, send two copies of the identical captured UDP datagram to the node's listening port in rapid succession (ideally via two sockets/threads to maximize the chance they are picked up by different reader routines nearly simultaneously).
4. Observe, on the receiving node, that `handleOutsideMessagePacket`/tun write occurs twice for the same counter before the replay window's `Update` call rejects the second occurrence — i.e., the payload is delivered to the tun device (or to `header.Control`/`header.LightHouse` handlers) more than once, contrary to the intended once-only semantics of the `Bits` anti-replay tracker in `connection_state.go`.

(Note: confirming the precise timing window under real scheduling would require running this against a live multi-routine build; the race is architecturally present given the lock-release-between-Check-and-Update pattern shown above, but its practical reliability under production I/O scheduling could not be empirically measured with the tools available here.)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	if err != nil {
		return nil, err
	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
