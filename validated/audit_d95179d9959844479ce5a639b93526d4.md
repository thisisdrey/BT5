### Title
Hard-coded static-gas budgets in the Wallet Contract's rlp_execute callback chain can starve refund logic as host-function gas costs change - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract (NEP-518, used to give ETH-implicit accounts a NEAR-native execution path) attaches fixed, hard-coded `Gas` constants to every promise/callback it schedules instead of forwarding "all remaining gas" or a value derived from current cost parameters. This is the direct structural analog of the reported Solidity bug: `.transfer()`/`.send()` hard-coding 2300 gas regardless of how EVM opcode costs evolve. Here, `RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, `REGISTRAR_LOOKUP_GAS`, and the composite `ADDRESS_CHECK_CALLBACK_GAS` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` are all fixed at `Gas::from_tgas(5)` (or small sums thereof): [1](#0-0) 

### Finding Description
`rlp_execute_callback` is the terminal callback that determines whether the user's action succeeded, and — critically — it is the only place that issues a refund of the caller's attached deposit (`caller_deposit`) when the underlying cross-contract action fails: [2](#0-1) 

This callback (and the intermediate `address_check_callback` / `nep_141_storage_balance_callback` callbacks that also perform refund-relevant branching) is always scheduled with a fixed, hard-coded static gas amount taken from module-level constants: [3](#0-2) 

These constants are not derived from `RuntimeConfig`/`RuntimeFeesConfig` (which nearcore does version and adjust over protocol upgrades — e.g. `AccountCostIncrease`, NEP-536, per-byte cost changes documented in `core/parameters/res/runtime_configs/*.yaml`), nor do they forward all remaining prepaid gas. They are baked into the compiled contract binary at `Gas::from_tgas(5)`. If future protocol versions raise the gas cost of the host functions exercised inside these callbacks (JSON/Borsh deserialization of `PromiseResult`, `env::promise_batch_create`, `env::promise_batch_action_transfer`, or SDK-generated dispatch overhead — directly analogous to Solidity's SLOAD going from 200 to 800 gas), the callback could exceed its statically attached gas budget and abort with a `FunctionCallError::ExecutionError` (gas exhaustion) before the refund transfer promise action is ever scheduled.

Because the wallet contract is deployed as the code for ETH-implicit accounts (a single shared/global contract used across many accounts, per `EthImplicitGlobalContract`, PV 83), and these accounts explicitly cannot receive a full-access key or be otherwise administered (`docs/DataStructures/Account.md:121`), there is no way for an affected account owner to bypass or patch the hard-coded gas constants after the fact if a future cost increase renders them insufficient — unlike a typical Solidity contract where at least the deploying protocol/team can redeploy a fixed version for new users.

### Impact Explanation
If a future gas-cost increase pushes execution of `rlp_execute_callback` (or `address_check_callback` / `nep_141_storage_balance_callback`) past the hard-coded 5/10/15 Tgas budget:
- The callback function call fails with an out-of-gas error before the `if let Some(CallerDeposit ...)` refund branch executes.
- The deposit that the caller (relayer or user) attached to `rlp_execute` — held as balance on the wallet contract's account — is never refunded via `env::promise_batch_action_transfer`.
- Because the wallet account has no full-access key and cannot be administered outside of further `rlp_execute` calls signed by the ETH private key, that stranded balance is not straightforwardly recoverable by the party who was supposed to receive the refund (typically a third-party relayer), constituting a loss/freezing of funds for that party.

This matches the accepted impact category of "permanent freezing of funds" for an unprivileged actor (a relayer/user submitting an ordinary `rlp_execute` transaction), reachable purely through normal contract execution — no malicious node, validator, or protocol-admin action required.

### Likelihood Explanation
Likelihood is inherently tied to future gas-cost/parameter changes, exactly as the original ENS finding was judged Medium because "there are external factors required to make this problem occur." nearcore's gas-cost model is not static — the codebase already shows multiple historical/ongoing cost changes (`AccountCostIncrease` at PV 85, per-byte cost recalibration in `85.yaml`/testnet configs, planned `gas_refund_penalty` activation). Any future increase to the cost of promise/cross-contract-call host functions, larger SDK-generated dispatch overhead, or added validation logic in these specific callback methods could push actual usage above the fixed 5 Tgas constant. Since the wallet contract is compiled once and (for `CodeHash`-referenced global contracts) immutable, this is a latent, not currently triggered, condition — likelihood today is low, but the design pattern (no headroom, no dynamic scaling with `GasWeight`/`prepaid_gas`) is fragile by construction, exactly mirroring the reported bug class.

### Recommendation
- Use `Promise::function_call_weight` with a `GasWeight` (as already used for `ban_relayer`, see `create_ban_relayer_promise`) to forward a proportion of remaining prepaid gas to refund-critical callbacks instead of a small fixed absolute amount. [4](#0-3) 
- At minimum, add meaningful safety margin to the static gas constants and periodically re-validate them against the parameter estimator (`runtime/runtime-params-estimator`) whenever `RuntimeFeesConfig`/host-function costs change, treating the wallet contract like a first-class protocol component subject to the same gas-estimation discipline as native actions.
- Ensure the refund-issuing branch of `rlp_execute_callback` is prioritized/cheap and gas-metered defensively (e.g., early-exit before any unnecessary deserialization) so it remains executable even under constrained gas.

### Proof of Concept
Conceptual PoC (cannot be executed without a future protocol change that raises the relevant host-function gas costs):
1. Deploy/observe an existing ETH-implicit account running the Wallet Contract global contract.
2. A relayer calls `rlp_execute(target, tx_bytes_b64)` with an attached deposit for a `Transfer` or `ERC20Transfer` action, entering the `nep_141_storage_balance_callback` → `rlp_execute_callback` chain, each scheduled with the hard-coded `RLP_EXECUTE_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` constants: [5](#0-4) 
3. Assume a future protocol version raises the gas price of `PromiseResult` deserialization or `promise_batch_action_transfer` (analogous to Solidity's SLOAD 200→800 gas EIP change) such that `rlp_execute_callback`'s work now exceeds 5 Tgas.
4. The action underlying the user's transaction fails (e.g., the target function call panics), triggering the `PromiseResult::Failed` branch that is supposed to refund `caller_deposit`: [6](#0-5) 
5. Because the callback itself now exceeds its statically attached gas, the callback function aborts with an out-of-gas error *before* `env::promise_batch_create`/`env::promise_batch_action_transfer` execute, so no refund receipt is ever created — the caller's deposit remains stuck on the wallet account's balance with no privileged path to recover it.

**Confidence caveat:** I could not fully trace the `CallerDeposit`/`ExecutionContext::new` construction logic (only found via `grep_search`, not read in full) to confirm the exact yoctoNEAR amount at risk in every code path, and I did not find a live protocol-version-gated cost increase in this codebase that already triggers the condition today — the vulnerability is a latent design fragility rather than a currently-exploitable bug. If you need the full contents of `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs` for exact refund-amount accounting, note that index size limits may exclude some of that file; a full Devin session could inspect the complete file if deeper verification is required.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
