### Title
Concurrency limiter uses only repository `RelativePath` (ignoring `StorageName`) as its accounting key, causing per-repository limits to be shared/miscounted across distinct repositories — ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
The C4 report's root cause is an accounting mismatch: the denominator used by the rate-distribution function (`totalStaked`) does not correspond to the actual population being measured by the numerator (`stakedOf`, which spans multiple pools), so the limiter's key space does not match the real resource being rationed, over/under-crediting rewards. The analogous defect class — "the bucket key used for resource accounting does not match the actual resource being isolated" — is reachable in Gitaly's concurrency-limiting middleware, which is the RPC-handler resource-limit gate explicitly in scope.

### Finding Description
Gitaly's per-repository concurrency limiter buckets in-flight/queued RPCs by a `GetLockKey` string computed once per request: [1](#0-0) 

`LimitConcurrencyByRepo` derives the limiting key **solely from `info.Repository.GetRelativePath()`**, omitting `StorageName` entirely. The `RequestInfo.Repository` field is populated from the RPC's target repository field via reflection over the proto registry: [2](#0-1) 

That key is then used as the sole identity for a `keyedConcurrencyLimiter` (semaphore) instance, lazily created and cached in `limitsByKey[limitingKey]`: [3](#0-2) 

Because the storage name is dropped from the key, two **distinct** repositories that happen to share the same `RelativePath` on different storages (a routine, unprivileged configuration — e.g. replicated/mirrored storages, or any Gitaly node configured with multiple `[[storage]]` entries) collapse onto the same semaphore bucket. This is structurally identical to the report's bug: the quantity used to gate/ration a shared resource (`totalStaked`/limiter key) does not enumerate the same population as the quantity that consumes it (`stakedOf`/actual per-repo RPC traffic), so the accounting is wrong in both directions:
- Unrelated repositories on different storages sharing a relative path are forced to share one concurrency budget, meaning ordinary traffic against repository A on storage-1 can starve or throttle repository B on storage-2 even though `max_per_repo` was configured to isolate concurrency **per repository**.
- Conversely, when `info.Repository` is `nil` or has an empty relative path (any RPC where `RequestInfo.Repository` extraction fails, e.g. `mi.TargetRepo` returning an error), `LimitConcurrencyByRepo` returns `""`, and *all* such requests from *all* callers collapse into a single global bucket, which is a resource-limit bypass in the opposite direction — the limiter no longer isolates per-repository load at all for that class of request.

### Impact Explanation
This breaks the isolation guarantee documented for Gitaly's backpressure mechanism ("Limit the number of concurrent RPCs ... for each repository"): [4](#0-3) 

An ordinary, unprivileged client issuing routine RPCs (clone/fetch/push) against one repository can consume or starve the shared concurrency/queue tokens intended for a completely unrelated repository that happens to collide on `RelativePath` across storages, or (for the empty-key case) can exhaust the queue budget meant to protect the whole fleet of repositories that fall back to the empty key. This is a Denial-of-Service class issue on the RPC-handler resource-limit gate, directly matching the "RPC-handler resource limits" analog category and requiring no elevated privilege — it is triggerable by any authenticated Gitaly client performing normal Git operations.

### Likelihood Explanation
Moderate-to-high: multi-storage Gitaly deployments (a standard, documented configuration, not a privileged/attacker-controlled setup) routinely have repositories with identical relative paths across different storage roots (e.g., replicated project layouts). Any RPC whose method-registry lookup does not yield a target repository (`mi.TargetRepo` error path) also silently degrades to the shared empty-key bucket, which can occur without any malicious input — just ordinary RPC traffic hitting the fallback path.

### Recommendation
Update `LimitConcurrencyByRepo` in `internal/grpc/middleware/limithandler/middleware.go` to compose the limiting key from **both** `StorageName` and `RelativePath` (e.g., `repo.GetStorageName() + "/" + repo.GetRelativePath()`, mirroring the pattern already used elsewhere in the codebase such as `cgroups.WithCgroupKey(repo.GetStorageName() + "/" + relativePath)` in `internal/git/gitcmd/command_factory.go` and `NewRepositoryKey` in `internal/backup/pipeline.go`), and audit/guard the empty-key fallback path so RPCs lacking a resolvable target repository do not silently share one global, unbounded bucket.

### Proof of Concept
1. Configure a Gitaly node with two storages, `storage-a` and `storage-b`, each containing a repository at the same relative path `@hashed/xx/yy/project.git`.
2. Configure `[[concurrency]] rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel" max_per_repo = 1`.
3. Issue a long-running clone against `storage-a`'s repository (occupies the sole concurrency token for key `@hashed/xx/yy/project.git`, per `LimitConcurrencyByRepo` at `internal/grpc/middleware/limithandler/middleware.go:19-25`).
4. Concurrently issue a clone against the unrelated repository on `storage-b` with the identical relative path — it is queued/blocked behind step 3's request instead of being processed independently, because both map to the same `limitsByKey` entry in `internal/limiter/concurrency_limiter.go:245-270`, violating the intended per-repository isolation.

// GetLockKey function defines the lock key of an RPC invocation based on its context
type GetLockKey func(context.Context) string

// LimitConcurrencyByRepo implements GetLockKey by using the repository path as lock.
func LimitConcurrencyByRepo(ctx context.Context) string {
	if info := requestinfohandler.Extract(ctx); info != nil {
		return info.Repository.GetRelativePath()
	}

	return ""
}

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}
