Audit Report

## Title
Missing duplicate-registration guard in Snowbridge `register_token` allows repeated `RegisterForeignToken` bridge commands for an already-registered asset - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`, `bridges/snowbridge/pallets/system/src/lib.rs`)

## Summary
`do_register_token` in `bridges/snowbridge/pallets/system/src/lib.rs` and `register_token` in `bridges/snowbridge/pallets/system-v2/src/lib.rs` both only use `ForeignToNativeId::<T>::contains_key(token_id)` to conditionally skip the storage *insert*, but unconditionally build and send a fresh `Command::RegisterForeignToken` and emit `RegisterToken` regardless of whether the asset is already registered. Any asset owner reachable via the unprivileged `snowbridge-pallet-system-frontend::register_token` extrinsic (gated only by `ForeignAssetOwner`, which checks asset ownership, not registration status) can repeatedly trigger this path with attacker-chosen `name`/`symbol`/`decimals` metadata.

## Finding Description
The confirmed code at [1](#0-0)  shows `do_register_token` computing `token_id` and only guarding the `ForeignToNativeId` storage insert with `if !ForeignToNativeId::<T>::contains_key(token_id)`, then unconditionally proceeding to build `Command::RegisterForeignToken` and call `Self::send(...)`, followed by an unconditional `Event::RegisterToken` deposit. The identical pattern exists in the v2/user-facing path at [2](#0-1) .

This v2 `register_token` is reachable by an ordinary, unprivileged user through `snowbridge-pallet-system-frontend`'s `register_token` extrinsic, as shown at [3](#0-2) , which is gated only by `T::RegisterTokenOrigin::ensure_origin`. The `ForeignAssetOwner` origin implementation confirms this check only verifies the caller is the current asset owner — it never checks registration status — as seen in the `ForeignAssetOwner::try_origin` logic. A repo-wide search for an "already registered" error in these pallets (`TokenAlreadyRegistered`/`AlreadyRegistered`) returns no hits in the Snowbridge system pallets, confirming no such guard exists anywhere in this call chain.

The `contains_key` check is thus purely cosmetic with respect to the outbound bridge message: the on-chain "already registered" marker (`ForeignToNativeId`) and the outbound `Command::RegisterForeignToken` stream diverge, allowing repeated, differently-parameterized registration commands for the same `token_id` to be dispatched to the Ethereum Gateway.

## Impact Explanation
This violates the intended one-time-registration invariant for `RegisterForeignToken`, matching the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot. The storage-level dedup check gives a false sense of protection while the actual state-changing bridge effect (the outbound `Command::RegisterForeignToken` and `RegisterToken` event) is repeated with attacker-controlled `name`/`symbol`/`decimals` metadata that can differ from the original registration, undermining any assumption on the Ethereum side that registration is a one-time, idempotent event for a given `token_id`.

## Likelihood Explanation
High reachability: any account that is the current owner of an already-registered foreign asset (satisfying `ForeignAssetOwner`/`RegisterTokenOrigin`) can call the public `register_token` extrinsic on `snowbridge-pallet-system-frontend` repeatedly, paying only the normal fee-asset swap-and-burn cost each time — no root, governance, or relayer/prover compromise is required. This is directly exploitable via public extrinsic submission by an unprivileged, legitimate asset owner.

## Recommendation
Add an explicit guard that turns "already registered" into a hard error (or a true no-op that also skips sending the command) in both `do_register_token` (`bridges/snowbridge/pallets/system/src/lib.rs`) and `register_token` (`bridges/snowbridge/pallets/system-v2/src/lib.rs`):
```rust
ensure!(!ForeignToNativeId::<T>::contains_key(token_id), Error::<T>::TokenAlreadyRegistered);
ForeignToNativeId::<T>::insert(token_id, location.clone());
```
so the `Command::RegisterForeignToken` dispatch and `RegisterToken` event are only produced on first registration.

## Proof of Concept
1. Asset owner `A` calls `snowbridge-pallet-system-frontend::register_token(asset_id = X, metadata = M1, fee_asset = F)`. This forwards to `system-v2::register_token`, setting `ForeignToNativeId[token_id(X)]` and sending `Command::RegisterForeignToken{token_id, name: M1.name, ...}` to Ethereum, burning fee `F`.
2. `A` (still owner of `X`) calls `register_token(asset_id = X, metadata = M2, fee_asset = F)` again. The `contains_key` check is true so the storage insert is skipped, but `Command::RegisterForeignToken{token_id, name: M2.name, ...}` is built and sent again via `Self::send`, and `Event::RegisterToken` is emitted again — no error is raised at [4](#0-3) .
3. Repeating step 2 produces an unbounded number of `RegisterForeignToken` commands for a single already-registered `token_id`, each with independently attacker-chosen metadata, which can be verified via a unit test asserting that `Command::RegisterForeignToken` is sent (and `RegisterToken` event emitted) on a second call to `register_token` for a location already present in `ForeignToNativeId`.

		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}

		pub fn register_token(
			origin: OriginFor<T>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			fee_asset: Asset,
		) -> DispatchResult {
			ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);

			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let origin_location = T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)?;

			let ether_gained = if origin_location.is_here() {
				// Root origin/location does not pay any fees/tip.
				0
			} else {
				Self::swap_fee_asset_and_burn(origin_location.clone(), fee_asset)?
			};

			let call = Self::build_register_token_call(
				origin_location.clone(),
				asset_location,
				metadata,
				ether_gained,
			)?;

			Self::send_transact_call(origin_location, call)
		}
