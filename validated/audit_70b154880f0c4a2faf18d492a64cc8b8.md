### Title
`StackerDBSession::get_chunks` reads raw HTTP body with no size cap, bypassing the `STACKERDB_MAX_CHUNK_SIZE` bound enforced by `StackerDBChunkData::consensus_deserialize` - ([File: libsigner/src/session.rs])

### Summary
`StackerDBChunkData::consensus_deserialize` correctly bounds the chunk `data` field via `read_next_at_most(fd, STACKERDB_MAX_CHUNK_SIZE)` [1](#0-0) , but `StackerDBSession::get_chunks` never runs the fetched bytes through this codec path at all — it hands back the raw HTTP body from `rpc_request` unchecked, and the underlying `run_http_request` reads the entire response with `sock.read_to_end(&mut buf)` with no length cap whatsoever, not even a Content-Length-based one. This is confirmed by contrast with the sibling method `get_latest_chunks`, which explicitly re-checks `body_bytes.len() > limit` after the read — a check `get_chunks` omits entirely.

### Finding Description
`get_chunks` (libsigner/src/session.rs:201-227) issues a GET for each `(slot_id, slot_version)` and returns `Some(body_bytes)` straight from `self.rpc_request(...)` with no post-read size validation [2](#0-1) . Compare this to `get_latest_chunks` (lines 230-262), which computes a `limit` from `STACKERDB_MAX_CHUNK_SIZE`/`SIGNERS_STACKERDB_CHUNK_SIZE` and rejects (returns `None`) any body exceeding it [3](#0-2) . `get_chunks` has no equivalent guard.

Tracing further into `rpc_request` → `run_http_request` (libsigner/src/http.rs:221-262), the response is read with an unbounded `sock.read_to_end(&mut buf)` [4](#0-3) , and the body is then extracted via `decode_http_body`, which for non-chunked responses simply does `buf.to_vec()` with no length check against any declared Content-Length or hard cap [5](#0-4) . So the codec-level bound (`STACKERDB_MAX_CHUNK_SIZE` via `read_next_at_most`) that protects `StackerDBChunkData::consensus_deserialize` is never invoked on this path at all — `get_chunks` bypasses it completely, and the HTTP layer itself has no size limit (it isn't even a Content-Length trust issue; there's no cap at all, bounded only by TCP stream length until EOF/close).

### Impact Explanation
A stacks-node (or any host masquerading as the StackerDB replica endpoint that a signer's `StackerDBSession` is configured/connects to) can respond to a chunk-fetch GET request with an arbitrarily large HTTP body. Because `get_chunks` performs no size check and `run_http_request` imposes no cap, the signer process will buffer the entire attacker-controlled response into memory (`Vec<u8>`), independent of `STACKERDB_MAX_CHUNK_SIZE`. This is a memory-exhaustion / unauthenticated DoS vector against the signer process, triggerable by a single oversized response, and repeatable on every chunk fetch. This matches the Critical category "remote crash/unauthenticated DoS from few messages."

### Likelihood Explanation
The signer must be querying a StackerDB replica endpoint (host:port) that is malicious or compromised/byzantine — i.e., the "remote sender" here is the queried replica node, and the signer's outbound `StackerDBSession` connection is the reachable channel. No secret, signature, or privileged role is required to serve an oversized response: the attacker simply needs to be (or spoof/MITM) the endpoint the signer's session connects to and return a large HTTP body for a GET on the chunk path. Repeatable per request; low attacker cost.

### Recommendation
Add the same size check used in `get_latest_chunks` to `get_chunks`, and additionally enforce a hard cap inside `run_http_request`/`decode_http_body` (e.g., reading incrementally and aborting/erroring once bytes read exceed `STACKERDB_MAX_CHUNK_SIZE` or `MAX_MESSAGE_LEN`, and validating against the response's own Content-Length header) rather than relying on `read_to_end` with no bound.
