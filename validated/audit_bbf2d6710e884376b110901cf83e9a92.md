### Title
Excess `attached_deposit` sent to `rlp_execute` is never refunded on success and is permanently absorbed by the eth‑implicit wallet contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit `WalletContract::rlp_execute` entry point is `#[payable]` and accepts an arbitrary `attached_deposit` from an external, unprivileged caller (typically a relayer). The actual NEAR value forwarded to the underlying action is computed independently from the *signed Ethereum transaction's* `value`/`yocto_near` fields, not from `attached_deposit`. If the caller attaches more NEAR than the decoded action actually needs, the excess is only ever refunded when the downstream promise **fails**; on **success** there is no logic to return any unused portion of the deposit. The surplus is silently absorbed into the wallet-contract account's own balance, permanently transferring the caller's funds to the wallet owner with no recourse — the same "leftover funds get stuck/diverted because refund logic is all-or-nothing on success vs failure" bug class described in the external report.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the full `attached_deposit` of the call: [1](#0-0) 

But the actual deposit given to the downstream Near action is derived purely from the signed Ethereum transaction's `value` field (plus any inline `yocto_near`), completely independent of `attached_deposit`: [2](#0-1) [3](#0-2) 

`CallerDeposit` only tracks the *entire* attached deposit for the purpose of an all-or-nothing refund: [4](#0-3) 

The refund is only issued in `rlp_execute_callback` when the promise **fails**; on success, no refund of any unused portion is ever generated: [5](#0-4) 

Because `rlp_execute` credits `attached_deposit` to the wallet contract's own account balance the moment the receipt executes (standard NEAR semantics for payable calls), and the promise deposit is drawn from that balance based only on the RLP-decoded `tx.value`/`yocto_near`, any amount the caller attached beyond what the decoded transaction specifies is never returned to the caller once the action succeeds — it simply becomes part of the wallet owner's balance. The dedicated fee-refund path exists only for the specific `EOABaseTokenTransfer`/`ERC20Transfer` "fee" case, not for the general case of an over-funded call: [6](#0-5) 

The associated test suite documents this as intended behavior rather than treating it as a partial-refund bug: [7](#0-6) 

### Impact Explanation
Any unprivileged relayer/caller of `rlp_execute` who attaches a deposit larger than the amount actually consumed by the decoded Ethereum-style action (`tx.value` + inline `yocto_near`) permanently loses the difference to the wallet-contract account on a successful call. There is no mechanism to reclaim the surplus deposit; only a fully failed promise triggers any refund, and even then it refunds the whole deposit rather than the unused remainder. This is a genuine, unrecoverable loss of NEAR tokens for an ordinary transaction signer, matching the report's "leftover funds get stuck because refund logic only fires in one branch" bug class.

### Likelihood Explanation
This requires only an ordinary, unprivileged caller invoking a production entry point (`rlp_execute`) with a deposit that does not exactly match the value encoded in the signed transaction they are relaying — an easy and plausible mistake (e.g., relayer estimation error, race condition between quoting and executing, or a relayer intentionally over-funding to be safe against `MAX_YOCTO_NEAR` precision loss). No special privileges, malicious nodes, or protocol-level conditions are needed.

### Recommendation
Track the actually-required action deposit (`tx.value` + `yocto_near`) separately from `attached_deposit`, and refund the *difference* (`attached_deposit - required_amount`) back to `predecessor_account_id` unconditionally, regardless of whether the downstream promise succeeds or fails, rather than only refunding the full amount on failure.

### Proof of Concept
1. A relayer calls `rlp_execute` attaching `attached_deposit = 5 NEAR`, relaying a validly signed Ethereum transaction whose `value` field (once converted) plus `yocto_near` in the payload total only `0.001 NEAR`.
2. `inner_rlp_execute` computes `caller_deposit = CallerDeposit { account_id: relayer, yocto_near: 5 NEAR }` per `types.rs:180-191`, but constructs the actual downstream action's `deposit` from `tx.value`/`yocto_near` only (`internal.rs:162-163`), i.e. `0.001 NEAR`.
3. The downstream promise (e.g., a `Transfer` or `FunctionCall`) succeeds.
4. `rlp_execute_callback` hits the `PromiseResult::Successful` branch (`lib.rs:313-315`), which contains no logic referencing `caller_deposit` at all — no refund is issued.
5. The wallet-contract account's balance now permanently retains the `4.999 NEAR` surplus that was attached by the relayer, with no way for the relayer to recover it.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
