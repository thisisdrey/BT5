## Title
`checkUnfreezeBalance()` / `checkExistFrozenBalance()` only inspect the first matching `FreezeV2` entry instead of summing all entries of the same resource type - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java], [File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java])

### Summary
`UnfreezeBalanceV2Actuator.checkUnfreezeBalance()` and its TVM twin `UnfreezeBalanceV2Processor.checkUnfreezeBalance()` iterate over `accountCapsule.getFrozenV2List()` and `break` as soon as they find the first `FreezeV2` entry matching the requested `freezeType`, using only that single entry's `getAmount()` as `frozenAmount`. Everywhere else in the codebase (e.g. `getFrozenV2BalanceForBandwidth`, `getFrozenV2BalanceForEnergy`, `getTronPowerFrozenV2Balance`) the correct pattern is used: `stream().filter(type).mapToLong(FreezeV2::getAmount).sum()`. This is exactly the "take first value instead of summing all matching entries" bug class described in the external report.

### Finding Description [1](#0-0) 

and the actuator equivalent: [2](#0-1) 

Both methods loop through `freezeV2List`/`frozenV2List` and, on the first `FreezeV2` element whose `getType()` matches the requested `freezeType`, immediately capture `frozenAmount = freezeV2.getAmount()` and `break`. If an account's `FreezeV2` list ever contains more than one entry of the same resource type, only the amount of the first one is considered when validating whether an unfreeze request is permissible, rather than the sum of all entries of that type — contrasted with the correct summed accessors elsewhere in `AccountCapsule` (`getFrozenV2BalanceForBandwidth`, `getFrozenV2BalanceForEnergy`, `getTronPowerFrozenV2Balance`), which use `.stream().filter(...).mapToLong(FreezeV2::getAmount).sum()`.

I was not able to conclusively verify, within the available indexed code, whether `AccountCapsule`'s freeze-add path (`addFrozenBalanceForResource`, `addFrozenV2List`) can produce multiple separate `FreezeV2` entries of the same type in the list (versus always merging into a single per-type entry). The correct summed getters (`getFrozenV2BalanceForBandwidth`/`getFrozenV2BalanceForEnergy`) defensively sum over the list, which suggests the list is expected/allowed to contain multiple entries per type — otherwise these sums would be unnecessary. Confirming whether multiple same-type entries can actually be produced (and reproducing a case where `checkUnfreezeBalance`/`checkExistFrozenBalance` see a stale/incomplete `frozenAmount` due to only inspecting the first match) requires deeper tracing through `addFrozenBalanceForResource` that I could not complete given the remaining budget.

### Impact Explanation
If the `FreezeV2` list can contain multiple entries of the same resource type (e.g. due to freeze/unfreeze/delegate sequences building up separate entries rather than merging), `checkUnfreezeBalance()` would validate an unfreeze request against only the first entry's amount rather than the account's true total frozen balance for that resource. This could allow an account to either (a) be incorrectly blocked from unfreezing balance it legitimately has (denial of service on the user's own funds), or (b) in the inverse direction, be granted permission to unfreeze more than the first entry alone would allow, if further code paths use this check as an authorization gate rather than a strict bound (impact direction is uncertain without confirming exact invariants of the list construction).

### Likelihood Explanation
Low — this requires the underlying `FreezeV2` list to actually contain multiple entries of the same resource type for the same account, which I could not confirm/deny with certainty from the indexed code. If the freeze-add logic always coalesces same-type frozen balances into a single list entry, this code path is dead/harmless despite the flawed pattern.

### Recommendation
Change `checkUnfreezeBalance()` in both `UnfreezeBalanceV2Actuator.java` and `UnfreezeBalanceV2Processor.java` to sum all matching entries instead of breaking on the first match, mirroring the pattern already used in `AccountCapsule.getFrozenV2BalanceForBandwidth()` / `getFrozenV2BalanceForEnergy()`:
```java
long frozenAmount = freezeV2List.stream()
    .filter(f -> f.getType().equals(freezeType))
    .mapToLong(Protocol.Account.FreezeV2::getAmount)
    .sum();
```

  private boolean checkUnfreezeBalance(
      AccountCapsule accountCapsule, long unfreezeBalance, Common.ResourceCode freezeType)  {
    if (unfreezeBalance <= 0) {
      return false;
    }
    long frozenBalance = 0L;
    List<Protocol.Account.FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (Protocol.Account.FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenBalance = freezeV2.getAmount();
        break;
      }
    }

    return unfreezeBalance <= frozenBalance;
  }

  public boolean checkUnfreezeBalance(AccountCapsule accountCapsule,
                                      final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                      ResourceCode freezeType) {
    boolean checkOk = false;

    long frozenAmount = 0L;
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenAmount = freezeV2.getAmount();
        break;
      }
    }

    if (unfreezeBalanceV2Contract.getUnfreezeBalance() > 0
        && unfreezeBalanceV2Contract.getUnfreezeBalance() <= frozenAmount) {
      checkOk = true;
    }

    return checkOk;
  }
