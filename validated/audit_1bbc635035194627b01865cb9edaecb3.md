### Title
Missing ownership check on `RelayFromAddr` in relay request handling allows arbitrary relay-state poisoning - (File: `relay_manager.go`)

### Summary
`handleCreateRelayRequest` trusts the `RelayFromAddr` field of an incoming `CreateRelayRequest` control message at face value and never verifies that the sending, authenticated peer (`h`, whose `vpnAddrs` were fixed during its own handshake) actually owns that address. This is the same root-cause class as the reported Magnetar bug: a privileged operation is keyed off an attacker-supplied identifier instead of the identifier that was actually authenticated for the caller, so the wrong entity's ownership is assumed.

### Finding Description
When a node receives a `NebulaControl_CreateRelayRequest` and determines it is itself the relay target, it extracts the claimed originator address directly from the wire message: [1](#0-0) 

```go
func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)
	...
	if f.myVpnAddrsTable.Contains(from) { ... }
	if f.myVpnAddrsTable.Contains(target) {
``` [2](#0-1) 

`h` is the `HostInfo` of the authenticated peer that sent the control message — its identity (`h.vpnAddrs`) was fixed by the certificate presented during its own Noise handshake (see `validatePeerCert`/`continueHandshake`, `handshake_manager.go:992-1039` and `handshake_manager.go:870-921`). However, `from` (`RelayFromAddr`) is an arbitrary field inside the message payload that `h` fully controls and that is never cross-checked against `h.vpnAddrs`. The code proceeds to call:

```go
_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
``` [3](#0-2) 

This registers relay state on the local `HostInfo` object, keyed by `from`, in the `Established` state — with no verification that `h` is actually entitled to relay on behalf of that address. Any authenticated peer can therefore claim an arbitrary victim VPN address as `RelayFromAddr` and cause the local relay bookkeeping (`relayForByAddr`/`relayForByIdx`, and via `AddRelay`, `hm.Relays`) to associate that peer as an `Established` terminal relay for the claimed address, exactly analogous to the Magnetar report's core defect: a function checks/relies on an identity/ownership field that does not correspond to the actually-verified caller.

### Impact Explanation
Once state is created for an arbitrary claimed address, it silently poisons the local relay bookkeeping for that VPN address:
- A subsequent legitimate `CreateRelayRequest` for the real address owner can hit `existingRelay.State == Established` and be rejected/mismatched (`existingRelay.RemoteIndex != m.InitiatorRelayIndex` branch, `relay_manager.go:457-464`), causing denial of relay service for the real host.
- The hostmap's `Relays` index (`hm.Relays[index] = relayHostInfo`) and `relayForByAddr` map are populated based on unverified attacker input, corrupting routing metadata used by `QueryVpnAddrsRelayFor` for subsequent forwarding decisions.

This falls under remote state poisoning of the hostmap/relay trust structures reachable by any peer that has completed its own (unrelated) handshake — it does not require holding a certificate for the address being claimed.

### Likelihood Explanation
Any node that can complete a normal handshake with the relay-capable target (a low bar — no special privilege beyond a valid CA-signed cert for its own identity) can send a `CreateRelayRequest` with a forged `RelayFromAddr`. The relay manager performs no additional authorization check tying `RelayFromAddr` to the sender's `HostInfo.vpnAddrs`, so exploitation is straightforward and requires no race condition or timing dependency.

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`), verify that the `RelayFromAddr`/`from` value asserted in the message is actually contained in `h.vpnAddrs` (the addresses that were cryptographically bound to `h` during its own handshake) before creating or updating any relay state on behalf of that address. Reject the message otherwise, mirroring how `handshake_manager.go`'s `validatePeerCert` binds vpn addresses strictly to the verified certificate.

### Proof of Concept
1. Node `Evil` completes a normal handshake with relay-capable node `Me`, obtaining a `HostInfo` `h` with `h.vpnAddrs = [EvilAddr]`.
2. `Evil` sends `Me` a `Control`/`NebulaControl_CreateRelayRequest` message with `RelayFromAddr = VictimAddr` (an address `Evil` does not own) and `RelayToAddr = MeAddr`.
3. `Me`'s `handleCreateRelayRequest` sees `target == MeAddr`, finds no existing relay for `VictimAddr` on `h`, and calls `AddRelay(rm.l, h, f.hostMap, VictimAddr, &m.InitiatorRelayIndex, TerminalType, Established)` — creating an `Established` relay entry for `VictimAddr` pointed at `Evil`'s `HostInfo`, without ever validating that `Evil` is authorized to speak for `VictimAddr`.
4. `Me` responds with a `CreateRelayResponse`, completing the bogus relay association; any later legitimate `CreateRelayRequest` from the real `Victim` for the same relay path can then collide with this attacker-seeded state (`relay_manager.go:457-471`).
