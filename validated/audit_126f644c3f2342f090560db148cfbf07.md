### Title
Floating-point precision loss in legacy Bancor-style TRC10 Exchange math causes incorrect (exploitable) settlement amounts - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The default (non-hardened) TRC10 `Exchange` bonding-curve arithmetic in `ExchangeProcessor` computes trade/inject/withdraw outputs using IEEE-754 `double` exponentiation (`Math.pow`/`StrictMath.pow`) with a fractional exponent (`0.0005`) and its inverse (`2000`), then truncates the *whole compounded result* to a `long` only once. Because `double` carries only ~15–17 significant decimal digits, and the `2000`-power step amplifies relative error roughly 2000×, the resulting integer amount can diverge measurably from the mathematically correct bonding-curve output — the exact bug class described in the Fei `Roots.cubeRoot`/`twoThirdsRoot` report, where premature/insufficient-precision arithmetic in a fractional-power formula biases the settled amount away from the true value. This path is reachable by any account issuing `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transactions whenever the chain-wide `allowHardenExchangeCalculation` flag has not been enabled (the historical/default behavior), enabling traders to shift value into or out of the exchange pool beyond what the formula intends.

### Finding Description
`ExchangeCapsule.transaction()` dispatches to either the legacy `ExchangeProcessor` (float-based) or the newer `SafeExchangeProcessor` (BigDecimal-based) depending on the `hardenedCalc` flag: [1](#0-0) 

The legacy path performs the Bancor formula entirely in `double` precision: [2](#0-1) 

Compare this to the hardened replacement, which was introduced specifically to fix the precision problem by using `BigDecimal` with an explicit 18-digit scale and controlled rounding mode, truncating only at the very end: [3](#0-2) 

The existence of `allowHardenExchangeCalculation` as an opt-in dynamic property confirms the legacy `ExchangeProcessor` path is known to be imprecise and is still the default/fallback: [4](#0-3) 

This legacy processor is directly reachable from unprivileged, signed transactions via `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and immediately credits the computed `anotherTokenQuant` to the trader's account: [5](#0-4) 

The same imprecise processor also underlies `ExchangeInjectActuator` and `ExchangeWithdrawActuator` balance/ratio computations reachable by any asset issuer/order placer.

The root cause mirrors the external report precisely: a fractional-power (root-like) formula is evaluated with insufficient precision/incorrect intermediate handling and only truncated to an integer at the end of a long chain of floating-point operations whose per-step relative error is amplified by a large exponent (2000), rather than being computed with fixed high-precision decimal arithmetic and rounding performed once at the very end as in `SafeExchangeProcessor`.

### Impact Explanation
Any account can trigger this arithmetic by submitting an `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract`. Because the legacy formula's precision degrades for the exponent range used (`0.0005` / `2000`) and for large token/TRX balances (`long` values up to ~9.2×10^18), repeated or crafted trades can cause the settled `anotherTokenQuant` to differ from the value a correct high-precision calculation would produce. Over many trades this can lead to systematic value leakage from an exchange's paired-asset pool (effectively an unbacked-balance condition for TRC10/TRX pairs) or unfairly disadvantage counterparties, since the pool balances (`firstTokenBalance`/`secondTokenBalance`) are updated using the imprecise output.

### Likelihood Explanation
The vulnerable code path is not test-only or mocked — it's the actual production default until the `allowHardenExchangeCalculation` proposal is activated network-wide by the committee, and it is triggered by ordinary signed transactions from any account holding TRX/TRC10 assets in an `Exchange`. No special privileges are required; only crafted `quant` values and repeated trades are needed to accumulate/exploit the rounding bias, similar to how the Fei report demonstrated systematic, non-random deviation (not mere ±1 noise).

### Recommendation
Ensure `allowHardenExchangeCalculation` (the `SafeExchangeProcessor` BigDecimal path) is enabled/mandatory network-wide, and consider removing or hard-deprecating the floating-point `ExchangeProcessor` entirely so unprivileged transactions can no longer select the imprecise legacy computation path. Add regression tests comparing legacy vs. hardened output across the full range of realistic TRX/TRC10 balances to bound and eliminate residual precision-loss discrepancies, following the same intermediate-truncation-elimination approach used in the actual Fei PR#31 fix.

### Proof of Concept
1. Ensure `allowHardenExchangeCalculation` is at its default/disabled value on the target chain (or a devnet with default config), so `AbstractExchangeActuator.allowHarden()` returns `false`.
2. Create an `Exchange` pair with a large `firstTokenBalance`/`secondTokenBalance` (e.g., near the `long` range used in test configs).
3. Submit an `ExchangeTransactionContract` with a `quant` chosen so that `1.0 + quant/newBalance` and the subsequent `pow(x, 2000)` step accumulate maximal floating-point relative error (verified analogous to the ~1 order-of-magnitude discrepancy reported for `BondingCurve`'s `Pre Scale` test, e.g. `51529` vs. correct `51977`).
4. Compare the `anotherTokenQuant` returned by `ExchangeProcessor.exchange()` (legacy path) against the value produced by `SafeExchangeProcessor.exchange()` for the identical inputs; a measurable, non-negligible, and directionally consistent discrepancy demonstrates the exploitable rounding bias, matching `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:17-39` vs `chainbase/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java:19-38`.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }
