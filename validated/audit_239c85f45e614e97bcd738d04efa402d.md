Audit Report

## Title
`harvest_rewards` never persists the updated `PoolInfo` reward checkpoint, allowing repeated over-accrual/duplicate reward payout in `pallet-asset-rewards` - (`substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`Pallet::harvest_rewards` calls `update_pool_and_staker_rewards` to compute an advanced `pool_info` (with bumped `reward_per_token_stored` and `last_update_block`) and uses it to pay out the staker's reward via `T::Assets::transfer`, but unlike `stake` and `unstake`, it never writes this updated `pool_info` back into the `Pools<T>` storage map with `Pools::<T>::insert(pool_id, pool_info)`. This causes `Pools::<T>::get(pool_id).last_update_block` to remain stale after every harvest, so the next call to `reward_per_token` re-counts the same elapsed-block interval that was already paid out, inflating the pool-wide `reward_per_token_stored` and over-crediting other stakers.

## Finding Description
`update_pool_and_staker_rewards` (`substrate/frame/asset-rewards/src/lib.rs:754-765`) is a pure function that derives `reward_per_token` from `pool_info.reward_rate_per_block`, `pool_info.total_tokens_staked`, and `pool_info.last_update_block` versus the current block (`reward_per_token`, lines 786-810), and returns a new `pool_info` with `last_update_block` advanced to `now` and `reward_per_token_stored` bumped (`update_pool_rewards`, lines 775-784), plus a `new_staker_info` whose `reward_per_token_paid` is checkpointed to the new stored value.

`stake` (lines 472-502) calls this helper and then executes `Pools::<T>::insert(pool_id, pool_info);` at line 492, persisting the checkpoint. `unstake` (lines 513-560) does the same at line 545. `harvest_rewards` (lines 569-615) calls the identical helper at line 584-585, uses `pool_info.reward_asset_id`/`pool_info.account` to perform the transfer at lines 588-595, but at no point calls `Pools::<T>::insert(pool_id, pool_info)` — the advanced `pool_info` (with the new `last_update_block`/`reward_per_token_stored`) is discarded when the extrinsic returns, and the on-chain `Pools<T>` entry keeps the pre-harvest `last_update_block`.

Because `reward_per_token` computes `rewardable_blocks_elapsed` as `current_block - pool_info.last_update_block` (lines 794-801), and `harvest_rewards` never advances `last_update_block` in storage, the next call to `reward_per_token` from any other staker's `stake`/`unstake`/`harvest_rewards` re-includes the block interval already paid out to the harvesting staker, inflating `reward_per_token_stored` for the whole pool beyond what `reward_rate_per_block × elapsed_blocks` should produce. There is no invariant elsewhere in the pallet (no reserve/pot integrity check) that catches this drift before `T::Assets::transfer` executes with `Preservation::Expendable`, so the corrupted `reward_per_token_stored` value directly inflates every other staker's `derive_rewards` output and thus their payout amount drawn from `pool_info.account`.

## Impact Explanation
This is duplicate/over-settlement of payout state: the pallet-controlled pool account (`pool_info.account`) pays out reward-asset amounts that exceed what `reward_rate_per_block` and elapsed blocks should account for, because the `last_update_block`/`reward_per_token_stored` checkpoint silently fails to advance on `harvest_rewards`. This matches the required impact of duplicate settlement/payout causing unbacked extraction of value from a pallet-held account, reachable via a normal public, unprivileged extrinsic.

## Likelihood Explanation
Any staker calling `harvest_rewards` triggers this path unconditionally — no special preconditions, privileged origin, or governance action are required. It is also actively exploitable: a staker can repeatedly call `harvest_rewards` to keep the persisted `last_update_block` pinned to a stale value while other stakers' rewards keep accruing from that same stale checkpoint, amplifying the drift.

## Recommendation
In `harvest_rewards`, persist the updated `pool_info` the same way `stake`/`unstake` do:
```rust
let (pool_info, mut staker_info) =
    Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;
Pools::<T>::insert(pool_id, pool_info.clone());
```
placed before or immediately after the `T::Assets::transfer` call, so `last_update_block`/`reward_per_token_stored` are checkpointed in storage identically to `stake` and `unstake`.

## Proof of Concept
1. Create a pool with `reward_rate_per_block = R` and stake tokens from staker A and staker B via `create_pool`/`stake`.
2. At block `N`, staker A calls `harvest_rewards(pool_id, None)`. `update_pool_and_staker_rewards` computes a `pool_info` with `last_update_block = N` and an advanced `reward_per_token_stored`, but since `Pools::<T>::insert` is never called (`substrate/frame/asset-rewards/src/lib.rs:584-615`), `Pools::<T>::get(pool_id).last_update_block` remains the pre-harvest value.
3. At block `N + K`, staker B calls `stake`/`unstake`/`harvest_rewards`. `reward_per_token` (lines 794-801) recomputes `rewardable_blocks_elapsed` from the stale `last_update_block`, re-including the `[stale_value, N]` window already paid to staker A, inflating `reward_per_token_stored` and staker B's derived rewards beyond `R * (N+K - original_last_update_block)/total_tokens_staked`.
4. Add a runtime test asserting `Pools::<T>::get(pool_id).last_update_block` and total rewards paid across a `harvest_rewards` → `stake`/`unstake` sequence to confirm the numeric over-accrual and the pool account's reward-asset balance depleting faster than `reward_rate_per_block` intends.
