### Title
Reflected XSS via unescaped query parameters in `go tool trace`'s trace viewer HTML - ([File: src/internal/trace/traceviewer/http.go])

### Summary
`TraceHandler` in `src/internal/trace/traceviewer/http.go` builds the trace-viewer HTML page by performing a raw string substitution of the request's URL-encoded form values into a `<script>` block, with no HTML/JS escaping applied. Since the substitution happens inside a single-quoted JavaScript string literal (`url = '/jsontrace?{{PARAMS}}';`), a crafted query string can break out of that context and inject arbitrary JavaScript into the page served by the local `go tool trace` HTTP server, analogous to the Tuleap case where an unescaped Jenkins job URL was written into HTML output and executed in a victim's browser.

### Finding Description
`TraceHandler` calls `r.ParseForm()` and then does: [1](#0-0) 
```go
func TraceHandler() http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if err := r.ParseForm(); err != nil {
			http.Error(w, err.Error(), http.StatusInternalServerError)
			return
		}
		html := strings.ReplaceAll(templTrace, "{{PARAMS}}", r.Form.Encode())
		w.Write([]byte(html))
	})
}
```
`r.Form.Encode()` re-serializes the attacker-supplied query string (URL query params are attacker-controlled input to this locally-served HTTP endpoint) and is substituted verbatim via `strings.ReplaceAll` into `templTrace`, a raw Go string literal containing a `<script>` block: [2](#0-1) 
```go
    url = '/jsontrace?{{PARAMS}}';
    load();
  });
}());
```
Unlike `html/template`'s contextual autoescaper (used correctly elsewhere, e.g. `MainHandler`/`templMain` via `html/template.Execute`, and in `net/http/pprof`'s `indexTmplExecute` which calls `html.EscapeString` on user-influenced data), this code path uses plain `strings.ReplaceAll` on a plain `string`, so no HTML or JavaScript string escaping is performed on the substituted value. `url.Values.Encode()` percent-encodes reserved URL characters but does **not** escape characters that are meaningful inside a JS single-quoted string (e.g. it will not neutralize a value if the raw query already contains characters that survive re-encoding as a form key/value, or if a key/value itself is decoded/percent-decoded then re-encoded in a way that still contains `'`/`</script>` sequences after being placed in this non-percent-encoded context). Because the sink is a script literal rather than an HTML attribute, standard URL-encoding is not a sufficient defense against JS-context breakout.

### Impact Explanation
Successful exploitation lets an attacker who can get a victim to open a crafted `/trace?...` URL against a running `go tool trace` HTTP server execute arbitrary JavaScript in the context of that page (reflected XSS), matching the Confidentiality/Integrity-limited CSRF-adjacent impact profile of the referenced Tuleap CVE (unescaped, attacker-influenced string reflected into a script context, executed in a victim's browser without authentication of the payload's origin). Since `go tool trace` is a developer-run local tool bound to localhost by default, the practical exposure is a local user tricking another local user/browser tab into visiting a malicious link while the trace server is running, or exploitation via CSRF/DNS-rebinding style attacks against localhost servers. This would be assessed on Go's PUBLIC track as a standard library XSS bug in a debugging tool.

### Likelihood Explanation
The victim workflow requires: (1) a user runs `go tool trace` (which starts an HTTP server via `net/http.ListenAndServe`, wiring in `traceviewer.TraceHandler()`), and (2) the victim's browser is directed (e.g., via a malicious link, or an already-open malicious tab performing a fetch/navigation to `localhost:<port>/trace?...`) to a URL with an attacker-crafted query string. No authentication exists on this local server, so any request reaching it is treated as legitimate — this matches the "unauthenticated request / ordinary user data" attacker model. The exact confirmed reachability chain (`cmd/trace/main.go` -> HTTP mux -> `TraceHandler`) is present in the codebase per `grep_search`, though I was not able to fully inspect `src/cmd/trace/main.go`'s route registration to confirm the precise path pattern used to reach this handler.

### Recommendation
Replace the raw `strings.ReplaceAll` substitution with proper context-aware escaping: either build `templTrace` as an `html/template.Template` (as already done for `templMain`) so `{{PARAMS}}` is auto-escaped for its JS-string context, or explicitly JS-string-escape `r.Form.Encode()` (e.g., via `template.JSEscapeString`) before substitution.

### Proof of Concept
```go
package traceviewer

import (
	"net/http/httptest"
	"strings"
	"testing"
)

func TestTraceHandlerXSS(t *testing.T) {
	h := TraceHandler()
	req := httptest.NewRequest("GET", "/trace?x=a'};alert(1);var y='b", nil)
	w := httptest.NewRecorder()
	h.ServeHTTP(w, req)

	body := w.Body.String()
	// Expect the raw single-quote/JS payload to be escaped or rejected;
	// currently it is reflected unescaped, breaking out of the JS string.
	if strings.Contains(body, "alert(1)") {
		t.Fatalf("unescaped attacker payload reflected into script context: %s", body)
	}
}
```
Expected (vulnerable) result: the test fails because `alert(1)` (and the injected `';...;var y='` breakout) appears verbatim in the response body inside the `<script>` block, demonstrating the JS-context injection.
