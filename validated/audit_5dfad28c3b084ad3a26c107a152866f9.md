### Title
Exchange actuators ignore the boolean result of `reduceAssetAmountV2`/`addAssetAmountV2`, allowing exchange pool state to diverge from actual account token balances - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` mutate the `ExchangeCapsule` pool balances and then move tokens between the user account and the pool by calling `AccountCapsule.reduceAssetAmountV2()` / `addAssetAmountV2()`, but they never check the boolean return value of these calls. This is the same bug class as the reported UXD issue: a token "transfer" call whose success/failure result is discarded, so the caller proceeds as if the transfer succeeded even when it silently failed.

### Finding Description
`reduceAssetAmountV2` and `addAssetAmountV2` in `AccountCapsule` return `false` when the account does not actually hold the asset (e.g., the key was never imported, or `currentAmount` is `null`) instead of throwing: [1](#0-0) 

Some actuators correctly check this return value and abort the whole execution via `ContractExeException` when it fails, e.g. `TransferAssetActuator`: [2](#0-1) 
and `ParticipateAssetIssueActuator`: [3](#0-2) 

However, the Exchange actuators do not follow this pattern. In `ExchangeInjectActuator.execute()`, the exchange pool balance is updated first (`exchangeCapsule.setBalance(...)`), and the user's token debit is then performed via unchecked calls: [4](#0-3) 

The same unchecked pattern exists in `ExchangeWithdrawActuator.execute()` (credit side): [5](#0-4) 

and in `ExchangeTransactionActuator.execute()` (both debit and credit sides): [6](#0-5) 

Because these calls are ignored, if `reduceAssetAmountV2`/`addAssetAmountV2` returns `false` for any reason, the exchange pool's on-chain accounting (`ExchangeCapsule` balances written via `Commons.putExchangeCapsule`) is committed and the transaction reports `SUCESS`, even though the account's actual asset ledger was never debited or credited to match.

### Impact Explanation
Any unprivileged account holder can broadcast `ExchangeInjectContract`, `ExchangeWithdrawContract`, or `ExchangeTransactionContract` transactions (these actuators are directly reachable actuator/validate-execute paths for ordinary transactions). If the underlying asset ledger update silently fails while the pool-side bookkeeping still updates and commits, the exchange pool's recorded reserves become inconsistent with the sum of actual token balances backing them — i.e., unbacked/mismatched balances in the on-chain TRON DEX (Bancor-style exchange) subsystem, which is the accounting primitive relied upon by every subsequent trade against that exchange pool. This matches the reported bug class: a token move whose result is unchecked, letting protocol-level state (pool reserves) advance as if a transfer succeeded when it did not.

### Likelihood Explanation
Under normal circumstances `validate()` (`assetBalanceEnoughV2` / balance checks) is expected to guarantee sufficiency before `execute()` runs, which reduces (but per the audited code does not structurally guarantee, since `validate()` and `execute()` are separate, unenforced-by-type-system code paths) the chance of the underlying reduce/add call actually returning `false`. I was not able to fully confirm within this investigation whether there exists a concrete input (e.g., toggling `AllowSameTokenName`, or an asset-map/`AssetIssueStore` inconsistency between the check and the mutation) that can make `reduceAssetAmountV2`/`addAssetAmountV2` return `false` after `validate()` passed for these three actuators specifically — this would need dedicated fuzzing/testing of the Exchange actuators, ideally in a Devin session with full test-suite access, to determine whether it is reachable in practice or only a defense-in-depth gap.

### Recommendation
Mirror the pattern already used in `TransferAssetActuator` and `ParticipateAssetIssueActuator`: check the boolean return of every `reduceAssetAmountV2`/`addAssetAmountV2` call in `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`, and throw `ContractExeException` (aborting the whole transaction, including the `exchangeCapsule.setBalance` update) if any of them return `false`.

### Proof of Concept
Not independently reproduced — the index does not show a concrete transcript demonstrating `reduceAssetAmountV2`/`addAssetAmountV2` returning `false` after `validate()` succeeds for these Exchange actuators. Confirming exploitability would require running/instrumenting the actuator test suite (e.g. `ExchangeInjectActuatorTest`, `ExchangeWithdrawActuatorTest`, `ExchangeTransactionActuatorTest`) to search for an input sequence where the pre-execute check and the in-execute mutation diverge.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
