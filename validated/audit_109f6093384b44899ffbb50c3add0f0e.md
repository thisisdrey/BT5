### Title
Reverted TVM Constant Calls Return Uncleared Log Events, Enabling Fake Event Spoofing to Off-Chain Consumers - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.execute` special-cases constant/read-only calls (`isConstantCall == true`, used by `TriggerConstantContract`/`EstimateEnergy`/`eth_call`) and returns *before* reaching the log-clearing logic that normal (non-constant) execution performs on revert or exception.

### Finding Description
For a normal transaction, when the VM run ends in an exception or a `REVERT`, `VMActuator.execute` explicitly discards any state/log side effects: [1](#0-0) 
This mirrors the correct Ethereum semantics — logs emitted before a revert must not be observable, since all execution effects are rolled back.

However, for constant calls the method takes an early-return branch that only handles the `getException() != null` case (marking internal transactions rejected) and never touches `result.getLogInfoList()`: [2](#0-1) 
Critically, when the contract executes a `REVERT` opcode without throwing a Java exception (`result.isRevert() == true`, `result.getException() == null`), this branch is a no-op with respect to logs — the `logInfoList` populated during the reverted execution is left completely intact.

That uncleared list then flows straight into the constant-call response builder in `Wallet.callConstantContract`, which unconditionally serializes every entry in `result.getLogInfoList()` into the returned `TransactionExtention`, while separately marking the result `FAILED`: [3](#0-2) 
The `FAILED`/`REVERT opcode executed` status and the (bogus) `logs` list are two independent fields on the same response; any consumer that follows common Ethereum-tooling conventions of iterating `logs`/`events` first — exactly the flaw described in the Phoenix SDK report, which failed to check `is_err` before parsing logs — will process log data that describes state changes that never happened. This is reachable by any unauthenticated caller of `TriggerConstantContract`/`EstimateEnergy`/`TriggerConstantContractOnSolidity`/`TriggerConstantContractOnPBFT` via `Wallet.callConstantContract`, and via JSON-RPC `eth_call`/`eth_estimateGas` in `TronJsonRpcImpl`, simply by deploying a contract that emits an ERC20-style `Transfer`/`Approval` event (or any custom event) and then executes `REVERT`.

### Impact Explanation
An attacker can craft a contract whose fallback/entrypoint emits a legitimate-looking `Transfer` (or any other) log and then reverts. Calling `TriggerConstantContract` against this contract returns a response containing that log while `result` is `FAILED`. Off-chain infrastructure (exchanges, wallets, bridges, indexer/monitoring services) that use `TriggerConstantContract`/`eth_call`-style simulation to pre-validate a transfer/deposit before crediting funds, and that inspects the `logs`/`log` field without strictly gating on the `result` code first (the exact bug class from the referenced Phoenix SDK report), can be tricked into believing a token transfer occurred when it did not — leading to unbacked balance crediting / theft-adjacent conditions for the operator of that off-chain service.

### Likelihood Explanation
Triggering the bug requires nothing more than deploying an ordinary smart contract (open to any user) and calling the public, unauthenticated `TriggerConstantContract` query endpoint (or `eth_call`) with a transaction that reverts — there is no special permission required and no on-chain state is even needed to be persisted, since this executes only against the constant/estimate path. The only extra condition (as in the source Phoenix advisory) is that a downstream SDK/consumer parses the log/event fields before checking the result status, which is a common integration pattern for balance-crediting bots.

### Recommendation
In `VMActuator.execute`, before returning from the `isConstantCall` branch, clear `result.getLogInfoList()` (and `result.getDeleteAccounts()`) whenever `result.getException() != null || result.isRevert()`, mirroring exactly what the non-constant branch already does at lines 240–244. Alternatively/additionally, have `Wallet.callConstantContract` skip populating `builder.addLogs(...)` whenever `result.getException() != null`, `result.isRevert()`, or `StringUtils.isNoneEmpty(result.getRuntimeError())` is true.

### Proof of Concept
1. Deploy a contract with a function such as:
```solidity
event Transfer(address indexed from, address indexed to, uint256 value);
function fakeTransfer(address to, uint256 value) public {
    emit Transfer(msg.sender, to, value);
    revert("forced revert");
}
```
2. Call `TriggerConstantContract` (HTTP: `framework/src/main/java/org/tron/core/services/http/TriggerConstantContractServlet.java`, or JSON-RPC `eth_call` via `TronJsonRpcImpl`) invoking `fakeTransfer(victimOrExchangeDeposit, largeAmount)`.
3. Observe the response: `result.result` is `FAILED` / `contractResult=REVERT`, but `constant_result`/`logs` still contains the `Transfer(msg.sender, victim, largeAmount)` log entry, because `VMActuator.execute`'s `isConstantCall` branch (lines 231-238) never clears `logInfoList` and `Wallet.callConstantContract` (lines 3181-3197) copies it unconditionally into the response.
4. Any downstream consumer inspecting only `logs`/events from this response (without checking `result`) would treat this as a genuine on-chain transfer, despite no state change ever occurring.
