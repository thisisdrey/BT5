### Title
Missing bounds validation in ARM `.ARM.attributes` ELF-section parsing can cause slice-bounds panic in the Go linker - ([File: src/cmd/link/internal/loadelf/ldelf.go])

### Summary
`parseArmAttributes` in `cmd/link/internal/loadelf` parses the `.ARM.attributes` section of ELF object files without validating the encoded section/subsection lengths before slicing, mirroring the CVE-2022-47519 pattern (an in-kernel attribute parser trusting an attacker-supplied length field and writing/reading out of bounds). This is invoked when the Go linker loads ARM ELF object files (e.g., `.syso`/cgo-produced `.o` files bundled in a module) during `go build`.

### Finding Description
Attacker input: a malicious module or vendored archive ships a crafted ARM ELF `.o`/`.syso` file with a bogus `.ARM.attributes` section.
Go entry point: `loadelf.Load` reads the ELF section table and, for `SHT_ARM_ATTRIBUTES`, calls `parseArmAttributes(e, data)`. [1](#0-0) 
Inside the function, `sectionlength := e.Uint32(data)` and `sectiondata := data[4:sectionlength]` are computed directly from attacker-controlled bytes with no check that `sectionlength >= 4` or `sectionlength <= len(data)`, and the same unchecked pattern repeats for `subsectionsize` inside the inner loop. [2](#0-1) 
If `sectionlength` is less than 4, or greater than `len(data)`, or if `data[0]` is accessed on an empty slice, this slicing panics ("slice bounds out of range") — the memory-safe analog of the kernel's OOB write, since Go's runtime traps the invalid access as a crash rather than corrupting memory silently. This is the same root-cause shape as CVE-2022-47519: an attribute/length field parsed from untrusted input is used directly as a slice/array bound without validating it against the buffer's actual size.

### Impact Explanation
A crafted object file (which can be embedded/vendored inside an otherwise-normal Go module and picked up automatically by `go build` when targeting `GOARCH=arm`, e.g. via a `.syso` file or a cgo-produced `.o`) can crash the `go build`/link step with a runtime panic. This is a build-time parser panic, not memory corruption or code execution, since Go's bounds checks convert what would be a C-level OOB write into a safe panic. Under Go's vulnerability policy this is a plausible malicious-input parser panic (denial-of-service of the build tool), not remote code execution or an authentication/integrity bypass.

### Likelihood Explanation
Reachable through a normal victim workflow: a developer runs `go build` on a module/package that contains (or vendors) a malicious ARM ELF object file with a malformed `.ARM.attributes` section. No special privileges, network exposure, or malicious build environment are required — only that the ELF file be included in the build, which is consistent with the "published module/archive/source consumed by a normal victim workflow" premise. However, I could not fully confirm from the available files whether every call path always supplies a well-formed, in-bounds `data` slice (e.g., whether `elfmap`/section-size checks upstream already guarantee `len(data) >= sect.size` and that arbitrary encoded sub-lengths can actually exceed that), because deeper call-site validation (e.g., in `elfmap` and section-size gating) was only partially inspected due to iteration limits.

### Recommendation
Add explicit bounds checks in `parseArmAttributes` before every slice operation derived from parsed integers: verify `len(data) >= 1` before indexing `data[0]`, verify `4 <= sectionlength <= len(data)` before slicing `data[4:sectionlength]`, and verify `sz+4 <= subsectionsize <= len(sectiondata)` before slicing `sectiondata[sz+4:subsectionsize]`. Return a descriptive error (as already done elsewhere in this function) instead of allowing the slice expression to panic.

func parseArmAttributes(e binary.ByteOrder, data []byte) (found bool, ehdrFlags uint32, err error) {
	found = false
	if data[0] != 'A' {
		return false, 0, fmt.Errorf(".ARM.attributes has unexpected format %c\n", data[0])
	}
	data = data[1:]
	for len(data) != 0 {
		sectionlength := e.Uint32(data)
		sectiondata := data[4:sectionlength]
		data = data[sectionlength:]

		nulIndex := bytes.IndexByte(sectiondata, 0)
		if nulIndex < 0 {
			return false, 0, fmt.Errorf("corrupt .ARM.attributes (section name not NUL-terminated)\n")
		}
		name := string(sectiondata[:nulIndex])
		sectiondata = sectiondata[nulIndex+1:]

		if name != "aeabi" {
			continue
		}
		for len(sectiondata) != 0 {
			subsectiontag, sz := binary.Uvarint(sectiondata)
			subsectionsize := e.Uint32(sectiondata[sz:])
			subsectiondata := sectiondata[sz+4 : subsectionsize]
			sectiondata = sectiondata[subsectionsize:]

			if subsectiontag != TagFile {
				continue
			}
			attrList := elfAttributeList{data: subsectiondata}
			for !attrList.done() {
				attr := attrList.armAttr()
				if attr.tag == TagABIVFPArgs && attr.ival == 1 {
					found = true
					ehdrFlags = 0x5000402 // has entry point, Version5 EABI, hard-float ABI
				}
			}
			if attrList.err != nil {
				return false, 0, fmt.Errorf("could not parse .ARM.attributes\n")
			}
		}
	}
	return found, ehdrFlags, nil
}
