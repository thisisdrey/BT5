## Finding

### Title
FreezeBalanceV2 TVM native-contract path skips the committee "unfreeze delay" feature gate enforced by the transaction actuator - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceV2Processor.java])

### Summary
`FreezeBalanceV2Actuator`, the entry point for a standalone `FreezeBalanceV2Contract` transaction, explicitly gates the whole FreezeV2 feature behind a committee-controlled dynamic parameter before allowing any freeze-v2 state mutation: [1](#0-0) 

```java
if (!dynamicStore.supportUnfreezeDelay()) {
  throw new ContractValidateException("Not support FreezeV2 transaction,"
      + " need to be opened by the committee");
}
```

The same freeze-v2 logic is also reachable from inside a smart contract via the TVM `FREEZEBALANCEV2` opcode (`freezeBalanceV2Action` in `OperationActions.java`, backed by `Program.freezeBalanceV2()`), which delegates validation/execution to `FreezeBalanceV2Processor`: [2](#0-1) 

```java
public static void freezeBalanceV2Action(Program program) {
  if (program.isStaticCall()) {
    throw new Program.StaticCallModificationException();
  }
  DataWord resourceType = program.stackPop();
  DataWord frozenBalance = program.stackPop();
  boolean result = program.freezeBalanceV2(frozenBalance, resourceType);
  ...
}
``` [3](#0-2) 

But `FreezeBalanceV2Processor.validate()` — the sole validation performed for this internal path — never checks `supportUnfreezeDelay()`: [4](#0-3) 

It only validates the owner address, balance bounds, resource type, and a self-destruct/CPU-timing edge case — the committee feature-flag check present in the actuator is absent.

### Finding Description
The FreezeV2 resource model is a committee-gated feature: `supportUnfreezeDelay()` must be turned on via an on-chain proposal before FreezeV2 semantics (new frozen-balance accounting, unfreeze delay, `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` bookkeeping) are meant to be active on the network. `FreezeBalanceV2Actuator.validate()` enforces this as a hard precondition for the "normal" transaction path. `FreezeBalanceV2Processor`, however, is shared logic invoked both by the actuator and directly by the TVM `FREEZEBALANCEV2`/`UNFREEZEBALANCEV2` opcodes (via `Program.freezeBalanceV2()` / `Program.unfreezeBalanceV2()`), and it omits the `supportUnfreezeDelay()` check entirely. Any account can reach this via a simple `TriggerSmartContract` call to a contract that executes the TVM opcode — no special privilege is required, mirroring the "loopback path with a separate spawn route that misses the denylist/gate" pattern from the advisory: one call path (actuator) enforces the access-control gate, a second call path (TVM opcode → shared processor) reaches the same sensitive state mutation but omits it.

### Impact Explanation
If reached before the committee has enacted `ALLOW_TVM_FREEZE_V2`/`supportUnfreezeDelay`, this lets any contract invoker mutate `FrozenV2` balances and global weight totals (`TotalNetWeight`, `TotalEnergyWeight`, `TotalTronPowerWeight`) through a feature the network has not yet activated, producing state inconsistent with the rest of the consensus logic that assumes FreezeV2 accounting is only reachable once the flag is on. This can corrupt bandwidth/energy/vote-weight accounting network-wide (a chain-consistency/consensus-affecting bug), which given the rules ("unbacked balance ... or chain split") would be scoped as Medium/High depending on exploitability once FreezeV2 is not yet enabled on mainnet.

### Likelihood Explanation
Low-to-moderate in practice on current mainnet since FreezeV2 is very likely already enabled (`supportUnfreezeDelay()==true`) by now, making the gate check currently moot; however, on any future network (new private chain, test network, or a network that reverts/rolls this feature back) where the proposal has not been passed, an unprivileged contract call is sufficient to reach the bypass — no signature beyond a normal `TriggerSmartContract` transaction, and no elevated permission is required.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `FreezeBalanceV2Processor.validate()` (and equivalently to `UnfreezeBalanceV2Processor`, `WithdrawExpireUnfreezeActuator`'s processor path, and any other FreezeV2 native-contract processor invoked from `Program`), so that the TVM opcode entry point enforces the identical committee gate that the transaction actuator enforces.

### Proof of Concept
1. On a network/state where `DynamicPropertiesStore.getUnfreezeDelay()` (i.e., `supportUnfreezeDelay()`) is `0` (feature not yet enacted).
2. Deploy a trivial contract containing the TRON-specific `FREEZEBALANCEV2` opcode (e.g. via `target.freezeBalanceV2(amount, resourceType)` as compiled by `tron-solc`, similar to the pattern used in `framework/src/test/java/org/tron/common/runtime/vm/FreezeV2Test.java`).
3. Send an ordinary `TriggerSmartContract` transaction invoking that function.
4. Observe that `Program.freezeBalanceV2()` → `FreezeBalanceV2Processor.validate()`/`execute()` succeeds and mutates frozen balances/weight totals, whereas sending an equivalent `FreezeBalanceV2Contract` transaction directly through `FreezeBalanceV2Actuator` is rejected with "Not support FreezeV2 transaction, need to be opened by the committee".

*Note: I was unable to fully confirm within the available tool-call budget whether the `FREEZEBALANCEV2`/`UNFREEZEBALANCEV2` opcodes themselves are gated by a fork/`VMConfig` "enabled" predicate at the `Operation`/`OperationRegistry` registration level (which could make the opcode unreachable until a related hard fork is active). If such an opcode-level gate exists and is kept in lockstep with `supportUnfreezeDelay`, the practical bypass window would be limited to a race between the two flags; this would need to be verified in a live session before treating this as fully proven.*

  public void validate(FreezeBalanceV2Param param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    if (ownerCapsule == null) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + readableOwnerAddress + "] does not exist");
    }
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException(
          "FrozenBalance must be less than or equal to accountBalance");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      case TRON_POWER:
        if (!repo.getDynamicPropertiesStore().supportAllowNewResourceModel()) {
          throw new ContractValidateException(
              "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
        }
        break;
      default:
        if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()) {
          throw new ContractValidateException(
              "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY、TRON_POWER]");
        } else {
          throw new ContractValidateException(
              "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
        }
    }

    if (repo.isSelfDestructed(ownerAddress)) {
      MUtil.checkCPUTimeForFreezeV2AfterSelfDestruct();
    }
  }
