### Title
Unauthenticated RecvError packets allow any network attacker to force-close a peer's tunnel - ([File: outside.go])

### Summary
Nebula processes `header.RecvError` packets *before* any cryptographic authentication (AEAD decryption/certificate check) is performed, and the only defense against a forged sender is an unauthenticated comparison of the observed UDP source address against a cached remote address. This lets any attacker who can spoof UDP source addresses and knows/guesses a target's `RemoteIndex` force-close a legitimate tunnel and purge state from the pending handshake map — the "anyone can call a privileged function" bug class applied to the tunnel-teardown path.

### Finding Description
In `readOutsidePackets`, `header.RecvError` is handled in the "Unencrypted packets" branch, dispatched purely from the parsed header, with no AEAD decryption or peer-certificate verification: [1](#0-0) 

The handler `handleRecvError` then only checks a config policy (`ShouldRecvError`) and compares the packet's `RemoteIndex` against the hostmap and the packet's source address against a cached remote endpoint: [2](#0-1) 

If the check passes, it immediately tears down the tunnel and deletes the pending handshake state:
```go
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
``` [3](#0-2) 

The only "authentication" here is `hr.IsValid() && hr != addr` — comparing the sender's UDP source address as reported by the socket read against the hostinfo's stored remote endpoint. This is not a cryptographic check: UDP allows arbitrary IP source-address spoofing on most networks (particularly UDP-over-IP without ingress filtering), and even without spoofing, an attacker at the same NAT'd network or one who can observe/guess `h.RemoteIndex` (a 32-bit locally allocated index, not secret, and observable on the wire in every packet exchanged with that peer) can trigger this path from the correct-looking source address if any on-path or off-path spoofing is possible. Unlike `header.CloseTunnel`, which is processed only *after* successful AEAD decryption (see `outside.go:124-166`), `RecvError` has no equivalent cryptographic binding to the session keys derived from the CA-signed certificate handshake.

### Impact Explanation
This is a remote, unauthenticated denial-of-service / state-poisoning primitive: an attacker with no valid CA-signed certificate can force termination of an established, authenticated tunnel between two legitimate peers by sending a single spoofed/forged `RecvError` packet, without needing a handshake, key material, or a valid certificate. Repeated exploitation can prevent tunnel stability entirely, and combined with the fact that `handshakeManager.DeleteHostInfo` also clears pending handshake info, it can be used to disrupt reconnection attempts as well.

### Likelihood Explanation
The packet type is explicitly whitelisted for unauthenticated processing at `outside.go:76-84` (grouped as "Unencrypted packets"), so no key material, decryption, or certificate validation is required to reach `handleRecvError`. The `RemoteIndex` needed is a non-secret 32-bit value transmitted in cleartext in every packet header for a session, and the source-address check can be defeated via IP spoofing (a well-known limitation of UDP-based session identification when the address is the only anti-spoof control). Given accept_recv_error defaults to "always" in some configurations (`outside.go:522-526`, `interface.go` reload logic), the exposure is realistic on default/typical deployments without explicit ingress filtering.

### Recommendation
- Require `RecvError` packets to be cryptographically bound to the session, e.g., by including a MAC computed with the tunnel's negotiated key (or requiring accompaniment of the current AEAD-authenticated Message counter) rather than relying solely on a plaintext index + address comparison.
- Alternatively, harden the existing address check to require exact `netip.AddrPort` matching plus rate-limiting/token validation, and default `listen.accept_recv_error` to `never`/`private` rather than `always`.
- Consider deprecating the unauthenticated `RecvError` fast-teardown path in favor of the connection manager's existing traffic-check based rehandshake/teardown logic, which already validates certificate state (`connection_manager.go` `isInvalidCertificate`).

### Proof of Concept
1. Establish a legitimate tunnel between A and B (2 CA-signed nodes).
2. As attacker M (no valid certificate), observe or infer the `RemoteIndex` A uses for the tunnel to B (visible in cleartext in packet headers exchanged between A and B, e.g., via passive network observation).
3. Craft a UDP packet with header `Type = header.RecvError`, `RemoteIndex = <A's local index for the B tunnel>`, spoofing the source IP:port to match B's known UDP endpoint (or send from an address the target hasn't yet validated a mismatch on), and send it to A.
4. A's `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees `addr` matches (or bypasses check with valid spoof), and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` — tearing down the tunnel to B without any cryptographic proof of identity from M.

Note: I was unable to fully verify OS/network-level UDP source spoofing feasibility or the exact entropy/predictability of `RemoteIndex` generation (`generateIndex`) within the scope of this reasoning session; a background Devin session with full repo access could confirm the exact randomness source for indices and any additional ingress protections that might mitigate spoofing in specific deployment configurations.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
