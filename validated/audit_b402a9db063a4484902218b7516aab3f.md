### Title
NPE in `UnDelegateResourceActuator.execute()` on unlocked `DelegatedResourceCapsule` when only a locked delegation record exists - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.validate()` accepts an `UnDelegateResourceContract` as long as *either* the unlocked (`lock=false`) or the locked (`lock=true`) `DelegatedResourceCapsule` record exists, but `execute()` unconditionally dereferences the unlocked record without a null check, causing a `NullPointerException` when only the locked record was ever created.

### Finding Description
`validate()` fetches both possible `DelegatedResourceCapsule` records: [1](#0-0) 
and only rejects the transaction if **both** are null:
```
if (unlockResourceCapsule == null && lockResourceCapsule == null) {
  throw new ContractValidateException("delegated Resource does not exist");
}
```
The subsequent balance checks in `switch (unDelegateResourceContract.getResource())` (BANDWIDTH/ENERGY cases) sum `unlockResourceCapsule.getFrozenBalanceForBandwidth()` (guarded by `if (unlockResourceCapsule != null)`) and `lockResourceCapsule.getFrozenBalanceForBandwidth()` (guarded by `if (lockResourceCapsule != null ...)`), so validation can pass purely on the strength of the locked record while the unlocked record is `null`: [2](#0-1) 

In `execute()`, the unlocked record is fetched again and used **unconditionally**, with no null guard: [3](#0-2) 
```
byte[] unlockKey = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, false);
DelegatedResourceCapsule unlockResource = delegatedResourceStore.get(unlockKey);
...
switch (unDelegateResourceContract.getResource()) {
  case BANDWIDTH: {
    unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);
```
If `unlockResource` is `null` (no unlocked delegation record ever existed for the owner/receiver pair, only a locked one), this line throws a `NullPointerException`. This is structurally identical to the CVE's root cause: an accessor path assumes a table/record has been initialized and dereferences it without checking, because a sibling validation path allowed an alternate, unrelated record to satisfy the precondition.

### Impact Explanation
A `NullPointerException` thrown inside `AbstractActuator.execute()` during transaction processing is an unchecked `RuntimeException`, not one of the actuator's declared checked exceptions (`ContractExeException`/`ContractValidateException`). Depending on how the call site (`TransactionTrace`/`Manager.processTransaction`) handles unchecked exceptions during block application, this can propagate as an unexpected exception while applying a block containing the malicious transaction, causing an abnormal failure/crash of transaction processing for that block on every node that processes it — a reachable node-crash/DoS condition triggered by a single, ordinary signed transaction pair (`DelegateResourceContract` with `lock=true` followed by `UnDelegateResourceContract`). This matches the "node crash or halt" impact category permitted by the rules.

### Likelihood Explanation
Reachable by any account holder with frozen bandwidth (FreezeBalanceV2) balance to delegate — no special privilege, SR/witness/committee role, or contract deployment is required. Both `DelegateResourceContract` (with `lock=true`) and `UnDelegateResourceContract` are ordinary broadcastable transactions any wallet/API client can submit via `broadcastTransaction`. The precondition (creating only a locked delegated-resource record, never an unlocked one, and later expiring the lock so `validate()`'s balance checks pass) is straightforward to construct deterministically.

### Recommendation
In `UnDelegateResourceActuator.execute()`, null-check `unlockResource` before dereferencing it (mirroring the `Objects.nonNull(receiverCapsule)` pattern already used elsewhere in the same method), and only call `unlockResource.addFrozenBalanceForBandwidth(...)`/`addFrozenBalanceForEnergy(...)` when `unlockResource != null`, falling back to operating solely on `lockResource` when the unlocked record does not exist — analogous to fixing `dev_pm_opp_find_bw_*()` by asserting the table exists before use.

### Proof of Concept
1. Owner account freezes bandwidth via `FreezeBalanceV2Contract` to obtain `FrozenV2BalanceForBandwidth`.
2. Owner broadcasts `DelegateResourceContract{resource=BANDWIDTH, lock=true, receiverAddress=R, balance=B}`. This creates only the **locked** `DelegatedResourceCapsule` (key with `lock=true`) for (owner, R); no unlocked record (key with `lock=false`) is ever created for this pair.
3. Wait/simulate until the lock period expires so `lockResourceCapsule.getExpireTimeForBandwidth() < now`.
4. Owner broadcasts `UnDelegateResourceContract{resource=BANDWIDTH, receiverAddress=R, balance=B}`.
   - `validate()` passes: `unlockResourceCapsule == null` but `lockResourceCapsule != null` and `lockResourceCapsule.getFrozenBalanceForBandwidth() >= B` with the lock expired, so the "both null" check and balance check both pass.
   - `execute()` runs `unlockResource = delegatedResourceStore.get(unlockKey)` → `null` (no unlocked record exists), then unconditionally calls `unlockResource.addFrozenBalanceForBandwidth(-B, 0)` → `NullPointerException`.

Note: I could not fully trace how the top-level block-application/transaction-execution loop in `Manager`/`TransactionTrace` handles an uncaught `RuntimeException` thrown from an actuator's `execute()` in this specific version, so I cannot state with certainty whether the failure mode is a full node crash, a halted block application, or a transaction-level failure that gets swallowed. This detail should be verified in `TransactionTrace.exec()`/`Manager.processTransaction()` before treating the crash/halt impact as fully confirmed; regardless, the NPE itself is confirmed by direct code inspection.
