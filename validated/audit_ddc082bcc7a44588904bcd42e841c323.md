### Title
Attacker can fill a victim's `MAX_TOKENS_PER_USER` slots with dust deposit-token transfers, blocking the victim from depositing new collateral types or opening new debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` keeps two per-account enumerable sets — `depositTokensOfAccount` and `debtTokensOfAccount` (`contracts/storage/PoolStorage.sol:78-83`) — and enforces a hard cap of `MAX_TOKENS_PER_USER = 30` combined entries via the `onlyIfAdditionWillNotReachMaxTokens` modifier (`contracts/Pool.sol:143-148`), which reverts with `UserReachedMaxTokens`. Entries are added to a *recipient's* set, not the sender's: `DepositToken._transfer` and `DepositToken._mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero (`contracts/DepositToken.sol:486-488`, `518-519`). Because `transfer`, `transferFrom`, and `deposit(amount_, onBehalfOf_)` are public, an unprivileged attacker can push entries into a victim's set without the victim's consent — the same bug class as the VoteEscrowDelegation griefing (unauthorized filling of a bounded per-account list).

### Finding Description
- `deposit(uint256 amount_, address onBehalfOf_)` (`contracts/DepositToken.sol:211-237`) mints msdTOKEN to an arbitrary `onBehalfOf_` with no opt-in; `_mint` adds the token to the recipient's `depositTokensOfAccount` when their balance was zero.
- `transfer(to_, amount_)` / `transferFrom` (`contracts/DepositToken.sol:348-376`) reach `_transfer`, which calls `pool.addToDepositTokensOfAccount(recipient_)` for a first-time recipient.
- There is no deduplication problem (the set prevents same-token duplicates), but there is no per-token minimum amount — a 1-wei dust transfer or dust deposit permanently occupies one slot until the victim fully zeroes that balance.
- Once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`, every subsequent action that would add a *new* token reverts: deposits into collateral types the victim doesn't already hold (`deposit` → `_mint` → `addToDepositTokensOfAccount`), minting synthetic assets not already held (`DebtToken.issue` → `addToDebtTokensOfAccount`), receiving transfers of new msdTOKENs, and being the recipient of liquidation `seize` proceeds of a new token type.
- Withdrawals, repayments, transfers of already-held tokens, and liquidation of the victim still work — the attack blocks expansion of the position, not exit.

### Impact Explanation
Liveness/griefing: the victim is prevented from adding new collateral types to their position and from minting new synths. The dangerous scenario mirrors the original report — a victim with an open debt position approaching the liquidation threshold cannot deposit a *new* collateral type to restore health and is forced into liquidation. Funds already deposited are not frozen (existing-token deposits, withdraw, and repay still function), so this is a partial denial of service with an indirect path to forcing liquidation, not direct theft.

### Likelihood Explanation
Feasibility is bounded by pool configuration: each distinct whitelisted `DepositToken` can occupy at most one slot, and debt tokens cannot be pushed to a victim (debt is issued to the minter). An attacker therefore needs the pool to list roughly 30 deposit tokens (minus the victim's existing slots) to fully saturate the cap. On pools with few collaterals the attack only consumes the victim's remaining slack — still harmful (e.g., a victim holding 2 tokens in a 10-collateral pool can be pushed to 10+ slots, reducing headroom) but not a complete lockout. Cost per slot is gas plus a dust amount of the underlying, recoverable in part since the attacker retains the deposit balance they deposited on the victim's behalf only if they `transfer` dust instead of `deposit`. Caveat: I could not enumerate the per-deployment collateral lists from the indexed artifacts, so the worst-case full saturation depends on the deployed pool having near-30 registered deposit tokens.

### Recommendation
- Enforce a minimum amount for adding a token to a per-account set (e.g., only call `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the resulting balance exceeds a dust threshold), or
- Only add tokens on actions initiated by the account itself (deposit to self, self-mint), not on inbound transfers or `onBehalfOf_` deposits, or
- Remove the `MAX_TOKENS_PER_USER` cap / replace the enumerable per-account tracking with an off-chain enumerable mechanism, since the cap exists only for `debtPositionOf` gas bounding.

### Proof of Concept
Hardhat (local deployment harness):

```ts
// Assume pool has N registered DepositTokens: dt[0..N-1]
// Victim currently has 0 tokens; MAX_TOKENS_PER_USER = 30
for (let i = 0; i < N && i < 30; i++) {
  const underlying = await dt[i].underlying();
  // path A: dust deposit on behalf of victim
  await underlying.connect(attacker).approve(dt[i].address, 1);
  await dt[i].connect(attacker).deposit(1, victim.address);
  // or path B: attacker deposits to self once, then dust-transfers
  // await dt[i].connect(attacker).transfer(victim.address, 1);
}

// victim's list is now saturated
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(Math.min(N, 30));

// victim can no longer deposit into a collateral they don't already hold
await expect(
  dt[newIdx].connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// nor mint a synth they don't already owe
await expect(
  pool.connect(victim).mint(newSynth.address, amount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Key assertions: each `transfer`/`deposit` of 1 wei flips the victim's zero-balance check in `_transfer`/`_mint` and inserts into `depositTokensOfAccount`; at the cap, `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`) reverts every subsequent new-token deposit/mint. Whether all 30 slots are reachable depends on the count of registered deposit tokens in the target pool, which should be confirmed against the target chain's deployment before reporting severity.
