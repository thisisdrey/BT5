Based on my investigation, I found a genuine analog in `internal/git/localrepo/tree.go`'s `recurse` function, which is used by `TreeEntry.Delete` (called when Gitaly builds/modifies commit trees, e.g. for `UserDeleteBranch`-related, `TreeEntry.Add`/`Delete` operations reachable from user-driven RPCs building custom trees).

### Title
Infinite loop in `TreeEntry.recurse` when a path component is not found ([File: internal/git/localrepo/tree.go])

### Summary
`recurse` walks tree entries by cutting the path into `firstComponent`/`secondComponent` at the top of an unconditional `for {}` loop, but if `firstComponent` does not match any entry in `currentTree.Entries`, the loop body falls through to the bottom where it only checks `if secondComponent == ""`. If `secondComponent` is not empty (i.e., there are more path segments left to resolve, and none matched), the loop repeats and re-cuts the *same, unmodified* `secondComponent` value, producing the exact same `firstComponent` again — an infinite loop, mirroring the ARK bug class where `prev` is never advanced to `next`.

### Finding Description [1](#0-0) 

In `recurse`, the loop cuts `secondComponent` into `firstComponent`/`secondComponent` at the top of each iteration [2](#0-1) . It then scans `currentTree.Entries` for `firstComponent`; if found and it's the terminal component, `entryFn` is invoked and the function returns [3](#0-2) ; if found but not terminal, `currentTree`/`parentDirs` advance and the loop continues (correctly, akin to `prev = next`) [4](#0-3) . However, when no entry matches `firstComponent` at all, none of the "advance" branches execute — `currentTree`, `parentDirs`, and the yet-to-be-consumed `secondComponent` remain byte-for-byte identical to the prior iteration. The bottom-of-loop check `if secondComponent == "" { return ErrEntryNotFound }` only terminates the loop for the case where the failing component was the *last* one; if the unmatched component is not the final path segment (`secondComponent` still non-empty), the loop falls through and restarts, re-deriving the identical `firstComponent`/`secondComponent` pair forever — exactly the "state pointer never advances" defect described in the report.

### Impact Explanation
`recurse` backs `TreeEntry.Delete` [5](#0-4) , which is used when Gitaly programmatically builds/edits a Git tree from user-supplied paths (e.g. multi-file/batch commit or web-IDE-style tree editing RPCs that construct commits by adding/removing entries by path). An unprivileged caller who supplies a path where an intermediate directory component does not exist in the tree (while deeper components remain) can drive the server into this loop, hanging the goroutine servicing that RPC indefinitely — a CPU/goroutine exhaustion DoS of the Gitaly process handling tree-modification RPCs.

### Likelihood Explanation
Reaching this requires only a crafted path argument to a tree-modification RPC with a non-existent intermediate directory segment and no request-level cancellation kicking in before CPU pegs; the trigger condition (mismatched non-terminal path component) is easy for any caller controlling the delete/path parameter to construct, and no special privileges or race conditions are needed.

### Recommendation
Add a proper "not found" exit at the point where the inner `for i, entry := range currentTree.Entries` loop completes without finding a match for `firstComponent`, rather than relying solely on the `secondComponent == ""` check at the bottom of the outer loop, so unmatched intermediate components immediately return `ErrEntryNotFound` instead of re-looping on unchanged state.

### Proof of Concept
Conceptually: call the code path exercising `TreeEntry.Delete("a/b/c")` on a tree that has no entry named `a` (or `a` exists but `b` doesn't) while a further path segment remains — the inner scan finds no match, `secondComponent` (`"b/c"` or `"c"`) is non-empty, so the outer `for {}` loop reiterates with identical `currentTree`/`secondComponent`, spinning forever. A focused unit test constructing a `TreeEntry` tree and calling `Delete` with such a path would reproduce a permanently blocked goroutine (test timeout / hang), matching the ARK Cairo PoC pattern of an operation that can never reach termination once removal/lookup fails to advance the traversal pointer.

func (t *TreeEntry) recurse(
	path string,
	entryFn func(currentTree, entry *TreeEntry, i int) error,
	treeFn func(entry *TreeEntry) error,
) error {
	var firstComponent string
	var parentDirs string
	secondComponent := path

	currentTree := t
	for {
		// Loop through each layer of the tree based on the directory
		// structure specified by path.
		// firstComponent is the current directory name, and secondComponent is the rest
		// of the sub directories we have yet to walk down into.
		firstComponent, secondComponent, _ = strings.Cut(secondComponent, "/")

		// Look through the current tree's entries.
		for i, entry := range currentTree.Entries {
			if firstComponent != entry.Path {
				continue
			}

			if filepath.Join(parentDirs, entry.Path) == path {
				currentTree.OID = ""

				// Once we find the entry in question, apply the
				// function to modify the current tree and/or
				// entry.
				return entryFn(currentTree, entry, i)
			}

			if err := treeFn(currentTree); err != nil {
				return err
			}
			currentTree = entry
			parentDirs = filepath.Join(parentDirs, entry.Path)
		}

		if secondComponent == "" {
			return ErrEntryNotFound
		}
	}
}

func (t *TreeEntry) Delete(
	path string,
) error {
	path, err := validateFileCreationPath(path)
	if err != nil {
		return err
	}

	entriesRemaining := 0

	if err := t.recurse(
		path,
		func(currentTree, entry *TreeEntry, i int) error {
			currentTree.Entries = append(
				currentTree.Entries[:i],
				currentTree.Entries[i+1:]...)

			entriesRemaining = len(currentTree.Entries)

			return nil
		},
		func(entry *TreeEntry) error {
			entry.OID = ""
			return nil
		},
	); err != nil {
		return err
	}
