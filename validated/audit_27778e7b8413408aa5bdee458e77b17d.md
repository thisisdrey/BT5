### Title
Stale StackerDB slot data/version not re-validated against updated `max-writes`/signer config, allowing pre-reconfig chunk versions to remain served as canonical - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The audited SoftClay bug is about a threshold/config value being changed after a user already qualified under the old threshold, with no mechanism to re-evaluate already-stored state against the new rule. The direct analog in this repo's in-scope StackerDB code is `max_writes`/signer config being changed via `reconfigure_stackerdb()` and `eval_config()`, while previously-written slot versions and slot metadata that were valid under the *old* config are never re-checked or reset against the *new* config unless the specific slot's signer principal changes at that position.

### Finding Description
`StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` (lines 398-438) enforces `slot_desc.slot_version > self.config.max_writes` at write time using whatever `StackerDBConfig` is currently loaded (`self.config`, derived from `eval_config` in `stackslib/src/net/stackerdb/config.rs`). This is the only enforcement point for the write-count ceiling. [1](#0-0) 

When the StackerDB's control contract is updated to lower `max-writes` or otherwise tighten config, `StackerDBTx::reconfigure_stackerdb` is the mechanism that updates persisted slot state - but it only resets a slot's stored `version`/`data`/`signature` when the *signer principal* recomputed for that slot_id differs from the previously recorded signer. If the signer at a given slot_id is unchanged across the reconfiguration, the branch `if existing_validation.signer == *principal { continue; }` is taken and the slot's existing `version` (which may already exceed the new, lower `max_writes`) is left untouched. [2](#0-1) 

Because `get_slot_metadata`/`get_latest_chunk` continue to serve whatever version is currently stored regardless of whether it satisfies the *current* config's `max_writes`, and `make_stacker_db_getchunk_response` / `make_StackerDBChunksInv_or_Nack` serve inventories and chunks straight from persisted state without re-checking them against the live `StackerDBConfig`, a slot that was written to version 50 under an old `max_writes: 100` config continues to be served and gossiped as version 50 even after the control contract is updated to `max_writes: 10`. [3](#0-2) [4](#0-3) 

This exactly mirrors the SoftClay bug class: a value ("softClay level" / "slot version") that was valid under an old threshold is never re-evaluated when the threshold configuration changes, and the codebase has "no methods to update all fields as required" for this case - here, `reconfigure_stackerdb` only resets slots whose owning signer changed, not slots whose write-count now silently exceeds the new cap.

### Impact Explanation
This does not itself allow an attacker to forge new writes above the new cap (new writes are still checked against the live `max_writes`), but it means already-accepted state that violates the current config is retained and propagated as canonical to peers via `StackerDBChunkInv`/`StackerDBChunk` responses and `StackerDBSync`. Peers that reconfigure and expect any slot's write budget to be capped at the new `max_writes` will instead see and store data written at higher versions from before the reconfiguration, i.e., non-canonical state (with respect to the current, live control-contract config) is served/propagated as canonical. This fits the "High - serving non-canonical state as canonical" impact bucket.

### Likelihood Explanation
Likelihood is moderate: it requires a StackerDB control contract to actually reduce `max-writes` (or otherwise tighten config) while an unchanged signer already has a high slot version stored - a legitimate, foreseeable operational scenario (e.g., signer-set/reward-cycle rotation config updates), not an attacker-crafted edge case. No attacker action beyond normal chunk writes prior to the reconfiguration is required.

### Recommendation
When `reconfigure_stackerdb` runs (or generally whenever `StackerDBConfig` for a contract changes), re-validate every slot's persisted `version` against the new `max_writes` (and any other config-derived limits) even when the owning signer is unchanged, and reset/clip slot state that no longer satisfies the current config, rather than only resetting on signer-principal change.

### Proof of Concept
1. Deploy a StackerDB control contract with `max-writes: u100`, and one signer principal `P` owning slot 0.
2. `P` writes to slot 0 up to `slot_version = 50` (allowed, since `50 <= 100` per `try_replace_chunk` check at `stackslib/src/net/stackerdb/db.rs:430`).
3. Update the control contract to `max-writes: u10` (config is re-evaluated by `eval_config` in `stackslib/src/net/stackerdb/config.rs`), and trigger `reconfigure_stackerdb` with the same signer set (slot 0 still owned by `P`).
4. Because `existing_validation.signer == *principal` at `stackslib/src/net/stackerdb/db.rs:323`, the slot is skipped (`continue`) and its stored `version = 50` is left in place, despite `50 > 10` under the new config.
5. Any peer querying `StackerDBGetChunkInv`/`StackerDBGetChunk` for slot 0 still receives `slot_version = 50` via `make_StackerDBChunksInv_or_Nack` / `make_stacker_db_getchunk_response`, serving state that violates the currently active `max_writes` config as if it were canonical.
