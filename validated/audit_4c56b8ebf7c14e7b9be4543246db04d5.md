### Title
User-controlled `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` can be set to the zero pubkey, permanently locking the migrated account and all its positions - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The account-authority-callable instructions `transfer_to_new_account` and `transfer_to_new_account_pda` accept a `new_authority` account that is explicitly documented as "completely unchecked," with no validation that it is not `Pubkey::default()`. This is the same bug class as the report: an address that grants control over a resource (here, an account's `authority`) can be set to the zero address, which has no corresponding private key, resulting in loss of control.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` take `new_authority` as an `UncheckedAccount` with the comment "WARN: New authority is completely unchecked": [1](#0-0) 

`transfer_to_new_account` copies the caller-supplied `new_authority` directly into the freshly-initialized account via `initialize_migrated_account`, and moves the old account's `lending_account` (all balances/positions) into the new account: [2](#0-1) [3](#0-2) 

The old account is then disabled and its balances zeroed, marking the migration complete and irreversible (`migrated_to` prevents any further migration): [4](#0-3) [5](#0-4) 

There is no `require(new_authority != Pubkey::default())`-style check anywhere in the on-chain instruction handler or its `Accounts` validation. All subsequent authorization for deposit/withdraw/borrow/repay/close/etc. on the new account relies on `is_signer_authorized`, which checks `marginfi_account.authority == signer`: [6](#0-5) 

Since `Pubkey::default()` (the all-zero pubkey) has no known private key, no signer can ever satisfy this check for the migrated account. Freezing does not help either — freeze only grants the group admin operational access *while frozen*, and freezing is a separate admin action that isn't automatic; it does not restore normal control to a legitimate user, and there is no protocol mechanism to reassign a zeroed authority.

Notably, an off-chain CLI helper (`p0-cli`) does defensively reject a zero `new_authority`, but this is a client-side check only, not an on-chain guarantee, and does not protect calls made via any other client, SDK, or direct instruction construction: [7](#0-6) 

The equivalent PDA-variant instruction has the same unchecked `new_authority` field and the same unrestricted flow: [8](#0-7) 

### Impact Explanation
If a user (the account authority itself) — or a UI/integration bug, malicious front-end, or user error — sends `new_authority = Pubkey::default()` to `transfer_to_new_account`/`transfer_to_new_account_pda`, all of that account's lending/borrowing positions and rent-exempt SOL become permanently inaccessible. No one — not the original user, not any liquidator (the account may be healthy and not liquidatable), not the group admin — can ever sign as the zero pubkey to withdraw, repay, or close the new account. This is a genuine, unprivileged-user-reachable, permanent loss/lock of user funds, consistent with the accepted "permanent lock/freeze" impact class in the validation rules.

### Likelihood Explanation
The instruction is directly and freely callable by any account authority with no special privilege needed; the vulnerable parameter (`new_authority`) is fully attacker/self-controlled and unchecked on-chain. The only reason this hasn't necessarily been exploited widely is that the primary CLI defends against it client-side, but that provides no protection against other integrations, custom transactions, or accidental zero-value construction (e.g., an uninitialized/default `Pubkey` in client code).

### Recommendation
Add an explicit on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` (and their `Accounts` structs) rejecting `new_authority == Pubkey::default()`, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or a new dedicated error
);
```
placed before `initialize_migrated_account` is called, mirroring the pattern already used defensively in `p0-cli`.

### Proof of Concept
1. User owns `MarginfiAccount` A with authority = `authority_kp` and has active deposit/borrow balances.
2. User (or a buggy client) submits `transfer_to_new_account` with:
   - `old_marginfi_account = A`
   - `authority = authority_kp` (signer)
   - `new_marginfi_account = B` (new keypair)
   - `new_authority = Pubkey::default()` (11111111111111111111111111111111)
3. Instruction succeeds: `initialize_migrated_account` sets `B.authority = Pubkey::default()` and copies `A`'s `lending_account` (balances) into `B`; `A` is disabled and its `migrated_to` set to `B`, making the migration final.
4. Any subsequent attempt to deposit/withdraw/borrow/repay/close on `B` fails `is_signer_authorized` because no signer can ever equal `Pubkey::default()`. The funds in `B` are permanently locked.

pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}
