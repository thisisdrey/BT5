### Title
Out-of-bounds read while parsing attacker-supplied ZIP central directory entries in ijar — (`third_party/ijar/zip.cc`)

### Summary
`ijar`, the tool Bazel uses to generate interface jars from any `.jar` used as a Java compile-time dependency (including jars fetched by `http_jar`/`http_archive`/`java_import`), parses the ZIP central directory of an untrusted, attacker-supplied jar via `InputZipFile::ProcessCentralDirEntry`. Unlike its sibling `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before reading variable-length fields, `ProcessCentralDirEntry` never validates that `file_name_length`, `extra_field_length`, or the extra-field walk stay within the memory-mapped file bounds before dereferencing pointers derived from them.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` is careful to bound-check reads with `EnsureRemaining()`: [1](#0-0) 

By contrast, `ProcessCentralDirEntry`, which is invoked for every entry while scanning the central directory (`InputZipFile::ProcessNext` and `CalculateOutputLength`), reads attacker-controlled 16-bit length fields and walks the extra-field chain purely by pointer arithmetic, with no equivalent bounds check against the mapped file's end: [2](#0-1) 

The only defensive comment in the code, "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe," is not actually enforced anywhere in this function — there is no check that `p`, `extra_p`, or `extra_p + data_size` remain inside `[bytes, bytes + in_length)`. A crafted `file_name_length`/`extra_field_length`/nested extra-field `data_size` can push the cursor arbitrarily far past the end of the `MappedInputFile` mapping, causing `get_u2le`/`get_u4le`/`get_u8le`/`memcpy` to read out-of-bounds memory beyond the mapped region.

This is invoked from `InputZipFile::ProcessNext` (per-entry loop) and `InputZipFile::CalculateOutputLength` (pre-scan loop): [3](#0-2) [4](#0-3) 

The Bazel-native singlejar tool, which shares the same bug class of "packed ZIP header" parsing, was explicitly patched with a bounds-checked `ExtraField::find` (checking `start + sizeof < end` and `start + size <= end` before dereferencing) — see the regression test `CreateZipWithMalformedExtraField` added specifically to exercise a malformed, oversized extra-field payload: [5](#0-4) [6](#0-5) 

`ijar`'s central-directory parser has no analogous containment check.

### Impact Explanation
A jar file is an attacker-controlled artifact whenever it originates from an external dependency (e.g., `http_jar`, `http_archive` unpacking a `.jar`, or a Maven/registry-resolved artifact used by `java_import`). Even though `sha256`/`integrity` pins the byte content of the file, that hash only guarantees the bytes are unmodified in transit — it does nothing to prevent the file's internal ZIP structure from being deliberately malformed by the publisher. Because `ijar` runs as a build action over every jar used for Java compilation, an out-of-bounds read here can crash the Bazel build action (denial of service is out of scope per the analog's exclusions) or, more relevantly, read adjacent process memory that ends up influencing computed sizes/offsets used later in `zip.cc`, which is the same "OOB read via crafted archive" bug class as the reported V8 CVE.

### Likelihood Explanation
Any project depending on an externally supplied `.jar` (common in Java rules) exercises this code path automatically at build time with no user interaction beyond a normal `bazel build`/`bazel fetch`. The attacker only needs to control the bytes of one dependency jar that still satisfies its declared checksum.

### Recommendation
Add explicit bounds validation in `InputZipFile::ProcessCentralDirEntry` (mirroring `EnsureRemaining()` used in `ProcessLocalFileEntry`) before reading `file_name_length`, `extra_field_length`, and before/while iterating the extra-field chain (`header_id`, `data_size`), ensuring `extra_p + 4 <= p` and `extra_p + data_size <= p` (and that `p` itself never exceeds `bytes + in_length`) prior to dereferencing.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to `test_strip_prefix_errors`/`CreateZipWithMalformedExtraField` should:
1. Construct a minimal valid ZIP with one central directory entry.
2. Set that entry's `extra_field_length` (and/or a nested extra-field `data_size`) to a large value (e.g., `0xFFFF`) that exceeds the actual remaining bytes in the file/mapping.
3. Run `ijar` (or trigger a `java_import`/Java compile action that invokes it) over this crafted jar.
4. Observe a crash (SIGSEGV/ASan heap-buffer-overflow) or read of out-of-bounds memory in `ProcessCentralDirEntry`, analogous to the existing `CreateZipWithMalformedExtraField` regression test that was added for singlejar's `zip_headers.h`.

  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
