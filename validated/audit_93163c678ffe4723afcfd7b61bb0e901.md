### Title
Two-phase check-then-lock in `AccountLocks::try_lock_transaction_batch` fails to serialize intra-batch write conflicts - (File: accounts-db/src/account_locks.rs)

### Summary
`try_lock_transaction_batch` validates every transaction's account keys against the *pre-batch* lock state in a first `for_each` pass, and only applies the actual write/read locks in a second, separate `.map` pass over `lock_accounts`. Because the check pass never observes locks that will be taken by earlier elements of the *same* batch (those locks don't exist yet when the check runs), two transactions in the same batch that write the same `Pubkey` can both be marked `Ok(())` and both get write-locked.

### Finding Description
The function is implemented as two fully separate passes over the batch: [1](#0-0) 

Phase 1 (`validated_batch_keys.iter_mut().for_each`) calls `can_lock_accounts`, which only reads `self.write_locks` / `self.readonly_locks` — the shared `AccountLocks` state — and does not mutate it: [2](#0-1) 

Phase 2 (`.into_iter().map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))`) then unconditionally locks every key that was marked `Ok` in phase 1, with no re-validation: [3](#0-2) 

For a batch `[A, B]` where both A and B write the same `Pubkey` `P`:
- Phase 1 checks A against `self` (P not yet locked by anyone in this batch) → `can_write_lock(P)` is `true` → `Ok(())`.
- Phase 1 checks B against `self` — still unmodified, because phase 1 never calls `lock_accounts` — so `can_write_lock(P)` is *still* `true` → `Ok(())`.
- Phase 2 then calls `lock_accounts` for A (increments `write_locks[P]` to 1) and then for B (increments `write_locks[P]` to 2), with no re-check of `can_write_lock` in `lock_accounts` itself.

Both A and B end up marked `Ok(())` and both hold a write lock on `P` simultaneously. The design comment says the function locks "all transactions in a batch which don't conflict with existing locks," but the intra-batch check never accounts for locks about to be taken by other elements of the same call, so same-batch write-write (and write-read) conflicts are not detected at all — only conflicts against locks held from *previously completed, separate* calls to this function are caught.

### Impact Explanation
If a caller ever passes multiple transactions from the same "batch" argument that write the same account, both will be granted a write lock concurrently. If that guarantee is then relied upon elsewhere (e.g., scheduling/PoH assuming account locks give mutual exclusion for concurrently-scheduled transactions), it could let racy/non-deterministic execution slip through, producing recorded results that cannot be reproduced by replay — matching the "invalid block / non-deterministic recorded entry" category (LOCK_CORRECTNESS) described in the question.

However, I could not verify, within available context, that the actual call site (`Accounts`/banking-stage scheduler) ever invokes `try_lock_transaction_batch` with multiple transactions from a *single* untrusted packet batch that write the same account without an intervening per-transaction dedup/serialization step (e.g., `has_duplicates`/`validate_account_locks` operates within one transaction's own keys, not across transactions in a batch). The `accounts.rs` caller code and the scheduler code that constructs `validated_batch_keys` were not fully inspected in the time available, so whether this two-pass design is exploitable end-to-end by an unstaked network attacker (as opposed to being an internal invariant bug reachable only through validator-internal scheduling code, which is out of scope per the "requires validator/leader control" exclusion) is uncertain.

### Likelihood Explanation
The check-then-lock split is a straightforward, always-reachable logic gap in the function itself — no attacker interaction is needed to demonstrate the two-phase bug in isolation (it can be shown with a pure unit test on `AccountLocks`). What remains unverified is whether the transaction-batch scheduler that feeds this function is ever fed multiple write-conflicting transactions in the same call from attacker-controlled packet data, or whether transactions are always locked one-at-a-time (batch of size 1) or pre-filtered/deduped by scheduler logic before reaching this API, which would make the two-pass gap unreachable in practice via untrusted input.

### Recommendation
Merge the check and lock steps into a single pass per transaction (check `can_lock_accounts`, and if `Ok`, immediately call `lock_accounts` before moving to the next transaction in the batch), so that each subsequent transaction's check reflects locks taken by earlier transactions in the same batch.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (add to #[cfg(test)] mod tests)
#[test]
fn test_try_lock_transaction_batch_intra_batch_write_conflict() {
    let key = Pubkey::new_unique();
    let mut locks = AccountLocks::default();

    // Two transactions in the SAME batch call, both writing `key`.
    let tx_a_keys = vec![(&key, true)];
    let tx_b_keys = vec![(&key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx_a_keys.into_iter()),
        Ok(tx_b_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // Expected (correct) behavior: exactly one of A/B succeeds, the other
    // gets AccountInUse, and the lock count for `key` should be 1.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(ok_count, 1, "both transactions were allowed to write-lock the same account in one batch");
    assert!(locks.is_locked_write(&key));
}
```
Running this test against the current implementation fails: both results come back `Ok(())`, demonstrating that `try_lock_transaction_batch`'s two-phase design does not serialize intra-batch write conflicts.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
