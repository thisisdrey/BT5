Audit Report

## Title
Relayer reward is paid and `PendingOrder` removed on Snowbridge outbound delivery receipt regardless of `receipt.success` value - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::<T>::process_delivery_receipt` decodes a verified `DeliveryReceipt` (which carries a `success: bool` field derived from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event) but never inspects `receipt.success` before unconditionally paying the relayer reward via `T::RewardPayment::register_reward` and removing the `PendingOrder` from storage. [1](#0-0) [2](#0-1) 

## Finding Description
`process_delivery_receipt` verifies the gateway address, resolves the `reward_account`, fetches the `PendingOrder` for `receipt.nonce`, and then — gated only on `order.fee > 0`, not on `receipt.success` — calls `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` and removes the order from `PendingOrders`:

```rust
let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

if order.fee > 0 {
    // Pay relayer reward
    T::RewardPayment::register_reward(
        &reward_account,
        T::DefaultRewardKind::get(),
        order.fee,
    );
}

<PendingOrders<T>>::remove(nonce);
``` [3](#0-2) 

The `DeliveryReceipt` struct is constructed directly from the Ethereum `InboundMessageDispatched` event, which explicitly emits a `success: bool` field distinguishing successful from failed/reverted execution on the Ethereum gateway: [2](#0-1)  The public extrinsic `submit_delivery_receipt` verifies the Merkle/event proof via `T::Verifier::verify`, decodes the `DeliveryReceipt` from the log, and forwards it directly to `process_delivery_receipt` without any additional gating on `success`: [4](#0-3)  The pallet-level docs describe the intended flow as "verify the message... fetch the pending order... pay reward... remove the order," with no mention of checking a success flag, confirming this omission is not an intentional design choice reflected elsewhere in the code: [5](#0-4) 

Because the proof/verification path (`T::Verifier::verify`) only attests that the event log was included on Ethereum — not that the underlying message execution succeeded — a reverted/failed `InboundMessageDispatched(success=false)` event is just as provable as a successful one. The pallet's existing guards (`InvalidGateway`, `InvalidPendingNonce`) check gateway identity and nonce existence but do not check the success flag, so they are insufficient to prevent reward payout for failed deliveries.

## Impact Explanation
This is a duplicate/incorrect settlement of bridge relayer rewards: `order.fee` is unconditionally transferred to `reward_account` via `register_reward`, and the `PendingOrder` entry for that `nonce` is permanently removed from `PendingOrders`, regardless of whether the Ethereum-side message execution actually succeeded. This matches the "duplicate settlement or payout" and "public underpriced work" impact categories in the Polkadot SDK Impact Gate — a relayer receives an unbacked reward payout not tied to actual successful message delivery, and the corresponding `PendingOrder` state is irrecoverably cleared (losing the ability to reprocess/retry a failed message), i.e., the exact corrupted value is the reward payout amount `order.fee` credited to `reward_account` and the removed `PendingOrder` entry keyed by `nonce`.

## Likelihood Explanation
Any unprivileged, signed account can call the public extrinsic `submit_delivery_receipt` with a valid inclusion proof for an `InboundMessageDispatched` event that has `success = false` (a normal outcome of a reverted/failed gateway call on Ethereum, outside the relayer's control but well within their ability to observe and submit). No malicious validator, governance action, or compromised key is required — an ordinary relayer submitting a legitimately failed delivery's receipt triggers the bug deterministically and repeatably for every failed nonce.

## Recommendation
Gate the reward payment and order removal on `receipt.success`. For example, only pay the reward and remove the order when `receipt.success` is `true`; for `false`, emit a distinct event (e.g., `MessageDeliveryFailed`) and decide separately whether/how to retry, penalize, or otherwise handle the failed delivery without crediting a reward:
```rust
ensure!(receipt.success, Error::<T>::DeliveryFailed);
```

## Proof of Concept
1. A message with `fee > 0` is queued via `do_process_message`, creating `PendingOrder { nonce, fee, .. }` in `PendingOrders`. [6](#0-5) 
2. On Ethereum, execution of the message reverts/fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid Merkle/inclusion proof for this event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (it only verifies inclusion, not execution outcome); `DeliveryReceipt::try_from` decodes `success: false` into the `receipt`. [7](#0-6) 
5. `process_delivery_receipt` is invoked with this `receipt`; since `receipt.success` is never checked, `order.fee > 0` triggers `register_reward` and `PendingOrders::remove(nonce)` runs unconditionally, crediting a full reward for a failed delivery and permanently clearing the order. [8](#0-7)

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
