### Title
Unbounded `sock.read_to_end()` in `run_http_request` allows a malicious StackerDB replica to force unbounded memory allocation in the signer client before any size check runs - ([File: libsigner/src/http.rs])

### Summary
`StackerDBSession::get_latest_chunks()` enforces a chunk-size limit (`SIGNERS_STACKERDB_CHUNK_SIZE` / `STACKERDB_MAX_CHUNK_SIZE`) only *after* the entire HTTP response body has already been buffered in memory by `run_http_request`. Because `run_http_request` calls `sock.read_to_end(&mut buf)` with no cap on the number of bytes read, a malicious or compromised node that a signer queries over RPC can return an arbitrarily large `HTTP/1.1 200 OK` body and force the signer process to allocate memory proportional to whatever the attacker sends, regardless of the configured chunk-size limit.

### Finding Description
The claimed equality — "bytes buffered before the size-check equals the enforced chunk-size limit" — is false. In `libsigner/src/http.rs`: [1](#0-0) 

`sock.read_to_end(&mut buf)` reads until the peer closes the connection (the request always sends `Connection: close`), with no maximum byte count applied during the read. Only after the full buffer is in memory does `decode_http_response`/`decode_http_body` run; for non-chunked bodies, `decode_http_body` simply does `buf.to_vec()` with no size cap at all, and even for chunked bodies the `MAX_MESSAGE_LEN` cap inside `HttpChunkedTransferReader` is applied to a stream that has *already* been fully materialized in `buf` by the prior unbounded read.

Back in `libsigner/src/session.rs`: [2](#0-1) 

`get_latest_chunks()` only checks `body_bytes.len() > limit` after `rpc_request` (which calls `run_http_request`) has already returned the fully-buffered `Vec<u8>`. By the time this check runs, the oversized allocation has already occurred; the `None` result discards the data but not the memory-pressure event that already happened.

The root cause is that `run_http_request` is a generic HTTP client helper used by all `StackerDBSession` RPC calls (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`), and it never validates a `Content-Length` header or imposes any read cap before or during `read_to_end`. No `MAX_MESSAGE_LEN`-style guard is applied prior to the read; `MAX_MESSAGE_LEN` is only used inside chunked-transfer decoding, downstream of the unbounded read.

### Impact Explanation
A stacks-node or StackerDB replica endpoint that a `stacks-signer` process connects to (via `StackerDBSession`) can return a very large HTTP response body (bounded only by attacker patience/bandwidth) and force the connecting signer process to allocate that much memory per request, for every RPC call the signer makes (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk` ack). This is a memory-amplification / unauthenticated DoS vector against the signer client process: repeated queries (which signers perform routinely, e.g., during each `get_latest_chunks` poll of the `.signers` StackerDB) allow repeated/sustained memory exhaustion, potentially crashing the signer.

### Likelihood Explanation
The only precondition is that the signer is configured to query, or is redirected/MITM'd to, a node/RPC endpoint controlled by the attacker, and no RPC secret, peer key, or slot ownership is required to serve a crafted HTTP response — the attacker just needs to be the one answering the signer's outbound GET/POST request. This is a low-cost, remotely-triggerable, and repeatable attack (once per RPC call the signer issues).

### Recommendation
Enforce a maximum-length bound during the read in `run_http_request` — e.g., use a `Read::take(MAX_MESSAGE_LEN)` (or a caller-supplied limit reflecting `SIGNERS_STACKERDB_CHUNK_SIZE`/`STACKERDB_MAX_CHUNK_SIZE` plus header overhead) instead of unconditional `read_to_end`, and additionally validate any `Content-Length` header against that limit before allocating/reading the body, so oversized responses are rejected during the read rather than after full buffering.

### Proof of Concept
```rust
// libsigner/src/session.rs (or http.rs) test module
use std::io::Write;
use std::net::TcpListener;
use std::thread;

#[test]
fn oversized_body_is_fully_buffered_before_limit_check() {
    let listener = TcpListener::bind("127.0.0.1:0").unwrap();
    let addr = listener.local_addr().unwrap();

    thread::spawn(move || {
        if let Ok((mut stream, _)) = listener.accept() {
            let body = vec![b'A'; 50 * 1024 * 1024]; // 50MB
            let header = format!(
                "HTTP/1.1 200 OK\r\nContent-Length: {}\r\nConnection: close\r\n\r\n",
                body.len()
            );
            stream.write_all(header.as_bytes()).unwrap();
            stream.write_all(&body).unwrap();
        }
    });

    let contract_id = /* a "signers-..." contract id so `limit = SIGNERS_STACKERDB_CHUNK_SIZE` */;
    let mut session = StackerDBSession::new(&addr.to_string(), contract_id, Duration::from_secs(30));
    session.connect_or_reconnect().unwrap();

    // Instrument or wrap run_http_request to assert buf.len() == 50MB
    // immediately after sock.read_to_end(&mut buf) returns, BEFORE
    // get_latest_chunks' `body_bytes.len() > limit` check runs.
    let result = session.get_latest_chunks(&[0]).unwrap();
    assert_eq!(result, vec![None]); // post-hoc discard — but 50MB was already resident in memory
}
```
The assertion to add inside `run_http_request` (or via a debug hook) is `assert!(buf.len() >= 50 * 1024 * 1024)` right after the `sock.read_to_end(&mut buf)?` call, demonstrating the full oversized body is materialized in memory before `get_latest_chunks`'s `limit` check ever executes.
