The behavior described is intentional design, not a bug. In `BandwidthRequest::make_from_receipt_sizes`, once `total_size` exceeds `values[values.len()-1]` (which equals `params.max_single_grant`), `cur_value_idx` reaches `values.len()` and the loop `break`s [1](#0-0) . This is correct because `max_single_grant` is by construction the maximum bandwidth that can be granted on a single shard-to-shard link in a single height, enforced by the assertion `max_single_grant <= max_shard_bandwidth` [2](#0-1) . Requesting more than `max_single_grant` would be pointless since the scheduler can never grant more than that on one link anyway. The existing unit test `test_make_bandwidth_request_from_receipt_sizes` explicitly documents this as intended behavior for `two_max_size_receipts`, noting "2 * max_size_receipt > max_shard_bandwidth, so it doesn't make sense to request more bandwidth" [3](#0-2) .

Critically, the claim of "permanent" exclusion is incorrect: the bandwidth request is not a one-time computation but is regenerated from the actual current buffer state (via `ReceiptGroupsQueue`/`OutgoingMetadatas`) at every height that the bandwidth scheduler runs [4](#0-3) . As receipts at the front of the outgoing buffer are sent and popped (`update_on_receipt_popped`), `total_size` shrinks, so the next height's `make_from_receipt_sizes` call recomputes `cur_value_idx` from scratch and will cover receipts further back in the buffer as the queue drains [5](#0-4) . There is no persistent index or state that could cause "middle" receipts to be permanently skipped — every receipt eventually reaches the front of the FIFO buffer once the requested (fully max-granted) bandwidth allows earlier receipts to be sent, and each height's request always covers at least up to `max_single_grant` worth of the front of the queue. This is a throughput/liveness characteristic by design (bounded by `max_single_grant` per height per link), not a bookkeeping overflow or fund-freezing vulnerability, and does not meet the bar for concrete permanent freezing of funds.
