### Title
Unbounded per-file `git-check-attr` round trips in `Instance.Stats` cause O(N) synchronous work bound to attacker-controlled tree size - ([File: internal/gitaly/linguist/linguist.go])

### Summary
`Instance.Stats` performs a full language-detection recalculation by iterating every blob returned by `gitpipe.LsTree` and calling `checkAttr.Check(filename)` synchronously for each one, with no batching, concurrency, or cap on the number of files processed per RPC invocation. Because a normal unprivileged user can push a commit with an arbitrarily large number of tracked files, this handler's runtime is linearly bound to attacker-controlled repository content, all within a single gRPC handler execution (reachable via `CommitService.CommitLanguages`).

### Finding Description
`Instance.Stats` (internal/gitaly/linguist/linguist.go:80) creates a `CheckAttrCmd` via `gitattributes.CheckAttr(ctx, inst.repo, commitID.Revision(), linguistAttrs)` [1](#0-0)  and, on a full recalculation, builds an iterator over every blob in the tree via `gitpipe.LsTree(... LsTreeWithRecursive() ...)` [2](#0-1) . For every returned object it constructs a `fileInstance` and calls `checkAttr.Check(filename)` inside the `for objectIt.Next()` loop [3](#0-2) .

`CheckAttrCmd` under the hood is a single long-lived `git check-attr --stdin -z` process, not a per-file subprocess spawn [4](#0-3) . Each call to `Check()` writes one path to the process's stdin, flushes, and then performs a blocking read of that file's `-z`-delimited response before returning, guarded by a mutex [5](#0-4) . This means each file processed by `Stats` requires one full synchronous write+flush+read round trip with the subprocess, executed serially in the loop with no concurrency, batching, or upper bound on file count. There is no limit enforced anywhere in `Stats`, `gitpipe.LsTree`, or `CheckAttrCmd` on the number of paths that can be checked in one call — the loop runs once per entry emitted by `git ls-tree`, whose count is fully controlled by the pushed commit's tree.

`GetCommitLanguages` in `internal/gitaly/service/commit/languages.go` invokes `linguist.New(...).Stats(ctx, commitID)` synchronously as a unary RPC handler, so the entire O(N) sequence executes inside a single gRPC handler invocation, holding a worker/goroutine and associated resources for the duration.

### Impact Explanation
An attacker with only push access to a repository they control (own project or fork) can create a commit with an extremely large number of trivial tracked files (e.g., 10^5+ empty files) in one tree. Triggering language statistics computation (e.g., via GitLab's language-detection background job or by invoking `CommitLanguages` directly if reachable) causes the Gitaly RPC handler to block for time proportional to N, consuming a gRPC worker slot and CPU/goroutine resources for an attacker-scalable duration. On a busy Gitaly node this can degrade or starve concurrent legitimate RPCs, constituting resource exhaustion / DoS of an RPC handler, matching the "Denial of Service" bounty impact class for a single Gitaly node.

### Likelihood Explanation
Preconditions are minimal: any unprivileged GitLab user who can push to a repository they own or a fork can construct a commit with an arbitrarily large flat tree of trivial files at no meaningful cost to themselves (creating many small blobs is cheap). No special role, secret, or non-default configuration is required. The main variable is whether GitLab Rails enforces any file-count or repository-size limit before triggering language detection — this is outside Gitaly and not verified here, so real-world likelihood depends on that external control. Within Gitaly itself, there is no cap, making the RPC handler path fully exploitable if reached.

### Recommendation
Impose an upper bound (or streaming/incremental cap) on the number of files processed per `Instance.Stats` full recalculation, and/or make the per-file `check-attr` round trips concurrent/batched rather than fully serialized. Consider capping recalculation cost based on total tree size or file count, falling back to a partial/best-effort result or explicit error when limits are exceeded, and ensure any background job invoking this RPC applies a timeout independent of N.

func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}

	return attrs, nil
