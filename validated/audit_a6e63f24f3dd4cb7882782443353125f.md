### Title
Unguarded Division by Total Energy Weight Can Throw Uncaught `ArithmeticException` in `RepositoryImpl.calculateGlobalEnergyLimit` - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The Sherlock report describes a division-by-zero in Arcadia's `Tranche.previewWithdraw`, where `totalAssets() + VAS` can evaluate to zero and is used as a divisor without any guard. The closest analog in java-tron is `RepositoryImpl.calculateGlobalEnergyLimit`, which divides an account's energy weight by the network-wide `totalEnergyWeight` to compute a contract's usable energy from frozen TRX, using only a Java `assert` statement (a no-op in production JVMs) as protection against a zero divisor.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes: [1](#0-0) 

The only defense against `totalEnergyWeight` being zero is `assert totalEnergyWeight > 0;` at line 1001. Java assertions are disabled by default (`-ea` is not typically passed to production JVMs), so this statement is a runtime no-op, and execution falls straight through to:
- The hardened path: `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(totalEnergyWeight))` — throws `ArithmeticException: BigInteger divide by zero` if `totalEnergyWeight == 0`.
- The legacy path: `(double) totalEnergyLimit / totalEnergyWeight` — does not throw, but yields `Infinity`/`NaN`, and the subsequent cast to `long` silently produces `Long.MAX_VALUE` or `0`, corrupting the energy-limit calculation.

By contrast, the equivalent method in `EnergyProcessor` (used elsewhere in the resource-accounting stack) contains real, non-assert guards before performing the same division: [2](#0-1) 

`RepositoryImpl.calculateGlobalEnergyLimit` lacks both the `supportUnfreezeDelay()` redirect to a zero-checked V2 path and the explicit `totalEnergyWeight <= 0` early return that `EnergyProcessor` has, leaving only the disabled `assert` as protection.

`calculateGlobalEnergyLimit` is exposed through the `Repository` interface and delegated by `ContractState`, which is the repository object used throughout TVM contract execution: [3](#0-2) 

This means the vulnerable code path is reachable during ordinary TVM contract execution (`TriggerSmartContract`/`CreateSmartContract`), i.e., by any unprivileged account that triggers a smart contract, whenever the resource-accounting logic needs to compute an account's global energy limit from frozen balances.

### Impact Explanation
If `totalEnergyWeight` (the sum of network-wide frozen-balance-for-energy weight) is ever zero while an individual account still has a frozen energy balance ≥ `TRX_PRECISION` (a state achievable at least conceptually on freshly bootstrapped or low-activity/private chains, or transiently due to accounting inconsistencies between per-account frozen balances and the aggregate `totalEnergyWeight` counter maintained separately by freeze/unfreeze/delegate actuators), the hardened calculation path throws an uncaught `ArithmeticException`. Because this computation occurs inside TVM execution/resource accounting invoked for every contract call, an uncaught exception here can propagate up through contract execution and disrupt block processing/validation for the node, i.e., a potential node halt/crash condition — the closest java-tron equivalent to the "transaction fails/reverts unexpectedly due to unguarded division by zero" impact described in the report. In the non-hardened path, silently producing `Infinity`/`Long.MAX_VALUE` for an energy limit could also grant an account effectively unlimited energy relative to its actual stake, corrupting resource accounting.

### Likelihood Explanation
Medium/low-to-medium likelihood on a fully matured mainnet, since `totalEnergyWeight` reaching exactly zero while individual accounts retain non-trivial frozen energy balances requires either a fresh/private network state or a divergence between per-account weight tracking and the separately-maintained global counter. The root cause — an `assert`-only guard around a divisor that is otherwise checked with real conditionals in the parallel `EnergyProcessor` implementation — is a clear code-quality/robustness defect regardless of how difficult it is to trigger `totalEnergyWeight == 0` in practice.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (mirroring `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`), returning `0` when `totalEnergyWeight <= 0` instead of relying on an assertion that is disabled in production builds. Align `RepositoryImpl`'s method with `EnergyProcessor`'s `supportUnfreezeDelay()`/zero-check logic to avoid inconsistent behavior between the two resource-accounting code paths.

### Proof of Concept
1. Deploy/trigger a smart contract on a chain state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., freshly initialized chain/private network before any `FreezeBalance(V2)` for energy has been broadcast, or a state where an account's own `getAllFrozenBalanceForEnergy()` is ≥ `TRX_PRECISION` while the aggregate `totalEnergyWeight` counter is `0` due to accounting timing).
2. Invoke any TVM contract call for that account; the VM resource accounting path calls `ContractState.calculateGlobalEnergyLimit` → `RepositoryImpl.calculateGlobalEnergyLimit`.
3. With `VMConfig.allowHardenResourceCalculation()` enabled, the call `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` throws `ArithmeticException`, since the preceding `assert totalEnergyWeight > 0;` is a no-op without `-ea`. [4](#0-3) 

**Uncertainty note:** I could not fully confirm from the indexed code exactly which byte code / VMActuator call site first invokes `calculateGlobalEnergyLimit` during a standard trigger-contract flow, nor verify a concrete transaction sequence that drives `totalEnergyWeight` to `0` while a participating account still has nonzero frozen energy balance (this would require deeper tracing of `DynamicPropertiesStore` weight bookkeeping across all freeze/unfreeze/delegate actuators, which is beyond what the current search coverage could establish with certainty). If a Devin session with full repo/test access is desired to trace this precisely, that would need to be run separately since it exceeds ask-only read verification.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
