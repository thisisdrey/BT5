### Title
Cross-transaction interference via guessable `TransactionID` and unscoped shared internal-socket token - (File: internal/git/gitcmd/hooks_payload.go)

### Summary
`HooksPayload.TransactionID` (`internal/git/gitcmd/hooks_payload.go:97-99`) is a small, sequential, per-process integer assigned by `storagemgr.TransactionRegistry.register` (`internal/gitaly/storage/storagemgr/transaction_registry.go:26-33`), and it is looked up with a bare map access in `TransactionRegistry.Get` (same file, lines 42-51) with no check that the caller is the legitimate owner of that transaction. The only "authentication" gating access to it is `InternalSocketToken`, which is simply the single, static, install-wide Gitaly auth secret (`cfg.Auth.GetToken()`, set in `NewHooksPayload`, `hooks_payload.go:171`) — the same secret every hook invocation on the node receives, not a per-transaction credential.

### Finding Description
`gitaly-hooks` reads `GITALY_HOOKS_PAYLOAD` from its environment and uses `InternalSocketToken` to dial Gitaly's internal socket (`cmd/gitaly-hooks/hooks.go:189-222`, `dialGitaly`). The server-side auth interceptor (`internal/gitaly/server/auth/auth.go:56-81`, `internal/gitaly/server/server.go:165`) only checks that this shared secret is valid — it does not bind the token to a specific transaction, repository, or hook invocation. Consequently, any process that has legitimately received this static token (e.g., an attacker-controlled custom hook script running under `custom_hooks/pre-receive.d/…`) can independently connect to the internal socket and invoke `HookService` RPCs (e.g. `ReferenceTransactionHook`, `PostReceiveHook`) with an arbitrary, self-crafted `GITALY_HOOKS_PAYLOAD` environment string, including a `transaction_id` value it did not receive.

On the server, `hook.GitLabHookManager.ReferenceTransactionHook` (`internal/gitaly/hook/referencetransaction.go:46-51`) and `PostReceiveHook` (`internal/gitaly/hook/postreceive.go:130-170`) call `m.txRegistry.Get(payload.TransactionID)`, which resolves directly through `TransactionRegistry.Get` (`internal/gitaly/storage/storagemgr/transaction_registry.go:42-51`) — a plain `map[storage.TransactionID]storage.Transaction` lookup keyed by a sequential counter (`r.idSequence++` in `register`, line 30). There is no verification that the calling hook's own `TransactionID`, repository, or user session actually corresponds to the transaction being fetched. Once resolved, the handler operates on that `storage.Transaction` object directly — e.g. `tx.RecordInitialReferenceValues`, `tx.UpdateReferences`, `tx.Commit`, `tx.RewriteRepository` — all of which act on another push's in-flight transaction state.

Because `TransactionID` is a small monotonically-increasing integer scoped per Gitaly process (not per-repository, per-user, or randomly generated), and because the internal-socket token possessed by any hook process is a static, non-transaction-scoped secret, an attacker's own custom hook process can enumerate nearby IDs (`N-1`, `N+1`, …) to reach a concurrently running transaction belonging to a different, unrelated push and interact with it through the internal `HookService` RPCs.

### Impact Explanation
This allows a low-privileged user (who can push to any repository they control and thus have a custom hook executed) to interfere with another user's concurrent push transaction on the same Gitaly node: forcing premature `Commit()` of someone else's transaction, injecting forged `RecordInitialReferenceValues`/`UpdateReferences` calls, or reading/holding a handle to another repository's transaction via `tx.OriginalRepository`/`tx.RewriteRepository`. This matches GitLab's "cross-repository object access" / "auth bypass leading to unauthorized action on another user's data" bounty class, since the check that "a caller holding a valid token for its own transaction must not be able to act on another transaction's ID" is absent.

### Likelihood Explanation
Preconditions are modest but real: the attacker needs (1) to control a custom hook script in a repository they can push to (a supported, if operator-enabled, Gitaly feature), (2) the ability to run concurrently with another user's push on the same Gitaly storage node, and (3) to guess a nearby `TransactionID`, which is trivial since IDs are small sequential integers assigned in registration order — an attacker who knows their own assigned ID can simply try adjacent values. Custom hooks being enabled at all, and multiple pushes landing on the same node concurrently, are the main gating factors, but neither requires privileged access or leaked secrets beyond the token the attacker already legitimately possesses.

### Recommendation
Do not expose the in-memory `TransactionRegistry` map for lookup by a bare guessable integer over a connection authenticated only with the shared static Gitaly secret. Bind `TransactionID` resolution to the specific hook invocation that created it (e.g. issue a per-invocation random/unguessable token or nonce embedded in the payload, verified against the transaction on lookup), or otherwise scope/validate that the calling hook's own repository/session matches the transaction before allowing `Get()` to succeed.
