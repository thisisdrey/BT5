### Title
Non-atomic ObjectPool lifecycle allows concurrent Link/Delete race that corrupts member repositories - ([File: internal/gitaly/service/objectpool/delete.go], [File: internal/git/objectpool/link.go])

### Summary
The reported DeFi bug is a class of "check-then-act on shared aggregate state without atomicity", where an admin operation (`updatePool()`) overwrites shared pool accounting without verifying the state hasn't changed underneath it, letting another actor interleave operations against the same shared resource and profit at another user's expense. The Gitaly analog is the `ObjectPoolService` lifecycle: `DeleteObjectPool` unconditionally removes the pool repository with **no check that member repositories are still linked to it** [1](#0-0) , while `Link()` independently reads the alternates state and then writes a new alternates file pointing at the pool with no lock shared with deletion [2](#0-1) . There is no cross-RPC/cross-repository synchronization tying "pool exists and has members" together atomically, so the two operations can interleave, similar to how `updatePool()`'s `poolSize` write can interleave with a redemption.

### Finding Description
`ObjectPoolService.DeleteObjectPool` deletes the pool repository outright and is documented to have **no safety checks**: *"There are no safety checks in place, so if any repository is still using this object pool it will become corrupted."* [1](#0-0)  The handler simply resolves the pool and calls `repoutil.Remove`, without consulting or locking any registry of member repositories [3](#0-2) .

Meanwhile, `LinkRepositoryToObjectPool` (`objectpool.Link`) performs a classic check-then-act sequence: it computes the expected relative alternates path, checks `linkedToRepository()` against the pool's *current* on-disk state, and — if not yet linked — writes a new `objects/info/alternates` file that references the pool's `objects` directory [4](#0-3) . Both `linkedToRepository()` and the actual write only ever read/write the *member* repository's alternates file; they do not take any lock against the *pool* repository, and nothing in the pool-deletion path checks for or blocks in-flight linking operations. `FetchIntoObjectPool` similarly writes/updates pool contents concurrently and independently of member link/unlink state [5](#0-4) .

Because these RPCs are ordinary user/fork-lifecycle operations (fork creation links a new member into a pool via `LinkRepositoryToObjectPool`, fork deletion/pool pruning triggers `DeleteObjectPool`, and pushes to any pool member trigger `FetchIntoObjectPool`), a client that can race `LinkRepositoryToObjectPool` against `DeleteObjectPool` for the same pool (e.g., forking a repository at the same time GitLab decides to prune the now-unreferenced pool, or racing an unlink/relink with a concurrent delete) can end up with:
- A member repository's `objects/info/alternates` referencing a pool directory that gets removed mid-write, or
- A newly linked member being granted a "linked" alternates file for a pool that is deleted immediately after the `linkedToRepository()` check but before/after the alternates file write completes.

This is directly analogous to `updatePool()`: a shared piece of cross-entity state (`poolSize` / the object pool's existence & object set) is mutated by one actor without verifying it is still consistent with the state observed by a concurrent actor performing a dependent operation (redeem / link).

### Impact Explanation
If a member repository is left referencing a deleted (or partially deleted) object pool, subsequent Git operations (`git-fsck`, clone, fetch, `git rev-list`) against that member repository will fail to resolve objects that were deduplicated into the now-missing pool, corrupting the repository from the perspective of any other user of that repository (equivalent to "stealing"/destroying shared value from other legitimate stakeholders of the pool, i.e. every other fork/member sharing the pool). This is a data-integrity/availability (DoS) impact on repositories that are not directly involved in the racing request, matching the report's requirement of harming a party other than the attacker.

### Likelihood Explanation
Exploitation requires timing two independent gRPC calls (`LinkRepositoryToObjectPool` / `FetchIntoObjectPool` vs `DeleteObjectPool`) against the same object pool, which are both reachable through ordinary repository lifecycle actions (fork/import, and pool pruning triggered by GitLab or an admin who controls their own pool member set). No cross-repository lock exists to serialize these, so the race window is real, though it requires precise timing to hit, which is why likelihood should be assessed as Medium rather than High.

### Recommendation
Introduce an atomic guard (e.g., a per-pool reference count, lock, or requiring `DeleteObjectPool` to re-verify zero linked members inside the same lock/transaction used by `Link`) so pool deletion cannot proceed while a link/fetch operation for the same pool is in flight, and so `Link`/`FetchIntoObjectPool` cannot complete against a pool that is concurrently being deleted. This mirrors the report's recommendation of making the "pool" only mutable when consistency with dependent operations (its members) can be guaranteed, or serializing mutation of the pool and its members via a shared lock/transaction boundary.

### Proof of Concept
Not independently reproduced; based on static analysis of the referenced call paths. The claim rests on:
1. `proto/objectpool.proto` documenting `DeleteObjectPool` as having no safety checks for existing members [1](#0-0) .
2. `internal/gitaly/service/objectpool/delete.go` performing unconditional removal [3](#0-2) .
3. `internal/git/objectpool/link.go` performing an unlocked check-then-write against the pool's alternates path [4](#0-3) .

To fully confirm exploitability (exact race window sizes, whether transaction voting in the WAL-based storage manager already serializes these two RPCs at a lower layer), a live/dynamic test against the `ObjectPoolService` gRPC handlers with concurrent `Link`/`Delete` calls would be needed — this is beyond what static code reading can conclusively prove, so this should be treated as a plausible but unverified race rather than a confirmed exploit.

```go
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

	if err := transaction.CommitLockedFile(ctx, txManager, alternatesWriter); err != nil {
		return fmt.Errorf("committing alternates: %w", err)
	}
```

```go
func (s *server) DeleteObjectPool(ctx context.Context, in *gitalypb.DeleteObjectPoolRequest) (*gitalypb.DeleteObjectPoolResponse, error) {
	pool, err := s.poolForRequest(ctx, in)
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			// TODO: we really should return an error in case we're trying to delete an
			// object pool that does not exist.
			return &gitalypb.DeleteObjectPoolResponse{}, nil
		}

		return nil, err
	}

	if err := repoutil.Remove(ctx, s.logger, s.locator, nil, s.repositoryCounter, pool); err != nil {
		return nil, fmt.Errorf("remove: %w", err)
	}
```

```go
func (s *server) FetchIntoObjectPool(ctx context.Context, req *gitalypb.FetchIntoObjectPoolRequest) (*gitalypb.FetchIntoObjectPoolResponse, error) {
	if err := validateFetchIntoObjectPoolRequest(req); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	objectPool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		return nil, structerr.NewInvalidArgument("object pool invalid: %w", err)
	}

	origin := s.localRepoFactory.Build(req.GetOrigin())

	if err := objectPool.FetchFromOrigin(ctx, origin, func(repo *gitalypb.Repository) *localrepo.Repo {
		return s.localRepoFactory.Build(repo)
	}); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}
```
