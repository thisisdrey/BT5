### Title
Repeated `RewriteHistory` invocations force full-repository housekeeping with no minimum interval, enabling repeated resource-intensive optimization and dilution of scheduled maintenance thresholds - (File: internal/grpc/middleware/housekeeping/middleware.go)

### Summary
The Blend `gulp_emissions` bug class is: an unprivileged caller can repeatedly invoke a function that recomputes a time/threshold-based scheduling window, with no minimum interval enforced between calls, allowing the caller to indefinitely dilute/delay/repeat work that should be rate-limited. Gitaly's housekeeping scheduling middleware contains an analogous unthrottled-recompute pattern around `forceHousekeepingRPCs`.

### Finding Description
`Middleware.scheduleHousekeeping` in [1](#0-0)  tracks, per repository, a `writeCount` and a `writeCountAtLastRun` map used to decide when each housekeeping operation (`OpRepackRefs`, `OpRepackObjects`, `OpPruneObjects`, `OpWriteCommitGraph`) should run, based on `RPCInterval` thresholds in `pendingOperations` [2](#0-1) .

`CleanupService.RewriteHistory` is registered in `forceHousekeepingRPCs` [3](#0-2) , so every successful call passes `force=true` into `scheduleHousekeeping`. With `force=true`, `pendingOperations` unconditionally returns *all* operation types regardless of their thresholds, and the middleware immediately resets `writeCountAtLastRun` for every operation type to the current `writeCount` [4](#0-3) , then kicks off a full `OptimizeRepository` (repack refs, repack objects, prune, write-commit-graph) run [5](#0-4) .

There is no minimum wall-clock interval enforced between forced runs — the only guard is the `active` flag, which merely prevents *concurrent* overlap, not repeated *sequential* invocation [6](#0-5) . `RewriteHistory` itself is a lightweight-to-call mutator RPC reachable by any client with write access to the target repository (no maintenance-only ACL) [7](#0-6) , and its handler will proceed as long as a single blob ID or a redaction pattern is supplied — it does not require the request to actually change repository content in a costly way before the force-housekeeping side effect fires [8](#0-7) .

This mirrors the reported bug class: a caller-triggerable operation recomputes and resets a scheduling/threshold state (`writeCountAtLastRun`) with no minimum time gate, letting the caller perpetually reset the "since last run" counters that gate normal automatic housekeeping (repack/prune/commit-graph), and additionally forces a new full optimization pass on the caller's own schedule rather than the intended threshold-based one.

### Impact Explanation
An authenticated user with ordinary write access to a single repository can call `RewriteHistory` back-to-back (each waiting only for the previous forced `OptimizeRepository` run to complete, since `active` only blocks concurrency, not repetition). Each call:
- Forces a complete `OptimizeRepository` pass (repack objects, prune, commit-graph rebuild) regardless of whether any real threshold was crossed, consuming CPU, memory, and disk I/O on the Gitaly node hosting that repository's storage.
- Resets the `writeCountAtLastRun` baseline for all four operation types, so ordinary threshold-based auto-housekeeping triggered by regular mutator/accessor RPCs on the same repository is effectively neutralized/delayed for as long as the attacker keeps calling the forcing RPC.

This is a resource-exhaustion / unfair-scheduling issue on a shared Gitaly storage node — repeated heavy optimizations for one repository can starve I/O/CPU for other repositories on the same node and prevent legitimate, threshold-driven maintenance from ever running as designed, which is directly analogous to the "dilute emissions/delay distribution to other stakers" impact in the report (delay of legitimate work for other users of a shared resource due to an unthrottled reset primitive).

### Likelihood Explanation
Likelihood is moderate: the attacker needs write access to a repository (the same access level typically required for the redaction/BFG-cleanup feature) but no special maintenance/admin privilege, and the call pattern (loop of minimal `RewriteHistory` requests) is trivial to script. The main friction is that each forced run must actually complete (bounded by `active`) before the next call has full effect, and `RewriteHistory` itself runs `git filter-repo` and a mirror fetch which has non-trivial cost, so an attacker is trading their own request cost for triggering server-side optimization cost — but for small/empty repositories this cost is low while the forced full optimize (and denial of normal scheduling) recurs on every call.

### Recommendation
Add a minimum wall-clock interval (not just a write-count-based interval) that must elapse before a `force=true` housekeeping request can trigger another forced run for the same repository, independent of the `active` in-flight guard. Track a `lastForcedRunAt time.Time` per `repoKey` in `activity`, and in `scheduleHousekeeping`, skip resetting `writeCountAtLastRun` / launching a new forced `OptimizeRepository` if the elapsed time since the last forced run is below a configured minimum (analogous to the Blend fix of bounding how often `distribute`/`gulp` can run per pool to once per day).

### Proof of Concept
1. As a client with write access to a target repository, open a `CleanupService.RewriteHistory` stream and send a `RewriteHistoryRequest` with a single throwaway `redactions` pattern, then close the stream — this is accepted by the handler as long as `blobsToRemove` or `redactions` is non-empty [9](#0-8) .
2. Repeat this call in a loop against the same repository, each time waiting only for the previous call to return (bounded by the `active` flag in `scheduleHousekeeping`).
3. Observe (as demonstrated in the middleware's own test, `t.Run("when forceHousekeepingRPCs bypass interval compared to regular mutators", ...)`) that each call increments `optimizeRepositoryInvocations` immediately, bypassing the `RPCInterval` gating that applies to regular mutator RPCs [10](#0-9) .
4. Concurrently send ordinary mutator RPCs (e.g. `WriteRef`) on the same repository and observe that their contribution toward `writeCountAtLastRun`-based auto-housekeeping is perpetually reset by the interleaved forced calls, so scheduled repack/prune/commit-graph maintenance never fires on its intended threshold while the attacker's loop is running.

// pendingOperations returns operations that have exceeded their RPC interval thresholds.
func (m *Middleware) pendingOperations(a *activity, force bool) []config.OperationType {
	var pending []config.OperationType

	for _, op := range allOperations {
		thresholds := m.getThresholds(op)
		lastRun := a.writeCountAtLastRun[op]
		writesSinceLastRun := a.writeCount - lastRun

		if force || writesSinceLastRun > thresholds.RPCInterval {
			pending = append(pending, op)
		}
	}

	return pending
}

// operationsExceedingStatThreshold returns operations whose stat threshold is exceeded.
func (m *Middleware) operationsExceedingStatThreshold(statCount int) []config.OperationType {
	var ops []config.OperationType

	for _, op := range allOperations {
		thresholds := m.getThresholds(op)
		if statCount > thresholds.StatThreshold {
			ops = append(ops, op)
		}
	}

	return ops
}

func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++

	if a.active {
		return
	}

	pendingOps := m.pendingOperations(a, force)
	if len(pendingOps) == 0 {
		return
	}

	m.logger.WithFields(log.Fields{
		"forced":     force,
		"operations": pendingOps,
	}).InfoContext(ctx, "beginning scheduled housekeeping")

	// Mark that these operations are running at the current write count
	for _, op := range pendingOps {
		a.writeCountAtLastRun[op] = a.writeCount
	}
