### Title
Unvalidated offset/length fields from calldata cause uncaught array-index exceptions in precompiled-contract signature/array decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `extractBytesArray` and `extractSigArray` helper methods in `PrecompiledContracts.java` decode variable-length arrays of signatures/byte-strings out of a `DataWord[] words` array that is built directly from a TVM precompiled-contract call's `data` payload. Only the *first* index (`offset`) is bounds-checked against `words.length`; every subsequent index derived from attacker-controlled length/offset fields (`len`, `bytesOffset`) is used to index `words[]` and the raw `data[]` byte array with no further validation. This mirrors the openjpeg `pi.c` bug class: a length/index value taken from untrusted input is trusted to build offsets used for direct memory/array access, producing an out-of-bounds read.

### Finding Description
`extractBytesArray`: [1](#0-0) 

`extractSigArray`: [2](#0-1) 

Both functions:
1. Check `offset > words.length - 1` once, before the loop.
2. Read `len` from `words[offset]` — a value entirely controlled by the calldata of the transaction/contract call that invokes this precompile.
3. Loop `i` from `0` to `len`, computing `words[offset + i + 1]` and, in `extractBytesArray`, a second attacker-controlled index `words[offset + bytesOffset + 1]` (`bytesOffset` itself derived from calldata) — none of these are checked against `words.length` before the array access.
4. `extractBytes(data, ...)` then calls `Arrays.copyOfRange(data, offset, offset + len)` on the raw calldata `data[]` using offsets computed from the same unchecked, attacker-controlled values, which can also run past `data.length`.

Because `len`/`bytesOffset` come straight from `intValueSafe()` on attacker-supplied `DataWord`s, a caller can supply a very large `len` or an out-of-range `bytesOffset` to force `words[...]`/`data[...]` accesses beyond the array bounds. In Java this manifests as an uncaught `ArrayIndexOutOfBoundsException` (the java-tron equivalent of a native OOB read) rather than memory disclosure.

The repository's own test suite documents this same failure mode for the related legacy decoder path that also lacks bound checks and is reachable without any activation gate: [3](#0-2) 
The test comment explicitly states: "this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode." This confirms exceptions from this decoding path are not always caught by the surrounding TVM CALL-to-precompile machinery, i.e., they can propagate further than a normal contract revert.

### Impact Explanation
An `ArrayIndexOutOfBoundsException` raised deep inside precompiled-contract execution that escapes the expected revert/catch path can abort transaction/block execution unexpectedly. Since this code runs during block application (any node validating or replaying the block executes the same TVM call), an uncaught exception on this path risks destabilizing block processing in `Manager`/TVM execution rather than cleanly reverting the single transaction — i.e., node crash/halt on a class of TVM CALL data that any address can trigger by invoking the affected precompiled contract with crafted calldata. This satisfies the "node crash or halt" bar required by the validation rules.

### Likelihood Explanation
Any unprivileged account can construct a transaction that performs a `CALL`/`STATICCALL` to the affected precompiled-contract address with crafted `data` containing an oversized `len` word or an out-of-range offset word. No special privileges, victim cooperation, or existing on-chain state are required — only knowledge of the ABI-like word layout these helpers expect, which is derivable from the decompiled bytecode/tests in the repo.

### Recommendation
Add explicit bounds checks in `extractBytesArray` and `extractSigArray` (and `extractBytes32Array`, which has no bounds check at all) before every `words[...]` access: verify `offset + i + 1 < words.length` and `offset + bytesOffset + 1 < words.length` inside the loop, and verify the final byte-range passed to `extractBytes`/`Arrays.copyOfRange` does not exceed `data.length`. On violation, fail closed (return `Pair.of(false, EMPTY_BYTE_ARRAY)`) rather than throwing, consistent with how other precompiles in this file already guard against malformed ABI input (`isValidAbiEncoding`).

### Proof of Concept
1. Craft a transaction that performs a `CALL` (or a top-level contract-call transaction) to the precompiled-contract address served by `extractSigArray`/`extractBytesArray` (the signature-array decoding precompile referenced by `ValidateMultiSignContractTest`).
2. Set the calldata word at `offset` (the declared array length) to a large value (e.g., `0xFFFFFFFF` truncated via `intValueSafe`) while making the actual calldata short.
3. Execution reaches the loop `for (int i = 0; i < len; i++) { ... words[offset + i + 1] ... }`; since `len` is unchecked against the real size of `words`, the access throws `ArrayIndexOutOfBoundsException` once `offset + i + 1 >= words.length`.
4. If this exception is not caught by an outer handler on this call path (as documented by the pre-activation test comment for the sibling decoder), it propagates out of ordinary "revert on bad input" handling, causing abnormal termination of block/transaction processing for any node executing this call.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
