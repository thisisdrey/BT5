### Title
Missing slippage/expected-amount protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables sandwich attacks on AMM liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`java-tron`'s built-in bancor-style AMM exchange lets any account trade against a pool via `ExchangeTransactionContract`, and lets the pool's creator add/remove liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Trading (`ExchangeTransactionActuator`) protects the caller with a caller-supplied `expected` minimum-output check, but liquidity injection and withdrawal do not let the creator specify any acceptable ratio bound or deadline — the paired token amount is derived purely from whatever the pool's current balances happen to be at execution time.

### Finding Description
In `ExchangeTransactionActuator.doValidate()` the caller supplies `tokenExpected` and the actuator enforces `anotherTokenQuant >= tokenExpected` before execution: [1](#0-0) 

No equivalent bound exists for liquidity injection. `ExchangeInjectActuator.doValidate()` computes `anotherTokenQuant` strictly from the exchange's current `firstTokenBalance`/`secondTokenBalance` at validation time, with no caller-supplied acceptable ratio, min/max, or deadline: [2](#0-1)  The same is true in `execute()`, which recomputes `anotherTokenQuant` again from whatever the on-chain pool state is at that point: [3](#0-2) 

`ExchangeWithdrawActuator` has the same structure — the paired withdrawal amount is derived from the live pool ratio with only a fixed "not precise enough" tolerance check, not a caller-specified range or deadline: [4](#0-3) 

Because Tron block producers order and pack multiple transactions into the same block, and `Manager` applies all contracts in a block deterministically in sequence, an attacker who observes an unconfirmed `ExchangeInjectContract` or `ExchangeWithdrawContract` in the pending pool can submit their own `ExchangeTransactionContract` trade against the same exchange ID to shift `firstTokenBalance`/`secondTokenBalance` immediately before the victim's transaction executes, then submit a reverse trade immediately after to restore the ratio and extract the difference (classic sandwich attack) — extracting value from the liquidity provider. This directly parallels the reported bug class: prices/ratios that are "inferred contextually" for AMM inject/withdraw without a user-specified acceptable range or deadline.

### Impact Explanation
This allows an unprivileged transaction broadcaster to extract value (TRX/TRC10 tokens) from an exchange creator's liquidity injection or withdrawal via a same-block sandwich, resulting in concrete loss of funds for the liquidity provider (asset-for-asset value skew captured by the attacker). This is a Medium-severity, fund-loss issue reachable purely through normal signed transactions (`ExchangeTransactionContract` + `ExchangeInjectContract`/`ExchangeWithdrawContract`), no privileged role required.

### Likelihood Explanation
Exploitation requires only submitting ordinary transactions and does not require any SR/witness/committee privilege, chain-halting behavior, or special network position beyond normal transaction broadcasting and observing the mempool/pending transactions, which any client can do. The `ExchangeInjectContract`/`ExchangeWithdrawContract` restriction to the exchange creator (`!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check) limits the victim set to creators actively managing liquidity, but does not prevent third parties from sandwiching those actions.

### Recommendation
Add caller-specified bounds to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., minimum/maximum acceptable paired-token amount, analogous to the existing `expected` field in `ExchangeTransactionContract`), and enforce them in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()`. Optionally add an expiration/deadline field checked against `dynamicStore`'s latest block timestamp to bound execution staleness.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeInjectContract` intending to inject at the currently observed pool ratio (no `expected`/bound field exists to protect them).
2. Attacker observes the pending transaction and submits `ExchangeTransactionContract` (using `ExchangeTransactionActuator`) trading a large amount into the same `exchangeId`, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for the injector, ordered before the victim's transaction in the same block.
3. Victim's `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from the now-skewed balances at lines [5](#0-4) , causing the creator to inject at a worse ratio than intended.
4. Attacker submits a reverse `ExchangeTransactionContract` after the injection to restore the ratio, pocketing the difference extracted from the creator's liquidity contribution.
