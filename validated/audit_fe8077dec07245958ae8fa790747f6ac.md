### Title
Unvalidated array-length field in TVM precompile input causes uncontrolled memory allocation - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read an array-length word directly from the raw calldata passed into a TVM precompiled contract call and use it, unchecked, to allocate a Java array (`new byte[len][]`), mirroring the elfutils `read_long_names` bug class: a length taken from untrusted input is trusted for allocation sizing instead of being validated against the actual size of the remaining input.

### Finding Description
`extractBytes32Array` and `extractBytesArray` derive `len` from `words[offset].intValueSafe()` — a 256-bit word taken straight from the calldata `data` of a precompiled-contract call — and immediately allocate `byte[len][]` before any bound is enforced against the actual length of `words`/`data`: [1](#0-0) 

`extractSigArray` follows the identical unchecked pattern: [2](#0-1) 

Unlike the sibling `VerifyTransferProof.execute` code path, which explicitly bounds attacker-supplied counts (`spendCount < 1 || spendCount > 2 || receiveCount < 1 || receiveCount > 2`) before allocating arrays sized by those counts: [3](#0-2) 

`extractBytesArray`/`extractBytes32Array`/`extractSigArray` perform no such sanity check on `len` before allocating `new byte[len][]`. `DataWord.intValueSafe()` only guards against negative/overflowing 256-bit-to-int conversion; it does not validate that `len` is consistent with the actual size of `words`/`data` available in the current call. A caller of the precompiled contract (any account able to deploy or invoke a contract that reaches these decode helpers) can therefore set the length word to a very large positive int (up to `Integer.MAX_VALUE`), triggering an attempt to allocate an array of that many object references — tens of gigabytes of address space — before any subsequent loop even touches `words[offset + i + 1]`. This is the exact bug class in ALPINE-CVE-2019-7148: a size read from untrusted, attacker-controlled input is used to size a memory allocation without validating it against the amount of data actually present.

### Impact Explanation
Attempting `new byte[Integer.MAX_VALUE][]` (or any sufficiently large `len`) throws (or attempts) a multi-gigabyte heap allocation inside the shared JVM process that executes all transactions for the node, not inside a sandboxed context. Depending on heap headroom this manifests as an `OutOfMemoryError`, GC storms, or degraded throughput across the whole node, i.e. a remotely triggerable denial-of-service against block/transaction processing reachable from a single crafted transaction that invokes the precompiled contract with malicious calldata — matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The precompiled contract is invoked by ordinary `CALL`/`STATICCALL` opcodes from any deployed contract, so no special privilege is required — an unprivileged contract deployer/caller can construct calldata with an oversized length word at the offset consumed by these helpers. The energy/gas metering for the precompile is charged based on declared input size or a fixed cost, not on the derived `len` used for array allocation, so the attacker does not need to pre-pay energy proportional to the attempted allocation.

### Recommendation
Before allocating `new byte[len][]` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate `len` against the actual available length of `words` (i.e., `offset + 1 + len <= words.length`, similar to `RLP.verifyLength`'s bound check against `data.length`), and reject/return an empty result if the declared length exceeds what the input can support, exactly as `isValidAbiEncoding` and the zk-proof precompiles already do for their own count fields.

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL`/`CALL` to the precompiled-contract address whose `execute(byte[] data)` implementation invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray`.
2. Craft `data` such that the `DataWord` at the consumed `offset` decodes (via `intValueSafe()`) to a very large positive integer (e.g., near `Integer.MAX_VALUE`), while the rest of `data`/`words` is short/empty.
3. Broadcast the transaction; execution reaches `int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];` with no bound check, forcing the node's JVM to attempt a huge allocation, producing an `OutOfMemoryError`/severe GC pressure during transaction execution.

Note: I was unable to fully trace, within the tool budget, exactly which precompile class(es)/address(es) call `extractBytesArray`/`extractBytes32Array`/`extractSigArray` (they appear to back a batch-signature-validation style precompile in this file), and I could not inspect the full body of `DataWord.intValueSafe()` to confirm its exact clamping behavior. These would need to be confirmed by a follow-up code read to pin down the precise precompile address and the maximum achievable `len` value.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
