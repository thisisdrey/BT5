### Title
Missing hash verification in `AttachmentsBatchStateContext::extend_with_attachments` allows a malicious peer to satisfy an `AttachmentRequest` with unrelated content - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any successfully-decoded `GetAttachmentResponse` for an in-flight `AttachmentRequest` without ever comparing the returned `Attachment`'s content hash to the `content_hash` that was actually requested. Any remote peer serving `/v2/attachments/<hash>` can therefore answer a request for content `X` with arbitrary bytes hashing to `Y != X`.

### Finding Description
In `stackslib/src/net/atlas/download.rs`, `extend_with_attachments` iterates `results.succeeded` (keyed by the original `AttachmentRequest`, which carries `content_hash`) and does:

```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

The `request` (which holds `request.content_hash`, the value the batch is actually trying to resolve) is completely discarded once decoding succeeds — there is no `assert!(response.attachment.hash() == request.content_hash)` or equivalent check anywhere in this function. The only validation performed is that the bytes decode into a well-formed `GetAttachmentResponse`/`Attachment` (`decode_atlas_get_attachment`) and that the reported HTTP status is not 404, both of which a malicious peer trivially satisfies by returning any valid, arbitrary attachment payload.

Downstream, in `AttachmentsDownloader::run`, the collected attachments are drained and processed keyed by `attachment.hash()` (the actual hash of whatever bytes the peer sent), not by the original requested `content_hash`: [2](#0-1) 

Because the lookup and the resolution use the attacker-controlled attachment's own hash, and the queued `AttachmentRequest` for `X` is never explicitly matched/removed by `content_hash`, a malicious peer can cause the request for `X` to be marked "successful" at the reliability-report layer (`report.bump_successful_requests()`) and consume a slot in the batch, without the content for `X` ever actually being resolved — while unrelated attacker-chosen bytes under `Y` get processed and inserted into the atlas database via `insert_instantiated_attachment`.

### Impact Explanation
An attacker-controlled peer selected as an Atlas attachment source can:
- Cause the reliability-tracking layer to record a false "successful" delivery for a request it did not actually satisfy, gaming peer scoring.
- Cause the `AttachmentRequest` for the genuinely committed content hash `X` (e.g., a BNS zonefile hash referenced on-chain) to go unresolved for that download cycle even though the peer "answered", since nothing ties the returned attachment back to `X`.
- Cause arbitrary, unsolicited attachment bytes (`Y`) to be pushed into the local node's attachment processing/storage path, since there is no check that `Y` was ever an outstanding, requested hash.

This matches the "attachment/BNS mismatch" high-impact category: content that is canonically committed (`X`) can fail to resolve via a given peer while irrelevant peer-supplied bytes are accepted as a "successful" response.

### Likelihood Explanation
Any remote node that is included in `AttachmentsDownloader`'s peer set for a batch (i.e., any outbound sync peer providing a data URL, which requires no special privilege beyond being a normally-connected peer) can serve this response to `/v2/attachments/<hash>` GET requests originated by the victim node. No secret, signature, or privileged role is required — only that the victim's node queries the attacker for the attachment, which happens naturally as part of normal Atlas gossip/sync. The attack is repeatable per attachment request.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, explicitly verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments` and before calling `report.bump_successful_requests()`. On mismatch, treat it as a failed/faulty response (`report.bump_failed_requests()` and/or mark the peer as faulty) rather than silently accepting it.

### Proof of Concept
A Rust test in `stackslib::net::atlas::download` (or a new test module) can:
1. Build an `AttachmentRequest` with `content_hash = X` and a fake `sources` map with a stub peer URL.
2. Construct a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains `(request, Some(response))`, where `response` is built such that `response.decode_atlas_get_attachment()` returns `GetAttachmentResponse { attachment: Attachment(bytes) }` with `attachment.hash() = Y != X` (e.g., using `getattachment.rs`'s response-encoding helpers used in `stackslib/src/net/api/tests/getattachment.rs`).
3. Call `AttachmentsBatchStateContext::extend_with_attachments(context, &mut results)`.
4. Assert that `context.attachments` contains an `Attachment` whose `.hash() == Y` (not `X`), and that `report.bump_successful_requests()` was invoked for the peer — demonstrating the request for `X` was marked "succeeded" while never actually being satisfied, with no assertion anywhere checking `attachment.hash() == request.content_hash`.

Note: I was unable to fully trace `AtlasDB::insert_instantiated_attachment`, `find_all_attachment_instances`, and `AttachmentsBatch::resolve_attachment` in this pass due to tool-call limits, so the precise downstream storage/resolution semantics (e.g., whether content-addressing in the DB neutralizes secondary effects) could not be fully confirmed; the core finding — the absence of the `attachment.hash() == request.content_hash` check in `extend_with_attachments` — is directly confirmed in code.
