## Analog Found: Global, single-lane bridge congestion state can be forcibly triggered by any user to grief all bridge traffic

### Title
Unprivileged flooding of a shared bridge outbound lane forces global congestion/suspension state, degrading bridge processing for all users - (File: `bridges/modules/xcm-bridge-hub/src/exporter.rs`, `bridges/modules/xcm-bridge-hub-router/src/lib.rs`)

### Summary
`pallet-xcm-bridge-hub` monitors a single outbound lane's queued-message count and automatically flips a shared `BridgeState` to `Suspended` once a fixed threshold is crossed, then signals congestion back to the sending chain. `pallet-xcm-bridge-hub-router`, which fronts this bridge on the sending chain (e.g. Asset Hub), stores this congestion/fee-factor state in a single, non-keyed `StorageValue<BridgeState>` — explicitly documented as applying to "all outbound messages through this router," i.e. every user routing XCM over that lane shares one congestion/fee state. Any unprivileged account can send enough messages over the bridge to cross the threshold and force this shared state to degrade for every other user, exactly mirroring the reported pattern of an attacker forcibly activating a shared, global throttling mechanism to grief unrelated users.

### Finding Description
The outbound congestion threshold is a fixed constant, not scoped per sender: [1](#0-0) 

When any message is delivered (i.e. any user's XCM export over the bridge), the pallet checks the *total* enqueued message count for the lane and, once it exceeds `OUTBOUND_LANE_CONGESTED_THRESHOLD`, suspends the whole bridge (a single `BridgeId`/lane serving potentially many independent senders) and emits a congestion signal to the local origin: [2](#0-1) 

Note the comment that the bridge still keeps accepting new messages even while "suspended," which the code itself flags as a known gap ("we either need fishermen to watch this rule violation ... or we need a hard limit"): [3](#0-2) 

On the sending side, `pallet-xcm-bridge-hub-router` explicitly documents that it assumes a single shared lane/remote consensus per pallet instance — meaning the `Bridge` congestion/fee state is not per-sender or per-destination-account, but global to the instance: [4](#0-3) 

Once congestion is reported (via the privileged-but-automatic `report_bridge_status` call from the bridge hub, triggered purely by queue depth, not by any admin judgment), every subsequent unrelated sender pays an exponentially increasing fee via `do_increase_fee_factor`, and while `is_congested`, the fee factor never decreases: [5](#0-4) [6](#0-5) 

This is the same broken invariant as the external report: a single global (not per-flow/per-actor) throttling/queue-activation mechanism, driven by attacker-controlled traffic volume, that punishes all unrelated participants once crossed — no privileged actor is required to trigger it, only enough ordinary sends.

### Impact Explanation
An unprivileged attacker who repeatedly sends low-value XCM messages across a bridge lane (e.g., Asset Hub ⇄ Asset Hub bridge over BridgeHub) can:
1. Push the outbound lane's queued message count past `OUTBOUND_LANE_CONGESTED_THRESHOLD` (8,192), causing `pallet-xcm-bridge-hub` to mark the shared bridge `Suspended` and emit a congestion signal.
2. Cause `pallet-xcm-bridge-hub-router` on the sending chain to set `bridge.is_congested = true`, which then exponentially escalates delivery fees for every other, unrelated user of that same router instance, and prevents the fee factor from decaying while the attacker keeps the queue backed up.
3. Repeat this cheaply and indefinitely (since the exporter keeps accepting new messages into the "suspended" bridge per its own documented gap), degrading UX/cost for the entire bridge for as long as the attacker wants, exactly as in the external report's Exploit Scenario 2 (repeated triggering to degrade UX/hinder legitimate withdrawals/messages while exploiting the resulting confusion/backlog window).

This matches the required impact category of "public underpriced work that degrades block production or stalls bridge processing," since the attacker's own cost (ordinary message fees) is far lower than the aggregate cost imposed on all other bridge users via the exponential fee factor and suspension signal.

### Likelihood Explanation
No malicious peer, validator, collator, relayer, or governance/admin action is required — an ordinary signed account can drive traffic through the bridge's public `SendXcm`/`ExportXcm` entrypoints. The threshold is a fixed constant known from the source, and the congestion/fee state is explicitly shared/global per the pallet's own documentation, so the attack surface is deterministic and repeatable each time the attacker is willing to pay for enough messages.

### Recommendation
- Scope congestion/suspension detection and the resulting fee-factor escalation per-sender or per-flow rather than to a single shared `BridgeState`/`StorageValue`, similar to the report's recommendation of per-token buckets instead of one global queue.
- Enforce a genuine hard limit that rejects (rather than continues accepting) new messages once a lane is marked `Suspended`, closing the gap flagged in the code's own `TODO`.
- Consider rate-limiting per-origin message submission into the bridge lane before it can influence the shared congestion signal.

### Proof of Concept
1. Attacker submits many small, cheap XCM messages via the router's public `SendXcm::validate`/`deliver` path targeting the bridged network so they are exported through `pallet-xcm-bridge-hub`'s `deliver` (`bridges/modules/xcm-bridge-hub/src/exporter.rs:188-206`).
2. Each successful delivery increments the outbound lane's `enqueued_messages` count; once `enqueued_messages > OUTBOUND_LANE_CONGESTED_THRESHOLD` (8,192), `on_bridge_message_enqueued` (`exporter.rs:217-282`) flips the shared `BridgeState` to `Suspended` and calls `T::LocalXcmChannelManager::suspend_bridge`, which sends a congestion `Transact` to the sending chain's router pallet.
3. `pallet-xcm-bridge-hub-router::report_bridge_status` (`lib.rs:165-185`) sets the single, shared `Bridge.is_congested = true`.
4. From this point, every unrelated user's `exporter_for`/`validate` call (`lib.rs:260-343`, `lib.rs:352-...`) computes fees using the escalating `fee_factor`, and `on_initialize` (`lib.rs:126-136`) refuses to decay the factor while `is_congested` remains true — which the attacker can sustain by continuing to submit cheap messages, indefinitely degrading the bridge experience for all other users on that shared lane/router instance.

	/// Called when new message is pushed onto outbound bridge queue.
	fn on_bridge_message_enqueued(
		bridge_id: BridgeId,
		bridge: BridgeOf<T, I>,
		enqueued_messages: MessageNonce,
	) {
		// if the bridge queue is not congested, we don't want to do anything
		let is_congested = enqueued_messages > OUTBOUND_LANE_CONGESTED_THRESHOLD;
		if !is_congested {
			return;
		}

		// TODO: https://github.com/paritytech/parity-bridges-common/issues/2006 we either need fishermens
		// to watch this rule violation (suspended, but keep sending new messages), or we need a
		// hard limit for that like other XCM queues have

		// check if the lane is already suspended. If it is, do nothing. We still accept new
		// messages to the suspended bridge, hoping that it'll be actually resumed soon
		if bridge.state == BridgeState::Suspended {
			return;
		}

		// else - suspend the bridge
		let result_bridge_origin_relative_location =
			(*bridge.bridge_origin_relative_location).clone().try_into();
		let bridge_origin_relative_location = match &result_bridge_origin_relative_location {
			Ok(bridge_origin_relative_location) => bridge_origin_relative_location,
			Err(_) => {
				tracing::debug!(
					target: LOG_TARGET,
					?bridge_id,
					origin_location=?bridge.bridge_origin_relative_location,
					"Failed to convert"
				);

				return;
			},
		};
		let suspend_result =
			T::LocalXcmChannelManager::suspend_bridge(bridge_origin_relative_location, bridge_id);

			if bridge.is_congested {
				return T::WeightInfo::on_initialize_when_congested();

			// if we can't decrease the delivery fee factor anymore, we don't change anything
			if !Self::do_decrease_fee_factor(&mut bridge.delivery_fee_factor) {
				return T::WeightInfo::on_initialize_when_congested();
			}

			tracing::info!(
				target: LOG_TARGET,
				from=%previous_factor,
				to=%bridge.delivery_fee_factor,
				"Bridge channel is uncongested. Decreased fee factor"
			);
			Self::deposit_event(Event::DeliveryFeeFactorDecreased {
				new_value: bridge.delivery_fee_factor,
			});

			Bridge::<T, I>::put(bridge);

			T::WeightInfo::on_initialize_when_non_congested()
		}
