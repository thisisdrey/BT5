### Title
Unprivileged dust-transfer griefing fills victim's `depositTokensOfAccount` list to `MAX_TOKENS_PER_USER`, blocking new-collateral deposits and rescue of underwater positions - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's msdTOKEN balance goes from zero to non-zero, including transfers the recipient never requested. `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` (declared in `contracts/storage/PoolStorage.sol` and checked in `contracts/Pool.sol`), reverting once the cap is reached. An unprivileged attacker can deposit dust amounts of every registered collateral and `transfer` 1 wei of each distinct msdTOKEN to a victim, permanently occupying all slots in the victim's collateral list. From then on, any `deposit()`/`_mint` of a *new* collateral type for that victim reverts inside `addToDepositTokensOfAccount`, preventing the victim from adding collateral to an unhealthy position — a reachable, attacker-triggered denial of service analogous to the crafted-message crash. ### Finding Description
The attack path is fully public:

1. For each listed collateral `i`, attacker calls `DepositToken_i.deposit(dust, attacker)` — minting dust msdTOKEN_i to themselves (`deposit` only requires the token be active and supply cap not reached; `DepositToken.sol:211-237`).
2. Attacker calls `DepositToken_i.transfer(victim, 1)`. `transfer` only checks the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`, `DepositToken.sol:350`) — the recipient has no way to opt out.
3. Inside `_transfer`, because `balanceOf[victim] == 0`, `pool.addToDepositTokensOfAccount(victim)` is invoked (`DepositToken.sol:518-519`). Repeated across all `N = MAX_TOKENS_PER_USER` distinct DepositTokens, the victim's list saturates.
4. Any subsequent `deposit` of a collateral the victim does not yet hold mints to them via `_mint`, which hits the same `addToDepositTokensOfAccount` call (`DepositToken.sol:486-488`) and reverts once the list is at cap.

The invariant that breaks is liveness of the collateral-management path: a victim can no longer increase collateralization with a new asset, so an attacker (or any liquidator) can `liquidate` a deteriorating position that the victim could otherwise have rescued. Note the victim can purge a dust slot by transferring the dust balance out (`_transfer` removes the entry when sender balance hits zero, `DepositToken.sol:523-524`), so the freeze is temporary/gas-cost-bound rather than permanent — but it can be re-applied cheaply and timed around a price move or liquidation.

### Impact Explanation
Attacker-induced denial of service on `deposit()` for new collateral types. Materialized impact: a victim whose health factor is declining cannot top up with an unheld collateral (e.g., a different stablecoin), making them liquidatable when they would not have been — enabling forced liquidation loss and temporary freezing of the deposit functionality. The attack costs only dust amounts of each collateral plus gas, and needs no privileged role, oracle manipulation, or victim interaction.

### Likelihood Explanation
Reachability is confirmed: `transfer` is permissionless and the list-add hook fires on any first receipt. Feasibility depends on the deployed value of `MAX_TOKENS_PER_USER` relative to the number of registered DepositTokens — the attack requires `registeredTokens >= MAX_TOKENS_PER_USER` distinct collateral markets so the attacker can fill every slot. If fewer collaterals exist than the cap, the attack cannot saturate the list and the DoS does not materialize; this is the main uncertainty, as the cap is a `PoolStorage`/deployment constant that should be verified against live `Pool` deployments. RewardsDistributor hooks in `updateRewardsBeforeTransfer` and pause flags do not block this path.

### Recommendation
- Do not mutate the victim's `depositTokensOfAccount` list on unsolicited inbound `transfer`/`transferFrom`; only register the token in the list on `deposit()`/seize paths where the account actively receives collateral, or make list membership opt-in.
- Alternatively, ignore balances below a dust threshold when deciding list membership, or replace the revert-on-cap with a cap on the number of collaterals counted toward `debtPositionOf`.
- Add a regression test: attacker dust-transfers all msdTOKEN types to a victim; victim's `deposit` of a new collateral must still succeed.

### Proof of Concept
Hardhat/Foundry fork sketch (fill deployment addresses from `deployments/mainnet/Pool.json` etc.):

```solidity
// attacker = fresh EOA, victim = existing depositor with unhealthy position
for (uint i; i < depositTokens.length; ++i) {
    DepositToken dt = depositTokens[i];
    uint dust = 1e3; // enough underlying to mint >=1 wei of msdTOKEN after fee
    deal(address(dt.underlying()), attacker, dust);
    IERC20(dt.underlying()).approve(address(dt), dust);
    dt.deposit(dust, attacker);          // mint dust msdTOKEN to attacker
    dt.transfer(victim, 1);              // victim's list gains entry i
}
// victim now has MAX_TOKENS_PER_USER entries
DepositToken newCollateral = ...;        // a listed token victim doesn't hold
underlying.approve(address(newCollateral), amount);
vm.prank(victim);
vm.expectRevert();                       // addToDepositTokensOfAccount cap revert
newCollateral.deposit(amount, victim);
// meanwhile pool.liquidate(...) against victim succeeds
```

Uncertainty noted: the exact revert inside `Pool.addToDepositTokensOfAccount` and the deployed value of `MAX_TOKENS_PER_USER` were not directly read in this pass; verify against `contracts/Pool.sol` and `contracts/storage/PoolStorage.sol`. If the cap exceeds the number of registered collaterals, the finding reduces to non-exploitable and should be downgraded or rejected.
