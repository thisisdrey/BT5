Audit Report

## Title
`OutboundQueue::calculate_fee` rounds the remote (relayer-reward) component to zero, letting senders under-pay for a promised Ethereum-side payout - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::calculate_fee` computes the DOT-denominated fee charged to a message sender to cover Ethereum-side gas refund and relayer reward, but its final step `convert_from_ether_decimals` performs a floor integer division that truncates the `remote` component to zero whenever the ether-denominated value is smaller than the `10^(18-Decimals)` scaler. `PricingParameters::validate` only checks for fully-zero fields and does not prevent this truncation, so legitimately valid, non-zero pricing parameters (as the pallet's own test demonstrates) can still yield `fee.remote == 0` while the message committed to Ethereum still promises the full `reward`/`max_fee_per_gas`.

## Finding Description
`calculate_fee` computes `calculate_remote_fee` (wei), scales it by `multiplier`/`exchange_rate`, and finally calls `convert_from_ether_decimals(value)`, which executes `value.checked_div(denom)` where `denom = 10^(18-Decimals)`. Any `value` below `denom` truncates to `0`. `PricingParameters::validate` only rejects the case where fields are exactly zero, not the case where their product is merely small relative to the decimal scaler, so this guard is insufficient. Separately, `do_process_message` builds the `CommittedMessage` sent to Ethereum using the raw, untruncated `pricing_params.rewards.remote` and `pricing_params.fee_per_gas` values — not the (possibly zero) computed fee — so the promised Ethereum-side payout is fully decoupled from what is actually collected from the sender via `EthereumBlobExporter::validate`, which charges exactly `fee.total()` with no check that `fee.remote > 0`.

## Impact Explanation
This is a public underpriced work condition: any unprivileged sender routing an Ethereum-bound command through `pallet_xcm`/`transfer_assets` → `EthereumBlobExporter` pays only `fee.local` while the bridge still commits to fully reimbursing relayers on the Ethereum Gateway contract. Repeated at scale (whenever governance-set pricing parameters happen to be small relative to the decimal scaler, e.g., after an exchange-rate update), this drains the reward-funding backing without corresponding fee collection and can starve/de-incentivize relayers, degrading bridge message processing.

## Likelihood Explanation
No privileged action or malicious relayer/validator is required — any user submitting a low-cost command through the public XCM export path can trigger the truncation whenever prevailing `PricingParameters` (fee_per_gas, reward, exchange_rate, multiplier) combined with a command's gas estimate produce an ether fee below `10^(18-Decimals)` wei. The pallet's own test (`test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`) proves this is reachable with entirely plausible, non-degenerate parameters.

## Recommendation
In `convert_from_ether_decimals` or `calculate_fee`, use round-up division (`div_ceil`) instead of floor division, or explicitly reject/floor a zero `remote` result when `params.rewards.remote` and `params.fee_per_gas` are non-zero (e.g., `ensure!(fee.remote > 0, Error::<T>::FeeTooLow)`) before returning the fee to be charged and before enqueuing the message that promises the full un-truncated reward on Ethereum.

## Proof of Concept
Use the existing repository test as the reproduction: set `PricingParameters { exchange_rate: 1, fee_per_gas: 1, rewards: { local: 1, remote: 1 }, multiplier: 1 }` (valid per `PricingParameters::validate`), call `OutboundQueue::calculate_fee(gas_used, price_params)`, and observe `fee.local = 698000000` (charged) but `fee.remote = 0`, while `do_process_message` still commits the full `reward = 1` and `max_fee_per_gas = 1` into the `CommittedMessage` sent to Ethereum's Gateway contract.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}
