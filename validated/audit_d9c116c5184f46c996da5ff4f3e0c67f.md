### Title
Unbounded array allocation from unchecked calldata length in TVM precompile helpers - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE-2024-34905 report describes a crafted, oversized input field (`password`) that is used to size/allocate a buffer without an upper bound, causing a Denial-of-Service crash. The closest reachable analog in java-tron is the family of calldata-array extraction helpers used by the TVM precompiled contracts (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`), which take an attacker-controlled 32-byte "length" word straight from the transaction's contract-call data and use it to allocate a Java array, with no upper-bound check on the value before allocation.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each read a count directly from the caller-supplied `data` (via `words[offset].intValueSafe()`) and immediately allocate a two-dimensional array sized by that count: [1](#0-0) 

Unlike other precompiles in the same file — e.g. `ModExp.execute`, which explicitly caps `baseLen`, `expLen`, `modLen` to `UPPER_BOUND = 1024` before doing any work — these array-extraction helpers perform no equivalent bound check on the decoded length before calling `new byte[len][]`: [2](#0-1) 

Any account can reach these precompiles by deploying or invoking a smart contract that performs a `CALL`/`STATICCALL` to the corresponding precompile address (the batch-signature-validation and multi-sign-validation precompiles are the only callers of these helper functions in this file), which is exactly the "unprivileged contract caller" surface named in the validation rules. Because `intValueSafe()` only clamps a `DataWord` to a non-negative `int` (up to `Integer.MAX_VALUE`) rather than to a small sane bound, a crafted transaction can set the length word to a very large value (e.g. close to `Integer.MAX_VALUE`), causing the JVM to attempt to allocate an outsized array. This throws `OutOfMemoryError` (or induces heavy GC pressure) inside the actuator/VM execution path used by every node validating or re-executing the transaction, mirroring the "attacker-controlled length used for allocation" root cause of CVE-2024-34905.

### Impact Explanation
An `OutOfMemoryError` triggered while executing a smart-contract call inside `VMActuator`/`Program` execution is not confined to the calling thread’s stack in the way a checked exception would be — it can destabilize the JVM, degrade or crash node availability, and because it occurs during transaction processing (which every full node in the network re-executes when applying the block), it can be triggered network-wide by a single signed transaction, producing a broad denial-of-service.

### Likelihood Explanation
This is reachable by any unprivileged account able to deploy a contract and issue a `TriggerSmartContract` transaction that performs a `CALL` to the batch/multi-signature-validation precompile addresses (gated by `VMConfig.allowTvmSolidity059()`), with fully attacker-controlled calldata bytes. No special permissions, staking, or witness/committee role is required — only a signed transaction and enough TRX to cover the (fixed, low) `getEnergyForData` cost of the precompile, since the energy costs for these precompiles are not scaled to the size implied by the unbounded length field.

### Recommendation
Add an explicit upper bound check on the decoded `len` value in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (mirroring `ModExp`'s `UPPER_BOUND` pattern) before allocating the array, and validate that `len` is consistent with the actual remaining size of `data` so that array sizes can never exceed what the supplied calldata can possibly encode.

### Proof of Concept
1. Deploy or use any contract, then issue a `TriggerSmartContract` transaction that calls the batch-validate-signature (or multi-sign-validate) precompile address with calldata encoding a count word (the `words[offset]` slot consumed by `extractBytesArray`/`extractSigArray`) set to a very large value (e.g. `0x7FFFFFFF`), while keeping the enclosing `TriggerSmartContract` payload minimal so the transaction is otherwise well-formed and passes basic size/fee checks.
2. Broadcast the transaction; when nodes execute it through `VMActuator.call()` → the precompile's `execute(data)`, the helper allocates `new byte[len][...]`, attempting to allocate gigabytes of memory in a single call.
3. Observe `OutOfMemoryError`/severe GC pause on the executing node(s), causing degraded processing or crash — reproducible by any single unprivileged account without further capital or privilege beyond covering the modest declared energy cost.

Note: I was unable to fully trace the exact call sites for `extractBytesArray`/`extractSigArray`/`extractBytes32Array` inside `BatchValidateSign`/`ValidateMultiSign`'s `execute()` methods before running out of tool iterations, so the precise offset/format used in the PoC calldata (and whether any partial length pre-check exists closer to those specific call sites) could not be independently confirmed from the excerpts retrieved. This should be verified directly in the repository before treating the PoC as exact.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
