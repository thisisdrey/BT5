### Title
Unprivileged attacker can manufacture permanent-conflict filler transactions to poison `buffer_size()` saturation accounting and force sigverify to drop unrelated victim transactions via the priority floor - ([File: core/src/banking_stage/transaction_scheduler/scheduler_controller.rs])

### Summary
`TransactionStateContainer::buffer_size()` simply returns the length of `id_to_transaction_state` (a `Slab`), counting every buffered transaction regardless of whether it can ever be scheduled. Transactions that fail account-lock scheduling with `TransactionSchedulingError::UnschedulableConflicts` are pushed back into the queue every scheduling pass and never removed, so an attacker can fill the buffer with self-conflicting, never-executing (and thus fee-free) transactions to trigger `SaturationState` and raise `SchedulerPriorityFloor`, causing sigverify to drop unrelated victim transactions pre-verification.

### Finding Description
The scheduler's saturation/priority-floor mechanism is driven purely by raw buffer occupancy:

- `TransactionStateContainer::buffer_size()` returns `self.id_to_transaction_state.len()` [1](#0-0) , with no distinction between schedulable and permanently-conflicting entries.
- `SchedulerController::update_scheduler_priority_floor` feeds this raw `buffer_size()` into `SaturationState::update`, and once saturated publishes the container's current minimum queued priority as the floor [2](#0-1) .
- `SaturationState::update` saturates once `buffer_size >= saturation_watermark` (99% of `TOTAL_BUFFERED_PACKETS`) [3](#0-2) .
- In `GreedyScheduler`, transactions that cannot be locked due to `TryLockError::MultipleConflicts` are classified `UnschedulableConflicts`, pushed to `self.unschedulables`, and re-inserted into the queue at the end of every pass via `container.push_ids_into_queue(self.unschedulables.drain(..))` — they are never removed from `id_to_transaction_state` [4](#0-3) [5](#0-4) .
- Once saturated, sigverify (`run_transaction_task` / `apply_priority_floor_to_batch`) discards any *incoming* packet whose fee-derived priority is at or below the floor, before signature verification even runs [6](#0-5) [7](#0-6) .

Crucially, `check_fee_payer_unlocked` (run when buffering, not when executing) only checks that a fee payer *currently* has enough lamports; it does not debit or reserve the balance [8](#0-7) . Fees are only ever actually deducted during `load_and_execute_transactions`, which never happens for transactions permanently blocked by `AccountInUse`/`UnschedulableConflicts`. Thus an attacker can reuse one funded keypair (whose own account is implicitly write-locked as a signer) to sign an arbitrarily large number of distinct, mutually write-conflicting transactions (e.g., all using the same fee-payer/writable account) at essentially zero real cost, since none of them ever execute and get charged.

By choosing filler priority higher than the priority of the transactions they want to censor, the attacker drives `get_min_max_priority()`'s minimum up, so `SchedulerController::update_scheduler_priority_floor` publishes a floor that causes sigverify to discard legitimate, unrelated (non-conflicting-account) victim transactions before they are even verified — a pre-sigverify censorship/drop of fee-paying transactions that never touch the contested accounts.

### Impact Explanation
This is a Denial-of-Service / QoS-evasion issue: an unprivileged, unstaked attacker can manufacture a bounded but near-capacity set of permanently unschedulable, self-conflicting, essentially fee-free transactions that stay resident in `id_to_transaction_state` indefinitely, hijacking the `SaturationState`/`SchedulerPriorityFloor` mechanism to force the pre-sigverify drop of unrelated victims' legitimate, fee-paying transactions. This matches the bounty's "ingress buffers/scheduler containers stay bounded and their fullness must reflect genuinely schedulable work" invariant violation and the "unrelated victim's fee-paying transaction... dropped" scoped impact.

### Likelihood Explanation
Feasibility is high and repeatable: the attacker needs only one funded keypair, valid signatures on transactions that write-lock a shared account (trivially the fee-payer's own account or any other single writable account across all filler transactions), and enough throughput to keep `buffer_size()` near the 99% `SATURATION_BUFFER_PCT` watermark of `TOTAL_BUFFERED_PACKETS`. Since none of the filler transactions execute, the attacker pays no fees for them; the only ongoing cost is resending fresh ones as older ones expire due to blockhash age. This is straightforwardly reachable from an unstaked TPU client sending ordinary signed transactions.

### Recommendation
Decouple saturation/priority-floor accounting from raw `buffer_size()`. Track a separate count of transactions that are schedulable/making progress (e.g., exclude entries repeatedly returned as `UnschedulableConflicts` across passes, or cap/evict transactions that have failed to schedule for N consecutive passes) so that `SaturationState::update` reflects genuinely schedulable backlog rather than attacker-manufactured, permanently conflicting filler. Additionally, consider bounding how many buffered transactions may share/conflict on the same account(s) so a single account family cannot occupy an unbounded fraction of the buffer.

### Proof of Concept
Integration test plan (in `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs` test module, reusing existing `create_test_frame`/`TransactionStateContainer` test scaffolding):
1. Fund a single fee-payer keypair.
2. Construct N transactions from that keypair, all writing to the same target account (or to the fee-payer's own account), each with a distinct message (varying instruction data/blockhash) but high compute-unit-price, to avoid triggering the `AlreadyProcessed`/dedup path while ensuring pairwise `AccountInUse` conflicts.
3. Buffer these via `receive_and_buffer_packets`/`insert_new_transaction` until `container.buffer_size()` reaches `SATURATION_BUFFER_PCT` of `TOTAL_BUFFERED_PACKETS`.
4. Run one scheduling pass (`GreedyScheduler::schedule`) and assert `scheduling_summary.num_unschedulable_conflicts > 0` and that all N ids remain in `container` (buffer_size unchanged) after `push_ids_into_queue(self.unschedulables.drain(..))`.
5. Call `update_scheduler_priority_floor` and assert `SchedulerPriorityFloor::get()` returns a nonzero value equal to the attacker's filler priority.
6. Construct one unrelated low-priority "victim" transaction touching a disjoint account, run it through `apply_priority_floor_to_batch` with the published floor, and assert it is marked `discard` (dropped) despite having no account overlap with the attacker's transactions — demonstrating unrelated-transaction censorship caused purely by attacker-manufactured, self-conflicting buffer filler.

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)
