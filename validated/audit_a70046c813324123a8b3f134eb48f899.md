### Title
Symlink tar entry in custom_hooks archive allows arbitrary file write outside the extraction directory via `ExtractHooks` - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Summary
`ExtractHooks` (`internal/gitaly/repoutil/custom_hooks.go:55`) pipes an attacker-supplied tar stream directly to the system `tar` binary with no symlink filtering or path validation, unlike the hardened `extractTarToDirectory` used elsewhere in the codebase (`internal/gitaly/service/repository/replicate.go`, validated by `TestExtractTarToDirectory_SymlinkValidation`). A tar archive containing a `custom_hooks` entry of `TypeSymlink` followed by `custom_hooks/<file>` entries can cause the `tar` CLI to write file contents through the symlink target rather than into the intended temporary directory.

### Finding Description
`SetCustomHooks`/`RestoreCustomHooks` (reachable by any user able to push/create a repo, via `SetCustomHooksRequest`/`RestoreCustomHooksRequest`) call `repoutil.ExtractHooks(ctx, logger, reader, tmpDir.Path(), false)` with `reader` fully attacker-controlled tar bytes [1](#0-0) . `ExtractHooks` executes `tar -xf - -C <tmpDir> --strip-components 0 custom_hooks` [2](#0-1) , passing the raw stream to the OS `tar` utility with no inspection of entry types. The member filter is the name `custom_hooks`, which matches both a top-level `custom_hooks` entry and any nested `custom_hooks/*` entries, so an archive with `{Name:"custom_hooks", Typeflag: TypeSymlink, Linkname:"<relative-escape-or-absolute-path>"}` followed by `{Name:"custom_hooks/evilfile", Typeflag: TypeReg, ...}` is accepted by the filter. Standard `tar` extraction resolves intermediate path components through existing symlinks (this is default POSIX path-resolution behavior that GNU/BSD tar do not override), so the second entry's file content is written through the symlink target instead of into `tmpDir`.

This is materially different from `extractTarToDirectory` in `replicate.go`, which contains explicit checks rejecting absolute symlinks and symlinks that escape the destination directory [3](#0-2) , proving the maintainers are aware this exact archive-based symlink-traversal class needs mitigation — but that mitigation was never applied to `ExtractHooks`.

Because `tempdir.NewWithoutContext(repo.GetStorageName(), ...)` creates the temp directory under the same storage root as all repositories, a relative symlink (e.g. `../../<other-repo-relative-path>`) can point at a sibling repository directory that the Gitaly process user can already write to, achieving a cross-repository write without needing absolute-path/root privileges. The subsequent code in `SetCustomHooks` treats `os.Mkdir` on the now-symlinked `tempHooksPath` as tolerable (`errors.Is(err, fs.ErrExist)`) [4](#0-3) , and the eventual failure of `newDirectoryVote` (which will error trying to read a directory as a file, or succeed if the symlink instead points at a writable file) does not undo the write that already occurred outside `tmpDir` during the `tar` invocation, since cleanup only does `os.RemoveAll(tmpDir.Path())` [5](#0-4) .

### Impact Explanation
An unprivileged user who can push a custom-hooks tar (via `SetCustomHooksRequest`/`RestoreCustomHooksRequest`, or via `gitaly-hooks`/backup-restore flows using the same `ExtractHooks`) can cause Gitaly to write attacker-chosen file content to a location outside the intended temporary hooks directory, including into another repository's directory on the same storage (cross-repository object/file write). This matches the "storage-path escape" / "cross-repository object access" bounty impact classes.

### Likelihood Explanation
Precondition is only that the attacker controls the tar payload sent to `SetCustomHooks`/`RestoreCustomHooks`, which any authenticated Gitaly client (a GitLab user operating on their own repo through GitLab Rails) can do. No special role, secret, or misconfiguration is required. The main uncertainty is (a) exact target path predictability (attacker needs to know/guess a relative path to a target on the same storage), and (b) whether the deployed `tar` binary's specific version/flags mitigate mid-path symlink traversal in all cases — this could not be verified by direct execution in this environment and should be confirmed with the PoC below on the actual Gitaly deployment target.

### Recommendation
Do not shell out to the system `tar` binary for extracting attacker-controlled hooks archives. Replace `ExtractHooks` with a Go `archive/tar` based extractor that rejects `TypeSymlink`/`TypeLink` entries (or validates their `Linkname` stays within the destination directory) before writing any file, mirroring the validation already implemented in `extractTarToDirectory` (`internal/gitaly/service/repository/replicate.go`).

### Proof of Concept
```go
func TestExtractHooks_SymlinkEscape(t *testing.T) {
    ctx := testhelper.Context(t)
    tmpDir := t.TempDir()
    targetDir := t.TempDir() // simulate another repository's directory

    var buf bytes.Buffer
    tw := tar.NewWriter(&buf)
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name:     "custom_hooks",
        Typeflag: tar.TypeSymlink,
        Linkname: targetDir, // or a relative "../../<sibling-repo>" path
    }))
    content := []byte("malicious payload")
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name: "custom_hooks/evilfile",
        Mode: 0o644,
        Size: int64(len(content)),
    }))
    _, err := tw.Write(content)
    require.NoError(t, err)
    require.NoError(t, tw.Close())

    _ = repoutil.ExtractHooks(ctx, testhelper.NewLogger(t), &buf, tmpDir, false)

    // Expected (if vulnerable): file written into targetDir, not tmpDir
    written, err := os.ReadFile(filepath.Join(targetDir, "evilfile"))
    require.NoError(t, err)
    require.Equal(t, content, written)
}
```
Run this against the deployed `tar` binary used by Gitaly to confirm whether the symlink is followed (as GNU/BSD tar path resolution generally does for non-final path components) versus rejected.
