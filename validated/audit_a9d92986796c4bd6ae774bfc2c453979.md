### Title
Division-by-zero DoS in vault `system-repay` when vault debt is zero - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) exposes a `system-repay` function that divides by `debt` (i.e. `(total-debt)`) without ever checking that `debt` is non-zero, unlike the sibling `socialize-debt` function in the very same file, which explicitly guards the analogous zero-denominator case. This mirrors the reported bug class: a helper computes a ratio using a denominator that legitimately can be zero, and only some of the call sites in the codebase defend against it while others do not, producing an unguarded division-by-zero panic that reverts the caller's transaction.

### Finding Description
`system-repay` is defined identically in each vault, e.g.: [1](#0-0) 

```clarity
(define-public (system-repay (amount uint))
  (let (
        (states (var-get pause-states))
        (u (try! (accrue)))
        (scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (debt (total-debt))
        (total-borrowed-amount (var-get total-borrowed))
        (capped-amount (if (> amount debt) debt amount))
        (principal-reduction (calc-principal-ratio-reduction capped-amount scaled-principal debt))
        (capped-reduction (if (> principal-reduction scaled-principal) scaled-principal principal-reduction))
        (updated-scaled-principal (- scaled-principal capped-reduction))
        (principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
        ...
```

`total-debt` and `calc-principal-ratio-reduction` are defined as: [2](#0-1) 

```clarity
(define-private (calc-cumulative-debt (principal-amount uint) (idx uint))
  (mul-div-up principal-amount idx INDEX-PRECISION))
...
(define-private (calc-principal-ratio-reduction (amount uint) (scaled-principal uint) (debt-amount uint))
  (mul-div-down amount scaled-principal debt-amount))
```

`total-debt` is `0` exactly when `principal-scaled == 0` (no outstanding borrowed principal in the vault). In that state, `calc-principal-ratio-reduction` and `mul-div-down capped-amount total-borrowed-amount debt` both divide by `debt = 0`. Clarity's `/` operator panics on division by zero (the same class of failure as Solidity's panic 0x12 in the referenced report), reverting the whole `let` before any of the `asserts!` checks even execute.

By contrast, `socialize-debt` in the same file explicitly guards the identical zero-denominator scenario: [3](#0-2) 

```clarity
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        ...
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ...
```

This asymmetry — one privileged system function guards the "no debt" edge case, its sibling does not — is the exact bug class from the report: a derived/related zero-state variable that is not universally checked before being used as a division denominator across all code paths that reach it.

### Impact Explanation
`system-repay` is invoked by the market contract (`market.clar`/`v0-4-market.clar`) as part of ordinary user-triggered debt-repayment and liquidation flows (the vault-level counterpart of a user's `repay`). If it is called while the vault's `principal-scaled` is `0` — e.g. immediately after the last outstanding borrower's debt has been fully repaid but a repay transaction with a non-zero `amount` is still processed/pending, or during any code path that resolves to a repay call on a vault with no active debt — the transaction reverts due to division by zero instead of failing gracefully. This blocks the repay/liquidation path for that vault until the caller adjusts behavior, which is a temporary freezing-of-funds condition for borrowers trying to close out debt and liquidators trying to process undercollateralized positions, matching the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
The vulnerable state (`principal-scaled == 0`, i.e., zero total debt in a vault) is a normal, easily reachable state — it occurs whenever a vault currently has no borrowers, which is common right after deployment, after all borrowers repay, or transiently between borrow/repay cycles. No privileged action or governance compromise is needed to reach the zero-debt state; only a subsequent repay-style call routed through the market contract with `amount > 0` while debt is `0` is required to trigger the panic. I was not able to fully confirm from the market contract's call sites (`market.clar` / `v0-4-market.clar`) whether an upstream guard always prevents `system-repay` from being invoked when a vault's global debt is zero; this is a gap in my verification that a full code review of the market's repay/liquidation dispatch logic would need to close.

### Recommendation
Add an explicit zero-guard for `debt` in `system-repay` mirroring the one already used in `socialize-debt`, e.g. short-circuit to `capped-amount = u0`, `principal-repaid = u0` when `debt == u0`, before computing `calc-principal-ratio-reduction` and `mul-div-down ... debt`. Apply this fix uniformly across all vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) since the logic is duplicated identically in each.

### Proof of Concept
Conceptual PoC (Clarinet/clarigen test), analogous to the reported PoC's "first actor drives a shared denominator to zero, subsequent legitimate call reverts":
1. Deploy a vault with zero borrowed principal (`principal-scaled == 0`), e.g. right after `initialize`.
2. Call `system-repay` (via the authorized market-vault caller, satisfying `check-caller-auth`) with `amount > 0` while `principal-scaled == 0`.
3. Observe the transaction revert with a division-by-zero panic inside `calc-principal-ratio-reduction`/`mul-div-down`, before any `asserts!` runs — confirming the unguarded division identified above. [4](#0-3)
