### Title
Exchange creators can front-run `ExchangeTransactionContract` trades by injecting/withdrawing liquidity to sandwich and steal value from traders - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Any account that creates a bancor-style `Exchange` pool via `ExchangeCreateActuator` becomes its permanent, permissionless "creator" and is the only account allowed to call `ExchangeInjectContract` / `ExchangeWithdrawContract`, which arbitrarily move the pool's `firstTokenBalance`/`secondTokenBalance` ratio. A trader's `ExchangeTransactionContract` only protects against getting *less* than a self-declared minimum (`expected`), exactly analogous to the Teller `submitBid` report where a single unauthenticated market-parameter check ("modifying market parameters just before the borrower transaction") was insufficient to stop the privileged party from extracting value by acting right before the victim's transaction executes. Here, the exchange creator can observe a pending `ExchangeTransactionContract` in the mempool and submit `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions immediately before and after it (classic sandwich), extracting value from the trader while still satisfying the trader's `expected` floor.

### Finding Description
`ExchangeTransactionActuator.doValidate()` only enforces that the output amount is not less than the caller-supplied `tokenExpected`: [1](#0-0) 

This is the only "consent" check the trader has over pool state at execution time — it does not fix the exchange rate, nor does it prevent the pool ratio from being shifted by other transactions ordered immediately before/after the trader's transaction in the same block.

The pool ratio itself can be freely and immediately altered by the exchange's `creatorAddress` via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, whose `doValidate()` requires only that the caller equals `exchangeCapsule.getCreatorAddress()` — no other party's consent or lock is checked: [2](#0-1) [3](#0-2) 

Both inject and withdraw immediately mutate the AMM balances used by `ExchangeCapsule.transaction()` (constant-product-like formula) that determines how much a trader receives for a given `tokenQuant`: [4](#0-3) 

Because pool creation (`ExchangeCreateActuator`) is permissionless, any address can become a pool "creator" — this is directly analogous to the "marketplace owner" in the Teller report: a privileged-but-attacker-reachable role that controls a pricing/duration parameter which affects a victim's already-broadcast transaction, and that role can be assumed by an attacker who also plays the counter-party trade. The creator, observing a pending trade in the mempool, can:
1. Inject liquidity that skews the price against the direction of the pending trade just before it lands, worsening the rate the victim receives (but still ≥ `expected` since the victim set a loose slippage tolerance, as most users do).
2. Immediately withdraw liquidity afterward, extracting the price impact caused by the victim's trade — a textbook sandwich attack — realizing the loss suffered by the victim as their own profit.

This reproduces the report's root cause: reliance on a value (the AMM ratio, analogous to `bidDefaultDuration`/market settings) that a privileged, attacker-controllable actor can change in the same window the victim's transaction is pending, with no atomic binding of the trade to the state the victim actually observed when signing.

### Impact Explanation
The exchange creator (an attacker-reachable, permissionlessly obtained role) can systematically extract value from ordinary traders using `ExchangeTransactionContract`, effectively stealing part of the tokens/TRX a trader intended to receive, each time a trade is submitted. Because `calcFee()` is `0` for inject/withdraw, this attack is essentially free to repeat, and losses accumulate across trades — a concrete theft-of-funds impact meeting High severity.

### Likelihood Explanation
Likelihood is high: creating an exchange is unrestricted, and once created, the creator can call inject/withdraw with no cooldown, no taxation beyond negligible bandwidth/energy cost, and no requirement to coordinate with anyone else. Any pending `ExchangeTransactionContract` broadcast to the network is visible before inclusion, giving the creator the opportunity to bracket it with inject/withdraw calls in the same or adjacent block.

### Recommendation
Bind the trader's expected execution to the exact market state they observed, similar to the fix proposed in the source report: require the trader to supply (and the actuator to verify) the pool's `firstTokenBalance`/`secondTokenBalance` (or a hash of them) at signing time, and revert if the current pool state has diverged. Alternatively, enforce a minimum time lock or fee/impact cap on `ExchangeInjectContract`/`ExchangeWithdrawContract` when a same-block trade exists, or require slippage bounds symmetric to both sides of the AMM instead of a one-sided `expected` floor.

### Proof of Concept
1. Attacker calls `ExchangeCreateActuator` to create pool P(tokenA, tokenB), becoming `creatorAddress`.
2. Victim broadcasts `ExchangeTransactionContract` selling `tokenA` for `tokenB` with a loose `expected` (still satisfies validation at `ExchangeTransactionActuator.doValidate()` line 219-221).
3. Before the victim's transaction is packed, attacker (as creator) submits `ExchangeInjectContract` skewing the ratio unfavorably for the victim's trade direction — accepted per `ExchangeInjectActuator` validate at lines 155-177 (only creator check, no external lock).
4. Victim's trade executes at the worsened rate via `ExchangeCapsule.transaction()` (lines 124-158), still passing the `expected` check but receiving less than the pre-manipulation rate.
5. Attacker immediately submits `ExchangeWithdrawContract` to unwind the injected liquidity, capturing the price impact the victim just paid as profit.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }
