Based on the investigation, a genuine analog exists in `VerifyTransferProof.execute` in `PrecompiledContracts.java`.

### Title
Attacker-controlled offsets in Sapling `VerifyTransferProof` precompile cause unbounded array reads on TVM contract calls - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`VerifyTransferProof.execute()` only validates the *total length* of the precompile input against a fixed set of sizes, then reads three "unfixed field offset" integers directly out of attacker-supplied data and uses them, unchecked, as absolute byte-array indices for further reads. This mirrors the CVE-2026-68402 bug class: an offset/length field taken from untrusted input is used to index into a buffer without validating that the resulting read stays within bounds.

### Finding Description
`execute()` first checks `data.length` against `SIZE = {2080, 2368, 2464, 2752}` [1](#0-0) . It then parses three offsets directly from attacker data with no range validation: [2](#0-1) 

These `spendOffset`, `spendAuthSigOffset`, `receiveOffset` values are fully attacker-controlled 32-bit integers derived from `parseInt(data, 0/32/64)` and are never checked against `data.length`. They are then used directly to index into `data` again: [3](#0-2) 

and subsequently to drive loop-based `System.arraycopy` calls with attacker-controlled base offsets and counts (`spendCount`, `receiveCount` themselves also derived from the same attacker-controlled offset reads): [4](#0-3) 

Unlike the sibling `VerifyMintProof.execute()`, which only uses fixed, hardcoded offsets into a fixed-size buffer [5](#0-4) , `VerifyTransferProof` introduces variable offsets read from the payload itself without any bound checking against `data.length`, directly analogous to `cfg80211_is_element_inherited()` reading `elem->data[0]` without checking the element actually has that many bytes.

### Impact Explanation
A crafted `data` payload passed to the Sapling `VerifyTransferProof` precompile (reachable via any TVM contract that invokes this precompiled contract, e.g. through a Solidity call to the corresponding precompile address) can set `spendOffset`/`spendAuthSigOffset`/`receiveOffset` to arbitrary values, causing `parseInt`/`System.arraycopy` to read past the end of `data`. This throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`, which is caught by the generic `catch (Throwable any)` at the end of the method [6](#0-5) , so it degrades to returning a failure result rather than crashing the node outright. This limits impact compared to the kernel OOB read (no memory disclosure/crash), but it still represents a bounds-safety defect reachable from ordinary contract execution and energy is already spent for a call that does uncontrolled buffer indexing, worth hardening.

### Likelihood Explanation
High reachability: any account can deploy or call a contract that invokes this precompile with attacker-chosen `data`, no privileged role needed. The offset fields are the very first values read from `data` and are trivial to manipulate.

### Recommendation
Validate `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and the derived `spendCount`/`spendAuthSigCount`/`receiveCount` and all computed byte ranges) are within `[0, data.length)` and that every subsequent `arraycopy`/`parseInt`/`parseLong` access stays within `data.length` before performing the copy, returning the standard failure result (`Pair.of(true, DataWord.ZERO().getData())`) otherwise — mirroring the fix pattern in the CVE (bounds-check before dereferencing a length/offset value taken from untrusted data).

### Proof of Concept
Construct a `data` array of exactly one of the valid `SIZE` values (e.g. 2080 bytes) such that the first 4-byte-aligned field at offset 0 (`spendOffset`) is set to a large value (e.g. `Integer.MAX_VALUE - 100` or a small value causing `spendOffset + 320*spendCount` to exceed `data.length`). Deploy/call a contract that invokes this precompile with that payload; `parseInt(data, spendOffset)` at line 1492 or the `System.arraycopy` calls at lines 1514-1530 throw `ArrayIndexOutOfBoundsException`, demonstrating the unchecked offset-driven read.
