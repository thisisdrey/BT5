### Title
Unvalidated `cursor_depth` in `IncrementalMerkleVoucher` causes out-of-bounds array access / crash - ([File: chainbase/src/main/java/org/tron/common/zksnark/IncrementalMerkleTreeContainer.java])

### Summary
`IncrementalMerkleTreeContainer.EmptyMerkleRoots.emptyRoot(int depth)` indexes into a fixed-size `List<PedersenHashCapsule>` (`emptyRoots`, size `DEPTH+1 = 33`) with a caller-supplied `depth` value and performs no bounds validation, mirroring the ocfs2 `l_tree_depth` bug where an on-disk/attacker-controlled depth field is used to index an array without validation. [1](#0-0) 

### Finding Description
`IncrementalMerkleVoucher.cursor_depth` is an `int64` protobuf field fully controlled by an API caller building a shielded transaction: [2](#0-1) 

`IncrementalMerkleVoucherCapsule.getCursorDepth()` returns this raw value verbatim, with no validation on construction (`IncrementalMerkleVoucherCapsule(byte[] data)` just calls `parseFrom`): [3](#0-2) [4](#0-3) 

When a spend note's voucher is used to build the merkle path/root, `partialPath()` and `root()` pass this attacker-controlled `cursorDepth` straight into `IncrementalMerkleTreeContainer.root(depth, fillerHashes)`: [5](#0-4) [6](#0-5) 

Inside `root(depth, fillerHashes)`, the loop `while (d < depth) { ... filler.next(d) ... d++; }` runs with `d` growing unbounded up to the attacker-supplied `depth`: [7](#0-6) 

`PathFiller.next(depth)` falls back to `EmptyMerkleRoots.emptyRoot(depth)` whenever the filler queue is empty (which is true when the client supplies no/insufficient `filled`/uncle hashes): [8](#0-7) 

`emptyRoot(depth)` does `emptyRoots.get(depth)` unconditionally — since `emptyRoots` only has `DEPTH+1` (33) entries, any `depth >= 33` (trivially reachable since the caller controls `cursor_depth` up to `Long.MAX_VALUE`, or a negative value flowing into `.get()`) throws an unhandled `IndexOutOfBoundsException`: [9](#0-8) 

This is directly analogous to the ocfs2 CVE-2025-22079 pattern: a length/depth field originating from untrusted input (there: on-disk inode extent record `l_tree_depth`; here: a caller-supplied protobuf field `cursor_depth`) is used as an array/loop index without validating it against the maximum permissible depth (`OCFS2_MAX_PATH_DEPTH` there, `DEPTH` = 32 here).

### Impact Explanation
The entry point is `Wallet.createShieldedTransaction`, exposed via the HTTP servlet `CreateShieldedTransactionServlet` (and gRPC equivalents), which is an unauthenticated/anonymous API endpoint that merely builds an offline transaction from caller-supplied `PrivateParameters`, including raw `SpendNote.voucher` bytes: [10](#0-9) [11](#0-10) 

The caller can supply an arbitrary `IncrementalMerkleVoucher` (via `spendNote.getVoucher()`), including a malicious `cursor_depth` and an empty `cursor`/`filled` list, causing the unhandled `IndexOutOfBoundsException` deep inside the merkle root/path computation. Although the servlet wraps the whole call in a try/catch (`Util.processError`), the underlying issue demonstrates unvalidated attacker-controlled depth being used directly as an array index in core shielded-pool logic that is also invoked from other consensus-adjacent paths (e.g., `MerkleContainer`, `ZenTransactionBuilder.generateSpendProof`) where such unhandled exceptions are less consistently caught, risking a crash of the request-handling thread or of node logic that manipulates shielded pool state, and at minimum a reliable, unauthenticated crash/DoS of the shielded-transaction API path.

### Likelihood Explanation
High: the vulnerable field (`cursor_depth`) is directly settable by any client of the `CreateShieldedTransaction`/`CreateShieldedTransactionWithoutSpendAuthSig` HTTP or gRPC API without requiring any prior on-chain state or special privilege — the caller only needs to supply spending/viewing keys of their own note plus an arbitrary voucher blob, and setting `cursor_depth` to any value ≥ 33 (or negative, feeding a negative array index) reliably triggers the crash on the very first request.

### Recommendation
Validate `cursor_depth` (and any other externally-supplied depth values feeding tree/path computations) against the fixed `DEPTH` bound immediately when the `IncrementalMerkleVoucher`/`IncrementalMerkleTreeContainer` is constructed from external protobuf bytes, e.g. reject or clamp any `depth < 0 || depth > DEPTH` before it reaches `EmptyMerkleRoots.emptyRoot(int depth)`, and add an explicit bounds check inside `emptyRoot()` itself (`if (depth < 0 || depth >= emptyRoots.size()) throw new ZksnarkException(...)`) so it fails safely rather than throwing an unchecked `IndexOutOfBoundsException`.

### Proof of Concept
1. Craft a `PrivateParameters` JSON/protobuf payload for `CreateShieldedTransactionServlet` with a `shielded_spends[0].voucher` where:
   - `tree` and `cursor` are set to a minimally valid (or empty) tree so `cursorExist()` returns true (non-empty `cursor` tree),
   - `filled` list is empty,
   - `cursor_depth` is set to a large value, e.g. `1000` (or `Long.MAX_VALUE`).
2. POST this payload to `/wallet/createshieldedtransaction`.
3. Server-side call chain: `Wallet.createShieldedTransaction` → `builder.addSpend(..., voucherContainer)` → later root/path computation invokes `IncrementalMerkleVoucherContainer.partialPath()`/`root()` → `IncrementalMerkleTreeContainer.root(cursorDepth, ...)` → loop calls `PathFiller.next(d)` → `EmptyMerkleRoots.emptyRoot(d)` → `emptyRoots.get(d)` throws `IndexOutOfBoundsException` once `d` exceeds 32.
4. Observe the exception (crash trace) in server logs / error response, confirming out-of-bounds access triggered purely by the unauthenticated request payload.

  public static class EmptyMerkleRoots {

    @Setter
    @Getter
    private static EmptyMerkleRoots emptyMerkleRootsInstance = new EmptyMerkleRoots();
    private List<PedersenHashCapsule> emptyRoots = new ArrayList<>();

    public EmptyMerkleRoots() {
      try {
        emptyRoots.add(PedersenHashCapsule.uncommitted());
        for (int d = 1; d <= DEPTH; d++) {
          PedersenHash a = emptyRoots.get(d - 1).getInstance();
          PedersenHash b = emptyRoots.get(d - 1).getInstance();
          emptyRoots.add(PedersenHashCapsule.combine(a, b, d - 1));
        }
      } catch (ZksnarkException e) {
        logger.error("generate EmptyMerkleRoots error!", e);
      }
    }

    public PedersenHash emptyRoot(int depth) {
      return emptyRoots.get(depth).getInstance();
    }
  }
