### Title
Unauthenticated RecvError packet allows remote state poisoning / forced tunnel teardown - (File: outside.go)

### Summary
Nebula's `RecvError` control message is processed before any Noise handshake authentication or per-packet AEAD verification, and its only anti-spoofing check is a comparison of the received UDP source address against the last-known remote address for the referenced tunnel index. Both the `RemoteIndex` (carried in cleartext in every packet header) and, on many networks, the peer's UDP source address are observable/spoofable by an unauthenticated attacker. This lets an attacker force `handleRecvError` to close a legitimate tunnel and purge its handshake state, exactly mirroring the "Vow.flop" pattern in the external report: an unprivileged party manipulates externally-observable/forgeable state to repeatedly block or destroy a legitimate protocol operation.

### Finding Description
Incoming UDP packets are dispatched in `readOutsidePackets` before decryption or peer verification. The `header.RecvError` type is handled immediately, with no requirement that the sender hold a valid certificate or have completed a handshake: [1](#0-0) 

`handleRecvError` looks up the tunnel purely by the plaintext `RemoteIndex` field from the header and only performs a coarse source-address comparison before tearing the tunnel down: [2](#0-1) 

The `RemoteIndex` used to key this lookup is not secret — it is placed in the unencrypted header of every data packet sent on the wire (see the same field written for outgoing `Message` packets): [3](#0-2) 

`generateIndex` produces this value from `crypto/rand`, but because it travels in cleartext on every subsequent packet, an attacker in a position to observe traffic (or an off-path attacker who can spoof the victim's UDP source `AddrPort`) does not need to guess it — it can be captured directly from any legitimate packet exchanged between the two peers, analogous to how the Vow contract's flop precondition (`vat.dai(address(this)) == 0`) can be defeated by anyone who can observe pending transactions and race a cheap counter-transaction. [4](#0-3) 

The only defense in `handleRecvError` is:
```
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    ... "Someone spoofing recv_errors?" ...
    return
}
```
This defends against an attacker who does not know/spoof the peer's UDP source `AddrPort`, but UDP source addresses are trivially forgeable for an off-path attacker without a return-routability check, and for a path-adjacent/on-path attacker, both the index and the address are observable directly from the traffic being attacked.

### Impact Explanation
A successful spoof causes `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` to run, unilaterally destroying an established, authenticated tunnel and its pending-handshake bookkeeping. Repeating this whenever the target completes a handshake (racing the real traffic, exactly as "Eve" races `vow.flop` in the report) produces a persistent denial of service: the victim's tunnel to a peer never stabilizes, degrading or blocking legitimate communication — a direct analog of the report's "bad debt remains uncovered, confidence in Dai declines" outcome, here manifesting as repeated tunnel teardown / connectivity loss. This is a remote state-poisoning / DoS impact reachable by an attacker holding no CA-signed certificate.

### Likelihood Explanation
Likelihood is moderate-to-high in the on-path/observing-attacker case (e.g., a network intermediary, a compromised router, or anyone able to sniff UDP traffic between the two Nebula nodes) since both required fields (`RemoteIndex`, source `AddrPort`) are visible in plaintext. For a fully off-path/blind attacker, exploitation additionally depends on the ability to spoof UDP source addresses on the path to the victim, which is possible on many networks lacking egress/ingress filtering (BCP38), and on both endpoints' `accept_recv_error`/`send_recv_error` allow-list configuration (`acceptRecvErrorConfig.ShouldRecvError`) not excluding the attacker's claimed source. The 1.9.7 changelog entry that disabled *sending* `recv_error` outside the counter window (#1459) shows this control channel has already been a source of hardening work, but the accept path's authentication is still limited to a source-address match rather than any cryptographic binding.

### Recommendation
- Require the `RecvError` message to be authenticated/bound to the encrypted session (e.g., protect it with the established transport key, or require it to reference a valid, recently-observed message counter within the replay window) rather than trusting a bare index + UDP source-address match.
- Rate-limit and log repeated `RecvError`-triggered teardown per remote index/address so a single forged packet cannot be immediately effective, and consider requiring corroborating signal (e.g., a subsequent failed handshake attempt) before tearing down an active tunnel.
- Treat `handleRecvError`'s address check as a heuristic only, not a security boundary, and document the residual DoS risk in threat-model docs.

### Proof of Concept
1. Attacker observes (via sniffing, or by being on-path) a `Message` packet exchanged between Nebula peers A and B; extracts the cleartext `RemoteIndex` field from the header (`header.Encode(..., hostinfo.remoteIndexId, c)`), and notes B's UDP `AddrPort`.
2. Attacker crafts a `RecvError` packet: `header.Encode(buf, header.Version, header.RecvError, 0, <captured RemoteIndex>, 0)`.
3. Attacker sends this packet to A, spoofing the source `AddrPort` as B's address (or, if on-path, simply forwards/injects it).
4. `readOutsidePackets` on A routes it directly to `f.handleRecvError` without any handshake/authentication check; `hostinfo.GetRemote() == addr` matches, so A calls `closeTunnel` and `DeleteHostInfo`, destroying the legitimate tunnel to B.
5. Repeating this whenever A and B attempt to re-handshake prevents the tunnel from ever stabilizing, achieving persistent denial of service — directly analogous to Eve repeatedly blocking `vow.flop` in the external report.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```

```go
func generateIndex(l *slog.Logger) (uint32, error) {
	b := make([]byte, 4)

	// Let zero mean we don't know the ID, so don't generate zero
	var index uint32
	for index == 0 {
		_, err := rand.Read(b)
		if err != nil {
			l.Error("Failed to generate index", "error", err)
			return 0, err
		}

		index = binary.BigEndian.Uint32(b)
	}

	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("Generated index", "index", index)
	}
	return index, nil
}
```
