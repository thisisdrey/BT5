### Title
`storage_deposit` outcome is never checked or refunded in `do_ft_withdraw`, permanently stranding the wNEAR spent on it - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`do_ft_withdraw` only gates on the result of `near_withdraw` (`promise_result_checked_void(0)`) before scheduling `storage_deposit`, but never inspects or reacts to the `storage_deposit` promise's own outcome. `ft_resolve_withdraw` subsequently only re-credits `sender_id` for the `token`/`amount` leg (via `ft_transfer`/`ft_transfer_call` result), leaving no code path to refund the wNEAR that was converted to raw NEAR and consumed/refunded by a failing or no-op `storage_deposit` call.

### Finding Description
The broken binding is:
`owner_balance_debited(wNEAR, storage_deposit_amount)` == `NEAR actually consumed by a successful storage_deposit()` + `NEAR re-credited to owner on storage_deposit failure/refund`

In `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:60-74`), `self.withdraw` immediately debits the owner's wNEAR balance for `storage_deposit.amount` before any promise executes. This wNEAR is unwrapped to raw NEAR via `ext_wnear::near_withdraw` (`withdraw.rs:78-94`), then in `do_ft_withdraw` (`withdraw.rs:118-151`):

```
require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed");
ext_storage_management::ext(withdraw.token)
    .with_attached_deposit(storage_deposit)
    ...
    .storage_deposit(Some(withdraw.receiver_id.clone()), None)
```

Only index `0` (`near_withdraw`) is checked. The `storage_deposit` promise `p` is passed straight into `ext_ft_core::ext_on(p)` to schedule `ft_transfer`/`ft_transfer_call`, and NEAR's `.then()` combinator executes the next action unconditionally regardless of whether `p` succeeded, refunded, or failed. `ft_resolve_withdraw` (`withdraw.rs:157-194`) then checks only promise index `0` there (which is the `ft_transfer`/`ft_transfer_call` result, a *different* promise index in that callback context) and computes `refund` solely from the token/amount leg — there is no logic anywhere that inspects the `storage_deposit` promise result or credits the owner back the wNEAR-derived NEAR if `storage_deposit` fails, partially refunds, or is a no-op (e.g., NEP-145 requires refunding the deposit when the account is already registered and `registration_only` is not needed).

Any owner withdrawing with a non-zero `storage_deposit` amount to a `receiver_id` that is already registered on `token`, or to a token contract whose `storage_deposit` reverts/refunds, triggers this: the wNEAR is irrevocably debited from the owner's ledger balance, converted to NEAR, sent out, and — on failure/refund — returned as a bare NEAR transfer to the Defuse contract's account with no ledger entry crediting any user. The existing `require!` guard only prevents proceeding when `near_withdraw` itself fails; it provides no protection for `storage_deposit`'s own outcome.

### Impact Explanation
The owner's wNEAR balance is permanently reduced by `storage_deposit` amount whenever the corresponding `storage_deposit` call on the target token fails or is refunded (e.g., already-registered `receiver_id`), with no matching credit to any account in the Defuse ledger. This is a real, repeatable loss of user funds: any owner can trigger it against any token whose `receiver_id` is already storage-registered (an extremely common, benign scenario, not even requiring malicious behavior from the token contract). It matches the "Critical — user funds permanently frozen" category since value leaves the Verifier's own accounting without any owner ever being credited for it.

### Likelihood Explanation
This requires no privileged role and no attacker-controlled malicious token contract — it can be triggered unintentionally by any ordinary withdrawal where `storage_deposit` is supplied but `receiver_id` is already registered on `token` (the normal NEP-145 refund path), or intentionally by an attacker picking such a `receiver_id`/`token` pair to guarantee the wNEAR is unaccounted for. It is fully repeatable per withdrawal call and scales with however much `storage_deposit` NEAR the withdrawer attaches each time.

### Recommendation
Chain a `storage_deposit` outcome check (and refund path) analogous to the `near_withdraw` check: inspect `storage_deposit`'s own promise result inside `do_ft_withdraw` or a dedicated resolver, and on failure/refund, re-credit the owner for the unconsumed wNEAR (converting the refunded/failed NEAR back to wNEAR, or crediting an equivalent ledger amount) instead of proceeding silently into `ft_transfer`/`ft_transfer_call`.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy Defuse contract and a NEP-141 token implementing NEP-145 `storage_deposit`, with `receiver_id` pre-registered on `token`.
2. Owner deposits wNEAR and `token` balances into Defuse; record owner's wNEAR ledger balance `B0`.
3. Call `ft_withdraw` with `storage_deposit: Some(amount)` and `receiver_id` = the already-registered account.
4. Await promise resolution; assert `storage_deposit` on `token` returns `used_bytes = 0` / refunds the attached deposit (per NEP-145 spec for already-registered accounts).
5. Assert owner's post-withdrawal wNEAR ledger balance is `B0 - amount` (funds gone) while the Defuse contract's actual NEAR account balance increased by the refunded `amount` with no corresponding ledger credit to any account — proving `sum(all ledger balances)` no longer nets to the contract's real custodied value, i.e., the wNEAR is permanently lost from the owner's perspective.
