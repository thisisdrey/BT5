## Finding

### Title
Silent loss of ERC20 asset value when multiple ERC20-matched assets are deposited in a single XCM `DepositAsset` — `ERC20Transactor::deposit_asset_with_surplus` drops all but the first asset - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor`, the `TransactAsset` implementation that lets Asset Hub route XCM `WithdrawAsset`/`DepositAsset` to arbitrary `pallet-revive` ERC20 contracts, only ever transacts the **first** fungible asset out of the `AssetsInHolding` it receives in `deposit_asset_with_surplus`. Any additional matched ERC20 assets bundled in the same holding are consumed (moved into the function) and then dropped without being credited to the beneficiary or returned to the caller — they are permanently lost.

### Finding Description
The XCM executor's `DepositAsset` instruction filters the holding register and calls `TransactAsset::deposit_asset`/`deposit_asset_with_surplus` once with all assets that match a given transactor (per [1](#0-0) , `TransactAsset` deals with `AssetsInHolding`, a plural collection, not a single asset).

`ERC20Transactor::deposit_asset_with_surplus` only inspects the first fungible asset it finds: [2](#0-1) 

The function's own doc comment admits the flaw: *"This implementation only handles a single fungible asset at a time... If multiple assets are present, only the first fungible asset will be deposited and the rest will be silently ignored."* The only safeguard is `defensive_assert!(what.len() == 1, ...)`, which is a no-op in production builds and does not return an error — it never prevents the code path from executing.

On the success path, the function returns only `Ok(surplus)`: [3](#0-2) 

`what: AssetsInHolding` is consumed by value and is not returned or otherwise reintroduced into the executor's holding register on success. Any assets besides the one matched by `Matcher::matches_fungibles(&asset)` (the single item picked via `.fungible_assets_iter().next()`) are simply dropped when the function returns, i.e. burned from the holding with no corresponding on-chain ERC20 transfer and no beneficiary credit.

### Impact Explanation
An unprivileged, signed account can trigger this via `pallet_xcm::execute` (exactly as exercised by the existing local tests `withdraw_and_deposit_erc20s`, `non_existent_erc20_will_error`, etc. in [4](#0-3) ), by constructing an XCM program that:
1. Withdraws two or more distinct ERC20 assets (each matched by `IsLocalAccountKey20`/the ERC20 matcher) into holding via `withdraw_asset` (each individually and correctly debited from the sender's ERC20 balance through `withdraw_asset_with_surplus`).
2. Issues a single `DepositAsset` with a wildcard/`AllCounted(n>=2)` filter that causes the executor to hand all matched ERC20 assets to `ERC20Transactor::deposit_asset_with_surplus` in one call.

Only the first asset is actually transferred to the beneficiary contract; the rest are silently discarded from the holding with `Ok(surplus)` returned, so the XCM instruction reports success. The sender's on-chain ERC20 balance was already reduced for every withdrawn asset, but the beneficiary only receives one of them — the remaining value is permanently and unrecoverably lost (no error, no revert, no refund path), violating the value-conservation invariant ("Balances, assets, ... must conserve value and settle exactly once to the rightful beneficiary and amount").

### Likelihood Explanation
High for any deployment that enables this transactor with more than one ERC20 asset class reachable in the same `Assets`/`AssetFilter` combination (which the PR introducing this transactor explicitly targets — Asset Hub Westend, per `prdoc/stable2506/pr_7762.prdoc`). No governance, admin, relayer, or validator collusion is required — a normal signed user assembling an XCM program with two ERC20 withdraws followed by one combined deposit is sufficient. The guard that exists (`defensive_assert!`) does not stop production execution, only flags misuse in test/debug configurations.

### Recommendation
Make `ERC20Transactor::deposit_asset_with_surplus` (and the analogous withdraw path, if it can ever receive multiple assets) iterate over **all** fungible assets in `what`, transacting each one, aggregating surplus, and returning an error (with the untransacted remainder reinstated) if any individual leg fails, instead of silently truncating to the first entry. Alternatively, if the transactor is fundamentally single-asset, it must return an explicit `Err` (not `Ok`) when `what.len() != 1`, and callers/executor config must guarantee at most one matched asset per invocation — never rely on a `defensive_assert!` for correctness.

### Proof of Concept
1. Deploy two ERC20 contracts (`erc20_a`, `erc20_b`) on Asset Hub via `pallet_revive`, as done in `withdraw_and_deposit_erc20s`.
2. Fund `sender` with both tokens.
3. Build and execute (via `PolkadotXcm::execute`, signed by `sender`) an XCM program:
   - `WithdrawAsset((AccountKey20{erc20_a}, amount_a))`
   - `WithdrawAsset((AccountKey20{erc20_b}, amount_b))`
   - `DepositAsset(AllCounted(2), beneficiary)` — matching both ERC20 assets into a single holding passed to `ERC20Transactor::deposit_asset_with_surplus`.
4. Observe: `PolkadotXcm::execute` returns `Ok`, `sender`'s balance for both `erc20_a` and `erc20_b` is reduced, but `beneficiary` only receives one of the two tokens (whichever is returned first by `fungible_assets_iter().next()`); the other token's value is unaccounted for anywhere on-chain.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
