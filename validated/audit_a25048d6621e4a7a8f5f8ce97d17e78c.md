### Title
Attacker-controlled `Payload.Time` used unauthenticated in `CheckAndComplete` hijack check enables tunnel-takeover replay — ([File: handshake_manager.go])

### Summary
`HostInfo.lastHandshakeTime` is populated directly from the peer-supplied, unauthenticated `Payload.Time` field carried in the handshake payload [1](#0-0) . This value is then used as the sole discriminator in `CheckAndComplete` to decide whether a newly-arriving handshake should be allowed to replace ("Taking new handshake") an already-established tunnel for the same VPN address [2](#0-1) . Because the comparison trusts a value the peer fully controls (like the RocketJoe pattern of trusting an externally-influenced value instead of internally tracked state), an attacker who already holds a valid handshake credential for a given identity can force a stale/duplicate handshake to be treated as "newer" and used to supersede an existing hostinfo, without any additional protocol-level check tying `Time` to actual elapsed wall-clock progress.

### Finding Description
In `handshake/machine.go`, the wire payload's `Time` field (`fieldTime`, proto field 5) is attacker-supplied and only range/type-checked, never validated against local time or a monotonic per-peer counter [3](#0-2) . On processing, `m.result.HandshakeTime = payload.Time` is set unconditionally from that wire value [1](#0-0) .

`beginHandshake` and `continueHandshake` copy this attacker-controlled value straight into `HostInfo.lastHandshakeTime` [4](#0-3) [5](#0-4) , with no server-side timestamp cross-check.

`CheckAndComplete` then uses this value to gate whether an incoming handshake is allowed to take over an existing, live main-hostmap entry for the same vpn address:
```go
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}
existingHostInfo.logger(hm.l).Info("Taking new handshake")
``` [6](#0-5) 

Because `hostinfo.lastHandshakeTime` is taken verbatim from a field the remote peer fully controls at payload-marshal time (`p.Time = uint64(time.Now().UnixNano())` on the sender's local clock [7](#0-6) , with nothing preventing a modified client from sending an arbitrary future value), the comparison `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` is not an authenticated freshness guarantee — it's exactly the RocketJoe class of bug: relying on an externally influenceable quantity in place of internally tracked, trust-boundary-respecting state (there, `joe.balanceOf(address(this))`; here, the peer-chosen `Payload.Time`).

### Impact Explanation
A peer who can complete a valid, cert-authenticated handshake (any legitimate credential holder for that identity, e.g., a compromised/duplicated key, or the legitimate peer replaying/racing handshakes) can manufacture `Payload.Time` values to always win the `>=` comparison, forcing `CheckAndComplete` to accept a new handshake as authoritative and evict/replace the active `ConnectionState` for an existing tunnel (`existingHostInfo.logger(hm.l).Info("Taking new handshake")` path). This can be used to force spurious tunnel replacement/state churn for an existing session, since the "is this handshake newer" decision is not tied to any value nebula itself tracks or authenticates independent of the peer's say-so.

### Likelihood Explanation
Reaching this path requires only that the attacker complete a normal, certificate-authenticated handshake against `beginHandshake`/`continueHandshake` — this is squarely within the "no CA-signed certificate needed to reach the code, but cert-holder abuse of protocol logic" class explicitly permitted by the rules (packet/handshake-authentication logic), since the vulnerable comparison itself is in the handshake-authentication/session-establishment logic, not gated behind any additional secret. The `Time` field has no validation against local clocks or a per-hostinfo monotonic counter anywhere in `unmarshalPayloadDetails` [3](#0-2)  or in `processPayload` [1](#0-0) , so likelihood of triggering the miscomparison is high whenever an attacker races or replays handshake completion.

### Recommendation
Do not use the peer-supplied `Payload.Time` as the sole ordering key for tunnel-takeover decisions in `CheckAndComplete`. Track handshake completion order using a value the local node fully controls and cannot be influenced by the remote (e.g., a monotonically increasing local sequence/generation counter assigned when the hostinfo is created, or `time.Now()` recorded locally at completion), analogous to the RocketJoe fix of tracking actual deposits in local storage instead of trusting `balanceOf`. If `Payload.Time` must remain for logging/diagnostics, it should not be part of the security-relevant `>=` gate in `handshake_manager.go`.

### Proof of Concept
1. Establish a normal tunnel between attacker-controlled node A (holding a valid signed cert) and victim node B, completing a handshake so B has `existingHostInfo.lastHandshakeTime = T0` (attacker-chosen value sent in msg1/msg2 `Payload.Time`).
2. From A, initiate a second handshake (new `HandshakeHostInfo`/Machine) to B for the same identity, this time crafting the outgoing payload's `Time` field to an arbitrary larger value `T1 > T0` (a custom client can set this arbitrarily; the stock implementation uses `time.Now().UnixNano()` but nothing enforces this on the wire) [7](#0-6) .
3. B's `beginHandshake` processes the new handshake, sets `hostinfo.lastHandshakeTime = T1` [4](#0-3) , and calls `CheckAndComplete`.
4. Because `T0 >= T1` is false, B logs `"Taking new handshake"` and replaces the existing hostinfo/`ConnectionState` [6](#0-5) , even though the "new" handshake carries no proof of being causally later than the original — purely because the attacker chose a larger `Time` value in the payload.
