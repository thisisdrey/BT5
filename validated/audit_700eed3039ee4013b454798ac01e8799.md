### Title
Unauthenticated, spoofable IP-based TXT-query gate allows hostMap certificate enumeration via `QueryCert` - ([File: dns_server.go])

### Summary
The DNS TXT-query authorization check `isSelfNebulaOrLocalhost` in `dns_server.go` validates the caller only by inspecting the raw OS-level UDP source address of the incoming packet — it never checks a cryptographic (Noise handshake) identity. Once that check passes, `QueryCert` accepts an arbitrary caller-supplied VPN address string with no relation to the caller's own identity and returns the full peer certificate for any address the lighthouse's `hostMap` has ever handshaked with, enabling systematic certificate enumeration.

### Finding Description
`handleDnsRequest` → `parseQuery` gates TXT queries with: [1](#0-0) 
and the gate itself is purely IP-address based: [2](#0-1) 
`isSelfNebulaOrLocalhost` only checks `w.RemoteAddr().String()` — the source address field of the received UDP packet — against loopback or the local certificate's own `myVpnAddrsTable`. This is not a cryptographic authentication check; it never verifies a Noise handshake, session key, or any signed identity. Nebula's DNS listener is a plain OS-level UDP socket (`Net: "udp"`) bound to `lighthouse.dns.host:lighthouse.dns.port`: [3](#0-2) 
`getDnsServerAddr` defaults `dnsHost` to `""`, which resolves to a wildcard bind (`:53`) unless explicitly configured to a tun-only address: [4](#0-3) 
If bound to a wildcard or otherwise routable address, this socket is reachable by packets that never traversed the encrypted Nebula overlay tunnel at all — plain UDP has no source-address integrity, so any attacker capable of forging (or, on a shared broadcast segment/VPC, actually possessing) a source IP that is loopback or matches the lighthouse's own certified addresses can satisfy the gate.

Once past the gate, `QueryCert` takes the DNS query name (an arbitrary attacker-chosen string) and looks it up directly in `d.hostMap`, independent of whatever identity satisfied the outer gate: [5](#0-4) 
`hostMap.QueryVpnAddr` returns any hostinfo the lighthouse has previously handshaked with, and its certificate is serialized and returned verbatim. There is no binding between "who is asking" (checked by the gate) and "what is being asked about" (the `data` parameter) — the invariant that only the peer whose identity was cryptographically proven may read its own hostmap-derived state is not enforced; the gate is coarse-grained ("is this loopback/self") while the query itself is peer-address-parameterized and unrestricted.

### Impact Explanation
An attacker satisfying the IP-based gate can iterate VPN address strings through `QueryCert` and harvest every peer certificate (name, VPN addresses, groups, issuer, validity) currently known to the lighthouse's `hostMap`. This is metadata useful for planning targeted roaming/relay spoofing or social-engineering against specific hosts, matching a mass information-disclosure impact rather than key/traffic compromise — no decryption, forgery, or handshake bypass results directly from this bug.

### Likelihood Explanation
Exploitability is conditional and not universally reachable:
- TXT queries must be enabled (`serve_dns` + `am_lighthouse` true), which is opt-in.
- The DNS socket must be reachable by packets whose spoofed/forged source address can pass the `isSelfNebulaOrLocalhost` check. Loopback-sourced packets arriving from a non-loopback interface are typically dropped by the OS as martian packets on most kernels, and blind UDP source spoofing on the open internet is frequently blocked by network ingress/egress (BCP38) filtering, and even when unfiltered, the attacker would not see the response unless on-path or the spoofed address is one they control.
- If `lighthouse.dns.host` is left at its default (wildcard bind), the exposure surface is real; if bound explicitly to a tun-only address, this listener is only reachable through addresses that are themselves gated by OS routing to the tun device.

Given these preconditions, the design flaw (identity check decoupled from query scope, and identity check being non-cryptographic) is real and independently exploitable wherever source-address spoofing or shared-segment address reuse is feasible (e.g., same LAN/VPC as the lighthouse, or unfiltered upstream networks) — but the requirement for a spoofable/forgeable network path meaningfully limits likelihood outside of certain deployments.

### Recommendation
Do not authorize TXT/`QueryCert` responses based on the OS-level socket source address. Either (a) restrict the TXT/QueryCert responder to loopback only, removing the `myVpnAddrsTable` branch entirely so no remote address is ever considered "trusted," or (b) require the caller to prove possession of a real Nebula-authenticated identity (e.g., only serve `QueryCert` over a path that has already passed Nebula's handshake/AEAD verification, not the raw OS UDP listener), and additionally scope `QueryCert` results so a caller can only ever retrieve records related to its own proven identity rather than arbitrary hostMap entries.

### Proof of Concept
Unit/integration test plan for `dns_server_test.go`:
1. Construct a `dnsServer` with a `hostMap` populated with several fake `HostInfo` entries (distinct VPN addresses/certs), and a `certState` with `myVpnAddrsTable` containing address `A`.
2. Simulate `parseQuery`/`handleDnsRequest` with a `dns.ResponseWriter` whose `RemoteAddr()` returns a UDP address equal to `A` (the lighthouse's own address) — i.e., a "spoofed" caller identity that isn't cryptographically the lighthouse itself.
3. Send TXT queries iterating through the VPN addresses of the other (non-self) `HostInfo` entries in `hostMap`.
4. Assert that `QueryCert` returns certificate JSON for peers unrelated to the calling identity, demonstrating that passing the IP-based gate (rather than a handshake-proven identity) is sufficient to enumerate arbitrary hostMap entries — i.e., assert this is true `m.Answer` non-empty for each iterated peer address, confirming the responder serves cert JSON to a caller whose identity wasn't proven by handshake.

func (d *dnsServer) QueryCert(data string) string {
	if len(data) < 2 {
		return ""
	}
	ip, err := netip.ParseAddr(data[:len(data)-1])
	if err != nil {
		return ""
	}

	// The hostmap only ever contains peers we have handshaked with, so it never carries an entry for ourselves.
	// Answer self lookups straight from the local cert state.
	if cs := d.certState(); cs != nil && cs.myVpnAddrsTable != nil && cs.myVpnAddrsTable.Contains(ip) {
		c := cs.GetDefaultCertificate()
		if c == nil {
			return ""
		}
		b, err := c.MarshalJSON()
		if err != nil {
			return ""
		}
		return string(b)
	}

	hostinfo := d.hostMap.QueryVpnAddr(ip)
	if hostinfo == nil {
		return ""
	}

	q := hostinfo.GetCert()
	if q == nil {
		return ""
	}

	b, err := q.Certificate.MarshalJSON()
	if err != nil {
		return ""
	}
	return string(b)
}

func (d *dnsServer) isSelfNebulaOrLocalhost(addr string) bool {
	a, _, _ := net.SplitHostPort(addr)
	b, err := netip.ParseAddr(a)
	if err != nil {
		return false
	}

	if b.IsLoopback() {
		return true
	}

	cs := d.certState()
	if cs == nil || cs.myVpnAddrsTable == nil {
		return false
	}
	//if we found it in this table, it's good
	return cs.myVpnAddrsTable.Contains(b)
}

func getDnsServerAddr(c *config.C) string {
	dnsHost := strings.TrimSpace(c.GetString("lighthouse.dns.host", ""))
	// Old guidance was to provide the literal `[::]` in `lighthouse.dns.host` but that won't resolve.
	if dnsHost == "[::]" {
		dnsHost = "::"
	}
	return net.JoinHostPort(dnsHost, strconv.Itoa(c.GetInt("lighthouse.dns.port", 53)))
}
