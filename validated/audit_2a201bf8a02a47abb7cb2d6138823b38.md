### Title
Malicious peer can monopolize `AttachmentRequest` retries via `ReliabilityReport::score()`, causing an on-chain-committed attachment's batch to be dropped without ever trying the honest source - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentRequest::get_url()` always selects a single peer — the one with the highest `ReliabilityReport::score()` — out of `sources`, rather than trying all sources for a given `content_hash`. Because `score()` is dominated by the total number of requests sent (`+ n`) rather than the success ratio, a peer that is repeatedly tried and repeatedly fails/serves bad data can end up with a *higher* score than an honest peer that has never been tried, causing the malicious peer to be re-selected every retry round while the honest peer is starved out until `max_attachment_retry_count` is hit and the batch is dropped.

### Finding Description
The claimed equality `dropped_permanently == exhausted_all_known_peer_sources_for_this_hash` is broken. For a given `content_hash`, `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds one `AttachmentRequest` per hash containing *all* peer URLs that advertise the attachment in their inventory in `sources: HashMap<UrlString, ReliabilityReport>` [1](#0-0) . However, `Requestable::get_url()` for `AttachmentRequest` only ever returns the single most "reliable" source: [2](#0-1) 

Only that one URL is used to build/dispatch the actual HTTP request in `BatchedRequestsState::try_proceed` (`PeerNetwork::begin_request` is invoked with the single `Requestable`), so only one of possibly several honest+malicious sources is contacted per retry round for that hash.

`extend_with_attachments` records the outcome (decode failure or fetch failure) against that peer's `ReliabilityReport` via `bump_failed_requests` [3](#0-2) .

The selection of "most reliable" uses `ReliabilityReport::score()`: [4](#0-3) 

This formula is `success/n + n` (with integer-truncated division). The `+ n` term dominates: an untried honest peer has `n=0 → score=0`, while a malicious peer that has been tried even once and failed has `n=1, success=0 → score=1`, which is *already higher* than the untried honest peer. Each subsequent failed attempt against the malicious peer further increases `n` and thus its score, since the additive `n` term outweighs the bounded `success/n ≤ 1` term. Because `get_most_reliable_source` (used both for `get_url()` dispatch and for `Ord`/priority-queue comparisons via `AttachmentRequest::cmp`) picks by `max_by_key(score)`, the malicious peer that is progressively "punished" by real failures paradoxically becomes and remains the preferred/selected source across retries, while the honest peer is never contacted.

Each retry round, `AttachmentsBatch::bump_retry_count` increments `retry_count` and computes a bounded backoff delay (`MAX_RETRY_DELAY = 600`) [5](#0-4) . When `retry_count >= max_attachment_retry_count`, the batch is dropped permanently and never re-enqueued: [6](#0-5) 

There is no logic anywhere in `download.rs` that removes/deprioritizes a source that has failed within the same `AttachmentRequest`/round, nor forces trying a different peer on the next retry — the same `sources` map (rebuilt fresh from inventories each round, still containing both peers) is re-evaluated by the same flawed `score()`, so the same malicious peer is likely to win again.

### Impact Explanation
An attacker running a single peer that is included in `AttachmentRequest.sources` for a target `content_hash` (e.g., because it is one of the outbound peers with an advertised inventory bit set for that page/index) can, by always returning HTTP 200 with an undecodable body or a body that fails `decode_atlas_get_attachment`, cause its own `ReliabilityReport.score()` to rise with each failed attempt while the honest peer's score remains at the default `0`. This steers `get_most_reliable_source()`/`get_url()` toward the malicious peer on every subsequent retry, so the honest peer is starved of exposure. After `max_attachment_retry_count` retries, the batch is dropped ("Atlas: dropping batch ... retries count exceeded") even though an honest peer's inventory advertises and could have served the valid attachment. This matches "High: serving/steering behavior causing an attachment whose hash is on-chain committed to be permanently deemed unresolvable," since the node never resolves an attachment that other honest peers could have supplied.

### Likelihood Explanation
Preconditions: the attacker must run an outbound-connectable peer that the victim node syncs with, and must be one of (ideally with priority over) the sources listed for the target attachment's `content_hash` in `AttachmentRequest.sources` (i.e., its self-reported/actual inventory bit for that hash must be set — the attacker fully controls this, since it is their own attachments-inv response). No secret/privileged role is required — the attacker just needs to run a normal peer with an outbound URL and respond to `/v2/attachments/inv` and `/v2/attachments/<hash>` GET requests. The attack is fully repeatable across retry rounds and does not require volumetric traffic, only correctly-timed HTTP 200 responses with bad content. The main uncertainty is HashMap-iteration-order tie-breaking when scores are equal in the very first attempt (Rust `HashMap` iteration order is randomized per run but deterministic within a run), meaning the malicious peer may not always win the very first selection, but once it has been tried even once, its score advantage over an untried honest peer (`score=1` vs `score=0`) persists and compounds, per the `score()` formula.

### Recommendation
Fix `ReliabilityReport::score()` so failures do not increase apparent reliability — e.g., use `success_ratio` directly (not `success/n + n`) or add a penalty term for failures, and ensure ties/never-tried peers are not penalized relative to peers with a track record of failures. Additionally, within a single `AttachmentRequest`/retry round, when the selected source fails, try the next-best source from `sources` before exhausting the retry budget, rather than relying solely on the batch-level retry loop which reuses the same (broken) selection logic. Consider excluding/deprioritizing a source for a given `content_hash` after a decode/hash-mismatch failure specific to that hash, distinct from generic connectivity failures.

### Proof of Concept
Rust net test plan (to be placed in `stackslib/src/net/atlas/tests.rs`):
1. Construct an `AttachmentsBatchStateContext` with two peers, `malicious_url` and `honest_url`, both inserted into `context.peers` with `ReliabilityReport::empty()`.
2. Build one `AttachmentRequest` for a target `content_hash` with `sources` containing both peer URLs and equal (empty) reports — mirror `get_prioritized_attachments_requests`.
3. Simulate `connection_options.max_attachment_retry_count` retry rounds: each round, call `request.get_most_reliable_source()` to determine which peer is "selected", assert it equals `malicious_url` (or track after round 1 that it stays malicious), then call `context.extend_with_attachments` with a `BatchedRequestsResult` whose `succeeded` entry for that request has a `StacksHttpResponse` that fails `decode_atlas_get_attachment` (e.g., malformed body), verifying `report.bump_failed_requests()` is invoked and `report.score()` increases.
4. After `max_attachment_retry_count` rounds, call `AttachmentsBatch::bump_retry_count` repeatedly and assert `retry_count >= max_attachment_retry_count`, confirming the batch would be dropped per the `Atlas::run` logic at [6](#0-5) .
5. Assert that `honest_url`'s `ReliabilityReport.total_requests_sent == 0` at the point the batch is dropped, proving the honest source was never contacted despite being present in `sources` for every round — i.e., `dropped_permanently == true` while `exhausted_all_known_peer_sources_for_this_hash == false`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

                self.attachments.insert(response.attachment);
                report.bump_successful_requests();

                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

    }

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }

    pub fn bump_retry_count(&mut self) {
        self.retry_count += 1;
        let delay = cmp::min(
            MAX_RETRY_DELAY,
            2u64.saturating_pow(self.retry_count as u32).saturating_add(
                thread_rng().gen::<u64>() % 2u64.saturating_pow((self.retry_count - 1) as u32),
            ),
        );

        debug!("Atlas: Re-attempt download in {} seconds", delay);
        self.retry_deadline = get_epoch_time_secs() + delay;
    }
