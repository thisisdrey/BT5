### Title
Attacker can fill a victim's deposit-token account list via dust `onBehalfOf` deposits, permanently blocking the victim's deposits and incoming transfers - (File: contracts/DepositToken.sol)

### Summary
The Undertow advisory is an uncontrolled-resource-consumption DoS: attacker-supplied input exhausts a bounded server resource, denying service. The Metronome analog is the per-account deposit-token list in `Pool`. `DepositToken._mint` and `DepositToken._transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance was previously zero, and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the account holds `MAX_TOKENS_PER_USER` entries. Because `DepositToken.deposit(uint256, address onBehalfOf_)` is a public, permissionless entry point that mints to an arbitrary `onBehalfOf_`, an attacker can deposit dust amounts of every listed collateral on behalf of a victim, filling the victim's list. Any subsequent deposit to the victim for a token not already in the list (including the victim's own deposits and any incoming `transfer`/`seize`) reverts.

### Finding Description
- `DepositToken.deposit` accepts an arbitrary beneficiary: `deposit(uint256 amount_, address onBehalfOf_)` only rejects `onBehalfOf_ == address(0)` and the treasury; there is no opt-in or allowance requirement (contracts/DepositToken.sol:211-237).
- `_mint` registers the token on the account when `_balanceBefore == 0 && amount_ > 0` via `pool.addToDepositTokensOfAccount(account_)` (contracts/DepositToken.sol:486-488).
- `_transfer` does the same for recipients (contracts/DepositToken.sol:518-520), so plain `transfer` of a dust amount to the victim also consumes a slot.
- `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` and reverts `UserReachedMaxTokens` when the list is full (confirmed by the revert test in test/Pool.test.ts:1517-1520).
- Removal only happens when a balance returns exactly to zero (contracts/DepositToken.sol:460-462, 523-525), which is under the attacker's control for the dust positions — the attacker simply never withdraws, so the slots stay occupied permanently.
- Because the revert propagates through `_mint`/`_transfer`, the attacker's `deposit` call cannot be split so as to avoid the revert: the whole deposit reverts only once the cap is hit, i.e., exactly at the attacker's desired cutoff.

Invariant broken: liveness. The victim's ability to open new collateral positions (and to receive msdTOKEN transfers, including liquidation `seize` payouts directed at them) is revoked at zero ongoing cost.

### Impact Explanation
Denial of service against a targeted account:

- The victim cannot deposit any collateral token that is not already in their `depositTokensOfAccount` list — every such `deposit` and `transfer` to them reverts with `UserReachedMaxTokens`. This is a temporary-to-permanent freezing of deposit/transfer functionality for that account, persisting as long as the attacker keeps dust balances.
- Existing balances are not frozen (withdrawals reduce balances and do not add list entries), so impact is limited to blocking new positions/incoming transfers — this matches the "temporary freezing of funds" acceptance class rather than theft or insolvency.
- Cost to the attacker is bounded and tiny: one dust deposit per pool collateral type (the pool has a small, fixed set of deposit tokens), plus the dust is recoverable later.

### Likelihood Explanation
- Fully permissionless: `deposit` is `whenNotPaused`, `nonReentrant`, with no beneficiary whitelist; any EOA can specify any `onBehalfOf_`.
- No privileged role, oracle manipulation, or governance action needed; only requires the victim to not already hold every deposit-token type (the common case).
- Deterministic and cheap; works on the deployed configuration (the `MAX_TOKENS_PER_USER` cap and revert behavior are exercised in the unit test suite).

### Recommendation
Do not let an attacker populate a victim's list without consent. Options:

- Only add to `depositTokensOfAccount` inside `_mint` when `account_ == _msgSender()` (or when `account_` has opted in), and for `_transfer` require explicit recipient registration; or
- Make `addToDepositTokensOfAccount` fail-soft: if the list is full, skip adding instead of reverting, and make `debtPositionOf`/`depositOf` iterate `balanceOf` independently of the list; or
- Allow anyone to call a `removeDustEntries(account)` that deletes entries whose balance is below a threshold, so the victim can clear slots without the attacker's cooperation.

### Proof of Concept
Foundry-style sketch against a deployed pool:

```solidity
// Victim holds no deposit tokens (or fewer than all types).
IPool pool = IPool(POOL);
IDepositToken[] memory dts = pool.getDepositTokens(); // all listed collateral tokens
uint256 max = pool.MAX_TOKENS_PER_USER();

// 1) Attacker fills victim's list with dust deposits on behalf of victim.
for (uint256 i; i < max; ++i) {
    IERC20 underlying = dts[i].underlying();
    underlying.approve(address(dts[i]), 1);
    dts[i].deposit(1, victim); // mints 1 wei msdTOKEN to victim, adds to their list
}
assertEq(pool.getDepositTokensOfAccount(victim).length, max);

// 2) Victim's own deposit of a token not in the list reverts.
IERC20 other = dts[max].underlying(); // a collateral type the victim doesn't hold
other.approve(address(dts[max]), 1e18);
vm.prank(victim);
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
dts[max].deposit(1e18, victim);

// 3) Even a third-party transfer of an unlisted msdTOKEN to the victim reverts.
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
dts[max].transfer(victim, 1);

// 4) Grief persists: attacker never withdraws the dust, so slots are never freed
//    (removal requires balance == 0 in DepositToken._burn/_transfer).
```

Note: I verified the add/remove paths and the revert behavior from `DepositToken.sol` and the pool test, but was unable to read `Pool.sol`'s exact `MAX_TOKENS_PER_USER` value and `addToDepositTokensOfAccount` body in this session; the test at test/Pool.test.ts:1503-1520 confirms the cap exists and the revert propagates through the deposit-token call path.
