### Title
HTTP Request Smuggling via CL/TE Desync — Request Parser Ignores `Transfer-Encoding` and Frames Bodies by `Content-Length` Only - (File: `stackslib/src/net/http/request.rs`)

### Summary
`HttpRequestPreamble::consensus_deserialize` never inspects or rejects the `Transfer-Encoding` header on incoming HTTP requests. Any such header is silently folded into the generic `headers` map like an arbitrary opaque header, while the framing layer (`StacksHttp::payload_len` / `read_payload` in `httpcore.rs`) always frames the request body strictly by `Content-Length`. On a persistent (`keep-alive`) connection, bytes beyond the declared `Content-Length` are interpreted as the start of a subsequent, independent request. This is the same bug class as GHSA-22gh-3r9q-xf38 (CWE-444): conflicting length signals (`Content-Length` vs `Transfer-Encoding: chunked`) are not reconciled/rejected, breaking the equality between "what the sender intended as one message" and "what the receiver parses as one message."

### Finding Description
In `stackslib/src/net/http/request.rs`, the header loop that builds `HttpRequestPreamble` explicitly special-cases `host`, `content-type`, `content-length`, `connection`, and `set-cookie`: [1](#0-0) 

There is no `else if key == "transfer-encoding"` branch. Any `Transfer-Encoding` header (e.g. `chunked`) falls into the final `else` arm and is stored verbatim in `headers` — it has zero effect on how the body is framed.

Compare this to the *response* parser, which explicitly recognizes and validates `transfer-encoding`, and rejects the case where both `Content-Length` and chunked `Transfer-Encoding` are present: [2](#0-1) 

For requests, framing is done unconditionally via `Content-Length`: [3](#0-2) 

and the request path of `read_payload` reads exactly `get_content_length()` bytes as the body, with a comment explicitly (and incorrectly, in terms of enforcement) assuming requests are never chunked: [4](#0-3) [5](#0-4) 

Because HTTP/1.1 connections default to keep-alive unless `Connection: close` is present: [6](#0-5) 

an attacker can send a single TCP payload containing a request with both `Content-Length: N` and `Transfer-Encoding: chunked`. The Stacks node consumes only `N` bytes as the first request's body and treats the remaining, attacker-controlled bytes as a second, independently-dispatched request on the same connection — a classic "CL.TE" smuggling primitive. If this endpoint sits behind any component that instead honors `Transfer-Encoding` (a reverse proxy, load balancer, or another HTTP/1.1 implementation in front of the RPC endpoint), the two components disagree on where one request ends and the next begins, letting an attacker's smuggled request bypass whatever inspection/ACL/auth logic the front-end applied to the outer, "legitimate-looking" request.

### Impact Explanation
This breaks the equality "one HTTP message sent == one HTTP message parsed," which is the exact bug class of the referenced advisory. In this codebase it manifests as unauthenticated request smuggling on any RPC/API endpoint reachable over `stackslib/src/net/http`, including sensitive StackerDB write endpoints such as `poststackerdbchunk.rs`. Smuggled requests are not just malformed input — they are entire additional requests, dispatched to arbitrary handlers, that a fronting proxy's security policy (path filtering, auth) may never have inspected. This matches the "Critical: request smuggling or auth bypass" bucket in scope.

### Likelihood Explanation
The attack requires no authentication and only a single crafted TCP stream to any HTTP-serving Stacks node endpoint that keeps the connection alive (the default for HTTP/1.1 unless the client sends `Connection: close`). No secret keys, admin roles, or bulk traffic are needed — a single conflicting request is sufficient to desync framing state, satisfying the "remote, unprivileged, few messages" bar.

### Recommendation
In `HttpRequestPreamble::consensus_deserialize`, explicitly recognize `transfer-encoding` and:
1. Reject requests that declare `Transfer-Encoding` at all (since the framing layer never implements chunked *request* bodies), returning a `CodecError::DeserializeError`, mirroring the response-side rejection logic in `response.rs`.
2. Reject requests where both `Content-Length` and `Transfer-Encoding` are present, regardless of value, rather than silently ignoring the latter.
3. Add a regression test analogous to `test_parse_stacks_http_preamble_response_err` (`stackslib/src/net/tests/httpcore.rs`) but for requests, asserting that `Transfer-Encoding` on a request is rejected outright.

### Proof of Concept
Send the following bytes over a single TCP connection to the node's HTTP RPC port (`keep-alive` implied by HTTP/1.1 defaults):
```
POST /v2/stackerdb/SP000.../foo/chunks HTTP/1.1
Host: 127.0.0.1:20443
Content-Type: application/json
Content-Length: 4
Transfer-Encoding: chunked

0\r\n\r\nGET /v2/info HTTP/1.1\r\nHost: 127.0.0.1:20443\r\n\r\n
```
`HttpRequestPreamble::consensus_deserialize` accepts this preamble (no rejection for the coexisting headers), and `read_payload` frames the body as exactly 4 bytes (`"0\r\n"` + 1 byte), leaving `\r\nGET /v2/info HTTP/1.1\r\nHost: ...\r\n\r\n` to be parsed by `read_preamble` as a second, independent request on the same connection — demonstrating the desync/smuggling primitive. (Exact byte offsets depend on the chosen `Content-Length`; the point is that any `Content-Length` value smaller than the full attacker payload lets bytes past it be reinterpreted as a new request.)
