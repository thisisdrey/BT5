### Title
Missing bounds check on attacker-controlled array length in `extractBytes32Array` allows out-of-bounds array access in TVM precompiled contracts - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array(DataWord[] words, int offset)` reads an element count directly from attacker-supplied call data and uses it to index into the `words` array without any bounds validation, unlike its sibling helpers `extractBytesArray` and `extractSigArray`, which explicitly guard against `offset` (and implicitly the derived length) running past the end of `words`.

### Finding Description
`extractBytes32Array` is:
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
}
``` [1](#0-0) 

`len` comes straight from calldata (`words[offset].intValueSafe()`), fully attacker-controlled, and the loop then reads `words[offset + i + 1]` for `i` up to `len - 1` with no check that `offset + i + 1 < words.length`. Compare this to the two nearly identical helpers in the same file that *do* validate the offset before trusting the length-derived index arithmetic:
```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    ...
``` [2](#0-1) 
```java
private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    ...
``` [3](#0-2) 

This is structurally the same class of bug as the FreeRDP CVE: an on-wire/on-calldata element count is trusted to drive array indexing/writes against a buffer whose real size was fixed independently of that count (`words`, sized from the actual calldata length, versus `hints`-derived heap buffer in FreeRDP). In FreeRDP this becomes a heap buffer overflow; in java-tron's managed-memory context the analogous fault is an unguarded read past `words.length`, which throws an uncaught `ArrayIndexOutOfBoundsException` (or, for very large `len`, a `NegativeArraySizeException`/`OutOfMemoryError` from `new byte[len][]`) inside precompiled-contract execution that is not defensively bounded like the sibling helpers.

### Impact Explanation
Any account able to invoke the precompiled contract(s) that call `extractBytes32Array` with attacker-supplied calldata can trigger an unhandled runtime exception deep inside TVM precompile execution. Depending on how far up the exception propagates before being caught, this can abort transaction execution non-gracefully (inconsistent with the guarded siblings' safe empty-array fallback), and in the worst case an unguarded `RuntimeException` escaping the expected `Program.Exception` handling path during block application can affect node availability for that transaction — a node-crash/halt-class impact per the scope rules. Because the other two extractor functions in the same file were hardened with an explicit `offset > words.length - 1` check, this method's lack of the same guard indicates an incomplete fix/inconsistent bounds validation across an equivalent codepath.

### Likelihood Explanation
Reaching this code only requires composing calldata (attacker fully controls the `len` word and the surrounding `words` array size) and invoking whichever precompiled contract path calls `extractBytes32Array` — a capability available to any unprivileged contract caller/deployer who can send a transaction invoking a TVM precompile. No special privileges, timing, or race conditions are needed; the trigger is a single crafted transaction.

### Recommendation
Add the same guard used in `extractBytesArray`/`extractSigArray` to `extractBytes32Array`: validate `offset` against `words.length`, and additionally validate that `offset + len` does not exceed `words.length` (or that `len` itself is bounded to a sane maximum) before allocating `new byte[len][]` or indexing `words[offset + i + 1]`. Return a safe empty array (or reject cleanly) on invalid input, consistent with the sibling methods.

### Proof of Concept
1. Craft transaction calldata for a TVM precompiled contract call whose internal decoding path invokes `extractBytes32Array(words, offset)`.
2. Set the DataWord at `words[offset]` (the length field) to a value larger than the number of remaining words actually present in the decoded `words` array (e.g., set it to `words.length` or larger while only supplying a short calldata buffer that decodes to a small `words` array).
3. Submit the transaction/contract call; the precompile's execution reaches `words[offset + i + 1]` for an `i` that pushes the index past `words.length - 1`, throwing an unguarded `ArrayIndexOutOfBoundsException` (or, for an extremely large length value, triggering `new byte[len][]` with pathological size), unlike the identical-shaped `extractBytesArray`/`extractSigArray` calls which safely short-circuit via their `offset > words.length - 1` guard.
