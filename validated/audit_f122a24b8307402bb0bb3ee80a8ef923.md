No vulnerability confirmed here. The premise misdescribes the code path.

**Key facts from the code:**

1. Global contract distribution propagates **shard-by-shard exactly once per shard**, not once per calling account. `forward_distribution_next_shard` walks the fixed `shard_layout.shard_ids()` list, appending the just-processed shard to `already_delivered_shards` and forwarding to the next undelivered shard until all shards have received it once [1](#0-0) . The number of shards is a protocol-level constant unrelated to how many accounts later call `UseGlobalContract`.

2. `apply_distribution_current_shard` — where `precompile_contract_with_warming` runs — is gated by a nonce-freshness check, guaranteeing compilation happens **once per shard per distribution**, not once per `UseGlobalContract` call [2](#0-1) .

3. This per-shard compile cost is explicitly metered as compute via `deploy_global_contract_execution_base`/`deploy_global_contract_execution_per_byte`, which count against that shard's chunk compute budget — this is exactly the fee model built to cover "precompilation overhead" per the parameter doc comments [3](#0-2)  and is demonstrated/tested to bound throughput (one distribution receipt saturates a chunk) [4](#0-3) .

4. Critically, `UseGlobalContract` (the action invoked by "N calling accounts") does **not** trigger any compilation at all. `action_use_global_contract`/`use_global_contract` only checks that the global contract code key exists in that shard's trie and repoints the account's `AccountContract` field — no call into `precompile_contract_with_warming` or any VM compile routine [5](#0-4) .

So the attack scenario described — "N shards (one per calling account) each independently compile via `apply_distribution_current_shard`" — cannot occur: `apply_distribution_current_shard` only ever runs once per shard as part of the fixed, one-time distribution walk, is charged compute against `deploy_global_contract_execution_base/_per_byte` (rate-limiting further deploys via chunk compute budget, as the test at [6](#0-5)  demonstrates), and is never re-triggered by downstream `UseGlobalContract` receipts from arbitrary accounts. Actual contract compilation triggered by later `FunctionCall`s against an account using the global contract goes through the normal `with_compiled_and_loaded` cache-and-loading-fee path [7](#0-6) , which charges the calling receipt's own gas for loading/compiling, not the original deployer.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}
