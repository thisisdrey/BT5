### Title
`StacksHttpRecvStream::consume_data` reallocates a full `CHUNK_BUF_LEN` buffer on every chunk-decode iteration, allowing attacker-controlled tiny chunks to induce disproportionate allocation/zeroing cost - ([File: stackslib/src/net/httpcore.rs])

### Summary
`consume_data` runs a `while !blocked` loop that allocates a brand-new `vec![0u8; CHUNK_BUF_LEN]` buffer on every pass, and only exits when `do_read` reports 0 bytes decoded or a would-block/timeout error. A malicious HTTP peer that sends a chunked response encoded as many minimal (e.g. 1-byte) chunks forces this loop to perform one full `CHUNK_BUF_LEN`-sized allocation-and-zero-init per tiny chunk, instead of amortized O(1) work per decoded byte.

### Finding Description
The loop body is: [1](#0-0) 

Each iteration:
1. Allocates and zero-fills a fresh `CHUNK_BUF_LEN`-sized `Vec<u8>` (`decoded_buf`).
2. Calls `self.state.do_read(fd, &mut decoded_buf)`.
3. Only sets `blocked = true` when `do_read` returns `(0, num_consumed)` (no bytes decoded) or a `WouldBlock`/`TimedOut` I/O error; any non-zero `num_read` (even `1`) keeps the loop going with `blocked` staying `false`.
4. `self.state.is_eof()` is checked only *after* the loop exits, not per-iteration, so it cannot short-circuit a long run of tiny-chunk iterations.

Since `HttpChunkedTransferReaderState` decodes exactly one HTTP chunk's payload per call to `do_read` (bounded by the chunk's declared size, not by `CHUNK_BUF_LEN`), an attacker who crafts a chunked body composed of many 1-byte chunks (`"1\r\nX\r\n"` repeated) causes `do_read` to return `(1, small_consumed)` on each call. As long as more encoded bytes are available to `fd` in that invocation, the loop keeps iterating without blocking, and each iteration pays the full `CHUNK_BUF_LEN` allocation+zero cost for just 1 real payload byte. This is used specifically to decode chunked-encoded HTTP **responses** received by the node's own outbound HTTP client (e.g., when the node itself connects out to fetch RPC data from another peer), so a malicious peer being contacted by the victim node fully controls the bytes fed into this function.

The only bound on total damage is `self.state.max_size` (the overall decoded-size cap passed into `HttpChunkedTransferReaderState::new`), which caps the total number of chunks/bytes an attacker can force through a single logical HTTP response, but does not change the fact that the cost-per-decoded-byte is amplified by a `CHUNK_BUF_LEN` factor whenever chunks are kept minimal. No existing guard (`max_size`, `is_eof` check, or the `blocked` exit condition) prevents the tight reallocation loop from running per-chunk; they only bound the total number of chunks that can eventually be sent before the message is rejected or completed.

### Impact Explanation
The node acting as an HTTP client (e.g., fetching from another peer's RPC endpoint) pays a CPU/allocation cost proportional to `CHUNK_BUF_LEN × (number of chunks)` rather than to the number of real payload bytes transferred. Because the loop is bounded by `max_size` (an overall cap on decoded bytes), this is a **bounded compute DoS on a read path**, not an unbounded single-message crash — matching the "High - bounded compute DoS on a read endpoint" category rather than Critical. The affected party is the victim node's own outbound-fetch code path (`net::httpcore`), and the attack is trivially repeatable against every response the victim requests from the malicious peer.

### Likelihood Explanation
No privileged role, secret, or signature bypass is required — the attacker only needs to be a peer that the victim node's HTTP client connects to (e.g., a normal RPC peer), and to answer a legitimate outbound RPC request with an adversarial chunked-encoded body. Attacker cost is minimal (sending many tiny chunk headers is cheap), while the victim performs disproportionate allocation/zeroing work per response. This is remotely reachable and repeatable on every request the victim node issues to the malicious peer.

### Recommendation
Allocate `decoded_buf` once, outside the `while !blocked` loop, and reuse/reset it across iterations instead of reallocating a fresh `CHUNK_BUF_LEN` vector every pass. Additionally, consider checking `self.state.is_eof()` inside the loop to exit as soon as the message is fully decoded, and/or enforce a maximum chunk-count (not just max decoded-byte total) to bound the number of loop iterations per `consume_data` call independent of chunk size chosen by the remote peer.
