## Title
Permanent freeze of an ETH-implicit wallet via a malicious NEP-141 token that exhausts gas in `nep_141_storage_balance_callback`, leaving `has_in_flight_tx` stuck `true` forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` that backs every ETH-implicit account uses a single boolean flag, `has_in_flight_tx`, to serialize execution of Ethereum-emulated transactions. `rlp_execute` refuses to start a new transaction while this flag is `true`, and every callback is documented to reset it to `false` as its very first statement. However, if a callback's *own execution* fails (e.g. runs out of gas) after that reset statement but before the receipt completes, the whole receipt — including the flag reset — is rolled back by the runtime, because contract-storage writes are only durable when the receipt succeeds. An attacker-controlled or simply buggy NEP-141 token, invoked as the target of an emulated ERC-20 transfer, can trigger exactly this: return an oversized `storage_balance_of` response that blows the small, attacker-choosable gas budget allocated to `nep_141_storage_balance_callback`, permanently corrupting the wallet's `has_in_flight_tx` state to `true` and freezing the wallet forever. This is the direct on-chain analog of the reported "malicious token reward could disable withdrawals" bug class: a malicious external token contract breaks an unprivileged user's ability to ever transact again.

### Finding Description
`rlp_execute` guards re-entrancy with a single flag persisted in contract state: [1](#0-0) 

For ERC-20 emulation, execution is split across a `storage_balance_of` cross-contract call to the (attacker-influenced) `target` token and a subsequent callback: [2](#0-1) 

The very first line of the callback resets `has_in_flight_tx = false`, and the JSON-decoded `PromiseResult::Successful(value)` from the token is deserialized right after: [3](#0-2) 

The gas budget given to this callback is fixed at `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` plus `action.gas()`, both of which are effectively user/relayer-controlled inputs derived from the signed Ethereum transaction, so an attacker crafting the transaction can make this budget arbitrarily small: [4](#0-3) [5](#0-4) 

If the malicious `token_id` contract returns a large enough `Successful` payload, deserializing/handling it inside `nep_141_storage_balance_callback` consumes more gas than was allotted, and the function call fails with an out-of-gas error. NEAR's execution model makes a failed receipt fully atomic: a receipt whose result is `Err` triggers `state_update.rollback()`, discarding *all* state changes made during that receipt, not just the ones after the point of failure: [6](#0-5) [7](#0-6) 

Contract `storage_write`s are only buffered as "prospective" trie changes during execution and are never durable until the receipt succeeds: [8](#0-7) 

Consequently, the `self.has_in_flight_tx = false;` write executed at the top of `nep_141_storage_balance_callback` is rolled back along with everything else in that failed receipt, and the persisted state retains `has_in_flight_tx = true` from the prior (already-committed) `rlp_execute` receipt. Because `rlp_execute` unconditionally rejects any call while `has_in_flight_tx` is `true`, and there is no other public/private method that can clear this flag outside of the very callback chain that is now permanently unreachable, the wallet can never process another transaction.

### Impact Explanation
This causes a **permanent freeze of an ordinary user's ETH-implicit account**: no future `rlp_execute` call can ever succeed again, so any $NEAR or fungible tokens held by, or accessible only through, that wallet become permanently inaccessible. This is a direct analog of the external report's "malicious reward token disables withdrawal" — here a malicious/adversarial NEP-141 token disables the entire wallet contract, not just one operation, which is at least as severe as the original finding (permanent freezing of funds).

### Likelihood Explanation
The interacting token is user/relayer-chosen as the `target` of the emulated ERC-20 transfer; an ordinary user attempting to interact with a malicious or merely buggy NEP-141 token (or a relayer forwarding a transaction whose `target` is such a token, since `target` is signed by the account owner via the Ethereum tx contents but its trustworthiness isn't otherwise validated) is enough to trigger this. The attacker fully controls: (1) the token contract's `storage_balance_of` response size/content, and (2) `action.gas()` in the signed transaction that determines the callback's total gas budget, making a gas-exhaustion condition straightforward to engineer deterministically.

### Recommendation
- Reserve a fixed, sufficiently large *minimum* gas budget for the callback logic that does not depend on `action.gas()`, and/or cap/validate the size of `storage_balance_of` responses before attempting to deserialize them (e.g., check `env::register_len` against a small bound before copying/parsing).
- More fundamentally, do not rely on a single in-receipt storage write executed at the very start of a callback to represent "transaction no longer in flight." Reset `has_in_flight_tx` using a mechanism that is robust to the callback itself failing later — for example, splitting the reset into its own always-succeeding step, or using `promise_batch_then`/separate low-gas finalization receipt guaranteed to succeed regardless of what happens with the token's response, similar in spirit to an "emergencyWithdraw"-style unconditional recovery path recommended in the original report.

### Proof of Concept
1. User (or their relayer) sends a signed Ethereum transaction to their ETH-implicit account's `WalletContract::rlp_execute`, emulating an ERC-20 `transfer` whose `target` is `evil-token.near`, a token contract deployed by an attacker (or simply buggy).
2. `inner_rlp_execute` sets `has_in_flight_tx = true` and issues `Promise::new(evil-token.near).function_call("storage_balance_of", ...).then(nep_141_storage_balance_callback(...))` with a fixed small static gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()`), where `action.gas()` is chosen minimally by the attacker crafting the tx.
3. `evil-token.near::storage_balance_of` returns `PromiseResult::Successful` with a payload engineered to be large/complex enough that `serde_json::from_slice::<Option<StorageBalance>>` plus subsequent processing in `nep_141_storage_balance_callback` exceeds the allotted gas.
4. The callback's function call fails with `Exceeded the prepaid gas.`; the enclosing receipt fails and is rolled back in its entirety (`TrieUpdate::rollback`), discarding the `has_in_flight_tx = false` write made at the top of the callback.
5. The wallet's persisted `has_in_flight_tx` remains `true` (from step 2's committed receipt).
6. Any subsequent call to `rlp_execute` on this account immediately returns `ExecuteResponse { success: false, error: Some("Error: transaction already in progress, please try again later.") }` and never dispatches a new promise — permanently, since nothing can ever again reach a callback that resets the flag.
