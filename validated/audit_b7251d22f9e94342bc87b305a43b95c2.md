### Title
Unbounded full-store scan over `VotesStore` in `MaintenanceManager.countVote` and `Wallet.getPaginatedNowWitnessList` enables node-halting / API DoS via cheap unprivileged votes - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java], [File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
Analogous to the Arcadia `tranches` array that is iterated unboundedly by `_syncInterestsToLiquidityProviders`/`_processDefault`, java-tron maintains a `VotesStore` whose size grows with every distinct account that casts a vote via the unprivileged `VoteWitnessContract`. Two code paths perform a full linear scan of this store: `MaintenanceManager.countVote()`, executed automatically during every maintenance/epoch block (`doMaintenance()`), and `Wallet.countVote()`, executed on every call to the public `getPaginatedNowWitnessList` API (reachable via gRPC, HTTP, and solidity-node interfaces). Neither path bounds the number of `VotesStore` entries it iterates.

### Finding Description
`VoteWitnessActuator.execute` / `VoteWitnessProcessor.execute` create or update one `VotesCapsule` entry per distinct voter address in `VotesStore` whenever any account with frozen TRX ("tron power") casts a vote [1](#0-0) . There is no cap on the number of distinct voter accounts, only a per-transaction cap of 30 witnesses per vote (`MAX_VOTE_NUMBER`) [2](#0-1) . Since freezing even a minimal amount of TRX and voting is a cheap, fully unprivileged action, an attacker can create an arbitrarily large number of accounts that each cast one vote per epoch, causing `VotesStore` to accumulate unboundedly many entries before the next maintenance cycle clears it.

`MaintenanceManager.doMaintenance()` — invoked automatically as part of block application whenever the maintenance time boundary is crossed — calls `countVote(votesStore)`, which does a full `Iterator<Entry<byte[], VotesCapsule>>` scan over the entire store, deleting entries one by one, with no bound on iteration count: [3](#0-2) . This call is reached from `applyBlock`, i.e. normal block application in `Manager`/`MaintenanceManager` [4](#0-3) .

Separately, the identical unbounded scan is duplicated in `Wallet.countVote()`, which backs the public `getPaginatedNowWitnessList` query API exposed over gRPC (`RpcApiService`), the fullnode HTTP API (`GetPaginatedNowWitnessListServlet` / `FullNodeHttpApiService`), and the solidity-node HTTP/gRPC interfaces [5](#0-4) [6](#0-5) . Any anonymous client can invoke this endpoint at any time, forcing the node to scan the full `VotesStore` synchronously on the calling thread for every request.

### Impact Explanation
As the number of unique voting accounts in an epoch grows (cheap to inflate via many low-value frozen accounts, similar to the `addTranche` growth in the original report), both the per-block `doMaintenance()` path and the public query path degrade linearly with store size. On the consensus path, this increases block-application time during maintenance blocks across all nodes simultaneously (since every node executes `doMaintenance()` when applying the same block), risking missed block production windows / degraded liveness under sufficiently large vote counts. On the API path, it allows an anonymous caller to force expensive full-store scans repeatedly, degrading or exhausting node resources serving `getPaginatedNowWitnessList` for legitimate users — a concrete "API the node can no longer serve" outcome.

### Likelihood Explanation
Casting a vote only requires freezing a small amount of TRX (bounded only by dust-level economic cost) and submitting an unprivileged `VoteWitnessContract` transaction; there is no cap on the number of distinct voter accounts that can exist in a single epoch. Both vulnerable code paths (`doMaintenance` and `getPaginatedNowWitnessList`) are always reachable — the former automatically every maintenance cycle, the latter on every unauthenticated API call — making exploitation straightforward for an attacker willing to create many accounts and vote from each.

### Recommendation
Bound `VotesStore` growth per epoch (e.g., cap the number of distinct voting accounts processed per maintenance cycle, or amortize `countVote` processing across multiple blocks instead of one synchronous full scan), and/or move the `getPaginatedNowWitnessList` vote-delta aggregation off the full-store hot path (e.g., maintain incrementally-updated aggregate vote deltas rather than re-scanning `VotesStore` on every call).

### Proof of Concept
1. Generate N accounts, each freezing the minimum TRX required to obtain non-zero tron power.
2. From each account, submit a `VoteWitnessContract` transaction voting for any valid witness (unprivileged, one transaction each).
3. Before the next maintenance boundary, `VotesStore` now contains N entries.
4. Observe: (a) the next block that crosses the maintenance boundary takes proportionally longer to apply due to `MaintenanceManager.countVote()` scanning all N entries [3](#0-2) ; (b) repeated calls to `getPaginatedNowWitnessList` via gRPC/HTTP force the same full N-entry scan per request [5](#0-4) , and cost scales linearly with N with no upper bound.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
