Based on my investigation, I've found the strongest analog for the report's bug class in Gitaly's `ObjectPoolService`.

### Title
`LinkRepositoryToObjectPool`/`DeleteObjectPool` lack ownership verification, allowing any repository owner to corrupt or DoS unrelated repositories sharing an object pool - (File: internal/gitaly/service/objectpool/link.go, internal/gitaly/service/objectpool/delete.go)

### Summary
Just as `NFTFloorOracle.removeFeeder()` let any caller destroy a shared resource (feeders) that other users' liquidation logic depended on, Gitaly's `ObjectPoolService` RPCs perform no check that the caller (or the target repository they control) is actually an authorized member/owner of the object pool before mutating it. `LinkRepositoryToObjectPool` [1](#0-0)  only validates that `req.GetObjectPool()` resolves to *some* valid pool repository via `poolForRequest`/`objectpool.FromProto` [2](#0-1)  and that the repository is a well-formed pool path [3](#0-2) , but it never verifies that the caller's target `repository` is supposed to belong to that specific pool, or that the pool "belongs" to the caller's project in any authorization sense. Likewise `DeleteObjectPool` documents itself as having "no safety checks in place, so if any repository is still using this object pool it will become corrupted" [4](#0-3)  and its handler performs the deletion unconditionally [5](#0-4) .

### Finding Description
The `NFTFloorOracle` bug's root cause was that a destructive, shared-state-mutating function was reachable by any caller because the intended privilege check was never actually verifying identity. In the Gitaly analog, any actor that can invoke `ObjectPoolService` RPCs for a repository they control can:
1. Call `LinkRepositoryToObjectPool` with an arbitrary `object_pool` field pointing at any repository that satisfies `storage.IsPoolRepository`/`IsValid` checks [6](#0-5) , causing their repository to be linked to (and deduplicated against) an object pool without any verification that they should be a member of it.
2. Call `DeleteObjectPool` on a pool that other, unrelated repositories still depend on as their alternates source. Because deletion has "no safety checks in place" [7](#0-6) , this immediately corrupts every other member repository that still references the deleted pool via `objects/info/alternates`, since those repositories can no longer resolve objects that only exist in the (now-deleted) pool [8](#0-7) .

This mirrors the oracle bug precisely: a single caller can destroy or repurpose a resource that other, unrelated parties depend on for correctness, with no ownership/ACL check tying the mutating RPC to the specific pool-member relationship being altered.

### Impact Explanation
Any repository whose alternates still point at a deleted or hijacked pool will fail to resolve objects that live only in the pool, causing read/fetch/clone failures and effectively DoS'ing all fork members of that pool — analogous to how removing all price feeders DoS'd `liquidateERC721()` for every position relying on that NFT's price feed. Because Gitaly's pool corruption is filesystem-level and immediate, recovery requires administrator intervention (as acknowledged directly in the RPC's own doc comment) [7](#0-6) .

### Likelihood Explanation
Both `LinkRepositoryToObjectPool` and `DeleteObjectPool` are declared as `MUTATOR` RPCs reachable from any client holding a normal Gitaly auth token (i.e., from GitLab Rails acting on behalf of any project/fork owner) [9](#0-8) . The handlers themselves add no additional cross-repository ownership check beyond confirming the `object_pool` value is *a* valid pool [2](#0-1) , so likelihood of reachability is high wherever calling code (e.g., Rails) doesn't itself enforce that the pool and the target repository are related.

### Recommendation
Add an explicit check in `LinkRepositoryToObjectPool`, `DisconnectGitAlternates`, and `DeleteObjectPool` that the target repository's derived/expected pool path matches `req.GetObjectPool()` (or that the caller-supplied repository is a known member per the `PoolStore`/state manager records) before performing the mutation, rather than relying solely on generic "is this a syntactically valid pool" checks.

### Proof of Concept
1. Repository A is forked from repository B, and Gitaly creates object pool P with A and B as members via `CreateObjectPool`/`LinkRepositoryToObjectPool`.
2. An actor controlling only repository A (not B, and with no legitimate relationship to P beyond being a member) issues `DeleteObjectPool(object_pool=P)` — the handler in `internal/gitaly/service/objectpool/delete.go` performs `repoutil.Remove` on P unconditionally [5](#0-4) .
3. Repository B, which still has `objects/info/alternates` pointing at P, is now corrupted: any subsequent read of an object that exists only in P fails, as documented directly in the RPC comment ("if any repository is still using this object pool it will become corrupted") [7](#0-6) .

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

```go
func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
```

```go
// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}
```

```go
func (s *server) DeleteObjectPool(ctx context.Context, in *gitalypb.DeleteObjectPoolRequest) (*gitalypb.DeleteObjectPoolResponse, error) {
	pool, err := s.poolForRequest(ctx, in)
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			// TODO: we really should return an error in case we're trying to delete an
			// object pool that does not exist.
			return &gitalypb.DeleteObjectPoolResponse{}, nil
		}

		return nil, err
	}

	if err := repoutil.Remove(ctx, s.logger, s.locator, nil, s.repositoryCounter, pool); err != nil {
		return nil, fmt.Errorf("remove: %w", err)
	}
```

```markdown
Removing a member from an object pool is slightly more involved, as members of
an object pool members will miss objects which are only part of the object pool.
It is thus not as simple as removing `objects/info/alternates`, as that would
leave behind a corrupt repository. Instead, Gitaly hard-links all objects which
are part of the object pool into the dissociating member first and removes the
alternate afterwards. In order to check whether the operation succeeded, Gitaly
now runs `git-fsck(1)` to check for missing objects. If there are none, the
dissociation has succeeded. Otherwise, it will fail and re-add the alternates
file.
```
