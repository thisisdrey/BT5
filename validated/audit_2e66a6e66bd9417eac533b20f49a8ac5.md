### Title
Permanent freezing of TRX sent to the reserved TIP-2935 `HISTORY_STORAGE_ADDRESS` before activation - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP-2935 (EIP-2935) `BlockHashHistory` system contract at the hardcoded address `0x0000f90827f1c53a10cb7a02335b175320002935` when the `AllowTvmPrague` proposal activates. Any ordinary, unprivileged transaction can send TRX to that address before activation, and when `deploy()` later runs it converts the pre-existing account in place into a permanent, immutable system contract that has no function capable of transferring out its balance — permanently freezing any TRX that was sent to it beforehand.

### Finding Description
`deploy()` is called from `ProposalService` at maintenance time once `AllowTvmPrague` is enabled [1](#0-0) . The window between the chain being live (so anyone can send TRX to the well-known, hardcoded address) and the actual activation of the proposal is exactly the kind of "unprotected init" window described in the external report: the target address is known in advance, and the deploy step happens later, in a separate operation, with no protection against state that accumulated at the address in the meantime.

When `deploy()` runs, it explicitly branches on whether an account already exists at the address: [2](#0-1) 

If an account (funded via ordinary TRX transfers, which require no private key or signature from the recipient) already exists, the code preserves its balance but flips its `AccountType` to `Contract` and installs the fixed `HISTORY_STORAGE_CODE` bytecode at that address. That bytecode only implements a read-only historical-hash lookup (`SLOAD`/`STATICCALL` style get) with no transfer, withdraw, or `selfdestruct` capability [3](#0-2) . There is no code path, before or after activation, that can move TRX back out of this address — the only way to reach the balance would be via contract execution, and the deployed bytecode contains no operation to do so.

The class-level comment even documents this exact scenario as expected/acceptable behavior: "Anyone can transfer TRX to `HISTORY_STORAGE_ADDRESS` before the proposal fires, leaving an EOA at the canonical address ... we upgrade its type to `Contract` in place ... preserving balance/asset state" [4](#0-3) , and this is directly covered by a test that asserts the balance is preserved through the conversion (`deploySkipsWhenForeignBytecodePresent`/related account-preservation tests) [5](#0-4) .

### Impact Explanation
Any TRX sent by any unprivileged account to the fixed address `HISTORY_STORAGE_ADDRESS` prior to `AllowTvmPrague` activation becomes irrecoverably locked the moment the network activates TIP-2935, because the address is turned into an immutable system contract with no method to release funds. Since the target address is a fixed, publicly known constant (mirroring Ethereum's EIP-2935 address) [6](#0-5) , it can be targeted well in advance, and any TRX that lands there (whether by mistake, by a phishing scheme directing victims to "deposit" to that address, or otherwise) is permanently frozen once the hard fork proposal takes effect network-wide.

### Likelihood Explanation
Sending TRX to an arbitrary address on TRON requires no cooperation or signature from the recipient, so funding this specific address is trivial for any transaction broadcaster at any time before the hard fork activates. The precise activation block is known ahead of time (via governance/committee proposal), giving ample opportunity to either accidentally or intentionally place funds there.

### Recommendation
Do not silently reuse and freeze a pre-existing account's balance when installing the TIP-2935 system contract. Instead, either (a) refuse to activate/deploy while a non-zero balance exists at the canonical address and require it to be handled explicitly (e.g., refunded or burned in a well-defined, audited manner), or (b) reserve/blacklist the address from receiving ordinary transfers before activation so no balance can accumulate there in the first place.

### Proof of Concept
1. Before the `AllowTvmPrague` proposal is active, any account (e.g. a normal wallet) submits a standard TRX transfer to `410000f90827f1c53a10cb7a02335b175320002935`.
2. This creates a normal `AccountCapsule` with a balance at that address (no signature validation is required from the recipient for a transfer to succeed).
3. When the committee/proposal activates TIP-2935, `ProposalService` calls `HistoryBlockHashUtil.deploy(manager)`.
4. `deploy()` finds the pre-existing account, calls `account.updateAccountType(Contract)` and `clearDelegatedResource()`, keeping the balance, and installs the fixed read-only bytecode [2](#0-1) .
5. From this point on, the address is a `Contract` running immutable bytecode with no transfer-out capability, so the TRX balance deposited in step 1 can never be withdrawn by anyone.

   * Collision guard: if foreign bytecode already sits at the canonical address

  @Test
  public void deploySkipsWhenForeignBytecodePresent() {
    byte[] addr = HistoryBlockHashUtil.HISTORY_STORAGE_ADDRESS;
    byte[] foreignCode = new byte[]{0x60, 0x00};
    chainBaseManager.getCodeStore().put(addr, new CodeCapsule(foreignCode));

    HistoryBlockHashUtil.deploy(dbManager);

    assertArrayEquals(foreignCode,
        chainBaseManager.getCodeStore().get(addr).getData());
    assertFalse(chainBaseManager.getContractStore().has(addr));
