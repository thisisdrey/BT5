### Title
Inner `DelegateAction` ML-DSA-65 signature verification compute escapes receiver-shard `compute_limit` accounting while `fix_ml_dsa_cost_charging` is unstabilized on mainnet - ([File: runtime/runtime/src/actions.rs])

### Summary
`apply_delegate_action` only meters the inner delegate's signature-verification compute against the receiver shard's `compute_limit` when `apply_state.config.wasm_config.fix_ml_dsa_cost_charging` is `true`. That protocol feature (`ProtocolFeature::FixMlDsaCostCharging`) is registered at protocol version 153, in the "Nightly features" section of `core/primitives-core/src/version.rs`, meaning it is not yet stabilized for mainnet, while `PostQuantumSignatures` (ML-DSA-65 key support) is already stable at protocol version 85. This gap lets an unprivileged relayer construct a meta-transaction whose real, expensive ML-DSA-65 `signature.verify()` call executes unmetered against the receiver shard's compute budget.

### Finding Description
`apply_delegate_action` (`runtime/runtime/src/actions.rs:437-461`) gates compute accounting for the inner-delegate signature verification behind the `fix_ml_dsa_cost_charging` flag: [1](#0-0) 

When the flag is disabled, `result.compute_usage` is never incremented before the actual expensive verification, `signed_delegate_action.verify()`, is executed just below it. That call performs real CPU work (ML-DSA-65 verify, ~80 µs mean per the project's own benchmarks documented in `docs/architecture/how/post_quantum_signatures.md`) regardless of whether the flag is set, since `SignedDelegateAction::verify()` in `core/primitives/src/action/delegate.rs:84-90` unconditionally calls `self.signature.verify(...)`.

Gas for the ML-DSA verification is charged only at transaction-conversion time on the signer's shard, in `signature_verification_cost` (`runtime/runtime/src/config.rs:542-561`), which strips out the compute portion of the cost when `meter_inner_verify_on_receiver` (i.e. the fix flag) is true - implying that, correspondingly, the compute must be picked up on the receiver shard by `delegate_signature_verification_compute` at execution time. But when the flag is false (pre-stabilization, i.e. current mainnet default), the signer shard charges gas only, no compute is charged there either, and the receiver shard's `apply_delegate_action` skips crediting compute for the verify it actually performs. This is a genuine metering gap, not a hypothetical one - it's exactly what the fix's own code comment describes: [2](#0-1) 

The repo's own protocol-version table confirms the fix is not live on the current stable/mainnet protocol version: [3](#0-2) 

Attacker steps: (1) create an account with an ML-DSA-65 access key (permitted since `PostQuantumSignatures` is already stable, protocol version 85); (2) construct a `DelegateAction` with `public_key` set to that ML-DSA-65 key and any inner actions; (3) sign the `SignedDelegateAction` with the ML-DSA-65 key so `verify()` succeeds; (4) wrap it in an outer transaction signed by a cheap ED25519 relayer key and submit it. No existing signature, nonce, access-key, or size-limit check intercepts this - the inner delegate signature is intentionally valid, and the outer transaction is a normal, well-formed relayed meta-transaction.

### Impact Explanation
Every such delegate action forces the receiver shard to spend real wall-clock CPU time performing ML-DSA-65 verification that is not reflected in `result.compute_usage`, hence not counted against that shard's `compute_limit`. Repeated submission of many such delegate actions in receipts destined for the same shard lets an attacker push actual per-chunk execution time beyond what `compute_limit` is meant to bound, without the accounting mechanism seeing it - a compute-metering-totality violation. This falls into a shard-liveness/resource-exhaustion risk category (the mechanism `compute_limit` exists specifically to protect chunk-application timing), though it stops short of an outright shard-halting panic; it is a metering escape that degrades the receiver shard's timing guarantees, matching the maintainers' own stated rationale for introducing `FixMlDsaCostCharging`.

### Likelihood Explanation
Preconditions are cheap and fully within an unprivileged attacker's control: any account can add an ML-DSA-65 access key (feature already stable at protocol version 85), and any account can act as a relayer signing with a classical (ED25519) key. The exploit is trivially repeatable - each delegate action with an ML-DSA-65 inner public key costs the attacker only the ED25519-priced relayer transaction fee while imposing ~80 µs of extra, uncharged verification time on the receiver shard per occurrence. The bug is gated purely on `fix_ml_dsa_cost_charging` being at its current (disabled) mainnet value, which is a real, currently-shipped state, not a hypothetical future misconfiguration.

### Recommendation
Stabilize and enable `ProtocolFeature::FixMlDsaCostCharging` for mainnet (moving it out of the nightly-only section) so that `delegate_signature_verification_compute` is always credited to `result.compute_usage` in `apply_delegate_action`, independent of a feature flag tied to a not-yet-activated protocol version, or otherwise ensure compute for inner-delegate ML-DSA verification is charged unconditionally on the receiver shard.

### Proof of Concept
Reuse the existing test `test_delegate_action_meters_inner_verify_compute` in `runtime/runtime/src/actions.rs:1354-1393` as a template: [4](#0-3) 
1. Set up a `SignedDelegateAction` whose inner `public_key` is an ML-DSA-65 key, sign it correctly.
2. Run `apply_delegate_action` with `wasm_config.fix_ml_dsa_cost_charging = false` (mainnet default) and record `result.compute_usage`.
3. Run again with the flag `= true` and record `result.compute_usage`.
4. Assert that with the flag off, `result.compute_usage` for the inner-verify portion is `0` even though `signed_delegate_action.verify()` executed real ML-DSA verification work, demonstrating the receiver shard's `compute_limit` accounting does not reflect the CPU cost actually incurred - matching the difference the existing test measures (`run(true) - run(false) == verify_compute`) but interpreted as "escape from budget" when the flag is at its true current mainnet value (disabled).

    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }

    #[test]
    fn test_delegate_action_meters_inner_verify_compute() {
        use near_parameters::cost::SignatureKind;
        use near_primitives::types::Gas;
        use std::sync::Arc;

        let (action_receipt, sda) = create_delegate_action_receipt();
        let sender_id = sda.delegate_action.sender_id.clone();
        let sender_pub_key = sda.delegate_action.public_key.clone();
        let access_key = AccessKey { nonce: 19000000, permission: AccessKeyPermission::FullAccess };
        let verify_compute: u64 = 777_000_000_000;

        let run = |fix_enabled: bool| -> u64 {
            let mut apply_state = create_apply_state(sda.delegate_action.max_block_height);
            let mut cfg = (*apply_state.config).clone();
            Arc::make_mut(&mut cfg.fees).signature_verification_costs[SignatureKind::Ed25519] =
                ParameterCost::new(Gas::from_gas(0), verify_compute);
            Arc::make_mut(&mut cfg.wasm_config).fix_ml_dsa_cost_charging = fix_enabled;
            apply_state.config = Arc::new(cfg);
            let mut state_update = setup_account(&sender_id, &sender_pub_key, &access_key);
            let mut result = ActionResult::default();
            apply_delegate_action(
                &mut state_update,
                &apply_state,
                &VersionedActionReceipt::from(&action_receipt),
                &sender_id,
                (&sda).into(),
                &mut result,
            )
            .expect("apply ok");
            assert!(result.result.is_ok(), "inner verify should pass: {:?}", result.result.err());
            result.compute_usage
        };

        assert_eq!(
            run(true) - run(false),
            verify_compute,
            "receiver shard must meter the inner-delegate verify compute when the fix is enabled"
        );
    }
