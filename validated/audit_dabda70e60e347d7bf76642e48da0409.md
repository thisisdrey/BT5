### Title
Fixed-window (not sliding-window) per-connection stream throttling allows a single QUIC connection to burst ~2x `max_streams_per_throttling_interval` streams across a window boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a lazy *fixed*-window counter rather than a true sliding window: it only resets `stream_count` when a caller observes that more than `STREAM_THROTTLING_INTERVAL` has elapsed since the last reset. Because the window boundary is defined by whenever a stream happens to trigger the reset (not by wall-clock ticks), an attacker who controls stream timing can send `max_streams_per_throttling_interval` streams just before the boundary and another full batch just after it, getting roughly double the intended stream count within a much shorter real time span than one throttling interval.

### Finding Description
`throttle_stream` (`streamer/src/nonblocking/stream_throttle.rs:233-271`) is invoked from `SwQos::on_new_stream` for every new QUIC stream a connection opens [1](#0-0) . It calls `stream_counter.reset_throttling_params_if_needed()` and compares `stream_count` to `max_streams_per_throttling_interval` [2](#0-1) .

`reset_throttling_params_if_needed` only resets the counter and window start (`last_throttling_instant`) the next time *any* stream is processed after the interval has already elapsed [3](#0-2) . This is a "lazy" fixed window: the window boundary is set to whatever `Instant::now()` happens to be at the moment a caller notices the interval expired, not to a fixed grid aligned to connection start.

Exploit flow for an unstaked (or low-stake) attacker-controlled connection:
1. At time `t0`, send `max_streams_per_throttling_interval` streams in quick succession. Each call to `throttle_stream` sees `streams_read_in_throttle_interval < max`, so none are throttled; `stream_count` reaches `max`.
2. Wait until just after `t0 + STREAM_THROTTLING_INTERVAL` (e.g., `t0 + 101ms`).
3. Send one more stream. `reset_throttling_params_if_needed` observes `elapsed > STREAM_THROTTLING_INTERVAL`, resets `last_throttling_instant = now` and `stream_count = 0`.
4. Immediately (at `~t0 + 101ms`) burst another `max_streams_per_throttling_interval` streams — none throttled because the counter was just reset.

Net effect: `2 * max_streams_per_throttling_interval` streams accepted within a real time span of ~101ms, i.e., well under `2 * STREAM_THROTTLING_INTERVAL`, and easily within a single sliding 100ms window if timed more tightly around the reset instant. This violates the intended invariant that no sliding `STREAM_THROTTLING_INTERVAL` window should ever see more than `max_streams_per_throttling_interval` accepted streams for that connection.

No other guard compensates for this on the single-connection axis: `SwQos::max_streams_per_throttling_interval` derives the cap from `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration`, which is evaluated fresh on each call and does not track a rolling accepted-stream history [4](#0-3) ; it only limits aggregate global load via a continuous EMA, not this specific per-connection fixed-window bypass.

### Impact Explanation
This is a QoS-evasion class issue: a single unstaked/low-stake connection can accepted roughly double its allotted stream (and therefore transaction packet) rate by precisely timing its bursts around the lazy window boundary, consuming more banking-stage packet-batch capacity than intended relative to its stake share. The magnitude is bounded (~2x, not unbounded) and constrained by the already-small unstaked allocation (`MAX_UNSTAKED_TPS` / `max_unstaked_load_in_throttling_window`), and by the separate connection-count and connection-rate limiters, so it does not by itself cause unbounded memory growth, a panic, or an invalid recorded block — it is a bounded, repeatable rate-limiter-evasion bug affecting fairness among unstaked/low-stake senders, matching the "QoS evasion" bounty category.

### Likelihood Explanation
Exploitation only requires an unprivileged remote client that can open a QUIC connection to the leader's TPU port and control the timing of when it sends streams relative to `STREAM_THROTTLING_INTERVAL_MS` (100ms) — no stake, gossip, or validator control needed. The timing precision required (tens of milliseconds) is easily achievable from a normal network client, making this readily reproducible, though it must be re-triggered every ~100ms window to sustain the effect, and yields at most ~2x amplification rather than unbounded escalation.

### Recommendation
Replace the lazy fixed-window reset with either (a) a true fixed-grid window computed from a monotonic epoch (e.g., `epoch_ms / STREAM_THROTTLING_INTERVAL_MS`) so resets always align to the same absolute grid regardless of when they're observed, or (b) a sliding-window/token-bucket algorithm (e.g., decrement remaining budget continuously based on elapsed time fraction, or track a rolling log of accepted stream timestamps) so that no sliding `STREAM_THROTTLING_INTERVAL` window can ever exceed `max_streams_per_throttling_interval` regardless of when streams are observed relative to a reset boundary.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_boundary_double_burst_violates_sliding_window_invariant() {
    let stats = StreamerStats::default();
    let stream_counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams: u64 = 20; // e.g. unstaked cap per STREAM_THROTTLING_INTERVAL
    let mut accepted_in_window = 0u64;

    // Burst A: fill up to max just before interval elapses.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:1".parse().unwrap(),
            &stream_counter, max_streams).await;
        accepted_in_window += 1;
    }

    // Advance time to just past STREAM_THROTTLING_INTERVAL, triggering a reset on next call.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst B: immediately after reset, another full burst is accepted un-throttled.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:1".parse().unwrap(),
            &stream_counter, max_streams).await;
        accepted_in_window += 1;
    }

    // Invariant expected: no sliding STREAM_THROTTLING_INTERVAL window should exceed max_streams.
    // Actual: 2 * max_streams accepted within ~STREAM_THROTTLING_INTERVAL + 1ms real time.
    assert!(
        accepted_in_window <= max_streams,
        "sliding-window stream cap violated: accepted {accepted_in_window} > {max_streams}"
    );
}
```
This test currently fails (accepts `2 * max_streams`), demonstrating the fixed-window boundary bypass in `ConnectionStreamCounter::reset_throttling_params_if_needed` / `throttle_stream`.

    /// Reset the counter and last throttling instant and
    /// return last_throttling_instant regardless it is reset or not.
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
