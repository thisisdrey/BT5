### Title
Priority-floor QoS gate trusts unsigned, unverified transaction bytes to compute fee/priority, allowing spam to evade admission control ahead of expensive signature verification - (File: core/src/transaction_priority.rs, core/src/sigverify.rs)

### Summary
The external report's core bug class is: an economically significant decision (loan principal / liquidation) is driven by a value that is never verified on-chain before it is trusted, and the only protective check (deadline) is checked too late to prevent loss. The closest concrete, reachable analog on an unprivileged-user path in Agave is the sigverify-stage "priority floor" mechanism, which similarly makes an admission-control decision (whether to drop or admit a packet under load) based on a `priority`/fee value computed from **raw, unverified packet bytes** — before signatures are checked and before dedup-derived guarantees apply — trusting attacker-supplied `compute_unit_price` fields to represent real economic value that will never actually be collected.

### Finding Description
`calculate_priority_from_bytes()` in [1](#0-0)  parses raw packet bytes with `SanitizedTransactionView::try_new_sanitized` and computes a `priority` value from the claimed `compute_unit_price`/`compute_unit_limit` and estimated cost — entirely from unverified bytes, prior to Ed25519 signature verification.

This value is used in `apply_priority_floor_to_batch()` in [2](#0-1)  to decide, under scheduler saturation, which packets to discard *before* the expensive `ed25519_verify_serial` call runs: [3](#0-2) 

Because the floor check happens ahead of `ed25519_verify_serial`, and the priority is derived purely from self-declared, unsigned bytes (`compute_unit_price`), an attacker can freely inflate the claimed `compute_unit_price` in spam packets to make them appear high-priority. This value is never validated against a real signature/fee payment for packets that end up failing sigverify — analogous to the report's `offerAmount` being trusted from an unverified source without an on-chain check that the value actually corresponds to anything real. The only "settlement" check equivalent to the report's deadline-based liquidation is the eventual signature verification, which happens only *after* the floor has already spent the "admission" decision and let the packet through to consume the costlier verification stage.

### Impact Explanation
This does not represent an on-chain solvency loss (Agave nodes don't hold collateral), but it undermines the specific purpose of the priority floor: protecting the node from being overwhelmed during saturation by prioritizing real, fee-paying traffic. Spammed, unsigned/garbage-signature packets that lie about `compute_unit_price` bypass the intended admission control and consume the CPU-expensive `ed25519_verify_serial` step and channel capacity toward banking stage, exactly the resource the floor is meant to protect, while never paying the fee the priority number implied (the transaction is dropped at sigverify or later fails on-chain, so no `underpriced pre-fee work` is ever actually charged). This is a form of QoS evasion / grossly underpriced pre-fee work.

### Likelihood Explanation
Reachable by any unprivileged, unstaked sender submitting raw packets through the normal transaction ingress path (QUIC/UDP → sigverify stage), with no special permissions or trust required — it only requires crafting a byte sequence that satisfies `SanitizedTransactionView::try_new_sanitized` and sets an inflated `compute_unit_price` field. It requires the node to already be under scheduler saturation for the floor to be active, which is precisely the situation an attacker attempting a QoS-evasion/DoS-style attack would want to trigger.

### Recommendation
Do not use unsigned/unverified fee fields to gate admission ahead of the cost they are meant to justify. Options:
- Move the priority-floor check to after Ed25519 verification (or at minimum after a lightweight signature-count/format check) so only signature-valid transactions are prioritized by their claimed fee.
- Rate-limit or separately budget CPU spent on `ed25519_verify_serial` for packets whose priority is self-reported and unverified, independent of the claimed `compute_unit_price`.
- Consider stake-weighted or connection-based throttling (already present via QUIC QoS/stake weighting) as the primary gate, treating the byte-derived priority floor purely as a secondary, non-authoritative heuristic that cannot be used to bypass base rate limiting.

### Proof of Concept
Not independently reproduced in this session (would require running the QUIC/sigverify pipeline under load). Conceptually:
1. Attacker saturates the scheduler buffer to activate the priority floor (`SaturationState`, see [4](#0-3) ).
2. Attacker crafts packets that parse successfully via `SanitizedTransactionView::try_new_sanitized` with an artificially high `compute_unit_price` instruction, but with invalid/garbage signatures.
3. Because `apply_priority_floor_to_batch` computes priority from these unverified bytes before signature checking, the packets pass the floor and proceed to `ed25519_verify_serial`, consuming CPU that the floor mechanism was designed to conserve, then fail verification and are dropped — no actual fee is ever paid for the "priority" that was granted.

Note: I could not fully verify within this session whether `SanitizedTransactionView::try_new_sanitized` performs any signature-format/count validation that would partially mitigate this (e.g., rejecting malformed signature arrays cheaply) — this would need to be checked in `runtime-transaction/src/runtime_transaction/transaction_view.rs`, which the tool access ran out of budget to inspect in full. If that sanitization already enforces meaningful signature-shape checks cheap enough to prevent CPU-cost asymmetry, this finding's severity would be reduced to informational.

/// Apply the scheduler-published priority floor to a single batch in place.
///
/// Below-floor packets are marked `discard`. Returns `(dropped, all_below)`,
/// where `dropped` is the number of packets newly marked and `all_below` is
/// true iff no useful packets remain in the batch (so the caller can skip
/// downstream work for this batch entirely).
fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)

    /// Update the scheduler priority floor.
    ///
    /// Semantics: when the retained scheduler buffer is nearly full, drop
    /// arrivals that are at-or-below the current queue-min priority, i.e. no
    /// better than what the bounded scheduler candidate set would evict.
    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {
        let buffer_size = self.container.buffer_size();
        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);
        let priority_floor = if saturated {
            self.container
                .get_min_max_priority()
                .map_or(0, |(min, _)| min)
        } else {
            0
        };

        self.saturation_state.publish_floor(priority_floor);
    }
