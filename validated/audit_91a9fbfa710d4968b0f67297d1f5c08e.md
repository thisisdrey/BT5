### Title
Out-of-bounds read when parsing attacker-controlled ZIP/JAR central directory entries in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in [1](#0-0)  reads attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) straight out of a memory-mapped, untrusted ZIP/JAR file and advances/dereferences pointers based on them without any bounds check against the mapped file's actual size. This is the same "memory-safety bug while parsing untrusted content" class as CVE-2023-4585, just in Bazel's native ZIP-parsing code (`ijar`) instead of Firefox's parsers.

### Finding Description
`ProcessLocalFileEntry` in the same file deliberately guards every read against the mapped input length via `EnsureRemaining()`, e.g. before reading the file name and extra field: [2](#0-1) .

`ProcessCentralDirEntry`, however, has no such guard. After reading the fixed 46-byte central-directory-header fields, it reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker bytes and immediately:
- `memcpy`s `file_name_length` (clamped only to the caller's `filename[PATH_MAX]` buffer, not to the remaining mapped input) bytes from `p` into `filename`: [3](#0-2) 
- advances `p += file_name_length` and then walks an "extra fields" loop `extra_p != p` driven entirely by attacker-supplied `data_size` values, with no check that `extra_p`/`p` stay inside the mapped buffer: [4](#0-3) 

The code comment even states the (false) assumption that this is safe: "Note that the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" [5](#0-4) . That assumption only holds for a well-formed ZIP; a malicious or truncated central directory entry near the end of the mmap'd region can set `file_name_length`/`extra_field_length`/`file_comment_length` large enough to move `p`/`extra_p` past `zipdata_in_ + input_file_->Length()`, causing subsequent `get_u2le`/`get_u4le`/`get_u8le` reads and the `memcpy` into `filename` to read out-of-bounds memory adjacent to the mapping (heap/mmap over-read), and to attacker-influence the contents copied into the fixed-size `filename[PATH_MAX]` buffer used later by `processor->Accept()`/`Process()`.

This code path is reachable from any consumer of the shared `ZipExtractor`/`InputZipFile` implementation in `zip.cc`, which is used by `ijar` (interface-jar generation, run on every `.jar` used for Java compilation, including jars fetched from external registries/mirrors via `http_jar`/`http_archive`/Maven rules) as confirmed by references in `third_party/ijar/ijar.cc` and `third_party/ijar/zip_main.cc` (the `zipper`/`unzip` tool). Both entry points ultimately call `ProcessCentralDirEntry` to enumerate the untrusted archive.

### Impact Explanation
An unprivileged attacker who controls the bytes of a JAR/ZIP that Bazel's build consumes (e.g., a malicious artifact behind a `http_jar`/`http_archive`/Maven mirror, or a crafted file checked into an untrusted branch) can craft a central directory entry whose length fields point past the end of the mapped file. This drives an out-of-bounds read in Bazel's native `ijar`/`zipper` tooling during routine interface-jar generation or extraction, which can (a) crash the build tool (memory-unsafety-induced SIGSEGV/SIGBUS), or (b) leak adjacent process memory into the `filename` buffer, which is subsequently used for path/attribute decisions in `processor->Accept()`/`Process()`. This is a genuine memory-safety analog to CVE-2023-4585 (uncontrolled input parsing leading to memory corruption/OOB access), not a sandbox or resource-exhaustion issue — it's an integrity failure in native code that trusts unchecked, attacker-supplied length fields.

### Likelihood Explanation
`ijar` is invoked automatically as part of ordinary Java compilation for essentially every `.jar` dependency, including externally-fetched ones, so any attacker able to serve a crafted jar (compromised mirror/registry, MITM-protected-by-nothing legacy `http_jar` without integrity pinning, or a malicious file in a source branch a CI job builds) can trigger this path without any special privileges. The missing bounds check is unconditional — it applies regardless of `sha256`/`integrity` settings on the download, because the vulnerability is in *parsing* the (possibly already-integrity-verified) file's internal structure, not in the download step itself.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before reading/copying `file_name_length`, `extra_field_length`, and `file_comment_length` bytes, and before/while walking the "extra fields" loop, rejecting the entry if the declared lengths would run past `zipdata_in_ + input_file_->Length()`.

### Proof of Concept
Construct a ZIP file where the End Of Central Directory correctly locates a Central Directory, but the last Central Directory Header's `file_name_length` (or `extra_field_length`/`file_comment_length`) field is set to a large value (e.g., `0xFFFF`) such that `p += file_name_length` would extend past the actual mapped file length (i.e., place the header near the very end of the file so the declared length overruns the mmap'd region). Run `ijar`/`zipper` (or trigger a `java_library`/`http_jar` build referencing this JAR) against the crafted file; because `ProcessCentralDirEntry` performs no `EnsureRemaining` check, the tool will `memcpy`/read beyond the mapped buffer, observable as a crash (ASAN heap-buffer-overflow / SIGBUS) or, under ASAN, an explicit out-of-bounds-read report. A native `gtest`/shell-based reproduction under `third_party/ijar/test/` (mirroring `third_party/ijar/test/zip_test.sh`) exercising `zipper x` on such a crafted `.jar` under AddressSanitizer would confirm the OOB read.

Note: I was not able to execute this PoC or find an existing JUnit/shell test that exercises this exact missing-bounds-check path; verification would need to be done with an ASAN-instrumented build of the `zipper`/`ijar` binaries against a purpose-crafted malformed ZIP, as described above.

                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
