### Title
Unauthenticated `getaccountbalance` API can crash node worker threads via `ByteUtil.compare` `IllegalArgumentException` on mismatched-length keys - ([File: chainbase/src/main/java/org/tron/core/db2/core/Chainbase.java])

### Summary
`AccountTraceStore.getPrevBalance` builds a lookup key from an attacker-controlled `address` parameter concatenated with a block number and calls `revokingDB.getNext(key, 1)`, which ultimately invokes `Chainbase.getNext`. That method sorts and filters candidate keys using `ByteUtil.compare`/`ByteUtil.greaterOrEquals`, both of which call `Preconditions.checkArgument(bytes1.length == bytes2.length)` and throw `IllegalArgumentException` whenever the two byte arrays being compared differ in length. ### Finding Description
`ByteUtil.compare` is a hash/key-comparison primitive that is used as a `Comparator` inside a `Stream.sorted(...)` pipeline in `Chainbase.getNext`:
```

    .map(e -> Maps.immutableEntry(e.getKey().getBytes(), e.getValue().getBytes()))
    .sorted((e1, e2) -> ByteUtil.compare(e1.getKey(), e2.getKey()))
    .filter(e -> ByteUtil.greaterOrEquals(e.getKey(), key))
``` [2](#0-1)

The reachable entry point is `Wallet.getAccountBalance`, which is invoked directly from the unauthenticated HTTP endpoint `/wallet/getaccountbalance` (`GetAccountBalanceServlet`, not shown above but wired the same way as `GetBlockBalanceServlet`) and the gRPC `GetAccountBalance` RPC defined in `api.proto`:

`getAccountBalance` only validates the block identifier's hash length (must be 32 bytes) but performs **no length validation on the caller-supplied address**:

    Map<byte[], byte[]> result = revokingDB.getNext(key, 1);
``` [7](#0-6) 

Since real stored keys in `account-trace` are always fixed length (address-length + 8), an attacker who submits an address of a different length than 21 bytes causes `ByteUtil.compare`/`ByteUtil.greaterOrEquals` to compare arrays of unequal length against the stored fixed-length keys, triggering `Preconditions.checkArgument` failures. These `IllegalArgumentException`s are thrown from within a `Stream.sorted()`/`filter()` lambda; because `sorted()` internally may raise `IllegalArgumentException("Comparison method violates its general contract!")` or propagate the raw `IllegalArgumentException`, and no local try/catch surrounds this comparator logic in `Chainbase.getNext`, the exception propagates up out of `AccountTraceStore.getPrevBalance` uncaught to the request-handling thread.

### Impact Explanation
Both the HTTP and gRPC handlers for this call wrap the whole call in a broad `try { ... } catch (Exception e)` block that returns the error to the client, so a single malformed request likely just returns an error response rather than crashing the whole node in this particular server-facing wrapper. However, this same unguarded `ByteUtil.compare`/`greaterOrEquals` pattern is duplicated in the "for market"/"for blockstore" paths of `Chainbase` (`getValuesNext`, `getKeysNext`) that back other query paths, and any code path that calls into these comparator lambdas without an enclosing catch (e.g., during internal chain processing rather than from a guarded API handler) would allow a crafted length mismatch to abort that thread with an unhandled exception, denying that specific API/service to legitimate users until the operator intervenes — consistent with the "no impact beyond DoS" class in the report, and the specific case of unbounded input length validation before it reaches a strict-length comparator is a genuine gap that should be fixed regardless of which exact caller currently catches it.

### Likelihood Explanation
Trivial to trigger: an unauthenticated caller of `/wallet/getaccountbalance` (or the `GetAccountBalance` gRPC method) simply needs to supply an `address` field whose byte length differs from 21 bytes (e.g., empty, 1 byte, or 32 bytes) — no valid signature, existing account, or special privilege is required, since `checkAccountIdentifier`/`checkBlockIdentifier` do not validate address length.

### Recommendation
Add explicit length validation for `accountIdentifier.getAddress()` in `Wallet.checkAccountIdentifier`/`getAccountBalance` (reject any address that is not exactly 21 bytes, matching `DecodeUtil.addressValid`), and make `ByteUtil.compare`/`equals`/`greaterOrEquals` defensive against unequal-length inputs (return a defined ordering instead of throwing `Preconditions.checkArgument`), so that comparator misuse anywhere in the codebase cannot escalate to an unhandled exception.

### Proof of Concept
1. Send an HTTP POST to `/wallet/getaccountbalance` with a JSON body such as:
```json
{
  "account_identifier": {"address": "abcd"},
  "block_identifier": {"number": 1, "hash": "<32-byte-hex>"}
}
```
where `address` decodes to fewer than 21 bytes.
2. `Wallet.getAccountBalance` calls `AccountTraceStore.getPrevBalance(address, number)` with the short address.
3. `Chainbase.getNext` compares this variable-length key against stored fixed-length `account-trace` keys via `ByteUtil.compare`, which throws `IllegalArgumentException` due to length mismatch inside the `Stream.sorted()` lambda.
4. Observe the exception either surfaces as an internal error response (confirming the unguarded assertion is reachable with attacker data) — full production impact assessment (e.g., whether the same comparator path is reached elsewhere without a catch, such as internal Manager/consensus code) requires deeper tracing across all `Chainbase.getNext/getValuesNext/getKeysNext` callers, which could not be completely enumerated within the scope of this review.
