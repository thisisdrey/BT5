Based on my investigation, I found a concrete analog in `VoteWitnessActuator`.

### Title
VoteWitnessActuator does not deduplicate/merge witness addresses in the votes array, causing duplicated Vote entries in AccountCapsule and inconsistent state versus the TVM native path - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
`VoteWitnessActuator.validate()` only checks that the number of vote entries is between 1 and `MAX_VOTE_NUMBER` and that the total vote count does not exceed `tronPower` [1](#0-0) . It never checks whether the same witness address appears multiple times in the `votes` list. In `countVoteAccount()`, every entry from the client-supplied `voteContract.getVotesList()` is appended as-is via `accountCapsule.addVotes(...)` and `votesCapsule.addNewVotes(...)`, with no merging by witness address [2](#0-1) . `AccountCapsule.addVotes()` unconditionally appends a new `Vote` protobuf entry to the account's persisted `votes` list [3](#0-2) .

This is the direct analog of the reported OlympusTreasury bug: an actuator/contract accepts a user-supplied array (`locations` / `votes`) and persists it into on-chain state without deduplicating identical entries (`location` / `vote_address`), even though downstream logic assumes distinct entries per key.

### Finding Description
By contrast, the newer TVM-native voting path (`VoteWitnessProcessor`, reachable from Solidity contracts once `allowTvmVote` is enabled) explicitly merges votes for the same witness into a `Map<ByteString, Long>` before writing to `AccountCapsule`/`VotesCapsule` [4](#0-3) , showing that the codebase's own intended invariant is "one Vote entry per witness address" in `AccountCapsule.votes`. The legacy `VoteWitnessActuator` (used by the plain `VoteWitnessContract` broadcast transaction, reachable by any unprivileged signed transaction) violates this invariant: a single `VoteWitnessContract` with up to `MAX_VOTE_NUMBER` (30) entries can point the same witness address 30 times, and the actuator will persist 30 separate `Vote` entries for that one witness in the voter's `AccountCapsule.votes`. This is confirmed by the existing test `vote1WitnssOneMoreTiems`, which builds a contract with 30 duplicate votes to the same witness via `getRepeateContract(OWNER_ADDRESS, WITNESS_ADDRESS, 1L, 30)` [5](#0-4) , and this passes `validate()`/`execute()` successfully [6](#0-5) .

The persisted `AccountCapsule.votes` list is then consumed in multiple places that iterate it (`MortgageService.computeReward`, `VoteRewardUtil.computeReward`, `UnfreezeBalanceProcessor`, `PrecompiledContracts.VoteCount`) [7](#0-6) [8](#0-7) . While these particular consumers sum contributions linearly (so the mathematical total happens to remain correct because `deltaVi` is multiplied by each entry's vote count and summed), the underlying data-integrity issue matches the report's root cause exactly: the actuator fails to enforce uniqueness on a persisted array key (witness address / location), unlike the parallel TVM-native code path that does enforce it. This produces inconsistent representations of "the same logical position" (one witness) between the legacy actuator path and the TVM path, and permanently bloats a user's `AccountCapsule.votes` with redundant entries that were never deduplicated on any subsequent vote/withdraw/maintenance cycle (since `clearVotes()`/rebuild only replaces per-transaction, not per-witness).

### Impact Explanation
Because reward computation is linear over vote entries, the currently-observed effect is data-integrity/storage bloat rather than a proven fund-theft or double-payment. I was not able to find a downstream consumer of `AccountCapsule.getVotesList()` that assumes at-most-one-entry-per-witness and would double-count value as a result (unlike the TRSRY `getAssetBalance()` case, which explicitly sums balances per location assuming distinct locations). This weakens the severity relative to the original report; it does not clearly rise to "unauthorized account operation, theft, or permanent freezing of funds" on its own. Given the audit-mapping rules, this should be treated with caution — it is a plausible but not conclusively proven Medium-severity data-integrity issue rather than a confirmed fund-impacting bug.

### Likelihood Explanation
Trivially reachable by any account: broadcast a `VoteWitnessContract` transaction with duplicate `vote_address` entries pointing to the same witness within the `MAX_VOTE_NUMBER` (30) limit. No special permissions are required.

### Recommendation
Deduplicate/merge `Vote` entries by `vote_address` in `VoteWitnessActuator.validate()`/`countVoteAccount()` before persisting to `AccountCapsule`/`VotesCapsule`, mirroring the `voteMap` merge logic already implemented in `VoteWitnessProcessor.execute()` [9](#0-8) .

### Proof of Concept
1. Freeze balance to obtain `tronPower` for `OWNER_ADDRESS`.
2. Build a `VoteWitnessContract` with 30 `Vote` entries, all pointing to the same `WITNESS_ADDRESS` with `vote_count=1` each (as in `getRepeateContract`) [5](#0-4) .
3. Call `actuator.validate()` — passes because `votesCount=30 <= MAX_VOTE_NUMBER=30` and `sum(30) <= tronPower` [1](#0-0) .
4. Call `actuator.execute()` — `countVoteAccount()` appends 30 separate `Vote` entries for the same witness into `AccountCapsule.votes` [2](#0-1) , confirmed by test `vote1WitnssOneMoreTiems` [6](#0-5) .
5. Inspect `AccountCapsule.getVotesList()` — it now contains 30 redundant entries for one witness instead of a single merged entry.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
