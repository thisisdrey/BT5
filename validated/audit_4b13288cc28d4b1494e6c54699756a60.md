### Title
Floating-point precision loss in `ExchangeProcessor` AMM swap math allows draining an Exchange pool beyond its actual reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
CVE-2017-7596 is a libtiff bug where a `double`/`float` value exceeds the representable range of the target type, producing undefined/garbage results. java-tron's legacy (non-hardened) AMM bancor-style swap implementation has the analogous bug class: it performs the entire exchange-rate calculation in `double` precision and casts the result straight to `long` with no bounds/consistency check, then applies the result with un-checked `+`/`-` arithmetic to the pool balances. A transaction broadcaster who calls `ExchangeTransactionContract` can pick `sellTokenQuant`/pool state combinations that push the intermediate `double` values to extremes (large ratios, values approaching `Long.MAX_VALUE` when cast back), causing the computed `buyTokenQuant` to diverge from what the pool actually holds.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the bancor-relay formula purely in `double` and truncate to `long`: [1](#0-0) 

This is invoked from the default (non-hardened) branch of `ExchangeCapsule.transaction`, which is only guarded from going negative when `hardenedCalc` is true; the legacy path performs raw `+`/`-` without validating the resulting balances: [2](#0-1) 

The reachable entry point is `ExchangeTransactionActuator.execute`, which calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and then unconditionally credits `anotherTokenQuant` to the caller and applies it to the pool via `Commons.putExchangeCapsule`, with no additional sanity check that the resulting pool balance is non-negative or that `anotherTokenQuant` does not exceed the pool's actual reserve: [3](#0-2) 

Because floating-point arithmetic loses precision (and can approach the representable-range boundary of `double`/`long` conversion, mirroring the CVE's "outside the range of representable values" class), a crafted `sellTokenQuant` can make `(long) issuedSupply` / `(long) exchangeBalance` return a value inconsistent with the true bancor formula result — large enough that `secondTokenBalance - buyTokenQuant` (or the symmetric first-token case) goes negative in the legacy branch. Since only the `hardenedCalc` path (`SafeExchangeProcessor`, gated by the `AllowHardenExchangeCalculation` dynamic parameter) checks `newFirstTokenBalance < 0 || newSecondTokenBalance < 0`, on chains/forks where that hardening flag is not enabled this results in the pool balance being driven below zero (an unbacked negative reserve) while the attacker's account is credited real TRX/TRC10 tokens — a direct pool-draining/theft primitive.

### Impact Explanation
An unprivileged holder of any tokens listed in an on-chain Exchange pool can, via a single `ExchangeTransactionContract`, extract more of the counter-asset than the pool actually holds, or push the pool's recorded balance negative (unbacked balance), which is a concrete theft-of-funds / permanent value-corruption impact matching the "Validate" criteria (unauthorized account operation / theft or unbacked balance).

### Likelihood Explanation
The path only requires funding two ordinary token balances and broadcasting one `ExchangeTransactionContract`; no special privilege, contract deployment, or SR/witness role is needed. Exploitability depends on the network's `AllowHardenExchangeCalculation` dynamic parameter being disabled (the legacy default before the hardening was introduced), which is a config/version-dependent condition rather than a privileged action.

### Recommendation
Force the hardened path (`SafeExchangeProcessor`/`BigDecimal`-based calculation with `addExact`/`subtractExact` and explicit non-negative checks) unconditionally in `ExchangeCapsule.transaction`, removing the legacy double-based `ExchangeProcessor` computation entirely (or gating it behind a hard requirement that `AllowHardenExchangeCalculation` cannot be disabled once activated), and add an explicit invariant check in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction` that both post-trade pool balances are `>= 0` before committing state, regardless of which math mode is active.

### Proof of Concept
1. Create an Exchange pool (via `ExchangeCreateActuator`) between TRX and a TRC10 token with modest reserves (e.g. `firstTokenBalance = 100_000_000`, `secondTokenBalance = 100_000_000`), on a node/network state where `AllowHardenExchangeCalculation == 0` (default/legacy).
2. As an attacker holding a large amount of the "sell" token, submit `ExchangeTransactionContract` with a `sellTokenQuant` chosen so that in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` the ratio `quant / newBalance` or `supplyQuant / supply` pushes the `double` computation to values where the subsequent `(long)` cast yields a `buyTokenQuant` larger than `secondTokenBalance` actually holds (verified experimentally, e.g. via the existing `ExchangeProcessorTest.testStrictMath`/`testHardenedExchange` fixtures at `framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java:218-281`, which already show `ExchangeProcessor` (non-hardened) and `SafeExchangeProcessor` (hardened) diverging (`assertNotEquals(anotherTokenQuant, result)`) for the same inputs).
3. `ExchangeTransactionActuator.execute` credits the attacker with the inflated `anotherTokenQuant` and calls `Commons.putExchangeCapsule` to persist the pool with `secondTokenBalance - buyTokenQuant`, which the legacy branch does not validate for negativity, unlike `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check that exists only for `hardenedCalc == true` in `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:160-162`.
4. The pool ends up with a negative/unbacked reserve while the attacker holds real, spendable tokens — confirming fund theft.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {

    logger.debug("exchangeBalance: " + exchangeBalance);

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();
