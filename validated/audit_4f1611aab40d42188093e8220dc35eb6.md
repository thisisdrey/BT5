### Title
Attacker can permanently block a victim from opening new collateral or debt positions by filling the victim's `MAX_TOKENS_PER_USER` slots with dust `DepositToken` transfers — ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` enforces a per-account cap of `MAX_TOKENS_PER_USER = 30` combined deposit + debt tokens via the `onlyIfAdditionWillNotReachMaxTokens` modifier on `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero, and only the *sender's* lock is checked (`_revertIfLocked(_msgSender, amount_)` in `transfer`). An unprivileged attacker can therefore push dust amounts of every registered `DepositToken` to a victim, permanently occupying the victim's token slots so any subsequent first-time deposit, transfer, or debt issuance to that account reverts with `UserReachedMaxTokens`.

### Finding Description
The chain is fully unprivileged:

1. Attacker deposits a dust amount (or acquires `msdTOKEN` shares) in each `DepositToken` registered in the `Pool` (`depositTokens` set).
2. Attacker calls `DepositToken.transfer(victim, 1)` for each deposit token. `transfer` only checks the attacker's own unlocked balance (`_revertIfLocked`), then `_transfer` sees `balanceOf[victim] == 0` and calls `pool.addToDepositTokensOfAccount(victim)`, which adds the token to `depositTokensOfAccount[victim]`.
3. Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`, the modifier `onlyIfAdditionWillNotReachMaxTokens` reverts every subsequent addition.
4. Result for the victim:
   - `DepositToken.deposit(amount_, victim)` (i.e., any deposit `onBehalfOf_` the victim, including via `NativeTokenGateway.deposit`) reverts in `_mint → addToDepositTokensOfAccount`.
   - Any `transfer`/`transferFrom`/`seize` sending a new deposit token to the victim reverts in `_transfer`.
   - `DebtToken.issue`/`mint` for a synthetic the victim doesn't yet hold reverts in `addToDebtTokensOfAccount`, blocking the victim from borrowing new synths.
   - `Pool.liquidate` payouts that would give the liquidator a new token are also affected for `seize` to a fresh liquidator, and the victim cannot use `SmartFarmingManager.leverage` into new positions.

The victim can evict a dust token by transferring it out (balance → 0 triggers `removeFromDepositTokensOfAccount`), but the attacker can re-dust within the same block or persistently, so the DoS is repeatable at near-zero cost while the victim must actively clear slots.

### Impact Explanation
Liveness / availability impact analog to the FTS crash-DoS class: a victim's position-management surface is hung. All deposits and transfers *to* the victim for tokens they don't already hold revert, and all issuance of new debt types reverts. This is a temporary freezing of funds/positions (funds sent via `deposit(..., onBehalfOf_=victim)` cannot be received; liquidation `seize` flows to fresh recipients revert), sustained as long as the attacker keeps slots filled. No privileged role, oracle manipulation, or governance action is required — only public `transfer`/`deposit` calls.

### Likelihood Explanation
Anyone holding or able to deposit a dust amount of each collateral can execute it. Cost is bounded by the number of registered deposit/debt tokens in a pool (≤ 30 dust transfers). The only mitigation is the victim actively sweeping dust out, which the attacker can front-run or redo cheaply. It does not let the attacker steal funds and does not permanently freeze already-held collateral (existing tokens can still be withdrawn/repaid), which bounds severity to a griefing/DoS.

### Recommendation
- Check the recipient's capacity before mutating balances: in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, treat "account already at cap and token not already in set" as a no-op-revert only where appropriate, or allow the recipient to opt out (e.g., skip adding tokens on inbound transfers when balance is below a dust threshold).
- Alternatively, exempt `seize`/`deposit(onBehalfOf)` paths from the cap for the recipient, or require a minimum first-deposit amount so dust cannot occupy a slot.

### Proof of Concept
```solidity
// Fork test against deployed Pool with registered deposit tokens
function test_DustGriefingBlocksNewPositions() public {
    address victim = makeAddr("victim");
    IPool pool = IPool(POOL);
    address[] memory dTokens = pool.getDepositTokens(); // registered deposit tokens

    // Attacker deposits dust in each collateral and transfers 1 wei of msdTOKEN to victim
    for (uint i; i < dTokens.length && i < 30; ++i) {
        IDepositToken d = IDepositToken(dTokens[i]);
        IERC20 u = d.underlying();
        deal(address(u), attacker, 1 ether);
        u.approve(address(d), 1 ether);
        d.deposit(1 ether, attacker);          // mint shares to attacker
        d.transfer(victim, 1);                 // occupies one slot for victim
    }
    // fill remaining slots with additional debt/deposit tokens as needed...

    // Now: any deposit on behalf of victim into a token they don't hold reverts
    vm.expectRevert(UserReachedMaxTokens.selector);
    newDepositToken.deposit(1 ether, victim);  // _mint -> addToDepositTokensOfAccount reverts

    // And victim cannot issue a new synthetic debt type
    vm.expectRevert(UserReachedMaxTokens.selector);
    newDebtToken.issue(1e18);                  // _mint -> addToDebtTokensOfAccount reverts
}
```
