### Title
Unbounded `git grep --perl-regexp` execution in `SearchFilesByContent` enables CPU-exhaustion DoS - ([File: internal/gitaly/service/repository/search_files.go])

### Summary
`SearchFilesByContent` passes the client-supplied `Query` string, unvalidated for length or complexity, directly into `git grep --perl-regexp -e <query>` with no per-request execution timeout, and Gitaly does not enable any concurrency limiter for this RPC by default. An unprivileged user who owns a repository can submit a pathological PCRE pattern (e.g. `(a+)+$`) and issue many concurrent requests to exhaust CPU on the shared Gitaly node.

### Finding Description
`SearchFilesByContent` in [1](#0-0)  builds a `git grep` invocation using `gitcmd.ValueFlag{Name: "-e", Value: req.GetQuery()}` together with `gitcmd.Flag{Name: "--perl-regexp"}`. Unlike `SearchFilesByName`, which enforces `searchFilesFilterMaxLength = 1000` on its filter regex [2](#0-1) , `SearchFilesByContentRequest.Query` has no length or complexity limit anywhere in `validateSearchFilesRequest` and no length cap defined in the proto [3](#0-2) .

The `grep` command description in `command_description.go` only sets `grep.threads` based on `runtime.NumCPU()` to avoid `git-grep` spawning too many OS threads per invocation [4](#0-3) ; this bounds thread count per process but does nothing to bound the CPU time consumed by a single-threaded PCRE backtracking blow-up, nor does it bound the number of concurrent `git-grep` processes that can be spawned.

The command is executed with `repo.Exec(ctx, ...)` where `ctx` is simply `stream.Context()` — the gRPC request context — with no additional deadline or watchdog applied by the handler itself (unlike, e.g., `runUploadCommand` in the SSH service, which explicitly wraps negotiation with a `pktline.ReadMonitor` timeout [5](#0-4) ). There is no equivalent safeguard in `SearchFilesByContent`.

Concurrency limiting exists in Gitaly (`limithandler` package, `[[concurrency]]` config) but is strictly opt-in per RPC via `cfg.Concurrency` [6](#0-5) ; no such limiter is registered for `SearchFilesByContent` by default (only a default fallback exists for `ReplicateRepository` [7](#0-6) ). Thus, absent an operator explicitly configuring a concurrency cap for this specific RPC, there is no built-in bound on how many concurrent `git grep --perl-regexp` processes an attacker can spawn against their own repository, nor any per-invocation CPU/time budget.

Because `--perl-regexp` uses the PCRE backtracking engine, a pattern like `(a+)+$` matched against non-matching input (or long lines) exhibits classic catastrophic/exponential backtracking, causing a single `git grep` invocation to consume a CPU core for a very long time before completing or being cut off only by client disconnect/gRPC deadline (which the attacker themselves controls, since they are the client).

### Impact Explanation
An attacker can repeatedly and concurrently call `SearchFilesByContent` against a repository they control, each request spawning a `git grep --perl-regexp` process pinned to consuming a CPU core for a duration dictated by the pathological pattern rather than by the actual repository content size. Because Gitaly nodes are multi-tenant (host many repositories/projects), sustained CPU exhaustion degrades or denies service for other tenants' RPCs on the same node — this matches the "Denial of Service of a Gitaly RPC handler" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: any authenticated GitLab user with read access to a repository they own (default access an unprivileged user has to their own project) can call `SearchFilesByContent` repeatedly and concurrently — no special role, config, or secret is required. The exploit requires no exotic tooling, just a crafted regex string, and is straightforward to reproduce and repeat. The main variable affecting real-world severity is the client-imposed gRPC deadline and how quickly the client disconnects (which is attacker-controlled) and whether the deployment enables `grep.threads` reduction or PCRE match-limit defaults, which may cap worst-case blow-up but not eliminate meaningfully elevated CPU cost per request.

### Recommendation
- Enforce a maximum length on `SearchFilesByContentRequest.Query`, mirroring the `searchFilesFilterMaxLength` limit already applied to `SearchFilesByName`.
- Apply a hard, server-side execution timeout/context deadline around the `git grep` invocation in `SearchFilesByContent`, independent of the caller's gRPC deadline, and kill the process if exceeded.
- Consider passing `--perl-regexp` execution through the PCRE `match_limit`/`match_limit_recursion` equivalents (e.g., embedding `(*LIMIT_MATCH=...)` or an equivalent git/PCRE configuration) to bound backtracking work per invocation.
- Register a default `[[concurrency]]` limiter for `SearchFilesByContent` (and similar search RPCs) keyed by repository to bound the number of concurrent `git grep` processes per repo/node.

### Proof of Concept
```go
func TestSearchFilesByContent_PathologicalRegexDoS(t *testing.T) {
	ctx := testhelper.Context(t)
	cfg, client := setupRepositoryService(t)

	repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg)
	// A large-ish file so grep has non-trivial line content to backtrack against.
	gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"), gittest.WithTreeEntries(
		gittest.TreeEntry{
			Path: "big.txt", Mode: "100644",
			Content: strings.Repeat("a", 50) + "!", // no trailing match, forces backtracking
		},
	))

	var wg sync.WaitGroup
	start := time.Now()
	for i := 0; i < 20; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			stream, err := client.SearchFilesByContent(ctx, &gitalypb.SearchFilesByContentRequest{
				Repository: repoProto,
				Query:      `(a+)+$`, // classic catastrophic-backtracking pattern
				Ref:        []byte("main"),
			})
			require.NoError(t, err)
			for {
				if _, err := stream.Recv(); err != nil {
					break
				}
			}
		}()
	}
	wg.Wait()
	// Assert this does NOT take an unbounded/very long time; today there is no
	// per-request execution timeout, so this will demonstrate multi-second-plus
	// CPU-bound stalls proportional to input length, worsening with more concurrent
	// callers and longer non-matching lines.
	require.Less(t, time.Since(start), 2*time.Second, "SearchFilesByContent took excessively long, indicating unmitigated regex backtracking DoS")
}
```
Expected result on the current implementation: wall-clock time grows superlinearly with input length/concurrency and is not bounded by any Gitaly-enforced timeout, demonstrating the missing per-request throttling/timeout called out in the target commandDescription.

// WithConcurrencyLimiters sets up middleware to limit the concurrency of
// requests based on RPC and repository
func WithConcurrencyLimiters(cfg config.Cfg) (map[string]*limiter.AdaptiveLimit, map[string]*limiter.AdaptiveLimit, SetupFunc) {
	perRPCLimits := map[string]*limiter.AdaptiveLimit{}
	perRPCLimitsUnauthenticated := map[string]*limiter.AdaptiveLimit{}

	for _, concurrency := range cfg.Concurrency {
		// Create authenticated limiter
		limitName := fmt.Sprintf("perRPC%s", concurrency.RPC)
		if concurrency.Adaptive {
			perRPCLimits[concurrency.RPC] = limiter.NewAdaptiveLimit(limitName, limiter.AdaptiveSetting{
				Initial:       concurrency.InitialLimit,
				Max:           concurrency.MaxLimit,
				Min:           concurrency.MinLimit,
				BackoffFactor: limiter.DefaultBackoffFactor,
			})
		} else {
			perRPCLimits[concurrency.RPC] = limiter.NewAdaptiveLimit(limitName, limiter.AdaptiveSetting{
				Initial: concurrency.Concurrency(),
			})
		}

		// Create unauthenticated limiter if configured
		unauthLimits := concurrency.Unauthenticated
		if unauthLimits.IsSet() {
			limitNameUnauth := fmt.Sprintf("perRPC%s-unauthenticated", concurrency.RPC)
			if unauthLimits.Adaptive {
				perRPCLimitsUnauthenticated[concurrency.RPC] = limiter.NewAdaptiveLimit(limitNameUnauth, limiter.AdaptiveSetting{
					Initial:       unauthLimits.InitialLimit,
					Max:           unauthLimits.MaxLimit,
					Min:           unauthLimits.MinLimit,
					BackoffFactor: limiter.DefaultBackoffFactor,
				})
			} else if unauthLimits.Concurrency() > 0 {
				perRPCLimitsUnauthenticated[concurrency.RPC] = limiter.NewAdaptiveLimit(limitNameUnauth, limiter.AdaptiveSetting{
					Initial: unauthLimits.Concurrency(),
				})
			}
		}
	}
