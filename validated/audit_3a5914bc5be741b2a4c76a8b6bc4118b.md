### Title
Unbounded `mint_decimals` indexing into `EXP_10_I80F48` causes panics in `calc_value`/`calc_amount`, permanently bricking any bank whose mint has >23 decimals - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
The core risk-engine helpers `calc_value` and `calc_amount` index a fixed 24-entry lookup table (`EXP_10_I80F48`, indices `0..=23`) directly with `mint_decimals as usize`, with no bounds check, mirroring the reported bug class of hardcoding an assumed maximum decimals value.

### Finding Description
`calc_value` and `calc_amount` compute `EXP_10_I80F48[mint_decimals as usize]` unconditionally: [1](#0-0) [2](#0-1) 

`EXP_10_I80F48` has exactly `MAX_EXP_10_I80F48 = 24` entries (10^0 .. 10^23): [3](#0-2) 

`mint_decimals` is a `u8` sourced directly from the SPL/Token-2022 mint (which permits up to 255 decimals), and is stored on the `Bank` account as-is when a bank is created (`Bank::new(... mint_decimals ...)` in `clone_bank.rs` and the various `add_pool*` instructions). There is no evidence in the codebase of a check rejecting mints with `decimals > 23` before this value is stored and later used to index `EXP_10_I80F48`. This is the same root-cause pattern as the reported bug (an unvalidated decimals value driving array/scaling math that assumes a maximum of 18–23 decimals): if `mint_decimals >= 24`, `EXP_10_I80F48[mint_decimals as usize]` is an out-of-bounds array index, which panics in Rust (Solana BPF programs treat a panic as an aborted/failed transaction, not a graceful `MarginfiResult::Err`).

The other locations in the codebase that consume this same table are more defensive: `p0-cli/src/output.rs` explicitly clamps the index (`safe_decimals`), and `programs/marginfi/tests/misc/operational_state.rs`'s `shares_to_ui` uses `.get(decimals as usize).expect(...)`, and `type-crate/src/types/price.rs::scale_supplies` uses `.get(decimals as usize)?` returning `None` instead of panicking. `calc_value`/`calc_amount`, which sit on the hot path of every health check, deposit, withdrawal, and liquidation, do not have this protection.

### Impact Explanation
Since `calc_value`/`calc_amount` are called from the core risk engine (health calculations) and various deposit/withdraw/liquidate paths across every integration (native, Drift, Kamino, Solend, JupLend — see the call-sites in `liquidate.rs`, `drift/deposit.rs`, `drift/withdraw.rs`, `kamino/deposit.rs`, `kamino/withdraw.rs`, `solend/deposit.rs`, `solend/withdraw.rs`, `juplend/deposit.rs`, `juplend/withdraw.rs`), any bank whose underlying mint has 24 or more decimals would panic on any transaction that touches the bank's health/value computation. This causes a permanent denial of service for that specific bank and all positions/accounts referencing it — funds already deposited into such a bank prior to discovery could become permanently unwithdrawable/unliquidatable, matching the "permanent lock/freeze" impact category.

### Likelihood Explanation
Likelihood depends on whether a bank can actually be created for a mint with `decimals > 23` in this codebase's admin/permissionless bank-creation flow. I found `add_pool_permissionless.rs`, which suggests an unprivileged actor might be able to trigger bank creation for an arbitrary mint, but I was not able to fully confirm within the available searches whether decimals validation exists elsewhere in that instruction path (e.g., in `bank_config.rs` validation routines) that would reject such mints before they are persisted. SPL Token and Token-2022 mints can technically be initialized with decimals values up to 255, so the precondition (a mint with ≥24 decimals) is technically reachable on-chain, though such tokens are extremely rare in practice. Given this uncertainty, likelihood should be treated as **Low-to-Medium** rather than confirmed high — this needs verification against the actual add-bank/permissionless-add-bank validation code, which was not fully visible in this scan.

### Recommendation
Add explicit validation when a bank is created/configured (in the shared bank-config validation code, e.g. `bank_config.rs`) rejecting any mint with `decimals >= MAX_EXP_10_I80F48` (24) with a proper `MarginfiError`, and additionally harden `calc_value`/`calc_amount` themselves to use `.get(mint_decimals as usize).ok_or_else(math_error!())?` instead of direct indexing, consistent with the defensive pattern already used in `type-crate/src/types/price.rs::scale_supplies` and the CLI's `safe_decimals` helper.

### Proof of Concept
1. Create (or use Token-2022 mint extensions to configure) a mint with `decimals = 24` (or higher, up to 255).
2. Initialize a marginfi bank for that mint via the admin `add_pool*` instruction (or the permissionless variant, if decimals are unvalidated there).
3. Attempt any deposit, withdrawal, or health-check-triggering transaction (e.g., a borrow against another bank that includes this bank's balance in the health calculation).
4. `calc_value`/`calc_amount` executes `EXP_10_I80F48[24]` (or higher), which is out of bounds for the 24-element array, causing a panic/transaction abort. This makes the bank/mint permanently unusable and can strand user funds already deposited into it.

*Note: I could not conclusively verify from the indexed code whether the bank-creation instructions independently reject mints with decimals ≥ 24 before persisting `mint_decimals`; this would need to be confirmed directly in the repository (e.g., via a Devin session with full file access) to fully validate exploitability.*

pub fn calc_amount(value: I80F48, price: I80F48, mint_decimals: u8) -> MarginfiResult<I80F48> {
    let scaling_factor = EXP_10_I80F48[mint_decimals as usize];

    let qt = value
        .checked_mul(scaling_factor)
        .ok_or_else(math_error!())?
        .checked_div(price)
        .ok_or_else(math_error!())?;

    Ok(qt)
}
