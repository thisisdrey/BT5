### Title
Dust deposits fill victim's token list to `MAX_TOKENS_PER_USER`, permanently DoSing new collateral types and debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.MAX_TOKENS_PER_USER = 30` is enforced inside `onlyIfAdditionWillNotReachMaxTokens`, which reverts before the callee (`DepositToken._mint`, `DepositToken._transfer`, `DebtToken._mint`) can complete. Because `DepositToken.deposit` mints to an attacker-chosen recipient and `DepositToken.transfer` moves balances to any recipient, an unprivileged attacker can fill a victim's `depositTokensOfAccount` set with 1-wei entries of every registered deposit token (plus synthetic-token dust via `SyntheticToken.transfer`-driven paths is not needed — deposit tokens alone suffice). Once the combined `debtTokensOfAccount + depositTokensOfAccount` length reaches 30, every code path that would add a *new* token to the victim's sets reverts: `deposit` into a collateral type the victim hasn't used, `issue`/`mint` of a new debt token (its `_mint` calls `addToDebtTokensOfAccount`), and `seize` during liquidation if the liquidator-victim flow would register a new token. This is a reachable, unprivileged DoS of the position-management surface — the analog of "crafted input crashes the scanning process".

### Finding Description
Relevant mechanics:

- `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` before the token callback even registers the entry (`Pool.sol:143-148`).
- `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are called by `DepositToken._mint` / `_transfer` (`DepositToken.sol:486-488`, `517-520`) and `DebtToken._mint` (`DebtToken.sol:598-600`) whenever the recipient's prior balance is zero. A revert there bubbles up and reverts the whole `deposit`/`issue`/`seize`/`transfer`/`swap` transaction.
- Entries are only removed when a balance goes to exactly zero (`DepositToken.sol:460-462`, `523-525`; `DebtToken.sol` `_burn` counterpart), so the attacker can re-dust the victim cheaply and indefinitely; there is no bulk "remove token from my account" escape hatch that doesn't itself require a successful zero-out transfer of that token.

Attack path (all public, no privileged role):

1. Attacker acquires tiny amounts of underlying for each of the pool's registered `DepositToken`s.
2. For each deposit token `msdX`, attacker calls `msdX.deposit(1, victim)` (or deposits to self then `msdX.transfer(victim, 1)`). Each call hits `_mint`/`_transfer` → `pool.addToDepositTokensOfAccount(victim)`.
3. After filling to 30 entries, any `deposit`, `issue`, `flashIssue`/`mint` (via SmartFarmingManager `leverage`), or `swap`-minted position that would add a token the victim doesn't already hold reverts with `UserReachedMaxTokens`.

The invariant broken is liveness of per-account position management: the victim cannot open new collateral or debt positions, and the attacker can keep the list saturated at negligible cost by re-dusting whenever an entry is removed.

### Impact Explanation
- **Temporary freezing / denial of protocol functionality**: the victim's existing collateral is not stolen and existing-token operations still work, but all *new* collateral types, new borrows (`issue`, leverage), and cross-token swaps that would register a new token are blocked while the list is saturated. For a victim whose current positions are approaching liquidation, this prevents the exact remedial action (depositing a different collateral type) needed to restore health — turning a liveness DoS into an indirect loss-of-funds vector when the position is liquidated.
- Cost to attack is bounded by gas + dust value of the underlying (fractions of a cent per entry on L2 deployments like Base/Optimism/Hemi where the pool is deployed); cost to recover is the victim zeroing out and re-receiving each spam token, which the attacker can re-trigger.

### Likelihood Explanation
- Fully unprivileged: any EOA can call `DepositToken.deposit`/`transfer` (`DepositToken.sol:348-353`, `_mint` at `469-489`); no governor/keeper/oracle/bridge trust assumption is needed.
- Deterministic: no rounding, price, or timing dependency; the set only grows while recipient balance > 0.
- Limitations: does not affect already-held token types, cannot freeze withdrawal of existing balances (`withdraw`/`_burn` only removes set entries), and a victim can recover by transferring each dust balance to zero — hence DoS-class rather than permanent freeze.

### Recommendation
- Add a `removeFromDepositTokensOfAccount`-style self-service escape: let an account force-remove a token entry when its balance is below a dust threshold, or track `balanceOf == 0` membership lazily instead of reverting.
- Alternatively, only count tokens with non-trivial balances toward `MAX_TOKENS_PER_USER` (e.g., require `amount_ > dustThreshold` before `addToDepositTokensOfAccount`), so 1-wei spam cannot consume slots.
- At minimum, `seize` (liquidation path) should not be blockable by the victim's list state; consider making the seize recipient registration bypass the cap since blocking liquidations harms protocol solvency.

### Proof of Concept
Hardhat sketch (deployed pool with N ≥ 30 registered `DepositToken`s — or fill 30 minus existing entries):

```ts
it('griefs victim: fills depositTokensOfAccount to MAX_TOKENS_PER_USER', async () => {
  const victim = alice.address
  const attacker = bob
  const depositTokens = await pool.getDepositTokens() // all registered msdTOKENs

  // Attacker deposits 1 wei of underlying for the victim in each token
  for (const dt of depositTokens) {
    const depositToken = await ethers.getContractAt('DepositToken', dt)
    const underlying = await ethers.getContractAt('ERC20Mock', await depositToken.underlying())
    await underlying.mint(attacker.address, 2)
    await underlying.connect(attacker).approve(depositToken.address, 2)
    await depositToken.connect(attacker).deposit(1, victim) // adds entry for victim
  }
  // Optionally fill remaining slots via dust transfers of the same tokens
  expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30)

  // Victim cannot deposit into a collateral type they don't already hold
  const newMsd = depositTokens[0] // any token victim has 0 balance of after re-dust
  const newToken = await ethers.getContractAt('DepositToken', newMsd)
  const under = await ethers.getContractAt('ERC20Mock', await newToken.underlying())
  await under.mint(victim, parseEther('10'))
  await under.connect(alice).approve(newMsd, parseEther('10'))
  await expect(newToken.connect(alice).deposit(parseEther('10'), victim))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // Victim cannot issue a new debt type either (addToDebtTokensOfAccount reverts)
  await expect(
    msDOGEdebtToken.connect(alice).issue(amount, alice.address)
  ).revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```
