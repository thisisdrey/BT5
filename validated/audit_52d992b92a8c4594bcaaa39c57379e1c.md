### Title
Double-precision rounding error in resource-delegation usage transfer causes fund-accounting loss - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
The Napier `Tranche.sol#_computeTargetBelongsToYT` bug is a classic "divide-then-multiply causes double rounding" pattern. The same class of bug is reachable in java-tron's TRC-10-style resource delegation code (`DelegateResourceActuator`, `UnDelegateResourceActuator`, `UnDelegateResourceProcessor`), which computes resource usage transfers using `double` arithmetic that divides large weight/limit ratios before multiplying by usage/balance values, instead of using the exact multiply-then-divide (`BigInteger`) approach that the same codebase already uses elsewhere (e.g. `ResourceProcessor.calculateGlobalLimitV1/V2`, `RepositoryImpl.usageToBalance`, `EnergyProcessor.calculateGlobalEnergyLimit` when `allowHardenResourceCalculation` is enabled).

### Finding Description
In `UnDelegateResourceActuator.execute()`:
```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
``` [1](#0-0) 

and identically for ENERGY: [2](#0-1) 

The identical unguarded double-arithmetic pattern also exists in the native-contract equivalent used by TVM opcodes for `unDelegateResource`: [3](#0-2) [4](#0-3) 

and in `DelegateResourceActuator.doValidate()`, which similarly computes the ratio `totalNetWeight/totalNetLimit` (or `totalEnergyWeight/totalEnergyCurrentLimit`) as a `double` *before* multiplying by `accountNetUsage`/`energyUsage` and `TRX_PRECISION`: [5](#0-4) 

This is the same root cause as the Napier issue: performing an integer/floating-point division early (`totalNetLimit/totalNetWeight` or `unDelegateBalance/getAllFrozenBalanceForBandwidth`) before the multiplication, rather than combining the operation into a single multiply-then-divide with exact (arbitrary-precision) arithmetic. The codebase itself already recognizes and fixes this exact bug class elsewhere: `ResourceProcessor.calculateGlobalLimitV1`/`calculateGlobalLimitV2` and `RepositoryImpl.usageToBalance` use `BigInteger.multiply().divide()` specifically to avoid "double precision loss" (see the explicit Javadoc and test `testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss` / `testUsageToBalanceCorrectAcrossDoublePrecision`): [6](#0-5) [7](#0-6) 

However, the `DelegateResourceActuator`, `UnDelegateResourceActuator`, and `UnDelegateResourceProcessor` computations of `netUsage`/`energyUsage`/`unDelegateMaxUsage`/`transferUsage` are **not** gated by `allowHardenResourceCalculation()`/`disableJavaLangMath()` and always use the unguarded `double` divide-before-multiply formula, unlike the parallel "hardened" code paths in `ResourceProcessor`/`RepositoryImpl`/`EnergyProcessor`/`BandwidthProcessor`.

### Impact Explanation
Because `double` has only 53 bits of mantissa, for accounts with large frozen balances / large `totalNetWeight`/`totalEnergyWeight` (which grow over time as TVM freeze/delegate activity increases network-wide), the intermediate ratio and the final multiplication can lose precision, producing a `transferUsage`/`netUsage`/`energyUsage` value that differs from the exact (BigInteger) result. Depending on rounding direction this can:
- Under-report `transferUsage` on undelegate, leaving the receiver's usage counter stale/too high relative to actual granted resource, effectively creating resource usage inconsistent with backing frozen balance (unbacked resource accounting), or
- Over-report/limit delegatable amount in `DelegateResourceActuator.doValidate()`, incorrectly rejecting valid delegate transactions (denial of legitimate resource use) — or under-reporting usage and permitting delegation beyond what should be allowed, allowing accounts to obtain more bandwidth/energy than their frozen TRX backs.

This is directly reachable by any account issuing `DelegateResourceContract`/`UnDelegateResourceContract` transactions, or via the TVM `unDelegateResource` native contract triggered from a smart contract call — i.e., a single signed transaction or contract call, matching the required reachability bar.

### Likelihood Explanation
The precision-loss magnitude depends on the actual numeric ranges of `totalNetWeight`/`totalEnergyWeight` and balances in production, which is not directly knowable from the codebase alone; the repository's own hardening tests demonstrate that at realistic scales (e.g. `totalWeight = 1e11`, `usage = 1e8`) the double path diverges from the exact BigInteger path (`testUsageToBalanceCorrectAcrossDoublePrecision`, comment: "usage * weight = 1e19, beyond 2^53"). Since `DelegateResourceActuator`/`UnDelegateResourceActuator` use the same order of operations (divide ratio then multiply) without the BigInteger safeguard applied to the rest of the resource-accounting code, similar divergence is plausible for high-weight/high-balance accounts, though I could not directly confirm the magnitude of loss achievable in these specific call sites (as opposed to the `ResourceProcessor` sites that were explicitly tested) — this is an area of uncertainty given the available index.

### Recommendation
Replace the double-based ratio computations in `DelegateResourceActuator.doValidate()`, `UnDelegateResourceActuator.execute()`, and `UnDelegateResourceProcessor.execute()` with the same `BigInteger` multiply-then-divide approach already used in `ResourceProcessor.calculateGlobalLimitV1/V2` and `RepositoryImpl.usageToBalance`, i.e. compute `numerator.multiply(other).divide(denominator)` in one step instead of dividing first and then multiplying with `double`, gated the same way as the rest of the hardened resource-calculation code paths.

### Proof of Concept
Not directly executable from the available index (no test harness for these exact call sites with adversarial large values was found). Conceptually: choose an account with a very large `getAllFrozenBalanceForBandwidth()`/`totalNetWeight` such that `unDelegateBalance * receiverCapsule.getNetUsage()` (or the ratio computation) exceeds `2^53`, then compare the resulting `transferUsage` from `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` against the exact `BigInteger` computation (as done in `CalculateGlobalLimitHardenTest.testUsageToBalanceCorrectAcrossDoublePrecision`) to observe divergence.

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
