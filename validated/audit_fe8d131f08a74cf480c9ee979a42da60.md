### Title
ERC-20 transfer emulation combined with a non-zero Ethereum `value` field causes wasted relayer fees and a silently-failed transfer in the Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The reported DeXe bug is a class of "simultaneous dual-funding" issue: a function lets a caller fund an action through two independent value channels at once (native ETH `msg.value` and an ERC-20 transfer), but only one channel is actually consumed/refunded, so the other becomes stuck. The nearcore analog is the `near-wallet-contract`, which emulates Ethereum transactions (including ERC-20 `transfer`) on top of NEAR native actions and unconditionally folds the Ethereum transaction's `value` field into the NEAR deposit attached to *any* parsed action — including emulated ERC-20 transfers that also carry a hard-coded `yocto_near: 1` deposit required by the NEP-141 `assert_one_yocto` convention.

### Finding Description
`parse_rlp_tx_to_action` computes the action/kind (which may be `EthEmulationKind::ERC20Transfer`) and then, regardless of the transaction kind, always adds the Ethereum tx's `value` field (scaled to yoctoNEAR) to whatever deposit the action already carries: [1](#0-0) 

For an emulated ERC-20 `transfer`, `eth_emulation::try_emulation` builds a `FunctionCall` to `ft_transfer` with a hard-coded `yocto_near: 1` (the exact amount required by the NEP-141 one-yocto security check): [2](#0-1) 

`Action::try_into_near_action` then sums the hard-coded `yocto_near` with the *additional* `tx.value`-derived amount to form the final deposit attached to the outgoing `ft_transfer` promise: [3](#0-2) 

If the user signs an Ethereum transaction whose calldata is an ERC-20 `transfer(to, value)` call **and** also sets a non-zero native `value` field on that same transaction (i.e., funds the call through both the "ERC-20" channel and the "ETH-native" channel simultaneously, exactly analogous to the DeXe report's dual ETH+ERC20 funding), the resulting NEAR deposit attached to `ft_transfer` will be `1 + additional_value`, not `1`. Because virtually all NEP-141 implementations (including `near-contract-standards`, which this contract itself depends on for `StorageBalance`, etc.) enforce `assert_one_yocto()` on `ft_transfer`, any deposit other than exactly `1` yoctoNEAR causes the whole `ft_transfer` promise to panic and fail.

Independently of that inner failure, `inner_rlp_execute` unconditionally schedules a fee refund to the relayer as soon as the transaction is parsed as `ERC20Transfer`/`EOABaseTokenTransfer` with a non-zero fee — before the underlying action promise is even attempted, and irrespective of whether it will later succeed: [4](#0-3) 

The nonce is also advanced immediately for this transaction kind (since it does not need the address-registrar detour): [5](#0-4) 

So the sequence is: relayer fee is paid out unconditionally, the nonce is consumed (transaction can never be replayed/retried), and then the `ft_transfer` call fails due to the extra attached deposit violating `assert_one_yocto`. The failed promise's NEAR deposit is refunded by protocol-level receipt-refund semantics back to the wallet contract account itself (the deposit was sent from the wallet account as predecessor of that receipt), so the raw NEAR amount is not permanently destroyed — but the **user-paid relayer fee is permanently lost** and the user's intended ERC-20 transfer never executes, even though the transaction is consumed as if it had a chance to succeed.

### Impact Explanation
Every legitimately-signed Ethereum-style ERC-20 `transfer` transaction that also carries a non-zero native `value` field will unconditionally: (1) pay out the relayer fee, (2) permanently consume the wallet's nonce, and (3) fail to execute the intended token transfer due to the NEP-141 `assert_one_yocto` mismatch caused by unconditionally adding `tx.value` to an already-fixed `yocto_near: 1` deposit. This is a genuine, permanent loss of the fee paid by the account owner with no compensating action performed, and it silently defeats a class of otherwise well-formed user transactions. It maps to the DeXe report's core defect: a function that accepts value through two independent channels at once, but whose bookkeeping/consumption logic only correctly accounts for one of them.

### Likelihood Explanation
Reachable by any external, unprivileged holder of an ETH-implicit account calling `rlp_execute` through a relayer (or self) with a normal, validly-signed EIP-2930/legacy Ethereum transaction whose calldata matches the ERC-20 `transfer` selector and whose `value` field is non-zero. No special permissions are required; the action-selection and deposit-composition logic in `internal.rs`/`types.rs`/`eth_emulation.rs` applies identically regardless of caller.

### Recommendation
In `parse_rlp_tx_to_action` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:159-165`), do not blindly add `tx.value`-derived `additional_value` to actions whose deposit is a protocol-fixed sentinel (e.g., NEP-141's mandatory `1` yoctoNEAR for `ft_transfer`/`ERC20Transfer`). Either reject (as a `UserError`) any `ERC20Transfer`/other NEP-141-related emulation transaction that carries a non-zero `tx.value`, mirroring the DeXe fix of reverting when a token-only funding path also receives native value, or route the native `value` portion to a separate, correctly-tracked transfer rather than folding it into the fixed one-yocto deposit of the ERC-20 emulation call.

### Proof of Concept
1. Deploy the wallet contract on an ETH-implicit account with a positive balance.
2. Construct and sign (with the account's Secp256k1 key) an Ethereum-style transaction whose `to`/calldata matches `ERC20_TRANSFER_SELECTOR` (`eth_emulation.rs:19`) with a valid NEP-141 token target, but set `value` to a non-zero amount (e.g., `1` ETH-equivalent).
3. Relay this transaction via `rlp_execute`. Observe that:
   - The relayer immediately receives the computed `tx_fee` refund (`internal.rs:378-385`, `lib.rs:374-385`).
   - The nonce is incremented, permanently consuming this transaction (`lib.rs:358-365`).
   - The subsequent `ft_transfer` promise (deposit `= 1 + value_in_yocto`) panics inside the token contract's `assert_one_yocto()` check, so no tokens are transferred.
4. The account owner has paid the relayer fee for a transaction that can never successfully execute the intended ERC-20 transfer, and cannot resubmit it (nonce already consumed).

Note: this analysis is based on standard NEP-141 `assert_one_yocto` semantics from `near-contract-standards` (used as a dependency by this contract); the exact panic behavior of the specific token contract deployed was not independently re-verified in this session due to tool-call limits, so confirming with a live/integration test against `near-contract-standards`'s fungible token implementation is recommended before treating this as fully proven.
