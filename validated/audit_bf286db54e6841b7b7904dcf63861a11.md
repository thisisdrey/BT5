### Title
Unbounded array allocation from attacker-controlled ABI length words in TVM precompiled contracts - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray` and `extractSigArray` read a "length" value directly out of an ABI-encoded `DataWord` supplied as part of the `data` payload to a precompiled-contract call, and immediately use it to size a Java array (`new byte[len][]`) with no upper bound check against the actual amount of call data available. This mirrors the GNU tar sparse-map class of bug: a small, cheaply-crafted input can encode an attacker-chosen count that is used to drive an allocation before the parser validates that enough real data exists to back that count.

### Finding Description
`extractBytes32Array` reads `len` from `words[offset].intValueSafe()` and unconditionally allocates `byte[len][]`: [1](#0-0) 

`extractBytesArray` and `extractSigArray` have the same pattern; they only bound-check the *offset* word index (`offset > words.length - 1`), not the decoded `len` value itself, before doing `new byte[len][]`: [2](#0-1) 

Because `DataWord` is a 256-bit value fully controlled by the caller (it is simply 32 bytes taken from the call data), `intValueSafe()` can return values up to `Integer.MAX_VALUE` from a *single* 32-byte word, regardless of how small the actual `data` payload is. This is architecturally identical to the tar bug: a count field in the input is trusted to size an allocation before the parser confirms the corresponding payload actually exists.

### Impact Explanation
A crafted contract call (e.g. to one of the shielded-pool / zk precompiled contracts that assemble spend/receive/signature arrays from `DataWord[]` input, such as the code path building `spendCv`/`rk`/`spendProof` arrays around) can supply a tiny calldata buffer whose length-word decodes to a very large integer. This drives an immediate `new byte[len][]` (and subsequent `byte[len][32]`-style nested allocations for spend/receive fields) before any validation that `len` is consistent with the real payload size, causing a large or OutOfMemoryError-triggering allocation on the full node processing the transaction. This is reachable from any unprivileged TVM contract call (a `TriggerSmartContract` transaction invoking the precompiled address), i.e. exactly the "unprivileged transaction broadcaster / contract deployer" threat actor in scope, and can crash or degrade the validating/executing node (denial of service), matching the "node crash or halt" impact bucket.

### Likelihood Explanation
Likelihood is constrained by the fact that this path is only reachable through the specific precompiled-contract entry points that call these helper functions with attacker-supplied `DataWord[]` arrays (the shielded/zk-related precompiles), and by the fact that `getEnergyForData` charges energy based on `data.length`, not on the derived `len`, so the attacker pays only for a small calldata blob while triggering an allocation sized by the decoded word value. I was not able to fully confirm from the available index the exact call sites of `extractBytes32Array` (my search for the exact call expressions returned no results even though the method is referenced 8 times in the file), so I cannot state with certainty every reachable entry point or whether an outer bound check exists earlier in the call chain that limits `len` before these helpers are invoked. This uncertainty should be resolved by a full code review of the file, since the index used here has size limits and may not have surfaced every call site.

### Recommendation
Add explicit upper-bound checks on `len` derived from `words[offset].intValueSafe()` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, ensuring `len` cannot exceed a sane maximum and is consistent with the number of remaining `words` (i.e., `offset + len` must be within `words.length`) before any array is allocated. Reject the call (return failure / `Pair.of(false, ...)`) instead of allocating when the declared count is inconsistent with the actual data length, analogous to the fix Go applied by bounding sparse-map allocations to the actual archive size.

### Proof of Concept
Not independently verified against a running node in this session; conceptual PoC: construct a `TriggerSmartContract` transaction that calls the precompiled-contract address whose handler invokes `extractBytes32Array`/`extractBytesArray` with attacker-controlled `words`, where the "offset" word points at a length word set to `0x7FFFFFFF` (or similar large value) while the actual call data is only a few words long. Since `getEnergyForData` bases energy purely on `data.length`, this costs little energy but drives `new byte[len][]` before any bound check, per [3](#0-2) .

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
