### Title
Unprivileged dust transfers poison other accounts' token lists (`depositTokensOfAccount` / `debtTokensOfAccount`), blocking deposits, mints and fee accrual once `MAX_TOKENS_PER_USER` is reached - (File: contracts/Pool.sol)

### Summary
Analogous to prototype pollution (CWE-471: attacker-controlled writes to state belonging to another entity), any unprivileged EOA can force arbitrary keys into another account's per-account token list in `Pool`. `DepositToken._transfer` adds the token to the *recipient's* `depositTokensOfAccount` list via `Pool.addToDepositTokensOfAccount`, and both `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the combined list length reaches `MAX_TOKENS_PER_USER` (30). Dust-transferring all whitelisted deposit tokens to a victim permanently "fills" their list, after which any attempt to give them a *new* token — deposit, transfer, mint fee accrual, or liquidation seizure — reverts.

### Finding Description
`DepositToken` shares are freely transferable: `transfer`/`transferFrom` only check that the amount does not exceed the sender's *unlocked* balance (`_revertIfLocked`, `DepositToken.sol:180-182, 348-376`). Every `_transfer` where the recipient previously had a zero balance calls `pool.addToDepositTokensOfAccount(recipient_)` (`DepositToken.sol:517-520`), and `_mint` does the same for mint recipients (`DepositToken.sol:485-488`). In `Pool`, both add functions enforce `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:143-148, 204-220`).

Because the check counts *both* lists, an attacker can dust-transfer 1 wei of each whitelisted `DepositToken` (the pool's `depositTokens` set is itself capped at 30 entries, `Pool.sol:703`) to a chosen victim, saturating their account list. From then on:

- `deposit(amount_, onBehalfOf_ = victim)` on any deposit token the victim doesn't already hold reverts inside `_mint → addToDepositTokensOfAccount` — the victim cannot onboard new collateral types.
- `depositToken_.seize(account_, liquidator, …)` inside `Pool.liquidate` reverts if the *liquidator's* list is full — but more importantly, the fee leg `seize(account_, feeCollector, _fee)` adds the token to the **feeCollector's** list (`Pool.sol:591-593`). If an attacker dust-fills the feeCollector account (a contract that likely cannot initiate transfers to clear slots), *every* `deposit()` with `depositFee > 0` (`DepositToken.sol:230-232`) and *every* `withdraw`/`liquidate` that mints fee to the collector reverts — a protocol-wide DoS of deposits and fee-collecting operations on token types the collector doesn't already hold.
- The victim can only recover by manually zeroing each dust balance (one transfer per token), and the attacker can top-up the list again in the same block, making cleanup races unreliable.

Nothing stops this: `transfer` has no `nonReentrant`/`whenNotPaused` issue to exploit, the invariant `UserReachedMaxTokens` is enforced exactly where the attacker wants the revert, and no authorization is required to push entries into someone else's list.

### Impact Explanation
Temporary freezing of funds / griefing with a potentially permanent edge: a targeted user is unable to deposit collateral of any token not already in their list (which can be all remaining types), preventing them from adding collateral to rescue a deteriorating position via new collateral types; and if the `feeCollector` account is saturated, all deposits on new token types revert protocol-wide until governance intervenes — and recovery requires the collector contract to be able to dispose of dust balances, which may be impossible if it lacks a transfer path. Unclaimed yield is also affected: `updateRewardsBeforeTransfer` runs before the revert, but the transfer itself fails.

### Likelihood Explanation
Fully unprivileged: requires only acquiring dust amounts of each `DepositToken` (they are ERC-20-like shares, obtainable by depositing minimal underlying or buying on the market) and calling `transfer(victim, 1)` once per token — ~30 cheap calls. No privileged role, oracle manipulation, or timing dependence. The victim's consent is never required because ERC-20 transfers cannot be refused. Certainty of impact depends only on how many whitelisted deposit/debt tokens exist on the deployed pool and whether the target (especially `feeCollector`) can clear entries afterward.

### Recommendation
Do not revert when the recipient's list is full; alternatives: (a) stop tracking per-account lists for `depositOf`/`debtOf` and instead iterate the global `depositTokens`/`debtTokens` sets (bounded at 30 anyway), or (b) make list membership non-blocking — skip the `add` if it fails rather than reverting the whole transfer/mint, or (c) exempt the `feeCollector` (or give it a bounded/system-maintained list), and allow any account to remove a token entry via an explicit `removeFrom*` escape callable by the account itself.

// Foundry fork test sketch
// Setup: pool with N whitelisted DepositTokens (dt[0..N-1]),
//        attacker holds at least 1 wei of each (via deposit()).

function test_listPoisoning() public {
    address victim = makeAddr("victim");
    // Victim deposits token[0] normally to get a position.
    vm.prank(victim);
    dt[0].deposit(1 ether, victim);

    // Attacker dust-fills victim's list with every other token.
    for (uint i = 1; i < pool.getDepositTokens().length; i++) {
        vm.prank(attacker);
        IDepositToken(pool.getDepositTokens()[i]).transfer(victim, 1);
    }
    // debtTokensOfAccount + depositTokensOfAccount == MAX_TOKENS_PER_USER

    // Any new token type can't be given to victim:
    vm.prank(victim);
    newDepositToken.deposit(1 ether, victim); // reverts: UserReachedMaxTokens

    // Protocol-wide: if attacker targeted feeCollector instead,
    // every deposit with depositFee>0 on a new token type reverts.
}
