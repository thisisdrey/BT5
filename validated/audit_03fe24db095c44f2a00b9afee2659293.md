### Title
Same-block DeleteKey+AddKey nonce reseed permits replay of an already-executed FunctionCall receipt against a third-party contract - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`action_add_key` seeds a regular access key's nonce to `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` rather than preserving/advancing past any nonce previously used under the same public key at the same height, and `verify_nonce` only requires `tx_nonce > current_nonce` (Monotonic mode). If an attacker deletes and re-adds the same public key **within the same block height** as a prior FunctionCall transaction signed by that key, the reseeded nonce collapses back to the value it had before that transaction executed, making the already-executed, already-signed transaction valid again in a later block.

### Finding Description
`action_add_key` (`runtime/runtime/src/access_keys.rs:149`) calls `add_regular_key` (`:230`), which seeds `access_key.nonce = initial_nonce_value(block_height)` = `(block_height-1) * AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (`access_keys.rs:46`) whenever a regular key is added, with no memory of any nonce previously used by an identical public key. `action_delete_key` (`:52`) simply removes the key and its storage accounting, likewise with no memory retained.

`verify_nonce` (`runtime/runtime/src/verifier.rs:212`) in `NonceMode::Monotonic` only requires `tx_nonce > current_nonce` — there is no chain-wide check that a transaction hash or `(signer, public_key, nonce)` tuple has ever been seen before; the only cross-chunk protection is `UniqueChunkTransactions`, which dedupes tx hashes **within a single chunk** (`runtime/runtime/src/lib.rs:2031-2042`), not across blocks.

The nonce-seeding scheme is height-based specifically to prevent replay after key deletion/recreation (this is exactly what `test_transaction_hash_collision` / `test_transaction_hash_collision_for_near_implicit_account_fail` in `integration-tests/src/tests/features/access_key_nonce_for_implicit_accounts.rs` exercise), and it works whenever enough blocks elapse between the original transaction and the delete+recreate so that `(block_height-1)*1_000_000` exceeds the old nonce. However, the seed is a pure function of `block_height`; if the `DeleteKey` and `AddKey` actions for the identical public key are both applied in the **same block** as the block that contained the original signed transaction, the reseeded nonce equals exactly `(block_height-1)*1_000_000`, i.e. one less than the nonce used by the original transaction (`(block_height-1)*1_000_000 + 1`). Re-submitting the original, already-signed and already-executed transaction bytes in a subsequent block then satisfies `tx_nonce (= seed+1) > current_nonce (= seed)` and is accepted again, generating a second, independent `FunctionCall` action receipt with identical `(receiver_id, method_name, args, deposit)` dispatched to the third-party contract.

This is also acknowledged as a known gap in the codebase itself: the test comment in `integration-tests/src/tests/standard_cases/mod.rs:1170-1173` explicitly states "Normally, retries are handled by nonces, but we forget the nonce when we delete a key!" — confirming that key deletion resets replay protection state, and that the fix (height-scaled reseeding) is a probabilistic/heuristic mitigation, not an absolute one, because it depends on enough block-height distance existing between original use and reseed.

No existing check (signature, nonce, access-key permission, gas metering, storage staking, `UniqueChunkTransactions`) stops the specific same-block-reseed sequence, because signature/permission checks pass (it's a validly-signed transaction by an account the attacker controls), and the nonce check is satisfied by construction.

### Impact Explanation
This is a replay/double-spend class bug against a third-party contract's application-level state. Any receiving contract method that is not idempotent per-call (e.g., a staking-pool `deposit`/`stake` handler that increments an internal ledger without its own nonce/idempotency key) would be invoked twice from what the off-chain agreement and the signer treated as a single logical action, silently doubling the recorded deposit/stake for the attacker's account on that contract. This maps to the "double-spend/replay" bounty category. The blast radius is scoped to whatever cross-contract accounting the target dApp performs on deposit — it does not corrupt nearcore consensus state itself (the attacker's own NEAR balance is correctly debited twice, matching the deposit sent twice), but it forces two independent state transitions on a third party from what should have been one signed intent, violating the deposit/tx determinism the third-party contract relies on.

### Likelihood Explanation
Preconditions are narrow but attacker-controlled: (1) attacker must get `AddKey(target)`, the FunctionCall transaction using `target`, `DeleteKey(target)`, and `AddKey(target)` again all included in transactions that land at the exact same `block_height` (a tight but self-controlled batch of self-signed transactions submitted in one go, relying on the chunk producer including multiple of the attacker's own sequential-nonce transactions in a single chunk); (2) the attacker must be able to resubmit the original already-included transaction bytes to a later block/chunk, which is not blocked by any cross-block hash-uniqueness check in the reviewed code. This requires no validator, node-operator, or protocol-level privilege — only ordinary transaction submission — but the precise same-height sequencing is a timing constraint that is not always guaranteed by chunk-production scheduling and would need to be validated empirically against real chunk producer batching behavior, which is not available from static code review alone.

### Recommendation
Persist and check a durable "last used nonce" (or a monotonically non-decreasing high-water-mark) per `(account_id, public_key)` that survives `DeleteKey`, so a re-`AddKey`'d key can never reseed below any nonce previously observed for that exact public key, regardless of block-height granularity. Alternatively, disallow `AddKey` from reusing a public key that was deleted in the same block (or within the same nonce-range window) as its own prior usage, or fold `DeleteKey`+`AddKey` nonce-continuity into the existing `AccessKeyNonceRange`/`ACCESS_KEY_NONCE_RANGE_MULTIPLIER` mechanism so the seed is derived from `max(current height-based seed, previously-recorded nonce + 1)`.

### Proof of Concept
Test-loop / runtime integration test plan:
1. Deploy a minimal "staking-pool-like" contract exposing `deposit()` that increments a `HashMap<AccountId, u128>` ledger with no idempotency key.
2. From attacker account `A` (full-access key `F`), in one prepared batch targeting the same block height:
   a. `AddKey(F-signed, target_pub)` — creates access key `target_pub` on `A`.
   b. `FunctionCall` signed by `target_pub`, nonce `= seed+1`, calling `deposit()` on the pool contract with some deposit amount. Capture the exact signed transaction bytes/hash as `tx1`.
   c. `DeleteKey(F-signed, target_pub)`.
   d. `AddKey(F-signed, target_pub)` again, same public key.
   Submit all four so they land in the same chunk/block height `B` (verify via test-loop block height assertions).
3. Assert `tx1` succeeded and the pool's ledger for `A` shows one deposit.
4. In the next block, resubmit the identical `tx1` bytes via the RPC/test-loop runner.
5. Assert the resubmitted `tx1` is accepted (`SuccessValue`), not rejected with `InvalidNonce`, and that the pool contract's ledger entry for `A` has doubled (asserting deposit count/balance == 2x the original amount), demonstrating unauthorized double execution against the third-party contract from a single logical signed intent. /// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}

/// Helper for checking that duplicate transactions from NEAR-implicit accounts are properly rejected.
/// It creates NEAR-implicit account, deletes it and creates again, so that nonce of the access
/// key is updated. Then it tries to send tx from NEAR-implicit account with invalid nonce, which
/// should fail since the protocol upgrade.
fn get_status_of_tx_hash_collision_for_near_implicit_account(
    protocol_version: ProtocolVersion,
    near_implicit_account_signer: Signer,
) -> ProcessTxResponse {
    let epoch_length = 100;
    let mut genesis = Genesis::test(vec!["test0".parse().unwrap(), "test1".parse().unwrap()], 1);
    genesis.config.epoch_length = epoch_length;
    genesis.config.transaction_validity_period = epoch_length * 2;
    genesis.config.protocol_version = protocol_version;
    let mut env = TestEnv::builder(&genesis.config).nightshade_runtimes(&genesis).build();
    let genesis_block = env.clients[0].chain.get_block_by_height(0).unwrap();
    let deposit_for_account_creation = Balance::from_millinear(100);
    let mut height = 1;
    let blocks_number = 5;
    let signer1 = InMemorySigner::test_signer(&"test1".parse().unwrap());
    let near_implicit_account_id = near_implicit_account_signer.get_account_id();

    // Send money to NEAR-implicit account, invoking its creation.
    let send_money_tx = SignedTransaction::send_money(
        1,
        "test1".parse().unwrap(),
        near_implicit_account_id.clone(),
        &signer1,
        deposit_for_account_creation,
        *genesis_block.hash(),
    );
    height = check_tx_processing(&mut env, send_money_tx, height, blocks_number);
    let block = env.clients[0].chain.get_block_by_height(height - 1).unwrap();

    // Delete NEAR-implicit account.
    let delete_account_tx = SignedTransaction::delete_account(
        // Because AccessKeyNonceRange is enabled, correctness of this nonce is guaranteed.
        (height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER,
        near_implicit_account_id.clone(),
        near_implicit_account_id.clone(),
        "test0".parse().unwrap(),
        &near_implicit_account_signer,
        *block.hash(),
    );
    height = check_tx_processing(&mut env, delete_account_tx, height, blocks_number);
    let block = env.clients[0].chain.get_block_by_height(height - 1).unwrap();

    // Send money to NEAR-implicit account again, invoking its second creation.
    let send_money_again_tx = SignedTransaction::send_money(
        2,
        "test1".parse().unwrap(),
        near_implicit_account_id.clone(),
        &signer1,
        deposit_for_account_creation,
        *block.hash(),
    );
    height = check_tx_processing(&mut env, send_money_again_tx, height, blocks_number);
    let block = env.clients[0].chain.get_block_by_height(height - 1).unwrap();

    // Send money from NEAR-implicit account with incorrect nonce.
    let send_money_from_near_implicit_account_tx = SignedTransaction::send_money(
        1,
        near_implicit_account_id.clone(),
        "test0".parse().unwrap(),
        &near_implicit_account_signer,
        Balance::from_yoctonear(100),
        *block.hash(),
    );
    let response =
        env.rpc_handlers[0].process_tx(send_money_from_near_implicit_account_tx, false, false);

    // Check that sending money from NEAR-implicit account with correct nonce is still valid.
    let send_money_from_near_implicit_account_tx = SignedTransaction::send_money(
        (height - 1) * AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER,
        near_implicit_account_id,
        "test0".parse().unwrap(),
        &near_implicit_account_signer,
        Balance::from_yoctonear(100),
        *block.hash(),
    );
    check_tx_processing(&mut env, send_money_from_near_implicit_account_tx, height, blocks_number);

    response
}

`action_add_key` (`access_keys.rs:149`): rejects a duplicate public key with `AddKeyAlreadyExists` (`:157`), then branches on whether the new key's permission carries a `GasKeyInfo` (`:168`):

1. **Regular key** (`add_regular_key`, `:230`): seeds `access_key.nonce = (block_height-1)*1_000_000` (`initial_nonce_value`, `:46`), writes it with `set_access_key`, and `checked_add`s `access_key_storage_usage` (`:17`) to the account's `storage_usage`. Storage usage uses `public_key.trie_id_len()` (the on-trie identifier length), so an ML-DSA-65 key — stored as a 33-byte SHA3-256 hash form — costs the same as ed25519 rather than its ~1953-byte raw form (`:26`, asserted by `test_ml_dsa_65_access_key_storage_scales`).
2. **Gas key** (`add_gas_key`, `:194`): forces the on-key `nonce` to 0 (`:206`), writes the access key, then writes `num_nonces` separate nonce entries each initialized to `initial_nonce_value(block_height)` via `set_gas_key_nonce` (`:212`). Storage usage uses `gas_key_storage_cost` (`:31`) = the access-key cost plus, per nonce, key length (`trie_id_len + size_of::<NonceIndex>`) + value length (`size_of::<Nonce>`) + `num_extra_bytes_record`.

`action_delete_key` (`access_keys.rs:52`) looks the key up; missing → `DeleteKeyDoesNotExist` (`:84`). Otherwise it branches on `gas_key_info()` (`:62`):
- **Regular** (`delete_regular_key`, `:136`): removes the key and `saturating_sub`s its storage cost.
- **Gas key** (`delete_gas_key`, `:93`): if `balance > MAX_BALANCE_TO_BURN` (1 NEAR) it errors `GasKeyBalanceTooHigh` and leaves the key intact (`:103`); otherwise it adds the balance to `result.tokens_burnt` (the prepaid pot is **burned**, not refunded, `:112`), removes every nonce entry, charges removal compute, removes the access key, and `saturating_sub`s the gas-key storage cost.
