### Title
Non-constant-time authorization token comparison enables remote timing side-channel on write-capable RPC endpoints - (File: `stackslib/src/net/api/postblock_proposal.rs`, `stackslib/src/net/api/postblock_v3.rs`, `stackslib/src/net/api/txsimulate.rs`, `stackslib/src/net/api/blockreplay.rs`, `stackslib/src/net/api/blocksimulate.rs`)

### Summary
Several stacks-node RPC endpoints (`/v3/block_proposal`, `/v2/blocks?broadcast=1`, `/v3/transactions/simulate`, block-replay/block-simulate debug endpoints) authenticate the caller by comparing the `authorization` HTTP header against the node's configured `auth_token`/password using a plain, non-constant-time string comparison (`auth_header != password`). This is analogous in bug-class to CVE-2024-39329 (Django `ModelBackend.authenticate()` timing side-channel): a secret value is compared to attacker-supplied input using a comparison whose timing depends on how many leading bytes match, which is exploitable remotely by an unauthenticated caller over the network.

### Finding Description
`RPCBlockProposalRequestHandler`/`RPCPostBlockRequestHandler`/`RPCTransactionSimulateRequestHandler` etc. each store an optional secret (`self.auth`, sourced from `connection_options.auth_token` in the node config) and validate incoming requests as follows: [1](#0-0) 
The comparison `auth_header != password` is a standard Rust `&str`/`String` equality check, which is not constant-time: it typically returns as soon as a length mismatch or first differing byte is found (via `memcmp`), so the elapsed time correlates with the number of correctly-guessed leading bytes of the secret. The same pattern is repeated for the block broadcast authorization gate: [2](#0-1) 
and is exercised the same way for `blockreplay.rs`/`blocksimulate.rs`/`postblock_proposal.rs` test harnesses that construct handlers with `Some("password".into())` and compare the `authorization` header verbatim. An attacker who can send many HTTP requests to a node's RPC port (default unauthenticated network reachability, since these endpoints exist specifically to be called before authentication succeeds) can measure response latency across repeated guesses to recover the `auth_token` byte-by-byte, breaking the "authenticated vs. not" equality that gates block broadcast, block-proposal submission, and transaction simulation.

### Impact Explanation
If the timing channel is practically exploitable (it depends on network jitter, comparison bytes-per-instruction leak size, and how many attempts are needed — this was not verified experimentally, only from a static-code standpoint), a successful token-recovery attack yields unauthenticated write access to:
- `/v2/blocks?broadcast=1` — unauthenticated block broadcast into the network.
- `/v3/block_proposal` — able to submit block proposals to a miner's signer-connected node, potentially influencing consensus-adjacent flows.
- `/v3/transactions/simulate` — read-side but was explicitly gated as disabled unless a password is set.

This matches the "unauthenticated/unauthorized write to state" category (Critical) if the token can be feasibly recovered remotely.

### Likelihood Explanation
Likelihood is **uncertain/low-to-moderate** and could not be conclusively proven from static analysis alone:
- The comparison is over an HTTP request/response round trip, where network jitter is typically on the order of milliseconds to sub-milliseconds, while a `memcmp`-based short-circuit only saves nanoseconds per correct byte — this is a much noisier channel than the Django in-process timing case (which compared password hashing costs, a millisecond-scale difference).
- No throttling/rate-limiting or lockout was observed on these auth checks in the excerpts reviewed, which would otherwise mitigate brute-force timing attacks.
- I was unable to fully confirm whether any statistical amplification (e.g., repeated sampling to average out jitter) would make this practically exploit given the actual latency differential is sub-microsecond per byte on a memcmp, versus network RTT variance typically much larger. This makes real-world exploitability speculative without further empirical timing measurements, which I could not perform via static code search.

### Recommendation
Replace all instances of direct `String`/`&str` inequality checks against secret tokens (`auth_header != password`) with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or `ring::constant_time::verify_slices_are_equal`) across all affected handlers: `postblock_proposal.rs`, `postblock_v3.rs`, `txsimulate.rs`, `blockreplay.rs`, `blocksimulate.rs`, and any other handler in `stackslib/src/net/api/**` that gates on `self.auth`.

### Proof of Concept
Not independently reproduced/timed in this review. A PoC would require: (1) configuring a node with `auth_token` set, (2) sending a large number of requests to `/v3/block_proposal` (or another gated endpoint) with different candidate authorization headers, (3) statistically measuring response latency per byte-prefix match to attempt secret recovery. I could not execute or time this given the available tools, so exploitability remains unconfirmed and should be treated as a code-quality/defense-in-depth finding pending empirical validation.
