This confirms the concrete analog. The `record_withdrawal_outflow` function in `programs/marginfi/src/utils/general.rs` explicitly performs the same "check-then-defer-append" pattern flagged in the shardus-core report: the group-level cap is validated against a **stale, not-yet-updated counter** (`group.rate_limiter`), and the actual increment only happens later when an off-chain `delegate_flow_admin` aggregates emitted events and calls `update_group_rate_limiter`.

### Title
Group-level rate limiter validates outflows against a stale counter that is never updated at request time, allowing concurrent withdraws/borrows to collectively exceed the configured hourly/daily USD cap - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
`record_withdrawal_outflow` checks a withdraw/borrow's USD value against `group.rate_limiter.hourly/daily.effective_remaining_capacity(...)`, but this check is explicitly documented and tested as **read-only**: the group account's counter is *not* mutated during the user instruction. [1](#0-0)  The real update only lands later, when the `delegate_flow_admin` aggregates `RateLimitFlowEvent`s off-chain and submits a single `update_group_rate_limiter` transaction. [2](#0-1)  This is confirmed directly by the test `group rate limiter is read-only during user instructions`, which asserts the on-chain counter is unchanged after a borrow/repay. [3](#0-2) 

### Finding Description
This mirrors the exact bug class in the report: a limit is enforced by checking a candidate action against a shared counter, but the counter is only updated by a **separate, deferred, batched process** — not atomically with the check. In the shardus-core bug, `addArchiverJoinRequest` checked `archivers.size` (the last-settled state) while every accepted join request was unconditionally appended to `joinRequests` and later promoted to `joinedArchivers` in the next cycle, regardless of how many other requests had already been accepted in the same window.

In marginfi, the analogous window is the interval between successive `update_group_rate_limiter` admin settlements (which the design assumes happens "every ~10 minutes", per the batched aggregation test). [4](#0-3)  Within that window, every individual withdraw/borrow transaction (or any number of them submitted in parallel, from different accounts or in different transactions/slots) independently reads the *same* stale `group.rate_limiter.hourly/daily.cur_window_outflow` and each computes its own `effective_remaining_capacity` against it — none of them see each other's outflow, because none of them write to the group account. [5](#0-4)  Any number of borrows/withdraws that each individually fit under the configured cap can therefore all pass simultaneously, and their sum can far exceed the intended hourly/daily USD outflow cap before the admin's aggregated settlement transaction ever lands.

The design guide itself acknowledges the reason for this architecture — avoiding making the group account writable on every user transaction — but does not mitigate the resulting bypass: "Group-level rate limiting is checked read-only during user actions, then settled later from aggregated events." [6](#0-5) 

The same pattern independently applies to the deleverage withdraw limit flow, which is also "checked read-only during the withdraw, then settled later from aggregated events," via `group.check_deleverage_withdraw_limit`. [7](#0-6) 

### Impact Explanation
The group rate limiter and deleverage withdraw-limit are risk-mitigation controls explicitly intended to cap aggregate USD outflow from a group as "a defense if the risk workflow is abused or compromised," and to prevent runaway liquidity drains. [8](#0-7)  If the actual aggregate outflow during the admin settlement window can exceed the configured hourly/daily cap by an amount limited only by how many independent transactions can be crammed in before the off-chain aggregator catches up, the control provides materially less protection than its configuration implies — undermining insolvency/bad-debt defenses that depend on bounding outflow velocity. This does not itself directly cause bad debt (the risk engine/health checks and bank-level rate limiter, which is updated inline, still independently gate each transaction), but it is a genuine unauthorized bypass of an enforced accounting limit, matching the report's bug class (check against stale aggregate state, unconditional commit, deferred real update).

### Likelihood Explanation
Exploitation requires no special privilege — any set of users (or a single user across several accounts) can simply submit multiple withdraw/borrow transactions within the same settlement window, each individually valid against the last-settled counter. This is a permissionless, unprivileged-user path (borrow/withdraw), consistent with reachable production behavior rather than a purely theoretical race; the codebase's own test explicitly demonstrates and relies on the read-only nature of the check within a batch window. [9](#0-8)  The severity is bounded by how fast/aggressively the off-chain `delegate_flow_admin` settles (design assumption ~10 minutes) and by the `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` staleness check, but neither prevents overshoot within a settlement interval. [10](#0-9) 

### Recommendation
If the group/deleverage outflow caps are meant to be hard limits rather than best-effort monitoring aids, consider maintaining a conservative in-memory/session-level reservation (e.g., an atomic counter account that is written per-transaction, sized to be cheap to touch, or a probabilistic/optimistic-lock design) so concurrent transactions within a settlement window cannot all pass against the same stale baseline. At minimum, documentation and any external-facing claims about the strictness of the group/deleverage caps should clearly state that they are eventually-consistent, best-effort controls with a bounded overshoot window rather than hard real-time limits, and the bank-level (inline, always-consistent) rate limiter should be treated as the primary enforcement mechanism.

### Proof of Concept
1. Configure a group with `groupHourly = 10` (USD) via `configure_group_rate_limits`, and a high bank-level limit so it is not the binding constraint.
2. From two or more distinct marginfi accounts (or two transactions built from the current on-chain group state before either lands), each independently borrow/withdraw an amount whose USD value is individually ≤ 10 (e.g., 8 USD each). Both `record_withdrawal_outflow` calls read `group.rate_limiter.hourly.effective_remaining_capacity()` against the same pre-settlement value (0, since nothing has been aggregated yet) and both succeed, exactly as demonstrated by the "read-only during user instructions" test. [3](#0-2) 
3. Total realized outflow (16 USD) exceeds the configured 10 USD hourly cap before the `delegate_flow_admin` ever calls `update_group_rate_limiter`, and the on-chain check had no way to observe this because the counter is not mutated at request time. [1](#0-0) 
4. Repeat across additional concurrent accounts/transactions within the same ~10-minute settlement window to amplify the overshoot arbitrarily, analogous to how the shardus-core report repeatedly appended join requests past the enforced archiver cap before the cycle record was finalized.

pub fn update_group_rate_limiter(
    ctx: Context<UpdateGroupRateLimiter>,
    outflow_usd: Option<u64>,
    inflow_usd: Option<u64>,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,

        outflow_usd.is_some() || inflow_usd.is_some(),
        MarginfiError::GroupRateLimiterUpdateEmpty

        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::GroupRateLimiterUpdateFutureSlot

        clock.slot.saturating_sub(event_end_slot) <= MAX_RATE_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::GroupRateLimiterUpdateStale

        MarginfiError::GroupRateLimiterUpdateOutOfOrderSeq

            is_valid_rate_limit_amount(inflow),
            MarginfiError::InvalidConfig

            .rate_limiter
            .record_inflow(inflow, clock.unix_timestamp);

## Why These Flows Exist

Both systems avoid making the group account writable in every user transaction.

- Bank-level rate limiting is updated inline because the bank account is already writable.
- Group-level rate limiting is checked read-only during user actions, then settled later from
  aggregated events.
- Deleverage withdraw limits are also checked read-only during the withdraw, then settled later from
  aggregated events.

This avoids serializing all activity in a group through one writable group account.
