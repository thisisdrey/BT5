### Title
Heap-overflow-class crash in VerifyTransferProof precompile via unvalidated attacker-controlled offsets - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The GPAC CVE is a heap overflow caused by trusting attacker-supplied length/offset fields inside a parsed structure without validating them against the buffer size before using them to index/copy memory. The `VerifyTransferProof` Sapling precompiled contract in java-tron shares the same bug class: it reads offset fields directly out of attacker-controlled `data` and then re-indexes into that same buffer using those unchecked offsets.

### Finding Description
`VerifyTransferProof.execute()` only validates the *overall* length of `data` against a fixed set of sizes: [1](#0-0) 

It then parses three offset fields directly from the untrusted input and uses them, unchecked, as new indices into the very same `data` array: [2](#0-1) 

`spendOffset`, `spendAuthSigOffset`, and `receiveOffset` are fully attacker-controlled 32-bit integers taken from the first 96 bytes of `data` (`parseInt(data, 0/32/64)`). Unlike `ByteUtil.parseBytes`, which right-pads out-of-range reads with zero bytes, `PrecompiledContracts.parseInt`/`parseLong` (used at `spendOffset`, `spendAuthSigOffset`, `receiveOffset`, `parseLong(data, 1280)`, etc.) are invoked with these attacker-chosen offsets without any prior bounds check comparing them to `data.length`. Because `data.length` is fixed to one of `{2080, 2368, 2464, 2752}` while `spendOffset`/`spendAuthSigOffset`/`receiveOffset` can be any `int` value (including negative, huge positive, or values far beyond the fixed-size region), the subsequent `parseInt(data, spendOffset)` / `parseInt(data, spendAuthSigOffset)` / `parseInt(data, receiveOffset)` calls read at attacker-chosen positions in the array. If the underlying parse helper does not clamp/right-pad (as `ByteUtil.parseBytes` does) and instead directly slices `data[offset..offset+n]`, a crafted offset causes an `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` deep inside the precompile.

This mirrors the GPAC `uncv_parse_config()` bug class: an untrusted "config"/offset value taken from parsed data is trusted to index into the same buffer without being checked against the buffer's actual bounds, leading to an out-of-bounds access.

I was not able to fully re-confirm the exact body of `parseInt`/`parseLong` before the tool budget ran out (I only located their call sites, not the full method bodies), so I cannot state with 100% certainty whether they silently clamp or throw. Given the surrounding code style in this file (fixed-size arrays, direct `System.arraycopy` from `data` at computed offsets such as `data[i * 32 + 224]`), and the absence of any explicit `if (spendOffset < 0 || spendOffset > data.length) return ...` guard before their use (unlike the length-array check at lines 1469-1471), this is a credible reachable analog and should be verified directly in a full checkout.

### Impact Explanation
`VerifyTransferProof` is a TVM precompiled contract, reachable by any account issuing a `CALL`/`STATICCALL` to the corresponding precompile address with crafted calldata — i.e., any unprivileged transaction broadcaster or contract that forwards attacker data. An uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown from deep inside offset parsing, if not fully absorbed by the enclosing `catch (Throwable any)` block at line ~1604, or if it manifests as excessive/failed allocation before reaching that catch, can disrupt transaction execution and, in the worst case (depending on how the runtime propagates such exceptions through the VM `try`/`catch` in `VM.play`), crash node processing for that transaction, matching the DoS impact of the source CVE.

### Likelihood Explanation
The `data.length` whitelist check only guards the fixed-size structure; it performs no correlation between the attacker-controlled offset fields and any legitimate range within that fixed size. This makes the vulnerable code path trivially reachable by supplying calldata of one of the 4 allowed lengths (e.g., 2080 bytes) with `spendOffset`/`spendAuthSigOffset`/`receiveOffset` set to out-of-range values.

### Recommendation
Add explicit bounds validation immediately after parsing `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and similarly for `leafCount`-derived indices), rejecting the call (returning `Pair.of(true, DataWord.ZERO().getData())`) if any offset is negative or if `offset + requiredFieldSize` exceeds `data.length`, before any subsequent `parseInt`/`parseLong`/`System.arraycopy` call uses it. Apply the same audit to the sibling precompile `VerifyMintProof` and any other Sapling-related precompiled contracts in `PrecompiledContracts.java` that parse fixed offsets from untrusted `data`.

### Proof of Concept
1. Craft a transaction that performs a TVM `CALL` to the `verifyTransferProof` precompile address (see `getContractForAddress`) with `data.length == 2080` (a value accepted by the `SIZE` whitelist).
2. Set the first 32 bytes of `data` (the `spendOffset` field) to a large value such as `0xFFFFFFFF` (or any value causing `spendOffset` to resolve to an out-of-range index, e.g., a negative int or an int greater than `data.length`).
3. Broadcast the transaction; when `execute()` reaches `parseInt(data, spendOffset)` at [3](#0-2) , the offset is used unchecked against `data.length`, triggering an out-of-bounds access analogous to the GPAC heap overflow.
