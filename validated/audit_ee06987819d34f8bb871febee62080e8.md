I found a concrete, reachable analog: the StackerDB chunk-authentication digest omits the StackerDB's contract identity, and in real deployments multiple sibling StackerDB contracts intentionally share the exact same slot-to-signer mapping — enabling unauthenticated cross-contract chunk replay.

### Title
Unauthenticated StackerDB chunk replay across sibling contracts due to signature not binding to `smart_contract_id` - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest as `slot_id || slot_version || data_hash`, deliberately excluding which StackerDB (`QualifiedContractIdentifier`) the chunk belongs to. Because several `.signers-<page>-<message_id>` StackerDB contracts in the same reward cycle are configured with an *identical* signer→slot_id mapping (they all read the same `stackerdb-get-signer-slots-page` value), a validly-signed chunk observed for one contract can be replayed verbatim into a sibling contract and will pass all server-side checks, without the replaying party possessing any private key.

### Finding Description
The signed digest only commits to `slot_id`, `slot_version`, and `data_hash`:
<cite repo="Loderfordw/stacks-core--007" path="libstackerdb/src/libstackerdb.rs" start="159="/> [1](#0-0) 

`verify()` only checks that the signature recovers to the expected public-key hash — it takes no `smart_contract_id` parameter at all, so a signature is portable across any StackerDB whose slot owner happens to match: [2](#0-1) 

Both the HTTP write path and the P2P validation path enforce authorization purely by looking up `(smart_contract, slot_id) -> signer address` and calling `verify(&signer)` — they never fold the contract identity into what was actually signed: [3](#0-2) [4](#0-3) 

The SQL schema comment for the `chunks` table even documents this gap explicitly ("the following is NOT covered by the signature ... signer"): [5](#0-4) 

Critically, this isn't a theoretical coincidence. The `.signers` boot contract stores exactly two slot-mapping vectors (`stackerdb-signer-slots-0` / `-1`, keyed only by `reward-cycle % 2`), and every `signers-<page>-<message_id>` contract for the same page reads the *same* mapping via `stackerdb-get-signer-slots-page`: [6](#0-5) [7](#0-6) 

This is confirmed by the test suite iterating multiple `message_id` values against the identical expected slot list per page: [8](#0-7) 

So for a given reward cycle, signer address `S` owns the same `slot_id` in every `signers-0-*` contract (and separately in every `signers-1-*` contract). A chunk `S` legitimately signs and posts to `signers-0-A` (e.g. via `POST /v2/stackerdb/.../chunks`) can be taken by *any* network observer — no key required — and POSTed unmodified to `signers-0-B`, `signers-0-C`, etc. As long as the target's currently-stored version for that slot is lower (which is the common case, since versions across sibling DBs are usually independent counters) and the payload fits the target's `chunk_size`/`max-writes` (essentially unbounded, `max-writes = u32::MAX`), `try_replace_chunk` will accept it.

### Impact Explanation
This is an unauthenticated write into StackerDB state: an attacker who never holds any signer's private key can force one signer-message-type's payload bytes to be committed and gossiped as though they were a valid slot update in a different message-type StackerDB. Consumers of that sibling DB (e.g. signer state-machine/block-vote message processors) will deserialize/interpret attacker-selected byte content — sourced from a *different* message schema — as canonical data for their own message type, which can corrupt signer coordination state, trigger parser errors, or (depending on the consuming code's tolerance for malformed/foreign payloads) be leveraged to desynchronize signer views. It also propagates network-wide, since accepted chunks are relayed via `StackerDBPushChunk` gossip (`node.set_relay_message`), matching the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" categories.

### Likelihood Explanation
High. No secret material is required — only observation of a chunk that is already broadcast over gossip or readable via the public `GET /v2/stackerdb/.../chunks/...` endpoint. The only precondition (same signer owning the same slot_id across sibling `signers-<page>-*` contracts) is guaranteed by the current boot-contract design for every reward cycle, not an edge case.

### Recommendation
Include the `smart_contract_id` (or a stable per-DB namespace derived from it) inside `SlotMetadata::auth_digest()`, so a chunk's signature is only valid for the specific StackerDB it targets. This requires a coordinated wire/format change (chunk verification is used by both nodes and the `stacks-signer` client), so it should be versioned/rolled out carefully, but closes the replay path at the signature level rather than relying on operational happenstance for chunk versions to diverge across sibling DBs.

### Proof of Concept
1. During a reward cycle, signer `S` is assigned `slot_id = 3` in both `signers-0-0` and `signers-0-1` (guaranteed, since both read `stackerdb-get-signer-slots-page(u0)`).
2. `S` legitimately signs and POSTs a chunk `(slot_id=3, slot_version=5, data=D)` to `signers-0-0`; the chunk is accepted and gossiped via `StackerDBPushChunk`.
3. An unrelated, unauthenticated observer captures this chunk (from the gossip message or via `GET /v2/stackerdb/<S>/signers-0-0/chunks/3`).
4. The observer POSTs the *same* `(slot_id=3, slot_version=5, sig, data=D)` tuple to `/v2/stackerdb/<S>/signers-0-1/chunks`. Since `signers-0-1`'s slot 3 is also owned by `S`, and its stored version for slot 3 is `< 5`, `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:411-423`) accepts it — `D` (data intended for message type "0-0") is now committed and re-gossiped as canonical data for message type "0-1", without `S` ever authorizing that write.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
