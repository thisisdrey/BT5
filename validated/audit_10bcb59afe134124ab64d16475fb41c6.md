### Title
ProcReceiveHook RPC trusts caller-supplied TransactionID without verifying the caller is the legitimate receive-pack process for that transaction - ([File: internal/gitaly/service/hook/proc_receive.go])

### Summary
`HookService.ProcReceiveHook` ( [1](#0-0) ) accepts a stream whose first message carries `EnvironmentVariables`, from which `gitalyhook.NewProcReceiveHandler` extracts a `HooksPayload` and, critically, a `TransactionID` ( [2](#0-1) ). The handler is then handed to `ProcReceiveRegistry.Transmit`, which looks up the waiting `ReceivePack` RPC purely `by handler.TransactionID()` ( [3](#0-2) ) with no check that the calling process actually is the `git-receive-pack` subprocess that Gitaly itself spawned for that specific transaction/repository.

### Finding Description
This mirrors the audited flash-loan bug: `MarginTrading.executeOperation` trusted `msg.sender == lendingPool` but never checked `_initiator == address(this)`, letting anyone drive a flash loan whose funds were pulled from the `MarginTrading` contract. Here, `ProcReceiveHook` similarly authenticates only "is this a legitimate gRPC caller to the internal HookService" but never authenticates "is this actually *my own* `git-receive-pack` subprocess for transaction N." The only binding between a `ProcReceiveHook` stream and a specific in-flight `ReceivePack` operation is the caller-supplied `TransactionID` embedded in the `HooksPayload` environment variable blob sent in the request itself — a value that is entirely attacker-controlled from the RPC caller's perspective and, per `transaction_registry.go`, is a small sequential integer.

Any caller able to reach the HookService socket (this is the same trust boundary as the real `gitaly-hooks` binary uses) can therefore construct a `ProcReceiveHookRequest` with a guessed/enumerated `TransactionID` belonging to a *different, concurrent* legitimate push (potentially against a different repository — note the proto comment that `ProcReceiveHookRequest.repository` is "unused currently since we gather all information from stdin", [4](#0-3) ), register itself via `Transmit`, and thereby hijack the `ProcReceiveHandler` that the victim's `ReceivePack` RPC is waiting on ( [5](#0-4) ). From there the attacker fully controls the pkt-line protocol exchanged with `git-receive-pack`: they decide which reference updates are reported, can forge `AcceptUpdate`/`RejectUpdate` decisions ( [6](#0-5) ), and can `Close` the handler with an artificial success/error status, all for a transaction and repository they did not initiate.

### Impact Explanation
An attacker that wins this race can:
- Cause a legitimate victim push to appear to fail or succeed with attacker-decided per-ref outcomes, corrupting the victim's `ReceivePack` result (DoS / integrity of the write path) — the WAL commit path in `procReceiveHook` relies entirely on what `handler.ReferenceUpdates()`/accept-reject decisions report ( [7](#0-6) ).
- Since the hijacked handler is driven by the attacker's own `stdin` stream rather than the victim's actual git process, the attacker can also inject fabricated reference-update proposals that get evaluated as if they came from the real `git-receive-pack`, subverting the intended cross-check between what Git wants to do and what gets committed to the WAL.

This is a DoS/integrity issue on the receive-pack write path rather than direct fund/object theft, but it breaks the assumption that only Gitaly's own hook invocation for a given transaction can drive that transaction's outcome — the exact "missing initiator check" class from the report.

### Likelihood Explanation
Exploitability depends on the caller being able to reach the internal `HookService.ProcReceiveHook` RPC and being able to guess a `TransactionID` for a transaction it did not create. Because IDs are small sequential integers with no per-transaction secret binding, and because any process that can spawn the `gitaly-hooks proc-receive` hook (i.e., anyone who can trigger a push at all) already has the exact same access path to this RPC, the barrier to hitting another concurrent transaction is purely a race/enumeration problem, not a privilege problem — this is analogous to how anyone could call Aave's public `flashLoan` naming `MarginTrading` as receiver. It requires precise timing to target a specific victim's concurrent transaction, which limits ease of exploitation but does not require any elevated privilege beyond normal push access.

### Recommendation
Bind the `ProcReceiveHandler` to more than just the caller-supplied `TransactionID`. Options:
- Have `ReceivePack` generate and pass a per-invocation secret/nonce (in addition to the transaction ID) through the `HooksPayload` when spawning `git-receive-pack`, and require `ProcReceiveHook` to present that same nonce before `Transmit` will bind the handler to the waiter.
- Alternatively, verify server-side that the `ProcReceiveHook` stream originates from a subprocess actually spawned by this same Gitaly process for that transaction (e.g., via a process-scoped/one-time credential minted at `RegisterWaiter` time and never sent anywhere except into the specific hook subprocess's environment), analogous to the `require(_initiator == address(this))` fix in the reference report.

### Proof of Concept
1. Attacker starts a push (`ReceivePack`) to their own repository, which registers a waiter for `TransactionID = N` in `ProcReceiveRegistry` and spawns a `proc-receive` hook whose `HooksPayload` env carries `TransactionID = N`.
2. Concurrently, a victim pushes to a different repository on the same Gitaly node; their `ReceivePack` registers a waiter for `TransactionID = N+1` (or nearby, given the sequential counter in `transaction_registry.go:26-33`).
3. Instead of letting its own real `proc-receive` hook subprocess call back, the attacker directly opens a `ProcReceiveHook` gRPC stream (using the same HookService access it already has) and sends a crafted `HooksPayload` environment variable claiming `TransactionID = N+1` along with attacker-chosen stdin pkt-lines.
4. `NewProcReceiveHandler` builds a handler for `TransactionID = N+1` and `registry.Transmit` binds it to the victim's waiting `ReceivePack` (`procreceive_registry.go:101-120`), because the lookup is solely keyed by the numeric ID with no verification the caller actually is the victim's spawned hook process.
5. The attacker's stream now drives the victim's receive-pack outcome (accept/reject arbitrary refs, or abort the transaction), completing the hijack without ever being the legitimate initiator of transaction `N+1`.

// Transmit transmits a handler to its waiter.
func (r *ProcReceiveRegistry) Transmit(ctx context.Context, handler ProcReceiveHandler) error {
	r.m.Lock()
	ch, ok := r.waiters[handler.TransactionID()]
	r.m.Unlock()

	if !ok {
		return fmt.Errorf("no waiters for id: %d", handler.TransactionID())
	}

	// It is possible that the RPC (waiter) returned because receive-pack
	// returned an error. In such scenarios, we don't want to block indefinitely.
	select {
	case <-ctx.Done():
		return ctx.Err()
	case ch <- handler:
	}

	return nil
}
