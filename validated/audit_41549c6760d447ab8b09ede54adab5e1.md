### Title
Unprivileged attacker can fill a victim's per-account token list via dust `deposit(..., onBehalfOf_)` / `transfer`, DoSing the victim's deposits, issuance, and receipt of new collateral - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The reference bug is a pre-auth, single-packet crash that halts service for all users. The Metronome analog is a permissionless griefing vector: `Pool` tracks every `DebtToken`/`DepositToken` an account has ever held in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30`, and reverts any *new* token addition once the cap is reached. Because `DepositToken.deposit` credits an arbitrary `onBehalfOf_` account and `DepositToken.transfer` is unrestricted (only the sender's unlocked balance is checked), any EOA can push dust balances of every supported collateral into a victim's list until it hits 30, after which the victim can no longer receive a new deposit-token type or debt-token type.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (`contracts/Pool.sol:143-148`, `:204-220`).

Two unprivileged entry points add a victim to these lists without their consent:

- `DepositToken.deposit(amount_, onBehalfOf_)` mints to `onBehalfOf_` via `_mint`, which calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was zero (`contracts/DepositToken.sol:211-237`, `:486-488`). Attacker deposits 1 wei of each collateral into their own account, or directly deposits dust `onBehalfOf_ = victim`.
- `DepositToken.transfer(to_, amount_)` calls `_transfer`, which also calls `addToDepositTokensOfAccount(recipient_)` on a first-time receipt (`contracts/DepositToken.sol:348-354`, `:517-520`). The only check is `_revertIfLocked` on the *sender*.

Debt tokens are non-transferable (`DebtToken.transfer`/`transferFrom` revert, `contracts/DebtToken.sol:507-519`), so an attacker cannot push debt tokens into a victim's list; the achievable fill is bounded by the number of registered `DepositToken`s in the pool (itself capped at 30 via `addDepositToken`, `contracts/Pool.sol:703`). If the deployed pool has enough collateral types that `existing + deposited_dust ≥ 30`, all subsequent `deposit` of a new collateral, `issue`/`leverage` creating a new debt-token entry, `Pool.liquidate` `seize` delivering a new deposit-token to a full liquidator, and plain `transfer`/`transferFrom` to the victim revert with `UserReachedMaxTokens`.

### Impact Explanation
The invariant broken is per-account liveness: a user can be forcibly barred from depositing additional collateral types and from taking on new debt types. For a victim with an open position approaching the liquidation threshold, this prevents the standard self-rescue of "deposit more collateral" when the collateral they hold is exhausted and they need a different collateral type — their account is bricked for the intended remediation while still being liquidatable. Any smart-contract wallet or strategy contract (whose slots the attacker fills) that cannot itself call `transfer` to shed the dust is *permanently* frozen out of new deposits. This matches the accepted impact of temporary freezing of funds / liveness denial.

### Likelihood Explanation
Fully permissionless: no governor, guardian, oracle, or bridge involvement; no flash loan needed. Cost is dust amounts of each supported underlying plus gas. The attack's reach depends on the deployed collateral count — the attacker can only fill the victim's list up to the number of registered deposit tokens, so the victim is fully blocked only if their existing entries plus the pool's collateral count reach 30. Victims can recover by transferring the dust balances out (balance → 0 triggers `removeFromDepositTokensOfAccount`), but contracts lacking a generic token-call path cannot, and the attacker can re-grief after cleanup.

### Recommendation
- Enforce a minimum credited amount before calling `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (e.g., only register tokens above a dust threshold), making the grief economically non-dust.
- Alternatively, allow `deposit`/`seize`/`issue` to proceed when the cap is reached by treating the per-account lists as a cache and falling back to iterating the global `depositTokens`/`debtTokens` sets in `depositOf`/`debtOf` for the missing entries.
- At minimum, let the account itself cheaply shed unwanted entries (already possible via `transfer` for EOAs), and document that integrator contracts must expose a token-recovery function.

### Proof of Concept
Hardhat (fork or local) sketch:

```ts
// attacker: any EOA; victim: target account
const depositTokens: DepositToken[] = await Promise.all(
  (await pool.getDepositTokens()).map(a => ethers.getContractAt('DepositToken', a))
);

// Fill victim's list: deposit dust on behalf of victim for each collateral
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  await underlying.mint(attacker.address, 1);            // or swap/acquire 1 wei
  await underlying.approve(dt.address, 1);
  await dt.deposit(1, victim.address);                   // adds dt to victim's list
}

// Sanity: victim list is now at cap (existing + pushed >= 30)
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(30);

// Victim deposit of any NEW collateral type reverts
await expect(newCollateralDepositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim issue of a synth whose debt token is new to them also reverts
await expect(newDebtToken.connect(victim).issue(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note: severity is bounded by the number of registered `DepositToken`s on the deployed pool; if `pool.getDepositTokens().length` plus the victim's existing entries cannot reach 30, the attack only partially fills the list and is not exploitable on that deployment. Confirm the deployed collateral count on the target chain before reporting.
