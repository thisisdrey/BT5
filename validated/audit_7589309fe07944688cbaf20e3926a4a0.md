### Title
Global (cross-repository) load shedding lets an attacker-controlled CPU-heavy accessor RPC cause `LoadShedder` to snipe unrelated users' in-flight RPCs - (File: internal/burdenmonitor/load_shedder.go)

### Summary
The `LoadShedder` reacts to node-wide critical resource pressure by cancelling the top-N highest-CPU in-flight RPCs across the *entire* Gitaly node, without any per-repository or per-tenant scoping. An attacker who can trigger CPU-intensive processing on their own repository (e.g. via a pathologically crafted object graph fetched through an accessor RPC) can push the node into "critical" pressure and, because the shedding selection is purely CPU-ranked and global, cause the shedder to also cancel other unrelated tenants' in-flight requests with `RESOURCE_EXHAUSTED`, even though those tenants did nothing wrong. This mirrors the referenced report's pattern: one actor's crafted, resource-heavy artifact silently imposes a cost/consequence on an unrelated victim through an automatic, unscoped accounting/enforcement mechanism.

### Finding Description
`BurdenMonitor.UnaryInterceptor`/`StreamInterceptor` registers every accessor RPC into a single shared `entries` map keyed only by a random UUID, without any repository or tenant partitioning: [1](#0-0) 

When a critical condition fires (e.g. sustained CPU PSI or OOM events), `LoadShedder.shed` asks the `BurdenMonitor` for the top 10 CPU-consuming entries across **all** tracked RPCs system-wide and cancels every one of them: [2](#0-1) 

`GetTopNEntries`/`entriesSortedBy` operate over the full `bm.entries` map with no filtering by repository, correlation ID, or requesting actor - it is purely a global CPU-time ranking: [3](#0-2) 

Because the load monitor's critical-pressure conditions are node-level aggregates (`AggregatedPressure`, cgroup PSI, etc., documented in `doc/load-management-architecture.md`), any single tenant that can push the node into critical pressure (e.g. via CPU-expensive Git object processing over an accessor RPC such as `CommitDiff`, `GetBlobs`, `ListCommits`, or a costly `PostUploadPackWithSidechannel` negotiation) triggers a *global* shed event. The shed event then cancels whichever 10 RPCs currently have the highest CPU time - a set that is not guaranteed to include (or be limited to) the RPC that actually caused the pressure spike. A concurrently-running, entirely legitimate RPC belonging to another user/repository/project that simply happens to be CPU-heavy (e.g. a large but ordinary diff or blob fetch) will be collaterally cancelled with `RESOURCE_EXHAUSTED`, exactly as an innocent bystander whose transaction is forced to pay/consume for another actor's manufactured resource usage in the referenced bug.

### Impact Explanation
This is a concrete, reachable DoS of an RPC handler for entirely unrelated users: an attacker's own (single-tenant) requests can be engineered to consume CPU on their own repository, tripping node-wide critical thresholds, after which the shedder's global, unscoped top-N-by-CPU selection cancels in-flight RPCs belonging to other tenants sharing the same Gitaly node/storage. Cancelled RPCs return `RESOURCE_EXHAUSTED` to legitimate clients, causing failed clones/fetches/diffs for uninvolved users/projects — a cross-tenant availability impact triggered entirely by an ordinary, unprivileged user's crafted repository content or fetch pattern.

### Likelihood Explanation
Reaching the vulnerable path requires only: (1) an ordinary authenticated user able to perform accessor RPCs (fetch/clone, `CommitDiff`, `GetBlobs`, etc.) against a repository they control, and (2) the ability to make that RPC unusually CPU-heavy (e.g. large diffs, deep delta chains, pathological pack negotiation) — both are standard, unprivileged capabilities on a multi-tenant Gitaly instance. The mechanism is gated by the `BurdenMonitorTrackCommands` feature flag and requires the node to already be under load-monitor-detected critical pressure (PSI thresholds or OOM events), so likelihood scales with how loaded the shared node normally is; on a busy multi-tenant node this condition is not unusual, making the collateral-cancellation effect realistically triggerable.

### Recommendation
Scope load shedding decisions to the RPC(s)/repositories that are actually responsible for the resource spike rather than a purely global top-N-by-CPU ranking: correlate the triggering condition to specific repositories/tenants where feasible, prefer shedding entries associated with the source of the pressure event, and/or apply per-repository/per-tenant fairness weighting (similar to the existing per-repo concurrency limiter) before falling back to a global cancellation. At minimum, log/alert distinctly when a shed event cancels RPCs unrelated to the repository that caused the triggering condition, and consider bounding how many distinct repositories/tenants can be affected by a single shed event.

### Proof of Concept
1. Tenant A creates a repository with content engineered to be CPU-expensive to process for an accessor RPC (e.g., a large/complex diff for `CommitDiff`, or a fetch pattern that causes expensive `git-upload-pack` negotiation), and repeatedly issues such requests.
2. This sustained CPU usage pushes the node's PSI/cgroup CPU signal past the critical threshold configured for `newPSICriticalCondition(psiResourceCPU, ...)`, emitting a critical `loadmonitor.Event`.
3. `LoadShedder.run` receives the event and calls `shed`, which calls `bm.GetTopNEntries(shedTopN, SortByCPU)` — a global, cross-tenant ranking — and cancels the top 10 CPU-heavy in-flight accessor RPCs via `entry.Cancel(err)`. [4](#0-3) 
4. Tenant B, running an unrelated but CPU-moderately-heavy legitimate accessor RPC on a different repository at the same time, is among the top 10 by CPU time and receives `RESOURCE_EXHAUSTED`, despite having no relation to Tenant A's activity — demonstrating cross-tenant DoS caused entirely by Tenant A's unprivileged, crafted repository content.

func (ls *LoadShedder) shed(ctx context.Context, event loadmonitor.Event) {
	entries := ls.bm.GetTopNEntries(shedTopN, SortByCPU)
	reason := SortByCPU.reason()

	for _, entry := range entries {
		ls.cancel(entry, reason)
	}

	ls.logger.WithFields(log.Fields{
		"condition":    event.ConditionName,
		"reason":       event.Description,
		"sniped_count": len(entries),
	}).WarnContext(ctx, "load shedder cancelled in-flight RPCs")
}

// EntriesSortedBy returns all tracked RPC entries sorted by the specified field.
// The returned entries are sorted in descending order (highest resource usage first).
func (bm *BurdenMonitor) entriesSortedBy(sortBy SortBy) []*RPCEntry {
	entries := bm.Entries()

	switch sortBy {
	case SortByCPU:
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].TotalCPUTime() > entries[j].TotalCPUTime()
		})
	case SortByMemory:
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].TotalMemory() > entries[j].TotalMemory()
		})
	case SortByDuration:
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].StartTime.Before(entries[j].StartTime)
		})
	}

	return entries
}

// GetTopNEntries returns the top N tracked RPC entries sorted by the specified
// field, in descending order. If fewer than N entries exist, the returned slice
// is shorter than N.
func (bm *BurdenMonitor) GetTopNEntries(n int, sortBy SortBy) []*RPCEntry {
	entries := bm.entriesSortedBy(sortBy)
	if len(entries) > n {
		entries = entries[:n]
	}
	return entries
}
