## Analysis

The HackerOne report describes a class of bug where a resource that is normally gated by a strict validation path (uploading a Design requires Developer role) can be pushed through an alternate mutation path ("Move to") that re-parents the resource without re-checking the destination's constraints.

The closest reachable analog in java-tron is in the TVM's `SUICIDE`/`SUICIDE2` opcode handling. The **normal** path for delegating/moving frozen TRX resources — `DelegateResourceActuator` — explicitly forbids sending frozen resources to a smart-contract address: [1](#0-0) 

However, `Program.suicide()` / `Program.suicide2()` move the *same class* of state (an account's FrozenV2 balances for bandwidth/energy/TRON_POWER) to an arbitrary attacker-chosen `inheritor` address via `transferFrozenV2BalanceToInheritor`, and that helper never checks whether the inheritor is a contract account: [2](#0-1) 

### Title
Frozen TRX permanently locked via `SUICIDE`/`SUICIDE2` to a contract inheritor, bypassing the "no delegate to contract" safeguard - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`DelegateResourceActuator.validate()` deliberately rejects delegating frozen v2 resources to a `Contract`-type account because contract accounts cannot broadcast signed `UnfreezeBalanceV2Contract`/`WithdrawExpireUnfreezeContract` transactions to reclaim them. This safeguard exists only in that one actuator. The TVM's contract-inheritance path (`SUICIDE`/`SUICIDE2`) reaches the same underlying state — an account's FrozenV2 balances — through `transferFrozenV2BalanceToInheritor` in `Program.java`, which performs no equivalent check on the `inheritor` address.

### Finding Description
When a smart contract self-destructs, `Program.suicide()` (line 451) and `Program.suicide2()` (line 520) call `transferFrozenV2BalanceToInheritor(owner, inheritorAddr, repo)` unconditionally for any caller-supplied `inheritorAddr`: [3](#0-2) 

That helper directly increments the inheritor's `FrozenV2` fields (bandwidth/energy/TRON_POWER): [4](#0-3) 

There is no check whether the `inheritor` is `AccountType.Contract`. This contrasts with the only legitimate on-chain path for creating/moving frozen v2 balances between accounts — `DelegateResourceActuator` — which explicitly rejects contract receivers: [1](#0-0) 
and its native-contract twin `DelegateResourceProcessor`: [5](#0-4) 

Because a contract account has no private key, it can never sign an `UnfreezeBalanceV2Contract` or `WithdrawExpireUnfreezeContract` transaction to release resources credited to it. Any attacker deploying a contract that self-destructs to a target contract address as the inheritor (its own address, another attacker-controlled contract, or even a third-party contract to grief it) causes the associated TRX principal represented by that FrozenV2 balance to become permanently unfreezable — the value is accounted for in `FrozenV2` state but the corresponding unfreeze/withdraw actuators can never be triggered by that account.

### Impact Explanation
This is a permanent freezing-of-funds bug: TRX that should eventually be unlockable (after the freeze lock period) becomes irrecoverably stuck once credited as FrozenV2 balance on a contract account, since no actuator-level transaction can ever originate from a contract address to reclaim it. This matches "permanent freezing of funds" impact criteria.

### Likelihood Explanation
Trivially reachable by any unprivileged account: deploy a contract, freeze balance for itself (FreezeBalanceV2), then call `SUICIDE`/`SELFDESTRUCT` targeting a contract address as inheritor. No special privilege, committee proposal, or witness/SR cooperation is required — only `supportDR()`/`allowTvmFreezeV2` chain features need to be enabled (already default on current mainnet).

### Recommendation
Add the same check present in `DelegateResourceActuator.validate()` ("Do not allow delegate resources to contract addresses") inside `transferFrozenV2BalanceToInheritor` (and its FreezeV1 counterpart `transferDelegatedResourceToInheritor`) in `Program.java`: if the resolved inheritor account is `AccountType.Contract`, redirect the frozen-resource transfer to the black-hole address (as already done when `owner == obtainer`) instead of crediting the contract account directly.

### Proof of Concept
1. Deploy `ContractA`, fund it with TRX.
2. From `ContractA`, call the native `freezeBalanceV2`-equivalent path (or have it freeze for itself) so it accumulates `FrozenV2` balance for bandwidth/energy.
3. Deploy `ContractB` (a plain contract with no special logic, i.e. any contract address with no private key).
4. From `ContractA`, execute `SELFDESTRUCT(ContractB_address)`.
5. Observe `Program.suicide()` invokes `transferFrozenV2BalanceToInheritor(ContractA, ContractB, repo)`, which credits `ContractB`'s `FrozenV2BalanceForBandwidth`/`FrozenV2BalanceForEnergy` directly.
6. Attempt to broadcast `UnfreezeBalanceV2Contract` or `WithdrawExpireUnfreezeContract` with `owner_address = ContractB` — impossible, since no private key/signature can be produced for a contract address, so the frozen TRX is permanently locked.

  private long transferFrozenV2BalanceToInheritor(byte[] ownerAddr, byte[] inheritorAddr, Repository repo) {
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddr);
    AccountCapsule inheritorCapsule = repo.getAccount(inheritorAddr);
    long now = repo.getHeadSlot();

    // transfer frozen resource
    ownerCapsule.getFrozenV2List().stream()
        .filter(freezeV2 -> freezeV2.getAmount() > 0)
        .forEach(
            freezeV2 -> {
              switch (freezeV2.getType()) {
                case BANDWIDTH:
                  inheritorCapsule.addFrozenBalanceForBandwidthV2(freezeV2.getAmount());
                  break;
                case ENERGY:
                  inheritorCapsule.addFrozenBalanceForEnergyV2(freezeV2.getAmount());
                  break;
                case TRON_POWER:
                  inheritorCapsule.addFrozenForTronPowerV2(freezeV2.getAmount());
                  break;
              }
            });
