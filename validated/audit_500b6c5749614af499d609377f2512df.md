## Finding

### Title
Disabling the `ALLOW_MARKET_TRANSACTION` Committee Parameter Permanently Locks Assets Escrowed in Open TRC10 Market Orders - ([File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java])

### Summary
`MarketSellAssetActuator` and `MarketCancelOrderActuator` both gate their `validate()` logic on the same governance-controlled boolean, `DynamicPropertiesStore.supportAllowMarketTransaction()`. Placing a sell order transfers (locks) the seller's TRX/TRC10 balance into the order, and the **only** way to get those funds back before a match is to submit a `MarketCancelOrderContract`. If the committee later disables the market feature (sets `ALLOW_MARKET_TRANSACTION` back to `0` via a normal proposal), `MarketCancelOrderActuator.validate()` unconditionally rejects the cancel transaction, so users with pre-existing active orders can never reclaim their escrowed assets. This mirrors the reported Sui Kiosk pattern exactly: a single feature-toggle protects both the "deposit" and the "withdraw" path, and disabling it after users already have funds "in flight" (locked in the vault/order) leaves no fallback to release them.

### Finding Description
`MarketSellAssetActuator.validate()` requires `dynamicStore.supportAllowMarketTransaction()` to place an order, and moves the seller's balance/token out of their account into the order (`transferBalanceOrToken`), matching/escrowing it until a trade fills or the order is cancelled. [1](#0-0) 

The only redemption path, `MarketCancelOrderActuator`, guards its `validate()` with the identical flag check: [2](#0-1) 

and only if that check passes does it reach `MarketUtils.returnSellTokenRemain(...)`, which is what actually credits the escrowed remainder back to the owner's account: [3](#0-2) 

`ALLOW_MARKET_TRANSACTION` is a standard committee proposal parameter, toggled through the normal proposal/vote mechanism (not a malicious-actor-only knob) in `ProposalService`/`ProposalUtil`, exactly like any other chain parameter (e.g. `ALLOW_TVM_FREEZE`, `ALLOW_SAME_TOKEN_NAME`). [4](#0-3) 

There is no code path that lets a user cancel an already-open order, or that lets the network automatically settle/return outstanding orders, once `ALLOW_MARKET_TRANSACTION` is turned off — cancellation and creation share the exact same gate. This is functionally identical to the Sui Kiosk bug: `uid_mut` (needed by extensions to move funds in/out) is gated by `allow_extensions`, and turning that flag off after an extension already holds user funds leaves no fallback to retrieve them.

### Impact Explanation
Any TRX/TRC10 balance placed into an active (unfilled or partially filled) market order becomes permanently unrecoverable the moment the committee sets `ALLOW_MARKET_TRANSACTION` back to `0`, because both order creation and order cancellation are blocked by the same check, and no other actuator provides access to `returnSellTokenRemain`. This is a permanent freezing-of-funds condition for every account with an open order at the time the feature is disabled — a protocol design flaw that can be triggered by an entirely legitimate, non-malicious governance action (a normal committee proposal to pause the market feature, e.g. in response to a bug elsewhere in `MarketSellAssetActuator`).

### Likelihood Explanation
Likelihood is realistic rather than purely theoretical: disabling a controversial or buggy feature via committee proposal is a normal operational response (the codebase already toggles many `Allow*` flags this way), and any user who placed an order and has not been fully matched before that vote passes is immediately and irreversibly affected. No attacker action is required beyond having placed an order before the parameter flip — an unprivileged trader can trigger this at any time by placing an order and being caught by the disable event, and there is no code recourse to reverse it.

### Recommendation
Decouple the "open new orders" gate from the "cancel/settle existing orders" gate. `MarketCancelOrderActuator.validate()` (and any order-settlement path) should not depend on `supportAllowMarketTransaction()`, or should provide an explicit fallback/migration mechanism so that once the feature is disabled, holders of already-open orders can still retrieve their escrowed balance via cancellation, mirroring the "termination path" fix ultimately adopted upstream by Sui for the Kiosk API.

### Proof of Concept
1. Committee proposal enables `ALLOW_MARKET_TRANSACTION` (as needed for any market trading to work).
2. User A submits `MarketSellAssetContract` selling TRX for TRC10 token X; `MarketSellAssetActuator.execute()` debits A's TRX balance into an active `MarketOrderCapsule` (partial or no match).
3. Committee submits/passes a proposal setting `ALLOW_MARKET_TRANSACTION` back to `0` (e.g., in response to an unrelated exploit in the market module).
4. User A submits `MarketCancelOrderContract` to reclaim the remaining escrowed TRX.
5. `MarketCancelOrderActuator.validate()` throws `ContractValidateException("Not support Market Transaction, need to be opened by the committee")` at [5](#0-4) 
before `returnSellTokenRemain` ever runs — User A's TRX remains locked in the order with no way to retrieve it as long as the parameter stays disabled.
