### Title
StackerDB slot-signature does not bind to the target contract, allowing cross-contract chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::verify`/`sign` authenticate a chunk write using only `(slot_id, slot_version, data_hash)` — the target StackerDB `QualifiedContractIdentifier` is never part of the signed digest. Because the same signer is assigned the same `slot_id` across multiple sibling `.signers-N-X` StackerDB contracts within one signer set, a chunk that is validly signed for one contract's slot is also a valid signature for the identically-numbered slot in a *different* contract. This is the StackerDB analog of the reported "whitelisted function not scoped to a specific contract" bug: the authenticator (signature) is not scoped to the specific resource (contract_id) it's meant to protect.

### Finding Description
`SlotMetadata::auth_digest()` computes `hash(slot_id || slot_version || data_hash)` with no contract binding: [1](#0-0) 

`verify()`/`sign()` operate purely on this digest and a supplied `StacksAddress`, never on the contract identifier: [2](#0-1) 

On the write path, `StackerDBTx::try_replace_chunk` looks up the expected signer for `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` — again with no check that the signature was produced *for this smart_contract*: [3](#0-2) 

The same gap exists in the p2p/gossip validation path, `PeerNetwork::validate_received_chunk`, which resolves `get_slot_signer(smart_contract_id, slot_id)` and calls `slot_metadata.verify(&addr)` — the contract id is used only to look up which address *should* own the slot, never mixed into the signed payload: [4](#0-3) 

Critically, slot-to-signer assignment is identical across the sibling per-message-type contracts within a signer set. The Clarity boot contract `signers.clar` stores a single page of `(signer, num-slots)` tuples per signer-set (`stackerdb-signer-slots-0`/`-1`), and *every* `.signers-N-X` contract for that set reads the same page via `stackerdb-get-signer-slots-page`: [5](#0-4) 

The node applies that identical slot ordering to configure each of the `MessageSlotID` contracts (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`), each of which resolves to its own `QualifiedContractIdentifier` but shares the same signer→slot_id mapping: [6](#0-5) 

Consequently, for a given signer at slot index `i`, a chunk `(slot_id=i, slot_version=v, sig, data)` that is validly signed and accepted into contract A (e.g. `signers-0-1`) will *also* pass signature verification for contract B (e.g. `signers-0-2`), because the signature never committed to which of the two contracts it targets. The write endpoint that accepts this is unauthenticated w.r.t. contract identity — anyone (not just the signer, since these chunks are broadcast in the clear over p2p and via the public `POST /v2/stackerdb/:principal/:contract/chunks` HTTP RPC) can capture a legitimately-signed chunk and resubmit it against a different sibling contract: [7](#0-6) 

### Impact Explanation
This breaks the intended invariant that a stored/relayed StackerDB chunk in a given contract is an authentic message *for that specific message type/contract*. An attacker (any unprivileged network participant who observes gossip traffic) can replay a signer's `BlockResponse`-signed chunk into the `StateMachineUpdate` or `BlockPreCommit` contract's identical slot (or vice versa), as long as the target slot's expected version there is still satisfiable (e.g., an unused/low-version slot). The chunk is accepted, stored, and further gossiped by `handle_unsolicited_StackerDBPushChunk`, i.e. forged/misattributed data is propagated network-wide as if it belonged to the wrong protocol contract, potentially confusing downstream consumers such as `StackerDBListener`/`GlobalStateEvaluator` (which parses the raw chunk bytes as a specific `SignerMessageV0` variant) or bloating other contracts' storage with attacker-replayed data. This qualifies as unauthorized write to StackerDB / network-wide propagation of forged data.

### Likelihood Explanation
High. No secret key or privileged role is required by the attacker — StackerDB chunks are broadcast unencrypted over the p2p network and can also be submitted through the public `/v2/stackerdb/.../chunks` HTTP endpoint on any node. The only precondition is that the target slot in the sibling contract hasn't already advanced past the replayed `slot_version` — trivially satisfiable for freshly-rotated reward cycles/contracts or slots that a given signer hasn't yet written to in the sibling contract.

### Recommendation
Bind the signed digest to the specific StackerDB contract by including the `QualifiedContractIdentifier` (or a stable contract-scoped tag) in `SlotMetadata::auth_digest()`, and require verification against that same contract context in both `try_replace_chunk` and `validate_received_chunk`. This mirrors the audit's recommendation to scope authorization to the specific target rather than accept it wherever the recovered address happens to match.

### Proof of Concept
1. Registered signer `X` is assigned `slot_id = 3` in both `signers-0-1` (BlockResponse) and `signers-0-2` (StateMachineUpdate), per the shared slot page in `signers.clar`.
2. `X` legitimately signs and pushes chunk `C = (slot_id=3, slot_version=1, data=D)` to `signers-0-1` via normal signer operation; this chunk (and its signature `sig`) is visible on the p2p network/gossip.
3. Attacker `A` (no keys, no special role) crafts a `StackerDBPushChunkData`/HTTP `POST /v2/stackerdb/<addr>/signers-0-2/chunks` request reusing the exact same `(slot_id=3, slot_version=1, sig, data=D)` tuple, but targeting contract `signers-0-2`.
4. The receiving node's `validate_received_chunk` (or `try_replace_chunk` via the RPC handler) resolves `get_slot_signer("signers-0-2", 3) == X`, calls `slot_metadata.verify(&X)`, which succeeds because the digest never included the contract id — the chunk is accepted and stored/gossiped under `signers-0-2` even though it was never authorized for that contract.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
