### Title
Order-execution authorization bypasses account freeze, allowing withdrawals/repayments on a frozen `MarginfiAccount` - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
`is_signer_authorized` evaluates the `ACCOUNT_IN_ORDER_EXECUTION` bypass *before* the `ACCOUNT_FROZEN` check, so an account that is simultaneously flagged as frozen (by the admin) and in order execution (by the permissionless order-fill flow) will authorize any signer, not just the group admin, exactly like the Ethena `WHITELISTED_ROLE`/`BLACKLISTED_ROLE` overlap where a positive-state check (`hasRole(WHITELISTED_ROLE)`) is evaluated without excluding the conflicting state (`BLACKLISTED_ROLE`).

### Finding Description
`is_signer_authorized` in [1](#0-0)  checks flags in this order:
1. `allow_receivership && ACCOUNT_IN_RECEIVERSHIP` → authorize any non-authority signer
2. `allow_order_execution && ACCOUNT_IN_ORDER_EXECUTION` → authorize **any** signer, unconditionally
3. `ACCOUNT_FROZEN` → authorize only the group admin
4. Otherwise → authorize only the account authority

Because check (2) short-circuits and returns before check (3) is ever evaluated, if an account is both `ACCOUNT_FROZEN` and `ACCOUNT_IN_ORDER_EXECUTION` at the same time, the frozen restriction is never enforced — any signer is authorized.

`lending_account_withdraw` and `lending_account_repay` both call `is_signer_authorized(&a, g.admin, authority.key(), true, true)` (i.e., `allow_receivership=true`, `allow_order_execution=true`), as seen in [2](#0-1)  and [3](#0-2) .

Additionally, the separate `account_not_frozen_for_authority` guard used alongside `is_signer_authorized` only blocks the case where the frozen account's *own authority* is the signer — [4](#0-3) . It does not block a third-party order-execution keeper signer either, so there is no secondary defense against this bypass.

Per the project's own documentation, freezing is meant to be an exclusive lock: "Only the group admin can operate on the account" while frozen — [5](#0-4)  and [6](#0-5) . The overlapping-flag ordering bug directly violates this invariant, mirroring the Ethena report's root cause: a state-machine check that grants access based on one positive condition (`WHITELISTED_ROLE` / `ACCOUNT_IN_ORDER_EXECUTION`) without excluding a conflicting, more restrictive condition (`BLACKLISTED_ROLE` / `ACCOUNT_FROZEN`) that can legitimately coexist on the same account.

### Impact Explanation
An account can enter `ACCOUNT_IN_ORDER_EXECUTION` from a previously placed limit/stop order (`PlaceOrder`, a permissionless-fill order type) and later be frozen by the admin for compliance/investigation reasons before the order fills. Because the freeze check in `is_signer_authorized` is skipped whenever order execution is active, the pending order can still be executed by any third-party filler, moving assets (withdraw/repay) out of or on the account despite the admin's explicit freeze. This is an unauthorized state change / bypass of an admin-imposed control, undermining the compliance guarantee the freeze mechanism is documented to provide.

### Likelihood Explanation
Requires: (1) the account authority places an order (a normal, permissionless user action), and (2) the admin freezes the account before the order is filled/executed. Since order execution windows and freeze timing are independent and not synchronized in the codebase, this can occur in practice whenever an admin needs to freeze an account with an outstanding order — a realistic scenario for compliance/incident response, which is precisely when freeze is most likely to be used.

### Recommendation
Reorder the checks in `is_signer_authorized` so that `ACCOUNT_FROZEN` is evaluated first (or made mutually exclusive with `ACCOUNT_IN_ORDER_EXECUTION`/`ACCOUNT_IN_RECEIVERSHIP`), ensuring a frozen account cannot be acted upon by any non-admin signer regardless of other simultaneously-set flags. Alternatively, prevent orders from executing/filling at all while `ACCOUNT_FROZEN` is set, or automatically cancel/pause outstanding orders when an account is frozen.

### Proof of Concept
1. User places an order via `PlaceOrder` on their `MarginfiAccount` (sets nothing yet; the flag is set at fill time per `order.rs`).
2. Admin calls `marginfi_account_set_freeze(true)` on the account, setting `ACCOUNT_FROZEN`.
3. A keeper/any third party triggers order execution, which sets `ACCOUNT_IN_ORDER_EXECUTION` and then calls into `lending_account_withdraw`/`lending_account_repay`.
4. In `is_signer_authorized`, the `allow_order_execution && ACCOUNT_IN_ORDER_EXECUTION` branch returns `true` before the `ACCOUNT_FROZEN` branch is reached — the withdraw/repay succeeds despite the account being frozen, contradicting the documented invariant that "only the group admin can operate on the account" while frozen.

```rust
pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}
```

```rust
/// Checks if the account authority is allowed to act on their account based on frozen status.
///
/// Returns `true` if the action is allowed, `false` if blocked.
///
/// Returns `false` when both conditions are met:
/// - The account is frozen
/// - The signer is the account authority
///
/// This is intentionally separate from [`is_signer_authorized`] to return a distinct
/// `AccountFrozen` error in the instruction context  rather than `Unauthorized`.
pub fn account_not_frozen_for_authority(
    marginfi_account: &MarginfiAccount,
    signer: Pubkey,
) -> bool {
    !(marginfi_account.get_flag(ACCOUNT_FROZEN) && marginfi_account.authority == signer)
}
```

```markdown
## Special Account States

### Frozen Accounts

The group admin can freeze any individual user account. When frozen:
- The account's authority is blocked from all operations.
- Only the group admin can operate on the account (e.g. to withdraw or rebalance).
- The account remains frozen until explicitly unfrozen by the admin.

This is used for compliance, investigations, or protecting accounts in unusual situations.
```
