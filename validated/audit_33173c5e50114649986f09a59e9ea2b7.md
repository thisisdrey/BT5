### Title
Attacker can fill a victim's per-account token list with dust `DepositToken` transfers, blocking deposits, receives, and new debt issuance - (File: contracts/Pool.sol)

### Summary
`Pool` caps each account at `MAX_TOKENS_PER_USER = 30` combined deposit/debt tokens, enforced by `onlyIfAdditionWillNotReachMaxTokens` on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`. `DepositToken`s are freely transferable ERC20s, and `DepositToken._transfer` registers the token in the recipient's per-account set whenever the recipient's prior balance was zero. An unprivileged attacker can therefore push 1-wei dust of every whitelisted deposit token to a victim, filling the victim's slots so that subsequent `deposit`, `transfer`/`seize` receipts, and `DebtToken.issue` mints (all of which call the same `addTo*` functions) revert with `UserReachedMaxTokens` — directly analogous to filling the 5-slot NFT limit in the referenced OpenQ finding.

### Finding Description
- `Pool.sol:143-148` — `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (30).
- `Pool.sol:204-220` — `addToDebtTokensOfAccount` / `addToDepositTokensOfAccount` are gated by that modifier and are callable by any registered token contract.
- `DepositToken.sol:498-526` — `_transfer` moves balances and calls `pool.addToDepositTokensOfAccount(recipient_)` when `_recipientBalanceBefore == 0 && amount_ > 0`. There is no opt-in: any holder can add an entry to anyone's list.
- `DepositToken.sol:348-354` — `transfer` only checks `_revertIfLocked(_msgSender, amount_)` (unlocked balance), so an attacker holding dust of each collateral's `msdTOKEN` can spam the victim.
- The same accounting applies to `deposit` (mints → `addToDepositTokensOfAccount`), `seize` (liquidated collateral lands in the liquidator's list), and `DebtToken` issuance (calls `addToDebtTokensOfAccount`).

Attack: attacker deposits minimal collateral into each whitelisted `DepositToken`, then calls `msdTOKEN_i.transfer(victim, 1)` for every token the victim doesn't already hold, until the victim's combined list reaches 30. All of the victim's subsequent new-token interactions revert. Front-running the victim's own deposit transaction makes the griefing continuous: every time the victim clears a slot (by transferring/withdrawing the dust), the attacker can refill it in the same or next block for ~1 wei per slot.

### Impact Explanation
Temporary freezing of funds / liveness: the victim cannot deposit additional collateral types, cannot receive deposit tokens (including via liquidation `seize`), and cannot mint new synthetic debt in a debt token they don't already hold. If the victim's position is deteriorating and they need a new collateral type or new debt to stay healthy, the block can force liquidation of their existing position. Funds already held remain withdrawable only for tokens already in the list; the attack denies all new positions.

### Likelihood Explanation
Requires only standard ERC20 `transfer` calls on whitelisted `DepositToken`s and trivial dust amounts of each underlying collateral — fully reachable by any EOA with no privileged role. The constraint is that pools must whitelist enough distinct deposit tokens for the victim's combined list to reach 30 (the counter includes tokens the victim already legitimately holds, lowering the attacker's required count). Even when 30 cannot be fully reached, filling the remaining slots blocks the victim's next distinct-token deposit. The victim can clear slots themselves, so the impact is a repeatable grief rather than permanent lock — consistent with the Medium severity of the source report.

### Recommendation
Only register a deposit token in the recipient's account list on `deposit` (an action the beneficiary initiates or funds flow through `Treasury`), not on bare `transfer`/`seize`; or let recipients claim/acknowledge tokens. Alternatively, remove entries from `depositTokensOfAccount` lazily (e.g., iterate with a cap and skip zero balances in `depositOf`/`debtOf`) so dust does not consume the quota, or raise/eliminate `MAX_TOKENS_PER_USER` by bounding iteration cost differently.

### Proof of Concept
Hardhat sketch (based on `test/Pool.test.ts` fixtures):

```ts
// given: pool with whitelisted DepositTokens [msdA, msdB, ...], victim = bob
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30

// 1. attacker deposits dust into each collateral and transfers 1 wei of msdTOKEN to bob
for (const msd of depositTokens) {
  await underlying.mint(attacker.address, 2);
  await underlying.connect(attacker).approve(msd.address, 2);
  await msd.connect(attacker).deposit(2, attacker.address);   // attacker holds dust
  await msd.connect(attacker).transfer(bob.address, 1);        // adds entry to bob's list
}

// bob now has `max` entries
expect(await pool.getDepositTokensOfAccount(bob.address)).to.have.length(max);

// 2. bob's deposit into a new collateral reverts
await expect(
  msdNew.connect(bob).deposit(parseEther('1'), bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3. bob's mint of a new debt token also reverts (addToDebtTokensOfAccount)
await expect(
  debtTokenNew.connect(bob).issue(...) // via Pool/synthetic flow
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 4. attacker re-griefs: after bob withdraws dust to free a slot, attacker front-runs
//    bob's next deposit with another 1-wei transfer, keeping the list full.
```

Reproducible on a fork using deployed pools (e.g., `deployments/base/Pool.json`) since the revert path is purely internal accounting — no oracle or privileged state is needed beyond the whitelisted `DepositToken` set.
