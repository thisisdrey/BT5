Based on my research, the strongest local analog to the report's core broken invariant ("a fund-recovery/settlement path assumes a happy-path precondition that doesn't hold, and the fallback state has no way to actually return funds to the rightful party") is the Snowbridge **`LostTips`** mechanism in `snowbridge-pallet-system-v2`.

### Title
Permanently unrecoverable relayer tips via `LostTips` fallback with no reclaim path - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
When a user (or relayer) adds a tip for an inbound/outbound Snowbridge message via `AddTip`, the tip is credited to the message's `nonce`/`message_id` only if that nonce has not yet been consumed. If the underlying message was already processed by the time the tip lands (a normal, permissionless race — anyone can submit the message first), the tip is diverted into the `LostTips` storage map instead of being returned to the sender or paid to a relayer, and the codebase contains no dispatchable to reclaim it.

### Finding Description
`LostTips` is documented explicitly as capturing "Relayer reward tips that were paid by the user ... but then could not be added to their message reward (e.g. the nonce was already processed or their order could not be found)", with a note that this "supports implementing a recovery method in the future" [1](#0-0) . This confirms that, as it stands, no recovery method exists — the future tense in the comment and the absence of any `claim_lost_tip`/`withdraw_lost_tip`-style call in the pallet's `Call` enum [2](#0-1)  mean funds routed here are stuck.

The `TipProcessed` event explicitly documents this dead-end outcome: "It could have succeeded or failed (and then added to LostTips)" [3](#0-2) . Integration tests confirm the pattern happens today: tipping a nonce/message id that doesn't exist produces `TipProcessed{success: false}` and increments `LostTips` for the sender, with the assertion only checking `relayer_lost_tip > 0` — no subsequent claim [4](#0-3) .

On the consuming side, `InboundQueue::process_message` only pays out a tip if it finds one keyed by the exact `nonce` at the moment of processing: `Tips::<T>::take(nonce).unwrap_or_default()` [5](#0-4) . Because tip submission (`add_tip`, permissionless, user-signed) and message processing (also permissionless, first-relayer-wins on the nonce) are two independently-timed, unprivileged extrinsics, there is an inherent TOCTOU race: any user can submit `add_tip` for a nonce that gets consumed by a relayer moments earlier, and the tip is silently converted into an unreachable `LostTips` balance instead of being refunded to the depositor.

This is structurally the same defect class as the audit report: a settlement/recovery mechanism (`recover()` in the report, the `LostTips` fallback here) is invoked on a path whose invariant ("nonce is still open" / "totalSupply == 0") is not guaranteed to hold in normal operation, and when it fails the funds end up in a state with no way back to the rightful owner.

### Impact Explanation
This falls under the accepted impact category "permanent user-fund ... lock": an unprivileged user's tip (locked/reserved DOT or other asset) can be permanently trapped in on-chain storage with no dispatchable extrinsic to reclaim it, for any Snowbridge relayer-incentive user who tips a message that gets processed before/without their tip landing on the same nonce. No malicious peer, validator, or admin is required — it is a routine race between two permissionless calls.

### Likelihood Explanation
High under normal network conditions: relayers race constantly to process messages for their own reward, so submitting a `add_tip` transaction shortly after (or concurrently with) message submission is a common, easily triggered scenario, not a contrived attack. The described integration test already demonstrates the "lost tip" state is reachable trivially (tipping an already-consumed/non-existent nonce).

### Recommendation
Add a permissionless (or depositor-restricted) `claim_lost_tip`/`withdraw_lost_tip` extrinsic that allows the original tipper (tracked as the `AccountIdOf<T>` key of `LostTips`) to reclaim their stranded balance, mirroring how the report's fix modified `recover()` to actually return funds to the rightful party instead of relying on an assumption that silently fails.

### Proof of Concept
1. User A calls `SnowbridgeSystemFrontend::add_tip` (or the outbound equivalent) targeting `MessageId`/nonce `N`, reserving/transferring their tip amount.
2. Before or concurrently, any relayer calls `process_message`/`process_delivery_receipt` for nonce `N`, marking it consumed via `Nonce::<T>::set(nonce)` [6](#0-5) .
3. The `add_tip` call (processed after step 2, or targeting an already-invalid id) fails to attach to the live `Tips` map and instead increments `LostTips::<T>::get(user_A)` [7](#0-6) .
4. User A has no on-chain call to retrieve this balance — it is permanently stranded, confirmed by the absence of any claim function in the pallet's public `Call` interface [2](#0-1) .

**Caveat**: I was unable to fully inspect `snowbridge-pallet-system-frontend`'s `add_tip` implementation (the exact fund-transfer/reservation code path) before running out of tool calls, so the precise mechanics of how the tip asset moves from the user before landing in `LostTips` are inferred from the storage/event definitions and integration test rather than directly read from `system-frontend/src/lib.rs`. A Devin session with full file access should verify that code path to confirm the exact custody of funds prior to being marked "lost."
