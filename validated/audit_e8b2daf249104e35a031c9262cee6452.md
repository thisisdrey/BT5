### Title
`remove_account` fails to purge `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` rows, letting stale yields auto-resume against a deleted-and-recreated account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` deletes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` rows belonging to the deleted account. Because the timeout mechanism (`resolve_promise_yield_timeouts`) triggers automatically off these leftover rows without any action from the account's new owner, a stale yielded `FunctionCall` (with attacker-chosen method/args, fixed at yield-creation time) is executed self-authorized against whatever contract now occupies that account id.

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs:504-575` only removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [1](#0-0) [2](#0-1) 

It does not touch `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId`, all of which are keyed by `receiver_id`/`account_id` as defined in `core/primitives/src/trie_key.rs:278-291`: [3](#0-2) 

`action_delete_account` in `runtime/runtime/src/actions.rs:314-390` calls `remove_account` and then sets `*account = None`, with no additional cleanup of yield-related state: [4](#0-3) 

An account can create a `PromiseYield` receipt targeting itself (self-yield with method_name/args of the attacker's choosing) via `promise_yield_create`; the receipt gets stored under `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` by `set_promise_yield_receipt`, and a global (not per-account) timeout queue entry is enqueued via `enqueue_promise_yield_timeout`: [5](#0-4) 

`DeleteAccount` on that same account then removes `Account`/`ContractCode`/keys/`ContractData`, but leaves the `PromiseYieldReceipt`/`PromiseYieldStatus` rows in place. `CreateAccount` (only callable by the parent, which the attacker controls) plus `DeployContract` recreate the account id with new code/keys - this is a normal, already-tested scenario (`test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`).

Critically, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) fires automatically once `expires_at <= block_height`, purely by checking `state_update.contains_key(&promise_yield_key, ...)` - i.e., whether the stale `PromiseYieldReceipt` row still exists: [6](#0-5) 

Because `remove_account` never deleted that row, this check passes and a `PromiseResume` receipt targeting `queue_entry.account_id` (the recreated account) is synthesized without any consent or action from the new occupant. When that `PromiseResume` is processed, `get_promise_yield_receipt` still finds the stale receipt and `apply_action_receipt` executes its original actions (predecessor_id == receiver_id == the shared account id, since it was a self-yield) against the newly deployed contract's storage: [7](#0-6) 

Since predecessor_id equals receiver_id (both are the string account id, unchanged by delete/recreate), any internal "self-call only" gate (`predecessor_id() == current_account_id()`) in the *new* contract is trivially satisfied, letting the attacker's pre-deletion, fully attacker-controlled `method_name`/`args` execute as an authorized self-call against a contract that never issued that callback.

### Impact Explanation
This is an authorization/promise-containment violation: an attacker forces execution of an arbitrary, pre-chosen `FunctionCall` (method name and arguments fixed before account deletion) against whichever contract now occupies the reused account id, with the self-check trivially bypassed because `predecessor_id == receiver_id == account_id` regardless of which code/owner currently controls the account. This can corrupt state or trigger privileged internal callback logic of the new contract deployment, matching the "authorization escalation across accounts or promises" bounty category. It does not require the new occupant to do anything - the trigger is fully automatic via the timeout path.

### Likelihood Explanation
Fully reachable by an unprivileged account: (1) call `promise_yield_create` on itself with a chosen callback method/args; (2) before timeout, submit `DeleteAccount`; (3) recreate the subaccount (attacker's parent account is the only one permitted to do `CreateAccount` for that subaccount id, and it is under attacker's control) and deploy new code; (4) wait for `yield_timeout_length_in_blocks` to elapse - the timeout fires automatically. No validator, RPC-operator, or node access is needed; no signature/nonce/access-key checks stop this because deletion and recreation are both individually valid, standalone actions, and nothing cross-checks the yield rows against account lifecycle. It is fully repeatable.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also iterate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows scoped to the account being deleted (analogous to how it already iterates access keys and contract data by prefix), and/or have `resolve_promise_yield_timeouts` / the `PromiseResume` handling path additionally validate that the account has not been deleted/recreated since the yield was created (e.g., by tying the receipt to an account "generation"/creation nonce) before executing the stale receipt.

### Proof of Concept

3. Assert (currently failing) that `get_promise_yield_receipt`, `has_promise_yield_status`, and `get_data_id_for_yield_id`/`get_yield_id_for_data_id` all return `None`/`false` after commit - today they still return the stale data.
4. Integration/test-loop level: reproduce the full scenario (create self-yield on `child.alice.near`, `DeleteAccount`, `CreateAccount`+`DeployContract` with different code, advance blocks past `yield_timeout_length_in_blocks`) and assert that the original yield's `FunctionCall` action executes against the *new* contract's storage (e.g., writes a value the new contract never authorized), analogous to the existing `test_simple_yield_timeout` and `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` tests.

// Enqueues given timeout to the PromiseYield timeout queue
pub fn enqueue_promise_yield_timeout(
    state_update: &mut TrieUpdate,
    promise_yield_indices: &mut PromiseYieldIndices,
    account_id: AccountId,
    data_id: CryptoHash,
    expires_at: BlockHeight,
) {
    set(
        state_update,
        TrieKey::PromiseYieldTimeout { index: promise_yield_indices.next_available_index },
        &PromiseYieldTimeout { account_id, data_id, expires_at },
    );
    promise_yield_indices.next_available_index = promise_yield_indices
        .next_available_index
        .checked_add(1)
        .expect("Next available index for PromiseYield timeout queue exceeded the integer limit");
}

pub fn set_promise_yield_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }
}
