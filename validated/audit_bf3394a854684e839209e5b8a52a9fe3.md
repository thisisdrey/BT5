### Title
QoS Bypass via TOCTOU Race Between `ConnectionRateLimiter::is_allowed` and `register_connection` - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Finding Description
`ConnectionRateLimiter::is_allowed` is a non-mutating, read-only check against the token bucket for a given `IpAddr` [1](#0-0) , while the actual token consumption that enforces `max_connections_per_ipaddr_per_min` only happens in `register_connection` via `self.limiter.consume_tokens(*ip, 1)` [2](#0-1) . These are two distinct, non-atomic operations on the shared `KeyedRateLimiter` state. Because the streamer's connection accept loop performs the `is_allowed` check first and only calls `register_connection` later after the per-connection setup/handshake task has been spawned (per the documented call sequence: accept -> `is_allowed` pre-check -> spawn `setup_connection` concurrently -> `register_connection` post-handshake), an attacker who opens many concurrent QUIC connection attempts from the same source IP within a short window can have all of them pass the `is_allowed` pre-check before any of the concurrently running tasks reach the mutating `register_connection` call. This is a classic check-then-act (TOCTOU) race: the read-only gate and the token-consuming gate are decoupled in time and execution context (async tasks), so the invariant "no more than N connections per IP per minute" is not atomically enforced at admission time.

### Impact Explanation
This falls under QoS/rate-limit evasion: an unstaked, unprivileged client can temporarily exceed `max_connections_per_ipaddr_per_min` and capture a disproportionate share of concurrent TPU QUIC connection slots during the race window, which can starve or delay legitimate/staked senders from establishing connections, degrading TPU ingress fairness.

### Likelihood Explanation
The attack requires only an unprivileged remote client capable of opening many concurrent QUIC handshakes to the public TPU port from one source IP within the same rate-limiter window — no staking, gossip, or validator control needed. Feasibility depends on how large the race window is in practice (time between the accept-time `is_allowed` check and the completion of the handshake plus `register_connection` call) and whether `is_allowed` is even present on the specific accept-time gating path used before spawning `setup_connection`; this timing detail could not be fully confirmed from the excerpted code alone since the full `streamer/src/nonblocking/quic.rs` call sequence around `run_server`/`setup_connection` was not completely traced in this session. The race is repeatable under concurrent connection floods and is bounded by the size of the async task spawn/handshake latency window, making it plausible but its severity is capped by how tight that window is and by max_burst token-bucket allowances (which already permit some burst by design).

### Recommendation
Make admission atomic by folding the check into the mutation: replace the separate `is_allowed` pre-check + later `register_connection` pattern with a single atomic `try_consume`/`register_connection`-only call performed synchronously before spawning the connection setup task, so the token is reserved at accept time rather than after handshake completion. If a pre-check is still needed for early rejection without consuming a token, ensure the actual `consume_tokens` call happens before any concurrent task is spawned, not after.

### Proof of Concept
```rust
// streamer/src/nonblocking/connection_rate_limiter.rs (integration-style test)
use std::{net::{IpAddr, Ipv4Addr}, sync::Arc};
use tokio::task::JoinSet;

#[tokio::test]
async fn test_concurrent_register_connection_race() {
    let limiter = Arc::new(ConnectionRateLimiter::new(1, 1, 4)); // max 1 conn/min
    let ip = IpAddr::V4(Ipv4Addr::new(10, 0, 0, 1));

    let mut set = JoinSet::new();
    for _ in 0..50 {
        let limiter = limiter.clone();
        set.spawn(async move {
            // Simulates accept-time pre-check
            let pre_ok = limiter.is_allowed(&ip);
            // Simulates concurrent handshake/setup_connection latency
            tokio::task::yield_now().await;
            let registered = limiter.register_connection(&ip);
            (pre_ok, registered)
        });
    }

    let mut allowed_count = 0;
    while let Some(res) = set.join_next().await {
        let (_, registered) = res.unwrap();
        if registered {
            allowed_count += 1;
        }
    }

    // Expected invariant: only 1 connection registered given max_connections_per_ipaddr_per_min=1
    assert_eq!(allowed_count, 1, "more than the configured limit was registered due to TOCTOU race");
}
```
