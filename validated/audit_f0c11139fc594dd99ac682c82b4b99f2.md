#No Vulnerability found for this question.

**Analysis supporting this conclusion:**

The storage-usage accounting in `use_global_contract` at [1](#0-0)  does indeed charge storage usage only for the `GlobalContractIdentifier` length (32 bytes for a `CodeHash`, or `AccountId` length), not for the referenced contract's code size. This is not unique to `DeterministicStateInitAction` — it is the exact same behavior used by the pre-existing `UseGlobalContractAction` (`action_use_global_contract` calls the same `use_global_contract` helper at [2](#0-1) ), and is validated by existing tests asserting `storage_usage == baseline + identifier.len()` [3](#0-2) . This is the intended design of the global-contracts feature: it lets many accounts cheaply reference one already-stored contract instead of duplicating the code in every account's storage.

Regarding compilation cost: `use_global_contract` performs no WASM preparation or compilation — it only does a trie `contains_key` check and updates account metadata [4](#0-3) . Compilation is deferred to first `FunctionCall` invocation via `with_compiled_and_loaded`/`compile_and_cache`, which charges `contract_loading_base`/`contract_loading_bytes` fees to whichever call actually invokes the contract, based on the real code size [5](#0-4) [6](#0-5) . Critically, the compiled-artifact cache key is derived from the contract's `code_hash` (not the account), so compilation happens at most once per unique code across the entire node regardless of how many accounts point at it [7](#0-6) , and concurrent/duplicate compiles are deduplicated via a per-key lock [8](#0-7) . This directly refutes the premise that each `0u` account "imposes full re-validation/compilation cost on chunk producers" — chunk producers pay compilation cost once per unique code hash, amortized and cached, not once per referencing account.

The attacker's real, unavoidable cost is the one-time global-contract deployment fee, which is proportional to the code size (`global_contract_storage_amount_per_byte * code.len()`), charged synchronously in `action_deploy_global_contract` [9](#0-8) . Fanning out cheap references to that already-paid-for contract across N accounts is the explicit intended use case of the global-contracts NEP, not a metering bypass — no funds are stolen or frozen, no consensus divergence occurs, and no unpaid, unbounded compute is imposed on chunk producers beyond the standard, size-proportional `contract_loading_bytes` fee charged at actual invocation time to whoever calls the contract.

    /// Compile a contract and store the result in the cache. Blocks on the
    /// per-key compilation lock while another thread is compiling the same
    /// contract — use when the caller needs the artifact (synchronous apply
    /// path, foreground pipelining).
    fn compile_and_cache(
        &self,
        code: &ContractCode,
        cache: &dyn ContractRuntimeCache,
    ) -> Result<CachedArtifact, CacheError> {
        let key = get_contract_cache_key(*code.hash(), &self.config, self.vm_hash());

        // Double-checked locking — outer step. An unlocked cache check before
        // touching `compilation_locks` lets already-cached cases skip both
        // mutex acquires entirely.
        if let Some(compiled) = read_cache(cache, &key)? {
            return Ok(compiled);
        }
        let entry = compilation_locks().entry(key);
        self.compile_and_persist(key, code, cache, entry.lock())
    }
