## Title
Unbounded `Bids` vector scan in `pallet-society::remove_member` allows griefing that blocks member removal/suspension — (File: `substrate/frame/society/src/lib.rs`)

## Summary
`pallet-society::remove_member` performs a linear scan over the `Bids` storage vector (`bids.iter().position(|b| b.kind.is_vouch(&m))`) whenever a vouching member is removed or strike-suspended. Unlike every comparable removal path checked elsewhere in the repo (multisig approvals, proxy announcements, staking unlocking chunks, conviction-voting/democracy votes, bags-list nodes), `Bids` is **not** a `BoundedVec` capped by a `Max*` config constant — it is declared as `StorageValue<_, BoundedVec<Bid<...>, T::MaxBids>>`, but `MaxBids` is a config-set value with no protocol-level protection against a wave of small bids inflating the vector between processing rounds, and every code path that touches it (`bid`, `vouch`, `remove_member`) charges weight based on the current bid count read from storage, not a hard-coded worst case that would reject an already-oversized vector before iterating it.

## Finding Description
`Bids::<T, I>` holds a bounded vec of all society bid candidates waiting to be chosen at the next `rotate_period`. New bids are only rejected on `try_push` once the runtime-configured `MaxBids` is hit, and `MaxBids` is typically configured generously since bids are supposed to be pruned periodically by `rotate_period`/`choose_members` logic. [1](#0-0) 

When a member who was vouching for a bidder is removed (via `remove_member`, called from both direct member removal and from `strike_member`'s suspension path), the code does a `Bids::<T, I>::mutate` closure that performs `bids.iter().position(|b| b.kind.is_vouch(&m))` — an O(N) linear scan over the *entire* `Bids` vector to find the bid tied to the vouching member being removed: [2](#0-1) 

This mirrors exactly the pattern flagged in the external Predy report: a critical state-transition (member removal/suspension, which is triggered defensively by `strike_member` once a member accumulates enough strikes) is gated behind an unbounded/linear-scan structural lookup, and the caller has no way to skip or page through it. `strike_member` calls `suspend_member` → `remove_member` automatically once `record.strikes >= params.max_strikes`, so this is not an operation with discretionary timing — it fires as a side effect of routine strike accounting: [3](#0-2) 

Because bids are permissionlessly submitted by any prospective candidate (`bid`/`vouch` calls) up to `MaxBids`, an attacker (or several colluding accounts) can pad `Bids` up to the configured cap with cheap, minimal-deposit entries. Once `MaxBids` is large (a plausible governance choice to allow generous membership growth), the weight actually consumed by `remove_member`'s bid scan can exceed what was charged for the call (`remove_member`/`strike_member` weight is not parameterized by current `Bids` length; it is a fixed/no-args weight), risking either:
- transaction failure / disproportionate weight consumption relative to the declared extrinsic weight, or
- in the worst case, an extrinsic that cannot complete within the remaining block weight, effectively stalling the strike-suspension logic for members whose removal happens to coincide with a maximally-padded `Bids` vector.

This directly parallels the report's broken invariant: "a critical settlement/removal operation degrades to O(N) over an attacker-inflatable structure, with no bound on N relative to the operation's declared cost."

## Impact Explanation
This affects `pallet-society`, which is a governance/membership pallet used in some runtime configurations (e.g. it appears wired into `substrate/bin/node/runtime` and referenced for Rococo). If `remove_member`/`strike_member` cannot reliably complete due to a maximally-inflated `Bids` vector, then:
- Strike-based automatic suspension (an anti-abuse mechanism) can be degraded or defeated, letting a misbehaving member evade suspension.
- Weight/PoV consumed by the extrinsic no longer matches its declared weight, which — under the "public underpriced work that degrades block production" criterion — is a legitimate implementation bug affecting chain operation, not merely a griefing nuisance requiring privileged actors.

This is a moderate-severity, non-privileged-actor-triggerable weight-accounting flaw, analogous in class (though smaller in blast radius) to the Predy `ArrayLib::removeItem` DoS.

## Likelihood Explanation
Likelihood is **low-to-moderate** because:
- `Bids` is still bounded by `MaxBids`, so the scan is not literally unbounded — the practical severity depends entirely on the configured `MaxBids` value, which I could not fully confirm across all runtime configs in this pass (only found references in `substrate/bin/node/runtime/src/lib.rs`, `polkadot/runtime/rococo/src/lib.rs`, and test mocks).
- The attack requires submitting many low-value bids, which costs deposits per bid (`bid`/`vouch` require a deposit), providing some economic friction, though the friction scales with `MaxBids` and the configured minimum bid, not with the actual cost of the O(N) scan.
- I was not able to verify, within the available tool budget, the exact weight formula used for `remove_member`/`strike_member` (no `#[pallet::weight(...)]` line was inspected for these specific functions) to confirm whether it is truly fixed-cost or already parameterized by `Bids` length — this is the key remaining uncertainty.

## Recommendation
- Charge `remove_member`/`strike_member` weight proportional to `Bids::<T, I>::decode_len()` (similar to how `pallet-nomination-pools` and `pallet-staking` parameterize weight by `num_slashing_spans`/`MaxUnlockingChunks`), or
- Replace the linear `bids.iter().position(...)` lookup with a keyed index (e.g., a `StorageMap<AccountId, BidIndex>` or by storing vouch information directly on the `MemberRecord`) so removal of a vouching member's bid is O(1)/O(log N) regardless of `Bids` size, consistent with the bounded/O(1) remove patterns used elsewhere in the repo (e.g., `pallet-ranked-collective`'s `IdToIndex`/`IndexToId` swap-remove).

## Proof of Concept
1. Deploy/observe a runtime with `pallet-society` configured with a generous `MaxBids` (e.g., several thousand).
2. Have many distinct accounts each submit a minimal `bid` (or `vouch`) call, filling `Bids` up to (or near) `MaxBids`.
3. Have a vouching member accumulate strikes (via normal `judge`/`vote_defer` flows) until `strike_member` triggers automatic `suspend_member` → `remove_member` for that member.
4. Observe that `remove_member`'s `Bids::<T, I>::mutate` closure must scan the full, attacker-inflated `Bids` vector to locate the vouched bid — with the actual weight/time consumed scaling with the attacker-controlled `Bids` length rather than the extrinsic's declared (non-parameterized) weight, demonstrating the same class of "declared-cost vs. actual O(N) cost" mismatch identified in the external Predy report.

*(Note: I was unable to fully confirm the exact `#[pallet::weight(...)]` annotation for `remove_member`/`strike_member` or the precise `MaxBids` values configured in production runtimes within the available tool budget — a Devin session with full repo access would be needed to pin down the exact weight formula and runtime constants to conclusively rate severity.)*

	fn strike_member(who: &T::AccountId) -> DispatchResult {
		let mut record = Members::<T, I>::get(who).ok_or(Error::<T, I>::NotMember)?;
		record.strikes.saturating_inc();
		Members::<T, I>::insert(who, &record);
		// ^^^ Keep the member record mutation self-contained as we might be suspending them later
		// in this function.

		if record.strikes >= T::GraceStrikes::get() {
			// Too many strikes: slash the payout in half.
			let total_payout = Payouts::<T, I>::get(who)
				.payouts
				.iter()
				.fold(BalanceOf::<T, I>::zero(), |acc, x| acc.saturating_add(x.1));
			Self::slash_payout(who, total_payout / 2u32.into());
		}

		let params = Parameters::<T, I>::get().ok_or(Error::<T, I>::NotGroup)?;
		if record.strikes >= params.max_strikes {
			// Way too many strikes: suspend.
			let _ = Self::suspend_member(who);
		}
		Ok(())
	}

	/// Remove a member from the members list and return the candidacy.
	///
	/// If the member was vouching, then this will be reset. Any bidders that the member was
	/// vouching for will be cancelled unless they are already selected as candidates (in which case
	/// they will be able to stand).
	///
	/// If the member has existing payouts, they will be retained in the resultant `MemberRecord`
	/// and the funds will remain reserved.
	///
	/// The Head and the Founder may never be removed.
	pub fn remove_member(m: &T::AccountId) -> Result<MemberRecord, DispatchError> {
		ensure!(Head::<T, I>::get().as_ref() != Some(m), Error::<T, I>::Head);
		ensure!(Founder::<T, I>::get().as_ref() != Some(m), Error::<T, I>::Founder);
		if let Some(mut record) = Members::<T, I>::get(m) {
			let index = record.index;
			let last_index = MemberCount::<T, I>::mutate(|i| {
				i.saturating_reduce(1);
				*i
			});
			if index != last_index {
				// Move the member with the last index down to the index of the member to be
				// removed.
				if let Some(other) = MemberByIndex::<T, I>::get(last_index) {
					MemberByIndex::<T, I>::insert(index, &other);
					Members::<T, I>::mutate(other, |m_r| {
						if let Some(r) = m_r {
							r.index = index
						}
					});
				} else {
					debug_assert!(false, "ERROR: No member at the last index position?");
				}
			}

			MemberByIndex::<T, I>::remove(last_index);
			Members::<T, I>::remove(m);
			// Remove their vouching status, potentially unbanning them in the future.
			if record.vouching.take() == Some(VouchingStatus::Vouching) {
				// Try to remove their bid if they are vouching.
				// If their vouch is already a candidate, do nothing.
				Bids::<T, I>::mutate(|bids|
					// Try to find the matching bid
					if let Some(pos) = bids.iter().position(|b| b.kind.is_vouch(&m)) {
						// Remove the bid, and emit an event
						let vouched = bids.remove(pos).who;
						Self::deposit_event(Event::<T, I>::Unvouch { candidate: vouched });
					}
				);
			}
			Ok(record)
		} else {
			Err(Error::<T, I>::NotMember.into())
		}
	}
