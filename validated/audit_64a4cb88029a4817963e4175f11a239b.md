### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled contract signature parsing can crash a node with OutOfMemoryError - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts parse call data supplied by any smart-contract caller into `DataWord[]` and use an attacker-supplied word as an array-length before validating it against a bound, mirroring the Kafka CVE-2022-34917 class of bug (untrusted length field used directly in a memory allocation, CWE-789/CWE-400).

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read a length directly from caller-controlled `DataWord[]` data and allocate a `byte[len][]` before any range check is applied: [1](#0-0) 

`len` comes from `words[offset].intValueSafe()`, which for any oversized word is clamped to `Integer.MAX_VALUE` rather than rejected: [2](#0-1) 

The size cap (`MAX_SIZE`) that is supposed to bound this length is only enforced when the `allowTvmSelfdestructRestriction()` chain feature flag is active — the extraction call itself happens unconditionally, and when the flag is inactive the guard is skipped entirely, calling `extractBytesArray`/`extractBytes32Array` with the raw, unbounded `len`: [3](#0-2) [4](#0-3) 

`allowTvmSelfdestructRestriction()` is a governance-controlled `VMConfig` flag toggled via a chain proposal (`ProposalUtil`/`DynamicPropertiesStore`); I was not able to confirm in this session whether it is enabled by default on current mainnet/testnet configurations, so whether this path is presently reachable depends on that chain parameter's live state, which I could not verify with the tools available.

### Impact Explanation
If the guard is inactive (or on any private/test network, or older node that hasn't activated the proposal), any account can deploy/call a contract that invokes `ValidateMultiSign` or `BatchValidateSign` with call data encoding a huge length word. This triggers `new byte[Integer.MAX_VALUE][]`, an ~8–17GB allocation request per byte[][] entry, which will throw `OutOfMemoryError` on the node processing the transaction/contract call — a single unauthenticated (unprivileged) transaction/contract call can crash or destabilize a validating node, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Low-to-moderate confidence of current exploitability: the code path exists and is reachable by any transaction broadcaster/contract caller with no special privilege, but it is gated behind a proposal-activated feature flag whose live default state could not be confirmed here. If the flag is already active network-wide, this specific path is dead; if it is inactive (or a node runs with older config), the analog is directly exploitable with a single crafted contract call.

### Recommendation
Move the `MAX_SIZE` bound check (and a hard, non-config-gated sanity cap, e.g., reject any length whose value doesn't fit safely and reasonably before allocation) to be unconditionally enforced inside `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves, prior to allocating `new byte[len][]`, rather than relying on an optional/history-dependent proposal flag at the call sites.

### Proof of Concept
Deploy a contract that calls the `BatchValidateSign` precompile address with ABI-encoded input where the word at the signature-array-length offset is set to a very large value (e.g., `0xFFFFFFFF`). On a node where `allowTvmSelfdestructRestriction()` is not active, `extractBytesArray`/`extractBytes32Array` will execute `new byte[len][]` with `len` clamped to `Integer.MAX_VALUE`, causing an immediate large heap allocation attempt and `OutOfMemoryError` during transaction/contract execution.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {

      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();

      return Integer.MAX_VALUE;
