Since `VoteStateFrameV4::try_new` is a total function of its input `&[u8]` slice — parsing offsets sequentially with no timing, allocation-count, or environment dependence that could vary between leader execution and replay — any given byte sequence produces exactly the same `VoteStateFrameV4` (and thus the same `VoteStateView`) every time it's parsed, regardless of how "pathologically large" the encoded lists are (bounded to 255 items max each by the `u8` cast). Both the leader (producing the block) and the replaying validator invoke this identical parser on the identical resulting account bytes (the vote program's execution result, which is itself deterministic and part of consensus), so byte-for-byte reproducibility across replay is a direct consequence of the parser being pure/stateless — there is no code path in `try_new` or its callees (`BlsPubkeyCompressedFrame::read`, `LandedVotesListFrame::read`, `RootSlotFrame::read`, `AuthorizedVotersListFrame::read`, `EpochCreditsListFrame::read`) that could diverge between two invocations on the same bytes.
