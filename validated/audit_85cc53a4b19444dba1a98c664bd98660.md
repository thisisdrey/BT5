### Title
Unauthenticated-equivalent SSRF via `CreateRepositoryFromSnapshot`'s `HttpUrl` field allows Gitaly to fetch arbitrary internal/external URLs - (File: `internal/gitaly/service/repository/create_repository_from_snapshot.go`)

### Summary
The `CreateRepositoryFromSnapshot` RPC lets a caller supply an arbitrary `HttpUrl` which Gitaly fetches server-side via `http.NewRequestWithContext` and pipes directly into `tar -xvf -`. Unless the caller also supplies a `ResolvedAddress`, the request is sent with the standard `httpClient` and normal DNS resolution/routing, with no restriction preventing the target from being a loopback, link-local (e.g. cloud metadata endpoint), or other internal address. This mirrors the reported csstidy bug class: an externally reachable, unauthenticated-style interface accepts a `url` parameter and performs a server-side HTTP fetch with no destination restriction, and additionally writes the fetched content to disk (there via a CSS temp file, here via `tar` extraction into the repository path).

### Finding Description
`untar` builds and issues an HTTP GET using the caller-controlled `in.GetHttpUrl()`: [1](#0-0) 

If the caller does not set `ResolvedAddress` (an optional field), Gitaly falls back to the plain `httpClient`, which uses `http.ProxyFromEnvironment` and a normal `net.Dialer` — i.e., regular DNS resolution with no allow-list, no blocking of RFC1918/loopback/link-local ranges: [2](#0-1) 

Even when `ResolvedAddress` is supplied, `newResolvedHTTPClient` only validates that it parses as an IP address — it never checks that the address is non-private/non-loopback, so the "DNS-rebinding protection" mechanism does not actually prevent SSRF, it merely pins the destination to whatever IP the caller specifies: [3](#0-2) 

The response body is then streamed directly into `tar -C path -xvf -`, so the fetched remote content is extracted onto disk inside the new repository's storage path: [4](#0-3) 

The code comment itself acknowledges the trust assumption is fragile: "The received archive is trusted *a lot*. Before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening," confirming the maintainers recognize the SSRF/trust-boundary risk but have not implemented destination restrictions.

### Impact Explanation
Any caller able to invoke `CreateRepositoryFromSnapshot` (RPC-level authorization only, no destination validation) can force the Gitaly node to make arbitrary outbound HTTP(S) requests to internal services — including localhost-bound admin interfaces, other Gitaly/Praefect nodes, or cloud metadata endpoints — and can also write arbitrary attacker-controlled tar content into the newly created repository path, going beyond pure SSRF into local file write/extraction-escape territory (path traversal in the tar archive is not filtered before extraction). This is more severe than the original csstidy report because the fetched content is not just stored as a CSS file but actively extracted as a repository archive.

### Likelihood Explanation
The `HttpUrl`, `HttpAuth`, and `ResolvedAddress` fields are all attacker-influenceable RPC request fields; no server-side validation restricts the target host, scheme (aside from what `net/http` itself rejects), or IP range. Any RPC caller with access to invoke this handler (e.g., during a crafted repository-creation/import flow) can trigger the SSRF deterministically and reliably.

### Recommendation
Enforce destination validation for `HttpUrl`/`ResolvedAddress` (reject loopback, link-local, and private ranges unless explicitly allow-listed), require `ResolvedAddress` to be supplied and validated against an allow-list rather than merely being IP-parseable, and sanitize/validate the tar archive contents (path traversal checks) before extraction, consistent with the hardening already applied in `CreateRepositoryFromURL`'s handling of `transfer.bundleURI` and `GetURLAndResolveConfig`.

### Proof of Concept
1. Send a `CreateRepositoryFromSnapshot` RPC with `HttpUrl` set to `http://169.254.169.254/latest/meta-data/` (or any internal service URL) and no `ResolvedAddress`.
2. Gitaly's `untar` function issues the GET request via `httpClient`, resolving and connecting through normal DNS/network paths.
3. The response body is piped into `tar -xvf -`, extracting whatever content the internal endpoint returns into the new repository's storage path — confirming both SSRF (server-side fetch to attacker-chosen internal host) and secondary file-write/extraction impact.

// newResolvedHTTPClient is a modified version of the httpClient variable but here we resolve the
// URL to predefined IP:PORT. This is to avoid DNS rebinding.
func newResolvedHTTPClient(httpAddress, resolvedAddress string) (*http.Client, error) {
	url, err := url.ParseRequestURI(httpAddress)
	if err != nil {
		return nil, structerr.NewInvalidArgument("parsing HTTP URL: %w", err)
	}

	port := url.Port()
	if port == "" {
		switch url.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		default:
			return nil, structerr.NewInvalidArgument("unsupported schema %q", url.Scheme)
		}
	}

	// Sanity-check whether the resolved address is a valid IP address.
	if net.ParseIP(resolvedAddress) == nil {
		return nil, structerr.NewInvalidArgument("invalid resolved address %q", resolvedAddress)
	}

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}
