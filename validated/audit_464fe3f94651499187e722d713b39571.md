### Title
Unbounded attacker-controlled length fields in TVM precompile ABI decoding can trigger uncaught `NegativeArraySizeException`/`OutOfMemoryError`/`ArrayIndexOutOfBoundsException` — (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
Squid's ESI bug stems from trusting an attacker-influenced length/offset value when writing into a fixed buffer, causing out-of-bounds memory corruption. The closest reachable analog in java-tron is in the TVM precompiled-contract calldata decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java`, which read length and offset fields directly from attacker-supplied calldata words without validating them against the actual data size before using them to allocate arrays and slice byte ranges.

### Finding Description
`extractBytesArray` and `extractSigArray` read a length value from `words[offset].intValueSafe()` and immediately use it to allocate `new byte[len][]`, then loop `i < len` reading further offset/length words from the same attacker-controlled `words` array and slicing `data` via `extractBytes`: [1](#0-0) 

`extractBytes` performs a raw `Arrays.copyOfRange(data, offset, offset + len)` with no bounds checking against `data.length`: [2](#0-1) 

`extractBytes32Array` similarly trusts `len` from `words[offset]` without any upper-bound or overflow check before allocating an array of that size and indexing further into `words`: [3](#0-2) 

These helpers are used by the multi-signature verification precompiled contracts (`ValidateMultiSign` / `BatchValidateSign`), which are reachable by any address that constructs and sends a transaction calling into that precompile from a smart contract — an unprivileged, attacker-controlled entry point. Because `len`, `bytesOffset`, and `bytesLen` are derived from calldata words fully under caller control, a crafted call can set `len` to a very large positive value (triggering huge/failed allocation → `OutOfMemoryError`), or set offset/length combinations that read past the bounds of `words`/`data` (triggering `ArrayIndexOutOfBoundsException`), or push values that overflow int arithmetic (`bytesOffset + offset + 2) * WORD_SIZE`) to reference unintended memory.

Unlike Squid (native C/C++), java-tron is written in Java, which is memory-safe — there is no possibility of direct heap corruption/RCE. The realistic impact class is a Java runtime exception thrown during precompile execution.

### Impact Explanation
If such an exception (`OutOfMemoryError`, `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`) is not caught cleanly at the TVM/`Program` execution boundary and instead propagates as an unexpected `Error`/`RuntimeException` outside the normal `ContractValidateException`/`ContractExeException`/`BytecodeExecutionException` handling used elsewhere in the VM (e.g., as seen in `Program.voteWitness`, which only catches specific checked exceptions and lets `ArithmeticException` and others surface), it could crash the node process executing/validating that block or transaction, producing a denial-of-service impact for API/validation nodes. This falls short of memory corruption/RCE but matches the "node crash or halt" impact category permitted by the rules.

### Likelihood Explanation
Reaching this code requires only a normal signed transaction invoking the `ValidateMultiSign`/`BatchValidateSign` precompiled contract with crafted calldata — no special privileges are needed, matching the "unprivileged contract caller" reachability requirement. However, I could not fully confirm within the available index whether the top-level TVM interpreter loop wraps precompile execution in a catch-all that would downgrade any resulting `Error`/`RuntimeException` into a normal transaction revert rather than a node crash; this is the key open uncertainty limiting confidence in the "crash" impact.

### Recommendation
Add explicit bounds validation before using `len`, `bytesOffset`, and `bytesLen` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` — verify `len >= 0` and within a sane maximum, verify `offset + i + 1 < words.length`, and verify `bytesOffset`/`bytesLen`-derived byte ranges stay within `data.length` before allocation/copy, throwing a well-defined `BytecodeExecutionException`/`ContractValidateException` instead of letting raw `RuntimeException`/`Error` propagate.

### Proof of Concept
Concrete PoC could not be fully constructed/verified with the available tooling because the exact TVM dispatch/try-catch wrapper around precompile invocation (needed to confirm whether the thrown exception actually escapes to crash the node versus being caught as a transaction revert) was not located within the indexed portion of the codebase in the remaining investigation budget. This is a known limitation — a Devin session with full repository access could trace the call path from `getContractForAddress` through `Program`'s call-dispatch logic to confirm exception propagation behavior and build a concrete crafted-calldata PoC.
