### Title
Unsolicited StackerDB push chunk causes ack of unstored data due to inventory patched before actual storage - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` speculatively "patches" the outgoing `StackerDBChunkInv` reply to claim the local replica already holds a newly-pushed chunk's version, but the actual write to the local StackerDB happens later and asynchronously via the relayer (`Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`). This breaks the equality between "advertised inventory" and "actually stored data," analogous to the Oracle report's core flaw of using/committing to a value before the authoritative state is settled.

### Finding Description
When an unsolicited `StackerDBPushChunk` arrives, `handle_unsolicited_StackerDBPushChunk` builds a chunk inventory reply via `make_StackerDBChunksInv_or_Nack` and then cryptographically validates the pushed chunk with `validate_received_chunk` (signature, size, staleness relative to the *snapshot* `data.slot_versions`, and `max_writes`) [1](#0-0) . Immediately after this validation succeeds, the code patches the in-memory inventory (`*slot_version = chunk_data.chunk_data.slot_version;`) to claim the new version is present, and only afterward returns `(false, true)`, meaning "don't buffer, forward to relayer" — the actual database write has *not yet occurred* [2](#0-1) . The reply carrying this patched inventory is signed and sent back to the peer right away [3](#0-2) .

The actual persistence happens later, out-of-band, in `Relayer::process_pushed_stacker_db_chunks`, which converts the push into a `StackerDBSyncResult` and calls `process_stacker_db_chunks`, which in turn calls `StackerDBTx::try_replace_chunk` [4](#0-3) [5](#0-4) . `try_replace_chunk` re-checks the slot's stored version against `slot_desc.slot_version` and rejects with `StaleChunk` if the version is not strictly greater than what's already stored [6](#0-5) .

Because the check in `validate_received_chunk` used a version snapshot (`data.slot_versions`, taken from `get_slot_versions` inside `make_StackerDBChunksInv_or_Nack`) that can be stale relative to the DB by the time the deferred write actually executes, a second write for the same slot (arriving via a concurrent sync round, another unsolicited push, or an HTTP upload processed on a different thread) can commit first. When the relayer later attempts to store the chunk that was already acknowledged as present, `try_replace_chunk` returns `StaleChunk` and the write is silently dropped (only logged at `debug!` level in `process_stacker_db_chunks`) [7](#0-6) . The peer that received the ack, however, has already been told (via the signed `StackerDBChunkInv` reply) that this node holds that exact chunk version.

### Impact Explanation
This produces a durable mismatch between advertised inventory and actual stored state on the acking node: a remote, unprivileged peer can push a validly-signed chunk and receive an inventory acknowledgment claiming successful storage of a specific version, while the node's local StackerDB never actually contains that data (due to the race with `StaleChunk`). Downstream peers running `StackerDBSync`'s rarest/newest-first scheduling rely on these inventories to decide what to fetch and from whom; a node advertising data it doesn't have can cause peers to skip fetching that chunk from a node that legitimately has it, delaying or blocking propagation of legitimate signer/miner StackerDB messages. This matches the "serving non-canonical state as canonical" / "false inventory" impact class, since the served inventory does not reflect the node's true persisted state.

### Likelihood Explanation
Triggering the race requires two writers to the same slot competing close in time (e.g., two peers pushing successive chunk versions, or an HTTP upload racing a P2P push) — an unprivileged, remote condition that any StackerDB participant (or an attacker impersonating slot data flow, though it still needs a validly-signed chunk from the legitimate slot owner or an already-accepted higher version) can provoke by simply sending overlapping pushes. It does not require any special privilege beyond normal StackerDB write access, matching the "remote, unprivileged" bar, though it does depend on timing/race conditions rather than being deterministic on every message.

### Recommendation
Do not patch/acknowledge the chunk inventory until after the chunk has actually been durably written (i.e., only build/send the `StackerDBChunkInv` ack after `try_replace_chunk` succeeds in the relayer path, or perform the ack synchronously with the store rather than speculatively before handoff to the relayer). Alternatively, re-validate/re-fetch the true slot version at ack time so the acked inventory is guaranteed to reflect actually-committed state, consistent with the general principle (from the referenced report) of not using a value that can change out from under you before it is authoritatively committed.

### Proof of Concept
1. Node A replicates a StackerDB with a valid slot owned by signer key `K`.
2. Two `StackerDBPushChunk` messages for the same slot are sent to Node A in quick succession by different (or racing) connections: `chunk_v2` and `chunk_v3`, both validly signed by `K`, both currently satisfying `slot_version >= expected_version` against the stale inventory snapshot Node A had when each was received.
3. For `chunk_v3` (processed on one path), `handle_unsolicited_StackerDBPushChunk` validates and patches its local `StackerDBChunkInv` to slot_version=3 and sends a signed ack to the sender before actually storing it, then forwards it to the relayer queue.
4. Meanwhile `chunk_v2` is processed and physically stored first via a competing code path (e.g., `process_uploaded_stackerdb_chunks`/an independent sync round), setting stored version to 2.
5. When the relayer later processes the deferred write of `chunk_v3`, if a version 3 (or the same reused/duplicated slot_version marker) collides or if writes interleave such that `try_replace_chunk` sees a stored version >= 3 already (e.g., from a different push accepted in between), the second write is rejected as `StaleChunk` and silently dropped — yet the sender of `chunk_v3` already received a signed ack claiming Node A holds version 3.
6. Query Node A's actual StackerDB slot content/version afterward and compare against what was advertised in the earlier ack to confirm the mismatch.

Note: exact reproduction requires precise interleaving of the relayer's deferred storage step versus the immediate inventory-patch/ack step; this was identified through code-path analysis of `handle_unsolicited_StackerDBPushChunk`, `process_pushed_stacker_db_chunks`, and `try_replace_chunk`, and could not be dynamically executed in this environment to confirm exact timing windows in the current test suite.

        // synthesize StackerDBSyncResults from each chunk

            .collect();

            rc_consensus_hash,
