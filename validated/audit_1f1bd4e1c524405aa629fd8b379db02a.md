### Title
Lack of minimum liquidity requirement in TRC10 Exchange (Bancor-formula) allows single-transaction price manipulation - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
Compound's Open Oracle bug is that `medianPrice` accepts any sample size, letting an attacker manipulate the "official" price when few sources report. The java-tron analog is the TRC10 `Exchange` market: `ExchangeCreateActuator` only requires `firstTokenBalance > 0` and `secondTokenBalance > 0` (no minimum-liquidity floor), so any unprivileged account can create a "price" pool with an arbitrarily small, skewed reserve ratio, then trade against it in the same or a following transaction via `ExchangeTransactionActuator` to move the pool's implied exchange rate by orders of magnitude with negligible capital.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks `firstTokenBalance <= 0 || secondTokenBalance <= 0` and an upper `balanceLimit`, with no minimum reserve/liquidity threshold: [1](#0-0) 

This means the "sample size" backing the exchange's price — i.e., the reserve depth of the pool — can be as small as 1 unit on either side. The price/exchange-rate returned by the Bancor-style formula in `ExchangeCapsule.transaction`/`ExchangeProcessor.exchange` is derived purely from these two reserve balances: [2](#0-1) [3](#0-2) 

Because there is no minimum sample size / liquidity floor, a single attacker-controlled `ExchangeCreateContract` followed immediately by `ExchangeTransactionContract` trades (which only enforce a caller-supplied `tokenExpected` minimum-output slippage check, not a floor on total pool depth) can shift the reported/implied "price" of the pool dramatically within one or two transactions: [4](#0-3) 

This exchange price is exposed to unprivileged API clients via `getMarketPriceByPair` in `Wallet` (though this specific query path is for the separate order-book market, the `Exchange`/`ExchangeV2` store price itself is queryable/consumable elsewhere in Wallet, e.g. `getExchangeById`), and other on-chain contracts/relayers relying on the exchange's balance ratio as an oracle-like signal for a TRC10 pair would receive a manipulated value.

### Impact Explanation
Any protocol, contract or off-chain integrator that trusts the `Exchange`/`ExchangeV2` reserve ratio as a price reference for a TRC10 token pair can be manipulated with a single account controlling both sides of a low-liquidity pool it created itself, at near-zero cost. Downstream users who trade against this manipulated pool via `ExchangeTransactionActuator` can be made to receive far less than fair value, resulting in direct fund loss for the counterparties — this is a concrete unauthorized value-transfer/theft vector, matching the Medium/High bug class described in the analog report.

### Likelihood Explanation
High: creating an `Exchange` and injecting/trading against it are both ordinary, permissionless, single-signature transaction types (`ExchangeCreateContract`, `ExchangeTransactionContract`) reachable by any account with minimal TRX/asset balance — no special privilege, SR/witness status, or off-chain coordination is required.

### Recommendation
Add a minimum reserve/liquidity requirement in `ExchangeCreateActuator.doValidate()` (and correspondingly in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) enforcing that `firstTokenBalance` and `secondTokenBalance` each meet a protocol-defined minimum before a pool is considered a valid price source, and/or expose the pool's total liquidity alongside any price query so integrators can apply their own minimum-sample-size safeguards, mirroring the Compound Open Oracle recommendation of enforcing or surfacing a minimum sample size.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` with `firstTokenBalance = 1`, `secondTokenBalance = balanceLimit` (or vice versa) — this passes validation in `ExchangeCreateActuator.doValidate()` since only `>0` is required. [1](#0-0) 
2. The resulting pool's implied exchange rate is now extreme (e.g., `balanceLimit : 1`).
3. Attacker or a victim relying on this rate submits `ExchangeTransactionContract`; because the pool depth is trivial, small trades cause large rate swings per `ExchangeProcessor.exchange`, and the attacker can front/back-run the victim's `tokenExpected` slippage bound to extract value. [4](#0-3)
