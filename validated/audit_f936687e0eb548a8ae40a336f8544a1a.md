Audit Report

## Title
`reward_per_token` precision loss allows a griefer to permanently zero out staking rewards in `pallet-asset-rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` computes `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, where `PRECISION_SCALING_FACTOR` is a small fixed `u16` constant of `4096` [1](#0-0) . `update_pool_rewards` unconditionally advances `last_update_block` to the current block and overwrites `reward_per_token_stored` with the freshly computed value, regardless of whether that increment rounded down to zero [2](#0-1) . Because this update runs at the top of the public, unprivileged `stake`, `unstake`, and `harvest_rewards` extrinsics, an attacker who is (or cheaply becomes) a staker can call one of these every single block to force `blocks_elapsed = 1` on each commitment, maximizing the likelihood of integer-division rounding to zero and irrecoverably discarding that block's true reward contribution for every staker in the pool.

## Finding Description
`reward_per_token` derives `rewardable_blocks_elapsed` from `last_block_reward_applicable(...) - pool_info.last_update_block`, then computes `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` and adds it to `reward_per_token_stored` [3](#0-2) . `update_pool_and_staker_rewards` calls this and then `update_pool_rewards`, which commits both `last_update_block` and `reward_per_token_stored` unconditionally — there is no check that the increment was non-zero before advancing the window marker [4](#0-3) . All three public extrinsics (`stake`, `unstake`, `harvest_rewards`) call `update_pool_and_staker_rewards` as their first action [5](#0-4) [6](#0-5) .

Since `PRECISION_SCALING_FACTOR` is only `4096` (a `u16`, not a `u128`-scale fixed-point base like `1e18` or the `FixedU128`-based reward counters used in `nomination-pools`), any pool where `total_tokens_staked > reward_rate_per_block * 4096` will round its per-block increment to `0` when computed over a 1-block window. If the attacker forces `blocks_elapsed` to always equal `1` by invoking a cheap public extrinsic every block, `reward_per_token_stored` never accumulates the true multi-block reward, and `last_update_block` keeps ratcheting forward — permanently discarding the fractional/rounded reward for that window for every staker in the pool, not just the attacker. There is no accumulator for remainders and no gate preventing `last_update_block` advancement on a zero-increment commit.

## Impact Explanation
This degrades payout correctness for a public `RewardsPool` primitive: legitimate stakers who never interact can have their accrued rewards silently reduced toward zero indefinitely, as long as the attacker sustains one cheap call per block. The attack requires no privileged role — only being an existing staker (achievable via a minimal `stake` call) and paying ordinary per-block transaction fees, matching the "runtime bugs that compromise intended behavior" / degraded-payout-state category.

## Likelihood Explanation
Exploitability is configuration-dependent: it requires `total_tokens_staked` to be large relative to `reward_rate_per_block * 4096`, which is realistic for pools with a large total stake and modest reward rate (e.g., whale-heavy pools). The attacker must sustain a call every block, which is an ongoing cost (not free), so the "permanence" of the loss lasts only as long as the attacker continues submitting transactions; if the attacker stops, `blocks_elapsed` grows and normal accrual resumes. This makes the issue a real, reachable griefing/precision-loss primitive, though its severity is bounded by the attacker's willingness to continuously pay transaction fees on every block.

## Recommendation
- Avoid discarding the elapsed-block window when the computed increment rounds to zero — either accumulate a remainder for future computations, or use a much larger precision multiplier (`u128`-scale, similar to `nomination-pools`' `FixedU128`-based `RewardCounter`) so rounding-to-zero is not realistically reachable at 1-block granularity.
- Alternatively, avoid advancing `last_update_block` when the resulting increment is zero, so the effective accrual window keeps growing until it produces a non-zero, correctly rounded increment.

## Proof of Concept
1. `create_pool` with `reward_rate_per_block = R` and have a whale stake `S` tokens such that `R * 4096 / S < 1` for `blocks_elapsed = 1`, but `R * N * 4096 / S >= 1` for accumulated `N` blocks.
2. Attacker calls `stake(pool_id, 1)` (or `harvest_rewards`) every block.
3. Each call runs `reward_per_token` with `blocks_elapsed = 1`, yielding a `0` increment via integer division at [7](#0-6) , and `update_pool_rewards` unconditionally advances `last_update_block` [8](#0-7) .
4. After `N` blocks, a legitimate staker who never interacted calls `harvest_rewards`: their `derive_rewards` output is `0` or far below the honest `R * N * 4096 / S` expectation, because `reward_per_token_stored` was never allowed to accumulate over the full window.

		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,

			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
