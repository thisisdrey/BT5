### Title
Missing slippage protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` enables sandwich attacks against Bancor-style exchange liquidity providers - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The reported bug class is the lack of a caller-specified minimum/maximum bound on the "other side" of an AMM-style liquidity operation, which lets the exact output of a proportional-ratio computation be manipulated by a transaction that executes in between submission and inclusion (front-running/sandwiching). Java-tron's on-chain Bancor-formula exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) reproduces this exact pattern for liquidity injection and withdrawal.

### Finding Description
`ExchangeInjectActuator.execute`/`doValidate` computes the counterpart token amount (`anotherTokenQuant`) purely as a function of the exchange's *current* `firstTokenBalance`/`secondTokenBalance` ratio at execution time: [1](#0-0) 

Unlike `ExchangeTransactionContract`, which was deliberately given an `expected` field to bound slippage: [2](#0-1) 
and enforced in `ExchangeTransactionActuator.doValidate`: [3](#0-2) 

`ExchangeInjectContract` (and `ExchangeWithdrawContract`) only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum/maximum bound field on the counterpart amount at all: [4](#0-3) 

`ExchangeWithdrawActuator` has the same structure: `anotherTokenQuant` is derived solely from the pool ratio at execution time with no caller-supplied bound: [5](#0-4) 

Because `ExchangeTransactionContract` is permissionless (any account holding the token can call it) and directly mutates `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction`: [6](#0-5) 

an attacker who observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) in the mempool/same block can submit a large `ExchangeTransactionContract` swap immediately before it to shift the ratio, then reverse it afterward — a classic sandwich. Since the injecting/withdrawing party has no way to bound `anotherTokenQuant`, they are forced to accept whatever ratio exists at the moment of block execution.

### Impact Explanation
The exchange creator (the only party permitted to inject/withdraw, per the `is not creator` check in both actuators) can be forced to deposit or receive counterpart-token amounts far from what they intended, resulting in direct, unauthorized financial loss extractable by the attacker via the surrounding sandwich trades. This matches the reported consequence category (financial loss due to unenforced slippage bounds on an AMM-style balance operation).

### Likelihood Explanation
Medium. It only requires an unprivileged account to submit a permissionless `ExchangeTransactionContract` transaction ordered before a known pending `ExchangeInjectContract`/`ExchangeWithdrawContract` in the same block — no special privilege, witness/SR role, or protocol bug is needed, only normal transaction-ordering/MEV capability that any node operator or block producer has.

### Recommendation
Add a caller-specified minimum (for withdraw) or maximum (for inject) bound field for `anotherTokenQuant` to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the existing `expected` field pattern already used in `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate`/`execute` and `ExchangeWithdrawActuator.doValidate`/`execute`.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeInjectContract{exchangeId, tokenId=A, quant=X}` expecting `anotherTokenQuant ≈ secondBalance*X/firstBalance` based on the ratio they last observed.
2. Before this transaction is packed into a block, an attacker broadcasts `ExchangeTransactionContract` selling a large amount of token A (or B) into the same exchange, shifting `firstTokenBalance`/`secondTokenBalance` (via `ExchangeCapsule.transaction`, `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:57-69`).
3. The creator's `ExchangeInjectContract` is then executed against the manipulated ratio (`ExchangeInjectActuator.java:215-227`), forcing them to inject an `anotherTokenQuant` far larger/smaller than intended, with no on-chain check to reject the deviation.
4. The attacker submits a reverse trade to restore the ratio and pocket the difference, completing the sandwich — analogous to the `addLiquidity`/`swapTokensForCounterpart` PoC in the source report.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }
