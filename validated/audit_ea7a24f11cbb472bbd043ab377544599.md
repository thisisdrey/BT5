## Title
Data race on shared, unsynchronized `JumpTable` opcode tables during concurrent TVM execution enables opcode/energy-cost corruption reachable from public constant-call APIs - (File: `actuator/src/main/java/org/tron/core/vm/OperationRegistry.java`)

### Summary
The reported Node.js bug class is a re-entrant/concurrent mutation of shared execution state while it is being actively read by another in-flight execution, producing memory corruption. The closest reachable analog in java-tron is the TVM's `OperationRegistry`/`JumpTable` design: a small number of `static` `JumpTable` instances (the shared consensus table and the dedicated `CONSTANT_CALL_TABLE`) back every VM execution, and `Operation` entries inside them are mutated in place (`table.set(...)`) on every top-level call via `adjustTable()`, concurrently with other threads reading (`table.get(op)`) and executing opcodes from the very same table object.

### Finding Description
`OperationRegistry` keeps two mutable, `static` `JumpTable` instances that are shared across the whole node process: [1](#0-0) 

Each top-level VM execution — including every unauthenticated `triggerconstantcontract` / `eth_call` / `estimateenergy` request — calls `prepareAndGetTable()`, which fetches the shared table object and then mutates entries inside it in place: [2](#0-1) 

`adjustTable()` calls `adjustMemOperations`, `adjustVoteWitness`, and `adjustSelfdestruct`, each of which does `table.set(new Operation(...))`, replacing entries in the same array-backed structure while other requests may be simultaneously iterating over it: [3](#0-2) 

`JumpTable` is a plain `Operation[256]` array with unsynchronized `get`/`set` — there is no lock, no volatile, no copy-on-write semantics. Every call into `VMActuator.execute()` triggers this in-place mutation of the shared table before executing opcodes with `VM.play`: [4](#0-3) 

`VM.play` then reads `jumpTable.get(...)` on every single opcode step for the whole execution, so any request currently executing keeps referencing the same shared object while other requests concurrently call `prepareAndGetTable()` → `adjustTable()` on it: [5](#0-4) 

This is directly reachable from unauthenticated, unprivileged callers: `Wallet.callConstantContract` builds a fresh `VMActuator(true)` for every RPC/HTTP/gRPC `triggerconstantcontract`/`eth_call` request, and each of these calls independently drives `prepareAndGetTable(true)` against the single shared `CONSTANT_CALL_TABLE`: [6](#0-5) 

gRPC (`RpcApiService`), HTTP, and JSON-RPC (`TronJsonRpcImpl.call`) all route anonymous, concurrent client requests into this same code path: [7](#0-6) [8](#0-7) 

The bug-class parallel to CVE-2026-56848 is: one execution path (`VM.play` reading `table.get(op)` while stepping through opcodes) is re-entered/interleaved with another execution path (`adjustTable()` mutating `table.set(op)` on the same object) with no synchronization. In Java this cannot produce a native heap-use-after-free, but it is a genuine unsynchronized concurrent read/write race on a shared mutable array that backs consensus-critical opcode dispatch and energy metering for every TVM execution on the node.

### Impact Explanation
- Energy/dispatch inconsistency under race: A thread executing an opcode via `jumpTable.get(op)` can observe a torn/partially-updated `Operation` reference (e.g., mid-swap between the "default" and "adjusted" cost function variant) if `adjustTable()` on another thread is concurrently calling `table.set(...)` for the same opcode slot. Because `Operation` objects are immutable and array writes of object references are atomic in the JVM memory model, a torn *object* is not possible, but a stale/inconsistent *choice* between two valid variants (default vs. adjusted energy-cost function) can be observed, meaning identical opcodes executed at effectively the same time can be metered with different energy-cost logic depending on the interleaving with a concurrent `adjustTable()` call. Since `CONSTANT_CALL_TABLE`'s adjustments are purely a function of live `VMConfig` proposal/fork flags (which are process-wide, not per-request), this does not currently allow forging execution against a different, attacker-chosen historic table version, but it does allow non-deterministic accounting/metering between concurrently issued constant calls.
- Availability: A high volume of concurrent constant-call/eth_call requests to a public full node hammering the shared `JumpTable` mutation path adds unnecessary per-request array writes to a globally shared object on a hot path, increasing contention/cache-thrashing across all constant-call worker threads. This does not crash the JVM (arrays are memory-safe in Java), so it does not rise to the RCE/heap-corruption severity of the original Node.js CVE.

### Likelihood Explanation
Any anonymous client can trigger this by issuing ordinary `triggerconstantcontract`/`eth_call`/`estimateenergy` requests concurrently — no special privileges, signed transaction, or contract deployment is required, and modern RPC/HTTP/JSON-RPC front-ends process such requests on many worker threads simultaneously by design. However, actually observing the race requires the concurrent execution window (`table.set` interleaved with a live `table.get` for the exact opcode) and requires that `VMConfig` flags are already in an "adjustable" state (config-flag toggles are effectively idempotent no-ops most of the time, so the practical window in which distinct `Operation` variants are actually swapped is narrow and depends on flag flips or first-call cold-start races).

### Recommendation
Do not mutate the shared, `static` `JumpTable` instances in place on the hot request path. Instead:
- Compute the adjusted variant of the table once and only pass an immutable, request-scoped copy (or a properly published, versioned, immutable snapshot) into `VM.play`, or
- Guard `adjustTable()` with synchronization/CAS-published table swaps so concurrent requests never observe interleaved reads/writes on the same mutable array, or
- Precompute all `Operation` variants ahead of time and select between fully-immutable pre-built tables based on the current `VMConfig` state, rather than mutating a shared table's slots per request.

### Proof of Concept
Conceptual PoC (concurrency-dependent, not deterministically reproducible without control of `VMConfig` flag transitions):
1. Start a full node with `vm.supportConstant = true` and RPC/HTTP enabled.
2. From two or more separate client connections, continuously and concurrently call `/wallet/triggerconstantcontract` (or `eth_call`) against any deployed contract that exercises `MLOAD`/`MSTORE`/`VOTEWITNESS`/`SUICIDE` opcodes, while flipping the relevant fork/config flags (`allowHigherLimitForMaxCpuTimeOfOneTx`, `allowEnergyAdjustment`, `allowTvmOsaka`, `allowTvmSelfdestructRestriction`) that drive `adjustMemOperations`/`adjustVoteWitness`/`adjustSelfdestruct` in `OperationRegistry.java`.
3. Observe (with instrumentation/logging inserted into `JumpTable.get`/`set`) that `Operation` instances returned for the same opcode differ between concurrently-executing requests, or occur in interleavings inconsistent with any single well-ordered execution, demonstrating the unsynchronized read/write race on the shared table object.

**Note on confidence**: I could not find evidence that this specific race has caused an observed consensus-breaking or crash-inducing incident in this codebase, and I could not fully verify how often/whether `VMConfig` flags actually flip during live production traffic (this determines how often `adjustTable()` actually performs a `table.set` versus a no-op). This weakens the case for High severity impact versus the original Node.js CVE, which was a memory-safety heap-use-after-free (RCE-class). I flag this uncertainty because the Java runtime's memory safety prevents this from reaching the "node crash/RCE" bar demanded by the validation rules, and I was not able to fully explore whether concurrent execution of `triggerconstantcontract` is actually possible under the node's current threading model (e.g., whether gRPC/HTTP worker pools truly execute these handlers in parallel against the same `Manager`/`Wallet` singleton) within my available tool budget — this would need to be confirmed by tracing the gRPC/HTTP server thread-pool configuration in a live session.

  public static JumpTable prepareAndGetTable(boolean isConstantCall) {
    JumpTable table = getTable(isConstantCall);
    // Apply configuration-dependent changes once at the top level.
    adjustTable(table);
    return table;
  }

  public static JumpTable getTable(boolean isConstantCall) {
    return isConstantCall ? CONSTANT_CALL_TABLE : tableMap.get(LATEST_VERSION);
  }

  private static void adjustTable(JumpTable table) {
    // Make the corresponding changes, excluding opcode activation.
    adjustMemOperations(table);
    adjustVoteWitness(table);
    adjustSelfdestruct(table);
  }
