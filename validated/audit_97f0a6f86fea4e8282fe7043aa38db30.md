### Title
Heap out-of-bounds read parsing ZIP central-directory extra fields in ijar - (File: third_party/ijar/zip.cc)

### Summary
`ldns_rr_new_frm_str_internal` in ldns 1.7.1 trusted length/field data taken from an attacker-supplied zone file and read past the end of the allocated buffer. Bazel's own ZIP/JAR parser used by the `ijar` tool has the same bug class: `InputZipFile::ProcessCentralDirEntry` trusts attacker-controlled length fields inside a `.jar`'s central directory record without validating them against the mapped file's bounds, leading to an out-of-bounds heap read.

### Finding Description
`ijar` is Bazel's interface-JAR generator; it memory-maps an input JAR and walks its ZIP central directory to compute per-entry metadata. `FindZipCentralDirectory` bounds-checks only the aggregate `central_dir_offset + central_dir_size` against the file length [1](#0-0) , but per-entry parsing in `ProcessCentralDirEntry` performs no `EnsureRemaining`-style check at all (unlike `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining` before every read [2](#0-1) ).

`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the untrusted CDH record and unconditionally advances the cursor `p` and `extra_p` by these attacker-controlled 16-bit values [3](#0-2) . It then loops over the "extra fields" region reading a `header_id` and `data_size` from `extra_p`, and when `header_id == ZIP64_EXTRA_FIELD_TAG` it unconditionally calls `get_u8le(extra)` (reading 8 bytes) regardless of whether `data_size` is actually ≥ 8 or whether those 8 bytes still fall inside the declared extra-field/central-directory/file bounds [4](#0-3) . If a malicious JAR declares an extra field with `data_size` smaller than 8 (or an `extra_field_length`/`file_comment_length` that runs past the actual mapped-file end near the boundary of the last central-directory entry), the loop's `extra_p != p` termination condition can be skipped over, and the `get_u8le`/`get_u4le`/`get_u2le` primitives — which perform no bounds checking themselves — read past the end of the mmap'ed input buffer, leaking adjacent heap/mapped memory contents into the computed offset/size values (which are later used to build filenames/attributes and could be surfaced in error messages or the emitted interface jar).

This is functionally the same class of bug as CVE-2020-19860: a length-prefixed record format is parsed by trusting embedded, attacker-controlled length fields without validating them against the actual remaining buffer, producing a heap out-of-bounds read.

### Impact Explanation
An attacker who controls the bytes of a `.jar`/`.srcjar` that ends up processed by `ijar` (e.g., a JAR fetched from a hostile HTTP mirror via `http_jar`/`http_file` without a `sha256` pin, or a JAR checked into an untrusted branch that CI builds with `java_import`) can craft a central directory whose length fields cause `ProcessCentralDirEntry` to read past the mapped file. This is an information-disclosure primitive (heap/mmap adjacent memory read), and depending on how the leaked bytes propagate (filenames, size/offset fields used downstream) it could also destabilize the build (crash on unmapped page) — matching the "heap out of bounds read... leak information on the heap" pattern of the CVE.

### Likelihood Explanation
Reachable whenever `ijar` processes a JAR whose bytes are not integrity-checked against a pinned digest before being handed to `ijar` — e.g., `http_jar`/`http_file`/`maven_jar` rules used without `sha256`, or JARs coming from an untrusted VCS branch built via `java_import`. No credentials or local machine access are required; this only requires an attacker able to publish/serve the JAR bytes that the build consumes. There is existing test coverage (`MalformedExtraField` in `output_jar_simple_test.cc` [5](#0-4) ) confirming that malformed-extra-field handling was previously identified as a bug class and fixed in the separate `singlejar`/`output_jar.cc` code path (`AppendToDirectoryBuffer` now validates `ef` bounds against `ef_end` and calls `diag_errx` on overflow [6](#0-5) ) — but the equivalent validation is absent in `third_party/ijar/zip.cc`'s `ProcessCentralDirEntry`, indicating the fix was not applied uniformly across Bazel's two independent ZIP-parsing implementations.

### Recommendation
In `ProcessCentralDirEntry` (`third_party/ijar/zip.cc`), validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the remaining bytes in the mapped file (an `EnsureRemaining`-equivalent check, as already done in `ProcessLocalFileEntry`) before advancing `p`. Within the extra-field loop, verify that `extra_p + 4 + data_size` does not exceed the extra-field region end before reading `header_id`/`data_size`, and additionally verify `data_size >= 8` before calling `get_u8le(extra)` for the ZIP64 extra field, mirroring the bounds checks already present in `ExtraField::find` in `src/tools/singlejar/zip_headers.h` [7](#0-6)  and in `AppendToDirectoryBuffer`'s extra-field validation.

### Proof of Concept
A JUnit/shell reproduction path: construct a minimal ZIP with one central-directory entry whose `extra_field_length` declares an ZIP64 extra field with `data_size < 8` (e.g., `data_size = 2`) placed at the very end of the mapped file (i.e., no trailing EOCD bytes beyond it, or crafted so the extra field abuts the file boundary), then invoke `ijar` (`bazel-bin/third_party/ijar/ijar` or the `ZipExtractor`/`InputZipFile::ProcessNext` path) on this file under ASan; the `get_u8le(extra)` call in `ProcessCentralDirEntry` reads 8 bytes starting at `extra`, running past the declared 2-byte payload and potentially past the mapped file's end, which ASan/valgrind would flag as a heap-buffer-overflow (read). This mirrors the existing `CreateZipWithMalformedExtraField` test-construction pattern used for the analogous, already-fixed bug in `output_jar_simple_test.cc` [8](#0-7) , but targeting `third_party/ijar/zip.cc`'s unguarded `ProcessCentralDirEntry` instead.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}

                                const uint8_t* end) {
    while (start < end) {

        break;

      }
