Based on my investigation, `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` defaults to `0` (disabled) unless a committee proposal has activated it on a given network [1](#0-0) , so on any TRON-based network where this proposal has not been passed, the legacy unguarded code path is live.

### Title
Unbounded array allocation from attacker-controlled ABI length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes node OOM crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `extractBytesArray` and `extractBytes32Array` helpers used by the `ValidateMultiSign` (address `0x...a`) and `BatchValidateSign` (address `0x...9`) TVM precompiles read an array-length word directly from attacker-supplied calldata and immediately allocate a Java array of that size, before any bound (`MAX_SIZE`) check is applied. When the `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` chain parameter is not active (its default state, `getAllowTvmSelfdestructRestriction()` defaults to `0`), the size-limiting guard is skipped entirely and the unbounded allocation runs unconditionally, exactly analogous to CVE-2024-24478's pattern of an attacker-controlled length field driving unbounded resource consumption in a parser.

### Finding Description
`extractBytesArray` and `extractBytes32Array` take an ABI-word array and an `offset`, read `int len = words[offset].intValueSafe()`, and immediately do `new byte[len][]` with no upper bound check: [2](#0-1) 

In `ValidateMultiSign.execute`, the `MAX_SIZE` (5) check on `sigArraySize` is only performed `if (VMConfig.allowTvmSelfdestructRestriction())`; otherwise `extractBytesArray` is invoked directly with the attacker-controlled length, and the `signatures.length > MAX_SIZE` check happens only *after* the array has already been allocated: [3](#0-2) 

In `BatchValidateSign.doExecute`, the same pattern applies to `extractBytesArray` for signatures, and critically `extractBytes32Array` for the address array is called **unconditionally** (not gated by the size check at all) using the exact same attacker-controlled length word: [4](#0-3) 

Energy for these precompiles is charged purely off `data.length / WORD_SIZE`, not off the length value embedded inside the ABI payload: [5](#0-4) [6](#0-5)  An attacker can therefore submit a tiny calldata payload (a handful of words) whose embedded "array length" word is set to a huge value (e.g. close to `Integer.MAX_VALUE`), triggering a huge `new byte[len][]` allocation attempt while paying negligible energy for the actual calldata size.

The allocation attempt throws `OutOfMemoryError`, which is a JVM `Error`, not a `RuntimeException`. Neither `ValidateMultiSign.execute` nor the outer `PrecompiledContracts` call chain wrap this allocation in a `catch (Throwable)`; the only `Throwable` catch in `ValidateMultiSign` is scoped to the weight-computation loop that runs *after* the allocation already succeeded/failed. The main `VM.play()` interpreter loop only catches `RuntimeException`, `JVMStackOverFlowException`, and `OutOfTimeException` around opcode execution [7](#0-6) [8](#0-7) , so an uncaught `OutOfMemoryError` propagates up through transaction execution unhandled, on every full node that must execute/validate this transaction as part of block processing.

### Impact Explanation
Every full node in the network processes each transaction to validate blocks. A single crafted transaction that calls either precompile with a malicious embedded array-length word can force each processing node's JVM to attempt a multi-gigabyte array allocation for the price of a few words of calldata. This causes `OutOfMemoryError`, which can destabilize or crash the node process, or degrade the JVM heap for all other concurrent activity on that node (including consensus and RPC serving). Because this must be replayed by all full nodes validating the block containing the transaction, it is a network-wide denial-of-service vector, not merely a single-node issue.

### Likelihood Explanation
Exploitability is high on any TRON-based chain (mainnet, testnet, or private/side chain) where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated via committee proposal — the default value is `0` [1](#0-0) . Triggering the bug requires only: (1) deploying or reusing any contract that performs a `CALL`/`STATICCALL` to the precompile address (`0x...9` or `0x...a`), and (2) crafting calldata whose ABI "array length" word is set to a very large value — both trivially achievable by any unprivileged transaction broadcaster via `TriggerSmartContract`/`TriggerConstantContract`.

### Recommendation
Move the `sigArraySize`/`addrArraySize` bound check (against `MAX_SIZE`) so it always executes unconditionally, before calling `extractBytesArray`/`extractBytes32Array`, regardless of `VMConfig.allowTvmSelfdestructRestriction()`. Additionally, add an internal length sanity check inside `extractBytesArray`/`extractBytes32Array` themselves (e.g., reject `len < 0` or `len` beyond a small constant) before performing `new byte[len][]`, so the helpers are safe by construction and not solely dependent on caller discipline.

### Proof of Concept
1. Deploy a trivial forwarder contract, or directly target the precompile address via `TriggerSmartContract`, on a network where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION == 0` (default).
2. Build calldata for `batchvalidatesign(bytes32,bytes[],address[])` (address `0x...9`) or `validatemultisign(address,uint256,bytes32,bytes[])` (address `0x...a`) by hand rather than through a well-formed ABI encoder:
   - Populate the static head words normally (hash/address/permissionId).
   - Set the `bytes[]`/`address[]` offset word to point at a location within the small calldata buffer.
   - At that location, set the "array length" word to `0x7FFFFFFF` (or another very large value), and omit the actual per-element data (keeping total calldata small, e.g. under 300 bytes).
3. Submit this as calldata in a `TriggerSmartContract` transaction with a modest `fee_limit`.
4. On execution, `extractBytesArray`/`extractBytes32Array` executes `new byte[0x7FFFFFFF][]`, which attempts to allocate on the order of tens of gigabytes, immediately raising an uncaught `OutOfMemoryError` that propagates out of `VM.play()` unhandled on every node executing/validating the block.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();

    }
    return bytesArray;
  }
