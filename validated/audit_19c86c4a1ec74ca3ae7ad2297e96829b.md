### Title
Pre-staged EOA balance/resources merge into the TIP-2935 system contract account on activation, letting an attacker retain funded/staked state under a privileged system address - ([File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java])

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP-2935 `BlockHashHistory` system contract at the fixed address `HISTORY_STORAGE_ADDRESS` when the `ALLOW_TVM_PRAGUE` proposal is activated by the committee, via `ProposalService.process()`. Any unprivileged account can, before activation, send a normal TRX transfer to this fixed, publicly known address, creating a normal `AccountCapsule` there with balance, frozen (staked) balance, votes, and other state. When `deploy()` later runs, it only checks `CodeStore`/`ContractStore` for a foreign occupant; if the account exists but is not yet code-bearing, it silently *upgrades* the pre-existing account in place (`account.updateAccountType(Contract)`, `account.clearDelegatedResource()`) rather than rejecting or resetting it, and merges the attacker-controlled balance/state into the resulting system contract account.

### Finding Description
`deploy()` is analogous to the reported bug class (CWE-501, trust boundary violation via name/identity confusion): the resource identity used for a privileged operation (a fixed, well-known address that will host a protocol-critical system contract) is checked for collision on the wrong stores. It checks `manager.getCodeStore().has(...)` and `manager.getContractStore().has(...)` but does not require the `AccountStore` entry at that address to be empty/new: [1](#0-0) 

Any transaction broadcaster can pre-fund/pre-stake this exact address before the SR committee ever activates `ALLOW_TVM_PRAGUE` — the address is a fixed constant published in the source, so anyone can compute it in advance: [2](#0-1) 

The project's own test suite documents this exact scenario as expected behavior rather than as a defect: an EOA squatting on the canonical address before activation gets upgraded in place with its balance preserved: [3](#0-2) [4](#0-3) 

The upgrade path only clears `delegatedResource` state; it does not clear/settle frozen (staked) balance, votes, asset balances, or account permissions that an attacker could have set on that account prior to activation: [5](#0-4) 

This mirrors the GHSA-fg9q-5cw2-p6r9 pattern where a user-controlled identifier (a Kubernetes PV name matching a worker node) is used to claim/merge into a privileged resource without the system verifying that the pre-existing resource is actually "empty"/newly-provisioned. Here the "name" is the fixed system contract address, and an unprivileged, ordinary account operation (a plain TRX transfer / freeze / vote, all reachable by any broadcaster) is used to plant state under that identity ahead of the privileged activation transaction (the proposal).

### Impact Explanation
The direct funds-theft angle is limited because the address is deterministic and public, so no other party's real funds land there accidentally; the primary attacker-reachable effect is that the attacker's own frozen TRX, votes, and resource-delegation state become attached to a protocol system contract account once it goes live. Depending on how staking/voting reward accounting and resource distribution treat an `AccountType.Contract` account with leftover `frozen`/vote state (not fully investigated here — see uncertainty below), this could let an attacker retain artificial TRON Power/voting weight, bandwidth/energy allowances, or block reward eligibility permanently associated with a system address that is not supposed to be a normal staking participant, since the account is never fully reset on the type-upgrade path. This is a Medium/High severity integrity issue (unbacked resource/stake accounting tied to a privileged system identity) rather than a direct fund-theft/RCE bug.

### Likelihood Explanation
Likelihood is high for triggering the "collision-merge" code path itself: any user can send a transfer, freeze, or vote against the fixed, publicly known `HISTORY_STORAGE_ADDRESS` at any time before the `ALLOW_TVM_PRAGUE` proposal passes, and committee proposal activation timing is generally observable/predictable in advance. The exact economic exploitability of the merged leftover state (whether it produces double-counted TRON Power, uncollectable rewards, or accounting drift once the account becomes type `Contract`) is not confirmed from the code read so far.

### Recommendation
In `HistoryBlockHashUtil.deploy()`, before upgrading a pre-existing account in place, fully reset/settle any staking-related state (frozen balances, votes, delegated resource records, asset balances, permissions) rather than only calling `clearDelegatedResource()`, or reject activation onto a non-empty account and instead redirect/refund the pre-existing balance to its rightful state before conversion. At minimum, add an explicit collision check against non-empty `AccountStore` state (not just `CodeStore`/`ContractStore`) and document/handle the full set of account fields that must not silently carry over into a system contract account.

### Proof of Concept
1. Before the SRs pass the `ALLOW_TVM_PRAGUE` proposal, an attacker sends a `TransferContract` to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`), creating a normal `AccountCapsule` there.
2. The attacker further freezes TRX for bandwidth/energy and/or votes for witnesses using that same address (all ordinary, unprivileged transactions any broadcaster can send).
3. The SR committee later activates `ALLOW_TVM_PRAGUE` via a normal proposal; `ProposalService.process()` calls `HistoryBlockHashUtil.deploy(manager)`.
4. `deploy()` finds the account already exists, calls `account.updateAccountType(Contract)` and `account.clearDelegatedResource()` only, then writes the account back — preserving balance and (per the code) not clearing frozen/vote state — as confirmed by the project's own `deployUpgradesPreExistingNormalAccountPreservingBalance` test.
5. The account at the canonical system-contract address now carries attacker-originated frozen balance/vote state merged with the system contract identity, a state the design never anticipated a normal account holder to inject into a protocol-managed address.

  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);
