### Title
Unprivileged account can permanently occupy a victim's `depositTokensOfAccount`/`debtTokensOfAccount` slots via 1-wei deposits, blocking new collateral deposits and new debt issuance (griefing into liquidation) - ([File: contracts/Pool.sol])

### Summary
The Nokogiri/libxml XEE advisory (CVE-2015-1819) is an expansion-based resource exhaustion: a small crafted input inflates a bounded resource and the consumer chokes on it. The Metronome analog is the per-account token list in `Pool`, which is hard-capped at `MAX_TOKENS_PER_USER = 30` combined deposit+debt tokens. Any account can inflate a *victim's* list by depositing or transferring 1 wei of each enabled `DepositToken` to them, because `DepositToken._mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero [1](#0-0) . Once the cap is reached, `onlyIfAdditionWillNotReachMaxTokens` reverts every subsequent first-time token addition for that victim [2](#0-1) .

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are called by the token contracts, not by the recipient, and enforce `debtTokensOfAccount.length + depositTokensOfAccount.length < 30` [3](#0-2) .
- `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint dust `msdTOKEN` directly to a victim's address (`onBehalfOf_` is attacker-chosen) [4](#0-3) . `DepositToken.transfer` achieves the same for tokens the attacker already holds [5](#0-4) .
- An entry is only removed when the victim's balance of that token goes to zero, via `_burn`/`_transfer` → `removeFromDepositTokensOfAccount` [6](#0-5) . Both `withdraw` and `transfer` require `unlockedBalanceOf(account) >= amount` [7](#0-6) . For a victim with an at-limit debt position, `unlockedBalanceOf` returns 0 (`_issuableInUsd == 0` → `_unlockedBalance` stays 0) [8](#0-7) , so the dust entries cannot be removed at all while the position is tight.

Invariant broken: liveness of victim's position management — the victim cannot deposit a new collateral type (mint → `addToDepositTokensOfAccount` reverts) nor issue a new debt token type (`DebtToken._mint` → `addToDebtTokensOfAccount` reverts) [9](#0-8) . No modifier (`whenNotPaused`, `nonReentrant`, SynthContext checks) stops the dust insertion; `TreasuryCanNotDeposit` and `onlyIfDepositTokenExists` are irrelevant.

### Impact Explanation
Direct, exploitable harm: a victim whose health factor is degrading normally rescues the position by depositing *a different* collateral (e.g., the depegged/falling one is no longer useful) or issuing a different synth. With all 30 slots filled by attacker's dust, `deposit()` of any not-yet-held collateral reverts with `UserReachedMaxTokens`, so the victim cannot add collateral and is pushed into liquidation — the attacker can liquidate them via `Pool.liquidate` and collect the liquidation incentive. Impact = forced liquidation / temporary-to-semi-permanent freezing of the victim's ability to manage their position; cleanup is impossible precisely when `unlockedBalanceOf` is 0.

### Likelihood Explanation
Cost is trivial: `deposit(1, victim)` (or `transfer(victim, 1)`) per enabled deposit token — on the deployed pools only a handful of deposit/debt tokens exist, so filling 30 slots requires repeating dust deposits on the same token? No — a token is only added once per account, so the attacker needs ~30 distinct enabled deposit/debt tokens OR must combine with debt tokens. This is the limiting factor: the attack requires the pool to have enough enabled deposit tokens (or the victim to already occupy some slots) to reach 30. Pools with many listed collaterals (e.g., mainnet deployment) make it cheap; pools with few tokens make it infeasible. Likelihood is therefore moderate and configuration-dependent, but the mechanism is fully reachable by an unprivileged EOA with no privileged roles.

### Recommendation
- Only add to `depositTokensOfAccount` on `deposit()` when `onBehalfOf_ == _msgSender()` or when the minted amount exceeds a minimum dust threshold; alternatively add an opt-out/remove path callable by the account itself (`Pool.removeFromDepositTokensOfAccount` permissioned to the account, burning their dust balance).
- Alternatively, let `withdraw`/`transfer` of the full balance bypass `unlockedBalanceOf` when the token contributes negligibly to collateral, so victims can always evict dust entries.
- Raise or remove the combined cap, or count deposit and debt tokens in separate caps so one list can't be exhausted by the other.

### Proof of Concept
```ts
// Hardhat sketch — pool with >=30 enabled deposit tokens
it('fills victim token list via dust deposits, blocking new collateral', async () => {
  const victim = bob.address;

  // Attacker deposits 1 wei of every enabled DepositToken on behalf of victim
  for (const dt of depositTokens) { // 30 enabled deposit tokens
    await underlying(dt).approve(dt.address, 1);
    await dt.deposit(1, victim); // mints dust -> pool.addToDepositTokensOfAccount(victim)
  }

  expect(await pool.getDepositTokensOfAccount(victim)).to.have.lengthOf(30);

  // Victim tries to deposit a collateral they don't hold yet -> reverts
  const newCollateral = depositToken31;
  await underlying(newCollateral).mint(victim, parseEther('10'));
  await underlying(newCollateral).connect(bob).approve(newCollateral.address, parseEther('10'));
  await expect(
    newCollateral.connect(bob).deposit(parseEther('10'), victim)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // Same for issuing a not-yet-held debt token
  await expect(
    newDebtToken.connect(bob).issue(1, victim)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // If victim has debt with _issuableInUsd == 0, unlockedBalanceOf(victim) == 0,
  // so withdraw(1)/transfer(dust) revert -> entries cannot be evicted.
});
```
