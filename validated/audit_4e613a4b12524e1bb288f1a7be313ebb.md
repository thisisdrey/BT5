### Title
Overpaid deposit is permanently locked in `AddressRegistrar::register` on successful registration - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
`AddressRegistrar::register` only validates that the attached deposit is *at least* the required storage cost (`given_deposit < required_deposit` → panic), but on the success path (new address registered) it never refunds the difference between `given_deposit` and `required_deposit`. The full `given_deposit`, including any overpayment, is retained by the contract with no way for the caller to reclaim the excess.

### Finding Description
`register()` computes the exact storage cost needed to store the new `(address, account_id)` entry: [1](#0-0) 

It only checks a lower bound (`given_deposit < required_deposit`) and panics if insufficient, but performs no upper-bound check or refund logic on the success path. When the entry is `Vacant` (i.e., registration succeeds), the code simply inserts the entry and logs a message — it never returns any part of `given_deposit` to the caller: [2](#0-1) 

By contrast, the `Occupied` (collision) branch explicitly refunds the *entire* `given_deposit` back to the predecessor: [3](#0-2) 

This asymmetry shows the refund mechanism was clearly intended (it exists for the failure/no-op path) but was omitted for the success path where an overpayment can occur. The contract has no `withdraw`, `owner`, or other mechanism to later recover excess balance held by the contract, so any yoctoNEAR/NEAR sent above the exact `required_deposit` is effectively burned into the contract's balance with no way for the original payer (or anyone else) to reclaim it.

This is directly reachable by any unprivileged NEAR account: `register` is a `#[payable]` public method, callable via an ordinary `FunctionCall` transaction/receipt with an attached deposit chosen by the caller. There is no protocol-level protection against this because attached-deposit handling and refunding is entirely up to the receiving contract's logic (per `docs/RuntimeSpec/Refunds.md`, deposit refunds are only auto-generated by the runtime when the *receipt itself* fails — a successful `FunctionCall` deposits the full amount to the receiver and any refund of unused portions is the contract's own responsibility).

### Impact Explanation
Any ordinary user who overestimates the storage cost (e.g., pads the deposit for safety margin, or miscalculates because `account_id.len()` differs from what they expect) and calls `register` successfully will permanently lose the excess deposit. Since `AddressRegistrar` is part of the ETH-implicit account infrastructure shipped in-repo (`runtime/near-wallet-contract`), and is expected to be deployed and used by ordinary/relayer-driven wallet-contract flows, this is a genuine, permanent loss-of-funds bug for end users, not a hypothetical third-party dApp issue.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: callers commonly attach a deposit that is a round number or a conservative upper bound rather than computing the exact storage byte cost client-side, especially since the exact cost depends on `account_id.len()` which the caller must replicate precisely to avoid under/over-payment. Any deposit strictly greater than the exact required amount triggers the bug on every successful (non-colliding) registration.

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute `excess = given_deposit.saturating_sub(required_deposit)` and, if non-zero, issue a promise transfer of `excess` back to `env::predecessor_account_id()`, mirroring the refund already performed in the `Entry::Occupied` branch.

### Proof of Concept
1. Compute `required_deposit` for a target `account_id` off-chain (equal to `storage_byte_cost * (20 + account_id.len())`).
2. Call `register(account_id)` attaching `given_deposit = required_deposit + X` (any `X > 0`), from an account not previously colliding on that address.
3. Registration succeeds (`Entry::Vacant` branch executes, returns `Some(address)`), and the caller's account balance is now permanently reduced by `required_deposit + X`, while the contract account absorbs the entire deposit with no code path to ever return `X` to the caller.
