### Title
Cache-key granularity in `PackObjectsHookWithSidechannel` allows unprivileged clients to force repeated expensive `git-pack-objects` invocations at negligible per-request cost - ([File: internal/gitaly/service/hook/pack_objects.go])

### Summary
The `packObjectsHook` handler caches the output of expensive `git-pack-objects` invocations keyed by a hash of the repository, RPC `Args`, `GitProtocol`, and the buffered stdin (the "wants"/"haves" list). [1](#0-0)  This is architecturally the same bug class as the reported oracle DoS: a cheap, attacker-controlled input variation (varying `Args`/stdin slightly) causes the expensive backend operation (spawning `git-pack-objects`, an O(repository-size) CPU/IO operation) to be recomputed on every request instead of being amortized by the cache, while each such request is inexpensive for the attacker to issue (an ordinary fetch/clone RPC over SSH or SmartHTTP).

### Finding Description
`computeCacheKey` builds the cache key from the exact `Args` and stdin bytes sent by the client. [2](#0-1)  The design doc for this cache explicitly documents that "requests with slightly different args" or different negotiated `want`/`have` lines are treated as distinct cache keys and will not hit the cache, each triggering a fresh, expensive `git-pack-objects` run. [3](#0-2)  An authenticated but otherwise ordinary/unprivileged client performing `git fetch`/`git clone` controls the exact `want`/`have` negotiation lines sent to the server, and can trivially perturb them (e.g., add or reorder a benign `have` line, tweak client capability flags) to defeat the cache on every single request while still requesting substantially the same object set, forcing full pack generation each time. This mirrors the reported oracle bug: the attacker's per-request cost is small (a shallow/varied fetch negotiation) whereas the triggered backend cost is large (packing the requested object graph), and the mechanism intended to absorb repeated cheap requests (the pack-objects cache, analogous to the "fixed minimum fee" mitigation) can be bypassed by minor field manipulation.

### Impact Explanation
Because the cache key is derived from the literal client-supplied `Args`/stdin rather than a normalized/canonicalized representation of the requested object set, an attacker can force disproportionate CPU/IO load on the Gitaly node per request at minimal cost to themselves, degrading service for other repositories and RPCs on the same node — a DoS on the RPC handler's resource limits, directly analogous to the reported oracle-fee-bypass DoS ("Medium" impact class in the source report: delaying processing for other legitimate clients).

### Likelihood Explanation
Likelihood is high for any client with fetch/clone access to a repository (not necessarily privileged): the negotiation payload sent to `git-pack-objects` via `PostUploadPackWithSidechannel`/`SSHUploadPackWithSidechannel` is fully client-controlled, and no normalization of this input is performed before hashing it into the cache key, so evading the cache requires no special access, only trivial protocol-level variation between repeated fetches.

### Recommendation
- Normalize/canonicalize the negotiated inputs (e.g., sort and deduplicate `want`/`have` OIDs, strip inconsequential capability flags) before computing the cache key so that semantically-equivalent requests collapse to the same key.
- Apply per-client (per-IP/per-user) rate limiting or a minimum-interval throttle on cache-miss `git-pack-objects` invocations in `runPackObjectsLimited`, independent of the exact cache key, so that an attacker cannot force unlimited full-cost pack generations merely by varying request payloads.
- Consider bounding the number of concurrent/total cache-miss pack-objects generations per identity within a time window, consistent with the concurrency-limiter/backpressure mechanisms already used elsewhere in Gitaly (`internal/limiter/concurrency_limiter.go`).

### Proof of Concept
1. As any client with fetch access to a repository, repeatedly issue `git fetch`/upload-pack requests to the same repository, each time slightly varying the negotiation payload (e.g., alternate `have` lines, toggle a capability such as `--progress`/`--delta-base-offset`), as demonstrated by the cache-miss behavior for "requests with slightly different args" and "requests with different protocols" in `testServerPackObjectsHookUsesCache`. [4](#0-3) 
2. Each such request bypasses the pack-objects cache (`created == true` on every call) and triggers a fresh `git-pack-objects` subprocess via `runPackObjects`/`runPackObjectsLimited`. [5](#0-4) 
3. Repeating this at scale across many connections/IPs consumes disproportionate CPU/IO on the Gitaly node relative to the attacker's negligible cost per request, delaying legitimate RPCs — the same cost-asymmetry pattern described in the source report.

**Note:** I was unable to inspect `runPackObjectsLimited` and `internal/gitaly/service/hook/server.go` in full (tool access ended before those reads completed), so I cannot confirm whether an existing per-IP concurrency limiter in `runPackObjectsLimited` already partially mitigates concurrent abuse from a single IP. If it exists, it would only limit concurrency, not the repeated-cache-miss cost-amplification described above, since the limiter is unrelated to cache-key normalization. A Devin session with full file access should verify `runPackObjectsLimited`'s exact throttling logic before implementing the recommended fix.

// computeCacheKey returns the cache key used for caching pack-objects. A cache key is made up of
// both the requested objects and essential parameters that could impact the content of the
// generated packfile. Including any insignificant information could result in a lower cache hit rate.
func (s *server) computeCacheKey(ctx context.Context, req *gitalypb.PackObjectsHookWithSidechannelRequest, stdinReader io.Reader) (string, io.ReadCloser, error) {
	cacheHash := sha256.New()

	repository := req.GetRepository()
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		// The cache uses the requests as the keys. As the request's repository in the RPC handler has been rewritten
		// to point to the transaction's repository, the handler sees each request as different even if they point to
		// the same repository. Restore the original request to ensure identical requests get the same key.
		repository = tx.OriginalRepository(req.GetRepository())
	}

	cacheKeyPrefix, err := protojson.Marshal(&gitalypb.PackObjectsHookWithSidechannelRequest{
		Repository:  repository,
		Args:        req.GetArgs(),
		GitProtocol: req.GetGitProtocol(),
	})
	if err != nil {
		return "", nil, err
	}
	if _, err := cacheHash.Write(cacheKeyPrefix); err != nil {
		return "", nil, err
	}
	stdin, err := bufferStdin(stdinReader, cacheHash)
	if err != nil {
		return "", nil, err
	}
	cacheKey := hex.EncodeToString(cacheHash.Sum(nil))
	return cacheKey, stdin, nil
}

func (s *server) runPackObjects(
	ctx context.Context,
	w io.Writer,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	// We want to keep the context for logging, but we want to block all its
	// cancellation signals (deadline, cancel etc.). This is because of
	// the following scenario. Imagine client1 calls PackObjectsHook and
	// causes runPackObjects to run in a goroutine. Now suppose that client2
	// calls PackObjectsHook with the same arguments and stdin, so it joins
	// client1 in waiting for this goroutine. Now client1 hangs up before the
	// runPackObjects goroutine is done.
	//
	// If the cancellation of client1 propagated into the runPackObjects
	// goroutine this would affect client2. We don't want that. So to prevent
	// that, we suppress the cancellation of the originating context.
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	return s.runPackObjectsFn(ctx, s.gitCmdFactory, w, req, args, stdin, key)
}
