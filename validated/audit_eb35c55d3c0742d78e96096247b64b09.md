### Title
Unchecked long addition/overflow in `ExchangeProcessor.exchangeToSupply` used for on-chain TRX/token exchange calculations - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The Loopring report flags `MulDivGadget` for performing a multiply/divide fee computation without validating the bit-size of its operands or the bounded-ness of the intermediate product, which lets an attacker cause a silent overflow and manipulate the resulting fee/quantity. The closest reachable analog in java-tron is `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java), the default (non-hardened) arithmetic engine behind `ExchangeCapsule.transaction`, which is invoked directly from unprivileged, broadcastable transactions (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`).

### Finding Description
`ExchangeCapsule.transaction()` selects between two arithmetic engines depending on the `allowHardenExchangeCalculation` dynamic parameter: [1](#0-0) 

When hardened mode is not enabled (its default/legacy behavior), the pool math is delegated to `ExchangeProcessor`, whose core routine computes: [2](#0-1) 

Unlike every other balance mutation in the exchange actuators (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`), which consistently route additions/subtractions/multiplications through `addExact`/`subtractExact`/`multiplyExact` (checked arithmetic that throws `ArithmeticException` on overflow) via `AbstractActuator`/`AbstractExchangeActuator`: [3](#0-2) [4](#0-3) 

`exchangeToSupply` performs the raw, unchecked expression `long newBalance = balance + quant;` with no bit-size/bounds validation on `balance` or `quant`, and then derives the traded amount via a floating-point `pow()` computation that is finally narrowed with `(long) issuedSupply`. There is no assertion that the inputs stay within a safe range (analogous to the missing `numBitsValue`/`numBitsNumerator`/`numBitsDenominator` checks in `MulDivGadget`), and no bound on the final product/quotient (analogous to the missing "product is bounded" assertion). This is exactly the class of defect Trail of Bits flagged: unchecked arithmetic feeding a value that determines how much of a counter-asset a user receives from/pays into a liquidity pool.

The existence of `SafeExchangeProcessor` (chainbase/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java), which reimplements the same math using `BigDecimal` and `StrictMathWrapper.addExact`, and of the `allowHardenExchangeCalculation` toggle plus dedicated regression tests (`ExchangeProcessorTest.testHardenedOverflowDetection`, `testSafeProcessorAddExactOverflowThrows`) confirms this was recognized internally as an overflow-prone code path that needed hardening — but the legacy `ExchangeProcessor` path remains in the codebase and is used whenever the chain parameter is not toggled on.

### Impact Explanation
If `balance + quant` overflows a `long` (wraps to a negative value) or the floating point `pow` computation loses precision at extreme magnitudes, `exchangeToSupply`/`exchangeFromSupply` can produce an incorrect `buyTokenQuant`. Because this quantity directly drives:
- how much of the counter-token an attacker receives from `ExchangeTransactionActuator.execute` (`ret.setExchangeReceivedAmount`), and
- how the pool's `firstTokenBalance`/`secondTokenBalance` are subsequently updated,

an attacker who can drive the computation into the overflow/precision-loss region could extract more tokens than they are entitled to (theft from the liquidity pool / other exchange participants) or desynchronize pool accounting, which over repeated transactions could allow draining the exchange pool — a concrete unauthorized asset transfer. This mirrors the Loopring report's exploit scenario where an overflowing multiply/divide in a fee-relevant calculation lets an attacker extract more value than intended.

### Likelihood Explanation
Reachability is high: any unprivileged account can call `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` through a normal signed transaction, and the vulnerable code path (`ExchangeProcessor`) is the default unless the committee has separately enabled `allowHardenExchangeCalculation`. However, actually forcing an overflow requires pool balances/quant near `Long.MAX_VALUE`, and other validation code (`getExchangeBalanceLimit` checks, `addExact` checks in the actuators' balance-adjustment code) constrains how large `firstTokenBalance`/`secondTokenBalance`/`tokenQuant` can practically get before those checked-arithmetic guards elsewhere throw first. This somewhat limits — but does not fully eliminate — the practical likelihood, since it depends on the specific bounds enforced by `dynamicStore.getExchangeBalanceLimit()` versus the values actually passed into `exchangeToSupply`/`exchangeFromSupply` before any checked-arithmetic guard intercepts them.

### Recommendation
- Make hardened, `BigDecimal`/checked-arithmetic exchange math (`SafeExchangeProcessor`) the mandatory path, removing the legacy unchecked `ExchangeProcessor`, or unconditionally validate all operands' bit sizes/bounds before performing the `balance + quant` and subsequent `pow` computations in `ExchangeProcessor`.
- Add an explicit bounded-ness assertion on the final `buyTokenQuant`/`issuedSupply` result before it is used to mutate account balances or pool balances, so silent overflow/precision loss cannot propagate into consensus-critical state.
- Extend regression tests to fuzz `ExchangeProcessor` (non-hardened) directly at pool-balance boundaries to confirm no exploitable rounding/overflow discrepancy versus `SafeExchangeProcessor`.

### Proof of Concept
Not independently reproduced against a running node within this investigation; a full PoC would require a background Devin agent to stand up a test network, create/inject into an `Exchange` pool such that `firstTokenBalance`/`secondTokenBalance` approach the practical limits allowed by `getExchangeBalanceLimit()`, disable `allowHardenExchangeCalculation`, and drive repeated `ExchangeTransactionContract` calls to attempt to trigger the unchecked-addition/overflow path in `ExchangeProcessor.exchangeToSupply`, comparing observed `anotherTokenQuant` against the `SafeExchangeProcessor`/`BigInteger` reference computation used elsewhere in the same actuators.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }
