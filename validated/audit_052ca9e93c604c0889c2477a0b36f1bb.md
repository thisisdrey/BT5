### Title
Cross-StackerDB Signature Replay Due to Missing Contract Binding in `SlotMetadata::auth_digest` - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` — the digest signed by a StackerDB slot owner and verified on chunk write/relay — only commits to `(slot_id, slot_version, data_hash)`. It never binds the signature to the specific StackerDB contract (`QualifiedContractIdentifier`) the chunk is destined for. Because every `.signers-0-{message_id}` contract (and every `.signers-1-{message_id}` contract) for a given signer set derives its slot assignment from the *same* underlying page (`stackerdb-get-signer-slots-page`), a given signer address is assigned the identical `slot_id` across all message-type StackerDB contracts in that signer set. A signature that authenticates a chunk for one contract is therefore also a valid signature for the same `(slot_id, slot_version, data)` tuple in every sibling contract, letting an unprivileged relayer/observer replay a legitimately observed chunk into a StackerDB it was never intended for.

### Finding Description
`SlotMetadata::auth_digest` computes: [1](#0-0) 
which hashes only `slot_id`, `slot_version`, and `data_hash`. `verify()` recovers the public key from this digest and checks it against the expected slot owner address: [2](#0-1) 
No contract identifier, chunk-inv namespace, or other domain separator is included.

On the write path (`stackslib/src/net/api/poststackerdbchunk.rs`) and the P2P relay/validation path (`PeerNetwork::handle_unsolicited_StackerDBPushChunk` / `StackerDBs::validate_received_chunk`), the contract is used only to look up the *expected signer address* for the given `slot_id` in that specific DB — it is never folded into the signature check itself: [3](#0-2) 

Crucially, slot assignment is identical across sibling contracts. Each `.signers-0-{message_id}` contract calls the same read-only function to get its slot list: [4](#0-3) 
which is backed by a single stored list per signer-set parity in `.signers`: [5](#0-4) 
and this is verified by the test asserting that *every* message-id contract in the same signer set returns the exact same slot list (same address → same slot_id): [6](#0-5) 

Consequently, if a given signer address owns `slot_id = k` in contract `.signers-0-1` (e.g. `BlockResponse` messages), it also owns `slot_id = k` in `.signers-0-2`, `.signers-0-3`, etc. (other message types) for the same signer set. A chunk signed by that signer for one of those contracts recovers to the identical valid signer address in all of them, because `auth_digest` never encodes which contract the signature is scoped to.

### Impact Explanation
This breaks the equality the report's bug class targets: "authenticated for X" vs. "accepted/stored as authenticated for Y." An unprivileged network participant who observes a validly signed `StackerDBChunkData` posted/gossiped for one signer StackerDB (any of the several `.signers-0-*`/`.signers-1-*` contracts sharing that signer's slot) can resubmit the exact same wire message to a *different sibling contract* via `POST /v2/stackerdb/.../chunks` or via unsolicited `StackerDBPushChunk` gossip. The target node's per-DB validation (`validate_received_chunk` / `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`) will accept it as authentically signed by that signer for that slot — since the digest only checks `(slot_id, slot_version, data_hash)`, and the signer/slot mapping happens to coincide — even though the signer never authorized data for that particular message-type DB. This is an unauthorized write of forged/misplaced but "validly signed" data into a StackerDB namespace the signer did not intend, and it will legitimately propagate across the network (peers replicate/relay it as valid, matching the "network-wide propagation of forged data" / "unauthenticated write to StackerDB" impact bucket), because every downstream node performs the same context-blind verification.

The practical damage depends on what a receiver does with cross-context bytes: at minimum it lets an attacker force acceptance of a chunk with attacker-controlled *timing/version* into an unintended DB slot (denial/confusion for downstream consumers parsing `SignerMessage` from the wrong DB, and it consumes that signer's slot version/write budget in a DB they never wrote to, potentially causing `TooManySlotWrites`/`StaleChunk` griefing against the legitimate signer for that contract). This is a genuine, remotely triggerable, unprivileged fault reachable purely by relaying/replaying already-broadcast messages — no secret key or admin role required.

### Likelihood Explanation
High feasibility: the attacker does not need to forge anything — they only need to capture a message that was already broadcast in the normal signer-messaging protocol (StackerDB chunk pushes are relayed peer-to-peer and are, by design, publicly observable) and resend it to a sibling contract endpoint. Both the HTTP POST endpoint and the P2P unsolicited-push path perform identical, contract-blind signature verification, so the replay works against either interface without any race condition or timing constraint beyond the target slot's version/write-frequency gating.

### Recommendation
Bind the signature to the specific StackerDB by including the `QualifiedContractIdentifier` (or a stable hash of it) in `SlotMetadata::auth_digest()`, and require both the signer and verifier to always supply the destination contract identifier when signing/verifying a chunk. Alternatively, add an explicit domain-separation tag encoding the contract into the digest, and reject any writes where the recomputed digest doesn't match the target DB.

### Proof of Concept
1. Signer `S` owns `slot_id = k` in both `.signers-0-1` (contract A, message type `BlockResponse`) and `.signers-0-2` (contract B, message type e.g. `Transactions`) for the current signer set, per `signers-0-xxx.clar`'s shared slot page.
2. `S` legitimately signs and pushes `StackerDBChunkData { slot_id: k, slot_version: v, data: D }` to contract A; this chunk is observed on the wire by an attacker via normal StackerDB gossip/relay.
3. Attacker resubmits the identical `StackerDBChunkData` (unchanged `slot_id`, `slot_version`, `sig`, `data`) to contract B, either via `POST /v2/stackerdb/<contract-B>/chunks` or via an unsolicited `StackerDBPushChunk` P2P message naming contract B.
4. `StackerDBs::validate_received_chunk` for contract B calls `get_slot_signer(contract_B, k)` → returns `S`'s address; `slot_metadata.verify(&S_addr)` succeeds because `auth_digest` never referenced contract A vs B. [3](#0-2) 
5. As long as `v` satisfies contract B's own `slot_version`/`max_writes` gating (`stackslib/src/net/stackerdb/db.rs::try_replace_chunk`), the chunk is stored/relayed in contract B as if `S` had authored it there, even though `S` never wrote to contract B with that content.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

fn signers_db_get_slots() {
    let stacker_1 = TestStacker::from_seed(&[3, 4]);
    let stacker_2 = TestStacker::from_seed(&[5, 6]);

    let (mut peer, test_signers, latest_block_id, _) = prepare_signers_test(
        function_name!(),
        vec![],

    let mut expected_signers: Vec<_> =
        [&stacker_1.signer_private_key, &stacker_2.signer_private_key]
            .iter()
            .map(|sk| {
                let pk = Secp256k1PublicKey::from_private(sk);
                let pk_bytes = pk.to_bytes_compressed();
                let signer_addr = StacksAddress::p2pkh(false, &pk);
                let stackerdb_entry = TupleData::from_data(vec![
                    (
                        ClarityName::from_literal("signer"),
                        PrincipalData::from(signer_addr).into(),
                    ),
                    (ClarityName::from_literal("num-slots"), Value::UInt(1)),
                ])
                .unwrap();
                (pk_bytes, stackerdb_entry)
            })
            .collect();

    // should be sorted by the pk bytes
    expected_signers.sort_by_key(|x| x.0.clone());
    let expected_stackerdb_slots = Value::cons_list_unsanitized(
        expected_signers
            .into_iter()
            .map(|(_pk, entry)| Value::from(entry))
            .collect(),
    )
    .unwrap();

    for signer_set in 0..2 {
        for message_id in 0..SIGNER_SLOTS_PER_USER {
            let contract_name =
                ContractName::try_from(format!("signers-{}-{}", &signer_set, &message_id)).unwrap();
            let signers = readonly_call(
                &mut peer,
                &latest_block_id,
                contract_name.clone(),
                ClarityName::from_literal("stackerdb-get-signer-slots"),
                vec![],
            )
            .expect_result_ok()
            .unwrap();

            debug!("Check .{}", contract_name);
            if signer_set == 0 {
                assert_eq!(signers.expect_list().unwrap(), vec![]);
            } else {
                assert_eq!(signers, expected_stackerdb_slots);
            }
        }
