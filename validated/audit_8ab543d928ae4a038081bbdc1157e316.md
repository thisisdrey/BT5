### No vulnerability found for this question.

Investigation summary: `commandDescription.args()` unconditionally inserts a literal `"--"` separator before `PostSepArgs` whenever `len(postSepArgs) > 0`, independent of the `scNoEndOfOptions` flag [1](#0-0) . The `scNoEndOfOptions` flag only controls whether the newer `--end-of-options` Git option is appended after flags [2](#0-1) ; it says nothing about the traditional `--` separator, which `git-blame(1)`, `git-show(1)`, and `git-check-attr(1)` all honor to stop option parsing before positional path arguments.

`RawBlame` puts the user-controlled path into `PostSepArgs` and the revision into `Args`, exactly per the documented convention in `Command`'s field comments (`Args` must not start with `-`; `PostSepArgs` is for arbitrary user input like paths) [3](#0-2) . In `raw_blame.go`, `revision` goes to `Args` (validated by `validatePositionalArg`/`git.ValidateRevision`) and `path` goes to `PostSepArgs`, preceded by the literal `--` before reaching `git-blame` [4](#0-3) . This is confirmed by the existing test asserting a dash-prefixed `Revision` is rejected via `validatePositionalArg`, while dash-prefixed `Path` values are accepted and safely passed after `--` [5](#0-4) . The same pattern (`Args` for revision, `PostSepArgs` for path with `--` prefix) is used elsewhere, e.g. `ls-tree` in `listLastCommitsForTree` [6](#0-5)  and `git-archive` [7](#0-6) .

The premise that "blame ... doesn't honor `--`" is incorrect — `git-blame(1)`'s own synopsis is `git blame [options] [rev-opts] [rev] [--] file`, and the code path never skips validation of `Args` (revisions), nor does it need to validate `PostSepArgs` since the `--` separator is Git's own guaranteed mechanism for disambiguating options from paths, independent of `--end-of-options` support. No code path was found that builds `PostSepArgs` from unsanitized input while skipping the `--` insertion, and `RawBlameRequest.Path` additionally goes through `filepath.IsLocal` validation before reaching this point [8](#0-7) .

```go
// supportsEndOfOptions indicates whether a command can handle the
// `--end-of-options` option.
func (c commandDescription) supportsEndOfOptions() bool {
	return c.flags&scNoEndOfOptions == 0
}

// args validates the given flags and arguments and, if valid, returns the complete command line.
func (c commandDescription) args(flags []Option, args []string, postSepArgs []string) ([]string, error) {
	var commandArgs []string

	for _, o := range flags {
		args, err := o.OptionArgs()
		if err != nil {
			return nil, err
		}
		commandArgs = append(commandArgs, args...)
	}

	if c.supportsEndOfOptions() {
		commandArgs = append(commandArgs, "--end-of-options")
	}
```
