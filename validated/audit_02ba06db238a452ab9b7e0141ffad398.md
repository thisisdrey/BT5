Audit Report

## Title
Missing slippage protection (`amount_out_min = None`) in `swap_and_burn` allows spot-price manipulation of the AssetConversion pool when converting tip/registration fee assets to Ether - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::swap_and_burn`, invoked from the public, unprivileged `add_tip` and `register_token` extrinsics via `swap_fee_asset_and_burn`, calls `T::Swap::swap_exact_tokens_for_tokens` with the minimum-output parameter hard-coded to `None`, meaning the AMM spot price at execution time is trusted unconditionally, with no bound comparison to `quote_price_exact_tokens_for_tokens` or any caller-supplied floor. The resulting `ether_gained` — real Ether actually withdrawn from the `pallet-asset-conversion` pool reserves — is burned via `burn_for_teleport` and forwarded as the authoritative `amount` in the `AddTip`/`RegisterToken` XCM `Transact` call to `EthereumSystem` on BridgeHub, so any attacker who skews the pool's reserves immediately before calling `add_tip`/`register_token` (e.g., via `pallet_utility::batch_all`) can extract a disproportionate amount of Ether from AMM liquidity providers for a fixed `tip_amount`/`fee_amount` input, converting stolen pool liquidity into an inflated recorded relayer tip/registration fee.

## Finding Description
`add_tip` (call index 2) and `register_token` (call index 1) are both public, unprivileged, signed-origin-callable extrinsics that route into `swap_fee_asset_and_burn`, which for any non-Ether fee asset calls `swap_and_burn`: [1](#0-0) [2](#0-1) 

The critical unprotected call is: [3](#0-2) 

`pallet-asset-conversion`'s `Swap` trait explicitly supports an `amount_out_min: Option<Balance>` bound designed for exactly this purpose (`swap_exact_tokens_for_tokens... If an amount_out_min is specified, it will return an error if it is unable to acquire the amount desired`), and the pallet exposes `quote_price_exact_tokens_for_tokens` as a reference price function: [4](#0-3) [5](#0-4) . `swap_and_burn` never calls this quote function or supplies any bound — it explicitly passes `None`, so the swap executes purely against whatever pool reserves exist at that instant, with no delta/TWAP check.

Because `who` (the caller) both funds the swap input and receives the swap output (`send_to: who`) before that same output is burned from `origin`, the attacker can, within one atomic transaction (e.g., `pallet_utility::batch_all`): (1) execute a preceding swap that skews the `(fee_asset, ether)` pool reserves, (2) call `add_tip`/`register_token` with a fixed `tip_amount`/fee amount, causing the AMM to return an inflated `ether_gained` computed off the skewed reserves, and (3) have that inflated (but real, pool-sourced) Ether amount burned via `burn_for_teleport::<T::AssetTransactor>` and forwarded as the trusted `amount` field in the `AddTip`/`RegisterToken` `Transact` call to `EthereumSystem`. No existing guard in `swap_and_burn`, `swap_fee_asset_and_burn`, `add_tip`, or `register_token` checks this value against a reference price or caller-supplied minimum.

## Impact Explanation
This is a genuine "public underpriced work"/value-extraction vector: because `ether_gained` is Ether *actually withdrawn from the AMM pool's real reserves* (not minted from nothing), the manipulation drains value from `pallet-asset-conversion` liquidity providers and converts it into an inflated Ether amount that is burned and reported to `EthereumSystem` as the tip/registration-fee credit for relayer rewards — a real transfer of value from an unrelated pool of LPs into the bridge's reward accounting, controlled entirely by an unprivileged caller's chosen `tip_amount` and manipulation size. This matches the impact gate's "public underpriced work that degrades... bridge processing" category, since the relayer reward/registration-fee amount forwarded to Ethereum no longer reflects the fair economic cost paid by the caller, and LPs bear an uncompensated loss.

## Likelihood Explanation
The attack requires no privileged role, validator collusion, or multi-block timing — it is executable entirely within a single atomic transaction by any signed account using ordinary `pallet_utility::batch_all` to sequence a pool-skewing swap immediately before `add_tip`/`register_token`, satisfying the "unprivileged attacker, public entrypoint" requirement. Feasibility depends on pool liquidity depth (shallower pools are more exploitable) and on `add_tip`/`register_token` being wired to a live, non-trivial `(fee_asset, ether)` `pallet-asset-conversion` pool in the deployed runtime configuration, which I could not fully confirm from the indexed files (no BridgeHub runtime `Config` wiring for `T::Swap` was located in this pass) — this is a configuration-dependent precondition that should be verified in a full-repo session, but the vulnerable code path itself (`swap_and_burn`'s hard-coded `None`) is confirmed present and unconditionally reachable from public extrinsics.

## Recommendation
Never hard-code `None` for `amount_out_min` in `swap_and_burn` when the swap's output feeds settlement/reward accounting. Compute a reference price via `T::Swap`'s companion `QuotePrice::quote_price_exact_tokens_for_tokens` (or an analogous quote mechanism exposed through the `Swap` trait/config) immediately before the swap, and pass a bounded `amount_out_min` (e.g., quoted price minus an allowed slippage tolerance) instead of `None`, or require the caller to supply an explicit `min_ether_out` parameter on `add_tip`/`register_token` that is enforced by the swap call.

## Proof of Concept
1. Deploy/identify a `pallet-asset-conversion` pool for `(fee_asset_location, ether_location)` with limited liquidity relative to attacker capital.
2. Attacker constructs a single `pallet_utility::batch_all` extrinsic containing:
   - a `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` call trading Ether into the pool for `fee_asset` (raising the pool's Ether-per-`fee_asset` price), followed by
   - `snowbridge_pallet_system_frontend::add_tip(message_id, fee_asset_amount)`.
3. Inside `add_tip` → `swap_fee_asset_and_burn` → `swap_and_burn`, the exact-input swap executes against the now-skewed reserves with `amount_out_min = None`, at `bridges/snowbridge/pallets/system-frontend/src/lib.rs:301-308`, returning an `ether_gained` larger than the fair-price value of `fee_asset_amount`.
4. `ether_gained` is burned via `burn_for_teleport` and forwarded in the `AddTip` `Transact` call to BridgeHub's `EthereumSystem`, recording an inflated tip credit relative to the true economic cost paid, at the expense of the pool's liquidity providers.
5. A unit/integration test in `pallet-snowbridge-system-frontend`'s test suite (extending existing mocks in `bridges/snowbridge/pallets/system-frontend/src/mock.rs`/`tests.rs`) can assert that `ether_gained` returned by `swap_and_burn` diverges from `quote_price_exact_tokens_for_tokens` computed on unmanipulated reserves by more than a reasonable tolerance when a manipulating swap is injected beforehand, demonstrating the missing bound.
