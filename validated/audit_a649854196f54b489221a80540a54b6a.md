### Title
Unbounded Repository Write-Lock Renewal via Repeated Same-Phase Votes Causes Perpetual Write-Lock DoS - (File: internal/praefect/transactions/manager.go)

### Summary
Praefect's serialized-writes feature grants a client-controlled reference-transaction an exclusive, cluster-wide PostgreSQL-backed lock on a repository at `PREPARING_PHASE`, and then indefinitely extends that lock's expiry every time a `PREPARED_PHASE` (or `COMMITTED_PHASE`) vote is received for the same transaction, with no cap on the number of renewals or on how long a single transaction may hold the lock.

### Finding Description
`lockRepoForTransaction` acquires the per-repository write lock on `PREPARING_PHASE` via `WriteLockManager.Lock`, and on every subsequent `PREPARED_PHASE`/`COMMITTED_PHASE` vote calls `lock.Renew(ctx)`, which pushes `expired_at` forward by another `renewInterval` (20s) in the `repository_reference_write_locks` table each time: [1](#0-0) 

The underlying SQL simply extends the deadline unconditionally as long as the caller still holds `holder_txn_id`, with no bound on total renewals or elapsed lock-hold time: [2](#0-1) 

Each `VoteTransaction` RPC call drives one vote per node into `transaction.vote()`, which creates a new subtransaction each time all voters have completed the prior one, and there is no upper bound on the number of subtransactions/votes a single registered transaction can process before it is finally committed or canceled: [3](#0-2) [4](#0-3) 

Because a reference-transaction hook fires at `preparing`/`prepared`/`committed` stages driven by Git during an ordinary push, and Git can call the hook multiple times per push (multiple ref updates / batches), a party influencing the hook invocation cadence for a long-running or crafted push can keep casting `PREPARED_PHASE` votes against the same `transactionID` before ever reaching `COMMITTED_PHASE`. Each such vote re-invokes `lockRepoForTransaction`, extends `expired_at`, and the write lock for that specific repository is never released as long as the caller keeps voting `PREPARED_PHASE` faster than the 20-second interval expires. The lock is only released on failure or on `COMMITTED_PHASE`/`StopTransaction`/cancellation: [5](#0-4) 

This mirrors the reported bug class exactly: a lock/timer intended to be transient is perpetually reset by repeated legitimate-looking actions from an ordinary actor, preventing any other party (here, every other writer to that repository) from ever acquiring the resource.

### Impact Explanation
Since the repository write lock is exclusive per `(virtualStorage, relativePath)` and blocks all other `PREPARING_PHASE` acquisitions cluster-wide across all Praefect instances, an attacker who can sustain repeated `PREPARED_PHASE` votes for one transaction without ever committing can hold the lock indefinitely, causing a denial-of-service against all subsequent write RPCs (pushes, branch/tag updates, MRs, etc.) targeting that repository. This is a DoS of a Praefect RPC handler resource (the shared write-lock table row), reachable from an ordinary user's push through the standard reference-transaction hook path documented in `doc/serialized_writes.md`.

### Likelihood Explanation
Likelihood is moderate: it requires the ability to prolong the hook's `prepared` phase (or keep re-voting `PREPARED_PHASE`) without ever reaching `COMMITTED_PHASE`/failing, e.g., a hung or maliciously slow client feeding ref updates in many small batches, or a compromised/misbehaving Gitaly node repeatedly re-voting. There's no explicit safeguard in `voteTransaction`/`lockRepoForTransaction` limiting total renewals or total hold time, so if the attack surface allows sustained `PREPARED_PHASE` votes on one `transactionID`, the lock hold is unbounded by design.

### Recommendation
Bound the total time or number of renewals a single transaction may hold the write lock (e.g., a maximum lock lifetime independent of individual renew calls), and/or cap the number of subtransactions/`PREPARED_PHASE` votes permitted per transaction before forcing a fail/unlock, so that a stalled or repeatedly-voting client cannot indefinitely extend `expired_at` in `repository_reference_write_locks`.

### Proof of Concept
Not executed; based on static analysis of `internal/praefect/transactions/manager.go`, `internal/praefect/datastore/lock_manager.go`, and `internal/praefect/transactions/transaction.go`. Conceptually: register a transaction, vote `PREPARING_PHASE` to acquire the lock, then repeatedly vote `PREPARED_PHASE` (each within the 20s `renewInterval`) without ever voting `COMMITTED_PHASE`; `test_write_serialization_test.go`'s `TestPraefectWriteSerialization_HangAfterPrepared` demonstrates the mechanics of the lock/renew/expire lifecycle that this analog exploits by never letting the lock expire: [6](#0-5)

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}

func (mgr *Manager) unlockRepoForTransaction(ctx context.Context, transactionID uint64, returnedErr error, phase gitalypb.VoteTransactionRequest_Phase) {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return
	}

	// Decide whether this call releases the write lock. The lock spans all the
	// phases of one transaction and is only released when either the vote
	// failed (so callers can't advance to the next phase) or the committed
	// phase completes. Phases outside the reference transaction hook
	// lifecycle (e.g. SYNCHRONIZED_PHASE) never acquired a lock.
	var shouldUnlock bool
	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE:
		shouldUnlock = returnedErr != nil
	case gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		shouldUnlock = true
	default:
		return
	}

	if !shouldUnlock {
		return
	}

	mgr.releaseRepoLockOnPhase(transactionID, phase.String())
}

// renew extends the expiry of the write lock held by txnID by another renewInterval.
// It returns an error if the lock is not currently held by txnID.
func (r *RepoReferenceWriteLockManager) renew(ctx context.Context, virtualStorage string, relativePath string, txnID uint64) error {
	query := `
UPDATE repository_reference_write_locks as locks
SET  expired_at = (NOW() + $3::interval)
WHERE locks.lock_id = $1 AND holder_txn_id = $2
RETURNING expired_at;
`
	lockID := repoLockID(virtualStorage, relativePath)
	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "renew").Observe(time.Since(start).Seconds())
	if err != nil {
		return fmt.Errorf("renew repo reference write lock (executing query): %s, %w", lockID, err)
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		return nil
	}
	if err := rows.Err(); err != nil {
		return fmt.Errorf("renew repo reference write lock (iterating rows): %s, %w", lockID, err)
	}
	return fmt.Errorf("renew repo reference write lock (no rows): %s", lockID)
}

// getOrCreateSubtransaction gets an ongoing subtransaction on which the given
// node hasn't yet voted on or creates a new one if the node has succeeded on
// all subtransactions. In case the node has failed on any of the
// subtransactions, an error will be returned.
func (t *transaction) getOrCreateSubtransaction(node string) (*subtransaction, error) {
	t.lock.Lock()
	defer t.lock.Unlock()

	switch t.state {
	case transactionOpen:
		// expected state, nothing to do
	case transactionCanceled:
		return nil, ErrTransactionCanceled
	case transactionStopped:
		return nil, ErrTransactionStopped
	default:
		return nil, errors.New("invalid transaction state")
	}

	// Check for pending subtransactions on the specified node.
	if subtransactions, err := t.getPendingNodeSubtransactions(node); err != nil {
		return nil, err
	} else if len(subtransactions) != 0 {
		// First pending subtransaction is the next in queue for processing.
		return subtransactions[0], nil
	}

	// If we arrive here, then we know that all the node has voted and
	// reached quorum on all subtransactions. We can thus create a new one.
	subtransaction, err := t.createSubtransaction()
	if err != nil {
		return nil, err
	}

	t.subtransactions = append(t.subtransactions, subtransaction)

	return subtransaction, nil
}

func (t *transaction) vote(ctx context.Context, node string, vote voting.Vote) error {
	subtransaction, err := t.getOrCreateSubtransaction(node)
	if err != nil {
		return err
	}

	if err := subtransaction.vote(node, vote); err != nil {
		return err
	}

	return subtransaction.collectVotes(ctx, node)
}
