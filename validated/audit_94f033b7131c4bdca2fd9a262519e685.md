### Title
Energy metering for `BatchValidateSign`/`ValidateMultiSign` precompiles undercharges the real signature-recovery cost via aliased ABI pointers - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The L1-data-fee report describes a fee model that only bills for one cost component (L2 execution gas) while ignoring the real, dominant cost of the operation (L1 data publishing), letting callers get expensive work done for a price that doesn't reflect the actual resource consumed. The same fee-model/real-cost mismatch class exists in java-tron's `BatchValidateSign` and `ValidateMultiSign` precompiles: `getEnergyForData()` estimates the number of signatures to be verified purely from the raw calldata *length*, assuming a fixed, dense words-per-item layout, while `execute()` actually derives the number of signature/ECDSA-recovery operations from a user-controlled length word reachable through an offset pointer inside the same calldata [1](#0-0) . Because the offset-based extraction lets many array "items" alias the same underlying signature bytes, an attacker can make the real number of `ECDSA`/`ecrecover`-style operations performed by `execute()` far exceed what the length-based formula billed for.

### Finding Description
`BatchValidateSign.getEnergyForData()` computes the number of signatures to charge for strictly from `data.length`, assuming each signature entry consumes a fixed 6 words: [1](#0-0) 

`ValidateMultiSign` follows the identical pattern with 5 words/item: [2](#0-1) 

However, the actual number of signature-recovery operations performed at execution time is not derived from `data.length` at all - it comes from a length word read at an attacker-chosen offset inside the payload, via `extractSigArray`/`extractBytesArray`/`extractBytes32Array`: [3](#0-2) 

Each entry in the signature array is located through its own 32-byte offset word (`words[offset + i + 1]`), and the actual signature bytes read from `data` are determined by that offset, not by a dedicated per-item data slot. This means many different `i` indices can be crafted to point at the *same* underlying 65-byte signature blob, so the attacker only pays the "1 offset word per item" cost while reusing one shared payload for the expensive part of the work (the actual ECDSA public-key recovery in `recoverAddrBySign`): [4](#0-3) 

For `BatchValidateSign`, this aliasing is used to run up to `MAX_SIZE = 16` full elliptic-curve public-key recoveries per call (dispatched to a shared, node-wide thread pool `workers`) while the calldata length only needs to grow by roughly one word per additional recovery instead of the six words the fee formula assumes: [5](#0-4) 

So `getEnergyForData()` bills for a linear function of `data.length` under the assumption of one fixed encoding density, but `execute()`'s real CPU cost (number of secp256k1 recoveries, each comparable in cost to the dedicated `ECRecover` precompile priced at 3000 energy) is driven by a completely different, attacker-controlled quantity. This is the same structural flaw as the L1-data-fee report: the code only accounts for one cost signal (calldata size) and silently ignores the actual dominant cost driver (number/complexity of cryptographic operations actually executed), so the "reimbursement" (energy charged) does not track the real work performed.

The `isValidAbiEncoding()` guard that would reject non-canonical/aliased encodings is gated behind `VMConfig.allowTvmOsaka()` and is only exercised for the newest hard-fork behavior; it is not applied unconditionally to both code paths: [6](#0-5) [7](#0-6) 

### Impact Explanation
Every full node/SR that re-executes the transaction (e.g., during block validation/re-application in `Manager`) must perform the same disproportionate number of expensive ECDSA public-key recoveries that the caller under-paid for in energy. Because energy is the resource-metering unit that is supposed to make execution cost proportional to fee paid, an attacker can craft transactions/contract calls (reachable by any unprivileged account through a plain `CALL`/`STATICCALL` to precompile address `0x...09`) that force disproportionately expensive cryptographic verification work onto every validating node relative to the energy fee actually charged. Repeated or batched invocations of this pattern amplify CPU cost per unit of TRX/energy spent, which is a resource-metering failure that can be used to degrade block-processing throughput across the network - the same "job execution/relayer underpayment leading to systemic harm" impact class described in the source report, mapped onto TVM energy metering and node CPU instead of L1/L2 gas.

### Likelihood Explanation
This is directly reachable by any account with no special privileges: it only requires deploying/calling a contract that invokes the `BatchValidateSign`/`ValidateMultiSign` precompile addresses with hand-crafted ABI-like calldata containing aliased offset pointers. No collusion with a validator or special permission is needed, and the underlying `extractSigArray`/`extractBytesArray` functions perform no sanity check that offsets are distinct/canonical outside the Osaka-only `isValidAbiEncoding` gate.

### Recommendation
Make the energy cost strictly proportional to the actual number of recovery operations performed (`signatures.length`/`cnt` as computed inside `execute()`), rather than inferring it from `data.length` under an assumed dense encoding. Additionally, always validate canonical/non-aliased ABI encoding (making `isValidAbiEncoding()`-style checks unconditional, not just under `allowTvmOsaka()`), and cap/verify offsets in `extractSigArray`/`extractBytesArray`/`extractBytes32Array` so multiple array items cannot reference overlapping/identical byte ranges to cheat the size-based cost estimate.

### Proof of Concept
1. Craft calldata for `BatchValidateSign` (address `0x...09`) with the 5-word header (`hash`, offset-to-sigArray, offset-to-addrArray, ...).
2. In the signature-array section, set the length word to `MAX_SIZE = 16`, followed by 16 offset words that all point to the *same* single 65-byte signature blob placed once in the payload.
3. In the address-array section, provide 16 (necessarily distinct) 32-byte address words (required since `extractBytes32Array` reads them inline).
4. Compute the resulting `data.length`; verify that `cnt = (data.length/32 - 5)/6` computed by `getEnergyForData()` is significantly smaller than the 16 actual ECDSA recoveries that `execute()` performs in the thread pool.
5. Submit this as a `CALL` from a trigger-smart-contract transaction; observe that energy billed (`cnt * 1500`) undercharges relative to 16 real secp256k1 recoveries (`16 * 1500` expected if billed correctly), demonstrating the fee/real-cost mismatch that every validating node absorbs for free.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  public static class BatchValidateSign extends PrecompiledContract {

    private static final ExecutorService workers;
    private static final String workersName = "validate-sign-contract";
    private static final int ENGERYPERSIGN = 1500;
    private static final int MAX_SIZE = 16;
    private static final int ABI_HEADER_WORDS = 5;
    private static final int ABI_ITEM_WORDS = 6;

    static {
      workers = ExecutorServiceManager.newFixedThreadPool(workersName,
          Runtime.getRuntime().availableProcessors() / 2 + 1);
    }

    @Override
    public long getEnergyForData(byte[] data) {
      long cnt = (data.length / WORD_SIZE - 5) / 6;
      // one sign 1500, half of ecrecover
      return cnt * ENGERYPERSIGN;
    }

    @Override
    public Pair<Boolean, byte[]> execute(byte[] data) {
      try {
        return doExecute(data);
      } catch (Throwable t) {
        if (t instanceof InterruptedException){
          Thread.currentThread().interrupt();
        }
        return Pair.of(true, new byte[WORD_SIZE]);
      }
    }

    private Pair<Boolean, byte[]> doExecute(byte[] data)
        throws InterruptedException, ExecutionException {
      if (VMConfig.allowTvmOsaka()
          && !isValidAbiEncoding(data, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
        return Pair.of(false, EMPTY_BYTE_ARRAY);
      }
      DataWord[] words = DataWord.parseArray(data);
      byte[] hash = words[0].getData();

      if (VMConfig.allowTvmSelfdestructRestriction()) {
        int sigArraySize = words[words[1].intValueSafe() / WORD_SIZE].intValueSafe();
        int addrArraySize = words[words[2].intValueSafe() / WORD_SIZE].intValueSafe();
        if (sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE) {
          return Pair.of(true, DATA_FALSE);
        }
      }

      byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
          extractSigArray(words, words[1].intValueSafe() / WORD_SIZE, data) :
          extractBytesArray(words, words[1].intValueSafe() / WORD_SIZE, data);
      byte[][] addresses = extractBytes32Array(
          words, words[2].intValueSafe() / WORD_SIZE);
      int cnt = signatures.length;
      if (cnt == 0 || cnt > MAX_SIZE || signatures.length != addresses.length) {
        return Pair.of(true, DATA_FALSE);
