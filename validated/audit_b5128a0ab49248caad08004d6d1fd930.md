### Title
Truncated oracle price can reach zero and cause division-by-zero reverts in liquidation math - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The Pyth price normalization routine truncates integer division and can legitimately return a price of `0` for a low-value asset/exponent combination. That zero price is later used as a divisor in the liquidation math (`process-debt-asset` / `process-collateral-asset`), which will revert the entire transaction. This is the same root-cause class as Sherlock M-3: an oracle-adjacent function that is only checked for non-negativity (or not checked for zero at all) is later used as a denominator.

### Finding Description
`normalize-pyth` converts a raw Pyth `(price, expo)` pair to 8-decimal precision using truncating integer division: [1](#0-0) 

For assets where `expo` is more negative than -8 (adj negative, requiring `(/ p (pow 10 (- adj)))`), a sufficiently small raw `price` value truncates to `0`. There is no check anywhere in the price-resolution pipeline (`resolve-pyth`, `resolve-price-feed`, `resolve-callcode`) that the resulting price is strictly positive before it is stored/used — only confidence checks are applied: [2](#0-1) 

That price is subsequently consumed as a **divisor** in liquidation accounting, where debt/collateral USD amounts are converted back into token amounts: [3](#0-2) [4](#0-3) 

`mul-div-down` performs `(/ (* x y) z)` with `z` being `debt-price` or `coll-price`: [5](#0-4) 

If either price is `0`, this division reverts the call with a runtime arithmetic error. Grep confirms the same `mul-div-down`/`debt-price`/`coll-price` patterns exist in the mainnet `v0-4-market.clar` contract as well, though I could not pin the exact line numbers for that copy within the available indexed context.

### Impact Explanation
If a supported asset's Pyth price is ever truncated to zero (a low absolute raw price combined with a large negative exponent), any liquidation call touching that asset as debt or collateral reverts. Because liquidation is the mechanism that keeps the protocol solvent for undercollateralized positions, a stuck/reverting liquidation path is a denial-of-service on debt clearing for that asset — positions that should be liquidated cannot be, which can lead to protocol insolvency (bad debt accumulating past the point of recovery) or temporary freezing of collateral/debt resolution for affected positions. This matches the in-scope impact classes of temporary freezing of funds / protocol insolvency.

### Likelihood Explanation
This requires a specific, but not implausible, combination of a legitimate Pyth feed value and exponent that truncates to zero under the fixed 8-decimal normalization — analogous to the original Notional report where a legitimate but extreme price ratio zeroes out the division. No malicious oracle behavior or DAO compromise is required; it can occur purely from normal price feed values for a sufficiently low-priced asset (or if the DAO onboards an asset with a very small/very negative exponent feed in the future, consistent with the report's "may in the future" framing for `decimals`).

### Recommendation
After computing a resolved/normalized price anywhere in the oracle pipeline (`normalize-pyth`, `resolve-pyth`, `resolve-price-feed`, `resolve-callcode`, and the final value returned to `price-resolve`), assert the value is strictly greater than zero before it is cached or used, e.g. `(asserts! (> final-price u0) ERR-ORACLE-ZERO-PRICE)`. Additionally, guard the liquidation helpers (`process-debt-asset`, `process-collateral-asset`) with an explicit check that `debt-price`/`coll-price` are non-zero before dividing, returning a clear error instead of an unhandled arithmetic revert.

### Proof of Concept
1. A supported asset's Pyth feed publishes `price = 1`, `expo = -9` (one order of magnitude smaller precision than the market's fixed 8-decimal target).
2. `normalize-pyth` computes `adj = expo + 8 = -1`, so since `adj < 0`: `(/ price (pow 10 (- adj))) = (/ 1 10) = 0` — truncated to zero.
3. `resolve-pyth` returns `{ value: 0, timestamp: ... }`; no positivity check rejects it.
4. That price is cached as the asset's `price` field in the assets list used during health/liquidation calculations.
5. A liquidator calls the liquidation entry point on a position holding this asset as collateral or debt; `process-debt-asset`/`process-collateral-asset` executes `mul-div-down(... , ..., debt-price)` (or `coll-price`) with the zero price as divisor, causing the transaction to revert.
6. The affected position cannot be liquidated through this path as long as the price remains zero, risking bad debt accumulation.
