### Title
Unvalidated `git_object_directory`/`git_alternate_object_directories` fields in `Repository` proto allow cross-repository object read via crafted RPC field - (File: `internal/git/gitcmd/command_factory.go`)

### Summary
Every gRPC request that embeds a `gitalypb.Repository` message allows the caller to directly set `git_object_directory` and `git_alternate_object_directories`. These fields are trusted and joined into `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables for the git process spawned by Gitaly, with no path-containment validation at the point of command execution.

### Finding Description
When Gitaly builds a git command, it fetches the repository path and then unconditionally injects the client-supplied object-directory fields into the process environment: [1](#0-0) 

which calls: [2](#0-1) 

`alternates.Env` performs a plain `filepath.Join(repoPath, dir)` with **no** call to `storage.ValidateRelativePath` or any check that the resulting path stays under the repository/storage root. This contrasts with the dedicated validation that exists elsewhere for the same fields, e.g. `localrepo.Repo.ObjectDirectoryPath` (used only by `GetObjectDirectorySize`) which explicitly checks the resolved path against the storage root and rejects traversal/escape: [3](#0-2) 

The `git_object_directory` / `git_alternate_object_directories` fields are ordinary, client-settable fields on the public `Repository` proto message: [4](#0-3) 

The intended design is that these fields are only ever populated by Gitaly itself (quarantine setup) or looped back from Rails' `/allowed` access-check callback — never supplied directly by an external/ordinary client. This assumption is explicitly called out (and acknowledged as unenforced) in the WAL transaction middleware: [5](#0-4) 

The comment states: *"This property is violated in tests which manually configure the object directory... This allows for circumventing the transaction management... We'll leave this unaddressed for now."* This confirms the underlying design intent is currently unenforced at the RPC boundary for non-transactional/legacy code paths, and that `command_factory.go`'s environment construction has no equivalent guard at all — it runs for every git invocation regardless of WAL/transaction state.

This is directly analogous to the reported smart-contract bug: an access-control-relevant piece of state (`allowedModule`) was implicitly trusted based on attacker-controlled input (an arbitrary `requestId` created by anyone). Here, an access-control-relevant piece of state (which object directories a git process may read objects from) is implicitly trusted based on attacker-controlled input (a `Repository.git_object_directory`/`git_alternate_object_directories` field on any RPC), rather than being derived and validated authoritatively by Gitaly.

### Impact Explanation
An ordinary gRPC caller (any client with access to a repository-scoped RPC, e.g. `GetBlob`, `TreeEntry`, `FindCommit`, `CatFile`-backed calls, etc.) can set `git_alternate_object_directories` to an arbitrary path — including another repository's `objects` directory or any other directory readable by the Gitaly process — and Gitaly will configure `GIT_ALTERNATE_OBJECT_DIRECTORIES` to that path when spawning git. Since git resolves objects by OID across all configured alternate directories, an attacker who knows or can guess an object ID (OID) in a foreign, otherwise-inaccessible repository (e.g., a private repository) could retrieve its blob/commit/tree contents through their own (or any) repository context, producing unauthorized cross-repository object disclosure. This is a concrete storage-boundary/authorization bypass: it lets a repository-scoped access check for repo A be used to read objects that in fact belong to repo B.

### Likelihood Explanation
Likelihood is high for reachability (the fields are directly on the wire and accepted by any RPC using `Repository`), but exploitation requires the attacker to know a target OID (since raw object listing/enumeration is not exposed) and requires that no gRPC-level or Praefect-level filtering strips these fields before reaching Gitaly for the specific deployment/RPC in question. The WAL-enabled `storagemgr` middleware does close this gap for `ScopeRepository` mutators (rejecting requests with these fields set) and rewrites certain accessor flows, but the raw environment-construction code path in `command_factory.go` has no such gate, and non-WAL (or RPCs outside repository-scope transactionalization) deployments/services would be unprotected.

### Recommendation
- Short term: Add authoritative validation of `GitObjectDirectory`/`GitAlternateObjectDirectories` at the single choke point where they are turned into environment variables (`alternates.Env` / `command_factory.go`), verifying the resolved absolute path is contained within the storage root (reusing `storage.ValidateRelativePath`) and, where applicable, matches an expected quarantine-directory prefix, mirroring the checks already implemented in `localrepo.Repo.ObjectDirectoryPath`.
- Long term: Stop trusting these fields when supplied directly by external RPC callers. Strip or reject `git_object_directory`/`git_alternate_object_directories` on inbound requests from untrusted clients and only allow them to be set internally by Gitaly's own quarantine machinery or via the Rails access-check loopback path (as already partially enforced by `storagemgr.beginTransactionForRepository`), extending this enforcement uniformly to all RPC scopes and to non-WAL command execution.

### Proof of Concept
1. Attacker has push/read access to `repoA` (attacker-owned) and knows (or can brute-force/guess) an object ID `X` that exists only in a private `repoB`'s object store, e.g. leaked via a commit hash in a URL, CI log, or webhook.
2. Attacker calls any repository-scoped read RPC against `repoA` while directly setting:
   ```
   Repository{
     StorageName: "default",
     RelativePath: "repoA.git",
     GitAlternateObjectDirectories: ["<absolute-or-relative-path-to-repoB>/objects"],
   }
   ```
3. Because `command_factory.go` passes this straight to `alternates.Env` without validating containment, Gitaly executes git for `repoA` with `GIT_ALTERNATE_OBJECT_DIRECTORIES` pointing at `repoB`'s object directory.
4. The attacker requests object `X` (e.g., via `GetBlob`/`TreeEntry`/`CatFile`-backed RPC) against `repoA`; git resolves `X` from the alternate directory belonging to `repoB` and returns its contents to the attacker, despite the attacker having no authorization on `repoB`.

Note: I was not able to fully verify from the indexed code whether every currently-shipped repository-scoped RPC path is gated by the WAL `storagemgr` middleware in all deployment configurations (non-WAL Gitaly, Praefect-fronted setups, or RPCs outside `ScopeRepository`); this would require a live/full-repo review (e.g., a Devin session) to enumerate all reachable RPCs and confirm which ones bypass the `beginTransactionForRepository` gate entirely.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}

func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}

	parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
	baseDir := filepath.Base(relativeObjectDirectoryPath)
	isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))

	// Transactions quarantine a repository by pointing the object directory to a 'quarantine' named
	// directory in the transaction's temporary directory. If the base directory is `quarantine`,
	// Git push may apply an additional layer of quarantine such as `/quarantine/tmp_objdir-incoming-Gbc29N`
	// so we don't assert the `/quarantine` being the last element of the path. We thus also check for
	// whether the parent directory is in `quarantine` and whether the base directory has the expected
	// `tmp_objdir` suffix.
	if !isTransactionQuarantineDir {
		// We need to check whether the relative object directory as given by the repository is
		// a valid path. This may either be a path in the Git repository itself, where it may either
		// point to the main object directory storage or to an object quarantine directory as
		// created by git-receive-pack(1). Alternatively, if that is not the case, then it may be a
		// manual object quarantine directory located in the storage's temporary directory. These
		// have a repository-specific prefix which we must check in order to determine whether the
		// quarantine directory does in fact belong to the repo at hand.
		if _, origError := storage.ValidateRelativePath(repoPath, objectDirectoryPath); origError != nil {
			tempDir, err := repo.locator.TempDir(repo.GetStorageName())
			if err != nil {
				return "", structerr.NewInvalidArgument("getting storage's temporary directory: %w", err)
			}

			expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))
			absoluteObjectDirectoryPath := filepath.Join(repoPath, objectDirectoryPath)

			// The relative path is outside of the repository
			if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
				return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
			}
		}
	}

	fullPath := filepath.Join(repoPath, objectDirectoryPath)
	if _, err := os.Stat(fullPath); os.IsNotExist(err) {
		return "", structerr.NewNotFound("object directory does not exist: %q", fullPath)
	}

	return fullPath, nil
}
