## Title
Contract-type check in `DelegateResourceActuator`/`FreezeBalanceActuator` can be bypassed for CREATE2-precomputed addresses, allowing resource delegation to (soon-to-be) smart contracts - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator.validate()` and `FreezeBalanceActuator.validate()` both attempt to prevent bandwidth/energy resources from being delegated to smart-contract addresses by checking the *stored* account type (`AccountType.Contract`) rather than any runtime code inspection. Because this type is only set at the moment a contract account is actually created, an attacker can pre-fund a CREATE2-derived address (which is currently a plain/normal account) to pass the "not a contract" check, then later deploy a contract to that exact address, effectively delegating resources to a contract despite the explicit guard against it.

### Finding Description
Both actuators enforce "no resource delegation/freezing to contracts" purely via the account's stored `AccountType`: [1](#0-0) [2](#0-1) 

This mirrors the reported bug class: the guard relies on an address's *current* state (`Address.isContract()` in Solidity / `AccountType.Contract` in java-tron) rather than an immutable property of the address itself. TVM supports the `CREATE2` opcode, which allows deterministically precomputing a contract's future address from `(sender, salt, init-code hash)` before the contract is deployed [3](#0-2) . An attacker can:
1. Compute the future CREATE2 contract address off-chain.
2. Send TRX to that address (or otherwise cause an `AccountCapsule` with `AccountType.Normal` to be created there) — at this point `receiverCapsule.getType() != AccountType.Contract`.
3. Have another account delegate resources (or freeze-and-delegate via `FreezeBalanceActuator`'s `receiverAddress`) to this address; validation passes because the account is still typed `Normal`.
4. Deploy the actual contract to the precomputed address via `CREATE2`.

The account type is flipped to `AccountType.Contract` only inside `VMActuator`'s contract-creation path, at `rootRepository.createAccount(contractAddress, ..., Protocol.AccountType.Contract)` [4](#0-3)  — this happens strictly after the delegate/freeze transaction has already been validated and committed, so the earlier check cannot see the address's eventual contract status.

### Impact Explanation
This lets an attacker route delegated bandwidth/energy (or locked/frozen resources) to an address that will become a smart contract, defeating the explicit protocol invariant "Do not allow delegate resources to contract addresses." Depending on downstream assumptions in resource accounting/usage code that assume a delegatee is a normal account (e.g., resource usage/refund bookkeeping, `DelegatedResourceCapsule` lifecycle, or governance/voting-adjacent flows that key off account type), this could allow a contract to accumulate acquired resources it was never supposed to receive, or be used as a building block for further logic that assumes contract addresses never hold delegated resources.

### Likelihood Explanation
CREATE2 address precomputation is a normal, permissionless capability reachable by any unprivileged contract deployer/transaction broadcaster; no special privileges are required to fund an address and later deploy a contract there. This makes the bypass straightforward to execute with two ordinary transactions from an unprivileged account.

### Recommendation
Do not gate this invariant solely on the currently stored `AccountType`. Options:
- Re-validate/enforce the "no contract receiver" invariant at the point resources are actually granted to the receiver (e.g., inside `VMActuator.create()`/contract creation) by checking whether the target address has any outstanding delegated resources and rejecting/reclaiming them, or blocking contract creation at addresses that already have delegated-resource records.
- Alternatively, treat the check as best-effort and clearly document/accept that `AccountType.Contract` is not a durable guarantee against future contract deployment, adjusting any downstream logic that depends on delegatees never being contracts.

### Proof of Concept
1. Attacker (or colluding party) computes a CREATE2 target address `X` for a not-yet-deployed contract using `CREATE2(sender, salt, keccak256(init_code))`.
2. Attacker sends a small TRX transfer to `X`, causing `AccountStore` to create an `AccountCapsule` for `X` with `AccountType.Normal` (via the same "auto-create account on receipt" logic used elsewhere, e.g. `TransferActuator.execute()` at lines 49-58) [5](#0-4) .
3. A `DelegateResourceContract` transaction is submitted with `receiverAddress = X`. `DelegateResourceActuator.validate()` checks `receiverCapsule.getType() == AccountType.Contract` [1](#0-0)  — this is false (still `Normal`), so validation passes and resources are delegated.
4. Attacker deploys the contract at `X` via `CREATE2` from the same deployer/salt/init-code, converting `X` into a smart contract account (`AccountType.Contract`) inside `VMActuator`'s creation flow [4](#0-3) .
5. `X` is now a smart contract holding previously delegated resources, in violation of the explicit "Do not allow delegate resources to contract addresses" invariant.

Note: I was not able to directly execute this scenario in a test environment; this analysis is based on static code review of the validate/execute paths and the CREATE2 opcode support in the TVM. A background Devin session with test-execution access could confirm end-to-end via `framework/src/test/java/org/tron/common/runtime/vm/Create2Test.java` and `DelegateResourceActuatorTest.java` to empirically verify the bypass.
