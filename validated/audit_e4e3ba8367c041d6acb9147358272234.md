### Title
Dust-transfer griefing fills `depositTokensOfAccount`, DoS-ing a victim's deposits and token receipts - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken._transfer` and `_mint` add the token to the recipient's `depositTokensOfAccount` set whenever the recipient's prior balance was zero (`DepositToken.sol:486-488, 518-520`). `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once an account's combined deposit-token + debt-token set reaches `Pool.MAX_TOKENS_PER_USER` (confirmed by the revert test in `test/Pool.test.ts:1491-1521`). Because `transfer`/`transferFrom` are permissionless and only gated by `_revertIfLocked` on the *sender* (`DepositToken.sol:348-376`), an unprivileged attacker can push dust amounts of many distinct deposit tokens to a victim, exhausting the victim's set slots and causing every subsequent first-time receipt — `deposit` to `onBehalfOf_` = victim, `transfer`, `transferFrom`, or `Pool.liquidate` → `seize` — to revert.

### Finding Description
This is the on-chain analog of CVE-2015-3238's "large attacker-controlled input causes hang/DoS": here the attacker-controlled input is the cardinality of a victim's account token set, which the victim never opted into populating.

Attack path:
1. Attacker deposits dust amounts of collateral across many different `DepositToken`s (or acquires them via `Pool.swap`/transfers).
2. Attacker calls `DepositToken.transfer(victim, 1 wei)` for each token. Each call hits `pool.addToDepositTokensOfAccount(victim)` because `balanceOf[victim] == 0` before the dust (`DepositToken.sol:518-520`).
3. Once the victim's combined set size hits `MAX_TOKENS_PER_USER`, `Pool.addToDepositTokensOfAccount` reverts `UserReachedMaxTokens`.
4. Any subsequent action that would add a *new* token to the victim's set reverts: `DepositToken.deposit(amount, victim)` for a collateral the victim doesn't hold (`DepositToken.sol:234` → `_mint` → line 486-488), incoming `transfer`/`transferFrom`, `DebtToken.issue/mint` for a synth the victim hasn't held (same pattern in `DebtToken.sol`), and `DepositToken.seize` to the victim during liquidation (`DepositToken.sol:343-345`).

### Impact Explanation
The victim's ability to deposit new collateral types and to receive any deposit/debt token they don't already hold is frozen. Concretely: a user whose position is deteriorating cannot deposit a *new* collateral type to improve health, pushing them toward liquidation; a liquidator designating such an account as `to_` in `seize` reverts; leveraged/operator flows crediting new tokens to the account revert. Recovery requires the victim to transfer the dusted tokens back out so `balanceOf` returns to zero and `removeFromDepositTokensOfAccount` fires — a per-token, attacker-priced remediation. This is a temporary freezing of funds/protocol functionality caused entirely by an unprivileged third party, which satisfies the accepted impact classes.

### Likelihood Explanation
- No privileged role required: `deposit`, `transfer`, and `transferFrom` are public entry points callable directly or via `Operator.execute`.
- No modifier stops it: `transfer` checks only the *sender's* unlocked balance (`_revertIfLocked(_msgSender, ...)`), never the recipient's set size or consent. `nonReentrant`, `whenNotPaused`, and `SynthContext` checks are orthogonal.
- Cost is bounded: the attacker needs `MAX_TOKENS_PER_USER - current set size` distinct tokens and dust of each, plus gas. Dust of already-held token types is free to repeatedly re-add to new victims.
- Limitation (affecting severity, not validity): existing token types already in the victim's set are unaffected, and the victim can self-recover by sending the dust back out, so the freeze is temporary and partial rather than permanent.

### Recommendation
- Only add to `depositTokensOfAccount`/`debtTokensOfAccount` on user-initiated actions (`deposit`, `issue`) rather than on incoming `transfer`s; or
- Let recipients opt out (e.g., skip the set-add when the incoming amount is below a dust threshold — though thresholds are gameable); or
- Make `addToDepositTokensOfAccount` non-reverting on overflow and exclude over-limit tokens from `debtPositionOf`, documenting the risk; or
- Allow anyone to call `removeFromDepositTokensOfAccount` on behalf of an account whose balance is zero, so cleanup is permissionless.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";

contract DustGriefingTest is Test {
    IPool pool;             // deployed Pool on fork
    DepositToken[] tokens;  // N >= MAX_TOKENS_PER_USER active DepositTokens
    address attacker = address(0xA77);
    address victim   = address(0xB0B);

    function test_dustFillsVictimSet_blocksDeposit() public {
        uint256 max = pool.MAX_TOKENS_PER_USER();

        // 1. Attacker mints dust of many deposit tokens and pushes to victim
        for (uint256 i; i < max; ++i) {
            DepositToken dt = tokens[i];
            deal(address(dt.underlying()), attacker, 1e18);
            vm.startPrank(attacker);
            dt.underlying().approve(address(dt), 1e18);
            dt.deposit(1e18, attacker);          // attacker holds msdTOKEN
            dt.transfer(victim, 1);              // balance 0 -> addToDepositTokensOfAccount(victim)
            vm.stopPrank();
        }

        // victim's combined deposit+debt token set is now at MAX_TOKENS_PER_USER
        assertEq(pool.getDepositTokensOfAccount(victim).length, max);

        // 2. Any deposit of a NEW collateral type to victim reverts
        DepositToken newToken = tokens[max]; // a token victim doesn't hold
        deal(address(newToken.underlying()), attacker, 1e18);
        vm.startPrank(attacker);
        newToken.underlying().approve(address(newToken), 1e18);
        vm.expectRevert(IPool.UserReachedMaxTokens.selector);
        newToken.deposit(1e18, victim);
        vm.stopPrank();

        // 3. Even an incoming transfer of a new token reverts
        // (same revert path via _transfer -> addToDepositTokensOfAccount)

        // 4. Victim must spend gas per token to clear: send dust back out
        vm.prank(victim);
        tokens[0].transfer(attacker, tokens[0].balanceOf(victim));
        assertLt(pool.getDepositTokensOfAccount(victim).length, max);
    }
}
```

Uncertainty: I verified the `UserReachedMaxTokens` revert path via `test/Pool.test.ts:1491-1521` and the set-add hooks in `DepositToken.sol`, but did not read the exact `Pool.addToDepositTokensOfAccount` implementation to confirm whether the max counts deposit + debt tokens jointly or separately (the test suggests a combined `MAX_TOKENS_PER_USER` budget). The value of `MAX_TOKENS_PER_USER` also was not read; the attack cost scales with it, and if it is very large relative to the number of active deposit tokens, feasibility depends on there being enough distinct tokens in the deployed configuration.
