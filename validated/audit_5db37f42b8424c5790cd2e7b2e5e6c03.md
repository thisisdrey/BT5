## Analysis

The key permission check is `check_actor_permissions` in `runtime/runtime/src/actions.rs`, which for `Action::AddKey` requires only `actor_id == account_id` [1](#0-0) . `actor_id` is derived from the receipt's predecessor (self-receipt pattern), not re-validated against the *current* account's ownership or any signature at apply time. Postponed-receipt storage (`TrieKey::PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`) is completely disjoint from account state and is never touched by `remove_account` [2](#0-1)  or by `action_delete_account` [3](#0-2) , and `CreateAccount` handling in `check_account_existence` doesn't clear or check for postponed receipts either [4](#0-3) . When the missing data eventually arrives, `process_receipt` dequeues the postponed receipt and calls `apply_action_receipt` unconditionally on the stored actions [5](#0-4) .

### Where the attack path breaks

`apply_action` invokes `check_account_existence` before `check_actor_permissions` for every action [6](#0-5) . `Action::AddKey` is in the branch that requires `account.is_some()`, returning `AccountDoesNotExist` otherwise. In the described sequence, step 3 (`X→A CreateAccount`) happens *before* step 4 (dependency resolves and the postponed receipt runs), so by the time the stale postponed `AddKey` action from A's original receipt executes, the account **does exist** again (freshly created by `X`). `check_account_existence` therefore does not block this—the account is present, so `AddKey` proceeds to `check_actor_permissions`, which only checks `actor_id == account_id`. Since the postponed receipt still carries `predecessor_id == receiver_id == account_id (A)`, `actor_id` is set to `A` (the receipt's own predecessor) and trivially equals `account_id` (`A`), so the permission check **passes** regardless of who actually owns the re-created account now.

This confirms the core claim in the audit prompt: `remove_account` and `action_delete_account` do not purge postponed-receipt/pending-data-count state tied to the deleted account, and the postponed receipt's stale `AddKey` action is authorized purely via the SIR (`predecessor_id==receiver_id`) invariant, which was valid when the receipt was first created but is no longer meaningful once the account has been deleted and recreated by an unrelated party. I did not find any additional guard (e.g., a check that the account's creation/re-creation nonce or timestamp matches, or that postponed receipts are invalidated on `DeleteAccount`) in `action_delete_account`, `remove_account`, `process_receipt`, or `process_action_receipt` that would prevent this. I was unable to fully verify the `DeleteAccount`-must-be-instant/final constraints and whether an intervening block boundary or the second-preimage requirement (`X` must be able to recreate exactly account name `A`, which is trivial since anyone can send `CreateAccount` to an arbitrary receiver id) impose any friction against exploitation — but from the code reviewed, no such friction exists.

### Title
Stale postponed receipt with `AddKey` survives account deletion and executes against a re-created account - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
An account `A` can postpone a self-receipt (predecessor==receiver==A) containing `AddKey(FullAccess)` plus an unresolved cross-contract call dependency, then delete itself via `DeleteAccount`. Because `remove_account` only clears `Account`/`ContractCode`/`AccessKey`/`GasKeyNonce`/`ContractData` and never touches `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`, the postponed receipt survives account deletion. Any third party can then re-create account `A` via `CreateAccount`, and once the outstanding data dependency resolves, the stale postponed receipt executes its `AddKey` action against the new occupant of `A`, because `check_actor_permissions` for `AddKey` only checks `actor_id == account_id` (true by construction, since the receipt's predecessor is `A` itself) without any check that the account is the same logical entity that created the receipt.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:504-575`) removes `Account`, `ContractCode`, all `AccessKey`/`GasKeyNonce` entries, and `ContractData`, but has no knowledge of and does not remove `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by the same `account_id` as `receiver_id`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) calls only `remove_account` and never queries/cleans postponed-receipt bookkeeping.

Separately, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores any action receipt with unresolved `input_data_ids` as a postponed receipt via `set_postponed_receipt`, keyed by `receiver_id`+`receipt_id`, and records a `PendingDataCount`. When the last dependency resolves, `process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1386-1455`) fetches the postponed receipt via `get_postponed_receipt`, removes the bookkeeping, and unconditionally calls `apply_action_receipt` on the stored `Receipt` — with no re-validation of the receiver account's identity/ownership at execution time (only the previously-serialized actions are replayed).

Authorization for `AddKey` inside `apply_action` is enforced by `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-760`), which requires only `actor_id == account_id`. `actor_id` is set from `receipt.predecessor_id()` for this receipt kind, and since the receipt was self-addressed (`predecessor_id == receiver_id == A`), this check passes trivially regardless of which entity currently controls account `A`. `check_account_existence` (`runtime/runtime/src/actions.rs:787-855`) only checks that *some* account exists at `account_id`, not that it is the same account instance that originated the receipt — so a freshly `CreateAccount`-created `A` passes this check too.

The attacker's transaction inputs required: (1) a signed transaction/receipt from `A` to `A` containing `[AddKey(FullAccess), FunctionCall(...)]` where the `FunctionCall` produces a promise with an `input_data_id` dependency that never resolves before deletion (e.g., by never issuing the corresponding callback, or the callee simply not calling back); (2) a subsequent `A`→`A` `DeleteAccount(beneficiary=B)` receipt; (3) an arbitrary `X`→`A` `CreateAccount` receipt; (4) an eventual `Data` receipt that resolves the pending dependency (attacker controls when to send this, since they control the original call).

None of the existing checks (nonce/signature checks happen only at transaction verification for the original tx, not replayed at postponed-receipt execution time; `check_account_existence`; `check_actor_permissions`; storage staking checks) detect that account `A`'s identity/ownership changed between receipt creation and postponed execution.

### Impact Explanation
This is an authorization-escalation bug: the attacker who used to own `A` (and no longer does, since they deleted it) can implant a `FullAccess` `AddKey` onto whatever future occupant claims the name `A`, without that occupant's consent. This directly violates "owner privilege must not survive account deletion," matching the NEAR bounty category of authorization escalation across accounts/promises. Concretely, if `X` deploys a contract at `A` believing it to be a fresh, keyless (or self-controlled) account, the attacker gains a lingering full-access key on it, and can subsequently drain funds/control the contract — a path to theft or loss of funds for the new owner of `A`.

### Likelihood Explanation
Preconditions are fully attacker-controlled and require no privileged access: fund account `A`, submit a self-receipt with `AddKey`+`FunctionCall`(cross-contract call to any account, including one the attacker controls, that simply never replies), then submit `DeleteAccount`. Cost is limited to gas/storage fees for these ordinary transactions. The trigger (data receipt resolving the dependency) is entirely under the attacker's control since they can arrange the dependency to resolve at a time of their choosing (e.g., control the callee contract to call back on demand). Re-creation of `A` by an unrelated third party (`X`) is a necessary but plausible real-world event for popular/short account names, and the attack is repeatable for any account the attacker controls before deletion.

### Recommendation
When deleting an account (`action_delete_account`/`remove_account`), also purge any outstanding `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries keyed by that `account_id` as `receiver_id` (this requires iterating/prefix-scanning those columns similarly to how access keys and contract data are cleaned up). Alternatively/additionally, bind postponed receipts to an account-generation/version identifier and re-validate at resume time that the account has not been deleted and recreated since the receipt was postponed, failing the receipt (and refunding/burning deposits) if the receiver account's identity has changed.

### Proof of Concept
Runtime-level integration test (test-loop or `runtime/runtime/src/tests/apply.rs` style, similar to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Set up account `alice` funded, no contract.
2. Submit an `alice`→`alice` `ActionReceipt` with actions `[AddKey(FullAccess, pk_attacker)]` and `input_data_ids: [data_id]` (so it becomes postponed) — assert it lands in `TrieKey::PostponedReceipt`/`TrieKey::PendingDataCount` via `get_postponed_receipt`/state inspection.
3. Submit `alice`→`alice` `DeleteAccount(beneficiary=bob)` receipt; apply and commit; assert `get_account(alice)` is `None` and `get_postponed_receipt(alice, receipt_id)` is still `Some(...)` (bug confirmation).
4. Submit `bob`→`alice` `CreateAccount` receipt; apply and commit; assert `get_account(alice)` is `Some` with zero access keys via `get_raw_prefix_for_access_keys` iteration.
5. Submit the missing `Data` receipt for `data_id` targeted at `alice`; apply and commit.
6. Assert (expected-safe / failing-on-bug): `get_access_key(alice, pk_attacker)` is `None`. If the bug is present, this assertion fails because the `AddKey` from the stale postponed receipt was applied to the newly created `alice` account, giving `pk_attacker` `FullAccess`.
