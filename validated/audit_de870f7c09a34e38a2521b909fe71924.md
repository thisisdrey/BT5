### Title
DepositToken self-transfer inflates collateral balance and enables unbacked synthetic borrowing - ([File: contracts/DepositToken.sol])

### Summary

`DepositToken._transfer()` reads the sender and recipient balances before writing both balances, but it does not handle `sender_ == recipient_`. [1](#0-0)  In that case, the recipient write overwrites the sender write, increasing the account balance by `amount_` without changing `totalSupply` or moving collateral. [1](#0-0)  An unprivileged caller can reach this through public `transfer()` after passing only the unlocked-balance check. [2](#0-1) 

### Finding Description

`transfer()` obtains the actual sender, verifies that the requested amount is unlocked, and calls `_transfer()`. [3](#0-2)  For an account with no debt, `unlockedBalanceOf()` returns the full `balanceOf[account_]`, so transferring the account's full balance to itself is permitted. [4](#0-3)  `_transfer()` then writes `balanceOf[sender_] = balanceBefore - amount_`, followed immediately by `balanceOf[recipient_] = recipientBalanceBefore + amount_`; when both addresses are identical, the second write leaves the balance at `balanceBefore + amount_`. [1](#0-0) 

The pool values collateral using `DepositToken.balanceOf(account_)`, not `totalSupply` or Treasury holdings. [5](#0-4)  `DebtToken.issue()` derives the available issuance capacity from that inflated collateral balance and mints synthetic tokens to the caller-selected beneficiary. [6](#0-5) 

### Impact Explanation

An attacker can deposit collateral once, repeatedly self-transfer the resulting deposit-token balance to multiply reported collateral, and issue synthetic assets far beyond the value actually held by Treasury. [7](#0-6) [5](#0-4)  The resulting debt remains bounded only by the synthetic token's configured supply cap, while the protocol's true collateral backing remains the original deposit. [8](#0-7)  The attacker can swap the minted synthetic asset, transfer it, or bridge it before liquidation/accounting catches up, producing direct protocol insolvency and losses for other users. [9](#0-8) 

### Likelihood Explanation

The exploit requires only an unprivileged EOA, a supported collateral deposit, and calls to public `transfer()` and `DebtToken.issue()`. [2](#0-1) [10](#0-9)  No privileged role, governance action, external oracle failure, malicious bridge component, or timing assumption is required. [11](#0-10) 

The same stale-balance overwrite is also present in `SyntheticToken._transfer()` if the code follows the same pattern, but the demonstrated impact through collateral valuation is the critical path. [12](#0-11) 

### Recommendation

Reject self-transfers or make them an explicit no-op in `DepositToken._transfer()` before balance writes. [13](#0-12)  Apply the same correction to `SyntheticToken._transfer()` if it shares the aliased sender/recipient implementation. [12](#0-11)  Add invariant coverage asserting `sum(balanceOf) == totalSupply` before and after arbitrary transfers, including self-transfers. [1](#0-0)

```solidity
pragma solidity ^0.8.24;

import "forge-std/Test.sol";
import {IDepositToken} from "contracts/interfaces/IDepositToken.sol";
import {IDebtToken} from "contracts/interfaces/IDebtToken.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DepositTokenSelfTransferTest is Test {
    IDepositToken depositToken; // Deployed or fixture collateral token.
    IDebtToken debtToken;       // Debt token for the chosen synthetic asset.
    IERC20 underlying;          // depositToken.underlying()
    address attacker = address(0xA11CE);

    function testSelfTransferCreatesUnbackedCollateral() public {
        uint256 amount = 100 ether;

        deal(address(underlying), attacker, amount);
        vm.startPrank(attacker);
        underlying.approve(address(depositToken), amount);
        depositToken.deposit(amount, attacker);

        uint256 beforeBalance = depositToken.balanceOf(attacker);
        depositToken.transfer(attacker, beforeBalance);
        vm.stopPrank();

        uint256 inflated = depositToken.balanceOf(attacker);
        assertEq(inflated, beforeBalance * 2);
        assertEq(depositToken.totalSupply(), beforeBalance);
    }

    function testInflatedBalanceSupportsDebt() public {
        uint256 amount = 100 ether;

        deal(address(underlying), attacker, amount);
        vm.startPrank(attacker);
        underlying.approve(address(depositToken), amount);
        depositToken.deposit(amount, attacker);

        // Repeat as needed to multiply collateral while supply remains unchanged.
        uint256 b = depositToken.balanceOf(attacker);
        depositToken.transfer(attacker, b);
        b = depositToken.balanceOf(attacker);
        depositToken.transfer(attacker, b);

        // Query amount from masterOracle for the selected synthetic asset.
        uint256 issueAmount = debtToken.balanceOf(attacker); // Replace with a quoted positive amount below maxTotalSupply.
        debtToken.issue(issueAmount, attacker);
        vm.stopPrank();
    }
}
```

The first assertion is the minimal reproduction: one deposit followed by `depositToken.transfer(attacker, balance)` doubles `balanceOf(attacker)` while `totalSupply` remains unchanged. [1](#0-0)  The second test should use `pool.masterOracle().quoteUsdToToken()` against a positive amount allowed by `DebtToken.issue()` to demonstrate that the inflated balance mints real synthetic assets. [14](#0-13)
