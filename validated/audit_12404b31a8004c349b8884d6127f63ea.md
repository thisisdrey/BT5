## Confirmed: `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`) never enforces `StackerDBConfig::write_freq`

### Title
StackerDB HTTP chunk writes bypass the configured wall-clock write-frequency limit, letting a slot owner rewrite state at unbounded rate up to `max_writes` - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBTx::try_replace_chunk` is the single gate that the `POST /v2/stackerdb/.../chunks` RPC handler (`stackslib/src/net/api/poststackerdbchunk.rs`) calls to accept a signed chunk write. It checks chunk size, slot existence, signer validity, staleness, and `max_writes`, but it never checks `self.config.write_freq` — the minimum wall-clock time that is supposed to separate two writes to the same slot.

### Finding Description
`StackerDBConfig::write_freq` is documented as "minimum wall-clock time between writes to the same slot" [1](#0-0) . The `Error::TooFrequentSlotWrites(u64)` variant exists specifically to reject writes that violate this constraint [2](#0-1) , and its `Display` implementation is wired up [3](#0-2) , yet `try_replace_chunk` — the only function that actually performs the write on the RPC ingestion path — checks only chunk size, `NoSuchSlot`, `BadSlotSigner`, `StaleChunk`, and `TooManySlotWrites`, and never reads `slot_validation.write_time` or compares it against `self.config.write_freq` before calling `insert_chunk`: [4](#0-3) 

`insert_chunk` does record a fresh `write_time` on every accepted write [5](#0-4) , so the bookkeeping data needed to enforce the frequency cap exists and is maintained — it's simply never read back and checked in the write path.

The HTTP RPC handler `RPCPostStackerDBChunkRequestHandler::try_handle_request` calls `tx.try_replace_chunk(...)` directly with no additional frequency gate of its own; it only classifies whatever `net_error` variant `try_replace_chunk` returns (`StaleChunk`, `NoSuchSlot`, `BadSlotSigner`/`VerifyingError`, `StackerDBChunkTooBig`, `TooManySlotWrites`) into an ack code, and `TooFrequentSlotWrites` is conspicuously absent from that match arm list [6](#0-5) .

By contrast, the *replication* path (`validate_received_chunk`, used when accepting chunks over p2p gossip/push) explicitly documents that it doesn't check write frequency "since the caller has different ways of doing this" [7](#0-6) , implying the frequency check is expected to live in the DB write path (`try_replace_chunk`) instead — but it isn't there. The download-scheduling logic in `sync.rs` does respect `write_freq` when deciding whether to *fetch* a chunk from a peer [8](#0-7) , but that is a scheduling optimization for the pulling replica, not an authorization gate on the writer — it does not prevent a signer from posting new versions to their own node's RPC endpoint faster than `write_freq` allows.

The existing unit test's docstring even claims this property is verified ("verifies that they cannot exceed the config-given wall-clock write frequency" [9](#0-8) ), but the test body that follows only exercises `StaleChunk`, `TooManySlotWrites`, and `BadSlotSigner` — it never actually asserts a `TooFrequentSlotWrites` rejection [10](#0-9) , consistent with the fact that no such check exists to test.

### Impact Explanation
This breaks the equality between "declared/configured policy" (`write_freq` as set by the StackerDB-controlling smart contract) and "enforced policy" (what `try_replace_chunk` actually allows). Any legitimate slot signer (e.g., a Nakamoto stacking signer or miner writing to its StackerDB slot) can post new chunk versions to a node's HTTP RPC endpoint at essentially unlimited rate, limited only by `max_writes` and `chunk_size`, ignoring the intended `write_freq` throttle. This is directly analogous to the Tigris "riskless trades" bug class: a rate-limit/delay parameter that is enforced inconsistently across code paths (checked on the read/fetch side, but not on the write/authorization side), allowing a party who controls a legitimate write credential to defeat the timing invariant the protocol relies on for eventual-consistency assumptions and anti-spam/DoS protection of StackerDB replicas. Because `write_freq` is meant to bound resource consumption (write frequency) network-wide as chunks propagate to all replicas, an authorized-but-malicious signer can flood their own slot with new versions far faster than intended, which is a bounded-but-real DoS/anti-throttle bypass on a node-write endpoint reachable by anyone who holds a valid slot-signing key. It does not require a privileged/admin role beyond the slot's own signer key, and the malformed policy adherence propagates to all replicas via the normal chunk-inventory sync mechanism (each unthrottled version becomes "expected" and is fetched by peers per `validate_received_chunk`'s stale/max_writes checks, which likewise don't check frequency there either).

### Likelihood Explanation
High. Any account controlling a StackerDB slot signing key can trivially and repeatedly call the `POST /v2/stackerdb/{principal}/{contract}/chunks` endpoint with monotonically increasing `slot_version` values; no special conditions, races, or privileged access are required — just a valid signature over each chunk, which the caller already possesses by definition of owning the slot.

### Recommendation
Add a `write_freq` check in `try_replace_chunk` (or immediately before calling it in the RPC handler), comparing `get_epoch_time_secs()` against `slot_validation.write_time + self.config.write_freq`, and return `net_error::TooFrequentSlotWrites` when the deadline hasn't elapsed. Also update `poststackerdbchunk.rs`'s error-classification match to map `TooFrequentSlotWrites` to a dedicated `StackerDBErrorCodes` variant (analogous to `TooManySlotWrites`) so clients get a proper retryable ack rather than a 500.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u120` (120 seconds) and any `max-writes` ≥ 2.
2. As the legitimate signer for slot `i`, sign and `POST` chunk version 1 to `/v2/stackerdb/{principal}/{contract}/chunks` — accepted.
3. Immediately (same second) sign and `POST` chunk version 2 for the same slot.
4. Observe the second write is accepted with `accepted: true` (per `try_handle_request`'s success path, since `try_replace_chunk` only checks size/slot/signer/staleness/max_writes), even though `write_time` recorded from step 2 shows less than `write_freq` seconds elapsed — demonstrating the `write_freq` policy is never enforced on the write path, unlike `max_writes` and staleness which are correctly enforced (as covered by `test_request_fail_stale_chunk` and `test_request_fail_too_many_slot_writes` in `stackslib/src/net/api/tests/poststackerdbchunk.rs`, which have no `TooFrequentSlotWrites` counterpart).

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
