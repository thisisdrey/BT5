### Title
Unauthenticated `RecvError` packet allows source-spoofed attacker to force tunnel teardown / remote state poisoning - ([File: outside.go])

### Summary
Nebula processes `header.RecvError` packets before any certificate or handshake authentication is performed. `handleRecvError` identifies the target tunnel purely by the `RemoteIndex` field in the (unauthenticated, unencrypted) header and a UDP source-address equality check, then tears down the tunnel's state (`closeTunnel` + `DeleteHostInfo`). An attacker with no CA-signed certificate who can guess/observe a 32-bit index and spoof the peer's known UDP source address can force state destruction without ever completing a handshake.

### Finding Description
In `readOutsidePackets`, `header.RecvError` is dispatched to `f.handleRecvError` immediately after header parsing and before any handshake/cert verification, in the same branch as `header.Handshake`: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely from the attacker-controlled `h.RemoteIndex` field via `QueryReverseIndex`, and its only authentication is comparing the UDP source address against the currently known remote address of that hostinfo: [2](#0-1) 

The `hr.IsValid() && hr != addr` check is a *spoofing heuristic*, not a cryptographic authentication check — it only blocks the message if the recorded remote address differs from the packet's source. UDP has no return-routability guarantee, so any off-path or on-path attacker (with no Nebula certificate at all, since this code path is fully unauthenticated) can spoof the source `UdpAddr:port` of an already-established peer and supply the correct `RemoteIndex` (which travels in plaintext in every packet to that peer, and is therefore observable on the wire) to satisfy this check.

This is the direct analog of the reported bug class: state (deposit accounting in the DeFi report; the tunnel/hostmap/handshake state here) is mutated by input that never went through the intended, authenticated "function" (an authenticated `CloseTunnel` message or connection-manager decision) — an attacker can trigger the state transition (`closeTunnel`, `DeleteHostInfo`) via an unauthenticated side channel, "unexpectedly" poisoning the state that the rest of the system assumes only legitimate/authenticated actors can change.

### Impact Explanation
This yields a remote, unauthenticated denial-of-service / state-poisoning primitive: an attacker with no CA-signed certificate can force closure of a live tunnel between two legitimate peers by spoofing UDP source address/port and replaying/guessing the (plaintext, observable) `RemoteIndex`. This matches the "remote state poisoning" and "remote crash/DoS impact" categories the validation rules accept, and does not require the attacker to hold a valid certificate or be a trusted peer/lighthouse.

### Likelihood Explanation
Feasibility depends on:
- `RemoteIndex` is sent in cleartext in every packet header (`header.H`), so it is trivially observable by anyone who can see traffic between the two peers (on-path attacker), and is a 32-bit value that must be guessed by a pure off-path attacker.
- The UDP source address/port equality check is the only gate, and UDP source addresses are trivially spoofable by an off-path attacker without needing to receive any reply (no three-way handshake).
- The feature is configurable (`accept_recv_error` / `send_recv_error` settings referenced in `interface.go`), so exposure varies by deployment; this reduces likelihood somewhat but the code path itself performs no cryptographic authentication when enabled.

### Recommendation
- Do not act on `RecvError` messages, and any other pre-authentication signal, purely on the basis of an attacker-controlled index plus a spoofable UDP source-address match. Require message-level authentication (e.g. MAC/AEAD binding to the session, or only accept post-handshake authenticated `CloseTunnel` messages) before mutating hostmap/tunnel state.
- If `RecvError` handling must remain unauthenticated for performance reasons, treat it only as a *hint* to accelerate re-handshake attempts, not as a trigger for immediate `closeTunnel`/`DeleteHostInfo` — require corroboration (e.g., failing decrypt attempts, or a signed ack) before destructive state changes.
- Consider rate-limiting/backing off `RecvError`-triggered teardown per remote index to blunt spoofing-based DoS.

### Proof of Concept
1. Two legitimate Nebula nodes, A and B, establish a tunnel; A knows B's `RemoteIndex` because it is sent in cleartext on every packet A receives from B.
2. Attacker C, holding no Nebula certificate, observes traffic between A and B (or otherwise learns B's `RemoteIndex` toward A, e.g. by sniffing on a shared network segment) and learns/spoofs B's UDP source address/port as seen by A.
3. C crafts a bare `RecvError` header (`header.Encode(..., header.RecvError, 0, index, 0)` as built in `sendRecvError`) with `RemoteIndex` set to the index B uses toward A, and sends it to A's UDP listener with a spoofed source address matching B's known address.
4. A's `readOutsidePackets` routes it directly to `handleRecvError` without any handshake or cert check; the address-match check passes because the spoofed source matches; A calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the tunnel state despite C never having authenticated. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
