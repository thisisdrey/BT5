### Title
Non-constant-time HTTP `authorization` token comparison enables remote timing side-channel recovery of `auth_token` - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
Six in-scope RPC handlers authenticate privileged endpoints by comparing the client-supplied `authorization` header against the node's configured secret using plain `!=` string comparison. Rust's `String`/`&str` `PartialEq` is implemented as a byte-wise, early-exit comparison (not constant-time), so the time taken to reject a guess leaks the length of the matching prefix. A remote, unauthenticated attacker can use this timing oracle to recover the `auth_token` byte-by-byte, then use it to authenticate to state-changing/compute-heavy endpoints.

### Finding Description
The affected handlers all implement the identical pattern: [1](#0-0) 

```
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

The same pattern appears in: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`auth_header != password` uses the standard library's `str`/`String` equality, which compares byte-by-byte and returns as soon as a mismatch is found (and even checks length first). This is the classic timing side-channel bug class cited in the external report (CWE-208): the "equal vs. not equal" comparison's *timing* leaks information about *how much of the secret matched*, breaking the intended equality invariant of "attacker-supplied token equals server-stored token" as a constant-time, information-hiding operation. This is directly analogous to the phpseclib AES-CBC padding-oracle timing issue — both are remote, unauthenticated timing oracles against a secret-dependent comparison, differing only in the specific secret being probed (padding validity vs. auth token bytes).

### Impact Explanation
`auth_token` gates several privileged endpoints in this repo:
- `/v3/block_proposal` — accepts and validates a Nakamoto block proposal (compute-heavy; also feeds into miner/signer state) [7](#0-6) 
- `/v2/blocks?broadcast=1` — authenticated write path that broadcasts a block [8](#0-7) 
- `/v3/blocks/replay/*`, `/v3/blocks/simulate/*`, `/v3/transactions/simulate`, `/v3/contracts/fast-call-read/*` — all gated read/compute endpoints that can be used to force expensive block/transaction replays or contract calls.

Recovering the `auth_token` via a timing oracle allows an unauthenticated remote attacker to bypass authentication for these endpoints, enabling unauthorized triggering of block validation/broadcast and unbounded compute-heavy read requests (replay/simulate/fast-call-read). This satisfies the "High" bar (bounded compute DoS on a read endpoint, auth bypass) and edges toward "Critical" for the `/v2/blocks?broadcast=1` write path, since a leaked token converts an otherwise-protected write endpoint into an unauthenticated one.

### Likelihood Explanation
Exploitability depends on the network jitter between the attacker and node and on the length/entropy of the operator-configured `auth_token` (a plaintext string, per `docs/rpc/openapi.yaml` and `sample/conf/*-conf.toml`) [9](#0-8) . Because each of the 6 endpoints performs this same comparison independently, an attacker gets multiple independent timing oracles and can average out noise with many requests per guessed prefix byte. This raises practical likelihood versus a single endpoint, though it still requires statistical timing measurement over a network (CVSS AC:H in the referenced advisory reflects this same class of difficulty).

### Recommendation
Replace `auth_header != password` in all six handlers with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or `ring`/`hmac`-based comparison over a fixed-size digest of the token) that does not short-circuit on the first mismatched byte and does not leak matching-prefix length via timing.

### Proof of Concept
Not independently timed/measured in this analysis (would require live network timing measurements against a running node); the vulnerable code path is directly demonstrated at the cited call sites, where `auth_header != password` is a native Rust string/slice comparison, which is documented to be non-constant-time (early-exit on the first differing byte, and on length mismatch). Existing unit tests confirm the exact-match requirement of this comparison, e.g.: [10](#0-9)
