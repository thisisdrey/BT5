### Title
Unbounded array allocation from attacker-controlled length word in precompiled-contract ABI decoding causes node OutOfMemoryError / crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The CVE describes libzip's `_zip_read_eocd64` trusting a size field from a crafted ZIP header without validating it against the real amount of remaining data, so a downstream allocation (`_zip_cdir_grow`) is sized directly from attacker input and fails/aborts. The analogous pattern in java-tron is the helper array-extraction routines used by TVM precompiled contracts that decode "dynamic array" ABI parameters: `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java`.

### Finding Description
`extractBytes32Array`, `extractBytesArray` and `extractSigArray` read a 32-byte word from the caller-supplied `data` (interpreted as an EVM `DataWord[]`) and treat it as an element count: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three, `len` is obtained via `words[offset].intValueSafe()` and is used immediately to allocate `new byte[len][]` (or, for `extractBytes32Array`, to iterate `words[offset+i+1]`) **before** any check that `len` is consistent with the actual size of `words`/`data`. A caller only needs to supply a single 32-byte word containing a large value (e.g. close to `Integer.MAX_VALUE`) at the expected offset; there is no comparison of `len` against `words.length` or against the real remaining payload size at the point of allocation. This mirrors the libzip bug class: a size header is trusted for an allocation instead of being bounds-checked against the real data first, so a malformed/crafted input can force a huge memory allocation attempt.

The `isValidAbiEncoding` helper only validates that the *total* calldata length is a multiple of 32 and that the tail is consistent with a fixed item size; it does not cross-check the `len` value read inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray` against the actual number of words present, so a value that is wildly larger than the real array can still reach the allocation call: [4](#0-3) 

### Impact Explanation
A remote, unprivileged contract caller (any account that can trigger a contract invoking the affected precompiled contract, or directly call the precompile address via a transaction/`triggersmartcontract`) can supply calldata whose "array length" word is set to a very large value. This drives `new byte[len][]` with an attacker-chosen `len`, which can throw `OutOfMemoryError` inside TVM execution or otherwise exhaust heap memory for the executing node, potentially disrupting block/transaction processing for that node (denial of service), consistent with the reachable-impact bar of "node crash or halt."

### Likelihood Explanation
Reachability requires only a single signed transaction (or `TriggerConstantContract`/`TriggerContract` API call) that invokes the precompiled contract using these helpers with a crafted length word; no special privileges, validator status, or multi-step setup are needed, making likelihood moderate-to-high provided the specific precompile using `extractBytesArray`/`extractBytes32Array`/`extractSigArray` accepts attacker-controlled offsets for the length word (the codebase places no cross-validation between the declared `len` and the real remaining word count before allocating).

### Recommendation
Before allocating `bytesArray`/`bytes32Array` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate that `len` is non-negative and does not exceed a sane bound derived from `words.length` (or the actual remaining `data` size), returning an error/failure result instead of allocating when the declared count cannot be satisfied by the real payload — the same principle libzip's fix applied to EOCD64 record parsing.

### Proof of Concept
Construct calldata for a precompiled-contract call whose ABI-encoded "array length" word (the word read by `words[offset].intValueSafe()` at the `offset` used in `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) is set to a large 32-byte integer (e.g. `0x00000000000000000000000000000000000000000000000000000000FFFFFF` or `Integer.MAX_VALUE`), while the remainder of calldata is minimal/short. Sending this as a `TriggerSmartContract`/`TriggerConstantContract` call to the corresponding precompile address causes `new byte[len][]` to be executed with the attacker-chosen size at: [5](#0-4) 
before any bound check against the real data length, potentially throwing `OutOfMemoryError` and destabilizing the executing node.

**Uncertainty note:** Because the tool budget was exhausted before locating the exact precompile class (e.g. `BatchValidateSign` or similar) that invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, I could not fully confirm the precise calling contract, its precompile address, or whether an additional cross-check exists elsewhere in that specific caller that mitigates this before the array extraction is invoked.
