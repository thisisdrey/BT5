### Title
Unprivileged dust-transfer griefing fills a victim's deposit-token list to `MAX_TOKENS_PER_USER`, blocking them from depositing or receiving any further collateral types - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
The GitLab report (BIT-gitlab-2022-3285) is an unauthenticated bypass of an allowlist that lets an attacker deny service to legitimate users. The closest Metronome analog is the `depositTokensOfAccount` allowlist-style cap: any user can `transfer()` dust `DepositToken`s to a victim, each new token type calling `Pool.addToDepositTokensOfAccount(recipient)` until the victim's list hits `MAX_TOKENS_PER_USER = 30`, after which every mint/transfer of a new collateral type to that account reverts with `UserReachedMaxTokens`.

### Finding Description
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient previously held a zero balance, and `DepositToken._mint` does the same on deposits (`DepositToken.sol:469-489`, `DepositToken.sol:498-526`). `Pool` enforces `MAX_TOKENS_PER_USER = 30` and reverts with `UserReachedMaxTokens` once the per-account token list is full (`Pool.sol:32`, `Pool.sol:79`). The lock check `_revertIfLocked` is only applied to the *sender* (`DepositToken.sol:348-354`), so a recipient's consent or unlocked status is irrelevant — anyone can push arbitrary dust balances onto any address. An attacker deposits minimum amounts of each supported `DepositToken`, then transfers 1 wei of each to the victim until their list is full. Thereafter:

- `DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount` reverts `UserReachedMaxTokens` for any collateral type the victim doesn't already hold.
- `transfer`/`transferFrom`/`seize` of a new token type to the victim revert for the same reason.
- `unlockedBalanceOf`/`debtPositionOf` iterate the user's token list, but the concrete revert is the cap check, not gas.

### Impact Explanation
The victim is temporarily unable to onboard new collateral types or receive new `DepositToken`s — a temporary freezing of deposit functionality (liveness), matching the bug class of an unauthorized actor denying access to a protected function. If a liquidator's own list is full, `liquidate` → `seize` of a collateral type they don't hold also reverts, which a griefer can exploit by dust-filling known liquidation bots' lists to slow liquidations; the victim can self-recover by transferring the dust back out (removing tokens from the list when balances hit zero), so the freeze is temporary rather than permanent.

### Likelihood Explanation
Requires the pool to have enough distinct `DepositToken`s to reach 30 slots and the attacker to front real deposits plus deposit fees on each token — feasible on pools with many collaterals, impossible where fewer than ~30 tokens exist. Cost is linear in dust and bounded; recovery by the victim is cheap, which caps the impact at griefing-level DoS rather than fund loss.

### Recommendation
Have `addToDepositTokensOfAccount` skip (not revert) when the cap is reached and treat unlisted tokens as non-accounting, or remove the cap and bound `debtPositionOf` iteration differently; alternatively require `transfer` to only credit recipients whose list already contains the token or has capacity, e.g. let a full list evict zero-value dust entries automatically.

### Proof of Concept
Hardhat fork PoC sketch (deployed Pool/DepositTokens on Base):

```ts
// attacker: for each DepositToken dt[i] supported by pool:
//   dt[i].deposit(dust, attacker)            // pulls underlying via transferFrom
//   dt[i].transfer(victim, 1)                // adds dt[i] to victim list
// repeat until depositTokensOfAccount(victim).length == 30
// then: dt[j].connect(victim).deposit(amount, victim)
//   -> reverts UserReachedMaxTokens for any j not already in victim's list
// victim recovery: transfer each dust token out to free slots
```
