Audit Report

## Title
Relayer reward is paid out on `submit_delivery_receipt` without checking the on-chain `success` flag reported by the Ethereum event - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` decodes a `success: bool` field directly from the `InboundMessageDispatched` Solidity event log emitted by the Ethereum Gateway contract [1](#0-0) . `submit_delivery_receipt` verifies the proof, decodes the receipt, and forwards it unconditionally to `Self::process_delivery_receipt` [2](#0-1) , but the pallet's own source never references the `success` field again after decoding, and the `Error` enum has no delivery-failure variant.

## Finding Description
`submit_delivery_receipt` calls `T::Verifier::verify` to confirm the event log is authentic, then decodes it via `DeliveryReceipt::try_from`, and immediately calls `Self::process_delivery_receipt(relayer, receipt)` with no branch on `receipt.success` [3](#0-2) . Searching the entire pallet module for the token `success` returns no occurrences outside of the struct definition in the primitives crate — it is decoded into the `DeliveryReceipt` struct but the pallet logic that pays rewards and clears `PendingOrders` never inspects it. The `Error<T>` enum only guards against verification failure, invalid envelope, invalid gateway, invalid pending nonce, and reward-payment-transport failure — there is no `DeliveryFailed` or equivalent variant tied to `success == false` [4](#0-3) . Every exercised test path in the pallet and integration suite constructs `DeliveryReceipt` with `success: true` and asserts a successful payout [5](#0-4) [6](#0-5) ; there is no coverage of the `success: false` path, which is consistent with the field never being consulted before reward payout and `PendingOrder` removal.

## Impact Explanation
Because `success` is decoded but never checked, an honest relayer submitting a genuine but failed Ethereum dispatch event (`InboundMessageDispatched(nonce, topic, success=false, reward_address)`) would still trigger a full reward payout from `T::RewardPayment` and removal of the `PendingOrder`, as if the message had been successfully delivered. This is a duplicate/incorrect settlement issue — rewards are disbursed and delivery bookkeeping is finalized for work that did not actually complete, matching the "duplicate settlement or payout" category in the impact gate.

## Likelihood Explanation
The path only requires `ensure_signed` and a legitimately verifiable proof for a real Ethereum event [7](#0-6) . Any relayer relaying a genuine `success: false` event from the actual Gateway contract — no malicious behavior, privileged access, or compromised key required — is sufficient to trigger the improper payout.

## Recommendation
In `process_delivery_receipt`, explicitly branch on `receipt.success`. Only disburse the relayer reward when `success == true`; when `success == false`, settle/clear the `PendingOrder` through a distinct "delivery failed" path that does not pay out the reward tied to a failed dispatch.

## Proof of Concept
1. A message is queued and committed via `commit()`, producing a `PendingOrder` keyed by nonce with an attached fee.
2. On Ethereum, the Gateway contract processes the command but the dispatch fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits this genuine event log via `submit_delivery_receipt`; `T::Verifier::verify` succeeds since the event is real and provable, and `DeliveryReceipt::try_from` decodes `success: false`.
4. Since no code path in `process_delivery_receipt` inspects `receipt.success`, the relayer is paid the reward and the `PendingOrder` is removed exactly as in the passing tests that only use `success: true`, confirming the reward is settled for a failed delivery.

		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
