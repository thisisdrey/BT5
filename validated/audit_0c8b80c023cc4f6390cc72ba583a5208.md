### Title
`updateUsageForDelegated` decays bandwidth usage without refreshing `latestConsumeTime`, allowing repeated/inflated decay in resource-delegation accounting - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
`BandwidthProcessor.updateUsageForDelegated()` computes a new (decayed) `netUsage` for an account based on elapsed time since `latestConsumeTime`, sets the new usage on the capsule, but never updates `latestConsumeTime` to `now`, unlike the otherwise-symmetric `updateUsage()` method for the account's own consumption path and unlike the explicit `setLatestConsumeTime(now)` calls performed right after the decay in `UnDelegateResourceActuator.execute()`.

### Finding Description
`increase()`/`recover()` in `ResourceProcessor`/`BandwidthProcessor` implement a sliding-window decay of resource usage: given `lastUsage`, `lastTime`, and `now`, they compute how much of `lastUsage` should be decayed away based on the elapsed slots (`now - lastTime`) relative to `windowSize`. [1](#0-0) 

`updateUsageForDelegated()` calls this decay function using the account's current `latestConsumeTime`, writes the resulting (already-decayed) usage back onto the capsule via `setNetUsage(...)`, but never calls `ac.setLatestConsumeTime(now)`: [2](#0-1) 

Compare this to the sibling function `updateUsage()` in the same class, which performs the identical decay pattern for the account's own usage — it also fails to persist an updated `latestConsumeTime` for `netUsage` in that helper (the timestamp is instead updated later by the actual consumption callers such as `useAccountNet`), meaning `updateUsageForDelegated`/`updateUsage` are meant to be "preview" helpers whose caller is responsible for persisting the refreshed timestamp: [3](#0-2) 

This "preview only" contract is honored correctly in `UnDelegateResourceActuator.execute()`, which calls `bandwidthProcessor.updateUsageForDelegated(receiverCapsule)` and then explicitly sets `receiverCapsule.setLatestConsumeTime(now)` before persisting: [4](#0-3) 

However, `DelegateResourceActuator.validate()` calls the same `updateUsageForDelegated(ownerCapsule)` (and `EnergyProcessor.updateUsage(ownerCapsule)`) purely to compute `accountNetUsage`/`energyUsage` for a delegatable-balance check — it does not persist `ownerCapsule` at all in `validate()`, and the actual `execute()` path never re-runs decay or refreshes `latestConsumeTime` on the owner before persisting via `accountStore.put(ownerCapsule.createDbKey(), ownerCapsule)`: [5](#0-4) [6](#0-5) 

Because `validate()` and `execute()` run against separately-fetched `AccountCapsule` instances (`accountStore.get(...)` is called independently in each), any usage/timestamp mutation performed in `validate()` is discarded and never reaches disk — this differs from the Aloe bug (which is about a persisted state field going stale) mainly in that here the mutation is simply thrown away, so the actual on-chain `netUsage`/`latestConsumeTime` for the owner are left completely unrecovered/undecayed at delegation time. This means an owner who freezes/delegates bandwidth repeatedly can have their stored `netUsage` remain artificially high (not decayed) across delegate operations, since `execute()` performs no decay/update of the owner's own bandwidth usage or `latestConsumeTime` at all before persisting other field changes.

### Impact Explanation
If the owner's bandwidth `netUsage`/`latestConsumeTime` are never refreshed on the actual persisted `AccountCapsule` during `DelegateResourceActuator.execute()`, a subsequent read of the owner's usage window (e.g., by `BandwidthProcessor.useAccountNet`, `calculateGlobalNetLimit`-based checks, or the `getAccountLeftEnergyFromFreeze`/`getAccountNetUsageBalanceAndRestoreSeconds` queries used by delegation/undelegation accounting) will compute decay relative to a stale `latestConsumeTime`, potentially causing incorrect bandwidth accounting when usage transfers occur on `UnDelegateResource`/`DelegateResource`. This is a Medium-severity resource-accounting correctness issue rather than a fund-loss primitive, since TRX bandwidth/energy usage tracking errors affect resource availability/fee computation, not direct balance theft.

### Likelihood Explanation
Reachable directly by any account owner calling `DelegateResourceContract` (a standard broadcastable transaction type) repeatedly with intervening time gaps, requiring no special privilege — but the actual on-chain effect is limited because `validate()`'s mutations are discarded, so the exploitable window is narrow and the impact bounded to accounting drift rather than a clear fund-loss/freeze primitive.

### Recommendation
In `DelegateResourceActuator.execute()`, decay and persist the owner's `netUsage`/`energyUsage` and refresh `latestConsumeTime`/`latestConsumeTimeForEnergy` before applying delegation balance changes, mirroring the pattern already used in `UnDelegateResourceActuator.execute()`.

### Proof of Concept
1. Freeze TRX for bandwidth on account A, causing non-zero `netUsage` and `latestConsumeTime = T0`.
2. Call `DelegateResourceContract` from A at time `T1 > T0`; `validate()` internally calls `updateUsageForDelegated(ownerCapsule)` on a freshly-fetched capsule, computing decayed usage for the balance check, but this capsule/mutation is discarded.
3. `execute()` re-fetches the owner's `AccountCapsule` and only mutates `delegated_frozen_balance`/`frozen_balance_v2` fields before persisting — `netUsage`/`latestConsumeTime` remain at their pre-`T1` values in the persisted account.
4. Subsequent bandwidth checks for A use the stale `latestConsumeTime`, producing decay calculations inconsistent with the actual elapsed time since `T1`. [2](#0-1)

  protected long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }
