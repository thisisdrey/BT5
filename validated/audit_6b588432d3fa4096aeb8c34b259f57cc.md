### Title
CREATE (non-CREATE2) contract deployment can be permanently DoS'd via front-run account creation at the deterministic contract address - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
Top-level smart-contract deployment (`CreateSmartContract`) computes the new contract's address deterministically from the pending transaction's own ID and the owner address, before the transaction is confirmed. Because the transaction ID is visible in the mempool prior to inclusion, any unprivileged party can compute the future contract address off-chain and race to create/fund a normal account at that exact address first. When the legitimate deployment transaction is later executed, the actuator rejects it because the address is already occupied, causing the deployment to fail. This mirrors the referenced Wormhole bug class: a derived account address that can be pre-created/front-run before the legitimate owner's transaction lands, causing denial of service.

### Finding Description
`WalletUtil.generateContractAddress(Transaction trx)` derives the new contract address as `sha3omit12(txRawDataHash || ownerAddress)`, where `txRawDataHash` is simply the transaction's own ID (`TransactionCapsule(trx).getTransactionId()`): [1](#0-0) 

This transaction ID is fully determined the moment the deploying user signs and broadcasts the `CreateSmartContract` transaction — it does not depend on any future, unpredictable chain state (unlike an incrementing account nonce used by classic EVM `CREATE`). Consequently, once the transaction enters the mempool (or is even just known to an observer, e.g. via P2P propagation, a wallet, or the submitter accidentally sharing it), the future contract address is fully computable by any third party before the transaction is mined.

`VMActuator.create()`, which runs during `validate()`/`execute()` of every `CreateSmartContract` transaction, then unconditionally rejects deployment if any account already exists at the computed address: [2](#0-1) 

An attacker who has observed the pending deployment transaction can submit an ordinary `TransferContract` (sending even 1 SUN) to the precomputed `contractAddress` and get it included in an earlier or the same block (e.g., by paying more bandwidth/priority, or simply because transaction ordering within a block is not guaranteed to favor the original submitter). This creates a normal `AccountCapsule` at that address via `RepositoryImpl.createAccount`: [3](#0-2) 

Once that account exists, the legitimate `CreateSmartContract` transaction from the original deployer will always hit the `rootRepository.getAccount(contractAddress) != null` branch and throw `ContractValidateException`, failing the deployment (the transaction fee/bandwidth for the attempt is still consumed by the victim, and the specific transaction can never succeed since its ID — hence its target address — is fixed).

This is analogous to the underlying Wormhole issue described in the report: a deterministically-derived account address, known before the legitimate creation transaction is finalized, can be pre-created by an unrelated party, denying/blocking the intended account/contract creation.

### Impact Explanation
Any user attempting to deploy a smart contract via `CreateSmartContract` can be griefed by an attacker who front-runs the exact predicted contract address with a trivial value transfer. The victim's specific signed transaction becomes permanently unusable (must be re-created/re-signed with different `timestamp`/`expiration`/`ref_block` fields to get a new transaction ID and therefore a new target address), wasting bandwidth/energy fees already paid and creating a reliable, repeatable denial-of-service primitive against targeted contract deployments (e.g., disrupting time-sensitive protocol launches, airdrops, or CTF/competition deployments where a specific deployment must land in a specific block or before a deadline).

### Likelihood Explanation
High feasibility: computing the target address requires only knowledge of the pending transaction's raw data (owner address + tx hash), both of which are visible to anyone observing the transaction in the P2P network/mempool prior to confirmation, or which can be predicted if the deployer’s tooling is predictable. The griefing transaction itself is a trivial, cheap `TransferContract`. No special privileges are required by the attacker.

### Recommendation
Avoid deriving the initial `CREATE`-style contract address purely from transaction-visible-before-confirmation data such as the raw transaction hash. Consider deriving the address using additional non-observable-in-advance entropy (e.g., combine with the owner's on-chain account nonce/sequence at execution time, or persist enough contract metadata in the account so a pre-funded/pre-created account does not block legitimate creation, mirroring the CREATE2 collision-handling logic already present in `Program.createContractImpl` (`isContractExist`/`existingAccount` branch) that gracefully takes over pre-existing non-contract accounts instead of unconditionally failing).

### Proof of Concept
1. Alice constructs and signs a `CreateSmartContract` transaction `T` (this fixes `T`'s transaction ID / raw data hash).
2. Before `T` is confirmed, Bob observes `T` (e.g., via mempool broadcast) and computes `contractAddress = WalletUtil.generateContractAddress(T)`.
3. Bob broadcasts a cheap `TransferContract` sending 1 SUN to `contractAddress`, and it gets included in a block prior to (or in the same block ordered before) `T`.
4. When `T` is executed, `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException`, permanently failing Alice's deployment transaction `T` (she must sign a brand-new transaction with different raw data to try again).

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
