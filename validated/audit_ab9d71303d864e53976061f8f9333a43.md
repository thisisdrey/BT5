### Title
TOCTOU race window in ConnectionState.Decrypt allows duplicate decryption/delivery of a replayed ciphertext - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` releases `cs.decryptLock` between `cs.window.Check` and `cs.dKey.DecryptDanger`, and re-acquires it only around the final `cs.window.Update` call. Two goroutines racing on the same `messageCounter` can both pass `Check`, both successfully run `DecryptDanger`, and both return non-nil plaintext to the caller before either calls `Update`, since `Update` (the only call that marks the counter as consumed) happens strictly after decryption.

### Finding Description
The relevant code is: [1](#0-0) 

`Check` (bits.go) is read-only — it inspects the window state but does not mutate it, so calling it twice in parallel with the same `messageCounter` returns `true` both times as long as the counter has not yet been marked via `Update`: [2](#0-1) 

Only `Update` mutates the bitmap and returns `false` for a duplicate: [3](#0-2) 

Because `decryptLock` is dropped after `Check` and not held across `DecryptDanger`, the sequence `Check→Check→DecryptDanger→DecryptDanger→Update→Update` is possible under a race: goroutine A calls `Check(counter)` → true, releases lock; goroutine B calls `Check(counter)` → true (window not yet updated), releases lock; both A and B independently call `cs.dKey.DecryptDanger(...)` with the same `messageCounter` (AES-GCM/ChaCha20-Poly1305 decryption with that nonce is deterministic and stateless on the cipher object, so both succeed and produce the same plaintext); both then acquire the lock for `Update`, only one of which returns `true`, but by that point both plaintexts have already been computed and returned from `Decrypt` to whatever code path called it (e.g. packet handling in `outside.go` → `handleOutsideMessagePacket`, firewall check, tun write) — the rejection from `Update` for the loser only prevents that call from also succeeding, it does not un-deliver the payload that already happened on the winning call, and crucially **both** calls already got a decrypted payload before `Update` runs at all in this ordering, since `Update` is called after `DecryptDanger` returns in each goroutine independently.

This does not require compromising cryptographic keys or breaking AEAD authentication — the attacker only needs to cause the same authenticated ciphertext to be processed by two concurrent `Decrypt` invocations on the same `ConnectionState` (e.g., replaying a captured packet at the moment the original is mid-flight, or triggering two receive paths to race), which is a plausible unprivileged network-timing condition, not a crypto break.

### Impact Explanation
A single valid (previously-sent) ciphertext byte stream can be delivered twice to the tun device / firewall conntrack layer, defeating the intended single-delivery guarantee of the anti-replay window. This matches the "traffic decryption/forgery/replay" and "firewall bypass" bounty categories: firewall/conntrack logic and higher-level protocols that assume per-packet uniqueness (e.g. stateful rules, at-most-once semantics) can be fooled into processing a duplicated packet as if it were two distinct packets. It does not allow decrypting new ciphertext without the key or forging unauthenticated data — it is a duplicate-delivery/local ordering bug rather than a cryptographic break.

### Likelihood Explanation
Exploitability depends on the packet processing model: if each `ConnectionState`'s inbound packets are always processed by a single dedicated goroutine (serialized per hostinfo/tunnel), this race is unreachable in practice. In this repo's multi-routine design (`nebula--017`'s `outside.go` reads with multiple listener routines dispatched per-connection), whether two different reader goroutines can be dispatched concurrently for the *same* `ConnectionState`/tunnel needs confirmation from the dispatch code; I was unable to fully verify the goroutine-to-tunnel assignment invariant in the available `outside.go` excerpt due to iteration limits. If routine affinity strictly binds one tunnel to one goroutine, this finding's likelihood is low/theoretical; if any code path (e.g. relay processing via `VerifyRelay`, which has the identical pattern) allows concurrent calls to `Decrypt`/`VerifyRelay` for one `ConnectionState`, the race is a straightforward, repeatable timing race reproducible under `go test -race`.

### Recommendation
Hold `cs.decryptLock` for the entire duration of `Check → DecryptDanger → Update`, or perform an atomic "check-and-reserve" step (e.g., tentatively mark the counter as consumed inside the same critical section as `Check`, and roll back only on decryption failure) so that no other goroutine can pass `Check` for the same counter while a decryption is in flight.

### Proof of Concept
Add a test in `connection_state_test.go`:
1. Build a `ConnectionState` with a real cipher via `newConnectionStateFromResult` (or equivalent test helper already used in `connection_state_test.go`).
2. Encrypt one packet at a known `messageCounter` with `cs.eKey`.
3. Launch two goroutines that both call `cs.Decrypt(l, messageCounter, ...)` with the same ciphertext, synchronized via a `sync.WaitGroup`/barrier so both goroutines call `Check` before either calls `DecryptDanger` (e.g. by adding a small `sync.WaitGroup` release inside a mocked/instrumented path, or by relying on `-race` combined with tight timing loops repeated many iterations).
4. Assert: at most one goroutine returns a non-nil `[]byte` plaintext; run under `go test -race` and repeat N iterations to catch the window statistically, since it is a timing race and not deterministically triggered in every run.

Note: this PoC characterizes a real code-level TOCTOU gap in `ConnectionState.Decrypt`/`VerifyRelay`; confirming full exploitability from unprivileged attacker-sent UDP requires verifying (outside what I could confirm here) whether concurrent goroutines can ever be dispatched against the same `ConnectionState` in this version's packet-reading architecture.

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
