Based on my investigation, I found a reachable analog in the relay/hostmap subsystem of Nebula's core VPN protocol logic.

### Title
Relay entry permanently deleted on a single lookup failure, causing loss of the only remaining path to a peer - (File: `inside.go`, `hostmap.go`)

### Summary
The report describes reward-token structs being fully deleted on removal, which permanently destroys any outstanding claimable state instead of putting the token into a safe "claim-only" mode. The equivalent pattern in Nebula is `RelayState.DeleteRelay`, which unconditionally and permanently removes a relay's VPN address from `hostinfo.relayState.relays` the moment a single relay lookup fails, with no "disabled/retry" intermediate state to preserve the ability to re-use or re-establish that relay path later.

### Finding Description
When `Interface.sendNoMetrics` cannot reach a peer directly (no valid remote address) it falls back to relaying: [1](#0-0) 

For each candidate relay IP it calls `hm.QueryVpnAddrsRelayFor`; on *any* error from that lookup, it immediately calls `hostinfo.relayState.DeleteRelay(relayIP)` and moves on, permanently forgetting the relay: [2](#0-1) 

`DeleteRelay` performs an unconditional, permanent removal from the `relays` slice — there is no "retry later" or "disestablished but still tracked" state analogous to the reward-token report's recommended "claim-only" mode. Compare this with the more careful state machine elsewhere in the same subsystem, where relay entries are demoted to `Disestablished` and can be revived (`UpdateRelayForByIpState`, `handleCreateRelayRequest`'s `Disestablished` branch re-marks the relay `Established`): [3](#0-2) [4](#0-3) 

The `sendNoMetrics` path bypasses that safer disestablish/re-establish flow entirely and hard-deletes the entry on the first transient failure of `QueryVpnAddrsRelayFor` — e.g. a race where the relay's hostinfo is mid-promotion, has just been replaced as primary, or its remote address isn't valid yet. This is the same general class of transient-failure race the project has had to patch repeatedly in this exact area (see CHANGELOG entries for "Fix a race in relay state handling" (#1753), "Don't build new relay state on a tunnel that was just discarded" (#1796), and the dedicated regression test `TestRelayHandshakeOverDisestablishedEntry`, which documents an almost identical "first transmit deletes its only relay and the tunnel is born transmit-dead" bug that was fixed for the `Disestablished` state): [5](#0-4) [6](#0-5) 

That fix (#1805) only covers the `handleCreateRelayRequest`/`Disestablished` re-establishment path. The `DeleteRelay` call in `sendNoMetrics` is a separate code path that still performs an outright, non-recoverable removal rather than a state demotion, exactly mirroring the reward-token report's root cause: "remove the whole struct" instead of "demote to an inert/claim-only state that preserves recoverability."

### Impact Explanation
If the deleted relay was the only viable path to a peer (direct remote not yet valid, e.g. mid-handshake/NAT punch), removing it from `relays` permanently strands the tunnel: no further attempt will be made against that relay for this hostinfo unless a brand-new relay is established from scratch (new `AddRelay`/`CreateRelayRequest` cycle), which normally only happens on a fresh handshake. This can silently break traffic (remote peer receives nothing) — a remote state poisoning / connectivity-loss impact consistent with what the Validate rules classify as acceptable ("remote state poisoning").

### Likelihood Explanation
This can be triggered without any CA-signed certificate by an already-connected peer through ordinary protocol churn — re-handshakes, tunnel closes/promotions on either end of the relay chain — since `QueryVpnAddrsRelayFor`'s failure conditions depend on hostmap state that legitimate peers can perturb during normal operation (as demonstrated by the closely related, already-patched `TestRelayHandshakeOverDisestablishedEntry` scenario in the same code path).

### Recommendation
Do not call `DeleteRelay` on a single transient lookup failure in `sendNoMetrics`. Instead, mirror the existing `Disestablished`/re-establish pattern used elsewhere in `relay_manager.go`: mark the relay entry as `Disestablished` (keeping it in `relayForByAddr`/`relayForByIdx` and `relays`) so a subsequent `CreateRelayRequest` or retry can revive it, only removing the entry outright once the hostinfo/relay is confirmed permanently gone (e.g., via `unlockedDeleteHostInfo`'s existing disestablish-on-final-teardown logic).

### Proof of Concept
Not independently reproduced beyond the code-path analysis above; I was unable to fully retrieve `HostMap.QueryVpnAddrsRelayFor`'s complete implementation and enumerate every condition under which it returns an error, so I cannot state with certainty how easily a remote peer can trigger the specific error branch that reaches the `DeleteRelay` call in `inside.go`. This should be validated with a targeted e2e test analogous to `TestRelayHandshakeOverDisestablishedEntry` but exercising the `sendNoMetrics` relay-selection loop directly.

func (rs *RelayState) DeleteRelay(ip netip.Addr) {
	rs.Lock()
	defer rs.Unlock()
	for idx, val := range rs.relays {
		if val == ip {
			rs.relays = append(rs.relays[:idx], rs.relays[idx+1:]...)
			return
		}
	}
}
