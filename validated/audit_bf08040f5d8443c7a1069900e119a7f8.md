### Title
Floating-point (double) precision loss in the default (non-hardened) TRX/TRC10 Bancor-style exchange pricing formula allows swap-output manipulation and pool draining - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionActuator` (reachable by any signed `ExchangeTransactionContract` broadcast from an unprivileged account) computes the "another token" amount received from a swap via `ExchangeCapsule.transaction()`, which by default (`allowHarden()` == false unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal is enabled by the committee) uses `ExchangeProcessor`, a Bancor-formula implementation built entirely on Java `double` arithmetic and `Math.pow`/`StrictMath.pow` with an exponent of `2000.0`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` implement the constant-supply Bancor relay-token formula:
```
issuedSupply = -supply * (1 - (1 + quant/newBalance)^0.0005)
exchangeBalance = balance * ((1 + supplyQuant/supply)^2000 - 1)
```
Both use IEEE-754 `double` values and `pow()` calls, then truncate to `long` via `(long) issuedSupply` / `(long) exchangeBalance`. [4](#0-3) 

Because the second stage raises `(1 + supplyQuant/supply)` to the power `2000`, any tiny floating-point rounding error in the base (on the order of `1e-16` from double precision) is amplified multiplicatively across 2000 factors, producing a materially different (and unpredictable, in either direction) `exchangeBalance` result compared to the mathematically exact value. Since `supply` (`1_000_000_000_000_000_000L`) and account balances can be arbitrarily large TRX/TRC10 amounts chosen by the caller (subject only to `getExchangeBalanceLimit()`), an attacker fully controls `sellTokenQuant`, `firstTokenBalance`, and `secondTokenBalance` (by first creating their own exchange with `ExchangeCreateContract`, then injecting/withdrawing to tune the ratio, or simply choosing quantities that hit floating-point edge cases) and can search off-chain for input combinations that make the double-precision computation return a payout larger than the exact Bancor-curve value would allow, at the expense of the pool's real reserves.

The project's own author(s) acknowledged this exact defect: a parallel `SafeExchangeProcessor` was added, which performs the identical formula with `BigDecimal` (18-digit scale) instead of raw doubles, is gated behind the `allowHarden()` / `ALLOW_HARDEN_EXCHANGE_CALCULATION` dynamic-property proposal, and is *not* the default path. [5](#0-4) [6](#0-5) 

The actuator's own test suite documents that the strict/non-strict double paths and the hardened BigDecimal path produce *different* results for the same inputs:
```
Assert.assertNotEquals(anotherTokenQuant, result);   // non-strict vs strict double differ
Assert.assertEquals(safeResult, result);              // strict double happens to equal hardened here
``` [7](#0-6) 

This confirms the double-based formula is numerically unstable and inconsistent, and that the fix (`SafeExchangeProcessor`) exists in code but is not enabled unless a chain-wide committee proposal turns on `allowHardenExchangeCalculation`. Until/unless that proposal is passed on a given network, every `ExchangeTransactionContract` (a market swap reachable by any account with tokens, exactly analogous to the AMM/lending pricing-formula bug class implicated in the UniLend incident) is settled using the unsafe double-based curve.

### Impact Explanation
`ExchangeTransactionActuator.execute()` directly credits `anotherTokenQuant` (the actuator-computed output) to the trader's account and debits the pool's `ExchangeCapsule` balances by the same amount, with no independent sanity check that the output is consistent with the exact Bancor curve. [8](#0-7) 
An attacker who can craft (or search for) input quantities where the double-precision `pow` computation diverges upward from the true value can extract more of the counter-asset than the pool's true invariant should allow, draining real TRX/TRC10 reserves supplied by the pool creator (and any other users who injected liquidity) — i.e., unbacked value extraction / theft of pool funds, matching the "Medium" severity, fund-loss class of the UniLend report.

### Likelihood Explanation
The attack requires no special privilege — any account holding TRX or the relevant TRC10 token can call `ExchangeTransactionContract` (and can first create their own pool via `ExchangeCreateContract` and tune it via `ExchangeInjectContract`/`ExchangeWithdrawContract`, both of which are also open to the pool creator). Finding an exploitable floating-point divergence requires numerical experimentation but is a search problem over a public, deterministic formula — feasible offline. The barrier is only that this legacy Bancor-exchange feature is largely superseded by the newer `MarketSellAssetContract` order-book system in modern TRON usage, but the actuator and RPC endpoints (`ExchangeTransaction`, `ExchangeInject`, `ExchangeWithdraw`, `ExchangeCreate`) remain live and callable in the protobuf/Wallet API. [9](#0-8) 

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based) the unconditional implementation for all exchange transactions, injects, and withdraws, removing the `allowHarden()`/committee-proposal gate, or at minimum enable `ALLOW_HARDEN_EXCHANGE_CALCULATION` by default on all networks. Additionally, add a post-computation invariant check in `ExchangeCapsule.transaction()` (e.g., verifying the new `firstTokenBalance * secondTokenBalance` product has not decreased beyond the expected relay-token-implied bound) as defense in depth against any residual precision error.

### Proof of Concept
Conceptual (cannot be executed without a live chain, but derivable from the code):
1. Attacker calls `ExchangeCreateContract` to create a TRX/TRC10 pool with attacker-chosen `firstTokenBalance`/`secondTokenBalance`.
2. Attacker calls `ExchangeInjectContract`/`ExchangeWithdrawContract` (creator-only) to tune the pool ratio to a magnitude where `(1 + supplyQuant/supply)^2000` in `ExchangeProcessor.exchangeFromSupply` is most sensitive to double rounding (e.g., `supplyQuant` chosen so that `supplyQuant/supply` sits near a power-of-two boundary in IEEE-754 representation).
3. Attacker (or a colluding second account) calls `ExchangeTransactionContract` with a `sellTokenQuantity` calibrated so `exchangeToSupply`'s truncation (`(long) issuedSupply`) and `exchangeFromSupply`'s `pow(base, 2000)` amplify the rounding error, yielding `anotherTokenQuant` larger than the exact Bancor-curve value.
4. `ExchangeTransactionActuator.execute()` credits this amount unconditionally, extracting excess reserve tokens from the pool.
5. Repeating with `ExchangeProcessorTest.testStrictMath`-style differing input sets (which the test itself shows diverge between strict/non-strict/hardened paths) demonstrates the formula is not deterministic/exact, supporting exploitability at scale. [10](#0-9)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
