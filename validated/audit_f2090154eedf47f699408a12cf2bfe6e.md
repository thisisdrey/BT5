### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer Capability Delegation - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary

`SignerCapabilityOfferProofChallengeV2`, the signed proof challenge used by `offer_signer_capability`, omits the `chain_id` field that its sibling struct `RotationCapabilityOfferProofChallengeV2` explicitly includes. A valid signer-capability-offer signature produced on one Aptos chain (e.g., testnet) can be replayed verbatim on any other Aptos chain (e.g., mainnet) where the same account address exists at the same sequence number, granting an unauthorized party a `SignerCapability` over the victim's mainnet account.

### Finding Description

The framework defines two proof-challenge structs for capability delegation:

**`RotationCapabilityOfferProofChallengeV2`** — correctly includes `chain_id`: [1](#0-0) 

**`SignerCapabilityOfferProofChallengeV2`** — **missing `chain_id`**: [2](#0-1) 

The comment on `RotationCapabilityOfferProofChallengeV2` explicitly states the rationale: *"This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message."* The same protection was not applied to `SignerCapabilityOfferProofChallengeV2`.

`offer_signer_capability` constructs the proof challenge without `chain_id`: [3](#0-2) 

Compare with `offer_rotation_capability`, which correctly binds to the chain: [4](#0-3) 

The signed message for `offer_signer_capability` is therefore: `BCS(struct_tag || sequence_number || source_address || recipient_address)`. Because `chain_id` is absent, the same bytes are valid on every Aptos chain that shares the same account address and sequence number.

### Impact Explanation

`SignerCapability` allows its holder to call `create_authorized_signer`, which produces a full `signer` for the delegating account: [5](#0-4) 

With that signer, the attacker can execute arbitrary transactions on behalf of the victim — transferring APT, fungible assets, or any other on-chain resource. This constitutes **direct theft of user-controlled on-chain assets**.

### Likelihood Explanation

The precondition is that the victim's account exists on two Aptos chains (e.g., testnet and mainnet) at the same address with the same sequence number at the moment the testnet signature is captured. This is common: accounts are often created on testnet before mainnet, and sequence numbers reset or match at low values. An attacker who observes a testnet `offer_signer_capability` transaction (all transactions are public) can immediately replay the extracted `signer_capability_sig_bytes` on mainnet with an identical call, since the on-chain proof challenge reconstruction will produce the same bytes.

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2`, mirroring `RotationCapabilityOfferProofChallengeV2`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // ADD THIS
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

And populate it in `offer_signer_capability`:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),   // ADD THIS
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

### Proof of Concept

1. Alice has account `addr_A` on both testnet (chain_id=2) and mainnet (chain_id=1), both at sequence number 0.
2. On testnet, Alice calls `offer_signer_capability(alice, sig, 0, alice_pk, bob_addr)`. The signed bytes are `BCS(0x1::account::SignerCapabilityOfferProofChallengeV2 || seq=0 || addr_A || bob_addr)` — no chain_id.
3. Bob (or any observer) extracts `sig` from the testnet transaction.
4. Bob submits the identical call on **mainnet**: `offer_signer_capability(alice_addr_as_sender, sig, 0, alice_pk, bob_addr)`. The VM reconstructs the same proof challenge bytes (same struct tag, same seq=0, same `addr_A`, same `bob_addr`) and the signature verifies.
5. Alice's mainnet `Account.signer_capability_offer.for` is now set to `bob_addr`.
6. Bob calls `create_authorized_signer(&bob, addr_A)` on mainnet, receives a signer for Alice's mainnet account, and transfers all her APT.
