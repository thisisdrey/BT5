### Title
Heap buffer over-read in ijar's ZIP central directory parser due to missing length validation - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in Bazel's `ijar` tool parses ZIP/JAR central directory records without validating that the attacker-controlled `file_name_length`, `extra_field_length`, and `file_comment_length` fields fit within the bytes actually remaining in the mapped input file, unlike the sibling routine `ProcessLocalFileEntry`, which explicitly guards every variable-length read with `EnsureRemaining()`.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` reads the local file header and, before touching any variable-length field, calls `EnsureRemaining(file_name_length_, "file_name")` and `EnsureRemaining(extra_field_length_, "extra_field")` to make sure the mmap'ed file actually contains that many bytes. [1](#0-0) 

`InputZipFile::ProcessCentralDirEntry`, which is used to walk the ZIP central directory, has no such checks. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight from attacker-supplied bytes and then unconditionally advances the cursor and `memcpy`s `file_name_length` bytes out of `p`, and walks `extra_p` forward by each entry's untrusted `data_size`: [2](#0-1) 

The function's own comment asserts an invariant that "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but that invariant only holds for well-formed archives, and nothing in the code enforces it. A central directory record whose `file_name_length`/`extra_field_length`/`file_comment_length` values are inflated beyond the actual remaining bytes of the mmap'ed input causes:
- `memcpy(filename, p, len)` to read out-of-bounds heap/mmap memory into the `filename` buffer used later for `processor->Accept()`/`processor->Process()`.
- The extra-field walk (`while (extra_p != p)`) to dereference `get_u2le`/`get_u8le` at attacker-chosen offsets that may lie past the mapped region.

This is the same bug class as CVE-2019-9778 (LibreDWG's `dwg_dxf_LTYPE`): a record-parsing routine trusts length fields from untrusted input and reads/copies memory beyond the bounds of the buffer that holds the parsed structure, with no bounds check comparable to the one present in a sibling parsing routine in the same file.

### Impact Explanation
`ijar` is invoked by Bazel to strip interface jars from any `.jar`/`.zip`/`.aar` file used as a Java compile-time dependency, including archives fetched via `http_jar`/`http_archive` and pinned with a `sha256`/`integrity` checksum. The checksum only guarantees byte-for-byte reproducibility of whatever content was originally published — it does nothing to guarantee the ZIP structure is well-formed. An attacker who controls the published artifact (e.g., a malicious or compromised upstream release) can therefore ship a byte-identical, hash-matching but deliberately malformed central directory that triggers the over-read whenever any build processes that dependency through ijar, i.e., on every build, with default flags, no opt-in required. The resulting out-of-bounds read can leak adjacent process memory into the `filename`/attribute data used to build the output interface jar (or crash the ijar helper process on an unmapped page).

### Likelihood Explanation
Any project depending on an externally-fetched `.jar` (via `http_jar`, `http_archive` + `java_import`, or similar) routes that artifact through `ijar`'s ZIP reader as an ordinary part of Java compilation actions — no special configuration, flags, or root-repo Starlark trust is required. The bug is deterministically reachable by simply crafting one corrupted central directory entry in an otherwise valid ZIP/JAR.

### Recommendation
Add the same `EnsureRemaining()` bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before reading/copying `file_name`, `extra_fields`, and `file_comment`, and validate that `extra_field_length`-bounded sub-entries (`header_id`/`data_size`) never advance `extra_p` past `p`'s already-validated bound.

### Proof of Concept
Construct a minimal ZIP/JAR with:
1. A valid End-Of-Central-Directory record.
2. A single central directory entry (`CENTRAL_FILE_HEADER_SIGNATURE`) whose `file_name_length` (or `extra_field_length`/`file_comment_length`) field is set to a value larger than the number of bytes actually remaining in the file.

Feeding this file to `ijar` (e.g. via `ZipExtractor::Create(...)->ProcessAll()`, which drives `InputZipFile::ProcessNext -> ProcessCentralDirEntry`) causes `memcpy(filename, p, len)` in `ProcessCentralDirEntry` (`third_party/ijar/zip.cc:520`) to read past the end of the mmap'ed input file. A JUnit/`BuildIntegrationTestCase`-style reproduction should build a `java_library` that depends on such a crafted jar via `java_import`/`http_jar` and observe the ijar helper process crash or produce filename bytes derived from adjacent heap memory. bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
