### Title
Dusted DepositToken with a reverting oracle permanently bricks victim's `debtPositionOf`, freezing all withdrawals, transfers, and liquidations - (contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
Any whitelisted `DepositToken` can be dust-transferred to a victim, which silently appends it to the victim's `depositTokensOfAccount` list in `Pool`. `Pool.depositOf()` then iterates the whole list and calls `masterOracle.quoteTokenToUsd(underlying, balance)` for every entry — if that token's oracle reverts (e.g., a stale pull oracle reverting with `invalid-token-price`, as the repo's own E2E tests demonstrate), the victim's `debtPositionOf()`/`unlockedBalanceOf()` revert unconditionally. Because the victim cannot even transfer the dust away (`transfer` → `_revertIfLocked` → `unlockedBalanceOf` → `debtPositionOf` → reverts), all of the victim's collateral and debt operations are DoS'd. This is the Metronome analog of CVE-2019-12995: a mishandled/unsanitized token entry crashes the core position-evaluation path (availability loss).

### Finding Description
`DepositToken._transfer` adds the token to the recipient's per-account list whenever the recipient's prior balance is zero (`DepositToken.sol:518-520`), calling `pool.addToDepositTokensOfAccount(recipient_)`. There is no oracle sanity check and no opt-in — an attacker who deposits any amount of a whitelisted collateral can then `transfer(1, victim)` to inject that `DepositToken` into the victim's accounting list.

`Pool.depositOf` then unconditionally iterates every entry and quotes each token's underlying through `masterOracle` (`Pool.sol:279-287`). A single entry whose oracle reverts poisons the entire view:

```solidity
// contracts/Pool.sol:279-287
for (uint256 i; i < _length; ++i) {
    IDepositToken _depositToken = IDepositToken(depositTokensOfAccount.at(account_, i));
    uint256 _amountInUsd = _masterOracle.quoteTokenToUsd(
        address(_depositToken.underlying()),
        _depositToken.balanceOf(account_)
    );
    ...
}
```

Reverting oracles are a realistic deployed configuration: the repo's own tests show `pool.debtPositionOf` reverting with `invalid-token-price` until the pull price provider is updated (`test/E2E.hemi.pullOracle.test.ts:113-114`), i.e., `quoteTokenToUsd` does revert for stale/unpushed feeds.

Crucially, the victim cannot self-heal:
- `DepositToken.transfer` → `_revertIfLocked` → `unlockedBalanceOf` → `pool.debtPositionOf` → reverts (`DepositToken.sol:348-353, 383-398`).
- `DepositToken.withdraw`/`_withdraw` on any collateral → same `_revertIfLocked` chain → reverts (`DepositToken.sol:406-412`).
- `DebtToken.repay`/`issue` and `Pool.liquidate` all call `debtPositionOf`/`debtOf`, which revert (`Pool.sol:227-237, 559`).

The attacker's only cost is a dust deposit in an oracle-broken collateral token.

### Impact Explanation
Temporary-to-permanent freezing of user funds: while the poisoned token's oracle reverts, the victim cannot withdraw any collateral, transfer, repay debt, or issue — and their position cannot be liquidated, which additionally exposes the pool to bad debt if the victim goes underwater during the outage. The freeze is permanent if the underlying feed is abandoned; otherwise it lasts for the duration of the oracle outage, with no victim-side escape hatch. This meets the "temporary freezing of funds" / liveness-impact bar and mirrors the CVE's availability loss from a mishandled token.

### Likelihood Explanation
Likelihood is moderate: it requires a whitelisted `DepositToken` whose oracle path can revert (stale pull oracle, misconfigured `MasterOracle` route, feed deprecation), plus a victim to dust. No privileged role, governance action, or trusted-relayer assumption is needed — the dust injection uses only the public `DepositToken.transfer` entry point. All modifiers (`nonReentrant`, `whenNotShutdown`, `onlyIfAdditionWillNotReachMaxTokens`) do not prevent it; the only mitigation is the per-account token cap, which the attacker stays under by adding a single token.

### Recommendation
- In `Pool.depositOf`/`debtOf`, wrap each `quoteTokenToUsd` call in a `try/catch` and skip entries whose oracle reverts (or treat as 0 with a dedicated fallback), so one broken collateral cannot brick the whole account.
- Alternatively, gate `addToDepositTokensOfAccount` additions on an explicit user opt-in or a minimum meaningful balance, and/or provide a `Pool.removeDepositTokenFromAccount(account, token)` escape that lets a user purge a dust entry whose oracle reverts.

### Proof of Concept
Foundry fork outline (deterministic; uses a stub oracle only to reproduce the deployed stale-feed revert observed in `E2E.hemi.pullOracle.test.ts`):

```solidity
// Fork test — pool, msdWETH (healthy oracle), msdBROKEN (oracle reverts)
address victim = makeAddr("victim");

// 1. Victim deposits WETH collateral normally
deal(WETH, victim, 10 ether);
vm.startPrank(victim);
IERC20(WETH).approve(msdWETH, 10 ether);
msdWETH.deposit(10 ether, victim);
assertGt(msdWETH.unlockedBalanceOf(victim), 0); // works

// 2. Attacker deposits dust of oracle-broken collateral, transfers to victim
deal(BROKEN_UNDERLYING, attacker, 1 ether);
vm.startPrank(attacker);
IERC20(BROKEN_UNDERLYING).approve(msdBROKEN, 1 ether);
msdBROKEN.deposit(1 ether, attacker);
msdBROKEN.transfer(victim, 1); // adds msdBROKEN to victim's list (DepositToken.sol:518)
vm.stopPrank();

// 3. Oracle feed for BROKEN_UNDERLYING goes stale / reverts
//    (equivalent to real 'invalid-token-price' revert on expired pull oracle)
MockRevertingOracle.forceRevert(BROKEN_UNDERLYING);

// 4. Victim is fully bricked — cannot even eject the dust
vm.startPrank(victim);
vm.expectRevert("invalid-token-price");
msdWETH.withdraw(1 ether, victim);
vm.expectRevert("invalid-token-price");
msdBROKEN.transfer(attacker, 1); // _revertIfLocked -> unlockedBalanceOf -> reverts

// 5. Position is also unliquidatable
vm.expectRevert("invalid-token-price");
pool.debtPositionOf(victim);
```

Unverified assumption: `MasterOracle.quoteTokenToUsd` reverts (rather than returning 0) for an unconfigured/stale token — supported by the repo's pull-oracle tests but the `MasterOracle` implementation itself is external to `contracts/`; if it returns 0 instead of reverting, this analog reduces to zero-value accounting and the finding does not hold.
