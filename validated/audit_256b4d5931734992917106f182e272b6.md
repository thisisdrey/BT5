### Title
Stale in-memory registry snapshot in `collateral-add` lets a reentrant `debt-add-scaled` call be silently overwritten, desyncing `mask` from the `debt` map - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`collateral-add` reads the account's registry `entry`/`mask` into local `let` bindings, then performs an external token transfer via `receive-tokens` (calling the attacker-supplied `<ft-trait>`), and only afterward calls `insert updated-entry` to persist the mask. [1](#0-0)  If a malicious `ft-trait`'s `transfer` implementation reenters the market and successfully triggers `debt-add-scaled` for the same account before `receive-tokens` returns, that nested call correctly updates `registry.mask` with the debt bit set and adds a row to the `debt` map. [2](#0-1)  However, `collateral-add`'s own `updated-entry` was computed from the pre-reentrancy mask, so its subsequent `(insert updated-entry)` overwrites `registry` and clobbers the debt bit the nested call just set, while the `debt` map row remains. [3](#0-2) 

### Finding Description
`collateral-add`'s `let` bindings capture `entry`, `mask`, and `updated-mask` before any external call occurs: [4](#0-3) . The `add-user-collateral` map-set (crediting the `collateral` map for the deposited asset) also executes eagerly during binding evaluation, before `check-impl-auth`/pause/amount assertions and before `receive-tokens` is called. [5](#0-4)  The token transfer, `(try! (receive-tokens ft amount account))`, calls `transfer` on the attacker-controlled `ft` contract. [6](#0-5)  Only after this returns does `(insert updated-entry)` persist the mask that was computed from the stale, pre-call `entry`. [7](#0-6) 

`debt-add-scaled` follows the identical read-mutate-write pattern: it reads `entry`/`mask` from `registry`, computes an updated mask with the debt bit inserted, mutates the `debt` map via `add-user-scaled-debt`, and calls `insert` to persist the new mask. [2](#0-1)  Both `collateral-add` and `debt-add-scaled` are gated only by `check-impl-auth`, which asserts `contract-caller == (var-get impl)` — i.e., whichever contract makes the *immediate* call into the vault. [8](#0-7)  This check does not prevent re-entrant calls originating from the market implementation contract itself during a nested callback triggered by `receive-tokens`, since `contract-caller` would still be the implementation contract in that nested call.

If the market implementation's `borrow` path (in `v0-4-market.clar`) has no reentrancy lock protecting the vault's `debt-add-scaled` call, and the attacker account already holds pre-existing, previously-recorded collateral (with its mask bit already committed in a prior transaction) sufficient to cover a new borrow, then: the attacker calls `collateral-add` with a malicious `<ft-trait>` whose `transfer` reenters `borrow` for that pre-existing collateral; the reentrant `debt-add-scaled` call succeeds (health check passes against the *already-committed* collateral, unaffected by the in-flight, not-yet-inserted deposit) and commits a mask with the debt bit set plus a non-zero `debt` map row; control returns to `receive-tokens`, and `collateral-add` then calls `(insert updated-entry)` with the stale mask, erasing the debt bit while the `debt` map row remains.

I was **not able to verify** within my available searches whether `v0-4-market.clar`'s `borrow` function contains a reentrancy guard, nonce/lock check, or otherwise prevents this specific reentrant call sequence before it reaches `debt-add-scaled`. This is essential to conclude the finding is a complete, end-to-end exploitable path rather than a latent pattern in the vault contract alone.

### Impact Explanation
If reachable, the consequence matches **Critical - protocol insolvency**: an account with a debt map row (real, borrowed funds) but a registry mask with the debt bit cleared would be treated as debt-free by `get-position`, `lookup-debt` (via mask-derived enumeration), and any code path relying on the mask to determine "has debt." Such an account could then call `collateral-remove` for its full collateral with any health check that gates on mask-derived debt lookups passing (`false`) — permanently freeing collateral without repaying tracked debt, i.e., unbacked debt / insolvency.

### Likelihood Explanation
Preconditions: the attacker needs (1) a funded principal, (2) an attacker-deployed `<ft-trait>` contract with a malicious `transfer` implementing a reentrant callback, (3) prior, legitimately committed collateral already reflected in the account's registry mask sufficient to satisfy `borrow`'s health check independent of the in-flight deposit, and (4) crucially, that `v0-4-market.clar`'s `borrow` function contains no reentrancy guard blocking this nested call. Capital cost is limited to whatever collateral is needed to pass the health check once; this is attacker-controlled and can be minimized. Repeatability is high if the guard is absent, since the pattern can be triggered on any `collateral-add` call. However, this whole scenario hinges on confirmation of point (4), which I could not verify from the code retrieved.

### Recommendation
Re-fetch the account's registry entry immediately before the final `insert` call (or merge only the specific bit change into the freshly-read state) rather than relying on a mask value computed before any external call in `collateral-add`, `collateral-remove`, `debt-add-scaled`, and `debt-remove-scaled`. Alternatively, apply the checks-effects-interactions pattern strictly: perform `receive-tokens`/`send-tokens` before computing/writing the mask, or add a reentrancy lock (e.g., an "in-operation" flag) around all vault position-mutating entry points so nested calls from the same transaction are rejected.

### Proof of Concept
Clarinet/vitest simnet plan (would need to be run to confirm, given `v0-4-market.clar`'s `borrow` internals were not fully inspected):
1. Deploy a mock `<ft-trait>` contract whose `transfer` function, when called with a specific magic amount/account, calls back into `v0-4-market.borrow` for a *different, already-collateralized* asset for the same account before returning `(ok true)`.
2. Setup: fund the attacker account, have it deposit legitimate collateral (asset A) via a normal `collateral-add` call so `registry.mask` already has asset A's bit set.
3. Call `collateral-add(account, amount, malicious-ft, asset-id-B)`. During `receive-tokens`, the malicious `transfer` reenters `borrow` on asset A (within the pre-existing, sufficient collateral), causing a nested `debt-add-scaled` to succeed, setting the debt bit in `registry.mask` and a non-zero `debt` map row.
4. After the outer `collateral-add` completes, assert: `debt` map row for asset A is non-zero (`get-debt`/`debt-scaled`), but `registry.mask` for the account has the corresponding debt bit cleared (inspect via `lookup`/`resolve`).
5. Call `get-position` and confirm `debt` field in output does not include asset A despite the non-zero `debt` map row.
6. Attempt `collateral-remove` for the full amount of asset A and confirm it succeeds without any debt-driven health check blocking it.

Note: step 3's success (the reentrant `borrow` not being blocked) depends on `v0-4-market.clar` internals I did not confirm. If `borrow` includes a reentrancy guard or an early "not in-progress" assertion, this PoC will fail at that step and the finding does not hold end-to-end.

(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))
    
    (insert updated-entry)

    (print {
      action: "collateral-add",
      caller: contract-caller,

        account: account,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: result,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
      
    (ok result)))
