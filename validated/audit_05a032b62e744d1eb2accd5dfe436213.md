### Title
`FetchRemote` fails to disable Git's client-side bundle-URI feature when fetching from a user-controlled remote, enabling SSRF via attacker-advertised bundle URIs - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`FetchRemote` invokes `git-fetch(1)` against an attacker-controlled remote URL (`req.GetRemoteParams().GetUrl()`) without ever setting `transfer.bundleURI=false`, unlike the sibling `cloneFromURLCommand` used by `CreateRepositoryFromURL`, which explicitly disables the feature "since the URI can point to any server, including localhost." Because `FetchRemote`'s `buildCommandOpts` only sets refspec, remote URL, resolve, proactive-auth, and per-URL `extraHeader` config [1](#0-0) , a malicious remote server can advertise a bundle URI during the fetch negotiation that points Git at an arbitrary internal/attacker host, and the local `git` client run by Gitaly will follow it.

### Finding Description
`FetchRemote` builds the `git-fetch` invocation in `buildCommandOpts`, which sets `remote.inmemory.url` to the caller-supplied URL and applies auth/resolve config, but contains no `transfer.bundleURI` config pair [2](#0-1) . This is then used to run `quarantineRepo.FetchRemote(ctx, "inmemory", opts)` [3](#0-2) .

By contrast, the code that handles `CreateRepositoryFromURL` explicitly disables this exact feature with the comment: "Drop support for bundle URI when fetching from a remote repository. Since the URI can point to any server, including localhost, this is to prevent attack vectors that could abuse this mechanism." [4](#0-3) 

This shows that the Gitaly maintainers are aware that a Git server (attacker-controlled, since the URL is caller-supplied) can respond to a fetch/clone negotiation with a bundle-URI advertisement, and that Git's client-side bundle-URI feature (`transfer.bundleURI`) will cause the local `git` process to fetch that bundle from wherever it points — including internal-only hosts, cloud metadata endpoints, or an attacker's own listener designed to capture whatever credentials Git includes in the request. `FetchRemote`, which is reachable by an unprivileged user configuring a pull mirror or push mirror with an arbitrary remote URL, does not apply the same mitigation.

The bundle-URI feature within Gitaly's own server-side advertisement code (`internal/bundleuri`) always signs and scopes URIs to Gitaly's own trusted bucket [5](#0-4) , so that side is safe — but that is irrelevant here: the risk is Gitaly acting as a bundle-URI *client* against an attacker-controlled remote during `FetchRemote`, not Gitaly as a bundle-URI server.

### Impact Explanation
If `transfer.bundleURI` is not disabled for `FetchRemote`, an attacker who configures a pull mirror or remote fetch pointing at a server they control can have that server advertise a bundle URI pointing to an internal endpoint (e.g. cloud metadata service, internal admin API) reachable from the Gitaly host, causing Gitaly's `git` process to issue an HTTP request there — an SSRF primitive. Because bundle URIs can also be `file://` or other scheme URIs depending on Git's compiled-in transport support, this could additionally be leveraged for local file disclosure if `file://` is permitted by the Git binary's bundle-uri transport. This matches the GitLab HackerOne "SSRF to an internal endpoint" impact class.

### Likelihood Explanation
Any unprivileged GitLab user who can configure a pull/push mirror or set an import/remote URL for a repository they own controls the remote endpoint that `FetchRemote`'s `RemoteParams.Url` targets, and controls what that endpoint's Git server advertises during the fetch negotiation (including a `bundle-uri` capability). No privileged role, stolen secret, or MITM is required — the attacker simply runs their own git server as the fetch target. This is directly reachable via the standard mirror/fetch feature.

### Recommendation
Explicitly disable `transfer.bundleURI` for all Gitaly-initiated fetches from externally-supplied remotes, matching the hardening already applied in `cloneFromURLCommand`. Add `gitcmd.ConfigPair{Key: "transfer.bundleURI", Value: "false"}` (or the equivalent `WithGlobalOption`) to `buildCommandOpts` in `fetch_remote.go`, and audit other RPCs that invoke `git-fetch`/`git-clone` against caller-supplied remote URLs (e.g. `FetchSourceBranch`, `CreateRepositoryFromURL` snapshot/bundle variants) to ensure the same mitigation is applied consistently.

### Proof of Concept
```go
func TestFetchRemote_BundleURISSRF(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)

    // Malicious git server that advertises a bundle-uri pointing at an
    // internal/attacker-controlled endpoint during upload-pack negotiation.
    maliciousRemoteURL := startMaliciousBundleURIServer(t, "http://169.254.169.254/latest/meta-data/")

    repoProto, _ := gittest.CreateRepository(t, ctx, cfg)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.Remote{
            Url: maliciousRemoteURL,
        },
    })
    require.NoError(t, err)

    // Assertion: the malicious server's bundle-uri handler should never have
    // been contacted; if it captured a request, transfer.bundleURI was
    // honored, confirming the SSRF.
    require.False(t, maliciousServerReceivedBundleFetch, "Gitaly's git-fetch followed an attacker-advertised bundle URI")
}
```
Expected (vulnerable) behavior: the internal/attacker endpoint records an inbound request originating from the Gitaly host during `FetchRemote`, because `transfer.bundleURI` is not disabled in `buildCommandOpts` [1](#0-0) , contrasted with the explicit disablement present in `cloneFromURLCommand` [4](#0-3) .

```go
func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if featureflag.FetchRemoteProactiveAuth.IsEnabled(ctx) {
		if u, err := url.Parse(remoteURL); err == nil && u.User != nil {
			password, _ := u.User.Password()
			if u.User.Username() != "" && password != "" {
				config = append(config, gitcmd.ConfigPair{
					Key:   "http.proactiveAuth",
					Value: "basic",
				})
			}
		}
	}

	if authHeader := req.GetRemoteParams().GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", req.GetRemoteParams().GetUrl()),
			Value: "Authorization: " + authHeader,
		})
	}

	opts.CommandOptions = append(opts.CommandOptions, gitcmd.WithConfigEnv(config...))

	return nil
```

```go
// SignedURL returns a public URL to give anyone access to download the bundle from.
func (g *GenerationManager) SignedURL(ctx context.Context, repo storage.Repository) (string, error) {
	relativePath := bundleRelativePath(ctx, repo, defaultBundle)

	repoProto, ok := repo.(*gitalypb.Repository)
	if !ok {
		return "", fmt.Errorf("unexpected repository type %t", repo)
	}

	if tx := storage.ExtractTransaction(ctx); tx != nil {
		origRepo := tx.OriginalRepository(repoProto)
		relativePath = bundleRelativePath(ctx, origRepo, defaultBundle)
	}

	return g.sink.signedURL(ctx, relativePath)
}
```
