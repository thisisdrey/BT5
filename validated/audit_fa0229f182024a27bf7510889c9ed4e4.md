### Title
Node-operator API restrictions (`node.disabledApi`) are not enforced on the JSON-RPC query path, letting a fully disabled Wallet API remain reachable via its JSON-RPC equivalent - (File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java)

### Summary
`node.disabledApi` is java-tron's mechanism for an operator to hide/disable specific query APIs (e.g. `getaccount`, `getnowblock2`) that they consider sensitive or that they don't want exposed publicly. This restriction is enforced for the HTTP servlet path and the gRPC path (and their Solidity/PBFT variants), but is explicitly documented as *not* applying to the JSON-RPC interface. Since almost every disable-able Wallet query has a semantically equivalent JSON-RPC method (e.g. `eth_getBalance`, `eth_getTransactionByHash`, `eth_call`, `eth_blockNumber`), an anonymous API client can still retrieve the exact information the operator intended to block, simply by using the JSON-RPC endpoint instead of the HTTP/gRPC one. This is directly analogous to the FreeScout bug class: an access restriction is applied to some query builders/paths (direct view, folder queries / HTTP, gRPC, PBFT) but not to a parallel non-restricted query path (global search / JSON-RPC), which still discloses the data that was supposed to be hidden.

### Finding Description
The disable mechanism is implemented in two places:
- `HttpApiAccessFilter.isDisabled` [1](#0-0)  checks the requested servlet path segment against `CommonParameter.getInstance().getDisabledApiList()` and returns `404` if matched, applied via `addFilter` in `FullNodeHttpApiService`, `HttpApiOnPBFTService`, and `HttpApiOnSolidityService`.
- `RpcApiAccessInterceptor.isDisabled` [2](#0-1)  performs the same check for gRPC method names and closes the call with `UNAVAILABLE` if disabled.

The configuration file itself documents the scope limitation explicitly:
"Disabled API list (works for http, rpc and pbft, not jsonrpc)" [3](#0-2) 

Searching the JSON-RPC implementation (`TronJsonRpcImpl.java`, `FullNodeJsonRpcHttpService.java`, `JsonRpcServlet.java`) shows no reference to `disabledApiList`/`DisabledApi` anywhere in that code path — unlike the HTTP filter and gRPC interceptor classes, which are the only files in the codebase that consult `CommonParameter.getDisabledApiList()`. Consequently, when an operator disables an HTTP/gRPC API such as `getaccount`, `getnowblock`, `gettransactionbyid`, etc. for privacy, DoS-mitigation, or compliance reasons, the JSON-RPC layer (`eth_getBalance`, `eth_getTransactionByHash`, `eth_getBlockByNumber`, `eth_call`, etc., served over `node.jsonrpc.httpFullNodeEnable`) remains fully enabled and unfiltered, exposing the same underlying data through `Wallet`/`chainBaseManager` calls that the operator explicitly tried to block.

### Impact Explanation
An operator who disables a Wallet query API via `node.disabledApi` because it discloses sensitive information (account balances/details, transaction history, block contents, etc.) has no equivalent way to block that data through JSON-RPC. Any anonymous JSON-RPC client can retrieve the "hidden" information via the semantically equivalent `eth_*` method, defeating the operator's access-control intent. This is a genuine confidentiality bypass of an admin-configured restriction, reachable by any unauthenticated API client with no special privileges - matching the CWE class of the reported FreeScout issue (an authorization restriction correctly enforced on one query path but omitted from a parallel query path).

### Likelihood Explanation
Any node operator that runs JSON-RPC (`node.jsonrpc.httpFullNodeEnable = true`, disabled by default but commonly enabled for wallet/dApp compatibility) alongside `node.disabledApi` restrictions is affected immediately, with zero additional preconditions - any anonymous JSON-RPC caller reaches the bypass by simply calling the corresponding `eth_*` method instead of the disabled Wallet HTTP/gRPC method. This requires no signed transaction, no privilege, and no race condition.

### Recommendation
Add disabled-API enforcement to the JSON-RPC dispatch path (e.g., in `JsonRpcServlet`/`TronJsonRpcImpl`), mapping each JSON-RPC method to its underlying Wallet/gRPC data source and rejecting requests whose backing capability is listed in `disabledApiList`, mirroring the checks already performed in `HttpApiAccessFilter` and `RpcApiAccessInterceptor`. At minimum, document loudly (beyond a config comment) that `disabledApi` provides no protection against JSON-RPC disclosure, and provide an explicit `jsonrpc.disabledApi` (or reuse the same list) enforcement point.

### Proof of Concept
1. Start a fullnode with:
   ```
   node.disabledApi = ["getaccount"]
   node.jsonrpc.httpFullNodeEnable = true
   ```
2. Confirm the HTTP path is blocked:
   ```
   curl http://<node>:8090/wallet/getaccount -d '{"address":"..."}'
   # => {"Error":"this API is unavailable due to config"}
   ```
   (per `HttpApiAccessFilter.doFilter`) [4](#0-3) 
3. Query the same account data via JSON-RPC, which is unaffected by `disabledApiList`:
   ```
   curl -X POST http://<node>:8545 -d '{"jsonrpc":"2.0","method":"eth_getBalance","params":["0x...","latest"],"id":1}'
   # => returns the balance the operator tried to hide
   ```
4. No `disabledApiList` check exists anywhere in `TronJsonRpcImpl`/`FullNodeJsonRpcHttpService`/`JsonRpcServlet`, confirming the bypass is structural, not a request-specific edge case.

Note: I was not able to inspect the full body of `FullNodeJsonRpcHttpService.java` or `TronJsonRpcImpl.java` (only grep/reference snippets were available through the indexed search), so the exact JSON-RPC method-to-Wallet-call mapping should be verified directly in those files before remediation; however, the absence of any `disabledApiList` reference in JSON-RPC-related files, combined with the explicit config-file documentation of the exclusion, is sufficient to establish the root cause.

          resp.getWriter().println(jsonObject.toJSONString());
          return;

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
