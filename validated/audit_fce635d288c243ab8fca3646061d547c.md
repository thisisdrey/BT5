### Title
Cache key collision in `GetArchive` due to unescaped concatenation of untrusted request fields - (File: `internal/gitaly/service/repository/archive.go`)

### Summary
`createArchiveCacheKey` builds the cache key for the shared `GetArchive` streamcache by hashing `gitLabProjectPath`, `strings.Join(args, ",")`, and `strings.Join(pathspecs, ",")` back-to-back into a single SHA-256 digest, with no length prefixing or delimiter between the three segments. [1](#0-0) 

### Finding Description
The bug class in the referenced report is that a hash/key used to index a mapping is computed by encoding several distinguishing fields without unambiguous framing, so two different logical inputs can produce the same key and one entry silently overwrites/serves in place of the other.

In Gitaly's `GetArchive` RPC, the pack-cache key is derived from attacker-influenced fields: `commitId`, `path`, and `exclude` entries from `GetArchiveRequest`, which become `args` and `pathspecs` in `handleArchive`. [2](#0-1) 
These are fed into `createArchiveCacheKey(repo.GetGlProjectPath(), args, pathspecs)`, which simply concatenates `Write([]byte(gitLabProjectPath))`, `Write([]byte(strings.Join(args, ",")))`, and `Write([]byte(strings.Join(pathspecs, ",")))` into the same hash state with no delimiter separating the three writes and no length-prefixing of the individual strings. [3](#0-2) 

Because the byte streams from the three `Write` calls are concatenated directly, the boundary between `args` and `pathspecs` is not fixed: a request where `args=["X"]`, `pathspecs=["YZ"]` writes the same underlying bytes as a request where `args=["XY"]`, `pathspecs=["Z"]` (both produce literal byte sequence `"XYZ"`). Because `commitId`/`path` are validated only for revision syntax and path validity within the repo tree (not for absence of characters that could shift this boundary), a request for one `(commitId, path, exclude)` triple can, in principle, hash to the same cache key as a request for a *different* triple as long as the concatenated literal bytes coincide — this is exactly the "insufficient key differentiation via naive concatenation" class described in the report (order fields hashed without full framing, permitting collisions).

Notably, Gitaly's own `internal/cache` keyer explicitly guards against this exact bug class: `compositeKeyHashHex` writes each field through `prefixLen(i)` before hashing, deliberately length-prefixing every component (version, method, genID, request bytes, feature flags) to avoid concatenation ambiguity. [4](#0-3) 
`createArchiveCacheKey` in `archive.go` does not use this pattern and lacks any equivalent framing. [3](#0-2) 

### Impact Explanation
The archive cache (`streamcache.Cache`) is a shared, project-scoped, disk-backed cache keyed purely by this hash; a colliding key means `s.archiveCache.Fetch` will serve the previously cached archive content for a request whose parameters differ from what was actually cached, rather than regenerating it. [5](#0-4) 
In the worst case, this allows one client's `GetArchive` request (e.g., for a private/protected `path` or `commitId`) to receive an archive that was generated for a different, unrelated request/commit/path combination within the same project — a cross-request cache-poisoning/data-substitution issue. It does not directly compromise the object store or hooks, but it does return incorrect/unintended archive content to a caller, undermining the integrity guarantee "the cache key uniquely identifies the archive content" that the function's own doc comment claims. [6](#0-5) 

### Likelihood Explanation
Exploitation requires constructing two distinct `(commitId, path, exclude...)` combinations whose `args`/`pathspecs` concatenation yields identical bytes, and requires both requests to pass all preconditions independently (revision must resolve, `path`/`exclude` must exist in the target tree via `validateGetArchivePrecondition`). [7](#0-6) 
This constrains realistic exploitation, since `commitId` and `path`/`exclude` values must both be valid, existing repository content, making arbitrary crafted collisions harder than in the original report's arbitrary-order-hash scenario. It is a genuine design weakness rather than a trivially exploitable one, given the difficulty of finding two valid, existing tree entries whose concatenated bytes coincide across the args/pathspecs boundary.

### Recommendation
Length-prefix or otherwise unambiguously delimit each field before hashing in `createArchiveCacheKey`, following the same pattern already used by `compositeKeyHashHex`/`prefixLen` in `internal/cache/keyer.go` — e.g., write the length of `gitLabProjectPath`, each `args` element, and each `pathspecs` element before their contents, instead of relying on `strings.Join(..., ",")` and back-to-back `Write` calls. [3](#0-2) [8](#0-7) 

### Proof of Concept
Conceptually: 
1. Request A: `commitId="X"`, `path` resolves such that `pathspecs = ["YZ"]` (a valid, existing pathspec under commit `X`'s tree).
2. Request B: `commitId="XY"`, `pathspecs=["Z"]` (a different valid, existing pathspec under a different commit `XY`).
3. Both requests reduce to the identical concatenated byte stream `gitLabProjectPath + "XY" + "Z"` = `gitLabProjectPath + "X" + "YZ"` fed into `createArchiveCacheKey`, producing the same SHA-256 cache key. [3](#0-2) 
4. Whichever request populates the cache first, `s.archiveCache.Fetch` for the second request returns the first request's cached archive content instead of generating its own. [9](#0-8) 

Note: constructing concrete `commitId`/`path` values that satisfy both the boundary-collision requirement and the tree-existence validation in `validateGetArchivePrecondition` was not verified end-to-end in this analysis; the finding demonstrates the root-cause design flaw (missing length-prefixing/delimiting in the cache key construction) rather than a fully instantiated exploit payload.

	ctx context.Context,
	repo gitcmd.RepositoryExecutor,
	commitID string,

		return err
	}

	f := catfile.NewTreeEntryFinder(objectReader)

		if ok, err := findGetArchivePath(ctx, f, commitID, path); err != nil {
			return err
		} else if !ok {
			return structerr.NewFailedPrecondition("path doesn't exist")
		}

			return err
		}

		if err != nil {
			return err
		}

		rootTree, err := objectInfoReader.Info(ctx, git.ObjectID(commitID).Revision()+"^{tree}")

		}

		if rootTree.ObjectID() == repoHash.EmptyTreeOID {

		}

			return err
		} else if !ok {
			return structerr.NewFailedPrecondition("exclude[%d] doesn't exist", i)
		}
	}

	return nil
}

// createArchiveCacheKey creates a cache key using the GitLab project's path, the `git archive`
// command arguments and the pathspecs. The goal is to create a key that is unique not only
// across repository, but also across the content of each archive within the same repository.
func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}
