### Title
Front-running dust repayment can DoS exact full debt repayment - (File: `contracts/DebtToken.sol`) [1](#0-0) 

### Summary
`DebtToken.repay` allows any payer to reduce the debt of an arbitrary `onBehalfOf_` account because the payer is `_msgSender()` while the beneficiary is supplied separately. [1](#0-0) [2](#0-1) 

An attacker can front-run a victim’s fixed-amount full repayment with a dust repayment for the same account, causing the victim’s stale full-repayment amount to exceed the remaining debt and revert. [3](#0-2) [4](#0-3) 

### Finding Description
`repay` converts the caller-provided gross `amount_` into a net repayment through `quoteRepayOut`, without first checking that the resulting `_repaid` does not exceed the beneficiary’s current debt. [5](#0-4) 

With zero repay fee, `quoteRepayOut` returns the input unchanged, so passing exactly `balanceOf(victim)` attempts to burn exactly that amount of debt. [6](#0-5) 

With a nonzero repay fee, `quoteRepayIn(debt)` returns the gross amount needed to net `debt`, and that fixed gross amount is likewise stale after an intervening repayment. [7](#0-6) 

The beneficiary’s debt is only reduced at the end of `repay` through `_burn(onBehalfOf_, _repaid)`. [3](#0-2) 

`_burn` explicitly reverts with `BurnAmountExceedsBalance` when the calculated repayment is greater than the beneficiary’s post-front-running balance. [4](#0-3) 

If `debtFloorInUsd` is enabled, the earlier `balanceOf(onBehalfOf_) - _repaid` calculation can also underflow and revert before `_burn` is reached. [8](#0-7) 

### Impact Explanation
The attacker can repeatedly invalidate a user’s fixed-size “repay my entire debt” transaction by spending only enough synthetic tokens to repay one wei of the victim’s debt. [9](#0-8) 

This is a temporary liveness failure for full repayment through `repay`, because the victim must submit `repayAll` or recalculate and submit a lower amount rather than having the contract cap the repayment. [10](#0-9) 

The attack does not directly steal the victim’s funds because the stale transaction reverts atomically, and the attacker’s dust payment reduces the victim’s debt. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
Any unprivileged account can invoke `repay` because it is external and does not restrict `onBehalfOf_` to the payer. [9](#0-8) 

The attacker only needs a small positive synthetic-token balance and the ability to order their transaction before the victim’s transaction. [13](#0-12) 

The `whenNotShutdown`, `nonReentrant`, and synthetic-token existence checks do not prevent two separate, non-reentrant repayment transactions from different EOAs. [14](#0-13) 

`repayAll` gives users an alternate path, which limits the impact to temporary denial of the fixed-amount flow rather than permanent freezing. [10](#0-9) 

### Recommendation
Read the beneficiary’s post-accrual debt inside `repay` and cap the requested net repayment to that balance. [15](#0-14) 

Conceptually:

```solidity
// contracts/DebtToken.sol
uint256 _debt = balanceOf(onBehalfOf_);
(_repaid, _fee) = quoteRepayOut(amount_);

if (_repaid > _debt) {
    _repaid = _debt;
    (amount_, _fee) = quoteRepayIn(_debt);
}
```

The adjusted `amount_` should be used as the actual gross amount paid by `_msgSender`, while `_repaid` remains the amount burned from the beneficiary’s debt position. [7](#0-6) [11](#0-10) 

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DebtToken} from "../contracts/DebtToken.sol";
import {SyntheticToken} from "../contracts/SyntheticToken.sol";

contract DebtTokenRepayGriefingTest is Test {
    DebtToken internal debtToken;
    SyntheticToken internal synth;

    address internal victim = address(0x1001);
    address internal attacker = address(0x2002);

    function test_fixedFullRepayCanBeFrontRun() public {
        // Arrange using the existing collateral/deployment helpers:
        // 1. Deposit collateral for victim.
        // 2. debtToken.issue(D, victim) so victim has D debt and D synth.
        // 3. Deposit collateral for attacker.
        // 4. debtToken.issue(dustGross, attacker) so attacker holds dust synth.

        uint256 debtBefore = debtToken.balanceOf(victim);
        assertGt(debtBefore, 1);

        (uint256 fullRepayGross,) = debtToken.quoteRepayIn(debtBefore);
        (uint256 dustGross,) = debtToken.quoteRepayIn(1);

        // Attacker pays dust to reduce victim's debt by one wei.
        vm.prank(attacker);
        debtToken.repay(victim, dustGross);
        assertEq(debtToken.balanceOf(victim), debtBefore - 1);

        // Victim's already-submitted fixed full repayment now requests
        // the old debt amount and reverts.
        vm.prank(victim);
        vm.expectRevert();
        debtToken.repay(victim, fullRepayGross);
    }
}
```

When `repayFee == 0`, `fullRepayGross == debtBefore` and `dustGross == 1`. [16](#0-15) 

The victim transaction reverts either at the debt-floor subtraction if configured or at `BurnAmountExceedsBalance` otherwise. [17](#0-16) [4](#0-3)
