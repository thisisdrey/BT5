Audit Report

## Title
Reward-counter overflow permanently DoSes `pallet-nomination-pools` payout, join, and commission-claim paths - ([File: substrate/frame/nomination-pools/src/lib.rs])

## Summary
`RewardPool::current_reward_counter` computes `last_recorded_reward_counter + checked_from_rational(new_pending_rewards, bonded_points)` using checked arithmetic and returns `Error::OverflowRisk` on failure instead of saturating. [1](#0-0)  Every mutating extrinsic that touches pool points or rewards (`join`, `bond_extra`, `claim_payout`, `claim_commission`) must call `update_records` or `current_reward_counter`/`pending_rewards` first, so once this computation overflows for a given pool's stored state, it deterministically fails on every subsequent call with the same or worse inputs, since neither `last_recorded_total_payouts` nor `bonded_points` self-correct. [2](#0-1) 

## Finding Description
`current_reward_counter` derives `current_payout_balance` from the reward account's balance and recorded totals, then computes `new_pending_rewards / bonded_points` as a `FixedU128` and adds it to `last_recorded_reward_counter` via `checked_add`, bailing out with `Error::<T>::OverflowRisk` if either the division or the addition fails. [3](#0-2)  `update_records`, which is invoked by `join`/`bond_extra` before mutating bonded points, calls `current_reward_counter` and propagates the same error, and additionally has its own checked-add that can fail. [4](#0-3)  `do_reward_payout` (used by both `claim_payout` and `claim_commission` code paths) also calls `current_reward_counter` before any transfer, and then `PoolMember::pending_rewards` performs a further `checked_mul_int(...).ok_or(Error::<T>::OverflowRisk)`. [5](#0-4) [6](#0-5) 

The repository's own test `reward_counter_update_can_fail_if_pool_is_highly_slashed` reproduces this: a pool is bonded with a large amount, slashed by 99% (shrinking `bonded_points` relative to accumulated payout balance), and a subsequent large `join` by an unprivileged account fails with `Error::<T>::OverflowRisk`. [7](#0-6)  Since none of `last_recorded_total_payouts`, `last_recorded_reward_counter`, or `bonded_points` are reduced by a failed call, and no code path resets or re-baselines them independently of this same checked computation, the failure is not transient: every future `join`, `bond_extra`, `claim_payout`, and `claim_commission` on that pool will repeat the identical overflowing computation and fail identically.

## Impact Explanation
This is a permanent, pool-wide reward-accounting lock triggerable by unprivileged users via public extrinsics (`join`/`bond_extra` after an externally-triggered slash). It matches the impact gate's "permanent user-fund or bridge-state lock": members' already-accrued rewards become permanently unclaimable (`claim_payout`), pool operator commission becomes permanently unclaimable (`claim_commission`), and the pool becomes permanently closed to new deposits (`join`/`bond_extra`), all without any admin/governance action required to trigger or to remain wedged.

## Likelihood Explanation
The condition is proven reachable in-repo by `reward_counter_update_can_fail_if_pool_is_highly_slashed` using realistic (not `FixedU128::MAX` edge-case) parameters — a severe slash followed by a large deposit — both of which are ordinary, permissionless operations (staking slashes are a normal chain event; `join` is a public extrinsic). Any pool that is heavily slashed and later receives a disproportionately large `join`/`bond_extra` relative to its shrunken `bonded_points` is at risk.

## Recommendation
- Do not gate all pool reward availability on a single checked `FixedU128` operation with no recovery path; provide a permissionless "resync"/rebase extrinsic that recomputes `last_recorded_reward_counter`/`last_recorded_total_payouts` from current balances without requiring the intermediate multiplication/division to fit within the same bounds.
- In `join`/`bond_extra`, reject deposits that would push the reward counter toward the overflow boundary rather than allowing the deposit while wedging the entire pool for all other members.
- Consider bounding the ratio between `bonded_points` and `current_payout_balance`/reward-account balance, or switching to saturating arithmetic with an explicit, bounded "unclaimable dust" concept instead of an unrecoverable hard failure.

## Proof of Concept
Existing repository test demonstrates the full exploit path:
1. Create a pool bonded with `pool_bond = inflation(10) / 2`.
2. Slash the pool by 99% via `StakingMock::slash_by(1, pool_bond * 99 / 100)`, shrinking `bonded_points` relative to the reward pool's payout bookkeeping.
3. An unprivileged large depositor calls `Pools::join(RuntimeOrigin::signed(20), pool_bond, 1)`; `current_reward_counter`'s `checked_from_rational`/`checked_add` chain overflows, returning `Error::<T>::OverflowRisk`.
4. Because `bonded_points` and the recorded payout totals are unchanged by the failed call, any subsequent `join`, `bond_extra`, `claim_payout`, or `claim_commission` on pool `1` will repeat the same failing computation, permanently locking pending rewards/commission and blocking new deposits. 	fn update_records(
		&mut self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(), Error<T>> {
		let balance = Self::current_balance(id);

		let (current_reward_counter, new_pending_commission) =
			self.current_reward_counter(id, bonded_points, commission)?;

		// Store the reward counter at the time of this update. This is used in subsequent calls to
		// `current_reward_counter`, whereby newly pending rewards (in points) are added to this
		// value.
		self.last_recorded_reward_counter = current_reward_counter;

		// Add any new pending commission that has been calculated from `current_reward_counter` to
		// determine the total pending commission at the time of this update.
		self.total_commission_pending =
			self.total_commission_pending.saturating_add(new_pending_commission);

		// Total payouts are essentially the entire historical balance of the reward pool, equating
		// to the current balance + the total rewards that have left the pool + the total commission
		// that has left the pool.
		let last_recorded_total_payouts = balance
			.checked_add(&self.total_rewards_claimed.saturating_add(self.total_commission_claimed))
			.ok_or(Error::<T>::OverflowRisk)?;

	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

		// * accuracy notes regarding the multiplication in `checked_from_rational`:
		// `current_payout_balance` is a subset of the total_issuance at the very worse.
		// `bonded_points` are similarly, in a non-slashed pool, have the same granularity as
		// balance, and are thus below within the range of total_issuance. In the worse case
		// scenario, for `saturating_from_rational`, we have:
		//
		// dot_total_issuance * 10^18 / `minJoinBond`
		//
		// assuming `MinJoinBond == ED`
		//
		// dot_total_issuance * 10^18 / 10^10 = dot_total_issuance * 10^8
		//
		// which, with the current numbers, is a miniscule fraction of the u128 capacity.
		//
		// Thus, adding two values of type reward counter should be safe for ages in a chain like
		// Polkadot. The important note here is that `reward_pool.last_recorded_reward_counter` only
		// ever accumulates, but its semantics imply that it is less than total_issuance, when
		// represented as `FixedU128`, which means it is less than `total_issuance * 10^18`.
		//
		// * accuracy notes regarding `checked_from_rational` collapsing to zero, meaning that no
		//   reward can be claimed:
		//
		// largest `bonded_points`, such that the reward counter is non-zero, with `FixedU128` will
		// be when the payout is being computed. This essentially means `payout/bonded_points` needs
		// to be more than 1/1^18. Thus, assuming that `bonded_points` will always be less than `10
		// * dot_total_issuance`, if the reward_counter is the smallest possible value, the value of
		//   the
		// reward being calculated is:
		//
		// x / 10^20 = 1/ 10^18
		//
		// x = 100
		//
		// which is basically 10^-8 DOTs. See `smallest_claimable_reward` for an example of this.
		let current_reward_counter =
			T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
				.and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
				.ok_or(Error::<T>::OverflowRisk)?;

		Ok((current_reward_counter, new_pending_commission))
	}

	#[test]
	fn reward_counter_update_can_fail_if_pool_is_highly_slashed() {
		// create a pool that has roughly half of the polkadot issuance in 10 years.
		let pool_bond = inflation(10) / 2;
		ExtBuilder::default().ed(DOT).min_bond(pool_bond).build_and_execute(|| {
			assert_eq!(
				pool_events_since_last_call(),
				vec![
					Event::Created { depositor: 10, pool_id: 1 },
					Event::Bonded {
						member: 10,
						pool_id: 1,
						bonded: 12_968_712_300_500_000_000,
						joined: true,
					},
					Event::MetadataUpdated { pool_id: 1, caller: 900 },
				]
			);

			// slash this pool by 99% of that.
			StakingMock::slash_by(1, pool_bond * 99 / 100);

			// some whale now joins with the other half ot the total issuance. This will trigger an
			// overflow. This test is actually a bit too lenient because all the reward counters are
			// set to zero. In other tests that we want to assert a scenario won't fail, we should
			// also set the reward counters to some large value.
			Currency::set_balance(&20, pool_bond * 2);
			assert_err!(
				Pools::join(RuntimeOrigin::signed(20), pool_bond, 1),
				Error::<T>::OverflowRisk
			);
		})
