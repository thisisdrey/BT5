Audit Report

## Title
`process_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries an explicit `success: bool` field indicating whether the dispatch on Ethereum actually succeeded, but `process_delivery_receipt` never reads or branches on this field. It only checks that the gateway address matches and that a `PendingOrder` exists for the nonce, then unconditionally pays `order.fee` to the reward account and removes the pending order regardless of `receipt.success`.

## Finding Description
The `DeliveryReceipt` struct explicitly models the delivery outcome via `success: bool`, populated directly from the decoded Ethereum log in `TryFrom<&Log>`: [1](#0-0) [2](#0-1) 

`process_delivery_receipt` validates only the gateway address and the existence of a `PendingOrder` keyed by `nonce`, then pays the reward and removes the order — `receipt.success` is never inspected: [3](#0-2) 

This matches the "reply accepted purely on ID match, without verifying its outcome field" bug class: the reward payout is settled solely because a `PendingOrder` exists for `receipt.nonce`, irrespective of whether `receipt.success` is `true` or `false`.

## Impact Explanation
This is a duplicate/incorrect settlement bug: bridge reward funds are paid out to relayers for message deliveries that Ethereum itself reported as failed (`success == false`), and the `PendingOrder` state is irreversibly removed as if delivery succeeded, precluding any correct retry/accounting. This directly corrupts the payout amount and the `PendingOrders` settlement state, matching the "duplicate settlement or payout" and "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" impact categories.

## Likelihood Explanation
`submit_delivery_receipt` is a public, signed extrinsic reachable by any unprivileged relayer. The only gates before reaching `process_delivery_receipt` are proof verification (`T::Verifier::verify`) and the gateway-address check — both of which are satisfied by a legitimate, correctly-proven Ethereum event that legitimately reports `success = false` (this is by protocol design; the Gateway emits `InboundMessageDispatched` regardless of dispatch outcome). No malicious relayer or compromised infrastructure is required — a normal, honest relayer submitting a real failed-dispatch receipt triggers the incorrect payout.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` when `success == true`. When `success == false`, still remove/settle the `PendingOrder` to avoid indefinite accumulation, but skip the reward payment, and consider emitting a distinct event (e.g., `MessageDeliveryFailed`) for downstream monitoring.

## Proof of Concept
1. A message is queued via `queue_message` (or equivalent submission path), recording `PendingOrder { nonce, fee, .. }` with `fee > 0` at [4](#0-3) .
2. The message is delivered to the Ethereum Gateway but its execution fails; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains proof of this event and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false`.
4. `process_delivery_receipt` checks gateway match and `PendingOrders::get(nonce)` — both pass — and pays `order.fee` via `T::RewardPayment::register_reward`, then removes the `PendingOrder`, exactly mirroring the success-path behavior shown in the existing test `submit_delivery_receipt_succeeds_after_unhalt`: [5](#0-4) .
5. Result: reward is paid despite failed delivery, and the pending-order settlement state is finalized incorrectly with no way to recover or retry.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
