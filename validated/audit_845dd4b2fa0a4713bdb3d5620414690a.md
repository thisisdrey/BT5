### Title
Missing zero-address (default pubkey) validation on `new_authority` allows permanent lock of a migrated MarginfiAccount and its funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let any account authority (unprivileged user) migrate their `MarginfiAccount` to a brand-new account under a caller-supplied `new_authority`. The `new_authority` account is typed as `UncheckedAccount` with the code comment "WARN: New authority is completely unchecked," and no check anywhere in the instruction rejects `Pubkey::default()` (Solana's "zero address" analog, i.e. an address no wallet holds the private key for). This mirrors the reported bug class of missing zero-address checks on values that become effectively immutable once set.

### Finding Description
In `TransferToNewAccount`/`TransferToNewAccountPda`, `new_authority` is declared as an `UncheckedAccount` with no `constraint` or `require!` validating it is non-default: [1](#0-0) 

The value is used directly to seed/initialize the new account's `authority` field via `initialize_migrated_account`, and the old account is irreversibly marked as migrated (`migrated_to`) and disabled: [2](#0-1) 

The same unchecked pattern exists in the PDA variant, where `new_authority` is also an `UncheckedAccount` used both to derive the new account's PDA seeds and to set the resulting account's `authority`: [3](#0-2) 

Once migration completes: the old account is flagged `ACCOUNT_DISABLED` and `migrated_to` is set (permanently, since the check `migrated_to == Pubkey::default()` gate prevents a second migration attempt from succeeding again): [4](#0-3) . If `new_authority` was `Pubkey::default()`, the new account's `authority` field is permanently `Pubkey::default()` — an address with no corresponding private key that can ever sign transactions — while all lending balances, positions, and points are inherited by that new account.

Notably, the off-chain `p0-cli` tooling for this same operation explicitly guards against this: [5](#0-4) , confirming the team is aware zero-address transfer is an unsafe/undesired state, but the on-chain instruction itself enforces no equivalent check.

### Impact Explanation
This is directly analogous to the reported "missing zero address check on immutable values" bug: `new_authority` becomes effectively immutable once set (there is no way to reset `authority` on the new account, and the old account cannot re-migrate since `migrated_to` is already set). If a user (accidentally via a bug in their own tooling/UI, or via a griefing/social-engineering vector where a malicious front-end or integrator populates `new_authority` with the default pubkey) migrates to `Pubkey::default()`, all deposited assets, borrow positions, and other state on the new account become permanently unrecoverable — a permanent lock/freeze of user funds with no possible remediation, since no signer exists for the zero address.

### Likelihood Explanation
The instruction is fully permissionless from the perspective of the account authority (any user can call it on their own account) and requires no admin/group approval; `new_authority` is attacker/user-controlled and explicitly documented in code as unchecked. While a competent, honest integrator would validate this client-side, the guide's own documentation shows the transfer flow is expected to be composed by third-party integrators and PDA-based programs where an off-by-default value or logic bug could plausibly pass `Pubkey::default()` unchecked, and no on-chain safety net exists.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` (and their `Accounts` structs) rejecting `new_authority.key() == Pubkey::default()` (and ideally also rejecting the marginfi program ID or other known-unsignable addresses), mirroring the check already present in the off-chain `p0-cli` tool, e.g.:
```
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority
);
```

### Proof of Concept
1. User creates a `MarginfiAccount` with deposits/borrows.
2. User (or a buggy/malicious integrator building the transaction) calls `transfer_to_new_account` (or `transfer_to_new_account_pda`), passing `new_authority = Pubkey::default()`.
3. The instruction succeeds: `old_marginfi_account` is flagged `ACCOUNT_DISABLED`, `migrated_to` is set to the new account, and `new_marginfi_account.authority` is set to `Pubkey::default()`, as shown in [6](#0-5) .
4. No entity can ever sign as `Pubkey::default()`, so all balances/positions on the new account (and the now-disabled old account, which cannot re-migrate per the `migrated_to == Pubkey::default()` guard) are permanently frozen and unrecoverable.
