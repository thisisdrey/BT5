### Title
Non-hardened `ExchangeCapsule.transaction()` can drive AMM pool reserves negative, permanently bricking `ExchangeTransactionContract`/`ExchangeWithdrawContract` for an exchange pair - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeTransactionActuator` and `ExchangeWithdrawActuator` are broadcastable transaction types that let any account trade or withdraw from a TRC10 bancor-style liquidity pool tracked in `ExchangeCapsule` (`firstTokenBalance`/`secondTokenBalance`). Like the reported Derby `MainVault` bug, where an internal accounting variable (`reservedFunds`) can diverge from the true underlying balance and later cause an underflow that permanently reverts subsequent user operations, java-tron's exchange pool keeps its own internal reserve counters that are updated via floating-point math and are **only bounds-checked when the "hardened" calculation path is enabled**. When the hardened path is disabled (which is the historical/default behavior gated by a still-proposal-controlled parameter), the reserve values can go negative and are never validated, corrupting the pool state for all future traders on that pair.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances using either a checked/hardened path or a plain long-arithmetic path selected by the `hardenedCalc` flag: [1](#0-0) 

The `hardenedCalc` guard `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` only throws when hardened math is used; in the non-hardened branch the same arithmetic is performed with plain `+`/`-` and the resulting (possibly negative) balances are written directly into the capsule with no validation. This flag is controlled per-call by `allowHarden()`: [2](#0-1) 
which reads a dynamic property (`allowHardenExchangeCalculation`) that is a committee-controlled feature flag, i.e., not guaranteed to be enabled on chain.

Once `firstTokenBalance`/`secondTokenBalance` become negative or otherwise inconsistent with actual token reserves backing the pool (analogous to the vault's `reservedFunds` exceeding actual `vaultCurrency.balanceOf`), every subsequent `ExchangeTransactionActuator.execute()`/`ExchangeWithdrawActuator.execute()` call for that exchange ID recomputes ratios off the corrupted state: [3](#0-2) [4](#0-3) 
`ExchangeWithdrawActuator` in particular uses `BigInteger` division against the (possibly negative or zero) pool balances, which can throw an `ArithmeticException`/`longValueExact()` overflow for every future caller, or produce nonsensical (unbacked) token payouts, permanently degrading/bricking the exchange pair — the same class of "insufficient/inconsistent internal accounting variable causes future user transactions to revert or misbehave" identified in the Derby report.

The floating point calculation itself (`Math.pow`/`double` arithmetic in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`) is inherently capable of producing balances that don't match true integer reserve invariants for edge-case quantities, which is exactly why the hardened path with explicit `< 0` checks was later added — confirming the underlying non-hardened path is unsafe: [5](#0-4) 

### Impact Explanation
If pool reserves go negative or inconsistent while the hardened check is not active, any account holding the affected token can no longer reliably trade or withdraw from that exchange (permanent freezing of pool functionality for that pair), and depending on how the corrupted ratio is used, traders could receive `anotherTokenQuant` computed from a broken invariant — an unbacked-balance risk on the counter token. This matches the Medium-severity impact class described in the original report (DoS on core financial operation via corrupted internal accounting state), scoped to the Exchange/Market subsystem reachable by any signed transaction (`ExchangeTransactionContract`, `ExchangeWithdrawContract`).

### Likelihood Explanation
Reaching this requires (a) `allowHardenExchangeCalculation` not being enabled by committee vote (the un-hardened path is the original/legacy code path, so any exchange pair created and used before/without this proposal enabled is exposed), and (b) constructing sell/withdraw quantities that push the floating-point-derived balances negative. This is plausible for pools with very small reserves or specifically crafted large trade sizes relative to reserves, since `exchangeToSupply`/`exchangeFromSupply` rely on `double` math without integer-safe bounds in the non-hardened path. Exploitability depends on committee configuration state, which is outside code control and cannot be fully confirmed from static review alone.

### Recommendation
Make the reserve-balance validation (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditional in `ExchangeCapsule.transaction()` rather than gated behind `hardenedCalc`/`allowHardenExchangeCalculation`, so pool balances can never go negative regardless of committee proposal state. Additionally, consider deprecating/removing the non-hardened arithmetic path entirely once all live exchanges are confirmed unaffected, and add an on-chain invariant check on `ExchangeWithdrawActuator`/`ExchangeTransactionActuator` validate() to reject transactions that would leave `firstTokenBalance`/`secondTokenBalance` in an inconsistent state.

### Proof of Concept
1. Ensure `allowHardenExchangeCalculation` dynamic property is `0` (its historical default), so `allowHarden()` returns `false` and `ExchangeCapsule.transaction()` uses the unguarded plain-arithmetic branch.
2. Create/select an `ExchangeCapsule` (TRC10 pair) with small `firstTokenBalance`/`secondTokenBalance`.
3. Submit a `MarketSellAssetContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract` transaction with a sell/withdraw quantity engineered (via the double-precision `Math.pow` calculation in `ExchangeProcessor`) to make `newFirstTokenBalance` or `newSecondTokenBalance` negative — this succeeds silently because the `< 0` check only fires when `hardenedCalc == true`.
4. Observe the persisted `ExchangeCapsule` now has a negative token balance.
5. Any subsequent `ExchangeTransactionContract`/`ExchangeWithdrawActuator` call against this exchange ID either reverts (e.g., `BigInteger` division/`longValueExact()` failures in `ExchangeWithdrawActuator`) or returns economically inconsistent amounts, denying normal trading/withdrawal on that pair going forward — mirroring the Derby vault's "subsequent operations revert due to corrupted internal accounting" bug class.

Note: I could not verify from the indexed code what the actual on-chain/default value of `allowHardenExchangeCalculation` is or whether it has already been permanently activated via a committee proposal on mainnet; that would need confirmation via a live node or `DynamicPropertiesStore` genesis config, which is outside the scope of static code search.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
