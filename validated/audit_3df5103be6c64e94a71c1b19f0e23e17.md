I found a strong analog: `DeleteObjectPool` in the `ObjectPoolService`, which explicitly has **no safety checks** to verify the pool has no remaining members before deletion — directly mirroring the reported bug class ("removal of a shared/backing resource while dependents still rely on it, breaking accounting/integrity").

### Title
`DeleteObjectPool` permits removal of an object pool while member repositories still depend on it, corrupting members via missing objects - ([File: proto/objectpool.proto], [File: internal/gitaly/service/objectpool/server.go])

### Summary
The `RestakeManager` bug class describes removing a shared backing resource (`collateralTokens`) while other protocol state (pending `WithdrawQueue` balances) still depends on it, causing broken accounting (TVL/mint/redeem rate corruption) with no on-chain enforcement to prevent it. The Gitaly `ObjectPoolService.DeleteObjectPool` RPC exhibits the same structural weakness in the git-object domain: pool members keep relying on the pool's objects via the `objects/info/alternates` mechanism, but `DeleteObjectPool` performs the deletion with **no verification that zero members remain linked**.

### Finding Description
Gitaly's object pool mechanism lets multiple repositories (fork members) share objects via Git alternates, pointing at a shared pool repository's object database [1](#0-0) . The `ObjectPoolServiceClient`/`Server` interface documents the pool lifecycle and explicitly states that `DeleteObjectPool` has **no safety checks**, and that it is the caller's sole responsibility to ensure no members remain: "There are no safety checks in place, so if any repository is still using this object pool it will become corrupted." [2](#0-1) [3](#0-2) 

This mirrors the `RestakeManager` root cause precisely: an entity (`token`/`object pool`) that other live records (`WithdrawQueue` balances/`objects/info/alternates` links) still depend on can be removed without any reachability/dependency check, and the protocol/service provides no built-in enforcement — only documentation asking the caller to be careful.

By contrast, note that Gitaly *does* implement a proper safe-removal pattern elsewhere in the very same domain: `DisconnectGitAlternates` (member-initiated pool departure) hard-links all pool objects into the member, removes the alternates link, and then runs `git-fsck` connectivity validation, rolling back (re-adding the alternates file) if the member would become corrupt [4](#0-3) . That is the equivalent of the recommended mitigation ("only allow removal if `claimReserve[token] == 0`" / include pending balance in TVL) — but it protects the *member* side, not the *pool* deletion path itself. `DeleteObjectPool` has no analogous check that zero members remain linked to the pool before physically deleting it, unlike `RemoveRepository`, which enforces repository-level distributed locking, existence re-checks, and 3-phase voting before commit [5](#0-4) .

### Impact Explanation
If `DeleteObjectPool` is invoked (e.g., by an ordinary authenticated RPC caller / GitLab Rails workflow, such as when a fork network is being cleaned up) while any repository is still linked to the pool via `objects/info/alternates`, all such member repositories become permanently corrupted: they will be missing objects that were deduplicated into the pool, and subsequent Git operations (fetch, clone, `git-fsck`) against the member will fail with missing-object errors. This is a persistent data-integrity/availability failure analogous to the "inflated ezETH mint/redeem rate" impact in the original report — an unenforced removal invariant that damages other live protocol state.

### Likelihood Explanation
This is reachable through ordinary, unprivileged RPC use of `ObjectPoolService`: any client with access to the gRPC API that manages object pools (as used by GitLab's fork/pool lifecycle automation) can call `DeleteObjectPool` on a pool that still has members if lifecycle bookkeeping is even briefly inconsistent (e.g., race between unlinking the last known member and deleting the pool, or an incomplete member inventory). Because the RPC contract itself documents "no safety checks," any caller-side bug, race, or incomplete membership tracking directly translates into repository corruption, with no server-side backstop.

### Recommendation
Add a server-side reachability/membership check to `DeleteObjectPool`, analogous to the recommended mitigation in the source report and to the pattern already used by `RemoveRepository`/`Disconnect`:
- Before performing the physical deletion, scan for/require that no remaining repository has this pool referenced in its `objects/info/alternates`, or maintain an authoritative membership count that must be zero.
- Alternatively, perform the deletion transactionally with distributed voting (as `repoutil.Remove` does), and re-verify no in-flight `LinkRepositoryToObjectPool` operations are targeting the pool.
- At minimum, run a `git-fsck`-style connectivity guard for known dependents before allowing deletion, mirroring the safeguard already implemented in `Disconnect`.

### Proof of Concept
1. Create an object pool `P` from a source repository via `CreateObjectPool`.
2. Link repository `R` to `P` via `LinkRepositoryToObjectPool`, so `R`'s `objects/info/alternates` points at `P`'s object directory, and `R`'s duplicate objects are pruned on next repack (per `doc/object_pools.md`) [6](#0-5) .
3. Call `DeleteObjectPool` on `P` directly, without first calling `DisconnectGitAlternates` for `R`.
4. Because `DeleteObjectPool` performs no membership check [3](#0-2) , `P`'s repository directory (and its objects) are removed from disk while `R` still references it as an alternate.
5. Any subsequent read of `R` (e.g., `GetObjectPool`, `Commit`, `Blob` fetch, or `git-fsck`) fails with missing-object errors, permanently corrupting `R`.

# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.

## Lifetime of Object Pools

The lifetime of object pools is maintained via the
[ObjectPoolService](../proto/objectpool.proto), which provides various RPCs to
create and delete object pools as well as to add members to or remove members
from the pool.
