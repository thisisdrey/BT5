### Title
`mt_resolve_withdraw` full-refunds a withdrawal whose tokens were already delivered externally, when the attacker's own MT `token` contract returns a wrong-length `Vec<U128>` - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
In `mt_resolve_withdraw`, a syntactically valid but wrong-length `Ok(Vec<U128>)` result from the external `mt_batch_transfer_call` promise is treated as "nothing was used," forcing a full refund of the withdrawn amount back into the sender's internal Verifier balance, even though the tokens have already left the Verifier's custody on the external `token` contract. Because the attacker controls that `token` contract, they can guarantee the tokens are never returned while still causing the Verifier to re-credit the full amount internally, producing a double-credit of value.

### Finding Description
The intended binding is: `amount_debited_from_sender == amount_that_left_custody_externally + amount_refunded_internally`, i.e. the internal refund must equal exactly what the external `token` contract did *not* keep (`amounts - used`).

`internal_mt_withdraw` first debits `sender_id`'s internal balance for the full `amounts` via `self.withdraw(...)` [1](#0-0) , then schedules `do_mt_withdraw`, which calls `ext_mt_core::ext_on(p).mt_batch_transfer_call(...)` against the externally-supplied `token` account [2](#0-1) . This is a normal cross-contract call to an arbitrary attacker-controlled account — the actual token custody change (debiting the Verifier's balance on `token`, crediting `receiver_id`) happens synchronously inside `token`'s own contract logic, driven entirely by code the attacker deployed.

`mt_resolve_withdraw` then inspects the promise result to decide how much to refund back into `sender_id`'s Verifier balance:

```
let mut used = if is_call {
    match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
        Ok(Ok(used)) if used.len() == amounts.len() => used,
        Ok(_) => vec![U128(0); amounts.len()],   // <-- treats mismatched length as "nothing used"
        Err(_) => amounts.clone(),                // <-- deliberately opposite choice for gas-DoS case
    }
    ...
``` [3](#0-2) 

The `Err(_)` branch intentionally assumes "fully used, no refund" to defend against a known NEP-141-style gas-griefing vulnerability (per the inline comment). But the `Ok(_)` wrong-length branch does the **opposite**: it assumes "nothing used, full refund." Since `token` is fully attacker-controlled, the attacker can make `mt_batch_transfer_call`'s resolved value be a `Vec<U128>` of the wrong length (e.g., too short or too long) while never returning any tokens back to the Verifier's account on `token`. The refund computation then credits the full `amounts` back to `sender_id` inside the Verifier via `self.deposit(...)` [4](#0-3) , even though the tokens permanently left the Verifier's custody on the external `token` ledger.

No existing guard prevents this: `promise_result_checked_json_with_len` only deserializes/bounds the payload size, it does not enforce semantic correctness of length matching (that check is done ad hoc at each call site) [5](#0-4) ; `#[private]` only restricts the caller to the Verifier itself (the callback), not the semantics of the returned data; there is no cross-check against actual balance movement on the external `token` contract.

### Impact Explanation
The attacker (as `sender_id`, self-authorized owner of the withdraw) ends up with:
1. The real underlying MT tokens, delivered externally to `receiver_id` on the attacker's own `token` contract (never returned to the Verifier), and
2. The full withdrawn amount re-credited into their internal Verifier balance via `self.deposit`.

This is a direct double-credit of value out of the Verifier ("a refund or resolver credit that does not match what failed to settle"), Critical severity. It is repeatable per withdrawal call, across any `token_id`/amount the attacker deposits and withdraws, and drains value the Verifier custodies on behalf of all users backed by that token, since the internal ledger balance no longer corresponds to any real custodied asset.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: they need only (a) deploy their own MT contract and register/deposit some amount of a token type into the Verifier normally, then (b) call `mt_withdraw` with `msg` set (so `is_call = true`) and `token`/`receiver_id` pointing at their own contract/account, and (c) implement `mt_on_transfer`/the transfer-call resolution logic on their own contract to intentionally return a `Vec<U128>` of mismatched length. No relayer, DAO role, or victim key is required. Cost is just gas and a small self-funded deposit; the exploit is deterministic and repeatable.

### Recommendation
Make the `Ok(_)` mismatched-length branch conservative in the same direction as the `Err(_)` branch: treat an untrusted/malformed result as "fully used, no refund" (`amounts.clone()`) rather than "nothing used, full refund" (`vec![U128(0); amounts.len()]`), since the tokens have unconditionally already left custody by the time this callback runs and any refund must be treated as unverifiable data from an adversarial external contract. Change:
```rust
Ok(_) => amounts.clone(), // assume fully used to avoid over-crediting sender
```

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy the Verifier (`defuse`) contract and a malicious MT contract `mal_mt` fully controlled by the attacker, implementing `mt_batch_transfer_call`/`mt_on_transfer`/its own resolver so that the outer `mt_batch_transfer_call` return value is a `Vec<U128>` with length `!= token_ids.len()` (e.g., empty vec, or one extra element), while never transferring anything back to the Verifier's account on `mal_mt`.
2. As attacker, deposit `N` units of a `Nep245TokenId(mal_mt, "tok")` into the Verifier (so `used_id.token_balances` for the Verifier's account on `mal_mt` show `N` and attacker's internal Verifier balance for that `TokenId` is `N`).
3. Call `mt_withdraw(token=mal_mt, receiver_id=attacker, token_ids=["tok"], amounts=[N], msg=Some("..."))`.
4. Assert, after execution:
   - Attacker's Verifier internal balance for `TokenId(Nep245TokenId(mal_mt,"tok"))` == `N` (refunded, per `mt_resolve_withdraw`'s `self.deposit`), and
   - `mal_mt`'s ledger shows the Verifier's account balance decreased by `N` and the attacker's/receiver's account balance increased by `N` (tokens genuinely delivered externally, never returned).
   - This demonstrates `N` (internal) + `N` (external) = `2N` accounted for a single `N`-unit deposit — violating the equality `amount_debited == amount_externally_delivered + amount_refunded`.
