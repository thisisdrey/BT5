## Analysis: `protocol.file.allow=always` re-enables git's CVE-2022-39253 local-file-disclosure class in `git_repository`/`new_git_repository` submodule handling

### Title
Forced `protocol.file.allow=always` in Git submodule updates allows an attacker-controlled remote's `.gitmodules` to read files outside the repository checkout - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`tools/build_defs/repo/git_worker.bzl`'s `update_submodules()` unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init [--recursive]`. This is exactly the setting that upstream Git hardened (default changed from `always` to `user`, disabled for automated/non-interactive submodule fetches) after CVE-2022-39253, where a hostile repository's `.gitmodules` could point a submodule at a local `file://` path and have Git's "local clone" optimization hard-link/copy files from anywhere reachable on the build machine into the checkout. Bazel's repository rule deliberately reinstates the pre-fix, insecure behavior for every `git_repository`/`new_git_repository` invocation that sets `init_submodules = True` or `recursive_init_submodules = True`. [1](#0-0) 

### Finding Description
`update_submodules()` calls `_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive"/"--checkout", "--force", ...)`. The comment justifies this as needed so that "`protocol.file.allow=always` allows the submodule command clone from a local directory" (referencing bazelbuild/bazel#17040). [1](#0-0) 

This flag is passed to `_execute`, which invokes the real `git` binary directly via argv (not a shell), so classic shell-metacharacter injection is not possible here — but the git-level protocol restriction is what's being bypassed. [2](#0-1) 

`git_repo()` is invoked by `git_repository`'s implementation, and clones the `remote` URL supplied in the rule, then optionally runs `update_submodules`: [3](#0-2) 

The `remote`, `branch`, and `tag` attributes are documented as non-reproducible/mutable references — unlike `commit`, they carry no content-addressed pin, so the content actually checked out (including `.gitmodules`) is whatever the hostile origin serves at fetch time: [4](#0-3) [5](#0-4) 

Because `protocol.file.allow=always` is forced on, an attacker who controls the content served at the pinned/tracked ref (e.g. a `branch`/`tag`-based `git_repository`, or any mutable ref where no integrity/commit hash is declared) can ship a `.gitmodules` entry with a `url = "file:///absolute/or/relative/path"` pointing outside the intended checkout tree (e.g. another already-checked-out external repo, a shared cache directory, or other paths reachable on the build host). Git's local-clone fast path for `file://` submodules will read/hard-link that filesystem content directly into the submodule's destination inside the external repository directory — a read that escapes the intended external-repository boundary and pulls arbitrary local build-machine files into content that subsequent BUILD/Starlark logic (`glob`, `read`, `genrule` `srcs`, etc.) can consume and re-expose in build outputs.

### Impact Explanation
This is a read-outside-the-repository primitive driven entirely by attacker-served repository content, satisfying "read outside the repository/exec root" for a `git_repository`/`new_git_repository` dependency that uses `init_submodules`/`recursive_init_submodules` without a `commit`-pinned (content-addressed) reference. Disclosed file content becomes visible to the rest of the build graph and can be exfiltrated through normal build artifacts, causing information disclosure of files the attacker should not otherwise be able to read.

### Likelihood Explanation
Requires: (1) a `git_repository`/`new_git_repository` target with `init_submodules = True` or `recursive_init_submodules = True`, and (2) the `remote`/`branch`/`tag` (mutable, non-content-pinned) attribute set so the attacker fully controls the served commit content, including `.gitmodules`. This is a realistic, common configuration for third-party dependencies that are tracked by branch rather than pinned commit.

### Recommendation
Do not force `protocol.file.allow=always` for submodule updates. Restrict it to the minimal case actually needed (e.g. only for local-file-based testing paths under `bazelbuild/bazel#17040`), or explicitly restrict submodule URL schemes (e.g. via `protocol.file.allow=user`/deny plus an allow-list of `https`/`ssh`) so a repository's own `.gitmodules` cannot direct Git to clone from local filesystem paths outside the checkout.

### Proof of Concept
A `src/test/shell/bazel` integration test can reproduce this: serve a git repository (e.g. via a local `git daemon` or `file://` served test fixture) whose `.gitmodules` contains a submodule pointing at `file://$TEST_TMPDIR/secret_dir` (a directory outside the workspace containing a marker file), reference it from a `git_repository(..., init_submodules = True)` rule using a `branch` (not `commit`) attribute, run `bazel build`, and assert that the marker file's content appears inside the external repository's submodule directory — demonstrating the local-file read despite the attacker not being the build's operator.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
