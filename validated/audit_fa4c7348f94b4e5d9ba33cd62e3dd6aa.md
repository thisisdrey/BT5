### Title
DeleteAccount + CreateAccount race allows a stale PostponedReceipt to execute against a recreated account - ([File: runtime/runtime/src/lib.rs], [File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only clears `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but never clears `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt`. When an account with a postponed multi-input-data `ActionReceipt` is deleted and then recreated before the pending `Data` receipts arrive, `process_receipt`'s `Data` branch will still find the stale `PostponedReceiptId`/`PendingDataCount` entries and eventually call `apply_action_receipt` on the old, now-orphaned `PostponedReceipt`, executing its actions against the newly created account/contract.

### Finding Description
`remove_account` ( [1](#0-0) ) removes `Account`, `ContractCode`, access keys, gas key nonces, and `ContractData`, but has no logic to enumerate or clear `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` entries for the account being deleted.

Meanwhile, `process_receipt`'s `Data` branch ( [2](#0-1) ) looks up `TrieKey::PostponedReceiptId{receiver_id, data_id}` purely from trie state, decrements `PendingDataCount`, and when it hits zero, fetches the `PostponedReceipt` via `get_postponed_receipt` and calls `apply_action_receipt` on it — with no check that the account has been deleted/recreated in the interim, and no check that the "receiver" identity is the same account instance that existed when the receipt was postponed.

So the exploit path is:
1. Attacker (or anyone) causes a `FunctionCall` receipt targeting account `X` with `input_data_ids=[d1,d2]` to be postponed, writing `PostponedReceiptId{X,d1}`, `PostponedReceiptId{X,d2}`, `PendingDataCount{X,receipt_id}=2`, and `PostponedReceipt{X,receipt_id}`.
2. Before `d1`/`d2` arrive, the account owner (attacker, if they control `X`) submits `DeleteAccount(X)` and then `CreateAccount(X)` with a new key/contract in the same or later block/chunk.
3. `remove_account` is invoked during `DeleteAccount` processing but does not touch the postponed-receipt bookkeeping, so those trie entries survive under the same account_id.
4. When `d1` and `d2` eventually arrive as `Data` receipts, `process_receipt`'s Data branch decrements `PendingDataCount` to 0, fetches the old `PostponedReceipt`, and executes it via `apply_action_receipt` — but by now `X` refers to the new account/contract state.

This breaks the authorization-exactness invariant: a promise created against the *old* `X` account executes against the *new* `X`'s contract, potentially with the new contract's storage being mutated by actions the new account owner never authorized, at attacker-controlled timing (they control when they submit the delete+recreate and can attempt to time it against inbound data receipts).

I was not able to fully verify within the available iterations (a) the exact code of `action_delete_account`/`action_create_account` in `runtime/runtime/src/actions.rs` to confirm there is no separate guard rejecting `DeleteAccount` while postponed receipts exist, and (b) whether protocol-level receipt ordering/congestion-control guarantees (e.g., same-shard receipt processing order, delayed receipt queue ordering) might make the "Data receipts arrive after DeleteAccount+CreateAccount for the same account in the same shard" ordering actually unreachable in practice. Given the receipt pipeline is typically FIFO per-shard and `DeleteAccount`/`CreateAccount` receipts sent from the same predecessor to the same receiver would generally be processed in the order they were sent, and given `Data` receipts are separate receipts generated by a different predecessor chain (the callee that resolves the promise), whether they can be reordered relative to `DeleteAccount`+`CreateAccount` receipts targeting `X` depends on receipt routing/execution order guarantees I could not fully trace in this session (delayed receipt queue, congestion control buffering, and gas/shard scheduling in `runtime/runtime/src/lib.rs`).

### Impact Explanation
If the described ordering is achievable, this is an authorization escalation / arbitrary code injection into a victim's re-created account: the old owner's postponed promise callback executes against the new owner's contract state, potentially draining funds, corrupting contract state, or triggering unintended cross-contract calls with `predecessor_id` matching `X` itself (self-calls bypassing intended access checks). This would map to NEAR's "authorization escalation across accounts or promises" / "state-root divergence" bounty category if reproducible on all nodes deterministically (which it would be, since this is a pure state-transition function executed identically by all validators, so it does not by itself cause a chain split — every node computes the same wrong result).

### Likelihood Explanation
Uncertain without further verification. The precondition (delete+recreate an account you own, with an outstanding postponed callback, timed against pending data receipts) is something only the account owner can trigger for their own account, meaning the "attacker" would primarily be attacking themselves unless a third party can also submit `DeleteAccount`/`CreateAccount` for `X` — which is not the case, since only `X`'s own full-access key can sign those actions for `X`. This substantially narrows the impact: the "new owner" and "old owner" would need to be different entities gaining/losing control of the account across the delete/recreate boundary within the same block of pending callbacks, which requires precise control over receipt timing that a single unprivileged account holder does not fully have (receipt delivery timing is determined by the runtime/shard scheduler, not by the attacker directly). I could not confirm a concrete, attacker-controlled way to guarantee the required interleaving without deeper tracing of the receipt delay/congestion queue and cross-shard scheduling code, which was not completed in this session.

### Recommendation
`remove_account` should also enumerate and remove all `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` trie entries for the account being deleted (similar to how it already iterates access keys and contract data by prefix), and any associated `ReceivedData` entries, refunding/dropping in-flight postponed receipts rather than leaving them dangling for a potential future re-creation of the same `account_id`.

### Proof of Concept
Integration/runtime test-loop plan (not fully executed in this session — recommend validation before filing):
1. Create account `X` with a contract that issues a `FunctionCall` promise depending on two data receipts (`input_data_ids=[d1,d2]`), causing `PostponedReceiptId{X,d1}`, `PostponedReceiptId{X,d2}`, `PendingDataCount{X,receipt_id}=2`, `PostponedReceipt{X,receipt_id}` to be written.
2. In the same/subsequent block, submit `DeleteAccount(X)->beneficiary` followed by `CreateAccount(X)` with a new key and a different (instrumented) contract.
3. Deliver `Data` receipts for `d1` then `d2`.
4. Assert: `apply_action_receipt` is invoked on the old `PostponedReceipt` and its actions execute against the new account `X`'s contract/state (e.g., the new contract's storage is mutated in a way the new owner did not author), and that `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries persisted across the `remove_account` call in step 2. pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
