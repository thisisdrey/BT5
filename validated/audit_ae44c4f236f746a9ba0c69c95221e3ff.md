### Title
EIP-8264 `finaliseAmsterdam` self-destruct handling resurrects the ORIGINAL nonce/code/storage instead of clearing them for pre-existing contracts - (`core/state/statedb.go`)

### Summary
`StateDB.finaliseAmsterdam` implements the (repo-local) EIP-8264 SELFDESTRUCT semantics: a self-destructed account that ends the transaction with non-zero balance is supposed to survive as a "balance-only account" — nonce reset to 0, code cleared, storage cleared — exactly as the code's own comment states. However, the implementation builds the replacement object from `obj.origin` (the account's state *before this transaction*) rather than from an empty account, so for any contract that already existed prior to the transaction (i.e. was not created in the same tx), the resulting persisted account retains its pre-tx nonce, code hash and storage root — only the balance field is actually reset/overwritten.

For a contract that was created earlier (in a previous transaction/block) and is now self-destructing while ending with a non-zero balance, `obj.origin` is the account's pre-transaction `*types.StateAccount` — with its real `Nonce`, `CodeHash`, and storage `Root`. Passing this non-nil `origin` into `newObject` means the freshly-finalised account is built with those *original* fields, and only `Balance` is subsequently overwritten via `o.setBalance(...)`. Nonce is **not** reset to 0, code is **not** cleared, and storage is **not** cleared — directly contradicting the behavior documented in the surrounding comment and required by EIP-8264/EIP-8246 ("balance-only account: nonce reset to 0 and no code... storage must be cleared", as also asserted by this repo's own tests).

The only tests exercising this code path (`TestEIP8246SelfdestructNoBurn`, `TestEIP8246SelfdestructRefunded`) both self-destruct a contract that was *created within the same transaction* — in that case `obj.origin` is `nil` (the account didn't exist before the tx), so `newObject` falls into the `acct == nil` branch and correctly synthesizes an empty account. This masks the bug: it never exercises the case of a pre-existing contract self-destructing with a non-zero end-of-tx balance, which is exactly the scenario that hits `newObject(s, obj.address, obj.origin)` with a non-nil, non-empty origin.

### Impact Explanation
This is the direct analog of the Taurus finding: a piece of persisted state ("debt"/here nonce+code+storage) that the code explicitly documents and intends to reset to zero on a destructive event is instead left populated from stale pre-event data on one code branch. Concretely:
- A pre-existing contract that self-destructs but is refunded (e.g. re-funded by another call in the same tx, or already carrying a balance the destructor doesn't drain) will finalize with its **old code and old storage root still present** and **its old nonce retained** instead of being wiped, even though its balance is correctly kept.
- This produces a `stateRoot` that differs from what a correct implementation of the documented/intended EIP-8264 semantics would compute — a state divergence bug (Critical-class stateRoot mismatch under this repo's own consensus rules), since the account object committed to the trie carries fields (nonce, codeHash, root) that should have been reset but were not.
- It also means the "destroyed" contract's old code remains callable/executable going forward (since `CodeHash` is unchanged) and its old storage slots remain readable, effectively undoing the SELFDESTRUCT's intended state-clearing effect for any account satisfying this condition.

### Likelihood Explanation
Any self-destructing contract that (a) existed prior to the transaction and (b) ends the transaction with a non-zero balance takes this path — this is a common, easily-triggerable scenario (e.g. a contract that receives value after marking itself for destruction, or is called with value in the same call that triggers SELFDESTRUCT). This is not a corner case requiring privileged access; a single ordinary transaction against an existing contract can trigger it.

### Recommendation
When constructing the balance-only replacement object in the `obj.selfDestructed` branch of `finaliseAmsterdam`, always start from an empty account (nil origin) rather than `obj.origin`, e.g.:
```go
o := newObject(s, obj.address, nil)
o.setBalance(new(uint256.Int).Set(obj.Balance()))
```
so that nonce, code hash, and storage root are unconditionally reset regardless of whether the account existed prior to the transaction, matching the documented EIP-8264 semantics. Add a regression test that self-destructs a *pre-existing* contract (created in a prior block, with non-empty code/storage/non-zero nonce) and ends the transaction with a non-zero balance, then asserts nonce == 0, code size == 0, and all storage slots are cleared.

### Proof of Concept
1. Deploy contract `AA` in block N with `Nonce > 0`, non-empty `Code`, and storage slots set (analogous to the existing `testDeleteRecreateAccount` fixture but simpler — no recreation needed).
2. In block N+1 (Amsterdam active), send a transaction that calls `AA`, which executes `SELFDESTRUCT(AA)` (self-beneficiary) while `AA` has a non-zero balance (or is refunded value after the SELFDESTRUCT within the same tx, mirroring `TestEIP8246SelfdestructRefunded`'s factory pattern but on a pre-existing, not newly-created, contract).
3. After the block is finalized (`Finalise`/`finaliseAmsterdam` runs), read back state at the new root:
   - `GetNonce(AA)` — expected `0` per the EIP-8264 comment, but actual value equals the pre-tx nonce.
   - `GetCodeSize(AA)` — expected `0`, but actual code remains from before the tx.
   - `GetState(AA, slot)` — expected cleared (`0x00..0`), but actual value equals the pre-tx storage value.
4. This demonstrates the persisted state at the new root diverges from the specification's documented intent (nonce=0, code cleared, storage cleared), confirmed directly by the code path cited in `core/state/statedb.go` lines 881-885 and `core/state/state_object.go` lines 96-106.
