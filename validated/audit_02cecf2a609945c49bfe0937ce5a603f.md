### Title
Unbounded / amplifiable precompile signature-verification loops enable underpriced CPU-exhaustion DoS - (File: precompiles/src/secp256k1.rs, precompiles/src/ed25519.rs, precompiles/src/secp256r1.rs)

### Summary
The `verify()` functions for the `secp256k1`, `ed25519`, and `secp256r1` precompile programs each run an unbounded, attacker-controlled loop (`for i in 0..num_signatures`) performing expensive cryptographic verification per iteration [1](#0-0) [2](#0-1) [3](#0-2) . This is the closest reachable analog to the reported Forta `redeem` unbounded-loop DoS pattern (attacker-influenced loop count driving unbounded per-unit work).

### Finding Description
Each precompile's instruction data begins with a single byte `num_signatures` that directly controls the loop bound: up to 255 for `secp256k1`/`ed25519` [4](#0-3) [5](#0-4) , and up to 8 for `secp256r1` [6](#0-5) . Critically, the signature/pubkey/message offsets in each iteration are attacker-supplied indices that can point into *any* instruction's data in the same transaction (via `signature_instruction_index`, `public_key_instruction_index`, `message_instruction_index`), including reusing a single tiny instruction repeatedly [7](#0-6) . This lets an attacker cram many expensive verifications (secp256r1 uses OpenSSL ECDSA `Verifier` over an EC curve — the most expensive of the three [8](#0-7) ) into a small transaction by pointing multiple precompile instructions at the same few bytes of signature/message data, and by including many such precompile instructions in one transaction.

The cost model does account for `SECP256R1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, and `SECP256K1_VERIFY_COST` per counted signature [9](#0-8) [10](#0-9) , and fees scale with total signature count [11](#0-10) . This pricing is derived purely from the single `num_signatures` byte per instruction [12](#0-11)  and does not account for the actual instruction-data reuse/aliasing that the `verify()` functions permit, so the priced cost is a rough proxy, not a hard bound tied to the true amount of distinct cryptographic material processed.

### Impact Explanation
If precompile verification (`verify_if_precompile` / `Precompile::verify`) is invoked prior to (or independent of) the point where a transaction is dropped for exceeding block/account cost limits, an attacker can force validators to spend disproportionate CPU on OpenSSL EC verification for transactions that are cheap to construct and may ultimately be rejected or never landed, degrading validator throughput. Because loop bounds and aliasing are attacker-controlled and not hard-capped against actual distinct data processed, this matches the reported bug class of "unbounded loop driven by attacker input causing compute exhaustion," now expressed through the precompile signature-verification path rather than a smart-contract redeem loop.

### Likelihood Explanation
I was **not able to fully confirm**, within the scope of this repo index, the exact call ordering between `Bank::verify_transaction`/`verify_precompiles` and the cost-tracker/QoS rejection path in the banking stage or blockstore replay path — i.e., whether precompile verification for a given transaction always occurs strictly after cost/QoS acceptance (in which case the existing signature-cost accounting already gates this) or can occur before such gating for some code paths (replay verification, forwarding, or simulate paths). This ordering is decisive for whether the amplification described above yields real underpriced CPU work or is already fully covered by the existing per-signature cost/fee charge. Given the effort/tooling constraints of this pass, I cannot assert a concrete, currently-exploitable gap with certainty.

### Recommendation
Not applicable without confirming the call-path ordering above; if pursued, verify whether `verify_if_precompile`/`Bank::verify_transaction` can be reached for a transaction before cost-tracker/QoS-based rejection in all ingestion paths (QUIC/TPU receive, forwarding, replay), and whether repeated aliasing of a single instruction's data across many signature slots is intended/priced correctly.

### Proof of Concept
Not established — the described aliasing loop is structurally present in `precompiles/src/secp256r1.rs`, `precompiles/src/ed25519.rs`, and `precompiles/src/secp256k1.rs`, but a working end-to-end PoC requires confirming the ordering issue above, which could not be completed in this session.

```rust
fn get_data_slice<'a>(
    data: &'a [u8],
    instruction_datas: &'a [&[u8]],
    instruction_index: u16,
    offset_start: u16,
    size: usize,
) -> Result<&'a [u8], PrecompileError> {
    let instruction = if instruction_index == u16::MAX {
        data
    } else {
        let signature_index = instruction_index as usize;
        if signature_index >= instruction_datas.len() {
            return Err(PrecompileError::InvalidDataOffsets);
        }
        instruction_datas[signature_index]
    };

    let start = offset_start as usize;
    let end = start.saturating_add(size);
    if end > instruction.len() {
        return Err(PrecompileError::InvalidDataOffsets);
    }

    Ok(&instruction[start..end])
}
```

```rust
/// Calculate fees from signatures.
pub fn calculate_signature_fee(
    SignatureCounts {
        num_transaction_signatures,
        num_ed25519_signatures,
        num_secp256k1_signatures,
        num_secp256r1_signatures,
    }: SignatureCounts,
    lamports_per_signature: u64,
) -> u64 {
    let signature_count = num_transaction_signatures
        .saturating_add(num_ed25519_signatures)
        .saturating_add(num_secp256k1_signatures)
        .saturating_add(num_secp256r1_signatures);
    signature_count.saturating_mul(lamports_per_signature)
}
```
