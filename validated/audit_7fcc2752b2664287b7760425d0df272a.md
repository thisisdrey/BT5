## Analog Found

### Title
Single-step `owner` permission key replacement in `AccountPermissionUpdateContract` can permanently lock an account with no recovery path - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The C4 report describes `changeUberOwner()` allowing a privileged role to be reassigned to an unverified address in a single transaction, with no way to recover if the address is wrong. The same bug class exists in java-tron's account-permission (multi-sig) system: `AccountPermissionUpdateActuator` lets the current `Owner` permission holder replace the entire set of `Owner` permission keys in one atomic, single-step transaction, with only address-format validation (no proof-of-possession of the private key), and the `Owner` permission is the sole permission capable of ever changing permissions again.

### Finding Description
`AccountPermissionUpdateActuator.validate()` accepts an `AccountPermissionUpdateContract` and validates the new `owner` `Permission` via `checkPermission()`. For each key in the new permission, it only checks address well-formedness: [1](#0-0) 
No signature, ownership proof, or "claim" step is required from the new key addresses. `execute()` then immediately overwrites the account's permissions in one step: [2](#0-1) 

Critically, any future `AccountPermissionUpdateContract` for that account (including one to fix a mistaken key) must itself be authorized by the `Owner` permission (`permissionId == 0`), since permission-changing transactions are gated by the owner's permission and weight threshold in `TransactionCapsule.validateSignature`/`checkWeight`: [3](#0-2) 

If the new `owner` permission's keys are set to addresses the account holder does not control (typo, wrong copy-paste, or an address with no known private key), there is no second confirmation step to catch the mistake before it takes effect, and no path exists afterward to correct it — mirroring the `uberOwner` bug exactly, just applied to per-account multi-sig ownership rather than a factory-level admin role.

### Impact Explanation
Once the `Owner` permission's keys are irrecoverably set to inaccessible addresses, the account can never again submit a valid `AccountPermissionUpdateContract` (which requires `Owner`-permission signatures), permanently freezing that account's ability to manage its own permission structure. Any account whose `Active` permissions later need adjustment, or whose `Owner` key set was compromised/mistyped, has no recovery mechanism — an irreversible, permanent loss of administrative control over the account's multisig configuration. This satisfies the "permanent freezing of funds/control" impact bar, since assets under active permissions may remain unmanageable and unmigrable if operational needs change.

### Likelihood Explanation
Low probability (requires a genuine user/operator mistake when submitting a permission-update transaction with a large `Owner` key set) but high impact when it occurs, consistent with the original report being rated Medium risk ("very low probability coupled with very high impact"). Any account owner using TRON's native multisig (`AllowMultiSign`) feature is exposed, since this is a standard, unprivileged, broadcastable transaction type reachable directly from `Wallet`/`TronJsonRpcImpl` transaction creation endpoints.

### Recommendation
Introduce a two-step confirmation process for `Owner` permission changes: the current `Owner` permission proposes a `pendingOwner` permission structure, and a subsequent transaction — signed under the *new* `Owner` keys — must confirm/claim it before it takes effect. Alternatively, require that the new owner permission's keys demonstrate control (e.g., a co-signature from at least one new key) before the update is finalized, and/or add a time-locked rollback window during which the previous `Owner` permission can revert an erroneous update.

### Proof of Concept
1. Account `A` has `AllowMultiSign` enabled and default `Owner`/`Active` permissions.
2. `A`'s current `Owner` key submits `AccountPermissionUpdateContract` setting the new `Owner` permission's `keys` to an address `B` for which no one holds the private key (typo/wrong paste), satisfying only `checkPermission()`'s format/threshold checks. [4](#0-3) 
3. The transaction is validated and executed, overwriting `A`'s stored `Owner` permission via `account.updatePermissions(...)`. [5](#0-4) 
4. Any subsequent attempt to submit another `AccountPermissionUpdateContract` for account `A` (e.g., to correct the mistake) fails signature verification, because `TransactionCapsule.validateSignature` requires signatures meeting the `Owner` permission threshold from keys nobody controls. [6](#0-5) 
5. Account `A`'s permission configuration is now permanently frozen with no recovery path.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
