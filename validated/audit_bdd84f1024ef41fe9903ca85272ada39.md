### Title
Unconditional Decrease of Receiver's Acquired Delegated Bandwidth/Energy in `UnfreezeBalanceActuator` Can Underflow to a Negative Balance - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`)

### Summary
`UnfreezeBalanceActuator.execute()` maintains two mirrored accounting records for a delegated resource relationship: the owner-side `DelegatedResourceCapsule` (frozen balance for bandwidth/energy) and the receiver-side `AccountCapsule` (`AcquiredDelegatedFrozenBalanceForBandwidth`/`...ForEnergy`). The owner-side record is always fully reset to `0` on unfreeze, but the receiver-side record is only clamped to `0` when `dynamicStore.getAllowTvmSolidity059() == 1` and the receiver's acquired balance is *already* less than the amount being unfrozen; otherwise the code unconditionally subtracts the full `unfreezeBalance` from the receiver's tracked value. This is the same asymmetric increase/decrease pattern described in the external report: one side of a paired ledger is adjusted unconditionally by the full amount while the other side's adjustment is only conditionally safe, allowing the two sides to diverge.

The legacy `UnfreezeBalanceActuator` path does not use this safe helper in all cases — it only avoids underflow when `getAllowTvmSolidity059()` is active, leaving a code path where the owner side fully decreases its bookkeeping to zero while the receiver side can be driven negative (or, depending on ordering of prior delegate/undelegate operations across the V1/V2 resource models, diverge from the true delegated amount).

### Impact Explanation
`AcquiredDelegatedFrozenBalanceForBandwidth`/`ForEnergy` values feed directly into net/energy weight and usage accounting for the receiving account. A negative or corrupted value here can distort bandwidth/energy entitlement calculations for that account (used throughout `BandwidthProcessor`/`EnergyProcessor`), potentially granting incorrect free resource, causing incorrect fee charging, or leading to inconsistent state that diverges between nodes if the divergence interacts with fork-dependent branches (`getAllowTvmSolidity059`) that differ across network configurations.

### Likelihood Explanation
This is reachable by any account issuing a plain `UnfreezeBalanceContract` transaction against a delegated resource it previously granted to another account, i.e., a fully unprivileged, broadcastable transaction. The trigger condition depends on the receiver's acquired balance being less than the amount being unfrozen while `getAllowTvmSolidity059` is not active for the current chain parameters — a state achievable through legitimate sequences of freeze/delegate/unfreeze operations, particularly interactions with contract accounts that self-destruct and are recreated (a scenario the codebase itself calls out as expected in the V2 `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` comments).

### Recommendation
Replace the unconditional `addAcquiredDelegatedFrozenBalanceForBandwidth(-unfreezeBalance)` / `...ForEnergy(-unfreezeBalance)` calls in `UnfreezeBalanceActuator` with the same floor-clamped, `disableJavaLangMath`-aware helper already used in `UnfreezeBalanceProcessor` (`safeAddAcquiredDelegatedFrozenBalanceForBandwidth`/`...ForEnergy`), regardless of the `getAllowTvmSolidity059` flag, so that the receiver-side ledger can never be decreased below zero independent of how much the owner-side ledger was decreased, mirroring the report's recommendation to make the paired increase/decrease operations symmetric.

### Proof of Concept
Not independently executable from static analysis alone; a concrete underflow requires reconstructing a specific sequence of freeze/delegate/unfreeze (or V1/V2 resource-model interleavings) that leaves the receiver's `AcquiredDelegatedFrozenBalanceForBandwidth` below the `unfreezeBalance` being reclaimed while `getAllowTvmSolidity059` is inactive for the target network; this could not be fully validated with static/indexed reading alone and would need dynamic testing (e.g., via a Devin session with test execution) to confirm the exact state transitions that trigger the unconditional subtraction path.
