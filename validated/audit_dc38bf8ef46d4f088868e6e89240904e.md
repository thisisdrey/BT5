### Title
Attacker-controlled attachment content is stored in `AtlasDB` without verifying `Attachment::hash()` matches the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
In `AttachmentsDownloader::run`, when the `AttachmentsBatchStateMachine` reaches `Done`, every `Attachment` collected in `context.attachments` is looked up and stored using `attachment.hash()` — the hash *recomputed from the received bytes* — rather than the `AttachmentRequest.content_hash` that was actually requested. A malicious peer that is listed as a source for some `content_hash` (by lying in its `GetAttachmentsInvResponse`) can respond to the corresponding `/v2/attachments/<content_hash>` GET with arbitrary content whose hash does not match the request, and that unrequested content is unconditionally written into `AtlasDB` via `insert_instantiated_attachment`.

### Finding Description
The requested hash is never compared against the received content's hash anywhere in this path:

- `AttachmentsBatchStateContext::extend_with_attachments` decodes the HTTP response and inserts the returned `Attachment` into `self.attachments` purely based on `response.decode_atlas_get_attachment()` succeeding, with no comparison to `request.content_hash`: [1](#0-0) 

- In `AttachmentsDownloader::run`'s `Done` arm, the loop iterates `context.attachments.drain()` and, for each attacker-supplied `Attachment`, calls `find_all_attachment_instances(&attachment.hash())` and unconditionally `insert_instantiated_attachment(&attachment)` — using the hash *derived from the received bytes*, not the originally requested `content_hash`: [2](#0-1) 

- The only place the request's `content_hash` is used downstream is `context.attachments_batch.resolve_attachment(&attachment.hash())`, which also uses the *received* hash, so it cannot "catch" the mismatch — it simply fails silently to resolve the original pending instance while the garbage content is already stored.

- `insert_instantiated_attachment` is demonstrably capable of inserting brand-new attachment rows (not just updating pre-existing ones), because it is called on attachments that were fetched precisely *because* no local attachment row existed for them (they only reach the download queue after `check_attachment_instances` failed to find them via `find_attachment`/`find_uninstantiated_attachment`): [3](#0-2) 

Because a peer becomes a "source" for a `content_hash` merely by self-reporting a `1` bit in its attachments inventory response (`AttachmentsBatchStateContext.inventories`, populated in `extend_with_inventories` with no cross-check against real content), an attacker fully controls both (a) being selected as a download source for a given `content_hash`, and (b) the bytes returned for that download, with no signature or hash-binding enforced before the write to `AtlasDB`.

### Impact Explanation
A remote, unprivileged peer can cause a victim node to persist arbitrary attacker-chosen byte blobs into its `AtlasDB` attachments table, keyed under a hash the attacker fully controls (since it's simply `Hash160::from_data(content)` of whatever bytes they send), with zero on-chain `AttachmentInstance` ever committing to that content. This is an unauthenticated write to node storage state, repeatable per attachment-batch cycle, enabling storage growth with content that carries no consensus backing — matching the "Critical: unauthenticated/unauthorized write to state" category.

### Likelihood Explanation
Preconditions are attacker-cheap: the attacker just needs to run a peer that (1) is selected as an outbound sync peer / data-URL source, (2) responds to `GetAttachmentsInv` requests with a fabricated inventory bit set for the target `content_hash` so it appears in `AttachmentsBatchStateContext.inventories`/sources, and (3) responds to the follow-up `/v2/attachments/<content_hash>` GET with arbitrary content. No secret, signature, or privileged role is required — this is a normal Atlas peer-to-peer HTTP exchange. The behavior is deterministic and repeatable on every batch cycle where the attacker is chosen as a source.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or immediately before storing in `AttachmentsDownloader::run`), verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`/before calling `insert_instantiated_attachment`; drop and penalize (bump failed requests / mark faulty) any peer whose returned content does not match the requested hash.

### Proof of Concept
Rust test plan in `stackslib::net::atlas`:
1. Build an `AttachmentsBatchStateContext` with one peer URL, and an `attachments_batch` containing one legitimate `AttachmentInstance` with `content_hash = H_legit`.
2. Populate `context.inventories` so that the peer is a valid source for `H_legit` (as `get_prioritized_attachments_requests` would produce).
3. Simulate `extend_with_attachments` by constructing a `BatchedRequestsResult` where the `succeeded` response for the `AttachmentRequest{content_hash: H_legit, ...}` decodes to a `GetAttachmentResponse{ attachment: Attachment{ content: b"malicious" } }`, i.e. `Hash160::from_data(b"malicious") != H_legit`.
4. Drive the state machine into `AttachmentsBatchStateMachine::Done` and call the equivalent of the `run` loop body directly on `network.atlasdb`.
5. Assert `network.atlasdb.find_attachment(&Hash160::from_data(b"malicious")).unwrap().is_some()` is `true` (unrequested content stored), while `network.atlasdb.find_attachment(&H_legit).unwrap()` remains `None` (the originally requested attachment was never actually resolved).
