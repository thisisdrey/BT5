### Title
Permissionless energy/bandwidth stake dilution via `FreezeBalance`/`FreezeBalanceV2` degrades every other staker's resource share, mirroring the Ajna EMA-ratio griefing pattern - ([File: chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java])

### Summary
The Ajna bug lets an unprivileged actor pledge outsized, near-idle "collateral" into a shared ratio (`Debt/LUP*Collateral`) that every other participant's pricing depends on, permanently skewing that ratio to their detriment for a cost proportional only to the collateral asset's opportunity cost. java-tron has a structurally identical shared-ratio resource model: any account can call `FreezeBalanceContract`/`FreezeBalanceV2Contract` to add stake to the global `TotalEnergyWeight`/`TotalNetWeight` denominator used to compute every staker's personal resource allocation, without ever consuming the resource they staked for.

### Finding Description
`FreezeBalanceActuator.execute` and `FreezeBalanceV2Processor.execute` let any signed transaction increase `totalEnergyWeight`/`totalNetWeight` in `DynamicPropertiesStore` proportionally to the frozen TRX amount: [1](#0-0)  and [2](#0-1) , with the denominator update itself performed unconditionally in [3](#0-2) .

Every account's actual energy allowance is computed as a simple linear share of a fixed pool: `frozenBalance/TRX_PRECISION * totalEnergyLimit / totalEnergyWeight`, in both the legacy and V2 code paths: [4](#0-3)  and the VM-facing equivalent [5](#0-4) . Critically, `totalEnergyLimit` (the numerator, the "target utilization" analog) is only adjusted via `updateAdaptiveTotalEnergyLimit`, which reacts to *actual measured block energy usage* (`totalEnergyAverageUsage` vs `totalEnergyTargetLimit`) — not to how much TRX is frozen: [6](#0-5) .

This reproduces the exact Ajna mechanic: a party can add a large amount of low-activity "collateral" (frozen TRX for ENERGY/BANDWIDTH) that inflates the shared denominator without contributing to the numerator (no corresponding rise in actual usage/limit), permanently diluting the resource-per-TRX ratio that every other already-staked, honest account relies on — until the attacker unfreezes. There is no cap on how much one account may freeze relative to the network total, and there is no debt/usage-weighting of the denominator (the fix Ajna adopted — weighting collateral by corresponding debt/usage — is exactly what's missing here too).

### Impact Explanation
Every legitimate account that has already frozen TRX for ENERGY/BANDWIDTH sees its per-TRX resource allowance (`calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`) drop proportionally as soon as the attacker's freeze transaction lands, forcing them either to freeze additional TRX (capital cost) or to burn TRX fees to execute the same transactions they could previously execute for free — a direct, network-wide, involuntary degradation of value for existing stakers caused by a single unprivileged transaction, exactly analogous to "current borrowers experiencing losses from the manipulated ... rate" in the Ajna report.

### Likelihood Explanation
The action requires only a single signed `FreezeBalanceContract` or `FreezeBalanceV2Contract` transaction from any account with sufficient TRX; it is fully permissionless, requires no special privileges, and — like the Ajna attack — the primary "cost" to the attacker is the opportunity cost of locking the TRX rather than loss of principal, making it a low-cost, high-leverage griefing vector reachable by any wallet.

### Recommendation
Weight the frozen-balance denominator contribution by demonstrated resource consumption (analogous to Ajna's debt-weighted collateral fix), or introduce diminishing/decayed weighting for large low-utilization freezes, and/or cap the rate at which a single account's freeze can move `totalEnergyWeight`/`totalNetWeight` per epoch so idle stake cannot instantaneously and disproportionately dilute other accounts' resource share.

### Proof of Concept
1. Attacker observes current `totalEnergyWeight` W and `totalEnergyCurrentLimit` L in `DynamicPropertiesStore`.
2. Attacker sends one `FreezeBalanceV2Contract` transaction freezing a very large TRX amount F for `ENERGY`, calling `FreezeBalanceV2Processor.execute`, which calls `repo.addTotalEnergyWeight(F/TRX_PRECISION)` (`actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceV2Processor.java:90-95`), immediately setting `totalEnergyWeight = W + F/TRX_PRECISION`.
3. Any other honest account with previously frozen balance B now gets `calculateGlobalEnergyLimit = B/TRX_PRECISION * L / (W + F/TRX_PRECISION)` (`chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java:168-179`), strictly smaller than before, even though the attacker never triggers any contract to actually consume energy — `totalEnergyCurrentLimit` L does not rise in response because `updateAdaptiveTotalEnergyLimit` only tracks measured usage, not frozen weight (`chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java:65-93`).
4. Attacker later calls `UnfreezeBalanceV2Contract` to reclaim F (subject to the unfreeze/withdraw delay), having paid only the opportunity cost of locking F for that period while degrading every other staker's energy allowance in the interim.

  public void updateAdaptiveTotalEnergyLimit() {
    long totalEnergyAverageUsage = dynamicPropertiesStore
        .getTotalEnergyAverageUsage();
    long targetTotalEnergyLimit = dynamicPropertiesStore.getTotalEnergyTargetLimit();
    long totalEnergyCurrentLimit = dynamicPropertiesStore
        .getTotalEnergyCurrentLimit();
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyLimit();

    long result;
    if (totalEnergyAverageUsage > targetTotalEnergyLimit) {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_DENOMINATOR);
    } else {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.EXPAND_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.EXPAND_RATE_DENOMINATOR);
    }
    long upperBound = hardenCalculation()
        ? BigInteger.valueOf(totalEnergyLimit).multiply(BigInteger.valueOf(
            dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier())).longValueExact()
        : totalEnergyLimit * dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier();
    result = min(max(result, totalEnergyLimit, this.disableJavaLangMath()),
        upperBound, this.disableJavaLangMath());

    dynamicPropertiesStore.saveTotalEnergyCurrentLimit(result);
    logger.debug("Adjust totalEnergyCurrentLimit, old: {}, new: {}.",
        totalEnergyCurrentLimit, result);
  }

    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {

    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {

      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
