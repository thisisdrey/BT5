Audit Report

## Title
Remote fee rounding to zero lets Snowbridge outbound messages be sent with an unpaid Ethereum relayer reward - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`Pallet::calculate_fee` converts the ETH-denominated relayer reward into a local (DOT) fee via a multi-step fixed-point calculation, but never validates that the resulting `fee.remote` is non-zero before returning it to the sender-charging path. Because `do_process_message` independently derives the `reward` field embedded in the `CommittedMessage` sent to Ethereum from the raw, always-non-zero `pricing_params.rewards.remote`, a sender can be charged `fee.remote == 0` while Ethereum still commits to paying out a real, non-zero reward to relayers.

## Finding Description
`calculate_fee` computes `calculate_remote_fee` in wei, downcasts to `u128`, multiplies by `params.multiplier`, divides by `params.exchange_rate` (guarded only against a zero divisor via `expect`), and then calls `convert_from_ether_decimals` to rescale into local-currency decimals, returning `Fee::from((Self::calculate_local_fee(), fee))` with no check that `fee` (the remote component) is non-zero: [1](#0-0) 

`PricingParameters::validate` only checks that each individual input field (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) is non-zero — it does not, and cannot, guarantee that the *derived* `fee.remote` output of `calculate_fee` stays non-zero after the chained multiplication/division/decimal-rescaling: [2](#0-1) 

The pallet's own test suite reproduces this exact condition: with fully valid, non-zero `PricingParameters` (`exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local: 1, remote: 1}`, `multiplier = 1/1`) and `gas_used = 250000`, `calculate_fee` returns `fee.remote == 0`, and the test comment explicitly flags this as invalid behavior that "should be avoided": [3](#0-2) 

Meanwhile, `do_process_message` — which builds the `CommittedMessage` actually sent to Ethereum — reads `reward` directly from `pricing_params.rewards.remote` (the raw, validated-non-zero configuration value), completely independent of whatever `fee.remote` was charged to the sender at `send_message_impl::validate` time: [4](#0-3) 

`send_message_impl::validate` is the public entry point for every outbound message; it calls `calculate_fee` and returns the resulting `Fee` (used elsewhere to charge the sender) with no zero-check gate before returning `Ok`: [5](#0-4) 

This breaks the invariant that the DOT amount collected from the sender for the remote/reward component must cover the ETH reward promised to relayers in the committed message. Existing guards are insufficient because `PricingParameters::validate` only checks raw input fields, not the derived, rounded fee output, and neither `calculate_fee` nor `send_message_impl::validate` re-checks the computed `fee.remote` before it is used to charge the sender or before the corresponding message (with its independently-sourced non-zero `reward`) is committed.

## Impact Explanation
Any unprivileged account able to trigger an outbound Snowbridge message (via XCM export or direct `SendMessage` usage) pays `fee.local + fee.remote` in DOT, while the `reward` value embedded in the Ethereum-bound `CommittedMessage` is sourced independently from `pricing_params.rewards.remote` and remains non-zero. When `fee.remote` rounds to `0` under realistic, validated `PricingParameters` (as demonstrated by the in-repo test), the pallet commits a message promising a real ETH reward to relayers while collecting no DOT to back it — this is public underpriced work that drains reward funding without matching payment, falling within the "public underpriced work that degrades block production or stalls bridge processing" / unbacked payout impact category.

## Likelihood Explanation
No privileged access is required — any user submitting a message through the public `SendMessage::validate`/`send_message_impl` path is charged whatever `calculate_fee` computes, and the pallet's own regression test proves that ordinary, fully-valid governance-set `PricingParameters` combined with typical `gas_used_at_most` values already produce `fee.remote == 0`. This condition can arise from normal parameter drift (e.g., ETH/DOT exchange-rate changes without proportional `fee_per_gas`/`reward` updates), making it a realistic, repeatable operational scenario rather than a contrived edge case.

## Recommendation
Add an explicit zero-check on the computed `fee.remote` inside `Pallet::calculate_fee` (or in `send_message_impl::validate` immediately after calling it), returning a `SendError` when the derived remote fee is zero, mirroring the pattern used for other invalid-parameter rejections. Alternatively, derive the `reward` field written into `CommittedMessage` in `do_process_message` from the same charged `fee.remote` value (with appropriate reverse-conversion) rather than independently from `pricing_params.rewards.remote`, ensuring collected fees and promised remote rewards can never diverge.

## Proof of Concept
The existing unit test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` already reproduces the exact vulnerable state in-tree: [3](#0-2)  — with `exchange_rate=1/1`, `fee_per_gas=1`, `rewards={local:1, remote:1}`, `multiplier=1/1`, `gas_used=250000`, `send_message_impl::validate` returns `Fee { local: 698000000, remote: 0 }` to charge the sender, while `do_process_message` still writes the non-zero `pricing_params.rewards.remote` value into the `reward` field of the `CommittedMessage` sent to Ethereum, as shown at [6](#0-5) .

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
