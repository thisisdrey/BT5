### Title
Unbounded in-memory accumulation of proc-receive reference updates and push options allows push-triggered memory exhaustion - (File: internal/gitaly/hook/procreceive_handler.go)

### Summary
The RUSTSEC-2020-0019 report describes a class of bug where a reader continues buffering data indefinitely because the loop that reads never enforces a termination/limit condition, leading to unbounded memory growth and DoS. `NewProcReceiveHandler` in Gitaly exhibits the same bug class: it scans an attacker-influenced pkt-line stream (from `git-receive-pack(1)`'s proc-receive protocol, driven by an ordinary user's `git push`) and appends every parsed reference update and push option into unbounded Go slices, with no cap on the number of iterations or total bytes consumed.

### Finding Description
`NewProcReceiveHandler` reads the proc-receive protocol from `stdin` using a `pktline.Scanner` [1](#0-0) . After version/feature negotiation, it loops over every pkt-line, parsing each one into a `ReferenceUpdate` and appending it to the `updates` slice with no bound on the number of updates: [2](#0-1) 

If the client negotiated push options, it performs an identical unbounded loop appending each push option string to `pushOptions`: [3](#0-2) 

Both loops terminate only on a flush packet or an I/O/parse error — there is no limit on the number of reference updates, no limit on the number of push options, and no limit on the cumulative size of the accumulated data. This handler is invoked as part of the standard `git-receive-pack(1)` push flow whenever a transaction is present (this is the proc-receive hook interception path used by ordinary pushes) [4](#0-3) . The resulting `ProcReceiveHandler` is transmitted to the waiting RPC and its `ReferenceUpdates()`/`PushOptions()` accessors simply return these unbounded slices [5](#0-4) .

This mirrors the RUSTSEC-2020-0019 bug class: a read loop that keeps consuming and buffering attacker-supplied network/stream data without any termination or size cap, allowing memory to grow unbounded as long as the attacker keeps supplying data faster than any natural limit is hit.

### Impact Explanation
An unprivileged user capable of pushing to a repository (which triggers `git-receive-pack(1)` and, when a Gitaly transaction is active, the proc-receive hook path) can craft a push with an extremely large number of reference updates and/or push options. Because each is individually parsed and appended to unbounded in-memory slices without any cap, a malicious or automated push (e.g., with thousands to millions of ref updates/push options) can cause the Gitaly process to allocate excessive memory, potentially exhausting available memory and causing the Gitaly node to slow down, be OOM-killed, or degrade service for other repositories/tenants sharing the process. This is a resource-exhaustion DoS reachable from an ordinary user action (a push), not requiring any privileged access, leaked token, or malicious peer/node.

### Likelihood Explanation
Likelihood is moderate-to-high: pushing is a routine, low-privilege operation, and proc-receive-hook interception is part of Gitaly's core transactional push handling (used whenever a transaction ID is present in the hook payload). Constructing a push with a huge number of reference updates or push options does not require exploiting a memory-corruption bug — it is a straightforward resource-consumption abuse of the parsing loop. The main constraint is generating a request with the desired count of ref updates/push options, which is feasible via a client or crafted git protocol input.

### Recommendation
- Enforce a hard upper bound on the number of reference updates and push options processed by `NewProcReceiveHandler` (mirroring similar caps applied elsewhere in Gitaly's push/limithandler infrastructure), rejecting the push with an error once the limit is exceeded.
- Enforce a maximum cumulative byte size for the buffered reference-update and push-option data, in addition to a count-based cap.
- Consider streaming/validating counts against the number of reference updates already known from the pack negotiation (e.g., cross-check against the actual number of commands sent to `git-receive-pack`) rather than trusting the proc-receive stream unconditionally.
- Add regression tests exercising the proc-receive handler with pathologically large update/push-option counts to confirm bounded resource consumption.

### Proof of Concept
1. As an ordinary authenticated user with push access to a repository, initiate a `git push` that goes through Gitaly's transactional receive-pack path (proc-receive hook active, i.e., `payload.TransactionID != 0`).
2. Craft (or use a modified git client/proxy) a receive-pack negotiation that, after version/feature negotiation, sends an extremely large number of well-formed reference-update pkt-lines (e.g., millions of small `<old-oid> <new-oid> <ref>` lines) before the terminating flush packet, and/or a large number of push-option pkt-lines if the `push-options` capability was negotiated.
3. Observe that `NewProcReceiveHandler`'s loops at `internal/gitaly/hook/procreceive_handler.go:80-99` and `:101-118` accept and buffer every line into the `updates`/`pushOptions` slices with no limit check, causing Gitaly's memory usage to grow proportionally to the attacker-controlled input size, degrading or crashing the Gitaly process.
