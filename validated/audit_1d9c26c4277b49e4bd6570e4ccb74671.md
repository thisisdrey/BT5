### Title
Attacker can dust-fill a victim's bounded deposit-token list past `MAX_TOKENS_PER_USER`, blocking their deposits and collateral top-ups - (contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
The kernel bug is a missing size check letting user-controlled input overflow a fixed 4K buffer. The Metronome analog: `Pool` maintains a per-account bounded list of deposit tokens (`MappedEnumerableSet` capped by `MAX_TOKENS_PER_USER`). Any account — not just the owner — gets entries appended to its list when it receives a `DepositToken` balance, and `DepositToken.transfer`/`transferFrom` is permissionless. An unprivileged attacker can deposit 1-wei dust positions across every `DepositToken` in the pool and `transfer` dust to a victim, pushing the victim's list past the cap so that every subsequent push (new `deposit` `onBehalfOf_` the victim, `transfer` to the victim, `seize` to the victim) reverts.

### Finding Description
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero, and `_mint` (reached via `deposit`) does the same for `onBehalfOf_`. [1](#0-0) [2](#0-1)  Neither `transfer` nor `transferFrom` requires the recipient's consent or checks `to_`/recipient list capacity before mutating balances; the only guard is `_revertIfLocked` on the *sender*. [3](#0-2)  In `Pool`, `addToDepositTokensOfAccount` enforces a hard cap (`MAX_TOKENS_PER_USER`); once the set is full, the add reverts, which bubbles up and reverts the entire `transfer`/`deposit`/`seize`. [4](#0-3)  (grep confirms the cap is enforced in `Pool.sol`; exact revert line could not be re-read in the remaining iterations, but `Pool.sol` contains all `MAX_TOKENS_PER_USER` checks.) This mirrors the advisory: input larger than a fixed bound (list capacity) is accepted from an unprivileged caller and corrupts/blocks the bounded structure.

### Impact Explanation
- A victim holding a leveraged/at-risk position cannot receive any new collateral token type: `deposit(amount, victim)` on a token the victim doesn't yet hold reverts at `addToDepositTokensOfAccount`, so the victim (or a helper) cannot add a *new* collateral to improve health before liquidation. That is temporary freezing of funds / forced liquidation of an otherwise salvageable position.
- Any integrator sending `DepositToken`s to the victim (zaps, `SmartFarmingManager` flows minting via `_mint`, liquidation `seize` to a specific beneficiary) reverts for token types not already in the victim's set.

### Likelihood Explanation
- Fully unprivileged: the attacker only needs dust balances in each pool `DepositToken` (deposit 1 unit, `transfer` 1 wei to victim). Cost is roughly `MAX_TOKENS_PER_USER` transfers — cheap on L2s (Base/Optimism deployments exist).
- No modifier stops it: `transfer` only checks the sender's unlocked balance; recipient consent/capacity is never checked before the pool-set push. Pause doesn't help the victim, and removing tokens only shrinks the list when a balance hits zero — the victim can clear entries by transferring dust out, but the attacker can refill, and during an active liquidation window the victim may not react in time.
- Caveat: impact is bounded to blocking *new* token types (existing held tokens still work), so severity is moderate rather than critical — consistent with the "temporary freezing" acceptance criterion, not theft.

### Recommendation
- Only add to `depositTokensOfAccount` on mint/deposit (which the recipient implicitly consents to via `onBehalfOf_`), or allow `transfer`/`seize` to skip the list push when the set is full (treat the token as unlisted-but-held), or make the push non-reverting and surface a soft-failure.
- Alternatively, require recipient opt-in for first-time receipts, or check `length(set) < MAX_TOKENS_PER_USER` inside `_transfer` and revert early with a clear error.

```solidity
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {DepositToken} from "contracts/DepositToken.sol";

contract DustFillListTest is Test {
    Pool pool;            // fork: deployed Pool proxy on base/mainnet
    DepositToken[] tokens; // all pool deposit tokens
    address attacker = address(0xA);
    address victim = makeAddr("victim");

    function setUp() public {
        // vm.createSelectFork("<rpc>");
        // pool = Pool(<POOL_ADDR>);
        // collect tokens = pool.getDepositTokens()
    }

    function test_dust_fill_blocks_victim_deposits() public {
        uint256 cap = /* pool MAX_TOKENS_PER_USER */;
        // 1) Victim opens a position with token[0] and borrows near limit.
        // 2) Attacker deposits 1 wei in each DepositToken victim doesn't hold
        //    and transfers dust to victim until victim's list length == cap.
        for (uint256 i; i < cap; ++i) {
            DepositToken t = tokens[i];
            deal(address(t.underlying()), attacker, 2);
            vm.startPrank(attacker);
            t.underlying().approve(address(t), 2);
            t.deposit(1, attacker);
            t.transfer(victim, 1);   // pushes token into victim's set
            vm.stopPrank();
        }
        // assert pool.depositTokensOfAccountLength(victim) == cap

        // 3) Victim tries to deposit a NEW collateral type to save position.
        DepositToken fresh = tokens[cap]; // a token not in victim's list
        deal(address(fresh.underlying()), victim, 100e18);
        vm.startPrank(victim);
        fresh.underlying().approve(address(fresh), 100e18);
        vm.expectRevert(); // addToDepositTokensOfAccount overflows bounded set
        fresh.deposit(100e18, victim);
        vm.stopPrank();

        // 4) Liquidator can now seize the victim's undercollateralized position.
    }
}
```
