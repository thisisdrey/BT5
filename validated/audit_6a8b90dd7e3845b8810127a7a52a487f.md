Based on my research, I found a genuine analog for this bug class in Bazel's Bzlmod "facts" mechanism for non-reproducible module extensions.

### Title
Non-reproducible module extension "facts" from an untrusted `MODULE.bazel.lock` are trusted without re-validation, allowing lockfile poisoning to persist attacker-controlled data - (File: `src/main/java/com/google/devtools/build/lib/bazel/bzlmod` extension eval/lockfile-writing logic)

### Summary
Bazel's Bzlmod "facts" feature lets a module extension persist arbitrary JSON-like data across evaluations in `MODULE.bazel.lock` (the extension's `facts` field), intended for values such as hashes of network resources that aren't otherwise integrity-checked [1](#0-0) . For **non-reproducible** extensions, if the `facts` recorded in the workspace `MODULE.bazel.lock` are externally changed (e.g. by pulling/checking out a branch containing an edited lockfile) without the extension's other inputs changing, `--lockfile_mode=update` deliberately keeps the new facts "as is" and does not rerun the extension to validate them, on the stated rationale that "a cold machine would not rerun the extension either" [2](#0-1) .

### Finding Description
The extension `facts` mechanism exists specifically for extensions that fetch "effectively immutable data... from the network, but you don't have a checksum available to guard the download" — i.e., facts are explicitly the substitute for integrity verification in these code paths [3](#0-2) . `module_ctx.facts` values are consumed directly by extension implementations (e.g., to skip fetching and instead reuse a previously recorded hash/URL) [4](#0-3) .

The regression tests explicitly document the trust model: for a **non-reproducible** extension, when the workspace lockfile's facts are edited underneath a warm output base ("e.g. due to a branch switch or pull that brings in facts produced by an evaluation of the extension on a different machine"), `update` mode keeps the edited facts and does **not** rerun the extension to check them against a freshly-computed value [5](#0-4) , [6](#0-5) . This is contrasted with reproducible extensions, where a facts mismatch against the hidden (machine-local) lockfile record *does* trigger a rerun [7](#0-6) . For non-reproducible extensions, however, there is no such re-derivation: the workspace lockfile's facts content is accepted verbatim in `update` mode as long as the extension's usages/inputs digest is unchanged, even though the facts value itself was never produced by (or verified against) the current evaluation.

This mirrors the reported analog precisely: a piece of previously-approved/recorded state (the redemption request in the original report; the `facts` entry here) can be re-processed/accepted a second time under attacker influence without re-validating it against the authoritative source, because the code assumes "if inputs didn't change, the previously recorded output is still good" — but the attacker controls the recorded output directly via a file (`MODULE.bazel.lock`) that ships with the source tree and that CI/build systems on untrusted branches will read.

### Impact Explanation
An attacker who can get a victim's CI or developer machine to build from a hostile branch/PR (a normal, unprivileged attack vector for public repos with CI) can commit a `MODULE.bazel.lock` whose `facts` entries contain forged hashes/URLs for a non-reproducible extension. Because the update mode accepts such facts without rerunning the extension or checking them against any external source of truth, an extension that trusts `ctx.facts["some_pkg"]["sha256"]` to skip download verification will use attacker-supplied hash/URL data as if it were previously verified. Depending on how the extension consumes `facts` (the documented use case is precisely "trust an externally recorded checksum"), this can result in a build using attacker-chosen "immutable" artifact metadata, i.e., an integrity bypass of data that the lockfile mechanism is supposed to make tamper-evident.

### Likelihood Explanation
Requires: (1) an extension author who follows the documented `facts` pattern for un-checksummed downloads (an intended, encouraged usage per the docs) and (2) a victim building from a branch/lockfile they don't fully control (common in CI for external PRs). No special privileges beyond publishing content on a branch/PR are needed; this fits the "untrusted branch CI builds" attacker model directly.

### Recommendation
For non-reproducible extensions, do not blindly trust externally-modified `facts` entries in the workspace lockfile when only the entry value (not the extension's usages/bzl digest) has changed; either re-run the extension to re-derive/validate facts, or require the facts entries themselves to carry a digest that Bazel can verify was produced by a legitimate previous evaluation (as is effectively already done for reproducible extensions via the hidden, machine-local lockfile comparison).

### Proof of Concept
The existing regression test demonstrates the trust behavior and can be adapted as the PoC: `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` shows that manually editing `MODULE.bazel.lock["facts"][extension_id]` to add an attacker-chosen fact entry, then running `bazel build --lockfile_mode=update`, results in the extension **not** being re-evaluated and the forged fact persisting in the lockfile output [8](#0-7) . A concrete exploit PoC would extend `_setUpExtensionWithFacts` so the extension implementation uses `ctx.facts[...]["hash"]` to skip a checksum-guarded `ctx.download()`/`repo_rule` call, then show that after `_addFactToLockfile` injects an attacker-controlled hash, the build consumes that hash without any verification or extension rerun.

If your extension relies on effectively immutable data obtained from outside
the build, most commonly from the network, but you don't have a checksum
available to guard the download, consider using the `facts` parameter of
[`extension_metadata`](/rules/lib/builtins/module_ctx#extension_metadata) to
persistently record such data and thus allow your extension to become
reproducible. `facts` is expected to be a dictionary with string keys and
arbitrary JSON-like Starlark values that is always persisted in the lockfile and
available to future evaluations of the extension via the
[`facts`](/rules/lib/builtins/module_ctx#facts) field of `module_ctx`.

`facts` are not invalidated even when the code of your module extension changes,
so be prepared to handle the case where the structure of `facts` changes.
Bazel also assumes that two different `facts` dicts produced by two different
evaluations of the same extension can be shallowly merged (i.e., as if by using
the `|` operator on two dicts). This is partially enforced by `module_ctx.facts`
not supporting enumeration of its entries, just lookups by key.

An example of using `facts` would be to record a mapping from version numbers of
some SDK to the an object containing the download URL and checksum of that
version. The first time the extension is evaluated, it can fetch this mapping
from the network, but on later evaluations it can use the mapping from `facts`
to avoid the network requests.

  def _addFactToLockfile(self, extension_id, fact_key, fact_value):
    """Adds a facts entry to the workspace lockfile."""
    # Simulates the workspace lockfile changing underneath a warm output base,
    # e.g. due to a branch switch or pull that brings in facts produced by an
    # evaluation of the extension on a different machine.
    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    lockfile['facts'][extension_id][fact_key] = fact_value
    with open(self.Path('MODULE.bazel.lock'), 'w') as f:
      json.dump(lockfile, f, indent=2)

  def testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension(
      self,
  ):
    """UPDATE mode keeps updated facts of a non-reproducible extension.

    The hidden lockfile records the facts produced by the most recent local
    evaluation of the extension. If the workspace lockfile's facts for a
    non-reproducible extension change without any of its inputs changing (e.g.
    a branch switch or pull brings in a re-pin performed on another machine),
    the cached result must be reused with the new facts as is: a cold machine
    would not rerun the extension either and a rerun could require network
    access or credentials that are only available to the person updating the
    pins.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {
            '1.25.0': {'hash': 'olleh'},
            '1.26.1': {'hash': 'hello'},
            '1.27.0': {'hash': 'hola'},
        },
    )

  def testExternallyUpdatedFactsRegenerateReproducibleExtension(self):
    """UPDATE mode reruns a reproducible extension on changed facts.

    A reproducible extension's facts can only legitimately change together
    with its inputs, so facts that differ from the record of its most recent
    evaluation despite unchanged inputs indicate an edited workspace lockfile
    and the extension is rerun to regenerate them. This is safe: a reproducible
    extension's result is only ever cached in the machine-local hidden
    lockfile, so a cold machine would rerun it anyway.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=True)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )
