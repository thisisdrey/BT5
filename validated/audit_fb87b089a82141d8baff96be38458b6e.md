### Title
Non-atomic check-then-update in the anti-replay window allows a TOCTOU race that lets a captured packet be replayed - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection with a **check → decrypt → update** sequence, but the check and the update are performed under two *separate* lock acquisitions instead of one atomic critical section. Concurrent packet-processing goroutines (Nebula spawns multiple UDP listener routines that call `readOutsidePackets` in parallel) can both pass the `window.Check()` gate for the same message counter before either of them has called `window.Update()`, allowing a captured/duplicated ciphertext to be decrypted and processed twice. This mirrors the reported bug class: a state-transition step ("mark this index/counter as consumed") that is decoupled from the action it is supposed to gate, leaving a window where the protected resource (here, the replay window) has not yet been updated.

### Finding Description
`ConnectionState.Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, releases the lock, performs the (unlocked) AEAD decryption, then re-acquires `decryptLock` to call `cs.window.Update(l, messageCounter)`: [1](#0-0) 

The same pattern exists in `VerifyRelay`, used for relay (forwarding) frames: [2](#0-1) 

`Bits.Check` only *reads* the anti-replay bitmap; it does not mark the counter as seen. That marking only happens later in `Bits.Update`: [3](#0-2) [4](#0-3) 

Because `Check` and `Update` are two independently-locked operations with an unlocked decrypt step in between, an attacker who captures a single ciphertext packet and re-injects it multiple times in quick succession (feasible because Nebula can run multiple UDP reader routines/goroutines concurrently processing inbound packets for the same tunnel) can cause two or more of those goroutines to call `Check()` for the identical `messageCounter` before any of them reaches `Update()`. Every one of those goroutines will observe "not yet seen" and proceed to decrypt and hand the packet to the data plane (or, for relay frames, forward it onward), effectively defeating the anti-replay window despite it nominally being present. This is structurally the same defect class as the reported bug: a required state-transition ("commit that this unit of work has been consumed") is not performed atomically with the check that gates the action, so the protection can be bypassed by an attacker who needs no valid certificate or trusted position — only the ability to capture and re-send a UDP datagram.

### Impact Explanation
If exploitable, this allows replay of previously-observed encrypted traffic to be decrypted/processed more than once by the receiving Nebula node and, for `ForwardingType` relays, re-forwarded to the ultimate destination — effectively a traffic-replay vulnerability, which is explicitly listed as an acceptable impact (`traffic decryption/forgery/replay`). Since `VerifyRelay` is on the fully external-reachable relay-forwarding path (`handleOutsideRelayPacket`), a remote attacker with no certificate signed by the network's CA can trigger this purely by racing duplicate UDP frames at a relay or terminal node.

### Likelihood Explanation
Exploitability depends on actually winning the race window between `Check()` returning true and the corresponding `Update()` committing the bit — a window that includes a full AEAD decrypt operation. This is more likely to be won when Nebula is configured with multiple listener/tun routines (`listen.routines` > 1) so that separate goroutines can genuinely process two copies of the same captured packet in parallel, or under load/head-of-line jitter that widens the window even in a single-reader configuration. This is a genuine correctness gap in the locking discipline (check and update should be a single atomic critical section), but the practical window is narrow and timing-dependent, so likelihood is moderate rather than trivial.

### Recommendation
Make the replay-window check-and-mark atomic with respect to concurrent decrypt attempts for the same `ConnectionState`/counter — e.g., hold `decryptLock` for the entire check-decrypt-update sequence (or provisionally mark the counter as "in-flight" under the lock before decrypting, and roll it back on decryption failure) so that no two concurrent goroutines can both observe an unmarked counter for the same message index. Apply the fix uniformly to both `Decrypt` and `VerifyRelay`, and add a concurrency test that fires the same captured packet from multiple goroutines simultaneously to confirm only one is ever accepted.

### Proof of Concept
1. Establish a tunnel through a `ForwardingType` relay (as in `TestRelayReplayProtection`) and capture one legitimate relay frame `relayFrame` addressed to the relay.
2. Instead of injecting the captured frame sequentially (as the existing regression test does), inject it concurrently from multiple goroutines at (or near) the same instant, e.g.:
```go
var wg sync.WaitGroup
for i := 0; i < N; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        relayControl.InjectUDPPacket(relayFrame)
    }()
}
wg.Wait()
```
3. Count forwarded frames arriving at `theirUdpAddr` (as `drainForwards` does in the existing test at [5](#0-4) ). If the check/update race is won, more than one forwarded copy of the replayed frame will be observed, whereas the intended behavior (as asserted sequentially in `TestRelayReplayProtection`) is that only the first delivery is ever forwarded. func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]

		return err
	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
