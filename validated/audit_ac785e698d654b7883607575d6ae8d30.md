### Title
Fee-on-transfer (Token-2022 `TransferFeeConfig`) mints break the "transfer then use same amount" assumption in JupLend/Drift/Solend/Kamino integration deposit CPIs, causing DoS or drain of pooled vault funds - (File: `programs/marginfi/src/instructions/juplend/deposit.rs`)

### Summary
The external report's root cause — transferring tokens into an intermediary account and then invoking a downstream call with the pre-transfer amount instead of the amount actually received — has a direct analog in marginfi's external-protocol integration deposit instructions (JupLend, Drift, Solend, Kamino). These instructions move funds `user -> bank liquidity_vault` via `transfer_checked(amount)` and then immediately call the external protocol's CPI deposit with the *same* `amount`, without accounting for Token-2022 transfer-fee mints, unlike the core `lending_account_deposit` path which explicitly compensates for transfer fees.

### Finding Description
In the core marginfi deposit flow, `lending_account_deposit` correctly handles Token-2022 fee-on-transfer mints by computing the pre-fee amount to send so that the vault receives exactly the intended `deposit_amount`: [1](#0-0) 

This fee-awareness is implemented via `calculate_pre_fee_spl_deposit_amount` in `programs/marginfi/src/utils/general.rs`: [2](#0-1) 

However, the external-protocol integration deposit paths (JupLend, Drift, Solend) do **not** use this helper at all. They transfer a raw `amount` from the user to the bank's `liquidity_vault`, and then reuse the identical `amount` in the downstream CPI to the external lending protocol, implicitly assuming the vault received the full `amount`:

`juplend_deposit`: [3](#0-2) 

`JuplendDeposit::cpi_transfer_user_to_liquidity_vault` / `cpi_juplend_deposit`: [4](#0-3) [5](#0-4) 

The identical pattern exists in `juplend_init_position` (`cpi_transfer_user_to_liquidity_vault` then `cpi_juplend_deposit` with the same `amount`), in Drift's `cpi_transfer_user_to_liquidity_vault`/`cpi_drift_deposit`, and in Solend's `cpi_transfer_user_to_liquidity_vault`/`cpi_solend_deposit`: [6](#0-5) [7](#0-6) [8](#0-7) 

None of the `add_pool` instructions for these integration bank types (`lending_pool_add_bank_juplend`, `lending_pool_add_bank_drift`, `lending_pool_add_bank_solend`, `lending_pool_add_bank_kamino`) validate/reject Token-2022 `TransferFeeConfig` extensions on the bank mint — they only check oracle setup and set the `IS_T22` flag when the mint is owned by Token-2022: [9](#0-8) [10](#0-9) 

If such a bank mint carries a nonzero `TransferFeeConfig` fee, `transfer_checked(amount)` delivers only `amount - fee` to the shared `liquidity_vault`, but the downstream CPI (`deposit(cpi_ctx, amount)` for JupLend, `deposit_reserve_liquidity_and_obligation_collateral(cpi_ctx, amount)` for Solend, `deposit(cpi_ctx, market_index, amount, false)` for Drift) attempts to move the full pre-fee `amount` out of that same vault into the external protocol.

### Impact Explanation
Because `liquidity_vault` is a single pooled account shared across all depositors of that bank (not a per-user account), if the vault happens to hold residual balance (from other users' deposits, rounding dust, or accrued but un-swept interest), the shortfall caused by the transfer fee is silently covered by that pooled balance — the external protocol CPI succeeds, but the vault is left short by the fee amount relative to what marginfi's internal share accounting assumes was deposited. This is the same class of loss as the referenced report: real value is either (a) permanently lost/stuck when the CPI reverts due to insufficient vault balance (`transfer_checked`/CPI deposit failing outright — DoS on deposits for that bank), or (b) siphoned from other depositors' pooled principal to mask the fee, creating an accounting mismatch between the external protocol's minted position size and the value actually backing marginfi bank shares — a form of insolvency/bad debt for the bank.

### Likelihood Explanation
This requires a group admin to configure a JupLend/Drift/Solend/Kamino bank using a Token-2022 mint that has an active `TransferFeeConfig` extension, since these bank types are group-admin-created (not driven by end users). No `add_pool` validation currently rejects fee-bearing T22 mints for these bank types, and none of the deposit/init_position/init_obligation instructions are fee-aware, so any such misconfiguration is directly exploitable by any regular user who calls the deposit/init instruction (an unprivileged action) once the bank exists. Given the codebase explicitly implements fee-awareness for the default deposit path but not for these integration paths, and the JupLend Token-2022 test (`jlr09_withT22.spec.ts`) does not appear to exercise a mint with `transferFee` configured, this gap looks untested and real, though its practical likelihood depends on an admin actually onboarding a fee-bearing mint for one of these integrations.

### Recommendation
- For JupLend, Drift, Solend, and Kamino bank creation (`lending_pool_add_bank_*`), explicitly reject bank mints that have a Token-2022 `TransferFeeConfig` extension with a nonzero fee, mirroring the `nonzero_fee` check already available in `utils/general.rs`.
- Alternatively, make each integration's deposit/init-position/init-obligation flow fee-aware: measure the liquidity vault's actual balance delta after the `transfer_checked` call (or use `calculate_post_fee_spl_deposit_amount`) and pass that post-fee amount into the downstream external-protocol CPI, instead of reusing the pre-fee `amount`.

### Proof of Concept
1. Group admin creates a JupLend-type marginfi bank (`lending_pool_add_bank_juplend`) whose `bank_mint` is a Token-2022 mint initialized with `TransferFeeConfig` (nonzero `transfer_fee_basis_points`) — no current validation prevents this.
2. Admin calls `juplend_init_position` to activate the bank; the small seed transfer would itself be short by the fee, but assume the seed happens to succeed via vault dust or is set up with fee temporarily disabled.
3. A user calls `juplend_deposit(amount)`. `cpi_transfer_user_to_liquidity_vault(amount)` moves `amount` from the user, but the vault only receives `amount - fee` due to the mint's transfer fee.
4. `cpi_juplend_deposit(amount, ...)` is invoked with the full pre-fee `amount`, attempting to move `amount` out of the vault into JupLend's f-token vault: [11](#0-10) 
   - If the vault has no other balance, this CPI fails, reverting the deposit (deposits become impossible for this bank — DoS), matching the "always revert" branch of the referenced report.
   - If the vault holds any other users' pooled balance (e.g., after multiple deposits/withdrawals leave residual funds), the shortfall is covered from that pooled balance, meaning the depositing user's shares are minted based on `amount` while the vault is actually short by `fee`, silently under-collateralizing the bank — analogous to the "steal/grief" branch of the referenced report where the aggregator's rescuable funds were drained to pay for the fee shortfall.

pub fn calculate_pre_fee_spl_deposit_amount(
    mint_ai: AccountInfo,
    post_fee_amount: u64,
    epoch: u64,
) -> MarginfiResult<u64> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(post_fee_amount);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    match mint.get_extension::<TransferFeeConfig>() {
        Ok(transfer_fee_config) => {
            let epoch_fee = transfer_fee_config.get_epoch_fee(epoch);
            let pre_fee_amount = calculate_pre_fee_amount(epoch_fee, post_fee_amount).unwrap();
            Ok(pre_fee_amount)
        }
        Err(_) => Ok(post_fee_amount),
    }
}
