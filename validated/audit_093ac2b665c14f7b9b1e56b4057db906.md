Audit Report

## Title
`pallet-bridge-relayers::claim_rewards_to()` clears the reward ledger before confirming the beneficiary can actually receive the asset on the remote chain, letting a relayer permanently lose (or grief) their own Snowbridge reward via an unreceivable AssetHub beneficiary - (File: `bridges/snowbridge/primitives/core/src/reward.rs`, `bridges/modules/relayers/src/lib.rs`)

## Summary
`PayAccountOnLocation::pay_reward` returns `Ok(())` as soon as the reward-carrying XCM is handed off to `XcmSender::deliver`, without any confirmation that the terminal `DepositAsset` instruction succeeds at the beneficiary on AssetHub. `do_claim_rewards` treats this `Ok` return as final settlement: it deletes the relayer's `RelayerRewards` entry and emits `RewardPaid` inside the same `try_mutate_exists` closure, so a beneficiary that cannot actually receive the reserve-deposited foreign asset (unfunded account, insufficient ED, non-existent target) causes the asset to be trapped on AssetHub while the reward accounting on BridgeHub is irreversibly finalized.

## Finding Description
`PayAccountOnLocation::pay_reward` builds an XCM program of `UnpaidExecution`, `DescendOrigin(InboundQueueLocation)`, `UniversalOrigin(GlobalConsensus(EthereumNetwork))`, `ReserveAssetDeposited`, and `DepositAsset { assets: AllCounted(1), beneficiary }`, then calls `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver(ticket)`, returning `Ok(())` immediately after `deliver` succeeds — there is no wait for, or check of, the remote execution outcome of `DepositAsset` [1](#0-0) .

`do_claim_rewards` uses `RelayerRewards::<T, I>::try_mutate_exists` to `take()` (delete) the relayer's accrued reward, calls `T::PaymentProcedure::pay_reward(...)`, and — only if that returns `Err` — rolls the deletion back via the `?` operator; on `Ok`, it emits `Event::RewardPaid` and the deletion is kept [2](#0-1) . The public extrinsic `claim_rewards_to` passes an arbitrary, caller-supplied `beneficiary: BeneficiaryOf<T, I>` straight into this flow with no origin/route validation on the beneficiary itself [3](#0-2) .

No `SetAssetClaimer` is included in the outbound XCM program, and the trap origin used by the XCM executor at the point of failure (derived from `DescendOrigin`/`UniversalOrigin(GlobalConsensus(Ethereum))`) is not a location the relayer or beneficiary practically controls, so there is no realistic recovery path via `pallet_xcm::claim_assets` for the relayer. The existing test suite (`claim_rewards_works`, exercising a funded beneficiary, and `claim_snowbridge_rewards_to_local_account_fails`, exercising a `pay_reward` `Err` from an incompatible beneficiary variant) does not cover the case where `pay_reward` returns `Ok` (successful delivery) yet the remote `DepositAsset` traps — precisely the unguarded gap identified here [4](#0-3) .

## Impact Explanation
This matches the "permanent user-fund...lock" impact class: the reward ledger entry (`RelayerRewards`) is deleted and `RewardPaid` is emitted based purely on successful XCM hand-off rather than confirmed remote settlement, so a relayer whose supplied `beneficiary` cannot accept the `eth_location()` foreign asset on AssetHub permanently loses the reward with no fallback settlement or re-credit mechanism tied back to the specific claim.

## Likelihood Explanation
`claim_rewards_to` is a normal, unprivileged, frequently used relayer extrinsic, and the beneficiary `Location`/`VersionedLocation` is fully caller-supplied with zero on-chain validation of its capacity to receive the deposited asset before the reward balance is irreversibly taken from storage; the only tested failure mode is a `pay_reward`-level `Err`, not a downstream remote-execution trap, so this gap is unexercised by current tests.

## Recommendation
Do not finalize the `RelayerRewards` deletion and `RewardPaid` event until receiving remote confirmation that `DepositAsset` succeeded (e.g., via a delivery/execution acknowledgment channel), or validate the beneficiary's ability to receive the specific foreign asset before consuming the reward balance. Alternatively, add `SetAssetClaimer` to the outbound program so a relayer-recoverable claim path exists if the deposit traps, and/or implement a two-phase "in-flight" reward state that is only cleared upon confirmed settlement.

## Proof of Concept
1. Register a `Snowbridge` reward for a relayer via `register_reward`.
2. Call `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::V5(location)))` where `location` resolves to an unfunded/ED-insufficient AssetHub account.
3. Observe on BridgeHub: `RelayerRewards` entry deleted and `Event::RewardPaid` emitted because `PayAccountOnLocation::pay_reward` returned `Ok(())` after `XcmSender::deliver` succeeded [5](#0-4) .
4. On AssetHub, the `DepositAsset` instruction fails to credit the beneficiary and the asset is trapped by the XCM executor instead of being credited to any relayer-controlled account.
5. Result: the relayer's reward accounting is permanently gone with no recorded or automatically recoverable asset on AssetHub.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)
