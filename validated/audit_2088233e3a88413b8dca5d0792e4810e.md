### Title
Handshake retransmit replay allows on-path attacker to hijack an established tunnel's remote address - ([File: handshake_manager.go])

### Summary
The Yaxis report describes a value (AMM reserves) that can be manipulated by an unauthenticated attacker and is then trusted directly for a security decision (voting power) without validating that it reflects genuine, unmanipulated state. The same bug class — trusting attacker-replayable wire data to update security-relevant state without re-authenticating it — exists in Nebula's handshake-retransmit path, where a raw, previously captured handshake packet, replayed from a new source address, is used to redirect where an already-established tunnel's encrypted traffic is sent.

### Finding Description
When a responder gets a stage-0 handshake packet that byte-for-byte matches one it has already processed, `HandshakeManager.CheckAndComplete` treats it as a harmless retransmit (`ErrAlreadySeen`) rather than a fresh handshake: [1](#0-0) 

This byte-equality check operates purely on the raw wire bytes of the handshake packet captured at `hostinfo.HandshakePacket[handshakePacketStage0]` — no additional per-message authentication or freshness proof is required, since equality with a previously-accepted packet is (mis)treated as sufficient. Because Nebula's handshake stage-0 message is sent as plaintext-framed UDP (only the header/format needs to parse), any on-path observer can capture one legitimate initiator packet and replay it from a different source `UdpAddr` — no CA-signed certificate or successful Noise handshake completion is required by the replayer at all.

`handleCheckAndCompleteError` then acts on this "already seen" classification by calling `SetRemoteIfPreferred` with the attacker-controlled `via.UdpAddr`: [2](#0-1) 

`SetRemoteIfPreferred` will overwrite the `HostInfo.remote` (the address the data plane subsequently sends encrypted traffic to) whenever the new source address falls inside a configured "preferred range" and the current remote isn't already preferred: [3](#0-2) 

The check only compares the *addresses* against `preferredRanges` — it never re-validates that the sender who produced this packet at this new address actually possesses the keys/cert of the already-authenticated peer. An attacker positioned in the preferred-range subnet (e.g., a local network segment nebula is configured to prefer for direct connectivity) can therefore replay a sniffed handshake packet to redirect an existing tunnel's outbound remote address to itself.

### Impact Explanation
This is directly analogous to the report's "manipulate externally observable state, then leverage it for a trust decision without re-verifying authenticity." Here the manipulated state is `HostInfo.remote` on an already fully-authenticated tunnel. Redirecting it lets an on-path/local attacker:
- Cause encrypted data-plane traffic for a legitimate, established tunnel to be sent to an address they control (traffic redirection / potential black-holing, denial of service for that tunnel), and
- Do so with **no CA-signed certificate and no completed Noise handshake of their own** — only replay of previously observed ciphertext bytes.

This satisfies the "remote state poisoning" / "hostmap/lighthouse/relay address trust" impact category: an unauthenticated party changes trusted routing state for a session it does not own.

### Likelihood Explanation
Requires the attacker to be on-path to capture a genuine stage-0 handshake packet and to be able to send from (or spoof, on UDP) a source address inside the victim's configured `preferred_ranges` (a common configuration for hosts on the same LAN/subnet as other nebula nodes). This is a realistic scenario for local-network attackers who lack any valid nebula certificate, matching the medium-severity, "frontrun on the same window" character of the original finding.

### Recommendation
Do not let a byte-identical retransmit alone justify updating `HostInfo.remote`. `SetRemoteIfPreferred` (or its caller in the `ErrAlreadySeen` branch) should require that the roam/preference update be backed by a freshly authenticated data-plane or handshake exchange (e.g., verify a signed/keyed proof tied to the current session, such as a successful decrypt from the new address) rather than accepting the mere fact that old handshake bytes were replayed from a new source IP.

### Proof of Concept
1. Establish a legitimate tunnel between `me` and `them`; capture `them`'s stage-0 handshake UDP packet (e.g., via passive sniffing on a shared/preferred-range network segment).
2. From an attacker-controlled host whose IP falls inside `me`'s configured `preferred_ranges`, replay the exact captured packet bytes to `me`.
3. `CheckAndComplete` matches the byte-identical packet against the existing `HostInfo` and returns `ErrAlreadySeen` (`handshake_manager.go:441`).
4. `handleCheckAndCompleteError`'s `ErrAlreadySeen` branch calls `existing.SetRemoteIfPreferred(f.hostMap, via)` with the attacker's `via.UdpAddr`; since it is in `preferredRanges`, `me`'s `HostInfo.remote` for `them` is updated to the attacker's address (`hostmap.go:806-819`), with no cert or handshake ever verified from the attacker.
5. Subsequent encrypted data-plane packets from `me` destined for `them` are now sent to the attacker's address.

// SetRemoteIfPreferred returns true if the remote was changed. The lastRoam
// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}
