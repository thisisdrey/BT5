## Title
Relayer reward/tip permanently stuck with no recovery when Ethereum light client goes stale — analog of unassigned exit-administrator lock (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
Snowfork's `TokenDeposit.exitAdministrator` bug boils down to: a privileged "dead-state" recovery path is gated by a liveness check, that liveness check has no fallback, and once it trips there is no way for a normal user to ever reclaim value that is already locked in escrow. The same structural pattern exists in `snowbridge-pallet-outbound-queue-v2`: fees collected up-front from users are held in `PendingOrders` and can only be released via `submit_delivery_receipt`, which is unconditionally gated on `T::Verifier::verify()` succeeding. If the Ethereum light client (`EthereumBeaconClient`) falls behind/stalls (analogous to Sonic's "not updated within 24h ⇒ dead" condition), `verify()` returns `VerificationError::Halted` forever, and there is no alternate path (no admin/root override, no expiry/cancel/refund extrinsic) to settle or reclaim the pending fee.

## Finding Description
`Pallet::do_process_message` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` (lines 426-436) collects a user-supplied `fee` at message-commit time and stores it in `PendingOrders<T>` keyed by `nonce`: [1](#0-0) 

The only way this fee is ever paid out (and the only way `PendingOrders` entry is ever removed) is through `submit_delivery_receipt` → `process_delivery_receipt`: [2](#0-1) [3](#0-2) 

`submit_delivery_receipt` unconditionally requires `T::Verifier::verify(&event.event_log, &event.proof)` to succeed before any state changes. There is no fallback branch, no root/governance override, and no expiry mechanism for `PendingOrders`. If the verifier (the Ethereum beacon/finality light client) is unable to produce a valid proof — e.g., because the light client's checkpoint has gone stale, similar in spirit to Sonic's dead-state condition ("state has not been updated within X time ⇒ considered dead") — `verify()` deterministically returns `Err(VerificationError::Halted)`, and the call reverts every time it's attempted, indefinitely.

This exact behavior is already validated by an existing unit test in the repository, `poc_m1`, which demonstrates that when the verifier reports `Halted`, the pending order's fee remains locked in storage with no way to release it: [4](#0-3) 

Unlike `TokenDeposit`, which at least has a `withdrawWhileDead()` design intent (a recovery path gated by an assignable `exitAdministrator`), `outbound-queue-v2` has **no dead-state recovery path at all** for `PendingOrders`: no `cancel`, no timeout-based refund, and no privileged force-settle call. The `Error::Halted` variant and `Event::OperatingModeChanged` exist in the pallet's `Error`/`Event` enums but there is no corresponding `OperatingMode` storage item or `set_operating_mode` extrinsic in this pallet (unlike `inbound-queue-v2` and `outbound-queue` v1, which do have `set_operating_mode`), so there isn't even a governance lever to bypass or reset the stuck state for this specific pallet's pending-order fees. [5](#0-4) 

## Impact Explanation
Users pay a fee up-front when sending a message to Ethereum (via the outbound queue) to incentivize relayer delivery. If the Ethereum light client becomes permanently stale (which can happen without any malicious actor — e.g., missed sync committee updates, unresponsive syncing infrastructure, or an intentionally long resync gap), `submit_delivery_receipt` can never succeed again for any outstanding nonce. All fees held in `PendingOrders` become permanently unspendable/unclaimable — the funds are neither refunded to the sender nor paid to the relayer who did the delivery work. This is a permanent fund lock in the bridge's escrow-like `PendingOrders` state, matching the "permanent user-fund or bridge-state lock" impact class in the gate criteria.

## Likelihood Explanation
No malicious actor is required. This condition is triggered purely by the liveness of the underlying Ethereum light client falling behind (an operational/infrastructure risk inherent to any light-client-based bridge, not a "malicious relayer" scenario), which is exactly the scenario the Sonic report calls out as expected to eventually occur ("after 200 days" in their case). The bug is latent but will manifest under long resync windows or verifier misconfiguration and there is no way to detect it in advance from within the pallet, since the halted/stale determination lives entirely in `T::Verifier`.

## Recommendation
Add either: (1) a governance-callable emergency function to force-settle or refund pending orders whose age exceeds a bound (independent of the verifier's Halted state), or (2) a time-bound expiry on `PendingOrders` entries that reverts the collected fee back to the original sender if no delivery receipt is submitted within an SLA window, so that a stalled light client cannot indefinitely trap already-collected fees.

## Proof of Concept
The repository already contains a proof of concept for this exact scenario: [6](#0-5) 

It inserts a `PendingOrder` with a non-zero fee, sets the mock verifier to `Halted`, and shows that `submit_delivery_receipt` fails with `Error::Verification(VerificationError::Halted)` while `PendingOrders` retains the order untouched — confirming there is no code path in this pallet to release or refund that fee absent verifier success, and no expiry/governance override exists.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// Reward processing must be blocked while the bridge is halted: `submit_delivery_receipt`
// should not pay out `PendingOrder` fees if the verifier reports the bridge as halted.
#[test]
fn poc_m1() {
	new_tester().execute_with(|| {
		let nonce = 1;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_event_proof());

		set_verifier_halted(true);

		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);

		let order_after = PendingOrders::<Test>::get(nonce).expect("order still present");
		assert_eq!(order_after.fee, fee);

		set_verifier_halted(false);
	});
}
