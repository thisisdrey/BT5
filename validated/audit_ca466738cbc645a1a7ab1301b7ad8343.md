### Title
Cross-StackerDB chunk replay due to missing contract/channel binding in the signed digest - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` (and thus every signature verified by `StackerDBChunkData::verify`/`SlotMetadata::verify`) only commits to `slot_id`, `slot_version`, and `data_hash`. It does not bind the signature to the specific StackerDB smart-contract/channel the chunk is destined for. Because the Stacks Nakamoto signer set assigns the *same* signer address to the *same* `slot_id` across multiple distinct StackerDB contracts (one per signer message type, e.g. `signers-0-0`, `signers-0-1`, …, `signers-1-0`, `signers-1-1`, …), a chunk validly signed for one contract/message channel is also a validly-verifying chunk for any other channel where that signer owns the same slot. A relaying peer can take a legitimately-signed chunk observed for one channel and push/replay it into a different channel, and the receiving node's signature check will accept it because the digest never encodes which contract it was meant for.

### Finding Description
`SlotMetadata::auth_digest` only hashes: [1](#0-0) 

`verify()` recovers the signer's public key from that same digest and compares only the public-key hash to the expected `principal` passed in by the caller — it never checks which contract the message is destined for: [2](#0-1) 

The contract identity is only used *outside* the signature, to select which per-contract signer/version table to check against: [3](#0-2) [4](#0-3) 

The Nakamoto signer set architecture creates many separate StackerDB contracts per signer set that all draw their slot-to-signer mapping from the *same* underlying `.signers` state, split only by message type/id: [5](#0-4) [6](#0-5) 

This is directly confirmed by a test that shows the *identical* slot list is returned for every `signers-{set}-{message_id}` contract belonging to the same signer set: [7](#0-6) 

Consequently, for a given signer address `S` assigned slot `K` in signer-set page `p`, `S`'s signature over `(K, version, hash)` verifies successfully against *every* `signers-p-*` contract, because `verify()` never checks the contract id, and `try_replace_chunk`/`validate_received_chunk` only look up the per-contract signer table for slot `K`, not whether the signature itself is scoped to that contract: [8](#0-7) 

This is the analog of the reported "Unchecked Refund Token" bug class: a critical binding field (there, `refund_token`; here, the destination contract/channel identifier) is omitted from the value that gets cryptographically committed to, allowing an attacker to reuse an authorization object (there, the `prepared_order` PDA; here, a signed `StackerDBChunkData`) in an unintended context that the signer did not commit to.

### Impact Explanation
An unprivileged relaying node that has observed (or itself received via prior legitimate replication) a validly-signed chunk for one signer-message StackerDB contract can inject that exact chunk (unmodified `sig`, `slot_id`, `slot_version`, `data`) as a push chunk (`StackerDBPushChunkData`) targeting a *different* contract, as long as:
- the same signer address owns the same `slot_id` in the target contract (guaranteed by the `.signers` shared-state design), and
- the target contract's stored version for that slot is currently lower than the replayed `slot_version` (a condition attacker/relay can wait for or arrange, since versions are tracked independently per contract).

The receiving node will accept and store the wrong-channel data as if it were legitimate content of that other channel (`try_replace_chunk` succeeds because `slot_desc.verify(&slot_validation.signer)` passes), and will then re-broadcast it to further neighbors during normal StackerDB gossip/replication, propagating forged/misattributed data network-wide. This is a case of serving/storing non-canonical data (data intended and signed for a different message channel) as canonical content of the target channel — a data-integrity break in the signer message-routing system that downstream consumers (e.g. signer software / miner coordination logic) rely on to be message-type-scoped by construction of the digest, which it is not.

### Likelihood Explanation
No signer private key or admin role is required by the attacker — only observation of network traffic (or possession of any previously-replicated chunk) and the ability to relay a `StackerDBPushChunkData` message, both of which are ordinary unauthenticated p2p capabilities available to any peer. The precondition (shared signer/slot mapping across message-type contracts of the same signer set) is not incidental — it is the designed behavior of `.signers`/`signers-{set}-{id}.clar`, so it holds for every signer in every reward cycle, making the attack broadly and reliably reachable, bounded only by the target slot's current version being behind the replayed version.

### Recommendation
Include the destination `smart_contract_id` (or an equivalent StackerDB/channel identifier) in `SlotMetadata::auth_digest()` so that a signature is only valid for the specific contract/channel it was created for, mirroring the fix applied for the analogous `refund_token`-omission bug (binding all context-defining fields into the hashed/committed value before signing/verifying).

### Proof of Concept
1. Let signer `S` (private key `sk`) own `slot_id = K` in both `signers-0-0` and `signers-0-1` (guaranteed since both draw from `stackerdb-signer-slots-0` in `.signers`).
2. `S` legitimately signs and pushes chunk `C = StackerDBChunkData{ slot_id: K, slot_version: V, sig, data: D }` to `signers-0-0` (e.g. a legitimate block-response message for that channel). Signature verifies via `auth_digest()` over `(K, V, hash(D))`.
3. An observing relay node (no key required) copies `C` verbatim and sends it as a `StackerDBPushChunkData{ contract_id: signers-0-1, chunk_data: C }` to a victim node whose local version for `(signers-0-1, K)` is `< V`.
4. Victim's `validate_received_chunk`/`try_replace_chunk` look up the `signers-0-1` signer table, find `S` at slot `K`, call `slot_desc.verify(&S)`, which succeeds because the digest never referenced `signers-0-0`.
5. The victim stores `D` (data meant for the other channel) as the current chunk for `signers-0-1` slot `K`, and rebroadcasts it to its own neighbors during StackerDB replication.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
