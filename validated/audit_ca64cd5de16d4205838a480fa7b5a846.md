### Title
Unvalidated ABI-decoded array length causes OOM/DoS in TVM precompiled-contract signature helpers - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE describes `libnfs_zdr_string` trusting an attacker-controlled length field from XDR data and using it to size a buffer without validating it against the actual available bytes, causing an integer overflow. The same bug class exists in java-tron's TVM precompiled-contract ABI decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, which read a 32-byte "length" word directly out of caller-supplied `data` and use it to allocate arrays / compute byte offsets with no bounds check against `data.length`.

### Finding Description
`extractBytesArray` and `extractSigArray` take `offset` into a `DataWord[] words` array (derived from the raw precompiled-contract call `data`) and read `len = words[offset].intValueSafe()`: [1](#0-0) [2](#0-1) 

`DataWord.intValueSafe()` only guards against negative/overflowing conversion by clamping to `Integer.MAX_VALUE`; it performs no validation that the value is a plausible/consistent array length for the supplied `data` buffer: [3](#0-2) 

The decoded `len` (attacker-controlled, up to `Integer.MAX_VALUE`) is then used directly to allocate `new byte[len][]`, and per-element `bytesOffset`/`bytesLen` values are likewise taken from attacker data and used to slice `data` via `Arrays.copyOfRange(data, offset, offset + len)` in `extractBytes`, with no check that `offset`/`offset+len` stay inside `data.length`: [4](#0-3) 

The only sanity check present anywhere near these helpers, `isValidAbiEncoding`, validates the overall `data.length` is a multiple of `WORD_SIZE` and has a consistent tail size for a fixed `itemWords`; it does not verify the decoded `len`/`bytesOffset`/`bytesLen` values extracted from inside `data` are within bounds: [5](#0-4) 

This mirrors the libnfs pattern exactly: a length is read from untrusted wire data and trusted for buffer sizing/slicing without validating it against the real payload size.

### Impact Explanation
Because `len` can be driven up to `Integer.MAX_VALUE` via `intValueSafe()`, `new byte[len][]` can trigger a huge/oversized array allocation attempt, throwing `OutOfMemoryError` (an unchecked `Error`, not a checked `Exception`) while a node is processing a transaction that calls the affected precompiled contract. Additionally, out-of-range `bytesOffset`/`bytesLen` values feed `Arrays.copyOfRange` with invalid bounds, causing `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` deep inside precompiled-contract execution. Depending on how these are caught (or not) up the TVM execution stack, this can crash/halt block processing for the node executing the transaction — consistent with the "node crash or halt" impact class in scope.

### Likelihood Explanation
This code sits in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`, which implements TVM precompiled contracts reachable from any smart-contract `CALL`/`STATICCALL` performed by an unprivileged transaction sender or contract deployer — no special privilege is required to reach this code, only crafting the call data (`data`) with a malicious length/offset word. This makes the likelihood high for any deployed contract invoking the affected precompile with attacker-influenced call data.

### Recommendation
Add explicit bounds validation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before using decoded `len`, `bytesOffset`, and `bytesLen`: verify `offset + len` stays within `words.length`, and that computed byte offsets/lengths stay within `data.length`, rejecting (returning failure) instead of allocating or slicing on out-of-range values. Also consider capping `len` to a sane maximum before allocation to avoid `OutOfMemoryError` from a single crafted call.

### Proof of Concept
Not fully confirmed at the call-site level: I located the three unsafe decode helpers and traced their unsafe integer-based length/offset handling, but I was not able to conclusively identify (within tool budget) which specific precompiled-contract `execute()` method (e.g., a signature-batch-verification contract) invokes `extractBytesArray`/`extractSigArray`, nor whether an additional bounds check exists earlier in that caller that might already mitigate this. A background Devin session with full file access would be needed to enumerate the exact `execute(byte[] data)` call sites for these three helpers, construct a minimal call-data payload with an oversized length word, and confirm whether it reaches these unchecked allocations/slices at runtime.

    if (offset > words.length - 1) {

    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
