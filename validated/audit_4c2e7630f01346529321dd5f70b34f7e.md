## Analog Found

### Title
Missing bounds validation on precompile ABI array length fields causes out-of-bounds array access in `ValidateMultiSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (invoked by any TVM contract call to its fixed address) decodes an attacker-supplied ABI-encoded signature array using `extractBytesArray()`/`extractSigArray()`. Like the OCFS2 `ocfs2_check_dir_entry()` bug — where a directory-entry length field taken from disk was used to index into a buffer without validating it stayed within the block — these helpers take an attacker-controlled length word from the call data and use it to index further into the `DataWord[] words` array without validating that the resulting index stays inside array bounds.

### Finding Description
`extractBytesArray` and `extractSigArray` only guard against the initial `offset` being past the end of the words array, but never validate `len` (attacker-controlled) against the remaining array size before looping: [1](#0-0) [2](#0-1) 

`len = words[offset].intValueSafe()` is fully attacker-controlled (any 32-bit value coerced via `intValueSafe()`), and the loop then reads `words[offset + i + 1]` for `i` up to `len - 1` with no check that `offset + i + 1 < words.length`, so a crafted call triggers `ArrayIndexOutOfBoundsException`.

This is reached directly from `ValidateMultiSign.execute()`: [3](#0-2) 

Critically, the call to `extractBytesArray`/`extractSigArray` happens **before** the method's own `try { ... } catch (Throwable t)` block (which only wraps the permission/signature-recovery logic starting later), so the thrown `ArrayIndexOutOfBoundsException` is not locally caught. By contrast, the neighboring `BatchValidateSign.execute()` defensively wraps its whole `doExecute` call in a broad `try/catch (Throwable t)`, showing the codebase is aware such runtime exceptions from these decoders are unsafe if left unguarded — an awareness that was not applied to `ValidateMultiSign`.

### Impact Explanation
Any account can trigger this by deploying/calling a contract that invokes the `ValidateMultiSign` precompile (a byte4-selected function of a fixed precompiled address, reachable from ordinary `TriggerSmartContract` transactions) with a crafted `words[3]`-derived offset/length so that the array index escapes the `DataWord[] words` bounds. This produces an uncaught `ArrayIndexOutOfBoundsException` inside VM execution triggered by a single unprivileged transaction, which is the same "attacker-controlled length used to read past a validated buffer" root cause as CVE-2024-41015. Depending on whether upstream transaction/block processing genuinely isolates VM runtime exceptions per-transaction, this can manifest as a node processing exception disrupting execution of that transaction/block, i.e. a denial-of-service surface reachable by any address with an ordinary, unprivileged contract call.

### Likelihood Explanation
High — the trigger is a single unprivileged smart contract call carrying attacker-chosen ABI words; no special permissions, staking, or SR/witness status is required, and the vulnerable code path (`ValidateMultiSign.execute()`) is on the default (non-`allowTvmSelfdestructRestriction`) branch as well as the sig-array branch.

### Recommendation
Add explicit bounds checks in `extractBytesArray` and `extractSigArray` (and `extractBytes32Array`, which has no offset check at all) verifying that `len >= 0` and `offset + len + 1 <= words.length` (and that computed `bytesOffset`/`bytesLen` stay within `data.length`) before indexing, returning an empty/failure result otherwise — mirroring the `ocfs2_check_dir_entry()` fix of validating every derived offset/length against the real buffer bounds before use. Additionally wrap the array-extraction calls in `ValidateMultiSign.execute()` within the existing defensive `try/catch` (as already done in `BatchValidateSign`) so any residual decoding fault degrades to `DATA_FALSE` rather than propagating an uncaught runtime exception.

### Proof of Concept
1. Craft ABI-encoded call data for `ValidateMultiSign`'s functional signature where the pointer at `words[3]` selects an `offset` near the end of the encoded word array.
2. Set the length word `words[offset]` to a large value (e.g., `0x7fffffff`) so the loop in `extractBytesArray`/`extractSigArray` computes `offset + i + 1` indices beyond `words.length`.
3. Broadcast a `TriggerSmartContract` transaction invoking the precompile with this data; `words[offset + i + 1]` throws `ArrayIndexOutOfBoundsException` before the local `try/catch` in `ValidateMultiSign.execute()` can intercept it, propagating up through the VM's call-execution path for that transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
