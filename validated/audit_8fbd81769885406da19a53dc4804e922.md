### Title
Unprivileged repository-creation RPC leaves a permanent stale partition assignment that grieves the target relative path - ([File: internal/gitaly/storage/storagemgr/middleware.go], [File: internal/gitaly/storage/storagemgr/partition_assigner.go])

### Summary
Gitaly's WAL/transaction-based storage manager assigns every repository a `PartitionID` in a key-value table before the repository actually exists on disk. For repository-creating RPCs (e.g. `CreateRepository`, `CreateRepositoryFromBundle`, `CreateRepositoryFromURL`, `CreateRepositoryFromSnapshot`, `CreateFork`), the assignment is written first, and only afterwards does the actual repository creation happen. If the creation step then fails, the partition assignment is not rolled back, so a stale entry is left keyed by the target `relativePath` permanently in the key-value store.

### Finding Description
`beginTransactionForRepository` explicitly documents the non-atomicity: [1](#0-0) 

For an RPC classified in `repositoryCreatingRPCs`, `Begin` is called with `AllowPartitionAssignmentWithoutRepository: isRepositoryCreation` set to `true` for a `relativePath` that does not yet exist on disk.

Inside `partitionAssigner.getPartitionIDRecursive`, when the assignment is not found, the assigner takes the "slow path": it validates whether the git directory exists, and if it does not — but the call is a repository-creation RPC — it proceeds to allocate and durably persist a partition ID for that path anyway: [2](#0-1) 

The persisted mapping is written unconditionally via `assignPartitionID` → `partitionAssignmentTable.setPartitionID`: [3](#0-2) 

This assignment happens purely as a side effect of opening the transaction for the RPC — before any quorum vote, before `repoutil.Create` performs its `os.Stat` existence check, and before the actual repository payload (bundle, snapshot, clone, etc.) is validated. An ordinary, unprivileged caller of a repository-creation RPC can trivially force the *actual* repository-creation step to fail after the assignment has already been persisted, for example by submitting an invalid Git bundle to `CreateRepositoryFromBundle` (observed to fail with `"cloning bundle: waiting for git-clone: exit status 128"`) or a bad URL/host to `CreateRepositoryFromURL`/`CreateRepositoryFromSnapshot`. In all such cases the repository is never created on disk, and `repoutil.Create`'s pre-lock `os.Stat` check confirms nothing is written to the real path, yet the partition assignment made in `Begin` remains recorded in the KV store keyed by that exact relative path, with no compensating cleanup path shown in the codebase.

### Impact Explanation
This is a direct structural analog of the reported `initMarketStartTime` bug: an unprivileged actor triggers a one-time "already assigned" guard for a resource identifier before the resource is legitimately created, and the guard is never reset on failure. Once a `relativePath` has a stale partition assignment, any subsequent repository-creation attempt for that same relative path will resolve to the (already-allocated, but semantically orphaned) partition rather than being treated as a fresh partition assignment — since `getPartitionIDRecursive`'s fast path immediately returns the existing (stale) `PartitionID` on the next call without re-validating repository state. Because partition IDs and transaction semantics (WAL replay, snapshotting, quorum voting) are built around the assumption that a partition assignment corresponds to a coherent, eventually-created repository, an attacker can pollute the KV keyspace with orphaned assignments purely by supplying malformed payloads to repository-creation RPCs, at effectively zero cost per attempt. This is a denial-of-service / storage-metadata corruption primitive reachable by any caller entitled to invoke a repository-creation RPC (which, per the code's own comment, is a known, unresolved gap referencing gitlab-org/gitaly#5957), not a privileged operator action.

### Likelihood Explanation
Likelihood is high: the bug is deterministically triggerable with a single malformed RPC call (e.g. `CreateRepositoryFromBundle` with garbage bundle bytes, or `CreateRepositoryFromURL`/`CreateRepositoryFromSnapshot` pointed at an unreachable or invalid resource), requires no race condition, no elevated privileges beyond what is needed to call any repository-creating RPC, and is explicitly acknowledged as non-atomic in the code's own comment.

### Recommendation
Make partition assignment and repository creation atomic, or add compensating cleanup: if the repository-creation RPC fails after a partition assignment was newly created for a non-existent repository, delete the corresponding `partition_assignment/<relativePath>` entry (and any allocated partition metadata) as part of the transaction rollback path in `beginTransactionForRepository`/`Transaction.finish`. Alternatively, defer persisting the partition assignment until the repository-creation transaction actually commits successfully, tracking the tentative assignment only in memory until then.

### Proof of Concept
1. Call `CreateRepositoryFromBundle` (or `CreateRepositoryFromURL`/`CreateRepositoryFromSnapshot`) with a `Repository{RelativePath: "attacker-target.git"}` and a deliberately invalid bundle/URL/tar payload.
2. `beginTransactionForRepository` begins a write transaction for `"attacker-target.git"` with `AllowPartitionAssignmentWithoutRepository=true` because the RPC is in `repositoryCreatingRPCs`.
3. `partitionAssigner.getPartitionIDRecursive` finds no existing repository on disk, confirms `isRepositoryCreation=true`, and calls `assignPartitionID`, persisting `partition_assignment/attacker-target.git → <new PartitionID>` in the KV store.
4. The RPC handler subsequently fails while trying to materialize repository contents (invalid bundle/URL/tar), and `repoutil.Create`'s pre-lock `os.Stat` confirms no directory exists at the target path — the RPC returns an error and no repository is created.
5. The partition assignment persisted in step 3 is never removed. `internal/gitaly/storage/storagemgr/partition_assigner.go` provides no rollback of `setPartitionID` on transaction failure, leaving `"attacker-target.git"` permanently bound to an orphaned partition ID in the KV store.

func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}
