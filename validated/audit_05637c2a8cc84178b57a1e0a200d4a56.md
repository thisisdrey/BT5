### Title
Strict sequential nonce enforcement in Snowbridge inbound queue causes permanent head-of-line-blocking fund lock - (File: bridges/snowbridge/pallets/inbound-queue/src/lib.rs)

### Summary
The Snowbridge inbound-queue v1 pallet requires every Ethereum-originated message to be submitted to Substrate in strict, gapless nonce order per channel (`envelope.nonce != nonce.saturating_add(1)` → reject). This is structurally the same "transaction order dependence" broken invariant flagged in the CBTC report: a monotonic counter comparison couples on-chain settlement acceptance to submission order of an off-chain, permissionless relayer network, with no mechanism to skip or re-derive a missing/unprovable nonce.

### Finding Description
`Pallet::submit` in `bridges/snowbridge/pallets/inbound-queue/src/lib.rs` verifies the message nonce with: [1](#0-0) 

This mirrors the CBTC pattern of gating settlement on strict counter progression, except stricter: it demands exact equality to `current+1` rather than a "greater than" check, so it cannot even silently skip ahead — any nonce submitted before its immediate predecessor is rejected as `InvalidNonce`, and there is no `Set`-of-processed-nonces fallback (the recommendation the CBTC auditor gave). Because `submit` is a public, unprivileged extrinsic (`ensure_signed(origin)?`) callable by any relayer, and Ethereum events for a channel are emitted independently of Substrate block production/relayer availability, delivery order to the pallet is not guaranteed by the protocol — it depends entirely on off-chain relayer behavior (exactly the "off-chain and out-of-scope systems" caveat from the report).

Critically, proving nonce `N` requires an execution-header ancestry proof anchored in a beacon-chain finalized header that is retained only in the bounded ring buffer `FinalizedBeaconStateBuffer` in `bridges/snowbridge/pallets/ethereum-client/src/lib.rs`: [2](#0-1) [3](#0-2) 

If message with nonce `N` is delayed (relayer outage, censorship, mempool congestion, or the relayer simply never submits it) while the beacon client continues advancing and evicts the finalized state needed to prove `N`'s inclusion, nonce `N` becomes permanently unprovable. Because `Nonce<T>` requires exact sequential progression with no set-based tracking, every subsequent nonce `N+1, N+2, ...` for that channel is permanently blocked — this is a stronger version of the CBTC "revert a valid deposit" scenario: instead of one deposit reverting and being retried, an entire channel's future inbound messages (and the Ether/token value locked in the Ethereum Gateway contract awaiting those messages) become permanently stuck.

### Impact Explanation
This qualifies as "permanent user-fund or bridge-state lock": user assets locked in the Ethereum Gateway contract are represented on the Substrate side only once the corresponding nonce is accepted. A stuck low nonce blocks the entire channel indefinitely, since `Nonce<T>` is a single scalar per `ChannelId` with no gap-tolerant tracking, unlike the outbound-queue-v2/inbound-queue-v2 designs which key state by nonce (`PendingOrders<T>` map, `SparseBitmapImpl` `Nonce<T>` bitmap) and therefore tolerate reordering. This is a design regression specific to the v1 inbound queue still present in the runtime (bridge-hub-rococo/wococo use `snowbridge_pallet_inbound_queue`, confirmed by governance test references to `snowbridge_pallet_inbound_queue::Nonce`).

### Likelihood Explanation
No malicious actor is required — this can be triggered by ordinary relayer unavailability, network partition, or resource exhaustion of a single relayer combined with normal beacon-client header rotation (evicting the old finalized state needed to re-prove the stuck nonce). Since `submit` is permissionless and open to any relayer, and Ethereum event emission timing versus Substrate relayer availability is not coordinated, this is a realistic operational condition, not a contrived edge case.

### Recommendation
Apply the same fix the CBTC auditor recommended: replace the strict `nonce == last+1` sequential gate with a set/bitmap of processed nonces (as already done in `inbound-queue-v2`'s `SparseBitmapImpl`), decoupling dispatch order from Ethereum emission order, and/or ensure the beacon client retains (or can re-derive via long-range ancestry proofs) sufficient finalized state so that no valid, not-yet-delivered nonce ever becomes unprovable before it can be replayed.

### Proof of Concept
1. Channel C has last accepted nonce = 10.
2. Ethereum Gateway emits events for nonces 11 and 12 (two independent deposits/messages).
3. Relayer submitting nonce 11 goes offline/is censored; another relayer submits nonce 12 first.
4. `submit(nonce=12)` fails with `InvalidNonce` since `12 != 10+1` [1](#0-0) , so it is simply retried — but if nonce 11's underlying beacon finalized-state proof window rolls out of `FinalizedBeaconStateBuffer` (bounded ring buffer) before any relayer submits it [3](#0-2) , nonce 11 becomes permanently unprovable.
5. Nonce 12 (and all subsequent nonces for channel C) can never be accepted because `Nonce<T>` for the channel never advances past 10, permanently locking the Ethereum-side value associated with nonces 11+ from ever being represented/settled on the Substrate side.
