### Title
Priority-ordered scan-budget exhaustion by mutually-conflicting attacker transactions starves lower-priority victim transactions - (File: core/src/banking_stage/transaction_scheduler/greedy_scheduler.rs)

### Summary
`GreedyScheduler::schedule` pops transactions from the container's `BTreeSet` priority queue strictly by priority and increments `num_scanned` for every pop, whether or not the transaction is actually scheduled. [1](#0-0)  Transactions that fail with `UnschedulableConflicts`/`UnschedulableThread` are simply collected into `unschedulables` and reinserted into the same priority queue at the end of the pass with their original (unchanged) priority. [2](#0-1) [3](#0-2)  If a large enough number of higher-priority-but-unschedulable transactions exist above a lower-priority legitimate ("victim") transaction, every scheduling pass will scan exactly `max_scanned_transactions_per_scheduling_pass` items, all belonging to the attacker, and terminate before the victim is ever popped.

### Finding Description
The scheduling loop condition is:
```
while budget > 0
    && num_scanned < self.config.max_scanned_transactions_per_scheduling_pass
    && !schedulable_threads.is_empty()
    && !container.is_empty()
``` [4](#0-3) 
`container.pop()` always returns the current highest-priority `TransactionPriorityId` in the `BTreeSet`, regardless of whether it can be scheduled. [5](#0-4)  When `try_schedule_transaction` returns `TransactionSchedulingError::UnschedulableConflicts` (from `ThreadAwareAccountLocks::try_lock_accounts` returning `TryLockError::MultipleConflicts`, i.e. the transaction's accounts are already locked on more than one worker thread), the id is only pushed to `self.unschedulables`, not dropped, and is reinserted into the priority queue with the same priority at the end of the pass via `container.push_ids_into_queue(self.unschedulables.drain(..))`. [6](#0-5) [3](#0-2)  The test `test_schedule_single_threaded_scheduling_scan_limit` and `test_schedule_scan_past_highest_priority` confirm that scanning (not scheduling) is what consumes the scan budget, and that `UnschedulableConflicts` items are counted separately from scheduled ones and simply skipped. [7](#0-6) [8](#0-7) 

If an attacker submits more than `max_scanned_transactions_per_scheduling_pass` (default 100,000) transactions, all with priority strictly above the victim's transaction, and constructed so each references accounts that are simultaneously locked on two or more different worker threads (`MultipleConflicts`), then every call to `schedule()` will: pop all attacker transactions in priority order, mark them `UnschedulableConflicts`, hit `num_scanned == max_scanned_transactions_per_scheduling_pass`, and requeue them at their original priority — before the loop ever reaches the victim transaction sitting lower in the `BTreeSet`. Because `push_ids_into_queue` re-inserts with unchanged priority, this state is stable across an arbitrary number of subsequent `schedule()` invocations (i.e., the entire leader slot, and potentially subsequent slots if the container is not cleared/expired), so the victim is never popped, never scheduled, and never charged a fee.

Existing safeguards do not mitigate this:
- Sigverify/QoS rate limits packets/connections but do not enforce priority diversity or per-account rate limiting sufficient to prevent priority-ordered flooding.
- The container's capacity-based eviction (`push_ids_into_queue` dropping the lowest-priority entries when over capacity) actually works against the victim: since the victim is lower-priority, it is the first to be evicted if the container fills up, rather than protecting it. [9](#0-8) 
- There is no mechanism that decays or penalizes the priority of repeatedly-`UnschedulableConflicts` transactions, nor any fairness/aging boost for the victim.

### Impact Explanation
This is a scoped liveness/QoS-evasion issue: an unprivileged, unstaked attacker can perform work (CPU scanning cycles in the hot `schedule()` path) that is never paid for via fees (the attacker's transactions never execute, since they're perpetually `UnschedulableConflicts`), while consuming the entire per-pass scan budget every pass. This matches "grossly underpriced pre-fee work" and denies scheduling opportunity to legitimate lower-priority transactions for the scope of the affected slot(s), which is a QoS/fairness violation of the intended priority-based scheduling guarantee, not a crash or consensus fault.

### Likelihood Explanation
Feasibility requires the attacker to sustain >100,000 (default `max_scanned_transactions_per_scheduling_pass`) uniquely-signed transactions with priority above the target victim, engineered so each one touches accounts locked concurrently on ≥2 different worker threads (to trigger `MultipleConflicts` rather than simple same-thread sequencing, which the scheduler handles fine per `test_schedule_single_threaded_conflict`). [10](#0-9)  This is a non-trivial but plausible engineering effort: it needs sustained throughput of signed transactions (cheap to generate, since fee is only assessed on execution) and does not require staked/privileged access — only high-throughput TPU packet submission, which is within the described unprivileged threat model. The condition is self-sustaining as long as the attacker keeps refreshing/replacing conflicting transactions with valid blockhashes before `max_age` expiry.

### Recommendation
- Separate the "scan" counter from "unschedulable-due-to-conflict" pops so that transactions repeatedly failing due to `UnschedulableConflicts`/`UnschedulableThread` do not indefinitely consume scan budget ahead of lower-priority schedulable transactions — e.g., track and skip past a bounded number of same-pass unschedulable conflicts once already visited, or apply a decaying "effective priority" for transactions that have been kicked back N times within the same slot.
- Consider bounding how many times a given transaction may be marked unschedulable before being deprioritized/held (similar to `hold_transaction`) so it doesn't repeatedly block the head of the queue.
- Add a fairness mechanism (e.g., a small quota reserved for the tail of the queue during each pass) to guarantee forward progress for lower-priority transactions.

### Proof of Concept
```rust
// core/src/banking_stage/transaction_scheduler/greedy_scheduler.rs (test module)
#[test]
fn test_schedule_priority_conflict_starves_lower_priority_victim() {
    let (mut scheduler, work_receivers, _finished_work_sender) = create_test_frame(
        2, // 2 threads needed to create genuine MultipleConflicts
        GreedySchedulerConfig {
            max_scanned_transactions_per_scheduling_pass: 4, // small budget for test
            ..GreedySchedulerConfig::default()
        },
    );

    let pubkey_a = Pubkey::new_unique(); // will be locked on thread 0
    let pubkey_b = Pubkey::new_unique(); // will be locked on thread 1
    let victim_pubkey = Pubkey::new_unique();

    // Two high-priority txs occupy thread 0 and thread 1 respectively.
    // Several higher-priority "attacker" txs each reference BOTH pubkey_a and
    // pubkey_b, causing MultipleConflicts (UnschedulableConflicts) every pass,
    // and are requeued at the same priority.
    // The victim tx (lowest priority) should never be scanned/scheduled
    // once attacker tx count exceeds max_scanned_transactions_per_scheduling_pass.
    let mut container = create_container([
        (Keypair::new(), &[pubkey_a][..], 100, 0),
        (Keypair::new(), &[pubkey_b][..], 99, 1),
        (Keypair::new(), &[pubkey_a, pubkey_b][..], 90, 2), // attacker conflict #1
        (Keypair::new(), &[pubkey_a, pubkey_b][..], 89, 3), // attacker conflict #2
        (Keypair::new(), &[pubkey_a, pubkey_b][..], 88, 4), // attacker conflict #3
        (Keypair::new(), &[pubkey_a, pubkey_b][..], 87, 5), // attacker conflict #4
        (Keypair::new(), &[victim_pubkey][..], 1, 6),       // victim, lowest priority
    ]);

    // Run several scheduling passes simulating repeated calls within/across slots.
    for _ in 0..10 {
        let _ = scheduler.schedule(&mut container, u64::MAX).unwrap();
    }

    // Assert victim's transaction id (6) was never sent to any consume worker.
    let (_, ids0) = collect_work(&work_receivers[0]);
    let (_, ids1) = collect_work(&work_receivers[1]);
    let all_scheduled: Vec<_> = ids0.into_iter().chain(ids1).flatten().collect();
    assert!(
        !all_scheduled.contains(&6),
        "victim transaction should not be starved indefinitely, but was never scheduled"
    );
}
```
Expected result (demonstrating the bug): the victim id `6` is never present in `all_scheduled` across all repeated `schedule()` calls, showing that as long as attacker-controlled `UnschedulableConflicts` transactions occupy the top of the priority queue in numbers ≥ `max_scanned_transactions_per_scheduling_pass`, the victim transaction is starved indefinitely.

            .schedule(
                &mut container,
                u64::MAX, // no budget
            )
            .unwrap();

        assert_eq!(scheduling_summary.num_unschedulable_conflicts, 1);

        assert_eq!(collect_work(&work_receivers[1]).1, [vec![2]]);

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }
