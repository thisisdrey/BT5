Found a concrete resource-leak analog in `BatchValidateSign`.

### Title
Thread-pool task leak on timeout in `BatchValidateSign` precompile can exhaust the shared VM signature-verification thread pool - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The libming CVE describes memory leaked on error/abort paths of an untrusted-input parser, causing resource exhaustion under repeated crafted input. The `BatchValidateSign` precompile has an analogous "leak on early-abort" pattern: work items submitted to a shared, statically-sized `ExecutorService` are never cancelled or removed when the caller-controlled CPU-time budget is exceeded, so submitted `RecoverAddrTask`s continue running/queuing in the shared pool even though the triggering transaction has already failed.

### Finding Description
`BatchValidateSign.doExecute` is reachable by any account that can call a smart contract invoking the `batchvalidatesign` precompile (address `0x66...09`), i.e. any unprivileged contract-triggering transaction. For non-constant calls it submits up to `MAX_SIZE` (16) `RecoverAddrTask` callables to a small, statically shared `ExecutorService workers` sized `availableProcessors()/2 + 1`: [1](#0-0) 

When the aggregate CPU-time budget for the transaction expires before all recover-address tasks finish, `countDownLatch.await(...)` returns `false` and the method immediately throws `Program.Exception.notEnoughTime(...)`: [2](#0-1) 

The `futures` list is abandoned at that point — none of the still-running or still-queued `Future` tasks are cancelled (`future.cancel(...)` is never called), and the outer `execute()` wrapper simply swallows the exception and returns a zero result: [3](#0-2) 

`workers` is a `static` field shared across *all* invocations of this precompile from every transaction/contract in the node process, and is sized independent of transaction volume: [4](#0-3) 

Because energy/CPU-time accounting already lets `getCPUTimeLeftInNanoSecond()` be near-exhausted before submission (it is only checked once via `getCPUTimeLeftInNanoSecond()` for the `await` call, not before submitting the batch), an attacker can repeatedly send transactions that submit near-`MAX_SIZE` batches of `ecrecover`-equivalent tasks (`recoverAddrBySign`, which does EC point recovery — relatively expensive) with a CPU-time budget deliberately tuned so the `countDownLatch.await` frequently times out. Each timeout abandons its `RecoverAddrTask`s in the shared pool without cancellation, so the fixed-size worker pool backs up with abandoned work from many prior transactions, delaying/blocking legitimate `BatchValidateSign` calls (and other TVM execution paths, since the pool is only bounded by CPU cores) queued behind stale work — a queuing/backlog resource exhaustion directly analogous to the libming leak-on-abort pattern.

### Impact Explanation
This is a resource-exhaustion / DoS analog: a small, fixed-size shared thread pool used by a security-critical precompile (batch signature/permission validation) can accumulate abandoned tasks whenever the transaction's CPU-time budget is hit, without any cancellation. Repeated exploitation from unprivileged, cheaply-broadcastable transactions can starve the pool, delaying processing of legitimate `BatchValidateSign` calls and consuming node CPU/threads — a node-level service-degradation impact, consistent with the "Medium" DoS class of the CVE.

### Likelihood Explanation
Likelihood is moderate: it requires deliberately crafting transaction `feeLimit`/CPU-time windows so that `countDownLatch.await` times out after tasks are already submitted (rather than being blocked before submission), and requires repeated invocation to build up backlog in the shared pool. This is achievable by any account able to construct and broadcast `TriggerSmartContract` transactions calling the precompile with a large signature array and a tight CPU-time budget, without needing SR/witness/committee privilege.

### Recommendation
On the `!withNoTimeout` path (and in the `catch` in `execute()`), iterate over `futures` and call `future.cancel(true)` (or track/interrupt in-flight tasks) before throwing/returning, so abandoned work does not linger or execute against a shared pool. Consider also bounding the CPU-time check to occur before task submission, and/or using a per-call bounded executor rather than a small, globally shared one for signature verification.

### Proof of Concept
1. Deploy a contract that calls the `BatchValidateSign` precompile (`0x0000...1009`) with the maximum allowed signature/address arrays (`MAX_SIZE` = 16 signatures), each requiring EC-recover computation.
2. Set the transaction `feeLimit`/CPU budget so that `vmShouldEndInUs` is reached shortly after the 16 `RecoverAddrTask`s are submitted to `workers` but before `countDownLatch.await` completes (tunable by choosing signature counts and `maxCpuTimeOfOneTx` proximity).
3. Broadcast many such transactions in parallel/sequence from an ordinary account; each triggers `notEnoughTime` and abandons its submitted tasks in the shared, small (`cores/2+1`-sized) `workers` pool without cancellation.
4. Observe that concurrent/legitimate calls to `BatchValidateSign` (and, since it's a shared pool, other traffic contending for its threads) experience increasing latency/backlog as abandoned tasks accumulate, degrading node throughput for this API path.
