### Title
Unbounded Memory Allocation in TVM Precompile Array Extraction Helpers - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts (addresses `0x...09` and `0x...0a`) parse calldata-supplied array length words and immediately allocate Java arrays sized by that untrusted value, before any upper-bound validation is enforced. An attacker who deploys or calls a contract that invokes these precompiles with crafted calldata can force the node to attempt allocation of an oversized array, causing excessive memory pressure or an `OutOfMemoryError` on the executing full node.

### Finding Description
`extractBytes32Array` reads a length directly from attacker-controlled calldata and allocates an array of that size with no bound check at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` follow the same unchecked-allocation pattern (`int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];`): [2](#0-1) 

In `BatchValidateSign.doExecute`, the size guard (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) is only checked when `VMConfig.allowTvmSelfdestructRestriction()` is active, yet `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)` for the `addresses` array is invoked unconditionally, regardless of that flag: [3](#0-2) 

Similarly, `ValidateMultiSign.execute` only bounds `sigArraySize` when `allowTvmSelfdestructRestriction()` is enabled, otherwise falling straight into `extractBytesArray`, whose internal `new byte[len][]` allocation happens before the post-hoc `signatures.length > MAX_SIZE` check on line 1076: [4](#0-3) 

The only upstream validation, `isValidAbiEncoding`, merely checks that `data.length` is 32-byte aligned and that the tail is a multiple of the per-item word size; it does not constrain the *value* stored in any individual word, so an attacker can freely set the "array length" word (e.g., to `0xFFFF...FFFF`) independent of the actual calldata size: [5](#0-4) 

This is structurally the same bug class as the rust-zserio advisory: a length prefix taken from untrusted input is trusted and used directly to allocate memory before validation, rather than validating the value against a sane maximum (or against the available buffer size) first.

### Impact Explanation
A crafted `CALL`/`STATICCALL` to the `batchValidateSign` or `validateMultiSign` precompile from any deployed smart contract can trigger allocation of an array with attacker-chosen size (up to `Integer.MAX_VALUE` object-reference slots, i.e. multi-gigabyte allocations on a 64-bit JVM) before any bound/energy-derived sanity check rejects the call. Repeated or parallel invocation (the precompile also spins up thread-pool tasks for signature recovery) can exhaust node heap memory, leading to `OutOfMemoryError`, degraded performance, or a full node crash — a denial-of-service against any node that must execute the transaction, including all validating SRs and API/full nodes. This matches the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Both precompiles are reachable by any account through an ordinary `TriggerSmartContract` (`CALL` to a contract that in turn calls the precompile address, or in some TVM implementations directly if the precompile address is dialed), gated only by `VMConfig.allowTvmSolidity059()`, which has long been active on TRON mainnet. No special privilege, stake, or witness/committee role is required — an unprivileged contract deployer/caller can build and broadcast the malicious calldata. The `extractBytes32Array` path in `BatchValidateSign` has no gating flag whatsoever, so it is unconditionally reachable on any network running this code.

### Recommendation
Validate every length word extracted from calldata (`len` in `extractBytes32Array`, `extractBytesArray`, `extractSigArray`) against the applicable `MAX_SIZE` constant (5 for `ValidateMultiSign`, 16 for `BatchValidateSign`) and against the remaining `words` buffer bounds *before* allocating any array, not just as a post-allocation guard, and do so unconditionally rather than only under the `allowTvmSelfdestructRestriction()` feature flag.

### Proof of Concept
1. Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the ABI header is well-formed (32-byte aligned, tail length consistent with `isValidAbiEncoding`) but the length word at the offset pointed to by the `address[]` array pointer (`words[2]`) is set to a very large value such as `0x00000000000000000000000000000000000000000000000000000000FFFFFF` (or larger, clamped by `intValueSafe()`).
2. Deploy a contract that performs a low-level `call` to the `BatchValidateSign` precompile address (`0x...09`) with this calldata, and broadcast a `TriggerSmartContract` transaction invoking it.
3. On execution, `extractBytes32Array` executes `new byte[len][]` with the attacker-chosen `len` before the `addrArraySize > MAX_SIZE` guard is enforced, causing a large memory allocation attempt on the executing node.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
