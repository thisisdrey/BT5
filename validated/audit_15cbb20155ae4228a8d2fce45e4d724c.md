### Title
Anti-replay window check-then-update race allows duplicate packet acceptance in `ConnectionState.Decrypt` / `VerifyRelay` - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection by calling `window.Check()` to test a message counter, releasing the lock, performing the (comparatively expensive) AEAD decrypt/verify operation with the lock released, and only afterwards re-acquiring the lock to call `window.Update()` which actually records the counter as seen. This mirrors the reported Beedle `Lender.repay` bug class: an externally-observable side effect (successful decryption/acceptance of a message) is allowed to happen before the state that is supposed to prevent duplicate/replayed use of the same counter is committed.

### Finding Description
`Decrypt` (and the structurally identical `VerifyRelay`) is:

```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // "Checks"
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)           // "Interaction" (heavy, lock-free)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)    // "Effects" — committed too late
cs.decryptLock.Unlock()
``` [1](#0-0) [2](#0-1) 

`Bits.Check` only reads the bitmap non-destructively; the counter is only marked as "seen" by `Bits.Update`, which runs after decryption completes: [3](#0-2) [4](#0-3) 

Because the lock is released between `Check` and the decrypt call, and Nebula explicitly supports processing send/receive packets on multiple concurrent routines (`routines` config option), an attacker positioned to capture and duplicate/replay a single legitimate ciphertext packet to the victim in rapid succession can cause two goroutines to enter `Decrypt`/`VerifyRelay` concurrently for the same `messageCounter`. Both goroutines can pass `Check` (since neither has yet called `Update`), both decrypt/verify successfully, and both get treated by the caller in `readOutsidePackets` as a newly-accepted, distinct message — including triggering side effects such as `handleHostRoaming`, `connectionManager.In`, tunnel-payload delivery (`handleOutsideMessagePacket`), lighthouse handling, or relay forwarding — twice for what should be a single, already-consumed message counter. [5](#0-4) 

This is reachable without possessing a CA-signed certificate: the attacker does not need to complete their own authenticated handshake, they only need network-path access to duplicate/replay UDP datagrams belonging to an already-established tunnel between two legitimate, certificate-holding peers.

### Impact Explanation
This breaks the nonce/replay-protection guarantee that the anti-replay window is supposed to provide. A duplicated ciphertext can be accepted twice by the data plane, resulting in message replay (duplicated tunnel traffic delivery, duplicated lighthouse/control message processing, or duplicated relay-forwarded traffic) rather than being rejected as expected. This falls under the explicitly accepted "traffic decryption/forgery/replay" impact category.

### Likelihood Explanation
Exploitation requires (a) network path visibility/duplication capability against a live, already-established tunnel and (b) winning a narrow race window between `Check` and `Update` across concurrent packet-processing routines — feasible when `routines` > 1 (documented multi-core packet processing) or via other packet dispatch parallelism, but timing-sensitive and non-deterministic. It does not require any secret key material or a trusted certificate, only the ability to duplicate an observed packet onto the wire, which is a realistic on-path/off-path UDP attacker capability.

### Recommendation
Follow a Check-Effect ordering that commits the "seen" state atomically with (or before, using an optimistic/pending mark rolled back on failure) the decrypt operation, all under a single critical section, e.g.:
- Hold `decryptLock` across the full `Check` → `Decrypt` → `Update` sequence (or use `window.Update`'s return as the sole gate and roll back on decrypt failure), so no two callers can observe `Check()==true` for the same counter before one of them commits `Update()`.
- Alternatively, replace the two-phase Check/Update with a single atomic "test-and-set" operation on the bitmap performed while still holding the lock across decryption, ensuring no window exists where a duplicate can pass both phases concurrently.

### Proof of Concept
1. Establish a legitimate tunnel between host A and host B (normal handshake, valid certs).
2. Attacker captures one data-plane packet (`header.Message`) sent from A to B, identified by its `MessageCounter` field in the Nebula header.
3. Attacker replays this exact captured UDP datagram to B twice in quick succession (e.g., from two source paths, or via a network tap that duplicates the frame), so B's UDP read path dispatches both copies to `readOutsidePackets` on two different routines concurrently.
4. Both goroutines call `hostinfo.ConnectionState.Decrypt(...)` for the same `messageCounter`; because `window.Check` is called before `window.Update`, and the lock is released between them, both may pass `Check`, both successfully decrypt with the valid (replayed) ciphertext, and both are delivered to `handleOutsideMessagePacket`, duplicating the message/traffic on B's tun device.

Note: exact timing to win the race was not verified with an actual reproduction/test run in this analysis (no execution environment available); the vulnerability is derived from static analysis of the lock/check/decrypt/update ordering in `connection_state.go` and `bits.go`.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
