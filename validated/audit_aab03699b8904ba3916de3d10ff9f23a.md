### Title
Attacker can fill a victim's per-account token lists with dust deposits/transfers, DoSing the victim's deposits, mints, and liquidations — (File: `contracts/DepositToken.sol`, `contracts/Pool.sol`)

### Summary
Metronome tracks each account's held deposit tokens and debt tokens in per-account enumerable sets (`depositTokensOfAccount`, `debtTokensOfAccount` in `Pool`). A combined cap of `MAX_TOKENS_PER_USER = 30` is enforced inside `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the sum of both lists reaches 30 (Pool.sol:79,143-148). Any unprivileged user can add entries to a *victim's* list — without the victim's consent — by calling `DepositToken.deposit(dust, victim)` or `DepositToken.transfer(victim, dust)`, since `_mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance is 0 (DepositToken.sol:486-488, 518-520). This is the same bug class as the reported finding: an unauthenticated caller inflates a per-victim data structure until the victim's own operations start reverting.

### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` lets anyone mint `msdToken` to an arbitrary `onBehalfOf_` address (DepositToken.sol:211-237).
- `DepositToken._mint` and `_transfer` push the token into `depositTokensOfAccount[recipient]` when the recipient's balance goes from 0 to >0 (DepositToken.sol:486-488, 517-520).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens(account_)`, reverting with `UserReachedMaxTokens` when `debt + deposit` list length hits 30 (Pool.sol:204-220, 143-148).
- `DebtToken` follows the same pattern: minting a new debt type calls `pool.addToDebtTokensOfAccount(account_)`, which shares the same combined cap.

Attack path: for every registered `DepositToken` (and the attacker can also route through `VesperGateway.deposit`/`NativeTokenGateway`), the attacker deposits or transfers 1 wei to the victim. After 30 distinct dust entries, the victim's lists are full. From then on:

- Any `deposit(x, victim)` for a deposit token the victim doesn't already hold reverts (`UserReachedMaxTokens` bubbles out of `addToDepositTokensOfAccount` inside `_mint`), so nobody can send the victim a new collateral position.
- The victim cannot mint a `DebtToken` type they don't already hold — `addToDebtTokensOfAccount` reverts — so the victim cannot open a new borrow position or use `SmartFarmingManager.leverage` into a new synthetic.
- `Pool.swap`, liquidation `seize` to `feeCollector`/`liquidator`, and `RewardsDistributor`-driven transfers can also revert when they would add a token to an account already at the cap, extending the DoS surface to third parties interacting with the victim.

### Impact Explanation
Temporary freezing of funds / liveness griefing: the victim is blocked from depositing new collateral types, receiving msdToken transfers, and issuing new debt until they manually clear the dust entries by transferring each dust balance out (a zeroed balance triggers `removeFromDepositTokensOfAccount`, DepositToken.sol:523-525). Existing balances are not stolen and the victim can self-recover, so this is a temporary DoS rather than permanent loss — matching the "temporary freezing of funds" acceptance criterion, though on the weaker end since recovery is available at gas cost to the victim.

### Likelihood Explanation
Fully unprivileged and cheap: the attacker needs only dust amounts of each underlying (or existing msdToken balances) plus gas. No privileged role, oracle manipulation, or timing requirement. The only constraint is the number of registered deposit/debt tokens; the combined cap of 30 makes filling the lists feasible on deployed pools with several collaterals. Note the attack cost scales with the number of distinct registered tokens, so on a pool with few tokens the attacker may need to combine both deposit-token dust and debt-token mints (a dust mint of each synthetic via `DebtToken.issue` against dust collateral also occupies victim slots only for the attacker's own account — the deposit-token path is the primary vector).

### Recommendation
- Gate entries into `depositTokensOfAccount`/`debtTokensOfAccount` on the recipient's consent for unsolicited flows, or exempt dust below a minimum amount (e.g., skip `addToDepositTokensOfAccount` when `amount_` is below a floor, and reject sub-floor first-time deposits/transfers to third-party recipients in `DepositToken._mint`/`_transfer`).
- Alternatively, allow list growth beyond `MAX_TOKENS_PER_USER` for unsolicited inbound entries while keeping the cap enforced only for actions initiated by the account itself (e.g., in `deposit` check `if (_msgSender == onBehalfOf_)` for cap enforcement), so an attacker cannot consume slots the victim needs.

### Proof of Concept
```solidity
// Foundry-style test against a deployed pool
function test_fillVictimTokenLists() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // For each registered deposit token, attacker dust-deposits to victim
    address[] memory dts = pool.getDepositTokens();
    for (uint i; i < dts.length && i < 30; ++i) {
        IDepositToken dt = IDepositToken(dts[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1);
        dt.deposit(1, victim); // adds dts[i] to depositTokensOfAccount[victim]
        vm.stopPrank();
    }
    // Optionally fill remaining slots via transfers of attacker-held msdTokens
    // until debt + deposit list length == MAX_TOKENS_PER_USER (30)

    // Victim can no longer receive a new deposit token type
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    vm.prank(attacker);
    IDepositToken(newDt).deposit(1e18, victim);

    // Victim can no longer mint a new debt/synthetic type
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    vm.prank(victim);
    debtToken.issue(victim, 1e18);
}
```
Caveat: this PoC assumes enough registered deposit tokens exist to reach the cap; on pools with few collaterals the attacker supplements with dust `transfer`s of each msdToken. Victim self-recovery (transferring dust out to free slots) limits the finding to temporary DoS rather than permanent freezing — that limitation should be weighed when assessing severity.
