### Title
Missing Domain Separation in StackerDB Chunk Signature Enables Cross-Contract Replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk as `hash(slot_id, slot_version, data_hash)` only, omitting any binding to the target contract (`QualifiedContractIdentifier`/message-type "lane"). Because the same signer set (and therefore the same `slot_id -> signer address` mapping) is shared across all eight `.signers-{0,1}-{message_id}` StackerDB replicas for a reward cycle, a chunk validly signed by a legitimate signer for one message type/contract can be replayed verbatim into a different `.signers-*` contract where that signer owns the same slot, since the signature's preimage carries no notion of which "deployment"/contract/message-lane it was intended for.

### Finding Description
`SlotMetadata::auth_digest()` [1](#0-0)  and its `verify()`/`sign()` counterparts [2](#0-1)  only commit to `(slot_id, slot_version, data_hash)`. Nothing in the signed preimage binds the signature to a specific `contract_id` (deployment/session equivalent in the external report) or to the message type the chunk is supposed to carry.

The signer slot assignment for a given reward cycle's signer set (0 or 1) is shared verbatim across all eight per-message-type contracts (`signers-{set}-0` through `signers-{set}-7`, covering `BlockProposal`, `BlockResponse`, `BlockPushed`, `MockProposal`, `MockSignature`, `MockBlock`, `StateMachineUpdate`, `BlockPreCommit`), since each queries the same underlying page via `stackerdb-get-signer-slots-page` [3](#0-2)  and `signers-0-xxx.clar`/`signers-1-xxx.clar` [4](#0-3) . Consequently, the same `StacksAddress` typically owns the identical `slot_id` in every one of these eight contracts for that reward cycle parity.

Both the node-local storage path and the P2P sync path validate a received chunk purely by (a) resolving the slot's expected signer address from the *target* contract's config, and (b) verifying the signature against `auth_digest()` — with no cross-check that the chunk was actually produced for that contract/message type:
- `StackerDBSync::validate_received_chunk` [5](#0-4) 
- `StackerDBTx::try_replace_chunk` invoked from the HTTP POST handler [6](#0-5) 

Because the signature itself carries no contract/message-type binding, an attacker who has observed one legitimately-signed chunk from a signer (e.g. a `BlockResponse` chunk from `.signers-0-1`) can resubmit the exact same `(slot_id, slot_version, sig, data)` tuple to a *different* contract in the same signer set (e.g. `.signers-0-3`, the `BlockPushed` lane) where that signer owns the same slot. The target contract's `validate_received_chunk`/`try_replace_chunk` will accept it as authentically signed, because `auth_digest()` produces the identical hash regardless of which contract it's being submitted to.

The payload-type/"lane" consistency check (`signer_message_payload_matches_lane`) exists only in `libsigner`'s downstream event-consumption code [7](#0-6) , which is client-side filtering after the chunk has already been accepted, stored, and gossiped by the node — it does not gate storage or relay.

### Impact Explanation
Once `try_replace_chunk` accepts the replayed chunk, the node immediately relays it network-wide as a `StackerDBPushChunk` message to all peers [8](#0-7) , and peer-to-peer sync (`validate_received_chunk` in `stackerdb/mod.rs`) will likewise accept and further propagate it, since it independently performs the same insufficiently-scoped check. This achieves network-wide propagation of data that is authentically signed but semantically forged for the receiving contract/lane — an unauthorized write of attacker-chosen bytes (the previously-observed chunk's payload) into a StackerDB replica whose meaning/consumers differ from the one the signer intended. This satisfies the "network-wide propagation of forged data" / "unauthenticated/unauthorized write to state" impact class, since the write is not authorized for that specific contract's semantic purpose even though the underlying key is legitimate.

### Likelihood Explanation
Exploitation requires only passively observing one legitimately broadcast, validly-signed StackerDB chunk (chunks are gossiped in the clear over the p2p network and served over public HTTP `/v2/stackerdb/.../chunks` endpoints) and resubmitting the same bytes to a sibling `.signers-*` contract for the same reward-cycle parity. No node secret, signer key, or admin role is needed — this is a pure unprivileged replay by any network participant who can reach the target node's p2p or HTTP-RPC surface.

### Recommendation
Bind the signed digest to the domain/session it is intended for. At minimum, include the target `contract_id` (or a fixed contract-specific "lane"/message-id tag) in `SlotMetadata::auth_digest()`:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.serialize_to_vec()); // or contract name/message_id
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
This requires threading `contract_id` through `sign()`/`verify()` in both `SlotMetadata` and `StackerDBChunkData`, and updating all call sites (`validate_received_chunk`, `try_replace_chunk`, signer clients) to pass the contract being targeted.

### Proof of Concept
1. Observe a legitimately-signed chunk `(slot_id=3, slot_version=5, sig=S, data=D)` broadcast by signer address `A` under contract `.signers-0-1` (`BlockResponse` lane), e.g. via the public `/v2/stackerdb/.../chunks` GET endpoint or p2p `StackerDBPushChunk` gossip.
2. Confirm (via `stackerdb-get-signer-slots-page`, which is identical across `.signers-0-0`..`.signers-0-7`) that `A` also owns `slot_id=3` in `.signers-0-3` (`BlockPushed` lane).
3. POST the identical tuple `(slot_id=3, slot_version=5, sig=S, data=D)` to `/v2/stackerdb/{signers-0-3-address}/signers-0-3/chunks` on any target node.
4. `try_replace_chunk` → `validate_received_chunk`-equivalent checks pass because `SlotMetadata::verify()` recomputes the same `auth_digest()` independent of contract, and slot version/size checks succeed against `.signers-0-3`'s independently-tracked version counter (which starts fresh, so version 5 is likely still "newer").
5. The node accepts, stores, and relays the chunk as an authentic `BlockPushed` message in `.signers-0-3`, even though `A` never signed anything intended for that lane.
