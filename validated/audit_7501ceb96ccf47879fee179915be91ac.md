Nowhere in this digest is the target `QualifiedContractIdentifier` (i.e., which StackerDB instance the write is intended for) included. Both the write path in `StackerDBTx::try_replace_chunk` and the network-facing gate `PeerNetwork::validate_received_chunk` verify the signature purely against `(slot_id, slot_version, data_hash)` and the slot's registered signer for *that* contract — they never bind the signature to the contract identifier itself: [2](#0-1) [3](#0-2) 

Because chunks and their signatures are broadcast/gossiped publicly (`process_stacker_db_chunks` rebroadcasts any newly stored chunk to neighbors) [4](#0-3) , and because the same signer address commonly owns the same `slot_id` across multiple distinct StackerDB contracts (e.g., successive reward-cycle signer-set contracts, or miner contracts sharing signer/miner key sets), an already-observed, validly-signed chunk that was authorized by its signer for contract A can be resubmitted verbatim (same `slot_id`, `slot_version`, `data`/`sig`) to a *different* contract B via the unauthenticated HTTP `POST /stackerdb/...` endpoint, as long as B independently registers the same address as owner of that `slot_id` and the target slot's current version in B is lower than the replayed `slot_version`. `try_replace_chunk`/`validate_received_chunk` will accept it because every check they perform (`chunk_size`, `slot_desc.verify(&slot_validation.signer)`, staleness, `max_writes`) is scoped per-contract and none of them re-derive or check the contract identifier from the signed payload. ## Title
Cross-Contract StackerDB Chunk Signature Replay — Signed Chunks Are Not Bound to Their Target Contract Identifier - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
A StackerDB chunk's authentication digest (`SlotMetadata::auth_digest`) only covers `slot_id`, `slot_version`, and `data_hash`, omitting the target contract identifier. This lets a legitimately-signed, publicly-observable chunk be replayed unmodified into any other StackerDB instance where the same address happens to own the same slot ID, resulting in unauthorized writes of attacker-chosen (but victim-signed) data into a StackerDB the signer never intended to write into.

### Finding Description
`SlotMetadata::sign`/`verify` operate over `auth_digest()`, whose scope is `(slot_id, slot_version, data_hash)` only [6](#0-5) . Every write-acceptance path — the node-to-node chunk relay validator `PeerNetwork::validate_received_chunk` [7](#0-6) , the storage-layer gate `StackerDBTx::try_replace_chunk` [8](#0-7) , and the HTTP `POST /stackerdb` handler [5](#0-4)  — resolve the expected signer *per target contract* and check the signature/version against that contract's own slot bookkeeping, but never verify that the signature itself commits to that specific contract. Consequently the equality that should hold — "chunk authorized by signer for contract X" ⇒ "chunk only storable in contract X" — is not enforced; it degrades to "chunk authorized by signer for slot N of any signature scheme" ⇒ "storable in any contract where signer owns slot N of a not-yet-superseded version."

### Impact Explanation
This is an unauthenticated/unauthorized write to StackerDB state: an attacker with no keys of their own can take a chunk broadcast for one StackerDB contract (chunks are gossiped/broadcast to all replicating neighbors via `process_stacker_db_chunks` [4](#0-3) , and are also servable/queryable) and cross-post it into a different contract's identical slot, causing that unrelated contract's replica state to be overwritten with data the signer never approved for that context. Depending on which contract is targeted (e.g., miner or signer coordination StackerDBs that reuse the same signer addressing across contracts/reward cycles), this can corrupt or desynchronize application-layer protocol state that consensus-critical off-chain components (miners/signers) rely on, satisfying the "unauthenticated/unauthorized write to state or StackerDB" Critical-impact criterion.

### Likelihood Explanation
Requires only: (1) observing a previously broadcast, validly-signed chunk (trivial, since chunks propagate over the p2p network and are queryable), and (2) a second StackerDB contract configured with the same address as the owner of the same `slot_id` — a configuration pattern that recurs naturally across reward-cycle-indexed signer/miner StackerDB contracts. No private key or privileged role is needed by the attacker.

### Recommendation
Include the target `QualifiedContractIdentifier` (and ideally the reward-cycle/consensus context, mirroring `rc_consensus_hash` used elsewhere) inside `SlotMetadata::auth_digest()` so that a signature is cryptographically bound to the specific StackerDB instance it was created for, preventing cross-contract replay.

### Proof of Concept
1. Signer `S` owns slot `0` in StackerDB contract `A` and also owns slot `0` in StackerDB contract `B` (a realistic scenario when the same signer set is reused across successive reward-cycle contracts).
2. `S` signs and pushes a legitimate chunk `(slot_id=0, slot_version=5, data=D_A)` to contract `A`; this propagates via gossip (`process_stacker_db_chunks`).
3. Attacker observes this chunk (e.g., via `GET` StackerDB chunk endpoint or network sniffing) and resubmits the identical `(slot_id, slot_version, sig, data)` tuple to contract `B`'s `POST /stackerdb` endpoint, provided B's current version for slot 0 is `< 5`.
4. `try_replace_chunk` for contract `B` calls `slot_desc.verify(&slot_validation.signer)`, which succeeds because the digest never referenced contract `A`, so `D_A` is stored into `B`'s slot 0 despite `S` never authorizing a write to `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
