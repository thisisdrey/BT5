Confirmed. The vulnerability is in the `taker == maker` exact-match branch of `matchSingleOrder` in `MarketSellAssetActuator.java`, which lacks the zero-check safeguard present in the `taker > maker` branch.

### Title
Integer division rounding in exact-match order path lets a taker drain a maker's remaining order for zero payment - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`matchSingleOrder` computes the buy-token amount a maker receives using floor division via `MarketUtils.multiplyAndDivide`. In the "taker == maker" exact-match branch, this computed amount is used without any zero-value guard, unlike the structurally identical "taker > maker" branch, which explicitly checks for and refunds a zero result. This asymmetry allows an attacker to craft a taker order whose remaining sell quantity produces a `takerBuyTokenQuantityRemain` that exactly equals an existing maker order's remaining sell quantity, while the reverse-direction floor-division computation for the maker's payout rounds down to zero — extracting the maker's entire remaining token balance for free.

### Finding Description
In `matchSingleOrder`, `takerBuyTokenQuantityRemain` is computed with `MarketUtils.multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity, ...)`, which performs `floorDiv` division (see `MarketUtils.multiplyAndDivide` at `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java:264-277`). [1](#0-0) 

When `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`, the code enters the "taker == maker" branch and computes the amount owed to the maker with the inverse ratio: [2](#0-1) 

Because both divisions use floor rounding, and they are performed with inverted numerator/denominator relative to each other, it is mathematically possible to choose `takerSellRemainQuantity` such that the forward floor division exactly equals the maker's remaining quantity `R`, while the reverse floor division `R * makerBuyQuantity / makerSellQuantity` rounds down to `0`. In that case, `makerOrderCapsule.setSellTokenQuantityRemain(0)` unconditionally zeroes out the maker's order, `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the full remaining sell amount) is transferred to the taker via `addTrxOrToken`, and `makerBuyTokenQuantityReceive = 0` is credited to the maker — i.e. the maker gets nothing back for the tokens they lose. [3](#0-2) 

By contrast, the "taker > maker" branch performs the exact same reverse computation but explicitly guards against the zero result and refunds the maker's remaining sell tokens instead of zeroing the order with no payout: [4](#0-3) 

No equivalent guard exists in the "taker == maker" branch, so the safety property the code relies on ("it would not happen here", commented at line 468) is not actually enforced for this code path.

**Concrete example:** Suppose a maker's book order has `makerSellQuantity = 11`, `makerBuyQuantity = 2`, and (due to prior partial fills) `makerSellRemainQuantity = 5`. An attacker submits a taker sell order with `takerSellRemainQuantity = 1` against this pair. Then:
- `takerBuyTokenQuantityRemain = floor(1 * 11 / 2) = 5`, which equals `makerSellRemainQuantity = 5` → enters the "taker == maker" branch.
- `makerBuyTokenQuantityReceive = floor(5 * 2 / 11) = floor(10/11) = 0`.
- The maker's remaining 5 units of sell token are transferred entirely to the taker (`takerBuyTokenQuantityReceive = 5`), while the maker's order is set to `0` remain and credited with `0` buy tokens.

The attacker (as taker) has effectively taken 5 units of the maker's asset for 1 unit of payment that produces zero credit to the maker, resulting in a real, uncompensated loss for the maker.

### Impact Explanation
This is a direct theft-of-funds bug reachable by any unprivileged account that can place a `MarketSellAssetContract` transaction (`MarketSellAssetActuator`). A victim maker's resting order in the on-chain order book can be drained for free by a carefully-sized taker order, permanently transferring the maker's remaining balance to the attacker without compensation. This meets the bar for concrete unauthorized theft of funds via a single signed transaction.

### Likelihood Explanation
Exploitability requires the attacker to find or wait for a maker order whose `sellTokenQuantityRemain` falls into a vulnerable ratio window relative to `makerSellQuantity`/`makerBuyQuantity` (achievable by partial fills that naturally reduce `sellTokenQuantityRemain` over time, or by the attacker's own prior partial fill of the victim's order to engineer the remain value), then submitting a taker order with the specific `sellTokenQuantityRemain` that satisfies the exact-equality condition. This is deterministic arithmetic that an attacker can compute off-chain in advance, making the attack practical and repeatable, especially for markets with resting orders that have small remaining balances after multiple partial fills.

### Recommendation
Add the same zero-value guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive` computed via `MarketUtils.multiplyAndDivide` is `0`, refund the maker's remaining sell tokens via `MarketUtils.returnSellTokenRemain` (as already done at `MarketSellAssetActuator.java:475-477`) instead of unconditionally zeroing the maker's order and crediting it with nothing.

### Proof of Concept
1. Create a market sell order (maker) with `sellTokenQuantity = 11`, `buyTokenQuantity = 2` for a token pair.
2. Arrange (via a prior small partial fill, or directly if creating the order with these exact remain values) for `sellTokenQuantityRemain = 5` on this maker order.
3. Submit a taker `MarketSellAssetContract` order on the opposite side of the pair with `sellTokenQuantity = 1` (matching quantity such that `takerSellRemainQuantity = 1`).
4. Observe in `matchSingleOrder` (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:402-439`) that `takerBuyTokenQuantityRemain = floor(1*11/2) = 5 == makerSellRemainQuantity`, entering the "taker == maker" branch.
5. Observe `makerBuyTokenQuantityReceive = floor(5*2/11) = 0`, `makerOrderCapsule.setSellTokenQuantityRemain(0)`, and `addTrxOrToken(makerOrderCapsule, 0)` — the maker's remaining 5 units of sell token are fully consumed and transferred to the taker via `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()`, while the maker receives `0` in return.
