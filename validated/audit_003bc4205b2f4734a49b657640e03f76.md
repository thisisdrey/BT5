### Title
Reference counter leak on partial `OperationService` write-hook failure permanently blocks repository moves - (File: internal/gitaly/hook/updateref/update_with_hooks.go)

### Summary
`UpdaterWithHooks.UpdateReference` is used by most `OperationService` RPCs (`UserCreateBranch`, `UserMergeBranch`, `UserCommitFiles`, `UserCreateTag`, etc.) to apply a single reference update with hooks. It increments GitLab's per-repository push-in-progress reference counter via the pre-receive hook before doing any of the actual ref update work, but only decrements it via the post-receive hook at the very end of a fully successful call. Any error on the path between those two points causes the counter to leak, exactly mirroring the reported bug class where a mandatory "release" step (owner fee transfer completing a withdrawal) can be skipped by an earlier revert, permanently denying legitimate users a resource — here, the ability to have the repository considered idle.

### Finding Description
`PreReceiveHook`/`preReceiveHook` calls `gitlabClient.PreReceive`, which increments GitLab's reference counter that tracks active pushes for the repository [1](#0-0) . `PostReceiveHook`/`postReceiveHook` calls `gitlabClient.PostReceive`, decrementing the same counter [5](#0-4) . The documentation explicitly states this counter is used by GitLab to know "when a certain repository can be moved. If the reference counter is not at 0, there are active pushes happening" [6](#0-5) .

`UpdaterWithHooks.UpdateReference` calls `PreReceiveHook` first (line 224), and only calls `PostReceiveHook` as the very last step (line 309) if every intermediate step succeeds [7](#0-6) . Every intermediate failure path — `quarantineDir.Migrate` (line 233), `UpdateHook` (line 246), the "preparing"/"prepared"/"committed" reference-transaction hook calls (lines 277, 292, 305), and critically `updater.Prepare()`/`updater.Commit()` (lines 283, 296) — returns an error directly without ever invoking `PostReceiveHook`, so the counter increment from `PreReceiveHook` is never undone.

Unlike the raw `git-receive-pack` path (where Git always executes `post-receive` once pre-receive succeeds, regardless of individual per-ref update outcomes, per `doc/hooks.md`), the `OperationService` path implemented in `update_with_hooks.go` has no `defer`/cleanup that guarantees the counter is released on early return. `updater.Prepare()`/`updater.Commit()` failing is a completely ordinary, unprivileged occurrence: it happens whenever the reference's current value no longer matches the expected `oldrev` (e.g., a concurrent write from another ordinary user, or the caller supplying a stale `oldrev`), causing a `CAS`-style lock/verify failure in `git-update-ref`.

### Impact Explanation
Each such failure leaks one increment of the repository's push-activity counter. Because GitLab gates repository storage moves on this counter reaching zero, repeated triggering (which requires no privilege — merely losing a race on a ref update, or any transient failure in the update/reference-transaction hook phases) can push the counter arbitrarily far from zero, permanently preventing GitLab from ever considering the repository idle enough to move. This is a resource-exhaustion / persistent-state corruption issue impacting repository storage management availability, not data loss, but it denies an intended operational capability indefinitely without any way to reset the counter through user action.

### Likelihood Explanation
Likelihood is fairly high for the concurrency-driven trigger: any two ordinary users (or automated processes) racing to update the same reference through `OperationService` RPCs can cause `updater.Prepare()` or `updater.Commit()` to fail after `PreReceiveHook` already incremented the counter. No administrator/custom-hook cooperation or malicious token/dependency is required — this is reachable purely from concurrent, otherwise-legitimate write RPCs.

### Recommendation
Ensure the post-receive counter decrement (or an equivalent explicit "release" call to `gitlabClient.PostReceive`/a dedicated cleanup RPC) is executed via `defer` immediately after `PreReceiveHook` succeeds in `UpdateReference`, so that the counter is always balanced regardless of where the function returns afterward, mirroring how `updater.Close()` is deferred right after acquisition at line 267.

### Proof of Concept
1. Set up transactions/OperationService normally (e.g., call `UserCommitFiles` or `UserMergeBranch` against a branch).
2. Concurrently issue two `OperationService` write RPCs against the same target reference with the same `oldrev`, from two ordinary user sessions, so that one commits first.
3. The first call proceeds through `PreReceiveHook` (counter incremented via `gitlabClient.PreReceive`), then successfully completes `updater.Commit()` and `PostReceiveHook` (counter decremented) — balanced.
4. The second call also passes `PreReceiveHook` (counter incremented again) before hitting the ref update, then fails at `updater.Prepare()` or `updater.Commit()` in `internal/gitaly/hook/updateref/update_with_hooks.go` lines 283–303 because the reference's actual old value no longer matches its expected `oldrev` — the function returns an `Error{...}` immediately, and `PostReceiveHook` (and thus the decrement call) is never reached.
5. Repeating step 2–4 accumulates a positive, never-decremented counter value on GitLab's side for that repository, which per `doc/hooks.md` lines 229–231 is used to determine "if the reference counter is not at 0, there are active pushes happening," permanently blocking a legitimate repository move for that project.
