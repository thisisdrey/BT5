### Title
StackerDB chunk signatures omit the target contract identifier, enabling cross-StackerDB replay of authenticated writes - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` — the digest that a StackerDB signer actually signs — commits only to `slot_id`, `slot_version`, and `data_hash`. It never includes the StackerDB's smart-contract identifier (the "context" that determines which slot-ownership table the write is validated against). This is structurally the same class of bug as H-29: a piece of context that determines how a signed payload should be validated/routed (there: `nlrType`; here: the target `QualifiedContractIdentifier`/`stackerdb_id`) is left out of the signed data, so if that context "overlaps" between two instances (here: the same signer address is assigned the same `slot_id` in two different StackerDB contracts), a message signed and accepted for one context can be replayed into the other.

### Finding Description
`SlotMetadata::auth_digest` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify`/`StackerDBChunkData::verify` recover the public key from this digest and compare its `Hash160` to an address supplied by the caller — but the digest itself carries no information about which contract that address was authorized for: [2](#0-1) 

The contract binding is only enforced *outside* the signature, by looking up the expected signer per-contract via `get_slot_signer(smart_contract_id, slot_id)` and comparing recovered pubkey-hash to that address: [3](#0-2) 

Because `smart_contract_id` is not part of what was signed, the check reduces to: "is this signature valid for *some* (slot_id, slot_version, data_hash) triple, and does the recovered address happen to be the assigned signer for slot_id in *this* contract?" If the same signer address is assigned the same `slot_id` in two different StackerDB contracts (a common situation, since signer/miner slot assignments are frequently rotated deterministically across reward cycles and StackerDB contracts, e.g. `.miners` vs per-cycle signer-message DBs), a signed chunk broadcast for contract A can be replayed verbatim against contract B, and it will pass `slot_metadata.verify(&addr)` because the signature check is identical — the contract identity is never part of the equality being checked cryptographically.

The storage layer does key chunks by `stackerdb_id` (derived from the contract), so the write lands in the "wrong" DB's slot rather than corrupting the source DB, but this is purely a database bookkeeping detail — the signer never authorized that chunk to be written into contract B's namespace: [4](#0-3) 

This mirrors the report's root cause precisely: the routing/validation-determining field (`nlrType` there, target-contract there for us) is excluded from the signed payload, so cross-context confusion becomes possible whenever the unsigned discriminator overlaps between two valid, independently-authorized contexts.

### Impact Explanation
This allows an unauthenticated/unauthorized write to a StackerDB slot: an attacker who observes a validly-signed chunk broadcast for StackerDB contract A can re-submit (via `POST /v2/stackerdb/.../chunks` or via p2p push) that exact same signed chunk against StackerDB contract B, and it will be accepted as if signer had authorized a write there, as long as the (slot_id, address) pairing coincides across A and B and B's expected version allows it. This is a "write to state that was never authorized by the signer for that context," matching the Critical-impact "unauthenticated/unauthorized write to StackerDB" and "network-wide propagation of forged data" categories.

### Likelihood Explanation
Exploitation requires: (1) capturing a legitimately-signed chunk (trivial, since these are broadcast/replicated in plaintext over the p2p StackerDB sync protocol and are also readable via the RPC get-chunk endpoint), and (2) a coincidence (or attacker-induced situation) where the signer's address holds the same `slot_id` in two different StackerDB contracts with compatible version state. Slot assignments are often derived deterministically (e.g., same reward-cycle signer set index used across the `.miners` contract and signer-message contracts), so this precondition is plausible rather than purely theoretical, though it is not guaranteed in every deployment and depends on specific slot-assignment configuration.

### Recommendation
Include the target StackerDB's contract identifier (or its internal `stackerdb_id`) in the signed digest, e.g. modify `SlotMetadata::auth_digest` to hash `smart_contract_id.to_string()` (or a canonical serialization of the `QualifiedContractIdentifier`) in addition to `slot_id`, `slot_version`, and `data_hash`. This requires plumbing the contract identifier into `SlotMetadata`/`StackerDBChunkData` signing and verification paths (`libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/mod.rs`, `stackslib/src/net/stackerdb/db.rs`) so that a signature is cryptographically bound to exactly one StackerDB instance and cannot be replayed into another.

### Proof of Concept
1. Configure two StackerDB contracts, A and B, such that signer key `K` (address `addr_K`) is registered as the authorized signer for `slot_id = 0` in both A and B (a realistic configuration given deterministic slot assignment across reward cycles/contracts).
2. `K` signs and pushes a chunk `StackerDBChunkData { slot_id: 0, slot_version: 1, data: D }` for contract A (`chunk.sign(&K)` per `StackerDBChunkData::sign`, `libstackerdb/src/libstackerdb.rs:226-231`); the node stores it as version 1 in A.
3. An attacker observes this chunk on the wire (via p2p relay or `GET` chunk RPC) and resubmits the identical `StackerDBChunkData` (same `slot_id`, `slot_version`, `sig`, `data`) but targeted at contract B's endpoint/message.
4. `validate_received_chunk` for contract B looks up `get_slot_signer(B, 0)` → `addr_K`, calls `data.get_slot_metadata().verify(&addr_K)`, which recovers the same public key from the same `auth_digest` (unchanged since it never included the contract id) and succeeds — the chunk is accepted into B's slot 0 version 1, even though `K` never signed anything authorizing a write to contract B.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
