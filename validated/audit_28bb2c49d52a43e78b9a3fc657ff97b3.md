### Title
Uncaught `ArithmeticException` in `MarketSellAssetActuator` order matching crashes transaction/block processing - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` performs order-book matching (`matchOrder` → `matchSingleOrder`) that calls `MarketUtils.multiplyAndDivide(...)`, a helper that (per its sibling usages) can throw `ArithmeticException` on overflow/zero-division during price ratio computation. Unlike `ExchangeInjectActuator` and `ExchangeTransactionActuator`, which explicitly declare `validate()`/`execute()` to catch `ArithmeticException` and convert it into a `ContractValidateException`/`ContractExeException`, `MarketSellAssetActuator.execute()` only catches `ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException` [1](#0-0) . This asymmetry means a crafted `MarketSellAssetContract` that triggers arithmetic overflow/underflow in `matchSingleOrder`'s price computation raises an unchecked `ArithmeticException` that is not handled by this actuator at all.

### Finding Description
`MarketSellAssetActuator.matchSingleOrder` computes cross-rates between a taker's incoming sell order and resting maker orders using `MarketUtils.multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity, this.disableJavaLangMath())` [2](#0-1) , and again later for the maker-consumed branch [3](#0-2) . `MarketUtils.multiplyAndDivide` (chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java) performs the multiply/divide arithmetic that other actuators guard against by catching `ArithmeticException` — see `ExchangeInjectActuator.validate()`/`.execute()` which explicitly wrap the logic in `try { return doValidate(); } catch (ArithmeticException e) { throw new ContractValidateException(...); }` and catch `ArithmeticException` in `execute()`'s catch list [4](#0-3) , and identically in `ExchangeTransactionActuator` [5](#0-4) .

`MarketSellAssetActuator.execute()`, however, only declares:
```
catch (ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException e)
``` [1](#0-0) 
There is no equivalent `ArithmeticException` guard around `matchOrder`/`matchSingleOrder`, despite the same class of arithmetic (`multiplyAndDivide`, `addExact`/`subtractExact`) being used in matching. `MarketSellAssetContract.sellTokenQuantity`/`buyTokenQuantity` are only checked to be `> 0` in `validate()` [6](#0-5)  — there is no upper bound. Because a TRC10 asset issuer can set an asset's total supply arbitrarily large (up to `Long.MAX_VALUE`) via `AssetIssueContract`, and asset balances used as `sellTokenQuantity`/existing resting maker order quantities can be correspondingly large, the multiplication step in `multiplyAndDivide` can overflow, triggering `Math.multiplyExact`'s documented `ArithmeticException` (assuming, consistent with `addExact`/`subtractExact`'s use elsewhere in this same file, that "exact" arithmetic helpers are used to detect overflow).

Because this exception type is not caught, it propagates out of `execute()` as an unchecked `RuntimeException`, out of `RuntimeImpl.execute()` [7](#0-6) , out of `TransactionTrace.exec()`, and into `Manager.processTransaction()` [8](#0-7) . During block application this method is called per-transaction inside `processBlock()`'s for-loop with no per-transaction try/catch [9](#0-8) , so the uncaught exception aborts `processBlock`/`applyBlock` entirely. `Manager.pushBlock()`'s block-application try/catch only catches `Throwable` generically to roll back and rethrow [10](#0-9) ; downstream, `TronNetDelegate.processBlock()` only catches a fixed, exhaustive list of specific checked blockchain exceptions and does not catch generic `RuntimeException`/`ArithmeticException` [11](#0-10) , so the exception is not gracefully absorbed at this layer either.

### Impact Explanation
An `ArithmeticException` thrown mid-`matchSingleOrder` occurs after order state has already been partially mutated (balances debited, sell orders created/removed from the order book in earlier steps of `execute()`), so if the exception is caught at a higher, generic layer instead of `ContractExeException`, the transaction's DB session may not be cleanly rolled back the way a properly-typed `ContractExeException` would be, and repeated occurrence of this condition during block validation could cause nodes to diverge in how they process/reject the offending block (some paths catch `Exception` generically and continue, e.g. `BlockMsgHandler.processBlock`'s outer catch [12](#0-11) , while the direct `Manager.pushBlock`/`applyBlock` call path does not have this generic net). This creates inconsistent handling of a malicious transaction across code paths (self-generation vs. sync vs. broadcast), which is the kind of DoS/crash inconsistency the CVE analog targets: an unhandled runtime fault triggered by crafted (here: overflow-inducing) transaction data disrupts normal transaction/block processing.

### Likelihood Explanation
Reaching this requires: (1) issuing a TRC10 asset with an extremely large total supply (`AssetIssueContract`, permitted by any account with sufficient balance for the issuance fee), (2) placing existing sell orders using very large quantities of that asset, and (3) submitting a `MarketSellAssetContract` designed so the taker/maker cross-multiplication in `multiplyAndDivide` overflows `long`. All of these are actions available to an unprivileged asset issuer / order placer as explicitly listed in-scope in the prompt. I was not able to directly view `MarketUtils.multiplyAndDivide`'s implementation body in the search results to confirm definitively that it uses an overflow-checking exact-multiply (vs. `Math.multiplyHigh`/unchecked multiply with silent wraparound); this is the main uncertainty in this finding. The surrounding code in the same actuator does use `addExact`/`subtractExact`/`multiplyExact` (imported statically, e.g. `floorDiv(multiplyExact(...))` in `ExchangeInjectActuator`), which is a strong signal the codebase consistently uses overflow-checked long arithmetic in this area, but I could not fetch the exact `MarketUtils.multiplyAndDivide` source in the remaining budget.

### Recommendation
Wrap the order-matching logic in `MarketSellAssetActuator.execute()` (and `validate()`, if it calls similar arithmetic helpers) in a try/catch for `ArithmeticException`, mirroring `ExchangeInjectActuator` and `ExchangeTransactionActuator`, converting it into a `ContractExeException`/`ContractValidateException` so it is handled the same as other actuator failure modes rather than propagating as an unchecked `RuntimeException`. Additionally, add explicit upper-bound sanity checks on `sellTokenQuantity`/`buyTokenQuantity` (and on total asset supply used in market orders) to make overflow unreachable rather than relying solely on exception handling.

### Proof of Concept
1. Issue a TRC10 asset (`AssetIssueContract`) with total supply near `Long.MAX_VALUE`.
2. Using two colluding or unrelated accounts holding large balances of this asset, place a resting maker `MarketSellAssetContract` order pairing this asset against another token/TRX with quantities chosen so that `makerSellQuantity * takerSellRemainQuantity` (as computed in `matchSingleOrder`, `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:402-404`) exceeds `Long.MAX_VALUE` when multiplied.
3. Submit a taker `MarketSellAssetContract` transaction that matches against this maker order, triggering `matchOrder`/`matchSingleOrder`.
4. Observe that `MarketUtils.multiplyAndDivide` throws `ArithmeticException`, which is not caught by `MarketSellAssetActuator.execute()`'s catch clause (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:152-159`), propagating as an unchecked exception through transaction execution.

Note: I was unable to directly confirm the internal implementation of `MarketUtils.multiplyAndDivide` (only its usage sites) within the available tool budget; a Devin session with full repository access should verify the exact overflow behavior of this method before treating this as fully confirmed.
