### Title
Unchecked `u64` multiplication of attacker-controlled `estimated_len` causes overflow panic/wrap in fee estimation - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` takes `estimated_len` directly from the client-supplied JSON body (`FeeRateEstimateRequestBody.estimated_len: Option<u64>`) with no upper bound, then `estimate_tx_fee_from_cost_and_length` computes `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` without any checked/saturating arithmetic. A single POST to `/v2/fees/transaction` with a tiny valid `transaction_payload` and a huge `estimated_len` triggers this unchecked multiplication.

### Finding Description
In `try_parse_request` [1](#0-0) , the only length gate applied is on the raw HTTP body size: `content_len > 0 && content_len < MAX_PAYLOAD_LEN` [2](#0-1) . This limits the size of the JSON text itself, but does not bound the numeric *value* of the `estimated_len` field inside that JSON — a short JSON body can easily encode `"estimated_len": 18446744073709551615` (u64::MAX). The handler then computes:

```
let estimated_len = std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64);
``` [3](#0-2) 

Since `body.estimated_len` can be arbitrarily large and `payload_data.len()` is small (from a tiny valid `transaction_payload`), `std::cmp::max` simply passes through the attacker's huge value unchanged.

This `estimated_len` is stored and later passed unmodified in `try_handle_request` to `Self::estimate_tx_fee_from_cost_and_length` [4](#0-3) , which performs:

```
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
``` [5](#0-4) 

This is a plain `*` operator with no `checked_mul`/`saturating_mul`. With `estimated_len` near `u64::MAX` and `MINIMUM_TX_FEE_RATE_PER_BYTE` being a nonzero constant defined in `stackslib/src/chainstate/stacks/db/blocks.rs`, the product overflows `u64`. In a debug/overflow-checked build this panics (arithmetic overflow), taking down the RPC-handling thread/node; in a release build it silently wraps to an incorrect (small/wrong) `minimum_fee` value returned as authoritative in the JSON response.

No authentication or RPC secret gates this endpoint (`/v2/fees/transaction` is a standard public read-style RPC endpoint), and no `TransactionPayload` cost/size caps intervene before the multiplication because `estimated_len` is decoupled from the actual decoded transaction size.

### Impact Explanation
A single crafted, unauthenticated POST to `/v2/fees/transaction` can crash a node's RPC handling path (panic) on any build compiled with overflow checks (Rust debug profile, or any deployment that enables `overflow-checks = true`), which is a remote unauthenticated DoS from one message. On non-overflow-checked (default release) builds, the wrapped `minimum_fee` silently corrupts the fee-estimate response, which downstream fee-estimate consumers (wallets, tooling) could treat as authoritative, leading to incorrect fee assessments. This matches the "Critical — remote crash/unauthenticated DoS from few messages" category for the panic case.

### Likelihood Explanation
The attacker needs only network reachability to the node's RPC port and no privileges, secrets, or special peer/tip state — a single POST body with a small valid hex-encoded `TransactionPayload` and `estimated_len` set near `u64::MAX` is sufficient and fully repeatable. The only precondition is that the node has fee/cost estimators configured (`rpc_args.get_estimators_ref()` returns `Some`), which is a common node configuration, not a security control.

### Recommendation
Bound `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or the maximum allowed transaction size) in `try_parse_request`, rejecting values above that cap, and/or replace the raw multiplication in `estimate_tx_fee_from_cost_and_length` with `estimated_len.saturating_mul(MINIMUM_TX_FEE_RATE_PER_BYTE)` (or `checked_mul` with an explicit error response) to eliminate the overflow/wrap regardless of input.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs` that:
1. Constructs a `FeeRateEstimateRequestBody { estimated_len: Some(u64::MAX), transaction_payload: <hex of a minimal valid TransactionPayload, e.g. a short Coinbase/TokenTransfer payload> }`.
2. Serializes it to JSON, builds an `HttpRequestPreamble` with `Content-Length` under `MAX_PAYLOAD_LEN` and `Content-Type: application/json`.
3. Calls `RPCPostFeeRateRequestHandler::try_parse_request` (succeeds, sets `self.estimated_len = Some(u64::MAX)`), then calls `try_handle_request` with a `StacksNodeState` configured with mock cost/fee estimators.
4. Asserts that under `#[should_panic(expected = "attempt to multiply with overflow")]` (debug/overflow-checked run) the call panics at `stackslib/src/net/api/postfeerate.rs:112`, or, in a release-mode run, asserts the returned `RPCFeeEstimateResponse.estimations[..].fee` values do not match the mathematically true (unbounded) product of `u64::MAX * MINIMUM_TX_FEE_RATE_PER_BYTE`, demonstrating silent wraparound.
