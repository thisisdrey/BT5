### Title
Cross-lane StackerDB chunk replay defeats signer message-type binding via `SlotMetadata` signature scope - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` binds a StackerDB chunk signature only to `(slot_id, slot_version, data_hash)`. It does **not** bind the signature to the StackerDB contract (`smart_contract_id`) the chunk is destined for. Because the `.signers-<set>-<message_id>` contracts (e.g. `BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) share the *same* slot-to-signer-address allocation for a given signer set/reward cycle [1](#0-0) , a validly-signed chunk captured on one "lane" contract can be replayed unmodified onto a different lane contract at the same slot_id, and the receiving node's signature check will still succeed, because it only asks "does this address own slot X in *this* contract" without checking that the chunk was ever intended for this contract.

### Finding Description
The signable digest for a chunk is:
```
auth_digest = SHA512/256(slot_id || slot_version || data_hash)
``` [2](#0-1) 

`verify()` only recovers the public key from this digest and checks it against the expected principal for the given slot — the contract identifier plays no role in the signed material [3](#0-2) .

Server-side validation (`validate_received_chunk` and the `poststackerdbchunk` RPC handler) fetches the expected signer via `get_slot_signer(smart_contract_id, slot_id)` and then calls `slot_metadata.verify(&addr)` [4](#0-3) . This correctly checks "is this signature valid for the owner of slot X in contract C", but the signature itself does not encode C, so the *same bytes* verify equally well against any other contract C' where the same address owns the same slot_id.

Critically, the four `.signers-<set>-{1,2,3}` (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`) contracts for a given reward cycle draw their slot list from the identical `stackerdb-signer-slots-<set>` page in the `.signers` boot contract [1](#0-0) , confirmed by the test iterating `signer_set` × `message_id` and asserting the exact same slot list for every message_id [5](#0-4) . So the mapping (slot_id → signer address) is identical across all lanes for a given signer set.

This means an unprivileged network observer who captures a legitimately signed `StackerDBChunkData` (slot_id, slot_version, sig, data) posted by a signer to one lane (e.g. `BlockResponse`) can re-POST the identical bytes to a different lane contract for the same signer_set/reward cycle (e.g. `StateMachineUpdate` or `BlockPreCommit`) at the same slot_id. Since:
- the signature still verifies (same address owns that slot in the target contract),
- the freshness check (`slot_version` vs. `expected_version`) is per-contract and independently tracked, so an unused version number in the target lane will pass,

the forged/misplaced chunk gets accepted and stored on the target lane.

`stackerdb_listener.rs` deserializes chunk bytes directly as `SignerMessageV0` per the contract it read from (`StateMachineUpdate` lane expects `StateMachineUpdate` payload) [6](#0-5) ; a `BlockResponse` payload injected into the `StateMachineUpdate` lane would simply fail to parse as the expected type and be silently ignored there. However, note that `libsigner/src/events.rs` independently implements `signer_message_payload_matches_lane`, which explicitly checks that the payload's `SignerMessageTypePrefix` matches the lane's expected `MessageSlotID` before accepting an event [7](#0-6)  — this is a **type-prefix** check at the event-consumption layer, not a signature-scope fix. It mitigates outright type confusion for consumers that go through this path, but it does not prevent the chunk from being *written and stored* on the wrong lane's StackerDB (an unauthorized write to a peer's on-disk StackerDB replica state, corrupting/occupying that lane's slot and version counter, and propagating over the p2p StackerDB gossip/relay to other nodes as legitimate-looking, correctly-"signed" data for that lane).

### Impact Explanation
This is a capture-and-replay authentication-bypass analog to CVE-2022-22936: the attacker needs no private key, only the ability to observe one broadcast/GET chunk and re-POST it to a sibling StackerDB endpoint. The impact is an **unauthenticated/unauthorized write into another StackerDB lane's state** (consuming/advancing a slot's version counter in a database it was never intended for) and **network-wide propagation of forged/misplaced data** via StackerDB replication once a peer accepts and re-gossips the chunk (`handle_unsolicited_StackerDBPushChunk` / inventory-driven sync accept any chunk whose signature verifies for that (contract, slot) pair, with no cross-contract binding) [8](#0-7) . This matches the "Critical" bucket ("unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data") in the rules.

### Likelihood Explanation
StackerDB chunks are broadcast/readable without authentication (any node can `list_chunks`/`get_chunks` over the read RPC) [9](#0-8) , so capturing a legitimate chunk requires no special access. Replaying it to a sibling `.signers-<set>-<other_message_id>` contract only requires knowing the mapping (which is public, queryable via `stackerdb-get-signer-slots-page`) and issuing a normal `put_chunk` POST — the same mechanism any signer uses. No secret key or privileged role is required, satisfying the "remote, unprivileged" scope constraint.

### Recommendation
Bind the StackerDB chunk signature to the destination `smart_contract_id` (or an equivalent lane/message-type identifier) by including it in `SlotMetadata::auth_digest()`, e.g.:
```
hasher.update(contract_id.serialize());
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```
This requires plumbing the contract identifier through `sign()`/`verify()`/`recover_pk()` in `libstackerdb/src/libstackerdb.rs`, and updating all call sites in `stackslib/src/net/stackerdb/`, `stackslib/src/net/api/poststackerdbchunk.rs`, `libsigner`, and `stacks-signer` that sign or verify chunks. This is a wire-incompatible change and would need a protocol version bump / coordinated rollout.

### Proof of Concept
1. Observe (via unauthenticated `GET /v2/stackerdb/<contract>/<slot>/<version>` or p2p StackerDB chunk gossip) a validly signed `StackerDBChunkData { slot_id: 3, slot_version: 5, sig, data }` posted by signer S to `.signers-1-1` (BlockResponse lane).
2. Compute or reuse the same `(slot_id=3, slot_version, sig, data)` tuple.
3. POST this identical chunk to `.signers-1-2` (StateMachineUpdate lane) or `.signers-1-3` (BlockPreCommit lane) for the same reward cycle/signer set, where slot 3 is also owned by S and the target lane hasn't yet stored a version ≥ 5 for slot 3.
4. `poststackerdbchunk`/`validate_received_chunk` on the receiving node calls `get_slot_signer(target_contract, 3)` → returns S's address, then `slot_metadata.verify(S_addr)` succeeds because the digest never encoded which contract it was for. The chunk is accepted and stored in the wrong lane's StackerDB, and propagated to peers as legitimate.

Note: I could not fully trace every consumer of each `.signers-<set>-<message_id>` StackerDB (e.g., whether every consumer beyond `stackerdb_listener.rs` applies the `signer_message_payload_matches_lane` guard from `libsigner/src/events.rs`) due to time constraints on this final pass; a full audit of all downstream readers of these StackerDB contracts would be needed to fully bound the blast radius of the misplaced/forged data.

/// Whether a `SignerMessage` payload type is the one expected for the given contract message id.
///
/// `lane_message_id` is the trailing number in the `signers-X-{lane_message_id}` boot
/// contract. Each signer-message contract is dedicated to exactly one `SignerMessage`
/// variant, so the payload's type-prefix byte must map to the same numeric `MessageSlotID`.
///
/// Miner-only payloads (`BlockProposal`, `BlockPushed`, `MockProposal`, `MockBlock`) are not
/// written to a signer contract and never match.
fn signer_message_payload_matches_lane(
    payload_kind: SignerMessageTypePrefix,
    lane_message_id: u32,
) -> bool {
    payload_kind
        .msg_id()
        .is_some_and(|slot| slot.to_u32() == lane_message_id)
}
```
