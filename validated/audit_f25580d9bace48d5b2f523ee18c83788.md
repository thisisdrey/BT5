Audit Report

## Title
ERC20 XCM Asset Transactor credits the nominal transfer amount instead of the actual ERC20 balance delta, permanently locking funds for fee-on-transfer/deflationary tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke the target contract's `transfer()` and, upon a `true` boolean return, unconditionally record/consume the nominal `amount` taken from the XCM `Asset` spec into `AssetsInHolding` via `Erc20Credit`, without ever reading the ERC20 contract's `balanceOf` before/after the call. Any unprivileged user can deploy an arbitrary contract via `pallet_revive` and reference it as an XCM asset through an `AccountKey20` location, matched unconditionally by `ERC20Matcher`, so a fee-on-transfer/deflationary token can desync the runtime's internal accounting from the real balance held by `ERC20TransfersCheckingAccount`, leading to permanently stuck funds.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` to move `amount` from the user to the checking account, and on success constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the nominal `amount`, not a measured balance delta. [1](#0-0) 
`deposit_asset_with_surplus` symmetrically transfers `amount` out of the checking account to the beneficiary and trusts the boolean return value from `transferCall` alone. [2](#0-1) 
`Erc20Credit` is a bare accounting wrapper whose documentation explicitly states that "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime," confirming there is no reconciliation against real contract state. [3](#0-2) 
The asset id matching that gates which contracts can be used is `ERC20Matcher`, which matches any local `AccountKey20` location without any allow-list, registry, or contract-code verification — any contract address qualifies. [4](#0-3) 
This transactor is wired into asset-hub-westend's `AssetTransactors` and reachable from user-submitted XCM programs (e.g., via `pallet_xcm::execute`). [5](#0-4) 
The runtime's own test demonstrates the exact call path: deploying a fresh contract via `pallet_revive` and referencing its address directly in a `withdraw_asset`/`deposit_asset` XCM program executed by an ordinary signed account. [6](#0-5) 
None of the existing guards (`matches_fungibles`, `did_revert()`, boolean-return decode) verify the actual token balance moved; they only validate location shape and the contract's self-reported boolean result.

## Impact Explanation
This is a permanent user-fund lock: a fee-on-transfer/deflationary ERC20 contract causes `TransfersCheckingAccount`'s real balance to increase by less than the `amount` credited into `AssetsInHolding` as an `Erc20Credit`. When that credit is later deposited (to a beneficiary or via a trap/refund path) for the recorded `amount`, the checking account's real balance is insufficient, causing `deposit_asset_with_surplus`'s `transferCall` to fail (`Ok(false)`) — the underlying withdrawal already executed irreversibly, so the value is permanently stranded in the checking account with no reconciliation mechanism. This matches the "permanent user-fund lock" impact class.

## Likelihood Explanation
Fully unprivileged and repeatable: an attacker deploys an ordinary Solidity contract through `pallet_revive::Pallet::bare_instantiate` (permissionless) and submits a self-authored XCM program via `pallet_xcm::execute` referencing the contract as an `AccountKey20` asset, exactly as the existing runtime test harness does. No governance, relayer, or validator involvement is required, and `ERC20Matcher` places no restriction on which contract addresses are usable as asset ids.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query `balanceOf` for the relevant account before and after the `transferCall`, and use the observed delta — not the nominal `amount` — when constructing/consuming `Erc20Credit`. If the delta differs from the requested amount, fail with `XcmError::FailedToTransactAsset` rather than crediting/debiting the nominal amount.

## Proof of Concept
1. Deploy a fee-on-transfer ERC20 contract (`transfer()` moves `amount - fee` but returns `true`) via `pallet_revive::Pallet::bare_instantiate`, following the pattern in `withdraw_and_deposit_erc20s`. [7](#0-6) 
2. Submit `pallet_xcm::execute` with `WithdrawAsset` for this token (as `AccountKey20`) for `amount`, then `DepositAsset` to a beneficiary, mirroring the existing test's XCM shape. [8](#0-7) 
3. Observe `withdraw_asset_with_surplus` credits `Erc20Credit(amount)` while the checking account's real ERC20 balance only rose by `amount - fee`. [9](#0-8) 
4. On the subsequent `deposit_asset_with_surplus` call for the full `amount`, the checking-account `transferCall` returns `false` due to insufficient real balance, producing a stranded/erroring credit while the withdrawn value remains locked in the checking account. [10](#0-9)

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
