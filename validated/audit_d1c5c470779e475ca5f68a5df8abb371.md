### Title
Unauthenticated RecvError packet allows remote attacker to force-close an established tunnel - (File: outside.go)

### Summary
`Interface.readOutsidePackets` dispatches `header.RecvError` packets to `handleRecvError` before any cryptographic authentication (no cert/handshake state check), trusting an attacker-supplied `RemoteIndex` field to look up and tear down a victim's live `HostInfo`/tunnel. This mirrors the `DcntEth::setRouter` bug class: a security-relevant state transition (closing/rebuilding a trusted tunnel) is triggered by data from an unauthenticated party, with the only mitigating check being a UDP source-address comparison that is not cryptographically bound to anything.

### Finding Description
In `readOutsidePackets`, the switch on `h.Type` in the "Unencrypted packets" section handles `header.RecvError` immediately after `h.Parse(packet)` and basic header sanity checks (`h.Version`, `h.IsValidSubType()`), with no requirement that the sender hold a valid CA-signed certificate or have completed a handshake: [1](#0-0) 

This routes to `handleRecvError`, which looks up a `HostInfo` purely from the attacker-controlled `h.RemoteIndex` field via `f.hostMap.QueryReverseIndex(h.RemoteIndex)`, and if found, compares the packet's source address to the currently known remote of that tunnel; if they match (or if no remote is yet set), it calls `f.closeTunnel(hostinfo)` and also deletes pending handshake state: [2](#0-1) 

The only defense is `f.acceptRecvErrorConfig.ShouldRecvError(addr)` (a rate/config gate, not an authentication mechanism) and the `hr != addr` address check. Neither of these validates that the packet actually originated from the genuine authenticated peer — the address check is defeated by any attacker able to spoof the victim's current UDP source address (or by attacking before the tunnel has an established remote, where `hr.IsValid()` is false and the check is skipped entirely).

Just as `DcntEth::setRouter` let anyone reassign a trust anchor (`router`) that gated `mint`/`burn`, this path lets anyone claiming a matching `RemoteIndex`/source address force a mutation of trusted session state (tunnel teardown) without ever presenting a valid certificate or completing the Noise handshake.

### Impact Explanation
An attacker who can send a single UDP packet with a guessed/observed 32-bit local index and a spoofed or path-observed source address can:
- Force `closeTunnel` on an established, authenticated tunnel between two legitimate mesh nodes, causing denial of service and forcing renegotiation.
- Also purge pending handshake state via `f.handshakeManager.DeleteHostInfo(hostinfo)`, disrupting in-progress connection setup.

This is reachable entirely pre-authentication (no CA pool verification, no completed Noise handshake) and directly analogous to the reported issue's core flaw: a caller with no proof of authorization can mutate trusted routing/session state that other, authenticated code paths rely on.

### Likelihood Explanation
Exploitation requires the attacker to know (or brute-force within the 32-bit index space) a victim's current `localIndexId` and to be able to place a packet with a source address matching the victim's currently known remote (trivial for an on-path/off-path attacker able to spoof UDP source addresses, or straightforward if the victim's public UDP endpoint is otherwise known/observed). No cryptographic material or CA-issued certificate is required, which is a materially lower bar than for any legitimate peer operation. Likelihood is assessed as moderate: it requires index guessing/observation and possibly source spoofing, but neither requires holding a valid Nebula certificate.

### Recommendation
Do not act on `RecvError` (or any similarly unauthenticated control message) using only a source-IP-address match. Bind acceptance of `RecvError` to an authenticated property of the session — e.g., require the packet to be authenticated with a MAC/keyed value derived from a value shared only with the legitimate peer of that specific `HostInfo` (e.g., include the session's ephemeral key/index pair signed or MAC'd rather than trusting the plaintext `RemoteIndex` and comparing only source IP), or otherwise rate-limit and treat mismatched/absent-remote cases conservatively so an unauthenticated attacker cannot single-packet a live tunnel closed.

### Proof of Concept
1. Attacker observes (or otherwise learns) the current UDP source/destination address pair used by Node A's tunnel to Node B, and captures/guesses Node B's `localIndexId` for that tunnel (visible in cleartext in exchanged packet headers, since `RemoteIndex`/`h.RemoteIndex` is not encrypted at the header level).
2. Attacker crafts a raw UDP packet with `header.Type = header.RecvError` and `RemoteIndex` set to Node B's known local index, sourced (or spoofed) from Node A's currently active UDP endpoint, and sends it to Node B.
3. `readOutsidePackets` routes it to `handleRecvError` without any certificate/handshake validation: [3](#0-2) 
4. `hostinfo.GetRemote()` matches the spoofed source address (or is not yet set), so the address check passes and `f.closeTunnel(hostinfo)` executes, tearing down the legitimate tunnel between A and B without either party's cooperation.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
