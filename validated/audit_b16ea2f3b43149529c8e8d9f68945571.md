### Title
Bazel's `git_repository`/`new_git_repository` submodule fetch forcibly re-enables Git's `file://` local-clone protocol, reintroducing arbitrary-file-write via attacker-controlled submodules - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`'s submodule initialization unconditionally passes `-c protocol.file.allow=always` to `git submodule update`, overriding the Git-upstream security fix (CVE-2022-39253) that restricts local/`file://`-transport submodule clones by default. Since the content that defines submodule URLs (`.gitmodules`) is fully attacker-controlled (it lives in the fetched, externally-hosted repository), a malicious repository author can craft submodules that abuse the re-enabled local-clone path to write files outside the intended checkout directory when `init_submodules`/`recursive_init_submodules` is used.

### Finding Description
`update_submodules` in [1](#0-0)  runs:

```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
```
in both the recursive and non-recursive branches, with a comment explicitly acknowledging this is necessary to keep local-directory submodule clones working (referencing bazelbuild/bazel#17040). This directly negates Git's own default of `protocol.file.allow=user`/restricted, which upstream Git tightened specifically to stop a submodule-driven local-clone attack (CVE-2022-39253) where a maliciously crafted `.gitmodules` submodule path/URL, combined with Git's local ("file"/relative-path) clone optimization (which may use hardlinks or symlink-following during checkout), can cause files to land outside of the intended working tree.

The attacker surface here is exactly the class described in the report: an unprivileged outsider who owns/publishes a Git repository that a `git_repository`/`new_git_repository` rule fetches (`ctx.attr.remote`, `ctx.attr.commit`/`tag`/`branch`, see attrs in [2](#0-1)  and [3](#0-2) ). The victim only needs `init_submodules = True` (or `recursive_init_submodules = True`) to trigger `update_submodules`, called from `_update` in [4](#0-3) . The `.gitmodules` file and its submodule `url`/`path` entries are entirely part of the attacker's repository content — nothing in Bazel validates or sandboxes submodule URLs before they reach `git submodule update`.

Because the commit hash pinning (when `commit` is used) only ensures the victim gets exactly the content the attacker published — it does not protect against the attacker publishing malicious `.gitmodules` content in the first place. The "declared digest" (the git commit SHA) is not being bypassed; it simply pins content that was malicious from the start, which is squarely within the described attacker model ("an outsider who publishes ... content a victim's build consumes").

### Impact Explanation
Git's local submodule-clone optimization, when re-enabled via `protocol.file.allow=always`, can be abused by a submodule whose path/URL is crafted to exploit symlink or hardlink behavior during checkout, causing Git to write files to locations outside of the intended repository checkout directory (i.e., outside of the sandboxed external-repository directory Bazel expects to confine writes to). This is a "write outside the repository/exec root/output base" primitive with attacker-chosen file content, on the machine executing the fetch — exactly the class this vulnerability was assigned CVE-2022-39253 for in upstream Git before Git hardened the default.

### Likelihood Explanation
Any `MODULE.bazel`/`WORKSPACE` usage of `git_repository` (or the deprecated `new_git_repository`) with `init_submodules = True` or `recursive_init_submodules = True` against a third-party/attacker-influenced remote is affected, with default Bazel flags — no opt-in flag disables this behavior, and the `-c protocol.file.allow=always` override is unconditional in both call sites in `update_submodules`.

### Recommendation
Do not unconditionally force `protocol.file.allow=always`. Only clone submodules using safer defaults (e.g. Git's restricted `protocol.file.allow=user`/deny for untrusted content), or explicitly validate/sanitize submodule URLs (reject `file://`/relative local paths pointing outside the checkout, or require `--no-local` on submodule clones) before invoking `git submodule update`, restoring the containment Git's own fix intended to provide.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` proof would: (1) create an attacker-controlled git repo containing a `.gitmodules` entry whose `url` is a relative/`file://` path plus a symlink placed in the working tree (mirroring the upstream CVE-2022-39253 reproduction, e.g. a submodule directory pre-populated with a symlink named `.git` pointing outside the checkout before `git submodule update --init` runs); (2) define `git_repository(name="g", remote="<attacker_repo>", commit=<pinned_sha>, init_submodules=True)`; (3) run `bazel fetch @g//...` and observe that a file is written/overwritten at a path outside `bazel-<ws>/external/+git_repository+g`, confirming the local-clone/symlink escape enabled by the forced `protocol.file.allow=always`. def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
