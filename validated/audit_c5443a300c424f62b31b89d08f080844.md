### Title
Bank Cache Updated Before (Not After) Balance Mutation in `lending_account_close_balance` - (File: `programs/marginfi/src/instructions/marginfi_account/close_balance.rs`)

### Summary
This is a direct analog of the reported veRAACToken bug class: a state-aggregation update function (`_updateBoostState()` in RAAC, `update_bank_cache()` in marginfi) must run *after* the operation that changes the underlying accounting values, but in `lending_account_close_balance` it is invoked *before* the balance-modifying call, leaving the bank's cached aggregate state stale relative to the just-mutated `total_asset_shares`/`total_liability_shares`.

### Finding Description
In `lending_account_close_balance`, the call order is:
1. `bank.accrue_interest(...)`
2. `bank.update_bank_cache(group)?;` — recomputes/refreshes cached values (rates, oracle price cache, etc.) from the bank's *current* `total_asset_shares`/`total_liability_shares`.
3. Only afterwards does `bank_account.close_balance(in_receivership)?;` actually mutate the user's balance and, transitively, the bank's total share counters. [1](#0-0) 

This is the inverse of the correct pattern used everywhere else in the codebase, where `update_bank_cache()` is deliberately called *after* the balance mutation so the cache reflects the final post-operation state — e.g. in `lending_account_deposit`: [2](#0-1) 

`lending_account_withdraw`: [3](#0-2) 

`lending_account_repay`: [4](#0-3) 

`lending_account_borrow`: [5](#0-4) 

and the Solend/Drift/JupLend integration withdraw handlers, all of which explicitly comment "Update bank cache after modifying balances": [6](#0-5) [7](#0-6) 

Notably, the test suite records that the exact same class of bug was previously found and fixed in `handle_bankruptcy.rs` ("the fix ... that moves `update_bank_cache` after repay"), confirming the team is aware that calling this function before the balance-mutating operation produces a stale/incorrect cache: [8](#0-7) 

`close_balance.rs`, however, still has the update-before-mutation ordering that was fixed elsewhere.

### Impact Explanation
`update_bank_cache()` refreshes cached rate/price fields that other instructions and off-chain consumers rely on for interest accrual and risk decisions. Because `close_balance()` (which zeroes out the position and adjusts `total_asset_shares`/`total_liability_shares` when the position is the last one, or otherwise changes share totals) runs after the cache is written, the cache can reflect stale share totals until the next bank-touching instruction refreshes it. This directly parallels the RAAC report's core risk: “all calculations protocol-wide dependent on \[the aggregate cached state\] will be affected” until the next incidental update. Given this could feed into interest-rate curve calculations or health/price staleness assumptions for other users of the same bank, it's a state-integrity issue affecting core accounting rather than a purely cosmetic one.

### Likelihood Explanation
`lending_account_close_balance` is a standard, permissionless (any account owner) instruction used routinely to prune dust/zero balances, so this ordering bug is triggered on essentially every call to it — the likelihood of triggering the bug is high, though the observable "distortion window" only persists until the bank's cache is next refreshed by another instruction, similar to the transient nature of the RAAC issue.

### Recommendation
Move `bank.update_bank_cache(group)?;` to execute after `bank_account.close_balance(in_receivership)?;`, mirroring the pattern already used in `deposit.rs`, `withdraw.rs`, `repay.rs`, `borrow.rs`, and the fix already applied in `handle_bankruptcy.rs`.

### Proof of Concept
Not fully verified with a runnable exploit — I was unable to inspect the full body of `update_bank_cache()`/`close_balance()` in `programs/marginfi/src/state/bank.rs` and `programs/marginfi/src/state/marginfi_account.rs` before running out of tool calls, so I cannot conclusively demonstrate which specific cached fields (rates vs. price) become stale as a result of this ordering, only that the ordering itself deviates from the pattern the codebase enforces everywhere else (and previously fixed for the analogous `handle_bankruptcy` case). A Devin session with repo access would be needed to trace `update_bank_cache`'s exact dependence on `total_asset_shares`/`total_liability_shares` and confirm the concrete on-chain effect.
