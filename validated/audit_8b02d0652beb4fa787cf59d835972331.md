### Title
Missing zero-address validation on `new_authority` permanently locks migrated MarginfiAccount funds - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let a `MarginfiAccount` authority (an ordinary, unprivileged user) migrate all of their account's balances/positions to a brand-new `MarginfiAccount` under a caller-supplied `new_authority`. The `new_authority` account is explicitly documented and implemented as completely unchecked, with no validation that it is non-zero, mirroring the "Missing Input Validation" bug class described in the external report (no zero-address check before writing an address into privileged/controlling state).

### Finding Description
In `transfer_to_new_account`, the `new_authority` account is declared as: [1](#0-0) 

and its key is written directly into the freshly-initialized account without any check that it differs from `Pubkey::default()`: [2](#0-1) 

`initialize_migrated_account` copies over all of the old account's positions (`lending_account`, flags, etc.) into the new account: [3](#0-2) 

and the old account is simultaneously zeroed out and irreversibly marked as migrated: [4](#0-3) 

with a hard guard preventing any further migration from the old account: [5](#0-4) 

The identical unchecked pattern exists in the PDA variant, `transfer_to_new_account_pda`: [6](#0-5) [7](#0-6) 

Notably, the off-chain `p0-cli` tooling recognizes this exact risk and defensively rejects it client-side before building the transaction: [8](#0-7) 

but this check exists only in the CLI, not in the on-chain instruction handler itself, so any other client, integrator, or direct RPC call bypasses it entirely.

### Impact Explanation
If `new_authority` is passed as `Pubkey::default()` (or any other address with no discoverable private key), the program:
1. Creates a new `MarginfiAccount` with `authority = Pubkey::default()`.
2. Copies all of the old account's lending/borrowing positions into that new account.
3. Permanently disables the old account (`ACCOUNT_DISABLED`) and marks it as migrated, with `AccountAlreadyMigrated` blocking any retry from the old account.

Since no one controls `Pubkey::default()`, every asset and liability position transferred is permanently unrecoverable — no withdraw, repay, close-balance, or any other authority-gated instruction can ever be executed against the new account. This is a permanent lock/freeze of user funds, matching one of the accepted impact categories.

### Likelihood Explanation
The path is directly reachable by any regular (unprivileged) account holder calling `lending_account_transfer_to_new_account` / `...pda` — no admin privilege is required, only the account's own `authority` signature. The bug is only exploitable/triggerable by the account owner against their own account (self-inflicted, or triggered via a buggy/malicious front-end/integration that forgets to validate the destination), so it does not enable one user to steal or freeze another user's funds, but it does allow accidental or integration-driven permanent loss of an account's entire position set with no on-chain safeguard, despite the protocol's own CLI recognizing and guarding against exactly this input.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that rejects `new_authority == Pubkey::default()` (and any other well-known "burn"/uncontrollable addresses if desired) before initializing `new_account`, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAccountAuthorityTransfer // or a new dedicated error
);
```
placed before `initialize_migrated_account` is called, so the migration reverts instead of silently freezing all migrated balances.

### Proof of Concept
1. User creates a `MarginfiAccount` and deposits/borrows normally.
2. User (or an integrator calling on their behalf) invokes `lending_account_transfer_to_new_account` (or the PDA variant) with `new_authority = Pubkey::default()`.
3. Transaction succeeds: old account is zeroed/disabled and marked migrated; new account is created holding all copied positions with `authority = Pubkey::default()`.
4. No subsequent instruction can be authorized against the new account (`is_signer_authorized` will never match a signer to `Pubkey::default()`), permanently freezing the funds represented by those positions.
