### Title
Out-of-bounds read while parsing ZIP central directory extra fields in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses each Central Directory Header of a ZIP/JAR file without validating that attacker-controlled length fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and the per-record `data_size` inside the extra-field sub-records) stay within the bounds of the mapped input file. This mirrors the root cause of CVE-2019-11035, where PHP's `exif_iif_add_value` trusted an attacker-controlled tag length and read past the allocated EXIF buffer.

### Finding Description
`FindZipCentralDirectory` (same file, lines 704-778) only validates that the *aggregate* central directory region fits inside the mapped file: `cd.central_dir_offset + cd.central_dir_size > in_length` is rejected [1](#0-0) . It relies on the comment "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" [2](#0-1) , i.e. it assumes each individual entry is well-formed and the sum of correctly-parsed entries lands exactly on that trailing signature.

`ProcessCentralDirEntry` never checks this per-entry invariant. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly off the wire and unconditionally advances the cursor `p` by these values with no equivalent of the `EnsureRemaining()` bound check used for local file headers: [3](#0-2) .

Worse, the nested extra-field loop trusts the attacker-supplied `data_size` of each sub-record and advances `extra_p` by it without checking it against the remaining `extra_field_length`: [4](#0-3) . If `data_size` (or the outer `extra_field_length`/`file_name_length`/`file_comment_length`) is larger than what actually remains in the mapped file, `extra_p`/`p` overruns the mapped buffer, and every subsequent `get_u2le`/`get_u4le`/`get_u8le`/`memcpy` call reads out-of-bounds memory before any signature check can catch the corruption — exactly the pattern in `exif_iif_add_value`, where a length field taken from an untrusted tag was trusted to bound a subsequent read.

By contrast, `ProcessLocalFileEntry` (used for local headers) does call `EnsureRemaining()` before consuming `file_name_length` and `extra_field_length` [5](#0-4) , showing the project is aware of this exact class of bug but did not apply the same check to the central-directory parser.

### Impact Explanation
`InputZipFile`/`ZipExtractor` (of which `ProcessCentralDirEntry` is the entry-parsing primitive) is the shared ZIP parser used by Bazel's `ijar` tool, `zip_main.cc` (`zipper`), and the client-side self-extraction path in `src/main/cpp/archive_utils.cc` (`PartialZipExtractor::UnzipUntil`) [6](#0-5) . Any of these tools processing an attacker-influenced JAR/ZIP (e.g. a `java_import`/`http_jar`/Maven artifact fetched into the build) reaches this code. An out-of-bounds read past the mmap'd input file can crash the build tool (denial of service) or, if adjacent memory is copied into the `filename` buffer or leaked through downstream size/offset computations, disclose process memory contents — the same disclosure/crash impact profile as CVE-2019-11035.

### Likelihood Explanation
The mapped file's overall central-directory boundary is checked, but per-entry field lengths and nested extra-field `data_size` are fully attacker-controlled 16-bit values with no bound check against the remaining bytes in the mapped file, so triggering the overrun requires only crafting a single malformed Central Directory Header (or a malformed ZIP64 extra field) inside an otherwise valid-looking ZIP/JAR — a low-effort, deterministic manipulation, not a race or timing-dependent condition.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry` — analogous to `EnsureRemaining()` in `ProcessLocalFileEntry` — before consuming `file_name_length`, `extra_field_length`, `file_comment_length`, and before advancing `extra_p` by each sub-record's `data_size` inside the extra-field loop. Reject the entry (and abort parsing) whenever consumption would move the cursor past `central_dir_ + central_dir_size` or past the end of the mapped input file.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to the existing `third_party/ijar/test/zip_test.sh` `test_no_path_traversal` case [7](#0-6)  can be constructed: craft a minimal ZIP whose last Central Directory Header entry declares `extra_field_length` (or a nested extra-field `data_size`) larger than the number of bytes actually remaining before the End-Of-Central-Directory record, then run it through `zipper x` (or `ijar`). Under a memory-sanitized build (ASan) this reproducibly triggers a heap-buffer-overflow/read report inside `ProcessCentralDirEntry`; without sanitizers it can be observed as a crash or as corrupted/garbage entry names emitted by the tool.
