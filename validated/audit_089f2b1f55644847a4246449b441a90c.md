## Title
Heap out-of-bounds read in `InputZipFile::ProcessCentralDirEntry` via unchecked ZIP extra-field `data_size` - ([File: third_party/ijar/zip.cc])

### Summary
`third_party/ijar/zip.cc`'s `ProcessCentralDirEntry` parses the extra-field list of a ZIP central directory entry (used by ijar/singlejar-family tooling when processing jar files, e.g. jars pulled in via `http_jar`/`http_archive` and consumed as `java_import`/`java_library` deps) without validating that the attacker-controlled `data_size` field stays within the bounds of the extra-field region, unlike the equivalent local-header parsing path which is bounds-checked via `EnsureRemaining`.

### Finding Description
In `ProcessCentralDirEntry`, after reading `file_name_length` and `extra_field_length` from the CDH record, the code walks the extra-field list with no boundary validation: [1](#0-0) 

```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) {
      *uncompressed_size = get_u8le(extra);
    }
    ...
```

`data_size` is a raw, attacker-controlled 16-bit value taken directly from the archive and used to advance `extra_p` with no check against the `extra_field_length`-bounded end (`p`). This differs from the sibling function `ProcessLocalFileEntry`, and from the `ExtraField::find`/`ExtraField::next` bounds checks used in `src/tools/singlejar/zip_headers.h` and `output_jar.cc` (which explicitly verify `byte_ptr(ef) + ef->size() <= byte_ptr(end)` before touching payload bytes, e.g. ` [2](#0-1) `). In `zip.cc` no equivalent check exists: if `data_size` is large enough that `header_id == ZIP64_EXTRA_FIELD_TAG` and the entry claims a 64-bit field is present, `get_u8le(extra)` reads 8 bytes starting at `extra`, which can be located arbitrarily close to (or even at) the end of the mmap'd input file if `extra_field_length` is small but `data_size` lies. This mirrors the "AuthorityKeyIdentifier size confusion" bug class in the reference report: an internal size field taken from parsed, untrusted binary input is trusted without validating it against the actual bounds of the containing structure, leading to an out-of-bounds read/heap overflow when the mismatched size is later dereferenced (`get_u8le`).

Because `InputZipFile` mmaps the archive file directly (`zipdata_in_`, `MappedInputFile`), an out-of-bounds read here reads adjacent heap/mapped memory beyond the file's mapped region, and if `extra_p` overshoots `p`, the `while (extra_p != p)` loop condition can also fail to terminate correctly, continuing to walk and dereference attacker-influenced pointers past the intended extra-field/central-directory bounds.

### Impact Explanation
An attacker who controls the contents of a ZIP/JAR file that Bazel processes through this code path (e.g. a `.jar` fetched via `http_jar`/`http_archive`/`java_import`, or any archive routed through the ijar toolchain) can craft a central directory entry with a malformed `data_size` in an extra field to trigger an out-of-bounds read at the process level. This can crash the build process (build worker) or, depending on adjacent memory layout, leak adjacent heap bytes into a computed size value that then influences subsequent memory operations elsewhere in the ijar/zip processing pipeline. This matches the CVSS profile of the reference report (confidentiality impact via heap OOB read due to size-field confusion), scoped to an unprivileged content publisher, not a MITM or malicious peer.

### Likelihood Explanation
Reaching this code requires only that Bazel process an untrusted ZIP/JAR archive with the ijar/zip tooling — a routine, default operation whenever a `.jar` dependency (fetched from an external, attacker-influenced URL/registry) is consumed. No special flags are required, and the existing sha256/integrity checksum on the download does not prevent the attack because it only verifies that the archive matches what the attacker deliberately published — the checksum is not a defense against the archive's *internal* structure being malformed. Likelihood is elevated because JAR consumption from external repositories is one of the most common developer workflows in Bazel/Java builds.

### Recommendation
Add the same bounds validation used in `src/tools/singlejar/zip_headers.h`'s `ExtraField::find` to `ProcessCentralDirEntry` (and any other callers walking extra-field lists in `third_party/ijar/zip.cc`): before reading `header_id`/`data_size`, verify `extra_p + 4 <= p`; after computing `extra_p += data_size`, verify the new `extra_p <= p` before proceeding, and verify `extra + 8 <= extra_p` (or the appropriate bound) before calling `get_u8le(extra)`. On violation, fail with an explicit "malformed extra field" error rather than continuing to parse.

### Proof of Concept
A concrete PoC would need to be executed on the actual toolchain (I could not run `bazel` or the `ijar`/`singlejar` binaries from this read-only environment to confirm the crash/OOB-read empirically); the following describes the reproduction that a background agent or engineer with build/test access should carry out:
1. Hand-craft a ZIP file whose central directory contains one file entry with `extra_field_length` set to a small value (e.g. 4), but whose extra-field bytes encode `header_id = 0x0001` (ZIP64) and `data_size = 0xFFFF`.
2. Ensure the corresponding local-file-header 32-bit uncompressed/compressed size fields are `0xFFFFFFFF` (triggering the ZIP64 fallback path in `ProcessCentralDirEntry`).
3. Run this file through `ijar`'s `zip_main`/`UnzipProcessor`, or through the ijar step of a `java_import`/`java_library` build referencing this jar, under ASan/valgrind, and confirm a heap-buffer-overflow read is reported at the `get_u8le(extra)` call in `ProcessCentralDirEntry`.
4. Add a corresponding `src/test/...` regression test (analogous to `output_jar_simple_test.cc`'s `MalformedExtraField` test, cited above) asserting the parser rejects the malformed archive with an error rather than reading out of bounds. [3](#0-2) [4](#0-3)

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
