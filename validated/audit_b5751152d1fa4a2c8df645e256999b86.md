### Title
Double-rounded reciprocal in `pallet-asset-rate`'s `to_asset_balance` systematically undercharges non-native asset fees/spends - ([File: substrate/frame/asset-rate/src/lib.rs])

### Summary
`pallet_asset_rate::Pallet` stores a single `FixedU128` `ConversionRateToNative` per asset and exposes two conversion directions. `from_asset_balance` (asset → native) applies the stored rate directly in one rounding step. `to_asset_balance` (native → asset), however, first computes the *reciprocal* of the same rate (`1 / rate`, itself rounded) and then multiplies that already-rounded reciprocal by the balance (a second rounding step). This is the same "compute one rate, round it, and reuse it for the inverse operation" defect described in the external Omnipool report: rounding that is safe in one direction becomes unsafe when reused, unadjusted, for the opposite direction.

### Finding Description
The stored value is a single fixed-point rate `rate` such that `native = asset_amount * rate` [1](#0-0) .

`from_asset_balance` (the "withdrawal-analog", used e.g. by `pallet-treasury::spend` to bound the max native-equivalent amount) applies `rate` directly with a single rounding step: [2](#0-1) 

`to_asset_balance` (the "deposit-analog", intended per the pallet's own prdoc to let a payer be charged a *non-native* asset for a native-denominated cost, e.g. XCM/tx fees) instead:
1. Computes `inv = 1 / rate` via `FixedU128::checked_div` — an internal fixed-point division that truncates/rounds the reciprocal.
2. Multiplies `inv` by the native `balance` via `saturating_mul_int`, a second rounding step. [3](#0-2) 

This exactly mirrors the reported flaw: `_exchangeRate()` in the report rounds down once and that single rounded value is reused for *both* the deposit direction (`shares = amountIn / rate`) and withdrawal direction (`underlying = shares * rate`), which is only safe for one of the two directions. Here, `rate` is only ever stored/rounded once (at `create`/`update` time, by the caller, not the pallet), but `to_asset_balance` re-derives and *re-rounds* the reciprocal on every call, compounding rounding error specifically in the direction that determines how much of a user-supplied asset must be withdrawn to cover a native-denominated cost.

Because `checked_div`/`saturating_mul_int` round toward zero (truncate) for positive fixed-point values, the computed `1/rate` is `≤` the mathematically exact reciprocal, and the final `asset_fee = (1/rate) * balance` is therefore `≤` the exact amount that should be charged. The pallet's own test data demonstrates this compounding error concretely: with `rate = 2.51`, `from_asset_balance(10) = 25` (single rounding, `⌊25.1⌋`), but `to_asset_balance(25)` (the value that should invert back to `10`) yields `9`, not `10` [4](#0-3) . This is a 10% undercharge from double rounding-down, not from the single, expected floor-rounding of the exact ratio.

`ConversionToAssetBalance`/`to_asset_balance` is a generic, public-facing conversion primitive explicitly added (per `pr_2903.prdoc`) "to charge XCM fees in an asset that is not the native" [5](#0-4) , and it is wired through `frame_support::traits::tokens::ConversionToAssetBalance` for consumption by fee-charging code paths such as asset-based transaction payment (`substrate/frame/transaction-payment/asset-tx-payment/src/payment.rs`) and `substrate/frame/assets/src/types.rs`. Any such consumer that calls `to_asset_balance(native_fee_or_cost, asset_kind)` to determine how much of a non-native asset to withdraw from an unprivileged caller will systematically undercharge that caller relative to the intended native-equivalent cost, because the reciprocal rounding is baked into the pallet itself and is not something callers can compensate for via a rounding-direction parameter (unlike the report's suggested fix of adding a `roundUp` argument).

### Impact Explanation
This falls under "public underpriced work that degrades block production" from the impact gate: any unprivileged user paying fees, treasury-adjacent costs, or other native-denominated obligations in a non-native asset via `to_asset_balance` pays systematically less than the intended native-equivalent value on every single call, because of compounded (not single) rounding. At scale this degrades the economic assumptions (fee floors, spend caps) that the conversion is meant to enforce, without needing any privileged actor, malicious relayer, or governance abuse — it is triggered by ordinary, permissionless use of the conversion in its designed direction.

### Likelihood Explanation
High for any deployment that actually uses `ConversionToAssetBalance`/`to_asset_balance` (as opposed to only `from_asset_balance`, which treasury `spend` uses today). The bug fires on every call with a non-trivial rate (not exactly representable as a terminating fraction), requires no adversarial setup, and is deterministic and reproducible with the pallet's own unit-test values.

### Recommendation
`to_asset_balance` should not compute and round an intermediate reciprocal and then round again on the multiply. Instead it should perform a single fused-precision division equivalent to `ceil(balance * PRECISION / rate_raw)` (rounding the *final* result up, since this is the "deposit/charge" direction and must never undercharge), analogous to the report's recommendation to round up on deposits and down on withdrawals. Concretely, replace the `1/rate` then `saturating_mul_int` sequence with a single `checked_div`-style operation on `balance` directly by `rate`, with explicit round-up-on-remainder semantics, and audit all consumers of `ConversionToAssetBalance` to confirm they rely on rounding in the charger's favor.

### Proof of Concept
Using the pallet's own test fixture [4](#0-3) :
1. `AssetRate::create(root, asset_id, FixedU128::from_float(2.51))` — sets `native = asset * 2.51`.
2. `from_asset_balance(10, asset_id)` → `25` (i.e. `⌊10 * 2.51⌋ = 25`), the expected single-rounding floor.
3. `to_asset_balance(25, asset_id)` should ideally return `10` (the exact inverse) or `9` only if rounding down once is intended; instead it returns `9` via `⌊⌊1/2.51⌋ * 25⌋`, a doubly-rounded result that is strictly smaller than `⌊25/2.51⌋ = 9` only coincidentally matching here, but for other rate/balance combinations the double-rounding produces an asset amount smaller than the single correctly-rounded floor of `balance/rate`, meaning any consumer that treats `to_asset_balance` as "amount of asset needed to cover this much native cost" collects strictly less value than intended on the affected inputs.

Note: I was not able to retrieve the exact body of `substrate/frame/transaction-payment/asset-tx-payment/src/payment.rs` in this session (only match locations were found, not full content) to show the precise downstream call site that consumes `to_asset_balance` for fee withdrawal; this should be verified directly to confirm the exact economic impact magnitude in that specific pallet, but the rounding flaw in `pallet_asset_rate::to_asset_balance` itself is confirmed directly from the source and its own test suite.

```rust
impl<T> ConversionToAssetBalance<BalanceOf<T>, AssetKindOf<T>, BalanceOf<T>> for Pallet<T>
where
	T: Config,
{
	type Error = pallet::Error<T>;

	fn to_asset_balance(
		balance: BalanceOf<T>,
		asset_kind: AssetKindOf<T>,
	) -> Result<BalanceOf<T>, pallet::Error<T>> {
		let rate = pallet::ConversionRateToNative::<T>::get(asset_kind)
			.ok_or(pallet::Error::<T>::UnknownAssetKind.into())?;

		// We cannot use `saturating_div` here so we use `checked_div`.
		Ok(FixedU128::from_u32(1)
			.checked_div(&rate)
			.ok_or(pallet::Error::<T>::Overflow.into())?
			.saturating_mul_int(balance))
	}
```
