### Title
Uncontrolled array index derived from attacker-supplied ABI offset word causes ArrayIndexOutOfBoundsException in `ValidateMultiSign` precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x...0a`) decodes its `bytes` calldata into a `DataWord[]` array and then uses an attacker-controlled offset word to index into that same array, without validating that the derived index is within bounds. This mirrors the DBI bug class: a size/offset field supplied by the caller is trusted to be consistent with the actual buffer length, and when it is not, the internal indexing logic reads out of bounds.

### Finding Description
In `execute(byte[] rawData)`: [1](#0-0) 
the code parses `rawData` into `words = DataWord.parseArray(rawData)` and then computes `words[3].intValueSafe() / WORD_SIZE` as an offset used to index directly into `words` (`words[words[3].intValueSafe() / WORD_SIZE]`) to read `sigArraySize`, and later passes that same offset into `extractSigArray`/`extractBytesArray`. The `words[3]` value comes entirely from the caller's calldata and is never checked against `words.length` before being used as an array index.

The `isValidAbiEncoding` bounds/shape check is only invoked when `VMConfig.allowTvmOsaka()` is enabled: [2](#0-1) 
Prior to that feature flag (and this is a mainnet-activatable TIP flag, meaning the legacy code path is exercised on any chain/version where TIP-854 has not been activated), no such check exists, so a crafted `words[3]` offset that exceeds `words.length` throws an uncaught `ArrayIndexOutOfBoundsException` deep inside `PrecompiledContract.execute()`.

This is confirmed by the project's own regression test comment, which documents this exact pre-activation failure mode: [3](#0-2) 

Unlike `BatchValidateSign`, which wraps `doExecute` in a `try { } catch (Throwable t)` that swallows any exception and returns a safe `(true, zero-bytes)` result: [4](#0-3) 
`ValidateMultiSign.execute` has **no such outer catch**, so the `ArrayIndexOutOfBoundsException` (or a similarly-caused `NegativeArraySizeException` if the derived length ends up negative) propagates directly out of `contract.execute(data)` in `Program.callToPrecompiledAddress`: [5](#0-4) 

### Impact Explanation
An unprivileged caller can trigger this by simply deploying and calling a contract that performs a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address (`0x...0a`) with crafted `bytes` data where the offset word (`words[3]`) is a large or malformed value inconsistent with the actual array length — exactly the "statement handle has no fields but the row is non-empty" class of bug, translated to ABI-decoded word arrays. Because `RuntimeException`/`Error` subclasses like `ArrayIndexOutOfBoundsException` are not among the checked/expected TVM exceptions handled by `Program.Exception` or `RuntimeImpl.setResultCode`, this can surface as an unhandled `UNKNOWN` result code path (see the exhaustive `if (exception instanceof ...)` chain in `RuntimeImpl.setResultCode`), and more importantly, on the pre-activation code path it is not contained at all inside the precompile — it propagates as a raw Java runtime exception through transaction execution. Whether this can be forced up to `Manager.processTransaction`/block application depends on higher-level catch clauses (`VMIllegalException`, generic try/catch around `runtime.execute`) which were not exhaustively traced in this session; if any Java `RuntimeException` from this path escapes the transaction-execution try/catch used during block application, it can crash the node while applying a block/broadcasting a transaction, which is a denial-of-service against the node.

### Likelihood Explanation
High reachability: any account can deploy a trivial contract and invoke this precompile address directly with attacker-chosen calldata bytes — no special privilege, SR/witness status, or preexisting account permission structure is required. The only gating factor is whether the TIP-854 / `allowTvmOsaka` feature is active on the target network; on any network/version where it is not yet activated, the legacy unguarded decoder path is used unconditionally.

### Recommendation
Add the same `isValidAbiEncoding`/offset-bounds validation used for the post-TIP-854 path unconditionally (not gated behind `VMConfig.allowTvmOsaka()`), and/or wrap `ValidateMultiSign.execute` in a `try/catch(Throwable)` fallback identical to `BatchValidateSign.execute`, returning `Pair.of(true, DATA_FALSE)` on any decoding failure instead of allowing the exception to propagate out of the precompile boundary.

### Proof of Concept
1. Deploy a minimal contract that performs a raw `CALL` to precompile address `0x...0a` (`ValidateMultiSign`).
2. Construct calldata as a `bytes` blob whose first three 32-byte words are arbitrary (`address`, `permissionId`, `hash`), and whose fourth word (`words[3]`, meant to encode the offset to the `bytes[]` signatures array) is set to a value such as `0xFFFFFFFF` (or any value whose `/32` division yields an index ≥ the actual `words.length`).
3. Ensure the network does not have TIP-854 (`allowTvmOsaka`) activated, or supply calldata where `isValidAbiEncoding` incorrectly is bypassed.
4. Invoke the contract; observe that `words[words[3].intValueSafe() / WORD_SIZE]` in `PrecompiledContracts.java:1067` throws `ArrayIndexOutOfBoundsException`, which is not caught inside `ValidateMultiSign.execute` (contrast with `BatchValidateSign`'s outer try/catch), and propagates through `Program.callToPrecompiledAddress`.
