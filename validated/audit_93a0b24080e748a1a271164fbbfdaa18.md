### Title
Stale Postponed/Yielded ActionReceipt state survives `remove_account`, letting an attacker inject owner-level actions (`AddKey`/`DeployContract`) into an account recreated by a different owner - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) deletes the `Account`, `ContractCode`, access keys, gas-key nonces, and contract data for an account, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount` (and likewise `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`), all of which are keyed by `receiver_id`. Because `check_actor_permissions` only compares account-name strings (`actor_id == account_id`), a postponed/yielded receipt an attacker crafted against the old incarnation of an account name will still execute with owner-level permissions once the account name is deleted and later recreated by an unrelated party.

### Finding Description
`set_postponed_receipt` and `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) persist an action receipt keyed only by `receiver_id` (`TrieKey::PostponedReceipt{receiver_id, receipt_id}`, `TrieKey::PostponedReceiptId{receiver_id, data_id}`, `TrieKey::PendingDataCount{receiver_id, receipt_id}`) whenever the receipt has unresolved `input_data_ids`.

An attacker who owns account `A` can:
1. Send `A -> A` a `FunctionCall` that issues a self-callback receipt containing owner-level actions (`AddKey` full-access, `DeployContract`) with an `input_data_id` that depends on a second cross-contract call the attacker fully controls the timing of (a helper contract that only resolves the promise on a later, attacker-chosen transaction, or, more directly, `yield_create`/`yield_resume`, which is an explicit "hold-until-resumed" primitive). This receipt is postponed and stored under `receiver_id = A` (`lib.rs:1610-1655`), with `predecessor_id = A`.
2. Submit `DeleteAccount(A, beneficiary=B)` from `A` (satisfies `check_actor_permissions`, `runtime/runtime/src/actions.rs:761-776`, since `actor_id == account_id == A`). `action_delete_account` (`actions.rs:314-390`) calls `remove_account`, which does **not** purge the postponed/yield trie keys still referencing `A`.
3. `A` becomes an available account name again. Because `action_create_account` (`actions.rs:167-210`) allows *any* predecessor to create a top-level account whose length is `>= min_allowed_top_level_account_length`, or allows any parent account to (re)create its own sub-account, a completely unrelated party can register the same name `A` as a fresh account (this is a normal, unprivileged, permitted operation).
4. The attacker then delivers the withheld `DataReceipt` (or resumes the yield). `process_receipt`'s Data arm (`lib.rs:1386-1454`) finds the still-present `PostponedReceiptId`/`PendingDataCount` rows for `receiver_id = A`, decrements to zero, fetches the stale receipt via `get_postponed_receipt`, and executes it via `apply_action_receipt` against the **new** account state.
5. Inside `apply_action_receipt`, `actor_id` is set from `receipt.predecessor_id()` (`lib.rs:855`), which is still `A` (set by the attacker before deletion). `apply_action` → `check_actor_permissions` (`actions.rs:739-785`) only checks `actor_id == account_id` by name, so `AddKey`/`DeployContract` execute successfully — the new owner of `A` never signed or authorized these actions.

Nothing in `action_delete_account` checks for outstanding postponed receipts, pending data counts, or yielded promises before deleting the account, and nothing in `action_create_account` clears or checks for leftover postponed/yield state for the account name being (re)created.

### Impact Explanation
This is authorization escalation across the account-name lifecycle boundary (a promise/receipt crafted by a previous account holder executes with owner authority against a subsequently, legitimately re-registered account). The attacker can install a full-access key (`AddKey`) or replace the contract (`DeployContract`) on an account they no longer own, seizing control of the new owner's account and any funds/assets subsequently deposited into it — matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are all achievable by an unprivileged attacker: they own account `A`, can deploy their own contract, can construct a multi-hop async call (or use the public `yield_create`/`yield_resume` host functions) to hold a data dependency open indefinitely under their own control, and can submit ordinary `DeleteAccount`/(later) trigger transactions. The only external dependency is that some other unaffiliated party re-registers the exact same account name after it becomes available (for long top-level names this requires no special permission at all; for sub-accounts the new registrant must be the same parent account, e.g. a factory contract that reissues freed sub-account names). This is a plausible, repeatable scenario, e.g. for account names deliberately released and re-sold/re-issued by third-party account-name marketplaces or factory contracts.

### Recommendation
`remove_account` (`core/store/src/utils/mod.rs`) must also purge all outstanding data tied to the deleted account, iterating and removing:
- `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount` keyed by `receiver_id = account_id` (and any `ReceivedData` rows), and
- `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId` for the same `receiver_id`.

Alternatively/additionally, `action_delete_account` should reject deletion (or force-resolve/drop pending postponed/yielded receipts) while such state still exists for the account, so no stale receipt can survive into a future incarnation of the account name.

### Proof of Concept
Runtime/test-loop integration test plan:
1. Fund account `A`; deploy a contract on `A` with a method that issues a self `FunctionCall` receipt containing `AddKey(full_access)` gated behind an `input_data_id`, and a second helper method (or `yield_create`) that the attacker triggers manually to resolve that dependency later.
2. Call the method to create the postponed receipt on `A`; assert via direct trie inspection that `TrieKey::PostponedReceipt{receiver_id: A, ..}`, `PostponedReceiptId{receiver_id: A, ..}`, and `PendingDataCount{receiver_id: A, ..}` exist.
3. Submit `DeleteAccount(A, beneficiary=B)` from `A`; confirm the account is gone (`view_account` fails) but the postponed-receipt trie keys for `A` still exist (assert the set is non-empty — this is the failing invariant).
4. Register a fresh `A` (owned by a different signer/key) using `CreateAccount` (top-level name of sufficient length, or as a sub-account of a factory the new owner controls).
5. Trigger the withheld `DataReceipt`/`yield_resume`; run the chunk to completion.
6. Assert the new `A` now has a full-access key it never signed for (`view_access_key_list` includes the attacker's injected key), demonstrating unauthorized privilege escalation into the freshly re-registered account.
