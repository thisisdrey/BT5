### Title
Ungated Transfer Allows Unauthorized Module Upgrade via Stolen Code Object Ownership — (`aptos-move/framework/aptos-framework/sources/object_code_deployment.move`)

### Summary
The `publish` function creates a named object with `allow_ungated_transfer: true` (the framework default) but never disables ungated transfers. Any unprivileged account can call `object::transfer_call` to become the direct owner of the code object, then immediately call `upgrade` to replace the deployed module bytecode with attacker-controlled code.

### Finding Description
`object::create_named_object` (called inside `publish`) delegates to `create_object_internal`, which initialises `ObjectCore` with `allow_ungated_transfer: true`. [5](#0-4) 

`publish` stores only an `ExtendRef` in `ManagingRefs` and emits an event; it never calls `object::disable_ungated_transfer` or generates a `TransferRef` to lock the object. [6](#0-5) 

Because the flag remains `true`, the public entry function `object::transfer_call` succeeds for any caller who is the current owner (or indirect owner), writing the new owner address directly into `ObjectCore.owner`. [7](#0-6) [8](#0-7) 

`upgrade` then checks only `object::is_owner`, which reads that same mutable `owner` field: [4](#0-3) [9](#0-8) 

After the transfer the check passes, and `upgrade` calls `code::publish_package_txn` with the attacker's `metadata_serialized` and `code`, overwriting the module bytecode at the code object address. [10](#0-9) 

### Impact Explanation
An attacker who replaces the bytecode of a deployed module can redirect any logic in that module: steal fungible assets, mint tokens, drain staking or vesting balances, or corrupt any on-chain state managed by the module. This is a direct, unauthorized state transition affecting user-controlled on-chain value.

### Likelihood Explanation
The precondition (`allow_ungated_transfer == true`) is the framework default and is set automatically by `publish` with no opt-out. Any code object deployed through `object_code_deployment::publish` is vulnerable from the moment it is created. The attack requires only a single `transfer_call` transaction followed by an `upgrade` transaction — no privileged access, no governance, no validator control.

### Recommendation
In `publish`, after generating the `ConstructorRef`, generate a `TransferRef` and immediately disable ungated transfers so the code object can only be moved via the `TransferRef` held by the original publisher:

```move
let transfer_ref = constructor_ref.generate_transfer_ref();
object::disable_ungated_transfer(&transfer_ref);
// store transfer_ref in ManagingRefs if owner-controlled transfer is desired,
// or simply drop it to make the object permanently non-transferable.
```

Alternatively, store the original publisher address in `ManagingRefs` and check it (rather than the mutable `owner` field) in `upgrade` and `freeze_code_object`.

    aptos_framework: &signer,

    // Setup: victim publishes a package
    object_code_deployment::publish(victim, VICTIM_METADATA, VICTIM_CODE);
    let code_obj_addr = /* derive from victim address + seed */;
    let code_obj = object::address_to_object<PackageRegistry>(code_obj_addr);

    // Step 1: attacker steals ownership via ungated transfer
    // (victim is current owner, allow_ungated_transfer == true)
    object::transfer_call(victim, code_obj_addr, @0xB); // or attacker self-transfers if indirect owner

    // Step 2: attacker upgrades with malicious bytecode
    object_code_deployment::upgrade(attacker, MALICIOUS_METADATA, MALICIOUS_CODE, code_obj);

    // (upgrade succeeds without abort)
