### Title
Lost-update / clobbered balance write in `MarketSellAssetActuator` order matching when taker self-matches a resting order - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.execute()` keeps a single in-memory `AccountCapsule` for the order owner ("taker") for the whole duration of order matching and only persists it once, at the very end of the method. During matching, however, the private helper `addTrxOrToken(MarketOrderCapsule, long)` (the "maker" variant) independently re-reads the maker's account row from `AccountStore` and immediately writes it back mid-transaction. If the taker is also the maker of a resting order it matches against (a self-trade on the same asset pair), the maker-side re-read fetches a stale, pre-mutation copy of the very same account row, credits it, and persists it — and that write is then unconditionally overwritten by the final `accountStore.put()` call using the stale in-memory taker capsule, which never received the maker credit. This is a lost-update/stale-reference bug in the vein of the referenced kernel CVE (an object mutated/persisted during a "clash resolution" step whose result is discarded because the caller continues operating on an earlier snapshot).

### Finding Description
In `execute()`: [1](#0-0) 

`accountCapsule` (the taker) is fetched once, fee-debited, asset-debited (`transferBalanceOrToken`), and then passed by reference into `matchOrder(...)`. It is not written to the store again until line 148, after all matching has completed.

Inside matching, for every maker fill, two different code paths update account balances: [2](#0-1) 

- `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` mutates the same in-memory taker object passed from `execute()` — no store write happens here.
- `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` uses the maker-only overload: [3](#0-2) 

This overload performs its own `accountStore.get(orderCapsule.getOwnerAddress()...)`, mutates it, and immediately calls `accountStore.put(...)`.

If the taker's own address equals the maker's owner address (i.e., the trader is matching against their own earlier resting order — a legal, unrestricted scenario since nothing in `validate()`/`execute()` prevents self-matching), then:
1. The maker-side `addTrxOrToken` reads the account row from `accountStore` — at that point in the transaction this row still reflects the pre-match, pre-fee, pre-debit state (the in-memory `accountCapsule` mutations from steps 1–2 of `execute()` have not yet been flushed).
2. It credits the maker proceeds onto that stale base and immediately persists it to `accountStore`.
3. Execution returns to `execute()`, which later unconditionally does `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` (line 148) using the taker's in-memory object — which has the fee/debit/taker-credit applied, but never received the maker credit written in step 2.
4. The final persisted state for the account is the taker-side view, and the maker-side credit written in step 2 is silently discarded.

This is structurally the same bug class as the CVE: a stale, previously-fetched in-memory representation of state is written back after a nested "resolution" step (order match) that itself derived and committed a fresher, but ultimately superseded, view of the same underlying object.

### Impact Explanation
The trader who self-matches loses the token/TRX proceeds that should have been credited to them as the maker side of the fill — these funds are effectively vanished (not moved to blackhole, not credited to anyone), a permanent loss-of-funds bug reachable by any unprivileged account issuing a `MarketSellAssetContract`. Depending on match direction and ordering of multiple fills within `MAX_MATCH_NUM`, the discarded amount can also affect other legitimate makers matched in the same transaction whose credit calls occur before the final taker-capsule flush, compounding the loss across multiple counterparties in one transaction.

### Likelihood Explanation
Reachable directly from a single signed `MarketSellAssetContract` transaction with no special privileges: an account only needs to already have a resting order on the opposite side of the same token pair (which any user can create trivially with a prior `MarketSellAssetContract`) and then submit a matching order. No admin/committee/witness action, no reentrancy, and no TVM contract calls are required — pure actuator logic. This is a straightforward, deterministic sequence any client can trigger.

### Recommendation
Do not let the maker-side credit path (`addTrxOrToken(MarketOrderCapsule, long)`) perform an independent `accountStore.get`/`put` for the *same* account transaction the taker capsule is representing. Instead:
- Detect when `makerOrderCapsule.getOwnerAddress()` equals the taker's owner address and route the credit through the already-loaded `takerAccountCapsule` object instead of re-fetching from the store.
- More generally, defer all store writes for account balances involved in the match to the end of `execute()`, using a single map/cache of `AccountCapsule` keyed by address so all mutations converge onto the same in-memory object before the final persist, eliminating the possibility of a stale read clobbering a fresher write (or vice versa).

### Proof of Concept
1. Account `A` issues `MarketSellAssetContract` selling token `X` for token `Y` at a given price and lets it rest in the order book (maker order `O1`, `sell X / buy Y`).
2. Account `A` (same address) issues a second `MarketSellAssetContract` selling token `Y` for token `X` at a matching/crossing price (taker order `O2`, `sell Y / buy X`), causing `matchOrder` to match `O2` against `A`'s own resting `O1`.
3. During `matchSingleOrder`, `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` re-reads `A`'s account from `AccountStore`, credits the `Y` proceeds owed to `A` as maker, and writes it back immediately.
4. `execute()` finishes and persists its own in-memory `accountCapsule` for `A` (line 148), which reflects `A`'s taker-side debit/credit but not the maker credit applied in step 3, overwriting the earlier store write.
5. Inspect `AccountStore` after the transaction: `A`'s balance/asset amount for token `Y` is short by the maker-side proceeds that were computed and briefly persisted in step 3 — funds are permanently lost with no compensating entry anywhere else in the state.
