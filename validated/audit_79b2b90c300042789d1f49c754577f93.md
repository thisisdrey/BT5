### Title
Unauthenticated handshake initiation forces expensive Noise crypto per packet with no per-source cost, enabling oracle-style DOS flooding - (File: `handshake_manager.go`, `handshake/machine.go`)

### Summary
`HandshakeManager.HandleIncoming` / `beginHandshake` accepts any UDP packet that merely matches the wire-format shape of a stage-1 handshake message (correct `Subtype`, `MessageCounter == 1`, `RemoteIndex == 0`) and, before any certificate is seen or authenticated, builds a fresh Noise `HandshakeState` and runs `ReadMessage` on it — i.e. it performs the DH/crypto work of a handshake attempt for every such packet. There is no per-source-address limit on how many distinct stage-1 attempts an unauthenticated remote can trigger, so an attacker who holds no CA-signed certificate at all can cheaply flood a node with spoofed or replayed stage-1 packets and force it to repeatedly spend crypto/allocation cost, delaying legitimate handshakes — the same "trivially cheap request forces expensive backend work, repeatable without bound" pattern as the oracle DOS report.

### Finding Description
`HandleIncoming` gates only on subtype and a zero `RemoteIndex`, then calls `beginHandshake`, which allocates a new `handshake.Machine` (`handshake.NewMachine`) and calls `machine.ProcessPacket`, which in turn calls the Noise library's `ReadMessage`, performing X25519 DH and cryptographic mixing for every packet [1](#0-0) . Certificate validation (`validatePeerCert`) only happens after this cryptographic work has already completed [2](#0-1) . The only pre-crypto checks are the remote allow list (`AllowUnknownVpnAddr`, default-allow when unconfigured) and a purely structural `RemoteIndex == 0` check [3](#0-2) ; neither has any relation to certificate possession or per-source rate limiting. `handshake.Machine.ProcessPacket` explicitly documents that after `ReadMessage` succeeds "noise state has advanced" and cost has been paid regardless of whether the sender is subsequently found to be unauthenticated [4](#0-3) . There is no accounting of failed/pending handshake attempts per source IP that would throttle repeat offenders — `beginHandshake` runs the same expensive path for every inbound stage-1 packet indefinitely.

This is the direct analog of the reported oracle bug: a caller with no real standing (no valid trade / no valid certificate) can trigger a comparatively expensive backend operation (oracle round-trip / Noise DH) for a token cost (a $0.045 fee / a single UDP packet), and can repeat this without limit, at scale (every trading pair / every spoofed source address), to degrade service for legitimate users.

### Impact Explanation
Every crafted stage-1 packet forces a full Noise responder computation (ephemeral key generation, DH, and certificate deserialization overhead in `beginHandshake`) on the target node before any authentication occurs. An attacker with no certificate at all can source-spoof or repeat such packets at line rate, consuming CPU on X25519 operations and heap allocations (`HostInfo`, `handshake.Machine`, `RelayState`) for garbage that is discarded once `validatePeerCert` fails. This delays or starves legitimate handshake processing and lighthouse/tunnel setup for real peers, i.e. remote CPU-exhaustion/DOS against the responder — directly mapping to "Impact: Medium... delaying the processing of legitimate transactions" in the source report.

### Likelihood Explanation
Likelihood is high: no certificate, no prior handshake state, and no rate limiting are required to reach `beginHandshake` — only a well-formed stage-1 header (fixed subtype, `RemoteIndex=0`, `MessageCounter=1`) is needed, all of which are trivially attacker-controlled and require zero cost per attempt. This mirrors the report's "high likelihood ... exploited whenever [conditions are met]" framing, since the condition here (no rate limit on stage-1 handshake attempts) is always present, not tied to a market-closure window.

### Recommendation
- Add per-source (and/or global) rate limiting on inbound stage-1 handshake attempts in `HandleIncoming`/`beginHandshake` before constructing a `handshake.Machine` or invoking `ProcessPacket`, e.g. a token bucket keyed by `via.UdpAddr.Addr()`.
- Consider a lightweight, pre-crypto proof-of-work or cookie/puzzle exchange for first-contact stage-1 packets from unknown sources, deferring expensive Noise processing until the sender demonstrates minimal cost/return-routability.
- Track and cap the number of concurrently pending (uncompleted) responder handshakes per source address, dropping excess attempts before they reach `handshake.NewMachine`/`ProcessPacket`.

### Proof of Concept
1. Attacker crafts UDP packets with `header.H{Type: Handshake, Subtype: HandshakeIXPSK0, MessageCounter: 1, RemoteIndex: 0}` and an arbitrary/garbage Noise payload of valid length.
2. Attacker sends these packets in a loop, either spoofing distinct source addresses or reusing one uncontrolled by any allow-list restriction (default `remote_allow_list` is allow-all).
3. Each packet passes the cheap header checks in `HandleIncoming` [5](#0-4)  and reaches `beginHandshake`, which allocates a new `handshake.Machine` and calls `ProcessPacket`, performing full Noise `ReadMessage`/DH work [6](#0-5) .
4. Certificate validation fails afterward and the work is discarded, but the crypto cost has already been paid by the victim node — repeating step 2 indefinitely floods the responder's handshake-processing path with no cost/authentication requirement on the attacker's side.
