### Title
Per-IP connection-rate limiter never engages for handshake-stalling connections, allowing a single unstaked attacker to exhaust `max_concurrent_connections()` and cause `refused_connections_too_many_open_connections` - (streamer/src/nonblocking/quic.rs)

### Summary
`run_server` gates new QUIC connection attempts with `ConnectionRateLimiter::is_allowed()`, but that check only consults per-IP token-bucket state that is populated by `register_connection()`, which is invoked only *after* the QUIC handshake completes in `setup_connection` [1](#0-0) [2](#0-1) . For an IP that never completes a handshake, `is_allowed` unconditionally returns `true` because `current_tokens` returns `None` for unseen IPs [3](#0-2) . This means the "rate-limit abusive peers by (control-asserted) ip" mitigation described in the code comment is bypassed entirely by an attacker who only ever half-opens connections, leaving only the global `overall_connection_rate_limiter` (2500/s sustained, burst 1000) as a backstop [4](#0-3) .

### Finding Description
In `run_server`, each accepted incoming connection is checked against `overall_connection_rate_limiter` and then `rate_limiter.is_allowed(&ip)` before `ClientConnectionTracker::new` reserves a slot out of `qos.max_concurrent_connections()` [5](#0-4) . The `ClientConnectionTracker` increments `stats.open_connections` at creation and only decrements on `Drop`, which happens either when `setup_connection` returns (e.g. after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) or when the tracker is later moved into a `ConnectionEntry` [6](#0-5) [7](#0-6) . `setup_connection` awaits the handshake with a 2-second timeout (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) and only calls `rate_limiter.register_connection(&from.ip())` — the call that actually records/consumes a token for that IP — *after* the handshake succeeds [8](#0-7) [2](#0-1) .

Because `is_allowed` treats "no record" as "allowed" [3](#0-2) , an attacker who sends only Initial packets and never completes the TLS handshake never accumulates a rate-limiter record for their IP, so every subsequent half-open attempt from that same IP still passes `is_allowed`. The only throttle left is the *global* `overall_connection_rate_limiter` shared by all peers (legitimate and malicious) at up to `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) with burst 1000 [9](#0-8) . `max_concurrent_connections()` for `SwQos` is only `(max_staked + max_unstaked) * 5 / 4`, a modest 25% buffer intended to cover legitimate in-flight handshakes [10](#0-9) . An attacker sustaining a stream of half-open connections at a fraction of the 2500/s global cap can fill this small buffer within well under the 2-second handshake timeout window and keep it full indefinitely by continuously opening new half-open connections as old ones expire, since `open_connections` (and therefore `ClientConnectionTracker::new`'s admission check) is shared across staked and unstaked traffic alike [11](#0-10) . Once `open_connections >= max_concurrent_connections`, every legitimate `Incoming` (staked or unstaked) is refused and counted under `refused_connections_too_many_open_connections` [12](#0-11) .

### Impact Explanation
This is a QoS/availability bypass: an unprivileged, unstaked attacker can consume the shared `open_connections` budget gated by `qos.max_concurrent_connections()` without ever completing a handshake, causing legitimate (including staked) clients' connection attempts to be refused with `refused_connections_too_many_open_connections`. This is a scoped denial-of-service against the TPU QUIC ingress path, falling under the QoS-evasion / resource-exhaustion bounty category rather than a memory-safety or consensus-breaking bug.

### Likelihood Explanation
Feasibility depends on whether the global rate limiter's throughput (2500/s sustained, burst 1000) combined with the 2-second handshake timeout is sufficient for a single attacker to keep the small 25%-buffer pool saturated using only its own IP (no spoofing, no multiple clients required) — arithmetically, filling ~25% extra capacity above `max_staked_connections + max_unstaked_connections` for 2 seconds requires only a modest sustained rate, well within the 2500/s global ceiling, so this is plausible with a single attacking host. However, this analysis could not fully verify quinn/`Endpoint` behavior around anti-amplification limits and whether `Incoming`/`Connecting` is instantiated (and thus counted) before any address-validation exchange with the peer, or the exact default values of `max_staked_connections`/`max_unstaked_connections` used in production configuration — these bound the real-world size of the buffer to exhaust and were not fully confirmed from the indexed code.

### Recommendation
Apply per-IP throttling to *attempted* (not just completed) connections — e.g., consume a token from `rate_limiter` at the point `ClientConnectionTracker::new` is attempted (before or alongside the `is_allowed` check), rather than deferring `register_connection` until after a successful handshake. Additionally, consider tracking outstanding half-open (`outstanding_incoming_connection_attempts`) capacity separately per-IP or with a stricter global cap distinct from the post-handshake `open_connections` budget, so a burst of never-completing handshakes cannot crowd out legitimate staked/unstaked slots.

### Proof of Concept
Integration test plan (tokio, using existing `setup_quic_server` test harness in `streamer/src/nonblocking/quic.rs`):
1. Configure a test QUIC server with a small `max_staked_connections`/`max_unstaked_connections` (e.g., 4 total, giving `max_concurrent_connections() == 5`).
2. From a single simulated client IP, repeatedly open new QUIC connections (via `quinn::Endpoint::connect`) that send only the Initial packet and then are dropped/never advance the handshake (e.g., by not responding to `Connecting`/never calling `.await` to completion, or dropping the socket immediately after the first flight), timed just under `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) apart so the tracker's slot is held close to the full timeout each time.
3. Assert that `stats.open_connections` reaches `max_concurrent_connections()` and stays saturated across multiple timeout cycles (i.e., the attacker keeps refilling slots as old ones expire).
4. Concurrently, attempt a legitimate client connection (`make_client_endpoint`) and assert it is refused, observing `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0`.
5. Additionally assert `rate_limiter.is_allowed(&attacker_ip)` remains `true` throughout (i.e., no per-IP throttling kicks in) since `register_connection` is never called for an IP that never completes a handshake, confirming the bypass described above.

impl Drop for ClientConnectionTracker {
    /// When this is dropped, reduce the open connection count.
    fn drop(&mut self) {
        self.stats.open_connections.fetch_sub(1, Ordering::Relaxed);
    }
}

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
