Based on my investigation, the closest analog to "duplicate assets causing wrong LTV" in java-tron is in the `ValidateMultiSign` precompiled contract's signature deduplication logic.

### Title
Weight double-counting via non-canonical duplicate signatures in `ValidateMultiSign` precompile bypasses multi-sig threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` deduplicates signer weight contributions by comparing the *exact signature bytes* rather than only the *recovered address*, so a caller who supplies two syntactically-different but validly-recovering signatures for the same address can have that single key's weight counted twice toward the permission threshold — analogous to the reported "duplicate asset" bug where failing to deduplicate identical entries corrupts the count used in a threshold/ratio calculation.

### Finding Description
The precompile iterates the caller-supplied `signatures` array and, for each one, recovers the signer address, then decides whether to count its weight: [1](#0-0) 

The dedup check is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
        continue;   // skip only if this EXACT signature was already used
    }
    MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
```
This only skips counting when the *identical* signature bytes have already been seen for that address. If the recovered address is already present but the raw signature bytes differ (e.g., a malleable ECDSA signature `(r, n-s)` for the same `(r,s)`, or any other byte-distinguishable encoding that still recovers to the same address), the weight for that address is added again. Unlike `TransactionCapsule.checkWeight()` (used for normal transaction signature verification), which deduplicates strictly by recovered address via a `HashMap` and rejects re-signing by the same address ("has signed twice!") — [2](#0-1)  — the TVM precompile path deduplicates by signature bytes, leaving the address-level double count possible.

This mirrors the report's root cause pattern: a caller-controlled list is trusted to represent distinct entities (distinct assets in the report; distinct signers here), but the code fails to dedupe by the actual identity (asset address / signer address) and instead relies on a weaker equality check, corrupting a downstream sum used for a security-critical comparison (LTV ratio in the report; multi-sig `totalWeight >= threshold` here).

### Impact Explanation
If exploitable, an attacker controlling only `k` of the `n` keys required to reach a permission's threshold could potentially satisfy `ValidateMultiSign` by supplying multiple malleable/duplicate-byte signatures per controlled key, inflating `totalWeight` past the threshold without actually possessing enough distinct authorized keys. Since `ValidateMultiSign` is used by smart contracts to gate privileged actions (this is the on-chain multisig-check primitive exposed to any contract via `staticcall`/`call`), this could lead to unauthorized execution of actions gated by that check — a concrete unauthorized-account-operation / fund-theft scenario for any contract or protocol relying on this precompile for permission enforcement.

### Likelihood Explanation
Exploitability depends entirely on whether ECDSA/other supported signature schemes here permit two *distinct byte representations* that both recover to the same address for the same message hash (i.e., signature malleability is not rejected before reaching this dedup logic). I was not able to confirm, within the available index, whether `recoverAddrBySign` or the underlying `SignUtils`/`ECKey` recovery path enforces canonical low-S signatures or otherwise rejects the malleable counterpart before this comparison. This is a material uncertainty — if canonical-form is enforced upstream, this specific vector is not exploitable, and only pure exact-duplicate signatures (which are already correctly deduped) would occur in practice.

### Recommendation
Deduplicate strictly by recovered address (as `TransactionCapsule.checkWeight` and `VoteWitnessProcessor`'s vote-merging already do), not by raw signature bytes, so that repeated or malleable signatures for the same address can only ever contribute that address's weight once. Additionally verify that the signature recovery path enforces canonical (low-S) signatures to eliminate the malleable-signature vector entirely.

### Proof of Concept
Not able to construct a concrete calldata PoC without confirming whether the signature verification path enforces canonical low-S signatures — this would require access to `recoverAddrBySign`'s implementation and the `SignUtils`/`ECKey` recovery code, which I could not fully retrieve. Conceptually: craft a permission with threshold `T` and a single key of weight `W ≥ T/2`; produce two signatures over the same `hash` from that one key such that both recover to the same address but have differing raw bytes (e.g., malleable `s`/`n-s` pair, or differing recovery-id encodings); submit both in the `signatures` array to `ValidateMultiSign`; if the check returns `true` with `totalWeight = 2W ≥ T`, the threshold is satisfied using only one real key.
