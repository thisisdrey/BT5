### Title
Unbounded array size from attacker-controlled word in BatchValidateSign precompile causes OOM/DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytesArray` reads a length field `len` directly from calldata (`words[offset].intValueSafe()`) and immediately allocates `new byte[len][]`, exactly like the ImageMagick cineon flaw where `ReadCINImage` trusted a claimed image size without checking it against actual available data.

### Finding Description
`extractBytesArray` at [1](#0-0)  reads `len` from a caller-controlled `DataWord` and allocates `byte[len][]` plus loops `len` times performing further un-bounds-checked `extractBytes`/`Arrays.copyOfRange` calls, with no explicit maximum size check inside the function itself. The only guard against an oversized `len` lives in `BatchValidateSign.doExecute`, gated behind the `VMConfig.allowTvmSelfdestructRestriction()` feature flag: [2](#0-1)  — when that flag is off, `extractBytesArray` is invoked with the attacker-supplied `len` completely unchecked before allocation, so a huge `len` value (up to `Integer.MAX_VALUE`, since `intValueSafe()` caps a DataWord to an int) drives a massive array allocation before any other validation occurs. `extractSigArray` has the identical unguarded-length-then-allocate pattern at [3](#0-2) .

### Impact Explanation
An attacker deploying/calling a contract that invokes the BatchValidateSign precompile (address 0x66, reachable via any `CALL`/`STATICCALL` from a transaction) with crafted calldata can force a huge `byte[len][]` allocation, driving the node to OutOfMemoryError. This is a node crash/DoS condition, matching the "resource consumption" pattern of the CVE, and satisfies the "node crash or halt" acceptance criterion when `allowTvmSelfdestructRestriction` is disabled (its default/historical state on many chains before that hard fork activated).

### Likelihood Explanation
Reachable by any unprivileged account submitting a `TriggerSmartContract` transaction that calls the precompile address with crafted `data`; no special privilege is required, only enough energy to reach the precompile call (energy for this precompile does not scale with the huge allocation before the OOM occurs). Exploitability is entirely contingent on the `allowTvmSelfdestructRestriction` config flag being unset in the target network, which reduces likelihood on networks where the hard fork is already activated.

### Recommendation
Move the `MAX_SIZE` bound check (or an equivalent hard cap plus verification that `len` is consistent with `data.length`) unconditionally inside `extractBytesArray` and `extractSigArray` themselves, rather than only in the caller and only under a feature flag, so the length is always validated against actual buffer size before allocation, analogous to fixing `ReadCINImage` to validate `image->columns`/`rows` against available file data before allocating decode buffers.

### Proof of Concept
Craft calldata for `BatchValidateSign.execute`/precompile 0x66 where `words[1]` (offset to signature-array length) points to a word whose value is set to a very large integer (e.g., `0x7fffffff`), with `VMConfig.allowTvmSelfdestructRestriction()` disabled. Calling `extractBytesArray(words, offset, data)` allocates `new byte[0x7fffffff][]` and immediately throws `OutOfMemoryError`/exhausts heap during the TVM execution triggered by a normal `TriggerSmartContract` transaction, crashing or stalling the node's transaction-processing thread.
