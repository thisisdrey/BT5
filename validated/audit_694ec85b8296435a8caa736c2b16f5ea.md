### Title
Unauthenticated relay identity spoofing via `RelayFromAddr` in `CreateRelayRequest` — (File: `relay_manager.go`)

### Summary
`handleCreateRelayRequest` derives the "relay-from" identity used to create and index relay state entirely from an attacker-controlled protobuf field (`m.RelayFromAddr`) inside the `NebulaControl` message, instead of binding it to the actual cryptographically-authenticated sender of that control message (`h.vpnAddrs`). This is the same bug class as the C4 report: an operation is accounted against an identity taken from an untrusted/self-declared parameter rather than the identity established by authentication (there, `_msgSender()` vs. the real depositor; here, `h.vpnAddrs` — the Noise-handshake-verified peer — vs. `m.RelayFromAddr` — an arbitrary claim in the control payload).

### Finding Description
`handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl)` in `relay_manager.go` receives `h`, the `HostInfo` of the peer that completed a genuine, certificate-verified Noise handshake, and `m`, the `NebulaControl` payload from that peer. [1](#0-0) 

The function immediately does:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(from) {
    logMsg.Error("Discarding relay request from myself", "myIP", from)
    return
}
```
Only a check against the local node's own address is performed — there is no check that `from` actually equals one of `h.vpnAddrs` (the address(es) cryptographically bound to `h` via its certificate). Any authenticated peer `h` can set `RelayFromAddr` to an arbitrary third-party VPN address (e.g. a victim's address) rather than its own.

If `target` (also attacker-supplied and likewise unchecked against reality) resolves to the local node, the code proceeds to bind relay state to the spoofed `from` value: [2](#0-1) 
```go
if f.myVpnAddrsTable.Contains(target) {
    existingRelay, ok := h.relayState.QueryRelayForByIp(from)
    ...
    _, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
    ...
    relay, ok := h.relayState.QueryRelayForByIp(from)
```
The relay entry keyed by `from` is attached to `h`'s relay state and marked `Established` directly (no further handshake needed for the `TerminalType` branch), with `h` (the attacker's own, real hostinfo/tunnel) as the transport. Because `AddRelay` is called with the spoofed `from` and the caller's genuine `h`, any subsequent decision that trusts `relay.PeerAddr`/`from` as "the peer this relay represents" is poisoned: it now believes address `from` (potentially the victim's address, which the attacker does not control) is reachable/relayed through `h`.

This mirrors the "wrong receiver" root cause described in the report — an identity value used for state accounting (`userInfo[_pid][_msgSender()]` there; `relayState`/`AddRelay(..., from, ...)` here) is taken from an untrusted actor-supplied slot (the caller's account context there; the peer-declared protobuf field here) instead of the verified principal (the real depositor there; `h.vpnAddrs` here).

The same unauthenticated binding pattern also appears on the "am I the source" / forwarding branch (`else` branch below line 525) and in `handleCreateRelayResponse`, which trusts `peer.vpnAddrs[0]` for outbound fields but still processes attacker-supplied `RelayToAddr`/`RelayFromAddr` without cross-checking the responder's declared "from" against the known relay-state entry keyed by the real `h`.

### Impact Explanation
By spoofing `RelayFromAddr`, a fully authenticated but malicious peer can:
- Register bogus relay/route state on a relay node, associating a third party's VPN address with the attacker's own established tunnel, effectively poisoning the relay's routing table (`relayState`) for that address without ever handshaking as/for that address.
- Potentially intercept or disrupt traffic that legitimate handshake-completion logic or relay forwarding (`handleOutsideRelayPacket` in `outside.go`, which trusts `relay.PeerAddr`) would otherwise route to the genuine owner of that VPN address, since a `TerminalType, Established` relay entry is created immediately without validating that the claimed source ever authenticated as that address.
- Cause remote state poisoning of the hostmap/relay tables on any node acting as `am_relay`, which can lead to misdirected relay traffic or denial of service for the legitimate address (its real relay-through-this-node path may be blocked or shadowed by the attacker's spoofed entry).

This satisfies the "remote state poisoning" / firewall-bypass-adjacent impact class permitted by the validation rules, and is reachable by any node that can complete a normal (CA-signed) handshake and then send a crafted Control message — i.e., an authenticated peer with no special privilege, not a "malicious lighthouse" or "valid-certificate-holder acting within its own identity" scenario, since here the peer explicitly asserts an identity it does not hold.

### Likelihood Explanation
Likelihood is significant given:
- Any node with `relay.am_relay: true` will process `CreateRelayRequest` from any peer it has already handshaked with.
- No cross-check exists between the attacker-declared `RelayFromAddr` and the actual `h.vpnAddrs` bound to the authenticated tunnel that delivered the control message.
- Exploitation requires only a normal handshake (which any CA-signed cert holder can complete) plus crafting one `NebulaControl_CreateRelayRequest` message with a forged `RelayFromAddr`.

### Recommendation
In `handleCreateRelayRequest` (and the corresponding response handler), require that the declared `from` (`RelayFromAddr`) matches one of the addresses in `h.vpnAddrs` — i.e., bind relay-from identity to the certificate-verified `HostInfo` of the actual sender rather than trusting the protobuf-supplied address. Reject the request (analogous to `depositFor`'s `onlyDepositor`/verified-caller pattern in the report's recommendation) if `from` is not contained in `h.vpnAddrs`:
```go
if !slices.Contains(h.vpnAddrs, from) {
    logMsg.Error("Discarding relay request with spoofed RelayFromAddr", "claimedFrom", from, "actual", h.vpnAddrs)
    return
}
```

### Proof of Concept
1. Attacker node `A` completes a legitimate Noise handshake with relay node `R` (`am_relay: true`), so `R` has `HostInfo h` for `A` with `h.vpnAddrs = [A]`.
2. `A` sends `R` a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to `V` (a victim's real VPN address, not `A`'s) and `RelayToAddr` set to `R`'s own address.
3. `handleCreateRelayRequest` on `R` checks only `f.myVpnAddrsTable.Contains(from)` (false, since `from = V ≠ R`) and `f.myVpnAddrsTable.Contains(target)` (true, since `target = R`) — no check that `from == h.vpnAddrs`.
4. `R` calls `AddRelay(rm.l, h, f.hostMap, from /* = V */, &m.InitiatorRelayIndex, TerminalType, Established)`, creating relay state on `R` claiming that `V` is reachable/relayed via `h` (`A`'s tunnel), and sends back a `CreateRelayResponse` claiming `RelayFromAddr = V`.
5. `R`'s relay table for `V` is now bound to attacker `A`'s tunnel, without `V` ever participating — a state-poisoning outcome directly analogous to `userInfo[_pid][wrongAddress]` being populated instead of the real owner's slot in the original report.
