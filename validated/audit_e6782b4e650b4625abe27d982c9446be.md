# Finding: Bancor-style Exchange inject/withdraw operations have no slippage/minimum-output bound, enabling sandwich attacks

The externally reported issue is a sandwich-attack pattern caused by missing user-supplied slippage bounds. The analogous, reachable pattern in java-tron is TRON's own Bancor-style Exchange (TRC10/TRX AMM pools), not the Uniswap-swap mechanism itself.

## Finding Description

`ExchangeTransactionContract` (a normal trade against the pool) *does* implement slippage protection: the caller supplies `expected` (minimum output) and `ExchangeTransactionActuator.doValidate()` rejects the trade if `anotherTokenQuant < tokenExpected` [1](#0-0) .

However, `ExchangeInjectContract` and `ExchangeWithdrawContract` — which add/remove liquidity to/from the same pool and compute a *proportional counter-token amount from the pool's live ratio* — expose no equivalent bound at all. In `ExchangeInjectActuator.doValidate()`/`execute()`, `anotherTokenQuant` is derived purely from the current `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no minimum or maximum the caller can enforce: [2](#0-1) . The same is true for `ExchangeWithdrawActuator`, which likewise derives `anotherTokenQuant` from the live ratio with only a "precision" (rounding) check, not a slippage/expected-amount check: [3](#0-2) .

The `ExchangeInjectContract`/`ExchangeWithdrawContract` proto messages confirm there is no `expected`/min-out field, unlike `ExchangeTransactionContract` which explicitly carries `expected`: [4](#0-3) .

This is the direct structural analog of the reported bug class: a value-transferring, price-dependent operation is executed against whatever the pool state happens to be at execution time, with no caller-supplied guard rail against the state having moved unfavorably between transaction submission and execution — exactly the "no valid deadline/no slippage bound" pattern flagged in the report, just applied to liquidity provisioning instead of a swap.

## Impact Explanation

An attacker who can get a trade included immediately before (and, to capture profit, immediately after) a victim's `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction can manipulate the pool ratio via an `ExchangeTransactionContract` trade, causing the victim to inject (or withdraw) an unfavorable, attacker-chosen proportion of the two tokens. This directly transfers value from the exchange creator to the attacker — a theft-of-funds outcome for whoever calls inject/withdraw, since neither actuator offers any mechanism to cap the counter-token amount actually taken/returned.

## Likelihood Explanation

Both actions are restricted to the exchange's creator address (`account[...] is not creator` check) [5](#0-4) , but that creator is any ordinary account that created a token-pair exchange — not a privileged validator/witness. Any other unprivileged account can broadcast the surrounding sandwich trades via ordinary `ExchangeTransactionContract` transactions, which require no special permission. Given TRON's normal transaction ordering (no priority-fee auction), this requires only mempool-observation-based ordering luck rather than SR collusion, so it is reachable by a standard adversarial API/broadcast client.

## Recommendation

Add a caller-supplied bound to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., a minimum/maximum `anotherTokenQuant`, analogous to `expected` in `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate/execute so the transaction reverts if the pool ratio has moved beyond the caller's tolerance.

## Proof of Concept

1. Attacker observes a pending `ExchangeInjectContract` from the pool creator for pair (A, TRX) with `tokenQuant` of A.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of TRX into the pool just before the victim's tx, shifting the A/TRX ratio.
3. The creator's inject executes with the shifted ratio (see computation at `ExchangeInjectActuator.java:73-83`), causing them to deposit an unfavorable amount of the counter token relative to fair value.
4. Attacker submits a second `ExchangeTransactionContract` reversing their initial trade, extracting the value effectively transferred out of the creator's injected liquidity — all without violating any validate-time check, since no `expected`/min-out field exists for `ExchangeInjectContract`.
