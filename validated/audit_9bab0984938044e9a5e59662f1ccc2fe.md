### Title
Unbounded witness-set growth causes O(n) iteration cost in `MaintenanceManager.doMaintenance()` and `IncentiveManager.reward()` on every maintenance cycle - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`doMaintenance()` iterates over `consensusDelegate.getAllWitnesses()` — the entire `WitnessStore` — multiple times every maintenance cycle (every 6 hours, deterministically triggered inside block application in `Manager`), with no cap on the number of witnesses. Any account can add itself to this list permanently via a single `WitnessCreateContract` transaction, growing the loop bound with each new witness account created. This mirrors the reported `distributeDividends` pattern: unbounded iteration over an attacker-extensible set that executes automatically as part of core protocol processing.

### Finding Description
`MaintenanceManager.doMaintenance()` calls `consensusDelegate.getAllWitnesses()` (which returns every entry ever written into `WitnessStore`, via `Streams.stream(iterator()).collect(...)`) and iterates over the full result set in at least three separate `.forEach` loops within a single maintenance pass: [1](#0-0) [2](#0-1) [3](#0-2) 

This list is built by `WitnessStore.getAllWitnesses()` with no size bound: [4](#0-3) 

The `newWitnessAddressList` produced from the full witness set is also passed unbounded into `IncentiveManager.reward()`, which itself contains an unbounded `for` loop before trimming to `WITNESS_STANDBY_LENGTH`: [5](#0-4) 

Any account can grow this set indefinitely: `WitnessCreateActuator.execute()`/`createWitness()` is a normal, broadcastable transaction that writes a new `WitnessCapsule` into `WitnessStore` for any distinct address, subject only to paying `dynamicStore.getAccountUpgradeCost()`: [6](#0-5) [7](#0-6) 

`doMaintenance()` is invoked automatically as part of block application (through `DposService`/`Manager` consensus processing at each maintenance boundary), so this cost is not gated behind any privileged role — it fires unconditionally for every node whenever the maintenance time arrives, exactly analogous to `distributeDividends` being called on every dividend distribution regardless of who inflated the recipient list.

### Impact Explanation
As the number of witness accounts grows (each addition costs a fixed `AccountUpgradeCost`, not a growing/quadratic cost), the per-maintenance-cycle work in `doMaintenance()` and `IncentiveManager.reward()` grows linearly and unboundedly. Because this logic runs synchronously as part of consensus/block processing on every full node and every witness, sufficiently large witness counts increase the wall-clock cost of maintenance processing, threatening block-production timeliness and potentially triggering timeouts/halts during the maintenance block — a chain-liveness risk shared by all nodes simultaneously (unlike a single user's isolated transaction being slow).

### Likelihood Explanation
Likelihood is constrained by economics: each new witness costs `AccountUpgradeCost` (a fixed TRX fee on the account, not scaling with existing witness count), so an attacker with sufficient capital can add as many entries as desired at linear cost — there is no on-chain cap on total witness count. The barrier is purely financial, not protocol-enforced, so given enough funds this can be executed by a single unprivileged account without any special permissions. I could not fully verify the exact current mainnet value of `getAccountUpgradeCost()` or measure the practical breakeven point where this becomes disruptive, which limits certainty on real-world exploitability magnitude within this review.

### Recommendation
Cap the number of witnesses that can ever be registered (or cap the number processed per maintenance loop, processing the rest in later cycles/batches), similar to the `WITNESS_STANDBY_LENGTH`-based truncation already used elsewhere (e.g., `getWitnessStandby`). Alternatively, refactor `doMaintenance()`/`IncentiveManager.reward()` to only operate over the bounded "active"/"standby" witness set rather than the full unbounded `WitnessStore`.

### Proof of Concept
1. Fund an arbitrary number of accounts each with at least `AccountUpgradeCost` TRX.
2. From each account, broadcast a `WitnessCreateContract` transaction (`WitnessCreateActuator`) with a unique owner address — each succeeds since `witnessStore.has(ownerAddress)` only rejects duplicates for the same address, not a global cap.
3. Repeat to grow `WitnessStore` to an arbitrarily large size (e.g., tens of thousands of entries).
4. At the next maintenance boundary, `MaintenanceManager.doMaintenance()` calls `consensusDelegate.getAllWitnesses()` and iterates the entire set multiple times (lines 98-100, 108-109, 157-161), and `IncentiveManager.reward()` iterates the full list before truncating — increasing per-maintenance-cycle processing time proportionally to the number of created witnesses.

  private void createWitness(final WitnessCreateContract witnessCreateContract)
      throws BalanceInsufficientException {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    WitnessStore witnessStore = chainBaseManager.getWitnessStore();
    //Create Witness by witnessCreateContract
    final WitnessCapsule witnessCapsule = new WitnessCapsule(
        witnessCreateContract.getOwnerAddress(),
        0,
        witnessCreateContract.getUrl().toStringUtf8());

    logger.debug("createWitness,address[{}]", witnessCapsule.createReadableString());
    witnessStore.put(witnessCapsule.createDbKey(), witnessCapsule);
    AccountCapsule accountCapsule = accountStore
        .get(witnessCapsule.createDbKey());
    accountCapsule.setIsWitness(true);
    if (dynamicStore.getAllowMultiSign() == 1) {
      accountCapsule.setDefaultWitnessPermission(dynamicStore);
    }
    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    long cost = dynamicStore.getAccountUpgradeCost();
    adjustBalance(accountStore, witnessCreateContract.getOwnerAddress().toByteArray(), -cost);
    if (dynamicStore.supportBlackHoleOptimization()) {
      dynamicStore.burnTrx(cost);
    } else {
      adjustBalance(accountStore, accountStore.getBlackhole(), +cost);
    }
    dynamicStore.addTotalCreateWitnessCost(cost);
  }
