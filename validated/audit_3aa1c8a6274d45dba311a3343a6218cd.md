### Title
Slot version reset on signer reassignment allows replay of stale StackerDB chunks with a valid old signature - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
`StackerDBTx::reconfigure_stackerdb` resets a slot's version counter to `NO_VERSION` (0) whenever the slot's assigned signer address changes, and wipes only the *stored data*, not any memory of prior versions ever used by a signer address [1](#0-0) . Because slot ownership/freshness is validated purely by "signature recovers to the current slot signer" plus "submitted version > stored version" [2](#0-1) , once an address returns to a slot it previously held (after some other address occupied it in between), the version counter restarts from 0. This is the same bug class as the SKALE `MessageProxy` finding: resetting a monotonic replay-protection counter on remove/reconnect allows previously valid signed data to be replayed as if new.

### Finding Description
StackerDB slot freshness is enforced only by a per-slot Lamport-clock-style `version` field: a write is accepted if `slot_desc.slot_version > slot_validation.version` and the chunk's signature recovers to the slot's currently configured signer [2](#0-1) . There is no cryptographic binding between a chunk and the specific "epoch"/assignment during which it was created (e.g. no consensus-hash or reward-cycle nonce embedded in the signed payload, no monotonically-increasing counter that survives across reconfigurations for the same principal).

When the on-chain contract (or Nakamoto miner-election logic) reassigns a `slot_id` to a *different* signer, `reconfigure_stackerdb` resets that slot: `version = NO_VERSION`, `data = []`, `data_hash = 0`, `signature = empty` [3](#0-2) . `create_or_reconfigure_stackerdbs` triggers this reconfiguration path any time the computed `StackerDBConfig` signer list differs from what's currently stored [4](#0-3) . For the `.miners` StackerDB, this configuration is regenerated from `NakamotoChainState::make_miners_stackerdb_config` at essentially every sortition, alternating winners between two slots while trying to preserve each miner's relative slot position [5](#0-4) . Over a sequence of sortitions, the same miner address can vacate a slot (displaced by another miner, causing a reset for that slot) and later return to that same `slot_id` after intervening winners have occupied it — the test `test_make_miners_stackerdb_config` explicitly documents this alternating/rotating slot assignment behavior [6](#0-5) .

When a signer re-occupies a slot it previously held, `reconfigure_stackerdb` compares only against the *most recent* `existing_validation.signer`; it has no record of the slot's prior version history for that (now returning) signer, so the version resets to 0 [7](#0-6) . At that point, any historical, validly-signed chunk that this signer produced earlier (e.g. an old, stale block proposal or a superseded signer message) — which anyone on the network may have observed and archived — can be replayed:
- Signature check passes, because the address genuinely still is (again) the slot's signer [8](#0-7) .
- Freshness check passes, because the historical chunk's `slot_version` is greater than the freshly-reset `0` [9](#0-8) .

This write can be submitted by any unprivileged remote peer via the public HTTP endpoint `POST /v2/stackerdb/:principal/:contract/chunks`, which requires no authentication beyond the chunk carrying a valid signature and calls straight into `try_replace_chunk` [10](#0-9) . A successfully stored chunk is then re-broadcast to the p2p network as a `StackerDBPushChunk`, and other nodes' `validate_received_chunk`/`process_stacker_db_chunks` accept and propagate it further because their local `expected_versions` for that slot were reset the same way [11](#0-10) [12](#0-11) .

### Impact Explanation
This lets a remote, unprivileged party (re)inject stale-but-validly-signed StackerDB content (e.g. an outdated miner block proposal or signer coordination message) into the network's replicated state, where it is treated as canonical/current because it clears the (now-reset) version bar. Consumers of that StackerDB data (miners, signers) would observe non-canonical, outdated data as if it were fresh, which can steer coordination logic off the correct state — matching the "serving non-canonical state as canonical" High-impact category. It does not directly compromise consensus block validation, but it corrupts the StackerDB replication layer used for miner/signer messaging.

### Likelihood Explanation
Requires: (1) a slot signer to be evicted and later reassigned to the same slot_id after another signer occupied it (naturally occurring for `.miners`, given the alternating two-slot rotation across sortitions, and possible for `.signers-N` StackerDBs across reward cycles), and (2) an attacker or observer to have recorded a previously valid signed chunk from that signer. Both are plausible for a long-running network without requiring privileged access, node secrets, or another party's key — the "old signature" is legitimately produced by the returning signer at an earlier point and simply replayed by a third party or the signer itself.

### Recommendation
Do not rely solely on a per-slot version counter that gets wiped on signer reassignment. Either:
- Persist and continue the highest version ever seen for a given `(slot_id, signer)` pair (or globally per signer public key) rather than resetting to 0 when a signer returns to a slot, mirroring the SKALE fix of not resetting counters on reconnection; or
- Bind chunk validity to the specific StackerDB configuration epoch (e.g. include the reward-cycle/consensus-hash config epoch in the signed payload and reject chunks whose epoch does not match the current one), preventing chunks signed under an earlier assignment from being replayed under a later one for the same slot.

### Proof of Concept
1. Node observes/stores a StackerDB chunk `C = (slot_id=5, version=42, sig=Sig_A)` legitimately produced and pushed by signer `A` while `A` occupies `slot_id=5`.
2. The StackerDB contract/config reassigns `slot_id=5` to signer `B` (e.g., next sortition/reward cycle). `reconfigure_stackerdb` resets slot 5 to `version=0`, `data=empty` [3](#0-2) .
3. The configuration later reassigns `slot_id=5` back to `A` (e.g., `A` wins a subsequent sortition and the miner-slot-preservation logic in `make_miners_stackerdb_config` maps it back to slot 5). This triggers another `reconfigure_stackerdb` reset of slot 5 to `version=0`.
4. Any peer replays the previously recorded chunk `C` (`version=42`, `sig=Sig_A`) via `POST /v2/stackerdb/A/.miners/chunks`.
5. `try_replace_chunk` accepts it: `A` is again the slot signer (`BadSlotSigner` check passes) and `42 > 0` (staleness check passes) [2](#0-1) , storing and then rebroadcasting stale data as if it were the latest state for slot 5.

    /// Chunk data for slots that no longer exist will be dropped.
    /// Newly-created slots will be instantiated with empty data.
    /// If the address for a slot changes, then its data will be dropped.
    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
