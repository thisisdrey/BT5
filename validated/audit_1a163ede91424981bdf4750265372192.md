### Title
Unvalidated attacker-controlled array-length field in TVM precompile ABI decoding causes oversized allocation and node OOM - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` decode dynamic-array parameters passed to TVM precompiled contracts (e.g. `BatchValidateSign`/multi-signature precompiles) by reading a length word directly out of attacker-supplied call data and immediately allocating a Java array of that length, with no upper bound check against the actual size of the supplied `data` buffer.

### Finding Description
In `extractBytesArray` and `extractSigArray`: [1](#0-0) [2](#0-1) 
and in `extractBytes32Array`: [3](#0-2) 

`len` is computed as `words[offset].intValueSafe()` — a value taken directly from the caller-controlled `DataWord` at a caller-chosen offset in the precompile input — and is used verbatim to size `new byte[len][]`/`new byte[][]` before any bytes are actually read out of `data`. There is no check that `len` is consistent with the length of `data` (or with any energy/gas budget) prior to the allocation. Any contract call/`TriggerConstantContract`/`TriggerContract` transaction that invokes a precompile using these ABI-array decoding helpers (the multi-signature validation precompile family reachable through TVM `CALL`/precompile dispatch in `PrecompiledContracts.getContractForAddress`) can supply a crafted 32-byte length word (e.g. close to `Integer.MAX_VALUE`) to force the JVM to allocate an array of that many object references (a `byte[Integer.MAX_VALUE][]` reference array alone requires multiple gigabytes on a 64-bit JVM) before the VM's own energy metering for the actual per-signature/per-item work has a chance to reject the call.

This is the same bug class as the reported Jetty advisory (CWE-400): an externally supplied "declared size" field is trusted to drive a large allocation without validating it against the real payload size or available resources, enabling remote memory-exhaustion.

### Impact Explanation
A successful trigger can force the full node (or any node executing/estimating the transaction, including nodes serving `TriggerConstantContract`/`EstimateEnergy` JSON-RPC/gRPC/HTTP calls) to attempt a multi-gigabyte heap allocation. This can throw `OutOfMemoryError`, degrade or crash the JVM process, and in the worst case be triggered repeatedly by any anonymous API client or any address broadcasting/simulating a smart-contract call, causing node-wide denial of service. Because block validation must reproduce the same execution result, a malicious transaction embedding this crafted input could also cause OOM on the broader validating network if it enters a block, escalating from a single-node crash to a chain-wide availability problem.

### Likelihood Explanation
Reaching this code only requires crafting call data to a smart contract that eventually calls one of the affected precompiled contracts (e.g. through the batch signature validation precompile) with a manipulated dynamic-array length header — something any unprivileged contract deployer/caller can construct and submit via `TriggerSmartContract`/`TriggerConstantContract` or a deployed contract's `CALL` to the precompile address. No special privileges are needed. The main uncertainty (which could not be fully confirmed in this pass) is whether `DataWord.intValueSafe()` or an upstream energy-cost calculation for the specific precompile clamps `len` to a small bound before `execute()` is reached; this needs to be verified against `DataWord.intValueSafe()` and each precompile's `getEnergyForData` implementation to determine the exact maximum allocatable size and whether existing energy metering already prevents an outsized `len` from being processed.

### Recommendation
Bound `len` before allocation in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` — reject decoding when `len` exceeds a sane maximum (e.g. derived from the remaining size of `data`, or a fixed protocol maximum such as `MAX_UINT` of expected signer/parameter counts) prior to calling `new byte[len][]`, and ensure energy is charged proportionally to `len` before the allocation occurs rather than after.

### Proof of Concept
Not independently executed in this session; based on static analysis: submit a `TriggerConstantContract`/`TriggerSmartContract` call whose ABI-encoded parameters route through `extractBytesArray`/`extractSigArray` (e.g. a multi-signature precompile call) with the array-length word set to a large value like `0x7FFFFFFF` while the actual call-data buffer is small. Execution should attempt to allocate a reference array of that length inside `PrecompiledContracts`, causing an `OutOfMemoryError` before any bounds/energy check against the real data size is applied. Confirming the exact reachable precompile entry point and gas-check ordering requires reading `BatchValidateSign.execute()`/`getEnergyForData()` and `DataWord.intValueSafe()`, which was not completed before the tool budget was exhausted.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
