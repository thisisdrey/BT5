Audit Report

## Title
Permanent reward loss via integer-division rounding in `reward_per_token` — attacker-inflatable stake can zero out reward accrual - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` function computes the per-block reward increment as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, using Euclidean integer division with a fixed, small scaling constant (`4096`). Because `total_tokens_staked` is fully attacker-controllable via the permissionless `stake` extrinsic and no minimum stake-to-reward-rate ratio is enforced anywhere, an attacker can inflate `total_tokens_staked` enough to make this term permanently round down to zero, freezing reward accrual for the whole pool.

## Finding Description
`reward_per_token` at [1](#0-0)  computes:

```rust
pool_info.reward_rate_per_block
    .ensure_mul(rewardable_blocks_elapsed.into())?
    .ensure_mul(PRECISION_SCALING_FACTOR.into())?
    .ensure_div(pool_info.total_tokens_staked)?
```

`PRECISION_SCALING_FACTOR` is fixed at `4096` [2](#0-1) , far smaller than the large fixed-point scales (e.g. `1e18`) typically used to avoid rounding-to-zero in this exact reward-per-token pattern. If `reward_rate_per_block * blocks_elapsed * 4096 < total_tokens_staked`, the division truncates to `0`.

Once this happens, `update_pool_rewards` unconditionally advances `last_update_block` to the current block and stores the (zero) increment [3](#0-2) , with no accumulator/remainder carried forward — the reward for that window is permanently lost, not merely deferred.

`total_tokens_staked` is fully attacker-controllable: `stake` is a permissionless, unprivileged extrinsic with no minimum/maximum bound on `amount` [4](#0-3) , and neither `create_pool` [5](#0-4)  nor `set_pool_reward_rate_per_block` enforces any minimum ratio between `reward_rate_per_block` and plausible `total_tokens_staked`. Note pool creation/admin management is documented as permissioned (`Currently, pool creation and management restricted to a configured Origin`) [6](#0-5) , but `stake` itself remains open to any signed account holding the staked asset, which is the actual attack surface — no admin/governance action is required to trigger the rounding condition, only ordinary staking by a holder of the staked asset.

## Impact Explanation
This matches the "permanent user-fund lock" impact category: reward tokens already deposited into the pool account become permanently unclaimable by legitimate stakers once `reward_per_token_stored` stops advancing, since accrual state is discarded each update with no fixed-point remainder tracking. The condition is triggerable by a single unprivileged extrinsic call (`stake`) from any account holding a sufficiently large balance of the pool's staked asset, without requiring governance, validator, or admin compromise.

## Likelihood Explanation
Feasibility depends on the staked asset's available supply relative to `reward_rate_per_block * 4096`. Because `PRECISION_SCALING_FACTOR` is fixed at a small constant rather than scaled to the asset's decimals or to `reward_rate_per_block`, pools using higher-decimal assets (e.g. 18-decimal tokens) or pools configured with modest reward rates are easily driven into the rounding-to-zero regime by staking a realistic amount of the asset — no artificial supply inflation is needed, just ordinary large-scale staking. No code path in `create_pool`, `stake`, or `set_pool_reward_rate_per_block` validates or bounds this ratio.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to a much larger fixed-point scale (comparable to `1e18`)-style precision, and/or track and carry forward the truncated remainder in `reward_per_token`/`update_pool_rewards` instead of discarding it, and/or enforce a minimum `reward_rate_per_block`-to-`total_tokens_staked` ratio when accepting new stakes so accrual cannot silently round to zero across a distribution window.

## Proof of Concept
1. Admin creates a pool via `create_pool` with `reward_rate_per_block = R` on staked asset `X` [7](#0-6) .
2. A staker calls `stake(pool_id, amount)` with `amount` such that `R * 4096 < total_tokens_staked` after staking [8](#0-7) .
3. Subsequent calls to `reward_per_token` compute `R * blocks_elapsed * 4096 / total_tokens_staked = 0` due to integer truncation [9](#0-8) .
4. `update_pool_rewards` advances `last_update_block` while `reward_per_token_stored` stays unchanged [10](#0-9) , permanently losing that window's reward for all stakers, while deposited reward-asset funds remain stranded in the pool account.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}
