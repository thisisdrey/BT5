### Title
Unrestricted initial reserve ratio in `ExchangeCreateContract` allows first-pool price manipulation - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator` lets any account with sufficient balance create a bancor-style token-pair pool (`ExchangeCreateContract`) while setting the two initial reserves (`firstTokenBalance`, `secondTokenBalance`) to any values, with the only checks being `> 0` and `< exchangeBalanceLimit()`. This is the on-chain equivalent of the ERC4626 "first depositor sets price per share" bug: the entity that creates the pool fully controls its initial exchange rate, and can pick an arbitrarily skewed ratio (e.g. `firstTokenBalance = 1`, `secondTokenBalance = balanceLimit`) with no minimum-liquidity or 1:1 sanity constraint.

### Finding Description
`doValidate()` in `ExchangeCreateActuator` only enforces: [1](#0-0) 
i.e. the two token IDs differ, both balances are `> 0`, and both are below `dynamicStore.getExchangeBalanceLimit()`. There is no requirement that the ratio be reasonable, no minimum absolute reserve, and no check tying the initial ratio to any external price reference. `execute()` then simply stores whatever ratio was supplied as the pool's live price: [2](#0-1) 

This ratio directly parameterizes the bancor relay curve used by every subsequent trade in `ExchangeCapsule.transaction()` / `ExchangeProcessor.exchange()`: [3](#0-2) 
Because the curve computation is driven directly by `sellTokenBalance`/`buyTokenBalance` (the reserves the creator freely chose), an attacker can create a pool with an extremely lopsided ratio (e.g. 1 unit of token A against the maximum allowed amount of token B) to set an artificial, arbitrary "price" for the pair from the very first block the pool exists — exactly analogous to the ERC4626 report's "first vault deposit sets an arbitrary price-per-share" issue, since there's no floor/anchor and no minimum initial liquidity requirement.

### Impact Explanation
Once the skewed pool exists, `ExchangeInjectContract` (liquidity injection) computes the paired amount proportionally from the attacker-chosen ratio: [4](#0-3) 
so any third party who injects liquidity into the pool (e.g. believing it reflects a real market price, or via UI/tooling that doesn't verify reserves) locks in value at the attacker's fabricated exchange rate, which the creator can then extract by trading against the pool. Unsuspecting traders using `ExchangeTransactionContract` are also exposed to an artificial price for that pair unless they explicitly set `expected` tight enough (`tokenExpected`, checked at `ExchangeTransactionActuator.java:219`) — many wallets/relayers may not do this by default. This can result in unauthorized value transfer (theft) from later liquidity providers/traders to the pool creator, which meets the "concrete unauthorized... theft... of funds" bar.

### Likelihood Explanation
This requires only a single signed `ExchangeCreateContract` transaction from any funded account (no special privilege), making it fully reachable by an unprivileged transaction broadcaster. The attack is cheap: the attacker need only supply the calcFee() cost and a small quantity of one token (as little as `1`) plus a larger amount of another token they control (up to `exchangeBalanceLimit()`), which for TRX/TRC10 tokens the attacker fully controls the denomination of. The main mitigating factor is that other participants using slippage protection (`expected`) are not directly harmed on a single trade — the primary victims are those who add liquidity via `ExchangeInjectContract` without validating current reserves.

### Recommendation
Add a minimum-reserve / minimum-ratio sanity check in `ExchangeCreateActuator.doValidate()`, e.g. require both `firstTokenBalance` and `secondTokenBalance` to be above a protocol-defined minimum (comparable to Uniswap/Solmate's `MINIMUM_LIQUIDITY` concept), and/or require the creator to lock a portion of the initial "shares"/reserves permanently so the ratio cannot be trivially set and then unwound. At minimum, document that `ExchangeInjectContract` callers and wallets must independently validate pool reserves before injecting liquidity, since the create-time ratio is fully attacker-controlled.

### Proof of Concept
1. Attacker (any funded account) issues a TRC10 token `X` and holds all supply.
2. Attacker broadcasts `ExchangeCreateContract` with `first_token_id = "_"` (TRX), `first_token_balance = 1` (1 sun), `second_token_id = X`, `second_token_balance = 1` (validated only by `firstTokenBalance <= 0 || secondTokenBalance <= 0` and the `exchangeBalanceLimit()` upper bound — see `ExchangeCreateActuator.java:201-208`), effectively fixing an artificial 1:1 (or any chosen ratio) TRX/X price regardless of X's real value.
3. A third party calls `ExchangeInjectContract` to add liquidity, and `ExchangeInjectActuator` computes the paired amount using the attacker's fabricated ratio (`ExchangeInjectActuator.java:71-83`), locking the third party's assets in at the fake rate.
4. Attacker then trades against the pool via `ExchangeTransactionContract`, extracting the injected value at the manipulated rate. [5](#0-4) [4](#0-3)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
