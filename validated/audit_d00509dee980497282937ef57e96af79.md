### Title
Exchange (Bancor-style) pool injection rounds down the required paired-token amount, letting the injector under-fund the pool and skew the price invariant - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator`, reachable via a normal `ExchangeInjectContract` broadcast by any account that is the creator of a TRC10 exchange pair, computes the counter-token amount (`anotherTokenQuant`) that must be deposited together with the injected token using floor/truncating integer division in both `doValidate()` and `execute()`. This mirrors the reported bug class: a value the protocol/pool should receive is calculated with a rounding mode that favors the payer (round-down) instead of rounding up in the protocol's favor, causing the pool's invariant ratio to be under-collateralized on every injection.

### Finding Description
In `execute()`: [1](#0-0) 
`anotherTokenQuant` is computed with `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (or the symmetric branch), which truncates toward zero/down.

The same truncating computation is repeated in `doValidate()`: [2](#0-1) 
using `BigInteger.divide()` (also floor for positive operands), so validation and execution agree on the rounded-down value.

The exact amount required to keep the pool's implied price ratio `firstTokenBalance / secondTokenBalance` unchanged after injecting `tokenQuant` of one side is `secondTokenBalance * tokenQuant / firstTokenBalance` computed without truncation. Because the code always floors this division, the injector deposits strictly less than the exact proportional amount whenever the division has a remainder. The pool balances are then updated with the under-funded amount: [3](#0-2) 
so `newSecondTokenBalance` (or `newFirstTokenBalance`) is smaller than the value needed to preserve the pre-injection ratio, permanently shifting the on-chain price used by every subsequent `ExchangeTransactionActuator` trade and `ExchangeWithdrawActuator` withdrawal against that pool: [4](#0-3) 

This is functionally the same class of defect as the reported issue: a value flowing *into* the protocol-controlled pool is truncated instead of rounded up, so the party providing the funds (the injector) systematically contributes fractionally less than required, while the pool (and, transitively, other traders/withdrawers who rely on its stored balances as the price oracle) absorbs the shortfall.

### Impact Explanation
Every `ExchangeInjectContract` call that produces a non-exact division skews the exchange's stored `firstTokenBalance`/`secondTokenBalance` ratio slightly in favor of the injector. Because `ExchangeTransactionActuator` and `ExchangeWithdrawActuator` both use these stored balances as the sole price/liquidity reference for all subsequent trades and withdrawals, repeated or large-value injections accumulate a persistent, protocol-level accounting drift that misprices the pool relative to its true backing, which is a fund-accounting integrity issue for the on-chain AMM state (not merely a cosmetic rounding artifact). This matches the "Medium" classification used in the original report: no single call is catastrophic, but the systemic under-funding accrues over time and corrupts the exchange's invariant that other users' trades/withdrawals depend on.

### Likelihood Explanation
The path is reached by any account that created an exchange pair (an ordinary, unprivileged "asset issuer"/liquidity-provider role, not an SR/witness/committee role) simply broadcasting a normal `ExchangeInjectContract` transaction with a `tokenQuant` chosen such that `secondTokenBalance * tokenQuant` is not evenly divisible by `firstTokenBalance` — a condition that is trivial to construct and will occur naturally in the vast majority of injections given arbitrary pool balances.

### Recommendation
When computing `anotherTokenQuant` for `ExchangeInjectContract` in both `doValidate()` and `execute()` of `ExchangeInjectActuator.java`, round the division up (ceiling) instead of truncating, so the injector is required to contribute at least the exact proportional amount needed to preserve (or slightly increase) the pool's invariant ratio, consistent with the general principle that amounts flowing into protocol-held reserves should round in the protocol's favor.

### Proof of Concept
1. Create an exchange pair via `ExchangeCreateContract` with `firstTokenBalance = 3`, `secondTokenBalance = 10` (ratio 10/3).
2. As the pool creator, broadcast `ExchangeInjectContract` with `tokenID = firstTokenID`, `tokenQuant = 1`.
3. `ExchangeInjectActuator.execute()` computes `anotherTokenQuant = floorDiv(10 * 1, 3) = 3` (exact value would be `10/3 = 3.33`, i.e. it should require ceil = 4 to keep the ratio non-decreasing). [5](#0-4) 
4. New balances become `firstTokenBalance = 4`, `secondTokenBalance = 13`, giving a new ratio `13/4 = 3.25`, lower than the original `10/3 ≈ 3.33`. The injector has permanently diluted the pool's second-token backing relative to the first token by less than the exact proportional contribution, and this discrepancy compounds with every subsequent injection that hits a non-exact division.
