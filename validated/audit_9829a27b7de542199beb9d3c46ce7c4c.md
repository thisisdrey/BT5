### Title
Non-deterministic Bancor-style exchange math (`Math.pow` vs `StrictMath.pow` on x86 vs ARM64) can desynchronize node state on `ExchangeTransactionContract` execution - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The core TRX/TRC10 Bancor-relay swap math used by `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` still supports (and defaults to, unless a committee proposal enables `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION`) a legacy floating-point code path whose `pow()` implementation is architecture-dependent: on x86_64 it calls `java.lang.Math.pow` (JIT/hardware intrinsic), on ARM64 it calls `StrictMath.pow` with a static table of pre-computed historical corrections for known mainnet block inputs only. Any new/unrecorded `(base, exponent)` combination on ARM64 falls back to `StrictMath.pow`, which is not guaranteed to be bit-identical to the hardware `Math.pow` used on x86_64 nodes.

### Finding Description
`ExchangeCapsule.transaction()` selects the swap processor based on the `allowHarden`/`hardenedCalc` flag: [1](#0-0) . When not hardened, it uses `ExchangeProcessor`, whose Bancor-style relay math computes `Math.pow` through a platform-selectable wrapper: [2](#0-1) [3](#0-2) .

The `MathWrapper` class is compiled per architecture from separate source trees selected at build time (`archSource = isArm64 ? "arm" : "x86"`): [4](#0-3) . On x86_64, `pow()` is a direct call to `java.lang.Math.pow` (hardware/JIT intrinsic): [5](#0-4) . On ARM64, `pow()` looks up historical `(a, b)` pairs recorded from known past mainnet blocks and only falls back to `StrictMath.pow` (fdlibm software algorithm) for anything not in that hardcoded table: [6](#0-5) . `Math.pow` (hardware/library intrinsic) and `StrictMath.pow` (portable fdlibm) are not guaranteed to produce bit-identical `double` results for all inputs — this is exactly why the codebase introduced `StrictMathWrapper` and marked the old `Maths`/`MathWrapper` classes `@Deprecated` with the comment "for cross-platform consistency, please use `StrictMathWrapper` instead": [7](#0-6) . The project's own unit test explicitly demonstrates that legacy (non-strict) and strict/safe computations diverge for real inputs: [8](#0-7) .

`ExchangeTransactionActuator.execute()`/`validate()` pass `dynamicStore.allowStrictMath()` and `allowHarden()` straight into `exchangeCapsule.transaction(...)`, and the resulting `anotherTokenQuant` directly mutates account balances/asset amounts and is persisted to the exchange capsule store: [9](#0-8) . This is reachable by any unprivileged account that broadcasts a signed `ExchangeTransactionContract`, `ExchangeInjectContract` (for the swap portion) — no special privilege is required, only an existing bancor-style Exchange and sufficient balance.

Because the ARM64/x86_64 split, `useStrictMath` flag, and hardened `SafeExchangeProcessor` (BigDecimal-based) all exist specifically to fix a **known historical determinism problem** in this exact code path, the underlying risk is real: whenever `ALLOW_STRICT_MATH` and `ALLOW_HARDEN_EXCHANGE_CALCULATION` are not both active (i.e., default/newly-bootstrapped chains, private/consortium chains, or any period before the corresponding committee proposal is passed on a given network), an attacker who crafts an `ExchangeTransactionContract` with a `(balance, quant)` pair that is *not* present in ARM64's hardcoded correction table can cause ARM64 full nodes to compute a different `anotherTokenQuant` than x86_64 full nodes processing the identical transaction/block. Since this value updates account balances/asset supply and is part of consensus state, the two architectures would diverge in their resulting state root for the same block — a consensus/chain split between heterogeneous-architecture validators (or between a witness on one architecture and a syncing node on the other) — without requiring any malicious SR/witness behavior, purely from ordinary user activity.

### Impact Explanation
If mixed-architecture nodes (which the project explicitly supports and documents, requiring separate JDK 8/x86 vs JDK 17/ARM64 builds) diverge on this deterministic computation for a single ordinary transaction, they will produce different post-state (balances/asset totals) for the same block, leading to a chain split among honest, non-malicious nodes/validators. This is exactly the class of impact the scope permits ("chain split"). It also risks an "unbacked balance" condition (one architecture's ledger diverges from the true swap output), which the scope also explicitly allows.

### Likelihood Explanation
Likelihood is Medium: exploitation only manifests when a real, deployed network runs both x86_64 and ARM64 full nodes without both `ALLOW_STRICT_MATH` and `ALLOW_HARDEN_EXCHANGE_CALCULATION` fully active, and requires the attacker to find/craft `(balance, quant)` combinations outside ARM64's hardcoded correction list where `Math.pow` and `StrictMath.pow` diverge at the precision level that changes the final `long` truncation of `exchangeToSupply`/`exchangeFromSupply`. This is plausible given ARM64 support is comparatively new (documented as introduced in GreatVoyage-v4.8.1) and mainnet's historical correction table only covers pre-existing recorded blocks, not future/novel inputs. I was not able to confirm from the index whether `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION` are already permanently activated on TRON mainnet in this codebase version (their default values and current activation status could not be conclusively verified from the available file contents), which affects real-world exploitability today.

### Recommendation
- Make `StrictMathWrapper`/`SafeExchangeProcessor` (BigDecimal-based, deterministic) the unconditional, non-optional code path for exchange swap math, removing the legacy `Math.pow`-based `ExchangeProcessor`/`MathWrapper` fallback entirely rather than gating it behind a committee-activated flag.
- If backward compatibility requires keeping the legacy path for historical replay, ensure it is only reachable for blocks strictly older than the hard-fork activation height, and reject any new transaction from using the non-strict path once `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION` exist as a proposal (i.e., default them to enabled and disallow disabling).
- Add cross-architecture consensus tests that feed random/edge-case `(balance, quant)` pairs into both the x86 and ARM `MathWrapker.pow` implementations and assert exact bit-for-bit `long` output equality with `StrictMathWrapper`, to catch divergences before mainnet deployment.

### Proof of Concept
1. Deploy or use an existing TRC10 Bancor-style Exchange (`ExchangeCreateContract`) with non-trivial first/second token balances.
2. Ensure network has `ALLOW_STRICT_MATH = 0` and `ALLOW_HARDEN_EXCHANGE_CALCULATION = 0` (default/non-activated state) — verified via `DynamicPropertiesStore.allowStrictMath()`/`allowHarden()` gating in `ExchangeTransactionActuator.execute()` [10](#0-9) .
3. Run one full node compiled for x86_64 (using `platform/src/main/java/x86/.../MathWrapper.java`) and one for ARM64 (using `platform/src/main/java/arm/.../MathWrapper.java`) against the same chain.
4. Broadcast an `ExchangeTransactionContract` with a `(firstTokenBalance, secondTokenBalance, quant)` triple not present in the ARM64 hardcoded `powData` table (i.e., any pool state/quantity combination novel relative to the mainnet-block-derived corrections list in `arm/.../MathWrapper.java`).
5. Compare `ExchangeCapsule.getFirstTokenBalance()`/`getSecondTokenBalance()` and the resulting account asset balances on both nodes after executing the same block — as demonstrated by `ExchangeProcessorTest.testStrictMath`, legacy (`Math.pow`) and strict (`StrictMath.pow`) results for identical inputs are `assertNotEquals` in general [8](#0-7) , confirming the two architectures compute different final balances for the same transaction, i.e., a state/consensus divergence.
