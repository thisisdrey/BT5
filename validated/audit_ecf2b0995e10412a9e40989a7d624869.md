### Title
Unbounded `sock.read_to_end` in `run_http_request` allows single malicious HTTP response to exhaust signer memory - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` in `libsigner/src/http.rs` reads an entire HTTP response into memory via `sock.read_to_end(&mut buf)` with no size cap before any header/status/Content-Length validation occurs. A malicious StackerDB host that the signer's `StackerDBSession` is configured to query can stream an arbitrarily large body, forcing the signer process to buffer unbounded data in memory before `decode_http_response`/`decode_http_body` or the `get_latest_chunks` size-limit check ever run.

### Finding Description
`run_http_request` (`libsigner/src/http.rs:221-262`) writes the request, then calls `sock.read_to_end(&mut buf)?` at line 251 with no bound on `buf`'s growth — this happens before `decode_http_response` is invoked at line 253. [1](#0-0) 

`decode_http_response` (lines 134-194) does short-circuit on non-200 status codes at lines 142-145, but that check only fires *after* `read_to_end` has already fully buffered whatever the peer sent — the status-code check cannot bound the read because the read happens first. [2](#0-1) 

For the non-chunked path, `decode_http_body` (lines 197-217) does `buf.to_vec()` with no length check against `MAX_MESSAGE_LEN` at all — only the chunked path enforces `MAX_MESSAGE_LEN` via `HttpChunkedTransferReader`. [3](#0-2) 

Downstream, `StackerDBSession::get_latest_chunks` (`libsigner/src/session.rs:230-262`) only checks `body_bytes.len() > limit` after `self.rpc_request(...)` returns, i.e., after the full body has already been read into memory by `run_http_request`; oversized chunks are merely discarded (set to `None`), not prevented from being buffered. [4](#0-3) 

A malicious StackerDB host (the peer that `StackerDBSession.host` is configured to query) can respond with `HTTP/1.1 200 OK\r\nContent-Length: <small-or-huge>\r\n\r\n` followed by an arbitrarily large stream of bytes (Content-Length can even be lied about, since it is never checked against actual bytes read); `read_to_end` will keep growing `buf` until the socket closes or memory is exhausted. No guard in this repo (`MAX_MESSAGE_LEN`, `MAX_HTTP_HEADER_LEN`, or the 200-status check) intercepts this because they all execute after the unbounded read completes.

### Impact Explanation
A single malicious/misbehaving StackerDB host response can force unbounded memory allocation on the signer's client-side polling loop (`StackerDBSession::get_latest_chunks`/`get_chunks`/`list_chunks`/`put_chunk`, all of which route through `run_http_request`), leading to memory exhaustion and process crash/DoS of the signer. This matches the Critical category ("remote crash/unauthenticated DoS from few messages").

### Likelihood Explanation
The precondition is that the attacker controls (or has compromised) the node that a signer's `StackerDBSession` is configured to query for a given StackerDB replica — this is a remote, reachable client-loop interaction requiring no secret, no privileged role, and no local access; it only requires the attacker's node to be one that a signer legitimately connects to for StackerDB sync (e.g., a Stacks node or peer signer's replica endpoint). The attack is trivially repeatable on every poll cycle and costs the attacker only bandwidth to stream data (not connection-flooding, so it is not the excluded "volumetric DDoS/bandwidth flooding" class — it's a single malicious response exploiting the absence of a read-size cap in the client's HTTP decoding logic itself).

### Recommendation
Enforce a maximum read size in `run_http_request` independent of the wire-declared Content-Length, e.g., wrap `sock` in a limited reader (bounded by `MAX_MESSAGE_LEN` or the StackerDB max chunk size) before calling `read_to_end`, and validate any `Content-Length` header against that same cap prior to reading the body. Apply an equivalent cap to the non-chunked branch of `decode_http_body` (currently only the chunked branch enforces `MAX_MESSAGE_LEN`).

### Proof of Concept
```rust
// libsigner/src/tests/http.rs (concept)
use std::io::Write;
use std::net::TcpListener;
use std::thread;

#[test]
fn test_unbounded_read_to_end_dos() {
    let listener = TcpListener::bind("127.0.0.1:0").unwrap();
    let addr = listener.local_addr().unwrap();

    let handle = thread::spawn(move || {
        let (mut stream, _) = listener.accept().unwrap();
        // consume the request
        let mut discard = [0u8; 4096];
        let _ = stream.read(&mut discard);
        // send headers claiming a small Content-Length, then keep streaming far more
        stream.write_all(b"HTTP/1.1 200 OK\r\nContent-Length: 10\r\n\r\n").unwrap();
        let chunk = vec![b'A'; 1024 * 1024]; // 1MB chunk
        loop {
            if stream.write_all(&chunk).is_err() {
                break; // stop once test aborts / connection closes
            }
        }
    });

    let mut sock = std::net::TcpStream::connect(addr).unwrap();
    // run_http_request will call sock.read_to_end(&mut buf) unboundedly here;
    // assert process memory grows without bound / test times out or OOMs,
    // demonstrating no cap is applied before decode_http_response/decode_http_body run.
    let result = libsigner::http::run_http_request(&mut sock, "127.0.0.1", "GET", "/", None, &[]);
    // In a fixed implementation, this should return an error (e.g., body too large)
    // instead of hanging/allocating unbounded memory.
    assert!(result.is_err());
}
```
The crash/assertion site is `libsigner/src/http.rs:251` (`sock.read_to_end(&mut buf)`), which has no size cap and executes before any status-code, header, or `MAX_MESSAGE_LEN` check.
