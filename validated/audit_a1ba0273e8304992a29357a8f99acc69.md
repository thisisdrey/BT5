### Title
Missing contract-domain binding in `SlotMetadata::auth_digest()` allows cross-StackerDB chunk replay to a different `.signers` contract sharing the same slot-owner address - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` binds only `(slot_id, slot_version, data_hash)` and never the `smart_contract_id`, so a signature valid for slot `S` in StackerDB contract `A` is byte-for-byte valid for slot `S` in any other StackerDB contract `B` where the owner address happens to be the same. In the shipped `.signers-{0,1}-{0..N}` design, all per-message-type StackerDB contracts for a given signer set derive their slot→address mapping from the same shared `stackerdb-signer-slots-{0,1}` list, so the same signer address legitimately owns slot `S` in every one of those contracts simultaneously - making this collision the normal, not the exceptional, case.

### Finding Description
`SlotMetadata::auth_digest()` computes `SHA512/256(slot_id || slot_version || data_hash)` [1](#0-0) , and both `SlotMetadata::sign`/`verify` and `StackerDBChunkData::recover_pk`/`verify` use only this digest [2](#0-1) [3](#0-2) . The `smart_contract_id` is never mixed into what is signed.

`StackerDBs::try_replace_chunk` looks up `slot_validation.signer` for the *specific* `(smart_contract, slot_id)` pair via `get_slot_validation`, then calls `slot_desc.verify(&slot_validation.signer)` [4](#0-3) . This check only confirms the recovered pubkey-hash equals the owner address configured for *that* contract/slot pair - it does not confirm the signature was produced with the *intent* of authorizing that particular contract, because the contract id never entered the signed payload.

Slot ownership assignment is contract-specific in the DB schema (`get_slot_signer`/`get_slot_validation` are keyed by `stackerdb_id`) [5](#0-4) , but the *value* assigned to slot `S` across different contracts can be (and, for `.signers` contracts, by design routinely is) identical. The boot contract `.signers` stores one shared page (`stackerdb-signer-slots-0`/`-1`) that every per-message-type contract (`signers-{0,1}-{0..N}`, one per `MessageSlotID`) reads via `stackerdb-get-signer-slots-page`, giving every message-type contract in a signer set an identical slot-index→address mapping [6](#0-5) . This is exercised in `signers_db_get_slots`, which asserts the same signer/slot tuple list is returned for every `message_id` in `0..SIGNER_SLOTS_PER_USER` [7](#0-6) .

Exploit flow for an unprivileged remote peer:
1. Attacker observes (via the public `GET /v2/stackerdb/...` RPC or via P2P gossip) a validly-signed `StackerDBChunkData{slot_id: S, slot_version: V, sig, data}` published by signer `X` into contract `A` (e.g. `.signers-0-3`).
2. Attacker resends the identical bytes via `POST /v2/stackerdb/<addr>/<contract-B>/chunks` targeting a different contract `B` (e.g. `.signers-0-7`) in which slot `S` is also owned by `X`, as handled by `RPCPostStackerDBChunkRequestHandler::try_handle_request` → `tx.try_replace_chunk(&contract_identifier_B, ...)` [8](#0-7) .
3. `try_replace_chunk` looks up `slot_validation.signer` for contract `B`, finds it equals `X` (same as contract `A`), and `slot_desc.verify(&slot_validation.signer)` succeeds because the digest never referenced contract `A` vs `B` [9](#0-8) .
4. If `B`'s current slot version for `S` is below `V`, the chunk is accepted, stored, and relayed as a legitimate `StackerDBPushChunk` for contract `B` [10](#0-9) , even though `X` never signed anything binding that data to contract `B`.

Existing guards that fail to stop this: the signature check (bound to owner address, not contract), the chunk-size cap, and the staleness/version check (`slot_version <= slot_validation.version`) only prevent *downgrade* replay within the same contract, not cross-contract replay when the target contract's version counter for slot `S` is lower (which is common right after a new signer-message contract for a new reward cycle is deployed with version reset to 0).

### Impact Explanation
An unauthenticated/unauthorized write is made to a StackerDB contract that the signer never intended to authorize with that specific signature - the "ownership" invariant (stored chunk's recovered signer == this contract's configured owner *and* that owner intended this specific contract to receive this content) is broken because contract binding is absent from the signed payload. This lets any remote observer (no private key needed - just a copy of a publicly-visible chunk) inject a message of one type/context into another `.signers-N-*` contract's slot, which is stored and relayed network-wide as though it were freshly authorized for that contract. This matches the Critical category "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data," since the write is accepted purely on the strength of a signature that never bound the target contract.

### Likelihood Explanation
Preconditions: the target contract's current slot version for `S` must be lower than the replayed chunk's version (trivially true for a freshly-instantiated `.signers-N-M` contract, e.g. at the start of a new reward cycle, or for message-type slots that are rarely written to). The attacker needs no privileged role, no RPC secret, and no private key - only the ability to fetch a public chunk (RPC `GET` or gossip) and POST/relay it to a different contract, both of which are reachable by any remote unprivileged peer. This is fully repeatable per (contract-pair, slot, valid-old-chunk) tuple as long as the version-ordering precondition holds.

### Recommendation
Bind the `smart_contract_id` (and ideally a network/chain identifier) into `SlotMetadata::auth_digest()` so that a signature is only valid for the specific StackerDB contract it targets; alternately, pass the `smart_contract_id` into `sign`/`verify`/`recover_pk` and hash it alongside `slot_id`, `slot_version`, and `data_hash`. This requires a wire-format/protocol version bump since it changes what signers must sign.

### Proof of Concept
Rust test in `stackslib/src/net/stackerdb/tests/db.rs`:
1. Create two `StackerDBs` contracts, `A = QualifiedContractIdentifier(issuer, "db-a")` and `B = QualifiedContractIdentifier(issuer, "db-b")`, both configured via `create_stackerdb`/`reconfigure_stackerdb` with slot 0 owned by the same address `X` (derived from a single `StacksPrivateKey`).
2. Build a `StackerDBChunkData{slot_id: 0, slot_version: 1, data: b"hello".to_vec()}`, sign it with `X`'s private key (`sign`), and call `tx.try_replace_chunk(&A, &chunk.get_slot_metadata(), &chunk.data)` - expect `Ok(())`.
3. Take the *same* `chunk` object (same `sig`, `slot_id`, `slot_version`, `data`) and call `tx.try_replace_chunk(&B, &chunk.get_slot_metadata(), &chunk.data)`.
4. Assert the current (buggy) behavior returns `Ok(())` (i.e., it is accepted into `B` despite never being signed "for" `B`), rather than `Err(net_error::BadSlotSigner(..))`, demonstrating the cross-contract replay.

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
