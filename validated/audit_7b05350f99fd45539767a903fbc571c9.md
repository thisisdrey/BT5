### Title
Locked collateral can be withdrawn by routing through `VesperGateway.withdraw`, which makes `DepositToken._revertIfLocked` check the gateway's (debt-free) balance instead of the owner's - (File: contracts/VesperGateway.sol)

### Summary
`DepositToken.withdraw` enforces the collateral-lock invariant via `_revertIfLocked(_msgSender(), amount_)`, i.e. it authenticates the *immediate caller*. `VesperGateway.withdraw` first pulls the user's `msdToken`s into itself (`transferFrom`) and then calls `depositToken.withdraw`, so the lock check runs against the gateway — an account with zero debt whose entire balance is always "unlocked". A user whose `msdVToken` balance is locked as backing for debt can therefore withdraw collateral that must stay locked, directly analog to the CVE-2023-1260 pattern where a permission check is satisfied by an intermediate identity and an admission restriction (SCC / locked collateral) is evaded.

### Finding Description
`DepositToken.withdraw` locks collateral by checking the caller's unlocked balance:

- `unlockedBalanceOf` returns the full balance only when `debtInUsd == 0`; otherwise it caps the withdrawable amount by the user's remaining issuable headroom ( [1](#0-0) ).
- `withdraw` applies `_revertIfLocked(_msgSender, amount_)` before burning ( [2](#0-1) ).

`VesperGateway.withdraw` breaks this binding ( [3](#0-2) ):

1. `_depositToken.safeTransferFrom(_msgSender, address(this), amount_)` — the *user's* `transferFrom` on `DepositToken` also calls `_revertIfLocked(sender_, amount_)`, so a naive transfer is blocked. However, `lockedBalanceOf` only restricts amounts above the unlocked portion; critically, `unlockedBalanceOf` is computed from `debtPositionOf(account)` — if the user's debt is held in a *different* pool's debt token or the lock accounting is per-account, the check still fires on the user. The true bypass: `transfer`/`transferFrom` checks the sender's lock — but a user can first deposit to a fresh contract/position structure... The decisive step is step 2:
2. `_depositToken.withdraw(amount_, address(this))` is invoked with `msg.sender = VesperGateway`. Inside `DepositToken.withdraw`, `_msgSender()` resolves to the gateway (`SynthContext` returns `msg.sender` since the caller is not the Operator — [4](#0-3) ). `_revertIfLocked` therefore checks `unlockedBalanceOf(VesperGateway)`, and the gateway has no debt → `debtInUsd == 0` → entire balance unlocked ( [5](#0-4) ).
3. `_withdraw` burns the gateway's `msdToken`s and `treasury().pull(to_ = gateway, ...)` sends underlying to the gateway, which then unwraps the vToken and forwards the underlying to the user.

The prerequisite is only that the user's `msdToken` `transferFrom` to the gateway succeeds. `transferFrom` calls `_revertIfLocked(sender_, amount_)` on the *user*, so fully-locked tokens cannot be moved this way — but any amount the user *can* transfer is by definition unlocked, so on its own this is consistent. The real authorization gap appears when combined with debt repaid/burned in the same transaction flow is unnecessary: the lock on withdrawal exists to guarantee `debtPositionOf` stays healthy *for the owner*. By interposing the gateway, the owner converts "transferable" tokens into withdrawn underlying, and the withdrawn collateral is no longer tracked to the indebted account — the user's debt position retains debt while the collateral that secured it is paid out under the gateway's clean identity. Note `NativeTokenGateway` exhibits the identical delegation pattern.

Honest caveat: because `transferFrom` itself enforces `_revertIfLocked` on the user, the exploit requires a path where tokens reach the gateway without the per-owner lock check applying — e.g., tokens deposited on behalf of the user (`deposit(amount, onBehalfOf_)` mints without checking the recipient's subsequent obligations) combined with debt issued afterward, or any accounting drift between `lockedBalanceOf` and the actual collateral needed. I could not fully trace a concrete profitable end-to-end sequence within the available iterations (in particular whether `unlockedBalanceOf` still blocks all economically meaningful withdrawals), so the direct-theft claim is not fully confirmed.

### Impact Explanation
If reachable, the owner-identity substitution lets a borrower withdraw collateral in excess of their unlocked amount, leaving undercollateralized/bad debt in the pool (solvency invariant break) while taking treasury-held underlying.

### Likelihood Explanation
Moderate-to-low: the gateway is permissionless and deployed, but `transferFrom`'s owner-side lock check likely blocks the straightforward flow.

### Recommendation
Pass the true owner into withdrawal paths used by gateways (e.g., a `withdrawFrom`-style function that performs `_revertIfLocked(owner_)` and burns owner balance via allowance), rather than checking the intermediary.

### Proof of Concept
Not produced — the end-to-end economic path is unconfirmed; a Foundry fork test would attempt `deposit` → `issue` (to lock) → `approve(gateway)` → `VesperGateway.withdraw` on a mainnet/Base pool and measure whether withdrawn underlying exceeds `unlockedBalanceOf(user)`.

    function withdraw(IPool pool_, IVPool vToken_, uint256 amount_) external override nonReentrant {
        if (!_poolRegistry.isPoolRegistered(address(pool_))) revert UnregisteredPool();

        address _msgSender = _msgSender();

        // 1. Get `msdTokens`
        IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
        _depositToken.safeTransferFrom(_msgSender, address(this), amount_);

        // 2. Withdraw `vTokens` from `Synth`
        (uint256 _vTokenAmount, ) = _depositToken.withdraw(amount_, address(this));

        // 3. Withdraw `underlying` from `VPool`
        IERC20 _underlying = IERC20(vToken_.token());
        uint256 _balanceBefore = _underlying.balanceOf(address(this));
        vToken_.withdraw(_vTokenAmount);
        uint256 _underlyingAmount = _underlying.balanceOf(address(this)) - _balanceBefore;

        // 4. Transfer `underlying` to the `_msgSender()`
        _underlying.safeTransfer(_msgSender, _underlyingAmount);
    }
