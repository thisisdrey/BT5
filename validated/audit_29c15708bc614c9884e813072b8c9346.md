### Title
`pallet-assets::approve_transfer` uses additive (not overwrite) allowance semantics, letting a delegate accumulate a larger allowance than the owner ever intended to grant at once — the same "N+M withdrawal" invariant break as the ERC-20 approve/transferFrom bug - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
The classic ERC-20 bug (EIP-738) is rooted in one broken invariant: an owner who tries to *update* a delegate's allowance from `N` to `M` can end up granting the delegate `N+M` instead of `M`, because the approval storage is not atomically replaced. `pallet-assets` reproduces this exact invariant break — deterministically, without needing any transaction race — because `do_approve_transfer` adds the new `amount` to whatever allowance already exists rather than setting it: [1](#0-0) 

The dispatchable that exposes this to any signed user documents the behavior but the wording ("acts additively") hides how easily a caller who expects ERC-20 "set" semantics can misuse it: [2](#0-1) 

### Finding Description
`Pallet::approve_transfer` (call index 22) is a public, unprivileged, signed extrinsic. Its handler forwards directly to `do_approve_transfer`: [3](#0-2) 

Inside `do_approve_transfer`, the existing `Approvals` entry (if any) is read, and the new `amount` is *added* to it rather than replacing it:

```
approved.amount = approved.amount.saturating_add(amount);
``` [4](#0-3) 

This means: if owner Alice first approves delegate Bob for `N` tokens, then later calls `approve_transfer` again intending to *change* the allowance to `M` (a lower or different value, as in the EIP-738 scenario), the resulting on-chain allowance is `N+M`, not `M`. Unlike the original EIP-738 bug, this doesn't even require Bob to race a pending transaction — it happens on every sequential call, because the pallet's only way to reduce an allowance is a full `cancel_approval` (revoking everything) followed by a fresh `approve_transfer`, and any two `approve_transfer` calls compound.

This is a known, previously-fixed class of bug in this exact codebase: the ERC-20 precompile that wraps `pallet-assets` had precisely this issue and was patched in `prdoc/stable2606/pr_11279.prdoc`, which states plainly: *"The ERC-20 approve(spender, amount) spec sets the allowance to amount. The precompile was calling do_approve_transfer, which adds to the existing allowance — breaking ERC-20 compliance."* The precompile fix works around the problem by calling `do_cancel_approval` first and then `do_approve_transfer`: [5](#0-4) 

However, this fix only lives in the precompile shim. The native `pallet_assets::approve_transfer` extrinsic — used directly by end users, wallets, other pallets, and any XCM/asset-hub integration that assumes standard "set allowance" accounting — remains additive and unpatched at the pallet level.

### Impact Explanation
Any integrator (wallet, dApp, another pallet, or a naive off-chain agent) that calls `approve_transfer` a second time believing it *replaces* the delegate's allowance (the natural ERC-20 mental model, and the exact mental model the precompile itself had to be fixed to match) will silently grant the delegate access to the sum of all previously approved amounts instead of the intended final amount. The delegate can then call `transfer_approved`/`do_transfer_approved` to withdraw the full accumulated (unintended) amount: [6](#0-5) 

This breaks the "assets must conserve value and settle exactly once to the rightful beneficiary and amount" invariant: the delegate becomes authorized to move funds far beyond what the owner most recently intended, i.e., an unintended escalation of a third party's spending authority over the owner's assets — the same fund-exposure outcome as the original ERC-20 bug, sourced from an accounting/state-update defect rather than a race condition.

### Likelihood Explanation
High for any integration that mirrors ERC-20 "approve sets the allowance" semantics against the raw pallet call (which is exactly why the precompile needed the dedicated fix). No malicious peer, validator, collator, relayer, or governance action is required — an ordinary owner performing two legitimate, sequential `approve_transfer` calls (e.g., to adjust a previously granted allowance) triggers the unintended accumulation deterministically, with no timing dependency.

### Recommendation
Change `do_approve_transfer` to accept explicit "increase" vs "set" semantics (mirroring the precompile's cancel-then-set pattern), or update the dispatchable's contract/documentation and add a `set_approval`-style call that first zeroes/cancels any existing approval before writing the new amount — analogous to the EIP-738 recommendation to require `amount == 0 || current_allowance == 0` before allowing a non-additive update. At minimum, `approve_transfer`'s documentation should be strengthened with an explicit warning and downstream pallets/precompiles auditted to ensure none of them assume "set" semantics when calling the additive primitive directly.

### Proof of Concept
1. Owner (Alice) calls `Assets::approve_transfer(origin=Alice, id, delegate=Bob, amount=100)`. `Approvals[(id, Alice, Bob)].amount == 100`.
2. Alice later decides she wants Bob's allowance to be only `50` (e.g., she miscalculated, or is trying to "reset" it) and calls `Assets::approve_transfer(origin=Alice, id, delegate=Bob, amount=50)` again (no cancellation in between).
3. Per `do_approve_transfer`'s additive logic (`substrate/frame/assets/src/functions.rs:963`), `Approvals[(id, Alice, Bob)].amount` becomes `100 + 50 = 150`, not `50`.
4. Bob calls `Assets::transfer_approved(origin=Bob, id, owner=Alice, destination=Bob, amount=150)`, successfully withdrawing `150` tokens from Alice — `100` more than Alice's last intended approval — exactly mirroring the "N+M withdrawal" outcome described in the EIP-738 report, without needing to race any transaction.

	/// Creates an approval from `owner` to spend `amount` of asset `id` tokens by 'delegate'
	/// while reserving `T::ApprovalDeposit` from owner
	///
	/// If an approval already exists, the new amount is added to such existing approval
	pub fn do_approve_transfer(
		id: T::AssetId,
		owner: &T::AccountId,
		delegate: &T::AccountId,
		amount: T::Balance,
	) -> DispatchResult {
		let mut d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(d.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);
		Approvals::<T, I>::try_mutate(
			(id.clone(), &owner, &delegate),
			|maybe_approved| -> DispatchResult {
				let mut approved = match maybe_approved.take() {
					// an approval already exists and is being updated
					Some(a) => a,
					// a new approval is created
					None => {
						d.approvals.saturating_inc();
						Default::default()
					},
				};
				let deposit_required = T::ApprovalDeposit::get();
				if approved.deposit < deposit_required {
					T::Currency::reserve(owner, deposit_required - approved.deposit)?;
					approved.deposit = deposit_required;
				}
				approved.amount = approved.amount.saturating_add(amount);
				*maybe_approved = Some(approved);
				Ok(())
			},
		)?;
