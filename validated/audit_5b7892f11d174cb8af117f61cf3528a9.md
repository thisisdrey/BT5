Based on my investigation, I found a concrete fee-boundary bypass in the `TokenDiff` intent execution that mirrors the reported bug class: a caller-controlled, arbitrarily small per-intent value (`|delta| == 1`) permanently disables an economic safety mechanism (protocol fee) for the token class, and this can be fragmented across a valid, invariant-satisfying batch to move unlimited volume fee-free.

### Title
Protocol fee bypass on NEP-245/IMT token swaps via delta-fragmentation into unit-sized `TokenDiff` intents - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee()` unconditionally waives the protocol fee whenever the absolute delta on a `Nep245` or `Imt` token is `<= 1`. Because fee evaluation is performed independently per `TokenDiff` intent (not on the net traded volume of a session/batch), a user can split an arbitrarily large swap into many unit-sized legs, each of which is fee-exempt, and satisfy the batch-level zero-sum invariant enforced by `TransferMatcher::finalize`, thereby moving unlimited economic value while paying zero protocol fee.

### Finding Description
`TokenDiff::execute_intent` computes the fee per intent from the intent's own `delta`: [1](#0-0) 

The fee itself is computed by `token_fee`, which explicitly zeroes out the fee for NFTs, and for MTs/IMTs specifically when `amount <= 1`: [2](#0-1) 

This exemption is applied at the granularity of a single `TokenDiff` intent's delta, not at the granularity of the total economic volume transferred in a settlement. The engine's invariant check only requires that the sum of all deltas across all executed intents in a batch nets to zero per token (`TransferMatcher::finalize`), it does not aggregate or cap the number of intents nor inspect cumulative volume when deciding fee applicability: [3](#0-2) [4](#0-3) 

Consequently, two colluding (or self-controlled) accounts can submit `N` separate signed `TokenDiff` intents, each moving exactly `1` unit of an NEP-245/IMT token in opposite directions, all within one `execute_intents` call. Each individual intent has `token_fee(... , 1, fee) == Pips::ZERO`, so `fees_collected` is empty for every leg, and the batch still nets to zero as required. The `MT_ON_TRANSFER`/`TransferMatcher` machinery matches these deposits/withdrawals into net transfers of size `N`, i.e., the same real-world volume a single large `TokenDiff` would have produced — but with the protocol fee entirely avoided.

### Impact Explanation
This breaks the "fees owed versus fees collected" invariant explicitly listed as Critical impact: fees are structurally bypassed for MT/IMT-denominated swaps by structuring trade legs at `delta == 1`, regardless of how large the true traded amount is. The `fee_collector` account permanently loses fee revenue on any MT/IMT-based trading route that an attacker chooses to fragment this way, and this is directly exploitable for attacker profit (0% effective fee vs. the intended `fee` config) without needing any privileged role, relayer key, or misconfiguration — it works against the documented, in-scope fee configuration (`FeesConfig`/`Pips`).

### Likelihood Explanation
Likelihood is high for any deployment that lists NEP-245 (multi-token, including wrapped/bridged tokens represented as MT) or IMT assets and charges a non-zero protocol fee (`Pips`) on them. Any two parties (which can be the same actor operating two accounts) can construct and sign the fragmented `TokenDiff` payloads themselves — no special contract state, timing, or third-party cooperation is required, and gas/transaction-count cost scales linearly with volume but is otherwise unbounded by any per-batch entry limit visible in `execute_signed_intents`.

### Recommendation
Compute and apply the MT/IMT fee based on cumulative net volume per token across the intents being executed in the same call (or eliminate the `amount <= 1` fee exemption and instead round the fee using `fee_ceil` so a fee floor of at least 1 unit is guaranteed on any nonzero MT/IMT delta), so that fragmenting a trade into unit-sized legs cannot reduce the aggregate fee below what a single equivalent-volume trade would incur.

### Proof of Concept
1. Deploy Defuse with `FeesConfig { fee: Pips::ONE_PERCENT, .. }` and an NEP-245/IMT token registered.
2. Attacker controls accounts `A` and `B`, each holding balances of `mt_token`/`other_token`.
3. Instead of one `TokenDiff` intent trading `-10_000`/`+10_000` (which would incur `fee_ceil(10_000)` per the normal path, as shown in existing tests using `TokenDiff::closure_delta`, e.g. [5](#0-4) ), `A` and `B` sign `10_000` separate `TokenDiff` intents, each with `diff = { mt_token: -1, other_token: +1 }` / `{ mt_token: +1, other_token: -1 }` respectively.
4. Submit all `20_000` signed payloads in a single `execute_intents([...])` call.
5. For every intent, `TokenDiff::token_fee` returns `Pips::ZERO` because `amount == 1` for the `Nep245`/`Imt` token type (`contracts/defuse/core/src/intents/token_diff.rs:206-217`), so `fees_collected` stays empty for the whole batch.
6. The batch nets to zero per `TransferMatcher::finalize` (`contracts/defuse/core/src/engine/state/deltas.rs:265-283`) and the call succeeds, transferring the full `10_000`-unit volume between `A` and `B` with `0` collected by `fee_collector`, versus the `fee_ceil(10_000)` that would have been collected via a single equivalent `TokenDiff`.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
