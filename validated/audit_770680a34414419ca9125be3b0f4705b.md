### Title
`lending_pool_handle_bankruptcy` unconditionally attempts an SPL transfer from the insurance vault, so a frozen/blocked vault permanently prevents bankruptcy resolution - ([File: programs/marginfi/src/instructions/marginfi_group/handle_bankruptcy.rs])

### Summary
This is an analog of the Derby M-13 bug class: an emergency/cleanup function (`Vault.blacklistProtocol`) tries to withdraw funds as part of its state-change logic, and if that withdrawal reverts (e.g. because the underlying asset is paused/frozen), the emergency state transition can never complete. In marginfi, `lending_pool_handle_bankruptcy` performs the equivalent pattern: before it disables the bankrupt account, socializes the loss, and (potentially) kills the bank, it unconditionally calls `bank.withdraw_spl_transfer` to move funds out of the insurance vault. If that transfer fails for any reason external to marginfi's own logic (most notably: the insurance vault or liquidity vault token account being frozen by the mint's freeze authority, which is common for regulated/centralized stablecoins), the entire instruction reverts and none of the critical bad-debt-settlement state changes occur.

### Finding Description
`lending_pool_handle_bankruptcy` computes `covered_by_insurance` and then calls: [1](#0-0) 
before performing `bank.socialize_loss(...)`, `BankAccountWrapper::repay(...)`, setting `ACCOUNT_DISABLED`, and potentially setting `BankOperationalState::KilledByBankruptcy`: [2](#0-1) 

The underlying transfer routine `withdraw_spl_transfer` performs a real SPL/Token-2022 CPI transfer with no fallback path if the CPI fails: [3](#0-2) 

Per SPL Token semantics, a `Transfer`/`TransferChecked` instruction fails outright if either the source or destination token account is in the `Frozen` state — this is enforced regardless of the transfer amount, including zero-amount transfers. Since `insurance_coverage_deposit_pre_fee` is passed to `withdraw_spl_transfer` unconditionally (even when it is `0`, i.e. when the insurance fund holds nothing), any freeze on the insurance vault or liquidity vault token account (e.g. imposed by a centralized stablecoin issuer's freeze authority on a hacked/flagged account, analogous to "protocol is hacked or paused" in the source report) will cause `lending_pool_handle_bankruptcy` to revert every time it is called against that bank.

This mirrors the Derby bug precisely: the emergency/cleanup instruction bundles a token-movement step with the state-transition logic, so a transfer failure blocks the state transition (settlement/disable/kill) entirely, with no way to separate "mark resolved" from "move funds."

### Impact Explanation
If a bank's insurance or liquidity vault becomes frozen (or the transfer otherwise reverts, e.g. via a Token-2022 extension that blocks transfers), `HandleBankruptcy` can never succeed for that bank:
- The bankrupt account can never be disabled (`ACCOUNT_DISABLED` never gets set), its bad debt is never cleared, and `socialize_loss`/`repay` never run.
- Per the project's own documentation, if bankruptcy cannot be executed, remaining depositors "can never withdraw the whole balance in the bank" — the last depositors attempting withdrawal find insufficient funds proportional to the unresolved bad debt: [4](#0-3) 
- For banks with `PERMISSIONLESS_BAD_DEBT_SETTLEMENT_FLAG` set, this is directly reachable by unprivileged callers (anyone can call `HandleBankruptcy`), and the guide explicitly documents this permissionless path: [5](#0-4) 

This is a permanent-lock/insolvency class impact: bad debt is stuck on the books indefinitely, remaining depositors are frozen out of a portion of their funds, and the bank cannot be wound down.

### Likelihood Explanation
Likelihood is low-to-moderate and situational (similar to the original Derby report, which was accepted as valid but of reduced severity because it does not by itself cause direct loss of funds beyond what's already lost to the bankruptcy). It requires an external condition — a frozen/blocked vault token account — that marginfi does not control, e.g., a stablecoin issuer freezing an address tied to a hack, sanctions, or compliance action, or a Token-2022 mint extension that blocks transfers under certain conditions. Because marginfi already supports Token-2022 mints (as seen in `T22WithFee` bank tests), this scenario is plausible for real bank deployments, though it depends on real-world admin actions outside the protocol.

### Recommendation
Decouple the insurance-fund transfer from the account/bank state transition so a transfer failure cannot block bad-debt settlement:
- Skip the `withdraw_spl_transfer` call entirely when `insurance_coverage_deposit_pre_fee == 0` (this alone would prevent the "empty insurance fund + frozen vault" failure mode, but does not fix the case where the fund is nonzero but frozen).
- More robustly, perform the state changes (`socialize_loss`, `repay`, `ACCOUNT_DISABLED`, `KilledByBankruptcy`) first (or independent of transfer success), and record any insurance-fund amount that could not be transferred as an outstanding/receivable balance to be swept later once the freeze is lifted or via a separate instruction — analogous to the report's recommendation to add a "needToWithdraw" parameter and allow retrying the transfer once conditions permit.

### Proof of Concept
1. Deploy a bank whose mint has Token-2022 (or SPL Token with freeze authority) support, with a nonzero insurance vault balance, as is already exercised in the `T22WithFee` bankruptcy tests: [6](#0-5) 
2. Have the mint's freeze authority freeze the bank's `insurance_vault` (or `liquidity_vault`) token account — analogous to a "hacked or paused" underlying asset in the source report.
3. Put a borrower into a bankrupt state as in the existing bankruptcy test flow (nullify collateral, then attempt `try_handle_bankruptcy`): [7](#0-6) 
4. Because `bank.withdraw_spl_transfer` (lines 174-187 of `handle_bankruptcy.rs`) now targets a frozen account, the CPI transfer fails, causing the entire `lending_pool_handle_bankruptcy` instruction to revert.
5. Confirm the bankrupt account remains enabled with its bad debt intact (`ACCOUNT_DISABLED` unset, liability shares nonzero), and that the instruction reverts on every retry as long as the freeze persists — demonstrating the permanent block on bad-debt settlement.

Note: I was unable to directly execute this PoC or confirm at the SPL Token program level (outside this repo) that zero-amount transfers are blocked on frozen accounts; this is standard SPL Token program behavior but wasn't verified within the indexed codebase. If further certainty is needed, a Devin session with full repository and toolchain access could run the test scenario above to confirm the revert behavior end-to-end.

    #[allow(unused_variables)]
    fn withdraw_spl_transfer<'info>(
        &self,
        amount: u64,
        from: AccountInfo<'info>,
        to: AccountInfo<'info>,
        authority: AccountInfo<'info>,
        maybe_mint: Option<&InterfaceAccount<'info, Mint>>,
        program: AccountInfo<'info>,
        signer_seeds: &[&[&[u8]]],
        remaining_accounts: &[AccountInfo<'info>],
    ) -> MarginfiResult {
        debug!(
            "withdraw_spl_transfer: amount: {} from {} to {}, auth {}",
            amount, from.key, to.key, authority.key
        );

        #[cfg(feature = "client")]
        if let Some(mint) = maybe_mint {
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                Some(mint.to_account_info()),
                to,
                authority,
                Some(mint.decimals),
                remaining_accounts,
                signer_seeds,
            )?;
        } else {
            // `transfer_checked` and `transfer` does the same thing, the additional `_checked` logic
            // is only to assert the expected attributes by the user (mint, decimal scaling),
            //
            // Security of `transfer` is equal to `transfer_checked`.
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                None,
                to,
                authority,
                None,
                remaining_accounts,
                signer_seeds,
            )?;
        }

        #[cfg(not(feature = "client"))]
        if let Some(mint) = maybe_mint {
            spl_token_2022::onchain::invoke_transfer_checked(
                program.key,
                from,
                mint.to_account_info(),
                to,
                authority,
                remaining_accounts,
                amount,
                mint.decimals,
                signer_seeds,
            )?;
        } else {
            // `transfer_checked` and `transfer` does the same thing, the additional `_checked` logic
            // is only to assert the expected attributes by the user (mint, decimal scaling),
            //
            // Security of `transfer` is equal to `transfer_checked`.
            #[allow(deprecated)]
            transfer(
                CpiContext::new_with_signer(
                    program.key(),
                    Transfer {
                        from,
                        to,
                        authority,
                    },
                    signer_seeds,
                ),
                amount,
            )?;
        }

        Ok(())
    }
