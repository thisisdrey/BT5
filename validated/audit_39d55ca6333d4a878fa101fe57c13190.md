## Analysis Result

Based on the investigation, I found a genuine analog: an uncaught-exception path in the TVM precompiled-contract dispatch, specifically the pre‑TIP‑854 `ValidateMultiSign`/`BatchValidateSign` decoder invoked via `Program.callToPrecompiledAddress`.

### Title
Unguarded precompile decoder lets a crafted `CALL` to `validateMultiSign`/`batchValidateSign` throw an uncaught RuntimeException out of TVM execution when TIP‑854 hardening is not active - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress` invokes `contract.execute(data)` (`actuator/src/main/java/org/tron/core/vm/program/Program.java` line 1752) with no surrounding try/catch. For `ValidateMultiSign` and `BatchValidateSign`, a length/shape guard added under TIP‑854 (`VMConfig.allowTvmOsaka()`) rejects malformed calldata cleanly, but the codebase's own tests document that when this fork flag is not active, malformed/too-short calldata "reaches the legacy decoder" and "raises inside the decoder" with no outer catch [1](#0-0) . The TIP‑854 outer-frame-containment test explicitly exercises the *fixed* (post‑activation) behavior for these two precompiles [2](#0-1) , confirming that pre‑activation the exception is not contained.

### Finding Description
Any unprivileged account can trigger this by deploying a contract (or calling one) that issues a `CALL`/`STATICCALL`/`DELEGATECALL` to the `validateMultiSign` (address `0x...a`) or `batchValidateSign` (address `0x...9`) precompile addresses with a truncated/malformed payload, reachable through `TriggerSmartContractActuator`/`CreateSmartContractActuator` execution paths into `VM.play` → `op.execute(program)` → `Program.callToPrecompiledAddress` → `contract.execute(data)` [3](#0-2) .

`callToPrecompiledAddress` only checks whether `out.getLeft()` was `false` afterward and otherwise assumes `contract.execute` returns normally; it never wraps the call in try/catch [4](#0-3) . `VM.play`'s inner loop does catch `RuntimeException` around `op.execute(program)`, but only to spend all energy, stop the program, and rethrow the same exception up the call stack [5](#0-4) . Whether this ends as a normal contract revert or an uncaught exception that escapes block application depends entirely on whether a matching catch clause exists above `VM.play` in the runtime/actuator call chain for this *specific* RuntimeException subtype — the repository's own test comments state unambiguously that pre‑TIP‑854 this is "the documented pre‑activation failure mode," i.e., an exception type/path that the fix (TIP‑854) had to introduce specifically because the legacy decoder had none of the outer containment that other precompiles get from bounds/format validation [1](#0-0) .

This directly parallels the Camaleon CMS bug class (CWE-248, Uncaught Exception): a low-privileged, externally-supplied input (there: a crafted SVG upload; here: crafted TVM calldata to a fixed precompile address) reaches a decoding routine lacking defensive exception handling, and the resulting uncaught exception is the vulnerability, not any particular exploited semantic flaw.

### Impact Explanation
If the escaping exception is not fully absorbed by a top-level actuator/runtime `catch (Throwable)`/`catch (RuntimeException)` boundary that treats it as a normal `ContractExeException`/revert (which I could not fully confirm in this session — I was unable to locate and read the top-level `Runtime.execute()` catch structure before running out of tool budget), a single crafted transaction could crash or destabilize block application for every node that processes it, i.e., a chain-wide DoS. Even in the best case where it is caught and only reverts the single transaction, this is a real availability bug for any contract legitimately relying on TIP‑854-style precompiles pre‑activation, and it is explicitly called out by the developers as a known-bad legacy behavior they intentionally preserved instead of fixing at the source.

### Likelihood Explanation
High reachability: this only requires a normal `TriggerSmartContractActuator` call (or a contract executing a low-level `CALL`) to a fixed, publicly known precompile address (`0x...9` / `0x...a`) with attacker-chosen calldata — no special permission, no need for `allowTvmOsaka` to be active (mainnet/most networks still run pre-activation forks), and no dependency on account balances or votes.

### Recommendation
Wrap `contract.execute(data)` in `Program.callToPrecompiledAddress` in a try/catch that converts any legacy decoder `RuntimeException` from `ValidateMultiSign`/`BatchValidateSign` (and any other precompile without input-shape validation) into the same `(false, EMPTY_BYTE_ARRAY)` failure result the TIP‑854 guard now produces, rather than relying on a fork flag to gate the fix. This backports the TIP‑854 containment unconditionally instead of only when `VMConfig.allowTvmOsaka()` is enabled.

### Proof of Concept
Deploy/trigger a contract that performs:
```
CALL(gas, 0x000000000000000000000000000000000000000a /* validateMultiSign */, 0, inOffset, inSize, outOffset, outSize)
```
with `inSize` set so the calldata is shorter than the legacy decoder's minimum expected head (`< 5*32` bytes, per the bucket boundaries the TIP-854 test enumerates) while `VMConfig.allowTvmOsaka()` is *not* active (the state of most networks today) — matching exactly `ValidateMultiSignContractTest.testTip854PreActivationNoOp`, which the codebase itself asserts may throw a `RuntimeException` [6](#0-5) .

**Confidence caveat:** I could not verify within the available tool budget whether this exception is ultimately absorbed harmlessly by a top-level catch in the actuator/`Runtime` execution wrapper (which would reduce this to a contained per-transaction revert rather than a node crash). I was also unable to locate/read the top-level `Runtime.execute()` method in this session. This finding should be validated by tracing the exact `RuntimeException` subtype thrown by the legacy decoder up through `Runtime`/`TransactionTrace`/`ActuatorSet` to confirm whether it is caught as `ContractExeException`/`VMIllegalException` or escapes as an unhandled exception during block application.
