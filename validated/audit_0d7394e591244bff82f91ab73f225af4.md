### Title
Unbounded Prometheus label cardinality DoS via attacker-controlled `client_name`/`call_site` gRPC metadata - (File: internal/grpc/middleware/requestinfohandler/requestinfohandler.go)

### Finding Description
`newRequestInfo` reads the `call_site` and `client_name` values directly from incoming gRPC metadata with no validation, allowlist, or length/character restriction: [1](#0-0) 

These attacker-controlled strings are then used unconditionally as label values on the `requests` `CounterVec`, which is a `promauto`-registered global Prometheus metric: [2](#0-1) [3](#0-2) 

`reportPrometheusMetrics` is invoked at the end of every unary and streaming RPC in `UnaryInterceptor`/`StreamInterceptor`, which is registered as a standard gRPC middleware in the server bootstrap: [4](#0-3) 

Prometheus client libraries keep one time series per unique label-value combination indefinitely (until process restart), so supplying a fresh, unique `client_name` or `call_site` value on every RPC causes the `requests` CounterVec (and its underlying `prometheus_client` registry storage) to grow without bound. This is independent of `LookupMethod`/`FullMethod`, which — as the question states — is fixed per RPC method and not attacker-controlled; the actual injection point is the metadata-derived label values, not `FullMethod`.

There is no sanitization such as `helper.SanitizeString`, no allowlist of known client names, and no cap on cardinality anywhere in this file or in the metric registration.

### Impact Explanation
This matches a metrics/monitoring resource-exhaustion DoS: unbounded Prometheus series growth increases process RSS and CPU (label hashing, scrape serialization) over time, and in extreme cases can degrade or crash the Gitaly node serving many tenants/repositories, causing a node-wide service degradation for unrelated legitimate traffic. This is a plausible node-level DoS impact class, though slower/subtler than a single-request crash — it requires sustained traffic to accumulate significant memory (each series with these ~9 labels is a modest allocation, so many thousands to millions of unique combinations are needed for meaningful memory impact).

### Likelihood Explanation
An attacker with normal, unprivileged access to a Gitaly-backed GitLab instance can freely set arbitrary custom gRPC metadata headers (`client_name`, `call_site`) on any RPC they can call against their own repository, including lightweight streaming RPCs. No special role, secret, or configuration is required — this is default behavior of the middleware. The main constraint is the volume of unique values/RPCs needed to produce a meaningful memory footprint, and that repeated RPCs may also be constrained by other rate-limiting/concurrency-limiting middleware (`limithandler`) that could throttle raw RPC volume, though that limiting is orthogonal to and does not fix the underlying unbounded-cardinality label design.

### Recommendation
- Restrict `client_name` and `call_site` label values to a fixed, curated allowlist (known Gitaly/GitLab client identifiers) and map any other value to `"unknown"` before use as a Prometheus label, rather than passing the raw metadata value through.
- Alternatively, drop these fields from the low-cardinality Prometheus metric and only retain them in the structured log tags (`Tags()`), where high cardinality is less problematic operationally.
- Consider adding a cap on the number of distinct label combinations tracked (e.g. via `prometheus.CounterVec` with pre-registered/curated label sets) to make cardinality explosion structurally impossible.

// For N unique metadata values, invoke a lightweight RPC (e.g. a client-streaming
// RPC like UserCommitFiles opened/closed immediately) with distinct

// the `gitaly_service_client_requests_total` metric's series count via
// prometheus.DefaultGatherer or the exposed /metrics endpoint.

for i := 0; i < N; i++ {
    md := metadata.Pairs("client_name", fmt.Sprintf("attacker-client-%d", i))
    ctx := metadata.NewOutgoingContext(context.Background(), md)
    stream, _ := client.UserCommitFiles(ctx)
    stream.CloseAndRecv() // minimal payload, immediate teardown
}

// Assertion: number of distinct series for gitaly_service_client_requests_total
// grows linearly with N and is never capped/normalized, confirming unbounded
// cardinality growth from attacker-controlled input.

		i.methodScope,

func UnaryInterceptor(ctx context.Context, req interface{}, serverInfo *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
	tags := grpcmwtags.NewTags()

	info := newRequestInfo(ctx, serverInfo.FullMethod, "unary")
	info.extractRequestInfo(req)

	ctx = context.WithValue(ctx, requestInfoKey{}, info)

	ctx = info.injectTags(ctx, tags)
	res, err := handler(ctx, req)
	info.reportPrometheusMetrics(err)

	return res, err
}

// StreamInterceptor returns a Stream Interceptor
func StreamInterceptor(srv interface{}, stream grpc.ServerStream, serverInfo *grpc.StreamServerInfo, handler grpc.StreamHandler) error {
	tags := grpcmwtags.NewTags()

	ctx := stream.Context()
	info := newRequestInfo(ctx, serverInfo.FullMethod, streamRPCType(serverInfo))

	ctx = context.WithValue(ctx, requestInfoKey{}, info)

	// Even though we don't yet have all information set up we already inject the tags here. This is done such that
	// log messages will at least have the metadata set up correctly in case there is no first request.
	ctx = info.injectTags(ctx, tags)
	err := handler(srv, &wrappedServerStream{
		ServerStream: stream,
		ctx:          ctx,
		info:         info,
		tags:         tags,
		initial:      true,
	})
	info.reportPrometheusMetrics(err)

	return err
}
