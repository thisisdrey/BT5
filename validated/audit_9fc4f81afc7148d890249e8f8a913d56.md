### Title
Unbounded array allocation from attacker-controlled length words in `PrecompiledContracts` signature-array extraction (`extractBytesArray`/`extractBytes32Array`/`extractSigArray`) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Mattermost advisory describes a failure to bound memory allocation based on an attacker-controlled length field before validating it against the actual available data, leading to memory exhaustion. The same bug class exists in java-tron's TVM precompiled-contract calldata parsing helpers, which allocate arrays sized directly from an unvalidated 256-bit word taken from smart-contract call data.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` in `PrecompiledContracts.java` read a length value directly out of the ABI-encoded calldata words and immediately allocate a Java array of that size, before any check that the declared length is consistent with the amount of data actually supplied: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case `int len = words[offset].intValueSafe();` extracts an integer directly from a word supplied in the transaction's smart-contract call data, and it is used unconditionally as the size for `new byte[len][]` (an object-array allocation, ~16 bytes/element overhead on a 64-bit JVM even before the inner arrays are populated). There is no upper bound check comparing `len` against `words.length`, `data.length`, or any energy/CPU-derived cap before the allocation occurs, unlike other precompiled-contract code paths in the same file (e.g. `ModExp`) which explicitly bound input lengths with an `UPPER_BOUND` check before any big allocation: [4](#0-3) 

These helpers back the `ValidateMultiSign`/`BatchValidateSign`-style precompiled contracts invoked via TVM `CALL`/`STATICCALL` opcodes to fixed precompile addresses, which are reachable from any `TriggerSmartContractContract` transaction submitted by an unprivileged account — no special permission is required to call a precompile from a deployed or inline contract.

### Impact Explanation
Because `words[offset].intValueSafe()` can be attacker-controlled up to a very large positive integer (limited only by `intValueSafe`'s int-range clamp, not by actual calldata size), a single crafted transaction can force the node to attempt allocating an array with billions of reference slots. On a 64-bit JVM this can request tens of gigabytes of heap in one allocation, causing an `OutOfMemoryError` in the node's VM execution thread and, depending on JVM/heap configuration, destabilizing or crashing the full node process — a denial-of-service impact analogous to the Mattermost DOC-file memory-exhaustion issue, matching CWE-789 (uncontrolled memory allocation).

### Likelihood Explanation
Likelihood is high for any FullNode/SolidityNode that executes TVM contract calls: an attacker only needs to deploy or call a trivial smart contract that invokes the vulnerable precompile with a crafted calldata word for the array-length field, then broadcast one signed transaction. No special privilege, staking weight, or witness/SR role is needed — it is reachable by any address able to submit a `TriggerSmartContractContract` transaction, consistent with the "unprivileged contract deployer/caller" reachability required by the scope rules.

### Recommendation
Add an explicit upper bound on the extracted `len` value in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` before allocating the array — validating it against the remaining bytes in `words`/`data` (as is already done in other parts of the file, e.g. `verifyLength`-style checks in `RLP.java`) and/or against a fixed maximum array size, rejecting the precompile call with an execution failure if the declared length is inconsistent with the actual supplied calldata length.

### Proof of Concept
1. Deploy (or reuse) a smart contract that performs a low-level `staticcall`/`call` to the precompile address backing `ValidateMultiSign`/`BatchValidateSign`.
2. Construct calldata whose `words[offset]` word (the "signature/bytes array length" field consumed by `extractSigArray`/`extractBytesArray`/`extractBytes32Array`) encodes a very large positive integer (e.g. close to `Integer.MAX_VALUE`), while the remainder of the calldata is short/minimal.
3. Broadcast a single `TriggerSmartContractContract` transaction invoking this call.
4. During execution, `intValueSafe()` returns the large length unchecked, and `new byte[len][]` attempts a multi-gigabyte allocation, triggering `OutOfMemoryError`/heap exhaustion on the executing node before any TVM energy-metering-based early rejection occurs based on the true payload size.
