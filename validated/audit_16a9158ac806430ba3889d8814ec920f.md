### Title
Forged, unauthenticated peer chunk-inventory poisons `expected_versions` and permanently blocks legitimate StackerDB writes for a slot - ([File: stackslib/src/net/stackerdb/sync.rs])

### Summary
`StackerDBSync::recalculate_chunk_request_schedule` derives the local node's `expected_versions` vector purely from the self-reported `slot_versions` field of a peer's `StackerDBChunkInvData`, which carries no signature or proof that the claimed version actually exists. Any remote, unauthenticated StackerDB replica peer can advertise an arbitrarily high (up to `u32::MAX`) version number for a victim's slot; the local node then treats that forged number as its new "current" reference point and rejects every subsequent legitimately-signed chunk from the real slot owner as stale, exactly mirroring the `Overseer.rebase()` bug class where an attacker-inflated value crosses/poisons a threshold the honest party can never realistically re-cross.

### Finding Description
`StackerDBChunkInvData::slot_versions` is a bare `Vec<u32>` sent by a peer in response to `StackerDBGetChunkInv`, or embedded in a push-chunk exchange [1](#0-0) . This vector is never checked against actual signed chunk data before being trusted — it is simply a peer's claim about what versions it holds.

That untrusted vector is folded directly into `expected_versions` by taking the max across all peers' reported inventories, with no validation: [2](#0-1) 

The same happens on initial inventory collection via `getchunksinv_try_finish`, which also just stores whatever a peer replied with `chunk_invs.insert(naddr.clone(), chunk_inv)` without any signature or proof-of-possession check [3](#0-2) .

`expected_versions` is then used as the authority for whether an incoming, properly-signed chunk is "stale": [4](#0-3) 

This same `expected_versions`/inventory field is also consulted directly in the unsolicited push-chunk handler, where the "inventory" used for `validate_received_chunk`'s staleness check is the locally regenerated `StackerDBChunkInv` (via `make_StackerDBChunksInv_or_Nack`) but is then *patched* with whatever slot version the pushing peer's chunk claims, again with no cross-check against a genuinely-stored, signed chunk of that version: [5](#0-4) .

Because a slot's `max_writes` is capped (often bounded, e.g. `TooManySlotWrites` at `slot_desc.slot_version > self.config.max_writes`) [6](#0-5) , once `expected_versions[slot]` is poisoned to a value at or near `max_writes`, the true slot owner — whose next legitimate version can only increment by 1 each write and is capped by the same `max_writes` — can never again produce a version that satisfies `data.slot_version >= *expected_version`, so `validate_received_chunk`/`validate_downloaded_chunk` will reject it as "stale" forever on that node. This breaks the intended equality that "served/accepted version == actually the highest genuinely-signed version," analogous to the `Overseer` case where an attacker-inflated delta permanently exceeds a threshold the honest protocol flow can never clear.

### Impact Explanation
This is a remote, unauthenticated denial of service against StackerDB replication (used for miner/signer coordination data) on any node that peers with the attacker for StackerDB sync: a single malicious StackerDB-replica peer, with no special privileges and no valid slot-owning key, can poison a victim node's view of one or more slots (including slots not owned by the attacker) so that node permanently stops accepting/relaying genuine updates for those slots. Downstream, this can stall propagation of signer/miner StackerDB messages on the affected node, matching the "High: bounded compute DoS on a read endpoint" / stale inventory class described in the rules, since it degrades the node to serving/accepting only non-canonical (frozen, stale) StackerDB state as if it were canonical.

### Likelihood Explanation
Likelihood is high for reachability (any peer that can complete a StackerDB `GetChunksInv`/push-chunk exchange can supply an arbitrary `slot_versions` vector) but the blast radius is confined to nodes that directly sync with the attacker (the poisoned `expected_versions` is per-node, in-memory bookkeeping, not itself gossiped as a signed/canonical artifact), so it does not by itself propagate network-wide the way a signed forged chunk would. Still, it requires no signature forgery and no compromise of any key.

### Recommendation
Do not let an unauthenticated inventory claim (`StackerDBChunkInvData.slot_versions`) directly set `expected_versions` used to reject genuinely-signed chunks. Either (a) only ratchet `expected_versions` up to a version once a chunk of that version has actually been fetched and had its signature verified, or (b) treat inventory-derived expectations as a hint for scheduling downloads only, and keep the staleness/acceptance check keyed off the last chunk verified to actually exist (rejecting a chunk only if the local DB already holds a strictly newer *verified* one), so a peer's unproven claim can never block acceptance of a legitimately signed, higher-numbered-than-currently-stored chunk.

### Proof of Concept
1. Attacker runs a node/peer that another target node includes among its StackerDB replicas for contract `C`.
2. Target sends `StackerDBGetChunkInv` for `C`; attacker replies with `StackerDBChunkInvData { slot_versions: [u32::MAX, ...] }` for the victim's slot ID, without ever having produced a valid signed chunk at that version.
3. Target's `getchunksinv_try_finish` stores this inventory unconditionally [7](#0-6) , and `recalculate_chunk_request_schedule`/`getchunksinv_try_finish` sets `expected_versions[slot] = u32::MAX` [8](#0-7) .
4. The real slot owner later pushes (or the target fetches) a legitimately signed chunk at version `N` (N ≪ u32::MAX, and bounded by `max_writes`); `validate_received_chunk` computes `data.slot_version (N) < *expected_version (u32::MAX)` → `Ok(false)`, permanently rejecting all future genuine updates to that slot on the target node [9](#0-8) .

    /// Recalculate the download schedule based on chunkinvs received on push
    pub fn recalculate_chunk_request_schedule(
        &mut self,
        network: &PeerNetwork,
    ) -> Result<(), net_error> {
        // figure out the new expected versions
        let mut expected_versions = vec![0u32; self.num_slots];
        for (_, chunk_inv) in self.chunk_invs.iter() {
            for (slot_version, expected_version) in chunk_inv
                .slot_versions
                .iter()
                .zip(expected_versions.iter_mut())
            {
                *expected_version = (*slot_version).max(*expected_version);
            }
        }

        let priorities =
            self.make_chunk_request_schedule(network, Some(expected_versions.clone()))?;

        self.chunk_fetch_priorities = priorities;
        self.expected_versions = expected_versions;
        Ok(())
    }
