### Title
Out-of-bounds array read via malformed calldata in `ValidateMultiSign` precompile before TIP-854/Osaka activation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract parses ABI-encoded call data into a `DataWord[]` and immediately indexes into it (`words[1]`, `words[2]`, `words[3]`, offsets derived from those words) without first checking that the supplied byte array is long enough to contain those words, or that any offset it reads is within bounds of the array. Any account can reach this precompile with a single `CALL`/`STATICCALL` from a smart contract, supplying arbitrarily short or malformed calldata, causing an `ArrayIndexOutOfBoundsException` deep inside the decoder. Test code in the repository explicitly documents that pre-TIP-854 activation "this precompile has no outer catch" and the exception may propagate.

### Finding Description
`ValidateMultiSign.execute()` does the following unconditionally: [1](#0-0) 

Only when `VMConfig.allowTvmOsaka()` is enabled does it call `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` to reject malformed input before decoding: [2](#0-1) 

When that config flag is not active (i.e., the guard added by TIP-854 has not been activated on the chain), `DataWord.parseArray(rawData)` and the subsequent `words[1]`, `words[2]`, `words[3]` accesses run on unchecked-length data, and helper functions like `extractBytesArray`/`extractSigArray` compute offsets (`words[offset + i + 1]`) directly from attacker-supplied word values with no upper-bound validation against `words.length`: [3](#0-2) 

This is the same bug class as CVE-2016-3183: insufficient bounds checking on a length/offset value taken from crafted, untrusted input, leading to a read outside the intended buffer. In Java this manifests as an uncaught `ArrayIndexOutOfBoundsException` rather than raw memory disclosure, but the root cause (parsing offsets/lengths from attacker data without validating against the actual buffer size before indexing) is identical.

Test comments in the codebase itself confirm the missing guard's real-world effect: [4](#0-3) 

By contrast, the sibling precompile `BatchValidateSign` wraps its equivalent logic in a catch-all (`doExecute` inside `try { } catch (Throwable t)`), so the same class of malformed input is safely contained there: [5](#0-4) 

`ValidateMultiSign` has no equivalent outer catch around the decode step, only a narrower `try` that starts after decoding, around the signature-recovery loop: [6](#0-5) 

### Impact Explanation
An unhandled `ArrayIndexOutOfBoundsException` thrown from inside a precompiled contract invoked via `CALL`/`STATICCALL` can propagate out of `Program.callToPrecompiledAddress` and up the TVM execution stack. Depending on how far up the exception is caught (transaction-level exception handling vs. uncaught at block-application time), this can degrade from "transaction reverts" to a node-level fault while processing a block containing the crafted transaction, since the code path is explicitly documented as lacking outer containment pre-TIP-854. Because `ValidateMultiSign` is reachable by any contract deployer or caller who can trigger a `CALL` to the fixed precompile address, this is a broadcaster-reachable denial-of-service vector against nodes that have not activated the TIP-854/Osaka guard.

### Likelihood Explanation
Reaching this code requires only deploying or calling a trivial contract that performs a low-level `call`/`staticcall` to the `ValidateMultiSign` precompile address with a short or misaligned byte payload — no special privileges, no cooperation from other parties, and no waiting for chain state. The guard exists (`isValidAbiEncoding`) but is conditioned on `VMConfig.allowTvmOsaka()`, meaning any network/version where this feature flag has not yet been activated remains exposed to the unguarded legacy path that the project's own tests document as capable of throwing uncaught.

### Recommendation
Move the `isValidAbiEncoding` (or an equivalent length/offset bounds check) validation in `ValidateMultiSign.execute()` outside of the `VMConfig.allowTvmOsaka()` conditional so it always runs before `DataWord.parseArray` and any indexing into `words[]`, matching the unconditional safety `BatchValidateSign` achieves via its outer `try/catch`. Additionally, wrap `ValidateMultiSign.execute()`'s decode section in a catch-all similar to `BatchValidateSign.execute()` so any residual malformed-input exception is converted into `Pair.of(true, DATA_FALSE)` rather than propagating.

### Proof of Concept
1. Deploy a contract that performs `staticcall(gas, VALIDATE_MULTISIGN_ADDRESS, ptr, len, out, 32)` where `len` is smaller than 4 words (128 bytes), e.g. `len = 32`.
2. On a network/version where TIP-854 (`VMConfig.allowTvmOsaka()`) has not been activated, invoke this contract via a normal `TriggerSmartContract` transaction.
3. Execution reaches `ValidateMultiSign.execute(rawData)` with `rawData.length < 128`; `DataWord.parseArray(rawData)` produces a `words` array too short for the subsequent `words[3]` access, throwing `ArrayIndexOutOfBoundsException` with no enclosing try/catch in this precompile, consistent with the behavior explicitly exercised in `testTip854PreActivationNoOp` (`framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java:249-260`), which catches a `RuntimeException` from the very same `execute()` call to document this legacy behavior.
