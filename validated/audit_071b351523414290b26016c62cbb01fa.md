### Title
`has_in_flight_tx` in the eth-implicit wallet contract is never reset if a callback panics, permanently freezing the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
This is the same bug class as the reported `emergencyResume`/`afterDepositCancellation` issue: a state flag that gates whether the contract can process further operations is only cleared on the "happy path" of a callback, and is never restored if that callback fails to complete normally. In the eth-implicit `WalletContract`, the `has_in_flight_tx` boolean plays the role of the vault's `status` field, and none of the `#[private]` callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) have any external "unstick" mechanism if their execution aborts instead of returning normally.

### Finding Description
`rlp_execute` is the sole entry point for executing any Ethereum-style transaction against this account and is gated by an in-flight flag: [1](#0-0) 

The flag is set to `true` before returning a promise, and is only cleared inside the various callback functions, each of which begins by writing `self.has_in_flight_tx = false;` as their very first statement: [2](#0-1) [3](#0-2) [4](#0-3) 

This mirrors exactly the flawed assumption in the GMX report: the code assumes the callback will always run to completion (successfully or via a handled error branch) so that the flag write is committed. However, in the NEAR runtime, any panic/abort during receipt execution causes the *entire* state mutation of that receipt to be rolled back, discarding all writes made during the call — including the very `has_in_flight_tx = false` write made at the top of the function: [5](#0-4) 

So if `address_check_callback`, `nep_141_storage_balance_callback`, or `rlp_execute_callback` panics for any reason after being scheduled (e.g. gas exhaustion while reading/deserializing an oversized or malformed `PromiseResult` value returned by an externally-targeted, attacker-controlled contract such as the `target` NEP-141 token in the `ERC20Transfer` path, or the address registrar lookup), the callback receipt fails, the `has_in_flight_tx = false` write is rolled back, and `has_in_flight_tx` remains `true` forever. There is no other entry point in the contract that resets it — `ban_relayer` also only clears it in its own successful body and is itself invoked from a promise chain subject to the same rollback risk.

Once stuck, every future call to `rlp_execute` short-circuits at the guard check and returns an error response without ever executing the user's intended action: [6](#0-5) 

### Impact Explanation
The `WalletContract` is deployed at eth-implicit accounts and is the only way to move funds/execute actions out of that account. If `has_in_flight_tx` becomes permanently stuck at `true`, the account is bricked: no NEAR transfers, token transfers, or contract calls can ever be executed from it again via `rlp_execute`. This constitutes permanent freezing of all funds and assets held by that account, matching the "permanent freezing of funds" impact criterion. The trigger is reachable by an ordinary, unprivileged signer simply routing a transaction (e.g. an `ERC20Transfer`) through a `target` contract they interact with, whose response causes the fixed-gas callback to abort.

### Likelihood Explanation
The affected code paths (`nep_141_storage_balance_callback`, `address_check_callback`) attach fixed static gas budgets (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`) plus caller-chosen `action.gas()` to callbacks that must read and deserialize a `PromiseResult` payload coming from a contract the caller does not control the implementation of (the `target`/token contract, or the hardcoded registrar). Since the promise-result payload size and shape are outside the wallet contract's control, an oversized or adversarial response can exhaust the callback's gas budget before it reaches any of the graceful `Err`/`Failed` handling branches, causing an abort rather than a handled failure. This requires no privileged access — only that the account owner (or a relayer acting for them) issue a transaction whose target returns an oversized/malicious response.

### Recommendation
Do not rely on writing `has_in_flight_tx = false` as a side effect that can be rolled back by an unrelated panic later in the same function. Instead:
- Clear `has_in_flight_tx` in a way that is robust to partial failure, e.g., persist it via a low-level, panic-safe mechanism, or restructure callbacks so gas-sensitive/attacker-influenced work (deserializing untrusted promise results) happens in a sub-call whose failure is caught via `PromiseResult::Failed` rather than by unwinding the callback itself.
- Add gas headroom / bound the size of data read from `promise_result` before deserializing, to avoid the callback provably running out of gas on adversarial input.
- Provide an administrative or self-service recovery path (e.g., allow the account's owner key to force-reset `has_in_flight_tx` after some timeout) so a single failed callback cannot permanently brick the account.

### Proof of Concept
1. Deploy a NEP-141-like contract `evil.near` whose `storage_balance_of` method returns a maximal-size (or deeply nested/slow-to-parse) response.
2. From the eth-implicit wallet, sign and submit (via any relayer) an `ERC20Transfer`-emulated transaction targeting `evil.near`.
3. `inner_rlp_execute` builds `nep_141_storage_balance_callback` with a fixed gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` + `action.gas()`); `has_in_flight_tx` is set to `true`, see `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458` / `271`.
4. When the callback runs, reading/deserializing `evil.near`'s oversized response causes the callback to exceed its attached gas and abort before returning a value.
5. Because of the abort, the entire callback receipt's state changes (including the `has_in_flight_tx = false` write at line 202) are rolled back per `runtime/runtime/src/lib.rs:1024-1034`.
6. Any subsequent call to `rlp_execute` on this wallet now permanently returns `"transaction already in progress, please try again later"` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:97-105`), and no recovery function exists to clear the flag — the account is permanently unable to move funds.
