### Title
Vault `initialize()` can be front-run, letting an attacker seed a malicious share price before the DAO's minimum-liquidity deposit lands - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Every Zest vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) is deployed with an `initialized` flag that starts `false` and is only flipped by a separate, public `initialize` function, mirroring the analog report's `Pools.sol` pattern where a contract has an `init()`-style bootstrap step distinct from the constructor/deploy transaction.

### Finding Description
Each vault declares: [1](#0-0) 

and exposes: [2](#0-1) 

`initialize` is guarded against double-initialization (`asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED`), but nothing prevents the vault's other public entry points (deposit, withdraw, borrow, etc., implemented via the `tokenized-vault`/`lending` traits) from being invoked by any ordinary principal in the window between contract deployment and the DAO's `initialize` call. In production this call is only executed later, as part of a DAO proposal: [3](#0-2) 

The purpose of `initialize()` seeding `MINIMUM-LIQUIDITY` to `NULL-ADDRESS` is exactly the standard ERC4626-style defense against the "first depositor / share inflation" attack: it locks in a minimum amount of shares/assets so the share price (`convert-to-shares`/`convert-to-assets`) can't be trivially manipulated by whoever deposits first when `total-supply` and `total-assets` are both zero. Because deposit-style functions are not blocked by the `initialized` flag, an attacker who monitors the deployment transaction can call the vault's own deposit function ahead of the DAO's `initialize` transaction, becoming the true "first depositor" with an arbitrary self-chosen amount and then donating/transferring extra underlying directly to the vault to skew the assets-per-share ratio before the DAO's minimum-liquidity deposit (or any legitimate user's first deposit) executes. This is precisely the front-running-of-initialization root cause described in the M-14 report, just realized against Zest's vault share-price bootstrap invariant rather than `Pools.sol`.

Note: I was not able to fully confirm within the indexed content whether the vault's `deposit` entry point requires the caller to be in `authorized-contracts` (i.e., restricted to the `market` contract) or is open to any principal (the tokenized-vault trait suggests it's meant to be user-facing). This affects whether the attack is reachable by an "ordinary principal" directly or only via a compromised/absent authorization state pre-initialization. Given the size limits on the indexed codebase, this uncertainty could not be resolved with the available tools — a Devin session with full repo access would be needed to inspect the complete `deposit` implementation and its auth checks in `v0-vault-stx.clar` (and siblings) to conclusively confirm the caller-permission gate.

### Impact Explanation
If `deposit` (or equivalent) is callable by an unprivileged principal before `initialize()` runs, this lands on **Temporary freezing of funds** or worse **theft of unclaimed yield**, since a skewed initial share price directly corrupts the vault share-math invariant (`convert-to-shares-preview`/`convert-to-assets-preview`) that all subsequent depositors and the lending accounting rely on, potentially causing legitimate depositors to receive fewer shares than they are entitled to, or the attacker to redeem disproportionately more assets later.

### Likelihood Explanation
Likelihood is judged similarly to the original report's judge comment: harder to execute (requires monitoring/racing the deploy-to-initialize window) and only exploitable during a narrow deployment window, but structurally always present because the DAO's `initialize` call is a separate transaction from vault deployment, giving any observer of the mempool/deploy sequence an opportunity to front-run it. This is not a DAO-compromise scenario; it purely exploits the gap in bootstrap ordering that any ordinary principal can exploit against the vault's own deployed bytecode.

### Recommendation
Guard all state-mutating public functions (deposit/withdraw/borrow/repay/flashloan) with a check on the `initialized` var-get, so they revert until `initialize()` has run, or fold the minimum-liquidity mint into the vault's deploy-time constant setup so there's no separate front-runnable initialization transaction at all.

### Proof of Concept
1. DAO/deployer deploys `vault-stx` (or any vault); `initialized` is `false`.
2. Before the DAO's `proposal-init-vaults` transaction executes `(contract-call? .vault-stx initialize)`, an attacker submits `deposit` with a chosen amount to become the vault's first depositor and receives shares at an arbitrary self-set ratio (total-supply/total-assets both effectively zero or attacker-controlled).
3. Attacker then transfers/donates extra underlying directly to the vault (if the vault's `total-assets-preview` counts raw balance) to inflate `assets-per-share`.
4. The DAO's subsequent `initialize()` call and any real users' deposits are now priced against the attacker-corrupted share ratio, as seen in the initialize flow: [3](#0-2) .
