### Title
Positions with debt in the `(debtFloorInUsd, 2 * debtFloorInUsd)` band can never be liquidated - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two independent bounds on `amountToRepay_`: it cannot exceed `maxLiquidable` (50%) of the account's debt-token balance, and the *remaining* debt after repayment must be either `0` or `>= debtFloorInUsd`. When a position's debt lies in `(debtFloorInUsd, 2 * debtFloorInUsd)`, every admissible repayment either leaves a sub-floor remainder or exceeds the 50% cap, so all liquidations revert. The position becomes permanently unliquidatable.

### Finding Description
In `contracts/Pool.sol`, `liquidate` applies:

```solidity
// contracts/Pool.sol:567-579
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_), _debtTokenBalance - amountToRepay_);
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

`maxLiquidable` is initialized to `0.5e18` (50%) at `contracts/Pool.sol:181`. Let `D` be the position's debt in USD and `F = debtFloorInUsd`. For `F < D < 2F`:

- Any `amountToRepay <= 0.5 * D` leaves remaining debt `> D/2 > 0` and `< D - 0 = D < 2F`; more precisely remaining `∈ (0, F)` for any repay that doesn't zero the debt, and repaying to exactly `0` requires `amountToRepay = D`, i.e. `wadDiv = 1e18 > 0.5e18` → `AmountGreaterThanMaxLiquidable`.
- Any `amountToRepay > 0.5 * D` reverts on the `maxLiquidable` check.

So every possible `amountToRepay_` reverts. `quoteLiquidateMax` (`contracts/Pool.sol:419-440`) only ever returns values `<= maxLiquidable * balance`, so keepers/UIs using it are equally stuck. No privileged action is needed to create the trapped state: an attacker calls `DepositToken.deposit` and `DebtToken.issue` to open a position with total debt just above `F`, then lets collateral price decline (or deliberately pushes it via allowed same-transaction AMM moves where the oracle sources permit). Once `debtPositionOf` reports unhealthy, `liquidate` can never succeed for that account.

`whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, `onlyIfDepositTokenExists`, and the health check do not prevent this; the revert is inside the repayment bounds logic itself. Repaying via `DebtToken.repay/repayAll` is possible but requires a third party to donate synths, which no one is incentivized to do for an insolvent account.

### Impact Explanation
Liquidation liveness for an entire band of positions is permanently broken — the direct analog of the CVE's "repeatable crash / hang (complete DOS)" availability impact. Positions in the trapped band accrue interest indefinitely while collateral value falls, converting a recoverable underwater account into protocol bad debt (insolvency borne by the pool's synthetic-token holders). The attacker can open many such positions cheaply since only the floor-scale debt is needed.

### Likelihood Explanation
Reachable by any EOA through public `deposit`/`issue`/`Operator.execute`. Preconditions: `debtFloorInUsd > 0` configured (the feature exists for this purpose and reverts are unconditional once set) and `maxLiquidable < 1e18` (50% by default and capped at 1e18 by `updateMaxLiquidable` at `contracts/Pool.sol:778-784`). The attacker only needs the position to go unhealthy, which normal market volatility produces; if the pool lists a volatile collateral, the attacker can also force it within a single window by trading the underlying AMM the oracle reads. Note this is a genuine invariant interaction (cap vs floor), not a gas/unbounded-loop issue and not a governance-misconfiguration alone — the math fails for *any* nonzero floor with any `maxLiquidable < 1e18`.

### Recommendation
Allow the debt-floor check to pass when the liquidation fully exits the position under the cap, e.g. treat "repay capped by `maxLiquidable`" and "remaining debt < floor" jointly: if the position's total debt is below the floor-equivalent, permit full liquidation (`amountToRepay_ == _debtTokenBalance`) regardless of `maxLiquidable`, or clamp `amountToRepay_` to the balance and skip the floor check when the position is already below the floor. Alternatively, when computing the floor check, treat remaining debt that results *solely* from the `maxLiquidable` cap as exempt.

### Proof of Concept
Hardhat-style sketch (pool deployed with `debtFloorInUsd = 1000e18`, `maxLiquidable = 0.5e18`):

```typescript
// setup: collateral MET priced so that debt D = 1500e18 USD is just above floor
await metDepositToken.connect(attacker).deposit(collateralFor1500UsdDebt, attacker.address);
await debtToken.connect(attacker).issue(attacker.address, msUsd1500); // D = 1500 USD, F = 1000 USD

// collateral price drops -> position unhealthy
await oracle.setPrice(met.address, lowerPrice);
expect((await pool.debtPositionOf(attacker.address))._isHealthy).to.be.false;

// liquidator holds msUSD and tries every possible repay amount
// (a) full repay: fraction = 1e18 > 0.5e18 -> AmountGreaterThanMaxLiquidable
await expect(pool.connect(liq).liquidate(msUsd, attacker.address, debtBal, metDepositToken))
  .to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// (b) max allowed repay (50%): remaining = 750 USD < floor -> RemainingDebtIsLowerThanTheFloor
await expect(pool.connect(liq).liquidate(msUsd, attacker.address, debtBal.div(2), metDepositToken))
  .to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// (c) any smaller partial repay also leaves remaining in (0, floor) -> same revert
// position is permanently unliquidatable; bad debt accrues via accrueInterest()
```

Caveat: I was unable to confirm the on-chain value of `debtFloorInUsd` for deployed pools from the indexed context; if it is `0` on every live pool, the revert branch is unreachable and this reduces to a latent defect rather than an exploitable one.
