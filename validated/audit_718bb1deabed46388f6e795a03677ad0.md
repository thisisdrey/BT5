### Title
`FORBID_TRANSFER_TO_CONTRACT` governance restriction can be bypassed via TVM CALL, allowing forced TRX/TRC10 delivery to a contract the committee intended to block - ([File: actuator/src/main/java/org/tron/core/vm/VMUtils.java])

### Summary
The `FORBID_TRANSFER_TO_CONTRACT` chain parameter is meant to prevent value (TRX or TRC10) from being sent directly to smart-contract accounts. It is enforced only in the account-level actuators (`TransferActuator`, `TransferAssetActuator`), but the low-level balance-movement primitives used internally by the TVM (`MUtil.transfer`/`MUtil.transferToken`, backed by `VMUtils.validateForSmartContract`) never check this flag. Any contract call that carries `callValue`/`tokenValue` to another contract address bypasses the restriction entirely, mirroring the reported Uniswap issue where a security check that gates a specific privileged/blocked address is enforced only on one entry point (`transfer`) while another entry point (`buy`) that ultimately moves the same balance is left unchecked.

### Finding Description
`TransferActuator.validate()` and `TransferAssetActuator.validate()` explicitly reject a transfer whose recipient is a `Contract`-type account when `dynamicStore.getForbidTransferToContract() == 1`: [1](#0-0) [2](#0-1) 

However, value transfers that happen *inside* TVM execution (e.g. a `CALL` with non-zero value, or an internal TRC10 transfer via `transferToken`) go through `Program.callToAddress()`, which calls `VMUtils.validateForSmartContract(...)` and then `deposit.addBalance`/`deposit.addTokenBalance` directly: [3](#0-2) 

`VMUtils.validateForSmartContract` only checks address validity, self-transfer, account existence, and balance sufficiency — it never reads `DynamicPropertiesStore.getForbidTransferToContract()`: [4](#0-3) 

The same gap exists in `MUtil.transfer`/`MUtil.transferToken`, used for callValue delivery on contract creation/call and for `transferToken` in `VMActuator`: [5](#0-4) [6](#0-5) 

Consequently, an unprivileged transaction broadcaster can trivially route TRX/TRC10 to a "forbidden" contract address by first sending value to an intermediary contract they control, which then forwards it to the target contract via a normal Solidity `.transfer()`/`.call{value:}()`/TRC10 transfer, or by directly calling the target contract with `call_value`/`call_token_value` set on a `TriggerSmartContract`. This is structurally the same class of bug as the reported issue: a single high-level entry point enforces an "address X must not receive funds" invariant, while a different, semantically-equivalent low-level path that moves the exact same kind of balance does not enforce it, letting an attacker fully defeat the protection using only ordinary transactions.

### Impact Explanation
`FORBID_TRANSFER_TO_CONTRACT` is a committee-controlled security parameter (ProposalType #35) specifically designed to stop uncontrolled value injection into arbitrary smart contracts (e.g., to prevent balance-based accounting attacks, unexpected `this.balance` manipulation, or griefing of contracts that rely on `address(this).balance` for accounting, similar in spirit to protecting an unmigrated liquidity pool from balance manipulation). Since the restriction can be fully bypassed through TVM-level calls, any contract whose logic depends on this invariant holding (e.g., contracts that assume they cannot receive unsolicited TRX/TRC10, or that a specific target contract is unreachable) can have their balance manipulated regardless of the flag, enabling accounting exploitation or reentrancy-adjacent value injection attacks that the FORBID_TRANSFER_TO_CONTRACT was meant to prevent.

### Likelihood Explanation
Likelihood is high for any attacker who wants to move value into a specific contract while the flag is enabled: it requires only deploying a trivial forwarding contract (or directly triggering the target contract with `call_value`), which is available to any account able to broadcast a `TriggerSmartContract`/`CreateSmartContract` transaction — no special privileges needed.

### Recommendation
Enforce `dynamicStore.getForbidTransferToContract()` (and the related `AllowTvmCompatibleEvm` contract-version check) inside `VMUtils.validateForSmartContract` (and/or `MUtil.transfer`/`MUtil.transferToken`) so that the restriction applies uniformly to both the actuator-level transfer paths and the internal TVM value-transfer paths, closing the gap between the two enforcement points.

### Proof of Concept
1. Committee enables `FORBID_TRANSFER_TO_CONTRACT` (`dynamicStore.saveForbidTransferToContract(1)`).
2. Attacker deploys `Forwarder` contract with a payable fallback that does `target.transfer(msg.value)` (or `target.call{value: msg.value}("")`), where `target` is the protected contract address.
3. Attacker sends a `TriggerSmartContract` transaction with non-zero `call_value` to `Forwarder`.
4. `TransferActuator`/`TransferAssetActuator` are never invoked for the second hop — the TRX moves via `Program.callToAddress()` → `VMUtils.validateForSmartContract()` → `deposit.addBalance(target, amount)`, none of which check `getForbidTransferToContract()`.
5. `target`'s balance increases despite the governance-level prohibition, demonstrating the bypass.

  public static boolean validateForSmartContract(Repository deposit, byte[] ownerAddress,
      byte[] toAddress, long amount) throws ContractValidateException {
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid ownerAddress!");
    }
    if (!DecodeUtil.addressValid(toAddress)) {
      throw new ContractValidateException("Invalid toAddress!");
    }

    if (Arrays.equals(toAddress, ownerAddress)) {
      throw new ContractValidateException("Cannot transfer TRX to yourself.");
    }

    AccountCapsule ownerAccount = deposit.getAccount(ownerAddress);
    if (ownerAccount == null) {
      throw new ContractValidateException("Validate InternalTransfer error, no OwnerAccount.");
    }

    AccountCapsule toAccount = deposit.getAccount(toAddress);
    if (toAccount == null) {
      throw new ContractValidateException(
          "Validate InternalTransfer error, no ToAccount. And not allowed to create an account in a smartContract.");
    }

    long balance = ownerAccount.getBalance();

    if (amount < 0) {
      throw new ContractValidateException("Amount must be greater than or equals 0.");
    }

    try {
      if (balance < amount) {
        throw new ContractValidateException(
            "Validate InternalTransfer error, balance is not sufficient.");
      }

      addExact(toAccount.getBalance(), amount, VMConfig.disableJavaLangMath());
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }

    return true;
  }

  public static void transfer(Repository deposit, byte[] fromAddress, byte[] toAddress, long amount)
      throws ContractValidateException {
    if (0 == amount) {
      return;

    VMUtils.validateForSmartContract(deposit, fromAddress, toAddress, amount);
    deposit.addBalance(toAddress, amount);
    deposit.addBalance(fromAddress, -amount);
  }

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }

  public static void transferToken(Repository deposit, byte[] fromAddress, byte[] toAddress,
      String tokenId, long amount)

      return;

    deposit.addTokenBalance(toAddress, tokenId.getBytes(), amount);
    deposit.addTokenBalance(fromAddress, tokenId.getBytes(), -amount);
  }
