### Title
Attacker can grief users by filling their `MAX_TOKENS_PER_USER` slots with dust msdTOKEN transfers, blocking all new deposits and borrows — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The reported bug class is *unvalidated, attacker-controllable account identifier / front-running griefing*: an unprivileged user can cheaply pre-empt or poison a victim's operation so that the victim's transaction reverts, costing them gas and denying service. The strongest Metronome analog lives in the per-account token lists in `Pool` (`depositTokensOfAccount` / `debtTokensOfAccount`), which are capped by `MAX_TOKENS_PER_USER` and are mutated not only by deposits/mints but also by plain ERC20 `transfer`/`transferFrom` of `DepositToken` shares. Because `DepositToken` positions are freely transferable, an attacker can push dust msdTOKENs into a victim's account, filling all list slots. Once the cap is reached, every subsequent `deposit`, `mint` (borrow) or `transfer` that would add a *new* token for that victim reverts with `UserReachedMaxTokens` — the attacker can also front-run a victim's pending deposit of a new collateral type to make it revert.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` [1](#0-0) [2](#0-1) .

The critical property is that list membership is added on **behalf of the recipient** inside `DepositToken._transfer`: whenever a recipient's balance of a deposit token goes from 0 to non-zero, `pool.addToDepositTokensOfAccount(recipient_)` is invoked [3](#0-2) . Transfers are public and only check the *sender's* unlocked balance (`_revertIfLocked`), never the recipient's list capacity before adding — the cap check happens inside the Pool call and simply reverts the whole transaction [4](#0-3) .

Attack path (all unprivileged, public entry points):
1. Attacker calls `deposit(1 wei, attacker)` on `K` distinct `DepositToken`s (or uses `transferFrom` relay), obtaining dust balances in `K` different msdTOKENs.
2. Attacker calls `depositToken.transfer(victim, 1)` for each of the `K` tokens. Each call appends that token to `depositTokensOfAccount[victim]` until `debt + deposit` count hits `MAX_TOKENS_PER_USER`.
3. From then on: victim's `DepositToken.deposit(...)` into any *new* collateral reverts in `_mint → addToDepositTokensOfAccount` [5](#0-4) ; victim's borrow (`DebtToken.issue/mint`, which adds the debt token to `debtTokensOfAccount` when the balance moves from zero) reverts identically; and any third party transferring the victim a new msdTOKEN reverts.
4. To gas-grief deterministically, the attacker watches the mempool and executes the dust-filling transfer *before* a victim's first-time deposit/borrow transaction, so the victim's transaction reverts after paying gas — directly analogous to the front-running `createAccount` grief in the report.

Nothing stops this: there is no opt-in/whitelist for receiving msdTOKENs, no minimum transfer amount, no `SynthContext`/meta-sender restriction on `transfer`, and the `onlyIfAdditionWillNotReachMaxTokens` cap is checked against the *recipient* while being triggered by the *sender*. The `nonReentrant` guard, pause flags and `onlyIfDepositTokenExists` checks do not help — the griefing path uses the normal transfer flow, and `addToDepositTokensOfAccount` deliberately accepts the recipient as a parameter with only a `address(0)` caution noted [6](#0-5) .

### Impact Explanation
- **Temporary freezing of funds / denial of position management**: while the victim's list is saturated, they cannot deposit any new collateral type and cannot open any new debt position (mint/issue path adds the debt token to the account list). If the victim had a pending intent (e.g., deposit new collateral to rescue an unhealthy position), the block is griefed.
- **Gas griefing (the direct analog of the report)**: front-running a victim's transaction causes it to revert with `UserReachedMaxTokens`, burning the victim's gas — same economic shape as the reported `createAccount` front-run.
- Recovery requires the victim to fully empty one dusted token (transfer it out so `removeFromDepositTokensOfAccount` fires), costing additional transactions and gas for every slot the attacker filled [7](#0-6) .

### Likelihood Explanation
- Fully unprivileged: only needs public `deposit`/`transfer`.
- Cost: one dust deposit per token (gas + a negligible amount of each underlying, which can be the cheapest-to-deposit collateral reused across Pools' deposit tokens the attacker already holds); dust msdTOKENs remain recoverable by the attacker afterward, so the only real cost is gas.
- No timing assumption beyond a standard mempool front-run for the revert-griefing variant; the list-filling variant works at any time.

### Recommendation
- Only add a token to `depositTokensOfAccount`/`debtTokensOfAccount` via the explicit user actions (`deposit`, borrow issuance) — i.e., skip or soften `addToDepositTokensOfAccount` on inbound `transfer`/`transferFrom`/`seize`, or gate it on the recipient's consent.
- Alternatively, treat unsolicited dust as non-counting: only register a token once the recipient's balance exceeds a protocol-defined minimum, or allow the recipient to self-remove tokens without fully zeroing the balance.
- If list membership on transfer is retained, make `transfer`/`transferFrom` revert with a dedicated, recipient-aware check so a malicious sender bears the failure, and document that `MAX_TOKENS_PER_USER` slots are attacker-fillable.

### Proof of Concept
Foundry-style test (assumes a deployed/initialized `Pool` with `K` registered active `DepositToken`s, where `K` ≥ `MAX_TOKENS_PER_USER` minus the victim's current list length):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.24;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {DepositToken} from "contracts/DepositToken.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DustGrief_Test is Test {
    Pool pool;                 // forked / deployed instance
    DepositToken[] dTokens;    // registered deposit tokens of the pool
    IERC20[] underlyings;
    address victim = address(0xV1C);
    address attacker = address(0xA77);

    function test_DustFillBlocksVictimDeposit() public {
        uint256 cap = pool.MAX_TOKENS_PER_USER(); // public constant
        uint256 slots = cap; // assume victim currently at 0

        // 1) Attacker deposits dust into `slots` distinct deposit tokens
        for (uint256 i; i < slots; ++i) {
            IERC20 u = dTokens[i].underlying();
            deal(address(u), attacker, 1);           // 1 wei of underlying
            vm.startPrank(attacker);
            u.approve(address(dTokens[i]), 1);
            dTokens[i].deposit(1, attacker);         // attacker holds dust msdTOKEN
            vm.stopPrank();
        }

        // 2) Attacker transfers 1 wei of each msdTOKEN to the victim
        for (uint256 i; i < slots; ++i) {
            vm.prank(attacker);
            dTokens[i].transfer(victim, 1);          // fills depositTokensOfAccount[victim]
        }
        assertEq(
            pool.depositTokensOfAccountLength(victim) /* getter over MappedEnumerableSet */,
            slots
        );

        // 3) Victim's deposit of a NEW collateral now reverts
        DepositToken newDT = dTokens[slots];         // one more registered token
        IERC20 un = newDT.underlying();
        deal(address(un), victim, 1e18);
        vm.startPrank(victim);
        un.approve(address(newDT), 1e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newDT.deposit(1e18, victim);                 // _mint -> addToDepositTokensOfAccount -> revert
        vm.stopPrank();

        // 4) Same blocking applies to borrowing a new debt token
        //    (DebtToken.issue/mint -> pool.addToDebtTokensOfAccount(victim) -> revert)

        // 5) Front-run variant: attacker executes step 2 while the victim's
        //    deposit tx is pending -> victim's tx reverts, gas is lost.
    }
}
```

**Caveats / unverified details:** the exact value of `MAX_TOKENS_PER_USER` and the public getter names over `MappedEnumerableSet` were not fully enumerated in this pass; the PoC assumes enough distinct deposit tokens exist across registered `DepositToken`s to reach the cap — on deployments with few collateral types the attacker may need `debtTokensOfAccount` slots too, which are only added via actual borrows, limiting the attack on such pools. Also note that on pools where the number of registered deposit tokens is below the cap, the attack only constrains, not fully blocks, the victim.
