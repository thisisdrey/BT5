### Title
Untrusted Pointer Dereference in ijar's ZIP Central Directory Parser via Unbounded Length Fields - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` advances the raw central-directory cursor `p` using attacker-controlled `file_name_length`, `extra_field_length`, and `file_comment_length` fields without ever checking that the resulting pointer stays inside the memory-mapped file. This is the same bug class as CVE-2021-46023 (untrusted pointer dereference causing a crash while parsing attacker-supplied bytes): a malicious but checksum-valid `.jar`/`.zip` dependency can drive `p` past the end of the `mmap`'d buffer, causing an out-of-bounds read and SIGSEGV in the `ijar`/`singlejar` toolchain that Bazel invokes on every Java dependency to build interface jars.

### Finding Description
`ijar` (used to build interface jars for `java_library`/`java_import` and consumed by `singlejar`) opens the downloaded/checked-out jar with `InputZipFile::Open` → `FindZipCentralDirectory`, then iterates central-directory entries via `InputZipFile::ProcessNext` → `ProcessCentralDirEntry`: [1](#0-0) 

Compare this with `ProcessLocalFileEntry`, which explicitly guards every pointer advance with `EnsureRemaining()`: [2](#0-1) 

`ProcessCentralDirEntry` has **no equivalent bounds check**. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` as raw `u2` values (up to 65535 each) straight from attacker-controlled bytes and unconditionally does:
```
p += file_name_length;
...
p += extra_field_length;
...
p += file_comment_length;
```
with no comparison against the mapped file's end. The `while (extra_p != p)` extra-field loop (lines 526-541) is similarly unchecked and can read `header_id`/`data_size` from anywhere `extra_p` lands. Because `ProcessNext()` is invoked repeatedly for however many entries the crafted central directory claims to contain, an attacker can chain several oversized length fields to walk `p` arbitrarily far past the actual mmap'd extent, then have the *next* `get_u4le(p)`/`get_u2le(p)` call dereference unmapped memory.

This directly maps to the "Extraction and patching" surface named in the bug-class list (`ZipDecompressor`-equivalent parsing code) and is a genuine, reachable Untrusted Pointer Dereference: attacker-published archive bytes flow straight into pointer arithmetic with no containment check, mirroring `mrb_vm_exec`'s unchecked pointer dereference on attacker-controlled bytecode in CVE-2021-46023.

### Impact Explanation
Bazel invokes `ijar` on essentially every Java dependency jar to strip it down to an interface jar (and `singlejar` uses the analogous, but bounds-checked, zip reader in `src/tools/singlejar/`). A jar fetched from an `http_jar`/`http_archive`/Maven-style dependency whose SHA-256/integrity the attacker computes over their own crafted file passes Bazel's checksum gate cleanly — the checksum only proves byte-for-byte integrity of the download, not structural validity of the ZIP format. The malformed central directory then reaches `ijar`'s unguarded parser and crashes the build (worker) process with a SIGSEGV. This is a denial-of-service/crash of the build action for any consumer of that dependency, consistent with the "segmentation fault and application crash" impact described in the CVE.

### Likelihood Explanation
High for any project that consumes a third-party jar via a URL or registry the attacker controls or can influence (e.g., a compromised mirror, or the attacker is the legitimate publisher of a malicious library version). No privileged access, no MITM, and no bypass of the declared checksum is required — the attacker simply computes a correct hash over their own malformed jar. Because `ijar` runs unconditionally as part of normal Java build actions, the crash is trivially triggered on first build.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before advancing `p` by `file_name_length`, `extra_field_length`, or `file_comment_length`, verify the remaining central-directory/mapped-file extent is sufficient, and reject (`error(...)`) rather than dereference when it is not. The `while (extra_p != p)` extra-field loop should also bound-check `data_size` against the remaining `extra_field_length` before advancing.

### Proof of Concept
Extend the existing ijar test harness (`third_party/ijar/test/IjarTests.java` / `third_party/ijar/test/ijar_test.sh`) with a crafted `.zip`:
1. Build a minimal valid EOCD/ECD record declaring N central-directory entries.
2. For the last declared entry, set `extra_field_length` (or `file_comment_length`) to `0xFFFF` while providing far fewer actual bytes in the file (i.e., truncate the file right after the CDH's fixed fields).
3. Run `ijar` (or call `ZipExtractor::Create(...)->ProcessNext()` directly, mirroring `PartialZipExtractor::UnzipUntil` in `src/main/cpp/archive_utils.cc`) against this file.
4. Observe a SIGSEGV/out-of-bounds read inside `InputZipFile::ProcessCentralDirEntry` (`third_party/ijar/zip.cc:507-525`) instead of a graceful `error("invalid central file header ...")`, confirming the untrusted pointer dereference. [3](#0-2)

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
