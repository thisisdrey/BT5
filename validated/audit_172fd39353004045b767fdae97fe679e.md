### Title
Data race on unsynchronized static `ENERGY_LIMIT_HARD_FORK` flag read during concurrent transaction/energy-limit processing - ([File: common/src/main/java/org/tron/common/parameter/CommonParameter.java])

### Summary
`CommonParameter.ENERGY_LIMIT_HARD_FORK` is a plain (non-`volatile`) `public static boolean` field that is written from the consensus/governance path via `VMConfig.initVmHardFork()` (itself driven by `ConfigLoader.load()` on every transaction/block processed) and read concurrently by `ReceiptCapsule.checkForEnergyLimit()` and `StorageUtils.getEnergyLimitHardFork()` from transaction-execution threads. This mirrors the CVE-2022-49639 class of bug: a globally-shared configuration flag mutated by one path and read by concurrent paths without the memory-visibility guarantee (`READ_ONCE`/`volatile`) needed for safe concurrent access.

### Finding Description
`ENERGY_LIMIT_HARD_FORK` is declared as: [1](#0-0) 

It is written by `VMConfig.initVmHardFork(boolean pass)`: [2](#0-1) 

which is invoked on every call to `ConfigLoader.load()`, itself invoked on every transaction validated through `VMActuator.validate()` — i.e., on every broadcast smart-contract call/creation and constant call, from potentially many concurrently-executing transaction/RPC threads: [3](#0-2) [4](#0-3) 

The same flag is read without any synchronization from `StorageUtils.getEnergyLimitHardFork()`: [5](#0-4) 

and from `ReceiptCapsule.checkForEnergyLimit()`, which is called by `ConfigLoader.load()` on the transaction-execution path itself.

Because the field is neither `volatile` nor accessed under a lock, there is no guarantee that a write on one thread (from block application / governance-proposal handling) becomes visible to a reader on another thread (transaction validation/execution). Under the Java Memory Model this is a genuine data race: readers may observe a stale value indefinitely, and in the worst case (with aggressive JIT optimizations akin to compiler tearing/hoisting that `READ_ONCE`/`volatile` prevent in the kernel analog) could get inconsistent results across calls within the same logical operation.

### Impact Explanation
`ENERGY_LIMIT_HARD_FORK` gates energy-limit enforcement logic (`checkForEnergyLimit`) that affects the max-CPU/energy calculations used in transaction execution and constant calls (`VMActuator.validate()` divides `feeLimit` by `getEnergyFee()`, gated by hard-fork state). A stale/incorrect read of this flag under concurrent load could cause energy-limit checks to be applied inconsistently across concurrently executing transactions on the same node, potentially permitting transactions to execute with the wrong energy/CPU accounting policy or causing divergent results across nodes if some threads observe the flag flip and others don't in the same block-processing window. This falls into "unbacked balance / incorrect resource accounting" territory reachable from an unprivileged transaction broadcaster, but the severity is bounded because reads eventually settle (flag flips are rare, tied to hard-fork activation) and there's no direct fund theft primitive demonstrated.

### Likelihood Explanation
The write happens only on the (rare) hard-fork activation transition, but the field is read on every single transaction/constant-call validation path from many threads concurrently (`ConfigLoader.load()` is on the hot path for every `TriggerSmartContract`/`CreateSmartContract`). This gives a wide reader surface with a narrow but real writer window, making a torn/stale read plausible around the activation boundary, exactly analogous to the cipso sysctl race (frequent concurrent reads, occasional concurrent write).

### Recommendation
Mark `CommonParameter.ENERGY_LIMIT_HARD_FORK` as `volatile` (or route reads exclusively through a `volatile`-backed accessor as `VMConfig`'s `Snapshot`/`globalSnapshot` pattern already does for the other governance flags) so that writes from the block-processing path are safely published to concurrent transaction-execution readers, consistent with the fix pattern already applied in `VMConfig.globalSnapshot`: [6](#0-5) 

### Proof of Concept
1. Thread A (governance/consensus path) processes the block that activates the energy-limit hard fork, calling `VMConfig.initVmHardFork(true)` which performs a plain, non-volatile write to `CommonParameter.ENERGY_LIMIT_HARD_FORK`.
2. Thread B (concurrently executing a `TriggerSmartContractContract`/`CreateSmartContractContract` broadcast by an unprivileged user) calls `ConfigLoader.load()` → `ReceiptCapsule.checkForEnergyLimit()` → (indirectly) `StorageUtils.getEnergyLimitHardFork()`, reading the flag with no `volatile`/lock synchronization.
3. Without a memory barrier, the JMM does not guarantee Thread B observes Thread A's write promptly (or in the correct order relative to other state changes made in the same block-processing step), so Thread B may apply energy-limit logic based on the pre-activation state even after activation is logically complete, producing inconsistent energy accounting across concurrently processing transactions.
