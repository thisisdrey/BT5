### Title
Stale PostponedReceiptId/PendingDataCount/PostponedReceipt rows survive account deletion, letting a resumed cross-contract callback execute with self-call authority against a re-created account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in [1](#0-0) , invoked from `action_delete_account` in [2](#0-1) , only clears `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for the deleted account. It never touches `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` rows. If an account has an outstanding cross-contract callback awaiting a `DataReceipt` when it self-destructs, those rows remain keyed to the (now-vacant) account name. If the same account name is later re-created and the delayed `DataReceipt` finally arrives, `process_receipt` will still match the stale `PostponedReceiptId`, decrement `PendingDataCount`, and execute the stale `PostponedReceipt` against the newly created account.

### Finding Description
When an `ActionReceipt` destined for account `A` has unmet `input_data_ids` (e.g., a `.then()` callback awaiting a cross-contract call result from `B`), the runtime postpones it by writing:
- `PostponedReceiptId{receiver_id:A, data_id}` → `receipt_id`
- `PendingDataCount{receiver_id:A, receipt_id}` → count
- `PostponedReceipt{receiver_id:A, receipt_id}` → the full receipt

This is done in `process_action_receipt`/documented in [3](#0-2) , and consumed in `process_receipt`'s `Data` branch at [4](#0-3) , which looks up the receiver purely by `account_id` string with no binding to the account's identity/incarnation (no nonce, creation height, or code-hash check).

`action_delete_account` performs a storage-usage check and a gas-key-balance check, but nothing about outstanding postponed receipts, then calls `remove_account`: [5](#0-4) 

`remove_account` only removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [6](#0-5) 

It does not iterate/remove `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, or `POSTPONED_RECEIPT` columns for the account, confirmed by the column list in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` at [7](#0-6)  versus the actual removal logic. These rows are also excluded from storage-usage accounting (`StorageComputer::process_record` returns `None` for `PostponedReceipt`/`ReceivedData`), per [8](#0-7) , so the delete-account storage-usage cap in `action_delete_account` cannot detect or block this condition either.

Exploit flow:
1. Attacker controls a parent account (e.g., `attacker.near`) and creates subaccount `A = "child.attacker.near"`, deploying a contract that does a cross-contract call to attacker-controlled contract `B` with a `.then()` callback back to `A`.
2. The callback receipt (self-receipt, `predecessor_id == receiver_id == A`) arrives at `A`'s shard before `B`'s `DataReceipt`, so it is postponed: `PostponedReceiptId{A,data_id}`, `PendingDataCount{A,receipt_id}`, `PostponedReceipt{A,receipt_id}` are written.
3. Before `B` responds, the attacker submits `DeleteAccountAction{beneficiary_id: attacker}` on `A`. `remove_account` deletes `A`'s account/keys/contract/data but leaves the three postponed-receipt rows dangling.
4. The attacker (via the parent `attacker.near`, which they still control) issues `CreateAccountAction` to re-create `A` with a different contract/keys/balance.
5. `B` (attacker-controlled) finally emits the delayed `DataReceipt` for `data_id`. `process_receipt`'s `Data` branch matches the stale `PostponedReceiptId{A,data_id}`, decrements `PendingDataCount` to 0, fetches the stale `PostponedReceipt`, and calls `apply_action_receipt` against the *current* (newly created) account state for `A`.
6. The resumed receipt still carries `predecessor_id == receiver_id == A` (self-call / `sir=true`), giving it the same trust level a legitimate self-call would have on the new account — bypassing any `#[private]`/self-only guard the new deployment relies on, and potentially transferring funds, corrupting storage, or granting access on the new account's assets.

None of the existing checks (nonce/signature validation, access-key permission checks, storage-staking limits, `DeleteAccountWithLargeState`, `GasKeyBalanceTooHigh`) inspect or block this condition, because postponed-receipt state is intentionally excluded from account storage accounting and `remove_account` was never extended to sweep it.

### Impact Explanation
This is an authorization-escalation / promise-resumption bug: a receipt authorized under one account incarnation executes with full self-call privilege against a later, unrelated incarnation of the same account name. In deployments where account names are reused (subaccount factories, username-reclaim platforms, or an attacker deliberately recreating their own subaccount to trigger a stale privileged self-call), this can be used to run arbitrary residual logic — including fund transfers or state corruption — on an account the "resumed" receipt's real owner never authorized. This matches the "authorization escalation across accounts or promises" and potential "theft/freezing of funds" bounty categories.

### Likelihood Explanation
Preconditions are attacker-affordable: control of a parent account able to re-create the subaccount name, a contract capable of a cross-contract call + callback, and a colluding/attacker-controlled callee `B` that can delay its `DataReceipt`. No validator, node, or protocol-level access is required — only ordinary signed transactions (`FunctionCall`, `DeleteAccount`, `CreateAccount`) from accounts the attacker owns. The scenario is fully attacker-repeatable in a controlled account hierarchy; the main limiting factor for cross-victim impact is convincing/arranging for the *same* account name to later be legitimately re-created by a third party (e.g., a username-reuse or subaccount-recycling application), which is a plausible but narrower real-world precondition than a pure self-attack.

### Recommendation
Extend `remove_account` (or `action_delete_account`) to also iterate and remove all `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt` (and ideally `ReceivedData`, `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId`) rows keyed to the deleted `account_id` before the account is removed, refunding/discarding any postponed receipt appropriately (e.g., generating a failure/refund receipt) rather than leaving it resumable. Alternatively, disallow `DeleteAccount` while the account has any outstanding postponed receipts or pending data counts.

### Proof of Concept
Runtime integration test (`runtime/runtime/src` apply/integration test):
1. Set up account `A` with a contract, and an `ActionReceipt` targeting `A` with `input_data_ids: [data_id]` that is not yet satisfied — assert it is stored as `PostponedReceiptId{A,data_id}`, `PendingDataCount{A,receipt_id}`, `PostponedReceipt{A,receipt_id}`.
2. Apply a `DeleteAccountAction` receipt for `A` (via `action_delete_account`/full `apply`), then assert `get(state_update, &TrieKey::PostponedReceiptId{A,data_id})`, `PendingDataCount{A,receipt_id}`, and `PostponedReceipt{A,receipt_id}` are still `Some(..)` (demonstrating the bug) rather than `None`.
3. Apply a `CreateAccountAction` re-creating `A` with new keys/contract/balance.
4. Deliver the pending `DataReceipt{receiver_id:A, data_id}` and assert that `process_receipt` executes the stale postponed `ActionReceipt` against the newly created `A` (e.g., observe a state mutation or balance transfer on the new account that the new owner never authorized), confirming the authorization-exactness violation.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

## Postponed receipts

For each awaited `DataReceipt` we store

*key = `receiver_id`,`data_id`*
*value = `receipt_id`*

Runtime saves incoming [ActionReceipt](Receipts.md#actionreceipt) until all required `DataReceipt` items for the same `receiver_id` have been received and matched, so that the postponed `receipt_id` receipt can be executed once its data dependencies are fully satisfied. See the [Receipt Case](Receipts.md#case-1-call-to-multiple-contracts-and-await-responses) for more details.
