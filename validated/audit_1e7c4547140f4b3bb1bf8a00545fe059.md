Audit Report

## Title
Bridge close/reopen with a reused deterministic `LaneId` resets message nonces, allowing duplicate dispatch of an already-settled XCM message - (File: `bridges/modules/xcm-bridge-hub/src/lib.rs`)

## Summary
`pallet_xcm_bridge_hub::close_bridge` fully purges `InboundLaneData`/`OutboundLaneData` for a lane once its queued outbound messages are drained, and removes the corresponding `Bridges`/`LaneToBridge` entries. Because `LaneId` is deterministically derived from the two endpoint locations and is explicitly documented to "never change," a subsequent `open_bridge`/`do_open_bridge` call between the same two endpoints recreates the lane at the identical `LaneId` with a fresh, zeroed `last_delivered_nonce`, which is the sole replay-protection state checked by `InboundLane::receive_message`.

## Finding Description
`close_bridge` mutates the bridge to `Closed`, drains up to `may_prune_messages` outbound queue entries, and once the outbound queue is empty calls `inbound_lane.purge()` / `outbound_lane.purge()`, followed by `Bridges::<T, I>::remove(...)` and `LaneToBridge::<T, I>::remove(bridge.lane_id)`: [1](#0-0) 

`LaneId` is a pure function of the two bridge endpoint locations and the pallet's own doc comments state it must "never change," since it is embedded in cross-chain message-key proofs: [2](#0-1) 

`do_open_bridge` re-inserts the `Bridges` and `LaneToBridge` entries for the same `lane_id` (both `try_mutate`/`try_mutate_exists` succeed because the prior entries were removed by `close_bridge`), and then unconditionally calls `create_inbound_lane`/`create_outbound_lane`: [3](#0-2) 

`create_inbound_lane`/`create_outbound_lane` insert `InboundLaneData { state: Opened, ..Default::default() }` (i.e., `last_delivered_nonce = 0`) and `OutboundLaneData { state: Opened, ..Default::default() }` for that `lane_id`: [4](#0-3) 

The messages pallet's only replay check for inbound delivery is that the supplied nonce equals `last_delivered_nonce + 1`: [5](#0-4) 

There is no independent, permanent record of nonces already dispatched at a given `LaneId` outside of this per-lane counter, so once the lane is recreated with `last_delivered_nonce = 0`, nonce `1` (and subsequent nonces already dispatched in the bridge's prior lifetime) become acceptable again.

## Impact Explanation
If exploited, this would allow duplicate dispatch of an already-settled cross-chain XCM message (e.g., an asset teleport/reserve-transfer), causing the destination chain to execute the same fund-moving instruction twice — an unbacked mint/unlock or duplicate settlement, which matches the "theft or unbacked mint or unlock" / "duplicate settlement or payout" categories in the impact gate. This is a legitimate structural defect in the replay-protection design: the pallets rely entirely on a per-lane monotonic counter that is deleted and reset to zero by ordinary `close_bridge`/`open_bridge` operations rather than being permanently retired per `LaneId`.

## Likelihood Explanation
`close_bridge` and `open_bridge` are unprivileged, signed-origin extrinsics reachable by any origin satisfying `T::OpenBridgeOrigin` (typically a sibling parachain or the relay chain acting as one endpoint), and `receive_messages_proof` is a permissionless relayer extrinsic. However, actual exploitation requires the attacker/relayer to submit a storage/finality proof for a source-chain header containing the original (already-delivered) message, verified against the currently-recognized finalized state tracked by the bridged GRANDPA/parachains header-chain pallet. Whether an old header remains verifiable after enough time/blocks have passed depends on the pruning behavior of those header-chain pallets (e.g., `pallet-bridge-grandpa`'s retained header set), which I was not able to fully verify within the available tool budget. This external constraint affects exploitation feasibility/timing but does not change the fact that the nonce-reset defect itself exists in the code as described: the messages pallet's replay protection is fully reset by an ordinary bridge close/reopen cycle at the same `LaneId`, and no additional binding (epoch, generation counter, or permanent nonce ledger) prevents reuse.

## Recommendation
Do not fully reset per-lane nonce counters when reopening a bridge on a `LaneId` that was previously used and purged. Options:
- Persist `last_delivered_nonce` (and outbound `latest_generated_nonce`) across `close_bridge`/`open_bridge` cycles for a given `LaneId` instead of deleting the storage entries, so the nonce counter is monotonic per `LaneId` across its entire lifetime.
- Introduce a bridge "epoch"/"generation" identifier that increments on every `open_bridge` and is bound into the nonce/replay domain, so a proof anchored to a prior epoch is rejected even if the raw nonce coincides.
- Generate a fresh, never-reused `LaneId` (rather than the deterministic endpoint-derived one) whenever a bridge is fully closed and reopened, or refuse `open_bridge` for endpoint pairs whose `LaneId` was previously purged unless an explicit continuation mechanism preserves the prior nonce state.

## Proof of Concept
1. Chains A and B open a bridge; lane `L = calculate_lane_id(A, B)` is created via `do_open_bridge` in `Opened` state with `InboundLaneData::default()` (`last_delivered_nonce = 0`).
2. A message is sent with nonce 1 and delivered via `receive_messages_proof`, dispatching an XCM that unlocks/mints funds on chain B. The relayer retains the message bytes and the finality/storage proof used.
3. The bridge owner calls `close_bridge` repeatedly until the outbound queue is drained; the pallet then executes `inbound_lane.purge()` / `outbound_lane.purge()` and removes `Bridges`/`LaneToBridge` for lane `L` (`bridges/modules/xcm-bridge-hub/src/lib.rs` L408-412).
4. The bridge is reopened for the same `(A, B)` pair via `open_bridge` → `do_open_bridge`, which recreates lane `L` via `create_inbound_lane`, resetting `last_delivered_nonce` to 0 (`bridges/modules/messages/src/lanes_manager.rs` L68-83).
5. The relayer resubmits the original nonce-1 message/proof from step 2 via `receive_messages_proof`. `InboundLane::receive_message` sees `Some(1) == data.last_delivered_nonce().checked_add(1)` (now `Some(0+1)`), the nonce check passes, and the same fund-moving XCM is dispatched a second time — contingent on the header/finality proof from step 2 still being acceptable to the source-chain light client pallet at the time of resubmission.
