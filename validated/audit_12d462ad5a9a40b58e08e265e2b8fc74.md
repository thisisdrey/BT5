### Title
Protocol fee on token swaps can be fully bypassed by using `Transfer` intents instead of `TokenDiff` - (File: `contracts/defuse/core/src/intents/tokens.rs`)

### Summary
The protocol fee (`fee`/`fee_collector`) is only computed and collected inside `TokenDiff::execute_intent`, based on the negative deltas ("token_in") of a diff. However, the exact same economic outcome — an atomic P2P swap between two parties — can be achieved by having each party sign a `Transfer` intent instead of a `TokenDiff` intent and bundling both signed payloads into a single `execute_intents`/`MultiPayload` call. `Transfer::execute_intent` performs a raw balance move (`internal_sub_balance` / `internal_add_balance`) with no fee logic whatsoever, so the protocol fee is entirely avoided while the swap still settles atomically.

### Finding Description
The fee is only ever assessed in one code path: [1](#0-0) 

Note the comment "take fees only from negative deltas (i.e. token_in)" — this fee logic exists exclusively inside `TokenDiff`.

In contrast, the `Transfer` intent moves balances directly with no fee assessment at all: [2](#0-1) 

The engine executes an arbitrary list of independently-signed `MultiPayload`s atomically in a single call, verifying each signature/nonce and applying all intents, then checking global balance conservation at the end: [3](#0-2) [4](#0-3) 

The project's own README describes the canonical "trustless P2P swap" use case as exactly this pattern — two independently signed intents bundled into one `execute_intents` call and settled atomically: [5](#0-4) 

Nothing prevents the two counterparties from using `Transfer` intents for this same "swap" pattern (each transferring token A to the other in exchange for token B) instead of `TokenDiff`. Since `Transfer` has no fee logic, the exact same value transfer that would normally be charged a fee under `TokenDiff` completely bypasses `fee_collector` when performed as a matched pair/set of `Transfer` intents.

This is the intents-repo analog of the reported bug class: a custody-adjacent action (swap settlement) that is supposed to always pay a fee (fees owed vs. fees collected) has an alternate, fully-authorized, in-scope code path (`Transfer`) that achieves the identical balance movement with zero fee collected.

### Impact Explanation
This breaks the "fees owed versus fees collected" invariant expected of the protocol: any solver/market-maker or pair of counterparties can route 100% of their swap volume through paired `Transfer` intents instead of `TokenDiff`, permanently denying the `fee_collector` (and thus the DAO/protocol) all protocol fee revenue on that volume, with no loss to the counterparties themselves. Per the stated impact categories this is a fee-bypass issue (Critical: "fees bypassed or over-collected").

### Likelihood Explanation
High. No privileged role, relayer key, or special configuration is required — any two (or more) unprivileged accounts with existing balances in the Verifier contract can construct and sign ordinary `Transfer` intents and submit them together via the public `execute_intents` entrypoint. This requires no more sophistication than constructing a normal `TokenDiff`-based swap (which is documented/expected usage), just substituting the intent type.

### Recommendation
Consider moving fee assessment out of the `TokenDiff`-specific path and into a common settlement/balance-application layer (e.g. inside `internal_apply_deltas` or a shared post-processing step over all balance-affecting intents in a batch), so that any intent causing a negative balance delta on a signer (whether via `TokenDiff` or `Transfer`) is subject to the same fee policy. Alternatively, treat `Transfer` between two distinct accounts occurring within the same batch as a swap subject to fee if it is "matched" by an inverse transfer, though a structural fix (fee at the balance-mutation layer rather than at the intent-type layer) is more robust.

### Proof of Concept
1. Alice and Bob each deposit tokens into the Verifier contract (Alice: 1000 USDT, Bob: 1000 USDC), as in the README's documented swap flow: [5](#0-4) .
2. Instead of each signing a `TokenDiff` (which would trigger `Self::token_fee` in `contracts/defuse/core/src/intents/token_diff.rs:70-78`), Alice signs a `Transfer { receiver_id: Bob, tokens: {USDT: 1000} }` and Bob signs a `Transfer { receiver_id: Alice, tokens: {USDC: 1000} }`.
3. A relayer submits both signed payloads together via `execute_intents([alice_payload, bob_payload])`.
4. `Engine::execute_signed_intents` (`contracts/defuse/core/src/engine/mod.rs:32-40`) verifies both signatures/nonces and executes both `Transfer::execute_intent` calls (`contracts/defuse/core/src/intents/tokens.rs:107-112`), each of which calls `internal_sub_balance`/`internal_add_balance` with no fee computation.
5. Result: Alice ends up with 1000 USDC, Bob ends up with 1000 USDT — an atomic swap identical in economic effect to a `TokenDiff`-based swap — but `fee_collector`'s balance is never credited, in contrast to the `swap_p2p` test which shows fees collected when the same swap is done via `TokenDiff`: [6](#0-5) .

impl ExecutableIntent for Transfer {
    fn execute_intent<S, I>(
        self,
        sender_id: &AccountIdRef,
        engine: &mut Engine<S, I>,
        intent_hash: [u8; 32],
    ) -> Result<()>
    where
        S: State,
        I: Inspector,
    {
        if sender_id == self.receiver_id || self.tokens.is_empty() {
            return Err(DefuseError::InvalidIntent);
        }

        engine
            .inspector
            .on_event(DefuseEvent::Transfer(Cow::Borrowed(
                [MaybeIntentEvent::new_intent(
                    AccountEvent::new(sender_id, TransferEvent::from(&self)),
                    intent_hash,
                )]
                .as_slice(),
            )));

        engine
            .state
            .internal_sub_balance(sender_id, self.tokens.clone())?;
        engine
            .state
            .internal_add_balance(self.receiver_id.clone(), self.tokens.clone())?;

        if let Some(mut notification) = self.notification {
            notification.min_gas = Some(
                notification
                    .min_gas
                    .unwrap_or(MT_ON_TRANSFER_GAS_DEFAULT)
                    .max(MT_ON_TRANSFER_GAS_MIN),
            );

            engine
                .state
                .notify_on_transfer(sender_id, self.receiver_id, self.tokens, notification);
        }

        Ok(())
    }
}

    pub fn execute_signed_intents(
        mut self,
        signed: impl IntoIterator<Item = MultiPayload>,
    ) -> Result<Transfers> {
        for signed in signed {
            self.execute_signed_intent(signed)?;
        }
        self.finalize()
    }

    fn execute_signed_intent(&mut self, signed: MultiPayload) -> Result<()> {
        // verify signed payload and get public key
        let public_key = signed.verify().ok_or(DefuseError::InvalidSignature)?;

        // calculate intent hash
        let hash = signed.hash();

        // extract NEP-413 payload
        let DefusePayload::<DefuseIntents> {
            signer_id,
            verifying_contract,
            deadline,
            nonce,
            message: intents,
        } = signed.extract_defuse_payload()?;

        // check recipient
        if verifying_contract != *self.state.verifying_contract() {
            return Err(DefuseError::WrongVerifyingContract);
        }

        self.inspector.on_deadline(deadline);

        // make sure message is still valid
        if deadline < Timestamp::now() {
            return Err(DefuseError::DeadlineExpired);
        }

        // make sure the account has this public key
        if !self.state.has_public_key(&signer_id, &public_key) {
            return Err(DefuseError::PublicKeyNotExist(signer_id, public_key));
        }

        // commit nonce
        self.verify_intent_nonce(nonce, deadline)?;
        self.state.commit_nonce(signer_id.clone(), nonce)?;

        intents.execute_intent(&signer_id, self, hash)?;
        self.inspector.on_intent_executed(&signer_id, hash, nonce);

        Ok(())
    }

impl Intents for Contract {

    fn execute_intents(&mut self, signed: Vec<MultiPayload>) {
        if let Some(event) = Engine::new(self, ExecuteInspector::default())
            .execute_signed_intents(signed)
            .unwrap_or_else(|e| e.panic())
            .as_mt_event()
        {
            // NOTE: Not all `mt_transfer` events are refundable, but it's safe to check them
            // all at once since non-refundable transfers only increase the potential refund
            // log size without affecting correctness. This can actually prevent resolve transfer
            // from failing due to too long event log !!!
            event
                .check_refund()
                .unwrap_or_else(|err| err.panic())
                .emit();
        }
    }

### Example

Alice wants to trade 1000 USDT with Bob for 1000 USDC. If Alice sends her 1000 USDT first, she risks Bob not fulfilling the promise of sending his 1000 USDC. Same risk for Bob if he goes first.

Solution:

Both Alice and Bob create accounts in the [NEAR Intents smart contract](https://nearblocks.io/address/intents.near). They then deposit their 1000 USDT/USDC. They create two intents. In Alice's, Alice declares her will to lose 1000 USDT for 1000 USDC, and Bob creates another intent showing his will to lose 1000 USDC for 1000 USDT. Each of them sign their intent. They put both intents in an array, and then call [the function](https://near.github.io/intents/defuse/intents/trait.Intents.html#tymethod.execute_intents) `execute_intents` in the NEAR Intents smart contract with the intents' array.

The Verifier smart contract will evaluate the intents and check whether the requests can be fulfilled, and will ensure that the transaction is done atomically, and the 1000 USDC/USDT will be swapped.

Finally, Alice and Bob can withdraw their USDC/USDT from the Verifier smart contract to their individual accounts.
