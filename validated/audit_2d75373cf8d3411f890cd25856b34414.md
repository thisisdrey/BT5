## Title
`pallet-broker::drop_history` can permanently strand contributor revenue before `claim_revenue` runs — unguarded, origin-less cleanup call removes payout bookkeeping ahead of settlement - (File: `substrate/frame/broker/src/dispatchable_impls.rs`)

### Summary
`pallet-broker` exposes four "cleanup" extrinsics — `drop_region`, `drop_contribution`, `drop_history`, `drop_renewal` — that all accept `_origin: OriginFor<T>` (i.e. *any* origin, not even `ensure_signed`), by explicit design (`prdoc/1.6.0/pr_2656.prdoc`: "Change the permissionless calls … to allow any kind of origin"). `drop_history` removes (`take`s) an `InstaPoolHistoryRecord` and simultaneously debits its `maybe_payout` out of the pallet pot via `Self::charge`. The record it deletes is the exact same per-timeslice bookkeeping entry that `claim_revenue` reads to compute a contributor's payout share. Because the two cleanup guards are keyed on different timelines (`drop_history` on the record's own timeslice `when`; `drop_contribution` on the *end* of the whole contribution range), a history record inside an unexpired, unclaimed contribution can become droppable and be wiped by anyone before the contributor ever calls `claim_revenue`. This is the same class of bug as the report: a public/unprotected "cleanup" primitive mutates an accounting structure (removes an entry representing owed value) while the funds tied to that entry are not routed to the rightful beneficiary, resulting in unaccounted/stranded funds.

### Finding Description
`do_claim_revenue` walks a contributor's `InstaPoolContribution` from `region.begin` to `region.begin + contribution.length`, and for each timeslice `r` reads `InstaPoolHistory::<T>::get(r)` to determine `total_payout`, splits it pro-rata by `contributed_parts`, and pays it out: [1](#0-0) 

If `InstaPoolHistory::<T>::get(r)` returns `None` for a given timeslice, the loop silently `continue`s — no error, no event, the share for that timeslice is simply zero: [2](#0-1) 

`do_drop_history` is exactly what can make that lookup return `None`. Its only guard is:
```
ensure!(status.last_timeslice > when.saturating_add(config.contribution_timeout), Error::<T>::StillValid);
let record = InstaPoolHistory::<T>::take(when).ok_or(Error::<T>::NoHistory)?;
if let Some(payout) = record.maybe_payout {
    let _ = Self::charge(&Self::account_id(), payout);
}
``` [3](#0-2) 

Compare this to `do_drop_contribution`'s guard, which is keyed on the **end** of the contribution's range, not on any single timeslice within it:
```
let end = region_id.begin.saturating_add(contrib.length);
ensure!(status.last_timeslice >= end.saturating_add(config.contribution_timeout), Error::<T>::StillValid);
``` [4](#0-3) 

A single `InstaPoolContribution` can span many timeslices (`region.begin .. region.begin + contribution.length`, with `length` unbounded by anything relevant here). The *earliest* timeslice in that range, `when = region.begin`, becomes eligible for `drop_history` as soon as `status.last_timeslice > region.begin + contribution_timeout`. The contribution itself only becomes droppable once `status.last_timeslice >= region.begin + contribution.length + contribution_timeout` — strictly later whenever `length > 0`. In that window, the contribution is still valid and unclaimed, yet its early history record can be, and per the four dispatchables' explicit "any origin" design intentionally is meant to be, permissionlessly removed: [5](#0-4) [6](#0-5) 

Once `drop_history` runs for that early `when`, `Self::charge(&Self::account_id(), payout)` removes the payout amount from the pot's ledger (an accounting debit), and the `InstaPoolHistoryRecord` is gone from storage. When the contributor subsequently calls `claim_revenue` for a region whose range includes that timeslice, the loop's `else { continue }` means their share for that timeslice is silently dropped to zero — the value was already charged out of the pot in `drop_history`, but never routed to the contributor via `T::Currency::transfer` in `do_claim_revenue`. No error is raised anywhere in this path; the contributor simply receives less than they are entitled to, with no on-chain indicator distinguishing "nothing was owed" from "it was cleaned up before I claimed."

This mirrors the reported pattern precisely: a data structure representing per-user owed funds (`activeLendOrderIds`/unfilled orders ↔ `InstaPoolHistory` payout records) is mutated by a permissionless "cleanup" function (`cleanUpOrders` ↔ `drop_history`) whose caller is expected — but not enforced — to ensure the associated funds are correctly settled to the party who is owed them (`FundManagementLogic._cleanUpOrders` ↔ `claim_revenue`'s per-timeslice payout).

### Impact Explanation
Any account (the calls take no origin restriction at all) can race a still-valid, unclaimed pool contribution's early timeslices out from under its owner, permanently zeroing that portion of the contributor's `claim_revenue` payout while the corresponding value has already been debited from the pot's accounting via `Self::charge`. This is a fund-loss / permanent-lock condition for the contributor and constitutes unbacked accounting drift in `pallet-broker`'s instantaneous-pool revenue-sharing mechanism — directly matching the "theft or unbacked mint or unlock … permanent user-fund … lock" impact category for live-scope findings.

### Likelihood Explanation
The attack requires no privileged role, no validator/collator/relayer collusion, and no governance action — it is a plain, permissionless extrinsic call (`drop_history(when)`) available to any signed or even unsigned/root-substituted caller per the pallet's own documented design. The only precondition is that `contribution.length > 1` timeslices (a very common case for pool contributions spanning more than a single timeslice) and that enough time has elapsed for the *earliest* timeslice in the contribution's range to cross the `contribution_timeout` threshold while the contribution's own `end`-based timeout has not yet elapsed — a naturally occurring window for any multi-timeslice contribution, not an edge case.

### Recommendation
1. Guard `do_drop_history(when)` against dropping a record while any `InstaPoolContribution` still overlapping `when` remains unclaimed — e.g., track outstanding contributions per timeslice, or defer dropping until the timeslice is outside the range of *all* live contributions, not just measured from its own timeout.
2. Alternatively, key both `drop_history` and `drop_contribution` off the same reference point (the contribution's end) so a per-timeslice record can never be reaped before every contribution that could still read it has itself expired or been claimed/dropped.
3. Ensure `Self::charge` in `do_drop_history` and the payout in `do_claim_revenue` are mutually exclusive/atomic with respect to a given `(region_id, when)` pair — e.g., by making `drop_history` fail (rather than silently succeed) if the record is still referenced by outstanding `InstaPoolContribution` entries.

### Proof of Concept
1. Chain starts sales; `region` is purchased and placed in the Instantaneous Pool with `do_pool(region, ..., Final)`, creating an `InstaPoolContribution { length: N, payee: victim, .. }` spanning timeslices `region.begin .. region.begin + N`.
2. Coretime usage/revenue reports populate `InstaPoolHistory` for each timeslice in that range with `maybe_payout = Some(revenue_r)`.
3. Time advances so that `status.last_timeslice > region.begin + contribution_timeout`, but `status.last_timeslice < region.begin + N + contribution_timeout` (true for any `N > 1` in this window) — i.e., the contribution as a whole is still `StillValid` for `drop_contribution`, but the earliest timeslice already satisfies `drop_history`'s check.
4. An attacker (any account, unsigned/root-substitutable per the pallet's origin design) calls `drop_history(region.begin)`. This succeeds: `InstaPoolHistory::take(region.begin)` removes the record, and `Self::charge(&Self::account_id(), revenue_region_begin)` debits the pot.
5. The victim later calls `claim_revenue(region_id, N)`. Inside `do_claim_revenue`'s loop, `InstaPoolHistory::<T>::get(region.begin)` returns `None`, so that timeslice's `continue` skips it — the victim's payout is short by exactly `revenue_region_begin * contributed_parts / private_contributions`, funds that were already removed from the pot's balance in step 4 but never reached the victim.

**Uncertainty note:** I could not directly view the body of `Self::charge` (`substrate/frame/broker/src/utility_impls.rs`) in this session, so the precise mechanics of how the debited payout is disposed of (burn vs. internal re-allocation) are inferred from call context (`let _ = Self::charge(&Self::account_id(), payout)`, discarding the result, immediately after removing the only record that ties that payout to its rightful claimant) rather than confirmed by reading that function's implementation. A Devin session with full repository access should verify `charge`'s exact semantics to confirm whether the debited value is destroyed outright or merely reallocated, which affects whether this is pure value destruction or a beneficiary-mismatch/misdirection.

	pub(crate) fn do_claim_revenue(
		mut region: RegionId,
		max_timeslices: Timeslice,
	) -> DispatchResult {
		ensure!(max_timeslices > 0, Error::<T>::NoClaimTimeslices);
		let mut contribution =
			InstaPoolContribution::<T>::take(region).ok_or(Error::<T>::UnknownContribution)?;
		let contributed_parts = region.mask.count_ones();

		Self::deposit_event(Event::RevenueClaimBegun { region, max_timeslices });

		let mut payout = BalanceOf::<T>::zero();
		let last = region.begin + contribution.length.min(max_timeslices);
		for r in region.begin..last {
			region.begin = r + 1;
			contribution.length.saturating_dec();

			let Some(mut pool_record) = InstaPoolHistory::<T>::get(r) else { continue };
			let Some(total_payout) = pool_record.maybe_payout else { break };
			let p = total_payout
				.saturating_mul(contributed_parts.into())
				.checked_div(&pool_record.private_contributions.into())
				.unwrap_or_default();

			payout.saturating_accrue(p);
			pool_record.private_contributions.saturating_reduce(contributed_parts);

			let remaining_payout = total_payout.saturating_sub(p);
			if !remaining_payout.is_zero() && pool_record.private_contributions > 0 {
				pool_record.maybe_payout = Some(remaining_payout);
				InstaPoolHistory::<T>::insert(r, &pool_record);
			} else {
				InstaPoolHistory::<T>::remove(r);
			}
			if !p.is_zero() {
				Self::deposit_event(Event::RevenueClaimItem { when: r, amount: p });
			}
		}

	pub(crate) fn do_drop_contribution(region_id: RegionId) -> DispatchResult {
		let config = Configuration::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let contrib =
			InstaPoolContribution::<T>::get(&region_id).ok_or(Error::<T>::UnknownContribution)?;
		let end = region_id.begin.saturating_add(contrib.length);
		ensure!(
			status.last_timeslice >= end.saturating_add(config.contribution_timeout),
			Error::<T>::StillValid
		);
		InstaPoolContribution::<T>::remove(region_id);
		Self::deposit_event(Event::ContributionDropped { region_id });
		Ok(())
	}

	pub(crate) fn do_drop_history(when: Timeslice) -> DispatchResult {
		let config = Configuration::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		ensure!(
			status.last_timeslice > when.saturating_add(config.contribution_timeout),
			Error::<T>::StillValid
		);
		let record = InstaPoolHistory::<T>::take(when).ok_or(Error::<T>::NoHistory)?;
		if let Some(payout) = record.maybe_payout {
			let _ = Self::charge(&Self::account_id(), payout);
		}
		let revenue = record.maybe_payout.unwrap_or_default();
		Self::deposit_event(Event::HistoryDropped { when, revenue });
		Ok(())
	}
