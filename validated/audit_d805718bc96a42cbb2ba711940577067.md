### Title
StackerDB `write_freq` write-rate limit is defined but never enforced on the chunk write path, allowing a slot owner to force unbounded, amplified re-broadcast of a critical replica - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The reported Flux bug is a class of "gate that is supposed to bound how often a privileged action may repeat, but can be bypassed because the check is not actually enforced where the state mutation happens." In `stacks-core`'s StackerDB subsystem, the `write_freq` parameter is designed and documented as exactly this kind of gate — a per-slot wall-clock rate limit on writes — but it is never checked in the function that actually authorizes and commits a chunk write, `StackerDBTx::try_replace_chunk`.

### Finding Description
`StackerDBConfig` carries a `write_freq` field that is described in the StackerDB control-plane documentation as governing how often a given slot may legitimately be rewritten [1](#0-0) . The only place `write_freq` is actually consulted is `StackerDBSync`'s peer-fetch scheduling logic (deciding whether *this node* should bother requesting a chunk from a neighbor) and its own sync-loop throttle [2](#0-1) [3](#0-2) .

The authoritative function that actually validates and commits a chunk to a slot — `StackerDBTx::try_replace_chunk` — checks chunk size, slot existence, signer authenticity, monotonic version (staleness), and `max_writes`, but contains **no `write_freq`/timestamp check at all**: [4](#0-3) 

This is the single function used both when a chunk arrives via the authenticated HTTP `POST /v2/stackerdb/:principal/:contract/chunks` endpoint [5](#0-4)  and when a chunk is accepted during p2p relay/sync (`stackslib/src/net/relay.rs`). Corroborating this, the dedicated `net_error::TooFrequentSlotWrites` variant exists in the error enum and its `Display` impl [6](#0-5) [7](#0-6) , but it is never constructed/returned anywhere in the codebase — it is dead code, meaning the enforcement path was intended but never wired into `try_replace_chunk`.

Just like the Flux report — where `Voter.reset()`'s "once per epoch" gate was real in the modifier `onlyNewEpoch` but bypassable because the underlying resource identity could change (`merge`) without resetting the true constraint — here the `write_freq` gate is real in configuration and in the *scheduling/relay-throttle* logic, but the actual state-mutating write path (`try_replace_chunk`) never checks it, so the constraint is trivially "bypassed" simply by writing directly (or via HTTP), i.e., it fails open by omission rather than by identity-laundering, but the effect is the same: an intended once-per-period write gate can be exceeded without limit by any party who legitimately owns a slot (e.g., a registered Nakamoto signer or miner for `.signers`/`.miners` StackerDBs).

### Impact Explanation
Any node that is a legitimate slot owner for a StackerDB (e.g., a Nakamoto signer with a `.signers-N-M` slot, or a miner with a `.miners` slot) can submit new chunk versions at the maximum rate allowed only by `max_writes` and the version being monotonic (i.e., every millisecond if desired), even though `write_freq` in the same `StackerDBConfig` was supposed to cap this. Because every accepted write on the HTTP path is immediately queued for p2p relay via `node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))` [8](#0-7) , and each replica that stores a pushed chunk further re-broadcasts it to its own DB neighbors during `pushchunks_begin` [9](#0-8) , an attacker-controlled but legitimately-registered slot owner can force network-wide amplified propagation of chunk writes at a rate far beyond what the StackerDB's own configured `write_freq` was meant to allow. For safety-critical StackerDBs (`.signers-*`, `.miners`) this can degrade the timeliness/availability of block-signing coordination data across the whole network — a bounded-compute DoS on a system relied upon by consensus-adjacent infrastructure, triggered by a small number of unbounded-rate writes rather than raw traffic volume from an unprivileged/unauthenticated party.

### Likelihood Explanation
High for any actor already holding a valid StackerDB slot key (any active Nakamoto signer or miner qualifies, and slot assignment does not require any elevated node privilege beyond normal protocol participation). No race condition or subtle timing is needed — the omission is a straightforward missing check, confirmed by grepping the codebase: `write_freq` is referenced only in `sync.rs`/`config.rs`/tests, and `TooFrequentSlotWrites` is never constructed anywhere despite being defined.

### Recommendation
Add a `write_freq` / last-write-timestamp check inside `StackerDBTx::try_replace_chunk` (using the existing `write_time` column already tracked per slot, as seen in `get_slot_write_timestamps`), returning `net_error::TooFrequentSlotWrites` when a write arrives before `write_time + write_freq` has elapsed, mirroring the check style already used for `max_writes` and staleness in the same function [10](#0-9) . Wire the new error into `RPCPostStackerDBChunkRequestHandler::try_handle_request`'s error-classification `match` so it maps to a dedicated `StackerDBErrorCodes` variant, analogous to `TooManySlotWrites` [11](#0-10) .

### Proof of Concept
1. Register as a legitimate signer for a test StackerDB contract with `write_freq = 3600` (one write per hour) and `max_writes = u32::MAX`.
2. Using the existing test harness pattern from `stackslib/src/net/stackerdb/tests/db.rs` (`test_stackerdb_insert_query_chunks`), repeatedly call `tx.try_replace_chunk(&sc, &chunk_md, &data)` with strictly increasing `slot_version` in a tight loop, with no delay between calls.
3. Observe that every call succeeds immediately (only version/signature/size/`max_writes` are checked) despite `write_freq = 3600`, i.e., there is no `TooFrequentSlotWrites` rejection ever produced, confirmed by the fact that this error is dead code (never constructed anywhere in the codebase, per repository grep).
4. Repeating step 2 via the real HTTP endpoint (`POST /v2/stackerdb/:principal/:contract/chunks`) with a valid slot signature demonstrates that each accepted write is queued for network-wide relay (`node.set_relay_message`), so the unenforced rate limit directly translates into unbounded StackerDB chunk-push traffic being propagated to all replicating peers.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
