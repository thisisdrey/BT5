### Title
Dust transfer of deposit tokens fills victim's per-account token list, blocking new collateral deposits and debt positions (`UserReachedMaxTokens`) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` on the combined size of `depositTokensOfAccount` and `debtTokensOfAccount`. An entry is added to `depositTokensOfAccount[recipient]` whenever an account's balance of a `DepositToken` goes from `0` to non-zero — including via a plain `transfer`. An attacker can cheaply dust-transfer 1 wei of every whitelisted `DepositToken` to a victim, filling all 30 slots and causing any subsequent deposit of a *new* collateral type, receipt of a new `DepositToken`, or issuance of a new `DebtToken` for that account to revert with `UserReachedMaxTokens`. [1](#0-0) [2](#0-1) 

### Finding Description
`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance was `0` [3](#0-2) . `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) [4](#0-3) .

Attack path, all unprivileged:
1. Attacker deposits a minimal amount of each whitelisted collateral via `DepositToken.deposit(amount, attacker)` to obtain dust `msd*` balances (up to 30 distinct deposit tokens exist per pool, since `addDepositToken` caps the pool list at `MAX_TOKENS_PER_USER` [5](#0-4) ).
2. Attacker calls `DepositToken.transfer(victim, 1)` for each token. Each call passes `_revertIfLocked` (attacker's own unlocked balance) and adds the token to `depositTokensOfAccount[victim]` [6](#0-5) .
3. Victim now has 30 entries. Any `deposit()` of a new collateral to `onBehalfOf_ == victim`, any issuance of a new debt token (`DebtToken` calls `addToDebtTokensOfAccount` on first balance [7](#0-6) ), and even `seize()` to a liquidator targeting a victim-held token revert.

The victim can remove an entry only by transferring/withdrawing a dust token to zero (`_burn`/`_transfer` calls `removeFromDepositTokensOfAccount` on 0-balance [8](#0-7) ), but the attacker can re-dust the same token immediately afterward, making the block persistent for as long as the attacker is willing to spend gas. This mirrors the report's bug class: the protocol consumes an unbounded-by-victim resource (the per-account set) driven entirely by attacker-supplied input with no opt-in, causing denial of the victim's normal operations.

### Impact Explanation
Temporary freezing of funds and forced-liquidation griefing. A victim whose position is approaching the liquidation threshold cannot deposit a *new* collateral type to restore health — `deposit` reverts — and cannot receive collateral top-ups from a third party via `onBehalfOf_`. If their existing collateral types are exhausted, they cannot deleverage by adding collateral and their position becomes liquidatable; the attacker (or a confederate) liquidates via `Pool.liquidate` and collects the liquidation fee spread. Funds already deposited remain withdrawable only for tokens already in the victim's set, so existing balances aren't permanently frozen, but the ability to add collateral is attacker-controlled.

### Likelihood Explanation
Cost is bounded and low: the attacker needs only dust `msd*` balances (1 wei each) for up to 30 deposit tokens plus gas for ~30 `transfer` calls. No privileged role, no oracle manipulation, no governance action is required — `transfer`, `addToDepositTokensOfAccount` are unprivileged entry points. The only mitigation is that a sophisticated victim can empty one dust slot and deposit in the same transaction (atomicity), but the attacker can front-run/back-run to re-fill slots, sustaining the DoS. Repeatable against any account at negligible marginal cost.

### Recommendation
- Remove the per-account addition on `transfer`/`seize`, or only register tokens on `deposit`-minted balances (the `_mint` path), not on secondary transfers.
- Alternatively, allow `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to silently no-op instead of reverting when the cap is reached, so dust griefing cannot brick `transfer`, `seize`, or `deposit` for tokens the victim doesn't want; or track account token sets only for debt-side accounting and enumerate collateral via `depositTokens` at health-check time.
- At minimum, let the recipient remove arbitrary set entries via a public `removeFromDepositTokensOfAccount`-style escape that doesn't require zeroing a balance they may want to keep.

### Proof of Concept
Hardhat sketch (repository test suite is ethers-based; see `test/Pool.test.ts` [9](#0-8) ):

```ts
// Setup: pool with >= MAX_TOKENS_PER_USER whitelisted deposit tokens
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30
const dustTokens = await getAllDepositTokens(pool); // msdA, msdB, ...

// Attacker acquires dust of each token (deposit tiny amount or buy off market)
for (const t of dustTokens) {
  await underlyingOf[t].connect(attacker).approve(t.address, 1);
  // deposit mints to attacker if attacker has no debt; skip if capped, buy instead
}

// Grief: fill victim's depositTokensOfAccount
for (const t of dustTokens) {
  await t.connect(attacker).transfer(victim.address, 1);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(max);

// Victim tries to deposit a new collateral type -> reverts
const newToken = await deployNewDepositToken(...); // any whitelisted token not in victim's set
await collateral.approve(newToken.address, parseEther('10'));
await expect(
  newToken.connect(victim).deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim tries to repay health by receiving a new deposit token -> reverts
await expect(
  dustTokens[0] === alreadyInSet
    ? null
    : someToken.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim's unhealthy position can no longer be collateralized with new token types;
// attacker liquidates via pool.liquidate(...)
```

Note: the attack requires the pool to actually have many whitelisted deposit/debt tokens (cap is 30 total), and the victim retains an atomic escape (empty one slot + deposit in a single tx), so the DoS is sustainable only through continued attacker transactions — consistent with "temporary freezing" severity rather than permanent loss.
