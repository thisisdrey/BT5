## Finding: Unbounded HTTP body read in `libsigner`'s signer event receiver causes unauthenticated remote OOM

### Title
Unbounded HTTP request body buffering in the signer's event-receiver HTTP server allows remote unauthenticated OOM - (File: `libsigner/src/events.rs`)

### Summary
The stacks-signer binds an HTTP server (`SignerEventReceiver::bind`) to receive event-observer callbacks from a Stacks node, and every incoming request is dispatched to `process_event`, which reads the *entire* request body into memory with `request.as_reader().read_to_string(&mut body)` and **no size limit whatsoever**. Every other message/body parser in this codebase (P2P messages, StackerDB chunks, HTTP request/response payloads, signer wire messages) enforces an explicit upper bound (`MAX_MESSAGE_LEN`, `STACKERDB_MAX_CHUNK_SIZE`, `BLOCK_RESPONSE_DATA_MAX_SIZE`, `STATE_MACHINE_UPDATE_MAX_SIZE`, chunked-transfer `max_size`) before or during buffering. This one path has none, breaking the "bounded wire length" invariant that holds everywhere else in the network stack.

### Finding Description
`SignerEventReceiver::bind` starts a `tiny_http::HttpServer` on an operator-configured socket address: [1](#0-0) 

`next_event` dispatches unauthenticated POST requests on recognized URLs (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`) directly to `process_event`: [2](#0-1) 

`process_event` reads the full body into a `String` with no bound before even attempting JSON deserialization: [3](#0-2) 

There is no `Content-Length` cap check, no `MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN`-style ceiling, and no chunked-transfer size cap comparable to what is used elsewhere in the codebase, e.g.:
- P2P messages are capped via `MAX_MESSAGE_LEN`: [4](#0-3) 
- StackerDB chunk decoding is capped via `STACKERDB_MAX_CHUNK_SIZE`: [5](#0-4) 
- Signer wire messages (`BlockProposalData`, `StateMachineUpdate`) are capped via `BLOCK_RESPONSE_DATA_MAX_SIZE` / `STATE_MACHINE_UPDATE_MAX_SIZE`: [6](#0-5) [7](#0-6) 
- The signer's own outbound HTTP client bounds chunked bodies with `MAX_MESSAGE_LEN`: [8](#0-7) 

Only the inbound event-receiver path — the one endpoint reachable by any TCP client that can connect to the bound port — skips this bound entirely.

### Impact Explanation
Any client capable of establishing a TCP connection to the signer's event-observer port (no authentication is performed on this endpoint; `next_event` accepts any POST to a known URL) can submit a request whose body is arbitrarily large. The `read_to_string` call will buffer that entire body into process memory before any validation or size check occurs, so a single connection sending a very large body drives up the signer's memory usage roughly 1:1 with bytes sent, with no early-rejection based on declared length. Because signer processes are typically provisioned modestly and this endpoint is on the hot path for every signer, this can crash or degrade the signer via memory exhaustion — directly analogous to the referenced Wings CWE-400/770/789 issue where a parser without a size limit allows OOM.

### Likelihood Explanation
The endpoint is unauthenticated by design (it exists to receive callbacks from the paired Stacks node, but `tiny_http`/the code performs no origin check), and reaching it only requires network connectivity to the bound address/port — no protocol handshake, key, or role is required. The missing bound is a straightforward, deterministic code-path defect (not a race or timing issue), making exploitation reliable once the port is reachable.

### Recommendation
Enforce an explicit maximum body size in `process_event` (and ideally in `SignerEventReceiver::next_event` before dispatch), consistent with the bounds already used elsewhere (e.g., `MAX_MESSAGE_LEN` or a purpose-specific cap for event payloads). Reject/drain-and-close requests whose `Content-Length` exceeds the cap before reading the body, and cap the number of bytes actually read (e.g., via a bounded reader) to defend against chunked-encoded bodies that omit `Content-Length`.

### Proof of Concept
1. Start a stacks-signer with its event-receiver bound to a reachable address/port (as configured via `event_out`/`bind` in normal signer configuration).
2. From an unauthenticated remote host, send: `POST /new_burn_block HTTP/1.1` with a `Content-Length` header declaring a very large body (e.g., several GB) and stream that many bytes.
3. Observe `libsigner::events::process_event` buffering the entire streamed body into a `String` via `read_to_string` with no size check, driving process memory usage up proportionally, potentially triggering OOM/crash of the signer process — all without any authentication.
