### Title
Unbounded `Paths`/`Attributes` list in `GetFileAttributes` causes sequential subprocess I/O loop with no size cap - (File: internal/gitaly/service/repository/file_attributes.go)

### Summary
`GetFileAttributes` accepts attacker-controlled `Paths` and `Attributes` slices with no upper-bound validation, then iterates every path and performs a blocking write+flush+read round-trip against a `git check-attr` subprocess for each one, sequentially and without any context-cancellation check. A single request with a very large number of paths forces the handler to spend proportional CPU/wall-time and to hold a `git check-attr` subprocess (and its `finishAttr` cleanup) open for the entire duration.

### Finding Description
`validateGetFileAttributesRequest` only checks that `Revision`, `Paths`, and `Attributes` are non-empty; it never bounds their length or content size [1](#0-0) . `GetFileAttributes` then starts one `check-attr` process via `gitattributes.CheckAttr` and loops over every entry of `in.GetPaths()`, calling `checkAttrCmd.Check(path)` for each [2](#0-1) . `Check` performs a synchronous, mutex-serialized write to the subprocess's stdin, a flush, and a blocking read of `-z`-delimited output from stdout for every single path [3](#0-2) . There is no batching, no worker-pool parallelism, and no `ctx.Done()` check inside the loop, so the entire per-path cost scales linearly and is fully attributable to one RPC call. Because this is a unary (non-streaming) RPC and no `grpc.MaxRecvMsgSize` override was found configured anywhere in the repo, the effective bound on `len(Paths)` is only the default gRPC message-size limit (4 MiB), which still permits hundreds of thousands to millions of short path entries in a single request.

### Impact Explanation
A single crafted `GetFileAttributesRequest` can force the Gitaly worker handling it to perform hundreds of thousands of sequential blocking read/write syscalls against a child `git check-attr` process, consuming a disproportionate amount of CPU/wall-clock time and tying up one RPC-handling goroutine and one subprocess slot for the duration. Repeated concurrent invocations by the same low-privilege user can amplify this into worker-pool starvation on the Gitaly node, degrading service for other tenants sharing that Gitaly host — this matches GitLab's "Denial of service of a Gitaly/RPC handler" impact class.

### Likelihood Explanation
The attacker only needs any RPC access to a repository they control (own project) and the ability to send a single well-formed gRPC request with a large `Paths` array — no special role, git object crafting, or write access is required, and the message fits within the default gRPC size limit. This makes the attack trivially repeatable and low-cost for the attacker.

### Recommendation
Add an explicit maximum bound on `len(in.GetPaths())` and `len(in.GetAttributes())` in `validateGetFileAttributesRequest` (returning `InvalidArgument` beyond a sane limit, e.g. a few thousand), and/or process paths in bounded batches with periodic `ctx.Err()` checks so the handler can be cancelled if the client disconnects or a deadline is exceeded.

### Proof of Concept
```go
func TestGetFileAttributes_LargePathsDoS(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)
    repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg)
    gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"),
        gittest.WithTreeEntries(gittest.TreeEntry{Path: "a", Mode: "100644", Content: "x"}))

    paths := make([]string, 500000)
    for i := range paths {
        paths[i] = "a" // reuse an existing path to keep message size small
    }

    start := time.Now()
    _, err := client.GetFileAttributes(ctx, &gitalypb.GetFileAttributesRequest{
        Repository: repoProto,
        Revision:   []byte("main"),
        Attributes: []string{"diff"},
        Paths:      paths,
    })
    require.NoError(t, err)
    t.Logf("handler duration: %s", time.Since(start))
    // Assert: handler duration scales linearly with len(paths) with no
    // enforced cap, unlike a size-bounded baseline (e.g. 1000 paths).
}
```
Expected result: request succeeds (no `InvalidArgument`) and handler duration/CPU grows roughly linearly with the number of paths, confirming the absence of any enforced limit in `validateGetFileAttributesRequest`.

```go
func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}

	return attrs, nil
}
```
