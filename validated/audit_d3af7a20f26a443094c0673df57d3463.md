### Title
Unbounded pre-allocation of a 16MB `Vec<u8>` from an unverified length prefix in `StackerDBChunkData::consensus_deserialize` - (File: libstackerdb/src/libstackerdb.rs / stacks-common/src/codec/mod.rs)

### Summary
`StackerDBChunkData::consensus_deserialize` calls `read_next_at_most(fd, STACKERDB_MAX_CHUNK_SIZE)` to read the `data` field, which internally calls `read_next_vec`. That function reads only a 4-byte length prefix from the wire, validates it against `max_items` and a byte-size bound, and then immediately does `Vec::with_capacity(len as usize)` before any of the declared bytes have actually been read from the stream.

### Finding Description
The broken equality: allocated-buffer-size should track actual-bytes-successfully-read, not the attacker-declared length prefix. In `stacks-common/src/codec/mod.rs`, `read_next_vec` (used by `read_next_at_most`, which backs the `data: Vec<u8>` field of `StackerDBChunkData`) does: [1](#0-0) 
1. Read a `u32` length (`len`) from the stream — only 4 bytes of attacker-controlled input required.
2. Check `len <= max_items` (here `STACKERDB_MAX_CHUNK_SIZE` = 16MB) and `size_of::<T>() * len <= MAX_MESSAGE_LEN`, both of which a `len` of exactly 16MB satisfies since `T = u8`.
3. Immediately call `Vec::with_capacity(len as usize)` — allocating up to 16MB **before** attempting to read a single payload byte.
4. Only then loop calling `T::consensus_deserialize(fd)` (i.e., `u8::consensus_deserialize`, a 1-byte `read_exact`) to actually pull bytes off the wire; if the attacker sends none, this read fails immediately with `UnexpectedEof`.

The attacker's exact message: connect to the chunk-POST endpoint, send `slot_id` (4 bytes), `slot_version` (4 bytes), `sig` (65 bytes), then a 4-byte length prefix of `0x01000000` (16,777,216) for the `data` field, and then close the connection (or send nothing further). Per the trace, the server has already performed `Vec::with_capacity(16 * 1024 * 1024)` by the time it discovers there are no more bytes to read, and only then returns an error and drops the allocation.

Existing guards (`MAX_MESSAGE_LEN`/`STACKERDB_MAX_CHUNK_SIZE` caps) bound the *maximum* size of a single allocation to 16MB, but they do nothing to prevent the allocation from happening *before* the corresponding bytes are verified to exist on the wire. The cap only prevents allocations larger than 16MB per message — it does not enforce that allocation is proportional to bytes actually received.

### Impact Explanation
Each malicious connection costs the attacker roughly 77 bytes of upload (headers/preamble/length-prefix) but forces the node to perform a 16MB heap allocation (`Vec::with_capacity`) before the read fails. This is a disproportionate allocation-per-byte-sent pattern (memory-amplification), distinct from plain volumetric flooding, and is repeatable indefinitely by opening new connections to the StackerDB chunk-POST endpoint, which any unprivileged remote peer can reach without holding a slot key or the node's RPC secret (the vulnerable code path executes before any chunk signature/authorization check, since it is inside the wire deserialization of the request body itself). Repeated concurrent connections can drive sustained allocator churn/memory pressure on the node, matching the "Critical - remote crash/unauthenticated DoS from few messages" category if allocator pressure induces OOM or allocator-latency-driven service degradation.

### Likelihood Explanation
- Preconditions: none beyond the ability to open a TCP connection to the node's chunk-POST endpoint and send raw bytes — no slot ownership, no valid signature, no RPC secret required, since the allocation happens during message parsing prior to any content or signature validation.
- Attacker cost: near-zero (a handful of bytes per connection).
- Remote reachability: yes, this is the standard StackerDB chunk write path (`consensus_deserialize` on `StackerDBChunkData`), reachable by any unprivileged party.
- Repeatability: unlimited, bounded only by connection-establishment cost, which is far cheaper than the 16MB allocation it triggers each time.

### Recommendation
Change `read_next_vec` (or add a specialized fast path for byte vectors, i.e. `Vec<u8>`) so that it does not pre-allocate the full declared capacity up front. Options:
- Read incrementally into a bounded buffer (e.g., read in fixed-size chunks, e.g. 8–64 KB at a time, growing the `Vec` only as bytes are actually confirmed read), so allocation tracks bytes received rather than the declared length.
- Alternatively, use `Read::take(len as u64)` combined with `read_to_end` (or a manually bounded loop) so the OS/stream naturally limits reads to available bytes without pre-committing capacity.
- For the specific `u8` case (the `data` field), replace the generic `T::consensus_deserialize` per-item loop with a single bounded `read_exact`/incremental read into a buffer that grows geometrically as data actually arrives, capped at `STACKERDB_MAX_CHUNK_SIZE`.

```rust
// stackslib/src/net (or libstackerdb/src/tests) — memory-amplification test
use std::io::Cursor;
use libstackerdb::StackerDBChunkData;
use stacks_common::codec::StacksMessageCodec;

#[test]
fn test_chunk_data_length_prefix_overallocation() {
    // slot_id (4) + slot_version (4) + sig (65) + declared data len = 16MB, but 0 actual data bytes
    let mut bytes = vec![];
    bytes.extend_from_slice(&0u32.to_be_bytes());       // slot_id
    bytes.extend_from_slice(&0u32.to_be_bytes());       // slot_version
    bytes.extend_from_slice(&[0u8; 65]);                // sig (MessageSignature)
    bytes.extend_from_slice(&(16 * 1024 * 1024u32).to_be_bytes()); // declared data length = 16MB
    // no actual data bytes appended -- stream ends here

    let mut cursor = Cursor::new(bytes);
    let result = StackerDBChunkData::consensus_deserialize(&mut cursor);

    // Expect an UnexpectedEof/ReadError, but by the time this returns,
    // Vec::with_capacity(16*1024*1024) has already executed inside read_next_vec
    // (stacks-common/src/codec/mod.rs:183), which can be observed via an
    // allocator-instrumented build (e.g. a custom #[global_allocator] wrapper
    // recording peak allocation size) asserting peak_alloc >= 16*1024*1024
    // despite only ~77 bytes being sent on the wire.
    assert!(result.is_err());
}
```
Run this with an instrumented global allocator (tracking peak single-allocation size) to assert that a ~16MB allocation occurs despite zero payload bytes being available, confirming the allocation is driven by the untrusted length prefix rather than actual bytes read.

```rust
fn read_next_vec<T: StacksMessageCodec + Sized, R: Read>(
    fd: &mut R,
    num_items: u32,
    max_items: u32,
) -> Result<Vec<T>, Error> {
    let len = u32::consensus_deserialize(fd)?;

    if max_items > 0 {
        if len > max_items {
            // too many items
            return Err(Error::DeserializeError(format!(
                "Array has too many items ({len} > {max_items})"
            )));
        }
    } else if len != num_items {
        // inexact item count
        return Err(Error::DeserializeError(format!(
            "Array has incorrect number of items ({len} != {num_items})"
        )));
    }

    if (mem::size_of::<T>() as u128) * (len as u128) > MAX_MESSAGE_LEN as u128 {
        return Err(Error::DeserializeError(format!(
            "Message occupies too many bytes (tried to allocate {}*{}={})",
            mem::size_of::<T>() as u128,
            len,
            (mem::size_of::<T>() as u128) * (len as u128)
        )));
    }

    let mut ret = Vec::with_capacity(len as usize);
    for _i in 0..len {
        let next_item = T::consensus_deserialize(fd)?;
        ret.push(next_item);
    }

    Ok(ret)
}
```
