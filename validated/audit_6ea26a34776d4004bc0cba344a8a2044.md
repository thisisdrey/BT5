### Title
Front-running a user's signed Wallet Contract transaction lets an attacker steal the relayer fee/refund - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The reported Permit2 bug is a nonce-based front-running issue: a signed authorization (with a fixed nonce) can be observed and submitted by a third party ahead of the intended caller, consuming the nonce and diverting the outcome. The closest reachable analog in nearcore is the ETH-implicit `WalletContract`'s `rlp_execute` entry point, which accepts a signed RLP Ethereum transaction (`tx_bytes_b64`) from *any* predecessor account and validates it purely against an on-chain `nonce` counter and the embedded ECDSA signature [1](#0-0) , with nonce/target validation performed in `validate_tx_relayer_data` [2](#0-1) .

### Finding Description
The Wallet Contract implements NEP-518 meta-transactions: a user signs an Ethereum-style transaction off-chain (via their Secp256K1 key) and hands the RLP bytes to a relayer, who calls `rlp_execute(target, tx_bytes_b64)` on the user's ETH-implicit account. Anyone can be `predecessor_account_id` (the "relayer") — there is no restriction on who submits the call, since the security guarantee is supposed to come entirely from the embedded signature and nonce check, exactly like a `Permit2.permit` call.

Because the signed transaction bytes must be transmitted to a relayer to be submitted, they are inherently visible to that relayer (and to anyone who can observe the relayer's mempool/backend) before being included on-chain. A malicious party who intercepts these bytes can call `rlp_execute` themselves, before the intended/honest relayer's transaction lands. `validate_tx_relayer_data` only checks that `tx.nonce == expected_nonce` and increments `self.nonce` once processed [2](#0-1) ; it performs no check on who the caller (`predecessor_account_id`) is [3](#0-2) .

Crucially, the contract pays gas/fee refunds and caller deposit refunds back to whichever account happened to invoke `rlp_execute` (the `predecessor`/caller), not to the relayer the user intended. This is visible in the `ExecuteResponse`/`CallerDeposit` refund flow in `rlp_execute_callback`, which refunds `CallerDeposit{account_id, ...}` — populated from the caller of `rlp_execute` — on promise failure [4](#0-3) , and the EVM-emulation fee computed from the signed tx's `max_fee_per_gas * gas_limit` is intended to reimburse "whichever relayer" submits it [5](#0-4) ; a test explicitly documents this design: "If an external relayer triggers the transaction then it is compensated for the Near gas" [6](#0-5) .

Because the nonce/signature check has nothing to do with which account calls `rlp_execute`, an attacker who obtains the signed bytes (from mempool sniffing, a leaked relayer API, or any off-chain channel where the user shared them with the intended relayer) can front-run the honest relayer's submission of that same nonce, executing the user's transaction themselves and collecting the relayer compensation instead of the intended relayer — directly mirroring the missing-front-run-protection bug class described in the report (anyone able to observe/replay the pre-signed authorization can act on it ahead of the intended party).

### Impact Explanation
This does not put user funds directly at risk (the action executed is exactly what the user signed, and it can only be executed once due to the nonce), but it constitutes economic theft of the relayer's expected fee/gas-refund compensation — an unprivileged third party can systematically intercept and front-run relayer submissions to redirect fees intended for the honest relayer to themselves. It also causes denial-of-service/wasted-gas for the honest relayer's now-stale (already-consumed-nonce) submission, which will revert with `RelayerError::InvalidNonce` and can even trigger a self-ban path if the honest relayer is also `signer_account_id == current_account_id` [7](#0-6) .

### Likelihood Explanation
Exploitation requires only observing the RLP-encoded, base64-signed transaction before it lands on-chain — a plausible scenario in any real-world relayer network, mempool-like transport, or a slow/multi-hop relayer path. No special privileges are needed; the attack is a straightforward unprivileged-signer front-run once the signed payload is known.

### Recommendation
Bind the relayer identity into the meta-transaction protocol so a specific caller (or a caller-agnostic escrow that always refunds the *original signer's designated relayer*) is required, or require the intended relayer's account to be committed to at signing time and checked against `predecessor_account_id` in `validate_tx_relayer_data`. Alternatively, adopt a commit-reveal or authorization scheme that cannot be redirected to a different fee recipient after being shared with a relayer, analogous to wrapping front-runnable permission grants (e.g., `Permit2.permit`) in protections that tie the beneficiary to the original request rather than to whoever submits it first.

### Proof of Concept
1. User signs an RLP Ethereum transaction (e.g., a token transfer or self base-token transfer) with nonce `N` intended for relayer `R`, computing a fee reimbursement in the tx's `max_fee_per_gas * gas_limit` per `parse_rlp_tx_to_action` [5](#0-4) .
2. User transmits the base64 `tx_bytes_b64` to relayer `R` for submission via `rlp_execute`.
3. Attacker `A`, having observed the bytes in transit (e.g., via a shared relayer backend, public mempool relay, or interception), calls `rlp_execute(target, tx_bytes_b64)` from their own account before `R` does.
4. `validate_tx_relayer_data` accepts the call because `tx.nonce == expected_nonce` and the signature is valid — it never checks `predecessor_account_id` [8](#0-7) ; `self.nonce` increments in `address_check_callback`/`inner_rlp_execute` flow [9](#0-8) .
5. The action executes as signed, and any gas/fee compensation configured to go to the calling relayer is paid to `A` instead of `R`.
6. `R`'s later submission of the same signed bytes with nonce `N` now fails with `Error::Relayer(RelayerError::InvalidNonce)`, wasting `R`'s gas and potentially triggering a self-ban if `R == current_account_id` [7](#0-6) .

fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

    let nonce = if tx.nonce <= U64_MAX {
        tx.nonce.low_u64()
    } else {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    };
    if nonce != expected_nonce {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    }

    // Relayers must attach at least as much gas as the user requested.
    let gas_limit = if tx.gas_limit < U64_MAX { tx.gas_limit.as_u64() } else { u64::MAX };
    if env::prepaid_gas().as_gas() < gas_limit.saturating_mul(GAS_MULTIPLIER) {
        return Err(Error::Relayer(RelayerError::InsufficientGas));
    }

    Ok(target_kind)
