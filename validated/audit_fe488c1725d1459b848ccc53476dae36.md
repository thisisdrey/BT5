### Title
Unstaked attacker can exhaust the shared `ClientConnectionTracker` slot pool during the QUIC handshake window, starving staked senders of TPU connections - (streamer/src/nonblocking/quic.rs)

### Summary
`ClientConnectionTracker::new` enforces a single, un-partitioned `max_concurrent_connections()` limit that is shared by staked and unstaked peers alike, and the slot is reserved as soon as a connection attempt passes the overall/per-IP rate limiters — before the QUIC handshake completes. An unstaked attacker who opens connections that stall for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) can keep this shared pool saturated and cause legitimate staked connection attempts to be refused with `refused_connections_too_many_open_connections`.

### Finding Description
In `run_server`, incoming QUIC connections are admitted in this order: overall rate limiter check, per-IP rate limiter check, then `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` [1](#0-0) . Only after the tracker slot is successfully reserved does the code call `incoming.accept()` and spawn `setup_connection`, which performs the actual QUIC/TLS handshake. The tracker slot is not released until the `ClientConnectionTracker` is dropped [2](#0-1) , which happens only when the connection setup finishes or times out.

Crucially, `max_concurrent_connections()` is a single global counter shared across staked and unstaked peer types — it does not reserve any portion exclusively for staked peers: [3](#0-2) [4](#0-3) 

The per-staked/per-unstaked separation (`ConnectionTable` with `ConnectionTableType::Staked`/`Unstaked`, and per-peer connection caps in `SwQosConfig`) is only enforced later, inside `cache_new_connection`/`try_add_connection`, i.e., *after* the handshake has already completed and the connection has already consumed a tracker slot [5](#0-4) . There is no reservation of tracker capacity specifically for staked peers at admission time.

The handshake timeout window is `QUIC_CONNECTION_HANDSHAKE_TIMEOUT = Duration::from_secs(2)`, described as starting once the Initial packet is received and canceled once the Handshake packet is received [6](#0-5) . Because the tracker slot is acquired at connection-attempt time and not released until this handshake process resolves (success, error, or timeout), an attacker that causes connections to stall for the full window occupies a slot for up to 2 seconds per connection attempt.

The only defenses upstream of the tracker are:
- an overall token-bucket rate limiter (`overall_connection_rate_limiter`), which limits burst rate but refills continuously, so a sustained (non-bursty) attack rate under the refill rate is never blocked [7](#0-6) ;
- a per-IP rate limiter, which only limits the rate from a single IP, not the aggregate rate from many distinct attacker-controlled source IPs [8](#0-7) .

Neither of these limits the *number of concurrently outstanding, not-yet-handshaken* connections per peer type — they only throttle new-connection attempt rate. The `max_concurrent_connections()` formula comment ("Allow 25% more connections than required to allow for handshake") shows the developers intended a small buffer for handshake-in-flight connections, but that buffer is a fixed percentage of the *total* configured capacity and is shared indiscriminately — an unstaked attacker sustaining enough slow/stalled handshakes (spread across enough source IPs to stay under per-IP limiting, and at a rate under the overall token-bucket refill rate) can consume this shared headroom (and beyond, since unstaked connections are not blocked from taking tracker slots up to the full `max_concurrent_connections()` value) continuously, so that legitimate staked connection attempts fail at the tracker-slot check itself, before ever reaching the staked-aware `ConnectionTable` logic that would otherwise prioritize them.

### Impact Explanation
This is a QoS/prioritization-bypass leading to denial of TPU connection capacity for staked (fee-paying, consensus-participating) senders, caused entirely by an unstaked, unprivileged remote client. It matches the "unprivileged client bypasses/unfairly captures connection... QoS limits and starves legitimate senders of TPU capacity" bounty category referenced in the question. The impact is transient (bounded by traffic duration) but directly attacks validator availability for real transaction ingestion — a leader under this attack could refuse legitimate staked traffic while it is leader.

### Likelihood Explanation
Feasible for an attacker with access to multiple source IPs (e.g., cloud/VPS IP ranges) and no stake requirement. The attacker only needs to:
1. Open connections from many distinct IPs to remain under per-IP rate limiting,
2. Keep aggregate new-connection rate under the overall token-bucket refill rate to avoid the burst limiter,
3. Cause connections to stall during the handshake phase for close to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (e.g., by completing the Initial exchange but delaying/no-oping subsequent handshake flight, or via network-level delay), repeatedly.

This requires no validator, leader, gossip, or staked control, and no more than ordinary QUIC client behavior against the public TPU port — well within the defined attacker model.

### Recommendation
Partition `max_concurrent_connections` capacity by peer type at admission time (before/while acquiring the `ClientConnectionTracker` slot), e.g., maintain separate tracker slot pools/counters for staked vs. unstaked in-flight connections, or reserve a guaranteed minimum number of slots for staked peers that unstaked connections cannot consume. Additionally, consider lowering `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` for unstaked-looking connections or tracking per-IP concurrent (not just rate-limited) outstanding handshake attempts to bound how many slots a single attacker-controlled address space can occupy at once.

### Proof of Concept
Unit/integration test plan (in `streamer/src/nonblocking/quic.rs` test module, alongside `test_client_connection_tracker`):
1. Configure a `QosController` (e.g., `SwQos`/`SimpleQos`) with a small `max_staked_connections`/`max_unstaked_connections` so `max_concurrent_connections()` is small and deterministic (e.g., 4).
2. Spawn `N = max_concurrent_connections()` client QUIC connections from distinct simulated source IPs, each configured to stall during the TLS handshake (e.g., a custom `quinn::Connecting` future that never completes, or a client that sends the Initial packet then withholds the Handshake flight) so that each call to `ClientConnectionTracker::new` succeeds and holds its slot for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
3. Concurrently (while the stalled attacker connections are still pending) attempt a legitimate, well-behaved connection using a keypair that is present in `StakedNodes` (i.e., staked).
4. Assert that the staked connection attempt is refused (`stats.refused_connections_too_many_open_connections` increments and the staked client's connection fails/times out), demonstrating that a fully unstaked flood of stalled handshakes can deny tracker slots to a staked sender — i.e., `qos.max_concurrent_connections()` provides no reserved capacity for staked-only admission.
5. As a fuzz variant, randomize per-connection stall duration up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` and randomize the number/arrival timing of attacker connections relative to the staked connection arrival, asserting in all cases that the staked connection is never starved when attacker slot usage stays at or below `max_concurrent_connections() - 1`, but is starved once attacker connections saturate `max_concurrent_connections()`.
