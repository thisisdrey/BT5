### Title
Per-source stream throttling is enforced per-QUIC-connection, not per-IP, letting an unprivileged unstaked peer multiply its effective transaction-stream throughput by `max_connections_per_unstaked_peer` - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`ConnectionStreamCounter` and `throttle_stream` bound the stream rate of a *single* QUIC connection to `max_unstaked_load_in_throttling_window` streams per `STREAM_THROTTLING_INTERVAL`, but this budget is never aggregated across the multiple connections a single unstaked IP is allowed to hold. Because `SwQos::cache_new_connection` allocates a brand-new `ConnectionStreamCounter` for every connection, an unstaked attacker can open up to `max_connections_per_unstaked_peer` concurrent connections from one IP and drive each at its own independent per-connection cap, achieving an aggregate stream (and therefore sigverify/dedup/scheduling) rate that is a multiple of the intended per-source budget.

### Finding Description
`StakedStreamLoadEMA::new` derives `max_unstaked_load_in_throttling_window` from the fixed constant `MAX_UNSTAKED_TPS = 200` [1](#0-0) [2](#0-1) . This value is returned unconditionally as the per-connection cap for `ConnectionPeerType::Unstaked` from `available_load_capacity_in_throttling_duration` [3](#0-2) .

Every new connection gets its own independent `ConnectionStreamCounter`, created inline when the connection is added to the table: [4](#0-3) 

`throttle_stream` only ever reads/reset the `stream_count` on the `ConnectionStreamCounter` belonging to that one connection [5](#0-4) , and `on_stream_accepted` increments only that connection's own counter (`conn_context.stream_counter...stream_count.fetch_add`) [6](#0-5) . Critically, `StakedStreamLoadEMA::increment_load` — the only place that tracks *aggregate* load across connections — only updates `load_in_recent_interval` `if peer_type.is_staked()` [7](#0-6) ; unstaked traffic is never accumulated into any cross-connection counter.

Since a single unstaked IP is permitted up to `max_connections_per_unstaked_peer` (default `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER = 8`) simultaneous connections [8](#0-7) , each with its own independent 200-TPS-derived budget, the attacker does not even need clever stream-interleaving — simply opening N ≤ `max_connections_per_unstaked_peer` connections and driving streams on all of them concurrently at full per-connection rate yields an aggregate throughput of `N × max_unstaked_load_in_throttling_window`, i.e. up to 8× the value the constant name (`MAX_UNSTAKED_TPS`) implies is the intended per-source ceiling. No existing guard aggregates this across connections from the same IP: the connection-count limiter (`max_connections_per_unstaked_peer`) and per-IP new-connection-rate limiter (`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`) only cap the number/rate of connections, not the summed stream throughput once those connections are open.

### Impact Explanation
This lets an unprivileged, fee-free (or minimally-fee-paying) unstaked attacker push several times the intended per-source unstaked stream budget into the leader's sigverify/dedup/scheduling pipeline, by merely opening the number of connections already permitted per peer and driving each concurrently. This matches the "cheaply force sigverify, dedup, scheduling, or buffering work that vastly exceeds the fees ever collected" impact category — pre-fee CPU work (QUIC stream reads, packet framing, sigverify, dedup) is incurred per-stream regardless of whether the underlying transaction is ultimately dropped or unfunded.

### Likelihood Explanation
Fully reachable by an unprivileged remote client: it only requires establishing up to `max_connections_per_unstaked_peer` (default 8) QUIC connections from a single IP to the TPU port and sending streams concurrently on all of them, which is explicitly allowed by the connection-table logic. No staking, gossip participation, or special config is required — it works with default settings. The multiplier is bounded (equal to `max_connections_per_unstaked_peer`), so this is a throughput-amplification issue rather than an unbounded resource exhaustion.

### Recommendation
Aggregate stream-rate accounting per source IP (or per unstaked identity) rather than per connection — e.g., maintain a shared token bucket/counter keyed by `ConnectionTableKey` (IP) shared across all connections opened by that peer, so `max_unstaked_load_in_throttling_window` bounds the *sum* of streams across all of a peer's concurrent connections, not each connection independently.

### Proof of Concept
```rust
// streamer/src/nonblocking/swqos.rs (test module)
#[tokio::test(flavor = "multi_thread")]
async fn test_unstaked_aggregate_stream_rate_exceeds_per_source_cap() {
    // Configure max_connections_per_unstaked_peer = 8 (default), single IP.
    let SpawnTestServerResult { server_address, stats, .. } = setup_quic_server(
        None,
        QuicStreamerConfig::default_for_tests(),
        SwQosConfig {
            max_connections_per_unstaked_peer: 8,
            ..SwQosConfig::default()
        },
    );

    // Open 8 concurrent connections from the same client IP.
    let mut conns = Vec::new();
    for _ in 0..8 {
        let endpoint = /* bind_to_localhost_unique + quinn::Endpoint as in existing tests */;
        let conn = endpoint.connect(server_address, "localhost").unwrap().await.unwrap();
        conns.push(conn);
    }

    // Drive each connection to its individual per-connection throttle cap
    // (max_unstaked_load_in_throttling_window streams) within one STREAM_THROTTLING_INTERVAL,
    // concurrently across all 8 connections.
    let mut handles = Vec::new();
    for conn in &conns {
        handles.push(tokio::spawn({
            let conn = conn.clone();
            async move {
                for _ in 0..20 { // per-connection cap for unstaked (derived from MAX_UNSTAKED_TPS)
                    let mut s = conn.open_uni().await.unwrap();
                    s.write_all(&[0u8]).await.unwrap();
                    s.finish().unwrap();
                }
            }
        }));
    }
    for h in handles { h.await.unwrap(); }

    // Assert: total accepted (non-throttled) streams within the interval from this single IP
    // is bounded by the intended per-source cap (~20), not 8x that (~160).
    // Expected finding: total_new_streams / throttled_streams shows aggregate acceptance
    // scales linearly with connection count instead of being capped independent of it.
    assert!(
        stats.total_new_streams.load(Ordering::Relaxed) <= 20,
        "aggregate unstaked stream throughput from single IP exceeded intended per-source cap: got {}",
        stats.total_new_streams.load(Ordering::Relaxed)
    );
}
```
Expected current (buggy) behavior: `total_new_streams` reaches ~160 (8 × 20) with `throttled_streams` staying near zero, demonstrating the per-source cap is evaded by connection parallelism rather than bounded at ~20 as the `MAX_UNSTAKED_TPS` constant implies.

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
