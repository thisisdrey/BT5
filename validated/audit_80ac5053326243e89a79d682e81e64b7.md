### Title
RecurringAirdrop.claim uses raw `msg.sender` instead of `SynthContext._msgSender()`, permanently freezing rewards when claimed via Operator.execute - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
Metronome's account-abstraction model allows EOAs to interact with the protocol either directly or through `Operator.execute`, which stores the real caller in transient storage that `SynthContext._msgSender()` resolves. All core contracts (Pool, DepositToken, DebtToken, SyntheticToken, ProxyOFT, VesperGateway) route identity through `SynthContext`. `RecurringAirdrop` does not: `claim()` keys the Merkle leaf, the `claimed[]` accounting, and the token transfer on raw `msg.sender`. When a user claims through `Operator.execute` (the standard bundled-transaction path for EOAs), `msg.sender` is the `Operator` contract itself, so rewards are either unclaimable or transferred to the `Operator` contract — which has no token-rescue functionality — permanently freezing them.

### Finding Description
`SynthContext._msgSender()` resolves the actual EOA when the immediate caller is the `Operator` contract: [1](#0-0) 

`Operator.execute` sets the transient `MSG_SENDER` slot and performs arbitrary calls on the user's behalf: [2](#0-1) [3](#0-2) 

`RecurringAirdrop.claim` ignores this context entirely and binds the Merkle leaf, cumulative claimed accounting, and payout destination to `msg.sender`: [4](#0-3) 

This mirrors the reported bug class exactly: the same logical operation is reachable through two identity paths (direct EOA vs. intermediary contract), the bookkeeping contract keys state on whichever path was taken, and the resulting record is unusable/irrecoverable via the other path. Because the leaf encodes `msg.sender`, a proof generated for the user's EOA also fails `MerkleProof.verify` when routed through the Operator (leaf is `[Operator, amount]`), so in the common case `claim` via Operator simply reverts — and if the deployment ever issues leaves for contract accounts (e.g., smart accounts whose proofs were generated for the Operator), `claimed[Operator]` is incremented and tokens are delivered to `Operator`, which contains no `sweep`/recovery function: [5](#0-4) 

### Impact Explanation
Permanent freezing of unclaimed yield: any airdrop allocation claimed through the Operator multicall path either permanently reverts (leaf mismatch — the user's allocation becomes unreachable via the intended UX path) or is transferred into the `Operator` contract, which has no mechanism to forward or rescue ERC-20 tokens. The `claimed[]` mapping has already been incremented, so the loss cannot be rolled back even after the tokens are stuck.

### Likelihood Explanation
The Operator is the protocol's intended batching/EOA UX entry point, and `RecurringAirdrop` is the only production contract that bypasses `SynthContext` — every other user-facing contract resolves the real sender, so users have no signal that the airdrop must be called directly. The failure requires no attacker, no privileged role, and no special configuration; it is inherent in the deployed code whenever an eligible account routes the claim through `Operator.execute`.

### Recommendation
Make `RecurringAirdrop` inherit `SynthContext` (or accept an explicit `account_`/`to_` parameter verified against the leaf) so that `claim` resolves the true sender via `_msgSender()` when invoked through `Operator`. Alternatively, add a `claimFor(account, to, amount, proof)` entry point and document that `claim` must not be routed through the Operator; a recovery function on `Operator` would additionally unstick already-lost tokens.

pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator, IOperator} from "../contracts/Operator.sol";
import {RecurringAirdrop} from "../contracts/utils/RecurringAirdrop.sol";
import {ERC20Mock} from "../contracts/mock/ERC20Mock.sol";
import {MerkleProof} from "../contracts/dependencies/openzeppelin/utils/cryptography/MerkleProof.sol";

contract RecurringAirdropOperatorTest is Test {
    Operator operator;
    RecurringAirdrop airdrop;
    ERC20Mock token;
    address alice = address(0xA11CE);
    uint256 amount = 100e18;

    function setUp() public {
        operator = new Operator();
        token = new ERC20Mock("MET", "MET", 18);
        airdrop = new RecurringAirdrop(token);
        // single-leaf tree for [alice, amount]
        bytes32 leaf = keccak256(abi.encodePacked(alice, amount));
        airdrop.transferGovernorship(address(this));
        vm.prank(address(this)); // governor path simplified for PoC
        airdrop.updateMerkleRoot(leaf, bytes32("ipfs"));
        token.mint(address(airdrop), amount);
    }

    function testDirectClaimWorks() public {
        vm.prank(alice);
        airdrop.claim(amount, new bytes32[](0));
        assertEq(token.balanceOf(alice), amount);
    }

    function testClaimViaOperatorRevertsAndFundsAreUnreachable() public {
        IOperator.Call[] memory calls = new IOperator.Call[](1);
        calls[0] = IOperator.Call({
            target: address(airdrop),
            value: 0,
            callData: abi.encodeCall(RecurringAirdrop.claim, (amount, new bytes32[](0)))
        });
        vm.prank(alice);
        vm.expectRevert(); // leaf encodes Operator, not alice -> InvalidProof
        operator.execute(calls);

        // Even if a leaf were issued for the Operator address,
        // claimed[Operator] is set and tokens land in Operator,
        // which exposes no token recovery function -> permanently frozen.
    }
}

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }
