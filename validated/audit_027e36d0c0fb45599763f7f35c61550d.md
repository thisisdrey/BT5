### Title
Unauthorized cross-repository object disclosure via `LinkRepositoryToObjectPool` missing ownership/relationship check - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` accepts any `(Repository, ObjectPool)` pair from the caller and links them without verifying that the object pool actually belongs to, or was created from, the target repository. Any caller able to invoke this RPC (i.e., Rails/any authenticated frontend on behalf of a user with write access to *some* repository) can point an arbitrary repository's alternates at an arbitrary pre-existing object pool whose relative path they can guess or otherwise learn, causing that repository to gain read access to all objects contained in the (potentially unrelated/private) pool.

### Finding Description
The handler resolves the target `repository` and the `pool` independently and links them with no cross-check: [1](#0-0) 

`poolForRequest`/`objectpool.FromProto` only validates that the pool path is a syntactically valid, existing pool repository — it does not verify that the object pool was created from, or is otherwise associated with, the `repository` being linked. The underlying `Link` function in `internal/git/objectpool/link.go` only checks whether the repository is already linked to a *different* pool (to avoid clobbering), but performs no authorization/ownership check tying the pool to the repository's lineage: [2](#0-1) 

Once linked, the repository's `objects/info/alternates` file references the pool's object directory, and Git (and any Gitaly RPC reading objects from that repository, e.g. `CommitService`) will transparently resolve any object ID that exists in the pool — even ones never pushed to the linking repository itself, as demonstrated by the project's own `TestLink` test which shows a pool commit becoming readable through the newly linked repository: [3](#0-2) 

This is exactly the object-pool/alternates isolation boundary called out in the docs — object pool membership is supposed to be scoped to legitimate fork relationships: [4](#0-3) 

The only mitigating control is that Rails is expected to only ever call this RPC for legitimate fork relationships, but Gitaly itself enforces no such invariant at the RPC layer — the same "someone forgot the authorization check" class of bug identified in the referenced Solidity report (`closeLoan()` trusting the caller to be the borrower with no explicit check).

### Impact Explanation
If an actor can reach this RPC directly (e.g., a compromised/less-trusted Rails-adjacent caller, or a bug elsewhere that allows arbitrary `LinkRepositoryToObjectPool` calls to reach Gitaly unauthorized), they can disclose objects (blobs, commits, potentially private source code) from a private or unrelated repository's object pool into a repository they control, then read those objects out via ordinary Gitaly read RPCs. This is a cross-repository object confidentiality violation — objects that should be scoped to one project boundary become readable from another.

### Likelihood Explanation
Exploitability depends on whether an unprivileged/unrelated caller can invoke `LinkRepositoryToObjectPool` with an `ObjectPool` value it doesn't legitimately own — this RPC is designed to be called by Rails only in the context of fork creation, so the primary trust boundary is enforced above Gitaly, not within it. Within Gitaly's own code there is no defense-in-depth check, so any path that lets a user influence the `ObjectPool` field of this request (misconfiguration, another vulnerability, or a trusted-but-compromised caller) directly yields cross-repository object access.

### Recommendation
Add an explicit check in `LinkRepositoryToObjectPool` (and in `internal/git/objectpool/link.go`'s `Link`) that the object pool was actually created from, or has a legitimate recorded relationship (e.g., via `CreateObjectPool`'s origin) with the target repository, rather than trusting the caller-supplied pairing unconditionally. At minimum, defense-in-depth should reject linking to a pool the repository has no established provenance with.

### Proof of Concept
1. Create repository A and repository B (unrelated, no fork relationship) on the same storage.
2. Create object pool P from A via `CreateObjectPool(origin=A)`, so P contains A's objects (including sensitive commits).
3. Call `LinkRepositoryToObjectPool(repository=B, object_pool=P)` — this succeeds with no error, as shown by the flow in `internal/gitaly/service/objectpool/link.go` and validated by `TestLink`'s "successful" case which only checks pool existence, not lineage: [5](#0-4) 
4. From B's context, read any object ID belonging to A's pool via `CommitService`/`ReadObject` — it now resolves successfully through B's newly-added alternates, disclosing A's objects to B.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}
