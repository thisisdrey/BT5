## Title
Silent transfer failure in `claim_child_bounty` permanently locks child-bounty funds and finalizes a fake payout - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`pallet-child-bounties::claim_child_bounty` pays the curator fee and beneficiary payout via `T::Currency::transfer(..., AllowDeath)` but only verifies success with `debug_assert!`, which compiles to a no-op in release/production builds. If either transfer fails (e.g. the destination account does not exist and the amount is below the Existential Deposit), the pallet still deletes the child-bounty record and emits a `Claimed` event as if payment succeeded, permanently orphaning the funds still held in the child-bounty sub-account.

## Finding Description
In `claim_child_bounty` [1](#0-0) , the curator-fee and beneficiary payouts are performed like this:

```rust
let fee_transfer_result = T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath);
debug_assert!(fee_transfer_result.is_ok());
...
let payout_transfer_result = T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath);
debug_assert!(payout_transfer_result.is_ok());
```

Regardless of whether either `transfer` call actually succeeded, execution continues unconditionally: the `Claimed` event is deposited, the child-bounty count is decremented, the description is removed, and `*maybe_child_bounty = None;` deletes the bounty record [2](#0-1) .

`pallet_balances`'s `transfer` (via `Currency::withdraw`/`deposit_creating`) enforces the Existential Deposit rule for the destination account: if the destination doesn't already exist and the transferred amount is below `ExistentialDeposit`, the call returns `Error::<T,I>::ExistentialDeposit` rather than creating a dusted account [3](#0-2) . `AllowDeath` only relaxes the requirement on the *source* account continuing to exist — it does not bypass the destination-side ED requirement.

Because `debug_assert!` is stripped in release builds (which is how production runtimes are compiled), this failure is silently swallowed: the child-bounty is deleted from storage as if paid, but the balance never left the `child_bounty_account`. There is no reclaim path for child bounties analogous to `pallet-bounties::reclaim_bounty_funds` (added in a later PR for the parent-bounty case, see `prdoc/stable2603-1/pr_11425.prdoc`) — `substrate/frame/child-bounties/src/lib.rs` has no such permissionless-sweep call, so the funds sitting in the deterministic `child_bounty_account` become permanently unreachable once the bounty record is gone.

This directly mirrors the external report's core pattern: an unchecked return value from a token transfer causes the caller to proceed as though the operation succeeded, corrupting downstream state (here: the child-bounty storage entry and the `Claimed` event) and causing fund loss to the intended beneficiary/curator.

## Impact Explanation
This is a permanent user/protocol fund lock: value that was earmarked for a beneficiary or curator becomes irrecoverably stranded in a sub-account with no code path referencing it afterward, while the chain simultaneously emits state (`Claimed` event, bounty removal) asserting the payment succeeded. This aligns with the "permanent user-fund or bridge-state lock" and "public underpriced work/false state acceptance" categories in scope, since it happens through a normal permissionless `claim_child_bounty` call with no attacker privilege beyond being the signer who triggers the (anyone-can-call) claim.

## Likelihood Explanation
The triggering condition (destination account non-existent, payout amount below `ExistentialDeposit`) is realistic: a curator fee or a small residual bounty payout can easily fall under ED, and a fresh curator/beneficiary account may never have received funds before. No malicious relayer, validator, or governance action is required — a normal, permissionless `claim_child_bounty` call by any signed account after the payout delay elapses is sufficient to hit this path.

## Recommendation
Replace the `debug_assert!` checks in `claim_child_bounty` with proper `?`-propagated `DispatchResult` handling (as is already done correctly elsewhere in the pallet, e.g. `impl_close_child_bounty`'s transfer is also only `debug_assert`-checked and should be fixed too), so a failed transfer aborts the whole extrinsic (rolling back the `try_mutate_exists`) instead of silently deleting the bounty. Additionally, add a permissionless "reclaim stranded child-bounty funds" extrinsic analogous to `pallet-bounties::reclaim_bounty_funds` for cases where funds do get orphaned.

## Proof of Concept
1. Council/curator flow creates and funds a child bounty with a small `fee`/`value` (e.g. slightly below `ExistentialDeposit`) and assigns a `curator`/`beneficiary` whose account has never existed on-chain.
2. Bounty transitions to `PendingPayout`; wait for `unlock_at`.
3. Anyone calls `claim_child_bounty(parent_bounty_id, child_bounty_id)`.
4. Inside, `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)` returns `Err(Error::<T>::ExistentialDeposit)` because `beneficiary` doesn't exist and `payout < ED`.
5. In a release-mode runtime, `debug_assert!(payout_transfer_result.is_ok())` is compiled out and does nothing.
6. Execution proceeds: `Claimed` event fires, `ParentChildBounties` count decrements, `ChildBountyDescriptionsV1` is removed, and `*maybe_child_bounty = None` deletes the bounty.
7. The balance remains in `child_bounty_account` (still derivable via `Self::child_bounty_account_id`) but with no remaining pallet call able to reference or recover it, permanently locking the funds while the chain's event log falsely records a successful payout.

		if value.is_zero() {
			return Self::PositiveImbalance::zero();
		}

		Self::try_mutate_account_handling_dust(
			who,
			false,
			|account, is_new| -> Result<Self::PositiveImbalance, DispatchError> {
				let ed = T::ExistentialDeposit::get();
				ensure!(value >= ed || !is_new, Error::<T, I>::ExistentialDeposit);

				// defensive only: overflow should never happen, however in case it does, then this
				// operation is a no-op.
				account.free = match account.free.checked_add(&value) {
					Some(x) => x,
					None => return Ok(Self::PositiveImbalance::zero()),
				};

				Self::deposit_event(Event::Deposit { who: who.clone(), amount: value });
				Ok(PositiveImbalance::new(value))
			},
		)
		.unwrap_or_else(|_| Self::PositiveImbalance::zero())
