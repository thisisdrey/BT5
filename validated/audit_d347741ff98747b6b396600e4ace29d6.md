### Title
Attacker can permanently saturate a victim's per-account token list via dust deposits/transfers, blocking new collateral deposits and debt issuance - (`contracts/Pool.sol`, `contracts/DepositToken.sol`)

### Summary
CVE-2020-35498 is a DoS where a single crafted packet makes the kernel megaflow disproportionately "wide," exhausting resources. The Metronome analog is the `MAX_TOKENS_PER_USER = 30` cap on `depositTokensOfAccount`/`debtTokensOfAccount` in `Pool`: an unprivileged attacker can "widen" any victim's position-tracking list at dust cost, after which the victim cannot add any new collateral or debt token. Because dust entries cannot be cleared while the victim carries debt (`unlockedBalanceOf` returns 0 for underwater accounts), the slot occupation is effectively permanent for the accounts that most need to add collateral.

### Finding Description
`Pool` tracks per-account token sets with `MappedEnumerableSet` (`depositTokensOfAccount`, `debtTokensOfAccount`) and enforces `MAX_TOKENS_PER_USER = 30` through `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0) . Entries are added whenever an account's balance of a deposit token or debt token goes from 0 to >0:

- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` when `_balanceBefore == 0` [2](#0-1) .
- `DepositToken._transfer` does the same on recipient first receipt [3](#0-2) .
- `DebtToken._mint` calls `pool.addToDebtTokensOfAccount` similarly [4](#0-3) .

Two permissionless pushes exist:

1. `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` [5](#0-4)  — the attacker can deposit 1 wei of each registered collateral directly into the victim's list, no transfer needed.
2. `DepositToken.transfer` is public and only checks the *sender's* unlocked balance [6](#0-5)  — the recipient's consent is never required, so dust `transfer(victim, 1)` also fills a slot.

Once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`, every subsequent `deposit` of a new collateral type, `issue`/`mint` of a new synthetic debt (`DebtToken.issue` → `_mint` → `addToDebtTokensOfAccount`), and inbound `transfer`/`seize` of a new deposit token reverts with `UserReachedMaxTokens`.

Critically, the victim often cannot clear the dust entries. `transfer`/`withdraw` require `unlockedBalanceOf(account_) >= amount`, and `unlockedBalanceOf` returns 0 when the account's `issuableInUsd` is 0 — i.e., precisely for an underwater or fully-collateralized-to-limit victim [7](#0-6) . So the accounts most in need of depositing a *different* collateral type to restore health are permanently barred from doing so.

### Impact Explanation
A targeted victim holding a leveraged position that drifts toward liquidation cannot deposit any collateral type not already in their list. If their existing collateral is the asset that crashed, they have no recovery path: `deposit` reverts, `issue` of a new debt type reverts, and the forced-dust tokens cannot be transferred or withdrawn because the underwater position locks them (`NotEnoughFreeBalance`). The position is pushed to liquidation — the attacker can even act as liquidator to capture the liquidation bonus — causing direct loss of the victim's collateral and/or freezing of their deposits until all debt is repaid by other means. This is a temporary/permanent freezing of funds plus indirect theft via guaranteed liquidation, matching the CVE's availability-loss bug class.

### Likelihood Explanation
Likelihood is bounded by the number of registered deposit tokens in the target pool: the attacker can only add entries for deposit tokens the pool actually lists (`_revertIfSenderIsNotDepositToken` gates the list) [8](#0-7) . Debt tokens cannot be pushed (they are non-transferable [9](#0-8)  and `issue` charges the caller's own collateral), so the attacker needs `30 - (victim's existing tokens)` distinct registered deposit tokens. For a victim already holding several positions and a pool with ~10+ collateral types, saturation is cheap (dust amounts × number of tokens, plus gas). A healthy victim could clear entries by transferring dust to a fresh address, so the attack only fully lands against accounts at/near their collateral limit — but those are exactly the accounts where blocking new collateral is decisive. No privileged role, oracle manipulation, or external dependency is required; `whenNotPaused`/`nonReentrant`/`SynthContext` checks do not impede the attack.

### Recommendation
- Require recipient opt-in for list additions: e.g., only add to `depositTokensOfAccount` on user-initiated `deposit`/`withdraw` paths where `account_ == _msgSender()` or an explicit `accept` flag, or make `transfer`/`deposit(..., onBehalfOf_)` for first-time tokens revert unless the recipient pre-approves.
- Alternatively, allow `transfer` of a full balance even when locked solely to free a list slot, or raise/remove the hard cap and bound iteration cost by computing `debtPositionOf`/`depositOf` over a caller-supplied token subset.
- Emit/index list membership so users can cheaply detect and clean unsolicited dust entries.

### Proof of Concept
Hardhat (fork or unit with deployed pool, `N` registered deposit tokens, `N ≥ 30 - victimSlots`):

```ts
// attacker: fill victim's depositTokensOfAccount to the cap
const victim = alice.address
const dts: DepositToken[] = [msdVaUSDC, msdVaETH, /* ... all registered ... */]
for (const dt of dts) {
  if ((await dt.balanceOf(victim)) === 0) {
    const underlying = await ethers.getContractAt('IERC20', await dt.underlying())
    await underlying.connect(attacker).approve(dt.address, 1)
    await dt.connect(attacker).deposit(1, victim) // 1 wei, onBehalfOf = victim
    // or: await dt.connect(attacker).transfer(victim, 1)
  }
}
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length.gte(30)

// victim's position is now at cap: any new collateral deposit reverts
const newDt = msdNewCollateral // deposit token victim doesn't hold
await expect(newDt.connect(alice).deposit(parseUnits('1', 18), alice.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim cannot issue a new debt type either
await expect(debtTokenMsETH.connect(alice).issue(1, alice.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// if victim is underwater (issuableInUsd == 0), dust cannot be cleared:
await expect(dts[0].connect(alice).transfer(bob.address, 1))
  .revertedWithCustomError(dts[0], 'NotEnoughFreeBalance')
// => victim permanently cannot add collateral -> forced liquidation
```

Note: a concrete fork PoC must use the actual deployed pool's registered deposit token set; if a pool registers fewer tokens than needed to reach 30 for a fresh account, target accounts that already occupy slots.
