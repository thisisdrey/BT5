**Analysis summary:**

The exclusion of `DelayedReceipt`/`DelayedReceiptIndices`/`BufferedReceipt*` from `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` and thus from `remove_account` is intentional: these are documented as "global state for the shard" — a shard-wide FIFO queue, not per-account state [1](#0-0) . `remove_account` only clears `Account`, `ContractCode`, `AccessKey`/gas-key rows, and `ContractData` [2](#0-1) , deliberately leaving the delayed-receipt queue untouched.

The scenario described (receipt admitted to D, D deleted and recreated, receipt later pops and delivers to "new" D) does not create an authorization bypass because:

1. **Delivery always resolves against current state, by design.** `apply_action_receipt` loads the receiver account fresh from `state_update` at the moment of delivery — not at admission time [3](#0-2) . This is the same mechanism exercised (and explicitly asserted correct) by the existing same-chunk test `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`, which documents that "a FunctionCall whose receiver is deleted and recreated ... must resolve to the freshly recreated (no-code) account, not to a stale contract" [4](#0-3) . The delayed-queue case is the identical mechanism spread across chunks instead of within one chunk.

2. **`check_actor_permissions` does not gate `FunctionCall`/`Transfer` by the receiver's access-key set at all.** Only self-management actions (`AddKey`, `DeleteKey`, `DeployContract`, `Stake`, etc.) require `actor_id == account_id`, and `DeleteAccount` additionally checks locked balance [5](#0-4) . `FunctionCall`/`Transfer`/`CreateAccount`/`Delegate` have no actor-permission gate at all [6](#0-5) . So there is no "old owner's AddKey set" ever consulted for a delayed `FunctionCall` receipt — access-key authorization for that action already happened on the *sender's* shard at transaction-signing/verification time (nonce, signature, access-key permission), which is a separate, already-consumed authorization step, not something re-derived from the receiver account's key set at delivery.

3. This is the fundamental, unavoidable consequence of NEAR's asynchronous cross-shard/cross-chunk receipt model — any receipt (delayed or not) executes against whatever state the receiver account holds when it is finally processed, which can differ from state at receipt-creation time by design. This is documented in `docs/RuntimeSpec/ApplyingChunk.md` and the runtime-execution spec, and is not something `remove_account`'s account-scoped design introduces or could plausibly "fix" — the delayed queue is explicitly shard-global and independent of the account lifecycle by design [7](#0-6) .

No unprivileged-attacker-reachable theft, fund freezing, double-spend, or authorization escalation results from this; the behavior matches the intended/documented model and is already covered by existing tests for the analogous same-chunk case.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}

### Why delayed receipts are special?

For all the other columns, there is no dependency between entries, but in case of delayed receipts - we are forming a 'queue'. We store the information about the first index and the last index (in DelayedReceiptIndices struct).

Then, when receipt arrives, we add it as the 'DELAYED_RECEIPT + last_index' key (and increment last_index by 1).

That is why we cannot move this trie entry type in the same way as others where account id is part of the key. Instead we do it by iterating over this queue and inserting entries to the queue of the relevant child shard.
