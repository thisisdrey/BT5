### Title
Unbounded array allocation from attacker-controlled length field in `ValidateMultiSign`/`BatchValidateSign` precompiles when `allowTvmSelfdestructRestriction` is inactive - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Ankaios CVE describes an agent that trusts a length field declared inside a message and allocates memory for it without any upper bound, letting an unprivileged sender crash the process. The java-tron TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign` contain the same pattern: they read a "count" value directly out of attacker-supplied calldata words and immediately allocate a `byte[count][]` array, with the sanity check on that count gated behind a feature flag.

### Finding Description
`extractBytesArray` and `extractBytes32Array` take the array length directly from calldata without any bound checking: [1](#0-0) 

In `ValidateMultiSign.execute`, the `MAX_SIZE` bound is only enforced when `VMConfig.allowTvmSelfdestructRestriction()` is true; when it is false, `extractBytesArray` is invoked directly on the attacker-controlled offset with no prior size check: [2](#0-1) 

The same pattern repeats in `BatchValidateSign.doExecute`, where `sigArraySize`/`addrArraySize` are only validated inside the `allowTvmSelfdestructRestriction()` branch before calling `extractBytesArray`/`extractBytes32Array`: [3](#0-2) 

Both precompiles are reachable from any smart contract via `CALL`/`STATICCALL`/`DELEGATECALL` to the fixed precompile address, dispatched from `Program.callToPrecompiledAddress`: [4](#0-3) 

Energy cost for these calls is computed from `data.length / WORD_SIZE`, not from the value encoded in the declared count word, so a caller can submit a small calldata buffer that nonetheless encodes a huge count value (up to whatever `DataWord.intValueSafe()` returns, close to `Integer.MAX_VALUE`) at negligible energy cost, triggering allocation of an array with billions of `byte[]` reference slots before any bound is checked.

### Impact Explanation
Successful triggering of `new byte[len][]` with an attacker-chosen huge `len` throws `OutOfMemoryError` or otherwise forces a very large heap allocation inside the TVM execution path. Unlike normal exceptions in `execute()`, an `OutOfMemoryError` is unchecked and can propagate outside the caught `Throwable t` guard in `BatchValidateSign.execute` in some JVM states (heap exhaustion can also affect unrelated threads/GC first), risking node process abort or denial of orchestration/consensus service for the whole node — matching the "node crash" impact category.

### Likelihood Explanation
This is reachable by any account able to broadcast a `TriggerSmartContract` transaction (no special permission needed) or by any deployed contract calling the fixed precompile addresses for `ValidateMultiSign`/`BatchValidateSign`. Exploitability is contingent on `VMConfig.allowTvmSelfdestructRestriction()` being disabled for the chain/fork in question; when this hard-fork flag is active the size checks are correctly applied before allocation. This makes the bug's real-world reachability dependent on network configuration/chain parameters that I could not fully verify are always enabled on all java-tron deployments (mainnet vs. private/test networks vs. pre-activation windows).

### Recommendation
Move the `MAX_SIZE`/`sigArraySize`/`addrArraySize` bound checks so they are unconditionally applied before calling `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, regardless of `VMConfig.allowTvmSelfdestructRestriction()`. Additionally, add an explicit sanity bound inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves (e.g., reject `len < 0` or `len > MAX_SIZE`) so the length is validated at the point of allocation rather than relying on call-site discipline.

### Proof of Concept
1. Deploy or use any contract that issues a low-level `CALL` to the `ValidateMultiSign` precompile address with calldata sized to only a few ABI words (small `data.length`, hence negligible `getEnergyForData`).
2. Encode the word at the offset pointed to by `words[3]` (the "signatures array" slot) with a value close to `Integer.MAX_VALUE` for its length field, while leaving the "real" payload minimal.
3. On a network where `VMConfig.allowTvmSelfdestructRestriction()` is not activated, `ValidateMultiSign.execute` skips the `sigArraySize > MAX_SIZE` guard and calls `extractBytesArray(words, offset, rawData)` directly, which executes `byte[][] bytesArray = new byte[len][]` with `len` near `Integer.MAX_VALUE`.
4. This large array allocation exhausts/spikes heap memory and can trigger `OutOfMemoryError`, potentially aborting the node process — reproducing the Ankaios-style "unbounded allocation from a declared length" crash within the TVM execution path.

Note: I was unable to directly confirm within the indexed context whether `allowTvmSelfdestructRestriction()` is enabled by default on current java-tron mainnet parameters (the hard-fork activation state lives in `DynamicPropertiesStore`/chain parameters not fully retrievable here), which affects whether this is exploitable today versus only on older/un-upgraded nodes.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
