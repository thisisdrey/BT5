## Finding: Floating-point precision drain in TRON's on-chain TRC10 Bancor-style Exchange pricing (legacy, default-enabled path)

### Summary
The Levana incident stemmed from an attacker manipulating the price-determination mechanism a DeFi protocol relies on to systematically drain liquidity from a pool over many transactions. Java-tron ships its own on-chain AMM ("Exchange" TRC10 <-> TRX/TRC10 bancor-relay market) whose price/quantity calculation is reachable by any account via a signed `ExchangeTransactionContract`. The legacy (default) calculation path in `ExchangeProcessor` uses `double`/`Math.pow` floating-point arithmetic rather than exact fixed-point math, and this is the code path used unless the network has separately activated a committee-gated hardening proposal.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, which selects between two `Processor` implementations based on `allowHardenExchangeCalculation()`: [1](#0-0) 

`allowHarden()` simply reads a dynamic-store flag driven by a committee proposal parameter (`ALLOW_HARDEN_EXCHANGE_CALCULATION`), meaning the safe, precision-exact `SafeExchangeProcessor` (BigDecimal-based) is only used when that proposal has been passed: [2](#0-1) 

Absent that governance action, every `ExchangeTransactionContract` is priced through `ExchangeProcessor`, which computes the bancor "relay" value and the resulting output quantity using `double` arithmetic and `Math.pow`: [3](#0-2) 

This is directly analogous, in bug class, to the Levana incident: both cases involve an unprivileged caller exploiting the exact math used to determine exchange output/price in an on-chain liquidity pool. Floating-point `pow`/division introduces small, direction-dependent rounding at every trade. Because `ExchangeTransactionActuator` is callable by any account holding the relevant TRX/TRC10 balance, with only a caller-supplied minimum-received guard (`tokenExpected`) and no protocol-level check that the pool's *value* is non-decreasing: [4](#0-3) 

an attacker can programmatically issue a long sequence of small trades (in both directions across an Exchange pool) engineered so that rounding in `exchangeToSupply`/`exchangeFromSupply` systematically favors the trader over the pool on each round-trip, extracting value from `firstTokenBalance`/`secondTokenBalance` reserves stored in the `ExchangeCapsule`, in the same way the Levana attacker drained ~10% of pool liquidity through many small, price-mechanism-exploiting operations over an extended window (Dec 13–26).

### Impact Explanation
Successful exploitation directly drains real, backed value (TRX and/or TRC10 assets) from an Exchange pool's reserves, at the expense of the pool creator/other liquidity holders who rely on `ExchangeCapsule.getFirstTokenBalance()`/`getSecondTokenBalance()` for future settlement (injects/withdrawals/other trades). This is a concrete unauthorized theft of pooled funds, matching the "unbacked balance / theft of funds" impact bar.

### Likelihood Explanation
The `ExchangeTransactionActuator` path is reachable by any address that owns TRX or the relevant TRC10 asset — no special privilege, SR status, or witness role is required, and the actuator performs no rate-limiting or manipulation-detection across a sequence of trades. The only real precondition is that the network has not activated `allowHardenExchangeCalculation` (an opt-in committee proposal, not confirmed here to be default-on in this codebase), so exploitability depends on current chain governance state, which could not be verified from static code alone.

### Recommendation
- Make the `SafeExchangeProcessor` (BigDecimal, exact-rounding) path the unconditional default for `ExchangeCapsule.transaction`, removing the legacy `ExchangeProcessor` double/`Math.pow` path entirely rather than gating it behind an optional proposal.
- Add an invariant check in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction` that the pool's constant-product/bancor invariant does not decrease (net of fees) after each trade, rejecting any trade that would leave the pool worse off due to rounding.
- Add telemetry/limits on trade frequency or minimum trade size relative to pool depth to blunt precision-grinding strategies.

### Proof of Concept
Conceptual sequence (cannot be executed without live chain state/governance flags):
1. Attacker creates or locates an `Exchange` with modest reserves (`firstTokenBalance`, `secondTokenBalance`).
2. Attacker repeatedly submits `ExchangeTransactionContract` transactions alternating buy/sell direction with `tokenQuant` sized to maximize the `Math.pow` rounding error captured on each leg in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`.
3. Over many blocks, the accumulated rounding bias transfers reserve value from the pool into the attacker's account balance, mirroring the "10% liquidity drained over 13 days" pattern described in the Levana report.

**Caveat:** I could not conclusively verify from the indexed code alone whether `allowHardenExchangeCalculation` is default-on in the live/mainnet configuration (only that it's a governance-controlled dynamic property), so likelihood is conditional on that governance state — flagging this as the main open uncertainty in this analysis.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);

  }
