### Title
Stale `PostponedReceipt`/`ReceivedData` state surviving `action_delete_account` allows authorization escalation on account-name reuse - (File: runtime/runtime/src/actions.rs, core/store/src/utils/mod.rs)

### Summary
`action_delete_account` calls `remove_account`, which only removes the `Account`, `ContractCode`, access keys/gas-key nonces, and contract data trie entries for the deleted account. It never removes `TrieKey::PostponedReceipt`, `TrieKey::ReceivedData`, or the associated pending-data-count/index keys keyed on that `receiver_id`. This lets a still-pending, previously self-authorized `ActionReceipt` (e.g. containing `AddKey`) survive account deletion and later execute against whatever account is subsequently created under the same `account_id`.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) performs storage-usage/gas-key checks, refunds the balance, and then calls `remove_account(state_update, account_id)` at line 371 before setting `*account = None`.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) only:
- removes `TrieKey::Account`
- removes `TrieKey::ContractCode`
- iterates and removes `AccessKey`/gas-key-nonce entries under the account's access-key prefix
- iterates and removes `TrieKey::ContractData` entries

It does **not** touch `TrieKey::PostponedReceipt { receiver_id, receipt_id }` (set via `set_postponed_receipt`, `core/store/src/utils/mod.rs:120-127`), nor `TrieKey::ReceivedData { receiver_id, data_id }` entries, nor any pending-data-count bookkeeping tied to that `receiver_id`. These keys are all namespaced by `receiver_id = account_id`, so they remain in the trie under `x.near`'s key-space even after the `Account` record itself is deleted.

Exploit flow:
1. Attacker deploys a contract on `x.near` and issues a cross-contract call that creates a self-targeted `ActionReceipt` on `x.near` containing `AddKey(attacker_pubkey)`, with an `input_data_ids` dependency that is not yet satisfied. The runtime persists this as a `PostponedReceipt` keyed by `(receiver_id = x.near, receipt_id)` because not all required `DataReceipt`s have arrived yet.
2. In the same or a later block, the attacker submits a transaction with `DeleteAccount { beneficiary_id }` for `x.near`. `action_delete_account` succeeds, `remove_account` deletes the `Account`/keys/contract data, but the `PostponedReceipt` and any associated `ReceivedData`/pending-count entries for `x.near` are left untouched in state.
3. The account name `x.near` is later recreated (e.g., a subsequent owner registers/recreates the account, or a marketplace/registrar flow re-issues the name) — a scenario outside the attacker's direct control but not prevented at the protocol level, since `CreateAccount` does not check for or purge dangling postponed-receipt state under the new account.
4. The attacker (who still controls the helper account supplying the missing input data) triggers delivery of the awaited `DataReceipt`. Runtime matching logic looks up pending data solely by `(receiver_id, data_id)`, finds the stale link, decrements the pending count, and once satisfied, loads and executes the stale `PostponedReceipt` — now against the new account occupying `x.near`. The postponed `AddKey(attacker_pubkey)` action is applied to the new account's state.

This breaks authorization exactness: the `AddKey` action was authorized only in the context of the receipt's original predecessor/receiver relationship, not against the identity of whatever unrelated account subsequently reuses the same `AccountId`. No component in this path re-validates that the account that receives the postponed receipt is the same account that existed when the receipt was postponed — `action_delete_account`'s cleanup is incomplete and none of the create-account or receipt-matching logic performs a defensive purge keyed on the fact that the account identity changed.

### Impact Explanation
If reachable, this is an authorization/state-consistency violation: an attacker can plant a privileged action (`AddKey`, or in principle other postponed actions) that executes later against a completely different account owner than the one who authorized it, i.e., account takeover of the recreated account without its owner's consent — matching NEAR's "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
The core code-level gap is confirmed: `remove_account` (`core/store/src/utils/mod.rs:505-575`) definitively does not clean up `PostponedReceipt`/`ReceivedData`/pending-data trie keys tied to the deleted `receiver_id`, and `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) does nothing to compensate for this. However, I was not able to fully trace and confirm within the available context (a) the exact current TrieKey layout used for pending-data bookkeeping in this repository version (`TrieKey::PendingDataCount`/`PostponedReceiptId` were referenced by name in the prompt but I could only directly confirm `PostponedReceipt` and `ReceivedData` handling via `core/store/src/utils/mod.rs`), and (b) whether `apply_action_receipt`/receipt-matching in `runtime/runtime/src/lib.rs` performs any additional identity/liveness check before executing a postponed receipt that would block this specific escalation. Practical exploitability also depends on an external, non-protocol precondition — that the same `AccountId` can be legitimately recreated by a different, unrelated party after deletion (true for sub-accounts under a different parent chain of control, and historically relevant for top-level name reuse/marketplaces) — which is plausible but not something the runtime code itself controls.

### Recommendation
In `action_delete_account`/`remove_account`, purge all `receiver_id`-scoped queue state before finalizing account deletion: iterate and remove `TrieKey::PostponedReceipt`, `TrieKey::ReceivedData`, and any pending-data-count/index entries keyed on `account_id` as `receiver_id`, mirroring the existing access-key and contract-data cleanup loops in `core/store/src/utils/mod.rs:505-575`. Alternatively/additionally, when applying a `CreateAccount` action, defensively clear any residual postponed-receipt/received-data state under the newly created `account_id` before allowing execution to proceed, so no dangling cross-shard state from a prior account incarnation can ever be attributed to the new owner.

### Proof of Concept
Runtime/apply-path integration test (test-loop or `runtime/runtime/src/tests`):
1. Create account `x.near` with a deployed contract capable of issuing a self-directed `FunctionCall` receipt to itself with an unmet `input_data_id` (so it gets stored as a `PostponedReceipt`) whose actions include `AddKey(attacker_pubkey)`.
2. Assert via `get_postponed_receipt(trie, "x.near", receipt_id)` that the postponed receipt is stored.
3. Submit `DeleteAccount { beneficiary_id }` for `x.near` from the attacker signer; assert the account no longer exists (`get_account` returns `None`) while `get_postponed_receipt` still returns `Some(receipt)` for the same key — proving the cleanup gap.
4. Recreate `x.near` via a `CreateAccount` action from a different signer/account (simulating the victim), and assert no `AddKey` for `attacker_pubkey` exists yet under the new account.
5. Deliver the missing `DataReceipt` for the original `input_data_id`, driving receipt matching/`apply_action_receipt` to fetch and execute the stale `PostponedReceipt`.
6. Assert failure expectation: the test should currently show `attacker_pubkey` added to the *new* `x.near` account's access keys (`get_access_key(trie, "x.near", attacker_pubkey)` returns `Some(..)`) despite the new owner never authorizing it — demonstrating the takeover. A fixed implementation should instead show the postponed receipt was purged at step 3 (or ignored due to missing account context), and the access key is never added.
