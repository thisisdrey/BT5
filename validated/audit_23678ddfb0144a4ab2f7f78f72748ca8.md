### Title
Postponed action receipts survive `DeleteAccount` and execute stale attacker actions (e.g. `AddKey` FullAccess) against a later-recreated account of the same name - ([File: runtime/runtime/src/lib.rs] / [File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (used by `action_delete_account`) removes the `Account`, `ContractCode`, access/gas keys, and contract data trie entries, but never touches the `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` trie keys that are indexed purely by `receiver_id` (an `AccountId` string). A postponed self-receipt crafted by the attacker's own contract before deletion therefore survives account deletion and is later matched and executed by `process_receipt`/`process_action_receipt` against whatever account currently exists under that name, with no re-validation tying the receipt to the specific account instance that created it.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an action receipt whose `input_data_ids` are not yet all in state as a `PostponedReceipt`, plus `PendingDataCount` and `PostponedReceiptId` entries keyed by `receiver_id` (`lib.rs:1608-1654`). These bookkeeping keys are only consulted by `process_receipt`'s `Data` branch (`lib.rs:1385-1474`), which looks them up strictly by `(receiver_id, data_id)` and, once the count reaches zero, fetches and executes the stored `Receipt` via `apply_action_receipt` — with no check that the account it will run against is the same account instance that existed when the receipt was postponed.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) — invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) — removes `TrieKey::Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`, but does **not** remove `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, or `ReceivedData` entries for that account. Thus a postponed action receipt whose `receiver_id` equals the deleted account remains fully intact in state after `DeleteAccount` executes.

The attacker crafts a *self*-receipt: `receiver_id == predecessor_id == account_id` (an ordinary contract-to-self promise batch), containing an `AddKeyAction` granting `FullAccess` to an attacker-controlled public key, with two `input_data_ids` from slower cross-contract calls the attacker also controls. `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-760`) gates `AddKey` solely on `actor_id == account_id`, a pure `AccountId` string comparison; `actor_id` is initialized from `receipt.predecessor_id()` (`lib.rs:855`) and is unaffected by whether the account was deleted/recreated in the interim — it was already baked into the receipt at creation time. Consequently, once the account is deleted and later recreated (e.g., a third party re-registers the now-available account name via `CreateAccount`), the still-pending `DataReceipt`s eventually arrive, the stale postponed receipt is dequeued and its `AddKeyAction` executes against the *new* account, passing the self-check trivially because `receiver_id`/`predecessor_id` in the frozen receipt still textually equal the reused `account_id` — even though the new account's owner never authorized or signed anything.

### Impact Explanation
Authorization escalation across accounts: an attacker plants a durable `FullAccess` key on any account subsequently created under a name the attacker previously controlled and deleted, without any action or signature from the new legitimate owner. This matches the "authorization escalation across promises/accounts" bounty category.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's reach: control of a contract deployed on the account they intend to delete, ability to schedule two asynchronous cross-contract calls with predictable multi-block completion timing to keep the action receipt postponed, and a subsequent self-signed `DeleteAccountAction` transaction on that same account (`actor_id == account_id` also holds trivially for delete). The remaining step — someone else recreating an account under the freed name — is realistic for top-level account names freed after deletion (re-registered through normal account-creation flows) and costs the attacker only ordinary gas/storage fees. The race is deterministic given the attacker fully controls the timing of both the postponement and the deletion.

### Recommendation
When an account is deleted, purge all postponed-receipt-related state indexed by that `receiver_id`: iterate and remove `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, and `ReceivedData` trie entries for the account in `remove_account` (or in `action_delete_account`) before returning success, mirroring the existing cleanup done for access keys and contract data. Alternatively/additionally, bind postponed receipts to an account "generation" (e.g., a counter incremented on every `CreateAccount`) and have `apply_action_receipt` refuse to execute a postponed receipt whose captured generation does not match the account's current generation.

### Proof of Concept
Runtime/test-loop integration test:
1. Deploy a contract to `account0` and have `account0` call itself via a batch promise with `input_data_ids` from two `FunctionCall`s to helper contracts (`account1`, `account2`) that are configured to return data only after several blocks (e.g. by looping/burning gas or via a delayed cross-shard call), plus an `AddKeyAction(FullAccess, attacker_pubkey)` action targeting `account0` itself, ensuring the receipt gets postponed (`process_action_receipt`).
2. In the next block, submit a `DeleteAccountAction` transaction signed by `account0`'s own key, beneficiary `account1`. Assert the account is gone (`QueryError::UnknownAccount`).
3. Have a different signer submit a `CreateAccount`+`Transfer`+`AddKey(own_key)` batch to recreate `account0` (or, for the top-level-name variant, register it fresh through normal account creation).
4. Allow the two delayed `DataReceipt`s to land in subsequent blocks.
5. Assert that `account0`'s access-key list now contains the attacker's `FullAccess` public key even though the new owner never authorized it — proving the postponed receipt executed against the recreated account.
