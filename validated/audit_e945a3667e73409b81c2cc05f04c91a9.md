## Finding

<br>

### Title
Relayer rewards are settled and cleared on `pay_reward` **delivery**, not on remote **execution**, causing permanent, unrecoverable loss of reward funds - ([File: bridges/modules/relayers/src/lib.rs])

### Summary
The Amphora bug's core invariant break is: **the protocol permanently advances/clears internal accounting state based on the assumption that an external, asynchronous action succeeded, when in fact only the "initiation" of that action was verified** (Convex `deposit` reverting silently changes external pool state; the vault's `isTokenStaked` flag was never re-synchronized, and no update path exists to recover). The same broken invariant exists in `pallet-bridge-relayers`' reward-claim flow: the pallet deletes the relayer's registered reward and emits `RewardPaid` as soon as the XCM `deliver()` call succeeds — i.e. as soon as the message is *handed off* to the router — without any guarantee that the reward-minting instructions actually execute successfully on the remote chain (AssetHub).

### Finding Description
`do_claim_rewards` in [1](#0-0)  does the following inside a single `try_mutate_exists`:
1. Takes (removes) the stored `reward_balance` from `RelayerRewards`.
2. Calls `T::PaymentProcedure::pay_reward(...)`.
3. If `pay_reward` returns `Ok(())`, it deposits `Event::RewardPaid` and commits — the reward record is now gone forever.

For the Snowbridge reward kind, `PaymentProcedure::pay_reward` is implemented by `BridgeRewardPayer` in [2](#0-1) , which forwards to `PayAccountOnLocation::pay_reward` in [3](#0-2) :

```rust
let xcm: Xcm<()> = alloc::vec![
    UnpaidExecution { weight_limit: Unlimited, check_origin: None },
    DescendOrigin(InboundQueueLocation::get().into()),
    UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
    ReserveAssetDeposited(assets.into()),
    DepositAsset { assets: AllCounted(1).into(), beneficiary },
].into();

let (ticket, fee) = validate_send::<XcmSender>(AssetHubLocation::get(), xcm)...;
XcmExecutor::charge_fees(relayer.clone(), fee)...;
XcmSender::deliver(ticket)...;
Ok(())
```

`pay_reward` returns `Ok(())` as soon as `XcmSender::deliver` succeeds — i.e. once the XCM message is *enqueued for the destination* (this is confirmed by the module's own unit tests, `pay_reward_success` and `pay_reward_fails_on_delivery`, which only assert success/failure of `validate`/`deliver`, never of remote execution). XCM `send`/`deliver` is inherently a one-way, fire-and-forget primitive: there is no callback or receipt that reports back whether `ReserveAssetDeposited`/`DepositAsset` actually succeeded on AssetHub. If that execution fails remotely — e.g. because the supplied `beneficiary` `Location` (arbitrary, attacker-supplied via `claim_rewards_to`'s `VersionedLocation` beneficiary, see [4](#0-3) ) is malformed, points to a filtered/non-existent account, or AssetHub's barrier/trust configuration rejects the reserve deposit — the funds are trapped (`AssetsTrapped`) or simply never minted, with no automatic recovery mechanism.

By the time that remote failure could even be detected, `RelayerRewards` has already been cleared and `RewardPaid` has already been emitted on BridgeHub — the exact same "guard doesn't stop the path" pattern as the Amphora bug, where `isTokenStaked` was left stale and `updateRegisteredErc20` had no way to reflect the external Convex shutdown.

### Impact Explanation
A relayer's earned reward can be **permanently and irrecoverably lost** with no on-chain path to reclaim it — this is a "permanent user-fund lock" per the impact gate. Because settlement (clearing the ledger entry) is decoupled from confirmation of remote execution, the protocol's reward accounting can silently diverge from actual asset custody, matching the required-impact category of "duplicate settlement or payout" / "message queues... and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here settlement advances before execution succeeds.

### Likelihood Explanation
No governance, admin, relayer-maliciousness, or validator collusion is required. Any legitimate relayer calling the permissionless `claim_rewards_to` extrinsic with a beneficiary location that AssetHub cannot successfully process (a routine configuration/version mismatch, filtered account, or malformed junction — external factors exactly analogous to Convex "pool shutdown") triggers the loss. The existing test suite's own comment — *"In unit tests without proper HRMP channel setup, the claim will fail at XCM sending"* ( [5](#0-4) ) — only covers the delivery-failure case, never the far more likely remote-execution-failure case, confirming this path is untested and unguarded.

### Recommendation
Do not treat `XcmSender::deliver()` success as final settlement. Either:
1. Keep the reward entry pending until a delivery/execution confirmation (e.g., via `SetTopic`/report-back XCM instructions or the existing bridge delivery-receipt mechanism) is received, only then clearing `RelayerRewards`, or
2. Provide a permissionless recovery/retry path (analogous to the Amphora fix's `updateRegisteredErc20` recovery hook) that lets a relayer reclaim/resubmit a reward if remote execution is later proven to have failed, instead of unconditionally deleting the ledger entry on mere delivery success.

### Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(some_location))` where `some_location` is a syntactically valid `VersionedLocation` that AssetHub's XCM executor will reject at the `DepositAsset`/`ReserveAssetDeposited` stage (e.g., an account/junction combination not recognized, or reserve-trust misconfigured for the `GlobalConsensus(Ethereum)` origin from BridgeHub's perspective at that time).
3. On BridgeHub: `validate_send` and `XcmSender::deliver` both succeed (message is merely enqueued into the outbound XCM channel) → `pay_reward` returns `Ok(())` → `do_claim_rewards` removes the `RelayerRewards` entry and emits `RewardPaid`.
4. On AssetHub: the XCM message executes and fails at `ReserveAssetDeposited`/`DepositAsset`; the asset is trapped or never created.
5. Relayer has no reward balance left in `RelayerRewards` (already cleared in step 3) and never receives the minted asset on AssetHub — the reward is permanently lost with no path to reclaim it on-chain.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)
		}

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
