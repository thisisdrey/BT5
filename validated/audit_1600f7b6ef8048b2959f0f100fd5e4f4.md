### Title
Dust `DepositToken` transfers permanently occupy a borrower's collateral slots and can block all new collateral deposits - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken._transfer` registers the recipient in `Pool`'s per-account deposit-token list whenever they receive a token for the first time, and the entry is only freed when that account's balance returns to zero. Because removal is gated on `unlockedBalanceOf` (any outgoing transfer requires unlocked balance), an underwater/fully-locked borrower cannot evict dust balances that an attacker pushed to them. Once the account's combined deposit+debt token count reaches `MAX_TOKENS_PER_USER`, every subsequent `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens`, permanently preventing the victim from depositing any new collateral type — the exact "allocated and never freed" pattern of the referenced memory-leak class, applied to storage-slot/list entries.

### Finding Description
- `DepositToken._transfer` pushes the recipient into `depositTokensOfAccount` on first receipt: `if (_recipientBalanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(recipient_); }` (contracts/DepositToken.sol, `L517-L520`).
- The only deallocation path is `pool.removeFromDepositTokensOfAccount(sender_)` when the *sender's* balance hits zero (`L523-L525`), or via `_burn` (`L459-L462`). There is no self-service removal: `Pool.removeFromDepositTokensOfAccount` is `onlyDepositToken`-gated, so the victim must transfer the dust out.
- `transfer`/`transferFrom`/`withdraw` all call `_revertIfLocked`, which compares against `unlockedBalanceOf` (`L180-L182`, `L348-L354`, `L406-L411`). `unlockedBalanceOf` returns 0 whenever the account has debt and `_issuableInUsd == 0` (`L383-L398`). A victim with a distressed position therefore holds dust they cannot move — the allocation leaks permanently while debt exists.
- `addToDepositTokensOfAccount` counts deposit + debt token list entries and reverts `UserReachedMaxTokens` at the cap (contracts/Pool.sol, `UserReachedMaxTokens` error; cap enforced in the add functions). With the victim's slots filled by attacker-chosen dust, `deposit(..., onBehalfOf_ = victim)` for any *new* collateral token reverts inside `_mint` (`L486-L488`), so nobody can top up the position.

### Impact Explanation
An unprivileged attacker can force a targeted borrower's account into a state where no new collateral can ever be added. If the victim's existing collateral mix is insufficient or declining in value, the position cannot be rescued and will be liquidated — indirect freezing of the victim's funds (they cannot use other assets they hold to avoid liquidation) and forced loss through liquidation fees/price. At minimum this is temporary freezing of funds; for positions that can only be saved by adding a collateral type not already held, it is effectively permanent until the debt is repaid.

### Likelihood Explanation
- Reachability: `transfer(to_, amount_)` is a public, unprivileged entry point; the attacker only needs to hold 1 wei of each `DepositToken` they want to inject (acquired by depositing dust amounts of each underlying, which is open to anyone).
- Constraints: the attacker can only inject tokens that are registered deposit tokens (debt tokens revert on `transfer`, so `debtTokensOfAccount` cannot be spammed). The attack fully blocks the victim only if the number of registered deposit tokens is enough to bring the victim's combined count to `MAX_TOKENS_PER_USER`, and is most damaging when the victim is already near or below healthy collateralization (`_issuableInUsd == 0`) so the dust cannot be removed. Even before the hard cap, each forced entry permanently increases gas cost of `debtPositionOf`/`depositOf`/`debtOf` loops over the account's token lists for every interaction the victim makes.
- No modifier stops it: `nonReentrant`, pause flags, and the health checks do not apply to plain `transfer` of an unlocked balance, and the protocol intentionally permits transferring deposit tokens.

### Recommendation
- Let the victim opt out of or prune list entries: e.g., add a `Pool`/`DepositToken` function that lets an account remove a deposit-token entry (the contract can verify and zero out a residual balance or refund dust to the treasury), or only add recipients to the list above a dust threshold.
- Alternatively, do not count attack-injected balances against `MAX_TOKENS_PER_USER` — e.g., only register on `deposit`/mint paths rather than on `_transfer`, and handle unregistered balances explicitly in `debtPositionOf`.
- Ensure `withdraw`/burn of a dust balance is possible even when the rest of the position is locked (allow outgoing burns regardless of `unlockedBalanceOf`), so leaked entries can always be freed.

### Proof of Concept
Foundry-style sketch (deployed-address fork):

```solidity
// Assume: pool, depositTokenA..N registered; victim has debt with
// pool.debtPositionOf(victim).issuableInUsd == 0 (unlockedBalanceOf == 0).

// 1) Attacker acquires 1 wei of each deposit token (deposit dust of each underlying).
// 2) Inject dust into victim's account list:
for (uint i; i < depositTokens.length; ++i) {
    IDepositToken(depositTokens[i]).transfer(victim, 1);
}
// victim's depositTokensOfAccount length is now len + N

// 3) Repeat until combined deposit+debt entries == pool.MAX_TOKENS_PER_USER().

// 4) Victim (or anyone via deposit onBehalfOf) tries to add a new collateral:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(amount, victim);   // reverts inside _mint -> addToDepositTokensOfAccount

// 5) Victim cannot free the slots:
vm.expectRevert(DepositToken.NotEnoughFreeBalance.selector);
vm.prank(victim);
IDepositToken(depositTokens[0]).transfer(attacker, 1); // unlockedBalanceOf(victim) == 0
```

Uncertainty I could not fully verify within the available context: the exact value of `MAX_TOKENS_PER_USER` and the number of currently registered deposit tokens per deployment, which determine whether the hard cap is reachable in practice. If the registered deposit-token count alone cannot reach the cap, the residual impact is forced gas inflation of the victim's health-check loops rather than an outright deposit block — still a real leak of unfreeable per-account state, but weaker.
