## Title
Unpartitioned global connection-slot exhaustion via slow/incomplete QUIC handshakes bypasses stake-based QoS - ([File: streamer/src/nonblocking/quic.rs])

## Summary
`run_server` reserves a slot in the shared `open_connections` counter via `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` before the peer's identity/stake is known, and only releases it after the handshake completes or times out (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`). Because this counter is a single global pool shared by staked and unstaked peers alike, an unstaked attacker who opens many connections that stall during the handshake can fill this pool and cause `refused_connections_too_many_open_connections` for legitimate staked peers, even though staked/unstaked separation exists later in `try_add_connection`.

## Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-379`), for every accepted `incoming` connection, the server:
1. Applies the overall `TokenBucket` rate limiter and per-IP `ConnectionRateLimiter` [1](#0-0) .
2. If those pass, calls `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, which increments `stats.open_connections` and fails only if the current count already `>= max_concurrent_connections` [2](#0-1) . This check happens **before** `incoming.accept()` is even called, i.e., before any handshake data from the peer has been validated and long before stake/pubkey is known.
3. `setup_connection` then awaits the handshake wrapped in `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` [3](#0-2) , where `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` is a **2-second** local constant [4](#0-3) . Only after this timeout (or success/failure of the handshake) does the `ClientConnectionTracker` drop and decrement the counter.
4. `qos.max_concurrent_connections()` (both `SimpleQos` and `SwQos` implementations) is computed purely from `max_staked_connections * 5/4`, with no separate reservation split between staked/unstaked traffic [5](#0-4) . Stake-aware partitioning (`staked_connection_table` vs. `unstaked_connection_table`, pruning by stake) only happens later inside `try_add_connection`, which runs *after* the tracker slot has already been reserved and the handshake has already completed [6](#0-5) .

An unstaked attacker can hold a tracker slot open for the full 2-second window on many connections simultaneously by initiating the QUIC handshake and then stalling (e.g., sending Initial but not completing Finished, or an unresponsive client). This does not require IP spoofing — the attacker only needs enough real sockets/ports to open connections and let them idle until the handshake timeout fires, then repeat. If the number of concurrently-held slots approaches `max_concurrent_connections()`, subsequent connections (staked or not) get `incoming.refuse()` with `stats.refused_connections_too_many_open_connections` incremented at `streamer/src/nonblocking/quic.rs:371-379`, denying legitimate staked senders a slot to even attempt the handshake.

The existing mitigations (per-IP rate limiter, global `TokenBucket`, `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) reduce, but do not eliminate, this: they bound the *rate* of new connection attempts (`TOTAL_CONNECTIONS_PER_SECOND = 2500`, burst `1000`) and per-IP attempts, but do not partition the `open_connections` capacity itself by stake. Given the 2-second handshake window, a sustained attacker using enough distinct IPs (to avoid per-IP limiting) staying just under the global rate limiter can maintain a steady-state occupancy of stalled connections approaching the `TOTAL_CONNECTIONS_PER_SECOND * QUIC_CONNECTION_HANDSHAKE_TIMEOUT` order of magnitude, which is on the same order as or can exceed `max_concurrent_connections()` depending on configured `max_staked_connections`.

## Impact Explanation
This is a QoS-evasion / denial-of-service style issue: unstaked, unprivileged traffic can consume the shared handshake-slot capacity that is supposed to eventually be partitioned between staked and unstaked connections, causing legitimate staked validators/RPC senders to receive `refused_connections_too_many_open_connections` during the attack window. This maps to the Agave bounty category of QoS evasion / stake-weighted QoS bypass, since the invariant "unstaked resource usage cannot starve staked senders" is violated at the pre-handshake admission stage, even though it is enforced later in `try_add_connection`.

## Likelihood Explanation
Preconditions: attacker needs no stake, only the ability to open many QUIC connections to the leader's public TPU port and let handshakes stall for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) before being torn down/timed out. This is fully within the "unstaked remote client" threat model. Feasibility depends on defeating/avoiding the per-IP (`max_connections_per_ipaddr_per_min`) and global (`TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST`) rate limiters, which requires either many source IPs or careful pacing just under the global token bucket rate; this is a real but nontrivial cost, and is repeatable as long as the attack is sustained.

## Recommendation
Reserve a portion of `max_concurrent_connections()` capacity specifically for unstaked/unauthenticated in-flight handshakes (i.e., partition the pre-handshake slot pool similarly to how `try_add_connection` partitions post-handshake connections between `staked_connection_table` and `unstaked_connection_table`), or shrink `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` further / add a distinct, smaller cap on concurrently in-flight (not-yet-authenticated) handshakes that is separate from the steady-state `max_concurrent_connections()` budget, so a flood of stalled handshakes cannot exhaust capacity needed for legitimate staked connections.

## Proof of Concept
Integration test plan (extending existing test infra in `streamer/src/nonblocking/quic.rs` test module, using `setup_quic_server`/`spawn_stake_weighted_qos_server` helpers already present):
1. Configure `SwQosConfig` (or `SimpleQosConfig`) with a small `max_staked_connections` (e.g., 10), so `max_concurrent_connections() = 10 * 5/4 = 12`.
2. Spawn `N = 12` client `Endpoint`s that call `endpoint.connect(server_addr, "localhost")` but deliberately withhold completion of the handshake (e.g., drop the socket after sending the Initial packet, or use a raw UDP socket to send an Initial without completing Finished) so that `connecting.await` inside `setup_connection` stalls for the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s).
3. Immediately after issuing the flood, attempt a legitimate connection from a keypair with real stake (`make_client_endpoint` + `create_staked_nodes_with_keypairs`), and assert:
   - `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) >= 1`, and/or
   - the staked client's `connect()` future fails/times out during the ~2s window.
4. After `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` elapses and the stalled connections are torn down, assert the staked client can now connect successfully, confirming the window of denial was caused solely by the unpartitioned `open_connections` counter.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
