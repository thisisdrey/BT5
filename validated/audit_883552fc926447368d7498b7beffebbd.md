### Title
Malicious peer's `Attachment` content is accepted without verifying it hashes to the requested `content_hash`, causing wrong BNS attachment instances to be resolved - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts a peer-returned `Attachment` into `self.attachments` purely based on successful HTTP decode, without ever comparing `response.attachment.hash()` to the `request.content_hash` that was actually requested. The `Done` branch of `AttachmentsDownloader::run` then keys `find_all_attachment_instances` off the attacker-controlled `attachment.hash()`, so a peer can serve arbitrary content and have it bound to whatever pending `AttachmentInstance` happens to match that content's own hash (or none, silently dropping the correct one).

### Finding Description
The property that should hold is: for every `AttachmentRequest{content_hash: H, ...}` sent out, the paired response's `Attachment` must satisfy `attachment.hash() == H` before it is trusted and used to resolve `AttachmentInstance` records.

In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`):
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
This code has access to `request` (which carries `request.content_hash`, the hash actually asked for) in the same loop, but it never checks `response.attachment.hash() == request.content_hash`. The `Attachment` is admitted into the `context.attachments: HashSet<Attachment>` purely because the HTTP body decoded successfully.

Then, in `AttachmentsDownloader::run`'s `Done` branch (`stackslib/src/net/atlas/download.rs:153-169`):
```rust
for attachment in context.attachments.drain() {
    let attachments_instances = network
        .atlasdb
        .find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    for attachment_instance in attachments_instances.into_iter() {
        resolved_attachments.push((attachment_instance, attachment.clone()));
    }
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
```
This code uses `attachment.hash()` — a value fully controlled by the attacker's HTTP response body — both to look up which `AttachmentInstance` records to satisfy and to mark the batch's tracked `content_hash` as resolved. There is no re-derivation or cross-check against the `content_hash` that was originally sent out in the `AttachmentRequest`.

Exploit flow: A malicious peer that is selected as a data-URL source (an unprivileged, network-reachable peer that legitimately advertises an attachment inventory bit) receives a `GET /attachments/{H}`-style request for `content_hash = H`. Instead of returning the real content, it returns an arbitrary blob whose hash is `H2`. `decode_atlas_get_attachment()` only decodes the HTTP body into an `Attachment` — it does not enforce `H2 == H`. The forged attachment is inserted into `context.attachments`, then in `run()` it gets bound via `find_all_attachment_instances(&H2)` to whatever `AttachmentInstance`(s) in the atlasdb happen to reference `H2` (which could be a completely different, legitimate pending name-registration/zonefile binding), and `insert_instantiated_attachment` persists the attacker's blob into the atlasdb keyed by `H2`.

### Impact Explanation
This lets a single malicious data-source peer cause the node to (a) persist forged, non-canonical attachment content into its `atlasdb`, and (b) pair that forged content with unrelated `AttachmentInstance` records (e.g., a different, legitimate BNS name's on-chain content-hash commitment), if that instance's expected hash happens to coincide with `H2`. In the common case where `H2` matches no pending instance, the legitimate request for `H` is falsely marked resolved (`context.attachments_batch.resolve_attachment(&attachment.hash())` uses `H2`, not `H`) while the actually-requested `H` instance is left unresolved/dropped from tracking, causing legitimate BNS zonefile content to never be fetched/served even though a well-formed answer could exist. This matches the "attachment/BNS mismatch" High-impact category: content is stored/served that doesn't correspond to what the on-chain instance actually committed to.

### Likelihood Explanation
Precondition: the attacker's node/URL must be one of the `peers` selected via `network.get_outbound_sync_peers()` / advertised via the attachment inventory as holding the requested content — this is reachable by any peer that gossips an attachment inventory bit for the page/index in question, requiring no privileged role or secret. Cost is a single crafted HTTP response per attachment request; the bug is deterministic and repeatable on every subsequent atlas sync round where the attacker is chosen as a source.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`), do not insert, and consider marking the peer unreliable/faulty. This restores the invariant expected by `find_all_attachment_instances` in `AttachmentsDownloader::run`.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
