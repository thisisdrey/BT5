Audit Report

## Title
`ERC20Transactor` credits/debits XCM holding by nominal `amount` instead of measured `balanceOf()` delta, letting fee-on-transfer/rebasing ERC20s desync the shared `TransfersCheckingAccount` and lock user funds - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the target contract's `transfer()` with a nominal `amount` and, on a `true` boolean return, unconditionally credit/debit the XCM holding register with that same nominal `amount` rather than the amount actually moved into/out of the shared `TransfersCheckingAccount`. Because the matcher used in production (`ERC20Matcher` = `IsLocalAccountKey20`) accepts *any* local `AccountKey20` location as a valid ERC20 asset ID with no allowlist, an unprivileged user can register/reference an arbitrary fee-on-transfer or rebasing contract and desync the checking account's real balance from the XCM-tracked balance, eventually causing unrelated deposits to fail and lock funds.

## Finding Description
`withdraw_asset_with_surplus` transfers `amount` to the checking account and, if the ERC20 `transfer()` call returns `true`, credits `AssetsInHolding::new_from_fungible_credit(..., Erc20Credit(amount))` with the full requested `amount`, never checking `balanceOf(TransfersCheckingAccount)` before/after: [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` debits the checking account by transferring `amount` to the beneficiary and treats a `true` return as full success without verifying the beneficiary actually received `amount`: [2](#0-1) 

The matcher wired into production, `ERC20Matcher`, is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, and `IsLocalAccountKey20` matches *any* location of the shape `(0, [AccountKey20 { .. }])` — there is no allowlist or registry restricting which contract addresses are treated as valid ERC20 assets: [3](#0-2) 

This transactor is live in Asset Hub Westend's `AssetTransactors` tuple: [4](#0-3) 

Since any `AccountKey20`-addressed contract is accepted, an unprivileged attacker can deploy a fee-on-transfer/rebasing ERC20 and drive XCM `WithdrawAsset`/`DepositAsset` operations against it through ordinary, permissionless XCM messages, with no governance or registry gate in the way.

## Impact Explanation
This matches "permanent user-fund or bridge-state lock": a fee-on-transfer withdrawal credits the XCM holding register with more than what the shared `TransfersCheckingAccount` actually received, and a later, unrelated deposit for another user of the same asset can then fail when the checking account's real on-chain balance is insufficient to cover the nominal `amount` being paid out, per `deposit_asset_with_surplus`'s `Ok(false)`/revert branches at [5](#0-4) , causing that user's assets to be trapped/lost while the first user's tokens remain stuck in the shared account.

## Likelihood Explanation
Reachability requires only an unprivileged actor deploying a non-standard ERC20 (fee-on-transfer or rebasing) and submitting ordinary XCM `WithdrawAsset`/`DepositAsset` instructions referencing that contract's `AccountKey20` address as the asset ID. Because `IsLocalAccountKey20` imposes no allowlist, this precondition is fully attacker-controlled with no need for governance, a malicious relayer, or key compromise.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf(TransfersCheckingAccount)` (or the destination address) immediately before and after the `transfer()` call and use the measured delta — not the requested `amount` — for both the value credited/debited in `AssetsInHolding` and for success validation, failing atomically if the delta is less than requested so the checking account's tracked balance never diverges from its real on-chain balance.

## Proof of Concept
1. Deploy an ERC20 contract via `pallet-revive` whose `transfer(to, amount)` moves only `amount * 99 / 100` to `to` (fee-on-transfer) while returning `true`.
2. Submit an XCM `WithdrawAsset` for `amount = 1000` of this token referencing the contract's `AccountKey20` location; `withdraw_asset_with_surplus` transfers `1000` nominally but only `990` lands in `TransfersCheckingAccount`, yet credits `Erc20Credit(1000)` into holding.
3. A second, unrelated user submits an XCM `DepositAsset` for `1000` of the same token; `deposit_asset_with_surplus` attempts `transfer(beneficiary, 1000)` from `TransfersCheckingAccount`, which fails/reverts once the shortfall accumulates, causing `XcmError::FailedToTransactAsset` and trapping/losing that user's assets.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
