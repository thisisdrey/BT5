### Title
Arbitrary local-file disclosure via `git_repository`/`new_git_repository` submodule fetch forcing `protocol.file.allow=always` - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
When a Bazel `git_repository` or `new_git_repository` invocation sets `init_submodules` or `recursive_init_submodules` to true, Bazel unconditionally re-enables Git's `file://` submodule protocol via `-c protocol.file.allow=always` before running `git submodule update --init [--recursive] --checkout --force`. A malicious remote repository (the attacker-controlled `remote` URL content, analogous to the "maliciously crafted URL" in the OpenTofu/go-getter advisory) can ship a `.gitmodules` file whose submodule `url` points to an arbitrary local filesystem path on the machine performing the build (e.g. another already-cloned external repository, a shared cache directory, or any other local git repository reachable by path). Because the file protocol is force-enabled, `git` will happily "clone" from that local path into the submodule directory of the newly created external repository, pulling its full contents (history, working tree, any file readable by the build user) into a location that the attacker's own (equally malicious) `BUILD`/`build_file_content` can then expose as ordinary build outputs.

### Finding Description
`update_submodules` in `tools/build_defs/repo/git_worker.bzl` explicitly overrides Git's security default that disables the `file` transport for submodules (a protection Git added specifically to stop this class of local-path submodule attacks): [1](#0-0) 

This happens after the top-level repository has been fetched, reset, and cleaned from the attacker-controlled `remote`: [2](#0-1) 

The `remote` value and all git invocations for the submodule step run with the operator's Bazel-invoking user's filesystem access and environment, inside `_execute`: [3](#0-2) 

No validation is performed on submodule URLs recorded in `.gitmodules` — that file is part of the untrusted content fetched from `remote`. Nothing in `git.bzl` constrains `init_submodules`/`recursive_init_submodules` fetch targets to remote/network sources or to paths inside the checkout: [4](#0-3) 

Because `protocol.file.allow=always` is passed unconditionally whenever submodules are initialized, the standard Git mitigation for "malicious submodule clones from arbitrary local paths" (which normally blocks the `file://` transport for submodules by default) is disabled for every `git_repository`/`new_git_repository` invocation that uses submodules, regardless of whether the top-level `remote` is trusted.

### Impact Explanation
An attacker who controls the content of a git repository referenced by a `git_repository`/`new_git_repository` rule (a normal untrusted dependency scenario — the operator supplies `remote`, but the attacker controls everything the server returns, including `.gitmodules` and submodule commits) can cause Bazel to read and materialize the contents of an arbitrary local path on the build machine into the external repository's checkout. If the attacker can guess or predict a path likely to exist on build machines (e.g., other Bazel external repo checkouts under the same output base, shared caches, or repos checked out by CI), the resulting submodule contents — potentially including file contents not otherwise intended to be exposed — become part of the malicious repository's file tree, from which the malicious `build_file`/`build_file_content` (also attacker-supplied) can copy them into ordinary build outputs, disclosing them to the operator/build log/artifacts. This mirrors the "possible arbitrary file read... via a maliciously crafted URL" impact in the referenced advisory: confidentiality impact with no attacker access to the victim machine beyond serving git content.

### Likelihood Explanation
Requires the operator to use `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` against an untrusted or compromised remote — a realistic and documented pattern (both attributes are public, supported rule attributes). No credentials, sandbox escape, or victim machine access beyond normal dependency fetch is needed; only the ability to publish/control the git content at `remote`.

### Recommendation
Do not force `protocol.file.allow=always` unconditionally for submodule updates. If the workaround for Git 2.38.1's blanket file-protocol restriction is still required for legitimate use cases (e.g., local-directory `remote`), scope the override narrowly — for example, only when the top-level `remote` itself is a local `file://`/path remote — and otherwise let Git's default submodule protocol restrictions apply so that submodule URLs pointing at arbitrary local paths are rejected. At minimum, validate/sanitize submodule URLs recorded in `.gitmodules` before allowing local-path clones, and document/gate this behavior behind an explicit user-set attribute rather than enabling it silently for every submodule fetch.

### Proof of Concept
1. Attacker publishes (or compromises) a git repository `evil.git` that is used as the `remote` of a `git_repository`/`new_git_repository` rule with `recursive_init_submodules = True`.
2. Inside `evil.git`, commit a `.gitmodules` entry:
   ```
   [submodule "leak"]
     path = leak
     url = file:///home/victim/.cache/bazel/_bazel_victim/<hash>/external/some_other_repo
   ```
   (or any other local path reachable on the build machine, e.g. another checked-out external repository).
3. Add a `build_file_content` in the malicious repo that declares a `filegroup`/`genrule` exposing files under `leak/`.
4. When the operator runs `bazel build //...`, `git_repo()` clones `evil.git`, then `update_submodules()` runs:
   `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force`
   which clones from the local `file://` path (bypassing Git's default block on file-protocol submodules) and materializes its contents under `leak/` inside the external repository.
5. A build target depending on `@evil//:leak_files` now copies the disclosed local content into a build output, which can be inspected by the attacker via any channel the operator uses to share/publish build artifacts, or simply confirmed by a `BuildIntegrationTestCase`/`src/test/shell/bazel/starlark_git_repository_test.sh`-style test asserting the submodule directory contains files from the local target path rather than a legitimate remote submodule.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
