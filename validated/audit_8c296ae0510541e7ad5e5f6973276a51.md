### Title
DNS TXT/cert-disclosure gate relies on spoofable UDP source address instead of cryptographic authentication - ([File: dns_server.go])

### Summary
`dnsServer.isSelfNebulaOrLocalhost` gates certificate/TXT disclosure purely on the string form of `w.RemoteAddr()` from a plain `dns.Server` bound with `Net: "udp"`. Because UDP is connectionless, the "remote address" reported to the handler is taken directly from the source-IP field of the received datagram's IP header with no cryptographic handshake, so any attacker who can get a spoofed-source UDP packet delivered to the listening socket satisfies the check without ever participating in a Noise handshake or holding a certificate.

### Finding Description
The call chain is: `dns.Server.ListenAndServe()` (UDP) -> `handleDnsRequest` (dns_server.go:438) -> `parseQuery` (dns_server.go:391) -> for `dns.TypeTXT` queries, `isSelfNebulaOrLocalhost(w.RemoteAddr().String())` (dns_server.go:417). `isSelfNebulaOrLocalhost` (dns_server.go:372-389) parses the host portion of that address and returns true if it is loopback or contained in `cs.myVpnAddrsTable`. If true, `QueryCert` (dns_server.go:252-290) is invoked and returns the full PEM/JSON-marshaled certificate of the queried peer or of the lighthouse itself, which is written back into the DNS response.

The security property the comment at dns_server.go:416 ("We only answer these queries from nebula nodes or localhost") assumes is that the source address on the packet corresponds to traffic that has already passed through nebula's cryptographic/firewall pipeline (i.e., only reachable via the tun device after a successful Noise handshake). But this DNS listener is a bare `net.PacketConn`-based UDP socket (`dns.Server{Net: "udp"}`), not something wired into nebula's Noise/firewall pipeline. For a UDP socket, the source address handed to the application on each received datagram is whatever was in the IP header of the packet as delivered by the kernel — there is no three-way handshake or return-routability check as there would be for TCP. Consequently, if the DNS listener's bind address (`lighthouse.dns.host`/`lighthouse.dns.port`, see `getDnsServerAddr`, dns_server.go:451-458) is reachable from a network path where an attacker can inject packets with a forged source IP (e.g., no BCP38/ingress filtering, an off-path spoofer, or an on-link attacker on the same broadcast domain as the lighthouse), the attacker can craft a UDP datagram with source IP set to a loopback address or to an address contained in `myVpnAddrsTable`, and `isSelfNebulaOrLocalhost` will return `true` with no proof of possession of any nebula credential, key, or completed handshake.

This differs materially from the rest of nebula's design, where all overlay traffic is required to pass Noise handshake authentication and per-packet AEAD verification before reaching application logic (see the handshake/hostmap packet-processing path). The DNS listener sits entirely outside that pipeline and substitutes IP-string comparison for cryptographic authentication, which is not equivalent — UDP source addresses are trivially forgeable at the network layer independent of any nebula-specific cryptographic guarantee.

### Impact Explanation
If exploitable given the network path preconditions, an unauthenticated attacker can retrieve the lighthouse's own certificate or any peer certificate present in the lighthouse's hostmap via a single forged UDP TXT query, without any Noise handshake or valid nebula identity. This maps to a Nebula bounty "information disclosure" impact: certificate contents (subject name, fingerprint, VPN addresses, groups, validity) are disclosed to an unauthenticated party, which the finding correctly notes can help an attacker craft packets/certs that are more likely to pass firewall group/CIDR checks (i.e., reconnaissance that lowers the cost of a subsequent, separately-gated attack). It is not itself a decryption/replay/authentication bypass of the overlay tunnel — the impact is limited to disclosure of certificate material that is not secret by design in nebula's threat model (certificates are routinely exchanged during handshakes and are not confidential), which limits severity somewhat, but the check is clearly intended to restrict *who* can query, and that restriction is bypassable.

### Likelihood Explanation
Preconditions: `lighthouse.serve_dns` and `lighthouse.am_lighthouse` must both be true (dns_server.go:94-96), and the DNS UDP port must be reachable by the attacker on a network path that permits spoofed source addresses to be delivered to the socket. This is a real-world-common but non-universal precondition — most cloud/hosting networks perform egress filtering that blocks off-path IP spoofing (BCP38), so the practical feasibility depends heavily on deployment network hygiene and whether the lighthouse operator bound `lighthouse.dns.host` to an interface reachable from a spoofing-permissive network segment (e.g., same LAN, or a provider without anti-spoofing). Where those network conditions hold, the exploit is trivially repeatable with a single crafted UDP packet and requires no interaction with nebula's crypto stack at all.

### Recommendation
Do not use the peer-supplied UDP source address as an authentication signal for privileged DNS responses. Options:
- Bind the DNS listener strictly to the nebula tun interface's own address (and verify at startup that `lighthouse.dns.host` resolves to a tun-owned address rather than any routable interface), so that only traffic that has already traversed nebula's decrypt/authenticate/firewall path in the kernel routing table can reach the socket, and document/enforce this as a hard requirement rather than best-effort convention.
- Alternatively, remove the IP-based trust check entirely for TXT/cert responses and require the query to be authenticated by other means (e.g., serve QueryCert data only over control-plane channels within nebula, not over a plain UDP DNS responder), or drop TXT/QueryCert support unless the request can be proven to originate from an already-handshaked peer (e.g., cross-check against `hostMap` reachability plus a nonce/challenge, not just source-IP string equality).
- At minimum, add explicit operator guidance/config validation warning when `lighthouse.dns.host` is bound to a non-tun, externally-reachable address, since the current code silently trusts spoofable UDP source addresses.

### Proof of Concept
Integration test (Go, using `dnsServer` directly, simulating what an attacker-controlled UDP source would produce):
1. Construct a `dnsServer` with `pki` set to a `PKI`/`CertState` whose `myVpnAddrsTable` contains `10.0.0.9/32` (a "victim" VPN address), and with `hostMap` containing a handshaked peer's cert.
2. Do not perform any Noise handshake or send any packet through the tun/firewall path.
3. Call `ds.isSelfNebulaOrLocalhost("10.0.0.9:12345")` directly (this string is exactly what `w.RemoteAddr().String()` would return for a UDP packet whose spoofed IP header source is `10.0.0.9`) and assert it returns `true`.
4. Call `ds.QueryCert("10.0.0.9.")` and assert it returns the non-empty marshaled certificate JSON.
5. For a full network-level PoC (not unit-testable in Go alone): start `dnsServer.Start()` bound to a UDP address reachable from a raw-socket-capable test harness; from a separate process/namespace, craft a raw IP+UDP packet with source IP `10.0.0.9` and destination the DNS listener, containing a TXT query for the lighthouse's own hostname; assert the received DNS response contains a TXT record with certificate JSON, confirming disclosure without any Noise handshake having occurred. func (d *dnsServer) QueryCert(data string) string {
	if len(data) < 2 {
		return ""
	}
	ip, err := netip.ParseAddr(data[:len(data)-1])
	if err != nil {
		return ""
	}

	// The hostmap only ever contains peers we have handshaked with, so it never carries an entry for ourselves.
	// Answer self lookups straight from the local cert state.
	if cs := d.certState(); cs != nil && cs.myVpnAddrsTable != nil && cs.myVpnAddrsTable.Contains(ip) {
		c := cs.GetDefaultCertificate()
		if c == nil {
			return ""
		}
		b, err := c.MarshalJSON()
		if err != nil {
			return ""
		}
		return string(b)
	}

	hostinfo := d.hostMap.QueryVpnAddr(ip)
	if hostinfo == nil {
		return ""
	}

	q := hostinfo.GetCert()
	if q == nil {
		return ""
	}

	b, err := q.Certificate.MarshalJSON()
	if err != nil {
		return ""
	}
	return string(b)
}

func (d *dnsServer) isSelfNebulaOrLocalhost(addr string) bool {
	a, _, _ := net.SplitHostPort(addr)
	b, err := netip.ParseAddr(a)
	if err != nil {
		return false
	}

	if b.IsLoopback() {
		return true
	}

	cs := d.certState()
	if cs == nil || cs.myVpnAddrsTable == nil {
		return false
	}
	//if we found it in this table, it's good
	return cs.myVpnAddrsTable.Contains(b)
}

func getDnsServerAddr(c *config.C) string {
	dnsHost := strings.TrimSpace(c.GetString("lighthouse.dns.host", ""))
	// Old guidance was to provide the literal `[::]` in `lighthouse.dns.host` but that won't resolve.
	if dnsHost == "[::]" {
		dnsHost = "::"
	}
	return net.JoinHostPort(dnsHost, strconv.Itoa(c.GetInt("lighthouse.dns.port", 53)))
}
