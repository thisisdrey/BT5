Confirmed: the `SUICIDE`/`SELFDESTRUCT` opcode energy cost in java-tron is a fixed constant (`SUICIDE = 0`, `SUICIDE_V2 = 5000`) regardless of how many distinct TRC10 tokens the self-destructing account holds, while `MUtil.transferAllToken` iterates over the *entire* `AssetMapV2` of the account unmetered.

### Title
Unmetered iteration over an account's full TRC10 asset map during SELFDESTRUCT enables cheap, attacker-triggered CPU exhaustion - (File: `actuator/src/main/java/org/tron/core/vm/utils/MUtil.java`)

### Summary
When a smart contract executes `SELFDESTRUCT`, `Program.suicide`/`Program.suicide2` call `MUtil.transferAllToken`, which iterates over every entry in the destroying account's `AssetMapV2` (all TRC10 token balances the account holds) and copies each one to the beneficiary. This loop is charged **zero additional energy** beyond the fixed `SUICIDE` opcode cost, mirroring the "unmetered balance iteration" bug class from the external report: an attacker can inflate the number of distinct token balances on a target address for a negligible, fixed per-token transfer cost, then trigger a single opcode (`SELFDESTRUCT`) whose gas/energy cost does not scale with that iteration.

### Finding Description
- `EnergyCost.getSuicideCost`/`getSuicideCost2`/`getSuicideCost3` in `actuator/src/main/java/org/tron/core/vm/EnergyCost.java` return fixed constants (`SUICIDE = 0`, `SUICIDE_V2 = 5000`, plus at most `NEW_ACCT_CALL = 25000` if the beneficiary account doesn't exist). None of these costs depend on the number of TRC10 tokens the self-destructing account holds. [1](#0-0) [2](#0-1) 
- `Program.suicide`/`Program.suicide2` (executed by `OperationActions.suicideAction`/`suicideAction2` when the opcode fires) call `MUtil.transferAllToken(getContractState(), owner, obtainer)` whenever `VMConfig.allowTvmTransferTrc10()` is enabled. [3](#0-2) [4](#0-3) 
- `MUtil.transferAllToken` reads the full `getAssetMapV2()` of the source account and iterates it via `forEach`, performing a map get/put for every distinct token id — no bound, no per-item metering. [5](#0-4) 
- An attacker can cheaply give a contract (or any account) an arbitrarily large number of distinct TRC10 token balances via ordinary `TransferAssetContract`/`transferToken` operations spread over many blocks (each such transfer is itself individually metered/charged normally), then call `SELFDESTRUCT` on that contract in one transaction. The single `SELFDESTRUCT` opcode pays the same fixed energy regardless of whether the account holds 1 or 100,000 distinct token balances, so the node performs unbounded work (map iteration, protobuf builder rebuilding, DB writes) for a fixed, attacker-controlled fee.

### Impact Explanation
Because the per-opcode energy accounting doesn't scale with the number of tokens transferred during self-destruct, a single transaction with a fixed `feeLimit`/energy budget can force the executing node to do CPU/memory work proportional to an attacker-chosen (and attacker-fundable) number of distinct TRC10 balances. Depending on how large the attacker grows this set, this can materially slow down or stall transaction/block processing on validating nodes for that transaction, which is the same class of impact as the reported "permissionlessly halt the chain on demand" issue: unbounded, unmetered iteration over an account's balances triggered by a cheap, permissionless action.

### Likelihood Explanation
Reachable by any unprivileged account: deploy or reuse any contract, fund it with many distinct TRC10 token ids via standard `TransferAssetContract`/`transferToken` (each of these operations is itself cheap and can be split across blocks or batched), then submit one transaction invoking `SELFDESTRUCT` on that contract. No special permissions, SR/witness role, or privileged state is required — it is directly reachable via the standard actuator/TVM transaction path (`suicideAction`/`suicideAction2` in `actuator/src/main/java/org/tron/core/vm/OperationActions.java`).

### Recommendation
Meter `MUtil.transferAllToken` proportionally to the number of TRC10 tokens held by the self-destructing account (e.g., charge energy per token entry before executing the loop, similar to how `LOG` costs scale with data size in `EnergyCost.getLogCost`), or cap/require a bounded list of tokens to migrate on self-destruct, consistent with the "require a list of denoms" / "scale gas with iteration count" recommendation from the referenced report.

### Proof of Concept
1. Deploy a minimal contract `C` with a `SELFDESTRUCT(address)` function, enabling `allowTvmTransferTrc10`.
2. From an unprivileged account, issue/acquire N distinct TRC10 token ids and send 1 unit of each to `C` via `transferToken`/`TransferAssetContract` across multiple blocks (cheap, linear cost per transfer, same class as the report's `ibc/0..N` token flood).
3. Call `C.SELFDESTRUCT(beneficiary)` in a single transaction with a normal `feeLimit`.
4. Observe that `Program.suicide`/`suicide2` invoke `MUtil.transferAllToken`, which iterates all N entries in `fromAccountCap.getAssetMapV2()` [6](#0-5) , while the opcode's energy charge is the fixed `SUICIDE`/`SUICIDE_V2` constant plus at most `NEW_ACCT_CALL`, unaffected by N. Increasing N increases node-side work for the same fixed energy cost, analogous to the reported reward-pool balance flood.

```java
    if (isDeadAccount(program, inheritorAddress)) {
      return getSuicideCost(program) + NEW_ACCT_CALL;
    }
```

```java
  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
```
