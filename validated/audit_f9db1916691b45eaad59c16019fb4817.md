### Title
Out-of-bounds read in `Zip64ExtraField::attr64()` due to unchecked attribute index derived from untrusted CDH/LH size fields - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`CDH::compressed_file_size()`, `CDH::local_header_offset()`, and the analogous `LH` accessors compute an index into the Zip64 extra field's `attr_[]` flexible array based on which 32-bit size fields in the (attacker-controlled) Central Directory/Local Header are set to the `0xFFFFFFFF` ZIP64 sentinel, then read `attr64(index)` without verifying that `index < attr_count()`. This mirrors the FreeRDP ADPCM bug class: an index/selector value taken directly from untrusted input data is used to access a table/array without a bounds check against the table's actual declared size.

### Finding Description
The Zip64 extra field is defined as a 4-byte tag/length header followed by a variable number of 64-bit attributes, with the count derived from the field's own `payload_size()`: [1](#0-0) 

`attr64(int index)` performs no bounds check against `attr_count()`: [2](#0-1) 

`CDH::compressed_file_size()` and `CDH::local_header_offset()` derive the index to pass into `attr64()` from the `compressed_file_size32_`/`uncompressed_file_size32_` fields of the very same (attacker-supplied) Central Directory Header, via `ziph::zfield_has_ext64()` (checks for the `0xFFFFFFFF` sentinel): [3](#0-2) [4](#0-3) 

Nothing checks that the actual Zip64 extra field found via `zip64_extra_field()` (which itself only validates that the field's declared `payload_size()` fits within the extra-fields buffer, via `ExtraField::find`) contains enough 64-bit attributes to satisfy the computed `attr_no`: [5](#0-4) 

Concretely, an attacker can craft a ZIP/JAR whose CDH has `compressed_file_size32_ = uncompressed_file_size32_ = local_header_offset32_ = 0xFFFFFFFF` (implying up to 3 stored 64-bit attributes are required) but whose accompanying Zip64 extra field has `payload_size() == 0` or `8` (i.e., `attr_count()` of 0 or 1). `zip64_extra_field()` still returns a valid, in-bounds pointer to this truncated field (its own size check passes), but `local_header_offset()` will then compute `attr_no` up to 2 and call `attr64(2)`, reading 16+ bytes past the field's declared/actual payload — an out-of-bounds read relative to the extra-field's own bounds and potentially past the mapped file/heap buffer entirely.

This code is reached whenever Bazel's `singlejar` tool (used to merge/repackage JARs, e.g. building deploy jars, or the `zipper`/output-jar machinery) parses a Central Directory entry: `InputJar::NextEntry()` computes `cdh->local_header_offset()` to locate the local header, and `OutputJar::AddJar()` uses `jar_entry->compressed_file_size()`/`uncompressed_file_size()` when copying entries: [6](#0-5) [7](#0-6) 

Since `singlejar` operates on JAR files that are frequently third-party dependency artifacts (e.g. fetched by `http_jar`/`http_archive` or maven rules) that an unprivileged attacker (hostile registry/mirror or dependency author) can fully control, a maliciously crafted JAR can trigger this out-of-bounds read purely by being consumed as a build input.

### Impact Explanation
The bug is an out-of-bounds read (CWE-125) in the CDH/LH parsing path of Bazel's own JAR-processing tool. Best case it produces a garbage offset/size that is later used for further memory addressing (e.g. `mapped_file_.address(cdh->local_header_offset() + preamble_size_)` in `InputJar::LocalHeader`), which can lead to reading further out-of-bounds memory, a crash (denial of build), or leaking adjacent process memory content into the build output. It does not by itself grant code execution or write outside sandboxed directories, matching the "Medium" severity of the analog FreeRDP CVE.

### Likelihood Explanation
Any unprivileged party that can publish a JAR/ZIP file consumed by a Bazel build (a dependency author, compromised mirror, or a hostile CI-served archive) can trigger this by crafting a Central Directory entry whose ZIP64 sentinel fields (`0xFFFFFFFF`) are inconsistent with the actual size of the accompanying Zip64 extra field. No credentials, checksum bypass, or privileged access is required — this is a pure parsing bug independent of Bazel's integrity-checking layer (which validates the downloaded archive's hash, not the internal consistency of its ZIP structure).

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site in `CDH`/`LH`), validate `index < attr_count()` before dereferencing `attr_[index]`, and treat a mismatch as a malformed/corrupt archive error (returning a sentinel/error rather than reading past the field). Apply the same validation in `local_header_offset()` and `compressed_file_size()`/`uncompressed_file_size()` in both `CDH` and `LH`.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test (e.g. alongside `src/tools/singlejar/zip_headers_test.cc`) can construct a `CDH` byte buffer with:
- `compressed_file_size32_ = uncompressed_file_size32_ = local_header_offset32_ = 0xFFFFFFFF`
- A trailing Zip64 extra field with tag `0x0001` and `payload_size = 0` (or `8`, i.e., 0 or 1 stored attributes)

Then call `cdh->local_header_offset()` (or `compressed_file_size()`) and observe (e.g. under AddressSanitizer) an out-of-bounds heap/stack read as `attr64()` indexes past the extra field's declared payload — analogous to the existing `ZipHeadersTest.CentralDirectoryHeader` test in `src/tools/singlejar/zip_headers_test.cc`, but with a truncated/inconsistent Zip64 extra field instead of a fully-populated one.

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
