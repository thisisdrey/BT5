### Title
Floating-point truncation in vote reward computation permanently loses part of a voter's SR reward - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long, List<Pair<byte[], Long>>)` (the "old" per-cycle reward algorithm) computes a voter's share of a witness's cycle reward pool using `double` arithmetic and then truncates the result to a `long`. The truncated remainder is never re-added to the reward pool or otherwise accounted for, so it is permanently lost — directly analogous to the reported truncation bug where dividing before multiplying (or using a lossy intermediate representation) silently drops value that the depositor/voter was entitled to.

### Finding Description
`computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [1](#0-0) 

`totalReward` is `delegationStore.getReward(cycle, srAddress)`, a fixed pool for that witness/cycle read via `delegationStore.getReward` [2](#0-1) . Each voter's share is computed independently as `(double) userVote / totalVote * totalReward`, cast/added into a `long reward`. Because the ratio is computed in double-precision floating point rather than exact integer arithmetic (as is done elsewhere in the codebase, e.g. the newer VI-based reward path which uses `BigInteger` multiply/divide, see `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DelegationStore.DECIMAL_OF_VI_REWARD)` [3](#0-2) ), the computation truncates fractional TRX-wei amounts per voter, per cycle. This is the "old reward algorithm" path used for cycles before `getNewRewardAlgorithmEffectiveCycle()` [4](#0-3) , and it is still reachable for any account whose voting history spans cycles prior to the new-algorithm effective cycle (or when `allowOldRewardOpt` is not enabled) via `getOldReward` → `computeReward(cycle, votes)` in a loop over cycles [5](#0-4) .

This is reachable by any unprivileged voter: `withdrawReward(address)` and `queryReward(address)` are invoked from `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `VoteWitnessActuator` — all standard, broadcastable, signed transactions that any account can submit.

Unlike the exchange truncation paths in this codebase (`ExchangeWithdrawActuator`), which were explicitly hardened with `BigDecimal`/precision checks ("Not precise enough") and a `SafeExchangeProcessor` [6](#0-5) , the old-algorithm `computeReward` in `MortgageService` has no such safeguard and still uses raw `double` math with silent truncation, mirroring the reported vulnerability class: computing a proportional user amount via a lossy division/multiplication that discards a remainder no one ever recovers.

### Impact Explanation
Each affected voter permanently loses the fractional (sub-integer, i.e. sub-sun) portion of their rightful reward every cycle the old algorithm is used. While individually tiny, this occurs on every reward computation across every voter and every cycle prior to the new-algorithm cutover, and the lost sun amounts are never credited to any account (not the voter, not the SR, not a pool) — they are a genuine unbacked/loss-of-funds bug consistent with "permanent freezing/loss of funds," matching the External Report's medium-severity classification for truncation-caused fund loss.

### Likelihood Explanation
This code path executes automatically whenever a voter's reward for a pre-cutover cycle is computed, which happens on ordinary user actions like `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`, or `VoteWitnessActuator` execution — normal, frequent, unprivileged transactions. No special conditions or malicious setup are required beyond having voted in an eligible cycle, so likelihood is high for any long-lived voter account, though the loss magnitude is capped by floating point precision (sub-sun rounding) per cycle.

### Recommendation
Replace the double-based ratio computation in `MortgageService.computeReward(long, List<Pair<byte[], Long>>)` with exact integer arithmetic, e.g. `BigInteger.valueOf(totalReward).multiply(BigInteger.valueOf(userVote)).divide(BigInteger.valueOf(totalVote))`, consistent with the exact `BigInteger` approach already used in the new VI-based reward algorithm (`DECIMAL_OF_VI_REWARD` path). If exact integer division still leaves an irreducible remainder (multiple voters dividing one pool), track and roll over the remainder into the pool for the next cycle rather than discarding it.

### Proof of Concept
1. Configure a witness with `totalReward` = 100 sun for a cycle and two voters with `userVote` = 1 and `totalVote` = 3 respectively (i.e., one voter holds 1/3 of votes).
2. `voteRate = 1.0/3.0` in double ≈ `0.3333333333333333`; `reward = (long)(0.3333333333333333 * 100)` = `33` (via truncating cast in the accumulation `reward += voteRate * totalReward` at [7](#0-6) ).
3. The other voter with 2/3 share similarly nets `66`. Total distributed = `99`, leaving `1` sun permanently unaccounted for and unrecoverable by either voter, the witness, or the protocol — demonstrating the same "amount truncated, remainder becomes permanently lost" pattern described in the External Report.

**Note on completeness**: I could not fully verify how frequently the old-algorithm path is exercised in the current mainnet configuration (i.e., whether `allowOldRewardOpt`/`newRewardAlgorithmEffectiveCycle` has already passed for all live cycles), since that requires runtime/on-chain state not available via static code search. If the old algorithm is fully deprecated for all currently reachable cycles, the practical impact would be limited to historical state rather than newly exploitable loss going forward.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
