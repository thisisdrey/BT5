### Title
Relayer reward paid regardless of on-chain execution outcome (`success` field ignored) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The core broken invariant in the external report is that a *settlement-relevant* value (payout calculator, fee, LP manager) can be swapped or ignored between "commitment" and "settlement", producing an incorrect payout without the correctness check being enforced at settlement time. The real local analog is `Pallet::process_delivery_receipt` in the Snowbridge Ethereum outbound queue v2 pallet, which computes and pays a relayer reward from a `DeliveryReceipt` without ever checking the receipt's `success` field.

### Finding Description
`DeliveryReceipt` decodes the Ethereum `InboundMessageDispatched(nonce, topic, bool success, reward_address)` event and explicitly carries a `success: bool` flag indicating whether the message execution on the Ethereum Gateway contract actually succeeded: [1](#0-0) 

However, `Pallet::process_delivery_receipt`, which is invoked by the public extrinsic that verifies and submits this receipt, never inspects `receipt.success`. It only checks the gateway address matches, looks up the `PendingOrder` by nonce, and unconditionally registers the relayer reward and removes the pending order: [2](#0-1) 

The pending-order state advance (`<PendingOrders<T>>::remove(nonce)`) and the reward payout (`T::RewardPayment::register_reward`) both occur purely based on proof of log inclusion/decoding, not based on whether the referenced message actually executed successfully on the destination chain. This violates the invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here the *decode* of a valid log is treated as sufficient for *settlement*, even when the decoded payload states `success = false`.

### Impact Explanation
Any relayer can submit a delivery receipt (via the public `submit_delivery_receipt` entrypoint, which decodes and verifies the Ethereum event proof and calls this function) for a message whose `InboundMessageDispatched` event reports `success: false` (i.e., the message reverted or failed to execute on Ethereum), and still receive the full relayer reward as if delivery succeeded. This is not privileged/admin behavior — it is the ordinary, unprivileged relaying flow — and results in unbacked reward payout: value is minted/transferred to a relayer for work that did not actually complete, draining the bridge reward pot without corresponding successful message delivery. This matches the "theft or unbacked mint" and "duplicate settlement or payout" impact classes.

### Likelihood Explanation
The flow requires no malicious peer, validator, admin, or governance action — merely a normal relayer submitting a genuine, correctly-signed/verified Ethereum log proof for a message whose on-chain execution failed (which can legitimately happen, e.g., due to gas exhaustion or a reverting downstream call in the Gateway contract). Because `success` is already present in the decoded struct but simply unused in the payout path, the bug is a straightforward missing-check rather than a complex exploit chain, making it highly likely to be triggerable in normal operation.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, the pending order should still be resolved (e.g., removed or marked as failed) but the reward should not be paid, and ideally an event distinguishing failed delivery should be emitted so downstream systems (and potentially retry/refund logic) can react correctly.

### Proof of Concept
Using the existing test harness in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` (e.g., `poc_m1`, which already demonstrates the halted-bridge case), construct a `DeliveryReceipt` with `success: false` for a `PendingOrder` inserted with `fee = 1_000_000`, and call `OutboundQueue::submit_delivery_receipt` (or directly `Pallet::<Test>::process_delivery_receipt`) with that receipt: [3](#0-2) 
Assert that the call returns `Ok(())`, that `RewardRegistered`/reward balance for the relayer increases by `order.fee`, and that `<PendingOrders<T>>::get(nonce)` is now `None` — despite `success` being `false`. This demonstrates the reward is paid for a failed delivery, confirming the missing `success` check identified in `process_delivery_receipt`.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
