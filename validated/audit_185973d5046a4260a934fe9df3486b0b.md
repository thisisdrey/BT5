### Title
Permanent DoS lock of `WalletContract` via callback-receipt gas exhaustion/failure discarding the `has_in_flight_tx` reset - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit `WalletContract` uses a boolean flag `has_in_flight_tx` as a re-entrancy/concurrency guard to ensure only one asynchronous RLP-emulated transaction is "in flight" at a time [1](#0-0) . The flag is reset to `false` as the *first statement* of each `#[private]` callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) before any further logic runs [2](#0-1) [3](#0-2) [4](#0-3) . If that same receipt subsequently fails for any reason (panic, or running out of the statically-attached callback gas while parsing an oversized/attacker-controlled cross-contract response), the entire receipt — including the earlier `has_in_flight_tx = false` write — is rolled back by the runtime, per the documented "failed receipt atomicity" invariant: a receipt whose result is `Err` triggers `state_update.rollback()`, discarding *all* state changes from that receipt [5](#0-4) . Because `has_in_flight_tx` was already set `true` by the *previous* (already-committed) receipt, the rollback leaves it permanently stuck at `true`, and `rlp_execute` unconditionally rejects all future calls while it is `true` [6](#0-5) .

### Finding Description
This is the async-receipt analog of the Solidity reentrancy bug: the external report exploits a state-mutating function that fails to protect itself against being re-entered/interrupted mid-flight, letting the attacker corrupt persistent contract state via a callback path. In NEAR there is no synchronous reentrancy, but `WalletContract` implements the exact same "in-flight lock" pattern (`has_in_flight_tx`) to serialize its own asynchronous, multi-receipt execution flow across promise callbacks — explicitly documented as an invariant: "`has_in_flight_tx` must be `true` when a mutable method of this contract returns a promise and `false` otherwise" [7](#0-6) .

The bug is that the flag reset (`self.has_in_flight_tx = false;`) is written in the *same* receipt as the rest of the callback's logic, which can subsequently fail:

- `nep_141_storage_balance_callback` is invoked with `target`/`token_id` fully controlled by the attacker's RLP-encoded Ethereum "transaction" for an `ERC20Transfer` — the target account only needs to hash to the address in the `to` field [8](#0-7) , so an attacker can deploy an arbitrary contract as `token_id` and control the payload returned from `storage_balance_of`.
- The callback deserializes that attacker-controlled payload via `serde_json::from_slice` and does further work, all funded by a small fixed gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` = 5+5+5 = 15 TGas, plus the user's `action.gas()`) [9](#0-8) [10](#0-9) .
- If this attacker-influenced work exhausts the receipt's attached gas (or otherwise causes the receipt to error), the runtime treats the whole receipt as failed and rolls back *every* state write made in it, per `apply_action_receipt`'s commit/rollback logic [5](#0-4)  and the documented invariant "**Failed receipt atomicity**: a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting" [11](#0-10) .
- Because the earlier receipt (the one that dispatched this callback) already committed `has_in_flight_tx = true` before this callback ran, the rollback of the callback receipt leaves `has_in_flight_tx` stuck at `true` forever, with no code path in the contract able to reset it (`rlp_execute` immediately refuses further calls while `has_in_flight_tx` is `true`) [12](#0-11) .

This mirrors the report's root cause pattern — a guard/flag update placed alongside externally-influenced logic in the same atomic unit, such that a crafted external interaction (there: reentrant call; here: an attacker-controlled callback payload that forces receipt failure) prevents the guard's reset from taking effect, corrupting the contract's availability invariant.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the `WalletContract` account is permanently locked: `rlp_execute` — the sole entry point for emulated Ethereum transactions on that account — will reject every subsequent call, forever, with "transaction already in progress" [12](#0-11) . There is no owner-privileged reset or timeout mechanism in the contract. This constitutes a permanent freeze of the eth-implicit account's ability to transact via its Ethereum-compatible interface (transfers, ERC-20 operations, etc. can no longer be submitted), matching the "permanent freezing of funds" impact category. An attacker only needs to control (or trick a relayer into relaying) a single RLP transaction whose `ERC20Transfer` target is an attacker-deployed contract engineered to return a payload that exhausts the fixed callback gas budget.

### Likelihood Explanation
The attack requires only an ordinary, unprivileged transaction: the attacker crafts an RLP-encoded "ERC-20 transfer" whose decoded `to` address resolves to an account they control, deploys a minimal contract there whose `storage_balance_of` returns a payload sized/structured to blow through the fixed ~15 TGas callback budget during JSON deserialization, and calls `rlp_execute` (or has any relayer relay it) targeting that contract. No special privileges, races, or validator cooperation are needed — it is directly reachable by any client transaction against a deployed `WalletContract` instance.

### Recommendation
Do not couple the `has_in_flight_tx` reset to logic that can fail within the same receipt. Options:
- Reset `has_in_flight_tx = false` in a dedicated, minimal, panic-free step that is guaranteed to run and commit before any externally-influenced/attacker-controlled parsing or gas-variable logic executes (e.g., persist the reset via a separate cheap receipt/promise that cannot itself fail from attacker-controlled input).
- Bound/validate the size of cross-contract responses (e.g. `storage_balance_of`) before deserializing, and ensure sufficient fixed gas headroom independent of attacker-controlled response size.
- Add a recovery/unlock path (e.g., an owner- or timeout-gated reset of `has_in_flight_tx`) so a stuck flag cannot permanently disable the account.

### Proof of Concept
1. Attacker (or a compromised/malicious relayer) computes an eth-implicit address whose corresponding NEAR account they control, and deploys a minimal "fake NEP-141" contract there whose `storage_balance_of` method returns an oversized/adversarial JSON blob.
2. Attacker RLP-encodes an ERC-20 `transfer(to, value)` call with `to` matching that address and submits it via `rlp_execute` on the victim's `WalletContract` (`inner_rlp_execute` → `try_emulation` → `ERC20Transfer` path) [13](#0-12) .
3. `has_in_flight_tx` is set `true` and committed by the first receipt [14](#0-13) .
4. `nep_141_storage_balance_callback` is invoked as the next receipt; it sets `has_in_flight_tx = false` then deserializes the attacker's oversized response, exhausting its statically-attached gas before it can dispatch/complete the follow-up promise, causing the receipt to fail [15](#0-14) .
5. Per runtime semantics, the failed receipt is rolled back in full, so the `has_in_flight_tx = false` write never persists; `has_in_flight_tx` remains `true` in the account's committed state [5](#0-4) .
6. Any future call to `rlp_execute` on this `WalletContract` account now fails permanently with "transaction already in progress" [12](#0-11) .
