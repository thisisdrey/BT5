### Title
Missing validation of the `type` field in `AccountCreateContract` allows spoofing an account as `AccountType.Contract` - (File: actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java)

### Summary
`CreateAccountActuator`, which any signed `AccountCreateContract` transaction can invoke, never validates the `type` field of the contract. A caller can therefore create a brand-new account explicitly stamped as `AccountType.Contract` without ever deploying a smart contract through `CreateSmartContract`. This mirrors the reported bug class: a "create X" entry point fails to constrain a discriminator field, letting the caller mint an unintended, more privileged/differently-trusted object type.

### Finding Description
`CreateAccountActuator.validate()` explicitly comments out the only check that would have inspected the contract's `type` field: [1](#0-0) 
No other check anywhere in `validate()` or `execute()` restricts `type` to `AccountType.Normal`/`AssetIssue`, or rejects `AccountType.Contract`: [2](#0-1) [3](#0-2) 

The proto definition allows the `type` field to be freely set to any `AccountType`, including `Contract`: [4](#0-3) 

Elsewhere in the codebase, `AccountType.Contract` is used as a security-relevant discriminator by several actuators/processors that branch behavior based on whether an account is a "contract" account, e.g. `TransferActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceActuator`, `DelegateResourceActuator`, `TransferAssetActuator`, and native TVM contract processors: [5](#0-4) [6](#0-5) 

These actuators assume the `type` stored in `AccountCapsule` faithfully reflects whether the account is an EOA or an actual deployed contract (normally only set to `Contract` as a side effect of `CreateSmartContract`, never via `AccountCreateContract`). Because `CreateAccountActuator` performs no such restriction, any externally-owned account (an "unprivileged transaction broadcaster") can mint an address that the account store, and every downstream actuator that reads `AccountCapsule.getType()`, will treat as a genuine contract account — even though it has no deployed bytecode and is fully controlled by a private key.

### Impact Explanation
Account-type spoofing breaks the invariant that `AccountType.Contract` implies "this address is a TVM contract, not a plain key-controlled address." Actuators that gate behavior on this flag (for example the `FORBID_TRANSFER_TO_CONTRACT` protection intended to stop TRX from being sent directly to contract addresses so it isn't inadvertently locked, and resource-delegation/freeze logic that treats contract accounts differently from normal accounts) can be misled by a spoofed account. An attacker fully controlling the private key of a "fake contract" account can accept, move, or otherwise manipulate funds or votes in ways the protocol's type-based checks were designed to prevent for genuine contract accounts, while none of the safety assumptions those checks rely on (immutable bytecode, no private key control) actually hold.

### Likelihood Explanation
Reaching this defect requires only submitting a single signed `AccountCreateContract` transaction with `type = Contract` and paying the standard account-creation fee — no special privilege, contract deployment, or governance action is needed, making this trivially reachable by any broadcaster.

### Recommendation
In `CreateAccountActuator.validate()`, reject any `AccountCreateContract` whose `type` is not `AccountType.Normal` (or `AssetIssue` if still supported), i.e. reinstate and strengthen the currently commented-out type check so that `AccountType.Contract` can only ever be assigned through the `CreateSmartContract` code path.

### Proof of Concept
1. An attacker generates a keypair and constructs an `AccountCreateContract` with `owner_address` = attacker's existing funded account, `account_address` = new address, and `type = Contract`.
2. The attacker signs and broadcasts the transaction; `CreateAccountActuator.validate()` performs no check on `type` [3](#0-2) , so validation passes.
3. `CreateAccountActuator.execute()` persists an `AccountCapsule` built directly from the attacker-supplied contract, including the spoofed `type` [7](#0-6) .
4. The new address is now stored with `AccountType.Contract` even though it is a plain EOA controlled by the attacker's private key, and it will be treated as such by every actuator/opcode that checks `getType() == AccountType.Contract`.

Note: I was not able to fully trace, within the available iterations, the exact conditional logic inside `TransferActuator`, `FreezeBalanceActuator`, and `DelegateResourceActuator` that consumes `AccountType.Contract` (only confirmed their references to this enum value), so the precise quantitative impact of the spoofed type on each of those actuators should be independently verified before treating this purely as a funds-theft/freezing primitive.
