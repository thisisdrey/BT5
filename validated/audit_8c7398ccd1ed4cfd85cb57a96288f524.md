## Title
Witness reward increments recorded while a witness's live vote count is zero are permanently dropped by the VI (reward-index) accumulator, leaving that portion of the reward unclaimable forever - (`File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
The reported Beedle bug is a class of issue where a Compound-style reward index (`index`/`Vi`) is only initialized/incremented relative to a denominator (`totalSupply` in Beedle, `voteCount` in java-tron), and any reward that accrues while that denominator is zero gets permanently excluded from the index, so it can never be attributed to anyone. Java-tron's DPoS voting-reward mechanism (the "new reward algorithm") uses the exact same pattern: a cumulative value-index `Vi` per witness that is advanced by `reward / voteCount`, and rewards for a cycle in which the recorded `voteCount` is `0` are simply "forwarded" without being folded into `Vi`.

### Finding Description
`DelegationStore.accumulateWitnessVi` computes the witness reward index the same way Beedle's `Staking.update()` computes its share index: [1](#0-0) 

If `voteCount == 0` for the cycle being processed, the method takes the "just forward pre vi" branch and does **not** add the reward already recorded for that cycle into `Vi`. That recorded reward value (`getReward(cycle, address)`) is never revisited or redistributed afterwards - it is effectively discarded from the reward-index bookkeeping permanently.

This method is invoked once per cycle, per witness, from `MaintenanceManager.doMaintenance()`, using the witness's **live** `voteCount` field at the moment the maintenance cycle turns over: [2](#0-1) 

Meanwhile, the reward value being accumulated for the cycle is populated unconditionally, independent of the witness's vote count, every time a block/standby reward is paid: [3](#0-2) 

So the temporal sequence that reproduces the Beedle-class bug is:
1. A witness earns block/transaction-fee/standby reward during cycle `N`, which is booked via `delegationStore.addReward(N, witnessAddress, value)` (`MortgageService.payReward`), independent of the witness's current vote count.
2. Before `MaintenanceManager.doMaintenance()` processes cycle `N` (i.e., before `accumulateWitnessVi` runs at the top of `doMaintenance()`), the witness's live `WitnessCapsule.voteCount` becomes `0` — e.g., all voters withdraw/un-vote the witness within the same cycle, or `tryRemoveThePowerOfTheGr()` zeroes out a genesis representative's vote power.
3. `accumulateWitnessVi(N, witness, 0)` takes the "forward pre vi" branch, so the reward recorded for cycle `N` is never converted into a `Vi` increment.
4. Any later voter who votes for that same witness in a subsequent cycle computes their reward from `endVi - beginVi` (`MortgageService.computeReward` / `VoteRewardUtil.computeReward`), which never reflects the dropped cycle-`N` reward: [4](#0-3) 

Because `Vi` is a monotonically-forwarded cumulative counter and the dropped cycle's reward is never re-injected into a future `Vi` delta, this reward becomes permanently unattributable to any account, mirroring exactly how Beedle's pre-first-staker WETH becomes permanently unclaimable once `index`/`supplyIndex` initializes without accounting for the earlier accrual.

### Impact Explanation
The TRX/energy value already earmarked as a voter reward (i.e., the portion of block/standby reward not taken as witness brokerage) becomes economically unrecoverable: it is recorded in `DelegationStore`'s per-cycle reward key but can never be paid out to any voter through `withdrawReward`/`queryReward`, nor is it returned to the witness or any other party. This is a permanent loss of the intended voter-reward funds, consistent with a "permanent freezing of funds" impact.

### Likelihood Explanation
This requires a specific but reachable condition: a witness's live vote count drops to exactly zero within the same maintenance cycle in which it has already accrued a nonzero recorded reward, before `MaintenanceManager.doMaintenance()` runs its VI accumulation pass. This can occur via ordinary user-triggered vote-withdrawal actions (`VoteWitnessActuator`/`WithdrawBalanceActuator`, unvote-to-zero) reachable by any account, or via the built-in `tryRemoveThePowerOfTheGr()` genesis-representative power removal path. No special/privileged access is required beyond normal transaction broadcasting, making it a Medium-likelihood scenario.

### Recommendation
When `voteCount == 0` but `reward > 0` for a cycle in `DelegationStore.accumulateWitnessVi`, do not silently discard the reward. Either (a) roll the un-distributable reward forward into the next cycle's `getReward` bucket for the same witness so it can be distributed once votes reappear, or (b) redirect it to a recoverable pool (e.g., return it to the block-reward/incentive pool) instead of leaving it permanently orphaned in a reward key that is never read again by any consumer.

### Proof of Concept
1. Register and elect witness `W` with nonzero votes so it earns block rewards each cycle (`MortgageService.payBlockReward` → `DelegationStore.addReward`).
2. Have the sole voter(s) for `W` fully unvote `W` (vote count → 0) within the same cycle `N` in which `W` has already accrued reward via block production, before the next `MaintenanceManager.doMaintenance()` tick.
3. Observe that `doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)`, hitting the `voteCount == 0` branch and forwarding `preVi` unchanged, discarding cycle `N`'s reward from `Vi`.
4. Have a new voter vote for `W` in a later cycle and call `queryReward`/`withdrawReward`; confirm the reward attributable via `Vi` delta excludes the value that was recorded via `addReward(N, W, ...)`, and that no other code path in `DelegationStore`/`MortgageService` ever reads or redistributes that specific `reward-N-W` entry again.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
