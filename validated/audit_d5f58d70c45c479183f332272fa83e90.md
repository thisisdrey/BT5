### Title
Permissionless lamport donation to `pool_onramp_info` inflates `StakedWithPythPush` oracle price via `staked_pool_net_asset_value` - ([File: programs/marginfi/src/state/price.rs])

### Summary
Under `OnRampTransition::OnRampEnabled`, `load_oracle_context_with_max_age`'s `OracleSetup::StakedWithPythPush` branch computes the LST price multiplier from the raw lamport balance of `pool_onramp_info` (`ais[3]`), without verifying that those lamports were legitimately deposited through the stake pool's deposit flow. Because System Program lamport transfers succeed against any destination pubkey regardless of its owner, any unprivileged caller can inflate this balance immediately before a deposit/borrow instruction and cause the health check to see an inflated collateral price.

### Finding Description
`staked_pool_net_asset_value` (programs/marginfi/src/state/price.rs, lines 106-122) computes:
```
main_stake_value = pool_stake_info.lamports() - rent_exempt_reserve
onramp_value     = pool_onramp_info.lamports() - rent_exempt_reserve
NAV = main_stake_value + onramp_value
``` [1](#0-0) 

In `load_oracle_context_with_max_age`, when `bank.on_ramp_transition()` returns `OnRampTransition::OnRampEnabled`, `ais[3]` is checked only for **key equality** against `expected_staked_onramp(bank)` (a PDA derived from the validator vote account or an explicit `oracle_keys[3]`) — there is no check on the account's owner, data, or that its lamport balance corresponds only to legitimately-staked/pending SOL: [2](#0-1) 

The resulting `sol_pool_adjusted_balance` (i.e. NAV) is then divided by `lst_supply` to produce `multiplier`, and used to scale both `price` and `ema_price` of the Pyth feed used for the bank's collateral valuation: [3](#0-2) 

Since the onramp PDA is a plain account holding native SOL (used to accumulate SOL pending staking), Solana's `SystemProgram::transfer` instruction can add lamports to it from any funding account/signer, without requiring the destination to be owned by the System Program. An attacker can, in a single atomic transaction:
1. `SystemProgram::transfer` lamports into `expected_staked_onramp(bank)` (a well-known/derivable PDA).
2. Call a health-checked `deposit`/`borrow` instruction referencing the affected bank.

The oracle load computes an inflated `NAV`, thus an inflated `multiplier`, thus an inflated scaled `price`/`ema_price`, which the health check consumes directly as this asset's collateral value — no downstream check cross-validates the multiplier against a trusted/previous value or against the true stake-pool accounting.

### Impact Explanation
This breaks the core invariant that health checks reflect true backing collateral. If the attacker holds a deposit position in the affected `StakedWithPythPush` bank, donating lamports to the onramp account inflates the reported value of their own collateral, letting them borrow more than the bank's true backing supports — this is a classic share-price/NAV donation-inflation attack, applied to marginfi's on-chain LST exchange-rate oracle rather than a share vault. The economic severity scales inversely with the bank's real staked/LST supply: for a newly-created or thinly-staked bank (low `lst_supply`/NAV), a modest lamport donation produces a large multiplier deviation, directly enabling undercollateralized borrows and potential bad debt to the bank.

### Likelihood Explanation
Preconditions are realistic and reachable by any unprivileged user: the bank must use `OracleSetup::StakedWithPythPush` with `OnRampTransition::OnRampEnabled` (an active, non-deprecated configuration per `staked_settings.rs`), and the onramp PDA address is deterministically derivable via `derive_staked_onramp_from_vote` or directly readable from `bank.config.oracle_keys[3]`. No admin/governance action, leaked keys, or non-atomic race is required — the donation and the borrow can be composed in one transaction. The main constraint on profitability is the ratio of donation size to existing NAV/lst_supply, which is attacker-favorable for low-liquidity or newly onboarded staked banks.

### Recommendation
Do not derive the multiplier from raw, unauthenticated lamport balances of `pool_onramp_info`/`pool_stake_info`. Instead:
- Verify the onramp account's owner/program and, if possible, deserialize a program-tracked balance field rather than trusting `AccountInfo::lamports()` directly, or
- Bound the per-observation change in `multiplier`/NAV against a stored previous value (a max-deviation clamp similar to confidence-interval checks already used elsewhere in this file), rejecting price updates whose multiplier moves beyond a sane bound in a single slot, and/or
- Require that `pool_onramp_info` lamports only be recognized up to a value provably attributable to legitimate stake-pool deposit instructions (e.g., tracked via that program's own state) rather than the live lamport balance which is trivially donatable.

### Proof of Concept
Rust integration test plan (using existing `TestFixture`/`marginfi_group` test utilities, e.g. as in `programs/marginfi/tests/admin_actions/on_ramp_transition.rs`):
1. Create a `StakedWithPythPush` bank with `OnRampTransition::OnRampEnabled`, a small `lst_supply`, and known `pool_stake_info`/`pool_onramp_info` balances (call `staked_pool_net_asset_value` to record baseline NAV/multiplier).
2. Attacker deposits a modest amount of the LST as collateral.
3. In one transaction: (a) `SystemProgram::transfer` a chosen lamport amount from attacker's wallet into the derived onramp PDA (`expected_staked_onramp`), then (b) call `borrow` against the deposited collateral referencing `OraclePriceFeedAdapter::try_from_bank`.
4. Assert: `multiplier_after > multiplier_before` proportional to the donated lamports / `lst_supply`, and that `borrowed_value` obtained exceeds what would be permitted under the pre-donation (true) multiplier — i.e., `borrowed_value > true_collateral_value * max_ltv`, demonstrating an undercollateralized borrow accepted by the health check.
5. Fuzz variant: sweep donated lamport amounts and `lst_supply` sizes, asserting the invariant `borrowed_value <= true_collateral_value` fails once donation exceeds a threshold — proving the health check does not bound this manipulation.

fn staked_pool_net_asset_value(
    pool_stake_info: &AccountInfo,
    pool_onramp_info: &AccountInfo,
    rent: &Rent,
) -> MarginfiResult<u64> {
    let pool_rent_exempt_reserve = rent.minimum_balance(pool_stake_info.data_len());
    let onramp_rent_exempt_reserve = rent.minimum_balance(pool_onramp_info.data_len());

    let main_stake_value = pool_stake_info
        .lamports()
        .saturating_sub(pool_rent_exempt_reserve);
    let onramp_value = pool_onramp_info
        .lamports()
        .saturating_sub(onramp_rent_exempt_reserve);

    Ok(main_stake_value.saturating_add(onramp_value))
}
