### Title
Unauthenticated brute-force of the RPC `auth_token` due to missing rate limiting on password-gated endpoints - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
Several `stackslib` RPC handlers gate privileged, compute-heavy operations behind a single shared secret (`connection_options.auth_token`) sent in the `authorization` header. The check is a bare, unthrottled string comparison performed once per request with no attempt counter, lockout, or backoff, so a remote unauthenticated client can send unlimited guesses at line speed to brute-force the token, exactly the CWE-290 "lack of rate limiting on the login gate" class described in the Shiori advisory (GHSA-mw8h-g64c-rxv4).

### Finding Description
The following handlers all implement `try_parse_request` with the identical pattern: fetch the configured `password` (from `self.auth`), fetch the `authorization` header, and reject with `401` only if they don't match — no counting of failures, no delay, no lockout: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The same `auth_header != password` pattern also appears in `stackslib/src/net/api/postblock_v3.rs` and `stackslib/src/net/api/fastcallreadonly.rs`. Searches across `stackslib/src/net/**` for any rate-limiting, connection-throttling, ban-list, or failed-attempt counter around HTTP request handling turned up nothing that would gate repeated failed `authorization` attempts (the "rate limit"/"throttle" hits found in `rpc.rs`, `p2p.rs`, `chat.rs`, `server.rs`, etc. relate to inventory/handshake/relay pacing, not to HTTP auth failures) — this is a real gap, not merely an assumption I couldn't verify.

Equality broken: "authenticated vs. presented" — the endpoint is meant to accept only requests that know the operator's secret, but with no throttling the secret space can be exhaustively searched remotely. Additionally, the comparison `auth_header != password` is a standard (non-constant-time) `String`/`&str` comparison, which short-circuits on the first mismatched byte, giving a timing side channel that further reduces the effective search space compared to a truly random guess (this compounds, but is not required for, the rate-limiting gap).

### Impact Explanation
If an attacker successfully guesses/brute-forces the `auth_token`, they gain access to:
- `/v3/block_proposal` (`postblock_proposal.rs`) — triggers full block-proposal validation (chainstate/Clarity execution), a compute-heavy operation that can be invoked repeatedly to exhaust CPU (bounded compute DoS on a privileged endpoint).
- `/v3/blocks/simulate`, `/v3/transactions/simulate` — likewise execute Clarity code against chain state, again compute-heavy and repeatable.
- `/v3/blocks/replay` and `/v3/blocks/upload/` (`postblock_v3.rs`) — replay/ingest block data.

This matches the "bounded compute DoS on a read/privileged endpoint" impact tier: an attacker who brute-forces the shared secret can repeatedly invoke expensive validation/simulation/replay logic on the node without needing any node secret or admin role beforehand (the whole point of the flaw is that they never possessed it).

### Likelihood Explanation
Likelihood depends on the entropy of the operator-chosen `auth_token`/`auth_password` (documented in `docs/signing.md` and sample config files as a plain shared string the operator sets). Because there is no rate limiting, lockout, or CAPTCHA-equivalent, likelihood scales purely with how weak/short the configured token is and with attacker bandwidth to the RPC port — identical dynamic to the referenced Shiori advisory, where success also depends on password strength, but is not mitigated by the server. Nodes that expose the RPC/miner endpoints on non-loopback interfaces (as some sample configs and the miner conf's `[connection_options]` block imply is expected for signer/miner coordination) are directly exposed to this remotely.

### Recommendation
- Enforce constant-time comparison of the `authorization` header against the configured token, e.g. `subtle::ConstantTimeEq`, to remove the timing side channel.
- Add a per-source-IP failed-attempt counter with exponential backoff / temporary lockout on repeated auth failures within `postblock_proposal.rs`, `blocksimulate.rs`, `txsimulate.rs`, `blockreplay.rs`, `postblock_v3.rs`, and `fastcallreadonly.rs`, or centralize this check in a shared helper enforced before dispatch to any of these handlers.
- Document/require that operators bind these password-gated endpoints to loopback or a private network by default, and warn when `auth_token`/`auth_password` is short.

### Proof of Concept
1. Configure a `stacks-node` with a `connection_options.auth_token` (or equivalent per-endpoint `auth`) and expose the RPC bind address to the network.
2. Repeatedly POST to `/v3/block_proposal` (or `/v3/blocks/simulate`, `/v3/transactions/simulate`, `/v3/blocks/replay`) with the `authorization` header set to successive guesses of the token.
3. Observe that the server returns `401 Unauthorized` for wrong guesses (per `stackslib/src/net/api/postblock_proposal.rs:1139-1144`) with no increase in response latency, no lockout, and no cap on request rate — allowing an unlimited, unthrottled brute-force search of the token space until a match is found, at which point the attacker gains authorized access to the endpoint's compute-heavy validation/simulation logic.
