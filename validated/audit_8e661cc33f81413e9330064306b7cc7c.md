### Title
Dust transfers permanently fill a victim's per-account token list, DoSing their deposits, issuance, and token receipt - (File: contracts/DepositToken.sol / contracts/Pool.sol)

### Summary
CVE-2015-5194 is an input-driven crash/DoS: a crafted `logconfig` command crashes `ntpd`. The Metronome analog is a crafted-input DoS against a specific victim: an unprivileged attacker can dust-transfer `DepositToken` shares to a victim to fill the victim's `depositTokensOfAccount`/`debtTokensOfAccount` list up to `MAX_TOKENS_PER_USER` (30). Once the list is full, `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`, which makes every subsequent `_transfer`, `_mint`, `deposit(onBehalfOf_ = victim)`, `DebtToken.issue`, `DebtToken.mint`, `DepositToken.seize` to that victim revert — permanently until the victim frees slots, and the attacker can refill them at dust cost.

### Finding Description
Every balance increase on a `DepositToken` that goes to an account with zero prior balance calls back into the `Pool` to register the token in the account's list:

- `DepositToken._transfer` adds the token to `recipient_`'s list when `_recipientBalanceBefore == 0` [1](#0-0) 
- `DepositToken._mint` does the same for mint recipients [2](#0-1) 
- `DebtToken._mint` does the same for debt tokens [3](#0-2) 
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce a shared cap of `MAX_TOKENS_PER_USER = 30` across *both* lists and revert `UserReachedMaxTokens` [4](#0-3) [5](#0-4) 

Crucially, the recipient is not the caller. `transfer(to_, amount_)` and `transferFrom` are public and only check the *sender's* unlocked balance [6](#0-5) . Liquidation `seize` also routes through `_transfer`, so a liquidator's own list being full reverts the whole `Pool.liquidate` [7](#0-6) [8](#0-7) . `Pool.addDepositToken` itself caps the pool at 30 deposit tokens [9](#0-8) , so an attacker can exhaust a victim's entire list with one dust unit of each listed deposit token.

Attack steps:

1. Attacker deposits a minimal amount into each listed `DepositToken` (or receives dust of each).
2. For each deposit token `d_i` where `victim`'s balance is 0, attacker calls `d_i.transfer(victim, 1)`. Each call hits `_transfer` → `pool.addToDepositTokensOfAccount(victim)` and consumes one slot.
3. After ~`30 - current` transfers, `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`.
4. From then on, any operation that would add a *new* token to the victim's lists reverts: `deposit(amount, victim)` reverts inside `_mint` → `addToDepositTokensOfAccount`; `DebtToken.issue` reverts inside `_mint` → `addToDebtTokensOfAccount`; any third party trying to send the victim a deposit token they don't already hold reverts in `transfer`.

### Impact Explanation
The victim is locked out of adding collateral of any type they don't already hold and out of opening debt in any new synthetic market. If their existing collateral set is limited (e.g. they hold only one msd token), they cannot top up with other collateral types to defend a position approaching liquidation — converting a temporary liquidity squeeze into real loss via `Pool.liquidate`. The freeze is temporary in principle (the victim can zero out a dust balance to free a slot), but the attacker can immediately refill the freed slot at 1-wei cost, making the DoS effectively permanent and griefing-priced. This matches the accepted impact classes of temporary/permanent freezing of protocol functionality for a targeted user. The attack costs only gas plus dust balances.

### Likelihood Explanation
Fully reachable by any unprivileged EOA: `DepositToken.transfer` requires only an unlocked sender balance; acquiring dust of each deposit token only requires depositing minimum amounts (no `depositFee` blocks it, and even with a fee the cost stays trivial). No privileged actor, oracle manipulation, or governance misconfiguration is required. `onlyIfAdditionWillNotReachMaxTokens` is the exact missing check — it protects the *add* but there is no mechanism preventing forced additions, since the callback is triggered by the token contract based on `recipient_` balance rather than recipient consent. Modifiers that do apply (`whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`) do not stop it on the deployed configuration.

### Recommendation
- Remove the hard `UserReachedMaxTokens` revert on token-triggered callbacks, or make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` a no-op (or push into an overflow structure) once the cap is reached, so receipt of tokens is never blocked.
- Alternatively, only count "position-relevant" tokens toward the cap: e.g. gate `debtPositionOf`/`depositOf` iteration on the capped list but allow balances to exist outside it, and require an explicit opt-in (deposit/issue path) to register the account.
- A minimal fix is to skip `pool.addToDepositTokensOfAccount` in `_transfer` for unsolicited transfers and instead register on first `deposit`/health-relevant use, so dust transfers cannot consume victim slots.

### Proof of Concept
Hardhat-style sketch against deployed pool (assume ≥1 deposit token per slot; with fewer listed tokens, combine dust transfers of deposit tokens plus forcing debt registration is not needed since deposit tokens alone can fill all 30 if 30 are listed — if fewer than 30 are listed the attacker fills the remaining capacity up to the listed count, still blocking all un-held tokens):

```typescript
// victim has e.g. 10 tokens already; attacker fills remaining 20 slots
for (const dt of depositTokensNotHeldByVictim) {
  // attacker holds dust of dt
  await dt.connect(attacker).transfer(victim.address, 1);
  // each call: _recipientBalanceBefore == 0 -> pool.addToDepositTokensOfAccount(victim)
}
// now list is full:
await expect(
  someNewDepositToken.connect(anyone).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  someNewDepositToken.connect(friend).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  someDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// victim frees one slot by zeroing dust balance:
await dustToken.connect(victim).transfer(attacker.address, 1);
// attacker immediately refills it:
await dustToken.connect(attacker).transfer(victim.address, 1);
```
