### Title
Unchecked integer division on chain-wide resource weights causes `ArithmeticException` (`/ by zero`) reachable from a TVM contract call - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
The GPAC CVE describes an unguarded arithmetic operation (`avidmx_process`) that crashes the process with a floating-point exception because a denominator can become zero/invalid. The analogous bug class in java-tron is **unguarded integer division inside resource-accounting math that a contract can trigger via a precompiled contract call**, where the divisor comes from mutable chain state (`TOTAL_ENERGY_WEIGHT` / `TOTAL_NET_WEIGHT` / `TOTAL_ENERGY_CURRENT_LIMIT` / `TOTAL_NET_LIMIT`) and is protected only by a Java `assert` statement, which is compiled out and disabled by default in production JVMs (`java -ea` is not used to run FullNode).

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` after only an `assert totalEnergyWeight > 0;` guard: [1](#0-0) 

`assert` statements are no-ops unless the JVM is started with `-ea`; java-tron's production entrypoints do not enable assertions, so this "guard" provides no runtime protection. If `totalEnergyWeight` (or, in the sibling helper `usageToBalance`, `totalLimit`) is ever `0`, the `BigInteger.divide(...)` call throws `ArithmeticException: BigInteger divide by zero` (when `allowHardenResourceCalculation()` is on) or, in the non-hardened path, silently produces `NaN`/`Infinity` via double division — an analogous "floating point exception" class of bug where a critical divisor is not validated before use: [2](#0-1) 

This code is reachable from smart-contract execution through `FreezeV2Util`, which is invoked by TVM precompiled contracts that any account can call by deploying/triggering a contract (`getAccountEnergyUsageBalanceAndRestoreSeconds`, `getAccountNetUsageBalanceAndRestoreSeconds`, `queryFrozenBalanceUsage`, `queryDelegatableResource`, `checkUndelegateResource`): [3](#0-2) [4](#0-3) 

The equivalent chainbase-side function (`EnergyProcessor.calculateGlobalEnergyLimit`) explicitly checks `totalEnergyWeight <= 0` and returns `0` instead of relying on `assert`: [5](#0-4) 
This shows the codebase is aware this divisor can be zero/non-positive in some code paths, but the TVM/`RepositoryImpl` variant does not apply the same defensive check, relying only on the disabled `assert`.

Existing unit tests further confirm the developers are aware of overflow/zero-division risk in this exact function and have written tests that *expect* `ArithmeticException` under related edge conditions (overflow), but not for the zero-weight case guarded merely by `assert`: [6](#0-5) 

### Impact Explanation
If `totalEnergyWeight` (or the analogous `totalNetWeight`/`totalLimit` denominators) reaches `0` — a state that is only prevented by network-wide economic assumptions, not by code-level validation — any TVM contract call into these query paths throws an unhandled `ArithmeticException`. Depending on how the TVM call stack propagates this exception during block processing (rather than a simple read-only query), an uncaught runtime exception during transaction execution/energy accounting could disrupt block application, denying that transaction or, in the worst case, causing inconsistent node behavior across implementations if some nodes hit the hardened path (`BigInteger` throw) and others hit the legacy silent-double path (`NaN`/`Infinity` propagated into balance math), which is a chain-split risk class.

### Likelihood Explanation
Likelihood is difficult to fully confirm without further investigation: on a live mainnet, `totalEnergyWeight`/`totalNetWeight` are extremely unlikely to be exactly zero because many accounts already have frozen resources contributing to the totals. This makes the finding **conditionally exploitable** — practical exploitation would most plausibly occur on a private/test chain, immediately post-genesis before large freezes have accumulated, or if a future accounting bug decrements these globals to zero. Given the rules require rejecting "no-impact" or purely theoretical issues, this should be treated as a real but **narrow-likelihood** finding whose severity is Medium: the code path exists, is attacker-reachable via a standard TVM precompile call, and relies on a broken safety mechanism (`assert`), but the precondition (`totalEnergyWeight == 0` or `totalLimit == 0` on a live chain) is not something an unprivileged attacker can unilaterally force today with the parts of the code examined.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (mirroring `EnergyProcessor.calculateGlobalEnergyLimit`'s `if (totalEnergyWeight <= 0) return 0;`), and add the same explicit zero/negative check for `totalLimit` in `usageToBalance` before performing either the `BigInteger` divide or the double divide, so that a `0` denominator returns a defined value (e.g., `0`) instead of throwing `ArithmeticException` or silently producing `NaN`/`Infinity`.

### Proof of Concept
Not fully verifiable without live/staged chain state: reproducing this requires driving `TOTAL_ENERGY_WEIGHT` (or `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_CURRENT_LIMIT`/`TOTAL_NET_LIMIT`) to `0` in `DynamicPropertiesStore`, then invoking a smart contract that calls the freeze-v2 precompiled contract (e.g. type `queryFrozenBalanceUsage`/`queryDelegatableResource`) against an account with `frozeBalance >= TRX_PRECISION`, which triggers `RepositoryImpl.calculateGlobalEnergyLimit`/`usageToBalance` and, with `allowHardenResourceCalculation()` enabled, throws `ArithmeticException: BigInteger divide by zero`. This condition is most reachable on a fresh/private testnet at genesis or in a debug/test harness (as seen in `RepositoryImplHardenTest`), and I could not confirm from the code available whether mainnet invariants make `totalEnergyWeight == 0` unreachable at all times.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
