## Title
JSON field-injection via unescaped form-urlencoded values in `Util.getJsonString` used by the HTTP API body parser - (File: `framework/src/main/java/org/tron/core/services/http/Util.java`, `framework/src/main/java/org/tron/core/services/http/PostParams.java`)

### Summary
`PostParams.getPostParams` converts any `application/x-www-form-urlencoded` HTTP POST body into a JSON string by calling `Util.getJsonString(input)` before that JSON is parsed with `JsonFormat.merge` into the target request/contract object. [1](#0-0)  The observed behavior of `getJsonString`, confirmed by its own unit test, is to split the body on `&` and `=` and then wrap each raw key/value in double quotes with string concatenation (`"key":"value"`), exactly the same "concatenate untrusted data into a delimited wire format without escaping the delimiter characters" pattern as `handlerFormDataBodyData()` in the reported `http-proxy-middleware` advisory. [2](#0-1) 

### Finding Description
`Util.getJsonString` is only invoked for the urlencoded content-type branch and its test shows it does simple `key=value` splitting followed by naive quoting to synthesize a JSON object, with no escaping of `"`, `\`, or `,` in the decoded key/value strings. [3](#0-2)  If a client-controlled field value contains a `"` followed by `,"newField":"value`, the resulting string is no longer a single JSON string value; it becomes a syntactically valid JSON document with the attacker's injected key appended as a sibling of the legitimate field, the same "single input field becomes multiple fields" desync described in the advisory for the multipart writer. Because this JSON blob is what `Wallet`'s HTTP handlers subsequently feed into `JsonFormat.merge` to populate the actual request/contract object, any field-level assumptions the endpoint's outer logic makes about `req` (e.g., which keys are present, or that `visible`/`owner_address` weren't set twice) can diverge from what the protobuf builder ultimately fills in — a parameter/trust-boundary desync analogous to the reported bug, except triggered here by any anonymous client posting `application/x-www-form-urlencoded` to a Wallet HTTP endpoint instead of by a downstream multipart re-encoder.

Note: `framework/src/main/java/org/tron/core/services/http/JsonFormat.java` and its accompanying `JsonFormatEscapeTest` show that the *outbound* (protobuf → JSON) direction of this exact bug class was already hardened (control characters, `\`, and `"` are now escaped in `escapeText`/`escapeBytesSelfType`). [4](#0-3)  That fix does not cover the *inbound* urlencoded-to-JSON conversion path in `Util.getJsonString`, which remains unescaped by the evidence available.

### Impact Explanation
An unauthenticated HTTP API client can smuggle additional JSON keys into the object that is later merged into a Wallet request/contract via `JsonFormat.merge`, potentially overriding or adding fields (e.g., duplicating/overwriting `owner_address`, `visible`, or contract-specific fields) that the endpoint's own validation did not see as present. This falls into the "parameter tampering / validation-bypass" impact class named in the advisory, reachable through any Wallet HTTP endpoint that accepts POST bodies and calls `PostParams.getPostParams` / `Util.getJsonString`.

### Likelihood Explanation
Reachable by any anonymous HTTP API client with no authentication, purely by setting `Content-Type: application/x-www-form-urlencoded` and crafting a value containing `"` and `,`; this matches the "single unprivileged API client" reachability bar required by the scope rules. However, I was unable to retrieve the exact source of `Util.getJsonString` (only its test-observed behavior and call site), so I cannot show the precise line-level implementation confirming whether any partial sanitization exists inside that method.

### Recommendation
Replace the manual string-splitting/quoting in `Util.getJsonString` with a real JSON encoder (e.g., build a `JsonObject`/`Map` and serialize it with Gson/Jackson), or at minimum escape `"`, `\`, and control characters in both keys and values before interpolating them into the JSON template, mirroring the fix already applied to `JsonFormat.escapeText`/`escapeBytesSelfType`.

### Proof of Concept
Send to any Wallet HTTP endpoint that uses `PostParams.getPostParams` (e.g. `/wallet/*`) with:
```
Content-Type: application/x-www-form-urlencoded

owner_address=abc%22%2C%22visible%22%3A%22true
```
This decodes to the value `abc","visible":"true`, so `Util.getJsonString` (per its own test's demonstrated quoting behavior) would emit:
```
{"owner_address":"abc","visible":"true"}
```
injecting a `visible` key that was never intended by the caller, analogous to the `role=admin` part-injection PoC in the advisory.

**Uncertainty note:** I was not able to view the literal source lines of `Util.getJsonString` (only its call site in `PostParams.java` and its behavior implied by `UtilMockTest.testGetJsonString`) due to index/tool limits, so the exact escaping (or lack thereof) inside that method should be verified directly in a full checkout before treating this as confirmed-exploitable.

  public static PostParams getPostParams(HttpServletRequest request) throws Exception {
    String input = request.getReader().lines().collect(Collectors.joining(System.lineSeparator()));
    Util.checkBodySize(input);
    if (APPLICATION_FORM_URLENCODED.getMimeType().equals(request.getContentType())) {
      input = getJsonString(input);
    }
    boolean visible = Util.getVisiblePost(input);
    return new PostParams(input, visible);
  }

  static String escapeText(String input) {
    StringBuilder builder = new StringBuilder(input.length());
    CharacterIterator iter = new StringCharacterIterator(input);
    for (char c = iter.first(); c != CharacterIterator.DONE; c = iter.next()) {
      switch (c) {
        case '\b':
          builder.append("\\b");
          break;
        case '\f':
          builder.append("\\f");
          break;
        case '\n':
          builder.append("\\n");
          break;
        case '\r':
          builder.append("\\r");
          break;
        case '\t':
          builder.append("\\t");
          break;
        case '\\':
          builder.append("\\\\");
          break;
        case '"':
          builder.append("\\\"");
          break;
        default:
          // Check for other control characters
          if (c >= 0x0000 && c <= 0x001F) {
            appendEscapedUnicode(builder, c);
          } else if (Character.isHighSurrogate(c)) {
            // Encode the surrogate pair using 2 six-character sequence (\\uXXXX\\uXXXX)
            appendEscapedUnicode(builder, c);
            c = iter.next();
            if (c == CharacterIterator.DONE) {
              throw new IllegalArgumentException(
                  "invalid unicode string: unexpected high surrogate pair value "
                      + "without corresponding low value.");
            }
            appendEscapedUnicode(builder, c);
          } else {
            // Anything else can be printed as-is
            builder.append(c);
          }
          break;
      }
    }
    return builder.toString();
  }
