### Title
Unbounded attachment body allocation in `GetAttachmentResponse` deserialization allows bounded memory/compute DoS via oversized `/v2/attachments/:hash` response - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`GetAttachmentResponse`'s custom `Deserialize` impl hex-decodes and stores the entire response body into `Attachment::new(bytes)` with no length check against `AtlasConfig.attachments_max_size`, and `StacksHttpResponse::decode_atlas_get_attachment` performs no size validation either. A malicious peer answering a `/v2/attachments/:hash` request can return an oversized hex-encoded payload that gets fully allocated in memory before any `attachments_max_size` enforcement occurs.

### Finding Description
`GetAttachmentResponse::deserialize` reads the JSON string, calls `hex_bytes(&hex_encoded)`, and unconditionally constructs `Attachment::new(bytes)` with no cap on the resulting byte length: [1](#0-0) 

`StacksHttpResponse::decode_atlas_get_attachment` converts the whole HTTP payload to a `serde_json::Value` and deserializes it into `GetAttachmentResponse` via `serde_json::from_value`, again with no size gate: [2](#0-1) 

The only structural bound on the response body comes from `HttpResponseContents::from_ram`'s `assert!(bytes.len() < (u32::MAX as usize))` in `stackslib/src/net/http/response.rs`, which is unrelated to and vastly larger than the configured `attachments_max_size` (default 1 MiB, `ATTACHMENTS_MAX_SIZE_MIN`): [3](#0-2) [4](#0-3) 

`attachments_max_size` is referenced elsewhere (in `download.rs`/`db.rs`/`config/mod.rs`) but not at the decode boundary that allocates the `Vec<u8>` for the attachment content, meaning the size check — if it exists at all in the download pipeline — occurs only after the oversized buffer has already been allocated and decoded from hex.

### Impact Explanation
A malicious remote peer that a node contacts to fetch a missing attachment (via the atlas attachment-download subsystem) can respond to a `GET /v2/attachments/:hash` request with an arbitrarily large hex-encoded JSON string body. The downloading node will hex-decode and allocate the full content into memory (bounded practically by the `u32::MAX` assertion, i.e. up to ~4 GiB per response) before any `attachments_max_size` (1 MiB default) check is applied. This is a bounded compute/memory DoS on the downloading node, repeatable per request/peer, since each malicious response forces a large allocation and hex-decode pass.

### Likelihood Explanation
The attacker only needs to be selected as a peer to serve an attachment (a normal, unprivileged role in the atlas gossip/download protocol) and respond to a legitimately-issued `/v2/attachments/:hash` request with a crafted oversized body. No secrets, signatures, or privileged roles are required — remote reachability is all that's needed, and the attack is repeatable at will.

### Recommendation
Enforce `attachments_max_size` (or a hard protocol-level cap) inside `GetAttachmentResponse::deserialize` before or immediately after `hex_bytes` decoding — reject the payload early if the decoded byte length exceeds the configured/maximum bound — and/or add an explicit length check in `decode_atlas_get_attachment` prior to constructing `Attachment`, so that the oversized buffer is never fully allocated.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` (or a new unit test module) that:
1. Constructs a `serde_json::Value` string whose hex content decodes to, e.g., 200 MiB of bytes (well above `ATTACHMENTS_MAX_SIZE_MIN` of 1 MiB).
2. Builds a `StacksHttpResponse` wrapping that JSON body as the HTTP payload (matching how `try_parse_response`/`get_http_payload_ok` would receive it from the wire).
3. Calls `resp.decode_atlas_get_attachment()` and asserts it succeeds (`Ok(GetAttachmentResponse { attachment })`) with `attachment.content.len() == 200 * 1024 * 1024`, demonstrating that no `attachments_max_size` bound was enforced during decode — the allocation and hex-decode already occurred at line `stackslib/src/net/atlas/mod.rs:74` and `stackslib/src/net/api/getattachment.rs:162` before any downstream size check could run.

    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
