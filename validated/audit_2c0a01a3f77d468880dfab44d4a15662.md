Audit Report

## Title
Silent fund loss when ERC20 asset deposit fails during `transfer_asset`/`transfer_asset_with_surplus` fallback — the `Erc20Credit` imbalance is dropped without any compensating on-chain balance action (File: `polkadot/xcm/xcm-executor/src/traits/transact_asset.rs`, `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor` only implements the `_with_surplus` variants of `TransactAsset` (`withdraw_asset_with_surplus`, `deposit_asset_with_surplus`), leaving the plain `withdraw_asset`/`deposit_asset`/`internal_transfer_asset` methods to fall back to the trait defaults that return `Err(XcmError::Unimplemented)`. The generic best-effort refund logic in both `transfer_asset` and `transfer_asset_with_surplus` (in `polkadot/xcm/xcm-executor/src/traits/transact_asset.rs`) calls the plain `Self::deposit_asset(unspent, from, ...)` to return funds to the sender when the primary deposit fails, and discards the result via `let _ = ...`; because `ERC20Transactor` never implements plain `deposit_asset`, this refund attempt is guaranteed to fail every single time a deposit fails, silently dropping the `Erc20Credit` imbalance while the real ERC20 tokens remain stuck in `TransfersCheckingAccount`.

## Finding Description
`ERC20Transactor` overrides only `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`: [1](#0-0) [2](#0-1)  It does not implement plain `withdraw_asset`, `deposit_asset`, or `internal_transfer_asset`, so those fall back to the trait defaults returning `Err(XcmError::Unimplemented)`: [3](#0-2) [4](#0-3) 

Both fallback transfer paths on the trait discard the result of the recovery deposit with `let _ = Self::deposit_asset(unspent, from, Some(context));`:
- `transfer_asset`: [5](#0-4) 
- `transfer_asset_with_surplus`: [6](#0-5) 

Critically, in `transfer_asset_with_surplus` — the surplus-aware path actually exercised by `ERC20Transactor`'s weight-metered semantics — the refund call still uses the plain (non-surplus) `Self::deposit_asset`, which is unimplemented for `ERC20Transactor` and therefore *always* returns `Err(Unimplemented)` regardless of whether the recipient is blacklisted. This means the refund-to-owner step is not merely fragile against "weird tokens" as the report frames it — for `ERC20Transactor` it is structurally guaranteed to fail unconditionally whenever the primary deposit fails.

Meanwhile `withdraw_asset_with_surplus` performs a real, irreversible ERC20 `transfer` moving the user's tokens into the shared `TransfersCheckingAccount`: [7](#0-6)  If the subsequent `deposit_asset_with_surplus` to the destination fails (as demonstrated by the repository's own `smart_contract_does_not_return_bool_fails` test with non-conforming ERC20 return semantics): [8](#0-7)  the executor's best-effort refund is guaranteed to fail (unimplemented), and its `Ok`/`Err` outcome is discarded. The `Erc20Credit` value carrying the withdrawn amount is dropped with no `Drop`/`handle_dust` recovery, as its own documentation states it performs no runtime-level balance enforcement: [9](#0-8)  The real tokens remain permanently held in `TransfersCheckingAccount` with no on-chain ledger entry recording who is owed what.

## Impact Explanation
This is a permanent user-fund lock reachable by an ordinary unprivileged user submitting an XCM program via `pallet_xcm::execute` (or any instruction path hitting `transfer_asset`/`transfer_asset_with_surplus`) that involves an ERC20 asset matched by `ERC20Transactor`. Any deposit failure to the destination — which the repo's own test suite shows is a realistic occurrence for non-standard ERC20 contracts — combined with the structurally-guaranteed failure of the refund-to-owner step (since plain `deposit_asset` is unimplemented for this transactor) results in real, already-transferred ERC20 value being erased from XCM accounting while remaining stranded in the shared checking account with no recovery mechanism exposed to users.

## Likelihood Explanation
No privileged actor is required. Any user can register or reference a non-conforming ERC20 asset (blacklist-style, non-bool-returning, or gas-hungry) as an `ERC20Transactor`-matched asset and construct an XCM program that withdraws it and attempts a deposit to a destination for which the deposit call fails. Because the refund fallback for `ERC20Transactor` is unconditionally unimplemented (not merely conditionally blocked by a blacklist), this failure mode is trivially and repeatably triggerable, not a narrow edge case.

## Recommendation
- Make the best-effort refund in `transfer_asset`/`transfer_asset_with_surplus` use the same `_with_surplus` variant that was actually used for the primary deposit attempt, so implementations that only provide `_with_surplus` methods (like `ERC20Transactor`) can actually execute the refund.
- Do not silently discard the outcome of the refund attempt; surface a distinct error/event when both the primary deposit and the refund fail, so the stuck value is auditable.
- For `ERC20Transactor`, maintain a persisted per-user/per-asset ledger of amounts held in `TransfersCheckingAccount` rather than relying solely on an in-memory `Erc20Credit` with no enforcement, and expose a recovery/claim extrinsic for reconciling failed transfers.

## Proof of Concept
1. Deploy an ERC20 contract with non-standard `transfer` semantics (e.g., returns a non-bool type, always returns `false`, or reverts for specific recipients), matching the pattern in the existing `smart_contract_does_not_return_bool_fails` test at `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` lines 2021-2073.
2. Register the contract as an XCM-transactable asset matched by `ERC20Matcher` on Asset Hub.
3. As an unprivileged user, submit an XCM program via `pallet_xcm::execute` that withdraws this asset from `from` and attempts to deposit it to a `to` for which the deposit fails.
4. Observe: `withdraw_asset_with_surplus` succeeds, moving real tokens into `TransfersCheckingAccount`; `deposit_asset_with_surplus` to `to` fails; the refund attempt via plain `deposit_asset` fails with `Unimplemented` (confirmable by adding an assertion/trace around `transfer_asset_with_surplus`'s `let _ = Self::deposit_asset(...)` call); the `Erc20Credit` is dropped and no on-chain record of the stuck balance exists, while `TransfersCheckingAccount`'s real ERC20 balance remains elevated by the withdrawn amount indefinitely.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

	fn transfer_asset(
		asset: &Asset,
		from: &Location,
		to: &Location,
		context: &XcmContext,
	) -> Result<Asset, XcmError> {
		match Self::internal_transfer_asset(asset, from, to, context) {
			Err(XcmError::AssetNotFound | XcmError::Unimplemented) => {
				let credit = Self::withdraw_asset(asset, from, Some(context))?;
				Self::deposit_asset(credit, to, Some(context)).map_err(|(unspent, error)| {
					// best effort try to return the assets to original owner
					let _ = Self::deposit_asset(unspent, from, Some(context));
					error
				})?;
				Ok(asset.clone())
			},
			result => result,
		}
	}

	fn transfer_asset_with_surplus(
		asset: &Asset,
		from: &Location,
		to: &Location,
		context: &XcmContext,
	) -> Result<(Asset, Weight), XcmError> {
		match Self::internal_transfer_asset_with_surplus(asset, from, to, context) {
			Err(XcmError::AssetNotFound | XcmError::Unimplemented) => {
				let (credit, withdraw_surplus) =
					Self::withdraw_asset_with_surplus(asset, from, Some(context))?;
				let deposit_surplus = Self::deposit_asset_with_surplus(credit, to, Some(context))
					.map_err(|(unspent, error)| {
					// best effort try to return the assets to original owner
					let _ = Self::deposit_asset(unspent, from, Some(context));
					error
				})?;
				let total_surplus = withdraw_surplus.saturating_add(deposit_surplus);
				Ok((asset.clone(), total_surplus))
			},
			result => result,
		}
	}
