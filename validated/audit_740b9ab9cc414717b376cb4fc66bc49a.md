### Title
`remove_account` fails to clear ReceivedData, PostponedReceiptId, PendingDataCount, PostponedReceipt, PromiseYieldReceipt, PromiseYieldStatus, YieldIdToDataId and DataIdToYieldId - (core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only deletes the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for a deleted account. It never removes the other eight column families listed in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, so those rows survive account deletion and remain permanently in the trie under the now-deleted account's key prefix.

### Finding Description
`remove_account` explicitly removes only four families: [1](#0-0) 
It removes the account, contract code, then iterates `get_raw_prefix_for_access_keys` to delete access keys/gas-key nonces, then iterates `get_raw_prefix_for_contract_data` to delete contract data: [2](#0-1) 

However, `TrieKey::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` declares 12 columns that carry an account id in the key, including `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId`: [3](#0-2) 

These entries are written by an ordinary attacker-reachable flow: an unprivileged account can trigger cross-contract calls with multiple input data dependencies (writing `ReceivedData`/`PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` while some inputs are still pending) or use `promise_yield_create`/`promise_yield_resume` (writing `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) on their own account, and then submit a `DeleteAccount` action (via `action_delete_account` in `runtime/runtime/src/actions.rs`, which calls `remove_account`) before those pending receipts/yields resolve. Because `remove_account` never enumerates or deletes these eight columns, the rows are orphaned in the trie forever, keyed by an account id that no longer exists.

The unit test described in the prompt — writing one entry for each of the 12 columns in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` for a single `account_id`, calling `remove_account`, then iterating the raw trie prefix per column — would fail (find non-empty prefixes) for exactly the eight columns named in the question: `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId`. `Account`, `ContractCode`, `AccessKey`, and `ContractData` would correctly be empty.

No existing check (signature/nonce/access-key/action validation/gas metering/storage staking) prevents this: `DeleteAccount` action validation only concerns beneficiary/self-delete/stake rules, not pending postponed receipts or yields, and there is no code path elsewhere in the runtime that later reaps these orphaned rows once the owning account is gone.

### Impact Explanation
Orphaned trie entries under a deleted account's key prefix cause value/state conservation to break across the account lifecycle: `set(written) - set(cleared)` is non-empty. This is a state-root divergence / accounting-integrity issue — the state root reflects data logically belonging to no live account, inflating state size indefinitely and creating dangling rows that could later be reachable by an account of the same name being recreated (authorization/data confusion), which matches the "state-root divergence risk and later authorization escalation via survivor rows" category cited in the question.

### Likelihood Explanation
Any unprivileged account holder can trigger this by: (1) issuing a cross-contract call to itself with unresolved input data dependencies or (2) calling `promise_yield_create`/timeout paths, and then (3) submitting a `DeleteAccount` action for the same account before those pending items resolve. This requires no special privilege, no validator/node access, and no leaked keys — only the account's own full-access key and normal transaction submission to a public RPC endpoint. It is fully repeatable per account created and deleted this way.

### Recommendation
Extend `remove_account` to enumerate and delete raw-prefix ranges for `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` for the account being deleted, analogous to the existing access-key and contract-data iteration/removal loops, ideally by iterating `TrieKey::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` generically to avoid this class of column-by-column omission in the future.

### Proof of Concept
1. In `core/store/src/utils/mod.rs` test module, construct a `TrieUpdate` and, for one `account_id`, write one entry for each of the 12 `TrieKey` variants matching `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (`Account`, `ContractCode`, `AccessKey`, `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `ContractData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) via `set(...)`.
2. Call `remove_account(&mut state_update, &account_id)`.
3. For each column, build the raw prefix (column byte + account_id bytes, using the appropriate separator per `trie_key_parsers::get_raw_prefix_for_*` helpers or manual construction for the columns lacking a dedicated helper) and iterate the trie for keys with that prefix.
4. Assert the iterator yields no entries for every column.
5. Expected/actual result: the assertion passes for `Account`, `ContractCode`, `AccessKey`, `ContractData`; it fails (non-empty) for `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`, confirming the orphaned-row defect.
