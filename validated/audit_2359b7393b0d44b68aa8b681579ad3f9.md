## Analog Found

### Title
Replay window Check/Decrypt/Update split allows duplicate packets to bypass anti-replay protection under concurrent processing - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` in [1](#0-0)  splits anti-replay enforcement into three separate steps — `window.Check` (lock, check, unlock), `dKey.DecryptDanger` (unlocked), and `window.Update` (lock, mark-seen, unlock) — instead of atomically reserving the message counter before performing the expensive decrypt. This mirrors the M-35 bug class: a security-relevant computation/commit (here, "this counter has been consumed") is finalized only *after* the work that should have gated it (decryption) rather than being committed at the point that should authoritatively decide it, leaving a window where the same value can be processed twice.

### Finding Description
`Decrypt` is invoked from `readOutsidePackets` at [2](#0-1)  which is dispatched per-UDP-queue-goroutine from `listenOut` at [3](#0-2) ; on Linux, `SupportsMultipleReaders()` returns true at [4](#0-3) , so `f.routines > 1` spins up several concurrent `listenOut` goroutines reading from the same underlay socket set, each capable of independently calling `hostinfo.ConnectionState.Decrypt` for the same peer's `ConnectionState`.

Inside `Decrypt`:
```
cs.decryptLock.Lock(); result := cs.window.Check(...); cs.decryptLock.Unlock()   // step 1
out, err = cs.dKey.DecryptDanger(...)                                            // step 2, NOT holding decryptLock
cs.decryptLock.Lock(); result = cs.window.Update(...); cs.decryptLock.Unlock()   // step 3
``` [1](#0-0) 

If two copies of the same ciphertext packet (e.g., a network-level duplicate, or an attacker-injected replay of a previously observed on-wire packet) reach two different queue goroutines before either finishes, both can pass `Check` (the counter hasn't been marked yet), both decrypt successfully (AEAD decryption with a given counter is deterministic and doesn't consume any shared state), and only after both decrypts complete does `Update` run — the second `Update` call will detect the duplicate and return `false`, but by then the plaintext has already been produced and (in `handleOutsideMessagePacket` at [5](#0-4) ) written to the tun device, or for the `header.Message` control path, already advanced `handleHostRoaming`/`connectionManager.In` state at [6](#0-5) . The intended invariant — a message counter is authenticated for delivery *at most once* — is violated because the "is this counter allowed" decision (`Check`) and the "this counter is now consumed" commit (`Update`) are not atomic around the actual decrypt.

This is analogous to M-35: the state that should gate/represent completion of a process (here, "packet N has been delivered") is computed/committed too early relative to the actual authoritative step (the decrypt + delivery), creating a window where duplicate processing is possible.

### Impact Explanation
An attacker who can capture and replay a single legitimate ciphertext UDP packet (no CA-signed certificate needed — this is pure ciphertext duplication, not a new handshake) can, under multi-routine (`routines > 1`) configurations, cause the same encrypted packet to be decrypted and delivered to the tun device more than once, defeating Nebula's AEAD-nonce-based replay protection for that race window. This is a concrete traffic-replay bypass in the data plane.

### Likelihood Explanation
Requires `routines > 1` (multiple UDP reader queues), which is a supported and documented configuration on Linux, and requires the attacker to win a race by delivering (or causing delivery of, e.g. via a network path that duplicates packets, or an on-path replay) two copies of the same packet to different queues within the small window between `Check` and `Update`. This is a genuine, reachable race rather than a purely theoretical one, though it depends on timing and multi-routine deployment.

### Recommendation
Perform the replay-window check-and-reserve as a single atomic operation under `decryptLock` before calling `DecryptDanger`, i.e., merge `Check`+`Update` (or use a single `Reserve(i)`-style call that marks the bit as provisionally consumed) prior to decrypting, and roll back the reservation only if decryption subsequently fails. This closes the TOCTOU window between validating and committing the replay-window state, similar to how M-35 recommends moving the reward commit to the single authoritative point (`sendRewardsToGame`) rather than the earlier, premature point.

### Proof of Concept
1. Configure a Nebula node with `routines: 2` (or more) on Linux so `SupportsMultipleReaders()` is true and multiple `listenOut` goroutines run concurrently (`interface.go` `activate`/`run`, `udp_linux.go` `SupportsMultipleReaders`).
2. Establish a tunnel and capture one legitimate outside ciphertext packet (`header.Message`) destined to this node.
3. Inject the identical captured packet twice, timed so that both underlying UDP `recvmmsg`/queue reads occur essentially simultaneously (e.g., using `recvmmsg` batch delivery or two near-simultaneous `sendto` calls so both land in the same or adjacent batches on different reader queues).
4. Observe that `ConnectionState.Decrypt` is entered twice concurrently for the same `messageCounter`; both `window.Check` calls (locked individually) can return `true` before either `window.Update` executes, so both `DecryptDanger` calls succeed and the plaintext is delivered to the tun device twice (or roaming/connection-manager side effects at `outside.go:134-136` fire twice) despite being the same wire message — demonstrating a replay of a single ciphertext packet bypassing the anti-replay window.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (f *Interface) handleOutsideMessagePacket(hostinfo *HostInfo, out []byte, packet []byte, fwPacket *firewall.Packet, nb []byte, q int, localCache firewall.ConntrackCache) {
	err := newPacket(out, true, fwPacket)
	if err != nil {
		hostinfo.logger(f.l).Warn("Error while validating inbound packet",
			"error", err,
			"packet", out,
		)
		return
	}

	dropReason := f.firewall.Drop(*fwPacket, true, hostinfo, f.pki.GetCAPool(), localCache)
	if dropReason != nil {
		// NOTE: We give `packet` as the `out` here since we already decrypted from it and we don't need it anymore
		// This gives us a buffer to build the reject packet in
		f.rejectOutside(out, hostinfo.ConnectionState, hostinfo, nb, packet, q)
		if f.l.Enabled(context.Background(), slog.LevelDebug) {
			hostinfo.logger(f.l).Debug("dropping inbound packet",
				"fwPacket", fwPacket,
				"reason", dropReason,
			)
		}
		return
	}

	_, err = f.readers[q].Write(out)
	if err != nil {
		f.l.Error("Failed to write to tun", "error", err)
	}
}
