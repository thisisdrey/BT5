### Title
RewardsDistributor credits a full balance-sized reward to unindexed accounts when token index equals `INITIAL_INDEX` — ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`_calculateTokenDelta` falls back to `INITIAL_INDEX` for an account whose stored `accountIndexOf` is `0`, but only when the global token index is **strictly greater** than `INITIAL_INDEX`. When the index is exactly `INITIAL_INDEX` (freshly registered token, or the same block in which `updateTokenSpeed` first set the speed), the stored `0` index is used directly, producing `_deltaIndex = 1e18` and `_tokensDelta = balance * 1e18 / 1e18 = full balance` — the same "compare against a zero-initialized value instead of the correctly initialized state" bug class as the `SurplusGuildMinter` `userStake` report, except here it mints rewards instead of slashing.

### Finding Description
In `_calculateTokenDelta` (contracts/RewardsDistributor.sol:217-231):

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The `> INITIAL_INDEX` comparison is the wrong bound. When `tokenStates[token_].index == INITIAL_INDEX` (set at registration in `_updateTokenSpeed`, contracts/RewardsDistributor.sol:298) and `accountIndexOf[token_][account_] == 0`, `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, so the account is credited `tokensDelta` equal to its entire token balance.

`accountIndexOf` stays `0` for any account whose `updateBeforeMintOrBurn`/`updateBeforeTransfer` ran while `tokenStates[token_].index == 0` (i.e., the token was not yet registered with the distributor — those hooks no-op when `index == 0`, contracts/RewardsDistributor.sol:175-192). Any pre-existing `DepositToken`/`DebtToken` holder therefore has `accountIndexOf == 0` until their first post-registration accrual.

Exploit path: governance (or the `tokenSpeedKeeper` on Vesper-synced deployments) calls `updateTokenSpeed(token, speed)` / `syncTokenSpeed(token)`. In the same block, `_calculateTokenIndex` returns `_deltaTimestamps == 0`, so `_updateTokenIndex` leaves `index == INITIAL_INDEX`. Any unindexed account that calls `claimRewards(account, [token])` — or is touched by `updateBeforeMintOrBurn`/`updateBeforeTransfer` — in that block accrues `tokensDelta = balanceOf(account)`. `claimRewards` is permissionless (`claimRewards(accounts_, tokens_)` takes arbitrary accounts and is only `nonReentrant`), so the attacker can trigger it for themselves or for any victim.

The attack is fully atomic within the registration block: flash-mint `DepositToken` shares (deposit → `updateBeforeMintOrBurn` sets `tokensAccruedOf[attacker] += depositAmount`), call `claimRewards(attacker, [depositToken])`, then withdraw. `DepositToken.deposit`/`withdraw` and `RewardsDistributor.claimRewards` are public, unprivileged entry points; no health check, pause flag, or `SynthContext` restriction applies to `claimRewards`.

### Impact Explanation
Direct theft of unclaimed yield: the attacker extracts reward tokens (`rewardToken.safeTransfer` in `_transferRewardIfEnoughTokens`, contracts/RewardsDistributor.sol:248-255) proportional to their token balance, up to the distributor's full reward balance — draining the reward pool before legitimate accrual begins. With flash leverage via `SmartFarmingManager.leverage` or a flash loan into `deposit`, the claimed amount can far exceed organic accrual. Rewards are finite (only transferred `if amount_ <= _balance`), so a large deposit drains the contract.

### Likelihood Explanation
Requires a window where `tokenStates[token_].index == INITIAL_INDEX` while an unindexed account holds a positive balance — i.e., the block in which a token's speed is first set (or re-set after the index was reset). The deployed configuration keeps `tokenSpeeds` in sync with external reward rates via `tokenSpeedKeeper`/`syncTokenSpeed`, and pre-existing deposit tokens with existing holders get registered after launch — every such registration block is exploitable. An attacker watching the mempool can sandwich the keeper/governor transaction atomically, so no special privilege is needed.

### Recommendation
Change the fallback condition in `_calculateTokenDelta` to also cover the equality case:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = _tokenIndex; // or INITIAL_INDEX
}
```

Setting `_accountIndex = _tokenIndex` (not `INITIAL_INDEX`) when `accountIndexOf == 0` makes a first-time-indexed account start accruing only from the moment it is checkpointed, matching the `GuildToken.lastGaugeLossApplied[gauge][user] = block.timestamp` fix recommended in the analogous report.

### Proof of Concept
Hardhat test sketch (extend `test/RewardDistributor.test.ts`):

```ts
it('drains rewards via unindexed account in registration block', async function () {
  // alice holds deposit-token balance before token is registered
  msdTOKEN1.balanceOf.returns(parseEther('100'))
  msdTOKEN1.totalSupply.returns(parseEther('100'))

  // governor registers the token; index = INITIAL_INDEX, timestamp = now
  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))

  // same block: index still == INITIAL_INDEX, alice's accountIndexOf == 0
  const claimable = await rewardDistributor['claimable(address)'](alice.address)
  // BUG: returns ~100e18 (full balance) instead of 0
  expect(claimable).to.eq(parseEther('100')) // demonstrates the flaw

  // attacker path: flash-deposit -> claimRewards(attacker) -> withdraw
  // drains min(balance, rewardToken.balanceOf(distributor))
})
```

On a fork: call `claimRewards` for any `DepositToken`/`DebtToken` holder whose `accountIndexOf == 0` in the block where `updateTokenSpeed`/`syncTokenSpeed` first initializes `tokenStates[token].index`, then observe `tokensAccruedOf[account] == token.balanceOf(account)` and the reward transfer draining the distributor.
