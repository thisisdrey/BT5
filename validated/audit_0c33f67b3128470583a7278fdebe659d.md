### Title
Unbounded array allocation from attacker-controlled length in TVM precompile ABI decoding (`extractSigArray` / `extractBytesArray` / `extractBytes32Array`) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2016-6250 bug class is "attacker-controlled length field used to size a buffer/array without adequate bounds checking, causing memory corruption/crash." The closest reachable analog in java-tron is not memory corruption (Java arrays are bounds-checked) but the same root cause pattern — trusting a caller-supplied 256-bit word as an array-size argument and using it directly to allocate a Java array (`new byte[len][]`) before any energy/bounds check is applied — inside the `ValidateMultiSign`/`BatchValidateSign` precompiled-contract ABI-decoding helpers.

### Finding Description
`extractSigArray`, `extractBytesArray`, and `extractBytes32Array` in `PrecompiledContracts.java` read an array length directly out of the raw calldata word array: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `int len = words[offset].intValueSafe();` is taken directly from an untrusted `DataWord` (a 256-bit value truncated/clamped by `intValueSafe()`), and is immediately used as the dimension of a new array (`new byte[len][]`) with no upper bound check and no explicit relationship to the energy already charged for the call. `intValueSafe()` can return values up to `Integer.MAX_VALUE`, so a contract can supply a calldata word that decodes to a very large `len`, forcing the node to attempt an allocation of that many array slots before any subsequent index-based read fails.

This mirrors the libarchive bug class: a length value taken from untrusted input is used to size a buffer without validating it against the actual available/reasonable bounds first, only discovering the problem when the code beyond the header is accessed (in this case, an `ArrayIndexOutOfBoundsException` on `words[offset + i + 1]` or an `OutOfMemoryError` on the initial `new byte[len][]` allocation, rather than a native buffer overflow, because the JVM enforces array bounds/heap limits instead of allowing corruption).

### Impact Explanation
An unprivileged contract deployer can invoke the `ValidateMultiSign`/`BatchValidateSign` precompile (called via `STATICCALL`/`CALL` from any contract) with calldata engineered so that `words[offset]` decodes to a huge integer. Depending on the magnitude:
- A moderately large `len` (tens of millions) causes a large but valid allocation attempt (`new byte[len][]`), consuming significant heap and potentially triggering `OutOfMemoryError` in the execution thread, which could destabilize the node process depending on how `OutOfMemoryError` is caught elsewhere in the VM error handling.
- A `len` that exceeds `words.length` causes an `ArrayIndexOutOfBoundsException` when the loop dereferences `words[offset + i + 1]`, which is presumably caught somewhere up the call stack as a generic VM exception (reverting the call), limiting impact to a reverted transaction rather than a node crash — but this could not be fully confirmed from the available context since the calling precompile's exception-handling wrapper was not retrieved before the tool budget was exhausted.

### Likelihood Explanation
Likelihood is uncertain and could not be fully confirmed. It depends on:
1. Whether the energy metering for the `ValidateMultiSign` precompile (`getEnergyForData`) already bounds `len` before `execute()` runs the vulnerable helper — this could not be located within the available search budget.
2. Whether an `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` thrown inside precompile execution is caught generically by the TVM `Program`/`VMActuator` exception handling (which would turn this into a simple revert, not a crash) — again not confirmed from the retrieved code.

Because these two mitigating factors are unverified, this should be treated as a **potential** finding requiring confirmation, not a proven high-severity vulnerability.

### Recommendation
- Add an explicit upper bound check on `len` in `extractSigArray`, `extractBytesArray`, and `extractBytes32Array` (e.g., against `words.length` or a small constant maximum signer/array count) before calling `new byte[len][]`, mirroring the bounds validation that the ISO9660 fix added for filename lengths.
- Verify that `getEnergyForData` for the corresponding precompile charges energy proportional to the claimed array length *before* `execute()` performs the allocation, so that unbounded allocation cannot occur cheaply.
- Confirm that any `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` thrown during precompile execution is safely caught and converted into a contract revert rather than propagating and destabilizing the node.

### Proof of Concept
Conceptual PoC (not executed, pending verification of the caller/energy path):
1. Deploy a contract that calls the `ValidateMultiSign` precompiled contract address via low-level `staticcall`/`call`.
2. Craft calldata so that the ABI-encoded "array length" word at the expected `offset` (consumed by `extractSigArray`/`extractBytesArray`) decodes (via `intValueSafe()`) to a very large value (e.g., `0x7FFFFFFF`) while the rest of the calldata is minimal.
3. Observe whether the call causes the node to attempt a large `byte[][]` allocation (`OutOfMemoryError`) or immediately throws an unhandled exception, and whether this exception propagates beyond the transaction's execution boundary.

Given the incomplete verification of the exception-handling and energy-charging paths, this finding is submitted with **reduced confidence** and should be validated by locating the precompile's `getEnergyForData`/`execute()` wrapper and the top-level TVM exception handler before treating it as a confirmed high-impact issue.
