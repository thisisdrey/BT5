Audit Report

## Title
`harvest_rewards` computes updated pool reward checkpoint but never persists it, causing duplicate reward accrual over the same elapsed period - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` uses a reward-per-token accumulator scheme stored in `Pools::<T>` (`last_update_block`, `reward_per_token_stored`). `stake` and `unstake` correctly recompute this checkpoint via `update_pool_and_staker_rewards` and persist it back with `Pools::<T>::insert`, but `harvest_rewards` computes the same updated `pool_info` locally, uses it only to pay out the staker, and never writes it back into `Pools::<T>` storage.

## Finding Description
`reward_per_token` derives newly accrued rewards from the elapsed blocks since `pool_info.last_update_block`, using `pool_info.reward_per_token_stored` as the base [1](#0-0) . Both `stake` and `unstake` call `Self::update_pool_and_staker_rewards` and then persist the resulting `pool_info` via `Pools::<T>::insert(pool_id, pool_info)` [2](#0-1) [3](#0-2) . In `harvest_rewards`, the identical call produces an updated `pool_info` local binding at line 584-585, which is used only to source `pool_info.reward_asset_id` and `pool_info.account` for the `T::Assets::transfer` payout, and the staker's own state is persisted via `PoolStakers::<T>::insert` — but `pool_info` is never written back to `Pools::<T>` [4](#0-3) . Consequently the pool's `last_update_block`/`reward_per_token_stored` checkpoint stays stale after every `harvest_rewards` call. The next `stake`, `unstake`, or `harvest_rewards` call by any staker recomputes `reward_per_token` over the full elapsed period since that stale checkpoint, re-crediting the block-range reward that was already paid out to the previous harvester.

## Impact Explanation
This breaks the fund-conservation invariant of the reward pool: aggregate claimable rewards across stakers can exceed `reward_rate_per_block * elapsed_blocks`, since the same reward-per-token delta gets disbursed to more than one staker. Because `harvest_rewards` transfers directly from `pool_info.account` via `T::Assets::transfer`, this permits draining the pool's reward-asset reserves beyond the intended schedule and can starve other legitimate stakers' payouts — a duplicate settlement/payout of pooled funds.

## Likelihood Explanation
`harvest_rewards` is a permissionless, frequently-used extrinsic reachable by any staker with no admin or governance precondition. Any pool with more than one active staker where one staker calls `harvest_rewards` before another calls `stake`, `unstake`, or `harvest_rewards` triggers the stale-checkpoint reuse under ordinary sequential block production, with no race condition required.

## Recommendation
In `harvest_rewards`, persist the updated `pool_info` back into `Pools::<T>` immediately after `update_pool_and_staker_rewards`, matching the pattern already used in `stake` and `unstake`:
```rust
let (pool_info, mut staker_info) =
    Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;
Pools::<T>::insert(pool_id, pool_info.clone());
```

## Proof of Concept
1. Create a pool with `reward_rate_per_block = R`; stakers A and B each stake equally, so `total_tokens_staked = X`, `last_update_block = 0`, `reward_per_token_stored = 0`.
2. At block `N`, A calls `harvest_rewards`: internally computes `reward_per_token = R*N*SCALE/X`, pays A their share, updates A's `PoolStakers` entry, but `Pools::<T>` remains at `last_update_block = 0`, `reward_per_token_stored = 0`.
3. At block `N+M`, B calls `harvest_rewards`: reads the stale pool state and recomputes `reward_per_token` over the full `0..N+M` range, double-counting the `0..N` window already paid to A, since B's `reward_per_token_paid` was never advanced for that window either.
4. Total rewards paid to A and B exceed the intended `R*(N+M)` emission, draining the pool's reward-asset account beyond its designed schedule.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
