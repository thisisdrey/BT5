## Title
Order matching in `MarketSellAssetActuator` can be griefed into a full-transaction revert instead of partial-fill, causing exchange DoS - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchOrder` walks the resting maker order book for a token pair and matches a taker order against as many maker orders as needed. It enforces a hard cap `MAX_MATCH_NUM = 20` on the number of maker orders it will process in a single taker transaction, but instead of stopping and persisting the partial fill once the cap is hit, it throws a `ContractValidateException`, which unwinds the whole actuator execution and fails the entire transaction. An unprivileged order placer can populate the order book with more than `MAX_MATCH_NUM` resting orders at the best price for a pair, causing any legitimate taker whose order would need to consume more than 20 of them to have their entire transaction fail, even though a correct, partial match was achievable.

### Finding Description
`matchOrder` iterates maker orders at the best matching price and calls `matchSingleOrder` for each one, incrementing `matchOrderCount`: [1](#0-0) 

When `matchOrderCount` exceeds `MAX_MATCH_NUM`, the loop throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM)` rather than gracefully truncating the match and persisting the partial fill accumulated so far. [2](#0-1) 

This exception is caught in `execute()` alongside `ItemNotFoundException`, `InvalidProtocolBufferException`, and `BalanceInsufficientException`, and is converted into a `ContractExeException`, which propagates out of `execute()` entirely: [3](#0-2) 

Because the actuator's state mutations (`orderStore.put`, `accountStore.put`, balance/asset transfers) are only persisted to the store at the very end of `execute()`, once `ContractExeException` is thrown mid-way, none of the actuator's changes for that transaction are committed — the entire order-matching operation is discarded, not just the excess matches beyond `MAX_MATCH_NUM`. At the block-application layer, the transaction's session is not merged/committed when an exception is thrown: [4](#0-3) 

The result: any taker order that requires matching against more than 20 maker orders at the current best price fails completely, regardless of how much of it could have been legitimately filled. This is the direct java-tron analog of the reported 0x pattern — a batch-style operation (matching against many book entries in one call) that reverts in its entirety when one element of the batch (the 21st match) trips a limit, instead of using a "NoThrow"/partial-success semantic.

An anonymous order placer (any account funded to post `MarketSellAssetContract` orders) fully controls the number and size of resting orders at a given price, since order creation is validated only for balance/format, not order count: [5](#0-4) 

and matching itself is purely mechanical, based on `MarketUtils.priceMatch`/`createPairPriceKey`, which groups same-price orders into a single price-key bucket that `matchOrder` walks front-to-back: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker (any account that can afford the market sell fee and minimal token amounts) can flood the best price level of any token pair on TRON's on-chain exchange with more than 20 tiny resting orders. Any subsequent legitimate taker who tries to sell/buy a larger quantity at that price will have their transaction fail outright with "Too many matches", instead of receiving a partial fill up to the cap and leaving the remainder on the book. This:
- Denies legitimate market participants the ability to trade at the best available price.
- Wastes the taker's transaction fee/bandwidth/energy on a transaction that reverts with no economic effect.
- Can be sustained indefinitely and cheaply by the attacker (small order amounts, replenished as makers get consumed), effectively griefing the on-chain exchange feature for a chosen token pair.

This is a Medium-severity availability/griefing issue against the exchange/market order feature; it does not directly cause fund theft or permanent freezing, but it denies correctly-formed transactions their intended effect and can be weaponized to sabotage specific trading pairs.

### Likelihood Explanation
Likelihood is high: no special privileges are required, the attack only needs enough TRX/TRC-10 balance to post >20 small sell orders at the best price of a targeted pair (`MarketSellAssetContract` is reachable by any account), and the `MAX_MATCH_NUM` boundary is a fixed, publicly known constant (`20`). No front-running or timing precision is required — the attacker simply pre-populates the book.

### Recommendation
- **Short term:** Change the `MAX_MATCH_NUM` overflow handling in `matchOrder` from throwing `ContractValidateException` (which aborts and discards the whole transaction) to stopping the loop and persisting the partial match already performed, leaving the taker's remaining unmatched quantity on the book (consistent with how partial fills are already handled elsewhere in this method, e.g. `saveRemainOrder`).
- **Long term:** Audit other actuators/paths that iterate over externally-influenced collections (order books, batched matches, etc.) within a single all-or-nothing execution, and ensure that hitting an internal safety limit degrades gracefully (partial success) rather than reverting the entire operation, consistent with the spirit of "NoThrow" batch semantics recommended for exchange-style contracts.

### Proof of Concept
1. Attacker account `A` creates 21 `MarketSellAssetContract` orders selling token `X` for token `Y` at the same price (e.g., `sellTokenQuantity=1, buyTokenQuantity=1`), each in a separate transaction. These all land in the same price bucket via `createPairPriceKey`.
2. Victim `V` submits a `MarketSellAssetContract` selling `Y` for `X` at a matching/better price, with a size that would require matching more than 20 of `A`'s resting orders to fully or partially execute meaningfully.
3. `matchOrder` iterates `A`'s 21 orders; on the 21st match, `matchOrderCount > MAX_MATCH_NUM` triggers `ContractValidateException("Too many matches...")`, which is caught in `execute()` and rethrown as `ContractExeException`.
4. `V`'s entire transaction fails: no state changes are persisted (no partial fill, no new order stored), `V` loses transaction fees for a no-op, and must resubmit — repeating the process as long as `A` maintains >20 orders at the best price. [8](#0-7)

  private void matchOrder(MarketOrderCapsule takerCapsule, MarketPrice takerPrice,
      TransactionResultCapsule ret, AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }
      }

  public static byte[] createPairPriceKey(byte[] sellTokenId, byte[] buyTokenId,
      long sellTokenQuantity, long buyTokenQuantity) {

    byte[] sellTokenQuantityBytes;
    byte[] buyTokenQuantityBytes;

    // cal the GCD
    long gcd = findGCD(sellTokenQuantity, buyTokenQuantity);
    if (gcd == 0) {
      sellTokenQuantityBytes = ByteArray.fromLong(sellTokenQuantity);
      buyTokenQuantityBytes = ByteArray.fromLong(buyTokenQuantity);
    } else {
      sellTokenQuantityBytes = ByteArray.fromLong(sellTokenQuantity / gcd);
      buyTokenQuantityBytes = ByteArray.fromLong(buyTokenQuantity / gcd);
    }

    return doCreatePairPriceKey(sellTokenId, buyTokenId,
        sellTokenQuantityBytes, buyTokenQuantityBytes);
  }

  public static boolean priceMatch(MarketPrice takerPrice, MarketPrice makerPrice) {
    // for takerPrice, buyToken is A,sellToken is TRX.
    // price_A_taker * buyQuantity_taker = Price_TRX * sellQuantity_taker
    // ==> price_A_taker = Price_TRX * sellQuantity_taker/buyQuantity_taker

    // price_A_taker must be greater or equal to price_A_maker
    // price_A_taker / price_A_maker >= 1
    // ==> Price_TRX * sellQuantity_taker/buyQuantity_taker >= Price_TRX * buyQuantity_maker/sellQuantity_maker
    // ==> sellQuantity_taker * sellQuantity_maker > buyQuantity_taker * buyQuantity_maker

    return MarketComparator.comparePrice(takerPrice.getBuyTokenQuantity(),
        takerPrice.getSellTokenQuantity(),
        makerPrice.getSellTokenQuantity(), makerPrice.getBuyTokenQuantity()) >= 0;
  }
