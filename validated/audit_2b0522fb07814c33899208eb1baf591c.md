### Title
Permanent freeze of underlying tokens sent to JupLend's `withdraw_intermediary_ata` (`integration_acc_3`) - ([File: programs/marginfi/src/instructions/juplend/withdraw.rs])

### Summary
The stETH→wstETH report describes a class of bug where a token can be transferred directly into an intermediary/wrapper account that has no path to recover any balance beyond what the contract's own logic expects, permanently freezing the excess. The marginfi-v2 JupLend integration has a structurally identical intermediary account: `integration_acc_3`, the "withdraw intermediary ATA" owned by the bank's `liquidity_vault_authority` PDA. Unlike the analogous Drift integration paths, the JupLend withdraw instruction never sweeps this account's *full* balance — it only moves the exact delta produced by the current CPI call, so any tokens sitting in (or later donated to) that ATA outside of that delta can never be extracted by any instruction in the program.

### Finding Description
`juplend_withdraw` reads the pre-CPI balance of `integration_acc_3`, performs the JupLend withdraw CPI, then computes `received_underlying` strictly as the *difference* between post- and pre-CPI balances, and transfers only that delta to the destination: [1](#0-0) 

This is a `checked_sub`-based delta calculation, not a "transfer entire balance" sweep. Contrast this with the Drift integration's equivalent hop accounts, where the code explicitly documents and implements full-balance sweeps to avoid stranding tokens:
- `drift_harvest_reward`'s intermediary token account: `// Transfer entire balance` then `let amount = accessor::amount(&self.intermediary_token_account.to_account_info())?;` [2](#0-1) 
- `drift_claim_bad_debt`'s claimant ATA: "claims tokens ... then transfers the full balance to the global fee wallet's ATA" via `cpi_transfer_to_destination`, which reads `accessor::amount(&self.claimant_token_account...)` and moves the whole thing. [3](#0-2) [4](#0-3) 

`integration_acc_3` (the withdraw intermediary ATA) is a standard SPL/Token-2022 associated token account whose address is derived deterministically as the ATA of `liquidity_vault_authority` for the bank's mint — this is a publicly known, permissionless-to-fund address: [5](#0-4) 

Because it is a normal token account, any unprivileged actor can transfer tokens into it directly (e.g., a plain SPL `Transfer` instruction) at any time — completely outside of any marginfi instruction. The fuzz-test invariant for this path explicitly assumes the account nets to zero over a withdraw, treating it purely as a "hop," which confirms the code never accounts for or reconciles any balance beyond the expected CPI delta: [6](#0-5) [7](#0-6) 

Because the withdraw instruction only ever moves `post_withdraw_intermediary_ata_balance - pre_withdraw_intermediary_ata_balance` to the destination, and no other instruction in the codebase reads or sweeps `integration_acc_3`'s balance (grep across the repo shows it is only ever passed as an account reference in withdraw/init/add_pool contexts, never swept), any token balance sent to this ATA outside a JupLend-withdraw CPI round-trip is permanently unreachable by any on-chain path.

### Impact Explanation
Any tokens landing in `integration_acc_3` beyond the exact CPI-produced delta (whether from a griefing/donation transfer, a rounding/CPI edge case that leaves residual balance, or any future protocol behavior that credits slightly more than expected) become permanently locked — there is no admin or permissionless instruction to reclaim them, unlike the explicit full-balance sweep pattern used for the analogous Drift hop accounts (`harvest_reward`, `claim_bad_debt`). This is a permanent-freeze/fund-loss condition matching the required impact bar (permanent lock/freeze of tokens), reachable by an unprivileged actor (anyone can transfer to a known ATA address) without needing any special permission.

### Likelihood Explanation
Moderate. Triggering it requires only a plain SPL token transfer to a deterministically-derivable ATA address — no interaction with marginfi's instruction set is needed, and no signer/authority checks gate inbound transfers to a standard token account. The condition is a pure "donation"-style griefing vector (locking someone else's funds, e.g. an attacker deliberately stranding tokens to grief protocol accounting, or accidental user error sending funds to the wrong-looking but valid intermediary address) rather than a self-serving exploit for the attacker; likelihood of accidental triggering is realistic given the account has a normal, discoverable SPL token account structure.

### Recommendation
Add a permissionless "sweep" instruction (mirroring `drift_harvest_reward`/`drift_claim_bad_debt`'s pattern) for `integration_acc_3` that reads its full current balance rather than only the CPI-delta, and either credits it to the bank (raising `asset_share_value`, similar to `super_admin_deposit`) or forwards it to the global fee wallet, ensuring no token value sent to this intermediary account can become permanently unrecoverable.

### Proof of Concept
1. Determine `withdraw_intermediary_ata` for a target JupLend bank via `getAssociatedTokenAddressSync(mint, liquidity_vault_authority, true, tokenProgram)` (as done in `deriveJuplendPoolKeys`) [5](#0-4) .
2. As any unprivileged actor holding the underlying mint, submit a standard SPL `Transfer`/`TransferChecked` instruction sending an arbitrary amount `X` directly to that ATA (no marginfi instruction call needed; the account already exists per `juplend_init_position`'s `create_withdraw_intermediary_ata_ix`) [8](#0-7) .
3. Have any user perform a normal `juplend_withdraw` on that bank. Observe that `pre_withdraw_intermediary_ata_balance` now includes the donated `X`, but `received_underlying` is computed strictly as `post - pre` (the JupLend CPI's own credited amount), so only the CPI-derived amount is forwarded to the destination — the donated `X` remains in the ATA [9](#0-8) .
4. Confirm no subsequent instruction (grep across the repo for `integration_acc_3` usage) ever reads or transfers the ATA's full balance — the donated `X` remains stuck indefinitely.

    //
    // NOTE: Unlike Drift (which has reachable dust due to double-rounding in its
    // assets → scaled_balance → assets conversion), this case is UNREACHABLE in JupLend
    // under normal operation because:
    //
    // - JupLend uses single-level math: shares = floor(assets * 1e12 / price)
    // - Minimum shares = 1 (u64 integer, not fractional)
    // - Exchange price >= 1e12 (starts at 1:1, only increases with yield)
    // - Therefore: floor(1 * 1e12 / 1e12) = 1 (always at least 1 underlying)
    //
    // Drift's dust is reachable because it uses multi-step rounding:
    // 1. assets → scaled_balance (floor + variable precision per token)
    // 2. scaled_balance + 1 (round up for safety)
    // 3. scaled_balance → assets (floor again)
    // This cascading rounding can produce 0 tokens from small positions.
    //
    // This defensive code exists for potential edge cases:
    // - Socialized loss reducing JupLend's exchange price below 1e12
    // - Future protocol changes affecting share/price invariants
    //
    // If we can guarantee that JupLend's exchange price never drops below 1e12, this branch is dead code.
    let received_underlying = if withdraw_all && token_amount == 0 {
        0
    } else {
        // CPI withdraw: burns fTokens and credits underlying into withdraw intermediary ATA.
        ctx.accounts
            .cpi_juplend_withdraw(token_amount, authority_bump)?;

        let post_withdraw_intermediary_ata_balance =
            accessor::amount(&ctx.accounts.integration_acc_3.to_account_info())?;
        let post_f_token_balance =
            accessor::amount(&ctx.accounts.integration_acc_2.to_account_info())?;

        let received_underlying = post_withdraw_intermediary_ata_balance
            .checked_sub(pre_withdraw_intermediary_ata_balance)
            .ok_or_else(|| error!(MarginfiError::MathError))?;
        require_eq!(
            received_underlying,
            token_amount,
            MarginfiError::JuplendWithdrawFailed
        );

        let burned_shares = pre_f_token_balance
            .checked_sub(post_f_token_balance)
            .ok_or_else(|| error!(MarginfiError::MathError))?;
        require_eq!(
            burned_shares,
            shares_to_burn,
            MarginfiError::JuplendWithdrawFailed
        );

        ctx.accounts

        let program = self.token_program.to_account_info();

            to: self.destination_token_account.to_account_info(),

        // Transfer entire balance
        let amount = accessor::amount(&self.intermediary_token_account.to_account_info())?;
        transfer_checked(cpi_ctx, amount, decimals)?;

/// Claim a Drift bad-debt portal allocation for a Drift bank.
///
/// The bad-debt portal's merkle leaf must use this bank's `liquidity_vault_authority` as the
/// claimant. The distributor requires claimed tokens to land in a token account owned by that
/// claimant, so this instruction claims into the authority's ATA, then transfers the full balance
/// to the global fee wallet's ATA.
pub fn drift_claim_bad_debt<'info>(
    ctx: Context<'info, DriftClaimBadDebt<'info>>,
    amount: u64,
    proof: Vec<[u8; 32]>,
) -> MarginfiResult {
    ctx.accounts.create_claimant_token_account()?;
    ctx.accounts.create_destination_token_account()?;
    ctx.accounts.prefund_claim_status()?;
    let pre_claim_balance = ctx.accounts.claimant_token_balance()?;
    ctx.accounts.cpi_new_claim(amount, proof)?;
    let post_claim_balance = ctx.accounts.claimant_token_balance()?;
    let received_amount = post_claim_balance
        .checked_sub(pre_claim_balance)
        .ok_or_else(|| error!(MarginfiError::InternalLogicError))?;
    let swept_amount = ctx.accounts.cpi_transfer_to_destination()?;
    ctx.accounts
        .emit_claim_event(amount, received_amount, swept_amount)?;
    Ok(())
}

    fn cpi_transfer_to_destination(&self) -> MarginfiResult<u64> {
        let amount = accessor::amount(&self.claimant_token_account.to_account_info())?;
        if amount == 0 {
            return Ok(0);
        }

        let accounts = Transfer {
            from: self.claimant_token_account.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
        };

        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(self.token_program.key(), accounts, signer_seeds);

        token::transfer(cpi_ctx, amount)?;
        Ok(amount)
    }

### Juplend integration (`invariants/juplend/*`)

- **Deposit (success)**: user decreases; fToken vault increases; marginfi liquidity vault behaves as a hop (net-zero movement when applicable), with `amount == 0` treated as no movement.
- **Deposit (failure)**: user / marginfi vault / fToken vault remain unchanged.
- **Withdraw (success)**: user increases; fToken vault decreases; withdraw intermediary ATA is a hop (net-zero), with `withdraw_all` handled explicitly.
- **Withdraw (failure)**: user / withdraw intermediary ATA / marginfi vault / fToken vault remain unchanged.
