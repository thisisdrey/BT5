## Analysis

The Mochi bug is fundamentally: **an automatic, non-attacker-controlled asset swap executes with no caller-supplied minimum-output bound, allowing value extraction via pool manipulation.** Searching the AMM-related code paths in this repo, the actual public extrinsics of `pallet-asset-conversion` (`swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`) are correctly protected — they require and enforce explicit `amount_out_min`/`amount_in_max` parameters [1](#0-0) . The `SwapAssetAdapter` used for asset-fee payments also protects the swap by computing an exact quote up front and treating any deviation as a hard failure rather than a silent shortfall [2](#0-1) .

However, `SwapFirstAssetTrader` — the `WeightTrader` used by the XCM executor to pay/refund XCM execution fees by swapping through `pallet-asset-conversion`'s `SwapCredit` interface — has exactly this gap in its **refund** path.

### Title
Unprotected AMM swap with no `amount_out_min` in `SwapFirstAssetTrader::refund_weight` enables MEV/sandwich value extraction from XCM fee refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader::refund_weight` swaps the unused portion of collected `Target` fee credit back into the user's original fee-paying asset via `SwapCredit::swap_exact_tokens_for_tokens`, passing `None` for `amount_out_min` — i.e. no slippage floor at all.

### Finding Description
`buy_weight` swaps the user's asset into the `Target` fee asset using `swap_tokens_for_exact_tokens`, where the exact output (`fee`) is fixed and the user-supplied `credit_in` itself caps the input, so a failed/expensive swap simply errors out rather than silently overcharging [3](#0-2) .

`refund_weight`, however, does the reverse swap — turning excess `Target` credit back into the original asset for the user — using `swap_exact_tokens_for_tokens` with an explicit `None` in place of `amount_out_min`: [4](#0-3) 

Because the input amount (`refund_amount`) is fixed and there is no floor on the output, whatever the AMM pool's instantaneous price happens to be at the moment this swap executes is accepted unconditionally. If the pool reserves for `Target`/`refund_swap_asset` have been pushed away from fair value by other trades landing in the same block/queue window (the same “MEV searcher” pattern the Mochi report describes), the user's refund is settled at a worse price with no protection, and the difference is captured by whoever moved the pool.

### Impact Explanation
This directly parallels the reported bug class: a public, automatically-triggered swap of user value with zero minimum-received guarantee. Every XCM message that pays fees in a non-`Target` asset and receives any refund (e.g. from `RefundSurplus`/unused weight) goes through this exact code path, so the exposure is systemic across all XCM traffic using `SwapFirstAssetTrader`, not a one-off. The result is silent, unbounded fund loss for XCM senders whenever the underlying `pallet-asset-conversion` pool can be moved between the fee-charge and the refund.

### Likelihood Explanation
`SwapFirstAssetTrader` is a general-purpose, reusable `WeightTrader` intended for parachain XCM configs that need to price fees via `pallet-asset-conversion`; the pools it swaps against are the same public, permissionless liquidity pools anyone can trade in. No privileged actor, relayer, or validator misbehavior is required — any user (or a bot economically incentivized like the "MEV searchers" cited in the original report) trading against the pool around the time the message is processed can shift the price the refund settles at, exactly mirroring the missing-`minReceivedAmount` pattern from the referenced finding.

### Recommendation
Compute an expected/fair output for the refund swap (e.g. via `QuotePrice::quote_price_exact_tokens_for_tokens`, which the trait bound already provides) and pass a derived `amount_out_min` (with an acceptable tolerance) instead of `None` to `SwapCredit::swap_exact_tokens_for_tokens`, mirroring the protection already used elsewhere for swap-based fee payment (`SwapAssetAdapter`).

### Proof of Concept
1. Deploy/parametrize a parachain runtime that uses `SwapFirstAssetTrader<Target, SwapCredit=pallet_asset_conversion, ...>` as its `WeightTrader`, with a live `Target`/`AssetX` pool in `pallet-asset-conversion`.
2. A user sends an XCM message with `BuyExecution` using `AssetX`, over-provisioning weight so a non-trivial refund is expected on `RefundSurplus`.
3. `buy_weight` runs, swapping some `AssetX` into `Target` via `swap_tokens_for_exact_tokens` — this part is bounded by the user's `credit_in`.
4. Before/while `refund_weight` executes later in the same block/queue processing window, an attacker executes trades against the `Target`/`AssetX` pool in `pallet-asset-conversion` to depress the `AssetX` output per unit of `Target`.
5. `refund_weight` calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target, AssetX], refund, None)` — with `None` as `amount_out_min`, the swap accepts whatever `AssetX` amount the manipulated pool state produces [5](#0-4) .
6. The user receives a refund worth less than fair value; the attacker profits from the price impact on the reverse trade, reproducing the exact "no slippage control ⇒ sandwiched" outcome from the Mochi report.
