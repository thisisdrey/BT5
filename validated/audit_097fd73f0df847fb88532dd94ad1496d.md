### Title
Unbounded repeatable `skip_deduct` exemption in `promise_batch_action_function_call_weight` mints yoctoNEAR via unreconciled `subsidized_amount` - ([File: runtime/near-vm-runner/src/logic/logic.rs])

### Summary
The `skip_deduct` exemption at [1](#0-0)  only checks `amount == 1 yoctoNEAR`, the `one_yocto_on_promise` config flag, and that `current_account_balance` is currently zero — it does not cap how many times this can happen within a single execution, nor does it ever decrement any bounded allowance. Because the exemption branch explicitly bypasses `deduct_balance` and instead only increments `subsidized_amount`, `current_account_balance` never changes across repeated calls, so the same zero-balance precondition is satisfied on every iteration of a loop, allowing `subsidized_amount` to grow unboundedly (up to `max_number_promises` times) while real balance is never touched.

### Finding Description
`promise_batch_action_function_call_weight` computes `skip_deduct` purely from local/session state that the exemption itself never mutates: [2](#0-1) 

- In the `skip_deduct == true` branch, only `self.result_state.subsidized_amount` is incremented; `self.result_state.current_account_balance` is left untouched.
- In the `else` branch, `deduct_balance(amount)` is called, which would normally subtract from `current_account_balance` and fail with `NotEnoughBalance` if the account can't cover it.

Since `current_account_balance.is_zero()` is unaffected by taking the `skip_deduct` path, a contract with a genuinely zero balance can call `promise_batch_action_function_call_weight` repeatedly within a single `FunctionCall` execution (bounded only by `max_number_promises` and gas), each time attaching exactly `1` yoctoNEAR. Every call satisfies the same three conditions and takes the exemption branch again, so `subsidized_amount` accumulates `1` yoctoNEAR per call with no reconciling debit anywhere in this function. Each iteration also calls `self.ext.append_action_function_call_weight(... amount ...)` at [3](#0-2) , which creates a real outgoing receipt carrying that 1 yoctoNEAR to the receiver — i.e., real value is dispatched to receipts while the sender's tracked balance and the "subsidy" ledger never reflect a bounded, singular exemption.

Existing checks (nonce/signature/access-key permission, gas metering, `max_number_promises`, `prepay_gas`) do not address this because they don't limit repetition of the *specific* zero-balance/1-yocto condition; they only bound the number of promises/actions and gas, which still allows many repeated exploitations of the exemption within one execution.

### Impact Explanation
This is a token-inflation category issue: `subsidized_amount` is meant to represent a bounded, per-account/per-call accounting adjustment reconciled 1:1 against `total_balance_burnt` in `chain/chain/src/runtime/mod.rs`. If the exemption can be triggered `max_number_promises` times per execution instead of being a single, capped subsidy, the aggregate `subsidized_amount` can diverge from the intended single-use exemption, and each hit dispatches a real 1-yoctoNEAR transfer in an outgoing receipt without any corresponding balance debit. Repeated across many receipts/transactions, this is effectively minting yoctoNEAR-denominated value out of a zero-balance account, which is a real value-conservation violation.

### Likelihood Explanation
The precondition is inexpensive and fully attacker-controlled: an ordinary unprivileged user only needs to deploy a contract with zero balance and issue a `FunctionCall` that loops calling `promise_batch_action_function_call_weight` with `amount = 1` up to `max_number_promises` times, paying only for gas of the loop and action-dispatch fees. No validator/node/protocol privilege is required. The exploit is deterministic and fully repeatable across executions/transactions, limited only by `max_number_promises` and available gas per call, meaning the attacker can amplify by issuing many transactions.

### Recommendation
Bound the `skip_deduct` exemption so it can only be taken once per execution (or per account, or per receipt) rather than being re-derived from state (`current_account_balance.is_zero()`) that the exemption itself does not change. For example, track a one-time "has used zero-balance one-yocto exemption" flag in `result_state` that is consumed (set to used) the first time `skip_deduct` triggers, and require `!already_used_exemption` as an additional guard condition before allowing `skip_deduct`, or alternatively deduct from a strictly capped `subsidized_amount` budget derived from protocol parameters and enforce that per-execution cap explicitly rather than relying solely on the balance-is-zero check.

### Proof of Concept
Integration test (runtime apply-path, e.g. in `runtime/runtime/src/tests/apply.rs` style):
1. Deploy a contract with account balance = 0.
2. Submit one `FunctionCall` transaction whose wasm body loops `max_number_promises` times, each iteration calling `promise_batch_action_function_call_weight` with `amount_ptr` pointing to `1u128` (1 yoctoNEAR), targeting a fresh promise/receipt each time.
3. Apply the transaction through the normal runtime apply path (as chain/chain/src/runtime/mod.rs would call it).
4. Assert that `current_account_balance` of the sender is still `0` after execution (never deducted).
5. Assert that `result_state.subsidized_amount` equals `max_number_promises * 1` yoctoNEAR, not `1` yoctoNEAR (i.e., the exemption fired on every iteration, not just once).
6. Assert that `total_balance_burnt`/protocol balance reconciliation in `chain/chain/src/runtime/mod.rs` does not account for this multiplied `subsidized_amount`, demonstrating a conservation mismatch of `(max_number_promises - 1)` yoctoNEAR.

        // when the contract has zero balance. This lets deterministic accounts
        // call functions like ft_transfer_call that require an attached deposit
        // without needing to be seeded with balance first.
        let skip_deduct = amount == Balance::from_yoctonear(1)
            && self.config.one_yocto_on_promise
            && self.result_state.current_account_balance.is_zero();
        if skip_deduct {
            self.result_state.subsidized_amount = self
                .result_state
                .subsidized_amount
                .checked_add(amount)
                .expect("subsidized_amount overflow");
        } else {
            self.result_state.deduct_balance(amount)?;
        }
