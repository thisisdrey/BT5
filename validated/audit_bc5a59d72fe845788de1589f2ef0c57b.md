### Title
Attacker can saturate a victim's per-account token list with dust deposits/transfers, blocking new deposits and debt issuance (DoS) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Metronome tracks, per account, which `DepositToken`s and `DebtToken`s the account has a non-zero balance in, and enforces a shared hard cap of `MAX_TOKENS_PER_USER = 30` via the `onlyIfAdditionWillNotReachMaxTokens` modifier. Any unprivileged EOA can force entries into a victim's lists by depositing dust `onBehalfOf` the victim (`DepositToken.deposit(amount_, onBehalfOf_)`) or by transferring dust `msdTOKEN`s to the victim. Once the victim's combined list reaches 30 entries, any action that would add a new token — depositing a collateral type the victim doesn't already hold, or issuing a synthetic asset whose debt token the victim doesn't already hold — reverts with `UserReachedMaxTokens`. This is a griefing-based denial of service analogous to the reported bug class (unprivileged-induced DoS of protocol functionality).

### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30` and `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount + depositTokensOfAccount` lengths reach the cap.
- `Pool.addToDepositTokensOfAccount(account_)` / `addToDebtTokensOfAccount(account_)` are called by the token contracts, not by the user, whenever a balance goes 0 → >0.
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` on first mint; `deposit(amount_, onBehalfOf_)` lets anyone mint to an arbitrary `onBehalfOf_`, so an attacker can add a deposit-token entry to any victim without consent.
- `DepositToken._transfer` likewise calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance is zero, so plain dust transfers to the victim also consume slots.
- `DebtToken` performs the symmetric `addToDebtTokensOfAccount` on mint (debt is only minted to the issuer's own account, so the attack vector here is primarily deposit-token slots plus the victim's own existing debt tokens counting toward the same cap).
- No modifier stops this: `deposit`/`transfer` are public, unprivileged, and do not require recipient consent. There is no way for a victim to reject inbound tokens.

### Impact Explanation
While the cap is saturated, the victim cannot:
- deposit a collateral type they do not already hold (`DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount` reverts atomically),
- issue a synthetic asset whose `DebtToken` is not already in their list (`DebtToken.issue`/`_mint` path reverts),
- receive `msdTOKEN`s of a new type (transfers revert on the recipient-add).

A liquidator whose list is saturated and who does not already hold the seized `DepositToken` will also have `seize` revert, marginally raising the cost/friction of liquidations (a fresh liquidator address is a workaround). The victim can self-recover by transferring the dust out (each outbound transfer that zeroes a balance removes the entry via `removeFromDepositTokensOfAccount`), but only for the unlocked portion, and the attacker can refill slots cheaply and repeatedly, causing temporary freezing of the victim's ability to open positions. During a price crash this directly delays topping-up with a new collateral type, which can turn a recoverable position into a liquidatable one.

### Likelihood Explanation
Requires only an EOA and dust amounts of whitelisted underlyings (or existing `msdTOKEN` balances). Cost per slot is a trivial token amount plus gas; the pool can have up to 30 deposit tokens and each contributes one slot. No privileged role, oracle manipulation, or governance action is needed. Impact is bounded (temporary, self-recoverable at gas cost, and cannot freeze already-held balances or withdrawals), so severity is moderate/low.

### Recommendation
- Do not count attacker-forced positions against the cap: either drop the global per-account cap or charge slots only for tokens the user explicitly opted into (e.g., only on `deposit` initiated via the user's own `SynthContext` sender, not arbitrary `onBehalfOf`/`transfer` recipients).
- Alternatively, allow users to force-remove entries (e.g., a `Pool.ejectToken(account, token)` callable by the account that transfers/burns dust) so recovery is one transaction regardless of attacker refill.

### Proof of Concept
Hardhat sketch (against deployed `Pool`/`DepositToken` set):

```ts
// attacker fills victim's deposit-token slots
for (const dt of depositTokens.slice(0, 30)) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.approve(dt.address, 1);
  // deposit 1 wei of underlying on behalf of the victim
  await dt.deposit(1, victim.address); // adds dt to victim's list
}

// victim already holds debtTokens too; once combined length == 30:
const newCollateral = depositTokens[30]; // a deposit token victim doesn't hold
await expect(newCollateral.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// same for issuing a new synth
await expect(newDebtToken.connect(victim).issue(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim must spend gas transferring each dust token out to recover:
await depositTokens[0].connect(victim).transfer(attacker.address, 1); // frees 1 slot
```
