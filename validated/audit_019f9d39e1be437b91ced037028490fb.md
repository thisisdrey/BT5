### Title
Unvalidated length parameter causes ArrayIndexOutOfBounds/NegativeArraySize crash in TVM precompiled-contract argument parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array` and `extractBytesArray` read an attacker-controlled length/offset value directly out of the `DataWord[] words` array parsed from the calldata sent to a precompiled contract, and then use it to index further into the same array without validating it against the actual array bounds. This mirrors the CVE-2023-49100 bug class: a caller-supplied register/parameter value is used as an index/loop bound without sufficient bounds validation before it is dereferenced, leading to an out-of-bounds read (or, in the Java case, an unhandled `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`) inside a privileged execution context (here, the TVM/EL3-equivalent, the node's transaction execution engine).

### Finding Description
`extractBytes32Array` computes `len` from `words[offset].intValueSafe()` (fully attacker controlled via calldata to a `TriggerSmartContract`/precompiled call) and then loops `for (int i = 0; i < len; i++) { bytes32Array[i] = words[offset + i + 1].getData(); }` with no check that `offset + i + 1 < words.length`: [1](#0-0) 

`extractBytesArray` performs a partial guard (`offset > words.length - 1`) but the inner loop still reads `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` for `i` up to an attacker-supplied `len`, again without validating these indices against `words.length`: [2](#0-1) 

This is directly analogous to the TF-A SDEI bug: `sdei_interrupt_bind` takes an attacker-controlled register value and passes it, with insufficient validation, into `plat_ic_get_interrupt_type`/`plat_ic_is_sgi`, causing an out-of-bounds read in the privileged EL3 context. Here, a value taken from user-supplied calldata (`words[offset]`) is used, with insufficient validation, as a loop bound/index into a Java array inside the node's privileged VM execution context, which can throw an uncaught `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` (if `len` is negative) during execution of a precompiled contract call.

Both helper methods are internal to `PrecompiledContracts.java`; they are used to parse `DataWord[]` argument arrays for precompiled-contract implementations (e.g., multi-signature validation precompiles) that accept variable-length arrays supplied directly by a smart-contract caller via `CALL`/`STATICCALL` to a precompiled address, i.e., input fully controlled by an unprivileged contract-calling transaction.

### Impact Explanation
If reachable with an out-of-range `len`/`offset` combination that is not otherwise caught by the specific precompile's own validation, the resulting Java runtime exception (`ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`) would propagate up through TVM execution. Depending on how the calling precompile and `Program`/`VM` layer handle it, this can crash the transaction execution path or cause the node to fail to process the block/transaction, which — consistent with the CVE's "crash TF-A" outcome — is a denial-of-service impact against the executing node.

### Likelihood Explanation
Reachability depends on which precompile actually calls these two helpers with attacker-controlled offsets/lengths without additional bounds validation before the call. I was not able to confirm, within the available tool budget, which specific `PrecompiledContract.execute()` implementation invokes `extractBytes32Array`/`extractBytesArray`, nor whether that call site pre-validates `len`/`offset` against `words.length` before calling these helpers (the earlier partial check in `extractBytesArray` suggests some validation awareness exists, but it is incomplete). Without confirming the exact call site and its guards, I cannot assert with confidence that a real, exploitable OOB/crash primitive is reachable end-to-end from a signed transaction.

### Recommendation
Add explicit bounds checks in `extractBytes32Array` and `extractBytesArray` verifying `len >= 0` and `offset + len < words.length` (and similarly for `bytesOffset`/`bytesLen` derived indices) before performing any array reads, throwing a well-defined VM exception (e.g., `Program.Exception`) instead of allowing an unchecked Java runtime exception to propagate.

### Proof of Concept
Not able to be constructed with confidence: the exact precompiled-contract call site that invokes `extractBytes32Array`/`extractBytesArray` with attacker-supplied `words`/`offset` was not located in the available search results, so I cannot confirm without further investigation (e.g., a live Devin session with full file access) that this path is reachable end-to-end from a transaction without additional length validation performed by the caller.
