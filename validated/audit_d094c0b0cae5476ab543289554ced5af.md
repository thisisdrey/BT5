Found the strongest analog: `UnDelegateResourceActuator.execute` / `UnDelegateResourceProcessor.execute`, which computes the receiver's resource-usage transfer as a *fair-share proportion* of the requested `unDelegateBalance`, but under the "acquired < requested" edge case it zeroes out the receiver's acquired balance entirely instead of recomputing that proportion against the amount actually available — the same root-cause pattern as the `Vault.withdraw` bug (computing a share from a *requested* amount when the *actual* available/transferred amount is smaller, without re-deriving the share).

### Title
Unbounded resource-usage transfer / windowSize desync in `UnDelegateResourceActuator` when receiver's acquired delegated balance is less than the requested undelegate amount - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.execute` (and its TVM-native twin `UnDelegateResourceProcessor.execute`) computes `transferUsage` — the portion of the receiver's bandwidth/energy usage window that must move back to the owner — as a ratio of `unDelegateBalance` (the amount requested by the caller) over the receiver's *total* frozen balance for that resource. This is exactly analogous to the `Vault.withdraw` bug: a proportional "share" is derived from the full requested amount, but the code branches into a degenerate special case (`receiverCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth() < unDelegateBalance`) where the *actual* balance being moved is different (it just zeroes the receiver's whole acquired balance) — yet the surrounding usage-transfer math is never adjusted to reflect that the real "fair share" no longer matches `unDelegateBalance`.

### Finding Description
In `UnDelegateResourceActuator.execute()`: [1](#0-0) 

```
if (receiverCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth() < unDelegateBalance) {
  // A TVM contract suicide, re-create will produce this situation
  receiverCapsule.setAcquiredDelegatedFrozenV2BalanceForBandwidth(0);
} else {

  long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
      * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
  transferUsage = (long) (receiverCapsule.getNetUsage()
      * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
  transferUsage = min(unDelegateMaxUsage, transferUsage);

  receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(-unDelegateBalance);
}
```

In the "insufficient acquired balance" branch, the receiver's entire `AcquiredDelegatedFrozenV2BalanceForBandwidth` is reset to `0` — meaning the *actual* amount effectively "un-delegated" from the receiver's perspective can be far less than `unDelegateBalance` (it is whatever was still tracked as acquired, which could be `0` up to `unDelegateBalance - 1`). However:
- `transferUsage` in that branch remains `0`, so none of the receiver's `netUsage`/`energyUsage` bandwidth-usage window is transferred back to the owner, even though the owner's side of the ledger (`unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)`, `ownerCapsule.addDelegatedFrozenV2BalanceForBandwidth(-unDelegateBalance)`, `ownerCapsule.addFrozenBalanceForBandwidthV2(unDelegateBalance)`) is always adjusted by the *full requested* `unDelegateBalance`, not the smaller amount actually reclaimed from the receiver: [2](#0-1) 

This mirrors the Vault bug structurally: the "shares" (here, `transferUsage`, computed as a proportion of the requested amount over the receiver's total delegated balance) are derived from the caller's *requested* value, while the actual quantity moved from the receiver (their acquired balance) can be smaller and is handled via an unrelated fallback (`setAcquiredDelegatedFrozenV2BalanceForBandwidth(0)`) instead of recomputing the proportional share against what was truly available. The owner's account is unconditionally credited/debited by the full `unDelegateBalance` in both branches regardless of what actually happened on the receiver side.

### Impact Explanation
This can result in accounting desync between an owner's and receiver's resource windows: the owner reclaims `unDelegateBalance` worth of frozen balance (and it becomes usable, unlocked TRX resource) even in cases where the receiver's tracked "acquired" balance was smaller than what is being subtracted from the owner-side delegated ledger. Because `netUsage`/`energyUsage` accounting underlies the network's resource/bandwidth allowance system, a persistent mismatch between delegated-balance bookkeeping and actual usage-window transfers can let a resource delegator effectively re-inflate their own resource limit disproportionately to what was truly freed from the receiver, degrading the integrity of the bandwidth/energy accounting invariant (total weight vs. actual usage) enforced elsewhere in the codebase.

### Likelihood Explanation
The degenerate branch is explicitly documented in the code comment as reachable "A TVM contract suicide, re-create will produce this situation" — i.e., a receiver contract can be made to self-destruct and be re-deployed at the same address by a normal, unprivileged transaction sequence (`SUICIDE` opcode + `CREATE2`), which is fully reachable by any transaction broadcaster/contract deployer without special privilege. An owner can then call `UnDelegateResourceContract` for a `receiverAddress` whose acquired balance has been reset by the suicide/re-create sequence, deterministically triggering this code path.

### Recommendation
Recompute `transferUsage` (and, more importantly, the amount actually deducted from the owner's `DelegatedFrozenV2Balance`/added back to `FrozenBalanceV2`) based on the *actual* amount reclaimed from the receiver rather than unconditionally using the full requested `unDelegateBalance` in the insufficient-balance branch. If only a partial (or zero) amount can be verified as retrievable from the receiver's ledger, the owner-side state changes and any associated usage-window transfer should be scaled to that verified amount, analogous to recomputing `_shares` from the actual `_amount` withdrawn in the `Vault.withdraw` fix.

### Proof of Concept
1. Owner delegates bandwidth resource to a contract `receiver` via `DelegateResourceContract`, so `receiverCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth() == delegateBalance` and `ownerCapsule.getDelegatedFrozenV2BalanceForBandwidth() == delegateBalance`.
2. The `receiver` contract self-destructs (`SUICIDE`) and is re-created at the same address (a normal TVM operation reachable by any contract deployer), resetting its account state so `getAcquiredDelegatedFrozenV2BalanceForBandwidth()` becomes `0` (as documented in the code comment) while the owner's `DelegatedFrozenV2BalanceForBandwidth` ledger entry for that receiver still reflects `delegateBalance`.
3. Owner submits `UnDelegateResourceContract` for `receiverAddress` requesting `unDelegateBalance == delegateBalance`.
4. In `execute()`, since `receiverCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth() (0) < unDelegateBalance`, the code takes the `setAcquiredDelegatedFrozenV2BalanceForBandwidth(0)` branch (no-op on an already-zero value, `transferUsage = 0`), yet the owner-side code unconditionally executes `ownerCapsule.addDelegatedFrozenV2BalanceForBandwidth(-unDelegateBalance)` and `ownerCapsule.addFrozenBalanceForBandwidthV2(unDelegateBalance)`, fully crediting the owner as if a genuine, verified `unDelegateBalance` worth of resource was reclaimed from the receiver — even though the receiver's ledger already showed nothing outstanding to reclaim.

Note: I was not able to run this scenario end-to-end in the index (no direct execution environment available here), so the exact numeric consequence (e.g., whether this can be chained to exceed `TotalNetWeight` bounds) should be validated with a live/test-node reproduction; this write-up is based on static analysis of the actuator logic and its existing test comments, which explicitly acknowledge the "acquired < requested" scenario as reachable via ordinary contract suicide/re-create.
