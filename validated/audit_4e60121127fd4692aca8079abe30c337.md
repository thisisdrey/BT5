## Title
Priority-floor computed from unresolved packet bytes can undercount address-lookup-table write locks, letting low-priority transactions evade the sigverify drop filter - (File: `core/src/sigverify.rs`, `core/src/transaction_priority.rs`)

### Summary
The external report's bug class is: a "declared/intended" value (`SwapParams`) is not cross-checked against the value actually decoded from raw calldata that is forwarded to execution, allowing the two to diverge and be treated inconsistently. The closest reachable analog in agave is the `SchedulerPriorityFloor` mechanism: sigverify computes a transaction's priority from **raw, unresolved packet bytes** (a fast, pre-verification estimate) and compares it against a floor published by the banking-stage scheduler, which computes priority from the **fully resolved, typed transaction**. These two computations are only asserted to agree by a unit test comment, not enforced at runtime, and they use different account-key/cost inputs for v0 transactions that use address lookup tables.

### Finding Description
`core/src/sigverify.rs::apply_priority_floor_to_batch` calls `calculate_priority_from_bytes(bank, data)` on the raw packet bytes, ahead of signature verification and address-lookup-table resolution, to decide whether to drop a packet as being at-or-below the scheduler's published floor: [1](#0-0) 

`calculate_priority_from_bytes` (in `core/src/transaction_priority.rs`) builds a `SanitizedTransactionView` directly from packet bytes and computes cost/priority via `calculate_priority_and_cost`: [2](#0-1) 

The actual/authoritative priority used by the scheduler for buffering and eviction (`SaturationState`/`get_min_max_priority`) is computed from the fully sanitized, resolved transaction (post signature-verification, post address-lookup-table resolution) via the same `calculate_priority_and_cost` function, but fed a `TransactionMeta + SVMStaticMessage` whose `static_account_keys()`/write-lock accounting reflects resolved addresses: [3](#0-2) [4](#0-3) 

The code comment and test `floor_priority_from_bytes_matches_typed_path` explicitly document that this equivalence is an assumption the code relies on, not something structurally guaranteed: [5](#0-4) 

For a v0 transaction that uses address lookup tables, `SanitizedTransactionView` (bytes path, pre-verification) only has access to the static account keys embedded in the packet — the dynamically loaded write-locked accounts referenced via lookup tables are not resolved at this stage. `CostModel`'s `num_requested_write_locks`/write-lock cost accounting therefore undercounts the true cost `C` for such a transaction in the bytes-path calculation, while priority is `P = R / (1 + C)`, i.e., **priority is inversely proportional to cost** as documented in the function itself: [6](#0-5) 

An attacker who crafts a v0 transaction with a modest fee/compute-unit-price but many additional writable accounts resolved only via address lookup tables can produce a bytes-path priority estimate that is inflated relative to the true, fully-resolved priority the scheduler would assign. This lets such packets survive `apply_priority_floor_to_batch`'s at-or-below-floor drop, even though the scheduler-side (typed-path) priority — the actual value used for admission/eviction ordering — would have placed them below the floor and had them dropped.

### Impact Explanation
The `SchedulerPriorityFloor` mechanism exists specifically to protect the validator under saturation: it lets the banking-stage scheduler tell sigverify to cheaply discard low-value transactions **before** paying the cost of Ed25519 signature verification, which is the expensive step. If the bytes-path estimate systematically overestimates priority relative to the typed-path value for a class of transactions (ALT-heavy, low real priority), an attacker can flood the validator during saturation with such transactions that should be dropped pre-verification but instead consume signature-verification CPU cycles — a form of QoS evasion / underpriced pre-fee work against the exact mechanism designed to prevent it.

### Likelihood Explanation
This requires the validator to already be under buffer saturation (the floor is only non-zero once `SaturationState` detects saturation), and requires constructing v0 transactions with address-lookup-table-resolved writable accounts to inflate the priority estimate relative to true cost. This is achievable by any unprivileged transaction sender (no special validator/operator role needed) using ordinary v0 transactions and lookup tables, which are a standard, permissionless feature.

### Recommendation
- Make the bytes-path priority estimate conservative (a lower bound) relative to the typed-path value rather than merely asserting they match, e.g., by accounting for the maximum possible write-lock cost contributable by unresolved address lookup tables (from `num_lookup_tables()`/table entries in the view) when computing cost, so that `apply_priority_floor_to_batch` cannot systematically overestimate priority for such packets.
- Alternatively, cheaply resolve (or worst-case-cost estimate) address-lookup-table content before applying the priority floor, or exclude ALT-using packets from bypassing the floor filter.
- Turn the `floor_priority_from_bytes_matches_typed_path` test assumption into an enforced invariant (e.g., assert or clamp) rather than a documentation-only guarantee, matching the report's core recommendation to validate a "declared" fast-path value against the authoritative typed value before trusting it for a security-relevant gate.

### Proof of Concept
1. Wait for (or induce, via a burst of transactions) validator saturation so `SchedulerPriorityFloor` becomes non-zero (see `SaturationState::update`/`publish_floor` in `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs`).
2. Construct a v0 transaction with a small `compute_unit_price`/fee (true priority below the current floor) but referencing many writable accounts solely through one or more address lookup tables (not in the static account keys carried in the packet), such that `SanitizedTransactionView` (used by `calculate_priority_from_bytes`) cannot see these accounts and computes a cost `C_bytes` far lower than the true cost `C_typed` the scheduler would later compute after lookup-table resolution.
3. Send this transaction while the floor is active. Because `P = R / (1 + C_bytes)` is computed with the understated cost, the packet's bytes-path priority can exceed the floor even though its true (typed-path) priority would not.
4. `apply_priority_floor_to_batch` (`core/src/sigverify.rs:413-439`) keeps the packet instead of discarding it, so it proceeds to full Ed25519 signature verification — CPU work the floor mechanism was meant to avoid for genuinely low-priority transactions.
5. Verifying the actual magnitude of the discrepancy (i.e., confirming `num_write_locks`/`CostModel` inputs differ meaningfully between the `SanitizedTransactionView` pre-ALT-resolution path and the fully resolved typed path for v0+ALT transactions) requires deeper tracing through `cost-model/src/cost_model.rs` and `runtime-transaction/src/runtime_transaction/transaction_view.rs` than was retrievable from the indexed snippets available here; this should be validated directly in a Devin session with full file access before treating the magnitude of exploitation as confirmed.

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}

    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}

    /// Update the scheduler priority floor.
    ///
    /// Semantics: when the retained scheduler buffer is nearly full, drop
    /// arrivals that are at-or-below the current queue-min priority, i.e. no
    /// better than what the bounded scheduler candidate set would evict.
    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {
        let buffer_size = self.container.buffer_size();
        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);
        let priority_floor = if saturated {
            self.container
                .get_min_max_priority()
                .map_or(0, |(min, _)| min)
        } else {
            0
        };

        self.saturation_state.publish_floor(priority_floor);
    }
