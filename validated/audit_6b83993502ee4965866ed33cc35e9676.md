### Title
TOCTOU race between `throttle_stream`'s `stream_count.load()` check and the deferred `stream_count.fetch_add` in `on_stream_accepted` allows concurrent unstaked streams to bypass per-interval throttling - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`throttle_stream` reads `stream_counter.stream_count.load(Ordering::Relaxed)` and compares it to `max_streams_per_throttling_interval` to decide whether to sleep, but the corresponding increment (`stream_count.fetch_add(1, ...)`) happens later, in a separate call (`on_stream_accepted` in `streamer/src/nonblocking/swqos.rs`), not atomically with the check. If many uni-streams are opened concurrently on the same connection, all of them can observe the same stale (low) `stream_count` value before any of their increments land, letting all of them skip the sleep-based backoff in the same throttling interval.

### Finding Description
In `streamer/src/nonblocking/stream_throttle.rs`, `throttle_stream` (lines 233-271) does:
```
let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
if streams_read_in_throttle_interval >= max_streams_per_throttling_interval { ... sleep ... }
```
This is only invoked from `on_new_stream` in `streamer/src/nonblocking/swqos.rs` (lines 496-516). The actual increment of `stream_count` happens in a *different* method, `on_stream_accepted` (lines 445-454), which is called separately (presumably right after a stream is accepted, before `on_new_stream`'s throttle check runs for that stream, per the normal per-stream handling flow). Because these are two separate atomic operations with no shared lock or CAS between "read count" and "increment count," concurrently-processed streams on the same connection (each spawned/awaited independently, as is typical for QUIC uni-stream handling) can all execute `stream_count.load()` before any of their `fetch_add`s complete, i.e., a classic check-then-act race. As a result, a burst of concurrently opened streams can all pass the `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` check simultaneously, exceeding the intended per-interval cap by up to the degree of concurrency, bounded only by the connection's configured `max_concurrent_uni_streams` (`QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS = 128` for unstaked peers, set in `cache_new_connection`/`compute_max_allowed_uni_streams_with_rtt` in `streamer/src/nonblocking/swqos.rs`).

For unstaked connections this cap (`max_unstaked_load_in_throttling_window = MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000`, e.g. 20 in the existing `test_max_streams_for_unstaked_connection` test) is normally meant to bound stream admission per 100ms window per connection, but a burst of concurrently opened streams (up to the per-connection QUIC max, 128) can all bypass the sleep in the same window.

### Impact Explanation
This is a real, in-repo verifiable race condition (check-then-act without synchronization) that allows an unstaked attacker to exceed the intended per-connection/per-interval stream-admission throttle by a bounded multiplier (up to the connection's max concurrent uni-stream limit, e.g. ~128 vs. an intended ~20 for unstaked peers), feeding more transaction-bytes into the packet path per interval than the throttle design intends. This maps to the "QoS evasion" bounty category (rate-limit bypass), not to unbounded resource exhaustion, since the burst is still bounded by `max_concurrent_uni_streams` set via `connection.set_max_concurrent_uni_streams` and by the connection/table limits (`max_connections_per_unstaked_peer`, `max_unstaked_connections`). It increases sigverify/dedup/ingress work disproportionately for a short window but does not itself cause unbounded memory growth, a panic, or a consensus-breaking effect.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: an unstaked remote client opening one QUIC connection to the TPU port and issuing many uni-streams concurrently (up to the per-connection uni-stream cap) is standard client behavior requiring no special privilege. The race window (between `load()` in `throttle_stream` and the later `fetch_add` in `on_stream_accepted`) is small but real, and repeatable — every burst of concurrently-processed streams on a connection is susceptible, not a one-off race requiring precise timing. This makes it a reliably-exploitable "bypass a soft window," not a probabilistic edge case.

### Recommendation
Make the check-and-increment atomic: replace the separate `load()` (in `throttle_stream`) and `fetch_add()` (in `on_stream_accepted`) with a single atomic `fetch_add` performed in `throttle_stream` itself, and use the *previous* value returned by `fetch_add` to decide whether to sleep. E.g.:
```rust
let prev = stream_counter.stream_count.fetch_add(1, Ordering::Relaxed);
if prev >= max_streams_per_throttling_interval { /* sleep */ }
```
This closes the TOCTOU gap because the increment and comparison become one atomic step, so no two concurrent streams can observe the same "pre-increment" value.

### Proof of Concept
Add an integration test in `streamer/src/nonblocking/stream_throttle.rs`'s `test` module that:
1. Constructs a `ConnectionStreamCounter` and a fixed `max_streams_per_throttling_interval` (e.g., 5).
2. Spawns `N` (e.g., 50) concurrent Tokio tasks that all call `throttle_stream(...)` at roughly the same instant (synchronized via a barrier), each simulating a stream, followed immediately by the equivalent of `on_stream_accepted`'s `stream_count.fetch_add(1, Ordering::Relaxed)` (mirroring current production call ordering — check first, increment after, in two separate steps).
3. Assert that the number of tasks that returned from `throttle_stream` *without* sleeping (i.e., did not hit the `sleep(throttle_duration).await` branch) exceeds `max_streams_per_throttling_interval` plus a small slack — demonstrating that far more than the configured cap were admitted within one `STREAM_THROTTLING_INTERVAL`.
4. As a regression check for the fix, re-run the same test using the proposed atomic `fetch_add`-based `throttle_stream` and assert the admitted count is bounded by `max_streams_per_throttling_interval` (+1 for the boundary check), confirming the race is closed.
