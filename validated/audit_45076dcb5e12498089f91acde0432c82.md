### Title
Unvalidated attacker-controlled length used for array allocation in TVM precompile ABI decoding leads to node OOM crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` helper methods in `PrecompiledContracts.java`, used to decode dynamic array parameters passed to the `BatchValidateSign` and `ValidateMultiSign` precompiled contracts, read a 32-byte "length" word directly from attacker-supplied call data and use it unchecked to size a Java array allocation (`new byte[len][]`). This mirrors the root cause of CVE-2018-10540: an untrusted size field taken from input data is used to drive a memory allocation without validating that it is sane relative to the actual available data, allowing a small, cheaply-crafted input to trigger a disproportionate/invalid allocation attempt. [1](#0-0) [2](#0-1) 

### Finding Description
`extractBytes32Array(DataWord[] words, int offset)` computes `int len = words[offset].intValueSafe();` and immediately allocates `new byte[len][]` with no upper-bound check on `len` and, unlike its sibling methods, without even a bound check that `offset` is inside `words.length`: [1](#0-0) 

`extractBytesArray` and `extractSigArray` do check `offset > words.length - 1`, but they perform the same unchecked-length allocation pattern (`int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];`) before any per-element bound checking occurs: [3](#0-2) 

Since `words` is derived from raw call data supplied to a precompiled contract invocation (via a `CALL`/`STATICCALL` TVM opcode targeting the `BatchValidateSign` or `ValidateMultiSign` precompile addresses), an attacker fully controls the 32-byte word at `offset`, and therefore fully controls `len` — up to `Integer.MAX_VALUE` via `DataWord.intValueSafe()`. This is directly analogous to WavPack's `ParseWave64HeaderConfig`, where a small header-controlled chunk-size field is used for a `malloc` without validating it against the actual data size, producing an invalid/undersized allocation and downstream out-of-bounds behavior. Here the analogous defect is: the size used to allocate `byte[len][]` is never checked against the remaining `words.length`, the actual number of encoded array elements, or any sane upper bound before the JVM attempts to satisfy the allocation.

### Impact Explanation
Because `len` can be set to a huge value (e.g., near `Integer.MAX_VALUE`) using a tiny, cheap transaction that merely calls the precompile with one crafted word, the JVM will attempt to allocate a correspondingly huge `Object[]`/`byte[][]` array. This throws `OutOfMemoryError` (or, for large-but-negative interpretations, `NegativeArraySizeException`) inside TVM execution. TVM/precompile execution happens synchronously in the block-application/transaction-validation path of every full node that processes the transaction or block containing it, so this can crash or destabilize the node process (`OutOfMemoryError` is not reliably contained by normal Java exception handling and can corrupt shared VM/heap state), satisfying the "node crash or halt" impact bar for reachable transaction-triggered bugs.

### Likelihood Explanation
Likelihood is high for reachability: `BatchValidateSign` and `ValidateMultiSign` are TVM precompiled contracts invocable by any contract deployer or caller through a standard `CALL` to the fixed precompile address — no special privilege, SR/witness role, or specific state is required, only a single signed transaction invoking the precompile with attacker-chosen call data. The exploit input is tiny (a handful of ABI words), making construction trivial once the vulnerable length field is identified. However, the actual crash depends on the JVM/heap configuration (heap size, GC behavior on huge allocation attempts) — some environments may just throw a catchable `OutOfMemoryError` that is absorbed by the VM's execution wrapper rather than truly halting the node, so I was not able to fully verify from the indexed code paths whether callers of `execute()` wrap and swallow this specific error in `BatchValidateSign`/`ValidateMultiSign` execute paths (their full method bodies were not fully retrieved before the tool budget ran out).

### Recommendation
Add explicit upper-bound validation on `len` (and on `offset + len` versus `words.length`) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating the result arrays — e.g., reject if `len < 0`, `len > words.length - offset - 1`, or `len` exceeds a small sane maximum consistent with the maximum signature/array count these precompiles are meant to support. Add the missing `offset > words.length - 1` bound check to `extractBytes32Array` to match its sibling methods.

### Proof of Concept
1. Deploy or use any contract that performs a `CALL` (or `STATICCALL`) to the `BatchValidateSign` precompile address with ABI-encoded calldata where the dynamic-array "length" word (the word read by `extractBytes32Array`/`extractSigArray` at the expected `offset`) is set to a very large value such as `0x7FFFFFFF`.
2. Broadcast the transaction invoking this contract call.
3. During TVM execution, `words[offset].intValueSafe()` returns the attacker-chosen large value, and `new byte[len][]` triggers a huge allocation attempt inside the node's transaction-processing thread. [4](#0-3) 

Note: I could not fully trace `BatchValidateSign.execute()`/`ValidateMultiSign.execute()` bodies within the available tool budget to confirm whether any prior length sanity check exists before these helper calls (index search only surfaced the helper methods themselves and test files referencing them); this should be verified directly in the full file before treating the PoC as final.
