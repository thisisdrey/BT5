### Title
Server-Side Request Forgery and untrusted archive extraction via `CreateRepositoryFromSnapshot` RPC's `HttpUrl`/`ResolvedAddress` fields - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
The `CreateRepositoryFromSnapshot` RPC lets a caller supply an arbitrary `HttpUrl`, `HttpAuth`, and `ResolvedAddress` in the request, which Gitaly uses to fetch and then blindly pipe into `tar -C <path> -xvf -` without validating the contents of the response or authenticating the destination beyond basic IP parsing. This mirrors the DeFi report's "no input validation" bug class: an externally supplied, attacker-influenced field (`HttpUrl`) is trusted and acted upon without sufficient checks before performing a privileged operation (fetching a resource and extracting it as if it were the caller).

### Finding Description
`untar` builds an HTTP request directly from `in.GetHttpUrl()` and issues it with the caller-controlled `HttpAuth` header [1](#0-0) . The `HttpUrl` value is not restricted to any allow-list of destinations, protocols, or ports beyond a scheme check for `http`/`https` and a decorative "resolved address" is-a-valid-IP check [2](#0-1) ; this lets a caller point Gitaly's HTTP client at internal-only endpoints (metadata services, internal admin APIs, other cluster nodes) or attach the caller-controlled `HttpAuth` header to arbitrary hosts, disclosing that credential.

The HTTP response body is piped, unvalidated, into a raw `tar -xvf -` invocation targeting the repository's on-disk path [3](#0-2) . Unlike `internal/gitaly/service/repository/replicate.go`'s `extractTarToDirectory`, which explicitly validates each tar entry's target path against the extraction root and rejects absolute/escaping symlinks and hard links [4](#0-3) , this code path delegates extraction entirely to the system `tar` binary with no equivalent path-traversal or symlink-escape checks. The code's own comment acknowledges this: *"NOTE: The received archive is trusted a lot. Before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening."* [5](#0-4) 

### Impact Explanation
An ordinary user able to invoke `CreateRepositoryFromSnapshot` (a MUTATOR RPC creating a new repository) can direct Gitaly's outbound HTTP client toward arbitrary internal/external hosts (SSRF), leak the supplied `HttpAuth` bearer/credential to any destination reachable from the Gitaly host, and—because the fetched archive is extracted with an unhardened `tar -xvf -` invocation—potentially write files outside the intended repository path if the archive contains path-traversal entries or crafted symlinks/hardlinks, corrupting or escaping the storage root. This aligns with "concrete storage escape" and "SSRF or credential disclosure" categories called out in the validation criteria.

### Likelihood Explanation
Reaching this code only requires calling the `CreateRepositoryFromSnapshot` RPC with attacker-chosen `HttpUrl`/`HttpAuth`/`ResolvedAddress` values, which is exactly the kind of "crafted RPC field" from an ordinary caller described in scope. No privileged actor, leaked token, or malicious peer is required — a standard gRPC client with access to the RepositoryService can trigger it directly.

### Recommendation
- Restrict `HttpUrl` to trusted, allow-listed hosts/schemes for snapshot fetches, or require the caller to already be a trusted internal peer for this RPC (this RPC is documented as intended for peer-to-peer/DR flows, not arbitrary external endpoints).
- Replace the shell-out `tar -xvf -` extraction with the same hardened Go-based extraction routine already used in `replicate.go` (`extractTarToDirectory`), which enforces path containment and rejects unsafe symlinks/hardlinks.
- Avoid forwarding caller-supplied `HttpAuth` values to arbitrary destinations; scope credential usage to validated targets only.
- Add SSRF protections (deny private/link-local ranges unless explicitly required, validate `ResolvedAddress` against DNS-rebinding-safe policies).

### Proof of Concept
1. As an ordinary client with RepositoryService access, call `CreateRepositoryFromSnapshot` with:
   - `Repository`: a new repository path.
   - `HttpUrl`: pointed at an internal service (e.g., `http://169.254.169.254/latest/meta-data/` or an internal admin endpoint) or attacker-controlled server.
   - `HttpAuth`: any secret value to observe it being sent to the attacker-controlled server, confirming credential disclosure.
2. Optionally, have the attacker-controlled server respond with a tar stream containing entries with `../` traversal or symlink targets outside the target directory, and observe whether `tar -xvf -` writes outside the intended repository path (this depends on the specific `tar` binary's own protections, which Gitaly does not itself enforce here, unlike the validated `extractTarToDirectory` path in `replicate.go`).

**Note on confidence**: I was not able to fully verify runtime behavior of the underlying `tar` binary's own protections (many `tar` implementations do reject absolute paths/`..` by default), so the concrete "storage escape" portion of impact depends on tar version/flags in the Gitaly build environment; the SSRF/credential-disclosure component of this finding is confirmed directly from the code shown above.

func newResolvedHTTPClient(httpAddress, resolvedAddress string) (*http.Client, error) {
	url, err := url.ParseRequestURI(httpAddress)
	if err != nil {
		return nil, structerr.NewInvalidArgument("parsing HTTP URL: %w", err)
	}

	port := url.Port()
	if port == "" {
		switch url.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		default:
			return nil, structerr.NewInvalidArgument("unsupported schema %q", url.Scheme)
		}
	}

	// Sanity-check whether the resolved address is a valid IP address.
	if net.ParseIP(resolvedAddress) == nil {
		return nil, structerr.NewInvalidArgument("invalid resolved address %q", resolvedAddress)
	}

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}
