## Analysis

The reported bug class (accumulated-length loop combined with unpredictable-cost external calls, executed serially within a single completing operation, leading to resource-limit DoS) maps to Gitaly's non-atomic `proc-receive` hook handling path.

### Title
Unbounded per-reference custom-hook loop in non-atomic `proc-receive` hook processing can exhaust RPC resources - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
When a client pushes with `proc-receive` in non-atomic mode, Gitaly iterates over every reference update contained in the push and, for each one, spawns the `update` custom hook (an arbitrary, admin-installed external script) and performs a Git reference commit, all within a single RPC handler invocation. The number of loop iterations is directly controlled by how many reference updates an ordinary pushing user includes in one push, and each iteration's cost is unbounded because it depends on external, unpredictable custom-hook execution.

### Finding Description
`procReceiveHook` branches on `handler.Atomic()`. In the non-atomic branch it loops once per reference update returned by `handler.ReferenceUpdates()`: [1](#0-0) 

For every single update, `receivePackReferenceUpdates` is invoked, which calls out to `hookManager.UpdateHook(...)` — executing the repository's custom `update` hook script — before committing that one reference via `updater.Commit()`: [2](#0-1) 

This is structurally analogous to the reported issue: the iteration count of the "heaviest" loop scales with a client-controlled quantity (number of pushed reference updates, analogous to the number of processed burn requests), and each iteration invokes an external, unpredictable-cost operation (a custom hook script, analogous to the external token contract calls) inside the same completing call. Because each iteration also performs its own `updater.Commit()`, references are durably updated to disk incrementally as the loop progresses — there is no way to "un-apply" already-committed reference updates if the RPC subsequently times out or is killed partway through the remaining updates, mirroring the "no way to un-process requests" property of the original finding.

### Impact Explanation
A single push containing a very large number of reference updates (git allows pushing many refs in one invocation) forces Gitaly's `HookService.ReceivePack`/`ProcReceiveHook` goroutine to serially execute one external custom-hook process and one ref-update commit per reference. Because custom hooks are administrator-supplied but their execution time is not bounded by Gitaly, this loop's total runtime is attacker-influenceable and can be driven arbitrarily long, risking RPC/goroutine timeouts, connection resource exhaustion, and partially-applied reference state that cannot be cleanly rolled back mid-loop.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) `proc-receive` non-atomic mode to be configured/used and (b) a repository with a custom `update` hook installed, both of which are legitimate, supported configurations reachable via an ordinary authorized push containing many reference updates — no privileged access or malicious peer/node is required.

### Recommendation
Bound the number of reference updates processed per `proc-receive` invocation loop (e.g., cap `handler.ReferenceUpdates()` length or chunk them with periodic progress/deadline checks), and consider making the total custom-hook execution budget for a single push configurable and enforced, rather than letting it grow unbounded with the size of client-controlled input.

### Proof of Concept
1. Enable `proc-receive` (non-atomic) on a repository and install a custom `update` hook that performs non-trivial work (or simply sleeps).
2. As an ordinary authorized user, push a single request containing a very large number of branch/reference updates.
3. Gitaly's `procReceiveHook` loop at [3](#0-2)  executes the custom hook and a ref commit for every update serially, causing the RPC to run long enough to hit gRPC/transaction timeouts while having already committed a subset of the reference updates that cannot be rolled back mid-flight.
