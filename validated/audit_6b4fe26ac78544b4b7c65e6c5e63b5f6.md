### Title
Multi-sig transaction signatures are validated against the current, mutable `Permission` fetched by `permission_id` rather than a value pinned at signing time, allowing front-running of `AccountPermissionUpdateContract` to bypass an already-collected multi-sig threshold - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
The external report describes a class of bug where a privileged actor (pool manager) approves/acts on mutable data (`proposalBid`/`metadata`) supplied by an unprivileged user, and that data can be front-run/changed between the time the approver decides to act and the time the approval transaction actually lands on-chain, causing the approver to unknowingly bless different data than intended. The structurally equivalent condition in java-tron is that multi-sig `Transaction`s reference a `Permission` only by `permission_id`, and both signature collection (`addSign`) and final execution-time validation (`validateSignature`) re-fetch the *live* `Permission` object (keys/weights/threshold) from `AccountStore` at each step rather than binding to the specific permission content that existed when the co-signers actually signed.

### Finding Description
`TransactionCapsule.validateSignature` looks up `Permission permission = account.getPermissionById(permissionId);` using only the `permissionId` from the transaction, and then calls `checkWeight(permission, ...)` against whatever `Permission` is currently stored in `AccountStore` at execution/broadcast time: [1](#0-0) 

The same pattern is used earlier, when signers add their signature via `addSign`, which also re-reads the current `Permission` by id: [2](#0-1) 

`AccountPermissionUpdateActuator` allows an account (with sufficient Owner-permission weight) to change any of `owner`, `witness`, or up to 8 `active` permissions — including which keys are present and their weights/threshold — and this update takes effect immediately upon execution: [3](#0-2) 

Because the id-to-content binding of a `Permission` is mutable, a multi-sig transaction that a set of co-signers have already collected sufficient weight for (e.g., 3-of-5 under `permission_id=2`) is *not* validated against the permission definition the signers actually agreed to sign under. If an `AccountPermissionUpdateContract` altering `permission_id=2` (e.g., changing keys/weights/threshold) is broadcast and processed by `Manager.pushTransaction`/`processTransaction` before the pending multi-sig transaction is packed into a block, the pending transaction's signatures will be re-checked by `checkWeight` against the *new* permission content: [4](#0-3) 

This is the direct analog of the reported bug class: an approver (here, the chain's signature-weight check acting as the "approval" gate) trusts data (`Permission` content addressed by a stable id) that an interested party can mutate via a normal, unprivileged-reachable transaction (`AccountPermissionUpdateContract`) between the moment co-signers commit to a set of signatures and the moment that set is actually evaluated on-chain.

### Impact Explanation
Depending on how the permission is altered, this TOCTOU condition can be leveraged for:
- **Griefing/denial of a legitimate multi-sig operation**: an account holder can invalidate a transaction that other co-signers already signed off on (e.g., raise the threshold or drop a required key) right before it lands, forcing wasted signing rounds and potential loss of time-sensitive operations.
- **Unauthorized bypass of the agreed threshold**: if the permission is changed to lower the threshold or substitute keys while a signature set collected under the old definition is still pending, the effective authorization semantics the other signers believed they were enforcing no longer hold at the moment of on-chain evaluation, since `checkWeight`/`validateSignature` only look at the live permission, not the one signers reviewed.

The severity is tempered because typically only a party who already holds sufficient Owner-permission weight can execute `AccountPermissionUpdateContract`, so a fully external, zero-permission attacker cannot trigger this by itself; but *within* a legitimate multi-party wallet, a single member with owner-level editing rights can unilaterally undermine the wallet's threshold guarantees for any pending active-permission transaction, which is the same "malicious peer with legitimate but limited standing exploits pending state" pattern described in the report.

### Likelihood Explanation
Exploitation requires: (1) visibility into a pending multi-sig transaction (observable via mempool/`pushTransactionQueue` or `getTransactionSignWeight`/`getTransactionApprovedList` endpoints that expose in-progress approvals), and (2) the attacker already possessing enough Owner-permission weight to submit `AccountPermissionUpdateContract` for the same account. This is a narrower reach than the original Gitcoin bug (which needed no special permission at all), so likelihood is lower, but it is trivially reachable by any account participant with Owner rights broadcasting a single ordinary transaction, with no witness/SR/network-level compromise needed.

### Recommendation
Bind multi-sig authorization to the specific `Permission` content that was in effect and referenced at signing time rather than re-resolving purely by `permission_id`, e.g., by including/hashing the permission's key set, weights, and threshold in the signed payload, or by invalidating/re-validating in-flight transactions whenever the referenced permission is updated (comparable to the report's recommendation to lock/commit data or time-lock changes).

### Proof of Concept
1. Account `A` has an `Active` permission (`permission_id = 2`) with keys `{K1: w=2, K2: w=2, K3: w=2}` and `threshold = 4` (i.e., 2-of-3 by weight).
2. `K1` and `K2` sign a `TransferContract` moving funds out of `A`, reaching weight 4 (meets threshold). This transaction is broadcast and sits in the pending/mempool state.
3. The holder of Owner-permission for `A` (which may be `K3`, or `A` itself) submits `AccountPermissionUpdateContract` updating `permission_id = 2` to `{K3: w=10}`, `threshold = 10` — instantly making the previous signature set (`K1`,`K2`) invalid, per `AccountPermissionUpdateActuator.execute` / `updatePermissions`: [5](#0-4) .
4. When the pending transfer transaction from step 2 is finally processed, `Manager.processTransaction` calls `trxCap.validateSignature(...)`, which re-fetches the now-changed `Permission` for id `2` and calls `checkWeight` against it: [1](#0-0)  — `K1`/`K2` no longer meet the (now-different) weight/threshold requirement and the previously-valid, already-collected multi-sig transaction fails/rejects unexpectedly, even though it met the wallet's rules at signing time. Conversely, an attacker could instead *lower* the threshold and swap in their own key so a transaction they alone control (with a different `permission_id`/signature set) is accepted where multiple co-signers were originally required — undermining the wallet's intended multi-party control.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public void addSign(byte[] privateKey, AccountStore accountStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = this.transaction.getRawData().getContract(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwnerAddress();
    AccountCapsule account = accountStore.get(owner);
    if (account == null) {
      throw new PermissionException("Account is not exist!");
    }
    Permission permission = account.getPermissionById(permissionId);
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    List<ByteString> approveList = new ArrayList<>();
    SignInterface cryptoEngine = SignUtils
        .fromPrivate(privateKey, CommonParameter.getInstance().isECKeyCryptoEngine());
    byte[] address = cryptoEngine.getAddress();
    if (this.transaction.getSignatureCount() > 0) {
      checkWeight(permission, this.transaction.getSignatureList(),
          this.getTransactionId().getBytes(),
          approveList);
      if (approveList.contains(ByteString.copyFrom(address))) {
        throw new PermissionException(encode58Check(address) + " had signed!");
      }
    }

    long weight = getWeight(permission, address);
    if (weight == 0) {
      throw new PermissionException(
          ByteArray.toHexString(privateKey) + "'s address is " + encode58Check(address)
              + " but it is not contained of permission.");
    }
    ByteString sig = ByteString.copyFrom(cryptoEngine.Base64toBytes(cryptoEngine
        .signHash(getTransactionId().getBytes())));
    this.transaction = this.transaction.toBuilder().addSignature(sig).build();
  }

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }
