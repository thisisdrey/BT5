Audit Report

## Title
Truncated remote fee can compute to zero without validation, causing free/underpriced Snowbridge message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::calculate_fee` truncates the computed remote (Ethereum-side) fee to local decimal precision via integer division in `convert_from_ether_decimals`, which can silently round the remote fee to `0` even with non-zero, plausible `PricingParameters`. `SendMessage::validate` in `send_message_impl.rs` returns this `Fee{local, remote}` to the caller without any check that `remote` is non-zero or sufficient, while `do_process_message` still embeds the full, un-truncated `pricing_params.rewards.remote` and `fee_per_gas` into the committed message sent to Ethereum.

## Finding Description
`calculate_fee` computes the remote fee in ether units, converts it via `FixedU128` multiplier/exchange-rate math, and then calls `convert_from_ether_decimals`, which performs `value.checked_div(denom)` — an integer division that rounds towards zero: [1](#0-0) 

This truncation is demonstrably reachable with realistic non-zero parameters, as shown by the existing regression test whose own comment states the result "should be avoided": [2](#0-1) 

The caller, `SendMessage::validate`, invokes `calculate_fee` and returns the resulting `Fee` directly with no validation that `fee.remote` is non-zero or economically sufficient: [3](#0-2) 

Meanwhile, `do_process_message` constructs the actual `CommittedMessage` sent to Ethereum using the full, untruncated `pricing_params.rewards.remote` and `pricing_params.fee_per_gas`, independent of what was charged to the sender in `validate`: [4](#0-3) 

There is no invariant anywhere in this path enforcing that the fee charged to the sender (`fee.local + fee.remote`) covers the reward/gas-refund promised on-chain in the committed message, so a zero-truncated `fee.remote` is accepted and used unchecked.

## Impact Explanation
This is a case of public, underpriced work: any account able to route a message through the Snowbridge exporter (e.g., via XCM `ExportMessage`) can have its remote-fee component silently truncate to zero while the outbound queue still commits a message on Ethereum that promises relayers the full configured reward. Repeated exploitation can drain relayer-reward funding or leave relayers uncompensated for real delivery costs, which falls under "public underpriced work that degrades... or stalls bridge processing."

## Likelihood Explanation
No malicious or privileged actor is required to trigger the bug itself — it is a pure arithmetic property of `calculate_fee`/`convert_from_ether_decimals` for certain (plausible, non-malicious) pricing-parameter combinations, as proven by the existing unit test using realistic values (`exchange_rate=1`, `fee_per_gas=1`, `reward=1`). Any ordinary user sending a message while such parameters are in effect reaches the zero-fee path deterministically and repeatably.

## Recommendation
Add an explicit check in `calculate_fee` or immediately after it in `SendMessage::validate` that rejects (returns a `SendError`) when `fee.remote == 0` (or below a configured minimum) while `pricing_params.rewards.remote` / `fee_per_gas` are non-zero. Alternatively, switch `convert_from_ether_decimals` to round up for the fee-charging path, and add an invariant tying the charged `fee.remote` to the reward/gas-refund actually embedded in the committed message.

## Proof of Concept
1. Configure `PricingParameters { exchange_rate: 1, fee_per_gas: 1, rewards: { local: 1, remote: 1 }, multiplier: 1 }` — reproduced exactly by the existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` in `bridges/snowbridge/pallets/outbound-queue/src/test.rs`.
2. Any user sends a message through `SendMessage::validate` (`send_message_impl.rs:59-60`), which calls `Self::calculate_fee` and receives `Fee { local: 698000000, remote: 0 }`.
3. `do_process_message` (`lib.rs:332-352`) still embeds `pricing_params.rewards.remote` and `pricing_params.fee_per_gas` (both non-zero) into the `CommittedMessage` sent to Ethereum.
4. Result: the sender pays `0` for remote delivery while the bridge commits to a non-zero relayer reward on Ethereum — an unchecked, exploitable discrepancy.
