### Title
Missing zero-quantity check in exact-match branch of `MarketSellAssetActuator.matchSingleOrder()` allows a maker to transfer sell-tokens while receiving zero payment - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketUtils.multiplyAndDivide()` performs integer (floor) division when computing token match quantities for the TRON on-chain order book (Market feature). This is the same class of bug as Sherlock M-9 in Surge Protocol: an integer-division truncation to `0` in an interest/quantity calculation lets one party escape paying, while the other party's balance is still debited/consumed.

### Finding Description
`matchSingleOrder()` in `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java` handles three cases when a taker order matches a maker order:

1. **taker < maker** (lines 440-452): no zero check needed, `takerBuyTokenQuantityReceive = takerBuyTokenQuantityRemain` which was already validated non-zero at line 406.
2. **taker > maker** (lines 453-483): explicitly checks `makerBuyTokenQuantityReceive == 0` (lines 466-477) and, if zero, refunds the maker's remaining sell tokens instead of consuming them for free.
3. **taker == maker** (lines 418-439): computes
```java
makerBuyTokenQuantityReceive = MarketUtils
    .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity,
        this.disableJavaLangMath());
takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();
long takerSellTokenLeft =
    takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
makerOrderCapsule.setSellTokenQuantityRemain(0);
``` [1](#0-0) 

This branch has **no check for `makerBuyTokenQuantityReceive == 0`**, unlike branch 2. `multiplyAndDivide` uses `floorDiv`/`BigInteger.divide`, which truncates toward zero: [2](#0-1) 

If `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`, the division truncates to `0`. In that case:
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` fully consumes the maker's remaining sell tokens.
- The maker is credited `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` with `0` — i.e., the maker gets nothing in return.
- The taker receives the maker's entire remaining sell-token balance (`takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()`), and `takerSellTokenLeft` is reduced by `0`, so the taker pays nothing for those tokens (effectively getting them for free), consuming the maker's balance entirely.

This mirrors the root cause in the Surge report: the code explicitly reasons about and guards against the zero-division case in one branch but omits the identical guard in a structurally symmetric branch, leading to state updates being committed based on a zero-valued interest/quantity result.

### Impact Explanation
This results in a maker's on-chain asset balance being irrecoverably consumed (`setSellTokenQuantityRemain(0)`, order marked `INACTIVE`) while the maker's account is credited `0` tokens in return, and the counterparty (taker) obtains the maker's tokens for free. This is a direct unauthorized/unbacked value transfer — a concrete theft/permanent-freezing-of-funds condition triggered purely by placing an order via the standard `MarketSellAssetContract` transaction, reachable by any unprivileged transaction broadcaster.

### Likelihood Explanation
Reachable whenever the exact-match branch (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`) is hit and `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`. Because `takerBuyTokenQuantityRemain` is itself computed as `taker.sellRemain * makerSellQuantity / makerBuyQuantity` (also truncated), an attacker (as taker) can choose `sellTokenQuantity`/`buyTokenQuantity` ratios and target a maker order with a small `makerSellQuantity/makerBuyQuantity` ratio and small remaining balance to deterministically hit this exact-equality branch with a truncated-to-zero `makerBuyTokenQuantityReceive`. This requires crafting specific order sizes/prices but no special privilege — feasible for any market participant.

### Recommendation
Add the same zero-quantity guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell tokens via `returnSellTokenRemain`/refund logic instead of zeroing out `makerOrderCapsule.getSellTokenQuantityRemain()` and crediting the taker for free. More generally, audit all uses of `multiplyAndDivide` in the matching engine for missing zero-result checks, and consider increasing internal precision (extra decimals) as recommended in the referenced report to reduce truncation-to-zero occurrences.

### Proof of Concept
1. Attacker creates a maker sell order: sell `makerSellQuantity` of token A for `makerBuyQuantity` of token B, with the ratio and remaining amount chosen so that `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity == 0` (e.g., `makerSellRemainQuantity = 1`, `makerBuyQuantity = 1`, `makerSellQuantity = 2` → `1*1/2 = 0`).
2. A taker submits a `MarketSellAssetContract` order whose computed `takerBuyTokenQuantityRemain` (via `multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity, ...)`) exactly equals `makerOrderCapsule.getSellTokenQuantityRemain()`, hitting the "taker == maker" branch in `matchSingleOrder()`.
3. `makerBuyTokenQuantityReceive` truncates to `0`; the maker's `sellTokenQuantityRemain` is zeroed and the order marked `INACTIVE`, while the maker's account is credited `0` via `addTrxOrToken(makerOrderCapsule, 0)`.
4. The taker receives `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the maker's full remaining balance) while the taker's own `sellTokenQuantityRemain` is decremented by `0`, i.e., the taker pays nothing for the tokens received — a net unbacked transfer of value from the maker to the taker.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
