### Title
Attacker can fill a victim's per-account token list via dust deposits/transfers to reach `MAX_TOKENS_PER_USER`, DoS-ing deposits, borrowing, and collateral top-ups - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` keeps a bounded per-account list of deposit tokens and debt tokens (`MAX_TOKENS_PER_USER = 30`). Both `DepositToken._mint` (via `deposit(amount_, onBehalfOf_)`) and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to positive, and `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list length hits 30. Any EOA can push entries into an arbitrary victim's list by depositing dust on their behalf or transferring dust msdTOKEN, permanently blocking the victim from adding any new collateral type or new debt position until they manually zero out balances.

### Finding Description
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30`. [1](#0-0) [2](#0-1) 
- `DepositToken._mint` adds the token to the recipient's list whenever `_balanceBefore == 0 && amount_ > 0`, with no minimum amount. [3](#0-2) 
- `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint msdTOKEN directly to a victim. [4](#0-3) 
- `DepositToken._transfer` adds the token to the recipient's list on first receipt, and `transfer`/`transferFrom` only check the sender's unlocked balance — dust transfers of each whitelisted deposit token to the victim work identically. [5](#0-4) 
- Debt tokens share the same counter: `DebtToken` mints call `addToDebtTokensOfAccount`, which has the same `onlyIfAdditionWillNotReachMaxTokens` guard. [6](#0-5) 

Attack trace (all public, unprivileged):
1. Attacker calls `msdX.deposit(1, victim)` (or `msdX.transfer(victim, 1)` after depositing once) for each of the pool's whitelisted deposit tokens, plus fills remaining slots until `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30`.
2. Every subsequent `deposit`/`transfer`/`issue`/`flashIssue`/`leverage` path that would add a *new* token to the victim's list reverts with `UserReachedMaxTokens` inside `_mint`/`_transfer`/debt-token mint, reverting the whole transaction.

### Impact Explanation
Temporary freezing of funds and forced-liquidation DoS:
- A victim whose position is drifting toward unhealthy cannot deposit a *different* collateral type to recapitalize (any new deposit token reverts), and cannot receive msdTOKEN transfers, blocking rescue while `liquidate` remains callable on them — enabling seizure of their collateral with liquidator incentive.
- The victim cannot open a position in any synthetic asset whose debt token isn't already in their list (`issue` reverts), and SmartFarmingManager `leverage` reverts for them.
- Clearing a slot requires fully zeroing a dust balance (withdraw/transfer out of each poisoned token), which is forced labor the attacker can re-trigger at dust cost; for non-18-decimal or fee-on-transfer underlyings, fully draining a dust remainder can be impractical, approaching permanent freezing of the slot.
- Invariant broken: liveness — a user cannot perform legitimate deposit/borrow operations solely due to attacker-crafted state.

### Likelihood Explanation
- Fully permissionless: `deposit` credits `onBehalfOf_` arbitrarily, and msdTOKEN `transfer` to any address is allowed up to the sender's unlocked balance — no consent mechanism exists on the receiving side.
- Cost is bounded by ~30 dust deposits/transfers of tokens the attacker can acquire (or deposit 1 wei each, subject to `maxTotalSupply` headroom which is large). No privileged role, oracle manipulation, or governance action needed; not a gas/unbounded-loop DoS — the DoS is state-based (revert condition on a bounded set).
- Not blocked by `ReentrancyGuardTransient`, `SynthContext` sender resolution, pause flags, or supply caps; the deployed `MAX_TOKENS_PER_USER` is 30 on all recorded deployments.

### Recommendation
- Decouple the revert from the token-list add: make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` a no-op (or track via a different structure) when at the cap instead of reverting, and iterate over actual balances rather than the capped list for `debtPositionOf` — or
- Gate additions behind recipient opt-in (e.g., only add on `deposit` where `onBehalfOf == _msgSender()` or an allowance/whitelist), and/or
- Require a minimum first-deposit amount so dust cannot occupy a slot.

### Proof of Concept
Hardhat (fork, using deployed pool + two whitelisted deposit tokens `msdA`, `msdB`, ...):

```ts
it('griefs victim token slots via dust deposits', async () => {
  const victim = bob.address;
  // Attacker deposits 1 wei of each whitelisted collateral on behalf of victim
  for (const msd of depositTokens) {           // repeat until 30 total entries
    const underlying = await ethers.getContractAt('IERC20', await msd.underlying());
    await underlying.connect(attacker).approve(msd.address, 1);
    await msd.connect(attacker).deposit(1, victim); // adds msd to victim's list
  }
  // Also possible: await msd.connect(attacker).transfer(victim, 1);

  const n = (await pool.getDepositTokensOfAccount(victim)).length
          + (await pool.getDebtTokensOfAccount(victim)).length;
  expect(n).to.eq(30);

  // Victim can no longer deposit a collateral type not already in their list
  const underlyingNew = await ethers.getContractAt('IERC20', await msdNew.underlying());
  await underlyingNew.connect(bob).approve(msdNew.address, parseEther('100'));
  await expect(msdNew.connect(bob).deposit(parseEther('100'), victim))
    .to.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // Nor open a debt position in a synthetic whose debt token isn't in their list
  await expect(msUsdDebtToken.connect(bob).issue(1, victim))
    .to.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Pre-existing unit coverage confirms the revert trigger (`UserReachedMaxTokens` when combined length reaches `MAX_TOKENS_PER_USER`) at `test/Pool.test.ts` around the `addToDepositTokensOfAccount` suite.
