## Title
Snowbridge relayer reward is permanently lost on premature success reporting when the cross-chain deposit is never checked - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`PayAccountOnLocation::pay_reward` (used by `BridgeRewardPayer` on BridgeHub for `BridgeReward::Snowbridge`) reports `Ok(())` as soon as the reward-minting XCM message is *sent* to AssetHub. It never verifies that the `DepositAsset` instruction inside that XCM actually executes and credits the beneficiary. The caller, `pallet-bridge-relayers::do_claim_rewards`, treats this `Ok(())` as final settlement and permanently removes the relayer's reward entry from storage. If the XCM later fails to execute on AssetHub (e.g. account cannot satisfy the foreign-asset existential deposit, asset not yet created, or any other execution failure), the relayer's funds are trapped/lost with no route to reclaim them and no record left on BridgeHub to retry.

### Finding Description
`PayAccountOnLocation::pay_reward` [1](#0-0)  only checks three local, synchronous outcomes:
- `validate_send` (message construction/routing validity)
- `XcmExecutor::charge_fees` (relayer has funds for delivery fee)
- `XcmSender::deliver` (message handed off to the transport queue)

It never checks whether the `ReserveAssetDeposited` + `DepositAsset { assets: AllCounted(1), beneficiary }` instructions [2](#0-1)  actually succeed when the message is executed on AssetHub. `deliver()` only guarantees the message reached the transport layer, not that its instructions will complete successfully at the destination — this is structurally identical to the `ERC20Wrapper` bug: a call returns "success" as soon as the outer operation is queued/attempted, while the underlying value-moving step can silently fail.

The caller assumes `pay_reward`'s `Ok(())` means the reward has been fully settled:
```rust
RelayerRewards::<T, I>::try_mutate_exists(&relayer, reward_kind, |maybe_reward| -> DispatchResult {
    let reward_balance = maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
    T::PaymentProcedure::pay_reward(&relayer, reward_kind, reward_balance, beneficiary.clone())
        .map_err(|e| { ... Error::<T, I>::FailedToPayReward })?;
    Self::deposit_event(Event::RewardPaid { .. });
    Ok(())
})
``` [3](#0-2) 

Because `pay_reward` returns `Ok(())` even though the destination-side deposit is only "in flight," `maybe_reward.take()` permanently removes the reward record from `RelayerRewards` storage and the `RewardPaid` event is emitted before the actual crediting on AssetHub is known to succeed. There is no `Attempted`/`check_status`/retry state machine here (unlike `pallet-treasury`'s `Paymaster` interface, which has `PaymentState::Attempted { id }` and a `check_status` call precisely to avoid this class of bug — see `substrate/frame/treasury/src/lib.rs` lines 736-814). If the destination `DepositAsset` fails (e.g. `UnpaidExecution` message executes on AssetHub but the beneficiary account can't satisfy the reward asset's minimum balance, or any other execution failure), the reward asset is trapped via XCM's asset-trap mechanism. Reclaiming a trapped asset requires sending a `ClaimAsset` from the *exact original origin context* (`DescendOrigin(InboundQueueLocation) + UniversalOrigin(Ethereum)`), which an ordinary relayer account cannot reconstruct or authorize — the funds are effectively unrecoverable, and the relayer has no on-chain record left to even detect or retry the failure.

### Impact Explanation
This directly matches the "duplicate settlement or payout" / "permanent user-fund or bridge-state lock" impact class: bridge relayer reward state (`RelayerRewards` storage + `RewardPaid` event) advances to a final, non-retryable state before the actual settlement (crediting the beneficiary on AssetHub) is confirmed. A relayer that has legitimately earned a reward can permanently lose it through no fault of their own (e.g., insufficient existential deposit for the reward asset on the beneficiary account at delivery time), with no path to re-claim since the reward record is deleted and the trapped assets are unreachable by a normal user.

### Likelihood Explanation
No privileged or adversarial actor is required — an unprivileged relayer normally calling `claim_rewards_to` (public, signed-origin extrinsic) can trigger this simply by supplying (or having) an under-funded/undercreated beneficiary account on AssetHub, or the failure can occur due to ordinary transient destination-side conditions (e.g., asset registration/ED edge cases). This is a straightforward, repeatable path with no reliance on malicious peers, validators, or governance.

### Recommendation
Do not treat `deliver()` success as final settlement for cross-chain reward payment. Introduce an attempted/pending state (mirroring `pallet-treasury`'s `Paymaster`/`PaymentStatus` pattern) so that:
- `do_claim_rewards` transitions the reward to an `Attempted` state instead of removing it outright once the XCM is sent.
- A follow-up mechanism (e.g. delivery/execution receipt, or a `check_status` call) confirms actual settlement before permanently clearing the reward, and reverts to a claimable state (or provides a safe re-mint path) if the destination execution fails.

### Proof of Concept
1. On BridgeHub, have a relayer accumulate a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Call `claim_rewards_to` with an `AssetHubLocation` beneficiary that is not able to satisfy the destination foreign-asset's existential deposit (or otherwise causes the AssetHub-side `DepositAsset` to fail) — `validate_send`, `charge_fees`, and `deliver` all succeed locally, so `pay_reward` returns `Ok(())` and the pallet emits `RewardPaid` and removes the `RelayerRewards` entry [4](#0-3) .
3. On AssetHub, the XCM executes; `DepositAsset` fails because the beneficiary cannot satisfy the reward asset's ED, so the reserve-deposited assets are trapped instead of credited.
4. The relayer calls `claim_rewards_to` again and receives `Error::NoRewardForRelayer` — the reward is gone from BridgeHub storage, and the trapped assets on AssetHub cannot be reclaimed by the relayer (claiming requires reconstructing the original `DescendOrigin`/`UniversalOrigin` context, which only the Ethereum-side inbound queue location can authorize).

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
