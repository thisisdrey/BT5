### Title
Rounding-down in `convert-to-shares-preview` lets small deposits mint zero vault shares, permanently forfeiting the depositor's underlying assets - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
This is the same "rounding to zero" defect described in the external Niftyswap report, mapped onto Zest's ERC-4626-style tokenized vaults. Instead of a liquidity-removal step losing a low-fungibility token to floor-division, a `deposit` in any Zest vault can compute zero shares to mint for a non-zero underlying deposit due to integer division rounding down, while the deposited assets are still recorded as vault assets.

### Finding Description
Every vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) uses the same share-pricing helper: [1](#0-0) 

`convert-to-shares-preview` computes `mul-div-down amount ts ta`, i.e. `amount * total_supply / total_assets`, rounding down. Once the vault has accrued interest so that `total_assets` (`ta`) exceeds `total_supply` (`ts`) — the normal state for any lending vault after interest accrual via `accrue` — the share price per unit becomes greater than 1. For a sufficiently small `amount` (down to the smallest indivisible unit of the underlying, e.g. 1 micro-STX, 1 satoshi of sBTC, or 1 unit of a stablecoin), `floor(amount * ts / ta)` can equal `0`.

The `deposit` function only validates that the raw deposit `amount` is non-zero and that the minted `inkind` is `>= min-out` — it never asserts `inkind > u0`: [2](#0-1) 

If a caller sets `min-out` to `u0` (the natural default when depositing dust or when a client miscalculates), the deposit proceeds: the underlying `amount` is transferred into the vault and added to `assets`, but `ft-mint? zft inkind recipient` mints `u0` shares. The depositor permanently loses the deposited underlying with no `zft` balance to redeem it back, and the value is instead absorbed pro-rata by all existing shareholders.

Contrast this with `redeem`, which explicitly guards against the mirrored rounding case: [3](#0-2) 

`redeem` reverts with `ERR-OUTPUT-ZERO` if `inkind` (assets to be returned) rounds to zero — but the symmetric protection is absent on the deposit path, so this is a real asymmetry/gap rather than a deliberate design choice already covered elsewhere.

### Impact Explanation
Any ordinary depositor who submits a small-enough deposit (relative to the vault's `total_assets/total_supply` ratio) loses their underlying funds outright: they transfer real assets into the vault and never receive any vault shares (`zft`) representing a claim on them. Those funds become a permanent, un-recoverable gain to the other current shareholders. This is a direct theft/permanent loss of user funds at rest, matching the Critical impact bucket (direct theft of user funds at rest other than unclaimed yield).

### Likelihood Explanation
The trigger condition — `total_assets > total_supply` — is not an edge case; it is the vault's normal steady state once any interest has accrued via `accrue`, since interest inflates `total_assets` relative to unchanged `total_supply` until the next mint. As the ratio `ta/ts` drifts further above 1 over time, an increasingly large range of small deposit amounts round down to zero shares. Any caller passing `min-out = u0` (default/naive usage) for a small deposit triggers the loss with no special privileges required — this is reachable directly from `deposit`, a standard user-facing entry point.

### Recommendation
Add an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check in `deposit` (mirroring the existing check already present in `redeem`) across all vault contracts, so that deposits which would mint zero shares revert instead of silently absorbing the depositor's funds. Additionally consider enforcing a protocol-level minimum deposit amount tied to each underlying asset's precision, consistent with the Niftyswap resolution of requiring adequate decimal precision to bound rounding loss.

### Proof of Concept
1. Let a vault (e.g. `v0-vault-stx.clar`) have `total_supply = 1_000_000` shares and, after interest accrual via `accrue`, `total_assets = 1_000_001` (i.e., `ta/ts` slightly above 1 due to accrued interest, as computed by `total-assets-preview`).
2. A user calls `deposit` with `amount = u1` and `min-out = u0`.
3. `convert-to-shares-preview` computes `inkind = mul-div-down(1, 1_000_000, 1_000_001) = 0`.
4. `deposit`'s checks pass (`amount > 0` ✓, `inkind (0) >= min-out (0)` ✓, no `ERR-OUTPUT-ZERO`-style check exists on this path).
5. `receive-underlying` pulls the 1 unit from the user into the vault, `assets` is incremented by 1, and `ft-mint? zft u0 recipient` mints zero shares to the depositor.
6. The depositor has permanently lost 1 unit of the underlying with no corresponding `zft` balance; the value is now shared among all existing `zft` holders.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
