## Title
Floating-point precision loss in legacy SR voting-reward computation permits under/over-payment of user rewards — (`chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The reward-distribution flaw described in the Sherlock report (integer/precision-loss during proportional reward division in `GammaRewarder.createDistribution`) has a direct structural analog in java-tron's legacy ("old") SR voting-reward algorithm. `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each voter's proportional share of a cycle's total reward using **double-precision floating point** division and multiplication instead of exact integer/`BigInteger` arithmetic, which is exactly the class of bug flagged in the report (dividing an amount to distribute it proportionally without preserving precision).

### Finding Description
When a user withdraws their voting reward via a signed `WithdrawBalanceContract`, execution flows:

`WithdrawBalanceActuator.execute()` → `MortgageService.withdrawReward()` → `computeReward(beginCycle, endCycle, accountCapsule)` → for any cycle prior to `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`, it falls back to `getOldReward()` → `computeReward(cycle, votes)`. [1](#0-0) [2](#0-1) 

The legacy per-cycle reward split is:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [3](#0-2) 

Because `voteRate` and the multiplication are performed in IEEE-754 `double` precision and then implicitly narrowed back into the `long reward` accumulator, this exhibits the exact same root cause the report describes: proportional-share division that discards precision instead of using a fixed high-precision scaling factor (as the report's suggested mitigation using `10**18` multiplier). Note that java-tron's own newer algorithm (the "VI" delegation reward system) explicitly fixes this by using `BigInteger` scaled by `DECIMAL_OF_VI_REWARD = 10^18` before dividing: [4](#0-3) [5](#0-4) 
— confirming that the maintainers themselves recognized double-based division as imprecise and replaced it, but the old vulnerable path remains reachable for any account/cycle combination still below `newRewardAlgorithmEffectiveCycle` that has not yet withdrawn.

`IncentiveManager.reward()` (standby witness pay, invoked during block application, not directly by a user transaction) contains the identical anti-pattern (`(long) (voteCount * ((double) totalPay / voteSum))`), reinforcing that this is a systemic pattern rather than an isolated line: [6](#0-5) 

### Impact Explanation
Any unprivileged account that voted for a super representative in a cycle prior to the new-algorithm effective cycle and has not yet withdrawn can trigger `computeReward` via a normal `WithdrawBalanceContract`. Because the calculation for that reward uses lossy double-precision arithmetic instead of exact integer math, the amount credited to the user's `allowance` (and ultimately their TRX balance) can deviate from the mathematically correct proportional share — either underpaying the voter (loss of funds) or, in aggregate across all voters for a given SR/cycle, producing a total payout that doesn't exactly reconcile against `delegationStore.getReward(cycle, srAddress)`, since each voter's share is independently rounded via `double` truncation rather than distributing/tracking the remainder.

### Likelihood Explanation
Likelihood is limited by the fact that this path only activates for legacy cycles (`beginCycle < newRewardAlgorithmEffectiveCycle`), a cutover which committee governance already set on the live network, meaning most historical accounts have already claimed. It nonetheless remains reachable to any account with an outstanding unclaimed pre-cutover reward balance (long-dormant voter accounts), and is fully triggerable by a normal, permissionless `WithdrawBalanceContract` transaction with no special privileges required.

### Recommendation
Replace the `double`-based proportional computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` (and the analogous computation in `IncentiveManager.reward()`) with exact integer/`BigInteger` arithmetic scaled by a fixed high-precision factor (mirroring the `DECIMAL_OF_VI_REWARD` approach already used in `DelegationStore`/`RewardViCalService`), and account for/redistribute any remainder so that the sum of individually rounded shares does not diverge from the total reward pool for that cycle.

### Proof of Concept
1. Set `dynamicPropertiesStore` such that `getNewRewardAlgorithmEffectiveCycle()` is greater than 0 (legacy cycles exist) and an SR's cycle reward and total vote produce a non-terminating fraction (e.g., `totalReward = 100000001`, `totalVote = 3`, `userVote = 1`).
2. Have a voter account cast votes for that SR at that cycle and never withdraw until after the cycle passes.
3. Submit a `WithdrawBalanceContract` transaction for that account, triggering `WithdrawBalanceActuator.execute()` → `MortgageService.withdrawReward()` → legacy `computeReward(cycle, votes)`.
4. Compare the resulting `allowance` credited against the exact `BigInteger`-computed expected proportional share; the double-precision computation yields a divergent (truncated/rounded) value, demonstrating the precision-loss analog to the reported `GammaRewarder.createDistribution` bug.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
