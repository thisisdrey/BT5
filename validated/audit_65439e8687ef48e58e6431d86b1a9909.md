### Title
Unbounded Array Allocation from Attacker-Controlled Length Word in TVM Precompile ABI Decoding - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
Several private helper methods in `PrecompiledContracts.java` decode ABI-encoded dynamic arrays passed as `data` to a precompiled contract call by reading a length word directly out of the calldata and using it, unchecked, as an array-allocation size. This mirrors the `pad_packed_sequence` bug class: a length value taken from untrusted input is used to size a memory allocation without first validating it against the bounds of the actual buffer, allowing an attacker to trigger an oversized allocation (or a `NegativeArraySizeException`/`OutOfMemoryError`) from a single contract call.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` all take the number of array elements from an attacker-supplied word in the decoded call data and immediately allocate a Java array of that size, before verifying that `data`/`words` actually contains that many entries: [1](#0-0) [2](#0-1) [3](#0-2) 

In `extractBytes32Array`, `len` comes straight from `words[offset].intValueSafe()` with no check at all before `new byte[len][]` is allocated, and the subsequent loop indexes `words[offset + i + 1]` without any bound on `i` relative to `words.length`, which can also throw `ArrayIndexOutOfBoundsException` if `len` is large but positive and does not match the actual encoded array — but before that happens, the allocation itself (`new byte[len][]`) can already be enormous since `len` is fully attacker-controlled via calldata to the precompile. `extractBytesArray` and `extractSigArray` at least guard `offset > words.length - 1`, but still allocate `new byte[len][]` using an unchecked `len` before validating that `len` matches available data.

This is structurally the same root cause as the PyTorch advisory: a size/length parameter taken from untrusted input is trusted for a memory allocation without validating it against the true size of the backing data first. The codebase demonstrates awareness of this exact bug class elsewhere — `RLP.decode`'s `verifyLength` explicitly checks a length parsed from encoded data against the remaining available buffer before use [4](#0-3)  and even wraps decoding in a catch for `OutOfMemoryError` from "excessive mem allocation while parsing" [5](#0-4)  — but the `extract*Array` helpers in `PrecompiledContracts.java` do not apply the same defensive bound.

### Impact Explanation
A precompiled contract call whose input is decoded through these helpers can be crafted so that the length word is an arbitrarily large positive `int` (up to `Integer.MAX_VALUE`, since `intValueSafe()` clamps to int range). This forces the JVM to attempt allocating a reference array of that size (`new byte[len][]`), which for large `len` (tens/hundreds of millions of elements) can exhaust heap memory and trigger `OutOfMemoryError` on the node processing the transaction inside the TVM. Because TVM execution happens inside the same process as block application/consensus, an uncontrolled `OutOfMemoryError` during precompile execution risks destabilizing the node process (crash or unpredictable behavior across threads), which affects node availability — matching the "node crash or halt" impact bar for this class of bug.

### Likelihood Explanation
Reachability requires that this decoding path is wired to a specific precompiled contract accessible via a normal contract call (`CALL`/`STATICCALL` to the precompile's fixed address), which any unprivileged contract deployer or transaction sender can trigger by invoking the corresponding precompile with crafted calldata. I was not able to fully confirm within the available search budget which precompile constant/address dispatches to `extractBytesArray`/`extractBytes32Array`/`extractSigArray` (e.g. whether it is the multi-sig/zero-knowledge related precompile), nor whether an upstream `getEnergyForData` check effectively bounds `len` before these helpers run in practice. This should be verified against the specific precompile's `execute`/`getEnergyForData` implementation before treating this as fully confirmed; the array-allocation-from-unchecked-length pattern itself, however, is directly present and unguarded in the code as shown above.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual remaining length of `words`/`data` (analogous to `RLP.verifyLength`), rejecting the precompile call with a decode/validation error if the claimed length is inconsistent with the available buffer, rather than allocating first and failing later.

### Proof of Concept
Not independently executed; based on static code reading. Conceptually: invoke the precompiled contract that routes through `extractBytes32Array`/`extractBytesArray`/`extractSigArray` with an ABI-encoded array whose length word is set to a very large value (e.g. `0x7fffffff`) while the accompanying calldata is otherwise minimal/short. The call reaches `new byte[len][]` with `len` unchecked against real data size, triggering an oversized allocation attempt.
