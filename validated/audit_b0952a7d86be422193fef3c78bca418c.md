**Analysis:**

The scenario describes exactly the documented, intended behavior of `FtWithdraw` — not a bug. Tracing the code:

1. `internal_ft_withdraw` in [1](#0-0)  debits the signer's internal balance for both the FT `amount` and, if `storage_deposit` is `Some`, an equal amount of `wNEAR` — both amounts debited synchronously in the same state transition, before any promise executes.

2. The promise chain then does `near_withdraw` → `storage_deposit(receiver_id)` on `token` with the attached deposit exactly equal to the debited `wNEAR` amount → `ft_transfer`, followed by `ft_resolve_withdraw` as documented in [2](#0-1) .

3. `ft_resolve_withdraw` checks only the result of the final `ft_transfer`/`ft_transfer_call` promise; if it failed (as in the scenario where `token` panics on `ft_transfer` after accepting `storage_deposit`), the FT `amount` is refunded back to the signer via `self.deposit(...)`, but the `wNEAR` spent on `storage_deposit` is never refunded — see [3](#0-2) .

This exact outcome is explicitly documented on the `storage_deposit` field: "the `wNEAR` will not be refunded in case of fail," and reiterated in `min_gas()`'s comments about why a hard gas minimum is enforced — see [4](#0-3)  and [5](#0-4) .

Critically, `FtWithdraw` only ever debits the signing owner's own account (`owner_id` comes from the verified signer, not an attacker-chosen victim) — see the balance subtraction in [6](#0-5)  and [7](#0-6) . There is no cross-account attack surface: the "attacker" in this scenario can only spend their own `wNEAR` this way, and the real NEAR sent as `storage_deposit` is not lost — it is actually delivered to `token` and registers `receiver_id`'s storage there, matching `wNEAR_debited(signer) == NEAR_delivered_as_storage(token, receiver_id)` exactly, while the FT leg (`FT_delivered(receiver_id)`) independently nets to zero via the resolver's refund. This is a self-inflicted, explicitly-warned-about cost of a self-signed intent, not unauthorized value leaving the Verifier, and does not fit any of the Critical/High impact categories (no third party's funds are moved without authorization, no double-settlement, and the batch nets to what the signer explicitly authorized by signing with `storage_deposit: Some(...)`).

    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }
