### Title
StackerDB chunk signatures omit the target contract, allowing cross-StackerDB replay of authenticated chunks - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata`'s signed digest binds only `slot_id`, `slot_version`, and `data_hash` — it never binds the target `QualifiedContractIdentifier`. Any node that observes a validly-signed `StackerDBChunkData` for one StackerDB replica can re-wrap it (same `slot_id`/`slot_version`/`data`/`sig`, but with a different `contract_id` in the `StackerDBPushChunkData`/upload) and have it accepted as valid and stored/rebroadcast in any *other* StackerDB replica configured on the node, as long as that other replica also assigns the same `slot_id` to a principal whose address recovers from the (unchanged) signature. This is structurally the same "missing binding" defect as the reported bug: data authenticated for one context (contract A) is accepted as canonical in an unintended context (contract B) because nothing ties the authentication to the destination.

### Finding Description
`SlotMetadata::auth_digest` computes the signed hash as: [1](#0-0) 

This digest is used both to sign (`SlotMetadata::sign`) and to verify (`SlotMetadata::verify`) a chunk: [2](#0-1) 

Note that the smart-contract identifier (StackerDB name) is never part of the digest. All downstream verification paths rely solely on this digest:

- `StackerDBTx::try_replace_chunk` (used both by the HTTP upload path and by `Relayer::process_stacker_db_chunks`) looks up the expected signer *for the given contract and slot_id* and calls `slot_desc.verify(&slot_validation.signer)`, but the signature check itself is contract-agnostic: [3](#0-2) 

- `PeerNetwork::validate_received_chunk`, used for both StackerDB sync and for gossip pushes (`handle_unsolicited_StackerDBPushChunk`), performs the same contract-agnostic signature check via `get_slot_signer(smart_contract_id, data.slot_id)` + `slot_metadata.verify(&addr)`: [4](#0-3) 

Because the `contract_id` is carried as a separate, unauthenticated field alongside the signed `StackerDBChunkData` in both `StackerDBPushChunkData` (P2P gossip) and the HTTP chunk-upload path, an attacker (any unprivileged peer that receives/observes a legitimately-signed chunk broadcast for contract A) can take that exact `(slot_id, slot_version, sig, data)` tuple and submit/relay it against a different `contract_id` = B. If contract B's slot table happens to assign the same `slot_id` to the same signer address (which is common — StackerDB slot layouts for signer-set StackerDBs are typically derived deterministically from the same reward-cycle signer ordering across different sibling contracts, e.g. multiple `.signers-*` message DBs for the same cycle/signer set), the signature-recovery check in both `try_replace_chunk` and `validate_received_chunk` succeeds, and the (attacker-chosen, but originally content-authored-by-the-real-signer) chunk is accepted, stored, and rebroadcast under contract B — a context the real signer never authorized it for.

This is the direct analog of the Reservoir issue's root cause: an entity/authentication is not scoped to the specific destination it is meant for, so authenticated data ends up materializing in the wrong "bucket" (here, the wrong StackerDB/contract) as canonical, valid state.

### Impact Explanation
This breaks the equality "authenticated-for-contract-A == stored-under-contract-A": data whose authenticity was only ever established for one StackerDB smart contract gets propagated and stored as canonical, signer-authored data under a different StackerDB smart contract, network-wide (rebroadcast via `broadcast_message` in `process_stacker_db_chunks`/`process_uploaded_stackerdb_chunks`). This can corrupt or desynchronize the state of an unrelated StackerDB application (e.g., replaying a signer's block-response message from one message-type DB into another), and it happens without needing the target signer's cooperation, key, or the node's own key — the attacker only needs to observe one legitimately gossiped/uploaded chunk and knows the target StackerDB's slot layout (public smart-contract configuration). This matches the "network-wide propagation of forged data" / "unauthorized write to StackerDB state" criteria.

### Likelihood Explanation
Requires: (1) an observed, validly-signed chunk for some StackerDB contract A (trivially obtainable by any peer since chunks/gossip are broadcast in the clear), and (2) a second StackerDB contract B configured on target nodes whose slot table assigns the identical `slot_id` to the same signer principal as in A. Condition (2) is plausible in the Nakamoto signer-set StackerDB deployment model, where multiple sibling `.signers-*` contracts for a given reward cycle are populated from the same ordered `RewardSet`/signer list, making identical slot-to-signer assignment across sibling contracts likely by construction, without requiring any secret or privileged access.

### Recommendation
Include the target `QualifiedContractIdentifier` (and ideally a network/chain identifier) in the signed digest computed by `SlotMetadata::auth_digest`, so a signature is only valid for the specific StackerDB it was produced for. This requires a coordinated protocol/version change since it alters what is signed by all StackerDB participants (miners, signers), but it closes off cross-contract chunk replay.

### Proof of Concept
1. Configure two StackerDB contracts, A and B, each with a slot table where `slot_id = 0` is owned by the same signer address (plausible for sibling `.signers-*` contracts sharing a reward-cycle signer order).
2. The legitimate signer signs and pushes a chunk `(slot_id=0, slot_version=v, data=D)` for contract A; this is broadcast via `StackerDBPushChunk` as shown in `process_stacker_db_chunks`.
3. An attacker observes this gossip message, extracts `StackerDBChunkData{slot_id:0, slot_version:v, sig, data:D}`, and submits it (e.g. via the HTTP `POST /v2/stackerdb/.../chunks` endpoint in `poststackerdbchunk.rs`, or crafts a `StackerDBPushChunkData` with `contract_id = B`) to a node that also serves contract B.
4. `try_replace_chunk`/`validate_received_chunk` for contract B recovers the signer address from `sig` using the contract-agnostic `auth_digest`, finds it matches B's slot-0 signer, and accepts/stores/rebroadcasts the chunk as valid data for contract B — even though the real signer never authored or authorized this chunk for B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
