## Finding

### Title
StackerDB chunk signatures are not bound to the target contract, enabling cross-StackerDB chunk replay/confusion - (File: libstackerdb/src/libstackerdb.rs)

### Summary
The Docling advisory is a path-containment failure: a resource identifier (`\includegraphics`/`\input` path) is trusted without verifying it stays inside the intended container (the document's base directory). The stacks-core analog is a scope-containment failure in `SlotMetadata`'s signing digest: a StackerDB chunk's signature authenticates `(slot_id, slot_version, data_hash)` but never binds to *which StackerDB contract* it belongs to. A chunk legitimately signed for one contract is therefore a valid, verifiable chunk for any other contract that happens to assign the same signer to the same `slot_id` — exactly the "authenticated-for-X served/stored-as-Y" equality break called out in the rules.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest from only three fields: [1](#0-0) 

`SlotMetadata::verify()` / `StackerDBChunkData::verify()` recover the signer purely from this digest, with no contract identifier mixed in: [2](#0-1) 

The write path, `StackerDBTx::try_replace_chunk`, looks up the signer *expected for this contract* and calls `slot_desc.verify(&slot_validation.signer)`, then checks version/`max_writes`, but never checks that the signature was produced "for this contract": [3](#0-2) 

The unsolicited-push validation path (`validate_received_chunk`) has the identical gap — it resolves the expected signer for the *target* `smart_contract_id` and checks the chunk's signature against it, again without any cross-contract binding: [4](#0-3) 

This matters because Nakamoto's signer subsystem deploys many distinct StackerDB contracts — one per `(reward_cycle % 2, message_id)` pair — that all reuse the *same* signer→slot assignment for a given signer set: [5](#0-4) [6](#0-5) 

Contracts `signers-{0|1}-1` (BlockResponse), `signers-{0|1}-4` (MockSignature), `signers-{0|1}-6` (StateMachineUpdate), `signers-{0|1}-7` (BlockPreCommit), etc. all draw from the same `stackerdb-get-signer-slots-page` list, so signer address `S` occupies the *same numeric slot_id* across all of them. Because the signature never encodes the contract/message-type, a chunk `(slot_id, slot_version, sig, data)` that `S` legitimately signed and published to `signers-0-1` is a fully valid, independently-verifiable chunk for `signers-0-6` (or any sibling contract), as long as it satisfies that other contract's own freshness/`max_writes` checks — checks that operate purely on local per-contract version counters and are trivially satisfiable by any observer who already saw the original broadcast.

Any unauthenticated remote peer that observes a chunk gossiped over the network (StackerDB chunks are broadcast in the clear to any peer, and are also directly fetchable/postable via the public `/v2/stackerdb/.../chunks` HTTP RPC — see `RPCPostStackerDBChunkRequestHandler::try_handle_request`) can resubmit that exact same bytes against a *different* sibling contract's endpoint: [7](#0-6) 

`try_replace_chunk` will accept it (assuming the target slot's version counter allows it), and on success the node treats the store as legitimate, relaying it onward as a `StackerDBPushChunk` to the rest of the network: [8](#0-7) 

The FutureView buffering path in relay handling exhibits the same gap — it validates the chunk's signature/version but has no notion that the chunk's signed content must correspond to the specific contract it's being buffered/relayed for: [9](#0-8) 

### Impact Explanation
This lets an unauthenticated remote party (anyone relaying network traffic, not necessarily a signer) cause a node to store and further gossip data into a StackerDB slot under a message-type/contract it was never intended for. Concretely: replaying a signer's `BlockResponse` (or `MockSignature`) chunk bytes into the `signers-{set}-6` (`StateMachineUpdate`) slot for that signer causes downstream consumers — e.g. `StackerDBListener`/`GlobalStateEvaluator`, which deserializes whatever bytes sit in that slot as a `StateMachineUpdate` — to either fail to parse (denial of the signer's real state) or, if a stale/other-message payload happens to parse as a different but valid `SignerMessageV0` variant, be treated as canonical state from that signer. This is a form of unauthenticated write into StackerDB state plus network-wide propagation of misattributed/forged-context data, matching the Critical "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" bar in the rules. It does not require the node's secret key, the signer's private key, or any privileged role — only replaying publicly-observable bytes to a different endpoint.

### Likelihood Explanation
High likelihood of reachability: StackerDB chunks for the signer contracts are routinely broadcast/fetchable by any peer, the `/v2/stackerdb/:principal/:contract/chunks` POST endpoint is unauthenticated by design (any peer chunk-pushes), and the sibling `signers-{set}-{msg_id}` contracts share slot assignment deterministically per reward cycle, so an attacker does not need to guess anything — they only need to select a *different* message-id contract than the one a given signed chunk was originally published to, and stay within that contract's own version/`max_writes` bookkeeping (each contract's version counter starts independently, so the "next version" constraint is easy to satisfy for at least one sibling).

### Recommendation
Bind the signature to the target StackerDB by mixing the `QualifiedContractIdentifier` (or at minimum the message/slot-namespace identifier) into `SlotMetadata::auth_digest()`, and thread the contract id through `sign()`/`verify()` call sites (`StackerDBChunkData::sign`, `get_slot_metadata`, `try_replace_chunk`, `validate_received_chunk`) so a chunk's signature is cryptographically scoped to exactly one StackerDB contract. This is a wire/consensus-adjacent format change and needs a version-gated rollout across `libstackerdb`, `stackslib/src/net/stackerdb/**`, and the signer/miner clients that construct these signatures.

### Proof of Concept
1. Let signer `S` (private key `sk`) own `slot_id = k` in both `signers-0-1` (BlockResponse) and `signers-0-6` (StateMachineUpdate) for the current reward cycle (guaranteed, since both contracts derive their slot list from the same `.signers` page for `signer_set = 0`).
2. `S` (or any relay) legitimately signs and posts a `BlockResponse` payload as `StackerDBChunkData { slot_id: k, slot_version: v, sig, data }` to `signers-0-1`; this propagates via `StackerDBPushChunk` gossip, per `poststackerdbchunk.rs`.
3. Any remote peer that observed this gossiped chunk (no login/authorization needed) issues `POST /v2/stackerdb/<addr>/signers-0-6/chunks` with the *identical* `slot_id`, `slot_version` (or `+1` if `signers-0-6`'s slot `k` is currently at a lower version), `sig`, `data` bytes.
4. `try_replace_chunk` for `signers-0-6` calls `slot_desc.verify(&slot_validation.signer)`, which succeeds because `auth_digest()` only depends on `(slot_id, slot_version, data_hash)` — none of which differ between the two contracts — so the signature recovers to `S`, who is indeed the registered signer of slot `k` in `signers-0-6` too.
5. The node accepts and stores the `BlockResponse` bytes into the `StateMachineUpdate` slot, then relays it to the network as a `StackerDBPushChunk` for `signers-0-6`, and `StackerDBListener`/`GlobalStateEvaluator` on other nodes will attempt to interpret it as `S`'s current `StateMachineUpdate`.

        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())

            ))?;

            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,

            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }

                                        &contract_identifier, &e

                        accepted: false,
                        reason: Some(reason),
                        metadata: slot_metadata_opt,
                        code: Some(err_code.code()),
