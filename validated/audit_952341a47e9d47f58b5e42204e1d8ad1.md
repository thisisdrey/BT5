### Title
Unbounded persistence of attacker-supplied garbage as "instantiated" Atlas attachments - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `Attachment` returned by a peer for an `AttachmentRequest` without verifying that the returned content's hash matches the `content_hash` that was actually requested. `AttachmentsDownloader::run`'s `Done` branch then unconditionally calls `AtlasDB::insert_instantiated_attachment` for every drained attachment, so a malicious "most reliable" peer can cause arbitrary, semantically-unrelated attachment bytes to be written and permanently kept in the `attachments` table with `was_instantiated = 1`, which is never subject to the existing eviction routines.

### Finding Description
The claimed equality: number/size of `was_instantiated = 1` rows in the `attachments` table should equal the set of hashes actually referenced by confirmed `AttachmentInstance` commitments (i.e. tracked in `AttachmentsBatch::attachments_instances`, populated from real BNS name-op events). This is broken.

Trace:
- `AttachmentRequest` is built per missing `content_hash` and sent to the peer chosen by `AttachmentRequest::get_most_reliable_source` [1](#0-0) , which simply picks whichever URL has the best `ReliabilityReport` score — attainable by any peer that answers enough prior requests.
- The HTTP response is decoded via `decode_atlas_get_attachment` into a `GetAttachmentResponse{ attachment }` with **no comparison to the requested `content_hash`** [2](#0-1) .
- `extend_with_attachments` inserts this response's attachment directly into `self.attachments` (a `HashSet<Attachment>`), gated only by whether JSON decoding succeeded — again no hash check against the original request: [3](#0-2) .
- In `AttachmentsDownloader::run`'s `Done` branch, every attachment drained from `context.attachments` is looked up by `find_all_attachment_instances(&attachment.hash())` (i.e. the hash of the *received* garbage content, not the originally requested hash) and then unconditionally persisted via `insert_instantiated_attachment`, regardless of whether any instance actually matched: [4](#0-3) .
- `insert_instantiated_attachment` does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` keyed by `attachment.hash()`, i.e. the hash of the attacker's own garbage — so each distinct garbage payload always succeeds and creates a distinct permanent row: [5](#0-4) .
- The only relevant eviction routine, `evict_expired_uninstantiated_attachments`, only deletes rows with `was_instantiated = 0`, never touching instantiated garbage rows: [6](#0-5) .

Root cause: the download/insert path never verifies `attachment.hash() == request.content_hash` (or equivalently `== attachment_instance.content_hash`) before treating the payload as a validated, permanently-stored attachment. `find_attachment`/`find_all_attachment_instances` lookups by the *received* hash create the illusion of validation, but since the attacker controls both the content and thus its hash, this "lookup" trivially can return nothing while the insert still happens unconditionally.

### Impact Explanation
A malicious outbound sync peer, once selected as the most-reliable source for one or more `AttachmentRequest`s, can return arbitrary distinct byte blobs for each request. Every such blob becomes a new row in the node's `attachments` SQLite table tagged `was_instantiated = 1`, consuming disk space with content that has no relationship to any BNS `AttachmentInstance` the node has ever tracked, and that is never evicted by existing cleanup logic. This is unbounded, attacker-controlled storage growth on a state table that should only ever contain data corresponding to confirmed on-chain BNS commitments — matching the "attachment/BNS mismatch" / storage-exhaustion High-severity category. It does not directly cause a crash, but produces persistent state divergence from what consensus committed and consumes disk resources with each additional distinct hash the attacker chooses.

### Likelihood Explanation
- The attacker only needs to be a normal, reachable peer that a node includes in `network.get_outbound_sync_peers()` and that legitimately responds to some Atlas inventory/attachment requests to build up a `ReliabilityReport` — no signing key, RPC secret, or admin role is required.
- Once selected as the most-reliable source for a `content_hash`, the attacker's response is accepted verbatim, so the attack is fully repeatable for every subsequent request it wins.
- Attacker cost is minimal: run a p2p-reachable node and answer HTTP GET `/v2/attachments/<hash>` requests with self-consistent garbage.
- Preconditions (a real BNS name op existing to trigger a pending `AttachmentInstance`/request) are ordinary and occur naturally on any node syncing BNS zonefiles.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; treat a mismatch as a failed/faulty request (`report.bump_failed_requests()`, and consider marking the peer as unreliable/faulty). Additionally, in the `Done` branch of `AttachmentsDownloader::run` (`download.rs:153-169`), only call `insert_instantiated_attachment` when `attachments_instances` (or the batch's own tracked `content_hash` set) is non-empty for that hash, so unrequested/unmatched content is never persisted as instantiated.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
