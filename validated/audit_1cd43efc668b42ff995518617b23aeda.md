### Title
Wallet Contract skips the address-registrar check for unparsable-calldata / self-action base-token transfers, permanently misdirecting funds sent to a registered named account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs)

### Summary
The report describes a cross-domain identity-translation bug: a bridge encodes an address as the destination on another chain, assuming that address is controlled by the same party there, without verifying that assumption — risking permanent misdirection/loss of funds to an address the intended recipient doesn't control. NEAR's ETH-implicit **Wallet Contract** performs an analogous translation between Ethereum-style addresses and NEAR account IDs, and it has a purpose-built defense (the **Address Registrar**) for exactly this class of bug — but that defense is only invoked on one of three code paths that route base-token transfers to another eth-implicit-shaped `target`.

### Finding Description
The Wallet Contract lets an Ethereum-style transaction (submitted via `rlp_execute`) act on a NEAR account. Because Ethereum transactions only carry a raw 20-byte `to` address, the relayer supplies a NEAR `target: AccountId`, and the contract must decide whether the address in the signed transaction really identifies that account. `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:221-232` (`parse_target`) classifies the `target` as `CurrentAccount`, `EthImplicit(address)`, or `OtherNearAccount`.

When `target` is `EthImplicit(address)` (i.e., a "0x…" NEAR account different from the current one), the protocol must decide whether the address has actually been claimed by some *named* NEAR account through the `AddressRegistrar` contract (`runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs:37-86`, `register`), in which case funds must be routed to the named account, not to the literal `0x…` account id, because nobody may hold the secp256k1 private key that would let them ever control that literal implicit account (the registrar hashes the account-id *string*, not a public key: `account_id_to_address`, `address-registrar/src/lib.rs:114-119`).

`parse_rlp_tx_to_action` (`internal.rs:83-157`) implements this check **only** in one of three `TargetKind::EthImplicit` branches:

- Line 107-122: calldata recognized as an emulated ERC-20 call (`ParsableTransactionKind::EthEmulation`) but target is `EthImplicit` → sets `address_check: Some(address)`, which triggers a `lookup` against the `AddressRegistrar` before transferring (`lib.rs:412-432`, `address_check_callback`, `lib.rs:130-192`).
- Line 87-106: calldata recognized as a `SelfNearNativeAction` (AddKey/DeleteKey) but target is `EthImplicit` → falls back to a plain `Transfer` to `target` with `address_check: None` (no registrar lookup).
- Line 123-155: calldata is **not parsable** at all (`UserError::InvalidAbiEncodedData` / `UnknownFunctionSelector`) and target is `EthImplicit` → also falls back to a plain `Transfer` to `target` with `address_check: None` (no registrar lookup).

In `inner_rlp_execute` (`lib.rs:412-471`), only the `address_check: Some(_)` variant is routed through the registrar-lookup/callback flow; the `address_check: None` variants fall into the generic `_ =>` branch (`lib.rs:466-470`) and transfer directly to the literal `target` AccountId via `action_to_promise` (`lib.rs:475-483`).

This is precisely the scenario the external report warns about: the sender's Ethereum-style tooling only knows a 20-byte address; the protocol must decide who controls that address on the "destination" identity space (NEAR account IDs). The registrar exists to answer that question correctly, but two of the three call paths that can transfer native tokens to another `EthImplicit`-shaped target skip the check entirely — meaning the correctness of fund delivery for the most common case (a plain, non-selector-matching Ethereum "send" — i.e., the majority of ordinary base-token transfers, which carry empty or non-ABI calldata) depends on an unverified assumption that the literal `0x…` account, not any registered named account, is the intended and controllable recipient.

### Impact Explanation
If an address has been registered by a named account (e.g., `alice.near` registers `hash("alice.near")` via `AddressRegistrar::register`) to receive base-token payments from Ethereum-style wallets, and a Wallet-Contract user sends a plain native-token transfer (empty/unparsable calldata, the standard EOA-to-EOA case) to that address, the funds are sent to the literal `0x…` eth-implicit account instead of to `alice.near`. Because that literal account's address was derived by hashing an arbitrary account-id string rather than a real secp256k1 public key, it is computationally infeasible for anyone (including Alice) to ever find a private key controlling it. NEAR's implicit-account-creation-by-transfer semantics (`action_implicit_account_creation_transfer`, documented in `docs/DataStructures/Account.md:108-122`) mean this account is created and the tokens are irrecoverably locked in it — a permanent freezing (effectively theft/loss) of funds, matching the exact "destination the recipient doesn't control" bug class from the report.

### Likelihood Explanation
Reaching this path requires only ordinary user/relayer interaction with a deployed Wallet Contract (`rlp_execute`), no privileged or validator access. It is triggered by the routine, unremarkable case of a plain ETH-style value transfer (calldata that is empty or fails the ABI selector match), which is arguably the *most common* transaction type wallets emit — more common than the ERC-20-shaped calldata that the code does protect. The bug requires the target address to coincide with one registered in the `AddressRegistrar`, which is an intended, documented use of that registry (to let named accounts receive Ethereum-tooling payments), making the precondition realistic rather than contrived.

### Recommendation
Apply the registrar `address_check` uniformly to every code path that would transfer tokens to a `TargetKind::EthImplicit(address)` target, not only the ERC-20-emulation branch — i.e., also set `address_check: Some(address)` for the `SelfNearNativeAction`-with-mismatched-target branch (`internal.rs:87-106`) and the unparsable-calldata branch (`internal.rs:123-155`), so all of them are gated through `address_check_callback`'s registrar lookup before defaulting to a direct transfer to the literal eth-implicit account id.

### Proof of Concept
1. Alice owns `alice.near` and calls `AddressRegistrar::register("alice.near")`, obtaining address `0xAAA…` (`address-registrar/src/lib.rs:37-86`).
2. Bob controls a deployed Wallet Contract at a different eth-implicit account `0xBBB…`.
3. Bob's wallet (ordinary Ethereum tooling) constructs a plain value-transfer transaction: `to = 0xAAA…`, some `value`, and calldata that is empty or does not match any of `FUNCTION_CALL_SELECTOR/TRANSFER_SELECTOR/ADD_KEY_SELECTOR/DELETE_KEY_SELECTOR/ERC20_*` (`types.rs:13-47`, `eth_emulation.rs:16-25`).
4. A relayer (honest or not — the wallet contract cannot distinguish) calls `rlp_execute(target = "0xAAA...", tx_bytes_b64)`.
5. `parse_target` returns `TargetKind::EthImplicit(0xAAA)` (`internal.rs:221-232`); `parse_tx_data` returns `Err(UserError::InvalidAbiEncodedData)` (`internal.rs:240-242`); the match at `internal.rs:123-155` hits `TargetKind::EthImplicit(_) => address_check: None`.
6. `inner_rlp_execute`'s `_ =>` branch (`lib.rs:466-470`) directly executes `Promise::new("0xAAA...").transfer(...)`, creating/crediting the literal eth-implicit account `0xAAA…` instead of routing to `alice.near`, even though `0xAAA…` is registered to `alice.near` in the `AddressRegistrar`.
7. Funds are now held by an implicit account for which no known private key exists — permanently inaccessible to Alice (or anyone).

Note: I could not execute this scenario against a live network/test harness (index access only); the control-flow trace above is based on direct reading of `internal.rs`, `lib.rs`, `types.rs`, and `eth_emulation.rs`, and I found existing unit tests only for `user_error.rs` cases, not one that specifically exercises "unparsable calldata to a registered address." A Devin session with repository/test access would be needed to confirm this via an integration test that registers an address and submits an unparsable-calldata `rlp_execute` transaction targeting it.
