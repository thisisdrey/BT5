### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` via cheap `FreezeBalanceContract` delegation spam - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
When the legacy (non-optimized) delegated-resource indexing path is active, any account can call `FreezeBalanceContract` with a `receiverAddress` repeatedly, each time appending a new receiver to a single, unbounded protobuf list stored under one DB key (`DelegatedResourceAccountIndexStore`). There is no cap on the number of entries, and the cost per entry is minimal (1 TRX temporarily frozen plus, for new receivers, a one-time account-activation fee), enabling an attacker to bloat a single record indefinitely, mirroring the reported `userAddresses` spam pattern from the external report.

### Finding Description
`FreezeBalanceActuator.execute()` calls `delegateResource()` whenever a `receiverAddress` is present and `dynamicStore.supportDR()` is true. [1](#0-0) 

Inside `delegateResource()`, when `dynamicStore.supportAllowDelegateOptimization()` is `false` (legacy mode), the code loads the owner's `DelegatedResourceAccountIndexCapsule`, checks whether the receiver is already in `toAccountsList`, and if not, calls `addToAccount(...)`, which appends unconditionally to the underlying protobuf `repeated` field with no size limit. The same happens symmetrically for the receiver's `fromAccountsList`. [2](#0-1) 

`addToAccount`/`addFromAccount` in the capsule simply append to the list with no bound check: [3](#0-2) 

The only requirement to add a *new, unique* entry is a distinct `receiverAddress` that already exists as an account (created cheaply via a 0.1 TRX-class account activation) and a `frozenBalance` of at least 1 TRX per `FreezeBalanceActuator.validate()`: [4](#0-3) [5](#0-4) 

Because the whole `toAccountsList`/`fromAccountsList` is stored as one serialized protobuf value under a single DB key (the owner's/receiver's address), every read (`get`), every subsequent delegate/undelegate, and the `convert()` migration routine must deserialize and iterate the *entire* list: [6](#0-5) 

The same unbounded list is also returned wholesale by the `GetDelegatedResourceAccountIndex`/V2 HTTP and gRPC query paths (`Wallet.getDelegatedResourceAccountIndex`), meaning an attacker can force any single query response, and every re-serialization on delegate/undelegate, to carry an ever-growing payload.

### Impact Explanation
An attacker with a modest, mostly-recoverable amount of TRX (1 TRX frozen per entry, refunded after the freeze duration, plus a small one-time activation fee per new receiver address) can append arbitrarily many entries into a single account's `DelegatedResourceAccountIndexCapsule` record. This:
- Causes unbounded growth of a single DB value with no cap, unlike normal expected usage patterns (delegating to a handful of contracts/nodes).
- Increases CPU/serialization cost for every subsequent `FreezeBalance`, `UnfreezeBalance`, `DelegateResource`, and `UnDelegateResource` transaction touching that account, since `toAccountsList`/`fromAccountsList` must be fully rebuilt (`new ArrayList<>(...)`, `.remove(...)`, `setAllToAccounts(...)`) each time.
- Bloats the response of the public `getDelegatedResourceAccountIndex`/V2 API endpoints, degrading service for any consumer (wallets, explorers, liquidation/monitoring bots) that queries an attacker-targeted address.
- The `convert()` legacy-migration routine iterates the full list on every account touched during the optimization migration, so a bloated record can materially slow down that one-time migration path as well.

This matches the "Medium" impact class of the referenced report: a resource/DoS-style degradation reachable by an unprivileged, low-cost transaction, without requiring any special privilege.

### Likelihood Explanation
Reachable by any account holder via a standard, broadcastable `FreezeBalanceContract` transaction — no special permission, witness/SR status, or contract deployment needed. The per-entry cost is very low (1 TRX, largely refundable, plus a small account-activation fee for new receiver addresses), so an attacker can cheaply generate large numbers of distinct receiver addresses and repeat the delegate call to grow the list without bound. The only gating condition is that `dynamicStore.supportAllowDelegateOptimization()` be `false`, i.e., this legacy code path being active for the network/version under test; where it is active (older networks, or in migration windows) the vector is straightforwardly exploitable.

### Recommendation
Add an explicit cap (e.g., a hard-coded or dynamic-parameter maximum) on the number of entries permitted in `toAccountsList`/`fromAccountsList` inside `delegateResource()` before calling `addToAccount`/`addFromAccount`, rejecting the contract with a `ContractValidateException` (or a no-op in `execute`) once the cap is reached. Alternatively, migrate fully to the V2 index scheme (`supportAllowDelegateOptimization()==true`), which stores each delegation under its own DB key rather than as an ever-growing single serialized list, and ensure legacy paths are deprecated/disabled by default going forward.

### Proof of Concept
1. Ensure `dynamicStore.supportAllowDelegateOptimization()` is `false` on the target network (legacy path).
2. As attacker `A`, create `N` fresh receiver accounts `R_1..R_N` (activate each with a minimal TRX transfer).
3. For each `R_i`, submit a `FreezeBalanceContract` from `A` with `frozenBalance = 1_000_000` (1 TRX), `resource = BANDWIDTH` (or `ENERGY`), and `receiverAddress = R_i`.
4. Each transaction is accepted by `FreezeBalanceActuator.validate()`/`execute()` and appends `R_i` to `A`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` via `delegateResource()`.
5. Repeat for large `N`; observe `A`'s `DelegatedResourceAccountIndexStore` record and the response of `getDelegatedResourceAccountIndex(A)` growing without bound, and subsequent freeze/unfreeze operations on `A` (or on any `R_i`, via `fromAccountsList`) becoming progressively more expensive due to full-list deserialization/rebuild in `UnfreezeBalanceActuator` and `DelegatedResourceAccountIndexStore.convert()`.

Note: I could not fully verify, within the available index, the exact current default value of `supportAllowDelegateOptimization()` on mainnet or the precise account-activation fee constant, since those runtime/dynamic-parameter values are not fully covered by the code index. A Devin session with full repository and possibly live-node access would be needed to confirm the exact default configuration and quantify current spam cost precisely.

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();

    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);

      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);

      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
