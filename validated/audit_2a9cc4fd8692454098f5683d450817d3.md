### Title
Nonce-reseed collision on delete/re-add of an access key within the same block enables signed-transaction replay - (File: runtime/runtime/src/access_keys.rs)

### Summary
`initial_nonce_value` reseeds a re-added access key's nonce purely as a function of `block_height` (`(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`), with no memory of nonces actually consumed by a prior incarnation of the same public key within that same block. If the same public key is deleted and re-added twice at the same `block_height`, both reseeds produce a byte-identical nonce floor, and a previously executed transaction signed against the first incarnation can be replayed successfully against the second incarnation.

### Finding Description
`action_delete_key`/`delete_regular_key` (runtime/runtime/src/access_keys.rs:52-147) remove the `AccessKey` trie entry without persisting the consumed nonce anywhere ("no graveyard"). `add_regular_key` (runtime/runtime/src/access_keys.rs:230-255) then reseeds any newly (re-)added key's nonce to `initial_nonce_value(apply_state.block_height)` [1](#0-0) , a value that depends solely on the current block height, not on the account's or key's prior history.

The comment at line 47-49 explains this seeding exists specifically to defeat replay of a captured old signed transaction after key deletion/recreation (referencing near/nearcore#3779), relying on the invariant that `block_height` for the re-add is strictly greater than the block height at which any old transaction against the prior incarnation was accepted, and that `verify_nonce`'s `NonceTooLarge` check (`runtime/runtime/src/verifier.rs:229-235`) bounds any nonce used at height `h` to be `< h * MULTIPLIER`, so a subsequent reseed at height `h' > h` is guaranteed to floor above it.

That invariant assumes exactly one delete/add cycle per block height for a given key. It breaks if the *same* public key is deleted and re-added *twice* within one block (same `block_height` for both reseeds):

1. Key `pk` exists, used normally with nonce `n`.
2. `DeleteKey(pk)` executes → trie row removed, no state trace of `n`.
3. `AddKey(pk)` executes at height `H` → `access_key.nonce = floor = (H-1)*MULTIPLIER`.
4. A transaction signed with `pk`, `nonce = floor+1` (e.g. a `Transfer`), executes successfully → `access_key.nonce = floor+1`. This transaction is captured by the attacker.
5. `DeleteKey(pk)` executes again, still at height `H`.
6. `AddKey(pk)` executes again, still at height `H` → reseeds to the **same** `floor` value as in step 3 (byte-identical, since `initial_nonce_value` only depends on `H`).
7. The captured transaction from step 4 (`nonce = floor+1`) is resubmitted. `verify_nonce` (Monotonic mode) only checks `tx_nonce > current_nonce`; since `current_nonce = floor` again, `floor+1 > floor` passes, and the transaction (e.g., the `Transfer`) is executed a second time.

None of the existing checks catch this: `verify_nonce` (runtime/runtime/src/verifier.rs:211-237) only compares against the access key's current on-trie nonce, which was reset backward by step 6; there is no separate replay-hash cache or "highest nonce ever seen for this key" ledger that survives a delete. The nonce upper-bound check (`NonceTooLarge`) is also satisfied because `floor+1 < H*MULTIPLIER`.

The attacker needs to control a `FullAccess` key on the account (either `pk` itself, since deleting/re-adding one's own signing key mid-transaction-list is permitted, or a second helper `FullAccess` key) to issue the `DeleteKey`/`AddKey` action pairs, and needs all six transactions to land in application order within the same block/chunk apply pass (all sharing one `apply_state.block_height`) — feasible since the attacker fully controls submission of their own transactions and both keys.

### Impact Explanation
This allows an unprivileged account owner to double-execute one of their own previously-signed transactions (e.g., a `Transfer`, `FunctionCall`, or other action) by exploiting the reseed collision, effectively defeating the nonce anti-replay mechanism the code explicitly claims to provide (per the #3779 reference). Depending on the replayed transaction's actions this could duplicate a `Transfer` receipt (double-spend against a receiver, e.g. draining a discount/promo contract that only checks "have I seen this nonce/signature before" via the chain's canonical replay protection), or duplicate any other stateful side effect an idempotency-unaware contract relies on nonce-uniqueness for. This maps to the "double-spend/replay" bounty category.

### Likelihood Explanation
The attacker only needs an account they control with a `FullAccess` access key (or two), no special privileges. They must construct and submit an ordered sequence of transactions (`DeleteKey`, `AddKey`, victim tx, `DeleteKey`, `AddKey`, replay) that all get included and applied in the same block/chunk, in that exact order. This is plausible for a determined self-attacker submitting a tight burst of transactions to a single RPC/chunk producer, but landing all six in one specific order within a single block is not fully guaranteed by the attacker (it depends on mempool/chunk inclusion behavior), making this a non-trivial but plausible and repeatable griefing-of-self / replay primitive rather than a trivially always-exploitable bug. I was not able to fully verify from the indexed code whether the mempool/chunk-producer transaction-pool ordering guarantees this exact sequential inclusion within one chunk for interleaved keys of the same account (this warrants a runtime/test-loop integration test to confirm reproducibility end-to-end).

### Recommendation
Do not let `initial_nonce_value` depend solely on `block_height`. Persist a per-account (or per-account+pubkey) monotonic "last seen nonce/incarnation" watermark that survives key deletion (e.g., store the maximum nonce ever used, or an incarnation counter, in account-level state rather than solely in the deletable `AccessKey` trie row), and seed newly added keys' nonces to `max(initial_nonce_value(block_height), persisted_watermark + 1)`. Alternatively, disallow deleting and re-adding the exact same public key more than once within a single block/chunk apply, or bump the floor by a strictly-increasing per-block sequence counter each time the same key is recreated within one block.

### Proof of Concept
Runtime/test-loop integration test plan (extending the pattern of `access_key_nonce_for_implicit_accounts.rs`'s `test_transaction_hash_collision`):
1. Create account `alice` with a `FullAccess` key `pk0`.
2. At block height `H`, submit in order within the same chunk/apply:
   - `tx1`: `DeleteKey(pk0)` signed by a second `FullAccess` key `pk1` (added at genesis alongside `pk0`).
   - `tx2`: `AddKey(pk0, FullAccess)` signed by `pk1`.
   - `tx3`: `Transfer(1 yoctoNEAR)` from `alice` to `bob`, signed by `pk0` with `nonce = initial_nonce_value(H) + 1`. Capture `tx3` bytes/hash and record `bob`'s balance after this executes.
   - `tx4`: `DeleteKey(pk0)` signed by `pk1`.
   - `tx5`: `AddKey(pk0, FullAccess)` signed by `pk1`.
   - `tx6`: resubmit the exact captured `tx3` bytes.
3. Assert all six transactions land in the same block (same `apply_state.block_height`).
4. Assert `tx6` is accepted (`ProcessTxResponse::ValidTx` / `FinalExecutionStatus::SuccessValue`) rather than rejected with `InvalidTxError::InvalidNonce`.
5. Assert `bob`'s balance increased by `2 yoctoNEAR` total (i.e., the transfer was applied twice), proving the replay succeeded. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```

```rust
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
```
