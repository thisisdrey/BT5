This confirms the vulnerability class: the `pipe.Write` backpressure implementation in `internal/streamcache/pipe.go` computes the writer's progress cursor (`rcursor`) as the position of the **slowest reader**, i.e. `p.rcursor.Position()` reflects the minimum progress among all subscribed `pipeReader`s [1](#0-0) , and `Write` blocks whenever `wcursor.Position() > rcursor.Position()` until a reader (any reader) advances [2](#0-1) . This is exactly the resource-griefing pattern from the report, translated to Gitaly's domain.

### Title
Fetch-negotiation griefing via pack-objects cache backpressure stalls concurrent `git-pack-objects` processes for unrelated clients - (File: internal/streamcache/pipe.go)

### Summary
Gitaly's pack-objects cache (used by `PostUploadPackWithSidechannel` / `SSHUploadPack` fetches) streams the output of a single `git-pack-objects` process to every concurrent client that requests the same cache key, using a shared `pipe` with backpressure enabled by default [3](#0-2) . The pipe writer is only allowed to advance as fast as its *slowest* reader [2](#0-1) . An unprivileged fetch client can open a sidechannel connection that matches the cache key of a legitimate, concurrent fetch and then simply stop reading (or read at a crawl), forcing the shared `git-pack-objects` process — and the CPU/memory/IO resources it holds — to stall for every other client sharing that cache entry, without the attacker paying any of that cost or being charged/limited for it. This mirrors the `RefuelAction`/`TransferAction` gas-griefing pattern: an attacker-controlled peer's inaction/failure causes the shared resource-consuming operation to be paid for entirely by other, honest parties, with no compensating mechanism.

### Finding Description
When `packObjectsHook` receives a `PackObjectsHookWithSidechannelRequest`, it computes a cache key from the request's repository/args/protocol/stdin and calls `s.packObjectsCache.Fetch(ctx, cacheKey, output, ...)` [4](#0-3) . If a `git-pack-objects` process is already running (or writing to disk) for that key, additional concurrent requesters attach as extra readers to the same underlying `pipe` rather than spawning a new process, as documented in `doc/design_pack_objects_cache.md`.

The `pipe` implementation explicitly ties the writer's forward progress to the slowest attached reader:
- `wcursor` tracks total bytes written.
- `rcursor` tracks the *minimum* position among all open `pipeReader`s [1](#0-0) .
- `Write()` blocks in a loop while `wcursor.Position() > rcursor.Position()`, i.e. while any subscribed reader has fallen behind [2](#0-1) .

This is acknowledged as an operational risk in the project's own documentation: "`git-pack-objects` processes may remain in a waiting state until the fastest client requesting the same cache key completes its operation. During this waiting period, these processes can occupy substantial server resources," and lists "Hung `git-pack-objects` processes occupying excessive server resources" as a symptom administrators are told to watch for [5](#0-4) . Backpressure is enabled by default (`backpressure = true`) [6](#0-5) .

Crucially, an attacker does not need to be a privileged actor or hold any special access — any user able to trigger a fetch (`git clone`/`git fetch` via SSH or HTTP) against a repository they can read is able to:
1. Send a `want`/`have` negotiation that produces the same cache key as an ongoing, legitimate fetch from another client (e.g., a CI runner or another ordinary user fetching the same ref set concurrently), reachable via `PostUploadPackWithSidechannel` [7](#0-6) .
2. Attach as an additional `pipeReader` to the shared cache entry.
3. Simply stop reading from the sidechannel connection (or throttle reads to near zero), which is entirely under the attacker's control and costs the attacker nothing (they hold one TCP/Unix-socket connection open).
4. Because `rcursor` reflects the slowest reader, the single shared `git-pack-objects` process serving all readers (including honest, paying clients) stalls, tying up the process' CPU/memory/file-descriptor footprint on the Gitaly node for as long as the attacker withholds reads (or until some external timeout intervenes).

The `Fetch` operation is only accounted for/limited when it is created (a cache miss) — cache hits (and pipe-attached readers) explicitly bypass the RPC concurrency limiter per the documented "cost-aware admission" design, since they are assumed to be cheap "disk streaming" [8](#0-7) . This assumption is invalidated by the backpressure design: an attached reader is not cheap when it can stall the shared writer indefinitely, so the "fee"/limiting logic never re-evaluates or charges for the actual resource cost incurred, exactly like the `RefuelAction` fee being computed only in the successful, non-griefed path.

### Impact Explanation
An unauthenticated-adjacent or low-privilege client (anyone with fetch access to a repository) can hold open a slow/stalled sidechannel read to force Gitaly to keep a `git-pack-objects` subprocess (and its memory/CPU allocation for the packfile computation) alive far longer than necessary, degrading service for every other client fetching the same objects concurrently and consuming server resources without commensurate accounting or throttling, since these piggy-backed readers bypass the concurrency limiter. Repeated in parallel across many cache keys, this can produce a resource-exhaustion/DoS condition on the Gitaly node — the same "victim pays, attacker doesn't" asymmetry described in the source report, mapped onto Gitaly's RPC-handler resource limits rather than gas accounting.

### Likelihood Explanation
Likelihood is moderate-to-high in environments with the pack-objects cache and backpressure enabled (the default), which is the recommended production configuration for busy GitLab instances with many concurrent CI fetches — precisely the scenario the cache was built for [9](#0-8) . No special timing/front-running precision is required (unlike the EIP-7702 front-run in the original report): the attacker only needs to issue a fetch that collides with an active cache key and then withhold reads, which is straightforward to arrange by fetching the same popular ref (e.g., default branch) concurrently with other traffic.

### Recommendation
- Bound the amount of time (or bytes-behind) a slow reader is allowed to stall the shared writer; forcibly detach/close readers that fall too far behind rather than blocking the producer indefinitely (a partial mitigation already exists as documented — disabling backpressure — but that has its own I/O-pressure tradeoffs, and readers should be evicted rather than simply written past).
- Feed pipe-attached ("hit"/shared) readers into the load/burden-monitoring and concurrency-limiting system so that a reader that is actively delaying a shared producer is accounted for and can be throttled or cancelled by the `LoadShedder`, rather than being unconditionally exempt as a "cheap" cache-served request.
- Consider a per-reader read-progress timeout independent of the overall RPC deadline, mirroring the negotiation-phase `ReadMonitor` pattern already used elsewhere in Gitaly to bound TOCTOU-style stalls [10](#0-9) .

### Proof of Concept
1. Enable the pack-objects cache with backpressure (default) on a Gitaly node.
2. Client A starts a legitimate `git fetch` of a large ref set via `PostUploadPackWithSidechannel`, causing a cache miss and spawning `git-pack-objects` for cache key `K`.
3. Attacker B, with only read access to the same repository, issues a fetch request that negotiates the same `want`/`have` set (reproducing key `K`) while A's fetch is still in flight, attaching as a second `pipeReader` on the same `pipe`.
4. Attacker B stops reading from its sidechannel socket (e.g., stalls after the TCP handshake without draining the pktline stream).
5. Because `pipe.Write` blocks while `wcursor.Position() > rcursor.Position()` and `rcursor` reflects B's stalled position [2](#0-1) , the shared `git-pack-objects` process backing both A's and B's fetch stalls, and A's legitimate fetch stops progressing/servedBytes stops increasing (observable via `gitaly_pack_objects_generated_bytes_total`) — reproducing the resource-hold documented as an operational hazard in `doc/design_pack_objects_cache.md`.

Note: I was not able to execute this against a live Gitaly instance (no runtime/filesystem access in this environment) to confirm the exact observable stall duration or whether any additional guard (e.g., RPC deadline) mitigates it in practice; the finding is based on static analysis of `pipe.go`'s backpressure algorithm and the project's own documentation acknowledging the hazard.

// A cursor is an integer value with a list of subscribers (see cursor.go).

// cursor datatype works, the rcursor counter reflects the file position of
// the fastest reader. The writer is the sole subscriber of rcursor.
// Before each write, the writer checks the rcursor counter to make sure

func (p *pipe) Write(b []byte) (int, error) {
	// Loop (block) until at least one reader catches up with our last write.
	if p.backpressure {
		for p.wcursor.Position() > p.rcursor.Position() {
			select {
			case <-p.wcursor.Done():
				// Prevent writing bytes no-one will read
				return 0, errWrongCloseOrder
			case <-p.wnotifier.C:
			}
		}

		select {
		case <-p.wcursor.Done():
			return 0, errWrongCloseOrder
		default:
		}
	}

	// In that case, that separate goroutine will be responsible for closing

		}

				stdin,
				cacheKey,

## Problem scope

We designed this cache to solve a specific problem on GitLab.com: high

```markdown
### Cost-Aware Admission

A separate admission layer that sits before the concurrency limiter in the
gRPC interceptor chain. If a request can be served from
[`streamcache`](../internal/streamcache/cache.go), it bypasses the concurrency
limiter entirely and proceeds directly to the handler. Currently this applies
to:

- [`PostUploadPackWithSidechannel`](../internal/gitaly/service/smarthttp/upload_pack.go) (clone/fetch)

```plaintext
Request -> Cost-Aware Admission -> Concurrency Limiter -> Handler
                 |
           (cache hit?)
                 |
           bypass limiter -> Handler directly
```

The concurrency limiter today treats every request as equally expensive. In
practice, requests served from cache consume minimal resources (disk streaming)
while cache misses run full Git subprocess pipelines. Rather than feeding the
limiter a cost hint (which still consumes a limiter slot), cache-hit requests
skip the limiter entirely — keeping the concurrency limiter pure and ensuring
limits designed for expensive operations do not penalize cheap ones.

This separation also keeps the concurrency limiter's responsibility narrow: every
request that reaches it is treated as expensive.
```
