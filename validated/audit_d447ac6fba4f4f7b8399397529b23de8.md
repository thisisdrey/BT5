### Title
Unbounded caller-supplied `estimated_len` causes u64 multiplication overflow in `estimate_tx_fee_from_cost_and_length` - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` accepts a fully caller-controlled `estimated_len: Option<u64>` JSON field with no upper-bound validation, and only takes its `max()` with the actual decoded transaction payload length. This unconstrained value is later multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length` without any overflow-safe arithmetic.

### Finding Description
In `try_parse_request` [1](#0-0) , the handler computes:
```
let estimated_len = std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64);
```
`body.estimated_len` is deserialized directly from the JSON request body [2](#0-1)  with no range check against `MAX_PAYLOAD_LEN` or any sane transaction size limit. The only size guard present, `content_len < MAX_PAYLOAD_LEN` [3](#0-2) , bounds the raw HTTP body's byte length, not the numeric *value* of the `estimated_len` JSON field — a compact literal like `18446744073709551615` fits easily within a small HTTP body.

This attacker-controlled `estimated_len` is passed straight through to `estimate_tx_fee_from_cost_and_length`, where:
```
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
```
is computed with no bounds check or checked/saturating arithmetic [4](#0-3) . Since `MINIMUM_TX_FEE_RATE_PER_BYTE` is a nonzero constant, any `estimated_len` close to `u64::MAX` overflows this multiplication. In a debug build (where Rust's `debug_assertions` are enabled), this triggers a runtime panic; in a release build without `overflow-checks`, it silently wraps around to an arbitrary small value, which is then used as the minimum served fee.

No authentication, secret, or privileged role is required to reach `/v2/fees/transaction` — the handler performs no RPC-secret check before `try_parse_request`/`try_handle_request` runs.

### Impact Explanation
An unauthenticated remote caller can send a single POST to `/v2/fees/transaction` with a crafted `estimated_len` value near `u64::MAX` and a minimal valid `transaction_payload`. In debug builds, this crashes the request-handling thread with an arithmetic-overflow panic — a single-message remote DoS. In release builds without overflow checks, the multiplication silently wraps, causing the node to report a bogus (typically very small) minimum fee to any wallet or bridge relying on this endpoint for fee estimation, undermining the integrity of served fee data.

### Likelihood Explanation
The endpoint is a standard, publicly reachable RPC route with no authentication gate shown in this handler, requires only a single crafted HTTP POST, and needs no peer state, StackerDB slot, or prior handshake. Attacker cost is negligible and the issue is trivially repeatable per request.

### Recommendation
Clamp/validate `body.estimated_len` against a sane maximum (e.g., `MAX_PAYLOAD_LEN` or block size limit) in `try_parse_request`, rejecting values outside a reasonable range, and use `checked_mul`/`saturating_mul` for `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length` to avoid overflow regardless of upstream validation.
