No vulnerability found for this question.

**Reasoning:** The report's premise doesn't match `crates/primitives/token-id/src/nep141.rs`. `Nep141TokenId` has no sub-id field at all — it only wraps a `contract_id: AccountId`, and its `FromStr`/`Display` simply defer to `AccountId`'s own strict parsing (which disallows `:`, empty strings, and non-ASCII characters), so there is no `split_once(':')` call and no sub-id round-trip issue in this file at all. [1](#0-0) 

The `split_once(':')`-based parsing the question describes actually exists in `Nep171TokenId` and `Nep245TokenId`, not `Nep141TokenId`. [2](#0-1) [3](#0-2) 

Even there, the exploit described doesn't hold: `split_once` splits only on the *first* colon, and everything after it (which may itself contain colons) is stored verbatim as the `nft_token_id` / `mt_token_id` string field without further parsing. `Display` re-emits `"{contract_id}:{token_id}"` unchanged, so a sub-id containing colons round-trips correctly — `contract:sub:extra` → `contract_id="contract"`, `token_id="sub:extra"` → re-displays as `contract:sub:extra"`, identical to the original. There is no divergence between the written and read-back id for any input that successfully parses as an `AccountId` for the contract part. [4](#0-3) 

Existing tests already assert this round-trip property for all three token-id kinds and for the top-level `TokenId` enum using `arbitrary`-generated random values, including edge cases via property-based generation. [5](#0-4) [6](#0-5) 

No path exists through `mt_transfer_call`/`mt_batch_transfer_call` with attacker-chosen `token_ids` that causes the `Nep141TokenId` Display/FromStr binding to diverge, since that type has no sub-id to manipulate at all.

impl FromStr for TokenId {
    type Err = TokenIdError;

    #[inline]
    fn from_str(s: &str) -> Result<Self, Self::Err> {
        let (typ, data) = s
            .split_once(':')
            .ok_or(strum::ParseError::VariantNotFound)?;
        match typ.parse()? {
            TokenIdType::Nep141 => data.parse().map(Self::Nep141),
            TokenIdType::Nep171 => data.parse().map(Self::Nep171),
            TokenIdType::Nep245 => data.parse().map(Self::Nep245),
            TokenIdType::Imt => data.parse().map(Self::Imt),
        }
    }
}
