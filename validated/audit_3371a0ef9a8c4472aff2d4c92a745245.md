This confirms the analog: Gitaly's `ObjectPoolService` has no membership/reference tracking mechanism analogous to LP "shares." Any pool member can be linked via `LinkRepositoryToObjectPool` (writing an alternates file per [1](#0-0) ), but the object pool itself keeps no record of which repositories depend on it. `DeleteObjectPool` performs no safety check that other members still rely on the pool before removing it, exactly mirroring the LP-share vulnerability where a withdrawer can drain a resource that another unaccounted party still depends on.

### Title
Unaccounted Object Pool Membership Allows Any Caller to Delete a Pool Still Relied On By Other Repositories, Corrupting Them - (File: internal/gitaly/service/objectpool/delete.go)

### Summary
Gitaly's object pool mechanism deduplicates objects across repository forks by linking member repositories to a shared pool repository via an `objects/info/alternates` file [2](#0-1) . However, Gitaly never records, anywhere in its own state, which repositories are linked to a given pool. `DeleteObjectPool` removes the pool repository unconditionally as soon as `poolForRequest` resolves it, with no check of live members [3](#0-2) .

### Finding Description
Just like the Vader Synth-minting bug where minted Synths obtain no LP "shares," so an LP that owns 100% of tracked shares can withdraw all pooled assets even though a Synth-holder's funds still depend on that liquidity, Gitaly's `LinkRepositoryToObjectPool` RPC creates a dependency (a member repository's alternates pointing at the pool) without creating any corresponding "share"/reference record in the pool or in Gitaly's storage metadata [1](#0-0) . The `DeleteObjectPoolServiceServer` interface documentation explicitly acknowledges this: "There are no safety checks in place, so if any repository is still using this object pool it will become corrupted" and "It is the responsibility of the caller to ensure that it really has no members left, else any existing member will become corrupt" [4](#0-3) . The `DeleteObjectPool` handler then calls `repoutil.Remove` on the pool immediately once the request is validated, with no membership check whatsoever [3](#0-2) . Any ordinary, unprivileged gRPC caller able to invoke `ObjectPoolService.DeleteObjectPool` for a given storage/relative path (the same trust level required to invoke any other repository-scoped mutator RPC) can therefore delete a pool while other forks are still linked to it via alternates, exactly the LP-withdraws-while-Synth-still-owed-funds scenario from the referenced report.

### Impact Explanation
Once the pool is deleted, any member repository whose alternates still reference it loses access to all objects that were deduplicated into the pool (which, per `doc/object_pools.md`, is most objects for forked repositories) [5](#0-4) . Git operations against those repositories (clone, fetch, read, `git-fsck`) will fail with missing-object errors, corrupting all pool members that were not the caller-intended target — a availability/data-integrity impact directly analogous to the Synth holder being unable to withdraw because the underlying liquidity was removed by another party who was never tracked as sharing ownership of the resource.

### Likelihood Explanation
Reaching this requires only two ordinary RPC calls on repositories/pools the caller has legitimate but non-exclusive access to: `LinkRepositoryToObjectPool` establishing an unaccounted dependency, and `DeleteObjectPool` on the same pool from another actor (or the same actor unaware/uncaring of the shared members) [3](#0-2) . There is no privilege escalation, no leaked token, and no malicious peer required — it is a straightforward misuse of a documented-as-unsafe RPC pairing that any client library or automation using these RPCs could trigger accidentally or via a confused-deputy-style caller.

### Recommendation
Track object pool membership as first-class state (e.g., a manifest or reverse index of linked repositories maintained by `Link`/`DisconnectGitAlternates`) and have `DeleteObjectPool` refuse to proceed (or automatically disconnect remaining members first) when live members are still recorded, instead of relying purely on caller discipline as documented in `proto/objectpool.proto` [4](#0-3) .

### Proof of Concept
1. Create repository A and an object pool P from it via `CreateObjectPool`.
2. Link repository A to pool P via `LinkRepositoryToObjectPool`, causing A's `objects/info/alternates` to point at P and A's own duplicated objects to be repacked away [6](#0-5) .
3. Without disconnecting A, call `DeleteObjectPool` on P; the handler immediately resolves and removes P with no check that A is still linked [3](#0-2) .
4. Any subsequent read of repository A (e.g. via `CommitService`) fails to find objects that now only lived in the deleted pool, corrupting repository A analogous to the Synth holder losing funds when the LP withdrew all liquidity.

func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

		return fmt.Errorf("committing alternates: %w", err)

# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.
