### Title
StackerDB chunk signatures omit the target smart contract from the signed digest, enabling cross-StackerDB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures authenticate only `(slot_id, slot_version, data_hash)`, never the StackerDB's `smart_contract_id`. Because slot IDs are assigned per-database starting at 0 and the same signer principal frequently owns the same slot index across multiple independently-configured StackerDB instances (e.g. successive reward-cycle signer-set contracts), a chunk validly signed and gossiped for one StackerDB can be relayed by any observer (no private key required) and accepted as an authentic, fresh write into a *different* StackerDB, as long as the slot owner and version constraints happen to line up. This breaks the "authenticated for this contract vs. stored under that contract" equality that `try_replace_chunk`/`validate_received_chunk` are supposed to enforce.

### Finding Description
`SlotMetadata::auth_digest()` builds the signed hash from only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify()` recovers the public key from that digest and only checks it against the `principal` (slot owner) address supplied by the caller — it never checks which `QualifiedContractIdentifier` (StackerDB) the metadata is being verified against: [2](#0-1) 

Both write paths look up the slot owner *for the target contract* and then call `verify(&addr)` using this contract-agnostic digest:

- `StackerDBTx::try_replace_chunk` looks up `slot_validation` (owner + version) for `smart_contract`, then verifies the chunk against that owner without binding `smart_contract` into the signed data: [3](#0-2) 

- `StackerDBs::validate_received_chunk` does the same for gossiped/pushed chunks — it resolves the owner via `get_slot_signer(smart_contract_id, data.slot_id)` and calls `slot_metadata.verify(&addr)`, again with no contract binding in the digest: [4](#0-3) 

Because slot allocation is local to each StackerDB (slot IDs restart at 0 per contract, as shown by `create_stackerdb`/`reconfigure_stackerdb` assigning `slot_id` sequentially per contract) and StackerDB "control-plane" contracts are re-deployed/re-queried every reward cycle: [5](#0-4) 

the same signing principal will very often occupy the same `slot_id` across multiple contracts over time (e.g. the signer-set StackerDB contracts across successive reward cycles, where slot indices are derived from stacking rank and frequently recur for the same signers). Any relaying peer that has seen a legitimately-signed `StackerDBChunkData` broadcast for contract A can resend the exact same bytes, unmodified, tagged with a different `contract_id` (B), and the node will independently resolve B's slot owner, find it matches the embedded signature's recoverable address, and accept it as a fresh write for B — even though the original signer never authorized anything for B. This is a direct analog of the reported veNFT bug: the *authenticating token* (here, the signature) is not scoped to the *context it's meant to protect* (here, the specific StackerDB contract), so it can be legitimately-looking "moved" into a second context to duplicate/misattribute its effect, exactly as the transferable veNFT let the same voting power be counted twice across two contracts.

### Impact Explanation
This allows network-wide propagation of forged/misattributed data: a remote, unprivileged relayer (not the original signer) can cause a node to store, and gossip onward, stale or out-of-context chunk data under a *different* StackerDB contract as if it were freshly and correctly authorized for that contract, provided slot/version alignment. This falls under "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" since the write for contract B was never approved by anyone acting on B's behalf — the approval was scoped to A.

### Likelihood Explanation
Exploitation does not require compromising any key: the attacker only needs to capture a chunk broadcast (chunks are gossiped over the p2p `StackerDBChunkInvData`/push-chunk protocol, and served via `GET /v2/stackerdb/.../chunks` HTTP endpoints) and resend it against a second StackerDB whose slot-owner-to-slot_id mapping happens to coincide, which is likely across successive-reward-cycle signer StackerDBs since slot indices are stable/re-derived from the same stacking ranks. The remaining constraint (target slot version must be less than the replayed version) is easily satisfiable right after a StackerDB is reconfigured for a new cycle, since `reconfigure_stackerdb` resets `version` to `NO_VERSION`/0 for changed slots.

### Recommendation
Include the `smart_contract_id` (and ideally a chain/network identifier) in the `SlotMetadata::auth_digest()` computation, so a chunk signature is cryptographically bound to the specific StackerDB it is intended for. This requires a protocol/version bump for `StackerDBChunkData`/`SlotMetadata` since existing signed chunks would fail verification under the new digest.

### Proof of Concept
1. Signer S owns slot 0 in StackerDB contract A (e.g. `signers-1-1`) and also owns slot 0 in StackerDB contract B (e.g. `signers-1-2`), which is common since signer index assignment repeats across the per-cycle signer-set contracts.
2. S legitimately signs and pushes `StackerDBChunkData { slot_id: 0, slot_version: 5, sig, data }` for contract A. This is observed by any peer via `handle_unsolicited_StackerDBPushChunk` gossip.
3. An unrelated peer (attacker) resends the identical `StackerDBChunkData` (same `sig`, same `data`, same `slot_id`/`slot_version`) but wraps it with `contract_id = B` in a new `StackerDBPushChunkData`/HTTP POST to `/v2/stackerdb/.../chunks`.
4. `validate_received_chunk`/`try_replace_chunk` for contract B resolves slot 0's owner as S (via `get_slot_signer(B, 0)`), calls `slot_metadata.verify(&S_addr)`, which succeeds because the digest never referenced B, and the node stores/relays the chunk under B — the write required only that the auth-digest of `(slot_id=0, slot_version=5, data_hash)` matches, at `libstackerdb/src/libstackerdb.rs:159-193`, with the accepting code paths at `stackslib/src/net/stackerdb/db.rs:410-423` and `stackslib/src/net/stackerdb/mod.rs:679-697`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
