## Analysis

The reported bug class — depositing right before a reward epoch snapshot and withdrawing immediately after to capture a full epoch's reward without providing real economic backing — has a direct analog in java-tron's DPoS vote-reward system.

### Root cause

`VoteWitnessActuator.countVoteAccount()` lets any account re-point its TRON Power (frozen balance) to a different witness in *any* block, with zero fee (`calcFee()` returns `0`) and no cooldown: [1](#0-0) 

Reward accounting is cycle-based. `MaintenanceManager.doMaintenance()` computes each witness's per-vote reward index (`Vi`) for the ending cycle using the witness's **live vote count at maintenance time**, before that same maintenance call processes newly cast votes into the count: [2](#0-1) 

When a voter later withdraws/updates their vote, `MortgageService.withdrawReward()` (and its TVM analog `VoteRewardUtil.withdrawReward()`) settles their reward by multiplying the delta of the witness's accumulated `Vi` over `[beginCycle, endCycle)` by the voter's **current** vote count — treating that vote weight as if it had been held for the *entire* cycle, regardless of when within the cycle the vote was actually cast: [3](#0-2) [4](#0-3) [5](#0-4) 

Because `beginCycle` is only ever set to the *current* cycle number the moment a vote is cast (via the `withdrawReward()` call embedded in `countVoteAccount()`), an account that already has frozen TRON Power can:
1. Cast a vote for witness W in the last block before a maintenance/cycle rollover.
2. Receive the entire cycle's proportional reward share for W (computed from `Vi` deltas that are agnostic to how long the vote was actually held during the cycle).
3. Immediately re-vote away from W (or to any other witness) in the very next block, at zero cost and with no lockup, repeating the process for the next witness/cycle.

This dilutes the rewards genuine long-term voters for W would have received for that cycle, exactly analogous to the OTLM epoch-frontrunning issue — deposit right before the epoch snapshot, withdraw right after, without providing sustained value (long-term voting/governance participation) to the protocol.

### Reachability

This is reachable from a single signed `VoteWitnessContract` transaction (via `actuator/.../VoteWitnessActuator.java`) or the TVM native `voteWitness()` precompile (`actuator/.../vm/program/Program.java` → `VoteWitnessProcessor`), by any unprivileged account holding frozen TRON Power — no special permissions required.

### Title
Reward-epoch frontrunning via cost-free, cooldown-free re-voting in DPoS vote reward accounting - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
Voters can cast a witness vote in the final block of a reward cycle and receive that entire cycle's proportional reward share, then immediately move their vote away with no fee and no lockup, repeatedly capturing full-cycle rewards while never bearing the cycle-long voting/governance exposure that other voters incur.

### Finding Description
`MaintenanceManager.doMaintenance()` computes the witness reward index `Vi` for a completed cycle from the witness's vote total captured at that same maintenance call, and reward for an individual voter is later computed in `MortgageService.computeReward()`/`VoteRewardUtil.computeReward()` as `deltaVi(beginCycle-1, endCycle-1) * currentVoteCount` — i.e., the voter's *current* vote weight applied uniformly across the whole `[beginCycle, endCycle)` span, with `beginCycle` set to whatever cycle they most recently voted in. `VoteWitnessActuator` (and the TVM `voteWitness` native contract) allow changing votes in any block for free, with no minimum holding period.

### Impact Explanation
An attacker with already-frozen TRON Power can vote for a witness immediately before a cycle boundary, receive that witness's full-cycle reward share on withdrawal, then re-vote elsewhere in the next block — repeating indefinitely. This siphons reward pool funds intended for voters who provided sustained voting weight throughout the cycle, degrading the economic incentive model and diminishing legitimate voters' rewards (a form of unbacked/ill-gotten reward extraction).

### Likelihood Explanation
Requires only ordinary frozen balance (TRON Power) and the ability to broadcast a `VoteWitnessContract` transaction (or call the TVM `voteWitness` precompile) at a predictable point relative to the known, deterministic maintenance/cycle boundary — both of which are trivially available to any account and require no special privileges or timing luck beyond normal transaction submission.

### Recommendation
Track time-weighted vote exposure within a cycle (e.g., require votes to be held from before the cycle start to count for that cycle's `Vi` delta) or impose a minimum holding/cooldown period on `VoteWitnessContract` (and the TVM `voteWitness` operation) analogous to freeze/unfreeze lockups, so voters can only earn reward proportional to the time their vote was actually outstanding during the cycle.

### Proof of Concept
1. Freeze balance to obtain TRON Power (`FreezeBalanceContract`/`FreezeBalanceV2Contract`), independent of any specific witness.
2. Just before `MaintenanceManager.doMaintenance()` triggers the cycle rollover, submit `VoteWitnessContract` voting for witness W with the full TRON Power.
3. After maintenance runs, call `WithdrawBalanceContract` (or TVM `withdrawReward()`), and observe via `MortgageService.queryReward()`/`computeReward()` that the account receives W's full-cycle reward share despite having voted for only the final block of that cycle — see the cycle-boundary reward semantics exercised in `VoteRewardUtil`/`MortgageService` and the maintenance test flow in `framework/src/test/java/org/tron/common/runtime/vm/VoteTest.java` (`testRewardAlgorithmNo1`/`No2`/`No3`), which confirm rewards are granted for full cycles based on the vote snapshot present at cycle-end regardless of intra-cycle timing.
4. Immediately re-vote away from W in the next block (no fee, no cooldown) and repeat for the next cycle/witness.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
