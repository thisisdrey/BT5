### Title
Missing slippage protection in `ExchangeWithdrawActuator`/`ExchangeInjectActuator` enables sandwich attacks on TRC10 Bancor-style exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract` (and analogously `ExchangeInjectContract`) computes the counter-token amount to pay/receive purely from the pool's live token balances at execution time, with no caller-supplied minimum/maximum bound field in the protobuf message. This mirrors the Curve `remove_liquidity`/`_removeLiquidity` bug: the amount of the "other side" of a liquidity operation is determined entirely by pool state at execution, with zero protection against price movement between submission and inclusion, exposing the caller to a sandwich attack.

### Finding Description
`ExchangeTransactionContract` (a swap) intentionally exposes an `expected` field that is enforced in `ExchangeTransactionActuator.doValidate`: `anotherTokenQuant < tokenExpected` reverts the transaction [1](#0-0) . This is the TRON equivalent of Curve's `amountOutMin`/`remove_liquidity_one_coin` slippage guard.

By contrast, `ExchangeWithdrawContract` only carries `exchange_id`, `token_id`, and `quant` — there is no field for a minimum/maximum bound on the reciprocal token amount at all. In `ExchangeWithdrawActuator.doValidate`/`execute`, `anotherTokenQuant` (the amount of the *other* pooled token the withdrawer receives, or in the inject case, pays) is computed strictly from the exchange's `firstTokenBalance`/`secondTokenBalance` at the moment the transaction is processed: [2](#0-1) 

The only checks performed are that the computed amount is `> 0` and within a fixed 0.01% integer-rounding precision tolerance ("Not precise enough") — there is no way for the caller to bound the value they will actually receive: [3](#0-2) 

The same pattern exists in `ExchangeInjectActuator`, where `anotherTokenQuant` (the amount of the second token the injector must also deposit) is likewise derived only from the current pool ratio with no caller-specified cap: [4](#0-3) 

Because `ExchangeTransactionContract` (swap), `ExchangeInjectContract`, and `ExchangeWithdrawContract` are all ordinary broadcastable transactions that any account can submit against a public TRC10 exchange pool it created (`ExchangeCreateContract`), an attacker can observe a pending withdraw/inject transaction and manipulate the pool ratio immediately before it executes, then reverse the manipulation immediately after, exactly as described in the Curve report for `remove_liquidity`'s zero `minOuts`.

### Impact Explanation
An attacker who can predict or observe a pending `ExchangeWithdrawContract` (or `ExchangeInjectContract`) transaction can sandwich it:
1. Front-run with an `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance` in the attacker's favor.
2. The victim's withdraw executes at the skewed ratio, receiving materially less value of the counter-token than the pool's fair-value ratio would have given (or, for inject, being forced to contribute materially more of the counter-token than intended).
3. Back-run with a reverse swap to restore the ratio, extracting the difference as profit at the victim's expense.

This is concrete unauthorized value extraction (theft of funds) from the exchange creator's TRC10/TRX balance with no protocol-level bound, satisfying the "unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
Reachable by any unprivileged account: creating an `ExchangeCreateContract` pool and calling `withdraw`/`inject` on it requires no special privilege, and TRX/TRC10 swaps via `ExchangeTransactionContract` are permissionless. An attacker only needs to observe the victim's pending transaction (mempool visibility or transaction ordering influence within a block) to construct the sandwich, which is a standard, low-cost MEV technique already proven viable against the analogous Curve pattern.

### Recommendation
Add an explicit slippage-bound field to `ExchangeWithdrawContract` and `ExchangeInjectContract` (e.g., `expected_another_token_min`/`expected_another_token_max`), and enforce it in `ExchangeWithdrawActuator.doValidate`/`ExchangeInjectActuator.doValidate` the same way `tokenExpected` is enforced in `ExchangeTransactionActuator`, so callers can bound the counter-token amount they are willing to receive or pay before the transaction executes.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from victim (creator of exchange `id`) requesting withdrawal of `tokenQuant` of `firstTokenID`.
2. Attacker submits (with higher fee/priority so it lands first in the block) an `ExchangeTransactionContract` swap that sells a large amount of `secondTokenID` into the pool, sharply increasing `firstTokenBalance` relative to `secondTokenBalance`.
3. Victim's `ExchangeWithdrawContract` executes: `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` [5](#0-4)  now yields far less `secondTokenID` than before the manipulation, with no `expected`/minimum check to reject it.
4. Attacker submits a reverse `ExchangeTransactionContract` swap restoring the ratio, pocketing the value difference extracted from the victim's withdrawal.
