This confirms the vulnerability path clearly. `SlotMetadata::auth_digest()` binds a signature only to `(slot_id, slot_version, data_hash)` and never to the `smart_contract`/`QualifiedContractIdentifier`, while every storage/validation entry point (`try_replace_chunk`, `validate_received_chunk`) looks up the signer *per contract* but re-checks the signature against that same context-free digest.

### Title
Cross-StackerDB Chunk Replay via Missing Contract-Identifier Binding in Signature Digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest solely from `slot_id`, `slot_version`, and `data_hash`, omitting the StackerDB's `QualifiedContractIdentifier`. [1](#0-0)  Consequently, a chunk validly signed for one StackerDB contract can be replayed and accepted by a node as valid for a *different* StackerDB contract, as long as the replayed slot's registered signer address is the same in both contracts (a common real-world configuration, since many Stacks StackerDB contracts, e.g. signer-set contracts across successive reward cycles/indices, reuse the same signer key set at matching slot indices).

### Finding Description
Every chunk-acceptance path — the HTTP `POST /v2/stackerdb/{contract}/chunks` handler via `try_replace_chunk` [2](#0-1) , and the p2p gossip path via `validate_received_chunk`/`handle_unsolicited_StackerDBPushChunk` [3](#0-2) [4](#0-3)  — resolves the slot's authorized signer *scoped to a specific contract* (`get_slot_validation(smart_contract, slot_id)` / `get_slot_signer(smart_contract_id, slot_id)`), but then verifies the *signature* using `SlotMetadata::verify()`, whose underlying digest never includes the contract identifier: [5](#0-4) .

This breaks the intended equality "signed for contract A" == "authorized to be stored under contract A". Instead the actual check reduces to "signed by address X" == "X is the registered signer for slot N in *whatever contract the caller claims*." An attacker (any unauthenticated/unprivileged peer that has observed a broadcast chunk, since StackerDB chunks are gossiped/relayed across the p2p network and also fetchable via the HTTP StackerDB endpoints) can take a chunk `(slot_id, slot_version, data, sig)` that was legitimately produced and broadcast for StackerDB contract A, and re-wrap it as a `StackerDBPushChunkData` (or `POST` request) targeting contract B's `contract_id`. If contract B independently registers the same signer address at the same `slot_id` (a normal pattern for successive-cycle StackerDB contracts sharing a signer set), the node will:
1. Look up B's registered signer for that slot — finds the same address X.
2. Verify the signature against the digest of `(slot_id, slot_version, data_hash)` — succeeds, because the digest never mentions which contract it was meant for.
3. Accept and store the chunk into B's replica if `slot_version` exceeds B's currently stored version, then re-broadcast it network-wide via `process_stacker_db_chunks`/`broadcast_message` [6](#0-5) .

This lets an unprivileged relayer inject data into a StackerDB it has no write authorization for, and propagate that forged-context data network-wide, purely by replaying validly-signed bytes across a different logical database.

### Impact Explanation
This is an unauthenticated/unauthorized write to StackerDB state and network-wide propagation of forged (miscontextualized) data — matching the Critical impact bucket. Data intended and authenticated for contract A gets stored and served as canonical content of contract B, which downstream consumers (signer coordination logic, miner/observer tooling reading `.signers-*` DBs, etc.) trust as being specific to B's protocol context. Any code path relying on contract-scoped semantics of a chunk's contents (e.g., different message formats/expectations per contract) can be fed attacker-controlled cross-contract content without ever compromising a key.

### Likelihood Explanation
Exploitability only requires: (a) observing one broadcast, network-visible chunk from contract A (chunks are gossiped to all replicating peers and are also directly retrievable via `GET`), and (b) the target contract B sharing the same signer address at the same slot index and having a currently-stored version lower than the replayed chunk's version — a condition naturally satisfied whenever operators/protocols reuse identical signer sets across multiple StackerDB contracts (a documented, expected pattern per the module's own design notes on StackerDB usage). No special privileges, no key compromise, and no consensus/chain-tip control are needed.

### Recommendation
Include the `smart_contract`/`QualifiedContractIdentifier` (or equivalently a StackerDB-specific domain-separation tag) inside `SlotMetadata::auth_digest()` before hashing, and require callers of `sign`/`verify` to supply and bind the target contract identifier. All existing signed chunks and clients producing signatures (e.g. `StackerDBChunkData::sign`) must be updated consistently, and this is a breaking wire/protocol change requiring versioning/epoch-gating.

### Proof of Concept
1. Node operator registers the same signer key `S` for slot 0 in both StackerDB contract `A` and StackerDB contract `B` (both currently at slot version 0) — a normal deployment pattern for successive-cycle signer-set contracts.
2. Legitimate signer `S` signs and broadcasts chunk `C = (slot_id=0, slot_version=1, data=D)` for contract `A`. This propagates via `process_stacker_db_chunks`/gossip to the network. [6](#0-5) 
3. Attacker (any peer, no keys needed) observes this chunk on the wire, then crafts `StackerDBPushChunkData { contract_id: B, chunk_data: C.chunk_data }` (same `slot_id`, `slot_version`, `sig`, `data`) and sends it to a victim node as an unsolicited push, or `POST`s it to the victim's `/v2/stackerdb/B/chunks` HTTP endpoint.
4. The victim resolves signer for `(B, slot 0)` → `S`, verifies `C.chunk_data.sig` against the contract-agnostic digest → succeeds, `slot_version 1 > 0` → chunk is stored into `B`'s replica and re-broadcast as if it were legitimately produced for `B`. [7](#0-6)
