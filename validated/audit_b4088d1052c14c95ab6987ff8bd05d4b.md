### Title
No slippage/maximum-payment limit for liquidators in `lending_account_liquidate` - (File: `programs/marginfi/src/instructions/marginfi_account/liquidate.rs`)

### Summary
`lending_account_liquidate` only accepts `asset_amount` (`q_a`, the collateral quantity to seize) as a fixed, liquidator-supplied input. The liability amount the liquidator must actually pay (`q_ll`) is computed on-chain, at execution time, from live oracle prices fetched inside the instruction. There is no parameter allowing the liquidator to cap the maximum liability amount they are willing to pay for a given `q_a`, so price movement between transaction submission and execution can force the liquidator to pay materially more than they intended for the same seized collateral — the same bug class described in the referenced Frax report for `mintFrax`, where dynamically price-derived payment amounts had no caller-supplied ceiling.

### Finding Description
The instruction's own doc comment explains the design intent and its limitation: `q_a` is treated as "the most bounded variable in this process," relying only on the fact that the liquidatee's actual collateral balance bounds `q_a` from above [1](#0-0) . But `q_a` being bounded by the liquidatee's balance says nothing about the liability quantity the liquidator must give up for the same `q_a` — that quantity is a function of live, execution-time prices:

```
q_ll = q_a * p_a * (1 - f_l) / p_l
``` [2](#0-1) 

Concretely, `asset_price` and `liab_price` are fetched fresh from oracles inside the instruction at execution time (`fetch_asset_price_for_bank_low_bias`, `OraclePriceFeedAdapter::try_from_bank(...).get_price_of_type(...)`), and `liab_amount_liquidator` is derived from those live prices multiplied by the caller-supplied `asset_amount`: [3](#0-2) 

The instruction signature exposes no `max_liab_amount` (or equivalent slippage-bound) parameter — only `asset_amount`, `liquidatee_accounts`, and `liquidator_accounts`: [4](#0-3) 

This is structurally identical to the Frax `mintFrax` issue: a caller submits a transaction specifying a fixed input quantity, while the actual price-dependent payment amount is computed dynamically at execution time from oracle/market data that can shift between submission and landing, with no on-chain mechanism for the caller to bound the unfavorable side of that computation.

By contrast, the codebase already recognizes and fixes this exact bug class elsewhere: limit orders enforce a caller-supplied `max_slippage` capped at `MAX_ORDER_SLIPPAGE` [5](#0-4)  and constants reserve dedicated slippage constants [6](#0-5) . No analogous protection exists for classic liquidation.

### Impact Explanation
A liquidator (an unprivileged, third-party protocol user) who broadcasts a `lending_account_liquidate` transaction with a given `asset_amount` has no way to guarantee an upper bound on `q_ll`, the liability they will be forced to pay. If asset or liability oracle prices move unfavorably (e.g., the liability token's price spikes, or the seized asset's price drops) between broadcast and landing, the liquidator can be forced to pay substantially more liability value than intended for the same collateral seized, resulting in an unexpected and uncapped monetary loss for that liquidator. This is a direct, concrete loss-of-funds risk in a core, unprivileged-user-facing accounting path (classic/legacy liquidation, which the project explicitly states it will "support indefinitely" per `guides/RISK_AND_LIQUIDATORS/CLASSIC_LIQUIDATION.md`).

### Likelihood Explanation
Price volatility between transaction submission and landing is routine on Solana (network congestion, MEV, oracle updates), and liquidations are precisely the scenario where prices are actively moving (that's what makes the account unhealthy in the first place). Any liquidator submitting `lending_account_liquidate` during a volatile price move is exposed, and no explicit user-facing guard prevents it.

### Recommendation
- Short term: add a `max_liab_amount` (or `min_asset_value`) parameter to `lending_account_liquidate` that the liquidator supplies, and revert if the computed `liab_amount_liquidator` exceeds it (mirroring the `max_slippage` pattern already used for limit orders in `programs/marginfi/src/state/order.rs`).
- Long term: apply the same principle — an explicit caller-supplied bound — to any instruction where the amount paid/received by an unprivileged caller is derived from oracle/market data at execution time rather than fixed by the caller.

### Proof of Concept
1. Liquidatee's account becomes unhealthy; liquidator observes `q_a` = amount of collateral available and computes an expected `q_ll` based on current oracle prices, then submits `lending_account_liquidate(asset_amount=q_a, ...)`.
2. Before the transaction lands, the liability token's oracle price rises (or the asset token's price falls) due to normal market movement.
3. The transaction executes using the now-current, less favorable prices: `liab_amount_liquidator` is computed as `calc_amount(calc_value(asset_amount, asset_price, ...), liab_price, ...)` at lines 242–251 of `liquidate.rs`, using the fresh, unfavorable prices.
4. The liquidator ends up paying significantly more liability value than anticipated for the same `q_a` of seized collateral, with no on-chain mechanism to have reverted the transaction instead. [7](#0-6)
