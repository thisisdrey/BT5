### Title
Account-name reuse after `DeleteAccount` lets a stale postponed self-receipt apply privileged actions (e.g. `AddKey`) to the newly re-created account - ([File: core/store/src/utils/mod.rs::remove_account])

### Summary
`remove_account` deletes the `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData` entries for an account, but it never touches the receiver-keyed congestion/data-dependency bookkeeping (`PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`) that references the same `account_id` as `receiver_id`. If a postponed self-receipt (`receiver_id == predecessor_id == A`) is still waiting on an input data dependency when `A` is deleted, that state survives deletion and will later be dispatched against whatever account currently occupies the trie slot for account-id `A`, since `AccountId` is compared as a plain string with no notion of account "generation".

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access-key/gas-key entries, and `TrieKey::ContractData`: [1](#0-0) 
It never issues `state_update.remove` for `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, or `TrieKey::ReceivedData` keyed by `receiver_id == account_id`.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` unconditionally, with checks only for storage size (`DeleteAccountWithLargeState`) and gas-key balance, not for any outstanding postponed/pending receipt bookkeeping: [2](#0-1) 

An attacker can arrange for account `A` to have a *postponed self-receipt* — an `ActionReceipt` with `predecessor_id == receiver_id == A` and an unmet `input_data_id` — via the normal cross-contract-call flow in `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`), which stores `PendingDataCount{receiver_id:A, receipt_id}` and `set_postponed_receipt` when data is still missing: [3](#0-2) 

The attacker then submits `DeleteAccount(A)`. Because `remove_account` leaves the postponed bookkeeping intact, once account name `A` becomes available again (e.g. a top-level or freed name re-registered by a different, unrelated party) and any new account sits at trie key `Account{A}`, the still-outstanding `Data` receipt (whose delivery the attacker also controls/anticipates) is processed by `process_receipt`'s `Data` arm (`runtime/runtime/src/lib.rs:1386-1473`), which looks up `PostponedReceiptId{receiver_id:A, data_id}` — unaffected by the deletion — decrements `PendingDataCount`, retrieves the old postponed `Receipt` via `get_postponed_receipt`, and executes it via `apply_action_receipt` against the account currently stored at `A`: [4](#0-3) 

Per the protocol's action rules, actions such as `AddKey`, `DeleteKey`, `Stake`, `DeployContract`, and `DeleteAccount` require `actor_id == receiver_id`, and this is satisfied purely by string equality (the docs describe the mutable `actor_id` mechanism explicitly): [5](#0-4) 
Because the stale postponed receipt's `predecessor_id` is the string `"A"`, and the *new* account also has `account_id == "A"`, the actor-permission check passes even though the new account is a logically distinct entity created by an unrelated party. This lets the attacker's original privileged self-action (e.g. `AddKey(attacker_pubkey)`) execute against the new owner's account once the data dependency resolves.

This confirms the audit target: `remove_account` does not clean up receiver-side congestion/data bookkeeping before allowing account deletion, and the runtime has no separate guard preventing execution of stale postponed receipts against a re-created same-named account.

### Impact Explanation
The exploit is deterministic — every validator/RPC node processing the same receipt sequence reaches the identical outcome, so there is no state-root divergence. The concrete impact is **authorization escalation**: an attacker can plant a self-authorized privileged action (most notably `AddKey`, granting a new access key) that gets applied to a different, unrelated account merely because it shares the deleted account's name string. This matches the NEAR bounty "authorization escalation across accounts" category.

### Likelihood Explanation
Preconditions: the attacker needs an ordinary funded account and a contract capable of (a) creating a postponed self-receipt with an unresolved `input_data_id`, and (b) later delivering the corresponding `Data` receipt at a time of the attacker's choosing. Both are achievable with a simple attacker-authored contract (e.g., a self promise chained on a cross-contract call whose completion the attacker controls). The remaining step — an unrelated third party recreating exactly the same account name after deletion — is the main precondition limiting broad exploitation; it is realistic for freed top-level `.near` names (registrar allows re-registration once a name becomes available) but not for arbitrary subaccounts unless the same parent recreates the child. This makes the attack fully attacker-controlled and repeatable whenever account-name reuse under the same parent/registrar is possible, and it requires no privileged network role, matching the "unprivileged attacker" threat model.

### Recommendation
`remove_account` should also purge any receiver-keyed pending state before allowing account deletion, e.g.:
- Enumerate and remove `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, and `ReceivedData` entries for `account_id` (or reject `DeleteAccount` while such state exists, similar to the existing `DeleteAccountStaking`/`DeleteAccountWithLargeState` guards).
- Alternatively, disambiguate `actor_id`/receiver checks so that a receipt whose predecessor was generated before a `DeleteAccount`+recreate cycle cannot satisfy `actor_id == receiver_id` against a logically different (recreated) account, e.g. by tracking an account generation/nonce that must match between receipt creation and execution.

### Proof of Concept
Integration test plan (runtime apply-level, similar in structure to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` in `runtime/runtime/src/tests/apply.rs`):
1. Set up account `A` (subaccount of a controlled parent) with a contract that, on call, issues a cross-contract call to `B` and schedules a callback action receipt on itself (`receiver_id=predecessor_id=A`) containing `AddKey(attacker_pubkey2)`, with `input_data_ids=[pending_data_id]` unresolved (simulate by directly constructing the postponed `ActionReceipt` and applying it, as in `action_receipt_awaiting` helper).
2. Apply a `DeleteAccount(A)` receipt (self-receipt) with beneficiary elsewhere; assert `Account{A}` is gone but `PostponedReceipt{A,receipt_id}` / `PendingDataCount{A,receipt_id}` / `PostponedReceiptId{A,pending_data_id}` are still present in the resulting trie (`get_postponed_receipt`, `get` on `PendingDataCount`/`PostponedReceiptId` should return `Some`).
3. Recreate account `A` via a fresh `CreateAccount`+`AddKey(victim_pubkey)` receipt from an unrelated predecessor.
4. Deliver the `Data` receipt satisfying `pending_data_id` targeted at `A`.
5. Assert: the resulting `Account{A}` now has an access key for `attacker_pubkey2` even though it was never authorized by the recreated account's owner, and re-running the identical three-receipt sequence on a fresh trie snapshot produces an identical state root/outcome (demonstrating determinism while confirming the escalation).
