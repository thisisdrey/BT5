### Title
Malicious maker orders can permanently DOS legitimate taker trades via `MAX_MATCH_NUM` revert in `matchOrder` - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchOrder` matches a taker order against the resting maker order book for a token pair, incrementing `matchOrderCount` for every maker order consumed and hard-reverting the whole transaction with `ContractValidateException` once more than `MAX_MATCH_NUM` (20) maker orders are touched. There is no upfront simulation and no try/catch/partial-fill fallback around this loop, so once the count is exceeded the entire transaction (including the taker's own newly-created order and balance debit performed earlier in the same `execute()` call) is rolled back and fails. A user can cheaply flood the best price level of a token pair with many tiny maker orders, guaranteeing that any legitimate taker order attempting to consume that liquidity always exceeds `MAX_MATCH_NUM` and reverts, denying honest traders the ability to execute against that market pair — directly analogous to the reported offchain-order batch DOS where a single failing/zero-size condition in an unguarded loop blocks execution for all honest participants.

### Finding Description
`matchOrder` walks price levels and, within a price level, walks individual maker orders in a `while` loop, calling `matchSingleOrder` for each one and incrementing a counter: [1](#0-0) 

If the number of maker orders matched in a single taker call exceeds `MAX_MATCH_NUM` (20), the method throws `ContractValidateException`: [2](#0-1) 

This exception propagates out of `execute()`, which wraps the whole order lifecycle (fee deduction, balance/asset transfer, order creation, and matching) in a single try/catch that converts any `ContractValidateException` into a `ContractExeException`, aborting the transaction: [3](#0-2) 

Crucially, there is no minimum order size / minimum notional-value validation in `validate()` — only that quantities are `> 0` and below an upper `quantityLimit`: [4](#0-3) 

and up to `MAX_ACTIVE_ORDER_NUM` (100) resting orders are allowed per account per side: [5](#0-4) 

This mirrors the report's core defect class: batch/iterative execution over multiple discrete order units with a hard revert condition and no partial-success/try-catch handling, so a single attacker-controlled condition (excess maker matches, analogous to the zero-size order) blocks execution for honest participants who would otherwise fully or partially succeed. The existing test suite confirms this exact revert behavior is by design/known but unmitigated: [6](#0-5) 

### Impact Explanation
An attacker who wants to grief a specific token-pair market can place ≥21 small maker orders at (or better than) the best resting price for that pair, at the cost of `MAX_ACTIVE_ORDER_NUM`-bounded but otherwise cheap fees (`calcFee()` = `dynamicStore.getMarketSellFee()`, a fixed committee-configurable TRX fee, not scaled to trade size). Any honest taker who then tries to place a sell order large enough to need to walk through that price level will always have `matchOrderCount` exceed `MAX_MATCH_NUM`, causing:
- The taker's transaction to fail with `ContractExeException`, reverting the order creation and any balance changes made earlier in `execute()`.
- Legitimate large orders on that pair to be permanently un-executable as long as the attacker maintains ≥21 dust orders at the best price (cost to refill is cheap and orders persist until consumed or cancelled).
- Denial of service for the exchange functionality on that specific market pair, which can delay/prevent legitimate trade settlement — a medium/high severity availability impact on an on-chain financial primitive reachable by any account with minimal TRX and no special privilege.

### Likelihood Explanation
Likelihood is high: `MarketSellAssetContract` is a standard broadcastable transaction type reachable by any unprivileged account (once the committee has enabled `supportAllowMarketTransaction`), requires no special permission, and the only cost is the per-order market fee plus the value locked in dust orders (which can be minimal, e.g., 1 unit quantities, since there is no minimum order size check). The `MAX_MATCH_NUM`/`MAX_ACTIVE_ORDER_NUM` constants are fixed and well below what an attacker can trivially reach (100 orders allowed per account, only 21 needed to trip the limit for one pair).

### Recommendation
- Enforce a minimum order size / minimum notional value in `validate()` to make dust-order flooding economically costly relative to potential griefed volume.
- Change `matchOrder`/`execute()` semantics so that hitting `MAX_MATCH_NUM` results in a partial fill (persist all successfully matched quantity and return the remainder to the order book or to the taker) instead of throwing and rolling back the entire transaction.
- Alternatively, increase `MAX_MATCH_NUM` dynamically based on quantity/order count economics, or charge fees proportional to the number of orders matched to disincentivize spam liquidity.
- Consider adding an on-chain limit on the number of maker orders any single account may place at the exact same/adjacent best price for a given pair.

### Proof of Concept
Reference existing repository test demonstrating the revert condition, which an attacker can trigger deliberately against a victim's large taker order by pre-seeding the order book: [7](#0-6) 

1. Attacker broadcasts 21 `MarketSellAssetContract` transactions selling `TOKEN_ID_TWO` for `TOKEN_ID_ONE` at the best/lowest price for the pair, each with minimal (non-zero) quantities, at the cost of 21× `getMarketSellFee()`.
2. A victim broadcasts a legitimate `MarketSellAssetContract` selling `TOKEN_ID_ONE` for `TOKEN_ID_TWO` with a quantity large enough to require matching more than 20 maker orders at that price level.
3. `matchOrder` walks the 21 dust orders, `matchOrderCount` exceeds `MAX_MATCH_NUM` = 20, and `ContractValidateException("Too many matches...")` is thrown, causing the victim's entire transaction (including the balance already reserved) to revert via `ContractExeException`, exactly as validated by `exceedMaxMatchNumLimit()`.
4. As long as the attacker maintains ≥21 dust orders at the best price, every honest large taker transaction against that pair will continue to fail, achieving persistent DOS.

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
