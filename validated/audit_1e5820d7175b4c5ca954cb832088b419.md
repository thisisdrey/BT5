### Title
Unchecked uint64 subtraction in geometric-repack heuristic can underflow, forcing repeated wasteful repacks - ([File: internal/git/housekeeping/optimization_strategy.go])

### Summary
The reported issue is a Solidity contract performing arithmetic (`profitFactor * callCost < credit.add(profit)`) without safe-math protection, risking overflow/incorrect results. The closest reachable analog in this gitaly repo is unchecked unsigned-integer subtraction in the housekeeping heuristics that decide whether to repack a repository, which can underflow and silently produce an enormous, incorrect result.

### Finding Description
In `HeuristicalOptimizationStrategy.ShouldRepackObjects`, the number of packfiles that are not yet tracked by the multi-pack-index is computed as a plain, unguarded `uint64` subtraction: [1](#0-0) 

```go
allowedUpperLimit := math.Log(float64(s.info.Packfiles.Size/1024/1024)) / math.Log(1.8)
actualLimit := math.Max(allowedLowerLimit, allowedUpperLimit)

untrackedPackfiles := s.info.Packfiles.Count - s.info.Packfiles.MultiPackIndex.PackfileCount

if untrackedPackfiles > uint64(actualLimit) {
    return true, geometricRepackCfg
}
```

`s.info.Packfiles.Count` is derived by counting actual `pack-*.pack` files found on disk during a directory scan (`PackfilesInfoForRepository`), while `s.info.Packfiles.MultiPackIndex.PackfileCount` is derived from metadata embedded in the on-disk `multi-pack-index` file itself: [2](#0-1) 

There is no `SafeMath`-equivalent check (e.g. verifying `Count >= PackfileCount`, or using a signed/checked subtraction) before performing this subtraction. If a repository's on-disk state has the multi-pack-index claim to track more packfiles than are physically present in `objects/pack/` — which can occur for a repository transferred/imported/forked from an external source, or reconstructed from a crafted bundle/snapshot where the `multi-pack-index` file is inconsistent with the actual pack files delivered — the subtraction of two `uint64` values underflows and wraps around to a value near `2^64`, rather than producing a small or negative-clamped number.

### Impact Explanation
When the subtraction underflows, `untrackedPackfiles` becomes astronomically large and will always exceed `actualLimit` (a small heuristic threshold, typically 2–19 per the documented table). This forces `ShouldRepackObjects` to unconditionally return `true, geometricRepackCfg` for that repository on every housekeeping evaluation, regardless of the true, healthy on-disk packfile state. Because Gitaly's housekeeping runs periodically/automatically for repositories, this can cause the affected repository to be selected for an (unnecessary and heavier) geometric repack repeatedly, consuming CPU, disk I/O, and disk space on every housekeeping cycle — a resource-exhaustion condition on the Gitaly node triggered purely by a mismatched-but-attacker-influenceable on-disk state, rather than by any real backlog of untracked packfiles. This maps to the DoS-of-a-handler class called out as acceptable impact.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to get gitaly to observe a repository whose `multi-pack-index` metadata disagrees with the actual packfiles on disk (e.g., via a project import/fork of externally supplied repository data, or a bundle where the multi-pack-index and pack directory were not shipped consistently). This does not require any privileged access — only the ability to have gitaly ingest/host a specially crafted repository, which is a standard unprivileged user flow (import/fork). It does not rely on a malicious peer/node, leaked token, or MITM.

### Recommendation
Guard the subtraction so it cannot underflow, e.g.:
```go
var untrackedPackfiles uint64
if s.info.Packfiles.Count > s.info.Packfiles.MultiPackIndex.PackfileCount {
    untrackedPackfiles = s.info.Packfiles.Count - s.info.Packfiles.MultiPackIndex.PackfileCount
}
```
or use a signed integer type and clamp negative results to zero, so an inconsistent/crafted `multi-pack-index` cannot force the heuristic into a permanent "always repack" state.

### Proof of Concept
1. Import or fork a repository into Gitaly whose `objects/pack/multi-pack-index` file has been crafted (or corrupted in transit) to declare a `pack-count` header value larger than the number of `pack-*.pack` files actually present under `objects/pack/` (`MultiPackIndexInfoForPath` parses this count directly from the file's binary header).
2. Trigger (or wait for) Gitaly's housekeeping/optimization pass to evaluate `HeuristicalOptimizationStrategy.ShouldRepackObjects` for this repository.
3. `s.info.Packfiles.Count` (real on-disk count) is smaller than `s.info.Packfiles.MultiPackIndex.PackfileCount` (claimed count from the crafted midx), so `untrackedPackfiles` underflows to near `2^64`, unconditionally satisfying `untrackedPackfiles > uint64(actualLimit)`.
4. The repository is repeatedly selected for a full geometric repack on every housekeeping cycle instead of being skipped, wasting CPU/IO/disk resources on the Gitaly node.
