## Title
Missing Domain Separation in StackerDB Chunk Signatures Enables Cross-Contract Chunk Replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a StackerDB writer signs to authenticate a chunk. The digest only commits to `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific `smart_contract`/`QualifiedContractIdentifier` the chunk is destined for. Because every StackerDB verification path (`SlotMetadata::verify`, `StackerDBTx::try_replace_chunk`, `PeerNetwork::validate_received_chunk`) checks only "does this signature recover to the address on file for slot X *in this contract*", any validly-signed chunk observed on the network for one StackerDB contract can be replayed verbatim into a *different* StackerDB contract where the same signer address happens to own the same slot — exactly the missing "domain separator" flaw described in the external SGX report.

### Finding Description
The signing/verification logic lives in `libstackerdb/src/libstackerdb.rs`:

```

    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)

``` [1](#0-0) 

This digest is used both by `sign()` and `verify()`. Nowhere does it include the target contract's `QualifiedContractIdentifier` (analogous to `address(this)`) or any chain/network identifier — the exact "domain separator" the external report recommends adding.

Every place the signature is actually checked only re-derives authorization from the *target* contract's slot table, not from anything embedded in the signature itself:

- `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` looks up `slot_validation.signer` for `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` — it never checks that the signature was produced *for this contract*: [2](#0-1) 
- `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs` does the same thing for both downloaded and pushed chunks: it fetches `get_slot_signer(smart_contract_id, data.slot_id)` and calls `slot_metadata.verify(&addr)`, with no contract binding check: [3](#0-2) 

Because slot assignment for the signer set is derived from a single, shared, sorted list (`.signers` contract's `stackerdb-get-signer-slots-page`), the *same* signer address occupies the *same* `slot_id` across many distinct StackerDB contracts simultaneously — one per message type, for both the current and next signer set page: [4](#0-3) [5](#0-4) 

confirmed by the test iterating `signer_set` × `message_id` and expecting the identical slot list in every one of those contracts: [6](#0-5) 

Since the digest never encodes *which* contract the signature authorizes, a chunk `(slot_id, slot_version, data, sig)` that was legitimately broadcast for contract `A` is also a cryptographically valid chunk for contract `B`, provided the same signer address owns `slot_id` in `B` and `B`'s current stored version for that slot is still below `slot_version`. An unprivileged network relayer that merely observes a broadcast chunk (no private key required) can resubmit it — unmodified — to a different StackerDB contract, and both `try_replace_chunk`/`validate_received_chunk` will accept it as authentic, because their checks are blind to the chunk's original contract context.

### Impact Explanation
This is an unauthenticated/unauthorized-write class issue: it lets a third party who never held the signing key inject data into a StackerDB contract as though the legitimate signer wrote it there, and `handle_unsolicited_StackerDBPushChunk`/the sync logic will then relay this replayed chunk on to other peers, propagating forged/misattributed data network-wide. This can be used to plant stale or out-of-context signer data (e.g. a message crafted for one message-type slot) into another message-type's slot in a different StackerDB instance controlled by the same signer, confusing consumers (miners, other signers, monitoring tools) that trust "this slot's content == what the assigned signer intended for this specific database".

### Likelihood Explanation
Exploitation requires no privileged access: any network participant that can observe StackerDB chunk gossip (which is unauthenticated broadcast data by design) can capture a validly signed chunk and resubmit it to a different contract endpoint via the standard `PutChunk`/push-chunk RPC or P2P paths. The only preconditions — same signer address holding the same `slot_id` in two different StackerDB contracts, and a still-low version counter in the target — are the *normal, expected* state of the system given how slot assignment works across the `signers-{set}-{message_id}` family of contracts.

### Recommendation
Add domain separation to `SlotMetadata::auth_digest()` by including the target `QualifiedContractIdentifier` (and ideally a chain/network identifier) in the hashed material before signing/verifying, so a signature is only valid for the specific StackerDB contract it was produced for. This mirrors the report's recommendation to bind `address(this)`/`block.chainid` into the signed hash, and should be threaded through `sign()`, `verify()`, `try_replace_chunk()`, and `validate_received_chunk()`.

### Proof of Concept
1. Signer `S` legitimately writes chunk `C = (slot_id=k, slot_version=v, data=D, sig=Sig)` to StackerDB contract `A` (e.g. `signers-0-<msg_id_A>`), where `Sig` is computed over `auth_digest(k, v, hash(D))`.
2. An unprivileged observer captures `C` off the wire (StackerDB gossip is unauthenticated broadcast).
3. The observer determines that `S` also owns `slot_id=k` in contract `B` (e.g. `signers-0-<msg_id_B>`), which is guaranteed by the shared slot-list contract logic, and that `B`'s stored version for slot `k` is `< v`.
4. The observer submits `C` unmodified to contract `B` via `PutChunk`/`StackerDBPushChunk`.
5. `validate_received_chunk`/`try_replace_chunk` recompute `auth_digest(k, v, hash(D))`, recover `S`'s address, find it matches `B`'s recorded signer for slot `k`, and accept the chunk — even though `S` never signed anything intended for contract `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
