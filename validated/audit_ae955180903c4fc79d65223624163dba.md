### Title
Unbounded `AttachmentPage.inventory` size stored without validation in `extend_with_inventories` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentPage.inventory` is deserialized straight from a peer-supplied JSON HTTP response with no check that its length matches the fixed `AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE`, and `AttachmentsBatchStateContext::extend_with_inventories` stores the decoded `GetAttachmentsInvResponse` (including the oversized `Vec<u8>`) into `self.inventories` unconditionally. A malicious peer answering a `GET /v2/attachments/inv` request can therefore inflate its `inventory` field far beyond the expected page size, and that oversized allocation is retained in memory for the lifetime of the batch context.

### Finding Description
The expected invariant is that each `AttachmentPage.inventory` returned for a page contains exactly `ATTACHMENTS_INV_PAGE_SIZE` entries (one byte flag per attachment slot in that page), since the node's own handler (`RPCGetAttachmentsInvRequestHandler::try_handle_request` in `stackslib/src/net/api/getattachmentsinv.rs:186-189`) always builds `inventory` from `get_attachments_available_at_page_index`, which returns a page-sized vector. However, nothing on the client/consumer side enforces this when parsing a peer's response.

`decode_atlas_attachments_inv_response` (`stackslib/src/net/api/getattachmentsinv.rs:254-262`) simply does: [1](#0-0) 
parsing the JSON body into `GetAttachmentsInvResponse` with no per-page length assertion, and `AttachmentPage` (`stackslib/src/net/atlas/mod.rs:85-89`) has `inventory: Vec<u8>` with no bounded-size annotation: [2](#0-1) 

`extend_with_inventories` (`stackslib/src/net/atlas/download.rs:490-528`) then takes the decoded response and stores it directly into `self.inventories` keyed by `(contract_id, pages, ...)` → `peer_url` → `response`, with only reliability-report bookkeeping and no size/shape validation: [3](#0-2) 

The only place that later reads `inventory` is `get_prioritized_attachments_requests` (`stackslib/src/net/atlas/download.rs:404-478`), which does a bounds-checked `.get(position_in_page as usize)` — so an oversized vector does not cause an out-of-bounds panic; it just means the extra bytes are dead weight that was allocated and retained: [4](#0-3) 

An attacker acting as one of the queried `peers` can therefore return a `GetAttachmentsInvResponse` whose `pages[i].inventory` is many megabytes instead of the expected page-size (tens of bytes), and this will be accepted, decoded, and retained in `self.inventories` without truncation or rejection. The request itself is capped to `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST = 8` pages, but each of those 8 pages can independently carry an oversized `inventory`, and this repeats for every subsequent attachment inventory round the node performs against that same malicious peer (or a set of colluding malicious peers), scaling with the number of contracts/pages and peers tracked in a batch's `HashMap`-of-`HashMap` structure.

I could not fully confirm within this investigation whether there is a generic HTTP response body-size cap (`MAX_MESSAGE_LEN`/similar constant referenced in `stackslib/src/net/httpcore.rs`) that would clamp the overall response size before JSON parsing; if such a cap exists it would bound the *maximum* single-response inflation but would not eliminate the underlying design gap of missing per-page length validation.

### Impact Explanation
A malicious/compromised peer that the node queries for attachment inventories can force the node to retain large peer-supplied byte buffers in `AttachmentsBatchStateContext::inventories`, well beyond the ~64-byte size that the protocol design assumes per page. Because this happens per page (up to 8 pages per request) and accumulates per-peer per-contract entry in the batch state, a peer answering repeated inventory-sync polls can sustain elevated memory use on the querying node. This matches the "bounded compute DoS on a read endpoint"-style High-severity category in that it is an amplification of a small protocol interaction into disproportionate resource retention, though it is not a crash and does not corrupt canonical state — it is a resource-amplification/memory-retention issue tied to attachment-inventory gossip, repeatable on every inventory poll round against that peer.

### Likelihood Explanation
Preconditions are modest: the attacker only needs to be selected as one of the `peers` the node queries for a `contract_id`'s missing attachment pages (i.e., a normal Atlas peer, no privileged role or secret required), and must respond to `GET /v2/attachments/inv` with a crafted JSON body containing an inflated `inventory` array. This is fully within the described "any remote peer answering P2P/RPC requests" threat model, requires no signature bypass, and is repeatable each time the node re-polls that peer for attachment inventories.

### Recommendation
Enforce `inventory.len() == AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE` (and reject/truncate otherwise) either in `decode_atlas_attachments_inv_response` before returning `Ok(resp)`, or immediately in `extend_with_inventories` before inserting into `self.inventories`, treating a mismatched page size as a decode failure (`report.bump_failed_requests()` and skip storing that peer's response for the page).

### Proof of Concept
Rust test plan (net test) targeting `stackslib/src/net/atlas/download.rs` / `stackslib/src/net/api/getattachmentsinv.rs`:
1. Construct a `GetAttachmentsInvResponse { block_id, pages: vec![AttachmentPage { index: 0, inventory: vec![1u8; 10_000_000] }] }` (10 MB inventory vs. expected `ATTACHMENTS_INV_PAGE_SIZE`).
2. Serialize it to JSON and wrap it as a `StacksHttpResponse` payload (as would be received from `GET /v2/attachments/inv`), then call `decode_atlas_attachments_inv_response()` and assert it returns `Ok(..)` with `resp.pages[0].inventory.len() == 10_000_000` (no rejection/truncation).
3. Feed this `response` through `AttachmentsBatchStateContext::extend_with_inventories` via a `BatchedRequestsResult` with one `succeeded` entry for a crafted `AttachmentsInventoryRequest`.
4. Assert that `self.inventories` now contains an entry whose stored `AttachmentPage.inventory` still has length 10,000,000 (i.e., `context.inventories.get(&key).unwrap().get(&peer_url).unwrap().pages[0].inventory.len() == 10_000_000`), demonstrating the oversized peer-controlled allocation is retained unbounded and unvalidated.
