## Analog Found

### Title
Unauthenticated Account/Permission Existence and Structure Disclosure via `wallet/getsignweight` (`GetTransactionSignWeightServlet`) - (File: `framework/src/main/java/org/tron/core/services/http/GetTransactionSignWeightServlet.java`)

### Summary
The public, unauthenticated HTTP/gRPC endpoint that computes a transaction's "sign weight" accepts an arbitrary, unsigned (or partially signed) transaction body and returns distinct, information-rich error/result codes depending on whether the specified owner address exists, whether it has a given `permission_id`, and — when it does — full details of that account's multi-sig permission (threshold, keys, operations). No valid signature, balance, or prior relationship with the target account is required to query it, exactly mirroring the Capgo `rescind_invitation` pattern where distinguishable error codes (`NO_ORG` vs `NO_RIGHTS`) leak the existence of a protected resource to an anonymous caller.

### Finding Description
`GetTransactionSignWeightServlet.doPost` builds a `Transaction` straight from attacker-supplied JSON via `Util.packTransaction` and passes it — signatures optional — to `TransactionUtil.getTransactionSignWeight()`: [1](#0-0) 

Inside `getTransactionSignWeight`, the code extracts the owner address from `contract 0` of the supplied (unsigned) transaction and looks it up in `AccountStore`. It then returns one of several *distinguishable* outcomes without ever validating that the caller controls the owner address: [2](#0-1) 

- `PermissionException("Account does not exist!")` → surfaces as `response_code.PERMISSION_ERROR` with message `Account does not exist!` when the address is unused on-chain.
- `PermissionException("Permission for this, does not exist!")` → when the account exists but the requested `permission_id` was never configured (e.g., no `AccountPermissionUpdate` was ever executed, or an invalid id was chosen).
- Otherwise, on success, the endpoint echoes back the full `Permission` object (`tswBuilder.setPermission(permission)`), including operation bitmap, threshold, and the list of authorized keys/weights, plus `ENOUGH_PERMISSION`/`NOT_ENOUGH_PERMISSION` depending on the (attacker-controlled, possibly empty) signature list.

Because none of this requires bandwidth, a real transaction fee, or an actual signature from the target address, any anonymous API client can iterate over addresses/permission ids and learn (a) whether an address is a known TRON account, (b) whether it has customized multisig permissions, and (c) — when it does — the full authorized-key/threshold structure of that account's permission, all via distinct, machine-parseable response codes/messages. `getTransactionApprovedList` in `Wallet.java` exposes the identical oracle through a second endpoint: [3](#0-2) 

### Impact Explanation
This does not directly move funds, but it is a concrete information-disclosure oracle reachable by any unauthenticated JSON-RPC/HTTP client, exactly the bug class in the report: unauthenticated existence/structure enumeration of a protected resource (here, an account's multisig permission configuration) via differentiated error responses. Disclosing the exact keys/weights/thresholds of an account's active/owner permissions is a meaningful reconnaissance primitive for targeted phishing, social engineering, or key-compromise campaigns against high-value TRON accounts (exchanges, custodians, DAOs) — the same category of harm cited for the Capgo advisory (increased attack surface via organization/entity enumeration).

### Likelihood Explanation
Trivial to exploit: the endpoint is public, requires no authentication, no funded account, and no valid signature. An attacker only needs to POST a JSON transaction skeleton with an arbitrary `owner_address` (and optionally `Permission_id`) to enumerate accounts and dump permission structures at will, rate-limited only by `RateLimiterServlet`.

### Recommendation
Return a single, generic error/response code (or a constant success shape) for both "account does not exist" and "permission does not exist" cases so the two states are indistinguishable to the caller, and avoid echoing the full `Permission` object (keys/threshold) to unauthenticated callers — only weight/threshold-satisfaction booleans should be exposed, not the underlying key list. Apply the same fix consistently to both `TransactionUtil.getTransactionSignWeight` and `Wallet.getTransactionApprovedList`.

### Proof of Concept
1. `POST /wallet/getsignweight` with body:
```json
{"transaction":{"raw_data":{"contract":[{"type":"TransferContract","parameter":{"value":{"owner_address":"<TARGET_ADDRESS_HEX>","to_address":"...","amount":1}}}]}}}
```
2. Observe:
   - If `<TARGET_ADDRESS_HEX>` has never appeared on-chain → response `PERMISSION_ERROR` / `"Account does not exist!"`.
   - If it exists but the (optional) `Permission_id` in the contract references an unconfigured permission → `"Permission for this, does not exist!"`.
   - If it exists and has a custom active/owner permission → response includes the full `Permission` (threshold + `keys` list with addresses/weights) and `NOT_ENOUGH_PERMISSION`/`ENOUGH_PERMISSION`.
3. Iterate over a candidate address list to build a map of which addresses exist on-chain and which have multisig configured, plus dump their key/threshold structure — all without ever broadcasting a transaction or possessing any private key. [4](#0-3)

  public TransactionSignWeight getTransactionSignWeight(Transaction trx) {
    TransactionSignWeight.Builder tswBuilder = TransactionSignWeight.newBuilder();
    Result.Builder resultBuilder = Result.newBuilder();
    if (trx.getSignatureCount() > chainBaseManager.getDynamicPropertiesStore()
        .getTotalSignNum()) {
      resultBuilder.setCode(Result.response_code.OTHER_ERROR);
      resultBuilder.setMessage("too many signatures");
      tswBuilder.setResult(resultBuilder);
      return tswBuilder.build();
    }

    trx = truncateSignatures(trx);
    TransactionExtention.Builder trxExBuilder = TransactionExtention.newBuilder();
    trxExBuilder.setTransaction(trx);
    trxExBuilder.setTxid(ByteString.copyFrom(Sha256Hash.hash(CommonParameter
        .getInstance().isECKeyCryptoEngine(), trx.getRawData().toByteArray())));
    Return.Builder retBuilder = Return.newBuilder();
    retBuilder.setResult(true).setCode(response_code.SUCCESS);
    trxExBuilder.setResult(retBuilder);
    tswBuilder.setTransaction(trxExBuilder);

    if (trx.getRawData().getContractCount() == 0) {
      resultBuilder.setCode(Result.response_code.OTHER_ERROR);
      resultBuilder.setMessage("Invalid transaction: no valid contract");
    } else {
      try {
        Contract contract = trx.getRawData().getContract(0);
        byte[] owner = TransactionCapsule.getOwner(contract);
        AccountCapsule account = chainBaseManager.getAccountStore().get(owner);
        if (Objects.isNull(account)) {
          throw new PermissionException("Account does not exist!");
        }
        int permissionId = contract.getPermissionId();
        Permission permission = account.getPermissionById(permissionId);
        if (permission == null) {
          throw new PermissionException("Permission for this, does not exist!");
        }
        if (permissionId != 0) {
          if (permission.getType() != PermissionType.Active) {
            throw new PermissionException("Permission type is wrong!");
          }
          //check operations
          if (!checkPermissionOperations(permission, contract)) {
            throw new PermissionException("Permission denied!");
          }
        }
        tswBuilder.setPermission(permission);
