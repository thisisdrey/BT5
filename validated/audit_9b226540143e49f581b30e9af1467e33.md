## Title
Permissionless, refundable-deposit public proposal queue can be filled to block all legitimate proposals - (File: `substrate/frame/democracy/src/lib.rs`)

### Summary
`pallet-democracy`'s `propose` extrinsic is a public, unprivileged entrypoint that inserts an entry into the bounded `PublicProps` queue for the cost of only *reserving* (not spending) `MinimumDeposit`. Only one queue slot is drained per `LaunchPeriod` via `launch_next`. An attacker can reserve the minimum deposit on many accounts (or reuse one account across many `propose` calls limited only by nonce/fees) to fill `PublicProps` up to `MaxProposals`, after which `propose` unconditionally fails with `Error::TooMany` for every other user, for as long as the attacker keeps re-filling the queue. This mirrors the SEDA report's core invariant break: a permissionless, cheaply/refundably priced entry into a bounded, slow-draining processing queue can starve legitimate use of that queue.

### Finding Description
`PublicProps` is a `BoundedVec<..., T::MaxProposals>` [1](#0-0) . The `propose` call is `Signed`-only (no special permission) and enforces solely that the caller reserves at least `MinimumDeposit`: [2](#0-1) 

Key properties that make this a real analog of the SEDA bug:
- The cost to occupy a slot is a **reserved deposit**, not a burned fee — like SEDA's negligible gas payment that gets refunded once the request is processed, the `MinimumDeposit` here is returned to the proposer once the proposal is tabled (or slashed only on veto/cancel-by-governance) — see `deposit_for_proposals_should_be_returned` test confirming full deposit return [3](#0-2) .
- The queue itself has a **hard bound** (`MaxProposals`), and `propose` rejects with `TooMany` once full: `ensure!(real_prop_count < max_proposals, Error::<T>::TooMany);` [4](#0-3) 
- Draining is slow and bounded: only one queued proposal is tabled per `LaunchPeriod` (28 days in the reference `substrate/bin/node/runtime` config) [5](#0-4) .

An attacker with `MaxProposals * MinimumDeposit` in reservable balance (recoverable in full later) can submit `MaxProposals` low-effort proposals, permanently occupying the entire queue. Every subsequent legitimate `propose` call by any other account fails until the attacker's proposals are drained (at most 1 per `LaunchPeriod`), and the attacker can immediately re-propose as slots free up, indefinitely locking out legitimate governance proposals. This is functionally identical to SEDA's "cheap requests clog a bounded, slowly-processed queue and legitimate items never get through in time," except here the funds are fully recoverable (reserved, not spent), making the attack essentially free apart from opportunity cost and transaction fees.

### Impact Explanation
This blocks the primary permissionless governance entrypoint (public referenda proposals) for the whole chain, for as long as the attacker chooses to maintain the occupation, using only reservable (non-lost) funds. This matches the "public underpriced work that degrades block production or stalls processing" and "permanent user-fund or bridge-state lock"-adjacent impact class: legitimate proposers are locked out of using the public-proposal governance path, a live governance-availability degradation caused entirely by an unprivileged public call and existing (insufficient) anti-spam parameters.

### Likelihood Explanation
High for any chain still exposing `pallet-democracy`'s legacy proposal flow with a `MinimumDeposit`/`MaxProposals` configuration where `MaxProposals * MinimumDeposit` is within reach of a single actor (this is explicitly the reference `substrate/bin/node/runtime` configuration shown above: `MaxProposals: 100`, `MinimumDeposit: 100 DOLLARS`). No privileged role, governance action, validator, or malicious peer is required — a single signed account (or several) suffices, and the deposit is refunded, so the attack can be sustained indefinitely at near-zero net cost.

### Recommendation
- Introduce a non-refundable, escalating cost for proposal submission (e.g., a portion of the deposit burned rather than fully reserved/returned), or
- Rate-limit proposal submissions per account/per block, or
- Increase `MaxProposals` drain rate to be proportional to spam pressure, or restrict `propose` to require it be economically infeasible to occupy the full queue (e.g., require deposit scaling with current queue occupancy), analogous to fixing SEDA via mandatory fees or permissioning the entrypoint.

### Proof of Concept
1. Attacker account(s) call `Democracy::propose(origin, proposal, MinimumDeposit)` `MaxProposals` times in quick succession (bounded only by transaction fees and nonce increments), each reserving `MinimumDeposit` (fully refundable later).
2. `PublicProps::decode_len()` reaches `MaxProposals`; any subsequent `propose` call from a legitimate account fails with `Error::TooMany` (line 597 of `substrate/frame/democracy/src/lib.rs`).
3. Only one slot is freed per `LaunchPeriod` (28 days by default in the reference runtime) via the launch logic invoked from `on_initialize`/`begin_block`. The attacker can immediately re-submit a new proposal to refill the freed slot, keeping the queue permanently saturated and locking out legitimate proposers indefinitely, while eventually reclaiming all reserved deposits when their own (never-passing) proposals are processed.

Note: I could not fully trace the exact `launch_next`/`begin_block` drain-rate code in this pass (search hits were truncated before content could be inspected), so the "exactly one slot per LaunchPeriod" claim is based on the well-documented pallet design (see `README.md` describing the launch-period-based tabling mechanism) rather than a directly cited code excerpt of `launch_next`; a full Devin session with file access would be needed to confirm the precise drain cadence and any additional mitigations (e.g., prioritization by backing) that might partially blunt but likely do not eliminate this DoS vector.

		pub fn propose(
			origin: OriginFor<T>,
			proposal: BoundedCallOf<T>,
			#[pallet::compact] value: BalanceOf<T>,
		) -> DispatchResult {
			let who = T::SubmitOrigin::ensure_origin(origin)?;
			ensure!(value >= T::MinimumDeposit::get(), Error::<T>::ValueLow);

			let index = PublicPropCount::<T>::get();
			let real_prop_count = PublicProps::<T>::decode_len().unwrap_or(0) as u32;
			let max_proposals = T::MaxProposals::get();
			ensure!(real_prop_count < max_proposals, Error::<T>::TooMany);
			let proposal_hash = proposal.hash();

			if let Some((until, _)) = Blacklist::<T>::get(proposal_hash) {
				ensure!(
					frame_system::Pallet::<T>::block_number() >= until,
					Error::<T>::ProposalBlacklisted,
				);
			}

			T::Currency::reserve(&who, value)?;

			let depositors = BoundedVec::<_, T::MaxDeposits>::truncate_from(vec![who.clone()]);
			DepositOf::<T>::insert(index, (depositors, value));

			PublicPropCount::<T>::put(index + 1);

			PublicProps::<T>::try_append((index, proposal, who))
				.map_err(|_| Error::<T>::TooMany)?;

			Self::deposit_event(Event::<T>::Proposed { proposal_index: index, deposit: value });
			Ok(())
		}
