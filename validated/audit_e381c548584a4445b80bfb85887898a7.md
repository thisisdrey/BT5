## Finding: Quadratic-complexity resource-delegation bookkeeping in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` (legacy `DelegatedResourceAccountIndex` path)

### Title
Unbounded O(n) protobuf list rebuild per delegate/undelegate call causes quadratic-time DoS when the `AllowDelegateOptimization` chain parameter is not active - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
When the chain parameter `AllowDelegateOptimization` is not yet enabled (its default value is `0`/off until activated by a committee proposal), `FreezeBalanceActuator` and `UnfreezeBalanceActuator` maintain the list of delegation counterparties (`DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList`) as a single protobuf-encoded list per account. Every delegate/undelegate operation performs a linear scan (`contains()`/`remove()`) and rebuilds/re-serializes the *entire* list via `toBuilder().addAllToAccounts(...)`/`clearToAccounts().addAllToAccounts(...)`, which is `O(n)` in the current list size. An attacker who repeatedly freezes/delegates small amounts of TRX to many distinct new receiver addresses from a single account can grow this list to size `n`, making the total cost of `n` such transactions `O(n²)`, mirroring the write-time quadratic-algorithm pattern described in CVE-2021-32617 (an inefficient algorithm triggered by attacker-controlled "writes").

### Finding Description
`FreezeBalanceActuator.delegateResource()` reads `DelegatedResourceAccountIndexStore` and, on the legacy path (`!dynamicPropertiesStore.supportAllowDelegateOptimization()`), does: [1](#0-0) 

```
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
  ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
}
```
`getToAccountsList()`/`addToAccount()` operate on the underlying protobuf message, and `addToAccount` internally does `toBuilder().addToAccounts(toAccount).build()`, which copies the whole repeated field: [2](#0-1) 

The `contains()` check itself is also `O(n)` over the existing list. Symmetrically, `UnfreezeBalanceActuator.execute` copies the full list into an `ArrayList`, does a linear `remove()`, then calls `setAllToAccounts()` (another full rebuild): [3](#0-2) 

Because both the "does it already contain the receiver" check and the "rebuild the list" step scale with the current list length, any account that delegates bandwidth/energy to `n` distinct receiver addresses (or unfreezes `n` distinct delegations) pays cumulative `O(n²)` work in the actuator's `execute()`, which every full node must replay while applying that account's transactions/block. This is directly analogous to Exiv2's quadratic metadata-writing bug: the vulnerable operation is a "write" (mutating and re-persisting a growing collection) reachable purely from ordinary user-signed contracts (`FreezeBalanceContract`/`UnfreezeBalanceContract`), not from privileged roles.

### Impact Explanation
An attacker controlling one funded account can issue a sequence of `FreezeBalanceContract` transactions, each delegating a minimal amount (≥1 TRX, per validate()'s `frozenBalance >= TRX_PRECISION` check) to a freshly generated receiver address, forcing `DelegatedResourceAccountIndexStore` entries to grow unbounded. As nodes process these transactions (in mempool validation and/or block application), the per-transaction actuator cost grows linearly with the attacker's own list size, so `n` transactions cost `O(n²)` CPU/serialization time for the node, degrading block processing time for all nodes on the network and potentially causing block processing to fall behind (chain liveness/availability impact), consistent with the CVSS 3.1 vector in the analog report (`AV:L/AC:L/PR:N/UI:R/S:U/C:N/I:N/A:H`) mapped here to node availability degradation.

### Likelihood Explanation
The legacy code path is only exercised while `supportAllowDelegateOptimization()` returns false, i.e., before the corresponding chain parameter is activated by committee proposal on a given network. On networks/deployments where this optimization proposal has not been (or cannot be) activated — including private/consortium java-tron networks freshly bootstrapped from this codebase — the vulnerable path is the default and reachable by any unprivileged account with minimal TRX balance, at very low cost per transaction (1 TRX freeze, later unfreezable).

### Recommendation
- Regardless of `AllowDelegateOptimization` state, avoid `O(n)` `contains()`/list-rebuild patterns in `DelegatedResourceAccountIndexCapsule`; use the already-existing indexed key/value scheme (`DelegatedResourceAccountIndexStore.delegate/unDelegate`, keyed by `(from,to)` pairs) unconditionally instead of maintaining the legacy embedded-list index at all.
- If backward compatibility with the legacy format must be retained, bound the maximum number of distinct delegation counterparties per account (similar to `MAX_VOTE_NUMBER`/`MAX_MATCH_NUM` caps used elsewhere in the codebase) to cap worst-case work.
- Migrate/force-enable `AllowDelegateOptimization` semantics by default for new networks bootstrapped from this codebase so the legacy quadratic path is never reachable.

### Proof of Concept
1. Deploy/start a java-tron network from this codebase without activating the `AllowDelegateOptimization` proposal (`supportAllowDelegateOptimization()` returns `0`).
2. From a single funded account `A`, submit `n` (e.g., 5,000) `FreezeBalanceContract` transactions with `receiverAddress` set to `n` distinct, freshly generated addresses and `resource = BANDWIDTH`, each freezing the minimum `1 TRX`.
3. Observe that `DelegatedResourceAccountIndexStore` entry for `A` grows to hold `n` `toAccounts` entries, and that block/transaction processing time for each subsequent `FreezeBalanceContract` from `A` increases roughly linearly with `n`, so the whole sequence takes on the order of `n²` (via `FreezeBalanceActuator.delegateResource` → `DelegatedResourceAccountIndexCapsule.getToAccountsList().contains()` + `addToAccount()` at [4](#0-3) ).
4. Repeat with `UnfreezeBalanceContract` for the same `n` receivers to observe the symmetric quadratic cost in [5](#0-4) .
