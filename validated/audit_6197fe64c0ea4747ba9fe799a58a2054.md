### Title
Duplicate weight accumulation from the same key in `ValidateMultiSign` precompile allows multisig threshold bypass - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract accumulates permission weights per submitted signature, but its duplicate-detection logic only rejects a signature if the *exact byte-identical* signature was already used for a recovered address — not if the *same address* had already contributed weight via a different (e.g. malleated) signature. This lets a caller reach a multisig weight threshold by submitting several distinct valid signatures for a single private key, rather than genuinely obtaining independent signers, which mirrors the reported bug class: a participant count/weight used to decide whether a threshold is met can be inflated by repeated submissions from the same actor.

### Finding Description
`ValidateMultiSign.execute` loops over the supplied signatures, recovers the signer address for each, and adds the corresponding permission weight to `totalWeight` until `permission.getThreshold()` is met: [1](#0-0) 

The de-duplication check is:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
``` [2](#0-1) 

If `recoveredAddr` is already present in `executedSignList` (i.e. this key already contributed), the code only `continue`s (skips adding weight again) when the exact `sign` byte-array was already recorded. If the caller supplies a *different* valid signature for the same key over the same `hash` (ECDSA signature malleability produces a second valid `(r, n-s)` signature for the same `(message, key)` pair, or simply re-signing with a different nonce yields a different `(r,s)` for the same key), `matrixContains(executedSignList, sign)` is false, so execution falls through and `totalWeight += weight` is executed again for the same signer. The check `TransactionCapsule.getWeight(permission, recoveredAddr)` only validates that the address is a member of the permission with a weight — it does not prevent counting that weight more than once.

This is the same root-cause class as the reported issue: a threshold/quorum decision (`totalWeight >= permission.getThreshold()`) is computed from a count of *submissions* rather than a count of *distinct participants*, allowing a single actor to manipulate the outcome by supplying multiple submissions.

### Impact Explanation
`ValidateMultiSign` is a precompiled contract reachable from any TVM contract call by an unprivileged transaction sender/contract deployer — it is used by smart contracts (and off-chain integrations relying on multisig authorization patterns) to verify whether a set of signatures satisfies an account's `Permission` threshold, e.g. for gating custody/withdrawal logic implemented in Solidity that checks TRON account permissions on-chain. If a single co-signer, or an attacker who obtains just one private key of a multi-key permission, can synthesize multiple distinct valid signatures for that one key, they can satisfy `totalWeight >= threshold` without collecting the required number of independent co-signer approvals. Any contract-level authorization logic built on this precompile (multisig wallets, custodial vaults, governance gates) can therefore be bypassed with a single compromised or single legitimately-owned key, resulting in unauthorized approval/execution of account operations that were intended to require multiple independent signers — a concrete unauthorized-account-operation / theft-of-funds impact for any contract relying on it.

### Likelihood Explanation
Exploitability requires only: (1) a `Permission` configured with `threshold > weight_of_single_key` and multiple keys, and (2) the ability to produce two distinct valid signatures over the identical `hash` with one of the member keys — achievable trivially via ECDSA malleability (flipping `s` to `n-s` yields a second valid signature for the same message/key without needing the private key holder's cooperation) or simply by having the key holder sign twice with different nonces. Since `ValidateMultiSign` is invoked purely through a TVM `STATICCALL`/`CALL` from any contract by any transaction sender, the precompile is reachable without any special privilege, making this a directly and cheaply exploitable path.

### Recommendation
Track distinct signer addresses (not raw signature bytes) to prevent counting weight more than once per address:
```java
if (ByteArray.matrixContains(executedAddrList, recoveredAddr)) {
  continue; // this key has already contributed weight; skip regardless of signature bytes
}
...
totalWeight += weight;
executedAddrList.add(recoveredAddr);
```
Remove the byte-exact `sign` comparison entirely as the basis for allowing repeated weight accumulation, since only the *address* should determine whether weight has already been counted.

### Proof of Concept
1. Configure an account permission with two keys, `K1` and `K2`, each weight 1, threshold 2 (i.e. requires both signers).
2. An attacker who controls only `K1` computes a valid ECDSA signature `sig1 = (r, s)` over `hash`, and derives the malleable counterpart `sig2 = (r, n-s)`, both of which recover to the same address for `K1`.
3. Attacker (or any contract caller) invokes the `ValidateMultiSign` precompile with `signatures = [sig1, sig2]`.
4. In the loop: for `sig1`, `executedSignList` is empty, so weight for `K1` (1) is added; `sign`/`recoveredAddr` recorded. For `sig2`, `matrixContains(executedSignList, recoveredAddr)` is true (same address as `K1`), but `matrixContains(executedSignList, sign)` is false (different byte signature), so it does **not** `continue` — it proceeds to add another weight of 1 for `K1`.
5. `totalWeight` becomes 2, meeting `threshold = 2`, and the precompile returns success (`dataOne()`) even though only `K1` ever signed — `K2`'s participation was never actually obtained. [3](#0-2)
