### Title
Integer underflow in reftable ref-block parsing causes out-of-bounds panic on repository read - (File: internal/git/reftable/reftable.go)

### Summary
`Table.parseRefBlock` computes the start offset of a block's restart table using unsigned (`uint`) subtraction without validating that the subtrahend does not exceed the minuend, directly mirroring the PoolTogether `captureAwardBalance` bug class where a derived value (`totalInterest`) was subtracted from an accumulator without checking that the accumulator was large enough.

### Finding Description
In `parseRefBlock`, the restart-table offset is computed as: [1](#0-0) 

`b.RestartCount` is read directly from file bytes into a `uint16`, and `currentBS` (the on-disk block length) is extracted from the same untrusted region via `extractBlockLen`: [2](#0-1) 

All of `blockStart`, `currentBS`, and `RestartCount` are `uint`/`uint16` values sourced from parsing a `.ref` table file with no cross-validation between them before the subtraction `currentBS - 2 - 3*uint(b.RestartCount)` is performed. If `3*RestartCount` (plus 2) exceeds `blockStart+currentBS`, the unsigned subtraction wraps around to a huge value instead of erroring, exactly analogous to the Solidity bug where `_currentAwardBalance - totalInterest` could underflow when `totalInterest` exceeded the balance. The resulting `b.RestartStart` is then used unguarded as a loop bound and slice index in `getRefsFromBlock`: [3](#0-2) 

Because `idx < b.RestartStart` will now be true for an enormous `RestartStart`, the loop proceeds to index into `src` (a byte slice read fully into memory via `io.ReadAll`) far beyond its bounds, causing an out-of-bounds slice panic (crash) or, in principle, reading unrelated heap memory before the panic trigger.

### Impact Explanation
`Table.ParseTable`/`GetReferences` is used by Gitaly's transaction manager to resequence newly written reftable table files during transaction commit for repositories using the `reftable` reference backend (`internal/gitaly/storage/storagemgr/partition/reftable.go`, `stageTables`), and by `internal/git/stats/repository_info.go` when computing `RepositoryInfo` for a repository. These are integral, non-test code paths reachable during ordinary push/write-transaction processing and repository info collection RPCs. A corrupted or truncated reftable file — which could arise from crash-induced partial writes, storage corruption, or any code path that mis-produces a `.ref` file such that `RestartCount` is inconsistent with the block's actual size — will crash the goroutine handling that transaction/RPC with an out-of-bounds panic rather than a handled error, since there is no bounds check before the subtraction and no `recover` around this specific computation.

### Likelihood Explanation
The precondition (an internally-inconsistent block header/restart count) does not require an external malicious actor with elevated privileges; it can arise from ordinary write-transaction commit races, crashes mid-write, or any deviation between the assumed reftable format and actual on-disk bytes — the same "differing calculation vs. actual value" root cause identified in the referenced report. Because Gitaly reads these tables back during its own transaction commit (`stageTables`) rather than only in test helpers, this is a reachable, unprivileged-adjacent DoS surface for any repository using the reftable backend.

### Recommendation
Before computing `b.RestartStart`, validate that `currentBS >= 2 + 3*uint(b.RestartCount)` and that the resulting offset stays within `[blockStart+headerOffset, blockEnd]`; return an explicit parse error instead of allowing the unsigned subtraction to wrap. Apply the same bounds validation to `extractBlockLen` and `getVarInt` results before they are used as slice indices in `getRefsFromBlock`.

### Proof of Concept
Construct (or corrupt) a reftable `.ref` file whose ref-block header encodes a `block_len` (`currentBS`) and 2-byte restart count such that `3*RestartCount + 2 > currentBS`. Calling `reftable.ParseTable` followed by `GetReferences` (as done in `stageTables` during a write-transaction commit, or via `RepositoryInfoForRepository`) on such a file causes `parseRefBlock` to underflow `RestartStart` to a very large `uint`, making `getRefsFromBlock`'s loop condition `idx < b.RestartStart` true well beyond the actual buffer size and triggering an index-out-of-range panic when reading `src[idx]`.
