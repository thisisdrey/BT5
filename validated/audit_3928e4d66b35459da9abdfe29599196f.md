### Title
`VaultShareToken.setVault` revokes MINTER_ROLE/BURNER_ROLE from the outgoing vault, permanently freezing that vault's already-approved/claimable and pending ERC-7540 deposit/redeem requests - (File: `tare-io__tare-contracts/contracts/VaultShareToken.sol`)

### Summary
`VaultShareToken.setVault(newVault)` immediately revokes `MINTER_ROLE` and `BURNER_ROLE` from the outgoing `PortfolioVault` [1](#0-0) , but the outgoing `PortfolioVault` contract itself is not decommissioned, migrated, or drained by this call — it is a completely separate contract from `VaultShareToken` with its own independent `pendingDepositAssets`, `claimableDepositShares`, `pendingRedeemShares`, and `claimableRedeemAssets` counters. This is structurally the same root cause as the JBController `changeTokenOf` finding: an owner/guardian-triggered pointer swap silently strips the ability of honest, already-committed users to complete their entitled claim against the pre-existing balance, with no migration path or delay for those in-flight requests.

### Finding Description
`PortfolioVault.deposit`/`mint` call `shareToken.mint(...)` and `PortfolioVault.redeem`/`withdraw` call `shareToken.burn(...)`, which require `MINTER_ROLE`/`BURNER_ROLE` on `msg.sender` (the vault) respectively. When `setVault(newVault)` is called, `_revokeRole(MINTER_ROLE, oldVault)` and `_revokeRole(BURNER_ROLE, oldVault)` execute unconditionally and instantly, with no check for the old vault's outstanding liabilities [1](#0-0) . Any controller who already has:
- `claimableDepositShares[controller] > 0` (approved deposit awaiting `deposit()`/`mint()`) — needs `shareToken.mint` from the old vault,
- `pendingRedeemShares[controller] > 0` or `claimableRedeemAssets[controller] > 0` (redeem in flight or approved) — needs `shareToken.burn` from the old vault,

can no longer complete these calls on the old `PortfolioVault`, because that vault has lost its role and every `mint`/`burn` call will revert with `AccessControlUnauthorizedAccount`. The new vault is *not* auto-granted these roles (confirmed by the repo's own tests and spec) [2](#0-1) [3](#0-2) , and even if it were, the new vault has no knowledge of the old vault's per-controller `pending*`/`claimable*` state (those live in the old `PortfolioVault`'s storage, not in `VaultShareToken`), so there is no code path that lets a user redirect an in-flight claim to the new vault.

This mirrors the audited bug class exactly: a single admin-facing pointer swap (`changeTokenOf` / `setVault`) severs the link needed by *existing, unprivileged* holders to redeem value they are already entitled to, with the only stated recommendation in the original report being "add a delay" or "add a conversion path" — neither of which `setVault` implements.

### Impact Explanation
Any user with `claimableDepositShares`, `pendingRedeemShares`, or `claimableRedeemAssets` recorded against the outgoing vault at the moment `setVault` executes has their USDC or shares permanently stuck in that vault: `deposit`/`mint`/`redeem`/`withdraw` all revert going forward because the required `MINTER_ROLE`/`BURNER_ROLE` was revoked, and there is no re-grant, migration, or conversion function that lets these balances be honored through the new vault. This is an unrecoverable lock of USDC/shares belonging to honest, unprivileged shareholders — squarely inside the allowed impact ("Permanent or practically unrecoverable lock of USDC, claimable assets, shares... caused by an unprivileged path" combined with a privileged trigger that fails to protect existing user state, exactly as in the seed report). The only recovery listed anywhere in the repo (`Rescuable.rescueERC20Tokens`/`rescueERC721Tokens`) does not update the stale `pending*`/`claimable*` counters, so it does not actually make affected users whole and further desyncs internal accounting (as SECURITY.md item #2 separately warns for that mechanism).

### Likelihood Explanation
`setVault` is a documented, expected part of the protocol's operational lifecycle (share-token/vault rotation is explicitly called out in `specs/vault.md`'s role table and tests), so it is not a hypothetical edge case — it is a designed migration primitive. Unlike the `PortfolioVault`-side migrations (`setLoans`/`setExchange`/`setCalculator`), which have a dedicated, carefully engineered `vault-migration-runbook.md` with atomic batching, `_requireIdleNav` gating, and on-chain post-condition assertions to protect `pending*`/`claimable*` accounting during migration, there is **no equivalent runbook, drain requirement, or guard for `VaultShareToken.setVault`**. Any guardian action calling `setVault` while the old vault has outstanding requests immediately strands those users, and nothing in the codebase (tests, spec, or `SECURITY.md`) documents this as an accepted/known issue — item #17 in `SECURITY.md` covers a related but distinct gap (missing `SHAREHOLDER_ROLE` check on the new vault), not this one.

### Recommendation
Before or atomically with `setVault`, require the outgoing vault to be fully drained of liabilities (`totalPendingDepositAssets() == 0 && totalClaimableRedeemAssets() == 0`, and equivalent share-side counters), or provide an explicit migration function that transfers/settles the old vault's `pending*`/`claimable*` state into the new vault before revoking `MINTER_ROLE`/`BURNER_ROLE`. At minimum, add an on-chain precondition to `setVault` that reverts unless these counters on the outgoing `PortfolioVault` are zero, mirroring the idle-NAV/drain discipline already enforced for `PortfolioVault`'s own `setLoans`/`setExchange` migrations.

### Proof of Concept
1. Controller `C` calls `PortfolioVault(oldVault).requestRedeem(shares, C, C)`; `INVESTOR_MANAGER` calls `approveRedemption(...)`, setting `claimableRedeemAssets[C] > 0` and locking `C`'s shares inside `oldVault`.
2. Before `C` calls `withdraw`/`redeem`, guardian calls `VaultShareToken.setVault(newVault)` as part of a routine vault rotation — this revokes `BURNER_ROLE` from `oldVault` [1](#0-0) .
3. `C` calls `PortfolioVault(oldVault).withdraw(...)` / `redeem(...)`; internally this calls `shareToken.burn(C, shares)`, which now reverts with `AccessControlUnauthorizedAccount(oldVault, BURNER_ROLE)` (as directly demonstrated by the existing regression test for the analogous mint case) [4](#0-3) .
4. `C`'s USDC entitlement (`claimableRedeemAssets[C]`) remains stuck in `oldVault` indefinitely; there is no function anywhere in `PortfolioVault` or `VaultShareToken` to re-point, migrate, or convert this claim to `newVault`.

```text
  function setVault(address newVault) external onlyRole(GUARDIAN_ROLE) {
    require(newVault != address(0), ZeroAddress());

    // Revoke mint/burn authority from the outgoing vault so an exploited old
    // vault cannot mint or burn shares.
    address oldVault = _vault;
    _revokeRole(MINTER_ROLE, oldVault);
    _revokeRole(BURNER_ROLE, oldVault);

    _vault = newVault;
    emit VaultUpdate(_asset, newVault);
  }
```

Share transfers are restricted: both sender and recipient must have `SHAREHOLDER_ROLE`. For mints (`from == address(0)`), only the sender check is skipped — the recipient must still have `SHAREHOLDER_ROLE`. For burns (`to == address(0)`), only the recipient check is skipped — the sender must still have `SHAREHOLDER_ROLE`.

**Rotating the vault (`setVault`)**: the guardian-only `setVault(newVault)` updates the `vault(asset)` pointer and immediately revokes `MINTER_ROLE` and `BURNER_ROLE` from the outgoing vault, so an exploited old vault can no longer mint or burn shares. It does not grant those roles (or `SHAREHOLDER_ROLE`) to the new vault — the guardian must do that in a separate action before the new vault can operate.
