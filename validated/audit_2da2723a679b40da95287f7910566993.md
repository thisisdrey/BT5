## Analysis

The CVE describes `mp_box_deserialize_string` trusting an attacker-supplied length field and allocating memory for it without validating it against the available data, causing a DoS. The closest reachable analog in java-tron is in the precompiled-contract array-decoding helpers in `PrecompiledContracts.java`, which are invoked from TVM opcodes reachable by any contract call.

### Title
Unbounded array-length field from precompiled-contract calldata drives unchecked allocation, causing node DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array`, and (depending on the `allowTvmSelfdestructRestriction` feature flag) `extractBytesArray`/`extractSigArray`, take an attacker-controlled length word directly from the precompiled-contract's ABI-encoded input and use it to size a Java array (`new byte[len][]`) before any bound is enforced against `MAX_SIZE` or the actual payload size. ### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` straight from caller-supplied `DataWord[]` data and immediately allocates `new byte[len][]` with no upper bound check: [2](#0-1) 

This function is invoked unconditionally (regardless of `allowTvmSelfdestructRestriction`) from `BatchValidateSign.doExecute()` to build the `addresses` array: [3](#0-2) 

Similarly, `extractBytesArray`/`extractSigArray` (also length-unbounded internally) are only preceded by a `sigArraySize > MAX_SIZE` guard when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; when this hardfork-gated feature is off, the raw, unchecked length flows straight into the allocation: [4](#0-3) [5](#0-4) 

Both `ValidateMultiSign` (0x66-style) and `BatchValidateSign` precompiled contracts are reachable from any `TriggerSmartContract` call an unprivileged account can broadcast — an attacker only needs to craft calldata whose length-prefix word (e.g. `words[offset]`) is a very large integer, which is trivial and cheap to construct since the actual raw calldata can be tiny (a handful of 32-byte words) while the declared array length is set to a large value such as `0x7FFFFFFF`. This mirrors the CVE's root cause: a length field taken from untrusted input is used to size an allocation before validating it against the real payload/bounds, letting a tiny malicious input trigger a disproportionately large allocation attempt.

### Impact Explanation
A crafted `TriggerSmartContract` transaction invoking `ValidateMultiSign`/`BatchValidateSign` with a huge declared array length causes the node executing/validating the transaction to attempt a very large array allocation (`new byte[len][]`), which can throw `OutOfMemoryError` or cause severe GC pressure/heap exhaustion on the JVM processing the transaction. Since transaction validation happens on every full node that receives/validates/executes the block, this can crash or degrade multiple nodes in the network, which matches the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Any unprivileged account can broadcast a `TriggerSmartContract` transaction against a deployed contract that calls these precompiles (or directly invoke the precompile address if reachable), and the exploit calldata is small and easy to construct — no privileged keys or special roles are required.

### Recommendation
Add an explicit bound check (e.g., against `MAX_SIZE` or a sane maximum derived from `data.length`/`WORD_SIZE`) immediately after reading `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, before allocating the array, regardless of the `allowTvmSelfdestructRestriction` flag state. This mirrors the fix pattern already present for the guarded path.

### Proof of Concept
Construct ABI-encoded calldata for `BatchValidateSign(bytes32,bytes[],bytes32[])` (or `ValidateMultiSign`) where the pointer to the `addresses`/`signatures` array points to a word whose value is a very large integer (e.g., `0x7FFFFFFF`) while the rest of the calldata is minimal. Broadcast this via a `TriggerSmartContract` transaction to a contract calling the precompile (address for `BatchValidateSign`). During TVM execution, `extractBytes32Array`/`extractBytesArray` will attempt `new byte[0x7FFFFFFF][]`, triggering an `OutOfMemoryError` on the executing node.

**Note on verification limits**: I was unable to fully confirm the exact clamping behavior of `DataWord.intValueSafe()` (i.e., whether it always returns a value in the valid `int` range, and what the practical maximum it can return is) due to running out of tool iterations before reading `common/src/main/java/org/tron/common/runtime/vm/DataWord.java` in full. If `intValueSafe()` clamps to a smaller safe ceiling than `Integer.MAX_VALUE`, the achievable allocation size (and thus DoS severity) may be smaller than assumed here — this should be verified against that method's implementation before treating the PoC as final.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
