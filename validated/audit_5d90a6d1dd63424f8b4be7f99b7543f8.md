Based on my research, I found a strong analog in nearcore for the Keystore.sol "wrong rootHash" bug class: the **hardcoded `eth_wallet_global_contract_hash`** used to bind every ETH-implicit account to its executable logic, with no on-chain path to correct a mismatch.

### Title
Hardcoded ETH-implicit wallet-contract hash is the sole, unfixable pointer to account logic — a mismatch permanently freezes all funds sent to ETH-implicit accounts - (File: `runtime/near-wallet-contract/src/lib.rs`)

### Summary
When the `EthImplicitGlobalContract` protocol feature is active, every ETH-implicit account (`0x...` address) is created pointing at `AccountContract::Global(hash)` where `hash = eth_wallet_global_contract_hash(chain_id)` — a value hardcoded as a raw byte array in the binary [1](#0-0) , written into the new account at creation time [2](#0-1) . This is structurally identical to Keystore.sol's `rootHash`: a single committed hash that is the only way the account's logic/state can ever be resolved, and it is never re-validated against what's actually deployed on-chain.

### Finding Description
`RuntimeContractIdentifier::resolve` turns an account's `AccountContract::Global(hash)` into a lookup key for `DBCol` state under `TrieKey::GlobalContractCode { identifier: CodeHash(hash) }` [3](#0-2) . `GlobalContractIdentifier::CodeHash(hash).hash()` trusts the hash unconditionally and never checks that a contract is actually stored under it [4](#0-3) ; the failure only surfaces later, when the code is actually fetched (`.code()`, returning `None` if the state key is empty) or via `GlobalContractDoesNotExist` in `use_global_contract`/`prepare_function_call` paths [5](#0-4) .

If `eth_wallet_global_contract_hash` is ever wrong for a live chain_id — e.g., a bug when the constant was computed/updated for a wallet-contract redeploy (the exact "bug in the creation script" scenario from the report) — then:
1. Every ETH-implicit account created while that wrong hash is active gets `AccountContract::Global(wrong_hash)` baked into its account record permanently [2](#0-1) .
2. ETH-implicit accounts are created with **no access key at all** (unlike NEAR-implicit accounts, which get a `FullAccess` key) [6](#0-5) ; the only way to ever control such an account is through the Wallet Contract's `rlp_execute` method, per design [7](#0-6) .
3. If `wrong_hash` doesn't correspond to any contract actually deployed under `DeployGlobalContract`/`CodeHash` mode on that shard, every `FunctionCall` (including `rlp_execute`) against the account fails, because the contract-preparation pipeline resolves the same wrong hash and cannot find code for it [8](#0-7) .
4. There is **no recovery action**: `UseGlobalContractAction` (the only mechanism to repoint `AccountContract`) requires `check_actor_permissions`, which in turn requires signing with an access key belonging to the account — but no such key exists and can never be added, since `AddKey`/`DeleteAccount` on an ETH-implicit account can only be authorized by the account itself executing through the (now-unreachable) Wallet Contract.

This exactly mirrors the Keystore.sol bug class: a single hash, committed once with no independent validation against on-chain reality, that becomes the sole and irrevocable gate to an account's usability, with the codebase providing no admin/emergency path to repair it once wrong.

### Impact Explanation
Any funds sent via `Transfer` to any ETH-implicit account (a very common operation — the entire point of ETH-implicit accounts is receiving transfers from Ethereum-compatible wallets/relayers before the account is otherwise touched) would become **permanently and irrecoverably frozen** for the lifetime of the wrong-hash window: the account can never execute a function call, never add a key, and never be deleted, so its balance is locked forever with no on-chain remediation. This is a protocol-wide freezing-of-funds bug (matches the "permanent freezing of funds" acceptance criterion), not localized to one user's mistake — it is systemic, since every account of this type sharing the resolution function is equally locked out.

### Likelihood Explanation
This requires the hardcoded constant to actually be wrong on a live network — i.e., a maintenance/release bug when `eth_wallet_global_contract_hash` is updated for a new wallet-contract WASM build (there is already a documented history of correcting/tracking multiple contract variants across chains, `MAINNET`/`TESTNET`/`OLD_TESTNET`/`LOCALNET`, showing this value has changed and been chain-specific over time [9](#0-8) ). It is not attacker-triggerable, but it is a plausible operational/release-process error directly analogous to "a bug in the creation script" in the original report, and its blast radius (every ETH-implicit account, not just one) is broader than the original finding.

### Recommendation
Add a fallback/migration path so a wrong `eth_wallet_global_contract_hash` is recoverable without bricking existing accounts: e.g., allow the protocol to accept a short allow-list/history of valid wallet-contract hashes per chain (similar to the existing `LegacyEthWallet`/`OLD_TESTNET` special-casing already present in `code_hash_matches_wallet_contract` [10](#0-9) ), or gate activation of a corrected hash behind a protocol upgrade that re-points already-created accounts rather than leaving them permanently pinned to the value baked in at creation time.

### Proof of Concept
1. Assume `EthImplicitGlobalContract` is active and, due to a build/release error, `eth_wallet_global_contract_hash(chain_id)` returns a hash `H` that does not match any WASM actually distributed via `DeployGlobalContract{ deploy_mode: CodeHash }` for that hash on-chain.
2. Any user sends `Transfer` to a fresh `0x...` account; `action_implicit_account_creation_transfer` creates it with `AccountContract::Global(H)` [11](#0-10) .
3. Any subsequent attempt to interact with the account — `rlp_execute` via `FunctionCall`, `AddKey`, `DeleteAccount` — fails: `check_account_existence`/`check_actor_permissions` require an access key that was never created, and the contract-preparation path for `FunctionCall` cannot resolve code for `H` [8](#0-7) .
4. The deposited balance remains in the account forever; no action in the codebase can move `AccountContract` off `Global(H)` for this account (`UseGlobalContractAction` itself requires the same unreachable authorization).

/// Checks if the given code hash corresponds to the wallet contract (signalling
/// the runtime should treat the wallet contract as the code for the account).
pub fn code_hash_matches_wallet_contract(chain_id: &str, code_hash: &CryptoHash) -> bool {
    let magic_bytes = wallet_contract_magic_bytes(&chain_id);

    if code_hash == magic_bytes.hash() {
        return true;
    }

    // Extra check needed for an old version of the wallet contract
    // that was on testnet. Accounts with that hash are still intentionally
    // made to run the current version of the wallet contract because
    // the previous version had a bug in its implementation.
    if chain_id == chains::TESTNET {
        let alt_testnet_code = OLD_TESTNET.magic_bytes();
        return code_hash == alt_testnet_code.hash();
    }

    false
}
