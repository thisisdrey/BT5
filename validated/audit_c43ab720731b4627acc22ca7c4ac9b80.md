### Title
Vault accounting trusts the nominal `transfer` amount instead of the actual balance delta, breaking solvency for fee-on-transfer/non-standard SIP-010 underlying tokens - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, and equivalently `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`)

### Summary
Every Zest v0 vault's `receive-underlying`/`send-underlying` helper — and by extension `deposit`/`redeem` — assumes that calling `transfer` for `amount` on the underlying SIP-010 token moves exactly `amount` units of value into/out of the vault. If the underlying asset ever charges a transfer fee or otherwise delivers less than the nominal `amount` (the same root-cause class as the referenced AaveV3 fee-on-transfer redemption issue), the vault's internal `assets` variable and freshly minted zTokens will over-state the real backing held by the contract, exactly mirroring the reported bug class where a fixed expected amount is compared/credited against a fee-adjusted actual transfer.

### Finding Description
`receive-underlying` and `send-underlying` simply forward the caller-supplied `amount` to `contract-call? ... transfer` and treat success as proof that exactly `amount` moved: [1](#0-0) 

`deposit` then unconditionally uses that same nominal `amount` to size share minting and to bump the vault's internal ledger: [2](#0-1) 

and `redeem` symmetrically burns shares for `inkind` and calls `send-underlying inkind recipient`, again assuming the recipient receives exactly `inkind`: [3](#0-2) 

None of these functions read the SIP-010 token's balance before and after the transfer to confirm the delta equals the nominal amount — the same gap the external report describes for `AaveV3HoldingsOracle`'s `withdrawAmount` check, which compares a fixed expected value against a fee-adjusted actual transfer and is guaranteed to diverge whenever the underlying token takes a cut. Here the analog is even more direct: there is no check at all, so if the underlying token contract (or a future underlying swapped in via governance-approved but otherwise standard SIP-010 token) applies any transfer fee, tax, or rounding-down behavior, `var-set assets (+ current-assets amount)` on deposit will always overstate real backing, and `total-assets`/`convert-to-shares-preview`/`convert-to-assets-preview` (which are driven by `assets`) will be wrong for every subsequent depositor and redeemer.

### Impact Explanation
Because share pricing (`convert-to-shares-preview`, `convert-to-assets-preview`) and collateral/debt valuation throughout `market.clar`'s LTV and liquidation logic are all derived from the vault's `assets` variable, an inflated `assets` figure means the protocol believes it holds more redeemable underlying than it actually does. Early redeemers can drain the real (smaller) balance while later redeemers hit `ERR-INSUFFICIENT-LIQUIDITY`/`ERR-INSUFFICIENT-ASSETS`, i.e. temporary freezing of legitimate depositors' funds, and in the worst case a race to redeem before the shortfall is discovered results in some users being permanently unable to redeem the value their shares represent — protocol insolvency for that vault.

### Likelihood Explanation
This requires the deployed/governance-approved underlying SIP-010 token for a vault (or any token added in a future vault deployment) to not be a simple non-fee transfer. Today's target tokens (STX, sBTC, USDC-wrapper, USDH, stSTX, stSTXbtc) are not known fee-on-transfer assets, so likelihood under current configuration is low; however, the vault code itself provides no defense-in-depth balance check, so any onboarding of a fee-bearing or non-standard SIP-010 asset — a normal, unprivileged deployment action for new vaults — silently breaks solvency accounting with no revert to signal the problem, unlike Notional's version which at least reverts loudly on mismatch.

### Recommendation
In `receive-underlying` and `send-underlying` (all vault contracts), snapshot the underlying token balance via `ubalance` before and after the `transfer` call and use the actual observed delta — not the nominal `amount` — to mint shares and update `assets` on deposit, and to determine `assets` reduction on redeem (asserting the recipient-observed delta meets `min-out`/`inkind` expectations).

### Proof of Concept
1. Assume/deploy a vault whose underlying SIP-010 token implementation deducts a transfer fee (e.g., 1%) on `transfer`, which is possible for any token onboarded through normal, unprivileged vault configuration since the vault code performs no balance verification.
2. Call `deposit` with `amount = 1000`. `receive-underlying` calls `transfer amount account current-contract` — the vault contract's balance only increases by 990 (1000 - 1% fee), but `var-set assets (+ current-assets amount)` credits the full 1000, and shares are minted based on `convert-to-shares-preview` computed off `amount`, not the real 990 received: [4](#0-3) .
3. Repeat deposits accumulate a growing gap between the vault's recorded `assets` and its true SIP-010 token balance.
4. When redeemers call `redeem`, `available-assets`/`get-available-assets` (derived from the inflated `assets`) reports more liquidity than truly exists; the first redeemers succeed by draining the real balance, and subsequent redeemers revert with `ERR-INSUFFICIENT-LIQUIDITY` even though their zToken balance implies they are owed funds — freezing their principal.

(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (account contract-caller)
      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))

    (print {
      action: "deposit",
      caller: contract-caller,
      data: {
        depositor: account,
        recipient: recipient,
        amount: amount,
        shares-minted: inkind,
        assets: (+ current-assets amount)
      }
    })

    (ok inkind)))

(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)

  (try! (ft-burn? zft amount account))
  (try! (send-underlying inkind recipient))
  (var-set assets (- current-assets inkind))

  (print {
    action: "redeem",
    caller: contract-caller,
    data: {
      redeemer: account,
      recipient: recipient,
      shares-burned: amount,
      amount-received: inkind,
      assets: (- current-assets inkind)
    }
  })

  (ok inkind)))
