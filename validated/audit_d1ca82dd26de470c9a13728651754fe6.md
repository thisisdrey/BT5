### Title
Unbounded memory buffering in `sendSearchFilesResultChunked` allows DoS via dense-match repository content - ([File: internal/gitaly/service/repository/search_files.go])

### Summary
`sendSearchFilesResultChunked` accumulates `git grep` output into an in-memory `buf` and only flushes it to the gRPC stream when it encounters a literal `--\n` separator line or at EOF. Because `git grep` only emits `--` between *non-adjacent* context blocks, an attacker who controls repository content can craft a file where matches (and their fixed 2-line context) are dense enough that no `--` line ever appears within that file's output, forcing the entire matched region to be buffered in Gitaly's memory before any data is streamed to the client.

### Finding Description
`SearchFilesByContent` runs `git grep --before-context 2 --after-context 2 -e <Query> <ref>` and pipes its stdout into `sendSearchFilesResultChunked` [1](#0-0) . That function reads line-by-line and only calls `sendMatchInChunks(buf, stream)` (which flushes and resets `buf`) when a line is byte-equal to the delimiter `--\n`, otherwise it keeps appending to `buf` unconditionally [2](#0-1) .

`git grep`'s `--`-separated “hunk” behavior only inserts `--` between context blocks that are *not* contiguous. If an attacker pushes a repository containing a file where the search pattern (fully attacker-chosen via `Query`) matches on every line, or matches close enough together that the 2-line before/after context windows overlap for the entire file, `git grep` emits one continuous block of output for that file with no interior `--` line. Since `Query`, `Ref`, and the repository content are all attacker-controlled (via push/fork), the attacker can guarantee this dense-match condition for an arbitrarily large blob.

The existing test suite already demonstrates this exact code path: a file of 210,000 lines all matching the query is processed as a single buffered chunk with no interleaved `--` delimiter [3](#0-2)  and [4](#0-3) , confirming that the accumulation behavior is real and not accidental — it simply hasn't been stress-tested at a size sufficient to demonstrate memory exhaustion. No cap exists in `sendSearchFilesResultChunked` on `len(buf)`, and there is no per-request/response size ceiling enforced before `sendMatchInChunks` is invoked at line 104-106. `validateSearchFilesRequest` only checks for empty query/ref and a rejected leading `-` in `Ref`; it does not bound `Query` complexity or interact with blob size [5](#0-4) .

### Impact Explanation
An unprivileged user who owns/forks a repository can push a large text blob (limited only by whatever push/blob size limits exist upstream of Gitaly, which are typically large, e.g. hundreds of MB) crafted so the search query matches densely throughout, then call `SearchFilesByContent`. This forces the Gitaly node to buffer the entire matched region in process memory in a single `[]byte` before any of it is streamed out, which can be used to exhaust memory on the Gitaly node handling the RPC — a resource-exhaustion/DoS impact against the RPC handler.

### Likelihood Explanation
This is straightforward and repeatable: the attacker needs only ordinary repository push/fork capability (no special role), one crafted file, and a single RPC call. It does not require racing, timing, or any privileged state, and the vulnerable code path is already exercised (at smaller scale) in the existing test suite, confirming the mechanism works as described.

### Recommendation
Bound `buf` growth in `sendSearchFilesResultChunked`, e.g., by flushing (streaming) accumulated content once it exceeds a fixed threshold (independent of whether a `--` delimiter has been seen), or by streaming `git grep` output line-by-line directly to the gRPC stream instead of buffering an entire match block before sending.

### Proof of Concept
Using `gittest`, create a commit with a file such as:
```go
content := strings.Repeat("abcdefghi\n", N) // N large enough (e.g. tens of millions) to matter
```
where every line matches `Query: "abcdefg"`. Call `SearchFilesByContent` with that `Ref`/`Query` and observe (as in the existing `TestSearchFilesByContent` "large file" case at internal/gitaly/service/repository/search_files_test.go:157-166, but scaled up) that `sendMatchInChunks` is invoked exactly once for the whole file only after the entire `git grep` output has been read into `buf`, i.e., no partial streaming occurs and RSS grows proportionally to the full matched content size before any `MatchData` chunk is sent to the client.

func sendSearchFilesResultChunked(cmd *command.Command, stream gitalypb.RepositoryService_SearchFilesByContentServer) error {
	var buf []byte
	reader := bufio.NewReader(cmd)

	for {
		line, err := reader.ReadBytes('\n')
		if err == io.EOF {
			break
		} else if err != nil {
			return fmt.Errorf("readbytes: %w", err)
		}

		if bytes.Equal(line, contentDelimiter) {
			if err := sendMatchInChunks(buf, stream); err != nil {
				return err
			}

			buf = nil
			continue
		}

		buf = append(buf, line...)
	}

	if len(buf) > 0 {
		return sendMatchInChunks(buf, stream)
	}

	return nil
}

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
