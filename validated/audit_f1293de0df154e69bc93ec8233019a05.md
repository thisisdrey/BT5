### Title
StackerDB chunk signature omits the contract/DB identifier, enabling cross-DB signed-chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The digest that a signer authenticates when writing a StackerDB chunk (`SlotMetadata::auth_digest`) commits only to `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the specific `QualifiedContractIdentifier` (StackerDB instance) the chunk is destined for. Because the same signer address is routinely the designated owner of the same `slot_id` across multiple, distinct StackerDB contracts (e.g. successive reward-cycle `.signers-*` DBs), a chunk that was legitimately signed and broadcast for one StackerDB instance can be replayed verbatim into a different StackerDB instance where that signer also owns the same slot index, and it will pass all on-chain/off-chain validation as if freshly authored for that DB.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`sign()`/`verify()` operate solely over this digest, with no mixing-in of the target contract identifier, chain id, or any other DB-scoping value: [2](#0-1) 

Every place that authenticates an incoming chunk relies on exactly this scope-less digest. On the write path, `StackerDBTx::try_replace_chunk` checks only the per-slot signer address, staleness, and write-count — never the contract identity as part of the signature check: [3](#0-2) 

On the gossip/sync path, `PeerNetwork::validate_received_chunk` likewise verifies `slot_metadata.verify(&addr)` where `addr` is looked up per `(smart_contract_id, slot_id)`, but the signature itself never encodes which `smart_contract_id` it was made for: [4](#0-3) 

This is precisely the bug class from the external report: a signed payload that fails to uniquely bind the request/context (there, `registrar`+chain id+nonce; here, the StackerDB contract identifier) can be replayed into a different, similarly-shaped contract instance. In this codebase, signer sets are recomputed every reward cycle but frequently retain the same signer addresses; slot indices are assigned per-contract from that same signer set, so it is common for one signer's key to own identical `slot_id` values across successive `.signers-0-N` / `.signers-1-N` StackerDB instances. StackerDB chunks are, by design, broadcast openly on the p2p network (not secret), so an adversary can trivially harvest a validly-signed `(slot_id, slot_version, sig, data)` tuple from one StackerDB and replay it — unmodified — as a `StackerDBPushChunk`/`StackerDBChunkData` write against a *different* StackerDB contract where the same address occupies that slot, as long as the target replica's stored version for that slot is below the replayed version (trivially true for a newly created contract instance, which starts at version 0).

### Impact Explanation
This is an unauthenticated/unauthorized write into StackerDB state: an attacker who never possesses any signer's private key can inject a chunk into a StackerDB instance it was never signed for, and that write will be accepted as authentic by `try_replace_chunk` and further gossiped network-wide via `handle_unsolicited_StackerDBPushChunk`/the sync/broadcast machinery, since downstream code treats a signature-verified chunk as canonical for the DB it lands in. Because the signer/miner tooling that reads these StackerDB contracts trusts a verified signature as proof the message was authored for that specific DB/round, this can be used to inject stale or attacker-chosen (but honestly-signed-elsewhere) content into signer message DBs, misleading consumers into acting on data that was never actually authorized for that context. This matches the "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data" Critical bucket.

### Likelihood Explanation
Likelihood is moderate-to-high in principle since StackerDB chunks are public by design (no secrecy to break), and the only precondition is that the same signer address ends up owning the same `slot_id` in two different StackerDB contract instances — which is a natural consequence of how reward-cycle signer sets and slot assignment are derived, making cross-cycle or cross-DB slot-index collisions plausible over time rather than requiring an exotic setup.

### Recommendation
Bind the signed digest to the specific StackerDB instance by including the `QualifiedContractIdentifier` (and ideally `block.chainId`-equivalent network id) inside `SlotMetadata::auth_digest()`, mirroring the report's recommendation of committing to `address(this)`/`registrar`/chain id in addition to the existing fields. This requires threading the contract identifier into `SlotMetadata::sign`/`verify` and into `StackerDBChunkData`'s digest computation, plus a corresponding wire/format migration since it changes the signed payload.

### Proof of Concept
1. Signer `S` owns `slot_id = k` in StackerDB contract `A` (e.g. `.signers-1-5`) and signs+publishes chunk `C = (slot_id=k, slot_version=v, sig, data)` for `A`; this is broadcast in the clear over the p2p StackerDB gossip protocol.
2. In a later/adjacent reward cycle, signer `S` is again selected and, due to slot assignment, also owns `slot_id = k` in a different StackerDB contract `B`.
3. An attacker (no keys needed) captures chunk `C` from `A`'s replicas and submits it verbatim (same `slot_id`, `slot_version`, `sig`, `data`) to a node's `B` replica via `StackerDBPushChunk`/the chunk-post RPC.
4. `PeerNetwork::validate_received_chunk`/`StackerDBTx::try_replace_chunk` verify `slot_metadata.verify(&addr)` against `B`'s registered signer for slot `k` (also `S`), find the digest valid (since it never referenced `A`), see `v` is newer than `B`'s stored version (0 for a fresh contract), and accept the write — storing and then gossiping `A`'s old chunk as `B`'s legitimate content.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
