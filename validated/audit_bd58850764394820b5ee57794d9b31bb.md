### Title
`AtlasDB::insert_instantiated_attachment`/`insert_uninstantiated_attachment` never enforce `attachments_max_size` for attachments fetched from remote peers - ([File: stackslib/src/net/atlas/db.rs])

### Summary
The `attachments_max_size` bound is only checked in `AtlasDB::should_keep_attachment`, which is called exclusively on the locally-submitted-transaction path (`posttransaction.rs`). The Atlas peer-sync download path (`AttachmentsDownloader::run` / `check_attachment_instances`) calls `insert_instantiated_attachment` / `insert_uninstantiated_attachment` directly on content parsed from a remote peer's `GET /v2/attachments/<hash>` response, with no size check whatsoever.

### Finding Description
`AtlasDB::should_keep_attachment` is the only place that enforces `attachment.content.len() as u32 > self.atlas_config.attachments_max_size`: [1](#0-0) 

It is invoked only from the `POST /v2/transactions` handler before calling `insert_uninstantiated_attachment` for a locally-submitted contract-call attachment: [2](#0-1) 

However, `insert_instantiated_attachment` and `insert_uninstantiated_attachment` themselves perform no such check — they just `INSERT OR REPLACE` whatever `attachment.content` bytes they are given: [3](#0-2) [4](#0-3) 

The remote peer-download path reaches these functions without any size gate. When the `AttachmentsBatchStateMachine` reaches `Done`, every attachment collected via HTTP responses from remote peers is stored directly: [5](#0-4) 

The HTTP response body itself is decoded with no length check — `decode_atlas_get_attachment` simply hex-decodes whatever `attachment` field is in the peer's JSON body into an `Attachment`: [6](#0-5) 

`extend_with_attachments` then inserts this attacker-controlled `Attachment` into `self.attachments` with no validation of size or of matching the originally-requested `content_hash`: [7](#0-6) 

Additionally, `check_attachment_instances`'s "inboxed" branch also calls `insert_instantiated_attachment` on an already-stored uninstantiated attachment with no re-check of size: [8](#0-7) 

Root cause: the size-bound policy (`attachments_max_size`) lives in a helper (`should_keep_attachment`) that is called from only one of the two write paths into `AtlasDB`. The remote-peer-driven write path (`AttachmentsDownloader`) bypasses it entirely, so a malicious peer that is asked for an attachment can respond with content of arbitrary size and have it persisted verbatim, keyed by the hash of whatever bytes it chose to send.

### Impact Explanation
A malicious/compromised peer selected as an Atlas sync source for `GET /v2/attachments/<hash>` can return content far larger than the configured `attachments_max_size` (e.g. many times the 1 MiB minimum). This gets written to the requesting node's on-disk `AtlasDB` `attachments` table via `insert_instantiated_attachment` with no cap, and this can be repeated for every attachment instance the node is trying to resolve, and re-triggered on every retry/batch. This is a storage-bloat / unbounded-write vulnerability affecting any node syncing Atlas attachments from an adversarial peer — a write of unauthenticated/unbounded size into persistent node state that the size-limit policy was specifically meant to prevent.

### Likelihood Explanation
Preconditions: the target node must have an unresolved `AttachmentInstance` (an on-chain commitment referencing some `content_hash`) and select the attacker's peer/URL as a source for the `GET /v2/attachments/<hash>` request (attacker just needs to be an outbound sync peer with a reachable P2P/RPC data URL — no privileged role or secret needed). Attacker cost is a single crafted HTTP response per attachment request, fully remote and repeatable across retries/batches (`bump_retry_count` reintroduces batches for further rounds), and across every content hash the node is trying to resolve.

### Recommendation
Enforce `attachment.content.len() as u32 <= atlas_config.attachments_max_size` inside `AtlasDB::insert_instantiated_attachment` and `AtlasDB::insert_uninstantiated_attachment` themselves (not only in the caller-side `should_keep_attachment` helper used by the mempool/RPC path), and reject/drop oversized attachments returned by peers in `AttachmentsBatchStateContext::extend_with_attachments` before they are ever inserted. Also verify that the downloaded attachment's `hash()` matches the originally-requested `content_hash` before accepting/storing it.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (new test)
#[test]
fn test_insert_instantiated_attachment_enforces_max_size() {
    let atlas_config = AtlasConfig {
        contracts: HashSet::new(),
        attachments_max_size: 16,
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config).unwrap();

    // Simulate a malicious peer's oversized GET /v2/attachments/<hash> response,
    // as would be produced by AttachmentsBatchStateContext::extend_with_attachments
    // -> AttachmentsBatchStateMachine::Done -> AttachmentsDownloader::run.
    let oversized_attachment = Attachment::new(vec![0xAA; 10_000]); // >> attachments_max_size

    // EXPECTATION per the size-bound policy: this should be rejected.
    let res = atlas_db.insert_instantiated_attachment(&oversized_attachment);
    assert!(res.is_err(), "insert_instantiated_attachment must reject content exceeding attachments_max_size");

    // ACTUAL current behavior: this succeeds and the oversized content is persisted.
    assert!(atlas_db
        .find_attachment(&oversized_attachment.hash())
        .unwrap()
        .is_some());
}
```
This demonstrates that content whose length exceeds `attachments_max_size` is silently persisted by `insert_instantiated_attachment`, confirming the missing enforcement on the remote-peer download path.

        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,

            info!(

                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;

    }
