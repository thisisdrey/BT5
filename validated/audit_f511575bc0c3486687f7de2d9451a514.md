### Title
Peer-served attachment content is stored/matched by its own hash without verifying it against the requested `content_hash`, allowing attachment/BNS hash-binding mismatch - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever checking that `attachment.hash()` equals the `content_hash` from the `AttachmentRequest` that was actually sent to that peer. The `AttachmentsDownloader::run` `Done` branch then derives the DB key purely from `attachment.hash()` (the peer-supplied content), so a malicious peer can serve arbitrary bytes and have them accepted/stored under their own hash instead of the originally-requested, on-chain-committed hash.

### Finding Description
The requested equality that should hold is: for a request with `content_hash = H`, the response's `Attachment.content = B` must satisfy `Hash160::from_data(&B) == H`. Tracing the code:

- `get_prioritized_attachments_requests` builds an `AttachmentRequest { content_hash: H, sources, .. }` from `AttachmentsBatch` instance data derived from on-chain BNS operations [1](#0-0) .
- The request is dispatched, and the raw HTTP response is decoded in `extend_with_attachments`:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
There is no reference anywhere to `request.content_hash` in this function — the `request` variable is only used to fetch `request.get_url()` for the reliability report [2](#0-1) .
- Downstream, `AttachmentsDownloader::run`'s `Done` branch consumes `context.attachments` and computes the DB key from the attachment's own hash, not from the request that produced it:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [3](#0-2) 

Because `HashSet<Attachment>` deduplicates by the `Attachment`'s own `Hash`/`Eq` implementation (i.e., by content, not by the originally requested hash), and because `insert_instantiated_attachment` stores content keyed by `attachment.hash()` computed from the received bytes, a malicious peer that is one of the `sources` for a legitimate `AttachmentRequest` can respond with arbitrary bytes `B` unrelated to `H`. The code accepts and stores `B` under `hash(B)`, and `context.attachments_batch.resolve_attachment(&attachment.hash())` marks resolution using `hash(B)` rather than `H`, so the originally-requested attachment (keyed by `H`) is never resolved, while unrelated attacker-chosen content is now present in the AtlasDB.

No guard in this path (HTTP decode, `Requestable` traits, `BatchedRequestsState`) performs the hash comparison; `decode_atlas_get_attachment()` only parses the wire format, it does not validate content against any expected hash (based on available code, `GetAttachmentResponse`/`decode_atlas_get_attachment` definitions were only located by name; a full read of `stackslib/src/net/atlas/mod.rs` for their exact bodies was not completed in this session — this is worth confirming with a direct read, though the call site here in `download.rs` clearly does not consult `content_hash` at all).

### Impact Explanation
An unprivileged remote peer, when selected as a `source` for an `AttachmentRequest`, can serve arbitrary bytes for any requested `content_hash`. The node will store this attacker content in AtlasDB keyed by the attacker-controlled hash, and BNS attachment resolution logic that later looks up `find_attachment`/`find_all_attachment_instances` by the correct on-chain `content_hash` `H` will never find it (`is_available` stays false), while the wrong content is durably present under `hash(B)`. This is a High-severity "attachment/BNS mismatch" — the node can end up serving/storing non-canonical data that no on-chain name-update operation ever committed to, and permanently fails to resolve the correct attachment for the affected name.

### Likelihood Explanation
Preconditions: the node must be trying to sync attachments (an unresolved BNS zonefile/attachment instance) and the attacker's node/peer must be selected among the `sources` for that `AttachmentRequest` (i.e., attacker must claim to have the item in its `GetAttachmentsInvResponse` inventory, which is trivially forgeable since inventory responses are similarly not hash-verified prior to this point). This requires no secret, no privileged role, and no more than running an ordinary outbound-peer-reachable Stacks node and answering GetAttachment requests with crafted content — fully within the unprivileged remote-attacker model. It is repeatable per attachment/content_hash the attacker is asked about.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()`, compute `response.attachment.hash()` and compare it to `request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed/faulty response (bump `report.bump_failed_requests()` and/or register the peer as faulty) instead of storing the attachment. This restores the required equality `hash(received_bytes) == requested_content_hash` before any DB write in `AttachmentsDownloader::run`.

### Proof of Concept
1. In `stackslib/src/net/atlas/tests.rs` (or a new test module in `download.rs`), construct an `AttachmentRequest` with `content_hash = H` for some known on-chain-registered `AttachmentInstance`.
2. Build a `StacksHttpResponse` whose body decodes via `decode_atlas_get_attachment()` into `Attachment { content: B }` where `Hash160::from_data(&B) != H`.
3. Insert this `(request, Some(response))` pair into `BatchedRequestsResult::succeeded`, and call `AttachmentsBatchStateContext::extend_with_attachments` on it.
4. Feed the resulting context through the `Done` branch logic in `AttachmentsDownloader::run` (or replicate its loop directly) against a test `AtlasDB`.
5. Assert `atlasdb.find_attachment(&H).unwrap().is_none()` (original attachment never resolved) while `atlasdb.find_attachment(&Hash160::from_data(&B)).unwrap().is_some()` (attacker content stored instead) — demonstrating the mismatch.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
