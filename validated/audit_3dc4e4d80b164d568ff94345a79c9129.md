## Title
Bankrupt accounts are permanently `ACCOUNT_DISABLED` with no path to reclaim unrelated collateral, mirroring the Frankencoin "denied position" permanent-lock bug - (File: `programs/marginfi/src/instructions/marginfi_group/handle_bankruptcy.rs`)

### Summary
The external report describes Frankencoin's `deny()` placing a position into a permanent cooldown (`cooldown = expiration`) that blocks `withdrawCollateral` for the position owner with no way to reclaim collateral until expiry. The reachable analog in marginfi-v2 is `lending_pool_handle_bankruptcy`, which sets `ACCOUNT_DISABLED` on the entire `MarginfiAccount` after settling bad debt on a single bank balance, and this flag is never cleared anywhere in the codebase.

### Finding Description
`lending_pool_handle_bankruptcy` covers a bankrupt balance's bad debt (via insurance fund and/or socialized loss) and then unconditionally disables the whole account: [1](#0-0) 

This flag gates every user-authority instruction across the protocol — standard deposit/withdraw/borrow/repay, and all integration flows (Kamino, Drift, Juplend, Solend) — via the same `!acc.get_flag(ACCOUNT_DISABLED)` constraint pattern, e.g.: [2](#0-1) 

The account-lifecycle documentation confirms this is meant to be terminal ("typically after all positions have been zeroed out"): [3](#0-2) 

A grep across the entire Rust program surface found no instruction that clears `ACCOUNT_DISABLED` once set — `set_flag(ACCOUNT_DISABLED, ...)` is only ever invoked with `true`, and every other reference to the flag is a read-only gate blocking deposit, withdraw, borrow, repay, transfer, flashloan, order, and liquidation flows. Test coverage confirms withdraw/borrow/repay all revert with `AccountDisabled` once a single bank on the account has been bankrupted: [4](#0-3) 

Bankruptcy handling operates on a single `(marginfi_account, bank)` pair at a time — it looks up and repays only the balance matching `bank_loader.key()`: [5](#0-4) 

I was unable to fully verify, within the available index, the exact precondition enforced by `check_account_bankrupt` (i.e., whether it requires that *all* balances on the account be zero/liability-only before bankruptcy can be invoked, or only that the specific target balance is bad debt while other unrelated healthy balances in other banks may still exist). If the latter is possible, then — exactly as in the Frankencoin `deny()` case — a user with healthy collateral in an unrelated bank could have that collateral permanently frozen the moment any other position on the same account is bankrupted, with no owner-facing recovery instruction. This should be confirmed against `check_account_bankrupt` in `programs/marginfi/src/state/marginfi_account.rs` before treating this as a confirmed finding.

### Impact Explanation
If `check_account_bankrupt` does not require full-account liquidation to zero before bankruptcy processing, this constitutes a permanent freeze of user funds (unrelated healthy collateral) with no recovery path — matching the "permanent lock/freeze" acceptance criterion. This is a structural gap: unlike Frankencoin's fix (return collateral at deny-time), marginfi-v2 has no analogous "return remaining collateral" step in `handle_bankruptcy`, nor any admin/permissionless unlock instruction for `ACCOUNT_DISABLED`.

### Likelihood Explanation
Bankruptcy handling (`HandleBankruptcy`) is a normal, expected part of protocol operation — it is explicitly permissionless on banks with `PERMISSIONLESS_BAD_DEBT_SETTLEMENT_FLAG`, and admin-triggered otherwise. Any account that ends up with unrecoverable bad debt on one bank (a routine occurrence in undercollateralized positions) will trigger this path. If unrelated collateral can coexist on the account at the time of bankruptcy, the likelihood of hitting this state is moderate-to-high in normal operation, not a contrived edge case.

### Recommendation
Before `handle_bankruptcy` sets `ACCOUNT_DISABLED`, confirm (via `check_account_bankrupt`) whether other active, healthy balances can exist on the same account. If so, either (a) require full-account closure before allowing `ACCOUNT_DISABLED` to be set, or (b) add an owner/admin-permissioned instruction that lets the account authority withdraw any remaining non-bad-debt collateral after bankruptcy, analogous to Frankencoin's fix of returning collateral inside `deny()`.

### Proof of Concept
Conceptual reproduction (pending confirmation of `check_account_bankrupt`'s exact precondition):
1. User deposits healthy collateral in Bank A and separately borrows against Bank B, ending up with bad debt only on Bank B.
2. Admin or permissionless caller invokes `HandleBankruptcy` on Bank B, which repays/settles the Bank B bad debt and then calls `marginfi_account.set_flag(ACCOUNT_DISABLED, true)` [6](#0-5) .
3. User attempts `lending_account_withdraw` on their healthy Bank A collateral; the `!acc.get_flag(ACCOUNT_DISABLED)` constraint rejects the transaction with `MarginfiError::AccountDisabled` [7](#0-6) , and no instruction exists to ever clear the flag, permanently locking the Bank A collateral.

**Caveat:** This report could not verify from indexed content whether step 1 (coexistence of unrelated healthy collateral with a bankrupt balance) is actually reachable given `check_account_bankrupt`'s precise gating logic. A Devin session with full repository access should inspect `check_account_bankrupt` in `programs/marginfi/src/state/marginfi_account.rs` and `SECURITY.md` to confirm this is not already a documented/accepted design tradeoff before treating this as a confirmed vulnerability.
