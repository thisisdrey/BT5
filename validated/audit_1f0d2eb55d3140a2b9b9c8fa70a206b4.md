### Title
`PostUploadPackWithSidechannel` lacks the negotiation-phase timeout that mitigates use-after-check races applied to `SSHUploadPackWithSidechannel` - ([File: internal/gitaly/service/smarthttp/upload_pack.go])

### Summary
Gitaly's own codebase explicitly documents and mitigates a "use-after-check" (time-of-check-to-time-of-use) vulnerability class that is structurally analogous to the reported `ZNSSubRegistrar` bug: a value/permission is validated once ("access check"/"price check"), but the actual privileged action (git command execution / token transfer) happens later, and an attacker who controls timing can exploit the gap between check and use. In Gitaly this is implemented for `git-upload-pack`/`git-upload-archive` over SSH via `pktline.ReadMonitor`, but the equivalent SmartHTTP path, `PostUploadPackWithSidechannel` → `runUploadPack`, does not apply this same bound.

### Finding Description
For SSH-based fetches, `runUploadCommand` in `internal/gitaly/service/ssh/upload_command.go` wraps the client's stdin in a `pktline.ReadMonitor` and starts a timer that cancels the git process if the negotiation-terminating packet (`done`) isn't observed within a bounded window: [1](#0-0) [2](#0-1) 

The `ReadMonitor` type itself documents exactly the bug class being mitigated: [3](#0-2) 

This is used by `sshUploadPack` for `SSHUploadPackWithSidechannel`: [4](#0-3) 

The comment explains the root cause precisely: access checks (which in Gitaly's model correspond to authorization at RPC start, analogous to `getPrice()`/approval time in the report) happen at the beginning of the call, but the git negotiation phase — during which the client fully controls stdin timing — can be stalled indefinitely, allowing the actual data transfer ("use") to occur long after the check was valid, potentially after permissions or repository state that back the earlier check have changed: [5](#0-4) 

However, the SmartHTTP equivalent, `runUploadPack` (invoked by `PostUploadPackWithSidechannel`), performs `validateUploadPackRequest` once and then spawns `upload-pack` directly, waiting on `cmd.Wait()` with no `ReadMonitor` or any negotiation-phase timeout at all: [6](#0-5) 

Because an ordinary client fully controls the pace at which it sends `have`/`done` pktlines over this stdin stream (identical protocol semantics to the SSH transport), it can hold the negotiation open indefinitely without the bounded-timeout mitigation applied on the SSH path, reproducing the same use-after-check window that `ReadMonitor` was specifically built to close.

### Impact Explanation
This mirrors the reported bug class: a check performed at one point in time (repository/permission validation) is relied upon for an action (`upload-pack` data transfer) that can be deferred arbitrarily by the calling party, because there is no bound on the gap. Just as a malicious domain owner could swap the pricer contract after approval but before the price is charged, an unprivileged client could keep an already-authorized `PostUploadPackWithSidechannel` negotiation open well past the point at which their authorization to read the repository (e.g., due to a subsequent permission revocation) would normally have expired, and still complete the fetch using stale authorization.

### Likelihood Explanation
The attack requires only an ordinary user's ability to control pacing of pktline input in a standard HTTP-based git fetch/clone request — no privileged access, leaked token, or MITM position is needed. This is directly reachable from any authenticated Git HTTP client and is comparable in triggerability to the already-mitigated SSH path.

### Recommendation
Apply the same `pktline.ReadMonitor`-based negotiation-phase timeout used in `internal/gitaly/service/ssh/upload_command.go` to the SmartHTTP `runUploadPack` path in `internal/gitaly/service/smarthttp/upload_pack.go`, so that both transports for `upload-pack` share a consistent bound on the time between access check and completion of negotiation.

### Proof of Concept
1. As an ordinary authenticated user, initiate `PostUploadPackWithSidechannel` (an HTTP `git fetch`/`clone`) against a repository the user is currently authorized to read.
2. After the initial access check passes and `git-upload-pack --stateless-rpc` is spawned, deliberately withhold or trickle the pktline negotiation input (`want`/`have` lines) without ever sending the terminating `done`/flush packet, similar to the "short write" scenarios exercised in `upload_pack_test.go` for the SSH transport.
3. Because `runUploadPack` in `internal/gitaly/service/smarthttp/upload_pack.go` performs no `pktline.ReadMonitor`-style timeout on the negotiation phase (unlike `runUploadCommand` for SSH), the process remains alive and the RPC's original access check remains "in force" indefinitely, regardless of how long it has been since that check occurred — reproducing the exact use-after-check condition described in `internal/git/pktline/read_monitor.go`.

// ReadMonitor monitors an io.Reader, waiting for a specified packet. If the
// packet doesn't come within a timeout, a cancel function is called. This can
// be used to place a timeout on the *negotiation* phase of some git commands,
// aborting them if it is exceeded.
//
// This timeout prevents a class of "use-after-check" security issue when the
// access check for a git command is run before the command itself. The user
// has control of stdin for the git command, and if they can delay input for
// an arbitrarily long time, they can gain access days or weeks after the
// access check has completed.
//
// This approach is better than placing a timeout on the overall git operation
// because there is a conflict between mitigating the use-after-check with a
// short timeout, and allowing long-lived git operations to complete. The
// negotiation phase is a small proportion of the time taken for a large git
// fetch, for instance, so tighter limits can be placed on it, leading to a
// better mitigation.

func (s *server) validateUploadPackRequest(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest) (string, []gitcmd.ConfigPair, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return "", nil, err
	}
	repoPath, err := s.locator.GetRepoPath(ctx, repository)
	if err != nil {
		return "", nil, err
	}

	gitcmd.WarnIfTooManyBitmaps(ctx, s.logger, s.locator, repository.GetStorageName(), repoPath)

	config, err := gitcmd.ConvertConfigOptions(req.GetGitConfigOptions())
	if err != nil {
		return "", nil, err
	}

	return repoPath, config, nil
}

func (s *server) runUploadPack(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest, repoPath string, gitConfig []gitcmd.ConfigPair, stdin io.Reader, stdout io.Writer) (stats *stats.PackfileNegotiation, _ error) {
	h := sha1.New()

	stdin = io.TeeReader(stdin, h)
	stdin, collector := s.runStatsCollector(ctx, stdin)
	defer func() {
		if stats == nil {
			stats = collector.finish()
		}
	}()

	repo := s.localRepoFactory.Build(req.GetRepository())
	if s.bundleURIManager != nil {
		// Bundle generation is an optimization that is transparent to users.
		// If it fails, we log the error but continue with the regular upload-pack
		// operation without the bundle optimization.
		// If successful, a goroutine is spawned to generate the bundle, in which case
		// the bundle generation becomes independent of the RPC request.
		if err := s.bundleURIManager.GenerateWithStrategy(ctx, repo); err != nil {
			s.logger.WithError(err).Error("failed generating bundle")
		}
		gitConfig = append(gitConfig, s.bundleURIManager.UploadPackGitConfig(ctx, req.GetRepository())...)
	} else {
		gitConfig = append(gitConfig, bundleuri.CapabilitiesGitConfig(ctx, false)...)
	}

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return nil, fmt.Errorf("detecting object hash: %w", err)
	}

	commandOpts := []gitcmd.CmdOpt{
		gitcmd.WithStdin(stdin),
		gitcmd.WithSetupStdout(),
		gitcmd.WithGitProtocol(s.logger, req),
		gitcmd.WithConfig(gitConfig...),
		gitcmd.WithPackObjectsHookEnv(objectHash, req.GetRepository(), "http"),
	}

	if s.cfg.Hooks.PackObjectsHookMaxProc > 0 {
		commandOpts = append(commandOpts, gitcmd.WithEnv("GOMAXPROCS="+strconv.Itoa(int(s.cfg.Hooks.PackObjectsHookMaxProc))))
	}

	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name:  "upload-pack",
		Flags: []gitcmd.Option{gitcmd.Flag{Name: "--stateless-rpc"}},
		Args:  []string{repoPath},
	}, commandOpts...)
	if err != nil {
		return nil, structerr.NewFailedPrecondition("spawning upload-pack: %w", err)
	}

	// Use a custom buffer size to minimize the number of system calls.
	respBytes, err := io.CopyBuffer(stdout, cmd, make([]byte, 64*1024))
	if err != nil {
		return nil, structerr.NewFailedPrecondition("copying stdout from upload-pack: %w", err)
	}

	if err := cmd.Wait(); err != nil {
		stats = collector.finish()
		if _, ok := command.ExitStatus(err); ok && stats.Deepen != "" {
			// We have seen a 'deepen' message in the request. It is expected that
			// git-upload-pack has a non-zero exit status: don't treat this as an
			// error.
			s.recordServedBytes(stats, respBytes)
			return stats, nil
		}

		return nil, structerr.NewFailedPrecondition("waiting for upload-pack: %w", err)
	}
