Audit Report

## Title
Missing `AssetClaimer`/error-handling on final `DepositAsset` in Snowbridge inbound-queue v1 `SendToken`/`SendNativeToken` can permanently trap bridged funds - ([File: bridges/snowbridge/primitives/inbound-queue/src/v1.rs])

## Summary
`convert_send_token` and `convert_send_native_token` in the v1 inbound-queue message converter build XCM programs that move Ethereum-bridged assets into holding and end with a bare `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }`, with no `SetHints([AssetClaimer])` and, for the AssetHub-only (`None`) branch and the destination-parachain remote leg, no error handler/appendix protecting that final deposit. [1](#0-0) [2](#0-1) [3](#0-2)  If that final deposit fails (e.g. beneficiary account doesn't exist and asset isn't "sufficient", fee mis-estimation, or weight exhaustion on the remote leg), the generic XCM executor trap fires against whatever origin is active at that point, which for these programs is derived from `UniversalOrigin(GlobalConsensus(network))`/`DescendOrigin` or a reserve-transfer sovereign — not a location any ordinary signed account can reconstruct via `pallet_xcm::claim_assets`. [4](#0-3) 

## Finding Description
I confirmed the code exactly matches the claim's description: `convert_send_token`'s `None` branch (direct AssetHub destination) issues only `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` with no appendix at all [1](#0-0) , and the `Some(dest_para_id)` branch's `SetAppendix` only protects the local AssetHub leg (returning unspent assets to the bridge sovereign) while the remote program executed on the destination parachain ends in a bare `DepositAsset` with no protection of its own [5](#0-4) . `convert_send_native_token` follows the identical unprotected pattern [3](#0-2) . The `RegisterToken` path (`convert_register_token`), by contrast, does have a `SetAppendix` that protects leftover fees [6](#0-5) , showing the pattern is known but inconsistently applied. The `xcm-executor`'s trap-on-non-empty-holding logic confirms that any assets left in holding when the program ends up in an error state (or otherwise doesn't fully drain holding) get trapped against `asset_claimer.or(context.origin).unwrap_or(original_origin)` [4](#0-3) , and no `SetHints([AssetClaimer(...)])` is set anywhere in v1's `SendToken`/`SendNativeToken` programs. In contrast, v2's `converter.rs` explicitly threads a claimer location (message-supplied or a bridge-owner sovereign fallback anchored to `LocalNetwork`) through every converted message specifically to make later `claim_assets` calls possible [7](#0-6) , confirming this protective mechanism exists and is applied elsewhere but was not back-ported to v1.

## Impact Explanation
This matches the "permanent user-fund lock" impact category: assets already irreversibly withdrawn/burned on the Ethereum side can become permanently stuck in Polkadot XCM holding-register traps that ordinary signed accounts cannot reclaim through `pallet_xcm::claim_assets`, whose `ensure_origin` check requires a signed-account-derived origin that cannot reproduce a `UniversalOrigin`/bridge-sovereign-derived trap origin [8](#0-7) . This affects arbitrary bridge users sending tokens from Ethereum to AssetHub or a sibling parachain, not just privileged actors.

## Likelihood Explanation
No malicious actor is required. Ordinary conditions — sending to a not-yet-existing beneficiary paired with a non-"sufficient" asset, under-provisioned fees, or the remote parachain leg running short of weight during `DepositReserveAsset` — can trigger the failed final deposit. The message's destination, fee, and amount fields are attacker/user-controlled from the Ethereum side, making this reliably reproducible.

## Recommendation
Back-port the v2 pattern into v1: add `SetHints([AssetClaimer { location }])` (or a `SetAppendix`/error handler covering the final deposit) to both `convert_send_token` branches (including the remote leg embedded in `DepositReserveAsset`) and to `convert_send_native_token`, anchored on a location a real signed account can present to `claim_assets` (e.g. a bridge-owner sovereign account pinned with `network: Some(LocalNetwork::get())`, matching the v2 fix).

## Proof of Concept
1. Submit a `SendToken` message via the inbound queue with `Destination::AccountId32 { id }` where `id` has no existing account on AssetHub and the transferred asset is a non-"sufficient" `ForeignAssets` instance, or with fee amounts too low to satisfy ED after `BuyExecution`.
2. `convert_send_token`'s `None` branch produces `ReserveAssetDeposited` into holding followed only by `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` [1](#0-0) .
3. On AssetHub, the final `DepositAsset` fails (e.g. `FailedToTransactAsset`), leaving holding non-empty when the program ends.
4. The executor's `post_process` trap fires against the `UniversalOrigin`/context origin present at that point [4](#0-3) , which no signed account can reconstruct via `pallet_xcm::claim_assets`'s `ExecuteXcmOrigin::ensure_origin` check [8](#0-7) , permanently locking the bridged funds.
