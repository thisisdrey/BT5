### Title
Rewards emitted while a tracked `DepositToken`/`DebtToken` has zero total supply are permanently skipped and locked in `RewardsDistributor` - (`contracts/RewardsDistributor.sol`)

### Summary
`RewardsDistributor._calculateTokenIndex` distributes `tokenSpeeds[token_] * elapsed` rewards pro-rata over `token_.totalSupply()`. When `totalSupply() == 0` at index-update time, the reward ratio is computed as 0 but `timestamp` is still advanced to `block.timestamp`, so all rewards that accrued during the zero-supply window are silently discarded. Since the reward token balance is only ever released via index-based claims, those emissions remain locked in the distributor contract forever — the direct analog of the Babel `TroveManager` "emitted but never distributed" bug.

### Finding Description
The reward index is updated lazily by `_updateTokenIndex`, called from `updateBeforeMintOrBurn`, `updateBeforeTransfer`, and `claimRewards` (`contracts/RewardsDistributor.sol:175-192`, `150-168`). The index math is:

```solidity
// contracts/RewardsDistributor.sol
uint256 _totalSupply = token_.totalSupply();
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
``` [1](#0-0) 

When `_totalSupply == 0`, `_ratio` is 0 so `_newIndex` stays at the old index, but `_newTimestamp` is still set to `block.timestamp`. The next update therefore measures `_deltaTimestamps` from the end of the zero-supply window — the `speed * (t_empty)` emissions are never added to the index and no account can ever claim them. There is no accumulator for undistributed emissions and no sweep path tied to accrual (`TokenHolder` sweeping is governor-only and would rescue the tokens, but they remain unredeemable through the intended claim flow; `claimRewards` only pays out amounts recorded via the index). The same mechanism makes per-user truncation dust (`balance.wadMul(_deltaIndex)` at `contracts/RewardsDistributor.sol:230`) permanently undistributable, though that is dust-scale.

Triggering conditions are reachable by ordinary users with no privileges:

- For a `DepositToken`: all holders withdraw (via `withdraw`/`withdrawFrom`/`flashWithdraw` → `_burn` → `totalSupply == 0`) while `tokenSpeeds[token_] > 0`. If no `updateBefore*` call lands exactly at the empty instant, the whole gap is skipped; even if one does, emissions between the last burn and the next mint are lost because the next `_mint` calls `updateBeforeMintOrBurn` and advances the timestamp with `_ratio = 0` (`contracts/DepositToken.sol:444-489`, `536-554`).
- For a `DebtToken`: all debt is repaid (`repay`/`repayAll` → `_burn` drives `totalSupply_` to 0; `totalSupply()` is `totalSupply_ + accrued interest`, which is 0 once `totalSupply_` is 0), then the next borrower calls `issue`, whose `_mint` runs `updateRewardsBeforeMintOrBurn` after `accrueInterest` and skips the empty interval (`contracts/DebtToken.sol:235-271`, `466-495`, `500-503`, `525-543`, `572-601`).
- Bootstrap case: `updateTokenSpeed` sets `INITIAL_INDEX` and `timestamp = block.timestamp` (`contracts/RewardsDistributor.sol:296-299`) while supply is still 0; all emissions until the first deposit are skipped the same way.

### Impact Explanation
The invariant "rewards emitted at `speed` are eventually claimable by token holders" is broken: emitted rewards for zero-supply intervals are neither distributed nor recoverable through `claimRewards`, which is the only user-facing payout path (`_transferRewardIfEnoughTokens` only transfers amounts accrued through the index, `contracts/RewardsDistributor.sol:248-256`). This is permanent freezing of unclaimed yield belonging to the pool of depositors/debtors — matching the external report's class of "emissions allocated but effectively lost." The amount lost equals `speed * duration_of_empty_supply`, which can be arbitrarily large if a market is emptied for an extended period while its speed remains nonzero.

### Likelihood Explanation
Requires a tracked token's supply to hit zero while its reward speed is nonzero — plausible for smaller/newer collateral markets or after deleveraging events, and guaranteed to occur at least once at market bootstrap if speed is set before the first deposit. It is not attacker-profitable (no one can steal the stranded rewards), but it is a deterministic value loss triggered by ordinary usage. The governor could rescue funds via `TokenHolder.sweep`, but the accounting intent — distributing them to users — is unachievable once the timestamp has advanced.

### Recommendation
Do not advance `tokenStates[token_].timestamp` when `totalSupply == 0` (or `speed == 0` already handled) so emissions resume accumulating once supply returns; alternatively accrue the skipped amount into a global "undistributed" bucket credited to the next minter or redistributed on the next nonzero-supply update. Concretely, in `_calculateTokenIndex`, return early without updating `_newTimestamp` when `_totalSupply == 0` and `_speed > 0`, and apply the same treatment in `_updateTokenIndex`.

### Proof of Concept
Hardhat-style fork test outline (repo uses Hardhat; see `test/RewardDistributor.test.ts` for the mocking pattern):

```ts
// setup: pool with depositToken (msdTOKEN1), rewardDistributor, reward token VSP
// governor sets speed: rewardDistributor.updateTokenSpeed(msdTOKEN1, parseEther('1'))
// -> tokenStates[msdTOKEN1] = {index: INITIAL_INDEX, timestamp: t0} while supply == 0

// 1) warp 1000s with zero supply; alice deposits (mints).
//    _mint -> updateBeforeMintOrBurn -> _updateTokenIndex:
//    totalSupply == 0 => _ratio = 0, but timestamp becomes t0+1000.
//    => 1000 VSP emitted and permanently skipped.

// 2) alice holds all supply; warp another 1000s; bob deposits equal amount.
//    claimable(alice) ≈ 1000 VSP, claimable(bob) = 0.

// 3) warp 1000s; both claim: total paid ≈ 2000 VSP.
//    invariant check: paid + dust << speed * totalElapsed (3000 VSP).
//    ~1000 VSP is stranded in RewardsDistributor with no claim path.

// Variant for DebtToken: alice issues debt, then repayAll -> totalSupply()==0,
// warp, bob issues -> next updateBeforeMintOrBurn skips the empty window.
```

Uncertainty note: I verified the index math and the mint/burn hooks call `updateBeforeMintOrBurn`/`updateBeforeTransfer` before balance changes, but I did not confirm on a live fork that no other component (e.g., a keeper calling `updateBeforeMintOrBurn` permissionlessly — it is callable by anyone, `contracts/RewardsDistributor.sol:175-180`) advances the timestamp mid-gap; such a call would shrink but not eliminate the skipped window. The finding stands regardless: any elapsed zero-supply time between updates is lost.
