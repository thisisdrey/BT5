## Analog Vulnerability Found

### Title
Unchecked-by-default overflow in exchange-pool ratio calculation causes execute() to diverge from validate()-computed amount - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` (and the sibling `ExchangeWithdrawActuator`/`ExchangeTransactionActuator`) validate the injected/withdrawn "another token" amount in `doValidate()` using `BigInteger` arithmetic, which cannot overflow, but then **recompute the same value in `execute()` using `long` arithmetic via `multiplyExact`/`floorDiv`** [1](#0-0)  This mirrors the reported `Liquidation.sol` bug class: a ratio/multiplier is computed from user- and pool-controlled inputs without a hardened overflow check, and the checked/unchecked paths can disagree.

### Finding Description
In `doValidate()`, the amount of the counter-token is computed safely: [2](#0-1) 

But `execute()` independently re-derives the same value using `multiplyExact`/`floorDiv` helper methods that are only "hardened" (checked, via `StrictMathWrapper`) when `allowHardenExchangeCalculation()` is enabled on-chain; the sibling method `addExact`/`subtractExact` in `AbstractExchangeActuator` fall back to plain, unchecked `x + y` / `x - y` when hardening is disabled [3](#0-2) . The same de-hardened pattern exists for `multiplyExact`/`floorDiv` (defined in `AbstractActuator`, following the identical hardened/non-hardened toggle idiom used throughout the exchange actuators). `firstTokenBalance`/`secondTokenBalance` can each approach the configured `exchangeBalanceLimit` (on the order of 1e18) and `tokenQuant` is only bounded by the caller's own asset/TRX balance, so `secondTokenBalance * tokenQuant` can exceed `Long.MAX_VALUE` (~9.2e18) well before the pool balance limit is hit.

The fact that the codebase introduced a fully hardened, BigDecimal/BigInteger-based `SafeExchangeProcessor` [4](#0-3)  and a hardened `multiplyAndDivide` helper with BigInteger fallback for the market module [5](#0-4)  confirms that maintainers are aware overflow is reachable in this exact class of pool-ratio computation, but the fix is gated behind an `allowHarden...` chain parameter that is off by default (tests explicitly toggle it on) [6](#0-5) .

### Impact Explanation
If hardening is disabled (the default until a committee proposal enables it), `execute()`'s unchecked `long` multiplication can silently wrap/overflow to a value different from the correctly-validated `BigInteger` result. Because `execute()` uses its own recomputed value—not the one checked in `doValidate()`—to set the new pool balances and debit/credit the caller's assets [7](#0-6) , this can produce an incorrect `anotherTokenQuant`, resulting in miscredited/misdebited token balances in the exchange pool — an unbacked balance or fund-manipulation condition reachable via a single signed `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction from the exchange's creator account.

### Likelihood Explanation
Reachable by any account that is the creator of an Exchange pool (a permission any user can obtain by issuing an exchange), requiring only a single crafted `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction with pool balances and quant chosen to exceed `Long.MAX_VALUE` in the intermediate multiplication — a value attacker fully controls by first inflating pool balances toward the `exchangeBalanceLimit` and then injecting with a large but individually-valid `tokenQuant`. The likelihood is tempered by the practical need for pool balances to be large (near `exchangeBalanceLimit`, ~1e18), but this is attacker-achievable through legitimate prior injections.

### Recommendation
Make the `execute()` recomputation always use the same overflow-safe path as `doValidate()` (BigInteger, or the hardened `StrictMathWrapper`/`SafeExchangeProcessor` path) regardless of the `allowHardenExchangeCalculation()` flag, or better, have `execute()` reuse the exact value computed and validated in `doValidate()` instead of recomputing it independently, eliminating any possibility of divergence between the two computations.

### Proof of Concept
1. Attacker creates an Exchange pool and injects liquidity over several transactions until `firstTokenBalance`/`secondTokenBalance` approach `exchangeBalanceLimit` (~1e18 by default).
2. Attacker (as pool creator) submits an `ExchangeInjectContract` with a `tokenQuant` chosen (bounded only by their own asset/TRX balance) such that `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) exceeds `Long.MAX_VALUE`.
3. With `allowHardenExchangeCalculation` at its default (disabled) value, `doValidate()` correctly computes `anotherTokenQuant` via `BigInteger` and passes validation for a value under `balanceLimit`, while `execute()`'s unchecked `long` multiplication overflows and yields a different `anotherTokenQuant`, causing the pool/account balances set in `execute()` to diverge from the amount that was actually validated [8](#0-7) .

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
