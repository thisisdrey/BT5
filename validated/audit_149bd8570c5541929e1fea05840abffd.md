### Title
Heap buffer over-read in ijar's ZIP central-directory extra-field parser when processing an unpinned/attacker-served archive - (File: third_party/ijar/zip.cc)

### Summary

### Finding Description
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the ZIP64 extra-field records of a Central Directory Header entirely from attacker-controlled length fields, with no bounds validation against the mapped input file: [1](#0-0) [2](#0-1) 

The loop `while (extra_p != p)` walks the extra-field records by reading a 2-byte `header_id`, a 2-byte `data_size`, and then advancing `extra_p += data_size` — all three values are taken verbatim from the archive with no check that `extra_p + 4 + data_size` stays within `p` (the end of the declared extra-field region) or within the mapped file at all. When `header_id == ZIP64_EXTRA_FIELD_TAG`, the code unconditionally calls `get_u8le(extra)` up to three times (24 bytes) regardless of the record's declared `data_size`. A record that declares `data_size = 0` (or any value smaller than 24) but is tagged as the Zip64 extra field causes `get_u8le` to read up to 24 bytes past the legitimate end of that extra field — and if the whole extra-field length is itself crafted to end near the boundary of the mmap'd archive, this walks off the end of the mapped region into adjacent heap/mapped memory, i.e., a heap-based buffer over-read. Additionally, a corrupted `data_size` can push `extra_p` past `p`, so the loop condition `extra_p != p` never becomes false through normal alignment and continues reading further out-of-bounds `header_id`/`data_size` pairs.

This is structurally analogous to CVE-2019-7635 (SDL `Blit1to4`): both bugs read a fixed-size record (pixel data / Zip64 attribute slots) using an offset/format value taken from untrusted input without validating that the underlying buffer actually contains that many bytes, producing a heap over-read that can crash the process or leak adjacent memory into program state (in ijar's case, into `*uncompressed_size`/`*compressed_size`/`*offset`, which subsequently drive further pointer arithmetic and `memcpy` in `ProcessLocalFileEntry`/`UncompressFile`).

Contrast this with the sibling implementation in `src/tools/singlejar/zip_headers.h`, whose `ExtraField::find` explicitly checks `byte_ptr(start) + extra_field->size() > byte_ptr(end)` before dereferencing — that code path is safe. The vulnerable code is the separate, older `third_party/ijar` ZIP parser, which lacks this check entirely in `ProcessCentralDirEntry`.

### Impact Explanation
`ijar` (and its central-directory parser) is invoked by Bazel's Java toolchain to build interface jars from jars used in the build graph, including third-party `.jar` artifacts fetched via `http_jar`/`http_archive`. Since the `sha256`/`integrity` attribute on these repository rules is optional ("It is optional to make development easier but should be set before shipping" — see the `http_archive`/`http_jar` docs), an attacker controlling the download URL, a mirror, or the CI-visible dependency (any repo rule invocation without a pinned checksum) can serve an arbitrary crafted `.jar`/`.zip`. When Bazel processes that jar with `ijar`, the malformed Zip64 extra field triggers the out-of-bounds read, causing a crash (denial of the build) or, depending on heap layout, disclosure of adjacent process memory into fields (`uncompressed_size`, `compressed_size`, `offset`) that influence subsequent pointer arithmetic and memory copies in the same parser — a classic heap-buffer-over-read with potential for further memory-safety corruption in a native (non-sandboxed) build tool.

### Likelihood Explanation
Likelihood is limited by the precondition that no `sha256`/`integrity` is pinned for the archive (a very common real-world configuration, especially in early development or with `http_jar`); if a checksum is pinned, the attacker would need to produce a colliding SHA-256 file, which is infeasible. Given an unpinned checksum, the trigger only requires publishing a `.jar`/`.zip` with a malformed ZIP64 extra-field record — a low-effort, purely file-format-level attack requiring no code execution or credential access, matching the "unprivileged content publisher" threat model.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry` (and any other raw pointer-walk of extra fields in `third_party/ijar/zip.cc`) mirroring `ExtraField::find` in `zip_headers.h`: validate that `extra_p + 4 <= p` before reading `header_id`/`data_size`, that `data_size` does not cause `extra_p` to exceed `p`, and that at least 8/16/24 bytes (as required) remain before calling `get_u8le` for Zip64 attributes. Reject/`error()` out on malformed records instead of reading past the declared region.

### Proof of Concept
A reproducible JUnit/native test can be added under `src/test/cpp` or `third_party/ijar` test suite along the lines of the existing `zip_headers_test.cc` `Zip64ExtraFieldTest`, constructing a minimal in-memory ZIP whose Central Directory Header contains:
- `uncompressed_file_size32 = 0xFFFFFFFF`, `compressed_file_size32 = 0xFFFFFFFF` (forcing 64-bit lookup)
- an extra-field region of exactly 4 bytes: `tag = 0x0001` (`ZIP64_EXTRA_FIELD_TAG`), `data_size = 0`
- placed at the very end of the mmap'd buffer (e.g., a 1-page allocation sized to end right after the 4-byte extra field)

Then call `ZipExtractor::Create()`/`ProcessNext()` on this crafted archive and observe (under ASan) a heap-buffer-overflow/over-read report from the `get_u8le(extra)` calls in `ProcessCentralDirEntry`, confirming the read past the declared/mapped extent. [3](#0-2) [4](#0-3)

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
