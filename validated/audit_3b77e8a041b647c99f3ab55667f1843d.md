### Title
Unauthenticated nonce-account griefing evicts a victim's queued durable-nonce transaction via the banking-stage nonce-dedup path - ([File: core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs])

### Summary
The banking-stage receive path implements a "nonce dedup" mechanism (tracked via `num_dropped_on_nonce_dedup` / `num_evicted_on_nonce_dedup` counters in `ReceivingStats`) that keeps only the highest-priority transaction touching a given durable nonce account in the ingress buffer, evicting any lower-priority transaction that references the same nonce address [1](#0-0) . Because the dedup key is the nonce account address itself rather than any relationship (authority, fee payer) between the two transactions, an unprivileged attacker who merely knows a victim's public nonce account pubkey can craft a transaction naming that same account with an inflated priority fee to evict the victim's legitimately queued transaction from the buffer.

### Finding Description
`ReceivingStats` explicitly tracks drops and evictions attributable to nonce deduplication (`num_dropped_on_nonce_dedup`, `num_evicted_on_nonce_dedup`) [1](#0-0) , and these are accumulated across receive batches [2](#0-1) . This confirms a real code path where, on receiving a new durable-nonce transaction, the container is queried for any already-buffered transaction keyed on the same nonce account, and the lower-priority one is removed from the container (consistent with the question's described call sequence: locate the existing entry for `nonce_address`, compare priority, and evict the loser via the container's removal API).

The account referenced by an `AdvanceNonceAccount` instruction is public on-chain data (any client can read a nonce account's pubkey from the chain or from a shared victim address). The dedup logic identifies "transactions that use this nonce account" purely from the message's declared nonce-account key; nothing in this pre-execution stage validates that the attacker actually holds authority over that nonce account. Signature verification only checks that whichever pubkey the *attacker's own transaction* declares as a signer (e.g., an authority slot they control) has a valid signature — it does not cross-check that this authority actually matches the real on-chain nonce authority of the account named in the instruction. That mismatch is only caught later during bank execution (`system_processor.rs`), by which point the victim's legitimate transaction has already been silently evicted from the ingress buffer.

Thus:
1. Victim submits legitimate nonce transaction `T_v` referencing nonce account `N` with authority `A`.
2. Attacker, knowing only `N`'s public address, crafts transaction `T_a` also referencing `N` in an `AdvanceNonceAccount` instruction, with an artificially high priority fee, but with any signer of the attacker's own choosing sitting in the "authority" slot (self-signed, passes sigverify).
3. On receive, the nonce-dedup logic in `receive_and_buffer.rs` finds `T_v` already queued for nonce address `N`, compares priority, and evicts `T_v` from the container because `T_a` has higher priority.
4. `T_a` is guaranteed to fail on execution (nonce authority mismatch) and is never included in a valid block, but `T_v` has already been irrecoverably dropped from the scheduler's ingress buffer before that failure is observed.

### Impact Explanation
This falls under the stated "Ingress buffer eviction based on attacker-controlled interference with unrelated fee-payers" category: a victim's fee-paying, protocol-valid transaction can be silently and permanently stranded by an attacker who has no relationship to the victim's nonce account and never needs to succeed on-chain. Durable-nonce transactions are specifically used because clients expect them to remain valid indefinitely (no blockhash-based expiry), so victims/wallets have no expectation of needing to resubmit, and no automatic detection exists for this silent drop — the transaction simply never appears in a `ConsumeWork` batch and is never recorded on-chain.

### Likelihood Explanation
The only precondition is that the attacker knows the victim's nonce account address, which is public information (readable via RPC or observed on submission). No stake, no leader control, and no interaction with the victim beyond sending a single crafted low-cost packet with an inflated fee are required, and this can be repeated at will for any nonce account whose address is known, making it trivially and repeatably exploitable by any unstaked client with TPU/QUIC access.

### Recommendation
Before evicting a lower-priority nonce transaction for the same nonce address, the receive path should verify that the incoming transaction is actually capable of invalidating the buffered one — e.g., only dedup/evict entries from the *same fee payer* or when the incoming transaction's declared nonce authority matches the nonce account's current on-chain authority (requires a bank lookup) — rather than keying eviction purely off the syntactic nonce-account address referenced in the instruction.

### Proof of Concept
Integration test plan (in `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs` test module or a new integration test):
1. Create nonce account `N` with authority `A`, funded via a test bank.
2. Build `T_v`: valid `AdvanceNonceAccount` transaction over `N`, signed by `A`, with a normal priority fee, and buffer it via the receive-and-buffer path.
3. Build `T_a`: a transaction whose message also names `N` in an `AdvanceNonceAccount` instruction but signs with an attacker-controlled keypair `B` (not the real authority `A`) as the "authority" slot, with an inflated compute-unit price so its priority exceeds `T_v`.
4. Feed `T_a` through the same receive path.
5. Assert: `container` no longer contains `T_v`'s id (`num_evicted_on_nonce_dedup == 1`), and that a subsequent `ConsumeWork`/scheduling pass never yields `T_v`, while `T_a` eventually fails bank processing due to nonce-authority mismatch — demonstrating the victim's valid transaction was permanently and unrecoverably dropped in favor of a transaction that could never succeed on-chain.
