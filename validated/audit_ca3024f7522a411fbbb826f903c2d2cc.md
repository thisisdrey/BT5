### Title
Remote panic via `assert!(preamble.payload_len > 5)` in `validate_blocks_push`/`validate_microblocks_push` on empty blocks/microblocks push - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_blocks_push` (and its microblocks twin) enforce a minimum payload size with `assert!(preamble.payload_len > 5)` at `stackslib/src/net/chat.rs:2095` before any relayer or signature checks run. A `Blocks`/`Microblocks` push message whose payload encodes an empty block/microblock vector legitimately serializes to a `payload_len` of exactly 5 (1-byte type tag + 4-byte empty-vector length prefix), which fails the strict `>` comparison and panics the connection-handling thread instead of returning a `net_error`.

### Finding Description
`validate_blocks_push` is reached from the P2P message dispatch path for any already-handshaked peer sending a `StacksMessageType::Blocks` push, prior to `process_relayers` (which checks relay cycles) and long before any block/microblock signature verification occurs: [1](#0-0) .

The guard is written as a hard `assert!`, not a returned error:
```
assert!(preamble.payload_len > 5); // don't count 1-byte type prefix + 4 byte vector length
```
followed shortly by:
```
self.stats.add_block_push((preamble.payload_len as u64) - 5);
```
`preamble.payload_len` is a wire field set by the sender/serializer to the actual encoded size of the relayers + payload; for a `BlocksData` message carrying an empty vector of blocks, the minimum self-consistent encoding is exactly `1 (type byte) + 4 (u32 vector length = 0)` = 5 bytes, which is not `> 5`. Such a message is fully valid and parseable by the codec (it need not be internally inconsistent or "malformed" in the sense of failing length checks), but it trips the assert and panics the thread handling that peer's connection instead of gracefully returning `Err(net_error::...)`. The identical pattern exists in `validate_microblocks_push` at `stackslib/src/net/chat.rs:2135`.

Because this check executes before `process_relayers` and before any relayed-block signature/authenticity verification, an attacker only needs a completed handshake (unprivileged, no secret, no StackerDB slot, no relayer chain of legitimate peers) to reach it.

### Impact Explanation
A single crafted `Blocks` (or `Microblocks`) push message with an empty vector of blocks causes the P2P connection-handling thread to panic, crashing the node's networking (unauthenticated/remote DoS from a single message, matching the Critical "remote crash/unauthenticated DoS from few messages" category). This affects any node accepting P2P connections and is trivially repeatable against any peer the attacker can complete a handshake with.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to complete a normal P2P handshake (no privileged role, no RPC secret, no StackerDB ownership) and then send one `Blocks` (or `Microblocks`) message whose payload encodes zero blocks, yielding `preamble.payload_len == 5`. This is remotely reachable on the standard P2P port and costs a single message per crash attempt, making it highly likely to be exploitable if no other layer rejects empty-vector block pushes before reaching `validate_blocks_push`/`validate_microblocks_push`.

### Recommendation
Replace the `assert!(preamble.payload_len > 5)` checks in both `validate_blocks_push` and `validate_microblocks_push` with a non-panicking validation that returns `Err(net_error::InvalidMessage)` (updating `self.stats.msgs_err`) when `payload_len <= 5`, mirroring the error-handling style already used elsewhere in these functions (e.g., the relayer-cycle check).

### Proof of Concept
Rust test in `stackslib::net::chat` (or a new test module) that:
1. Builds a `StacksMessage` with `StacksMessageType::Blocks(BlocksData { blocks: vec![] })` and relayers `vec![]`, letting the codec compute/serialize the real `preamble.payload_len` (which will be 5 for the empty vector).
2. Constructs/obtains a `ConversationP2P` in a handshaked state and a `PeerNetwork`.
3. Calls `conversation.validate_blocks_push(&network, &message.preamble, message.relayers.clone())`.
4. Asserts the call returns `Err(net_error::InvalidMessage)` rather than panicking; currently the call panics at `chat.rs:2095` because `payload_len (5) > 5` is false.

    fn validate_blocks_push(
        &mut self,
        network: &PeerNetwork,
        preamble: &Preamble,
        relayers: Vec<RelayData>,
    ) -> Result<Option<ReplyHandleP2P>, net_error> {
        assert!(preamble.payload_len > 5); // don't count 1-byte type prefix + 4 byte vector length

        let local_peer = network.get_local_peer();
        let chain_view = network.get_chain_view();

        if !self.process_relayers(local_peer, preamble, &relayers) {
            warn!("Drop pushed blocks -- invalid relayers {:?}", &relayers);
            self.stats.msgs_err += 1;
            return Err(net_error::InvalidMessage);
        }

        self.stats.add_block_push((preamble.payload_len as u64) - 5);
