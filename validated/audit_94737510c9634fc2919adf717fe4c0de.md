### Title
On-Chain Bancor Exchange Price Manipulation via Sandwich Attack — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
The TRON on-chain "Exchange" feature (a Bancor-formula AMM for TRX/TRC10 token pairs) computes swap output entirely from the pool's current on-chain reserves at the moment a transaction executes, with slippage protection provided only by a caller-supplied `expected` minimum. Like the `_swap`/`_getBestFee` pattern in the external report, the price used to fill an order is derived on-chain from manipulable state immediately before execution, allowing a front-runner to shift the reserve ratio, let the victim's trade execute against the worse rate (but still above their `expected` floor), and then reverse the shift to extract the difference — a classic sandwich attack against an unprivileged trade.

### Finding Description
`ExchangeTransactionActuator` lets any account swap `tokenID` for `anotherTokenID` in a given pool. The swapped amount is computed purely from the pool's live reserves via `ExchangeCapsule.transaction()`: [1](#0-0) 

which delegates to the Bancor-relay formula in `ExchangeProcessor.exchange()`, driven only by `firstTokenBalance`/`secondTokenBalance` read at execution time: [2](#0-1) 

The only protection against an unfavorable fill is the caller-chosen `expected` (minimum-received) field, checked in `doValidate()`: [3](#0-2) 

This is directly analogous to `amountOutMin` in the external report: it bounds how bad a fill can be, but it does not prevent the pool price from being manipulated between when the victim decides on `expected` and when the transaction is actually included and executed. Because `ExchangeTransactionContract` is unrestricted (any account with sufficient balance can call it — no creator check, unlike inject/withdraw which do require creator status: [4](#0-3) , [5](#0-4) ), an attacker can:
1. Observe (or predict) a pending victim `ExchangeTransactionContract` in the broadcast pool.
2. Submit their own `ExchangeTransactionContract` ahead of it to shift the reserve ratio against the victim (front-run leg).
3. Let the victim's trade execute at the manipulated rate — it still succeeds as long as the output stays at or above the victim's `expected` floor, i.e., within the victim's tolerated slippage band.
4. Submit a reverse trade immediately after (back-run leg) to restore the ratio and capture the price difference extracted from the victim.

This mirrors exactly the risk class described in the report: an on-chain, reserve-derived quote with only a caller-set minimum-output guard is inherently sandwichable, since the guard only bounds loss, it does not prevent price manipulation within that bound.

### Impact Explanation
A successful sandwich against `ExchangeTransactionContract` results in direct value extraction (theft) from any ordinary user trading through the on-chain Exchange pools — the attacker profits at the expense of the victim's trade, and repeated sandwiching can also degrade the pool's implied exchange rate for a token pair. This is a fund-theft impact reachable by any unprivileged transaction broadcaster with no special permissions, matching the report's accepted-risk class (BVSS Medium).

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to reliably order two of their own transactions around a victim's `ExchangeTransactionContract`. TRON blocks are produced by Super Representatives on a short interval and transaction ordering within a block/mempool is not governed by a fee-priority auction, but an attacker monitoring pending transactions and racing to get sandwiching orders included in the same or adjacent block window can still realistically achieve this, especially against high-value or high-slippage-tolerance trades, without needing to compromise a witness/SR or any other privileged role.

### Recommendation
Introduce protections against reserve manipulation for the on-chain Exchange feature, e.g.: enforce a maximum allowed price-impact per single `ExchangeTransactionContract` relative to a time-weighted or previous-block reserve snapshot, rate-limit/cool-down large consecutive trades against the same pool within one block, or require `expected` to be validated against a recent block's reserve state rather than only against the state immediately preceding execution, reducing the profitable window for sandwiching.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from victim V selling `tokenA` for `tokenB` in exchange pool `P`, with `expected` set to a value tolerating up to X% slippage.
2. Attacker broadcasts `ExchangeTransactionContract` (front-run) selling a large amount of `tokenA` into `P`, shifting `firstTokenBalance`/`secondTokenBalance` so the Bancor formula in `ExchangeProcessor.exchange()` yields a worse rate for `tokenA`→`tokenB`.
3. Once included, V's trade executes via `ExchangeTransactionActuator.execute()` → `ExchangeCapsule.transaction()`, receiving less `tokenB` than it would have at the pre-attack ratio, but still ≥ `expected` (validated at `ExchangeTransactionActuator.java:219`), so the trade succeeds.
4. Attacker broadcasts a back-run `ExchangeTransactionContract` selling `tokenB` back for `tokenA` in `P`, restoring the ratio and realizing a profit equal to the value skimmed from V's trade, all using only `ExchangeTransactionContract`, which requires no special privilege beyond holding balance of `tokenA`/`tokenB`.
