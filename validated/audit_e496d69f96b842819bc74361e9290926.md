### Title
Load shedder cannot cancel resource-exhausting mutator RPCs (e.g. large pushes) - ([File: internal/burdenmonitor/interceptor.go])

### Summary
Gitaly's load-management stack lets the `LoadShedder` cancel the most expensive in-flight RPCs when the node hits critical resource pressure (OOM, sustained CPU/memory/IO throttling). However, `BurdenMonitor`'s gRPC interceptors only register RPCs whose method is classified as `protoregistry.OpAccessor` (read-only calls). Mutator RPCs — including the write paths an ordinary user triggers via `git push` (e.g. `SSHReceivePack`/`PostReceivePack` and the various `OperationService` RPCs) — are never registered with the `BurdenMonitor`, and therefore can never be selected or cancelled by the `LoadShedder`.

### Finding Description
The `BurdenMonitor.UnaryInterceptor` and `BurdenMonitor.StreamInterceptor` gate RPC tracking on an explicit operation-type check: [1](#0-0) [2](#0-1) 

Only when `mi.Operation == protoregistry.OpAccessor` does the interceptor call `bm.RegisterRPC(...)` and wrap the context so that spawned Git commands are attributed to the entry via `NotifyCommandStarted`/`NotifyCommandCompleted`. For any other RPC (i.e., any mutator/write RPC), the handler is invoked directly with no burden-monitor tracking at all: [3](#0-2) 

The `LoadShedder.shed` function, which is the only mechanism capable of forcibly cancelling an in-flight RPC when the node is under critical pressure, selects its victims exclusively from `BurdenMonitor`'s tracked entries: [4](#0-3) 

Since mutator RPCs are never registered, they are structurally invisible to `GetTopNEntries` and can never be `cancel`-ed, regardless of how much CPU/memory/IO they consume. This mirrors the reported bug class: just as `BlueBerryBank` has pause-gating for lend/borrow/repay but omits it for `withdrawLend`, Gitaly's load-shedding "kill switch" is wired for read (accessor) RPCs but is architecturally absent for write (mutator) RPCs that an ordinary, unprivileged user can trigger through a normal `git push`.

### Impact Explanation
An ordinary, unprivileged user can drive a mutator RPC (e.g. a push containing a very large pack that spawns expensive `git-receive-pack`/`git-index-pack`/hook subprocesses) that consumes large amounts of CPU, memory, or IO. Even after the `LoadMonitor` detects critical severity and instructs the `LoadShedder` to free capacity, the shedder cannot see or cancel this RPC because it was never registered by `BurdenMonitor` (mutator RPCs are excluded by design of the `OpAccessor` filter). This defeats the intended DoS-mitigation control for the exact class of RPC (heavy write operations) most likely to cause resource exhaustion, allowing sustained resource pressure/OOM conditions to persist and potentially degrade or crash the Gitaly node for all repositories/tenants it serves.

### Likelihood Explanation
High likelihood in any environment with the `BurdenMonitorTrackCommands` feature flag enabled and the load-shedding architecture active: no privileged access, malicious peer, or token leak is required — a normal authenticated Git user (or any client permitted to push) can send a large/expensive push, which is a routine and expected traffic pattern. The gap is deterministic (a hard-coded operation-type filter), not a race condition or timing-dependent condition.

### Recommendation
Extend `BurdenMonitor`'s interceptors to also register mutator RPCs (or at minimum, resource-intensive mutator RPCs such as those in `OperationService`, `SmartHTTPService`/`SSHService` receive-pack paths), so that the `LoadShedder` can locate and cancel them under critical resource pressure just as it does for accessor RPCs. Alternatively, provide an explicit opt-in mechanism, similar to `isBorrowAllowed`/`isRepayAllowed`/`isLendAllowed` in the referenced report, that ensures every RPC capable of significant subprocess resource consumption is subject to load-shedding admission and cancellation control, not only read-side accessors.

### Proof of Concept
1. Enable `featureflag.BurdenMonitorTrackCommands` and the load-management stack (`LoadMonitor`, `AdaptiveCalculator`, `LoadShedder`) as described in `doc/load-management-architecture.md`.
2. As an ordinary authenticated user, issue a `git push` of a large repository/pack, which triggers a mutator RPC (e.g., via `SSHReceivePack`/`PostReceivePack` or an `OperationService` write RPC) that spawns heavy Git subprocesses.
3. Confirm that `BurdenMonitor.UnaryInterceptor`/`StreamInterceptor` does not call `RegisterRPC` for this RPC because `mi.Operation != protoregistry.OpAccessor`.
4. Drive the node into critical resource pressure (e.g., via concurrent large pushes) so `LoadMonitor` fires a critical event.
5. Observe that `LoadShedder.shed` calls `bm.GetTopNEntries` and only ever finds/cancels tracked (accessor) RPCs — the resource-heavy push RPC is never present in the entry list and is never cancelled, continuing to consume node resources uninterrupted. [5](#0-4) [4](#0-3)

// NotifyCommandStarted registers a new command with the burden monitor if command tracking is enabled.
// This should be called when a command starts execution.
func NotifyCommandStarted(ctx context.Context, pid int, name string, startTime time.Time) {
	entry, ok := rpcEntryFromContext(ctx)
	if !ok {
		return
	}

	entry.RegisterCommand(pid, name, startTime)
}

// NotifyCommandCompleted notifies the burden monitor that a command has completed.
// This should be called when a command finishes execution.
func NotifyCommandCompleted(ctx context.Context, pid int, userTime, systemTime time.Duration) {
	entry, ok := rpcEntryFromContext(ctx)
	if !ok {
		return
	}

	entry.MarkCommandCompleted(pid, userTime, systemTime)
}

// UnaryInterceptor returns a gRPC unary server interceptor that tracks RPC execution.
func (bm *BurdenMonitor) UnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
		if featureflag.BurdenMonitorTrackCommands.IsEnabled(ctx) {
			mi, err := protoregistry.GitalyProtoPreregistered.LookupMethod(info.FullMethod)
			if err != nil {
				// The gRPC health checks calls are not part of the Gitaly proto
				// registry, yet they are legitimate requests. Let's not log
				// everytime a health check is received as it pollutes the logs,
				// mostly when using Praefect.
				if !strings.Contains(info.FullMethod, grpchealth.Health_ServiceDesc.ServiceName) {
					bm.logger.WithError(err).Warn("burden monitor stream interceptor: unable to lookup method info")
				}
				return handler(ctx, req)
			}

			// Only track accessor method in the burden monitor
			if mi.Operation == protoregistry.OpAccessor {
				ctx, entry := bm.RegisterRPC(ctx, info.FullMethod)

				defer bm.DeregisterRPC(entry.ID)
				return handler(ctx, req)

			}
		}

		return handler(ctx, req)
	}
}

func (ls *LoadShedder) shed(ctx context.Context, event loadmonitor.Event) {
	entries := ls.bm.GetTopNEntries(shedTopN, SortByCPU)
	reason := SortByCPU.reason()

	for _, entry := range entries {
		ls.cancel(entry, reason)
	}

	ls.logger.WithFields(log.Fields{
		"condition":    event.ConditionName,
		"reason":       event.Description,
		"sniped_count": len(entries),
	}).WarnContext(ctx, "load shedder cancelled in-flight RPCs")
}
