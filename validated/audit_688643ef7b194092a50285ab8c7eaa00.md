### Title
Unauthorized Privilege Escalation via AccountPermissionUpdateContract Scope Bypass - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` allows a transaction signed under any delegated Active permission (identified by `permission_id`) to rewrite an account's entire Owner/Witness/Active permission set — including granting brand-new Active permissions with arbitrary operation scopes (TransferContract, WitnessCreateContract, ExchangeCreateContract, VoteWitnessContract, etc.) — as long as the requested operations bitmap is a subset of the chain-wide `AVAILABLE_CONTRACT_TYPE` registry. The code never checks that the signing permission itself already possesses the scopes it is assigning to the new permissions, exactly mirroring GHSA-hjfh-p8f5-24wr's root cause ("validates only that requested scopes exist in the system registry... does not verify that the requester already possesses the scopes").

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` validates a proposed `Permission`'s `operations` bitmap solely against `dynamicStore.getAvailableContractType()` — the chain's globally enabled contract-type registry — not against the operations already granted to the specific permission that authorized the transaction: [1](#0-0) 

Separately, TRON's general transaction-authorization path (`TransactionCapsule.validateSignature` / `checkPermission`) allows any non-owner (`permissionId != 0`) Active permission to authorize a contract call, provided that Active permission's own `operations` bitmap has the bit set for the contract type being invoked: [2](#0-1) 

Because `AccountPermissionUpdateContract`'s type bit is present in `AVAILABLE_CONTRACT_TYPE` (only `UpdateBrokerageContract` is excluded, per the test asserting the registry value `7fff1fc0037ef90f...`), an account owner can — intentionally or not — delegate a narrowly-scoped Active permission whose only granted capability is to call `AccountPermissionUpdateContract` (e.g., for a key-rotation bot or co-signer service): [3](#0-2) 

Note that `ACTIVE_DEFAULT_OPERATIONS` (used only for the *default* auto-generated active permission) explicitly excludes `AccountPermissionUpdateContract`, but this exclusion is not enforced by `checkPermission()`'s validation of arbitrary custom permissions — it only bounds against `AVAILABLE_CONTRACT_TYPE`: [4](#0-3) 

Once that narrow key exists, it can sign a new `AccountPermissionUpdateContract` transaction (using its own `permission_id`) that overwrites the account's Active permission list with a brand-new permission containing a full operations bitmap (transfers, voting, exchange, contract creation, etc.) and keys entirely controlled by the attacker. `checkPermission()` only checks these bits against the global registry, not against the operations the signer's own permission actually holds, so the check passes. `execute()` then applies the change unconditionally: [5](#0-4) [6](#0-5) 

The result: a key delegated only for permission/key-management housekeeping escalates to full transactional control of the account (transfers, voting, resource/stake operations, contract deployment) without any Owner-key signature — a direct privilege-escalation analog of the OAuth scope-assignment bug (CWE-862, Missing Authorization).

### Impact Explanation
An attacker who compromises or is legitimately granted only a limited Active key (e.g., for automated permission housekeeping) can unilaterally grant themselves (or any address they control) unrestricted transactional authority over the victim account — enabling unauthorized asset transfers, stake/vote manipulation, and contract deployment under the victim's identity, all without the account Owner ever re-signing. This is a concrete unauthorized-account-operation / theft-of-funds vector, satisfying the High severity bar.

### Likelihood Explanation
Any account that uses TRON's multi-sig feature to delegate a scoped Active permission covering `AccountPermissionUpdateContract` (a legitimate and expected multisig pattern for key-rotation/custodial automation) is exposed. The attack requires only a single signed transaction from the delegated key — no additional privilege, race condition, or network-level assumption is needed, making exploitation straightforward once such a delegated key exists or is compromised.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()` (and/or `validate()`), when the transaction is authorized by a non-owner Active permission (`contract.getPermissionId() != 0`), additionally require that every operation bit being granted to the new Owner/Witness/Active permissions is already present in the *signing* permission's own `operations` bitmap (or otherwise restrict `AccountPermissionUpdateContract`-scoped Active permissions from being able to modify permissions beyond their own granted scope). This mirrors defense used for other operations and prevents scope amplification.

### Proof of Concept
1. Account Owner enables multisig (`AllowMultiSign=1`) and calls `AccountPermissionUpdateContract` to add an Active permission `P1` (threshold 1, key `K1`) whose `operations` bitmap has only the `AccountPermissionUpdateContract` bit set — intended for automated permission-rotation tooling.
2. `checkPermission()` accepts this because the bit is present in `AVAILABLE_CONTRACT_TYPE`; the actuator does not compare against `ACTIVE_DEFAULT_OPERATIONS` or any narrower "safe" set.
3. Key `K1` (or an attacker who compromises it) crafts a new transaction with `permission_id` referencing `P1`, containing a fresh `AccountPermissionUpdateContract` that replaces the Active permission list with a new permission `P2` (threshold 1, key `K2`, attacker-controlled) whose `operations` bitmap includes `TransferContract` and other high-value contract types (all still within `AVAILABLE_CONTRACT_TYPE`).
4. Sign with `K1` only; `TransactionCapsule.checkPermission`/`checkWeight` pass because `P1` is allowed to invoke `AccountPermissionUpdateContract`, and `AccountPermissionUpdateActuator.validate()`/`execute()` accept and apply the update, per `AccountCapsule.updatePermissions`.
5. Attacker now signs subsequent `TransferContract` transactions with `K2` under `P2`, moving funds out of the victim account — full privilege escalation from a narrow "permission-management-only" key to complete account control, achieved without any Owner-key signature.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
