### Title
Missing Domain Separation in ValidateMultiSign Precompile Enables Cross-Contract Signature Replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile at `0x0000...100` lets *any* smart contract check whether a set of off-chain ECDSA signatures satisfies an account's multisig `Permission` threshold, for an arbitrary, caller-supplied `data` blob. The message that is actually hashed and signed off-chain is `sha256(address || permissionId || data)`, which never includes the identity of the calling/verifying contract (analogous to the missing "verifying address" in `ApprovedCallsPolicy.messageHash` from the external report) nor the chain id. This allows a signature collected by one dApp for one purpose to be replayed by any other dApp that happens to use the same `(address, permissionId, data)` encoding, exactly the class of bug flagged in the ApprovedCallsPolicy report. ### Finding Description
`ValidateMultiSign.execute()` builds the signed hash purely from the TRON account address, permission id, and caller-provided `data`: [2](#0-1) 

It then recovers each signer, checks their weight against `permission`, and returns success once the accumulated weight passes threshold: [3](#0-2) 

Unlike `ApprovedCallsPolicy`, which at least embeds `txOrigin`/`nonce`/`chainid` (still found insufficient by the auditors because it omitted the *verifying contract address*), this precompile's hash has **no binding at all** to:
- the calling/consuming contract (`msg.sender` inside the TVM), i.e. no "verifying address" equivalent,
- `block.chainid`, so the exact same signature is valid identically on any TRON-compatible chain (mainnet, Nile, private/side chains) sharing the same account address and permission,
- any nonce or expiration, so a captured signature is valid forever and can be replayed an unlimited number of times as long as `data` matches.

Because `data` is fully controlled and interpreted by the calling contract (there is no canonical encoding enforced by the protocol), any two unrelated dApps that adopt similar off-chain approval schemes (e.g., "approve transfer of asset X to address Y") can produce identical `(address, permissionId, data)` triples. A user who signs an off-chain approval for a legitimate purpose in dApp A can have that same signature submitted to dApp B (or to dApp A again in a different context, or on a different chain) via `ValidateMultiSign`, since the precompile has no way to distinguish the calling context. This mirrors precisely the finding in `ApprovedCallsPolicy` where sharing the same `SIGNER_ROLE`/verification scheme across policy instances enabled signature reuse.

Additionally, signature malleability is not defended against: `ECDSASignature.validateComponents` only checks `s` is within `[1, SECP256K1N)` and does not restrict `s` to the lower half of the curve order the way `ECRecover`'s canonical form would require: [4](#0-3) 
`recoverAddrBySign`/`ValidateMultiSign`'s signature parsing path (`extractSigArray`/`recoverAddrBySign`) was not confirmed in this pass to reject the non-canonical high-`s` variant, matching the report's second complaint that `s` is "not checked" for canonicalization, though this is a secondary, lower-severity concern compared to the missing domain separation.

### Impact Explanation
Any contract deployer can build a dApp that calls `ValidateMultiSign` to gate privileged on-chain actions (fund transfers, order execution, permission changes) behind an off-chain multisig approval. Because the signed payload lacks a verifying-contract/chain binding, an attacker who has observed or obtained a signature intended for one context (one contract, one chain) can replay it verbatim against a different, unrelated contract or a fork/sidechain that reuses the same account/permission scheme, causing the victim's multisig approval to authorize an action the signer never intended. This can lead to unauthorized asset transfers or unauthorized state-changing operations gated by `ValidateMultiSign`, i.e., theft or unauthorized account operations facilitated entirely through a signed transaction/contract call path reachable by any unprivileged contract deployer/caller.

### Likelihood Explanation
Exploitation requires that two (or more) consumer contracts adopt the same `data` encoding for semantically different actions, or that the same signed message is valid on more than one chain instance sharing account state (e.g., a chain fork, or a private/enterprise TRON-compatible chain using the same genesis accounts) — both realistic scenarios for a precompile explicitly designed as a general-purpose "verify off-chain multisig approval" primitive with no protocol-enforced structured/typed-data encoding. Since the precompile is directly callable from any TVM contract with no privileged role required, likelihood is Medium: it depends on ecosystem dApp design choices reusing this primitive with colliding encodings, but the root cause (no domain separation) is unconditionally present.

### Recommendation
Include a domain separator in the hash computed inside `ValidateMultiSign` (and any other off-chain-approval verification helpers), analogous to EIP-712 style separation: bind the hash to the calling contract address (`msg.sender`/precompile caller context), `block.chainid`, and ideally a nonce/expiration if the primitive is meant to authorize one-time actions. At minimum, document and encourage callers to include their own contract address and chain id inside `data`, but preferably enforce it at the precompile level so dApp developers cannot omit it. Separately, enforce canonical (low-`s`) signature form consistently across all signature-verification code paths (`ECDSASignature.validateComponents`, `ValidateMultiSign`'s parsing) to eliminate malleability regardless of severity.

### Proof of Concept
1. Deploy two independent TVM contracts, `DAppA` and `DAppB`, both calling the `ValidateMultiSign` precompile (`0x0000...100`) to authorize a transfer, using the same encoding scheme for `data` (e.g., `abi.encode(amount, recipient)`).
2. A user with an active `Permission` on account `Acc` signs an off-chain message intended for `DAppA`'s withdrawal of `100` to `X`, producing `sig` over `sha256(Acc || permissionId || data)` as computed in `ValidateMultiSign.execute()`.
3. The user submits `sig` to `DAppA`, which calls `ValidateMultiSign(Acc, permissionId, data, [sig])` — succeeds, funds move as intended.
4. An attacker (or `DAppB` itself, deployed by an unrelated party) later submits the *same* `sig` and `data` to `DAppB`'s call into `ValidateMultiSign` for the identical `(Acc, permissionId, data)` triple — the precompile has no way to distinguish that this authorization was scoped to `DAppA`, and returns success again, letting `DAppB` execute an action the user only intended to authorize once, for a different contract.
5. Because `chainid` is likewise absent from the hash, the identical `sig` also validates unchanged if the same account/permission state exists on any other TRON-compatible chain instance, enabling cross-chain replay as well.

  public static class ValidateMultiSign extends PrecompiledContract {

    private static final int ENGERYPERSIGN = 1500;
    private static final int MAX_SIZE = 5;
    private static final int ABI_HEADER_WORDS = 5;
    private static final int ABI_ITEM_WORDS = 5;


    @Override
    public long getEnergyForData(byte[] data) {
      long cnt = (data.length / WORD_SIZE - 5) / 5;
      // one sign 1500, half of ecrecover
      return cnt * ENGERYPERSIGN;
    }

    @Override
    public Pair<Boolean, byte[]> execute(byte[] rawData) {
      if (VMConfig.allowTvmOsaka()
          && !isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
        return Pair.of(false, EMPTY_BYTE_ARRAY);
      }
      DataWord[] words = DataWord.parseArray(rawData);
      byte[] address = words[0].toTronAddress();
      int permissionId = words[1].intValueSafe();
      byte[] data = words[2].getData();

      byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
      byte[] hash = Sha256Hash.hash(CommonParameter
          .getInstance().isECKeyCryptoEngine(), combine);

      if (VMConfig.allowTvmSelfdestructRestriction()) {
        int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
        if (sigArraySize > MAX_SIZE) {
          return Pair.of(true, DATA_FALSE);
        }
      }
      byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
          extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
          extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);

      if (signatures.length == 0 || signatures.length > MAX_SIZE) {
        return Pair.of(true, DATA_FALSE);
      }
