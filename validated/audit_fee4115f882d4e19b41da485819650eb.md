### Title
Heap-based out-of-bounds read in `Zip64ExtraField::attr64` via unchecked attribute index when reading attacker-supplied Zip/Jar entries - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar`'s Zip/JAR parsing code (`CDH`/`LH` classes in `src/tools/singlejar/zip_headers.h`) reads the 64-bit ZIP64 extension values via `Zip64ExtraField::attr64(index)` whenever a 32-bit size/offset field equals `0xFFFFFFFF`, but never validates that the Zip64 extra field actually contains enough 64-bit attributes (`attr_count()`) to satisfy the requested `index`. A crafted archive can declare `compressed_file_size32`/`uncompressed_file_size32` as `0xFFFFFFFF` while supplying a Zip64 extra field with a short `payload_size` (e.g. 0 or 8 bytes instead of 16/24), causing `attr64()` to read a `uint64_t` past the end of the actual extra-field payload.

### Finding Description
The Zip64 extension mechanism is implemented in `src/tools/singlejar/zip_headers.h`: [1](#0-0) 

`attr64(int index)` performs a raw, unbounded array read (`attr_[index]`) with no check against `attr_count()` (which is derived from the extra field's own `payload_size()`). Both `CDH::compressed_file_size()/uncompressed_file_size()` and `LH::compressed_file_size()/uncompressed_file_size()` call `attr64()` with a fixed or conditionally computed index whenever the 32-bit counterpart equals `0xFFFFFFFF` (`ziph::zfield_has_ext64`): [2](#0-1) [3](#0-2) 

The only bound check performed before this happens is in `ExtraField::find`, which only validates that the extra field's declared `tag`+`payload_size` header fits within the extra-fields byte range — it does not validate that `payload_size` is large enough to contain the specific attribute index that `attr64()` will subsequently read: [4](#0-3) 

So an attacker who controls the bytes of a `.zip`/`.jar` (e.g. served from an `http_archive`/`http_jar` URL, a third-party dependency jar consumed by `singlejar` when assembling a deploy jar, or any build input processed by this parser) can craft:
- `compressed_file_size32_` (or `uncompressed_file_size32_`) = `0xFFFFFFFF`
- A Zip64 extra field (`tag == 1`) whose `payload_size` is smaller than required (e.g. `0` or `8` instead of `16`)

When `compressed_file_size()`/`uncompressed_file_size()` is invoked, `attr64(1)` (or `attr64(0)`) reads 8 bytes beyond the payload the attacker actually supplied. If the malformed field sits near the end of the mmap'd input file (`MappedInputFile`, used throughout `zip.cc`/`input_jar.cc`), this read can run past the mapped region boundary, producing a heap/mmap-based out-of-bounds read — directly analogous to Binaryen's `WasmBinaryReader::readExport` bug, where an index into a binary-format-declared structure is used without validating it against the structure's own declared/actual size.

### Impact Explanation
This is a memory-safety violation reachable purely from bytes inside an untrusted archive that Bazel is instructed to process (no local machine access, no credentials, no privileged root-repo Starlark required). An out-of-bounds read in a native (C++) tool can leak adjacent heap/mmap memory into subsequently used size fields (which then influence decompression buffer sizing, e.g. via `TransientBytes::DecompressEntryContents`), and in the worst case (crafted so the malformed field sits at a page boundary) crash the `singlejar` process (denial of service) or produce corrupted size values that propagate into further length-driven memory operations.

### Likelihood Explanation
Likelihood is limited by two factors that reduce, but do not eliminate, exploitability:
1. `ExtraField::find` does correctly bound the *tag header* + declared `payload_size` within the overall extra-fields region, so the out-of-bounds read is bounded to at most a few (8/16) bytes beyond the legitimately-scanned extra field region, not an arbitrarily large read.
2. Reaching a page/mmap boundary exactly at the malformed field requires the attacker to control the total file layout precisely (feasible for a fully attacker-controlled downloaded archive, since they control file size and offsets).

Given `singlejar` regularly processes third-party jars supplied as build inputs, and the attacker fully controls the archive bytes (no MITM or credential access needed), this is a realistic, attacker-reachable code path with no existing guard against it (no `attr_count()` check found anywhere in `zip_headers.h`, `zip.cc`, `output_jar.cc`, or `input_jar.cc`).

### Recommendation
Add bounds validation in `Zip64ExtraField::attr64()` (or at each call site in `CDH`/`LH`) that verifies `index < attr_count()` before dereferencing `attr_[index]`, returning a defined error/sentinel value (and propagating a parse failure) instead of performing the unchecked read when the declared Zip64 extra field is too short for the requested attribute.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` proof would:
1. Programmatically build a `.zip`/`.jar` file (mirroring the existing Zip64 test fixtures in `src/tools/singlejar/zip_headers_test.cc` and `input_jar_scan_entries_test.h`) containing one entry whose Central Directory Header sets `compressed_file_size32_ = 0xFFFFFFFF` but attaches a Zip64 extra field (`tag=1`) with `payload_size = 0` (i.e., zero declared 64-bit attributes).
2. Feed this archive through `singlejar`'s `InputJar`/`OutputJar` path (e.g. via the existing `TestZip64`-style test harness in `input_jar_scan_entries_test.h`) or through a `java_library`/genrule build that merges this crafted jar with `singlejar`.
3. Run the binary built with AddressSanitizer; observe a heap-buffer-overflow (read) report at `Zip64ExtraField::attr64` invoked from `CDH::compressed_file_size()`, confirming the out-of-bounds read. [5](#0-4) [6](#0-5)

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

class Zip64ExtraField : public ExtraField {
 public:
  static const Zip64ExtraField* find(const uint8_t* start, const uint8_t* end) {
    return reinterpret_cast<const Zip64ExtraField*>(
        ExtraField::find(1, start, end));
  }

  bool is() const { return is_zip64(); }
  void signature() { ExtraField::signature(1); }

  // The value of i-th attribute
  uint64_t attr64(int index) const { return le64toh(attr_[index]); }
  void attr64(int index, uint64_t v) { attr_[index] = htole64(v); }

  // Attribute count
  int attr_count() const { return payload_size() / sizeof(attr_[0]); }
  void attr_count(int n) { payload_size(n * sizeof(attr_[0])); }

  // Space needed for this field to accommodate n_attr attributes
  static uint16_t space_needed(int n_attrs) {
    return n_attrs > 0 ? sizeof(Zip64ExtraField) + n_attrs * sizeof(uint64_t)
                       : 0;
  }

 private:
  uint64_t attr_[];
} attr_packed;
