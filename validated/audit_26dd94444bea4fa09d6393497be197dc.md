### Title
Unclaimed TRON Power voting rewards are permanently frozen when a contract self-destructs to itself via `SUICIDE`/`SELFDESTRUCT` - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
In `Program.suicide2()`, when a contract self-destructs with the beneficiary address equal to its own address (`owner == obtainer`), the method returns immediately after marking the account self-destructed, **without** calling `withdrawRewardAndCancelVote(owner, ...)`. This is the exact analog of the Alchemix bug: a "burn"/finalization operation (self-destruct) happens before the account's accrued-but-unclaimed reward (`allowance`, accrued via `VoteRewardUtil.withdrawReward`) is settled, permanently freezing it.

### Finding Description
`Program.suicide2()` handles the `SUICIDE`/`SELFDESTRUCT` opcode logic used when the new (post-`allowTvmSelfdestructRestriction`) self-destruct semantics are active: [1](#0-0) 

Note the control flow:
1. If `owner == obtainer` (self-destruct-to-self), the code immediately calls `getContractState().markSelfDestruct(owner)` and **returns**, skipping the entire reward/vote settlement branch below.
2. Only in the `owner != obtainer` path does `withdrawRewardAndCancelVote(owner, getContractState())` get invoked, which is the function responsible for computing and crediting any pending vote reward into the account's `allowance`/`balance` and clearing its vote list: [2](#0-1) 

Compare this to the older `suicide()` (v1) implementation, where `withdrawRewardAndCancelVote` is called unconditionally **before** the owner==obtainer balance-zeroing branch, so the reward is always settled first: [3](#0-2) 

`withdrawRewardAndCancelVote` internally calls `VoteRewardUtil.withdrawReward`, which computes the reward accrued from the account's votes using `DelegationStore` cycle Vi deltas and moves it into `allowance` via `adjustAllowance`: [4](#0-3) 

Because `suicide2()`'s self-to-self branch skips this call entirely, any TRON Power voting reward accrued for cycles up to `getBeginCycle`/`getEndCycle` that has not yet been moved into `allowance` never gets computed/credited. The account is then marked self-destructed via `markSelfDestruct`, and its votes/allowance state is never reconciled again through this path — mirroring the Alchemix `VotingEscrow.merge()` bug where the `_from` token is burned before its unclaimed ALCX reward is claimed.

### Impact Explanation
Any account (including a normal EOA that has delegated bytecode execution rights, or more directly, any contract account) that has cast TRON Power votes and has an in-flight, uncredited reward for the current voting cycle will have that reward permanently lost the moment it self-destructs to itself. This is a permanent freezing/loss of the account's earned TRC reward (its `allowance`), reachable by any unprivileged contract deployer/caller who triggers the `SUICIDE` opcode with `obtainer == self`.

### Likelihood Explanation
This requires: (1) `VMConfig.allowTvmVote()` and the newer self-destruct restriction path to be active (both are on-chain-configurable but standard in current java-tron chain parameters), (2) the account has outstanding votes with pending un-credited reward for the current cycle, and (3) the account executes `SELFDESTRUCT`/`SUICIDE` targeting itself. All three conditions are fully controllable by a single unprivileged contract deployer through a normal transaction — no special privileges are required, making this straightforward to trigger deliberately or accidentally.

### Recommendation
In `Program.suicide2()`, call `withdrawRewardAndCancelVote(owner, getContractState())` (guarded by `VMConfig.allowTvmVote()`) **before** the `owner == obtainer` early-return branch, mirroring the ordering used in the legacy `suicide()` method, so that any pending vote reward is always settled and credited prior to marking the account self-destructed.

### Proof of Concept
Conceptual PoC (requires the full java-tron test harness, e.g. `framework/src/test/java/org/tron/common/runtime/vm/OperationsTest.java`, which already exercises `suicide2`):
1. Deploy a contract account `C`.
2. Freeze balance for `C` and cast a `VoteWitnessContract` vote (TRON Power vote) for a witness.
3. Advance to the next voting cycle so a reward accrues for `C` (verifiable via `VoteRewardUtil` reward computation / `distributor`-equivalent query).
4. From within `C`'s bytecode, execute `SELFDESTRUCT(address(this))` (i.e., `obtainer == owner`), which is routed to `Program.suicide2()`.
5. Observe that `withdrawRewardAndCancelVote` is never invoked (no `adjustAllowance` call occurs, no vote-clearing), while `markSelfDestruct(owner)` still executes — the reward computed in step 3 becomes permanently unreachable since the account is now flagged self-destructed and its vote list/allowance is never reconciled.

  public void suicide2(DataWord obtainerAddress) {
    byte[] owner = getContextAddress();

    if (getContractState().isSelfDestructed(obtainerAddress.toTronAddress())) {

          Hex.toHexString(obtainer),
          balance);
    }

    InternalTransaction internalTx = addInternalTx(null, owner, obtainer, balance, null,
        "suicide", nonce, getContractState().getAccount(owner).getAssetMapV2());

    if (FastByteComparisons.isEqual(owner, obtainer)) {
      getContractState().markSelfDestruct(owner);
      return;

      withdrawRewardAndCancelVote(owner, getContractState());
      balance = getContractState().getBalance(owner);
      if (internalTx != null && balance != internalTx.getValue()) {
        internalTx.setValue(balance);

  private void withdrawRewardAndCancelVote(byte[] owner, Repository repo) {
    VoteRewardUtil.withdrawReward(owner, repo);

    AccountCapsule ownerCapsule = repo.getAccount(owner);
    if (!ownerCapsule.getVotesList().isEmpty()) {
      VotesCapsule votesCapsule = repo.getVotes(owner);
      if (votesCapsule == null) {
        votesCapsule = new VotesCapsule(ByteString.copyFrom(owner),
            ownerCapsule.getVotesList());
      } else {
        votesCapsule.clearNewVotes();
      }
      ownerCapsule.clearVotes();
      ownerCapsule.setOldTronPower(0);
      repo.updateVotes(owner, votesCapsule);
    }
    try {
      long balance = ownerCapsule.getBalance();
      long allowance = ownerCapsule.getAllowance();
      ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
          .setBalance(addExact(balance, allowance, VMConfig.disableJavaLangMath()))
          .setAllowance(0)
          .setLatestWithdrawTime(getTimestamp().longValue() * 1000)
          .build());
      repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    } catch (ArithmeticException e) {
      throw new BytecodeExecutionException("Suicide: balance and allowance out of long range.");
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private static void adjustAllowance(byte[] address, long amount, Repository repository) {
    if (amount <= 0) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long allowance = accountCapsule.getAllowance();
    accountCapsule.setAllowance(allowance + amount);
    repository.updateAccount(accountCapsule.createDbKey(), accountCapsule);
  }
}
