### Title
Out-of-bounds read via unbounded extra-field walk in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s ZIP central-directory parser walks per-entry "extra field" records using an attacker-controlled `data_size`, but only checks the walk cursor for exact equality with the expected end offset instead of bounding every read against the mapped input buffer. A crafted extra-field length causes the cursor to overshoot the intended region and the loop to keep dereferencing memory beyond the mapped file, unlike other parsing paths in the same tool that use an explicit `EnsureRemaining` bounds check.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads a central directory header's `file_name_length`, `extra_field_length`, and `file_comment_length` from attacker-supplied bytes, then walks the extra-field records: [1](#0-0) 

```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```

`p` (the intended end of the extra-field region) is computed purely from the attacker-controlled `extra_field_length`; the loop's only termination/bounds test is `extra_p != p`. Each iteration unconditionally reads 4 bytes (`header_id`, `data_size`) from `extra_p` with no check that `extra_p + 4 <= p` (or that it is within the mapped file at all), and then advances `extra_p` by an attacker-controlled `data_size` with no check that the new `extra_p` lands on or before `p`. If `data_size` is chosen so the running sum never exactly equals `extra_field_length` (e.g., an odd/oversized value), `extra_p` overshoots `p` and the loop condition `extra_p != p` remains true — the parser continues reading 2/4-byte header fields and advancing by more attacker-controlled `data_size` values indefinitely past the intended extra-field region, past the local/central directory content, and potentially past the end of the `mmap`'d ZIP file (`zipdata_in_`/`central_dir_`), which is exactly the "incorrect bounds check leading to out-of-bounds read" class described in CVE-2019-2228's `array_find`.

This is the parser Bazel's own `ijar`/interface-jar generation tool uses on ZIP/JAR files, i.e. on content originating from external dependencies (e.g., jars fetched via `http_archive`/`http_jar`/Maven-style rules) — attacker-published archive bytes, not trusted root-repo Starlark or local files. No integrity check, `sha256`/`integrity` verification, or lockfile hash constrains the *parsed structure* of an already-downloaded archive; those only protect against tampering of the whole file, not against a malformed-but-checksum-matching archive deliberately crafted by its publisher.

Contrast with the tool's own established bounds-checking idiom elsewhere in the same file, which explicitly validates remaining bytes before every read: [2](#0-1) 

The extra-field walk in `ProcessCentralDirEntry` does not use this idiom or any equivalent check against the mapped file bounds, so the comment above the function ("parsing it this way is safe" because the central directory is followed by a signature) does not hold for this particular sub-loop, since the sub-loop can walk arbitrarily far past `p` (and past the whole central directory) before any signature is re-checked.

### Impact Explanation
An attacker who publishes a crafted ZIP/JAR (e.g., a dependency archive fetched by `http_archive`/`http_jar`, or any prebuilt jar consumed by java rules that get processed by `ijar`) can trigger reads outside the bounds of the mapped input file. Depending on memory layout this can crash the build (process death on unmapped page) or leak adjacent process memory content into decisions later made based on the corrupted `header_id`/`data_size` values (e.g., mis-detecting a `ZIP64_EXTRA_FIELD_TAG` and using out-of-bounds bytes as `uncompressed_size`/`compressed_size`/`offset` for subsequent reads), which is a local information-disclosure-style impact matching the CVE analog (`C:H` in the original CVSS vector), scoped to the build process's own memory.

### Likelihood Explanation
Reaching this code only requires supplying a ZIP/JAR whose central directory extra fields have a size that doesn't evenly divide/sum to `extra_field_length` — a straightforward, entirely attacker-controlled byte layout with no cryptographic or timing constraints. No special privileges beyond publishing/serving the archive that a victim's build fetches and processes with `ijar` are needed.

### Recommendation
Bound every extra-field read to the actual mapped extra-field region: before reading `header_id`/`data_size`, check `extra_p + 4 <= p` (and `<= zipdata_in_ + input_file_->Length()`), and after computing the new `extra_p`, check `extra_p <= p` before continuing the loop; otherwise treat the entry as malformed and abort with `error(...)`, mirroring the `EnsureRemaining` pattern already used elsewhere in the file.

### Proof of Concept
Construct a minimal ZIP whose single central directory entry has `extra_field_length = 4` but the embedded extra-field record declares `data_size = 0xFFFF` (i.e., bytes `[[[any header_id 2 bytes]], [0xFF, 0xFF]]`). After the first iteration, `extra_p` (which started at `p - 4`) becomes `extra_p + 4 + 0xFFFF`, far past `p`; because the check is `extra_p != p` rather than `extra_p <= p`, the loop keeps iterating, calling `get_u2le`/`get_u4le` on memory increasingly far past the mapped input buffer, which can be demonstrated to crash or read out-of-bounds under ASan in a unit test built on the existing `third_party/ijar` test harness (analogous to the malformed-extra-field regression test already present for singlejar): [3](#0-2) 

That existing singlejar test demonstrates the project's own pattern for reproducing this exact bug class (malformed/oversized extra-field payload) and can be adapted (with `ASAN`/`ASSERT_DEATH`) to `third_party/ijar/zip_test.cc` to prove the `ProcessCentralDirEntry` overshoot in `third_party/ijar/zip.cc`.

    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }
