## Analog Found

The upstream Sherlock finding (M‑6) is about `RioLRTIssuer` reverting because it assumes `ERC20::approve` strictly returns a `bool`, breaking support for tokens like USDT that don't conform. The exact same broken invariant — "the protocol assumes an ERC‑20 `transfer` call returns a strictly ABI‑encoded `bool`, but many real tokens don't" — exists in `polkadot-sdk`'s production `ERC20Transactor`, the `TransactAsset` implementation used by Asset Hub to let XCM move `pallet-revive`‑deployed ERC‑20 tokens.

### Title
XCM `ERC20Transactor` permanently breaks withdrawal/deposit of any ERC‑20 token whose `transfer()` does not strictly ABI‑encode a `bool` return - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `::deposit_asset_with_surplus` execute a Solidity `transfer()` call via `pallet_revive::Pallet::<T>::bare_call` and then require the return data to strictly decode as a `bool` via `IERC20::transferCall::abi_decode_returns_validate`. Any ERC‑20 contract that returns no data, extra data, or a non-`0/1` value on `transfer` (the exact class of tokens the original report calls out — USDT-style tokens) causes decoding to fail, and the whole XCM instruction is rejected with `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")`. This blocks all XCM-based withdrawal/deposit operations for that asset permanently, even though this class of tokens is explicitly anticipated to exist and to be supported as ordinary ERC-20 assets on Asset Hub. [1](#0-0) [2](#0-1) 

### Finding Description
`withdraw_asset_with_surplus` builds `IERC20::transferCall` data, calls the target contract via `bare_call`, and — when the call didn't revert — strictly ABI-decodes the return value as a `bool`:

```
let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
    ...
    XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
})?;
``` [3](#0-2) 

`deposit_asset_with_surplus` mirrors this on the deposit path: [4](#0-3) 

This is the identical assumption flagged in the Sherlock report: any contract not returning an exact `bool` word (no return data at all — the common USDT-style pattern; a `uint256` balance; or anything else) makes `abi_decode_validate` fail, so the transfer is treated as unusable even though the on-chain token transfer may be entirely well-formed by ERC-20-non-standard convention. The repository's own tests confirm this is a real, reachable failure mode of the current design, not a hypothetical: `smart_contract_does_not_return_bool_fails` and `smart_contract_not_erc20_will_error` both assert that `PolkadotXcm::execute` fails whenever the target contract's `transfer` doesn't return a strict bool. [5](#0-4) 

Because the XCM executor wraps each `WithdrawAsset`/`DepositAsset` instruction in `Config::TransactionalProcessor::process`, a failure here rolls back the entire instruction (so there is no double-transfer/fund-loss on top of it) — but the instruction/message itself is permanently unusable for that asset: [6](#0-5) 

No unprivileged caller needs to be malicious in the excluded sense (no malicious relayer/validator/collator/admin) — any ordinary user attempting a normal `WithdrawAsset`/`DepositAsset`/reserve-transfer XCM referencing a legitimately-deployed, non-standard-return ERC-20 asset on Asset Hub triggers this failure deterministically, every time.

### Impact Explanation
This breaks intended/advertised functionality: Asset Hub's `pallet-revive`-based Solidity ERC-20 interoperability layer cannot support the well-known class of non-standard-return ERC-20 tokens (the same tokens the original report explicitly calls out, e.g. USDT-style contracts) for any XCM transfer, teleport, or reserve-transfer. Users cannot move such assets in or out of holding via XCM at all — a permanent denial of core functionality for that asset class, matching the "runtime bugs that compromise intended behavior" and "message queues/settlement must only advance after decode ... succeed" pivots. This mirrors the sherlock-audit finding's own resolved severity (Medium: "breaks core functionality").

### Likelihood Explanation
High likelihood of occurrence in practice: any ERC-20 contract deployed to `pallet-revive` that doesn't strictly return a `bool` (a common real-world pattern, not an edge case) will hit this path on the very first XCM withdrawal/deposit attempt. No special conditions, timing, or privileged actor are required — a normal user's `PolkadotXcm::execute`/`limited_reserve_transfer_assets` call against such an asset fails deterministically, as already demonstrated by the repository's own test suite.

### Recommendation
Do not hard-fail the whole XCM instruction purely because the return data doesn't strictly decode as `bool`. Options:
- Treat a successful (non-reverted) call with empty or non-bool-shaped return data as success (mirroring `SafeERC20.forceApprove`/`safeTransfer`'s "no bytes returned = ok" tolerance), only failing when the return data decodes to `false` or the call reverted.
- Alternatively, gate acceptance of an ERC-20 asset by probing/whitelisting compliant `transfer` semantics before it's matched by `Matcher::matches_fungibles`, so non-conforming tokens are rejected up front with a clear error rather than failing silently and unpredictably per-transfer.

### Proof of Concept
1. Deploy (via `pallet-revive`) an ERC-20-like contract whose `transfer(address,uint256)` performs the balance update correctly but does not return a `bool` (e.g., returns nothing, or returns `uint256`) — exactly as done in the repo's own fixture `MyTokenFake` used by `smart_contract_does_not_return_bool_fails`.
2. Register this contract's address as an `AccountKey20` asset recognized by the asset-hub-westend `ERC20Transactor`/`Matcher`.
3. Submit `PolkadotXcm::execute` with a `WithdrawAsset`/`DepositAsset` program referencing this asset, as in: [7](#0-6) 
4. Observe the XCM execution fails with `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")`, for every such attempt, permanently, for this asset.
