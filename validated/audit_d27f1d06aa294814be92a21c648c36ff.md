### Title
Unbounded array allocation from an attacker-controlled length word before validation, causing OOM DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract (and other TVM precompiles that decode dynamic ABI arrays) use helper methods `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` to parse attacker-supplied calldata into Java arrays. Each of these methods reads a length word directly from the raw contract-call `data` and immediately uses it to size a Java array (`new byte[len][]`) before any bound check against a sane maximum or against the sender-controlled `data.length` is performed. This mirrors the libarchive `apply_substitution` bug class in CVE-2025-60753: a crafted length value drives an allocation whose size is never validated, leading to an out-of-memory condition.

### Finding Description
`extractBytesArray` and `extractSigArray` read `len` from `words[offset].intValueSafe()` and allocate arrays sized by that value with no upper bound check: [1](#0-0) [2](#0-1) 

`extractBytes32Array` has the identical pattern: [3](#0-2) 

These helpers are used by the `ValidateMultiSign` precompiled contract, which declares a `MAX_SIZE = 5` constant intended to cap the number of signatures/messages, but the constant is only referenced for energy accounting (`getEnergyForData`), not enforced inside the extraction helpers themselves: [4](#0-3) 

Because `intValueSafe()` can return any positive `int` up to `Integer.MAX_VALUE` from attacker-controlled calldata, calling this precompile (reachable via `STATICCALL`/`CALL` from any deployed smart contract, i.e. by any unprivileged transaction broadcaster) with a crafted length word causes the JVM to attempt allocating an oversized `byte[][]` array immediately, before any real bound/format validation such as `isValidAbiEncoding` is checked against the true length of `data`: [5](#0-4) 

### Impact Explanation
An oversized allocation request in these hot paths can throw `OutOfMemoryError` at the JVM level. Depending on how the VM interpreter/precompiled-contract dispatcher catches exceptions, this can either be absorbed as a reverted transaction (mostly a wasted-energy DoS) or, in the worst case, escape as an uncaught `Error` and destabilize/crash the node process, since `OutOfMemoryError` is a JVM `Error`, not a checked `Exception`, and is not guaranteed to be caught by ordinary `try/catch (Exception e)` blocks in the VM call chain. A crash of the node process while executing a broadcast transaction is a denial-of-service that fits the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The precompiled contract is reachable from any smart contract via a single `STATICCALL`/`CALL` invocation triggered by an unprivileged transaction, requiring no special privileges. The attacker only needs to control the ABI-encoded length word passed to the `ValidateMultiSign` precompile call data.

### Recommendation
Add explicit bound checks (e.g., `len <= MAX_SIZE` and `len >= 0`, and `len` consistent with `data.length`) in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` before allocating any array, returning a failure `Pair` instead of allocating when the length is out of range — mirroring how `isValidAbiEncoding` validates encoding shape, but doing so before, not after, allocation.

### Proof of Concept
Deploy a contract that performs a `STATICCALL` to the `ValidateMultiSign` precompiled contract address, crafting the input word at the relevant offset (the length field consumed by `extractSigArray`/`extractBytesArray`) to a very large positive value (e.g., close to `Integer.MAX_VALUE`) while keeping the rest of the call data minimal. Because `len` is used directly in `new byte[len][]` before any validation against `MAX_SIZE` or `data.length`, this triggers a large-memory allocation attempt during precompile execution.

**Note on confidence:** I was not able to fully trace the exact execution order inside `ValidateMultiSign.execute()` (i.e., whether `isValidAbiEncoding`/`MAX_SIZE` checks run before or after the call to `extractSigArray`/`extractBytesArray`) due to index truncation of the file; the snippets retrieved consistently show the extraction helpers allocating before validating, but a full read of the `execute()` method body would be needed to conclusively rule out an earlier guard. If a Devin session with full file access confirms an earlier bound check gates the call, this finding should be downgraded accordingly.
