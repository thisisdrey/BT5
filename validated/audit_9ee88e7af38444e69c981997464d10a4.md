### Title
RewardsDistributor credits borrower rewards on interest-inflated debt balance retroactively, draining the reward pool - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` computes a user's accrued rewards as `token_.balanceOf(account_).wadMul(deltaIndex)`, using the balance at *claim/update time* against an index range covering a past period. For `DebtToken`, `balanceOf` is not a stored value — it is `principalOf * _debtIndex / debtIndexOf` and grows every second as interest accrues (`contracts/DebtToken.sol:196-206`). Because interest accrual changes balances without calling `updateBeforeMintOrBurn`, a borrower earns rewards on debt balance that did not exist during the accrual window — the same bug class as the Drips finding (extracting payout for a position/period that never had backing). This silently dilutes all other reward earners and over-drains the distributor's reward token balance.

### Finding Description
- `RewardsDistributor._calculateTokenDelta` reads `balanceOf(account_)` at the moment of accrual and multiplies it by the full `_tokenIndex - _accountIndex` delta (`contracts/RewardsDistributor.sol:230`).
- `DebtToken.balanceOf` returns principal scaled by the live `debtIndex`, i.e. it grows continuously with interest (`contracts/DebtToken.sol:196-205`); `accrueInterest` mutates `debtIndex`/`totalSupply_` with no rewards hook (`contracts/DebtToken.sol:156-180`).
- The rewards checkpoint hooks (`updateBeforeMintOrBurn`/`updateBeforeTransfer`) only run inside `_mint`/`_burn`/transfers (`contracts/DebtToken.sol:114-121`, `525`, `577`). Interest growth between two checkpoints is invisible to the distributor, so it is priced at the *end-of-period* balance.
- Result: rewards for window `[t0, t1]` are computed as if the user held `balance(t1)` the whole time, crediting rewards on accrued interest that was never a live balance. `updateBeforeMintOrBurn` is permissionless, and `claimRewards` is callable by anyone for anyone (`contracts/RewardsDistributor.sol:150-168`), so the inflation is immediately realizable.

### Impact Explanation
Borrowers on DebtTokens listed in `tokenSpeeds` (borrower incentives are explicitly supported — the `onlyIfTokenExists` modifier accepts DebtTokens, and tests set speeds on debt tokens) are systematically overpaid. The overpayment scales with `interestRate * elapsed` and compounds across long claim gaps. The excess comes out of the distributor's reward-token balance, stealing yield legitimately accrued by other suppliers/borrowers (theft of unclaimed yield). Unlike the Drips PoC this does not empty the contract in one tx, but it is a persistent, attacker-amplifiable leak: maximize borrowed amount, let interest accrue, claim.

### Likelihood Explanation
Requires only: a DebtToken with non-zero `interestRate` and non-zero `tokenSpeed` in a registered RewardsDistributor, plus the attacker holding a debt position. All are normal deployed configurations. The inflation is automatic for every such borrower — no special timing needed — and an attacker maximizes it by taking the largest borrow their collateral allows and delaying claims.

### Recommendation
Accrue rewards using the same checkpointed balance the debt accounting uses. Options: have `DebtToken.accrueInterest` push a rewards update per account is impractical, so instead base the delta on `principalOf` (or snapshot balance at checkpoint time) rather than live `balanceOf`, or have `RewardsDistributor` integrate `principalOf`-style accounting for debt tokens so interest growth does not retroactively earn rewards. At minimum, document/cap the drift or update the account index whenever `accrueInterest` runs (e.g. call `updateBeforeMintOrBurn` for tracked borrowers, or make `claimRewards`/`_updateTokenIndex` snapshot via `accrueInterest`-aware virtual balances consistently for all accounts).

### Proof of Concept
Hardhat test sketch (mirroring `test/RewardDistributor.test.ts` structure, real contracts):

```ts
// setup: distributor registered on pool, speed set on msUSDDebt, rewardToken funded
await rewardDistributor.updateTokenSpeed(msUSDDebt.address, parseEther('1'))
await msUSDDebt.updateInterestRate(parseEther('1')) // 100% APR for clarity

// alice deposits collateral and borrows
await met.mint(alice.address, parseEther('10000'))
await met.connect(alice).approve(msdMET.address, MaxUint256)
await msdMET.connect(alice).deposit(parseEther('10000'), alice.address)
await msUSDDebt.connect(alice).issue(parseEther('1000'), alice.address)

// index checkpoint for alice (balance 1000 at t0)
await rewardDistributor.updateBeforeMintOrBurn(msUSDDebt.address, alice.address)

await time.increase(time.duration.years(1)) // debt balance ~2000 at t1
await msUSDDebt.accrueInterest()

// expected fair reward: integral of balance over time * speed/supply share < 2000-equivalent
// actual: tokensDelta = balanceOf(t1) * deltaIndex, i.e. rewards priced as if
// alice held ~2000 for the whole year instead of a balance growing 1000 -> 2000
const claimable = await rewardDistributor['claimable(address)'](alice.address)
// claimable exceeds the time-integrated entitlement; the excess is drawn
// from rewardToken balances owed to other users
await rewardDistributor['claimRewards(address)'](alice.address)
```

The discrepancy grows with interest rate and elapsed time; comparing `claimable` against a manual time-weighted integration of `balanceOf` (or against a second borrower who repays/re-borrows each block to checkpoint frequently) shows the systematic over-credit.
