### Title
`accrueInterest()` grows `totalSupply_` past `maxTotalSupply` without the `SurpassMaxDebtSupply` check enforced in `_mint` - ([File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
The Tokemak finding describes an invariant check present on the primary mutating path (`stake()`) but missing on a secondary path that mutates the same bounded state (`extend()`). The same pattern exists in Metronome's `DebtToken`: every mint path (`issue`, `mint`, flash-leverage debt minting) funnels through `_mint()`, which enforces `totalSupply_ + amount <= maxTotalSupply`, but `accrueInterest()` — a permissionless function that also increases `totalSupply_` — performs no such check. The `maxTotalSupply` debt ceiling can therefore be exceeded purely through interest accrual.

### Finding Description
`DebtToken._mint()` enforces the supply cap:

```solidity
// contracts/DebtToken.sol
totalSupply_ += amount_;
if (totalSupply_ > maxTotalSupply) revert SurpassMaxDebtSupply();
```

`accrueInterest()` is a public, unprivileged function that adds accrued interest directly to `totalSupply_` with no cap check:

```solidity
// contracts/DebtToken.sol
function accrueInterest() public override {
    ...
    if (_interestAmountAccrued > 0) {
        totalSupply_ += _interestAmountAccrued;   // <-- no maxTotalSupply check
        debtIndex = _debtIndex;
        try syntheticToken.mint(pool.feeCollector(), _interestAmountAccrued + pendingInterestFee) {
            pendingInterestFee = 0;
        } catch {
            pendingInterestFee += _interestAmountAccrued;
        }
    }
}
```

The inline comment even acknowledges the dependency ("states where minting will fail (e.g. ... it reached max supply)"), but the debt-token side of the invariant is never enforced. Once `totalSupply_` exceeds `maxTotalSupply`, every subsequent call to `issue()` and `mint()` (used by `SmartFarmingManager` leverage) reverts inside `_mint()` with `SurpassMaxDebtSupply`, even for amounts that a user would reasonably expect to be allowed.

Additionally, the interest-mint to `feeCollector` goes through `SyntheticToken._mint()`, which enforces the synthetic token's own `maxTotalSupply`. When that mint reverts, the fee is parked in `pendingInterestFee` and later retried via `collectPendingInterestFee()` — which calls the same reverting `mint`, so the fee can remain permanently uncollectable while the debt supply stays inflated.

### Impact Explanation
- **Broken invariant:** `totalSupply() <= maxTotalSupply` is a governor-configured debt ceiling; `accrueInterest()` violates it without any privileged action.
- **Temporary freezing of functionality / liveness:** after the cap is exceeded, all debt issuance (`issue()`, `SmartFarmingManager` leverage via `DebtToken.mint`/`flashIssue`) reverts until enough debt is repaid to bring `totalSupply_` back under the cap. Users with sufficient collateral are blocked from borrowing.
- **Fee accrual desynchronization:** `totalSupply_` grows (increasing every debtor's `balanceOf` via the debt index) while the corresponding synthetic token mint to the fee collector can silently fail, leaving `pendingInterestFee` stuck if the synthetic cap is also reached.

### Likelihood Explanation
- `accrueInterest()` is permissionless and is invoked on nearly every debt operation, so the overflow triggers organically whenever issuance brings supply near the cap and time passes. An unprivileged attacker can also call `accrueInterest()` directly to push `totalSupply_` over the cap at the exact moment it crosses.
- No modifier prevents it: `accrueInterest` has no `whenNotShutdown`/cap guard, and `interestRate > 0` is the only requirement.
- Severity is bounded: repaying debt (`repay`/`repayAll`/`liquidate`) reduces `totalSupply_` and restores issuance, so the freeze is temporary and requires supply near the configured cap.

### Recommendation
Enforce the same cap inside `accrueInterest()` (or bound the accrued amount so the cap is never exceeded):

```solidity
// contracts/DebtToken.sol — accrueInterest()
uint256 _newTotalSupply = totalSupply_ + _interestAmountAccrued;
if (_newTotalSupply > maxTotalSupply) {
    _interestAmountAccrued = maxTotalSupply - totalSupply_; // or revert
    _newTotalSupply = maxTotalSupply;
}
totalSupply_ = _newTotalSupply;
```

Alternatively, revert with `SurpassMaxDebtSupply()` so the breach is explicit rather than silent. Note that reverting would brick all debt operations (since they all call `accrueInterest`), so capping the accrual at `maxTotalSupply` is the safer fix, applied consistently in `_calculateInterestAccrual`/`totalSupply()` as well to keep view functions consistent.

### Proof of Concept
Foundry fork/unit sketch (repo uses Hardhat; the same works under `forge` with the repo's `foundry.toml`):

```solidity
function testAccrueInterestExceedsMaxDebtSupply() public {
    // Setup: pool, depositToken (e.g. msUSD collateral), debtToken (msETH debt),
    // governor sets debtToken.maxTotalSupply = 1000 ether

    // 1. User deposits collateral and issues debt up to the cap
    depositToken.deposit(collateralAmount, alice);
    debtToken.issue(999 ether, alice); // totalSupply_ = 999e18 <= maxTotalSupply

    // 2. Time passes; interest accrues
    vm.warp(block.timestamp + 365 days);

    // 3. Anyone calls accrueInterest — no cap check
    debtToken.accrueInterest();

    // 4. Invariant broken: totalSupply exceeds maxTotalSupply
    assertGt(debtToken.totalSupply(), debtToken.maxTotalSupply());

    // 5. All new issuance now reverts even though debtors can still repay
    vm.expectRevert(SurpassMaxDebtSupply.selector);
    debtToken.issue(1 ether, bob);
}
```
