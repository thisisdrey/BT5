### Title
Unbounded allocation from unsanitized array-length words in `ValidateMultiSign`/`BatchValidateSign` precompiles when `allowTvmSelfdestructRestriction` is not active - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode attacker-controlled ABI words from contract call data and use them directly as array lengths to allocate Java arrays (`extractBytesArray`, `extractBytes32Array`) before any size bound is enforced, unless the `allowTvmSelfdestructRestriction` hard-fork flag is active. This mirrors the CWE-400/125 pattern in the referenced `https-proxy-agent` advisory: an unsanitized, attacker-supplied length is passed straight into a buffer/array allocation.

### Finding Description
`ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` parse the call data into `DataWord[] words` and only apply a `MAX_SIZE` bound check on the decoded array length when `VMConfig.allowTvmSelfdestructRestriction()` returns true: [1](#0-0) 

When that flag is false, execution falls through to `extractBytesArray`, which allocates a `byte[][]` sized directly from an attacker-controlled `DataWord`: [2](#0-1) 

`extractBytes32Array` (used for the `addresses` array in `BatchValidateSign`) is called unconditionally, with no size guard at all regardless of the flag: [3](#0-2) [4](#0-3) 

The same pattern exists in `BatchValidateSign.doExecute()`, where the `MAX_SIZE` check is likewise conditioned on `allowTvmSelfdestructRestriction()`: [5](#0-4) 

### Impact Explanation
If `allowTvmSelfdestructRestriction` is not yet activated on a given network (this is a hard-fork/committee-controlled `Snapshot` flag read via `VMConfig.current()`), any unprivileged account can call the `ValidateMultiSign`/`BatchValidateSign` precompile address with crafted call data whose length-word is a very large value (up to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt a multi-gigabyte allocation. This can throw `OutOfMemoryError` on the node processing the transaction, potentially crashing or destabilizing it — a denial-of-service condition directly analogous to the `https-proxy-agent` `Buffer()` DoS.

### Likelihood Explanation
I could not verify from the available index whether `allowTvmSelfdestructRestriction` is already permanently activated (hard forks in java-tron are typically one-way/committee-triggered and, once turned on, cannot be reverted). If it is already active on all live networks (mainnet/Nile/testnets), this path is dead code and not exploitable today. I was unable to find the default/current activation value or the proposal that toggles this flag within the indexed files (`chainbase/.../DynamicPropertiesStore.java` and `actuator/.../ProposalUtil.java` reference it but their bodies were not surfaced in my searches), so I cannot confirm current reachability with certainty.

### Recommendation
Enforce the `MAX_SIZE` bound on decoded array lengths unconditionally (not gated behind `allowTvmSelfdestructRestriction`) in both `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`, and add the same guard before calling `extractBytesArray`/`extractBytes32Array` regardless of feature-flag state, so an attacker cannot force an unbounded allocation via a crafted length word.

### Proof of Concept
Uncertain/not fully verifiable from the index — I could not confirm the current on-chain value of `allowTvmSelfdestructRestriction`, so I cannot construct a concrete PoC transaction that is guaranteed exploitable on a live deployment today. If the flag is inactive, the PoC would be: deploy/trigger a contract that `CALL`s the `ValidateMultiSign` precompile address with ABI-encoded data where the signature-array length word (at the offset pointed to by `words[3]`) is set to a huge value (e.g., `0x7FFFFFFF`), causing `extractBytesArray` to attempt `new byte[0x7FFFFFFF][]`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
