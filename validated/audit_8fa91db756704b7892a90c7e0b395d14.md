### Title
Duplicate Vote-Address Entries in a Single VoteWitnessContract Are Not Deduplicated - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
An unprivileged account broadcasting a `VoteWitnessContract` can include multiple `Vote` entries that target the same witness (`vote_address`) within one transaction. `VoteWitnessActuator.validate()` sums up the individual `voteCount` values correctly for the tron-power check, but `countVoteAccount()` (called from `execute()`) never merges votes that share the same `vote_address` before writing them into the account's and votes' repeated fields.

### Finding Description
In `VoteWitnessActuator.countVoteAccount()`, votes from the transaction are applied one-by-one with no de-duplication by address: [1](#0-0) 

This is different from the TVM-native equivalent, `VoteWitnessProcessor.execute()`, which explicitly builds a `Map<ByteString, Long> voteMap` to merge multiple votes for the same witness before persisting: [2](#0-1) 

The comment `// merge vote for same witness` in the VM path confirms that duplicate vote addresses for the same witness are an anticipated and previously handled case elsewhere in the codebase — but the actuator path handling regular (non-VM) `VoteWitnessContract` transactions omits this merge step. `validate()` only checks each vote's address validity, count positivity, and the total sum against `tronPower`; it never rejects duplicate `vote_address` entries: [3](#0-2) 

Because `accountCapsule.addVotes(...)` and `votesCapsule.addNewVotes(...)` are invoked once per `Vote` entry in the transaction (rather than once per unique witness address with a merged count), a transaction with duplicate `vote_address` entries results in multiple separate `Vote` records for the same witness being appended to the account's persisted `votes` list and to `VotesCapsule`'s `new_votes` list, instead of a single merged record. I was unable to fully confirm within the available context whether `AccountCapsule.addVotes` / `VotesCapsule.addNewVotes` perform any internal merging by address (the read of `AccountCapsule.java` and `VotesCapsule.java` implementations did not complete before the tool budget was exhausted), so it is uncertain whether this produces duplicate list entries or an in-place merge. If they simply append (as the sibling code path's explicit merge logic strongly suggests is necessary), this creates duplicate `Vote` entries with the same address in on-chain state.

### Impact Explanation
If duplicate entries are persisted, downstream consumers that assume one `Vote` entry per witness per account — such as `MaintenanceManager.countVote()` (used during DPoS maintenance to tally witness vote deltas) and `PrecompiledContracts.VoteCount` (a TVM precompile reachable by any contract) — would process each duplicate independently. `MaintenanceManager.countVote()` sums `getOldVotes()`/`getNewVotes()` per address via `Map<ByteString, Long>` accumulation, so duplicate entries for the same address would still sum correctly there; however, other consumers such as `Wallet.getPaginatedNowWitnessList()`'s `countVote()` and `PrecompiledContracts.VoteCount.execute()` also aggregate per-vote entries, so functionally the effect may be limited to redundant data rather than a crash. Given the uncertainty in confirming the exact data-structure semantics, I cannot assert with confidence that this reaches a "node crash," "unbacked balance," or "unauthorized fund theft" bar required by the validation rules.

### Likelihood Explanation
Any account holder can trigger this by crafting a `VoteWitnessContract` with two or more `Vote` entries pointing at the same valid witness address and total vote count within their tron power — no special privileges are required, and `validate()` does not reject such a transaction.

### Recommendation
Add deduplication/merging of votes by `vote_address` in `VoteWitnessActuator.countVoteAccount()` (mirroring the `voteMap` merge logic in `VoteWitnessProcessor.execute()`), or reject transactions containing duplicate `vote_address` entries in `validate()`.

### Proof of Concept
Not fully verifiable from the indexed context: constructing a `VoteWitnessContract` with two `Vote` entries for the identical `vote_address` and observing the persisted `AccountCapsule.votesList` / `VotesCapsule.newVotesList` after `execute()` would confirm whether duplicate records are stored (as opposed to merged). This requires running the actuator against a live `AccountStore`/`VotesStore`, which was not available in this read-only investigation.

**Note:** Due to index size limits, the full implementations of `AccountCapsule.addVotes` and `VotesCapsule.addNewVotes` in `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` and `chainbase/src/main/java/org/tron/core/capsule/VotesCapsule.java` were not retrievable in this session. Confirming the exact severity (duplicate storage vs. no-op merge, and whether any consumer crashes on duplicates) requires a full Devin session with direct file access to verify these methods and trace all consumers of `getVotesList()`/`getNewVotes()`.
