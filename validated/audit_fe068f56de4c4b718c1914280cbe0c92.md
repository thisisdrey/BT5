### Title
Postponed receipts and pending-data-count entries survive `DeleteAccount`, allowing a stale self-authorized action (e.g. `AddFullAccessKey`) to execute against a later-recreated account under a different owner - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) deletes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed to the same `account_id`. If an account deletes itself while a postponed multi-`input_data_ids` action receipt targeting it is still pending, that postponed receipt survives the deletion and later fires against whatever account currently occupies that `account_id`, because `apply_action_receipt`/`check_actor_permissions` only compare string account IDs (`predecessor_id == receiver_id`), not any notion of "account incarnation."

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and sets `*account = None`, but it does not scan for or purge any `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` records for `account_id`: [1](#0-0) [2](#0-1) 

Meanwhile, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores a self-targeted `ActionReceipt` with two `input_data_ids` as a `PostponedReceipt`/`PendingDataCount{value=2}` keyed by `receiver_id = account_id`: [3](#0-2) 

Later, incoming `Data` receipts decrement `PendingDataCount` purely by `(receiver_id, receipt_id)` lookup, and once it reaches zero, fetch and execute the stored postponed receipt via `apply_action_receipt`, without re-validating that the account referenced still corresponds to the same "incarnation" that existed when the postponed receipt was created: [4](#0-3) 

Because the `ActionReceipt`'s `predecessor_id`/`receiver_id` fields are frozen at receipt-creation time, `check_actor_permissions`'s self-check (`actor_id == account_id`, as seen for `DeleteAccount` at `runtime/runtime/src/actions.rs:761-768`, and used analogously for `AddKey`/`DeployContract`) is satisfied purely from the stale string identity, regardless of whether the account was deleted and recreated (possibly under new ownership) in between. `remove_account`'s lack of cleanup for `PostponedReceipt`/`PendingDataCount` is the root cause that lets a queued privileged action outlive the account incarnation that authorized it, violating the stated invariant that a promise must never carry privileges its creator did not hold in the *current* incarnation.

### Impact Explanation
If `account_id` is deleted and later recreated by a different, unrelated party (e.g., a `near`-registrar re-issuing a top-level name after expiry/reclaim, or a legitimate re-registration of a subaccount name), the surviving `PendingDataCount`/`PostponedReceipt` entries can still be triggered by delivering the last missing `Data` receipt. This executes the stale actions (e.g., `AddFullAccessKey`, `DeployContract`) against the *new* account, granting the old account's promise-chain author access/control the new owner never authorized. This is an authorization-escalation-across-account-incarnations bug, matching NEAR's "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Exploitability requires: (1) the ability to self-trigger a multi-`input_data_ids` action receipt on one's own account before deleting it — cheap and fully attacker-controlled; (2) delaying delivery of the final `DataReceipt` until after `DeleteAccount`; (3) the account name being recreated afterward. Step (3) is the main constraint: for `.near` subaccounts, only the parent account (the registrar) can issue `CreateAccount` for that exact name (`action_create_account`, `is_sub_account_of` check), while NEAR-implicit accounts can be deterministically recreated by anyone holding the corresponding private key. This limits the "cross-owner" variant primarily to scenarios involving account-name reclamation/re-registration by a registrar or a parent account transferring/reissuing a subaccount name — a realistic but not universally-applicable precondition. The bug itself (orphaned trie entries) is deterministically reproducible regardless of whether a hostile re-owner ever appears.

### Recommendation
In `remove_account` (or in `action_delete_account` before calling it), also scan and remove any `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries whose `receiver_id == account_id`, mirroring the existing access-key/contract-data cleanup loops. Alternatively, bind postponed-receipt resolution to an account "incarnation" identifier (e.g., a monotonically increasing per-account creation nonce) so a `Data` receipt delivered after account resurrection cannot resolve a `PendingDataCount`/`PostponedReceipt` created under a prior incarnation.

### Proof of Concept
Integration test plan (in `runtime/runtime/src/tests/apply.rs` style, similar to `test_promise_input_size_limit_exceeded_fails_and_cleans_up` and `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create `victim.near` with a full access key; send it a self-`ActionReceipt` (`predecessor_id == receiver_id == victim.near`) with `input_data_ids = [d1, d2]` and actions `[AddKey(AddFullAccessKeyAction{new_pubkey})]`.
2. Apply chunk: assert `TrieKey::PendingDataCount{victim.near, receipt_id}` and `TrieKey::PostponedReceipt{victim.near, receipt_id}` exist in the resulting trie.
3. Send `DeleteAccount(victim.near, beneficiary)` from `victim.near` (with zero locked stake) in a subsequent chunk; apply and commit.
4. **Assertion A (expected failure in current code)**: `get_postponed_receipt(&state, &victim.near, receipt_id)` should be `None` after deletion — currently it remains `Some`.
5. Recreate `victim.near` (e.g., via registrar `CreateAccount`, or use a NEAR-implicit account name recreated via `Transfer` for a simpler PoC) without adding `new_pubkey`.
6. Deliver the `Data` receipt for `d1` then `d2` (the final one, driving `PendingDataCount` to 0).
7. **Assertion B**: query `get_access_key(&state, &victim.near, &new_pubkey)` — if `Some`, the stale `AddFullAccessKey` action executed against the freshly recreated account despite the new incarnation never having authorized it, confirming the vulnerability.
