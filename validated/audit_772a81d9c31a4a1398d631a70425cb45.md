### Title
Missing length validation in ZIP central-directory parsing causes out-of-bounds reads — (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's zip reader trusts attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and the nested extra-field `header_id`/`data_size` pairs read straight out of a memory-mapped, attacker-supplied `.zip`/`.jar` file, and advances its read cursor by those amounts with **no bounds check against the mapped file's actual length**. This is the same defect class as CVE-2022-46344 (X.Org `XIChangeProperty`): a length field taken from untrusted input is used to walk/read memory without validating it stays within the buffer, leading to out-of-bounds reads / potential information disclosure (and possibly a crash).

### Finding Description
`third_party/ijar/zip.cc` has two central parsing routines:

- `InputZipFile::ProcessLocalFileEntry` (lines 332–418) is careful: before trusting `file_name_length_`/`extra_field_length_`, it calls `EnsureRemaining()` [1](#0-0) , which checks the value against `input_file_->Length()` before advancing `p` [2](#0-1) .

- `InputZipFile::ProcessCentralDirEntry` (lines 493–545), by contrast, reads `file_name_length`, `extra_field_length`, `file_comment_length` directly from the central directory bytes and immediately does `p += file_name_length;`, `p += extra_field_length;` and later `p += file_comment_length;` with **no equivalent `EnsureRemaining`/bounds check** [3](#0-2) . It then walks the extra-field records with `while (extra_p != p) { header_id = get_u2le(extra_p); data_size = get_u2le(extra_p); extra_p += data_size; ... }`, again with no check that `extra_p`/`extra` stay inside the mapped buffer, and if `header_id == ZIP64_EXTRA_FIELD_TAG` it reads 8-byte values via `get_u8le(extra)` from whatever memory `extra` happens to point at [4](#0-3) .

The comment at line 491 ("Note that the central directory is always followed by another data structure that has a signature, so parsing it this way is safe") is the load-bearing but incorrect assumption — it does not hold once `file_name_length`/`extra_field_length`/`file_comment_length` are crafted to be larger than the remaining bytes actually present in the mapped input file, at which point `p`/`extra_p` walk past the end of `zipdata_in_ + input_file_->Length()` into unrelated process memory.

The buffer being parsed is a memory-mapped, attacker-controlled file (`MappedInputFile`), opened via `InputZipFile::Open()` [5](#0-4) , and `ProcessCentralDirEntry` is invoked in the main entry-processing loop `ProcessNext()` [6](#0-5)  as well as in `CalculateOutputLength()` [7](#0-6) . The `offset`, `*compressed_size`, `*uncompressed_size` values derived from this unchecked parsing are subsequently used to compute the pointer for reading the "local file" entry (`p = zipdata_in_ + in_offset_ + offset;`) [8](#0-7) , meaning out-of-bounds/garbage values read here can further steer downstream parsing.

ijar is Bazel's own native zip/jar tool, used (per `java_common.mdx`/build-tools tests) to produce interface jars from `.jar` inputs that flow through the Java build graph — inputs that can originate from an attacker-published archive (e.g. a `.jar` fetched via `http_jar`/`http_file`/a Maven-style dependency, or committed on an untrusted branch that CI builds). This satisfies the "attacker publishes bytes a victim's build consumes" model without needing MITM or credential access.

### Impact Explanation
An out-of-bounds read past the mmap'd input file lets an attacker-crafted `.jar`/`.zip` cause ijar to read adjacent process memory (heap/other mapped pages) as if it were legitimate ZIP length/offset/size fields. Best case this crashes the process (SIGSEGV when it walks off a mapped page); worst case, the OOB bytes read (as `compressed_size`, `uncompressed_size`, `offset`, or as raw filename bytes copied via `memcpy`) can leak adjacent process memory content into subsequent processing/derived filenames, or can misdirect the parser into reading further out-of-bounds regions of the file. This matches the CVE-2022-46344 class: missing length validation on an attacker-supplied field results in OOB reads and potential information disclosure, rather than a bounded, contained failure.

### Likelihood Explanation
No integrity check, sandboxing, or size-fencing exists between the raw central-directory bytes and the pointer arithmetic in `ProcessCentralDirEntry` — the bug is purely a missing bounds check in first-party C++ code, triggered on ordinary `.jar` parsing paths that are already reachable from externally-sourced archives consumed by Bazel Java tooling. No privileged access, credentials, or MITM position is required — a hostile origin serving/publishing a crafted `.jar` is sufficient once it is fed into ijar (e.g., as an interface-jar-producing action).

### Recommendation
Add the same defensive bound-checking used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before dereferencing/advancing `p` or `extra_p` by any length read from the file (`file_name_length`, `extra_field_length`, `file_comment_length`, `data_size`), verify the resulting pointer does not exceed `zipdata_in_ + input_file_->Length()` (or an explicit "central directory end" bound), and fail parsing with an error rather than continuing. The extra-field walking loop additionally needs a check that `data_size` doesn't cause `extra_p` to exceed the declared extra-field region and that `extra + 8 <= extra_p_end` before calling `get_u8le`.

### Proof of Concept
Construct a minimal ZIP/JAR whose single central directory entry declares:
- `file_name_length` = e.g. `0xFFFF`, or
- `extra_field_length` = e.g. `0xFFFF` with the actual file truncated shortly after the CDH fixed fields,

so that the real file is only a few hundred bytes but the declared lengths claim tens of thousands of trailing bytes. Feed this file to `ijar`/`zipper` (`third_party/ijar/zip_main.cc`) or to any Bazel action that runs the ijar binary over a `.jar` input. Because `ProcessCentralDirEntry` never calls `EnsureRemaining()` for these fields (unlike `ProcessLocalFileEntry`), `p`/`extra_p` walk past `input_file_->Length()` and the process reads/derefs memory beyond the `mmap`'d region — observable as a crash (ASan: heap/mmap "SEGV on unknown address" or "READ of size N" past `zipdata_in_ + Length()`) or as bogus size/offset values propagated into subsequent parsing. A `BuildIntegrationTestCase`/`src/test/shell` reproduction would build such a crafted `.jar`, run it through the existing `third_party/ijar/test/zip_test.sh` harness (which already tests malformed-archive handling, e.g. `test_no_path_traversal`) with ASan/UBSan-instrumented `zipper`/`ijar` binaries, and assert no OOB access occurs.

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
