### Title
Missing overflow/range check on frozen-duration derived expire time in `FreezeBalanceProcessor` (TVM native freeze) - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java])

### Summary
The CVE fixes a class of bug where a user/caller-supplied duration/time value is used directly in a downstream arithmetic/hardware operation without first validating that it is within a sane, non-overflowing range. The same bug class exists in java-tron's freeze-resource native contract: `FreezeBalanceProcessor.execute()` computes an expire time by multiplying an unvalidated duration by a constant and adding it to the current time, with no overflow guard, even though the exact same computation elsewhere in the codebase (`AssetIssueActuator`) was hardened with an explicit overflow check.

### Finding Description
In `FreezeBalanceProcessor.execute()`: [1](#0-0) 
the expire time is computed as `nowInMs + param.getFrozenDuration() * FROZEN_PERIOD`, and this value is then written into account/delegated-resource capsules via `setFrozenForBandwidth`/`setFrozenForEnergy`/`DelegatedResourceCapsule`. `FreezeBalanceProcessor.validate()` only checks `frozenBalance` bounds and `frozenCount`/resource type — it never validates `param.getFrozenDuration()` for range or for overflow when multiplied by `FROZEN_PERIOD`: [2](#0-1) 

This mirrors the legacy `FreezeBalanceActuator`, whose `execute()` performs the identical unchecked computation `long duration = freezeBalanceContract.getFrozenDuration() * FROZEN_PERIOD; long expireTime = now + duration;`: [3](#0-2) 
Its `validate()` only enforces the min/max frozen-time bounds when a test-only flag `needCheckFrozeTime` is enabled (`CommonParameter.getCheckFrozenTime() == 1`, commented `//for test`), meaning the range check is not unconditionally applied: [4](#0-3) 

By contrast, java-tron already recognizes and fixed this exact bug class elsewhere: `AssetIssueActuator.validate()` explicitly guards the analogous `startTime + frozenDays * FROZEN_PERIOD` computation with `StrictMathWrapper.addExact`, rejecting the transaction if it would overflow, with the comment "make sure FrozenSupply.expireTime not overflow": [5](#0-4) 
This demonstrates the project's own established mitigation pattern for this bug class was not consistently propagated to the freeze-resource actuator/processor, which is the direct analog of the kernel's missing `timespec64_valid_strict()` check being propagated to only some PTP drivers while others remained unguarded.

### Impact Explanation
If `frozenDuration` (attacker-controlled input in the `FreezeBalanceContract`/native freeze call) is large enough that `frozenDuration * FROZEN_PERIOD` overflows a `long`, or `now + duration` overflows, the resulting `expireTime` written into `AccountCapsule`/`DelegatedResourceCapsule` state can wrap to a negative or unexpectedly small value. Because unfreeze logic elsewhere in the codebase compares stored expire-time fields directly (`<=`/`>` against `now`), a corrupted (wrapped) expire time could make funds appear immediately unlockable or, conversely, permanently locked, and it also corrupts consensus-critical account state that must be deterministic and byte-identical across nodes. This falls into "unbacked balance / permanent freezing of funds / incorrect state" impact categories.

### Likelihood Explanation
Likelihood is uncertain from static analysis alone. `FreezeBalanceActuator` (`FreezeBalanceContract`) is explicitly disabled once freeze v2 is active on-chain (`if (dynamicStore.supportUnfreezeDelay()) throw ContractValidateException("freeze v2 is open, old freeze is closed")`), which likely already applies on current mainnet, reducing exploitability of that specific actuator. Whether the TVM-native `FreezeBalanceProcessor` path (invoked by Solidity `freezeForSelf`/`freezeForOther` opcodes) exposes `frozenDuration` as an attacker-controlled parameter, or always passes a protocol-fixed duration (e.g., `minFrozenTime`), could not be conclusively confirmed with the tools available in this session — this needs to be verified in `actuator/src/main/java/org/tron/core/vm/program/Program.java` (the `freezeBalance` TVM opcode implementation) before treating this as a directly exploitable, high-confidence finding.

### Recommendation
- Add the same overflow-safe guard used in `AssetIssueActuator` (`StrictMathWrapper.addExact` / `LongMath.checkedAdd`) to `FreezeBalanceProcessor.validate()` and `FreezeBalanceActuator.validate()` before computing `expireTime`, unconditionally (not gated behind a test-only flag).
- Confirm in `Program.java` whether `frozenDuration` passed into `FreezeBalanceParam` for the TVM `freezeForSelf`/`freezeForOther` opcodes originates from caller-controlled Solidity arguments; if so, bound it to `[minFrozenTime, maxFrozenTime]` and add an explicit overflow check identical to the `AssetIssueActuator` fix.
- Audit all other locations computing `now + X * FROZEN_PERIOD` (e.g., `UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime`, `UnfreezeBalanceV2Processor.calcUnfreezeExpireTime`) for the same missing-overflow-check pattern, since `unfreezeDelayDays` is a governance-controlled parameter rather than user input, likely lower risk, but should still be verified for consistency.

### Proof of Concept
Not fully constructible without confirming (a) whether the TVM `freezeForSelf`/`freezeForOther` opcode exposes `frozenDuration` as caller input, and (b) whether `FreezeBalanceContract` (legacy) can still be broadcast on the target network (pre freeze-v2 activation, or on private/test chains where `supportUnfreezeDelay()` is false). On a chain where `FreezeBalanceContract` is still enabled, a transaction with `frozenDuration` set to a value near `Long.MAX_VALUE / FROZEN_PERIOD` would cause `frozenDuration * FROZEN_PERIOD` in `FreezeBalanceActuator.execute()` (line 70) to overflow, producing a corrupted `expireTime` stored via `accountCapsule.setFrozenForBandwidth(...)`/`setFrozenForEnergy(...)`.
