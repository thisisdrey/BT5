### Title
Missing Time Limit on `MultisigAccountCreationMessage` Signature Allows Indefinitely Valid Stale Authorization — (`aptos-move/framework/aptos-framework/sources/multisig_account.move`)

---

### Summary

`create_with_existing_account` and `create_with_existing_account_and_revoke_auth_key` are `public entry` functions callable by **any** unprivileged sender. They accept a pre-signed `MultisigAccountCreationMessage` / `MultisigAccountCreationWithAuthKeyRevocationMessage` and verify it against the account's current sequence number. Neither struct contains a timestamp or deadline field. The only staleness guard is the sequence number, which only advances when the account itself sends a transaction. If the account owner signs the message, changes their mind, but never sends another transaction from that address, the signed message remains valid and executable by anyone who possesses it — indefinitely.

---

### Finding Description

Both proof-challenge structs are defined without any expiry field:

```move
struct MultisigAccountCreationMessage has copy, drop {
    chain_id: u8,
    account_address: address,
    sequence_number: u64,   // only staleness guard
    owners: vector<address>,
    num_signatures_required: u64,
    // ← no deadline / timestamp
}
```

The in-code comment even acknowledges the intent:

> *"Sequence number is not needed for replay protection as the multisig account can only be created once. But it's included to ensure timely execution of account creation."*

The sequence number is a weak proxy for time: it only increments when the account sends a transaction. A cold or low-activity account may go months or years without incrementing its sequence number, leaving any previously signed creation message permanently valid.

The verification path in `create_with_existing_account` (lines 634–647) and `create_with_existing_account_and_revoke_auth_key` (lines 715–728) reconstructs the challenge from live chain state and calls `account::verify_signed_message`. There is no timestamp comparison anywhere in this path. [1](#0-0) [2](#0-1) [3](#0-2) 

---

### Impact Explanation

**`create_with_existing_account`**: An attacker who possesses a stale signed message can call this public entry function at any future time (as long as the account's sequence number has not changed), creating a multisig account with the originally-signed owner set and threshold. The multisig owners gain the ability to execute arbitrary transactions on behalf of the victim account.

**`create_with_existing_account_and_revoke_auth_key`**: The same attack additionally rotates the account's authentication key to `0x0` and revokes any outstanding signer/rotation capability offers. The victim permanently loses auth-key-based access to their account. Control is transferred exclusively to the multisig owners specified in the stale message. [4](#0-3) 

---

### Likelihood Explanation

- Both functions are `public entry`, callable by any unprivileged account on mainnet.
- The signed message is produced off-chain and transmitted to a co-signer or service; interception or retention by a malicious party is realistic.
- Cold wallets and low-activity accounts (staking accounts, vesting accounts, DAO treasuries) may not increment their sequence number for extended periods, leaving the window open indefinitely.
- The account owner has no on-chain mechanism to invalidate the signed message other than sending an unrelated transaction to advance the sequence number — a non-obvious remediation step.

---

### Recommendation

Add an explicit `expiration_timestamp_secs: u64` field to both structs and enforce it inside the verification logic:

```move
struct MultisigAccountCreationMessage has copy, drop {
    chain_id: u8,
    account_address: address,
    sequence_number: u64,
    owners: vector<address>,
    num_signatures_required: u64,
    expiration_timestamp_secs: u64,   // ← add this
}
```

In `create_with_existing_account` and `create_with_existing_account_and_revoke_auth_key`, add before calling `account::verify_signed_message`:

```move
assert!(
    timestamp::now_seconds() <= proof_challenge.expiration_timestamp_secs,
    error::invalid_argument(ESIGNATURE_EXPIRED)
);
```

A reasonable maximum window (e.g., 3600 seconds) should be enforced, consistent with how orderless transactions cap their expiry at `MAX_EXP_TIME_SECONDS_FOR_ORDERLESS_TXNS`. [5](#0-4) 

---

### Proof of Concept

1. Alice holds account `A` with sequence number `N` and signs a `MultisigAccountCreationWithAuthKeyRevocationMessage` committing owners `[Mallory]` and threshold `1`, intending to migrate to multisig.
2. Alice shares the signed bytes with Mallory as part of a setup flow, then changes her mind and abandons the migration — but does not send any transaction from `A` (sequence number remains `N`).
3. Six months later, Mallory calls:
   ```
   create_with_existing_account_and_revoke_auth_key(
       A, [Mallory], 1, scheme, pubkey, stale_signed_bytes, [], []
   )
   ```
4. The on-chain check reconstructs the challenge with the current sequence number `N` (unchanged), verifies the signature — which is still valid — and proceeds.
5. `MultisigAccount` is created with Mallory as sole owner; Alice's auth key is rotated to `0x0`; all capability offers are revoked.
6. Alice has permanently lost access to account `A` and all assets it controls. [6](#0-5) [7](#0-6)

    public entry fun create_with_existing_account(
        multisig_address: address,
        owners: vector<address>,
        num_signatures_required: u64,
        account_scheme: u8,
        account_public_key: vector<u8>,
        create_multisig_account_signed_message: vector<u8>,
        metadata_keys: vector<String>,
        metadata_values: vector<vector<u8>>,
    ) {
        // Verify that the `MultisigAccountCreationMessage` has the right information and is signed by the account
        // owner's key.
        let proof_challenge = MultisigAccountCreationMessage {
            chain_id: chain_id::get(),
            account_address: multisig_address,
            sequence_number: account::get_sequence_number(multisig_address),
            owners,
            num_signatures_required,
        };
        account::verify_signed_message(
            multisig_address,
            account_scheme,
            account_public_key,
            create_multisig_account_signed_message,
            proof_challenge,
        );

        // We create the signer for the multisig account here since this is required to add the MultisigAccount resource
        // This should be safe and authorized because we have verified the signed message from the existing account
        // that authorizes creating a multisig account with the specified owners and signature threshold.
        let multisig_account = &create_signer(multisig_address);
        create_with_owners_internal(
            multisig_account,
            owners,
            num_signatures_required,
            option::none<SignerCapability>(),
            metadata_keys,
            metadata_values,
        );
    }

    public entry fun create_with_existing_account_and_revoke_auth_key(
        multisig_address: address,
        owners: vector<address>,
        num_signatures_required: u64,
        account_scheme: u8,
        account_public_key: vector<u8>,
        create_multisig_account_signed_message: vector<u8>,
        metadata_keys: vector<String>,
        metadata_values: vector<vector<u8>>,
    ) {
        // Verify that the `MultisigAccountCreationMessage` has the right information and is signed by the account
        // owner's key.
        let proof_challenge = MultisigAccountCreationWithAuthKeyRevocationMessage {
            chain_id: chain_id::get(),
            account_address: multisig_address,
            sequence_number: account::get_sequence_number(multisig_address),
            owners,
            num_signatures_required,
        };
        account::verify_signed_message(
            multisig_address,
            account_scheme,
            account_public_key,
            create_multisig_account_signed_message,
            proof_challenge,
        );

        // We create the signer for the multisig account here since this is required to add the MultisigAccount resource
        // This should be safe and authorized because we have verified the signed message from the existing account
        // that authorizes creating a multisig account with the specified owners and signature threshold.
        let multisig_account = &create_signer(multisig_address);
        create_with_owners_internal(
            multisig_account,
            owners,
            num_signatures_required,
            option::none<SignerCapability>(),
            metadata_keys,
            metadata_values,
        );

        // Rotate the account's auth key to 0x0, which effectively revokes control via auth key.
        let multisig_address = address_of(multisig_account);
        account::rotate_authentication_key_internal(multisig_account, ZERO_AUTH_KEY);
        // This also needs to revoke any signer capability or rotation capability that exists for the account to
        // completely remove all access to the account.
        if (account::is_signer_capability_offered(multisig_address)) {
            account::revoke_any_signer_capability(multisig_account);
        };
        if (account::is_rotation_capability_offered(multisig_address)) {
            account::revoke_any_rotation_capability(multisig_account);
        };
    }
