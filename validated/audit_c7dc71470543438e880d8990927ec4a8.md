### Title
`mt_resolve_withdraw` collapses a mismatched-length used-array to all-zero, causing a full double-credit refund - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
`mt_resolve_withdraw`'s match arm `Ok(_) => vec![U128(0); amounts.len()]` treats any successful promise result whose deserialized length doesn't equal `amounts.len()` as "nothing was used," refunding the *entire* withdrawn amount back to the sender even though the underlying `mt_batch_transfer_call` genuinely transferred the tokens out. Since the attacker fully controls the `token` contract (an arbitrary NEP-245 contract they deploy) that they use for withdrawal from their own Defuse balance, they can make its `mt_batch_transfer_call` promise resolve with a well-formed but wrong-length JSON array while still completing the real transfer, causing Defuse to refund the full amount on top of the completed transfer.

### Finding Description
The broken binding: `balance_debited_at_withdraw == assets_actually_left_receiver + amount_recredited_by_resolver`. Before the outbound promise, `internal_mt_withdraw` debits the sender's ledger balance for both tokens via `self.withdraw` [1](#0-0) . `do_mt_withdraw` then issues `mt_batch_transfer_call` to the attacker-controlled `token` contract [2](#0-1) . In the resolver, the promise result is parsed and matched:

```
Ok(Ok(used)) if used.len() == amounts.len() => used,
Ok(_) => vec![U128(0); amounts.len()],
Err(_) => amounts.clone(),
``` [3](#0-2) 

The `Ok(_)` arm fires both for JSON-parse failures and for a *successfully parsed* array whose length differs from `amounts.len()`. In that arm, `used` is forced to all zeros, so every element of `amounts` is treated as unused, and `self.deposit` re-credits the full original amount back to `sender_id` [4](#0-3) .

Because `token` is attacker-supplied and can be the attacker's own deployed MT contract, the attacker controls exactly what `mt_batch_transfer_call`'s final promise result contains, independent of whether the transfer genuinely completed on that contract. They can implement a `token` contract whose `mt_resolve_transfer`/equivalent logic actually keeps the transferred balance with the receiver (real state change on that contract) while returning a JSON array of the wrong length (e.g., length 1 instead of 2) to Defuse's resolver, triggering the Ok(_) fallback and full refund.

No existing guard prevents this: `promise_result_checked_json_with_len` only bounds the max byte length used for `env::promise_result_checked`; it does not validate the decoded array's element count before the resolver's own `match` does — and that match's fallback (intended to be "conservative" for malformed responses) already assumes zero usage rather than rejecting the case outright or panicking.

### Impact Explanation
The attacker's ledger balance for tokens `T1`/`T2` is restored to its pre-withdrawal amount while the same 300+300 units were also genuinely transferred out to the receiver on the underlying token contract. This is a resolver credit that does not match what failed to settle — nothing failed, yet the attacker is refunded as if everything failed. If that token/ledger balance is later used within Defuse to fulfill swap intents against genuine assets deposited by other users, the attacker can leverage the duplicated balance to extract real value from the Verifier, matching the Critical category ("a refund or resolver credit that does not match what failed to settle").

### Likelihood Explanation
The attacker needs to: deploy their own MT ("token") contract that both (a) performs a real internal transfer when receiving `mt_batch_transfer_call`/invokes `mt_on_transfer`, and (b) returns a wrong-length JSON array as the final resolved value of that call. They deposit into Defuse using this self-controlled token to obtain a legitimate Defuse-side balance, then call `mt_withdraw` with `msg` set (so `is_call = true`, hitting the vulnerable branch). This requires no privileged role, no victim key, and is fully repeatable across any number of tokens/batches per the same crafted contract.

### Recommendation
Treat any successfully-parsed result whose length doesn't match `amounts.len()` the same as a malformed/failed result that should NOT trigger a full refund of already-verified-transferred tokens — e.g., panic/abort the resolver (since this indicates a non-compliant token contract) rather than silently zeroing `used`, or require exact-length validation before accepting any values from that promise result at all.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy a malicious MT contract `EvilMT` implementing NEP-245 that: on `mt_batch_transfer_call`, actually credits the receiver's balance for `T1` and `T2` with 300 each, but returns the JSON array `[U128(0)]` (length 1) instead of `[U128(300), U128(300)]` as the final resolved promise value.
2. Deposit `T1`/`T2` (300 each) from `EvilMT` into the Defuse contract for attacker account `A`, verifying `A`'s Defuse balance is `T1: 300, T2: 300`.
3. Call `mt_withdraw` as `A` with `token = EvilMT`, `token_ids = [T1, T2]`, `amounts = [300, 300]`, `msg = Some(...)`.
4. Assert (binding check): `EvilMT` receiver balance for `T1`/`T2` == 300 each (genuinely transferred), AND `A`'s Defuse-side balance for `T1`/`T2` == 0 (not refunded) — i.e., `debited(600) == transferred(600) + recredited(0)`.
5. Currently, step 4 fails because the bug re-credits `A`'s Defuse balance back to 300/300 (`recredited(600)`), producing `debited(600) != transferred(600) + recredited(600) = 1200`, demonstrating the double-credit.
