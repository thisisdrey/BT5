### Title
Stale `YieldIdToDataId` trie entries survive `DeleteAccount`/`CreateAccount`, permanently blocking `promise_yield_create_with_id` for any yield_id used before deletion - (File: `runtime/runtime/src/ext.rs`, `core/store/src/utils/mod.rs`)

### Finding Description
`create_promise_yield_receipt_with_id` (`runtime/runtime/src/ext.rs:371-400`) checks for a duplicate `user_yield_id` via `has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)` before creating a new yield, and silently returns `Ok(None)` if the check returns `true`: [1](#0-0) 

`has_yield_id_mapping` (`core/store/src/utils/mod.rs:315-324`) does a plain `trie.contains_key(TrieKey::YieldIdToDataId { receiver_id, yield_id })` lookup: [2](#0-1) 

That key/value survives account deletion because `remove_account` (`core/store/src/utils/mod.rs:504-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`. It never iterates or removes `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, or `TrieKey::PromiseYieldStatus` entries for the account: [3](#0-2) [4](#0-3) 

`action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) calls only `remove_account`, confirming no yield cleanup happens on deletion: [5](#0-4) 

The only place `YieldIdToDataId`/`DataIdToYieldId` pairs are ever cleared is on a successful `PromiseResume` (`runtime/runtime/src/lib.rs:1523-1536`), gated by `remove_yield_id_mappings` finding a matching data_id via `get_yield_id_for_data_id`. If the yield is never resumed (the receiver account is deleted before resume), the mapping is never cleaned up, and no other code path clears it.

Exploit flow: account `X` (attacker's own account or any account they control) deploys/calls a contract exposing `yield_create_with_id`, invokes it with `user_yield_id = Y`, which writes `TrieKey::YieldIdToDataId{X, Y}` and `TrieKey::DataIdToYieldId{X, data_id}` and never resumes it. `X` then submits `DeleteAccount` (self-delete, refunding balance to a beneficiary) - `remove_account` deletes the `Account`/keys/code/data but leaves the yield rows untouched. A new account named `X` is later created (e.g. name squatting/re-registration, which NEAR permits after deletion) and its contract calls `promise_yield_create_with_id(Y)`. `has_yield_id_mapping` finds the stale `YieldIdToDataId{X, Y}` row still present and returns `true`, so `create_promise_yield_receipt_with_id` returns `Ok(None)`, and `promise_yield_create_with_id` in the VM logic returns the `u64::MAX` sentinel forever for that `(X, Y)` pair - the new owner of `X` can never create a yield with id `Y`.

### Impact Explanation
This is a permanent, silent functional deadlock scoped to a specific `(account_id, yield_id)` pair: the new occupant of a re-created account name can never again use that particular `yield_id` with `yield_create_with_id`, with no error or way to detect/clear it on their end (the VM logic only returns a sentinel `u64::MAX`, not a diagnosable error). It does not cause fund loss, consensus divergence, or a chain halt; it is a narrow liveness/griefing issue affecting only contracts that (a) use `promise_yield_create_with_id`, (b) let a yield go un-resumed, and (c) have their account deleted and recreated with the same name.

### Likelihood Explanation
Trivially reproducible by any unprivileged account: fund an account, deploy a contract calling `yield_create_with_id`, call `DeleteAccount`, recreate an account with the same name, and call `yield_create_with_id` with the same `yield_id` again. No special privileges, gas limits, or races are required, and the attacker (or a griefer targeting a specific account name they expect to be reused) fully controls all steps. Real-world impact is limited by the requirement that the victim/new owner actually adopts the exact same account name and that the specific `yield_id` value collides with one used pre-deletion (attacker-chosen if griefing themselves, or attacker must guess/collude on the id for third-party griefing).

### Recommendation
In `remove_account` (or in `action_delete_account`), iterate and remove all `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, and `TrieKey::PromiseYieldStatus` entries scoped to the account being deleted, mirroring the existing access-key/gas-key/contract-data cleanup loops, so no stale yield-id state can leak into a future account created under the same name.

### Proof of Concept
Rust unit test in `runtime/runtime/src/ext.rs` or `core/store/src/utils/mod.rs` tests module:
1. Build a `TrieUpdate`, call `set_yield_id_mapping(&mut state_update, &account_id, yield_id, data_id)` to simulate a pending `yield_create_with_id`.
2. Call `remove_account(&mut state_update, &account_id)` to simulate `DeleteAccount`.
3. Re-create the account (`set_account`) with the same `account_id`.
4. Call `has_yield_id_mapping(&state_update, &account_id, yield_id)` and assert it incorrectly returns `true`.
5. Call `create_promise_yield_receipt_with_id(account_id, yield_id)` via the runtime `Ext` and assert it returns `Ok(None)` instead of `Ok(Some(..))`, confirming the permanent block.
