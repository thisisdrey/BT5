### Title
Unbounded attachment content size in `GetAttachmentResponse` deserialization bypasses `attachments_max_size` - (File: stackslib/src/net/atlas/mod.rs)

### Summary
`GetAttachmentResponse`'s custom `Deserialize` impl decodes a hex string from a peer's HTTP response and constructs `Attachment::new(bytes)` with no length check against `AtlasConfig::attachments_max_size`. This value flows unchecked through `decode_atlas_get_attachment`, `AttachmentsBatchStateContext::extend_with_attachments`, and `AttachmentsDownloader::run` into `AtlasDB::insert_instantiated_attachment`, storing arbitrarily large peer-supplied content.

### Finding Description
In `stackslib/src/net/atlas/mod.rs` (lines 69-77), `GetAttachmentResponse::deserialize` reads an arbitrary JSON string, hex-decodes it, and builds `Attachment::new(bytes)` directly: [1](#0-0) 
There is no comparison of `bytes.len()` to `ATTACHMENTS_MAX_SIZE_MIN` or the configured `AtlasConfig::attachments_max_size`, which is only used for config validation, never enforced at parse time: [2](#0-1) 

The response passes through `RPCGetAttachmentRequestHandler::try_parse_response` -> `StacksHttpResponse::decode_atlas_get_attachment`, which only checks that the JSON parses, again with no size gate: [3](#0-2) 

The resulting attachment is then unconditionally inserted into the batch context's `attachments` set in `AttachmentsBatchStateContext::extend_with_attachments`: [4](#0-3) 

Finally, `AttachmentsDownloader::run` drains `context.attachments` and calls `AtlasDB::insert_instantiated_attachment` on each entry with no size validation visible in this path: [5](#0-4) 

An attacker running an ordinary outbound-sync peer that a victim node queries for an attachment (via `AttachmentRequest`) can respond to `/v2/attachments/<hash>` with a `GetAttachmentResponse` JSON body whose hex-encoded `content` field is far larger than the configured `attachments_max_size` (default `ATTACHMENTS_MAX_SIZE_MIN` = 1 MiB). This bypasses the config-intended cap entirely, since the cap is never checked in the deserialize/decode/extend/store path.

### Impact Explanation
A malicious or compromised peer answering attachment requests can cause the victim node to store attachment content of unbounded size in its `AtlasDB`, exceeding the operator-configured `attachments_max_size` bound. This is a storage-exhaustion vector against a node's local attachment database, achievable repeatedly for every attachment hash the node requests, matching the "attachment/BNS mismatch"-adjacent High-severity category of resource-bound violations on Atlas-managed state.

### Likelihood Explanation
No privileged access is required: any peer that a node syncs Atlas attachments from can answer a legitimate outbound `AttachmentRequest` with an oversized payload. The victim node must simply be actively requesting an attachment that the malicious peer's inventory claims to have (routine Atlas sync behavior). The attack is a single crafted HTTP response and can be repeated per hash/batch, with attacker cost limited to running a normal reachable peer/data-URL.

### Recommendation
Enforce a size check against `AtlasConfig::attachments_max_size` (or `ATTACHMENTS_MAX_SIZE_MIN` at minimum) inside `GetAttachmentResponse::deserialize` (or in `decode_atlas_get_attachment`/`extend_with_attachments`) before constructing/storing the `Attachment`, rejecting responses whose decoded byte length exceeds the configured cap.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/download.rs` or `net/api/tests/getattachment.rs`:
1. Construct a JSON body `{"attachment_hash":..., "content": "<hex string encoding N bytes where N > ATTACHMENTS_MAX_SIZE_MIN>"}` (or whatever the wire format serializes to per `GetAttachmentResponse::serialize`).
2. Build a `StacksHttpResponse` from this body and call `decode_atlas_get_attachment()` on it — observe it returns `Ok(GetAttachmentResponse { attachment })` with `attachment.content.len() > ATTACHMENTS_MAX_SIZE_MIN`.
3. Feed the response into a `BatchedRequestsResult<AttachmentRequest>` with `succeeded` containing this response, then call `AttachmentsBatchStateContext::extend_with_attachments`.
4. Assert `context.attachments` contains the oversized attachment (`context.attachments.iter().any(|a| a.content.len() > ATTACHMENTS_MAX_SIZE_MIN)`), confirming the size cap was never enforced before insertion into the store path leading to `AtlasDB::insert_instantiated_attachment`.

Note: I was unable to fully inspect `AtlasDB::insert_instantiated_attachment` in `stackslib/src/net/atlas/db.rs` within the available iterations to confirm whether a size check exists at the DB-insert boundary itself; the finding is based on the confirmed absence of checks in the deserialize/decode/extend-with-attachments path. If a size check exists inside `insert_instantiated_attachment`, it would mitigate this specific finding — this should be verified directly against `stackslib/src/net/atlas/db.rs` before treating this as fully confirmed.

        let attachment = Attachment::new(bytes);

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
