### Title
Unauthenticated event ingestion on the signer's HTTP receiver allows forged StackerDB/block-proposal events to be injected - ([File: libsigner/src/events.rs])

### Summary
The `stacks-signer`'s local HTTP event receiver (`SignerEventReceiver`, `libsigner/src/events.rs`) accepts and processes `POST` requests to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` from any TCP client that can reach the configured listen address, without validating any `Authorization`/`auth_token` credential. This mirrors the report's core bug class: a value (`auth_token`/`auth_password`) that is *documented* and *configured* as the mechanism securing this channel is never actually checked at the point where trust is supposed to be enforced, so "authenticated vs. stored/consumed" data is not actually verified before being fed into the signer.

### Finding Description
The node-side documentation and config explicitly describe `auth_token` (node) / `auth_password` (signer) as the credential that "secures the communication channel between this node and a connected `stacks-signer` instance": [1](#0-0) [2](#0-1) 

The event-dispatch side that pushes payloads to the signer's endpoint (`EventDispatcher::dispatch_to_observer` / `EventRequestData` / worker) builds and sends the HTTP request body but does not attach any `Authorization` header with the configured `auth_token`: [3](#0-2) 

On the receiving side, `SignerEventReceiver::next_event` (the signer's own HTTP server, bound via `bind()`) dispatches purely on the request path and method — `/status`, `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/shutdown`, `/new_block` — with no check of any header, token, or peer identity before decoding and forwarding the body as a trusted `SignerEvent`: [4](#0-3) 

`process_event` similarly just reads the body, JSON-deserializes it into a `StackerDBChunksEvent` / `BlockValidateResponse` / etc., and converts it into a `SignerEvent`, again without any authenticity check of the sender: [5](#0-4) 

The forwarded event is then handed directly into the signer's runloop via `forward_event`, which has no additional gating: [6](#0-5) 

This is the exact analog of the reported bug class: a credential (`auth_token`) is provisioned and documented as protecting a sensitive channel, but the actual enforcement point (here, the signer's transport-layer HTTP receiver) never checks it — an "auth-gate that fails open." Just as the mobile wallet's shared secret was supposed to secure device-to-desktop communication but was left unprotected at rest, here the `auth_token` is supposed to secure node-to-signer communication but is never validated at the point of receipt.

### Impact Explanation
Any host that can open a TCP connection to the signer's `endpoint` (which sample configs bind to `0.0.0.0:<port>`, e.g. `sample/conf/mainnet-signer-conf.toml` / `testnet-signer.toml`) can POST an arbitrary, forged `StackerDBChunksEvent`, `BlockValidateResponse`, `BurnBlockEvent`, or `StacksBlockEvent` payload and have it accepted as if it came from the trusted, paired `stacks-node`. Because the signer's runloop treats these events as authoritative inputs from its own node, this constitutes unauthenticated injection of forged data into the signer's decision pipeline at the transport layer — satisfying the "forged gossip/data relayed" and "auth bypass" criteria for a Critical-impact finding, independent of what the (out-of-scope) signer decision logic subsequently does with that data.

### Likelihood Explanation
Exploitation only requires network reachability to the signer's HTTP listener and knowledge of the well-known paths (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`), which are hardcoded string literals in `libsigner/src/events.rs`. No secrets, node keys, or privileged access are required — the `auth_token`/`auth_password` configured by the operator is never consulted by the receiver, so it provides no actual protection. The main mitigating factor is that operators are expected to bind the signer's endpoint to a private/local address and firewall it (per the warning in `stacks-signer/src/lib.rs`), but this is an operational mitigation, not a code-level control, and the configuration surface (`auth_token`) actively implies a security guarantee that the code does not provide.

### Recommendation
**Short term:** In `libsigner/src/events.rs`, validate an `Authorization` header (or equivalent shared-secret check) against the configured `auth_password`/`auth_token` in `SignerEventReceiver::next_event` before dispatching to `process_event`, rejecting unauthenticated requests. Correspondingly, in `stacks-node/src/event_dispatcher.rs`, attach the node's `auth_token` as an `Authorization` header when dispatching payloads to observers, so the credential documented in `stackslib/src/config/mod.rs` is enforced end-to-end rather than being purely advisory.

**Long term:** Audit all node↔signer and signer↔signer transport surfaces for similar "documented but unenforced" authentication assumptions, and add automated tests asserting that unauthenticated requests to signer event endpoints are rejected.

### Proof of Concept
1. Start a `stacks-signer` with `endpoint = "0.0.0.0:30000"` per `sample/conf/signer/mainnet-signer-conf.toml`, with `auth_password` set.
2. From an unrelated host with network access to port 30000, send:
```
POST /stackerdb_chunks HTTP/1.1
Host: <signer-ip>:30000
Content-Type: application/json
Content-Length: <n>

{"contract_id": "...", "modified_slots": [ ... forged StackerDBChunkData ... ]}
```
with no `Authorization` header at all.
3. Observe (per the code path in `libsigner/src/events.rs:410-459` and `519-542`) that the request is accepted, deserialized, and forwarded into the signer's runloop exactly as if it had originated from the paired, authenticated `stacks-node` — confirming that `auth_token`/`auth_password` is never checked at this endpoint.

```rust
    /// Wait for the node to post something, and then return it.
    /// Errors are recoverable -- the caller should call this method again even if it returns an
    /// error.
    fn next_event(&mut self) -> Result<SignerEvent<T>, EventError> {
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)
            } else if request.url() == "/new_block" {
                process_event::<T, StacksBlockEvent>(request)
            } else {
                let url = request.url().to_string();
                debug!(
                    "[{:?}] next_event got request with unexpected url {}, return OK so other side doesn't keep sending this",
                    event_receiver.local_addr,
                    url
                );
                ack_dispatcher(request);
                Err(EventError::UnrecognizedEvent(url))
            }
        })?
    }
```

```rust
    /// Forward an event
    /// Return true on success; false on error.
    /// Returning false terminates the event receiver.
    fn forward_event(&mut self, ev: SignerEvent<T>) -> bool {
        if self.out_channels.is_empty() {
            // nothing to do
            error!("No channels connected to event receiver");
            false
        } else if self.out_channels.len() == 1 {
            // avoid a clone
            if let Err(e) = self.out_channels[0].send(ev) {
                error!("Failed to send to signer runloop: {:?}", &e);
                return false;
            }
            true
        } else {
            for (i, out_channel) in self.out_channels.iter().enumerate() {
                if let Err(e) = out_channel.send(ev.clone()) {
                    error!("Failed to send to signer runloop #{}: {:?}", i, &e);
                    return false;
                }
            }
            true
        }
    }
```

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
```
