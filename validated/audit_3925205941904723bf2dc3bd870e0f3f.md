### Title
Non-constant-time HTTP `authorization` header comparison enables timing attack to recover the node's RPC auth token - (File: `stackslib/src/net/api/postblock_proposal.rs`, `blocksimulate.rs`, `blockreplay.rs`, `fastcallreadonly.rs`, `txsimulate.rs`, `postblock_v3.rs`)

### Summary
Several privileged Stacks node RPC endpoints authenticate callers by comparing the raw `authorization` HTTP header value against the node's configured secret using Rust's built-in `!=` operator on `String`/`&str`. This comparison short-circuits on the first mismatching byte and is not constant-time, mirroring the Mailman Core CVE-2021-34337 bug class where a REST API password comparison leaked timing information that let an attacker recover the secret byte-by-byte.

### Finding Description
Each of the following handlers implements `try_parse_request` and gates access with the identical pattern:
```
let Some(auth_header) = preamble.headers.get("authorization") else { ... 401 ... };
if auth_header != password { ... 401 ... }
``` [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The compared value is the plaintext secret documented as `connection_options.auth_token`, sent verbatim in the `authorization` header (an API-key-style scheme, not HMAC/challenge-based): [7](#0-6) 

Rust's default string/byte-slice equality (`==`/`!=`) is implemented as a length check followed by a `memcmp`-style comparison that returns as soon as a differing byte is found — it provides no constant-time guarantee. An attacker who can measure response latency with sufficient precision (this is a local network / same-datacenter RPC/P2P endpoint, so latency measurement is far more reliable than over the public Internet) can incrementally guess the auth token one byte at a time, exactly the technique described in the referenced Mailman advisory (GHSA-2jg5-xgvv-4wq7 / CVE-2021-34337).

### Impact Explanation
Recovering the node's auth token grants access to sensitive/privileged RPC endpoints: `/v3/block_proposal` (block validation used by signers), `/v3/blocks/simulate`, `/v3/blocks/replay`, `/v3/contracts/fast-call-read`, `/v3/transactions/simulate`, and authenticated `POST /v2/blocks` broadcast. This is an authentication-bypass primitive gained purely through observable timing, matching the report's "auth-gate" equality-break criterion. Once bypassed, an attacker can submit unauthenticated-equivalent block proposals/broadcasts or trigger compute-heavy read/simulate operations that are otherwise access-gated — a bounded compute DoS and privileged-write-path exposure.

### Likelihood Explanation
Exploitation requires many repeated requests (byte-by-byte brute force over the token's character space) and a low-jitter network path to the target node, which is realistic for signer/miner peers who already have general network connectivity to the node's RPC-bound interface. No credentials or special role are required to begin the attack — only the fact that these endpoints are network reachable and gated with this comparison, which matches the "authenticated vs stored equality" analog explicitly permitted by scope rules.

### Recommendation
Replace the direct `!=` string comparisons with a constant-time comparison (e.g., convert both sides to bytes and use a `subtle::ConstantTimeEq`-based comparison, or hash the token with a keyed MAC and compare digests) in `postblock_proposal.rs`, `blocksimulate.rs`, `blockreplay.rs`, `fastcallreadonly.rs`, `txsimulate.rs`, and `postblock_v3.rs`.

### Proof of Concept
1. Configure a node with `connection_options.auth_token` set (as used by `RPCBlockProposalRequestHandler::new`) and expose `/v3/block_proposal`.
2. From a low-latency vantage point, send POST requests with an `authorization` header where all but the last byte match a candidate prefix; measure response time to the 401 rejection.
3. Because `auth_header != password` short-circuits at the first mismatched byte, a correct-length matching prefix takes measurably longer to reject than an early mismatch, allowing byte-by-byte recovery of the full token, as demonstrated by `test_wrong_auth` in `stackslib/src/net/api/tests/fastcallreadonly.rs:414-443` showing the same comparison path is exercised on every request.
