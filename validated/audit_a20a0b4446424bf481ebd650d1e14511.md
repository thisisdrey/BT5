### Title
Replay-Window Check-Decrypt-Update Race Allows Duplicate Packet Acceptance - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` release `decryptLock` between the anti-replay `window.Check` call and the subsequent `window.Update` call that actually marks the message counter as seen. When Nebula is configured with multiple UDP reader routines (`listen.routines` > 1, using `SO_REUSEPORT`), two copies of the same encrypted packet can be received on different queues and processed concurrently by different goroutines for the same `ConnectionState`. Both goroutines can pass `Check` before either has called `Update`, letting the same ciphertext be decrypted and accepted twice — a duplicate/replay bypass of the intended one-shot delivery guarantee.

### Finding Description
`Decrypt` performs the replay check, decrypt, and window update as three separate critical sections instead of one atomic operation: [1](#0-0) 

The same pattern is repeated in `VerifyRelay`: [2](#0-1) 

`decryptLock.Lock()`/`Unlock()` is taken independently around `Check` and around `Update`, with the (comparatively expensive) `DecryptDanger` call happening entirely outside the lock. This is a classic check-then-act race: the replay-window bit for `messageCounter` is only *committed* by `Update`, which happens strictly after the packet has already been decrypted and used. If two goroutines call `Decrypt` with the identical `messageCounter` concentrated closely in time, both can observe `Check` returning true (window not yet updated by the other), both proceed to decrypt successfully, and both `Update` calls will then (redundantly) mark the counter seen — but by that point both copies have already been treated as valid, undetected replays.

This mirrors the reported bug class exactly: a value/state check (`liquidityAdded`/replay-window state) is evaluated before the state-mutating operation that should reflect the pending action (`flashloan transfer`/`window.Update`) has actually happened, so the guard is stale for the duration of the gap.

Concurrent delivery to the same `ConnectionState` is not merely theoretical: Nebula spawns one reader goroutine per configured routine, each independently invoking the read/decrypt path: [3](#0-2) 

and on Linux these routines bind the same port via `SO_REUSEPORT` when `multi` is enabled, so the kernel can deliver duplicate/retransmitted packets to different queues, each drained by a different goroutine: [4](#0-3) 

An attacker on the network path (no valid Nebula certificate required — they only need to capture and duplicate an already-observed valid ciphertext packet) can send two copies of the same packet in quick succession to increase the likelihood they land on different reader queues, racing the check/update gap.

### Impact Explanation
Successful exploitation lets an on-path attacker cause the exact same tunnel packet to be processed twice (decrypted and delivered to the receiving side's data plane / relay-forward path) despite Nebula's anti-replay window being designed to guarantee single delivery. This is a concrete replay-protection bypass: duplicate delivery of application data, and for `VerifyRelay`, duplicate re-forwarding of a relayed frame that replay protection is explicitly meant to prevent (the CHANGELOG shows this exact relay-replay case was previously a real bug: "Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them"). While it does not by itself decrypt unrelated traffic or forge new packets, it undermines a documented security guarantee (no packet processed twice) and can be leveraged for traffic duplication/DoS-style amplification or reinjection of state-changing overlay traffic.

### Likelihood Explanation
Requires: (1) the target running with `listen.routines > 1` (multi-queue UDP, common on Linux for performance), and (2) an attacker able to observe/capture and near-simultaneously replay a valid ciphertext packet — feasible for any network-path attacker without holding a valid certificate. The race window is small but reproducible under load or with adversary-controlled packet duplication (e.g., sending both copies back-to-back to increase scheduling overlap). Likelihood is moderate: it is a genuine TOCTOU race rather than a deterministic bypass, but it is remotely triggerable with no authentication.

### Recommendation
Perform the replay-window check and the corresponding "mark as seen" update as a single atomic operation covering the whole decrypt, or otherwise ensure only one in-flight decrypt per `messageCounter` can proceed: e.g., hold `decryptLock` (or a per-counter claim) across `Check`, `DecryptDanger`, and `Update`, or have `Update` perform an atomic check-and-set that both goroutines observe consistently (reject the second caller even if it reached `Update` after already decrypting, and ensure the decrypt call itself cannot happen for an already-claimed counter).

### Proof of Concept
1. Configure two Nebula nodes with `listen.routines: 2` (or more) so `SupportsMultipleReaders()` is true and multiple `SO_REUSEPORT` queues are active. [5](#0-4) 
2. Establish a tunnel and capture one valid, in-window encrypted data packet from initiator to responder.
3. Immediately resend two identical copies of that captured UDP packet to the responder's listen port, timed so the OS/kernel is likely to dispatch them to two different reader queues (e.g., burst them back-to-back).
4. Each reader goroutine independently calls `ConnectionState.Decrypt` for the same `HostInfo`/`ConnectionState`; because `window.Check` and `window.Update` are separate locked sections with `DecryptDanger` unlocked in between, both goroutines can pass `Check` before either commits `Update`, causing the payload to be decrypted and delivered twice on the responder's TUN device (observed as duplicate application-layer packets) instead of the second copy being rejected with `ErrAlreadySeen`. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
