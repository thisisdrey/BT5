Based on the investigation, I found a strong local analog in the PSM (Peg Stability Module) pallet, where a debt-ceiling parameter can be reduced by an instance admin without validating it against currently-outstanding minted debt, mirroring the exact `maxInvocations`-reduction pattern from the external report.

### Title
`set_asset_ceiling_weight` allows a PSM instance admin to shrink an external asset's mint capacity below its outstanding debt, freezing redemption capacity and destabilizing the peg - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`Pallet::set_asset_ceiling_weight` lets a PSM instance's admin (an instance-scoped privilege, not chain governance) change the `weight` used to compute `max_asset_debt = (weight / sum_of_weights) * info.max_debt` for an already-approved external asset [1](#0-0) . The call performs no check that the new weight (and therefore the recomputed `max_asset_debt`) remains at or above the external asset's already-outstanding minted debt [2](#0-1) . The code comment explicitly acknowledges the effect but treats it as benign ("an external left below its new ceiling simply can't be minted until redemptions bring its debt back down") [3](#0-2) , without accounting for the case where the ceiling is dropped for one external while other externals in the same PSM instance are re-normalized upward, or where legitimate users depending on that external's minting capacity are permanently locked out.

### Finding Description
This is the direct structural analog of the FantiumNFTV3 bug: a public config-update entrypoint that shrinks a "capacity" parameter (`maxInvocations` in the external report, `AssetCeilingWeight`/`max_asset_debt` here) without checking it against the corresponding "already consumed" counter (invocations minted vs. `max_asset_debt` vs. outstanding debt for that external asset).

Because weights are normalized across all externals of the PSM instance (`max_asset_debt = (weight / sum_of_weights) * info.max_debt`), a single call to `set_asset_ceiling_weight` for one external asset changes the effective ceiling for every other approved external asset in that instance as well (their share of `sum_of_weights` changes), yet none of the existing debt for any external is checked against the newly-recomputed ceilings before the change is committed [4](#0-3) . This mirrors the FantiumNFT flaw where reducing `maxInvocations` is done without verifying it against `collections[_collectionId].maxInvocations`/existing invocation state.

### Impact Explanation
Once an external asset's recomputed `max_asset_debt` drops below its outstanding debt, minting against that external is permanently blocked ("can't be minted until redemptions bring its debt back down" per the code's own comment). Since redemption requires other users to voluntarily redeem (and redemption is itself rate-limited by fees/liquidity), users and integrators depending on minting capacity for that external can be locked out indefinitely — a form of public underpriced/blocked work and protocol-level fund-flow lock consistent with the "public underpriced work that degrades... processing" and "permanent user-fund... lock" impact categories in scope. Because ceilings are shared/normalized across all externals in the instance, an admin adjusting the weight for asset A can silently invalidate the previously-valid capacity assumptions for asset B, an effect not visible from the single-parameter check performed by the call.

### Likelihood Explanation
The call is reachable by any account holding the PSM instance's "Full" admin privilege level (`ensure_psm_admin(... can_set_asset_ceiling())`) [5](#0-4)  — this is an instance-scoped operational role, analogous to the collection owner in the FantiumNFT report, not necessarily full chain governance. Any routine rebalancing of weights between externals (a normal, expected operation for this pallet) can trigger the harmful effect without any malicious intent, satisfying the "no malicious admin required" constraint of the analysis. The bug is deterministic and requires no race condition — any weight change that drops a given external's normalized share below its live debt reproduces the issue.

### Recommendation
Before committing a new weight, recompute `max_asset_debt` for every approved external asset of the instance under the new weight set and reject the update (return an error) if any external's outstanding debt would exceed its new ceiling — the direct analog of the recommended `_maxInvocations > collections[_collectionId].maxInvocations` check, generalized to "new_max_asset_debt >= current_outstanding_debt" for every affected external, not just the one being updated.

### Proof of Concept
1. PSM instance has externals `USDC` (weight 50) and `USDT` (weight 50), `max_debt = 1000`, giving each a `max_asset_debt` of 500.
2. Users mint against `USDC` up to 480 outstanding debt (within its 500 ceiling).
3. Admin calls `set_asset_ceiling_weight(internal, USDT, weight=90)` to favor `USDT` — a legitimate, non-malicious rebalancing action.
4. `sum_of_weights` becomes 140 (50 for USDC + 90 for USDT); `USDC`'s normalized `max_asset_debt` becomes `50/140 * 1000 ≈ 357`, which is now below its outstanding 480 debt.
5. No check in `set_asset_ceiling_weight` catches this; the update is accepted and emits `AssetCeilingWeightUpdated` [6](#0-5) .
6. All further `mint` calls against `USDC` now fail (debt already exceeds ceiling) until other users voluntarily redeem enough `USDC`-backed internal asset — a scenario entirely outside the control of `USDC` depositors, causing indefinite loss of minting capability for that market side.

**Uncertainty**: I could not fully trace the `mint`/`redeem`/`max_asset_debt` enforcement logic within the tool-call budget available (only the setter and its doc comments were confirmed) — a Devin session with full repository access should verify the exact debt-check code path (likely `do_mint`) to confirm the precise failure mode and any existing mitigations before treating this as fully proven.

		pub fn set_asset_ceiling_weight(
			origin: OriginFor<T>,
			internal_asset: T::AssetId,
			external_asset: T::AssetId,
			weight: Permill,
		) -> DispatchResult {
			Self::ensure_psm_admin(origin, &internal_asset, |l| l.can_set_asset_ceiling())?;
			ensure!(
				ExternalAssets::<T>::contains_key(&internal_asset, &external_asset),
				Error::<T>::AssetNotApproved
			);
			// Reweighting renormalises every external's ceiling; an external left below its new
			// ceiling simply can't be minted until redemptions bring its debt back down.
			let old_value = AssetCeilingWeight::<T>::get(&internal_asset, &external_asset);
			AssetCeilingWeight::<T>::insert(&internal_asset, &external_asset, weight);
			Self::deposit_event(Event::AssetCeilingWeightUpdated {
				internal_asset,
				external_asset,
				old_value,
				new_value: weight,
			});
			Ok(())
