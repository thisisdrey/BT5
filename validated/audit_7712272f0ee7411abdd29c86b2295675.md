Audit Report

## Title
`add_tip` in Snowbridge inbound-queue-v2 lets any signed account write unbounded, unvalidated entries into `Tips` for nonces that may never exist - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

## Summary
`AddTip::add_tip` in `snowbridge-pallet-inbound-queue-v2` only checks `amount > 0` and that the nonce is not already-consumed via `Nonce::<T>::get(nonce)`, before unconditionally inserting into the unbounded `Tips` storage map keyed by an attacker-supplied `u64` nonce. Unlike the outbound-queue-v2 sibling, which validates the nonce against an existing `PendingOrders` entry and rejects unknown nonces with `AddTipError::UnknownMessage`, the inbound path has no check that the nonce corresponds to a real or plausible in-flight message, allowing any signed AssetHub account (via `SnowbridgeSystemFrontend::add_tip` → XCM `Transact` → `EthereumSystemV2::add_tip`) to permanently grow `Tips` storage on BridgeHub with fabricated nonces.

## Finding Description
`Tips` is declared as `StorageMap<_, Blake2_128Concat, u64, u128, OptionQuery>` with no bound on the key space [1](#0-0) . `AddTip::add_tip` for this pallet checks only `amount > 0` and `!Nonce::<T>::get(nonce)` (i.e., not-yet-processed), then unconditionally mutates `Tips` for the given nonce [2](#0-1) . The `Nonce::<T>::get` check only rejects nonces that have *already* been consumed by a real, processed message — it does nothing to reject nonces that will never be reached (e.g., far beyond the current counter or values skipped by real Ethereum traffic).

The outbound-queue-v2 implementation of the same `AddTip` trait instead requires an existing `PendingOrders` entry, using `try_mutate_exists` and returning `AddTipError::UnknownMessage` for nonces without a live order [3](#0-2) . This asymmetry confirms the inbound path lacks an equivalent existence check, and the `AddTipError` enum itself only defines `NonceConsumed`, `UnknownMessage`, `AmountZero` — with `UnknownMessage` unused by the inbound implementation [7](#0-6) .

The only place a `Tips` entry is removed is `process_message`, which `take`s the tip for the *real* nonce of a message that has passed gateway/nonce verification and been marked processed [4](#0-3) . A fabricated nonce that never corresponds to a real Ethereum event will never be processed, so its `Tips` entry is never removed.

The full attack path is reachable end-to-end without privilege: `SnowbridgeSystemFrontend::add_tip` is callable by any signed account, requiring only `ensure_signed(origin)` before swapping/burning the supplied asset for Ether and dispatching a `Transact` call to BridgeHub [5](#0-4) . On BridgeHub, `EthereumSystemV2::add_tip` checks only `T::FrontendOrigin::ensure_origin(origin)` — i.e., that the call legitimately originated from the frontend pallet's XCM — and dispatches directly to `InboundQueue::add_tip(nonce, amount)` with no check relating the caller or the tip to any actual message [6](#0-5) .

## Impact Explanation
Each call costs the attacker only the minimal burnt tip amount (any `amount > 0` suffices) plus fixed extrinsic weight, but creates a permanent (until an improbable/never-occurring future event) entry in `Tips`, since there is no expiry, cap, or reaping mechanism. Repeated calls with distinct never-to-be-consumed nonces cause unbounded storage growth in `pallet-inbound-queue-v2` state on BridgeHub, inflating state size/PoV weight for all future block validation and node storage — this matches the "public underpriced work that degrades block production or stalls bridge processing" impact category, achievable by an unprivileged party without relayer, validator, or governance involvement.

## Likelihood Explanation
High. The path requires only a signed account with a minimal balance of any fee-eligible asset that can be swapped into Ether, and calls a fully public, user-facing extrinsic. No governance, relayer, or validator collusion is required. The discrepancy between the inbound implementation (no existence check) and the outbound implementation (explicit `PendingOrders` existence check) for the identical `AddTip` trait strongly indicates this is an oversight rather than an accepted design choice.

## Recommendation
In `snowbridge-pallet-inbound-queue-v2::AddTip::add_tip`, validate that the nonce is plausible/in-flight before inserting into `Tips`, mirroring the outbound-queue-v2 pattern of checking against a tracked "pending" set, or reject nonces above a reasonable bound relative to the next-expected nonce, and/or bound the total number of unconsumed `Tips` entries to prevent unprivileged callers from creating unbounded persistent state.

## Proof of Concept
1. On AssetHub, as any signed account `attacker` holding a minimal fee-eligible asset balance, call `SnowbridgeSystemFrontend::add_tip(origin = signed(attacker), message_id = MessageId::Inbound(nonce), asset)` for a `nonce` far beyond any nonce that will realistically be relayed (e.g., `u64::MAX - k`).
2. This forwards via `Transact` XCM to BridgeHub's `EthereumSystemV2::add_tip`, which checks only `T::FrontendOrigin::ensure_origin` and dispatches to `InboundQueue::add_tip(nonce, amount)`.
3. `Tips::<T>::mutate(nonce, ...)` unconditionally inserts the entry since `Nonce::<T>::get(nonce)` is `false` for an unused nonce — no check that `nonce` corresponds to any real pending message.
4. Repeat with many distinct bogus nonces at minimal per-call cost; each call permanently grows `Tips` storage since removal only occurs via `process_message` for that exact nonce, which never happens for a fabricated nonce.
