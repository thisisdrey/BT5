## Analog Found: EIP-8246 SELFDESTRUCT with retained balance fails to clear nonce, code, and storage for pre-existing accounts

### Title
Incorrect `finaliseAmsterdam` self-destruct handling leaves stale nonce/code/storage-root instead of clearing them (EIP-8246) - (File: `core/state/statedb.go`)

### Summary
The reported bug class is "new state opened while the previous state is not properly closed/cleared first, causing a clash between old and new data." The equivalent in this repository's consensus-critical state transition is in the EIP-8246 (Amsterdam) SELFDESTRUCT-with-retained-balance path of `StateDB.finaliseAmsterdam`: when a self-destructed account keeps a non-zero balance, the code constructs the "new" balance-only account object directly from the account's **pre-transaction origin data** and only overwrites the balance field, instead of clearing nonce/code/storage first as the EIP mandates.

### Finding Description
`core/state/statedb.go` implements the Amsterdam self-destruct semantics: [1](#0-0) 

```go
case obj.selfDestructed:
    // EIP-8264: accounts marked for self-destruction, instead of
    // being deleted, are modified as follows:
    // - nonce is reset to 0,
    // - balance is unchanged,
    // - code is cleared,
    // - all storage is cleared
    if !obj.Balance().IsZero() {
        o := newObject(s, obj.address, obj.origin)
        o.setBalance(new(uint256.Int).Set(obj.Balance()))
        s.setStateObject(o)
        s.markUpdate(addr)
    } else {
        ...
    }
```

`newObject` initializes the fresh object's `data` field directly from the `acct` argument passed in — here, `obj.origin`, i.e. the account's state as it existed **before this block's mutations**: [2](#0-1) 

```go
func newObject(db *StateDB, address common.Address, acct *types.StateAccount) *stateObject {
	origin := acct
	if acct == nil {
		acct = types.NewEmptyStateAccount()
	}
	return &stateObject{
		...
		data:               *acct,
		...
	}
}
```

Only `o.setBalance(...)` is subsequently called. `o.data.Nonce`, `o.data.CodeHash`, and `o.data.Root` are therefore left equal to whatever they were in `obj.origin` — the account's *pre-existing* nonce, code hash, and storage root.

For a **freshly created** contract that self-destructs within the same transaction, `obj.origin` is `nil`, so `newObject` substitutes `types.NewEmptyStateAccount()` and the resulting account correctly ends up with nonce 0, empty code, and empty storage root (this is the scenario covered by `TestEIP8246SelfdestructNoBurn` and `TestEIP8246Create2RecreatesBalanceOnly`, both of which use contracts that are created and destroyed in the same transaction). [3](#0-2) 

However, for a **pre-existing** account (one that already had a nonzero nonce, deployed code, and/or non-empty storage before the current block/transaction) that self-destructs while retaining a non-zero balance, `obj.origin` is the account's real pre-transaction `*types.StateAccount`, carrying the old nonce, old `CodeHash`, and old storage `Root`. The code above copies all three of those fields verbatim into the "new" object and never resets them, directly contradicting the comment immediately above it ("nonce is reset to 0", "code is cleared", "all storage is cleared").

Additionally, because this branch never adds the address to `s.stateObjectsDestruct` (unlike the zero-balance branch a few lines below, or the EIP-161 empty-account branch), `handleDestruction` — which is responsible for emitting the storage-slot deletions during commit — never runs for this account: [4](#0-3) 

So even the underlying storage trie is left untouched: the "cleared storage" requirement is violated both at the state-object level and at the trie-commit level.

### Impact Explanation
This is a state-transition/consensus bug in an activated EVM code path (`rules.IsAmsterdam`), not gated behind any privilege or RPC boundary — any transaction that self-destructs a pre-existing account while it retains a non-zero balance triggers it. The resulting account:
- Retains its old nonce instead of being reset to 0 — this is an unauthorized modification of persisted account state relative to the spec (an account nonce that should be 0 remains at its old value, or vice-versa when compared against a correct implementation).
- Retains its old code (`CodeHash`) instead of having code cleared — the account effectively still has "code" and CodeHash on-chain that per EIP-8246 must be erased.
- Retains its old storage root instead of being wiped — old storage slots remain semantically reachable/attributed to the account when they should have been deleted.

Because every Amsterdam-activated Geth node computes this same (incorrect) state, this produces a **stateRoot / persisted account state that diverges from the EIP-8246 specification**. Any client that correctly implements EIP-8246 (clearing nonce/code/storage) will compute a different post-state and stateRoot for the same block, resulting in a consensus split between this implementation and a spec-compliant implementation once Amsterdam activates.

### Likelihood Explanation
High likelihood of being hit on any Amsterdam-era chain: it requires only an ordinary transaction where a pre-existing contract (with nonzero nonce and/or code and/or storage) calls `SELFDESTRUCT` while it still holds (or receives in the same call) a non-zero balance — a completely normal, unprivileged operation, not requiring any special permissions, malicious peer, or RPC access. `TestEIP8246SelfdestructNoBurn` and `TestEIP8246Create2RecreatesBalanceOnly` only exercise the "created-and-destroyed-in-the-same-tx" subcase (where `obj.origin == nil` masks the bug), so the pre-existing-account subcase is not covered by the existing test suite.

### Recommendation
In the `!obj.Balance().IsZero()` branch of `finaliseAmsterdam`, construct the surviving balance-only object with nonce reset to 0, code cleared to `types.EmptyCodeHash`, and storage root reset to `types.EmptyRootHash`, e.g. build it via `newObject(s, obj.address, obj.origin)` and then explicitly clear those fields (mirroring `types.NewEmptyStateAccount()`) before setting the balance, and mark the address in `s.stateObjectsDestruct` (unless already resurrected) so that pre-existing storage slots are actually deleted from the trie during commit.

### Proof of Concept
1. Deploy contract `A` in block N with `Nonce=5`, non-empty `Code`, and a populated storage slot (e.g. slot 1 = 1), giving it a non-empty `Root`.
2. In block N+1 (Amsterdam active), send a transaction that first sends `A` some ETH (or `A` already has a balance) and then calls into `A`, whose code executes `SELFDESTRUCT(A)` (self-destruct-to-self) so that its balance is preserved.
3. After block N+1 is processed, inspect `A`'s post-state via `StateDB.GetNonce(A)`, `StateDB.GetCodeSize(A)`, and the raw account `Root`/storage slot 1:
   - Expected per EIP-8246: `Nonce == 0`, `CodeSize == 0`, slot 1 reads as `0`.
   - Actual with this implementation: `Nonce == 5` (unchanged), `CodeSize > 0` (code hash still points at the old code), and slot 1 still reads `1` (storage never cleared, `Root` unchanged), because `o.data` was seeded straight from `obj.origin` and never reset.

```go
func (s *StateDB) handleDestruction(rules params.Rules) (map[common.Hash]*AccountDelete, []*trienode.NodeSet, error) {
	var (
		nodes   []*trienode.NodeSet
		deletes = make(map[common.Hash]*AccountDelete)
	)
	for addr, prevObj := range s.stateObjectsDestruct {
		prev := prevObj.origin

		// The account was non-existent, and it's marked as destructed in the scope
		// of block. It can be either case (a) or (b) and will be interpreted as
		// null->null state transition.
		// - for (a), skip it without doing anything
		// - for (b), the resurrected account with nil as original will be handled afterwards
		if prev == nil {
			continue
		}
		// The account was existent, it can be either case (c) or (d).
		addrHash := prevObj.addrHash()
		op := &AccountDelete{
			Address: addr,
			Origin:  prev,
		}
		deletes[addrHash] = op

		// Short circuit if the origin storage was empty.
		if prev.Root == types.EmptyRootHash || s.db.Type().Is(TypeUBT) {
			continue
		}
```
