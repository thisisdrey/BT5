### Title
Node advertises an unstored StackerDB slot version in `StackerDBChunkInv`, letting a remote peer force propagation of a stale/false inventory claim - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an unsolicited `StackerDBPushChunk` against the *currently committed* slot versions, then immediately patches and signs a `StackerDBChunkInv` reply claiming the new (higher) `slot_version` is now held — before the chunk has actually been written to the StackerDB. Storage only happens later, asynchronously, in the relayer (`Relayer::process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`), which independently re-validates the chunk against the DB state *at that later time*. If that later re-validation fails (e.g., a different/newer valid chunk for the same slot commits first, making this one stale, or another node-local condition prevents storage), the previously sent, signed `StackerDBChunkInv` still claims the chunk is present.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 
the code calls `validate_received_chunk` against the inventory snapshot obtained moments earlier from `make_StackerDBChunksInv_or_Nack`/`get_slot_versions`, then unconditionally mutates the reply payload's `slot_versions[slot_id] = chunk_data.chunk_data.slot_version` and wakes the sync state machine — all *before* any call to `try_replace_chunk`/`insert_chunk`. The function then signs and sends this patched `StackerDBChunkInv` back to the remote peer: [2](#0-1) 
and separately returns `(false, true)` telling the caller to forward the chunk to the relayer for actual storage.

The relayer path performs storage independently and later: [3](#0-2) 
`try_replace_chunk` re-verifies signer, version-freshness, and `max_writes` against the DB state *as it exists at that later point in time*: [4](#0-3) 
If this second check fails (most plausibly `StaleChunk`, because a different, newer valid write for the same slot landed first via a concurrent/parallel path — e.g., another peer's push, or the node's own downloaded-chunk sync — between the optimistic inventory patch and the relayer's actual write), the chunk is silently dropped without any correction being sent to the peer that received the earlier "accepted" inventory.

This breaks the equality between *advertised/served state* (what `StackerDBChunkInv` tells the network this replica holds) and *actually committed state* (what's in the SQLite `chunks` table) — directly analogous to the reported bug class where a partial/optimistic bookkeeping update diverges from the real underlying state.

### Impact Explanation
Downstream peers use `StackerDBChunkInv` slot-version advertisements to decide what to request and from whom during StackerDB sync (rarest-first/newest-first scheduling, per the module's own documentation). A false "I have version N" claim can cause peers relying on this replica to skip requesting the real data from other sources, delaying or preventing propagation of a legitimate chunk (e.g., a signer's block-approval message) across the network — a false-inventory condition. It does not permit unauthenticated writes (the relayer still enforces the signature/version checks before storing), so the impact is bounded to serving a stale/incorrect state claim rather than corrupting the DB itself.

### Likelihood Explanation
Triggering the optimistic inventory patch requires only sending an unsolicited, validly-signed `StackerDBPushChunk` from any connected peer — no privileged role is needed, matching the "remote, unprivileged" requirement. Causing the *later* `try_replace_chunk` to actually fail after the optimistic ack was sent requires a race (a second, newer valid write landing first through another path, e.g. a concurrent StackerDB sync round or another peer's push for the same slot), which is plausible given the described asynchronous processing model but not certain to be exploited on every attempt — moderate likelihood, contingent on timing.

### Recommendation
Do not mutate/sign the outbound `StackerDBChunkInv` to reflect a `slot_version` that has not yet been committed. Either (a) defer sending the `StackerDBChunkInv` reply until after the relayer has confirmed successful storage via `try_replace_chunk`, or (b) have the relayer emit a corrective follow-up inventory update (or a Nack/stale notice) whenever the deferred `try_replace_chunk` call fails after an optimistic ack was already sent, so remote peers' view of this replica's inventory never diverges from what is actually stored.

### Proof of Concept
1. Attacker (or any two ordinary peers, P1 and P2, racing) connects to victim node V and sends an unsolicited `StackerDBPushChunk` for `(contract_id, slot_id=S)` with `slot_version = N`, validly signed by the slot's owning key.
2. `V.handle_unsolicited_StackerDBPushChunk` calls `make_StackerDBChunksInv_or_Nack` (current committed version < N), passes `validate_received_chunk`, patches `slot_versions[S] = N` in the reply, signs it, and sends the `StackerDBChunkInv` back to the sender claiming version N is held. It returns `(false, true)` to forward the raw chunk to the relayer for storage. [5](#0-4) 
3. Concurrently, a second valid chunk for the same slot with version `N' > N` is committed to V's DB first (via a parallel sync round or a second push processed slightly earlier by the relayer thread).
4. When the relayer eventually processes the first chunk via `process_stacker_db_chunks` → `try_replace_chunk`, the DB's current version is now `N' > N`, so the call returns `Error::StaleChunk` and the chunk is dropped without storage. [6](#0-5) 
5. V never actually stores version N, yet it already told the original sender (via the signed `StackerDBChunkInv`) that slot S is at version N — a claim that was never true and is never retracted, resulting in the peer network operating on stale/incorrect inventory information for that replica.

                slot_validation.signer,
                slot_desc.slot_id,
