### Title
Unconditional block relay regardless of `broadcast`/auth gate - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
`RPCPostBlockRequestHandler::try_handle_request` invokes `node.set_relay_message(...)` based solely on `data_resp.accepted`, never consulting `self.broadcast`. This means the `broadcast=1` + `authorization` gate enforced in `try_parse_request` has no effect on whether the node actually relays the block to its peers — any caller (authenticated or not, with or without `broadcast=1`) whose posted block is accepted by chainstate validation will cause the node to relay it network-wide.

### Finding Description
`try_parse_request` computes `broadcast` and `authenticated` and enforces: `if broadcast && !authenticated { return 401 }`, storing the result in `self.broadcast` [1](#0-0) . This value is passed into `Relayer::process_new_nakamoto_block_ext` as the `broadcast` parameter [2](#0-1) .

However, the subsequent decision to actually queue the block for network relay is made independently:
```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
``` [3](#0-2) 

This check depends only on `data_resp.accepted` (whether chainstate accepted the block), not on `self.broadcast`. So the exact case the question raises (authenticated request, `broadcast` query key absent → `self.broadcast = Some(false)`) does trigger relay whenever the block is accepted — contrary to the intended design that relay should require `broadcast == Some(true)`. Worse, this holds for *every* accepted submission regardless of authentication status at all, since `self.broadcast` is simply never read at the relay decision site.

### Impact Explanation
Any remote party able to reach the `/v3/blocks/upload/` RPC endpoint (no `broadcast=1` and no valid credentials required) can cause the node to invoke `node.set_relay_message`, forcing it to gossip the submitted block to all its peers whenever chainstate accepts it. This defeats the purpose of the `broadcast` opt-in/auth-gate entirely: the endpoint's access control model intends that unauthenticated/non-broadcast submissions be locally staged only, but the implementation relays on acceptance unconditionally. Because acceptance still requires the block to pass full Nakamoto consensus validation inside `process_new_nakamoto_block_ext`, this is not forgery of block content, but it is a genuine auth-bypass of the relay gate: an unauthenticated or non-broadcast-requesting caller obtains a network-wide side effect (peer relay) that the API explicitly tries to restrict to authenticated broadcast requests.

### Likelihood Explanation
No special preconditions beyond having the node's RPC port reachable and being able to submit a well-formed, already-valid Nakamoto block (e.g., a block that would legitimately be accepted, such as one it can obtain via other means). No password/secret is required at all for the relay side effect, only for the (irrelevant) `broadcast` query parameter which is ignored at the point where relay is actually decided. This is trivially and repeatably reachable on every accepted POST.

### Recommendation
Gate the `node.set_relay_message` call on `self.broadcast == Some(true)` in addition to `data_resp.accepted`, e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
so that the auth+broadcast check performed in `try_parse_request` actually controls whether the node relays the block.
