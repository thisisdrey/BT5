### Title
Newly registered reward token with index still equal to `INITIAL_INDEX` credits `balance * 1e18` rewards to any account, draining the distributor - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` only back-fills `accountIndexOf` to `INITIAL_INDEX` when the token's global index is *strictly greater* than `INITIAL_INDEX`. Whenever the global index is still exactly `INITIAL_INDEX` — which happens for any token freshly added via `updateTokenSpeed`/`syncTokenSpeed`, and persists as long as `totalSupply() == 0` or the same block — an uninitialized account keeps `accountIndex == 0`, so `deltaIndex = INITIAL_INDEX - 0 = 1e18` and the account is credited `balance.wadMul(1e18)` ≈ its full token balance in reward tokens. An unprivileged attacker can trigger this through the public `updateBeforeMintOrBurn` / `claimRewards` entry points and drain the distributor's reward-token balance.

### Finding Description
In `_updateTokenSpeed`, a newly rewarded token is registered with `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` [1](#0-0) . The index only grows when `_deltaTimestamps > 0 && _speed > 0 && totalSupply > 0`; otherwise `_newIndex` stays `0` and the stored index remains `INITIAL_INDEX` [2](#0-1) .

`_calculateTokenDelta` then computes:

```solidity
// contracts/RewardsDistributor.sol#L217-L231
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The strict `>` means that while `_tokenIndex == INITIAL_INDEX`, a first-time account's index stays `0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balance * 1e18` (in wad terms, `balance.wadMul(1e18) = balance`) [3](#0-2) . `updateBeforeMintOrBurn` is permissionless ("This function also may be called by anyone") and routes into `_updateTokensAccruedOf` whenever `index > 0` [4](#0-3) . `claimRewards` then pays out `tokensAccruedOf` up to the distributor's full `rewardToken` balance [5](#0-4) .

This is the same bug class as the reference report: a reward token entering the tracked set while a snapshot/initialization edge leaves an index at an uninitialized/boundary value, corrupting reward accrual. The reference produced underflow → freeze; Metronome's variant produces over-accrual → theft of unclaimed yield (and effective freeze for all legitimate claimants once the distributor is drained).

### Impact Explanation
Direct theft of unclaimed yield: the attacker mints themselves `tokensAccruedOf = balance * 1e18` reward units with a single call and immediately claims up to the distributor's entire `rewardToken` balance, stealing rewards owed to all other depositors/borrowers. `nonReentrant`, `onlyIfDistributorExists`, and `onlyIfTokenExists` do not stop this — the token is legitimately registered and the calls are whitelisted paths.

### Likelihood Explanation
Medium. Preconditions: a governor/keeper adds (or re-registers) a DepositToken/DebtToken speed while its index is `INITIAL_INDEX`. The attacker can act in the very same block as `updateTokenSpeed` (`_deltaTimestamps == 0` keeps the index pinned), or any later time while `totalSupply() == 0` keeps `index == INITIAL_INDEX`. Attacker only needs a nonzero `DepositToken` balance (a deposit) and two public calls; no privileged role is required for execution.

### Recommendation
Treat the boundary consistently: initialize the account index whenever the token index is at or above `INITIAL_INDEX`, e.g. change the condition to `if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) _accountIndex = INITIAL_INDEX;` (or `_accountIndex = _tokenIndex`), so a first-time account at the initial index accrues zero. Equivalently, skip accrual when `accountIndex == 0` on the same block the token was registered.

### Proof of Concept
Hardhat fork sketch:

1. Governor (or `tokenSpeedKeeper` via `syncTokenSpeed`) calls `updateTokenSpeed(depositToken, speed)` for a new DepositToken → `tokenStates[depositToken].index == INITIAL_INDEX`.
2. Attacker holds `B > 0` of `depositToken` (deposited underlying via `Pool.deposit`), `accountIndexOf[depositToken][attacker] == 0`.
3. Same block (or while `depositToken.totalSupply() == 0`): attacker calls `rewardsDistributor.updateBeforeMintOrBurn(depositToken, attacker)` → `_deltaIndex = 1e18`, `tokensAccruedOf[attacker] = B.wadMul(1e18)`.
4. Attacker calls `rewardsDistributor.claimRewards(attacker)` → receives `min(accrued, rewardToken.balanceOf(distributor))`, draining unclaimed rewards.
5. Assert: `rewardToken.balanceOf(distributor)` decreased by ~`min(B, balance)` while legitimate users' `claimable()` can no longer be paid.
