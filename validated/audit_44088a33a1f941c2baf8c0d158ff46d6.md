### Title
Missing `MAX_PAYLOAD_LEN`/`MAX_MESSAGE_LEN` check in mempool-query POST handler allows unbounded body size before deserialization - (File: stackslib/src/net/api/postmempoolquery.rs)

### Summary
`RPCMempoolQueryRequestHandler::try_parse_request` only checks that `preamble.get_content_length() != 0` before deserializing the body into `MemPoolSyncData`, unlike every sibling POST handler in the same module (`postblock.rs`, `postmicroblock.rs`, `posttransaction.rs`, `postfeerate.rs`, `postblock_proposal.rs`, `blocksimulate.rs`) which all explicitly reject requests whose `Content-Length` exceeds `MAX_PAYLOAD_LEN` before touching the body. This asymmetry means the attacker-controlled `Content-Length` header value is used by the generic HTTP framing layer (`payload_len()` in `stackslib/src/net/httpcore.rs`) to size the body buffer with no per-endpoint cap applied prior to `consensus_deserialize`.

### Finding Description
`try_parse_request` in `postmempoolquery.rs` does: [1](#0-0) 
It checks only for a zero-length body and then immediately calls `MemPoolSyncData::consensus_deserialize(&mut body_ptr)` on the raw `body: &[u8]` slice — there is no `if preamble.get_content_length() > MAX_PAYLOAD_LEN` guard, in contrast to the pattern used consistently elsewhere in the same directory, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

The two `MAX_MESSAGE_LEN` references that do exist in `postmempoolquery.rs` are unrelated to the inbound request-body size check: one bounds the *response streaming* chunk size (`generate_next_chunk`), and the other bounds the *client-side response* parser (`try_parse_response`), not the server-side request parser: [5](#0-4) [6](#0-5) 

The generic HTTP framing layer (`ProtocolFamily` impl for `StacksHttp`) determines the number of bytes to buffer for a known-length request purely from the attacker-supplied `Content-Length` header, with no cap applied at that layer either: [7](#0-6) 
The per-endpoint `MAX_PAYLOAD_LEN` check used by sibling handlers is therefore the actual enforcement mechanism in this codebase for request bodies of known length, and it is missing from `postmempoolquery.rs`. Since the body is fully materialized by the framing layer using the wire-controlled `Content-Length` before `try_parse_request` (and hence before any size check in this handler) is invoked, a remote unauthenticated client can supply a large `Content-Length` and body to force the node to buffer/allocate that many bytes prior to any endpoint-level rejection.

### Impact Explanation
A single unauthenticated `POST /v2/mempool/query` request with a large `Content-Length` forces the node's RPC handling layer to allocate/buffer a body of attacker-chosen size before the endpoint can reject it, unlike the sibling endpoints that reject the request based on `Content-Length` alone. This is a remote, unauthenticated, single-message resource-exhaustion vector reachable by any RPC client, matching the Critical DoS category (remote unauthenticated allocation DoS via a single oversized request), and it is trivially repeatable.

### Likelihood Explanation
No authentication, peer registration, StackerDB slot ownership, or special node/tip state is required — `/v2/mempool/query` is a public RPC endpoint. The attacker only needs network access to the node's RPC port and the ability to send a single HTTP POST with a crafted `Content-Length` and body. Cost to the attacker is negligible and the request can be repeated indefinitely.

### Recommendation
Add an explicit `Content-Length` bound check in `RPCMempoolQueryRequestHandler::try_parse_request`, mirroring the pattern used in `postblock.rs`/`postmicroblock.rs`/`postfeerate.rs`/`postblock_proposal.rs`:
```rust
if preamble.get_content_length() > MAX_PAYLOAD_LEN {
    return Err(Error::DecodeError(
        "Invalid Http request: mempool query body is too big".to_string(),
    ));
}
```
placed before `MemPoolSyncData::consensus_deserialize` is invoked, and ideally verify that the generic HTTP framing layer (`payload_len`/body-buffering code in `httpcore.rs`) also enforces a hard upper bound independent of per-handler checks, so a missing per-handler check cannot alone create an allocation DoS.

### Proof of Concept
Rust test in `stackslib/src/net/api/postmempoolquery.rs` (or a new integration test in the same module's test harness used by other `postX` handlers):
1. Construct an `HttpRequestPreamble` for `POST /v2/mempool/query` with `Content-Length` set to a value between `MAX_PAYLOAD_LEN` and `MAX_MESSAGE_LEN` (or larger), and a body of that size filled with dummy bytes (not a valid `MemPoolSyncData` encoding).
2. Call `RPCMempoolQueryRequestHandler::try_parse_request` directly (or via `StacksHttp::handle_try_parse_request` test helper as used in other `postX` handler tests) with this preamble/body.
3. Assert that `try_parse_request` returns `Err(Error::DecodeError(..))` due to the size check *before* `MemPoolSyncData::consensus_deserialize` runs — the assertion should fail on the current code because no such check exists and execution proceeds directly to `consensus_deserialize`, demonstrating the missing bound.
