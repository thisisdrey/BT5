## Analysis

This is a valid analog. The Zest v2 vault contracts implement the exact same anti-pattern described in the report: they call an SIP-10 `transfer` (the Stacks-token equivalent of `transferFrom`) to pull tokens into the vault, then perform all downstream share-minting and internal accounting using the *nominal* amount requested rather than the amount actually received.

### Root cause

Every vault's `receive-underlying` helper blindly calls the underlying token's `transfer` without checking the vault's balance before/after: [1](#0-0) [2](#0-1) 

The `deposit` function computes `inkind` (shares to mint) from the *nominal* `amount` via `convert-to-shares-preview`, *before* the token transfer occurs, and then unconditionally bumps the internal `assets` accumulator by that same nominal `amount` after the transfer — never re-checking the vault's real token balance: [3](#0-2) 

This mirrors exactly the Saddle `SwapUtils.swap`/`addLiquidity` pattern flagged in the report: `safeTransferFrom`/`transfer` is trusted to move the full stated amount, and all subsequent math (shares minted, `assets` ledger) assumes that assumption holds.

### Why it matters here

`assets` is the core of the vault's ERC4626-style share accounting (`total-assets-preview`, `convert-to-shares-preview`, `convert-to-assets-preview`) which underlies the "vault share math and interest accrual" surface explicitly listed as in-scope: [4](#0-3) 

If any of the vault-wrapped underlying tokens (USDC, USDH, sBTC, stSTX, stSTXbtc, wrapped STX) were to enable a transfer fee — as USDT itself did/could, and as the report explicitly warns can happen even when current fee is `0` — a depositor would be credited shares priced on the full nominal `amount`, while the vault's `assets` ledger is incremented by that same nominal amount even though the actual tokens held increased by less. This creates a permanent gap between the vault's believed backing (`assets`) and its real token balance (`ubalance`), which is never reconciled anywhere in the deposit/withdraw code path.

### Impact

Because `assets`/`total-supply` sets the exchange rate for every subsequent depositor and withdrawer, this systematically overstates the vault's real backing. Later redeemers exhaust the real underlying balance before all share-holders can redeem at the accounted rate — a shortfall that is not a user error but a direct accounting bug in this codebase, producing protocol insolvency / permanent freezing of funds for the vault's other depositors. The same nominal-vs-actual assumption is repeated in `market.clar`'s `supply-collateral-add`, which uses `ft transfer` and then feeds the same nominal `amount` into `vault-deposit`: [5](#0-4) 

### Likelihood

This requires the underlying SIP-10 token to actually implement a non-zero transfer fee, which is not the current behavior of any of the wrapped assets (USDC, USDH, sBTC, stSTX, stSTXbtc, STX-wrapper) as far as the indexed code shows. The report's own precedent (USDT fee currently `0%` but "may change") is the basis for treating this as a legitimate defensive-accounting gap rather than a purely theoretical concern, since none of these vault contracts have any mechanism (balance-diffing, fee-detection) to protect against it if it did change.

### Title
Fee-on-transfer underlying tokens break vault share accounting via unchecked `receive-underlying` - (File: mainnet/contracts/vault/v0-vault-usdc.clar / v0-vault-usdh.clar / v0-vault-sbtc.clar / v0-vault-ststx.clar / v0-vault-stx.clar / v0-vault-ststxbtc.clar)

### Summary
All six vault contracts pull underlying tokens into the vault via a bare `transfer` call in `receive-underlying`, then mint shares and update the `assets` ledger using the caller-supplied nominal `amount` rather than the balance actually received.

### Finding Description
`receive-underlying` performs `(contract-call? <token> transfer amount account current-contract none)` with no before/after balance check. `deposit` computes `inkind` shares from `amount` via `convert-to-shares-preview` and then does `(var-set assets (+ current-assets amount))` unconditionally after the transfer, assuming the full `amount` was received. If the underlying SIP-10 token ever deducts a transfer fee, the vault credits shares and internal assets for tokens it never actually received. [3](#0-2) 

### Impact Explanation
The `assets` variable and `total-supply` set the exchange rate (`convert-to-assets`) used by every future `redeem`. An inflated `assets` value relative to the vault's real token balance means the last redeemers cannot be paid in full — this is protocol insolvency / permanent freezing of funds for depositors, a Critical-class impact under vault share math and interest accrual.

### Likelihood Explanation
Requires the wrapped underlying token to introduce a non-zero transfer fee (currently none do). This is analogous to the original USDT-fee concern the report is based on — a latent, not-yet-triggered but structurally unguarded risk with no compensating balance check anywhere in the deposit/withdraw code.

### Recommendation
In `receive-underlying`, capture the vault's token balance before and after the `transfer` call, and use the delta (not the nominal `amount`) for `convert-to-shares-preview` and the `assets` ledger update, mirroring the balance-diffing recommendation in the original report.

### Proof of Concept
1. Assume vault's underlying token (e.g., a future-fee-enabled USDC-like token) charges a 1% transfer fee.
2. Attacker/user calls `deposit(1000, min_out, recipient)`.
3. `inkind` shares are minted based on `amount = 1000`; `assets` is incremented by `1000`.
4. Only `990` tokens actually arrive at the vault (`ubalance` reflects `990`, but `assets` var says `+1000`).
5. Repeating across all depositors accumulates a growing gap between `assets` (believed backing) and the vault's real token balance, until later `redeem` calls fail or drain remaining real balance disproportionately, leaving some depositors unable to redeem.
