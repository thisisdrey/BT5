### Title
Quarantine object migration occurs before the reference-transaction hook can still veto the push, allowing unbounded repository storage growth via repeated aborted pushes - ([File: internal/gitaly/hook/updateref/update_with_hooks.go])

### Summary
`UpdaterWithHooks.UpdateReference` irreversibly migrates all quarantined objects from a push into the repository's main object directory *before* it has confirmed that the reference update itself will succeed. Multiple later gating points — the `update` hook, the `reference-transaction` hook's `Preparing`/`Prepared` votes (which can return `ABORT`/`STOP` from Praefect, analogous to a "paused" gate), and `updater.Prepare()`/`Commit()` — can still fail and abort the whole `UpdateReference` call. When any of these later steps rejects the change, the function simply returns an error; the objects that were already migrated out of quarantine remain permanently in the repository, unreferenced by anything, with no compensating cleanup. This mirrors the external report's pattern: an irreversible "burn"-equivalent action (object migration) is performed before the corresponding "mint"-equivalent action (reference commit) is guaranteed, and a downstream gate (pause/vote/hook) can still block the second half, leaving a stuck, unrecoverable side effect.

### Finding Description
In `UpdateReference`, the sequence is:
1. `PreReceiveHook` runs against the quarantined repo.
2. If it passes, `quarantineDir.Migrate(ctx)` is called [1](#0-0)  — this hard-links/renames every object out of the per-push quarantine directory into the repository's real `objects/` directory. This step is explicitly documented as needing to happen "before we start updating the refs," and once done it cannot be undone; `Migrate` deletes the quarantine source directory entirely as part of the move [2](#0-1) .
3. Only *after* this irreversible migration does the code run `UpdateHook`, queue the ref update, and drive the `reference-transaction` hook through `Preparing` → `Prepared` → `Commit` [3](#0-2) .
4. Any of these can still fail and cause `UpdateReference` to return an error without ever committing the reference: the `update` hook can reject the change, `updater.Prepare()`/`Commit()` can fail, and — most relevant to the "pause" analogy — the reference-transaction hook's vote can be rejected by Praefect (`ABORT`) or the transaction can be `STOP`ped, both of which are explicit, expected outcomes handled in `ReferenceTransactionHook` [4](#0-3)  and exercised in tests [5](#0-4) .

In every one of these later-failure cases, the objects migrated in step 2 stay in the repository's object database permanently: they are no longer quarantined (so they won't be deleted as a rejected push would be), yet no reference points to them, so they become dangling objects that only get cleaned up by a future `git gc`/prune cycle (which, per `doc/object_quarantine.md`, is explicitly the slow path this quarantine mechanism was designed to avoid) [6](#0-5) .

### Impact Explanation
An ordinary, unprivileged user who can push to a repository (or trigger any RPC that uses `UpdateReference` with a quarantine directory, e.g. `UserCreateTag`/custom hooks scenarios shown in tests [7](#0-6) ) can repeatedly push large blobs/commits and arrange (via custom hooks, hook misconfiguration, or transient Praefect vote failures) for the reference-transaction hook or `updater.Commit()` to fail *after* the pre-receive hook accepted the push. Each such attempt permanently inflates the repository's object store with garbage that is not cleaned up immediately, unlike a normal rejected push (where the whole quarantine directory is simply `rm -rf`'d). Repeated abuse leads to unbounded on-disk storage growth until the next `git gc` cycle — a disk-exhaustion DoS vector against the Gitaly node/storage.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a way to make the hooks/vote fail specifically *after* the pre-receive hook succeeds (e.g. relying on custom `update` hooks, or unlucky/attacker-influenced Praefect quorum failures during the reference-transaction vote), which is a narrower window than a simple push rejection. However, the mechanism is entirely reachable from a normal authenticated push and does not require any privileged actor.

### Recommendation
Do not migrate quarantined objects out of the quarantine directory until the entire reference update — including the `update` hook and reference-transaction hook `Prepared`/`Committed` votes — has succeeded. If migration must happen earlier for `git-update-ref` verification purposes, add a compensating step that removes/re-quarantines the newly migrated objects (or schedules immediate deletion of now-unreferenced objects) whenever any subsequent step in `UpdateReference` fails, so a failed push cannot leave permanent, uncollected garbage in the object store.

### Proof of Concept
1. Configure a repository with a custom `reference-transaction` or `update` hook (or a Praefect-managed repo where the reference-transaction vote is arranged to return `ABORT`/`STOP` at the `Prepared` phase, as demonstrated in `TestReferenceTransactionHook`'s "hook fails with failed vote" case [8](#0-7) ).
2. Push a commit containing a large blob. The `pre-receive` hook accepts it, so `quarantineDir.Migrate(ctx)` runs and moves the large blob permanently into `objects/`.
3. The subsequent `update` hook or reference-transaction `Prepared` vote fails, causing `UpdateReference` to return an error and the overall push to be reported as failed to the client.
4. Inspect the repository's object database: the large blob object is present on disk even though no reference points to it and the client was told the push failed, and it will remain until the next `git gc` run.

```go
// Migrate migrates all objects part of the quarantine directory into the repository and thus makes
// them generally available. This implementation follows the git.git's `tmp_objdir_migrate()`.
func (d *Dir) Migrate(ctx context.Context) error {
	repoPath, err := d.locator.GetRepoPath(ctx, d.repo, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return fmt.Errorf("migrating quarantine: %w", err)
	}

	objectDir := d.repo.GetGitObjectDirectory()
	if objectDir == "" {
		// Migrate the objects to the default object directory if the repository
		// didn't have an object directory explicitly configured.
		objectDir = "objects"
	}

	return migrate(ctx, d.dir.Path(), filepath.Join(repoPath, objectDir))
}
```

**File:** doc/object_quarantine.md (L31-38)
```markdown
`pre-receive` rejects the push (step 5 above). It changes the _timing_ of the
cleanup. Without object quarantine, objects that were part of a
rejected push would sit around until `git gc` would judge them as both
unused and "old". How long that takes depends on how often `git gc`
runs (or `git prune`), and on the configuration of when objects are
"old". Because of object quarantine, rejected objects can be deleted
immediately: Git can just `rm -rf` the quarantine directory and
they're gone.
```
