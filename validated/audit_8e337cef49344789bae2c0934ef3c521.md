### Title
Unauthenticated `RecvError` message allows remote attackers to force tunnel teardown (state poisoning) - (File: outside.go)

### Summary
Nebula's `RecvError` control message is processed entirely in cleartext, with no cryptographic authentication tying it to the peer's certificate or an active Noise session. Any entity that can send a UDP packet to a node's listen port — with no CA-signed certificate and no completed handshake — can trigger `handleRecvError`, which unconditionally tears down an active, fully-authenticated tunnel if the attacker can supply the correct `RemoteIndex` and the tunnel's remote address happens to not yet be pinned (or is spoofable at the UDP layer). This mirrors the report's bug class: a value from an untrusted, attacker-influenced channel (`h.RemoteIndex`, a plaintext 32-bit field visible on every packet) is trusted to make a high-impact state change (`closeTunnel`) without adequate verification, analogous to `OCL_ZVE.sol::forwardYield` trusting a manipulable `fetchBasis()` value to gate a large, damaging state transition.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets to `f.handleRecvError` before any encryption/authentication check is performed — this happens in the same unencrypted-packet switch as `Handshake`: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely by the plaintext `h.RemoteIndex` value carried in the packet header, and if the stored remote address either isn't set yet or happens to match the packet's source address, it destroys the tunnel with no further authentication: [2](#0-1) 

The `RemoteIndex` is a 32-bit value transmitted unencrypted in the header of every single packet on the wire for a tunnel: [3](#0-2) [4](#0-3) 

Because this value is neither a nonce that resets per-message nor bound to any signature, an attacker who can observe or brute force it, and who can present the matching source `netip.AddrPort` (or induce a state where `hr` isn't yet locked), can force `closeTunnel` — deleting the hostinfo and purging cached lighthouse state — for a tunnel between two hosts that both hold valid, CA-signed certificates. Notably, `handleRecvError`'s only defense is an equality check against the currently pinned remote (`hr.IsValid() && hr != addr`), which does not verify the sender cryptographically at all; it merely compares network addresses observed at the UDP layer, which is spoofable by an off-path/on-path attacker without holding a certificate.

This is architecturally the same failure pattern as the `OCL_ZVE.sol` finding: a security-relevant decision (teardown of an authenticated session state / basis reset) is driven by an unauthenticated, attacker-observable/attacker-influenceable value instead of being gated behind proof of possession of a trusted credential.

### Impact Explanation
An attacker with no CA-signed certificate can repeatedly force teardown of established tunnels between legitimate, certificate-holding peers, causing denial of service, tunnel flapping, and loss of the in-flight state (relay associations, lighthouse cache, connection manager tracking) for the affected hostinfo: [5](#0-4) 

Repeated invocation degrades availability of the mesh and can be used to selectively disconnect targeted peers, which is a legitimate remote-crash/remote-DoS-class impact under the accepted categories (remote state poisoning / firewall & session integrity bypass), achievable without any valid certificate.

### Likelihood Explanation
The changelog itself documents that this exact message type has previously been treated as a security-sensitive signal ("You can set `listen.send_recv_error` to control the conditions in which `recv_error` messages are sent. Sending these messages can expose the fact that Nebula is running on a host") and that `accept_recv_error`/`send_recv_error` policy knobs (`always`/`never`/`private`) exist specifically to mitigate abuse of this channel: [6](#0-5) 

This indicates the project is aware `RecvError` is reachable by unauthenticated parties and has only a coarse allow/deny-by-source-network mitigation (`ShouldRecvError`), not cryptographic authentication. The likelihood is Medium: successfully exploiting it requires either observing the 32-bit `RemoteIndex` (visible on every packet if any traffic is sniffable) or being positioned to spoof the peer's source address before the remote is pinned, similar to the "possible but conditional" probability that Sherlock judges accepted as Medium for the original finding (only one favorable window is needed, not sustained access).

### Recommendation
Do not action `RecvError` based solely on the plaintext `RemoteIndex` and observed source address. Options:
1. Require `RecvError` to be authenticated (e.g., HMAC/AEAD-tagged with a value derived from the session's cipher state) before honoring it, similar to how the replay-window/Noise keys authenticate the `Message` type.
2. At minimum, rate-limit and require multiple independent unauthenticated `RecvError` observations combined with connection-manager idle detection before tearing down a tunnel, rather than acting on a single unauthenticated datagram.
3. Tighten `handleRecvError`'s address check so an unset (`!hr.IsValid()`) remote can never be torn down by an unauthenticated `RecvError` — currently that path is unconditionally trusted.

### Proof of Concept
1. Attacker (holding no CA-signed certificate) passively observes or otherwise learns the `RemoteIndex` used between victim node A and legitimate peer B (visible in cleartext on every packet header per `header.Parse`).
2. Attacker crafts a raw UDP datagram to A's listen port with `header.Type = RecvError`, `RemoteIndex` = the observed index, and a source address chosen to equal (or spoof) B's currently pinned remote address — or sent while A has not yet pinned a remote for that hostinfo.
3. A's `readOutsidePackets` routes the packet directly to `handleRecvError` without any decryption or certificate check.
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, the address check passes (equal or unset), and `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)` execute, destroying a fully-authenticated tunnel state between two legitimate, CA-verified peers — achieved entirely by an attacker holding no certificate.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```

```go
// Parse is a helper function to parses given bytes into new Header struct
func (h *H) Parse(b []byte) error {
	if len(b) < Len {
		return ErrHeaderTooShort
	}
	// get upper 4 bytes
	h.Version = uint8((b[0] >> 4) & 0x0f)
	// get lower 4 bytes
	h.Type = MessageType(b[0] & 0x0f)
	h.Subtype = MessageSubType(b[1])
	h.Reserved = binary.BigEndian.Uint16(b[2:4])
	h.RemoteIndex = binary.BigEndian.Uint32(b[4:8])
	h.MessageCounter = binary.BigEndian.Uint64(b[8:16])
	return nil
}
```
