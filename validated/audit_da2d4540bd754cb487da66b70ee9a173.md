Audit Report

## Title
Unbacked XCM asset credit can be minted via ERC20 contracts that lie about `transfer` success - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `::deposit_asset_with_surplus` treat any `pallet-revive` contract matched by `ERC20Matcher` as a valid ERC20 fungible asset for XCM purposes. Both functions call the token's `transfer()` function via `bare_call` and accept the operation as successful purely on `!did_revert()` plus a decoded `true` boolean return, never verifying that the `TransfersCheckingAccount`'s (or beneficiary's) actual token balance changed by `amount`.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` to move `amount` from `who` to the checking account, and on a non-reverted call decodes only the boolean return value before minting `Erc20Credit(amount)` into the XCM holding register. [3](#0-2)  The same pattern recurs in `deposit_asset_with_surplus`, which trusts `Ok(true)` from the decoded return to release `surplus` and considers the deposit complete. [4](#0-3) 

`Erc20Credit` is explicitly documented to perform no runtime-level balance enforcement, relying entirely on the target contract's own accounting: [5](#0-4) 

Critically, the `ERC20Matcher` used to select which contract addresses are eligible for this transactor imposes no allowlist or governance-controlled registry — `IsLocalAccountKey20` matches *any* `Location` of the form `(0, [AccountKey20{..}])`: [1](#0-0)  This is wired directly into the Asset Hub Westend runtime's `AssetTransactors` tuple: [2](#0-1) 

Consequently, an unprivileged user can deploy a `pallet-revive` contract with a `transfer(address,uint256)` function that always ABI-encodes and returns `true` while performing no storage mutation, and reference it by its `H160` address in an XCM program. The transactor has no defense against this because it checks only the decoded return value, not an actual balance delta before/after the call.

## Impact Explanation
This breaks value-conservation for XCM-held "ERC20" assets: an attacker can fabricate `Erc20Credit` holding entries with no corresponding real balance movement in the underlying contract or `TransfersCheckingAccount`. Since the holding register treats this credit identically to a genuine backed withdrawal, it can be forwarded via `DepositAsset`, `InitiateReserveWithdraw`, or `InitiateTeleport` to other locations/chains that assume 1:1 backing, producing unbacked mint/settlement and potential fund lock for legitimate holders when the real underlying balance turns out to be insufficient. This matches the "theft or unbacked mint" and "permanent user-fund or bridge-state lock" impact categories in the Polkadot SDK Impact Gate.

## Likelihood Explanation
High likelihood: deploying a `pallet-revive` contract and submitting an XCM program (e.g. via `pallet_xcm::execute`) referencing it via `AccountKey20` requires only ordinary contract-deployment and extrinsic-submission rights available to any unprivileged user — no governance, relayer compromise, or privileged origin is needed, since `ERC20Matcher`/`IsLocalAccountKey20` places no restriction on which contract addresses qualify.

## Recommendation
Before minting `Erc20Credit` or treating a deposit as successful, query the target account's balance via `IERC20::balanceOfCall` immediately before and after the `bare_call`, and require the observed delta to equal exactly `amount`, rather than trusting only the decoded boolean return.

## Proof of Concept
1. Deploy a `pallet-revive` contract `FakeERC20` whose `transfer(address,uint256)` always returns ABI-encoded `true` without mutating any balance storage.
2. Submit an XCM program via `pallet_xcm::execute` containing `WithdrawAsset` for `Asset { id: AccountKey20 { key: FakeERC20_address, network: None }.into(), fun: Fungible(amount) }` from the attacker's own signed origin.
3. `ERC20Transactor::withdraw_asset_with_surplus` invokes `FakeERC20.transfer(checking_address, amount)`, which returns `true` without moving balance; the transactor mints `Erc20Credit(amount)` into `AssetsInHolding` per lines 191-203 of `erc20_transactor.rs`.
4. Follow with `DepositAsset` or `InitiateReserveWithdraw`/`InitiateTeleport` to move the fabricated `amount` to a beneficiary or another chain, while `TransfersCheckingAccount`'s real balance in `FakeERC20` never changed — demonstrating unbacked value creation, analogous to the existing negative test `smart_contract_does_not_return_bool_fails` but using a contract that returns a syntactically valid `true` instead of an undecodable type.
