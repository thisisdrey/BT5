### Title
Missing contract-domain binding in `SlotMetadata` signature allows cross-StackerDB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
### Finding Description
`SlotMetadata::auth_digest()` computes the digest that a StackerDB chunk's signature is checked against using only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB smart contract (its `QualifiedContractIdentifier`) that the chunk is destined for: [1](#0-0) 

`verify()` recovers the public key from this contract-agnostic digest and only checks that it hashes to the expected `principal` address, again with no reference to which contract the caller is validating against: [2](#0-1) 

Chunk acceptance paths (`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` and `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`) look up the expected signer for a slot *per contract* via `get_slot_validation`/`get_slot_signer`, then call `SlotMetadata::verify(&addr)` — but since the digest itself carries no contract identity, any signature valid for slot `X` in contract `A` is equally valid for slot `X` in contract `B`, provided the same address is registered as the owner of slot `X` in `B` too: [3](#0-2) [4](#0-3) 

This is not a theoretical coincidence in this codebase: the signer-message StackerDB contracts are explicitly designed so that *many* contracts share the exact same slot→signer assignment. `.signers-0-xxx.clar` (one deployed per message type) simply forwards to the shared `.signers` contract to fetch the slot list: [5](#0-4) 

and `.signers` stores exactly one slot list per reward-cycle parity (`stackerdb-signer-slots-0` / `stackerdb-signer-slots-1`), reused by *every* `.signers-0-{message_id}` (or `.signers-1-{message_id}`) contract: [6](#0-5) 

So the same signer address `S` occupies identical `slot_id` across all `.signers-0-1`, `.signers-0-2`, `.signers-0-3`, … contracts (each carrying a distinct signer message type). A chunk signed by `S` for one of these contracts is bit-for-bit valid for all the others, because the signature never commits to the contract/message-type domain.

### Impact Explanation
An unprivileged remote attacker who observes any legitimately signed `StackerDBChunkData` for signer `S` — either via the public gossip broadcast (`StackerDBPushChunk`) or by fetching it from the public `GET /v2/stackerdb/.../chunks/...` RPC endpoint on any node — can replay that exact same chunk bytes (`slot_id`, `slot_version`, `sig`, `data`) as a POST to a *different* `.signers-0-{other_message_id}` contract's chunk endpoint on any node. As long as the target slot's current stored version is below the replayed `slot_version` (true on a fresh/behind node, or attacker can pick a high version once and permanently poison the slot up to `max_writes = u32::MAX`), the chunk passes `validate_received_chunk`/`try_replace_chunk` and is written into a StackerDB replica it was never intended for. This is an unauthenticated/unauthorized write into StackerDB state for a signer who did not author data for that specific contract/message-type — matching the Critical-severity class of "unauthenticated/unauthorized write to state or StackerDB" and, via gossip re-relay of the injected chunk, network-wide propagation of the cross-domain forged content to other honest nodes.

Concretely this can be used to: corrupt a `.signers-0-2` slot with bytes that were validly signed only for `.signers-0-1` (breaking message-type framing expectations for any consumer that deserializes the slot assuming a specific `SignerMessage` variant), and to irreversibly block future legitimate updates to that slot by burning through the (effectively unbounded) version counter with garbage cross-contract data.

### Likelihood Explanation
High. No secrets, no privileged role, and no consensus/chain-state manipulation are required — only observation of one broadcast/publicly-fetchable chunk and a normal HTTP POST to the `poststackerdbchunk` RPC endpoint (or a p2p `StackerDBPushChunk`) against a *different, but existing and slot-aligned* StackerDB contract. Every signer already writes to multiple `.signers-0-*`/`.signers-1-*` contracts with the identical slot assignment, so viable targets exist for every active signer on every reward cycle.

### Recommendation
Bind the signed digest to the StackerDB's identity, not just to slot/version/data. Concretely, include the `QualifiedContractIdentifier` (or a stable hash of it) — and ideally the network/chain id — inside `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and update `sign()`/`verify()` call sites throughout `stackslib/src/net/stackerdb/**` and `stacks-signer` to pass/consume the contract id as part of the signed payload. This requires a coordinated protocol/version bump since it changes what is signed, but it eliminates the cross-contract replay by construction.

### Proof of Concept
1. Signer `S` signs and pushes a `StackerDBChunkData { slot_id: 3, slot_version: 5, sig, data: D }` to `.signers-0-1` (e.g., a `BlockResponse` message). This is broadcast via `StackerDBPushChunk` gossip and/or retrievable via `GET /v2/stackerdb/<S-page-0-owner>.signers-0-1/chunks/3/5`.
2. Attacker (no privileges) observes/fetches this exact chunk.
3. Attacker checks that `.signers-0-2` (a different message-type StackerDB, e.g. for transaction replay messages) also assigns slot `3` to `S` — true by construction, since both contracts read the same `stackerdb-signer-slots-0` list from `.signers` (`stackslib/src/chainstate/stacks/boot/signers.clar` / `signers-0-xxx.clar`).
4. Attacker replays the identical chunk bytes via `POST /v2/stackerdb/<...>.signers-0-2/chunks` (see `stackslib/src/net/api/poststackerdbchunk.rs`).
5. `validate_received_chunk`/`try_replace_chunk` recompute `SlotMetadata::auth_digest()` — identical to step 1's digest since it excludes contract identity — recover the same address `S`, confirm it owns slot 3 in `.signers-0-2`, and accept/store the chunk as if `S` had legitimately written to `.signers-0-2`, even though `S` never signed anything for that contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
