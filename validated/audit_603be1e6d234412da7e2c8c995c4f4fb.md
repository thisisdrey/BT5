### Title
Unauthenticated Atlas DB poisoning via unverified attachment content hash on `GET /v2/attachments/:hash` response - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `GetAttachmentResponse` returned by a peer and stores its `Attachment` without ever checking that `Hash160::from_data(&content)` equals the `content_hash` that was originally requested in the corresponding `AttachmentRequest`. `AttachmentsDownloader::run()`'s `Done` branch then computes the DB key from `attachment.hash()` (i.e., the hash of the attacker-supplied bytes), not from the original `AttachmentRequest.content_hash`, so any peer selected via `network.get_outbound_sync_peers()`/`network.get_data_url()` can inject arbitrary unrelated content into the node's Atlas DB.

### Finding Description
The intended invariant is `Attachment::hash() == AttachmentRequest.content_hash` before storage — i.e., only content whose Hash160 matches the previously-committed, on-chain-derived `content_hash` should ever be inserted into the AtlasDB. Tracing the flow in `stackslib/src/net/atlas/download.rs`:

- `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest{ content_hash, sources, .. }` per missing attachment [1](#0-0) .
- The response is received and decoded purely as JSON with `StacksHttpResponse::decode_atlas_get_attachment`, which just deserializes `GetAttachmentResponse` from the body with no hash validation whatsoever [2](#0-1) .
- `extend_with_attachments` takes that decoded response and does `self.attachments.insert(response.attachment)` — again, no comparison against `request.content_hash` (the request/response pairing is available via `results.succeeded`, keyed by `AttachmentRequest`, yet the hash field is never consulted) [3](#0-2) .
- In `AttachmentsDownloader::run()`, the `Done` branch drains `context.attachments` and, for each attachment, calls `network.atlasdb.find_all_attachment_instances(&attachment.hash())` and `network.atlasdb.insert_instantiated_attachment(&attachment)` — using the hash computed from the attacker-controlled content, not the original requested `content_hash` [4](#0-3) .

Because the peers used for these requests come directly from `network.get_outbound_sync_peers()` / `network.get_data_url()` — ordinary remote peers with no authentication requirement beyond being an outbound sync peer — any such peer can answer `GET /v2/attachments/H` with `Attachment{content: C'}` where `Hash160::from_data(&C') != H`. This attacker-chosen content is inserted into `atlasdb` keyed by its own (attacker-computed) hash, and `resolve_attachment(&attachment.hash())` is called on the batch using that same wrong hash [5](#0-4) , meaning the original `AttachmentRequest` for `H` is falsely marked resolved even though `atlasdb.find_attachment(&H)` was never populated with the real, committed content.

### Impact Explanation
This is an unauthenticated write to Atlas DB state: the node stores content into its BNS attachment store that was never validated against the on-chain-committed hash. Any downstream RPC client calling `GET /v2/attachments/H` still gets a 404 (since `H` was never actually stored), but the attacker's fabricated hash/content pair becomes queryable, and any `AttachmentInstance` records that happen to reference `attachment.hash()` (the attacker's own computed hash, which the attacker fully controls) get falsely resolved and paired with attacker content via `find_all_attachment_instances(&attachment.hash())`. This lets a remote, unprivileged peer serve non-canonical attachment content as if validated ("attachment/BNS mismatch"), matching the High-severity category in scope.

### Likelihood Explanation
The attacker only needs to be selected as one of the node's outbound sync peers with a reachable data URL — no secret, key, or privileged role is required, and this is a normal, low-cost position for any peer participating in the P2P network to be in. The attack is a single crafted HTTP response per targeted `content_hash`, fully repeatable, and requires no race condition or timing precision.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding `response.attachment`, compute `Hash160::from_data(&response.attachment.content)` and compare it against `request.content_hash` (available since `results.succeeded` is keyed by the `AttachmentRequest`). Discard/treat as faulty any response where the hashes do not match (bump `report.bump_failed_requests()` and skip insertion), and only insert into `self.attachments` when the equality holds. Additionally, in `AttachmentsDownloader::run()`'s `Done` branch, prefer resolving/looking up by the originally-requested `content_hash` rather than by `attachment.hash()` recomputed from untrusted content, as a defense-in-depth measure.

### Proof of Concept
Rust test in `stackslib::net::atlas::download` (or a new test module) that:
1. Constructs an `AttachmentsBatchStateContext` with one `AttachmentRequest { content_hash: H, sources: {peer_url}, .. }`.
2. Simulates the `BatchedRequestsResult<AttachmentRequest>::succeeded` map containing `(request, Some(fake_http_200_response))` where the fake response's JSON body decodes (via `decode_atlas_get_attachment`) to `GetAttachmentResponse { attachment: Attachment::new(C') }` with `Hash160::from_data(&C') != H`.
3. Calls `context.extend_with_attachments(&mut results)` and asserts `context.attachments` contains the attacker's attachment.
4. Drives this context through `AttachmentsBatchStateMachine::Done` and executes the equivalent of the `run()` `Done` branch logic against a real `AtlasDB`.
5. Asserts `atlasdb.find_attachment(&H)` returns `None` (the originally requested content was never stored) while `atlasdb.find_attachment(&Hash160::from_data(&C'))` returns `Some(Attachment::new(C'))`, proving the requested-hash/stored-content equality is broken.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
