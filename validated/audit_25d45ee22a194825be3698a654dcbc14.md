### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id mappings survive `DeleteAccountAction`, letting a deleted account's parked yield fire against a later, unrelated re-creation of the same `AccountId` - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (called by `action_delete_account`) purges `Account`, `ContractCode`, `AccessKey`/gas keys and `ContractData`, but never removes the account's `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId` trie rows, nor the shard-global `PromiseYieldTimeout` queue entry created for the yield. Because the `PromiseResume` handling in `process_receipt` (lib.rs) looks up the parked receipt purely by `(account_id, data_id)` with no check that the account has existed continuously since the yield was created, a self-authorized action receipt planted by the *old* owner of an account can be resurrected and executed against whatever new owner/contract later occupies the same `AccountId`.

### Finding Description
- `promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660`, mirrored in `wasmtime_runner/logic.rs:3959`) lets an account `A` create a `PromiseYield` receipt with `predecessor_id == receiver_id == A`. The receipt is stored in state via `set_promise_yield_receipt` under `TrieKey::PromiseYieldReceipt { receiver_id: A, data_id }` (lib.rs:1495-1498), a `PromiseYieldStatus::Yielded` row is written (`ext.rs:353-369`), and a timeout entry is enqueued into the **shard-global** `PromiseYieldTimeout` queue (`function_call.rs:152-169`).
- `A` can immediately (or later) send `Action::DeleteAccount` on itself. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`), which only removes `Account`, `ContractCode`, `AccessKey`/gas-key rows and `ContractData`. It performs **no cleanup** of `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`, or the `PromiseYieldTimeout` queue entry for `A`.
- The account name `A` can later be re-created (e.g., by its parent account for a sub-account, or by a new owner in any account-recycling scheme) with entirely different keys/contract.
- Regardless of whether anyone resends a real resume, the protocol's own timeout mechanism (`resolve_promise_yield_timeouts`, documented at `runtime/runtime/src/lib.rs:2986` and referenced in `protocol-model/spec/cross-shard-congestion.md:299-307`) walks the shard-global `PromiseYieldTimeout` queue and, for each expired entry "whose yield still exists," synthesizes a `PromiseResume` with `data: None` targeting the same `account_id` — deterministically, with no external actor required.
- When that `PromiseResume` (whether the timeout-synthesized one or an original one still in flight) is delivered, `process_receipt`'s `PromiseResume` arm (`runtime/runtime/src/lib.rs:1500-1568`) calls `get_promise_yield_receipt(state_update, account_id, data_receipt.data_id)` — this still finds the stale row because it was never purged — and unconditionally executes it via `apply_action_receipt` (`lib.rs:1549-1562`) against the *current* account state, i.e., the new owner's account.
- The parked receipt has `predecessor_id == receiver_id == A`. `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) treats `actor_id == account_id` as sufficient to authorize privileged, actor-restricted actions (`AddKey`, `DeleteKey`, `DeployContract`, `Stake`, etc.) and self-only `FunctionCall`s. This authorization was valid when the *old* `A` created the receipt (it had legitimate self-authority at that time), but the check offers no guarantee that the account executing now is the same logical owner — it only checks the string equality of account IDs, which is trivially satisfied after account re-creation. A widely-used contract pattern (`assert_eq!(predecessor_account_id(), current_account_id())`, i.e., "self-only" callbacks) is therefore bypassable: the old owner can pre-plant a self-call (or, if actions can be appended to the yield receipt's `ReceiptIndex` via `promise_batch_action_*` before the yield returns, even administrative actions such as `AddKey`) that fires later against a completely different contract/owner who never authorized it.

### Impact Explanation
This is an authorization-escalation / cross-owner-execution bug: a receipt's authorization ("self == self") was established under the old occupant of an `AccountId` but is honored against a new, distinct occupant that never approved the pending action list. Depending on the parked receipt's actions/method, impact ranges from bypassing a re-created contract's "only self" internal invariants (allowing attacker-chosen state transitions, e.g., minting/transfer/finalization logic gated only by `predecessor == current_account_id`) up to attaching account-administrative actions (`AddKey`) if the yield receipt was augmented with extra actions before being parked. This falls under "authorization escalation across accounts or promises," and can lead to loss of funds/control for whoever re-creates the account.

### Likelihood Explanation
- Fully reachable by an ordinary, unprivileged account: it only needs to call `promise_yield_create` (or `promise_yield_create_with_id`) on itself and then submit `DeleteAccountAction` on itself — both are ordinary, permissionless transactions requiring no validator/node access.
- The `PromiseYieldTimeout` firing is deterministic and automatic (no cooperation from any other party needed once the timeout height is reached), making the "still in flight" resume unconditionally deliverable.
- The precondition of the `AccountId` being re-created by a different, unaware party is the main friction (top-level accounts require the registrar; sub-accounts require the parent to re-create the child), but this is a realistic scenario for any platform that reuses/recycles sub-account names (marketplaces, dApp-specific sub-accounts, "rent-a-name" patterns).

### Recommendation
`remove_account` (`core/store/src/utils/mod.rs`) should also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries whose `receiver_id` is the account being deleted, and either flush or mark-invalid the corresponding `PromiseYieldTimeout` queue entries (or have `process_receipt`'s `PromiseResume`/timeout-resolution path additionally verify the account existed continuously, e.g., via a per-account creation nonce/epoch, before executing a parked yield receipt).

### Proof of Concept
Integration/test-loop test plan:
1. Deploy a contract on account `A` (sub-account of `parent`) that in one method: (a) calls `promise_yield_create` with a `method_name`/`args` chosen to represent a "privileged self-call" (e.g., mimicking an `assert_self()`-guarded method name likely to exist on future contracts, or simply a benign marker method), returning the promise, and (b) in a follow-up transaction issues `Action::DeleteAccount { beneficiary_id: parent }` on itself.
2. Advance the chain past `yield_timeout_length_in_blocks` so `resolve_promise_yield_timeouts` fires a `PromiseResume` for the (now-deleted) account `A`, mirroring `test_yield_timeout_resume_receipt_has_receipt_to_tx` in `test-loop-tests/src/tests/yield_timeouts.rs`.
3. Before the timeout height, have `parent` re-create account `A` with a brand-new access key and a different contract that exposes a method with the same name used in step 1(a), gated by `assert_eq!(env::predecessor_account_id(), env::current_account_id())`.
4. Assert that when the timeout `PromiseResume` is delivered, the new contract's "self-only" method executes successfully (i.e., its guard passes) even though the new owner never authorized or even knew about the original yield — confirmed via `get_partial_transaction_result`/logs showing the guarded method ran, and via direct state inspection showing the stale `PromiseYieldReceipt`/`PromiseYieldStatus` rows for `A` were present in state immediately after `DeleteAccountAction` (i.e., `remove_account` did not purge them).
