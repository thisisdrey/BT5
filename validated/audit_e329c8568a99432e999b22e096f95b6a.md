### Title
Griefing via unsolicited deposit-token dust fills `MAX_TOKENS_PER_USER` and blocks victim's collateral/debt management - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to the Story Protocol report — where permissionless `mintLicenseTokens` froze a Group IP owner's management functions — Metronome lets any unprivileged account push entries into a victim's `depositTokensOfAccount` set by sending dust `DepositToken` transfers. Once `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER` (30), `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts every attempt to add a *new* collateral or debt token type to the victim's account, blocking deposits of new collateral and issuance of new synthetic debt — including emergency top-ups needed to avoid liquidation.

### Finding Description
`Pool` tracks per-account collateral and debt positions in two `MappedEnumerableSet.AddressSet` structures capped at `MAX_TOKENS_PER_USER = 30` combined. The guard is enforced in `onlyIfAdditionWillNotReachMaxTokens`:

```solidity
// contracts/Pool.sol:143-148
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
```

There are two permissionless insertion paths, neither requiring the recipient's consent:

1. `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` mints msdTOKEN to an arbitrary `onBehalfOf_` (contracts/DepositToken.sol:211-237). `_mint` calls `pool.addToDepositTokensOfAccount(account_)` when the recipient's balance was zero (contracts/DepositToken.sol:486-488).
2. `DepositToken.transfer(to_, amount_)` / `transferFrom` reach `_transfer`, which likewise calls `pool.addToDepositTokensOfAccount(recipient_)` on a zero-balance recipient (contracts/DepositToken.sol:517-520). `transfer` only checks `_revertIfLocked` on the *sender*, never the recipient (contracts/DepositToken.sol:348-354).

An attacker deposits once into each registered `DepositToken` (pool supports up to 30) and transfers 1 wei of each msdTOKEN to the victim. The victim's set fills to 30. After that:

- `DepositToken.deposit` for any collateral type the victim doesn't already hold reverts at `addToDepositTokensOfAccount` (UserReachedMaxTokens).
- `DebtToken.issue` for any synthetic the victim hasn't borrowed reverts via `addToDebtTokensOfAccount` inside `DebtToken._mint` (contracts/DebtToken.sol:598-600), since debt tokens share the same 30-slot budget.
- The same applies to `SmartFarmingManager.leverage` flows that mint debt/deposit tokens for the user.

Recovery requires the victim to burn each dust balance to zero (`withdraw`), which is possible but: (a) each dust withdrawal can be re-griefed in the same block the victim tries to deposit the real collateral — the attacker re-transfers dust of a *different* token to refill the slot, front-running; (b) if the victim holds debt, `_revertIfLocked` may prevent withdrawing the dust if their collateral is fully locked against the position... actually only the *unlocked* portion must cover `amount_`, and dust is tiny, so withdrawal of dust itself generally succeeds; the real damage window is blocking an urgent collateral top-up while the victim is being liquidated.

### Impact Explanation
Temporary freezing of position management plus indirect theft: an attacker can saturate the token list of a specific victim (e.g., a large position approaching the liquidation boundary) and keep refilling freed slots with dust transfers, so the victim cannot deposit a *new* collateral type or issue a *new* synthetic to restore health. If the victim's existing collateral types alone can't save the position, the attacker (or a cooperating liquidator) then calls `Pool.liquidate` and captures the liquidation incentive. This mirrors the report's DoS-on-management invariant break: a permissionless state mutation freezes the legitimate user's ability to operate their position.

### Likelihood Explanation
- Fully unprivileged: only requires holding/buying dust amounts of each whitelisted underlying, then `transfer` calls — no governance, keeper, or oracle cooperation.
- Cost is bounded: one deposit per deposit token plus 1-wei transfers; number of deposit tokens is governance-capped at 30, and in practice far fewer exist per pool.
- Constraints: attacker cannot exceed the pool's registered deposit tokens, so a victim already using many token types needs fewer dust transfers; a fresh/small account needs more. Re-griefing freed slots is cheap and repeatable while the attacker holds residual dust.

### Recommendation
- Restrict `DepositToken.deposit`'s `onBehalfOf_` path and/or require recipient opt-in (e.g., only add to the per-account set on user-initiated deposits, or add an allowlist/"accept collateral" flag).
- Alternatively, bound the griefing surface: exclude zero-or-tiny balances, sweep dust entries in `debtPositionOf`, or replace the hard revert with automatic eviction of the smallest/dust entry.
- Short term, per the report's remediation pattern, give accounts a user-controlled flag (analogous to `LicensingConfig.disabled`) that blocks unsolicited token additions until the owner enables them.

### Proof of Concept
Hardhat-style reproduction against the repo's own fixtures:

```ts
// attacker fills victim's token list
for (const dt of allDepositTokens) { // every registered DepositToken in the pool
  await underlying[dt].connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(2, attacker.address) // mint dust
  await dt.connect(attacker).transfer(victim.address, 1)  // adds dt to victim's set
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30)

// victim tries to deposit a new collateral type -> reverts
await expect(
  newDepositToken.connect(victim).deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim tries to issue a new synthetic -> reverts (debt tokens share the cap)
await expect(
  newDebtToken.connect(victim).issue(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim withdraws one dust token to free a slot; attacker front-runs the next
// deposit by transferring dust of a different deposit token again -> slot refilled
```
