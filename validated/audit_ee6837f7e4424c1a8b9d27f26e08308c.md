### Title
Server-side log credential leak via unsanitized RPCs (FindRemoteRepository/FindRemoteRootRef) not in URLSanitizerHook allowlist - (File: internal/log/url_sanitizer.go)

### Summary
`URLSanitizerHook.Fire` only sanitizes URLs in log entries when the `grpc.method` field matches one of three hardcoded method names registered in `internal/cli/gitaly/serve.go` (`CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`). Other RPCs that legitimately accept credentialed remote URLs, notably `RemoteService/FindRemoteRepository` and `RemoteService/FindRemoteRootRef`, are not registered, so credentials embedded in their `remote`/`remote_url` fields are logged in plaintext when the underlying git command fails.

### Finding Description
`FindRemoteRepository` at [1](#0-0)  takes an unprivileged, attacker-controlled `req.GetRemote()` string (which can embed `user:password@host` per `proto/remote.proto`'s comment "the remote parameter must specify a valid Git URL") and passes it directly as an argument to `git ls-remote` via `gitcmd.NewWithoutRepo`. Similarly, `FindRemoteRootRef` accepts a `remote_url` field with the same shape, per [2](#0-1) .

Every gRPC call, regardless of method, passes through the standard logging interceptor chain configured in [3](#0-2) , which uses `grpcmwlogrus` with `structerr.FieldsProducer` to attach the `error` field (and `grpc.method`) to the final log entry whenever the RPC returns an error (e.g. a malformed/failing git command including credential text in stderr).

`URLSanitizerHook.Fire` gates all sanitization on membership in `possibleGrpcMethods`: [4](#0-3) . That map is populated exactly once at startup with only three method names: [5](#0-4) . Because `FindRemoteRepository`/`FindRemoteRootRef` are absent from this list, any error entry logged with `grpc.method: "FindRemoteRepository"` (or `FindRemoteRootRef`) bypasses `sanitizeErrorLog` entirely, and the raw error string — potentially containing `https://user:password@host/repo` if git's own error output echoes the URL (e.g. connection/auth failures) — is written to Gitaly's log verbatim. The project's own test suite in `internal/log/url_sanitizer_test.go` explicitly documents this behavior for an unregistered method (`UserDeleteTag`) as the "no sanitization happens" case, confirming the allowlist design is not exhaustive and is a known incompleteness pattern, just applied to the wrong scope for these two RPCs.

### Impact Explanation
This is a credential-disclosure issue confined to Gitaly's own log stream: any attacker capable of invoking `FindRemoteRepository` or `FindRemoteRootRef` with a credentialed URL that provokes a git-level error can cause that credential to be written unredacted into server logs. If those logs are shipped to a less-trusted log aggregation system, or accessible to personnel/systems without direct repository access, this constitutes a secret-leak matching GitLab's "sensitive information disclosure" bounty class. It does not grant direct RPC-response disclosure (the gRPC response itself doesn't return the raw error text with the credential value beyond typical status wrapping) but a leak into logs.

### Likelihood Explanation
Both affected RPCs are reachable operations that accept a URL from an unprivileged caller (`FindRemoteRepository`'s proto explicitly documents that the caller supplies an arbitrary Git URL, and `FindRemoteRootRef` similarly takes `remote_url`). Provided that GitLab Rails/Workhorse forwards these fields largely as supplied (mirror configuration and import/mirror related flows are the normal callers of remote-URL-accepting RPCs), triggering a failing `git ls-remote`/`git ls-remote --symref` invocation with a credentialed URL is straightforward and repeatable, requiring no special privilege beyond normal use of features that specify remote URLs.

### Recommendation
Make the sanitizer allowlist exhaustive/comprehensive rather than an incomplete hardcoded list: either (1) enumerate all gitalypb RPCs whose request messages contain fields tagged/named `remote`, `remote_url`, or `url` at proto-generation/registration time and auto-register them with `AddPossibleGrpcMethod`, or (2) default `URLSanitizerHook.Fire` to sanitize by pattern for every RPC's `error`/`args`/message fields regardless of method name (removing the allowlist gate entirely), since the `hostPattern` regex sanitization is already narrowly scoped to credential-bearing URL syntax and is safe to apply broadly. Additionally add `FindRemoteRepository` and `FindRemoteRootRef` to `possibleGrpcMethods` in `internal/cli/gitaly/serve.go` as an immediate fix.

func (hook *URLSanitizerHook) Fire(entry *logrus.Entry) error {
	mth, ok := entry.Data["grpc.method"]
	if !ok {
		return nil
	}

	mthStr, ok := mth.(string)
	if !ok || !hook.possibleGrpcMethods[mthStr] {
		return nil
	}

	if _, ok := entry.Data["args"]; ok {
		sanitizeSpawnLog(entry)
	} else if _, ok := entry.Data["error"]; ok {
		sanitizeErrorLog(entry)
	} else {
		entry.Message = sanitizeString(entry.Message)
	}

	return nil
}
