### Title
Dust transfers of deposit tokens fill a victim's per-account token list, reverting all future deposits/issues - ([File: contracts/Pool.sol](contracts/Pool.sol), [contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Metronome tracks, per account, which `DepositToken`s and `DebtToken`s the account holds in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`). The combined list is capped at `MAX_TOKENS_PER_USER = 30`, and `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens()` once the cap is hit. Any account can push a new entry into a *victim's* list at dust cost by depositing a token and calling `DepositToken.transfer(victim, 1 wei)` — `_transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance was zero, and the max-tokens check runs inside that call [1](#0-0) [2](#0-1) . This mirrors the Derby issue: an unprivileged user injects a state element (here, a token-list entry; there, an allocation to a blacklisted protocol) that makes a subsequent operation on behalf of/affecting another party revert.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's account list on first receipt [1](#0-0) . `transfer`/`transferFrom` are permissionless and only check the *sender's* locked balance via `_revertIfLocked` — there is no opt-in or whitelist for recipients [3](#0-2) . An attacker therefore:

1. Deposits `1 wei` of each distinct underlying into each pool `DepositToken` (e.g., msUSD-WETH, msUSD-WBTC, msUSD-VAETH, etc.).
2. Calls `depositToken.transfer(victim, 1)` for each token. Each call invokes `pool.addToDepositTokensOfAccount(victim)`, which enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < MAX_TOKENS_PER_USER` [4](#0-3) .
3. After pushing enough distinct tokens so the victim's combined count reaches 30, every subsequent operation that would add a *new* token to the victim's account reverts with `UserReachedMaxTokens()`:
   - `DepositToken.deposit`/`_mint` into any collateral the victim doesn't already hold (`_mint` → `addToDepositTokensOfAccount`) [5](#0-4) .
   - `DebtToken.issue`/`mint` for any synth the victim doesn't already owe (`_mint` → `addToDebtTokensOfAccount`) [6](#0-5) .
   - Incoming `transfer`/`transferFrom`/`seize` of any deposit token the victim doesn't already hold.

The critical aggravation: a victim normally self-heals by transferring a dust balance out (balance → 0 triggers `removeFromDepositTokensOfAccount` [7](#0-6) ). But `transfer` is gated by `_revertIfLocked`, which uses `unlockedBalanceOf` — an account whose collateral is fully locked by existing debt (`unlockedBalanceOf == 0`) cannot send the dust away [8](#0-7) . Such a victim cannot deposit new collateral types to improve their position nor issue new synths until they first repay debt — while their position may be deteriorating toward liquidation and the seized collateral type they would want to add remains unreachable.

### Impact Explanation
- Liveness/DoS griefing analogous to the source report: a single unprivileged account permanently poisons another account's ability to add new position components by spending dust, with no privileged-action dependency.
- Victims with healthy `unlockedBalanceOf > 0` suffer only a temporary DoS (they can clear entries). Victims fully locked by debt are blocked from adding *any* new collateral or debt token until they externally acquire synths and repay — during which their position can be liquidated. For a smart-contract wallet or a position managed via `SmartFarmingManager.leverage` (which calls `DebtToken.mint(to_, ...)` for `to_ = request owner`), a stuffed list also bricks leverage/flashIssue flows into new synths [9](#0-8) .
- Bounded impact: no direct theft; existing balances remain withdrawable once unlocked. This is temporary freezing of protocol functionality per account, not global rebalance DoS (Metronome has no batched keeper step over user allocations, so a system-wide block like Derby's does not exist).

### Likelihood Explanation
- Requires only public entry points (`DepositToken.deposit`, `transfer`) and dust amounts of existing underlyings; costs scale with the number of deposit tokens needed to reach the cap minus entries the victim already holds.
- Most effective against accounts holding many token types or fully locked by debt; ineffective if the victim is already at/above cap (impossible — cap prevents it) or if the pool has fewer collaterals+debt tokens than needed combined with the victim's existing entries (attacker needs `30 - victimExisting` distinct tokens to push).

### Recommendation
Do not revert inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` for additions triggered by unsolicited inbound transfers — or better, only count a token against `MAX_TOKENS_PER_USER` when the account initiates the position (deposit/issue/leverage), not when receiving `transfer`/`transferFrom`. Alternatively, allow anyone to call a `removeFromDepositTokensOfAccount`-style cleanup that force-sends the dust to a burn/treasury address, or exempt dust below a threshold from list insertion. Aligns with the Derby fix of ignoring rather than reverting on forced state.

### Proof of Concept
Hardhat (fork or local deploy with ≥2 deposit tokens; concept shown):

```ts
// attacker: alice is the victim whose combined list is at 29 or lower
for (const dt of depositTokens /* each registered IDepositToken */) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying())
  await underlying.connect(attacker).approve(dt.address, MaxUint256)
  await dt.connect(attacker).deposit(1, attacker.address)   // gross amount covering fee
  await dt.connect(attacker).transfer(victim.address, 1)    // adds dt to victim's list
}
// victim list now == MAX_TOKENS_PER_USER (30)

// any new collateral deposit by victim reverts
await expect(
  newDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// any new synth issuance by victim reverts (DebtToken._mint -> addToDebtTokensOfAccount)
await expect(
  newDebtToken.connect(victim).issue(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// if victim.unlockedBalanceOf(token) == 0 (fully locked by debt),
// victim cannot transfer dust out -> entries cannot be removed until debt is repaid
```
