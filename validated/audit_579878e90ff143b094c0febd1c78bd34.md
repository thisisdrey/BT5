### Title
Anti-replay window check-then-update race allows duplicate processing of replayed packets - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection as two separate, individually-locked operations — `window.Check` and `window.Update` — with the lock released between them and the actual AEAD decryption performed outside the lock entirely. This mirrors the check-effect-interaction pattern from the reported reentrancy bug: the "will this be accepted" check and the "mark this as consumed" state update are not atomic, leaving a window in which the same message counter can pass the check twice before either call reaches the update.

### Finding Description
`ConnectionState.Decrypt` does:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)   // no lock held
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [1](#0-0) 

`VerifyRelay` follows the identical pattern for relay frames. [2](#0-1) 

`Bits.Check` and `Bits.Update` are separate methods on the sliding-window replay tracker; `Check` only reads state, `Update` is the only call that actually marks the slot as seen. [3](#0-2) 

Nebula supports multiple concurrent packet-processing routines (the `routines`/listener worker model referenced in `interface.go`), and the very existence of `decryptLock` on `ConnectionState` demonstrates the authors anticipated concurrent `Decrypt`/`VerifyRelay` calls against the same tunnel state. However, the lock is only held per-call to `Check` and per-call to `Update`, not across the full check→decrypt→update sequence. This is the same class of bug as the reported `claimRewards` issue: the code assumes a linear "check window, then eventually mark window" sequence per packet, but nothing prevents two invocations for the same `messageCounter` from both observing an "unseen" `Check` result before either reaches `Update`.

The project's own test suite shows this exact family of bug has already bitten Nebula once: `TestRelayReplayProtection` documents a prior fix where `handleOutsideRelayPacket` authenticated a relay frame but never advanced the replay window, causing every replay to be re-forwarded. [4](#0-3)  That fix moved the `Update` call into the authenticated path, but it did not make `Check`+decrypt+`Update` atomic — the lock is dropped between `Check` and `Update` in both `Decrypt` and `VerifyRelay`.

### Impact Explanation
An attacker with no valid CA-signed certificate can passively capture a legitimate encrypted UDP packet or relay frame traversing the network and re-inject it. If two copies of the same captured packet are delivered to the interface close together (e.g., via UDP retransmission at the network layer, packet duplication, or by an attacker deliberately sending the same captured datagram twice in quick succession — which requires no cryptographic material, just the raw bytes), both can reach `Check` before either reaches `Update`, since the lock is released in between. Both copies then pass AEAD decryption (the ciphertext/nonce is valid and unchanged) and are delivered to the tun device as if they were two distinct packets, and/or both are forwarded again in the relay case. This is a real anti-replay bypass: the protocol's stated guarantee that a captured packet can be decrypted/forwarded exactly once is violated under packet duplication, enabling remote traffic replay.

### Likelihood Explanation
Triggering the race does not require possession of any valid certificate or handshake participation — only the ability to observe and re-send a single legitimate ciphertext packet, which is achievable by any network-adjacent observer (the standard "malicious network" attacker model this class of report targets). The race window is small but real, and duplicate/out-of-order delivery of the same UDP datagram (whether attacker-crafted or naturally occurring in packet-duplication network paths) is exactly the condition `Check`/`Update` splitting was supposed to prevent.

### Recommendation
Hold `decryptLock` for the entire check→decrypt→mark sequence (or fold `Check`+`Update` into a single atomic `Bits.CheckAndReserve`-style call performed under one lock acquisition) so that no second caller can observe an "unseen" state for a counter that is concurrently being processed. This closes the TOCTOU window in both `Decrypt` and `VerifyRelay`.

### Proof of Concept
Conceptual PoC (no code execution available in this analysis mode):
1. Attacker observes one legitimate encrypted data-plane packet (or relay frame) with message counter `N` addressed to a live Nebula tunnel.
2. Attacker sends two copies of the exact same UDP datagram to the target's socket at (nearly) the same time.
3. If the target processes inbound packets across concurrent workers/goroutines, both copies invoke `ConnectionState.Decrypt` (or `VerifyRelay`) for the same `ConnectionState`.
4. Goroutine A calls `window.Check(N)` → true, unlocks, begins `DecryptDanger`.
5. Before goroutine A calls `window.Update(N)`, goroutine B calls `window.Check(N)` → still true (not yet updated), unlocks, begins `DecryptDanger`.
6. Both goroutines successfully decrypt/verify and both call `window.Update(N)`; only the second logically "wins" the accounting, but both already delivered/forwarded the payload — the replayed packet was processed twice, defeating the anti-replay guarantee.

I could not execute this against a running binary in this environment, so the concurrency trigger (multiple listener routines racing on the same `ConnectionState`) is inferred from the presence of `decryptLock` itself and Nebula's documented multi-routine UDP listener model in `interface.go`, rather than from direct observation of a reproduction; a background Devin session with full repo/build access would be needed to confirm the exact scheduling conditions required to win the race in practice.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
