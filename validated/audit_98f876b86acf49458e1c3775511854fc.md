### Title
RewardsDistributor accrues rewards past the external reward period end because `tokenSpeed` is never time-bounded - (File: contracts/RewardsDistributor.sol)

### Summary
The external report describes a rewarder whose `lastRewardTime` is not capped at the end of the distribution period, so the reward-per-share keeps growing after emissions should have stopped. Metronome's `RewardsDistributor` has the same defect in structural form: `tokenSpeeds[token]` is a flat rate-per-second with no stored end timestamp, and `_calculateTokenIndex` accrues `deltaTimestamps * speed` for the entire elapsed interval. For Vesper-backed deposit tokens, `syncTokenSpeed` only zeroes the speed when the `tokenSpeedKeeper` happens to call it after `periodFinish`. Between the external period end and the next keeper call, the index keeps growing at the stale speed, minting un-funded reward entitlement that any holder can claim permissionlessly.

### Finding Description
`_calculateTokenIndex` computes accrual purely from elapsed wall-clock time:

```solidity
uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
if (_deltaTimestamps > 0 && _speed > 0) {
    uint256 _tokensAccrued = _deltaTimestamps * _speed;
    ...
}
``` [1](#0-0) 

There is no `periodFinish`/`endTime` cap analogous to `lastRewardTime = min(now, periodEnd)`. The only mechanism that ever stops accrual is a governor `updateTokenSpeed(s)` call or a keeper `syncTokenSpeed` call:

```solidity
if (block.timestamp < _rewards.periodFinish(address(rewardToken))) {
    _speed = (_rewards.rewardRates(...) * _vPool.balanceOf(...)) / _vPool.totalSupply();
}
_updateTokenSpeed(IERC20(address(depositToken_)), _speed);
``` [2](#0-1) 

After `periodFinish`, `_speed` is set to `0` — but only inside `syncTokenSpeed`, which is gated by `if (_msgSender() != tokenSpeedKeeper) revert NotTokenSpeedKeeper()`. Until the keeper acts, `tokenSpeeds` remains at the last synced (non-zero) rate, and every call to `updateBeforeMintOrBurn`, `updateBeforeTransfer`, or `claimRewards` — all permissionless — pushes the index higher with rewards that were never funded for that window.

### Impact Explanation
DepositToken/DebtToken holders accrue `tokensAccruedOf` entitlements for a period in which the underlying Vesper reward stream has already ended. These excess accruals are paid out of the distributor's `rewardToken` balance on a first-come, first-served basis by `_transferRewardIfEnoughTokens`, so early claimers drain the balance and later claimers' legitimately accrued rewards become unpayable (the accrued amount is not even reset when the balance is insufficient — they simply get nothing). This is theft of unclaimed yield belonging to other users, exactly the "users accruing rewards meant for others" invariant break in the reference bug. The gap is unbounded: accrual continues at the stale speed indefinitely until a keeper or governor transaction lands.

### Likelihood Explanation
`periodFinish` on the underlying Vesper `PoolRewards` contract elapses deterministically; there is no guarantee the keeper transaction lands in the same block, and any latency window (keeper downtime, gas spikes, simple scheduling delay) creates an interval of un-funded accrual. Exploitation requires only that the attacker hold or acquire DepositToken shares and call the public `claimRewards(account_, tokens_)` or trigger accrual via ordinary deposit/withdraw flows, which call `updateBeforeMintOrBurn`/`updateBeforeTransfer`. No privileged role, oracle manipulation, or malformed argument is needed. The magnitude scales with `stale_speed × keeper_latency × attacker_share_of_supply`, so an attacker can amplify their share by depositing a large position during the stale window.

### Recommendation
Store a per-token accrual end timestamp (e.g., `rewardPeriodFinishOf[token]` populated from `_rewards.periodFinish(...)` inside `syncTokenSpeed`) and cap the accrual interval in `_calculateTokenIndex`:

```solidity
uint256 _end = rewardPeriodFinishOf[token_];
uint256 _now = _end > 0 && block.timestamp > _end ? _end : block.timestamp;
uint256 _deltaTimestamps = _now > _supplyState.timestamp ? _now - _supplyState.timestamp : 0;
```

This makes accrual self-capping at the end of the funded distribution period, removing the dependence on keeper timing, mirroring the upstream fix of setting `lastRewardTime` to the period end.

### Proof of Concept
Hardhat-style fork test sketch (Optimism fork, where `RewardsDistributor` is deployed per `deployments/optimism/RewardsDistributor.json`):

```ts
// Fork optimism at a block where Vesper poolRewards.periodFinish(rewardToken)
// has passed but syncTokenSpeed has not been called since.
const distributor = await ethers.getContractAt('RewardsDistributor', DIST);
const depositToken = await ethers.getContractAt('DepositToken', MSD_TOKEN);
const vPool = await ethers.getContractAt('IVPool', await depositToken.underlying());
const rewards = await ethers.getContractAt('IPoolRewardsExt', await vPool.poolRewards());
const rewardToken = await distributor.rewardToken();

const periodFinish = await rewards.periodFinish(rewardToken);
assert((await ethers.provider.getBlock('latest')).timestamp > periodFinish);

// tokenSpeed is still the stale non-zero rate synced before periodFinish
const staleSpeed = await distributor.tokenSpeeds(depositToken.address);
assert(staleSpeed.gt(0)); // BUG: speed never auto-zeroed at periodFinish

// Attacker deposits to gain share during the un-funded window
await underlying.connect(attacker).approve(pool.address, amount);
await pool.connect(attacker).deposit(collateral.address, amount); // mints DepositToken

// Advance time past periodFinish; index keeps growing at staleSpeed
await time.increase(3600);

// Anyone can settle the inflated index and claim
const accruedBefore = await distributor.tokensAccruedOf(attacker.address);
await distributor.claimRewards(attacker.address);
const accruedAfter = await distributor.tokensAccruedOf(attacker.address);
// accruedAfter > funded entitlement: rewards were emitted for
// block.timestamp - periodFinish seconds that no reward rate covered,
// paid from rewardToken balance owed to other users.
```

Key assertions: `tokenSpeeds[depositToken]` remains non-zero after `periodFinish`; `_calculateTokenIndex` accrues `deltaTimestamps * staleSpeed` over the post-`periodFinish` interval; and `claimRewards` transfers `rewardToken` against that un-funded accrual, demonstrably reducing the balance available for other users' `tokensAccruedOf`.
