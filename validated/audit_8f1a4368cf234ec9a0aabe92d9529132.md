### Title
Unbounded HTTP response body read in `run_http_request` allows a malicious StackerDB host to memory-bomb the signer - (File: libsigner/src/http.rs)

### Summary
`StackerDBSession::rpc_request` (used by every StackerDB RPC operation: `list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`) calls `run_http_request`, which reads the entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any `Content-Length` or body-size check is applied. This is the same fault class as the reported issue: unbounded, attacker-controlled data is unconditionally loaded into memory regardless of outcome, with no upper bound enforced before or during the read.

### Finding Description
In `libsigner/src/http.rs::run_http_request`, the signer writes its request and then does: [1](#0-0) 
```
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
```
This reads the full response body from the remote peer into an unbounded, growing `Vec<u8>` before any length/size validation occurs. Only *after* the entire response has been buffered does the code parse headers via `decode_http_response` and check the `Content-Length`/`chunked` framing, and even the chunked path in `decode_http_body` (`libsigner/src/http.rs` line ~207) bounds decoding only via `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())` — but that bound is applied to the *chunked-decode logic*, not to the initial `read_to_end` which has already consumed and materialized the raw bytes in memory.

`StackerDBSession` connects to `self.host`, i.e., whatever "node"/StackerDB replica host is configured (`connect`, `session.rs` line 177-185), and is exercised any time the signer fetches or pushes StackerDB chunks. A compromised, misconfigured, or malicious StackerDB endpoint the signer is pointed at can simply keep streaming bytes (e.g. an arbitrarily large, non-terminating or huge body, with or without a matching Content-Length header, or a slow trickle) causing the signer process to allocate unbounded memory before any of the size caps in `session.rs` (`SIGNERS_STACKERDB_CHUNK_SIZE`, `STACKERDB_MAX_CHUNK_SIZE`, `limit`) are ever consulted — those checks only run **after** `rpc_request` returns the fully-buffered `Vec<u8>`.

This mirrors the report's root cause: return/response data of unbounded size is unconditionally loaded into memory without a bound, regardless of whether the caller ultimately intends to enforce a size limit downstream.

### Impact Explanation
A malicious or compromised StackerDB host that the signer talks to can force unbounded memory growth in the signer process via a single or repeated RPC response, leading to OOM / crash of the signer (denial of service on a critical validator-adjacent process). This falls under "Critical - remote crash/unauthenticated DoS from few messages" since no authentication, size cap, or previous validation gates the amount of data read in `read_to_end`.

### Likelihood Explanation
Any signer configured to talk to a given StackerDB replica host (which is attacker-influenceable if that host is compromised, or if there is a network path allowing an on-path/malicious relay to respond as that host) can trivially trigger this: no special authentication or preconditions are required — a plain oversized HTTP response is sufficient. Likelihood is high given the trivial exploitation (send data, don't stop).

### Recommendation
Bound the HTTP response read using a size cap before/while reading, e.g. wrap the socket read in a bounded reader (the codebase already has `BoundReader` and `HttpChunkedTransferReader` with `MAX_MESSAGE_LEN`) enforced for *all* code paths, including the initial `read_to_end` in `run_http_request`, and validate `Content-Length` against a maximum before allocating/reading the body. Reject or terminate the connection early if the peer exceeds the expected/maximum StackerDB chunk size instead of buffering unbounded data first and checking size only afterward.

### Proof of Concept
1. Configure a signer to point `StackerDBSession::host` at an attacker-controlled TCP listener (or compromise/impersonate the configured StackerDB node).
2. When the signer issues any RPC (e.g., `list_chunks` → `GET /v2/stackerdb/.../chunks`), have the malicious server respond with `HTTP/1.1 200 OK\r\nContent-Length: <huge>\r\n\r\n` followed by an endless/very large stream of bytes (or a legitimate `Content-Length` far larger than any StackerDB chunk should be).
3. Observe that `run_http_request`'s `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) keeps growing `buf` in memory with no cap, exhausting available memory before `decode_http_response`/size-limit checks in `session.rs` (`limit`, `SIGNERS_STACKERDB_CHUNK_SIZE`) are ever reached. pub fn run_http_request<S: Read + Write>(
    sock: &mut S,
    host: &str,
    verb: &str,
    path: &str,
    content_type: Option<&str>,
    payload: &[u8],
) -> Result<Vec<u8>, RPCError> {
    let content_length_hdr = if !payload.is_empty() {
        format!("Content-Length: {}\r\n", payload.len())
    } else {
        "".to_string()
    };

    let req_txt = if let Some(content_type) = content_type {
        format!(
            "{verb} {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\nContent-Type: {content_type}\r\n{content_length_hdr}User-Agent: libsigner/0.1\r\nAccept: */*\r\n\r\n"
        )
    } else {
        format!(
            "{verb} {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n{content_length_hdr}User-Agent: libsigner/0.1\r\nAccept: */*\r\n\r\n"
        )
    };
    debug!("HTTP request\n{}", &req_txt);

    sock.write_all(req_txt.as_bytes())?;
    sock.write_all(payload)?;

    let mut buf = vec![];

    sock.read_to_end(&mut buf)?;

    let (headers, body_offset) = decode_http_response(&buf)?;
    if body_offset >= buf.len() {
        // no body
        debug!("No HTTP body");
        debug!("Headers: {:?}", &headers);
        return Ok(vec![]);
    }

    decode_http_body(&headers, &buf[body_offset..]).map_err(|e| e.into())
}

        for slot_id in slot_ids.iter() {
            let path = stackerdb_get_chunk_path(self.stackerdb_contract_id.clone(), *slot_id, None);
            let chunk = match self.rpc_request("GET", &path, None, &[]) {
                Ok(body_bytes) => {
                    // Verify that the chunk is not too large
                    if body_bytes.len() > limit {
                        None
                    } else {
                        Some(body_bytes)
                    }
                }
                Err(RPCError::HttpError(code)) => {
                    if code != 404 {
                        return Err(RPCError::HttpError(code));
                    }
                    None
                }
                Err(e) => {
                    return Err(e);
                }
            };
            payloads.push(chunk);
        }
        Ok(payloads)
    }
