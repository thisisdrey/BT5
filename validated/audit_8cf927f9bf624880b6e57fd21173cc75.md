### Title
Unprivileged attacker can permanently block a victim from adding new collateral/debt positions by saturating their per-account token lists via dust deposits and transfers, enabling forced liquidation - ([File: contracts/Pool.sol])

### Summary
The original bug class is a low-cost, unprivileged Denial of Service triggered by crafted inputs. The Metronome analog lives in `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, which revert with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Because `DepositToken._mint` and `DepositToken._transfer` push the token into the *recipient's* list whenever their prior balance is zero [2](#0-1) , and both `deposit(amount_, onBehalfOf_)` and `transfer(to_, amount_)` are callable by anyone toward an arbitrary `to_`/`onBehalfOf_`, an unprivileged attacker can fill a victim's combined list to the cap with dust.

### Finding Description
- `deposit(uint256 amount_, address onBehalfOf_)` mints deposit tokens to `onBehalfOf_`; inside `_mint`, when `balanceOf[account_] == 0`, `pool.addToDepositTokensOfAccount(account_)` is invoked [3](#0-2) .
- `transfer(to_, amount_)` / `seize` route through `_transfer`, which performs the same insert for the recipient [4](#0-3) .
- `Pool.addToDepositTokensOfAccount` first evaluates `onlyIfAdditionWillNotReachMaxTokens`, reverting when the sum of the two per-account sets is `>= 30` [5](#0-4) .
- The only removal paths are burning the balance to zero (`_burn`) or transferring the full balance [6](#0-5) , so the victim cannot evict attacker's dust entries without fully redeeming each token.

Attack: for every registered `DepositToken` in the pool, the attacker calls `deposit(1, victim)` (or acquires a dust balance and calls `transfer(victim, 1)`), until `depositTokensOfAccount.length(victim) == 30`. Combined with any existing `debtTokensOfAccount` entries, the victim's list hits the cap for the cost of ~30 dust deposits of distinct collateral (1 wei each, plus gas).

### Impact Explanation
Once saturated, every subsequent operation that would insert a *new* token into the victim's sets reverts with `UserReachedMaxTokens`:

- The victim cannot `deposit` a new collateral type — the mint reverts inside `addToDepositTokensOfAccount`.
- Nobody can `transfer` a new deposit-token type to the victim, and liquidation `seize` calls that would credit the victim with a new token type revert.
- If the victim still has free slots, the attacker can also push dust debt... (debt tokens are non-transferable, so only deposit-token slots are directly pushable; the deposit-token side alone can consume the shared 30-slot budget).

Concretely, a victim whose position becomes unhealthy cannot top up with a *new* collateral type to restore health — the rescue deposit reverts — so the position is forcibly liquidated. This is a direct, attacker-induced liveness break of position management (temporary freezing of the victim's ability to add collateral), reachable entirely from unprivileged EOAs, which matches the "Account list / freeze griefing" surface and the CVE's DoS bug class. The attack is fully reversible only by the victim emptying a dust position, and is repeatable.

Precondition: the pool must list enough deposit tokens (plus the victim's existing debt tokens) to reach 30 combined entries. Metronome pools are themselves capped at `ReachedMaxDepositTokens` under the same constant, so a pool near its token cap is sufficient; in pools with few collaterals the attack only constrains the victim proportionally.

### Likelihood Explanation
- Attacker needs no privileges: `deposit` and `transfer` are permissionless, and `addToDepositTokensOfAccount` is invoked by the token contract itself, so `_revertIfSenderIsNotDepositToken` passes [7](#0-6) .
- No pause, shutdown, supply-cap, reentrancy guard, or `SynthContext` check intervenes; `onlyIfAdditionWillNotReachMaxTokens` is precisely the mechanism that gets weaponized.
- Cost is bounded (~30 small ERC20 deposits/transfers) and can be done atomically via a contract or across transactions.

### Recommendation
Do not let entries be added to a user's per-account lists without consent. Options:

1. On `addTo*` reaching the cap, silently skip insertion instead of reverting, and change `debtPositionOf`/`depositOf` to iterate over the global `depositTokens`/`debtTokens` sets (or a superset) so an unlisted balance is still counted.
2. Alternatively, restrict `deposit`'s `onBehalfOf_` and `transfer`'s recipient inserts so a token is only added when the recipient previously opted in, or allow the recipient to remove entries unilaterally (e.g., a `pool.removeDepositTokenOfAccount(token)` callable by the account itself, provided balance checks still enumerate correctly).
3. Track a per-account nonce/consent mapping so dust cannot occupy slots the user never intended.

Any fix must keep `depositOf`/`debtOf` consistent with tokens actually held, otherwise health checks would ignore pushed dust.

### Proof of Concept
Hardhat sketch (pool with at least enough registered `DepositToken`s to reach the cap with victim's existing entries):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DustFillAttack {
    function fill(Pool pool, address victim, IERC20 underlyingSeed) external {
        address[] memory dTokens = pool.getDepositTokens();
        uint256 slots = pool.MAX_TOKENS_PER_USER()
            - pool.getDepositTokensOfAccount(victim).length
            - pool.getDebtTokensOfAccount(victim).length;
        for (uint256 i; i < dTokens.length && slots > 0; ++i) {
            DepositToken dt = DepositToken(dTokens[i]);
            IERC20 underlying = dt.underlying();
            // pull 1 wei of each underlying (pre-funded to this contract) and deposit to victim
            underlying.approve(address(dt), 1);
            dt.deposit(1, victim); // reverts only if victim already holds this token
            slots--;
        }
    }
}
```

Test assertion: after `fill`, `victim`'s combined list length equals `MAX_TOKENS_PER_USER`; any subsequent `depositToken_k.deposit(amount, victim)` for a token the victim does not hold reverts with `UserReachedMaxTokens`, and `depositToken_k.transfer(victim, x)` reverts identically via `_transfer` → `addToDepositTokensOfAccount`. Demonstrate liquidation path: drive victim unhealthy via oracle move, then show the victim's rescue `deposit` of a new collateral reverts while a third-party `liquidate` succeeds.
