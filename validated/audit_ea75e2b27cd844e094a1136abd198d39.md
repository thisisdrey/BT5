### Title
`AttachmentsDownloader` stores unverified peer-supplied attachment content as permanently-instantiated with no hash check and no eviction - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts whatever `Attachment` a peer returns for a `GET /v2/attachments/:hash` request into `context.attachments` without ever checking that `response.attachment.hash() == request.content_hash`. In `AttachmentsDownloader::run`'s `Done` branch, every drained attachment is then unconditionally persisted via `insert_instantiated_attachment` regardless of whether `find_all_attachment_instances(&attachment.hash())` returns any confirmed on-chain instance, and unlike `was_instantiated=0` rows there is no eviction routine for `was_instantiated=1` rows.

### Finding Description
The equality the code should preserve — every row persisted in the `attachments` table with `was_instantiated=1` corresponds to bytes whose `Hash160` was actually committed to by some confirmed `AttachmentInstance.content_hash` — is broken in two compounding ways:

1. No response-integrity check: `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) does `self.attachments.insert(response.attachment)` after only checking that the HTTP payload decoded as JSON [1](#0-0) . It never compares `response.attachment.hash()` against `request.content_hash` that was used to build the `AttachmentRequest` [2](#0-1) . Any peer that claims (via its inventory response) to have the attachment can return arbitrary bytes (≤ `attachments_max_size`) for that request and it will be accepted as-is.

2. Unconditional persistence: in the `Done` branch of `AttachmentsDownloader::run`, for every attachment drained from `context.attachments`, `find_all_attachment_instances(&attachment.hash())` is looked up, but regardless of whether it returns zero results, `network.atlasdb.insert_instantiated_attachment(&attachment)` is still called [3](#0-2) . `insert_instantiated_attachment` writes the row with `was_instantiated=1` unconditionally [4](#0-3) .

3. No eviction for instantiated rows: `evict_expired_uninstantiated_attachments` and `evict_k_oldest_uninstantiated_attachments` only ever target `was_instantiated = 0` rows [5](#0-4) ; there is no analogous cap/expiry for `was_instantiated = 1` rows, and `run()` only calls the uninstantiated-eviction routines [6](#0-5) .

Attack flow: a node has legitimate, on-chain-confirmed `AttachmentInstance`s that are still unresolved (queued via `find_unresolved_attachment_instances` in `do_attachment_downloads`) [7](#0-6) . A malicious/unprivileged outbound peer that the node happens to sync with can (a) answer the attachments-inventory request claiming to have the attachment, then (b) respond to the resulting `GET /v2/attachments/:hash` request with arbitrary garbage bytes up to `attachments_max_size` instead of the real content. Because there is no hash check, this garbage is inserted into `context.attachments`, and in the `Done` branch it is written to the `attachments` table with `was_instantiated=1` even though `find_all_attachment_instances(&garbage.hash())` returns nothing (no confirmed name op ever committed to that hash). Since the retry logic re-enqueues unresolved batches up to `max_attachment_retry_count` and the peer can return distinct garbage on each retry, and since `context.attachments` is a `HashSet<Attachment>` keyed by content (so distinct garbage payloads are distinct entries), this produces unbounded, permanently-stored, never-evicted garbage rows in the `attachments` table.

### Impact Explanation
The `attachments` table accumulates rows tagged `was_instantiated=1` that no confirmed BNS name-op ever committed to via `AttachmentInstance.content_hash` — a direct attachment/BNS mismatch (data served/stored as if validated when it never was). This is unbounded storage growth driven entirely by an unprivileged remote peer's chosen bytes, with no cap or expiry mechanism analogous to the uninstantiated-attachment eviction routines, and it is repeatable across every retry cycle and every unresolved attachment instance the node is tracking.

### Likelihood Explanation
Preconditions: the node must be running the Atlas downloader (default for BNS/Atlas-enabled nodes), have at least one outbound peer whose data URL is reachable, and have unresolved attachment instances queued (routine background activity, not attacker-controlled in count but naturally occurring). The attacker needs only to be a normal outbound-sync peer serving the node's own attachments-inventory and attachment HTTP requests — no secret, no privileged role, and no valid content is ever required. The attack is trivially repeatable across retries (bounded by `max_attachment_retry_count` per batch, but new batches recur as new BNS operations are processed) and costs the attacker only bandwidth to serve arbitrary bytes.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard and penalize (bump_failed_requests) any mismatching response instead of accepting it. Additionally, in `AttachmentsDownloader::run`'s `Done` branch, only call `insert_instantiated_attachment` when `find_all_attachment_instances` returns at least one matching instance (or, after the above fix, whenever the hash check passes), and add an eviction routine (age- and/or count-based) for `was_instantiated=1` rows analogous to `evict_k_oldest_uninstantiated_attachments`/`evict_expired_uninstantiated_attachments`.

### Proof of Concept
Rust net test plan (extending `stackslib/src/net/atlas/tests.rs`):
1. Set up two `TestPeer`s with Atlas enabled; seed peer B's atlasdb with a legitimate `AttachmentInstance` whose `content_hash = H(real_content)` but do not put `real_content` into B's `attachments` table (simulate B lying about having it).
2. Have B's HTTP `GET /v2/attachments/:hash` handler return arbitrary `garbage_bytes != real_content` (< `ATTACHMENTS_MAX_SIZE_MIN`) for the requested hash (simulate a malicious peer's `RPCGetAttachmentRequestHandler`/mock response bypassing the real DB lookup).
3. Drive `AttachmentsDownloader::run` on node A repeatedly (simulating retries with fresh garbage each time) against B.
4. Assert: `SELECT COUNT(*) FROM attachments WHERE was_instantiated=1` on A's atlasdb grows monotonically with each round, and that none of the stored hashes equal `H(real_content)` nor any hash present in a confirmed `AttachmentInstance.content_hash`, proving stored bytes were never committed to on-chain — i.e. `context.attachments.insert(response.attachment)` at `download.rs:548` and the unconditional `insert_instantiated_attachment` at `download.rs:161` are the exact lines exercised and the exploited gap.

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
