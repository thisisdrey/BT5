### Title
Replay-window check/decrypt/update race allows duplicate-packet replay bypass in `ConnectionState.Decrypt`/`VerifyRelay` - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the standard "check-then-use-then-commit" anti-replay pattern seen in the PRB-Proxy report: a piece of shared state (the replay window) is read (`window.Check`), used to gate an expensive/irreversible operation (AEAD decrypt), and only afterward is the state updated (`window.Update`) — with the lock released in between the check and the update, exactly like the PRB-Proxy pattern of reading `owner` into a local variable, letting arbitrary code run, then only comparing at the end. [1](#0-0) [2](#0-1) 

### Finding Description
Both `Decrypt` and `VerifyRelay` follow this sequence:
1. Lock `decryptLock`, call `window.Check(messageCounter)`, unlock.
2. Perform `DecryptDanger` (AEAD open) — this happens **without holding `decryptLock`**.
3. Lock `decryptLock` again, call `window.Update(messageCounter)`, unlock. [1](#0-0) 

The replay window (`Bits`) is the sole state guarding against processing the same message counter twice, and its invariant ("no counter is accepted twice") is only enforced by the pairing of `Check` and `Update`. Because the lock is dropped between steps 1 and 3, two goroutines processing the *same encrypted packet* concurrently (e.g., the packet queue workers in `readOutsidePackets`) can both pass `Check` for the same `messageCounter` before either calls `Update`: [3](#0-2) [4](#0-3) 

`Check` only inspects `b.current` and the bitmap; it does not reserve/mark the slot. The actual marking only happens in `Update`, which is called only after the (unlocked) decrypt/verify succeeds. This is structurally identical to the PRB-Proxy bug: a value is snapshotted, an attacker-influenceable operation runs while the lock/ownership is not held, and only a before/after-style check is performed — allowing the "same" state to be exploited twice within the window rather than once.

Nebula runs multiple UDP reader/writer goroutines (`listen.routines`), and `readOutsidePackets` is invoked concurrently for packets landing on the same `HostInfo`/`ConnectionState`. An attacker who captures a single valid ciphertext (no CA-signed certificate or session keys required — merely observing/replaying UDP traffic, which is the exact threat replay windows exist to stop) can duplicate that UDP datagram and send both copies at (near-)simultaneously. If both copies are scheduled onto different reader routines, both can reach `Decrypt`/`VerifyRelay` in the small window between `Check` and `Update`, and both will successfully decrypt/verify and get delivered to the TUN device (data-plane) or relay/forwarding logic (relay case), instead of the second being rejected as `ErrAlreadySeen`.

### Impact Explanation
This defeats the anti-replay/duplicate-suppression guarantee for the data plane and for relay verification:
- For `Decrypt` (used in the primary encrypted data path), a captured application packet can be delivered twice into the tun device, potentially duplicating application-level side effects (e.g., non-idempotent traffic) and corrupting flow/ordering assumptions that depend on messages being processed exactly once.
- For `VerifyRelay`, a captured relay frame can be double-processed and forwarded twice through `handleOutsideRelayPacket`, which also drives `connectionManager.RelayUsed`/roaming/refresh side effects on every accepted relay frame — a duplicate acceptance state-poisons those bookkeeping paths and can be leveraged for traffic amplification through the relay forwarding path.

This maps to the "nonce/replay handling" category explicitly permitted as a reachable analog, and does not require a CA-signed certificate, a malicious peer, or any special access — only the ability to capture and re-send one UDP datagram belonging to an existing tunnel, which any on-path/off-path network observer can attempt.

### Likelihood Explanation
Exploitation requires: (1) capturing at least one legitimate ciphertext (passively observable on the network since Nebula runs over plain UDP), and (2) causing two copies of it to be processed concurrently by different reader goroutines, which is realistic whenever `listen.routines` > 1 (a supported, non-default-but-common configuration for throughput) or, even with a single routine, whenever any inbound packet processing yields (e.g., due to Go scheduler preemption or coalesced/batched receive processing across NIC queues) between the `Check` and `Update` calls. The race window is small per-attempt but is trivially widened by sending many duplicate copies simultaneously, and the vulnerability is purely a synchronization defect rather than a cryptographic one, so it is deterministic once the race is won.

### Recommendation
Collapse the check-and-reserve step into a single atomic operation performed under one lock acquisition that is held until the counter is durably marked, e.g., have `Check`+"provisionally mark" be one locked operation, then only unmark on decrypt failure, instead of doing `Check` (unlocked window state), decrypt, then `Update`. Concretely: hold `decryptLock` across `Check`, and either mark the bit immediately (rolling back on decrypt failure) or use a per-counter reservation added atomically with the check, so no two callers can ever observe "not yet seen" for the same counter simultaneously.

### Proof of Concept
1. Establish a tunnel between two Nebula instances (`myControl`/`theirControl` as in the e2e tests).
2. Capture a single valid encrypted `header.Message` packet sent from `them` to `me` (e.g., using `theirControl.GetFromUDP` in the e2e harness, mirroring `TestStage1Race`-style packet capture).
3. Configure `me` with `listen.routines` > 1 (or otherwise ensure two goroutines call `readOutsidePackets` concurrently for the same `HostInfo`).
4. Simultaneously inject two copies of the captured packet via `myControl.InjectUDPPacket` from two goroutines so that both reach `ConnectionState.Decrypt` after both have passed `window.Check` but before either has called `window.Update`.
5. Observe that both copies are written to the tun device (`f.readers[q].Write(out)` in `handleOutsideMessagePacket`) instead of the second being rejected with `ErrAlreadySeen`, demonstrating a successful replay of the same message counter. [5](#0-4) [6](#0-5)

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (f *Interface) handleOutsideMessagePacket(hostinfo *HostInfo, out []byte, packet []byte, fwPacket *firewall.Packet, nb []byte, q int, localCache firewall.ConntrackCache) {
	err := newPacket(out, true, fwPacket)
	if err != nil {
		hostinfo.logger(f.l).Warn("Error while validating inbound packet",
			"error", err,
			"packet", out,
		)
		return
	}

	dropReason := f.firewall.Drop(*fwPacket, true, hostinfo, f.pki.GetCAPool(), localCache)
	if dropReason != nil {
		// NOTE: We give `packet` as the `out` here since we already decrypted from it and we don't need it anymore
		// This gives us a buffer to build the reject packet in
		f.rejectOutside(out, hostinfo.ConnectionState, hostinfo, nb, packet, q)
		if f.l.Enabled(context.Background(), slog.LevelDebug) {
			hostinfo.logger(f.l).Debug("dropping inbound packet",
				"fwPacket", fwPacket,
				"reason", dropReason,
			)
		}
		return
	}

	_, err = f.readers[q].Write(out)
	if err != nil {
		f.l.Error("Failed to write to tun", "error", err)
	}
}
