## Finding [1](#0-0) 

### Title
Active-permission (non-Owner) signers can be authorized to execute `AccountPermissionUpdateContract` and rewrite the Owner permission, bypassing the intended Owner-only control of account ownership - (File: `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java`, `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
TRON's multi-sig model mirrors the Safe/HatsSignerGate pattern: an account has an `Owner` permission (highest trust) and one or more `Active` permissions that are supposed to be scoped to a restricted set of operations via a 256-bit `operations` bitmap [2](#0-1) . The transaction-level permission check treats any non-zero `permissionId` as an `Active` permission and only requires that the invoked contract type's bit be set in that permission's `operations` bitmap — no special-casing exists for the permission-management contract itself [1](#0-0) . Because `AccountPermissionUpdateActuator.checkPermission` validates the operations bitmap only against `DynamicPropertiesStore.getAvailableContractType()` — whose default value includes `AccountPermissionUpdateContract` itself (confirmed by the compatibility test `checkAvailableContractTypeCorrespondingToCode`) [3](#0-2)  — a low-trust `Active` permission can legally be configured to include the bit for `AccountPermissionUpdateContract`. Once that bit is set, any signer(s) meeting that `Active` permission's (potentially much lower) threshold can call `AccountPermissionUpdateContract` and completely rewrite the account's `Owner` permission, `Witness` permission, and all `Active` permissions in one transaction, without ever needing an `Owner`-permission signature.

### Finding Description
The Owner/Active permission separation exists precisely so that "signers" holding a restricted, lower-trust `Active` permission (analogous to the Safe multi-sig "signers" in the external report) cannot unilaterally take control of account ownership. This is reinforced by the fact that the *default* Active-permission template deliberately excludes `AccountPermissionUpdateContract` from its allowed operations (`ACTIVE_DEFAULT_OPERATIONS` explicitly filters it out) [4](#0-3) , and the initial dynamic-store default `ACTIVE_DEFAULT_OPERATIONS` bytes are set without the `AccountPermissionUpdateContract` bit [5](#0-4) .

However, `AccountPermissionUpdateActuator.checkPermission` — the function that validates any *new* Active permission's operations during an `AccountPermissionUpdate` — checks the requested operations bitmap against `getAvailableContractType()`, not against the safer `ACTIVE_DEFAULT_OPERATIONS` template [6](#0-5) . Since `getAvailableContractType()`'s default value includes the `AccountPermissionUpdateContract` type bit, nothing in validation prevents an `Active` permission from being defined with that bit turned on.

Once such an `Active` permission exists, `TransactionCapsule.checkPermission` (used both when adding signatures and when validating on-chain) enforces access purely through the generic operations-bitmap check for any `permissionId != 0` [1](#0-0) , and `TransactionCapsule.validateSignature`/`addSign` apply the identical generic logic [7](#0-6) . There is no additional carve-out that forbids `AccountPermissionUpdateContract` from being executed under a non-zero (Active) `permissionId`. This is the direct analog of the reported issue: a role meant to be constrained (Active-permission signers, analogous to Safe "signers" under HSG) can invoke the master permission-management operation (`AccountPermissionUpdateContract`, analogous to Safe's `OwnerManager.addOwnerWithThreshold/removeOwner/swapOwner`) that is supposed to be gated at a higher trust level (Owner permission, analogous to genuine Safe-owner/HSG-governed control), because the enforcement layer (`checkPermission`/operations bitmap) does not specifically exclude this sensitive contract type from Active-permission delegation.

### Impact Explanation
If an `Active` permission is configured (intentionally for automation, or due to operator error, or via a compromised low-trust key that itself has `AccountPermissionUpdateContract` in its own delegated scope) with the `AccountPermissionUpdateContract` bit set, any set of signers meeting that Active permission's threshold can:
- Replace the `Owner` permission's key set/threshold entirely (e.g., install attacker-controlled keys as sole owner), achieving full unauthorized takeover of the account and all its funds/voting rights.
- Remove the legitimate account owner's keys, permanently locking the original owner out.
- Rewrite all `Active` permissions and the `Witness` permission, again without any Owner-level signature.

This satisfies "concrete unauthorized account operation" and "theft or permanent freezing of funds" criteria, since account takeover directly leads to loss of control over TRX/TRC10/TRC20 balances, staked/voting power, and witness identity tied to that address.

### Likelihood Explanation
The precondition (an Active permission whose `operations` bitmap includes `AccountPermissionUpdateContract`) is not blocked by any validation path in `AccountPermissionUpdateActuator.checkPermission`, so it is trivially reachable by any account owner performing a single `AccountPermissionUpdateContract` transaction (broadcastable by anyone controlling that account's Owner key at the time of configuration). Given the default `AccountPermissionUpdateContract` bit is present in `getAvailableContractType()` (not excluded like it is from `ACTIVE_DEFAULT_OPERATIONS`), there is a clear discrepancy between the "safe default" template and what validation actually permits, making it easy to set up—deliberately or by misunderstanding the semantics of "Active operations"—an Active permission that undermines the Owner/Active trust boundary.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission`, explicitly reject `AccountPermissionUpdateContract` (and any other identity/permission-management contract types) from being included in the `operations` bitmap of any `Active` permission, regardless of `getAvailableContractType()`'s contents — mirroring the exclusion already applied when computing `ACTIVE_DEFAULT_OPERATIONS`. This ensures only the true `Owner` permission (`permissionId == 0`) can ever authorize changes to an account's permission structure, closing the gap that lets Active-permission signers bypass the Owner-only control model.

### Proof of Concept
1. Account `A` has default Owner permission (key `O`) and calls `AccountPermissionUpdateContract` to define a new `Active` permission `P2` with `threshold = 1`, keys `{K1}`, and an `operations` bitmap that includes the bit for `ContractType.AccountPermissionUpdateContract` (allowed because `checkPermission` only validates against `getAvailableContractType()`, which includes this bit by default) [6](#0-5) .
2. Later, the holder of `K1` (an Active-permission signer, not the Owner) constructs a new transaction of type `AccountPermissionUpdateContract` with `ownerAddress = A`, `permissionId = P2's id`, setting a brand-new `Owner` permission containing only attacker keys and `threshold = 1`.
3. `TransactionCapsule.checkPermission` accepts this because `permissionId != 0`, `P2.getType() == Active`, and `checkPermissionOperations(P2, contract)` returns true (the bit is set) [1](#0-0) .
4. `AccountPermissionUpdateActuator.execute` applies the new Owner permission, fully transferring control of account `A` to the attacker without any signature from the original Owner key `O`.
