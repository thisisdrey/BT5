### Title
Unvalidated section-length arithmetic in `parseArmAttributes` allows a crafted ELF object to panic the Go linker - ([File: src/cmd/link/internal/loadelf/ldelf.go])

### Summary
`cmd/link/internal/loadelf.parseArmAttributes` parses the `.ARM.attributes` section of an ELF relocatable object being linked, using length fields read directly from the file to slice byte buffers without validating that the lengths fit within the remaining data. A crafted ARM object file (`.o`/`.syso`) with an undersized or oversized `sectionlength`/`subsectionsize` field triggers a Go runtime slice-bounds panic in the linker, matching the "crafted binary causing a crash during parsing/handling of machine-specific ELF flags" pattern in CVE-2017-9744's `sh_elf_set_mach_from_flags`.

### Finding Description
Attacker supplies a malicious ARM ELF relocatable object (e.g., a vendored `.syso` file or cgo-produced `.o` bundled in a Go module) that a victim links via `go build`. The linker's ARM loading path calls `loadelf.Load` (`src/cmd/link/internal/loadelf/ldelf.go:244`), which invokes `parseArmAttributes` (`src/cmd/link/internal/loadelf/ldelf.go:190-234`) on the raw bytes of the `.ARM.attributes` section: [1](#0-0) 

Here `sectionlength := e.Uint32(data)` and `sectiondata := data[4:sectionlength]` are computed straight from attacker-controlled bytes with no check that `sectionlength >= 4` or `sectionlength <= len(data)`. The nested loop similarly computes `subsectionsize := e.Uint32(sectiondata[sz:])` and slices `sectiondata[sz+4 : subsectionsize]` without validating `subsectionsize >= sz+4` or `subsectionsize <= len(sectiondata)`. Any of these conditions being violated causes a Go slice-bounds-out-of-range panic, crashing the linker mid-build.

This differs from the well-known, explicitly-out-of-scope `debug/elf` package (which itself documents that it is "not designed to be hardened against adversarial inputs" and is outside the Go security policy — [2](#0-1) , and which does perform bounds validation via `saferio` in `NewFile`, e.g. [3](#0-2) ). `loadelf` is part of the Go toolchain itself (`cmd/link`), consuming untrusted build inputs during a normal `go build` workflow, which is the kind of "build-time handling of untrusted source" the rules call out for special scrutiny.

### Impact Explanation
The impact is a linker panic/crash (denial of service against the build), not memory corruption or code execution, since Go's runtime bounds-checks slices and converts the out-of-bounds access into a panic rather than an exploitable buffer overflow. This is a legitimate parser-panic-on-malicious-input class of bug per Go's stated policy ("plausible malicious-input parser panic can qualify"), but it is confined to a build-time DoS of `go build`/`go tool link` when linking an attacker-supplied ARM object file, not a runtime-exploitable memory-safety issue as in the original BFD CVE. This would likely be assessed on Go's PUBLIC track (low-severity build-tool DoS) rather than URGENT, since no code execution or data corruption results.

### Likelihood Explanation
Requires the victim to run `go build`/`go link` on a target that includes an ARM ELF object supplied by the attacker (e.g., embedded in a third-party Go module as a `.syso` file, or a cgo-compiled `.o` from an untrusted C source tree). This is a plausible but narrow victim workflow (ARM cross-linking with externally supplied object files), not a common default path for most Go builds (amd64/arm64 with pure-Go modules never invoke this ARM-specific attribute parser).

### Recommendation
Add explicit bounds checks in `parseArmAttributes` before every slice operation derived from file-controlled lengths: validate `4 <= sectionlength <= len(data)` before computing `sectiondata`/advancing `data`, and validate `sz+4 <= subsectionsize <= len(sectiondata)` before computing `subsectiondata`/advancing `sectiondata`. On violation, return a parse error (as is already done for the missing-NUL-terminator case) instead of panicking.

### Proof of Concept
```go
package loadelf

import (
	"encoding/binary"
	"testing"
)

// Demonstrates a slice-bounds panic when parsing a crafted .ARM.attributes
// section with an oversized sectionlength field.
func TestParseArmAttributesCrash(t *testing.T) {
	e := binary.LittleEndian
	data := []byte{'A'}
	// section length field claims a length far larger than the
	// remaining buffer, causing data[4:sectionlength] to panic.
	sectionLen := make([]byte, 4)
	e.PutUint32(sectionLen, 0xFFFFFFFF)
	data = append(data, sectionLen...)
	data = append(data, []byte("aeabi\x00")...)

	defer func() {
		if r := recover(); r == nil {
			t.Fatalf("expected panic from out-of-range slice, got none")
		}
	}()

	// parseArmAttributes should return an error, not panic.
	_, _, _ = parseArmAttributes(e, data)
}
```
Expected (buggy) behavior: the test recovers a `runtime error: slice bounds out of range` panic from `sectiondata := data[4:sectionlength]`, confirming the crash. After the fix, `parseArmAttributes` should instead return a non-nil `err` and the test should be changed to assert `err != nil` with no panic.
