### Title
`extend_with_attachments` rewards peers with successful-request credit for hash-mismatched attachments - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558) calls `report.bump_successful_requests()` immediately after `response.decode_atlas_get_attachment()` succeeds, with no comparison of the returned attachment's hash against the requested `AttachmentRequest.content_hash`. A peer can therefore inflate its `ReliabilityReport` score by returning any well-formed but content-mismatched attachment blob.

### Finding Description
In `extend_with_attachments`, for each `(request, response)` pair pulled from `results.succeeded`, the code does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

`decode_atlas_get_attachment()` only validates that the HTTP response body deserializes into a `GetAttachmentResponse` (i.e., valid hex-encoded bytes forming an `Attachment`) — see the `Deserialize` impl, which just hex-decodes the payload into `Attachment::new(bytes)` with no hash check at all [2](#0-1) . The `AttachmentRequest` used to issue the request carries the expected `content_hash` [3](#0-2) , but `extend_with_attachments` never reads `request.content_hash` before calling `bump_successful_requests()`. Any equality check against the requested hash, if it exists at all, happens strictly after the reliability score has already been incremented, so the score-bump-implies-hash-match invariant is broken at this line.

A remote peer that is queried for an attachment can return a syntactically valid, hex-decodable but arbitrary/garbage attachment body for every request. Each such reply causes `bump_successful_requests()` to fire, letting the peer cheaply accumulate an arbitrarily high reliability score over many requests, since generating valid hex-encoded JSON responses costs the attacker nothing extra compared to serving the real content.

### Impact Explanation
Reliability reports drive `AttachmentRequest`'s ordering (`Ord`) and `get_most_reliable_source`-style peer selection used to prioritize which peer's data is trusted/retried first for future attachment fetches tied to BNS name resolution. An attacker who cheaply inflates their score via this decoupling can get preferentially selected as a data source, increasing the chance that poisoned/incorrect attachment content (e.g., BNS name-to-zonefile mappings) is fetched from and prioritized against that attacker in subsequent rounds, i.e., attachment/BNS mismatch — a High-severity outcome per the stated impact categories.

### Likelihood Explanation
The attacker only needs to be an outbound sync peer contactable over the node's P2P/RPC data URL, requiring no privileged role, secret, or slot ownership — reachable by any peer legitimately queried for attachments. The cost per request is trivial (return any hex-encoded byte blob), and the attack is fully repeatable across the lifetime of the node's reliability tracking for that peer URL.

### Recommendation
In `extend_with_attachments`, after decoding the response, compute the content hash of `response.attachment` (e.g., via its `MerkleHashFunc`/hash implementation) and compare it to `request.content_hash` before calling `report.bump_successful_requests()`. Only bump success on a matching hash; treat mismatches as failed requests (`report.bump_failed_requests()`) and discard/do not insert the mismatched attachment into `self.attachments`.

### Proof of Concept
Rust test plan (net test module for `atlas::download`):
1. Construct an `AttachmentsBatchStateContext` with a `peers` map containing one `ReliabilityReport::empty()` keyed to a test peer URL.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains one `AttachmentRequest` with a known `content_hash` (e.g., hash of `b"real-content"`), paired with a crafted `StacksHttpResponse` whose body hex-encodes an unrelated payload (e.g., `b"attacker-garbage"`).
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert: `context.peers[&peer_url].score()` increased (successful count incremented) even though `Hash160::from_data(b"attacker-garbage") != request.content_hash`, proving the equality "bump_successful_requests() called <=> served content hash matches requested content_hash" is violated at download.rs:547-549.

    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
