### Title
Unbounded attacker-controlled array-length allocation in TVM precompile signature-array parsing leads to node OOM/crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`BatchValidateSign` and `ValidateMultiSign` are TVM precompiled contracts (addresses `0x9` and `0xa`) reachable by any contract call from an unprivileged transaction (`TriggerSmartContract`). Both decode their calldata into `DataWord[] words` and then call `extractBytesArray` / `extractSigArray` / `extractBytes32Array`, which read a "length" word directly from attacker-supplied calldata and immediately allocate a Java array sized by that value, before any upper bound is enforced.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read an unchecked length from the calldata-derived `words` array and allocate accordingly: [1](#0-0) 

In `BatchValidateSign.doExecute` and `ValidateMultiSign.execute`, the `MAX_SIZE` bound check (16 / 5 respectively) is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; when that flag is not active, `extractBytesArray`/`extractBytes32Array` are invoked with the raw, attacker-controlled length taken from the calldata header before any size validation: [2](#0-1) [3](#0-2) 

Also, the ABI-shape guard (`isValidAbiEncoding`) that could otherwise reject malformed lengths is only applied when `VMConfig.allowTvmOsaka()` is active: [4](#0-3) [5](#0-4) 

This mirrors the CVE-2019-13960 bug class: a size field taken from untrusted input (there, JPEG width/height header fields; here, an ABI-encoded array-length word from transaction calldata) is used to drive a large memory allocation before the value is sanity-checked against any real limit, allowing a small malicious input to trigger disproportionate memory consumption.

### Impact Explanation
If either `allowTvmSelfdestructRestriction` or `allowTvmOsaka` (chain-parameter gated hard-fork flags) is not active on a given network/at a given block height, an attacker can craft calldata to `BatchValidateSign`/`ValidateMultiSign` where the length word controlling `extractBytesArray`/`extractBytes32Array`/`extractSigArray` is set to a very large value (e.g., near `Integer.MAX_VALUE`). This causes an immediate attempt to allocate a `byte[len][]` reference array, which can throw `OutOfMemoryError` in the executing thread. Because Java's `OutOfMemoryError` is a JVM-wide condition, this can destabilize or crash the FullNode process handling the transaction, potentially affecting concurrent transaction processing on the same JVM — a node crash/halt condition explicitly in scope.

### Likelihood Explanation
Any address can call a deployed contract that in turn triggers a `CALL` to the precompile address `0x9` or `0xa` with arbitrary calldata; no special permission is required, only enough energy to reach the precompile call (the `getEnergyForData` cost is computed from `data.length`, not from the malicious length word, so the energy charged does not reflect the requested allocation size). Exploitability depends on the state of `allowTvmSelfdestructRestriction`/`allowTvmOsaka` on the target network — since I could not confirm the current activation status of these TIP-gated parameters in this codebase snapshot, the exact current exposure on mainnet is uncertain and would need to be verified against live chain parameters.

### Recommendation
Move the length/array-size bound checks (`sigArraySize > MAX_SIZE`, `addrArraySize > MAX_SIZE`) so they are always enforced unconditionally in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` (not gated behind `allowTvmSelfdestructRestriction`), and validate that the decoded length is non-negative and does not exceed a small hard cap (e.g., `MAX_SIZE`) before any array allocation occurs, regardless of the `allowTvmOsaka`/ABI-encoding-validation flag state.

### Proof of Concept
1. Deploy a contract that performs a `CALL` (or `STATICCALL`) to precompile address `0x0000...0009` (BatchValidateSign) or `0x0000...000a` (ValidateMultiSign) with calldata where:
   - The header offset words are valid,
   - The word at the "array length" position (`words[offset]`) is set to a very large value, e.g. `0x7FFFFFFF`.
2. Submit this as a normal `TriggerSmartContract` transaction on a network where `allowTvmSelfdestructRestriction` (TIP for selfdestruct restriction) is not yet activated, so the `MAX_SIZE` pre-check is skipped and execution reaches `extractBytesArray(words, offset, data)` / `extractBytes32Array(words, offset)` directly with the attacker length.
3. Observe the resulting `new byte[len][]` allocation attempt, which triggers `OutOfMemoryError` in the transaction-executing thread and can destabilize the node process.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
