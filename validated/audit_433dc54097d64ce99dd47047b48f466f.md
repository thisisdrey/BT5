### Title
`NativeTokenGateway.deposit` accepts a registered pool without native-token collateral, permanently locking user ETH - ([File: contracts/NativeTokenGateway.sol](contracts/NativeTokenGateway.sol))

### Summary
`NativeTokenGateway.deposit` validates that `pool_` is registered, but never validates that the pool has a `DepositToken` for `nativeToken`. On a registered pool where `depositTokenOf(nativeToken) == address(0)`, the function first wraps the caller’s ETH into `nativeToken`, then calls `deposit` on the zero-address result, allowing the transaction to complete while the wrapped native tokens remain locked in the gateway. [1](#0-0) 

### Finding Description
The gateway checks only `_poolRegistry.isPoolRegistered(address(pool_))` before calling `nativeToken.deposit{value: msg.value}()`. [2](#0-1) 

It then obtains `pool_.depositTokenOf(nativeToken)` and uses the returned address without a non-zero check. [3](#0-2) 

`Pool.depositTokenOf` is a mapping keyed by underlying asset and therefore returns `address(0)` for an unsupported collateral. [4](#0-3) 

The deployed mainnet configuration has multiple registered pools, while Pool2 is configured with a USDC deposit token rather than a WETH/native-token deposit token. [5](#0-4) 

Because an EVM call to an account with no code succeeds and the two return values from `IDepositToken.deposit` are ignored, the final `_depositToken.deposit(...)` call can succeed when `_depositToken` is `address(0)`. The ETH is already wrapped and held by the gateway, but no msdToken is minted and no collateral position is created. [6](#0-5) 

The same unchecked descriptor pattern also exists in `VesperGateway.deposit`, which deposits underlying into the selected `vToken_` before calling the zero-value `pool_.depositTokenOf(vToken_)`. [7](#0-6) 

### Impact Explanation
This causes permanent freezing of user funds: the caller loses the ETH/native-token value, receives no deposit token, and has no public method to recover the wrapped tokens from the gateway. Token recovery exists only through `TokenHolder.sweep`, which is restricted by `_requireCanSweep`; in `NativeTokenGateway`, that hook is governor-only. [8](#0-7) [9](#0-8) 

The issue is analogous to the reported NULL-pointer dereference: attacker-controlled or mistaken input selects a valid outer object, but an internal lookup returns null and the code proceeds after the failed invariant instead of reverting before funds are committed. [1](#0-0) 

### Likelihood Explanation
Any unprivileged caller can trigger this path with a single public `deposit(pool_)` call and a registered pool that lacks native-token collateral. No privileged role, oracle manipulation, malicious deployment inside the protocol, or invalid pool registration is required. [1](#0-0) 

The risk is materially increased by the multi-pool deployment: the registry deliberately supports multiple pools, while collateral support is configured separately per pool through `addDepositToken`. [10](#0-9) [11](#0-10) 

### Recommendation
Resolve the deposit token before committing funds and revert if it is absent:

```solidity
// contracts/NativeTokenGateway.sol
IDepositToken _depositToken = pool_.depositTokenOf(nativeToken);
if (address(_depositToken) == address(0)) revert DepositTokenDoesNotExist();

nativeToken.deposit{value: msg.value}();
nativeToken.safeApprove(address(_depositToken), msg.value);
_depositToken.deposit(msg.value, _msgSender());
```

Apply the same validation in `VesperGateway.deposit` before transferring or depositing user assets, and in both `withdraw` functions before attempting `safeTransferFrom` through a missing deposit token. [12](#0-11) 

### Proof of Concept
The following Hardhat mainnet-fork proof demonstrates that a registered Pool2 returns no deposit token for WETH and that a deposit leaves WETH locked in the gateway:

```ts
// test/NativeTokenGatewayMissingCollateral.poc.ts
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {parseEther} from 'ethers/lib/utils'

const POOL_REGISTRY = '0x11eaD85C679eAF528c9C1FE094bF538Db880048A'
const WETH = '0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2'

it('locks ETH when the registered pool lacks a native deposit token', async () => {
  const [user] = await ethers.getSigners()

  const registry = await ethers.getContractAt(
    [
      'function getPools() view returns (address[])',
      'function nativeTokenGateway() view returns (address)',
      'function isPoolRegistered(address) view returns (bool)',
    ],
    POOL_REGISTRY
  )

  const [, pool2] = await registry.getPools()
  expect(await registry.isPoolRegistered(pool2)).to.eq(true)

  const pool = await ethers.getContractAt(
    ['function depositTokenOf(address) view returns (address)'],
    pool2
  )
  expect(await pool.depositTokenOf(WETH)).to.eq(ethers.constants.AddressZero)

  const gatewayAddress = await registry.nativeTokenGateway()
  const gateway = await ethers.getContractAt(
    ['function deposit(address) payable'],
    gatewayAddress,
    user
  )

  const weth = await ethers.getContractAt(
    ['function balanceOf(address) view returns (uint256)'],
    WETH
  )

  const amount = parseEther('1')
  await expect(gateway.deposit(pool2, {value: amount})).to.not.be.reverted

  expect(await weth.balanceOf(gatewayAddress)).to.eq(amount)
})
```

This matches the production flow: `Pool2` is registered, `depositTokenOf(WETH)` is zero, ETH is wrapped first, and the gateway retains the WETH because the zero-address deposit call does not create a position. [1](#0-0)

    function deposit(IPool pool_, IVPool vToken_, uint256 amount_) external override {
        if (!_poolRegistry.isPoolRegistered(address(pool_))) revert UnregisteredPool();

        address _msgSender = _msgSender();

        // 1. Get `underlying` asset
        IERC20 _underlying = IERC20(vToken_.token());
        _underlying.safeTransferFrom(_msgSender, address(this), amount_);

        // 2. Deposit `underlying` to `VPool`
        _underlying.safeApprove(address(vToken_), 0);
        _underlying.safeApprove(address(vToken_), amount_);
        uint256 _balanceBefore = vToken_.balanceOf(address(this));
        vToken_.deposit(amount_);
        uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;

        // 3. Deposit `VPool` to `Synth` and send `msdTokens` to the `_msgSender()`
        IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
        vToken_.safeApprove(address(_depositToken), 0);
        vToken_.safeApprove(address(_depositToken), _vTokenAmount);
        _depositToken.deposit(_vTokenAmount, _msgSender);
