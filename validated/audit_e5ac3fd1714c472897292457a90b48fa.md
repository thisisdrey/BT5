### Title
Missing negotiation-phase deadline in HTTP `upload-pack` enables time-of-check-to-time-of-use (TOCTOU) access-check bypass - (File: `internal/gitaly/service/smarthttp/upload_pack.go`)

### Summary
Gitaly explicitly documents and mitigates a "missing deadline" class of bug for `git-upload-pack`/`git-upload-archive` negotiation over SSH, but the equivalent HTTP path (`PostUploadPackWithSidechannel` → `runUploadPack`) does not apply this same negotiation-phase deadline, leaving it exposed to the analogous use-after-check race.

### Finding Description
Gitaly's `pktline.ReadMonitor` was purpose-built to prevent a "use-after-check" security issue: because the RPC's access check runs once at the start of the call while stdin (the pack negotiation) remains fully under client control, a client that stalls sending its negotiation packet can make the access check stale — its permissions could have changed by the time the actual data transfer happens. [1](#0-0) 

This mitigation is wired up for the SSH transport: `sshUploadPack` obtains a `timeoutTicker` and calls `runUploadCommand`, which wraps stdin in a `pktline.NewReadMonitor` and cancels the command's context if the boundary packet (`done`) is not observed before the ticker fires. [2](#0-1) [3](#0-2) 

The same class of vulnerability exists in `git-upload-archive` over SSH and is likewise mitigated (`WithArchiveRequestTimeoutTickerFactory`, tested in `upload_archive_test.go`).

However, the HTTP transport's equivalent handler, `PostUploadPackWithSidechannel` → `runUploadPack` in `internal/gitaly/service/smarthttp/upload_pack.go`, spawns `git-upload-pack --stateless-rpc` with the raw sidechannel connection as `stdin` and never installs a `pktline.ReadMonitor`, a `timeoutTicker`, or any other negotiation-phase deadline. The command's context is simply the RPC's `ctx`, with no bound on how long the client can withhold the negotiation-terminating packet before Gitaly's access check (performed earlier via `validateUploadPackRequest`) is considered stale. [4](#0-3) 

A `grep` across the codebase confirms `runUploadCommand`, `NewReadMonitor`, and `timeoutTicker` are referenced only from the `internal/gitaly/service/ssh` package (plus their own tests) — `internal/gitaly/service/smarthttp` never uses them.

### Impact Explanation
An ordinary authenticated user performing a `git clone`/`fetch` over HTTP (Smart HTTP transport, `PostUploadPackWithSidechannel`) can open the connection, pass Gitaly's initial access validation, and then hold the negotiation phase open indefinitely (never sending the `done` pktline) while their access to the repository is revoked in the interim (e.g., project made private, user removed from project, token revoked). Because no negotiation deadline exists on this path, Gitaly has no mechanism to re-check or expire the stale authorization, and `git-upload-pack` may still produce and serve a packfile of repository objects to a now-unauthorized client — a confidentiality/access-control bypass mirroring exactly the TOCTOU concern the `ReadMonitor` package itself calls out. This also represents a resource-exhaustion/DoS vector, since the underlying `git-upload-pack` process and its allocated resources remain held for however long the client withholds negotiation.

### Likelihood Explanation
No privileged access or malicious peer/node cooperation is required — any ordinary client capable of issuing a Smart HTTP fetch/clone request can trigger this by simply controlling the pacing of its own request body. The bug class is not hypothetical within this codebase; it's the identical scenario that motivated the `ReadMonitor` mitigation, just left unapplied to one of the two transports that share the same `git-upload-pack` access-check-then-negotiate pattern.

### Recommendation
Apply the same `pktline.ReadMonitor`/`timeoutTicker` negotiation-phase deadline used in `internal/gitaly/service/ssh/upload_command.go` to the HTTP `runUploadPack` path in `internal/gitaly/service/smarthttp/upload_pack.go`, canceling the `git-upload-pack --stateless-rpc` command's context if the negotiation-terminating packet is not observed within a bounded time window, consistent with the SSH implementation.

### Proof of Concept
1. As an authenticated user with read access to a repository, initiate a Smart HTTP `git clone`/`fetch`, which invokes `PostUploadPackWithSidechannel` → `runUploadPack` (`internal/gitaly/service/smarthttp/upload_pack.go:127`).
2. `validateUploadPackRequest` performs the access check once at the start of the call.
3. Deliberately withhold sending the final negotiation pktline (`done`) on the sidechannel connection for an extended period (there is no `pktline.ReadMonitor`/timeout on this path to cut off the command, unlike `sshUploadPack`).
4. During this window, have the repository's visibility changed to private or the user's access revoked.
5. Resume sending the negotiation packet; `git-upload-pack` proceeds to generate and stream the packfile via `io.CopyBuffer(stdout, cmd, ...)` at line 180, serving repository objects despite the now-revoked authorization — demonstrating the absence of the deadline-based mitigation present in the SSH transport.

```go
// ReadMonitor monitors an io.Reader, waiting for a specified packet. If the
// packet doesn't come within a timeout, a cancel function is called. This can
// be used to place a timeout on the *negotiation* phase of some git commands,
// aborting them if it is exceeded.
//
// This timeout prevents a class of "use-after-check" security issue when the
// access check for a git command is run before the command itself. The user
// has control of stdin for the git command, and if they can delay input for
// an arbitrarily long time, they can gain access days or weeks after the
// access check has completed.
//
// This approach is better than placing a timeout on the overall git operation
// because there is a conflict between mitigating the use-after-check with a
// short timeout, and allowing long-lived git operations to complete. The
// negotiation phase is a small proportion of the time taken for a large git
// fetch, for instance, so tighter limits can be placed on it, leading to a
// better mitigation.
```

```go
// runUploadCommand runs an uploading command like git-upload-pack(1) or git-upload-archive(1). It serves multiple
// purposes:
//
//   - It sets up a large buffer reader such that we can write the data more efficiently.
//
//   - It logs how many bytes have been sent.
//
//   - It installs a timeout such that we can address time-of-check-to-time-of-use-style races. Otherwise it would be
//     possible to open the connection early, keep it open for an extended amount of time, and only do the negotiation of
//     what is to be sent at a later point when permissions of the user might have changed.
func (s *server) runUploadCommand(
	rpcContext context.Context,
	repo gitcmd.RepositoryExecutor,
	stdin io.Reader,
	stdout, stderr io.Writer,
	timeoutTicker helper.Ticker,
	boundaryPacket []byte,
	sc gitcmd.Command,
	opts ...gitcmd.CmdOpt,
) error {
	ctx, cancelCtx := context.WithCancel(rpcContext)
	defer cancelCtx()

	var stderrBuilder strings.Builder
	stderr = io.MultiWriter(stderr, &stderrBuilder)

	stdoutCounter := &helper.CountingWriter{W: stdout}
	// Use large copy buffer to reduce the number of system calls
	stdout = &largeBufferReaderFrom{Writer: stdoutCounter}

	stdinPipe, monitor, cleanup, err := pktline.NewReadMonitor(ctx, stdin, s.logger)
	if err != nil {
		return fmt.Errorf("create monitor: %w", err)
	}

	cmd, err := repo.Exec(ctx, sc, append([]gitcmd.CmdOpt{
		gitcmd.WithStdin(stdinPipe),
		gitcmd.WithStdout(stdout),
		gitcmd.WithStderr(stderr),
		gitcmd.WithFinalizer(func(context.Context, *command.Command) { cleanup() }),
	}, opts...)...)
	stdinPipe.Close() // this now belongs to cmd
	if err != nil {
		cleanup()
		return fmt.Errorf("starting command: %w", err)
	}

	go monitor.Monitor(ctx, boundaryPacket, timeoutTicker, cancelCtx)
```

```go
func (s *server) runUploadPack(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest, repoPath string, gitConfig []gitcmd.ConfigPair, stdin io.Reader, stdout io.Writer) (stats *stats.PackfileNegotiation, _ error) {
	h := sha1.New()

	stdin = io.TeeReader(stdin, h)
	stdin, collector := s.runStatsCollector(ctx, stdin)
	defer func() {
		if stats == nil {
			stats = collector.finish()
		}
	}()

	repo := s.localRepoFactory.Build(req.GetRepository())
	if s.bundleURIManager != nil {
		// Bundle generation is an optimization that is transparent to users.
		// If it fails, we log the error but continue with the regular upload-pack
		// operation without the bundle optimization.
		// If successful, a goroutine is spawned to generate the bundle, in which case
		// the bundle generation becomes independent of the RPC request.
		if err := s.bundleURIManager.GenerateWithStrategy(ctx, repo); err != nil {
			s.logger.WithError(err).Error("failed generating bundle")
		}
		gitConfig = append(gitConfig, s.bundleURIManager.UploadPackGitConfig(ctx, req.GetRepository())...)
	} else {
		gitConfig = append(gitConfig, bundleuri.CapabilitiesGitConfig(ctx, false)...)
	}

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return nil, fmt.Errorf("detecting object hash: %w", err)
	}

	commandOpts := []gitcmd.CmdOpt{
		gitcmd.WithStdin(stdin),
		gitcmd.WithSetupStdout(),
		gitcmd.WithGitProtocol(s.logger, req),
		gitcmd.WithConfig(gitConfig...),
		gitcmd.WithPackObjectsHookEnv(objectHash, req.GetRepository(), "http"),
	}

	if s.cfg.Hooks.PackObjectsHookMaxProc > 0 {
		commandOpts = append(commandOpts, gitcmd.WithEnv("GOMAXPROCS="+strconv.Itoa(int(s.cfg.Hooks.PackObjectsHookMaxProc))))
	}

	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name:  "upload-pack",
		Flags: []gitcmd.Option{gitcmd.Flag{Name: "--stateless-rpc"}},
		Args:  []string{repoPath},
	}, commandOpts...)
	if err != nil {
		return nil, structerr.NewFailedPrecondition("spawning upload-pack: %w", err)
	}
```
