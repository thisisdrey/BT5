Confirmed: `ExchangeInjectContract` and `ExchangeWithdrawContract` have no `expected`/minimum field, unlike `ExchangeTransactionContract` which explicitly carries an `expected` slippage-protection field.

### Title
Missing slippage protection (no "expected" minimum) in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` allows sandwich attacks on liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Both TRON's bancor-style `Exchange` inject and withdraw actuators compute the counter-token amount (`anotherTokenQuant`) purely from the pool's live token balances at execution time, with no user-supplied minimum/maximum bound — functionally equivalent to the reported `amountOutMinimum: 0` hardcoded slippage bug in the Uniswap-based contract.

### Finding Description
`ExchangeTransactionContract` (a swap) is the only exchange contract that carries an `expected` field used as a slippage floor, checked in `ExchangeTransactionActuator`'s `doValidate` with `if (anotherTokenQuant < tokenExpected) throw ...`. [1](#0-0) 

`ExchangeInjectContract` and `ExchangeWithdrawContract`, by contrast, only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no field for a caller to bound the amount of the paired token they are willing to deposit (inject) or the amount they expect to receive back (withdraw). [2](#0-1) 

In `ExchangeInjectActuator.doValidate`/`execute`, `anotherTokenQuant` (the amount of the paired asset the injector must also contribute) is derived solely from the current on-chain pool ratio (`firstTokenBalance`/`secondTokenBalance`) at validation/execution time, then that exact amount is deducted from the caller's balance: [3](#0-2) [4](#0-3) 

Similarly, `ExchangeWithdrawActuator` computes `anotherTokenQuant` (what the withdrawer receives) from the live pool ratio with only a "greater than zero" check, no user-specified minimum: [5](#0-4) [6](#0-5) 

Because block producers order transactions and multiple `ExchangeTransactionContract` (swap) transactions can be injected before an inject/withdraw transaction lands in the same block or a subsequent one under the actor's control, an attacker can shift `firstTokenBalance`/`secondTokenBalance` immediately before the victim's inject/withdraw transaction executes, then reverse the swap afterward, extracting value from the mismatch between the ratio the victim expected off-chain and the ratio actually used at execution.

### Impact Explanation
For `ExchangeInjectActuator`, a manipulated ratio forces the injecting account to pay more of the paired token than they intended for the same `quant` of their chosen token, resulting in an unfavorable/loss-making liquidity contribution — a direct loss of user funds with no way to cap exposure. For `ExchangeWithdrawActuator`, a manipulated ratio can cause the withdrawer to receive fewer paired tokens than expected. This is unauthorized value extraction from the affected user's on-chain balance, reachable by any unprivileged account broadcasting an `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction, satisfying the "theft/loss of funds via signed transaction" criteria.

### Likelihood Explanation
Exploitation only requires an attacker to observe pending inject/withdraw transactions (via mempool or predictable behavior) and submit ordinary, unprivileged `ExchangeTransactionContract` (swap) transactions with higher energy/bandwidth priority or favorable ordering to shift the pool ratio before the target transaction executes, and revert it afterward — the same "sandwich" pattern described in the external report, fully reachable through normal wallet/HTTP transaction broadcast (`/wallet/exchangeinject`, `/wallet/exchangewithdraw`) with no special privileges needed.

### Recommendation
Add an `expected`-style bound to `ExchangeInjectContract` (e.g., `max_another_quant`) and `ExchangeWithdrawContract` (e.g., `min_another_quant`), and enforce it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` analogous to the existing check in `ExchangeTransactionActuator` (`if (anotherTokenQuant < tokenExpected) throw ...`), so callers can bound their slippage exposure the same way swap callers already can.

### Proof of Concept
1. Attacker observes an unconfirmed `ExchangeInjectContract` from victim specifying `token_id = firstTokenID`, `quant = Q`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` of the same `exchange_id` unfavorably before the victim's transaction is packed, per [7](#0-6) .
3. Victim's `ExchangeInjectActuator.execute` then computes `anotherTokenQuant` from the now-skewed ratio in [8](#0-7)  and deducts it from the victim's balance with no cap, per [9](#0-8) .
4. Attacker reverses the swap afterward, restoring the pool ratio and pocketing the difference extracted from the victim's forced overpayment.
