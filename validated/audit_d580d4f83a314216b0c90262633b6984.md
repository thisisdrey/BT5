### Title
StackerDB inventory reply advertises chunk versions before they are durably committed, creating a served-vs-committed mismatch - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
When a peer pushes a `StackerDBPushChunk` message, `PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates the chunk's signature/version/size and then immediately patches the `StackerDBChunkInvData` it is about to send *back to the sender* to claim the new (higher) slot version is now present — before the chunk has actually been written to the local `StackerDBs` sqlite store. The real, authoritative write only happens later, out-of-band, when the buffered `StackerDBPushChunk` is drained from `unhandled_messages`/`pushed_stackerdb_chunks` and run through `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`. This second, independent validation can reject the very same chunk (stale version due to a race, `TooManySlotWrites`, or any other `try_replace_chunk` error), in which case the inventory the node already sent out is now false: it "served" a version it never "committed."

### Finding Description
`handle_unsolicited_StackerDBPushChunk` in [1](#0-0)  builds a `StackerDBChunkInvData` reply from `make_StackerDBChunksInv_or_Nack`, which reflects the *actual current* stored slot versions. It then runs the pushed chunk through `validate_received_chunk` (signature, staleness, size, max-writes checks against the just-fetched versions) at [2](#0-1) , and on success speculatively overwrites the in-memory inventory entry to the new version and sends this patched inventory as the ack to the pushing peer: [3](#0-2) 

At this point **no write to `StackerDBs` has occurred**. The function returns `(false, true)` (do not buffer, do forward to relayer), and the actual chunk is only durably stored later when the relayer thread processes `pushed_stackerdb_chunks`: [4](#0-3) 

That path funnels into `Relayer::process_stacker_db_chunks`, which performs its own independent, authoritative check via `try_replace_chunk`: [5](#0-4) 

`try_replace_chunk` re-checks size, signer, staleness (`slot_version <= slot_validation.version`), and `max_writes` against the database state *at commit time*, which can differ from the state seen a moment earlier by `validate_received_chunk` (e.g., a concurrently-received, higher-versioned chunk for the same slot commits first): [6](#0-5) 

If `try_replace_chunk` fails, the error is only logged and the chunk is silently dropped (`continue;`) — there is no mechanism to retract or correct the inventory reply that was already sent to the pushing peer claiming the new version was accepted.

This breaks the invariant that a `StackerDBChunkInvData` reply must reflect only chunk data that is durably stored: the node serves an inventory saying "I have slot version N" for a version it never actually committed.

### Impact Explanation
StackerDB replication (used by the Nakamoto signer set and other StackerDB-backed protocols) relies on `StackerDBChunkInvData` to determine what needs to be (re)transmitted; see the sync design description at [7](#0-6) . A peer that receives an inventory claiming version N is present will treat that slot as synced and stop retransmitting/rebroadcasting the chunk. If the node's deferred commit for that version silently fails, the node is left holding a stale chunk while having told at least one peer it holds the new one — a served-vs-committed divergence that can stall propagation of that StackerDB slot's data (e.g., signer coordination messages) without any corrective retry, since the sending peer believes the transfer already succeeded. This is a remote, unauthenticated (no node secret or admin role needed) integrity issue in a core replication control-plane message.

### Likelihood Explanation
Any P2P peer that can present a validly-signed chunk for a slot (which requires only the slot signer's signature, not the recipient node's or any admin key — and a chunk observed from the network can be relayed/pushed again) can trigger the speculative inventory patch. The actual failure of the deferred commit only requires a naturally occurring race (e.g., two versions for the same slot arriving close together, which is expected StackerDB traffic) or hitting `max_writes`/other `try_replace_chunk` failure modes, all of which are ordinary conditions rather than requiring privileged capabilities.

### Recommendation
Do not patch/advertise the inventory version in `handle_unsolicited_StackerDBPushChunk` until the chunk has actually been durably committed via `try_replace_chunk`. Either perform the store synchronously before constructing the ack (and only advertise the version that was actually written), or defer sending the `StackerDBChunkInvData` reply until after the relayer's asynchronous commit has confirmed success/failure, and reflect the *authoritative* post-commit version in the sent inventory.

### Proof of Concept
1. Configure a `StackerDBConfig` with a slot owned by key `K` and `max_writes` set to some bound `M`.
2. From a peer connection, push a validly-signed `StackerDBPushChunk` for that slot at version `M+1` (exceeding `max_writes` is one concrete way to guarantee the deferred `try_replace_chunk` call fails while `validate_received_chunk`'s own max-writes check races against the same threshold under concurrent version updates — or simply race two pushes at versions `N` and `N+1` for the same slot from two connections so the second one to reach `try_replace_chunk` sees `StaleChunk` after the first commits).
3. Observe that `handle_unsolicited_StackerDBPushChunk` (lines 794-814 of `stackslib/src/net/stackerdb/mod.rs`) still returns a `StackerDBChunkInvData` ack with `slot_versions[slot_id]` patched to the pushed version, sent back to the peer, before the relayer thread has run `try_replace_chunk`.
4. Confirm via `process_stacker_db_chunks` (`stackslib/src/net/relay.rs` lines 2410-2437) that the deferred commit fails and is only logged/dropped (`continue;`), while the already-sent inventory continues to claim the higher version — no correction message is issued.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
