### Title
Deleting an account with a pending `PromiseYield` receipt permanently burns the attached deposit on timeout resume - (File: `runtime/runtime/src/lib.rs`)

### Finding Description
When a contract calls `promise_yield_create`, the deposit attached to the parked callback is deducted from the creator's balance at receipt-creation time (`deduct_balance` in `runtime/near-vm-runner/src/logic/logic.rs`, `promise_yield_create_with_id`), and the resulting `PromiseYield` receipt (carrying that deposit inside its actions) is stored unconditionally under the receiving account's trie-scoped storage via `set_promise_yield_receipt(state_update, receipt)` at [1](#0-0)  — with no existence/lifetime tie-in to the account that will eventually host it.

If that same account is subsequently deleted (`DeleteAccount`), the account's trie-scoped storage — including the parked `PromiseYield` record — is wiped. When the synthetic timeout `PromiseResume` produced by `resolve_promise_yield_timeouts` is later delivered, the runtime looks the record up via `get_promise_yield_receipt`; because the account's storage was cleared, it returns `None`, and the runtime takes the `else` branch which simply returns `Ok(None)`, dropping the receipt with **no balance movement whatsoever**: [2](#0-1) 

This differs materially from the ordinary `ActionReceipt` delivery path, where delivering a receipt to a non-existent account triggers deposit-refund-on-failure accounting. The `PromiseYield`/`PromiseResume` fast path bypasses that reconciliation: the deposit was already subtracted from the creator when the receipt was minted, and once the carrier account's storage is deleted, there is no remaining reference anywhere in state to that value — it is neither credited back to the creator, delivered to a beneficiary, nor recorded in `other_burnt_amount` / `BalanceStatsV1`. It simply vanishes from the ledger, breaking global value conservation.

### Impact Explanation
This is a token-loss / inflation-invariant violation: NEAR balance is deducted from a real account and never reappears anywhere in the system, silently breaking the protocol's value-conservation invariant that is normally enforced (and checked) via `BalanceStatsV1` bookkeeping. Depending on how conservation-checking code elsewhere treats this discrepancy, this can manifest as either quiet permanent loss of user funds or, if checked strictly, could trip conservation assertions that halt chunk application. This falls into the "token loss" / "value not conserved" bounty category.

### Likelihood Explanation
The preconditions are fully attacker-controlled and require no privileged access: an ordinary account deploys a contract that calls `promise_yield_create` with an attached deposit, and — before any resume/timeout occurs — issues a `DeleteAccount` action against the same account (an account can delete itself, or the owning key can trigger it as part of the same transaction batch or a fast follow-up transaction). Because the yield's timeout window can be arbitrarily longer than the time needed to submit a `DeleteAccount` transaction, an attacker can reliably race the deletion ahead of the timeout resume. This is fully repeatable and costs the attacker only the gas/storage fees for the transactions plus the deposit amount they choose to burn (which they may set arbitrarily low to test, or exploit against a victim scenario where deposits come from third parties, e.g. cross-contract calls carrying deposits from other users).

### Recommendation
Before allowing `DeleteAccount` to succeed, the runtime should check for and refuse deletion (or force-resolve) any outstanding `PromiseYield` receipts registered against the account, mirroring existing protections for other pending obligations. Alternatively, when a timeout `PromiseResume` cannot find its corresponding `PromiseYield` record because the account no longer exists, the runtime should route the originally-deducted deposit into `other_burnt_amount`/refund accounting rather than silently dropping it, so that `BalanceStatsV1` conservation invariants remain intact regardless of the code path taken.

### Proof of Concept
Test-loop / integration test plan:
1. Deploy a contract on account `A` that calls `promise_yield_create` with a non-zero attached deposit `D`, producing a `PromiseYield` receipt stored against `A`.
2. In a subsequent transaction (before any `PromiseResume`/timeout is processed), submit `DeleteAccount` for `A` with beneficiary `B`.
3. Advance the test-loop clock/height until the timeout scheduled by `resolve_promise_yield_timeouts` fires and the synthetic `PromiseResume` (with `data: None`) targeting `A`'s deleted state is delivered.
4. Assert: `get_promise_yield_receipt` returns `None` and the receipt is dropped via the `else` branch at `runtime/runtime/src/lib.rs:1563-1568`.
5. Assert conservation: `total_supply_before == total_supply_after + other_burnt_amount` — expect this to fail, i.e., `D` is missing from both account balances and `BalanceStatsV1`/`other_burnt_amount`, demonstrating the burn.
