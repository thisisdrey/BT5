**Analysis:**

The premise is factually incorrect. `extend_child` in `core/store/src/trie/ops/squash.rs` unconditionally calls `self.ensure_updated(child_id, opts)?` at line 120 *before* reading `memory_usage` via `self.take_node(child_id)` at line 121 [1](#0-0) . This means `child_id` can never remain an unresolved `GenericNodeOrIndex::Old` when its `memory_usage` is read — it is always converted to an `Updated` node first, going through each backend's `ensure_updated` implementation.

For `TrieStorageUpdate`, `ensure_updated` on an `Old` node calls `self.trie.move_node_to_mutable(...)`, which reads the node from storage [2](#0-1) . For `MemTrieUpdate`, `ensure_updated` on an `Old` node calls `self.convert_existing_to_updated(...)`, reading the node from the arena [3](#0-2) . Both paths produce a `memory_usage` value that is part of the node's canonical, hash-committed representation (`RawTrieNodeWithSize` on disk, and the arena-cached value derived from `MemTrieNodeId::new_with_hash_and_memory_usage` for memtrie) [4](#0-3) .

The scenario additionally requires `core/store/src/trie/split.rs` to leave the memtrie and disk-trie in an inconsistent, "partially applied" state for the same logical subtree. However, `find_trie_split`/`TrieDescent` in `split.rs` is a **read-only** analysis used only to *propose* a split boundary account ID; it does not mutate either trie [5](#0-4) . The actual state split (materializing separate shard states) is performed via `retain_multi_range_recursive` in `core/store/src/trie/ops/resharding.rs`, which is applied as a single atomic state transition whose resulting state root (which encodes `memory_usage` per node) must be identical whether computed via memtrie or disk trie — this is a pre-existing, foundational consistency invariant of nearcore's dual-backend trie design, not something specific to `squash.rs`/`extend_child`. If a resharding operation ever produced a differing `memory_usage`/hash between the two backends, that divergence would already manifest as a state-root mismatch at the block that performs the split, well before any subsequent `storage_remove` transaction could touch it.

No code evidence supports memtrie and disk-trie diverging in `memory_usage` for the "same logical node" following a resharding split, and the specific mechanism alleged in the question (an un-updated `Old` child reaching the `saturating_sub` in `extend_child`) does not occur due to the explicit `ensure_updated` call preceding it.
