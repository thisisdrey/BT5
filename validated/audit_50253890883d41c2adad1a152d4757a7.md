## Finding

### Title
Permanent Freezing of User Funds via Canonical-Address Account Conversion on TIP-2935 Activation - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` converts whatever `AccountCapsule` already sits at the hardcoded address `HISTORY_STORAGE_ADDRESS` into a system contract account in place, preserving its balance/asset state but stripping key resource bookkeeping and permanently removing the possibility of the original controller ever spending from it again, because the address has no private key (it is a well-known constant, not derived from any signature).

### Finding Description
The address `HISTORY_STORAGE_ADDRESS` is a fixed, publicly known 21-byte constant [1](#0-0) . Any unprivileged transaction broadcaster can send ordinary `TransferContract`/`TransferAssetContract` transactions to this address at any time before the TIP‑2935 proposal is activated, which will silently create a normal `AccountCapsule` holding TRX/TRC10 balance there — the code's own comment acknowledges this is "the common case" [2](#0-1) .

When the committee later activates the proposal, `deploy()` is invoked from `ProposalService` during maintenance-time block processing [3](#0-2) . It only checks `codeStore`/`contractStore` for a collision, not whether a normal EOA already lives at the address, then mutates the existing account in place instead of rejecting: `account.updateAccountType(Protocol.AccountType.Contract); account.clearDelegatedResource();` followed by a `put` back into `AccountStore` [4](#0-3) . From this point the account is permanently typed `Contract`, its `originAddress` is fixed to a different, un-controlled address, and the only code ever installed at it is the fixed 83-byte `HISTORY_STORAGE_CODE`, which implements nothing but a `SLOAD`/read path for the EIP-2935 history slots (no transfer, withdraw, or `SELFDESTRUCT`/beneficiary opcode) [5](#0-4) . Since nobody holds the private key for this address, and the deployed bytecode has no mechanism to move value out, any TRX/TRC10 balance, votes, or frozen-for-self resources that existed on the account prior to conversion become permanently unreachable by their original owner. This is confirmed by the test suite itself, which explicitly exercises the "pre-existing normal account, balance preserved" branch and demonstrates the balance stays on the now-contract-typed account with no recovery path [6](#0-5) .

### Impact Explanation
Any TRX or TRC10 balance an ordinary user sends to this fixed, publicly documented address before the TIP-2935 proposal is activated becomes permanently frozen once activation occurs, since the account is forcibly converted to a code-less-recoverable contract type with a fixed non-owner `originAddress` and no key. This is a concrete "permanent freezing of funds" outcome triggered by state that any unprivileged broadcaster can create ahead of time, combined with a routine, unavoidable committee action (proposal activation) that they cannot control or opt out of. It also silently wipes `AcquiredDelegatedFrozenBalanceForEnergy/Bandwidth` bookkeeping via `clearDelegatedResource()`, creating a mismatch with any third-party accounts that had delegated frozen resources to this address, leaving their own frozen balance similarly unredeemable.

### Likelihood Explanation
Reaching the vulnerable state requires only a single ordinary transfer transaction to a known, hardcoded address — no special privileges, signatures, or contract interactions are needed. The conversion itself is triggered by a one-time, deterministic, and eventually-inevitable protocol event (TIP-2935 activation), which is outside any individual user's control. The main limiting factor is that a victim must have sent funds to this specific address before activation, but because the address is a publicly documented constant (mirrored from Ethereum's canonical EIP-2935 address), it is straightforward to target intentionally or trigger accidentally via wallets/tools that reuse the well-known constant.

### Recommendation
In `deploy()`, treat a pre-existing account of type `Normal` with non-zero balance/assets/votes/frozen resources at `HISTORY_STORAGE_ADDRESS` the same way foreign code/contract state is treated: skip the deploy (log and leave the account untouched, deferring TIP-2935 functionality at that address) rather than silently converting it. If preserving funds recoverability is required, add an explicit sweep/refund path for the pre-existing balance/assets before flipping the account type, and make sure delegated-resource accounting on both sides of any delegation is reconciled rather than only cleared on the target side.

### Proof of Concept
1. Before the TIP-2935 proposal is activated, broadcast an ordinary `TransferContract` sending TRX (or a TRC10 asset) from an arbitrary account to `HISTORY_STORAGE_ADDRESS = 410000f90827f1c53a10cb7a02335b175320002935` (hex).
2. This creates a `Normal` `AccountCapsule` at that address holding the transferred balance, as confirmed by `HistoryBlockHashIntegrationTest.deployUpgradesPreExistingNormalAccountPreservingBalance` [7](#0-6) .
3. When the committee activates TIP-2935, `HistoryBlockHashUtil.deploy()` runs, converting the account's type to `Contract`, installing the fixed read-only bytecode, and setting `originAddress` to `HISTORY_DEPLOYER_ADDRESS` — a value the original sender never controlled [4](#0-3) .
4. The balance remains on-chain but is now permanently unreachable: there is no private key for the address and the installed bytecode exposes no transfer/withdraw functionality.

  public void deployUpgradesPreExistingNormalAccountPreservingBalance() {
    byte[] addr = HistoryBlockHashUtil.HISTORY_STORAGE_ADDRESS;
    long balance = 12345L;
    AccountCapsule eoa = new AccountCapsule(
        ByteString.copyFrom(addr), Protocol.AccountType.Normal);

    chainBaseManager.getAccountStore().put(addr, eoa);

    HistoryBlockHashUtil.deploy(dbManager);

    AccountCapsule after = chainBaseManager.getAccountStore().get(addr);
    assertEquals(Protocol.AccountType.Contract, after.getType());
    assertEquals(balance, after.getBalance());
    assertTrue(chainBaseManager.getCodeStore().has(addr));

  }
