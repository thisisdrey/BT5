Audit Report

## Title
Outbound delivery receipt pays relayer rewards for failed Ethereum executions - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
The Snowbridge outbound-queue-v2 pallet decodes the Ethereum `InboundMessageDispatched` event's `success` boolean into `DeliveryReceipt.success`, but `process_delivery_receipt` never reads it. A valid delivery proof for a message that reverted on Ethereum is settled exactly like a successful one: the relayer reward is registered, the `PendingOrder` is removed, and `MessageDelivered` is emitted.

## Finding Description
`DeliveryReceipt::try_from` decodes the `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` event log and populates `success` directly from the event field. [1](#0-0)  This field explicitly distinguishes a successful Ethereum-side dispatch from a reverted one, per the Solidity event signature. [2](#0-1) 

In `process_delivery_receipt`, the pallet verifies `receipt.gateway`, resolves `reward_account`, loads the `PendingOrder` by `nonce`, and — if `order.fee > 0` — calls `T::RewardPayment::register_reward` and unconditionally removes the order from `PendingOrders`, all without ever inspecting `receipt.success`. [3](#0-2)  A repository-wide search confirms `success` is referenced nowhere outside of the struct definition itself, so no other guard filters this case.

The pallet's own module documentation states that `submit_delivery_receipt` is meant to run "when the message has been verified and executed," implying successful execution should be a precondition for reward payout and order removal. [4](#0-3)  The implementation only enforces "verified" (via `T::Verifier::verify` and the `gateway` equality check inside `submit_delivery_receipt`/`process_delivery_receipt`) but not "executed successfully." [5](#0-4) 

## Impact Explanation
Because `receipt.success` is ignored, any relayer submitting a valid receipt proof for a message that reverted on Ethereum is paid the full fee attached to the corresponding `PendingOrder`, via `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`. [6](#0-5)  Simultaneously, `<PendingOrders<T>>::remove(nonce)` permanently deletes the order, so the sender has no path to retry or reclaim the fee for the failed message. [7](#0-6)  This is an unauthorized/duplicate settlement corrupting the `PendingOrders` payout state and the `reward_account` beneficiary correctness — matching the "theft or unbacked mint/unlock" and "duplicate settlement or payout" impact categories.

## Likelihood Explanation
`submit_delivery_receipt` is a public, signed extrinsic reachable by any relayer. [5](#0-4)  Any transaction on the Ethereum Gateway that reverts during dispatch still emits `InboundMessageDispatched` with `success=false`; a proof of that event's inclusion in a valid Ethereum receipt passes `T::Verifier::verify` identically to a successful case. The attacker only needs to submit that valid proof with `reward_address` set to a controlled account — no privileged or off-chain-compromise assumption is required.

## Recommendation
In `process_delivery_receipt`, require `receipt.success == true` before calling `register_reward` and removing the `PendingOrder`. For `success == false`, either leave the `PendingOrder` in place for retry, or route to a distinct failure/refund path, and emit a separate event (not `MessageDelivered`) to reflect the failed execution outcome.

## Proof of Concept
1. A user's outbound message is queued via `do_process_message`, creating `PendingOrder { nonce: N, fee: F, .. }` in storage. [8](#0-7) 
2. On Ethereum, the corresponding call reverts; the Gateway contract emits `InboundMessageDispatched(nonce=N, topic=T, success=false, reward_address=attacker)`.
3. The attacker submits a valid beacon/receipt proof of that event to `submit_delivery_receipt`; `T::Verifier::verify` accepts it since the event genuinely exists in a valid Ethereum receipt, and `DeliveryReceipt::try_from` decodes `success=false` faithfully. [9](#0-8) 
4. `process_delivery_receipt` checks only `gateway` equality, loads `PendingOrders[N]`, and — since `order.fee = F > 0` — calls `register_reward(&attacker, .., F)`, then removes `PendingOrders[N]`. [10](#0-9) 
5. The attacker successfully claims fee `F` for a message that never executed successfully on Ethereum, and the original sender permanently loses the fee with no retry path since the order no longer exists.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
