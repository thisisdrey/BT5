### Title
Missing bounds check on attacker-controlled offset in `extractBytes32Array` causes uncaught `ArrayIndexOutOfBoundsException` in precompiled contract execution - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array(DataWord[] words, int offset)` reads `words[offset]` directly to obtain an attacker-controlled length, then loops `words[offset + i + 1]` without ever checking that `offset` (or `offset + len`) stays within the bounds of the `words` array [2](#0-1) . This is inconsistent with the sibling helpers `extractBytesArray` and `extractSigArray` in the same class, both of which explicitly guard with `if (offset > words.length - 1) { return new byte[0][]; }` before indexing [3](#0-2) . `extractBytes` itself uses `Arrays.copyOfRange(data, offset, offset + len)`, which throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` when `offset` or `len` values derived from attacker-controlled call data are out of range [4](#0-3) .

### Finding Description
Precompiled contracts in `PrecompiledContracts.java` are invoked with raw `data` supplied by the caller of a TVM `CALL`/`STATICCALL` to a reserved precompile address — this data is fully attacker-controlled from any contract deployer or transaction sender that triggers a call into these addresses. Several precompile implementations parse this `data` into `DataWord[] words` and then use helper functions (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) to pull out variable-length sub-arrays whose length is itself read from the data (`words[offset].intValueSafe()`). Two of the three helpers validate that `offset` is within `words.length` before indexing; `extractBytes32Array` does not, meaning a crafted `offset` value (e.g., pointing past the end of the decoded words array) causes an uncontrolled `ArrayIndexOutOfBoundsException` while reading `words[offset]`. This mirrors the ImageMagick `ReadPSDChannelPixels` root cause: a length/offset value taken from untrusted input is used to index a buffer without validating it fits within the buffer, resulting in an out-of-bounds access.

### Impact Explanation
An uncaught runtime exception thrown deep inside TVM precompiled-contract execution, if not properly wrapped by the VM's exception-handling layer around `execute()`, can propagate as an unexpected/unhandled `Error`/`RuntimeException` rather than the VM's normal `Program.Exception` control flow, risking transaction processing failure or node instability for any node executing that transaction (including during block replay by all full nodes, since TVM execution is deterministic and replayed by every validating node). Because this executes during block application/transaction execution, an inconsistency in how the exception is handled between different node versions, or a case where it escapes intended `try/catch` guarding, could also cause block-application divergence.

### Likelihood Explanation
The precompiled contract addresses are directly callable by any contract via `CALL`, so the code path is reachable from an ordinary unprivileged transaction (any contract deployer or externally-owned account that triggers a call to the relevant precompile). No special privilege is required — only a well-formed transaction invoking the precompiled contract with crafted `data`.

### Recommendation
Add the same `offset > words.length - 1` (and computed length) bounds validation used in `extractBytesArray`/`extractSigArray` to `extractBytes32Array`, returning an empty array (or failing the precompile call gracefully via `Pair.of(false, ...)`) instead of allowing an unchecked array index. Audit all callers of `extractBytes32Array` to confirm they already handle a graceful-failure return rather than assuming success.

### Proof of Concept
Conceptually: construct a transaction that calls a precompiled contract whose `execute(byte[] data)` path invokes `extractBytes32Array(words, offset)` with a `data` payload where the encoded `offset` word value exceeds `words.length`. This causes `words[offset]` to throw `ArrayIndexOutOfBoundsException` when the array is accessed, matching the out-of-bounds read pattern from CVE-2016-7514.

**Caveat:** I was not able to fully confirm, within the available tool budget, which specific precompiled contract(s) call `extractBytes32Array` and whether the top-level TVM dispatcher wraps `execute()` calls in a catch-all that neutralizes the impact to a benign revert (in which case this would reduce to a low-severity/no-impact issue rather than a crash). This should be verified directly in `actuator/src/main/java/org/tron/core/vm/program/Program.java` (where precompiled contracts are invoked) before treating this as confirmed Medium/High severity — I'd recommend starting a full Devin session with repository access to trace this call path exhaustively if a definitive validation is required.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,

    }
    return bytesArray;
  }
