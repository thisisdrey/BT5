### Title
Unauthenticated replay of a captured stage-1 handshake packet can redirect an established peer's remote address via `SetRemoteIfPreferred` - ([File: handshake_manager.go])

### Summary
`HandshakeManager.beginHandshake` performs Noise/cert verification through `machine.ProcessPacket` before calling `CheckAndComplete`, but that verification only proves the packet was signed/derived correctly at some point in the past — it proves nothing about freshness or the sender's current network location. When `CheckAndComplete` detects the packet as a duplicate of an already-completed handshake (`ErrAlreadySeen`), `handleCheckAndCompleteError` calls `existing.SetRemoteIfPreferred(f.hostMap, via)` using the attacker-controlled/spoofed `via.UdpAddr`, which can move an authenticated peer's tracked remote address to the attacker's spoofed source without any proof of liveness from that address.

### Finding Description
In `beginHandshake` (`handshake_manager.go:701-810`), an inbound stage-1 packet is fed to `machine.ProcessPacket`, which validates the Noise DH math and certificate signature [1](#0-0) . This cryptographic check is deterministic on the packet bytes and the recipient's static key — it does not bind the packet to the UDP source address it arrives from, nor does it enforce freshness beyond what the underlying Noise pattern provides. Once cert validation succeeds, `hm.CheckAndComplete(hostinfo, handshakePacketStage0, f)` is called [2](#0-1) ; when the same stage-1 bytes have already produced a completed `HostInfo` for that peer, it returns `ErrAlreadySeen`, which is specifically documented as the case where "the peer's stage-1 retransmit landed" [3](#0-2) .

In `handleCheckAndCompleteError`, the `ErrAlreadySeen` branch calls `existing.SetRemoteIfPreferred(f.hostMap, via)` directly using the `via` of the just-received (replayed) packet: [4](#0-3) . `SetRemoteIfPreferred` (`hostmap.go:785-823`) will switch the `HostInfo`'s tracked remote to `via.UdpAddr` as soon as that address falls in a preferred range and the current remote does not [5](#0-4) . There is no requirement that a legitimately-keyed response ever be received back from the new address before the switch takes effect — `SetRemote` is called synchronously inside `SetRemoteIfPreferred` itself. The only feedback is a `Test`/`TestRequest` packet sent afterward [6](#0-5) , which is advisory and does not gate or roll back the address change.

Because the stage-1 packet bytes are exactly what an on-path (or previously-observed) attacker can capture and replay verbatim from a spoofed source, and because `machine.ProcessPacket`'s cryptographic verification succeeds identically regardless of the packet's actual sender, this path allows an attacker who never possesses any private key material to cause an established peer's remote address to be updated toward an address of the attacker's choosing (subject to it being in the local preferred-range configuration and not already the current remote).

### Impact Explanation
This is a remote state poisoning of hostmap/routing state: an authenticated tunnel's outbound remote address can be redirected to an attacker-chosen (spoofed) address without the attacker proving key possession or reachability. Consequences include misrouting/blackholing of subsequent data-plane traffic intended for the real peer (availability impact on that tunnel), and if the attacker is genuinely reachable/observable at the spoofed address (e.g., on shared/adjacent network segments), possible traffic redirection toward an attacker-influenced path. This matches Nebula's bounty category for remote state poisoning / traffic misrouting.

### Likelihood Explanation
Preconditions: attacker must capture one legitimate stage-1 handshake packet between two peers (passive capture, no decryption needed) and be able to send spoofed-source UDP packets that reach the target's listener with an address that falls within the target's configured `lighthouse.preferred_ranges`. Both preconditions are plausible on shared L2 segments, misconfigured networks, or where preferred ranges are broad (e.g., private RFC1918 ranges commonly used as preferred ranges). No CA/config/social-engineering assumptions are needed, consistent with the attacker model. The technique is trivially repeatable — same captured bytes can be replayed at will as long as the target's hostmap entry remains in the `ErrAlreadySeen`-eligible state.

### Recommendation
Do not trust `via` from a bare `ErrAlreadySeen`/retransmit detection to update `HostInfo.remote`. Require independent proof of liveness at the new address (e.g., only roam after receiving a valid post-handshake encrypted data-plane or `Test` *response* authenticated with the session's derived keys from that address, not merely a retransmitted/replayed handshake initiation). Alternatively, bind stage-1 packet acceptance/dedup to some freshness token (timestamp/nonce with a replay window) so identical captured bytes cannot be reprocessed successfully from a different source after the original exchange completed.

### Proof of Concept
Integration test plan (extending `e2e/handshake_manager_test.go`):
1. Establish two nebula nodes (A, B) with `lighthouse.preferred_ranges` covering a test subnet, complete a real handshake so `A` has a `HostInfo` for `B` with `remote = B_real_addr` (not in preferred range).
2. Capture the exact stage-1 packet bytes B→A used for that handshake.
3. From a third "attacker" UDP endpoint whose source address is spoofed/set to `attacker_addr` inside the preferred range, replay the captured stage-1 bytes to A.
4. Assert that `machine.ProcessPacket` succeeds (cert validation passes) and `CheckAndComplete` returns `ErrAlreadySeen`.
5. Assert (bug reproduction) that `A`'s `HostInfo.GetRemote()` for B changes to `attacker_addr` even though no packet cryptographically bound to that address (i.e., no packet decryptable only by B, sent to/received from `attacker_addr`) was ever produced.
6. Assert that subsequent data-plane packets from A intended for B are sent to `attacker_addr` instead of `B_real_addr`, demonstrating traffic misroute prior to any cryptographic confirmation of B's presence at that address.

// SetRemoteIfPreferred returns true if the remote was changed. The lastRoam
// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}
