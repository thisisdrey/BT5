## Analog Found

### Title
Unbounded Merkle-tree depth parameter passed from untrusted contract calldata into native `librustzcash` code - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `MerkleHash` precompiled contract accepts a `level`/depth value parsed directly from attacker-controlled TVM calldata and forwards it, unvalidated, into the native `librustzcashMerkleHash` JNI call. Unlike sibling precompiles (`VerifyMintProof`) that explicitly bound-check similar tree-position values (`leafCount >= TREE_WIDTH`), `MerkleHash` performs no range check on `level` before it crosses the JNI boundary into native (non-memory-safe) code — the same bug class as the OpenJPEG CVE, where insufficiently validated header/length data is used to index/write memory in native code.

### Finding Description
`MerkleHash.execute()` reads the depth/level value straight from the raw precompile input and passes it into the native call without validation: [1](#0-0) 

```
int level = parseInt(data);
System.arraycopy(data, 32, left, 0, 32);
System.arraycopy(data, 64, right, 0, 32);
JLibrustzcash.librustzcashMerkleHash(
    new LibrustzcashParam.MerkleHashParams(level, left, right, hash));
...
private int parseInt(byte[] data) {
  byte[] bytes = parseBytes(data, 0, 32);
  return new DataWord(bytes).intValueSafe();
}
```

`intValueSafe()` returns any value up to `Integer.MAX_VALUE` for attacker-supplied calldata — there is no upper bound corresponding to the actual Sapling Merkle tree depth (32) enforced in Java before the value reaches the native library: [2](#0-1) 

By contrast, the sibling `VerifyMintProof` precompile explicitly validates a similar bounded index before use: [3](#0-2) 

```
long leafCount = parseLong(data, 1472);
if (leafCount >= TREE_WIDTH) {
  return Pair.of(true, DataWord.ZERO().getData());
}
```

`MerkleHash` has no equivalent guard on `level` even though the Merkle tree depth is bounded (`IncrementalMerkleTreeContainer` in `chainbase/src/main/java/org/tron/common/zksnark/IncrementalMerkleTreeContainer.java` enforces a fixed tree depth for legitimate usage). If the native Rust `librustzcash_merkle_hash` implementation uses `level` to select/index a fixed-size table of "uncommitted" constants or similar per-depth buffers without its own bounds check (consistent with the general class of C/Rust FFI code that trusts caller-supplied indices), an out-of-range `level` can cause an out-of-bounds read/write across the JNI boundary — analogous to `opj_jp2_read_header` writing out of bounds when the caller-supplied/parsed size is not validated against the actual buffer.

Because Java's own array bounds checks do not extend across JNI calls into native code, this is one of the few places in java-tron where a bug class like the OpenJPEG OOB heap write is structurally reachable: attacker-supplied numeric input flows from TVM calldata directly into native memory-unsafe code.

### Impact Explanation
The `MerkleHash` precompile is reachable by any account that can send a transaction invoking a TVM `STATICCALL`/`CALL` to the precompile address — i.e., any unprivileged contract deployer or caller, satisfying the reachability requirement (no privileged role needed). If the native side indexes memory using the unvalidated `level`, the impact ranges from a native-code out-of-bounds read/write in the `FullNode`/`SolidityNode` process (crash / denial of node availability) to potential memory corruption depending on how the underlying `librustzcash` binary implements the uncommitted-value/hash table lookup for depth. This maps to the "node crash or halt" / potential "RCE" impact categories accepted by the scan rules.

### Likelihood Explanation
Likelihood is moderate: exploitability depends entirely on the internal implementation of the native `librustzcash_merkle_hash` function (not visible in this Java repository), specifically whether it indexes a depth-bounded array/table with the supplied `level` without its own bounds check. The presence of an explicit bound check for the analogous `leafCount`/`TREE_WIDTH` parameter in a sibling precompile (`VerifyMintProof`) but its conspicuous absence for `level` in `MerkleHash` strongly suggests this is a missed validation rather than an intentionally safe design, which is the direct code-level pattern matching the CVE's "stream too short / image not initialized" root cause (missing validation of a structural parameter before it is consumed by lower-level, unsafe code).

### Recommendation
Add explicit bounds validation for `level` in `MerkleHash.execute()` before invoking `JLibrustzcash.librustzcashMerkleHash`, mirroring the `leafCount >= TREE_WIDTH` check used in `VerifyMintProof`:
- Reject requests where `level < 0` or `level >= <max Sapling tree depth (32)>` and return the standard failure result (`Pair.of(false, EMPTY_BYTE_ARRAY)`), matching the pattern already used elsewhere in `PrecompiledContracts.java`.
- Additionally, review all other `JLibrustzcash`/`JLibsodium` JNI entry points that receive attacker-influenced integer parameters (not just fixed-length byte-array parameters, which are already validated via `LibrustzcashParam.valid32Params`/`validParamLength`) to ensure equivalent bounds checks exist before crossing into native code.

### Proof of Concept
1. Craft a smart contract (or raw transaction) that performs a `STATICCALL` to the `MerkleHash` precompiled contract address with input data:
   - Bytes `[0:32)`: a large/negative 32-byte big-endian integer for `level` (e.g., `0xFFFFFFFF` truncated via `intValueSafe`, or any value far outside `[0, 32)`).
   - Bytes `[32:64)` and `[64:96)`: arbitrary 32-byte `left`/`right` values.
2. Broadcast the transaction; the TVM executes the precompile via `PrecompiledContracts.MerkleHash.execute(data)`.
3. `level` is parsed via `parseInt(data)` with no range check and passed into `JLibrustzcash.librustzcashMerkleHash`, which calls into the native `librustzcash_merkle_hash` implementation with the out-of-range depth.
4. Observe node behavior (crash, memory-safety violation, or corrupted hash output) as evidence of the native code’s handling of the unchecked index.

Note: Because the native `librustzcash` implementation itself is not part of this Java codebase, the concrete exploitability (crash vs. silent corruption vs. no-op) could not be fully verified from source available here; a live/native-code test against the actual bundled `librustzcash` binary would be needed to confirm impact severity.

    @Override
    public Pair<Boolean, byte[]> execute(byte[] data) {
      byte[] left = new byte[32];
      byte[] right = new byte[32];
      byte[] hash = new byte[32];
      boolean res = true;
      try {
        int level = parseInt(data);
        System.arraycopy(data, 32, left, 0, 32);
        System.arraycopy(data, 64, right, 0, 32);
        JLibrustzcash.librustzcashMerkleHash(
            new LibrustzcashParam.MerkleHashParams(level, left, right, hash));
      } catch (Throwable any) {
        res = false;
        logger.info("Compute MerkleHash failed:{}", any.getMessage());
      }
      if (res) {
        return Pair.of(true, hash);
      } else {
        return Pair.of(false, EMPTY_BYTE_ARRAY);
      }
    }
