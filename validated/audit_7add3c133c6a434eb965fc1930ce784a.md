## Finding

Based on my research, the closest reachable analog to the referenced Vault issue exists in java-tron's `ExchangeInjectActuator` and `ExchangeTransactionActuator`. Both actuators update the exchange pool's reserve balances (`firstTokenBalance`/`secondTokenBalance`, the AMM-equivalent of the Vault's `totalShares`) unconditionally, while the corresponding debit from the user's asset balance is performed through `AccountCapsule.reduceAssetAmountV2()` **without checking its boolean return value**. Every other actuator in the codebase that calls this method (`TransferAssetActuator`, `ParticipateAssetIssueActuator`, `Commons.adjustAssetBalanceV2`) explicitly checks the return value and throws `ContractExeException` on failure — showing this omission is a deviation from the established pattern, not an intentional design.

### Title
Unchecked `reduceAssetAmountV2()` return value in Exchange actuators can desynchronize pool reserves from actual account balances - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeInjectActuator.execute()` and `ExchangeTransactionActuator.execute()` update the `ExchangeCapsule`'s token reserve balances (used by `ExchangeProcessor`/`SafeExchangeProcessor` as the shared pricing pool, analogous to a Vault's `totalShares`) and then call `AccountCapsule.reduceAssetAmountV2()` to debit the trader's TRC10 asset balance — but the boolean success/failure return of `reduceAssetAmountV2()` is discarded.

### Finding Description
`reduceAssetAmountV2()` returns `false` (silently, without throwing) whenever the requested reduction cannot be satisfied against the account's current asset map: [1](#0-0) 

In `TransferAssetActuator` this return value is checked and the actuator aborts with `ContractExeException("reduceAssetAmount failed !")` if it fails: [2](#0-1) 

`ParticipateAssetIssueActuator` and the shared helper `Commons.adjustAssetBalanceV2` do the same: [3](#0-2) [4](#0-3) 

But in `ExchangeInjectActuator.execute()`, the pool reserve is updated via `exchangeCapsule.setBalance(...)` **before** the debit, and both `reduceAssetAmountV2()` calls that follow ignore their return value: [5](#0-4) 

The same unchecked pattern exists in `ExchangeTransactionActuator.execute()`, where `exchangeCapsule.transaction(...)` mutates the pool's first/second token balances up front, and the trader-side debit via `reduceAssetAmountV2()` is likewise unchecked: [6](#0-5) 

If `reduceAssetAmountV2()` returns `false` at execute time (for instance, because the trader's balance for that asset was consumed in the interim — the actuator's `execute()` runs against whatever `AccountStore` state exists when the block is applied, not necessarily identical to the state seen during `validate()`), the exchange pool reserves (`firstTokenBalance`/`secondTokenBalance`) are still persisted via `Commons.putExchangeCapsule(...)` as if the deposit/trade succeeded, while the trader's TRC10 balance is left untouched. The pool's reserve accounting becomes unbacked — mirroring exactly the reported pattern where `totalShares()` was incremented without validating that the corresponding asset was actually received.

### Impact Explanation
The exchange pool balances (`firstTokenBalance`/`secondTokenBalance`) are the sole inputs to `ExchangeProcessor.exchange()`/`SafeExchangeProcessor.exchange()`, which determine the exchange rate for every subsequent `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` call against that exchange pair: [7](#0-6) 

An unbacked increase to pool reserves inflates the pool's stated liquidity relative to what is actually escrowed, corrupting the price/exchange-amount calculation for all future traders interacting with that pool — the same class of impact described in the report ("break the calculation for all account balances"), but here breaking the calculation for all future trades against the affected exchange pair, and creating a permanent accounting mismatch between recorded reserves and real asset holdings.

### Likelihood Explanation
This requires `reduceAssetAmountV2()` to return `false` at `execute()` time despite `doValidate()` having passed for the same transaction. Since `validate()` and `execute()` are invoked sequentially against the account state at block-application time in java-tron's actuator pipeline, under normal single-actuator-per-transaction processing this window is narrow. However, the missing check is a structural defect (not enforced by any surrounding invariant) that is inconsistent with the pattern used everywhere else `reduceAssetAmountV2` is called, making it a latent correctness/accounting bug rather than a hardened defense — any future change to actuator ordering, batching, or the exchange contract's calling flow that widens this window would allow it to be triggered by an ordinary unprivileged `ExchangeInjectContract`/`ExchangeTransactionContract` broadcaster.

### Recommendation
Check the boolean result of every `reduceAssetAmountV2()` (and `addAssetAmountV2()`) call inside `ExchangeInjectActuator.execute()` and `ExchangeTransactionActuator.execute()`, and throw `ContractExeException` (aborting the state changes to `exchangeCapsule`) if the debit fails, matching the pattern already used in `TransferAssetActuator` and `ParticipateAssetIssueActuator`.

### Proof of Concept
1. Craft an `ExchangeInjectContract`/`ExchangeTransactionContract` that passes `doValidate()`'s asset-sufficiency checks based on the account state visible at validation time.
2. Cause the account's relevant TRC10 asset balance to be reduced by another action before this transaction's `execute()` runs (e.g., another transaction from the same signer processed earlier in the same block, spending the same asset), so that at `execute()` time `reduceAssetAmountV2()` returns `false`.
3. Because the return value is discarded, `execute()` still calls `exchangeCapsule.setBalance(...)` / `exchangeCapsule.transaction(...)` and persists the updated (inflated) pool reserves via `Commons.putExchangeCapsule(...)`, while the trader's asset balance is left unchanged — producing pool reserves not backed by actual escrowed tokens.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
