### Title
Unbounded attachment size accepted via P2P download path bypasses `attachments_max_size` gate - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsDownloader::run` calls `AtlasDB::insert_instantiated_attachment` directly on every attachment resolved from a peer's `GetAttachmentResponse`, without ever invoking `AtlasDB::should_keep_attachment`'s size check against `AtlasConfig.attachments_max_size`. This lets any peer serving attachment data in response to a pending `AttachmentRequest` store attachments of unbounded size in the `attachments` table, unlike the `POST`-inbox ingestion path which does enforce the size cap.

### Finding Description
The intended invariant is that all attachment content written to the `attachments` table satisfies `content.len() <= atlas_config.attachments_max_size`, enforced via `AtlasDB::should_keep_attachment` (`stackslib/src/net/atlas/db.rs`), which is invoked on the POST-attachment inbox ingestion path (referenced in `stackslib/src/net/api/posttransaction.rs`).

However, the gossip/download path does not go through this gate. In `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs`, lines 149-169), once the `AttachmentsBatchStateMachine` reaches `Done`, the code drains `context.attachments` and calls: [1](#0-0) 
```rust
AttachmentsBatchStateMachine::Done(ref mut context) => {
    for attachment in context.attachments.drain() {
        let attachments_instances = network
            .atlasdb
            .find_all_attachment_instances(&attachment.hash())
            .map_err(net_error::DBError)?;
        network
            .atlasdb
            .insert_instantiated_attachment(&attachment)
            .map_err(net_error::DBError)?;
```
`insert_instantiated_attachment` is called unconditionally — there is no call to `should_keep_attachment` or any inline length check against `attachments_max_size` anywhere in `download.rs`; a repo-wide search for `should_keep_attachment` shows it is only referenced in `db.rs`, `posttransaction.rs`, and `tests.rs`, never in `download.rs`.

The attacker flow: be selected as (or become) the peer serving a `GetAttachmentsInv`/`AttachmentRequest` batch for a pending `AttachmentInstance`, respond with a `GetAttachmentResponse` whose `attachment.content` is arbitrarily large. The response content is added into `context.attachments` (a `HashSet`) via the batch state machine with no size validation at any earlier stage (the `check_attachment_instances` routine similarly only checks hash-based lookups, not length), and is then persisted unconditionally by `insert_instantiated_attachment`.

### Impact Explanation
A remote peer selected as an attachment-batch data source can force the victim node to write attachments of unbounded size to its `attachments` table each time it downloads an attachment, bypassing the `attachments_max_size` cap that is otherwise enforced on the POST-inbox path. This is a storage-exhaustion vector against a Stacks node's chainstate database driven purely by remote data the node did not choose to trust for size, matching the "attachment/BNS mismatch"-adjacent category of unauthenticated/uncontrolled writes to persistent state via the gossip/download path.

### Likelihood Explanation
Preconditions are modest: the attacker must be an outbound sync peer offering attachment data (`network.get_outbound_sync_peers()` / `get_data_url`) that the victim selects for a pending `AttachmentInstance`/`AttachmentRequest` — this requires no privileged role, RPC secret, or StackerDB slot ownership, only running an ordinary P2P peer that responds to attachment requests. Each malicious response yields one oversized write; the attacker can repeat this per pending attachment instance, and can also spin up bogus attachment instances via unconfirmed instance data to keep triggering downloads.

### Recommendation
In `AttachmentsDownloader::run`, before calling `network.atlasdb.insert_instantiated_attachment(&attachment)`, invoke the same size check used by `AtlasDB::should_keep_attachment` (or call `should_keep_attachment` directly) and discard/reject attachments whose `content.len()` exceeds `atlas_config.attachments_max_size`, mirroring the enforcement already present on the POST-inbox path.

### Proof of Concept
1. Construct an `AtlasDB` with `AtlasConfig.attachments_max_size` set to a small value (e.g., 16 bytes).
2. Build an `AttachmentsBatchStateContext`/`AttachmentsBatchStateMachine` (or directly call the code path exercised by `AttachmentsDownloader::run`) simulating a `Done` state whose `context.attachments` set contains an `Attachment` with `content` larger than 16 bytes.
3. Call `AttachmentsDownloader::run` (or directly exercise the `Done` branch logic) and observe that `network.atlasdb.insert_instantiated_attachment(&attachment)` succeeds without any size-based rejection.
4. Assert via `AtlasDB::find_attachment(&attachment.hash())` that the oversized attachment was persisted, and additionally assert `AtlasDB::should_keep_attachment` would have returned `false`/rejected for the same content, demonstrating the gate is bypassed on this path.
