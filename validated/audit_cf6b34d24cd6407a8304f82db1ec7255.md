Audit Report

## Title
Outbound-queue-v2 `process_delivery_receipt` ignores the `success` flag of the delivery receipt, paying relayer rewards and irreversibly clearing `PendingOrders` for failed deliveries - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`snowbridge_outbound_queue_primitives::v2::DeliveryReceipt` decodes the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event and explicitly carries a `success: bool` field indicating whether the message dispatch on Ethereum succeeded. [2](#0-1)  However, `Pallet::process_delivery_receipt` never reads or checks `receipt.success` before paying the reward and removing the `PendingOrders` entry. [1](#0-0) 

## Finding Description
The extrinsic `submit_delivery_receipt` verifies the receipt proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and unconditionally calls `process_delivery_receipt`. [3](#0-2) 

Inside `process_delivery_receipt`, the only checks performed are: (1) `receipt.gateway == T::GatewayAddress::get()`, and (2) a `PendingOrder` exists for `receipt.nonce`. If both hold, `T::RewardPayment::register_reward` is called with `order.fee` and `<PendingOrders<T>>::remove(nonce)` executes unconditionally — regardless of `receipt.success`. [4](#0-3)  The `success` field decoded from the on-chain Ethereum event is never referenced anywhere in this function or elsewhere in the pallet.

This breaks the invariant that message-queue/payout state should only advance after execution success is confirmed: the pallet pays out and permanently deletes the pending order regardless of whether the underlying Ethereum-side message dispatch actually succeeded. Because `PendingOrders::<T>::remove(nonce)` runs unconditionally once the order is found, once any receipt (successful or failed) for a given nonce is processed, `InvalidPendingNonce` is returned on any subsequent attempt, so there is no retry or reconciliation path.

## Impact Explanation
An honest, unprivileged relayer submitting a genuine, correctly-proven `InboundMessageDispatched` event with `success = false` (i.e., dispatch on Ethereum genuinely failed) still receives the full `order.fee` reward via `T::RewardPayment::register_reward`, identical to the successful case — an incorrect/unbacked payout not corresponding to completed work. The corresponding `PendingOrders` entry (keyed by `nonce`) is permanently deleted regardless of outcome, marking a failed message as settled with no path to retry or reconcile — a duplicate/incorrect settlement of bridge queue state divorced from actual execution outcome. This matches the "Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot and the "duplicate settlement or payout" impact gate.

## Likelihood Explanation
High. No malicious relayer, prover, or privileged actor is required — the underlying proof of the `InboundMessageDispatched(success=false)` event is genuine and passes `T::Verifier::verify` legitimately. Any Ethereum-side dispatch failure that still emits this event (e.g. a reverted command) will trigger the bug the moment any relayer calls the public extrinsic `submit_delivery_receipt`.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: on `true`, keep current behavior (pay reward, remove order); on `false`, skip or reduce the relayer reward and either retain the `PendingOrder` for retry/reconciliation or transition it to an explicit failed state instead of unconditionally removing it from `PendingOrders`.

## Proof of Concept
1. `do_process_message` inserts `PendingOrders[nonce] = { nonce, fee, block_number }`. [5](#0-4) 
2. Ethereum-side dispatch of the message fails, and the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer captures this genuine event and calls `submit_delivery_receipt(origin, event)`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly. [6](#0-5) 
4. `process_delivery_receipt` checks only `gateway` and existence of `PendingOrders[nonce]`, both pass, so it calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and then `<PendingOrders<T>>::remove(nonce)`. [4](#0-3) 
5. The relayer is paid despite the failed delivery, and the failed message is permanently marked as resolved with no retry mechanism.
