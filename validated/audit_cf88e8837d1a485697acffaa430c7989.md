### Title
Out-of-memory via unbounded array allocation from unvalidated length field in `BatchValidateSign` precompile helpers - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts` contains helper methods (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) that read a "count" field directly out of attacker-supplied EVM call data and immediately use it to allocate a two-dimensional `byte[][]` array, with no upper bound check against the actual size of the input data before the allocation happens.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and allocates `new byte[len][]` before any per-element data is validated: [1](#0-0) 

`extractBytesArray` and `extractSigArray` do the same pattern — they only check `offset > words.length - 1` (i.e., that the length word itself is present), but never validate that `len` is a sane value relative to the amount of call data actually supplied, before allocating `new byte[len][]`: [2](#0-1) 

`intValueSafe()` clamps a `DataWord` into the `int` range but does not restrict it to a value that has any relationship to the actual data length — an attacker fully controls this word in the calldata passed to the precompile and can set it to `Integer.MAX_VALUE` (or any large value up to that). The subsequent `new byte[len][]` (and, for `extractBytesArray`/`extractSigArray`, the additional per-element `extractBytes` allocations inside the loop) is performed before any bound-versus-data-length check occurs, mirroring the reported bug class: "reads data in size specified by the [input] itself," which can cause OOM/DoS. This is directly analogous to the plistlib issue, where a length taken from untrusted input is used to size a buffer/array without validating it against actual available data.

These helpers are internal to the zk-SNARK Sapling-related precompiled contracts (`VerifyMintProof`/`VerifyTransferProof`/`VerifyBurnProof` family) in `PrecompiledContracts.java`, which are reachable from any TVM `CALL`/`STATICCALL` to the corresponding precompile address by any contract-calling transaction — i.e., an unprivileged contract caller controls the `data` argument that feeds these length fields.

### Impact Explanation
An attacker who can invoke the precompile (via a smart-contract `CALL`, which any account can construct and broadcast) can supply a crafted length word that causes the node to attempt to allocate an outsized array, triggering `OutOfMemoryError` or extreme GC pressure on the full node processing the transaction/block. Because block validation across all consensus-participating nodes must execute the same TVM call, this can produce a crash or degraded availability across the network — a node crash/halt condition, which is in-scope per the validation criteria.

### Likelihood Explanation
The precompile is invoked purely via call data supplied in a transaction's TVM execution path; no special privilege beyond the ability to deploy/call a contract is required. The only existing guard is a bounds check on the *offset* into `words[]`, not on the resulting `len` value used to size the allocation, making the path plausible for any energy-funded caller to exploit (subject to whether the surrounding energy metering charges enough per-word cost to make a maximal-size request prohibitively expensive — I could not fully confirm the exact energy cost calculation for this path from the available snippets, so this should be verified further).

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual bounds of `words.length`/`data.length` (i.e., ensure `len` cannot exceed the number of words/bytes that could plausibly be present in the supplied calldata) and reject with an early return/exception otherwise, consistent with the bound-checking pattern already used elsewhere in the file (e.g., `isValidAbiEncoding`).

### Proof of Concept
Not independently reproduced in this analysis; conceptually, a transaction that `CALL`s the affected Sapling-verification precompile with the length word (at the array-count offset consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) set to a very large value (e.g., `0x7fffffff`) while omitting the corresponding element data would exercise the unguarded `new byte[len][]` allocation path shown above. I was not able to trace the exact precompile `execute()` call site that invokes these helper methods within the available iterations, so the full call chain from `execute(byte[] data)` down to these helpers should be confirmed directly in the repository before treating this as fully proven.

    int len = words[offset].intValueSafe();

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
