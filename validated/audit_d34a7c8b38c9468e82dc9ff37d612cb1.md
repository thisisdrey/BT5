Audit Report

## Title
Unbounded `assets` array in Snowbridge V2 inbound message allows underpriced, disproportionately heavy XCM construction per `submit()` call - ([File: bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs])

## Summary
The `submit()` extrinsic in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` is charged the flat weight `T::WeightInfo::submit()` regardless of how many `EthereumAsset` entries are present in the decoded message, while `Message::extract_assets`, `MessageToXcm::prepare`, and `MessageToXcm::convert` all iterate the attacker-influenced `assets: Vec<EthereumAsset>` with no maximum length check anywhere in the decode/convert path. [1](#0-0) [2](#0-1)  This lets a relayer submit a valid-but-heavy message that costs more to decode/convert/execute than the flat fee reflects.

## Finding Description
`Message::try_from(&Log)` decodes the Ethereum event log and calls `extract_assets`, which loops over `payload.assets` unconditionally, pushing every entry into `substrate_assets` with no cap: [1](#0-0) 

This message flows through the permissionless `submit()` extrinsic, weighed only by the fixed `T::WeightInfo::submit()` benchmark, into `process_message`, then into `T::MessageProcessor::process_message` → `MessageToXcm::convert` → `prepare()`: [3](#0-2) 

`prepare()` iterates `message.assets` a second time, performing a `reanchored()` computation and a `ConvertAssetId::maybe_convert` lookup per `ForeignTokenERC20` entry, with no bound on iteration count: [4](#0-3) 

`convert()` then iterates `message.assets` a third time to partition them into `reserve_deposit_assets`/`reserve_withdraw_assets` before assembling the final `Xcm<()>`: [5](#0-4) 

A repo-wide search confirms there is no `MaxAssets`/bounded-vec/`ensure!(assets.len() <= N, ...)` guard in the Snowbridge V2 message decode or conversion path (the `MaxAssets`-style hits found elsewhere in the repo are unrelated XCM pallet weight/config constants, not Snowbridge inbound-queue-v2 code). The only implicit bound is Substrate's block/extrinsic length limits, which constrain `event.event_log.data` size (and therefore practically bound `assets.len()`), but this is an indirect side effect of generic block-size limits, not an explicit weight-proportional charge or an enforced maximum on the specific field. The `submit()` weight annotation charges a single constant weight independent of `assets.len()`: [6](#0-5) 

## Impact Explanation
Because the number of `EthereumAsset` entries in the Ethereum-side `OutboundMessageAccepted` event is attacker-influenced and unbounded within the codec/decode logic, the actual per-call work (decode, `reanchored()` reanchoring, token-id lookups, and XCM instruction construction for both BridgeHub and downstream AssetHub execution) scales with `assets.len()`, but the fee/weight charged for `submit()` does not. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact class in the gate: a fee-paying, permissionless call can consume execution resources disproportionate to its charged weight.

## Likelihood Explanation
`submit()` is callable by any `ensure_signed` account after proof verification passes — no relayer allowlisting or privileged role is required. [7](#0-6)  Exploitation requires only crafting a real Ethereum event log (with a valid receipt/execution proof) whose `payload.assets` contains many entries, which is within reach of anyone who can call the Gateway contract on Ethereum. The only natural friction is the practical limit imposed by Substrate's block/extrinsic size ceiling on `event.event_log.data`, which bounds — but does not eliminate — the achievable degree of disproportion.

## Recommendation
Enforce an explicit `MaxAssetsPerMessage` bound during `Message::try_from`/`extract_assets`, rejecting messages whose `payload.assets.len()` exceeds the limit, and make the weight charged for `submit()` scale with the decoded `assets.len()` (e.g., a linear weight component similar to `pallet-utility`'s `batch`, which factors in `calls.len()`), so the fee paid is proportional to the work performed.

## Proof of Concept
1. On Ethereum, trigger the Gateway contract to emit an `OutboundMessageAccepted` event with a very large `payload.assets` array (e.g., thousands of dust `NativeTokenERC20`/`ForeignTokenERC20` entries) while keeping `value`/`executionFee` minimal.
2. Any relayer calls `EthereumInboundQueueV2::submit(origin, event)` with the corresponding receipt/execution proof; `T::Verifier::verify` only checks proof validity, not `assets.len()`. [8](#0-7) 
3. `process_message` → `MessageToXcm::prepare()`/`convert()` iterate all assets three times total (decode, prepare, convert), each doing per-asset work (reanchor/lookup), while the extrinsic is charged only the fixed `T::WeightInfo::submit()` weight. [4](#0-3) 
4. Compare charged weight vs. actual execution time/weight consumed as a function of `assets.len()` to demonstrate the disproportion, in a unit test that varies `message.assets.len()` and measures `Converter::convert` execution cost against the constant benchmarked weight.

		#[pallet::weight(T::WeightInfo::submit())]
		pub fn submit(origin: OriginFor<T>, event: Box<EventProof>) -> DispatchResult {
			let who = ensure_signed(origin)?;
			ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);

			// submit message for verification
			T::Verifier::verify(&event.event_log, &event.proof)
				.map_err(|e| Error::<T>::Verification(e))?;

			// Decode event log into a bridge message
			let message =
				Message::try_from(&event.event_log).map_err(|_| Error::<T>::InvalidMessage)?;

			Self::process_message(who, message)
		}
