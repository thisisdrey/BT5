## Finding

### Title
Unbounded array allocation from attacker-controlled length in `PrecompiledContracts.extractBytesArray` / `extractBytes32Array` reachable via `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract decodes a caller-supplied `bytes[]` signature array from raw calldata. When the `allowTvmSelfdestructRestriction` hard-fork flag is not active, the code skips its `MAX_SIZE` bound check and calls `extractBytesArray`/`extractBytes32Array`, which allocate a Java array sized directly from an attacker-controlled 256-bit word before any iteration or bounds validation occurs, mirroring the "Excessive Iteration"/unbounded-resource pattern in the reference CVE.

### Finding Description
`extractBytesArray` reads the array length straight from calldata and immediately allocates an array of that size: [1](#0-0) 

`extractBytes32Array` has the identical pattern: [2](#0-1) 

In `ValidateMultiSign.execute`, the size guard (`sigArraySize > MAX_SIZE`) is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is true; the fallback path calls the unguarded `extractBytesArray`, and this call sits *outside* the method's inner `try { ... } catch (Throwable t)` block that wraps the rest of the permission logic: [3](#0-2) 

`words[offset].intValueSafe()` derives `len` from a fully attacker-controlled `DataWord`, so a contract call can encode a very large declared array length (up to `Integer.MAX_VALUE`). `new byte[len][]` at that size (an array of object references, 8 bytes each on a 64-bit JVM) triggers an immediate large allocation attempt that can throw `OutOfMemoryError`. Because this call occurs before the `try` block that catches `Throwable`, the `OutOfMemoryError` is not contained inside `ValidateMultiSign.execute()` and propagates up through the TVM interpreter loop, which only catches `RuntimeException`, not `Error`: [4](#0-3) 

This is the same bug class as CVE-2018-6352 (an attacker-supplied size/length value drives unbounded resource consumption/iteration without validation before use), applied here to array allocation rather than a parse loop.

By contrast, `BatchValidateSign.execute()` wraps the equivalent extraction calls in `doExecute` inside a `try { return doExecute(data); } catch (Throwable t) { ... }`, so an `OutOfMemoryError` there is caught and handled gracefully — confirming that the missing containment in `ValidateMultiSign` is the anomaly, not the intended design: [5](#0-4) 

### Impact Explanation
An uncaught `OutOfMemoryError` thrown mid-execution inside the TVM interpreter can destabilize the node process (JVM-wide memory pressure, GC thrashing, or crash of the transaction-processing thread), leading to denial of service for that node. Because this is reachable via a single contract call carrying a crafted `bytes[]` argument to the `ValidateMultiSign` precompile (address `0x66` equivalent), any unprivileged contract deployer/caller can trigger it, and if enough validators/full nodes hit the same condition while processing the same block, it could cause a broader liveness disruption.

### Likelihood Explanation
Reachability is straightforward: any account can deploy or call a contract that invokes `ValidateMultiSign` with crafted ABI-encoded input; the precompile is a standard TVM precompiled contract, requiring no special permission. Exploitability depends on whether `allowTvmSelfdestructRestriction` (a chain-config/hard-fork flag) is active on the target network — on networks where this flag has not yet been activated (e.g., certain private/test/older-fork networks), the guard is entirely skipped, making the path directly exploitable.

### Recommendation
Apply the same `MAX_SIZE` length validation unconditionally (not gated behind `allowTvmSelfdestructRestriction`) before calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, and validate `len` against the actual `words.length` (as is effectively done for the `allowTvmSelfdestructRestriction` path) prior to allocation. Additionally, move the extraction calls inside `ValidateMultiSign.execute()`'s existing `try/catch(Throwable)` block so any allocation failure is safely converted to `DATA_FALSE` rather than propagating as an uncaught `Error`.

### Proof of Concept
1. Deploy any contract that calls the `validatemultisign` precompile (address corresponding to `ValidateMultiSign`) with hand-crafted calldata.
2. Encode the `bytes[]` signatures parameter's length word (the word at the offset pointed to by `words[3]`) as a very large value (e.g., `0x7FFFFFFF`), while keeping the rest of the calldata short.
3. On a network where `allowTvmSelfdestructRestriction` is not enabled, `ValidateMultiSign.execute()` calls `extractBytesArray(words, offset, rawData)` outside its `try/catch(Throwable)` block; `new byte[0x7FFFFFFF][]` attempts an outsized allocation, throwing `OutOfMemoryError`, which is not caught by the TVM's `VM.play` (`catch (RuntimeException e)` only) and propagates up the call stack, destabilizing the executing node.
