### Title
Global Adaptive Concurrency Backoff Enables Cross-Tenant Admission-Control DoS - (File: internal/limiter/adaptive_calculator.go)

### Summary
Gitaly's adaptive concurrency-limiting subsystem applies a single, node-wide backoff decision to *every* RPC/repository limiter that has been configured as adaptive, based on node-level cgroup resource pressure (CPU throttling, memory usage, PSI). An ordinary, unprivileged client that merely issues resource-heavy but otherwise legitimate Git operations (large clones, blames, archive/pack generation) against any repository hosted on a shared Gitaly node can repeatedly trigger the node-wide backoff condition, causing the shared `AdaptiveLimiter.Current()` value for all adaptively-limited RPCs to be multiplicatively decreased toward `MinLimit` — starving unrelated repositories and unrelated users of admission on that same node. This mirrors the reported bug class where a single well-funded actor abuses a shared, protocol-wide rate/limit mechanism to lock out other users, except here the "protocol" is Gitaly's RPC admission control and the "funds" are simply CPU/memory-intensive Git operations.

### Finding Description
`AdaptiveCalculator.Start` subscribes to node-wide `loadmonitor` conditions — CPU throttling (`newCPUThrottlingCondition`), memory usage (`newMemoryUsageCondition`), and cgroup PSI pressure — none of which are scoped to a specific repository, RPC, or client: [1](#0-0) 

When any of these node-level conditions fire, `calibrateLimits` iterates over *all* registered `AdaptiveLimiter`s and applies a multiplicative decrease to each of them simultaneously: [2](#0-1) 

These per-RPC adaptive limits are the same limits enforced by `LimitConcurrencyByRepo`-keyed `ConcurrencyLimiter`s that gate admission for *every* repository on the node, not just the repository whose traffic caused the resource pressure: [3](#0-2) [4](#0-3) 

The CPU-throttling condition fires whenever more than a threshold (default 50%) of the polling interval was spent throttled node-wide: [5](#0-4) 

and the memory condition fires on cgroup-wide anonymous-memory ratio or OOM, again node-wide rather than per-repository or per-client: [6](#0-5) 

Because none of these signals attribute load back to the offending repository/client, and because the resulting decrease is applied globally to `c.limits` (every RPC configured with `Adaptive = true` across the whole node), an ordinary user who can push/fetch/clone/blame any single repository on a multi-tenant Gitaly node can depress the shared admission-control budget for all other repositories and users on that node.

### Impact Explanation
Once the shared limit is driven down (bounded only by each limit's configured `MinLimit`), legitimate, unrelated clone/fetch/push requests to *other* repositories on the same node are queued behind the reduced `ConcurrencyLimiter` capacity and can be rejected with `RESOURCE_EXHAUSTED` once `MaxQueueSize`/`MaxQueueWait` are exceeded: [7](#0-6) 

By sustaining CPU/memory pressure (e.g., repeatedly cloning or blaming a large repository, or requesting expensive archive/diff operations) across successive `CalibrationInterval` windows, an attacker can keep the shared limit pinned near `MinLimit`, denying service to all other tenants relying on the same Gitaly node for as long as the attacker sustains the load — a cross-tenant, unprivileged-actor DoS of the RPC admission-control layer.

### Likelihood Explanation
This requires the operator to have enabled adaptive concurrency limiting (`Adaptive: true` on at least one `[[concurrency]]` entry, which is what causes `AdaptiveCalculator` to be started via `run()` in `internal/cli/gitaly/serve.go`), and the attacker only needs ordinary read/write Git access (clone/fetch/push) to any single repository hosted on the affected node — no special privileges, leaked tokens, or MITM position are needed. The resource-heavy operations needed to trip the CPU/memory thresholds (large clones, blames, archive generation) are normal, supported Git operations.

### Recommendation
- Scope backoff decisions and/or their downstream limiter reductions to the offending repository/RPC/client where feasible, rather than applying a single node-wide decrease to every adaptive limiter.
- Combine the node-wide backoff signal with per-request cost attribution (the `BurdenMonitor`/`BurdenTracker` design already tracks per-process resource use) so that the load shedder targets the actual high-cost in-flight requests instead of, or in addition to, globally throttling admission for unrelated repositories.
- Consider a floor on how much of the global budget any single tenant/repository can consume, and/or rate-limit how often a single repository can retrigger a backoff event within a calibration window.
- Add monitoring/alerting on sustained multiplicative-decrease events (`gitaly_concurrency_limiting_backoff_events_total`) correlated with the source of the triggering load, to detect abuse.

### Proof of Concept
1. Operator enables adaptive concurrency limiting for one or more RPCs (e.g. `PostUploadPackWithSidechannel`) via `Adaptive = true` in `[[concurrency]]` config, so `AdaptiveCalculator` is started for the node.
2. An unprivileged user with normal clone/fetch access to Repository A repeatedly performs expensive operations (e.g., concurrent large clones, `git blame` over large history, or repeated archive generation) against Repository A, sustaining CPU throttling above the configured `CPUThrottledThreshold` (default 0.5) or driving cgroup memory usage above `MemoryThreshold` for consecutive `CalibrationInterval` windows.
3. `AdaptiveCalculator.waitForEvents`/`calibrateLimits` observes the node-wide backoff condition and multiplicatively decreases every adaptively-configured `AdaptiveLimiter.Current()` value node-wide (`internal/limiter/adaptive_calculator.go:255-288`).
4. A second, unrelated user attempting to clone/fetch Repository B (unrelated to Repository A) on the same Gitaly node is now admitted under the reduced global concurrency limit; as the attacker sustains load, Repository B's requests queue and eventually receive `RESOURCE_EXHAUSTED` (`ErrMaxQueueSize`/`ErrMaxQueueTime`) from `ConcurrencyLimiter.Limit` (`internal/limiter/concurrency_limiter.go:216-234`), despite Repository B and its user having no relationship to the attacker or Repository A.

// newCPUThrottlingCondition returns a Condition that evaluates to true when CPU throttling occurred for more than 50% of the
// time between the last 2 polls.
func newCPUThrottlingCondition(threshold float64) loadmonitor.Condition {
	if threshold <= 0.0 {
		threshold = defaultCPUThrottlingThreshold
	}

	return loadmonitor.Condition{
		Name: conditionCgroupCPU,
		Fn: func(ctx context.Context, previous, current loadmonitor.Stats, pollInterval time.Duration) (bool, string) {
			cur, prev := current.CGroup.ParentStats, previous.CGroup.ParentStats

			// Somehow, cgroup stats are reset. It's usually the consequence of cgroup limits being changed.
			// Alternatively, they can be overridden by another program.
			// Either way, the watcher should update the stats accordingly.
			if cur.CPUThrottledCount < prev.CPUThrottledCount || cur.CPUThrottledDuration < prev.CPUThrottledDuration {
				return false, ""
			}

			throttledDuration := cur.CPUThrottledDuration - prev.CPUThrottledDuration

			// If the total throttled duration since the last poll exceeds 50%.
			if pollInterval > 0 && throttledDuration/pollInterval.Seconds() > threshold {
				return true, eventCPUThrottling
			}
			return false, ""
		},
	}

// newMemoryUsageCondition evaluates to `true` in 2 conditions:
// * The current memory usage exceeds a soft threshold.
// * The cgroup is under OOM.
func newMemoryUsageCondition(threshold float64) loadmonitor.Condition {
	if threshold <= 0.0 {
		threshold = defaultMemoryThreshold
	}

	return loadmonitor.Condition{
		Name: conditionCgroupMemory,
		Fn: func(ctx context.Context, previous, current loadmonitor.Stats, pollInterval time.Duration) (bool, string) {
			if current.CGroup.ParentStats.UnderOOM {
				return true, eventMemoryOOM
			}

			// This check is to avoid a division by 0 below
			if current.CGroup.ParentStats.MemoryLimit == 0 {
				return false, ""
			}

			anonRatio := float64(current.CGroup.ParentStats.TotalAnon) / float64(current.CGroup.ParentStats.MemoryLimit)
			if anonRatio >= threshold {
				return true, eventMemoryAnon
			}
			return false, ""
		},
	}
}
