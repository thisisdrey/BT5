### Title
Unauthenticated `recv_error` packet allows remote tunnel teardown / state poisoning without any CA-signed certificate - (File: `outside.go`)

### Summary
The `recv_error` message type is dispatched and fully processed in `Interface.readOutsidePackets` / `Interface.handleRecvError` before any certificate, handshake, or AEAD authentication is applied. The only gates are a config toggle and a soft "spoofing" heuristic that compares the sender's UDP source address to the currently-known remote address of the hostinfo — a comparison that is skipped entirely when the hostinfo has no valid remote yet. This mirrors the reported bug class (a state-mutating operation reachable without proper authorization) applied to Nebula's packet-processing path rather than to a Solidity contract.

### Finding Description
In `outside.go`, `readOutsidePackets` parses the wire header and, for `header.RecvError`, immediately calls `f.handleRecvError` — this happens *before* any hostinfo/`ConnectionState` lookup, decryption, or peer-certificate verification that gates every other message type: [1](#0-0) 

`handleRecvError` then:
1. Checks only a config predicate (`acceptRecvErrorConfig.ShouldRecvError`), not any cryptographic proof of peer identity.
2. Looks up the hostinfo purely from the plaintext `h.RemoteIndex` field carried in the unauthenticated header.
3. Applies a heuristic anti-spoofing check that only rejects the message if the hostinfo already has a *valid* remote address and it doesn't match the sender — if `hr.IsValid()` is false, the check is skipped entirely.
4. If it passes, it tears down the tunnel (`f.closeTunnel(hostinfo)`) and removes the pending handshake state (`f.handshakeManager.DeleteHostInfo(hostinfo)`). [2](#0-1) 

`RemoteIndex` is not secret: it is the plaintext index embedded in the header of every ordinary data/handshake packet on the wire (used by `f.hostMap.QueryIndex(h.RemoteIndex)` for routing), so any attacker who can observe traffic between two nodes — or simply guess a 32-bit index — has everything needed to construct a forged `RecvError` packet: [3](#0-2) 

Because `RecvError` packets require zero bytes of authenticated payload (`header.Encode(... header.RecvError, 0, index, 0)`) and are accepted with `ShouldRecvError` defaulting to `always` per the project's own changelog, the only real barrier to exploitation is UDP source-address spoofing, which is a much weaker bar than "possession of a CA-signed certificate."

This differs from the reported Solidity bug only in mechanism, not in bug class: in both cases a state-mutating operation (`proposeRemoveTransmitters` / `handleRecvError`→`closeTunnel`) is reachable by an unauthorized party because the access-control check that should gate it (an `onlyMsc`-style modifier / a cryptographic/certificate-based authentication check) is missing or insufficient on the externally reachable entry point.

### Impact Explanation
An attacker without any CA-signed certificate and without completing a handshake can force termination of an established, legitimate tunnel between two Nebula peers by forging a single small UDP packet, provided they can observe the target's `RemoteIndex` (visible on the wire) and spoof the peer's current UDP source address (or attack before a remote address is set on the hostinfo, in which case the spoofing check is bypassed entirely). This is a remote state-poisoning / denial-of-service primitive against otherwise-authenticated tunnels, achievable with no privileged access and using only crafted unencrypted packets — squarely within "remote state poisoning" and "remote crash/DoS" categories called out as acceptable impact classes.

### Likelihood Explanation
Likelihood is moderate: the attacker needs (a) visibility into legitimate wire traffic to learn a `RemoteIndex` (readily available to any on-path or off-path observer capable of capturing UDP packets, since the field is unauthenticated plaintext), and (b) either UDP source-address spoofing capability or a timing window where the target hostinfo has no valid remote address recorded yet. UDP source spoofing is feasible in many network environments (no TCP-style handshake/ack validation), and the code path explicitly acknowledges the spoofing risk with a partial mitigation, which itself signals the authors know this attack surface exists but only partially close it.

### Recommendation
Do not act on `recv_error` state changes based solely on a plaintext index and a best-effort source-address comparison. At minimum:
- Require the `hr.IsValid()` case to also reject/ignore (or heavily rate-limit) `recv_error` packets rather than skipping the anti-spoof check.
- Consider requiring `recv_error` to include an authenticated proof tied to the current session (e.g., a MAC keyed by the session's established key) before acting on it, rather than accepting a bare, unauthenticated index.
- At minimum, rate-limit and log-and-monitor `recv_error`-triggered teardown so mass forged teardown attempts are detectable.

### Proof of Concept
1. Observe/capture any packet exchanged between node A and node B; extract the 32-bit `RemoteIndex` carried in its plaintext header (used for `QueryIndex`).
2. Craft a UDP packet with `header.Encode(buf, header.Version, header.RecvError, 0, capturedIndex, 0)` and send it to node A, spoofing the source address as node B's currently-known UDP endpoint (or send it while B's hostinfo on A has no valid remote address recorded, e.g., during a race right after roam/reconnect).
3. On receipt, `readOutsidePackets` routes directly to `handleRecvError` without any certificate or AEAD check; if `acceptRecvErrorConfig.ShouldRecvError(addr)` is true (default `always`) and the spoof check doesn't block it, A calls `closeTunnel` and deletes the pending hostinfo — the legitimate tunnel is torn down without either peer's private key ever being involved.

I was unable to fully verify the exact runtime defaults/config wiring for `acceptRecvErrorConfig` (`ShouldRecvError`) and the precise conditions under which a hostinfo's remote address is `IsValid()==false` post-handshake, due to index/tool-call limits on this pass; a Devin session with full repo access could trace `interface.go`'s `acceptRecvErrorConfig` initialization and `hostmap.go`'s `GetRemote`/roaming logic to confirm exact exploitation windows.

func (f *Interface) maybeSendRecvError(endpoint netip.AddrPort, index uint32) {
	if f.sendRecvErrorConfig.ShouldRecvError(endpoint) {
		f.sendRecvError(endpoint, index)
	}
}

func (f *Interface) sendRecvError(endpoint netip.AddrPort, index uint32) {
	f.messageMetrics.Tx(header.RecvError, 0, 1)

	b := header.Encode(make([]byte, header.Len), header.Version, header.RecvError, 0, index, 0)
	_ = f.outside.WriteTo(b, endpoint)
	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error sent",
			"index", index,
			"udpAddr", endpoint,
		)
	}
}

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
