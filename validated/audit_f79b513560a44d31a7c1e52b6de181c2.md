### Title
Stale `PromiseYieldStatus`/`PromiseYieldReceipt` rows survive `DeleteAccount` and let a timed-out yield execute attacker-chosen actions against a recreated account - (File: core/store/src/utils/mod.rs, runtime/runtime/src/lib.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) removes `Account`, `ContractCode`, access keys/gas-key nonces and `ContractData`, but never touches `TrieKey::PromiseYieldStatus{receiver_id, data_id}` or `TrieKey::PromiseYieldReceipt{receiver_id, data_id}`. If a contract creates a promise-yield on itself and then self-deletes the account before the yield resolves, these rows remain in the trie keyed only by the (now-orphaned) `AccountId` string and `data_id`. A later account with the identical name inherits them.

### Finding Description
`ext.rs::create_promise_yield_receipt` (runtime/runtime/src/ext.rs:353-369) writes `TrieKey::PromiseYieldStatus{receiver_id, data_id} = Yielded` via `set_promise_yield_status`. When the corresponding `PromiseYield` receipt is delivered, `set_promise_yield_receipt` (core/store/src/utils/mod.rs:200-212, called from `runtime/runtime/src/lib.rs:1495-1499`) stores the full action receipt (with its embedded actions, e.g. `AddKey`) under `TrieKey::PromiseYieldReceipt{receiver_id, data_id}`.

`action_delete_account` (runtime/runtime/src/actions.rs:314-390) calls `remove_account`, which only clears `Account`, `ContractCode`, access/gas keys, and `ContractData` (core/store/src/utils/mod.rs:504-575). It never calls `remove_promise_yield_status`/`remove_promise_yield_receipt`, so both rows persist keyed purely by account-id string, decoupled from any notion of "account incarnation."

When the automatic timeout later fires, `PromiseResume{data: None}` is delivered for `receiver_id = A`. The handler (runtime/runtime/src/lib.rs:1500-1568):
1. Reads `get_promise_yield_status(state_update, account_id, data_id)` — since it was never cleared, it is `Some(Yielded)`, not `ResumeInitiated`, so the timeout is *not* cancelled.
2. Calls `get_promise_yield_receipt(state_update, account_id, data_id)`, finds the stale stored receipt, and executes it via `apply_action_receipt` against whatever account currently lives at `account_id = A`.

Because `check_actor_permissions` (runtime/runtime/src/actions.rs:739-785) authorizes privileged actions (`AddKey`, `DeployContract`, etc.) purely by comparing `actor_id == account_id` as strings — and both were originally set to the same self-targeting `AccountId` at yield-creation time — the check passes even though the account was destroyed and re-created by an unrelated victim in between. There is no check tying the yield/resume lifecycle to a specific account "incarnation" (e.g., a generation counter or storage-root epoch).

### Impact Explanation
This is authorization escalation / account takeover: an attacker can plant a self-targeted `PromiseYield` receipt whose payload contains a privileged follow-up action (`AddKey` with `FullAccess`, or `DeployContract`), delete their account, and have a victim who later claims the freed account name unknowingly inherit and execute that payload once the timeout fires, taking over their new account. This matches the NEAR bounty category "authorization escalation across accounts or promises."

### Likelihood Explanation
The precondition (name reuse after `DeleteAccount`) is unusual on mainnet for named accounts but is fully permitted by the protocol — nothing prevents recreating a deleted account with the same id, and NEAR's default yield timeout (`yield_timeout_length_in_blocks`, on the order of thousands of blocks) gives ample window between the attacker's deletion and a victim's re-registration. The attack requires only ordinary unprivileged contract deployment/calls (`promise_yield_create` + `DeleteAccount`), no validator/node access. Cost is minimal (deploy + a couple of calls); repeatable across any account name the attacker is willing to pre-poison and later monitor for reuse.

### Recommendation
Clear yield-related state in `remove_account`: iterate and remove all `TrieKey::PromiseYieldStatus`/`TrieKey::PromiseYieldReceipt`/`TrieKey::YieldIdToDataId`/`TrieKey::DataIdToYieldId` entries scoped to the account being deleted (similar to how access keys and contract data are already prefix-scanned and removed), or cancel/void any pending yields for the account before allowing `DeleteAccount` to proceed.

### Proof of Concept
Runtime/test-loop integration test:
1. Deploy a test contract to account `A` exposing a method that calls `promise_yield_create` targeting itself with a payload including `Action::AddKey(attacker_pubkey, FullAccess)`.
2. Execute that call so the `PromiseYieldStatus`/`PromiseYieldReceipt` rows are written for `A`/`data_id`.
3. Assert `get_promise_yield_status`/`get_promise_yield_receipt` return `Some` for `A`.
4. Submit `DeleteAccount(A)` signed by `A` itself (self actor, passes `check_actor_permissions`).
5. Assert account `A` no longer exists, but `get_promise_yield_status`/`get_promise_yield_receipt` for `A`/`data_id` still return `Some` (proving `remove_account` didn't clear them).
6. Have a victim `CreateAccount(A)` (or implicit-recreate) with their own key.
7. Advance blocks past `yield_timeout_length_in_blocks` so the runtime auto-generates `PromiseResume{account_id: A, data_id, data: None}`.
8. After processing, assert the victim's account `A` now has the attacker's public key with `FullAccess` permission — confirming the stale yield executed against the reborn account.
