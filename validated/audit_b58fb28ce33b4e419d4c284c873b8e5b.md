### Title
Liquidations of DIA-priced assets (USDH/zUSDH) become permanently frozen when the DIA oracle stops publishing, with no fallback or on-demand refresh path - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate()` resolves collateral/debt asset prices through `price-resolve`, which for DIA-typed assets calls `resolve-dia` → `call-dia`, reading from the external, push-only `dia-oracle` contract. Unlike the Pyth path, there is no mechanism for a caller to supply a fresh price update for DIA assets during the transaction. If the DIA oracle operator stops publishing updates (goes offline, is paused, or simply lags), `price-resolve`'s staleness assertion fails and the entire `liquidate` call reverts for any position holding USDH or zUSDH as collateral or debt, with no fallback price source.

### Finding Description
`resolve-price-feed` dispatches by oracle `type` to either `resolve-pyth` or `resolve-dia`: [1](#0-0) 

`call-dia` performs a direct external `contract-call?` to `dia-oracle` with `unwrap!`, and `resolve-dia` converts the returned timestamp for freshness checking: [2](#0-1) 

`price-resolve` then enforces both a legality check (`price > 0`) and a strict staleness check via `oracle-timestamp-fresh`, comparing the DIA-reported timestamp against `max-staleness`, and `asserts!`s on failure with `ERR-ORACLE-INVARIANT`, which unwinds the whole transaction: [3](#0-2) 

Critically, for Pyth-priced assets, `liquidate` accepts an optional `price-feeds` parameter that lets the caller push fresh signed VAAs into `pyth-storage-v4` before price resolution via `write-feeds`/`write-feed`, giving liquidators a permissionless path to refresh a stale Pyth price within the same transaction: [4](#0-3) [5](#0-4) 

No equivalent mechanism exists for the DIA oracle: `dia-oracle`'s data is written exclusively by its own off-chain operator, and Zest's market contracts contain no public entry point to push a fresh DIA value or any fallback price source. If the DIA operator stops publishing (goes offline/paused, has an incident, or simply stalls beyond `max-staleness`), every `liquidate` call touching USDH or zUSDH (as collateral or debt) will hit the `ERR-ORACLE-INVARIANT` revert path in `price-resolve` with no way to recover on-chain, since `get-assets`/`get-notional-evaluation` always resolves through this same `price-resolve` for any asset present in the position's mask, and `borrow()` likewise depends on it for health checks.

### Impact Explanation
During a DIA oracle outage, any position holding USDH/zUSDH as debt or collateral cannot be liquidated, even while it is severely undercollateralized. Bad debt in that period accrues unchecked and, because Zest has a bad-debt socialization mechanism keyed to liquidation completing, undercollateralized positions cannot be resolved and their losses cannot be socialized until the oracle recovers. This is a temporary freezing of the ability to liquidate at-risk positions that can, if the underlying collateral price drops during the outage, convert into permanent, uncollectable bad debt distributed onto protocol depositors — matching the in-scope "temporary freezing of funds" / potential insolvency impact class.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the third-party DIA oracle operator to stop publishing for longer than `max-staleness`, which is an external dependency outside Zest's control, similar to the original Chainlink-offline scenario. However, unlike Pyth (which has a permissionless, in-protocol refresh path via `price-feeds`), USDH/zUSDH has zero mitigation once the DIA feed stalls, making this strictly worse for that asset than for Pyth-priced assets.

### Recommendation
Add a fallback or emergency price path for DIA-priced assets analogous to the Pyth `price-feeds` pull mechanism (e.g., allow a permissioned emergency price update, a secondary oracle source, or a manual pause+socialize-debt escape hatch scoped specifically to DIA staleness) so that liquidations are not indefinitely blocked when the sole price source for USDH goes stale. At minimum, wrap DIA staleness failures in a distinct, monitorable error path so operators can quickly trigger the existing `pause-liquidation`/grace-period and socialize-debt mechanisms without waiting on the frozen `liquidate` call itself.

### Proof of Concept
1. USDH oracle key `DIA-USDH` in `dia-oracle` stops receiving updates (operator outage/pause) for longer than the `max-staleness` configured for the USDH/zUSDH asset entry.
2. A borrower holding zUSDH debt (or USDH/zUSDH collateral) becomes undercollateralized due to price movement in another asset in their position.
3. A liquidator calls `liquidate(borrower, collateral-ft, debt-ft, ...)`. Internally this calls `get-assets` → `price-multi-resolve` → `price-resolve` for the USDH/zUSDH asset, which calls `resolve-dia` and evaluates `oracle-timestamp-fresh` against the stale DIA timestamp. [6](#0-5) 
4. Because `delta > max-staleness`, `oracle-timestamp-fresh` returns `false`, the `asserts!` fails, and the entire `liquidate` transaction reverts with `ERR-ORACLE-INVARIANT`. Since no `price-feeds` equivalent exists for DIA, the liquidator has no way to supply a fresher price and the position remains unliquidatable for as long as the DIA outage lasts.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))

    ;; update timestamp if newer
    (if (> timestamp last-update-time)

        false)
