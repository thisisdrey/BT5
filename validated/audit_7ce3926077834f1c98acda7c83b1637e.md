Based on my analysis, the `rlp_execute` function in the wallet contract, when it fails early (e.g., `AccountId` parsing errors, `RelayerError`, or errors from `ExecutionContext::new`), returns `PromiseOrValue::Value(e.into())` without ever creating a `CallerDeposit` or a refund promise. Since `rlp_execute` is `#[payable]` [1](#0-0) , an external caller's `attached_deposit` is only tracked for refund via `CallerDeposit::new(&context)`, which requires a successfully constructed `ExecutionContext` [2](#0-1) . If `ExecutionContext::new` itself fails (`extract_address` error) [3](#0-2) , or if `parse_rlp_tx_to_action` fails with a `Relayer`/`AccountId` error [4](#0-3) , the function returns an error value directly — a successful (non-panicking) execution outcome from the runtime's perspective — with no promise ever created to refund the attached deposit.

Because the call does not panic and the receipt's execution status is `Success` (returning an `ExecuteResponse` with `success: false`), NEAR's protocol-level `refund_unspent_gas_and_deposits` does **not** trigger a deposit refund — that mechanism only refunds deposits when the *action/receipt itself* fails (`result.result.is_err()`) [5](#0-4) . Since `rlp_execute` deliberately avoids panicking ("this method is not meant to panic... to ensure the contract's state can be changed even in error cases") [6](#0-5) , the deposit becomes permanently stuck in the wallet contract's balance whenever an error occurs before `CallerDeposit` is constructed or a refund promise is queued — exactly the "no refund of remaining balance on some early-exit code paths" pattern described in the external report.

This is corroborated by the existing test `test_caller_refunds`, which only validates the refund happens for cross-contract call failures reached via the promise/callback path (`rlp_execute_callback`), not for the earlier synchronous-error paths in `inner_rlp_execute` [7](#0-6) .

### Title
External caller's attached deposit is not refunded on early-exit error paths in `rlp_execute` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`rlp_execute` is `#[payable]`, allowing any external caller (not just relayers) to attach a NEAR deposit when submitting an Ethereum-encoded transaction to a wallet contract. The contract only refunds this deposit via an explicit `CallerDeposit` refund promise constructed inside `inner_rlp_execute`/`rlp_execute_callback`. Several early-return error paths (`ExecutionContext::new` failure, `RelayerError`/`AccountIdError` from `parse_rlp_tx_to_action`) bypass `CallerDeposit` construction entirely and return an `Err`-derived `ExecuteResponse` directly, without any promise or transfer. Since the call is designed to never panic, the receipt succeeds at the protocol level, so NEAR's automatic deposit-refund-on-failure mechanism is not triggered either.

### Finding Description
`rlp_execute` accepts an attached deposit via `#[payable]` [8](#0-7) . It calls `inner_rlp_execute`, which builds an `ExecutionContext` from `env::attached_deposit()` and, only on success, constructs a `CallerDeposit` for later refunding [9](#0-8) . If `ExecutionContext::new` fails (address extraction error) or `parse_rlp_tx_to_action` returns a `RelayerError`/`AccountIdError`, `inner_rlp_execute` returns `Err(err)` immediately at lines 394-409, before any `CallerDeposit` is created and before any promise involving a transfer is queued. `rlp_execute` then converts this directly into `PromiseOrValue::Value(e.into())` (a value response, not a promise) [10](#0-9) . The deposit attached to the `FunctionCall` action is credited to the wallet contract's account balance by the runtime's standard `action_transfer` logic before the function call even begins [11](#0-10)  and stays there because the function call itself completes successfully (no panic → no error-driven refund per `refund_unspent_gas_and_deposits`) [5](#0-4) . This mirrors the reported pattern: some external-facing entry points (`addCoverAndAddLiquidity`, `addLiquidity`, `createNewPool` in the report) never call the "sweep leftover balance" logic, causing tokens sent by a legitimate caller to be permanently stranded in the receiving contract.

### Impact Explanation
Any external, non-relayer caller (an "unprivileged signer") who attaches a NEAR deposit to `rlp_execute` and whose transaction fails at address extraction, RLP parsing, sender/target/chain-id/nonce validation *before* `CallerDeposit` is constructed, loses that deposit permanently into the wallet contract's balance with no path to reclaim it (the contract has no withdrawal method for such funds). This is a fund-freezing/loss defect reachable purely from an ordinary user's transaction against a deployed eth-implicit wallet contract, which is explicitly in scope.

### Likelihood Explanation
The trigger conditions (malformed/invalid RLP transaction bytes, wrong `target`, invalid `chain_id`, bad signature/sender, or an unparseable current-account address) are all easily reachable by any caller constructing the `tx_bytes_b64` argument themselves — this does not require a malicious relayer, network-level manipulation, or any privileged role. A buggy or naive integration (e.g., a slightly malformed front-end-constructed RLP transaction) combined with a nonzero attached deposit would trigger this every time.

### Recommendation
Move deposit tracking/refund logic to occur unconditionally at the very start of `rlp_execute`/`inner_rlp_execute`, before any fallible parsing, so that every early-return error path is guaranteed to issue a refund promise for the attached deposit (mirroring how `CallerDeposit` refunds are already issued for post-parsing failures via `rlp_execute_callback`).

### Proof of Concept
1. A caller `alice.near` calls `rlp_execute` on a deployed wallet contract with a nonzero attached deposit and a `tx_bytes_b64` value that is not valid base64/RLP, or whose `chain_id`/signature is invalid, or whose `target` does not resolve to a valid address.
2. `ExecutionContext::new` or `internal::parse_rlp_tx_to_action` returns `Err(Error::AccountId(_))` or `Err(Error::Relayer(_))` before `CallerDeposit::new` is ever called [12](#0-11) .
3. `inner_rlp_execute` returns this `Err`, and `rlp_execute` returns `PromiseOrValue::Value(e.into())` — a successful FunctionCall receipt carrying a failure message, with no refund promise created [10](#0-9) .
4. Alice's attached deposit remains credited to the wallet contract's account balance (via the normal `Transfer`-with-`FunctionCall` deposit crediting) and is never returned to her.

Note: I was unable to fully trace every branch of `internal::parse_rlp_tx_to_action` (e.g., whether `RelayerError::InsufficientGas` or `InvalidNonce` occur before or after context construction in all cases) due to index size limits on file contents; a Devin session with full repository access would be needed to enumerate every exact error branch and confirm there is no other implicit refund mechanism triggered by the runtime along these specific paths.

fn inner_rlp_execute(
    current_account_id: AccountId,
    predecessor_account_id: AccountId,
    target: AccountId,
    tx_bytes_b64: String,
    nonce: &mut u64,
) -> Result<Promise, Error> {
    if *nonce == u64::MAX {
        return Err(Error::AccountNonceExhausted);
    }
    let context = ExecutionContext::new(
        current_account_id.clone(),
        predecessor_account_id,
        env::attached_deposit(),
    )?;
    let caller_deposit = CallerDeposit::new(&context);

    let parsing_result = internal::parse_rlp_tx_to_action(&tx_bytes_b64, &target, &context, *nonce);
    let (action, transaction_kind) = match parsing_result {
        Ok((action, transaction_kind)) => {
            // Increment nonce for all cases where the registrar contract is not needed
            // to prevent replay of those transactions. For transactions that go through
            // the registrar we still do not know if the transaction has a relayer error
            // or not, therefore we must delay incrementing the nonce.
            //
            // Note: relayers with access keys cannot use this delay to needlessly spend
            // the users tokens because only one transaction is allowed to be in-flight
            // at a time.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                address_check: Some(_),
                ..
            }) = &transaction_kind
            {
            } else {
                *nonce = nonce.saturating_add(1);
            }

            // If the action is an emulated base token or ERC-20 transfer with a non-zero fee then
            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                fee,
                ..
            })
            | TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
                &transaction_kind
            {
                if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
                    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
                    env::promise_batch_action_transfer(refund_promise, *fee);
                }
            }

            (action, transaction_kind)
        }
        Err(err @ Error::User(_)) => {
            // Increment nonce on all user errors to prevent replay.
            *nonce = nonce.saturating_add(1);
            return Err(err);
        }
        Err(err) => {
            // Do not increment nonce on Relayer or AccountId errors.
            // The latter error is an issue in the deployment (so the nonce is meaningless).
            // The former arises from the relayer itself doing something wrong and thus the
            // user's transaction could still be valid and potentially submitted properly by
            // another relayer. To allow this we do not increment the nonce.
            //
            // Note: if a relayer is using an access key for this wallet then that key will
            // still be revoked (in the main logic of `rlp_execute`). This fact together with
            // the condition that there only be one in-flight transaction at a time implies
            // that a relayer cannot maliciously burn a large portion of the user's tokens.
            // If the relayer is not using an access key then they are spending their own
            // resources on the gas and therefore we do not care if the relayer submits
            // the same faulty transaction multiple times.
            return Err(err);
        }

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
