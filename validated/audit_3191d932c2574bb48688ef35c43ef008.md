### Title
Unvalidated attachment content lets any accepted transaction evict pending BNS attachments from the Atlas cache - (File: `stackslib/src/net/atlas/db.rs`)

### Summary
`POST /v2/transactions` accepts an attacker-supplied `Attachment` blob alongside any transaction, and unconditionally caches it in the fixed-size Atlas "uninstantiated attachments" table as long as the transaction is a `ContractCall` to a watched contract (e.g. `bns`) and the blob is under the size cap — with no check that the attachment actually corresponds to a real, pending `AttachmentInstance`. Because the cache has a fixed capacity and evicts the oldest rows once full, an attacker can cheaply flood it with junk to evict legitimate, still-unresolved BNS/attachment records.

### Finding Description
`RPCPostTransactionRequestHandler` (`stackslib/src/net/api/posttransaction.rs`) requires no authentication header — unlike sibling handlers such as `blockreplay.rs`/`blocksimulate.rs`/`fastcallreadonly.rs`/`txsimulate.rs`, which all gate on an `authorization` header, `posttransaction.rs`'s `try_parse_request` has no such check [1](#0-0) . If the submitted transaction is a `ContractCall` and `AtlasDB::should_keep_attachment` returns true for it, the handler stores the attacker-controlled attachment via `insert_uninstantiated_attachment`: [2](#0-1) 

`should_keep_attachment` only checks that (a) the target contract is in the node's watched set and (b) the blob length is within `attachments_max_size` — confirmed by `test_keep_uninstantiated_attachments`, which shows the check is purely contract-id + size, with no correlation to any actual pending attachment instance [3](#0-2) .

`insert_uninstantiated_attachment` enforces a fixed capacity `max_uninstantiated_attachments` (minimum 50,000) and, once full, evicts the oldest rows purely by `created_at` via `evict_k_oldest_uninstantiated_attachments`, with no per-sender quota, no relevance check, and no verification that the entry will ever be claimed by a real `AttachmentInstance`: [4](#0-3) . This FIFO-eviction-on-overflow behavior (and its oldest-first eviction order) is exercised directly in `test_evict_k_oldest_uninstantiated_attachments` [5](#0-4) .

The equality that should hold — "an entry occupies the fixed-size uninstantiated-attachment cache only if it is a genuine, expected pending attachment" — is broken: any accepted `ContractCall` to a watched contract can inject an unrelated, unlinked blob into that same bounded cache, at the cost of only one ordinary transaction fee, with no special privilege or authentication.

### Impact Explanation
This matches the "High" bucket for "attachment/BNS mismatch": a node's Atlas cache can be poisoned so that real, pending BNS name-registration/attachment records — submitted by legitimate users and awaiting resolution by the `AttachmentsDownloader` — are evicted before they are ever matched and marked available (`insert_instantiated_attachment` / `find_uninstantiated_attachment`). This degrades BNS resolution and attachment availability on the targeted node and can be repeated against any node running the public RPC surface, since `/v2/transactions` is unauthenticated by design.

### Likelihood Explanation
Likelihood is moderate-to-high: no authentication or elevated privilege is required — only a validly-signed, mempool-acceptable `ContractCall` transaction targeting a contract already on the node's `atlas.contracts` watch-list (default includes `bns`). The attached blob does not need to correspond to any real attachment event; it merely needs to pass the size/contract filter. An attacker with modest STX for fees can repeatedly submit such transactions with distinct high-entropy blobs (up to `attachments_max_size`, minimum 1 MiB each) to fill and continuously evict the cache.

### Recommendation
Do not admit an attachment into the uninstantiated cache until it is actually correlated with an expected `AttachmentInstance` content hash discovered from the contract's print events (i.e., defer/condition the insert on a genuine pending reference), or add a per-sender/per-time-window quota independent of the global `max_uninstantiated_attachments` bound so that unauthenticated submissions cannot unilaterally displace other users' pending records.

### Proof of Concept
1. Configure/observe a node with default Atlas settings (`max_uninstantiated_attachments` at its minimum, 50,000).
2. Craft a `StacksTransaction` that is a valid, mempool-acceptable `ContractCall` to the watched `bns` contract (any callable function that passes mempool admission checks) — no BNS-specific validity is required.
3. Attach a distinct, high-entropy blob under `attachments_max_size` as `PostTransactionRequestBody.attachment`, JSON-encode, and `POST` to `/v2/transactions` (no `authorization` header needed).
4. Repeat with incrementing nonces until the number of uninstantiated attachments exceeds `max_uninstantiated_attachments`.
5. Query the node (or via `find_uninstantiated_attachment`) for a previously-stored, legitimate uninstantiated attachment hash and observe it has been evicted, per the eviction behavior demonstrated in `test_evict_k_oldest_uninstantiated_attachments` [6](#0-5) .

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
