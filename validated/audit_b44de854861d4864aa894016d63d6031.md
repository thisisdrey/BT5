### Title
Missing Cross-Shard Notification for Declared-But-Unwritten Keys Causes Permanent Executor Deadlock — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

### Summary

`send_remote_update_for_success` iterates over the **actual write set** of the committed output and sends cross-shard notifications only for keys that appear in it. It never iterates over `dependent_edges` to send a notification for every **declared** cross-shard key. When a transaction's actual write set omits a key K that was declared in `dependent_edges` (e.g., due to a Move abort, gas exhaustion, or a conditional execution path), no `RemoteTxnWriteMsg` is ever sent for K. The dependent shard's `RemoteStateValue` for K remains permanently in `Waiting`, and `get_value()` blocks forever on its condvar with no timeout, deadlocking the entire shard executor.

### Finding Description

**Step 1 — Dependent edges are built from static declarations.**

`CrossShardCommitSender::new` populates `dependent_edges` from `txn_with_deps.cross_shard_dependencies.dependent_edges()` — the statically declared cross-shard write set produced by the block partitioner. [1](#0-0) 

**Step 2 — The dependent shard initialises every declared required key in `Waiting` state.**

`CrossShardStateView::create_cross_shard_state_view` inserts every key from `required_edges_iter()` as `RemoteStateValue::waiting()`. There is no fallback to the base view for these keys. [2](#0-1) [3](#0-2) 

**Step 3 — `get_value()` blocks forever with no timeout.**

`RemoteStateValue::get_value` spins on `cvar.wait` until the status transitions to `Ready`. There is no timeout, no cancellation, and no error path. [4](#0-3) 

**Step 4 — The logic inversion in `send_remote_update_for_success`.**

The function iterates over `txn_output.write_set()` (the actual output) and checks whether each written key happens to be in `edges`. It never iterates over `edges` to guarantee a notification for every declared key. If K is in `edges` but absent from the actual write set, the loop body for K is never entered and no message is sent.

```
// ACTUAL (buggy): only notifies keys that were actually written
for (state_key, write_op) in txn_output.write_set().expect_write_op_iter() {
    if let Some(dependent_shard_ids) = edges.get(state_key) { ... }
}

// CORRECT: must iterate edges and send for every declared key
for (state_key, dependent_shard_ids) in edges.iter() {
    let write_op = txn_output.write_set().get(state_key); // may be None
    send(state_key, write_op);
}
``` [5](#0-4) 

**Step 5 — `on_transaction_committed` is called for aborted transactions too.**

`TransactionCommitHook` has a single method `on_transaction_committed` with no abort counterpart. [6](#0-5) 

Both the parallel and sequential commit paths call the hook unconditionally for every finalised output, including aborted ones whose write set contains only the gas-charge entry. [7](#0-6) [8](#0-7) 

**Step 6 — The deadlock propagates to the whole shard.**

`execute_transactions_with_dependencies` spawns two rayon tasks: the `CrossShardCommitReceiver` loop and the `execute_block` call. `execute_block` reads K through `CrossShardStateView::get_state_value`, which calls `get_value()` and blocks. The `execute_block` task never returns, `callback.send` is never called, and `block_on(callback_receiver)` blocks the calling thread. The `StopMsg` is never sent, so the receiver loop also never exits. The entire shard is wedged. [9](#0-8) 

### Impact Explanation

A single transaction that is statically declared as writing key K (causing the partitioner to create a cross-shard dependency) but whose actual execution does not write K (Move abort, gas exhaustion, conditional branch) permanently wedges the dependent shard executor. Because `block_on(callback_receiver)` never returns, the shard's `execute_block` call hangs, the coordinator never receives a result, and block production stalls. This is a **chain availability failure / executor deadlock** reachable from an unprivileged transaction.

### Likelihood Explanation

Any Move transaction with a conditional write (`if (cond) { move_to(...) }`) or one that can abort before reaching the write satisfies the precondition. The block partitioner's static analysis is conservative and will declare the write as a cross-shard dependency even when the runtime path skips it. No special privileges are required; a normal user transaction is sufficient.

### Recommendation

Invert the iteration in `send_remote_update_for_success`: iterate over `edges` (the declared keys) and look up each key in the actual write set, sending `RemoteTxnWrite::new(state_key, write_op_or_none)` for every declared key regardless of whether it was written. The `write_op` field of `RemoteTxnWrite` already supports `None` (documented as "transaction is aborted"), so the receiver side already handles the absent-write case correctly. [10](#0-9)

    pub fn create_cross_shard_state_view(
        base_view: &'a S,
        transactions: &[TransactionWithDependencies<AnalyzedTransaction>],
    ) -> CrossShardStateView<'a, S> {
        let mut cross_shard_state_key = HashSet::new();
        for txn in transactions {
            for (_, storage_locations) in txn.cross_shard_dependencies.required_edges_iter() {
                for storage_location in storage_locations {
                    cross_shard_state_key.insert(storage_location.clone().into_state_key());
                }
            }
        }
        CrossShardStateView::new(cross_shard_state_key, base_view)
    }

        let (lock, cvar) = &*self.value_condition;
        let mut status = lock.lock().unwrap();
        while let RemoteValueStatus::Waiting = *status {
            status = cvar.wait(status).unwrap();
        }

            RemoteValueStatus::Waiting => unreachable!(),
        }
