### Title
Non-constant-time authorization token comparison enables remote timing side-channel to recover node auth secrets - (File: `stackslib/src/net/api/postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`)

### Summary
Multiple HTTP RPC request handlers in `stackslib/src/net/api/` authenticate privileged, unprivileged-reachable endpoints by comparing the client-supplied `authorization` header directly against the configured secret (`connection_options.auth_token`) using Rust's default `String`/`&str` `PartialEq`, i.e. `auth_header != password`. This comparison is not constant-time: `str`/`String` equality in Rust short-circuits and returns as soon as the first mismatching byte is found. An unauthenticated remote attacker who can measure response timing can exploit this to recover the secret token byte-by-byte, analogous to how Umbraco's management API leaked account existence through response timing (GHSA-hmg4-wwm5-p999).

### Finding Description
The affected handlers are:
- `RPCPostBlockRequestHandler::try_parse_request` [1](#0-0) 
- `RPCBlockProposalRequestHandler::try_parse_request` [2](#0-1) 
- `RPCNakamotoBlockReplayRequestHandler::try_parse_request` [3](#0-2) 
- `RPCNakamotoBlockSimulateRequestHandler::try_parse_request` [4](#0-3) 
- `RPCFastCallReadOnlyRequestHandler::try_parse_request` [5](#0-4) 
- `RPCTransactionSimulateRequestHandler::try_parse_request` [6](#0-5) 

Each handler performs:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`auth_header != password` invokes Rust's `str::eq`, which is implemented as a length check followed by `memcmp`-like byte comparison that stops at the first differing byte. No constant-time comparison primitive (e.g. `subtle::ConstantTimeEq`) is used anywhere in this comparison path. Since these endpoints are reachable pre-authentication over the network (the whole point of the check is to *gate* access), an attacker can send many requests with candidate prefixes for the `auth_token` and use response-time statistics to determine how many leading bytes matched, iteratively reconstructing the full secret. This is the same underlying bug class as the referenced advisory: distinguishing "correct" vs "incorrect" secret material via timing of an HTTP response, rather than via a cryptographically-safe fixed-time check.

The `auth_token` config value is intentionally treated as a shared credential guarding privileged write/administrative paths, e.g. broadcasting arbitrary blocks via `/v3/blocks` (`broadcast=1`) and submitting block proposals via `/v3/block_proposal`, which is explicitly the channel between a `stacks-signer` and the node [7](#0-6) . The OpenAPI docs also confirm this token is meant to be a plain-text secret that must "exactly equal" the configured password [8](#0-7) .

### Impact Explanation
If successfully exploited, an attacker who recovers the `auth_token` gains the ability to:
- Submit and force-broadcast arbitrary blocks via `/v3/blocks?broadcast=1` (`postblock_v3.rs`), impersonating a trusted miner/signer relationship.
- Submit block proposals via `/v3/block_proposal`, interfering with the block validation pipeline used by signers.
- Access `/v3/blocks/replay`, `/v3/blocks/simulate`, `/v3/contracts/fast-call-read`, and `/v3/transactions/simulate`, which are normally gated to authenticated (trusted) parties, potentially enabling bounded compute DoS on a read endpoint or unauthorized privileged read/write actions.

This matches the "unauthenticated/unauthorized write to state" and "auth bypass" impact categories, since a successful timing attack ultimately produces the operator's shared secret and full impersonation of an authenticated caller.

### Likelihood Explanation
Exploiting this class of timing side-channel over a real network (rather than a local hardware channel) is generally difficult due to network jitter, and typically requires statistical averaging over many requests per candidate byte, and the secret alphabet/length must be guessable. The advisory this analog is drawn from (Umbraco CVE-2025-24011) was rated Medium severity for the same class of vulnerability (timing-based oracle), reflecting a real but non-trivial likelihood of successful exploitation. It is a legitimate but comparatively lower-likelihood remote vulnerability compared to, e.g., direct memory disclosure or an outright missing auth check.

### Recommendation
Replace all direct `!=`/`==` string comparisons of the `authorization` header value against the configured secret with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or hashing both sides with a keyed MAC and comparing the MACs in constant time). Apply this fix uniformly across `postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, and `txsimulate.rs`, ideally by centralizing the check into a single shared helper function used by all of these handlers to avoid future recurrence.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote unauthenticated client, repeatedly send POST requests to `/v3/block_proposal` (or any of the other listed endpoints) with an `authorization` header value that is a candidate string, incrementing candidate bytes one at a time and holding earlier bytes fixed once they are believed correct.
3. Measure the response latency to the `401 Unauthorized` response for each candidate byte at a given position; because `str::eq` inside `auth_header != password` short-circuits on first mismatch, correct-prefix candidates involve comparing one additional byte (and thus take a measurably different amount of CPU time) versus incorrect-prefix candidates.
4. Aggregate timing samples per candidate byte (to average out network noise) and select the byte value yielding the longest comparison time; repeat until the full token is recovered.
5. Once the full `auth_token` is recovered, use it in the `authorization` header to submit/broadcast attacker-controlled blocks via `/v3/blocks?broadcast=1` or forged block proposals via `/v3/block_proposal`, bypassing the intended authentication.
