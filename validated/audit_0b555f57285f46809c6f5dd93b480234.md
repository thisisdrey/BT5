### Title
Liability oracle failure unconditionally reverts liquidation health checks, freezing liquidations - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
`get_health_components`, which backs `check_pre_liquidation_condition_and_get_account_health` (used directly by `liquidate()` and `start_receivership`), computes each balance's liability value via `calc_weighted_liab_value_standalone`. Unlike the asset-side helper, which explicitly skips stale/failed oracle errors for `RequirementType::Initial`, the liability-side helper has no such bypass for any requirement type, including `Maintenance` (the type used for liquidation eligibility). If the oracle for a liability token becomes stale, unavailable, or otherwise fails to load, the whole health computation errors out, and any call to `liquidate()` for accounts holding debt in that bank reverts.

### Finding Description
In `calc_weighted_liab_value_standalone`, the oracle error is deliberately re-raised rather than tolerated: [1](#0-0) 

Contrast this with the asset-side function `calc_weighted_asset_value_standalone`, which explicitly skips stale oracle failures — but only for `RequirementType::Initial`: [2](#0-1) 

There is no equivalent skip for liabilities at any requirement type, and no skip for assets under `Maintenance`/`Equity` either. `get_health_components` calls `calc_weighted_value_for_balance` (which internally dispatches to the liability helper) per active balance and propagates any error with `?`: [3](#0-2) 

This propagates directly into `check_pre_liquidation_condition_and_get_account_health`, which is called with `RequirementType::Maintenance`: [4](#0-3) 

That function is the first call made inside the `liquidate` instruction handler: [5](#0-4) 

It is also the first call inside `start_receivership`, which backs `start_liquidation`/`start_deleverage`: [6](#0-5) 

So if any account's liability-side oracle (the debt token being liquidated, or any other bank the liquidatee has debt in) becomes stale (e.g., `PythPushStalePrice`, `SwitchboardStalePrice`) or otherwise fails to load, the transaction reverts with that error rather than proceeding with liquidation. This is architecturally consistent with the reported Blueberry bug class: liquidation and health-check paths that hard-fail on oracle problems, rather than degrading gracefully (e.g., pricing the position as maximally unhealthy), can be frozen exactly when they are needed most (a price crash/depeg event is often correlated with oracle staleness or a paused feed).

The codebase's own documentation confirms this is a designed asymmetry: stale asset oracles are tolerated for `Initial` checks ("we're ignoring the stale oracle errors for the collateral banks... the most important thing is to have enough collateral (in non-stale banks) in total"), but no equivalent tolerance exists for liabilities or for `Maintenance`-type (liquidation) checks: [7](#0-6) [8](#0-7) 

The second test (`re_one_oracle_stale_failure_2`) confirms directly that a stale oracle reverts a `Maintenance`-style borrow-adjacent check with `PythPushStalePrice`, demonstrating the general pattern that liquidation-path oracle checks (`Maintenance`) do not tolerate staleness the way `Initial` checks do.

### Impact Explanation
If the oracle for any bank in which the liquidatee holds a liability (or the liability bank in general market stress, e.g. a depeg event triggering an oracle pause/staleness) goes stale or fails, `liquidate()` and `start_liquidation`/`start_deleverage` will revert for that account. This blocks liquidators from seizing collateral to cover bad debt precisely during periods of high volatility or oracle outages, allowing undercollateralized positions to persist and potentially deepen protocol insolvency (bad debt) once/if the account's asset value continues to fall while liabilities cannot be liquidated. This matches the "permanent lock/freeze" and "insolvency/bad debt" impact categories.

### Likelihood Explanation
This is fully reachable by any unprivileged liquidator attempting a normal, permissionless `liquidate()` call — no privileged access is required, and the trigger condition (oracle staleness/failure for a liability-side token) is an external/environmental condition, not attacker-controlled, but it is a realistic condition (feed operator pause, node downtime, network congestion delaying a Pyth/Switchboard update past `oracle_max_age`) that has occurred for real oracles in the wild. Given the deliberate architecture that already special-cases stale-oracle tolerance for collateral/Initial checks, the omission of an equivalent fallback in the Maintenance/liability path is a design gap rather than a mere theoretical concern.

### Recommendation
Introduce a fallback for liquidation-eligibility and liquidation-execution health checks when a liability oracle is stale/unavailable, analogous to how `RequirementType::Initial` skips stale collateral oracles. For example: when a liability price cannot be fetched, either (a) allow liquidation to proceed using the last-known cached price (bounded by an age/emergency threshold) with an appropriately conservative bias, or (b) treat the affected liability as maximally punitive (i.e., do not silently zero it — that would understate risk — but permit a documented emergency price path, similar to protocols that add a fallback/backup oracle or an admin-settable "frozen price" mechanism) so liquidation is not indefinitely blocked. At minimum, document this as a known operational risk and provide risk-admin tooling (e.g., updating `oracle_max_age` or bank config) that can be exercised quickly without requiring a new deployment, and ensure this exists for the liability side, not just for collateral/Initial checks.

### Proof of Concept
1. Liquidatee deposits collateral in Bank A and borrows from Bank B.
2. Bank B's price oracle (Pyth push or Switchboard pull) is not updated for longer than `bank.config.get_oracle_max_age()` (e.g., feed operator halts due to a depeg event) — reproducing the "oracle goes offline" condition from the analog report. `SwitchboardPullPriceFeed::load_checked`/`PythPushOraclePriceFeed::load_checked` would return `SwitchboardStalePrice`/`PythPushStalePrice`, as directly demonstrated by the existing test `re_one_oracle_stale_failure_2`: [9](#0-8) 
3. Liquidatee's collateral value (in Bank A) drops such that the account becomes unhealthy under `Maintenance` weights.
4. A liquidator calls `liquidate()` targeting Bank B (or any bank where liability oracle is stale) as the liability bank. `check_pre_liquidation_condition_and_get_account_health` calls `get_health_components(..., RequirementType::Maintenance, ...)`, which iterates balances and calls `calc_weighted_liab_value_standalone` for the Bank B liability position.
5. Because `price_adapter_result` is `Err(PythPushStalePrice)` (or equivalent) and there is no staleness bypass for the liability path (unlike `calc_weighted_asset_value_standalone`'s `Initial`-only bypass), the function returns `Err`, which propagates through `get_health_components` and `check_pre_liquidation_condition_and_get_account_health`, causing the entire `liquidate()` instruction to revert with the oracle error.
6. The liquidator cannot complete the liquidation until the oracle recovers, even though the account remains (or becomes more) undercollateralized in the interim.
