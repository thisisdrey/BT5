### Title
Withdrawal of already-matured unfrozen TRX can be permanently blocked if the committee later disables `UNFREEZE_DELAY_DAYS` support - ([File: actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java])

### Summary
`WithdrawExpireUnfreezeActuator` (and `UnfreezeBalanceV2Actuator`) gate execution on a mutable, committee-controlled chain parameter, `dynamicStore.supportUnfreezeDelay()`. If an account unfreezes TRX under the new resource model while the feature is enabled, its balance is moved into the `unfrozenV2` list with a maturity timestamp. To actually retrieve that already-matured TRX back into the spendable `balance`, the account must later broadcast a `WithdrawExpireUnfreezeContract`, which is validated at [1](#0-0) . This mirrors the reported ERC1155-whitelist pattern: a state-dependent, admin-toggleable gate blocks a settlement action (withdrawal/liquidation) on obligations that were legitimately created under a prior state.

### Finding Description
`UnfreezeBalanceV2Actuator.validate()` requires the flag to be on before it will move funds from `frozenV2` into `unfrozenV2`: [2](#0-1) . Later, to move the already-matured entries in `unfrozenV2` into spendable `balance`, the user must submit a `WithdrawExpireUnfreezeContract`, whose validation independently re-checks the very same feature flag: [1](#0-0) . If this flag is disabled after the user's funds have already matured in `unfrozenV2` (but before the user withdraws them), the withdraw transaction reverts with `"Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee"`, exactly like `getCollateralValue` reverting for a de-whitelisted ERC1155 token in the original report — a check on current, mutable, admin-controlled state blocks completion of an obligation that was created under different state, rather than checking the specific historical action being finalized.

Note that the analogous native-contract path used from within TVM smart contracts, `WithdrawExpireUnfreezeProcessor.validate()`, does **not** perform this `supportUnfreezeDelay()` check at all [3](#0-2) , meaning the inconsistency exists specifically for ordinary account-level, plain-transaction withdrawal, which is exactly the "unprivileged transaction broadcaster" attack surface in scope.

### Impact Explanation
Funds that have already unfrozen and matured (i.e., are contractually owed back to the user, tracked in `unfrozenV2`) can become permanently stuck if the committee toggles the `UNFREEZE_DELAY_DAYS`/`supportUnfreezeDelay` parameter off after the user unfroze but before they withdraw. This is a freezing-of-funds condition reachable purely by an ordinary account broadcasting a `WithdrawExpireUnfreezeContract`, with no way to bypass the check on this path.

### Likelihood Explanation
This requires the chain parameter controlling `supportUnfreezeDelay()` (backed by `UNFREEZE_DELAY_DAYS`, adjustable via committee proposal per `ProposalUtil`) to change value between the time a user unfreezes and the time they attempt to withdraw. I was not able to fully confirm within the available searches whether the underlying `UNFREEZE_DELAY_DAYS` proposal parameter is restricted by `ProposalUtil` to a one-directional (enable-only) transition or can be freely toggled back down by the committee at any time — this distinction is central to whether the issue is exploitable at all, and I could not verify it with certainty in the time available.

### Recommendation
Given the residual uncertainty about whether `UNFREEZE_DELAY_DAYS`/`supportUnfreezeDelay()` can be toggled bidirectionally by committee proposal, this should be verified directly in `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java` and `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java`. If the parameter can be lowered/disabled after being enabled, `WithdrawExpireUnfreezeActuator.validate()` should not re-check the feature-enablement flag for entries that already exist in `unfrozenV2` — withdrawal of already-matured, previously-committed unfreeze entries should not depend on the current value of a governance switch, only on `UnfreezeExpireTime <= now`, mirroring the report's recommendation to decouple settlement/finalization logic from mutable admin-controlled gating state.

### Proof of Concept
1. Committee enables `UNFREEZE_DELAY_DAYS` (`supportUnfreezeDelay()` returns true).
2. Account A calls `UnfreezeBalanceV2Actuator` — funds move from `frozenV2` to `unfrozenV2` with an expire/maturity time, per [4](#0-3) .
3. Time passes; the entry in `unfrozenV2` matures (`UnfreezeExpireTime <= now`).
4. Before Account A withdraws, the committee lowers/disables `UNFREEZE_DELAY_DAYS`, making `supportUnfreezeDelay()` return false.
5. Account A broadcasts `WithdrawExpireUnfreezeContract`; `validate()` immediately throws `ContractValidateException` at the `supportUnfreezeDelay()` check [1](#0-0) , permanently preventing Account A from moving the already-matured TRX back to spendable balance via this path.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }
