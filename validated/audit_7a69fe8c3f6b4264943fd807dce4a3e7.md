### Title
Integer/allocation overflow via unbounded signature-count field in `ValidateMultiSign` precompile before size check - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract parses a signature-array length directly from attacker-supplied call data and uses it to size a `byte[][]` allocation via `extractBytesArray` *before* the number of signatures is validated against the `MAX_SIZE` bound, mirroring the dr_flac pattern of trusting an untrusted count field before computing buffer size.

### Finding Description
In `ValidateMultiSign.execute`, the signature array offset is read from raw call data and, when `VMConfig.allowTvmSelfdestructRestriction()` is **false** (the legacy/older behavior path), `extractBytesArray` is invoked directly without the size guard that exists on the newer path: [1](#0-0) 

`extractBytesArray` reads `len` straight from the attacker-controlled word and immediately allocates `new byte[len][]` with no upper bound check at all: [2](#0-1) 

Only *after* this allocation does the method check `signatures.length == 0 || signatures.length > MAX_SIZE` and reject: [3](#0-2) 

By contrast, the "restricted" branch performs the size check on `sigArraySize` *before* calling `extractSigArray`/`extractBytesArray`: [4](#0-3) 

This means whenever `allowTvmSelfdestructRestriction` is disabled (e.g. on chains/configurations where that hard-fork flag has not been activated, which historically is the default before the corresponding proposal is enabled), a contract can call the `ValidateMultiSign` precompile with a call-data word encoding a huge `len` (up to whatever `intValueSafe()` returns, capped near `Integer.MAX_VALUE`), causing an attempt to allocate a `byte[Integer.MAX_VALUE][]` reference array. This allocation happens outside of the later `try { ... } catch (Throwable t)` block that wraps the actual per-signature recovery logic, so an `OutOfMemoryError` thrown during allocation is not caught by that local handler and can propagate up through the TVM execution stack.

### Impact Explanation
An uncaught `OutOfMemoryError` triggered from a single transaction/contract call can destabilize or crash the executing node thread pool, denying service to that node (consistent with the CVE's DoS classification). Because `ValidateMultiSign` is reachable from any deployed smart contract via a `STATICCALL`/`CALL` to the precompile address, this is reachable by any unprivileged contract deployer or caller, matching the in-scope precompile/energy-metering path.

### Likelihood Explanation
Exploitability depends entirely on whether `VMConfig.allowTvmSelfdestructRestriction()` is active in the target network's current hard-fork configuration; on networks where it is not yet enabled, the unguarded `extractBytesArray` path is directly reachable by any transaction calling the precompile with crafted data, requiring no special privilege — only a single crafted contract call.

### Recommendation
Move the `MAX_SIZE` (and non-zero) length check before invoking `extractBytesArray`/`extractSigArray` regardless of the `allowTvmSelfdestructRestriction` flag, so the array length is bounded prior to allocation on every code path, not only the newer one.

### Proof of Concept
1. Deploy a contract that performs a low-level call to the `ValidateMultiSign` precompiled contract address.
2. Craft the call data so that the header word at the signature-array offset (`words[3]`) encodes an extremely large length value (e.g., close to `Integer.MAX_VALUE / 32`).
3. On a network configuration where `allowTvmSelfdestructRestriction()` is false, invoking this call routes into `extractBytesArray(words, offset, data)` at [5](#0-4) , which executes `new byte[len][]` with the unchecked huge `len` at [6](#0-5) , triggering excessive memory allocation before the `MAX_SIZE` check is ever reached.

    }
    return bytesArray;
  }
