Audit Report

## Title
`PendingOrders` fee never released or reclaimed if delivery receipt is never submitted — permanent lock of relayer reward in Snowbridge outbound queue v2 - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`do_process_message` inserts a `PendingOrder{nonce, fee, block_number}` into `PendingOrders` for every outbound message, and the pallet's only extrinsic, `submit_delivery_receipt`, is the sole path that removes an entry and pays the recorded fee to a relayer via `process_delivery_receipt`. There is no expiry check, timeout sweep, or governance/permissionless reclaim path keyed on the stored `block_number`, so any order whose Ethereum-side delivery receipt is never submitted remains in storage forever with its fee permanently unpayable.

## Finding Description
`do_process_message` builds the `PendingOrder` and inserts it keyed by `nonce`, explicitly noting the fee is only released "when the message is processed on ethereum side" and the relayer "sends the nonce back with delivery proof" [1](#0-0) . The pallet's `Call` enum exposes exactly one dispatchable, `submit_delivery_receipt` [2](#0-1) [3](#0-2) , which after proof verification calls `process_delivery_receipt` [4](#0-3) . This function is the only place that reads and then `remove`s a `PendingOrders` entry, paying `order.fee` to the reward account through `T::RewardPayment::register_reward` [5](#0-4) .

The `PendingOrder` struct does store `block_number` [6](#0-5) , but it is never read anywhere else in the pallet — there is no `on_initialize`/`on_idle` hook, no expiry constant, and no additional call that inspects `PendingOrders` for staleness. The pallet's only hooks (`on_initialize`, `on_finalize`) only manage the `Messages`/`MessageLeaves` transient storage and commitment, not `PendingOrders` [7](#0-6) . The only other write path touching `PendingOrders` is `AddTip::add_tip`, which increases `order.fee` for an existing order but requires the order to already exist and does not provide any removal/expiry mechanism [8](#0-7) .

This matches the existing repository test `poc_m1`, which demonstrates that while the verifier is halted, `submit_delivery_receipt` fails and the `PendingOrder` remains in storage with its fee untouched [9](#0-8) . Nothing in the codebase demonstrates recovery from this state absent an eventual valid receipt submission.

By contrast, other reward/payout subsystems in this codebase explicitly guard against this class of stuck state: `pallet-treasury`'s `check_status` extrinsic checks `spend.expire_at` and removes/settles a spend once it has expired [10](#0-9) , and `pallet-staking-async`'s `EraRewardManager::drain` explicitly sweeps unclaimed era-pot balances into an `UnclaimedRewardHandler` rather than letting them sit indefinitely [11](#0-10) . `outbound-queue-v2` has no analogous mechanism.

## Impact Explanation
`register_reward` only records/pays a reward when `process_delivery_receipt` succeeds [5](#0-4) ; the underlying `RewardLedger`/`PaymentProcedure` abstraction transfers from a rewards sovereign account to the beneficiary only at that point [12](#0-11) . If no valid delivery receipt is ever submitted for a given nonce — because the verifier remained halted long enough that relayers gave up (as exercised by `poc_m1`), the destination command becomes non-executable on Ethereum, or the receipt is otherwise lost off-chain — the corresponding `PendingOrder` and its `fee` value remain permanently in `PendingOrders` storage with no code path to reclaim, refund, or redistribute it. This is a genuine state-accounting lock (an entry that can never be resolved by any on-chain action), matching the "permanent... bridge-state lock" impact category.

## Likelihood Explanation
No privileged actor or malicious behavior is required — the condition arises purely from the absence of any relayer submitting a valid receipt for a given nonce, which can plausibly occur during extended verifier halts, gateway/contract migrations, or economically unattractive deliveries. The `poc_m1` test in the repository already demonstrates the halted-verifier scenario leaving the order untouched, confirming the code path exists and is exercised in the existing test suite [9](#0-8) . This is a design gap (missing cleanup/expiry) rather than a directly attacker-triggerable exploit against another party's funds, but it is a real, reachable stuck-state condition confirmed by reading all code paths touching `PendingOrders` in the pallet.

## Recommendation
Add an expiry-aware, permissionless resolution path for stale `PendingOrders`, analogous to `pallet-treasury::check_status` (using the already-stored `block_number` against a configurable expiry) or `pallet-staking-async`'s pot-draining pattern, so that orders whose receipts are never submitted can be refunded to the original payer or swept into a recoverable pool instead of remaining permanently unresolved.

## Proof of Concept
The existing `poc_m1` test in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` (lines 392-416) already demonstrates the core mechanism: a `PendingOrder` is inserted, the verifier is halted so `submit_delivery_receipt` fails with `Error::Verification(VerificationError::Halted)`, and the order remains present with `fee` unchanged after unhalting [9](#0-8) . Extending this test to simply never call `submit_delivery_receipt` again (i.e., omit any further receipt submission) and asserting `PendingOrders::<Test>::get(nonce)` still returns `Some` indefinitely, with no other pallet call able to clear it, confirms the permanent-lock condition described above.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

					return Ok(Pays::No.into());

	/// Drains an era pot's remaining balance to the unclaimed reward handler.
	///
	/// The pot account itself is kept alive (provider retained) so the same slot
	/// can be reused by a future era. No-op if the pot was never created (e.g.
	/// the era ran in legacy minting mode).
	pub(crate) fn drain(era: EraIndex, kind: RewardKind) {
		let pot_account = T::RewardPots::pot_account(RewardPot::Era(era, kind));

		// Skip if pot was never created (legacy mode doesn't create pots).
		if frame_system::Pallet::<T>::providers(&pot_account) == 0 {
			return;
		}

		let remaining = T::Currency::balance(&pot_account);

		if remaining.is_zero() {
			return;
		}

		match T::Currency::withdraw(
			&pot_account,
			remaining,
			Precision::BestEffort,
			Preservation::Expendable,
			Fortitude::Force,
		) {
			Ok(credit) => {
				T::UnclaimedRewardHandler::on_unbalanced(credit);
				log!(
					debug,
					"Drained {:?} unclaimed rewards from era {:?} {:?} pot",
					remaining,
					era,
					kind
				);
			},
			Err(e) => {
				defensive!("Failed to withdraw unclaimed rewards from era pot");
				log!(
					error,
					"Era {:?} {:?}: unclaimed reward withdrawal failed: {:?}",
					era,
					kind,
					e
				);
			},
		}
	}
