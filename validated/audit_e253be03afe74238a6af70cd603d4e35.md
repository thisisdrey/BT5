### Title
Malicious User Can Permanently Lock/Break Any TRC10 Bancor Exchange Pool In A Single Transaction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionContract` is a fully permissionless transaction — any account holding the traded token can call it against any exchange pair — and it mutates the pool's `firstTokenBalance`/`secondTokenBalance` using a Bancor-style relay calculation with no post-trade sanity check that the resulting balances stay positive, unless the network-wide `AllowHardenExchangeCalculation` proposal has been activated by governance. This mirrors the reported bug class: a value that is read/derived purely from the current, single-transaction spot state (here, the pool's on-chain token balances and the un-clamped Bancor formula output) is used to permit an irreversible, shared-resource-locking action that any unprivileged caller can trigger.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via `ExchangeProcessor.exchange()` (double-precision Bancor curve math) and then updates the pool balances: [1](#0-0) 

The non-hardened path performs plain `long` addition/subtraction with **no lower-bound check** — the `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` guard only applies when `hardenedCalc` is true: [2](#0-1) 

`hardenedCalc` is derived from `allowHarden()`, which reads the `AllowHardenExchangeCalculation` dynamic property — a value that only becomes `true` after a Notional/Tron-governance-style proposal is activated by the committee, i.e. it is off by default in normal chain operation: [3](#0-2) 

`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` and persists the resulting (potentially negative or exactly-zero) balances without any additional guard beyond what `transaction()` itself performs: [4](#0-3) 

`doValidate()` only checks that `firstTokenBalance`/`secondTokenBalance` are non-zero *before* the trade (to permanently reject future trades once a pool has already been drained), not that they remain positive *after* the current trade: [5](#0-4) 

Because `ExchangeProcessor.exchange()` (the default, non-hardened processor) relies on `double`-precision `pow` and simple `long` arithmetic with no clamping: [6](#0-5) 

a caller who supplies a sufficiently large `sellTokenQuant` for a low-liquidity pool can push `buyTokenQuant` to equal or exceed the current opposite-side balance in a single transaction (floating-point rounding/`(long) issuedSupply` truncation makes an exact or over-shoot value plausible for extreme inputs), driving `newFirstTokenBalance` or `newSecondTokenBalance` to `0` or negative. Once a balance reaches `0` (or goes negative, breaking the Bancor invariant entirely), every subsequent `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` against that pool is permanently rejected by the `"Token balance in exchange is equal with 0, the exchange has been closed"` validation, and any negative balance would produce nonsensical/`ArithmeticException` results in further Bancor calculations, both cases resulting in irrecoverable denial of service for the exchange pool.

### Impact Explanation
This permanently locks a shared, permissionless-access financial primitive (a TRC10↔TRX or TRC10↔TRC10 Bancor pool) that any account can otherwise trade against, mirroring the "force an emergency settlement/lockup on a shared vault" impact from the reference report: it is a single-signed-transaction, unauthorized-account action that produces a permanent freeze of pool functionality (no further trades, injects, or possibly withdraws), constituting a real loss of protocol functionality and locked liquidity for all other exchange participants — a concrete denial-of-service on an in-scope actuator path (Medium/High class per the rules, since it produces permanent freezing of the exchange feature for a pool, potentially trapping remaining pool liquidity from being fairly withdrawn/traded).

### Likelihood Explanation
The `ExchangeTransactionContract` path requires no special privilege — only holding enough of the sell-side token, which is obtainable on the open market (TRC10 exchanges or DEXes) — and the vulnerable non-hardened arithmetic path is the default unless the specific `AllowHardenExchangeCalculation` committee proposal has been activated on the running chain. Low-liquidity or newly created exchange pairs (created via the also-permissionless `ExchangeCreateActuator`) are especially easy to drain to zero/negative balance with a modest amount of capital, making this practically exploitable by any address without insider access.

### Recommendation
Make the post-trade non-negative-balance check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditional in `ExchangeCapsule.transaction()` rather than gating it behind `hardenedCalc`/`allowHarden()`, and additionally reject trades that would reduce either balance below a safe minimum (not just below zero), regardless of the network's proposal state. Consider migrating fully to the `SafeExchangeProcessor`/`StrictMathWrapper` BigDecimal-based computations by default instead of leaving the un-clamped double-precision `ExchangeProcessor` path as the default behavior.

### Proof of Concept
1. Any user creates (or targets an existing) low-liquidity `Exchange` pair via `ExchangeCreateContract`/uses an existing pool, e.g. `firstTokenBalance = 100`, `secondTokenBalance = 100`.
2. On a network where `AllowHardenExchangeCalculation` has not been enabled (default), the attacker submits a single `ExchangeTransactionContract` selling an extremely large `tokenQuant` of `firstToken`.
3. `ExchangeCapsule.transaction()` computes `buyTokenQuant` via the double-precision `ExchangeProcessor.exchange()` such that `buyTokenQuant >= secondTokenBalance`, and since the non-hardened path performs unchecked `long` subtraction (`secondTokenBalance - buyTokenQuant`), `newSecondTokenBalance` becomes `0` or negative and is persisted directly with no exception thrown: [7](#0-6) 
4. All subsequent `ExchangeTransactionContract`/`ExchangeInjectContract` calls against this exchange ID now fail validation permanently with `"Token balance in exchange is equal with 0, the exchange has been closed"`: [8](#0-7) 
5. The pool is permanently unusable for any future trade, with no privileged recovery path exposed in the actuators reviewed.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
