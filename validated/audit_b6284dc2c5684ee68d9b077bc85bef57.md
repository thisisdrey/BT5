## Title
Invalid memory address dereference in `InputJar::LocateCentralDirectory` via unchecked Zip64 central-directory size — (`src/tools/singlejar/input_jar.cc`)

## Summary
`InputJar::LocateCentralDirectory` computes the location of the ZIP Central Directory Header (`CDH`) by subtracting an attacker-controlled size field from a pointer inside the memory-mapped archive. For ordinary (32-bit) ZIP entries this subtraction is bounds-checked, but for the Zip64 code path the 64-bit `cen_size` value read straight from the untrusted archive's `ECD64` record is never validated before being used in pointer arithmetic, allowing the resulting `cdh_` pointer to point far outside the mapped file. The pointer is then unconditionally dereferenced (`cdh_->is()`), producing an out-of-bounds/invalid memory read — the same bug class as CVE-2021-45764's "invalid memory address dereference" in GPAC's chunk-offset handling.

## Finding Description
`InputJar::Open`/`LocateCentralDirectory` is the entry point singlejar (Bazel's `_deploy.jar`/jar-merging tool) uses to parse any input JAR/ZIP, including JARs that originate from external dependencies (e.g. `java_import`, Maven artifacts fetched via `http_jar`/`http_file`, or third-party prebuilt `.jar`s pulled in by `http_archive`).

In the 32-bit path, the code validates the central-directory size against the file: [1](#0-0) 

But this validation is guarded by `if (!ziph::zfield_has_ext64(cen_size))` — i.e. it is skipped entirely whenever the 32-bit `cen_size32()` field is `0xFFFFFFFF`, signaling that the real size lives in the Zip64 extension record. When the code then looks up the Zip64 extension (`ECD64`), it uses the 64-bit `cen_size()` value directly, with **no bounds check whatsoever**, to compute the location of the central directory: [2](#0-1) 

`ecd64->cen_size()` is a fully attacker-controlled 64-bit field parsed straight out of the archive bytes (see `ECD64::cen_size()`): [3](#0-2) 

An attacker can set this value larger than the offset of the `ECD64` record within the file, causing `ziph::byte_ptr(ecd64) - ecd64->cen_size()` to underflow past `mapped_file_.start()`. The resulting `cdh_` pointer is not checked with `mapped_file_.mapped(...)` (unlike, e.g., the `NextEntry()` bounds check later used elsewhere: `mapped_file_.mapped(new_cdr)`), and is unconditionally dereferenced immediately afterward: [4](#0-3) 

This is precisely analogous to GPAC's `shift_chunk_offsets.isra()` bug: a size/offset value taken from untrusted container metadata is used in pointer arithmetic and dereferenced without validating it stays within the mapped buffer, causing an invalid memory address dereference.

## Impact Explanation
A crafted JAR/ZIP file with a malicious Zip64 End-of-Central-Directory record can force singlejar to compute and dereference a pointer outside the bounds of the memory-mapped input file. Depending on the offset this can:
- Crash the build (SIGSEGV) processing an external dependency's JAR.
- Read from adjacent unmapped or unrelated memory, which — because `cdh_->is()`, and subsequent field accesses (`file_name_length()`, `extra_fields_length()`, etc.) all operate on this pointer — can propagate garbage/attacker-uncontrolled memory content into build outputs (e.g. copied into the file name buffer path in `OutputJar::AddJar`/`AppendToDirectoryBuffer`).

Because the checksum (e.g. `sha256`/`integrity` on `http_jar`/`http_archive`) only certifies that the *bytes* match the attacker's chosen content — not that the internal ZIP structure is well-formed — this is not something that a `sha256` pin can stop. If anything, publishing a byte-for-byte reproducible malicious JAR that matches a pinned digest is exactly the certified content that Bazel is required to trust.

## Likelihood Explanation
Any external dependency delivered as a JAR (Maven artifact, `http_jar`, hand-written `http_archive` containing `.jar` files that flow through Java rules/singlejar) is parsed by this code with no additional sandboxing of the ZIP structure. An unprivileged party who controls the content served at a dependency URL (or a malicious/compromised package registry entry) can trigger this simply by crafting the Zip64 EOCD fields; no privileged access to the build machine is required.

## Recommendation
Validate `ecd64->cen_size()` and `ecd64->cen_offset()` against the mapped file bounds (`mapped_file_.offset(ecd64)`/`mapped_file_.start()`) before using them in pointer arithmetic, mirroring the existing 32-bit check at lines 113–122. After computing `cdh_`, call `mapped_file_.mapped(cdh_)` (as already done for `new_cdr` in `NextEntry()`) before dereferencing `cdh_->is()`.

## Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Construct a minimal ZIP with a Zip64 EOCD Locator + Zip64 EOCD record where `cen_size` (8-byte field) is set to a value larger than the byte offset of the `ECD64` record within the file (e.g. `0xFFFFFFFFFFFFFFF0`).
2. Feed this file as an input jar to `InputJar::Open` (or through `singlejar --sources <malicious.jar>` as used when merging a `java_binary`'s dependency jars).
3. Observe that `LocateCentralDirectory` computes `cdh_ = ecd64_ptr - cen_size`, producing a pointer far outside `mapped_file_.start()`, and then dereferences it at `cdh_->is()`, causing a crash or out-of-bounds read (verifiable under ASan as an invalid-address read).
