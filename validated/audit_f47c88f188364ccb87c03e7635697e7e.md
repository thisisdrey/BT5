### Title
Self-liquidation via price-feed sandwiching inside a single `liquidate` call - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `liquidate` function accepts an optional `price-feeds` argument and calls `write-feeds` (which pushes new Pyth VAA prices on-chain via `verify-and-update-price-feeds`) *before* it reads asset prices and computes `current-ltv`, `liq-penalty`, and the seized-collateral amount. The only front-running guard in the function is a same-block check on `last-borrow-block`, which blocks "borrow + liquidate in the same block" but does nothing to prevent "push an attacker-chosen price update + liquidate" in the same call. Because Pyth uses a pull model where any previously signed VAA can be submitted by anyone as long as its `publish-time` is newer than the last stored one, an attacker who already holds a leveraged position from a prior block can submit a favorably timed price update and immediately self-liquidate in the same transaction, extracting more collateral value than the debt they repay — leaving the shortfall as socialized bad debt.

### Finding Description
`liquidate` (`mainnet/contracts/market/v0-4-market.clar:1382-1530`) executes the following sequence:

1. `(feeds-check (try! (write-feeds price-feeds)))` at line 1391 — pushes up to 3 caller-supplied Pyth VAA payloads on-chain via `write-feed`/`verify-and-update-price-feeds` (`mainnet/contracts/market/v0-4-market.clar:129-152`). [1](#0-0) [2](#0-1) 

2. Only *after* that price write does the function resolve `assets`, compute `total-collateral-usd`/`total-debt-usd`, and derive `current-ltv`: [3](#0-2) 

3. The only anti-frontrunning guard present checks `last-borrow-block` against the current block height — explicitly scoped to block "flash-loan based attacks where user borrows + gets liquidated in same block," not price-update sandwiching: [4](#0-3) 

4. Liquidation discount (`liq-penalty`) is derived from a graduated curve bounded by `LIQ-PENALTY-MIN`/`LIQ-PENALTY-MAX` from the egroup, and collateral seized includes this bonus: [5](#0-4) 
Example egroup values confirm plausible parameters: `LTV-BORROW: 70%`, `LTV-LIQ-PARTIAL: 85%`, `LIQ-PENALTY-MIN: 5%`, `LIQ-PENALTY-MAX: 10%`. [6](#0-5) 

Pyth's storage contract only requires that a submitted update's `publish-time` be strictly newer than the previously stored one and not stale — it does not require the update to be "the very latest" available signed price, so an attacker can choose, from a set of previously valid signed VAAs, whichever one is least favorable to their own collateral (subject to staleness bound) and submit it themselves inside the same `liquidate` call: [7](#0-6) 

Combining these: an attacker who built a leveraged position (with collateral and debt, using any capital source including a flashloan for capital only, which is out of scope but permissible per rules as "capital for a different attack") in a *previous* block passes the `last-borrow-block` guard trivially. In the very next call to `liquidate` (targeting themselves or a colluding sub-account), they supply `price-feeds` containing an adverse-but-valid price update for their collateral asset. `write-feeds` applies it atomically before `current-ltv`/`liq-penalty`/seized-collateral math run, letting the attacker choose the exact price at which they get liquidated and how much of the liquidation bonus/discount they capture, exactly as described in the external report's `LTV_borrow > discount_factor * (1 - priceDrop)` profitability condition.

### Impact Explanation
When `LTV-BORROW > liq-discount-factor` (a plausible relationship given `LIQ-PENALTY-MIN/MAX` are only 5-10% while `LTV-BORROW` can be 70%+), the attacker seizes collateral worth more than the debt they repay. The shortfall is not absorbed by the attacker — it becomes bad debt on the borrower's (attacker's own) position, which the protocol's socialize-debt path at the end of `liquidate` distributes across the vault (`other-debt-repayable`/`no-collateral-left` handling near line 1514-1530). This constitutes theft of protocol-held collateral funds and creates insolvency risk for other depositors in that vault, matching the in-scope "Critical" impact category (protocol insolvency / theft of user funds at rest). [8](#0-7) 

### Likelihood Explanation
Likelihood is high for any attacker willing to build a leveraged position near the liquidation threshold and hold a favorable-for-self signed Pyth VAA (or wait for one to become available within staleness bounds). No privileged access, DAO compromise, or third-party oracle corruption is required — only ordinary principal calls to `liquidate` with the standard `price-feeds` parameter that the protocol itself exposes for permissionless price pushing.

### Recommendation
Extend the existing frontrunning guard so it also blocks self-liquidation (or any liquidation) that occurs in the same transaction/call as an oracle price update supplied via the `price-feeds` parameter — e.g., require that `write-feeds`-sourced price updates be committed in a separate transaction from `liquidate`, or disallow `liquidate` from accepting `price-feeds` for the borrower calling on themselves, or enforce a minimum number of blocks between a price update affecting a mask's assets and liquidation of positions under that mask (mirroring the `last-borrow-block` same-block check but keyed to price update timestamps instead of borrow timestamps).

### Proof of Concept
1. Attacker deposits collateral and borrows debt near `LTV-BORROW` (e.g., 70%) in block N, using either their own capital or a flashloan purely as capital (permitted).
2. In block N+1 (or any later block, satisfying the `last-borrow-block != stacks-block-height` check), attacker calls `liquidate(borrower: <self-or-controlled-subaccount>, ..., price-feeds: (some (list <adverse-but-valid-VAA-for-collateral>)))`.
3. `write-feeds` applies the adverse price atomically at line 1391, dropping the collateral's on-chain price.
4. `current-ltv` computed at lines 1424-1426 now exceeds `LTV-LIQ-PARTIAL`/`LTV-LIQ-FULL`, triggering `calc-liquidation-params`, which yields `liq-penalty` bounded at `LIQ-PENALTY-MAX` (e.g. 10%).
5. Attacker (as liquidator) repays `debt-to-repay` and receives `coll-final` collateral, which — per the report's profitability condition `LTV-BORROW > discount-factor * (1 - priceDrop)` — exceeds the USD value of debt repaid, netting the attacker a profit and leaving the difference as bad debt socialized against the vault. [9](#0-8)

    (liquidator contract-caller)
    (position (try! (get-liquidation-position borrower)))
    (pos-full (try! (get-full-position borrower)))
    (mask (get mask position))
    (group (try! (get-egroup mask)))

    (coll-address (contract-of collateral-ft))
    (debt-address (contract-of debt-ft))
    (coll-asset (try! (get-asset coll-address)))
    (debt-asset (try! (get-asset debt-address)))
    (coll-aid (get id coll-asset))
    (debt-aid (get id debt-asset))

    ;; accrue FIRST - populates cache for zToken price resolution
    (u-debt (accrue-user-debts (get debt pos-full)))
    (u-coll (accrue-user-collateral (get collateral pos-full)))

    ;; NOW safe to resolve prices (cache is populated)
    (assets (get-assets mask))
    (notional-valued-assets (get-notional-evaluation { position: position, assets: assets }))
    (total-collateral-usd (get collateral notional-valued-assets))
    (total-debt-usd (get debt notional-valued-assets))

    ;; LTC thresholds, liq params, health
    (ltv-liq-partial (buff-to-uint-be (get LTV-LIQ-PARTIAL group)))
    (ltv-liq-full (buff-to-uint-be (get LTV-LIQ-FULL group)))
    (liq-penalty-min (buff-to-uint-be (get LIQ-PENALTY-MIN group)))
    (liq-penalty-max (buff-to-uint-be (get LIQ-PENALTY-MAX group)))
    (curve-exponent (buff-to-uint-be (get LIQ-CURVE-EXP group)))

    ;; LTV = (debt x 10,000) / collateral
    ;; handle edge case: If collateral = 0, return max LTV (BPS) or 0 if debt also 0
    (current-ltv   (if (is-eq total-collateral-usd u0)
                       (if (is-eq total-debt-usd u0) u0 BPS)
                       (mul-div-down total-debt-usd BPS total-collateral-usd)))
    
    ;; Oracle frontrunning protection: prevent same-block liquidation
    ;; This blocks flash-loan based attacks where user borrows + gets liquidated in same block
    (last-borrow-block (get last-borrow-block position))
    (same-block-check (asserts! (not (is-eq last-borrow-block stacks-block-height)) ERR-LIQUIDATION-BORROW-SAME-BLOCK))

    ;; health check (FAIL-FAST) 
    ;; Check position is liquidatable BEFORE calling calc-liq-factor
    (health-check  (asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY))
