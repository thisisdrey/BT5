### Title
Unvalidated attacker-supplied handshake `Time` value used as anti-replay defense - (File: `handshake_manager.go`)

### Summary
The comment on `HostInfo.lastHandshakeTime` states this field "is used to avoid an attack where a handshake packet is replayed after some time," but the value it stores (`result.HandshakeTime`, sourced from the peer-controlled `Payload.Time` field) is never validated against the local wall clock, a monotonic per-peer counter, or any bound. This is structurally the same bug class as the Chainlink `latestAnswer` finding: a value that is supposed to carry freshness/validity information is consumed and trusted for a security decision without checking that it is actually fresh, non-stale, or well-formed, instead of using a mechanism that can prove freshness (e.g., comparing to `time.Now()` with a bounded skew, or an authenticated monotonic counter).

### Finding Description
`Payload.Time` is a plain `uint64` field written by the sender as `p.Time = uint64(time.Now().UnixNano())` in `handshake/machine.go` (`marshalOutgoing`), and parsed on the receiving side with no bounds checking in `handshake/payload.go` (`unmarshalPayloadDetails`, `fieldTime` case) — any `uint64` value, including `0`, `1`, or `math.MaxUint64`, is accepted as long as it decodes as a valid varint. [1](#0-0) 

That parsed value flows straight into `m.result.HandshakeTime = payload.Time` in `processPayload`, with no validation beyond checking that other index fields aren't zero: [2](#0-1) 

It is then copied into `hostinfo.lastHandshakeTime` in both `beginHandshake` and `continueHandshake`: [3](#0-2) [4](#0-3) 

Finally, `CheckAndComplete` uses this attacker-influenced value as the sole gate for deciding whether a new handshake should replace an existing tunnel — i.e., it is the anti-replay/freshness check the field's own comment describes: [5](#0-4) [6](#0-5) 

Nowhere in this path is `lastHandshakeTime` checked against `time.Now()`, a previous known-good value from the *same* peer/cert across handshakes (persisted independent of the currently-live `HostInfo`), or any monotonicity guarantee tied to the certificate/session. Because the value is fully attacker-controlled at the protocol layer (the sender is free to set any `uint64`), a peer who has a valid certificate and can complete a handshake at all can pick a `Time` value larger than the current `lastHandshakeTime` to force `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` to evaluate false, satisfying the "is this a newer handshake" check regardless of true replay/freshness. This mirrors the Chainlink issue in that a "freshness/validity" signal (Chainlink: round timestamp/roundId; nebula: handshake `Time`) is consumed without the accompanying validation that would let the code detect a stale or forged value, so a value that looks "newer" is trusted even though nothing proves it actually reflects current wall-clock time.

### Impact Explanation
This weakens (but does not fully eliminate, since it's bounded by needing a valid completed handshake) the intended anti-replay property documented for `lastHandshakeTime`: a captured old handshake response could, in principle, be replayed later with a manipulated `Time` value chosen to be "newer" than the field's actual replay-window intent, causing tunnel state churn (tearing down/replacing an active `HostInfo`) — a remote state-poisoning / limited denial-of-service outcome on an existing tunnel, consistent with the "halting/disrupting the protocol" severity class the Chainlink judge applied (Medium: no direct key/data compromise, but disruption of tunnel state).

### Likelihood Explanation
Reaching this code path requires the attacker to be able to complete (or resend components of) a handshake that the responder accepts as coming from a legitimate-looking peer identity for the target `vpnAddr` — i.e., no CA-signed certificate is needed to *trigger* the comparison, since `CheckAndComplete` runs for every completed handshake regardless of which peer it came from, and the "Time" field is attacker-supplied on every handshake message, not just malicious ones. The narrow gate is that `CheckAndComplete`'s replacement logic only matters when there is already an existing `HostInfo` for the same `vpnAddr`, which is a normal, frequently-occurring condition (re-handshakes, roaming, retries).

### Recommendation
Do not treat the peer-supplied `Time` field as a trustworthy freshness/anti-replay signal on its own. Either:
- Bound-check `payload.Time` against the local clock (reject values far in the future or the past) before accepting it as `lastHandshakeTime`, or
- Replace/augment the check with a signal that isn't fully attacker-chosen — e.g., a per-session or per-certificate monotonic handshake counter enforced independently of the value itself, similar to how Chainlink's fix moved from a bare returned value (`latestAnswer`) to `latestRoundData` plus explicit `roundID`/`timestamp` consistency checks.

### Proof of Concept
1. Attacker completes (or captures) a valid handshake stage-1/stage-2 message pair for a legitimate certificate/peer relationship.
2. Attacker crafts (or replays with modification, since the payload is authenticated by the noise handshake AEAD and cannot be tampered with post-hoc, but the attacker fully controls the value on any *new* handshake they initiate) a stage message where `Payload.Time` is set to a very large `uint64` (e.g., `math.MaxUint64`), via `handshake.MarshalPayload`/`Payload{Time: ...}`.
3. This value passes through `unmarshalPayloadDetails` unmodified (no range check) and becomes `result.HandshakeTime` → `hostinfo.lastHandshakeTime`.
4. In `CheckAndComplete`, `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` is now guaranteed false for any future legitimate handshake attempt from the real peer, until the artificially inflated value is exceeded — meaning the attacker's forged-time handshake always "wins" the freshness check in `handshake_manager.go` lines 446-452, regardless of actual chronological order.

*Note: because the `Time` field is protected by the noise handshake's AEAD once inside a completed message, exploiting this specifically as a "replay" (rather than as a value chosen by an already-authorized peer able to initiate handshakes) is constrained; this reduces confidence to Medium/Low without further verification against nebula's threat model for what "replay" is meant to prevent here. This nuance could not be fully resolved from static reading alone within the available search budget.*
