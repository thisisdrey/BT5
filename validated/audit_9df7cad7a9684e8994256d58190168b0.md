### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign` precompile is not wrapped in a `Throwable` guard, unlike its sibling `BatchValidateSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
Both `ValidateMultiSign` and `BatchValidateSign` precompiled contracts parse their calldata into `byte[][]` arrays via `extractBytesArray`/`extractBytes32Array`, whose element count (`len`) is taken directly from attacker-controlled ABI-encoded calldata with `words[offset].intValueSafe()` and used to allocate `new byte[len][]` before any element is bounds-checked. `BatchValidateSign.execute()` defensively wraps its entire body in `catch (Throwable t)` [1](#0-0) , but `ValidateMultiSign.execute()` does not — the calls to `extractSigArray`/`extractBytesArray` happen before the only `try { } catch (Throwable t)` block in that method, which only wraps the later permission-weight logic [2](#0-1) .

### Finding Description
`extractBytesArray` computes `len` from a caller-supplied word with no upper bound and immediately allocates a reference array of that size: [3](#0-2) 

`ValidateMultiSign.execute` invokes this (or `extractSigArray`) unconditionally on the raw parsed words for every call to precompile address `0x0a`: [4](#0-3) 

A TIP-854 guard (`isValidAbiEncoding`) exists to reject malformed ABI shapes, but it is only consulted when `VMConfig.allowTvmOsaka()` is active [5](#0-4) ; the project's own tests document that "before activation the guard is not consulted" [6](#0-5) . On any network/config where this hard-fork flag is not yet enabled, a caller can craft `words[3]`'s referenced length word to be a huge positive `int` (e.g. close to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt an outsized allocation and throw `OutOfMemoryError`. Because `OutOfMemoryError` is a `java.lang.Error`, not an `Exception`, and the only surrounding `try` in `ValidateMultiSign.execute()` is placed *after* the vulnerable allocation, the error is not caught locally in this method — unlike the structurally identical `BatchValidateSign`, which explicitly wraps its whole body in `catch (Throwable t)` for exactly this class of failure [1](#0-0) .

### Impact Explanation
Since block/transaction execution (including precompile calls) is deterministic and must be replayed by every full node, an uncaught `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` escaping `ValidateMultiSign.execute()` depends entirely on whether an outer layer (e.g. `Program.callToPrecompiledAddress`, `TransactionTrace`, or `Manager` block application) catches `Throwable` broadly enough to convert it into a normal VM revert. If that outer layer only catches `Exception` (not `Error`), a single crafted contract call to precompile `0x0a` could crash node execution during transaction/block processing — a reachable, low-cost denial-of-service or, in the worst case, a chain-halt if this occurs identically on every validating node. This mirrors the CVE-2020-26759 bug class: an unvalidated length taken from untrusted input drives an oversized buffer/array allocation leading to a crash.

### Likelihood Explanation
I was unable to fully confirm, within the available search budget, whether `Program.callToPrecompiledAddress` (the caller of `PrecompiledContract.execute`) wraps precompile execution in a catch-all `Throwable` handler that would neutralize this gap. The presence of the identical, deliberate `catch (Throwable t)` wrapper in the sibling `BatchValidateSign` class strongly suggests the project is aware this specific failure mode needs handling at the precompile level, and its absence in `ValidateMultiSign` looks like an inconsistency rather than an intentional design choice. This should be verified directly in `actuator/src/main/java/org/tron/core/vm/program/Program.java` (method `callToPrecompiledAddress`) before treating this as confirmed-exploitable; if that method already catches all `Throwable`s, the practical impact is limited to a benign revert rather than a crash.

### Recommendation
- Wrap the entirety of `ValidateMultiSign.execute()` in a `catch (Throwable t)` block, mirroring `BatchValidateSign.execute()`, so that exceptions/errors thrown during ABI parsing (`extractBytesArray`, `extractSigArray`) cannot escape the precompile boundary.
- Independently of the `allowTvmOsaka`/TIP-854 flag, add an explicit sanity bound on `len` in `extractBytesArray`/`extractBytes32Array` (e.g. reject if `len < 0 || len > words.length`) before allocating `new byte[len][]`, so the fix does not depend on a hard-fork activation flag.
- Audit `Program.callToPrecompiledAddress` to confirm it uniformly catches `Throwable` (not just `Exception`) for all precompiled contracts, closing this class of bug at the framework layer as defense in depth.

### Proof of Concept
1. Construct calldata for `validateMultiSign(address,uint256,bytes,bytes[])` (precompile `0x0a`) with `VMConfig.allowTvmOsaka()` disabled (default/legacy config).
2. Set the word at the offset referenced by `words[3]` (the `bytes[]` length slot) to a large positive value such as `0x000000000000000000000000000000000000000000000000000000FFFFFFF0` (fits in 4 bytes per `intValueSafe`, so it is not clamped to `Integer.MAX_VALUE` via the "more than 4 bytes" check, but is still enormous).
3. Deploy/call a contract that issues this crafted call to address `0x...0a` via `CALL`/`STATICCALL`.
4. Observe that `extractBytesArray`/`extractSigArray` attempts `new byte[len][]`, triggering `OutOfMemoryError` before the later `try/catch(Throwable)` in `ValidateMultiSign.execute()` can intercept it, since that block only starts after line 1082 [7](#0-6) .
5. Confirm whether the error propagates out of `Program.callToPrecompiledAddress` and crashes/aborts transaction or block processing (this final confirmation step requires inspecting `Program.java`, which could not be completed in this session).

  @Test
  public void testTip854RejectsMalformedCalldata() {
    VMConfig.initAllowTvmOsaka(1);
    try {
      // Bucket 1: 32-aligned head + sub-word trailing bytes (r=1, r=31).
      for (int r : new int[]{1, 31}) {
        byte[] data = new byte[(5 + 5) * 32 + r];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("non-32-aligned len=" + data.length, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 2: fewer than the static head's 5 words.
      for (int bytes : new int[]{0, 32, 64, 96, 128}) {
        Pair<Boolean, byte[]> ret = contract.execute(new byte[bytes]);
        Assert.assertFalse("len=" + bytes + " < 5 words", ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 3: 32-aligned but tail not a multiple of I=5 words (k = 1..4).
      for (int k = 1; k <= 4; k++) {
        byte[] data = new byte[(5 + k) * 32];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("aligned bad-tail k=" + k, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Null calldata: explicit spec clause.
      Pair<Boolean, byte[]> ret = contract.execute(null);
      Assert.assertFalse("null calldata", ret.getLeft());
      Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
    } finally {
      VMConfig.initAllowTvmOsaka(0);
