### Title
Dust transfers permanently fill a victim's per-account token list, DoS-ing deposits of new collateral types - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` combined deposit + debt tokens per account via `onlyIfAdditionWillNotReachMaxTokens`. `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token was previously zero. An unprivileged attacker can deposit dust amounts of every listed collateral, transfer 1 wei of each `DepositToken` to a victim, and fill all 30 slots. Any subsequent mint to the victim (deposit, liquidation `seize`, leverage callback, or another transfer of a token type they don't yet hold) reverts with `UserReachedMaxTokens`, blocking the victim from adding new collateral types.

### Finding Description
The p2c-style flaw here is a numeric bound (`MAX_TOKENS_PER_USER`) that an attacker can force a *victim* to reach using inputs the victim never authorized. [1](#0-0) [2](#0-1) 

`addToDepositTokensOfAccount` is only callable by a registered DepositToken, but `DepositToken._transfer` invokes it on behalf of *any* recipient of a first-time balance: [3](#0-2) 

`transfer` only checks the *sender's* unlocked balance, so dust transfers to arbitrary recipients are unrestricted: [4](#0-3) 

Removal only happens when the balance reaches exactly zero (`_burn`/`_transfer`), so the victim must actively spend gas to clear each dust slot before they can onboard a new collateral type: [5](#0-4) 

### Impact Explanation
Temporary freezing of funds / liveness break. Once the victim's combined `depositTokensOfAccount + debtTokensOfAccount` count hits 30, every path that would add a new token reverts: `deposit(onBehalfOf = victim)` reverts inside `_mint → addToDepositTokensOfAccount`, `seize` to a liquidator whose list is full reverts, and SmartFarmingManager flows that mint to a recipient revert. A victim with an unhealthy position cannot deposit a new collateral type to restore health and is forced into liquidation; the cleanup requires the victim to zero-out and transfer away each dusted token, transaction by transaction, while interest accrues. The attacker cost is only dust collateral (recoverable by withdrawing) plus gas.

### Likelihood Explanation
Fully reachable by an unprivileged EOA with public entry points: `DepositToken.deposit` (any amount), then `DepositToken.transfer(victim, 1)` for each listed collateral. No privileged role, oracle manipulation, or governance action is required. The cap is a hard constant (30) and the check fires before any mint, so no modifier prevents it. Deployed pools list multiple collaterals, so filling 30 combined slots is realistic; the count only needs the deposit-token side if the victim holds no debt.

### Recommendation
- Charge the list-addition to the *sender's* slot accounting is impractical; instead, skip adding tokens for balances below a protocol-defined dust threshold, or
- allow `addToDepositTokensOfAccount` to silently no-op (rather than revert) when the cap is reached, tracking position health only over the tokens actually in the set — combined with iterating a bounded snapshot — or
- let anyone permissionlessly remove zero- or dust-balance entries from any account's list, so griefed slots self-clean.

### Proof of Concept
Hardhat sketch (against deployed-style pool with N ≥ 30 listed DepositTokens, or with the victim already holding some debt tokens so fewer are needed):

```ts
// pool has depositTokens[0..k]; attacker deposits dust into each
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, attacker.address);        // mint 1 wei msdTOKEN
  await dt.connect(attacker).transfer(victim.address, 1);         // adds dt to victim's list
}
// victim.depositTokensOfAccount.length + debtTokensOfAccount.length == 30 now

// victim tries to deposit a collateral type they don't yet hold:
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// anyone depositing a new type on behalf of the victim also reverts
await expect(
  newDepositToken.connect(helper).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

On a mainnet/Base fork, repeat `deposit(1, attacker) → transfer(victim, 1)` across the pool's listed DepositTokens until `getDepositTokensOfAccount(victim).length + getDebtTokensOfAccount(victim).length == 30`, then assert that a deposit of a collateral the victim doesn't hold reverts.
