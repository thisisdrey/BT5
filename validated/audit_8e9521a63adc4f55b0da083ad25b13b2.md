### Title
Existing pre-funded/permissioned account is silently converted into an owner-less smart contract via CREATE/CREATE2, discarding its original access control state - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The H1 report describes a bug class where a derived resource created from a private, owner-controlled asset (an image transformation) loses the access-control properties of its source and becomes an object that neither its creator nor anyone else can properly manage or reclaim. The closest reachable analog in java-tron is in `Program.createContractImpl`, where a smart-contract creation (`CREATE`/`CREATE2`) can target an address that already has an existing `AccountCapsule` (e.g., a normal, pre-funded account with balance, permissions, votes, or delegated resources). When this happens, the actuator overwrites the account's type and clears part of its resource state without any check tying the new contract's control (the `OriginAddress`) back to whoever actually controlled the pre-existing account. [1](#0-0) 

### Finding Description
`createContractImpl` fetches whatever `AccountCapsule` already sits at the deterministically-computed new contract address: [1](#0-0) 

If the account already exists but is not yet flagged as a contract (`contractAlreadyExists == false`), the code calls `existingAccount.updateAccountType(AccountType.Contract)` and `existingAccount.clearDelegatedResource()`, then persists it and creates a new `SmartContract` entry whose `OriginAddress` is set to the **caller's** address (`senderAddress`), not to whoever previously controlled the pre-existing account: [2](#0-1) 

This mirrors the reported bug class exactly:
- A resource that previously had well-defined ownership/permission semantics (a normal `AccountCapsule` with its own `OwnerPermission`/`ActivePermission`, balance, votes, and delegated-resource accounting) is transformed by an unrelated third-party action (any account can trigger a `CreateSmartContract`/CREATE2 targeting a predictable address) into a new artifact (a smart contract) whose control is now defined by the *transformer* (`senderAddress`), not by the original account holder.
- The original account's permission structure (multi-sig `Permission` records set via `AccountPermissionUpdateActuator`) is not consulted, cleared, or otherwise reconciled — the type flip happens unconditionally in the actuator/VM execution path, which is reachable by any signed `TriggerSmartContract`/`CreateSmartContract` transaction from an unprivileged account, matching the report's "no privilege needed, no way to modify/reclaim afterward" pattern.
- `clearDelegatedResource()` unilaterally zeroes only the *acquired* delegated resource fields, but the pre-existing account may still have its own frozen balances, votes, or `Permission` data intact in the raw `Account` proto that is now wrapped as `AccountType.Contract`, creating an inconsistent state the original owner can no longer manage as a normal account (no more `AccountPermissionUpdateContract`/`FreezeBalance` semantics apply once `AccountType.Contract` is set), yet who never authorized the state change. [3](#0-2) 

### Impact Explanation
Analogous to the H1 report, a resource that a user controlled (their normal account, with balance/votes/permissions) can be converted into an artifact controlled by someone else (the CREATE/CREATE2 caller becomes `OriginAddress`) without the involvement or consent of the account's original permission holders, and the resulting object can no longer be governed through the normal account-management actuators (permission update, freeze/unfreeze, vote) because its `AccountType` is now `Contract`. This is an improper access control condition that can result in unauthorized account state changes and effectively "freezes" or strands funds/votes/permissions that were tied to the pre-existing account, since post-conversion account-level actuators (e.g., `AccountPermissionUpdateActuator`, freeze/unfreeze) validate against contract-specific rules rather than the original owner's expectations.

### Likelihood Explanation
Reaching an address collision requires the attacker to predict the target address ahead of time (`CREATE` uses `rootTransactionId`+`nonce`; `CREATE2` uses a chosen salt plus code hash), which is feasible since these are deterministic and public. An unprivileged user can pre-fund/vote/set permissions on such a predictable address (intentionally or as a victim of griefing) and later have another party's `CreateSmartContract` transaction land on it, triggering the conversion — no special node privilege or signature bypass is required, just an ordinary broadcastable contract-deployment transaction.

### Recommendation
Before permitting `AccountType` to flip to `Contract` for a pre-existing account in `createContractImpl`, verify that the existing account does not hold user-set state that implies distinct ownership expectations (e.g., non-default `Permission`, non-zero `Frozen`/vote data), and/or require that the account be provably uninitialized (only balance, matching current genesis/precreate semantics) before allowing conversion. At minimum, preserve or explicitly reconcile the account's existing `Permission` records rather than silently discarding governance context.

### Proof of Concept
Not independently reproduced against a live node; this is a static-analysis-derived analog based on the code path shown above. A concrete PoC would require: (1) computing/pre-funding a target `CREATE`/`CREATE2` address as a normal multisig-enabled account with custom `AccountPermissionUpdateContract` permissions, then (2) broadcasting a `CreateSmartContract`/`TriggerSmartContract` deploying a contract to that exact address, and (3) observing that `AccountCapsule.getType()` becomes `Contract` and prior `Permission`/vote/frozen semantics are no longer reachable via standard account actuators — confirmed only through code review of `Program.java` lines 836–867 and `AccountCapsule.java` lines 1322–1337, not through live execution in this session.
