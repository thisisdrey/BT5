### Title
Premature StackerDBChunkInv advertisement of unwritten chunk version before relayer commit - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches and immediately replies with a `StackerDBChunkInv` advertising the pushed chunk's `slot_version` as soon as `validate_received_chunk` passes, but the actual durable write via `try_replace_chunk` happens later and independently in the relayer thread (`process_pushed_stacker_db_chunks`). If the later `try_replace_chunk` call fails (e.g. `StaleChunk` due to a concurrent write from another source winning the race), the node has already told its neighbor it holds a version it never stored.

### Finding Description
`validate_received_chunk` (stackerdb/mod.rs:649-718) only rejects a pushed chunk if `data.slot_version < *expected_version`; a strictly greater version passes. In `handle_unsolicited_StackerDBPushChunk` (mod.rs:742-871), once this check passes, the code immediately mutates the outgoing `StackerDBChunkInv`'s `slot_versions[slot_id]` to the new, higher `chunk_data.chunk_data.slot_version` (line 807) and sends this reply synchronously over the p2p connection (lines 858-870) — all without ever calling `try_replace_chunk` in this code path. The comment at line 862 ("we can store it right now") is misleading: no store happens here at all. The actual commit occurs later, out-of-band, when the relayer drains `network_result.pushed_stackerdb_chunks` via `process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` (relay.rs:2469-2493, 2385-2467), which calls `tx.try_replace_chunk(&sc, &md, &chunk.data)` (relay.rs:2412). `try_replace_chunk` (stackerdb/db.rs:400-438) can still reject the same chunk with `StaleChunk` if `slot_desc.slot_version <= slot_validation.version` at commit time — which can occur if a different write for the same slot (e.g. via the HTTP `poststackerdbchunk` upload path, or a concurrent sync round from another neighbor) commits an equal-or-higher version first, since the p2p reply and the relayer's DB transaction are decoupled and unsynchronized.

### Impact Explanation
A remote peer that legitimately owns a StackerDB slot can push a chunk whose version is momentarily ahead of what the node has stored, get an immediate `StackerDBChunkInv` acknowledgment advertising that version, and then have the actual store silently fail in the relayer. Other neighbors who received or requested that advertised inventory will believe this replica holds the newer chunk and will issue `StackerDBGetChunkData` requests for it, receiving repeated NACKs (`StaleVersion`) instead — a bounded compute/round-trip cost on the StackerDB sync state machine of any peer that trusts the advertised inventory. This matches the "steering a node off the tip via false inventory" / bounded compute DoS category (High), since it forges inventory data that does not reflect actual durable state.

### Likelihood Explanation
The attacker need only be a legitimate holder of a StackerDB slot (an unprivileged, remote precondition already permitted) and race their own push against another concurrent write to the same slot on the target node — e.g., by pushing a slightly stale chunk to two neighbors of the target roughly simultaneously, or racing against the target's own outbound sync fetching the same slot from a different peer. This requires no secret, no privileged role, and is repeatable per slot per version bump; the P2P push endpoint is reachable by any connected peer.

### Recommendation
Do not patch and reply with the updated `slot_versions` in `handle_unsolicited_StackerDBPushChunk` until after the chunk has actually been durably committed via `try_replace_chunk` (e.g., move the chunk into a synchronous store call in this handler, or defer sending the `StackerDBChunkInv` reply until the relayer confirms the write succeeded, replying with the pre-write version or an error otherwise).

### Proof of Concept
Rust test in `stackslib/src/net/stackerdb/tests/sync.rs`: construct a `TestPeer` with a StackerDB slot at version N; call `network.handle_unsolicited_StackerDBPushChunk` with a `StackerDBPushChunkData` at version N+1, capture the immediate `StackerDBChunkInv` reply and assert its `slot_versions[slot_id] == N+1`; separately, before invoking the relayer, commit a competing write to version N+1 or higher directly via `try_replace_chunk`; then run `relayer.process_pushed_stacker_db_chunks(...)` with the original pushed chunk and assert it returns `StaleChunk` (logged, dropped) while `stackerdbs.get_slot_versions()` never reaches N+1 from the pushed chunk — demonstrating the already-sent inventory reply diverges from the durably stored state.
