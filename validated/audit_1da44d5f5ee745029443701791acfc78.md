### Title
Out-of-bounds heap read parsing malformed ZIP64 extra field in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s central-directory parser reads several fixed-size, attacker-controlled fields (`compressed_size`, `uncompressed_size`, `offset`) from a per-entry "extra field" blob without validating that the declared `data_size` of that blob actually covers the bytes being read, mirroring the CVE-2023-3773 class of bug: a length-prefixed attribute is trusted to be at least as long as the fixed-size field the code unconditionally reads out of it.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` (used for per-file local headers) is careful to call `EnsureRemaining()` before every read [1](#0-0) , and does so repeatedly through the function [2](#0-1) .

`InputZipFile::ProcessCentralDirEntry`, which walks the ZIP central directory (also fully attacker-controlled, mmapped input bytes), performs **no** `EnsureRemaining` bounds checks at all. It reads the fixed header fields, then walks a chain of "extra field" TLV records purely driven by the attacker-supplied `header_id`/`data_size` fields: [3](#0-2) 

For the `ZIP64_EXTRA_FIELD_TAG` case, the code unconditionally calls `get_u8le(extra)` up to three times (16–24 bytes) against the `extra` pointer, but the only bound it derived was `data_size`, which is never checked to be `>= 8`, `>= 16`, or `>= 24` before these reads. If the crafted central directory entry declares `header_id == ZIP64_EXTRA_FIELD_TAG` with a `data_size` of 0 (or any value smaller than the number of 8-byte fields the code decides to read based on the *other*, independently-controlled `U4_MAX` sentinel checks on `uncompressed_size`/`compressed_size`/`offset`), `get_u8le(extra)` reads past the end of the declared extra-field payload. Because the whole central directory itself is not bounds-checked against the mapped input file length either (no `EnsureRemaining` calls anywhere in this function, unlike its sibling), a sufficiently crafted (truncated) central directory can push these reads past the end of the `mmap`'d input file entirely, producing a classic heap/mapping out-of-bounds read whose bytes flow into `uncompressed_size`/`compressed_size`/`offset`, which are then used to size subsequent copies/allocations in the ijar rewriting pipeline (`InputZipFile::ProcessNext` → `ProcessLocalFileEntry`) [4](#0-3) .

This is directly analogous to CVE-2023-3773: a subsystem reads a fixed-size field (there, `XFRMA_MTIMER_THRESH`; here, the ZIP64 8-byte size/offset fields) out of a variable, attacker-declared length-prefixed attribute without first verifying the declared length actually covers the field, leaking adjacent memory content into program state.

### Impact Explanation
The out-of-bounds bytes are used as size/offset values that steer subsequent parsing and copies of the archive contents processed by the `ijar` tool (invoked as a build action on jar inputs, including externally fetched jars such as via `http_jar`/Maven-resolved artifacts). This can leak adjacent heap data into the derived interface jar or corrupt later reads/writes of file data, and in the worst case crash the tool or read/write outside the intended buffer bounds during the subsequent local-header processing that trusts these now-corrupted size fields.

### Likelihood Explanation
An attacker who controls the origin server for an `http_jar`/`http_archive` URL (or a mirror) that a victim's build fetches can serve a specially crafted `.jar`/`.zip` whose central directory contains a ZIP64 extra field with an undersized `data_size`. Because this is a structural/parsing bug rather than a byte-content mismatch, a pinned `sha256`/`integrity` value does not prevent it if that hash was itself computed against the attacker's malicious file at the time it was first pinned (a realistic "hostile origin, TOFU-pinned checksum" scenario) — the checksum only proves byte-for-byte reproducibility of the same malicious file, not structural validity.

### Recommendation
Add `EnsureRemaining`-style bounds validation throughout `InputZipFile::ProcessCentralDirEntry`, and specifically validate `data_size >= 8` (or `>= 16`/`>= 24` depending on how many ZIP64 fields are expected) before each `get_u8le(extra)` call in the ZIP64 extra-field handling loop, matching the discipline already used in `ProcessLocalFileEntry`.

### Proof of Concept
1. Construct a minimal ZIP file whose central directory entry:
   - Sets `uncompressed_size32`/`compressed_size32`/`offset32` all to `0xFFFFFFFF` (forcing the ZIP64 extra-field path).
   - Declares an extra field with `header_id = 0x0001` (ZIP64) and `data_size = 0`.
   - Places this record at (or near) the very end of the mapped input file, so the subsequent `get_u8le(extra)` calls read past the end of the file mapping.
2. Run the `ijar` tool (or any Bazel build action that invokes it, e.g. via `java_import`/`http_jar` on this crafted jar) against this file.
3. Observe the out-of-bounds read (verifiable under ASan/Valgrind) and/or corrupted `uncompressed_size_`/`compressed_size_`/`offset` values propagating into subsequent processing, which should be codified as a `third_party/ijar` unit test analogous to `zip_headers_test.cc` [5](#0-4)  that feeds a truncated ZIP64 extra field into `ProcessCentralDirEntry` and asserts it is rejected rather than read out-of-bounds.

  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
