Audit Report

## Title
Relayer reward is paid and delivery order settled even when the Ethereum `success` flag reports message dispatch failure - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs` decodes the `success` field from the verified Ethereum `InboundMessageDispatched` event log, but `process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` only checks `receipt.gateway` and looks up the `PendingOrder` by `receipt.nonce`, never gating on `receipt.success`. As a result, a message that failed to dispatch on Ethereum (logged with `success: false`) is treated identically to a successful delivery: the relayer is paid `order.fee` and the `PendingOrders` entry is permanently removed.

## Finding Description
The `InboundMessageDispatched` Solidity event and its Rust decode target both carry a `success: bool` field [1](#0-0) . This field is populated straight from the on-chain log during decoding [2](#0-1) .

`submit_delivery_receipt` verifies the proof authenticity via `T::Verifier::verify`, decodes the log into a `DeliveryReceipt`, and passes it straight to `process_delivery_receipt` without inspecting `success` [3](#0-2) .

`process_delivery_receipt` then only validates `receipt.gateway` against `T::GatewayAddress`, resolves the reward account, fetches the `PendingOrder` by `nonce`, unconditionally pays `order.fee` via `T::RewardPayment::register_reward` if `fee > 0`, and unconditionally removes the pending order — `receipt.success` is never read [4](#0-3) . A repository-wide search confirms `success` is used nowhere else in the `outbound-queue-v2` pallet, and the module doc comment describes the intended flow as pay-then-remove with no success gating at all [5](#0-4) . The existing test suite exercises verification-halt scenarios but never exercises `success: false`, confirming the field is functionally dead code in the settlement path.

The verifier (`T::Verifier::verify`) only proves that the log genuinely occurred on Ethereum; it makes no assertion about the dispatch outcome encoded within that log. Thus the only existing guard (proof authenticity) is orthogonal to, and insufficient for, gating settlement on dispatch success.

## Impact Explanation
This breaks the required invariant that message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically. A genuine, correctly proven Ethereum-side dispatch failure (contract revert, gas underestimation by `GasMeter`, etc.) still results in unconditional relayer reward payout (`register_reward`) and permanent removal of the `PendingOrders` entry via `PendingOrders::remove(nonce)`, exactly as if delivery had succeeded. This is an unbacked reward payout paired with irrecoverable loss of the on-chain settlement/tracking record for a failed message, matching the "duplicate settlement or payout" / "theft or unbacked mint or unlock" impact category for bridge reward state.

## Likelihood Explanation
No adversarial behavior is required. Any relayer submitting a real, legitimately-proven Ethereum log with `success: false` — which is a normal, expected occurrence in bridge operation whenever the Gateway's inner dispatch reverts — triggers this path via the public `submit_delivery_receipt` extrinsic. The bug is deterministically reachable by ordinary bridge operation.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only proceed with `T::RewardPayment::register_reward` and `PendingOrders::remove(nonce)` when `success == true`. When `success == false`, avoid the reward payout and either remove the order while emitting a distinct failure event (e.g., `MessageDispatchFailed`), or retain the order for retry/reconciliation instead of silently treating the failure as a successful settlement.

## Proof of Concept
1. `do_process_message` enqueues a message with nonzero `fee`, creating `PendingOrder { nonce, fee, block_number }` in `PendingOrders` [6](#0-5) .
2. The message is delivered to the Ethereum Gateway but the inner dispatch fails at execution time; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer collects the genuine receipt and beacon proof for this real log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the log is authentic); `DeliveryReceipt::try_from` decodes `success: false`.
5. `process_delivery_receipt` checks only `gateway` and `PendingOrders::get(nonce)`, pays `order.fee` to the reward account via `register_reward`, and calls `PendingOrders::remove(nonce)` — identical to the success path, confirming the reward is paid and the record destroyed despite `success == false`.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
