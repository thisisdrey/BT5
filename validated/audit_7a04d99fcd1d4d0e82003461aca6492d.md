### Title
Stale `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries survive `DeleteAccount`, letting a resolved data dependency execute privileged actions against a subsequently recreated account of the same name - ([File: core/store/src/utils/mod.rs, runtime/runtime/src/actions.rs, runtime/runtime/src/lib.rs])

### Summary
`remove_account` only clears `TrieKey::Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData`, never `TrieKey::PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt`. Because these rows are keyed purely by `receiver_id: AccountId` with no per-incarnation nonce, deleting an account that still has an unresolved postponed action receipt and later recreating an account with the same name lets a stale postponed receipt fire against the new account once its outstanding `input_data_ids` are finally delivered.

### Finding Description
`remove_account` (core/store/src/utils/mod.rs:505-575) removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce` and `ContractData` entries, but never issues `state_update.remove` for `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt`: [1](#0-0) [2](#0-1) 

`action_delete_account` (runtime/runtime/src/actions.rs:314-390) calls `remove_account` unconditionally after only checking storage-usage size and gas-key-balance-burn limits - there is no check for outstanding postponed/pending-data state before deletion: [3](#0-2) 

Meanwhile, `process_receipt`'s `Data` branch (runtime/runtime/src/lib.rs:1386-1473) looks up `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` solely by `receiver_id` (the `AccountId` string), with no incarnation/generation identifier tying it to the specific account instance that created it: [4](#0-3) 

Exploit flow:
1. Attacker's factory account creates sub-account `slot.factory.near`.
2. `slot.factory.near`'s own contract issues a self-targeted `ActionReceipt` (e.g. via `promise_and`/`promise_batch_create` to itself) containing a privileged self-action (e.g. `AddKeyAction(FullAccess)`) with two `input_data_ids` that are not yet satisfied. `process_action_receipt` stores this as a `PostponedReceipt` plus `PendingDataCount=2` and two `PostponedReceiptId` entries, all keyed by `receiver_id = "slot.factory.near"`.
3. Before those two data dependencies resolve, `slot.factory.near` self-issues `DeleteAccount`. `action_delete_account` performs no check for pending postponed data and calls `remove_account`, which deletes the account record but leaves the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows in the trie under the same `AccountId` key.
4. The factory later calls `CreateAccount` again for `slot.factory.near`, provisioning it for a new, unrelated tenant.
5. When the two originally pending `DataReceipt`s eventually arrive (their production is entirely under the original attacker's control, since delivering a `Data` receipt does not check whether the receiver account currently exists), `process_receipt`'s `Data` branch decrements `PendingDataCount` to 0, fetches the still-present stale `PostponedReceipt`, and calls `apply_action_receipt` against whatever account presently exists at `slot.factory.near` - the new tenant's account - executing the attacker's embedded action (e.g. adding the attacker's full-access key) without any authorization from the new owner.

No existing check (signature/nonce validation happens only at the original transaction that created the postponed receipt; account-existence checks in `apply_action_receipt` only require *an* account to exist, not that it's the *same* account instance; `DeleteAccountWithLargeState`/`GasKeyBalanceTooHigh` checks are unrelated to postponed-receipt bookkeeping) prevents deleting an account while postponed data is outstanding, nor does anything invalidate stale postponed receipts on account recreation.

### Impact Explanation
This is an authorization-escalation flaw across account lifecycles: an entity that no longer has any claim to an account name (having deleted it) can still inject a privileged, self-authorized action (e.g. `AddKeyAction(FullAccess)`, or similarly `DeployContract`/`Stake`) into a completely different, later tenant's account once that tenant reuses the account name. This maps to "authorization escalation across accounts or promises" and can lead to full account takeover of the new tenant, i.e., theft of any funds subsequently deposited into `slot.factory.near`.

### Likelihood Explanation
The attacker needs only: (1) ability to create and control a factory account and its sub-accounts, (2) ability to deploy/execute an arbitrary WASM contract on the sub-account to construct a self-targeted batched promise with `input_data_ids` under attacker's control, and (3) ability to self-delete that sub-account and later coordinate the factory to recreate the same account name for a new tenant. All of these are ordinary unprivileged operations (deploy contract, sign/submit transactions) with no validator/node access required. The main precondition for real-world impact is a factory/marketplace pattern that reuses deterministic sub-account names for different tenants (common in NEAR "slot" or "rental" account patterns), and the ability for the attacker to control timing of when the pending data receipts resolve relative to account recreation - both of which are attacker-controlled since the attacker authored the original contract logic and can delay finalizing the promised sub-calls.

### Recommendation
Have `remove_account` also remove any pending `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` entries scoped to the deleted `account_id` (iterating the relevant trie prefixes similarly to how access keys and contract data are cleaned up today), and/or forbid `DeleteAccount` from completing while the account still has any outstanding postponed receipts/pending data counts, forcing those receipts to resolve or be explicitly discarded before the account can be deleted.

### Proof of Concept
Integration/test-loop test plan:
1. Deploy a test contract on `slot.factory.near` (created from a factory account) that, in one function call, creates a batched self-promise containing an `AddKeyAction(FullAccess, attacker_pubkey)` with two dependent `input_data_ids` from two separate async calls that have not yet returned.
2. In a subsequent action within the same or next call, have `slot.factory.near` execute `DeleteAccount` (self-receipt, predecessor==receiver) before the two async calls return their `DataReceipt`s.
3. Assert the account no longer exists via `view_account`.
4. Have the factory account issue `CreateAccount` for `slot.factory.near` again (simulating a new tenant), and add an access key belonging to the new tenant.
5. Let the two originally pending async calls complete, generating their `DataReceipt`s targeting `slot.factory.near`.
6. After both `DataReceipt`s are processed, query the recreated `slot.factory.near`'s access key list and assert it contains `attacker_pubkey` with `FullAccess` permission, even though the new tenant never authorized it - demonstrating the authorization-exactness violation.
