### Title
`remove_account` fails to clear `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`/`PromiseYieldReceipt` rows, allowing a deleted account's stale pending self-authorized `AddKey` receipt to fire on the freshly recreated account of the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) only clears `TrieKey::Account`, `TrieKey::ContractCode`, `AccessKey`/gas-key rows, and `ContractData` for a deleted account, but never removes `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, or `TrieKey::PromiseYieldReceipt`/`PromiseYieldStatus` rows keyed by that same `account_id`. The existing regression test `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` (`runtime/runtime/src/tests/apply.rs:4877-4954`) only guards the `ContractCode`/`ReceiptPreparationPipeline` caching path for `FunctionCall`; it does not exercise the receipt-lifecycle columns, so a self-targeted postponed `AddKey` (or `PromiseYield`) receipt left behind by a deleted account survives and can later be delivered onto whatever account gets created under the same `AccountId` string.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account(state_update, account_id)` and then sets `account = None`. `remove_account` (`core/store/src/utils/mod.rs:504-575`) explicitly removes:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- All `AccessKey`/gas-key-nonce rows
- All `ContractData` rows

but has no code path touching `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the yield-id mapping columns, even though these are all listed as account-keyed columns in `core/primitives/src/trie_key.rs:89-102` (`COLUMNS_WITH_ACCOUNT_ID_IN_KEY`).

If the account owner, prior to deleting the account, sent itself an action receipt containing `Action::AddKey` with an unmet `input_data_id` (e.g., via `promise_then`), the runtime's `process_action_receipt` (`runtime/runtime/src/lib.rs:1529+`) stores this receipt as postponed: a `PostponedReceiptId` link plus the receipt body under `TrieKey::PostponedReceipt{ receiver_id: account_id, receipt_id }` (`set_postponed_receipt`, `core/store/src/utils/mod.rs:120-127`). This entry is keyed purely by the `AccountId` string, with no binding to a particular "incarnation" of the account.

When the account is subsequently deleted (`DeleteAccountAction`) and later a new account of the identical name is created (`CreateAccountAction`), the stale postponed row is untouched. When the originally awaited data receipt eventually arrives, `process_receipt` (`runtime/runtime/src/lib.rs:1415-1455`) finds the `PendingDataCount` has reached zero, fetches and removes the postponed receipt, and executes it via `apply_action_receipt` against whatever account currently exists under that name — the newly created one.

Critically, `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) only enforces `actor_id == account_id` for `AddKey`; since the postponed receipt was originally self-targeted (`predecessor_id == receiver_id == old "child"`), `actor_id` trivially equals `account_id` regardless of which incarnation of the account is live, and `check_account_existence` (`actions.rs:787-855`) only requires the account to exist (true post-recreation). Neither check verifies that the account state visible at execution time is the same incarnation for which the receipt was postponed. The `AddKey` (or a similar privileged action) therefore lands on the fresh account, silently granting the old account controller's chosen public key full access to whatever party subsequently recreated the account name.

This is the exact sibling of the already-fixed `ContractCode` staleness bug (guarded by `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`), but for the receipt-lifecycle trie columns that `remove_account` never clears.

### Impact Explanation
This is an authorization-escalation-across-accounts bug: a party that once controlled an account name can plant a "time bomb" postponed `AddKey`/`PromiseYield` receipt, delete the account, and have a privileged action silently execute against whoever recreates that account name later — without that new owner ever authorizing it. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions: the attacker must (1) control the account whose name will later be reused, (2) create a self-targeted action receipt with an unmet data dependency that includes a privileged action (`AddKey`, `DeployContract`, etc.) before deleting the account, and (3) have some third party (or their future self, after transferring ownership of the parent namespace) recreate an account of the exact same name and later trigger/allow the dependency to resolve. All steps are achievable purely through an ordinary user's own transactions (self-calls, promises, delete) with no validator/node privilege required. The scenario is most directly reachable in the same-chunk delete+recreate pattern the codebase already tests for (mirroring `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`), and is fully deterministic and repeatable given the same account-name-reuse setup.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also enumerate and remove all `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, and yield-id-mapping rows for the account being deleted (mirroring the existing access-key/contract-data prefix-iteration removal logic already present in the function), and update `RemoveAccountResult`/storage-usage accounting accordingly.

### Proof of Concept
Extend `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` (`runtime/runtime/src/tests/apply.rs`):
1. Before the `delete` receipt, have `child` send itself an action receipt containing `Action::AddKey` with an `input_data_ids` dependency on a data id that has not yet been received (so it is stored as a `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`).
2. Apply `delete` (self `DeleteAccount`, beneficiary `parent`) and `create_and_call` (parent recreates `child` via `CreateAccount` + `FunctionCall`) in the same or next `apply()` call, exactly as in the cited test.
3. Then submit the corresponding `Data` receipt that satisfies the postponed dependency.
4. Assert: (a) the recreated `child` account now has the attacker's injected public key with `AccessKeyPermission::FullAccess` (via `get_access_key`), proving the stale postponed `AddKey` executed against the fresh account; (b) confirm this is unexpected because `create_and_call`'s actions never included `AddKey`, and no authorization from the new "owner" of `child` was ever given for that key.
