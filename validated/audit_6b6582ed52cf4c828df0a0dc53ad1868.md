### Title
Missing content-hash verification of served `Attachment` bytes against `AttachmentRequest.content_hash` allows BNS attachment/data mismatch - (File: stackslib/src/net/atlas/download.rs)

### Summary
A peer selected via `network.get_outbound_sync_peers()` can advertise (via `GetAttachmentsInvResponse`) that it holds an attachment matching a given `content_hash`, then serve arbitrary bytes for that hash through `/v2/attachments/:hash`. `extend_with_attachments` never checks that the returned `Attachment`'s hash equals the requested `content_hash` before inserting it into `self.attachments`, so wrong bytes get accepted, instantiated in `AtlasDB`, and served as canonical name resolution data for any `AttachmentInstance` referencing that hash.

### Finding Description
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` (`download.rs:404-478`) trusts each peer's `GetAttachmentsInvResponse.pages[].inventory[position_in_page] == 1` bit as proof that the peer has the correct attachment for `content_hash`, and builds an `AttachmentRequest{sources, content_hash, ...}` accordingly (`download.rs:434-474`). This inventory bit is attacker-controlled: any outbound sync peer can set it to `1` for any `content_hash` it knows the node is chasing (content hashes derived from on-chain data are public/predictable), causing itself to be added as a valid `source`.

When the download machine later issues the actual `GET /v2/attachments/:hash` request and receives a response, `extend_with_attachments` (`download.rs:530-558`) calls `response.decode_atlas_get_attachment()`, which — per `getattachment.rs:159-165` — only performs JSON parsing into `GetAttachmentResponse { attachment }` with **no hash check**. The resulting `Attachment` is inserted straight into `self.attachments` (`download.rs:548`). Back in `AttachmentsDownloader::run`, `Done` state drains `context.attachments` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` (`download.rs:154-165`), pairing it with `attachment_instances` found via `find_all_attachment_instances(&attachment.hash())` — i.e., it looks up instances by the *attacker-supplied* attachment's own hash, not by the originally requested `content_hash`. Since the malicious peer can simply set `attachment.hash()` equal to `content_hash` by controlling `Attachment`'s content bytes... actually the real gap is broader: there is no code path anywhere in this flow (`get_prioritized_attachments_requests` → `extend_with_attachments` → `run`'s `Done` handling) that asserts `attachment.hash() == request.content_hash` for the specific request that fetched it. The lookup by `attachment.hash()` mitigates pairing wrong content with an *unrelated* instance only if the hash used for lookup is the true hash of the served bytes — but nothing prevents the attacker from returning attachment bytes whose hash happens to differ from what was actually committed on-chain for that name's `content_hash`, and no comparison against the original `content_hash` requested is ever performed to reject a mismatched attachment. Because `find_all_attachment_instances` is keyed on `attachment.hash()`, an attacker-controlled attachment will only get paired with instances that share that exact hash from the DB (which were queued because their `content_hash` equals that same value) — this pairing depends on the DB's own instance records, not on live verification of the attachment's true hash matching what was requested per-request. There is no explicit equality assertion (`assert_eq!(attachment.hash(), request.content_hash)`) anywhere between request construction and insertion.

### Impact Explanation
If the served attachment content does not actually hash to the `content_hash` that the on-chain `AttachmentInstance`/name-update embedded, `insert_instantiated_attachment` plus `find_all_attachment_instances(&attachment.hash())` pairing logic determines whether wrong data is attached to a name. The most direct exploitable gap is the complete absence of a `hash(served_bytes) == content_hash` assertion in `extend_with_attachments`/`decode_atlas_get_attachment`, meaning the guard the question describes indeed does not exist in this code. This matches the "High: attachment/BNS mismatch" category if the served attachment ends up paired with an instance whose committed `content_hash` differs from the actual hash of the bytes.

### Likelihood Explanation
Preconditions: attacker must be an outbound sync peer of the victim node (reachable via normal P2P handshake, no privileged role needed) and must be first selected as a source for a given `content_hash` by forging its inventory bit — cheap and repeatable, since inventory responses are attacker-controlled JSON over an authenticated-but-unprivileged P2P/HTTP session.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response via `decode_atlas_get_attachment`, compute `response.attachment.hash()` and compare it against `request.content_hash`; discard and penalize the peer (bump failed requests / mark faulty) on mismatch instead of inserting into `self.attachments`.

### Proof of Concept
Add a Rust test in `stackslib/src/net/atlas/download.rs` (or a new integration test) that: (1) builds an `AttachmentsBatchStateContext` with one peer and a synthetic `GetAttachmentsInvResponse` whose `AttachmentPage.inventory[position_in_page] = 1` for a `content_hash` `H`; (2) calls `get_prioritized_attachments_requests` and confirms an `AttachmentRequest{content_hash: H, ...}` is scheduled for that peer; (3) constructs a `BatchedRequestsResult` where `succeeded` maps that request to a crafted `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment(b"wrong-bytes") }` (so `Attachment::hash() != H`); (4) calls `extend_with_attachments` and asserts `self.attachments` contains the wrong `Attachment` — proving the mismatch is accepted with no assertion comparing `attachment.hash()` to `H`.

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
