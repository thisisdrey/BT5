DECIMAL_OF_VI_REWARD is `10^18`. `deltaVi` is accumulated per-cycle as `reward * 10^18 / voteCount` and is stored unboundedly across many cycles (`accumulateWitnessVi`), so over a long span of cycles between a voter's `beginCycle` and `endCycle`, `deltaVi` grows roughly linearly with the number of cycles elapsed. In `computeReward`, the code does `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD).longValue()` — using `.longValue()` instead of `.longValueExact()`. `.longValue()` silently truncates/wraps to the low 64 bits when the `BigInteger` result exceeds `Long` range, exactly analogous to the reported `u256::shlw` bug where non-zero high-order bytes are silently discarded instead of raising an error.

### Title
Silent BigInteger-to-long truncation in vote reward computation (`.longValue()` instead of `.longValueExact()`) - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`, and `VoteRewardUtil.computeReward` all compute `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD).longValue()` [1](#0-0) [2](#0-1) [3](#0-2) . This mirrors the reported bug class exactly: an unvalidated numeric value is transformed into a narrower representation without checking whether the transformation drops significant bits, and no error path exists if it does.

### Finding Description
`deltaVi` is a `BigInteger` accumulated cycle-over-cycle as `reward * DECIMAL_OF_VI_REWARD (10^18) / voteCount`, then persisted and monotonically summed forward for as long as an account keeps voting without withdrawing, via `DelegationStore.accumulateWitnessVi`/`RewardViCalService.accumulateWitnessVi` [4](#0-3) . Because `DECIMAL_OF_VI_REWARD` is `10^18` [5](#0-4) , `deltaVi` for a witness that accumulates rewards over many cycles is unbounded in the number of digits it can grow to (it is stored as raw `BigInteger` bytes with no cap, see `setWitnessVi`/`getWitnessVi`). When `computeReward` later multiplies this large `deltaVi` by a user's `voteCount` (also caller-controlled up to their frozen TRX Power) and divides by `10^18`, the final `BigInteger` result can exceed `Long.MAX_VALUE` if a voter withholds withdrawal across a sufficiently large number of cycles/witnesses combined with a large vote count. Instead of using `longValueExact()` (which is used consistently elsewhere in the same codebase for exactly this reason, e.g. `ResourceProcessor.divideCeilExact`, `RepositoryImpl.usageToBalance`, `ExchangeInjectActuator`), the reward path uses plain `.longValue()`, which per the Java spec discards all but the low-order 64 bits without any exception — silently corrupting (and potentially producing a wrapped negative or otherwise incorrect) `reward` value that is then added to the account's on-chain `allowance` balance via `adjustAllowance` [6](#0-5) .

### Impact Explanation
If `.longValue()` truncation yields an incorrect (wrapped) reward, `adjustAllowance` unconditionally increases the account's `allowance` field, which is later paid out as real TRX balance. A wrapped value could produce a reward far larger than what is economically backed (unbacked balance / inflation), or in principle wrap into a value that still passes the `amount > 0` check while being drastically wrong, letting a voter claim TRX not actually owed to them. This directly implicates the theft-of-funds / unbacked-balance impact category, since `WithdrawBalanceContract`/TVM `withdrawReward` and `unfreezeBalance` code paths (`UnfreezeBalanceProcessor` calling `VoteRewardUtil.withdrawReward`) are reachable by any account holder issuing a standard signed transaction or contract call — no privileged role is required.

### Likelihood Explanation
Reaching the actual overflow requires a voter to accumulate delta-Vi across enough cycles/witnesses and combine with a large enough vote count that the final `BigInteger` product/quotient exceeds `Long.MAX_VALUE` (~9.2×10^18); this is a large but not impossible magnitude given `DECIMAL_OF_VI_REWARD = 10^18` scaling and unbounded cycle accumulation for accounts that never withdraw. This is analogous to how the original PoC required a specifically crafted large `liquidity`/`sqrt_price_diff` input to trigger the truncation — feasible but requiring deliberate long-term setup (e.g., not withdrawing for a very large number of cycles while maximizing vote weight), rather than a single ordinary transaction.

### Recommendation
Replace `.longValue()` with `.longValueExact()` in `MortgageService.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`, and `VoteRewardUtil.computeReward`, and handle the resulting `ArithmeticException` the same way `hardenCalculation()` guards do elsewhere in the codebase (reject/clamp instead of silently proceeding), consistent with the exact-conversion pattern already used in `ResourceProcessor`, `RepositoryImpl`, and `ExchangeInjectActuator`.

### Proof of Concept
Not independently executable from static analysis alone: reproducing the overflow requires simulating many delegation cycles with `DelegationStore`/`RewardViCalService` to grow `deltaVi` past a magnitude where `deltaVi * userVote / 10^18 > Long.MAX_VALUE`, which is not verifiable without running the node's full consensus/reward pipeline. [7](#0-6) 

**Uncertainty note:** I was not able to confirm within static review whether realistic on-chain economic bounds (total TRX supply, max vote count, max cycles before mandatory reward flush) actually permit `deltaVi * userVote` to exceed `Long.MAX_VALUE` in practice — this would need runtime/economic-bound analysis to fully validate exploitability, which is beyond what the indexed code search can confirm.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
