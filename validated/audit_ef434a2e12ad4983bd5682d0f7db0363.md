The QEMU bug class is "repeatedly hot-unplugging a device leaks memory → resource-exhaustion DoS." The Metronome analog is the per-account token list in `Pool`: every first receipt of a deposit token pushes an entry into `depositTokensOfAccount[account]`, entries are only removed when a balance returns to zero, and the combined deposit+debt list is capped at `MAX_TOKENS_PER_USER = 30`. An unprivileged attacker can "hot-plug" entries into a victim's list with dust transfers and never let them be released (the victim can clear them only by explicitly sweeping each token out), permanently blocking the victim's list slots.

### Title
Dust `DepositToken` transfers fill victim's `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, freezing deposits/borrows - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 [1](#0-0) . `Pool.addToDepositTokensOfAccount` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` shared between deposit and debt tokens [2](#0-1) . An attacker can deposit dust of every supported collateral into their own account and `transfer` 1 wei of each msdTOKEN to a victim, permanently occupying up to all 30 slots of the victim's list. Once the cap is reached, any further `addTo*` call reverts with `UserReachedMaxTokens`, so the victim cannot deposit any new collateral type nor open any new debt position.

### Finding Description
Like the QEMU EHCI leak where each hot-unplug permanently leaks a resource, each first-time receipt of an msdTOKEN permanently consumes one of the victim's 30 list slots in `depositTokensOfAccount` (stored in `MappedEnumerableSet.AddressSet` [3](#0-2) ). The attack path is fully public:

1. Attacker calls `DepositToken.deposit(dust, attacker)` for each supported collateral, minting themselves dust msdTOKEN balances.
2. Attacker calls `DepositToken.transfer(victim, 1)` on each msdTOKEN. `_revertIfLocked` only checks the sender's unlocked balance, so dust passes.
3. `_transfer` sees `_recipientBalanceBefore == 0 && amount_ > 0` and calls `pool.addToDepositTokensOfAccount(victim)`, which pushes the token into the victim's set [4](#0-3) .
4. After the victim's `depositTokensOfAccount + debtTokensOfAccount` length hits 30, every subsequent mint (deposit), issue (new debt token), and inbound transfer of a new token reverts inside `onlyIfAdditionWillNotReachMaxTokens` [5](#0-4) .

Removal is only possible via `removeFromDepositTokensOfAccount`, which requires the victim's full balance of that token to leave the account [6](#0-5)  — i.e., the victim must notice and manually sweep each dust token, an opt-in cleanup the attacker forces them to perform (and can immediately re-fill).

### Impact Explanation
Temporary freezing of protocol functionality for the victim: they cannot open new collateral positions, cannot receive any new msdTOKEN (transfers revert), and cannot borrow any new synthetic (debt token additions share the same 30-slot budget). If the victim has an existing position that later needs a different collateral to stay healthy, the blocked deposit path can contribute to liquidation. Cleanup requires the victim to transfer out each dust balance in full, which the attacker can immediately undo with another 1-wei transfer, at negligible cost (dust collateral per token).

### Likelihood Explanation
Fully unprivileged: requires only ERC-20 transfers of legitimately-minted msdTOKENs by the attacker. No privileged role, oracle manipulation, or malicious bridge needed. Cost is bounded by the number of registered deposit tokens (enough distinct tokens must exist to fill 30 slots alongside the victim's debt tokens); pools with several collaterals make partial-to-full starvation cheap. Mitigation exists (victim sweeping dust), which keeps severity at the griefing/temporary-freeze level rather than permanent loss.

### Recommendation
Do not add tokens to `depositTokensOfAccount` on permissionless `transfer`, or enforce a minimum meaningful amount; alternatively decouple the cap accounting so that unsolicited dust cannot consume a victim's slots (e.g., only add on `deposit`/mint, or allow permissionless removal of dust entries by anyone).

### Proof of Concept
```solidity
// Foundry/Hardhat-style sketch on a fork with a live Pool
// assumption: `depositTokens[i]` are registered IDepositToken contracts
function test_fillVictimTokenList() public {
    address victim = makeAddr("victim");
    address[] memory dtokens = pool.getDepositTokens();
    uint256 n = dtokens.length; // attacker fills as many slots as exist

    for (uint256 i; i < n; ++i) {
        IDepositToken dt = IDepositToken(dtokens[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 2);         // dust collateral
        underlying.approve(address(dt), 2);
        dt.deposit(1, attacker);                        // mint 1 wei msdTOKEN
        // ensure slot for attacker is added, then push to victim
        dt.transfer(victim, 1);                         // -> pool.addToDepositTokensOfAccount(victim)
    }

    // victim's deposit list now holds `n` entries they never asked for
    assertEq(pool.getDepositTokensOfAccount(victim).length, n);

    // If n (plus victim's debt tokens) reaches MAX_TOKENS_PER_USER (=30),
    // any further first-time deposit/mint/transfer to victim reverts:
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    vm.prank(someNewDepositor);
    IDepositToken(dtokens[0]).transfer(victim, 1); // or dt.deposit(x, victim)

    // victim can only recover by sweeping each dust balance out entirely
    vm.startPrank(victim);
    for (uint256 i; i < n; ++i) {
        IDepositToken dt = IDepositToken(dtokens[i]);
        dt.transfer(attacker, dt.balanceOf(victim)); // removeFromDepositTokensOfAccount
    }
    vm.stopPrank();
    assertEq(pool.getDepositTokensOfAccount(victim).length, 0);
    // attacker can immediately re-fill with another 1-wei transfer round
}
```
