### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract ABI decoding leading to node OOM/crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Monero report describes `load_from_binary()` trusting an attacker-supplied length field and calling `reserve()`/allocation with that raw value, producing multi-exabyte allocation requests and crashing the node. The analogous pattern exists in java-tron's TVM precompiled-contract ABI helpers, which read a length word directly out of caller-supplied `data`/`words` and immediately allocate a Java array of that size before any bound check against the actual size of the supplied call data.

### Finding Description
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` each read a 32-byte ABI word as the item count and allocate an array of that many elements without first checking it against the real size of the input buffer: [1](#0-0) 

Specifically:
- `extractBytes32Array`: `int len = words[offset].intValueSafe(); byte[][] bytes32Array = new byte[len][];` — no check that `len` is consistent with `words.length`.
- `extractBytesArray` / `extractSigArray`: same pattern, `len` comes straight from `words[offset].intValueSafe()`.

These helpers are invoked from precompiled-contract `execute(byte[] data)` implementations that are reachable by any address issuing a `CALL`/`STATICCALL` to a precompile (e.g. multi-signature / batch verification contracts) — i.e., an unprivileged smart-contract caller fully controls `data`, and therefore controls the length word that drives the allocation. Because `intValueSafe()` can return values up to `Integer.MAX_VALUE`, a crafted payload can request an array of ~2^31 elements. Each element of a `byte[][]` is an object reference (4–8 bytes depending on JVM), so `new byte[2^31-1][]` alone can attempt to allocate several gigabytes to ~16GB before any subsequent bounds-check or exception is thrown, independent of the energy that will eventually be charged for the call.

### Impact Explanation
A remote, unprivileged account can construct and broadcast a transaction that calls a precompiled contract using this decoding path with a malicious length field. The resulting allocation attempt can exhaust heap memory and crash or severely degrade the executing full node (validator/witness/API-serving node), which is a Denial-of-Service against the ability of the node to continue serving/executing transactions — directly analogous to the referenced Monero “exabyte allocation” DoS.

### Likelihood Explanation
Likelihood is high for triggering the code path (any account can send a transaction invoking the vulnerable precompiled contract; ABI encoding of the length word is trivial to control), but I was not able to fully confirm, within the available search budget, whether an energy/gas pre-check bounds `len` before these methods are invoked at every call site, nor which exact precompiled contract(s) (e.g. multi-sign/batch verify) invoke each helper and in what order relative to energy charging. This uncertainty should be resolved by a deeper code walk of the precompile `execute()` implementations that call `extractBytesArray`/`extractBytes32Array`/`extractSigArray` before treating this as confirmed exploitable in production.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate `len` against a sane upper bound derived from the actual `data`/`words` length (e.g., `len` must not exceed `(words.length - offset - 1)` or a hard protocol maximum) and reject/short-circuit with an empty result or exception otherwise, mirroring the bounds check already used elsewhere (`isValidAbiEncoding`) in the same file.

### Proof of Concept
Conceptual PoC: craft a transaction that calls a precompiled contract whose `execute()` path reaches `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, with the ABI word at the expected array-length offset set to `0x7fffffff` (or another large value) while providing only a minimal amount of actual trailing data. This causes `new byte[len][]` to be allocated with `len` far larger than what the truncated `data` could actually contain, exhausting memory. I was unable to fully trace and confirm a concrete top-level precompiled-contract entry point (function selector) using these helpers within the available time; this must be verified against the current precompile dispatch table before treating the PoC as complete.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
