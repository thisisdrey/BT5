### Title
Missing zero-address validation on `new_authority` in `TransferToNewAccount`/`TransferToNewAccountPda` permanently locks migrated account funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The on-chain `transfer_to_new_account`/`transfer_to_new_account_pda` instructions let any account authority migrate their `MarginfiAccount` to a new account under an arbitrary `new_authority`, but the program performs no validation that `new_authority != Pubkey::default()`. This mirrors the `LibOwnable._setAdmin` bug class (setting a critical authority to the zero address with no revert), except here the analog is unprivileged and directly causes fund lockup rather than just breaking admin functions.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` accept `new_authority` as a completely unchecked account: [1](#0-0) [2](#0-1) 

The instruction handler (`transfer_to_new_account_pda`) initializes the new account with `ctx.accounts.new_authority.key()` directly, with zero validation that this value is non-default: [3](#0-2) 

and `initialize_migrated_account` writes it straight into `new_account.authority` via `new_account.initialize(...)`: [4](#0-3) 

Meanwhile, the old account is unconditionally finalized/disabled and pointed at the new account (`migrated_to`), with no reversal path once the transfer completes: [5](#0-4) 

Only the off-chain CLI helper (`p0-cli`) contains a zero-address guard, which does not protect the on-chain program from being invoked directly (e.g. via any other client, integrator, or the CLI's own PDA-transfer command, which has no such check): [6](#0-5) 

Because `authority` on `MarginfiAccount` is later checked via `Signer<'info>` constraints for all fund-moving instructions (deposit/withdraw/borrow/repay/close), and `Pubkey::default()` has no corresponding private key, an account whose `authority` is set to the zero address can never again authorize any operation on it.

### Impact Explanation
If `new_authority` is ever set to `Pubkey::default()` — whether by user error, a buggy or malicious front-end/integrator, or a compromised/misused CPI call from a `third_party_id`-integrated caller — all balances migrated into the new account become permanently inaccessible: the new account cannot be signed for, and the old account is already disabled and irreversibly marked as `migrated_to` the (now-unusable) new account. This is a permanent freeze of the user's deposited/borrowed position value, matching the "permanent lock/freeze" impact criteria.

### Likelihood Explanation
The instruction is reachable by any regular unprivileged user through `transfer_to_new_account` / `transfer_to_new_account_pda`, and `new_authority` is explicitly documented as "completely unchecked" in the account struct comments, confirming the developers were aware no validation exists at the account-constraint level. Direct on-chain callers, third-party integrators using the CPI allowlist (`third_party_id`), or a front-end bug passing a default/zeroed pubkey would all trigger this without any revert, unlike the CLI path which does guard against it.

### Recommendation
Add an explicit check in `transfer_to_new_account_pda` (and the analogous keypair-based `transfer_to_new_account` handler) that `new_authority.key() != Pubkey::default()`, returning `MarginfiError::InvalidAuthority` (or similar) before finalizing the migration and disabling the old account.

### Proof of Concept
1. User holds a `MarginfiAccount` with authority `A` and non-zero deposits.
2. User (or an integrator/front-end acting on their behalf) calls `transfer_to_new_account_pda` with `new_authority = Pubkey::default()`.
3. The instruction succeeds: the new PDA account is initialized with `authority = Pubkey::default()` per `initialize_migrated_account` at [3](#0-2) , and the old account is disabled/finalized via `finalize_migrated_old_account` at [5](#0-4) .
4. No key exists that can produce a valid `Signer` for `Pubkey::default()`, so all subsequent deposit/withdraw/borrow/repay instructions requiring `authority: Signer<'info>` on the new account will fail permanently, and the old account is already disabled — permanently freezing the funds.
