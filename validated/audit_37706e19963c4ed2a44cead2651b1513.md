### Title
Unprivileged dust-transfer griefing fills `depositTokensOfAccount` and permanently blocks a victim's deposits of new collateral types - (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount + depositTokensOfAccount`, reverting with `UserReachedMaxTokens()` whenever a new entry must be added [1](#0-0) [2](#0-1) . `DepositToken` is freely transferable, and every `transfer`/`transferFrom` that gives a recipient a first-time non-zero balance calls `pool.addToDepositTokensOfAccount(recipient_)` [3](#0-2) . An attacker can therefore dust-transfer every registered `DepositToken` to a victim until the account hits the cap; afterward, any victim action that would add a *new* token entry — `DepositToken.deposit`/`_mint` into a collateral the victim doesn't already hold, or `DebtToken.issue`/`mint` for a new synthetic — reverts inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` [4](#0-3) [5](#0-4) . Analogous to CVE-2026-47013's availability-only impact: an unauthenticated network attacker causes a partial DoS of a protocol function.

### Finding Description
- `Pool.addToDepositTokensOfAccount` is `external`, callable by any registered `DepositToken`, and gated only by `onlyIfAdditionWillNotReachMaxTokens` [6](#0-5) .
- `DepositToken._transfer` auto-registers the token on the recipient whenever `recipientBalanceBefore == 0 && amount_ > 0`, with no opt-in, no minimum amount, and no recipient consent [7](#0-6) .
- Attack path: attacker buys/deposits a dust amount of every collateral underlying in a `Pool`, then calls `DepositToken.transfer(victim, 1 wei)` for each `DepositToken` the victim doesn't hold. Once the victim's `debtTokens + depositTokens` count reaches 30, `onlyIfAdditionWillNotReachMaxTokens` reverts [2](#0-1) .
- No modifier blocks this: `_transfer` has no `whenNotPaused`/lock checks on the recipient side, `addToDepositTokensOfAccount` only verifies the caller is a registered deposit token, and `SynthContext`/`Operator` paths are irrelevant since plain `transfer` suffices.

### Impact Explanation
Temporary freezing of funds / partial DoS per account: while saturated, the victim cannot deposit any collateral type they don't already hold and cannot mint any synthetic they don't already have a debt entry for — all such transactions revert. If the victim has an unhealthy position, they are blocked from depositing a *new* collateral type to restore health and can be liquidated while unable to add fresh collateral of a different asset (they can still add more of already-held collaterals). The victim can recover by transferring the dust positions out (each `transfer` that zeroes a balance calls `removeFromDepositTokensOfAccount` [8](#0-7) ), so the freeze is temporary and requires gas and awareness to unwind — matching a Medium, availability-only rating.

### Likelihood Explanation
Cost is bounded: the attacker must acquire a dust balance of each distinct `DepositToken` in the pool (a few wei of each underlying plus deposit fees). Feasibility depends on the deployed pool having enough registered collaterals such that `(number of DepositTokens attacker can push) + (victim's existing entries) >= 30`; `DebtToken` balances cannot be pushed (debt is minted to `_msgSender`'s own position in `issue` [9](#0-8) ), so this works best on pools with many listed collaterals or victims who already hold several tokens. No privileged role, oracle manipulation, or flash loan is required — just ERC20-style transfers.

### Recommendation
Make per-account token-list registration opt-in or attacker-proof, e.g.:
- Only call `addToDepositTokensOfAccount` on mints/deposits (initiated by the owner) rather than on `transfer`/`transferFrom`, or
- Let a recipient "sweep" unsolicited dust entries for free (e.g. allow `removeFromDepositTokensOfAccount` on transfers of tiny amounts), or
- Track a per-account whitelist instead of auto-registration, keeping the enumerable set only for positions the user opened themselves.

### Proof of Concept
Hardhat sketch (fork a deployed `Pool` with its registered `DepositToken`s):

```ts
// fork of mainnet; `pool` and deposit tokens loaded from deployments/mainnet
const victim = alice.address;

// 1) Attacker deposits dust of each underlying to obtain dust msdTOKEN balances
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1);          // attacker holds 1 wei of each msdTOKEN
}

// 2) Push dust to the victim until cap is hit
for (const dt of depositTokens) {
  const count = (await pool.getDepositTokensOfAccount(victim)).length
              + (await pool.getDebtTokensOfAccount(victim)).length;
  if (count >= (await pool.MAX_TOKENS_PER_USER())) break;
  if ((await dt.balanceOf(victim)) == 0) {
    await dt.connect(attacker).transfer(victim, 1); // adds entry via addToDepositTokensOfAccount
  }
}

// 3) Victim tries to deposit a collateral type they don't already hold -> reverts
const newDt = /* a DepositToken victim never held */;
await expect(newDt.connect(alice).deposit(parseEther('1')))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 4) Victim must spend gas transferring each dust token back to unblock themselves
```

Uncertainty noted: the exact number of registered `DepositToken`s per deployed pool wasn't fully enumerated from the artifacts, so on pools with few collaterals the attacker may only be able to fill the list for victims who already hold several tokens; the mechanic itself (unsolicited auto-registration + hard cap) is unconditional in the code.

            balanceOf[sender_] = _senderBalanceBefore - amount_;

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
