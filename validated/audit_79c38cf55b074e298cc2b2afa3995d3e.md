### Title
Unbounded HTTP Response Body Read in `run_http_request` Enables Memory-Exhaustion DoS of the Signer Process - (File: `libsigner/src/http.rs`)

### Summary
`run_http_request()` in `libsigner/src/http.rs` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any header parsing, `Content-Length` validation, or size bound is applied. A remote endpoint that a `stacks-signer` process connects to (the "node" configured via `StackerDBSession::host`) can return an arbitrarily large response body and force the signer to allocate unbounded memory, exactly mirroring the Tekton advisory's `io.ReadAll(resp.Body)`-without-limit pattern.

### Finding Description
`StackerDBSession::rpc_request` in `libsigner/src/session.rs` calls `run_http_request(sock, &session.host, verb, path, content_type, payload)` to fetch StackerDB metadata/chunks over a plain TCP/HTTP connection: [1](#0-0) 

`run_http_request` performs the request and then reads the reply with an unbounded `read_to_end`: [2](#0-1) 

Only *after* the entire response has been buffered into `buf` (of unbounded size) does the code call `decode_http_response` (to parse headers/status) and `decode_http_body` (which does bound chunked-decoding to `MAX_MESSAGE_LEN`): [3](#0-2) 

The only mitigating control is the socket read/write timeout set in `connect_or_reconnect`: [4](#0-3) 

Exactly as in the Tekton HTTP resolver bug, this timeout bounds only the *duration* of the read, not the number of bytes that can be allocated within that duration. A server capable of streaming data at even moderate speed can deliver a payload many times larger than any legitimate StackerDB chunk (StackerDB chunks are capped at ~1MB server-side, per `RPCGetStackerDBChunkRequestHandler`'s own comment) well within the configured timeout, causing `run_http_request`'s `buf` to grow unbounded and the signer process to be OOM-killed.

This breaks the same equality broken in the Tekton CVE: "bytes actually needed for a valid protocol message" vs. "bytes the peer chooses to send," with no `io.LimitReader`/`BoundReader` guard on the raw socket read.

### Impact Explanation
`run_http_request` is the sole request/response transport used by `StackerDBSession` (the client the `stacks-signer` uses to talk to its configured Stacks node RPC endpoint for StackerDB list/get/put operations). Any party able to respond on that connection — e.g., a network-path attacker between the signer and its configured node, or a malicious/compromised endpoint the signer is pointed at — can return an oversized HTTP response and exhaust the signer process's memory, crashing it (CWE-400, matches the CVSS `AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H` availability-only profile of the reported advisory). Because a single `StackerDBSession` is reused across `list_chunks`/`get_chunks`/`put_chunk` calls in the signer's normal operating loop, this is reachable on every routine RPC round-trip, not just a rare code path.

### Likelihood Explanation
The vulnerable code executes unconditionally on every `rpc_request` call before any content-length or status validation, so no special crafting beyond "send more bytes than expected" is required by the responding side. Exploitation only requires occupying the response side of a connection the signer initiates — no signature, private key, or admin privilege is needed.

### Recommendation
Wrap the socket in a bounded reader (the crate already has `stacks_common::util::retry::BoundReader` and `stacks_common::util::chunked_encoding::HttpChunkedTransferReader`, both used elsewhere in this codebase, e.g. `stackslib/src/net/http/error.rs`) before calling `read_to_end`, e.g.:

```rust
let mut bound_fd = BoundReader::from_reader(sock, MAX_MESSAGE_LEN as u64 + 1);
let mut buf = vec![];
bound_fd.read_to_end(&mut buf)?;
if buf.len() as u64 > MAX_MESSAGE_LEN as u64 {
    return Err(RPCError::MalformedResponse("Response too large".into()));
}
```
Apply the cap before any parsing, consistent with the bound already applied in `try_parse_error_response`/`consume_data` elsewhere in the codebase.

### Proof of Concept
1. Configure a `stacks-signer` to point `node_host`/`StackerDBSession::host` at an attacker-controlled TCP listener (or position on-path between the signer and its configured node).
2. Have the signer issue any StackerDB RPC call (`list_chunks`, `get_chunks`, etc.), which invokes `StackerDBSession::rpc_request` → `run_http_request`.
3. From the attacker listener, accept the connection, and stream several GB of arbitrary bytes back as the "HTTP response" (no need to match a valid `Content-Length`/terminate the stream) within the configured socket read timeout.
4. Observe the signer process's memory grow unbounded in `run_http_request`'s `sock.read_to_end(&mut buf)` call until the OS OOM-kills the process, denying signing service.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
