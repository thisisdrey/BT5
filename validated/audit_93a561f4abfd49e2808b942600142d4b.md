### Title
`write-freq` StackerDB write-rate limit is never enforced at chunk storage, only as a client-side fetch throttle — ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The StackerDB control-plane contract configures `write-freq` as the "minimum wall-clock time between writes to the same slot" [1](#0-0) . However, the only function that actually commits a chunk to storage, `StackerDBTx::try_replace_chunk`, never checks `write_freq` at all — it only validates chunk size, slot signer, monotonic version (staleness), and `max_writes` [2](#0-1) . `write_freq` is enforced only as an advisory client-side throttle when *deciding whether to fetch* a chunk during pull-based sync [3](#0-2) , and is explicitly *not* checked when validating pushed or downloaded chunks before they are stored.

### Finding Description
`validate_received_chunk`, which is used both for downloaded chunks and for unsolicited pushes, documents this gap directly: "NOTE: does not check write frequency, since the caller has different ways of doing this" [4](#0-3) . Likewise `handle_unsolicited_StackerDBPushChunk` states "The write frequency is not checked for this chunk. This is because the `ConversationP2P` on which this chunk arrived will have already bandwidth-throttled the remote peer" [5](#0-4) .

The actual write path, `StackerDBTx::try_replace_chunk` → `insert_chunk`, is reached from three surfaces:
- P2P chunk push relay (`process_stacker_db_chunks`) [6](#0-5) 
- The unauthenticated-by-write-freq HTTP `POST /v2/stackerdb/:address/:contract/chunks` endpoint, which calls `tx.try_replace_chunk` directly with no rate check [7](#0-6) 
- Pull-based sync, which does throttle *client-side* via `write_freq.max(1)` before even fetching [8](#0-7) 

None of these paths enforce `write_freq` at the point where the chunk is actually accepted and persisted (`try_replace_chunk`). The generic bandwidth-throttling check in `ConversationP2P::validate_stackerdb_push` bounds only aggregate bytes/sec across all StackerDB traffic from a peer [9](#0-8) , not per-slot write frequency, and does not apply at all to writes submitted through the local HTTP RPC endpoint.

### Impact Explanation
An authorized slot owner (someone with the private key corresponding to a slot's signer, as configured by the StackerDB control contract) can write new chunk versions as fast as the network/RPC layer allows, bounded only by `max_writes` per reward cycle — never by `write_freq`. Because `try_replace_chunk` succeeds, `process_stacker_db_chunks` immediately re-broadcasts every accepted write to the peer's neighbors [10](#0-9) , and those neighbors in turn store and re-broadcast it. This lets a legitimate-but-malicious signer bypass the smart contract's intended replication-rate cap and force network-wide propagation and storage churn at a much higher rate than the StackerDB's control-plane contract intended, for every replica of that StackerDB across the network. This is a form of forged/abusive-but-authenticated data propagating at an un-throttled rate network-wide, exceeding the smart contract's documented invariant that "how often a slot can be written to (in wall-clock time)" is governed by `write-freq` [11](#0-10) .

### Likelihood Explanation
Reaching this requires only a valid slot signer key (a normal, low-privilege participant for the app-specific StackerDB, not a node operator or admin secret), and submission through the standard, publicly reachable `POST /v2/stackerdb/.../chunks` RPC or via P2P push — both unauthenticated at the network layer beyond the per-chunk signature check. `max_writes` bounds total writes per reward cycle but not their rate, so an attacker can front-load all permitted writes in a burst.

### Recommendation
Enforce `write_freq` inside `try_replace_chunk` (or `insert_chunk`) using the stored `write_time` column, rejecting a write if `now < write_time + write_freq`, matching the intent already implemented for the client-side throttle in `sync.rs`. Ensure this check applies uniformly to writes coming from P2P push, pull-sync storage, and the HTTP POST endpoint.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u3600` and `max-writes: u10`.
2. As a valid slot signer, submit 10 chunks with strictly increasing `slot_version` back-to-back via `POST /v2/stackerdb/<addr>/<contract>/chunks`.
3. Observe that all 10 writes succeed immediately (no `TooFrequentSlotWrites`-style rejection is possible from this code path, since `try_replace_chunk` never checks `write_freq`), each triggering a network-wide broadcast, despite `write-freq` mandating at least 3600 seconds between writes to the same slot.

    /// Validate a pushed stackerdb chunk.
    /// Update bandwidth accounting, but forward the stackerdb chunk along if we can accept it.
    /// Possibly return a reply handle for a NACK if we throttle the remote sender
    fn validate_stackerdb_push(
        &mut self,
        network: &PeerNetwork,
        preamble: &Preamble,
        relayers: Vec<RelayData>,
    ) -> Result<Option<ReplyHandleP2P>, net_error> {
        assert!(preamble.payload_len > 1); // don't count 1-byte type prefix

        let local_peer = network.get_local_peer();
        let chain_view = network.get_chain_view();

        if !self.process_relayers(local_peer, preamble, &relayers) {
            warn!(
                "Drop pushed stackerdb chunk -- invalid relayers {:?}",
                &relayers
            );
            self.stats.msgs_err += 1;
            return Err(net_error::InvalidMessage);
        }

        self.stats
            .add_stackerdb_push((preamble.payload_len as u64) - 1);

        if self.connection.options.max_stackerdb_push_bandwidth > 0
            && self.stats.get_stackerdb_push_bandwidth()
                > (self.connection.options.max_stackerdb_push_bandwidth as f64)
        {
            debug!("{:?}: Neighbor {:?} exceeded max stackerdb-push bandwidth of {} bytes/sec (currently at {})", self, &self.to_neighbor_key(), self.connection.options.max_stackerdb_push_bandwidth, self.stats.get_stackerdb_push_bandwidth());
            return self
                .reply_nack(local_peer, chain_view, preamble, NackErrorCodes::Throttled)
                .map(Some);
        }

        Ok(None)
    }
