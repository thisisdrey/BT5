### Title
Dust-deposit spam fills a victim's `depositTokensOfAccount` set up to `MAX_TOKENS_PER_USER`, griefing new deposits, borrows, and token transfers - (File: contracts/Pool.sol)

### Summary
The reported bug class is an unauthenticated, rate-limit-free entry point that an attacker can spam to cause denial of service. The Metronome analog: `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer(to_, amount_)` are permissionless and let any caller grow an arbitrary victim's `depositTokensOfAccount` set. `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens`, reverting with `UserReachedMaxTokens` once the combined debt+deposit token count reaches 30. An unprivileged attacker can dust-fill a victim's set across all whitelisted deposit tokens, blocking the victim from depositing any new collateral type, receiving new deposit tokens, or issuing a new debt token, until the victim manually burns the dust.

### Finding Description
- `DepositToken.deposit` mints to an arbitrary `onBehalfOf_` chosen by the caller and, on first receipt, calls `pool.addToDepositTokensOfAccount(account_)` [1](#0-0) [2](#0-1) 
- `DepositToken._transfer` does the same for the recipient of any transfer [3](#0-2) 
- `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [4](#0-3) [5](#0-4) 
- The attacker only needs dust amounts of each whitelisted underlying (or dust deposit tokens obtained by depositing themselves and transferring). No privileged role, oracle manipulation, or large capital is required — mirroring the report's "spam calls without rate limiting" primitive.

Once the set is full:
- `deposit` of a *new* collateral by/for the victim reverts inside `_mint` → `addToDepositTokensOfAccount` (`UserReachedMaxTokens`).
- `transfer`/`transferFrom` to the victim of a deposit token they don't already hold reverts.
- `DebtToken.issue`/`mint` for a debt token the victim doesn't hold reverts at `addToDebtTokensOfAccount`, blocking new borrowing.
- The victim cannot remove entries without burning the dust balance to exactly zero via `withdraw`/`transfer`, which costs them withdraw fees and may be impossible while a portion of balance is locked by debt (`_revertIfLocked`/`unlockedBalanceOf`) [6](#0-5) .

### Impact Explanation
Temporary freezing/DoS of the victim's account functionality: the victim cannot add new collateral types, receive airdropped/transferred deposit tokens, or open new debt positions, and cleanup requires paying withdraw fees per dust token — and is blocked entirely for locked dust while the account carries debt near its limit. This maps directly to the report's "unauthenticated spam → denial of service" class; the on-chain equivalent of rate limiting (the 30-token cap) is what the spam attack exhausts.

### Likelihood Explanation
Moderate. It requires up to 30 dust deposits across whitelisted collaterals and delivers no profit — pure griefing, so motivated attackers (e.g., to prevent a specific borrower from adding collateral before liquidation, or blocking a SmartFarmingManager rebalance) are the realistic threat. No role or oracle precondition limits it; `onlyIfDepositTokenExists`/`whenNotPaused` are the only gates and are satisfied for supported tokens [7](#0-6) . Note the deployed pool set is itself capped at 30 deposit tokens (`ReachedMaxDepositTokens`), so an attacker can realistically fill most of a victim's quota [8](#0-7) .

### Recommendation
Reject or ignore `onBehalfOf_` deposits to accounts whose token list would reach the cap without their consent (e.g., require `onBehalfOf_ == _msgSender()` or an opt-in mapping), or track per-account lists such that unsolicited dust is cheap to shed. A minimum deposit amount per token would also raise attack cost, analogous to the report's per-origin rate limiting.

### Proof of Concept
Fork test (Hardhat, mainnet fork per `hardhat.config.ts`): for each whitelisted `DepositToken` from `pool.getDepositTokens()`, attacker acquires 1 wei of `underlying`, calls `underlying.approve(depositToken, 1)` and `depositToken.deposit(1, victim)`. After `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30`, assert that `depositToken2.deposit(x, victim)` and `debtToken.issue(...)` on a token not in the victim's list revert with `UserReachedMaxTokens`, and that `depositTokenX.transfer(victim, 1)` reverts. Then demonstrate victim cleanup requires `withdraw`/`transfer` of each dust balance to zero — blocked while `unlockedBalanceOf(victim)` is zero under debt.

        address _msgSender = _msgSender();

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);

        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
