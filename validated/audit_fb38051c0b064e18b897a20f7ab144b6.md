Audit Report

## Title
Unchecked (debug-only) tip payout transfer allows `close_tip` to finalize with fund loss - (File: `substrate/frame/tips/src/lib.rs`)

## Summary
`pallet-tips::close_tip` deletes the tip record from storage and then calls `payout_tip`, whose internal `T::Currency::transfer` calls to the finder and beneficiary are only checked via `debug_assert!`, which compiles to a no-op in production (non-`debug_assertions`) builds. If either transfer fails (e.g., destination account below `ExistentialDeposit`), `payout_tip` still returns `Ok(())`, `Event::TipClosed` is emitted as if payment succeeded, and the `Tips` entry that constituted the only claim to that payout is already gone, permanently preventing recovery.

## Finding Description
`close_tip` removes both `Reasons` and `Tips` entries before attempting payout: [1](#0-0) 

`payout_tip` then performs the actual transfers but only asserts success with `debug_assert!`, guarding neither the finder's-fee transfer nor the beneficiary transfer with real error handling: [2](#0-1) 

The inline comments ("this should go through ... but still we only make a best-effort") confirm this is a deliberate, acknowledged trade-off rather than an oversight, and the pattern is unchanged from upstream Substrate/polkadot-sdk `pallet-tips`. In release (non-debug) builds, `debug_assert!` bodies are compiled out entirely, so a failed `T::Currency::transfer` (for example because the destination account does not exist and `finders_fee` or `payout - finders_fee` is below `ExistentialDeposit` under `Preservation::Preserve`/`KeepAlive`) is silently ignored: `payout_tip` still returns `Ok(())`, and `Event::TipClosed { payout, .. }` is emitted reporting a successful payout. Because `Tips::<T, I>::remove(hash)` already ran in `close_tip` before `payout_tip` is invoked, there is no stored state left to retry or reconcile the failed transfer — the treasury pot's funds remain in the pot, unspent to the intended recipient, with no corresponding claim left in storage.

## Impact Explanation
This is a genuine correctness bug: an unprivileged, publicly-callable extrinsic (`close_tip`, callable by any signed account once the countdown expires) can finalize with a payout event that does not match the actual balance movement, and the sole state record that would let the beneficiary or finder claim their reward is deleted regardless of transfer outcome. This matches the "settle exactly once to the rightful beneficiary and amount" invariant class in the target scope — beneficiary/finder do not receive funds they are entitled to, while the chain's event log and any downstream accounting treat the payout as completed. The severity is bounded by the fact that no attacker gains value; the treasury pot itself does not lose funds (they remain in the pot), and the failure only manifests under the specific edge condition of a sub-ED transfer to a non-existent account, which requires `finders_fee` or the tip remainder to fall below `ExistentialDeposit`.

## Likelihood Explanation
No malicious or privileged actor is required — a normal tip with a small `finders_fee` split (`T::TipFindersFee::get() * payout`) paid to an account that hasn't been created on-chain yet is a plausible, mundane trigger, and `close_tip` can be called by anyone once the countdown elapses. Since `debug_assert!` is compiled out in all production runtime builds, the condition is never actually checked/caught in deployed chains, only in debug/test builds, which matches the report's characterization.

## Recommendation
Replace the `debug_assert!(res.is_ok())` checks in `payout_tip` with real error propagation, or fail the dispatch/keep the `Tips` entry until payout is confirmed successful (e.g., defer `Tips::remove` until after `payout_tip` succeeds, or hold undeliverable amounts in a separate claimable storage item). At minimum, do not remove `Tips` state prior to confirming successful settlement.

## Proof of Concept
1. Configure `pallet-tips` with `pallet-treasury` in a standard (non-`debug_assertions`) runtime build.
2. Arrange a tip whose `finders_fee` share (or `payout - finders_fee`) is below `ExistentialDeposit`, with the destination account not yet existing on-chain.
3. After the countdown, call `close_tip(hash)`.
4. Observe `Tips::remove(hash)` executes first; the subsequent `T::Currency::transfer` to the under-ED account returns `Err`, but the `debug_assert!` is stripped in release mode, so `payout_tip` still returns `Ok(())` and emits `Event::TipClosed { payout, .. }`.
5. Verify the destination account balance is unchanged (transfer did not land) while the `Tips` record — the only claim to that payout — no longer exists.
