### Title
Path traversal in `zipper`/ijar archive extraction via prefix-only containment check - (File: `third_party/ijar/zip_main.cc`)

### Summary
`UnzipProcessor::Process` in `third_party/ijar/zip_main.cc`, the extraction routine used by Bazel's bundled `zipper` tool (`third_party/ijar/zip_main.cc`, built as `@bazel_tools//tools/zip:zipper` and used by build/extraction tooling to unpack zip/jar archives), verifies that an extracted entry stays inside the target output directory using a bare string-prefix comparison instead of enforcing a path-separator boundary. This is the exact bug class described in the external advisory (`PagesRouter` boundary check using string-prefix comparison without a separator boundary): a resolved path that merely shares a same-prefix sibling directory name with the output root passes the containment check and is written outside the intended extraction directory.

### Finding Description
The containment check is: [1](#0-0) 

```
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  ... abort ...
}
```

`path` is built by `concat_path(output_root_, output_file_name)` where `output_file_name` comes directly from the attacker-controlled zip entry filename, and `normalize_path` (`third_party/ijar/platform_utils.cc:125`) lexically canonicalizes the path (collapsing `.`/`..`) without resolving it against the filesystem or checking for a trailing separator boundary: [2](#0-1) 

Because the check is `compare(0, normalized_root.size(), normalized_root)`, it only verifies that `normalized` starts with the same *characters* as `normalized_root` — not that the next character is a directory separator (or end of string). If `output_root_` is e.g. `/home/user/out` and a malicious zip entry is named `../outEVIL/payload`, after concatenation and lexical normalization the resulting path becomes `/home/user/outEVIL/payload`, whose first `strlen("/home/user/out")` characters equal `normalized_root` exactly, so the check spuriously passes even though the write target is a sibling directory (`outEVIL`) fully outside `out`.

This mirrors the reported analog precisely: a hostile, unauthenticated content producer (whoever authored the zip/jar being extracted — e.g. a fetched artifact, or any archive a build rule feeds through the bundled `zipper` binary) can choose entry names that defeat the containment check purely by causing the normalized result to share the literal prefix of the extraction root, without needing any separator after it.

### Impact Explanation
An attacker who controls the contents of a zip/jar archive that gets unpacked via this `zipper`/ijar code path (any build rule or tooling invoking the `zipper x`/extraction path on an externally supplied archive) can write files to a directory adjacent to the intended output directory, escaping the extraction sandbox. This is a containment/path-traversal bypass consistent with CWE-22, potentially allowing overwrite of files outside the intended extraction root on the machine performing the build.

### Likelihood Explanation
Exploitation requires only that: (1) the attacker can supply a zip/jar file (or influence one) that is later extracted by the `zipper` tool, and (2) a sibling directory of the fixed output root exists (or can be created via the traversal itself, since `make_dirs` will create missing directories) whose name begins with the same prefix as the output root's basename. No credentials or additional server compromise is required — this is a pure content/crafted-archive attack, matching the "unprivileged content producer" threat model of the analog advisory. The existing test `third_party/ijar/test/zip_test.sh:test_no_path_traversal` only exercises a straightforward `../..` escape and does not cover the same-prefix-sibling bypass, so the bug is not caught by current tests.

### Recommendation
Change the containment check in `UnzipProcessor::Process` to require a directory-separator boundary (or exact match), e.g.:
```cpp
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0 ||
    (normalized.size() > normalized_root.size() &&
     normalized[normalized_root.size()] != '/')) {
  ... abort ...
}
```
equivalent to the fix pattern already used correctly elsewhere in the codebase, e.g. `_starts_with` in `src/main/starlark/builtins_bzl/common/paths.bzl:301-314` and the `strip_prefix`/`add_prefix` checks in `tools/build_defs/repo/git.bzl:61` and `:101`, both of which explicitly append `/` before calling `startswith` to enforce the separator boundary.

### Proof of Concept
Extend `third_party/ijar/test/zip_test.sh` (alongside the existing `test_no_path_traversal`) with a new archive whose single entry name is crafted so that, after `output_root/../<sibling-with-shared-prefix>/...` concatenation and lexical normalization, the result shares the literal string prefix of `output_root` without a following separator, e.g. build a zip with entry name `../$(basename "$folder")EVIL/pwned` where `$folder` is the extraction output directory:

```bash
function test_prefix_boundary_path_traversal() {
  local folder=$(mktemp -d ${TEST_TMPDIR}/out.XXXXXXXX)
  local sibling="${folder}EVIL"
  # craft a zip whose entry, once "../" is resolved against $folder,
  # lands in $sibling (which shares $folder as a literal prefix)
  # e.g. entry name: "../$(basename ${sibling})/pwned"
  (cd $folder && $ZIPPER x prefix_traversal.jar)
  if [[ -e "${sibling}/pwned" ]]; then
    fail "Path traversal via prefix-only boundary check succeeded"
  fi
}
```
The `AbortIfCompare` guard at `third_party/ijar/zip_main.cc:136` will not trigger for such an entry because `normalized` (`.../outEVIL/pwned`) satisfies `compare(0, len(normalized_root), normalized_root) == 0`, so `write_file` proceeds and writes `pwned` into the sibling directory outside `folder`.
