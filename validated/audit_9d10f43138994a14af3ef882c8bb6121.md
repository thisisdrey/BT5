### Title
Unvalidated attacker-controlled array length in TVM precompiled-contract signature/byte-array extraction helpers causes OutOfMemoryError / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a length value directly from attacker-supplied `DataWord[]` input to the `BatchValidateSign` (address `0x...09`) and `ValidateMultiSign` (address `0x...0a`) precompiled contracts and use it, unvalidated, to size a Java array allocation before any bounds check against the actual size of the supplied call data.

### Finding Description
`extractBytes32Array` computes `len = words[offset].intValueSafe()` and immediately allocates `new byte[len][]` [1](#0-0) . Similarly `extractBytesArray` and `extractSigArray` take `len` from a single attacker-controlled 32-byte word and allocate `new byte[len][]` before iterating `i < len` and indexing further into the `words` array using additional attacker-controlled offsets [2](#0-1) [3](#0-2) .

`DataWord.intValueSafe()` clamps values to a maximum of `Integer.MAX_VALUE` rather than rejecting an oversized declared length, so a caller can set `len` to a very large value (e.g. `0x7fffffff`) directly from calldata passed into a contract call that reaches these precompiles. This is the same bug class as the Pillow `Convert.c` issue referenced in the report: a length/size field taken from untrusted input is passed straight into an allocation/copy routine without validating it against the bounds of the actual buffer supplied.

### Impact Explanation
`new byte[len][]` with `len` near `Integer.MAX_VALUE` immediately attempts to allocate an object-reference array of that size (8 bytes per reference on a 64-bit JVM without compressed oops, or 4 bytes with compressed oops — either way, multi-gigabyte), which throws `OutOfMemoryError`. Unlike checked exceptions, `OutOfMemoryError` is a `Throwable`/`Error`, and unless the specific precompile's `execute()` wraps this call in a broad `catch (Throwable ...)` (as `ECRecover.execute` does at [4](#0-3) ), it can propagate out of transaction execution and destabilize the node process executing the block, matching the "node crash or halt" impact category.

### Likelihood Explanation
Reachability requires locating and reading the `BatchValidateSign`/`ValidateMultiSign` precompiled-contract classes' `execute()` methods (registered at [5](#0-4)  and dispatched at [6](#0-5) ) to confirm whether `execute()` wraps the helper calls in a try/catch that would swallow `OutOfMemoryError`. I was not able to view the body of those two classes within my remaining tool budget (they appear later in the file, past the ranges I retrieved), so I cannot fully confirm whether an exception handler at the call site prevents the crash. This is a real limitation in my verification — the finding is based on the unguarded allocation itself, not a confirmed end-to-end crash trace through the precompile dispatcher.

### Recommendation
Validate any length value extracted from `DataWord` (`words[offset].intValueSafe()`) against a sane upper bound (e.g., the actual number of remaining `words`/bytes available) before using it to size an array, in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`. Reject the precompile call (return `Pair.of(false, ...)`) instead of allocating unbounded arrays.

### Proof of Concept
Not independently reproducible from the index alone: the exact call sites in `BatchValidateSign.execute()` / `ValidateMultiSign.execute()` that invoke these helpers, and whether they catch `Throwable`, could not be located within the available tool calls. Conceptually, a contract calling precompile address `0x...09` or `0x...0a` with calldata where the "signature count" or "bytes-array length" word is set to a very large value (e.g. `0x7fffffff`) would trigger the unguarded `new byte[len][]` allocation in the cited helper methods.
