### Title
Meta-transaction (`DelegateAction`/`NEP-366`/`NEP-611`) signatures lack a chain/network domain separator, enabling cross-network replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The NEP-366/NEP-611 meta-transaction signing scheme hashes `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` under an NEP-number discriminant, but never folds in a chain/genesis identifier. Because NEAR-implicit account IDs are deterministically derived from the raw public key, the same account, key, nonce state, and delegate action can exist on two independent nearcore-based networks (mainnet, testnet, or any other network/fork sharing this code), letting a signed `DelegateAction` be replayed unmodified on the second network.

### Finding Description
A meta-transaction is authorized purely by `SignedDelegateAction::verify()` / `VersionedSignedDelegateAction::verify()`, which check the signature against `DelegateAction::get_nep461_hash()`: [1](#0-0) [2](#0-1) 

The hash is built from a `SignableMessage` that only prefixes an NEP-specific `MessageDiscriminant` (a bare integer identifying NEP-366/611) in front of the borsh-serialized `DelegateAction`/`DelegateActionV2` payload — there is no chain id, genesis hash, or any other network-identifying value mixed into the signed bytes: [3](#0-2) [4](#0-3) 

The `DelegateAction` payload itself only carries `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`: [5](#0-4) 

At apply time, `apply_delegate_action` only checks the signature, `max_block_height`, and that `sender_id` matches the tx receiver; none of these are network-specific: [6](#0-5) 

Crucially, NEAR-implicit accounts are accounts whose ID *is* the hex encoding of the ED25519 public key, so the identical account/key pair can be independently created (via a plain transfer) on any other nearcore-based network: [7](#0-6) [8](#0-7) 

Because the access key's nonce is local per-network state (not globally unique across networks), an attacker (or even an unwitting relayer) who has a valid `SignedDelegateAction`/`VersionedSignedDelegateAction` for such an implicit account on one network can resubmit the exact same bytes wrapped in an outer transaction on any other network where that same implicit account has been created with a matching nonce, and `apply_delegate_action`'s signature check will pass identically — exactly the cross-instance replay pattern described in the report (there, cross-chain reuse of a signed quote digest that omits chain id/contract identity).

### Impact Explanation
A successfully replayed `DelegateAction` causes the relayer's network of choice to execute the sender's authorized actions (e.g. `FunctionCall`, `Transfer`, key management) a second time on a network the signer never intended, executing state transitions/spending funds without a fresh, network-scoped authorization from the signer. This falls under double-spend/replay of a signed authorization across accounts’ nonces on independent networks/instances, matching the intended impact class (replay of a signed authorization).

### Likelihood Explanation
Exploitability requires only that: (1) the victim signs a `DelegateAction`/`DelegateActionV2` for a NEAR-implicit account (a very common practice for wallets/relayers), and (2) the identical account (same derived implicit ID and public key) is separately created and reaches the same nonce/state on a second nearcore network. This is a realistic scenario for relayer-operated meta-transaction infrastructure that serves multiple nearcore-based networks (mainnet/testnet, or other independently-genesised nearcore deployments) with shared signer tooling, and it requires no privileged access, only an ordinary client-issued transaction/meta-transaction.

### Recommendation
Fold a per-network domain separator (e.g. `genesis_hash`/`chain_id`) into the NEP-366/611 signable payload — either as an explicit field on `DelegateAction`/`DelegateActionV2` that is validated at `apply_delegate_action`, or by mixing the genesis hash into `MessageDiscriminant`/`SignableMessage` construction in `core/primitives/src/signable_message.rs`, so that a signature computed for one network's genesis cannot verify against another network's state.

### Proof of Concept
1. Generate an ED25519 keypair; derive the NEAR-implicit account id via `derive_near_implicit_account_id` [7](#0-6) .
2. On Network A, fund that implicit account with a `Transfer` action so it gets created with a `FullAccess` key, per the implicit-account-creation rules [9](#0-8) .
3. Sign a `DelegateAction`/`DelegateActionV2` (e.g. a `Transfer` or `FunctionCall`) from that sender with `nonce`/`max_block_height` valid for Network A, using `SignedDelegateAction::sign`/`VersionedSignedDelegateAction::sign` [1](#0-0) .
4. Independently create/fund the same implicit account (same public key) on Network B so its access-key nonce state matches what the signed delegate action expects.
5. Wrap the identical `SignedDelegateAction` bytes in an outer transaction addressed to a relayer on Network B and submit it; `apply_delegate_action`'s `signed_delegate_action.verify()` check succeeds because the digest never included any network-identifying data [10](#0-9) , causing the delegated actions to execute a second time on Network B without a fresh authorization for that network.

```rust
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,

#[non_exhaustive]
pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum ReadDiscriminantError {
    #[error("does not fit any known categories")]
    UnknownMessageType,
    #[error("NEP {0} does not have a known on-chain use")]
    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum CreateDiscriminantError {
    #[error("nep number {0} is too big")]
    NepTooLarge(u32),
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
```

```rust
pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }
```

```markdown
## Implicit accounts

Implicit accounts work similarly to Bitcoin/Ethereum accounts.
You can reserve an account ID before it's created by generating a corresponding (public, private) key pair locally.
The public key maps to the account ID. The corresponding secret key allows you to use the account once it's created on chain.

### NEAR-implicit account ID

The account ID is a lowercase hex representation of the public key.
An ED25519 public key is 32 bytes long and maps to a 64-character account ID.

Example: a public key in base58 `BGCCDDHfysuuVnaNVtEhhqeT4k9Muyem3Kpgq2U1m9HX` will map to the account ID `98793cd91a3f870fb126f66285808c7e094afcfc4eda8a970f6648cdf0dbd6de`.

### ETH-implicit account ID

The account ID is derived from a Secp256K1 public key using the following formula: `'0x' + keccak256(public_key)[12:32].hex()`.

Example: a public key in base58 `2KFsZcvNUMBfmTp5DTMmguyeQyontXZ2CirPsb21GgPG3KMhwrkRuNiFCdMyRU3R4KbopMpSMXTFQfLoMkrg4HsT` will map to the account ID `0x87b435f1fcb4519306f9b755e274107cc78ac4e3`.

### Implicit account creation

An account with implicit account ID can only be created by sending a transaction/receipt with a single `Transfer` action to the implicit account ID receiver:

- The account will be created with the account ID.
- The account balance will have a transfer balance deposited to it.
- If this is NEAR-implicit account, it will have a new full access key with the ED25519-curve public key of `decode_hex(account_id)` and nonce `(block_height - 1) * MULTIPLIER` (to address an issues discussed [here](https://gov.near.org/t/issue-with-access-key-nonce/749)).
- If this is ETH-implicit account, it will have the [Wallet Contract](#wallet-contract) deployed, which can only be used by the owner of the Secp256K1 private key where `'0x' + keccak256(public_key)[12:32].hex()` matches the account ID.

Implicit account can not be created using `CreateAccount` action to avoid being able to hijack the account without having the corresponding private key.

Once a NEAR-implicit account is created it acts as a regular account until it's deleted.
```
