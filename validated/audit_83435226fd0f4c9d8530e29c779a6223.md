### Title
Users cannot add collateral during pause while liquidations remain active, causing preventable liquidations - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Metronome's two-tier emergency model suspends `DepositToken.deposit()` when the `Pool`/`PoolRegistry` is merely paused (`whenNotPaused`), but keeps `Pool.liquidate()` active until full shutdown (`whenNotShutdown`). A borrower whose position turns unhealthy during a pause cannot top up collateral to restore health, yet any unprivileged liquidator can still seize their collateral. The user loses funds specifically because a protocol-initiated pause blocked their only remaining protective action — the same "paused contract eats the user's grace window" bug class as the Carapace `renewProtection` report.

### Finding Description
The emergency-flag matrix is documented in `docs/emergency-flags.md`: `DepositToken.deposit()` is disabled if `PoolRegistry.paused() || Pool.paused() || !DepositToken.isActive()`, while `Pool.liquidate()`, `DebtToken.repay()`, and `DepositToken.withdraw()` are disabled only on `everythingStopped()` (shutdown). `Pool.paused()` additionally ORs in `_poolRegistry.paused()`, so a registry-level pause blocks deposits across all pools.

In `Pool.liquidate` (`contracts/Pool.sol:537-596`), the only pause-related guard is `whenNotShutdown`:

```solidity
function liquidate(...) external override whenNotShutdown nonReentrant ... {
    ...
    if (_isHealthy) revert PositionIsHealthy();
    ...
    depositToken_.seize(account_, _msgSender, _toLiquidator);
}
```

Meanwhile `DepositToken.deposit()` reverts on `IsPaused` via `Manageable.whenNotPaused` (`contracts/access/Manageable.sol:46-49`, `pool.paused()`). The test suite explicitly confirms the asymmetry: `withdraw` and `flashWithdraw` do not revert when `paused == true`, only when `everythingStopped == true` (`test/DepositToken.test.ts:146-169`), and the docs confirm `deposit` is the paused-only operation.

Scenario:
1. Alice has a debt position near the liquidation threshold; she holds underlying collateral (or vault shares via `VesperGateway`) but no synthetic tokens to call `DebtToken.repay()`.
2. Governor (or a guardian via `shutdown`, or `PoolRegistry.pause`) pauses the pool — a routine emergency action, e.g., in response to an oracle or market incident that simultaneously crashes collateral prices.
3. Alice's position becomes unhealthy. She calls `DepositToken.deposit(amount, alice)` (or `VesperGateway.deposit`) to add collateral — it reverts `IsPaused`.
4. Any liquidator calls `Pool.liquidate(synthetic, alice, amountToRepay, depositToken)` — it passes `whenNotShutdown` and seizes her collateral including the liquidation incentive.
5. The pause is lifted; Alice's collateral is gone even though she was willing and able to cure the position the entire time.

### Impact Explanation
Direct loss of user funds: the seized collateral includes the liquidator incentive (`quoteLiquidateOut` adds `liquidatorIncentive` and `protocolFee` on top of the repaid debt value), so the user loses strictly more than their debt reduction — a loss that would not have occurred had `deposit()` remained callable or had liquidation been paused alongside deposit. This is material during exactly the conditions where pause is most likely to be invoked: market volatility and oracle incidents that push positions underwater.

### Likelihood Explanation
- `pause()` is a designed, single-transaction governor action (`Pauseable.sol:105-108`); `PoolRegistry.pause()` propagates to every pool via `Pool.paused()` (`Pool.sol:608-610`).
- The only mitigation — `DebtToken.repay()` staying live under pause — requires the user to already hold or acquire synthetic tokens; a user holding only collateral has no path to save the position.
- No deadline extension, snapshot, or health-check exemption exists: `liquidate` re-evaluates `debtPositionOf` at call time and does not account for the paused deposit window.
- The flaw requires a governor/guardian pause as precondition (same precondition as the source report), which limits likelihood but is a normal protocol operation rather than adversarial privilege.

### Recommendation
Align the tiers so liquidation cannot run while the cure path is blocked. Options:
- Gate `Pool.liquidate` with `whenNotPaused` (or a dedicated liquidation flag) instead of only `whenNotShutdown`, or
- Keep `DepositToken.deposit` callable while paused for existing positions (e.g., allow deposits that improve an account's health factor), or
- Track pause duration and require positions that became unhealthy *during* a pause to be granted a grace window after unpause before they are liquidatable.

### Proof of Concept
Hardhat/fork outline against the deployed Base/Optimism configuration:

```ts
// 1. Setup: alice deposits collateral, issues synth debt near threshold.
await depositToken.connect(alice).deposit(collateralAmount, alice.address);
await debtToken.issue(debtAmount, alice.address); // via pool

// 2. Price drops (or oracle update) -> position unhealthy.
await masterOracle.setPrice(underlying, lowerPrice);
const [healthy] = await pool.debtPositionOf(alice.address);
expect(healthy).to.be.false;

// 3. Governor pauses (or PoolRegistry.pause()).
await pool.connect(governor).pause();

// 4. Alice's cure attempt is blocked.
await expect(
  depositToken.connect(alice).deposit(moreCollateral, alice.address)
).to.be.revertedWithCustomError(depositToken, 'IsPaused');

// 5. Liquidator still seizes collateral while pause is active.
const seizedBefore = await depositToken.balanceOf(alice.address);
await pool.connect(liquidator).liquidate(synthetic, alice.address, repayAmt, depositToken.address);
expect(await depositToken.balanceOf(alice.address)).to.be.lt(seizedBefore);
// Alice lost collateral + liquidation incentive despite being willing to top up.
```

A runnable test exists as a base: `test/DepositToken.test.ts` already demonstrates `deposit` reverting under `paused == true` while liquidation-side functions only check `everythingStopped`.
