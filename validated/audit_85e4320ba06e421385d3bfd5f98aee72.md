### Title
`VesperGateway.deposit()` will always revert if the Vesper pool's underlying asset is a fee-on-transfer ERC20 token - ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol))

### Summary
`VesperGateway.deposit()` assumes the full `amount_` of `underlying` is credited to the gateway after `safeTransferFrom`, then approves and calls `vToken_.deposit(amount_)` with the un-adjusted amount. For a fee-on-transfer underlying, the gateway holds less than `amount_`, and the VPool's internal `transferFrom(gateway, amount_)` reverts — so the function always reverts. This is the exact analog of the Blueberry `doPutCollateral`/`werc20.mint` issue: the caller trusts the nominal `amount_` instead of the actual balance delta.

### Finding Description
The flow in `VesperGateway.deposit` is:

```solidity
// 1. Get `underlying` asset
IERC20 _underlying = IERC20(vToken_.token());
_underlying.safeTransferFrom(_msgSender, address(this), amount_);   // no balance delta

// 2. Deposit `underlying` to `VPool`
_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);                                          // uses nominal amount_
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
``` [1](#0-0) 

With a fee-on-transfer `underlying` (e.g., a token that skims `f` on every transfer), `safeTransferFrom` credits the gateway with `amount_ - f`. `vToken_.deposit(amount_)` then makes the VPool pull the full `amount_` from the gateway, which fails with an insufficient-balance revert. Even if the VPool pulled only the received amount, the minted share count would still be computed against the wrong nominal value depending on the pool's internal accounting. Note the asymmetry: the code already uses the balance-delta pattern for `vToken` shares (`_vTokenAmount`) and for the `underlying` on `withdraw`, but not for `underlying` on `deposit`.

The rest of the codebase is consistent about this: `DepositToken.deposit` measures `_underlying.balanceOf(_treasury)` before/after the pull [2](#0-1) , and `SmartFarmingManager._safeTransferFrom` returns the actual transferred delta [3](#0-2) . `VesperGateway.deposit` is the one surface that skips the delta check on the inbound pull, mirroring the original report where `werc20.mint` handled FoT correctly but the caller ignored the actual minted amount.

### Impact Explanation
Any Vesper pool whose `token()` underlying is a fee-on-transfer ERC20 cannot be used through `VesperGateway.deposit` — every call reverts, permanently bricking that deposit path for the collateral. Users can still deposit the vToken shares directly via `DepositToken.deposit` (which handles FoT), so funds are not lost, but the gateway's advertised convenience path is dead for such collaterals, matching the original Medium finding's "always revert" impact.

### Likelihood Explanation
Requires a registered Pool plus a whitelisted `DepositToken` for a `vToken_` whose `token()` charges a transfer fee. `vToken_` is caller-supplied but constrained: `pool_.depositTokenOf(vToken_)` must return an existing deposit token or step 3 reverts with `CollateralIsInexistent` [4](#0-3) . FoT tokens are rare but real (e.g., USDT historically toggleable, various taxed tokens), and the protocol explicitly supports FoT collaterals elsewhere (see the FoT test in `DepositToken.test.ts`) [5](#0-4) . No attacker needed — any honest user triggers the revert.

### Recommendation
Measure the actual amount received before depositing into the VPool:

```diff
  IERC20 _underlying = IERC20(vToken_.token());
- _underlying.safeTransferFrom(_msgSender, address(this), amount_);
+ uint256 _balanceBeforeUnderlying = _underlying.balanceOf(address(this));
+ _underlying.safeTransferFrom(_msgSender, address(this), amount_);
+ amount_ = _underlying.balanceOf(address(this)) - _balanceBeforeUnderlying;
```

### Proof of Concept
Hardhat test sketch (mock `VPool` with a fee-on-transfer `underlying`, registered via `PoolRegistryMock`/`PoolMock` as in existing `VesperGateway` tests):

```typescript
// given: underlying charges a 10% transfer fee
await underlying.updateFee(parseEther('0.1'))          // same FoT mock pattern as DepositToken.test.ts
await underlying.mint(alice.address, amount)
await underlying.connect(alice).approve(vesperGateway.address, amount)
await poolMock.depositTokenOf.returns(depositToken.address) // whenCalledWith(vToken.address)
await poolRegistryMock.isPoolRegistered.returns(true)

// when
const tx = vesperGateway.connect(alice).deposit(pool.address, vToken.address, amount)

// then
// VPool.deposit pulls `amount` from the gateway, which only received `amount * 0.9`
await expect(tx).to.be.reverted // ERC20: transfer amount exceeds balance inside vPool.deposit
```

The gateway receives `0.9 * amount` of underlying [6](#0-5)  but the VPool attempts `transferFrom(gateway, amount)` [7](#0-6) , so the call always reverts for fee-on-transfer underlyings.
