### Title
Dust-transfer griefing fills a victim's per-account token list, causing `UserReachedMaxTokens` reverts that block deposits, transfers-in, and leverage operations - (File: contracts/Pool.sol)

### Summary
`Pool` tracks every deposit/debt token an account has ever interacted with in a `MappedEnumerableSet` capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from 0 to non-zero (`contracts/DepositToken.sol:517-520`), and `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the set is full. An unprivileged EOA can therefore `transfer` 1 wei of each existing msdTOKEN to any victim address, permanently occupying all 30 slots of the victim's account list.

### Finding Description
- `DepositToken.transfer`/`transferFrom` are public entry points gated only by `_revertIfLocked` on the sender (`contracts/DepositToken.sol:348-376`). There is no minimum amount and no opt-in on the recipient side.
- On first receipt of each token, `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` (`contracts/DepositToken.sol:517-520`). The same hook fires on `deposit(..., onBehalfOf_)` via `_mint` (`contracts/DepositToken.sol:485-488`), so `seize`, deposits on behalf, and SmartFarmingManager flows all hit the same cap.
- `Pool.addToDepositTokensOfAccount` reverts `UserReachedMaxTokens` when `depositTokensOfAccount.length(account_) >= 30` (error declared at `contracts/Pool.sol:32`, cap at `contracts/Pool.sol:79`).
- After the attack, any action that would add a *new* token type to the victim's list reverts:
  - `DepositToken.deposit(amount_, victim)` for any collateral the victim does not already hold
  - Incoming `transfer`/`transferFrom`/`seize` of a new msdTOKEN to the victim
  - `SmartFarmingManager.leverage`/zap flows that mint a new deposit token to the victim
- The corresponding debt-token side has the same pattern (`addToDebtTokensOfAccount`/`removeFromDebtTokensOfAccount`, `contracts/Pool.sol:618-622`), though an attacker cannot push debt tokens to a victim directly.
- Analogous to CVE-2025-13751 (unprivileged user triggers an error path causing denial of service): a single unprivileged transaction batch permanently degrades another user's account functionality until manually remediated.

### Impact Explanation
Denial of service / temporary freezing of funds. A victim whose account list is full cannot deposit *new* collateral types and cannot receive transfers of new msdTOKENs. For a leveraged borrower approaching liquidation, blocking the ability to top-up with a different collateral asset can force an otherwise avoidable liquidation (`Pool.liquidate` seizes collateral plus protocol fee, `contracts/Pool.sol:581-595`). The freeze is not permanent in the strict sense — a slot is released when the corresponding balance reaches zero (`removeFromDepositTokensOfAccount`, called from `_transfer`/`_burn`), so the victim can clear dusted slots by transferring or withdrawing the dust — but the victim may not know which tokens occupy slots, pays gas and withdraw fees to remediate, and can be re-griefed for the attacker's dust cost.

### Likelihood Explanation
High feasibility, moderate realized impact. The attack requires only holding ≥1 wei of up to 30 msdTOKENs (acquirable by depositing dust or receiving dust), then calling `DepositToken.transfer(victim, 1)` for each token — no privileged role, no oracle manipulation, no reentrancy. Cost is bounded by the underlying dust plus gas. The constraint is that `MAX_TOKENS_PER_USER` must actually be reachable, i.e., the pool must list enough deposit tokens, or the attacker must combine deposit-token and debt-token entries; on pools with few listed collaterals the attack degrades to partial slot-filling and may be infeasible. Timing value is highest when front-running a victim's defensive deposit during liquidation.

### Recommendation
- Require a minimum first-deposit/transfer amount (e.g., dust threshold) before registering a token in the per-account list, or maintain the list only for tokens minted via `deposit` rather than arbitrary transfers.
- Alternatively, make `addToDepositTokensOfAccount` silently no-op (or evict zero-dust entries) instead of reverting when the cap is reached, so recipient-side accounting cannot brick inbound transfers.
- Consider tracking "registered" tokens only for accounts that opted in (deposit/mint), and compute `debtPositionOf` over held balances rather than the enumerable set.

### Proof of Concept
Foundry fork sketch (mainnet pool):

```solidity
// test/foundry/MaxTokensGriefing.t.sol
function test_dustGriefingBlocksNewDeposits() public {
    IPool pool = IPool(MAINNET_POOL1);
    address victim = makeAddr("victim");

    // victim legitimately deposits WETH (slot 1)
    deal(WETH, victim, 10 ether);
    vm.startPrank(victim);
    IERC20(WETH).approve(address(wethDepositToken), 10 ether);
    wethDepositToken.deposit(10 ether, victim);
    vm.stopPrank();

    // attacker dusts every other listed deposit token to the victim
    IDepositToken[] memory tokens = pool.getDepositTokens();
    for (uint256 i; i < tokens.length && count(pool, victim) < 30; ++i) {
        if (tokens[i] == wethDepositToken) continue;
        address u = address(tokens[i].underlying());
        deal(u, attacker, 1 ether);
        IERC20(u).approve(address(tokens[i]), 1 ether);
        tokens[i].deposit(1, attacker);            // acquire 1 wei msdTOKEN
        tokens[i].transfer(victim, 1);             // fills victim's list
    }
    assertEq(count(pool, victim), 30);

    // victim now cannot deposit a new collateral type
    deal(DAI, victim, 1000 ether);
    vm.startPrank(victim);
    IERC20(DAI).approve(address(daiDepositToken), 1000 ether);
    vm.expectRevert(UserReachedMaxTokens.selector);
    daiDepositToken.deposit(1000 ether, victim);   // reverts -> DoS
    vm.stopPrank();
}
```

Uncertainty I could not fully verify in the remaining context: the exact body of `addToDepositTokensOfAccount`/`debtTokensOfAccount.length` check ordering (whether the cap is enforced on the combined set or per-type set), and whether deployed pools list enough deposit tokens for the full 30-slot fill — the finding is strongest on pools with many collaterals and weakest (partial) where few are listed.
