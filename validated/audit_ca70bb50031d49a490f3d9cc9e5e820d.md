### Title
NEP-245/IMT fee bypass via per-`TokenId` `amount<=1` exemption split across many sub-token-ids - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::execute_intent` computes and collects fees independently for each `TokenId` key in the diff, using `Self::token_fee(token_id, amount, protocol_fee)` on the per-key `amount = delta.unsigned_abs()`. For `Nep245`/`Imt` token types, `token_fee` returns `Pips::ZERO` whenever that per-`TokenId` `amount <= 1`. Because a single NEP-245 contract can expose unbounded distinct `mt_token_id`s, an attacker can decompose one large logical transfer into many `TokenId`s each with `delta == -1`, so every leg individually qualifies for the zero-fee exemption while the aggregate value moved is arbitrary.

### Finding Description
The binding that should hold is:
`fee_collected_for_contract_C == Pips::fee_ceil(protocol_fee, total_negative_volume_on_C)`
for the whole batch of intents touching NEP-245/IMT contract `C`.

What the code actually computes, per `TokenDiff::execute_intent`:
```
for (token_id, delta) in &self.diff {
    ...
    if *delta < 0 {
        let amount = delta.unsigned_abs();
        let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
        fees_collected.add(token_id.clone(), fee)...
    }
}
``` [1](#0-0) 

and `token_fee`:
```
TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
``` [2](#0-1) 

The fee/zero-fee decision is keyed on the **individual `TokenId`'s** delta magnitude, not on the aggregate volume moved for the underlying MT contract. `Nep245TokenId` is `{contract_id, mt_token_id: String}` and is unbounded in the number of distinct `mt_token_id`s per `contract_id` [3](#0-2) . Nothing in `internal_apply_deltas`, `Amounts::add`, or the fee loop aggregates deltas across distinct `TokenId`s belonging to the same NEP-245 contract before applying `token_fee`.

Exploit flow:
1. Attacker A and colluding Attacker B pre-provision balances across `N` distinct `mt_token_id`s (`id_1..id_N`) of the same NEP-245 contract `C`, each holding balance 1 on the paying side.
2. Attacker B submits (or the matched counter-leg is submitted) a `TokenDiff` where instead of one leg `{C:id_x: -N}` (which would trigger `amount > 1` and a nonzero fee), it is expressed as `N` separate legs `{C:id_1: -1, C:id_2: -1, ..., C:id_N: -1}`.
3. For every leg, `amount == 1`, so `token_fee` returns `Pips::ZERO`, and `fee_ceil(0, 1) == 0` for all `N` legs.
4. `fees_collected` stays empty/zero for the entire NEP-245 leg of the trade regardless of `N`, while the counterparty's matching positive legs (`token_out`, not fee-bearing by design) complete the two-sided trade.
5. `execute_intents` nets both `TokenDiff`s via `internal_apply_deltas`, the trade settles fully, and `fee_collector`'s balance for contract `C`'s tokens is unaffected — `0` instead of `Pips::fee_ceil(fee, N)`.

None of the existing guards (`MultiPayload::verify`, nonce/lock checks, `assert_one_yocto`, `#[private]`/`#[pause]`, `access_control_any`) address this because the transaction is fully valid, signed, and correctly netted — the flaw is purely in fee accounting granularity, not authorization or balance integrity.

### Impact Explanation
Protocol fees are bypassed on the NEP-245 (and identically-structured IMT) leg of a fully executed, balance-neutral trade. This is a direct "protocol fees bypassed" case, explicitly listed as Critical impact. Any two colluding (or even a single account acting as both parties across separate signed intents/self-trades where applicable) accounts holding many distinct sub-token-ids of a NEP-245 contract can apply this to any transfer size by simply fragmenting the transferred quantity into `amount == 1` chunks across unique `mt_token_id`s, at essentially zero marginal cost to the attacker beyond needing that many distinct token ids allocated. This is repeatable per trade, per NEP-245 contract, and scales to arbitrary aggregate volume with no upper bound on lost fee revenue for the `fee_collector`.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: an attacker needs (a) an NEP-245 (or IMT) contract with many distinct `mt_token_id`s (which the attacker can define themselves if they deploy/control the MT contract, or simply choose to hold many pre-existing distinct ids), and (b) balances split thinly (amount=1) across those ids in the Verifier. Constructing `N` legs in a single `TokenDiff.diff: BTreeMap<TokenId, i128>` is a normal, unprivileged, well-formed intent — no special role, relayer key, or DAO permission required. The only cost is the intent payload size / gas for enumerating `N` map entries, which is bounded by ordinary transaction limits but easily supports meaningful `N` (hundreds/thousands), making the bypass practical for real-value trades.

### Recommendation
Aggregate NEP-245/IMT deltas by `contract_id` (not by full `TokenId` including `mt_token_id`) before applying the `amount > 1` fee-exemption test in `token_fee`/`execute_intent`, so that the exemption is evaluated against total per-contract negative volume rather than per-sub-token-id volume. Alternatively, remove or tighten the `amount <= 1` exemption for `Nep245`/`Imt` so it only applies when the *entire* `TokenDiff`'s legs for a given contract sum to `<= 1`, or require the exemption to be evaluated on the total absolute value transferred per contract across the whole diff/batch.

This reproduces the divergence between the intended binding `fee_collected == Pips::fee_ceil(fee, total_negative_volume)` and the actual per-`TokenId` computation that yields `0`.
