### Title
Unbounded `DelegatedResourceAccountIndex` prefix-scan lets an attacker cheaply build a huge delegate index that causes CPU/memory-heavy full-DB scans on every `GetDelegatedResourceAccountIndex(V2)` query - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
This is the same bug class as the VotingEscrow `MAX_DELEGATES` finding: an on-chain, permissionless action (broadcasting `DelegateResourceContract`/`FreezeBalanceContract` delegations) can grow an unbounded per-address list with no cap analogous to `MAX_DELEGATES`, and a later operation that must walk the *entire* list becomes O(n) with no bound, eventually exceeding a resource budget. In java-tron the unbounded structure is the `DelegatedResourceAccountIndex` "to/from" account list, and the O(n) walk is `DelegatedResourceAccountIndexStore.getWithPrefix()`, invoked by the read-only wallet RPC/HTTP endpoints `GetDelegatedResourceAccountIndex` and `GetDelegatedResourceAccountIndexV2`.

### Finding Description
Any account can delegate a tiny amount of frozen bandwidth/energy to an arbitrary number of distinct receiver addresses via `DelegateResourceActuator`/`FreezeBalanceActuator`. Each delegation writes new index entries keyed by `FROM_PREFIX|V2_FROM_PREFIX + address` and `TO_PREFIX|V2_TO_PREFIX + address`: [1](#0-0) 

Nothing bounds the number of distinct receiver/sender pairs an address can accumulate — unlike `VoteWitnessContract`, which is capped by `MAX_VOTE_NUMBER` (30): [2](#0-1) 

or `UnfreezeBalanceV2Contract`, capped by `UNFREEZE_MAX_TIMES` (32): [3](#0-2) 

When any client — including an unauthenticated HTTP/gRPC caller — queries the delegate index for an address, `getIndex()`/`getV2Index()` call `getWithPrefix()`, which performs **two unbounded prefix scans** over the entire key-space for that address and materializes/sorts every match in memory: [4](#0-3) 

`prefixQuery()` itself has no limit parameter (contrast with `getKeysNext(key, limit)`/`getNext(key, limit)` elsewhere in the same class, which are properly bounded): [5](#0-4) 

and the `Chainbase` layer additionally merges root-DB results with an in-memory snapshot scan that iterates every pending snapshot layer with a linear filter: [6](#0-5) [7](#0-6) 

This is directly reachable by an anonymous API client through: [8](#0-7) 

exposed via HTTP servlets (`/wallet/getdelegatedresourceaccountindex`, `/wallet/getdelegatedresourceaccountindexv2`): [9](#0-8) 

and gRPC (`GetDelegatedResourceAccountIndex`, `GetDelegatedResourceAccountIndexV2`): [10](#0-9) 

### Impact Explanation
An attacker can, at negligible cost (delegating tiny frozen balances, e.g. 1 sun, to tens/hundreds of thousands of freshly generated receiver addresses, or having many addresses each delegate to one victim), inflate the `to`/`from` index of a target address to an arbitrarily large size with no protocol-level ceiling analogous to `MAX_VOTE_NUMBER`/`UNFREEZE_MAX_TIMES`. Any subsequent unauthenticated query for that address's delegated-resource index (`GetDelegatedResourceAccountIndex[V2]` via HTTP or gRPC) forces the node to run an unbounded RocksDB prefix scan plus an in-memory `HashMap`/list build and sort over the full result set, repeated for both the "to" and "from" prefixes and merged against every open snapshot layer. Because this is a read/query path (not consensus-critical), it does not directly corrupt state, but it lets an unprivileged caller impose disproportionate CPU/memory cost on a full/solidity node on a query that legitimate clients (wallets, explorers) routinely invoke, degrading or denying that API to other callers — this matches the "API the node can no longer serve" acceptance bar, and is structurally the same "hardcoded/absent bound on delegate list size leads to a DOS" pattern as the original VotingEscrow `MAX_DELEGATES` report, just manifesting as a query-time resource-exhaustion issue rather than a contract-call gas-limit revert.

### Likelihood Explanation
Likelihood is moderate-to-high: creating many distinct delegate relationships requires only ordinary `DelegateResourceContract`/`FreezeBalanceContract` transactions from an unprivileged account (no special permission needed), and the transaction fee cost scales roughly linearly with the number of relationships, which is cheap on TRON compared to the amplification achieved on the read path. Triggering the expensive query afterward requires zero authentication or special privilege — it's a public HTTP/gRPC endpoint. The main uncertainty is the precise number of entries needed to produce a materially harmful CPU/memory spike on a given node's hardware; this was not empirically benchmarked in this analysis (unlike the original report, which measured concrete gas figures), so the severity would benefit from a Proof-of-Concept load test to confirm real-world resource-exhaustion thresholds and any existing operational mitigations (e.g., `RateLimiterServlet`, discussed below).

### Recommendation
- Add a hard cap on the number of distinct delegate relationships (`toAccounts`/`fromAccounts`) an address may accumulate, enforced in `DelegateResourceActuator`/`FreezeBalanceActuator` validation (mirroring `MAX_VOTE_NUMBER`/`UNFREEZE_MAX_TIMES`).
- Bound `getWithPrefix()`/`prefixQuery()` with an explicit result-count limit (reusing the existing `getKeysNext`/`getNext(key, limit)` machinery) and support pagination in the `GetDelegatedResourceAccountIndex[V2]` API contract instead of returning the full unbounded list in one response.
- Consider rate-limiting or requiring a maximum page size for these public query endpoints at the servlet/gRPC layer.

### Proof of Concept
Not independently executed in this analysis (no code-execution access). Conceptually:
1. From a funded but otherwise unprivileged account, freeze a minimal balance and repeatedly submit `DelegateResourceContract` transactions delegating a minimal amount to N freshly generated receiver addresses (or, conversely, have N distinct senders delegate to a single victim address), building `toAccounts`/`fromAccounts` lists with tens of thousands of entries — there is no on-chain limit analogous to `MAX_VOTE_NUMBER`/`UNFREEZE_MAX_TIMES` preventing this.
2. Call `wallet/getdelegatedresourceaccountindexv2` (HTTP) or `GetDelegatedResourceAccountIndexV2` (gRPC) for that address and measure node CPU/latency versus a baseline address with few delegations, confirming that response time/resource usage scales with N with no server-side cap.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public List<byte[]> getKeysNext(byte[] key, long limit) {
    if (limit <= 0) {
      return new ArrayList<>();
    }
    resetDbLock.readLock().lock();
    try (final ReadOptions readOptions = getReadOptions();
         final RocksIterator iter = getRocksIterator(readOptions)) {
      List<byte[]> result = new ArrayList<>();
      long i = 0;
      for (iter.seek(key); iter.isValid() && i < limit; iter.next(), i++) {
        result.add(iter.key());
      }
      return result;
    } finally {
      resetDbLock.readLock().unlock();
    }
  }

  public Map<byte[], byte[]> getNext(byte[] key, long limit) {
    if (limit <= 0) {
      return Collections.emptyMap();
    }
    resetDbLock.readLock().lock();
    try (final ReadOptions readOptions = getReadOptions();
         final RocksIterator iter = getRocksIterator(readOptions)) {
      Map<byte[], byte[]> result = new HashMap<>();
      long i = 0;
      for (iter.seek(key); iter.isValid() && i < limit; iter.next(), i++) {
        result.put(iter.key(), iter.value());
      }
      return result;
    } finally {
      resetDbLock.readLock().unlock();
    }
  }

  @Override
  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    resetDbLock.readLock().lock();
    try (final ReadOptions readOptions = getReadOptions();
         final RocksIterator iterator = getRocksIterator(readOptions)) {
      Map<WrappedByteArray, byte[]> result = new HashMap<>();
      for (iterator.seek(key); iterator.isValid(); iterator.next()) {
        if (Bytes.indexOf(iterator.key(), key) == 0) {
          result.put(WrappedByteArray.of(iterator.key()), iterator.value());
        } else {
          return result;
        }
      }
      return result;
    } finally {
      resetDbLock.readLock().unlock();
    }
  }

  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    Map<WrappedByteArray, byte[]> result = prefixQueryRoot(key);
    Map<WrappedByteArray, byte[]>  snapshot = prefixQuerySnapshot(key);
    result.putAll(snapshot);
    result.entrySet().removeIf(e -> e.getValue() == null);
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      result = ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    }
    return result;
  }
