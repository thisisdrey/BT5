### Title
Unbounded, unauthenticated storage growth of the `attachments` (instantiated) table via unverified attachment content from a peer - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts the `Attachment` payload from any peer's `GET /v2/attachments/<hash>` response without checking that `attachment.hash()` equals the requested `content_hash`. In the `Done` branch of `AttachmentsBatchStateMachine::try_proceed`, every attachment collected this way is unconditionally persisted via `insert_instantiated_attachment`, which — unlike `insert_uninstantiated_attachment` — has no capacity cap and no corresponding eviction routine.

### Finding Description
The claimed equality/fault holds: nothing ties the returned `Attachment.content` to the requested `content_hash`.

- The client sends `GetAttachment` for a specific `content_hash` (`AttachmentRequest.content_hash`, populated from on-chain-tracked `AttachmentInstance`s in `get_prioritized_attachments_requests`, `download.rs:404-478`).
- The response is decoded with no hash verification: `response.decode_atlas_get_attachment()` just JSON-decodes the body and the resulting attachment is inserted straight into the context set: `self.attachments.insert(response.attachment);` [1](#0-0)  A malicious/misbehaving outbound peer (any peer the node syncs Atlas data with — reachable without privilege, per the allowed threat model of "run their own peer") can therefore return arbitrary bytes as `attachment.content` whose hash does not match the requested `content_hash`.
- In the `Done` branch, for every attachment drained from that set, the code looks up matching queued instances by the attachment's *own* (attacker-controlled) hash, but calls `insert_instantiated_attachment` regardless of whether any match was found: [2](#0-1) 
- `insert_instantiated_attachment` writes unconditionally to the shared `attachments` table with `was_instantiated=1`, with no size check and no eviction call: [3](#0-2) 
- Contrast with `insert_uninstantiated_attachment`, which enforces `max_uninstantiated_attachments` and evicts oldest rows before inserting: [4](#0-3) 
- The only eviction routine touching this table, `evict_expired_uninstantiated_attachments`, is scoped to `was_instantiated = 0` rows and never reclaims `was_instantiated = 1` rows: [5](#0-4) 

No guard (signature, length cap, hash-equality check) exists anywhere on this path to prevent an attacker-controlled peer from injecting mismatched attachment content that becomes a permanent, unevicted row.

### Impact Explanation
A peer the node syncs Atlas attachments with can cause the node to durably store attacker-chosen blobs (up to `attachments_max_size`) in its local SQLite `attachments` table with `was_instantiated=1`, for hashes that correspond to no real `AttachmentInstance`. Because there is no cap or eviction analogous to `max_uninstantiated_attachments`/`evict_k_oldest_uninstantiated_attachments`, this table grows without bound over the node's lifetime as attachment requests are retried and re-issued, leading to unbounded local disk consumption — an unauthenticated write to persistent node state with no corresponding cleanup path. This matches the "unauthenticated/unauthorized write to state" high-impact category.

### Likelihood Explanation
Preconditions: the attacker's node must be one of the node's `outbound_sync_peers` with an advertised data URL and must be selected as a source for at least one `AttachmentRequest` (driven by genuine on-chain `AttachmentInstance`s the victim node is trying to resolve) — this requires only running an ordinary peer, no secret or privileged role. Each response the attacker crafts with mismatched content produces one permanent garbage row; this repeats across retries (bounded by `max_attachment_retry_count` per batch) and across the lifetime of the node as new legitimate attachment instances appear, so the attack is repeatable but its rate is gated by the volume of genuine attachment-instance traffic the victim is chasing, not by the attacker's own message rate.

### Recommendation
In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/penalize the peer on mismatch instead of accepting the payload. Additionally, add a capacity bound and eviction policy for `was_instantiated = 1` rows in `insert_instantiated_attachment`/`AtlasDB`, symmetric to `insert_uninstantiated_attachment`'s `max_uninstantiated_attachments` handling.

### Proof of Concept
1. In `stackslib/src/net/atlas/tests.rs` (or a new test module), construct an `AttachmentsBatchStateContext` with a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains a request for `content_hash = H1` but whose `StacksHttpResponse` decodes (via a stub `decode_atlas_get_attachment`) to an `Attachment` whose `content` hashes to `H2 != H1`.
2. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the mismatched attachment.
3. Drive the `Done` branch logic (replicate the loop in `AttachmentsDownloader::run`, `download.rs:153-169`) using a real `AtlasDB`, asserting `atlasdb.find_all_attachment_instances(&H2)` returns empty while `atlasdb.insert_instantiated_attachment` still succeeds.
4. Repeat with N distinct mismatched attachments and assert `SELECT COUNT(*) FROM attachments WHERE was_instantiated = 1` grows to N with no call path in `AtlasDB` capable of reducing it — unlike the `was_instantiated = 0` case, which is bounded by `count_uninstantiated_attachments`/`evict_k_oldest_uninstantiated_attachments` in `insert_uninstantiated_attachment` (`db.rs:511-536`).

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

        &mut self,
        attachment: &Attachment,

        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
