### Title
Unbounded `attachments` table growth via unverified `GetAttachmentResponse` content stored as instantiated - ([File: stackslib/src/net/atlas/download.rs])

### Summary
A malicious peer that is queried for a specific `content_hash` via `GET /v2/attachments/{hash}` can return an arbitrary payload whose actual `Hash160` does not match the requested hash. `AttachmentsBatchStateContext::extend_with_attachments` accepts this payload into `context.attachments` with no hash-equality check, and `AttachmentsDownloader::run`'s `Done` branch then unconditionally calls `atlasdb.insert_instantiated_attachment(&attachment)` for every drained entry, regardless of whether any `AttachmentInstance.content_hash` matches `attachment.hash()`.

### Finding Description
The intended invariant is: every row in `attachments` with `was_instantiated = 1` corresponds to an `Attachment` whose `hash()` equals a `content_hash` tracked by a confirmed `AttachmentInstance` (an on-chain atlas event commitment). This is broken because:

1. `AttachmentRequest` is built for a specific `content_hash` [3](#0-2) , and the HTTP request is `GET /v2/attachments/{content_hash}` [4](#0-3) .
2. `extend_with_attachments` decodes the JSON response and does `self.attachments.insert(response.attachment)` without ever comparing `response.attachment.hash()` to `request.content_hash` [5](#0-4) .
3. `AttachmentsDownloader::run`'s `Done` branch drains `context.attachments` and, for each one, looks up `find_all_attachment_instances(&attachment.hash())` (using the *actual* hash of the received bytes, which may match nothing) but calls `insert_instantiated_attachment(&attachment)` unconditionally regardless of the lookup result [6](#0-5) .
4. `insert_instantiated_attachment` performs `INSERT OR REPLACE INTO attachments (... was_instantiated=1 ...)` with no size cap, no eviction, and no relation check to any instance [7](#0-6) , unlike `insert_uninstantiated_attachment`, which is bounded via `evict_k_oldest_uninstantiated_attachments` against `atlas_config.max_uninstantiated_attachments` [8](#0-7) .

For a peer to become the source queried for a given `content_hash`, it only needs to have earlier answered an `AttachmentsInventoryRequest` claiming (falsely) to have that page/attachment available; the inventory response is likewise unauthenticated content interpreted via `decode_atlas_attachments_inv_response` [9](#0-8) , and reliability scoring only affects request ordering, not correctness verification.

Each distinct payload the attacker serves produces a distinct `Hash160::from_data` value [10](#0-9) , so repeated cycles create unboundedly many rows with `was_instantiated=1`, which is not subject to the `max_uninstantiated_attachments` cap or any expiry (`evict_expired_uninstantiated_attachments` only targets `was_instantiated = 0` rows) [11](#0-10) .

### Impact Explanation
A remote, unprivileged peer that becomes an outbound sync source for the victim's Atlas downloader can cause unbounded growth of the victim's `attachments` SQLite table (`was_instantiated=1` rows) with content that no consensus/on-chain atlas event ever committed to. This is disk-storage exhaustion / unbounded state growth tied to no consensus commitment, distinct from and unmitigated by the uninstantiated-attachment cap (`max_uninstantiated_attachments`), matching the "High" impact category (serving/storing non-canonical state as if legitimate, attachment mismatch). It is repeatable indefinitely as long as the attacker keeps being selected as an inventory/attachment source.

### Likelihood Explanation
Preconditions: the attacker must run a reachable peer that the victim's `PeerNetwork::get_outbound_sync_peers()` treats as an outbound sync peer, and must have at least one `AttachmentInstance` with an unresolved `content_hash` queued for download (naturally occurs from normal atlas-event processing) so a batch/request gets created that names a `content_hash` the attacker can be queried against. No secret, admin role, or StackerDB slot is needed — a normal P2P/RPC-reachable peer suffices. Attacker cost is a single crafted HTTP JSON response per exploited hash, fully repeatable across many cycles/hashes.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs), verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/penalize the peer otherwise. Additionally, in `AttachmentsDownloader::run`'s `Done` branch, only call `insert_instantiated_attachment` when `find_all_attachment_instances(&attachment.hash())` is non-empty (or the hash was explicitly the one requested), and consider applying a bound/eviction policy to `was_instantiated=1` rows as a defense in depth.

### Proof of Concept
Rust test plan (`stackslib/src/net/atlas/tests.rs` or a new integration test in `net::atlas::download` tests):
1. Set up two `TestPeer`s (or a mocked `PeerNetwork` + `AttachmentsBatchStateContext`) where peer B is queried for `content_hash = H1` via an `AttachmentRequest`.
2. Have B's mocked HTTP handler respond with a `GetAttachmentResponse { attachment: Attachment::new(b"malicious-unrelated-content".to_vec()) }` whose `hash() != H1` and does not match any `AttachmentInstance.content_hash` in the DB.
3. Drive `AttachmentsBatchStateContext::extend_with_attachments` with this crafted `BatchedRequestsResult` and assert `context.attachments` contains the mismatched attachment (proves missing hash check at line 546-552).
4. Feed the resulting `Done` context through `AttachmentsDownloader::run`, then assert: `atlasdb.count_uninstantiated_attachments()` stays at 0/bounded, while a direct query `SELECT COUNT(*) FROM attachments WHERE was_instantiated = 1` increases by 1 per crafted cycle — repeat the crafted-response cycle N times with N distinct payloads and assert the `was_instantiated=1` count grows to N, demonstrating unbounded growth outside the `max_uninstantiated_attachments` cap.
