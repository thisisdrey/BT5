### Title
Stale postponed self-call receipts (e.g. AddKey) execute against a re-created account after DeleteAccount, because `check_actor_permissions`/`check_account_existence` compare only string `AccountId`s with no account-incarnation marker - ([File: runtime/runtime/src/actions.rs, runtime/runtime/src/lib.rs])

### Summary
`action_delete_account` clears the `Account` record via `remove_account` but does not purge any postponed receipts (`TrieKey::PostponedReceipt`/`TrieKey::PendingDataCount`) that are still queued targeting that `account_id`. When such a postponed receipt later resumes, `apply_action_receipt` re-fetches `get_account` and `check_actor_permissions`/`check_account_existence` re-validate against whatever account currently occupies that name, using pure string comparison of `AccountId`, with no incarnation/epoch marker to detect that the account was deleted and re-created in between.

### Finding Description
`check_actor_permissions` (runtime/runtime/src/actions.rs:739-785) authorizes self-referential actions like `AddKey`/`DeleteKey`/`Stake`/`DeployContract` purely by `actor_id != account_id` string equality, where `actor_id` is the receipt's `predecessor_id()` fixed at receipt-construction time: [1](#0-0) 

`check_account_existence` for `CreateAccount` only checks `account.is_some()`/`is_none()` and has no actor restriction at all for `CreateAccount`: [2](#0-1) [3](#0-2) 

`action_delete_account` nulls the in-memory `account` and calls `remove_account`, then sets `*actor_id = receipt.predecessor_id().clone(); *account = None;` — it never scans or purges postponed-receipt bookkeeping (`TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`) keyed by that same `account_id`: [4](#0-3) 

`apply_action_receipt` always re-fetches the account fresh at execution time, regardless of whether the receipt executes immediately or is a previously postponed receipt resumed once its input data finally arrives: [5](#0-4) 

Postponed receipts are resumed by `process_postponed_receipt`/`process_action_receipt`, which call `apply_action_receipt` unconditionally once `pending_data_count` reaches zero, without any check that the receiver account is the "same" account (by incarnation) as when the receipt was queued: [6](#0-5) 

Exploit flow (all steps performable by an unprivileged attacker who owns a parent account, e.g. `attacker.near`, and a sub-account `sub.attacker.near`):
1. Attacker deploys a contract on `sub.attacker.near` that issues a self-call receipt (`predecessor_id == receiver_id == "sub.attacker.near"`) containing an `AddKey` action, chained via `promise_then` on a data dependency the attacker controls the timing of. This is stored as a postponed receipt keyed by `receiver_id = "sub.attacker.near"`.
2. Attacker self-deletes `sub.attacker.near` via `DeleteAccount` (allowed because `actor_id == account_id` for a self-signed transaction), refunding balance to a beneficiary. `remove_account` clears the `Account`/keys/contract but not the postponed-receipt bookkeeping.
3. Attacker, still controlling parent `attacker.near`, issues `CreateAccount` for `sub.attacker.near` again (no actor check applies), and hands the account off to a new owner (e.g. via a sub-account sale/marketplace flow, setting up new access keys for the buyer).
4. The attacker later triggers the pending data dependency to resolve. `apply_action_receipt` re-fetches the (new) account, `check_account_existence` passes because the account now exists, and `check_actor_permissions` passes because `actor_id` (`"sub.attacker.near"`) still string-equals `account_id` (`"sub.attacker.near"`) — even though it is a completely different account incarnation. The stale `AddKey` action executes, adding the attacker's chosen public key to the new owner's account without the new owner's authorization.

None of the standard checks (signature/nonce verification, access-key permission checks, gas metering, storage staking) stop this, because they all operate correctly for the transactions as submitted; the flaw is that receipt-level authorization has no way to bind a queued postponed receipt to the specific account incarnation it was created against.

### Impact Explanation
This is an authorization-escalation bug: an attacker can retain a backdoor key (or otherwise mutate state, e.g., stake, deploy contract) on an account name after transferring/selling it, in violation of the recipient's expectation of exclusive control. This matches "authorization escalation across accounts" and results in permanent loss of control for the legitimate new owner of the re-created account name.

### Likelihood Explanation
Requires the attacker to own the parent account of the sub-account being deleted/re-created (so they can both delete and recreate the same name), to write/deploy a contract that schedules a delayed self-targeting receipt with a controllable data dependency, and to complete the delete→recreate→handoff sequence before triggering the postponed receipt. All of this is achievable with ordinary account/contract/transaction privileges (deploying wasm, sending transactions, scheduling cross-contract promises) and is fully repeatable at will, with the only "cost" being the gas/storage fees for account creation/deletion cycles and contract deployment. The scenario is somewhat narrow (it only applies to accounts whose name can be recreated by the attacker, i.e., sub-accounts under an attacker-controlled parent, and requires a "handoff" of the name to a new owner who trusts the name is clean), but it is a concrete, reachable path with no reliance on validator/node privileges.

### Recommendation
- When `action_delete_account` removes an account, also purge any postponed-receipt state (`TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and any dangling `TrieKey::PostponedReceiptId` links) still queued against that `account_id`, failing those receipts (e.g., with a new `ActionErrorKind` for "receiver account was deleted") rather than silently leaving them for the receiver's next incarnation.
- Alternatively/additionally, introduce an account incarnation/generation counter (e.g., persisted alongside or derived from `Account`, bumped on each `CreateAccount`) and have receipt creation capture the target's expected generation, so `apply_action_receipt`/`check_actor_permissions` can reject execution against a mismatched generation.

### Proof of Concept
Integration/runtime-test-loop plan:
1. Create sub-account `sub.attacker.near` and deploy a contract that, on a triggering call, issues a self-directed promise with `promise_then` on an unresolved data dependency, batching an `AddKey` action for an attacker-chosen public key targeting itself. Confirm via state inspection that a `TrieKey::PostponedReceipt` entry for `sub.attacker.near` is created and the account's `Account` struct/state records carry no incarnation/generation field.
2. Submit `DeleteAccount(sub.attacker.near, beneficiary)` from `sub.attacker.near` itself; confirm the `Account` record is gone but the postponed receipt entry persists in state (assert directly via trie key lookup).
3. Submit `CreateAccount` for `sub.attacker.near` from `attacker.near`, then `AddKey` with a "new owner" key (simulating handoff), asserting the new owner's key is the only key currently on the account.
4. Resolve the pending data dependency (e.g., complete the cross-shard call it depended on) so the postponed receipt executes.
5. Assert that the previously attacker-chosen public key from step 1 is now present as an access key on `sub.attacker.near`, despite never being authorized by the new owner — proving the AddKey action from the deleted incarnation executed against the new incarnation solely because `actor_id == account_id` string match succeeded and no generation marker existed to block it.
