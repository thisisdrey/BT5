### Title
Certificate `NotBefore`/`NotAfter` fields are unbounded and under-constrained during unmarshal, mirroring the unvalidated time-variable bug class - (File: `cert/cert_v2.go`, `cert/cert_v1.go`)

### Summary
The original finding describes sale-timing variables (`dsStartTime`, `daPriceCurveLength`, `daDropInterval`, `mintlistStartTime`, etc.) that are accepted without any bound or ordering constraint, allowing the derived price/phase calculation to go negative, overflow, or revert. The Nebula analog is the certificate `notBefore`/`notAfter` timestamp pair, which is decoded straight from attacker-influenced wire bytes with no check that `notBefore <= notAfter`, and no check that the values are sane (non-negative, bounded). This is the same root cause: two related time-derived fields are individually type-checked but never cross-validated, so a crafted value pair can produce an inverted or degenerate time window that downstream logic (`Expired`, CA-constraint checks, TTL metrics) does not defend against.

### Finding Description
`unmarshalDetails` for v2 certificates reads the two fields independently with only a presence/format check, no ordering check: [1](#0-0) 

and stores them directly as `time.Time` values used throughout the codebase: [2](#0-1) 

The v1 unmarshal path has the identical pattern — `NotBefore`/`NotAfter` are copied from the raw protobuf `int64` fields with no relationship check between them: [3](#0-2) 

The only place that later relates the two values across a chain is `checkCAConstraints`, and even there it only bounds the *sub* certificate's `notBefore`/`notAfter` against the *signer's* window — it never asserts that the sub certificate's own `notBefore` is before its own `notAfter`: [4](#0-3) 

`Expired()` then evaluates the (possibly inverted) window directly: [5](#0-4) 

Because a certificate with `notBefore > notAfter` can still satisfy `checkCAConstraints` (both values individually fall inside the signer's `[NotBefore, NotAfter]` range), such a certificate can be legitimately signed and will pass verification, yet produce a permanently-expired or paradoxical validity window depending on the exact ordering relative to `time.Now()`.

This is structurally identical to the reported bug class: two independently-bounded values (`daPriceCurveLength`/`daDropInterval`, or here `notBefore`/`notAfter`) are validated in isolation, but the *relationship* between them is never enforced, allowing a semantically invalid configuration that downstream arithmetic/comparisons were not designed to handle.

### Impact Explanation
- If `notBefore > notAfter` for a certificate that is otherwise validly chained and signed, `Expired(t)` returns `true` for effectively all `t`, causing peers who receive/verify this certificate during handshake to treat every tunnel using it as immediately expired, and features like `pki.disconnect_invalid` will tear down or refuse to establish tunnels — a remotely-triggerable denial of service against any node that is handed such a certificate over the wire during handshake processing.
- The metrics/TTL code performs `NotAfter().Sub(time.Now())` on certificate windows; an inverted or extreme window produces a nonsensical (very large negative) duration value fed into gauges (`certificate.ttl_seconds`), which, while not itself crashing, reflects the same "unbounded/under-constrained" pattern the report warns about — no code path defends against a semantically broken window once parsing succeeds.

### Likelihood Explanation
Certificate parsing (`unmarshalCertificateV1` / `unmarshalCertificateV2` → `unmarshalDetails`) is exercised on every handshake message before the peer has an established, mutually-authenticated tunnel — an unauthenticated remote party that possesses (or is issued) a certificate with an inverted window is enough to trigger the condition; no valid, already-authenticated CA-signed session is a prerequisite for delivering the malformed timestamp pair for parsing. The check gap itself is deterministic and requires no timing races.

### Recommendation
Add an explicit ordering/sanity constraint during certificate unmarshal/validate for both v1 and v2 formats:
- Reject certificates where `notBefore > notAfter`.
- Reject or clamp non-sensical negative/overflowing `notBefore`/`notAfter` values before they are converted to `time.Time` and used in duration arithmetic.
- Extend `checkCAConstraints` to also assert the sub-certificate's own `notBefore <= notAfter`, not just that each bound falls within the signer's window.

### Proof of Concept
1. Construct a v2 certificate `Details` ASN.1 blob where `TagDetailsNotBefore` encodes a Unix timestamp far in the future and `TagDetailsNotAfter` encodes an earlier timestamp (both individually satisfying `checkCAConstraints` against a legitimately-signed CA whose own window spans both values).
2. Have the CA sign this degenerate `TBSCertificate` (or, if only leaf-cert distribution channels are attacker-influenced, substitute the crafted `RawDetails` bytes before the final signature step in a MITM/relay scenario reachable pre-authentication).
3. Present the certificate during handshake to a victim node.
4. `unmarshalDetails`/`unmarshalCertificateV1` accept it without complaint; `Expired(time.Now())` subsequently evaluates `true` unconditionally, and any `pki.disconnect_invalid`-driven logic tears down or refuses the tunnel, denying service to legitimate peers relying on that certificate.

// checkCAConstraints is a very generic function allowing both Certificates and TBSCertificates to be tested.
func checkCAConstraints(signer Certificate, notBefore, notAfter time.Time, groups []string, networks, unsafeNetworks []netip.Prefix) error {
	// Make sure this cert isn't valid after the root
	if notAfter.After(signer.NotAfter()) {
		return fmt.Errorf("certificate expires after signing certificate")
	}

	// Make sure this cert wasn't valid before the root
	if notBefore.Before(signer.NotBefore()) {
		return fmt.Errorf("certificate is valid before the signing certificate")
	}
