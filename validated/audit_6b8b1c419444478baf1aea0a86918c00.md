### Title
`ValidateMultiSign`/`BatchValidateSign` TVM precompiles hard-code a signature-count ceiling decoupled from the on-chain `TotalSignNum` permission limit, permanently breaking multisig permissions with more keys - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`AccountPermissionUpdateActuator.checkPermission` allows an account's `Permission` to contain up to `dynamicStore.getTotalSignNum()` keys [1](#0-0) , a value stored in `DynamicPropertiesStore` and adjustable by the committee at any time. However, the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts — which any smart contract can call to verify a multisig permission on-chain — hard-code `MAX_SIZE = 5` and `MAX_SIZE = 16` respectively as compile-time constants, unconnected to `TotalSignNum` [2](#0-1) [3](#0-2) .

### Finding Description
When `VMConfig.allowTvmSelfdestructRestriction()` is active, both precompiles reject any call whose encoded signature-array size exceeds their local `MAX_SIZE`, returning `DATA_FALSE` instead of reverting so the caller sees a "verification failed" result rather than a size error: [4](#0-3) [5](#0-4) 

If the committee raises `TotalSignNum` above 5 (for `ValidateMultiSign`) or 16 (for `BatchValidateSign`) — which is exactly what the dynamic property exists to allow, and is the same mechanism the account-permission actuator uses to legitimately permit larger multisig configurations — every account whose permission legitimately uses more keys than the precompile's hard-coded ceiling can no longer have its signature set validated on-chain via these precompiles. The call always returns "false" (weight not met), even when the correct threshold of valid signatures is supplied, because the extraction/validation loop is never reached for oversized arrays.

This is the same root-cause pattern as the Redstone report: a fixed byte/array-size upper bound embedded in contract-facing logic that does not scale with the legitimately-configured, protocol-permitted size of the real data (there: oracle signer count/payload bytes bound by a 224-byte cap; here: signer/signature count bound by a hard-coded `MAX_SIZE` disconnected from the on-chain `TotalSignNum` dynamic property).

### Impact Explanation
Any DApp or wallet-recovery/permission-verification contract relying on `ValidateMultiSign`/`BatchValidateSign` for accounts configured (via a fully legitimate, protocol-supported `AccountPermissionUpdateContract`) with more keys than the precompile's constant permanently fails to authorize valid multisig approvals through these on-chain verifiers. This breaks core contract functionality for legitimately-configured accounts without any loss of funds by itself — matching the Sherlock Medium classification ("breaks core contract functionality, rendering the contract useless") rather than a fund-loss High.

### Likelihood Explanation
Reachable by any unprivileged contract caller (constant or state-changing call to the precompile address) using a legitimately signed transaction; no malicious actor or privileged role is required. The trigger condition (an account's active/owner permission configured with a key count between the precompile's `MAX_SIZE` and the current `TotalSignNum`) is fully within normal, protocol-sanctioned account configuration and depends only on the committee-controlled `TotalSignNum` dynamic property already exceeding the hard-coded constant — a parameter the codebase itself treats as adjustable rather than fixed.

### Recommendation
Replace the hard-coded `MAX_SIZE` constants in `ValidateMultiSign` and `BatchValidateSign` with a read of `getDeposit().getDynamicPropertiesStore().getTotalSignNum()` (or an equivalently synchronized upper bound), so the precompiles' signature-count ceiling always matches the actual maximum permission key count enforced by `AccountPermissionUpdateActuator`.

### Proof of Concept
1. Committee proposal raises `TotalSignNum` to, e.g., 10 (> the `ValidateMultiSign` `MAX_SIZE` of 5) via the standard dynamic-property proposal mechanism.
2. Account owner calls `AccountPermissionUpdateContract` to set an Active permission with 8 keys and threshold requiring 6 signatures — accepted by `checkPermission` since `8 <= TotalSignNum(10)` [1](#0-0) .
3. A contract calls the `ValidateMultiSign` precompile (address `0x0...9`) with `address`, `permissionId`, `hash`, and a `bytes[]` of 6 valid signatures satisfying the threshold.
4. Because `sigArraySize` (6) exceeds precompile `MAX_SIZE` (5), the guard at line 1066-1071 returns `(true, DATA_FALSE)` immediately — the call always reports failed verification regardless of how many valid signatures are supplied, permanently blocking on-chain multisig checks for this legitimately-configured account [4](#0-3) .
