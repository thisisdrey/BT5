### Title
Unbounded array allocation from unvalidated length field in TVM precompile helpers `extractBytesArray`/`extractSigArray`/`extractBytes32Array` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The signature/verification precompiles that back the `validatemultisign` and `batchvalidatesign` TVM opcodes decode a length field directly out of attacker-supplied calldata and use it, unchecked against the actual size of the input, to allocate a Java array. This mirrors the CVE-2018-5295 bug class: a length value taken from untrusted, structured input is trusted for a memory allocation without bounds-checking it against the real payload size, enabling a crafted input to trigger an oversized allocation / crash.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` each read a 32-byte word from the calldata and convert it to a Java `int` via `DataWord.intValueSafe()`, then immediately use that value as an array dimension with no cross-check against `data.length` or `words.length`: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `len = words[offset].intValueSafe()` is caller-controlled: it comes straight from the ABI-encoded calldata of a smart-contract call to the corresponding precompiled contract (used to implement `validatemultisign`/`batchvalidatesign`-style TVM opcodes, per `ValidateMultiSignContractTest`/`BatchValidateSignContractTest`). The code then does `new byte[len][]` (or `new byte[len][32]`) before any per-element bounds validation happens inside the loop body. Because `intValueSafe()` only guards against negative/overflowed values becoming invalid ints (it clamps to a safe non-negative `int`), an attacker can still supply a value close to `Integer.MAX_VALUE`, which is a legal, "safe" int but wildly larger than any real, well-formed input could justify. This is directly analogous to the PoDoFo `PdfXRefStreamParserObject::ParseStream` bug: a size/length field taken from untrusted data is used to drive a large allocation without validating it against the actual bounds of the surrounding buffer, in a routine that exists specifically to parse structured, attacker-supplied data.

### Impact Explanation
Any account (unprivileged) can broadcast a transaction that calls a smart contract invoking this precompile with a crafted length word, forcing the TVM execution thread to attempt an allocation on the order of gigabytes (e.g., `new byte[Integer.MAX_VALUE >> 3][]` still amounts to many GB of object-array overhead). This can throw `OutOfMemoryError` inside the node's transaction-execution path, potentially destabilizing or crashing the executing full node/SR — a denial-of-service condition reachable purely from contract-call input, consistent with the "node crash or halt" impact category in scope.

### Likelihood Explanation
The precompiled contracts are invoked via ordinary TVM `CALL`/`STATICCALL` opcodes at fixed precompile addresses, so any contract deployer or caller can reach this code with a single transaction; no special privilege, stake, or SR/witness role is required. The only constraint is that the transaction must supply enough energy to reach the precompile dispatch and pass the initial `offset > words.length - 1` guard, both of which are trivially satisfiable by a minimal calldata payload with a single inflated length word.

### Recommendation
Before allocating `bytesArray`/`bytes32Array` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate `len` against a sane upper bound derived from the actual `data.length`/`words.length` (e.g., require `len <= (words.length - offset - 1)` or an equivalent bound tied to the ABI-encoded input size) and reject/return an empty result or fail the precompile call if the declared length exceeds what the input could possibly contain, mirroring the bounds checks already present elsewhere in this file (e.g., `isValidAbiEncoding`).

### Proof of Concept
1. Deploy a trivial contract that calls the `validatemultisign` (or `batchvalidatesign`) precompiled contract address with calldata where the length word at the expected offset is set to a large value (e.g., `0x00000000000000000000000000000000000000000000000000000005f5e100` ~ 100,000,000, or larger, bounded only by gas available to reach the call) while the rest of the calldata is minimal/empty.
2. Broadcast this transaction; when the node executes the precompile, `extractBytesArray`/`extractSigArray` compute `len` from the crafted word and execute `new byte[len][]`, causing a very large short-lived allocation.
3. Repeating/tuning the length value can push memory pressure to the point of `OutOfMemoryError` during transaction execution, since `intValueSafe()` does not validate `len` against the real input size before the allocation occurs. [4](#0-3)

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
