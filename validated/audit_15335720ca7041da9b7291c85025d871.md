### Title
Exchange/Market actuators compute swap and order-matching ratios directly from raw token quantities without normalizing for each TRC10 asset's `precision`, causing mispriced trades between tokens of different precision - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
TRON's on-chain Bancor-style Exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`) and the order-book Market (`MarketSellAssetContract`) both compute conversion ratios and constant-product swap outputs purely from the raw `long` quantities supplied by the transaction, never consulting the `precision` field of the `AssetIssueContract` for either token in the pair. Because TRC10 tokens can be issued with different `precision` values (0 through 6, enforced in `AssetIssueActuator.validate`), a pool or order pairing two tokens with different precision will produce numerically "correct" (per the raw ratio) but economically wrong swap results, exactly mirroring the OmoOracle bug where `getUSDValue()`/`convertUSDToToken()` assumed all tokens share `1e18` decimals.

### Finding Description
- `AssetIssueContract.precision` is a per-token decimal-scale field, validated to be in `[0, ActuatorConstant.PRECISION_DECIMAL]` (6) in `AssetIssueActuator.validate()`: [1](#0-0) 
- `AssetIssueCapsule` exposes `getPrecision()`/`setPrecision()` purely as metadata storage: [2](#0-1) 
- `ExchangeCapsule.transaction()`, which implements the constant-product swap formula for the on-chain Exchange (created/funded via `ExchangeCreateActuator`/`ExchangeInjectActuator`, executed via `ExchangeTransactionActuator`), operates strictly on raw `firstTokenBalance`/`secondTokenBalance`/`sellTokenQuant` longs and never reads or applies `precision` for either `firstTokenId` or `secondTokenId`: [3](#0-2) 
- `ExchangeInjectActuator.doValidate()` similarly computes the proportional "another token" quantity to inject via a raw `BigInteger` ratio of `firstTokenBalance`/`secondTokenBalance`, with no decimal normalization: [4](#0-3) 
- The order-book Market (`MarketSellAssetActuator`, `MarketUtils`) likewise defines "price" purely as the raw ratio `sellTokenQuantity : buyTokenQuantity` for matching/comparison, with no reference to token precision anywhere in `MarketUtils`/`MarketComparator`: [5](#0-4) [6](#0-5) 

In each of these paths, `precision` is loaded and validated at asset-issuance time but is never joined back in at trade/swap time, so 1 raw unit of a precision-0 token is treated as economically equivalent to 1 raw unit of a precision-6 token when computing pool ratios, injection ratios, or order-matching prices — the same class of bug as the OmoOracle report, where price math ignored each token's actual decimal scale.

### Impact Explanation
Any account issuing two TRC10 tokens with different `precision` values and creating an `Exchange` or Market order pair between them (or between such a token and TRX) will have that pool/order's exchange rate be off by a factor of `10^(precisionA - precisionB)` relative to the tokens' "real" unit value, even though the raw balances are internally consistent. Because token balances (and hence swap outputs) are unbacked collateral inside the pool, this can be exploited by the pool creator/first liquidity provider to drain the "another token" side of the pool via `ExchangeTransactionActuator`/`MarketSellAssetActuator`, or to make injected liquidity appear disproportionately valuable, resulting in theft of the counter-party's TRC10/TRX inside the exchange or market — an unauthorized-account-operation / theft-of-funds impact reachable purely via standard, unprivileged `AssetIssueContract` + `ExchangeCreateContract`/`MarketSellAssetContract` transactions.

### Likelihood Explanation
Medium: any unprivileged account can freely choose `precision` (0-6) when issuing two different TRC10 assets via `AssetIssueContract`, then create an `Exchange` or place opposing Market orders pairing them. No special privilege, witness/SR status, or contract deployment is required — only standard signed transactions of types already in scope (`AssetIssueContract`, `ExchangeCreateContract`, `ExchangeTransactionContract`, `MarketSellAssetContract`). The victim must be enticed to trade against the mispriced pool/order, which is the standard precondition for this bug class (similar to oracle mispricing exploits).

### Recommendation
Normalize token quantities by each token's `precision` before computing exchange ratios, injection proportions, and market-order price comparisons — analogous to the report's suggested fix of scaling `amountToken` by `decimalsToken`/`decimalsUSD`. Concretely: when creating/injecting/trading via `ExchangeCapsule`, or when comparing prices in `MarketUtils`/`MarketComparator`, load each token's `precision` from `AssetIssueStore`/`AssetIssueV2Store` and scale raw quantities to a common base (e.g., `quantity * 10^(maxPrecision - tokenPrecision)`) before applying the constant-product/ratio math, or explicitly document and enforce that only tokens of equal `precision` may be paired.

### Proof of Concept
1. Issue token A with `precision = 0` and token B with `precision = 6`, each with `total_supply` denominated in their respective raw units, via `AssetIssueContract` (validated by `AssetIssueActuator.validate`, lines 176-181 above).
2. Create an `Exchange` pairing A and B with balances chosen so the raw ratio looks "fair" (e.g., 1,000,000 A : 1,000,000 B) via `ExchangeCreateContract`.
3. Because `ExchangeCapsule.transaction()` (lines 124-169 above) uses only raw balances with no precision scaling, 1 raw unit of A (worth `10^6` times more per "whole token" than B, given the precision difference) trades 1:1 against B in the constant-product formula.
4. Call `ExchangeTransactionContract` (via `ExchangeTransactionActuator`) to swap A for B (or vice versa) at this mispriced ratio, extracting B (or A) far in excess of fair value, repeating until the pool is drained — the same "no decimal adjustment" root cause as the OmoOracle `getUSDValue()`/`convertUSDToToken()` finding.
