### Title
`simulate_intents` reports a `Transfer` as landing at `receiver_id` while a receiver-contract failure causes `execute_intents` to fully refund it back to the sender - ([File: contracts/defuse/src/contract/intents/mod.rs])

### Summary
`simulate_intents` runs against `CachedState` whose `notify_on_transfer` is an explicit no-op (documented as unable to create promises in a view call), so any `Transfer` intent with a `notification` is reported as fully succeeded and settled at `receiver_id`. In real `execute_intents`, the same `Transfer` synchronously moves the balance to `receiver_id` but then asynchronously calls `mt_on_transfer` on that receiver; if that call fails/panics, `mt_resolve_transfer` refunds the *entire* transferred amount back to the sender. A party that settles on the `simulate_intents` report (transfer succeeded, tokens at `receiver_id`) will be shown a final ledger state that `execute_intents` does not actually produce whenever the attacker-controlled receiver fails the real call.

### Finding Description
Binding claimed: `SimulationOutput.report` from `simulate_intents(signed)` == the log/state outcome that `execute_intents(signed)` actually produces for the same `signed` batch.

- `simulate_intents` builds `Engine::new(self.cached(), &mut inspector)` and calls `execute_signed_intents(signed)`, returning `inspector.into_report()` as `SimulationOutput.report`, with the code comment "do not log transfers" only referring to the invariant-check path, not to the `Transfer` intent execution itself: [1](#0-0) 

- `CachedState::notify_on_transfer` is an explicit no-op, documented as unable to create promises because it's a view call: [2](#0-1) 

- `Transfer::execute_intent` unconditionally performs `internal_sub_balance(sender)` / `internal_add_balance(receiver)` *before* invoking `notify_on_transfer`, and emits the `Transfer` event regardless of what happens downstream: [3](#0-2) 

- In `execute_intents`, the real `Contract::notify_on_transfer` schedules `notify_and_resolve_transfer`, which calls `mt_on_transfer` on `receiver_id` and, in `.then(...)`, calls the `#[private]` `mt_resolve_transfer` callback: [4](#0-3) [5](#0-4) 

- `mt_resolve_transfer` reads the promise result of `mt_on_transfer`; if that promise failed/panicked, `promise_result_checked_json_with_len` yields `None`, and the code falls back to `unwrap_or_else(|| amounts.clone())`, i.e. the **full transferred amount is treated as a refund** and moved back from `receiver_id` to the original sender: [6](#0-5) 

Root cause: `simulate_intents`'s report is generated purely from the synchronous `Engine` state transition and inspector events, with no way to model the asynchronous `mt_on_transfer` outcome (by design, since it's a view call and cannot create promises). `execute_intents`, however, includes that asynchronous leg, whose failure changes the final settled balances via the refund path in `mt_resolve_transfer`. Existing guards (`MultiPayload::verify`, nonce/salt checks, `checked_*` arithmetic, `#[private]` on `mt_resolve_transfer`) all operate correctly and do not address this divergence — they were never meant to, and this is a structural gap between the view-only simulation and the real receipt chain.

Exploit outline: attacker signs (or is one of several signers in) a `Transfer` intent whose `receiver_id` is a contract they control and whose `mt_on_transfer` implementation deterministically panics on real (non-view) invocation while behaving (or simply not being invoked at all) during simulation. A relayer/counterparty who calls `simulate_intents` on the batch sees a report showing the transfer landed at `receiver_id`, decides to co-sign/settle other legs of a multi-party batch (e.g., release of an off-chain or on-chain asset) based on that belief, then submits the batch via `execute_intents`. On real execution, the receiver's `mt_on_transfer` fails and `mt_resolve_transfer` silently refunds the full amount back to the attacker (the original sender), so the receiver never actually keeps the tokens the counterparty believed it received.

### Impact Explanation
This matches the specified High-severity category: `simulate_intents` reporting an outcome `execute_intents` does not produce when a party settles on that report. The divergence is fully repeatable — an attacker can deploy any number of receiver contracts that panic on non-view calls, and reuse this against any counterparty that trusts `simulate_intents` results to decide whether to co-sign or release value tied to a batch's expected settlement. No DAO/role privilege, relayer key, or victim key is required; the attacker only needs to control the `receiver_id` contract and be a signer (or convince another signer to include such a `Transfer`) in the batch.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: deploy a receiver contract that behaves correctly (or isn't reachable) during simulation but panics on the real cross-contract call, sign a `Transfer` intent with `notification.msg` targeting that contract, and get the batch to a party that runs `simulate_intents` before deciding to co-sign/settle based on the report. This requires no special balances beyond whatever tokens are being transferred and no bypass of nonce/salt/signature checks. It is trivially repeatable across accounts, tokens, and batches.

### Recommendation
Do not let `simulate_intents` report a `Transfer` with a `notification` as unconditionally successful landing at `receiver_id`. Options: (1) have the `SimulateInspector`/report explicitly flag intents with a `NotifyOnTransfer` as "pending external call, outcome not simulated" rather than reporting them identically to notification-less transfers; (2) document and surface in the `SimulationReport` type itself (not just a source comment) that any `Transfer`/`mt_on_transfer`-notified balance change is provisional and may be reversed by a refund on real execution, so downstream consumers cannot treat `report` as a binding settlement guarantee.

    fn simulate_intents(&self, signed: Vec<MultiPayload>) -> SimulationOutput {
        let mut inspector = SimulateInspector::default();
        let engine = Engine::new(self.cached(), &mut inspector);

        let invariant_violated = match engine.execute_signed_intents(signed) {
            // do not log transfers
            Ok(_) => None,
            Err(DefuseError::InvariantViolated(v)) => Some(v),
            Err(err) => err.panic(),
        };

        SimulationOutput {
            report: inspector.into_report(),
            invariant_violated,
            state: StateOutput {
                fee: self.fee(),
                current_salt: self.salts.current(),
            },
        }
    }

    pub(crate) fn notify_and_resolve_transfer(
        sender_id: AccountId,
        receiver_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        notify: NotifyOnTransfer,
    ) -> PromiseOrValue<Vec<U128>> {
        let previous_owner_ids = vec![sender_id.clone(); token_ids.len()];

        Self::notify_on_transfer(
            sender_id,
            previous_owner_ids.clone(),
            receiver_id.clone(),
            token_ids.clone(),
            amounts.clone(),
            notify,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(Self::mt_resolve_gas(token_ids.len()))
                // do not distribute remaining gas here (so that all that's left goes to `mt_on_transfer`)
                .with_unused_gas_weight(0)
                .mt_resolve_transfer(previous_owner_ids, receiver_id, token_ids, amounts, None),
        )
        .into()
    }
