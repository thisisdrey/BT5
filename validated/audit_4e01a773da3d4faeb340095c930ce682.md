### Title
`RoamingSuppressSeconds` roaming-flap suppression window is too short to prevent off-path address hijack via captured/replayed packets - (File: hostmap.go, outside.go)

### Summary
Nebula's remote-address ("roaming") trust logic switches which underlay UDP address a tunnel will send to as soon as a single successfully-decrypted packet arrives from a new source address, and only guards against flapping *back* to a previously used address with a hard-coded 2-second suppression window `RoamingSuppressSeconds`. This mirrors the reported TWAP bug class: a security-relevant decision is gated by an observation/suppression window that is far too small relative to realistic attacker/network timing, so a single or few packets delivered within that narrow window can manipulate which address is trusted as the tunnel's current path.

### Finding Description

The roaming decision itself is: [3](#0-2) 

The only anti-flap protection is `RoamingSuppressSeconds`, a fixed constant of 2 seconds, documented as existing purely "to prevent flapping due to packets already in flight": [4](#0-3) 

Because the roam decision fires on the *first* authenticated packet from a differing source address (`curRemote != via.UdpAddr`), and the suppression only blocks *returning* to the immediately-prior address within 2 seconds, an attacker who can observe/capture a single legitimate encrypted packet in flight (e.g., an on-path or off-path attacker capable of UDP source spoofing, without holding any CA-signed certificate or session keys) can replay that captured ciphertext from a spoofed source address. Since the AEAD replay window (`ConnectionState.window`, `Bits`) tracks only the message counter and not the source address, a replayed packet with an unused/future counter passes decryption and immediately triggers `SetRemote` to redirect the tunnel's outbound traffic to the attacker-chosen address: [5](#0-4) [6](#0-5) 

The 2-second window is analogous to the reported TWAP's 10-second observation window: it is a fixed, short time-based safety margin meant to smooth out legitimate jitter, but it is far too small to serve as a robust anti-manipulation control, and it only protects one direction (return-roam) rather than gating the initial roam trust decision at all.

### Impact Explanation
A successful exploitation redirects the local node's outbound path for a tunnel to an address of the attacker's choosing, which can be used to blackhole traffic (denial of service) or, if the attacker also controls network position to receive the redirected UDP flow, to intercept/redirect traffic without needing tunnel keys or a CA-signed certificate. This falls under "remote state poisoning" (hostmap/address trust) per the audit's accepted impact categories.

### Likelihood Explanation
Exploitation requires the attacker to capture at least one legitimate encrypted packet in transit and be able to inject a UDP packet with a spoofed source address that reaches the victim before the natural, legitimate packet flow re-establishes the correct address (i.e., within the narrow window before the real host's next packet arrives). This is feasible for an on-path/off-path attacker on typical UDP transport, especially on lossy or high-latency links, without needing valid CA certificates or key material — matching the required attacker profile. However, it also requires packet capture capability, which somewhat limits it to network-adjacent or MITM-capable attackers.

### Recommendation
Increase the anti-flap/verification window substantially and, more importantly, do not treat a single authenticated packet from a new source as sufficient proof of a legitimate roam — require either (a) a short path-validation challenge/response (similar to QUIC path validation) before switching the authoritative remote address, or (b) a longer, consistently-enforced hysteresis window (well beyond typical network jitter, e.g., tens of seconds) applied symmetrically to both directions of address change, not just the "roam back" case.

### Proof of Concept
1. Establish a tunnel between `me` and `them`.
2. As an attacker with network visibility, capture one in-flight legitimate Nebula message-type packet from `them` to `me` (ciphertext, header intact).
3. Replay that exact captured packet unmodified from a spoofed source `AddrPort` (attacker-controlled) toward `me`.
4. Because the message counter has not yet been consumed, `ConnectionState.Decrypt` succeeds, and `handleHostRoaming` is invoked with `via.UdpAddr` set to the attacker's spoofed address, which differs from `curRemote` and is not equal to `hostinfo.lastRoamRemote`, so `RoamingSuppressSeconds` does not block it — `SetRemote` is called immediately, poisoning `me`'s outbound path to the attacker's address.

Note: I was not able to fully verify network-layer feasibility of UDP source-address spoofing reaching the victim in this environment (that depends on external network/NAT conditions outside the codebase), and I could not find an existing regression test in the repo that exercises this specific single-packet roam-hijack scenario, so this should be validated with a live/e2e reproduction before treating it as fully confirmed.

func (f *Interface) handleHostRoaming(hostinfo *HostInfo, via ViaSender) {
	curRemote := hostinfo.GetRemote()
	if !via.IsRelayed && curRemote != via.UdpAddr {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(hostinfo.vpnAddrs, via.UdpAddr.Addr()) {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				hostinfo.logger(f.l).Debug("lighthouse.remote_allow_list denied roaming", "newAddr", via.UdpAddr)
			}
			return
		}

		if !hostinfo.lastRoam.IsZero() && via.UdpAddr == hostinfo.lastRoamRemote && time.Since(hostinfo.lastRoam) < RoamingSuppressSeconds*time.Second {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				hostinfo.logger(f.l).Debug("Suppressing roam back to previous remote",
					"suppressSeconds", RoamingSuppressSeconds,
					"udpAddr", curRemote,
					"newAddr", via.UdpAddr,
				)
			}
			return
		}

		hostinfo.logger(f.l).Info("Host roamed to new udp ip/port.",
			"udpAddr", curRemote,
			"newAddr", via.UdpAddr,
		)
		hostinfo.lastRoam = time.Now()
		hostinfo.lastRoamRemote = curRemote
		hostinfo.SetRemote(via.UdpAddr)
	}

}

// SetRemoteIfPreferred returns true if the remote was changed. The lastRoam
// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
