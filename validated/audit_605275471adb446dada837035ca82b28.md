### Title
Unauthenticated `RecvError` packet lets an off-path attacker (no CA cert) force a one-sided tunnel teardown, desyncing hostmap/relay state — ([File: outside.go])

### Summary
The Sherlock report describes a class of bug where a protective mechanism (a gas-bounded, try/catch-recoverable notification call) can be bypassed under attacker-chosen conditions so that a state-changing operation (`unsubscribe`) commits while the paired cleanup/accounting update silently fails, leaving two coupled systems (Uniswap V4 position state vs. Deli gauge accounting) permanently out of sync and exploitable for reward dilution. The reachable structural analog in this repo is Nebula's `header.RecvError` packet path: it is processed as *plaintext*, before any certificate/AEAD authentication, and the only "authenticity" check it performs is a raw source-`netip.AddrPort` string compare against the hostinfo's currently known remote — something trivially spoofable by any off-path attacker who can forge UDP source information, with no CA-signed certificate required at all.

### Finding Description
`readOutsidePackets` dispatches on the header type *before* certificate/session data has anything to do with `RecvError`: `header.Handshake` and `header.RecvError` are handled immediately after `h.Parse`/`IsValidSubType`, ahead of the `hostinfo` lookup and AEAD `Decrypt` call that every other packet type goes through: [1](#0-0) 

`handleRecvError` then locates the hostinfo purely from an attacker-supplied `RemoteIndex` field via `QueryReverseIndex`, and "verifies" the sender only by comparing the packet's UDP source address to the hostinfo's currently recorded remote: [2](#0-1) 

Because `RecvError` packets carry no MAC/AEAD tag and are never decrypted, this "spoofing" check is the *entire* authentication for the packet — it is a plaintext address comparison, not a cryptographic proof of possession of a CA-signed identity. Any attacker able to spoof a UDP source address matching the peer's `CurrentRemote` (or race a roam/NAT-rebind window) can trigger `f.closeTunnel(hostinfo)`: [3](#0-2) 

`closeTunnel` unconditionally deletes the *local* hostinfo (and, if it was the last hostinfo for the peer, disestablishes relay state) — but it does **not** notify the remote peer, and the remote peer's own hostinfo/relay accounting is left completely untouched: [4](#0-3) [5](#0-4) 

This is structurally identical to the H-1 bug class: a narrow, resource/verification-limited recovery path (`unsubscribeGasLimit` try/catch in the report; the plaintext, pre-authentication `RecvError` short-circuit here) lets an attacker force one side of a two-sided accounting relationship (peer A's hostmap/relay bookkeeping vs. peer B's) to tear down while the other side's state is left stale — producing a durable state split between two systems that are supposed to stay in lock-step, exactly like the "position keeps liquidity in Deli gauge accounting after Uniswap V4 unsubscribe succeeds" desync in the source report.

### Impact Explanation
An attacker with no CA-issued certificate — someone who cannot complete a real handshake and thus can never become a legitimate peer — can still force a live peer to unilaterally destroy its local hostinfo/relay-tracking state for a real, otherwise-healthy tunnel, while the actual remote peer's hostinfo and relay bookkeeping remain untouched. This is a remote state-poisoning / denial-of-continuity primitive against the hostmap and relay subsystems: repeated forced desyncs can be used to keep tearing down tunnels (churn/DoS), and because the two sides disagree about whether the tunnel/relay exists, dependent bookkeeping (e.g., relay `Established`/`Disestablished` state, pending-deletion timers) can be driven into inconsistent states without either side ever completing a fresh, authenticated handshake.

### Likelihood Explanation
The `RecvError` path is reached before certificate verification and before AEAD decryption, so exploitation requires only: (1) knowledge or brute-forcing of a valid `RemoteIndex` (`localIndexId`) for an existing tunnel, which is a 32-bit value sent in cleartext on every packet and thus observable to any on-path or off-path attacker who can sniff/guess traffic, and (2) the ability to spoof (or otherwise match) the UDP source address the target already associates with that peer — a substantially weaker bar than possessing a CA-signed certificate. `acceptRecvErrorConfig` can restrict acceptance to private/never, but the default `recvErrorAlways` behavior (and the `recvErrorPrivate` behavior on private/LAN deployments, which is a common Nebula use case) both keep this path reachable to attackers without any certificate.

### Recommendation
Do not let an unauthenticated, unencrypted packet type unilaterally trigger destructive state changes (`closeTunnel`/hostmap deletion). At minimum:
- Require some replay-protected minimal proof tied to the session (e.g., a short authenticated tag derived from the session's negotiated keys) before acting on `RecvError`, rather than relying solely on a UDP source-address string compare, which is not a cryptographic authentication mechanism.
- Rate-limit/back off `RecvError`-triggered teardowns per remote index so a single spoofed packet cannot immediately destroy live tunnel/relay state; prefer marking the path suspect and re-verifying via the normal keepalive/dead-tunnel-detection machinery before deleting.
- Ensure `closeTunnel` triggered via `RecvError` also reconciles relay state defensively (as already done for the CHANGELOG-documented one-sided relay teardown fixes) so a one-sided deletion can't leave `Established`/`Disestablished` mismatches between peers.

### Proof of Concept
Not independently verifiable from static code alone; this repo's own `TestCloseTunnelAuthenticated` end-to-end test demonstrates the adjacent authenticated `CloseTunnel` path is hardened against a bogus injected packet (an attacker-crafted `CloseTunnel` header with a guessed `RemoteIndex` and no valid AEAD tag is correctly rejected): [6](#0-5) 
No equivalent e2e test was found in the indexed content that exercises spoofed/off-path `RecvError` injection against `handleRecvError`, so the exploit path above is derived directly from the code's control flow (`outside.go:76-84`, `outside.go:541-575`, `outside.go:250-257`) rather than from an existing PoC in the repository. Given the size limits on the codebase index, some additional context (e.g., full `acceptRecvErrorConfig` default wiring in `main.go`/`interface.go`, or any rate-limiting already applied to `RecvError`) may not have been captured; a full-repo review via a Devin session would be needed to confirm there is no additional mitigating check outside the indexed snippets.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}

func (hm *HostMap) unlockedDeleteHostInfo(hostinfo *HostInfo) bool {
	// Remove this hostinfo from each of its address lists. The lists are independent, so a
	// sibling is never promoted to an address it does not own and no other list is touched.
	final := true
	for _, addr := range hostinfo.vpnAddrs {
		if list, ok := hm.moreHosts[addr]; ok {
			list = removeHostInfo(list, hostinfo)
			hm.unlockedSetHostsForAddr(addr, list)
			if len(list) > 0 {
				final = false
			}
		} else if existing, ok := hm.Hosts[addr]; ok {
			if existing == hostinfo {
				// Common case, the only hostinfo for this address. moreHosts has no entry to clean up.
				delete(hm.Hosts, addr)
			} else {
				// We don't hold this address but another hostinfo does, we still have a tunnel to the peer
				final = false
			}
		}
	}

	// Go maps never shrink their buckets, replace fully drained maps so a node that churned
	// through a large peer count gives the memory back. Same idiom as the index maps below.
	if len(hm.Hosts) == 0 {
		hm.Hosts = map[netip.Addr]*HostInfo{}
	}
	if len(hm.moreHosts) == 0 {
		hm.moreHosts = map[netip.Addr][]*HostInfo{}
	}

	// The remote index uses index ids outside our control so lets make sure we are only removing
	// the remote index pointer here if it points to the hostinfo we are deleting
	hostinfo2, ok := hm.RemoteIndexes[hostinfo.remoteIndexId]
	if ok && hostinfo2 == hostinfo {
		delete(hm.RemoteIndexes, hostinfo.remoteIndexId)
		if len(hm.RemoteIndexes) == 0 {
			hm.RemoteIndexes = map[uint32]*HostInfo{}
		}
	}

	delete(hm.Indexes, hostinfo.localIndexId)
	if len(hm.Indexes) == 0 {
		hm.Indexes = map[uint32]*HostInfo{}
	}

	if hm.l.Enabled(context.Background(), slog.LevelDebug) {
		hm.l.Debug("Hostmap hostInfo deleted",
			"hostMap", m{"mapTotalSize": len(hm.Hosts),
				"vpnAddrs": hostinfo.vpnAddrs, "indexNumber": hostinfo.localIndexId, "remoteIndexNumber": hostinfo.remoteIndexId},
		)
	}

	if final {
		// I have lost connectivity to my peers. My relay tunnel is likely broken. Mark the next
		// hops as 'Requested' so that new relay tunnels are created in the future.
		hm.unlockedDisestablishVpnAddrRelayFor(hostinfo)
	}
	// Clean up any local relay indexes for which I am acting as a relay hop
	for _, localRelayIdx := range hostinfo.relayState.CopyRelayForIdxs() {
		delete(hm.Relays, localRelayIdx)
	}

	return final

	for _, relayHostIp := range hi.relayState.CopyRelayIps() {
