### Title
Unauthenticated `proof=1` query parameter forces expensive MARF proof construction on `GET /v2/contracts/source/<addr>/<contract>` with no execution-time cap - ([File: stackslib/src/net/api/getcontractsrc.rs])

### Summary
`RPCGetContractSrcRequestHandler::try_handle_request` reads the `with_proof` flag straight from the unauthenticated query string and, when set, calls `db.get_data_with_proof::<ContractCommitment>` instead of the cheaper `db.get_data`, incurring MARF Merkle-proof construction. Unlike the call-based read-only endpoints (`callreadonly.rs`, `fastcallreadonly.rs`), which enforce `read_only_max_execution_time`, this GET path has no execution-time budget at all.

### Finding Description
`try_parse_request` builds `HttpRequestContents` directly from the raw query string with no authentication check [1](#0-0) . In `try_handle_request`, `contents.get_with_proof()` (via `HttpRequestContentsExtensions`) selects between the cheap `db.get_data` and the proof-generating `db.get_data_with_proof::<ContractCommitment>` call [2](#0-1) . This is a pure client-supplied toggle (`?proof=1`) with no privilege check.

By contrast, the call-based read-only endpoints explicitly wire `read_only_max_execution_time` into their Clarity VM execution budget/cost tracker to bound per-request compute [3](#0-2) , and the same config knob is referenced in `httpcore.rs` for the connection-level read-only execution budget [4](#0-3) . `getcontractsrc.rs`'s handler does not consult `read_only_max_execution_time` or any other time/cost ceiling before invoking `get_data_with_proof`, so an attacker can force repeated MARF trie-walk-and-proof construction purely by toggling a query parameter, with no cost accounting or cutoff.

### Impact Explanation
Each request with `proof=1` against a contract with deep MARF history causes the node to perform MARF proof construction (trie traversal + serialization) rather than a single cheap lookup, on the RPC read path that is reachable by any remote, unauthenticated party. This is repeatable per request and scales with concurrency (many simultaneous requests to the RPC port), and the endpoint enforces no per-request execution-time ceiling analogous to `read_only_max_execution_time`, unlike the contract-call endpoints. This matches the "bounded compute DoS on a read endpoint" High-impact category: the node's RPC-serving capacity for legitimate clients can be degraded because expensive proof generation work is not time-bounded and is fully attacker-triggerable via an unauthenticated flag.

### Likelihood Explanation
No privileged role, secret, or special peer state is required — any remote client with access to the RPC port can issue `GET /v2/contracts/source/<addr>/<contract>?proof=1` against any known deployed contract. Attacker cost is a single HTTP GET per request; the only precondition is that a target contract has enough MARF history depth to make the proof construction meaningfully more expensive than a normal lookup, which is common for actively-used contracts. This is trivially repeatable and can be run concurrently to amplify load on the node.

### Recommendation
Apply the same execution-time/cost bounding used for `callreadonly`/`fastcallreadonly` (i.e., enforce `read_only_max_execution_time`, or a dedicated bound for MARF proof generation) to the `with_proof` branch in `RPCGetContractSrcRequestHandler::try_handle_request` (and the analogous `getaccount.rs`, `getdatavar.rs`, `getmapentry.rs`, `getclaritymarfvalue.rs` handlers that share this same `get_with_proof` pattern), or rate-limit/require additional cost accounting for `proof=1` requests specifically.

### Proof of Concept
Rust integration test plan (mirroring patterns in `stackslib/src/net/api/tests/getcontractsrc.rs`):
1. Set up a test chainstate with a contract that has many MARF-indexed historical versions (deep trie depth for the `make_contract_hash_key` entry).
2. Issue N concurrent `StacksHttpRequest::new_getcontractsrc(..., with_proof: false)` requests and record wall-clock latency/throughput via `RPCGetContractSrcRequestHandler::try_handle_request`.
3. Issue N concurrent requests with `with_proof: true` against the same contract and same N, and assert:
   - `duration(with_proof=true) >> duration(with_proof=false)` for deep-history contracts (demonstrating disproportionate cost).
   - No `Err`/timeout is produced by `try_handle_request` even when repeated calls exceed a configured `read_only_max_execution_time` equivalent — i.e., grep/assert that `read_only_max_execution_time` config is never read or enforced inside `getcontractsrc.rs`'s call path, confirming the absence of a compute ceiling that exists for `callreadonly.rs`.

    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        captures: &Captures,
        query: Option<&str>,
        _body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        if preamble.get_content_length() != 0 {
            return Err(Error::DecodeError(
                "Invalid Http request: expected 0-length body".to_string(),
            ));
        }

        let contract_identifier = request::get_contract_address(captures, "address", "contract")?;
        self.contract_identifier = Some(contract_identifier);

        let contents = HttpRequestContents::new().query_string(query);
        Ok(contents)
    }
