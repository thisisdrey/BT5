### Title
`RewardsDistributor` `uint32` timestamp cast permanently DoS all deposit/debt token operations after February 2106 - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor` stores the last index-update timestamp in a `uint32` and refreshes it via `block.timestamp.toUint32()`, which reverts once `block.timestamp > type(uint32).max` (Feb 7, 2106). The index update is invoked from `updateBeforeMintOrBurn`/`updateBeforeTransfer` hooks that `DepositToken` and `DebtToken` run on every mint, burn, and transfer, so once the cast starts reverting, all deposits, withdrawals, transfers, issues, repays, liquidations and seizes that touch a reward-tracked token revert — freezing user collateral until governor intervention or a contract upgrade.

### Finding Description
`TokenState.timestamp` is a `uint32` ( [1](#0-0) ). `_calculateTokenIndex` computes `block.timestamp.toUint32()` and `_updateTokenIndex` writes it back ( [2](#0-1) ). `toUint32` reverts on overflow ( [3](#0-2) ).

The hook chain reaching this revert:

- `DepositToken._mint` / `_burn` use `updateRewardsBeforeMintOrBurn`, and `_transfer` uses `updateRewardsBeforeTransfer`, both looping over `pool.getRewardsDistributors()` and calling `updateBeforeMintOrBurn`/`updateBeforeTransfer` ( [4](#0-3) , [5](#0-4) , [6](#0-5) ).
- `DebtToken._mint` / `_burn` use the same hook ( [7](#0-6) , [8](#0-7) ).
- `RewardsDistributor.updateBeforeMintOrBurn`/`updateBeforeTransfer` call `_updateTokenIndex` whenever `tokenStates[token_].index > 0` ( [9](#0-8) ).

Because the revert happens inside `_updateTokenIndex` (before the accrual math completes), every tracked DepositToken's `deposit`, `withdraw`, `withdrawFrom`, `flashWithdraw`, `transfer`, `transferFrom` and `seize` revert, and every tracked DebtToken's `issue`, `repay`, `repayAll`, `mint`, `burn` revert. `Pool.liquidate` (which calls `seize` and burns debt) also reverts, so underwater positions cannot be liquidated.

### Impact Explanation
Permanent freezing of funds by default: user collateral in `Treasury` cannot be withdrawn because `DepositToken.withdraw` → `_burn` → `updateBeforeMintOrBurn` → `_updateTokenIndex` → `toUint32` reverts. Debt cannot be repaid and liquidations are blocked, so positions accrue interest with no exit path. Recovery requires governance action (removing the RewardsDistributor from `pool.getRewardsDistributors()` via the pool's governor functions, or upgrading `DepositToken`/`DebtToken`/`RewardsDistributor`), which mitigates the impact to temporary freezing plus loss of all accrued unclaimed rewards, since indexes can no longer advance.

### Likelihood Explanation
No attacker action is needed — this is a deterministic time bomb: it triggers on the first state-changing call to any reward-tracked token after `block.timestamp` exceeds `2^32 - 1` (Unix year 2106). It only materializes if the deployed RewardsDistributor contracts remain in use at that date and the token state was ever initialized (`index > 0`). Given the ~80-year horizon, likelihood is very low, but the failure mode is unconditional once reached — unlike the referenced NFT report where only comparisons misbehave, here the `SafeCast` revert bricks the code path entirely, and even `updateTokenSpeed` (governor) cannot fix the state because it also calls `_updateTokenIndex` when a speed is set ( [10](#0-9) ).

### Recommendation
- Store the timestamp in a wider type (`uint64` or `uint256`) in `TokenState`, or stop reverting: e.g., use an `unchecked` `uint32(block.timestamp)` cast so the stored timestamp wraps, and compute deltas with modular `uint32` subtraction so elapsed-time math stays correct across the wrap.
- Alternatively, gate `updateBeforeMintOrBurn`/`updateBeforeTransfer` calls in `DepositToken`/`DebtToken` behind a try/catch so a broken distributor cannot brick core token operations.

### Proof of Concept
Hardhat/Foundry fork test outline:

```solidity
// fork mainnet, use deployed Pool, DepositToken (e.g. msETH or msdTOKEN), RewardsDistributor
// 1. Confirm a distributor exists and tokenStates[depositToken].index > 0
// 2. Warp past uint32 max
vm.warp(uint256(type(uint32).max) + 1);
// 3. Any deposit token op reverts inside SafeCast.toUint32
vm.expectRevert(); // "SafeCast: value doesn't fit in 32 bits"
depositToken.transfer(address(1), 1);       // updateBeforeTransfer -> _updateTokenIndex -> toUint32 reverts
vm.expectRevert();
depositToken.withdraw(amount, user);        // _burn -> updateBeforeMintOrBurn -> reverts
vm.expectRevert();
debtToken.repay(user, amount);              // _burn -> updateBeforeMintOrBurn -> reverts
// 4. Governor cannot repair via speed update either
vm.expectRevert();
vm.prank(governor);
rewardsDistributor.updateTokenSpeed(depositToken, 0); // _updateTokenIndex reverts
```

This mirrors the reported bug class exactly (timestamp-dependent DoS in 2106), but on Metronome the impact is broader: instead of only blocking mints, it freezes collateral withdrawals, debt repayment, transfers, and liquidations for every reward-tracked token.

    function _calculateTokenIndex(
        TokenState memory _supplyState,
        IERC20 token_
    ) private view returns (uint224 _newIndex, uint32 _newTimestamp) {
        uint256 _speed = tokenSpeeds[token_];
        uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
        if (_deltaTimestamps > 0 && _speed > 0) {
            uint256 _totalSupply = token_.totalSupply();
            uint256 _tokensAccrued = _deltaTimestamps * _speed;
            uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
            _newIndex = (_supplyState.index + _ratio).toUint224();
            _newTimestamp = block.timestamp.toUint32();
        } else if (_deltaTimestamps > 0 && _supplyState.index > 0) {
            _newTimestamp = block.timestamp.toUint32();
        }
    }
