### Title
Missing slippage enforcement on `expected` output in `ExchangeTransactionContract` allows users to receive less than the requested minimum - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeTransactionActuator` accepts an `expected` field (`tokenExpected`) intended to act as a minimum-received/slippage guard for a bancor-style exchange trade, but the field is only checked for being `> 0` in `doValidate()` and is never compared against the actual computed output amount (`anotherTokenQuant`) in `execute()`. This is the on-chain analog of the "insufficient checks for token/asset compatibility" class of bug in the report: the protocol assumes the caller's expectation of the exchanged amount will hold, but never verifies it, so a caller can be given output silently different (lower) than what they asked for.

### Finding Description
In `doValidate()`, `tokenExpected` is read from the contract and only validated for positivity: [1](#0-0) 

In `execute()`, the actual amount received (`anotherTokenQuant`) is computed via `exchangeCapsule.transaction(...)` and directly credited to the account, with no comparison to `tokenExpected` at all: [2](#0-1) 

The `expected` parameter therefore has no functional effect on the outcome of the trade — it is accepted by the protobuf contract and validated superficially, but the actual bancor-formula output (`ExchangeCapsule.transaction`, using `ExchangeProcessor`/`SafeExchangeProcessor`) can differ from what the caller expected, and the trade proceeds regardless: [3](#0-2) 

Because pool balances (`firstTokenBalance`/`secondTokenBalance`) can be moved by any other account's prior `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transaction packed into the same block (block producers order transactions), an attacker can sandwich a victim's exchange trade: inject/withdraw or trade against the pool immediately before the victim's transaction executes, shift the exchange rate unfavorably, and let the victim's trade execute at the worse rate — with no on-chain mechanism to abort the trade even though the victim explicitly specified a minimum expected output.

### Impact Explanation
This allows any unprivileged transaction broadcaster to extract value from other users' exchange trades by sandwiching them within a block, since the `expected` slippage-protection field the protocol exposes is not enforced. Victims lose funds to worse-than-expected exchange rates with no recourse, directly causing loss of user funds through the on-chain TRX/TRC10 bancor exchange feature (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract` actuators).

### Likelihood Explanation
High reachability: any account holding TRX or a TRC10 token registered in an exchange pair can broadcast an `ExchangeTransactionContract` with an `expected` value; no special privilege is required. The precondition (another transaction moving the pool balance before the victim's trade executes within the same block, or even across blocks since anyone can inject/withdraw at will) is trivially satisfiable by any user, making this readily exploitable rather than theoretical.

### Recommendation
Enforce the caller's `tokenExpected` as a true minimum-received check in `execute()` (or `doValidate()` re-checked at execute time): compare the computed `anotherTokenQuant` from `exchangeCapsule.transaction(...)` against `tokenExpected`, and throw `ContractExeException`/abort the trade if the actual output is less than the caller-specified expected minimum, mirroring standard AMM `amountOutMin` slippage protections.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from Victim specifying `tokenId=firstTokenID`, `quant=Q`, `expected=E` (a minimum acceptable output).
2. Attacker broadcasts (with higher energy/priority, or as SR ordering allows within the same block) an `ExchangeInjectContract` or `ExchangeTransactionContract` on the same `exchangeId` that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for the victim's trade direction (see `ExchangeInjectActuator.execute()` mutating pool balances at [4](#0-3) ).
3. Victim's transaction is applied: `doValidate()` only checks `tokenExpected > 0` (see above), and `execute()` computes `anotherTokenQuant` from the now-shifted pool and credits it without comparing to `E`. Victim receives `anotherTokenQuant < E` with the transaction still marked `SUCESS`.
4. Attacker reverses their injection/trade in a follow-up transaction, capturing the spread extracted from the victim's worse execution price.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
