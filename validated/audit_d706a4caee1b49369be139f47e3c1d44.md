### Title
`TOKENLESS_REPAYMENTS_COMPLETE` flag is never cleared when `TOKENLESS_REPAYMENTS_ALLOWED` is disabled and re-enabled, permanently unlocking permissionless-guarded deleverage purge on re-activation - (File: `programs/marginfi/src/state/bank.rs`)

### Summary
The Flayer bug is a state-machine "guard variable never reset on teardown" defect: `params.shutdownVotes` is checked to be `0` before a new shutdown can start, but is never reset when a shutdown completes and the collection is later re-initialized, permanently blocking re-shutdown. The marginfi analog is the inverse but structurally identical class of bug: a bank-level guard flag (`TOKENLESS_REPAYMENTS_COMPLETE`) that is auto-set once a deleverage cycle finishes is never cleared when the admin later re-arms the same guarded workflow (`TOKENLESS_REPAYMENTS_ALLOWED`) for a second deleverage round, so the guard is satisfied immediately for the new cycle even though the new cycle's debt has not actually been repaid.

### Finding Description
`Bank.flags` bit 5 is `TOKENLESS_REPAYMENTS_ALLOWED` and bit 6 is `TOKENLESS_REPAYMENTS_COMPLETE` [1](#0-0) . `TOKENLESS_REPAYMENTS_COMPLETE` is auto-set to `true` inside `lending_account_repay` whenever `TOKENLESS_REPAYMENTS_ALLOWED` is on and the bank's `total_liability_shares` collapses to near-zero [2](#0-1) . It can also be force-set by the risk admin via `lending_pool_force_tokenless_repay_complete` [3](#0-2) .

This flag then guards `purge_deleverage_balance`, which lets the risk admin permissionlessly wipe out a lender's remaining deposit shares in the bank without repaying anything, purely by checking `bank.get_flag(TOKENLESS_REPAYMENTS_COMPLETE)` [4](#0-3) .

The `Bank::configure()` function toggles `TOKENLESS_REPAYMENTS_ALLOWED` on/off via `update_flag(flag, TOKENLESS_REPAYMENTS_ALLOWED)` when the admin sets `config.tokenless_repayments_allowed` [5](#0-4) , but nowhere in `configure()` (or anywhere else that toggles this flag) is `TOKENLESS_REPAYMENTS_COMPLETE` ever cleared. This mirrors the Flayer root cause exactly: a guard bit that is set once a controlled process finishes, but is never reset when the *gating precondition* (`TOKENLESS_REPAYMENTS_ALLOWED` / the shutdown-eligible state) is turned off and later turned back on for a fresh cycle. The documentation itself only states the flag is "auto-set" and "force-set," never describing a clearing path [6](#0-5) .

Concretely: if a bank previously underwent a full tokenless-deleverage cycle (liabilities driven to zero, `TOKENLESS_REPAYMENTS_COMPLETE` set), and the admin later disables `TOKENLESS_REPAYMENTS_ALLOWED`, allows normal deposits/borrows to resume, and then re-enables `TOKENLESS_REPAYMENTS_ALLOWED` for a new deleverage event (with fresh, non-zero liabilities), `TOKENLESS_REPAYMENTS_COMPLETE` is still `true` from the prior cycle. `purge_deleverage_balance` only checks the bit, not the actual liability state, so the risk admin (or any code path relying on this guard) can immediately purge lenders' balances in the new cycle before the new round of debt has actually been zeroed out.

### Impact Explanation
This allows the risk-admin-privileged `purge_deleverage_balance` instruction to wipe out lender asset shares in a bank without the intended precondition (full debt discharge) actually being met for the current deleverage cycle. This is a real unauthorized state change / potential fund-loss path for depositors: shares are burned (`bank.change_asset_shares(-asset_shares, false)`) and the lending position closed with no compensating repayment, exactly mirroring the "irrecoverable" pattern the guard was meant to prevent. Since this requires the `risk_admin` role to act, the direct actor is privileged, but the vulnerability is a core-accounting/bad-debt-handling defect that causes unauthorized loss to unprivileged depositors who never consented to a second, premature purge.

### Likelihood Explanation
Requires a bank to go through two separate `TOKENLESS_REPAYMENTS_ALLOWED` on/off/on cycles - a plausible but not routine admin operation (e.g., re-using the same bank object for a second illiquidity event, or toggling the flag off during testing/cleanup and back on for a genuine second deleverage). The `guides/ADMIN/BANK_STATE.md` documentation and code both show no reset path, so the condition is reachable purely through documented admin workflows without any additional attacker action.

### Recommendation
Clear `TOKENLESS_REPAYMENTS_COMPLETE` in `Bank::configure()` whenever `TOKENLESS_REPAYMENTS_ALLOWED` transitions from `false` to `true` (i.e., a fresh deleverage cycle begins), or alternatively clear it whenever `TOKENLESS_REPAYMENTS_ALLOWED` is disabled. Additionally, consider having `purge_deleverage_balance` re-verify the bank's actual `total_liability_shares` is near zero at call time rather than relying solely on the stored flag, to avoid trusting stale guard state.

### Proof of Concept
1. Admin sets `tokenless_repayments_allowed = true` on Bank B via `configure_bank` [5](#0-4) .
2. Risk admin drives Bank B's liabilities to ~0 via `repay_all`, which auto-sets `TOKENLESS_REPAYMENTS_COMPLETE` [2](#0-1) .
3. Admin sets `tokenless_repayments_allowed = false`, and normal operations resume; new borrowers open new liabilities on Bank B.
4. Admin sets `tokenless_repayments_allowed = true` again to start a second deleverage cycle. `TOKENLESS_REPAYMENTS_COMPLETE` is still `true` from step 2 since nothing clears it.
5. Risk admin immediately calls `purge_deleverage_balance` on a lender in Bank B - the `has_one`/flag constraint passes because `TOKENLESS_REPAYMENTS_COMPLETE` is still set [4](#0-3) , purging the lender's assets even though the new cycle's liabilities have not been discharged.

Note: I could not find any code path that resets `TOKENLESS_REPAYMENTS_COMPLETE` back to `false`; this was confirmed by exhaustive `grep_search` across the repository for all writes to that constant. If such a reset exists in a file outside indexed coverage, it would invalidate this finding — a Devin session with full repo access could verify this with certainty.
