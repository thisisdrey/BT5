This confirms the mitigation is already in place. The `promise_and` implementation gates gas payment *before* the memory read: it computes `memory_len = promise_idx_count.checked_mul(8)` (overflow-checked, returning `IntegerOverflow` if it would overflow), then calls `pay_per(promise_and_per_promise, memory_len)` which charges gas proportional to `memory_len` and fails with `GasExceeded`/`GasLimitExceeded` if the account doesn't have enough gas — all *before* `self.memory.view(...)` is invoked to actually read/allocate the buffer. Since a real transaction's attached gas is bounded (protocol max gas per receipt, far below what would be needed to address `u64::MAX`-scale indices), an attacker cannot get `promise_idx_count` anywhere near a size that would cause unbounded allocation without first exhausting gas and receiving a graceful error.
