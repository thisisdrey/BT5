## Title
Snowbridge V2 outbound `AliasOrigin` filter only blocks AssetHub, letting any other chain forge an arbitrary sibling's Agent identity - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

### Summary
The `XcmConverter::convert()` used by the Snowbridge V2 outbound queue derives the `Message.origin` (an `AgentId`) directly from an attacker-supplied `AliasOrigin` instruction embedded in the `remote_xcm`, after checking it only against a `AllowedAliasOrigin: Contains<Location>` filter. In the Bridge Hub Westend runtime this filter is configured as `EverythingBut<Equals<AssetHubLocation>>` — i.e. it blocks *only* the AssetHub location, not every other possible chain identity. Any other origin able to build an `InitiateTransfer{preserve_origin: true, remote_xcm: [...AliasOrigin(X)...]}` message can therefore set `X` to the location of *any other sibling parachain* (or other non-AssetHub identity) and have the Gateway treat the resulting message as originating from that other chain's Agent, exactly mirroring the "one router can act on another router's components" bug class from the source report, but for Snowbridge Agents holding ETH/ERC-20 balances on Ethereum.

### Finding Description
`XcmConverter::convert()` in `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs` parses the `remote_xcm` syntactically instead of executing it under XCM-executor origin semantics: [1](#0-0) 

It only validates the aliased location against `AllowedAliasOrigin::contains`, then converts it straight into the `AgentId` that becomes `Message.origin`: [2](#0-1) 

This `origin` (an `AgentId`) is exactly the value the Gateway contract on Ethereum uses to authorize which Agent contract executes `CallContract`/token-unlock commands — Agents are per-chain isolated accounts that can hold ETH/ERC-20 value, analogous to the "component" concept (vaults holding funds) in the reported bug. The isolation control that was added (`prdoc/pr_12159.prdoc`) is deliberately narrow: it introduces `AllowedAliasOrigin` and wires it to `EverythingBut<Equals<AssetHubLocation>>` in the Bridge Hub Westend runtime configuration (`bridge_to_ethereum_config.rs` / `xcm_config.rs`), i.e. it defends only against forging the *AssetHub* sovereign/root location (whose Agent holds bridge-critical ERC20 assets) — it does not establish a general invariant that a sender may only alias to *its own* location.

Because the filter is an allow-everything-but-AssetHub `Contains` predicate, any parachain (or any XCM path capable of emitting `InitiateTransfer{preserve_origin:true, ...}` with a self-authored `remote_xcm`) can set `AliasOrigin` to the `Location` of a *different* sibling parachain (not AssetHub) and thereby derive that sibling's `AgentId` via `AgentIdOf::convert_location`, causing the resulting `Message` to be signed/attributed to the victim sibling's Agent when relayed to the Ethereum Gateway. This is the same broken invariant as the report: a caller (router/chain) reaching into another actor's isolated component (agent) because the isolation check binds only a hard-coded exception rather than "origin must equal the true sender."

### Impact Explanation
Snowbridge Agents are per-chain sovereign accounts on Ethereum that can hold native ETH and act as the execution context for `CallContract`/`UnlockNativeToken` commands. Successfully forging the derived `AgentId` to that of another parachain lets an unprivileged/attacker-controlled parachain direct `CallContract` (with attacker-chosen `target`, `calldata`, `value`) or asset-unlock commands to execute as if issued by the victim chain's Agent — theft or unauthorized execution of funds/assets belonging to a different chain's isolated bridge component, matching the "Impact Gate" categories of unauthorized execution/origin escalation and theft/unbacked unlock across the bridge.

### Likelihood Explanation
The path is reachable through a normal, unprivileged XCM execution: a signed account on any parachain (not just AssetHub) can submit `pallet_xcm::execute`/`send` with `WithdrawAsset`/`PayFees`/`InitiateTransfer{preserve_origin:true, remote_xcm}`, where `remote_xcm` is self-authored payload content, not itself subject to per-instruction origin authorization before being handed to the `XcmConverter`. No relayer, validator, governance, or leaked key is required — only crafting the `AliasOrigin` location to a targeted sibling's `Location` (which is public information), the same pattern already demonstrated as viable for AssetHub in the test `signed_assethub_user_cannot_bypass_origin_alteration_when_routing_to_ethereum` before the AssetHub-specific fix, but the fix's scope leaves every other chain unprotected.

### Recommendation
Do not implement `AllowedAliasOrigin` as a blocklist over a single privileged location. Instead, enforce that `AliasOrigin` (or the effective preserved origin) is constrained to equal the actual sending origin resolved by the XCM executor for the `InitiateTransfer`/`ExportMessage` call (i.e., verify `origin_location == real_origin` rather than `origin_location != AssetHubLocation`), or bind the Agent lookup to the executor-verified origin instead of an unauthenticated instruction embedded in attacker-controlled `remote_xcm` bytes. This restores the isolation invariant the external report describes: a component (Agent) should only ever be reachable through its own verified owner-origin, not through an arbitrary caller supplying its identifier.

### Proof of Concept
1. Attacker controls parachain `P` (any sibling other than AssetHub) with a signed account and sufficient local/remote fee assets.
2. Attacker submits, via `pallet_xcm::execute`, an XCM: `WithdrawAsset`, `PayFees`, `InitiateTransfer{destination: ethereum(), preserve_origin: true, remote_xcm: [AliasOrigin(Location::new(1,[Parachain(VICTIM_PARA_ID)])), DepositAsset{...}, Transact{ ContractCall::V1{ target: ATTACKER_CONTROLLED, value: X, calldata, gas } }, SetTopic(...)]}`.
3. The BridgeHub outbound-queue-v2 converter (`convert.rs`) checks `AllowedAliasOrigin::contains(victim_para_location)`, which passes because the filter only excludes `AssetHubLocation`.
4. `AgentIdOf::convert_location(victim_para_location)` derives the victim parachain's `AgentId`, which is placed into `Message.origin`.
5. When relayed and executed on the Ethereum Gateway, the `CallContract` command executes under the victim's Agent context (potentially spending the victim Agent's locked ETH via `value`), completing unauthorized cross-chain access to a component the attacker does not own — directly analogous to the reported "routers accessing other routers' components."
