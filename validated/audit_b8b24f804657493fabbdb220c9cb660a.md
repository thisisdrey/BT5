### Title
Unvalidated first-receive hook lets an attacker stuff a victim's collateral account list and block new collateral deposits - ([File: contracts/DepositToken.sol])

### Summary
Analogous to CVE-2019-15099 (a NULL dereference caused by an incompletely validated endpoint descriptor), `DepositToken` unconditionally registers itself into the recipient's per-account collateral list inside `Pool` on every first-time receive, with no opt-in, no minimum-amount check, and no validation that the recipient actually wants the position. Combined with `deposit(amount_, onBehalfOf_)` crediting arbitrary beneficiaries and permissionless `transfer`, any EOA can force-fill a victim's account list up to `MAX_TOKENS_PER_USER`, after which `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` for any *new* collateral token. The victim is then unable to deposit or receive collateral types they do not already hold - a denial of service that is fully attacker-controlled and costs only dust.

### Finding Description
Three code paths converge on `Pool.addToDepositTokensOfAccount`:

1. `DepositToken.deposit(amount_, onBehalfOf_)` mints msdTokens to any non-zero `onBehalfOf_` address [1](#0-0) 
2. `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was zero [2](#0-1) 
3. `_transfer` does the same on a first-time receipt, so plain `transfer`/`transferFrom`/`seize` also register the token [3](#0-2) 

`Pool` tracks each account's deposit tokens in a `MappedEnumerableSet` capped by `MAX_TOKENS_PER_USER` and reverts with `UserReachedMaxTokens` once the cap is reached . The attacker deposits 1 wei of every listed collateral `onBehalfOf` the victim (or transfers 1 wei of each msdToken). Each distinct token consumes one slot. Once the list is full:

- `deposit(..., onBehalfOf_ = victim)` for any collateral the victim doesn't hold reverts inside `_mint` → `addToDepositTokensOfAccount`.
- `transfer(victim, x)` of any msdToken the victim doesn't hold reverts inside `_transfer`.
- `VesperGateway.deposit` / `NativeTokenGateway.deposit` / `SmartFarmingManager.leverage` targeting the victim with a new collateral revert the same way.

There is no mechanism for the victim to remove a token whose balance is nonzero (removal only happens when balance returns to zero in `_burn`/`_transfer` [4](#0-3) ), and the victim cannot dump the forced dust if they have open debt, because `transfer` is gated by `_revertIfLocked`/`unlockedBalanceOf` [5](#0-4) : when `debtPositionOf` locks the full balance, the dust - and therefore the occupied slots - cannot be removed at all.

### Impact Explanation
- An attacker permanently dirties a victim's collateral list. The victim cannot onboard any additional collateral token type, which is a freeze of a core protocol function (depositing collateral) rather than a mere gas increase.
- Critical case: a victim holding an unhealthy or near-threshold debt position who needs to add a *different* collateral (e.g., their existing collateral is crashing or they only hold another asset) is blocked from doing so; `Pool.liquidate` can then seize their position. The forced dust also cannot be transferred out while the position locks their balance, so the condition is unrecoverable by the victim for the lifetime of the debt.
- Liquidators executing `seize` to a fresh receiver address are unaffected; the harm is borne by the targeted account.

### Likelihood Explanation
- Fully permissionless: `deposit(onBehalfOf_)` and `transfer` are public; no role, oracle, or privileged actor is required.
- Cost is the sum of minimum-deposit dust across listed collaterals plus gas - trivially cheap, and repeatable on every new victim. Attacker can recycle the same capital per victim since the msdTokens are credited to the victim, not burned.
- No guard stops it: `deposit` only checks `whenNotPaused`, `onlyIfDepositTokenExists`, and `onBehalfOf_ != 0`; `transfer` only checks the sender's unlocked balance.

### Recommendation
- Make collateral-list membership opt-in: do not call `addToDepositTokensOfAccount` from `_transfer`/`seize`, or gate registration behind a `useAsCollateral` flag the account controls.
- Alternatively, let any account remove tokens from its own list (e.g., a `removeFromDepositTokensOfAccount` path callable by the account when the position is dust/undesired), and skip tokens below a dust threshold in `debtPositionOf`.
- At minimum, enforce a meaningful minimum first-deposit amount per token so stuffing costs more than negligible dust.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Hardhat/Foundry fork test sketch — contracts/DepositToken.sol, contracts/Pool.sol
// Assumes pool has N listed DepositTokens and MAX_TOKENS_PER_USER slots.

function test_CollateralListStuffing() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // 1) Victim opens a normal position (optional but shows the freeze during debt)
    //    deposit + mint debt so balances become locked via _revertIfLocked.

    // 2) Attacker stuffs victim's account list with dust of every other collateral
    IDepositToken[] memory tokens = pool.getDepositTokens();
    for (uint256 i; i < tokens.length; ++i) {
        IERC20 underlying = tokens[i].underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(tokens[i]), 1);
        tokens[i].deposit(1, victim);          // onBehalfOf = victim
        vm.stopPrank();
    }

    // Victim's list is now at MAX_TOKENS_PER_USER.
    assertEq(pool.depositTokensOfAccount(victim).length, MAX);

    // 3) Any NEW collateral token deposit/transfer to victim reverts
    IDepositToken newToken = pool.getDepositTokens()[ /* token victim never held... all are held */ ];
    // Use a newly added collateral or an msdToken the victim doesn't hold:
    vm.expectRevert(UserReachedMaxTokens.selector);
    someNewDepositToken.deposit(amount, victim);

    // 4) Victim cannot clear slots while in debt: dust is locked
    vm.prank(victim);
    vm.expectRevert(NotEnoughFreeBalance.selector);
    tokens[0].transfer(attacker, 1);
}
```
Reproduction path: attacker → `DepositToken.deposit(1, victim)` (or `transfer(victim, 1)`) for each collateral → `_mint`/`_transfer` → `pool.addToDepositTokensOfAccount(victim)` → after `MAX_TOKENS_PER_USER` entries, any new-token deposit/transfer to the victim reverts with `UserReachedMaxTokens`, and `transfer` out of the dust reverts with `NotEnoughFreeBalance` while the victim carries debt. [6](#0-5) 

Caveat: I verified the account-list write path in `DepositToken.sol` and the existence of `UserReachedMaxTokens`/`MappedEnumerableSet` in `Pool.sol`, but I could not read the full `Pool.sol` in this session to confirm the exact cap value and revert site of `addToDepositTokensOfAccount`; the PoC should be validated against the deployed `Pool` implementation on a fork.
