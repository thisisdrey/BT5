### Title
Attacker can fill a victim's collateral/debt token list with dust deposits to freeze their ability to add positions — (`contracts/Pool.sol`, `contracts/DepositToken.sol`)

### Summary
Metronome's analog of the "unbounded attacker-created entries cause DoS" class is the per-account token list in `Pool`. Every account has a bounded list (`depositTokensOfAccount` + `debtTokensOfAccount`, capped by `MAX_TOKENS_PER_USER`), and entries are added permissionlessly: `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone deposit dust collateral on behalf of any account, and `DepositToken._transfer` adds the token to the recipient's list whenever their balance goes from 0 to positive. `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the cap is reached, which bricks any further first-time deposits and inbound transfers for the victim.

### Finding Description
- `DepositToken.deposit()` accepts an arbitrary `onBehalfOf_` beneficiary and mints msdTOKEN to them. On a first-time balance, `_mint` calls `pool.addToDepositTokensOfAccount(account_)`. [1](#0-0) [2](#0-1) 
- `DepositToken._transfer` does the same for plain transfers: a dust `transfer(victim, 1 wei)` of any msd token the victim doesn't yet hold appends it to the victim's list. [3](#0-2) 
- `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` across the combined deposit+debt token lists and reverts `UserReachedMaxTokens` when full — the test at `test/Pool.test.ts:1491-1521` confirms the revert is triggered by filling the combined lists to the cap.
- There is no minimum deposit amount (`deposit` only rejects `amount_ == 0`) and no way for the victim to refuse inbound tokens. Removal only happens when the victim's balance of that token reaches exactly 0 — the victim must spend gas to transfer/withdraw each dusted token to clear slots.

### Impact Explanation
Once the victim's list is saturated:
- Any `deposit()` of a *new* collateral type to the victim reverts (`addToDepositTokensOfAccount` fails inside `_mint`), so the victim cannot top up with a different collateral to avoid liquidation → their position can be liquidated while the rescue deposit path is bricked.
- Any inbound `transfer`/`transferFrom`/`seize` of a not-yet-held msd token reverts, freezing receipt of deposit tokens.
- Recovery requires the victim to fully zero out dust balances token-by-token, paying gas per token. This is temporary freezing of funds / griefing enabling forced liquidation, matching the accepted impact classes.

Feasibility caveat: the attacker can only push as many distinct tokens as are registered in the pool (deposit tokens via `deposit`/`transfer`; whether `DebtToken.issue(amount_, onBehalfOf_)` allows dust-debt stuffing depends on its health checks, which I did not fully verify). The attack works when `MAX_TOKENS_PER_USER` ≤ (registered deposit tokens + entries the victim already holds); on deployments with few collateral types and a small cap this is cheap — each entry costs only a dust deposit plus gas.

### Likelihood Explanation
Unprivileged: needs only public `deposit(amount_, onBehalfOf)` or `transfer` calls with dust of each listed underlying. No privileged role, oracle manipulation, or governance action required. Cost scales with the number of registered deposit tokens; the victim cannot prevent it since token receipt is permissionless.

### Recommendation
- Enforce a minimum deposit/transfer amount that registers a new token on an account's list (e.g., only call `addToDepositTokensOfAccount` when `amount_` exceeds a threshold, or a minimum USD value via `masterOracle`).
- Alternatively, keep the accounting list but don't revert user actions on the cap: decouple the position-tracking list from deposit/transfer execution, or allow deposits to succeed and only bound iteration where the list is actually looped (`debtPositionOf`, `depositOf`).
- Provide a `sweep`-style escape so a victim can clear dust entries in one call.

### Proof of Concept
Hardhat (mock-based, mirrors `test/Pool.test.ts` setup):

```ts
it('grief: attacker fills victim token list, blocking new deposits', async () => {
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber()

  // attacker deposits dust of every registered deposit token on behalf of victim
  for (const dt of depositTokens) {
    await underlying.mint(attacker.address, 1)
    await underlying.connect(attacker).approve(dt.address, 1)
    await dt.connect(attacker).deposit(1, victim.address) // adds token to victim's list
  }
  // (fill remaining slots via dust transfers / second pool tokens as needed)

  // victim can no longer deposit a new collateral type or receive a new msd token
  await expect(
    newDepositToken.connect(victim).deposit(parseEther('10'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // inbound transfer of a new msd token also reverts
  await expect(
    newDepositToken.connect(attacker).transfer(victim.address, 1)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Note: the exact `MAX_TOKENS_PER_USER` value and the number of registered deposit tokens on each live deployment determine reachability; I could not confirm the constant's value from indexed code within the available iterations. If the cap exceeds the total registered tokens, this vector is not exploitable on that deployment and only the dust-transfer/queue-growth portion of the class applies.
