### Title
`git_repository`/`new_git_repository` submodule fetch forces `protocol.file.allow=always`, enabling attacker-controlled `.gitmodules` to read/write outside the repository - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_worker.bzl`'s `update_submodules()` unconditionally re-enables Git's `file://` submodule transport (`protocol.file.allow=always`) when a `git_repository` rule sets `init_submodules` or `recursive_init_submodules`. This nullifies a Git security control (default `protocol.file.allow=user`, hardened after CVE-2022-39253) whose entire purpose is to stop a hostile repository from directing `git submodule update` to arbitrary local filesystem paths via a crafted `.gitmodules`.

### Finding Description
`git_repo()` calls `_update()` → `update_submodules()`: [1](#0-0) 

Both branches pass `-c protocol.file.allow=always` before invoking `git submodule update --init [--recursive] --checkout --force`. The commit added a comment acknowledging the override is specifically to work around Git's own local-clone restriction (bazelbuild/bazel#17040): [1](#0-0) 

The `remote`, `commit`, `tag`, and `branch` attributes on `git_repository` are declared by the trusted rule author, but the actual tree content fetched at that ref/commit — including `.gitmodules` — is content published by whoever controls the remote Git host, i.e., an unprivileged outsider from Bazel's perspective. Bazel never parses or sanitizes submodule `url`/`path` fields itself; it hands the entire decision to `git submodule update` with the safety gate (`protocol.file.allow`) explicitly disabled. A `.gitmodules` entry such as:

```
[submodule "x"]
    path = ../../outside
    url = file:///some/sensitive/path
```

is honored because `protocol.file.allow=always` permits `file://` remotes for submodules, and there is no containment check on the submodule checkout `path` anywhere in `git_worker.bzl` (unlike `_checkout_path()` in `git.bzl`, which does validate `add_prefix` against escaping the repo root): [2](#0-1) 

No equivalent check exists for submodule paths, so `git submodule update` can be steered to read from, or write into, locations outside the external-repository directory that Bazel manages.

### Impact Explanation
This breaks Bazel's containment invariant that fetched-repository content stays inside the repository/output-base directory the rule owns. A malicious or compromised Git host (or a mutable branch/tag pointed to by the rule) can smuggle a `.gitmodules` that (a) reads arbitrary local files/directories reachable via `file://` into the build tree (information disclosure of host files into build outputs), or (b) uses a `path` with `../` segments to place checked-out submodule content outside the intended external-repository directory (write outside the managed tree). Both are reachable purely from attacker-published Git content with default flags, no local machine access or MITM required.

### Likelihood Explanation
Any `git_repository`/`new_git_repository` usage with `init_submodules = True` or `recursive_init_submodules = True` (a documented, non-exotic attribute) triggers the code path on every fetch, with no user opt-in required to re-enable `protocol.file.allow`. This is a broadly reachable, default-flags condition, not a hardened edge case.

### Recommendation
Do not force `protocol.file.allow=always`. Instead, scope it narrowly (e.g., only allow `file://` for submodules whose resolved absolute URL is already inside the already-fetched repository's own object store / working tree, or require an explicit opt-in flag on the rule), and validate submodule checkout `path` values against directory escape the same way `_checkout_path()` already does for `add_prefix`.

### Proof of Concept
A `src/test/shell/bazel` (or Java `BuildIntegrationTestCase`) reproduction:
1. Create a local bare "attacker" git repo `outer` with a `.gitmodules` containing:
   ```
   [submodule "leak"]
       path = ../leaked
       url = file:///absolute/path/to/attacker-controlled-or-sensitive-dir
   ```
   committed alongside the referenced object.
2. Declare in `MODULE.bazel`/`WORKSPACE`:
   ```
   git_repository(
       name = "outer_repo",
       remote = "file:///path/to/outer",
       commit = "<pinned commit>",
       recursive_init_submodules = True,
   )
   ```
3. Run `bazel fetch @outer_repo` (or a target depending on it) and observe that `bazel-<workspace>/external/outer_repo/../leaked` (i.e., a path outside `external/outer_repo`) is created/populated, or that content from the arbitrary `file://` URL is copied into the managed external repo — demonstrating the submodule fetch escaped the intended repository root because `protocol.file.allow=always` allowed the local transport and no path-escape check exists for submodule paths.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
