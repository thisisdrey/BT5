### Title
Replay-window Check/Update race allows duplicate delivery of replayed data-plane and relay packets - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay as two separate locked operations — `window.Check()` then `window.Update()` — with the AEAD decrypt/verify sandwiched in between, executed *without* holding the lock. When two packets carrying the same `messageCounter` arrive concurrently (Nebula runs multiple UDP-listener routines per the `routines` config, each independently invoking `readOutsidePackets`/`Decrypt` for the same `hostinfo`), both can pass `Check()` before either calls `Update()`, so both decrypt and get delivered to the application even though only one `Update()` call will ultimately succeed. This mirrors the reported bug class: state (`stake_amount`/accumulator vs. here the replay bitmap) is read and later committed in two disjoint critical sections instead of one atomic check-and-commit, letting an attacker exploit the window between them.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, and releases the lock before doing anything else: [1](#0-0) 

The actual AEAD decryption (`cs.dKey.DecryptDanger`) happens fully outside the lock, and only afterward does the code re-acquire the lock to call `cs.window.Update(l, messageCounter)` to actually mark the counter as seen. `VerifyRelay` follows the identical pattern for relay frames: [2](#0-1) 

`Bits.Check` only inspects state (read-only), and `Bits.Update` is what durably records the counter as consumed: [3](#0-2) 

Because Nebula's UDP receive path runs `routines` concurrent listener goroutines that each call into the same `hostinfo.ConnectionState.Decrypt` for packets addressed to the same peer: [4](#0-3) 

a duplicated/replayed on-the-wire packet delivered to two different listener routines at (nearly) the same time can have both copies pass `Check()` (since neither has called `Update()` yet), both decrypt successfully (decryption itself does not consult or mutate the window), and both get forwarded into `handleOutsideMessagePacket`/onward processing before the second `Update()` call finally reports `ErrAlreadySeen` — too late, since the payload was already delivered once already and the "duplicate" detection only prevents a second delivery, not the race that let the first replay through despite the window logically already having "seen" that counter from a legitimate transmission moments earlier.

This is architecturally the same flaw pattern as the reported bug: a piece of state meant to gate an action (the accumulator / the replay bitmap) is updated in a step disjoint from the validating read, so a second actor exploiting the gap between read and commit gets to act on stale state.

### Impact Explanation
An on-path or capture/replay-capable attacker (no valid certificate required, since this occurs purely on already-established ciphertext capture/replay, comparable to the relay-replay scenario Nebula already defends against and even tests for) can cause a captured packet to be decrypted and processed twice by racing two copies of it into the multiple listener routines. This can result in duplicate processing of authenticated traffic (double-delivery of tunnel data, double relay-forwarding), undermining the anti-replay guarantee the `Bits` window is specifically designed to provide, and is functionally the same protocol violation the project's own `TestRelayReplayProtection` test guards against (replayed relay frames must be dropped, not reprocessed).

### Likelihood Explanation
Exploitability requires only capturing one legitimate ciphertext packet and re-injecting it twice within a very small timing window aimed at two different listener goroutines — achievable by any attacker able to observe and replay UDP traffic to the target's listening port(s) when `listen.routines` > 1 (a common multi-core configuration). No cryptographic material or valid certificate is needed since replay of already-valid ciphertext is sufficient; the race window, while narrow, is directly under attacker control (they choose when to fire the duplicate packets).

### Recommendation
Hold `decryptLock` for the entire check-decrypt-update sequence (or otherwise make `Check`+`Update` atomic with respect to the AEAD operation) in both `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`, so no second packet with the same `messageCounter` can pass `Check()` until the first packet's `Update()` has committed. Equivalently, replace the two-step Check/Update with a single atomic `CheckAndUpdate` operation performed under one critical section that also encompasses (or is ordered strictly before) delivering the decrypted payload downstream.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes with `listen.routines` set to 2 or more so multiple goroutines concurrently call `Decrypt`/`VerifyRelay` for the same `ConnectionState`.
2. Capture one legitimate ciphertext packet (as `e2e/tunnels_test.go`'s `TestRelayReplayProtection` already does for the relay path): [5](#0-4) 
3. Simultaneously inject two copies of the identical captured packet at the UDP layer, timed so both are picked up by different listener routines before either completes its `Update()` call.
4. Observe that both copies pass `window.Check()`, both decrypt successfully via `cs.dKey.DecryptDanger`, and both get forwarded to `handleOutsideMessagePacket`/relay-forward logic — i.e., the replayed packet is processed twice instead of being uniformly rejected as `ErrAlreadySeen`.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
