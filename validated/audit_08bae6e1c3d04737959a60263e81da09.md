### Title
Front-runnable contract-address squatting causes permanent deployment failure for `CreateSmartContract` transactions - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
The address of a to-be-deployed smart contract is computed deterministically from the raw transaction hash and the owner address, and this exact address is visible/computable by anyone who observes the pending transaction (e.g., in the mempool) before it is packed into a block. `VMActuator` then unconditionally rejects the deployment if *any* account already exists at that address — not just if contract code exists there — unlike the analogous internal `CREATE` path, which explicitly tolerates a pre-funded, code-less account. This asymmetry lets an unprivileged attacker permanently doom a specific pending deployment transaction by pre-funding its target address with a trivial TRX transfer.

### Finding Description
The contract address for a top-level `CreateSmartContract` transaction is generated as `sha3(txRawDataHash || ownerAddress)[12:]`: [1](#0-0) 

Before executing/validating the deployment, `VMActuator` performs a strict existence check on that address and throws if an account is already present there, with no exception for accounts that merely hold a balance and no contract code: [2](#0-1) 

This differs from the analogous internal `CREATE` opcode path, which explicitly allows a plain account (holding a balance but no code) at the computed address to be "upgraded" into the contract, only failing when actual contract bytecode already exists there (the Constantinople collision rule): [3](#0-2) 

Because `txRawDataHash` is derived from the full signed raw transaction bytes (ref_block info, timestamp, fee_limit, bytecode, etc.), an attacker cannot predict it before the deployer creates/signs their transaction — but once that transaction is broadcast and sits in the mempool (visible to any node), any observer can compute the resulting address using the same `WalletUtil.generateContractAddress` formula and race a plain TRX transfer to it before the deployment transaction is confirmed. This "poisons" the target address with an account entry, and the strict `rootRepository.getAccount(contractAddress) != null` check in `VMActuator` then permanently fails that specific deployment transaction.

### Impact Explanation
This is a denial-of-service against a legitimate, unprivileged contract deployer: any pending `CreateSmartContract` transaction observed in the mempool can be griefed by a third party at the cost of a single ordinary TRX transfer, causing the deployer's transaction to fail validation/execution once it is processed. Since the deployer must resubmit (each resubmission naturally changes `txRawDataHash` and thus the target address, requiring the attacker to repeat the race), this enables a griefing campaign that can persistently block a targeted address from ever successfully deploying a contract, wasting fee/bandwidth resources and disrupting protocol/dapp deployment flows that depend on deterministic addressing.

### Likelihood Explanation
The attack requires only mempool visibility (already broadly available to any node/peer) and the ability to broadcast an ordinary TRX transfer — no special privilege, no SR/witness/validator role, and no reliance on malicious nodes. The inconsistency between the top-level actuator (strict block on any existing account) and the internal `CREATE` opcode path (tolerant of pre-funded, code-less accounts) shows this isn't an intentional collision-safety design choice for the top-level path, increasing the likelihood this is an overlooked gap rather than deliberate hardening.

### Recommendation
Align `VMActuator`'s existence check with the internal `CREATE` collision-handling semantics already used in `Program.createContractImpl`: only reject/upgrade based on whether *contract code* already exists at the target address (using the same `isContractExist`-style check), and if only a plain balance/account entry is present, upgrade it into the new contract (preserving balance) rather than unconditionally rejecting the transaction. This removes the cheap, front-runnable griefing vector.

### Proof of Concept
1. Attacker monitors the mempool for pending `CreateSmartContract` transactions.
2. For a target transaction, attacker computes `contractAddress = sha3(txRawDataHash || ownerAddress)[12:]` using the same logic as `WalletUtil.generateContractAddress(trx)`.
3. Attacker broadcasts a plain TRX transfer to `contractAddress`, causing an `AccountCapsule` to be created there ahead of the original transaction's confirmation.
4. When the original `CreateSmartContract` transaction executes, `VMActuator`'s check `rootRepository.getAccount(contractAddress) != null` (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java:359-364`) fails, and the transaction reverts/fails permanently — the deployer must resubmit with a new transaction (and thus a new target address), which the attacker can repeat-grief.

Note: I was unable to fully verify from the indexed code whether the `create()` method containing this check runs strictly during `validate()` (pre-block, no fee consumed) or during `execute()` (in-block, consuming resources) — this affects whether the impact is "wasted bandwidth/energy fee" versus "transaction simply rejected before packing." I'd recommend a Devin session with full source access to trace `VMActuator.validate()`/`execute()` call order and confirm the exact fee-consumption/on-chain impact if precise severity classification is required.

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
