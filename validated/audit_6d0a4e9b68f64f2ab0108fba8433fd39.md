Confirmed: no `resolve_auth_call`/`auth_call_resolve` callback exists anywhere in the codebase — the chain in `Contract::auth_call` (contracts/defuse/src/contract/intents/state.rs:303-337) ends at `do_auth_call` with no subsequent `.then()` to catch a failed `near_withdraw` and re-credit the signer.

### Title
Failed `near_withdraw` in `AuthCall` permanently burns signer's wNEAR with no recredit path - (File: contracts/defuse/src/contract/intents/state.rs)

### Summary
When `AuthCall::attached_deposit` is non-zero, `Contract::auth_call` synchronously debits the signer's internal wNEAR `token_balances` via `self.withdraw(...)`, then asynchronously schedules `near_withdraw` followed by `do_auth_call`. If `near_withdraw` fails (e.g. wNEAR contract paused/errors), `do_auth_call`'s `require!(promise_result_checked_void(0).is_ok(), ...)` panics and the receipt aborts — but unlike the analogous `ft_withdraw`/`ft_resolve_withdraw` flow, there is no terminal resolver callback to detect this failure and call `self.deposit(...)` to restore the signer's balance.

### Finding Description
The binding that must hold is: `internal wNEAR debited from signer == value actually withdrawn-and-delivered OR re-credited to signer on failure`.

Trace:
1. `Contract::auth_call` (contracts/defuse/src/contract/intents/state.rs:303-337): when `attached_deposit` is non-zero, it calls `self.withdraw(signer_id, [(wnear_token_id, amount)], ...)` — this synchronously decrements `owner.token_balances` and `total_supplies` (contracts/defuse/src/contract/tokens/mod.rs:76-128) in the *current* receipt, committed regardless of what happens later.
2. It then schedules `ext_wnear::near_withdraw(...).then(Self::ext(...).do_auth_call(signer_id, auth_call))` — two chained promises, each executed in their own receipt.
3. `Contract::do_auth_call` (contracts/defuse/src/contract/intents/auth_call.rs:18-24): if `attached_deposit` is non-zero, it does `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")`. If `near_withdraw` failed (e.g. wNEAR contract paused), this `require!` panics, aborting the `do_auth_call` receipt entirely.
4. Unlike `internal_ft_withdraw`/`ft_resolve_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs:76-105, 154-195), which always schedules a final `.then(ft_resolve_withdraw)` that inspects the promise result and calls `self.deposit(...)` to refund on failure, the `auth_call` chain has **no terminal resolver**. `do_auth_call` is the last promise in the chain, and panicking there produces no callback that could re-credit the signer.
5. As a result, the signer's wNEAR `token_balances` entry (and `total_supplies`) already decremented in step 1 is never restored, even though the real wNEAR tokens were never actually converted/withdrawn (since `near_withdraw` itself failed) — the value stays custodied by the Defuse contract in the wNEAR NEP-141 contract, but the signer's claim to it is permanently erased from the internal ledger.

An attacker does not even need a "tiny nonzero attached_deposit trick" as speculated in the question — *any* non-zero `attached_deposit` already routes through this vulnerable `near_withdraw`→`do_auth_call` chain (the `is_zero()` branch is the only path that avoids it entirely and is safe, since it performs no debit at all). The bug is that once inside the non-zero branch, a failure at the `near_withdraw` step is unrecoverable.

### Impact Explanation
The signer's own wNEAR balance is permanently frozen/lost from the internal ledger with no path to recover it — this is a user funds-loss condition matching the Critical "user funds permanently frozen" category. It is repeatable per signed `AuthCall` intent with non-zero `attached_deposit` any time the configured wNEAR contract is paused, erroring, or otherwise rejects `near_withdraw` (e.g., due to insufficient wNEAR contract storage, a paused state, or gas exhaustion causing the callback status to read as failed). This affects any signer who submits such an intent while wNEAR withdrawal is failing — self-inflicted in the literal sense, but the code path itself is broken regardless of attacker intent, since it can also be triggered accidentally or by anyone racing to submit an `AuthCall` at a moment the wNEAR contract is paused (e.g., by the DAO), permanently destroying signer funds with no recredit.

### Likelihood Explanation
Preconditions: attacker (or any signer) needs a wNEAR balance in Defuse and must sign an `AuthCall` intent with non-zero `attached_deposit`, and the wNEAR contract must fail `near_withdraw` at execution time (pause is a DAO/role action out of the attacker's control, but transient failures — e.g., wNEAR contract congestion, gas limits, or its own pause state — are plausible external conditions). This is not something the unprivileged attacker can force onto another victim's funds — it only destroys the signer's own attached deposit — so it is a self-directed funds-loss bug rather than a cross-account theft, but it still is a permanent-freeze condition matching the Critical category "user funds permanently frozen."

### Recommendation
Add a terminal resolver callback (analogous to `ft_resolve_withdraw`) after `do_auth_call` (or restructure `do_auth_call` itself) that inspects the final promise's execution status and, on failure, calls `self.deposit(signer_id, [(wnear_token_id, attached_deposit)], Some(REFUND_MEMO))` to restore the signer's internal wNEAR balance, mirroring the pattern already used in `contracts/defuse/src/contract/tokens/nep141/withdraw.rs`.

    pub(crate) fn withdraw(
        &mut self,
        owner_id: &AccountIdRef,
        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<impl Into<String>>,
        force: bool,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        // Schedule to emit `mt_burn` events only in the end of tx
        // to avoid confusion when `mt_burn` occurs before relevant
        // `mt_transfer` arrives. This can happen due to postponed
        // delta-matching during intents execution.
        if !burn_event.amounts.is_empty() {
            self.runtime.postponed_burns.mt_burn(burn_event);
        }

        Ok(())
    }

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
