Important: `beginHandshake` runs the full Noise handshake (`machine.ProcessPacket`) on every stage-0 packet, including the exact byte-for-byte replay, *before* `CheckAndComplete` is even called. The stage-0 payload is fully re-verified against the CA and re-decrypted each time; nothing about the `ErrAlreadySeen` path skips cryptographic verification of the packet content, only of the *sender's UDP address*.

### Title
Unauthenticated remote roam via replayed stage-0 handshake packet in `ErrAlreadySeen` path - (File: handshake_manager.go)

### Summary
`HandshakeManager.CheckAndComplete` detects a duplicate stage-1/stage-0 handshake purely by `bytes.Equal` on the raw captured packet bytes [1](#0-0) , with no binding to the UDP source address that delivered it. `handleCheckAndCompleteError`'s `ErrAlreadySeen` branch then calls `existing.SetRemoteIfPreferred(f.hostMap, via)` using the *attacker-supplied* `via` (the source address of the just-processed packet) [2](#0-1) , and `SetRemoteIfPreferred` will switch `hostinfo.remote` to that address if it falls in a configured `preferred_ranges` entry [3](#0-2) .

### Finding Description
The flow is: `HandleIncoming` → `beginHandshake` (stage-1, `MessageCounter==1`, `RemoteIndex==0`) [4](#0-3)  → `machine.ProcessPacket` fully re-verifies the Noise handshake and cert (this is expensive but not skipped) [5](#0-4)  → `hostinfo.HandshakePacket[handshakePacketStage0]` is populated with the raw packet bytes [6](#0-5)  → `CheckAndComplete` compares this against every existing hostinfo for that VPN address using only `bytes.Equal`, with no comparison of the originating UDP source address [7](#0-6)  → on match, returns `ErrAlreadySeen` → `handleCheckAndCompleteError` invokes `existing.SetRemoteIfPreferred(f.hostMap, via)`, where `via.UdpAddr` is exactly the source address the attacker used to send the (identical, replayed) UDP datagram [2](#0-1) . `SetRemoteIfPreferred` roams to `via.UdpAddr` whenever the current remote is not already in a preferred range and the new address is [8](#0-7) . Nothing in this path authenticates that the source IP is under control of the legitimate peer that originally sent the packet — the exact-byte replay carries valid crypto content (because it's an unmodified capture), but the source address is a purely network-layer field that Nebula trusts implicitly for roaming purposes. This matches the historical, intentional behavior noted in `CHANGELOG.md` ("we will immediately switch to a preferred remote address after the reception of a handshake packet"), so the roam-on-any-handshake-packet design is known/intentional, but it was not designed with an unauthenticated/spoofed-source replay scenario in mind.

A **mutated** stage0 packet (as the question also raises) would fail `bytes.Equal` and fall into `ErrExistingHostInfo` (older timestamp) or would be re-processed/rejected by `machine.ProcessPacket`/`validatePeerCert`, so only the exact byte-for-byte replay is exploitable here; a slightly mutated copy does not reach `SetRemoteIfPreferred` through this path.

### Impact Explanation
An attacker who can (a) passively capture one legitimate stage-0 handshake packet between two real Nebula peers and (b) send that exact packet from a spoofed/attacker-controlled source address that falls inside the victim's configured `preferred_ranges`, can force the responder to redirect all future outbound encrypted traffic for that tunnel to the attacker's chosen address — a remote-state poisoning / traffic-redirection primitive, achieved without holding any key material and without a new authenticated handshake. Because `preferred_ranges` addresses are typically local/private network ranges, the practical blast radius is attackers already positioned on/near that trusted local segment (e.g., can sniff and spoof on the same LAN), which narrows but does not eliminate the impact — no cryptographic break, key leak, or lighthouse/CA compromise is required.

### Likelihood Explanation
Requires: (1) `preferred_ranges`/`local_range` configured (opt-in feature, not default), (2) attacker able to observe one legitimate stage-0 packet (passive sniffing on a shared segment, e.g. LAN/Wi-Fi), and (3) attacker able to send a UDP packet with a source address inside the preferred range (either genuinely originating there, or via source-address spoofing where the network path does not enforce BCP38 filtering for that range). These are non-trivial but realistic preconditions for a LAN-adjacent unprivileged attacker, and the replay itself is deterministic and repeatable (same captured bytes can be resent any number of times as long as the target hostinfo/handshake bytes remain cached).

### Recommendation
Do not use the raw source address of a duplicate/ErrAlreadySeen packet as authoritative "preferred" roam evidence. Either (a) require that a roam via `SetRemoteIfPreferred` only be triggered by a *freshly completed* handshake (i.e., only from the `nil`-error success path of `CheckAndComplete`, not from `ErrAlreadySeen`), or (b) bind the cached `HandshakePacket[handshakePacketStage0]` comparison to the address it was originally received from, so a byte-identical replay from a different source is treated as a new/invalid packet rather than silently reusing the old success state to alter `via`-derived remote/roam behavior.

### Proof of Concept
Integration test (extending `e2e/handshake_manager_test.go` alongside `TestHandshakeAlreadySeenPreferredRemote`):
1. Configure both `myControl` and `theirControl` with `lighthouse.preferred_ranges` (or `preferred_ranges`) containing an attacker-reachable subnet, e.g. `10.99.0.0/24`.
2. Complete a normal handshake between `myControl` and `theirControl` as in the existing test, and record `hi.CurrentRemote` on the responder side.
3. Capture the original stage-1 `msg1` packet (`myControl.GetFromUDP` equivalent, or persist a copy captured during step 2).
4. Construct a copy of that exact `msg1` packet (`Copy()`), and rewrite `From` to a spoofed address inside the preferred range (e.g. `10.99.0.5:4242`) not equal to the real peer's underlay address.
5. Inject the byte-identical replay into `theirControl` via `InjectUDPPacket`.
6. Assert that `theirControl.GetHostInfoByVpnAddr(...).CurrentRemote` is **unchanged** (i.e., still the original legitimate remote) — expected to currently **fail** (remote changes to the spoofed `10.99.0.5:4242`), demonstrating the poisoning.
7. Additionally assert no new hostmap index/hostinfo was created and that a `header.Test`/`TestRequest` probe was sent to the spoofed address (per `handleCheckAndCompleteError`'s `ErrAlreadySeen` branch), confirming the responder now targets the attacker-controlled address for that tunnel.

func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}
