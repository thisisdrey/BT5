### Title
NEAR-implicit account reseeded to a stale nonce window inside the same block as its own deletion, enabling replay of a pre-deletion signed transaction - ([File: runtime/runtime/src/access_keys.rs, runtime/runtime/src/actions.rs])

### Summary
`initial_nonce_value` seeds a freshly (re)created access key to `(block_height-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, where `block_height` is the height of the block in which the seeding action executes. Because `DeleteAccount` on a self-owned account is a *local* receipt (executed in the same block it is included) while the recreating `Transfer` to that account is typically an *incoming* receipt executed one block after being sent, an attacker can engineer both to land in the exact same block, with the incoming `Transfer` processed after the local `DeleteAccount` in that block's receipt-processing order. The recreated key's seed nonce is then computed from that same block height, landing below a nonce the owner had already consumed earlier in that very block, which re-validates an old signed transaction under the monotonic-nonce check.

### Finding Description
`initial_nonce_value(block_height)` at [1](#0-0)  seeds `access_key.nonce = (block_height-1)*M`. This same seeding is used both when a `NearImplicitAccount` is (re)created via `action_implicit_account_creation_transfer` [2](#0-1)  and, implicitly, by the fact that the account's only `FullAccess` key is deterministically derived from the account id itself, so recreating the account always reissues the *same* public key.

`action_delete_account` removes the account and its access key(s) via `remove_account` [3](#0-2) . A self-signed `DeleteAccount` transaction (`signer_id == receiver_id == account_id`) is converted to a *local* receipt and is executed within the *same* block it is included in, per the documented apply-order: transactions are converted to receipts, then "Process receipts in the order local → delayed → incoming" [4](#0-3) . A `Transfer` sent by an unrelated account to that implicit account id is *not* local (`signer_id != receiver_id`) and is therefore queued as an outgoing receipt processed by the target shard as an *incoming* receipt in the following block-apply — landing in the "incoming" phase, i.e. strictly after any local receipts of that same block.

`verify_nonce` bounds nonces below `block_height * M` for the block in which the transaction is *converted* to a receipt (nonce is consumed at tx-conversion time, not at receipt-execution time), per `verifier.rs` (documented at `protocol-model/spec/runtime-execution.md:58`). This lets the account owner (attacker) pick a nonce arbitrarily close to `H*M` for a transaction included in block `H`.

Exploit flow:
1. Attacker owns a NEAR-implicit account `A` and a second funder account `F`.
2. At block height `H`, attacker submits from `A` to itself (or self-consuming) a transaction `T_old` with nonce `n = H*M - k` (just under the upper bound) — this is a genuine, real transaction, and its nonce is committed to `A`'s access key at tx-conversion time in block `H`.
3. In the same chunk/block `H`, attacker submits a `DeleteAccount` transaction from `A` to itself with nonce `n+1`. Both are local receipts of block `H` and execute in block `H`'s local-receipt phase, in submission order: `T_old` executes, then `DeleteAccount` executes, removing `A`'s account and access key.
4. One block earlier, at height `H-1`, `F` submits a plain `Transfer` to `A`'s account id. This is non-local, so its receipt is delivered as an *incoming* receipt to be processed at height `H`.
5. Within block `H`'s apply, the incoming `Transfer` (from step 4) executes *after* the local receipts (per local→delayed→incoming ordering), recreating `A` via `action_implicit_account_creation_transfer` with a fresh `FullAccess` key seeded to `(H-1)*M`.
6. Since `(H-1)*M < n = H*M - k`, the old nonce `n` (already consumed by `T_old` in step 2) is *greater* than the freshly reseeded nonce. The monotonic nonce check (`tx_nonce > current_nonce`) therefore now accepts a resubmission of `T_old` (or any other previously signed transaction with nonce in `((H-1)*M, H*M)`), causing it to execute a second time and produce a brand-new receipt id (since receipt ids are derived from tx hash + execution block height), i.e., a genuine double execution.

Existing regression coverage (`access_key_nonce_for_implicit_accounts.rs::test_transaction_hash_collision_for_near_implicit_account_fail`) only exercises deletion and recreation separated by several blocks (`blocks_number = 5` gaps), so it never triggers the same-block collision window described above; it does not cover the tight-timing scenario where deletion and recreation are forced into the same block-apply.

### Impact Explanation
This is a replay/double-execution of a previously-settled, validly-signed transaction from the same access key, made possible purely through ordinary, permissionless transaction submission and block-height timing (no validator/node privilege required). It matches the "double-spend/replay" bounty category: a transaction that transferred funds out of (or invoked a contract from) the implicit account can be made to execute a second time after the account is deleted and immediately re-funded within the same block, producing a new receipt and duplicate on-chain effect.

### Likelihood Explanation
Feasibility hinges on an attacker being able to align, within a single block: (a) their own high-nonce transaction and self-`DeleteAccount` transaction (both local, fully under their control and ordering), and (b) a third account's plain `Transfer` to the same implicit id submitted exactly one block earlier so its receipt is processed as "incoming" in the deletion's block. Chain height is publicly observable and near-deterministic in timing, so an attacker can target the intended block height and resubmit if a given attempt misses (no cost beyond gas/tx fees and multiple attempts). No special privileges, leaked keys, or validator access are required — only control of the implicit account's private key and a second funded account.

### Recommendation
Seed a freshly (re)created access key's nonce using a height/marker that is guaranteed to exceed any nonce that could have been consumed by the account in its prior life within the same block, e.g. base the seed on `block_height` plus an intra-block sequence counter, or persist a monotonic "max nonce ever used" marker per account id that survives `DeleteAccount`/`remove_account` and is consulted by `action_implicit_account_creation_transfer` when reseeding.

### Proof of Concept
Runtime/test-loop integration test plan (extending `access_key_nonce_for_implicit_accounts.rs`):
1. Create NEAR-implicit account `A` via `Transfer` from `test1` at some height, producing key nonce seed `(H0-1)*M`.
2. From `A`, submit `tx_high_nonce` (e.g. a self-transfer or transfer to `test0`) with nonce `n = H*M - 10` at target block height `H`, and in the same chunk submit `delete_account_tx` from `A` to itself with nonce `n+1`, both included in the chunk for height `H`.
3. One block earlier (`H-1`), submit `refund_tx`: a `Transfer` from `test1` to `A`'s account id, timed so its resulting receipt is processed as an incoming receipt at height `H`.
4. Produce blocks to reach and apply height `H`, asserting: `delete_account_tx` succeeds, `A` is recreated at height `H` with `FullAccess` key nonce `(H-1)*M`.
5. Resubmit `tx_high_nonce` (or any other previously-executed transaction from `A` with nonce in `((H-1)*M, H*M)`) and assert it is accepted (`ProcessTxResponse::ValidTx`) and executes successfully a second time, producing a new receipt/execution outcome — demonstrating the double-execution/replay.
