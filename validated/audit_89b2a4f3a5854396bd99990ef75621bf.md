## Analysis

This is a valid analog to the Directus finding: an unauthenticated HTTP endpoint that leaks the node's **exact** software version, which an attacker can use to look up known CVEs for that specific build.

### Title
Unauthenticated `/wallet/getnodeinfo` (and `/monitor/getnodeinfo`) endpoint discloses the exact FullNode software version - (File: `framework/src/main/java/org/tron/core/services/http/GetNodeInfoServlet.java`)

### Summary
The java-tron FullNode HTTP API exposes a `GetNodeInfoServlet` at `/wallet/getnodeinfo` (and again at `/monitor/getnodeinfo`) that returns the node's exact `codeVersion` string without requiring any authentication, mirroring the Directus `GHSA-rmjh-cf9q-pv7q` issue where the precise running version is exposed via an unauthenticated API endpoint.

### Finding Description
`GetNodeInfoServlet.doGet` calls `NodeInfoService.getNodeInfo()` and serializes the result directly to the HTTP response as JSON with no permission or API-key check performed inside the servlet itself: [1](#0-0) 

`NodeInfoService.setConfigNodeInfo` populates `ConfigNodeInfo.codeVersion` with `Version.getVersion()`, which is the precise semantic version string (e.g. `"4.8.2.2"`), not just a generic build tag: [2](#0-1) [3](#0-2) 

The endpoint is registered in `FullNodeHttpApiService.addServlet` at both `/wallet/getnodeinfo` and `/monitor/getnodeinfo` paths without any authentication requirement — only a generic `HttpApiAccessFilter`/`LiteFnQueryHttpFilter` and rate limiter (`RateLimiterServlet`) sit in front, neither of which perform credential/permission checks; they only throttle QPS and handle lite-fullnode routing: [4](#0-3) [5](#0-4) [6](#0-5) 

The same data is also exposed via the gRPC `GetNodeInfo` RPC, which likewise performs no authorization check before returning the proto-encoded `NodeInfo` (including `codeVersion`): [7](#0-6) [8](#0-7) 

### Impact Explanation
Any anonymous client that can reach a node's HTTP or gRPC port can fingerprint the exact running java-tron version. This directly enables the same abuse pattern as the Directus advisory: an attacker enumerates public java-tron nodes/SR/witness/candidate nodes, matches the disclosed `codeVersion`/`versionNum` against known CVEs for that specific release, and targets nodes running vulnerable, unpatched builds — accelerating exploitation of any other unpatched vulnerability in that version. This is an information-disclosure issue (CWE-200) rather than a direct fund-theft or RCE primitive on its own, but it materially lowers the bar for follow-on attacks against the network.

### Likelihood Explanation
Likelihood is high: the endpoint requires no signed transaction, no credentials, and no special network position — a plain unauthenticated HTTP GET to `/wallet/getnodeinfo` (default port 8090) or a gRPC call to `GetNodeInfo` (default port 50051) is sufficient, and both are commonly exposed on public/candidate and even some SR nodes by default configuration.

### Recommendation
Restrict `/wallet/getnodeinfo`, `/monitor/getnodeinfo`, and the gRPC `GetNodeInfo` RPC to authenticated/internal callers only (e.g., gate behind the existing API-key mechanism used for sensitive wallet endpoints, or bind to a private/loopback interface by default), and consider truncating or omitting the precise patch-level version (`codeVersion`/`versionNum`) from the response returned to untrusted callers, exposing only a coarse major/minor version if needed for compatibility checks.

### Proof of Concept
```
curl http://<node-ip>:8090/wallet/getnodeinfo
```
Response includes:
```json
{
  "configNodeInfo": {
    "codeVersion": "4.8.2.2",
    "versionNum": "18828",
    ...
  }
}
```
No authentication header, API key, or prior handshake is required to obtain this response, matching the disclosure pattern in the Directus advisory.
