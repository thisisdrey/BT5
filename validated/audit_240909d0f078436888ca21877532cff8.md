### Title
Unauthorized cross-repository object disclosure via unrestricted `LinkRepositoryToObjectPool` / `CreateObjectPool` pairing - (File: `internal/gitaly/service/objectpool/link.go`, `internal/gitaly/service/objectpool/create.go`)

### Summary
Gitaly's `ObjectPoolService` lets a caller link an arbitrary repository to an arbitrary object pool by simply naming both in the RPC request, with no verification inside Gitaly that the target repository is legitimately related (e.g., a fork of / descendant from) the object pool it is being linked to. This mirrors the Turnstile bug class: a permissionless "registration" (here, "linking") operation lets an unrelated party attach itself to another party's resource and inherit its benefits — in this case, full read access to the pool's Git objects via `objects/info/alternates`, instead of gas-fee redirection.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the `repository` field is a valid repository and resolves the `pool` via `poolForRequest`; it performs no check that `repository` was ever forked from, or otherwise entitled to, the specified `object_pool`: [1](#0-0) 

The underlying `Link` function simply writes the pool's path into the repository's `objects/info/alternates` file once the two are validated to be in the same partition/storage — there is no ownership or provenance check between the two repositories: [2](#0-1) 

`CreateObjectPool` similarly accepts any `origin` repository as the basis to clone from and any `object_pool` target, again with no authorization tie between them beyond both being valid repositories on the same storage: [3](#0-2) 

Once linked via alternates, all objects in the pool become fully readable through the member repository's normal Git/RPC surface, as demonstrated by Gitaly's own tests, which show that after `Link`, a commit that exists only in the pool becomes fetchable/readable from the (unrelated) member repository: [4](#0-3) [5](#0-4) 

Documentation confirms this is the deliberate mechanism (alternates linking), and that the only safety checks concern the object pool's own health, not who may link to it: [6](#0-5) 

The proto/service documentation itself explicitly disclaims safety on the delete path ("There are no safety checks in place"), underscoring that Gitaly's ObjectPoolService is designed to trust its caller entirely for authorization decisions rather than enforcing any relationship invariant between pool and member: [7](#0-6) 

The only structural constraints enforced are storage/partition co-location, not ownership or provenance: [8](#0-7) [9](#0-8) 

### Impact Explanation
Exactly as in the Turnstile finding — where permissionless `register()` let anyone redirect fee benefits meant for another contract to themselves — Gitaly's `LinkRepositoryToObjectPool`/`CreateObjectPool` RPCs let any caller who can invoke them for two repository paths (which need not have any legitimate relationship) redirect the "benefit" (deduplicated object storage) of one repository's object pool to an unrelated repository, gaining full read access to every object contained in that pool. Because object pools are typically seeded from a private repository's full object set (via `git clone --local`), an attacker able to name the correct storage/relative path of a private pool (predictable/enumerable `@hashed/...` or replica paths in some deployments) can, by having Gitaly link any repository they control to that pool, exfiltrate all of the private repository's Git objects (commits, blobs, trees) without ever having read access to the original repository. This is a cross-repository object access vulnerability — high impact for confidentiality of private repository content.

### Likelihood Explanation
Exploitation requires the ability to invoke `ObjectPoolService.CreateObjectPool`/`LinkRepositoryToObjectPool` naming a target repository and an object pool the caller does not otherwise own, and knowledge of the pool's exact storage name/relative path. Gitaly itself performs no authorization here by design — it defers entirely to the calling layer (GitLab Rails) to authorize the pairing, similar to the way Turnstile's `register()` defers to whoever holds `msg.sender`. Any component or actor able to reach the ObjectPoolService RPCs with attacker-influenced repository identifiers (e.g., a compromised or insufficiently-validating orchestration layer, or a bug in caller-side authorization) can exercise this path without any additional Gitaly-side gate. Likelihood is therefore tied directly to whether the calling layer enforces the ownership relationship — Gitaly provides no defense-in-depth against a caller that gets this wrong.

### Recommendation
Add an explicit provenance/ownership check inside Gitaly's `ObjectPoolService` before allowing a link: e.g., record and verify that the object pool was created from (or the target repository is a recognized descendant of) the object pool's `origin` repository, rejecting `LinkRepositoryToObjectPool`/`CreateObjectPool` calls where no such recorded relationship exists. This adds defense-in-depth so that Gitaly does not unconditionally trust the caller to have already validated the repository/pool relationship, consistent with treating cross-repository alternate linking as a privileged, provenance-checked operation rather than a bare path-pairing operation.

### Proof of Concept
1. Attacker controls (or creates) `repoA` in storage `default`.
2. Attacker learns/guesses the exact `relative_path` of `poolB`, an object pool that was seeded from a private repository `repoB` the attacker cannot otherwise read (see `createObjectPool` helper for how a pool's `Repository.RelativePath` is structured): [10](#0-9) 
3. Attacker calls `LinkRepositoryToObjectPool(Repository: repoA, ObjectPool: {Repository: poolB})`.
4. Gitaly validates only that `repoA` is a valid repository and `poolB` is a valid pool on the same storage/partition, then writes `poolB`'s path into `repoA/objects/info/alternates`: [1](#0-0) 
5. Attacker now fetches/reads any object from `poolB` (i.e., originally private objects from `repoB`) through `repoA`'s normal Git/RPC interfaces, as confirmed by Gitaly's own test assertions that objects become readable through the member repository once linked: [11](#0-10)

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func TestDisconnectGitAlternates(t *testing.T) {
	t.Parallel()

	ctx := testhelper.Context(t)
	cfg, repoProto, repoPath, _, client := setup(t, ctx)
	repo := localrepo.NewTestRepo(t, cfg, repoProto)

	commitID := gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"))
	gittest.Exec(t, cfg, "-C", repoPath, "repack", "-Ad")

	// We create the object pool, link the original repository to it and then repack the pool
	// member. As the linking step should've pulled all objects into the pool, the repack should
	// get rid of the now-duplicate objects in the repository in favor of the pooled ones.
	_, pool, _ := createObjectPool(t, ctx, cfg, repoProto)
	require.NoError(t, pool.Link(ctx, repo))
	gittest.Exec(t, cfg, "-C", repoPath, "gc")

	// Corrupt the repository to check that the commit we have created can no longer be read.
	// This is done to ensure that the object really only exists in the pool repository now.
	altPath, err := repo.InfoAlternatesPath(ctx)
	require.NoError(t, err)
	require.NoError(t, os.Remove(altPath))
	gittest.RequireObjectNotExists(t, cfg, repoPath, commitID)

	// Recreate the alternates link and assert that we can now read the commit again.
	require.NoError(t, pool.Link(ctx, repo))
	require.FileExists(t, altPath, "objects/info/alternates should be back")
	gittest.RequireObjectExists(t, cfg, repoPath, commitID)

	// At this point we know that the repository has access to the commit, but only if
	// objects/info/alternates is in place.
	_, err = client.DisconnectGitAlternates(ctx, &gitalypb.DisconnectGitAlternatesRequest{Repository: repoProto})
	require.NoError(t, err)

	// Check that the object can still be found, even though objects/info/alternates is gone.
	// This is the purpose of DisconnectGitAlternates.
	commitClient := gitalypb.NewCommitServiceClient(gittest.DialService(t, ctx, cfg))
	gittest.RequireObjectExistsAPI(t, ctx, commitClient, repoProto, commitID)
}

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

// createObjectPool creates a new object pool from the given source repository. It returns the

	tb testing.TB,

	cfg config.Cfg,
