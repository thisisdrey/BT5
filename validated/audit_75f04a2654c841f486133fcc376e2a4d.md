### Title
Protocol fee bypass on NEP-245/IMT tokens via unit-chunked `TokenDiff` intents - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives fees on `Nep245`/`Imt` tokens only when the **per-intent** absolute delta is `<= 1`, but fees are computed independently for each `TokenDiff` intent rather than on the aggregate net delta of a token across the whole batch. An attacker can split a large negative delta (token spend) into many `-1`-sized `TokenDiff` intents within the same `MultiPayload`, collectively moving any amount while `Self::token_fee` returns `Pips::ZERO` on every single call.

### Finding Description
The broken binding: for a Nep245/Imt token with a net attacker-side outflow of `N` units in one settlement batch, `fee_collected(aggregate=N)` should equal `Pips::fee_ceil(N, protocol_fee)` (nonzero for `protocol_fee > 0`), but it instead equals `0` when the outflow is expressed as `N` intents of `delta = -1` each.

Code path: `TokenDiff::execute_intent` iterates over `self.diff` (the deltas of a *single* `TokenDiff` intent) and for each negative delta computes `Self::token_fee(token_id, delta.unsigned_abs(), protocol_fee).fee_ceil(amount)`: [1](#0-0) 

`token_fee` exempts `Nep245`/`Imt` from fees only when the *per-call* `amount <= 1`: [2](#0-1) 

The batch-wide invariant check (`TransferMatcher::finalize` via `Deltas::finalize`) only verifies that the **sum of all deltas per token across the entire batch** (including fee credits) nets to zero — it does not verify that the negative deltas contributing to a receiver were charged fee proportionally to the aggregate amount: [3](#0-2) 

Exploit: attacker (or attacker + counterparty in the same `MultiPayload`) signs a payload with `N` separate `TokenDiff` intents, each `{ diff: { <same Nep245/Imt TokenId>: -1 } }`, totaling `-N` on the sender side, matched by one (or many) `TokenDiff` intent(s) with `+N` positive delta(s) on the receiver side (positive deltas never incur fee regardless of size, per line 70 `if *delta < 0`). Since each of the `N` sender intents independently calls `token_fee` with `amount = 1`, each returns `Pips::ZERO`, so `fees_collected` stays empty for all `N` calls. The invariant check only requires `sum(deltas) + fee_credited == 0`; with `fee_credited = 0` and `-N + N = 0`, the batch passes cleanly with no fee collected — whereas a single `TokenDiff` intent with `delta = -N` (`N > 1`) would have applied `protocol_fee` via the `fee_ceil` calculation and required the receiver's amount to be reduced by the fee to keep the invariant balanced (as demonstrated by `TokenDiff::closure_delta`/`solver_user_closure` test using `fee`).

No existing guard (`verify_intent_nonce`, `MaybeLegacyNonces::commit`, `SaltRegistry::is_valid`, `#[pause]`, `TransferMatcher::finalize`) catches this because fee computation and the net-zero invariant check are two independent mechanisms — the invariant is agnostic to how the delta was split across intents, and fee exemption logic (`token_fee`) is evaluated strictly per-intent, per-token entry.

### Impact Explanation
Protocol fees are bypassed entirely on Nep245/Imt token transfers of any size, by construction of the intent structure rather than any actual restriction on transfer size. This directly reduces `fee_collector` balance versus what the protocol is entitled to under `protocol_fee`, matching the "protocol fees bypassed" Critical category. This is repeatable indefinitely by any account, on any Nep245/Imt token, for any amount (bounded only by gas/tx size per batch, not by protocol design), and does not require any privileged role — only the attacker's own signature over their own intents.

### Likelihood Explanation
The only precondition is holding a Nep245/Imt token balance in the Verifier and a willingness (or colluding counterparty within the same batch) to receive/send it in unit-sized chunks. No signature bypass, no locked-account interaction, and no special role is required — this is a straightforward misuse of `TokenDiff`'s documented per-intent, per-token fee exemption threshold. The cost to the attacker is only the incremental NEAR gas of iterating `N` intents instead of `1`; for realistic batch sizes this is easily affordable and fully repeatable.

### Recommendation
Compute `token_fee`'s size threshold and `protocol_fee` charge on the **aggregated per-signer, per-token negative delta across the whole `MultiPayload`/execution batch**, not per individual `TokenDiff` intent invocation — e.g., accumulate negative deltas per `(signer_id, token_id)` in the `Engine`/`Deltas` layer before applying `token_fee`, or remove/rework the `amount > 1` exemption for `Nep245`/`Imt` so it cannot be trivially defeated by chunking.

### Proof of Concept
`cargo test` (or `near-workspaces` sandbox) plan in `tests/src/tests/defuse/intents/token_diff.rs`:
1. Deploy a Nep245 MT token, deposit `N = 1000` units of one `Nep245TokenId` to `sender`, set `protocol_fee = Pips::ONE_PERCENT` (nonzero).
2. **Baseline**: sign one `TokenDiff` intent `{ token_id: -1000 }` from `sender` and a matching `TokenDiff` `{ token_id: closure_delta(...) }` from `receiver` (using `TokenDiff::closure_delta` to keep the batch balanced with the fee); execute via `execute_intents`; assert `fee_collector` balance for `token_id` equals `Pips::ONE_PERCENT.fee_ceil(1000) > 0`.
3. **Chunked**: reset state; sign `1000` separate `TokenDiff` intents from `sender`, each `{ token_id: -1 }`, plus one `TokenDiff` `{ token_id: +1000 }` from `receiver`, all in one `MultiPayload`; execute via `execute_intents`.
4. Assert `fee_collector` balance for `token_id` after step 3 equals `0`, while `receiver`'s balance increased by the full `1000` (not `1000 - fee`) — proving the two fee outcomes diverge and the aggregate binding `fee(N chunks) == fee(1 diff of N)` is violated.
