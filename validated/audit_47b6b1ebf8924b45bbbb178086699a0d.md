### Title
Unchecked libsodium ChaCha20-Poly1305 encrypt return code allows silently corrupted/undetected shielded note ciphertext to be embedded in broadcast transactions - (File: framework/src/main/java/org/tron/core/zen/note/NoteEncryption.java)

### Summary
`NoteEncryption.encryptToRecipient` and `NoteEncryption.encryptToOurselves` invoke the native `JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt` JNI binding but never check its integer return code, unlike every other libsodium/librustzcash call-site in the same class (`kdfSapling`, `attemptEncDecryption` x2, `attemptOutDecryption`, `encryptBurnMessageByOvk`, `decryptBurnMessageByOvk`), all of which explicitly test `!= 0`/`== 0`. This mirrors the libssh CVE-2025-5987 bug class: a native crypto library's error return is not detected, so the caller proceeds to use a cipher-context/output buffer that may not have actually been correctly (or fully) initialized by the underlying C implementation.

### Finding Description
`encryptToRecipient` ( [2](#0-1) ) and `encryptToOurselves` ( [3](#0-2) ) call:

```java
JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt(new Chacha20Poly1305IetfEncryptParams(
    ciphertext.data, null, message.data,
    ZenChainParams.ZC_ENCPLAINTEXT_SIZE, null, 0, null, cipherNonce, kEnc));
alreadyEncryptedEnc = true;
return Optional.of(ciphertext);
```

The `int` return value of the JNI call is discarded entirely — there is no `if (... != 0) { return Optional.empty(); }` guard, in contrast to the decrypt paths at [4](#0-3)  and the encrypt-burn-message path at [5](#0-4) , which both correctly check the code. `JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt` at [6](#0-5)  simply forwards to the native `Libsodium` binding and returns whatever integer code the native layer produces — the Java layer performs no validation of its own.

`Note.encrypt(byte[] pkD)` ( [1](#0-0)  ) is the caller used when constructing a Sapling shielded output for a shielded transaction (invoked from `ZenTransactionBuilder`, reachable from a normal, unprivileged user request to build/sign a shielded transfer via the wallet/gRPC API). If the underlying native call ever returns a non-zero failure code (heap exhaustion, allocation failure inside the native/JNI boundary, or any other internal libsodium error condition), the Java code has no way to detect it: it unconditionally treats `ciphertext.data` as successfully encrypted, marks `alreadyEncryptedEnc = true`, and returns `Optional.of(ciphertext)` as if encryption succeeded.

Because `EncCiphertext.data` is pre-allocated as a fixed-size, zero-initialized byte array ( [7](#0-6) ), a failed/partial native encrypt leaves it either all-zero or partially written by the native call before it failed. That buffer — containing no confidentiality protection over `message.data` (which embeds the note's diversifier, value, `rcm`, and memo) — is then embedded verbatim as the `cEnc`/`cOut` field of the sapling output description and gets signed and broadcast on-chain as part of the transaction, exactly analogous to how libssh proceeded to use a partially-initialized cipher context after silently swallowing an aliased OpenSSL error code.

### Impact Explanation
If the native encrypt call can fail (even rarely, under memory pressure or other native-layer error conditions), the confidentiality guarantee of Sapling shielded outputs is broken: the plaintext note fields (spending amount, `rcm`, memo, diversifier) could be committed to the immutable, public blockchain in a form that is not actually encrypted, exposing user transaction details that shielded transactions are specifically designed to hide. This matches the "compromised data confidentiality" impact category in the report, mapped onto the "key disclosure"/broken confidentiality-of-broadcast-content class permitted by the rules.

### Likelihood Explanation
Likelihood is low-to-moderate: libsodium's `crypto_aead_chacha20poly1305_ietf_encrypt` for these fixed, valid-length inputs essentially never fails in normal operation, so the missing check is primarily a defense-in-depth / robustness gap rather than a directly, trivially triggerable bug from external input. However, it is a genuine, provable inconsistency in the exact place the analog report calls out (silently accepting a native crypto library's non-success return code), and it sits on a path reachable by any unprivileged user building a standard shielded transaction.

### Recommendation
Check the return code of `JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt` in both `encryptToRecipient` and `encryptToOurselves`, mirroring the existing pattern used everywhere else in the file (`attemptEncDecryption`, `attemptOutDecryption`, `encryptBurnMessageByOvk`): on a non-zero return, return `Optional.empty()` (or throw `ZksnarkException`) instead of proceeding to treat `ciphertext.data` as valid, and propagate that failure up through `Note.encrypt` / `ZenTransactionBuilder` so that shielded-transaction construction aborts rather than silently embedding unencrypted/undefined data on-chain.

  public Optional<EncCiphertext> encryptToRecipient(byte[] pkD, EncPlaintext message)
      throws ZksnarkException {
    if (alreadyEncryptedEnc) {
      throw new ZksnarkException("already encrypted to the recipient using this key");
    }

    byte[] dhsecret = new byte[32];
    if (!JLibrustzcash.librustzcashKaAgree(new KaAgreeParams(pkD, esk, dhsecret))) {
