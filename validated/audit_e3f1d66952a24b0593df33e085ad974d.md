## Analysis

The C4 finding is a classic "numerator too small relative to a large fixed denominator" integer-truncation bug: a per-period linear amount is computed as `amount * elapsed / total`, and while `elapsed` is small, `amount * elapsed` stays below `total`, so the division floors to zero and the accrual is silently lost/delayed.

The same numerical pattern exists in java-tron's legacy (pre-VI) SR voting reward computation, reachable by any account holder who withdraws or queries their voting reward.

### Title
Legacy per-cycle vote reward computation truncates small voters' rewards to zero via floating-point division - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each voter's share of a super representative's per-cycle reward pool using `double` division and then narrows the result back into a `long` accumulator, causing complete truncation-to-zero of legitimately earned reward whenever a voter's share for that single cycle is fractional.

### Finding Description
For cycles prior to `newRewardAlgorithmEffectiveCycle`, `getOldReward` calls the per-cycle `computeReward`: [1](#0-0) 

Here `voteRate = (double) userVote / totalVote` is multiplied by `totalReward` and added into the `long reward` accumulator. Because the addition/assignment implicitly narrows the `double` product to `long`, any cycle in which `userVote / totalVote * totalReward < 1` contributes **zero** to `reward`, unlike the VTVL bug where the truncated amount eventually accrues once enough time passes — here each cycle is computed independently against that cycle's own reward pool, so the truncated fraction for that cycle is permanently lost, not merely postponed. A voter with a small stake relative to a popular SR's total vote, or an SR whose per-cycle reward pool is small, systematically loses reward every affected cycle.

This is exercised through `withdrawReward` / `queryReward`, which loop over historical cycles and invoke `computeReward` for each one via `getOldReward`: [2](#0-1) [3](#0-2) 

`withdrawReward` is invoked directly from `WithdrawBalanceActuator`, i.e. by any unprivileged account broadcasting a `WithdrawBalanceContract` transaction, and `queryReward` is exposed via `GetRewardServlet` for read-only API callers.

### Impact Explanation
Every cycle that falls into the legacy (`double`-based) reward-computation branch and produces a fractional per-voter share causes that voter to receive strictly less reward than the protocol intends to pay out — an unauthorized, systematic loss of already-accrued rewards for the affected account, with no mechanism to reclaim the lost fraction later (contrasted with the newer `BigInteger`/`DECIMAL_OF_VI_REWARD`-scaled VI algorithm used for post-cutover cycles, which correctly avoids this by deferring the division). This is a concrete loss-of-funds bug class, matching the Medium-severity rationale in the original report.

### Likelihood Explanation
The bug only affects cycles before `newRewardAlgorithmEffectiveCycle`; any account that still has an un-withdrawn `beginCycle` predating that cutover and calls `withdrawReward`/`queryReward` (directly, via `WithdrawBalanceActuator`, or via the HTTP `GetRewardServlet`) is affected. No special privileges are required — it is triggered purely by normal user reward withdrawal/query on historical cycles, so likelihood is tied to how many accounts still have unclaimed pre-cutover cycles, which is plausible for long-inactive voters.

### Recommendation
Replace the `double`-based `voteRate * totalReward` computation in `MortgageService.computeReward(long cycle, ...)` with integer/`BigInteger` arithmetic that defers division until after multiplication (e.g. `BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote))`), consistent with the precision-preserving approach already used in the newer VI-based algorithm (`DECIMAL_OF_VI_REWARD` scaling in `DelegationStore`/`RewardViCalService`).

### Proof of Concept
1. SR `W` accumulates a small `totalReward` for `cycle` (e.g. 1000 sun) with `totalVote = 10_000_000` (from many small voters).
2. Voter `A` has `userVote = 5000`.
3. `voteRate = 5000.0 / 10_000_000 = 0.0005`; `voteRate * totalReward = 0.5`.
4. `reward += 0.5` truncates to `reward += 0` when narrowed to `long` — voter `A` receives 0 reward for that cycle even though their proportional share of the pool was legitimately non-zero.
5. Repeating over many cycles, voter `A` permanently loses their fractional share every single cycle, unlike a one-time rounding error. [4](#0-3)

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;

    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);

    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
