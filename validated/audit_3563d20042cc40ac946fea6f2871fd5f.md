### Title
Aliased byte-array between `DataWord` and `StorageRowCapsule` allows in-place opcode mutation to silently corrupt cached contract storage - (File: `common/src/main/java/org/tron/common/runtime/vm/DataWord.java`)

### Summary
`DataWord`'s constructor and `Storage.getValue()` never defensively copy a 32-byte input array, so a `DataWord` produced from a storage read can alias the very `byte[]` held inside the cached `StorageRowCapsule`. Several `DataWord` mutator methods (`and`, `or`, `xor`, `signExtend`) modify `this.data` in place rather than allocating a new array. This mirrors the CVE-2023-23931 bug class: an object that appears immutable/independent is silently mutated through a shared, non-defensively-copied buffer, corrupting data the caller did not intend to change.

### Finding Description
`DataWord(byte[] data)` takes the `data.length == WORD_SIZE` fast path and assigns the reference directly instead of copying it: [1](#0-0) 

`Storage.getValue(DataWord key)` wraps the cached row's backing array directly into a new `DataWord` without cloning: [2](#0-1) 

`StorageRowCapsule.getValue()`/`getData()` also return the internal `rowValue` array by reference, with no clone: [3](#0-2) 

Because of this chain, a `DataWord` returned from an SLOAD-style read shares its backing array with the `StorageRowCapsule` sitting in `Storage.rowCache`. `DataWord` exposes several in-place mutators that write directly into `this.data`: [4](#0-3) [5](#0-4) 

If a contract loads a storage value and then executes a bitwise opcode (`AND`/`OR`/`XOR`) or `SIGNEXTEND` using that loaded `DataWord` as the receiver (`this`), the underlying array is mutated in place — which is the *same array* referenced by the cached `StorageRowCapsule.rowValue`. This happens purely as a side effect of arithmetic on the stack value, with no explicit `SSTORE`/`put()` call. Since `Storage.commit()` persists any row whose `dirty` flag is set using whatever is currently in `rowValue`, a row that is dirty for an unrelated, legitimate reason (e.g., an earlier or later `SSTORE` to the same key in the same execution) can end up being committed with this corrupted value instead of the value that was actually written via `put()`.

### Impact Explanation
This produces divergence between the storage value a contract explicitly wrote via `SSTORE`/`put()` and the value ultimately persisted to the chain state, i.e., corrupted/unbacked contract storage. Because storage values back token balances, allowances, ownership records, and other invariants enforced entirely by contract logic, silent corruption of storage slots is a data-integrity/fund-safety issue reachable by any account that can deploy or call a contract (no special privilege required) — matching the required "unbacked balance / permanent freezing / incorrect account state" impact bar.

### Likelihood Explanation
Reaching this requires only ordinary EVM/TVM bytecode: `SLOAD` followed by `AND`/`OR`/`XOR`/`SIGNEXTEND` operating on the loaded word, executed by any transaction sender. No consensus/mining privilege, no malicious SR, and no external dependency is needed — this is exactly the "single signed transaction/contract call" reachable class the scan targets. However, I was not able to fully trace, within the available iterations, the exact opcode dispatch code (`OperationActions`/`OperationRegistry`) to confirm which operand (`this` vs. the popped stack argument) is mutated for `AND`/`OR`/`XOR`, nor whether `Program.storageLoad`/`storageSave` always route through `Storage.getValue`/`put` in the aliasing manner described, or whether an intermediate `.clone()` is inserted at the opcode dispatch layer that would neutralize the aliasing. This uncertainty means the exploitability of the *exact* trigger sequence (which opcode order corrupts which row) is plausible from the code shown but not fully proven end-to-end.

### Recommendation
- Make `DataWord(byte[] data)` always defensively copy the input array (as `getClonedData()` already does), removing the zero-copy fast path for `length == WORD_SIZE`.
- Make `Storage.getValue()` return `new DataWord(row.getValue().clone())` (or have `StorageRowCapsule.getValue()`/`getData()` return a clone) so stack values never alias cache-internal storage arrays.
- Audit all other call sites that pass externally-owned/cache-owned byte arrays directly into `new DataWord(...)` for the same aliasing hazard.

### Proof of Concept
Conceptual sequence within a single contract call (exact opcode ordering needs confirmation against `OperationActions`/`Program.storageLoad`, which I could not fully verify in the available time):
1. Contract executes `SSTORE(slot, X)` — creates a dirty `StorageRowCapsule` in `rowCache` with `rowValue = X`.
2. Contract executes `SLOAD(slot)` — `Storage.getValue()` returns `new DataWord(row.getValue())`, aliasing `row.rowValue`.
3. Contract executes `AND`/`OR`/`XOR`/`SIGNEXTEND` on the loaded `DataWord` — this mutates `this.data` in place, which is the same array as `row.rowValue`, silently changing the cached (still-dirty) row's value to something other than `X` without any further `SSTORE`.
4. On `commit()`, the corrupted value (not the value from step 1's explicit `SSTORE`, and not a value from any subsequent explicit `SSTORE`) is written to the store because `row.isDirty()` is still `true`. [6](#0-5)

  public DataWord(byte[] data) {
    if (data == null) {
      this.data = ByteUtil.EMPTY_BYTE_ARRAY;
    } else if (data.length == WORD_SIZE) {
      this.data = data;
    } else if (data.length < WORD_SIZE) {
      System.arraycopy(data, 0, this.data, WORD_SIZE - data.length, data.length);
    } else {
      throw new RuntimeException("Data word can't exceed 32 bytes: " + ByteArray.toHexString(data));
    }
  }

    }

  public void commit() {
    rowCache.forEach((DataWord rowKey, StorageRowCapsule row) -> {
      if (row.isDirty()) {
        if (new DataWord(row.getValue()).isZero()) {
          this.store.delete(row.getRowKey());
        } else {
          this.store.put(row.getRowKey(), row);
        }
      }
    });
