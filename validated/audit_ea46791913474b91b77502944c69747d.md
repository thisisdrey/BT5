Confirmed: there is no special-case handling anywhere in `pallet-assets` (native pallet or the ERC-20 precompile) for the case where the delegate/spender equals the owner/`from`. The `Approvals` storage lookup in `do_transfer_approved` is required unconditionally.

### Title
ERC-20 `transferFrom` precompile always requires an `Approvals` entry, reverting (and stranding funds) even when `spender == from` - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

### Summary
The `pallet-assets` ERC-20 precompile's `transfer_from` implementation unconditionally calls `pallet_assets::Pallet::do_transfer_approved`, which requires a pre-existing `Approvals` storage entry for `(asset_id, from, spender)`, regardless of whether `spender == from`. This is the same defect class as the Surge Protocol `Pool#transferFrom` bug: the allowance mechanism is invoked even when the caller is moving its own tokens, breaking compatibility with the very common "pull-only" integration pattern used by many external protocols and contracts (e.g. sweep/rescue functions, vault/router contracts that always call `transferFrom(self, recipient, amount)` instead of `transfer`). Because this precompile exposes a standard `IERC20` ABI to arbitrary EVM-style contracts on `pallet-revive`, callers reasonably expect ERC-20-idiomatic self-pull semantics to work; here they instead hit `Error::Unapproved` and revert.

### Finding Description
`transfer_from` in the precompile: [1](#0-0) 

calls `do_transfer_approved` in `pallet-assets`, which does a `try_mutate_exists` on the `Approvals` map keyed by `(id, owner, delegate)` and fails with `Error::<T, I>::Unapproved` if no approval exists — with no branch for `owner == delegate`: [2](#0-1) 

No code path in `pallet-assets` (native calls, `impl_fungibles.rs` trait impl, or the precompile) special-cases the case where the delegate/spender is the same account as the owner/`from`: [3](#0-2) 

This mirrors the reported Surge Protocol issue precisely: the allowance check (and the requirement that an `Approvals` entry exist at all) is applied even when the spender is the token owner itself, instead of short-circuiting to a direct transfer as many pull-based ERC-20 integrations assume.

### Impact Explanation
Any external contract or protocol on `pallet-revive` that (a) holds this asset via the ERC-20 precompile address and (b) implements the widespread "always call `transferFrom`" pull pattern to move its own balance (common in generic sweep/rescue utilities, some vault/router contracts, and generic ERC-20 handling libraries) will have those calls revert with `Unapproved` unless the contract first self-approves. Funds intended to be moved by such flows become effectively stuck/unreachable through that code path, which is a fund-availability/lock issue consistent with the "permanent user-fund lock" impact class, and is purely a token-standard compliance/interoperability defect in this repo's own precompile rather than an external protocol's mistake.

### Likelihood Explanation
Likelihood is moderate: it only manifests for specific integration patterns (contracts that call `transferFrom(self, ..)` instead of `transfer`), but this is a well-known and common pattern in the broader EVM ecosystem this precompile is designed to be compatible with (as evidenced by the repo's own recent focus on ERC-20 spec compliance, e.g. the `approve` set-semantics fix in `prdoc/stable2606/pr_11279.prdoc`). No privileged actor, governance, or malicious peer is required — any unprivileged holder/contract triggering this call pattern hits the revert.

### Recommendation
In `do_transfer_approved` (or in the precompile's `transfer_from` before calling it), short-circuit when `delegate == owner`/`spender == from`: perform a direct transfer via the existing transfer primitive (bypassing the `Approvals` lookup) instead of requiring an `Approvals` entry, matching the intent expressed in the bug report's fix (`if from != msg.sender { check/consume allowance }`).

### Proof of Concept
1. Deploy/hold `pallet-assets` asset `X` where account `A` (an EVM-style contract address mapped via `AddressMapper`) holds a balance of `X` through the `pallet-assets` ERC-20 precompile at `asset_addr`.
2. From `A`, call `transferFrom(A, B, amount)` on `asset_addr` without ever calling `approve(A, amount)` from `A` to itself.
3. The call reaches `Self::transfer_from` → `pallet_assets::Pallet::do_transfer_approved(asset_id, &A, &A, &B, amount)`.
4. `Approvals::<T,I>::try_mutate_exists((asset_id, A, A), ...)` finds no entry and returns `Error::<T,I>::Unapproved`, reverting the call (see `functions.rs:1024-1029`), even though `A` owns the tokens and is the caller.
5. Any protocol relying on this generic pull pattern to move `A`'s own tokens fails and the transfer cannot complete through that path, matching the "tokens becoming stranded" impact from the source report.
