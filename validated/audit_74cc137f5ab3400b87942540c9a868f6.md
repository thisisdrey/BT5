## Analysis

The Holograph bug's core invariant break is: **value is irreversibly committed/spent as soon as a "fire" operation is issued, but the receiving side's actual execution can fail asynchronously/silently, with no linkage back to the sender to detect the failure or recover the value** — the caller's `msg.value` is consumed by `nonRevertingBridgeCall`, the operator's job is marked done via a swallowed `catch`, and the ETH is stranded with no path to reclaim it.

A structurally identical pattern exists in the Snowbridge relayer-reward payment path in this repository.

### Title
Snowbridge relayer rewards can be permanently trapped on AssetHub because the reward-payment XCM omits an `AssetClaimer` hint - (`bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`pallet-bridge-relayers::claim_rewards_to` marks a relayer's reward as paid and clears the storage entry as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge rewards, `pay_reward` is `PayAccountOnLocation::pay_reward`, which only guarantees that an XCM *ticket was validated, the local fee charged, and the message enqueued* to be sent to AssetHub — it does not, and cannot, know whether the remote `DepositAsset` to the relayer's beneficiary location actually succeeds on AssetHub. If that remote execution fails, the assets are trapped in AssetHub's `PolkadotXcm` asset trap under an origin the relayer does not control, because unlike the sibling inbound-message-processing code path, this reward XCM never sets a `SetHints{AssetClaimer}` instruction.

### Finding Description
`PayAccountOnLocation::pay_reward` builds and sends this XCM to AssetHub: [1](#0-0) 

Note there is no `SetHints { hints: [AssetClaimer{..}] }` instruction anywhere in this program, unlike the inbound message converter for the same bridge, which explicitly adds a claimer *specifically to guard against this failure mode*: [2](#0-1) 

The origin register for this reward XCM is set via `DescendOrigin(InboundQueueLocation)` then `UniversalOrigin(GlobalConsensus(Ethereum))` — a technical bridge/system location, not the relayer's account. If `DepositAsset { assets: AllCounted(1), beneficiary }` fails on AssetHub for any of the ordinary reasons XCM `DepositAsset` can fail (beneficiary account below existential deposit, asset not registered/known at the reanchored location, transient barrier/weight issue), the assets fall into holding and get trapped via `PolkadotXcm::AssetsTrapped` against that technical bridge origin — not against the relayer. The relayer has no way to construct an XCM that authenticates as that origin, so the reward is permanently unclaimable.

Meanwhile, on the source chain (BridgeHub), the reward was already considered "paid": `do_claim_rewards` calls `pay_reward`, and because `pay_reward` returns `Ok(())` as soon as the ticket is delivered into the queue (not when the remote deposit actually completes), the `RelayerRewards` storage entry is cleared and a `RewardPaid` event is emitted: [3](#0-2) 

This is precisely the Holograph pattern: the "job" (asset delivery) is considered done based on the sending step succeeding, while the actual execution that matters (the deposit to the true beneficiary) happens later, out-of-band, and its failure is invisible to and unrecoverable by the party who was supposed to receive value.

This differs from `pallet-revive`/`pallet-contracts`, where every value transfer inside a call/instantiate frame is wrapped in `with_transaction`, guaranteeing atomic rollback of the whole frame (including balance transfers) on failure: [4](#0-3) 
That protection only covers same-chain, synchronous execution; it cannot and does not extend across an XCM hop to another chain, which is exactly the gap exploited here.

### Impact Explanation
Any relayer earning Snowbridge rewards on BridgeHub can have their claimed reward permanently and unrecoverably trapped on AssetHub with no local error, no retry mechanism, and no compensating storage state (the pending reward entry is already cleared). This is a direct, unbacked loss of relayer funds and a broken settle-exactly-once guarantee for bridge reward payouts — falling under "permanent user-fund or bridge-state lock" and "duplicate settlement or payout state advancing before execution/settlement succeeds," both explicitly in-scope impact categories.

### Likelihood Explanation
No malicious actor, governance action, or leaked key is required. A single relayer whose registered/rewarded beneficiary location fails `DepositAsset` on AssetHub (e.g., an uninitialized/under-ED account, or any transient AssetHub-side condition affecting the specific asset/account) triggers the loss purely through normal `claim_rewards_to` usage. The codebase's own test suite demonstrates the project is aware trapped-asset scenarios are a real, reachable outcome of XCM-based settlement in this exact bridge (see `invalid_xcm_traps_funds_on_ah` and the `fallback_claimer_*` tests), and even fixed exactly this problem for the *inbound* asset path by adding an `AssetClaimer` fallback — but the analogous *reward-payment* path was left without that mitigation: [5](#0-4) [6](#0-5) 

### Recommendation
Add a `SetHints { hints: [AssetClaimer { location: beneficiary }] }` instruction to the XCM built in `PayAccountOnLocation::pay_reward`, mirroring the mitigation already applied in `MessageToXcm::convert` for inbound messages, so that if `DepositAsset` fails, the relayer (the actual beneficiary) — not an unreachable technical bridge origin — is the one able to claim the trapped assets via `pallet_xcm::claim_assets`.

### Proof of Concept
1. Register a relayer and accrue a Snowbridge reward via `pallet_bridge_relayers::register_relayer_reward` with `BridgeReward::Snowbridge`.
2. Call `claim_rewards_to` with a `BridgeRewardBeneficiaries::AssetHubLocation` beneficiary whose corresponding AccountId32 does not yet exist / has insufficient balance to satisfy AssetHub's existential deposit for the deposited asset, or whose target foreign-asset registration is missing at the reanchored Ethereum location.
3. Observe on BridgeHub: `pay_reward` returns `Ok(())` (ticket validated and delivered into the outbound queue), the `RelayerRewards` entry is cleared, and `RewardPaid` is emitted — the source chain believes settlement is final.
4. Observe on AssetHub: the XCM executes, `DepositAsset` fails, and `PolkadotXcm::AssetsTrapped` fires with `origin` equal to the descended/universal bridge-technical location (not the relayer or the intended beneficiary AccountId32).
5. Attempt `claim_assets` signed by the relayer/beneficiary using the technical trap origin location — it fails (unreachable/unauthenticatable origin), analogous to `fallback_claimer_trap_cannot_be_claimed_by_other_account` demonstrating that only the exact matching origin can claim. The relayer's reward is now permanently lost, with the same "value already consumed, execution failed, no recovery path" outcome as the Holograph `executeJob`/`nonRevertingBridgeCall` scenario.

		relayer: &Relayer,
		_: (),

		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

	fn transfer<S: State>(
		origin: &Origin<T>,
		from: &T::AccountId,
		to: &T::AccountId,
		value: U256,
		preservation: Preservation,
		meter: &mut ResourceMeter<T, S>,
		exec_config: &ExecConfig<T>,
	) -> DispatchResult {
		let value = BalanceWithDust::<BalanceOf<T>>::from_value::<T>(value)
			.map_err(|_| Error::<T>::BalanceConversionFailed)?;
		if value.is_zero() {
			return Ok(());
		}

		if <System<T>>::account_exists(to) {
			return transfer_with_dust::<T>(from, to, value, preservation);
		}

		let origin = origin.account_id()?;
		let ed = <T as Config>::Currency::minimum_balance();
		let is_eth_tx = exec_config.collect_deposit_from_hold.is_some();
		with_transaction(|| -> TransactionOutcome<DispatchResult> {
			// Meter the ED deposit only after the transfer succeeds: the meter is not rolled
			// back, so metering earlier would count an ED for an account never created.
			match Ok::<(), DispatchError>(())
				.and_then(|_| {
					if is_eth_tx {
						let credit = T::FeeInfo::withdraw_txfee(ed)
							.ok_or(Error::<T>::StorageDepositNotEnoughFunds)?;
						T::Currency::resolve(to, credit)
							.map_err(|_| Error::<T>::StorageDepositNotEnoughFunds)?;
						Ok(())
					} else {
						T::Currency::transfer(origin, to, ed, Preservation::Preserve)
							.map(|_| ())
							.map_err(|_| Error::<T>::StorageDepositNotEnoughFunds.into())
					}
				})
				.and_then(|_| transfer_with_dust::<T>(from, to, value, preservation))
				.and_then(|_| meter.charge_deposit(&StorageDeposit::Charge(ed)))
			{
				Ok(_) => TransactionOutcome::Commit(Ok(())),
				Err(err) => TransactionOutcome::Rollback(Err(err)),
			}
		})
	}

/// When an inbound message arrives without a (valid) claimer, the converter falls back
/// to the bridge owner sovereign account, anchored on the local network. This test
/// drives the full claim flow: invalid XCM payload causes the holding register to be
/// trapped against that fallback location on Asset Hub, and the bridge owner signed
/// origin then claims the trapped assets via `pallet_xcm::claim_assets`.
///
/// Before the fix, the fallback claimer used `network: None`, so the trap origin did
/// not match the location produced by Asset Hub's `SignedToAccountId32` converter
/// (which always tags the local network), and the claim would fail with `UnknownClaim`.
#[test]
fn fallback_claimer_traps_to_bridge_owner_and_claim_assets_succeeds() {
	use asset_hub_westend_runtime::xcm_config::RelayNetwork as AssetHubRelayNetwork;

	let relayer_account = BridgeHubWestendSender::get();
	let relayer_reward = 1_500_000_000_000u128;
	let bridge_owner = snowbridge_sovereign();

	// Fund the bridge owner so it has the existential deposit when claim_assets executes
	// (the claim deposits the assets back to the same account).
	AssetHubWestend::fund_accounts(vec![(bridge_owner.clone(), INITIAL_FUND)]);

	let value: u128 = 1_500_000_000_000;
	let execution_fee: u128 = 1_500_000_000_000;
	let weth_value: u128 = 2_800_000_000_000;

	let assets = vec![NativeTokenERC20 { token_id: WETH.into(), value: weth_value }];

	set_up_eth_and_dot_pool();

	BridgeHubWestend::execute_with(|| {
		type RuntimeEvent = <BridgeHubWestend as Chain>::RuntimeEvent;

		// Invalid XCM bytes — converter decodes this as an empty Xcm, leaving the
		// non-fee assets in holding to be trapped on AH.
		let invalid_xcm_payload = hex!("02806c072d50e2c7cd6821d1f084cbb4").to_vec();

		let message = Message {
			gateway: EthereumGatewayAddress::get(),
			nonce: 1,
			origin: EthereumGatewayAddress::get(),
			assets,
			payload: Payload::Raw(invalid_xcm_payload),
			// No claimer — exercises the bridge_owner fallback.
			claimer: None,
			value,
			execution_fee,
			relayer_fee: relayer_reward,
		};

		EthereumInboundQueueV2::process_message(relayer_account.clone(), message).unwrap();

		assert_expected_events!(

					reward_balance: *reward_balance == relayer_reward,

			]
		);
	});

	let expected_claimer_location = Location::new(

		[AccountId32Junction {
			network: Some(AssetHubRelayNetwork::get().expect("RelayNetwork is Some")),
			id: bridge_owner.clone().into(),
		}],
	);
