### Title
StackerDB chunk signatures are not bound to the target contract, enabling cross-StackerDB chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the signed digest over only `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's `QualifiedContractIdentifier`. Every verification path (`validate_received_chunk`, `try_replace_chunk`, HTTP `poststackerdbchunk`) checks the signature against the slot owner registered *for a given contract*, but the signature itself carries no binding to that contract. A chunk legitimately signed by a signer for one StackerDB instance is therefore also a valid signature for any other StackerDB instance in which that same signer address happens to own the same `slot_id`, as long as the `slot_version`/`data_hash` requirements of the target replica are satisfied.

### Finding Description
The signing/verification logic lives in `libstackerdb/src/libstackerdb.rs`: [1](#0-0) 
`auth_digest()` hashes `slot_id`, `slot_version`, and `data_hash` only — no contract identifier is part of the signed material, and `verify()` only checks that the recovered public key hash equals the passed-in `principal`.

Every call site that performs authorization does so by first looking up the expected signer *for a specific contract*, then calling this contract-agnostic `verify()`:
- `StackerDBs::try_replace_chunk` looks up `slot_validation.signer` for `smart_contract` and calls `slot_desc.verify(&slot_validation.signer)`: [2](#0-1) 
- `PeerNetwork::validate_received_chunk` (used by both the sync path and unsolicited `StackerDBPushChunk` handling) does the same: it fetches `get_slot_signer(smart_contract_id, data.slot_id)` and calls `slot_metadata.verify(&addr)`: [3](#0-2) 

Because the contract identity is never part of what's actually signed, if the same signer address is assigned the same `slot_id` in two different StackerDB contracts (a realistic scenario for Stacks signer-set StackerDBs, which are re-deployed per reward cycle and reuse the same signer ordering/slot assignment across cycles), a chunk signed for contract A's slot N is a cryptographically valid, unmodified message for contract B's slot N. An attacker (or any relayer) can capture a chunk originally written to StackerDB A and submit it — verbatim, signature included — as a write to StackerDB B's identically-slotted signer, as long as B's slot version/size checks are satisfied (e.g., a freshly-provisioned StackerDB starts at version 0, so any previously-captured version-1+ chunk from a different contract will pass the "not stale" check).

This breaks the equality the protocol is supposed to enforce: "signed for *this* StackerDB write" vs. "signed by the right key for *some* slot, in *some* context." It is directly analogous to the reported issue where a signature/authorization check succeeded without validating the auxiliary account (sysvar) that scopes what the signature is actually attesting to.

### Impact Explanation
This allows unauthorized/forged writes to a StackerDB replica that never actually received a signature from its own smart-contract-registered signer for that specific write, and such forged writes propagate network-wide via `process_stacker_db_chunks`/`broadcast_message` once accepted: [4](#0-3) 
This matches the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact tiers, since a chunk that was never authorized for the target contract can be accepted and rebroadcast as legitimate.

### Likelihood Explanation
Exploitability requires a target StackerDB contract where the attacker-controlled or observed signer's slot assignment collides with a chunk they can obtain from another StackerDB (or the same contract's prior/future reward cycle instance) — a condition that is plausible given Stacks' pattern of redeploying per-cycle signer StackerDB contracts with deterministic, often-repeating signer/slot mappings. No secret key or privileged role is required; the attacker only needs network read access to a previously broadcast, validly-signed chunk and a write/relay path to the target contract.

### Recommendation
Include the StackerDB's `QualifiedContractIdentifier` (or a stable numeric/contract-derived domain separator) in `SlotMetadata::auth_digest()` so signatures are cryptographically bound to the specific StackerDB instance they authorize, and require callers of `verify()`/`try_replace_chunk`/`validate_received_chunk` to pass in the contract context so it cannot be omitted or substituted.

### Proof of Concept
1. Deploy (or observe) two StackerDB contracts, A and B, in which the same signer address `S` is assigned `slot_id = N` (this occurs naturally across reward-cycle-specific signer StackerDB redeployments).
2. Have `S` sign and successfully write a chunk to contract A at slot `N`, version `V`, capturing the resulting `StackerDBChunkData { slot_id: N, slot_version: V, sig, data }` from the network (e.g., via `StackerDBPushChunk` gossip or the `/v2/stackerdb/.../chunks` GET endpoint).
3. Replay the identical `StackerDBChunkData` bytes to contract B's slot `N` (e.g., via `POST /v2/stackerdb/{B}/{contract}/chunks` or by injecting a `StackerDBPushChunk` P2P message naming contract B), where B's stored version for slot `N` is `< V`.
4. `validate_received_chunk`/`try_replace_chunk` for contract B will succeed because `slot_metadata.verify(&addr_for_B)` passes (same signer `S`, same digest inputs), even though `S` never signed anything scoped to contract B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
