### Title
Unvalidated `RelayFromAddr` in `CreateRelayRequest` Lets an Authenticated Peer Poison Relay State for an Arbitrary VPN Address - ([File: relay_manager.go])

### Summary
`handleCreateRelayRequest` in `relay_manager.go` accepts the `RelayFromAddr`/`RelayToAddr` fields of a `NebulaControl_CreateRelayRequest` message from any host with an already-authenticated tunnel (`h`), and uses the attacker-supplied `from` address directly as the key that identifies "who this relay entry is for," without ever checking that `from` corresponds to `h`'s own certificate-bound `vpnAddrs`. This mirrors the reported bug class: data taken from one context (an unrelated address claim inside a control message) is applied to a different context (the relay routing table) without validating it belongs together, letting an authenticated party's message be reinterpreted for someone else's benefit/detriment.

### Finding Description
When a peer with a live, authenticated tunnel (`h`) sends a `CreateRelayRequest` claiming to be the target (`f.myVpnAddrsTable.Contains(target)`), the code does: [1](#0-0) 

Specifically, `from := protoAddrToNetAddr(m.RelayFromAddr)` is taken straight from the message and is never compared against `h.vpnAddrs[0]` (the cryptographically verified identity of the peer that actually sent this authenticated control message). It is then used as the map key for the terminal relay association: [2](#0-1)

`AddRelay` stores `PeerAddr: vpnIp` (i.e., `from`) tied to `relayHostInfo` (`h`), inserted into `h.relayState.relayForByAddr[from]`: [3](#0-2) [4](#0-3) 

Nothing here confirms that `h` is the address in `from`, that `from`'s certificate actually designates `h` as a relay, or that `h` has any legitimate right to be recorded as relaying traffic "for" that address. By design, `from` is *supposed* to differ from `h.vpnAddrs[0]` in the legitimate middle-relay case (the middleman relays "for" the initiator), but the receiving/terminal node has no cryptographic means to verify that claim — it simply trusts whatever address the sending peer states in the control message.

### Impact Explanation
This is a remote state-poisoning primitive reachable by any peer that can complete an ordinary handshake with a target (no CA-signed cert forgery required — any legitimately-issued, non-privileged node in the mesh can do this). By repeatedly sending `CreateRelayRequest` messages with `RelayFromAddr` set to arbitrary victim VPN addresses, an attacker can:
- Populate the target's `relayState.relayForByAddr` table with entries that associate victim VPN addresses to the attacker's own `HostInfo`/tunnel.
- Influence subsequent relay-selection/forwarding logic (`QueryVpnAddrsRelayFor`, `handleOutsideRelayPacket` ForwardingType path) that consults this same state when routing traffic destined for those addresses, potentially diverting or exposing traffic intended for a legitimate third party through the attacker's own tunnel instead of the genuine relay path.
- Cause `AddRelay`'s `unlockedMakePrimary(relayHostInfo)` side effect to promote the attacker's `HostInfo` as primary for repeated victim-address claims, further entangling hostmap/relay bookkeeping.

This falls under the "remote state poisoning" impact category explicitly accepted by the validation rules, and is reachable purely over the data plane by an attacker holding a valid (but otherwise unprivileged) certificate — no CA-signing capability is required.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment that enables relays (`relay.use_relays`/`relay.am_relay`), since any two mesh members can already exchange `Control` messages once a handshake completes, and `handleCreateRelayRequest`'s terminal branch performs no authorization check binding `from` to the sender's own identity before mutating relay state.

### Recommendation
Validate that `RelayFromAddr`/`OldRelayFromAddr` in an inbound `CreateRelayRequest` corresponds to a value the receiving node can trust for that specific tunnel — e.g., require that the terminal node only accept `from` claims that match an address the sending peer (`h`) is entitled to relay for (analogous to how the reported DeFi fix removed the ability for a caller to freely choose unrelated data and instead bound the operation strictly to the specific record it belongs to). At minimum, cross-check `from` against lighthouse-provided/relay-list metadata for `h`, or require that `from` matches `h.vpnAddrs[0]` for the legitimate "I am relaying for myself" case and reject/flag third-party claims that cannot be otherwise attested.

### Proof of Concept
1. Attacker (`A`) establishes a normal, valid handshake/tunnel with target `T` (both hold legitimately CA-issued certs; `T` has `relay.am_relay`/accepts relay requests).
2. `A` sends `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <Victim V's vpn addr>, RelayToAddr: <T's own vpn addr>}` over its authenticated tunnel to `T`.
3. In `handleCreateRelayRequest`, `T` sees `target == self`, `from == V`'s address (not `A`'s), and — finding no existing relay entry for `V` — calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` where `h` is `A`'s `HostInfo`. This installs `T.relayState.relayForByAddr[V] -> {PeerAddr: V, via A's HostInfo}` with no verification that `A` is actually entitled to relay for `V`.
4. `T` replies with `CreateRelayResponse`, completing a relay association from `T`'s perspective that "traffic for `V` flows through `A`," entirely under `A`'s control and without `V`'s knowledge or consent — demonstrating the state-poisoning primitive described above.

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}
