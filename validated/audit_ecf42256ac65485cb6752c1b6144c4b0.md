## Analysis

The Sherlock bug class is: a subtraction between two **independently-tracked totals** that are assumed to satisfy an invariant (`_flow.totalSupply() >= _ve.totalSupply()`), used inside a function that fires on essentially every protocol interaction. When the invariant is violated (due to rounding/accounting drift between the two independently-maintained counters), the subtraction underflows and reverts, causing systemic DOS.

The Zest vault contracts contain the same pattern in `accrue()`, where `treasury-lp` (the DAO-treasury reserve mint) is computed as:

```clarity
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```

`total-assets-preview` and `reserve-inc` are derived from two **separately tracked** state variables — `assets`, `total-borrowed`, and `principal-scaled` — which are updated independently across `deposit`, `redeem`, `system-borrow`, `system-repay`, and `socialize-debt`. `system-repay` and `socialize-debt` both reduce `total-borrowed`/`principal-scaled` using floor-rounded proportional math (`calc-principal-ratio-reduction`, `mul-div-down`), which can let `total-borrowed` drift so that the implicit invariant `old-debt >= total-borrowed` (analogous to `_flow.totalSupply() >= _ve.totalSupply()`) erodes over repeated operations. Once `reserve-inc` exceeds `total-assets-preview`, the subtraction underflows, `accrue()` reverts with an arithmetic error, and since `accrue` is invoked via `try!` at the top of every `deposit`, `redeem`, `system-borrow`, and `system-repay` call, the entire vault becomes unusable — matching the "temporary freezing of funds" impact class. ### Title
Vault `accrue()` treasury-lp reserve calculation can underflow-revert, causing DOS of deposit/redeem/borrow/repay - (File: mainnet/contracts/vault/v0-vault-usdh.clar, mirrored identically in v0-vault-stx.clar, v0-vault-sbtc.clar, v0-vault-ststx.clar, v0-vault-usdc.clar, v0-vault-ststxbtc.clar)

### Summary
Each vault's `accrue()` function mints a treasury reserve fee (`treasury-lp`) using `(mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))`. `total-assets-preview` and `reserve-inc` are computed from separately-updated state variables (`assets`, `total-borrowed`, `principal-scaled`). Repeated `system-repay`/`socialize-debt` calls, which use floor-rounding proportional reductions, can erode the invariant that the interest embedded in `total-assets-preview` always exceeds `reserve-inc`, ultimately causing the subtraction to underflow and abort the transaction.

### Finding Description
`accrue()` computes:
```
old-debt = mul-div-down(principal-scaled, idx, PRECISION)
new-debt = mul-div-down(principal-scaled, next, PRECISION)
debt-delta = new-debt - old-debt (or 0)
reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)
treasury-lp = mul-div-down(reserve-inc, total-supply, total-assets-preview - reserve-inc)
```
`total-assets-preview = current-assets + (debt-preview - total-borrowed if positive else 0)`, and `debt-preview` is derived from the same `principal-scaled`/index state. `reserve-inc` is only safely smaller than `total-assets-preview` if the accrued-but-unpaid-interest buffer (`debt - total-borrowed`) stays non-negative and larger than the new fee slice every accrual. `system-repay` reduces `total-borrowed` by `principal-repaid = mul-div-down(capped-amount, total-borrowed, debt)` and `socialize-debt` reduces it similarly with `mul-div-down`, both floor-rounding the amount removed from `total-borrowed`. Because these reductions are computed independently from the debt/index math used for the fee calculation, repeated calls (including many small `system-repay`/`socialize-debt` operations) can drift `total-borrowed` relative to the true accrued debt, shrinking or eliminating the safety margin the subtraction depends on — exactly the same class of issue as the Minter's `circulating_supply()` comparing two independently maintained totals (`_flow.totalSupply()` vs `_ve.totalSupply()`) that are assumed, but not guaranteed, to satisfy an ordering invariant.

### Impact Explanation
`accrue()` is invoked via `try!` at the start of `deposit`, `redeem`, `system-borrow`, and `system-repay` in every vault contract. If the subtraction underflows, all of these entrypoints revert, freezing the vault — suppliers cannot redeem, borrowers cannot repay, and the DAO treasury cannot receive its accrued reserve share, which falls under temporary (or, if unrecoverable without an upgrade, permanent) freezing of funds/yield.

### Likelihood Explanation
Triggering requires driving `reserve-inc` above `total-assets-preview - reserve-inc`, i.e., accumulating enough rounding drift between `total-borrowed` and the true accrued debt through many `system-repay`/`socialize-debt` cycles, or hitting the edge case where `debt-preview <= total-borrowed` (interest term forced to zero) while `debt-delta > 0` still yields a nonzero `reserve-inc`. This is a state-dependent, multi-transaction path reachable by ordinary borrowers/repayers over time rather than a single-call exploit, so likelihood is moderate rather than trivial.

### Recommendation
Clamp the denominator the same way other parts of the codebase already clamp differences (e.g., `(if (> a b) (- a b) u0)`), e.g.:
```clarity
(denom (if (> (total-assets-preview) reserve-inc) (- (total-assets-preview) reserve-inc) u0))
(treasury-lp (if (and (> reserve-inc u0) (> denom u0)) (mul-div-down reserve-inc (total-supply) denom) u0))
```
and audit `system-repay`/`socialize-debt` rounding direction to ensure `total-borrowed` can never be tracked higher than the true accrued principal.

### Proof of Concept
1. Deploy a vault, have a borrower open debt via `system-borrow`.
2. Repeatedly call `system-repay` with small amounts crafted so that `mul-div-down(capped-amount, total-borrowed, debt)` floors to a value that removes less principal proportionally than warranted each time (dust-sized repayments maximize rounding loss).
3. Over enough iterations, `total-borrowed` converges toward (or exceeds, in aggregate rounding terms) the actual accrued debt tracked via `principal-scaled`/`index`, shrinking the `debt-preview - total-borrowed` interest term used in `total-assets-preview`.
4. Once a subsequent `accrue()` call computes `reserve-inc >= total-assets-preview`, the `(- (total-assets-preview) reserve-inc)` subtraction underflows and the transaction reverts, and since every vault entrypoint calls `accrue()` first, the vault becomes stuck for all users.
