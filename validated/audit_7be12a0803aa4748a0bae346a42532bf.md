## Analysis

The Sudoswap-style rounding-direction issue maps to java-tron's on-chain order book (`MarketSellAssetContract` / Market module), which lets any account place and match limit orders — reachable by an unprivileged transaction broadcaster.

### Title
Inconsistent floor-only rounding in on-chain order matching systematically shortchains makers - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`MarketUtils.multiplyAndDivide` always truncates (floor-rounds) the result of `a*b/c`, and this single rounding direction is reused for every quantity computation in `MarketSellAssetActuator.matchSingleOrder`, regardless of whether the computed value is a payment owed *to* the maker or an amount delivered *to* the taker. Because some code paths pair a floor-divided quantity with an *exact* (non-divided) counter-quantity, whichever side's exchanged amount is derived via division systematically loses up to 1 unit of value per match, and in the "taker > maker" full-consumption case this loss falls specifically on the maker.

### Finding Description
`MarketUtils.multiplyAndDivide` at [1](#0-0)  computes `floor(a*b/c)` with no rounding-mode parameter — it is always used as a floor/truncating division, both in the fast integer path (`floorDiv`) and in the `BigInteger` fallback (`divide`, which truncates toward zero for positive operands).

This helper is called from `MarketSellAssetActuator.matchSingleOrder` in three places [2](#0-1) [3](#0-2) [4](#0-3) .

In the `taker > maker` branch, the taker receives the maker's *entire remaining sell quantity* as an exact amount (`takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()`), while the corresponding payment the maker is owed (`makerBuyTokenQuantityReceive`) is computed via `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which floors [5](#0-4) . The same asymmetric pattern occurs in the `taker == maker` branch [6](#0-5) : the taker receives the maker's full remaining quantity exactly, but the maker's proceeds are the floored `multiplyAndDivide` result.

This is precisely the rounding-direction pattern flagged in the external report: because only floor rounding is used everywhere (no ceiling counterpart for the amount a "seller"/maker is owed), whenever a division determines what the maker receives, the maker is always paid at or below the fair proportional amount, never above it — a one-sided rounding bias rather than the recommended "round the amount owed to the seller up, round the amount given to the buyer down."

### Impact Explanation
Each individual match leaks at most 1 unit of the maker's buy-token (bounded by integer division truncation), but:
- For tokens with few decimals (the exact scenario the external report calls out as worse), a truncation of "up to 1 unit" is a much larger relative loss.
- A taker can deliberately construct many small matching trades against a target maker's resting order(s) to repeatedly trigger the floor-rounding branch and accumulate value extracted from makers across the trade history, since the mechanism (`MarketSellAssetContract`) is directly reachable by any account via a signed transaction with no special privilege.
- This causes an unbacked/incorrect balance state for maker orders (maker's `SellTokenQuantityRemain` is zeroed while it received less than the proportionally-owed buy token), i.e., actual value leaves the system in the taker's favor, matching the "unauthorized value transfer / financial loss for pair creators" impact class from the original report.

### Likelihood Explanation
Any account can call `MarketSellAssetActuator` to place and immediately match against existing orders; the floor rounding triggers deterministically whenever a division-derived quantity is used instead of an exact remaining-balance quantity (i.e., whenever an order is fully consumed by the counter side, which is a routine, easily engineered condition, especially with small-quantity, low-decimal token pairs to maximize relative rounding loss per trade).

### Recommendation
Round in favor of the party being paid: when computing the amount owed to the maker (the "seller" of the matched leg), round up (`ceil`) rather than floor; only round down amounts computed for the receiving/consuming side (the taker) or protocol fee accounting, consistent with the sudoswap fix direction (buy price/fees round up, sell payout amounts round down) so that the resting order side never receives less value than its quoted price implies.

### Proof of Concept
1. Maker places a sell order via `MarketSellAssetContract` with `sellTokenQuantity` / `buyTokenQuantity` chosen such that `sellTokenQuantity` does not evenly divide `buyTokenQuantity` (e.g., sell 3 units of token A for 10 units of token B).
2. Taker places a matching sell order for token B against A sized so the "taker > maker" branch in `matchSingleOrder` is hit (taker's order fully consumes the maker's remaining sell quantity).
3. `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` truncates the maker's true proportional payment down by a fractional unit while `takerBuyTokenQuantityReceive` is credited the maker's full remaining token A.
4. Repeat across many crafted small trades to accumulate the rounding difference at the maker's expense. [1](#0-0) [5](#0-4)
