### Title
Non-canonical (short, non-20-byte) `zonefile-hash` in a valid BNS transaction is silently dropped by `AttachmentInstance::try_new_from_value`, causing that name's attachment binding to never be tracked - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`bns.clar` declares `zonefile-hash` as `(buff 20)`, which in Clarity means "buffer of length **up to** 20 bytes," not exactly 20. An attacker can legitimately register a name and then call `name-update`/`name-renewal`/`name-transfer` with a `zonefile-hash` buffer of length 1-19 (neither empty nor 20 bytes). This is a fully valid, consensus-accepted transaction that increments the contract's `attachment-index` and emits a `print` event, but `AttachmentInstance::try_new_from_value` (`stackslib/src/net/atlas/mod.rs:186-236`) only special-cases a length-0 buffer (`Hash160::empty()`); for any other length that isn't exactly 20, `Hash160::from_bytes` returns `None` and the whole function returns `None`, silently discarding the `AttachmentInstance` for that on-chain commitment.

### Finding Description
The claimed equality "AttachmentInstance recorded == AttachmentInstance actually committed on-chain" is broken by omission. The code path: [1](#0-0) 

only handles `content_hash.data.is_empty()` as a special zero-length case; for `1 <= len < 20` and `len > 20`, `Hash160::from_bytes` returns `None`, and `try_new_from_value` returns `None` at line 208 with no logging, no error, no partial record. Meanwhile the on-chain contract accepts any buffer up to 20 bytes for `zonefile-hash`: [2](#0-1) [3](#0-2) 

The `update-zonefile-and-props` private function unconditionally increments the shared `attachment-index` cursor and emits the print event before the atlas layer ever sees it, so the attacker does not need any privileged role - just a normally registered BNS name (obtainable by anyone via `name-preorder`/`name-register`) and a subsequent `name-update` call with a short (non-20, non-empty) hash buffer. This transaction is fully valid Clarity execution and gets mined/confirmed like any other.

### Impact Explanation
The dropped `AttachmentInstance` means the atlas subsystem never queues/tracks a fetch for that name's zonefile update; the node keeps serving whatever content (or none) it had previously resolved for that name's `content_hash`, forever, for that specific attachment index. This is a real BNS/attachment mismatch: the node serves state that does not match what was canonically committed on-chain, matching the "attachment/BNS mismatch" High-impact category described in the rules. It is deterministic and repeatable per crafted transaction, and does not require any privileged secret, peer key, or admin role - it requires only a mined transaction from any user account holding the target name.

### Likelihood Explanation
Preconditions: attacker needs to control (or have registered) a BNS name, which anyone can do by paying the standard preorder/register fee - no special role or secret needed. The malformed hash length (1-19 bytes) must be crafted in the `name-update`/`name-transfer`/`name-renewal` transaction payload, which is straightforward since Clarity's `(buff 20)` type only bounds the maximum length. This requires a mined transaction (cost = normal tx fee), but no privileged access, no compromised dependency, and no reliance on race conditions - it is a deterministic, always-reproducible bug given a transaction of the crafted shape is confirmed.

### Recommendation
In `AttachmentInstance::try_new_from_value`, do not silently drop mismatched-length hashes. Either (a) reject/pad deterministically consistent with the contract's actual semantics (if the contract logically zero-pads or treats sub-20-byte buffers as valid hashes) so parsing matches on-chain semantics exactly, or (b) if such a value should never occur given the contract logic, log a loud error/warning and still track the instance with a well-defined sentinel (rather than `None`), so operators can detect indexing gaps instead of them being invisible. Ideally, harden the same by having `bns.clar` assert `(is-eq (len zonefile-hash) u20)` (as is already done elsewhere for `hashed-salted-namespace`, see line 334) so only exactly-20-byte or empty (cleared) hashes are ever emitted on-chain, closing the mismatch at the source.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (extending existing test patterns that already call `try_new_from_value`):
1. Build a `Value::Tuple` mirroring the `print` event shape emitted by `update-zonefile-and-props`, with `attachment.hash` set to a `Value::Sequence(SequenceData::Buffer(BuffData { data: vec![0u8; 10] }))` (10 bytes - neither 0 nor 20).
2. Call `AttachmentInstance::try_new_from_value(&value, &contract_id, index_block_hash, stacks_block_height, tx_id, None)`.
3. Assert the result is `None`.
4. Separately construct the equivalent legitimate on-chain scenario conceptually: a `name-update` transaction with `zonefile-hash` of length 10 is accepted by `bns.clar` (type-checks fine against `(buff 20)`), incrementing `attachment-index` and emitting the print event - demonstrating the divergence between "accepted on-chain" and "tracked by atlas" for the same transaction.
