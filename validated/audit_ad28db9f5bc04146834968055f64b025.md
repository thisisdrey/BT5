### Title
Remote peer can inject an attachment whose content does not hash to the requested `content_hash`, poisoning the Atlas attachments store - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever comparing `response.attachment.hash()` to the `request.content_hash` that was actually requested. The attachment is later written into the AtlasDB via `insert_instantiated_attachment` keyed by whatever hash the attacker's payload actually has, not the hash that was requested.

### Finding Description
In `extend_with_attachments` [1](#0-0) , the loop iterates over `results.succeeded` (pairs of `AttachmentRequest` and the peer's `StacksHttpResponse`), decodes the response via `decode_atlas_get_attachment()`, and unconditionally does `self.attachments.insert(response.attachment)` — there is no check that `response.attachment.hash() == request.content_hash`.

Downstream, in `AttachmentsDownloader::run`, the `Done` state drains `context.attachments` and, for each attachment, calls `atlasdb.find_all_attachment_instances(&attachment.hash())` and then unconditionally `atlasdb.insert_instantiated_attachment(&attachment)` [2](#0-1) . It then resolves `context.attachments_batch.resolve_attachment(&attachment.hash())` — using the attachment's *own* self-reported hash, not the originally-requested `content_hash`. This means a peer responding to a request for `content_hash = H1` can return any payload with `hash() = H2`, and the code will happily accept, store, and mark it resolved under `H2`, while the batch's entry for `H1` remains unresolved (and will eventually be retried/dropped) — exactly the "poisoned-absent" scenario described: `H1` never resolves, but arbitrary attacker-chosen bytes are permanently written into the AtlasDB's attachments table under `H2`.

The requestable `AttachmentRequest::make_request_type` only builds the outgoing GET request for `content_hash` [3](#0-2)  — there is no verification hook when the response comes back. No other code path in `download.rs` performs a hash check on attachment content received via this batched-attachment-download flow.

### Impact Explanation
A malicious/unprivileged peer serving `GET /v2/attachments/{content_hash}` can return arbitrary attacker-controlled bytes as the `attachment.content`, and the requesting node will store them in its AtlasDB indexed by the actual (attacker-chosen) hash of that content, consuming disk space and DB rows for content that is not referenced by any confirmed on-chain name operation. Meanwhile, the legitimately-requested `content_hash` remains unresolved, so BNS attachment lookups keyed by that hash continue to fail even though the batch believed it "succeeded" a request. This matches the described High-impact "attachment/BNS mismatch" category — data is stored that doesn't correspond to what was committed on-chain for that hash, and repeated exploitation lets any responding peer grow the node's Atlas attachments table indefinitely with unrelated data.

### Likelihood Explanation
The attacker only needs to run/control a peer that the target node considers a valid Atlas data-serving source (an outbound sync peer whose URL was previously registered) and answer any `AttachmentRequest` it receives with a 200 response containing crafted JSON. No secret, no signature, and no privileged role is needed — this is exactly the "unprivileged remote peer serving RPC" scenario in scope. It is fully repeatable per request/attachment batch cycle.

### Recommendation
In `extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; if the hash does not match, treat it as a failed/faulty response (bump `report.bump_failed_requests()` and/or mark the peer as faulty) rather than silently accepting content indexed by a different hash.

### Proof of Concept
Rust test in `stackslib::net::atlas::download` tests module:
1. Construct an `AttachmentsBatchStateContext` with a `peers` map containing one `UrlString`.
2. Build an `AttachmentRequest { content_hash: H1, sources: {url: report}, .. }`.
3. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has `{request: Some(response)}` where `response` is a `StacksHttpResponse` wrapping a `GetAttachmentResponse { attachment: Attachment { content: b"evil".to_vec() } }` (whose `hash()` = H2 ≠ H1).
4. Call `context.extend_with_attachments(&mut results)`.
5. Assert `context.attachments` contains the `H2`-hashing attachment (via `context.attachments.iter().any(|a| a.hash() == H2)`), while nothing ties it to `H1`, and that no equality check rejected it — demonstrating the missing `attachment.hash() == request.content_hash` guard.
6. Optionally drive it through `AttachmentsDownloader::run`'s `Done` branch to show `atlas_db.find_attachment(&H1)` stays `None` while `atlas_db.find_attachment(&H2)` becomes populated after `insert_instantiated_attachment`.

Note: I could not fully inspect `decode_atlas_get_attachment` / `GetAttachmentResponse` definitions in `stackslib/src/net/atlas/mod.rs` or `stackslib/src/net/api/getattachment.rs` within the available iterations to confirm there is no hash-check performed at the decode layer itself; based on the code read in `download.rs`, no such check exists in the consuming code path, but a full confirmation would require reviewing those decode functions directly.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
