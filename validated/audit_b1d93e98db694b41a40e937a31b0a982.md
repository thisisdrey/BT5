### Title
Committee-controlled `UNFREEZE_DELAY_DAYS` toggle gates `WithdrawExpireUnfreezeActuator`, allowing already-unfrozen funds to become permanently unwithdrawable - (File: actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java)

### Summary
`WithdrawExpireUnfreezeActuator.validate()` (and its TVM twin `WithdrawExpireUnfreezeProcessor.validate()`) gate the entire withdraw-expired-unfreeze transaction type behind a single mutable governance flag, `dynamicStore.supportUnfreezeDelay()`, which is backed by the committee-adjustable chain parameter `UNFREEZE_DELAY_DAYS`. This mirrors the reported Perennial pattern where an owner-controlled global parameter (`minCollateral`) is checked in a withdrawal-path invariant, and changing that parameter after users have already accrued state that satisfied the old condition can permanently strand their funds.

### Finding Description
`UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor` records pending unfreeze entries (`UnFreezeV2`) with an `unfreezeExpireTime` computed as `now + unfreezeDelayDays * FROZEN_PERIOD`, using the dynamic parameter `getUnfreezeDelayDays()`: [1](#0-0) 

The only way to convert these expired, matured entries back into spendable balance is `WithdrawExpireUnfreezeActuator`, whose `validate()` unconditionally requires the committee-controlled switch to be enabled: [2](#0-1) 

The same gate exists in the TVM-reachable equivalent used by contracts calling `withdrawExpireUnfreeze()`: [3](#0-2) 

`supportUnfreezeDelay()` is backed by `UNFREEZE_DELAY_DAYS`, which is a chain parameter modifiable via committee proposals through `ProposalUtil` and applied in `ProposalService`: [4](#0-3) [5](#0-4) 

Exactly like the Perennial issue — where an account's collateral was valid under the old `minCollateral` but a subsequent owner-triggered parameter change makes the same collateral fail the `collateralInvariant` check on withdraw — a user's `UnFreezeV2` entries are created and matured while `UNFREEZE_DELAY_DAYS` is non-zero (`supportUnfreezeDelay()==true`), but if the parameter is later changed such that `supportUnfreezeDelay()` becomes `false`, the withdraw transaction path (`WithdrawExpireUnfreezeActuator`/`WithdrawExpireUnfreezeProcessor`/TVM `withdrawExpireUnfreeze()`) immediately reverts for every account with already-matured `UnFreezeV2` entries, regardless of how much time has passed or how legitimate the claim is.

### Impact Explanation
If reachable, this would cause **permanent freezing of legitimately unlocked TRX** for any account that has matured `UnFreezeV2` entries at the time the flag is toggled off, since no other actuator/processor exists to redeem this specific unfrozen-but-unwithdrawn balance — the funds sit in `UnfrozenV2List` with no code path that credits them to `balance` except the gated `WithdrawExpireUnfreezeActuator`/processor. This satisfies the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
I could not verify with certainty, from the available indexed code, whether `ProposalUtil`'s validation for `UNFREEZE_DELAY_DAYS` permits the parameter to be reduced back to `0` once it has been set to a positive value (i.e., whether the committee proposal enforces a monotonic/one-way hard-fork style constraint or allows bidirectional changes). This is the crux of whether the described strand-of-funds scenario is practically reachable by committee governance, and I was not able to confirm the exact validation bounds inside `ProposalUtil.java` for this parameter before running out of tool budget.

### Recommendation
- Confirm in `ProposalUtil.java` whether `UNFREEZE_DELAY_DAYS` can be set back to `0` after being non-zero; if so, disallow decreasing it once `UnFreezeV2` entries may exist, or provide an independent, ungated withdrawal path for already-matured `UnFreezeV2` balances that does not depend on `supportUnfreezeDelay()`.
- Alternatively, gate only the *creation* of new `UnFreezeV2` entries (in `UnfreezeBalanceV2Actuator`) on the flag, and never gate the *redemption* (`WithdrawExpireUnfreezeActuator`) of already-matured entries.

### Proof of Concept
Note: this PoC's key step (committee reducing `UNFREEZE_DELAY_DAYS` back to 0 after being enabled) is unverified due to indexing limits noted above.
1. Committee enables stake-2.0 delayed unfreeze by setting `UNFREEZE_DELAY_DAYS > 0` via proposal.
2. Alice calls `UnfreezeBalanceV2Contract`, creating a `UnFreezeV2` entry with `unfreezeExpireTime = now + delay`.
3. Time passes; `unfreezeExpireTime <= now`, so Alice's funds are eligible for withdrawal.
4. Before Alice submits `WithdrawExpireUnfreezeContract`, the committee submits a proposal that sets `UNFREEZE_DELAY_DAYS` back to a value causing `supportUnfreezeDelay()` to return `false`.
5. Alice's `WithdrawExpireUnfreezeContract` transaction now fails validation at `actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java:84-87`, and there is no alternative actuator that can credit her matured `UnFreezeV2` balance back to her spendable `balance`.

```java
  public long withdrawExpireUnfreeze() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawExpireUnfreeze", nonce, null);

    try {
      WithdrawExpireUnfreezeParam param = new WithdrawExpireUnfreezeParam();
      param.setOwnerAddress(owner);

      WithdrawExpireUnfreezeProcessor processor = new WithdrawExpireUnfreezeProcessor();
      processor.validate(param, repository);
      long expireUnfreezeBalance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(expireUnfreezeBalance);
      }
      return expireUnfreezeBalance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawExpireUnfreeze: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawExpireUnfreeze: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
```
