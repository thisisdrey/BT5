## Finding

### Title
StackerDB chunk signatures are not bound to the target contract, enabling cross-database chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash` — it never incorporates the StackerDB's `QualifiedContractIdentifier`. Consequently, a valid chunk signature authenticates "this signer wrote this data at this slot/version" but says nothing about *which* StackerDB replica it was authorized for. Any node that legitimately observes a broadcast chunk for StackerDB contract A can replay the identical `(slot_id, slot_version, data, sig)` tuple against a different StackerDB contract B, and it will be accepted as long as the same signer address happens to occupy `slot_id` in B at a lower version. This is the direct analog of the SurrealDB bug: an authentication credential (here, a slot signature) that is valid in one namespace/context is accepted in a different namespace/context because the credential itself does not encode which context it belongs to.

The storage-side acceptance path, `try_replace_chunk`, looks up the expected signer *for that specific contract's slot* and calls `slot_desc.verify(&slot_validation.signer)`, then only enforces version monotonicity and write-count limits — both scoped to the target contract's own slot state, not to the source contract the chunk was originally authored for: [3](#0-2) 

The same pattern appears on the network-received/gossip path, `validate_received_chunk`, which fetches `get_slot_signer(smart_contract_id, data.slot_id)` for the *target* contract and verifies the chunk's signature against it, then checks only version/staleness relative to the target's own expected versions: [4](#0-3) 

Because the signed digest never contains `contract_id`, a signature produced for `(slot_id=N, slot_version=V, data_hash=H)` in contract A is bit-for-bit identical to what would be required for `(slot_id=N, slot_version=V, data_hash=H)` in contract B, provided the same `StacksAddress` is assigned `slot_id=N` in both. Signer-slot assignment across different StackerDB contracts is derived independently per-contract from Clarity read-only calls (`eval_signer_slots`/`parse_slot_entry`), and slot positions are explicitly designed in places to be *stable* across contracts/rotations — e.g. the `.miners` config comment: "preserve the miner's relative position in the stackerdb signer list -- if a miner was in slot 0, then it should stay in slot 0": [5](#0-4) 

and the boot `signers.clar` contract deterministically assigns per-cycle signer slot pages (`stackerdb-signer-slots-0`/`-1`) that are reused verbatim across the two parallel signer StackerDB contracts each cycle: [6](#0-5) 

Given identical relative signer ordering across reward cycles (a signer with stable stacking weight will often land on the same `slot_id`), the pre-condition for cross-contract collision — the same signer address at the same `slot_id` in two different StackerDB contracts — is a realistic and even common operational scenario, not merely a low-probability edge case.

### Impact Explanation
This breaks the equality "signature authenticates a write to *this* StackerDB" vs. "signature authenticates a write to *some* StackerDB where this signer holds this slot." An unprivileged network peer that observes a legitimately-published chunk (StackerDB data is broadcast/pull-able by any peer, not access-controlled) can replay it into a different StackerDB replica served by the same or another node via the unsolicited push path (`handle_unsolicited_StackerDBPushChunk`) or the RPC `POST` chunk endpoint, causing the victim replica to accept and store — and then gossip onward — data that its own signer never authorized for that specific database/context. This is an unauthorized write to StackerDB state and can propagate forged/misattributed data network-wide as the chunk is folded into the target's chunk inventory and further relayed.

### Likelihood Explanation
Exploitation requires no secret material and no privileged role: the attacker only needs to capture a broadcast chunk (trivially observable, since StackerDB replicates data to any peer) and resend it against a different target contract where the same signer/slot pairing exists. The pairing precondition is realistically satisfiable given how slot assignment is derived (stable relative ordering across the `.miners` config and per-cycle `signers-0`/`signers-1` pages), making this more than a theoretical collision.

### Recommendation
Bind the StackerDB signature to the specific replica by including the `QualifiedContractIdentifier` (and ideally a chain-view/consensus-hash context) in `SlotMetadata::auth_digest()`, so a signature produced for one contract cannot be replayed as valid for another. This would require a versioned digest format to preserve backward compatibility with existing signed chunks.

### Proof of Concept
1. Configure two StackerDB contracts, A and B, such that address `S` is assigned `slot_id = k` in both (a realistic outcome given deterministic slot-ordering by stacking weight, per the `.miners`/`signers.clar` slot-stability design).
2. Signer `S` legitimately signs and publishes chunk `(slot_id=k, slot_version=v, data=D)` to contract A; the chunk propagates over gossip/RPC as normal.
3. An unprivileged observer captures this `StackerDBChunkData` (slot_id, slot_version, sig, data) from the wire.
4. The observer submits the identical tuple to contract B's replica (either via `POST /v2/stackerdb/...` chunk endpoint or by injecting an unsolicited `StackerDBPushChunk` message) as long as contract B's stored version at `slot_id=k` is `< v`.
5. `try_replace_chunk`/`validate_received_chunk` for contract B look up `S` as the expected signer for `slot_id=k`, `slot_desc.verify(&S)` succeeds because the digest never referenced contract A, and the version check passes against B's own state — the forged-context chunk is accepted and stored in B.

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
