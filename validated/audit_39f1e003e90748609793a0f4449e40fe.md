Confirmed: `DecodeUtil.addressValid` only checks length (21 bytes) and the address prefix byte, not whether the remaining bytes are non-zero. So `0x41` followed by 20 zero bytes passes validation everywhere `addressValid` is used, including in `AccountPermissionUpdateActuator`.

### Title
Account permission keys can be set to the zero address, permanently locking account control - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator.checkPermission` validates each permission key's address only via `DecodeUtil.addressValid`, which does not reject the "zero address" (prefix byte + 20 zero bytes). A user can therefore set their Owner (or Active/Witness) permission's sole key to the zero address, an address for which no private key can ever exist, mirroring the reported `transferPosition`-to-`address(0)` bug class where a critical ownership/authorization slot is reassigned to an unrecoverable address.

### Finding Description
In `checkPermission`, each key's address is validated with: [1](#0-0) 
and `DecodeUtil.addressValid` only checks array length and the chain prefix byte: [2](#0-1) 
Nothing prevents `key.getAddress()` from being the all-zero-body address (prefix + 20 zero bytes). If a user submits an `AccountPermissionUpdateContract` where the Owner permission has a single key with weight ≥ threshold set to this zero address, `validate()` passes and `execute()` overwrites the account's permissions: [3](#0-2) 
Because no one holds the private key corresponding to that zero-body address, any future transaction requiring the Owner permission (including a subsequent `AccountPermissionUpdateContract` to fix the mistake) can never be authorized again.

### Impact Explanation
This permanently freezes control of the account under the Owner permission: TRX balance, TRC10/TRC20 assets, frozen/delegated resources, and voting rights tied to that account become unrecoverable, since the account can no longer authorize an Owner-permission transaction to change permissions back or to sign withdrawal/transfer/vote actions gated by Owner. This is a permanent freezing-of-funds condition analogous to the referenced report where a position is transferred to an address nobody controls.

### Likelihood Explanation
Reachable directly and unprivilegedly: any account owner (or an active-permission holder allowed to broadcast `AccountPermissionUpdateContract`) can construct and sign such a transaction themselves — self-inflicted, but the actuator does not stop it, and it could also be leveraged by a malicious co-signer in a multisig setup to intentionally brick shared account control. `getAllowMultiSign()` must be enabled on chain (a config that is generally on for mainnet), which is the only precondition besides normal signature checks.

### Recommendation
In `checkPermission` (and any other permission-key validation path), explicitly reject the zero-body address (i.e., the address whose 20-byte body is all zero) for every `Key` in `Owner`, `Witness`, and `Active` permissions, in addition to the existing `DecodeUtil.addressValid` check.

### Proof of Concept
1. Attacker (account owner) builds an `AccountPermissionUpdateContract` where:
   - `owner` permission has one `Key` with `address = <prefix byte>||<20 zero bytes>` and `weight = threshold`.
2. Attacker signs with their current valid Owner key and broadcasts.
3. `AccountPermissionUpdateActuator.validate()` passes because `DecodeUtil.addressValid` only checks length/prefix (see cited code).
4. `execute()` commits the new permission, replacing the Owner key with the zero-body address: [4](#0-3) 
5. No subsequent transaction can satisfy the Owner-permission signature requirement, permanently freezing the account's funds/control.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
