### Title
Unauthenticated forged miner-message injection via signer's `/stackerdb_chunks` event endpoint - (File: `libsigner/src/events.rs`)

### Summary
The `stacks-signer` process's built-in HTTP event server (`SignerEventReceiver`) has no authentication, shared secret, or origin check on POSTs to `/stackerdb_chunks`. Combined with `TryFrom<StackerDBChunksEvent> for SignerEvent<T>`'s `.miners` branch, which deserializes `chunk.data` into `SignerEvent::MinerMessages` without any `recover_pk()`/`verify()` call, any remote party able to reach this port can inject an arbitrary, unsigned "miner message" directly into the signer's runloop.

### Finding Description
In `libsigner/src/events.rs:544-567`, the `.miners` branch of `TryFrom<StackerDBChunksEvent>` iterates `event.modified_slots` and calls `T::consensus_deserialize(&mut chunk.data.as_slice())`, pushing every successfully-parsed message into `SignerEvent::MinerMessages(messages)` — with no signature check. This is intentional-by-design *only* under the assumption that the `StackerDBChunksEvent` reaching this code always originates from the trusted, already-validated node→signer event-dispatcher channel: on the node side, `stackslib/src/net/api/poststackerdbchunk.rs` and `stackslib/src/net/stackerdb/db.rs:398-439` (`try_replace_chunk`) verify `slot_desc.verify(&slot_validation.signer)` (i.e., that the chunk was signed by the `.miners` slot's designated owner) *before* the chunk is ever stored and forwarded via `stacks-node/src/event_dispatcher.rs:885` (`process_new_stackerdb_chunks`) to the signer's `/stackerdb_chunks` endpoint. The `SIGNERS_NAME` branch additionally calls `chunk.recover_pk()` only to *extract* the public key for its `(slot_id, pubkey, message)` tuple output type — not as an independent security gate — since `SignerEvent::MinerMessages(Vec<T>)`'s shape doesn't need a key.

The broken link is the transport, not the enum conversion: `SignerEventReceiver::bind` (`libsigner/src/events.rs:404-408`) opens a bare `tiny_http::HttpServer` with **no authentication of the sender** at all. The `auth_password`/`auth_token` settings documented in `docs/signing.md` and `stacks-signer/src/config.rs:320-327` only gate the *signer-to-node* RPC (block-proposal validation) direction; they are never checked on inbound event POSTs in `next_event`/`process_event` (`libsigner/src/events.rs:413-459`, `519-542`). Sample configs (`sample/conf/signer/mainnet-signer-conf.toml:39`) even default the signer's listening `endpoint` to `"0.0.0.0:30000"`. Any remote party that can route a TCP connection to that port can therefore POST a hand-crafted `StackerDBChunksEvent` JSON body with `contract_id.name = MINERS_NAME` and any `chunk.data`, bypassing the node's StackerDB chunk-signature verification entirely, and the signer will accept it as a genuine `SignerEvent::MinerMessages`.

### Impact Explanation
An attacker who can reach the signer's event-listener port can inject arbitrary forged "miner" messages (e.g. bogus `BlockProposal`/`MockProposal`/`MockBlock` payloads, depending on `T`) straight into the signer runloop's decision-making input, with no cryptographic binding to the actual `.miners` slot owner. This is repeatable per TCP connection/POST and requires no privileged role, node RPC secret, or peer key — only network reachability to the signer's bind address. Impact is scoped to that signer's belief about miner intent (signer transport only), matching "unauthenticated/unauthorized write to state" for that single signer process; it does not by itself corrupt on-chain StackerDB state (the node's own StackerDB copy still enforces `try_replace_chunk`'s signature check), so it is not a network-wide propagation of forged StackerDB data.

### Likelihood Explanation
Preconditions: the signer's event-receiver TCP port must be reachable from the attacker's network position (no additional peer/config/tip state is required, and no legitimate StackerDB slot ownership is needed at all — contrary to the question's framing, the attacker doesn't even need to own a slot in another contract, since there is no origin/auth check whatsoever on this endpoint). Attacker cost is minimal: one crafted JSON HTTP POST. Likelihood is high only if operators bind this endpoint to a non-loopback, reachable address without a firewall/reverse-proxy/auth in front of it — the documented deployment intent is that this port is reached only by the paired local `stacks-node` event-dispatcher, not by arbitrary remote peers.

### Recommendation
Add authentication to the signer's inbound event endpoint (e.g., require and check a shared secret/HMAC header on all `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block` POSTs, analogous to `auth_token`/`auth_password` but for the node→signer direction), and/or bind the event receiver to loopback by default, and/or restrict accepted source IPs to the configured node's address.

### Proof of Concept

            }
