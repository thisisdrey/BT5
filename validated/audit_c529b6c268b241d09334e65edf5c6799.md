The OpenClaw bug class involves persistent "allow-always" trust decisions for command execution approvals that fail to unwrap intermediary wrapper binaries (like `/usr/bin/script`) to the actual underlying target before caching the trust decision. This is a feature of an interactive coding-agent tool that prompts users to approve/deny command execution and remembers approvals by executable identity.

Bazel has no equivalent mechanism. It does not implement an interactive execution-approval system, nor does it persist "trust" decisions keyed on a resolved executable path that could be bypassed by wrapping the real target behind `/usr/bin/script` or similar. The closest analogous surfaces in bazel are:
- Credential helpers, which are scoped by URI domain, not by binary identity, and are invoked per-request rather than cached against a resolved executable target [1](#0-0) .
- `repository_ctx.execute()`, which directly executes the command specified in Starlark with no allowlist/trust-caching layer to unwrap [2](#0-1) .

Neither of these constitutes a "trust decision" cache keyed on an unwrapped executable identity, so there is no reachable bazel surface where a wrapper like `/usr/bin/script` could smuggle a different target past a stored approval. This bug class does not have a valid analog within bazel's own code.
