### Title
Unrestricted `AccountPermissionUpdateContract` can permanently invalidate in-flight, partially-collected multi-signature transactions, freezing controlled funds - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` allows an account owner to overwrite the account's `owner`/`witness`/`active` `Permission` structures (key sets, thresholds, `permission_id` slots) with a single signed transaction and no check for outstanding, not-yet-broadcast multi-signature transactions that were built against the *previous* permission configuration. Signature validation for multi-sig transactions is resolved dynamically against whatever permission currently sits at the referenced `permissionId`, not the permission that was active when the individual signatures were collected. This mirrors the reported NounsBuilder bug class: a privileged "renderer/config" swap (here, the account's permission structure) is allowed at any time with no protection for already-created objects that depend on the old configuration (there, minted tokens needing `attributes[tokenId]`; here, collected signatures needing the old `Permission`), and there is no way to migrate the old data to work with the new configuration.

### Finding Description
`AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)` unconditionally, replacing the account's owner/witness/active permissions in a single step: [1](#0-0) 

`validate()` only checks the new permission's own shape (threshold, key count, key validity, permission types); it performs no check for outstanding multi-sig transactions signed under the previous permission set: [2](#0-1) 

Multi-signature transactions in java-tron are built incrementally: a `permissionId` is fixed in the raw transaction, and signatures are added and re-validated against the account's *current* permission at time of signing/verification via `TransactionCapsule.addSign`, which fetches the permission live from the account store and checks weight/operations against it: [3](#0-2) 

The same live-lookup pattern is used by the read-only approval-status API `Wallet.getTransactionApprovedList`, which also resolves `account.getPermissionById(permissionId)` against the account's current state to validate previously-collected signatures: [4](#0-3) 

Because the permission is looked up by numeric `permissionId` from the *current* account state rather than being bound immutably to the signatures already gathered, if the owner (or an active-permission holder) submits a new `AccountPermissionUpdateContract` — for example changing the keys, threshold, or removing/altering the permission at that same `permissionId` slot — any signatures collected prior to that update against the old key/threshold combination become permanently unusable: `checkWeight`/`getWeight` will compute against the new key set, and the previously-valid signers may no longer count toward the new threshold, or the `permissionId` may map to a semantically different permission after the update. There is no mechanism to bind a partially-collected multi-sig transaction to a specific permission "version," and no restriction preventing the permission change while such transactions are outstanding — the exact analog of the original report's core finding: privileged reconfiguration is unguarded against objects/state that depend on the pre-change configuration, and there is no migration path once broken.

### Impact Explanation
If a multi-signature-controlled account (e.g., a treasury or DAO-style account) is mid-way through collecting the required threshold of signatures for a `TransferContract` or other fund-moving transaction, any account holder able to submit an `AccountPermissionUpdateContract` for that active permission slot (which requires the same threshold as before, but can be done unilaterally by the owner permission at `permissionId = 0`, or by an active key with sufficient weight) can invalidate all previously gathered signatures. Depending on how signers coordinate (typical multi-sig workflows collect signatures asynchronously off-chain before broadcasting the fully-signed transaction), this can result in permanent freezing of the funds targeted by the pending transaction, since the collected signatures cannot be reused after the permission structure changes and must be recollected from scratch — which may be impossible if the original combination of signers/weights is no longer achievable under the new permission.

### Likelihood Explanation
This requires a multi-signature account whose owner performs (or is compelled/tricked into performing) a permission update while a partially-signed transaction is outstanding — a realistic but non-default usage pattern for DAO/treasury accounts using java-tron's native multi-sig feature (`AllowMultiSign`). No special node/network privilege is needed: a single signed `AccountPermissionUpdateContract` transaction from the account owner (or an active permission holder with the operation permission bit set) is sufficient to trigger the invalidation, matching the "single signed transaction" reachability requirement.

### Recommendation
Bind in-flight multi-signature validation to the specific `Permission` (e.g., by hashing/versioning the permission definition referenced by `permissionId` and checking signatures against that snapshot) rather than resolving `permissionId` against the live/mutable account state, or require that transactions reference an explicit, immutable snapshot of the permission at signing time. Alternatively, disallow permission updates for `permissionId`/threshold combinations that would invalidate outstanding, not-yet-expired transactions, similarly to how the original report recommends either restricting the update or providing a migration path for data tied to the old configuration.

### Proof of Concept
1. Enable multi-sign on an account (`AllowMultiSign`), define an `active` `Permission` (id=2) with keys A and B, threshold 2.
2. Construct `TransferContract` moving funds out of the account, referencing `permissionId=2`.
3. Have signer A sign via `TransactionCapsule.addSign` (weight 1 of 2, not yet broadcastable). [3](#0-2) 
4. Before signer B signs, the account owner submits `AccountPermissionUpdateContract` replacing the active permission at id 2 with a different key set/threshold via `AccountPermissionUpdateActuator.execute()`. [1](#0-0) 
5. Signer A's collected signature is now checked against the new permission definition in any subsequent `addSign`/`getTransactionApprovedList` call, and no longer counts toward a valid threshold under the old intended semantics, permanently stranding the pending transfer.

  public void addSign(byte[] privateKey, AccountStore accountStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = this.transaction.getRawData().getContract(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwnerAddress();
    AccountCapsule account = accountStore.get(owner);
    if (account == null) {
      throw new PermissionException("Account is not exist!");
    }
    Permission permission = account.getPermissionById(permissionId);
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    List<ByteString> approveList = new ArrayList<>();
    SignInterface cryptoEngine = SignUtils
        .fromPrivate(privateKey, CommonParameter.getInstance().isECKeyCryptoEngine());
    byte[] address = cryptoEngine.getAddress();
    if (this.transaction.getSignatureCount() > 0) {
      checkWeight(permission, this.transaction.getSignatureList(),
          this.getTransactionId().getBytes(),
          approveList);
      if (approveList.contains(ByteString.copyFrom(address))) {
        throw new PermissionException(encode58Check(address) + " had signed!");
      }
    }

    long weight = getWeight(permission, address);
    if (weight == 0) {
      throw new PermissionException(
          ByteArray.toHexString(privateKey) + "'s address is " + encode58Check(address)
              + " but it is not contained of permission.");
    }
    ByteString sig = ByteString.copyFrom(cryptoEngine.Base64toBytes(cryptoEngine
        .signHash(getTransactionId().getBytes())));
    this.transaction = this.transaction.toBuilder().addSignature(sig).build();
  }
