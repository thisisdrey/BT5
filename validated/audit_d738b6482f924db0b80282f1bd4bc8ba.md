### Title
Deactivated DebtToken still allows synthetic issuance via `DebtToken.issue`, bypassing the emergency active-flag guard enforced on `flashIssue` - (File: contracts/DebtToken.sol)

### Summary
`DebtToken` exposes two minting paths: `issue()` (user-facing, collateral-checked) and `flashIssue()` (SmartFarmingManager-only, deferred health check). `flashIssue` is gated by `onlyIfDebtTokenIsActive`, but `issue` is not. When governance disables a DebtToken (`toggleIsActive` → `isActive = false`) to halt new debt on that pool, the restriction is trivially circumvented: any user simply calls `issue` instead, and synthetic tokens keep being minted and debt keeps accruing.

### Finding Description
The guard `onlyIfDebtTokenIsActive` exists precisely to stop issuance when the flag is off (`contracts/DebtToken.sol:97-100`). It is applied to `flashIssue` (`contracts/DebtToken.sol:291`) but omitted from `issue` (`contracts/DebtToken.sol:235-244`), which only carries `whenNotShutdown`, `nonReentrant`, and `onlyIfSyntheticTokenExists`.

Two sub-paths confirm the bypass:
- `issue` checks only the caller's collateral via `pool.debtPositionOf` and then calls `_mint` + `syntheticToken.mint`. `SyntheticToken._mint` checks `onlyIfSyntheticTokenIsActive` — the *synthetic* token's flag, not the *debt* token's — so an inactive DebtToken does not block `issue` at all.
- Similarly, `DebtToken.mint` (SmartFarmingManager path, `contracts/DebtToken.sol:328-345`) checks `onlyIfSyntheticTokenIsActive` but not `onlyIfDebtTokenIsActive`, so leveraged issuance also remains open after deactivation.

The asymmetric modifier application shows intent: `flashIssue` enforces the flag, `issue`/`mint` do not. The "intended authentication path" (deactivation = no more debt) is bypassed via the alternate entry point.

### Impact Explanation
The `isActive` flag is the governor's tool to stop new debt/minting on a specific pool — e.g., when a synth's oracle is compromised, a collateral is found mispriced, or a market must be wound down. An unprivileged attacker can keep opening debt positions through `DebtToken.issue` (and through `SmartFarmingManager.leverage` → `DebtToken.mint`/`flashIssue` is blocked but `mint` is not) after the emergency disable. If deactivation was triggered by a bad price feed or distressed collateral, continued issuance manufactures new undercollateralized debt, converting a contained incident into protocol insolvency and bad debt socialized across depositors.

### Likelihood Explanation
Exploitation requires no privileges: `issue` is a public, non-shutdown-gated entry point reachable directly or via `Operator.execute`. The precondition is governance having deactivated the DebtToken — which only happens in exactly the adversarial scenarios (broken oracle, toxic collateral) where continued minting is most damaging. Within those scenarios the bypass is deterministic: there is no lock, cap, or second check that substitutes for the missing modifier (supply cap `maxTotalSupply` on the synth can itself be set independently and does not implement the debt-token kill switch).

### Recommendation
Apply `onlyIfDebtTokenIsActive` to `DebtToken.issue` (and consider `DebtToken.mint` for symmetry with `flashIssue`), so deactivating a DebtToken halts every issuance path:

```solidity
// contracts/DebtToken.sol
function issue(uint256 amount_, address to_)
    external override
    whenNotShutdown
    nonReentrant
    onlyIfSyntheticTokenExists
    onlyIfDebtTokenIsActive   // added
    returns (uint256 _issued, uint256 _fee)
```

Verify on fork that `issue` reverts with `DebtTokenInactive` while `repay`/`repayAll`/`burn` remain open so users can still unwind.

### Proof of Concept
Foundry fork outline:

```solidity
// Assume forked pool with msdXXX collateral, msUSD DebtToken, alice funded
vm.startPrank(governor);
debtToken.toggleIsActive();           // emergency: isActive = false
vm.stopPrank();

// Direct path that SHOULD be blocked
vm.prank(attacker);
debtToken.flashIssue(attacker, 1e18); // reverts DebtTokenInactive (guard works)

// Alternate path bypasses the flag
depositToken.approve? // deposit collateral first via pool/depositToken.deposit
depositToken.deposit(collateralAmount, attacker);

vm.prank(attacker);
(uint256 issued, ) = debtToken.issue(amount, attacker); // succeeds — mints synth + debt

assertGt(syntheticToken.balanceOf(attacker), 0);
assertGt(debtToken.principalOf(attacker), 0); // new debt created despite isActive == false
```

The same bypass applies through `smartFarmingManager.leverage(...)` because `DebtToken.mint` also omits `onlyIfDebtTokenIsActive`.

Caveat: I verified modifier application on `issue`/`flashIssue`/`mint` directly in `contracts/DebtToken.sol`; the full `Pool`/`DepositToken` deposit flow for the PoC setup was not re-read line-by-line, but `issue`'s only collateral gate is `debtPositionOf`, which any funded account satisfies.
