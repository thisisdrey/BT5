The premise of this question conflicts with how Rust's `derive` macros work: `#[derive(PartialEq, Eq, PartialOrd, Ord)]` on the same type always generates implementations that compare the exact same underlying data (discriminant, then fields in declaration order) using the same field-by-field logic. There is no way for a derived `Ord::cmp` to return `Equal` while derived `PartialEq::eq` returns `false` (or vice versa), as long as every field type's own `Eq`/`Ord` derivations are consistent — which is true here since `AccountId` and `String` both have standard, mutually consistent `Eq`/`Ord` implementations.

Looking at the actual code:

- `TokenId` derives `Clone, PartialEq, Eq, PartialOrd, Ord, Hash` together on the enum with explicit discriminants `0..3`, and derived `Ord` for enums compares the discriminant first (matching what `PartialEq` checks via the tag), then falls through to field comparisons identical to those used by `PartialEq`. [1](#0-0) 
- `Nep171TokenId` and `Nep245TokenId` both derive `PartialEq, Eq, PartialOrd, Ord, Hash` on the same struct with fields `(contract_id, nft_token_id)` / `(contract_id, mt_token_id)`, in the same order for both derives. [2](#0-1) [3](#0-2) 

Since these are plain derives (no manual/custom `Ord` or `PartialEq` impl anywhere overriding the derived behavior), the binding `Ord::cmp(a,b) == Equal ⟺ a == b` is a language-level guarantee for these types, not something that depends on the specific `contract_id`/`token_id` string values chosen by an attacker. There is no crafted "colon-boundary" string or attacker-controlled value that can break this invariant, because both traits are derived mechanically from identical field access — this isn't a parsing/`FromStr` ambiguity issue (which would be a different, valid class of bug), it's asking whether derive-generated `Eq`/`Ord` can diverge, which they structurally cannot.
