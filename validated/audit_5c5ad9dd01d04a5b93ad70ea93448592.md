### Title
Legacy (non-hardened) Bancor-style exchange swap can push a pool reserve negative with no supply/balance check, permanently freezing the remaining reserve — (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes swap outputs with the double-precision `ExchangeProcessor` (Bancor-style relay/virtual-supply formula) whenever `allowHardenExchangeCalculation` is disabled (the legacy path), and only validates the resulting balances for negative values when `hardenedCalc` is `true` (the `SafeExchangeProcessor` path). In the legacy path the new balances are stored unconditionally, mirroring the audited Mento bug where a deduction/formula is applied without checking whether enough underlying reserve/supply remains to satisfy it.

### Finding Description
`ExchangeCapsule.transaction()` selects the processor based on `hardenedCalc`: [1](#0-0) 

When `hardenedCalc` is `false` (the default/legacy behavior, controlled by `DynamicPropertiesStore.allowHardenExchangeCalculation()`), `ExchangeProcessor` is used, which performs the Bancor relay math entirely in `double` arithmetic: [2](#0-1) 

The resulting `buyTokenQuant` is subtracted from the pool's opposite-token balance with plain `long` arithmetic (`secondTokenBalance - buyTokenQuant` or `firstTokenBalance - buyTokenQuant`), and the guard that rejects a negative resulting balance is only executed `if (hardenedCalc && ...)`: [3](#0-2) 

Because `Maths.pow`/`double` computation of the Bancor curve can round in a way that yields a `buyTokenQuant` slightly larger than the actual remaining opposite-token balance (especially as a sell approaches consuming nearly all of one side of the pool — analogous to "selling the last supply" in the Mento report), the legacy path can drive one side of the pool balance negative without any revert, and that corrupted state is persisted: [4](#0-3) 

This is reachable by any unprivileged account through `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(...)` and persists the exchange state unconditionally on success: [5](#0-4) 

Once a pool balance is negative, `ExchangeWithdrawActuator.doValidate()` will always reject subsequent withdrawals of the corrupted token, because it requires `secondTokenBalance < anotherTokenQuant` (or the symmetric check for `firstTokenBalance`) to be false — but any positive withdrawal amount will always exceed a negative balance: [6](#0-5) 

This mirrors the reported Mento bug: a fee/formula-driven deduction is applied to a shared pool/reserve without verifying enough balance/supply remains to satisfy it, permanently locking any remaining legitimate reserve for that exchange pair.

### Impact Explanation
Once the corrupted (negative) balance is written to `ExchangeStore`/`ExchangeV2Store`, all subsequent `ExchangeWithdrawContract` calls against that exchange for the affected token will permanently fail validation (`"exchange balance is not enough"`), and further `ExchangeTransactionContract` swaps continue to compound on the corrupted state. Any remaining reserve balance held by the exchange for the other token becomes permanently unredeemable by its creator, constituting a permanent freezing of funds — the same impact class as the referenced Mento finding.

### Likelihood Explanation
Reachability requires only a normal signed `ExchangeTransactionContract` transaction from any account (no privilege required), provided `allowHardenExchangeCalculation` is not enabled (the legacy calculation path, which is the historically default behavior before the hardening feature was introduced). Triggering the exact rounding condition requires carefully chosen pool balances/sell quantities that push the double-precision Bancor formula's output past the remaining opposite-side balance — feasible but requiring some numerical precision engineering, similar to the PoC needed in the original report.

### Recommendation
Apply the same negative-balance guard used in the hardened path (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check) unconditionally, regardless of `hardenedCalc`/`allowHardenExchangeCalculation`, so the legacy `ExchangeProcessor` path cannot persist a corrupted, negative pool balance. Consider deprecating the unguarded legacy path entirely in favor of `SafeExchangeProcessor`.

### Proof of Concept
Not independently executed against a live node; concretely reproducing requires selecting pool balances and a sell quantity such that `ExchangeProcessor.exchangeFromSupply`'s double-precision output exceeds the actual opposite-side balance, then calling `ExchangeTransactionActuator` (with `allowHardenExchangeCalculation` disabled) to drive `newSecondTokenBalance` (or `newFirstTokenBalance`) negative via the unchecked branch at `ExchangeCapsule.java:130-168`, and subsequently observing that `ExchangeWithdrawActuator` permanently rejects withdrawal of the remaining reserve (`ExchangeWithdrawActuator.java:218-250`, `"exchange balance is not enough"`). Exact numeric inputs to trigger the rounding overshoot were not derived within this analysis; the vulnerability rests on the documented absence of a negative-balance check in the non-hardened branch.

    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,

          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)

        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
