## Title
`UnfreezeBalanceActuator` Zeroes Out Receiver's Shared `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` Instead Of Decrementing It, Permanently Locking Other Delegators' Frozen TRX - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`)

### Summary
`UnfreezeBalanceActuator.execute()` maintains a receiver-side aggregate counter, `AcquiredDelegatedFrozenBalanceForBandwidth`/`AcquiredDelegatedFrozenBalanceForEnergy`, that sums the resource delegated to a receiver from *all* of its delegators. When the code detects that this aggregate is smaller than the amount a single delegator is currently unfreezing, instead of subtracting only that delegator's share it hard-resets the entire shared aggregate to `0`, wiping out the portion legitimately owed to every other delegator of that same receiver. This is structurally identical to the reported `ConvexStakingWrapper.enterShelter()` bug, where a shared accounting value (`amountInShelter[lpToken]`) that many users depend on for pro-rata accounting is overwritten instead of accumulated/decremented, leaving other users' claims unrecoverable.

### Finding Description
In `UnfreezeBalanceActuator.execute()`, when a delegator unfreezes bandwidth/energy that was delegated to a `receiver`, the code updates the receiver's aggregate counters: [1](#0-0) 

The same destructive pattern is repeated for `ENERGY`: [2](#0-1) 

`AcquiredDelegatedFrozenBalanceForBandwidth`/`Energy` on the `receiverCapsule` is a shared aggregate that can be increased by delegations from *multiple, unrelated* delegator accounts (each tracked individually in its own `DelegatedResourceCapsule`, keyed by `(owner, receiver)` via `DelegatedResourceCapsule.createDbKey`). Whenever the aggregate value is (for whatever reason) smaller than the amount a single unfreezing delegator claims, the code takes the `setAcquiredDelegatedFrozenBalanceForBandwidth(0)` / `setAcquiredDelegatedFrozenBalanceForEnergy(0)` branch — an overwrite of the whole shared counter to zero — rather than clamping only the excess or subtracting exactly the amount owed to that delegator. This mirrors the report's root cause: `amountInShelter[lpToken] = amount;` overwrote a value relied upon by multiple claimants instead of `amountInShelter[lpToken] += amount;`.

This zeroed aggregate then breaks the invariant relied on by `validate()` for every *other* delegator who still has an outstanding `DelegatedResourceCapsule` to the same receiver: [3](#0-2) 

Because `receiverCapsule.getAcquiredDelegatedFrozenBalanceForBandwidth()` is now `0` while `delegatedResourceCapsule.getFrozenBalanceForBandwidth()` for the other delegator is still positive, this check unconditionally fails and throws `ContractValidateException`, permanently blocking that delegator's own `UnfreezeBalanceContract` transaction.

### Impact Explanation
Any delegator with an outstanding delegation to the affected receiver becomes permanently unable to broadcast a valid `UnfreezeBalanceContract` transaction for that receiver once the aggregate is wiped, because `validate()` will always reject their unfreeze with `"AcquiredDelegatedFrozenBalanceForBandwidth[0] < delegatedBandwidth[...]"`. Their TRX remains frozen/delegated indefinitely with no on-chain path to reclaim it — a permanent freezing-of-funds condition matching the accepted severity of the original finding (locked funds due to overwritten shared accounting state).

### Likelihood Explanation
The trigger is reachable from an ordinary, unprivileged `UnfreezeBalanceContract` transaction (any account that previously froze-and-delegated TRX to a receiver can broadcast it); no special privilege is required to invoke `UnfreezeBalanceActuator`. The zeroing branch only fires when the receiver-side aggregate is smaller than what a single unfreeze claims, which can occur whenever the per-delegator (`DelegatedResourceCapsule`) and per-receiver aggregate (`AccountCapsule.AcquiredDelegatedFrozenBalanceForBandwidth/Energy`) bookkeeping drift apart — e.g. through interactions across the legacy V1 delegate path (`FreezeBalanceContract`/`UnfreezeBalanceContract`) and the newer V2 delegate/undelegate path, or through contract self-destruct resource inheritance in `Program.suicide2()`/`transferFrozenV2BalanceToInheritor`, which move delegated balances between accounts.

### Recommendation
Replace the destructive `setAcquiredDelegatedFrozenBalanceForBandwidth(0)` / `setAcquiredDelegatedFrozenBalanceForEnergy(0)` calls with a safe, floor-clamped subtraction that reduces the aggregate by exactly the amount being unfrozen (never below zero) rather than resetting the whole shared counter, analogous to the already-existing `safeAddAcquiredDelegatedFrozenBalanceForBandwidth`/`Energy` helpers used elsewhere in the codebase: [4](#0-3) 
Audit all call sites that can cause `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` and its per-delegator `DelegatedResourceCapsule` counterpart to desynchronize, and add invariant checks/migrations so the aggregate can never fall below the sum of outstanding individual delegations.

### Proof of Concept
1. Delegator A freezes and delegates bandwidth to Receiver R (`FreezeBalanceContract` with `receiver_address = R`), incrementing `R.AcquiredDelegatedFrozenBalanceForBandwidth`.
2. Delegator B independently freezes and delegates bandwidth to the same Receiver R, further incrementing the same aggregate field on R.
3. Through any path that desynchronizes the aggregate from the sum of individual `DelegatedResourceCapsule` records for R (e.g. legacy/V2 path interaction or inherited resources via contract `suicide`), `R.AcquiredDelegatedFrozenBalanceForBandwidth` becomes smaller than Delegator A's own `DelegatedResourceCapsule.getFrozenBalanceForBandwidth()`.
4. Delegator A broadcasts `UnfreezeBalanceContract`; `execute()` hits `receiverCapsule.setAcquiredDelegatedFrozenBalanceForBandwidth(0)` (`UnfreezeBalanceActuator.java:125`), wiping out Delegator B's share of the aggregate too.
5. Delegator B later broadcasts `UnfreezeBalanceContract` for R; `validate()` now sees `R.AcquiredDelegatedFrozenBalanceForBandwidth() (0) < delegatedResourceCapsule.getFrozenBalanceForBandwidth()` and throws `ContractValidateException` (`UnfreezeBalanceActuator.java:373-381`), permanently preventing Delegator B from ever unfreezing their delegated TRX to R.
