### Title
Unauthenticated stage-0 replay with spoofed source address triggers a reflected/amplified stage-2 handshake response - ([File: handshake_manager.go])

### Summary
`HandshakeManager.beginHandshake` fully re-processes any packet whose `MessageCounter == 1` through the Noise handshake machine before any source-address/return-routability check, and when the resulting handshake packet byte-matches an already-completed tunnel's stored stage-0 (`CheckAndComplete` -> `ErrAlreadySeen`), `handleCheckAndCompleteError` unconditionally resends the cached stage-2 response to `via.UdpAddr` — the source address of the just-received packet, with no verification that this address is the same peer that originally completed that handshake. Since UDP source addresses are trivially spoofable, an attacker who has captured (or otherwise possesses) one legitimate stage-0 packet from a live tunnel can replay it from a spoofed source repeatedly, forcing the responder to perform full asymmetric Noise processing and then transmit the victim's cached stage-2 material to an address of the attacker's choosing.

### Finding Description
The reachable path is: `HandshakeManager.HandleIncoming` (handshake_manager.go:151) routes any packet with `h.MessageCounter == 1` and `h.RemoteIndex == 0` straight to `beginHandshake` (handshake_manager.go:177-184) regardless of source. `beginHandshake` (handshake_manager.go:701) builds a brand-new responder `Machine` and calls `machine.ProcessPacket(nil, packet)` (handshake_manager.go:722) — this runs the full Noise IX crypto (ephemeral DH, static decryption, certificate verification) on the replayed bytes before any duplicate/replay check occurs. Because the packet is a byte-for-byte replay of a previously valid stage-0 message, it decrypts and validates successfully, reproducing the *original* initiator's certificate and vpn addresses.

The resulting `hostinfo.HandshakePacket[handshakePacketStage0]` is then compared via `bytes.Equal` against every hostinfo already in the main hostmap for that vpn address in `CheckAndComplete` (handshake_manager.go:440-444). Since the header is stripped before storage/comparison, this match succeeds against the completed tunnel's original stage-0 packet, returning `ErrAlreadySeen` along with the `existing` (already-established) hostinfo.

`handleCheckAndCompleteError`'s `ErrAlreadySeen` branch (handshake_manager.go:1104-1113) then calls `hm.sendHandshakeResponse(via, msg, existing, true)` where `msg = existing.HandshakePacket[handshakePacketStage2]` — the cached, previously-computed stage-2 response belonging to the real, live tunnel. `sendHandshakeResponse` (handshake_manager.go:1045) writes this message directly to `via.UdpAddr` (handshake_manager.go:1074) with no check that `via` corresponds to the peer that actually established that tunnel. `via` is derived purely from the UDP packet's source address, which is attacker-spoofable.

No existing check in this path validates return-routability of `via` before either (a) performing the expensive cryptographic processing, or (b) sending the cached response. The remote allow list check (`AllowUnknownVpnAddr`, handshake_manager.go:166) only filters against admin-configured CIDR ranges, not per-source state, and does not prevent an attacker inside an allowed range (or when no restrictive allow list is configured) from spoofing any address within reach.

### Impact Explanation
This provides a reflection/amplification primitive: a single previously-observed stage-0 packet can be replayed indefinitely (as long as the completed hostinfo remains in the main hostmap, i.e., for the life of the tunnel) from spoofed source addresses, causing the responder to (1) perform full asymmetric Noise handshake processing (DH + certificate/signature verification) on every replay — a non-trivial CPU cost — and (2) transmit the victim's stage-2 handshake bytes (ephemeral public key + encrypted certificate payload) to an arbitrary attacker-chosen destination. This is usable both as a UDP reflection/amplification vector against a spoofed victim IP and as a mechanism to redirect a live tunnel's stage-2 material to an address of the attacker's choosing. The confidentiality benefit is limited (the attacker must already possess the exact stage-0 bytes, which generally implies prior on-path visibility into the same handshake, including the original stage-2 response), so the primary scoped impact is reflected UDP amplification / unauthenticated triggering of privileged network sends and repeated CPU-costly handshake crypto processing — a resource-exhaustion / reflection primitive rather than a cryptographic bypass.

### Likelihood Explanation
Preconditions are modest: the attacker needs to obtain one legitimate stage-0 packet (via passive capture on any segment the packet traverses, or from their own prior handshake attempt if they control an endpoint) and the ability to spoof UDP source addresses toward the listener — both explicitly allowed under the stated threat model. No certificate, key material, or privileged access is required. The replay can be repeated indefinitely as long as the target tunnel/hostinfo remains established, making this a reliable and repeatable primitive rather than a one-shot condition.

### Recommendation
Before resending any cached stage-2 packet in the `ErrAlreadySeen` path, verify that `via` matches (or is at least consistent with) the address/relay already associated with `existing`'s established remote, rather than trusting the source of the replayed packet unconditionally. Alternatively, gate expensive Noise processing and cached-response resends behind a lightweight return-routability check (e.g., only resend to a `via` previously recorded for that hostinfo, or require a cookie/challenge round trip before honoring stage-0 for an already-completed tunnel) and consider rate-limiting or deduplicating stage-0 processing per source/index prior to invoking the full crypto machine.

### Proof of Concept
Integration test plan (extending `e2e/handshake_manager_test.go` style tests):
1. Establish a real tunnel between two simulated nebula instances A (initiator) and B (responder), capturing the raw stage-0 UDP packet A sent to B and confirming the tunnel completes (B's main hostmap now has a hostinfo with `HandshakePacket[handshakePacketStage2]` set).
2. From a third simulated source `C` (spoofing A's original UDP source address is not even required — any allowed source suffices), resend the exact captured stage-0 bytes to B's listener via `HandleIncoming`, with `via.UdpAddr` set to an arbitrary attacker-chosen `netip.AddrPort` (the "victim" reflection target) instead of A's real address.
3. Assert that B calls `outside.WriteTo` with the cached stage-2 message targeted at the attacker-chosen address (capturable via a mock `udp.Conn`), and that this happens on every replay without any check tying the response destination to A's previously established remote.
4. Additionally assert (for the CPU-cost claim) that `machine.ProcessPacket` / `certVerifier` is invoked afresh on each replay, i.e., no request-level replay cache is consulted prior to running the full Noise/cert-verification pipeline.
5. Expected secure behavior: the response should either not be sent to an address unrelated to the tunnel's established remote, or the responder should apply return-routability/reprocessing limits so repeated replays cannot cheaply trigger repeated expensive crypto work plus arbitrary-destination sends.
