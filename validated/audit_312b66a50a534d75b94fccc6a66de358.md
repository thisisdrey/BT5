### Title
Dust-transfer griefing fills `depositTokensOfAccount` past `MAX_TOKENS_PER_USER`, causing reverts that block deposits and transfers for the victim - ([File: contracts/Pool.sol, contracts/DepositToken.sol])

### Summary
Analogous to the quinn-proto panic on unknown frames (untrusted input triggering a hard revert that halts processing), `Pool.addToDepositTokensOfAccount` hard-reverts once a user's `depositTokensOfAccount` set reaches `MAX_TOKENS_PER_USER`. An attacker can force-add entries to a victim's list by sending dust `DepositToken` transfers (or dust `deposit(..., onBehalfOf_)`), causing subsequent deposits of a new collateral type and inbound transfers to revert unconditionally until entries are manually cleared.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `recipient_`'s balance goes from 0 to >0 ( [1](#0-0) ), and `_mint` does the same on first receipt ( [2](#0-1) ).
- `Pool` stores per-account sets (`depositTokensOfAccount`, `debtTokensOfAccount`) in `PoolStorage` and enforces `MAX_TOKENS_PER_USER` inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, reverting when the cap is hit ().
- Entries are only removed when the holder's balance of that specific token returns exactly to zero ( [3](#0-2) ).
- Attack path (unprivileged EOA, no privileged role):
  1. For each live `DepositToken` the victim does not yet hold, attacker calls `deposit(dust, victim)` (permissionless, `onBehalfOf_` is arbitrary ( [4](#0-3) )) or `transfer(victim, dust)`.
  2. Victim's `depositTokensOfAccount.length` reaches `MAX_TOKENS_PER_USER`.
  3. Any subsequent `deposit(amount, victim)` for a *new* collateral, inbound `transfer`/`transferFrom` of a new `DepositToken`, or `seize` during liquidation that would credit the victim a new token reverts in `addToDepositTokensOfAccount`.

### Impact Explanation
The revert is unconditional: because the set-length check throws inside the token-mint/transfer path, the whole transaction fails — the panic analog. Consequences:
- Victim cannot deposit additional collateral of a new type (blocked from opening/topping-up positions across new markets).
- Victim cannot receive a new `DepositToken` via transfer or via liquidation proceeds (`seize` → `_transfer` → `addToDepositTokensOfAccount` revert can make `Pool.liquidate` revert when the liquidator designates the victim as `to_`, and self-griefing also blocks a liquidator whose own list is full).
- This is temporary freezing/griefing, not permanent loss: the victim can reclaim slots by transferring each dust balance out to another account (balance → 0 triggers `removeFromDepositTokensOfAccount`), paying gas proportional to the number of filler tokens. Cost to sustain the grief is low for the attacker relative to the victim's cleanup cost when many collateral types exist.

### Likelihood Explanation
- Fully permissionless: `deposit` accepts arbitrary `onBehalfOf_`, and `transfer`/`transferFrom` are unrestricted ERC-20 paths ( [5](#0-4) ).
- Attacker cost is bounded by `dust × number of DepositTokens`; each filler token needs only a 1-wei-class amount to occupy a slot.
- No modifier stops it: `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` pass; `_revertIfLocked` only constrains the sender's own balance; the victim cannot opt out of receiving tokens since there is no allowance/registry check on the recipient.

### Recommendation
- On recipient-side `add`, treat a full set as a no-op or evictable condition instead of reverting (e.g., only track tokens the account actively deposited, or revert only for self-initiated `deposit`, not inbound `transfer`).
- Alternatively, allow `deposit(..., onBehalfOf_)` to be restricted when the beneficiary's list is full, or let users clear foreign dust entries cheaply (e.g., a `removeDustToken` path that transfers the residual balance to the treasury).

### Proof of Concept
Foundry/Hardhat fork sketch:

```solidity
// Assume pool has K deposit tokens and MAX_TOKENS_PER_USER == N
// 1. Attacker fills victim's list to capacity
for (uint i; i < N; ++i) {
    depositToken[i].deposit(1, victim);            // onBehalfOf_ = victim, adds slot
    // or: depositToken[i].transfer(victim, 1)
}
assertEq(pool.getDepositTokensOfAccount(victim).length, N);

// 2. A new deposit token is registered (or victim tries a collateral they never used)
vm.expectRevert(/* MaxTokensPerUserReached-style revert in addToDepositTokensOfAccount */);
depositTokenNew.deposit(1e18, victim);            // _mint -> addToDepositTokensOfAccount reverts

// 3. Inbound transfer of an unseen deposit token also reverts for the victim
vm.expectRevert();
depositTokenNew.connect(holder).transfer(victim, 1); // _transfer -> addToDepositTokensOfAccount reverts

// 4. Recovery path: victim pushes dust out; balance -> 0 removes the entry
depositToken[i].connect(victim).transfer(attackerHelper, 1);
// now deposit succeeds again
```

Caveat: I verified the add/remove hooks in `DepositToken` and the `MAX_TOKENS_PER_USER` storage/usage in `Pool.sol`/`PoolStorage.sol` by symbol match, but did not fully read the exact revert statement inside `addToDepositTokensOfAccount`; the mechanism (cap reached → revert propagating through `_mint`/`_transfer`) is the direct analog of "untrusted input triggers a panic/DoS" and stands on Metronome's own code.
