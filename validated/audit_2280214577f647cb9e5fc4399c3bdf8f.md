## Title
Bazel disables Git's `protocol.file.allow` sandbox during `git_repository` submodule updates, allowing a malicious repository's `.gitmodules` to pull arbitrary local paths into the build - ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
The CVE-2019-19604 bug class is "content inside a fetched repository (`.gitmodules`) drives dangerous behavior in `git submodule update` that upstream Git had to specifically restrict." Bazel's `git_repository`/`new_git_repository` implementation reproduces this exposure with its own code: `update_submodules()` unconditionally forces `-c protocol.file.allow=always` on every `git submodule update --init` invocation, for both the recursive and non‑recursive case. [1](#0-0) 

### Finding Description
Git ships a defense specifically for this class of attack: `protocol.file.allow` defaults to `user` for direct, interactive invocations, but `git` deliberately makes *automatic* operations that are driven by data inside an already-fetched repository (submodule recursion, `git clone --recurse-submodules`) refuse `file://`/local-path submodule URLs unless the operator opts back in with `protocol.file.allow=always`. This is precisely the boundary that stops a repository's own `.gitmodules` from silently redirecting Git to clone arbitrary local paths without the user explicitly asking for it — the same class of bug referenced by the GitLab disclosure `003_git_submodule` linked in this CVE's references.

Bazel's `git_worker.bzl` opts back into the unsafe mode by default, for every `git_repository`/`new_git_repository` invocation that sets `init_submodules` or `recursive_init_submodules`, regardless of whether the remote is trusted: [1](#0-0) 

The comment justifies this only for the `recursive_init_submodules` case (to let submodules declared with local/relative paths clone from the parent's local worktree, bazelbuild/bazel#17040), but the override is applied to *both* branches, including plain `init_submodules = True`.

Because `git_repo.directory` is a working tree inside Bazel's `output_base/external/<repo>` directory, a `.gitmodules` file supplied by an attacker-controlled remote (any dependency, or a transitive submodule of a dependency, fetched via `git_repository`) can declare a submodule whose `url` is a relative path that escapes the repository's own checkout — e.g. `../<sibling_external_repo>/.git` or an absolute path known to exist on the build host (`/etc`, a user's home directory, another `output_base/external/...` repo checked out earlier in the same build). With `protocol.file.allow=always` forced on, Git will happily treat that as a local clone source and copy its contents into the submodule directory inside the attacker's repository, where they become ordinary files consumable by that repository's `BUILD` file (e.g. via a `filegroup`/`genrule` that bundles "submodule" content into build outputs). This is a concrete containment violation: content from outside the repository's own checkout (potentially outside the intended `output_base` boundary entirely) is pulled in as if it were part of the untrusted repo, and can then be echoed into build outputs, logs, or further processed by the dependent's build rules.

### Impact Explanation
An attacker who only controls the content of a Git repository that some build depends on (directly, or as a nested submodule of that dependency) can cause the victim's Bazel build to read and incorporate arbitrary local filesystem content that the build host can access, without the attacker needing any access to the victim's machine, credentials, or trusted root-repo Starlark. This can leak locally cached secrets, other fetched repositories, or arbitrary readable files into build outputs.

### Likelihood Explanation
`init_submodules`/`recursive_init_submodules` are ordinary, commonly-used attributes of `git_repository`/`new_git_repository` [2](#0-1) 
and Bazel silently forces the unsafe Git flag on every invocation of `update_submodules`, with no opt-out and no restriction based on where the submodule URL points, so any project using `git_repository` with submodules is exposed as soon as it depends on (transitively or directly) an untrusted/compromised Git repository.

### Recommendation
Only set `protocol.file.allow=always` when actually needed (e.g., scope it to same-machine/local test remotes, or only for submodule URLs that resolve back under the already-trusted remote's own path), and otherwise leave Git's default `protocol.file.allow=user` in place for `git submodule update` so that repository-supplied `.gitmodules` content cannot direct Git to clone from arbitrary local filesystem paths.

### Proof of Concept
Extend the existing `test_git_repository_submodules` shell test in `src/test/shell/bazel/starlark_git_repository_test.sh` [3](#0-2) 
with a malicious "outer_planets" fixture repo whose `.gitmodules` declares a submodule URL that is a relative path escaping the repository root (e.g. `url = ../../secret_dir`), pointing at a directory created by the test harness outside the git repo that should not be reachable by a normal submodule checkout. Run `git_repository(name="outer_planets", init_submodules = True, ...)`, then assert that after `bazel build`, files from `secret_dir` appear inside `bazel-bin`/the external repo checkout via a `filegroup` that just globs the submodule directory — demonstrating that content outside the fetched repository was pulled in solely because `protocol.file.allow=always` is forced by `update_submodules()` in `tools/build_defs/repo/git_worker.bzl`.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```

```shellscript
function test_git_repository_submodules() {
  local outer_planets_repo_dir=$TEST_TMPDIR/repos/outer-planets

  # Create a workspace that clones the outer_planets repository.
  cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "outer_planets",
    remote = "$outer_planets_repo_dir",
    tag = "1-submodule",
    init_submodules = 1,
    build_file = "//:outer_planets.BUILD",
)
EOF

  cat > BUILD <<EOF
exports_files(['outer_planets.BUILD'])
EOF
  cat > outer_planets.BUILD <<EOF
filegroup(
    name = "neptune",
    srcs = ["neptune/info"],
    visibility = ["//visibility:public"],
)

filegroup(
    name = "pluto",
    srcs = ["pluto/info"],
    visibility = ["//visibility:public"],
)
EOF

  mkdir -p planets
  cat > planets/BUILD <<EOF
genrule(
    name = "planet-info",
    srcs = [
        "@outer_planets//:neptune",
        "@outer_planets//:pluto",
    ],
    outs = ["planet-info.txt"],
    cmd = "cat \$(SRCS) > \$@",
)
EOF

  bazel build //planets:planet-info >& $TEST_log \
    || echo "Expected build/run to succeed"
```
