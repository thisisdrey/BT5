### Title
Unvalidated attachment content hash in `extend_with_attachments` allows a malicious peer to permanently block resolution of a legitimately committed attachment - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas downloader requests `/v2/attachments/{content_hash}` from a peer for a specific `AttachmentRequest`, the response is decoded via `decode_atlas_get_attachment()` and inserted into the batch's `attachments` set without ever checking that the returned `Attachment`'s content actually hashes to the requested `content_hash`. The `Done` state then resolves the batch using `attachment.hash()` computed from the (attacker-controlled) response bytes rather than the tracked `content_hash`, so `AttachmentsBatch::resolve_attachment` never matches the real entry.

### Finding Description
`AttachmentsBatchStateContext::extend_with_attachments` iterates `results.succeeded`, decodes the HTTP body with `decode_atlas_get_attachment()`, and does `self.attachments.insert(response.attachment)` with no comparison against `request.content_hash`: [1](#0-0) 

The HTTP client-side decoder for `/v2/attachments/:hash` responses (`decode_atlas_get_attachment`) simply JSON-decodes the body into a `GetAttachmentResponse { attachment }` and performs no hash-equality check against the endpoint that was queried: [2](#0-1) 

Later, in `AttachmentsDownloader::run`, for each `attachment` drained from `context.attachments`, the code computes `attachment.hash()` from the (potentially attacker-forged) bytes, looks up matching tracked instances by that computed hash, and calls `context.attachments_batch.resolve_attachment(&attachment.hash())`: [3](#0-2) 

`AttachmentsBatch::resolve_attachment` only removes entries from `attachments_instances` whose tracked `content_hash` equals the hash passed in: [4](#0-3) 

Since the batch tracks the on-chain-committed `content_hash` X per `attachment_index` (via `track_attachment`), but the resolution call uses `hash(attacker_bytes)` (call it Y ≠ X) computed from whatever bytes the queried peer chose to send back, the entry for X is never removed. The malicious/buggy peer's bytes get stored under hash Y in the local `atlasdb` (harmless on their own), but the legitimate tracked instance for X remains "missing" forever from the batch's perspective. Because the same peer was the (or one of the) sources selected to serve that specific content_hash request, an attacker just needs to run a peer that answers `GET /v2/attachments/{X}` with arbitrary bytes whose hash is not X, and the response will be accepted as "succeeded" and swallowed with no rejection.

Nothing in this path enforces `response.attachment.hash() == request.content_hash`. The retry loop in `AttachmentsDownloader::run` (lines 187-204) re-enqueues the batch up to `max_attachment_retry_count`, but if the attacker is the peer this instance keeps drawing (or all providing peers behave this way for this attachment), the batch is eventually dropped ("Atlas: dropping batch ... retries count exceeded") with the real attachment's `AttachmentInstance` (for content_hash X) permanently unresolved, even if X's actual bytes exist and are servable by the very node under attack via other means (e.g., they were legitimately gossiped and are sitting in `uninstantiated_attachments` under the correct hash but a wrong instance mapping is never made because `find_all_attachment_instances(&attachment.hash())` for hash Y finds nothing).

### Impact Explanation
A remote, unprivileged peer that is selected as one of the download sources for a given attachment content hash (this is routine and requires no special privilege — any outbound-connectable peer with a declared data URL can be selected) can poison the resolution of that specific BNS attachment by returning arbitrary bytes instead of the real attachment for a requested content hash. This causes a confirmed, on-chain-committed name attachment (BNS zonefile, etc.) to be permanently treated as unresolved/absent by the local node's Atlas subsystem, even though the correct data may exist elsewhere or even locally. This matches the "High: attachment/BNS mismatch" impact category — canonical committed content is not served, and no forged content is accepted as canonical (it's stored under its own correct hash, not substituted for X), but resolution of X is denied indefinitely.

### Likelihood Explanation
- Attacker only needs to run a normal P2P peer that is discoverable/connectable and gets selected among the "sources" for an `AttachmentRequest` for the target content hash — this happens naturally through the existing peer-selection/reliability-report logic, no secret or privileged role needed.
- Attacker cost is a single crafted HTTP response per requested attachment; fully repeatable for every attachment they're asked to serve.
- No signature, length, or hash check gates this response path (`decode_atlas_get_attachment` / `extend_with_attachments`), so the guard that the audit specifically calls out (equality `resolved_hash == committed_content_hash`) does not exist at all in this code path.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; treat mismatches as a failed request (`report.bump_failed_requests()` and optionally penalize/deregister the peer), matching how `AttachmentRequest.content_hash` is used to key the requests in `get_prioritized_attachments_requests`. Additionally/alternatively, thread the originally-requested `content_hash` through to the `Done` handling loop in `AttachmentsDownloader::run` and call `resolve_attachment` using the verified/tracked hash rather than trusting `attachment.hash()` recomputed from unauthenticated response content.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (following the style of `test_downloader_context_attachment_requests`):
1. Build an `AttachmentInstance` with `content_hash = X` (e.g., from `new_attachment_from("facade01")`), `track_attachment` it into an `AttachmentsBatch`, and build an `AttachmentsBatchStateContext`.
2. Simulate `get_prioritized_attachments_requests()` to obtain the `AttachmentRequest` for `content_hash = X`.
3. Build a `BatchedRequestsResult` where `succeeded` maps that request to `Some(StacksHttpResponse)` whose JSON body decodes (via `decode_atlas_get_attachment`) to a `GetAttachmentResponse` wrapping a *different* payload (e.g., `Attachment::new(b"attacker-bytes".to_vec())`, hash Y ≠ X).
4. Call `context.extend_with_attachments(&mut results)` and observe `context.attachments` contains the attacker's `Attachment` (hash Y), with no error/rejection.
5. Simulate the `Done`-state loop from `AttachmentsDownloader::run`: for the drained attachment, call `attachments_batch.resolve_attachment(&attachment.hash())` (i.e., `resolve_attachment(&Y)`).
6. Assert `attachments_batch.has_fully_succeed()` is still `false` and `attachments_batch.attachments_instances_count()` is unchanged (X was never removed) — proving the tracked instance for the real, committed content hash X is never resolved despite a "successful" download round, matching the equality-break `resolved_hash (Y) != committed_content_hash (X)` described in the question.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn resolve_attachment(&mut self, content_hash: &Hash160) {
        for missing_attachments in self.attachments_instances.values_mut() {
            let mut keys = vec![];
            for (k, hash) in missing_attachments.iter() {
                if hash == content_hash {
                    keys.push(*k);
                }
            }
            for key in keys {
                missing_attachments.remove(&key);
            }
        }
    }
