### Title
`Operator.execute` sums call values in an `unchecked` block, allowing integer wraparound to bypass the `msg.value` equality check and drain ETH held by the Operator - (File: contracts/Operator.sol)

### Summary
`Operator.execute` accumulates the per-call `value` fields into `_sumOfValues` inside an `unchecked` block and then enforces `require(msg.value == _sumOfValues)`. An attacker can craft a `Call[]` whose individual `value`s sum to `2^256 + X`, wrapping `_sumOfValues` to a small `X`. The attacker then sends only `X` wei while each sub-call forwards its full `value` via `functionCallWithValue`, spending from the Operator contract's own ETH balance. This is the direct analog of the reported bug class (CWE-190: integer overflow/wraparound producing a security-relevant discrepancy between accounted and actual value).

### Finding Description
In `Operator.execute`, the loop body does:

```solidity
unchecked {
    _sumOfValues += _value;
}
_returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
``` [1](#0-0) 

Two consequences:

1. `_sumOfValues` is a `uint256` incremented with `unchecked` addition. Supplying e.g. two calls with `value = 2^255` wraps the sum to `0`; the final `require(msg.value == _sumOfValues)` is then satisfied by `msg.value = 0`.
2. `functionCallWithValue` performs a `call{value: _value}` from the Operator's own balance, so the per-call value is *not* constrained by `msg.value` — only by `address(operator).balance`.

Any ETH held by `Operator` (refunded/leftover native token from gateway interactions, ETH pushed via `selfdestruct`, or dust accumulated from prior executions) can be extracted by setting `_call.target` to an attacker-controlled contract (or `NativeTokenGateway.deposit` with the attacker as the underlying sender) and `_call.value` covering the Operator's balance, while `msg.value` only needs to equal the wrapped remainder.

Note `execute` is `payable` and `nonReentrant` but neither the reentrancy guard nor `setMsgSender` mitigates the arithmetic wrap; the invariant `sum(call.value) == msg.value` is broken purely by overflow.

### Impact Explanation
Theft of ETH held by the Operator contract. While the contract is not designed to custody funds, any ETH balance it transiently or permanently holds (gateway refunds, forced sends, residual balances) can be drained by an unprivileged EOA for a cost of only the wrapped remainder (`sum mod 2^256`), e.g. 1 wei to extract the full balance. This is a direct loss of funds reachable from a public entry point.

### Likelihood Explanation
Exploitability is conditional on `Operator` holding a nonzero ETH balance at attack time. The contract is `payable` and sits in the path of native-token flows (`NativeTokenGateway`), so refunds or forced ETH can make this live; the attacker needs no privileges, no oracle manipulation, and no privileged actor — only crafted calldata to the public `execute` function. The overflow itself is unconditional in the code path.

### Recommendation
Remove the `unchecked` block around `_sumOfValues += _value` so that overflowing sums revert, or additionally enforce `msg.value == _sumOfValues` with checked arithmetic. Consider also tracking and refunding `address(this).balance` deltas rather than relying on the exact-equality check.

### Proof of Concept
```solidity
// Foundry
function testExecuteValueOverflow() public {
    Operator op = new Operator();
    // simulate ETH sitting in Operator (e.g., refund/forced send)
    vm.deal(address(op), 2 ether);

    AttackerReceiver r = new AttackerReceiver();

    IOperator.Call[] memory calls = new IOperator.Call[](2);
    // value_0 + value_1 = 2^256 + 1  -> wraps to 1
    calls[0] = IOperator.Call({target: address(r), callData: "", value: type(uint256).max});
    calls[1] = IOperator.Call({target: address(r), callData: "", value: 2});

    // only pays 1 wei while calls attempt to forward 2^256+1 total,
    // bounded below by op's balance; each call{value} pulls from op's balance
    op.execute{value: 1}(calls);
    assertEq(address(op).balance, 0);
    assertGt(address(r).balance, 0);
}
```

The key assertion is that `msg.value == _sumOfValues` passes with `msg.value = 1` because `type(uint256).max + 2` wraps to `1`, while the forwarded call values draw down `Operator`'s actual balance.
