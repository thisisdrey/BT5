### Title
Reward claims silently succeed without paying accrued rewards when distributor balance is insufficient - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor.claimRewards` is publicly callable and ultimately invokes `_transferRewardIfEnoughTokens`, which checks whether the accrued reward amount fits within the distributor’s current `rewardToken` balance. If the balance is insufficient, the function performs no transfer, emits no failure or depletion event, and allows the outer claim transaction to complete successfully. This is analogous to silently reducing issuance to zero when the backing vault is depleted: the user receives no reward and gets no explicit signal that the claim failed.

### Finding Description
The public `claimRewards(address[] memory, IERC20[] memory)` entry point updates token indexes and accrued rewards for each supplied account, then calls `_transferRewardIfEnoughTokens` for every account. [1](#0-0) 

`_transferRewardIfEnoughTokens` transfers rewards only when `amount_ <= rewardToken.balanceOf(address(this))`. If the accrued amount exceeds the contract balance, execution exits the conditional block without reverting, emitting `RewardClaimed`, or clearing `tokensAccruedOf[account_]`. [2](#0-1) 

The accounting continues to report the unpaid amount through `claimable`, because the accrued balance remains stored and newly accrued rewards continue to be included. [3](#0-2) [4](#0-3) 

The reward index is time-based: `_calculateTokenIndex` multiplies elapsed time by `tokenSpeeds[token_]` and distributes the result proportionally across token supply. [5](#0-4)  Consequently, ordinary reward accrual can exceed the distributor’s funded token inventory, after which calls continue succeeding while producing no payout.

### Impact Explanation
Users with accrued rewards can have their payouts temporarily frozen because a nominally successful `claimRewards` transaction transfers zero tokens whenever the distributor is underfunded. The unpaid accounting remains claimable later, so this is not necessarily permanent loss, but users cannot distinguish a failed liquidity-dependent payout from a successful claim without separately inspecting token balances or transaction logs.

This can also create a first-come payout dynamic: earlier claims consume the available balance, while later claim transactions succeed and pay nothing until the distributor is replenished.

### Likelihood Explanation
The payout failure is reachable through the deployed public `claimRewards` interface and does not require a privileged role, malformed token, governance action during the claim, oracle manipulation, or reentrancy. It materializes whenever cumulative accrued rewards exceed the distributor’s current `rewardToken` balance.

The likelihood depends on whether the deployed distributor is funded sufficiently for configured reward speeds and accrued demand. Because underfunding is an operational state rather than something an attacker can force directly in this contract, the issue is primarily an availability and feedback failure rather than direct theft.

### Recommendation
Revert explicitly when `amount_ > _balance`, for example with an `InsufficientRewardBalance` error. Alternatively, pay `min(amount_, _balance)` only if partial payments are intended, reduce `tokensAccruedOf[account_]` by the amount actually paid, and emit a dedicated partial-payment or distributor-depleted event.

At minimum, emit an event when payment is skipped so off-chain monitoring can detect that the accrued reward remains unpaid.

### Proof of Concept
The following Hardhat test can be added to `test/RewardDistributor.test.ts`, inside the existing `RewardsDistributor` fixture:

```ts
it('silently succeeds without paying when reward balance is insufficient', async function () {
  const speed = parseEther('1')
  const aliceBalance = parseEther('10')
  const distributorBalance = parseEther('1')

  pool.doesDepositTokenExist.returns(true)
  msdTOKEN1.totalSupply.returns(aliceBalance)
  msdTOKEN1.balanceOf.whenCalledWith(alice.address).returns(aliceBalance)

  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, speed)

  // Fund less than Alice's accrued reward.
  await vsp.mint(rewardDistributor.address, distributorBalance)

  await increaseTimeOfNextBlock(10)

  const accruedBefore = await rewardDistributor['claimable(address)'](alice.address)
  expect(accruedBefore).gt(distributorBalance)

  const tx = rewardDistributor['claimRewards(address)'](alice.address)

  // The transaction succeeds despite paying nothing.
  await expect(tx).to.not.be.reverted
  await expect(tx).to.not.emit(rewardDistributor, 'RewardClaimed')

  expect(await vsp.balanceOf(alice.address)).eq(0)
  expect(await vsp.balanceOf(rewardDistributor.address)).eq(distributorBalance)

  // The unpaid reward remains recorded and therefore remains temporarily frozen.
  expect(await rewardDistributor['claimable(address)'](alice.address)).gte(accruedBefore)
})
```

This reproduces the same depletion pattern as the external report: a public call completes while available inventory constrains the payout to zero and no explicit error or payout-depleted signal is emitted.

    /**
     * @notice Transfer tokens to the user
     * @dev If there is not enough tokens, we do not perform the transfer
     */
    function _transferRewardIfEnoughTokens(address account_, uint256 amount_) private {
        IERC20 _rewardToken = rewardToken;
        uint256 _balance = _rewardToken.balanceOf(address(this));
        if (amount_ > 0 && amount_ <= _balance) {
            tokensAccruedOf[account_] = 0;
            _rewardToken.safeTransfer(account_, amount_);
            emit RewardClaimed(account_, amount_);
        }
    }
