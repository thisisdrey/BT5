### Title
Attachment content unverified against `AttachmentRequest::content_hash` before `bump_successful_requests()` - reliability-report poisoning - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` treats any HTTP 200 response that JSON-decodes into a `GetAttachmentResponse` as a "successful" request and calls `report.bump_successful_requests()`, without ever checking that the returned `attachment`'s hash matches the `content_hash` that was actually requested in the corresponding `AttachmentRequest`. A malicious peer can return the same (or any) wrong-hash attachment for every distinct request in a batch and get its reliability score bumped once per request, even though zero real attachments are resolved.

### Finding Description
In `stackslib/src/net/atlas/download.rs`, `extend_with_attachments` (lines 530-559) iterates `results.succeeded`, decodes each response via `StacksHttpResponse::decode_atlas_get_attachment` [1](#0-0) , and on successful decode does:
```
self.attachments.insert(response.attachment);
report.bump_successful_requests();
```
There is no comparison between `response.attachment.hash()` and `request.content_hash` — the `request` variable (which carries `content_hash`, see `AttachmentRequest` construction at lines 467-474) is only used to fetch the peer's `UrlString` (`request.get_url()`), never to validate the payload. `decode_atlas_get_attachment` itself (`stackslib/src/net/api/getattachment.rs` lines 159-165) merely parses JSON into `GetAttachmentResponse`; it performs no hash check either.

The actual correctness check only happens much later, in `AttachmentsDownloader::run`, where `context.attachments.drain()` is matched against real pending instances via `network.atlasdb.find_all_attachment_instances(&attachment.hash())` [2](#0-1) . If a peer returns garbage/wrong-hash bytes, this lookup returns no matching instances — so no bogus attachment is ever stored as resolved for the wrong content_hash — but by that point the reliability report has already been unconditionally incremented for each of the batch's requests that "successfully" decoded, regardless of correctness.

Because `HashSet<Attachment>` at `self.attachments` dedups by full struct equality (derived `Hash`/`Eq` on `Attachment`, not by request hash), sending identical bytes for N distinct `AttachmentRequest`s collapses to one entry in the set, but that does not matter for the exploit: each request's individual iteration through `results.succeeded` independently calls `report.bump_successful_requests()` before insertion/dedup even happens.

`ReliabilityReport` scores feed `AttachmentRequest::cmp`/`AttachmentsInventoryRequest` prioritization used by `get_prioritized_attachments_requests` (lines 404-478), which builds the `BinaryHeap` ordering peers/requests are drawn from. An attacker-controlled peer can thus inflate its own reported reliability without ever serving a single correct attachment, causing the scheduler to keep preferring it over genuinely honest peers.

### Impact Explanation
This lets a remote, unprivileged peer that is chosen as an outbound sync peer (any peer the victim node syncs Atlas attachments with) poison the local reliability accounting for its own URL. Because prioritization logic (`AttachmentRequest`/`AttachmentsInventoryRequest` ordering, which is driven by `ReliabilityReport`) uses this score to decide which peer to query first for future missing attachments, an attacker peer that always responds with wrong/garbage attachments but valid HTTP 200 JSON can appear more "reliable" than honest peers, and get preferentially selected on retries — starving/deprioritizing correctly-serving peers and stalling resolution of real BNS attachment instances (matches "High - attachment/BNS mismatch" category: the node keeps preferring a peer that never serves the matching data, delaying/blocking canonical attachment resolution). This is a bounded, repeatable per-message score inflation, not a crash or memory-disclosure issue.

### Likelihood Explanation
Preconditions: the attacker must be one of the node's outbound Atlas sync peers with a reachable HTTP data URL (a normal, unprivileged P2P peer relationship — no secrets, no admin role, no special StackerDB access required) and the victim node must have pending `AttachmentInstance`s to resolve (normal BNS operation). Attack cost is trivial: return HTTP 200 with any parseable `GetAttachmentResponse` JSON body for every attachment GET request, repeatedly, across every batch. This is directly reachable over the standard `/v2/attachments/:hash` RPC-shaped path used between peers, with no rate limiting tied to hash correctness.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment` succeeds, verify `response.attachment.hash() == request.content_hash` before calling `report.bump_successful_requests()`; if the hash doesn't match, treat it the same as a failed/faulty response (`report.bump_failed_requests()`, and consider adding the peer to `faulty_peers`/`events_to_deregister` for repeated offenses).

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/download.rs` test module or a new net test):
1. Construct an `AttachmentsBatchStateContext` with one peer URL and a `BatchedRequestsResult<AttachmentRequest>` where `succeeded` contains 3 `AttachmentRequest`s with distinct `content_hash` values (H1, H2, H3), each mapped to a mocked `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment(some_fixed_wrong_bytes) }` (hash = Hx, where Hx != H1, H2, H3).
2. Call `context.extend_with_attachments(&mut results)`.
3. Assert `context.peers.get(&peer_url).unwrap()`'s internal success counter was incremented 3 times (`bump_successful_requests()` called 3×) — inspect via a getter or by checking the computed reliability ordering shifts as if 3 genuine successes occurred.
4. Separately assert that `context.attachments` contains at most 1 entry (dedup by struct equality) and that none of H1/H2/H3 would resolve via `atlasdb.find_all_attachment_instances(&Hx)` for the real pending instances — i.e., zero genuine `AttachmentInstance` resolutions correspond to the 3 recorded "successes", proving the reliability score is decoupled from actual per-hash correctness.
