This is the key finding: unless a governance proposal enables `AllowHardenExchangeCalculation`, the ExchangeWithdraw/ExchangeInject/ExchangeTransaction flows compute the AMM balance updates with plain (non-overflow-checked) `long` arithmetic and the legacy `ExchangeProcessor`, which relies on `double`-based `Math.pow` for the bancor-style curve, instead of the safe `BigDecimal`-based `SafeExchangeProcessor`, and skips the post-transaction non-negative-balance invariant check entirely.

### Title
Missing enforcement of exchange balance invariant in legacy (non-hardened) AMM path allows disproportionate withdrawal — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
The mAsset report flags that `_redeemTo` trusts a governance-set collateralisation ratio without any on-chain bound, so a misconfigured/attacker-influenced ratio lets redemptions bypass the intended backing check. The closest reachable analog in java-tron is the Bancor-relay `Exchange*` actuator family (`ExchangeWithdrawActuator`, `ExchangeInjectActuator`, `ExchangeTransactionActuator`), whose safety (overflow checks, non-negative balance invariant, and precision method) is entirely gated by the dynamic-property flag `AllowHardenExchangeCalculation`, exposed only via `AbstractExchangeActuator.allowHarden()` [1](#0-0)  and consumed by `ExchangeCapsule.transaction` [2](#0-1) . As in the audited mAsset code, the contract logic itself performs no independent sanity/invariant check when the governance switch is off (`hardenedCalc == false`); it simply relies on the committee proposal being set correctly.

### Finding Description
`ExchangeCapsule.transaction` selects between two very different arithmetic engines based purely on the `hardenedCalc` boolean sourced from the dynamic property `AllowHardenExchangeCalculation`:
- When `hardenedCalc == true`, `SafeExchangeProcessor` (BigDecimal, `RoundingMode.DOWN`, 18-digit precision) is used, and the code explicitly re-validates that both pool balances remain `>= 0` after the update [3](#0-2) .
- When `hardenedCalc == false` (the default/legacy path, and the only path unless a super-representative proposal enables the flag), `ExchangeProcessor` is used, which computes the Bancor formula with plain Java `double`/`Math.pow` operations [4](#0-3) , and the resulting new balances are stored via plain `long` addition/subtraction with **no invariant check at all** — the `if (hardenedCalc && ...)` guard at [3](#0-2)  is skipped entirely when `hardenedCalc` is false.

This mirrors the mAsset pattern exactly: the code contains a strict, ratio/invariant-respecting path, but whether it is actually enforced depends on a governance-controlled switch that the actuator code does not itself require to be enabled. `ExchangeWithdrawActuator.execute` computes payouts using `BigInteger` division that is independent from this switch [5](#0-4) , but its accompanying validation only bounds the *rounding error* to within a fixed 0.01% tolerance band via `allowHarden()`-branching BigDecimal/double checks [6](#0-5) , and in the non-hardened branch this tolerance check itself uses `double` division, which is capable of losing precision at large pool sizes, again without an invariant re-check post-execution.

### Impact Explanation
If `AllowHardenExchangeCalculation` is not enabled (its default/legacy state), `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` all depend on floating-point Bancor math with no invariant enforcement. An attacker who can drive the pool into edge-case ratios (extreme balance skew, near-zero balances, or repeated small trades that accumulate floating-point drift) could extract more value from the exchange pool than they contributed, i.e., a disproportionate redemption from a shared token pool funded by other users — analogous to the disproportionate mAsset redemption described in the report. This is a fund-theft-class impact reachable by any account that can submit `ExchangeTransactionContract`/`ExchangeWithdrawContract`/`ExchangeInjectContract` transactions (no special privilege required).

### Likelihood Explanation
Medium. Exploitation requires precise construction of pool balances/trade sizes to trigger meaningful floating-point drift or rounding advantage repeatedly, and the actual `Bancor`-relay `Exchange*` contract type is a legacy, low-usage TRON feature; it's not clear whether current mainnet has `AllowHardenExchangeCalculation` enabled (if it is enabled network-wide, this analog is not exploitable). This uncertainty about the live on-chain proposal state should be confirmed by whoever validates this finding, since it is dispositive of exploitability.

### Recommendation
Require the invariant/precision-safety check unconditionally in `ExchangeCapsule.transaction` regardless of `hardenedCalc`, rather than gating it behind a governance switch: always validate `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` after any pool update, and consider making `SafeExchangeProcessor` (BigDecimal-based) the only supported computation path, removing the legacy `double`-based `ExchangeProcessor` entirely, consistent with the report's recommendation to bake protective bounds directly into the code path instead of relying on external configuration.

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation would require constructing specific `Exchange` pool balances (via `ExchangeCreateContract`/`ExchangeInjectContract`) and a sequence of `ExchangeTransactionContract`/`ExchangeWithdrawContract` calls while `AllowHardenExchangeCalculation` is disabled, then measuring whether the `double`-based `ExchangeProcessor.exchange` path yields a payout exceeding what `SafeExchangeProcessor` would compute for the same inputs — this divergence is visible in `ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection`, which already documents an observed ±1-unit difference between legacy and hardened results [7](#0-6) ; a background agent with test-execution access would be needed to determine whether larger, exploitable divergences are achievable at extreme pool ratios.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);

    logger.debug("balance + quant: " + newBalance);

  private long exchangeFromSupply(long balance, long supplyQuant) {

    return (long) exchangeBalance;
  }
