### Title
Unverified attachment content persisted via `GetAttachmentResponse` breaks attachment/content_hash binding - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the `AttachmentsDownloader` receives a peer's `GetAttachmentResponse`, it inserts the returned `Attachment` into `self.attachments` without checking that its hash matches the `content_hash` that was actually requested. It then unconditionally calls `AtlasDB::insert_instantiated_attachment`, persisting attacker-supplied content under `Attachment::hash()` even when no `AttachmentInstance.content_hash` row in `attachment_instances` matches that hash.

### Finding Description
The claimed equality — "served bytes' hash == committed content_hash" — is broken. In `AttachmentsBatchStateContext::extend_with_attachments` [1](#0-0) , the response is decoded via `decode_atlas_get_attachment()` and the resulting `Attachment` is inserted into a `HashSet<Attachment>` with no comparison against the `AttachmentRequest`'s expected `content_hash`.

Later, in `AttachmentsDownloader::run`, every attachment collected in `context.attachments` is persisted unconditionally: [2](#0-1) 
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())...;
    network.atlasdb.insert_instantiated_attachment(&attachment)...;
    for attachment_instance in attachments_instances.into_iter() {
        resolved_attachments.push((attachment_instance, attachment.clone()));
    }
    ...
}
```
`insert_instantiated_attachment` itself performs an `INSERT OR REPLACE INTO attachments (...) VALUES (..., was_instantiated=1, ...)` unconditionally, followed by an `UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = Checked` [3](#0-2) . The `UPDATE` is a no-op if no row matches, but the `INSERT` into the `attachments` table happens regardless of whether any confirmed `AttachmentInstance` ever referenced that hash.

Root cause: the response-processing code computes `attachment.hash()` from the attacker's own bytes and uses it purely as a lookup key — it never asserts that this hash equals the hash the request was originally made for (i.e., an `AttachmentInstance.content_hash` from a committed on-chain BNS event). A malicious peer answering any outbound `GetAttachmentResponse` request (from `AttachmentsBatchStateMachine`/`BatchedRequestsResult`) can therefore return arbitrary bytes `C`; the node computes `H = Hash160(C)` and stores `(H, C)` in the `attachments` table with `was_instantiated=1`, with `find_all_attachment_instances(&H)` simply returning empty (no instance updated, no confirmation), but the row persists.

### Impact Explanation
Any outbound peer selected by the Atlas downloader to serve an attachment batch can respond with unrelated/arbitrary payloads instead of the content actually committed on-chain. Each such payload is persisted into local disk storage (`attachments` table) under `was_instantiated=1`, and there is no eviction routine for `was_instantiated=1` rows (only `evict_expired_uninstantiated_attachments`/`evict_k_oldest_uninstantiated_attachments`, which act solely on `was_instantiated=0`) [4](#0-3) . This is repeatable per outbound sync attempt/response and per attacker-controlled peer, enabling unbounded disk growth from content that no `AttachmentInstance` (i.e., no on-chain BNS name operation) ever committed to. This matches the High-impact category "attachment/BNS mismatch" — content is stored and can even be served back via `find_attachment` / `GET /v2/attachments/{hash}` for a hash that no confirmed BNS event tracks, even though no `resolved_attachments` entry ties it to any name (since `find_all_attachment_instances` returns empty for a hash that has no matching instance, so BNS resolution logic is not directly deceived, but storage is polluted/exhausted with data outside the committed content_hash space).

### Likelihood Explanation
Preconditions: the target node must be running the Atlas downloader (`enable_atlas_attachment_downloads`-style outbound sync, standard for BNS support) and have the attacker as one of its `outbound_sync_peers`, which any unprivileged remote peer that establishes an outbound-eligible P2P/HTTP connection can become. No secret, signature, or privileged role is required — the attacker merely needs to be selected to serve a batch and respond to the resulting `GetAttachmentResponse` HTTP request with crafted content. This is repeatable on every batch/round the attacker is queried, at negligible attacker cost (one HTTP response per request, bounded only by `attachments_max_size`/`ATTACHMENTS_MAX_SIZE_MIN`, which does not appear enforced at the download-response ingestion point in the code paths inspected).

### Recommendation
In `extend_with_attachments` (and/or before calling `insert_instantiated_attachment` in `AttachmentsDownloader::run`), verify that `response.attachment.hash()` equals the `content_hash` of the specific `AttachmentRequest` that produced this response before accepting it into `self.attachments`/before persisting. Discard and penalize (`bump_failed_requests`) any response whose content hash does not match the requested hash, mirroring the check already implicitly relied upon by `find_all_attachment_instances`.

### Proof of Concept
Rust test plan (net test, in `stackslib/src/net/atlas/tests.rs` or `download.rs` test module):
1. Construct a `PeerNetwork`/`AtlasDB` test harness with one queued/checked `AttachmentInstance` whose `content_hash = H_expected` (a hash the attacker does NOT know the preimage of, e.g., derived from random bytes never revealed).
2. Simulate a `BatchedRequestsResult<AttachmentRequest>` where the "succeeded" response for that request contains an attacker-crafted `GetAttachmentResponse { attachment: Attachment { content: b"attacker-controlled-garbage" } }` (i.e., content whose hash `H_attacker != H_expected`).
3. Call `AttachmentsBatchStateContext::extend_with_attachments` with this result, then drive `AttachmentsDownloader::run` to completion.
4. Assert: `atlasdb.find_attachment(&H_attacker).unwrap().is_some()` returns `Some(Attachment { content: b"attacker-controlled-garbage" })`, while `atlasdb.find_all_attachment_instances(&H_attacker).unwrap()` is empty — proving content was persisted (`was_instantiated=1`) under a hash that no `AttachmentInstance.content_hash` in `attachment_instances` ever equals, confirming the storage-pollution/exhaustion vector at `stackslib/src/net/atlas/db.rs:576-592`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
