### Title
Attacker-controlled Atlas attachment download bypasses `attachments_max_size`, allowing unbounded SQLite BLOB writes - (File: `stackslib/src/net/atlas/download.rs`, `stackslib/src/net/atlas/mod.rs`)

### Summary
When a node downloads an attachment from a peer via `GET /v2/attachments/<hash>`, the response is decoded by `StacksHttpResponse::decode_atlas_get_attachment` and folded into the batch via `AttachmentsBatchStateContext::extend_with_attachments`, then unconditionally persisted with `AtlasDB::insert_instantiated_attachment`. Neither of these steps re-validates `attachment.content.len()` against `AtlasConfig::attachments_max_size`, unlike the sibling ingestion path `AtlasDB::should_keep_attachment` (used for POSTed transaction attachments), which does enforce this bound. A malicious peer answering an attachment-download request can therefore return oversized content that is written straight into the requester's SQLite `attachments` table.

### Finding Description
The claimed equality — "bytes accepted into AtlasDB == bytes within the configured `attachments_max_size` bound" — is broken on the download path.

- `GetAttachmentResponse::deserialize` (`stackslib/src/net/atlas/mod.rs:69-77`) takes an arbitrary hex string from the HTTP JSON body and turns it into `Attachment::new(bytes)` with no length check at all.
- `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) parses the JSON body into this struct — again, no size check against `attachments_max_size`.
- `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) simply calls `response.decode_atlas_get_attachment()` and inserts the resulting `Attachment` into `self.attachments` if decoding succeeds — no size check.
- In `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-169`), for every attachment produced by the state machine, the code does:
  ```rust
  let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
  network.atlasdb.insert_instantiated_attachment(&attachment)?;
  ```
  `insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) writes `attachment.content` directly into the `attachments` SQLite table with `INSERT OR REPLACE`, with **no size check whatsoever**. This call happens unconditionally regardless of whether `find_all_attachment_instances` found a matching, previously-tracked instance for that hash — i.e., the content is stored purely keyed by its own self-computed hash, not validated against the size cap that governs every other ingestion path (`AtlasDB::should_keep_attachment`, `stackslib/src/net/atlas/db.rs:249-266`, used in `posttransaction.rs`).

The only size ceiling actually enforced on this path is the generic P2P/HTTP message cap, `MAX_MESSAGE_LEN`, checked in `stackslib/src/net/connection.rs:716-724` and reused as the JSON-body bound in `httpcore.rs` (`RPCArbitraryResponseHandler::try_parse_response`, line ~953). That constant is a fixed protocol-wide ceiling (tens of MB), completely decoupled from the per-node-configured `attachments_max_size` (`ATTACHMENTS_MAX_SIZE_MIN = 1_048_576`, i.e. 1 MiB minimum, operator-configurable). A peer answering an attachment request can therefore return content up to `MAX_MESSAGE_LEN`, far larger than any reasonable `attachments_max_size` configuration, and it will be accepted and written to disk.

Exploit flow:
1. Victim node has an unresolved `AttachmentInstance` (from on-chain BNS data) and queues a batch of `AttachmentRequest`s to known peers, including the attacker's node/URL.
2. Attacker's node serves `GET /v2/attachments/<hash>` with a JSON body `{"attachment": "<huge_hex_string>"}` whose decoded length is tens of MB (below `MAX_MESSAGE_LEN`).
3. `extend_with_attachments` decodes and accepts it purely because JSON/hex decoding succeeded.
4. `AttachmentsDownloader::run` calls `insert_instantiated_attachment`, which performs an unconditional SQLite `INSERT OR REPLACE` of the oversized BLOB, regardless of `attachments_max_size` and regardless of whether the content's hash matches any tracked instance.

### Impact Explanation
A single crafted HTTP response from any peer the victim contacts for attachment resolution causes the victim to allocate and durably store an oversized BLOB (bounded only by `MAX_MESSAGE_LEN`, not by the configured `attachments_max_size`), consuming memory during JSON/hex decoding and disk space via the SQLite write. This is repeatable per attachment-instance / per distinct hash the attacker fabricates, allowing sustained disk/memory growth against the requesting node — an unauthenticated write to persisted node state that bypasses an explicit, operator-configured resource limit. This matches the Critical category "unauthenticated/unauthorized write to state."

### Likelihood Explanation
- Preconditions: the victim node must be actively running the Atlas attachment downloader (default behavior for nodes tracking BNS/Atlas attachments) and must contact the attacker's peer to resolve an attachment (attacker can advertise reachability/inventory to get selected, or simply be one of the peers a legitimate instance is queried against).
- Attacker cost: trivial — a single crafted HTTP JSON response from a normal, unprivileged remote peer; no secret, signature, or privileged role needed.
- Remote reachability: the `/v2/attachments/<hash>` RPC endpoint is a standard peer-reachable HTTP route; the download client uses the generic HTTP response path with no extra ingestion-time size validation.
- Repeatability: repeatable across any number of distinct fabricated hashes/requests.

### Recommendation
Enforce `atlas_config.attachments_max_size` at ingestion time in the download path, mirroring `AtlasDB::should_keep_attachment`:
- In `GetAttachmentResponse::deserialize` or, more robustly, in `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:547`), reject/drop responses whose `attachment.content.len()` exceeds `attachments_max_size` before inserting into `self.attachments`.
- Additionally, guard `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576`) itself to check size (and ideally that the attachment's hash matches an actually-tracked `AttachmentInstance.content_hash`) before writing to SQLite, so no caller path can bypass the limit.

### Proof of Concept
Rust test in `stackslib::net::atlas::download` (or `stackslib/src/net/api/tests/getattachment.rs`):
1. Build an `AtlasConfig` with `attachments_max_size = 1_048_576` (minimum).
2. Construct a `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment::new(vec![0u8; 5_000_000]) }` (hex-encoded, well under `MAX_MESSAGE_LEN` but over `attachments_max_size`).
3. Feed it through `response.decode_atlas_get_attachment()` and then `AttachmentsBatchStateContext::extend_with_attachments`.
4. Assert that `context.attachments` contains the 5,000,000-byte attachment (no rejection occurred), then call `atlasdb.insert_instantiated_attachment(&attachment)` and assert it succeeds and `atlasdb.find_attachment(&attachment.hash())` returns the full oversized content — demonstrating that `attachments_max_size` was never enforced, in contrast to `atlasdb.should_keep_attachment(...)` returning `false` for the same content on the POST-transaction path.
