### Title
Unbounded-cost MARF proof lookup on `GET /v2/clarity/marf/:marf_key_hash?proof=1` — no `LimitedCostTracker`/`ResourceLimiter` unlike sibling read-only RPC endpoints - (File: `stackslib/src/net/api/getclaritymarfvalue.rs`)

### Summary
`RPCGetClarityMarfRequestHandler::try_handle_request` calls `clarity_tx.with_clarity_db_readonly(...)` directly and invokes `clarity_db.get_data_with_proof_by_hash`/`get_data_by_hash` on a raw MARF trie walk, with no `LimitedCostTracker`, no `ResourceLimiter`/`ResourceBudget`, and no execution-time budget applied anywhere in the call path. This is unlike `callreadonly.rs` and `fastcallreadonly.rs`, which both construct a `LimitedCostTracker` (or `LimitedCostTracker::new_free()`) and explicitly install a `ResourceLimiter` via `set_execution_resource_limiter` bounding wall-clock duration and memory before doing any VM/database work.

### Finding Description
The equality claimed to hold across read-only RPC endpoints is: "IO/CPU spent per request == a configured, enforced read-only bound." For `callreadonly.rs` this is enforced twofold: a `LimitedCostTracker` built from `ConnectionOptions::read_only_call_limit` bounds Clarity VM execution cost [1](#0-0) , and a `ResourceLimiter`/`ResourceBudget` (`execution_resource_limiter`) bounds wall-clock duration and memory regardless of cost-tracker state [2](#0-1) . `fastcallreadonly.rs` uses `LimitedCostTracker::new_free()` but still installs the same `ResourceLimiter` to bound duration, with an explicit comment that "we enforce max_execution_time when cost tracking is disabled/free" [3](#0-2) .

`getclaritymarfvalue.rs`'s handler instead calls `chainstate.maybe_read_only_clarity_tx(...)` and then `clarity_tx.with_clarity_db_readonly(|clarity_db| ...)` directly — it never goes through `with_readonly_clarity_env`, never constructs any `LimitedCostTracker`, and never calls `set_execution_resource_limiter` [4](#0-3) . The `get_data_with_proof_by_hash` call descends straight to `MARF::get_with_proof_from_hash` / `TrieMerkleProof::from_path`, which walks the trie path and, for each backptr segment, performs a `make_backptr_shunt_proof` that walks back through ancestor blocks and recomputes root hashes [5](#0-4) , none of which is metered by any cost/time budget in this endpoint.

An attacker with only public RPC access can compute `TrieHash` values (`TrieHash::from_key(key)`) for known Clarity storage keys of deployed contracts (all deterministic and reproducible off-chain from public contract state), then repeatedly issue `GET /v2/clarity/marf/<hash>?proof=1` requests targeting entries with long backptr/shunt-proof chains, causing repeated unmetered trie/DB I/O and CPU work per request with no accounting.

### Impact Explanation
Each request causes the node to perform disk I/O and CPU work proportional to the trie/backptr-shunt-proof depth of the targeted key with zero cost or time enforcement, unlike every comparable read-only endpoint in the same module (`callreadonly.rs`, `fastcallreadonly.rs`). This is repeatable at will by an unauthenticated remote caller against any node exposing the RPC port, and can be used to degrade node responsiveness for other RPC/API consumers. This matches the "bounded compute DoS on a read endpoint" category (High) rather than "Critical," since the per-request work is still asymptotically bounded (fixed-length hash path plus `O(log(chain height))` shunt-proof segments) — there is no unbounded loop, panic, memory-safety violation, forged/stored data, or unauthenticated write.

### Likelihood Explanation
No authentication, secret, or privileged role is required — this is a plain public GET endpoint. The attacker needs only to know or derive valid `marf_key_hash` values for real, existing contract-data keys (computable off-chain from public chain state) to trigger the more expensive "found" code path with proof construction; cost per request is cheap for the attacker (a GET request) versus the node's trie-walk + shunt-proof work. It is trivially repeatable at arbitrary rate limited only by the attacker's own connection throughput.

### Recommendation
Bound this endpoint the same way `callreadonly.rs`/`fastcallreadonly.rs` are bounded: install a `ResourceLimiter`/`ResourceBudget` (wall-clock duration, and optionally memory) around the `with_clarity_db_readonly` closure before calling `get_data_with_proof_by_hash`/`get_data_by_hash`, and/or add an explicit maximum proof-depth / execution-time check inside the handler, configurable via `ConnectionOptions` similar to `read_only_max_execution_time_secs`.

### Proof of Concept
Add a test under `stackslib::net::api::tests::getclaritymarfvalue` (mirroring `stacks-node/src/tests/mem_abort.rs`'s `test_read_only_call_max_mem_bytes_threaded_into_http`) that:
1. Constructs `RPCGetClarityMarfRequestHandler` and confirms it has no `read_only_call_limit`/`execution_resource_limiter`-equivalent field, contrasting with `RPCCallReadOnlyRequestHandler::execution_resource_limiter` at `stackslib/src/net/api/callreadonly.rs:100-108`.
2. Seeds a chainstate with a contract that has a deeply nested/ancestor-spanning MARF key (many block updates to the same key to build a long backptr chain), computes its `TrieHash`, and issues repeated `GET /v2/clarity/marf/<hash>?proof=1` requests while timing `get_data_with_proof_by_hash`.
3. Asserts that wall-clock time grows with backptr chain depth and that no `ExecutionResourceBudgetExceeded`/timeout error is ever returned, in contrast to `callreadonly.rs`'s `ClarityEvalError::Vm(RuntimeCheck(RuntimeCheckErrorKind::ExecutionResourceBudgetExceeded(_)))` handling at `stackslib/src/net/api/callreadonly.rs:294-303`.
