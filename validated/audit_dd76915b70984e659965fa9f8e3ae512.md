### Title
`FetchRemote` fails to disable Git bundle-URI feature, enabling SSRF via a malicious remote — ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemote` builds `git-fetch(1)` invocations from a user-supplied remote URL without disabling the `transfer.bundleURI` feature, unlike the sibling `CreateRepositoryFromURL` RPC, which was explicitly patched to set `transfer.bundleURI=false` to prevent SSRF. This is the same class of bug as the external report: a security-relevant parameter (there, `refundAddress`; here, the bundle-URI opt-out) is correctly applied in one call path but silently omitted in another reachable path that processes the same kind of attacker-influenced input (a remote URL).

### Finding Description
`CreateRepositoryFromURL`'s `cloneFromURLCommand` explicitly disables bundle URIs when cloning from an arbitrary URL: [1](#0-0) 

This was added as a dedicated security fix, as recorded in the changelog: [2](#0-1) 

The Git bundle-URI mechanism allows a remote server (or a `git-fetch` response) to advertise an arbitrary URI which the fetching client (Gitaly, running server-side) will then fetch from, independent of the original remote's own trust boundary — precisely the SSRF vector the fix in `create_repository_from_url.go` addresses.

However, `FetchRemote`, which is another RPC that spawns `git-fetch(1)` against a fully attacker/administrator-supplied `RemoteParams.Url` (used for repository mirroring), builds its fetch options in `buildCommandOpts` without ever setting `transfer.bundleURI=false`: [3](#0-2) 

The fetch is executed through `quarantineRepo.FetchRemote(ctx, "inmemory", opts)`: [4](#0-3) 

Just like the four call paths analyzed in the original report for `refundAddress`, the security control (opt-out of bundle URIs) is applied inconsistently: it is present in the `CreateRepositoryFromURL` path but missing from the `FetchRemote` path, even though both paths take a fully user/admin-controlled remote URL and invoke Git networking code that can chase a secondary, attacker-controlled bundle URI.

### Impact Explanation
If a Git remote configured for mirroring (or reachable via `FetchRemote`) advertises a bundle URI during the `git-fetch(1)` protocol handshake, Gitaly (server-side) will follow that URI to fetch bundle data. Since `transfer.bundleURI` is not disabled here, an attacker who controls (or can register) the fetch target's Git server responses can cause the Gitaly server to issue requests to arbitrary internal addresses (e.g., cloud metadata endpoints, internal services), resulting in SSRF from the Gitaly node. This is the same impact class explicitly called out as the rationale for the fix in the sibling RPC.

### Likelihood Explanation
`FetchRemote` is a standard, reachable RPC used for repository mirroring configured by ordinary project maintainers/administrators (not a privileged Gitaly operator). Any repository owner who can configure a pull mirror URL can point it at a malicious/attacker-controlled Git server that returns a crafted bundle-URI advertisement, triggering the SSRF automatically on the next scheduled/triggered fetch. No additional privileges beyond normal mirror configuration are required, and the code path is exercised identically to the already-patched `CreateRepositoryFromURL` path.

### Recommendation
Apply the same mitigation used in `CreateRepositoryFromURL`: explicitly disable the bundle-URI feature for `FetchRemote`'s command options, e.g. by appending `gitcmd.ConfigPair{Key: "transfer.bundleURI", Value: "false"}` (or the equivalent `gitcmd.WithGlobalOption`) in `buildCommandOpts` before constructing the `git-fetch` invocation. Audit other RPCs that build outbound `git fetch`/`git clone` commands from user-supplied remote URLs (e.g. `UpdateRemoteMirror`, `FindRemoteRepository`, `FindRemoteRootRef`) to ensure the same opt-out is consistently applied everywhere fetch-like commands are constructed from external URLs.

### Proof of Concept
1. Configure a pull mirror (or otherwise trigger `FetchRemote`) pointing `RemoteParams.Url` at an attacker-controlled Git server.
2. The attacker's Git server, during the `git-fetch` v2 protocol exchange, advertises a `bundle-uri` capability pointing to an internal address (e.g., `http://169.254.169.254/latest/meta-data/` or an internal-only service).
3. Because `buildCommandOpts` in `internal/gitaly/service/repository/fetch_remote.go` never sets `transfer.bundleURI=false`, Git on the Gitaly server follows the advertised bundle URI and issues a request to the internal address, exfiltrating data or performing internal-network reconnaissance — the exact scenario the `CreateRepositoryFromURL` fix in `create_repository_from_url.go` (lines 72-76) was designed to prevent, but which remains open in `FetchRemote`.

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if featureflag.FetchRemoteProactiveAuth.IsEnabled(ctx) {
		if u, err := url.Parse(remoteURL); err == nil && u.User != nil {
			password, _ := u.User.Password()
			if u.User.Username() != "" && password != "" {
				config = append(config, gitcmd.ConfigPair{
					Key:   "http.proactiveAuth",
					Value: "basic",
				})
			}
		}
	}

	if authHeader := req.GetRemoteParams().GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", req.GetRemoteParams().GetUrl()),
			Value: "Authorization: " + authHeader,
		})
	}

	opts.CommandOptions = append(opts.CommandOptions, gitcmd.WithConfigEnv(config...))

	return nil
}
