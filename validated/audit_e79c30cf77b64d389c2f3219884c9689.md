## Title
`pallet-bridge-relayers::claim_rewards_to()` clears the reward ledger before confirming the beneficiary can actually receive the asset on the remote chain, letting a relayer permanently lose (or grief) their own Snowbridge reward via an unreceivable AssetHub beneficiary - (File: `bridges/snowbridge/primitives/core/src/reward.rs`, `bridges/modules/relayers/src/lib.rs`)

### Summary
`PayAccountOnLocation::pay_reward` (used as the `Snowbridge` branch of `BridgeRewardPayer`) treats a reward as "paid" the moment the XCM carrying the reward asset is *sent* to AssetHub, without any guarantee that the `DepositAsset` instruction will actually succeed at the beneficiary on the remote chain [1](#0-0) . `pallet_bridge_relayers::do_claim_rewards` removes the relayer's `RelayerRewards` entry and emits `RewardPaid` as soon as `PaymentProcedure::pay_reward` returns `Ok(())` [2](#0-1) . This is the same class of bug as the `L1Migrator` finding: a "successful" hand-off (an XCM `deliver()`/a low-level `.call()`) is conflated with actual, successful value receipt by the counterparty, and there is no fallback path once the transfer to that counterparty fails.

### Finding Description
The public, unprivileged extrinsic `claim_rewards_to(origin, reward_kind, beneficiary)` lets any relayer supply an arbitrary `BeneficiaryOf<T, I>` (for `Snowbridge` rewards this is `BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation)`) [3](#0-2) .

`do_claim_rewards` does the following, in order, inside a single `try_mutate_exists`:
1. Take (delete) the relayer's accrued reward balance from `RelayerRewards`.
2. Call `T::PaymentProcedure::pay_reward(...)`.
3. If that call returns `Ok`, emit `RewardPaid` and keep the reward deleted; only an `Err` return rolls the storage mutation back [2](#0-1) .

For the `Snowbridge` reward kind, `pay_reward` is implemented by `PayAccountOnLocation`, which builds an XCM program consisting of `UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, and `DepositAsset { assets: AllCounted(1), beneficiary }`, then calls `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver(ticket)` [1](#0-0) . The function returns `Ok(())` as soon as the message is queued for delivery (`deliver` succeeds) - it never waits for, or checks, the result of executing `DepositAsset` on AssetHub. No `SetAssetClaimer` is set for the reward beneficiary path, and no reservation/checks are made that the caller-supplied `beneficiary` location is capable of receiving the `eth_location()` foreign asset (e.g., that the account exists, meets ED requirements for that asset class, or resolves to a valid receiving account at all).

If the remote `DepositAsset` instruction fails (unregistered/insufficient beneficiary account, asset not marked sufficient, wrong `VersionedLocation` version/shape that resolves to a technically-valid-but-unreachable location, etc.), the XCM executor traps the assets on AssetHub. Meanwhile, on BridgeHub, the reward has already been irreversibly removed from `RelayerRewards` and `RewardPaid` has already been emitted, because `pay_reward` returned `Ok` the instant the message was handed off to `XcmSender::deliver`. There is no callback or receipt path from AssetHub back to BridgeHub that could re-credit the reward on failure, unlike, e.g., a delivery-receipt driven flow (`process_delivery_receipt` in the outbound queue only reacts to relayer delivery, not to reward payout success/failure).

This mirrors the `L1Migrator` bug precisely: the "sending" side (`BridgeMinter.call.value(...)`/here, `XcmSender::deliver`) is treated as proof of successful value transfer, while the receiving side (`L1Migrator`/here, the AssetHub beneficiary via `DepositAsset`) can silently be incapable of accepting the value, and the accounting on the sending side has already been finalized irreversibly.

### Impact Explanation
An unprivileged relayer can supply a `beneficiary` location that cannot actually receive the reward asset on AssetHub (through error, or simply because they mis-encode/forget to fund the destination account). The `RelayerRewards` entry is deleted and `RewardPaid` fires on BridgeHub regardless, while the underlying reward funds become trapped/lost on AssetHub with no re-claim path back to the relayer through the pallet's own accounting. This is a permanent loss of relayer-owed bridge reward funds -- the exact "permanent user-fund or bridge-state lock" class called out in the impact gate, achieved purely through a normal, unprivileged public call (`claim_rewards_to`), with no malicious relayer/validator/governance action required beyond the caller choosing (even accidentally) an unreachable beneficiary.

### Likelihood Explanation
Likelihood is moderate-to-high: `claim_rewards_to` is a normal, frequently-used relayer operation, and the beneficiary is fully attacker/user controlled (`VersionedLocation`), with no on-chain validation that it is actually capable of receiving the deposited foreign asset before the local reward ledger is cleared. The existing test suite only checks the "happy path" (`claim_rewards_works`) where the beneficiary is a pre-funded, well-formed account, and a distinct failure mode where `pay_reward` itself returns `Err` (`claim_snowbridge_rewards_to_local_account_fails`) [4](#0-3) . Neither test covers the case where `pay_reward` returns `Ok` (message delivered) but the remote `DepositAsset` subsequently fails/traps -- exactly the scenario this analysis identifies as unguarded.

### Recommendation
- Do not remove the `RelayerRewards` entry (or emit `RewardPaid`) until receipt of remote-side confirmation that the deposit succeeded, or add an asset-claim/refund mechanism tied back to the specific relayer/reward if the remote `DepositAsset` traps.
- Alternatively, validate the beneficiary (existence, ED sufficiency for the specific foreign asset, location well-formedness) before consuming the reward balance, and/or add `SetAssetClaimer` to the remote XCM program so a failed deposit can be recovered by the relayer via `pallet_xcm::claim_assets`, with clear on-chain guidance/automation for that recovery path.
- Consider a two-phase commit: mark the reward as "in-flight" rather than deleting it outright, and only finalize deletion upon a delivery/execution acknowledgment from AssetHub (similar in spirit to the existing `process_delivery_receipt` pattern already used elsewhere in Snowbridge for relayer rewards).

### Proof of Concept
1. A relayer accrues a `Snowbridge` reward via `register_reward` on BridgeHub [5](#0-4) .
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::V5(location)))`, where `location` resolves to an account on AssetHub that has never been funded and cannot satisfy the ED requirement for holding the `eth_location()` foreign asset (or is otherwise unable to accept `DepositAsset`).
3. On BridgeHub, `do_claim_rewards` deletes the `RelayerRewards` entry and emits `RewardPaid` because `PayAccountOnLocation::pay_reward` returns `Ok(())` after successfully calling `XcmSender::deliver` [6](#0-5) [7](#0-6) .
4. On AssetHub, the `DepositAsset { assets: AllCounted(1), beneficiary }` instruction in the delivered XCM fails to credit the beneficiary (no ED, invalid/uncreatable account), and the reward asset is trapped by the XCM executor instead of being credited (contrast with the passing `claim_rewards_works` test, which only exercises a valid, funded beneficiary and observes `pallet_assets::Event::Deposited` [8](#0-7) ).
5. Result: the relayer's `RelayerRewards` record is gone, `RewardPaid` was emitted, but no asset was actually delivered to any account the relayer controls - the reward is permanently unaccounted for and unrecoverable through the pallet's normal flow.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},

#[test]
fn claim_snowbridge_rewards_to_local_account_fails() {
	let assethub_location = BridgeHubWestend::sibling_location_of(AssetHubWestend::para_id());
	let assethub_sovereign = BridgeHubWestend::sovereign_account_id_of(assethub_location);

	let relayer_account = BridgeHubWestendSender::get();
	let reward_address = AssetHubWestendReceiver::get();

	BridgeHubWestend::fund_accounts(vec![
		(assethub_sovereign.clone(), INITIAL_FUND),
		(relayer_account.clone(), INITIAL_FUND),
	]);
	set_up_eth_and_dot_pool();

	BridgeHubWestend::execute_with(|| {
		type Runtime = <BridgeHubWestend as Chain>::Runtime;
		type RuntimeEvent = <BridgeHubWestend as Chain>::RuntimeEvent;
		type RuntimeOrigin = <BridgeHubWestend as Chain>::RuntimeOrigin;
		let reward_amount = ETHER_MIN_BALANCE * 2; // Reward should be more than Ether min balance

		type BridgeRelayers = <BridgeHubWestend as BridgeHubWestendPallet>::BridgeRelayers;
		BridgeRelayers::register_reward(
			&relayer_account.clone(),
			BridgeReward::Snowbridge,
			reward_amount,
		);

		// Check that the reward was registered.
		assert_expected_events!(
			BridgeHubWestend,
			vec![
				RuntimeEvent::BridgeRelayers(pallet_bridge_relayers::Event::RewardRegistered { relayer, reward_kind, reward_balance }) => {
					relayer: *relayer == relayer_account,
					reward_kind: *reward_kind == BridgeReward::Snowbridge,
					reward_balance: *reward_balance == reward_amount,
				},
			]
		);

		let reward_beneficiary = BridgeRewardBeneficiaries::LocalAccount(reward_address);
		let result = BridgeRelayers::claim_rewards_to(
			RuntimeOrigin::signed(relayer_account.clone()),
			BridgeReward::Snowbridge,
			reward_beneficiary.clone(),
		);
		assert_err!(result, FailedToPayReward::<Runtime, ()>);
	})
