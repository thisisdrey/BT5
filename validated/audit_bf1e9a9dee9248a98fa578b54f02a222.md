### Title
Unvalidated attacker-controlled block length causes out-of-bounds slice panic in reftable parser - (File: internal/git/reftable/reftable.go)

### Summary
This is an analog of the reported "read outside checked bounds" bug class (off-by-one/insufficient boundary check before consuming untrusted length data), found in Gitaly's custom reftable block parser used by the reftable/MVCC reference backend.

### Finding Description
`Table.parseRefBlock` reads a 24-bit block-length field directly from the reftable file bytes via `extractBlockLen` and uses it, mostly unchecked, to slice into the in-memory file buffer: [1](#0-0) 

The value `currentBS` originates entirely from file content (`t.extractBlockLen(src, blockStart+headerOffset)`), i.e. from the table file itself, not from a value Gitaly independently computed and trusts. The subsequent validation only conditionally clamps `fullBlockSize` when `t.blockSize != 0` *and* `currentBS < fullBlockSize` *and* `currentBS < (blockEnd-blockStart)`; it never validates `currentBS` before it is used at line 320:

```go
if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
```

If `currentBS` is corrupted/crafted so that `blockStart+currentBS-2` exceeds `len(src)`, this slice expression panics with "slice bounds out of range" in Go, which is functionally the same class of defect as the reported bug: consuming a boundary-adjacent/attacker-influenced length without confirming it stays within the valid data window (`bytecodeLength < jumpDst` vs `dst < bytecodeLength`). The nested `getVarInt` helper has the same weakness — it indexes `src[start]` before ever bounds-checking `start` against `blockEnd` or `len(src)`: [2](#0-1) 

This parser backs `Table.GetReferences`, which is exercised by the reftable/MVCC reference backend code paths in `internal/gitaly/storage/storagemgr/partition` (table resequencing, transaction manager reference handling) and by test helpers that mirror real backend behavior: [3](#0-2) 

### Impact Explanation
A corrupted or maliciously crafted `.ref` reftable file (e.g. arriving via inter-node replication of a reftable-backend repository, restoring a repository from an untrusted backup/bundle, or repository migration between reference backends) can trigger a Go runtime panic while Gitaly parses reference blocks. Since this code runs inside RPC-handling / transaction-manager goroutines, an unrecovered panic can crash or destabilize the Gitaly process/partition, resulting in a Denial of Service for the affected repository or the whole node depending on panic-recovery middleware coverage.

### Likelihood Explanation
Exploitability depends on Gitaly consuming a reftable file that it did not itself just write with a trusted `git` binary — e.g. during `ReplicateRepository` from another (compromised or buggy) Gitaly node, restoring backups, or importing repositories that already use the reftable backend. In routine operation, Gitaly-authored tables are well-formed, so likelihood in the default single-writer flow is low; likelihood rises for replication/import/restore flows where the reftable bytes are only partially or not validated before parsing.

### Recommendation
Add explicit bounds checks in `parseRefBlock` and `getVarInt` before any slicing/indexing operation: verify `blockStart+currentBS <= len(src)` (and `>= blockStart+headerOffset`) before doing `src[blockStart+currentBS-2:]`, and check `start < blockEnd` (not just `start > blockEnd` post-increment) as well as `start < uint(len(src))` before dereferencing `src[start]` in `getVarInt`. Return a descriptive parse error instead of allowing an out-of-range slice/index panic.

### Proof of Concept
Construct/patch a reftable `.ref` file where the 3-byte big-endian block-length field embedded at `blockStart+1..blockStart+4` (read by `extractBlockLen`) encodes a value large enough that `blockStart+currentBS-2` exceeds the file's total length, while `t.blockSize == 0` (so `fullBlockSize = currentBS` is accepted unconditionally, see the `if fullBlockSize == 0` branch). Feeding this file to `reftable.ParseTable(...).GetReferences()` — reachable via the reftable/MVCC backend code paths noted above — causes `binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), ...)` to panic with a slice-bounds-out-of-range error.

Note: I could not fully confirm from the indexed code every production RPC call site that directly invokes `Table.GetReferences()` on externally-supplied files (only `internal/gitaly/storage/storagemgr/partition/testhelper_test.go` and the resequencing path in `internal/gitaly/storage/storagemgr/partition/reftable.go` were located). Full confirmation of all reachable RPC-triggered ingestion paths (e.g., replication/backup-restore invoking this exact parser) would require deeper investigation with full repository access — the index may not include all relevant call sites due to size limits. Starting a Devin session with full codebase access would allow tracing every caller of `reftable.ParseTable`/`GetReferences` to fully confirm the reachable attack surface.

```go
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}
```

```go
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
```
