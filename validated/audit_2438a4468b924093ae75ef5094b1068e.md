### Title
Missing Zero-Address Validation in `set_beneficiary_for_operator` Permanently Blocks `distribute_internal` and `switch_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

---

### Summary

`staking_contract::set_beneficiary_for_operator` accepts any `new_beneficiary: address` without validating it is not `@0x0` (`@vm_reserved`). When the stored beneficiary is `@0x0`, every subsequent call to `distribute_internal` — which is invoked by both the public `distribute` entry and by `switch_operator` — aborts inside `aptos_account::deposit_coins` because `create_account(@0x0)` is unconditionally rejected for the VM-reserved address. This freezes all unlocked stake withdrawals for the staker and prevents operator rotation until the operator voluntarily resets their beneficiary.

---

### Finding Description

`set_beneficiary_for_operator` is a `public entry fun` callable by any operator signer:

```move
public entry fun set_beneficiary_for_operator(
    operator: &signer, new_beneficiary: address
) acquires BeneficiaryForOperator {
    ...
    borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
        new_beneficiary;   // ← no zero-address guard
    ...
}
``` [1](#0-0) 

The same pattern exists verbatim in `delegation_pool::set_beneficiary_for_operator`: [2](#0-1) 

`distribute_internal` later resolves the commission recipient:

```move
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);   // returns @0x0
};
aptos_account::deposit_coins(
    recipient, coin::extract(&mut coins, amount_to_distribute)
);
``` [3](#0-2) 

`aptos_account::deposit_coins` tries to create the account if it does not exist:

```move
if (!account::exists_at(to)) {
    create_account(to);   // aborts for @vm_reserved == @0x0
};
``` [4](#0-3) 

`@vm_reserved` is `0x0` (confirmed in named-address configs) and `aptos_account::create_account` unconditionally aborts for it: [5](#0-4) 

`system_addresses::is_reserved_address` confirms `@0x0` is reserved: [6](#0-5) 

`switch_operator` calls `distribute_internal` as its first step, so it is also blocked: [7](#0-6) 

---

### Impact Explanation

Once an operator stores `@0x0` as their beneficiary:

- `distribute(staker, operator)` — callable by anyone — aborts every time, preventing the staker from withdrawing any unlocked/inactive stake.
- `switch_operator` aborts because it calls `distribute_internal` before reassigning the pool, so the staker cannot rotate to a new operator.
- In the vesting module, `terminate_vesting_contract` calls `distribute` internally, so vesting termination is also blocked.

The staker's staking balance is effectively frozen until the operator calls `set_beneficiary_for_operator` again with a valid address. If the operator is unresponsive or malicious, the freeze is durable. This matches the "permanent freezing of staking balances" impact class in the bounty scope.

---

### Likelihood Explanation

The function is a `public entry fun` with no input validation beyond a feature-flag check. An operator can set `@0x0` accidentally (e.g., passing a zero-initialized address from an SDK) or deliberately. The `vesting::set_beneficiary_for_operator` wrapper delegates directly to this function with no additional guard: [8](#0-7) 

---

### Recommendation

Add a reserved-address guard in both `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator`:

```move
assert!(
    !system_addresses::is_reserved_address(new_beneficiary),
    error::invalid_argument(EINVALID_BENEFICIARY_ADDRESS)
);
assert!(
    account::exists_at(new_beneficiary),
    error::not_found(EACCOUNT_NOT_FOUND)
);
```

This mirrors the existing guard applied to `withdrawal_address` in `vesting::create_vesting_contract`: [9](#0-8) 

---

### Proof of Concept

```
1. Operator calls:
   staking_contract::set_beneficiary_for_operator(operator_signer, @0x0)
   → Succeeds. BeneficiaryForOperator { beneficiary_for_operator: @0x0 } stored.

2. Stake unlocks (inactive > 0).

3. Anyone calls:
   staking_contract::distribute(staker_addr, operator_addr)
   → distribute_internal is entered.
   → distribution_pool has operator as a shareholder.
   → recipient = beneficiary_for_operator(operator_addr) = @0x0
   → aptos_account::deposit_coins(@0x0, commission_coins)
     → account::exists_at(@0x0) == false
     → aptos_account::create_account(@0x0)
       → account::create_account(@0x0) ABORTS (auth_key == @vm_reserved)
   → distribute ABORTS. Staker's unlocked coins remain trapped.

4. Staker calls:
   staking_contract::switch_operator(staker_signer, operator_addr, new_op, pct)
   → distribute_internal called first → same abort.
   → Operator rotation is impossible.

5. Funds remain frozen until operator resets beneficiary to a valid address.
```

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
