### Title
Batch-wide check/lock split in `AccountLocks::try_lock_transaction_batch` allows two transactions in the same batch to both acquire a conflicting write lock on the same account - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` first runs `can_lock_accounts` for *every* transaction in the batch against the pre-batch lock state, and only afterwards applies `lock_accounts` for all transactions that passed. Because the check phase never observes the locks that other transactions in the *same* batch are about to take, two (or more) transactions in one batch that write to the same account can both pass the check and both end up incrementing `write_locks` for that key, yielding two simultaneously "locked" writers for one account.

### Finding Description
`AccountLocks::try_lock_transaction_batch` (accounts-db/src/account_locks.rs:22-40) is implemented as two separate passes over the batch:

```rust
validated_batch_keys.iter_mut().for_each(|validated_keys| {
    if let Ok(keys) = validated_keys.as_ref()
        && let Err(e) = self.can_lock_accounts(keys.clone())
    { *validated_keys = Err(e); }
});

validated_batch_keys
    .into_iter()
    .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
    .collect()
``` [1](#0-0) 

Pass 1 calls `can_lock_accounts` (read-only, `&self`) for every transaction sequentially, but this function only checks `self.write_locks` / `self.readonly_locks` as they stood *before the batch started* — it never mutates state, so a conflict between transaction *i* and transaction *j* within the same batch is invisible to this pass. [2](#0-1) 

Only in pass 2 does `lock_accounts` actually mutate `write_locks`/`readonly_locks` via `lock_write`/`lock_readonly`, which unconditionally increment a counter with no re-check of conflicts: [3](#0-2) [4](#0-3) 

Because the "canLock" check (pass 1) and the actual state mutation (pass 2) are split across the whole batch instead of being interleaved per-transaction, if transaction A and transaction B in the same batch both write to pubkey `X` (each individually valid — no duplicate keys within a single transaction, both under `MAX_TX_ACCOUNT_LOCKS`), both will pass `can_lock_accounts` in pass 1 (since `X` is not yet locked by anything), and then both `lock_write(X)` calls in pass 2 will succeed, leaving `write_locks[X] = 2` with two transactions marked as `Ok(())` for locking purposes. `validate_account_locks` only rejects duplicate keys *within a single* transaction's `AccountKeys`, and does nothing to catch cross-transaction conflicts within a batch. [5](#0-4) 

This directly violates the described invariant that account locks prevent conflicting concurrent execution, since both transactions now hold a "granted" write lock on the same account simultaneously.

### Impact Explanation
Two transactions that write the same account can be scheduled/executed concurrently by whichever component trusts the `Ok(())` results from `try_lock_transaction_batch` (e.g. the accounts/bank locking layer that gates concurrent execution). This can cause a state race on the account leading to non-deterministic execution results and a mismatch between the executed state and the recorded/replayed entry — a correctness/consensus-safety class bug (invalid recorded block / state divergence), matching the "verification bypass / invalid recorded block" bounty category rather than a DoS.

### Likelihood Explanation
This requires no privileged access — any unstaked client can submit a transaction batch (e.g., in a single QUIC/TPU packet or vote-processing batch) containing two or more independently-valid transactions that write to the same pubkey. No duplicate keys within a single transaction are needed, and no exotic account-count boundary condition is required — a minimal repro is two transactions in one batch, each writing the same single account. This is deterministic and trivially repeatable, not merely a rare boundary condition.

### Recommendation
Interleave the check-then-lock step per transaction instead of doing all checks first and all locks second: for each transaction in the batch, call `can_lock_accounts` and, if it succeeds, immediately call `lock_accounts` before moving to the next transaction. This way each subsequent transaction's `can_lock_accounts` check observes the locks taken by earlier transactions in the same batch. Equivalently, fold the check-and-lock into a single atomic "try_lock" operation per transaction rather than pre-computing all `Ok`/`Err` results before mutating state.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (add to tests module)
#[test]
fn test_try_lock_transaction_batch_same_batch_conflict() {
    let key = Pubkey::new_unique();
    let mut locks = AccountLocks::default();

    // Two transactions in the SAME batch both write `key`.
    let tx1_keys = vec![(&key, true)];
    let tx2_keys = vec![(&key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // BUG: both succeed, yet they conflict on a writable key.
    let both_ok = results.iter().all(|r| r.is_ok());
    assert!(
        !both_ok,
        "two transactions writing the same account in one batch must not both succeed"
    );

    // Additional invariant: write lock count for `key` should never exceed 1
    // if only one writer is allowed at a time.
    assert!(!locks.is_locked_write(&key) || results.iter().filter(|r| r.is_ok()).count() <= 1);
}
```
Expected current (buggy) behavior: both results are `Ok(())` and `write_locks[key] == 2`, demonstrating that two conflicting writers were simultaneously granted locks, violating the account-lock invariant.

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }

/// Validate account locks before locking.
pub fn validate_account_locks(
    account_keys: AccountKeys,
    tx_account_lock_limit: usize,
) -> TransactionResult<()> {
    if account_keys.len() > tx_account_lock_limit {
        Err(TransactionError::TooManyAccountLocks)
    } else if has_duplicates(account_keys) {
        Err(TransactionError::AccountLoadedTwice)
    } else {
        Ok(())
    }
}
