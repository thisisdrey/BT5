## Title
`process_delivery_receipt` pays relayer rewards without checking the Ethereum-side `success` flag, rewarding failed message deliveries - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The Snowbridge V2 outbound-queue pallet decodes a `DeliveryReceipt` from an Ethereum `InboundMessageDispatched` event log, which carries an explicit `success: bool` field indicating whether the Gateway actually executed the relayed message successfully on Ethereum. `process_delivery_receipt` never reads or branches on this field before paying the relayer reward, so a relayer can submit a real, verifiable receipt for a message that reverted on Ethereum and still collect the full fee.

## Finding Description
`DeliveryReceipt` decodes the Solidity event `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` and stores the `success` boolean field: [1](#0-0) 

`submit_delivery_receipt` verifies the log/proof with `T::Verifier::verify`, decodes the receipt, and immediately calls `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` checks only `T::GatewayAddress::get() == receipt.gateway`, looks up the `PendingOrder` by `nonce`, and pays the reward whenever `order.fee > 0` — it never inspects `receipt.success`: [3](#0-2) 

A repository-wide search confirms there is no reference to `success` anywhere within `bridges/snowbridge/pallets/outbound-queue-v2/**` (neither `lib.rs` nor `test.rs`), verifying the field is decoded but genuinely unused as a gating condition for settlement. The order is created with the fee amount at message-processing time in `do_process_message`: [4](#0-3) 

This breaks the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here the receipt is decoded and dispatch is acknowledged, but the actual execution outcome (`success`) is discarded before settlement.

## Impact Explanation
This is a duplicate/unbacked payout: relayers are rewarded identically whether the message they relayed executed successfully or reverted on the Ethereum Gateway. Delivery of a reverted message still consumes gas/fee resources but produces no useful outbound effect for the protocol, so this allows relayers to be paid via `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` for messages that never had their intended effect — a direct chain-funds impact matching the "theft or unbacked mint" / "duplicate settlement or payout" impact category in the Polkadot SDK impact gate.

## Likelihood Explanation
The path is reachable by any unprivileged signed relayer who can produce a legitimate Ethereum receipt proof for a message that reverted (e.g., due to insufficient gas supplied on the Ethereum side, or a downstream command failure) — no malicious peer, validator, governance, or leaked key is required. The relayer only needs to submit the transaction receipt log they naturally receive after their own relay attempt, so the reverted-but-real-receipt scenario is a normal operational occurrence rather than a contrived one.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: on `false`, either skip/reduce the reward (or apply a distinct penalty/no-op path) instead of unconditionally calling `T::RewardPayment::register_reward` for the full `order.fee`, and emit a distinguishing event (e.g., `MessageDeliveryFailed`) so downstream systems and the `PendingOrders` cleanup reflect the true outcome.

## Proof of Concept
1. A message with nonce `N` and fee `F` is queued via `do_process_message`, creating `PendingOrders[N] = { nonce: N, fee: F, ... }`. [5](#0-4) 
2. The relayer relays the message to Ethereum; the Gateway attempts execution but the message's command reverts, so the emitted `InboundMessageDispatched` event has `success = false` (still a valid, provable event log with correct `nonce`/`gateway`).
3. The relayer submits this receipt via `submit_delivery_receipt(origin, event)`, which passes verification (the proof and log are genuine) and decodes into a `DeliveryReceipt { success: false, .. }`. [6](#0-5) 
4. `process_delivery_receipt` ignores `receipt.success`, finds `order.fee > 0`, and calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, then removes the order and emits `MessageDelivered { nonce }` — identical to the successful-delivery path exercised in `submit_delivery_receipt_succeeds_after_unhalt`, which only asserts on `Halted`/no-halted state, never on `success`. [7](#0-6) 
5. Result: the relayer is fully rewarded for a message delivery that failed on Ethereum, with no on-chain distinction between success and failure outcomes.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
