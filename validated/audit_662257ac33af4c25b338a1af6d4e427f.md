### Title
Stale `PostponedReceipt`/`PendingDataCount` state survives `DeleteAccount`, enabling privilege injection into a recreated account - (core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` clears `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData`, but never iterates or removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` rows keyed by the deleted account's `receiver_id`. This confirmed gap means a `DeleteAccount` on an account with an outstanding postponed receipt leaves that receipt's queued actions in trie state to be executed later against whatever account subsequently occupies that `account_id`.

### Finding Description
`remove_account` is the sole cleanup routine invoked on account deletion: [1](#0-0) 

It removes account, contract code, access/gas keys, and contract data, but there is no corresponding iteration over `get_raw_prefix_for_postponed_receipts`/`PostponedReceiptId`/`PendingDataCount` prefixes for the account. Postponed receipts (created when an `ActionReceipt` references `input_data_ids` that have not all arrived yet, e.g. via `promise_and` joining two promises) are keyed purely by `receiver_id` + `receipt_id`/`data_id` strings, with no binding to an account "incarnation" or generation counter.

Because `AccountId` recreation is legal in NEAR (a parent such as `attacker.near` can always recreate `child.attacker.near` via `CreateAccount`), and because the runtime's authorization check for actions embedded in a receipt (`check_actor_permissions`, referenced from `runtime/runtime/src/actions.rs`) validates the actor purely by string equality of `actor_id`/`account_id` (predecessor/receiver identifiers fixed when the receipt was created) rather than by any notion of account identity/version, a postponed receipt created under an old incarnation of an account will still pass permission checks when later executed against a freshly recreated account with the same name.

Exploit flow:
1. Attacker deploys a contract on `child.attacker.near` and calls a method that issues two promises joined via `promise_and`, with one of them carrying an `AddKey(FullAccess)` action targeting `child.attacker.near` itself (self-authorized, since `actor_id == account_id`). Only one of the two required `DataReceipt`s arrives, so the runtime postpones the receipt and persists `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` rows for `receiver_id = child.attacker.near`.
2. Attacker submits `DeleteAccount` on `child.attacker.near` — `actor_id == account_id` so `check_actor_permissions` allows it (self-deletion), and `remove_account` runs, clearing account/keys/code/data but leaving the postponed-receipt rows untouched.
3. `attacker.near` recreates `child.attacker.near` (fresh `CreateAccount` + `AddKey` for a new owner).
4. The delayed second `DataReceipt` arrives; `PendingDataCount` reaches zero, and the runtime pulls the stale `PostponedReceipt` and executes its `AddKey(FullAccess)` action against the newly recreated account — since the check is purely name-based, it succeeds and grants the attacker's key full access on the "fresh" account without the new owner's knowledge or consent.

This bypasses all normal authorization/nonce/access-key checks because those checks are evaluated against literal account/actor ID strings, not against any per-incarnation identity that would distinguish the deleted account from its successor.

### Impact Explanation
This is an authorization-escalation / backdoor access-key-injection primitive: an attacker can plant privileged, self-authorizing actions that execute later against whatever occupies the account name after deletion/recreation, violating the invariant that a promise should never carry privileges beyond what its creator held on the current incarnation of the account. This matches NEAR's "authorization escalation across accounts or promises" bounty category, potentially enabling theft of any funds/state later deposited into or controlled by the recreated account.

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: own a parent account, deploy a contract, trigger `promise_and`-based postponement, then self-delete and recreate the child account — no privileged network role is needed. It's a normal unprivileged user action sequence and is fully repeatable. The primary uncertainty (not fully verified in this pass due to tool budget) is whether `action_delete_account` in `runtime/runtime/src/actions.rs` includes any independent guard rejecting deletion while postponed/pending receipts exist for that account; no such guard was found in the reviewed cleanup path (`remove_account`), and none is referenced from the areas inspected.

### Recommendation
Extend `remove_account` (core/store/src/utils/mod.rs) to also iterate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries keyed by the account's `receiver_id` before/при deletion, refunding or dropping any associated deposits/gas appropriately. Alternatively/additionally, reject `DeleteAccount` while the account has any outstanding postponed receipts, or bind receipts to an account generation/incarnation counter so stale postponed actions cannot execute against a differently-owned recreated account.

### Proof of Concept
Runtime/test-loop integration test:
1. Deploy a contract on `child.attacker.near` (created by `attacker.near`) that, in one function call, issues two cross-contract promises joined with `promise_and`, and schedules an `AddKey(FullAccess, attacker_pubkey)` action on `child.attacker.near` itself to run after the join resolves.
2. Apply only one of the two resulting `DataReceipt`s so the joined receipt is postponed; assert `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` trie entries exist for `child.attacker.near`.
3. Submit and apply a `DeleteAccount` transaction from `child.attacker.near` to `attacker.near`.
4. From `attacker.near`, submit `CreateAccount` + `AddKey(new_owner_pubkey)` recreating `child.attacker.near`.
5. Deliver the second, previously-missing `DataReceipt`.
6. Assert that post-apply state for `child.attacker.near` contains the attacker's `FullAccess` key that the new owner never authorized, proving the escalation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
