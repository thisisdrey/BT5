### Title
Deleting an account with an outstanding postponed multi-dependency `ActionReceipt` does not purge `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` trie entries, allowing a later `DataReceipt` to execute the stale receipt against a re-created account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) only clears the `Account`, `ContractCode`, `AccessKey`/gas-key nonce, and `ContractData` trie entries for an account. It does not clear `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` entries, which are the trie keys used to track receipts awaiting multiple `DataReceipt`s (e.g. from `Promise.and()`). If account A is deleted while it has a partially-satisfied postponed receipt, and the account ID is later re-created, delivery of the missing `DataReceipt` will resurrect and execute the stale queued `ActionReceipt` against the new account.

### Finding Description
`action_delete_account` in `runtime/runtime/src/actions.rs:314-390` validates only account storage-usage limits and gas-key balance-to-burn caps before calling `remove_account(state_update, account_id)` at line 371. There is no check for outstanding `PostponedReceipt` / `PendingDataCount` state for the account being deleted.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) explicitly enumerates and removes only:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- Access keys / gas-key nonces (via prefix iteration)
- `TrieKey::ContractData` (via prefix iteration)

It never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId`, all of which are legitimate trie-key variants used by the receipt-postponement machinery referenced throughout `runtime/runtime/src/lib.rs` (13 matches for these symbols) and `core/primitives/src/trie_key.rs`.

Exploit flow:
1. Attacker funds account A and deploys a contract that issues a multi-dependency promise (`Promise.and()`), producing an `ActionReceipt` with two `input_data_ids` stored under `PostponedReceipt{receiver_id:A}`/`PostponedReceiptId`, with `PendingDataCount(A) = 2`.
2. One `DataReceipt` arrives, decrementing `PendingDataCount` to 1 (the postponed receipt itself remains in the trie).
3. Before the second `DataReceipt` arrives, a `DeleteAccountAction{beneficiary}` targeting A is processed. `action_delete_account` succeeds and calls `remove_account`, which deletes the `Account`/keys/code/data but leaves `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` for A untouched.
4. Any third party creates a brand-new account A (same account ID) via `CreateAccountAction`.
5. The second, already-in-flight `DataReceipt` (from step 1's peer promise) is delivered. It decrements the leftover `PendingDataCount(A)` to 0, causing the runtime to load and execute the *stale* `ActionReceipt` from `PostponedReceipt{receiver_id:A}` against the newly created account.
6. If the stale receipt's actions include `AddKeyAction`, `DeleteKeyAction`, or `DeployContractAction` (predecessor==receiver==A, i.e., a self-call), these execute against the new owner's account without their consent, silently rewriting keys/code.

No existing signature, nonce, or access-key check catches this because the receipt is pulled from a legitimate previously-queued trie entry and processed through the normal postponed-receipt resumption path; the runtime has no notion that account "A" changed ownership between postponement and resumption.

### Impact Explanation
This is an authorization-escalation bug: an attacker (or anyone racing to claim a freed account ID) can have arbitrary residual promise actions execute on their newly created account, potentially adding attacker-controlled keys or deploying attacker-controlled code onto an account the victim believes they just created cleanly. This maps to NEAR's "authorization escalation across accounts" bounty category, and could lead to fund theft/account takeover if the resumed receipt includes `AddKeyAction` with a full-access key, or contract-logic hijack via `DeployContractAction`.

### Likelihood Explanation
Preconditions are attacker/ordinary-user-achievable: deploy a contract that issues `Promise.and()`, control the timing/order of its own `DataReceipt`s relative to a `DeleteAccountAction`, and either be the same actor deleting-then-recreating the account or race to claim the freed account ID. Cost is limited to normal gas/storage fees; no privileged access is required. The scenario is deterministic and repeatable since receipt/data delivery ordering across shards/blocks in NEAR is a normal, attacker-influenceable execution path (self-calls, batched actions), not a rare race.

### Recommendation
`remove_account` should also purge `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, and `TrieKey::PostponedReceipt` entries for the account being deleted (or `action_delete_account`/`process_action_receipt` should reject deletion while any such entries exist, similar to the existing `DeleteAccountStaking` check). Any yet-undelivered `DataReceipt`s referencing the removed postponed receipt should be treated as no-ops (or trigger receipt-failure/refund handling) rather than resurrecting the postponed `ActionReceipt`.

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or a runtime integration test near `runtime/runtime/src/tests/apply.rs`):
1. Build a `TrieUpdate` for account `"alice"` and manually insert:
   - `TrieKey::PostponedReceipt{receiver_id: alice, data_id: id1}` (or however keyed) containing a stub `ActionReceipt` with actions `[AddKeyAction{full_access}]`.
   - `TrieKey::PendingDataCount{receiver_id: alice, receipt_id}` = 1.
   - `TrieKey::PostponedReceiptId{...}` mapping.
2. Call `remove_account(&mut state_update, &"alice".parse().unwrap())`.
3. Assert (expected to fail today): iterating the trie under `alice`'s postponed-receipt prefixes returns no entries — i.e., `PendingDataCount`, `PostponedReceiptId`, and `PostponedReceipt` keys are gone.
4. As a stronger runtime-level PoC (test-loop / `runtime/runtime/src/tests/apply.rs` style, similar to `test_instant_delete_account` in `test-loop-tests/src/tests/create_delete_account.rs`): deploy a contract on account X that issues `Promise.and()` of two cross-contract calls, deliver one `DataReceipt`, then submit `DeleteAccountAction{beneficiary}` for X, then recreate X via `CreateAccountAction`, then deliver the second `DataReceipt`. Assert the postponed `AddKeyAction`/`DeployContractAction` from the stale receipt is (incorrectly) applied to the new X account, e.g. by querying `get_access_key` for the injected public key on the new account and observing it exists despite the new account never having authorized it.
