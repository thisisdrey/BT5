### Title
Replay-window Check/Update race in `ConnectionState.Decrypt` allows double-accept of a duplicated ciphertext - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` performs the replay-window `Check` and `Update` as two separate locked sections with `dKey.DecryptDanger` executed unlocked in between, rather than as one atomic check-and-set operation. An attacker who captures one legitimate ciphertext+counter off the wire and resends it concurrently on two reader goroutines (with `routines > 1`, each UDP queue served by its own `listenOut`) can cause both goroutines to pass `cs.window.Check` before either calls `cs.window.Update`, resulting in the same counter being decrypted and accepted twice.

### Finding Description

The window state is protected by `cs.decryptLock`, but the lock is released after `Check` and re-acquired only for `Update`, with the (unlocked) AEAD decryption in between. Because `window.Check` only tests whether the counter is inside the window and not yet marked seen — it does not mark it seen itself — two goroutines that both call `Check` for the same `messageCounter` before either has reached `Update` will both observe `result == true` and both proceed to `DecryptDanger`. Since the ciphertext is identical (attacker replayed a valid capture, not a new counter), both `DecryptDanger` calls succeed, and both then call `Update`, both incrementing/marking the window (the second `Update` call may return `false`, but by that time the payload from both decrypt calls has already been delivered to `out`/passed to the caller). The net effect is that the replayed ciphertext is decrypted and accepted twice, once per goroutine, before the anti-replay window has a chance to reject the duplicate.

This is directly reachable from unprivileged, unauthenticated attacker input: an attacker with no key material can simply capture one legitimate on-wire UDP packet (ciphertext + `header.MessageCounter`) and resend it as two near-simultaneous spoofed UDP datagrams. With `tun.routines > 1`, `listenOut` runs on multiple reader goroutines per queue index `i`, so the two duplicate packets can land on two different goroutines and call `ConnectionState.Decrypt` concurrently on the same `ConnectionState`, hitting exactly this TOCTOU window between `Check` and `Update`.

### Impact Explanation
This breaks the stated anti-replay invariant: a single captured/valid counter+ciphertext is accepted (decrypted and delivered) more than once instead of being dropped as a duplicate. While this does not forge new plaintext or break key secrecy on its own, it allows a captured legitimate packet to be re-processed/re-delivered into the session twice, which is a real replay-protection bypass on the data plane and matches the "replay-window bypass" impact category described in the prompt (tunnel traffic replayed into an established session).

### Likelihood Explanation
The attack only requires: (1) capturing a single valid ciphertext/counter pair off the wire (a passive/unprivileged capability, no cert/keys/CA needed), and (2) the ability to send two spoofed UDP datagrams that arrive close enough in time to race on `routines > 1` multi-queue listeners. Both preconditions are realistic for an on-path or off-path attacker who can observe and duplicate UDP traffic to the target's listen port; no cryptographic material or privileged access is required. The race window is narrow (bounded by one AEAD decrypt operation) but reproducible with a targeted concurrency test that removes wall-clock timing dependence.

### Recommendation
Make the replay-window check-and-mark atomic: hold `cs.decryptLock` across a single "reserve" operation that both validates the counter is in-window/unseen and immediately marks it seen, failing fast if another goroutine already reserved it, before calling `DecryptDanger`. Equivalently, combine `Check`+`Update` into one locked critical section (or one `Bits.CheckAndUpdate` method) so no other goroutine can observe the counter as unclaimed between validation and decryption.

### Proof of Concept
Unit test in `connection_state_test.go`:
1. Build a `ConnectionState` with real `eKey`/`dKey` ciphers (as in existing tests) and encrypt one plaintext to obtain `packet` and `messageCounter`.
2. Spawn two goroutines that both call `cs.Decrypt(logger, messageCounter, out, packet, nb)` concurrently for the same captured `packet`/`messageCounter` (simulating the duplicated spoofed UDP packet landing on two reader goroutines).
3. Assert that exactly one call returns a successful decrypted result and the other returns `ErrAlreadySeen` — i.e., the dupe-detection counter (or equivalent) increments by exactly one and the payload is delivered only once.
4. Expected current behavior (bug): under the race, both calls pass `window.Check` and both `DecryptDanger` succeed, so both return a non-error decrypted payload — violating the "exactly one succeeds" invariant.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
