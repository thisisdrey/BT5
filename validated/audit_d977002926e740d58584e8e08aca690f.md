### Title
Same-key ECDSA signature malleability lets a single private key double-count its weight in `ValidateMultiSign`, bypassing the multi-signer threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The rsync CVE-2018-5764 bug class is "a repeated use of a control parameter is not rejected, which lets an attacker bypass an intended sanitization/uniqueness guarantee." The analogous java-tron path is the `ValidateMultiSign` TVM precompile, whose per-signature de-duplication is keyed on the *raw signature bytes* rather than on the *recovered signer address*, so a single key can be counted twice (or more) toward a multisig `threshold` simply by supplying two different, but both cryptographically valid, signatures over the same hash.

### Finding Description
`TransactionCapsule.checkWeight` — used for normal transaction/permission signature checking — correctly de-duplicates by *recovered address*, rejecting an address that has "signed twice": [1](#0-0) 

However, the TVM precompile `ValidateMultiSign.execute` (reachable from any smart-contract call, i.e. from an unprivileged contract deployer/caller) implements its own, weaker de-duplication: [2](#0-1) 

In this loop, for each supplied signature `sign`:
1. `recoveredAddr` is computed from `sign` and the hash.
2. `sign` is rebound to `merge(recoveredAddr, sign)` (address‖signature bytes).
3. If `executedSignList` already contains `recoveredAddr` (i.e., this address already contributed weight from an earlier signature), the code only `continue`s (skips) if the exact same `sign` bytes (address+signature) were already seen. If the *bytes differ* (a different, but valid, signature by the same key over the same hash), it does **not** `continue` — it just does a CPU-timeout guard (`MUtil.checkCPUTime()`), then proceeds to add `weight` for that address to `totalWeight` **again**, and appends both the new `sign` and the address once more into `executedSignList`.

Because ECDSA signatures are malleable (for a given `(r, s)` there is always an equivalent valid signature `(r, n-s)` with the complementary recovery id, and a key can also sign the same hash multiple times with different nonces `k` to produce entirely different `(r, s)` pairs, both of which recover to the same address), an attacker holding a single private key that is one of the `keys` in a `Permission` can produce `N` (up to `MAX_SIZE = 5`) distinct valid signatures over the same hash and have each one credited with that key's full `weight`, inflating `totalWeight` beyond what a single key should be able to contribute. This defeats the entire purpose of `Permission.threshold` and multi-key co-signing, which is designed to require *distinct* signers (see `checkWeight`'s intentional one-weight-per-address rule, and `AccountPermissionUpdateActuator.checkPermission`'s requirement that `weightSum` — summed over *distinct* addresses — must reach `threshold`): [3](#0-2) 

The existing unit test `testDifferentCase` in `ValidateMultiSignContractTest` even exercises exactly this "repetitive" scenario, but only with a literal duplicate signature (same bytes), which is correctly skipped by the `if (matrixContains(executedSignList, sign)) continue;` branch — it does not test the malleable/re-signed case, so the double-counting via distinct signatures from the same key is not caught by existing tests: [4](#0-3) 

### Impact Explanation
Any active `Permission` that is meant to require signatures from multiple distinct keys (e.g., threshold 2 out of keys A and B) can be satisfied by key A alone, as long as an on-chain smart contract calls the `ValidateMultiSign` precompile to gate a sensitive action (e.g., release of funds held/controlled by contract logic, execution of a privileged operation gated by `validateMultiSign(...)`). This is a concrete authorization bypass: it allows an unauthorized single-key holder to satisfy a co-signing/multisig requirement that TRON contracts commonly rely on for custody or governance, i.e., unauthorized account operation / theft of funds guarded by multisig logic in a smart contract.

### Likelihood Explanation
The precompile is reachable by any contract deployer or caller — no special privilege is needed, only a deployed contract (or an existing multisig-guarded contract) that calls `validateMultiSign`. Producing a second valid ECDSA signature for the same message and key is trivial for the key holder (simply re-sign, or apply the well-known `s -> n-s` malleability transform), requiring no cryptographic breakthrough. The only friction is the `MUtil.checkCPUTime()` call, which — post the `VERSION_4_7_1` fork — throws `OutOfTimeException` on this path; this needs to be confirmed against the specific active fork parameters, but the un-forked/pre-fork behavior (and any network where that fork is not yet active) is exploitable, and even with the fork active, the fundamentally flawed same-address dedup logic (dedup by raw bytes vs. by address) remains a design defect independent of the CPU-time guard.

### Recommendation
De-duplicate `ValidateMultiSign` signatures by **recovered address only** (mirroring `TransactionCapsule.checkWeight`), not by the concatenation of address+raw-signature bytes. Once an address has contributed its weight, any further valid signature that recovers to the same address must be skipped entirely (not merely CPU-time-checked and then re-counted). Concretely, change the branch:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    continue; // always skip repeat signer, regardless of exact signature bytes
}
```
and drop the `executedSignList.add(sign)` (raw bytes) bookkeeping in favor of tracking recovered addresses only.

### Proof of Concept
1. Deploy an account with an `Active` `Permission` with `threshold = 2` and two keys, `keyA` (weight 1) and `keyB` (weight 1) — as in `ValidateMultiSignContractTest.testDifferentCase`.
2. From a smart contract, compute `hash = sha256(address ‖ permissionId ‖ data)` as done in `ValidateMultiSign.execute`.
3. Using only `keyA`'s private key, produce two different valid ECDSA signatures over `hash`:
   - `sig1 = keyA.sign(hash)` 
   - `sig2` = the malleable counterpart of `sig1` (`s' = n - s`, flipped recovery id) — both recover to `keyA`'s address but have different raw bytes.
4. Call `validateMultiSign(address, permissionId, data, [sig1, sig2])`.
5. In `ValidateMultiSign.execute`, the first signature adds `weight=1` for `keyA`. The second signature recovers to the same `keyA` address (already in `executedSignList`), but since its raw bytes differ from `sig1`, the `continue` is skipped; the code proceeds to add `weight=1` again, so `totalWeight = 2 >= threshold(2)`, and the call returns `true` — even though only `keyA` ever signed, `keyB` never participated.
