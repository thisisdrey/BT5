### Title
Stale `accountIndexOf` fallback lets a depositor claim reward tokens equal to their full deposit balance when a token's index is still at `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary

The kernel UAF pattern — an object accessed after its last valid reference was dropped — maps to `RewardsDistributor._calculateTokenDelta()`: an account's supply index that was never initialized (the "dropped reference") is dereferenced as `0` instead of being pinned to `INITIAL_INDEX`, producing a `deltaIndex` of `1e18` and crediting the account `balance * 1` reward tokens. [1](#0-0) 

### Finding Description

`_calculateTokenDelta()` reads `accountIndexOf[token_][account_]`. The fallback that corrects an uninitialized account index is gated on `_tokenIndex > INITIAL_INDEX`:

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a deposit/debt token is added to the distributor, `_updateTokenSpeed()` initializes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` [2](#0-1) . At that moment every existing holder still has `accountIndexOf == 0`.

If `_updateTokensAccruedOf()` runs while `_tokenState.index == INITIAL_INDEX` — i.e. in the same block/timestamp as the speed update, before `_calculateTokenIndex()` advances the index (`_deltaTimestamps == 0` returns `(0,0)`) — then `_accountIndex` stays `0`, `_deltaIndex = 1e18 - 0 = 1e18`, and `_tokensDelta = balanceOf(account_).wadMul(1e18) = balanceOf(account_)`. The account is credited one reward token per wei of deposit-token balance, for zero elapsed time.

`claimRewards(accounts_, tokens_)` is permissionless and calls `_updateTokensAccruedOf` for any account, then pays out `tokensAccruedOf` via `_transferRewardIfEnoughTokens` [3](#0-2) . No modifier (onlyIfTokenExists, onlyIfDistributorExists, reentrancy guard) prevents this: `claimRewards` does not validate `tokens_` at all — it only requires `tokenStates[_token].index > 0`, which is exactly true right after `_updateTokenSpeed` initializes the token.

### Impact Explanation

An attacker holding (or flash-loaning into) a deposit-token balance calls `claimRewards(attacker, [newlyAddedToken])` in the same block that governance executes `updateTokenSpeed(s)`. They receive reward tokens equal to their deposit balance, draining `rewardToken` held by the distributor up to the distributor's full balance (`_transferRewardIfEnoughTokens` caps at `balanceOf(this)`). This is direct theft of unclaimed yield belonging to all other depositors, financed by a same-transaction flash-loan deposit.

### Likelihood Explanation

The window is narrow: `tokenStates[token_].index` must equal `INITIAL_INDEX` exactly, which only holds in the block where the token is first given a nonzero speed (or re-added after `tokenStates` was set but index never grew — a second window exists whenever `speed` is later set from 0 while `_supplyState.index` is still `INITIAL_INDEX`). However:

- `updateTokenSpeed`/`updateTokenSpeeds` transactions are visible in the mempool; the attacker back-runs them in the same block (timestamp delta 0 → index does not advance).
- The attacker needs no privileged role — only a deposit-token balance at claim time, obtainable via flash loan → `DepositToken.deposit()` → `claimRewards` → `withdraw`.
- Reward claims are otherwise trustless and ungated, so nothing reverts.

Governance performing a routine speed update is itself the trigger, but the exploit requires no malicious or mistaken governor — just a normal parameter update.

### Recommendation

Change the fallback in `_calculateTokenDelta()` to initialize the account index whenever it is `0`, regardless of the current token index:

```solidity
if (_accountIndex == 0) {
    _accountIndex = INITIAL_INDEX; // or _tokenIndex
}
```

Alternatively set `_accountIndex = _tokenIndex` so a never-registered account starts accruing from the present index and gets `deltaIndex == 0` — matching the intended "new account earns from now" semantics that the `> INITIAL_INDEX` guard was clearly trying to express.

### Proof of Concept

Hardhat fork test sketch:

```ts
// 1. Existing holder: alice deposits MET, holds msdMET balance B.
await met.mint(alice.address, B);
await met.connect(alice).approve(msdMET.address, MaxUint256);
await msdMET.connect(alice).deposit(B, alice.address);

// 2. Fund RewardsDistributor with rewardToken.
await rewardToken.mint(rewardsDistributor.address, REWARD_SUPPLY);

// 3. Governor adds msdMET to the distributor (same block!).
await rewardsDistributor.connect(governor).updateTokenSpeed(msdMET.address, speed);

// 4. In the SAME block (no timestamp advance), attacker (or alice) claims.
//    tokenStates[msdMET].index == INITIAL_INDEX; accountIndexOf == 0.
//    _deltaIndex = 1e18; tokensDelta = B.
const before = await rewardToken.balanceOf(attacker.address);
await rewardsDistributor.claimRewards(attacker.address, [msdMET.address]);
// attacker must hold msdMET balance: flash-deposit before claim.
const after = await rewardToken.balanceOf(attacker.address);
expect(after.sub(before)).to.eq(attackerMsdBalance); // == full balance, ~free
```

To force same-block execution in the test, disable automining (`evm_setAutomine(false)`), submit `updateTokenSpeed` then `claimRewards`, then `evm_mine`. The asserted payout equals the attacker's entire deposit-token balance despite zero accrual time, demonstrating the broken reward-accrual invariant.
