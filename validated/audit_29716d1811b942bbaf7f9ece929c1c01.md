The bug class is "user prepays/debits value; if execution fails, the prepayment is burned instead of refunded." The Metronome analog lives in the bridge path: `ProxyOFT.sendFrom` burns the synthetic token on the source chain (`_debitFrom`) before dispatching the LayerZero message, and there is no refund/compensation path on source if the destination `_creditTo` (`SyntheticToken.mint`) fails — the message can only be retried verbatim, so a permanently-failing credit means the burned tokens are never re-minted anywhere.

Checking the credit path confirms it: `SyntheticToken.mint` reverts on `MintToNullAddress`, `SyntheticIsInactive`, or when `maxTotalSupply`/bridged-in caps are exceeded. `ComposableOFTCoreUpgradeable`/`NonblockingLzAppUpgradeable` store failed messages and `retryMessage` re-executes the identical payload — a `to_` of `address(0)` or an inactive token makes every retry revert, permanently freezing the burned supply. `lzReceive`/`retryMessage` are callable by anyone, so no privileged actor is required for the loss path.

### Title
Burned msAssets are never refunded when destination mint fails in `ProxyOFT.sendFrom` — (File: contracts/ProxyOFT.sol)

### Summary
`ProxyOFT.sendFrom`/`_send` debits the user by burning the full `amount_` of `SyntheticToken` on the source chain inside `_debitFrom` before the LayerZero message is dispatched (`contracts/ProxyOFT.sol:70-83`). Crediting on the destination happens later, asynchronously, via `_creditTo` → `syntheticToken.mint(toAddress_, amount_)` (`contracts/ProxyOFT.sol:86-93`). If the destination mint reverts, the non-blocking LayerZero app stores the payload and `retryMessage` re-executes the exact same payload — which fails deterministically when `toAddress_` is `address(0)` (`MintToNullAddress`), or fails until governance intervenes when the synthetic token is `!isActive` or `maxTotalSupply`/bridged-in caps are hit. There is no source-chain refund path: the burned tokens are permanently (or indefinitely) removed from circulation while the user holds nothing on either chain.

### Finding Description
- `OFTCoreUpgradeable._send` calls `_debitFrom` (burn) then `_lzSend`; once the transaction commits, the user's tokens are burned regardless of destination outcome.
- On the destination, `lzReceive` → `_nonblockingLzReceive` → `_sendAck` → `_creditTo` → `SyntheticToken.mint`. A revert is caught by `ExcessivelySafeCall` and recorded in `failedMessages`; `retryMessage` replays the identical payload and can never change `toAddress_` or `amount_`.
- For permanently-failing credits (e.g., `to_ == address(0)` reachable via the user-friendly `sendFrom(from_, dstChainId_, to_, amount_)`, which does not validate `to_`), every retry reverts forever → the burned tokens are lost with no compensation. For governance-dependent failures (token inactive, supply cap reached), funds are frozen until an admin acts — which may be never.
- The same gas-economics asymmetry as the reference bug applies: the user has fully paid (burned principal + LayerZero fee) for an execution result that the protocol could not deliver, and the protocol keeps the debit.

### Impact Explanation
Direct loss of user funds (burned synthetic tokens unrecoverable on both chains) for permanently-failing destinations, and temporary freezing of funds for cap/inactivity failures. It also breaks the bridge conservation invariant (`circulatingSupply` on source decremented, destination never incremented) and breaks the user trust assumption that a failed bridge delivery returns or preserves funds.

### Likelihood Explanation
Requires only a public `sendFrom` call; no privileged role. Permanent loss is triggered whenever `to_` cannot receive a mint (zero address is unchecked in `sendFrom`), and temporary freezing occurs whenever `syntheticToken.isActive()` is false or supply caps are saturated at delivery time — both plausible operational states. Not attacker-amplifiable against third parties, mirroring the original "sender loses own prepayment" severity.

### Recommendation
- Reject `to_ == address(0)` in `sendFrom`/`_send`.
- Add a source-side recovery: allow storing the failed destination outcome and expose a `refund`/re-credit (re-mint) on source when the message is irrecoverably failed, or mint into a claimable escrow instead of directly to `toAddress_`.
- Alternatively document that delivery failures require governor-assisted retry and provide a compensating mint mechanism.
