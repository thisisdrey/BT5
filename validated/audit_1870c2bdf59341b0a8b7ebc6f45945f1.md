### Title
Incorrect `total-borrowed` write-down formula in vault `socialize-debt` causes vault accounting to diverge from actual debt-index (analogous to `InfinityPool.writeOff`'s `totalBorrowed -= lostAmt` bug) - (File: `mainnet/contracts/vault/v0-vault-usdh.clar`, `mainnet/contracts/vault/v0-vault-sbtc.clar`, `mainnet/contracts/vault/v0-vault-stx.clar`, `mainnet/contracts/vault/v0-vault-ststx.clar`, `mainnet/contracts/vault/v0-vault-ststxbtc.clar`, `mainnet/contracts/vault/v0-vault-usdc.clar`)

### Summary
Every vault's `socialize-debt` function computes two different reduction amounts for the same write-off event — an index-based `debt-reduction` and a ratio-based `principal-reduction` — but only uses `principal-reduction` to decrement `total-borrowed`, while `debt-reduction` is used only for the `lindex` (share price) write-down. This mirrors the reported `InfinityPool.writeOff` flaw, where `totalBorrowed` was decremented by the wrong quantity (`lostAmt` instead of the account's true `principal`), leaving the pool's aggregate borrowed accounting inconsistent with the debt that was actually forgiven.

### Finding Description
In `socialize-debt`, the vault computes: [1](#0-0) 

- `debt-reduction = scaled-amount * idx / INDEX-PRECISION` — the actual, index-accrued face value of the scaled debt units being written off. This is the "true" economic value of the loss and is what feeds `new-lindex`, which write-downs the lender-facing exchange rate.
- `principal-reduction = scaled-amount * borrowed / scaled-principal` — a proportional-ratio value derived from the *current outstanding totals*, not from the index.

The state update then uses `principal-reduction`, not `debt-reduction`, to shrink `total-borrowed`: [2](#0-1) 

`total-borrowed` (raw uint, accrued through `borrow`/`repay`/`system-repay` operations) and `scaled-principal * idx / INDEX-PRECISION` (the index-derived value) are two independently maintained representations of the same quantity, and in a real deployment they diverge over time due to rounding in `mul-div-down`/`mul-div-up` across many `borrow`, `repay`, `system-repay`, and `accrue` calls, as seen in the repay path that also uses ratio-based `principal-reduction`: [3](#0-2) 

Because `socialize-debt` is invoked by the market's `socialize-debt-asset` during liquidation write-offs (an ordinary, permissionless flow triggered whenever a liquidated borrower has no collateral left): [4](#0-3) [5](#0-4) 

the mismatch between the value written off `lindex`/`total-assets` (`debt-reduction`, index-based) and the value subtracted from `total-borrowed` (`principal-reduction`, ratio-based) compounds every time a bad-debt write-off occurs. Just like the original `InfinityPool` bug — where `totalBorrowed -= lostAmt` failed to reflect the true `account.principal` being closed out — `total-borrowed` here is decremented by a formula that does not correspond to the actual debt-index value of the position being closed, so the vault's aggregate `total-borrowed` state drifts away from ground truth over repeated socialize-debt events.

### Impact Explanation
`total-borrowed` directly feeds `total-assets` (via `old-total-assets`) which determines `lindex` and the vault share exchange rate used for LP deposits/withdrawals. A persistent, attacker-triggerable (via repeated liquidation-driven write-offs on self-created undercollateralized positions) mismatch between the ratio-based debt reduction and the true index-based debt value skews `total-borrowed` versus real outstanding debt. Over many write-offs this either inflates or deflates the vault's reported assets relative to true backing, misappraising the exchange rate used to mint/redeem LP shares — a form of protocol insolvency / theft of unclaimed yield for depositors, since later depositors/withdrawers trade shares against an inaccurate asset base.

### Likelihood Explanation
Any ordinary principal can create a position, allow (or force via price/liquidation timing) it to be liquidated with `no-collateral-left`, triggering `socialize-debt-asset` → `vault-socialize-debt`. This path requires no privileged access and is a normal part of the liquidation flow, so the divergence between `principal-reduction` and `debt-reduction` is reachable by any user repeatedly through ordinary borrow/liquidate cycles, though the magnitude of drift per event is bounded by rounding and by how far `total-borrowed` has already diverged from the index-implied value.

### Recommendation
Use the same index-derived reduction value (`debt-reduction`) consistently for the `total-borrowed` write-down that is used for the `lindex` write-down, so the write-off is internally consistent (analogous to fixing `totalBorrowed -= lostAmt` to instead use the account's true `principal`), or reconcile `total-borrowed` against `scaled-principal * idx / INDEX-PRECISION` before/after socialization to eliminate drift.

### Proof of Concept
1. Borrower A borrows against `vault-usdh` (or any vault), pushing `total-borrowed` and `principal-scaled` to some state where accrued rounding has caused `total-borrowed` to diverge slightly from `scaled-principal * idx / INDEX-PRECISION` (naturally occurs after several `borrow`/`repay`/`accrue` cycles due to `mul-div-down`/`mul-div-up` rounding, e.g. via `v0-vault-usdh.clar:901-914`).
2. Borrower A's collateral value drops (or is manipulated within bounds of normal price movement) such that the position becomes liquidatable with zero collateral left.
3. Liquidator calls `liquidate`, triggering `no-collateral-left` and `fold socialize-debt-asset` (`v0-4-market.clar:1534-1560`), which calls `vault-socialize-debt` with the borrower's full remaining `scaled-debt`.
4. Inside `socialize-debt` (`v0-vault-usdh.clar:942-968`), `debt-reduction` (index-based) is computed and used only to derive `new-lindex`, while `principal-reduction` (ratio-based, using the already-drifted `total-borrowed`/`scaled-principal`) is subtracted from `total-borrowed`.
5. Repeating steps 1–4 across many small positions compounds the divergence between `total-borrowed` and the true index-implied debt, skewing `total-assets`/`lindex` used for LP share pricing over time.

**Note on confidence**: I could not fully verify the magnitude of real-world rounding drift between `total-borrowed` and `scaled-principal * idx / INDEX-PRECISION` in production usage patterns, since that depends on historical transaction sequences not available for static analysis; the root-cause code pattern (two different reduction formulas used inconsistently for the same write-off) is confirmed directly from the source, but the exact exploitability/severity would benefit from on-chain state analysis or a Devin session with test tooling to simulate compounding drift.
