Confirmed: `decode_atlas_get_attachment` at [1](#0-0)  performs no comparison between the parsed `GetAttachmentResponse.attachment` and the `AttachmentRequest.content_hash` that was sent out. The response is simply deserialized JSON with arbitrary attacker-controlled `content: Vec<u8>`, and `extend_with_attachments` inserts it into `self.attachments` unconditionally based on decode success alone.

### Title
Unvalidated attachment content lets a peer poison AtlasDB with arbitrary hash-mismatched blobs - (File: stackslib/src/net/atlas/download.rs)

### Summary
When the Atlas downloader fetches an `AttachmentRequest{content_hash: H}` from a peer, `AttachmentsBatchStateContext::extend_with_attachments` accepts and stores whatever `Attachment` the peer returns without checking that `attachment.hash() == H`. `AttachmentsDownloader::run` then unconditionally calls `AtlasDB::insert_instantiated_attachment` for every returned attachment, regardless of whether it matches any requested/committed content hash.

### Finding Description
The exploit path is: `AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558) drains `results.succeeded`, decodes the HTTP body via `response.decode_atlas_get_attachment()` (`stackslib/src/net/api/getattachment.rs:159-165`), and on successful JSON decode does `self.attachments.insert(response.attachment)` [2](#0-1)  — there is no comparison of `response.attachment.hash()` against `request.content_hash`. The `AttachmentRequest` that was sent (carrying the expected `content_hash`) is dropped/ignored once the response arrives; only its URL/report is used.

Then in `AttachmentsDownloader::run`, for every attachment collected in `context.attachments` (a `HashSet<Attachment>`, keyed by content not by the original request), the code does:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [3](#0-2) 

`insert_instantiated_attachment` (db.rs:576-592) unconditionally does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` keyed by `attachment.hash()` computed from the attacker-supplied content, with no check that this hash equals any queued `AttachmentInstance.content_hash` [4](#0-3) . If the returned content's hash doesn't match any real `content_hash` that was committed on-chain, `find_all_attachment_instances(&attachment.hash())` returns empty (db.rs:630-639), so no legitimate instance gets paired/resolved — but the row is still written to the `attachments` table with `was_instantiated=1`, which is not subject to the `max_uninstantiated_attachments`/eviction logic that only applies to `was_instantiated=0` rows (`insert_uninstantiated_attachment`, db.rs:511-536, `count_uninstantiated_attachments`/`evict_k_oldest_uninstantiated_attachments`, db.rs:538-567). Rows inserted via `insert_instantiated_attachment` have no equivalent cap or eviction routine in this file.

This is remotely reachable because `AttachmentsInventoryRequest`/`AttachmentRequest` HTTP fetches are made to whatever peer URL is advertised via the attachments-inventory response, i.e., any peer the node is syncing Atlas data from (an attacker can run their own peer/data-service URL and get selected as a source once its inventory bitmap claims to have the attachment). The attacker doesn't need any privileged role — just to be selected as an outbound sync peer and answer the `/v2/attachments/inv` and `/v2/attachments/{hash}` endpoints with attacker-chosen data.

### Impact Explanation
Each malicious response causes one `attachments` table row to be permanently stored (until node restart/manual cleanup) tied to zero canonical name-registration or namespace-preorder/register/update commitment — i.e., "attachment/BNS mismatch" storage with no corresponding validated `AttachmentInstance`. This matches the High-severity category "attachment/BNS mismatch," since it stores non-canonical data as if legitimate (though not actually served as an instance because `find_all_attachment_instances` won't find it and thus it won't be relayed/resolved to any consumer). It is repeatable per queued `AttachmentInstance`/batch retry cycle since the batch is re-queued (`bump_retry_count`, download.rs:187-205) if `has_fully_succeed()` is false — because a mismatched attachment never calls `resolve_attachment` with the *requested* hash, the batch keeps retrying and the attacker can keep sending fresh garbage each round, growing the `attachments` table with `was_instantiated=1` rows that are not bounded by `max_uninstantiated_attachments`/eviction.

### Likelihood Explanation
Requires the node to run Atlas attachment sync (default in Stacks nodes) and for the attacker's node to be selected as one of the `network.get_outbound_sync_peers()` sources with a URL claiming (via `/v2/attachments/inv`) to have the requested content — no special key, secret, or privileged role needed; being a normal, reachable P2P peer/data server is sufficient. Attacker cost is a handful of HTTP responses per batch cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; reject/penalize (bump_failed_requests) mismatches instead of accepting them. Additionally, apply an eviction/size cap to `was_instantiated=1` rows in `insert_instantiated_attachment` analogous to `max_uninstantiated_attachments`, or delete instantiated attachments that never get paired with any `attachment_instances` row within a bounded time.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs`:
1. Build an `AttachmentsBatchStateContext` with one `AttachmentRequest{content_hash: H}` (from a `new_attachment_instance_from` with content `"expected"`).
2. Construct a `BatchedRequestsResult` where `succeeded` maps that request to `Some(response)` whose `decode_atlas_get_attachment()` yields `GetAttachmentResponse{attachment: Attachment{content: b"garbage".to_vec()}}` (hash != H).
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the garbage `Attachment` (proving no hash check).
4. Feed this through `AtlasDB::insert_instantiated_attachment(&garbage_attachment)` and assert: `atlasdb.find_attachment(&garbage_attachment.hash())` returns `Some(...)` (row stored) while `atlasdb.find_all_attachment_instances(&H)` remains empty (no legitimate instance ever resolved) — demonstrating storage of attacker content unconnected to any real `AttachmentInstance.content_hash`.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
