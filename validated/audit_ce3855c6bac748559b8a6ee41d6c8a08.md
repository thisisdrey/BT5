### Title
Unbounded array index derived from untrusted TVM call data in `ValidateMultiSign`/`BatchValidateSign` precompiles causes out-of-bounds access - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts compute an array index directly from attacker-supplied call-data words and use it to index into the `words[]` array (produced by `DataWord.parseArray(rawData)`) without first validating that the computed index is within the bounds of that array — the exact "unchecked sumIndex_" pattern from the Ajna `Deposits.sol` report, just applied to Java array indexing reachable from a smart-contract call instead of a Solidity Fenwick tree.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse the raw precompile input into a `DataWord[] words` array and then compute an offset from a caller-controlled word to look up another element of that same array: [1](#0-0) 

```
DataWord[] words = DataWord.parseArray(rawData);
...
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  ...
}
```

and similarly in `BatchValidateSign`: [2](#0-1) 

```
DataWord[] words = DataWord.parseArray(data);
byte[] hash = words[0].getData();

if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[1].intValueSafe() / WORD_SIZE].intValueSafe();
  int addrArraySize = words[words[2].intValueSafe() / WORD_SIZE].intValueSafe();
  ...
}
```

In both cases, `words[3]` / `words[1]` / `words[2]` are attacker-controlled 32-byte words read from the transaction's smart-contract call data (the ABI-encoded offset fields for the signature/address arrays). The value `words[3].intValueSafe() / WORD_SIZE` (or `words[1]...`, `words[2]...`) is used directly as an index into `words[]` with **no check** that it is `< words.length` or non-negative before dereferencing. This mirrors the reported bug class exactly: an externally influenced index (`sumIndex_` in Ajna) is used to access a bounded array (`deposits_.values`/`scaling` in Ajna, `words[]` here) without a prior bounds check against the array's actual size.

This precompile is reachable by **any unprivileged account** simply by deploying/triggering a smart contract that performs a `CALL`/`STATICCALL` to the fixed precompile address for `ValidateMultiSign` or `BatchValidateSign` (both are exposed as standard precompiled contracts invoked from ordinary `TriggerSmartContractActuator`/`CreateSmartContractActuator` execution paths), i.e., from a single signed, unprivileged transaction.

### Impact Explanation
An out-of-range offset causes a Java `ArrayIndexOutOfBoundsException` to be thrown while executing the precompile. Because this is deep inside `PrecompiledContracts.execute`, invoked from the TVM's `Program`/`CALL` opcode dispatch, if the exception is not fully caught and normalized into an EVM/TVM revert at every call site, it can propagate as an unexpected `RuntimeException` out of contract execution, causing a node to fail to process an otherwise-valid transaction deterministically, or — depending on how the surrounding call/catch layers handle unchecked exceptions relative to gas/energy accounting — create nondeterministic behavior between nodes validating the same block (some nodes may throw before consuming energy that others computed successfully), which is a chain-halt/consensus-divergence class issue. At minimum this is a reliable, attacker-triggerable crash-inducing DoS vector for any node executing the malicious contract call.

### Likelihood Explanation
High reachability: no special privileges are required — any address can deploy a trivial contract that calls the `ValidateMultiSign` or `BatchValidateSign` precompile address with a single crafted `words[3]`/`words[1]`/`words[2]` value, and any full node executing that transaction (during broadcast validation or block application) will hit the vulnerable code path when `VMConfig.allowTvmSelfdestructRestriction()` is active (a config flag, not a runtime check the attacker needs elevated permission to influence).

### Recommendation
Before using any user-supplied offset/word index to dereference `words[]` in `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, validate that the computed index (`words[3].intValueSafe() / WORD_SIZE`, `words[1].intValueSafe() / WORD_SIZE`, `words[2].intValueSafe() / WORD_SIZE`) is non-negative and strictly less than `words.length`, returning the standard `Pair.of(true, DATA_FALSE)` failure result instead of throwing when the bound is violated — analogous to adding the `require(curIndex <= MAX_FENWICK_INDEX, ...)` boundary check recommended in the source report. The same bounds validation should be applied inside `extractSigArray`/`extractBytesArray`/`extractBytes32Array` (referenced but not shown in the excerpted context) wherever they index into `words[]` using offsets computed from raw call data.

### Proof of Concept
1. Deploy a trivial TVM contract whose bytecode performs a `CALL` to the `ValidateMultiSign` precompile address (0x...09 or equivalent reserved address) with an ABI payload where `words[3]` (the declared "signatures array offset" word) is set to a large value, e.g. `0xFFFFFFFF`, so that `words[3].intValueSafe() / WORD_SIZE` is far larger than `words.length`.
2. Trigger the contract via a normal `TriggerSmartContractContract` transaction (unprivileged account, standard fee/energy).
3. During TVM execution, `PrecompiledContracts.ValidateMultiSign.execute` reaches `words[words[3].intValueSafe() / WORD_SIZE]` and throws `ArrayIndexOutOfBoundsException`, since `VMConfig.allowTvmSelfdestructRestriction()` gates this check-less path (confirmed at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1066-1074`); the same crafted-offset technique applies to `BatchValidateSign` at lines 1165-1171 via `words[1]`/`words[2]`.
4. Observe whether the exception is caught generically (turning it into a revert) or escapes the call boundary uncaught, producing a node-level crash/energy-accounting mismatch — this determines whether impact is "clean revert" (low severity, already likely handled by outer catch blocks for `ValidateMultiSign`'s sibling `BatchValidateSign.execute` wrapper) or an uncaught propagation (Medium/High DoS), which requires runtime confirmation against the exact call-site exception handling not fully visible in the indexed excerpt.
