### Title
Unchecked `realloc()` in ijar's zlib decompressor causes a wild pointer write when decompressing an attacker-supplied ZIP/JAR entry - (File: `third_party/ijar/zlib_client.cc`)

### Summary
`Decompressor::UncompressFile` grows its output buffer with a raw `realloc()` call and never checks the result for `NULL` before continuing to use it as the base of a pointer computed from attacker-controlled decompressed-data length. This mirrors CVE-2024-6603's bug class: an allocation can fail, but the code proceeds as if it had succeeded, corrupting a pointer that is subsequently dereferenced/freed.

### Finding Description
`Decompressor::UncompressFile` maintains a growable heap buffer `uncompressed_data_` sized by `uncompressed_data_allocated_`. On each `Z_OK` result (output buffer too small), the code doubles the allocation and reallocates: [1](#0-0) 

`realloc()`'s return value is stored directly into `uncompressed_data_` without checking for `NULL`. If the allocation fails (e.g., the process is memory-constrained while `ijar` inflates an attacker-crafted, highly compressible ZIP/JAR entry toward the multi-hundred-MB/2GB `MAX_BUFFER_SIZE` ceiling), `uncompressed_data_` becomes `NULL`, and:
- The pointer to the previously allocated (and still populated) buffer is lost — that memory is neither used nor freed, corrupting the object's invariant that `uncompressed_data_` always references a valid buffer of size `uncompressed_data_allocated_`.
- On the very next loop iteration, `stream.next_out = uncompressed_data_ + uncompressed_until_now;` computes a wild pointer (`NULL + offset`, with `offset` fully attacker-influenced via how much data has already been inflated), and `inflate()` is invoked to write further attacker-controlled decompressed bytes at that address: [2](#0-1) 

This is reachable from real ZIP/JAR content processing: `InputZipFile::UncompressFile()` calls `decompressor_->UncompressFile(p, remaining)` for every DEFLATE-compressed entry while walking a ZIP file supplied on disk, and the resulting pointer/`DecompressedFile` is trusted by the caller and handed to the configured `ZipExtractorProcessor`: [3](#0-2) 

`ijar` is Bazel's interface-jar generator, invoked automatically when compiling against `.jar` dependencies (including externally-fetched artifacts, e.g. via `java_import`/Maven-derived jars). The bytes of such a jar are attacker-controlled content published at a URL a Bazel build consumes; a `sha256`/lockfile hash on the *download* only pins the outer archive bytes, it does not validate that the *contents parsed by ijar's ZIP/DEFLATE handling* are well-behaved. An attacker who legitimately publishes a jar artifact (no MITM required) can shape a ZIP entry to be highly compressible so its decompressed size approaches ijar's `MAX_BUFFER_SIZE` (`INT32_MAX` bytes), maximizing the chance that the doubling `realloc()` call fails under normal memory pressure, then have the corrupted/`NULL` `uncompressed_data_` used for further inflate writes.

### Impact Explanation
A successful trigger produces an out-of-bounds/wild write of attacker-controlled decompressed content at an attacker-influenced offset from address zero, in the native `ijar` binary that runs as part of every build that compiles Java code against jar dependencies. This is memory corruption in a build-time native tool, potentially leading to crashes or, depending on platform memory mappings, code execution in the build process — directly analogous to the underlying CVE ("allocation could fail but free would have been called on the pointer afterwards leading to memory corruption").

### Likelihood Explanation
Triggering requires the doubling `realloc()` to actually fail, which in turn requires either genuine memory pressure on the machine running the build or an extremely large decompressed entry that approaches the platform's allocatable/address-space limits. This makes reliable exploitation dependent on host memory conditions rather than purely on attacker-controlled input, lowering practical likelihood compared to a pure logic bug, but the missing NULL check itself is unconditional and present on every reallocation path, so any OOM/allocation-failure condition during ijar's jar processing turns into memory corruption rather than a clean, safe failure.

### Recommendation
Check the return value of `realloc()` in `Decompressor::UncompressFile` before overwriting `uncompressed_data_`; on failure, retain the original pointer, free it explicitly, set `uncompressed_data_` to `NULL`, and return an error from `UncompressFile()` (mirroring the existing `error(...); return NULL;` pattern used elsewhere in the function) instead of continuing to use a buffer of unknown validity.

### Proof of Concept
A deterministic proof requires forcing `realloc()` to fail, which cannot be reliably scripted without host-specific memory-limiting (e.g., `ulimit -v`/cgroup memory caps) combined with a crafted highly-compressible ZIP entry sized close to `MAX_BUFFER_SIZE`. I was not able to construct and verify a fully reproducible JUnit/shell test within this investigation; a background engineering session with terminal access (to set a tight virtual-memory limit and run `ijar`/a small harness calling `Decompressor::UncompressFile` against a zip-bomb-style DEFLATE stream while observing for a crash/write at a `NULL`-based address) would be needed to confirm exploitability, e.g. extending `third_party/ijar/zip_test.sh` or adding a new gtest similar to `src/tools/singlejar/transient_bytes_test.cc`'s `DecompressEntryContents` test, but forcing an allocation failure via a memory-limited subprocess.
