### Title
Unsigned integer underflow in `InputZipFile::CalculateOutputLength()` can wrap to a huge output-size estimate when processing an attacker-supplied jar/zip - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` (used by Bazel to build interface jars, e.g. `ijar`/`zipper` tooling that processes jar/zip archives originating from external dependencies) computes a worst-case output size for the generated jar via straightforward unsigned 64-bit arithmetic on attacker-controlled per-entry size fields taken from the zip central directory, with no bounds/consistency validation before the subtraction. This mirrors the Vault.sol pattern where an attacker-influenced value (`sponsorAmount`/here, `skipped_compressed_size`) is subtracted from another value (`totalUnderlying()`/here, `input_file_->Length()`) without checking that the subtrahend cannot exceed the minuend, allowing an unsigned underflow that wraps to a huge number instead of failing safely.

### Finding Description
`InputZipFile::CalculateOutputLength()` sums `compressed_file_size`/`uncompressed_file_size` fields read straight out of the zip central directory for every entry (both accepted and skipped), then computes: [1](#0-0) 

```
u8 InputZipFile::CalculateOutputLength() {
  ...
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
```

`compressed_file_size`/`uncompressed_file_size` are `u8` (`uint64_t`) values decoded directly from the (potentially 32-bit or ZIP64) central-directory header fields (see `CDH`/`LH` accessors), and are attacker-controlled: any party who serves a `.jar`/`.zip` that Bazel's `http_archive`/`http_jar`/`java_import` toolchain feeds into `ijar` (e.g. via `singlejar`'s counterpart logic, or ijar invoked to produce interface jars from a downloaded jar) fully controls these fields. `EnsureRemaining` only checks that the *local* file header's declared sizes don't exceed the bytes remaining in the mmapped input for each entry it actually reads — it does not check that the sum of central-directory-declared `compressed_file_size` values across all "skipped" entries can't exceed `input_file_->Length()`, nor that `compressed_size <= uncompressed_size` is required by the file format when computing the aggregate size estimate.

Because `skipped_compressed_size` is a straight sum of attacker-supplied per-entry `u8` values with no upper bound tied to the actual file length, and the first term of the return expression is `input_file_->Length() - skipped_compressed_size`, a central directory that declares one or more "skipped" (rejected-by-processor) entries with a compressed size larger than the whole file will make `skipped_compressed_size > input_file_->Length()`. Since this is unsigned 64-bit subtraction, the result underflows and wraps around to a value near `UINT64_MAX` instead of throwing/erroring — exactly the underflow-instead-of-revert failure mode in the reference Solidity bug, just manifesting as a wrapped huge integer instead of a Solidity revert.

### Impact Explanation
The returned value from `CalculateOutputLength()` is used by `ijar.cc` to size the output buffer/mmap for the generated interface jar (`kMaximumOutputSize` is checked against it). An underflowed, wrapped-to-huge value could:
- Cause the size check against `kMaximumOutputSize` (4GB limit) to behave incorrectly (a huge wrapped value would actually still exceed `kMaximumOutputSize` and thus likely be caught by that check downstream, but only if that check is applied to the *unwrapped* huge value rather than a value that could also wrap into a *small*, plausible-looking size via combination with the `(uncompressed_size - compressed_size)` term).
- More critically, the second term `(uncompressed_size - compressed_size)` is itself a second unsigned subtraction of two attacker-controlled `u8` sums with zero validation that `uncompressed_size >= compressed_size` — trivially violated by declaring bogus per-entry sizes, producing a second independent underflow that can combine with the first to make the final `u8` result land on an arbitrary, attacker-chosen small value. This defeats the intended "worst case is uncompressed input size" invariant the function is supposed to guarantee, and an undersized buffer computed this way is a precursor to a heap buffer overflow when ijar actually writes the (larger real) uncompressed data during processing.

### Likelihood Explanation
Reaching this code only requires convincing Bazel (or a build depending on the attacker's artifact) to run `ijar`/the zip-processing path over a hostile jar/zip file — i.e., any dependency fetched via `http_jar`/`http_archive`/`maven`-style rules where an unprivileged attacker controls the content served at a dependency URL (a hostile mirror/registry). No checksum is bound to the *internal structure* of the zip (a `sha256`/`integrity` pin only verifies the outer bytes match a fixed hash, which the attacker can freely satisfy for their own hostile file when the victim has not pinned a specific known-good hash, or in a first-fetch/unpinned scenario) — the invariant broken here is that "untrusted content stays data": the size fields inside the zip's own central directory, over which the attacker has full control, feed directly into unsigned arithmetic with no defensive validation, and that fact is orthogonal to whether the outer byte stream matches a fixed checksum.

### Recommendation
Add explicit invariant checks before performing the subtractions in `CalculateOutputLength()`:
```
if (compressed_size > uncompressed_size) {
  fprintf(stderr, "Malformed zip: compressed size exceeds uncompressed size\n");
  return false; // or otherwise fail safely
}
if (skipped_compressed_size > (u8) input_file_->Length()) {
  fprintf(stderr, "Malformed zip: declared entry sizes exceed file length\n");
  return false;
}
```
and propagate failure to the caller instead of returning a wrapped `u8` value, mirroring the fix pattern from the reference report (guard against the subtrahend exceeding the minuend and return a safe sentinel/error rather than allowing wraparound).

### Proof of Concept
Concrete reproduction requires constructing a minimal but well-formed (per `FindZipCentralDirectory`) zip file whose end-of-central-directory record is consistent, but whose central directory entries declare (a) a `compressed_file_size` for a "skipped" entry (one the processor's `Accept()` rejects) larger than `input_file->Length()`, and (b) a per-entry `compressed_file_size` larger than its own `uncompressed_file_size`, then invoking `ijar`/the `ZipExtractor::Create` + `CalculateOutputLength()` path on that file and observing the returned `u8` wraps to a value inconsistent with the actual archive size. I was not able to fully verify the downstream consumption (`third_party/ijar/ijar.cc`, `third_party/ijar/zip.h`) within the remaining tool budget to confirm precisely how the wrapped value is used for buffer allocation, so the concrete write-out-of-bounds consequence downstream of the arithmetic underflow is inferred from the surrounding buffer-sizing comments (`kMaximumOutputSize` check, "worst case is input uncompressed" comment) rather than directly traced through `ijar.cc`'s buffer allocation call site. A JUnit/shell reproduction would need to be authored against `ijar_test`/`zip_test` fixtures to construct the malformed central directory described above and assert on the returned length or on a crash/OOB write during `ProcessAll()`. // Gives a maximum bound on the size of the interface JAR. Basically, adds
// the difference between the compressed and uncompressed sizes to the size
// of the input file.
u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
