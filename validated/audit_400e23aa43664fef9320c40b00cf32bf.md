## Title
Energy-time budget for the `VerifyTransferProof` (Sapling shielded transfer) precompile is silently bypassed because the `CountDownLatch.await()` timeout result is discarded, letting an attacker stall the shared 5-thread verification pool past its metered time limit - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.VerifyTransferProof.doExecute()` submits Sapling spend/output/binding-signature verification tasks to a small, statically-shared `ExecutorService` (`workersInConstantCall` / `workersInNonConstantCall`, each sized `5`), then calls `countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` to enforce the remaining energy-derived CPU-time budget. The boolean result of that timed wait (`withNoTimeout`) is computed but never checked [1](#0-0) . Execution instead unconditionally falls through to `future.get()` on every submitted task, which blocks with no timeout at all until every task finishes, regardless of whether the CPU-time budget was exceeded.

### Finding Description
This is the same bug class as CVE-2019-19073 (Linux `ath9k` `htc_hst.c`): a `wait_for_completion_timeout()`-style call's failure/timeout outcome is not properly acted upon, so the calling code keeps waiting on outstanding work instead of bailing out and releasing the associated resource. Here the resource is the fixed-size (`5` threads) `ExecutorService` shared by *every* Sapling shielded transfer verification in the node (both TVM constant calls and non-constant/state-changing execution), declared statically: [2](#0-1) 

Compare this with the correctly-implemented sibling precompile `BatchValidateSign`, which does check the timeout and aborts immediately by throwing `Program.Exception.notEnoughTime` when `countDownLatch.await(...)` returns `false`: [3](#0-2) 

`VerifyTransferProof` omits this check entirely, so the intended energy-metering cutoff (`getCPUTimeLeftInNanoSecond()`) never actually bounds the wall-clock time consumed by a single precompile call — the call simply blocks on `future.get()` until every submitted `SaplingCheckSpendTask` / `SaplingCheckOutputTask` / `SaplingCheckBingdingSig` finishes: [4](#0-3) 

Each of those tasks invokes native `librustzcash` JNI verification routines (`librustzcashSaplingCheckSpendNew`, `librustzcashSaplingCheckOutputNew`), whose execution time is attacker-influenced via the proof bytes supplied in the transaction/contract call data. Because the pool only has 5 worker threads and is shared by *all* callers of this precompile across the node (block application, mempool validation, and `triggerConstantContract`/`triggercontract` API calls), an attacker who submits multiple concurrent transactions or constant-call requests invoking `VerifyTransferProof` with proof data crafted (or simply repeated) to be slow can occupy all 5 threads indefinitely. New calls to the same precompile — including ones made while the node is applying blocks containing legitimate shielded transactions — will queue behind the stuck workers, since the CPU-time abort path that would normally reclaim the caller's thread and let the energy/time budget terminate the call is dead code.

### Impact Explanation
Unlike the kernel CVE, which is a plain memory leak, this analog is a resource-exhaustion / DoS vector reachable from an unprivileged, unauthenticated actor: any account can broadcast a transaction (or issue a `triggerconstantcontract` JSON-RPC/HTTP call) that reaches a contract calling the `VerifyTransferProof` precompile. Because the intended timeout guard is inert, the attacker can pin all threads of the shared verification pool for an extended period, blocking further Sapling shielded-transfer verification node-wide — including verification needed for normal block application in `Manager` — degrading or halting the node's ability to process shielded transactions and to serve related Wallet/API query paths.

### Likelihood Explanation
Reaching the vulnerable path only requires crafting the fixed-size `VerifyTransferProof` input (`SIZE = {2080, 2368, 2464, 2752}` bytes) with spend/output counts within the allowed `1–2` range and calling the precompile from a contract — no special permissions or signer roles are needed [5](#0-4) . The only extra effort is finding or crafting proof inputs whose native verification takes long enough to matter, or simply issuing many concurrent calls to keep all 5 shared threads busy — well within reach of an ordinary broadcaster/API client.

### Recommendation
Check `withNoTimeout` immediately after the `countDownLatch.await(...)` call in `VerifyTransferProof.doExecute()`, mirroring `BatchValidateSign`: if the wait times out, abort the call (throw `Program.Exception.notEnoughTime` or return a failure result) instead of proceeding to unconditionally block on `future.get()`. Additionally, cancel outstanding `Future`s on timeout in both `BatchValidateSign` and `VerifyTransferProof` so abandoned tasks do not continue occupying the shared thread pool after the caller has given up on them.

### Proof of Concept
1. Deploy/call a contract that invokes the `VerifyTransferProof` precompile (address for `verifyTransferProof`) with a validly-sized (`2080`/`2368`/`2464`/`2752`-byte) payload containing `spendCount`/`receiveCount` in `[1,2]` and proof bytes engineered (or simply reused across many parallel calls) to make `librustzcashSaplingCheckSpendNew`/`CheckOutputNew` run for an extended time.
2. Fire several such transactions/`triggerconstantcontract` calls concurrently — enough to occupy all 5 threads of `workersInNonConstantCall` (or `workersInConstantCall` for read-only calls).
3. Observe that `countDownLatch.await(getCPUTimeLeftInNanoSecond(), ...)` returns `false` once the metered CPU-time budget is exceeded, per `getCPUTimeLeftInNanoSecond()` [6](#0-5) , yet the code proceeds to `future.get()` on every future without checking that boolean, so the calling thread (and the pool worker threads) remain blocked past the intended limit, and any additional `VerifyTransferProof` invocations from other transactions or API calls queue up behind the exhausted pool.
