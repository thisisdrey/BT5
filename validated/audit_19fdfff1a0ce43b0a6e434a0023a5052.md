Audit Report

## Title
Deferred slash silently dropped when its unbonding-era sub-pool bucket has already been merged - ([File: substrate/frame/nomination-pools/src/lib.rs])

## Summary
`Pallet::on_slash` in `pallet-nomination-pools` reduces `TotalValueLocked` by `total_slashed` unconditionally, but only applies the corresponding per-era balance reduction if `sub_pools.with_era.get_mut(era)` still contains that era's bucket. Because `SubPools::maybe_merge_pools` can fold a `with_era` bucket into `no_era` (driven only by `MaxUnbondingPools`/`bonding_duration`, independent of `SlashDeferDuration`), or `withdraw_unbonded` can remove a bucket entirely once fully drained, a deferred slash that still targets that era in `pallet-staking`'s ledger can find no matching bucket in the pools pallet and have its balance-side adjustment silently skipped, while TVL is still decremented.

## Finding Description
`on_slash` is registered as the `OnStakingUpdate` hook and is invoked by `pallet-staking` when deferred slashes are finally applied: [1](#0-0) 

`TotalValueLocked` is decremented unconditionally: [2](#0-1) 

Then, per era in `slashed_unlocking`, the code only mutates the bucket `if let Some(pool) = sub_pools.with_era.get_mut(era).defensive()`; if the key is missing, the branch is simply skipped with no accounting fallback, and `defensive!("Expected SubPools were not found")` only fires when `sub_pools` itself is entirely absent, not when an individual era key is missing: [3](#0-2) 

The era bucket can be removed by two independent paths unrelated to `SlashDeferDuration`:
- `maybe_merge_pools` folds `with_era` buckets older than `MaxUnbondingPools - bonding_duration()` into `no_era`, a purely bonding-duration/unbonding-pool-count-driven schedule: [4](#0-3) 
- `withdraw_unbonded` removes a `with_era` entry entirely once its points hit zero: [5](#0-4) 

There is an existing regression test (`slash_lands_in_correct_bucket_after_window_widens`) that only exercises the case where the bucket is correctly *retained* after widening the bonding duration; it does not cover, and the code does not handle, the case where the pools-side bucket has already been merged/removed by the time the deferred slash from staking finally lands. A related comment in the delegate-stake test suite explicitly flags adjacent routing/rounding edge cases here as things "that should not happen at all," corroborating that this exact interaction is a known fragile area of the code.

The invariant that should hold — "every era present in `slashed_unlocking` (from `pallet-staking`'s ledger) has a corresponding `with_era` bucket in `pallet-nomination-pools`, or the slash amount is redirected somewhere accounted for" — is not enforced anywhere. `maybe_merge_pools`'s merge schedule is derived only from `T::MaxUnbondingPools` and `T::StakeAdapter::bonding_duration()`, with no reference to `SlashDeferDuration`, so runtimes where the effective post-unbonding window is narrower than the slash-deferral period can hit this exact gap.

## Impact Explanation
When the branch is skipped, TVL and the (stale) `no_era`/other bucket balances continue to reflect pre-slash amounts even though the real staked funds backing the pool in `pallet-staking` have already been reduced. This is a genuine pools-accounting desync: `TotalValueLocked` and `SubPoolsStorage` no longer conserve value against the actual bonded/unbonding stake, which can let members redeem against an overstated balance while later withdrawals from the same (merged/no_era) bucket come up short — a fund-conservation violation in `pallet-nomination-pools`, matching the "permanent user-fund lock/shortfall" impact category.

## Likelihood Explanation
This requires a specific but plausible runtime parameterization: `T::MaxUnbondingPools` and `bonding_duration()` set such that the effective post-unbonding merge window is narrower than the staking pallet's actual `SlashDeferDuration`, combined with an ordinary offence/slash event landing on an era whose bucket has already been merged or drained. No privileged actor is needed — an ordinary equivocation/offence report combined with normal pool member unbond/withdraw activity and standard runtime configuration choices reproduces the condition. This is a legitimate runtime-configuration-dependent bug, not one requiring malicious node/validator/governance behavior.

## Recommendation
In `on_slash`, when the targeted `era` bucket is missing from `with_era`, apply the proportional balance reduction to `no_era` instead of doing nothing, using the same points-weighted reduction logic. Additionally, ensure `effective_post_unbonding_window` computation (or overall unbonding-pool retention policy) accounts for `SlashDeferDuration`, e.g. by bounding merges so that a bucket cannot be discarded before all slashes that could still target its era have been finalized.

## Proof of Concept
1. Configure a runtime where `MaxUnbondingPools - bonding_duration()` (the effective post-unbonding window in `maybe_merge_pools`) is smaller than `pallet-staking`'s `SlashDeferDuration`.
2. Create a pool; a member fully unbonds in era `E`, creating a `with_era` bucket for `E`.
3. Advance eras past the effective window so a subsequent pool operation triggers `maybe_merge_pools`, folding era `E`'s bucket into `no_era`.
4. Trigger an offence whose deferred slash (applied `SlashDeferDuration` eras later) still targets era `E`'s unlocking chunk in `pallet-staking`, producing a non-empty `slashed_unlocking` entry for era `E`.
5. Call `on_slash`; observe `TotalValueLocked` reduced by `total_slashed` while `sub_pools.with_era.get_mut(&E)` is `None` and `no_era`'s balance is unchanged — this can be directly asserted in a unit test analogous to `slash_lands_in_correct_bucket_after_window_widens`, but pre-merging era `E`'s bucket before calling `on_slash` and asserting `no_era.balance` and TVL diverge from the real slashed amount.
