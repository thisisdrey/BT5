### Title
Unchecked attacker-controlled array-length field in `PrecompiledContracts.extractBytesArray` can trigger uncaught `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` during precompiled contract execution - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2019-9036 is a heap-based buffer overflow in `matio`'s `ReadNextFunctionHandle()` caused by trusting an attacker-supplied length/dimension field from the parsed file to allocate/copy into a buffer without validating it against the actual remaining data size. The equivalent bug-class in java-tron is a length field taken directly from TVM call data (a `DataWord`) and used to size a Java array or index into an array without validating it against the bounds of the surrounding structure, in `extractBytesArray` / `extractBytes32Array` in `PrecompiledContracts.java`.

### Finding Description
`extractBytesArray` reads the array-length word directly out of attacker-controlled call data and uses it, unvalidated, both to allocate a new array and to index further into the `words` array: [1](#0-0) 

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen);
    }
    return bytesArray;
}
```

`len` comes from `words[offset].intValueSafe()` — a value taken straight out of the calldata a caller supplies to whatever precompiled contract invokes this helper (companion helper `extractBytes32Array` has the identical pattern): [2](#0-1) 

There is no upper bound check on `len` before `new byte[len][]` is allocated, and no bound check that `offset + i + 1` stays within `words.length` inside the loop. This mirrors the matio flaw: a size/count value parsed from untrusted input is trusted to drive allocation and indexing without validating it against the real size of the surrounding buffer.

Because `intValueSafe()` clamps a 256-bit `DataWord` to a Java `int` (up to `Integer.MAX_VALUE`), an attacker can set the length word to a very large positive value. `new byte[len][]` with `len` near `Integer.MAX_VALUE` immediately throws `OutOfMemoryError`, and even modestly large but still bogus `len` values (larger than the actual `words` array) will cause `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException` well before any `bytesLen`/`extractBytes` bound-check logic in `extractBytes` is reached.

### Impact Explanation
This code path is reached whenever a precompiled contract that calls `extractBytesArray`/`extractBytes32Array` is invoked via a TVM `CALL`, which is directly reachable by any account that can deploy or invoke a smart contract calling into the relevant precompiled address. An uncaught `OutOfMemoryError` or `ArrayIndexOutOfBoundsException` thrown deep inside contract-execution/argument-decoding logic, outside of the narrower `try { ... } catch (Throwable any)` guards visible elsewhere in `PrecompiledContracts.java` (e.g. around `recoverAddrBySign`), risks propagating up through block/transaction processing rather than being cleanly converted into a reverted transaction — a node crash or denial-of-service condition triggered by a single malicious transaction, which the report's escalation rules classify as an acceptable "node crash or halt" impact.

### Likelihood Explanation
Reaching this code only requires crafting a transaction that calls the affected precompiled contract with a manipulated length word in its input — no special privileges, staking, or network position are required, matching the "unprivileged transaction broadcaster / contract deployer" reachability bar in scope.

### Recommendation
Validate `len` (and every subsequent offset derived from calldata) against the bounds of `words`/`data` before allocation or indexing in `extractBytesArray` and `extractBytes32Array` — e.g., reject if `len < 0`, `len` exceeds a sane maximum, or `offset + len + 1 > words.length`, and ensure the exception path for oversized/malformed inputs is caught and converted into a normal `ContractExeException`/revert rather than an uncaught `Error`/`RuntimeException`.

### Proof of Concept
Not independently executed against a live precompiled-contract entry point in this pass — the exact precompiled contract(s) that call `extractBytesArray`/`extractBytes32Array` (versus other decode helpers such as `parseBytes`/`decodeItemBytes` in `RLP.java`, which do have `verifyLength` guards) could not be fully traced within the available tool budget, since the caller wiring for this specific helper was not located before the iteration limit was reached. Conceptually, a PoC would deploy a contract that performs a low-level `CALL` to the affected precompiled address with an ABI payload whose "array length" word is set to a very large value (e.g., `0x7fffffff`), and observe that the resulting exception is not gracefully converted into a reverted transaction.

**Caveat:** Because the codebase index has size limits, some file contents (particularly the exact caller of `extractBytesArray`/`extractBytes32Array` and any surrounding try/catch in the invoking precompiled contract's `execute()` method) may not be fully indexed. Confirming the precise precompiled contract address and exception-handling behavior around this call would require a full-repository session (e.g., a Devin session with complete file access) rather than the Ask-only index used here.
