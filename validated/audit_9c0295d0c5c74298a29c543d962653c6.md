### Title
Stale `PromiseYieldReceipt`/timeout state survives `remove_account`, letting a pre-planted callback execute as a self-call against an unrelated contract that later reuses the same account name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only clears the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie columns, but never removes `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, or `YieldIdToDataId`/`DataIdToYieldId` entries. Because `promise_yield_create` always targets `receiver_id = current_account_id` (self), an account can plant a yield on itself, self-delete via `DeleteAccountAction`, and the orphaned receipt/timeout entry will later be executed automatically against whatever contract subsequently occupies that same account name.

### Finding Description
`promise_yield_create` (both interpreter and wasmtime paths, e.g. `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:4008-4009`) always calls `ext.create_promise_yield_receipt(self.context.current_account_id.clone())`, i.e. the receiver of the parked yield receipt is always the calling account itself: [1](#0-0) . This writes a `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` entry and a `PromiseYieldTimeout` queue entry keyed by `{account_id, data_id, expires_at}` via `enqueue_promise_yield_timeout` [2](#0-1) .

When `DeleteAccountAction` executes, `action_delete_account` calls `remove_account`, which only iterates/removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData`: [3](#0-2)  and [4](#0-3) . The `PromiseYieldReceipt`, `PromiseYieldStatus`, and the pending `PromiseYieldTimeout` queue entry (and `YieldId`/`DataId` mappings) are never touched, so they remain in the trie after the account no longer exists.

`resolve_promise_yield_timeouts` runs unconditionally every chunk and, once `expires_at <= block_height`, checks only `state_update.contains_key(&promise_yield_key, ...)` — with no check that the owning account still exists or is the same account that created the yield — and if the key is present it synthesizes a `PromiseResume` receipt targeting `queue_entry.account_id`: [5](#0-4) . When that `PromiseResume` receipt is processed, `get_promise_yield_receipt` still finds the old receipt (never removed) and executes it via `apply_action_receipt`, with `predecessor_id == receiver_id` (the self-call trust pattern many contracts rely on for privileged internal callbacks): [6](#0-5) .

Top-level account names above `min_allowed_top_level_account_length` can be created by *any* predecessor, not only the registrar: [7](#0-6) . Combined with the fact that deleting an account frees its name for reuse by anyone, this lets an unrelated party later create a brand-new contract under the exact same account name that the attacker previously used and deleted, unknowingly inheriting a stale planted callback.

Note: the manual `promise_yield_resume` path is correctly gated — `submit_promise_resume_data` requires `self.account_id` (the caller's own execution context) to equal the receiver, so the original attacker cannot resume the yield once they no longer control that account's keys: [8](#0-7) . The actual reachable trigger is the **automatic timeout path** (`resolve_promise_yield_timeouts`), which requires no signature or actor permission check at all.

### Impact Explanation
This is authorization-escalation across accounts / promises: an attacker-chosen `FunctionCall` action (method name + arguments fixed at yield-creation time) executes against a completely different, later-created contract occupying the same account name, with `predecessor_id == receiver_id`, i.e. appearing as a legitimate self-call. Many NEAR contracts gate privileged internal/owner-only logic behind `assert_self()`/`predecessor_id == current_account_id` checks; this bug lets that trust boundary be forged by a party who no longer owns or controls the account. It also represents a general state-hygiene bug: dangling `PromiseYieldReceipt`/`PromiseYieldTimeout`/`PromiseYieldStatus`/yield-id-mapping trie entries persist indefinitely past account deletion and can be triggered against unrelated future occupants of the account name.

### Likelihood Explanation
Preconditions are all within reach of an unprivileged attacker: (1) create a top-level account of sufficient length (no registrar needed) or any sub-account they control, (2) deploy a contract that calls `promise_yield_create` targeting itself, (3) self-delete the account via `DeleteAccountAction`. No special access, validator, or node privileges are required — only ordinary transactions. The only uncertain step is a third party recreating the exact same account name and deploying a contract with a matching privileged method name/signature before or after the yield timeout fires; this narrows real-world exploitability but the underlying state-hygiene defect (stale trie entries surviving account deletion) is fully reachable and repeatable at will by the attacker.

### Recommendation
`remove_account` (or `action_delete_account`) should also purge any pending `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId` entries for the account being deleted, and either remove or invalidate the corresponding `PromiseYieldTimeout` queue entries (e.g. via a tombstone check in `resolve_promise_yield_timeouts` that verifies the account still exists before synthesizing the `PromiseResume`). Alternatively, disallow `DeleteAccountAction` while the account has any outstanding yielded promises, mirroring the existing checks for locked stake / large storage usage in `action_delete_account`.

### Proof of Concept
Test-loop scenario:
1. Deploy contract `A` to account `X` (long top-level name, self-created, no registrar needed).
2. From `X`, call a method that invokes `promise_yield_create` targeting itself with method `victim_priv_method` and record `data_id`/timeout `expires_at`.
3. Submit `DeleteAccountAction` for `X` (beneficiary arbitrary); assert `remove_account` result and that `TrieKey::PromiseYieldReceipt{receiver_id: X, data_id}` still exists in the post-state trie (demonstrating the gap).
4. Have a different signer create a fresh account `X` (same name) and deploy contract `B`, which defines a privileged method `victim_priv_method` guarded by `assert_eq!(env::predecessor_account_id(), env::current_account_id())`.
5. Advance blocks past `expires_at` and let `resolve_promise_yield_timeouts` run.
6. Assert that `victim_priv_method` on contract `B` executed successfully (i.e. its guarded/privileged branch ran) even though no key belonging to `B`'s owner authorized it — demonstrating the forged self-call.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
