### Title
Unauthenticated reset of the push-tracking reference counter via directly callable `PostReceiveHook`/`PreReceiveHook` RPCs - ([File: internal/gitaly/service/hook/post_receive.go])

### Summary
`HookService.PostReceiveHook` and `HookService.PreReceiveHook` are gRPC-reachable endpoints whose only request validation is `locator.ValidateRepository()`, i.e. "does this repository exist," with no check that the call actually corresponds to a legitimate, in-flight `git-receive-pack` invocation for that repository. This mirrors the reported Solidity bug class: a function that should only be invocable as part of one specific, tightly-coupled workflow (there `burn()` should only run as counterpart to a real `mint()`; here `PostReceiveHook` should only run as the counterpart to a real `PreReceiveHook` triggered by an actual push) is instead callable independently by any caller who can reach the RPC, letting them desynchronize a security-relevant counter.

### Finding Description
Per `doc/hooks.md`, the pre-receive hook "first increments a reference counter that tracks how many pushes are active at the same time" via a call to Rails, and `post-receive` "decrements the reference counter incremented in the pre-receive hook." GitLab uses this counter to know "when a certain repository can be moved" — the counter being non-zero signals an active push in progress and blocks repository relocation. [1](#0-0) 

The `PostReceiveHook` RPC handler only validates that the target repository exists: [2](#0-1) [3](#0-2) 

`PreReceiveHook` similarly only validates the repository before invoking the manager, which itself increments the counter through `m.gitlabClient.PreReceive(ctx, repo.GetGlRepository())`: [4](#0-3) [5](#0-4) 

Notably, a test comment in the codebase itself acknowledges this RPC is reachable over the external API and flags it as a known, unresolved design gap:

> "For now, include the header so the test runs. In the longer term, we should stop serving HookService on the external socket given it is a service intended only to be used internally by Gitaly for hook callbacks." [6](#0-5) 

Because `PreReceiveHook` and `PostReceiveHook` are independent RPCs with no shared session/transaction token binding one call to the other (they are only loosely correlated via the caller-supplied `HooksPayload` environment, which is not cross-checked for having actually gone through a real `PreReceiveHook` invocation with a matching in-flight state), a caller with the ability to invoke `HookService` RPCs directly (bypassing `git-receive-pack`) can call `PostReceiveHook` for an arbitrary repository without ever having called (or successfully completed) the matching `PreReceiveHook`. This decrements Rails' reference counter for that repository below its true in-flight-push count — exactly analogous to the reported bug where any caller could invoke `burn()` and zero out `minted` without having gone through the corresponding `mint()`/deposit flow, corrupting a state variable relied upon by a downstream security check (`calculateMinimumAmountOut`).

### Impact Explanation
The reference counter is the sole signal GitLab uses to determine "the reference counter [is] not at 0, there are active pushes happening," gating whether a repository is safe to move/relocate. [7](#0-6) 
An attacker able to drive this counter to zero (or negative) while a real push is genuinely in flight could cause GitLab to believe it is safe to relocate/move the repository mid-push, risking data loss or corruption of the repository during relocation. This is a security-relevant state-desync issue directly caused by lack of gating on who/what may invoke the hook RPCs — comparable in class (unauthorized manipulation of a state variable gating a downstream security decision) to the reported `burn()` issue, though the concrete blast radius here (repository relocation safety) differs from the reported "loss of funds during a swap."

### Likelihood Explanation
Likelihood is moderate-to-uncertain: exploitation requires a caller to reach `HookService` RPCs directly rather than through the intended `gitaly-hooks` binary spawned by `git-receive-pack`. The existing test comment confirms this RPC is at least reachable through Gitaly's external API socket in some configurations, and the codebase's own authors flag it as an open concern ("we should stop serving HookService on the external socket"). Because I could not fully trace the current production gRPC/Praefect routing configuration (i.e., whether `HookService` is exposed only on an internal socket in all deployment topologies, or protected further by additional token/session correlation not visible in the reviewed files), the exact reachability by an "ordinary" external, unprivileged user is not fully confirmed from the code reviewed.

### Recommendation
- Bind `PreReceiveHook` and `PostReceiveHook` calls to a single server-issued, unforgeable per-push transaction/session identifier (not just a caller-supplied env payload) so that `PostReceiveHook` can only decrement the counter for a session that previously and successfully executed `PreReceiveHook`.
- Restrict `HookService` to Gitaly's internal-only socket (as already recommended in the codebase's own test comments) so it cannot be invoked by arbitrary external gRPC clients.
- Have Rails/`internal/pre_receive` and `internal/post_receive` endpoints validate that decrements are paired with a matching, still-active increment (e.g., using a token returned from `pre_receive` that must be presented to `post_receive`), rather than trusting an unauthenticated decrement request tied only to a repository identifier.

### Proof of Concept
Conceptual (not fully verified end-to-end due to inability to confirm the exact network exposure of `HookService` in a running deployment):
1. Obtain (or bypass) access to Gitaly's `HookService` socket/interface used by `PostReceiveHook`.
2. Call `PostReceiveHook` directly with a `Repository` and a validly-formatted `HooksPayload` for a target repository that currently has a real, in-flight push (whose `PreReceiveHook` already incremented Rails' reference counter).
3. Observe that Rails' reference counter for that repository is decremented by this spurious call, per the decrement logic described in `doc/hooks.md` lines 225-227, even though no legitimate completion of that specific push occurred.
4. If the counter reaches zero while the real push is still in progress, GitLab may consider the repository safe to relocate, which could race with the still-active real push. [8](#0-7)

func (s *server) PostReceiveHook(stream gitalypb.HookService_PostReceiveHookServer) error {
	firstRequest, err := stream.Recv()
	if err != nil {
		return structerr.NewInternal("%w", err)
	}

	if err := validatePostReceiveHookRequest(stream.Context(), s.locator, firstRequest); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	stdin := streamio.NewReader(func() ([]byte, error) {
		req, err := stream.Recv()
		return req.GetStdin(), err
	})

	var m sync.Mutex
	stdout := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.PostReceiveHookResponse{Stdout: p})
	})
	stderr := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.PostReceiveHookResponse{Stderr: p})
	})

	if err := s.manager.PostReceiveHook(
		stream.Context(),
		firstRequest.GetRepository(),
		firstRequest.GetGitPushOptions(),
		firstRequest.GetEnvironmentVariables(),
		stdin,
		stdout,
		stderr,
	); err != nil {
		var exitError *exec.ExitError
		if errors.As(err, &exitError) {
			return postReceiveHookResponse(stream, int32(exitError.ExitCode()), "")
		}

		return postReceiveHookResponse(stream, 1, fmt.Sprintf("%s", err))
	}

	return postReceiveHookResponse(stream, 0, "")
}
