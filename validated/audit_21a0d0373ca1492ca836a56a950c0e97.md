### Title
Snowbridge v1 outbound queue locks user funds/messages permanently when adverse gas-price/exchange-rate conditions make delivery unprofitable, with no way to top up the reward - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
The Opyn report describes a system where a corrective action (liquidation) is capped in value and only executed by an unincentivized third party; when market conditions make the action unprofitable, no one performs it, and the protocol is left holding an uncollateralized/unresolved obligation that the original actor can later exploit or that never gets settled. The exact same "no rational actor will perform underpriced work" pattern exists in the Snowbridge v1 outbound message queue: a fixed relayer reward is baked into a message at commit time, based on `PricingParameters` that governance updates only "every few weeks." If Ethereum gas price or the ETH/DOT exchange rate moves adversely after a message is committed, the baked-in reward can become insufficient for any relayer to profitably deliver it, and — unlike the newer v2 queue — there is no permissionless "tip" call to top up the stale reward on v1. The message (and the assets/state it represents) is then stuck indefinitely.

### Finding Description
`calculate_fee` computes the fee/reward for a message using the pricing parameters known at the time the message is processed: `RemoteFee(Message) = MaxGasRequired(Message) * Params.MaxFeePerGas + Params.Reward`, adjusted by a `Multiplier` and `exchange_rate` [2](#0-1) . This fee/reward is fixed into the `CommittedMessage` at `do_process_message` time (`max_fee_per_gas`, `reward`) and is never revisited afterward [3](#0-2) .

The pallet's own documentation acknowledges that the pricing parameters are only manually refreshed by governance "every few weeks," and that this is explicitly "an interim measure" pending real liquidity-pool-based pricing [4](#0-3) . On the Ethereum settlement side, the relayer is only refunded `Min(GasPrice, Message.MaxFeePerGas) * GasUsed() + Message.Reward` [5](#0-4)  — i.e., the relayer bears any gas price above `MaxFeePerGas`, and the reward can never exceed what was locked in at commit time.

This exact bug class ("relayer reward too low and not profitable to process") is directly documented in the project's own PR history, but the fix (a permissionless tip top-up) was only implemented for the newer v2 pipeline (`snowbridge-pallet-inbound-queue-v2`, `snowbridge-pallet-outbound-queue-v2`, `snowbridge-pallet-system-v2`/`system-frontend`) [6](#0-5) . The v1 `snowbridge-pallet-outbound-queue` — still compiled into the live Bridge Hub Westend/Rococo runtimes (`impl snowbridge_outbound_queue_runtime_api::OutboundQueueApi<Block, Balance> for Runtime`) [7](#0-6)  — has no equivalent top-up entrypoint, confirmed by the absence of any tip/top-up code path in that pallet.

Because delivery via `deliver`/`do_process_message` is a plain message queue with no automatic price re-adjustment or expiry/refund mechanism [8](#0-7) , a message whose baked-in reward becomes economically unattractive (ETH gas spike, ETH/DOT rate move against relayers, or simply stale governance-set parameters) has no unprivileged/permissionless path to be rescued: nobody can raise its reward, and nobody is incentivized to deliver it at a loss. This mirrors precisely the Opyn scenario where the auction cap (collateral) can fall below what a rational liquidator needs to be paid, leaving the position permanently "stuck" absent an admin/governance donation.

### Impact Explanation
Messages in this queue typically represent locked/reserved assets or governance/asset-transfer commands destined for Ethereum. If a message becomes permanently unprofitable to deliver, the corresponding state transition on Ethereum never completes, while the originating side has already deducted/locked/reserved the underlying value. This falls squarely into "permanent user-fund or bridge-state lock" and "public underpriced work that degrades block production or stalls bridge processing" per the impact gate. Because the outbound queue is FIFO within a channel (nonce-incrementing `<Nonce<T>>::try_mutate`) [9](#0-8) , a single stuck, underpriced message can also stall processing/finality-confirmation flow for that channel's queue, amplifying the impact beyond the single message.

### Likelihood Explanation
This does not require a malicious relayer, validator, governance actor, or leaked key — it is triggered purely by ordinary market movement (ETH gas price spikes, ETH/DOT FX volatility) combined with the pallet's own acknowledged multi-week manual governance update cadence for `PricingParameters`. This is an unprivileged, externally-triggerable condition (any user can enqueue a message whose fee becomes stale) rather than an attacker exploit requiring special access, matching the "no malicious peer/relayer/governance actor" requirement of the impact gate.

### Recommendation
Backport the v2 tip/reward-topup mechanism (`snowbridge-pallet-system-frontend` / `outbound-queue-v2` reward primitives) to the v1 `snowbridge-pallet-outbound-queue`, allowing any account (including the original sender) to permissionlessly top up the `reward`/`max_fee_per_gas` of an already-committed, undelivered message. Alternatively, add automatic on-chain re-pricing (e.g., periodic reward escalation tied to elapsed blocks since commit, similar to Dutch-auction fee bumps) so that stuck messages become profitable over time without requiring governance intervention.

### Proof of Concept
1. Governance sets `PricingParameters` (`fee_per_gas`, `exchange_rate`, `multiplier`, `rewards.remote`) at time T0 via `set_pricing_parameters`.
2. A user submits an XCM message that gets queued through `OutboundQueue::validate`/`deliver`, which computes and locks in `fee` and `reward` from the T0 parameters [10](#0-9) .
3. `do_process_message` commits the message with the fixed `max_fee_per_gas`/`reward` fields into `CommittedMessage` [11](#0-10) .
4. Before any relayer submits the corresponding Ethereum transaction, Ethereum gas price spikes (or ETH/DOT rate moves against relayers) beyond the locked `fee_per_gas`/reward.
5. No relayer will submit the delivery transaction, since `Min(GasPrice, MaxFeePerGas) * GasUsed() + Reward` no longer covers real cost.
6. Since governance parameter updates only occur "every few weeks" and there is no permissionless topup for v1, the message (and any funds/state contingent on its delivery) remains stuck indefinitely — no unprivileged actor can force settlement or recover the locked value.

This is analogous to the Opyn liquidation-incentive-elimination bug: a corrective/settlement action with a hard-capped incentive becomes economically irrational under adverse market conditions, and the protocol lacks any permissionless mechanism (beyond a privileged "donate"-equivalent, here governance re-pricing) to restore the incentive, leaving an unresolved and potentially permanently locked obligation.

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);
