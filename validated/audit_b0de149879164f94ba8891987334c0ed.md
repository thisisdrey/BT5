### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiled-contract ABI parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a length value directly from attacker-supplied precompiled-contract call data and use it to size a Java array with no upper bound, mirroring the LibTIFF CVE-2015-7313 pattern of trusting a length field from crafted input to drive a memory allocation.

### Finding Description
The helper methods that decode ABI-encoded arguments for TVM precompiled contracts take the array length straight from the raw `DataWord` at the caller-supplied offset: [1](#0-0) [2](#0-1) [3](#0-2) 

`len = words[offset].intValueSafe()` is used directly as `new byte[len][]` with no comparison against the actual size of `data`/`words`, and no cap analogous to the `MEM_LIMIT`/`checkMemorySize` bound that the ordinary memory-copy opcodes (`CODECOPY`, `EXTCODECOPY`, `CALLDATACOPY`, etc.) enforce before allocating: [4](#0-3) 

By contrast, opcode-level memory copies are protected because the energy-cost calculation runs before the actual copy and throws `Program.Exception.memoryOverflow` once `newMemSize` exceeds the 3 MB `MEM_LIMIT`: [5](#0-4) 
No equivalent gate exists for the `len` values consumed inside `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, so a caller can supply an arbitrary 32-byte word (up to `Integer.MAX_VALUE`) as the "array length" for a precompiled-contract argument.

### Impact Explanation
Any contract deployer or transaction sender able to invoke one of the freeze/vote/resource precompiled contracts (gated behind `VMConfig.allowTvmFreezeV2()`/`allowTvmVote()` in `PrecompiledContracts.getContractForAddress`) that uses these array-extraction helpers can supply a crafted length word to force allocation of an oversized array (e.g. `new byte[Integer.MAX_VALUE][]`), triggering an uncaught `OutOfMemoryError` inside the TVM execution thread that processes the transaction. This is directly analogous to the LibTIFF bug class described in CVE-2015-7313: an attacker-controlled length field drives excessive memory allocation, producing a denial of service.

### Likelihood Explanation
Reaching this code only requires broadcasting a single transaction that calls a TVM contract which, in turn, `CALL`s one of the affected precompiled-contract addresses with a malformed length word — no special privileges are required, matching the "unprivileged transaction broadcaster/contract deployer" reachability criterion.

### Recommendation
Validate `len` against the actual remaining length of `data`/`words` (as `isValidAbiEncoding` already does for other paths) and/or cap it with a bound similar to `EnergyCost.MEM_LIMIT` before allocating `byte[len][]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`.

### Proof of Concept
Craft a transaction that calls a contract invoking one of the freeze/vote precompiled contracts (e.g. via `CALL` to `delegatableResourceAddr` or similar addresses gated by `VMConfig.allowTvmFreezeV2()`), with the ABI-encoded array-length word set to a very large value (e.g. `0x7fffffff`). When `PrecompiledContracts` decodes the argument via `extractBytesArray`/`extractBytes32Array`, the JVM attempts to allocate a correspondingly huge array, throwing `OutOfMemoryError` in the transaction-processing thread.

**Note on uncertainty:** I could not fully confirm from the indexed code whether the TVM/`Runtime` execution wrapper catches `OutOfMemoryError` at a higher level (some other paths in the codebase, e.g. `RLP.java`, explicitly catch `OutOfMemoryError` and rethrow as a bounded `RuntimeException`, but I found no equivalent catch surrounding the `PrecompiledContracts` array-extraction call sites). If such a catch exists further up the call stack, the practical impact would be limited to a failed/reverted transaction rather than a broader node crash — this distinction could not be verified with the tools available in this session.
