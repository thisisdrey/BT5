## Vulnerability Analog Found

### Title
Unbounded/unchecked length field from precompile calldata drives unguarded array allocation and array indexing in `ValidateMultiSign`/`BatchValidateSign`, causing a node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The OpenLDAP CVE-2020-36226 root cause is a `bv_len` value derived from attacker-supplied authzTo data being miscalculated/unvalidated before it is used to size and index a buffer, crashing `slapd`. The java-tron precompiled contracts `ValidateMultiSign` and `BatchValidateSign` (invocable by any smart contract via `STATICCALL`/`CALL` to the fixed precompile addresses) contain the same bug-class: a length word taken directly from user-controlled TVM calldata is used, without an upper bound check, both to allocate a Java array and as a loop bound for further array indexing.

### Finding Description
`PrecompiledContracts.extractBytesArray` and `extractSigArray` compute `len` from the raw calldata word at an attacker-chosen offset: [1](#0-0) 

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
```

`intValueSafe()` returns any value up to `Integer.MAX_VALUE` for a 32-byte word chosen by the caller: [2](#0-1) 

This value flows directly into the array allocation `new byte[len][]` and the subsequent loop `for (int i = 0; i < len; i++) { ... words[offset + i + 1] ... }` with no upper bound check on `len` before use, unlike `extractBytes32Array` and the sibling call sites which do enforce a `MAX_SIZE` check — but only when the `allowTvmSelfdestructRestriction` hard-fork flag is active: [3](#0-2) 

When that flag is off (or for the legacy code path), `extractBytesArray`/`extractSigArray` are invoked without any preceding size check, so `len` can be as large as `Integer.MAX_VALUE`. This leads to either:
1. An `OutOfMemoryError` from `new byte[len][]` (reference array allocation of up to ~16GB on 64-bit JVMs), or
2. An `ArrayIndexOutOfBoundsException` once the loop index exceeds `words.length`, since `words` is a fixed-size array parsed from the actual (bounded) calldata while `len` is attacker-controlled and independent of `words.length`.

Both exceptions are thrown from inside `ValidateMultiSign.execute()`/`BatchValidateSign.doExecute()` **outside** any local `try/catch` that wraps this call, so this is directly comparable to slapd's unguarded length-driven crash in authzTo processing: [4](#0-3) 

### Impact Explanation
This is reachable by any account that can deploy or invoke a smart contract that calls the `ValidateMultiSign` precompile address (or `BatchValidateSign`) with crafted calldata — no special privileges required, matching the "unprivileged transaction broadcaster / contract deployer" reachability requirement. An `OutOfMemoryError`/uncaught `ArrayIndexOutOfBoundsException` thrown while processing a transaction inside the TVM can propagate up through block application in `Manager`, potentially crashing or halting the node processing that block — a denial-of-service impact analogous to the OpenLDAP `slapd` crash.

### Likelihood Explanation
Exploitability is gated by whether `VMConfig.allowTvmSelfdestructRestriction()` is active. On networks where this hard fork has already been activated, the `sigArraySize > MAX_SIZE` guard prevents the unbounded path from being reached. On networks/environments where it is not yet enabled (or via the legacy unguarded branch when disabled), a single crafted contract call reaches the vulnerable, unguarded array-size code with no other prerequisites.

### Recommendation
- Validate `len` in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` against a strict upper bound (e.g., `MAX_SIZE`) unconditionally, not only when `allowTvmSelfdestructRestriction()` is enabled.
- Reject calldata where `len` would make `offset + len + 1` exceed `words.length` before allocating or indexing.
- Wrap the whole precompile body (including the array-extraction calls) in a `try/catch(Throwable)` that fails the call gracefully (returns `false`/`DATA_FALSE`) instead of letting `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` propagate out of VM execution.

### Proof of Concept
Deploy a contract that calls `STATICCALL` to the `ValidateMultiSign` (or `BatchValidateSign`) precompile address with calldata encoding a large value (e.g., `0x7fffffff`) at the position parsed as the signature-array-length word (`words[3]` interpreted offset), while `allowTvmSelfdestructRestriction()` is not active. This drives `extractBytesArray`/`extractSigArray` to execute `new byte[0x7fffffff][]`, triggering an `OutOfMemoryError` (or an `ArrayIndexOutOfBoundsException` for smaller-but-still-out-of-range values) inside precompile execution, unguarded by any catch in `execute()`.

*Note: I was not able to trace, within tool budget, whether a higher-level catch-all exists around precompile invocation in `Program.java`'s call-to-precompile path that might convert this into a contained revert rather than a full node crash; this should be verified before treating the impact as confirmed node-crash severity versus a contained VM exception.*
