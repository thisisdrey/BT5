### Title
StackerDB chunk broadcast before transaction commit in `process_stacker_db_chunks` - (File: stackslib/src/net/relay.rs)

### Summary
`Relayer::process_stacker_db_chunks` calls `self.p2p.broadcast_message(...)` to relay a `StackerDBPushChunk` message to peers immediately after `tx.try_replace_chunk()` succeeds, but the enclosing `tx.commit()` is only called after the entire per-contract loop finishes. If `tx.commit()` fails (e.g., a SQLite I/O error), the chunk(s) that were already broadcast during the loop will not actually be durably persisted locally, since a failed/aborted transaction discards the uncommitted writes.

### Finding Description
In `stackslib/src/net/relay.rs`, `process_stacker_db_chunks` opens one write transaction per StackerDB contract via `self.stacker_dbs.tx_begin(config.clone())?` [1](#0-0) . For each chunk in the batch, it calls `tx.try_replace_chunk(&sc, &md, &chunk.data)`, and on success it immediately constructs a `StackerDBPushChunk` message and calls `self.p2p.broadcast_message(vec![], msg)` — this happens *inside* the per-chunk loop, before the transaction is committed [2](#0-1) . Only after all chunks in the contract's batch have been processed does the code call `tx.commit()?` [3](#0-2) .

This ordering means the "broadcast" of a chunk's storage to the P2P network is not gated on the storage actually being durably committed. If `tx.commit()` subsequently fails and returns an `Err`, the function propagates that error via `?` and returns early — but any chunks that were already broadcast to peers within that same transaction remain broadcast, even though they were never durably written to the local StackerDB replica. This contrasts with the HTTP-upload path in `poststackerdbchunk.rs`, where `tx.commit()` is called and checked for success *before* the ack is marked `accepted: true` and *before* `node.set_relay_message()` is invoked [4](#0-3)  — that path correctly serializes commit-then-relay. The P2P-sync path in `relay.rs` does not follow this pattern.

### Impact Explanation
If the local node's StackerDB transaction commit fails after several chunks in a batch were already relayed via `broadcast_message`, other peers on the network receive and may themselves store/re-relay chunk data that the originating node never durably persisted. This causes peer inconsistency: peers believe the chunk is now part of the canonical StackerDB replica state and will report it in their inventories/`StackerDBChunkInv`, while the node that relayed it either doesn't have it or (on retry) may have a different reconciled state. This is a case of state being relayed across the network without durable local storage succeeding, matching the "network-wide propagation of forged/unstored data" concern.

### Likelihood Explanation
This requires the `tx.commit()` call in `process_stacker_db_chunks` to fail after at least one prior `try_replace_chunk` succeeded within the same batch/transaction — for example, a SQLite disk I/O error, lock contention, or DB corruption condition arising mid-transaction. No attacker action beyond normal StackerDB sync/gossip (which any StackerDB replica peer can trigger by legitimately pushing/serving chunks) is needed to reach this code path; the fault-injection scenario itself (forcing commit to fail) is an operational/environmental condition rather than something a remote attacker directly controls, which limits practical exploitability compared to a pure protocol-level bug. I could not fully verify the internals of `StackerDBTx::commit()` and `try_replace_chunk()` in `stackslib/src/net/stackerdb/db.rs` (their bodies were not retrievable via the available search/read tools due to index limitations), so I cannot conclusively confirm whether `try_replace_chunk` has any additional safeguard that would prevent broadcast-before-durability in practice, or whether the DB layer's transaction semantics fully roll back on commit failure. This uncertainty affects confidence in the exact severity but not the structural code-ordering issue found in `relay.rs`.

### Recommendation
Move `self.p2p.broadcast_message(...)` for each chunk in `process_stacker_db_chunks` to occur only after `tx.commit()` succeeds — e.g., buffer the set of successfully-stored chunks/messages during the loop, call `tx.commit()?` , and only then iterate over the buffered messages and call `broadcast_message` for each, mirroring the commit-then-relay pattern already used in `poststackerdbchunk.rs`.

### Proof of Concept
Rust test plan for `stackslib/src/net/relay.rs`:
1. Construct a `Relayer` with a `NetworkHandle::test_channel` (as in the existing `uploaded_chunk_is_broadcast_without_event_observer` test) and a `StackerDBs` instance whose underlying connection can be made to fail on `commit()` (e.g., wrap/mimic the DB with a test double that returns an `Err` from the transaction's commit call, or force a SQLite failure by closing/removing the underlying file mid-transaction).
2. Call `process_stacker_db_chunks` with a `sync_results` batch containing at least one chunk destined for a valid, configured contract.
3. Assert that `requests.try_recv()` returns `Err(TryRecvError::Empty)` (i.e., no `NetworkRequest::Broadcast(_, StacksMessageType::StackerDBPushChunk(_))` was queued) whenever `process_stacker_db_chunks` returns an `Err` due to commit failure.
4. Currently, because `broadcast_message` is called before `tx.commit()`, this assertion will fail — a `StackerDBPushChunk` broadcast request will be present in the channel even though the function returns an error and the chunk data was not durably committed.
