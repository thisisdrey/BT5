### Title
`mt_resolve_withdraw` trusts an attacker-controlled `token` contract's promise return value to compute the refund, allowing double settlement - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
`mt_resolve_withdraw` computes the amount to re-credit to the withdrawer purely from the JSON value returned by `token.mt_batch_transfer_call(...)`, clamped only by `min(amount)`. Since `token` is an arbitrary `AccountId` supplied by the caller in `mt_withdraw`, an attacker can deploy their own "token" contract that genuinely delivers the withdrawn balance to `receiver_id` while returning `used = [0]`, causing Defuse to re-credit the full amount back into the withdrawer's internal ledger even though the assets were actually delivered.

### Finding Description
The invariant that should hold is: `value debited by self.withdraw() == value actually retained by receiver_id + value re-credited by mt_resolve_withdraw`. In `internal_mt_withdraw` [1](#0-0) , the owner's Defuse-internal balance for `Nep245TokenId::new(token, token_id)` is debited unconditionally before any promise executes. `do_mt_withdraw` then calls `token.mt_batch_transfer_call(receiver_id, token_ids, amounts, ..., msg)` [2](#0-1) , and the resolver trusts the JSON the `token` contract returns to that call to decide `used` vs. `refund`:

```
match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
    Ok(Ok(used)) if used.len() == amounts.len() => used,
    ...
}
...
used.0 = used.0.min(amount.0);
let refund = amount.0.saturating_sub(used.0);
``` [3](#0-2) 

The clamp only guards against `used > amount` (over-reporting), not against `used` being *understated* relative to what the `token` contract actually delivered. In an honest NEP-245 implementation, this return value is produced by the token contract's own internal resolve logic, which is bound to real balance movements it tracks, so the reported `used` cannot diverge from reality. But here `token` is an arbitrary account supplied by the caller in `mt_withdraw`/`internal_mt_withdraw` [4](#0-3) , with no whitelist check. If the attacker deploys `token` themselves, its `mt_batch_transfer_call` can genuinely move real balance to `receiver_id` (also attacker-controlled) while returning a JSON array reporting `used = [0]` regardless of what actually happened, causing `mt_resolve_withdraw`'s `self.deposit(...)` call to re-credit the full withdrawn amount back to the attacker's Defuse balance for that `TokenId` [5](#0-4) .

The identical pattern also exists in the NEP-141 path, `ft_resolve_withdraw`, which clamps `used.0.min(amount.0)` from a trusted `promise_result_checked_json::<U128>` [6](#0-5) .

Note the exploit is bounded to the attacker's own listed `TokenId(token=attacker_contract, ...)`, since `self.withdraw()` only debits the caller's own balance for that specific `TokenId`, and the caller must already hold that Defuse-internal balance for the specific attacker-deployed `token` contract used in the withdrawal.

### Impact Explanation
The result is that `total_supplies`/the owner's internal ledger balance for `TokenId::Nep245(attacker_token, id)` is inflated above the real reserve Defuse actually holds at `attacker_token`, since one credit corresponds to a real deposit and the second credit (the refund) has no corresponding real asset movement into Defuse's custody. This matches "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies" / "a refund or resolver credit that does not match what failed to settle." Because the exploited `TokenId` is scoped to the attacker's own deployed contract, direct extraction of *other users'* real assets requires a second step (e.g. trading the phantom balance to an unsuspecting counterparty via an intent/swap), but the ledger insolvency for that `TokenId` is created purely through this resolver logic and is repeatable at will (attacker can withdraw/re-credit in a loop, limited only by gas/calls per block).

### Likelihood Explanation
The attacker needs only: (1) their own two contracts (a fake NEP-245 "token" and a receiver), (2) a prior legitimate deposit of that fake token into Defuse to obtain internal balance, and (3) a single signed `mt_withdraw`/`execute_intents` call with `msg` set (to trigger the `is_call` / `mt_batch_transfer_call` path). No privileged role, relayer key, or victim key is required — fully reachable by an unprivileged attacker.

### Recommendation
Do not trust the raw JSON return value of `mt_batch_transfer_call`/`ft_transfer_call` unconditionally for computing refunds when the token contract is not a vetted, protocol-controlled contract; alternatively/additionally, verify the actual balance change at the token contract (e.g. via a follow-up balance check `mt_balance_of`/`ft_balance_of` on the Defuse account, or restrict withdrawable `token` accounts to a registered token set) before crediting a refund equal to the reported unused amount.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox):
1. Deploy Defuse contract and a malicious MT contract `evil_token` that: on `mt_batch_transfer_call`, actually performs an internal balance decrement equivalent to a genuine transfer of the requested amount to `receiver_id`, but returns `vec![U128(0); amounts.len()]` from the call regardless.
2. Deploy a malicious receiver contract `evil_receiver` (or reuse `evil_token`'s account) that just implements `mt_on_transfer` returning `0` (unused).
3. As attacker, deposit `100` units of `evil_token`'s token id into Defuse (`mt_on_transfer` -> Defuse credits attacker balance `100`).
4. Assert `mt_balance_of(attacker, TokenId(evil_token,id)) == 100` before withdraw.
5. Call `mt_withdraw(token=evil_token, receiver_id=evil_receiver, token_ids=[id], amounts=[100], msg=Some("..."))` signed by attacker.
6. After promise resolution, assert:
   - `evil_receiver`'s real balance at `evil_token` == 100 (assets actually delivered), and
   - `mt_balance_of(attacker, TokenId(evil_token,id))` on Defuse == 100 again (re-credited), i.e. `100 (delivered) + 100 (re-credited) != 100 (debited)`, violating the invariant. [3](#0-2)
