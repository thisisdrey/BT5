### Title
HookService's PreReceiveHook/PostReceiveHook Can Be Invoked Directly by Any Authenticated Client, Manipulating GitLab's Reference Counter Without a Corresponding Push - ([File: internal/gitaly/hook/prereceive.go])

### Summary
`HookService` (`PreReceiveHook`, `PostReceiveHook`, `ReferenceTransactionHook`) is documented as intended only for internal use — invoked via the `gitaly-hooks` binary during an actual `git-receive-pack` execution — but the RPC handlers themselves perform no verification that the caller is genuinely Git invoking a real hook for an in-progress push. All trust is placed in the `GITALY_HOOKS_PAYLOAD`/`UserDetails`/`Changes` data supplied as ordinary RPC request fields (`EnvironmentVariables`, `Stdin`) by the caller. Any client holding valid Gitaly auth credentials can call `PreReceiveHook` or `PostReceiveHook` directly with a fabricated payload, causing Gitaly to call GitLab's internal `pre_receive`/`post_receive` endpoints (which increment/decrement the project's reference counter) without any real push having occurred — the same "state mutated, real action never happened" pattern as the reported `beneficiaryWithdrawable` bug.

### Finding Description
`HookService.PreReceiveHook` and `PostReceiveHook` are streaming RPCs whose request validation only checks that the `Repository` field is well-formed: [1](#0-0) [2](#0-1) 

The actual "authorization" for whether the hook logic runs (custom hooks + the GitLab reference-counter call) is performed inside `GitLabHookManager.preReceiveHook`, which decodes the `GITALY_HOOKS_PAYLOAD` supplied in `EnvironmentVariables` and the `UserDetails`/`Changes` fields the caller controls, then unconditionally calls the GitLab `Allowed` and `PreReceive` (reference counter) endpoints based on that self-supplied data: [3](#0-2) [4](#0-3) 

Documentation for the hook flow explicitly frames the RPC as being invoked exclusively by `gitaly-hooks` during a real Git hook execution, i.e., only after Git has actually decided to run the hook as part of `git-receive-pack`: [5](#0-4) 

The comments in `pre_receive_test.go` acknowledge the service is "intended only to be used internally by Gitaly for hook callbacks" but is nevertheless served on the external socket: [6](#0-5) 

Because the RPC does not verify that it is being invoked from a live Git hook process for a push actually in flight (e.g. no cryptographic binding of the payload to an active receive-pack/quarantine session, only trust in caller-supplied `EnvironmentVariables`), any caller that can reach `HookService` with a valid token can:
1. Fabricate a `GITALY_HOOKS_PAYLOAD` with arbitrary `UserDetails` and `Changes`.
2. Invoke `PreReceiveHook`/`PostReceiveHook` directly (bypassing `git-receive-pack` entirely).
3. Trigger `gitlabClient.PreReceive`/`PostReceive`, which increments/decrements GitLab's internal reference counter for the repository — the exact "quota reduced without funds transferred" pattern from the reported bug, since no actual reference update ever occurs.

### Impact Explanation
Repeated direct calls can desynchronize GitLab's reference counter from the true state of the repository (analogous to draining/inflating a withdrawal quota with no corresponding transfer). This can cause spurious `git gc`/housekeeping decisions, incorrect concurrent-push serialization on the Rails side, and potentially unblock genuinely-in-flight pushes prematurely or block legitimate ones, since GitLab's push-concurrency logic depends on this counter being accurate.

### Likelihood Explanation
Exploitability depends on whether an ordinary/unprivileged caller (not just Praefect/gitaly-hooks) can reach `HookService` over the external, authenticated Gitaly socket with knowledge of a valid `GITALY_HOOKS_PAYLOAD` format (which is well documented) and a `GlRepository`/`UserID` they know. The test comments confirm the RPC is currently reachable via the external listener rather than being restricted to the internal socket, but I could not fully verify from the indexed code whether additional authorization (e.g. a signed transaction id, `GITALY_HOOKS_PAYLOAD` HMAC, or a known-only-internally socket credential) fully blocks this in the current codebase; this needs a Devin session with terminal/browser access to trace `internal/gitaly/service/setup/register.go` and confirm whether `HookService` is actually registered on the external listener at runtime and whether the referenced GitLab issue (#3746) was resolved.

### Recommendation
Restrict `HookService` (`PreReceiveHook`, `PostReceiveHook`, `ReferenceTransactionHook`, `UpdateHook`, `ProcReceiveHook`) registration to the internal Unix-socket listener only (not the external client-facing listener), and/or bind the `GITALY_HOOKS_PAYLOAD` to a server-generated, single-use transaction/session token that is validated against an active `git-receive-pack` invocation before any GitLab reference-counter or access-check call is made.

### Proof of Concept
Not independently reproducible from the index alone; would require a running Gitaly server to confirm whether `HookService` is exposed on the external listener and whether a crafted `GITALY_HOOKS_PAYLOAD` (constructed with `gitcmd.NewHooksPayload`) sent directly via `PreReceiveHookRequest.EnvironmentVariables`/`PostReceiveHookRequest.EnvironmentVariables` without a genuine `git-receive-pack` invocation triggers `gitlabClient.PreReceive`/`PostReceive` calls, as seen in the test harness pattern: [7](#0-6)

func (m *GitLabHookManager) PreReceiveHook(ctx context.Context, repo *gitalypb.Repository, pushOptions, env []string, stdin io.Reader, stdout, stderr io.Writer) error {
	payload, err := gitcmd.HooksPayloadFromEnv(env)
	if err != nil {
		return structerr.NewInternal("extracting hooks payload: %w", err)
	}

	changes, err := io.ReadAll(stdin)
	if err != nil {
		return structerr.NewInternal("reading stdin from request: %w", err)
	}

	// Only the primary should execute hooks and increment reference counters.
	if isPrimary(payload) {
		if err := m.preReceiveHook(ctx, payload, repo, pushOptions, env, changes, stdout, stderr); err != nil {
			m.logger.WithError(err).WarnContext(ctx, "stopping transaction because pre-receive hook failed")

			// If the pre-receive hook declines the push, then we need to stop any
			// secondaries voting on the transaction.
			if err := m.stopTransaction(ctx, payload); err != nil {
				m.logger.WithError(err).ErrorContext(ctx, "failed stopping transaction in pre-receive hook")
			}

			return err
		}
	}

	if err := m.synchronizeHookExecution(ctx, payload, "pre-receive"); err != nil {
		return fmt.Errorf("synchronizing pre-receive hook: %w", err)
	}

	return nil
}

The `gitaly-hooks` executable is only a gateway to be able to use gRPC and
execute the hook logic inside of the Gitaly server process. It uses the injected
information to connect to Gitaly and execute the respective RPC call. The
execution path is:

1. Gitaly symlinks `pre-receive`, `update`, `post-receive`, and
   `reference-transaction` hooks to the `gitaly-hooks` binary from a
   subdirectory of Gitaly's runtime directory.
1. Git locates the hook using `core.hooksPath`.
1. `gitaly-hooks` connects to Gitaly and executes the corresponding RPC call in
   Gitaly, passing along any hook-specific information to the RPC.
1. Gitaly performs the hook-specific logic in the RPC handler.
