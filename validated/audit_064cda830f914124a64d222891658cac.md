### Title
Positions with debt below `2 * debtFloorInUsd` can never be liquidated due to the `maxLiquidable` cap conflicting with the debt-floor check - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two constraints that are mutually exclusive for a band of positions: the repaid amount cannot exceed `maxLiquidable` (50% by default) of the account's debt-token balance, and the remaining debt after repayment cannot land in `(0, debtFloorInUsd)`. For any account whose debt-token balance is worth less than `2 * debtFloorInUsd`, every possible `amountToRepay_` reverts — small repays trip `RemainingDebtIsLowerThanTheFloor` and full repays trip `AmountGreaterThanMaxLiquidable`. The result is a permanent denial of service of the liquidation function for exactly the small positions the floor was meant to govern, allowing attacker-created bad debt to accumulate against the protocol. This mirrors the CVE-2023-31630 class (crafted input causing a persistent DoS of a core protocol operation). [1](#0-0) 

### Finding Description
In `Pool.liquidate`:

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
``` [2](#0-1) 

`maxLiquidable` is initialized to `0.5e18` (50%) and on the deployed configuration is below `1e18`. [3](#0-2) 

Let `D` be the account's debt in USD for the synthetic token being repaid:

- Any `amountToRepay_` with `amountToRepay_ / _debtTokenBalance > maxLiquidable` reverts. With `maxLiquidable = 0.5e18`, a repay that reduces the balance to zero (or below `maxLiquidable` fraction) is forbidden, so the minimum enforceable remaining balance is `(1 - 0.5) * D = 0.5 * D`.
- Any repay leaving `0 < remainingUsd < debtFloorInUsd` reverts.

When `0.5 * D < debtFloorInUsd`, i.e. `D < 2 * debtFloorInUsd`, **every** permitted repay amount (`≤ 50%` of balance) leaves a remainder below the floor, and every repay above 50% is rejected by the cap. `liquidate` therefore always reverts for such positions. The same contradiction applies to the "close-out" intent of the floor: the position can neither be partially liquidated nor fully closed in one call, because a 100% repay has `wadDiv = 1e18 > maxLiquidable`.

The attacker path is fully permissionless:

1. Deposit collateral via `DepositToken.deposit` (any EOA; `whenNotPaused`, no role gating). [4](#0-3) 
2. Issue synthetic debt in the band `debtFloorInUsd < D < 2 * debtFloorInUsd` via `DebtToken.issue` (floor check at issuance only requires `D ≥ floor`, which this satisfies).
3. Wait for interest accrual (`DebtToken.accrueInterest` grows the balance) or an adverse price move so `debtPositionOf` returns unhealthy — no oracle manipulation is required since interest alone pushes `debtInUsd` above `issuableLimitInUsd` for a position issued near its limit. [5](#0-4) 
4. Any liquidator calling `Pool.liquidate` reverts for all `amountToRepay_` values, permanently. [6](#0-5) 

### Impact Explanation
The liveness invariant of liquidation breaks: a whole class of underwater positions becomes unliquidatable. Because `debtFloorInUsd` is meant to be set to a meaningful value (its only purpose is to prevent dust debt), the `D < 2 * floor` band is non-empty whenever the feature is enabled. An attacker can deliberately manufacture bad debt in this band — the seized collateral would be worth less than the outstanding debt once underwater — and the protocol has no recourse: `repay`/`repayAll` on the attacker's own position is voluntary, and `liquidate` is bricked. Repeated across accounts, this produces protocol insolvency (accepted impact class). At minimum it is a permanent freezing of the seized-collateral liquidation path for those positions.

### Likelihood Explanation
- Preconditions: `debtFloorInUsd > 0` (the feature's intended operating state) and `maxLiquidable < 1e18` (initialized to `0.5e18`). [7](#0-6) 
- Attacker needs only an EOA, collateral, and public calls (`deposit`, `DebtToken.issue`). No privileged role, no oracle manipulation, no fake contracts.
- Cost is bounded by the debt-floor band size and is recyclable across many accounts; interest accrual guarantees positions in this band eventually decay underwater if issued near the limit.
- Caveat: if `debtFloorInUsd` is currently `0` on a given deployment, the bug is latent until the governor enables the floor — I could not verify the live parameter value from the repo alone.

### Recommendation
Resolve the contradiction so the floor does not deadlock small positions. Options:

- Allow full repayment to bypass `maxLiquidable`: treat `amountToRepay_ == _debtTokenBalance` as a permitted close-out (skip the floor check when remaining debt is zero is already handled; the blocker is the cap). E.g. `if (amountToRepay_ != _debtTokenBalance && amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert`.
- Alternatively, enforce `debtFloorInUsd` at issuance such that `D ≥ 2 * debtFloorInUsd` (or ≥ `floor / (1 - maxLiquidable)`), and force-allow full liquidation of legacy positions below the band.
- Add a regression test covering liquidation of positions with `floor < D < 2 * floor`.

### Proof of Concept
Foundry fork test sketch (Hardhat equivalent works against `test/E2E.mainnet.test.ts` fixtures):

```solidity
// Fork mainnet at a recent block; use deployed Pool, a listed DepositToken,
// its underlying, and a DebtToken/SyntheticToken pair.
function test_unliquidatableSmallDebt() public {
    // Precondition: pool.debtFloorInUsd() == F > 0, pool.maxLiquidable() == 0.5e18

    // 1) Attacker deposits collateral and issues debt D with F < D_usd < 2*F.
    underlying.approve(address(depositToken), type(uint256).max);
    depositToken.deposit(collateralAmount, attacker);
    debtToken.issue(syntheticAmount, attacker); // debt usd value in (F, 2F)

    // 2) Push position underwater via interest accrual (or wait / warp).
    vm.warp(block.timestamp + 365 days);
    debtToken.accrueInterest();
    (bool healthy,,,,) = pool.debtPositionOf(attacker);
    assertFalse(healthy);

    // 3) Every liquidation amount reverts.
    uint256 bal = debtToken.balanceOf(attacker);
    for (uint256 pct = 1; pct <= 50; pct++) {
        uint256 amt = bal * pct / 100;
        vm.expectRevert(Pool.RemainingDebtIsLowerThanTheFloor.selector);
        pool.liquidate(synth, attacker, amt, depositToken);
    }
    for (uint256 pct = 51; pct <= 100; pct++) {
        uint256 amt = bal * pct / 100;
        vm.expectRevert(Pool.AmountGreaterThanMaxLiquidable.selector);
        pool.liquidate(synth, attacker, amt, depositToken);
    }
    // Position is permanently unliquidatable -> bad debt remains on the protocol.
}
```

Note: I verified the revert logic, `maxLiquidable` default, and the permissionless entry points from source; I did not confirm the live `debtFloorInUsd` value or whether `DebtToken.issue` enforces a stricter floor (the grep shows floor references exist in `DebtToken.sol` but line-level contents weren't read within the iteration budget). If issuance already requires `D ≥ 2 * floor`, the band is unreachable at creation but still becomes reachable via interest accrual growing an existing debt from just above `2*floor` downward in health terms — the contradiction itself remains a live defect worth fixing.

    function liquidate(
        ISyntheticToken syntheticToken_,
        address account_,
        uint256 amountToRepay_,
        IDepositToken depositToken_
    )
        external
        override
        whenNotShutdown
        nonReentrant
        onlyIfSyntheticTokenExists(syntheticToken_)
        onlyIfDepositTokenExists(depositToken_)
        returns (uint256 _totalSeized, uint256 _toLiquidator, uint256 _fee)
    {
        address _msgSender = _msgSender();

        if (amountToRepay_ == 0) revert AmountIsZero();
        if (_msgSender == account_) revert CanNotLiquidateOwnPosition();

        IDebtToken _debtToken = debtTokenOf[syntheticToken_];
        _debtToken.accrueInterest();

        (bool _isHealthy, , , , ) = debtPositionOf(account_);

        if (_isHealthy) {
            revert PositionIsHealthy();
        }

        uint256 _debtTokenBalance = _debtToken.balanceOf(account_);

        if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
            revert AmountGreaterThanMaxLiquidable();
        }

        if (debtFloorInUsd > 0) {
            uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
                address(syntheticToken_),
                _debtTokenBalance - amountToRepay_
            );
            if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
                revert RemainingDebtIsLowerThanTheFloor();
            }
        }

        (_totalSeized, _toLiquidator, _fee) = quoteLiquidateOut(syntheticToken_, amountToRepay_, depositToken_);

        if (_totalSeized > depositToken_.balanceOf(account_)) {
            revert AmountIsTooHigh();
        }

        syntheticToken_.burn(_msgSender, amountToRepay_);
        _debtToken.burn(account_, amountToRepay_);
        depositToken_.seize(account_, _msgSender, _toLiquidator);

        if (_fee > 0) {
            depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee);
        }

        emit PositionLiquidated(_msgSender, account_, syntheticToken_, amountToRepay_, _totalSeized, _fee);
    }
