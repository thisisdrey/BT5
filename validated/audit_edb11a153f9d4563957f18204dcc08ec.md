### Title
Unbounded `Content-Length`-driven body read causes attacker-controlled memory allocation in `process_event` - (File: `libsigner/src/events.rs`)

### Summary
`process_event<T, E>` reads the entire HTTP request body into a `String` via `request.as_reader().read_to_string(&mut body)` with no size cap, unlike `libsigner::http::decode_http_body`, which bounds chunked bodies against `MAX_MESSAGE_LEN`. Any client that can reach the signer's event-receiver HTTP port (bound by `SignerEventReceiver::bind`) can POST to a recognized URL such as `/stackerdb_chunks` with an attacker-chosen `Content-Length` and force the process to allocate memory proportional to that length.

### Finding Description
`SignerEventReceiver::next_event` dispatches any POST to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` straight into `process_event::<T, E>(request)` at [1](#0-0) . Inside `process_event`, the body is read with: [2](#0-1) 
`tiny_http`'s reader for a request with a declared `Content-Length` will attempt to deliver exactly that many bytes to `read_to_string`, which grows the destination `String`'s buffer to accommodate them — there is no explicit maximum enforced by `process_event` before or during this read. This contrasts with `decode_http_body` in `libsigner/src/http.rs`, which is bounded by `MAX_MESSAGE_LEN` for chunked encodings elsewhere in this codebase's HTTP-handling paths, showing the maintainers are aware such caps are needed but did not apply one here.

The attacker's exact message: a single HTTP POST to a recognized URL (e.g. `/stackerdb_chunks`) with `Content-Length: <huge N>` and a body of (up to) `N` bytes streamed at the attacker's pace. `process_event` will attempt to buffer all `N` bytes into `body: String` before any JSON parsing or validation occurs, so the allocation happens unconditionally regardless of whether the payload is otherwise well-formed.

### Impact Explanation
A single crafted request can force the signer process to allocate an attacker-chosen amount of memory (bounded only by available system memory and any implicit `Content-Length` limits within `tiny_http`), leading to memory exhaustion, OOM-kill, or severe slowdown of the signer process — a remote unauthenticated DoS from one message, matching the Critical category for "remote crash/unauthenticated DoS from few messages."

### Likelihood Explanation
The only precondition is TCP reachability to the port the `SignerEventReceiver` is bound to (configured as the signer's event-listener endpoint, which the node's event dispatcher POSTs to). No secret, signature, StackerDB slot ownership, or other privilege is required to open a TCP connection and issue an HTTP POST with a large `Content-Length`; `next_event` performs no authentication before routing to `process_event`. The attack is trivially repeatable per connection/request.

Caveat: I could not fully verify from the index alone whether `tiny_http`'s own request-size limits (if any exist inside that crate, outside this repo) would bound the read before `read_to_string` sees all `N` bytes — the repository's own code (`process_event`) applies no cap, which is the specific claim under audit and holds true based on the code shown. Whether the signer's event-receiver port is by default bound to a public/remote-reachable interface versus loopback in typical deployments could not be confirmed from the available files, which affects real-world remote exploitability.

### Recommendation
Enforce an explicit maximum body length in `process_event` before reading — e.g., check the `Content-Length` header (or use `request.as_reader().take(MAX_MESSAGE_LEN)`) and reject/drain-and-respond-error requests whose declared or actual body size exceeds a validated maximum (mirroring `MAX_MESSAGE_LEN` used elsewhere, e.g. in `libsigner/src/http.rs`), before allocating the `String` buffer.

### Proof of Concept
1. Bind a `SignerEventReceiver<T>` to a local test address via `bind()`.
2. Open a raw `TcpStream` to that address and send:
   ```
   POST /stackerdb_chunks HTTP/1.1\r\n
   Host: 127.0.0.1\r\n
   Content-Length: 2000000000\r\n
   Content-Type: application/json\r\n
   \r\n
   ```
   followed by streaming (or a large but finite, e.g. 500MB) body bytes.
3. Call `next_event()` on the receiver in a separate thread/process and observe RSS memory growth of the test process proportional to the streamed length, or observe the process hang/OOM as `read_to_string` in `libsigner/src/events.rs:526` attempts to fill a `String` to the declared `Content-Length`, with no early rejection based on any `MAX_MESSAGE_LEN`-style cap.
