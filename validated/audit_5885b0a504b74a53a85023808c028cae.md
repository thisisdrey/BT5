### Title
Protocol fee bypass via NEP-245/IMT tokens structured with `|delta| ≤ 1` in `TokenDiff` intent - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives the protocol fee entirely whenever the traded amount of a `Nep245` or `Imt` token is `≤ 1`, on the assumption that such tokens are NFT-like. However `Nep245` (multi-token) and `Imt` tokens can represent fungible value (e.g., a wrapped fungible token from another `defuse` instance, or a custom MT contract with 0 decimals), so a delta of `1` can carry arbitrary economic value. A user can structure a `TokenDiff` so that the fee-bearing (negative-delta) leg of the swap is always exactly `-1` of such a token, bypassing the fee that should be owed on that value, analogous to the reported `CreditManager.sol` issue where a user manipulates a caller-supplied parameter (`paths[i]`) to minimize the fee/profit computed by the protocol.

### Finding Description
In `execute_intent` for `TokenDiff` [1](#0-0) , the fee is computed per-token via `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` only for negative deltas (token being given away). `token_fee` is defined as: [2](#0-1) 

```rust
pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
    let token_id = token_id.into();
    match token_id {
        TokenIdType::Nep141 => {}
        TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
        // do not take fees on NFTs and MTs with |delta| <= 1
        TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
    }
    fee
}
```

This exemption is correct for `Nep171` (true NFTs, where a unit is always exactly `1` and inherently non-fungible/non-divisible), but incorrect for `Nep245` and `Imt`, which are multi-token standards that can represent arbitrary fungible balances (confirmed by `Nep245TokenId` storing an arbitrary `contract_id` + `mt_token_id` string with no NFT-only constraint, and by tests showing regular fungible tokens being wrapped as `Nep245` across `defuse` instances, e.g. `defuse2_nep245_ft_id` carrying `1000` units of value) [3](#0-2) [4](#0-3) .

The binding broken is **fees owed vs. fees collected**: the economic value transferred (unbounded, since a Nep245 balance of `1` can represent any underlying value depending on the wrapped asset's precision) is decoupled from the fee actually charged (forced to `0` whenever `|delta| ≤ 1`), letting an attacker deliberately keep `|delta| ≤ 1` on the fee-bearing leg to always collect `fees_collected = 0` regardless of trade value, exactly as the analog report describes a user manipulating an input (`paths[i]`) to minimize what the protocol computes as due.

### Impact Explanation
This falls under "fees bypassed" (Critical, per the accepted impact categories): a malicious counter-party in a P2P `TokenDiff` swap, or a solver matching intents, can structure trades on any `Nep245`/`Imt`-typed token so the negative-delta leg is always `1` unit, permanently avoiding the protocol fee on that leg while still moving full economic value (since the corresponding positive-delta leg on the other token is unrestricted). Since `Nep245` is explicitly used to wrap value from bridged/other-`defuse`-instance tokens, real value can be represented with `amount == 1` per unit depending on the wrapped token's decimals/denomination, making this practically exploitable, not merely theoretical for genuine NFTs.

### Likelihood Explanation
High likelihood: any user submitting `TokenDiff` intents controls the `diff` map, including which token is the negative-delta ("token_in") side and its magnitude. No privileged role, relayer, or victim key is required — a normal signer of `TokenDiff` can simply always choose `-1` for the `Nep245`/`Imt` leg of every swap involving a value-bearing MT/IMT token to systematically evade fees.

### Recommendation
Do not blanket-exempt `Nep245`/`Imt` token types from fees based on `amount ≤ 1`. Either (a) only apply the NFT fee exemption to `Nep171`, or (b) require an explicit, contract-level flag/metadata distinguishing genuinely non-fungible `Nep245`/`Imt` token ids (e.g., ids with a per-token supply cap of 1) from fungible ones, and charge fees on all fungible-typed balances regardless of the transferred amount.

### Proof of Concept
1. User wraps/holds a fungible-valued `Nep245` token (e.g. from another `defuse` instance) worth significant value even at `amount = 1` (depends on the wrapped token's decimals).
2. User (or two colluding counter-parties) submits a `TokenDiff` intent where the negative delta on that `Nep245` token id is exactly `-1`, paired with an arbitrarily large positive delta on the other traded `Nep141` token.
3. In `execute_intent`, `Self::token_fee` returns `Pips::ZERO` for the `Nep245` leg because `amount == 1`, so `fees_collected` is `0` for that leg while the counter-party's `Nep141` leg fee (if any) applies only to their own smaller-value negative delta, letting the attacker's full swap value transfer with no fee taken on the `Nep245` side [5](#0-4) .
