## Title
SSRF-analog: unauthenticated peer-supplied `data_url` in P2P Handshake is used unchecked to drive outbound HTTP requests (mempool sync, neighbor RPC) - (File: `stackslib/src/net/chat.rs`)

### Summary
The Stacks P2P `Handshake` message contains an attacker-controlled `data_url` field that is stored verbatim into the peer conversation state and later used by the node to initiate outbound HTTP connections (for mempool sync and generic neighbor RPC), without any restriction on which host/IP the URL may point to in most of these code paths. This mirrors the reported Jenkins GitHub Plugin SSRF pattern: an attacker who can only supply a URL (no other privilege) causes the target system to issue outbound requests to a host of the attacker's choosing.

### Finding Description
`HandshakeData::data_url: UrlString` is a free-form URL field sent by the *remote* peer in the `Handshake`/`HandshakeAccept` message [1](#0-0) . When a handshake is processed, `update_from_handshake_data` copies this attacker-supplied value directly into the local `ConversationP2P.data_url` field with no validation of scheme, host, or IP range: [2](#0-1) 

`validate_handshake` only checks that, for *outbound* connections, the reported `addrbytes`/`port` match the socket peer address — it never validates `data_url` at all [3](#0-2) . Since this equality check does not cover `data_url`, a remote peer that the local node dials out to (an "authenticated, outbound" conversation) can freely set `data_url` to any URL, e.g. `http://127.0.0.1:AdminPort/…` or an internal-only service address.

This `data_url` is later resolved via DNS/parsing (`chat.rs::try_decode_data_url_ipaddr` / DNS lookups) and used to open outbound HTTP connections in at least two places:

1. **Mempool sync** — `mempool_sync_pick_outbound_peer` selects any authenticated, outbound peer's `data_url` and resolves/queries it [4](#0-3) . The only mitigating check is a private-IP-range guard applied at query time, gated by the `private_neighbors` config option [5](#0-4) . If `private_neighbors` is enabled (a documented option for local test/private networks), or the attacker points the URL at a *public* address that the operator did not intend to be queried (e.g., a third‑party server, enabling the node as an SSRF/DoS proxy), the guard does not help.
2. **Generic Neighbor RPC** — `NeighborRPC::send_request` / `NeighborRPC::get_peer_host` builds the outbound request target directly from `convo.data_url` with **no private-range check at all** [6](#0-5) . This path is used broadly for peer-to-peer RPC (e.g., StackerDB chunk fetches, block/microblock inventory requests among Nakamoto peers), and unconditionally calls `PeerNetwork::connect_or_send_http_request` / `HttpPeer::connect_http`, which perform a raw TCP connect + HTTP request to the resolved address [7](#0-6) [8](#0-7) .

The equality broken here is: *the address the node uses to send follow-up application data (`data_url`) is assumed to correspond to the same principal that was handshake-authenticated at `addrbytes`/`port`* — but only `addrbytes`/`port` are checked; `data_url` is fully unvalidated attacker input.

### Impact Explanation
An attacker who is (or becomes) an outbound neighbor of a node — e.g., by being listed/gossiped as a neighbor and having the local node dial them — can set `data_url` to point the node's HTTP client at an arbitrary host:port. Via the `NeighborRPC` path (no private-range filtering at all), this allows the node to be induced into making outbound HTTP requests to internal-only services (bypassing network segmentation) or third-party hosts (making the node a scanning/DoS proxy). This aligns with "High" impact per the scan's own criteria (steering unauthorized network requests via a fully attacker-controlled destination) though it is bounded to sending fixed protocol-shaped HTTP requests rather than fully arbitrary payloads, and does not directly disclose secrets or corrupt consensus state.

### Likelihood Explanation
Any peer that can complete a valid signed `Handshake` (which requires no special credential beyond a secp256k1 keypair — anyone can run a node) can set an arbitrary `data_url`. The `validate_handshake` equality check explicitly does not extend to `data_url`, so this requires no protocol violation to exploit — it is a documented, reachable field with no destination validation on the `NeighborRPC` path.

### Recommendation
- Validate `data_url` at handshake-processing time (`update_from_handshake_data`) to reject or down-rank URLs whose resolved host is in a private/loopback/link-local range, unless explicitly permitted (mirroring the existing `mempool_sync` check).
- Apply the same private/loopback-IP filtering used in `mempool_sync` (`stackslib/src/net/mempool/mod.rs` lines ~488-498) to the generic `NeighborRPC::send_request`/`get_peer_host` path in `stackslib/src/net/neighbors/rpc.rs`, so all outbound HTTP driven by peer-supplied `data_url` is consistently constrained.

### Proof of Concept
1. Run a malicious peer node; have the victim node add it as an outbound neighbor (e.g., via neighbor gossip pointing to the attacker's advertised p2p `addrbytes:port`).
2. When the victim dials the attacker and completes a handshake, the attacker's `HandshakeAccept`/`HandshakeData.data_url` is set to `http://169.254.169.254:80/` or `http://<internal-service>:<port>/`.
3. `update_from_handshake_data` stores this into `convo.data_url` unvalidated (`stackslib/src/net/chat.rs:1147`).
4. Trigger any code path that uses `NeighborRPC::send_request` against this neighbor (e.g., a StackerDB/Nakamoto peer RPC request) — the victim node resolves and connects to the attacker-chosen internal/external host and sends an HTTP request there, confirming SSRF.

            PeerNetwork::with_http(network, |ref mut network, ref mut http| {
                match http.connect_http(
                    network_state,
                    network,
                    data_url.clone(),
                    addr,
                    Some(request.clone()),

                    Ok(event_id) => Ok(event_id),

                        }
                    }
                    Err(e) => Err(e),
