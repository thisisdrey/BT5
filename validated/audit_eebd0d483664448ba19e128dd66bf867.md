## Title
Reward payout marked as claimed before the underlying currency transfer succeeds, permanently locking staking rewards when the transfer fails - (File: `substrate/frame/staking-async/src/pallet/impls.rs`)

## Summary
In `do_payout_stakers_by_page`, `Eras::<T>::set_rewards_as_claimed(era, &stash, page)` is called unconditionally before the actual reward payout is computed and dispatched. When the transfer-based path (`use_dap_payout`) is active, `make_payout_from_provider` performs a `T::Currency::transfer` from the era reward pot to the payee's resolved account; if that transfer fails (e.g., destination account doesn't exist and amount is below the Existential Deposit), the error is only logged and `None` is returned, with no rollback of the already-committed claimed state.

## Finding Description
`do_payout_stakers_by_page` sets the claimed flag at line 386, well before the payout amounts are computed (lines 405-473) and before `payout_from_provider`/`make_payout_from_provider` attempt the actual transfer. [1](#0-0) 

`make_payout_from_provider` performs `T::Currency::transfer(&staker_rewards_pot, &payout_account, amount, Preservation::Expendable)`. If this fails, the error path only logs and returns `None`, without any retry, event, or state rollback: [2](#0-1) 

The caller `payout_from_provider` simply skips emitting the `Rewarded` event and does not increment `nominator_payout_count` when `make_payout_from_provider` returns `None`, but takes no corrective action on the already-set claimed flag: [3](#0-2) 

Because the `AlreadyClaimed` guard checks `Eras::<T>::is_rewards_claimed(era, &stash, page)` unconditionally on re-entry: [4](#0-3) 

there is no way to retry the payout for that `(era, stash, page)` combination once the transfer has failed for any nominator on that page — the funds remain stuck in the era reward pot (`RewardPot::Era(era, RewardKind::StakerRewards)`) with no path to settle to the intended payee. This is corroborated by the codebase's own test suite, which explicitly exercises a related failure mode (`defensive_panic_on_transfer_failure`) showing the authors are aware that pot-drain/transfer failures are a real, reachable condition in this pallet, though that particular test covers the validator incentive path (which panics defensively) rather than the nominator/validator reward path (which silently swallows the failure). [5](#0-4) 

By contrast, the legacy path uses `asset::mint_creating` via `make_payout_legacy`, which cannot fail on a non-existent destination since it creates new supply directly rather than transferring existing balance — confirming this specific failure mode is unique to the newer transfer-based reward-pot payout path.

## Impact Explanation
`payout_stakers` / `payout_stakers_by_page` are public, unprivileged extrinsics callable by anyone for any validator/era/page. Once `use_dap_payout` is active (post `DisableMintingGuard`), any per-nominator reward share that computes to less than the Existential Deposit and targets an unfunded/dead payee account will fail to transfer, yet the page's claimed state is permanently advanced. This matches the "permanent user-fund lock" and payout-settlement-invariant-violation impact category: the claimed-state advances unconditionally while settlement (the transfer) can independently and silently fail, and the affected nominator's reward becomes permanently unclaimable with funds orphaned in the reward pot.

## Likelihood Explanation
This is reachable under ordinary, non-adversarial conditions: nominator rewards are split proportionally via `Perbill::from_rational` across potentially many nominators per page, so small-stake nominators' per-page share can easily fall below ED. `RewardDestination::Account` is set via the standard, unprivileged `set_payee` extrinsic with no validation that the destination can safely receive small transfers, and `payout_account_for_dest` resolves this account directly for the transfer. No malicious actor, governance action, or leaked keys are needed — only routine payout dispatch against ordinary account states, making this readily reproducible and repeatable across eras/pages.

## Recommendation
- Do not advance `Eras::<T>::set_rewards_as_claimed` until the per-recipient transfer in `make_payout_from_provider` has been attempted and its outcome accounted for; consider tracking claimed state per-recipient rather than atomically per-page, or only marking the page claimed after all its constituent transfers have been dispatched (successfully or via a defined fallback).
- On transfer failure in `make_payout_from_provider`, apply a fallback such as topping up the destination to ED from the pot before crediting the reward, or redirecting the undeliverable amount to a designated treasury/fallback account instead of silently dropping it.
- Surface transfer failures via an on-chain event (not just a log) so the failure is observable to affected stakers and operators, and consider exposing a way to retry/reclaim orphaned pot balances.

/// Create a stash and controller pair, where payouts go to a dead payee account. This is used to
/// test worst case payout scenarios.
pub fn create_stash_and_dead_payee<T: Config>(
	n: u32,
	balance_factor: u32,
) -> Result<(T::AccountId, T::AccountId), &'static str> {
	let staker = create_funded_user::<T>("stash", n, 0);
	// payee has no funds
	let payee = create_funded_user::<T>("payee", n, 0);
	let amount = asset::existential_deposit::<T>() * (balance_factor / 10).max(1).into();
	Staking::<T>::bond(
		RawOrigin::Signed(staker.clone()).into(),
		amount,
		RewardDestination::Account(payee),
	)?;
	Ok((staker.clone(), staker))
}
