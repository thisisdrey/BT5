Based on my investigation, I found the strongest analog: `unmarshalDetails` in `cert/cert_v2.go` parses attacker-supplied ASN.1 `groups` and `networks`/`unsafeNetworks` sequences into unbounded Go slices with no cap on the *number* of entries, only on total certificate size and per-entry length.

### Title
Unbounded `groups`/`networks` count in ASN.1 certificate parsing allows resource-exhaustion before CA verification - (File: `cert/cert_v2.go`)

### Summary
`unmarshalDetails` reads `TagDetailsNetworks`, `TagDetailsUnsafeNetworks`, and `TagDetailsGroups` from an ASN.1-encoded certificate `Details` blob and appends each decoded element to a Go slice in an unbounded loop, with no limit on the *number* of elements — only `MaxCertificateSize` (65536 bytes total) and per-entry length caps (`MaxNetworkLength`, entry non-empty) are enforced.

### Finding Description
`unmarshalDetails` (`cert/cert_v2.go:641-745`) loops `for !subString.Empty()` for networks, unsafe networks, and groups, calling `append()` each iteration with no cap on the resulting slice length: [1](#0-0) [2](#0-1) 

This is reached from `cert.Recombine` → `unmarshalCertificateV2`, which is called by `Machine.validateCert` in the handshake state machine — **before** the `CertVerifier` (CA-pool signature check) runs: [3](#0-2) 

Because the attacker fully controls the raw certificate bytes sent in a handshake payload (public key aside), and the packed size limit is only on total bytes (65536) rather than element count, a crafted `Details` blob can pack thousands of minimal-size `groups` (each just a few ASN.1 bytes for a 1-character `UTF8String`) or `networks` entries (each ≥6 bytes) into a single certificate. This is directly analogous to the reported `addReward()`/`rewardTokens` bug class: unauthenticated data drives growth of an array that is later iterated in downstream logic (`Certificate.Groups()`/`Networks()` are iterated per-packet by firewall rule evaluation and by `hostinfo.buildNetworks`), and the cost of processing scales with attacker-chosen list length rather than being bounded by policy.

### Impact Explanation
Every handshake attempt (even from an unauthenticated peer with no CA-signed certificate) forces the responder to fully parse and materialize these slices before any trust decision is made. A crafted oversized `groups`/`networks` list increases per-handshake CPU/memory cost (allocation + iteration during unmarshal and later during `buildNetworks`/firewall rule matching if the handshake proceeds far enough), which can be replayed at high rate since handshake processing on `beginHandshake` runs on every stage-1 packet before signature/CA verification completes. This maps to the report's Medium-severity conclusion: not an outright crash, but a resource-amplification / DoS vector reachable pre-authentication.

### Likelihood Explanation
Likelihood is Medium: reachable by any unauthenticated network peer who can reach the UDP listener and send a handshake stage-1 packet (`HandleIncoming`/`beginHandshake`), requiring no valid CA-signed certificate to trigger the parse path. The 65536-byte total-size cap limits the worst case (bounded, unlike the unbounded on-chain report), but the number-of-elements is not separately capped, so an attacker can still maximize element count within that byte budget to amplify allocation/iteration cost relative to a well-formed certificate.

### Recommendation
Add explicit maximum counts for `networks`, `unsafeNetworks`, and `groups` entries in `unmarshalDetails` (e.g., reject if more than N entries, similar to `MaxNameLength`/`MaxNetworkLength` per-entry caps), and enforce the same bound in the V1 parser (`cert/cert_v1.go`) equivalent (`rc.Details.Groups`, `Ips`, `Subnets`) so certificate-driven slices used later in firewall/group matching cannot grow unbounded from attacker input.

### Proof of Concept
An attacker crafts a Version2 certificate `Details` ASN.1 blob whose `TagDetailsGroups` SEQUENCE contains as many minimal single-character `UTF8String` group names as fit under `MaxCertificateSize` (65536 bytes), then sends it as the certificate payload in a stage-1 handshake packet to a nebula node. `Machine.validateCert` → `cert.Recombine` → `unmarshalCertificateV2` → `unmarshalDetails` will parse and allocate a `groups` slice with thousands of entries before the `CertVerifier`/CA-pool check rejects the (unsigned or untrusted) certificate, at a CPU/allocation cost proportional to the crafted count rather than to a legitimate certificate's typical size.

**Note on scope/uncertainty:** I was unable to locate the `validate()` implementations for `certificateV1`/`certificateV2` in the indexed content (grep for the exact method signature returned no results, possibly due to index truncation), so I cannot fully confirm whether `validate()` imposes any additional count-based limits beyond what's shown above. If a Devin session were started, the full `cert/cert_v1.go` and `cert/cert_v2.go` `validate()` bodies should be reviewed to confirm no such cap exists before treating this as fully confirmed.

func (m *Machine) validateCert(payload Payload) error {
	cred := m.getCred(m.myVersion)
	if cred == nil {
		m.failed = true
		return fmt.Errorf("%w: %v", ErrNoCredential, m.myVersion)
	}
	rc, err := cert.Recombine(
		cert.Version(payload.CertVersion),
		payload.Cert,
		m.hs.PeerStatic(),
		cred.Cert.Curve(),
	)
	if err != nil {
		m.failed = true
		return fmt.Errorf("recombine cert: %w", err)
	}

	if !bytes.Equal(rc.PublicKey(), m.hs.PeerStatic()) {
		m.failed = true
		return ErrPublicKeyMismatch
	}

	// Version negotiation, if the peer sent a different version and we have it, switch
	if rc.Version() != m.myVersion {
		if m.getCred(rc.Version()) != nil {
			m.myVersion = rc.Version()
		}
	}

	verified, err := m.verifier(rc)
	if err != nil {
		m.failed = true
		return fmt.Errorf("verify cert: %w", err)
	}

	m.result.RemoteCert = verified
	m.remoteCertSet = true
	return nil
