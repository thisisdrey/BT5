## Finding: AtlasDB attachment size cap is not enforced when attachments are fetched from remote peers - ([File: stackslib/src/net/atlas/download.rs])

### Summary
The `attachments_max_size` cap that gates all attachment content written to `AtlasDB` is enforced on the locally-submitted path (`POST /v2/transactions`) but is never checked on the network-download path used by `AttachmentsDownloader`. A remote, unauthenticated peer answering a `GET /v2/attachments/{hash}` request can therefore cause an arbitrary-size blob to be written to the requesting node's `AtlasDB`, bypassing the size limit that the rest of the codebase treats as an invariant.

### Finding Description
`AtlasDB::should_keep_attachment` is the single gate that enforces the `attachments_max_size` configuration before content is persisted: [1](#0-0) 

It is called from the client-submitted-transaction path: [2](#0-1) 

However, when a node downloads an attachment from a peer via the Atlas gossip protocol, the response is decoded and inserted directly into the in-memory `attachments: HashSet<Attachment>` with no size check: [3](#0-2) 

and then unconditionally written to the database via `insert_instantiated_attachment`, again with no call to `should_keep_attachment`: [4](#0-3) [5](#0-4) 

`should_keep_attachment` is referenced in exactly three places in the whole repo — the atlas tests and `posttransaction.rs` — never in `download.rs`, confirming the network-fetch path is missing this gate entirely.

This is the same class of bug flagged in the external advisory: a value received untrusted from the network (there: raw X11 bytes interpreted as an arbitrary type without a validating boundary; here: peer-supplied attachment bytes accepted without validating against the size invariant other code paths enforce) is treated as if it had already passed the check that the rest of the system assumes is universal.

### Impact Explanation
Any peer that answers an Atlas `AttachmentRequest` (triggered automatically whenever the requesting node observes an on-chain `AttachmentInstance` event it doesn't yet have) can return a content blob far larger than the configured `attachments_max_size` (default 1 MiB, `ATTACHMENTS_MAX_SIZE_MIN`). Because the hash of the returned bytes is recomputed locally and used to resolve matching `AttachmentInstance`s, the attacker cannot forge content for an arbitrary target hash (this is not a full authentication bypass), but they can still:
- Force the local node to buffer an oversized blob in memory (`self.attachments: HashSet<Attachment>`) during the download batch.
- Force it to be permanently written into the on-disk `AtlasDB` `attachments` table via `insert_instantiated_attachment`, unbounded by the operator-configured cap.

Repeated over many attachment instances/content hashes that appear via BNS/Atlas contract events, this is a per-response bounded-but-uncapped storage/memory amplification vector from an unauthenticated remote party — a write into persistent node state that deliberately bypasses a size invariant enforced elsewhere in the same subsystem.

### Likelihood Explanation
Likelihood is moderate: it requires the target node to be actively syncing Atlas attachments (default enabled for BNS-related contracts) and to select a malicious/faulty peer as a source for a given `content_hash`. No signature, node key, or privileged role is needed — the response only needs to arrive over the ordinary `GET /v2/attachments/{hash}` HTTP flow used for Atlas replication.

### Recommendation
Call `AtlasDB::should_keep_attachment` (or an equivalent size/contract check) on every attachment received from `extend_with_attachments` / before `insert_instantiated_attachment` is invoked in `AttachmentsDownloader::run`/`try_proceed`, so the same invariant enforced for locally-submitted attachments is applied uniformly to network-downloaded ones. Additionally, consider bounding the HTTP response body size for `GET /v2/attachments/{hash}` fetches at the transport layer to `attachments_max_size` before allocation, not just after JSON decoding.

### Proof of Concept
1. Configure a node with the default Atlas config (`attachments_max_size` = 1 MiB).
2. As a malicious peer, respond to the node's `GET /v2/attachments/{hash}` request (issued after the node observes a matching on-chain `AttachmentInstance`) with an oversized hex-encoded JSON body (e.g. tens of MB) whose SHA/RIPEMD160 (`Hash160`) happens to be requested, or simply observe that `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) performs no length check regardless of the eventual hash match.
3. Observe that `AttachmentsBatchStateMachine::try_proceed`'s `Done` branch (`stackslib/src/net/atlas/download.rs:152-169`) calls `network.atlasdb.insert_instantiated_attachment(&attachment)` unconditionally — no call path reaches `should_keep_attachment`, unlike the `posttransaction.rs` flow which explicitly gates on it before acceptance.     pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
