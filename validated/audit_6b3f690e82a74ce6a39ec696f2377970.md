### Title
Attacker can permanently DoS withdrawals and liquidations by dust-filling `feeCollector`'s per-account token set past `MAX_TOKENS_PER_USER` - (File: contracts/Pool.sol)

### Summary
The LibTIFF bug class is "crafted input forces a failed allocation → abort → denial of service." The Metronome analog is `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` whenever `debtTokensOfAccount + depositTokensOfAccount` for a recipient reaches `MAX_TOKENS_PER_USER` (30) [1](#0-0) . Because `DepositToken._transfer` unconditionally adds the token to the recipient's set on a 0→positive balance, anyone can push entries into an arbitrary victim's set by sending dust [2](#0-1) . Since the pool itself caps deposit tokens at 30 [3](#0-2) , an attacker can completely fill the `feeCollector`'s set, making every fee-bearing `_transfer` to it revert — aborting `withdraw`/`flashWithdraw`/`withdrawFrom` and `liquidate` exactly like the malloc-failure abort.

### Finding Description
`DepositToken._withdraw` pays the withdrawal fee via `_transfer(account_, _pool.feeCollector(), _fee)`, which calls `pool.addToDepositTokensOfAccount(feeCollector)` when the collector's balance of that deposit token is zero [4](#0-3) . The same `_transfer` hook is exercised during `Pool.liquidate` → `DepositToken.seize` [5](#0-4) , so any liquidation that credits a new deposit token to the liquidator or feeCollector reverts once their set is full. `addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts at ≥30 combined entries [6](#0-5) . The attacker needs no privileges: they deposit dust in each listed collateral via `DepositToken.deposit(amount_, attacker)` [7](#0-6) , then `transfer(feeCollector, dust)` for each of the 30 deposit tokens. `_revertIfLocked` passes because the attacker has no debt, so `unlockedBalanceOf` returns their full balance [8](#0-7) . Entries can only be removed by driving the collector's balance to zero (`removeFromDepositTokensOfAccount` is only callable by the DepositToken itself on burn/full-transfer), which the feeCollector cannot do for tokens it never interacted with — the state is effectively irreversible by an EOA and requires feeCollector contract support to even attempt.

### Impact Explanation
Once `feeCollector`'s set holds 30 entries: (1) every `withdraw`/`withdrawFrom`/`flashWithdraw` with a nonzero `withdrawFee` reverts — user collateral is frozen in the Treasury; (2) `Pool.liquidate` reverts whenever the seize path must add a token to the liquidator's or feeCollector's set, so liquidations halt and underwater positions accrue bad debt (solvency/liveness invariant broken). The same dust-fill can be targeted at known liquidator addresses or at any user to block their future deposits/borrows (first-touch `issue`/`deposit` reverts). Impact: temporary/permanent freezing of funds and blocked liquidations — matching the "abort → remote DoS" shape of the LibTIFF report.

### Likelihood Explanation
Fully reachable by an unprivileged EOA: `deposit` and `transfer` are public, have no minimum-amount or whitelist checks, and dust transfers cost only gas. No governor, keeper, oracle, or privileged actor is required, and no modifier (`nonReentrant`, `whenNotPaused`, SynthContext `_msgSender`) prevents it — the revert is by design in `onlyIfAdditionWillNotReachMaxTokens`. The only precondition is that the pool lists enough deposit tokens to fill the set (up to 30, the governor-set cap), and that fees are nonzero for the withdrawal/liquidation DoS.

### Recommendation
Do not revert on recipient-set overflow for protocol-mandated transfers (fees, seize). Options: (a) exclude `feeCollector` (and Treasury) from the `addToDepositTokensOfAccount` tracking, or skip the add when the recipient already has a dust/tracked balance the protocol manages; (b) count deposit and debt tokens against the cap separately or raise the bound so it cannot be reached with listed tokens; (c) catch the revert in `seize`/`_withdraw` fee paths and route fees through `transfer`-free accounting.

### Proof of Concept
Foundry fork sketch (syntax approximate; assumes pool with ≥30 deposit tokens or governor-adds):

```solidity
function test_FeeCollectorSetFill_DoS() public {
    address attacker = address(0xA11CE);
    address[] memory dTokens = pool.getDepositTokens(); // <= 30

    // 1) Attacker dust-deposits each collateral and forwards 1 wei of each
    //    msdTOKEN to feeCollector, filling its per-account set to the max.
    for (uint i; i < dTokens.length; ++i) {
        IDepositToken dt = IDepositToken(dTokens[i]);
        deal(address(dt.underlying()), attacker, 1e6);
        vm.startPrank(attacker);
        dt.underlying().approve(address(dt), 1);
        dt.deposit(1, attacker);
        dt.transfer(pool.feeCollector(), 1); // adds dt to feeCollector set
        vm.stopPrank();
    }
    assertEq(pool.getDepositTokensOfAccount(pool.feeCollector()).length
             + pool.getDebtTokensOfAccount(pool.feeCollector()).length, 30);

    // 2) Any user withdraw with withdrawFee > 0 now reverts.
    address user = address(0xB0B);
    IDepositToken dt0 = IDepositToken(dTokens[0]);
    deal(address(dt0.underlying()), user, 100e18);
    vm.startPrank(user);
    dt0.underlying().approve(address(dt0), 100e18);
    dt0.deposit(100e18, user);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    dt0.withdraw(50e18, user); // _transfer fee to feeCollector -> revert
    vm.stopPrank();

    // 3) Liquidations that credit a new deposit token to feeCollector/liquidator
    //    revert identically once their sets are filled.
}
```

Reproduce on a mainnet/Base fork against the deployed `Pool`/`DepositToken` (`VERSION = "1.3.2"`) with `withdrawFee > 0`; the withdraw call must revert with `UserReachedMaxTokens`, confirming funds freezing.

Caveat: whether `Pool.liquidate` credits the protocol fee to `feeCollector` via `seize` on the deployed version was not fully line-verified; the withdrawal DoS path through `_withdraw` → `_transfer(feeCollector)` is confirmed.
