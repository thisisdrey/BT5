## Analog Found

### Title
Unbounded CPU cost in TRC10 asset/exchange listing APIs due to full-store scan and sort regardless of pagination `limit` - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
The ZooKeeper `wchp`/`wchc` bug (CVE-2017-5637) is a classic CWE-400 pattern: a cheap, unauthenticated command triggers server-side work proportional to *total* server state rather than to the requested/returned amount, letting a client spike CPU and starve legitimate requests. java-tron's TRC10 asset-issue and exchange listing paths have the same shape: every call to `getAssetIssuesPaginated()`/`getAllAssetIssues()` (and the exchange equivalents) iterates and sorts the *entire* `AssetIssueStore`/`ExchangeStore` before applying the requested `offset`/`limit`, so the requested page size never bounds the actual cost.

### Finding Description
`AssetIssueStore.getAssetIssuesPaginated()` first materializes the whole asset-issue table via `getAllAssetIssues()` (a full store iteration), then sorts the *complete* list with a `String`-comparator sort, and only afterwards applies the `offset`/`limit` window: [1](#0-0) 

`Commons.ASSET_ISSUE_COUNT_LIMIT_MAX` (referenced inside this class) only caps the *output* page size after the full scan+sort has already been paid for — it does nothing to bound the O(n log n) work that happens on every single request no matter how small `limit` is.

The same "scan-everything-then-answer" shape appears in:
- `Wallet.getAssetIssueByAccount()` and `Wallet.getAssetIssueListByName()`, both of which call `getAllAssetIssues()` and then `filter()` the full list, with **no pagination at all**: [2](#0-1) [3](#0-2) 
- `ExchangeStore.getAllExchanges()`, which is used by `Wallet.getExchangeList()` (backing `/wallet/listexchanges`) and also does a full-store iterate + sort on every call: [4](#0-3) 

All of these are reachable by any unauthenticated/unprivileged HTTP or gRPC client through servlets such as `GetPaginatedAssetIssueListServlet`, `ListExchangesServlet`, `GetAssetIssueByAccountServlet`, `GetAssetIssueListByNameServlet` registered on `FullNodeHttpApiService` and mirrored across the Solidity/PBFT HTTP services and `RpcApiService`: [5](#0-4) [6](#0-5) 

Crucially, the size of the scanned store (`n`) is attacker-controllable: `AssetIssueActuator` permits **any funded account** to issue exactly one TRC10 asset by paying `getAssetIssueFee()`, with no cap on the total number of distinct assets in the store: [7](#0-6) [8](#0-7) 

An attacker can therefore (1) grow `n` cheaply using many funded addresses (each pays only the asset-issue fee, no special permission required), and then (2) repeatedly hit the listing/query endpoints, each of which performs O(n) iteration plus O(n log n) sort on every single call — the requested `limit` has no effect on this cost. This is the direct analog of `wchp`/`wchc`: a low-cost client request forces the server to do work proportional to total accumulated state.

### Impact Explanation
Repeated calls to these endpoints (`/wallet/getpaginatedassetissuelist`, `/wallet/getassetissuebyaccount`, `/wallet/getassetissuelistbyname`, `/wallet/listexchanges`, and their gRPC/Solidity/PBFT equivalents) force full-store scans and sorts on every invocation. As `n` grows (attacker-inflatable via cheap, permissionless asset issuance), the per-request CPU cost grows without bound while the HTTP/gRPC request itself stays cheap to send. Sustained concurrent requests can saturate node CPU, degrading or denying service for legitimate wallet/API/dApp clients — matching the "API the node can no longer serve" impact bucket.

### Likelihood Explanation
The endpoints are exposed by default on full nodes (and mirrored on Solidity/PBFT nodes) and require no special account permission beyond normal transaction signing to grow the underlying data set (issuing an asset only requires funds for the `AssetIssueFee`). `RateLimiterServlet` applies per-endpoint/IP QPS limits, but rate limiting only throttles request *frequency*, not the *cost per request*; it does not fix the underlying algorithmic complexity, so distributed or sustained low-rate traffic from multiple IPs/keys can still accumulate significant CPU cost as the store grows over time.

### Recommendation
- Bound the cost of listing/query paths to the requested page, not to the total store size: maintain an ordered index (e.g., by numeric asset ID or a B-tree/skip-list keyed structure) so pagination can seek directly to `offset` instead of materializing and sorting the entire table (this is already done correctly in `Wallet.getPaginatedExchangeList()`, which computes keys directly via `ExchangeCapsule::calculateDbKey` instead of loading+sorting everything — the same pattern should be applied to `AssetIssueStore.getAssetIssuesPaginated()`).
- Enforce a hard cap on the total number of open-ended (unpaginated) results returned by `getAssetIssueByAccount()` / `getAssetIssueListByName()`, or convert them to paginated variants.
- Consider capping/deprecating unpaginated full-list endpoints (`listexchanges`, `getassetissuelist`) or caching their sorted result with invalidation on state change rather than recomputing per request.

### Proof of Concept
1. From N distinct funded accounts, each submits one `AssetIssueContract` transaction (only requires balance ≥ `getDynamicPropertiesStore().getAssetIssueFee()`), growing `AssetIssueStore` to a large number of entries — this is fully permitted by `AssetIssueActuator.validate()`/`execute()`.
2. Repeatedly call `GET /wallet/getpaginatedassetissuelist?offset=0&limit=1` (or `getassetissuebyaccount`, `getassetissuelistbyname`, `listexchanges`).
3. Each call triggers `AssetIssueStore.getAllAssetIssues()` (full iteration) followed by a full `List.sort()` over all N entries inside `getAssetIssuesPaginated()`, even though only 1 result is requested/returned.
4. Concurrent/sustained requests from multiple senders scale CPU cost with N per request, degrading the node's ability to serve other API/query traffic.

    return Streams.stream(iterator())

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
