### Title
Lack of slippage control (no minimum/expected-amount parameter) in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's on-chain bancor-style AMM pool (`Exchange`) exposes three actuators: `ExchangeTransactionActuator` (trade), `ExchangeInjectActuator` (add liquidity), and `ExchangeWithdrawActuator` (remove liquidity). The trade actuator was hardened with an explicit slippage-protection field (`tokenExpected`), but the inject/withdraw actuators were not given an equivalent protection, so the counter-token amount computed from the live pool ratio at execution time can differ arbitrarily from what the submitter expected when they signed the transaction — the exact bug class described in the external report for `IChiVaultSpell`/`MockIchiVault` deposit/withdraw.

### Finding Description
`ExchangeTransactionActuator` (a trade) validates the received amount against a caller-supplied minimum: [1](#0-0) 

By contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum-amount field. In `ExchangeInjectActuator.execute`, the amount of the counterpart token required is derived purely from the pool's current balances at the moment of execution: [2](#0-1) 

`doValidate()` in the same actuator recomputes this ratio with `BigInteger` but likewise has no upper bound the caller can specify to cap how much of the counterpart token they are willing to spend: [3](#0-2) 

Similarly, `ExchangeWithdrawActuator.execute` returns whatever `anotherTokenQuant` the current pool ratio dictates, with no floor the caller can enforce: [4](#0-3) 

Because a TRON transaction can sit in the pending pool/mempool for some time before being packed into a block, and any account can freely submit `ExchangeTransactionContract` trades against the same pool in the interim, the pool ratio (`firstTokenBalance`/`secondTokenBalance`) used to size the inject/withdraw amounts can shift materially between signing and execution — mirroring the ICHI vault `deposit`/`withdraw` issue where share/token amounts depend on pool state at execution time rather than at signing time.

### Impact Explanation
- For `ExchangeInjectActuator`: the liquidity provider signs a transaction expecting to pair `tokenQuant` of token A with a certain amount of token B; if other trades land first and shift the ratio unfavorably, the actuator will silently pull a larger amount of token B (up to the account's full balance, per `assetBalanceEnoughV2` check) than the provider intended, since there is no way to bound this amount in the request.
- For `ExchangeWithdrawActuator`: a liquidity provider withdrawing token A can receive materially less of token B than expected if adverse trades land first, again with no way to specify a minimum acceptable amount and no revert.
- This can result in unintended loss of funds for exchange creators (the only accounts authorized to inject/withdraw, since `doValidate()` requires `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` — see line 175-177/181-183 of the two actuators), reachable purely by broadcasting a normal signed transaction; no privileged role is required beyond having created one's own exchange pool via `ExchangeCreateContract`.

### Likelihood Explanation
Medium. Exploitation requires an adversary (or even accidental activity) to submit `ExchangeTransactionContract` trades that land between the victim's inject/withdraw transaction being signed and packed into a block — feasible for anyone able to observe pending transactions or simply race normal trading activity on an active pool. The `Exchange`/`ExchangeV2` feature is a legacy but still-live on-chain AMM in java-tron, and any account can create a pool and become its creator, making this reachable without special privileges.

### Recommendation
Add an `expected`/minimum-counterpart-amount field (and optionally an `expiration`/deadline field) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the `expected` field already present in `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` the same way `anotherTokenQuant < tokenExpected` is enforced for trades.

### Proof of Concept
1. Account C creates an `Exchange` pool for tokens A/B via `ExchangeCreateContract` (becoming its `creatorAddress`).
2. C signs an `ExchangeInjectContract` intending to add `tokenQuant` of A, expecting to pay roughly `X` of B based on the pool ratio observed when signing.
3. Before C's transaction is packed, any account submits `ExchangeTransactionContract` trades against the same pool that shift the A/B ratio.
4. C's `ExchangeInjectContract` executes using the now-shifted ratio (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:71-83`), pulling an amount of B far greater than `X` from C's account, with no field in the contract or check in the actuator to cap this or make the transaction revert — analogous to the un-slippage-protected `vault.deposit`/`vault.withdraw` calls in the referenced report.
