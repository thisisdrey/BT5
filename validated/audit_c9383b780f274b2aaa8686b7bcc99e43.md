### Title
Heap buffer over-read parsing untrusted ZIP central directory entries in `ijar` - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads the central directory of an input JAR/ZIP file with no bounds checking against the mapped file length, unlike its sibling `ProcessLocalFileEntry`, which validates every field via `EnsureRemaining()` before reading. This mirrors the ncurses `fmt_entry`/`comp_hash.c` bug class: a length-prefixed record is trusted to describe how many bytes to read/copy, and the reader advances past attacker-controlled offsets without verifying they stay inside the buffer.

### Finding Description
`ProcessCentralDirEntry` is invoked from `InputZipFile::ProcessNext` and `InputZipFile::CalculateOutputLength` to walk every entry of the central directory of an input `.jar`/`.zip` file that `ijar` processes (used when Bazel builds interface jars, e.g. for `java_import`/precompiled jars that can originate from external dependencies fetched over the network): [1](#0-0) 

Inside `ProcessCentralDirEntry`, after checking the 4-byte signature, the code blindly advances the cursor and reads size fields without any `EnsureRemaining`-style validation: [2](#0-1) 

Contrast this with `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every variable-length read (`file_name_length_`, `extra_field_length_`, `compressed_size_`): [3](#0-2) [4](#0-3) 

In `ProcessCentralDirEntry`, `file_name_length`, `extra_field_length`, and `file_comment_length` are read directly from attacker-controlled bytes and used to advance `p` and drive a `memcpy` and an unbounded `while (extra_p != p)` extra-field parsing loop, with no check that these advances stay within `input_file_->Length()` or within the mapped central directory region: [5](#0-4) 

The outer loop (`ProcessNext`/`CalculateOutputLength`) only terminates when a signature check fails; it does not independently bound iteration by `central_dir_size`/`central_dir_entries` from the EOCD record, so a corrupted central directory with either huge length fields or an unterminated/miscounted entry sequence causes the cursor to walk past the mapped file's central directory (and potentially past the end of the underlying mapping) while continuing to dereference memory, producing a heap-based buffer over-read analogous to the ncurses `fmt_entry` bug, where a corrupted hash-table entry's length field was trusted without bounds validation.

### Impact Explanation
An attacker who controls the bytes of a JAR/ZIP file that a build consumes (e.g., a malicious or corrupted archive served from an external dependency source, cache entry, or untrusted branch) can craft a central directory whose length fields cause `ijar`'s reader to read beyond the buffer holding the mapped file. This can crash the `ijar` process (denial of service for the build) or, if the over-read lands on adjacent heap/mapped memory containing sensitive data, leak that memory content into the derived interface-jar filename/attribute processing, which is then observable through processor callbacks and error messages (`errmsg`) or output artifacts.

### Likelihood Explanation
Reaching this code only requires ijar to process a maliciously crafted ZIP central directory, which is straightforward to construct (a normal 46-byte central directory header followed by manipulated `file_name_length`/`extra_field_length`/`file_comment_length` values and no bounds relationship enforced with the EOCD's declared central directory size). No special privileges, credentials, or code execution capability is required — only that the crafted archive reaches ijar as an input, which happens whenever Bazel builds an interface jar from an externally-supplied `.jar`.

### Recommendation
Add explicit bounds validation in `ProcessCentralDirEntry` (and its callers) mirroring `EnsureRemaining()`: verify that `p`, after each fixed and variable-length read (16-byte fixed header, `file_name_length`, `extra_field_length`, `file_comment_length`, and each extra-field sub-record), does not exceed the known end of the mapped file / declared central directory region before dereferencing. Additionally, bound the central-directory iteration loop by the `central_dir_entries` count and `central_dir_size` derived from the EOCD/Zip64 EOCD record rather than relying solely on signature matching to detect termination.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction would: (1) construct a minimal valid ZIP local file header/data, (2) append a central directory entry whose `file_name_length` + `extra_field_length` + `file_comment_length` fields are set such that the computed entry size exceeds the actual bytes remaining before the EOCD record, and (3) invoke the `ijar` binary (or `zip.cc`'s `InputZipFile` API directly in a C++ unit test under `third_party/ijar`) on this crafted file, observing a crash or out-of-bounds read (e.g., under AddressSanitizer) inside `ProcessCentralDirEntry`, in contrast to a `ProcessLocalFileEntry`-style corrupted local header, which is correctly rejected via `EnsureRemaining`.

I was not able to fully confirm from the index alone (1) whether `MappedInputFile` (`third_party/ijar/mapped_file_unix.cc`) maps the file with page-rounded guard bytes that would turn some over-reads into a hard segfault rather than a silent heap-content leak, and (2) whether any downstream caller (e.g., the `ijar` command-line tool wrapper) imposes additional file-size/central-directory consistency checks before invoking `Open()`. These would need to be checked directly in a full repository checkout to determine the precise exploitability boundary (crash-only DoS vs. actual data disclosure).

  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
