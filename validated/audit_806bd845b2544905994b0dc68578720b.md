### Title
TRC10 Exchange pool pricing uses non-strict floating-point Bancor math with zero-fee swaps, enabling cost-free repeated extraction of pool reserves - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The on-chain AMM-like liquidity pool feature of java-tron (`ExchangeTransactionContract` / `ExchangeCapsule`) prices swaps using the legacy `ExchangeProcessor`, which performs the Bancor relay-token formula with Java `double` arithmetic and truncates results to `long` via a hard cast. Because `ExchangeTransactionActuator.calcFee()` returns `0`, any unprivileged account can submit an unlimited number of zero-cost swap transactions against a pool, repeatedly exploiting the double-precision rounding/truncation bias to drain reserves from the pool — the same fundamental bug class as the Allbridge Core incident (price manipulation of an AMM-style liquidity pool leading to fund drainage), but here the manipulation doesn't even need a flash loan since each swap is free and the calculation itself is imprecise.

### Finding Description
`ExchangeTransactionActuator.execute()` computes the amount received from a swap purely through `ExchangeCapsule.transaction()`: [1](#0-0) 

By default `dynamicStore.allowHardenExchangeCalculation()` (accessed via `allowHarden()`) is `0`, so the actuator routes through the legacy, non-strict `ExchangeProcessor` rather than the BigDecimal-based `SafeExchangeProcessor`: [2](#0-1) 

`ExchangeProcessor` performs the relay-token Bancor formula with `double`/`Math.pow`, and truncates the intermediate "issued supply" and final "exchange balance" via a raw `(long)` cast rather than a symmetric rounding rule: [3](#0-2) 

The existence of a parallel, BigDecimal-precise `SafeExchangeProcessor` gated behind the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal confirms the team is aware the default (`ExchangeProcessor`) math is imprecise, yet this hardened path defaults to disabled and must be enabled via SR governance proposal: [4](#0-3) [5](#0-4) 

Critically, `ExchangeTransactionActuator.calcFee()` returns `0`, so swaps against the pool cost nothing beyond ordinary bandwidth/energy for the transaction itself: [6](#0-5) 

The only economic guard is the caller-supplied `expected` slippage parameter, checked against the caller's own transaction: [7](#0-6) 

Since this value is chosen by the attacker themselves, it provides no protection against the attacker's own round-trip manipulation strategy — it only protects the attacker from bad execution, not the pool from the attacker.

### Impact Explanation
An unprivileged account holding any amount of the pooled asset (or TRX) can call `ExchangeTransactionContract` in a tight loop, swapping token A→B and B→A repeatedly at zero protocol fee. Because the double-precision Bancor computation truncates on each leg rather than rounding to preserve the invariant `firstTokenBalance * secondTokenBalance ≈ constant`, each round trip can shift a small amount of value out of the pool in the attacker's favor. Because there is no fee to disincentivize this and no minimum-trade-size/anti-manipulation control, the attack can be automated and repeated across many blocks to fully drain the reserves of a `TRX/TRC10` or `TRC10/TRC10` exchange pool — a direct analog of the Allbridge liquidity-pool drain, resulting in theft of pooled funds from all LPs who injected liquidity via `ExchangeInjectActuator`.

### Likelihood Explanation
High. `ExchangeTransactionContract` is a standard broadcastable transaction type reachable by any signed account with no special permission; `calcFee()==0` removes the normal economic disincentive against high-frequency manipulation; and the default network configuration (`ALLOW_HARDEN_EXCHANGE_CALCULATION == 0`) uses the imprecise `ExchangeProcessor` unless/until a super-representative governance proposal enables the hardened path.

### Recommendation
- Enable `ALLOW_HARDEN_EXCHANGE_CALCULATION` (routing through `SafeExchangeProcessor`) by default, or remove the legacy `ExchangeProcessor` double-math path entirely.
- Ensure swap rounding always favors the pool (round down for amount paid out, round up for amount charged) so repeated round trips cannot be profitable for the caller.
- Reconsider `calcFee()==0` for `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` or add a minimum swap-size / rate-limiting control to make dust-trade manipulation loops economically unviable.

### Proof of Concept
1. An attacker (any unprivileged account) creates or finds an existing TRC10 `Exchange` pool (via `ExchangeCreateContract`/existing pool) with two tokens A/B.
2. Attacker repeatedly submits `ExchangeTransactionContract` transactions with small `quant` values, alternating direction (A→B, then B→A), setting `expected` to values they control themselves (e.g., 1).
3. Each call executes `ExchangeCapsule.transaction(...)` → `ExchangeProcessor.exchange(...)`, whose `(long)` truncation of `double` Bancor math does not preserve the pool invariant precisely.
4. Because `ExchangeTransactionActuator.calcFee()` is `0`, this loop costs nothing beyond bandwidth, so it can be run indefinitely across blocks (as demonstrated by test scaffolding such as `framework/src/test/java/org/tron/core/actuator/ExchangeTransactionActuatorTest.java` and `framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java`, which already show the non-strict math producing non-exact-inverse results across successive `exchange()` calls, e.g. selling then buying back does not return the original quantity — `testSellAndBuy`/`testSellAndBuy2`).
5. Repeating this drains the pool's `firstTokenBalance`/`secondTokenBalance` over time to the attacker's benefit, at the expense of the liquidity providers who funded the pool via `ExchangeInjectContract`.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
