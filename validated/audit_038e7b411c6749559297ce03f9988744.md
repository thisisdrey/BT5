### Title
Society pallet silently accepts partial `repatriate_reserved` transfers on candidate rejection, causing under-collateralized Society pot - (File: `substrate/frame/society/src/lib.rs`)

### Summary
`repatriate_reserved` (and its `Currency` trait definition) is a "best-effort" call: it returns `Ok(remainder)` where `remainder` is the amount that could **not** be moved (e.g., because a lock/freeze on the `slashed` account overlaps the free balance under `Polite` fortitude), rather than returning an error in that case. `Pallet::reject_candidate` in `substrate/frame/society/src/lib.rs` calls this function and only checks that the call returned `Ok(_)` via `debug_assert!(r.is_ok())` — it never inspects the returned `Balance` remainder to confirm the full deposit was actually moved. This is the same bug class as the Compound `enterMarket`/`exitMarket` report: a function that signals partial failure through its return value (instead of reverting/erroring) whose result is never checked by the caller.

### Finding Description
`ReservableCurrency::repatriate_reserved` is documented as: "This is `Polite` and thus will not repatriate any funds which would lead the total balance to be less than the frozen amount... Returns `Ok` with the actual amount of funds moved, which may be less than `value`" [1](#0-0)  The concrete implementation `do_transfer_reserved` clamps `actual` to `min(value, max)` where `max` is the reducible balance under `Polite` fortitude, and returns `value - actual` as the leftover that stayed reserved on the source account [2](#0-1) .

In `Pallet::reject_candidate` (society pallet), the deposit-forfeiture path does:
```
BidKind::Deposit(deposit) => {
    let pot = Self::account_id();
    let free = BalanceStatus::Free;
    let r = T::Currency::repatriate_reserved(&who, &pot, *deposit, free);
    debug_assert!(r.is_ok());
},
``` [3](#0-2) 

This mirrors exactly the flagged bug pattern: the call can "succeed" (`Ok`) while only partially completing the requested transfer, and the caller never checks the returned `Balance` value to detect the shortfall. Additionally, `debug_assert!` is compiled out entirely in release/production builds (the runtimes used in production are built without `debug-assertions`), so even the weak check that exists provides no protection on a live chain.

Other call sites in the same repo that use `repatriate_reserved`/`repatriate_reserved_named` correctly capture and validate the remainder (e.g. `pallet-assets::transfer_ownership` explicitly checks `ensure!(remaining.is_zero(), ...)` after a prior fix documented in `prdoc/pr_12366.prdoc`, and `pallet-indices::transfer` uses the returned `lost` value to adjust the recorded reserved amount) [4](#0-3) [5](#0-4) . `pallet-society::reject_candidate` is the outlier that neither checks nor accounts for a non-zero remainder.

### Impact Explanation
When a candidate's membership bid is rejected, the pallet intends to confiscate the full bid deposit into the Society treasury (`pot`) account. If the candidate account (`who`) has any lock or freeze covering part of its free balance overlapping the reserved deposit (which is achievable by the candidate themselves, e.g. by holding balances that are also locked for staking/vesting or by using another pallet that places freezes/holds on the same account, all without needing any privileged access), `do_transfer_reserved`'s `Polite`/`BestEffort` clamp will only move part of the deposit to the pot, silently leaving the rest reserved on the candidate's own account. The pallet's internal state treats the deposit as fully forfeited (the `Bid`/`Candidacy` record for that account is dropped) with no error and no corrective bookkeeping, meaning:
- The Society's pot receives less than the intended deposit, permanently under-collateralizing group funds.
- The rejected candidate's own account retains reserved funds that the protocol believed were confiscated, effectively letting an unprivileged bidder recover part of the "forfeited" bid.

This satisfies the "theft/unbacked accounting" and "public underpriced/incorrect settlement" categories in the impact gate — the confiscation dispatch settles for the wrong (lesser) amount to the rightful beneficiary (the Society pot) with no reconciliation, and no privileged or adversarial-infrastructure assumption is required.

### Likelihood Explanation
Likelihood is bounded by the precondition that the affected candidate account must hold a lock/freeze/hold that reduces its "reducible" reserved balance under `Fortitude::Polite`. This is realistically achievable by any user who is also, e.g., staking, vested, or otherwise using `pallet-balances` freezes/holds via other pallets on the same account used to bid into Society — an ordinary, permissionless user action, not requiring any privileged actor, relayer, or validator. It does require the attacker/candidate to engineer their own account state before bidding, which is a moderate but fully realistic and repeatable setup.

### Recommendation
In `Pallet::reject_candidate`, capture the returned remainder from `repatriate_reserved` and reconcile the accounting instead of discarding it via `debug_assert!`:
```rust
BidKind::Deposit(deposit) => {
    let pot = Self::account_id();
    let remainder = T::Currency::repatriate_reserved(&who, &pot, *deposit, BalanceStatus::Free)
        .unwrap_or(*deposit);
    if !remainder.is_zero() {
        // handle/attempt to slash or unreserve the leftover from `who`, or emit an event /
        // defensive! so the shortfall is visible and can be remediated, rather than
        // silently dropping funds accounting.
    }
},
```
Follow the pattern already used in `pallet-assets::transfer_ownership` (reject-on-partial) or `pallet-indices::transfer` (adjust recorded amount by the lost portion), and remove reliance on `debug_assert!` for correctness-critical fund accounting since it is a no-op in release builds.

### Proof of Concept
1. Bidder account `A` places a Society bid with `BidKind::Deposit(D)`, reserving `D` tokens via `T::Currency::reserve`.
2. Before the bid is judged, `A` acquires a lock/freeze `L` on part of its free balance (e.g., via `pallet-staking::bond`, `pallet-vesting`, or any pallet using `LockableCurrency`/`fungible::Mutate::hold`) such that, combined with existing free balance, the `reducible_total_balance_on_hold` under `Fortitude::Polite` for `A` is less than `D`.
3. Society governance rejects `A`'s candidacy, invoking `reject_candidate(&A, &BidKind::Deposit(D))`.
4. `do_transfer_reserved` computes `actual = min(D, max) < D` and moves only `actual` to the pot, returning `Ok(D - actual)`.
5. `debug_assert!(r.is_ok())` passes (it is `Ok`), the candidacy/bid record is dropped as fully processed, but the pot only received `actual < D`, and `D - actual` remains reserved on `A`'s own account — unaccounted-for fund loss to the Society pot with no error, event, or reconciliation raised.

		pub(crate) fn do_transfer_reserved(
			slashed: &T::AccountId,
			beneficiary: &T::AccountId,
			value: T::Balance,
			precision: Precision,
			fortitude: Fortitude,
			status: Status,
		) -> Result<T::Balance, DispatchError> {
			if value.is_zero() {
				return Ok(Zero::zero());
			}

			let max = <Self as fungible::InspectHold<_>>::reducible_total_balance_on_hold(
				slashed, fortitude,
			);
			let actual = match precision {
				Precision::BestEffort => value.min(max),
				Precision::Exact => value,
			};
			ensure!(actual <= max, TokenError::FundsUnavailable);
			if slashed == beneficiary {
				return match status {
					Status::Free => Ok(actual.saturating_sub(Self::unreserve(slashed, actual))),
					Status::Reserved => Ok(actual),
				};
			}
