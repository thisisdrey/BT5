Audit Report

## Title
Forced reward push in `unbond` can permanently lock a member's principal stake if the reward transfer fails - (File: `substrate/frame/nomination-pools/src/lib.rs`)

## Summary
`Pallet::unbond` unconditionally calls `Self::do_reward_payout(...)?` before any unbonding state mutation occurs, and `do_reward_payout` performs a push-style `T::Currency::transfer(..., Preservation::Preserve)?` directly to the member's account. Any failure of that transfer — due to account-level constraints unrelated to the pool (frozen/blocked recipient, `MaxFreezes`/`MaxHolds`/`MaxConsumers` limits, or asset-based blacklisting) — aborts the whole `unbond` call, including the member's principal unbonding.

## Finding Description
`unbond`'s doc comment states the reward payout is "not strictly necessary" and done only "for UX" [3](#0-2) , yet the implementation makes it mandatory by propagating the result with `?`: [5](#0-4) . `do_reward_payout` transfers pending rewards from the reward account to `member_account` and propagates any transfer error instead of catching or deferring it: [2](#0-1) . Because this reward payout happens before `bonded_pool.dissolve`, `T::StakeAdapter::unbond`, sub-pool bookkeeping, and `member.try_unbond`, a failing transfer means none of the unbonding state changes occur [6](#0-5) . `bonded_pool.ok_to_unbond_with`, called immediately prior, only checks pool-state/permission conditions and does not validate that the reward transfer will succeed [4](#0-3) , so no existing guard prevents this failure mode.

## Impact Explanation
This is a permanent user-fund lock: a pool member's staked principal becomes permanently unbondable as long as they have nonzero pending rewards and their account cannot accept the reward transfer. Because reward accrual via `reward_pool.update_records` is continuous and automatic, and `claim_payout` follows the identical `do_reward_payout` path, the member cannot escape the pool through any other dispatchable in the pallet once this condition arises.

## Likelihood Explanation
This requires the member's own account to be in a state that rejects the transfer (e.g., asset-based `fungible` `T::Currency` implementation with a freeze/block list, or an account at `MaxFreezes`/`MaxHolds`/`MaxConsumers` capacity). No malicious peer, validator, governance action, or leaked key is required — it is triggered purely by ordinary interaction between pallet logic and account-level constraints, making it a low-to-moderate likelihood but fully unprivileged and externally reachable issue.

## Recommendation
Decouple the mandatory unbonding state transition from the reward-payout transfer:
1. Make the reward-payout step in `unbond` best-effort — handle the `Result` from `do_reward_payout` and skip payout on error (leaving rewards claimable later) instead of propagating with `?`.
2. Alternatively, move to a pull-based reward model where the unbonding flow only updates claimable-reward accounting without invoking the push transfer.
3. Ensure the core unbonding state transition (`bonded_pool.dissolve`, `T::StakeAdapter::unbond`, sub-pool bookkeeping, `member.try_unbond`) is never gated on the reward transfer succeeding.

## Proof of Concept
1. Configure a runtime where `T::Currency` for `pallet-nomination-pools` can reject transfers to a specific account (e.g., an asset-based `fungible` implementation with freeze/block list, or an account already at `MaxFreezes`/`MaxHolds` capacity under `Preservation::Preserve`).
2. Member `A` joins a pool and accrues rewards.
3. Put `A`'s account into a state where `T::Currency::transfer(reward_account, A, pending_rewards, Preservation::Preserve)` returns `Err`.
4. Call `Pools::unbond(RuntimeOrigin::signed(A), A, unbonding_points)`.
5. Observe the call fails at `Self::do_reward_payout(...)?` in `substrate/frame/nomination-pools/src/lib.rs:2283-2288`, with no unbonding state change — `A`'s principal remains locked in the pool, and `claim_payout` fails identically for the same reason.
