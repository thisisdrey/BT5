## Title
Access-key recreation nonce reseed does not preserve the deleted key's nonce, enabling replay of previously-signed transactions against a re-added key with the same public key - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The upstream finding is a signature/authorization-replay bug: a signed artifact (`_insurance` claim) is validated only against fields (`target`, `insured`) that do not bind to the specific state instance it was issued for, so a stale but still-valid signed permission can be replayed once new state is created that matches those loosely-bound fields. The nearcore analog is in the access-key nonce model: NEAR's own documentation states the invariant needed to prevent this class of replay for access keys, but the runtime implementation does not enforce it.

### Finding Description
When an access key is deleted and later re-added with the *same* public key, `nearcore` explicitly documents the required invariant to prevent replay: [1](#0-0) 

> "NOTE: In some cases the access key needs to be recreated. If the new access key reuses the same public key, the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again."

However, `add_regular_key` in the runtime unconditionally reseeds the nonce from the current block height, with no reference at all to any nonce a previously-deleted key with the same public key may have had: [2](#0-1) 

The seed value is computed purely as a function of `block_height`: [3](#0-2) 

Meanwhile, transaction-nonce validation (`verify_nonce`) only rejects a nonce if it is `<=` the *current* access key nonce and enforces an upper bound based on the *current* block height at validation time (not at signing time): [4](#0-3) 

Because a user (or a `FunctionCall` access key holder such as a relayer) is free to sign — but not yet broadcast — a transaction with any nonce up to `current_block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, that signed transaction remains cryptographically valid indefinitely as long as it is not yet consumed. If the account owner deletes that access key (`action_delete_key` / `delete_regular_key`) — e.g., specifically to invalidate a compromised or over-permissioned key — and re-adds a key with the *same public key* shortly afterward (same block or the very next one), `add_regular_key` reseeds the nonce baseline from the current block height alone, ignoring the previous key's nonce. If the reseeded baseline is not already past the withheld transaction's nonce, that old, previously-signed transaction becomes valid again and can be replayed against the newly (re)created key.

This directly mirrors the reported bug class: an authorization credential (signature) is bound to fields that do not fully capture the specific "instance" or "epoch" of permission it was meant to authorize, so recreating the underlying object (the access key, analogous to a new insurance claim/incident) allows an old signed message to be replayed against it.

### Impact Explanation
The most concrete impact is on `FunctionCall` access keys with a finite `allowance`. A dApp/relayer holding such a key could hold in reserve a maximal-nonce, pre-signed transaction that spends the full allowance. If the account owner notices misuse and performs the standard "delete key, re-add key with same public key" remediation/renewal flow (which the docs describe as a normal, supported operation) to reset the allowance, the withheld transaction can still be replayed against the new key/allowance if the block-height-derived nonce seed has not advanced past the withheld nonce. This defeats the security intent of key rotation and can lead to the double-spend/replay of gas/allowance and unauthorized action execution the owner believed had been revoked — matching the "double-spend/replay" and "authorization escalation" acceptance criteria.

### Likelihood Explanation
Exploitation requires the withheld transaction and the delete+recreate to occur within a narrow block-height window (essentially the same or immediately adjacent block), since the nonce seed formula `(block_height-1) * MULTIPLIER` otherwise quickly outpaces any nonce realistically signable at an earlier, lower block height. This narrows the practical window but does not eliminate it — a relayer with a `FunctionCall` key naturally has the opportunity to sign and withhold a transaction just before the owner's revoke-and-reissue transaction lands, especially across chunk/receipt propagation delays. The scenario is squarely within the explicitly-documented invariant nearcore itself calls out as necessary, indicating the protocol authors are aware this exact case must be handled, yet the current implementation of `add_regular_key` does not reference the deleted key's prior nonce at all.

### Recommendation
When creating an access key whose public key matches a public key that previously existed on the account (i.e., was deleted and is now being re-added), persist or otherwise carry forward the maximum nonce ever observed for that `(account_id, public_key)` pair, and seed the new key's nonce to at least that value (in addition to the existing block-height-derived floor). Alternatively, disallow re-adding a public key that was recently deleted within the same "nonce epoch," or bump the deleted key's stored nonce to the current upper bound at delete time so that any recreation always starts from a value at least as high.

### Proof of Concept
1. Account `alice.near` grants a `FunctionCall` access key `PK` with allowance `A` to a relayer.
2. Relayer signs (but does not submit) transaction `T` under `PK` with `nonce = current_block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER - 1` (the maximum currently allowed by `verify_nonce`'s upper-bound check, see `runtime/runtime/src/verifier.rs:229-234`) that spends the full allowance `A`.
3. `alice.near` detects misuse of `PK` and, within the same or next block, submits `DeleteKey(PK)` followed by `AddKey(PK, new_access_key_with_allowance_A')`, per `action_delete_key`/`action_add_key` in `runtime/runtime/src/access_keys.rs`.
4. `add_regular_key` (`access_keys.rs:230-255`) reseeds `PK`'s nonce purely from `initial_nonce_value(block_height)` (`access_keys.rs:46-50`), with no reference to the nonce state of the just-deleted key.
5. If `initial_nonce_value(block_height) <= T.nonce`, the relayer submits the withheld transaction `T`; `verify_nonce` (`verifier.rs:210-237`) accepts it because `T.nonce > current_nonce` and `T.nonce` is still below the new upper bound, allowing `T` to execute against the newly-granted allowance `A'` despite `alice.near`'s attempt to revoke the relayer's prior authorization.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
