The PocketMine-MP issue is a PHP application-layer bug where an uninitialized property is accessed during offline login due to a missing check on the client-supplied `Certificate` field. The closest Go analog would be `crypto/tls` server-side client-certificate handling in `processCertsFromClient` in `src/crypto/tls/handshake_server.go`, since it's the unauthenticated-reachable path that parses attacker-controlled certificate data from an unauthenticated TLS client during handshake.

However, that function explicitly guards every certificate-array access:
- It rejects empty/missing certs with `len(certs) == 0 && requiresClientCert(...)` before requiring a cert [1](#0-0) .
- It gates client-cert verification and PublicKey extraction on `len(certs) > 0` in both the `VerifyClientCertIfGiven` branch and the FIPS/public-key-type switch below it [2](#0-1) [3](#0-2) .
- The caller in `doFullHandshake` similarly only indexes `c.peerCertificates[0]` after checking `len(certMsg.certificates) != 0` [4](#0-3) .
- The TLS 1.3 equivalent `readClientCertificate` in `handshake_server_tls13.go` only accesses `c.peerCertificates[0].PublicKey` inside a block gated by `len(certMsg.certificate.Certificate) != 0` [5](#0-4) .

There's no code path where an unauthenticated TLS client can supply an empty/absent certificate and have the server dereference an unset field, unlike the PocketMine-MP `Certificate` property case. No stretched analogy is warranted here.
