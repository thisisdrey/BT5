### Title
Unauthenticated handshake flood forces uncapped Noise DH computation, enabling CPU-exhaustion DoS of all handshake and tunnel operations - (File: handshake_manager.go, handshake/machine.go)

### Summary
The Sherlock report describes a shared, finite resource (LayerZero gas ETH held by `CrossChainRouter`) that any unprivileged caller can deplete by triggering cheap operations, causing every legitimate cross-chain operation to fail once the resource is exhausted. The analogous reachable surface in this repo is `HandshakeManager.HandleIncoming` / `beginHandshake`, which processes every inbound stage-1 (`msg1`) Noise handshake packet — from any UDP sender, with no prior authentication and no CA-signed certificate required — by constructing a brand-new `handshake.Machine` and running expensive asymmetric Noise DH computation (`machine.ProcessPacket`) before certificate verification/rejection occurs.

### Finding Description
`HandshakeManager.HandleIncoming` only gates on the handshake subtype and a coarse `RemoteAllowList` check (allow-all by default) before dispatching stage-1 packets to `beginHandshake`: [1](#0-0) 

`beginHandshake` then unconditionally builds a fresh `handshake.Machine` and calls `machine.ProcessPacket`, which performs the Noise/X25519 handshake cryptography (Diffie-Hellman operations) — this happens for every syntactically valid stage-1 packet regardless of whether the sender holds a CA-signed certificate: [2](#0-1) 

Only after this expensive computation completes does the code check for a `remoteCert` and route into `validatePeerCert`: [3](#0-2) 

`certVerifier` itself defers to `CAPool.VerifyCertificate`, but that verification is invoked from inside `ProcessPacket` only after the Noise crypto steps have already run: [4](#0-3) 

There is no per-source rate limiting, stateless cookie/proof-of-work challenge, or cost-asymmetric defense before the expensive DH step — a `TODO` even exists elsewhere in this codebase acknowledging missing resource caps for a related but separate subsystem (firewall conntrack), underscoring that resource-exhaustion protections are not systematically implemented: [5](#0-4) 

### Impact Explanation
Because `beginHandshake` performs costly asymmetric cryptography for every unauthenticated stage-1 packet before any certificate/CA validation gate can reject it, a remote attacker with no valid certificate can send a stream of forged `msg1` packets (small, cheap to generate, optionally with spoofed source addresses) to force the target node to continuously perform Noise DH operations. This starves the node's packet-processing path, delaying or preventing legitimate handshakes (`StartHandshake`/`handleOutbound`) and existing tunnel maintenance from completing — a denial-of-service of the same class as the LayerZero report: an attacker with no privileged/authenticated state exhausts a resource (here, CPU/handshake-processing capacity rather than ETH) that all legitimate cross-node operations depend on, causing tunnel establishment failures across the mesh.

### Likelihood Explanation
Likelihood is high in principle because the only gate before the expensive computation is a remote allow-list, which is permissive by default (`AllowAll`/`AllowUnknownVpnAddr`), and the handshake packet format is fixed and easy for any attacker to craft without holding a certificate. However, this analog is a "hint-driven" architectural comparison rather than a directly proven, exploited condition in this snapshot — the exact per-packet CPU cost of `ProcessPacket` and whether any implicit sender-based throttling exists elsewhere in the UDP receive loop was not fully verifiable within the available index, so real-world severity depends on unverified aspects of the surrounding listener loop.

### Recommendation
Add a cheap, stateless pre-check (e.g., a HMAC-based cookie/proof-of-work challenge similar to WireGuard's, or a per-source-IP token bucket) in `HandshakeManager.HandleIncoming` before dispatching to `beginHandshake`, so that expensive Noise DH computation is only performed after a lightweight anti-flood check. Additionally, consider capping total in-flight pending handshakes (`hm.indexes`) and adding metrics-driven alerting/backpressure so cert-less senders cannot force unbounded computational work.

### Proof of Concept
Not executed against a live instance; based on static code-path analysis: any client can send repeated valid-format stage-1 (`msg1`) Noise handshake packets (`header.HandshakeIXPSK0`, `MessageCounter == 1`, `RemoteIndex == 0`) to a target's listening UDP port. Each such packet reaches `beginHandshake` → `machine.ProcessPacket`, incurring full Noise DH cost, before any certificate is validated, as shown in the cited code paths above.

func (hm *HandshakeManager) HandleIncoming(via ViaSender, packet []byte, h *header.H) {
	// Gate on known handshake subtypes. Unknown subtypes (or future ones we
	// don't yet support) are dropped here rather than silently routed through
	// the IX path. Add a case when introducing a new pattern.
	switch h.Subtype {
	case header.HandshakeIXPSK0:
		// supported
	default:
		hm.l.Debug("dropping handshake with unsupported subtype",
			"from", via, "subtype", h.Subtype)
		return
	}

	// First remote allow list check before we know the vpnIp
	if !via.IsRelayed {
		if !hm.lightHouse.GetRemoteAllowList().AllowUnknownVpnAddr(via.UdpAddr.Addr()) {
			hm.l.Debug("lighthouse.remote_allow_list denied incoming handshake", "from", via)
			return
		}
	}

	// First message of a new handshake. The wire format requires RemoteIndex
	// to be zero here (the initiator has no responder index to fill in yet),
	// and generateIndex never allocates 0, so any non-zero RemoteIndex on a
	// stage-1 packet is malformed or someone probing for an index collision.
	// Drop without paying the cost of running noise on a pending Machine.
	if h.MessageCounter == 1 {
		if h.RemoteIndex != 0 {
			hm.l.Debug("dropping stage-1 handshake with non-zero RemoteIndex",
				"from", via, "remoteIndex", h.RemoteIndex)
			return
		}
		hm.beginHandshake(via, packet, h)
		return
	}

func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}

func (hm *HandshakeManager) certVerifier() handshake.CertVerifier {
	return func(c cert.Certificate) (*cert.CachedCertificate, error) {
		return hm.f.pki.GetCAPool().VerifyCertificate(time.Now(), c)
