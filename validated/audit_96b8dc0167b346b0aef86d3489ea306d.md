### Title
Precision loss in witness brokerage/reward split due to premature floating-point division - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward()` splits every block reward and transaction-fee reward between a witness's own brokerage cut and the shared delegator reward pool. The brokerage percentage is first divided by 100 as a `double`, then multiplied by the reward value and truncated to `long`. Performing the division before the multiplication (and using floating-point instead of integer/BigInteger math) causes the same class of rounding loss described in the referenced report, where `fee` should be computed by multiplying first and dividing last.

### Finding Description
`payReward` is invoked for every block reward and every transaction-fee reward paid to a super representative: [1](#0-0) 

```java
public void payBlockReward(byte[] witnessAddress, long value) { ... payReward(witnessAddress, value); }
public void payTransactionFeeReward(byte[] witnessAddress, long value) { ... payReward(witnessAddress, value); }

private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
```

`brokerage` is an integer percentage (0–100). Computing `brokerageRate = brokerage / 100` first produces a `double` that, for most percentages, is not exactly representable in binary floating point (e.g. `20/100 = 0.2` is a repeating binary fraction). The subsequent multiplication `brokerageRate * value` and truncation to `long` therefore loses precision exactly like the report's `feePct` intermediate — division is performed in the middle of the calculation instead of at the end. The mathematically equivalent, precision-preserving form would be integer/BigInteger math performed as `(brokerage * value) / 100`, multiplying first and dividing only once at the end.

Unlike the analogous bandwidth/energy calculations in this codebase (`BandwidthProcessor`, `EnergyProcessor`, `RepositoryImpl`), which have been hardened with `BigInteger`-based "multiply-then-divide" replacements guarded by `allowHardenResourceCalculation()`/`hardenCalculation()`, no such hardened path exists for `payReward`'s brokerage split.

The legacy `computeReward(long cycle, List<Pair<byte[], Long>> votes)` reward-distribution path has the same class of issue (`voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;`), though it's only used for cycles prior to `newRewardAlgorithmEffectiveCycle`: [2](#0-1) 

### Impact Explanation
`payReward` runs on every single block (`payBlockReward`) and every transaction-fee distribution (`payTransactionFeeReward`) for every active/standby witness, driven from block application/maintenance in `Manager`/`MaintenanceManager`. The floating-point truncation systematically under- or over-allocates the brokerage cut versus the shared delegator pool on every call, permanently leaking or misallocating a small fraction of TRX reward each time. Given the enormous number of blocks processed over the chain's lifetime, this compounds into a continuous, protocol-wide loss/misallocation of witness/delegator rewards — directly analogous to the "lost fees" impact in the original report, occurring without any privileged or malicious actor involvement.

### Likelihood Explanation
This is not an edge case — it triggers unconditionally on every block reward and every transaction fee reward for every witness, for as long as `allowChangeDelegation` reward accounting is active (which is the current mainnet default). No attacker action, special parameters, or malicious actor is required; it is a deterministic consequence of the block-reward flow reachable purely through normal chain operation (block application).

### Recommendation
Replace the `double`-based brokerage split with integer/`BigInteger` arithmetic that multiplies before dividing, mirroring the hardened patterns already used elsewhere in the codebase (e.g. `RepositoryImpl.calculateGlobalLimitV2`, `ResourceProcessor.calculateGlobalLimitV1`):

```java
long brokerageAmount = BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100))
    .longValueExact();
```

Guard the change behind a hardening flag (consistent with `allowHardenResourceCalculation`) if backward-compatible parity with historical results is required, and apply the same fix to the legacy `computeReward(cycle, votes)` double-based `voteRate` calculation.

### Proof of Concept
Given `brokerage = 33` (33%) and `value = 100` (sun):
- Current code: `brokerageRate = 33.0/100 = 0.33` (not exactly representable in binary floating point) → `brokerageAmount = (long)(0.33 * 100)` — for larger, realistic `value` magnitudes (reward values are commonly in the range of `10^7`–`10^9` sun), the double rounding error accumulates to a non-trivial integer sun difference versus the exact result.
- Correct calculation: `(100 * 33) / 100 = 33` exactly, with no rounding error introduced by an intermediate division.

Because this executes on every block/transaction-fee reward for every witness for the lifetime of the chain, the aggregate discrepancy between the double-based and integer-exact brokerage splits represents continuously leaked/misallocated value between witnesses and their delegators, matching the "Lost fees due to precision loss" pattern in the source report.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
