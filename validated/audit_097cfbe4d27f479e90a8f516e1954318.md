### Title
`remove_account` fails to purge PostponedReceipt/PromiseYieldReceipt/ReceivedData family keys, allowing a self-planted receipt to fire against a later-recreated account of the same name - ([File: core/store/src/utils/mod.rs -> remove_account])

### Summary
`remove_account` only removes 4 of the 12 `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` column families for an account: `Account`, `ContractCode`, `AccessKey` (via `get_raw_prefix_for_access_keys`, which also nets `GasKeyNonce`), and `ContractData` (via `get_raw_prefix_for_contract_data`) [1](#0-0) . The remaining 8 columns — `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` — are never swept, even though `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` explicitly documents all 12 as account-scoped rows [2](#0-1) . Because NEAR permits deleting and later recreating an account of the same name, this lets an attacker plant a dormant, self-authored postponed/yielded action receipt (e.g. containing `AddKey`) that survives `DeleteAccount` and later fires against whatever new account occupies that name, executing the attacker's stale actions without any re-authorization.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) validates storage size and gas-key balance, then calls `remove_account`, sets `*account = None`, and returns [3](#0-2) . Nowhere in this path (or in `remove_account`) is there a check for outstanding `PostponedReceipt`/`PromiseYieldReceipt` entries keyed to the account being deleted. Compare `remove_account`'s cleanup set — `Account`, `ContractCode`, iterate `get_raw_prefix_for_access_keys` (covers `AccessKey` + `GasKeyNonce`), iterate `get_raw_prefix_for_contract_data` (covers `ContractData`) — against the account-scoped column list, which additionally includes `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` [4](#0-3) .

All 8 missing columns are reachable by an ordinary, unprivileged account through normal host functions before self-deletion:
- `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`/`ReceivedData` are written whenever an account receives an `ActionReceipt` with unmet `input_data_ids` — the standard cross-contract-call/callback pattern (`process_action_receipt`, `runtime/runtime/src/lib.rs:1593-1658`) [5](#0-4) .
- `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` are written by the `promise_yield_create`/`promise_yield_resume` host-function pair, a standard unprivileged SDK feature (`set_promise_yield_receipt`, `set_promise_yield_status`, `set_yield_id_mapping` in `core/store/src/utils/mod.rs:200-334`) [6](#0-5) .

Exploit flow: an attacker deploys a contract on account A (their own subaccount, unprivileged). A calls `promise_yield_create` targeting itself with a batch of actions that includes `AddKey(attacker_key2, FullAccess)`, obtaining and privately storing the yield's `data_id`. This persists `PromiseYieldReceipt{A, data_id}` (containing the pending `AddKey` action), `PromiseYieldStatus{A, data_id}`, and `YieldIdToDataId`/`DataIdToYieldId{A, ...}` in state. A then self-deletes via `DeleteAccountAction`. Because `remove_account` does not clear these four columns, they remain in the trie under the byte-key prefix for account A even though `Account{A}` itself is gone. If account A's name is later reused — recreated by the attacker themselves, or (in scenarios where the name changes hands, e.g. a marketplace/relinquish-and-reclaim flow, or the attacker briefly recreates and funds it before "handing it off") — a resuming `PromiseResume` receipt whose `data_id` matches will still find `get_promise_yield_receipt(state_update, account_id, data_id)` populated (`runtime/runtime/src/lib.rs:1514-1562`), because that lookup is a pure keyed trie read that never checks whether the current `Account{A}` is the "same" logical account that existed when the yield was created [7](#0-6) . The stale receipt (with the attacker's planted `AddKey` action) is then executed via `apply_action_receipt` against whatever account currently sits at that name, silently granting the attacker a full-access key on it.

Existing checks do not stop this: `action_delete_account` only validates storage-usage size and gas-key balance sums, not pending postponed/yield state [8](#0-7) ; `apply_action_receipt`'s "account did not exist" handling only guards the moment of *execution*, not the earlier deletion, and once the account is recreated it "exists" again so that guard does not fire [9](#0-8) .

### Impact Explanation
This is an **authorization escalation across (recreated) accounts** — an unprivileged attacker can plant and later trigger arbitrary actions (most severely `AddKey` for full-access, but also `Transfer`/`FunctionCall`/further `DeleteAccount`) against a *different, later* occupant of a previously-owned account name, without any signature or access-key check being re-run at trigger time. Depending on how the reused name later accrues funds (deposits, staking rewards routed by name, contract redeployments under the same account id), this can lead to theft or takeover of funds credited to that account after recreation — matching NEAR's "authorization escalation across accounts" and "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions: (1) attacker needs to own/control an account that they intend to delete and see reused (trivially true for any subaccount they create themselves, or any top-level account they briefly hold), (2) attacker must be able to trigger the resume (`promise_yield_resume`/matching `Data` receipt) at a time of their choosing — since they created the yield, they retain the `data_id` off-chain and can fire it at any future point (subject to the yield timeout window, which is configurable up to the protocol's max timeout). Cost is minimal (one contract deployment + a few standard cross-contract-call/yield transactions, all normal gas costs). It is fully repeatable and requires no validator, node, or peer privileges — only standard transaction submission to a public RPC endpoint.

### Recommendation
Extend `remove_account` to also purge, for the account being deleted:
- All `PostponedReceipt` / `PostponedReceiptId` / `PendingDataCount` entries scoped to that `receiver_id` (requires an equivalent prefix-iteration helper, e.g. a new `trie_key_parsers::get_raw_prefix_for_postponed_receipts`/`get_raw_prefix_for_received_data` analogous to the existing access-key/contract-data prefix iterators).
- All `PromiseYieldReceipt` / `PromiseYieldStatus` / `YieldIdToDataId` / `DataIdToYieldId` entries scoped to that `receiver_id`.
- All `ReceivedData` entries scoped to that `receiver_id`.

Alternatively (or additionally, as defense in depth), have the `PromiseResume`/`Data` receipt handling paths verify that the account which originally produced the postponed/yield receipt is still logically "the same" account (e.g. by keying on account creation nonce/generation) before re-executing stale planted actions against a currently-existing account of the same name.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
