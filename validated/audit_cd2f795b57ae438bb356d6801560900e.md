### Title
Exchange creator can front-run trader swaps by injecting/withdrawing reserves with no minimum-hold time or price guard - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
Any account can create a Bancor-style TRX/TRC10 exchange pair via `ExchangeCreateContract` and become its `creatorAddress`. That creator, at any time and with no cooldown or timelock, can broadcast `ExchangeInjectContract` or `ExchangeWithdrawContract` transactions that instantly change the pool's `firstTokenBalance`/`secondTokenBalance`, and therefore the exchange rate used by `ExchangeCapsule.transaction()`. This is functionally identical to the reported "owner can change fee/exchange parameters right before a user's transaction lands" pattern: an unprivileged-but-permissioned actor (the pool creator, analogous to the vault "owner") can manipulate a market-rate parameter immediately before/after a victim's trade with zero delay protection.

### Finding Description
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` only require that the caller is the exchange's `creatorAddress` [1](#0-0) [2](#0-1) . There is no timelock, minimum holding period, or maximum single-transaction impact limit on these operations — the creator can inject or withdraw an amount up to `dynamicStore.getExchangeBalanceLimit()` in a single call [3](#0-2) , instantly re-basing `firstTokenBalance`/`secondTokenBalance` used by the constant-product/Bancor formula in `ExchangeCapsule.transaction()` [4](#0-3) .

Meanwhile, a normal trader's `ExchangeTransactionContract` only enforces a lower bound (`expected`) on the output amount at validation time [5](#0-4) , with no upper bound or reference-price/oracle check tied to when the trader observed the market rate. Because Inject/Withdraw and Transaction contracts execute atomically inside a block with no minimum inclusion delay between them, the pool creator can watch the mempool for a pending trader swap, then submit an `ExchangeInjectContract`/`ExchangeWithdrawContract` to shift the reserve ratio just before the victim's `ExchangeTransactionContract` is packed, extracting value up to the victim's slippage tolerance (`expected`) — a classic sandwich/front-running attack enabled purely because reserve-changing operations have no timelock or rate-of-change limit, exactly the root cause flagged in the external report ("owner can frontrun... use a timelock to avoid instant changes of the parameters").

### Impact Explanation
Any trader interacting with an `ExchangeTransactionContract` pool can have value siphoned by the pool's creator through instantaneous, uncapped reserve manipulation, resulting in unauthorized extraction of trader funds (theft) without requiring any privileged SR/witness/committee role — the creator is any ordinary account that funded the pool's creation fee.

### Likelihood Explanation
High: creating an exchange pool and injecting/withdrawing are ordinary, permissionless actuator calls available to any account; front-running via mempool observation plus adjacent-block-slot submission is a well-known, low-cost, repeatable technique, and the `expected`-only lower-bound check in `ExchangeTransactionActuator` provides no protection against price manipulation happening between broadcast and execution.

### Recommendation
Add a minimum holding/cooldown period (timelock) between `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` operations, or bound the maximum reserve-ratio change permitted per block/transaction, and consider adding a maximum acceptable price parameter to `ExchangeTransactionContract` (not just a minimum `expected`) so traders can bound both directions of slippage.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create a TRX/TOKEN pool and becomes `creatorAddress`.
2. Victim broadcasts `ExchangeTransactionContract` to sell TRX for TOKEN with `expected` set to the minimum they'll accept based on the currently observed rate.
3. Before the victim's transaction is packed, attacker broadcasts `ExchangeWithdrawContract` (or `ExchangeInjectContract`) removing/adding a large share of one token's reserve, shifting the exchange rate unfavorably for the victim within the bound still satisfying `anotherTokenQuant >= tokenExpected`.
4. Victim's `ExchangeTransactionActuator.execute()` proceeds and receives close to the bare minimum `expected` instead of the fair market rate observed at broadcast time [6](#0-5) .
5. Attacker calls `ExchangeInjectContract`/`ExchangeWithdrawContract` again to restore the reserve ratio, pocketing the difference extracted from the victim's trade.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
