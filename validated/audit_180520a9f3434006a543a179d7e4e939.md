### Title
Dust msdToken transfers fill victim's `MAX_TOKENS_PER_USER` slots, blocking new collateral deposits and enabling forced liquidation - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once an account's combined deposit+debt token list reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Any `DepositToken._transfer` or `_mint` where the recipient has a zero prior balance permissionlessly appends that token to the victim's list [2](#0-1) . This mirrors CVE-2023-20882's class: an unprivileged action wrongly evicts/exhausts a healthy resource (the victim's collateral slots), causing a denial of service — here, the ability to top-up collateral, leading to liquidation.

### Finding Description
`DepositToken.transfer` is a public, permissionless entry point gated only by `_revertIfLocked` on the *sender* [3](#0-2) . On the receiving side, `_transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero [2](#0-1) , and `addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens(account_)` [4](#0-3) .

Attack:
1. Attacker deposits dust amounts of underlying into N distinct `DepositToken`s of the same pool (or uses `deposit` then transfers), obtaining transferable msdTOKEN balances.
2. Attacker calls `msdToken_i.transfer(victim, 1 wei)` for enough distinct deposit tokens so that `depositTokensOfAccount[victim].length + debtTokensOfAccount[victim].length == 30`.
3. Any subsequent operation that would add a *new* token to the victim's list reverts with `UserReachedMaxTokens`:
   - `DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount` for any collateral the victim doesn't already hold [5](#0-4) .
   - `DebtToken.issue` → `_mint` → `addToDebtTokensOfAccount` for any new synthetic debt [6](#0-5) .
   - Incoming transfers/seizures of any new msdToken to the victim.

There is no opt-in or whitelist on receiving msdTokens, and no way for the victim to prevent the list from being filled.

### Impact Explanation
The invariant broken is liveness of collateral management. If the victim's position drifts unhealthy (price move or interest accrual via `accrueInterest`/`debtIndex` [7](#0-6) ), the victim cannot deposit additional collateral of a token type not already in their list — the standard remedy to avoid `Pool.liquidate` [8](#0-7) . The attacker can then liquidate the victim for profit, causing direct loss of user funds (seized collateral via `depositToken_.seize`). Even without liquidation, the victim's ability to deposit/issue is frozen until they manually burn/transfer out the dust tokens — a temporary freezing of funds/functionality. Note withdrawals of existing balances still work (`_burn` removes entries [9](#0-8) ), so impact is bounded to blocked new positions plus forced-liquidation losses.

### Likelihood Explanation
Fully unprivileged: requires only an EOA depositing dust collateral and calling `transfer`. Cost is bounded by the number of distinct deposit/debt tokens in the pool (up to 30) and dust amounts; front-running a victim's `deposit`/`issue` transaction guarantees the revert. No privileged role, oracle manipulation, or timing assumption is needed beyond normal liveness of the mempool.

### Recommendation
Do not count tokens added via unsolicited inbound transfers toward `MAX_TOKENS_PER_USER`, or move the cap check out of the revert path: e.g., let `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` silently skip (not revert) when at capacity and only enforce the cap on user-initiated `deposit`/`issue`, or track "counted" slots separately from balance-bearing tokens. Alternatively, allow the account owner to prune zero/dust entries, or compute deposit/debt enumeration lazily instead of via a bounded set.

### Proof of Concept
Hardhat sketch (real `Pool` + two or more real `DepositToken`s):

```ts
// setup: pool with depositTokens dt1..dt30, victim holds dtA collateral + debt
// attacker deposits 1 wei of underlying into dt1..dt(30 - k) where k = victim's current list length
for (const dt of fillers) {
  await underlying.mint(attacker.address, 1)
  await underlying.connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, attacker.address)
  await dt.connect(attacker).transfer(victim.address, 1) // adds dt to victim's list
}
// victim's list is now at MAX_TOKENS_PER_USER
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
// oracle price moves down → position unhealthy → victim cannot add new collateral
await expect(pool.connect(liquidator).liquidate(victim.address, synth.address, repayAmt, depositToken.address))
  .to.emit(pool, 'PositionLiquidated')
```

Reproducible on a mainnet/Base fork against deployed `Pool` (VERSION 1.3.2) [10](#0-9) .
