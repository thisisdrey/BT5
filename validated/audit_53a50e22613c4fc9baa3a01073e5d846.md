### Title
Dust deposit-token transfers permanently fill a victim's `depositTokensOfAccount` set up to `MAX_TOKENS_PER_USER`, blocking all new collateral deposits and inbound transfers - (`contracts/Pool.sol`)

### Summary
`Pool` caps the combined number of deposit tokens and debt tokens an account may hold at `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Every first-time credit of a deposit token — via `DepositToken.transfer`, `transferFrom`, `deposit(onBehalfOf_)`, or `seize` — calls `pool.addToDepositTokensOfAccount(recipient)`, which reverts with `UserReachedMaxTokens` once the cap is hit [2](#0-1) . An attacker can permissionlessly `transfer` 1-wei dust of each deposit token to any victim address, filling all 30 slots and making every subsequent "new token" deposit to, or transfer to, that account revert.

### Finding Description
`DepositToken._transfer` unconditionally adds a deposit token to the recipient's per-account list whenever the recipient's previous balance was 0 and the amount is non-zero [3](#0-2) . The recipient is never asked for consent: `transfer` only checks `_revertIfLocked` on the **sender** [4](#0-3) , and `deposit` accepts an arbitrary `onBehalfOf_` beneficiary [5](#0-4) . Entries are removed only when the balance returns to exactly zero [6](#0-5) , and only the victim can remove them (by transferring the dust out). This mirrors the reported bug class — repeated attacker-initiated actions lock out a victim account from further use of the feature.

### Impact Explanation
- The victim cannot deposit any additional collateral type (`DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount` reverts). An underwater victim holding only other assets cannot add a new collateral to save a position, and their position is forcibly liquidated — indirect loss of funds.
- Any `transfer`/`transferFrom`/`seize` crediting the victim with a token they don't already hold reverts, freezing inbound positions.
- The lockout is persistent until the victim notices and manually transfers the dust out of each token (costing gas and requiring them to know the attack), so it is at minimum a temporary freezing of protocol functionality against the victim's will.

### Likelihood Explanation
- Fully unprivileged: only requires public `DepositToken.transfer` calls with dust amounts.
- Cost is bounded: the attacker must first `deposit` real collateral to obtain msdTOKEN balances, but only dust quantities are needed and the collateral remains withdrawable by the attacker afterwards, so the effective cost is gas only.
- Requires the pool to have enough deposit-token offerings (or the victim having near-30 slots via debt tokens) to reach the cap; with N listed collaterals the attacker can occupy up to N slots.
- Limitation: the victim's existing funds are never frozen — `withdraw` and outbound transfers keep working — so the impact is denial of new deposits/inbound transfers rather than direct fund locking, keeping this in the medium/low range.

### Recommendation
- Remove spammed entries automatically: when crediting, don't count (or auto-evict) tokens below a dust threshold, or track a `nonZeroBalance` flag.
- Alternatively, make the victim's first credit opt-in (e.g., only add to the list on `deposit`/`seize` where the account is a protocol-relevant position, not on bare `transfer`), or drop `MAX_TOKENS_PER_USER` by iterating only over tokens actually needed for health checks.

### Proof of Concept
Hardhat-style reproduction against the deployed contracts:

```ts
// victim starts with 0 msd tokens; pool has >= MAX_TOKENS_PER_USER listed DepositTokens
const victim = bob.address;
for (const dt of depositTokens) { // each DepositToken listed in the Pool
  // attacker deposits a tiny amount of underlying for itself
  await dt.connect(attacker).deposit(1n, attacker.address);
  // dust-transfer to victim -> occupies one slot in depositTokensOfAccount[victim]
  await dt.connect(attacker).transfer(victim, 1n);
}
// Now: depositTokensOfAccount[victim].length === MAX_TOKENS_PER_USER

// 1) victim cannot deposit a collateral type they don't already hold
await expect(
  someOtherDepositToken.connect(bob).deposit(1000n, bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 2) nobody can transfer a new deposit token to victim
await expect(
  someOtherDepositToken.connect(alice).transfer(victim, 1n)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Relevant code paths: `DepositToken._transfer` adding to the per-account list [7](#0-6) , `Pool.addToDepositTokensOfAccount` enforcing the cap [8](#0-7) , and the revert modifier [2](#0-1) .
