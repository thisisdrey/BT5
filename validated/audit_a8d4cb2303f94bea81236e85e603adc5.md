### Title
Silent `long` truncation overflow in witness reward-per-vote (Vi) accumulation enables corrupted/inflated reward crediting - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
java-tron's DPoS reward accounting uses a "value-per-vote" (`Vi`) accumulator pattern that is structurally identical to the Sherlock `pointsPerShare` bug class: a per-cycle delta is computed by scaling a reward amount up by a large fixed constant and dividing by a small, attacker-influenceable "shares" denominator (a witness's total vote count), then accumulated indefinitely in `BigInteger`. When that inflated accumulator is later multiplied by a (potentially large) voter's own vote count and converted back with a non-exact `longValue()` call, the result can silently wrap instead of throwing, corrupting the credited reward.

### Finding Description
The core accumulation logic lives in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`: [1](#0-0) 

`DECIMAL_OF_VI_REWARD` is a fixed `10^18` scaling constant: [2](#0-1) 

For each cycle, `deltaVi = reward * 10^18 / voteCount`. `voteCount` is the witness's total vote count for that cycle, which is fully attacker-controllable: `VoteWitnessActuator` only rejects `voteCount <= 0`, allowing a witness to be voted for with as little as `1` (i.e., minimal frozen TRX), which becomes the witness's `totalVote` for a cycle if no one else votes for it: [3](#0-2) 

If that low-vote witness earns any reward that cycle (block reward or a share of the standby pool), `deltaVi` for that single cycle can become astronomically large (reward × 10^18 / 1). This `deltaVi` is added to a running `BigInteger` `Vi` value that is persisted forever and never bounded: [4](#0-3) 

Later, when any voter's reward is computed (including a voter who joins later with a much larger stake, or the same low-vote holder claiming/withdrawing across a cycle range that includes the inflated cycle), the code does:

```
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
```

This exact pattern appears in three independent reward paths: [5](#0-4) [6](#0-5) [7](#0-6) 

`BigInteger.longValue()` (unlike `longValueExact()`) does **not** throw on overflow — it silently truncates to the low 64 bits, which can produce an arbitrary, potentially negative, `long`. Because `deltaVi` can be inflated to values far exceeding `Long.MAX_VALUE / userVote`, and `userVote` for later/other voters is not bounded relative to the historical tiny `voteCount` that produced the inflated `deltaVi`, the final `reward` value credited via `adjustAllowance`/`accountCapsule.setAllowance(...)` can be a corrupted, wrapped number instead of the intended bounded value.

### Impact Explanation
This directly parallels the reported bug class: an attacker can, with a single cheap transaction (`VoteWitnessContract` broadcast, or the TVM `VoteWitnessProcessor` native contract path), vote for a witness with the minimum non-zero vote count, causing that witness's `Vi` value to be inflated for any cycle in which it earns even a small reward. Any subsequent reward computation that spans that cycle (via `MortgageService.withdrawReward/queryReward`, `VoteRewardUtil.withdrawReward/queryReward` reachable from TVM voting precompile, or the async `RewardViCalService`) can then produce a corrupted `long` reward amount due to the un-checked `.longValue()` truncation. This can result in an account being credited with an incorrect (unbacked) allowance/balance, or a legitimate voter's reward being lost/negative — i.e., theft or freezing of funds through unbacked-balance creation, which the rules explicitly treat as in-scope impact for stake/delegation/reward math.

### Likelihood Explanation
Reachability requires only unprivileged, single-transaction actions: freezing a minimal TRX amount and casting `VoteWitnessContract` votes (or the equivalent TVM `vote` precompile call) for a witness with very few or zero other voters. Getting that witness to actually earn a reward requires it to be an elected SR or one of the up-to-127 standby witnesses for at least one cycle — plausible on private/consortium/test networks or networks with fewer active participants than SR/standby slots, and always possible for a witness a colluding/self-controlled account manages. The subsequent multiplication-by-larger-vote and truncating `longValue()` conditions are a natural, reachable consequence of the existing multi-cycle accumulation design, not a contrived edge case.

### Recommendation
- Replace `.longValue()` with `.longValueExact()` (or explicit bounds checks) in `MortgageService.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`/`accumulateWitnessVi`, and `VoteRewardUtil.computeReward`, so an overflow throws instead of silently truncating.
- Enforce a sane minimum total-vote/stake threshold before allowing a witness's `Vi` to be updated from a reward against a near-zero `voteCount`, to prevent `deltaVi` from becoming arbitrarily large in the first place.
- Consider capping/validating `Vi` deltas or rewards against expected bounds before persisting.

### Proof of Concept
1. Attacker freezes the minimal amount of TRX (enough to satisfy `FreezeBalanceActuator`'s minimum) and submits `VoteWitnessContract` (or the TVM `vote` precompile) voting `1` for witness `W`, which currently has no other voters, giving `totalVote(cycle, W) = 1`.
2. Witness `W` earns any nonzero reward in that cycle (block reward or standby-pool share) via `MortgageService.payReward` → `delegationStore.addReward(cycle, W, value)`.
3. `RewardViCalService`/`DelegationStore.accumulateWitnessVi` computes `deltaVi = reward * 10^18 / 1`, a huge value, and persists it into the cumulative `Vi(cycle, W)` `BigInteger`.
4. Later, a legitimate large-stake voter votes for `W` in a subsequent cycle, increasing `totalVote` substantially, and both continue voting for `W` across the next cycles.
5. When either voter withdraws/queries their reward spanning a cycle range that includes the inflated cycle, `computeReward` executes `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD).longValue()`. With `deltaVi` inflated and `userVote` large, the intermediate value can exceed `Long.MAX_VALUE`, and `longValue()` silently wraps to an incorrect (possibly negative) `long`, which is then added to the account's `allowance` via `adjustAllowance`, corrupting the credited/stored reward balance.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
