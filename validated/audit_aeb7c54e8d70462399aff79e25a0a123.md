Confirmed: `ExchangeInjectContract` (unlike `ExchangeTransactionContract`) has no user-supplied bound field. This is the strongest analog to the reported `SolverVault.deposit()` issue.

### Title
Missing maximum/expected-output bound in `ExchangeInjectActuator` allows users to be debited more of the paired token than intended due to TOCTOU on the exchange ratio - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectContract` lets an account inject `quant` of one token of a bancor-style `Exchange` pair; the actuator computes the required amount of the paired token (`anotherTokenQuant`) proportionally to the pool's live ratio at execution time and deducts it from the signer's balance. Unlike `ExchangeTransactionContract`, which carries a caller-supplied `expected` field validated against the computed output [1](#0-0) , `ExchangeInjectContract` has no equivalent bound field [2](#0-1) .

### Finding Description
The root cause mirrors the reported bug class: a value computed from mutable on-chain state at execution time (the amount of "another token" a user must pay/receive) is used without letting the caller cap it in the transaction they sign.

In `ExchangeInjectActuator.doValidate()`/`execute()`, `anotherTokenQuant` is derived purely from the exchange's current `firstTokenBalance`/`secondTokenBalance` ratio and the caller's `tokenQuant`: [3](#0-2) 

That `anotherTokenQuant` is then subtracted directly from the account's balance/asset, with no user-supplied ceiling anywhere in `ExchangeInjectContract`: [4](#0-3) 

Because a transaction is signed offline and can sit in the mempool or be reordered relative to other `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` calls on the same pool before being packed into a block, the pool ratio (and thus `anotherTokenQuant`) at broadcast time can differ from the ratio at execution time. The user has no way to bound how much of the second token they are willing to spend, unlike `ExchangeTransactionActuator`, which explicitly validates `anotherTokenQuant >= tokenExpected` from the `expected` field the caller supplies [5](#0-4) , and unlike `ExchangeWithdrawActuator`, which at least performs a "Not precise enough" precision-drift check [6](#0-5) .

### Impact Explanation
An account issuing an `ExchangeInjectContract` transaction can end up paying (having deducted) a materially different — and larger — amount of the paired token than it intended when it signed the transaction, if the exchange ratio shifts between signing/broadcast and execution (e.g., due to another `ExchangeTransaction`/`ExchangeInject`/`ExchangeWithdraw` on the same exchange executing first in the same block or an earlier block). This is an unbounded-debit / unexpected-loss-of-funds condition for the transaction broadcaster, analogous to the reported `SolverVault.deposit()` issue where the caller had no way to enforce a minimum expected output.

### Likelihood Explanation
This is reachable by any unprivileged account holding both tokens in an existing `Exchange` pool by simply broadcasting an `ExchangeInjectContract` transaction — no special privilege required. It only requires that the pool ratio move between signing and block execution, which is a normal occurrence for actively-traded exchange pairs (any concurrent `ExchangeTransaction` shifts the ratio).

### Recommendation
Add a caller-supplied bound (e.g., `max_another_token_quant` or `expected` field) to `ExchangeInjectContract`, mirroring `ExchangeTransactionContract.expected`, and validate in `ExchangeInjectActuator.doValidate()` that the computed `anotherTokenQuant` does not exceed the caller's specified maximum before executing the balance deduction.

### Proof of Concept
1. Attacker/other participant observes a pending `ExchangeInjectContract` transaction from Victim in the mempool, computed off the current pool ratio (`firstTokenBalance`/`secondTokenBalance`).
2. Attacker submits and gets included first an `ExchangeTransactionContract` (or another `ExchangeInject`) against the same `exchange_id` that shifts the ratio unfavorably for Victim.
3. Victim's `ExchangeInjectContract` then executes with the now-shifted ratio; `ExchangeInjectActuator.execute()` computes a larger `anotherTokenQuant` than Victim expected and deducts it from Victim's account balance/asset without any check, since no field in `ExchangeInjectContract` allows Victim to cap this value [7](#0-6) .
