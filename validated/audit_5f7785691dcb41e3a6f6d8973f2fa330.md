### Title
Missing domain separation in `SlotMetadata::auth_digest()` enables cross-StackerDB signature replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` binds a signature only to `slot_id`, `slot_version`, and `data_hash`, never to the owning smart contract/StackerDB. Any chunk broadcast for one StackerDB contract can be replayed verbatim via `POST /v2/stackerdb/:addr/:contract/chunks` (or via P2P `StackerDBPushChunk` gossip) into any other StackerDB contract that happens to assign the same signer address to the same `slot_id`, causing an unauthenticated write of attacker-relayed (not attacker-authored) data into a different contract's slot.

### Finding Description
`SlotMetadata::auth_digest()` computes `SHA512/256(slot_id || slot_version || data_hash)` with no contract/database identifier mixed in: [1](#0-0) 

`SlotMetadata::verify()`/`StackerDBChunkData::verify()` recover the public key from this digest and only check that the resulting `Hash160` equals the address it is compared against — that address is *not* embedded in the digest, it is supplied externally by the caller: [2](#0-1) 

In `StackerDBTx::try_replace_chunk`, the "externally supplied" comparison address is `slot_validation.signer`, looked up per-contract from that contract's own `chunks` table (`get_slot_validation(smart_contract, slot_desc.slot_id)`), which was populated at `create_stackerdb`/`reconfigure_stackerdb` time from that contract's signer-set configuration: [3](#0-2) 

The check never involves the contract identifier in what is actually signed — it only asks "does this signature validate against whichever address my local config says owns `slot_id` in *this* database?" Because different StackerDB contracts (e.g. per-cycle `signers-0-*`, `signers-1-*`, `.miners`, etc.) independently assign `(signer address, slot_id)` pairs, and slot assignment ordering is deterministic and driven by common inputs (e.g. stacked amount ordering), it is realistic for the same address to land on the same `slot_id` in two different contracts across cycles/DBs.

The remote entry point is `RPCPostStackerDBChunkRequestHandler::try_handle_request`, which parses `contract_identifier` from the URL path and a `StackerDBChunkData` JSON body from an unauthenticated POST, then calls `tx.try_replace_chunk(&contract_identifier, &stackerdb_chunk.get_slot_metadata(), &stackerdb_chunk.data)`: [4](#0-3) 

Nothing in this path re-derives or checks that the signature was produced "for" `contract_identifier` — the same `(slot_id, slot_version, sig, data)` tuple that was valid (and already gossiped, since StackerDB chunks are broadcast) for contract A is byte-for-byte replayable against contract B's endpoint. If contract B's slot table also lists the same address as owner of that `slot_id`, and the replayed `slot_version` is greater than B's currently stored version and below `max_writes`, `try_replace_chunk` succeeds, and the chunk is committed and further relayed as a `StackerDBPushChunk`: [5](#0-4) 

No guard in this path checks the contract identifier against the signed data, so the equality `signature_authenticates(contract_id, slot_id, slot_version, data_hash)` degenerates to `signature_authenticates(slot_id, slot_version, data_hash)`, independent of `contract_id`.

### Impact Explanation
An observer of gossip/relay traffic (not necessarily the original signer) can capture any legitimately-signed `StackerDBChunkData` broadcast for contract A and resubmit it unmodified to contract B's `/v2/stackerdb/.../chunks` RPC endpoint (or push it via P2P `StackerDBPushChunk`). If contract B independently assigns the same signer address to that `slot_id`, the node stores and re-relays this data as an authentic write to contract B's slot, even though the signer never authorized writing that content into contract B. This is an unauthenticated/unauthorized write into StackerDB state and propagates network-wide via the subsequent relay of `StackerDBPushChunk`, matching the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" Critical category. The attacker does not need any secret or elevated role — only network visibility of the original broadcast and the ability to reach the RPC/P2P port.

### Likelihood Explanation
Exploitability is conditioned on a specific configuration coincidence: two distinct StackerDB contracts must assign the same signer address to the same `slot_id` (e.g., signer set reused across contiguous reward-cycle contracts with unchanged/similar stacking-amount ordering) and the target contract's stored `slot_version` for that slot must be lower than the replayed one. This condition is plausible but not guaranteed to hold for every deployment/every slot, and the resulting data must actually make sense to whatever consumes it (its impact is "written," not necessarily "consumed usefully," in mismatched contracts). Attacker cost is minimal (capture+replay one message), the RPC endpoint requires no admin secret, and the action is repeatable for every slot/version bump. Likelihood is moderate — dependent on real-world slot-assignment overlap across contracts, which is a plausible but not universally-guaranteed condition.

### Recommendation
Bind the contract/database identity into the signed digest. Change `SlotMetadata::auth_digest()` (and update `sign`/`verify`/`StackerDBChunkData` correspondingly) to include the StackerDB's `QualifiedContractIdentifier` (or a stable numeric `stackerdb_id`) as part of the hashed preimage, e.g. `hasher.update(smart_contract.to_string().as_bytes())` before hashing `slot_id`/`slot_version`/`data_hash`, and thread the contract identifier through `SlotMetadata::sign`/`verify` call sites (`StackerDBChunkData::sign`/`verify`/`recover_pk`, and all callers in `stackslib/src/net/stackerdb`). This must be a coordinated protocol change since it alters what signers sign over.

### Proof of Concept
Rust test in `stackslib::net::stackerdb::tests::db`:
1. Create two in-memory `StackerDBs` (or one `StackerDBs` with two contracts) `contract_a` and `contract_b`, each with `create_stackerdb` assigning the *same* `StacksAddress` (derived from one keypair) to `slot_id = 3` in both.
2. Build a `StackerDBChunkData { slot_id: 3, slot_version: 1, data: b"hello".to_vec(), .. }`, call `sign(&privk)` — this signs only `slot_id||slot_version||data_hash`.
3. Call `tx_a.try_replace_chunk(&contract_a, &chunk.get_slot_metadata(), &chunk.data)` — assert `Ok(())`.
4. Without re-signing, call `tx_b.try_replace_chunk(&contract_b, &chunk.get_slot_metadata(), &chunk.data)` on the second contract's transaction — assert this also returns `Ok(())`, proving the same signature validated for contract A is accepted verbatim by contract B, i.e. `try_replace_chunk` never rejects with `BadSlotSigner` despite the chunk never being signed "for" `contract_b`.
5. Contrast with expected secure behavior: if `auth_digest()` included the contract identifier, step 4 would fail with `net_error::BadSlotSigner` because the signature would not recover to a digest matching `contract_b`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
