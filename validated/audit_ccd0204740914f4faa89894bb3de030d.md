## Title
Permanent, unrecoverable lock of a Loan NFT and its cashflows when `LoansNFT.lock()` is used with an unresponsive or key-lost `unlocker` - (`File: contracts/LoansNFT.sol`)

## Summary
`LoansNFT.lock()` lets a loan's owner (or any approved address) hand transfer/settlement authority to an arbitrary `unlocker` address. Once locked, only that exact `unlocker` can restore normal control (`unlock()`), and the base contract provides **no privileged override** to clear the lock. This is the same root-cause shape as the reported Open Oracle bug: an unprivileged, self-inflicted state transition (`invalidateReporter` there, `lock()` here) creates a hard dependency on a single specific key for all future recovery, with zero fallback if that key is lost, compromised, or the counterparty simply goes unresponsive.

## Finding Description
`lock()` is a fully public function, callable by the token owner or any address `_isAuthorized` for the token (owner, per-token approved, or `setApprovalForAll` operator): [1](#0-0) 

After locking, `unlock()` is gated strictly to the stored unlocker with no alternate path: [2](#0-1) 

The guardian-only rescue function `forceTransfer` explicitly refuses to touch a locked token: [3](#0-2) 

The spec confirms this is a deliberate design gap at the `LoansNFT` layer — guardian recovery is only possible *after* whatever locked the token clears its own lock first: [4](#0-3) 

The only consumer that supplies a recovery path is `LoansExchange`, which layers its own guardian-only `forceCancelOffer` specifically to work around this gap for *exchange-created* locks: [5](#0-4) 

But `lock()` on `LoansNFT` is not restricted to `LoansExchange` — any owner or approved address can call it directly, naming any `unlocker`, entirely outside of the exchange's tracked-offer/`forceCancelOffer` safety net. Once locked this way, `Loans.investorWithdraw` requires the caller to be exactly the cached unlocker to release principal/interest: [6](#0-5) 

If the named `unlocker` address is an EOA whose key is lost, a contract with no way to call `unlock()`, or simply an unresponsive/malicious party, there is **no path in the protocol** (not the investor, not the admin, not the guardian) to reclaim control of the NFT or its cashflows — mirroring the report's scenario where a signed message from a now-inaccessible key becomes required to keep state moving forward, with no built-in fallback.

## Impact Explanation
This matches the allowed impact "Permanent or practically unrecoverable lock of ... claimable assets, shares, cashflows, or loan NFTs caused by an unprivileged path." The `lock()` call is fully unprivileged (owner/approved-address triggered), and once locked to a bad-faith or key-lost `unlocker`, the loan NFT's ownership transfer rights and every future principal/interest distribution routed through `investorWithdraw` become permanently frozen. Neither `unlock()`, `forceTransfer`, nor any exchange-level recovery function can reach a lock that was not created through `LoansExchange`.

## Likelihood Explanation
Medium. `lock()` is a generic, unrestricted primitive intended for future/other integrators beyond `LoansExchange` (per its own docstring: "This lets integrators such as `LoansExchange` lock listed loans..."), so any current or future direct caller of `lock()` — or an investor experimenting with the primitive directly — can trigger the unrecoverable state. `LoansExchange` itself never triggers the bug because it always retains `forceCancelOffer` as an escape hatch; the exposure is specifically for any locking path that bypasses the exchange.

## Recommendation
Add a guardian-gated rescue function on `LoansNFT` itself (mirroring `forceTransfer`'s design), e.g. `forceUnlock(uint256 tokenId)`, that clears `_unlockers[tokenId]` regardless of which component created the lock. This closes the same class of gap the Open Oracle report flagged: never let a single, possibly-lost external key be the sole path to keep protocol state (here, NFT transferability and cashflow routing) moving.

## Proof of Concept
1. Investor owns loan NFT `id` with active interest/principal accruing.
2. Investor (or any address they approved via `approve`/`setApprovalForAll`) calls `loansNFT.lock(badActor, id)` directly (not through `LoansExchange`).
3. `badActor`'s private key is lost/burned, or `badActor` is a contract lacking any call to `LoansNFT.unlock`.
4. `loansNFT.unlock(id)` now always reverts (`NotUnlocker`) since `msg.sender` can never equal `badActor`.
5. `loans.investorWithdraw([id], ...)` reverts for the investor (`Unauthorized`, since `cachedUnlocker != msg.sender`) and can never succeed since only `badActor` could call it.
6. `loansNFT.forceTransfer(...)` reverts `TokenLocked` for the guardian.
7. The loan NFT and all its future cashflows are permanently stranded with no recovery path in the protocol.

## Guardian Recovery via `forceTransfer`

`forceTransfer(address from, address to, uint256 tokenId)` is a guardian-only escape hatch for unlocked NFTs stuck in a recipient that cannot move them on its own. The common case is a contract that was used as the buyer of an `acceptOffer` settlement but lacks the surface area to call `transferFrom` from itself. It is also available as a generic recovery path for any other unlocked ownership-stuck scenario.

Permissioning:

- only addresses with `GUARDIAN_ROLE` on the `Loans` contract may call `forceTransfer`
- subject to the existing guardian timelock governance

Validation:

- `tokenId` must exist (reverts `ERC721NonexistentToken` otherwise)
- `from` must match the current `ownerOf(tokenId)` (reverts `InvalidFrom` otherwise) — this guards the guardian against a stale `from` argument
- `to` must not be `address(0)` (reverts `InvalidTo`); `forceTransfer` is a rescue path, not a burn path
- `tokenId` must not be locked (reverts `TokenLocked`); protocol-specific locks must be cleared by the lock owner first, such as by cancelling an active exchange offer

Execution:

1. transfer the NFT to `to`, bypassing ERC721 approvals; ownership nonces for `from` and `to` are bumped exactly as for a normal transfer
2. emit the standard ERC721 `Transfer` event
3. if `to` is a contract, invoke `onERC721Received` and revert unless it returns the ERC-721 receiver magic value (reverts `ERC721InvalidReceiver` otherwise).
4. emit `ForceTransfer(from, to, tokenId)`

`forceTransfer` deliberately bypasses ERC721 approval, but it does not bypass active locks. A lock means another protocol component currently controls transfer authority; that component must clear the lock through its own state-aware flow before guardian recovery can move the token.
