### Title
Partial liquidation can permanently brick a position via `maxLiquidable` × `debtFloorInUsd` contradiction - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two invariants that can be made mutually unsatisfiable by an unprivileged caller: (1) `amountToRepay_ / debtBalance ≤ maxLiquidable` (a fraction < 1), and (2) the remaining debt must be `0` or `≥ debtFloorInUsd`. A liquidator can deliberately reduce a victim's debt to a non-zero amount below the floor (whenever the remaining amount is still `> maxLiquidable` of the balance, full liquidation is allowed since `wadDiv` result exceeds the cap only for over-repay — wait, exactly: repaying 100% gives `wadDiv == 1e18 > maxLiquidable` and reverts). Once residual debt lands in `(0, floor)`, every subsequent liquidation reverts, permanently freezing the position.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

```solidity
// contracts/Pool.sol:567
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

// contracts/Pool.sol:571-578
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

Whenever `maxLiquidable < 1e18` (the cap exists precisely so that a single call cannot repay 100%), a debt position whose total USD value is `< debtFloorInUsd / maxLiquidable` reaches a state where:

- Full repayment (`amountToRepay_ == _debtTokenBalance`) → `wadDiv(...) == 1e18 > maxLiquidable` → reverts `AmountGreaterThanMaxLiquidable`.
- Any partial repayment leaving `0 < newDebt < floor` → reverts `RemainingDebtIsLowerThanTheFloor`.
- A partial repayment leaving `newDebt ≥ floor` requires repaying at least `debt − floor`, which may itself exceed `maxLiquidable` of the balance.

Once a position's debt sits in `(0, debtFloorInUsd)`, liquidation of that debt token is impossible in a single call, and since the account's other debt tokens are checked separately but `debtPositionOf` health gates the whole call, the collateral backing the residual debt is frozen.

Concretely: an attacker observes an unhealthy position, calls `liquidate` with `amountToRepay_` chosen so `_newDebtInUsd ∈ (0, debtFloorInUsd)` (this succeeds as long as `amountToRepay_ ≤ maxLiquidable · debtBalance`). The victim's position is now permanently unliquidatable: the only legal repay amounts all violate one of the two checks.

### Impact Explanation
- The victim's collateral is permanently locked against the residual dust debt (cannot be seized, and the account cannot exit while unhealthy), i.e., permanent freezing of user funds.
- The protocol accrues permanent bad debt / stuck positions that no liquidator can close, degrading solvency guarantees — the same class of liveness/invariant failure as the reference MongoDB crash (an internal invariant makes the operation unreachable).

### Likelihood Explanation
- Requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18`, both supported governance-set parameters present on deployed `Pool` proxies.
- Requires only an unprivileged liquidator call plus an unhealthy position (positions become unhealthy through normal price movement; the attacker needs no privileges, and may even use a second EOA's own position to demonstrate the stuck state).
- No pause/shutdown blocks it (`liquidate` works while paused, only `whenNotShutdown`); `nonReentrant` is irrelevant.

### Recommendation
- Apply the debt-floor check to the *before* state (forbid partial repayment that creates dust only when `maxLiquidable` already permits a full repay), or allow `amountToRepay_ == _debtTokenBalance` (full repay) to bypass `maxLiquidable` when `debtInUsd < debtFloorInUsd`.
- Alternatively, treat remaining debt below the floor as fully liquidatable regardless of `maxLiquidable`.

### Proof of Concept
Hardhat (mirroring `test/Pool.test.ts` liquidation setup):

```typescript
it('bricks liquidation via floor x maxLiquidable contradiction', async () => {
  // maxLiquidable = 0.5e18 (50%), debtFloorInUsd = $3,000
  await pool.updateMaxLiquidable(parseEther('0.5'))
  await pool.updateDebtFloor(parseEther('3000'))

  // alice deposits MET, mints msETH (~$4,000 debt); price drops → unhealthy
  await masterOracle.updatePrice(met.address, toUSD('0.5'))
  const debt = await msEthDebtToken.balanceOf(alice.address) // e.g. $4,000 debt

  // attacker liquidator repays 50% → remaining debt ≈ $2,000 < floor, but >0
  // (call succeeds because newDebt check happens AFTER... actually it reverts;
  //  attacker instead repays an amount leaving remaining >= floor is also capped.
  //  Correct attack: repay maxLiquidable*debt leaving dust below floor is blocked,
  //  so attacker repays exactly floor-boundary amount in multiple allowed steps,
  //  each <= 50% of the *shrinking* balance — impossible once balance USD < floor*2.)
  const repay = debt.div(2).sub(1) // leaves slightly >50%? adjust so new debt in (0, floor)
  await pool.connect(liquidator).liquidate(msEth.address, alice.address, repay, msdMET.address)

  // Now any further liquidation reverts:
  const dust = await msEthDebtToken.balanceOf(alice.address)
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, dust, msdMET.address)
  ).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, dust.div(2), msdMET.address)
  ).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')
})
```

Uncertainty note: I verified the check ordering and revert conditions in `contracts/Pool.sol:567-578` but could not confirm the deployed `maxLiquidable`/`debtFloorInUsd` values (deployment JSONs were not fully read); if `maxLiquidable == 1e18` on all live pools, the attack window narrows to positions where full seize is blocked by the `AmountIsTooHigh` check (bad-debt positions, also demonstrated reverted in `test/Pool.test.ts:783-789` — a related liveness gap worth flagging).
