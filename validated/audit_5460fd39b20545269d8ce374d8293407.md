### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` rows survive `DeleteAccountAction` and are later delivered as a self-call receipt against a re-created account with a different owner - ([File: core/store/src/utils/mod.rs], [runtime/runtime/src/actions.rs], [runtime/runtime/src/lib.rs])

### Summary
`remove_account` (called by `action_delete_account`) purges the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie rows for a deleted account, but never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` rows keyed under that same `account_id`. If the account had an outstanding `promise_yield_create` self-yield, that parked receipt (and its timeout-queue entry) survives account deletion. After the account name is later re-created by an unrelated party, the parked yield is delivered via the normal timeout mechanism as a `PromiseResume` receipt whose `predecessor_id == receiver_id == account_id`, and it is executed against the new account/contract state as a same-account (self) `FunctionCall`.

### Finding Description
`promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660-3718`) creates a `PromiseYield` action receipt whose `receiver_id` is `self.context.current_account_id` and whose single action is a `FunctionCall` to `method_name` chosen by the calling contract [1](#0-0) . When this receipt is processed it is simply stored keyed by `(receiver_id, data_id)` via `set_promise_yield_receipt`, plus a `PromiseYieldStatus::Yielded` row and a `PromiseYieldTimeout` queue entry [2](#0-1) .

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) refunds the balance and calls `remove_account` to purge the account's state [3](#0-2) . `remove_account` only removes `Account`, `ContractCode`, access/gas keys, and `ContractData` [4](#0-3) ; it never calls `remove_promise_yield_receipt`, `remove_promise_yield_status`, or any yield-id mapping cleanup, and it does not touch the `PromiseYieldTimeout`/`PromiseYieldIndices` queue.

Because `resolve_promise_yield_timeouts` only checks `state_update.contains_key(&PromiseYieldReceipt{...})` before firing the timeout resume [5](#0-4) , the queued timeout entry — created at the *original* account's yield time — still finds the stale `PromiseYieldReceipt` row present (it was never removed by account deletion) and synthesizes a fresh `PromiseResume` receipt with `predecessor_id = receiver_id = account_id` targeting the same account name, which is now owned by a different party.

When that `PromiseResume` receipt is processed by `process_receipt`'s `PromiseResume` arm, it re-fetches the still-present `PromiseYieldReceipt` under `account_id` and unconditionally executes it via `apply_action_receipt` [6](#0-5) . There is no check that the account owning the receiver_id today is the same account that originally created the yield (no equivalent of a "creation epoch"/generation check on the account). The delivered action receipt is a same-account `FunctionCall` (`predecessor_id == receiver_id == current_account_id`), which is exactly the shape many contracts use as an internal-trust boundary (e.g. `assert_eq!(predecessor_account_id(), current_account_id())` guarding privileged callback logic). The new owner's contract never authorized this call; it was queued by the previous, now-deleted, owner's contract code.

Checks that fail to stop this:
- `remove_account` has no cross-column cleanup for the four Promise-Yield-related columns, unlike access keys/contract data which it explicitly walks and removes [7](#0-6) .
- `action_create_account` for a sufficiently long top-level name allows creation by *any* predecessor (only short top-level names are gated to the registrar) , so the account name can be legitimately re-owned by an unrelated attacker/party.
- Receipt processing performs no "does this receiver account belong to the same lineage as the one that created this yield" check; state keyed purely by `(account_id, data_id)` is trusted implicitly.

### Impact Explanation
This is an authorization-escalation bug: a receipt authorized by account A's prior owner/contract is executed as a trusted self-call against the *new* owner's contract/account state, without the new owner's consent. Any NEAR pattern that gates privileged logic on "caller is myself" (a common and recommended self-call pattern for internal callbacks) can be triggered by an attacker who: (1) previously owned the account, (2) yielded a self-call to a chosen method name, (3) deleted the account, and (4) waited for someone else to re-create/reuse that account name. This maps to the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions: attacker must control the account before deletion (trivial — attacker deploys their own contract and calls `promise_yield_create` on itself), the account must be deletable (small storage footprint, no locked stake — both attacker-controlled), and the account name must be re-creatable by a different party (achievable for long top-level names, which require no registrar approval). Cost is limited to normal gas/storage fees; the attack is fully repeatable and deterministic (the timeout length is a fixed, known runtime config parameter, so the attacker can also pre-arrange the timing to land on any future block). No validator, node-operator, or leaked-key access is needed — purely a sequence of ordinary signed transactions from an unprivileged account.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also iterate and remove any `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` rows for the account being deleted, and additionally either purge or invalidate any outstanding `PromiseYieldTimeout` queue entries referencing that account (e.g., tombstone by account-generation counter, or scan-and-remove analogous to the access-key/contract-data removal loops already present). Alternatively, disallow `DeleteAccountAction` while the account has any pending yield (`PromiseYieldStatus` present), mirroring the existing `DeleteAccountStaking`-style precondition check.

### Proof of Concept
Integration/test-loop test plan:
1. Create account `A` (a long top-level account, e.g. 40+ chars, so it is not registrar-gated) and deploy a test contract exposing: `yield_self(method_name)` (calls `promise_yield_create` with `receiver_id = self`), and a privileged self-only method `privileged()` that asserts `predecessor_account_id() == current_account_id()`.
2. From `A`, call `yield_self("privileged")`, producing a `PromiseYieldReceipt`/`PromiseYieldStatus` and a `PromiseYieldTimeout` entry for `A`.
3. From `A`, submit `DeleteAccountAction` with some beneficiary before resuming/timing out; assert the account record is gone but (via `state-viewer` / direct trie read) the `PromiseYieldReceipt`/`PromiseYieldStatus` rows for `A`'s `data_id` are still present in state.
4. Have an unrelated party `B` (no relation to the original A key or contract) re-create account `A` via `CreateAccountAction` (allowed since it's a long top-level name) and deploy a different contract exposing its own `privileged()` gated the same way.
5. Advance blocks until `yield_timeout_length_in_blocks` elapses; assert a `PromiseResume` receipt with `data: None`, `predecessor_id == receiver_id == A` is produced and delivered.
6. Assert the new `A` contract's `privileged()` method executed successfully (state mutation observed) even though `B` never called or authorized it — demonstrating execution of a stale self-authorized action against an account `B` never granted such privilege to.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
