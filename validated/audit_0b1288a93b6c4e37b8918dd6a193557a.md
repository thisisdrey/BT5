### Title
Amsterdam self-destruct finalization does not clear nonce, code, or storage when balance is preserved - (File: core/state/statedb.go)

### Summary
`finaliseAmsterdam` in `core/state/statedb.go` implements the "EIP-8264" self-destruct semantics where a self-destructed account that still holds a nonzero balance at transaction end is supposed to survive as a balance-only account with nonce reset to 0, code cleared, and all storage cleared. The implementation only overwrites the balance field and leaves nonce, code hash, and storage root copied verbatim from the pre-transaction account state, so a pre-existing contract that self-destructs (but keeps a nonzero balance) retains its old nonce, code, and storage instead of being wiped as documented.

### Finding Description
In `finaliseAmsterdam`: [1](#0-0) 

```go
case obj.selfDestructed:
    // EIP-8264: accounts marked for self-destruction, instead of
    // being deleted, are modified as follows:
    // - nonce is reset to 0,
    // - balance is unchanged,
    // - code is cleared,
    // - all storage is cleared
    if !obj.Balance().IsZero() {
        o := newObject(s, obj.address, obj.origin)
        o.setBalance(new(uint256.Int).Set(obj.Balance()))
        s.setStateObject(o)
        s.markUpdate(addr)
    }
```

`newObject(s, obj.address, obj.origin)` constructs the replacement account by copying `obj.origin` — the account's state *before* the current transaction ran — verbatim into `data`: [2](#0-1)

Only `Balance` is subsequently overwritten via `o.setBalance(...)`. If `obj.origin` is non-nil (i.e., the account existed with a nonce, code hash, and/or non-empty storage root before this transaction — a pre-existing contract, not one freshly created in this same transaction), the resulting object `o` keeps:
- `o.data.Nonce` = the pre-tx nonce (not reset to 0),
- `o.data.CodeHash` = the pre-tx code hash (code is not cleared),
- `o.data.Root` = the pre-tx storage root (storage is not cleared).

Because `o` is a fresh `stateObject` with empty `originStorage`/`pendingStorage` caches, any subsequent read of its storage falls through to `GetCommittedState`, which loads from the database using `s.data.Root` — i.e., the old, un-cleared storage root: [3](#0-2) 

This directly contradicts the comment's specified semantics ("nonce reset to 0", "code is cleared", "all storage is cleared") and mirrors the reported bug class: a cleanup/removal path that is supposed to fully reset state but leaves stale data behind in a parallel structure, causing incorrect behavior on any subsequent access. Here, the "stale mapping" analog is the un-reset `Nonce`/`CodeHash`/`Root` fields carried over from `obj.origin`.

Only when `obj.origin` is `nil` (contract created and self-destructed within the very same transaction, as in the existing `TestEIP8246SelfdestructNoBurn` test) does this path behave correctly, because `newObject` falls back to `types.NewEmptyStateAccount()`. Any pre-existing contract (deployed in an earlier block) that self-destructs while retaining a nonzero balance in a later transaction hits the buggy path.

### Impact Explanation
This produces a state (`nonce`, `codeHash`, storage `Root`, and the storage trie contents actually persisted) that diverges from the specification the code itself documents for this fork rule. Every node running this exact code will compute the same (wrong) `stateRoot`, but that root is inconsistent with the documented/intended semantics of the finalization rule — a pre-existing contract's code and storage remain live and readable after a "self-destruct," when they are supposed to be wiped. This is a High-severity persistence/state-computation defect: it results in an incorrect account state (code/nonce/storage retained when the rule mandates clearing) that every proposer building on this code path will produce identically, and it represents unauthorized retention of code/storage on an account whose self-destruct should have cleared it.

### Likelihood Explanation
This triggers deterministically whenever a pre-existing contract (with nonzero nonce, code, or non-empty storage prior to the current transaction) executes `SELFDESTRUCT` while ending the transaction with a nonzero balance, under the "Amsterdam"/EIP-8264 rule set (`rules.IsAmsterdam`). This is a common real-world contract pattern (e.g., contracts self-destructing to themselves or to another address while still holding value), not a contrived edge case, so likelihood is high once this fork is activated.

### Recommendation
When preserving the balance of a self-destructed account in `finaliseAmsterdam`, construct the replacement object from an empty account (as `TestEIP8246SelfdestructNoBurn` implicitly relies on) rather than from `obj.origin`, e.g.:
```go
o := newObject(s, obj.address, nil)
o.setBalance(new(uint256.Int).Set(obj.Balance()))
```
so that `Nonce` is reset to 0, `CodeHash` becomes `EmptyCodeHash`, and `Root` becomes `EmptyRootHash`, matching the documented EIP-8264 semantics, and ensure the account's storage is actually deleted from the trie (via `handleDestruction`/`deleteStorage`) rather than merely being referenced by a stale root.

### Proof of Concept
1. Deploy contract `A` with nonzero nonce (e.g., it performed a `CREATE` earlier) and non-empty storage (e.g., `SSTORE(1, 1)`), committed in an earlier block.
2. In a later transaction/block under the Amsterdam rules, have another contract send value to `A` and have `A` execute `SELFDESTRUCT` (to itself or elsewhere), such that `A` ends the transaction with a nonzero balance.
3. Observe post-state: `A`'s nonce is not 0, `A`'s code size is not 0, and `A`'s previously stored slot 1 still reads `1` — contradicting the documented "nonce reset to 0 / code cleared / storage cleared" semantics enforced by `finaliseAmsterdam` at `core/state/statedb.go:873-892`.

// GetCommittedState retrieves the value associated with the specific key
// without any mutations caused in the current execution.
func (s *stateObject) GetCommittedState(key common.Hash) common.Hash {
	// Record slot access regardless of whether the storage slot exists.
	if s.db.stateAccessList != nil {
		s.db.stateAccessList.StorageRead(s.address, key)
	}
	// If we have a pending write or clean cached, return that
	if value, pending := s.pendingStorage[key]; pending {
		return value
	}
	if value, cached := s.originStorage[key]; cached {
		return value
	}
	// If the object was destructed in *this* block (and potentially resurrected),
	// the storage has been cleared out, and we should *not* consult the previous
	// database about any storage values. The only possible alternatives are:
	//   1) resurrect happened, and new slot values were set -- those should
	//      have been handles via pendingStorage above.
	//   2) we don't have new values, and can deliver empty response back
	if _, destructed := s.db.stateObjectsDestruct[s.address]; destructed {
		s.originStorage[key] = common.Hash{} // track the empty slot as origin value
		return common.Hash{}
	}
	s.db.StorageLoaded++

	start := time.Now()
	value, err := s.db.reader.Storage(s.address, key)
	if err != nil {
		s.db.setError(err)
		return common.Hash{}
	}
