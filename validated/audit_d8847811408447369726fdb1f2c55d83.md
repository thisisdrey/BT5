### Title
Unsolicited StackerDB chunk push acknowledges (patches inventory) a slot version before the chunk is actually persisted, allowing served inventory to diverge from committed state - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
The `M-11` report is a "double accounting" bug where a value used to decide an action (topic activation) is computed from state that had already been updated with that same value, producing an incorrect (inflated) result and letting the decision fire before the real, correctly-accounted condition holds. The reachable Stacks analog is in `PeerNetwork::handle_unsolicited_StackerDBPushChunk`, where the in-memory chunk inventory that is echoed back to the sender is optimistically mutated to reflect "chunk accepted" before the chunk has actually been committed to the StackerDB, breaking the equality between *advertised* inventory and *persisted* state.

### Finding Description
When a peer pushes an unsolicited `StackerDBPushChunk`, `handle_unsolicited_StackerDBPushChunk` builds a `StackerDBChunkInv` (or Nack) via `make_StackerDBChunksInv_or_Nack`, validates the chunk with `validate_received_chunk` (size, signer, version, `max_writes`), and then immediately patches the in-memory `slot_versions` array to reflect the *new* version: [1](#0-0) 

This patched inventory is what gets sent back to the remote peer as the reply/acknowledgment: [2](#0-1) 

Note the returned tuple `Ok((false, true))`: "don't buffer, forward to relayer" — meaning the *actual* database write of the chunk (via `StackerDBTx::try_replace_chunk`) happens later, in a separate processing step (the relayer path that turns pushed chunks into a `StackerDBSyncResult` and commits them), not inside this function: [3](#0-2) 

`try_replace_chunk` re-derives its own acceptance decision from the *current* on-disk `SlotValidation` at commit time (signer, monotonic version, `max_writes`), independent of the check that was done earlier in `validate_received_chunk`: [4](#0-3) 

Because the inventory that claims "I now have version V of slot S" is sent to the network *before* the write is durably committed, any divergence between the two independent checks (e.g., a concurrently-accepted higher-version chunk for the same slot committed between the `validate_received_chunk` call and the deferred `try_replace_chunk` call, or a later commit failure) leaves the node advertising a slot version it does not actually hold. This is the direct analog of the Allora bug: a decision (here, "tell the network I have this data") is made using a provisional/uncommitted state update rather than the actual, final ground truth, so the two views (advertised vs. persisted) can diverge.

### Impact Explanation
A false/prematurely-advertised `StackerDBChunkInv` is propagated to peers, which is exactly the "serving non-canonical state as canonical" / "steering a node off the tip via false inventory" category. Peers that trust this inventory will believe the slot is up to date and stop attempting to fetch or push the real chunk to this node, stalling propagation of legitimate signer/StackerDB data (e.g., signer messages) across the network without any way for the deceived peers to detect the mismatch until their own polling reconciles it.

### Likelihood Explanation
This requires only a remote, unprivileged peer to send an unsolicited, validly-formed `StackerDBPushChunk`; the divergent-commit window depends on races/ordering between the immediate in-memory patch and the deferred DB write, which is timing-dependent and not certain to be exploitable on every message, so likelihood is moderate rather than trivially reproducible on demand — this is the primary uncertainty in this analog and I was not able to fully trace the relayer-side commit path (in `relay.rs`) within the available tool budget to confirm the exact conditions under which the deferred write disagrees with the earlier validation.

### Recommendation
Do not mutate/return the patched `slot_versions` inventory as an acknowledgment until after the chunk has actually been durably written via `try_replace_chunk` (or otherwise gate the inventory reply on the real commit result), so that the inventory advertised to peers always reflects the current persisted `SlotValidation` state rather than a provisional, pre-commit projection.

### Proof of Concept
Not independently reproduced; based on static code-path analysis of `handle_unsolicited_StackerDBPushChunk` (patches and replies with inventory at lines 794-807/858-871) versus the deferred, independently-re-checked persistence in `StackerDBTx::try_replace_chunk` (lines 400-438). A concrete PoC would require constructing two peers racing to push different versions of the same slot to a victim node and observing whether the victim's advertised `StackerDBChunkInv` can reflect a version it never actually commits — this was not verified end-to-end due to tool-call limits.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
