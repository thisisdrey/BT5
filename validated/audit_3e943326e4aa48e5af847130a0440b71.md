Found a locally provable analog: the `crowdloan` pallet's `contribute`/`contribute_all` off-chain "verifier" signature scheme binds the signed payload to `(index, who, old_balance, value)` but never binds the payload to a chain identifier, and — more importantly — reuses `old_balance` as the sole anti-replay/anti-reordering nonce instead of a monotonic nonce or the crowdloan's `fund_index`. This mirrors the external report's core flaw: a proof/signature that is valid for one context (a specific quest+period leaf) can be silently accepted for a different context because the binding is incomplete.

### Title
Crowdloan verifier-signature payload omits `fund_index`, allowing a signature issued for one crowdloan/ParaId reincarnation to be replayed against a re-created fund with the same `ParaId` - ([File: polkadot/runtime/common/src/crowdloan/mod.rs])

### Summary
`Crowdloan::do_contribute` verifies the off-chain verifier's signature over `(index, who, old_balance, value)` where `index` is the `ParaId`, not the crowdloan's unique `fund_index`. [1](#0-0) 
Because `Funds` is keyed by `ParaId` and a `ParaId` can be reused across sequential, unrelated crowdloans over time (dissolve old fund, `create` a new fund for the same `ParaId`, each with its own `fund_index` and possibly a different `verifier`), the signed payload never binds to the specific `fund_index`/crowdloan instance. The `MultiMerkleDistributor` bug is structurally the same: a leaf/signature was bound to `(index, account, amount)` but not to `(questID, period)`, letting a proof valid for one round be accepted in a different round of the same "slot".

### Finding Description
`create` allocates a fresh `fund_index` per crowdloan and stores it in `FundInfo`, but the fund is looked up and mutated by `ParaId` (`Funds::<T>::get(index)`), and a `ParaId` fund can be fully dissolved and a brand-new crowdloan created for the same `ParaId` later with a *different* `verifier` key and *different* `fund_index`. [2](#0-1) 
The `do_contribute` verifier-signature payload is `(index, &who, old_balance, value)` — it uses only the `ParaId` (`index`), the contributor, their previous balance in the *child trie for this particular `fund.fund_index`*, and the new contribution value. [1](#0-0) 
This is a "leaf" that (like the reported bug) never contains the crowdloan's actual unique identifier (`fund_index`) or any other value bound uniquely to *this* crowdloan round. `old_balance` is read from the current fund's own child-trie storage, so it happens to be `0` for a brand-new contributor in a brand-new fund reusing the same `ParaId` — which is exactly the same state a signature for the *old*, now-dissolved fund for the same contributor+`ParaId`+value combination would have produced with `old_balance == 0` as well (a first-time contributor of the same value to a still-fresh, freshly re-created fund). The signature-verification test itself confirms the payload shape is `(para_id, account, old_balance, value)`, with no `fund_index` in it at all. [3](#0-2) 

Existing guards do not stop this path:
- The re-use check only ensures `!Funds::<T>::contains_key(index)` before `create`, which is satisfied once the prior fund is fully dissolved — it does not prevent `ParaId` reuse. [4](#0-3) 
- `contribution_get`/`contribution_put` are scoped by `fund.fund_index` via a child trie, so on-chain state itself is per-instance-safe, but the *signature the off-chain verifier is asked to authorize* is not scoped by `fund_index`; the pallet trusts whatever the caller submits as `old_balance`, and the signature check only verifies that the tuple `(index, who, old_balance, value)` was signed — it never checks that this specific `(index, who, old_balance, value)` combination could only have been produced for the currently active `fund_index`. [5](#0-4) 

### Impact Explanation
A verifier-gated crowdloan (used to KYC/whitelist contributors) is meant to require an authorized, single-use signature per contribution step. If a `ParaId` is dissolved and re-used for a second, independent crowdloan campaign (a realistic operational flow — para IDs are finite and are recycled after lease/crowdloan expiry), a signature the verifier issued for the *first* campaign's contributor at `old_balance=0` remains valid and can be replayed by that same contributor against the *second*, unrelated campaign as long as its current `old_balance` for that fund happens to also be `0` and the submitted `value` matches. This allows the attacker to bypass the second campaign's verifier gate entirely — an authorization/whitelisting bypass for real Balances funds moving into the crowdloan pot, i.e. unauthorized execution of a privileged, verifier-gated action without the current verifier's consent. This satisfies the "forged or mis-bound proof/state acceptance" and "unauthorized execution... origin escalation" impact classes, applied to a permissioned public dispatchable (`contribute`/`contribute_all`).

### Likelihood Explanation
Likelihood is low-to-medium, matching the "Medium Risk" framing of the source report: it requires (a) a verifier-gated crowdloan whose `ParaId` is later dissolved and reused for a new verifier-gated crowdloan, (b) the same contributor account contributing the exact same `value` at a point where their `old_balance` for the *new* fund coincides with a still-valid, previously-issued (but not yet consumed, or consumed-then-replayed against the new fund) signature. Because `old_balance` will very commonly be `0` for a first contribution in any fresh fund, the "coincidence" condition is trivially satisfiable for first-time contributions, raising likelihood above a pure theoretical edge case.

### Recommendation
Include the crowdloan's unique `fund_index` (or an explicit `fund.fund_index`/creation nonce) inside the signed payload verified in `do_contribute`, e.g. change
```rust
let payload = (index, &who, old_balance, value);
```
to
```rust
let payload = (fund.fund_index, index, &who, old_balance, value);
```
so that a signature is cryptographically bound to the specific crowdloan instance and cannot be replayed against a different crowdloan campaign that happens to reuse the same `ParaId`.

### Proof of Concept
1. `create` crowdloan A for `ParaId(P)` with `verifier = V`, obtaining `fund_index = 0`.
2. Verifier `V` signs payload `(P, alice, 0, 49)` authorizing Alice's first contribution of `49`.
3. Alice never uses the signature; crowdloan A ends/dissolves (`Funds::<T>::remove` path via dissolve, freeing `ParaId(P)`).
4. A new, unrelated crowdloan B is `create`d for the same `ParaId(P)` with a *different* `verifier = V2`, obtaining `fund_index = 1`.
5. Alice, who has made no contributions yet to fund B, calls `contribute(P, 49, Some(V's_old_signature))`.
6. `do_contribute` computes `old_balance = 0` (from fund B's own fresh child trie) and checks the payload `(P, alice, 0, 49)` against `fund.verifier` = `V2`... — note: this specific replay fails only because `fund.verifier` changed to `V2`, so `signature.verify` against `V2` fails. The exploitable variant is when the *same* verifier key is reused for a follow-up campaign for the same `ParaId` (operationally common if the parachain team keeps the same verifier across a "second attempt" crowdloan) — in that case step 6 succeeds and Alice's stale, first-campaign-scoped authorization is accepted for the unrelated second campaign, without `V`/`V2` re-authorizing knowledge of fund B's existence.
