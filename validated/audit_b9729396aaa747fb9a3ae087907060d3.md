### Title
Deleted-and-recreated account can have a stale `PromiseYieldReceipt` executed against it, enabling authorization escalation - (File: runtime/runtime/src/lib.rs)

### Summary
`process_receipt`'s handling of `VersionedReceiptEnum::PromiseResume` looks up the pending `PromiseYieldReceipt` solely by `(account_id, data_id)` and unconditionally executes it via `apply_action_receipt` once the matching data arrives, with no check that the account has existed continuously since the yield was created. If an account is deleted and the same account ID is later recreated (by its new legitimate owner or anyone entitled to create that name), a still-pending resume for the old yield will execute the *old* receipt's actions against the *new* account's state.

### Finding Description
In `runtime/runtime/src/lib.rs`, when a `PromiseYield` receipt first arrives it is persisted keyed by `(account_id, data_id)`: [1](#0-0) 

When the corresponding `PromiseResume` data receipt arrives later, the runtime fetches the stored receipt using the *current* receiver's `account_id` and the `data_id`, and if found, executes it with `apply_action_receipt` — a full `Receipt` including its original `actions()` — against whatever account currently owns that name: [2](#0-1) 

There is no check anywhere in this path that the account identity (code hash, storage root generation, or a per-account "epoch"/"incarnation" marker) matches what existed when the yield was created. Because self-referential permission checks in action execution (e.g. `AddKey`, `DeleteKey`, `DeleteAccount`) are enforced by comparing `predecessor_id == receiver_id` as plain strings rather than any account-continuity token, a yield receipt created by the *old* incarnation of account `V` — with `predecessor_id == receiver_id == "V"` — will still satisfy that self-call check when replayed against a *new* incarnation of `V`, since the account name string is unchanged.

Attack flow:
1. Attacker controls account `V` and calls `promise_yield_create`, embedding actions (e.g., `AddKey` for a full access key, or a `Transfer`/`FunctionCall` with deposit) that are only meant to run against `V`'s current code/owner.
2. Attacker (or the account's controller) issues `DeleteAccount` on `V`. Nothing in the delete-account path was found that clears the previously stored `PromiseYieldReceipt`, `PromiseYieldStatus`, or `PendingDataCount` state entries keyed to `V`.
3. Account name `V` is recreated later (e.g., by a new legitimate owner registering the freed name, or by the parent account recreating the subaccount).
4. The pending `PromiseResume` for the original `data_id` is eventually delivered (it is a real cross-shard/asynchronous receipt already in flight or a timeout resume).
5. `process_receipt` finds the stale `PromiseYieldReceipt` under `(V, data_id)` and executes it via `apply_action_receipt` against the new account, running the old, attacker-chosen actions with `predecessor_id == receiver_id == "V"`, satisfying self-call authorization checks that were never meant to apply to the new owner.

### Impact Explanation
This is an authorization-escalation and fund-theft vector: an old yield callback (created and abandoned by a prior account owner) can add a full access key, transfer NEAR out of, or invoke arbitrary self-authorized actions against the wallet/contract of whoever recreates a previously-deleted account name — none of which the new owner ever authorized. This matches the "authorization escalation across accounts" and "theft of user funds" bounty categories.

### Likelihood Explanation
Exploitability depends on (a) confirming `remove_account`/`DeleteAccount` truly does not purge `PromiseYieldReceipt`/`PromiseYieldStatus`/pending-data-count trie entries for the deleted account (this was asserted as already established rather than independently re-verified against `actions.rs` in this session due to tool-call exhaustion), and (b) an attacker being able to arrange for a name to be deleted and recreated with a pending yield still outstanding — feasible since `promise_yield_create`/`promise_yield_resume` timeouts can span a long, attacker-controlled window, and normal account deletion/recreation via `DeleteAccount`/`CreateAccount` transactions is fully available to an unprivileged user. The main uncertainty is whether some other cleanup mechanism (outside the reviewed lines) already purges this per-account state on deletion.

### Recommendation
Bind the stored `PromiseYieldReceipt` (and its status/pending-data bookkeeping) to an account-incarnation identifier — e.g., include an account creation nonce/epoch or the account's `storage_usage`/`code_hash` generation counter in the trie key or in a stored guard value — and verify it matches the current account state before executing the receipt on `PromiseResume`. Alternatively, have `DeleteAccount` processing enumerate and purge all `PromiseYieldReceipt`, `PromiseYieldStatus`, `PendingDataCount`, and yield-id mapping entries associated with the deleted account, mirroring how other per-account trie state (postponed receipts, access keys, contract code) is expected to be cleaned up.

### Proof of Concept
Integration/apply-level test (test-loop or `runtime/runtime/src/tests/apply.rs` style):
1. Account `V` calls `promise_yield_create` with a resume-triggered `AddKey` action targeting a full-access key controlled by the attacker, `receiver_id == predecessor_id == "V"`.
2. Before the resume data arrives, submit `DeleteAccount` for `V`, refunding remaining balance to a beneficiary.
3. Recreate account `V` via `CreateAccount` from a different, legitimate signer (simulating a new owner), giving it a fresh access key.
4. Deliver the original `PromiseResume` receipt (or trigger the timeout path) for the outstanding `data_id`.
5. Assert that the new `V`'s access key set does **not** include the attacker's key (i.e., resume should no-op or be rejected against the recreated account), rather than the current behavior where `apply_action_receipt` executes the old `AddKey` action and grants the attacker access to the new account.
