### Title
Fragmented interest accrual causes systematic truncation of protocol fee reserve to zero, permanently losing treasury yield - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, function `accrue`)

### Summary
In every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), the `accrue` function computes the protocol's fee-reserve cut of newly accrued interest as `(mul-div-down debt-delta (var-get fee-reserve) BPS)`, which floors to zero whenever `debt-delta * fee-reserve < BPS`. Any ordinary user can trigger `accrue` (it runs at the top of `deposit`, `redeem`, `system-borrow`, etc.) as frequently as once per block. By repeatedly calling any accrue-triggering entry point with minimal time gaps instead of allowing interest to accumulate over longer intervals, an unprivileged caller fragments the same total interest into many tiny `debt-delta` slices, each of which rounds `reserve-inc` down to `0`, while the borrow/liquidity indexes (`idx`/`lidx`) still advance in full. This is directly analogous to the referenced Buffer Finance issue where per-call integer division truncated `option.premium`/`settlementFee` to a lower (or zero) value.

### Finding Description
`accrue` is defined identically across all six vault contracts, e.g. in [1](#0-0) :

```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```

`debt-delta` is the increase in total scaled debt (in underlying-token base units) between the previous and current call to `accrue`, computed via `mul-div-down` on `principal-scaled` and the index: [2](#0-1) . `mul-bps-down`/`mul-div-down` intentionally round down (defined in the shared math helpers, e.g. [3](#0-2) ), so whenever the interval between two `accrue` calls is short, `debt-delta` is a small integer, and `debt-delta * fee-reserve` can be smaller than `BPS`, making `reserve-inc` floor to `0`. When `reserve-inc` is `0`, no `treasury-lp` shares are minted to `.dao-treasury` at all — the entire protocol fee slice for that call is lost, even though the underlying interest for that period was still fully applied to the borrow index `next` and the liquidity index `nliq` (both of which get written via `var-set index next` / `var-set lindex nliq`), and thus is still fully paid out to lenders/depositors.

Because `accrue` is a `define-public` function invoked as the first step of user-facing entry points such as `deposit` and `redeem` (see e.g. [4](#0-3) ) and `system-borrow` ( [5](#0-4) ), any ordinary principal can force `accrue` to run at a chosen high frequency simply by making repeated small deposits/redeems. Splitting a fixed accrual window into N sub-intervals compounds `debt-delta` into N small chunks; as long as each chunk's contribution `debt-delta * fee-reserve` stays below `BPS`, the protocol's entire share of interest for that window is truncated to zero on every call, rather than only losing sub-unit remainder once as would happen with a single accrual over the full period.

### Impact Explanation
This causes a permanent, protocol-wide loss of unclaimed yield that should have been minted as `treasury-lp` shares to `.dao-treasury`. The value is not merely delayed — it is destroyed: because `idx`/`lidx` (and thus `total-assets-preview`) have already advanced to reflect the "no reserve taken" state, there is no mechanism to retroactively recover the un-minted treasury share once the index has moved past that point. This matches the in-scope "High" impact category of theft/permanent freezing of unclaimed yield accruing to the treasury.

### Likelihood Explanation
No privileged access or special preconditions are required — merely calling public entry points (`deposit`, `redeem`, or any operation that begins with `(try! (accrue))`) at high frequency, which is normal, unprivileged usage available to any principal, including via the vault's own natural transaction traffic during periods of frequent small transactions. This makes the likelihood high whenever `fee-reserve` is a modest bps value and per-call `debt-delta` is small relative to `BPS`/token decimals, which is the common case for tokens with fewer decimals or short block-to-block intervals.

### Recommendation
Do not floor the reserve cut per `accrue` call. Instead, accumulate a running remainder (as is done correctly, e.g., with `mul-div-up` used elsewhere for `calc-cumulative-debt` and `debt-to-repay` in the same contracts, see [6](#0-5) ) so that fractional reserve amounts carry over between accruals rather than being discarded, or track reserve accrual using a higher-precision fixed-point accumulator that is only truncated once at withdrawal/minting time.

### Proof of Concept
1. Assume `fee-reserve = 1000` (10%) and `BPS = 10000`.
2. Over one block, natural interest accrual for the vault would yield `debt-delta = 50` (in base units) if `accrue` were called once → `reserve-inc = floor(50*1000/10000) = 5` → nonzero `treasury-lp` minted.
3. Instead, an ordinary user submits 5 separate small `deposit`/`redeem` transactions within the same block/short interval, each triggering `accrue`. Each call sees a fragment of the interest, e.g. `debt-delta = 10` per call → `reserve-inc = floor(10*1000/10000) = 1` (still nonzero here, but as `fee-reserve` or the fragment shrinks further, e.g. `debt-delta = 9`, `reserve-inc = floor(9000/10000) = 0`).
4. With enough fragmentation (more calls, smaller `debt-delta` per call), every individual `reserve-inc` rounds to `0`, so `treasury-lp` is never minted for that interest, while `idx`/`lindex` still advance to reflect the full interest — permanently zeroing the protocol's fee capture for that period across all six vault contracts sharing this `accrue` logic.
