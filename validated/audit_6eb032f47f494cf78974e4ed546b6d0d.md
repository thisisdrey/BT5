### Title
Missing zero-check on `totalEnergyWeight` causes division-by-zero-equivalent (energy-limit overflow to `Long.MAX_VALUE`) in `RepositoryImpl.calculateGlobalEnergyLimit` - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, the TVM-context implementation of the per-account energy-limit calculation, divides `totalEnergyLimit` by `totalEnergyWeight` without any guard against `totalEnergyWeight == 0`, unlike the sibling implementation in `EnergyProcessor`, which explicitly checks for this case and returns `0`.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)` reads `totalEnergyWeight` from the `DynamicPropertiesStore` and immediately uses it as a divisor, relying only on a Java `assert` statement (a no-op unless the JVM is started with `-ea`, which production nodes are not): [1](#0-0) 

Compare this with `EnergyProcessor.calculateGlobalEnergyLimit()`, which is the analogous computation used elsewhere in resource accounting, and which explicitly guards this exact case: [2](#0-1) [3](#0-2) 

In `RepositoryImpl`, when `hardenResourceCalculation()` is disabled (the non-hardened/legacy path, which is `VMConfig`-flag gated and therefore may be the live path depending on chain parameters), the divisor reaches Java's `double` arithmetic:
```
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
Unlike integer division, `double` division by zero does not throw — `totalEnergyLimit / 0` evaluates to `Double.POSITIVE_INFINITY`, and `energyWeight * Infinity` is also `Infinity`; casting `Infinity` to `long` in Java yields `Long.MAX_VALUE`. This is the functional analog of the TFLite `BatchToSpaceNd` bug: an externally influenceable value (`block_shape`/here `totalEnergyWeight`) is used as a divisor without a zero check, and instead of a controlled error path the code silently produces a nonsensical, attacker-favorable result rather than crashing outright.

`RepositoryImpl` is the `Repository` implementation wired into the TVM execution context (accessed indirectly through `ContractState`, which simply forwards `calculateGlobalEnergyLimit` calls to the underlying `Repository`): [4](#0-3) 

`totalEnergyWeight` is a network-wide aggregate of frozen TRX for energy, maintained via `addTotalEnergyWeight`/`saveTotalEnergyWeight`. Under the freeze/unfreeze resource model, if the aggregate energy weight legitimately reaches zero (e.g., after mass unfreezing under `UnfreezeBalanceV2`/`UnDelegateResourceActuator` activity), any account that still has `frozeBalance >= TRX_PRECISION` recorded (a stale/transitional state, or a race during accounting updates) hitting this code path will receive `Long.MAX_VALUE` as its energy limit instead of `0` or a validated error.

### Impact Explanation
If reached with `totalEnergyWeight == 0` and `hardenResourceCalculation()` disabled, an account's effective energy limit becomes unbounded (`Long.MAX_VALUE`) rather than the intended `0`. Energy limit is the core metering constraint that bounds how much TVM computation a single transaction/account can perform against staked resources before requiring TRX burn. An account granted an unbounded energy limit could execute arbitrarily expensive contract calls without consuming its real (zero) energy allowance, effectively bypassing energy metering — a form of unauthorized/unbacked resource grant, and a potential vector for a network-DoS by unmetered computation from that account. This matches the "unbacked balance"/"energy metering" and "node crash or halt" categories in scope.

### Likelihood Explanation
Reaching `totalEnergyWeight == 0` requires the aggregate network `totalEnergyWeight` in `DynamicPropertiesStore` to reach zero, which is a state that depends on global freeze/unfreeze activity across all accounts rather than something a single unprivileged attacker can trivially force on demand (though on a small/private/sidechain network, or transiently during the freeze→freeze-v2 migration, this could occur without insider access). Additionally, this specific division only triggers the non-hardened `double` path when `hardenResourceCalculation()` (a `VMConfig`/chain-parameter gated hardening flag) is not active. This reduces likelihood relative to a fully attacker-controlled trigger, but the missing guard itself — present in the sibling `EnergyProcessor` implementation but absent here — is a clear, unaddressed code defect exactly analogous to the reported bug class.

### Recommendation
Add the same zero/non-positive check found in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` to `RepositoryImpl.calculateGlobalEnergyLimit`: explicitly return `0` when `totalEnergyWeight <= 0` before performing either the `BigInteger` division or the `double` division, rather than relying on a disabled-by-default `assert`.

### Proof of Concept
1. Drive (or observe, on a network where this occurs) `DynamicPropertiesStore.totalEnergyWeight` down to `0` via mass `UnfreezeBalanceV2`/`UnDelegateResourceActuator` operations while `allowHardenResourceCalculation` remains disabled.
2. Trigger a smart-contract call (`TriggerSmartContract`) from an account whose `AccountCapsule.getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (any residual/stale frozen record).
3. Inside `VMActuator`/`Program` execution, the energy-limit computation calls into `RepositoryImpl.calculateGlobalEnergyLimit`, which computes `(long) (energyWeight * ((double) totalEnergyLimit / 0))`, returning `Long.MAX_VALUE` instead of `0`, granting the caller an effectively unlimited energy allowance for that call.

Full reproduction against a running node (to confirm the exact call chain from `VMActuator` into `RepositoryImpl.calculateGlobalEnergyLimit` and to exercise the freeze/unfreeze sequencing needed to zero `totalEnergyWeight`) would require running the code and is beyond what can be confirmed through static reading alone; the root-cause defect (missing zero-guard compared to `EnergyProcessor`) is confirmed by direct code comparison above.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
