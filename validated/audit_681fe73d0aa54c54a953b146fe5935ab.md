### Title
EIP-7918 reserve-price check is skipped whenever excess+used blob gas is below target, causing `CalcExcessBlobGas` to return 0 instead of the reserve-price formula - ([File: consensus/misc/eip4844/eip4844.go])

### Summary
`calcExcessBlobGas` computes the header's `excessBlobGas` for Osaka using an ordering that diverges from the EIP-7918 reference algorithm: it short-circuits to `return 0` whenever `parentExcessBlobGas+parentBlobGasUsed < targetGas`, before ever evaluating whether the EIP-7918 "reserve price" branch is active. Per spec, the reserve-price check must be evaluated unconditionally (independent of whether excess/used is below target), and only the *non-reserve* path uses the target/floor-at-zero logic.

### Finding Description [1](#0-0) 

```go
func calcExcessBlobGas(isOsaka bool, bcfg BlobConfig, parent *types.Header) uint64 {
	var parentExcessBlobGas, parentBlobGasUsed uint64
	if parent.ExcessBlobGas != nil {
		parentExcessBlobGas = *parent.ExcessBlobGas
		parentBlobGasUsed = *parent.BlobGasUsed
	}
	var (
		excessBlobGas = parentExcessBlobGas + parentBlobGasUsed
		targetGas     = uint64(bcfg.Target) * params.BlobTxBlobGasPerBlob
	)
	if excessBlobGas < targetGas {
		return 0
	}
	if isOsaka {
		var (
			baseCost     = big.NewInt(params.BlobBaseCost)
			reservePrice = baseCost.Mul(baseCost, parent.BaseFee)
			blobPrice    = bcfg.blobPrice(parentExcessBlobGas)
		)
		if reservePrice.Cmp(blobPrice) > 0 {
			scaledExcess := parentBlobGasUsed * uint64(bcfg.Max-bcfg.Target) / uint64(bcfg.Max)
			return parentExcessBlobGas + scaledExcess
		}
	}
	return excessBlobGas - targetGas
}
```

Per EIP-7918, `calc_excess_blob_gas` is specified as:
```
if is_reserve_price_active(parent):
    return parent.excess_blob_gas + parent.blob_gas_used * (MAX - TARGET) // MAX
else:
    excess = parent.excess_blob_gas + parent.blob_gas_used
    return 0 if excess < TARGET else excess - TARGET
```
`is_reserve_price_active` depends only on `parent.base_fee_per_gas` and `parent.excess_blob_gas` (via the blob base fee), not on whether `excess < target`. The reference check must therefore run first, unconditionally.

In this codebase, the `excessBlobGas < targetGas` early return happens *before* the `isOsaka`/reserve-price branch is ever reached. Any state where the parent's excess+used blob gas is below target — which is the common/likely case right after Osaka activation or during periods of low blob demand — causes the function to skip the reserve-price computation entirely and return `0`, even when the reserve price is active and the spec mandates returning `parentExcessBlobGas + scaledExcess` (a value that can be significantly non-zero).

### Impact Explanation
`excessBlobGas` is a consensus-critical header field: it is verified against the parent by `VerifyEIP4844Header` ( [2](#0-1) ) and is used to derive the blob base fee (`CalcBlobFee`) which prices blob transactions. Because this Geth build computes a different `excessBlobGas` than a spec-conformant client whenever the reserve price is active and excess+used is below target:
- Every Geth node will build/propose a header with an `excessBlobGas` (and downstream `blobBaseFee`) that diverges from spec-conformant clients, causing a chain split at the very first Osaka block satisfying these conditions.
- Conversely, Geth will reject as invalid any spec-correct block produced by another client under these conditions (`VerifyEIP4844Header` mismatch), and vice versa a spec-correct client will reject Geth's block.

This is a consensus-split defect on an activated hard-fork (Osaka) header field, matching the "Critical" bar in the rules (Geth accepts/produces a block/header that other spec-conformant clients treat oppositely).

### Likelihood Explanation
Reachability is high: reserve-price activation only requires `BLOB_BASE_COST * parent.BaseFee > blobBaseFee(parentExcessBlobGas)`, which is essentially always true at low `excessBlobGas` (blob base fee floors near `MIN_BLOB_GASPRICE`=1 wei while `BLOB_BASE_COST * base_fee` is orders of magnitude larger under any realistic execution gas price). Low excess blob gas (below target) is the expected/common condition at fork activation and during quiet blob-demand periods, so this divergence is likely to trigger on essentially the first blocks after Osaka activates, not merely a rare edge case.

I was not able to independently confirm whether Osaka is scheduled/activated on the configured mainnet chain config in this snapshot (the `OsakaTime` value in `params/config.go` was not retrieved in time), so confirm mainnet-activation status before treating this as in-scope per the "no pre-activation code" exclusion rule.

### Recommendation
Restructure `calcExcessBlobGas` to evaluate the Osaka reserve-price branch unconditionally before applying the `excessBlobGas < targetGas` floor-to-zero logic, matching the EIP-7918 order of operations:
```go
func calcExcessBlobGas(isOsaka bool, bcfg BlobConfig, parent *types.Header) uint64 {
	var parentExcessBlobGas, parentBlobGasUsed uint64
	if parent.ExcessBlobGas != nil {
		parentExcessBlobGas = *parent.ExcessBlobGas
		parentBlobGasUsed = *parent.BlobGasUsed
	}
	if isOsaka {
		baseCost := big.NewInt(params.BlobBaseCost)
		reservePrice := baseCost.Mul(baseCost, parent.BaseFee)
		blobPrice := bcfg.blobPrice(parentExcessBlobGas)
		if reservePrice.Cmp(blobPrice) > 0 {
			scaledExcess := parentBlobGasUsed * uint64(bcfg.Max-bcfg.Target) / uint64(bcfg.Max)
			return parentExcessBlobGas + scaledExcess
		}
	}
	excessBlobGas := parentExcessBlobGas + parentBlobGasUsed
	targetGas := uint64(bcfg.Target) * params.BlobTxBlobGasPerBlob
	if excessBlobGas < targetGas {
		return 0
	}
	return excessBlobGas - targetGas
}
```

### Proof of Concept
1. Configure an Osaka-active chain (`isOsaka=true`) with a target blob config, e.g. `Target=6`, `Max=9`.
2. Construct a `parent` header with `ExcessBlobGas=0`, `BlobGasUsed = 5 * BlobTxBlobGasPerBlob` (below target so `excessBlobGas(0+used) < targetGas`), and a large `BaseFee` (e.g. 50 gwei) so `BLOB_BASE_COST * BaseFee` clearly exceeds `blobPrice(0)` (which is at the price floor) — i.e., reserve price is active.
3. Call `CalcExcessBlobGas(config, parent, headTime)`.
   - Current code: returns `0` (short-circuited by the `excessBlobGas < targetGas` check).
   - Spec-conformant computation: should return `parentExcessBlobGas + parentBlobGasUsed*(Max-Target)/Max = 0 + 5*BlobTxBlobGasPerBlob*(9-6)/9`, a non-zero value.
4. This divergence means a header produced/validated with this excessBlobGas value will not match a spec-conformant client's expectation, demonstrating a header-validity/consensus-split condition.
