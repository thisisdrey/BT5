### Title
Forced `protocol.file.allow=always` in `git_repository` submodule fetches allows an attacker-controlled Git remote to read/copy local filesystem content outside the checkout — ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
`git_repository`'s submodule handling force-enables the `file://` transport for `git submodule update`, overriding Git's own hardening (introduced after CVE-2017-1000117 / CVE-2018-11235 / CVE-2022-39253) that normally disables local-file submodule clones by default.

### Finding Description
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` runs: [1](#0-0) 
Both the recursive and non-recursive paths pass `-c protocol.file.allow=always` unconditionally before `submodule update --init [--recursive] --checkout --force`. Since Git 2.38.1, `protocol.file.allow` defaults to `user`/restricted specifically to prevent an untrusted superproject's `.gitmodules` from declaring a submodule with a `file://` (or bare local-path) URL that Git would otherwise clone locally — this is exactly the class of bug behind CVE-2022-39253, where a malicious repo's submodule/symlink combination is used to copy arbitrary files from the local filesystem into the checkout. Bazel's `git_worker.bzl` explicitly re-enables this behavior "for Git 2.38.1 and associated backport versions" (per the comment referencing bazelbuild/bazel#17040), globally overriding the safe default for every `git_repository`/`new_git_repository` fetch that has `init_submodules` or `recursive_init_submodules` set.

The attacker model fits: the "remote" Git server (an untrusted mirror, a compromised upstream, or any Git host serving the pinned commit/tag/branch) is content an unprivileged outsider can serve. The `.gitmodules` file and submodule URLs are part of that server-controlled content and are not covered by any checksum — Bazel only pins the *superproject* commit hash, not the safety of the submodule transport it triggers. There is no `sha256`/`integrity` check that would catch a malicious `file://` submodule URL, because git_repository's "pinning" model relies entirely on Git's own content addressing and Git's protocol allowlist — a protection this code explicitly disables.

### Impact Explanation
When `init_submodules = True` or `recursive_init_submodules = True` is set on a `git_repository`/`new_git_repository` rule and the fetched history/branch/tag contains a `.gitmodules` entry with a `file://` URL (potentially combined with symlinks in the working tree, per the CVE-2022-39253 technique), Git will locally clone content from an attacker-chosen local path into the external repository directory that Bazel then feeds into the build (BUILD files, srcs, etc.). This is a read/copy of file-system content from outside the intended repository/output-base boundary into a location the build graph consumes, which can leak local file contents (e.g., other repos on disk) into build outputs or influence build behavior, and it does so purely from content served by an untrusted Git remote — no local machine access, credentials, or trusted root-repo BUILD/.bzl files are required by the attacker.

### Likelihood Explanation
Any consumer using `git_repository`/`new_git_repository` with submodules enabled against a remote not fully trusted (a mirror, a forked/compromised upstream, or any repo whose commit/tag/branch content an attacker can influence) is exposed by default, since the override is unconditional and not gated by a flag — there is no opt-out.

### Recommendation
Do not force `protocol.file.allow=always` unconditionally. Restrict submodule transport to the protocols required for the specific submodule URL (e.g. only allow `file://` when the resolved absolute path is verified to be a descendant of the already-fetched checkout directory), or scope the override to a Git-version-specific compatibility shim with an explicit allowlist check, consistent with the intent of upstream Git's protocol-allow hardening.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` proof would extend `starlark_git_repository_test.sh`:
1. Create a "victim-local" directory outside the test's git repo directory containing a sentinel file (analogous to the existing `test_git_repository_invalid_commit` sentinel pattern at [2](#0-1) ).
2. Create an upstream repo whose `.gitmodules` declares a submodule with `url = "file://$SENTINEL_DIR"`.
3. Configure `git_repository(..., commit = <that commit>, recursive_init_submodules = True)`.
4. Run `bazel fetch`; assert the sentinel directory's contents were copied into `external/+git_repository+.../<submodule path>` — demonstrating a read across the intended repository boundary that a normal (non-overridden) Git installation would refuse.

I was not able to fully verify from the indexed code whether any additional Bazel-side path/`protocol.file.allow` restriction exists elsewhere (e.g., a later patch narrowing this to only trusted paths) — the search only surfaced the single unconditional override in `update_submodules()`, and the referenced Bazel issue (#17040) explaining the original rationale for this override was not retrievable in the index. If deeper verification of intervening changes is needed, a full checkout via a Devin session would be required since the index may not contain all historical revisions of this file.

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
