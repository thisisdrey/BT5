### Title
Unstaked QUIC connections' `max_concurrent_uni_streams` limit scales with attacker-influenceable RTT, allowing up to 7x the intended stream budget - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`compute_max_allowed_uni_streams_with_rtt` scales the per-connection concurrent uni-stream limit linearly with the connection's measured RTT for **all** peer types, including `ConnectionPeerType::Unstaked`, with no additional cap tying the result back to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`. Since QUIC's RTT estimate is derived in part from a peer-self-reported "ack delay" field, an unstaked remote client can inflate the RTT the leader measures on its connection by deliberately delaying ACKs while under-reporting the ack-delay value, causing `connection.rtt()` to trend toward `MAX_RTT_MS` and granting far more concurrent streams than the unstaked budget is supposed to allow.

### Finding Description
`cache_new_connection` reads `connection.rtt()`, clamps it to `MAX_RTT_MS` (350ms), and feeds it into `compute_max_allowed_uni_streams_with_rtt`: [1](#0-0) 

The function itself computes, for the `Unstaked` case, `streams = QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` (128) and then unconditionally scales it by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS`: [2](#0-1) 

With `REFERENCE_RTT_MS = 50` and `MAX_RTT_MS = 350`: [3](#0-2) 

the scaling factor ranges up to `350/50 = 7`, so an unstaked peer's `max_concurrent_uni_streams` can reach `128 * 7 = 896`, not the intended `128`. The existing unit test already documents this scaling occurring for `Unstaked` peers at 1.5x RTT (192 streams instead of 128): [4](#0-3) 

The `rtt_millis` value comes from `quinn`'s RTT estimator, which computes `latest_rtt` from `(ack_arrival_time - packet_send_time) - peer_reported_ack_delay`. The `ack_delay` field is supplied by the receiving peer itself and is not independently verified against the peer's actual observed delay before sending the ACK. An unstaked, unprivileged client controls both when it sends ACKs and what `ack_delay` value it reports in them, so it can deliberately withhold ACKs while reporting an artificially small `ack_delay`, inflating the leader's computed RTT toward `MAX_RTT_MS` without deviating from QUIC protocol conformance (staying under loss-detection/PTO thresholds). Nothing in `compute_max_allowed_uni_streams_with_rtt` bounds the Unstaked result back to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`; the BDP-scaling clamp only bounds `rtt_millis` itself, not the derived stream count for unstaked peers (unlike the staked path, which is separately clamped to `QUIC_MAX_STAKED_CONCURRENT_STREAMS` before RTT scaling is applied on top of it — worse, that clamp is applied to `streams` before the RTT multiplier, so even the staked cap is multiplied by up to 7x).

### Impact Explanation
This lets a zero-stake, unprivileged remote client that only opens a QUIC connection to the leader's public TPU port obtain up to ~7x the intended concurrent uni-stream budget (896 vs. 128) per unstaked connection, at no cost beyond normal connection setup and control of its own ACK timing. Combined with the unstaked connection-table limits, this proportionally multiplies the number of concurrently in-flight (and therefore sigverify/dedup/scheduling-queued) transaction/vote streams an attacker can push per connection, forcing the leader to spend sigverify, dedup, and scheduling work far exceeding any fee ever paid by the attacker — matching the stated "High" scope: "An unprivileged attacker can cheaply force sigverify, dedup, scheduling, or buffering work that vastly exceeds the fees ever collected, degrading the leader below true cost."

### Likelihood Explanation
This requires no stake, no gossip/peer control, and no protocol violation — only an unstaked TPU/QUIC client that controls its own ACK delay reporting, which is standard client-side QUIC behavior. It is fully reproducible deterministically in a unit test of `compute_max_allowed_uni_streams_with_rtt` over the `REFERENCE_RTT_MS..MAX_RTT_MS` domain, and the existing test suite already demonstrates the scaling for `Unstaked` at one RTT point, confirming the behavior is by design rather than incidental.

### Recommendation
Clamp the RTT-scaled stream count for `ConnectionPeerType::Unstaked` (and the RTT-scaled result generally) to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` / `QUIC_MAX_STAKED_CONCURRENT_STREAMS` respectively, e.g. apply `.min(QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS)` (and `.min(QUIC_MAX_STAKED_CONCURRENT_STREAMS)`) after the RTT multiplication in `compute_max_allowed_uni_streams_with_rtt`, so BDP-based RTT scaling can only compensate for legitimate throughput loss on long-latency links without allowing untrusted, self-reported RTT to unlock a stream budget beyond the peer-type ceiling.

### Proof of Concept
Extend `streamer/src/nonblocking/swqos.rs`'s test module with a full-domain sweep:

```rust
#[test]
fn test_max_allowed_uni_streams_unstaked_bounded_by_cap() {
    for rtt in REFERENCE_RTT_MS..=MAX_RTT_MS {
        let streams = compute_max_allowed_uni_streams_with_rtt(
            rtt,
            ConnectionPeerType::Unstaked,
            10_000,
        );
        assert!(
            streams <= QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
            "rtt={rtt} produced {streams} streams, exceeding cap {QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS}"
        );
    }
}
```

Running this against the current implementation fails once `rtt > REFERENCE_RTT_MS` (e.g. at `rtt = MAX_RTT_MS = 350`, `streams = 896 > 128`), proving the unstaked stream budget is not capped and can be inflated purely by the connection's (attacker-influenceable) measured RTT.

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
