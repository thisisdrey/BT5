## Analysis

The CIFS CVE's root cause is a specific pattern: **a length-prefixed protocol buffer contains attacker/peer-supplied offset+length fields that are used to slice into that buffer without validating the resulting byte range against the buffer's actual size**, leading to an out-of-bounds read.

The closest analog in this Go tree is the Windows **reparse-point (symlink/junction) parser**, which has exactly the same shape of bug.

### Entry point and sink

`readReparseLinkHandle` reads a fixed `MAXIMUM_REPARSE_DATA_BUFFER_SIZE` buffer via `DeviceIoControl(FSCTL_GET_REPARSE_POINT, ...)` and dispatches to the reparse-point buffer type: [1](#0-0) 

The actual string extraction happens in `SymbolicLinkReparseBuffer.Path()` / `MountPointReparseBuffer.Path()`, which compute slice indices `n1`/`n2` purely from the `SubstituteNameOffset`/`SubstituteNameLength` fields stored *inside* the reparse data — fields that come straight from the on-disk/filesystem-driver-returned buffer with **no validation that `n1`/`n2` fall within the bytes actually returned by `DeviceIoControl`**, then indexes an `unsafe.Pointer` cast to a `*[0xffff]uint16` array: [2](#0-1) 

The exact duplicate logic (same missing check) also exists in `syscall.Readlink`: [3](#0-2) 

### Why this matches the CIFS bug's shape

- CIFS: `DfsPath`/`NetworkAddress` offsets from a server-controlled referral entry are used to compute pointers without checking against the response buffer bounds → OOB read via `kstrndup`/`strnlen`.
- Go analog: `SubstituteNameOffset`/`SubstituteNameLength` from a reparse-point buffer (which any unprivileged local user/process can set on a junction via `FSCTL_SET_REPARSE_POINT` — junctions, unlike symlinks, do not require `SeCreateSymbolicLinkPrivilege`) are used to compute `n1:n2` indices into a `*[0xffff]uint16` (131070-byte) view of a much smaller (16384-byte) real allocation. Because the cast array size (`0xffff`) is far larger than the actual buffer, Go's normal slice-bounds-check is defeated — it checks against the fabricated `[0xffff]uint16` array type, not against the real allocation size, so out-of-bounds heap memory is read into the returned path string (or the process can crash on an unmapped page).

### Reachability

Any code path that resolves a reparse point — `os.Readlink`, `filepath.EvalSymlinks`, directory-walk code that calls `Lstat`/opens with `FILE_FLAG_OPEN_REPARSE_POINT`, or `os/root_windows.go`'s `readlinkat`/`checkSymlink` — ends up calling `readReparseLinkHandle` → `Path()`: [4](#0-3) 

This means an unprivileged local attacker who can place a junction/reparse point in a shared directory (temp dir, a downloaded archive that is extracted preserving reparse points, a removable/network volume) can craft `SubstituteNameOffset/Length` to trigger the OOB read the moment a victim process resolves the path — no elevated privilege needed to *create* a junction, only to observe/crash the victim's process.

### Caveat

I could not find any bounds check comparing `SubstituteNameOffset + SubstituteNameLength` against `bytesReturned` or the real buffer length anywhere in this call chain in the indexed sources — this is consistent with the pattern, but I was not able to fully trace whether any Windows-API-level guarantee (e.g., the filesystem driver itself validating `ReparseDataLength`) prevents malformed data from reaching `Path()` in practice; that would require testing against real reparse-point creation on Windows, which is outside what I can verify via static code search alone.

### Title
Unvalidated reparse-point string offsets cause out-of-bounds read in Windows symlink/junction resolution - (`src/internal/syscall/windows/reparse_windows.go`)

### Summary
`SymbolicLinkReparseBuffer.Path()` and `MountPointReparseBuffer.Path()` compute `n1`/`n2` slice bounds from `SubstituteNameOffset`/`SubstituteNameLength` fields stored in a reparse-point buffer without validating them against the buffer actually returned by `DeviceIoControl`, then index a `*[0xffff]uint16` unsafe-pointer view of that buffer. A junction/reparse point (creatable without special privilege) with crafted offset/length fields causes an out-of-bounds heap read whenever any process resolves the link via `os.Readlink`, `filepath.EvalSymlinks`, or similar.

### Finding Description
Attacker input: a reparse-point buffer (`SubstituteNameOffset`, `SubstituteNameLength`) set on a filesystem junction/mount point by an unprivileged local process via `FSCTL_SET_REPARSE_POINT` → Go entry point: `os.Readlink`/`filepath.EvalSymlinks` → `readReparseLinkHandle` (`src/os/file_windows.go:476`) reads a fixed 16 KiB buffer via `DeviceIoControl` → dispatches to `MountPointReparseBuffer.Path()`/`SymbolicLinkReparseBuffer.Path()` (`src/internal/syscall/windows/reparse_windows.go:66-94`) → failed check: no validation that `n1`/`n2` (derived from attacker-controlled offset/length fields) are within the actual returned buffer size → sink: `(*[0xffff]uint16)(unsafe.Pointer(&rb.PathBuffer[0]))[n1:n2:n2]` reads memory beyond the real allocation because the array type is far larger (131070 bytes) than the true buffer (16384 bytes), defeating Go's slice bounds checking.

### Impact Explanation
Concrete impact: disclosure of adjacent heap memory contents (leaked into the "resolved" symlink path string) or a process crash on an unmapped page when resolving a malicious junction/reparse point — a memory-safety violation triggered by untrusted on-disk data, matching Go's PUBLIC track criteria for a parser OOB bug reachable from ordinary filesystem operations.

### Likelihood Explanation
Any unprivileged local user can create a directory junction with `FSCTL_SET_REPARSE_POINT` (no `SeCreateSymbolicLinkPrivilege` required for junctions) with attacker-chosen `SubstituteNameOffset/Length`. Any other process (including privileged ones) that later resolves that path with `os.Readlink`, `filepath.EvalSymlinks`, `os/root_windows.go`'s `checkSymlink`, or directory-walking code triggers the vulnerable code path.

### Recommendation
In `Path()` (both `SymbolicLinkReparseBuffer` and `MountPointReparseBuffer`) and in `syscall.Readlink`, validate `SubstituteNameOffset + SubstituteNameLength` against the actual number of bytes returned by `DeviceIoControl` (or against `ReparseDataLength`) before computing `n1`/`n2`, and reject/error out if the computed range exceeds the real buffer.

// TestReparsePathOffsetOOB demonstrates that Path() does not validate
// SubstituteNameOffset/Length against the real buffer size, allowing

func TestReparsePathOffsetOOB(t *testing.T) {
	// Simulate a small reparse buffer as would be returned by a
	// truncated/malicious DeviceIoControl(FSCTL_GET_REPARSE_POINT) call.
	buf := make([]byte, 16) // much smaller than MAXIMUM_REPARSE_DATA_BUFFER_SIZE
	rb := (*windows.MountPointReparseBuffer)(unsafe.Pointer(&buf[0]))

	// Attacker-controlled offset/length far beyond the real 16-byte buffer.
	rb.SubstituteNameOffset = 0
	rb.SubstituteNameLength = 4000 // bytes, well past len(buf)

	// This reads out-of-bounds relative to `buf`'s real allocation because
	// Path() casts to a [0xffff]uint16 array, defeating bounds checking.
	got := rb.Path()

	// Expected (fixed) behavior: Path() should return an error/empty string
	// or panic safely instead of silently reading adjacent heap memory.
	if len(got) > 8 { // 16 bytes real == 8 uint16 == max valid path chars
		t.Fatalf("Path() returned %d chars from a 16-byte buffer; out-of-bounds read occurred: %q", len(got), got)
	}
}

func readReparseLinkHandle(h syscall.Handle) (string, error) {
	rdbbuf := make([]byte, syscall.MAXIMUM_REPARSE_DATA_BUFFER_SIZE)
	var bytesReturned uint32
	err := syscall.DeviceIoControl(h, syscall.FSCTL_GET_REPARSE_POINT, nil, 0, &rdbbuf[0], uint32(len(rdbbuf)), &bytesReturned, nil)

func checkSymlink(parent syscall.Handle, name string, origError error) error {
	link, err := readlinkat(parent, name)
	if err != nil {
		return origError
	}
	return errSymlink(link)
}

func readlinkat(dirfd syscall.Handle, name string) (string, error) {
	fd, err := openat(dirfd, name, windows.O_FILE_FLAG_OPEN_REPARSE_POINT, 0)
	if err != nil {
		return "", err
	}
	defer syscall.CloseHandle(fd)
	return readReparseLinkHandle(fd)
