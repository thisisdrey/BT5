### Title
Compilation of freshly-deployed contracts is performed at zero gas cost for empty-`method_name` FunctionCall receipts due to check ordering in `with_compiled_and_loaded` / `before_loading_executable` - ([File: runtime/near-vm-runner/src/wasmtime_runner/mod.rs, runtime/near-vm-runner/src/logic/gas_counter.rs])

### Summary
`WasmtimeVM::with_compiled_and_loaded` performs the full cache-lookup/compile/deserialize/link pipeline for a contract *before* the VM-independent method-name validation in `GasCounter::before_loading_executable` runs, and that validation short-circuits on an empty `method_name` without ever calling `add_contract_loading_fee`. Because `fix_contract_loading_cost` is `false` on mainnet, the only other charging point (`after_loading_executable`) is never reached either, so a `FunctionCall` receipt with `method_name = ""` against a fresh, uncached contract causes the node to actually compile the wasm module while burning essentially zero gas for that work.

### Finding Description
`with_compiled_and_loaded` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:686-834`) runs `cache.memory_cache().try_lookup(...)` at line 704, whose closure (lines 706-802) does the real work: reading the persistent cache, and on a miss, calling `self.compile_and_cache(&code, cache)` (line 726) to actually compile the wasm, then `Module::deserialize` (line 747) and `linker.instantiate_pre` (line 774). All of this executes unconditionally, regardless of `method`.

Only after this entire pipeline completes does the code call: [1](#0-0) 

`GasCounter::before_loading_executable` is where the empty-method-name check lives: [2](#0-1) 

Because `method_name.is_empty()` returns `Err(MethodEmptyName)` *before* the `fix_contract_loading_cost` branch is evaluated, `add_contract_loading_fee` (which charges `contract_loading_bytes`/`contract_loading_base`) is never invoked for empty-method calls, on any protocol version. `after_loading_executable` (lines 259-272), the legacy fallback charging path used when `fix_contract_loading_cost` is `false` (mainnet default), is also never reached since `before_loading_executable` already returned an error at line 815, short-circuiting `with_compiled_and_loaded` at lines 815-818.

The receipt itself is admitted because, at the current point in this checkout, `ActionsValidationError::FunctionCallEmptyMethodName` is only enforced when `ProtocolFeature::RejectEmptyMethodName` is enabled for the current protocol version, and only for `ValidateReceiptMode::NewReceipt`: [3](#0-2) 

The associated test explicitly documents that this is a not-yet-stabilized feature meant to close exactly this gap: pre-upgrade, an empty-method transaction is "admitted and fails on-chain in the VM with the old `MethodEmptyName` error", i.e. it still reaches `with_compiled_and_loaded`: [4](#0-3) [5](#0-4) 

So on any protocol version where `RejectEmptyMethodName` is not yet enabled (matching the question's mainnet assumption that `fix_contract_loading_cost` is also `false`), an attacker's `FunctionCall(method_name="")` receipt against a freshly-deployed, not-yet-cached contract will: (1) pass admission/action validation, (2) be routed to `WasmtimeVM::prepare` → `with_compiled_and_loaded`, (3) trigger a full compile (cache miss) plus deserialize/link, and only then (4) abort with `MethodResolveError::MethodEmptyName` without the loading fee ever being charged.

### Impact Explanation
This is a metering-totality violation: real CPU work (wasm compilation, which is the single most expensive per-call operation in the VM pipeline and the exact reason the `contract_loading_bytes`/`contract_loading_base` fee exists) is performed while zero gas is burnt for it. The scoped impact is increased block/chunk-application wall time when many distinct large, freshly-deployed contracts are called this way, i.e. a compute/liveness degradation rather than a fund-loss or consensus-divergence bug.

### Likelihood Explanation
Exploiting this at scale requires the attacker to deploy many *distinct* large contracts, since the compile-avoiding fast path (memory/persistent cache hit) applies to any contract already compiled once — repeated empty-method calls against the *same* contract do not re-trigger full compilation. Each distinct large contract deployment costs real NEAR for `DeployContract` action fees and storage staking proportional to `max_contract_size`, which bounds the attacker's ability to cheaply generate many "cache-miss" compile events. This economic cost ties the severity of the DoS to how cheap it is to deploy many maximal-size contracts relative to the compile-time cost imposed on validators, which was not independently benchmarked here.

### Recommendation
Move the `method_name.is_empty()` check (and any other VM-independent, pre-loading validation) ahead of the cache-lookup/compile/deserialize/link pipeline in `with_compiled_and_loaded`, so an empty method name (or any other reason to reject before wasm execution) short-circuits before compilation is even attempted — not merely before the fee is charged after the fact. Alternatively/complementarily, expedite stabilization of `ProtocolFeature::RejectEmptyMethodName` so empty-method-name `FunctionCall` actions are rejected at admission/`validate_actions_with_mode` and never reach the VM runner at all.

### Proof of Concept
Integration/runtime-test-loop plan:
1. Build a large (near `max_contract_size`) synthetic wasm contract with distinctive content (to avoid cache hits) and deploy it via `DeployContractAction`.
2. Submit a `FunctionCall` receipt/transaction with `method_name = ""`, `args = []`, and minimal `prepaid_gas` (e.g. a few Tgas, enough to cover action base fee only) directly against the runtime (bypassing `RejectEmptyMethodName` if it is enabled in the checked-out `PROTOCOL_VERSION`, or running on a protocol version where it is disabled, mirroring `test_reject_empty_method_name_protocol_upgrade`'s pre-upgrade branch).
3. Measure wall-clock time spent inside `WasmtimeVM::with_compiled_and_loaded`/`compile_and_cache` for this receipt, and record `gas_burnt` from the resulting `ExecutionOutcome`.
4. Assert that `gas_burnt` for the compile-triggering empty-method call is far below what `add_contract_loading_fee(wasm_bytes)` would charge for that contract size (i.e., the loading fee was never applied), while wall time is comparable to a normal first-time compile+link of a contract of that size.
5. Repeat across N distinct freshly-generated large contracts to show the wall-time cost scales with N despite near-zero aggregate `gas_burnt`, and compare against the case where `method_name` is non-empty (which does pay the loading fee via `after_loading_executable` when `fix_contract_loading_cost` is false, or via `before_loading_executable` when it is true).

    pub(crate) fn before_loading_executable(
        &mut self,
        config: &near_parameters::vm::Config,
        method_name: &str,
        wasm_code_bytes: u64,
    ) -> std::result::Result<(), super::errors::FunctionCallError> {
        if method_name.is_empty() {
            let error = super::errors::FunctionCallError::MethodResolveError(
                super::errors::MethodResolveError::MethodEmptyName,
            );
            return Err(error);
        }
        if config.fix_contract_loading_cost {
            if self.add_contract_loading_fee(wasm_code_bytes).is_err() {
                let error =
                    super::errors::FunctionCallError::HostError(super::HostError::GasExceeded);
                return Err(error);
            }
        }
        Ok(())
    }
