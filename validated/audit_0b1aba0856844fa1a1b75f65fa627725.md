### Title
Heap buffer over-read parsing unbounded "extra field" records in ijar's ZIP central-directory reader - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the per-entry "extra field" data of a ZIP central directory record with no bounds validation against the mapped input file, directly analogous to the PJSIP STUN bug where an unknown/attacker-supplied attribute length field is trusted without checking it against the remaining buffer.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight from the (attacker-controlled) ZIP central directory bytes and then walks the extra-field records with: [1](#0-0) 

```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) {
      *uncompressed_size = get_u8le(extra);
    }
    ...
```

`get_u2le`/`get_u4le`/`get_u8le` unconditionally dereference and advance the pointer with no bounds checks, as seen in `third_party/ijar/common.h`: [2](#0-1) 

The loop condition is `extra_p != p` — an *exact-equality* check, not a `<` bound check. If an attacker crafts a `data_size` (or a chain of extra-field records) such that `extra_p` jumps past the intended end pointer `p` instead of landing exactly on it, the loop does **not** terminate at the extra-field boundary. It keeps calling `get_u2le`/`get_u8le`, walking past the extra-field region, past the central directory, and potentially past the end of the `mmap`'d input file (`zipdata_in_`), reading whatever adjacent memory follows the mapping. This is the same bug class as CVE-2022-23537: an "unknown attribute"/extra-field length taken from untrusted input is used to advance a cursor without verifying it stays within the buffer, causing a heap/mapping over-read. Unlike the local-file-header parser (`ProcessLocalFileEntry`), which explicitly calls `EnsureRemaining()` before every field read (see `third_party/ijar/zip.cc:334-370`), the central-directory extra-field loop has no equivalent check at all.

This code is reachable from ordinary Bazel builds: `ijar` is the tool Bazel runs to strip method bodies from `.jar` files to produce header/interface jars for Java compilation (`run_ijar` in `java_common`, and the `ijar`/`stamp_jar` toolchain tools). A `.jar` file supplied via `http_archive`/`http_jar`/`http_file` or any other externally-fetched dependency that the build compiles with `java_library` will be fed into `ijar`'s `InputZipFile::ProcessNext → ProcessCentralDirEntry` path. [3](#0-2) 

### Impact Explanation
An attacker who controls the content served at a dependency URL (a hostile origin/mirror hosting a Java `.jar` artifact) can craft a ZIP central directory with a malformed extra-field chain that causes the ijar central-directory parser to read past the mapped input file. Because the mismatched cursor never becomes exactly equal to `p`, the loop can run for an extended number of iterations reading unrelated heap/mapped memory, which can crash the `ijar` build tool (denial of service for that specific build action) or, depending on memory layout, cause it to interpret adjacent process memory as ZIP64 size/offset fields, corrupting subsequent parsing decisions. This is a memory-safety bug in Bazel's own C++ tooling triggered purely by untrusted archive bytes that a build consumes, matching the reachable-surface guidance for "Extraction and patching" bugs (`ZipDecompressor`-class parsing issues) called out in the prompt.

### Likelihood Explanation
Any Bazel project that consumes a `.jar` file from an external, attacker-influenced source (e.g., `http_jar`, `http_archive` unpacking a `.jar`/`.aar`, or a Maven-style dependency fetched via a registry mirror) and compiles against it with `java_library`/`java_import` will invoke `ijar` on that file. Since the pinned `sha256`/`integrity` hash is set by the project owner to match the exact bytes an attacker chooses to publish at that URL (the attacker is the origin), there is no integrity check that would prevent this malformed file from being consumed — the checksum only verifies the file wasn't tampered with in transit, not that its ZIP structure is well-formed. Crafting a ZIP central directory with a misaligned extra-field is straightforward and requires no special privileges beyond controlling the served artifact.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry`, bound the extra-field walk with an explicit `<` comparison against the extra-field end pointer (not `!=`), and additionally validate that each `data_size` does not push `extra_p` past `p` before dereferencing further fields (mirroring the containment checks already present in `ExtraField::find` in `src/tools/singlejar/zip_headers.h:99-115`, and the `EnsureRemaining()` pattern used in `ProcessLocalFileEntry`). Reject/­error out the entry instead of continuing to parse when the extra-field length is inconsistent.

### Proof of Concept
A reproducible test can be added under `third_party/ijar` (e.g. a `zip_test.cc`/`ijar` unit test or a `src/test/shell/bazel` integration test similar to the `singlejar` `MalformedExtraField` test already in the codebase): [4](#0-3) 

1. Build a minimal ZIP file containing one central directory entry with `extra_field_length` set (e.g. 8 bytes) but with an internal extra-field record whose `data_size` (e.g. `0xF000`) is larger than the remaining extra-field bytes, so that after `extra_p += data_size`, `extra_p` skips past `p` instead of landing on it.
2. Run `ijar` (or directly unit test `InputZipFile::ProcessCentralDirEntry`) against this crafted archive.
3. Observe that the `while (extra_p != p)` loop does not terminate at the intended boundary and continues to call `get_u2le`/`get_u8le` on memory beyond the mapped extra-field/central-directory region, producing a crash (ASan heap-buffer-overflow/SEGV) or reading attacker-uncontrolled adjacent memory into `*uncompressed_size`/`*compressed_size`/`*offset`.

I was not able to fully trace every intermediate caller that wires an externally-downloaded `.jar` into `ijar`'s invocation (e.g., the exact `java_toolchain`/action wiring in `JavaToolchainProvider`), so the end-to-end "external URL → ijar invocation" path should be confirmed by a background agent building a minimal `java_library` depending on an `http_jar` target and inspecting the generated `ijar` action's inputs.

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];

inline u4 get_u4be(const u1 *&p) {

    p += 4;
    return x;

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
