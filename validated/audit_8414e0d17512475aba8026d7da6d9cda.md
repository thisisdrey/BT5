### Title
Uncharged Memory Expansion When Copying Precompiled-Contract Return Data in Legacy `callToPrecompiledAddress` Path - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program.callToPrecompiledAddress` copies the full byte array returned by a precompiled contract into VM memory. When the `allowTvmSelfdestructRestriction` fork is *not* active, the copy is done with the legacy call `this.memorySave(msg.getOutDataOffs().intValue(), out.getRight())`, which allocates and writes memory sized to the **actual returned data length**, not to the `outDataSize` that the calling contract declared (and that was already energy-charged for) when it issued the `CALL`/`STATICCALL`/`DELEGATECALL`. [1](#0-0) 

### Finding Description
The energy cost for a `CALL`-family opcode is computed once, before the external call executes, in `EnergyCost.getCalculateCallCost`, which derives the memory-expansion cost only from the caller-declared `outOffset`/`outSize` operands on the stack: [2](#0-1) 

That pre-charged region is what `Program.memoryExpand(outDataOffs, outDataSize)` reserves before the call is dispatched in `exeCall`: [3](#0-2) 

For calls into a real contract address, the return-data copy back into memory is correctly bounded to the caller-declared `outDataSize` via `memorySaveLimited`, so the energy already paid for memory expansion matches the memory actually written: [4](#0-3) 

However, for calls into a **precompiled contract address**, `callToPrecompiledAddress` copies the precompile's *entire* output buffer, and — in the pre-`allowTvmSelfdestructRestriction` code path — does so with the unbounded 2-argument `memorySave(offset, out.getRight())` overload instead of the size-limited variant: [1](#0-0) 

`Program.memorySave(int addr, byte[] value)` resolves to `memorySave(addr, allocSize, value)` with `allocSize = value.length` (the full returned array), which calls `Memory.extendAndWrite(addr, allocSize, value)`: [5](#0-4) 

`Memory.extendAndWrite` unconditionally calls `extend(address, allocSize)` before writing, growing the VM memory buffer to fit the full return payload — regardless of how small the caller's declared `outDataSize` was, and regardless of whether the corresponding `calcMemEnergy` charge in `EnergyCost.getCalculateCallCost` covered that much memory: [6](#0-5) 

The only energy actually charged for the precompile invocation is `contract.getEnergyForData(data)`, which is a function of the **input** size, not the output size: [7](#0-6) 

This is structurally the same bug class as the reported `ExpressRelay.multicall` issue: an external/sub-call's return payload is copied into memory with a size controlled by the callee rather than being bounded by what the caller declared and paid for, allowing a large-but-cheap-to-produce output to inflate memory usage/energy accounting for free.

### Impact Explanation
If a precompiled contract's output length can be inflated by attacker-controlled input while its energy cost (`getEnergyForData`) does not scale proportionally with the output size, a contract invoking that precompile via low-level `CALL`/`STATICCALL` with a tiny declared `outDataSize` would still have the VM allocate/copy the *full* oversized output into memory at zero extra energy cost. This decouples real resource consumption (CPU/memory for `Memory.extend`/`arraycopy`, subsequent quadratic `calcMemEnergy` costs for later opcodes operating over the inflated `softSize`) from the energy actually billed to the transaction sender, which is a metering-integrity flaw: it can be used to force disproportionate node-side memory/CPU work per unit of energy paid, which is the DoS/gas-griefing pattern described in the source report.

### Likelihood Explanation
This path is only reachable while the `allowTvmSelfdestructRestriction` fork/proposal is *not yet activated* for the executing chain (private/forked chains, or older un-upgraded networks) — on chains where the proposal is enabled, `Program.java:1769` uses the size-limited `memorySave(offset, outDataSize, out.getRight())` instead, which caps the write to the caller-declared size. I could not fully confirm from the code available whether this proposal is enabled by default at genesis for new/forked chains or requires committee activation; if it defaults to "off" until a committee vote, any new/private java-tron deployment (a very common scenario for exchanges, testnets, and app-chains that fork this codebase) would run with the vulnerable path active by default. This is a single-transaction, unprivileged trigger (any contract call reaching a precompiled address with a crafted small `outDataSize`) — no privileged role is required to exploit it once the pre-condition (fork not active) holds.

### Recommendation
Make the size-limited memory write to `Program.memorySave(msg.getOutDataOffs().intValueSafe(), msg.getOutDataSize().intValueSafe(), out.getRight())` unconditional in `callToPrecompiledAddress`, rather than gating it behind `VMConfig.allowTvmSelfdestructRestriction()`, so that memory writes from precompiled-contract results are always bounded by the caller-declared, energy-charged `outDataSize`, matching the behavior already used for ordinary contract calls in `Program.callToAddress` (`memorySaveLimited`). If backward-compatibility for chains not yet on the fork is required, additionally ensure `EnergyCost.getCalculateCallCost`/`calcMemEnergy` charges for the *actual* returned size before any unlimited write is permitted.

### Proof of Concept
Conceptual PoC (cannot be executed in this environment):
1. Deploy a contract that issues a low-level `STATICCALL`/`CALL` to a precompiled contract address with a very small `outDataSize` (e.g., 32 bytes) in the memory-expansion stack arguments, on a java-tron network where `allowTvmSelfdestructRestriction` has not been activated.
2. Craft the precompile's input so that its returned byte array (`out.getRight()` in `Program.callToPrecompiledAddress`) is much larger than 32 bytes, while `contract.getEnergyForData(data)` remains cheap (input-size-based, not output-size-based).
3. Observe that `Program.memorySave(offset, out.getRight())` (2-arg overload) extends VM memory to fit the entire oversized output via `Memory.extendAndWrite`, at an energy cost far below what `calcMemEnergy`'s quadratic memory-expansion formula would normally charge for that memory size — this decoupling can be repeated/amplified across a batch of internal calls in a single transaction to multiply node-side memory/CPU cost per unit of energy billed.

  public static void exeCall(Program program, DataWord adjustedCallEnergy,
      DataWord codeAddress, DataWord value, DataWord tokenId, boolean isTokenTransferMsg) {

    DataWord inDataOffs = program.stackPop();
    DataWord inDataSize = program.stackPop();

    DataWord outDataOffs = program.stackPop();
    DataWord outDataSize = program.stackPop();

    program.memoryExpand(outDataOffs, outDataSize);
    int op = program.getCurrentOpIntValue();
    MessageCall msg = new MessageCall(
        op, adjustedCallEnergy, codeAddress, value, inDataOffs, inDataSize,
        outDataOffs, outDataSize, tokenId, isTokenTransferMsg);

    PrecompiledContracts.PrecompiledContract contract =
        PrecompiledContracts.getContractForAddress(codeAddress);
    if (contract != null) {
      if (program.isConstantCall()) {
        contract =  PrecompiledContracts.getOptimizedContractForConstant(contract);
      }
      program.callToPrecompiledAddress(msg, contract);
    } else {
      program.callToAddress(msg);
    }
    program.step();
  }

  public void extend(int address, int size) {
    if (size <= 0) {
      return;
    }
    final int newSize = addExact(address, size, VMConfig.disableJavaLangMath());
    int toAllocate = newSize - internalSize();
    if (toAllocate > 0) {
      addChunks((int) ceil((double) toAllocate / CHUNK_SIZE, VMConfig.disableJavaLangMath()));
    }

    toAllocate = newSize - softSize;
    if (toAllocate > 0) {
      toAllocate = (int) ceil((double) toAllocate / WORD_SIZE,
          VMConfig.disableJavaLangMath()) * WORD_SIZE;
      softSize = addExact(softSize, toAllocate, VMConfig.disableJavaLangMath());

      if (programListener != null) {
        programListener.onMemoryExtend(toAllocate);
      }
    }
