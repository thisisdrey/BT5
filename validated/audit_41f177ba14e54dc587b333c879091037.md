### Title
Unhandled Integer/Length-Underflow Exception in `ValidateMultiSign` Precompiled Contract Causes Uncaught Crash Path Inconsistent With `BatchValidateSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (`org.tron.core.vm.PrecompiledContracts.ValidateMultiSign#execute`) parses fully attacker-controlled TVM calldata using unchecked, ABI-derived offsets and lengths (`extractBytesArray` / `extractSigArray` / `extractBytes`) before entering any `try/catch`. This mirrors the CryptoLib `Crypto_TC_Prep_AAD` bug class: a length/offset value taken directly from untrusted input is used to compute a slice boundary (`Arrays.copyOfRange(data, offset, offset + len)`) without validating that the derived quantity is non-negative and in-bounds, which can throw `NegativeArraySizeException` / `ArrayIndexOutOfBoundsException`. Unlike the sibling contract `BatchValidateSign`, whose `execute()` wraps the entire parsing/verification path in `try { return doExecute(data); } catch (Throwable t) { ... }` [1](#0-0) , `ValidateMultiSign.execute()` has no such top-level guard [2](#0-1) .

### Finding Description
`ValidateMultiSign.execute(byte[] rawData)` only rejects malformed calldata via `isValidAbiEncoding(...)` when `VMConfig.allowTvmOsaka()` is active (a not-yet-activated hard-fork flag, per the TIP-854 tests) [3](#0-2) . Absent that flag, the method proceeds directly to `DataWord.parseArray(rawData)` and unguarded array indexing (`words[0]`, `words[1]`, `words[2]`, `words[3]`), and then into `extractBytesArray`/`extractSigArray`:

```
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  for (int i = 0; i < len; i++) {
    int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
    int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
    bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen);
  }
  return bytesArray;
}
``` [4](#0-3) 

`extractBytes` then performs the equivalent of the vulnerable CryptoLib pattern — computing a buffer slice boundary from an attacker-supplied length without bounds validation:
```
private static byte[] extractBytes(byte[] data, int offset, int len) {
  return Arrays.copyOfRange(data, offset, offset + len);
}
``` [5](#0-4) 

Because `bytesLen`/`bytesOffset` are derived from arbitrary attacker-controlled 256-bit words truncated via `intValueSafe()`, a crafted calldata can make `len` negative or `offset + len` exceed `data.length`, throwing `NegativeArraySizeException` or `ArrayIndexOutOfBoundsException`. This throw occurs **outside** the `try { ... } catch (Throwable t) { ... }` block that only wraps the signature-verification loop further down in `ValidateMultiSign.execute()` [6](#0-5) , so it propagates uncaught out of `execute()`.

The existence of the TIP-854 hardening (`isValidAbiEncoding`) and the dedicated `testTip854OuterFrameContainment` regression test — which explicitly asserts, for both `ValidateMultiSign` and `BatchValidateSign`, that "outer frame must not inherit an exception" after a `CALL` with malformed calldata [7](#0-6)  — confirms this exact bug class (uncaught exception from length/offset underflow reachable via a single `CALL`) was previously a real concern for these two precompiles. However, that test only exercises the path with `VMConfig.initAllowTvmOsaka(1)` set, i.e. after the new guard is active; it does not cover the pre-activation window in which `ValidateMultiSign` still lacks any outer `try/catch`, unlike `BatchValidateSign`.

### Impact Explanation
Any account can trigger this by issuing a `CALL`/`STATICCALL` (directly via a transaction or from within a smart contract) to the `ValidateMultiSign` precompiled contract address with crafted calldata. If the exception is not fully absorbed by a higher-level TVM exception handler (this could not be conclusively confirmed within the scope of this investigation because the implementation of `Program.callToPrecompiledAddress` was not fully inspected), the uncaught `RuntimeException` could propagate through transaction execution and disrupt processing of that transaction/block — a Denial-of-Service condition analogous to the segmentation fault caused by the unsigned-integer underflow in `Crypto_TC_Prep_AAD`. At minimum, it is a confirmed inconsistency: `BatchValidateSign` defends against the same class of malformed input with a blanket `catch (Throwable t)`, while `ValidateMultiSign` does not, meaning the two "same purpose" precompiles have materially different exception-safety guarantees for identical attacker-supplied ABI-encoded arrays.

### Likelihood Explanation
High reachability: `ValidateMultiSign` is a standard TVM precompiled contract callable by any unprivileged contract-deployer or transaction sender without special permissions, and its entire calldata is attacker-controlled ABI-encoded input. The only mitigating factor is the not-yet-activated `allowTvmOsaka` guard; until that hard fork gate is enabled network-wide, no calldata-shape validation occurs on this specific code path.

### Recommendation
Apply the same defensive pattern used in `BatchValidateSign.execute()` to `ValidateMultiSign.execute()`: wrap the entire method body (or at least the `DataWord.parseArray`/`extractBytesArray`/`extractSigArray` calls) in a `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }`, and/or make the `isValidAbiEncoding` bounds check unconditional (not gated behind `VMConfig.allowTvmOsaka()`) for both `ValidateMultiSign` and `BatchValidateSign`, so malformed ABI-encoded length/offset fields are rejected before any arithmetic or array-slicing operation is performed.

### Proof of Concept
Conceptually (cannot be executed without a running node):
1. Craft calldata for `validateMultiSign(address,uint256,bytes32,bytes[])` where the dynamic `bytes[]` array's per-element length word is set to a huge value (e.g. `0xFFFFFFFF...`) so that `words[...].intValueSafe()` truncates to a negative `int`.
2. Deploy/call a contract that issues a `CALL` to the `ValidateMultiSign` precompile address (`0x0000...1005` or equivalent) with this calldata, with `VMConfig.allowTvmOsaka()` not yet activated (current mainnet state per the TIP-854 gating in the code).
3. Execution reaches `extractBytesArray` → `extractBytes` → `Arrays.copyOfRange(data, offset, offset + len)` with a negative `len`, throwing `NegativeArraySizeException` outside of any `try/catch` in `ValidateMultiSign.execute()`.
4. Observe whether this exception is absorbed at a higher layer (as it should be for `BatchValidateSign`) or propagates further — the asymmetry between the two contracts is confirmed by source inspection; the ultimate blast radius (transaction revert vs. broader failure) depends on code in `Program.callToPrecompiledAddress` that could not be fully verified in this investigation.

  // batchValidateSign with malformed calldata must (a) push 0 onto the outer
  // stack, (b) leave the outer frame free of any propagated exception, and
  // (c) allow the outer frame to continue executing afterwards.
  @Test
  public void testTip854OuterFrameContainment() throws ContractValidateException {
    byte prePrefixByte = DecodeUtil.addressPreFixByte;
    DecodeUtil.addressPreFixByte = Constant.ADD_PRE_FIX_BYTE_MAINNET;
    VMConfig.initAllowTvmOsaka(1);
    try {
      for (PrecompiledContracts.PrecompiledContract contract :
          new PrecompiledContracts.PrecompiledContract[]{
              new PrecompiledContracts.ValidateMultiSign(),
              new PrecompiledContracts.BatchValidateSign()}) {
        invoke = new ProgramInvokeMockImpl();
        InternalTransaction interTrx = new InternalTransaction(
            Protocol.Transaction.getDefaultInstance(),
            InternalTransaction.TrxType.TRX_UNKNOWN_TYPE);
        program = new Program(new byte[0], new byte[0], invoke, interTrx);
        // inDataSize=0 ⇒ data=[] ⇒ fewer than H=5 head words ⇒ guard rejects.
        MessageCall messageCall = new MessageCall(
            Op.CALL, new DataWord(10000),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), false);
        program.callToPrecompiledAddress(messageCall, contract);

        Assert.assertNull(contract.getClass().getSimpleName()
                + ": outer frame must not inherit an exception",
            program.getResult().getException());
        Assert.assertEquals(contract.getClass().getSimpleName() + ": inner CALL pushes 0",
            DataWord.ZERO(), program.getStack().pop());
        // Outer frame continues: another stack op works without throwing.
        program.stackPush(new DataWord(1));
        Assert.assertEquals(new DataWord(1), program.getStack().pop());
      }
    } finally {
      VMConfig.initAllowTvmOsaka(0);
      DecodeUtil.addressPreFixByte = prePrefixByte;
    }
  }
