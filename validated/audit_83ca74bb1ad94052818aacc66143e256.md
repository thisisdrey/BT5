### Title
Resolver of `ft_resolve_withdraw` blindly trusts the attacker-controlled token's reported `used` amount, letting the Verifier's internal ledger become under-collateralized relative to real custody — (`File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs`)

### Summary
`ft_resolve_withdraw` computes the refund credited back to `sender_id` solely from the `U128` value returned by the withdrawn token's `ft_transfer_call` promise, without any check that this reported value matches the amount actually retained/refunded on the token's own ledger. Since token deposits are permissionless (`ft_on_transfer` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs` accepts any NEP-141 predecessor as a valid `TokenId`), an attacker can deploy a malicious FT contract that unconditionally sends the full `amount` to `receiver_id` while reporting `used = 1`, causing the Verifier to re-credit `sender_id` with `amount - 1` internally while its real custody balance of that token was fully drained externally.

### Finding Description
The binding that should hold is:

`ledger_delta(sender_id, token) == real_custody_delta(Verifier_account, token)`

i.e. every internal balance change made by `ft_resolve_withdraw` must correspond to an equal-and-opposite change in the Verifier's actual NEP-141 balance for `token`, so that `sum(internal ledger balances for TokenId) <= real FT balance held by Verifier account`.

Path:
1. `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:60-74`) synchronously debits `owner_id`'s internal balance by the full `amount` via `self.withdraw(...)` before any promise executes.
2. `do_ft_withdraw` (lines 118-151) issues `ft_transfer_call(receiver_id, amount, memo, msg)` against the attacker-controlled `token` contract, attaching the Verifier's real token balance transfer.
3. `ft_resolve_withdraw` (lines 157-194) reads the promise result and computes:
```rust
Ok(Ok(used)) => used.0.min(amount.0),
...
let refund = amount.0.saturating_sub(used);
if refund > 0 {
    self.deposit(sender_id, [(Nep141TokenId::new(token).into(), refund)], Some(REFUND_MEMO))...
}
```
This trusts `used` unconditionally — it is exactly the value the callee's `ft_transfer_call` chooses to return, with no verification against a real balance query (`ft_balance_of`) or any invariant check against what was actually moved on `token`'s ledger.

An honest, standard-compliant NEP-141 token guarantees `used == amount - (amount actually refunded back to the Verifier's real account on that token's ledger)`, so the internal credit mirrors the real refund and the invariant holds. A malicious token controlled by the withdrawing attacker breaks this equivalence: it can transfer the full `amount` to `receiver_id` (also attacker-controlled) and return `used = 1`. `ft_resolve_withdraw` then credits `sender_id` with `amount - 1` internally via `self.deposit`, even though the Verifier's real balance of `token` was reduced by the full `amount` and nothing was refunded back on-chain. The result: internal ledger for that `TokenId` now says `amount - 1` exists, backed by `0` real tokens in the Verifier's account — an under-collateralized ledger entry ("Verifier owes more than it custodies").

None of the existing guards mitigate this: `assert_one_yocto`/`#[private]`/`#[pause]` only gate call authorization, not the trustworthiness of `used`; there is no `checked_*`/balance-verification step comparing `used` against the token's real accounting; and `self.deposit` in `contracts/defuse/src/contract/tokens/mod.rs:18-74` unconditionally increases `total_supplies` and `token_balances` for any `TokenId`, with no cross-check against custodied balance.

### Impact Explanation
This manufactures internal ledger balance for a `TokenId` not backed by real custodied tokens — matching the explicitly listed Critical category "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies," and "a refund or resolver credit that does not match what failed to settle" (nothing failed; the transfer succeeded in full, yet a refund was still credited). While the immediately affected `TokenId` is the attacker's own deployed token, this phantom balance is fungible within the Verifier's intents system: the attacker can subsequently use the manufactured `amount - 1` internal balance in signed swap intents against real counterparties (other users' legitimate tokens), effectively extracting real value backed by nothing. This is repeatable per attacker-controlled token and per withdrawal call, with no bound other than gas/promise scheduling.

### Likelihood Explanation
Preconditions are fully within the stated unprivileged attacker capability: deploy and control an arbitrary FT contract, deposit its own tokens into the Verifier via the permissionless `ft_on_transfer`, then call `ft_withdraw` with `msg` set (to force the `is_call` / `ft_transfer_call` branch) so `ft_resolve_withdraw` parses a JSON `U128` from the promise result. Cost is a single deposit + withdraw transaction and a bespoke FT contract deployment; fully repeatable and deterministic.

### Recommendation
Do not trust the callee's self-reported `used` value for arbitrary/permissionlessly-listed tokens. Verify the real balance change on the token contract (e.g., query `ft_balance_of(Verifier_account)` before and after, or require refunds to be actual token transfers back to the Verifier rather than internally-fabricated ledger credits), or restrict withdrawal-refund crediting to a verified real transfer-back rather than the promise's return value alone.

### Proof of Concept

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }

    pub(crate) fn deposit(

        owner_id: AccountId,

        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())

            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)

            }

                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
