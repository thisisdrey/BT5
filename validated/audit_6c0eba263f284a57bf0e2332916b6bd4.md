### Title
Out-of-bounds read while parsing the ZIP central directory "property table" (CDH entries) in ijar - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP reader walks the memory-mapped Central Directory of a jar as a flat list of Central Directory Header (CDH) "properties" (filename, extra-field, comment) using raw pointer arithmetic, with **no bounds checking** against the end of the mapped file — unlike the sibling local-file-header parser, which explicitly bounds-checks via `EnsureRemaining()`.

### Finding Description
`ProcessCentralDirEntry` reads a CDH's `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and unconditionally advances the cursor `p` by those (16-bit, up to 65535) lengths, then dereferences the extra-field sub-records in a `while (extra_p != p)` loop that trusts each `data_size` field to correctly delimit the walk: [1](#0-0) 

Contrast this with `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every variable-length read (`file_name`, `extra_field`) to guarantee the read stays inside the mapped buffer: [2](#0-1) [3](#0-2) 

`ProcessCentralDirEntry` has no equivalent guard: it does not verify that `file_name_length`, `extra_field_length`, `file_comment_length`, or the extra-field `data_size` values keep `p`/`extra_p` inside the mmap'd region before advancing and dereferencing (`get_u2le`, `get_u4le`, `get_u8le`, `memcpy` into `filename`). The comment in the code even asserts a false safety invariant — "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — which does not hold for a maliciously crafted CDH chain whose declared lengths point past the actual mapped file length: [4](#0-3) 

This routine is driven from `FindZipCentralDirectory`/`InputZipFile::ProcessNext`/`CalculateOutputLength`, which iterate the central directory as a table of CDH "properties" exactly analogous to the X3F property-table list walked without bounds checks in the LibRaw CVE: [5](#0-4) [6](#0-5) 

Reachability: ijar is Bazel's interface-jar generator, invoked on `.jar` inputs to Java rules — including jars that originate from `http_archive`/`http_jar`/`http_file` fetches or `java_import` targets pointing at externally supplied jars. A hostile origin server or mirror that serves a crafted jar (whose bytes exactly match whatever checksum a user pins, since the attacker controls the artifact from the start) results in `ProcessCentralDirEntry` reading a CDH with an inflated `file_name_length`/`extra_field_length`/`comment_length`/`data_size` that walks `p`/`extra_p` past the end of the `mmap`'d input file.

### Impact Explanation
An out-of-bounds read past the mapped file's end can crash the Bazel build (SIGSEGV on an unmapped page) or, since the read bytes flow into `filename` (via `memcpy`) and central-directory–derived size/offset fields used later in `ProcessFile`/`UncompressFile`, it can leak adjacent process memory into build outputs (the generated interface jar) or corrupt downstream JAR-processing decisions (bad offsets driving reads elsewhere in the mapped region). This matches the reachable/attacker-published-content pattern of the LibRaw analog: an out-of-bounds read in a table-of-entries parser driven by untrusted length fields.

### Likelihood Explanation
No checksum, structural integrity check, or containment mechanism in Bazel prevents this: `sha256`/`integrity` on `http_archive`/`http_jar` only certify that fetched bytes match a pinned digest — they say nothing about the *structural validity* of the ZIP/JAR's Central Directory. `FindZipCentralDirectory` only sanity-checks that `central_dir_offset + central_dir_size <= in_length`, but does nothing to bound the per-entry `file_name_length`/`extra_field_length`/`comment_length`/extra-field `data_size` fields consumed inside `ProcessCentralDirEntry`, so a single malformed CDH entry deep inside an otherwise-valid-looking central directory can still walk off the end of the mapped file. Any project depending on an externally hosted jar (or a first-time/unpinned `http_jar`/`http_archive` fetch, or a `java_import` on a jar built from an untrusted mirror) triggers this path automatically during the build, with default flags, on a current release.

### Recommendation
Add bounds checks (analogous to `EnsureRemaining()` in `ProcessLocalFileEntry`) in `ProcessCentralDirEntry` before consuming `file_name_length`, `extra_field_length`, `file_comment_length`, and before advancing `extra_p` by each extra-field's `data_size`, verifying at every step that the resulting pointer stays within `[bytes, bytes + in_length)`. Fail parsing with an error rather than continuing the walk if any declared length would run past the mapped region.

### Proof of Concept
1. Build a syntactically-valid small ZIP/JAR with one entry.
2. In its single Central Directory Header, patch `file_name_length` (or `extra_field_length`/`comment_length`, or an extra-field `data_size`) to a large value (e.g. `0xFFFF`) such that `p + file_name_length` exceeds `bytes + in_length`, while keeping the End Of Central Directory record's `central_dir_size` self-consistent with the on-disk layout so `FindZipCentralDirectory`'s only check (`central_dir_offset + central_dir_size <= in_length`) still passes.
3. Serve this file at a URL and reference it via `http_jar`/`http_archive`/`java_import` with `sha256` pinned to the crafted file's own hash (attacker fully controls the published bytes and thus the pinned digest for a first-time dependency).
4. Run `bazel build` on a target depending on it; ijar's `ProcessCentralDirEntry` (invoked transitively from `ijar` binary / `Create`/`ProcessAll`) reads past the mmap'd file boundary, which can be demonstrated as a crash (SIGSEGV under ASan) or an out-of-bounds read flagged by AddressSanitizer in a `BuildIntegrationTestCase`/`src/test/shell/bazel` reproduction that builds ijar with ASan and feeds it the crafted jar directly (`ijar crafted.jar out-interface.jar`).

  u8 compressed, uncompressed;

    return false;

      return false;
    }

    return false;
  }

  return true;
}

// Reads and returns some metadata of the next file from the central directory:
// - compressed size
// - uncompressed size
// - whether the entry is a class file (to be included in the output).
// Precondition: p points to the beginning of an entry in the central dir
// Postcondition: p points to the beginning of the next entry in the central dir
// Returns true if the central directory contains another file and false if not.
// Of course, in the latter case, the size output variables are not changed.
// Note that the central directory is always followed by another data structure
// that has a signature, so parsing it this way is safe.
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
