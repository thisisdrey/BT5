## Title
StackerDB chunk signatures don't bind the target contract, enabling cross-lane chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::sign`/`verify` only authenticate `(slot_id, slot_version, data_hash)` and never bind the specific `QualifiedContractIdentifier` (StackerDB contract / "lane") the chunk was written for. Because every `.signers-{0|1}-{message_id}` StackerDB contract for a given reward-cycle parity assigns identical `slot_id`s to the same signer addresses (the slot list comes from the same `stackerdb-get-signer-slots-page` call), a chunk legitimately signed and broadcast for one message lane (e.g. `BlockResponse`, contract `signers-0-1`) can be captured off the wire by any unprivileged observer and replayed into a *different* lane (e.g. `StateMachineUpdate`, contract `signers-0-2`) that the same signer also owns at the same `slot_id`. The replica accepts and re-broadcasts it as legitimate content for the wrong contract because the write-path validation only checks that the signature recovers to the slot's owner for *that* contract — it never checks that the signature was produced for that contract.

### Finding Description
The signed digest is: [1](#0-0) 

It hashes only `slot_id`, `slot_version`, and `data_hash`. There is no contract/lane identifier in the digest, so a signature is valid for *any* StackerDB contract in which that address owns that `slot_id`.

The write-path validation checks the signature only against the slot owner of the specific contract being written to, never checking that the signature itself commits to that contract:
- HTTP path (`POST /v2/stackerdb/...`) resolves the slot's owner for `contract_identifier` and calls `try_replace_chunk`, which calls `slot_desc.verify(&slot_validation.signer)` — no contract binding: [2](#0-1) 
- P2P path performs the same check in `validate_received_chunk`, used both for `StackerDBGetChunkInv` sync results and for `handle_unsolicited_StackerDBPushChunk` (including the buffered "FutureView" branch): [3](#0-2) 

All signer-message lanes for a given reward-cycle parity share the exact same slot-to-signer assignment, because every `.signers-{set}-{message_id}` contract reads the same underlying page from `.signers`: [4](#0-3) 
This is directly confirmed by the test showing that all `signers-{signer_set}-{message_id}` contracts return the identical slot list for a fixed `signer_set`: [5](#0-4) 

The lanes carry semantically distinct message types (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`): [6](#0-5) 

Once a replica accepts a replayed chunk (because it out-versions what that lane currently holds and size/write-count limits pass), it is stored and unconditionally rebroadcast network-wide to peers as a `StackerDBPushChunk`: [7](#0-6) 

### Impact Explanation
This breaks the equality "signed for lane/contract X" vs. "accepted and stored into lane/contract Y." An attacker with no signing key and no privileged role — merely someone who has observed one broadcast chunk (chunks are gossiped in plaintext over the p2p StackerDB protocol and also servable via the public HTTP `GET`/inventory endpoints) — can inject that chunk's exact bytes into a different signer-message lane owned by the same signer address, as long as the target lane's stored slot version for that slot is currently lower. Nodes that replicate the target lane will store it and propagate it network-wide as authentic content for that lane, corrupting the signer/miner coordination data that downstream consumers (e.g. `stacks-signer`) parse expecting a specific `SignerMessage` variant for that lane. This matches "network-wide propagation of forged data" (Critical) since the data is neither authentic for that lane nor rejectable by any implemented check.

### Likelihood Explanation
Medium-to-high. It requires: (1) a signer address that owns the same `slot_id` in two lanes of the same reward-cycle parity — which is guaranteed by construction since all lanes for a parity share the identical slot list — and (2) the target lane's current slot version being behind the replayed chunk's version, which is common for lower-traffic lanes (e.g. `BlockPreCommit`) relative to higher-traffic ones (e.g. `BlockResponse`). No secret key, node role, or elevated access is required; only passive observation of one broadcast chunk plus a single unauthenticated write (HTTP POST or unsolicited P2P push) to the target node.

### Recommendation
Bind the signed digest to the specific StackerDB contract (and ideally the expected message-type/lane) it is intended for, e.g. include the `QualifiedContractIdentifier` (and/or `MessageSlotID`) bytes in `SlotMetadata::auth_digest`, and reject any chunk whose signature does not commit to the contract being written. This closes the cross-lane/cross-contract replay path while remaining backward-compatible if versioned appropriately.

### Proof of Concept
1. Signer S has private key `sk`; via `stackerdb-get-signer-slots-page`, S owns `slot_id = 5` in every lane for reward-cycle parity `p` (`signers-p-1` = BlockResponse, `signers-p-2` = StateMachineUpdate, `signers-p-3` = BlockPreCommit) since all three contracts return the same slot list, per `signers_db_get_slots`.
2. S legitimately signs and pushes a `StateMachineUpdate` chunk to `signers-p-2`, slot 5, version 10 — this is broadcast in cleartext over the p2p StackerDB gossip protocol.
3. Attacker M (no keys) observes/captures this `StackerDBChunkData { slot_id: 5, slot_version: 10, sig, data }`.
4. M sends the identical `StackerDBChunkData` (unchanged bytes) as a `POST` to the target node's `signers-p-3` (BlockPreCommit) contract, or as an unsolicited `StackerDBPushChunk` p2p message for that contract, where slot 5's currently stored version is `< 10`.
5. `try_replace_chunk`/`validate_received_chunk` look up the slot-5 owner for `signers-p-3` (also S, since slot assignment is shared), call `slot_desc.verify(&signer)` — which succeeds because the signature only ever attested to `(5, 10, data_hash)`, never to which contract it was for — and the chunk is accepted, stored, and rebroadcast as if it were a legitimate `BlockPreCommit` payload from S, even though the bytes actually decode as a `StateMachineUpdate` message (or arbitrary bytes) and were never signed for that lane.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
