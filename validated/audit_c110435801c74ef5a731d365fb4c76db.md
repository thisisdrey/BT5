### Title
Non-constant-time authorization comparison on `/v3/block_proposal` enables timing side-channel recovery of `auth_token` - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
`RPCBlockProposalRequestHandler::try_parse_request` compares the client-supplied `authorization` header to the operator's configured secret using a plain `!=` on `String` values, which is not constant-time. A remote, unprivileged attacker who can reach the RPC port can send many requests with crafted `authorization` headers and use response-timing differences to incrementally recover the secret byte-by-byte, ultimately achieving an unauthorized bypass of the auth gate protecting `/v3/block_proposal`.

### Finding Description
In `try_parse_request` [1](#0-0) , the handler retrieves the configured `password` (the operator's `auth_token`) and the request's `authorization` header, then performs:
```rust
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
Rust's `String`/`str` equality (`PartialEq`) first compares lengths and, for equal-length strings, performs a byte-wise comparison that returns as soon as a mismatch is found. For two secrets of the same length, the number of bytes compared before returning is proportional to the length of the matching prefix, so the time to reject a request is correlated with how many leading bytes of the guess match the real secret. No constant-time comparison primitive (e.g. `subtle::ConstantTimeEq`, `ring::constant_time::verify_slices_are_equal`) is used anywhere in the codebase to guard this or any similar secret comparison.

An attacker with no credentials can:
1. Send repeated `POST /v3/block_proposal` requests, each with an `authorization` header guess of the same length as a hypothesized secret length, varying the guessed byte at a fixed position while holding a already-confirmed prefix constant.
2. Statistically average response latency for each candidate byte value; the guess that consistently takes marginally longer to reject correlates with a correct prefix byte (because the mismatch point in the comparison loop occurs later).
3. Repeat position-by-position to reconstruct the full `auth_token`, after which the attacker submits a request with the correct header and passes the auth gate, gaining unauthorized access to submit `NakamotoBlockProposal` payloads to a gated validation endpoint.

The `Content-Length`/`MAX_PAYLOAD_LEN` guard at lines 1145-1155 and JSON content-type/shadow-block checks afterward are irrelevant to this issue since the auth comparison happens before them and is the mechanism being attacked directly.

### Impact Explanation
If exploited, this allows an unauthenticated party to forge the operator's secret and gain the ability to submit arbitrary block proposals to the node's block-validation RPC surface without authorization, matching the "auth bypass" category under the Critical bucket. It affects any node operator who has enabled and remotely exposed the block-proposal auth-gated endpoint (`self.auth` set via config). The channel is repeatable across many requests, which is inherent to timing attacks.

### Likelihood Explanation
Exploitation requires: (1) the operator has configured and exposed `/v3/block_proposal` with an `auth_token`, and (2) the attacker can reach the RPC port remotely, sending large volumes of requests and performing statistical timing analysis to overcome network/OS jitter. No privileged role or knowledge of the secret is required to attempt this, satisfying "unprivileged remote attacker" preconditions. Practical extraction requires a large number of samples due to real-world network noise dominating the nanosecond-scale timing differences of a short byte-wise string comparison; feasibility depends on network conditions (LAN vs. WAN) and attacker's statistical resources, but the underlying code defect (non-constant-time secret comparison) is real and unmitigated in this codebase.

### Recommendation
Replace the plain `!=` comparison at line 1142 with a constant-time comparison, e.g. using `subtle::ConstantTimeEq` on the byte representations, or by hashing both `auth_header` and `password` (e.g. with a keyed HMAC using a per-node random key) and comparing the hashes in constant time. Ensure the comparison also handles differing lengths without leaking length via early return.

### Proof of Concept
Add a Rust unit/net test that:
1. Constructs an `RPCBlockProposalRequestHandler` with a fixed multi-byte `auth` secret.
2. Repeatedly calls `try_parse_request` (or drives it through the HTTP request-handling path) with crafted `authorization` header guesses that share increasing correct-prefix lengths with the real secret (e.g. 0, 1, 2, ..., N-1 correct leading bytes, same total length, differing final byte), while measuring wall-clock time of the call using `std::time::Instant` over many repetitions per guess to average out jitter.
3. Assert that mean comparison time is statistically increasing with the length of the correct matching prefix (e.g., via a t-test or simple mean/variance comparison threshold), demonstrating the correlation between timing and prefix-match length claimed in the finding.
4. Contrast this with a proposed fix using a constant-time comparison and show the timing correlation disappears (flat timing curve across prefix-match lengths), confirming the vulnerability is specific to the `!=` `String` comparison at [2](#0-1) .
