### Title
Non-completing QUIC handshakes can saturate `max_concurrent_connections` and starve legitimate connection admission - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC ingress path admits a connection into the global `open_connections` counter (via `ClientConnectionTracker::new`) before the handshake completes, and only releases that slot after up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) if the handshake never finishes. Because the per-IP `ConnectionRateLimiter` only records/consumes state for IPs with a *confirmed* (completed) connection, an attacker who never completes the handshake is never rate-limited by IP, allowing repeated re-acquisition of tracker slots to keep `open_connections` pinned near `max_concurrent_connections` and starve legitimate admissions.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs`), an incoming connection passes the overall token-bucket limiter and `rate_limiter.is_allowed(&incoming.remote_address().ip())`, then `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` is called, which increments `stats.open_connections` and only fails once `open_connections >= max_concurrent_connections`. [1](#0-0) 

`max_concurrent_connections` is deliberately set to `(max_staked_connections + max_unstaked_connections) * 5 / 4` — a fixed 25% headroom explicitly intended "to allow for handshake" in-flight connections. [2](#0-1) 

Once the tracker is acquired, the connection is handed to `setup_connection`, which bounds handshake completion with `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` (2 seconds). If it never completes, the `ClientConnectionTracker` is dropped, decrementing `open_connections`. [3](#0-2) [4](#0-3) 

Critically, `rate_limiter.register_connection(&from.ip())` — the call that actually consumes tokens against the per-IP limit — is only invoked *after* the handshake succeeds (`Ok(new_connection)` branch), not when the attempt is admitted. [5](#0-4) 

`ConnectionRateLimiter::is_allowed` is documented to assume "only IPs with actual confirmed connections are stored in it" and returns `true` (unlimited) for any IP that has no recorded state — i.e., any IP that has never completed a handshake: [6](#0-5) 

Because an attacker can simply never complete the handshake (e.g., send Initial and then stop responding, or stall mid-handshake), `register_connection` is never called for that IP, so `is_allowed` keeps returning `true` indefinitely for that source. The attacker can repeat this cycle: acquire a `ClientConnectionTracker` slot, let it expire after ~2s via the handshake timeout, and immediately re-acquire another slot — from the same IP or a small set of IPs — bounded only by the global `overall_connection_rate_limiter` (`TOTAL_CONNECTIONS_PER_SECOND = 2500`, burst `1000`), not by the per-IP limiter. [7](#0-6) 

By sustaining a rate of new non-completing connection attempts roughly equal to `max_concurrent_connections / QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, the attacker can keep `open_connections` continuously at or near `max_concurrent_connections` (which is well under the global 2500/s budget for typical configured staked/unstaked connection limits). Legitimate clients attempting new connections then fail the `ClientConnectionTracker::new` check and are refused, incrementing `stats.refused_connections_too_many_open_connections` and calling `incoming.refuse()`. [8](#0-7) 

This defeats the specific design intent of the 25%-headroom margin (`max_concurrent_connections`), which exists precisely to tolerate a background level of in-flight/incomplete handshakes without blocking legitimate admission — but that margin assumes handshake-in-flight slots are bounded in number by per-IP/overall rate limiting, which is bypassed here for never-completing connections.

### Impact Explanation
Scoped impact: `refused_connections_too_many_open_connections` for legitimate staked and unstaked clients attempting to connect to a leader's TPU QUIC port, i.e., a remotely triggerable connection-admission denial-of-service against the validator's QUIC ingress, achievable by a single unstaked, unprivileged attacker (or a small number of attacker-controlled source addresses) without needing to complete any handshake or possess stake.

### Likelihood Explanation
Preconditions: attacker only needs to be able to open raw QUIC/UDP connections to the leader's public TPU port and intentionally stall/abandon the handshake — no stake, keys, or special network position required, satisfying the "unprivileged remote client" threat model. Feasibility is high: the attacker only needs to sustain a connection-attempt rate comparable to `max_concurrent_connections / 2s`, which is far below the `2500`/s + `1000` burst overall rate limiter, and per-IP limiting provides no protection for non-completing connections per the documented `is_allowed` semantics. The attack is fully repeatable indefinitely as long as the attacker keeps generating fresh incoming connection attempts (from one or a few IPs) faster than legitimate demand for the remaining margin.

### Recommendation
Track and rate-limit in-flight (not-yet-completed) handshake attempts per source IP as well, not only completed connections — e.g., call a "provisional" `register_connection`-style token consumption at the time `ClientConnectionTracker::new` succeeds (or when `incoming.accept()` is called), rather than deferring all per-IP accounting until handshake success. Alternatively, apply a stricter, separate cap on the number of concurrently outstanding (non-completed) handshake attempts per IP, distinct from the completed-connection quota, so a single or few IPs cannot monopolize the 25% handshake headroom.

### Proof of Concept
Integration test plan (extends existing test harness in `streamer/src/nonblocking/quic.rs`, using `setup_quic_server`):
1. Configure a `SwQosConfig`/`QuicStreamerConfig` with small `max_staked_connections`/`max_unstaked_connections` (e.g., 4 total) so `max_concurrent_connections = 5`.
2. Spawn N ≈ `max_concurrent_connections` client QUIC endpoints from the *same* source IP (using `make_client_endpoint`), each of which sends only the initial handshake packet and then is deliberately prevented from completing the handshake (e.g., drop/withhold the client's Finished flight, or connect to a black-holed responder that never replies after Initial).
3. Repeat launching such non-completing connection attempts continuously (spawn a new one every time an old one would time out, i.e., faster than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`), for a duration > `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
4. Concurrently, attempt a legitimate, fully-handshaking client connection using `make_client_endpoint` + normal handshake completion.
5. Assert that the legitimate connection either fails or takes longer than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` to succeed, and that `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0` while `stats.connection_rate_limited_per_ipaddr` remains `0` for the attacker's IP (demonstrating the per-IP limiter never engaged because `register_connection` was never called for non-completing attempts).

        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
