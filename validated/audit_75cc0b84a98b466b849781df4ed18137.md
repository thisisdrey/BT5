### Title
`add_or_schedule_replace_neighbor`/`replace_neighbors` can evict an `allowed` peer from its slot without any allow-list check - ([File: stackslib/src/net/neighbors/db.rs])

### Summary
`PeerDB::try_insert_peer` (stackslib/src/net/db.rs:1452-1488) correctly returns `false` when all of a neighbor's candidate slots are occupied, but the caller in the neighbor-walk state machine then falls back to `find_replaced_neighbor_slot`/`replace_neighbors`, which pick a slot to evict based purely on hash-bucket membership and the deny-list, never checking whether the incumbent occupant is marked `allowed`. This lets an attacker who can get the local node to walk to enough distinct, self-controlled peer identities that hash into the same slot bucket overwrite a legitimately-`allowed` peer's DB row.

### Finding Description
The eviction path is:
1. `PeerDBNeighborWalk::add_or_schedule_replace_neighbor` (stackslib/src/net/neighbors/db.rs:368-426) calls `neighbor_from_handshake.save(...)`, which internally uses `PeerDB::try_insert_peer`. If `try_insert_peer` returns `false` (all slots for that address/port hash-bucket full), it calls `Self::find_replaced_neighbor_slot(&tx, &neighbor_from_handshake.addr)` (line 412-413).
2. `find_replaced_neighbor_slot` (stackslib/src/net/neighbors/db.rs:287-302) fetches `PeerDB::peer_slots(...)` for the *new* neighbor's address/port and randomly picks **one of those slots** — with no lookup of what/who currently occupies it, and specifically no check of an "allowed" flag.
3. Later, `replace_neighbors` (stackslib/src/net/neighbors/db.rs:463-505) loads whatever peer is currently sitting in that chosen slot (`PeerDB::get_peer_at`) and overwrites it with the new neighbor via `PeerDB::insert_or_replace_peer`, gated **only** by `PeerDB::is_address_denied(&tx, &replacement.addr.addrbytes)` (line 483) — i.e., only the deny-list of the *new* candidate is checked. There is no check of whether the peer being evicted (`replaced`) is on the always-allowed list.

This breaks the implicit invariant the question calls out: `slot_occupant_after_eviction == a_peer_that_actually_proved_it_should_replace_the_evicted_entry`. In reality, any new peer whose address/port hashes into the same slot bucket as a trusted, `allowed` peer can end up overwriting that peer's slot purely by being new and not denied — no comparison of trust/allow status is ever made between the incumbent and the challenger.

### Impact Explanation
An attacker who can get the local node to attempt handshakes/walks with a sufficient number of distinct, attacker-controlled peer identities whose `(network_id, addrbytes, port)` hash into the same `peer_slots` bucket as a specific `allowed` peer can cause that `allowed` peer's DB row to be silently replaced. This is a targeted denial-of-service against the frontier/allow-list entry for that specific trusted peer: the node loses its persisted, trusted connection info for that peer and will treat the attacker's neighbor as the trusted slot occupant instead. This matches a "High" impact category (steering trusted peer-state without any prior authorization check) rather than crashing the whole node.

### Likelihood Explanation
Exploitation requires the attacker to establish enough distinct peer identities (attacker doesn't need to forge anyone else's key — self-generated keys/handshakes are sufficient) that collide into the same hash-bucket as the target `allowed` peer, and requires the local node's neighbor-walk logic to actually attempt to add these neighbors (e.g., via `getneighbors`/walk discovery, which an attacker can seed by advertising many addresses). This is more costly than a single crafted message — it needs a Sybil-like set of distinct connecting identities/addresses, and the hash-bucket collision (`PeerDB::peer_slots`) is address/port-dependent, so the exact number and addresses needed to force a collision with a specific slot were not verified in this pass (the `peer_slots` hashing implementation was not inspected). This uncertainty affects how "cheap" the attack really is: if the slot-selection is a small fixed hash space, collisions may be easy to arrange; if it is large/keyed by full IP, an attacker would need many distinct real source addresses, pushing the attack toward Sybil/volumetric territory that the audit scope excludes ("connection-slot exhaustion needing only traffic volume").

### Recommendation
In `replace_neighbors` (stackslib/src/net/neighbors/db.rs:463-505), before evicting the incumbent occupant of a slot, check whether that occupant is on the always-allowed list (e.g. via `PeerDB::is_address_allowed`/`get_always_allowed_peers`) and refuse to replace it (or require the same or higher trust level from the challenger). Likewise, `find_replaced_neighbor_slot` should prefer/only select slots whose current occupant is not `allowed` when choosing a replacement candidate.
