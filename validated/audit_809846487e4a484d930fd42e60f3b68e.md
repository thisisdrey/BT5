### Title
`liquidate` unconditionally enforces the debt-floor invariant even when `maxLiquidable` caps repayment below 100%, permanently bricking liquidation of below-floor underwater positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two relations on the same call: (1) `amountToRepay_ / debtBalance <= maxLiquidable` and (2) `remainingDebtInUsd == 0 || remainingDebtInUsd >= debtFloorInUsd`. When `maxLiquidable < 1e18` and `debtFloorInUsd > 0`, a position whose debt value has fallen below the floor has no valid `amountToRepay_` — every input reverts. This is the same bug class as the reference finding: an invariant (`mul/div` relation / debt-floor relation) is enforced unconditionally in a degenerate case where no satisfying inputs exist, turning the operation unexecutable and leaving bad debt stuck in the protocol.

### Finding Description
In `Pool.liquidate`:

```solidity
// contracts/Pool.sol:567
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
```

```solidity
// contracts/Pool.sol:571-578
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

Any `amountToRepay_` must satisfy both:

- `amountToRepay_ <= _debtTokenBalance * maxLiquidable` — so with `maxLiquidable < 1e18`, the liquidator **cannot** repay the full debt.
- `remainingDebt == 0 || remainingDebtUsd >= debtFloorInUsd` — so any partial repay on a position whose total debt is already below `debtFloorInUsd` leaves `_newDebtInUsd ∈ (0, floor)` and reverts.

The two constraints are mutually exclusive: repaying ≤ `maxLiquidable` fraction always leaves positive sub-floor debt → `RemainingDebtIsLowerThanTheFloor`; repaying enough to zero the debt exceeds `maxLiquidable` → `AmountGreaterThanMaxLiquidable`. `liquidate` is the only path to clear such a position (the account owner could use `DebtToken.repayAll`, but an underwater account has no incentive and no obligation to). Note the floor check itself correctly skips the zero-remainder case (mirroring "don't enforce the relation when divisor is zero"), but the `maxLiquidable` cap forbids reaching that exempted case.

### Impact Explanation
The unhealthy position becomes permanently unliquidatable. Collateral stays locked, the synthetic debt is never burned, and the protocol accumulates bad debt — solvency invariant breaks (liveness → protocol insolvency). No privileged action in the liquidate path can rescue it; `maxLiquidable`/`debtFloorInUsd` updates require governor intervention that may come only after collateral value has further deteriorated.

### Likelihood Explanation
Reachable under ordinary market conditions, no privilege or oracle manipulation needed:

1. Config: `debtFloorInUsd > 0` and `maxLiquidable < 1e18` (e.g., 50% close-factor — a standard deployed configuration).
2. A user opens a position with debt just above the floor, where the debt synth is a *different asset* than the collateral (e.g., msBTC debt vs ETH collateral, or any cross-asset mix — `debtPositionOf` aggregates all debt tokens and deposit tokens).
3. The debt asset's USD price declines relative to collateral (legitimate market move, not oracle manipulation): the quoted debt USD value falls below `debtFloorInUsd` while the position is simultaneously unhealthy (collateral USD fell faster, or accrued interest pushed debt up in token terms while the floor comparison still fails).

Both conditions are common in normal operation; nothing in `whenNotShutdown`, `nonReentrant`, `SynthContext._msgSender`, or the token checks prevents it. The analogous check in `DebtToken.repay` (lines 442-450) blocks user partial repays too, but `repayAll` exists there — `liquidate` has no full-repay escape hatch.

### Recommendation
Skip the floor check when the caller repays the maximum allowed / when no `amountToRepay_` can satisfy both constraints, or exempt full-balance liquidations from `maxLiquidable`. Concretely: allow `amountToRepay_ == _debtTokenBalance` regardless of `maxLiquidable`, or compute the check as `if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd && amountToRepay_ < _debtTokenBalance)` combined with raising the cap so full repayment is always permitted during liquidation.

### Proof of Concept
Foundry test sketch (fork or unit):

```solidity
// Setup: poolRegistry.setDebtFloorInUsd(1000e18); pool.updateMaxLiquidable(0.5e18) via governor prank
// 1. User deposits WETH collateral, issues msBTC debt worth ~1100 USD (>= floor at mint).
// 2. MasterOracleMock: drop BTC/USD 20% (debt now ~880 USD < floor), drop ETH enough that
//    debtPositionOf(user) returns _isHealthy == false.
// 3. Liquidator (any EOA) holds msUSD, swaps to msBTC or holds the synth, then:

uint256 bal = debtToken.balanceOf(user);

// Any partial repay -> floor revert
vm.expectRevert(RemainingDebtIsLowerThanTheFloor.selector);
pool.liquidate(msBTC, user, bal / 2, depositToken);

// Full repay -> cap revert
vm.expectRevert(AmountGreaterThanMaxLiquidable.selector);
pool.liquidate(msBTC, user, bal, depositToken);

// Position is unliquidatable: bad debt persists, collateral frozen.
```

Caveat: the finding assumes the deployed configuration has `debtFloorInUsd > 0` and `maxLiquidable < 1e18`; if `maxLiquidable == 1e18` the cap never binds and the issue is unreachable.
