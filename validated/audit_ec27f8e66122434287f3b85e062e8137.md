### Title
`Pool.swap` provides no minimum-out parameter — users are forced into unlimited slippage against the transaction-time oracle price - (File: contracts/Pool.sol)

### Summary
`Pool.swap(syntheticTokenIn_, syntheticTokenOut_, amountIn_)` burns the caller's input synth and mints the output synth at whatever `masterOracle().quote()` returns at execution time, minus the `FeeProvider` swap fee. There is no `amountOutMin_`/`minReturned` argument anywhere in the signature (`IPool.swap` has three parameters), so the user cannot bound the amount received. This is the exact analog of the Juicebox `_minReturnedTokens`-forced-to-zero class: the only "slippage check" is implicitly zero, and the effective rate is resolved at transaction time, after the tx leaves the user's control.

### Finding Description
In `Pool.sol:642-671`, the flow is:

```solidity
syntheticTokenIn_.burn(_msgSender, amountIn_);
(_amountOut, _fee) = quoteSwapOut(syntheticTokenIn_, syntheticTokenOut_, amountIn_);
if (_fee > 0) syntheticTokenOut_.mint(_poolRegistry.feeCollector(), _fee);
syntheticTokenOut_.mint(_msgSender, _amountOut);
```

`quoteSwapOut` (Pool.sol:508-525) prices the swap purely via `_poolRegistry.masterOracle().quote(...)`. Because the input is burned *before* pricing and there is no post-quote bound, any deviation between the price the user saw off-chain and the price at execution is borne entirely by the user — or, symmetrically, can be harvested by an attacker:

- Any EOA can call `swap` directly (`whenNotShutdown nonReentrant` only).
- If `MasterOracle` resolves a quote from a same-transaction-manipulable source (a DEX spot/twap-derived feed for the collateral or synth pair — the MasterOracle implementation is external and chain-specific), an attacker can in one transaction: (1) manipulate the quoted rate, (2) call `Pool.swap` to burn cheap `syntheticTokenIn_` and mint overvalued `syntheticTokenOut_`, (3) restore the price. The newly minted synth is unbacked, diluting the pool — protocol insolvency, not just user slippage.
- Even without manipulation, a pending user tx executed after a legitimate oracle update delivers an arbitrarily different `_amountOut` with no recourse — identical in spirit to M-01's "vanilla path with `_minReturnedTokens = 0`".

By contrast, `SmartFarmingManager.leverage`/`flashRepay` do pass `0` as `amountOutMin_` to `Swapper.swapExactInput` (SmartFarmingManager.sol:184, 197, 125) but backstop it with user-supplied `depositAmountMin_`/`swapAmountOutMin_` checked on the aggregate result (lines 198, 126) plus a final `debtPositionOf` health check — so those flows are protected. `Pool.swap` has no such backstop; `isSwapActive`, `nonReentrant`, and the `onlyIfSyntheticTokenExists` checks do not bound output.

### Impact Explanation
- User loss: a swapper receives arbitrarily fewer synths than quoted, with no ability to specify a floor — identical to the M-01 finding that the min-return guarantee is effectively null.
- Protocol insolvency: if the oracle quote is influenced in the same transaction (the rules explicitly allow same-transaction manipulation), an attacker mints synth at a manipulated rate and redeems/swaps against the pool at the restored price, extracting collateral backing and leaving bad debt.

### Likelihood Explanation
- `swap` is a public, unprivileged entry point; no role, list membership, or health check gates it.
- Whether the oracle quote is exploitable in-transaction depends on the deployed `MasterOracle`/`TokenOracle` sources per chain (not in this repo — only `IMasterOracle` is in scope), so exploitability is conditional; the missing slippage bound itself is unconditional and verifiable. As in M-01, the user-facing defect (forced zero minimum) exists regardless.

### Recommendation
Add a user-supplied minimum output parameter and enforce it after quoting:

```solidity
function swap(
    ISyntheticToken syntheticTokenIn_,
    ISyntheticToken syntheticTokenOut_,
    uint256 amountIn_,
    uint256 amountOutMin_
) external ... {
    ...
    (_amountOut, _fee) = quoteSwapOut(syntheticTokenIn_, syntheticTokenOut_, amountIn_);
    if (_amountOut < amountOutMin_) revert SlippageTooHigh();
    ...
}
```

Alternatively, document explicitly that swaps are executed strictly at oracle price and that users must accept unbounded execution-time deviation.

### Proof of Concept
Foundry fork sketch (base/optimism deployment of `Pool`):

```solidity
function test_swap_noMinOut() public {
    // victim holds msUSD, wants msETH
    uint256 amountIn = 1000e18;
    uint256 quoted = pool.quoteSwapOut(msUSD, msETH, amountIn)._amountOut;

    // attacker manipulates the oracle's price source for the pair in the same tx
    // (e.g., moves the underlying DEX pool the oracle reads), making quoteSwapOut
    // return less msETH per msUSD.
    vm.prank(attacker);
    skewOracleSource(); // e.g., large trade on the source pool, if spot-derived

    vm.prank(victim);
    (uint256 amountOut, ) = pool.swap(msUSD, msETH, amountIn);
    // victim receives less than quoted; has no parameter to prevent it
    assertLt(amountOut, quoted);

    // attacker variant: inflate syntheticTokenIn price, swap dust amountIn for
    // outsized syntheticTokenOut, unwind source => unbacked synth minted.
}
```

On a fork where `masterOracle()` resolves quotes from an on-chain-manipulable feed, the swap executes at the manipulated rate with no min-out revert; on any deployment the signature-level absence of a slippage bound (the M-01 analog) is directly observable at `Pool.sol:642` and `IPool.sol:100-104`.
