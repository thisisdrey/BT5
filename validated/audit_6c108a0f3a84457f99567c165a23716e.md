### Title
Unbounded array allocation from unvalidated signature/address array length in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode an attacker-supplied array length directly from call data and use it, unchecked, to allocate a Java array (`new byte[len][]`) before any bounds validation is guaranteed to run. The only length cap (`MAX_SIZE`) is applied conditionally, gated behind the `VMConfig.allowTvmSelfdestructRestriction()` feature flag, so any code path that reaches `extractBytesArray`/`extractBytes32Array`/`extractSigArray` without that guard being active processes a fully attacker-controlled size value, mirroring the XCreateImage()-style pattern of using a raw, unchecked, attacker-influenced size to drive a memory allocation.

### Finding Description
In `extractBytes32Array` and `extractBytesArray` [1](#0-0) , `len` is read straight from `words[offset].intValueSafe()` — a `DataWord` derived from raw call data — and immediately used to allocate `new byte[len][]` with no upper bound check inside these helper methods themselves.

The only bound enforcement lives in the callers, `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, and it is wrapped in an `if (VMConfig.allowTvmSelfdestructRestriction())` conditional: [2](#0-1) [3](#0-2) 

`intValueSafe()` can return values up to `Integer.MAX_VALUE` [4](#0-3) , so when the feature-flag guard is not active for a given call path, `len` is fully attacker-controlled and unbounded before the `new byte[len][]` allocation executes — the length check happens too late (only the subsequent `signatures.length > MAX_SIZE` check runs, and only *after* the array is already allocated).

This is the java-tron structural analog of the reported libX11 `XCreateImage()` bug class: a size value taken from external/attacker input is used to drive a buffer/array allocation without validating it first, instead of validating-then-allocating.

### Impact Explanation
A crafted `CALL` to the `validateMultiSign` (address suffix `...66`) or `batchValidateSign` (`...67`) precompile with a huge encoded array-length word can force the node to attempt allocating an enormous `byte[][]` in the middle of a single transaction's TVM execution. This can throw `OutOfMemoryError`, which is unchecked and can propagate out of the VM execution context and crash or destabilize the node process, since precompile execution here is not defensively guarded against this specific failure mode prior to allocation. This matches the accepted impact class of "node crash or halt" from a single, unprivileged, signed transaction/contract call.

### Likelihood Explanation
Reachability requires only deploying/calling a contract that issues a `CALL` to the fixed precompile address with crafted call data — no special privileges, SR/witness status, or network position needed, matching the "unprivileged contract deployer / caller" threat model. The actual triggering condition depends on `VMConfig.allowTvmSelfdestructRestriction()` being inactive for the code path taken; this is a chain-governance-controlled hard-fork flag (`ProposalUtil`/`DynamicPropertiesStore`), so its exact activation status across deployed java-tron networks (mainnet vs. private/test networks, or during a fork transition window) could not be fully verified from the available code context.

### Recommendation
Move the length validation (`MAX_SIZE` cap and non-negative check) unconditionally into `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves — before the `new byte[len][]` allocation — rather than relying on a feature flag applied only in some call sites. Reject with `Pair.of(false, EMPTY_BYTE_ARRAY)` (or the existing `DATA_FALSE` convention) whenever the decoded length exceeds a sane precompile-specific bound, independent of `VMConfig.allowTvmSelfdestructRestriction()`.

### Proof of Concept
1. Deploy a contract that performs a low-level `CALL` to `0x0000...0066` (`validateMultiSign`) or `0x0000...0067` (`batchValidateSign`).
2. Craft call data whose ABI-encoded dynamic array (`bytes[]` or address array) length word (`words[offset]`) is set to a very large value (e.g., `0x7fffffff`) while keeping the calldata itself short.
3. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is not active for the executing node/network (default/pre-activation state).
4. Invoke the contract; `extractBytesArray`/`extractBytes32Array` executes `new byte[len][]` with the attacker-supplied `len`, attempting a massive allocation and potentially throwing `OutOfMemoryError` during block/transaction processing on the node.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
