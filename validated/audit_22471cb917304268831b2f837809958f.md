### Title
StackerDB chunk signature does not bind the target StackerDB contract, enabling cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The referenced Mochi finding is about a balance/state field (`reward[msg.sender]`) not being reset, so an equality between "claimed" and "owed" is never re-established, letting the same authorization be reused indefinitely. The closest reachable analog in the in-scope StackerDB code is a missing binding in the authenticity check itself: `SlotMetadata::verify` re-establishes "signed by the slot owner" but the signed digest never commits to *which* StackerDB (smart contract) the chunk belongs to, only to `slot_id`, `slot_version`, and `data_hash`.

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest as: [1](#0-0) 

This digest is the only thing verified by `SlotMetadata::verify`/`StackerDBChunkData::verify`: [2](#0-1) 

Storage validation (`StackerDBTx::try_replace_chunk`) checks the signature against the `signer` recorded for `(smart_contract, slot_id)`, plus version freshness and write-count limits: [3](#0-2) 

Network-level acceptance (`PeerNetwork::validate_received_chunk`) performs the equivalent check for chunks received via push/inventory sync — it resolves the expected signer purely from `(smart_contract_id, slot_id)` and verifies the signature over the same contract-agnostic digest: [4](#0-3) 

Because the `QualifiedContractIdentifier` (the StackerDB instance identity) is never part of the signed payload, a chunk that is validly signed for slot `N` in StackerDB `A` is *also* a valid signature for slot `N` in any other StackerDB `B`, provided the same signing address is assigned to slot `N` in `B` as well (a `data_hash`/`slot_version` collision is all that's additionally needed, and an attacker who already possesses a validly-signed chunk from a legitimate signer controls both `data` and thus `data_hash`, and can freely pick `slot_version` up to `max_writes`). This breaks the intended equality "a signature over (slot_id, slot_version, data_hash) authorizes a write to *this* replica" — it actually authorizes a write to *any* replica sharing that signer/slot/version/hash tuple.

The Stacks network runs multiple parallel StackerDB replicas that reuse the same signer-set ordering across contracts — e.g. `.signers-<version>-<cycle>` DBs, and (per the network module's own documentation) multiple independent smart-contract-backed replicas can be configured concurrently with the same underlying signer principals occupying identical slot indices across contracts (the whole point of `StackerDBConfig.signers`, computed once per reward cycle and reused to configure several replicas). An unprivileged network peer that has observed (or replayed from a NACK-buffered future-view chunk, or from inventory sync) any signed chunk for one contract's slot can attempt to replay it verbatim as `StackerDBChunkData` into a *different* configured StackerDB contract at the matching slot, since neither `try_replace_chunk` nor `validate_received_chunk` re-derives or checks the contract identity as part of the cryptographic commitment — only as a lookup key to find the "expected" signer, which the attacker satisfies incidentally when the signer set is shared.

### Impact Explanation
This allows an unauthenticated/unauthorized write of forged/misattributed data into a StackerDB replica that the true owner never intended for that contract, and — because accepted chunks are re-broadcast via `process_stacker_db_chunks`/`StackerDBPushChunk` — the forged chunk propagates network-wide as if it were legitimately authored for that contract: [5](#0-4) 
This matches the Critical bar for "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
Exploitation requires only (a) observing one validly-signed chunk from any signer (chunks and their signatures are broadcast in the clear over the p2p StackerDB protocol, and also fetchable via the public GET chunk RPC endpoint) and (b) a target contract where the same signer occupies the same slot index with a version that is still `<= max_writes` and not yet superseded. Given that StackerDB configs for signer sets are derived deterministically from the same reward-cycle signer ordering and are reused across multiple named contracts, colliding slot assignments across contracts is a realistic and likely, not merely theoretical, occurrence for legitimate signer/miner StackerDB deployments.

### Recommendation
Include the target StackerDB's `QualifiedContractIdentifier` (and ideally a network/chain identifier) in `SlotMetadata::auth_digest`, so that a signature is only valid for the specific contract instance it was produced for:
```rust
fn auth_digest(&self, smart_contract: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(smart_contract.to_string().as_bytes());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
Thread the contract id through `sign`/`verify` call sites in `libstackerdb.rs`, `stackerdb/db.rs::try_replace_chunk`, and `stackerdb/mod.rs::validate_received_chunk`.

### Proof of Concept
1. Configure (or observe) two StackerDB contracts `A` and `B` whose `StackerDBConfig.signers` assign the same address to slot `0` (realistic given shared reward-cycle signer set derivation).
2. Wait for/observe a legitimately signed `StackerDBChunkData{slot_id:0, slot_version:v, sig, data}` broadcast for contract `A` (visible on the wire or via `GET /v2/stackerdb/.../chunks/0`).
3. As an unprivileged peer, submit the identical `StackerDBChunkData` to contract `B`'s slot `0` (e.g. via `POST /v2/stackerdb/<B>/chunks` or as an unsolicited `StackerDBPushChunk`).
4. `try_replace_chunk`/`validate_received_chunk` verify the signature purely against `(slot_id, slot_version, data_hash)` — since the same signer/slot/version/hash combination is valid, the chunk is accepted into `B`'s replica and rebroadcast, even though it was never authorized for `B`.         // validate -- must not exceed this replica's configured chunk size.

            info!(

                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
