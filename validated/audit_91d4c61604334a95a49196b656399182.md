### Title
`process_delivery_receipt` pays full relayer reward regardless of Ethereum-side dispatch outcome (`success` flag ignored) - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
The Snowbridge outbound-queue-v2 pallet processes the `InboundMessageDispatched` event emitted on Ethereum (decoded as `DeliveryReceipt`) to pay relayer rewards for delivering XCM-originated messages to the Gateway contract. The decoded receipt carries a `success: bool` field reflecting whether the message actually executed successfully on Ethereum, but `Pallet::process_delivery_receipt` never inspects it before releasing the full `order.fee` reward, contradicting the pallet's own documented intent that a reward is for confirmed, useful work.

### Finding Description
`DeliveryReceipt` decodes the `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` Ethereum event and explicitly exposes a `success` field: [1](#0-0) 

`submit_delivery_receipt` verifies the proof, decodes the receipt, and calls `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` only validates the gateway address and looks up the `PendingOrder` by nonce; it never checks `receipt.success` before paying `order.fee` to the reward account and removing the order: [3](#0-2) 

A grep across the pallet confirms `success` is decoded but never referenced anywhere in `outbound-queue-v2` logic — the field is dead for reward-gating purposes, even though the module doc explicitly frames the receipt step as confirmation that "the message has been verified **and executed**" before paying the reward: [4](#0-3) 

The only existing guard added by a prior audit fix blocks payout while the light-client verifier is halted (`VerificationError::Halted`), which is orthogonal to whether the *dispatched command itself* reverted on Ethereum: [5](#0-4) 

This is not a "malicious/compromised relayer" issue: any unprivileged signed account (`ensure_signed(origin)`) can submit a genuine, correctly-proved Ethereum transaction receipt for a message whose Gateway-side command execution failed (e.g., an XCM-triggered contract call that reverted for reasons unrelated to relaying, such as insufficient gas provided by the `GasMeter` estimate, a reentrant revert, or destination-side logic failure), and the pallet still releases the full attached fee as if the message had been successfully delivered and executed.

### Impact Explanation
This directly conserves-value-incorrectly: it constitutes an "unbacked" payout — the fee escrowed in `PendingOrder.fee` (funded by the original XCM sender/message fee) is fully paid out to a reward account even when the cross-chain command failed, i.e. paying for work that was not actually completed. Repeated abuse (submitting receipts for messages whose commands are engineered or naturally likely to fail) drains reward funds without commensurate useful delivery, degrading the bridge's fee/reward economics and potentially exhausting the rewards pot that legitimate relayers rely on. This falls under "public underpriced work" / "theft or unbacked payout" per the impact gate, and does not require any admin, governance, or relayer-compromise assumption.

### Likelihood Explanation
Likelihood is moderate-to-high: the extrinsic is fully public (`ensure_signed`), requires only a valid Merkle/receipt proof of a real Ethereum transaction log (which any relayer legitimately obtains regardless of the command's success), and the code path unconditionally pays out once nonce and gateway match. No special privilege, validator collusion, or off-chain infrastructure compromise is needed — only submission of a correctly-proven receipt for a message whose on-chain (Ethereum) execution outcome was `success: false`.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` with the full `order.fee` when `success == true`. For `success == false`, either withhold the reward entirely, pay a reduced base fee reflecting proof-submission cost only, or route the fee to a refund path for the original message sender, while still removing the `PendingOrder` to prevent nonce reuse. Add explicit unit tests mirroring `poc_m1`/`submit_delivery_receipt_succeeds_after_unhalt` but toggling `receipt.success` to assert reward is withheld/reduced on failed delivery.

### Proof of Concept
1. An XCM message is sent from AssetHub to Ethereum via the outbound-queue-v2 pipeline; a `PendingOrder{nonce, fee, ..}` is created with a non-zero fee, as shown in `do_process_message`: [6](#0-5) 
2. The message is delivered to the Gateway contract on Ethereum, but the encoded command (e.g., a token mint/transfer call) reverts on the Ethereum side due to insufficient gas or a destination-side check failure; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account submits `submit_delivery_receipt` with a valid proof of that (failed) event log.
4. `T::Verifier::verify` succeeds (the event/log genuinely occurred and is provable), `DeliveryReceipt::try_from` decodes `success = false`, and `process_delivery_receipt` proceeds to pay `order.fee` in full to `reward_account` and removes the `PendingOrder`, exactly as it would for `success = true` — confirmed by the code at: [7](#0-6) 
5. No test in the repository asserts that reward is withheld when `success == false`; existing tests (`poc_m1`, `submit_delivery_receipt_succeeds_after_unhalt`, `invalid_nonce_for_delivery_receipt_fails`) only cover halted-verifier and invalid-nonce cases, not the `success` flag, confirming the gap is unguarded. [8](#0-7)

```rust
		) -> DispatchResult
```

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```

```rust
// Reward processing must be blocked while the bridge is halted: `submit_delivery_receipt`
// should not pay out `PendingOrder` fees if the verifier reports the bridge as halted.
#[test]
fn poc_m1() {
	new_tester().execute_with(|| {
		let nonce = 1;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_event_proof());

		set_verifier_halted(true);

		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);

		let order_after = PendingOrders::<Test>::get(nonce).expect("order still present");
		assert_eq!(order_after.fee, fee);

		set_verifier_halted(false);
	});
}
```

```rust
// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
```
