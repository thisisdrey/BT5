### Title
Redirect logic in `net/http` `Client` unconditionally recomputes and re-sends the `Referer` header, ignoring an explicit attempt to suppress it - ([File: src/net/http/client.go])

### Summary
`net/http`'s `Client.do` computes the `Referer` header for each redirect hop via `refererForURL`, treating an empty string as "not explicitly set" rather than "explicitly cleared." [1](#0-0)  Because header copying for each hop is rebuilt from the *original* request's headers on every redirect (not from any per-hop mutation), a caller that sets `Referer` to `""` or deletes it (e.g. inside `CheckRedirect`) cannot prevent the library from re-adding the previous URL as `Referer` on the next hop. [2](#0-1)  This mirrors the libcurl bug pattern: an API consumer's explicit "clear the referrer" intent is silently discarded and the previous referrer value is reused/resent.

### Finding Description
- Entry point: `(*Client).do` in the redirect loop, called from `Client.Do`/`Get`/`Post` when a server response causes a redirect. [3](#0-2) 
- For each subsequent hop, headers are copied from the very first request's headers via `makeHeadersCopier`'s closure over `ireqhdr` (captured once, from `ireq.Header`, at `Do` invocation time): [4](#0-3) 
- The Referer value used for the new hop is computed by:
```go
if ref := refererForURL(reqs[len(reqs)-1].URL, req.URL, req.Header.Get("Referer")); ref != "" {
    req.Header.Set("Referer", ref)
}
``` [5](#0-4) 
- `refererForURL` treats an empty `explicitRef` string as "no explicit value was set" and falls back to computing a default referer from `lastReq.String()`:
```go
if explicitRef != "" {
    return explicitRef
}
referer := lastReq.String()
``` [6](#0-5) 
- Failed check: there is no distinction between "Referer header absent/never set" and "Referer explicitly cleared to empty string." Both produce `req.Header.Get("Referer") == ""`, and both are treated identically — the default (previous URL) is computed and injected.
- Additionally, even if a caller deletes/clears the `Referer` header from within `CheckRedirect` on one hop (which executes *after* the header has already been set for that hop, at `c.checkRedirect(req, reqs)` [7](#0-6) ), that mutation is not persisted: the next hop's headers are rebuilt fresh from `ireqhdr` (the original request), so the computed Referer reappears on the following redirect.
- Sink: the recomputed `Referer` header, containing the previous request's full URL (host, path, query string minus userinfo), is transmitted in the HTTP request to the redirect target — which for cross-host redirects can be an entirely different, potentially attacker-controlled or untrusted server.

### Impact Explanation
If a URL contains sensitive information in its path or query string (session tokens, search terms, internal identifiers), a caller that explicitly attempts to suppress the `Referer` header before or during a redirect chain will still leak that URL to the next hop's destination, which may be a third-party/untrusted host reached via a redirect. This is an information-disclosure primitive analogous to the libcurl CVE (previous-referrer persists despite an explicit clear request), not a memory-safety or auth-bypass issue. Under Go's vulnerability triage this would be assessed at most as a low-to-moderate confidentiality issue (PUBLIC track candidate) given it requires a specific application pattern (explicit suppression + redirect chain) rather than being exploitable purely by an unauthenticated network attacker without victim participation.

### Likelihood Explanation
Requires a victim Go program that (a) follows redirects with the default `Client.Do`/`Get` and (b) attempts privacy-conscious referer suppression via `Header.Set("Referer", "")`, `Header.Del("Referer")`, or removal in `CheckRedirect`. This is a plausible but non-default usage pattern; it is not exposed to a fully unauthenticated network attacker without the victim's application taking this specific step, so likelihood is moderate rather than high.

### Recommendation
Distinguish "no Referer configured" from "Referer explicitly cleared." One approach: use a sentinel (e.g., check for header presence via `req.Header["Referer"]` existence rather than `Get()` returning `""`) so that an explicitly empty/deleted Referer is honored and no default is computed for that hop; also honor `CheckRedirect`-time removal for subsequent hops rather than always rebuilding from the original request's captured headers.

### Proof of Concept
```go
package http_test

import (
	"net/http"
	"net/http/httptest"
	"testing"
)

func TestExplicitClearedRefererReappearsOnRedirect(t *testing.T) {
	var gotReferer string
	final := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		gotReferer = r.Header.Get("Referer")
	}))
	defer final.Close()

	redirector := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		http.Redirect(w, r, final.URL, http.StatusFound)
	}))
	defer redirector.Close()

	req, _ := http.NewRequest("GET", redirector.URL+"/secret-path?token=abc", nil)
	// Caller explicitly attempts to suppress the Referer header.
	req.Header.Set("Referer", "")

	c := &http.Client{}
	resp, err := c.Do(req)
	if err != nil {
		t.Fatal(err)
	}
	resp.Body.Close()

	if gotReferer != "" {
		t.Errorf("Referer explicitly cleared but was resent on redirect: got %q, want \"\"", gotReferer)
	}
}
```
Expected (per caller's explicit intent): `gotReferer == ""`. Actual behavior in `net/http`: `gotReferer` equals the original redirector URL (`.../secret-path?token=abc`), because `refererForURL` treats the empty explicit value as unset and computes the default from `reqs[len(reqs)-1].URL`. // refererForURL returns a referer without any authentication info or
// an empty string if lastReq scheme is https and newReq scheme is http.
// If the referer was explicitly set, then it will continue to be used.
func refererForURL(lastReq, newReq *url.URL, explicitRef string) string {
	// https://tools.ietf.org/html/rfc7231#section-5.5.2
	//   "Clients SHOULD NOT include a Referer header field in a
	//    (non-secure) HTTP request if the referring page was
	//    transferred with a secure protocol."
	if lastReq.Scheme == "https" && newReq.Scheme == "http" {
		return ""
	}
	if explicitRef != "" {
		return explicitRef
	}

	referer := lastReq.String()
```
