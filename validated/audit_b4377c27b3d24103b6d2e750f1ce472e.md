### Title
Attacker can permanently fill a victim's per-account token list with dust deposit tokens, DoS-ing new deposits/borrows/liquidation receives - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to CVE-2020-10958 (unauthenticated DoS triggered by attacker-controlled input), `Pool.addToDepositTokensOfAccount` lets an unprivileged attacker fill any victim's `depositTokensOfAccount`/`debtTokensOfAccount` set up to `MAX_TOKENS_PER_USER` by transferring 1 wei of each deposit token to the victim. Once the combined list reaches 30 entries, every subsequent first-time receipt of a deposit token (`_mint`, `_transfer`, `seize` to a fresh token) and every first-time debt token mint for the victim reverts with `UserReachedMaxTokens`, blocking the victim from depositing new collateral types, receiving deposit tokens, or issuing new synth types.

### Finding Description
`DepositToken._transfer` and `_mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token goes from 0 to >0 [1](#0-0) . `addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [2](#0-1) . The same check gates `DebtToken._mint` via `pool.addToDebtTokensOfAccount(account_)`, so `DebtToken.issue` and `mint` revert for the victim on any *new* debt token [3](#0-2) .

There is no minimum-transfer or opt-in requirement: `transfer(to_, amount_)` only checks the *sender's* unlocked balance, so an attacker can deposit dust into each of the pool's deposit tokens and forward 1 wei of each to the victim, each transfer adding a new entry to the victim's set [4](#0-3) .

### Impact Explanation
- The victim cannot deposit, receive via `transfer`, or receive via liquidation `seize` any deposit token they don't already hold — `deposit(amount, onBehalfOf_=victim)` reverts, and liquidators seizing to an address also hit the cap only for the liquidator's own set (liquidators can clear their own slots).
- The victim cannot `issue` a synth whose debt token is not already in their list — first-time borrowing of a new market reverts.
- Existing funds are not permanently lost: the victim can remove attacker-planted entries by transferring each dust balance to another address (each zeroing transfer calls `removeFromDepositTokensOfAccount`), so this is a temporary, attacker-renewable liveness/DoS griefing rather than permanent freezing. The attacker can also re-dust after cleanup, and can front-run the victim's cleanup transactions to re-add entries, making remediation unreliable while the attack is active.

### Likelihood Explanation
Fully unprivileged: the attacker needs only dust amounts of each underlying (no approvals, no privileged roles, no oracle manipulation). Cost is bounded by the number of distinct deposit/debt tokens the pool supports (each `addDepositToken` is governor-controlled, so the attack surface is the deployed collateral count). The attack must be maintained (victim can clear slots), so likelihood of sustained impact depends on attacker persistence, but the initial griefing is trivially reachable on any live deployment with multiple collateral types.

### Recommendation
- Make the per-account token set opt-in or bounded by value: e.g., only add tokens on `deposit`/`issue` initiated for `onBehalfOf_ == caller` or via an explicit `account_` allowlist, and do not add entries on plain `transfer`/`seize` of dust amounts.
- Alternatively, track "account added token" separately from raw ERC20 receipt: only call `addToDepositTokensOfAccount` inside `deposit`/`_mint`, and let `transfer` recipients hold a balance without occupying a list slot (adjust `depositOf`/`unlockedBalanceOf` accounting accordingly).
- At minimum, add a permissioned or value-threshold-based removal path so victims/keepers can purge dust entries.

### Proof of Concept
Hardhat-style test sketch (assumes a deployed `Pool` with N deposit tokens and attacker with dust of each underlying):

```ts
// Victim starts with an empty token list
expect(await pool.getDepositTokensOfAccount(victim)).deep.eq([]);

const depositTokens = await pool.getDepositTokens(); // N entries

// Attacker deposits 1 wei-equivalent dust of each underlying and transfers to victim
for (const dt of depositTokens.slice(0, MAX - victimExisting)) {
  const token = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('IERC20', await token.underlying());
  await underlying.connect(attacker).approve(token.address, 1);
  await token.connect(attacker).deposit(1, attacker.address);
  await token.connect(attacker).transfer(victim.address, 1); // adds entry to victim's set
}

// Now victim's list is at MAX_TOKENS_PER_USER
// 1) Any deposit on behalf of victim in a NEW deposit token reverts
const newToken = await ethers.getContractAt('DepositToken', someNewDepositToken);
await expect(
  newToken.connect(attacker).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 2) Victim issuing a synth whose debt token is new to them reverts inside DebtToken._mint
await expect(
  debtToken.connect(victim).issue(issueAmount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) Re-dusting: attacker can re-add an entry each time victim clears one,
//    front-running victim's cleanup transfers.
```

Note: full verification of the exact revert in `issue` depends on `debtFloorInUsd` configuration and the number of deployed deposit tokens on the target chain (each `addDepositToken` is governor-gated, so attacker-controlled collateral creation is not possible — the attack is bounded by existing tokens). A fork test against a live deployment (e.g., `deployments/mainnet/Pool.json`) is needed to confirm the reachable list size equals `MAX_TOKENS_PER_USER` before the deposit-token supply caps bind.
