### Title
Unbounded growth of shared `MarketPairPriceToOrderStore` price-index enables authenticated-user DB/index DoS analogous to Ceph RGW bucket-index OMAP exhaustion - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
CVE-2018-16846 describes authenticated Ceph RGW users flooding a bucket's OMAP index with unbounded object entries, degrading that shared index's performance for everyone using the bucket. The java-tron TRC10 exchange/market subsystem has an analogous shared, unbounded index: `MarketPairPriceToOrderStore`, keyed by `sellTokenId + buyTokenId + sellQuantity + buyQuantity` [1](#0-0) . Any signed `MarketSellAssetContract` can insert a brand-new, attacker-chosen key into this shared, globally-iterated store, and the only quota enforced is a **per-account** cap of active orders, not a per-token-pair or global cap on distinct price points.

### Finding Description
`MarketSellAssetActuator.validate()` only checks that the *calling account's* open order count is below `MAX_ACTIVE_ORDER_NUM = 100` [2](#0-1)  and enforces `MAX_ACTIVE_ORDER_NUM = 100` as a static field [3](#0-2) . There is no limit on:
- the number of *distinct* `(sellTokenId, buyTokenId, sellQuantity, buyQuantity)` combinations that can exist for a given token pair across the whole network, and
- the number of *different accounts* that can each contribute up to 100 orders with unique quantities to the same pair.

Every unmatched order is persisted via `saveRemainOrder`, which creates a brand-new key in `MarketPairPriceToOrderStore` whenever the exact quantity pair hasn't been used before, and bumps the pair's price-point counter in `MarketPairToPriceStore.addNewPriceKey` [4](#0-3) [5](#0-4) . Since `sellTokenQuantity`/`buyTokenQuantity` are attacker-controlled integers, an attacker (using many low-cost accounts, or repeatedly cancel-and-recreate cycles) can generate an effectively unbounded number of distinct keys for a single token pair, all persisted permanently in one physical LevelDB/RocksDB column that every node must maintain and scan.

This shared index is range-scanned by:
- `matchOrder`, on every subsequent sell of the opposite side, via `pairPriceToOrderStore.getPriceKeysList(...)` → `getKeysNext` [6](#0-5) [7](#0-6) 
- Public HTTP/gRPC read APIs `getMarketPriceByPair`, `getMarketPairList`, and `getMarketOrderListByPair` in `Wallet`, reachable by any anonymous API client via `GetMarketPriceByPairServlet` and `GetMarketOrderListByPairServlet` [8](#0-7) [9](#0-8) 
- The underlying `Chainbase.getKeysNext` implementation, which for market data must merge in-memory uncommitted snapshot maps with on-disk keys and sort/filter them per call [10](#0-9) , making the cost of every lookup proportional to the number of live snapshots and the size of the persisted key range for that pair.

Because `MarketCancelOrderActuator` only removes a price key when its order list becomes fully empty [11](#0-10) , and nothing stops repeated creation of new unique-quantity orders across large numbers of funded accounts, the store can be grown indefinitely at low, fixed marginal cost (`dynamicStore.getMarketSellFee()` per order, a fixed configurable TRX fee, not scaling with index size).

### Impact Explanation
This does not itself steal funds, but it degrades a shared, node-wide resource (the market price/order index and its API surface) that all participants and node operators rely on — directly analogous to the Ceph CVE's OMAP/bucket-index DoS. Once the index for a popular pair becomes very large:
- `matchOrder`'s snapshot-aware `getKeysNext` calls become progressively more expensive for every subsequent sell-side transaction on that pair, slowing block-application throughput for the Manager processing transactions against that pair.
- The public read-only API endpoints (`getmarketpricebypair`, `getmarketorderlistbypair`, `getmarketpairlist`) become slower/heavier for every caller, potentially exhausting node resources under repeated invocation and increasing the surface for API resource exhaustion.
- The condition is persistent — entries are stored in on-disk revoking stores and are not garbage collected unless every order at that price point is filled or explicitly cancelled by its owner, so an attacker willing to pay ordinary fees (and not bother cancelling) leaves permanent bloat.

### Likelihood Explanation
Any account holding a small amount of TRX for fees can broadcast `MarketSellAssetContract` transactions; distinct `sellTokenQuantity`/`buyTokenQuantity` values are entirely attacker-controlled, so generating thousands of unique keys per pair requires only paying the fixed market-sell fee repeatedly (optionally spreading the 100-order-per-account cap across multiple accounts, which is a very low barrier). No special privilege beyond an ordinary funded account and an existing/attacker-created TRC10 asset pair is required.

### Recommendation
- Introduce a cap on the total number of distinct price points (or total open orders) per token pair enforced in `MarketSellAssetActuator.validate()`, in addition to the existing per-account `MAX_ACTIVE_ORDER_NUM` check.
- Consider quantizing/bucketing prices (rounding sell/buy quantities to a limited set of price levels) so the number of distinct keys per pair is bounded regardless of account count.
- Add rate limiting or increasing marginal fees for creating new unique price points on a single pair to disincentivize index-bloat spam.

### Proof of Concept
1. Have `AllowMarketTransaction` enabled (committee-controlled dynamic property).
2. Create N funded accounts (any amount above minimal fee balance).
3. Issue two TRC10 assets to trade.
4. From each account, broadcast up to 100 `MarketSellAssetContract` transactions selling asset A for asset B, each transaction using a unique `(sellTokenQuantity, buyTokenQuantity)` pair chosen so it never matches an existing order (e.g., monotonically increasing `buyTokenQuantity`).
5. Repeat across many accounts; each transaction adds one new key to `MarketPairPriceToOrderStore` and increments `MarketPairToPriceStore`'s price count for that pair (`addNewPriceKey`), with no cross-account or pair-level ceiling.
6. Observe that `getMarketPriceByPair`/`getMarketOrderListByPair`/`getMarketPairList` calls and subsequent `matchOrder` matching executions against that pair grow proportionally slower as the index size increases, with no possibility to shrink it short of every order owner individually cancelling.

  public List<byte[]> getPriceKeysList(byte[] headKey, long count, long totalCount, boolean skip) {
    List<byte[]> result = new ArrayList<>();

    if (has(headKey)) {
      long limit = count > totalCount ? totalCount : count;
      if (skip) {
        // need to get one more
        result = getKeysNext(headKey, limit + 1).subList(1, (int)(limit + 1));

  // for market
  private List<byte[]> getKeysNext(Snapshot head, byte[] key, long limit) {
    if (limit <= 0) {
      return Collections.emptyList();
    }

    Map<WrappedByteArray, Operator> collectionList = new HashMap<>();
    if (head.getPrevious() != null) {
      ((SnapshotImpl) head).collectUnique(collectionList);
    }

    // just get the same token pair
    List<WrappedByteArray> snapshotList = new ArrayList<>();
    if (!collectionList.isEmpty()) {
      snapshotList = collectionList.keySet().stream()
          .filter(e -> MarketUtils.pairKeyIsEqual(e.getBytes(), key))
          .collect(Collectors.toList());
    }

    // for delete operation
    long limitLevelDB = limit + collectionList.size();

    List<WrappedByteArray> levelDBList = new ArrayList<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().getKeysNext(key, limitLevelDB)
          .forEach(e -> levelDBList.add(WrappedByteArray.of(e)));
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().getKeysNext(key, limitLevelDB)
          .forEach(e -> levelDBList.add(WrappedByteArray.of(e)));
    }

    // just get the same token pair
    List<WrappedByteArray> levelDBListFiltered = levelDBList.stream()
        .filter(e -> MarketUtils.pairKeyIsEqual(e.getBytes(), key))
        .collect(Collectors.toList());

    List<WrappedByteArray> keyList = new ArrayList<>();
    keyList.addAll(levelDBListFiltered);

    // snapshot and levelDB will have duplicated key, so need to check it before,
    // and remove the key which has been deleted
    snapshotList.forEach(ssKey -> {
      if (!keyList.contains(ssKey)) {
        keyList.add(ssKey);
      }
      if (collectionList.get(ssKey) == Operator.DELETE) {
        keyList.remove(ssKey);
      }
    });

    return keyList.stream()
        .filter(e -> MarketUtils.greaterOrEquals(e.getBytes(), key))
        .sorted((e1, e2) -> MarketUtils.comparePriceKey(e1.getBytes(), e2.getBytes()))
        .limit(limit)
        .map(WrappedByteArray::getBytes)
        .collect(Collectors.toList());
  }
