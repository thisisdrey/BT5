### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` rows survive `DeleteAccount`, letting a leaked yield resume execute an old account's callback against a freshly re-created account with the same id - ([File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/actions.rs])

### Summary
`remove_account` (called from `action_delete_account`) purges `Account`, `ContractCode`, `AccessKey`/gas-key rows and `ContractData`, but never removes the `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` trie rows keyed by the deleted account. If account `A` creates a `promise_yield_create` receipt targeting itself and then deletes itself, those four rows persist in the trie. When `A` is later re-created (a distinct logical account, new owner/contract), a `PromiseResume` receipt carrying the original `data_id` will still find the old `PromiseYieldReceipt` under key `receiver_id=A`, and the runtime will execute the stale receipt's callback using the current (new) account's code/storage, with `predecessor_id == receiver_id == A` inherited from the original receipt.

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs` only clears these column families for an account being deleted: [1](#0-0) [2](#0-1) 

It never iterates or removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` for the account, even though these are per-account columns (they are listed in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY`): [3](#0-2) 

`action_delete_account` calls only `remove_account` and does nothing further to purge yield-related state before erasing the account struct: [4](#0-3) 

When `A` calls `promise_yield_create` on itself, the runtime stores `PromiseYieldReceipt{receiver_id: A, data_id}` when the `PromiseYield` receipt is received, and `PromiseYieldStatus::Yielded` at creation time: [5](#0-4) [6](#0-5) 

The stored yield receipt's `predecessor_id` is set to the account that issued the `promise_yield_create` call, i.e. `A` itself (self-yield), when the wasm-created receipt is materialized: [7](#0-6) 

None of this state is cleaned up by `DeleteAccount`, so after `A` deletes itself and a brand-new account also named `A` is created (`action_create_account` only sets a fresh `Account` struct, doing nothing to the leftover yield keys): [8](#0-7) 

Later, when a `PromiseResume` receipt (or `PromiseResume` initiated via the `promise_yield_resume` host function) targeting the leaked `data_id` arrives for receiver `A`, the runtime looks it up purely by `(account_id, data_id)` without any check that the account is the same logical entity that created the yield, nor any created/deleted marker: [9](#0-8) 

It finds the stale `yield_receipt` (old-A's callback method/args), feeds it the resume payload as `ReceivedData`, and executes it via `apply_action_receipt` against the *current* account state - the freshly re-created `A`'s code and storage: [10](#0-9) 

The trigger for resume is the `promise_yield_resume` host function, which is gated only by `has_promise_yield_receipt`/`has_promise_yield_status` on the *current* `self.account_id` (the receiver of the receipt currently executing), with no notion of account identity/creation-time versioning: [11](#0-10) 

Because the callback that runs is the original (old-A-authored) `ActionReceiptMetadata.actions` — a method name and arguments chosen entirely by the old owner of `A` at `promise_yield_create` time — and it executes with `predecessor_id == receiver_id == A`, any "assert self-call" style authorization check in the new `A`'s contract (common for internal callback-only methods) will pass, since predecessor equals the account's own id. This is a genuine determinism/authorization-exactness violation: the identity `A` after re-creation is a logically distinct entity, but leftover state lets old-A's chosen code path execute under new-A's current storage/contract with self-call privileges it should never have.

The codebase is aware of a closely related class of bug (stale contract vs. fresh account within the same chunk for `FunctionCall`), evidenced by the existing regression test `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`, but that fix only addresses contract-preparation staleness, not the yield/resume trie-key leakage described here: [12](#0-11) 

### Impact Explanation
This is an authorization-escalation / cross-account privilege-carry-over bug: a previously-deleted account's yield callback (arbitrary method name and args chosen by the *old* owner) can be caused to execute later against a completely different, newly-created account sharing the same `AccountId`, with `predecessor_id == receiver_id == A`, i.e. with "self-call" privileges. Depending on what the new account's contract does with self-only-gated internal methods (a very common pattern for cross-contract callback completion, e.g. finalizing transfers, minting, or state updates), this can let an unrelated, unprivileged former-owner trigger privileged internal logic on the new account, potentially leading to unexpected state mutation, fund movement, or logic bypass on the new account. This maps to the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions: (1) account `A` must be deletable and then re-created with the identical `AccountId` (this is standard NEAR account lifecycle — sub-accounts and top-level accounts can be deleted and later re-registered by any party); (2) the resumption must ultimately be triggered by a `FunctionCall` receipt targeting the new `A` that ends up invoking `promise_yield_resume`/`submit_promise_resume_data` with the leaked `data_id` — either by the new owner's own contract forwarding attacker-supplied `data_id` arguments (a realistic pattern for generic yield/resume-based contracts), or via the timeout path in `resolve_promise_yield_timeouts` which checks `contains_key` on the stale `PromiseYieldReceipt` regardless of account identity and can auto-trigger a resume receipt once the timeout elapses: [13](#0-12) 
This means even without any cooperation from the new account, a stale yield can autonomously fire once the yield timeout window elapses, executing old-A's callback against new-A. The attacker's cost is only ordinary transaction fees to create the yield and delete the account; the entire attack chain uses standard unprivileged transactions/receipts.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows for the account being deleted (mirroring the existing access-key/contract-data cleanup loops), and correspondingly cancel/skip any outstanding `PromiseYieldTimeout` queue entries referencing the deleted account (e.g., by checking account existence, or an account-generation/version tag, before honoring a resume against a stale receiver). Alternatively/additionally, tie yield state to an account "incarnation" identifier so that a resume for a stale incarnation is rejected even if rows are not eagerly purged.

### Proof of Concept
Runtime integration test plan (extending `runtime/runtime/src/tests/apply.rs` / `integration-tests/src/tests/runtime/test_yield_resume.rs` style):
1. Deploy a yield-capable contract (e.g. `near_test_contracts::rs_contract()`) on account `A`.
2. Call `call_yield_create_return_data_id` on `A` targeting itself, capture `data_id`; assert `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` and `TrieKey::PromiseYieldStatus{receiver_id: A, data_id}` exist in state.
3. Submit `DeleteAccountAction` for `A` (beneficiary any account) and commit; assert `get_account(A)` is `None`, but directly query the trie and assert the `PromiseYieldReceipt`/`PromiseYieldStatus` rows for `A` still exist (this is the core bug assertion).
4. Re-create account `A` via `CreateAccountAction` + deploy a new contract exposing a method that forwards an attacker/caller-supplied `data_id` into `promise_yield_resume` (or reuse the same `call_yield_resume` test contract method).
5. Submit a `FunctionCallAction` invoking that resume-forwarding method on new-`A` with the original leaked `data_id` and a payload.
6. Assert the outcome shows the *original* yield callback (as specified by old-`A`) executed successfully (`SuccessValue`/expected side effect written to new-`A`'s storage) rather than failing with "no pending yield" — and assert `predecessor_id == receiver_id == A` on the executed receipt.
7. As an alternate path, skip step 5 and instead advance `block_height` past `yield_timeout_length_in_blocks` and run `resolve_promise_yield_timeouts`; assert a `PromiseResume` timeout receipt is generated and executed against new-`A` without any explicit resume call, confirming the leak is exploitable passively as well.

        data_id: CryptoHash,

        let has_yield_receipt_in_state =

                .map_err(wrap_storage_error)?;
        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }
