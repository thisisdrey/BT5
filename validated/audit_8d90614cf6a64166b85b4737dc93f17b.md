### Title
Unbounded array allocation from attacker-controlled length field in `BatchValidateSign` precompile can crash a node via OutOfMemoryError - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Roundcube CVE stems from trusting a size field taken from untrusted input to drive a large allocation/decompression without bounding it against the actual available data or a sane cap, letting a small crafted input trigger disproportionate resource consumption (DoS). The same anti-pattern exists in java-tron's `PrecompiledContracts` helper methods used by the `BatchValidateSign` precompiled contract (address `0x0b`), where a length word taken directly from the caller-supplied call data is used to size an array before any bound check tied to the size of the actual input.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read a length value straight out of the decoded `DataWord[]` words derived from the contract call's `data` argument and immediately allocate arrays sized by that value: [1](#0-0) [2](#0-1) [3](#0-2) 

In `extractBytesArray`/`extractSigArray`, `len` comes from `words[offset].intValueSafe()` — an attacker fully controls the raw call-data word that becomes `words[offset]`, so `len` can be crafted to be an arbitrarily large positive `int` (up to `Integer.MAX_VALUE`). The code then allocates `byte[len][]` immediately, before any subsequent bounds-check against the true length of `data`. Unlike `CALLDATACOPY`/`CODECOPY` (`OperationActions.java` lines 379-418) and TVM memory operations (`Memory.extend`, `EnergyCost.getVoteWitnessCost*`), which meter memory growth through energy costs (`calcMemEnergy`) proportional to the requested size and can throw `Program.OutOfMemoryException` before allocating, these array-extraction helpers used by the precompiled-contract dispatch path perform no such metering: energy for a precompile call is computed by `getEnergyForData(byte[] data)`, which is based only on the actual submitted `data.length`, not on the declared (and unchecked) array-length word embedded within that data.

This means a caller can submit a small, cheap `data` payload (only a few tens of bytes, so `getEnergyForData` charges very little energy) that encodes a length word claiming e.g. `0x7FFFFFFF` items, causing the node to attempt to allocate a huge two-dimensional byte array (`new byte[len][]`) while executing the precompile, well out of proportion to the energy actually paid and to the true size of the input.

### Impact Explanation
A crafted, cheaply-priced smart-contract call that invokes the `BatchValidateSign` (or related) precompile with a manipulated length word can force the executing node to attempt a very large heap allocation. This can throw `OutOfMemoryError`, degrade performance for all transactions being processed in that block, or crash the JVM handling the transaction, matching the "node crash or halt" impact class the CVE analog requires. Because any account can broadcast a transaction that triggers a contract call into this precompile, this is reachable by an unprivileged transaction sender.

### Likelihood Explanation
Likelihood is limited by the fact that `intValueSafe()` truncates/normalizes `DataWord` values rather than always yielding attacker-arbitrary magnitude, and by JVM heap sizing/limits which may throw `OutOfMemoryError` that is caught elsewhere in the VM execution try/catch chain rather than crashing the whole node outright. I was not able to fully verify (within the remaining investigation budget) whether an outer `catch (Throwable)`/`OutOfMemoryError` handler around precompile execution absorbs this cleanly as a reverted transaction versus destabilizing the node process, so the concrete crash/DoS severity here is uncertain without further validation of the execution wrapper (e.g., in `Program`/`VM` dispatch) and of `DataWord.intValueSafe()`'s exact clamping behavior.

### Recommendation
Bound `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` against the actual remaining length of `data`/`words` (similar to the existing `isValidAbiEncoding` check) before allocating, rejecting the call early when the declared count could not possibly fit within the supplied call data.

### Proof of Concept
Construct a TVM contract that calls the `BatchValidateSign` precompiled contract address with ABI-encoded data whose "array length" header word is set to a very large value (e.g. `0x7FFFFFFF`) while the actual payload after it is only a few words long; broadcast this as a normal `TriggerSmartContract` transaction with the minimum energy needed to pass `getEnergyForData`'s data-length-only charge, and observe the node attempt a huge `byte[][]` allocation inside `extractSigArray`/`extractBytesArray` during precompile execution.
