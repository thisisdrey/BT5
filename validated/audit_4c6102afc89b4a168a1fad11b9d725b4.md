### Title
Missing slippage/minimum-output protection in `ExchangeWithdrawActuator` allows sandwich attacks on TRC10 exchange (Bancor-style AMM) withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract` lets an exchange creator withdraw `quant` of one token from a Bancor-style TRC10 AMM pool, receiving a proportional amount (`anotherTokenQuant`) of the paired token, computed from the pool's *current* balances at the time the transaction executes. The protobuf contract carries no caller-supplied minimum for `anotherTokenQuant`, and the actuator's only sanity check is that the computed amount is `> 0` (plus an unrelated rounding-precision check). This mirrors exactly the reported Uniswap-V3 `_decreaseLiquidity` bug class: a liquidity/position-reduction call with no `amountMin` slippage guard, only a "non-zero" check.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes the paired-token amount from the exchange pool's live balances: [1](#0-0) 

The only value checks performed are `anotherTokenQuant <= 0` (must be greater than zero) and a `RoundingMode`-based "Not precise enough" check for internal math consistency — neither is a user-specified minimum-received guard: [2](#0-1) 

`execute()` then recomputes `anotherTokenQuant` from the (possibly changed) pool balances at execution time and credits the account with that amount, without re-validating it against any caller-provided floor: [3](#0-2) 

The contract message itself has no `expected`/`min` field (unlike `ExchangeTransactionContract`, which does carry an `expected` field, and unlike `MarketSellAssetContract`, whose `buy_token_quantity` is explicitly documented as "min to receive"): [4](#0-3) 

For comparison, `ExchangeTransactionActuator` (the trade/swap path) *does* enforce the caller's minimum via the `expected` field, confirming the pattern the withdraw path is missing: [5](#0-4) 

Because the pool ratio (`firstTokenBalance` / `secondTokenBalance`) can be moved by any unprivileged account submitting an `ExchangeTransactionContract` (buy/sell) transaction in a block before the withdrawal is packed, an attacker can sandwich a pending `ExchangeWithdrawContract`:
1. Front-run: attacker submits a large `ExchangeTransactionContract` trade that skews the pool ratio against the withdrawer's token.
2. The victim's `ExchangeWithdrawContract` executes against the now-skewed pool, receiving a much smaller `anotherTokenQuant` than expected when they signed the transaction (only guaranteed to be `> 0`).
3. Back-run: attacker reverses the trade, extracting the value the victim lost, keeping the pool balanced for subsequent activity.

### Impact Explanation
This directly exposes the exchange creator to value extraction on every withdrawal — an unprivileged transaction broadcaster can profit at the expense of the withdrawing account without needing any special privilege, purely by ordering trades around the victim's `ExchangeWithdrawContract`. Given no caller-side floor exists, losses are bounded only by pool depth and available capital for the sandwich trade, which for TRC10 exchange pools (that can hold significant TRX/token liquidity, as seen in `exchangeCapsule2.setBalance(1_000_000_000000L, 10_000_000L)` in the test fixtures) can be material. This is a concrete unauthorized transfer of value (theft of funds) from the withdrawer to the sandwiching attacker, matching the accepted impact bar.

### Likelihood Explanation
Likelihood is high: any account can submit `ExchangeTransactionContract` transactions, and Tron block producers order transactions from the pending pool, giving an attacker practical ability to position trades immediately before and after a known pending withdrawal (visible on the network before inclusion). No special permission, staking, or witness status is required — only the ability to broadcast ordinary signed transactions, matching the "unprivileged transaction broadcaster" threat model in scope.

### Recommendation
Add a caller-supplied minimum-output field (e.g., `expected_another_token_quant`) to `ExchangeWithdrawContract`, analogous to `ExchangeTransactionContract.expected` and `MarketSellAssetContract.buy_token_quantity`. In `ExchangeWithdrawActuator.doValidate()`/`execute()`, compare the computed `anotherTokenQuant` against this caller-supplied minimum and reject the transaction if it falls below it, rather than only checking for `> 0`.

### Proof of Concept
1. Exchange creator `V` holds pool `P` with `firstTokenBalance = A`, `secondTokenBalance = B` (ratio `A:B`).
2. `V` signs and broadcasts `ExchangeWithdrawContract{exchangeId, tokenId=first, quant=q}`, expecting `anotherTokenQuant ≈ B*q/A`.
3. Attacker `M` observes the pending transaction and broadcasts an `ExchangeTransactionContract` selling a large amount of the second token into pool `P`, sharply increasing `firstTokenBalance` and decreasing `secondTokenBalance` (skewing ratio).
4. Block producer includes `M`'s trade before `V`'s withdrawal in the same block (or in a preceding block).
5. `V`'s `ExchangeWithdrawActuator.execute()` runs against the skewed pool: `anotherTokenQuant` is recomputed from the new, unfavorable `firstTokenBalance`/`secondTokenBalance` — see the computation in [6](#0-5) . The only guard that could stop this is the `<= 0` check, which a moderately-sized skew will not trigger.
6. `M` broadcasts a reverse `ExchangeTransactionContract` to restore the pool ratio, realizing profit equal to the value `V` lost versus the expected withdrawal amount.
