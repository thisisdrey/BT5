Based on my investigation, I found a concrete analog. Any peer with an established tunnel to a relay node can send unlimited `CreateRelayRequest` control messages targeting arbitrary VPN addresses. Each request causes the relay to call `AddRelay`, allocating a new `Relay` entry in `hm.Relays` and inserting it into the requester's `relayState` — with **no bound, no rate limit, and no deduplication check keyed on the requester** before the state is created.### Title
Unbounded relay-state allocation via unauthenticated `CreateRelayRequest` control messages leads to remote memory exhaustion - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` (the handler for `NebulaControl_CreateRelayRequest`) allocates a new `Relay` entry in the shared `HostMap.Relays` index and in the sending peer's `relayState` on every request that names a `target` other than the receiving node, provided the node has `relay.am_relay` enabled. There is no per-peer limit, no deduplication beyond a single "already established" check for the exact `(from, target)` pair, and no way for the accrued forwarding relay state to be reclaimed except via full tunnel teardown. A peer holding a valid but otherwise unprivileged tunnel to a relay node can repeatedly request relaying to many distinct, even non-existent, target VPN addresses, each of which durably consumes an index in `hm.Relays` and an entry in `relayState.relayForByIdx`/`relayForByAddr` until the requester's tunnel is destroyed.

### Finding Description
`handleCreateRelayRequest` in `relay_manager.go` is reached whenever any peer with an established Nebula tunnel sends a `header.Control` / `NebulaControl_CreateRelayRequest` message, which requires no additional certificate authority beyond the one used for the tunnel handshake itself (i.e., the same low bar as any other data-plane traffic once a tunnel exists) [1](#0-0) .

When the request's target is not the receiving node, and the receiver has `am_relay` enabled, the handler proceeds to the forwarding branch:
```
peer := rm.hostmap.QueryVpnAddr(target)
...
index, err = AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)
...
peer.relayState.UpdateRelayForByIpState(from, Requested)
...
_, err := AddRelay(rm.l, h, f.hostMap, target, &m.InitiatorRelayIndex, ForwardingType, PeerRequested)
``` [2](#0-1) 

`AddRelay` unconditionally inserts a new index into `hm.Relays` and into the caller's `RelayState.InsertRelay`:
```
hm.Relays[index] = relayHostInfo
newRelay := Relay{...}
relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)
``` [3](#0-2) 

Each call generates a fresh 32-bit index (`generateIndex`) and adds a permanent map entry that is only removed when the owning `HostInfo` is deleted from the hostmap via `unlockedDeleteHostInfo`, which cleans up `hm.Relays` entries for indexes the departing hostinfo owns as a relay hop:
```
for _, localRelayIdx := range hostinfo.relayState.CopyRelayForIdxs() {
    delete(hm.Relays, localRelayIdx)
}
``` [4](#0-3) 

Because the check for an existing relay is keyed only on the exact `(from, target)` VPN-address pair, `QueryRelayForByIp(from)` for a fresh `target`, an attacker holding one authenticated tunnel to a relay node can iterate through many distinct target addresses (real or fabricated, since `f.hostMap.QueryVpnAddr(target)` returning `nil` merely triggers a handshake attempt to `target`, not a request rejection) and force the relay to allocate and retain relay-index state for each one [5](#0-4) . This state persists indefinitely as long as the attacker's own tunnel to the relay stays up, because state teardown is coupled to hostinfo deletion, not to any per-request lifetime or cap. There is no cap analogous to a "conntrack max tracked connections" limit — the firewall module even has a `TODO: need conntrack max tracked connections handling` acknowledging the general class of missing resource bound in this codebase [6](#0-5) , but no equivalent safeguard exists for relay state at all.

This mirrors the reported bug class: a fallback/accounting code path (`transferDebt`/relay-index allocation) creates persistent system-wide state to cover a request from an untrusted-but-connected party, and no mechanism exists to bound, reconcile, or reclaim that state short of a full connection teardown — leaving the system to accumulate unresolved "debt" (dangling relay indexes) that can eventually destabilize the relay node.

### Impact Explanation
A single authenticated-but-otherwise-low-privilege peer can force a relay node to allocate unbounded `Relay` map entries and per-hostinfo `relayState` slots, since each distinct target address (real or invented) yields a new index that is never proactively evicted. This is a remote state-poisoning / resource-exhaustion primitive against any node running `relay.am_relay = true`: sustained abuse degrades or crashes the relay process by exhausting memory in the shared `hm.Relays` map, denying relay service to legitimate peers relying on that relay.

### Likelihood Explanation
Likelihood is high for any deployment that enables `relay.am_relay` (a common configuration for hub/relay nodes in NAT-heavy topologies). The only prerequisite is a completed handshake with the relay — no special certificate attributes, no privileged VPN network membership, and no rate limiting gate this control-message path. An attacker only needs one valid Nebula certificate signed by an in-scope CA to establish a tunnel and can then send many `CreateRelayRequest` messages with arbitrary/fabricated target addresses.

### Recommendation
- Impose a per-peer and/or global cap on the number of `Relay` entries a single requester (`from`) can cause a relay node to allocate, rejecting further `CreateRelayRequest`s once the cap is hit.
- Add an idle/expiry timeout for `Requested`/`PeerRequested` relay entries that are never completed (mirroring the `FirewallConntrack` timer-wheel eviction model already used for conntrack state), so unacknowledged relay requests are proactively reclaimed rather than persisting until tunnel teardown.
- Rate-limit `NebulaControl_CreateRelayRequest` processing per source hostinfo.

### Proof of Concept
1. Configure node `R` with `relay.am_relay: true` and establish a valid tunnel from attacker-controlled node `A` to `R` using a certificate signed by an in-scope CA (no special attributes required).
2. From `A`, repeatedly send `NebulaControl_CreateRelayRequest` messages to `R` with `RelayFromAddr = A`'s own VPN address and `RelayToAddr` set to many distinct addresses (some real peers of `R`, some entirely fabricated, unrouted addresses).
3. Each request causes `R.relayManager.handleCreateRelayRequest` to enter the "target is not me" branch at [2](#0-1) , calling `AddRelay` twice (once against the queried/handshaking `peer` hostinfo, once against `A`'s own hostinfo `h`), each allocating a new entry in `hm.Relays` and `relayState`.
4. Because no request-count or memory cap exists, and cleanup only happens via `unlockedDeleteHostInfo` when a hostinfo is torn down [4](#0-3) , repeating step 2 with thousands of distinct fabricated targets grows `hm.Relays` and `A`'s `relayState` maps without bound as long as `A`'s tunnel to `R` remains alive, exhausting `R`'s memory.

				newRelay.RemoteIndex = *remoteIdx
			}

		}
