Audit Report

## Title
Public ERC20 XCM deposit path drains the shared `ERC20TransfersCheckingAccount` via unrefundable per-recipient storage deposits — ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::deposit_asset_with_surplus` executes the `IERC20::transferCall` for every incoming ERC20-over-XCM deposit using `OriginFor::<T>::signed(TransfersCheckingAccount::get())` as the call origin [1](#0-0) . Since `pallet-revive` charges/holds storage deposits against the call origin rather than the XCM message's actual fee payer, any unprivileged user can deploy an arbitrary contract accepted by the permissive `ERC20Matcher` and repeatedly force the shared checking account to pay unrefundable storage-deposit holds for new beneficiary addresses they fully control, eventually exhausting the account and stalling ERC20-over-XCM processing.

## Finding Description
`ERC20Matcher` is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [2](#0-1) , and `IsLocalAccountKey20` only checks that a `Location` has the shape `(0, [AccountKey20 { .. }])` with no verification that the referenced address is a genuine, well-behaved ERC20 contract [3](#0-2) . This means any address — including a contract the attacker deploys and fully controls — is accepted as a first-class XCM fungible asset by `ERC20Transactor`.

In `deposit_asset_with_surplus`, the beneficiary-chosen `who` is mapped to an `H160` address, and the transfer call is executed with `TransfersCheckingAccount` as the transaction origin, not the depositing user or fee payer [1](#0-0) . `pallet-revive`'s storage metering (`ReservingExt::charge` → `Pallet::<T>::charge_deposit`) charges and holds the storage deposit from the call's origin for any newly-created storage slot (e.g., a fresh entry in the ERC20 contract's balance mapping for a never-before-seen beneficiary), and this hold is only released via `refund_deposit` when that specific storage is later cleared/shrunk. Since deposits to brand-new attacker-chosen beneficiary addresses create permanent balance-mapping entries that are never cleared in this flow, the storage deposit paid by `TransfersCheckingAccount` is never refunded.

The `ERC20TransferStorageDepositLimit` constant of `10_200_000_000` bounds only the per-call deposit, not the cumulative exposure across many calls [4](#0-3) . An attacker who deploys a minimal always-succeeding contract (structurally similar to the repository's own `MyTokenFake.sol` fixture) can repeatedly submit `withdraw_asset`/`deposit_asset` XCM programs targeting fresh `AccountKey20` beneficiaries, each iteration consuming a new unrefundable slice of the checking account's native-currency balance.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge/asset processing" impact category: an unprivileged, low-cost attacker can drain the native-currency balance backing the shared, protocol-owned `py/revch` account, and once exhausted, subsequent `bare_call`s from that account fail their balance/liquidity checks, halting all ERC20-over-XCM deposit processing chain-wide until the account is manually replenished.

## Likelihood Explanation
High — no privileged role, compromised relayer, or validator misbehavior is required. Deploying a `pallet-revive` contract and issuing `PolkadotXcm::execute` with `withdraw_asset`/`deposit_asset` instructions are ordinary, publicly available capabilities on Asset Hub, and the attacker fully controls both the target contract's behavior and the choice of fresh beneficiary addresses that trigger new storage allocations.

## Recommendation
- Do not use a shared, protocol-owned account (`TransfersCheckingAccount`) as the storage-deposit-paying origin for contract calls triggered by arbitrary, user-supplied XCM messages; attribute the storage cost to the message's own fee/asset payer instead.
- Impose a hard, tracked ceiling on total outstanding (un-refunded) deposit exposure for the checking account, with alerting/circuit-breaking as it is approached.
- Require additional validation (bytecode/interface conformance checks or governance-gated registration) before an address can be treated as a valid `ERC20Matcher` asset, similar to the explicit registration required for `TrustBackedAssets`/`ForeignAssets`.

## Proof of Concept
1. Attacker deploys a minimal contract `C` whose `transfer(address,uint256)` always succeeds and allocates a fresh storage slot for every new recipient (structurally like `MyTokenFake.sol`).
2. Attacker submits an XCM program via `PolkadotXcm::execute` performing `withdraw_asset` for `(AccountKey20(C), amount)` and `deposit_asset` to a never-before-seen `AccountKey20` beneficiary.
3. `deposit_asset_with_surplus` calls `IERC20::transferCall` on `C` with origin `TransfersCheckingAccount`; `C` allocates a new balance-mapping slot for the new beneficiary, and `pallet-revive` charges/holds the corresponding storage deposit from `TransfersCheckingAccount`.
4. Repeating step 2 with a new beneficiary each time drains a fresh, unrefunded slice of `TransfersCheckingAccount`'s native balance per call (bounded by `ERC20TransferStorageDepositLimit` per call, unbounded in aggregate), eventually exhausting the account and breaking ERC20-over-XCM deposit processing.
