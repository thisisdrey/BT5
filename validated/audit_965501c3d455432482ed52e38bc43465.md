## Finding: Legacy Bancor `Exchange` balance underflow allows draining a trading pair's reserves (unhardened path lacks the negative-balance guard)

### Title
Missing negative-balance check in the default (non-hardened) TRC10 Exchange (Bancor) calculation allows underflowing pool reserves and draining a token pair — (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes new pool balances after a swap using plain `long` arithmetic (`firstTokenBalance - buyTokenQuant` / `secondTokenBalance - buyTokenQuant`) unless the chain-wide proposal `ALLOW_HARDEN_EXCHANGE_CALCULATION` is enabled. Only the hardened branch verifies the resulting balances are non-negative; the default branch does not. [1](#0-0) 

### Finding Description
`ExchangeCapsule.transaction()` selects between `SafeExchangeProcessor` (hardened, `BigDecimal`-based) and `ExchangeProcessor` (legacy, `double`-based) purely based on `hardenedCalc`, which is driven by the dynamic property `ALLOW_HARDEN_EXCHANGE_CALCULATION`. This property defaults to `0` and must be separately activated by a committee proposal, meaning every deployment starts in the unhardened state. [2](#0-1) [3](#0-2) 

In the unhardened branch, the new balances are computed with raw subtraction/addition and stored unconditionally:
```java
newFirstTokenBalance = hardenedCalc ? ... : firstTokenBalance - buyTokenQuant;
...
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException(...);
}
```
The bounds check `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` is gated on `hardenedCalc`, so when hardening is off (the default), a `buyTokenQuant` larger than the available reserve silently underflows the pool balance to a negative `long`, and the corrupted (negative) balance is persisted via `setBalance()`. [4](#0-3) 

`buyTokenQuant` itself is derived from the legacy Bancor formula in `ExchangeProcessor`, which has no cap relative to the actual reserve — it is a `double`-based approximation of a continuous formula that can return a value exceeding the current `buyTokenBalance` when `sellTokenQuant` is large relative to the sell-side reserve:
```java
private long exchangeFromSupply(long balance, long supplyQuant) {
  supply -= supplyQuant;
  double exchangeBalance = balance * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, useStrictMath) - 1.0);
  return (long) exchangeBalance;
}
``` [5](#0-4) 

The only checks performed by the callers (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) validate that the *caller* has sufficient TRX/asset balance and that the resulting `anotherTokenQuant` meets the user's minimum-expected amount — none of them verify that the exchange's own reserve for the *other* token remains non-negative in the unhardened path: [6](#0-5) 

After `transaction()` returns, the actuator unconditionally credits the caller with `anotherTokenQuant` of the other token via `addAssetAmountV2`/`addExact(newBalance, anotherTokenQuant)`, regardless of whether the pool balance underflowed: [7](#0-6) 

### Impact Explanation
Any account holding the `Exchange` creator's TRC10/TRX pair can broadcast repeated `ExchangeTransactionContract` (or `ExchangeWithdrawContract`) transactions engineered to make the Bancor formula return `anotherTokenQuant` exceeding the counter-token's actual pool reserve. The pool balance stored in `ExchangeCapsule`/`ExchangeV2Store` goes negative, while the attacker's own account is credited real TRX/TRC10 tokens they never should have received — this is a direct theft/creation of unbacked balance from the exchange counterparty's reserves. Because `ExchangeContract` transactions are broadcastable by any unprivileged account without special permissions, this is reachable by any anonymous transaction sender.

### Likelihood Explanation
`ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to `0` on all java-tron networks unless a super-representative proposal explicitly activates it, so the vulnerable unhardened code path is what runs by default. Exploitation only requires crafting `quant`/`expected` fields in a standard `ExchangeTransactionContract`, well within reach of any account with minimal TRX/TRC10 balance and no special privileges.

### Recommendation
Move the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` validation outside of the `hardenedCalc` gate in `ExchangeCapsule.transaction()` so it always throws `ContractValidateException` regardless of which processor computed the result, or make hardened exchange calculation mandatory (remove the legacy `ExchangeProcessor` double-based path) rather than opt-in via proposal.

### Proof of Concept
1. Create (or locate) an `Exchange` pair (via `ExchangeCreateContract`) with small reserves, e.g. `firstTokenBalance = X` TRX and `secondTokenBalance = Y` of TRC10 token `T`, with `ALLOW_HARDEN_EXCHANGE_CALCULATION` left at its default value `0`.
2. Broadcast an `ExchangeTransactionContract` selling TRX (`tokenID = firstTokenID`) with a `quant` chosen so that the Bancor formula in `ExchangeProcessor.exchangeFromSupply` returns `buyTokenQuant` (the amount of token `T`) greater than the exchange's current `secondTokenBalance` (achievable by driving `supplyQuant/supply` toward the point where `pow(...,2000)` overshoots the linear reserve, since `useStrictMath`/hardening is off and no cap exists relative to reserve).
3. Set `expected` low enough to pass the `anotherTokenQuant < tokenExpected` check.
4. Observe `exchangeCapsule.transaction()` returns `buyTokenQuant > secondTokenBalance`; `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` becomes negative and is persisted with `Commons.putExchangeCapsule(...)`, while the attacker's account is simultaneously credited the full `anotherTokenQuant` of token `T` via `accountCapsule.addAssetAmountV2(...)` — tokens the exchange pool did not actually have.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
