### Title
Deterministic same-priority tie-break by ascending `TransactionId` lets a later attacker transaction always evict an earlier victim transaction of identical priority on capacity eviction - (File: core/src/banking_stage/transaction_scheduler/transaction_priority_id.rs)

### Summary
`TransactionPriorityId` derives `Ord` over `(priority, id)`, and `id` is a monotonically increasing `Slab` key assigned in arrival order at `TransactionStateContainer::insert_map_only`. Because `priority_queue: BTreeSet<TransactionPriorityId>` sorts by this tuple and `push_ids_into_queue` evicts via `pop_first()` on capacity overflow, two transactions with identical computed `priority` are deterministically ordered by arrival order, and the earlier-arriving (lower-`id`) transaction is always the one evicted.

### Finding Description
`push_ids_into_queue` inserts each new `TransactionPriorityId` into the `BTreeSet` and, if `id_to_transaction_state.len() > capacity`, calls `self.priority_queue.pop_first()` to drop the lowest-ranked entries [1](#0-0) . `TransactionPriorityId`'s `Ord` is derived field-by-field over `(priority, id)` [2](#0-1) , and the crate's own unit test explicitly documents that at equal priority, the entry with the smaller `id` is "less than" the entry with the larger `id` [3](#0-2) .

`id` here is a `TransactionId` returned as the key of a `Slab::vacant_entry()` insertion, which increases monotonically with arrival order for newly received transactions [4](#0-3) , and this is exactly the flow used for freshly received network transactions in `receive_and_buffer.rs`, where `transaction_id = container.insert_map_only(state)` is computed right before `TransactionPriorityId::new(priority, transaction_id)` and pushed into the queue with `push_ids_into_queue` [5](#0-4) .

Consequently, if an attacker submits a transaction with a `priority` value exactly equal to a victim's transaction that already sits in the buffer, the attacker's transaction (inserted later, hence with a strictly larger `id`) is always ranked strictly higher in the `BTreeSet` ordering. When the container reaches capacity and `pop_first()` fires, the victim's earlier-arriving, equal-priority transaction is evicted first, not the attacker's. `priority` is computed deterministically from public inputs — `reward` (base fee + `compute_unit_price`) and `cost` from the `CostModel` — via `calculate_priority_and_cost`, `P = R * MULTIPLIER / (cost + 1)` [6](#0-5) . Because base fee, cost, and reward are derived from static/observable parameters (signature count, compute unit limit/price, instruction set), an attacker can trivially construct a transaction whose `(reward, cost)` pair yields the identical integer priority as a target transaction — for example, both using compute_unit_price = 0 with the same instruction shape and cost bucket, which is common for default-config wallets and yields priority 0 for many/most transactions (as shown by `priority_is_zero_when_base_and_priority_fees_are_zero`) [7](#0-6) . No existing mechanism randomizes or otherwise perturbs this tie-break, and no rate limit/QoS check inspects relative arrival order to protect already-buffered, equal-priority transactions from later arrivals.

### Impact Explanation
This is a QoS/scheduling-fairness bypass: an unstaked, unprivileged network sender can starve or silently drop another user's already-fee-paying, already-buffered transaction purely by flooding the leader's TPU with transactions computed to tie the victim's priority exactly, at zero marginal fee advantage. This falls under the "priority handling / buffer eviction" bounty category described in the prompt scope — a victim's transaction can be dropped (never scheduled, never included in a block) even though it arrived first and paid an equivalent fee rate, purely due to an implementation detail (ascending Slab-key tie-break) rather than genuine fee competition.

### Likelihood Explanation
- Feasibility is high for the many transactions with priority 0 (compute_unit_price 0, base-fee-zero banks, or any bank/config where a large share of default-fee transactions share the same computed integer priority) — no per-victim inspection is even needed, since the attacker simply needs to also submit priority-0 transactions.
- For non-zero priorities, an attacker can still deterministically tie a specific observed target by replicating cost/compute-unit-price so that `reward * MULTIPLIER / (cost+1)` matches, since the formula and cost model are public/deterministic.
- The attack requires no elevated privilege — only the ability to submit transactions to the TPU faster than they are drained, sufficient to force `id_to_transaction_state.len() > capacity` and trigger `pop_first()` eviction, which is within the described unprivileged/unstaked threat model.
- The behavior is 100% deterministic and reproducible in a unit test using `push_ids_into_queue` on a container filled at capacity.

### Recommendation
Change the tie-break so that at equal `priority`, earlier arrival wins over later arrival (i.e., FIFO fairness at equal price) rather than favoring the newest arrival. Concretely, either: (a) invert the `id` comparison for ties (e.g., implement a custom `Ord` that compares `priority` ascending but `Reverse(id)` for ties so lower `id` sorts higher/"more valuable" and survives eviction), or (b) introduce a secondary, arrival-order-independent tie-break (e.g., transaction signature hash) so ties cannot be systematically gamed by flooding after observing a target's fee. Add an explicit unit test asserting that among two entries with identical `priority`, the earlier-inserted (lower `id`) one is retained on `pop_first()` eviction and the later one is dropped.

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }

/// Calculate priority and cost for a transaction:
///
/// Cost is calculated through the `CostModel`,
/// and priority is calculated through a formula here that attempts to sell
/// blockspace to the highest bidder.
///
/// The priority is calculated as:
/// P = R / (1 + C)
/// where P is the priority, R is the reward,
/// and C is the cost towards block-limits.
///
/// Current minimum costs are on the order of several hundred,
/// so the denominator is effectively C, and the +1 is simply
/// to avoid any division by zero due to a bug - these costs
/// are calculated by the cost-model and are not direct
/// from user input. They should never be zero.
/// Any difference in the prioritization is negligible for
/// the current transaction costs.
pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
