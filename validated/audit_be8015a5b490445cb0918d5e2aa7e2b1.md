Key verification points:
1. `PRECISION_SCALING_FACTOR` is indeed `4096` [1](#0-0) 
2. `stake` has no zero-amount check and calls `update_pool_and_staker_rewards` unconditionally before adding `amount` (which can be zero) to storage [2](#0-1) 
3. `unstake` similarly has no zero-amount check [3](#0-2) 
4. `update_pool_rewards` unconditionally advances `last_update_block` regardless of whether `reward_per_token` increment was zero [4](#0-3)

Audit Report

## Title
Griefing via zero-value `stake`/`unstake` permanently advances `last_update_block`, rounding reward-per-token accrual to zero and losing rewards for the accrual period - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
The `pallet-asset-rewards` reward algorithm (`reward_per_token`) computes accrual as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, then `update_pool_rewards` unconditionally stamps `last_update_block = now`, regardless of whether the computed increment rounded to zero. Since `stake` and `unstake` are unprivileged, callable every block, and do not enforce a non-zero amount, an attacker can repeatedly call `stake(pool_id, 0)` on their own account each block to force `rewardable_blocks_elapsed = 1` on every invocation, and if `reward_rate_per_block * 4096 < total_tokens_staked`, the division truncates to zero while `last_update_block` still advances, permanently erasing that block's reward accrual for every staker in the pool.

## Finding Description
`reward_per_token` computes `rewardable_blocks_elapsed` relative to `pool_info.last_update_block`, then adds `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` to the stored accumulator using integer (checked) arithmetic via `ensure_mul`/`ensure_div` [6](#0-5) . `PRECISION_SCALING_FACTOR` is fixed at `4096` [1](#0-0) , so whenever `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked`, integer division truncates the increment to zero.

Regardless of that outcome, `update_pool_rewards` unconditionally sets `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()` [4](#0-3) . Both `stake` and `unstake` call `update_pool_and_staker_rewards` (which calls `reward_per_token` then `update_pool_rewards`) on every invocation, before touching `total_tokens_staked`/`staker_info.amount` with the caller-supplied `amount`, and neither extrinsic validates `amount > 0` [7](#0-6) [8](#0-7) . Since `rewardable_blocks_elapsed` is measured from `last_update_block`, calling `stake(pool_id, 0)` every block guarantees `rewardable_blocks_elapsed = 1` each time, maximizing the odds of the increment rounding to zero for a given `reward_rate_per_block`/`total_tokens_staked` ratio, while `last_update_block` is still bumped forward each call, permanently discarding that block's reward from `reward_per_token_stored`.

## Impact Explanation
This is a public, underpriced-work griefing vector against a live reward-accounting pallet, matching the "public underpriced work that degrades ... reward payouts" impact category in the Polkadot SDK gate. As `total_tokens_staked` grows, the zero-rounding window widens, letting an attacker indefinitely suppress reward accrual (`reward_per_token_stored`) for legitimate stakers in the affected pool at near-zero cost, causing an unrecoverable loss of foregone reward-asset payouts for other stakers.

## Likelihood Explanation
No privileged role, governance, or off-chain trust assumption is required — only a signed account calling the public `stake` (or `unstake`) extrinsic with `amount = 0` every block. This is trivially cheap and repeatable on any low-fee chain, and the small `PRECISION_SCALING_FACTOR` (`4096`) makes the rounding-to-zero condition realistically reachable for common `reward_rate_per_block`/`total_tokens_staked` ratios.

## Recommendation
- Reject zero-amount `stake`/`unstake` calls with `ensure!(!amount.is_zero(), Error::<T>::...)`.
- Do not advance `last_update_block` when the computed `reward_per_token` increment is zero; instead track fractional/dust remainder so unrounded reward-time is not discarded, or only advance `last_update_block` up to the point actually accounted for.
- Consider a higher-precision fixed-point accumulator (e.g. `FixedU128`) for `reward_per_token_stored`, similar to `pallet-nomination-pools`'s `RewardCounter` [9](#0-8) .

## Proof of Concept
1. Admin creates a pool via `create_pool` with `reward_rate_per_block = R` and existing `total_tokens_staked = S` such that `R * 4096 < S`.
2. Attacker calls `stake(pool_id, 0)` every subsequent block.
3. Each call triggers `reward_per_token` with `rewardable_blocks_elapsed = 1`; `R * 1 * 4096 / S == 0` due to truncation [5](#0-4) .
4. `update_pool_rewards` still advances `last_update_block = now` [10](#0-9) , discarding that block's reward.
5. Repeating step 2 indefinitely suppresses reward accrual for the pool while `S` stays large relative to `R`, at the cost of gas for zero-value `stake` calls.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()

					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
