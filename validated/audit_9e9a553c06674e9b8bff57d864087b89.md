### Title
Bridged-in supply accounting never decremented when bridged tokens are burned via repay/liquidate, permanently inflating `bridgedInSupply` and DoS-ing inbound bridging - (File: contracts/SyntheticToken.sol)

### Summary
`SyntheticToken` tracks cross-chain circulation with cumulative counters `totalBridgedIn` (incremented when `ProxyOFT` mints) and `totalBridgedOut` (incremented when `ProxyOFT` burns). However, tokens that were minted by `ProxyOFT` can also be burned through non-bridge paths — `DebtToken.repay`/`repayAll` and `Pool.liquidate`/`swap`-driven burns call `SyntheticToken.burn` with `msg.sender` being the DebtToken/Pool, and `_burn` only adjusts `amoSupply` (AMO path) or `totalBridgedOut` (ProxyOFT path). `totalBridgedIn` is never decremented, so `bridgedInSupply()` permanently overstates the net bridged-in amount. Once it crosses `maxBridgedInSupply`, all subsequent inbound bridge transfers revert with `SurpassMaxBridgingSupply`. This is the same class as the Nouns Builder finding: a burn path fails to decrement a supply counter, corrupting protocol accounting. [1](#0-0) [2](#0-1) 

### Finding Description
- `ProxyOFT._creditTo` mints via `SyntheticToken.mint` → `_mint` increments `totalBridgedIn` and enforces `bridgedInSupply() <= maxBridgedInSupply` [3](#0-2) .
- `DebtToken.repay` calls `syntheticToken.burn(_msgSender, _repaid)` where `_msgSender` is the DebtToken contract, so `_burn` takes neither the ProxyOFT nor AMO branch — `totalBridgedIn` is untouched even though bridged-in tokens were destroyed [4](#0-3) .
- The same applies to `Pool` burns (liquidation/fee seize paths that end in `burn`).
- Since `bridgedInSupply() = max(totalBridgedIn - totalBridgedOut, 0)` is computed from cumulative counters [5](#0-4) , each "bridge-in then repay/liquidate" cycle permanently adds to the numerator. An unprivileged user can repeat this: bridge in msX via `ProxyOFT.sendFrom` on a remote chain, then deposit collateral and `DebtToken.issue`/repay, or simply repay an existing position with the bridged tokens. Each loop requires only normal user actions and permanently consumes the `maxBridgedInSupply` budget.

### Impact Explanation
Once cumulative `totalBridgedIn - totalBridgedOut` exceeds `maxBridgedInSupply`, every subsequent `_creditTo` mint reverts with `SurpassMaxBridgingSupply`, so all inbound LayerZero transfers for that synthetic fail and must sit in the retry/StoredPayload queue — tokens were already debited on the source chain but cannot be credited on this chain. This is a griefing/permanent-inflation attack that causes temporary freezing of user bridged funds (recoverable only via governor raising `maxBridgedInSupply` or swapping out the ProxyOFT). It also silently breaks the bridge-conservation invariant the caps are meant to enforce, since the measured "bridged-in" circulation no longer corresponds to actual bridged-in tokens.

### Likelihood Explanation
No special privilege is needed: repaying debt with bridged-in synthetics is an ordinary user action, and it happens naturally over time (users bridge msUSD/msETH to a chain and repay positions or get liquidated). Even without an attacker deliberately looping, the counter drifts upward monotonically and will eventually reach any finite `maxBridgedInSupply`. Modifiers don't help: `onlyIfCanBurn` admits DebtToken/Pool, and the cap check at `mint` actively turns the drift into a DoS.

### Recommendation
Track bridge-origin supply accurately instead of relying on the caller identity of `burn`. Options: (a) decrement `totalBridgedIn` in `_burn` when burning on behalf of DebtToken/Pool up to the amount attributable to bridged-in circulation (requires accounting the bridged-in portion per burn, e.g. `totalBridgedIn -= min(amount_, totalBridgedIn - totalBridgedOut)`); or (b) drop the cumulative-counter model and cap current net bridged circulation using a counter that is decremented on every burn of bridged-minted tokens; or (c) compute the cap check against actual outstanding bridged supply rather than lifetime totals.

### Proof of Concept
Foundry fork/unit test sketch:
```solidity
// setup: pool, debtToken (msUSD), syntheticToken, proxyOFT wired; user has collateral deposited
uint256 amount = 100e18;

// 1. Simulate inbound bridge: prank ProxyOFT mint
vm.prank(address(proxyOFT));
syntheticToken.mint(user, amount);            // totalBridgedIn = 100e18

// 2. User repays debt (or any pool-side burn) with the bridged tokens
vm.prank(user);
debtToken.repay(user, amount);                // burn via DebtToken -> totalBridgedIn still 100e18

// bridgedInSupply() == 100e18 despite zero bridged tokens circulating
assertEq(syntheticToken.bridgedInSupply(), amount);
assertEq(syntheticToken.totalSupply(), /* decreased */);

// 3. Loop steps 1-2 until bridgedInSupply() > maxBridgedInSupply,
//    then the next ProxyOFT mint reverts with SurpassMaxBridgingSupply
vm.prank(address(proxyOFT));
vm.expectRevert(SurpassMaxBridgingSupply.selector);
syntheticToken.mint(user, 1);
```
Key assertions: `bridgedInSupply()` does not decrease after a DebtToken-initiated `burn`, and repeated bridge-in→repay cycles eventually make `SyntheticToken._mint` revert for all inbound bridge transfers.

    function _burn(address account_, uint256 amount_) private {
        if (account_ == address(0)) revert BurnFromTheZeroAddress();

        address _msgSender = _msgSender();

        if (_isMsgSenderProxyOFT(_msgSender)) {
            totalBridgedOut += amount_;
            if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
        } else if (_isMsgSenderAmo(_msgSender)) {
            // AMO can only burn from self address.
            // account_ should be AMO and in this case it is same as _msgSender()
            if (account_ != _msgSender) revert AmoInvalidAccount();

            amoSupply -= amount_;
        }

        uint256 _currentBalance = balanceOf[account_];
        if (_currentBalance < amount_) revert BurnAmountExceedsBalance();
        unchecked {
            balanceOf[account_] = _currentBalance - amount_;
            totalSupply -= amount_;
        }

        emit Transfer(account_, address(0), amount_);
    }
