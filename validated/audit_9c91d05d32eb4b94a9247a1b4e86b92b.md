### Title
`remove_account` fails to clear `PromiseYieldReceipt`/`PromiseYieldStatus` trie entries, allowing a stale yield-resume callback to execute privileged actions on a re-created account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account, but never removes `TrieKey::PromiseYieldReceipt` or `TrieKey::PromiseYieldStatus` entries keyed by that account's `receiver_id`. [1](#0-0)  If the account is subsequently re-created and the original `PromiseResume` for the outstanding yield is delivered, the runtime's resume handling will fetch the surviving stale `Receipt` via `get_promise_yield_receipt` and execute its embedded actions against the new account.

### Finding Description
`set_promise_yield_receipt` stores the full `Receipt` (including its action list and `predecessor_id`/`receiver_id`) under `TrieKey::PromiseYieldReceipt { receiver_id, data_id }`, separate from the `Account` trie entry. [2](#0-1)  Likewise `TrieKey::PromiseYieldStatus` is keyed independently. [3](#0-2) 

`remove_account` is the single account-teardown routine invoked when `DeleteAccountAction` is processed, and it only clears `Account`, `ContractCode`, access/gas keys, and `ContractData` for the given `account_id` — it does not scan for or remove `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` entries keyed by that same account as `receiver_id`. [1](#0-0)  `get_promise_yield_receipt` and `get_promise_yield_status` perform a raw lookup by `(receiver_id, data_id)` and return whatever is stored regardless of whether the corresponding `Account` still exists. [4](#0-3) 

As a result: (1) `victim.near` calls `promise_yield_create`, producing a `PromiseYield` receipt stored via `set_promise_yield_receipt`; (2) `victim.near` is deleted via `DeleteAccountAction`, which invokes `remove_account` — the `PromiseYieldReceipt`/`PromiseYieldStatus` entries survive; (3) an unrelated party creates a new `victim.near` account; (4) when the original `PromiseResume` (carrying the matching `data_id`) is finally delivered, the runtime's resume-processing path looks up the stale receipt via `get_promise_yield_receipt` and applies its stored actions — which still target `receiver_id == victim.near` — against the newly created account.

### Impact Explanation
This is authorization escalation across accounts: actions embedded in the old owner's yield-callback receipt (e.g., `Transfer`, `AddKey`, `DeployContract`) execute against the new account owner's state without their consent, potentially transferring funds out of / manipulating access keys or contract code on the freshly created account. This maps to the "theft of user funds" / "authorization escalation across accounts or promises" bounty categories.

### Likelihood Explanation
Preconditions are attacker-affordable and require no privileged access: any account can call `promise_yield_create` on a contract implementing yield/resume, then submit a normal `DeleteAccountAction` transaction (assuming `locked == 0` and normal delete-account preconditions) for its own account before the resume arrives. Reuse of a just-deleted account ID by "an unrelated party" is the one condition outside attacker control, but account-ID reuse after deletion is an accepted state in NEAR (`near_reserved` / no cool-down enforced at protocol level), so this is feasible, and PromiseYield timeout windows can be long enough for this race in principle.

### Recommendation
When processing `DeleteAccountAction` (i.e., inside `remove_account` or its caller), also purge any `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries whose key is scoped to the deleted `account_id`, mirroring the cleanup already done for access keys and contract data. Alternatively, when resuming, validate that the receipt's stored receiver still matches the account's current state/identity (e.g., an account "generation"/nonce check) before applying actions.

### Proof of Concept
Integration test (runtime-test-loop or `runtime/runtime` integration tests) plan:
1. Deploy a yield/resume-capable contract on `victim.near`; call `promise_yield_create`, causing a `PromiseYield` receipt to be stored via `set_promise_yield_receipt`, and assert `get_promise_yield_receipt(trie, "victim.near", data_id)` returns `Some`.
2. Submit a `DeleteAccountAction` for `victim.near` (fund conditions satisfied, `locked == 0`), apply the receipt through `remove_account`, and confirm `get_account(trie, "victim.near")` is `None` while `get_promise_yield_receipt(trie, "victim.near", data_id)` still returns `Some(receipt)` (assert survival, i.e., the bug).
3. Re-create `victim.near` (via a normal `CreateAccountAction`/`AddKeyAction` from a different signer) with a fresh `Account` state.
4. Deliver the original `PromiseResume` receipt with matching `data_id`, run `process_receipt`, and assert that the new account's `Account`/`AccessKey` state changed as dictated by the stale receipt's actions (e.g., new key added, balance transferred), proving that unauthorized actions executed against the re-created account.

pub fn set_promise_yield_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }
}

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
