### Title
Malformed `Content-Length` on HTTP requests is silently coerced to 0, enabling request-framing desync/smuggling on the RPC HTTP server - (File: `stackslib/src/net/http/request.rs`)

### Summary
`HttpRequestPreamble::consensus_deserialize` silently discards an unparseable `Content-Length` header on inbound requests instead of rejecting the request, while the equivalent response-side parser explicitly errors out on the same malformed input. This asymmetric, permissive parsing of a framing-critical header is the same bug class as CVE-2017-2666 (Undertow): invalid input in a value that determines message-body boundaries is accepted by this node when a stricter component (a proxy, or this node's own response parser) would treat it differently, producing disagreement about where one HTTP message ends and the next begins.

### Finding Description
When parsing an inbound HTTP request preamble, the `content-length` header value is parsed with `.parse::<u32>()`, and any parse failure is swallowed: [1](#0-0) 

If parsing fails (e.g. a non-numeric value, a negative sign, leading `+`, an overflowing value like `4294967296`, or any value httparse's ASCII/duplicate-header checks don't otherwise reject), `content_length` is set to `None` rather than causing a `DeserializeError`. Later, this is exposed via: [2](#0-1) 

`get_content_length()` collapses `None` to `0`. This value directly drives how many payload bytes the `StacksHttp` state machine will consume for this message: [3](#0-2) 

By contrast, the response-preamble parser treats the exact same malformed-value case as fatal: [4](#0-3) 

This is a genuine equality violation: the request parser's *effective* declared body length (0, due to silent coercion) no longer equals the *actual* number of body bytes the client placed on the wire and that any RFC-compliant intermediary (reverse proxy, load balancer) would have computed from the same header. Because HTTP/1.1 keep-alive is the default (`keep_alive` defaults to `true` for HTTP/1.1, see the preamble parser initializing `keep_alive` from version), the connection is not closed after this desynchronized message; the state machine will attempt to parse the next preamble starting at the byte immediately after the request headers — which is actually still-unconsumed body data from the "0-length" request. This is precisely a request-smuggling-class desync: one party (the fronting proxy validating/forwarding by RFC rules, or a naive client) believes N bytes of body were sent and consumed, while this node believes 0 bytes were consumed, so the extra N bytes get reinterpreted as the start of a subsequent, attacker-influenced "request" on the same connection.

### Impact Explanation
This falls under the "unchecked wire length" acceptable-impact category: an attacker can inject a request whose body bytes get misattributed to a different logical HTTP message boundary on the RPC HTTP server. In deployments where the Stacks node's HTTP interface sits behind a reverse proxy that keeps connections alive/pooled between clients and multiplexes requests to the backend (a common production pattern), this framing disagreement can let one client's crafted trailing bytes be spliced onto and parsed as part of a subsequent, different client's request on the same backend connection — a classic HTTP request-smuggling primitive that can be leveraged for request forgery, cache poisoning, or response/queue desync between clients sharing the proxy-to-node connection. It requires no authentication and only a single malformed request.

### Likelihood Explanation
Reaching this code path requires only sending a syntactically-valid-otherwise HTTP/1.1 request with a `Content-Length` value that fails `u32::parse` (trivial to construct, e.g. `Content-Length: -1`, `Content-Length: 99999999999`, or `Content-Length: 1x`) to any Stacks RPC HTTP listener. No special privileges, node secrets, or peer keys are needed — this is exactly the kind of remote, unauthenticated input the `HttpRequestPreamble::consensus_deserialize` codec is designed to accept from arbitrary clients.

### Recommendation
Make request-side `Content-Length` parsing symmetric with the response-side behavior: if the header is present but fails to parse as a valid non-negative `u32`, return `CodecError::DeserializeError` immediately instead of silently defaulting to `None`/`0`, mirroring the response-preamble handling in `stackslib/src/net/http/response.rs`. Additionally, consider rejecting requests that specify both `Content-Length` and `Transfer-Encoding`, and rejecting duplicate/ambiguous length headers as fatal errors (already partially covered by the duplicate-header check, but only for exact key repeats, not for malformed-but-unique values).

### Proof of Concept
Send the following over a raw TCP connection to the node's RPC HTTP port (illustrating the parser accepting a malformed length and defaulting to 0, while extra bytes remain framed as the start of the "next" message):

```
POST /v2/transactions HTTP/1.1
Host: node:20443
Content-Length: -1
Content-Type: application/octet-stream

GET /v2/info HTTP/1.1
Host: node:20443

```

`HttpRequestPreamble::consensus_deserialize` parses the first request, fails to parse `-1` as `u32`, and sets `content_length = None` (`get_content_length()` → `0`) instead of erroring. `StacksHttp::payload_len` then reports `0` bytes of body for this message, so the state machine treats the bytes starting at `GET /v2/info HTTP/1.1\r\n...` as the next pipelined request/message boundary rather than as body content of the first request — demonstrating the framing-length disagreement that underlies request smuggling.
