### Title
Unbounded array-length trusted from calldata causes OutOfMemoryError/node crash in TVM precompiled-contract signature/byte-array decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Several precompiled-contract helper methods (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) decode a dynamic array length directly from attacker-supplied calldata via `DataWord.intValueSafe()` and immediately use it to allocate a `byte[len][]` array, with no upper bound check against the actual size of `data`/`words`. A contract call can supply a crafted length word (e.g. close to `Integer.MAX_VALUE`) to force a huge allocation, crashing the node with an `OutOfMemoryError`.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read `len = words[offset].intValueSafe()` from the caller-controlled `data` byte array and then execute `new byte[len][]` before validating that `len` is consistent with the amount of data actually present: [1](#0-0) 

`intValueSafe()` only clamps to `Integer.MAX_VALUE` when the value overflows 4 bytes or is negative; any positive value that fits in an `int` (including values close to `Integer.MAX_VALUE`, e.g. `0x7FFFFFFF`) is returned unmodified: [2](#0-1) 

This is conceptually the same class of bug as CVE-2016-9190/Pillow's "Insecure Sign Extension": an attacker-supplied size/length field embedded in crafted input is trusted and used directly to drive memory allocation/array sizing without validating it against the real available data, leading to abnormal memory behavior (there it was heap corruption in `ImagingNew`/`Storage.c`; here it is an unchecked huge allocation).

These helper functions are reached from precompiled contracts that accept ABI-encoded dynamic arrays of signatures/bytes (e.g. batch/multi-signature verification precompiles), which are invoked through the standard TVM `CALL`-family opcode path: [3](#0-2) 

### Impact Explanation
Any account able to broadcast a `TriggerSmartContract` transaction (or deploy a contract that calls the vulnerable precompile) can trigger allocation of an array sized close to `Integer.MAX_VALUE` elements (each a `byte[]` reference, ~8 bytes on 64-bit JVM plus array overhead, i.e. up to ~16GB just for reference slots). This will throw `OutOfMemoryError` inside the JVM executing the transaction. Because `OutOfMemoryError` is an unchecked `Throwable` that can escape ordinary exception-handling assumptions used elsewhere in the VM execution stack, this can crash or destabilize the full node process, taking a validator/witness or API-serving node offline — matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The attack requires only crafting the ABI-encoded call data to one of the precompiled contracts that use `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, setting the length word for the dynamic array to a large value (e.g. `0x7FFFFFFF`). No special privileges, signing keys, or network position are required — a single, ordinary signed transaction from any unprivileged account suffices. This makes the likelihood high, limited only by the attacker needing minimal TRX for the transaction fee/bandwidth.

### Recommendation
Add strict bounds validation for `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating arrays — e.g., reject if `len` is negative, exceeds a reasonable maximum (bounded by the actual size of `words`/`data`), or would require allocating more elements than `(data.length / WORD_SIZE)`. This mirrors the bounds checks already present in `RLP.verifyLength` and `ContractEventParser.subBytes`, which should be applied consistently across all calldata-length-driven allocation sites in `PrecompiledContracts.java`.

### Proof of Concept
1. Deploy or call an existing precompiled contract (at a known TVM precompile address) whose `execute(byte[] data)` implementation internally calls `extractBytes32Array`, `extractBytesArray`, or `extractSigArray` with an offset/word structure controlled by the calling contract's ABI-encoded arguments.
2. Encode the calldata such that the word at the array-length position equals `0x7FFFFFFF` (or another very large positive value that fits into 4 bytes, e.g. `0x0FFFFFFF`).
3. Broadcast a `TriggerSmartContract` transaction invoking this precompile with the crafted calldata.
4. The node executing the transaction attempts `new byte[len][]`, which for large `len` throws `OutOfMemoryError`, potentially crashing or destabilizing the executing node/JVM.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
