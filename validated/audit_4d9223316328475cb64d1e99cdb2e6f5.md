### Title
DoS via dust `DepositToken` transfers filling a victim's per-account token list, blocking collateral top-ups and forcing liquidation - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The Rocket.Chat report is a CWE-400 denial of service: a crafted input exhausts a bounded resource and crashes a victim's session. The Metronome analog is the per-account token list in `Pool` capped at `MAX_TOKENS_PER_USER = 30` combined debt + deposit tokens [1](#0-0) . Because `DepositToken._transfer` (and `_mint`) unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero [2](#0-1) , any unprivileged attacker can permissionlessly push tokens into a victim's list by transferring 1-wei dust of every deposit token in the pool, no consent required. Once the list reaches 30, `onlyIfAdditionWillNotReachMaxTokens` reverts `UserReachedMaxTokens`, bricking every code path that adds a new token to that account.

### Finding Description
1. `DepositToken.transfer`/`transferFrom` only validate the *sender's* unlocked balance via `_revertIfLocked(sender_, amount_)` [3](#0-2) . The recipient is never consulted.
2. `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` when `_recipientBalanceBefore == 0` [4](#0-3) .
3. `Pool.addToDepositTokensOfAccount` reverts when `debtTokensOfAccount + depositTokensOfAccount >= 30` [5](#0-4) .
4. The same add-path is hit by `DepositToken._mint` on `deposit(amount_, onBehalfOf_)` and by liquidation `seize` proceeds to the liquidator, and by `DebtToken.issue`/`mint` via `addToDebtTokensOfAccount` — so a filled list reverts: deposits of any *new* collateral to the victim, minting any new synth debt, and receiving any new deposit token.

The victim cannot clear the attacker's entries while underwater: `removeFromDepositTokensOfAccount` only fires when a balance reaches zero, and if the victim has debt, `unlockedBalanceOf` locks the dust (it is counted inside `balanceOf` used by `debtPositionOf`), so the dust cannot be transferred back out [6](#0-5) .

### Impact Explanation
Temporary-to-condition-dependent freezing of funds and forced loss: a victim whose position approaches the liquidation threshold cannot deposit any additional collateral type (each `deposit` reverts in `_mint` → `addToDepositTokensOfAccount`), cannot open a new borrow, and cannot receive collateral top-ups from third parties via `onBehalfOf_` or plain transfers. Combined with a price move, the victim is guaranteed to be liquidated and loses the liquidation fee spread — a direct, attacker-caused loss that would not have occurred otherwise. This matches the "crafted input crashes the workspace" DoS class: a cheap, repeatable, permissionless input permanently consumes a bounded per-victim resource.

### Likelihood Explanation
Fully unprivileged and reachable: the attacker only needs an EOA, dust amounts of underlying collateral, and the public `deposit` + `transfer` functions (usable directly or through `Operator.execute`/`NativeTokenGateway`). Cost scales with the number of listed deposit/debt tokens in the pool; with ~15 deposit tokens the attacker fills half the cap themselves and the victim's existing positions typically supply the rest. No privileged role, oracle manipulation, or governance action is required. Constraints: the pool must list enough distinct deposit tokens for the attacker to fill the cap, and the attack is most damaging against accounts with existing debt near the liquidation threshold.

### Recommendation
- Do not add tokens to a recipient's list on plain `transfer`/`transferFrom`/`seize` without consent; gate list-addition behind an opt-in (e.g., track deposit tokens only for balances minted via `deposit`, or let users remove dust entries via a `sweep`-style function callable by the account itself).
- Alternatively, allow `removeFromDepositTokensOfAccount` to be triggered by the account holder for dust balances, or exclude balances below a minimum threshold from counting toward `MAX_TOKENS_PER_USER`.
- Ensure a victim can always burn/remove an unwanted token entry regardless of lock status (locked dust should still be removable since removing the entry only affects accounting iteration, not collateral value).

### Proof of Concept
Hardhat/foundry fork sketch:

```solidity
// Setup: pool P with deposit tokens d0..dN and victim V holding d0 deposit + active debt.
// Attacker A:
for (uint i; i < N; ++i) {
    DepositToken dt = depositTokens[i];
    underlying[i].approve(address(dt), DUST);
    dt.deposit(DUST, attacker);          // mints msdTOKEN_i to attacker
    dt.transfer(victim, 1);              // adds dt to victim's list — no consent
}
// Repeat / combine with victim's existing entries until
// debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30

// Assert DoS:
vm.expectRevert(UserReachedMaxTokens.selector);
depositTokenNew.deposit(amount, victim);        // top-up blocked

vm.expectRevert(UserReachedMaxTokens.selector);
debtToken.issue(amount, victim);                // new borrow blocked

// Price drops (or time passes with interest accrual): victim crosses liquidation
// threshold and cannot recapitalize → Pool.liquidate succeeds; victim loses
// collateral + liquidation fee. Assert position was liquidatable only because
// every add-token path reverted.
```

Key assertions: `pool.debtPositionOf(victim)` shows unhealthy; every `deposit(..., victim)` for a token not already in the victim's list reverts with `UserReachedMaxTokens`; `liquidate` then succeeds and seizes collateral. If the victim has debt, `dt.transfer(attacker, 1)` by the victim also reverts via `NotEnoughFreeBalance`, showing the dust cannot be cleared.
