### Title
`vesting::distribute()` Permanently DoS'd by Any Shareholder Opting Out of Direct Coin Transfers — (`File: aptos-move/framework/aptos-framework/sources/vesting.move`)

---

### Summary

`vesting::distribute()` iterates over every shareholder atomically and calls `aptos_account::deposit_coins` for each recipient. If any single deposit aborts, the entire transaction reverts. A shareholder whose account exists but is not registered for APT and who has called `set_allow_direct_coin_transfers(false)` causes every future `distribute()` call to abort permanently, freezing all other shareholders' vested APT in the contract forever. `create_vesting_contract` does not validate shareholder addresses for APT registration, while `set_beneficiary` explicitly does — the code even comments on the exact DoS risk — leaving the initial shareholder list unguarded.

---

### Finding Description

`vesting::distribute()` withdraws unlocked stake and distributes it to every shareholder in a single atomic loop:

```move
// vesting.move lines 730-740
let grant_pool = &vesting_contract.grant_pool;
let shareholders = &grant_pool.shareholders();
shareholders.for_each_ref(|shareholder| {
    let shareholder = *shareholder;
    let shares = pool_u64::shares(grant_pool, shareholder);
    let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
    let share_of_coins = coin::extract(&mut coins, amount);
    let recipient_address = get_beneficiary(vesting_contract, shareholder);
    aptos_account::deposit_coins(recipient_address, share_of_coins);  // ← aborts here
});
```

`aptos_account::deposit_coins` contains the following guard for accounts that exist but are not yet registered for the coin type:

```move
// aptos_account.move lines 123-128
if (!coin::is_account_registered<CoinType>(to)) {
    assert!(
        can_receive_direct_coin_transfers(to),
        error::permission_denied(EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS)
    );
    coin::register<CoinType>(&create_signer(to));
};
```

Any account holder can call `set_allow_direct_coin_transfers(false)` to set `allow_arbitrary_coin_transfers = false`. If that account was created via the lower-level `account::create_account` (which does not auto-register for APT, unlike `aptos_account::create_account`), then `can_receive_direct_coin_transfers` returns `false` and `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.

`create_vesting_contract` validates the `withdrawal_address` but **not** the shareholder addresses:

```move
// vesting.move lines 549-558
assert_account_is_registered_for_apt(withdrawal_address);   // ← withdrawal_address is checked
assert!(shareholders.length() > 0, ...);
assert!(buy_ins.length() == shareholders.length(), ...);
// ← no assert_account_is_registered_for_apt for each shareholder
```

By contrast, `set_beneficiary` explicitly performs the check and documents the exact DoS risk:

```move
// vesting.move lines 921-923
// Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
// fail and block all other accounts from receiving APT if one beneficiary is not registered.
assert_account_is_registered_for_apt(new_beneficiary);
```

The guard exists for the admin-controlled path but is absent for the initial shareholder list, which is set at contract creation and is not admin-modifiable per-shareholder without going through `set_beneficiary`.

---

### Impact Explanation

When `distribute()` aborts mid-loop, the entire transaction is rolled back: no shareholder receives any coins, the withdrawn stake is not re-deposited (Move's abort semantics unwind all state changes), and the vesting contract's `remaining_grant` and staking state remain unchanged. Subsequent calls to `distribute()` will hit the same abort. The unlocked APT is effectively frozen inside the contract's stake pool indefinitely. All honest shareholders permanently lose access to their vested tokens. `terminate_vesting_contract` also calls `distribute()` internally, so even the admin cannot cleanly terminate the contract.

---

### Likelihood Explanation

The trigger is fully unprivileged and requires only two on-chain transactions by the malicious shareholder:

1. Ensure the shareholder account was created via `account::create_account` (not `aptos_account::create_account`), so it is not registered for APT.
2. Call `set_allow_direct_coin_transfers(false)`.

After step 2, every future `distribute()` call on that vesting contract will abort. The malicious shareholder does not need any special role, capability, or governance power. The attack is permanent and irreversible without admin intervention via `set_beneficiary` — but `set_beneficiary` requires the admin to know which shareholder is the blocker and to act before the contract is fully stuck.

---

### Recommendation

Add the same `assert_account_is_registered_for_apt` check for each shareholder inside `create_vesting_contract`, mirroring the guard already present in `set_beneficiary`:

```move
shareholders.for_each_ref(|shareholder| {
    let shareholder: address = *shareholder;
    assert_account_is_registered_for_apt(shareholder);  // ← add this
    let (_, buy_in) = simple_map::remove(&mut buy_ins, &shareholder);
    ...
});
```

Additionally, consider restructuring `distribute()` to be fault-tolerant: skip or defer individual recipients that cannot receive funds rather than aborting the entire distribution, so one bad recipient cannot block all others.

---

### Proof of Concept

1. Admin calls `create_vesting_contract` with shareholders `[alice, bob]`.
2. Bob calls `account::create_account(bob_address)` (lower-level, no APT registration).
3. Bob calls `set_allow_direct_coin_transfers(false)`.
4. Time passes; vesting period elapses; stake unlocks.
5. Anyone calls `vesting::distribute(contract_address)`.
6. The loop reaches Bob: `deposit_coins(bob_address, bob_share)` → account exists, not registered for APT, direct transfers disabled → aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
7. Entire transaction reverts. Alice receives nothing.
8. Step 5–7 repeats on every future call. The vesting contract is permanently stuck.
