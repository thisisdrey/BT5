### Title
Deterministic accounts (NEP-616) can be permanently reprogrammed post-funding when initialized with a mutable `GlobalContractIdentifier::AccountId` code reference - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
NEP-616 "deterministic accounts" derive their account ID from a `DeterministicAccountStateInit` (code + data), with the intent that the account's behavior is fixed/deterministic once created. However, `state_init.code` can reference a global contract either by `GlobalContractIdentifier::CodeHash` (immutable) or `GlobalContractIdentifier::AccountId` (mutable, owner-upgradeable) [1](#0-0) . When `AccountId` mode is chosen, the deterministic account's actual contract logic can be silently changed at any time after the account is funded, undermining the "deterministic"/immutable guarantee implied by the account model, closely paralleling the original report's root cause where an immutable-by-design parameter choice made at creation time (there, `callOnDepositCallback`) permanently and unrecoverably determined critical account behavior with no way to fix except abandoning/migrating the account.

### Finding Description
A deterministic account is created via `action_deterministic_state_init`, which calls `deploy_deterministic_account` → `use_global_contract` to bind the account's code to the `GlobalContractIdentifier` given in `state_init.code()` [2](#0-1) . In `use_global_contract`, if the identifier is `GlobalContractIdentifier::AccountId(id)`, the account's contract field is set to `AccountContract::GlobalByAccount(id.clone())` rather than a fixed code hash [3](#0-2) . The actual bytecode used at execution time for `GlobalByAccount` accounts is whatever code `id` currently has deployed under `GlobalContractDeployMode::AccountId`, which that account's owner can redeploy/overwrite at will via `action_deploy_global_contract` with no versioning or consent from users of the deterministic accounts derived from it [4](#0-3) [5](#0-4) .

The deterministic-account creation code explicitly documents an intended security invariant — that the account's *actor_id* is pinned to the predecessor to prevent hijacking via `AddKey`/`DeployContract` [6](#0-5)  — but this protection is orthogonal to and does not prevent the global-contract owner from changing the code referenced by `AccountId` mode. Nothing in `action_deterministic_state_init` or `deploy_deterministic_account` restricts `state_init.code` to `CodeHash` only, so a deterministic account can be created (and its address permanently fixed, since the ID is derived from the initial state init payload) while its runtime logic remains fully mutable by a third party (the global contract owner), indefinitely, after funds/state have already been deposited into that account.

This is directly analogous to the reported bug class: a configuration decision made once at object-creation time (`callOnDepositCallback` there; choice of `CodeHash` vs `AccountId` code-reference mode here) silently and irreversibly determines critical behavior of the account for its entire lifetime, and an "avoidable misconfiguration" (choosing `AccountId` mode, or a user being fooled into depositing to a deterministic account whose code reference is `AccountId`-based) can nullify safety assumptions users hold about the account, with no direct recourse other than avoiding/abandoning the account.

### Impact Explanation
If a deterministic account (which by design/expectation should have unchangeable code, similar to how a CREATE2 counterfactual/deterministic contract is normally expected to be immutable once deployed) is instantiated using an `AccountId`-referenced (mutable) global contract, any party controlling that referenced account can unilaterally redeploy new code that is retroactively used by all deterministic accounts depending on it. If the deterministic account holds a balance or handles state on behalf of a user (e.g., is used as an escrow/vault whose behavior a user validated once), the code owner can later swap in malicious logic (e.g., a contract that transfers out the account's balance to an attacker-controlled address, or omits critical accounting the user is relying on), causing loss/theft of funds or breaking correctness assumptions users depend on. This crosses into authorization escalation across accounts, since a global-contract owner gains ongoing control over the logic of a technically independent account (the deterministic account) that was supposed to be behaviorally fixed once created.

### Likelihood Explanation
This requires an ordinary/unprivileged user to (a) choose `GlobalContractDeployMode::AccountId` when deploying a global contract, or unknowingly reference an `AccountId`-mode contract already deployed by a malicious party as the `code` for a `DeterministicAccountStateInitV1`, and (b) fund/use that resulting deterministic account. Since `DeterministicAccountStateInit` and `GlobalContractIdentifier::AccountId` are both fully reachable via ordinary transactions (`DeployGlobalContractAction`, `DeterministicStateInitAction`) with no privileged access required, the misconfiguration is directly reachable by any signer, matching the "avoidable misconfiguration" bug class from the source report.

### Recommendation
Either (1) disallow `GlobalContractIdentifier::AccountId` as the `code` field for `DeterministicAccountStateInit` (require `CodeHash` only, so that the "deterministic"/immutable guarantee actually holds for the lifetime of the account), or (2) clearly document/surface at the protocol and wallet/tooling level that deterministic accounts created with `AccountId`-mode code are NOT immutable and can be reprogrammed by the code owner at any time, so integrators and users can make an informed decision before depositing funds.

### Proof of Concept
1. Account `owner.near` deploys a global contract in `AccountId` mode (`DeployGlobalContractAction { deploy_mode: GlobalContractDeployMode::AccountId, code: benign_code }`) — this creates `GlobalContractIdentifier::AccountId(owner.near)` [7](#0-6) .
2. A user submits a `DeterministicStateInitAction` whose `state_init.code` is `GlobalContractIdentifier::AccountId(owner.near)`. The resulting deterministic account ID `0s...` is derived from this state init and is created with `AccountContract::GlobalByAccount(owner.near)` [3](#0-2) .
3. The user (or others) deposits funds into this deterministic account, trusting the currently-deployed benign code's logic (e.g., an escrow/vault method).
4. `owner.near` later calls `DeployGlobalContractAction` again with `deploy_mode: AccountId` and malicious code. This overwrites the code used by every `GlobalByAccount(owner.near)`-referencing account, including the deterministic account created in step 2, with no additional consent from that account or its depositors [4](#0-3) .
5. On the next invocation of the deterministic account, the new malicious logic executes (e.g., transferring the account's balance to an attacker address), even though the account's ID and the user's original trust were established under the prior contract version.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
