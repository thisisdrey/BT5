### Title
CREATE2 contract deployment can be front-run to permanently block a victim's deployment to the same address - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The reported Bravo `queue()` bug is a "predictable identity → squat it first" front-running problem: because the queued action's uniqueness key is derived purely from its content (not from proposal ID/sender), an attacker who sees a pending transaction can compute the same key and submit it first, permanently blocking the legitimate transaction with that content. In java-tron's TVM, the `CREATE2` opcode has the analogous property: the resulting contract address is fully deterministic from `(sender, salt, init-code hash)` via `WalletUtil.generateContractAddress2`, and the create logic rejects deployment if that address already has contract code deployed. This lets any observer of a pending `CREATE2` deployment (or any transaction that will trigger it) precompute the target address and race the deployer, permanently occupying that address and causing the victim's deployment to fail forever.

### Finding Description
`CREATE2` addresses are computed deterministically: [1](#0-0) 

When a contract creation (whether via `CREATE` or `CREATE2`) executes, `Program.createContractImpl` checks whether an account/contract already exists at the computed address, and if a contract already "exists" there, it aborts creation with an exception instead of overwriting it: [2](#0-1) [3](#0-2) 

The top-level `create()` entry point in `VMActuator` performs the equivalent existence check for the top-level `CreateSmartContract` transaction as well: [4](#0-3) 

Because the salt and init-code (and the deploying `Factory` contract address, or an EOA's address in the future `CREATE2` transaction-type case) are all attacker-observable in the mempool/broadcast transaction before it's included in a block, a third party can:
1. Observe a pending transaction that will call `create2(value, offset, size, salt)` with known `code` and `salt` (this is often visible directly, e.g., in the calldata of a `Factory.deploy(bytes code, uint256 salt)`-style call, as demonstrated by the project's own `Create2Test.testCreate2`).
2. Compute the resulting address off-chain using the same formula as `generateContractAddress2`.
3. Front-run with their own transaction that deploys *any* bytecode (even trivial/empty) to that same computed address before the victim's transaction is packed into a block.
4. Because the address now already has a contract/account with `contractAlreadyExists == true` (or - depending on the `allowTvmConstantinople` config path - the address is simply pre-occupied), the victim's original transaction fails permanently at that fixed salt, exactly mirroring the reported governance bug's "content-derived key gets squatted, victim's tx is permanently blocked."

This is not merely resource-griefing: it is a deterministic, permanent occupation of an address a legitimate protocol/user intended to deploy to (a common pattern for counterfactual/factory deployments, e.g., wallets, escrow contracts, or cross-chain deterministic addresses). The victim cannot retry with the same salt; they must burn a new salt, which can break systems (e.g., multi-chain deployment schemes, or off-chain-computed addresses referenced elsewhere) relying on a specific deterministic address.

### Impact Explanation
An attacker can permanently deny a legitimate deployer the ability to deploy a contract to a specific, protocol-significant deterministic address (frontrunning `CREATE2`), which can break systems that rely on address predictability (e.g., counterfactual instantiation, cross-chain address parity, or pre-funded/pre-referenced addresses). This matches "permanent freezing" of the deployer's intended on-chain identity/functionality at that address and can be leveraged for griefing or extortion (attacker could occupy addresses ahead of known factory deployments). This is a long-standing, well-known class of issue for `CREATE2`-based systems (same root cause as the reported Bravo issue: deterministic, attacker-computable keys with a public race window), warranting Medium severity consistent with the original report.

### Likelihood Explanation
Any unprivileged party who can observe the mempool/pending transactions (the calldata containing `code`/`salt`, or knowledge of a well-known factory + salt scheme) can compute the target address without any special privileges and broadcast a competing transaction with a higher fee/priority to front-run the victim, exactly as in the original report's front-running scenario. This requires no special access beyond ordinary transaction broadcasting.

### Recommendation
- Consider requiring `CREATE2` deployers to bind additional deployer-specific entropy (e.g., combine `msg.sender`/root transaction id in cases susceptible to griefing) where feasible, or provide protocol guidance discouraging use of easily-frontrunnable salts for security-critical deployments.
- At minimum, document this as an inherent business-logic risk of `CREATE2` (as in Ethereum) rather than a node-level defect, but confirm whether any java-tron-specific higher-level actuator (asset issuance name uniqueness, proposal id) shares the same weakness and needs a nonce/ID-based dedup instead of pure content hash, since `AssetIssueActuator`'s name-uniqueness check (`assetIssueStore.get(name)`) has a similar theoretical front-run/squat risk when `AllowSameTokenName == 0`.
- No production code fix is being proposed here since `CREATE2`'s deterministic-address front-running is an inherent, spec-defined behavior of the opcode (matching Ethereum semantics) rather than an implementation bug; the analog is presented for awareness given the reported bug class.

### Proof of Concept
1. Attacker monitors the P2P network / mempool for a pending transaction invoking a `Factory.deploy(bytes code, uint256 salt)`-style method (as in `Create2Test.testCreate2`) with visible `code` and `salt` parameters, and the caller (factory) address.
2. Attacker computes `expectedContract = generateContractAddress2(factoryAddress, salt, code)` exactly as done in the codebase's own test: [5](#0-4) 
3. Attacker crafts and broadcasts (with a higher energy/fee bid) a transaction that also triggers `create2` from the same factory-equivalent context with the same `salt`/`code` hash (or via any means causing the same target address to be populated) so it lands in a block before the victim's transaction.
4. When the victim's transaction executes, `createContractImpl` finds `existingAccount != null` and `contractAlreadyExists == true`, causing the create to fail with `Trying to create a contract with existing contract address: ...`, permanently blocking the intended deployment for that salt: [6](#0-5)
