### Title
Case-Sensitive Ethereum Address in `abstract_public_key` Causes Account Derivation / Authentication Mismatch, Permanently Locking User Funds — (`File: aptos-move/framework/aptos-framework/sources/account/common_account_abstractions/ethereum_derivable_account.move`)

---

### Summary

The Aptos Ethereum Derivable Account Abstraction (DAA) stores the Ethereum address as a raw UTF-8 byte vector inside `SIWEAbstractPublicKey.ethereum_address`. The Aptos account address is derived by hashing those raw bytes (case-sensitive), but the authentication check decodes the address using `base16_utf8_to_vec_u8`, which accepts both uppercase and lowercase hex characters (case-insensitive). This split creates the same root cause as the Mars Red Bank bug: the key used to identify the account (the hash of the raw address string) is case-sensitive, while the credential check is case-insensitive. A user who registers with one case representation (e.g., EIP-55 mixed-case from MetaMask) and later submits a transaction with a different case representation (e.g., all-lowercase from another tool) authenticates successfully but against a **different, empty Aptos account**, permanently locking their APT and fungible assets in the original account.

---

### Finding Description

**Step 1 — Account address derivation is case-sensitive.**

`derive_account_address` in `account_abstraction.move` hashes the raw BCS bytes of the `abstract_public_key` vector:

```move
public fun derive_account_address(derivable_func_info: FunctionInfo, abstract_public_key: &vector<u8>): address {
    let bytes = bcs::to_bytes(&derivable_func_info);
    bytes.append(bcs::to_bytes(abstract_public_key));
    bytes.push_back(DERIVABLE_ABSTRACTION_DERIVED_SCHEME);
    from_bcs::to_address(hash::sha3_256(bytes))
}
``` [1](#0-0) 

For the Ethereum DAA, `abstract_public_key` is a BCS-serialized `SIWEAbstractPublicKey` whose `ethereum_address` field is a `vector<u8>` of raw UTF-8 bytes. Because SHA3-256 is applied to the raw bytes, `"0xC7B576Ead6aFb962E2DEcB35814FB29723AEC98a"` and `"0xc7b576ead6afb962e2decb35814fb29723aec98a"` produce **different** Aptos account addresses.

**Step 2 — The authentication check is case-insensitive.**

Inside `authenticate_auth_data`, the stored `ethereum_address` string is decoded to raw bytes via `base16_utf8_to_vec_u8` and compared against the cryptographically recovered Ethereum address:

```move
let ethereum_address_without_prefix = abstract_public_key.ethereum_address.slice(2, ...);
let account_address_vec = base16_utf8_to_vec_u8(ethereum_address_without_prefix);
assert!(recovered_addr == account_address_vec, EADDR_MISMATCH);
``` [2](#0-1) 

`base16_utf8_to_vec_u8` (via `hex_char_to_u8`) explicitly handles both uppercase `A–F` (ASCII 65–70) and lowercase `a–f` (ASCII 97–102):

```move
} else if (c >= 65 && c <= 70) { // 'A' to 'F'
    c - 55
} else if (c >= 97 && c <= 102) { // 'a' to 'f'
    c - 87
``` [3](#0-2) 

So `"C7B576..."` and `"c7b576..."` both decode to the same 20 bytes and both pass the assertion.

**Step 3 — The VM enforces that the transaction sender matches the derived address.**

Before dispatching the authentication hook, the VM asserts:

```move
assert!(master_signer_addr == derive_account_address(func_info, signing_data.derivable_abstract_public_key()), ...);
``` [4](#0-3) 

This means the transaction's sender address is **always** the address derived from the `abstract_public_key` in the authenticator. If the user submits with a different case variant, the transaction targets a different Aptos account.

**Step 4 — The mismatch.**

| Step | Operation | Case sensitivity |
|---|---|---|
| Account registration | `derive_account_address(sha3_256(BCS(ethereum_address_bytes)))` | **Case-sensitive** |
| Authentication check | `base16_utf8_to_vec_u8(ethereum_address_without_prefix)` | **Case-insensitive** |

A user who registers with `"0xC7B576Ead6aFb962E2DEcB35814FB29723AEC98a"` (EIP-55 mixed-case, as MetaMask produces) gets Aptos account **X**. If they later submit a transaction with `"0xc7b576ead6afb962e2decb35814fb29723aec98a"` (all-lowercase, as many other tools normalize), the derived address is **Y ≠ X**. The authentication for Y succeeds (the Ethereum signature is valid), but the user's APT and fungible assets remain locked in X, which they can no longer reach unless they reproduce the exact original byte sequence.

---

### Impact Explanation

- **Permanent freezing of user-controlled on-chain assets (APT, fungible assets):** A user who funded their Ethereum-derived Aptos account and then submits subsequent transactions with a different case representation of their Ethereum address will authenticate against a different, empty account. Their original account's assets become permanently inaccessible unless the user can reproduce the exact original byte sequence — which is not guaranteed across different wallets and tools (MetaMask uses EIP-55 mixed-case; many SDKs and block explorers normalize to all-lowercase).
- **Unprivileged trigger:** Any user of the Ethereum DAA feature can trigger this by simply submitting a transaction with a different case variant of their own Ethereum address. No special privileges are required.
- **Scope:** Directly matches "permanent freezing of user-controlled on-chain assets" in the Aptos bounty scope.

---

### Likelihood Explanation

- Ethereum addresses are commonly represented in multiple case formats: EIP-55 mixed-case (MetaMask, ethers.js), all-lowercase (many APIs, block explorers, some SDKs), all-uppercase (rare but valid hex). A user who registers via one tool and transacts via another is likely to encounter this mismatch.
- The `SIWEAbstractPublicKey.ethereum_address` field is a raw `vector<u8>` with no normalization enforced at any layer — neither at deserialization, nor at account derivation, nor at authentication.
- The existing test in the repository uses the mixed-case EIP-55 address `b"0xC7B576Ead6aFb962E2DEcB35814FB29723AEC98a"`, confirming that real-world mixed-case input is expected and accepted. [5](#0-4) 

---

### Recommendation

Normalize the `ethereum_address` to a canonical form (all-lowercase, without `0x` prefix, or as raw 20 bytes) **before** it is included in the `abstract_public_key` that feeds `derive_account_address`. The normalization must happen at the same layer for both account derivation and authentication. The simplest fix is to store the Ethereum address as raw 20 bytes (`vector<u8>` of length 20) in `SIWEAbstractPublicKey` rather than as a UTF-8 hex string, eliminating the case ambiguity entirely. Alternatively, enforce lowercase normalization in `deserialize_abstract_public_key` before the struct is used in any downstream computation.

### Proof of Concept

**Setup:** Ethereum private key `K` with address `0xC7B576Ead6aFb962E2DEcB35814FB29723AEC98a` (EIP-55 mixed-case).

**Step 1 — Register account with mixed-case address (as MetaMask would):**
```
abstract_public_key_A = BCS({
    ethereum_address: b"0xC7B576Ead6aFb962E2DEcB35814FB29723AEC98a",
    domain: b"aptos.com"
})
aptos_account_X = derive_account_address(ethereum_derivable_account::authenticate, abstract_public_key_A)
```
Fund `aptos_account_X` with 100 APT.

**Step 2 — Submit a transfer transaction using all-lowercase address (as a different tool would):**
```
abstract_public_key_B = BCS({
    ethereum_address: b"0xc7b576ead6afb962e2decb35814fb29723aec98a",  // all lowercase
    domain: b"aptos.com"
})
aptos_account_Y = derive_account_address(ethereum_derivable_account::authenticate, abstract_public_key_B)
// aptos_account_Y != aptos_account_X
```

**Step 3 — Authentication outcome:**
- The SIWE message is constructed with `"0xc7b576ead6afb962e2decb35814fb29723aec98a"` embedded.
- The user signs this message with key `K`.
- `recover_public_key` recovers the correct public key for `K`.
- `base16_utf8_to_vec_u8("c7b576ead6afb962e2decb35814fb29723aec98a")` → 20 bytes `[0xC7, 0xB5, 0x76, ...]`
- `recovered_addr` → same 20 bytes.
- `assert!(recovered_addr == account_address_vec)` **passes**.
- Transaction executes against `aptos_account_Y` (empty account).
- `aptos_account_X` retains 100 APT, permanently inaccessible to the user via the lowercase path.

**Verification of case-insensitivity in `base16_utf8_to_vec_u8`:**
```
hex_char_to_u8('C') = 'C' - 55 = 67 - 55 = 12  // uppercase branch
hex_char_to_u8('c') = 'c' - 87 = 99 - 87 = 12  // lowercase branch
// Both produce 12 — identical output
``` [6](#0-5) [7](#0-6) [1](#0-0)
