### Title
Deleted-and-recreated account inherits stale postponed-receipt actions (AddKeyAction takeover) - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account()` in `core/store/src/utils/mod.rs` clears `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for a deleted account, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries associated with that account name. [1](#0-0)  If a receipt was postponed for account `A` awaiting a withheld `Data` receipt, deleting `A` and later recreating an account with the same name allows the stale postponed receipt to be delivered and executed against the new account occupant once the attacker finally supplies the matching data.

### Finding Description
`process_action_receipt` parks an `ActionReceipt` that has unresolved `input_data_ids` by writing `PostponedReceipt{receiver_id, receipt_id}`, `PostponedReceiptId{receiver_id, data_id}`, and `PendingDataCount{receiver_id, receipt_id}` into the trie, keyed purely by `receiver_id` (an `AccountId` string) and hashes — not by any generation/creation-epoch identifier tied to the specific account instance. [2](#0-1) 

`remove_account()` is the single cleanup routine invoked by `action_delete_account`, and it only iterates/removes `Account`, `ContractCode`, access keys / gas-key nonces, and `ContractData`. [1](#0-0)  It contains no logic that scans or removes `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` prefixes for the deleted `account_id`.

Because postponed-receipt state is addressed only by the textual `receiver_id`, once account `A` is deleted and a new account is created under the identical name `A` (permissionless for top-level names >32 chars via `CreateAccountOnlyByRegistrar`/`action_create_account`, or via subaccount re-creation by the same parent), the stale `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries silently persist and now logically "belong" to the new account. When the attacker finally delivers the withheld `Data` receipt with the matching `data_id`, the runtime's postponed-receipt resolution path (in `runtime/runtime/src/lib.rs`) finds the pending count has reached zero, promotes the postponed `ActionReceipt` to ready, and executes its actions (`AddKeyAction{full_access}`) against the account currently occupying the `A` slot in the trie — the brand-new account — not the one that originally created the receipt.

The actions inside that stale receipt were authorized only via the promise-creation-time check that `predecessor_id == receiver_id` (a self-call trust rule used for privileged self actions like `AddKeyAction`/`DeployContractAction`), not via any check that the account occupying `receiver_id` at *execution* time is the same account that existed when the receipt was queued. This violates authorization exactness: the promise carries privileges (full-access key installation) that its actual creator held over the account they controlled, but which the new occupant of the name never granted.

### Impact Explanation
This is an authorization-escalation / account-takeover bug: an attacker can cause a full-access key they control to be installed on an account they no longer own (and that a different, unrelated party may have just created and funded), matching NEAR's "authorization escalation across accounts or promises" bounty category. Concretely, whoever creates the new `A` can have their account seized by the original attacker's stale key, letting the attacker drain funds/transfer control without ever having current authority over the account.

### Likelihood Explanation
Preconditions are attacker-controlled and require no privileged access: the attacker only needs to (1) own account `A`, (2) issue a self-directed `FunctionCall` promise with an `AddKeyAction` and an artificially withheld dependent `Data` receipt (e.g., a cross-contract call the attacker never lets resolve, or delays via a helper contract under attacker control), (3) submit `DeleteAccountAction` on `A`, and (4) wait for/arrange recreation of an account with the same name (permissionless for >32-char top-level names, or trivial for subaccounts under an attacker-controlled parent — in which case the attacker could target their own recreated subaccount, or wait for a naive third party to claim the freed name). Because the code path (`remove_account`) unconditionally skips postponed-receipt cleanup regardless of network conditions, this is deterministic and repeatable, not probabilistic. The main variable affecting real-world impact is whether a third party actually recreates the exact same account name before the attacker delivers the data receipt (fully attacker-controllable if targeting a subaccount they own).

### Recommendation
In `core/store/src/utils/mod.rs::remove_account`, additionally scan and remove all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie entries prefixed by `account_id` before returning. Since postponed receipts can also have receipts already stored under `Receipt`/`ReceivedData` for the same account, either: (a) refund/discard the postponed action receipts (returning any attached deposit to a designated beneficiary or burning it, consistent with how other pending obligations are handled on deletion), or (b) block `DeleteAccountAction` entirely for accounts that still have pending `PostponedReceipt`/`PendingDataCount` entries, forcing the account owner to resolve or explicitly cancel pending promises before deletion is allowed.

### Proof of Concept
Runtime integration test (test-loop or `runtime/runtime/src/tests/apply.rs`-style):
1. Deploy a contract on account `A` that, on receiving a `FunctionCall`, issues a cross-contract call to helper `H` and, in the callback triggered by `H`'s response (`.then`), executes `AddKeyAction{full_access}` on itself (`predecessor_id == receiver_id == A`).
2. Have `H`'s contract never actually respond (or simulate by controlling test-loop scheduling to never deliver `H`'s `Data` receipt), leaving `A`'s callback receipt postponed; assert via state inspection that `TrieKey::PostponedReceipt{A, receipt_id}` and `TrieKey::PendingDataCount{A, receipt_id}` exist.
3. Submit `DeleteAccountAction` on `A` with `beneficiary_id = attacker2`; assert `A`'s `Account`/`AccessKey` entries are gone but the `PostponedReceipt`/`PendingDataCount` entries for `A` still exist in the trie.
4. Create a new account named `A` (e.g. a >32-character top-level name, or same-named subaccount under the same parent) with an independent access key belonging to a different party.
5. Manually deliver the previously withheld `Data` receipt with the matching `data_id` to receiver `A`.
6. Assert that the new `A`'s access-key set now contains the attacker's `AddKeyAction` full-access public key — confirming unauthorized key injection into an account the attacker does not currently control.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
