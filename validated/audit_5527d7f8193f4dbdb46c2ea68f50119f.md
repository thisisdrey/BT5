### Title
Lack of slippage/minimum-shares protection in `lending_account_withdraw` (and `juplend_withdraw`) exposes users to burning more shares than expected when `asset_share_value` worsens between submission and execution - (File: `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`)

### Summary
`lending_account_withdraw` and the integration-specific withdraw handlers (e.g. `juplend_withdraw`) accept only a fixed underlying `amount` to withdraw, with no user-supplied bound on the number of shares that may be burned to satisfy that amount. Exactly like the referenced Sherlock finding on Pool.sol/SuperPool, the shares-to-burn are computed from the *current* exchange rate (`asset_share_value` in marginfi, `token_exchange_price` in JupLend) at execution time, not the rate the user observed when they signed the transaction.

### Finding Description
`lending_account_withdraw` converts a fixed `amount_pre_fee` of underlying tokens into shares via `bank_account.withdraw(I80F48::from_num(amount_pre_fee))` [1](#0-0) , which calls `decrease_balance_internal`, converting the requested asset amount to shares using the bank's *current* `asset_share_value`: `bank.get_asset_shares(asset_amount_decrease)` [2](#0-1) , where `get_asset_shares` is `value / asset_share_value` [3](#0-2) .

`asset_share_value` is not monotonic: it is reduced by `socialize_loss` during `lending_pool_handle_bankruptcy`, which subtracts the bad debt from total asset value and redistributes it across the remaining shares, lowering `asset_share_value` for every depositor in that bank [4](#0-3) . `lending_pool_handle_bankruptcy` explicitly documents this "socializes the loss to all remaining depositors," and can even zero out `asset_share_value` in a super-bankruptcy, killing the bank [5](#0-4) , and is corroborated by the `lending_pool_handle_bankruptcy` instruction implementation [6](#0-5) .

If a user submits a withdraw for a fixed `amount` while, in the same slot window, a `lending_pool_handle_bankruptcy` (permissionless when `PERMISSIONLESS_BAD_DEBT_SETTLEMENT_FLAG` is set) or an admin bankruptcy call lands first and lowers `asset_share_value`, the withdraw instruction still delivers exactly `amount` of underlying tokens, but burns *more* of the user's shares than they would have burned under the pre-bankruptcy rate — exactly mirroring the Pool.sol/SuperPool root cause (fixed-assets-in, variable-shares-burned, no bound on shares consumed). There is no `withdraw` parameter analogous to a "max shares burned" or "min amount out" guard in `LendingAccountWithdraw` [7](#0-6) .

The same pattern exists in the JupLend integration: `juplend_withdraw` computes `shares_to_burn` from the *current* `token_exchange_price` fetched via `cpi_update_rate()` at the start of the instruction, and burns that many marginfi shares for the exact requested `amount` [8](#0-7) ; if the exchange rate worsens (e.g., due to intervening deposit/withdraw activity or rate updates) before this transaction lands, more marginfi shares are consumed for the same underlying amount than the user expected when signing.

### Impact Explanation
The user always receives the exact `amount` they requested in the withdraw instruction; the impact is limited to remaining shares/position value being lower than the user anticipated when they signed the transaction — i.e., they part with more of their claim on the bank/pool than intended for the same tokens received. This can only occur in the narrow window around a `lending_pool_handle_bankruptcy` call (or, in JupLend, exchange-rate movement between rate refresh and confirmation), and per the project's own documentation, bankruptcy is rare and "has never been executed in the main pool" [9](#0-8) . There is no attacker-controlled theft vector here — any value the user "loses" is exactly the socialized loss that every remaining depositor in the bank bears; the withdrawing user simply locks in that loss at execution time rather than at submission time. This matches the "Medium, acknowledged" characterization of the original Sherlock finding rather than a High-severity theft/insolvency bug.

### Likelihood Explanation
Low. Exploiting this requires a withdraw transaction to be in flight (already signed/broadcast) at the exact moment a bankruptcy-handling transaction executes and reduces `asset_share_value` for the same bank, or (for JupLend) an exchange-rate shift between the CPI rate refresh and confirmation. Bankruptcy handling is rare by design and typically administered deliberately, making unintentional races infrequent, and there is no way for an attacker to profit from a victim's shares being burned (the "lost" value is redistributed pool-wide, not captured by any single party).

### Recommendation
Add an optional slippage-protection parameter to `lending_account_withdraw` (and the integration-specific withdraw instructions such as `juplend_withdraw`), e.g. a `max_shares_burned` (or equivalent minimum-shares-remaining) bound, and revert the instruction if the shares actually required to fulfill `amount` at execution-time exceed that bound. This lets a user cap the effective exchange rate they accept, consistent with slippage guards used elsewhere in the codebase (e.g., order execution's `max_slippage` checks) [10](#0-9) .

### Proof of Concept
1. Depositor A holds shares in `usdc_bank` with `asset_share_value = V0`.
2. Depositor A submits `lending_account_withdraw(amount = 1000)`, expecting to burn `1000 / V0` shares.
3. Before A's transaction lands, a permissionless (or admin) `lending_pool_handle_bankruptcy` call executes against a bankrupt borrower on the same bank, invoking `socialize_loss`, which reduces `asset_share_value` to `V1 < V0` [11](#0-10) .
4. A's withdraw transaction now executes: `bank_account.withdraw(1000)` computes shares burned as `1000 / V1 > 1000 / V0` [2](#0-1) .
5. A receives exactly 1000 USDC as requested, but has burned more shares than anticipated, leaving fewer shares (less future claim on the bank) than expected at signing time — with no parameter available to cap or reject this at instruction level.

```rust
    /// Socialize a loss of `loss_amount` among depositors, the `total_deposit_shares` stays the
    /// same, but total value of deposits is reduced by `loss_amount`;
    ///
    /// In cases where assets < liabilities, the asset share value will be set to zero, but cannot
    /// go negative. Effectively, depositors forfeit their entire deposit AND all earned interest in
    /// this case.
    fn socialize_loss(&mut self, loss_amount: I80F48) -> MarginfiResult<bool> {
        let mut kill_bank = false;
        let total_asset_shares: I80F48 = self.total_asset_shares.into();
        let old_asset_share_value: I80F48 = self.asset_share_value.into();

        // Compute total "old" value of shares
        let total_value: I80F48 = total_asset_shares
            .checked_mul(old_asset_share_value)
            .ok_or_else(math_error!())?;

        // Subtract loss, clamping at zero (i.e. assets < liabilities, the bank is wiped out)
        if total_value <= loss_amount {
            self.asset_share_value = I80F48::ZERO.into();
            // This state is irrecoverable, the bank is dead.
            kill_bank = true;
        } else {
            // otherwise subtract then redistribute
            let new_share_value: I80F48 = (total_value - loss_amount)
                .checked_div(total_asset_shares)
                .ok_or_else(math_error!())?;
            self.asset_share_value = new_share_value.into();
            // Sanity check: should be unreachable.
            if new_share_value == I80F48::ZERO {
                kill_bank = true;
            }
        }

        Ok(kill_bank)
    }
```

```markdown
Next, the group administrator runs `handle_bankruptcy` on the user. For banks where
`PERMISSIONLESS_BAD_DEBT_SETTLEMENT_FLAG` is enabled, anyone can do this. This will perform the
following logic:

* If bank's insurance fund > liabilities, then the insurance fund is used to repay the user's liability.
* If the bank's insurance fund is not sufficient, the remainder will be covered by taking liquidity
  out of the bank, reducing the asset share value. This socializes the loss to all remaining
  depositors.
* If the bank's insurance fund and liquidity are not sufficient (super-bankruptcy), the bank is
  killed. The asset share value is set to zero, wiping out all holdings for all other depositors.
  This state is irrecoverable, and the bank is permanently disabled.
```
