## Analysis

The reported bug class is a **check/update ordering flaw around a monotonic counter used for replay/session-state protection**, where an increment (or, in this codebase's analog, a "mark-as-seen" update) is decoupled from the corresponding check, allowing the guard to be bypassed when the same operation runs concurrently. In Nebula the closest reachable analog is the anti-replay window in `ConnectionState.Decrypt` / `ConnectionState.VerifyRelay`, where `Bits.Check` (a pure read) and `Bits.Update` (the actual mark-as-seen write) are split across a lock release, with decryption happening in between.

### Title
Anti-replay window check/update race allows replayed data-plane packets to be double-accepted - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection using a "check, then decrypt, then update" pattern, but the mutex protecting the replay window (`decryptLock`) is released between the `Check` call and the `Update` call. `Bits.Check` only *peeks* at whether a counter has been seen and does not mark it; only `Bits.Update` marks the slot. Because packet processing in Nebula runs across multiple concurrent reader goroutines (`f.routines`, each running `listenOut`/`readOutsidePackets`), two copies of the same captured ciphertext packet delivered to different reader routines at roughly the same time can both pass `Check` before either has called `Update`, since neither has updated the window state yet. ### Finding Description
`Decrypt` locks `decryptLock`, calls `window.Check(l, messageCounter)`, unlocks, performs the (potentially slow) `DecryptDanger` AEAD operation, then re-locks and calls `window.Update(l, messageCounter)`. [1](#0-0) 

`Bits.Check` never mutates state — it only inspects whether the bit for `i` is already set: [2](#0-1) 

The write that actually marks a counter as "seen" only happens in `Bits.Update`/`updateSlow`. Because the lock is dropped for the duration of the decrypt operation, two threads processing the same replayed packet (same `messageCounter`) can both execute `Check` and get `true` before either calls `Update`. `VerifyRelay` (used for relay-forwarded frames) follows the identical check-decrypt-update pattern and has the same gap. [5](#0-4) 

This is directly reachable by a network attacker with no valid certificate: they only need to capture one legitimate ciphertext packet off the wire and re-inject it twice in quick succession. Nebula's UDP receive path runs `f.routines` independent goroutines, each with its own `readOutsidePackets` call chain, so the two injected copies of the replayed packet can genuinely be processed concurrently on different OS threads. [3](#0-2) [4](#0-3) 

This is the direct analog of the reported bug class: a state-changing operation (`++key.callIndex` / marking a counter consumed) that is supposed to gate re-entry is decoupled from the check that guards it, so a loop (there: `_bidFindingIteration`; here: concurrent packet-reader goroutines) can observe the pre-update state twice and process the same input twice.

### Impact Explanation
A successful race lets an attacker force Nebula to decrypt and accept the same encrypted payload/relay frame more than once. For plaintext tunnel packets, this manifests as duplicate delivery of application data to the tun device (traffic replay), and for `VerifyRelay`, a relay node can be tricked into re-forwarding a captured relay frame — undermining the anti-replay guarantee that is a core security property of the AEAD/nonce-based transport. This matches the "traffic decryption/forgery/replay" impact category since replay protection, one of Nebula's fundamental security controls against wire-level attackers, can be defeated under packet duplication/racing.

### Likelihood Explanation
Exploitation requires no valid certificate or trusted peer status — only the ability to capture one legitimate ciphertext packet and re-send it (a passive on-path or off-path duplication capability). The race window depends on `DecryptDanger`'s execution time and the multi-routine reader architecture (`routines > 1`), so success is probabilistic rather than deterministic, and single-routine deployments (`routines == 1`) are not affected since there's no true concurrency. This keeps the likelihood at a similar "Medium" tier as the reported analog — real, reachable by an unauthenticated network attacker, but timing-dependent.

### Recommendation
Hold `decryptLock` across the entire `Check` → `Decrypt` → `Update` sequence, or restructure `Bits` to provide a single atomic "check-and-reserve" operation (e.g., a `CheckAndMark` that marks the slot as provisionally consumed before decryption and rolls it back only on decryption failure) so no other goroutine can observe the pre-update state for the same counter while decryption is in flight.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes with `listen.routines` (or the compiled-in multi-reader path) configured with more than one reader routine.
2. Capture one legitimate outbound data-plane UDP packet (or relay frame) from the wire.
3. Simultaneously replay two copies of the exact same captured packet from the attacker's vantage point toward the target, timed so that the OS/UDP layer's multiple listener sockets/goroutines pick them up at nearly the same time (this is naturally the case when `SO_REUSEPORT`-style multi-reader sockets are used).
4. Because `Bits.Check` in [2](#0-1)  never marks the counter and `decryptLock` is released before `DecryptDanger` runs in [1](#0-0) , both goroutines can pass `Check` and both successfully decrypt/deliver (or, for relays, re-forward) the same message counter — observable as duplicate packets on the receiving tun device or duplicate forwarded relay frames, contrary to the intended single-delivery replay-protection guarantee documented by the existing `TestRelayReplayProtection` test's stated invariant.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
