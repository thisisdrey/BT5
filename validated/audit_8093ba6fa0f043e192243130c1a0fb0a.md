### Title
Broadcast transaction-ID cache is populated before validation and never cleaned up on failure, enabling denial-of-service against specific transactions - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.broadcastTransaction` inserts the transaction ID into `dbManager.getTransactionIdCache()` *before* the transaction has passed signature/contract/tapos/expiration validation. If any subsequent validation step throws (`ValidateSignatureException`, `ContractValidateException`, `ContractExeException`, `AccountResourceInsufficientException`, `TaposException`, `TooBigTransactionException`, `TransactionExpirationException`, or any generic `Exception`), the ID is never removed from the cache. This is the same bug class as the Zebra advisory: a dedup/sent cache is populated pre-validation and is never cleaned up on the failure path, so a later legitimate submission with the same identity is treated as a duplicate and rejected.

### Finding Description
In `Wallet.broadcastTransaction`, the transaction ID (`txID`) is computed from the transaction and immediately cached: [1](#0-0) 

Only afterwards does the method call `dbManager.pushTransaction(trx)`, which performs the real validation chain (`validateTapos`, `validateCommon`, `validateDup`, signature validation, contract execution): [2](#0-1) [3](#0-2) 

If `pushTransaction` throws any of the declared exceptions, `broadcastTransaction`'s catch blocks build an error `Return` and simply return — none of them evict the entry from `transactionIdCache`: [4](#0-3) 

The cache itself is a Guava cache with a 1-hour expiry and 100,000-entry capacity, defined in `Manager`: [5](#0-4) 

Critically, the transaction ID is computed as `Sha256Hash` of the raw transaction data only, independent of the signature list — this is explicit elsewhere in `Wallet` (`getTransactionApprovedList` computes `txid` the same way, from `rawData` alone): [6](#0-5) 

Because the ID is signature-independent, an attacker (or the legitimate sender retrying) can submit two different transaction "bodies" (e.g. same `rawData` with a corrupted/invalid signature, or a variant of `rawData` deliberately crafted to fail a validation step such as `TaposException`/`TooBigTransactionException`/`AccountResourceInsufficientException`) that share the same transaction ID as a later, valid version of that transaction. The first submission poisons `transactionIdCache` at line 564 before validation completes; when the correctly-signed/valid transaction with the same ID is subsequently broadcast, the dup check at lines 558-562 rejects it with `DUP_TRANSACTION_ERROR`, even though it never entered `pendingTransactions` or the chain.

### Impact Explanation
Any unauthenticated API caller reaching `broadcastTransaction` (exposed over gRPC and the `/wallet/broadcasttransaction` HTTP endpoint) can pre-poison the ID cache for a transaction whose `rawData` they can predict or observe (e.g. deterministic contract calls, previously-seen but not-yet-confirmed transactions, or their own transaction they intend to retry). Once poisoned, the legitimate transaction with that exact ID is rejected as a duplicate for up to one hour (cache TTL), causing denial-of-service against a specific transfer, vote, freeze/unfreeze, or contract call — this can be used to grief targeted withdrawals or time-sensitive operations, and an attacker can repeat the poisoning indefinitely by resubmitting right after expiry. This is a reachable-by-anonymous-API-client bug, matching CWE-460 (Incomplete Cleanup) and CWE-471 (Modification of Assumed-Immutable Data through signature-independent tx identity), analogous in mechanism to the Zebra advisory though scoped to the broadcast API's local dedup cache rather than consensus state.

### Likelihood Explanation
The precondition is knowledge of a target transaction's `rawData` before it is confirmed. This is achievable in several realistic scenarios: an application resubmits its own transaction after a transient failure (self-inflicted DoS), or an attacker observes an about-to-be-broadcast transaction (e.g., via a compromised or observed client, mempool visibility from other broadcast APIs, or by constructing a transaction with fully predictable fields, such as exchange sweep/withdraw transactions with fixed parameters). No special privileges, signing keys, or SR/witness status are required — only the ability to call the public broadcast API — so likelihood is moderate to high for an attacker who can win the "observe rawData, then front-run with a garbage-signed copy" race, which is comparable in spirit to the propagation race described in the analogous Zebra report.

### Recommendation
Remove the transaction ID from `dbManager.getTransactionIdCache()` on every failure path in `Wallet.broadcastTransaction` (i.e., in each `catch` block between lines 585-629), or move the cache insertion to occur only after `pushTransaction` succeeds. Alternatively, bind the cached identity to a value that reflects full transaction validity (not just `rawData` hash) so that malleated/invalid bodies cannot collide with a legitimate transaction's ID in the dedup cache.

### Proof of Concept
1. Construct transaction `T` with `rawData` `R` (e.g., a transfer with fixed owner/to/amount/timestamp fields that the attacker can predict).
2. Attacker submits `T'` = `R` signed with an invalid/garbage signature via `broadcastTransaction`. The ID `txID = hash(R)` is inserted into `transactionIdCache` at `Wallet.java:564` before signature validation runs.
3. `pushTransaction` throws `ValidateSignatureException` in `Manager.pushTransaction` (`Manager.java:905-909`); `broadcastTransaction`'s catch block at `Wallet.java:585-589` returns `SIGERROR` without evicting `txID` from the cache.
4. The legitimate sender broadcasts the correctly-signed transaction with identical `rawData` `R` (same `txID`).
5. `Wallet.broadcastTransaction` line 559 finds `txID` present in `transactionIdCache` and returns `DUP_TRANSACTION_ERROR`, even though the transaction never reached `pendingTransactions` or the chain — for up to 1 hour (cache expiry), or indefinitely if the attacker repeats step 2 before expiry.
