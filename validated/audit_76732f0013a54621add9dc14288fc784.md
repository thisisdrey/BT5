This is a confirmed, already-documented bug in the codebase (tracked as GitHub issue #12606), reachable by an ordinary unprivileged account via a promise DAG. I have enough evidence to answer.

### Title
Receipt size validated before `output_data_receivers` rewiring allows persisting/forwarding receipts above `max_receipt_size` - ([File: runtime/runtime/src/lib.rs])

### Summary
`validate_receipt` enforces `ReceiptSizeExceeded` only for `ValidateReceiptMode::NewReceipt`, and this check runs inside the per-action loop of `apply_action_receipt` immediately after each action produces `new_result.new_receipts` [1](#0-0) , using the size check in `validate_receipt` [2](#0-1) . After the action loop finishes, the runtime unconditionally appends `action_receipt.output_data_receivers()` onto an already-created new receipt (selected via `ReturnData::ReceiptIndex`) without re-checking size [3](#0-2) . This lets a receipt that was exactly at `max_receipt_size` when validated grow past the limit afterward.

### Finding Description
An unprivileged account deploys a contract and calls a method that builds a promise DAG using `promise_batch_create`/`promise_batch_then`/`promise_return`: an intermediate promise `A` creates receipt `C` sized to exactly `max_receipt_size` and calls `promise_return`, redirecting `A`'s outer `output_data_receivers` (from `A then B`) onto `C`. `validate_receipt` was already run on `C` when it was produced as a `new_receipt` of action `A` (`ValidateReceiptMode::NewReceipt`, `lib.rs:914-925`), passing because `C` was exactly at the limit. Later in the same `apply_action_receipt` call, since `result.result` is `Ok(ReturnData::ReceiptIndex(receipt_index))` (the `promise_return` case), the code extends `output_data_receivers` on the receipt at `receipt_index` in `result.new_receipts` [3](#0-2) , growing `C` beyond `max_receipt_size`. No second `validate_receipt` call occurs on this mutated receipt before it is assigned a `receipt_id` and handed to `receipt_sink.forward_or_buffer_receipt` [4](#0-3) . The `value_return` variant of the same bug (large `value_return` bytes turned into a `DataReceipt` and merged) is analogous.

This is a known, already-tracked issue in the codebase: the test file explicitly documents it as a bug with a link to the upstream issue [5](#0-4) , and a workaround already exists in `ReceiptSink::try_forward`, which clamps the *counted* size to `max_receipt_size` for admission-limit bookkeeping specifically to prevent forwarding from getting stuck, citing the same issue [6](#0-5) .

### Impact Explanation
An oversized receipt (still containing its true, larger byte count) is durably stored/forwarded even though the admission-control bookkeeping treats it as clamped to `max_receipt_size`. This matches the scoped impact described: aggregate `ChunkStateWitness`/`source_receipt_proofs` bytes computed from true receipt sizes can exceed the witness size budget, degrading chunk-validator endorsement and shard availability — a shard-halting/availability class of impact rather than fund theft. It is not a fund-theft or consensus-divergence bug on its own; the clamp in `try_forward` mitigates receipt forwarding from stalling indefinitely, but the true persisted/forwarded receipt bytes remain above `max_receipt_size`.

### Likelihood Explanation
Reachable by any funded account without special privileges: deploy an arbitrary wasm contract, call a method using `promise_batch_create`+`promise_batch_then`+`promise_return` (or a large `value_return`) to construct the DAG, sized precisely so the intermediate receipt sits exactly at `max_receipt_size` before the `output_data_receivers`/return-data merge. This is a deterministic, repeatable construction — the exact scenario already reproduced in `test_max_receipt_size_promise_return`/`test_max_receipt_size_value_return`, which explicitly assert the oversized-receipt condition occurs [7](#0-6) . Cost to the attacker is the gas/storage of one contract deployment and a couple of calls.

### Recommendation
Re-run `validate_receipt` (or at least the size check) on any `new_receipts` entry after `output_data_receivers` is appended (`lib.rs:1098-1136`) and after the `value_return`-derived `DataReceipt`s are constructed, rejecting the action with `ReceiptSizeExceeded`/`NewReceiptValidationError` if the post-mutation size exceeds `max_receipt_size`, mirroring the existing check at `lib.rs:914-925`.

### Proof of Concept
Reuse `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs`. After `assert_oversized_receipt_occurred`, additionally fetch the persisted/forwarded receipt (e.g., from `DBCol::OutgoingReceipts` or the receipt captured via `ReceiptFilter`) and assert `borsh::object_length(&receipt).unwrap() > max_receipt_size`, proving the receipt was never re-validated after the `output_data_receivers`/`value_return` mutation.

// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
