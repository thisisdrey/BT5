The closest analog in this Go repository is `crypto/rc4`'s `XORKeyStream` at [1](#0-0) , which already defends against out-of-bounds access: it explicitly bounds-checks with `_ = dst[len(src)-1]` (panicking if `dst` is shorter than `src`) and rejects invalid overlapping buffers via `alias.InexactOverlap`. This exact behavior — panicking rather than performing a silent out-of-bounds read/write when `dst` is too short — is deliberately tested in [2](#0-1)  (`TestRC4OutOfBoundsWrite`), confirming it's documented, defended, and intentional contract behavior rather than an unguarded memory-safety bug.

The iText CVE concerns a PDF-parsing-time decryption routine (`ARCFOUREncryption.encryptARCFOUR`) processing attacker-crafted length/offset fields from an untrusted PDF file — a parser-level bug class. Go's `crypto/rc4` has no PDF/file-format parsing layer feeding attacker-controlled lengths into array indices; callers (e.g., TLS's `cipherRC4` at [3](#0-2) ) always supply correctly-sized buffers from the TLS record layer, not arbitrary attacker-supplied indices into the RC4 state array. There is no reachable Go stdlib production path where untrusted input drives an out-of-bounds read analogous to the iText finding.

```go
func (c *Cipher) XORKeyStream(dst, src []byte) {
	if len(src) == 0 {
		return
	}
	if alias.InexactOverlap(dst[:len(src)], src) {
		panic("crypto/rc4: invalid buffer overlap")
	}
	i, j := c.i, c.j
	_ = dst[len(src)-1]
	dst = dst[:len(src)] // eliminate bounds check from loop
	for k, v := range src {
		i += 1
		x := c.s[i]
		j += uint8(x)
		y := c.s[j]
		c.s[i], c.s[j] = y, x
		dst[k] = v ^ uint8(c.s[uint8(x+y)])
	}
	c.i, c.j = i, j
}
```
