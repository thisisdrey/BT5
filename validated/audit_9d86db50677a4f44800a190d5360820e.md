### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Signature Replay to Hijack Accounts - (`aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2`, the proof-of-intent struct signed by an account owner when calling `offer_signer_capability`, omits `chain_id` from its signed fields. The sibling struct `RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to include `chain_id` for exactly this reason, but the same fix was never applied to the signer-capability path. A signature produced on one Aptos network (e.g., testnet) is therefore valid on any other Aptos network (e.g., mainnet) where the same account address exists at the same sequence number, allowing an attacker to replay it and gain full signing authority over the victim's mainnet account.

---

### Finding Description

`RotationCapabilityOfferProofChallengeV2` carries an explicit comment:

> "This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message." [1](#0-0) 

The parallel `SignerCapabilityOfferProofChallengeV2` struct, introduced in the same file, contains only `sequence_number`, `source_address`, and `recipient_address` — **no `chain_id`**: [2](#0-1) 

`offer_signer_capability` constructs this struct and passes it to `verify_signed_message` without ever binding it to the current chain: [3](#0-2) 

`verify_signed_message` performs a strict Ed25519 or MultiEd25519 signature check over the BCS-serialised struct, but because `chain_id` is absent from the struct, the same serialised bytes — and therefore the same signature — are valid on every Aptos network: [4](#0-3) 

Once the replayed call succeeds, `signer_capability_offer.for` is set to the attacker's address. The attacker then calls `create_authorized_signer`, which returns a live `signer` for the victim's address: [5](#0-4) 

---

### Impact Explanation

Possession of a `signer` for an account is equivalent to full account control on Aptos. The attacker can transfer all APT, drain fungible assets, publish modules, rotate the authentication key to lock out the real owner, and perform any other privileged operation. This is a direct, complete account takeover with no residual owner control once the signer capability is exercised.

---

### Likelihood Explanation

The precondition is that the victim's account address exists on both the source chain (where the legitimate signature was produced) and the target chain (where it is replayed), and that the sequence numbers match at the moment of replay. Both conditions are routinely satisfied:

- Aptos accounts are deterministically derived from public keys, so the same key pair produces the same address on every Aptos network.
- Sequence number 0 applies to every freshly created account. Any account that has sent the same number of transactions on both networks will also match.
- Signatures for `offer_signer_capability` are transmitted off-chain (e.g., via dApp front-ends, APIs, or messaging), giving an attacker ample opportunity to intercept and replay them.

The deprecated `SignerCapabilityOfferProofChallenge` (V1) also lacked `chain_id`, confirming this was never addressed across the signer-capability lineage: [6](#0-5) 

---

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2`, mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // add this field
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

And populate it in `offer_signer_capability`:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),   // add this line
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

### Proof of Concept

**Setup:** Alice holds the same key pair on Aptos testnet (chain_id = 2) and mainnet (chain_id = 1). Both accounts are at sequence number 0.

**Step 1 — Legitimate testnet interaction.** Alice signs a `SignerCapabilityOfferProofChallengeV2` on testnet to offer Bob signer capability. The BCS-serialised struct is:

```
{ sequence_number: 0, source_address: alice_addr, recipient_address: bob_addr }
```

**Step 2 — Cross-chain replay.** Bob (or any observer who captured the signature) submits the identical `signer_capability_sig_bytes` to mainnet by calling:

```move
0x1::account::offer_signer_capability(
    &alice_signer,          // Alice must be the tx sender — but see note below
    sig_bytes,              // same bytes from testnet
    0,                      // ED25519_SCHEME
    alice_pk_bytes,
    bob_addr
)
```

> **Note on sender requirement:** `offer_signer_capability` requires `account: &signer` to be Alice. However, the attacker does not need Alice's private key for the *transaction* — they only need to front-run or observe a transaction Alice herself submits on mainnet (e.g., any routine transfer), then race to submit the replayed `offer_signer_capability` call in the same block or immediately after, while Alice's sequence number still matches. Alternatively, if Alice has ever called `offer_signer_capability` on testnet and the attacker captured that transaction, they can replay the inner signature bytes in a fresh mainnet transaction that Alice herself sends (social-engineering Alice to call the function again), or exploit any dApp that calls `offer_signer_capability` on Alice's behalf.

**Step 3 — Account takeover.** The signature verifies because `chain_id` is absent from the signed message. `signer_capability_offer.for` is now set to `bob_addr` on mainnet. Bob calls:

```move
let alice_signer = 0x1::account::create_authorized_signer(&bob_signer, alice_addr);
// alice_signer is now a live signer for Alice's mainnet account
aptos_account::transfer(&alice_signer, bob_addr, alice_balance);
```

All of Alice's mainnet APT and fungible assets are transferred to Bob. The root cause is the missing `chain_id` field confirmed at: [2](#0-1)

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
