### Title
Transactions drained during fast-leader-handover wait are silently discarded on the happy ParentReady path, letting bank state diverge from broadcast PoH entries - ([File: core/src/block_creation_loop.rs])

### Summary
In `record_and_complete_block`, when `optimistic_parent` is `Some` and the block timeout is reached before `ParentReady` arrives, `shutdown_and_drain_record_receiver` is invoked to stop and drain in-flight records into `accumulated_txs`, so recording of these transactions into PoH is deferred rather than dropped [1](#0-0) . If `ParentReady` subsequently arrives and matches the optimistic parent (the "happy path" in `handle_parent_ready`), the function returns `Ok(None)` immediately without doing anything with the `accumulated_txs` it was handed, silently dropping them instead of recording or rescheduling them [2](#0-1) .

### Finding Description
The record channel carries batches (`bank_id`, `mixin`, `transactions`) that banking stage has already produced/committed against the working bank; the normal path calls `ctx.poh_recorder.write().unwrap().record(...)` to hash them into PoH [3](#0-2) . When `block_time_left` reaches zero while `optimistic_parent.is_some()` (fast leader handover still waiting on `ParentReady`), the code stops recording and instead drains the channel into `accumulated_txs`, explicitly to avoid an unbounded/OOM block while still preserving the transactions for the sad-handover reschedule path [4](#0-3) .

When `ParentReady` is later received for the same `bank_slot`, `process_parent_ready` takes `optimistic_parent` and the accumulated transactions and calls `handle_parent_ready` [5](#0-4) . Inside `handle_parent_ready`, if `leader_window_info.parent_block == optimistic_parent_block` (i.e. the optimistic parent was correct), the function takes the early "happy path" return `Ok(None)` and drops the `accumulated_txs` argument on the floor — it is never recorded via `poh_recorder.record()`, and it is never re-injected to the banking stage (that re-injection only happens further down in the sad-handover branch) [6](#0-5) . Because `handle_parent_ready` returned `None`, `process_parent_ready` does not reset `records_shutdown`, so the record intake for this bank stays permanently shut down for the remainder of block production [7](#0-6) . The outer loop then observes `optimistic_parent` is now `None` with `block_time_left` still zero and proceeds directly to the happy-path block-completion branch, which produces the footer and calls `tick_alpenglow` on the same (uncleared) bank [8](#0-7) [9](#0-8) .

Unlike the sad-handover branch, which explicitly clears the entire bank via `bank_forks_controller.clear_bank()` / `poh_recorder.clear_bank(true)` and re-injects `accumulated_txs` as fresh packets before continuing [10](#0-9) , the happy path keeps the same bank and thus keeps whatever state those drained transactions already produced in the bank, while never recording matching entries for them in the block's PoH stream. The subsequently computed `bank_hash` (via `bank.hash()` at freeze time) reflects the bank's actual state, but honest replaying nodes reconstructing the block purely from broadcast PoH entries will never see or execute those transactions, since no `record()` call for them was ever made and they were never rescheduled.

### Impact Explanation
This produces an invalid recorded block: the leader's own committed bank state is inconsistent with what it broadcasts as PoH entries for that slot, i.e. a QoS/consensus-safety-relevant "invalid recorded block" bug matching the "Invalid Recorded Block / consensus violation" bounty category. Any node reproducing the block strictly from its entries (as consensus mandates) computes a different result than the leader's local bank state, undermining the PoH-entry consistency invariant.

### Likelihood Explanation
This requires the leader to be running fast leader handover (`optimistic_parent.is_some()`, i.e. the leader started producing before receiving `ParentReady`) and for `ParentReady` to arrive after the block timeout has already triggered the FLH-wait drain, and for that `ParentReady` to match the optimistic parent (the "happy" resolution). An unprivileged attacker cannot force fast-leader-handover mode or force `ParentReady` timing, but can increase the odds of hitting this internal race by flooding the TPU with transactions right at the predictable leader-window boundary (derivable from the public leader schedule) so that in-flight records exist precisely when the FLH-wait drain fires. This is a timing-dependent race rather than a deterministically attacker-triggered bug, and its exact reachability depends on internals (votor `ParentReady` delivery timing) outside the attacker's direct control, so likelihood is moderate/opportunistic rather than guaranteed on demand.

### Recommendation
In the happy-path branch of `handle_parent_ready` (where `leader_window_info.parent_block == optimistic_parent_block`), either re-record `accumulated_txs` into PoH via `poh_recorder.record()` for the still-valid bank, or reset `records_shutdown` and re-inject the accumulated transactions back to the banking stage exactly as done in the sad-handover branch, so no transaction batch that was drained during the FLH-wait is ever silently discarded regardless of which ParentReady outcome occurs.

### Proof of Concept
Integration test plan (`core/src/block_creation_loop.rs` test module or new test):
1. Construct a `LeaderContext` with `fast_leader_handover = true` and an `optimistic_parent` set for `start_slot`.
2. Feed several `record_receiver` messages containing transactions T1..Tn that have already been "committed" to the working bank (simulate via test bank harness).
3. Advance `block_timer` past `block_timeout` without sending `ParentReady`, forcing entry into the FLH-wait branch and invoking `shutdown_and_drain_record_receiver`, capturing T1..Tn into `accumulated_txs`.
4. Send a `ParentReady` (`LeaderWindowInfo`) whose `parent_block` equals the optimistic parent (happy path).
5. Assert (POH_ENTRY_CONSISTENCY): after `record_and_complete_block` returns, every transaction in `accumulated_txs` either appears in a `PohRecorder::record()`-produced entry for the slot, or has been re-sent to `ctx.banking_stage_sender`. The current implementation fails this assertion because `handle_parent_ready`'s happy-path `Ok(None)` return drops `accumulated_txs` without recording or rescheduling.

    // marker. Otherwise, we could end up sending records for the old bank after the UpdateParent,
    // which causes a divergence between the leader and replayers.
    shutdown_and_drain_record_receiver(
        &ctx.poh_recorder,
        &mut ctx.record_receiver,
        Some(&mut accumulated_txs),
    )?;
    send_update_parent(&ctx.poh_recorder, leader_window_info.parent_block)?;

    let slot = leader_window_info.start_slot;
    let old_parent_slot = optimistic_parent_block.slot;
    let Block {
        slot: new_parent_slot,
        block_id: new_parent_hash,
    } = leader_window_info.parent_block;

    let bank = ctx
        .poh_recorder
        .read()
        .unwrap()
        .bank()
        .ok_or(PohRecorderError::ResetBankError(
            old_parent_slot,
            new_parent_slot,
        ))?;
    bank.wait_for_inflight_commits();
    ctx.bank_forks_controller
        .clear_bank(slot)
        .map_err(|_| PohRecorderError::ResetBankError(old_parent_slot, new_parent_slot))?;
    ctx.poh_recorder.write().unwrap().clear_bank(true);

    // Create the new bank before re-injecting transactions to avoid racing.
    let new_bank = start_leader_wait_for_parent_replay(
        slot,
        new_parent_slot,
        Some(new_parent_hash),
        *block_timer,
        ctx,
    )
    .map_err(|_| PohRecorderError::ResetBankError(old_parent_slot, new_parent_slot))?;

    // Re-inject accumulated transactions back to banking stage for rescheduling
    let packets: Vec<BytesPacket> = accumulated_txs
        .into_iter()

            // at most 1 batch.
            .send(banking_packet_batch)
            .map_err(|_| PohRecorderError::RescheduleTransactionsError(slot))?;
