### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists via legacy `FreezeBalanceContract` delegation enables cheap, victim-targeted CPU-DoS during `UnfreezeBalanceContract` processing - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
When resource delegation is enabled but the "delegate optimization" hard fork is not active (`DynamicPropertiesStore.supportAllowDelegateOptimization() == false`), `FreezeBalanceActuator` maintains legacy per-account index lists (`toAccounts`/`fromAccounts`) inside `DelegatedResourceAccountIndexCapsule` with no size limit. An attacker can cheaply grow another account's `fromAccounts` list to an arbitrary size using many low-value delegated freeze transactions targeting the same receiver, then force expensive O(n) list-copy-and-remove operations against that inflated list to be executed as part of *the attacker's own* `UnfreezeBalanceContract` transaction — the same "stuff an unbounded array, then trigger unmetered iteration over it" pattern described in the reference report for `LockingPositionService`.

### Finding Description
In the legacy (non-optimized) delegation path, `FreezeBalanceActuator.delegateResource()` appends the receiver address to the owner's `toAccounts` list and the owner address to the receiver's `fromAccounts` list, with no cap on list size: [1](#0-0) 

The underlying capsule simply appends without any bound check: [2](#0-1) 

Validation of `FreezeBalanceContract` only requires the frozen amount to be ≥ 1 TRX and the receiver account to exist — there is no restriction on how many distinct delegator ("owner") accounts may delegate to the same receiver, nor any cap on the resulting `fromAccounts`/`toAccounts` list sizes: [3](#0-2) [4](#0-3) 

Later, when any one of the attacker-controlled "owner" accounts unfreezes its (tiny) delegated balance to that receiver, `UnfreezeBalanceActuator.execute()` reconstructs the *entire* `toAccounts`/`fromAccounts` list into a fresh `ArrayList` and performs a linear `remove()` scan over it — for both the owner's index and the (victim) receiver's index: [5](#0-4) 

Because this native actuator logic executes inside block/transaction processing and is not metered by TVM energy (only VM contract execution is energy-metered; native actuator CPU cost is unmetered aside from fixed bandwidth/fee), an attacker can:
1. Cheaply create/fund many "owner" accounts and delegate a minimal (1 TRX) balance from each to a single victim receiver address, inflating the victim's `fromAccounts` list to a very large size at very low cost (this does not require the victim's cooperation).
2. Trigger any single `UnfreezeBalanceContract` unfreeze from one of the attacker-controlled owner accounts, which forces an O(n) copy + scan of the victim's bloated `fromAccounts` list as a side effect of the attacker's own transaction.

This mirrors the report's bug class exactly: a permissionless action lets an attacker unboundedly grow a per-account array with no cap, and a later "legitimate" state-processing path (there, `balanceOfMgCvgAt`; here, `UnfreezeBalanceActuator.execute()`) performs unmetered iteration over the full array.

### Impact Explanation
Repeated exploitation increases per-transaction and per-block CPU cost for any operation that touches the bloated index (unfreezing by any of the sybil owners, or future migrations/`convert()` calls, which also iterate the entire `toAccounts`/`fromAccounts` lists): [6](#0-5) 
This raises the CPU work validators must perform to process ordinary transactions without a corresponding energy/fee charge, degrading block processing throughput and potentially delaying block production/propagation for the network — a resource-exhaustion condition on core account/state processing reachable purely through user-submitted `FreezeBalanceContract`/`UnfreezeBalanceContract` transactions.

### Likelihood Explanation
Exploitability depends on the legacy delegation path still being reachable, i.e., `supportAllowDelegateOptimization()` not yet enabled on the target network (this flag is a hard-fork toggle; older/private networks or networks mid-migration remain exposed). Where reachable, the cost to the attacker is only the sum of minimal 1-TRX freezes plus transaction fees, making the attack cheap and repeatable, and it requires no special privileges (any unprivileged account can freeze/delegate/unfreeze).

### Recommendation
- Cap the size of `toAccounts`/`fromAccounts` in `DelegatedResourceAccountIndexCapsule`, or migrate fully to the per-pair key-based scheme (`delegate`/`unDelegate`) used by the optimized path, removing the array-based index entirely.
- Avoid full list reconstruction (`new ArrayList<>(...)` + `remove()`) in `UnfreezeBalanceActuator`/`UnDelegateResourceActuator` for legacy indices; use structures with O(1) membership removal (e.g., a set/map keyed by counterpart address) if the legacy path must remain supported.
- Meter or bound the CPU cost of native actuator logic that scales with attacker-controlled per-account collections.

### Proof of Concept
1. On a network where `supportAllowDelegateOptimization()` is disabled and `supportDR()` (delegate resource) is enabled, select a victim receiver address `V`.
2. Create `N` funded "owner" accounts `O_1..O_N`; from each, submit `FreezeBalanceContract` with `frozen_balance = 1 TRX`, `resource = BANDWIDTH`, `receiver_address = V`. Each call appends `V` to `O_i.toAccounts` and appends `O_i` to `V.fromAccounts` (`FreezeBalanceActuator.delegateResource`, lines 328–345).
3. Repeat for a large `N` (bounded only by attacker's willingness to pay ~N TRX + fees), inflating `V`'s `fromAccounts` list to size `N`.
4. From any `O_i`, submit `UnfreezeBalanceContract` for the same receiver `V`; this triggers `UnfreezeBalanceActuator.execute()`'s cleanup branch, which copies and linearly scans/removes from both `O_i`'s `toAccounts` and `V`'s `fromAccounts` (lines 162–188) — the latter being an O(N) operation embedded in the attacker's low-cost transaction, executed for every such unfreeze the attacker chooses to submit.

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
