### Title
Group-level rate limiter can be bypassed by splitting a large outflow into multiple smaller borrows/withdraws within the same transaction - ([File: programs/marginfi/src/utils/general.rs])

### Summary
The group-level (USD, cross-bank) rate limiter is intentionally read-only during user instructions to avoid making the `MarginfiGroup` account writable on every transaction. Settlement of the counter only happens later, out-of-band, via an admin-submitted batch (`update_group_rate_limiter`). Because the check performed inside `record_withdrawal_outflow` only *reads* `group.rate_limiter` and never mutates it, any number of `lending_account_borrow` / `lending_account_withdraw` (and the Kamino/Drift/Solend/JupLend withdraw equivalents) instructions packed into a single atomic transaction (or issued before the off-chain admin reconciles the previous batch) will each independently evaluate against the *same* unmutated "remaining capacity" baseline, exactly the same "evaluate each action in isolation" flaw described in the external report for `maxBetShare`.

### Finding Description
`record_withdrawal_outflow` performs the group-level check like this: [1](#0-0) 

The comparison uses `group.rate_limiter.hourly/daily.effective_remaining_capacity(...)`, a pure read of the currently-loaded `MarginfiGroup` account, which per the admin guide is explicitly **not** updated inline by user instructions: [2](#0-1) 

This is confirmed by the test suite itself, which asserts the group counter is unchanged immediately after a user borrow and only updates once the admin calls `update_group_rate_limiter`: [3](#0-2) 

Because `group` is loaded once per instruction and never persisted with the new outflow, if a user includes several borrow/withdraw instructions inside one transaction (or fires several transactions faster than the ~10-minute admin settlement cadence described in the guide), every single instruction reads the same "remaining capacity" value and each individually passes the `value.to_num::<i64>() > remaining` check, even though the summed USD outflow across all of them can vastly exceed the configured `groupHourly`/`groupDaily` cap. Only the bank-level limiter (which is inline/mutable) is updated synchronously — the group-level protection, which is meant to bound *aggregate* cross-bank USD outflow (the actual mitigation this control is designed to enforce, per `configure_group_rate_limits`), gives no real aggregate protection within an attacker-controlled batch of instructions.

This is structurally identical to the reported `maxBetShare`/`LargeBet` issue: a limit meant to bound cumulative exposure is implemented as a per-call check against a value that isn't updated between calls, so splitting a large flow into several smaller ones defeats the intended cap.

### Impact Explanation
Medium: the group rate limiter is a defense-in-depth control against large abrupt USD outflows across a group (e.g., in case of oracle manipulation, exploited config, or a compromised risk workflow — mirroring the purpose of `total_asset_value_init_limit`/deleverage caps). By packing multiple borrow/withdraw instructions into a single transaction, a user can extract multiples of the configured hourly/daily USD cap in one shot, defeating the invariant the feature exists to enforce and giving operators a false sense of the protocol's exposure limits during an incident window.

### Likelihood Explanation
Medium: no special privileges are required — any account holder with sufficient collateral/liquidity can trivially construct a single transaction with N borrow/withdraw instructions against different banks (each below the per-instance projected capacity) to bypass the aggregate group cap. There's limited attacker incentive absent an active incident (oracle manipulation, risk-workflow compromise) where this control is supposed to act as the safety net, which is exactly when bypassing it matters most.

### Recommendation
Track and enforce the group-level outflow accumulation intra-transaction as well, not just via the deferred off-chain settlement. Options: (a) make the group account writable/mutated in the same instruction (accepting the serialization cost the design intentionally avoided), (b) enforce a hard per-transaction/per-instruction ceiling independent of the rolling window so a single transaction cannot exceed the window's cap regardless of how it's split, or (c) maintain an intra-transaction running total (e.g., via a transient/ephemeral account or instruction-introspection of prior instructions in the same transaction) that is added to the "remaining capacity" baseline before each check, so sequential instructions in the same transaction cannot all read the identical stale capacity.

### Proof of Concept
1. Admin sets `groupHourly = 10` (USD) and a high bank-level limit so only the group limiter is the binding constraint, as in the existing test setup: [4](#0-3) 
2. Instead of issuing one `borrowUsdc(usdcNative(8))` (which the existing tests show correctly fails when it alone exceeds capacity), the user instead builds a single transaction containing multiple smaller borrow instructions (e.g., four separate `lending_account_borrow` instructions of `usdcNative(3)` each, potentially against different banks/oracles to stay under any single-instruction check) totaling far more than 10 USD.
3. Because `group.rate_limiter` is only loaded read-only and is identical for every instruction within that transaction (no instruction mutates/persists the group account), each of the four borrow instructions independently computes `effective_remaining_capacity` against the same starting value and each passes the `> remaining` check individually, even though their sum (12 USD) exceeds the configured 10 USD hourly cap.
4. The transaction succeeds atomically, and only after the fact does an off-chain worker emit/aggregate `RateLimitFlowEvent`s and call `update_group_rate_limiter` — by which time the outflow has already happened, so the cap was never actually enforced for this batch.

```markdown
### 2. User transaction path

During a withdraw or borrow:

- The bank rate limiter is updated immediately on the writable bank account.
- The group rate limiter is only checked read-only.
- The protocol converts the flow to USD using the instruction price/oracle path.
- If the projected group hourly or daily capacity is exceeded, the user instruction fails.
- A `RateLimitFlowEvent` is emitted for off-chain aggregation.

Important details:

- Flashloans, liquidations, and deleverages skip the normal rate-limit accounting path.
- `RateLimitFlowEvent` is an indexing aid, not a source of truth. Solana log truncation can drop
  events, so the off-chain worker must reconcile gaps instead of assuming no event means no flow.
```

```typescript
  it("(user 2) group rate limiter is read-only during user instructions", async () => {
    // Configure group hourly limit
    await setRateLimits({
      bankHourly: usdcNative(1_000),
      bankDaily: new BN(0),
      groupHourly: new BN(100),
      groupDaily: new BN(0),
    });

    const groupBefore = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    const outflowBefore =
      groupBefore.rateLimiter.hourly.curWindowOutflow.toNumber();

    // Borrow 5 USDC - this should succeed (within limit) but NOT update group state
    await borrowUsdc(usdcNative(5));

    const groupAfterBorrow = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    // Group rate limiter should NOT have changed (it's read-only during user instructions)
    assertBNEqual(
      groupAfterBorrow.rateLimiter.hourly.curWindowOutflow,
      outflowBefore,
    );

    // Repay 5 USDC - group state should also remain unchanged
    await repayUsdc(usdcNative(5));

    const groupAfterRepay = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    assertBNEqual(
      groupAfterRepay.rateLimiter.hourly.curWindowOutflow,
      outflowBefore,
    );
  });
```
