### Title
Committee-controlled feature flags can permanently pause withdrawal of already-released funds (`WithdrawExpireUnfreezeActuator` / `CancelAllUnfreezeV2Actuator`) - (File: actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java)

### Summary
The Sherlock report flags a centralization anti-pattern: gating *outbound* (withdraw/redeem) functions behind a pausable/committee-controlled switch, which lets a privileged party lock user funds that are already due. In java-tron, `WithdrawExpireUnfreezeActuator.validate()` and `CancelAllUnfreezeV2Actuator` (and the analogous TVM-native processors) gate the ability to *withdraw already-unfrozen TRX* behind the on-chain committee flag `unfreezeDelayDays` / `supportUnfreezeDelay()`.

### Finding Description
When a user unfreezes stake via `UnfreezeBalanceV2Actuator`, the funds are not returned immediately — they are placed into an `UnFreezeV2` pending-withdraw entry with an `unfreezeExpireTime`, and only become claimable later via `WithdrawExpireUnfreezeContract`/`WithdrawExpireUnfreezeActuator` (or via TVM's `withdrawExpireUnfreeze()` opcode, `WithdrawExpireUnfreezeProcessor`) or `CancelAllUnfreezeV2Contract`.

Both the withdraw path and the cancel path require the feature flag to remain enabled: [1](#0-0) [2](#0-1) 

This flag (`unfreezeDelayDays`, exposed via `DynamicPropertiesStore.supportUnfreezeDelay()`) is set by TRON committee (super representatives) through the on-chain proposal mechanism (`ProposalService`, `ProposalType`), the same governance mechanism that turns on/off many other features: [3](#0-2) 

Just like the Sense `Divider.redeem`/`Divider.collect` case — where `whenNotPaused` blocked users from getting back funds they were already entitled to — here, once a user has called `unfreezeBalanceV2` and their funds have "matured" into the `unfrozenV2List` awaiting withdrawal, the only way to actually move that balance back into their spendable `balance` field is through `WithdrawExpireUnfreezeActuator`/`CancelAllUnfreezeV2Actuator`. If the committee (through a majority SR governance vote) sets `unfreezeDelayDays` back to `0` (disabling `supportUnfreezeDelay()`), both actuators immediately start rejecting transactions with "Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee" / "Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee", even though the *inbound* freeze/unfreeze operations (`FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`) that put those funds in the pending state are governed separately and are unaffected.

This is architecturally analogous to the reported bug class: an outbound-only, user-funds-recovery operation is blocked by the same on/off switch used to gate the whole feature, rather than only gating the *creation* of new pending withdrawals.

### Impact Explanation
If a super-majority of witnesses/committee members disables `unfreezeDelayDays` (e.g., via a rollback proposal, or during migration/incident response), any account that already has funds sitting in `unfrozenV2List` awaiting expiry becomes unable to claim that TRX balance — `WithdrawExpireUnfreezeActuator` and `CancelAllUnfreezeV2Actuator` both hard-fail validation. Because there is no way for a normal user to route around this actuator gate (the balance transition only happens inside these actuator's `execute()`), the TRX is effectively frozen indefinitely — a centralization-driven denial-of-withdrawal, matching the "funds get frozen" impact class.

### Likelihood Explanation
This requires a witness/committee-level proposal to disable `unfreezeDelayDays`, which is a privileged, quorum-gated action (not something an ordinary unprivileged account can trigger). It is therefore lower-likelihood than a fully permissionless bug, but it is a legitimate, reachable centralization vulnerability: normal governance operations (e.g., disabling a buggy feature) unintentionally strand user funds, and there is no code path exempting "release already-committed unfreeze" from the same flag that gates "create a new unfreeze".

### Recommendation
Separate the feature flags: keep `unfreezeDelayDays`/`supportUnfreezeDelay()` gating the creation of new delayed-unfreeze entries (`UnfreezeBalanceV2Actuator`, `FreezeBalanceV2Actuator`), but do not use the same flag to block `WithdrawExpireUnfreezeActuator`/`CancelAllUnfreezeV2Actuator` from releasing funds that are already pending. Once a user's unfreeze request has been accepted on-chain, withdrawing the matured balance should always remain possible regardless of subsequent committee decisions, mirroring the "remove `whenNotPaused` from outbound functions" recommendation in the original report.

### Proof of Concept
1. Committee enables `unfreezeDelayDays = N` (`supportUnfreezeDelay()` returns true).
2. User calls `UnfreezeBalanceV2Contract` to unfreeze TRX; funds are added to `unfrozenV2List` with an `unfreezeExpireTime`.
3. Time passes past `unfreezeExpireTime`, so the funds are eligible for withdrawal.
4. Before the user calls `WithdrawExpireUnfreezeContract`, the committee passes a proposal setting `unfreezeDelayDays = 0`.
5. User submits `WithdrawExpireUnfreezeContract` (or `CancelAllUnfreezeV2Contract`); `WithdrawExpireUnfreezeActuator.validate()` now throws `ContractValidateException("Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee")` per [1](#0-0) , and the user cannot retrieve the matured funds until/unless the committee re-enables the flag.
