### Title
Precision loss in old-algorithm voting reward calculation due to floating-point division before multiplication - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a witness's cycle reward by first dividing `userVote` by `totalVote` as a `double`, then multiplying by `totalReward`, instead of doing the multiplication first (or using integer/`BigInteger` arithmetic throughout). This mirrors the reported Kairos bug class: `estimatedValue = loan.lent.mul(ONE.div(loan.shareLent))` divides before multiplying, which loses precision when the numerator of the division is small relative to the denominator. [1](#0-0) 

### Finding Description
```java

  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
``` [2](#0-1) 

`voteRate` is computed as a `double` division of `userVote / totalVote` before being multiplied by `totalReward`. Because `double` only has ~15-17 significant decimal digits of precision, when `userVote` is small relative to `totalVote` (e.g. a small delegator among a witness with a huge vote total), the intermediate `voteRate` value is rounded to a tiny double with limited precision, and this rounding error is then amplified/propagated when multiplied by `totalReward`. This is the same root-cause pattern as the reported issue (`ONE.div(loan.shareLent)` computed first, then multiplied), which produces unfair/incorrect final amounts because division-before-multiplication discards precision that would otherwise be preserved by multiplying first and dividing last.

This routine is used by the "old reward algorithm" path (cycles before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`), invoked from `computeReward(beginCycle, endCycle, accountCapsule)` via `getOldReward(...)`, which is itself reachable from `MortgageService.withdrawReward()` and `MortgageService.queryReward()`. [3](#0-2)

### Impact Explanation
Reward accounting is a real-money computation (TRX allowance credited to the withdrawing account) that is later added to `accountCapsule`'s balance on withdrawal. Precision loss in `voteRate * totalReward` can cause per-voter rewards to be systematically under- or over-computed for the "old reward algorithm" cycles, resulting in unfair distribution of rewards between the account claiming its allowance and the remaining reward pool tracked in `DelegationStore`. This is a fund-accounting correctness issue reachable by any staker.

### Likelihood Explanation
Every account that voted for a super representative before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` and calls `WithdrawBalanceContract` (or the TVM-exposed reward query paths) exercises this exact code path with attacker-influenceable vote/reward ratios (e.g. very large `totalVote` vs. small `userVote`), so the flawed computation order is reachable on every legacy-cycle reward withdrawal, not merely a rare edge case.

### Recommendation
Perform the multiplication before the division (or use `BigInteger`/scaled fixed-point arithmetic consistent with the newer Vi-based reward path, which already correctly does `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)`), e.g. compute `reward += (double) userVote * totalReward / totalVote;` or better, migrate the old-algorithm computation to integer/BigInteger math analogous to `RewardViCalService`/`DelegationStore.accumulateWitnessVi`. [6](#0-5) 

### Proof of Concept
Given `userVote = 1`, `totalVote = 3` (non-terminating binary fraction) and `totalReward = 1_000_000_000_000L`:
- Correct order (multiply first): `1 * 1_000_000_000_000 / 3 = 333_333_333_333` (integer truncation, exact).
- Current order (divide first as double): `voteRate = (double)1/3 ≈ 0.3333333333333333`; `voteRate * 1_000_000_000_000 ≈ 333333333333.3` cast/accumulated as `long`, subject to double rounding error that compounds across many `reward +=` accumulations in the loop over multiple witnesses/cycles, producing a final `reward` value that can drift from the mathematically exact value expected by the reward-sharing formula.
