### Title
Unprivileged attacker can dust-fill a victim's per-account token lists to `MAX_TOKENS_PER_USER`, permanently blocking new collateral deposits and new synth issuance - (File: contracts/Pool.sol)

### Summary
CVE-2020-2779 is an availability/DoS bug class: an attacker causes a repeatable hang/crash of a service. The Metronome analog is a per-account liveness denial: `Pool` tracks each account's deposit tokens and debt tokens in `MappedEnumerableSet` lists capped by `MAX_TOKENS_PER_USER`. Any account can be force-added to these lists without consent, because `DepositToken._transfer`/`_mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 [1](#0-0) , and `deposit(amount_, onBehalfOf_)` lets anyone mint deposit tokens to an arbitrary `onBehalfOf_` address [2](#0-1) . Once the combined lists reach the cap, `onlyIfAdditionWillNotReachMaxTokens` reverts every subsequent add with `UserReachedMaxTokens` [3](#0-2) .

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` enforce a shared cap on `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_)` [4](#0-3) . The lists are populated as a side effect of token balance changes, not by an opt-in from the account owner:

- An attacker calls `DepositToken.transfer(victim, 1)` (or `deposit(1, victim)`) for each distinct deposit token in the pool. Each 1-wei transfer sets `balanceOf[victim] > 0`, triggering `pool.addToDepositTokensOfAccount(victim)` [5](#0-4) .
- After `MAX_TOKENS_PER_USER` distinct entries (attacker supplies the dust for deposit tokens; the victim's own existing debt/deposit tokens fill the rest), any further `add` reverts.

Consequences for the victim:

- `DepositToken._mint` to the victim for any *new* collateral type reverts inside `pool.addToDepositTokensOfAccount`, so `deposit()`/`transfer()` of a new token type to the victim always fails — the victim can never top up their position with a different collateral.
- `DebtToken.issue`/`mint` (which calls `addToDebtTokensOfAccount` when the balance goes from 0 to positive) reverts for any synth the victim does not already hold, so the victim cannot open new debt positions.
- Dust received cannot be easily removed from the victim's list by the attacker, and the victim cannot remove entries without zeroing balances — but zeroing is blocked if the position's `unlockedBalanceOf` is less than the balance (locked collateral cannot be transferred out) [6](#0-5) .

The transaction simply reverts every time — the on-chain equivalent of the CVE's "repeatable crash."

### Impact Explanation
This is a targeted, unprivileged availability attack. If the victim's combined lists are at the cap, they cannot deposit additional collateral of any new type. If their position approaches the liquidation threshold, they are unable to add a different collateral to restore health, so the position is force-liquidated — a direct, attacker-induced loss of the liquidation fee/penalty. Additionally, victims holding SmartFarming positions whose unwind paths require minting or receiving a token type not already in their lists are temporarily frozen until they fully unwind an existing token entry. Invariant broken: liveness/exit-and-top-up for a specific account.

### Likelihood Explanation
- Fully unprivileged: any EOA can call `DepositToken.transfer`/`deposit(amount, onBehalfOf)` to push entries into the victim's lists; no governor, keeper, or privileged role is involved.
- Cost: the attacker must acquire 1 wei of each distinct deposit token (plus rely on the victim's own existing entries). Deposit tokens are freely transferable, so dust can be bought/transferred cheaply; the number of listed collateral/debt tokens is small and fixed by governance.
- No modifier stops it: `transfer` only checks `_revertIfLocked(sender_)` on the *sender*, not the recipient [6](#0-5) ; `deposit` only requires `whenNotPaused` and an existing deposit token [7](#0-6) .
- Requires `MAX_TOKENS_PER_USER` to be reachable with the deployed token count — the constant's exact value should be confirmed against `Pool.sol`; if it is much larger than the number of listed tokens, the attack is impractical and the finding degrades to informational.

### Recommendation
- Make per-account list entries opt-in, or only add to `depositTokensOfAccount` on `deposit()`/`seize()` (protocol-initiated mints), not on user-initiated `transfer`/`transferFrom`.
- Alternatively, let an account "opt out" / purge tokens below a dust threshold, or let `addTo*TokensOfAccount` silently skip instead of reverting when the cap is reached (return early rather than `UserReachedMaxTokens`).
- Raise `MAX_TOKENS_PER_USER` well above `depositTokens.length() + debtTokens.length()` so dust-filling is economically infeasible.

### Proof of Concept
Hardhat test outline against `Pool` + a real `DepositToken`:

```typescript
it('dust-fills victim lists and blocks new collateral deposits', async () => {
  // attacker deposits dust of every listed deposit token and transfers 1 wei to victim
  for (const dt of allDepositTokens) {
    await underlying(dt).approve(dt.address, 1)
    await dt.connect(attacker).deposit(1, attacker.address)   // or mint via own deposit
    await dt.connect(attacker).transfer(victim.address, 1)    // adds dt to victim list
  }
  // victim already holds k debt tokens; attacker pushes until:
  // debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == MAX_TOKENS_PER_USER

  // victim tries to deposit a collateral type not already in their list
  await expect(
    newDepositToken.connect(victim).deposit(parseEther('100'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // victim tries to issue a synth not already in their list
  await expect(
    newDebtToken.connect(victim).issue(parseEther('1'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Note: I could not verify the numeric value of `MAX_TOKENS_PER_USER` or the exact `DebtToken` mint→`addToDebtTokensOfAccount` call site within the available search budget; both should be confirmed in `contracts/Pool.sol` and `contracts/DebtToken.sol` before finalizing the PoC.
