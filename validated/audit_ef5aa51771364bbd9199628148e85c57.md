### Title
Premature StackerDB inventory acknowledgement before chunk is durably stored - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches and sends back a `StackerDBChunksInv` reply that advertises a newly-pushed chunk's slot version as already held, before the chunk itself is actually persisted. The chunk is only queued for storage via the return value `(false, true)`, which tells the relayer to process it later (and possibly durably store it via `Relayer::process_stacker_db_chunks`). This is the same "effects before/without settled interaction" ordering problem flagged in the external report (accounting/external-visible state updated ahead of the operation it is supposed to reflect), applied here to inventory advertisement vs. actual chunk storage rather than balance accounting vs. token transfer.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk` [1](#0-0) , when a pushed chunk validates against `validate_received_chunk` (signature, version freshness, size), the code immediately patches the reply's `slot_versions[chunk_data.chunk_data.slot_id]` to the new version and prepares to send that patched `StackerDBChunkInv` back to the sender [2](#0-1) . The function itself never calls `try_replace_chunk`/`insert_chunk`; actual durable storage is deferred to the relayer, which later calls `Relayer::process_stacker_db_chunks` -> `StackerDBTx::try_replace_chunk` [3](#0-2) , and only commits the SQLite transaction once per contract after iterating all chunks for that batch [4](#0-3) .

Because `validate_received_chunk`'s freshness check is only evaluated against the version snapshot known to the caller at that moment [5](#0-4) , two chunk pushes for the same slot arriving in close succession can both pass validation and both get an inventory reply that claims the pushed version is now held — yet only one of them will actually win the later `try_replace_chunk` call in `db.rs` (the loser gets `StaleChunk` and is silently dropped with `continue`, never stored, never re-broadcast) [6](#0-5) [7](#0-6) . The reply, however, has already gone out advertising that version as held, before storage was confirmed to have succeeded (or even attempted).

This breaks the equality "advertised inventory == actually stored chunk," the served-vs-committed analog called for by the mapping rules.

### Impact Explanation
A downstream peer relying on the advertised `StackerDBChunksInv` may believe this node holds a given slot version and schedule a fetch (`StackerDBGetChunkData`) for it, only to receive a NACK or stale/older data, since the win/loss between racing pushes is resolved later and asynchronously relative to when the inventory claim was sent. This is a non-canonical-state-served-as-canonical class issue (serving/advertising state that does not match what is durably committed), which can degrade StackerDB replication reliability and cause peers to misjudge freshness/availability of application data (e.g., signer message chunks) propagated over this channel.

### Likelihood Explanation
Reaching this requires only sending two (or more) validly-signed `StackerDBPushChunk` messages for the same slot in quick succession from an unprivileged remote peer — no special authentication beyond owning a slot signer key already permitted to write that slot, which is the normal expectation for any StackerDB writer. Because `send_p2p_message`/`add_relay_handle` happen synchronously in the unsolicited-message handler while actual storage happens later via the relayer loop, races are plausible under ordinary network conditions, not only adversarial timing.

### Recommendation
Do not patch or send the inventory acknowledgment claiming a version is held until after the chunk has been durably stored (i.e., only send the `StackerDBChunksInv` update once the corresponding `try_replace_chunk`/commit in the relayer path has actually succeeded), mirroring the checks-effects-interactions fix recommended in the source report: perform and confirm the internal state change (durable chunk write) before performing the externally observable action (advertising updated inventory).

### Proof of Concept
1. Attacker (or two independent legitimate writers racing) with a valid slot-signer key sends `StackerDBPushChunk` for slot `S` at version `V` to node `N` via two different open connections nearly simultaneously.
2. Both messages reach `handle_unsolicited_StackerDBPushChunk`; both pass `validate_received_chunk` because `make_StackerDBChunksInv_or_Nack` snapshots the versions before either write lands, and both replies are queued/sent claiming slot `S` is now at version `V` [8](#0-7) .
3. Both pushed chunks are forwarded to the relayer; `Relayer::process_stacker_db_chunks` processes them, and one call to `try_replace_chunk` succeeds while the second returns `StaleChunk` and is dropped without re-broadcast or correction of the earlier-sent inventory reply [9](#0-8) [10](#0-9) .
4. A third peer that received the (now-stale-mismatched) inventory acknowledgment for the losing push requests that specific chunk and receives a mismatch/NACK, confirming inventory sent did not reflect actually-committed state.
