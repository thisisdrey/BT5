### Title
Unstaked connection floods can exhaust the shared handshake-headroom slot pool, starving legitimate staked handshakes - (File: streamer/src/nonblocking/quic.rs, streamer/src/nonblocking/simple_qos.rs)

### Summary
`SimpleQos::max_concurrent_connections()` returns `max_staked_connections * 5 / 4`, describing the extra 25% as headroom purely for staked-handshake overhead, but the in-flight slot counter it bounds (`StreamerStats::open_connections`, enforced by `ClientConnectionTracker::new`) is peer-type-agnostic and is consumed by every incoming QUIC connection — staked or unstaked — before `SimpleQos` ever classifies the peer. An attacker with no stake can therefore occupy this shared headroom with unstaked handshake attempts and cause legitimate staked handshakes to be refused at the transport layer.

### Finding Description
In `streamer/src/nonblocking/quic.rs`, the accept loop creates a `ClientConnectionTracker` and checks it against `qos.max_concurrent_connections()` immediately after the per-IP and overall rate limiters pass, *before* the QUIC handshake (`connecting.accept()`/`Connecting` future) even completes: [1](#0-0) 

Only after this counter is incremented does `setup_connection` await the handshake (up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) and eventually call `qos.build_connection_context` / `qos.try_add_connection` to determine peer type: [2](#0-1) 

For `SimpleQos`, `try_add_connection` only ever admits `ConnectionPeerType::Staked` peers into `staked_connection_table`; unstaked peers are unconditionally rejected with `None` and there is no separate unstaked connection table or dedicated unstaked slot budget: [3](#0-2) 

Yet `max_concurrent_connections()` — the single global cap enforced by `ClientConnectionTracker` for *all* incoming connections regardless of eventual peer type — is sized only as 25% over `max_staked_connections`, with the comment stating this headroom exists "to allow for handshake" overhead of staked clients: [4](#0-3) 

Because the counter is incremented at initial accept and only decremented when the `ClientConnectionTracker` is dropped (i.e., after the handshake completes/times out and `try_add_connection` finishes and rejects unstaked traffic, or the handshake itself times out), an unstaked attacker can hold slots in this shared pool for the full handshake window. The only gates ahead of the shared counter are the per-IP `ConnectionRateLimiter` (`max_connections_per_ipaddr_per_min`, with a 10x burst allowance) and the global `overall_connection_rate_limiter` `TokenBucket` (`MAX_CONNECTION_BURST` / `TOTAL_CONNECTIONS_PER_SECOND`) — both are peer-type-agnostic and do not reserve any of that headroom for staked traffic: [5](#0-4) [6](#0-5) 

By spreading unstaked handshake attempts across enough source IPs to stay under per-IP limits, but timed to burst up to the global token-bucket capacity, an attacker can keep `open_connections` pinned at or above `max_concurrent_connections()` during the exact window a legitimate staked client is attempting its handshake. `ClientConnectionTracker::new` then rejects the staked handshake purely on the aggregate counter, before `SimpleQos::try_add_connection` (and its stake-aware pruning logic in `staked_connection_table`) is ever reached: [7](#0-6) 

This defeats the intent of the "staked headroom" comment: the 25% margin is not reserved for staked peers in any enforceable way — it is a shared, unpartitioned resource.

### Impact Explanation
Legitimate staked senders can be denied TPU access despite following all per-peer/per-IP QoS rules, because an unprivileged unstaked attacker can consume slots that are documented/intended as staked-only handshake headroom. This is a QoS/stake-prioritization evasion: the fundamental guarantee that staked connections get preferential admission over unstaked ones is bypassed at the pre-classification (transport) layer, which is squarely in scope as a "QoS evasion" finding affecting TPU availability for staked validators/RPC senders.

### Likelihood Explanation
Preconditions are minimal: no stake and only network access to the leader's public TPU QUIC endpoint are required. The attack is bounded by the per-IP rate limiter and the global `overall_connection_rate_limiter`, so a single-IP attacker cannot indefinitely sustain saturation, but bursts up to `MAX_CONNECTION_BURST` (and repeated across many source IPs, or with new connections replacing ones that finish the handshake-timeout window) are sufficient to intermittently starve concurrent staked handshakes, especially since the reserved headroom is only 25% of `max_staked_connections` — a small absolute number relative to burst capacity. Because the vulnerability requires no privileged control and is reproducible with concurrent unstaked handshakes generated by ordinary QUIC clients, it is feasible and repeatable, though its severity scales with how tightly `max_staked_connections`/`max_concurrent_connections` are configured relative to the rate limiters.

### Recommendation
Partition the in-flight handshake slot budget by intended peer class instead of using one global `open_connections` counter shared by all incoming (unclassified) connections. Options: (1) reserve a dedicated minimum slot count for staked-only headroom that unstaked in-flight handshakes cannot borrow from, only released after peer classification; (2) move admission-control accounting so the aggregate cap is consulted again (or a stricter unstaked-specific sub-cap is enforced) immediately after peer classification in `try_add_connection`, rather than relying solely on the pre-handshake global check in `ClientConnectionTracker::new`; or (3) apply a separate, tighter global in-flight cap specifically for connections that have not yet proven a staked pubkey, sized independently of `max_staked_connections`'s headroom.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/simple_qos.rs` or a new integration test alongside existing QUIC server tests):
1. Spin up a `SimpleQos`-backed QUIC server via `spawn_server` with a small `max_staked_connections` (e.g., 4), yielding `max_concurrent_connections() == 5`.
2. Concurrently launch `max_concurrent_connections()` unstaked client connections (no staked keypair / not present in `staked_nodes`) that intentionally stall mid-handshake (or simply race to occupy `open_connections` before completing), verifying via `stats.open_connections` that the counter reaches `max_concurrent_connections()`.
3. While those unstaked attempts are in flight, attempt a legitimate staked client connection (keypair present in `staked_nodes` with nonzero stake) and assert it is refused, observed via `stats.refused_connections_too_many_open_connections` incrementing and the staked connection attempt failing/timing out.
4. Assert failure: staked handshake success rate falls below the floor even though `staked_connection_table.total_size < max_staked_connections`, proving the invariant "unstaked traffic cannot consume capacity reserved for staked handshake overhead" is violated.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
