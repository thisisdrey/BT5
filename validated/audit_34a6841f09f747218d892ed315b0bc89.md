### Title
Same-shard bandwidth link is not exempted from congestion-based link blocking, causing intra-shard receipts to be starved of forwarding bandwidth - ([File: runtime/runtime/src/bandwidth_scheduler/scheduler.rs])

### Summary
`BandwidthScheduler::calculate_is_link_allowed` treats the self-link (`sender_index == receiver_index`) identically to any cross-shard link: if the shard's own status is `is_fully_congested` and the deterministic `allowed_sender_shard_index` for that height is not the shard itself, the function returns `false` for its own self-link. Since `try_grant_bandwidth` (scheduler.rs:467-471) refuses to grant any bandwidth on a link where `is_link_allowed` is `false`, the self-link can end up with `granted_bandwidth == 0` even though same-shard receipts are given `gas_limit = Gas::MAX` in `ReceiptSink::new` specifically because they are meant to bypass congestion backpressure.

### Finding Description
`calculate_is_link_allowed` (scheduler.rs:506-544) has three gates: unknown receiver status, `last_chunk_missing` on sender/receiver, and the "allowed shard" gate for fully congested receivers: [1](#0-0) 
None of these gates special-cases `sender_index == receiver_index`. If a shard congests itself (e.g., via mass transaction submission that fills its own outgoing buffers/receipts backlog and trips `is_fully_congested`), and the height's deterministically chosen `allowed_sender_shard_index` for that shard is a different shard, the shard's own self-link fails `calculate_is_link_allowed`, so `is_link_allowed` returns `false`: [2](#0-1) 
`try_grant_bandwidth` then refuses to grant any bandwidth on that self-link for the entire height: [3](#0-2) 
This directly contradicts the design intent encoded in congestion control, where the same-shard forward limit's gas is set to `Gas::MAX` because "the receipt takes the same memory if buffered or in the delayed receipts queue" — i.e., same-shard receipts are not supposed to be subject to congestion-based throttling the way cross-shard receipts are. Because the size admission check (`forward_limit.size >= size`) is independent of the gas admission check (`forward_limit.gas >= admission_gas`), an unlimited gas limit does not protect against a granted bandwidth (size) of zero.

### Impact Explanation
If confirmed end-to-end (i.e., if the size-based admission in the forward path for same-shard receipts truly derives `forward_limit.size` from `get_granted_bandwidth(shard, shard)`), the scoped impact is a liveness/funds-freezing bug: value-carrying same-account/same-shard receipts (e.g., a multi-step promise chain transferring NEAR within one account) would sit indefinitely in the outgoing buffer whenever the shard is self-congested and not its own "allowed sender," even though such receipts were explicitly designed to be exempt from bandwidth backpressure. This falls under the "permanent freezing of user funds" bounty category if the shard fails to become its own allowed sender for an extended period.

### Likelihood Explanation
Preconditions require an unprivileged attacker to congest their own shard (achievable by mass transaction submission, no special privileges) and for the deterministic `allowed_sender_shard_index` rotation to not select the shard itself for consecutive heights — both plausible and attacker-adjacent (the attacker doesn't control the allowed-shard selection but can time or sustain congestion to overlap unfavorable rotations). The freeze is not strictly "permanent" since `allowed_sender_shard_index` rotates and self-congestion may eventually clear, but it can cause extended, attacker-amplified stalls of same-shard receipts.

### Recommendation
Special-case `sender_index == receiver_index` in `calculate_is_link_allowed` to always return `true` (or otherwise bypass the "allowed shard" gate for self-links), consistent with the `Gas::MAX` exemption already applied to same-shard forwarding in `ReceiptSink::new`.

### Proof of Concept
Unit test in `scheduler.rs`'s test module: construct a `ShardIndexMap<ShardStatus>` where shard `S` has `is_fully_congested = true` and `allowed_sender_shard_index = Some(T)` with `T != S`. Run `BandwidthScheduler::calculate_is_link_allowed(S, S, &shards_status)` and assert it currently returns `false` (demonstrating the bug), then after the fix assert it returns `true`. Complement with an integration test running the full scheduler and asserting `get_granted_bandwidth(S, S)` is never `0` purely due to self-congestion, verifying same-shard receipts are never bandwidth-size-gated regardless of `allowed_sender_shard_index`.
