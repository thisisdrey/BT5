### Title
Consensus-critical multi-sig weight check (`checkWeight`) intentionally bypasses the stricter signature-length validation applied at P2P/RPC ingress - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`SignUtils.isValidLength()` was introduced as a strict, bounded signature-length check (`[PER_SIGN_LENGTH, MAX_PER_SIGN_LENGTH]`) and is explicitly wired into the P2P/relay/RPC transaction admission paths [1](#0-0) [2](#0-1) . However, the consensus-critical multi-signature weight-calculation routine, `TransactionCapsule.checkWeight`, was deliberately left using the old, unbounded `sig.size() < 65` check, per the doc comment in `SignUtils` itself: "Consensus paths (e.g. `TransactionCapsule.checkWeight`) intentionally keep the looser `size < 65` check ... do not call this helper from those paths" [1](#0-0) . This mirrors the CVE-2026-8328 pattern exactly: a fix (`makepasv`'s stricter validation) is applied to one entry point but a sibling function that consumes the same class of untrusted input (`ftpcp`/`checkWeight`) still uses raw, unvalidated data.

### Finding Description
`checkWeight(Permission permission, List<ByteString> sigs, byte[] hash, List<ByteString> approveList)` only rejects signatures with `sig.size() < 65`, with **no upper bound**, before calling `SignUtils.signatureToAddress(hash, base64, ...)` to recover the signer and grant permission weight [3](#0-2) . This function is reached from `validatePubSignature` → `validateSignature` on every broadcast transaction whose owner account has multi-sig permissions configured (`AccountPermissionUpdateContract`) [4](#0-3) , i.e. it is on the mandatory transaction-validation path for any account that has enabled multi-sig, invoked for every signed transaction that account submits.

In contrast, the same class of raw attacker-supplied byte arrays is length-bounded before being similarly parsed/consumed at the P2P ingress point (`TransactionsMsgHandler.check`) [2](#0-1) , and at other admission points referencing `isValidLength` in `Wallet.java` and `RelayService.java`. But a transaction that is submitted directly via RPC/HTTP `BroadcastTransaction` (bypassing gossip re-validation, or arriving locally) still reaches `checkWeight` with only the loose lower-bound check, since `pushTransaction`/`validateSignature` are the actual consensus gate, independent of the P2P `check()` pre-filter.

### Impact Explanation
Because `checkWeight` has no upper bound on signature length, arbitrarily large `ByteString` signature blobs (bounded only by overall transaction/message size limits elsewhere) are passed into `SignUtils.signatureToAddress` → `ECKey.signatureToAddress`/`SM2.signatureToAddress` for every signature in the list, once per weight-check invocation, and `checkWeight` is called again on every `addSign` call as well as on `validatePubSignature` [5](#0-4) . Because the loose check permits sizes well beyond the legitimate ECDSA/SM2 65-byte signature, this creates a discrepancy between what P2P ingress accepts (bounded) and what the consensus signature/permission-weight path accepts (unbounded), allowing an attacker who can get a transaction into the mempool through any path other than `TransactionsMsgHandler.check` (e.g., local RPC broadcast, or an already-connected trusted relay) to submit oversized signature buffers into consensus-critical signature-recovery code, an attack surface the P2P hardening specifically intended to close.

### Likelihood Explanation
Reaching `checkWeight` requires only that the transaction's owner account has multi-sig permissions enabled (`AllowMultiSign`) — a config any account holder can set via `AccountPermissionUpdateActuator` [6](#0-5)  — and then broadcast a transaction from that account with an oversized signature blob through any entry point that does not funnel through `TransactionsMsgHandler.check` (e.g. direct RPC/HTTP submission, self-authored transaction, or a peer connection that already passed the initial P2P check on a different message). This is attacker-controlled and requires only standard account setup, no privileged role.

### Recommendation
Apply `SignUtils.isValidLength()` (or an equivalent upper-bound check) inside `TransactionCapsule.checkWeight` before calling `signatureToAddress`, closing the same gap that `ftpcp()` left open relative to `makepasv()` in the CVE. If backward compatibility with historically-padded signatures is the reason for the looser check, add an explicit upper bound (e.g., `MAX_PER_SIGN_LENGTH`) rather than leaving the check fully unbounded, and ensure this same bound is enforced uniformly across every entry point that reaches `checkWeight`, not just P2P ingress.

### Proof of Concept
1. Create/control an account and enable multi-sign via `AccountPermissionUpdateContract`, setting an `Active` permission with at least one key.
2. Construct a transaction from that account and directly append a signature `ByteString` whose length is much larger than 65 bytes (e.g. several KB) via the raw protobuf `Transaction.signature` field (bypassing `TransactionCapsule.sign`/`addSign` helper methods that don't enforce an upper bound either).
3. Submit the transaction via an RPC/HTTP broadcast endpoint or via a P2P channel where `TransactionsMsgHandler.check`'s per-signature `isValidLength` gate can be bypassed (e.g., because the check happens on the message level, not necessarily re-run at every internal call site that invokes `pushTransaction`/`validateSignature` on already-verified/relayed transactions).
4. Observe that `TransactionCapsule.checkWeight` accepts the oversized signature (`sig.size() < 65` passes trivially) and forwards it into `SignUtils.signatureToAddress`, exercising the unbounded parsing path the P2P-layer fix was meant to eliminate.

Note: I was unable to fully trace every code path that leads to `checkWeight` without going through `TransactionsMsgHandler.check` (e.g., the exact behavior of local RPC broadcast validation in `Wallet.java`) within the available tool budget; confirming whether an oversized signature can reach `checkWeight` in practice without any `isValidLength` gate along that specific path would benefit from further review of `Wallet.java`'s broadcast handling and `Manager.pushTransaction`.

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
