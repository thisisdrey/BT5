## Analysis Result

I found a strong analog. Confirming the root-cause chain:

`recalculate_chunk_request_schedule` in `stackslib/src/net/stackerdb/sync.rs:1364-1387` computes `self.expected_versions` as the **max** of `slot_versions` across all entries in `self.chunk_invs` — a map populated entirely from unauthenticated, attacker-controlled `StackerDBChunkInvData.slot_versions` claims (accepted verbatim in `add_pushed_chunk` at `sync.rs:587-627` and `pushchunks_try_finish` at `sync.rs:1304-1352`, with no signature covering this vector). This inflated `expected_versions` is then used by `validate_downloaded_chunk` (`sync.rs:538-558`) → `PeerNetwork::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-718`), which rejects any chunk where `data.slot_version < *expected_version` (line 700). A single malicious replica can claim `slot_versions[i] = u32::MAX` in a `StackerDBChunkInv` reply to a push, poisoning `expected_versions` so that all subsequent legitimate (properly signed, sequentially-versioned) chunks for that slot are permanently rejected as "stale" by this syncing node — mirroring the report's clientId/nonce poisoning pattern (unauthenticated envelope field used to update persistent dedup/freshness state that then suppresses all future legitimate messages).

### Title
Unauthenticated peer-supplied `StackerDBChunkInvData.slot_versions` poisons `expected_versions`, permanently blocking legitimate StackerDB chunk sync - (File: `stackslib/src/net/stackerdb/sync.rs`)

### Finding Description
`StackerDBChunkInvData` (`stackslib/src/net/mod.rs:1130-1137`) carries a `slot_versions: Vec<u32>` that is **not signed or otherwise authenticated** — it is simply the remote peer's self-reported claim about which chunk versions it has [1](#0-0) . During the push-reconciliation path, `add_pushed_chunk` blindly stores this attacker-controlled vector into `self.chunk_invs` [2](#0-1) , and `pushchunks_try_finish` calls it after collecting `StackerDBChunkInv` replies with no version-cap check other than `slot_versions.len() != self.num_slots` [3](#0-2) .

When `need_resync` is set, `recalculate_chunk_request_schedule` recomputes `self.expected_versions` as the pointwise maximum of `slot_versions` across *all* stored `chunk_invs`, with no bound and no validation that the claimed version is actually achievable/signed: [4](#0-3) 

This `self.expected_versions` is later passed to `validate_downloaded_chunk`, which forwards it as the `expected_versions` argument to `PeerNetwork::validate_received_chunk`: [5](#0-4) 

Inside `validate_received_chunk`, a chunk is rejected outright if `data.slot_version < *expected_version` — a check performed *after* the legitimate size/signer checks but which uses the attacker-poisoned threshold: [6](#0-5) 

Because `slot_version` is a `u32` bounded by the real signer's actual Lamport clock (which increments by at most 1 per legitimate write and is capped by `config.max_writes`, checked at line 709 [7](#0-6) ), a single malicious replica reporting `slot_versions[i] = u32::MAX` (or any value far beyond what the real signer will ever reach) permanently and unrecoverably raises `expected_versions[i]` past what the legitimate signer can produce. Every subsequent, correctly-signed chunk from the real signer is then rejected as "stale" at `mod.rs:700-706`, exactly analogous to the WebSocket transport's `latestNonces` map being poisoned by a spoofed `clientId` with an inflated nonce.

### Impact Explanation
This causes a syncing Stacks node to be locked out of receiving any further legitimate updates to the affected StackerDB slot from any peer (not just the attacker), because `expected_versions` is a single scalar per slot shared across all fetch/validate operations for that sync round and persists via `self.expected_versions` on the `StackerDBSync` state machine until the next full connect/handshake resync cycle recomputes it from `self.stackerdbs.get_slot_versions` (`sync.rs:1007-1013`). Since real signers are bounded by `max_writes` and increment versions by 1, an attacker-inflated `u32::MAX` expected version can never be legitimately satisfied, degrading availability of the StackerDB replica (used by the Nakamoto signer set for block proposals/responses) on that node until process restart or full resync recovery. This is a remote, unauthenticated write to bookkeeping state that causes legitimate signed data to be dropped network-side — matching "unauthenticated/unauthorized write to state" impact criteria, though the effect is scoped to the syncing node's local view (mitigated somewhat by the next full `GetChunksInvFinish` resync round re-deriving `expected_versions` from local storage rather than peer claims, at `sync.rs:1009`).

### Likelihood Explanation
Reaching this path requires only: (1) being an unauthenticated inbound/outbound p2p peer that replicates the given StackerDB (any p2p neighbor can claim to replicate it), (2) responding to a `StackerDBPushChunk` from the victim with a `StackerDBChunkInv` containing an inflated `slot_versions` entry, or being one of the neighbors surveyed during a `need_resync`-triggered `recalculate_chunk_request_schedule`. No signature over `slot_versions` is required, and the check is purely `slot_versions.len() == num_slots`. This makes exploitation straightforward for any peer able to establish a StackerDB session, without needing the node secret or another party's key.

### Recommendation
Do not use unauthenticated `chunk_invs.slot_versions` values (or their max) directly as `expected_versions` for rejecting downloaded/pushed chunks. Instead, only ever raise `expected_versions[i]` after actually receiving and validating (signature + freshness) a chunk at that version — i.e., derive `expected_versions` solely from `self.stackerdbs.get_slot_versions()` (locally verified state), not from peer-claimed inventories. If claimed inventories are used to prioritize *what to fetch*, cap the impact of a false claim by not letting it also gate acceptance of *lower*, legitimately-signed versions.

### Proof of Concept
1. Attacker node establishes a StackerDB session with the victim node and is added to `chunk_invs`.
2. Victim pushes a chunk to the attacker via `pushchunks_begin`; attacker replies with a `StackerDBChunkInv` where `slot_versions[target_slot] = u32::MAX` (any inflated value beyond the real signer's practical max).
3. `pushchunks_try_finish` stores this in `chunk_invs` via `add_pushed_chunk`, setting `need_resync = true` since `old_version < new_version` [8](#0-7) .
4. State machine transitions back to `GetChunks` and calls `recalculate_chunk_request_schedule`, setting `self.expected_versions[target_slot] = u32::MAX` [9](#0-8) .
5. Any subsequent legitimately-signed chunk from the real signer for that slot (version ≤ `max_writes` ≪ `u32::MAX`) is rejected by `validate_received_chunk`'s `data.slot_version < *expected_version` check until the next full resync cycle re-derives `expected_versions` from local storage.

    /// Recalculate the download schedule based on chunkinvs received on push
    pub fn recalculate_chunk_request_schedule(
        &mut self,
        network: &PeerNetwork,
    ) -> Result<(), net_error> {
        // figure out the new expected versions
        let mut expected_versions = vec![0u32; self.num_slots];
        for (_, chunk_inv) in self.chunk_invs.iter() {
            for (slot_version, expected_version) in chunk_inv
                .slot_versions
                .iter()
                .zip(expected_versions.iter_mut())
            {
                *expected_version = (*slot_version).max(*expected_version);
            }
        }

        let priorities =
            self.make_chunk_request_schedule(network, Some(expected_versions.clone()))?;

        self.chunk_fetch_priorities = priorities;
        self.expected_versions = expected_versions;
        Ok(())
    }
