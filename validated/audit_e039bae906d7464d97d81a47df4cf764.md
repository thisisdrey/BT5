### Title
Insolvent positions with zero collateral can never be liquidated — bad debt persists permanently - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` requires the seized collateral amount (`_totalSeized = repaid value + liquidator incentive + protocol fee`) to be fully covered by the account's `DepositToken` balance, otherwise it reverts with `AmountIsTooHigh`. Once a position's collateral has been fully seized while debt remains — a state demonstrably reachable via partial/max liquidations (see `test/Pool.test.ts` "should liquidate by repaying max possible amount", where `msdMET.balanceOf(alice) ≈ 0` while `msEthDebtToken.balanceOf(alice) > 0` and `_isHealthy == false`) — no rational or possible liquidation can clear the residual debt. There is no bad-debt socialization or fallback mechanism.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

```solidity
(_totalSeized, _toLiquidator, _fee) = quoteLiquidateOut(syntheticToken_, amountToRepay_, depositToken_);

if (_totalSeized > depositToken_.balanceOf(account_)) {
    revert AmountIsTooHigh();
}

syntheticToken_.burn(_msgSender, amountToRepay_);
_debtToken.burn(account_, amountToRepay_);
depositToken_.seize(account_, _msgSender, _toLiquidator);
```

`quoteLiquidateOut` (contracts/Pool.sol:451-472) computes `_totalToSeize` purely from the oracle-quoted value of `amountToRepay_` plus `liquidatorIncentive` and `protocolFee` — it is never less than the repaid value (and strictly greater when `liquidatorIncentive > 0`). Consequently:

- If `depositToken_.balanceOf(account_) == 0`, every `amountToRepay_ > 0` reverts.
- If the balance is below `amountToRepay + incentive`, a liquidation either reverts or pays the liquidator less than they burn, so it will never be executed.
- `quoteLiquidateMax` only caps `amountToRepay_` so that `totalToSeize` fits the balance; it cannot create collateral where none exists.
- The liquidator must supply real synthetic tokens (`syntheticToken_.burn(_msgSender, amountToRepay_)`), so unlike a pure "fee" reward there is no source to pay an incentive from once collateral is exhausted.
- No `seize`-or-partial-write-off path exists: `DebtToken.burn` only proceeds when paired with a successful `depositToken_.seize`, and there is no shortfall/bad-debt accounting anywhere in `Pool`, `DebtToken`, or `Treasury`.

The unhealthy-debt check itself does not help: `debtPositionOf` continues to report the account unhealthy, but the `AmountIsTooHigh` guard blocks every liquidation attempt.

### Impact Explanation
Synthetic tokens minted against the wiped-out collateral remain in circulation, backed by unrecoverable `DebtToken` balances. This is permanent, uncleared bad debt — i.e. protocol insolvency that grows every time a position goes underwater faster than liquidators act. Since liquidation is the only mechanism that retires `DebtToken` principal, the debt can never be removed by any unprivileged actor, and the pool's effective collateralization is permanently overstated.

### Likelihood Explanation
Reachable through ordinary market movement (collateral price drop) or same-transaction oracle price manipulation combined with an existing max-LTV position: an attacker liquidates the account up to `quoteLiquidateMax`, draining all collateral while a residual `DebtToken` balance remains. No privileged role is required; `liquidate` is a public `whenNotShutdown` entry point and the residual state is demonstrated by the repository's own tests. Persistence is certain once reached — the revert is unconditional.

### Recommendation
Add a bad-debt resolution path, e.g.: allow `liquidate` to seize the entire remaining collateral even when `totalToSeize > balance` (cap `_toLiquidator`/`_fee` at the balance and reduce the `DebtToken.burn` proportionally), or implement a governance/keeper-invokable write-off that burns residual `DebtToken` of zero-collateral accounts and socializes the loss (e.g., via treasury cover or synth depeg acknowledgment). At minimum, document and monitor that deeply underwater accounts leave permanent bad debt.

### Proof of Concept
Foundry-style fork/Hardhat outline (mirrors the existing test at test/Pool.test.ts:795-819):

```solidity
// 1. alice deposits MET into msdMET, mints msETH at max issuable.
// 2. Drop MET oracle price (or snapshot-and-manipulate) so alice is unhealthy.
// 3. liquidator calls:
uint256 maxRepay = pool.quoteLiquidateMax(msETH, alice, msdMET);
pool.liquidate(msETH, alice, maxRepay, msdMET);
//    -> seizes ~all of alice's msdMET; assert:
assertApproxEq(msdMET.balanceOf(alice), 0);
assertGt(msETHDebtToken.balanceOf(alice), 0);   // residual bad debt
// 4. Any further liquidation is impossible:
vm.expectRevert(Pool.AmountIsTooHigh.selector);
pool.liquidate(msETH, alice, 1, msdMET);
//    quoteLiquidateMax also returns ~0 / reverts — debt is permanently stuck,
//    while alice's minted msETH remains circulating unbacked.
```

The residual-debt state is already asserted in `test/Pool.test.ts` ("should liquidate by repaying max possible amount"): `expect(await msEthDebtToken.balanceOf(alice.address)).gt(0)` with `msdMET.balanceOf(alice) ≈ 0`.

Note: I verified the revert guard and the absence of a bad-debt path in `Pool.sol`, `DepositToken.sol` (`seize`), and `DebtToken` interfaces, but I could not re-confirm the exact body of `DepositToken.seize` and `quoteLiquidateMax` line-by-line within tool limits; the conclusion rests on the `AmountIsTooHigh` revert at Pool.sol:583-585 and the protocol-fee/incentive math in `quoteLiquidateOut`, which make zero-collateral liquidation unconditionally impossible.
