### Title
Missing synchronization on shared static `LRUMap` cache in TVM `Program.getProgramPrecompile()` allows concurrent-access corruption / DoS - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
CVE-2023-2430 is a missing-lock race condition in a shared kernel structure (`io_cqring_event_overflow`) reachable by unprivileged local callers, causing corruption/DoS. The analogous pattern in java-tron is the static, unsynchronized `programPrecompileLRUMap` cache in `Program`, which is shared across **every** TVM execution context (block application, transaction validation, and constant/`eth_call` queries) with no lock protecting concurrent `containsKey`/`get`/`put` operations.

### Finding Description
`Program` declares a **class-level static** cache: [1](#0-0) 

and reads/writes it without any synchronization in `getProgramPrecompile()`: [2](#0-1) 

`LRUMap` (Apache Commons Collections) is explicitly **not thread-safe**: even its `get()` operation mutates the internal doubly-linked ordering list to record recency. When two threads call `containsKey`/`get`/`put` concurrently on the same static instance, the internal linked list can be corrupted (e.g., a node pointing to itself or a stale/removed node), which can produce an infinite loop or `NullPointerException`/`ArrayIndexOutOfBoundsException` on subsequent map operations.

This map is reachable concurrently because:
- Anonymous API/JSON-RPC/HTTP clients can invoke `triggerConstantContract` (a query path into `Wallet`), which runs the TVM without going through the single `Manager` block-processing lock, for any smart contract, from many concurrent request threads.
- Smart-contract transactions submitted over the network are dispatched to a worker pool (`trxHandlePool` in `TransactionsMsgHandler`) and to `smartContractQueue` processing, both of which can run TVM executions concurrently with each other and with constant-call query threads.
- Every such execution path constructs a `Program` and calls `getProgramPrecompile()`, touching the same static `programPrecompileLRUMap`.

Because insertion order/keys depend only on contract bytecode (`Key key = getJumpDestAnalysisCacheKey()`), an attacker does not need any special privilege — merely issuing concurrent constant calls or smart-contract transactions against varied (or even the same) contract addresses is enough to race the cache.

### Impact Explanation
Corruption of the shared `LRUMap`'s internal structure can cause the executing thread(s) to loop indefinitely or throw unexpected runtime exceptions inside TVM execution. Because this cache is touched on essentially every contract call/deployment/constant-call path, a corrupted or looping structure can stall or crash the threads that serve `triggerConstantContract`/`triggerSmartContract`, and could similarly disrupt the trigger-processing threads used during block application, leading to an unresponsive node — matching the "API the node can no longer serve" / node-crash-or-halt impact bar. This aligns with the CVE's medium-severity Availability-only impact profile (no confidentiality/integrity effect).

### Likelihood Explanation
No special privileges are required: any account can call `triggerConstantContract` via HTTP/JSON-RPC, and any address can broadcast `TriggerSmartContract`/`CreateSmartContract` transactions that are processed on background worker threads. Triggering the race only requires ordinary concurrent client behavior (multiple simultaneous requests), which is trivially reproducible by an external, unauthenticated caller — no cryptographic breakage or elevated permission is needed. The main uncertainty is the exact reliability/frequency of the corruption given `LRUMap`'s specific internal implementation, which was not further inspected due to index limits on third-party library sources.

### Recommendation
Guard `programPrecompileLRUMap` with proper synchronization (e.g., wrap it in `Collections.synchronizedMap(...)`, use a `ConcurrentHashMap`-based cache, or use Commons Collections' thread-safe decorator) so that concurrent `getProgramPrecompile()` calls from constant-call query threads and transaction-processing threads cannot race on the same cache instance.

### Proof of Concept
Conceptual PoC (not exhaustively validated against the exact `LRUMap` internals, which are outside this repo's index):
1. Deploy or reuse several distinct smart contracts.
2. From an unauthenticated client, fire a burst of concurrent `wallet/triggerconstantcontract` (or JSON-RPC `eth_call`) requests against these contracts, interleaved with broadcasting `TriggerSmartContract` transactions for the same contracts, so many threads invoke `Program.getProgramPrecompile()` on the shared `programPrecompileLRUMap` at the same time.
3. Repeated concurrent `get`/`put` operations can corrupt the LRU eviction linked list, leading to an infinite loop or exception in subsequent cache accesses on the affected node, degrading or halting its ability to serve further constant-call/API requests.

    if (isConstantCall()) {

    if (programPrecompile == null) {

      if (programPrecompileLRUMap.containsKey(key)) {
        programPrecompile = programPrecompileLRUMap.get(key);
      } else {
        programPrecompile = ProgramPrecompile.compile(ops);
        programPrecompileLRUMap.put(key, programPrecompile);
      }
    }
    return programPrecompile;
