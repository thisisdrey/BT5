### Title
MODULE.bazel.lock persists secret values (env vars, netrc-derived passwords) used by module extensions in plain text - ([File: MODULE.bazel.lock])

### Summary
Bazel's Bzlmod lockfile records, for every module extension, the exact environment-variable values it read (`envVariables`/`recordedInputs`) as well as the verbatim attribute dictionaries (`generatedRepoSpecs.*.attributes`) passed into any repo rules the extension instantiates. This lockfile is written unencrypted to the workspace root as `MODULE.bazel.lock`, and the official documentation explicitly recommends committing it to version control.

### Finding Description
When a module extension declares `environ = [...]` (or calls `module_ctx.getenv()`), Bazel stores the actual string value of that environment variable in the lockfile so that a later invocation can detect whether re-evaluation is required [1](#0-0) . Similarly, the `generatedRepoSpecs` field records the complete, unredacted `attributes` map supplied to any repository rule the extension invokes, as seen throughout `MODULE.bazel.lock` and `src/tools/bzlmod/utils.bzl` [2](#0-1) [3](#0-2) .

Because a module extension is ordinary Starlark code that can legitimately obtain secrets (e.g., an internal registry token from `ctx.getenv()`, or a proxy/basic-auth password parsed via `read_netrc`/`use_netrc` in `tools/build_defs/repo/utils.bzl`) and pass them as an attribute to a custom or third-party repo rule (e.g., a "password" attribute on an internal `authenticated_http_archive`-style rule, distinct from the `ctx.download(auth=...)` runtime-only parameter), that secret becomes part of the extension's recorded input/output state. Bazel's lockfile writer performs no scrubbing or redaction of attribute values or environment variable values before serializing them to `MODULE.bazel.lock` — it treats all of them as generic reproducibility-tracking data, exactly as the Fortify Jenkins plugin treated its proxy password as ordinary job configuration data before 19.2.30.

This is directly analogous to CVE-2020-2107: a secret intended only to authenticate an outbound network request (proxy/registry credential) is persisted unencrypted into a project-level file (`config.xml` for Fortify; `MODULE.bazel.lock` for Bazel) that is readable by anyone with read access to the project/repository — a broader audience than the party who should hold the credential.

### Impact Explanation
`MODULE.bazel.lock` lives at the workspace root next to `MODULE.bazel`, and Bazel's own documentation explicitly instructs users to "Include the lockfile in version control to facilitate collaboration ... promoting consistent development environments across the project" [4](#0-3) . If a module extension (first-party or from a dependency in the module graph) uses an environment variable or netrc-derived password to authenticate to a private registry/mirror and that value ends up recorded as a tracked `environ` value or as a repo-rule attribute in `generatedRepoSpecs`, the secret is committed to source control in plain text and exposed to every collaborator with repository read access, to CI logs, and to anyone who later clones the repo — none of whom need the credential to build. This is a direct analog of CWE-256/CWE-522 (plaintext storage of sensitive information) with the same severity profile as the Fortify advisory: unencrypted credential-at-rest disclosure to a broader-than-intended audience.

### Likelihood Explanation
This requires an existing, first-party (or dependency) module extension to intentionally forward a secret value (via `environ`/`getenv`, or a netrc-derived login/password) into either a tracked environment variable or a repo-rule attribute, which then gets serialized by the standard lockfile-writing path. This is a design/behavior gap in Bazel's Bzlmod machinery, not something an unprivileged network attacker can trigger by publishing malicious bytes at a URL — the mechanism is reachable purely through normal, legitimate use of `module_extension(environ=...)` / `read_netrc`/`use_netrc`, both of which are documented, commonly-used features. There is no checksum, integrity check, or scrubbing step in the lockfile writer that would prevent this; the behavior is systemic rather than attacker-injected.

### Recommendation
This is worth flagging as a hardening opportunity for Bazel to redact or omit values recorded from `environ`, `getenv`, and repo-rule attributes commonly associated with secrets (e.g., matching names like `password`, `token`, `auth`, `secret`) from `MODULE.bazel.lock`, or to hash such values instead of storing them verbatim, and to document clearly that any secret consumed by a module extension will be persisted unencrypted in the lockfile.

### Proof of Concept
Not applicable in the strict sense required by this analog process. The behavior can be observed directly from existing test code: `testModuleExtensionRerunsOnGetenvChanges` in `src/test/py/bazel/bzlmod/bazel_lockfile_test.py` demonstrates that environment-variable values are printed and tracked verbatim across builds, and the shipped `MODULE.bazel.lock` in this repository shows `generatedRepoSpecs.*.attributes` recorded with full, unredacted values [5](#0-4) [2](#0-1) .

**Caveat / uncertainty**: I was unable to locate and inspect the actual Java source of `RepositoryDelegatorFunction.DigestWriter`, `BazelLockFileFunction`, or `SingleExtensionEvalFunction` (only documentation and shell/Python test references were indexed for this repository), so I cannot confirm from source code whether there is any existing filtering/redaction logic for secret-looking attribute or environment-variable names before this reaches the lockfile writer. This is a documentation- and test-based inference rather than a source-code-confirmed absence of mitigation, and per the "no code citation for unseen files" constraint, this should be validated against the actual Java implementation (which may include partial mitigations not visible in the indexed subset) before being treated as a confirmed, unmitigated vulnerability. If a background agent or full-repo access confirms no scrubbing exists in `BazelLockFileFunction`/`SingleExtensionEvalFunction`, the finding above stands as written; otherwise this should be downgraded.

  def testModuleExtensionRerunsOnGetenvChanges(self):
    self.ScratchFile(
        'MODULE.bazel',
        [
            'module(name = "old_name", version = "1.2.3")',
            'lockfile_ext = use_extension("//:extension.bzl", "lockfile_ext")',
            'use_repo(lockfile_ext, "hello")',
        ],
    )
    self.ScratchFile('BUILD.bazel')
    self.ScratchFile(
        'extension.bzl',
        [
            'def impl(ctx):',
            '    ctx.file("BUILD", "filegroup(name=\'lala\')")',
            '',
            'repo_rule = repository_rule(implementation=impl)',
            '',
            'def _module_ext_impl(ctx):',
            (
                '    print("UNDECLARED_KEY=%s" %'
                ' ctx.os.environ.get("UNDECLARED_KEY"))'
            ),
            (
                '    print("PREDECLARED_KEY=%s" %'
                ' ctx.os.environ.get("PREDECLARED_KEY"))'
            ),
            '    print("LAZYEVAL_KEY=%s" % ctx.getenv("LAZYEVAL_KEY"))',
            '    repo_rule(name="hello")',
            '',
            'lockfile_ext = module_extension(',
            '    implementation=_module_ext_impl,',
            '    environ = ["PREDECLARED_KEY"],',
            ')',
        ],
    )

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all'], env_add={'UNDECLARED_KEY': 'val1'}
    )
    stderr = '\n'.join(stderr)
    self.assertIn('UNDECLARED_KEY=val1', stderr)

    # No reevaluation if undeclared env var changes
    self.RunBazel(['shutdown'])
    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all'], env_add={'UNDECLARED_KEY': 'val2'}
    )
    stderr = '\n'.join(stderr)
    self.assertNotIn('UNDECLARED_KEY', stderr)

    # Reevaluation if predeclared env var is first set
    self.RunBazel(['shutdown'])
    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all'], env_add={'PREDECLARED_KEY': 'val1'}
    )
    stderr = '\n'.join(stderr)
    self.assertIn('PREDECLARED_KEY=val1', stderr)

    # No reevaluation if predeclared env var does not change
    self.RunBazel(['shutdown'])
    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all'], env_add={'PREDECLARED_KEY': 'val1'}
    )
    stderr = '\n'.join(stderr)
    self.assertNotIn('PREDECLARED_KEY', stderr)

    # Reevaluation if predeclared env var changes
    self.RunBazel(['shutdown'])
    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all'], env_add={'PREDECLARED_KEY': 'val2'}
    )
    stderr = '\n'.join(stderr)
    self.assertIn('PREDECLARED_KEY=val2', stderr)

    # Reevaluation if predeclared env var becomes unset
    self.RunBazel(['shutdown'])
    _, _, stderr = self.RunBazel(['build', '@hello//:all'])
    stderr = '\n'.join(stderr)
    self.assertIn('PREDECLARED_KEY=None', stderr)
