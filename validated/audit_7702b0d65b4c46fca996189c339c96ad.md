### Title
Legacy (default) Exchange price calculation lets a single transaction distort the AMM pool and drain the opposite reserve via unchecked ratio math - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, ExchangeWithdrawActuator.java, ExchangeTransactionActuator.java, chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
The Fei Protocol incident involved a bonding-curve/joint-curve contract whose reserve pricing could be manipulated within a flash-loan-scoped set of calls to drain the Protocol Controlled Value. java-tron's built-in TRC10 `Exchange` feature implements an analogous bonding-curve/constant-formula AMM (`ExchangeCapsule.transaction`, backed by `ExchangeProcessor`/`SafeExchangeProcessor`) that is directly reachable by any account via `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract`. The "hardened" arithmetic path (`allowHardenExchangeCalculation`) that adds overflow and non-negative-balance invariant checks is optional and gated by a chain parameter/proposal; the legacy code path performs the same balance-ratio math using plain `long`/`double` arithmetic without post-condition checks.

### Finding Description
`ExchangeInjectActuator.execute` and `ExchangeWithdrawActuator.execute` compute the counter-token amount purely from the *current* mutable pool balances (`firstTokenBalance`, `secondTokenBalance`) read at call time: [1](#0-0) 

`ExchangeTransactionActuator` similarly delegates to `ExchangeCapsule.transaction`, which — unless `hardenedCalc` is enabled — uses the legacy `ExchangeProcessor`, a floating point bonding-curve formula (`Maths.pow` on `double`) with no check that resulting balances stay non-negative or that fee/rounding don't create unbacked balances: [2](#0-1) [3](#0-2) 

The safety checks (overflow-safe `addExact`/`subtractExact`, `SafeExchangeProcessor`'s BigDecimal precision arithmetic, and the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` invariant) only activate when `allowHardenExchangeCalculation()` returns true: [4](#0-3) [5](#0-4) 

This mirrors the Fei Protocol root cause: a reserve-balance-derived pricing function that can be pushed and pulled by a single actor issuing a sequence of same-block operations (buy/sell/inject/withdraw against the same `Exchange` pool) using plain floating-point/long math with no slippage or invariant protection in the default (non-hardened) code path, potentially producing rounding errors or negative/overshot balances that let an attacker extract more value from the pool than they put in.

### Impact Explanation
If `allowHardenExchangeCalculation` is not enabled on the live chain (its rollout is controlled by a committee proposal per `ProposalUtil`/`ProposalService`), the exchange pools are only protected by legacy `long`/`double` arithmetic. Because pool balances are attacker-influenced within a single or sequential set of self-authored transactions (inject → transact → withdraw), an attacker can exploit floating-point rounding in `ExchangeProcessor` or precision loss in the legacy withdraw ratio math to skew withdrawn/injected token quantities, draining the TRX or TRC10 reserve backing the exchange pool — an unbacked-balance/fund-theft condition equivalent in class to the Fei Protocol PCV drain.

### Likelihood Explanation
Exploitability depends entirely on whether `allowHardenExchangeCalculation` is active on the deployed chain; the presence of extensive hardened-mode tests (`hardenedSuccessExchangeTransaction`, `hardenedPrecisionCheckFailsWhenImprecise`, etc.) indicates the hardening was added specifically to close this class of arithmetic/invariant gap, implying the legacy path was previously exploitable and is only mitigated when the flag is turned on chain-wide via governance. I was unable to determine the on-chain default value of `allowHardenExchangeCalculation` (its getter/default is defined in `DynamicPropertiesStore`, which the indexed file did not fully expose), so I cannot confirm whether this networks currently run in the vulnerable legacy mode or the hardened mode by default.

### Recommendation
Make the hardened arithmetic (`SafeExchangeProcessor`, `addExact`/`subtractExact`, and the non-negative post-condition check) the mandatory, non-optional code path for all `Exchange*` actuators rather than gating it behind `allowHardenExchangeCalculation`, and add explicit slippage/precision validation identical to the hardened branch for `ExchangeInjectActuator`/`ExchangeWithdrawActuator` in the legacy branch as well, since a governance-controlled toggle should not be the sole guard against fund-draining rounding/invariant bugs.

### Proof of Concept
Not directly reproducible without confirming the live default of `allowHardenExchangeCalculation`; conceptually, an attacker would (1) create/locate an `Exchange` pool with small reserves, (2) repeatedly call `ExchangeTransactionContract`/`ExchangeWithdrawContract` in the legacy (non-hardened) mode with quantities chosen to maximize floating-point/`BigDecimal` rounding in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` or the ratio math in `ExchangeWithdrawActuator.doValidate`, and (3) repeat until accumulated rounding lets them withdraw more of the counter-token than their contributed relay/supply share, draining the pool's reserve.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
