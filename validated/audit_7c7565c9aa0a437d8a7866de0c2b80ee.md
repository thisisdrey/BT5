### Title
Quarantine-directory basename heuristic bypasses per-repository ownership check in `ObjectDirectoryPath` - (`internal/git/localrepo/paths.go`)

### Summary
`Repo.ObjectDirectoryPath` resolves the `git_object_directory` field of a client-supplied `Repository` protobuf message into an on-disk path. It contains two independent validation strategies gated by an "OR"-style choice: a strict, repository-scoped check, and a loose, pattern-based "this looks like a transaction quarantine directory" check. Because the loose check is chosen purely by inspecting the *basename* of the path rather than verifying that the path actually belongs to the requesting repository's own quarantine, an attacker who can set `git_object_directory` on the `Repository` message can steer resolution down the un-verified branch and obtain an object directory outside the strict per-repository containment the code is supposed to enforce — the same "attacker picks the weaker of two OR'd validation paths" pattern described in the source report, just applied to storage-path resolution instead of Merkle-proof validation.

### Finding Description
`ObjectDirectoryPath` first validates that the object directory resolves inside the *storage* root (not the repository root) via `storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))`: [1](#0-0) 

It then computes a heuristic flag purely from path basenames to decide whether the path is a legitimate transaction/quarantine directory: [2](#0-1) 

```go
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
```

If `isTransactionQuarantineDir` is true, the function *skips entirely* the second, stricter check that would otherwise verify the object directory is (a) contained in `repoPath` via `storage.ValidateRelativePath(repoPath, objectDirectoryPath)`, or (b) — as a fallback — located under the storage's temp dir with a prefix that is cryptographically/structurally tied to *this specific repository* (`storage.QuarantineDirectoryPrefix(repo)`): [3](#0-2) 

This mirrors the reported bug class exactly: two validation paths exist (global/loose vs. strategy-specific/strict), and the "OR" evaluates to true as soon as the looser condition is met, regardless of whether the strict, ownership-binding condition would fail. Here, the loose condition is satisfiable by anyone who controls the string value of `git_object_directory` on the RPC's `Repository` message — they only need the resulting basename to literally be `quarantine`, or the parent directory to be `quarantine` with a `tmp_objdir`-prefixed basename. Nothing ties this basename check back to the caller's own repository, storage-generated random suffix, or `QuarantineDirectoryPrefix(repo)` value that the strict branch enforces.

The only remaining containment is the storage-root check at line 38, which is deliberately broad (it allows any path under the *storage*, since transaction quarantine dirs legitimately live in the storage's shared temp area) — so it does not prevent cross-repository access within the same storage.

### Impact Explanation
Any RPC path that accepts a `Repository` message and calls `ObjectDirectoryPath` (e.g. repository size computation) can be pointed at another repository's or an attacker-influenced directory within the same storage, as long as that directory's basename matches the `quarantine`/`tmp_objdir` heuristic and exists on disk. This defeats the intended repository-scoped binding of quarantine object directories and is a concrete instance of unauthorized cross-repository object-directory access within a shared storage — the storage-path-resolution analog explicitly called out as in-scope. Depending on the downstream consumer of the resolved path (e.g. size accounting, object listing), this can leak information about, or misattribute state from, a directory that does not belong to the caller's repository.

### Likelihood Explanation
The heuristic is unconditional and requires no privileged access, race condition, or unusual timing — any caller able to set the `git_object_directory` field on a `Repository` request (a normal, client-writable protobuf field) can attempt to trigger the loose branch. The only precondition is that a directory with a matching basename must already exist within the storage root, which is realistic given that Gitaly's own transaction manager and git's own object-quarantine mechanism routinely create `quarantine`/`tmp_objdir`-named directories in the shared per-storage temp area as part of normal push/receive-pack processing.

### Recommendation
Do not decide whether a path is a legitimate quarantine directory from its basename alone. The loose branch should be replaced with (or subsumed by) the same ownership check used in the strict branch: verify the resolved path is prefixed by `filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))` for the *specific* requesting repository before treating it as a valid quarantine directory, exactly as already done for the manual-quarantine fallback case. In other words, remove the basename-based `isTransactionQuarantineDir` special case and unify both code paths on the repository-bound prefix check, so a "quarantine"-looking basename can never substitute for actual per-repository verification.

### Proof of Concept
1. Attacker (or a compromised/undertrusted caller with RPC access) issues any RPC that carries a `gitalypb.Repository` message and internally calls `Repo.ObjectDirectoryPath` (e.g. the repository-size RPC, per usage in `internal/gitaly/service/repository/size.go`). [4](#0-3) 
2. The attacker sets `relative_path` to their own (legitimate) repository, but sets `git_object_directory` to a relative path such as `../otherstorage-tmp/some-repo-quarantine-dir/quarantine` (or any existing directory within the storage root whose basename is exactly `quarantine`) — a directory it does not own, e.g. a stale/parallel transaction's quarantine directory belonging to a different repository within the same storage.
3. Line 38's `storage.ValidateRelativePath(storagePath, ...)` succeeds because the target directory is still within the storage root.
4. `isTransactionQuarantineDir` evaluates to `true` purely because `baseDir == "quarantine"`, so the strict, repository-bound check (lines 53–75, in particular the `expectedQuarantinePrefix` comparison) is skipped entirely.
5. `os.Stat(fullPath)` succeeds since the directory genuinely exists (created for another repository's transaction), and the function returns that foreign path as the "object directory" for the attacker's own repository — with no verification that it belongs to the attacker's repository at all.

Note: I could not fully confirm from the indexed code the exact on-disk naming convention produced by `tempdir.NewWithPrefix` combined with `storage.QuarantineDirectoryPrefix(repo)` (i.e., whether the final basename is always literally `quarantine` in practice, or a repo/random-suffixed name that merely contains it as a component) — this affects how easily a matching directory can be found/collided with in a real deployment, and would benefit from direct verification of `internal/gitaly/storage/locator.go`'s `QuarantineDirectoryPrefix` implementation and `internal/tempdir` in a live session.

func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}
