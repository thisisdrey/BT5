Audit Report

## Title
Permanently unrecoverable user funds in `LostTips` with no withdrawal/claim path - ([File: bridges/snowbridge/pallets/system-v2/src/lib.rs])

## Summary
`pallet-snowbridge-system-frontend::add_tip` unconditionally burns the user's tip asset via `swap_fee_asset_and_burn`/`burn_for_teleport` before the cross-chain `Transact` call even executes on BridgeHub. [1](#0-0)  If the subsequent `EthereumSystem::add_tip` call on BridgeHub fails (`AddTipError::NonceConsumed`, `UnknownMessage`, etc.), the amount is only recorded in `LostTips`, with no extrinsic anywhere in the codebase to claim or refund it. [2](#0-1) 

## Finding Description
On AssetHub, `add_tip` calls `Self::swap_fee_asset_and_burn`, which either swaps the fee asset for ether and burns it, or burns it directly if already ether — in both branches the asset is destroyed via `burn_for_teleport::<T::AssetTransactor>` before any confirmation that the tip will be successfully applied on BridgeHub. [3](#0-2) 

The frontend then dispatches a fire-and-forget `Transact` XCM to BridgeHub's `EthereumSystem::add_tip`. [4](#0-3) 

On BridgeHub, `pallet_snowbridge_system_v2::Pallet::add_tip` attempts `InboundQueue::add_tip`/`OutboundQueue::add_tip`; if this returns an `Err` (e.g., nonce already consumed or message unknown), the code path only mutates `LostTips::<T>` and emits `TipProcessed { success: false, .. }` — it never reverts the already-burned value or provides a redemption path. [5](#0-4) 

The storage doc comment itself acknowledges the gap: "Capturing the lost tips here supports implementing a recovery method in the future," confirming this recovery mechanism does not currently exist. [6](#0-5) 

The `AddTip` trait defines `NonceConsumed` and `UnknownMessage` as first-class, expected error variants rather than edge cases. [7](#0-6) 

A repository-wide search confirms `LostTips` is referenced only in its definition, its mutation in `add_tip`, unit tests in `bridges/snowbridge/pallets/system-v2/src/tests.rs`, and the integration test `tip_to_invalid_nonce_is_added_to_lost_tips` in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs` — no extrinsic, migration, or governance call anywhere reads, clears, or pays out this storage.

## Impact Explanation
Any signed AssetHub account whose tip lands on a nonce that is concurrently consumed by a relayer (a normal, expected race under `NonceConsumed`/`UnknownMessage` semantics) has its asset burned on AssetHub with the value permanently stuck as an unclaimable ledger entry in `LostTips` on BridgeHub. This is a genuine violation of the value-conservation invariant: user funds are destroyed and never settle to any beneficiary (neither the original user nor the intended relayer reward pool), constituting a "permanent user-fund... lock" as covered by the impact gate.

## Likelihood Explanation
High. This does not require any privileged actor, malicious relayer, or compromised infrastructure — an ordinary unprivileged user calling the public `add_tip` extrinsic under normal network timing/congestion (where a relayer processes the message before/concurrently with the tip transaction landing on BridgeHub) triggers this path. The existing integration test `tip_to_invalid_nonce_is_added_to_lost_tips` demonstrates the path is trivially reachable and is treated as an accepted/expected test outcome rather than a guarded invariant.

## Recommendation
Introduce a `claim_lost_tip(origin)` extrinsic in `pallet-snowbridge-system-v2` (or equivalent governance/self-service mechanism) that reads and clears `LostTips::<T>::get(&sender)` and settles the equivalent value back to the sender (e.g., via XCM refund to AssetHub, or minting/crediting ether on BridgeHub for teleport back). Alternatively, restructure the flow so the AssetHub-side burn only occurs after BridgeHub confirms the tip was successfully attached (e.g., an acknowledgment/receipt round-trip), so failures leave the funds recoverable at the origin instead of requiring a new redemption pathway.

## Proof of Concept
1. User calls `SnowbridgeSystemFrontend::add_tip(origin, MessageId::Outbound(nonce), asset)` on AssetHub for a `nonce` that is about to be, or already has been, consumed by the relayer processing the corresponding outbound message.
2. `swap_fee_asset_and_burn` burns the asset unconditionally at [8](#0-7)  before any cross-chain confirmation.
3. The `Transact` reaches BridgeHub's `EthereumSystem::add_tip`; `OutboundQueue::add_tip(nonce, amount)` returns `Err(AddTipError::NonceConsumed)`.
4. `pallet_snowbridge_system_v2::Pallet::add_tip` records the failure only into `LostTips::<T>::mutate(&sender, ...)` and emits `TipProcessed { success: false, .. }`. [9](#0-8) 
5. The sender's tip value is now permanently gone — burned on AssetHub, and unclaimable in `LostTips` on BridgeHub — as demonstrated by the existing integration test `tip_to_invalid_nonce_is_added_to_lost_tips` in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs`, which asserts `relayer_lost_tip > 0` as the terminal state with no follow-up recovery call.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
