## Title
Permanent DoS of a valid shielded transaction via state-dependent pool-value check being cached as an immutable ZK-proof result - (`File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
This is analogous to the reported VETH→VADER issue: a state/economic condition that is unrelated to the actual cryptographic proof causes a one-time-use validation artifact to be permanently marked invalid, so a user can never successfully resubmit the exact same, otherwise fully valid, transaction.

### Finding Description
`ShieldedTransferActuator.validate()` calls `checkProof()` to verify the zk-SNARK spend/output proofs and binding signature for a `ShieldedTransferContract` [1](#0-0) . `checkProof()` caches its result in `ZKProofStore`, keyed by the transaction id, so subsequent re-validations of the same transaction skip the expensive cryptography and just replay the cached verdict [2](#0-1) .

Inside the same cached code path, `checkProof()` also performs an economic/state check unrelated to the zk proof itself: it reads the current `totalShieldedPoolValue` from `DynamicPropertiesStore` and rejects the transaction with `"shieldedPoolValue error"` if the pool value would go negative given the *current* chain state [3](#0-2) . Crucially, this exception is thrown with `isFirstValidated = true`, exactly like the genuine cryptographic proof failures:

```
if (totalShieldedPoolValue < 0) {
  throw new ZkProofValidateException("shieldedPoolValue error", true);
}
```

Because `isFirstValidated` is `true`, `validate()`'s catch block permanently records the transaction id as invalid in `ZKProofStore` via `recordProof(tx.getTransactionId(), false)` [4](#0-3) . From that point forward, any future validate() call for the identical transaction bytes short-circuits at `proofStore.has(...)`/`proofStore.get(...)` and unconditionally throws `"record is fail, skip proof"`, regardless of whether `totalShieldedPoolValue` has since become sufficient [5](#0-4) .

This mirrors the reported pattern exactly: an unrelated, transient economic condition (`totalShieldedPoolValue`, analogous to the VETH allowance) is treated as if it invalidated the underlying proof, permanently poisoning a one-time-use verification artifact (`ZKProofStore` entry keyed by txid, analogous to the merkle-proof "used" flag) so the exact same signed transaction can never succeed again — even though the cryptographic proof itself was, and remains, fully valid.

### Impact Explanation
`totalShieldedPoolValue` is chain state that fluctuates block by block as other shielded transactions are processed; it is not an invariant property of a given transaction's proof. An unprivileged party can influence the timing/ordering of transactions relative to a victim's pending shielded transfer (e.g. by front-running with other shielded transfers that momentarily reduce `totalShieldedPoolValue`), causing the victim's otherwise perfectly valid, correctly-proven transaction to be evaluated once against a temporarily insufficient pool value. That single unlucky evaluation permanently blacklists the transaction id in `ZKProofStore`, so the wallet's identical signed bytes can never be broadcast successfully again — the user must discard the transaction and reconstruct an entirely new zk proof (fresh randomness/notes) to move the same funds, exactly the kind of "stuck" scenario described in the original finding. While the underlying notes themselves are not marked spent (nullifiers are only committed in `execute()`, after successful validation), this still constitutes a griefing/DoS vector against a specific, unprivileged, broadcastable transaction, since node-level revalidation of a resubmitted or re-broadcast transaction can never recover once the cache entry is poisoned.

### Likelihood Explanation
Reaching this path requires only submitting a normal `ShieldedTransferContract` transaction through the standard actuator `validate()`/`execute()` pipeline, which any unprivileged transaction broadcaster can do. The trigger condition (temporarily insufficient `totalShieldedPoolValue` at the moment of first validation) can occur naturally under normal network conditions (competing shielded transfers), and can be intentionally induced by an adversary controlling transaction ordering/timing relative to the victim's transaction.

### Recommendation
Do not conflate the caching of a purely cryptographic zk-SNARK proof verification result with checks against mutable chain state such as `totalShieldedPoolValue`. Move the `totalShieldedPoolValue` check out of `checkProof()`/out of the cached path entirely (it is already independently re-verified and enforced in `execute()` via `Commons.adjustTotalShieldedPoolValue` [6](#0-5) ), and only cache/record the ZK proof cache entry (`ZKProofStore`) for genuine cryptographic proof failures (`librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck`), never for transient economic/state-dependent conditions.

### Proof of Concept
1. Build a valid `ShieldedTransferContract` transaction with correct spend/output zk proofs and binding signature.
2. Arrange (or simply have occur naturally) for `totalShieldedPoolValue` to be momentarily insufficient at the time this transaction is first validated (e.g. broadcast a competing shielded transfer that consumes pool capacity first).
3. The victim's transaction fails `checkProof()` at the `totalShieldedPoolValue < 0` check with `isFirstValidated = true`, and `ZKProofStore` permanently records the transaction id as invalid.
4. Even after `totalShieldedPoolValue` recovers to a sufficient level, resubmitting the exact same signed transaction bytes always fails immediately with `"record is fail, skip proof"`, because `checkProof()` short-circuits on the cached `false` result without re-checking the pool value.
