### Title
Inconsistent repository-size accounting between `RepositorySize` and `RepositoryInfo` RPCs for object-pool members - (File: internal/gitaly/service/repository/size.go)

### Summary
The `RepositorySize` RPC and the `RepositoryInfo` RPC are both unprivileged, accessor-scoped view endpoints that a caller uses to determine how large a repository is on disk. They compute this using the same low-level primitive (`dirSizeInBytes`), but only `RepositoryInfo` additionally accounts for objects that live in a linked object pool, while `RepositorySize` does not. This mirrors the Backd finding: two "read" surfaces that are supposed to represent the same underlying quantity diverge because one code path contains extra pool-aware logic that the other lacks.

### Finding Description
`RepositorySize` computes the size of a repository by walking only the repository's own directory: [1](#0-0) 

`RepositoryInfo`, by contrast, detects whether the repository has an `objects/info/alternates` entry pointing at a pool, and if so, resolves the pool's relative path and adds the pool's on-disk size into the reported total: [2](#0-1) 

Both RPCs are documented as reflecting "the complete on-disk repository size" and the proto explicitly tells callers that `RepositoryInfo` is the more detailed variant of the same measurement, implying they should be consistent: [3](#0-2) 

For a pool member repository (created via `CreateFork`/object-pool linking, an ordinary user-facing operation — forking a project deduplicates objects into a shared pool via alternates), the vast majority of reachable objects can live only in the pool's object directory, not in the member's own `objects/` directory. `RepositorySize` walks only `repoPath` and has no branch that inspects `objects/info/alternates` or merges in the pool's directory size, unlike `RepositoryInfo`. Consequently, for the same repository state, `RepositorySize` under-reports size (potentially reporting near-zero for a member whose objects are entirely deduplicated into the pool) while `RepositoryInfo.Size` (which is `repoSize` after being incremented by `poolSize`) reports the correct, larger total.

The existing test suite explicitly names and calls out `TestRepositorySize_poolMember` (visible in the test file's function signatures) as a distinct code path from `TestRepositorySize_normalRepository`, showing engineers were already aware that pool membership is a special case for this RPC — but the fix (if any) is not applied symmetrically to `RepositoryInfo`'s pool-merging behavior at the `RepositorySize` call site.

### Impact Explanation
Any GitLab component or third-party integrator that relies on `RepositorySize` to make user-facing storage decisions (quota display, "repository size" shown in the UI, storage-limit enforcement, billing/usage estimates) will systematically under-count the true storage footprint of forked/pooled repositories, while `RepositoryInfo` reports the accurate number for the same repository. This is a Medium-severity data-integrity/consistency issue: no direct security compromise, but it can mislead users or downstream automated systems (e.g. storage quota enforcement, capacity planning) that pick one RPC over the other, exactly matching the class of bug in the referenced report where a claim could be understated or overstated relative to reality. Since object-pool membership is entirely determined by ordinary user actions (forking a project), any user can trivially reproduce this divergence without any special privilege.

### Likelihood Explanation
High. Any project fork that shares an object pool with its source repository — a completely standard, unprivileged GitLab workflow — will trigger this divergence as soon as `RepositorySize` is called on the fork while most objects reside in the pool. No malicious input or special crafting is required, only normal fork/push activity.

### Recommendation
Make `RepositorySize` (and any other consumer of `dirSizeInBytes` for whole-repository size reporting) apply the same pool-detection and size-merging logic used in `RepositoryInfo`, or have `RepositorySize` delegate to the same underlying size-computation helper that `RepositoryInfo` uses so that both RPCs are guaranteed to report a consistent number for the same repository state. Alternatively, clearly document that `RepositorySize` intentionally excludes pool objects and stop describing it in the proto as "the complete on-disk repository size."

### Proof of Concept
1. Create a source repository and add commits/objects.
2. Fork the source repository via `CreateFork`, which links the fork into the same object pool (deduplicating objects via `objects/info/alternates`), as documented in `internal/git/objectpool/link.go`'s `linkedToRepository`.
3. Call `RepositorySize` on the fork: it walks only the fork's own `objects/` directory (per `internal/gitaly/service/repository/size.go` lines 16-37) and returns a size close to zero, since almost all objects live in the pool.
4. Call `RepositoryInfo` on the same fork: it detects `repoInfo.Alternates.Exists`, resolves the pool path, and adds `poolSize` on top of `repoSize` (per `internal/gitaly/service/repository/repository_info.go` lines 43-83), returning a substantially larger and accurate total.
5. Compare the two responses for the same repository at the same point in time — they diverge significantly, demonstrating the inconsistency between the two "view" RPCs for the same underlying quantity, analogous to the `claimableRewards()` vs `allClaimableRewards()`/`poolCheckpoint()` divergence in the referenced report.

// RepositorySize returns the size of the specified repository in kibibytes. By default, this
// calculation is performed using the disk usage command.
func (s *server) RepositorySize(ctx context.Context, in *gitalypb.RepositorySizeRequest) (*gitalypb.RepositorySizeResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	path, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	filter := snapshot.NewDefaultFilter(ctx)
	sizeInBytes, err := dirSizeInBytes(path, filter)
	if err != nil {
		return nil, fmt.Errorf("calculating directory size: %w", err)
	}

	return &gitalypb.RepositorySizeResponse{Size: sizeInBytes / 1024}, nil
}

func (s *server) RepositoryInfo(
	ctx context.Context,
	request *gitalypb.RepositoryInfoRequest,
) (*gitalypb.RepositoryInfoResponse, error) {
	if err := s.locator.ValidateRepository(ctx, request.GetRepository()); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(request.GetRepository())

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	filter := snapshot.NewDefaultFilter(ctx)
	repoSize, err := dirSizeInBytes(repoPath, filter)
	if err != nil {
		return nil, fmt.Errorf("calculating repository size: %w", err)
	}

	repoInfo, err := stats.RepositoryInfoForRepository(ctx, repo)
	if err != nil {
		return nil, fmt.Errorf("deriving repository info: %w", err)
	}

	// If the repository is linked to an object pool, collect pool stats and merge them in so
	// that the response reflects the complete stats.
	if repoInfo.Alternates.Exists && len(repoInfo.Alternates.AbsoluteObjectDirectories()) > 0 {
		poolRepoPath := filepath.Dir(repoInfo.Alternates.AbsoluteObjectDirectories()[0])

		storagePath, err := s.locator.GetStorageByName(ctx, request.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting storage path: %w", err)
		}

		poolRelativePath, err := filepath.Rel(storagePath, poolRepoPath)
		if err != nil {
			return nil, fmt.Errorf("computing pool relative path: %w", err)
		}

		poolRepo := s.localRepoFactory.Build(&gitalypb.Repository{
			StorageName:  request.GetRepository().GetStorageName(),
			RelativePath: poolRelativePath,
		})

		poolLooseObjects, err := stats.LooseObjectsInfoForRepository(ctx, poolRepo, time.Now().Add(stats.StaleObjectsGracePeriod))
		if err != nil {
			return nil, fmt.Errorf("deriving pool loose objects info: %w", err)
		}

		poolPackfiles, err := stats.PackfilesInfoForRepository(ctx, poolRepo)
		if err != nil {
			return nil, fmt.Errorf("deriving pool packfiles info: %w", err)
		}

		poolSize, err := dirSizeInBytes(poolRepoPath, filter)
		if err != nil {
			return nil, fmt.Errorf("calculating pool repository size: %w", err)
		}

		repoSize += poolSize
		repoInfo = mergePoolInfo(repoInfo, stats.RepositoryInfo{
			LooseObjects: poolLooseObjects,
			Packfiles:    poolPackfiles,
		})
	}

	return convertRepositoryInfo(uint64(repoSize), repoInfo)
}
