### Title
Heap out-of-bounds read via unchecked `Zip64ExtraField::attr64()` index in singlejar's ZIP metadata parsing - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`Zip64ExtraField::attr64(int index)` is called by `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()` and the analogous `LH` accessors with an index computed from which 32-bit fields are `0xFFFFFFFF`, but the code never checks that the extra field's declared `payload_size()` (and thus `attr_count()`) actually contains that many 8-byte slots. [1](#0-0) [2](#0-1) 

### Finding Description
`ExtraField::find()` only validates that the extra-field header and its declared `size()` (`sizeof(ExtraField) + payload_size()`) fit within the enclosing `extra_fields_length()` window of the `CDH`/`LH` record: [3](#0-2) 

Once a `Zip64ExtraField` is located, however, `attr64(index)` performs unchecked pointer arithmetic on the flexible array member `attr_[]`: [4](#0-3) 

The callers in `CDH` derive `index` purely from the sentinel value `0xFFFFFFFF` appearing in the 32-bit `uncompressed_file_size32_`, `compressed_file_size32_`, and `local_header_offset32_` fields — fields fully controlled by the attacker-supplied ZIP/JAR bytes — without ever checking `z64->attr_count()`: [5](#0-4) [2](#0-1) 

An attacker who supplies a crafted JAR/ZIP (e.g. published as a `java_import`/`http_jar`/`http_file` dependency that ends up merged by `singlejar`, or fed via `combiners.cc`'s `Concatenator::Merge` / `TransientBytes::ReadEntryContents`/`DecompressEntryContents`) can create a Central Directory Header where all three 32-bit size/offset fields are `0xFFFFFFFF` (requesting 3 quads = 24-byte payload) but attach a `Zip64ExtraField` with `payload_size() == 0` or `8` (0 or 1 quad). `ExtraField::find` accepts this because the field's own declared, tiny size fits within `extra_fields_length()` — the mismatch between "how many quad values the flags imply" and "how many quads the payload actually holds" is never checked anywhere in the class. When `local_header_offset()`/`uncompressed_file_size()`/`compressed_file_size()` are subsequently invoked, `attr64(1)` or `attr64(2)` reads 8 bytes past the end of the attacker-declared (and possibly past the end of the allocated/mmap'd) central-directory buffer — a heap-based out-of-bounds read. [2](#0-1) 

The consequence is not merely an info leak: the garbage 64-bit value read out-of-bounds is then used as the authoritative `uncompressed_file_size()`/`compressed_file_size()` for the entry, which downstream flows into `TransientBytes::ReadEntryContents`/`DecompressEntryContents` (`Append(lh->data(), uncompressed_file_size)`), turning a heap-OOB metadata read into an attacker-influenced, wildly oversized copy length used against the (fixed-size) in-memory entry buffer. [6](#0-5) 

This mirrors the CVE-2026-21676 class: a validating/size-parsing routine (`CIccMBB::Validate` there, `CDH`/`Zip64ExtraField` accessors here) trusts an attacker-declared count/size field to index into a buffer whose *actual* allocated size was validated against a different (smaller) declared length, producing a heap buffer overflow.

### Impact Explanation
An attacker who controls the bytes of a ZIP/JAR that a Bazel build ingests (e.g. a `http_jar`/`http_archive`-fetched artifact, or any JAR merged via `singlejar`, which is used pervasively for Java `deploy_jar` construction) can trigger an out-of-bounds heap read whose value then drives a further, attacker-influenced buffer copy size, corrupting the build's in-memory representation of the archive and potentially crashing the build worker or leaking adjacent heap memory into the produced output artifact.

### Likelihood Explanation
Moderate-to-high: `singlejar` is invoked on every Java build that produces a merged/deploy jar, and its ZIP parsing accepts arbitrary attacker-controlled Central Directory/extra-field byte layouts with no cross-validation between the sentinel flags and `Zip64ExtraField`'s declared payload length. No checksum, containment, or lockfile mechanism protects the *contents* of an already-downloaded/trusted-origin JAR from this parsing bug — the flaw is purely in binary-format trust, independent of how the JAR arrived.

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site in `CDH`/`LH`), validate `index < attr_count()` before dereferencing `attr_[index]`, and treat a `Zip64ExtraField` whose `attr_count()` is insufficient for the number of sentinel (`0xFFFFFFFF`) fields present as a corrupt/invalid entry (`error`/`diag_errx`), aborting processing of that JAR entry instead of returning attacker-influenced or uninitialized data.

### Proof of Concept
A `JUnit`/`src/tools/singlejar/*_test.cc`-style test (analogous to the existing `CreateZipWithMalformedExtraField()` helper already present in `output_jar_simple_test.cc`) can construct a CDH with `compressed_file_size32_ = uncompressed_file_size32_ = local_header_offset32_ = 0xFFFFFFFF` and an accompanying `Zip64ExtraField` with `payload_size(0)` (or `8`), then call `cdh->local_header_offset()`/`cdh->uncompressed_file_size()` and observe (under ASan) a heap-buffer-overflow/out-of-bounds-read report from `attr64()`. [7](#0-6)

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

class Zip64ExtraField : public ExtraField {
 public:
  static const Zip64ExtraField* find(const uint8_t* start, const uint8_t* end) {
    return reinterpret_cast<const Zip64ExtraField*>(
        ExtraField::find(1, start, end));
  }

  bool is() const { return is_zip64(); }
  void signature() { ExtraField::signature(1); }

  // The value of i-th attribute
  uint64_t attr64(int index) const { return le64toh(attr_[index]); }
  void attr64(int index, uint64_t v) { attr_[index] = htole64(v); }

  // Attribute count
  int attr_count() const { return payload_size() / sizeof(attr_[0]); }
  void attr_count(int n) { payload_size(n * sizeof(attr_[0])); }

  // Space needed for this field to accommodate n_attr attributes
  static uint16_t space_needed(int n_attrs) {
    return n_attrs > 0 ? sizeof(Zip64ExtraField) + n_attrs * sizeof(uint64_t)
                       : 0;
  }

 private:
  uint64_t attr_[];
} attr_packed;

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
