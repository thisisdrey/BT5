### Title
Accidentally sent ERC20/native tokens are permanently stuck in `Treasury` (and other non-`TokenHolder` contracts) — no recovery path exists - (File: contracts/Treasury.sol)

### Summary
The reference issue class is "contract holds token balances but exposes no emergency/recovery function, so accidentally sent funds are locked forever." Metronome does implement this pattern for some contracts via `TokenHolder.sweep`, but several production contracts that receive or hold token balances — most notably `Treasury` — do not inherit `TokenHolder` and define no `sweep`/`rescue`/`recover` function. Any ERC20 or native token transferred to `Treasury` outside the accounting flow is permanently unrecoverable.

### Finding Description
Metronome centralizes stuck-token recovery in `contracts/utils/TokenHolder.sol`, which exposes `sweep(IERC20 token_, address to_, uint256 amount_)` gated by `_requireCanSweep()` (governor-only in practice). `DepositToken`, `DebtToken`, `NativeTokenGateway`, `VesperGateway`, and `AMO` all inherit it.

However, a grep over the production contracts shows `Treasury.sol`, `RewardsDistributor.sol`, `SmartFarmingManager.sol`, `Operator.sol`, `FeeProvider.sol`, `SyntheticToken.sol`, `MetAirdrop.sol`, and `utils/RecurringAirdrop.sol` contain no `sweep`, `rescue`, or `recover` function and do not inherit `TokenHolder`.

`Treasury` is the strongest analog:

- It is the fee-collection sink of the protocol — fees from deposits, withdrawals, swaps, interest, and liquidations are pushed/pulled into it, so its address is a well-known, token-holding contract that users and integrations can easily fat-finger a transfer to.
- Its balance bookkeeping is based on what the protocol pulls/pushes (and what the fee collector later withdraws via governed functions); a token donated directly to the contract is invisible to that accounting and there is no code path that can send it back out.
- The same applies to `RewardsDistributor` (holds undistributed reward token inventory) and `SmartFarmingManager` (transiently holds swap leftovers/refunds during `leverage`/`flashRepay`): tokens sent directly to either address cannot be extracted by anyone.

This mirrors the Mycelium finding exactly: the contract's meaningful balance is derived from internal accounting, so an externally transferred token (the analog of "accidentally sent LINK") is stranded with no withdrawal path.

### Impact Explanation
Any user (or integrated contract) that transfers ERC20 tokens — or native ETH where a payable path/selfdestruct forces it — directly to `Treasury`, `RewardsDistributor`, or `SmartFarmingManager` loses those funds permanently. No privileged or unprivileged function can recover them. This satisfies the "permanent freezing of funds" impact criterion. Severity is bounded by the same caveat as the original: the loss requires an erroneous external transfer, not an attacker action.

### Likelihood Explanation
Low-to-moderate. It requires a mistaken direct transfer rather than attacker exploitation. That said, these are long-lived, publicly documented contract addresses that routinely handle tokens (fees, rewards, leveraged swap outputs), so mistaken sends and stuck dust accumulate over time — identical to the reported Medium.

### Recommendation
Have `Treasury`, `RewardsDistributor`, and `SmartFarmingManager` inherit `TokenHolder` (with `_requireCanSweep()` requiring the governor, consistent with `VesperGateway`/`NativeTokenGateway`). Optionally guard `sweep` against draining tokens that back live accounting (e.g., reward-token inventory in `RewardsDistributor`, collateral tracked by `DepositToken`) by capping the sweepable amount to `balance - accountedBalance`.

### Proof of Concept
Conceptual (Foundry fork-style) reproduction:

```solidity
// assume mainnet fork, Treasury deployed at `treasury`, any ERC20 `token`
address user = makeAddr("user");
deal(address(token), user, 100e18);

vm.prank(user);
token.transfer(treasury, 100e18); // accidental send

assertEq(token.balanceOf(treasury), >= 100e18);

// No function on Treasury can move `token`:
// - no sweep/rescue/recover selector exists in Treasury.sol
// - Treasury does not inherit TokenHolder
// All governor/feeCollector paths only operate on protocol-tracked flows,
// so the 100e18 remains at the contract address forever.
```

Same test applies swapping `treasury` for `RewardsDistributor` or `SmartFarmingManager` addresses. Note: I verified via code search that none of these contracts declare a recovery function; I did not fully trace every external-transfer-out path in `Treasury.sol`, so if a governed "pull" or `transferOut`-style function exists that accepts an arbitrary token+recipient, the Treasury instance specifically may be partially mitigated — but no such selector surfaced in the search, and `RewardsDistributor`/`SmartFarmingManager` remain unaffected regardless.
