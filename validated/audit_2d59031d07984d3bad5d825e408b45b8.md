### Title
Unbounded asset-issue enumeration in `Wallet.getAssetIssueList()` allows permissionless growth of a query result set that a full node must fully materialize on every call - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`AssetIssueContract` is a permissionless, broadcastable transaction type: any funded account can call it to create a new asset via `AssetIssueActuator`. Each created asset is written to `AssetIssueStore`/`AssetIssueV2Store` and is never removed. The read API `Wallet.getAssetIssueList()` iterates over **every** asset ever issued on the chain, with no offset/limit, calling `BandwidthProcessor.updateUsage()` per item and building a full protobuf response in memory. [1](#0-0) 

### Finding Description
`AssetIssueActuator.execute()`/`validate()` let any account issue a new token by paying the asset-issue fee; there is no cap on the total number of distinct assets that can exist on the chain over time, only per-issuance limits (e.g. frozen-supply count). [2](#0-1) 

The paginated variant `getAssetIssueList(long offset, long limit)` correctly bounds work via `getAssetIssuesPaginated`, but the no-argument overload does not:
```java
public AssetIssueList getAssetIssueList() {
  BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
  AssetIssueList.Builder builder = AssetIssueList.newBuilder();
  getAssetIssueStoreFinal(...).getAllAssetIssues()
      .forEach(issueCapsule -> {
        processor.updateUsage(issueCapsule);
        builder.addAssetIssue(issueCapsule.getInstance());
      });
  return builder.build();
}
``` [1](#0-0) 

This full-scan variant is wired into multiple externally reachable endpoints (gRPC `GetAssetIssueList`, `/wallet/getassetissuelist` HTTP servlet, and the equivalent Solidity/PBFT node servlets), all of which are unauthenticated, publicly reachable query paths. [3](#0-2) 

This is the same bug class as the reported `massUpdatePools()` issue: a loop whose iteration count is driven by a collection that grows without bound as a side effect of ordinary, permissionless transactions (asset issuance here, pool creation there), with no per-call limit or pagination enforced on the unbounded code path.

### Impact Explanation
As the number of issued assets grows over the life of the chain (issuance is cheap and unrestricted other than a fee), each call to the unbounded `getAssetIssueList()` does more work: deserializing every `AssetIssueCapsule`, running `BandwidthProcessor.updateUsage()` on each, and serializing the full list into one response. Because this endpoint is exposed on full/solidity/PBFT nodes without offset/limit, it can degrade or stall query-serving threads on the affected node as the asset count increases, and a burst of concurrent requests to this endpoint amplifies CPU/memory pressure, degrading the node's ability to serve other API requests ("an API the node can no longer serve").

### Likelihood Explanation
Likelihood is moderate: it requires the total number of issued assets to become large enough to make full enumeration expensive, and/or repeated/concurrent calls to the endpoint by any anonymous API client. Since asset issuance itself is inexpensive and permissionless, an attacker can also proactively inflate the dataset by issuing many low-value assets to accelerate the effect, then repeatedly hit the unpaginated endpoint.

### Recommendation
- Deprecate/remove the unpaginated `getAssetIssueList()` code path (and its gRPC/HTTP wiring) in favor of the already-existing paginated `getAssetIssueList(offset, limit)`, or internally cap/paginate it with a hard-coded maximum count.
- If backward compatibility must be preserved, enforce a maximum default page size server-side and document that the caller must page through results.

### Proof of Concept
1. Broadcast many `AssetIssueContract` transactions from different funded accounts to grow the total number of assets in `AssetIssueStore`/`AssetIssueV2Store` (each is a normal, permissionless transaction handled by `AssetIssueActuator`).
2. Repeatedly call the unpaginated `GetAssetIssueList` gRPC method or `/wallet/getassetissuelist` HTTP endpoint on the target full node.
3. Observe that response latency and resource usage scale linearly with total asset count and that concurrent calls can starve the node's request-handling threads, degrading its ability to serve other API requests — with no way for an operator to mitigate other than restarting/hardening the node, since the vulnerable code path has no built-in limit.
