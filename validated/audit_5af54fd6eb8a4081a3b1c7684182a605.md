### Title
Newline smuggling via unvalidated `--glob=`/`--branches=`/`--tags=` suffix allows rev-list `--stdin` argument injection in `ObjectsSize` - (File: internal/gitaly/service/repository/objects_size.go)

### Summary
`ObjectsSize` validates each streamed revision with `git.ValidateRevision(revision, git.AllowPseudoRevision())` before writing `revision + "\n"` to `git rev-list --stdin`'s stdin pipe. The `AllowPseudoRevision` branches for `--glob=`, `--branches=`, and `--tags=` return `nil` immediately via `bytes.HasPrefix` without ever reaching the later whitespace/newline check, so an attacker-controlled suffix after the `=` may contain an embedded newline, letting a single "revision" value be split into two lines once written to the child process's stdin.

### Finding Description
In `internal/git/revision.go`, `ValidateRevision` first checks pseudo-revision prefixes when `AllowPseudoRevision()` is set: [1](#0-0) 
These `bytes.HasPrefix` matches (`--branches=`, `--tags=`, `--glob=`) return `nil` unconditionally, before the function reaches the whitespace/newline rejection at: [2](#0-1) 
That whitespace check is only applied to the non-pseudo-revision path, meaning a value like `"--glob=*\n--some-other-arg"` passes validation entirely.

In `ObjectsSize`, each validated revision is written to the `rev-list --stdin` pipe with an appended `\n`: [3](#0-2) 
Because git-rev-list's `--stdin` mode treats each line of standard input as if it were an additional command-line argument (not merely a revision), an attacker who sends the single gRPC field `revision = "--glob=*\n--some-flag"` causes two effective lines/arguments to be fed to `rev-list`: `--glob=*` and `--some-flag`, the latter being fully attacker-controlled and not subject to any of the leading-dash, whitespace, colon, or backslash restrictions that apply to ordinary revisions elsewhere in `ValidateRevision`. This breaks the intended invariant that `AllowPseudoRevision()` only lets through a small fixed allowlist of pseudo-revision tokens — the glob/branches/tags variants effectively bypass all further validation for their suffix.

### Impact Explanation
This is an argument-injection style vulnerability into `git rev-list`'s stdin option-processing, not a shell/OS command execution primitive. The practical impact is scoped to whatever arguments `git-rev-list` accepts when fed via `--stdin` (e.g. additional pseudo-revisions/exclusions, or ref-selection options such as `--exclude=`, further `--glob=` patterns, etc.), all operating within the same repository the RPC already targets. There is no cross-repository access, no arbitrary file write/read demonstrated, and no shell metacharacter execution, since `repo.Exec` invokes `git` directly via `exec.Command`-style argv, not a shell. The confirmed impact is limited to bypassing the revision syntax allowlist for `--glob=`/`--branches=`/`--tags=` prefixed pseudo-revisions, allowing an extra rev-list line/argument to be smuggled in — a validation bypass with unclear further exploitability, since I was not able to confirm within this repo (docs/tests) that any rev-list stdin-only option grants file write, cross-repo disclosure, or command execution.

### Likelihood Explanation
Reaching the vulnerable code only requires an unprivileged, authenticated caller of the `ObjectsSize` RPC — no special role is needed, as this RPC is reachable by any client that can issue Gitaly RPCs for a repository it can access. The bypass condition (supplying a `--glob=`/`--branches=`/`--tags=` prefixed value containing an embedded newline) is straightforward to construct at the protobuf field level, since gRPC string fields are not restricted to single lines.

### Recommendation
Apply the whitespace/NUL/backslash/colon validation to the suffix after `--glob=`, `--branches=`, and `--tags=` before returning `nil` in `ValidateRevision`'s pseudo-revision branch, or explicitly reject any embedded newline/CR in these suffixes so that a single revision value cannot be smuggled into multiple `rev-list --stdin` lines.

### Proof of Concept
```go
func TestValidateRevision_GlobNewlineBypass(t *testing.T) {
    err := git.ValidateRevision([]byte("--glob=*\n--exclude=refs/heads/*"), git.AllowPseudoRevision())
    require.NoError(t, err) // currently passes, demonstrating the smuggled newline is not rejected
}
```
At the RPC level, a client streaming `ObjectsSizeRequest{Revisions: []string{"--glob=*\n--exclude=refs/heads/*"}}` to `ObjectsSize` would have this single revision string written as two lines to `git rev-list --stdin`'s stdin, injecting the second line as an independent argument to `git-rev-list`.
