### Title
Unbounded growth of `DelegatedResourceAccountIndex` list via repeated 1-TRX `FreezeBalanceContract` delegations — state-bloat DoS ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
The legacy resource-delegation path in `FreezeBalanceActuator` lets any account append an unbounded number of entries to the `toAccounts`/`fromAccounts` repeated field of a single `DelegatedResourceAccountIndexCapsule`, at the minimum cost of only 1 TRX per unique receiver address (fully recoverable later via unfreeze). This mirrors the external report's bug class: no cap on the number of cheap, repeatable state-mutating calls a single user can make, letting an attacker grow a data structure without bound.

### Finding Description
When a `FreezeBalanceContract` is submitted with a `receiverAddress` (delegating BANDWIDTH/ENERGY) and `dynamicStore.supportAllowDelegateOptimization()` is `false`, `FreezeBalanceActuator.delegateResource` mutates the owner's and receiver's `DelegatedResourceAccountIndexCapsule` by unconditionally calling `addToAccount` / `addFromAccount` for every new, distinct receiver address: [1](#0-0) 

`DelegatedResourceAccountIndexCapsule.addToAccount` / `addFromAccount` simply append to the protobuf repeated field with no size limit: [2](#0-1) 

`validate()` only enforces `frozenBalance >= 1 TRX` and `frozenCount == 0 or 1` for the *owner's own* frozen slot — it places no limit whatsoever on how many *distinct receiver addresses* an owner may delegate to, nor any limit on how large the `toAccounts`/`fromAccounts` lists may grow: [3](#0-2) 

A test in the codebase confirms the list can already be grown to at least 100+ entries with no rejection, and each unique receiver simply gets appended: [4](#0-3) 

Because each iteration only needs a brand-new receiver account (cheap to create) and 1 TRX of frozen balance (which the attacker can later `unfreezeBalance` to recover), an attacker can drive this loop indefinitely at very low net cost, continuously growing the serialized size of a single `DelegatedResourceAccountIndexCapsule` record read/written on the owner's/receiver's key in `DelegatedResourceAccountIndexStore`.

This is functionally analogous to the reported `SolverVault` issue: there is no minimum/maximum bound preventing a single user from repeatedly invoking a state-mutating entrypoint at negligible cost, causing an ever-growing on-chain data structure.

Caveat: this legacy delegation branch is only reachable while `dynamicStore.supportUnfreezeDelay()` is `false` (i.e., before the FreezeBalanceV2/committee proposal that disables the old freeze API is activated) — `validate()` explicitly rejects the old `FreezeBalanceContract` once that proposal is turned on: [5](#0-4) 
On networks/forks where that committee parameter has not yet been enabled (or where `supportAllowDelegateOptimization` is also disabled), the vulnerable code path is fully reachable via a signed transaction from any unprivileged account.

### Impact Explanation
Repeated growth of a single `DelegatedResourceAccountIndexCapsule` record increases the cost of every subsequent read/write/(de)serialization of that key in `DelegatedResourceAccountIndexStore`, and of any code path that loads the full index (e.g. further freeze/unfreeze/delegate calls touching the same owner or receiver, `Wallet.getDelegatedResourceAccountIndex`). An attacker who repeats this thousands of times against a single target address (or against the node's global DB) can inflate per-key storage/CPU cost with negligible locked capital, degrading node performance for anyone interacting with the affected account and bloating the chain's persistent state permanently once the freeze-balance operations are confirmed on-chain.

### Likelihood Explanation
The attack requires only a signed `FreezeBalanceContract` transaction with a `receiverAddress`, 1 TRX of frozen balance, and a fresh receiver account — all cheap and fully within an unprivileged user's capability. It is only gated by the network having `supportUnfreezeDelay()` disabled (old freeze API still active), which limits it to chains/forks that haven't yet enabled that specific committee proposal.

### Recommendation
- Cap the number of distinct entries allowed in a single `DelegatedResourceAccountIndexCapsule`'s `toAccounts`/`fromAccounts` list (e.g., via a dynamic-property-configurable max), rejecting `FreezeBalanceContract`/delegate calls once the cap is reached.
- Alternatively, ensure the legacy, unbounded-list delegation path is fully retired (not just conditionally guarded) so it can never be reached regardless of committee-parameter state, consistent with the V2 delegate model which uses per-pair fixed DB keys instead of an in-place growing list.

### Proof of Concept
1. Deploy/target a java-tron network where `supportUnfreezeDelay()` is `false` and `supportAllowDelegateOptimization()` is `false`.
2. From account `A` with balance ≥ N TRX, generate N fresh receiver addresses `R1..RN` and fund/register them as accounts.
3. For each `Ri`, submit a `FreezeBalanceContract{ownerAddress=A, receiverAddress=Ri, frozenBalance=1_000_000 (1 TRX), resource=BANDWIDTH}` transaction.
4. Each call passes `validate()` (only checks `frozenCount == 0 or 1` for A's own frozen slot, not the delegation list size) and appends `Ri` to `A`'s `DelegatedResourceAccountIndexCapsule.toAccounts` list, and `A` to `Ri`'s `fromAccounts` list, per `FreezeBalanceActuator.delegateResource` [1](#0-0) .
5. Repeat for large N (e.g. 10,000+) — the list on `A`'s index record grows unbounded, exactly as demonstrated for smaller N in `testMultiFreezeDelegatedBalanceForBandwidth` [4](#0-3) , at a total cost of only N TRX (recoverable later via unfreeze) plus transaction fees.

  public void addFromAccount(ByteString fromAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addToAccounts(toAccount)
        .build();
  }

      List<ByteString> toList = new ArrayList<>(getToAccountsList());
