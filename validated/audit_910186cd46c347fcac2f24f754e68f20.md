### Title
Unstaked attacker can starve TPU connection admission via half-open QUIC handshakes that never trip pre-accept rate limiters - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server`'s pre-accept checks (`overall_connection_rate_limiter.current_tokens() == 0` and `rate_limiter.is_allowed(ip)`) are non-consuming "peeks" against token buckets that are only ever decremented in `setup_connection` *after* a handshake fully completes via `register_connection`/`consume_tokens`. An attacker who never completes the handshake never causes these buckets to drain, so the peeks always pass, letting the attacker acquire an unbounded stream of `ClientConnectionTracker` slots (bounded globally by `qos.max_concurrent_connections()`, shared across staked and unstaked peers) and hold each for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) before timing out.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-407`), for every incoming QUIC connection attempt the server:
1. Peeks `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
2. Peeks `rate_limiter.is_allowed(&ip)` [2](#0-1) 
3. Grabs a `ClientConnectionTracker` slot bounded by `qos.max_concurrent_connections()` [3](#0-2) 
4. Increments `outstanding_incoming_connection_attempts`, calls `incoming.accept()`, and spawns `setup_connection` which waits up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) for the handshake to finish [4](#0-3) 

Critically, both `rate_limiter.is_allowed` and the overall bucket's `current_tokens()` are **read-only peeks** — `ConnectionRateLimiter::is_allowed` explicitly does not mutate state [5](#0-4) . Token consumption (`register_connection` → `consume_tokens`, and `overall_connection_rate_limiter.consume_tokens(1)`) only happens inside `setup_connection` **after** the QUIC handshake successfully resolves (`Ok(new_connection)` branch) [6](#0-5) . If the attacker never lets the handshake finish (e.g., completes the transport-level `Connecting` future poorly, stalls key exchange, or simply lets it run to the 2s timeout), neither rate limiter bucket is ever debited, so the pre-accept peeks against them never trip. This defeats the “protect against connection attempt bursts with a global rate-limiter” and “rate-limit abusive peers by IP” goals stated in the code's own comment [7](#0-6) .

The one bound that *does* apply pre-handshake is `ClientConnectionTracker::new(stats, qos.max_concurrent_connections())`, which checks `stats.open_connections` against a single global cap shared by staked and unstaked connections [8](#0-7) . For `SwQos`, this cap is `(max_staked_connections + max_unstaked_connections) * 5 / 4` [9](#0-8)  and for `SimpleQos` it is `max_staked_connections * 5 / 4` [10](#0-9) . An attacker holding just above that many concurrent half-open connections continuously (refreshing them as each 2s timeout expires) keeps `open_connections` pinned at the cap, so `ClientConnectionTracker::new` fails for *all* new connection attempts — including from legitimate unstaked clients and even staked clients — via the `refused_connections_too_many_open_connections` path [3](#0-2) , before `qos.try_add_connection` is ever invoked.

Note: since `ClientConnectionTracker` acquisition happens before `incoming.accept()` and before any IP-ownership assertion, and a single attacker IP is not concurrency-limited by anything else at that point (the per-IP `ConnectionRateLimiter` is rate-based on completed handshakes, not a concurrency cap on in-flight attempts), one attacker source can occupy this shared pool without needing many source IPs.

### Impact Explanation
This is a denial-of-service against TPU connection admission: an unstaked, unprivileged attacker can exhaust the shared `max_concurrent_connections` pool with cheap, intentionally-incomplete QUIC handshakes, causing legitimate unstaked (and potentially staked) senders to be refused connections (`refused_connections_too_many_open_connections`) or to experience `connection_setup_timeout`/`outstanding_incoming_connection_attempts` starvation, prior to any QoS/stake-based admission control (`qos.try_add_connection`) ever running. This matches the "grossly underpriced pre-fee work" / QoS-evasion / DoS bounty category since the attacker spends only the cost of opening TCP/UDP-level QUIC handshakes (no fee, no stake, no valid transaction) to deny capacity that legitimate fee-paying or staked transaction senders would otherwise use.

### Likelihood Explanation
Preconditions match exactly what's allowed: an unstaked remote attacker with the ability to open many concurrent QUIC connections to the public TPU port. No control over gossip, stake, or validator config is required. The attack is fully client-controlled — simply refrain from completing the crypto handshake (or delay past the point where the server observes `Connecting` resolve) for each of many concurrently opened connections, and keep replenishing them every ~2s as the `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` expires. This is repeatable indefinitely with modest bandwidth/socket resources, since `max_concurrent_connections` defaults are bounded (a few thousand at most based on `DEFAULT_MAX_STAKED_CONNECTIONS`/`DEFAULT_MAX_UNSTAKED_CONNECTIONS`), well within reach of a single attacking host with modest concurrency.

### Recommendation
- Debit (or reserve) a token from `overall_connection_rate_limiter` and per-IP `ConnectionRateLimiter` at accept time (before handshake) rather than only after a successful handshake, refunding on early failure if desired, so that in-flight (not just completed) handshake volume is bounded per source and globally.
- Split `qos.max_concurrent_connections()`/`ClientConnectionTracker` accounting so unstaked pre-handshake slots cannot starve out staked or track separately from post-handshake admitted connections, and/or apply a per-IP cap on concurrently *outstanding* (not-yet-handshaken) connections independent of the completed-handshake rate limiter.
- Consider shortening `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or applying a stricter per-IP outstanding-attempt cap enforced at `incoming.accept()` time.

### Proof of Concept
Integration test plan (extending existing test harness in `streamer/src/nonblocking/quic.rs` tests, e.g. `setup_quic_server`/`SwQosConfig`):
```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_half_open_handshake_starves_legit_client() {
    let SpawnTestServerResult { join_handle, receiver, server_address, stats, cancel } =
        setup_quic_server(
            None,
            QuicStreamerConfig::default_for_tests(),
            SwQosConfig {
                max_staked_connections: 4,
                max_unstaked_connections: 4, // small pool: max_concurrent_connections = (4+4)*5/4 = 10
                ..SwQosConfig::default_for_tests()
            },
        );

    // Attacker: open just over max_concurrent_connections UDP sockets that send only
    // a QUIC Initial packet and then go silent (never completing handshake).
    let attacker_conns: Vec<_> = (0..12)
        .map(|_| spawn_half_open_connection_attempt(server_address))
        .collect();

    // Wait a bit (< 2s handshake timeout) then attempt a legitimate connection.
    tokio::time::sleep(Duration::from_millis(500)).await;
    let legit_result = make_client_endpoint(&server_address, None).await; // should time out / be refused

    // Assertions: refused_connections_too_many_open_connections > 0,
    // outstanding_incoming_connection_attempts saturated at max_concurrent_connections,
    // and legit_result fails/times out while attacker never trips
    // connection_rate_limited_across_all / connection_rate_limited_per_ipaddr.
    assert!(stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0);
    assert_eq!(stats.connection_rate_limited_per_ipaddr.load(Ordering::Relaxed), 0);

    cancel.cancel();
    drop(receiver);
    join_handle.await.unwrap();
}
```
`spawn_half_open_connection_attempt` would use a raw UDP socket or a quinn client configured to stall the TLS handshake (e.g., drop after sending Initial) to keep the server-side `Connecting` future pending near the 2s timeout, repeating just before each connection times out to keep the pool saturated.

    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
