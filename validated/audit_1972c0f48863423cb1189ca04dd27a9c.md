## Title
Cross-StackerDB Chunk Replay via Contract-Unbound Signature Verification — (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The StackerDB chunk-authentication scheme signs and verifies only `(slot_id, slot_version, data_hash)` — it never binds the signature to the specific StackerDB contract (`QualifiedContractIdentifier`) the chunk is destined for. Because Stacks signer nodes provision multiple sibling StackerDB replicas (`signers-<signer_set>-<message_id>`) that all share the *exact same* slot→signer-address assignment for a given `signer_set` (derived from the single `.signers` contract's `stackerdb-get-signer-slots-page`), a chunk that is validly signed and accepted into one lane's replica (e.g. `signers-0-1`) can be captured by any observer and unsolicitedly re-submitted, verbatim, as belonging to a *different* sibling contract (e.g. `signers-0-2`). `PeerNetwork::validate_received_chunk` will accept it because it never checks that the signature commits to the target `smart_contract_id`.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest as: [1](#0-0) 

and `SlotMetadata::verify()` / `StackerDBChunkData::verify()` only check that this digest recovers to the expected signer address — with no reference to which StackerDB contract the chunk belongs to: [2](#0-1) [3](#0-2) 

The node-side acceptance path, `PeerNetwork::validate_received_chunk`, is passed `smart_contract_id` but uses it only to look up the expected signer address for that slot — it never folds `smart_contract_id` into the signature check: [4](#0-3) 

This is invoked directly from the unsolicited push-chunk handler, which is remotely reachable from any connected peer without authentication: [5](#0-4) 

Critically, in the Nakamoto signer boot contracts, every message-type lane within a given `signer_set` (0 or 1) reuses the *same* signer→slot assignment, because `signers-<set>-<message_id>.clar` simply forwards to the shared `.signers` contract's page lookup, which is keyed only by `signer_set`, not `message_id`: [6](#0-5) [7](#0-6) 

So a signer occupying slot `X` in `signers-0-1` (e.g. the `BlockResponse` lane) occupies the identical slot `X` in `signers-0-2`, `signers-0-3`, etc. (all other lanes for that same signer set). Because the signature never commits to which of these sibling contracts it authorizes, a `StackerDBChunkData` legitimately observed on lane A (its `slot_id`, `slot_version`, `sig`, `data` are all public — they are gossiped/served over the p2p StackerDB inventory/get-chunk protocol) can be repackaged by any remote, unauthenticated peer into a `StackerDBPushChunkData` addressed at lane B's `contract_id`, and it will pass `validate_received_chunk`'s signer check, `TooManySlotWrites` check, and staleness check as long as B's expected version for that slot has not exceeded the replayed `slot_version`. The chunk is then written into lane B's on-disk replica via `StackerDBTx::try_replace_chunk`, and forwarded/broadcast to other peers as legitimate data for lane B.

This is a direct analog of the CVE-2025-59941 bug class: verification results (here, a signature over `slot_id`/`slot_version`/`data_hash`) are treated as valid without checking the full context (which specific StackerDB/contract the chunk is destined for), allowing reuse of an authentic artifact in a context where it should not be considered valid.

### Impact Explanation
This allows an unauthenticated, remote peer (no private key required) to overwrite a sibling StackerDB lane's slot with data that was never authorized for that lane, and to have it propagated network-wide as though it were legitimately signed content for that contract. Concretely:
- It corrupts state served/stored by the StackerDB replication layer, which is used by Nakamoto signer message lanes (`signers-<set>-<message_id>`), i.e. unauthorized write to StackerDB replicated state and network-wide propagation of misplaced/forged-context data.
- Depending on which lane is targeted (e.g. `BlockResponse` vs `Transactions` vs `DKG`), overwriting the current version with stale/foreign bytes can suppress the propagation of the legitimate current chunk for that lane until the true signer bumps the slot version again, degrading signer coordination liveness.

This matches the "High"/"Critical" categories in scope: unauthenticated/unauthorized write to StackerDB, and network-wide propagation of data outside its authorized context.

### Likelihood Explanation
Exploitation requires no secret key and no elevated privilege — only observing a legitimate chunk on one lane (trivial, since StackerDB chunks/inventories are openly served to any peer) and resubmitting it as an unsolicited push to another sibling contract that shares the same slot assignment. The `validate_received_chunk` gate that would need to be bypassed (`data_hash`/signature check) is inherently satisfied because the replayed bytes are byte-for-byte identical to a genuinely signed chunk — only the `contract_id` field of the outer message differs.

### Recommendation
Bind the signed digest to the specific StackerDB contract, e.g. include the `QualifiedContractIdentifier` (or a fixed-size hash of it) in `SlotMetadata::auth_digest()`, and thread the target `contract_id` through `sign()`/`verify()`/`recover_pk()` so that a chunk's signature is only valid for the exact StackerDB it was produced for. This requires plumbing the contract identifier into `libstackerdb::SlotMetadata` and `StackerDBChunkData`, and updating all signer/miner call sites that call `sign()`/`verify()` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`, `stacks-signer/src/client/stackerdb.rs`, etc.) to pass the correct contract context.

### Proof of Concept
1. Configure/observe a Nakamoto network where signer set 0 has at least two sibling stacker-DB lanes, e.g. `signers-0-1` (BlockResponse) and `signers-0-2` (Transactions), both with the same signer at `slot_id = 2`.
2. Capture a legitimately-signed `StackerDBChunkData { slot_id: 2, slot_version: 5, sig, data }` served by any node for `signers-0-1` (via `StackerDBGetChunkData` — publicly servable).
3. Craft a `StackerDBPushChunkData { contract_id: signers-0-2, rc_consensus_hash: <current>, chunk_data: <captured chunk> }` and send it unsolicited to a victim peer, as handled in `PeerNetwork::handle_unsolicited_StackerDBPushChunk`.
4. Observe that `validate_received_chunk` accepts it (assuming lane B's tracked version for slot 2 is `< 5`), the chunk inventory for `signers-0-2` slot 2 is patched to version 5, and the victim buffers/forwards it as legitimate `signers-0-2` content — even though it was never signed for that contract.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }
