### Title
Unbounded array-length read from attacker-controlled calldata in `ValidateMultiSign`/`BatchValidateSign` precompiles causes uncaught out-of-bounds exception during pre-activation execution - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The netpbm CVE-2017-2579 root cause is that `expandCodeOntoStack()` takes an attacker-controlled length/code value from file data and uses it to index/loop without validating it against the actual buffer bounds, causing an out-of-bounds read. The same bug class exists in java-tron's `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` helpers used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts: an attacker-controlled length field taken directly from calldata (`words[offset].intValueSafe()`) is used as a loop bound to index into the `words[]` array without validating it against `words.length`.

### Finding Description
`extractBytes32Array` reads a length directly from calldata with no bound check at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` add a shallow guard (`offset > words.length - 1`) that only validates the *offset* pointing at the length word, but the `len` value read from that word is still used unbounded in the following loop, so `words[offset + i + 1]` can walk past the end of the array: [2](#0-1) 

Both `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` call these helpers with offsets/lengths computed straight from attacker-controlled calldata words: [3](#0-2) [4](#0-3) 

`BatchValidateSign.execute` wraps `doExecute` in a `catch (Throwable t)` that swallows any resulting exception, so it is safe: [5](#0-4) 

However, `ValidateMultiSign.execute` has **no such enclosing try/catch** — its inner try/catch only starts after the length is read and the array is extracted (line ~1082), so an `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown while computing `sigArraySize` or inside `extractBytesArray`/`extractSigArray` propagates uncaught out of `ValidateMultiSign.execute`. `Program.callToPrecompiledAddress` invokes `contract.execute(data)` directly with no try/catch around it: [6](#0-5) 

The codebase's own tests confirm this is a live, acknowledged gap that is only masked by a hard-fork-gated ABI-encoding validation (`VMConfig.allowTvmOsaka()` + `isValidAbiEncoding`), and that pre-activation the legacy (vulnerable) decoding path is explicitly still reachable and can throw: [7](#0-6) 

The mitigating `isValidAbiEncoding` check is gated behind `VMConfig.allowTvmOsaka()`: [8](#0-7) 

### Impact Explanation
On networks/nodes where the Osaka feature flag has not yet activated (or is disabled), a smart contract can `CALL` the `ValidateMultiSign` precompile address with crafted calldata whose length field (`words[3]`/derived offset) is set so the computed array length overflows the actual calldata bounds. This raises an uncaught `ArrayIndexOutOfBoundsException` (or similar) inside `contract.execute(data)`, which is not caught anywhere between `PrecompiledContract.execute` and `Program.callToPrecompiledAddress`. Depending on how far up the exception propagates before being caught by the top-level VM/actuator exception handling, this can manifest as an unexpected runtime exception during transaction/contract execution rather than the intended graceful revert-with-zero behavior that `BatchValidateSign` and other precompiles implement. This is a reachable input-validation defect in a broadcastable-contract-call code path (any account can invoke this precompile via a `CALL`), directly analogous to the missing bounds check described in CVE-2017-2579.

### Likelihood Explanation
High reachability: any unprivileged account can deploy or call a contract that issues a `CALL` opcode to the `ValidateMultiSign` precompile address with attacker-chosen calldata — no special privilege is required. The precondition is that `VMConfig.allowTvmOsaka()` is not yet enabled (i.e., pre-hardfork state, or any future chain/testnet that hasn't activated it), which the project's own tests document as the "pre-activation" behavior still reachable in the current code.

### Recommendation
Add the same defensive bound check used by `extractBytesArray`/`extractSigArray` to `extractBytes32Array`, and additionally clamp/validate the `len` value read from calldata against the true remaining size of `words[]` in all three helpers (not just the entry offset). Independently of the `allowTvmOsaka`-gated ABI validation, wrap `ValidateMultiSign.execute`'s parsing/extraction logic (mirroring `BatchValidateSign.execute`'s `try { doExecute } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` pattern) so malformed calldata always fails gracefully instead of throwing, regardless of hard-fork activation state.

### Proof of Concept
Construct calldata for `ValidateMultiSign` (`validatemultisign(address,uint256,bytes32,bytes[])`) where the offset word (`words[3]`) points at a valid in-bounds word, but that word's value (interpreted as the array length by `extractBytesArray`/`extractSigArray`, or in `extractBytes32Array`'s callers via `BatchValidateSign`) is set to a large value (e.g., `0x7fffffff`) while `VMConfig.allowTvmOsaka()` is disabled (default/legacy state) and `VMConfig.allowTvmSelfdestructRestriction()` is disabled (skips the `MAX_SIZE` pre-check). Calling this precompile from a contract's `CALL` opcode drives execution into `extractBytesArray`, whose loop `words[offset + i + 1]` runs past the actual `words.length`, throwing an uncaught `ArrayIndexOutOfBoundsException` that is not intercepted by `ValidateMultiSign.execute` or `Program.callToPrecompiledAddress`. This is confirmed as the documented "existing behaviour" pre-activation by the project's own `testTip854PreActivationNoOp` test in `ValidateMultiSignContractTest.java` (lines 244-260), which explicitly expects a `RuntimeException` may be thrown from this path.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }

          SIG_LENGTH);
    }
