### Title
Out-of-bounds heap read in central directory parsing due to unchecked pointer arithmetic - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` (`third_party/ijar/zip.cc:493-545`) parses central directory records and their extra-field sub-records without any bounds checking against the mapped input file's length, unlike `ProcessLocalFileEntry` and `SkipFile`/`ProcessFile`, which explicitly call `EnsureRemaining()` before every pointer advance [1](#0-0) . In the central directory extra-field loop, `header_id`/`data_size` are read via `get_u2le(extra_p)` and `extra_p += data_size` in a `while (extra_p != p)` loop with no check that `data_size` stays within the declared `extra_field_length` region or within the mmap'd file bounds [2](#0-1) .

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, `file_comment_length` directly from attacker-controlled central-directory-header bytes and advances the cursor `p` by these values without verifying they don't run past the end of the mapped file buffer (`zipdata_in_` / `central_dir_`) [3](#0-2) . This differs from `ProcessLocalFileEntry`, which guards every field read with `EnsureRemaining(...)` [4](#0-3) . Crucially, the extra-field sub-record loop that parses ZIP64 fields (`header_id`, `data_size`, and reading `get_u8le(extra)` for size/offset overrides) has no bound at all relative to `extra_field_length` or the buffer end — a crafted `data_size` can make `extra_p` overshoot `p`, causing the loop to either read arbitrary heap memory beyond the mmap'd region as fake header/size fields, or loop indefinitely comparing pointers that never become equal, or wrap around and read out-of-bounds when interpreting the ZIP64 fields via `get_u8le` [5](#0-4) . `FindZipCentralDirectory` establishes the central directory offset from EOCD fields but only checks `central_dir_offset + central_dir_size > in_length` for the header start, not for each individual entry's declared lengths [6](#0-5) , so a crafted archive (consumed via `http_archive`/`download_and_extract` → ijar zip extraction path documented in `tools/build_defs/repo/http.bzl`) can trigger this heap over-read during central directory traversal.

### Impact Explanation
An out-of-bounds heap read while parsing a crafted ZIP central directory can crash the ijar/zip extraction process (`extract`/`ProcessAll` in `third_party/ijar/zip_main.cc`) used by Bazel's archive extraction tooling, or leak adjacent heap memory into subsequently emitted filenames/attrs if bytes are copied out. This mirrors the CVE-2018-1056 bug class: an OOB heap read while walking ZIP structural metadata (there, the central directory/extra fields in advzip; here, the equivalent unmet bounds check in ijar's central directory extra-field walk).

### Likelihood Explanation
Reachable purely through content an unprivileged attacker controls (a hostile or compromised URL/mirror serving a crafted `.zip`/`.jar` referenced by `http_archive`), no local access or credentials required. However, note that `http_archive` in this codebase enforces a `sha256`/`integrity` check on the downloaded archive bytes before extraction (per `docs/versions/8.1.1/rules/lib/repo/http.mdx`), which is the same checksum gate CVE-2018-1056-style flaws are usually run behind — an attacker would need to publish the malicious archive matching the pinned digest scenario, or this path is only reachable when no checksum is pinned. I was not able to fully confirm from the index whether ijar's zip.cc is invoked in the `download_and_extract` code path (I found references to it in `zip_main.cc`/singlejar tooling but did not trace the exact Java `DecompressorValue`/zip extraction implementation used for repository rules, which appears to be a separate Java-based decompressor not indexed here).

### Recommendation
Add `EnsureRemaining`-style bounds checks in `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, `file_comment_length` bytes and before/during the extra-field sub-record loop, ensuring `extra_p + data_size` never exceeds `p` (bound of the extra field) nor the overall mapped buffer end.

### Proof of Concept

A background Devin session with full repo access would be needed to confirm the exact extraction code path invoked for untrusted `http_archive` zips and to write a concrete `BuildIntegrationTestCase` or `zip_test.cc`-based crafted-central-directory test case triggering the OOB read.
