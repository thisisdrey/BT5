Audit Report

## Title
Relayer reward paid on `submit_delivery_receipt` regardless of the on-chain `success` flag in the `DeliveryReceipt` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries an explicit `success: bool` field, but `Pallet::process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` never reads or branches on it before calling `T::RewardPayment::register_reward` and `<PendingOrders<T>>::remove(nonce)`. This means relayer rewards for message delivery are settled identically whether the dispatched command actually succeeded or failed on Ethereum.

## Finding Description
The `DeliveryReceipt` struct explicitly decodes a `success` field from the `InboundMessageDispatched` Ethereum log via `TryFrom<&Log>` [1](#0-0)  and the decode logic sets it from `event.success` [2](#0-1) .

In `process_delivery_receipt`, only three checks are performed: gateway address match, existence of `PendingOrders` entry for the nonce, and (via `submit_delivery_receipt`) the Merkle/Ethereum proof validity through `T::Verifier::verify`. The `receipt.success` field is never referenced: [3](#0-2) . A grep across the entire `outbound-queue-v2` pallet crate (including `mock.rs` and `test.rs`) confirms the string `success` does not appear anywhere outside the primitives crate that decodes it — the field is fully unused after decoding.

The reward payout (`T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)`) and the settlement action (`<PendingOrders<T>>::remove(nonce)`) both execute unconditionally once a valid nonce/order and gateway match are found, regardless of whether the dispatched command reverted on the Ethereum Gateway contract.

## Impact Explanation
This matches the "duplicate settlement or payout" / "underpriced work" impact category: relayers are paid the full fee for delivering a message whose execution failed on Ethereum, exactly the same as for a successful execution. This removes the economic incentive design implied by encoding `success` in the ABI event and pallet's `DeliveryReceipt` struct, and represents a payout that is not conditioned on the underlying operation's actual outcome — the same class of bug as unconditional state advancement on event observation alone.

## Likelihood Explanation
This is triggerable by any relayer submitting a legitimate delivery receipt for a message that failed remote execution on Ethereum (e.g., a reverted `Transact` command, gas exhaustion of a dispatched command) — a condition reachable without any privileged actor, since `submit_delivery_receipt` is a public, permissionless, signed extrinsic requiring only a valid proof of the emitted log [4](#0-3) .

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only pay the full reward when `success == true`; for `success == false`, either withhold/reduce the reward or apply distinct settlement logic, and emit a differentiated event (e.g. `MessageDeliveryFailed`) instead of unconditionally emitting `MessageDelivered` and removing the order.

## Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` in `PendingOrders` storage [5](#0-4) .
2. The message is executed on Ethereum and the dispatched command fails/reverts, causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits `submit_delivery_receipt` with a valid Merkle/event proof of this log; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly [6](#0-5) .
4. `process_delivery_receipt` proceeds to call `T::RewardPayment::register_reward(..., order.fee)` and `<PendingOrders<T>>::remove(nonce)` exactly as it would for `success: true`, since `receipt.success` is never checked [7](#0-6) .
5. A unit test asserting reward parity between a `success: true` and `success: false` receipt for otherwise identical nonces/fees would confirm this — no such differentiation exists in the current `process_delivery_receipt` logic.

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
