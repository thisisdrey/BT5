### Title
Unbounded loose-reference count from a single push causes automatic pack-refs housekeeping to run out of resources / DoS the housekeeping handler - (File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go)

### Summary
Gitaly enforces no upper bound on the number of references a client can create in a single push/`UpdateReferences` call. Reference creation automatically increments a per-repository write counter (`internal/grpc/middleware/housekeeping/middleware.go`) that, once past a threshold, schedules an asynchronous `OptimizeRepository` housekeeping run. That housekeeping run's pack-refs step performs two full, non-batched filesystem walks of the repository's `refs/` directory tree and materializes every loose reference into in-memory maps, exactly the "inflate-then-iterate-everything" pattern described in the M-10 report, where unrestricted proposal creation forced an unbounded loop over all pending proposals during execution.

### Finding Description
`UpdateReferences` (`internal/gitaly/service/ref/update_references.go:47-97`) and `DeleteRefs` (`internal/gitaly/service/ref/delete_refs.go:20-123`) accept an arbitrary number of reference updates per RPC with no cap on `len(request.GetUpdates())` or `len(req.GetRefs())`, unlike `UpdateRemoteMirror`, which explicitly caps batch/response sizes via `pushBatchSize` and `maxDivergentRefs` (`internal/gitaly/service/remote/update_remote_mirror.go:20-26`). An ordinary authenticated user can therefore create an effectively unbounded number of loose references in one or a handful of requests.

Every mutator RPC increments a write counter that is used to decide, heuristically, when to schedule `OptimizeRepository` asynchronously (`scheduleHousekeeping`, `internal/grpc/middleware/housekeeping/middleware.go:337-401`). `HeuristicalOptimizationStrategy.ShouldRepackReferences` (`internal/git/housekeeping/optimization_strategy.go:313-374`) decides to run `git-pack-refs` once the number of loose references crosses a small threshold (as low as ~16-99 depending on packed-refs size).

Once triggered, `preparePackRefsFiles` (`internal/gitaly/storage/storagemgr/partition/transaction_manager.go:1589-1662`) performs:
1. A `filepath.WalkDir` over the entire `refs/` tree, inserting every loose reference into a map (`looseReferences`) and every directory into `runPackRefs.emptyDirectories` (lines 1607-1635).
2. A `git-pack-refs --all` execution.
3. A second walk (implicit via `os.Stat` per collected reference, lines 1650-1659) to detect pruned references.

The code comment explicitly acknowledges the scaling problem: "This workaround works but is not performant on large repositories with huge amount of loose references" (lines 1583-1586). The companion verification step, `verifyPackRefsFiles` (`internal/gitaly/storage/storagemgr/partition/transaction_manager_housekeeping.go:727-818`), additionally builds a `reftree` of all pruned references and empty directories and walks it post-order, checking `os.ReadDir` on every ancestor directory.

Because none of the RPCs that create references (`UpdateReferences`, `DeleteRefs`, `git push` with many refspecs) restrict the number of references created per call, and because housekeeping is auto-scheduled from ordinary push activity, an attacker-controlled reference count directly drives the cost of these unbounded, single-shot filesystem walks — mirroring the Gov.sol pattern where unrestricted proposal creation is later paid for in one unbounded pruning loop. ### Impact Explanation
A repository with a very large number of loose references (created via unbounded `UpdateReferences`/`DeleteRefs` calls or a push with many refspecs) forces every subsequent automatic pack-refs housekeeping run to perform O(n) filesystem walks and build O(n)-sized in-memory maps synchronously inside a WAL transaction. On a shared Gitaly node this can consume excessive CPU, I/O, and memory for that partition's transaction manager, delaying or starving other transactions/housekeeping work, and in severe cases (millions of refs, as explicitly anticipated by the benchmarking tooling comment "Repos can have millions of refs") risks long stalls or resource exhaustion of the process handling that repository's transactions — a DoS of the housekeeping/pack-refs handler analogous to the Gov.sol pruning-loop OOG.

### Likelihood Explanation
Likelihood is moderate: any authenticated user with push/write access to a repository (no special "sequencer"-style privilege) can drive up loose reference counts via ordinary write RPCs, and housekeeping scheduling is fully automatic based on write-count heuristics, requiring no operator action. However, the walk cost is proportional to reference count and does not by itself corrupt data or bypass access control; it is a resource-exhaustion/performance-degradation issue rather than a memory-safety bypass, and Gitaly's per-repository housekeeping concurrency guard limits it to one such expensive run at a time per repository.

### Recommendation
Introduce a hard cap on the number of reference updates/deletions accepted per `UpdateReferences`/`DeleteRefs` call (mirroring the `pushBatchSize`/`maxDivergentRefs` pattern already used in `UpdateRemoteMirror`), and/or bound the cost of `preparePackRefsFiles`/`verifyPackRefsFiles` by processing large `refs/` trees incrementally or capping how many loose references a single pack-refs housekeeping pass will process before yielding, deferring the remainder to subsequent runs.

### Proof of Concept
1. As an authenticated user with write access, issue a streaming `UpdateReferences` (or many `git push` refspecs) request creating a very large number of new branches/refs (e.g. hundreds of thousands), since no limit is enforced on `len(request.GetUpdates())`.
2. Continue issuing mutator RPCs against the repository until `HeuristicalOptimizationStrategy.ShouldRepackReferences` triggers (loose reference count exceeds the small computed threshold).
3. Observe `scheduleHousekeeping` launch `OptimizeRepository`, which calls `preparePackRefsFiles`, performing full `filepath.WalkDir` traversal and per-reference `os.Stat` calls over the entire inflated `refs/` tree, consuming CPU/IO proportional to the attacker-chosen reference count on every subsequent auto-triggered housekeeping run for that repository.

func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++

	if a.active {
		return
	}

	pendingOps := m.pendingOperations(a, force)
	if len(pendingOps) == 0 {
		return
	}

func (s HeuristicalOptimizationStrategy) ShouldRepackReferences(context.Context) bool {
	// If there aren't any loose refs then there is nothing we need to do.
	// For reftables, if there is a single reftable, then there is no auto-compaction
	// needed.
	if s.info.References.LooseReferencesCount == 0 && len(s.info.References.ReftableTables) <= 1 {
		return false
	}

	// Reftables auto-compact their tables on the fly and don't generally rely
	// on housekeeping or 'git-pack-refs(1)' to be run. In Gitaly, we override
	// the auto-compaction capabilities because we want finer control and to
	// also prevent conflicts between concurrent writes.
	//
	// This replicates the behavior in Git (reftable_stack_auto_compact from
	// reftable/stack.c) to ensure that the tables follow a geometric progression.
	if len(s.info.References.ReftableTables) > 1 {
		// Git uses a different overhead based on the version of the reftable
		// format. Let's just use the bigger value, this makes our calculations
		// here slightly different from Git, but that is okay, since we would
		// still maintain geometric progression.
		var overhead uint64 = 28

		tables := s.info.References.ReftableTables

		for i := len(tables) - 1; i > 0; i-- {
			sizePrev := tables[i-1].Size - overhead
			sizeCur := tables[i].Size - overhead

			if sizePrev < sizeCur*2 {
				return true
			}
		}
		return false
	}

	// Packing loose references into the packed-refs file scales with the number of references
	// we're about to write. We thus decide whether we repack refs by weighing the current size
	// of the packed-refs file against the number of loose references. This is done such that we
	// do not repack too often on repositories with a huge number of references, where we can
	// expect a lot of churn in the number of references.
	//
	// As a heuristic, we repack if the number of loose references in the repository exceeds
	// `log(packed_refs_size_in_bytes/100)/log(1.15)`, which scales as following (number of refs
	// is estimated with 100 bytes per reference):
	//
	// - 1kB ~ 10 packed refs: 16 refs
	// - 10kB ~ 100 packed refs: 33 refs
	// - 100kB ~ 1k packed refs: 49 refs
	// - 1MB ~ 10k packed refs: 66 refs
	// - 10MB ~ 100k packed refs: 82 refs
	// - 100MB ~ 1m packed refs: 99 refs
	//
	// We thus allow roughly 16 additional loose refs per factor of ten of packed refs.
	//
	// This heuristic may likely need tweaking in the future, but should serve as a good first
	// iteration.
	if uint64(math.Max(16, math.Log(float64(s.info.References.PackedReferencesSize)/100)/math.Log(1.15))) > s.info.References.LooseReferencesCount {
		return false
	}

	return true
}

// preparePackRefsFiles runs git-pack-refs command against the snapshot repository. It collects the resulting packed-refs
// file and the list of pruned references. Unfortunately, git-pack-refs doesn't output which refs are pruned. So, we
// performed two ref walkings before and after running the command. The difference between the two walks is the list of
// pruned refs. This workaround works but is not performant on large repositories with huge amount of loose references.
// Smaller repositories or ones that run housekeeping frequent won't have this issue.
// The work of adding pruned refs dump to `git-pack-refs` is tracked here:
// https://gitlab.com/gitlab-org/git/-/issues/222
func (mgr *TransactionManager) preparePackRefsFiles(ctx context.Context, transaction *Transaction) error {
	runPackRefs := transaction.runHousekeeping.packRefs
	for _, lock := range []string{".new", ".lock"} {
		lockRelativePath := filepath.Join(transaction.relativePath, "packed-refs"+lock)
		lockAbsolutePath := filepath.Join(transaction.snapshot.Root(), lockRelativePath)

		if err := os.Remove(lockAbsolutePath); err != nil {
			if errors.Is(err, fs.ErrNotExist) {
				continue
			}

			return fmt.Errorf("remove %v: %w", lockAbsolutePath, err)
		}

		// The lock file existed. Log its deletion.
		transaction.walEntry.RemoveDirectoryEntry(lockRelativePath)
	}

	// First walk to collect the list of loose refs.
	looseReferences := make(map[git.ReferenceName]struct{})
	repoPath := mgr.getAbsolutePath(transaction.snapshotRepository.GetRelativePath())
	if err := filepath.WalkDir(filepath.Join(repoPath, "refs"), func(path string, entry fs.DirEntry, err error) error {
		if err != nil {
			return err
		}

		relPath, err := filepath.Rel(repoPath, path)
		if err != nil {
			return fmt.Errorf("extracting ref name: %w", err)
		}

		// Since we are walking a child of the parent directory, parent can't be empty.
		delete(runPackRefs.emptyDirectories, filepath.Dir(relPath))

		if entry.IsDir() {
			// Mark the directory as potential empty
			runPackRefs.emptyDirectories[relPath] = struct{}{}
			return nil
		}

		// Get fully qualified refs.
		looseReferences[git.ReferenceName(relPath)] = struct{}{}

		return nil
	}); err != nil {
		return fmt.Errorf("initial walking refs directory: %w", err)
	}

	// Build a tree of the loose references and empty directories we need to prune.
	prunedPaths := reftree.New()
	for reference := range packRefs.PrunedRefs {
		if err := prunedPaths.InsertReference(reference.String()); err != nil {
			return nil, fmt.Errorf("insert reference: %w", err)
		}
	}
	for directory := range packRefs.emptyDirectories {
		if err := prunedPaths.InsertNode(directory, true, true); err != nil {
			return nil, fmt.Errorf("insert directory: %w", err)
		}
	}

	directoriesToKeep := map[string]struct{}{
		// Valid git directory needs to have a 'refs' directory, so we can't remove it.
		filepath.Join(transaction.relativePath, "refs"): {},
		// Git keeps these top-level directories. We keep them as well to reduce
		// conflicting operations on them.
		filepath.Join(transaction.relativePath, "refs", "heads"): {},
		filepath.Join(transaction.relativePath, "refs", "tags"):  {},
	}

	// Walk down the deleted references from the leaves towards the root. We'll log the deletion
	// of loose references as we walk towards the root, and the removal of directories along the
	// path that became empty as a result of removing the references. As we're operating on the real
	// repository here, we can't actually perform deletions in it. We instead keep track of the
	// files and directories we've deleted in-memory to ensure we only delete empty directories.
	deletedPaths := make(map[string]struct{}, len(packRefs.PrunedRefs)+len(packRefs.emptyDirectories))
	if err := prunedPaths.WalkPostOrder(func(path string, isDir bool) error {
		relativePath := filepath.Join(transaction.relativePath, path)
		if _, ok := directoriesToKeep[relativePath]; ok {
			return nil
		}

		if isDir {
			// If this is a directory, we need to ensure it is actually empty before removing
			// it. Check if we find any directory entries we haven't yet deleted.
			entries, err := os.ReadDir(mgr.getAbsolutePath(relativePath))
			if err != nil {
				return fmt.Errorf("read dir: %w", err)
			}

			for _, entry := range entries {
				if _, ok := deletedPaths[filepath.Join(relativePath, entry.Name())]; ok {
					// This path was already deleted. Don't consider it to exist.
					continue
				}

				// This directory was not empty because someone concurrently wrote
				// a reference into it. Keep it in place.
				directoriesToKeep[relativePath] = struct{}{}
				return nil
			}
		}

		deletedPaths[relativePath] = struct{}{}
		transaction.walEntry.RemoveDirectoryEntry(relativePath)

		return nil
	}); err != nil {
		return nil, fmt.Errorf("walk post order: %w", err)
	}
