### Title
Stale StackerDB signer whitelisting: reconfiguration is skipped whenever the on-chain signer set becomes empty, leaving revoked signers permanently authorized to write - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::create_or_reconfigure_stackerdbs` decides whether to re-apply a freshly-read StackerDB configuration to the local replica by comparing it to the previously stored config, but it explicitly refuses to apply the new configuration whenever the newly computed signer list is empty. This is the direct analog of the reported "workflow whitelisting" bug: a previously granted write-permission (a signer's authorization to write a StackerDB slot) is never revoked/updated once granted, even after the authoritative source (the controlling smart contract) stops listing that signer.

### Finding Description
`create_or_reconfigure_stackerdbs` computes `new_config` for each StackerDB contract from `StackerDBConfig::from_smart_contract` (or `make_miners_stackerdb_config` for `.miners`), and only calls `reconfigure_stackerdb` (which is the only code path that updates the `signer` column that authorizes writes for each slot) under this gate: [1](#0-0)

The condition `!new_config.signers.is_empty()` means: if the newly-read signer list from the contract is empty, the on-disk (previously stored) signer→slot mapping is left untouched, no matter how different it is from the new contract state. The actual authorization check for accepting a chunk write, `validate_received_chunk`/`try_replace_chunk`, relies entirely on the *stored* `chunks.signer` column (via `get_slot_signer`), not on live contract state: [2](#0-1) 

The stored mapping is only ever updated by `reconfigure_stackerdb`: [3](#0-2) 

Additionally, `from_smart_contract` falls back to `StackerDBConfig::noop()` (an empty-signers config) on any contract-evaluation error (`unwrap_or_else` in `create_or_reconfigure_stackerdbs`): [4](#0-3) 

So any transient failure to read the controlling contract (a Clarity read-only call failing, contract temporarily failing trait validation, etc.) or a legitimate on-chain transition where the signer list becomes empty (e.g., zero-participation reward cycle per `has_participation` in `update_signers`) produces `new_config.signers.is_empty() == true`, and the node silently keeps serving/accepting writes under the *old*, no-longer-current signer set. This breaks the equality "currently-authorized signer set (on-chain/contract) == stored write-authorization (StackerDB `chunks.signer` column)" — exactly the "permission remains active unless manually revoked" pattern described in the external report, but here it can also be triggered passively (no attacker action needed to leave it stale) and exploited by any previously-legitimate-but-now-revoked signer who still holds their old private key.

### Impact Explanation
Stale write authorization to a StackerDB (e.g. the `.signers-*` message DBs or a `.miners` DB) means an address that has been removed from the current reward-cycle signer set (rotated out, or a compromised key that the operator has since replaced) retains the ability to author authenticated-looking StackerDB chunks that peers will accept and gossip. This is an unauthorized/unauthenticated write to network-replicated state, potentially propagating forged signer/miner messages network-wide — this maps to the "Critical: unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data" category in scope.

### Likelihood Explanation
The precondition (new_config.signers being empty) can be reached either passively — any transient failure in `StackerDBConfig::from_smart_contract` (e.g. read-only Clarity evaluation hiccup) causes `unwrap_or_else(|_| StackerDBConfig::noop())`, which has an empty `signers` field — or as a legitimate on-chain event (zero participation for a cycle). No attacker interaction with the p2p network is needed to create the stale state; the attacker only needs to have possessed a previously-valid signer key that has since been rotated out, and continue emitting well-formed, correctly-signed `StackerDBChunkData` for the slot they used to own. Because the check `!new_config.signers.is_empty()` is unconditional (not limited to only the error/noop path), this is a real, reachable condition rather than a purely theoretical one, although it does depend on the specific timing of a signer-set change coinciding with an empty-signers observation.

### Recommendation
Do not gate `reconfigure_stackerdb` on `!new_config.signers.is_empty()`. Distinguish between "failed to load config" (keep old config, as intended for resilience) and "successfully loaded a legitimately-empty signer list" (which should still cause reconfiguration/revocation of stale signer slots). Concretely, only skip reconfiguration when `from_smart_contract` itself returned an `Err` (i.e., use the `Result` before defaulting to `noop()`), rather than inferring "failure" from an empty signers vector after the fact. This ensures that once the authoritative signer set changes (even to zero), previously-authorized signers immediately lose write access to the StackerDB slot instead of retaining it indefinitely.

### Proof of Concept
1. Node runs with `.signers-0-N` or `.miners` StackerDB where `signer A` currently owns slot `k` (established via prior `reconfigure_stackerdb`).
2. On-chain state transitions such that the contract's `stackerdb-get-signer-slots` legitimately returns an empty list for a cycle (e.g., `has_participation == false` in `update_signers`) or `StackerDBConfig::from_smart_contract` transiently errors (any Clarity read-only evaluation failure), causing `create_or_reconfigure_stackerdbs` to compute `new_config` with `signers = vec![]`.
3. Because `!new_config.signers.is_empty()` is `false`, the `if`/`else if` branch is skipped entirely; `reconfigure_stackerdb` is never called, and the `chunks` table for that StackerDB keeps `signer = A` for slot `k`.
4. `signer A`, despite no longer being part of the authoritative signer set, continues to sign and POST `StackerDBChunkData` to `/v2/stackerdb/.../chunks` (or push it unsolicited over p2p). `validate_received_chunk`/`try_replace_chunk` call `get_slot_signer`, which still returns `A`, so the signature check in `SlotMetadata::verify` succeeds and the chunk is accepted and replicated network-wide, even though `A` is no longer authorized under current chain state.
