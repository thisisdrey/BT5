## Finding: Unchecked return value of `addAssetAmountV2` in TRC10 asset actuators mirrors the reported "missing check for successful transfer" bug class

### Summary
The external report flags an ERC20-style contract for not checking the boolean return of `transfer()` before assuming success. The closest reachable analog in java-tron is the TRC10 asset-balance-mutation API `AccountCapsule.addAssetAmountV2(...)`, which — like `reduceAssetAmountV2` — returns a `boolean` indicating whether the operation succeeded (it can fail, e.g. on overflow). While `reduceAssetAmountV2` calls are consistently checked in the actuators, several `addAssetAmountV2` (and one `reduceAssetAmountV2`) call sites silently discard the return value and still report the transaction as `SUCESS`.

### Finding Description
In `ParticipateAssetIssueActuator.execute` (an unprivileged, single-signed-transaction actuator any account can broadcast), the debit side is checked but the credit side is not: [1](#0-0) 

`ownerAccount.addAssetAmountV2(key, exchangeAmount, dynamicStore, assetIssueStore);` on line 79 is invoked without checking its boolean result, whereas the mirrored `toAccount.reduceAssetAmountV2(...)` on line 85 is wrapped in `if (! ... ) throw new ContractExeException(...)`.

The same pattern (both sides unchecked) appears in `ExchangeTransactionActuator.execute`: [2](#0-1) 

Here `accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, ...)` (line 83) and `accountCapsule.addAssetAmountV2(anotherTokenID, anotherTokenQuant, ...)` (line 90) are both called with their boolean results discarded, and the transaction is unconditionally marked `code.SUCESS` at line 99.

By contrast, `TransferAssetActuator.execute` correctly checks the reduce call but note that its `addAssetAmountV2` call is also unchecked: [3](#0-2) 

### Impact Explanation
If `addAssetAmountV2` (or `reduceAssetAmountV2` in the exchange case) returns `false` — its documented failure path — the balance mutation is silently skipped while the corresponding debit has already been applied and persisted (`accountStore.put(...)`), and the transaction result is still marked as `SUCESS`. This produces:
- Permanent loss ("burning") of a user's TRC10 tokens with no corresponding credit anywhere (unbacked/lost balance), since the debited asset amount vanishes from total circulating balances tracked across accounts.
- In the exchange path, `ExchangeCapsule.transaction(...)` state is committed even though the account-side asset ledger update may have silently failed, causing a balance/exchange-pool inconsistency reachable by any account issuing an `ExchangeTransactionContract` or `ParticipateAssetIssueContract`.

I was not able to fully inspect the body of `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` in this pass to confirm the exact conditions under which they return `false` (likely long-overflow guard) — this should be verified directly in `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` to determine precisely which numeric conditions trigger a `false` return and confirm the loss-of-funds path is reachable with attacker-controlled amounts.

### Likelihood Explanation
Both `ParticipateAssetIssueContract` and `ExchangeTransactionContract` are ordinary broadcastable transactions signable by any account holding a small TRX balance and a TRC10 token/exchange pair — no special privilege is required. The only obstacle is finding input amounts that push `addAssetAmountV2`/`reduceAssetAmountV2` into their failure branch (most plausibly a `long` overflow on the receiving account's existing asset balance plus the incoming amount), which is a data-dependent but attacker-influenceable condition since the attacker controls `amount`/`exchangeAmount` and can pre-inflate the target account's balance across prior transactions.

### Recommendation
Check the boolean return values of `addAssetAmountV2` and `reduceAssetAmountV2` at every call site (`TransferAssetActuator`, `ParticipateAssetIssueActuator`, `ExchangeTransactionActuator`, and any others), and throw `ContractExeException` (mirroring the existing pattern already used for `reduceAssetAmountV2` checks) instead of allowing the actuator to persist a partially-applied state change and report `SUCESS`.

### Proof of Concept
Conceptual PoC (needs confirmation against the exact overflow condition in `AccountCapsule`):
1. Attacker sets up an account whose existing TRC10 asset balance for token `T` is already close to `Long.MAX_VALUE` (achievable via repeated legitimate transfers/exchanges since token issuance amounts and counts are attacker-controllable within protocol limits).
2. Attacker (or a counterparty) broadcasts a `ParticipateAssetIssueContract`/`ExchangeTransactionContract` transaction whose computed `exchangeAmount`/`anotherTokenQuant` added to that near-max balance would overflow `long`.
3. `addAssetAmountV2` returns `false` (guarding against overflow) but the call site ignores it; the paired debit (`reduceAssetAmountV2`, already checked) succeeds and is persisted.
4. The transaction commits with `code.SUCESS`; the debited token amount is permanently lost — it was subtracted from one account and never credited to the other, and no exception rolled back the operation. [4](#0-3) [5](#0-4) [6](#0-5)
