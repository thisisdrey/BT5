### Title
StackerDB `write_freq` rate limit is never enforced on chunk writes, only on sync-fetch decisions - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The StackerDB control-plane config exposes a `write_freq` field, documented as "minimum wall-clock time between writes to the same slot" [1](#0-0) . This is exactly the "latency timelock" construct from the reported bug class: a time-based gate meant to bound how often an authorized party (a slot signer) may push a new value. As in the report, the actual write path that stores a new chunk never checks this timelock, only two orthogonal properties (monotonic version, and total write count).

### Finding Description
The single function that actually commits a chunk to storage, `StackerDBTx::try_replace_chunk`, checks chunk size, slot existence, signer signature, staleness (`slot_version <= slot_validation.version`), and `max_writes`, but contains **no check of `write_freq`/`write_time`** at all: [2](#0-1) 

The underlying `insert_chunk` simply records `write_time = get_epoch_time_secs()` for bookkeeping, but nothing gates the call based on the previous `write_time`: [3](#0-2) 

This is the only place `try_replace_chunk` is called from the HTTP write endpoint (`POST /v2/stackerdb/:address/:contract/chunks`), which is directly reachable, unauthenticated-at-the-transport-level, by any remote peer holding a valid slot signer key: [4](#0-3) 

The relay/gossip path that stores chunks received from peers, `NetworkResult`/`Relayer::process_stacker_db_chunks`, also calls `tx.try_replace_chunk` directly with no `write_freq` gate, and on success unconditionally re-broadcasts the chunk to all connected peers: [5](#0-4) 

By contrast, `write_freq` **is** checked, but only inside the sync-download decision logic that decides whether the local node should bother *fetching* a chunk from a neighbor because it was written too recently to be worth refreshing: [6](#0-5) 

And `validate_received_chunk`, used when validating downloaded/pushed chunks, explicitly documents that it does *not* check write frequency, leaving that entirely to callers — but no caller in the write/commit path ever does: [7](#0-6) 

This mirrors the reported Solidity bug precisely: the protocol defines a time-based throttle intended to bound how often a legitimately-privileged actor (a maintainer setting a fee; here, an authorized StackerDB slot signer) can update state, but the enforcement of that throttle is either missing or applied on the wrong side of the state machine, so the actor can update at unlimited real frequency by simply incrementing `slot_version` on every call — no signature or lock is violated, since only version-monotonicity and total write-count are enforced.

### Impact Explanation
Any signer who legitimately owns one or more StackerDB slots (e.g., a Nakamoto signer registered for the miner/signer StackerDB contracts) can push chunks at a rate far higher than the contract's configured `write_freq` intends, up to the `max_writes` ceiling. Each accepted write:
- triggers a SQLite `UPDATE` per chunk,
- and is unconditionally rebroadcast to every connected peer via `p2p.broadcast_message` in `process_stacker_db_chunks`.

Because `write_freq` is a network-wide throttle meant to bound the replication/storage/bandwidth cost that all replicating nodes must absorb per slot, bypassing it lets one authorized signer amplify write/broadcast traffic network-wide well beyond what operators configured and tuned for. This is a logic defect (a documented rate limit whose enforcement point does not exist), not merely raw traffic volume from an attacker — the same request rate would be rejected if the enforcement existed, and the flaw is structural (missing check in `try_replace_chunk`), matching the "bounded compute DoS" / resource-amplification impact class rather than pure volumetric flooding.

### Likelihood Explanation
Any actor who is an authorized signer for at least one active StackerDB slot (a normal, expected role, not requiring theft of another party's key or admin privileges) can trigger this simply by sending `POST /v2/stackerdb/...` requests back-to-back with incrementing `slot_version`. No special timing, race condition, or protocol quirk is required; the check is simply absent from the code path.

### Recommendation
Enforce `config.write_freq` inside `StackerDBTx::try_replace_chunk` (and/or `insert_chunk`) by comparing the slot's stored `write_time` against `get_epoch_time_secs()` and rejecting with `Error::TooFrequentSlotWrites` (which already exists as an error variant but is seemingly unused on this path) if the elapsed time since the last write is less than `write_freq`. Since `Error::TooFrequentSlotWrites` and a corresponding ack error code (`StackerDBErrorCodes`) do not currently include this case, add one, and route it consistently through both the HTTP POST handler (`poststackerdbchunk.rs`) and the peer-relay chunk-storage path (`relay.rs::process_stacker_db_chunks`).

### Proof of Concept
1. Deploy/observe an existing StackerDB contract with `write-freq: u120` (minimum 120s between writes to a slot) and `max-writes` set high.
2. As the owner of slot `N` (holding its private key), sign and `POST` a chunk with `slot_version = v+1` to `/v2/stackerdb/<addr>/<contract>/chunks`; observe it is `accepted: true` with `write_time` updated.
3. Immediately (within 1 second, well under the 120s `write_freq`) sign and `POST` another chunk for the same slot with `slot_version = v+2`.
4. Observe the second write is also `accepted: true` — `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` only checks `slot_version <= slot_validation.version` (staleness) and `slot_version > max_writes`, neither of which blocks a rapid resubmission with a monotonically increasing version. Repeat indefinitely up to `max_writes` to confirm no time-based throttling is ever applied, and that each accepted write is rebroadcast to the network via `process_stacker_db_chunks`.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
