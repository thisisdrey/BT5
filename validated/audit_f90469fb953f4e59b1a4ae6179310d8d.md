### Title
Token-name impersonation due to missing issuer↔name binding in `AssetIssueActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
`AssetIssueActuator` only rejects a TRC10 issuance whose `name` collides with an existing token when the network-wide dynamic property `AllowSameTokenName` is `0`. Once this switch is `1` (the state activated on TRON mainnet via governance proposal and now the standard mode, since assets are tracked by numeric `id` in `AssetIssueV2Store` rather than by `name`), any account can freely mint a new TRC10 asset re-using the exact `name`/`abbr` of an already reputable, existing token. This is the same root cause as the reported OpenQ issue: there is no mapping that binds a human-readable identifier (organization/token name) to the original issuer's address, so anyone can impersonate it.

### Finding Description
In `validate()`, the duplicate-name check is gated behind the legacy flag: [1](#0-0) 

and the "can't be trx" check is likewise gated behind `getAllowSameTokenName() != 0`, meaning it only fires when the feature is enabled — but it only excludes the literal string "trx", not other reputable/pre-existing names: [2](#0-1) 

When `AllowSameTokenName == 1`, `execute()` only writes to `AssetIssueV2Store` keyed by the numeric token id, never checking or updating the legacy name-keyed `AssetIssueStore`, so no uniqueness constraint on `name`/`abbr` is enforced at all: [3](#0-2) 

Because token identity in wallets/exchanges/dApps is commonly surfaced to end users by `name`/`abbr` rather than the opaque numeric `id`, an attacker can issue a brand-new TRC10 token with the same `name` and `abbr` as a well-known, reputable token (e.g., a stablecoin or an established project's token) and use it for phishing: victims believe they are receiving/holding the legitimate asset because the display name matches, but it is actually the attacker's worthless token. This directly parallels the reported bug class ("anyone can mint under a trusted identity, with no owner↔identity binding").

### Impact Explanation
This enables organization/brand impersonation at the protocol level with no way for the real organization to prevent it, since there's no `issuer => name` uniqueness or reservation mechanism once `AllowSameTokenName` is active. Victims can be deceived into treating counterfeit tokens as the genuine asset, leading to funds effectively lost (accepting worthless tokens in exchange for value, or being tricked into interacting with a fraudulent token contract believing it is the reputable one). This matches the "concrete unauthorized... theft of funds" bar via social-engineering-enabled phishing built directly on a protocol-level lack of uniqueness guarantee.

### Likelihood Explanation
`AllowSameTokenName` is the standard/activated mode on TRON mainnet (assets identified by unique `id`, not `name`), so this validate-path gap is live for any transaction broadcaster today — a single `AssetIssueContract` transaction from any funded account can duplicate an existing token's `name`/`abbr` with no special privilege required.

### Recommendation
Enforce global uniqueness (or at least an issuer-reservation mapping) on `name`/`abbr` regardless of `AllowSameTokenName`, e.g., maintain a name→(first issuer address) or name→existing-id index that `AssetIssueActuator.validate()` consults on every issuance (not only when `AllowSameTokenName == 0`), rejecting new issuances that reuse a `name`/`abbr` already associated with a different owner address.

### Proof of Concept
1. Ensure `AllowSameTokenName == 1` (current mainnet state).
2. Attacker broadcasts an `AssetIssueContract` transaction with `name = "USDT"` (or any existing reputable token's name/abbr) and a different owner address.
3. `AssetIssueActuator.validate()` skips the `assetIssueStore.get(name) != null` check (only active when `AllowSameTokenName == 0`) and only checks the literal string `"trx"`.
4. `execute()` stores the new token in `AssetIssueV2Store` keyed by a fresh numeric `id`, successfully creating a token with a colliding `name`/`abbr` to the legitimate one, with no linkage or warning tying the name back to the original issuer.
