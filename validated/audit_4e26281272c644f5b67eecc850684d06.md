### Title
Non-constant-time authorization header comparison enables timing side-channel to recover the fast-call-read secret - (File: stackslib/src/net/api/fastcallreadonly.rs)

### Summary
`RPCFastCallReadOnlyRequestHandler::try_parse_request` compares the caller-supplied `authorization` header against the configured secret using Rust's default `String`/`&str` `!=` operator, which is not constant-time. Because the comparison result gates access to the `/v3/contracts/fast-call-read/...` endpoint and the header value is fully attacker-controlled, a remote unprivileged party can send repeated single requests with incrementally-guessed prefixes and use response-time differences to infer correct secret bytes one at a time.

### Finding Description
At [1](#0-0)  the handler does:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`auth_header` and `password` are both `String`/`&str`, and `PartialEq` for these types is backed by a byte-slice comparison that first checks length equality and then performs `memcmp`-style comparison, which is free to (and in practice does) short-circuit on the first mismatching byte. This is not a guaranteed constant-time comparison such as `subtle::ConstantTimeEq::ct_eq`. The `authorization` header is attacker-controlled input read directly from the parsed HTTP preamble at [2](#0-1) , and the secret `password` is `self.auth`, set at node configuration time via `RPCFastCallReadOnlyRequestHandler::new` at [3](#0-2) . No length-hiding, hashing, or constant-time equality primitive (e.g. `subtle::ConstantTimeEq`, `ring::constant_time::verify_slices_are_equal`) is used anywhere in this comparison path.

An attacker with only network access to the RPC port can send POST requests to `/v3/contracts/fast-call-read/:principal/:contract/:function` with a guessed `authorization` value, measure response latency, and iteratively extend a correct prefix, guess byte-by-byte the full secret in a number of requests roughly linear in secret length times alphabet size, rather than needing to brute-force the full keyspace.

### Impact Explanation
If successfully exploited, this results in authentication bypass on the fast-call-read endpoint (matches the "auth bypass" Critical category), allowing an unprivileged remote party to eventually construct a valid `authorization` header and invoke privileged read-only contract calls that are supposed to require possession of the configured secret. This does not directly corrupt on-chain state or write to StackerDB, but it defeats the endpoint's sole access control, which is the intended severity boundary for this endpoint.

### Likelihood Explanation
Exploitability is real in principle but has practical caveats: real-world timing-attack extraction over a network requires statistical averaging across many measurements per byte to overcome network jitter, OS scheduling noise, and TLS/HTTP framing overhead, meaning the "single-message repeated" framing in the question understates the realistic sample count needed (each byte position typically needs many repeated measurements, not one). The vulnerable code path itself is reachable at zero privilege — no session, no StackerDB slot, no prior authentication is needed to reach the comparison, since the check happens in `try_parse_request` before any other validation. The endpoint is only enabled when `self.auth` is configured (`Some`), which is an operator-configured deployment condition, not an attacker precondition.

### Recommendation
Replace the plain `!=` comparison with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq::ct_eq` on the byte representations of `auth_header` and `password`, or `ring::constant_time::verify_slices_are_equal`, ensuring the comparison time is independent of where the first mismatching byte occurs and independent of input length where feasible (e.g. by comparing fixed-size hashes of both values instead of raw secrets).

### Proof of Concept
A Rust test in `stackslib/src/net/api/tests/fastcallreadonly.rs` can assert the fix rather than measure wall-clock time directly (as recommended for repo-local proof determinism):
```rust
#[test]
fn auth_comparison_is_constant_time() {
    // Assert that the comparison implementation uses a constant-time primitive
    // (e.g. subtle::ConstantTimeEq) rather than `String`/`&str` `!=`.
    // This can be enforced via a static/lint check on the auth-comparison call site,
    // or by refactoring the comparison into a testable helper:
    //   fn secure_compare(a: &str, b: &str) -> bool
    // and asserting its implementation calls `ct_eq` internally (e.g. via a mock or
    // code-inspection test), so the guarantee doesn't rely on flaky timing measurements.
}
```
Currently no such constant-time helper exists; the direct `if auth_header != password` at [4](#0-3)  is the exact vulnerable line to be replaced and covered by this test.
