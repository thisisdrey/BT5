### Title
`core.hooksPath` / `receive.procReceiveRefs` set by `configureHooks` can be overridden by caller-supplied `GitConfigOptions`, bypassing mandatory receive-pack hooks - ([File: internal/git/gitcmd/hooks_options.go])

### Summary
`configureHooks` in `internal/git/gitcmd/hooks_options.go` injects `core.hooksPath` (and, for proc-receive, `receive.procReceiveRefs`) into `cc.globals` via `WithReceivePackHooks`, but both the SSH and smarthttp `receive-pack` code paths apply `gitcmd.WithConfig(config...)` — built from `req.GetGitConfigOptions()` via `gitcmd.ConvertConfigOptions` — *after* `WithReceivePackHooks` in the `CmdOpt` list. Because `-c` flags are applied in the order globals are appended and Git lets a later `-c` for the same key win, caller-supplied config for `core.hooksPath` or `receive.procReceiveRefs` overrides the value Gitaly set for hook enforcement.

### Finding Description
`configureHooks` appends the hook-critical config pairs to `cc.globals`: [1](#0-0) 

In both `internal/gitaly/service/ssh/receive_pack.go` and `internal/gitaly/service/smarthttp/receive_pack.go`, the `CmdOpt`s are passed to `repo.Exec` with `gitcmd.WithReceivePackHooks(...)` listed *before* `gitcmd.WithConfig(config...)`, where `config` comes straight from `gitcmd.ConvertConfigOptions(req.GetGitConfigOptions())`: [2](#0-1) [3](#0-2) 

`ExecCommandFactory.combineArgs` builds the final argument list in the order the `CmdOpt`s were applied: default globals, then command-specific opts, then `cc.globals` (which contains the hooks-config pairs followed by the caller-supplied ones), then admin config: [4](#0-3) 

`ConvertConfigOptions` performs no allowlisting of keys — it only splits `key=value` on `=`: [5](#0-4) 

`GitConfig.Validate()` (called from `GlobalArgs()`) only checks generic syntactic validity (non-empty, no `=`, has a dot, doesn't start/end with a dot, matches a key regex) — it never blocks security-sensitive keys such as `core.hooksPath` or `receive.procReceiveRefs`: [6](#0-5) 

Existing tests confirm that when the same key appears multiple times in the globals list, the later entry wins: [7](#0-6) 

Since the caller-supplied globals from `WithConfig` are appended after the hooks-derived globals from `WithReceivePackHooks`/`configureHooks`, a `core.hooksPath=<attacker path>` (or empty/no-op path) entry in `req.GetGitConfigOptions()` overrides Gitaly's own `core.hooksPath`, causing `git-receive-pack` to look for hooks in an attacker-chosen (or non-existent) directory instead of the `gitaly-hooks`-backed directory. Likewise, `receive.procReceiveRefs=` could suppress the proc-receive interception Gitaly relies on for transactional ref updates when `enableProcReceive` is set.

### Impact Explanation
If `GitConfigOptions` reaches Gitaly with attacker-controlled content, this allows a hook/quarantine bypass: `pre-receive`, `update`, `post-receive`, and (when applicable) `proc-receive` hook execution — which Gitaly relies on for access control, quota checks, and safe reference-transaction routing — can be silently skipped or redirected, letting a push land without those checks running. This matches the "hook or quarantine bypass" impact class called out in scope.

### Likelihood Explanation
The vulnerability inside Gitaly's own code is deterministic and easily reproduced: no key allowlist exists in `ConvertConfigOptions`/`GitConfig.Validate`, and the CmdOpt ordering in both `ssh` and `smarthttp` receive-pack handlers unconditionally lets caller config win over hook config. The remaining uncertainty is external to this repository: in the standard GitLab architecture, `SSHReceivePackRequest.GitConfigOptions`/`PostReceivePackRequest.GitConfigOptions` are populated by the trusted `gitlab-shell`/Workhorse/Rails layer from server-side settings, not forwarded verbatim from an unprivileged pusher's local `git -c` flags transmitted over the wire (the SSH/HTTP git transport protocols do not carry the client's local config to the server). Whether an unprivileged user can actually control this field end-to-end depends on that intermediary layer, which is outside this repository and cannot be verified with the available tools/index.

### Recommendation
- In `configureHooks`/`WithReceivePackHooks`, apply the hook-critical config pairs (`core.hooksPath`, `receive.procReceiveRefs`) *after* any caller-supplied config, or enforce them as non-overridable (e.g., via `cf.cfg.Git.Config`-equivalent placement, which is documented as always overriding all other items) so they cannot be shadowed regardless of `CmdOpt` ordering.
- Add an explicit denylist/allowlist in `gitcmd.ConvertConfigOptions` (or at the RPC boundary) rejecting security-sensitive keys such as `core.hooksPath`, `receive.procReceiveRefs`, `uploadpack.packObjectsHook`, `core.fsmonitor`, etc. from caller-supplied `GitConfigOptions`.
- Add a regression test asserting that `WithConfig` cannot override `core.hooksPath` once `WithReceivePackHooks` has configured it.

### Proof of Concept
```go
func TestReceivePackHooks_ConfigOverride(t *testing.T) {
    cfg := testcfg.Build(t)
    ctx := testhelper.Context(t)
    gitCmdFactory := gittest.NewCommandFactory(t, cfg)

    repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg)
    repo := localrepo.NewTestRepo(t, cfg, repoProto)
    objectHash, err := repo.ObjectHash(ctx)
    require.NoError(t, err)

    // Attacker-controlled GitConfigOptions from SSHReceivePackRequest/PostReceivePackRequest.
    attackerConfig, err := gitcmd.ConvertConfigOptions([]string{"core.hooksPath=/tmp/attacker-hooks"})
    require.NoError(t, err)

    cmd, err := repo.Exec(ctx, gitcmd.Command{Name: "config", Args: []string{"--get", "core.hooksPath"}},
        gitcmd.WithReceivePackHooks(objectHash, &gitalypb.PostReceivePackRequest{
            Repository: repoProto, GlId: "user-1",
        }, "ssh", false),
        gitcmd.WithConfig(attackerConfig...), // appended after hooks config, same as production code
    )
    require.NoError(t, err)

    out, _ := io.ReadAll(cmd)
    require.NoError(t, cmd.Wait())
    // Expected (vulnerable) result: "/tmp/attacker-hooks" instead of gitCmdFactory.HooksPath(ctx).
    require.Equal(t, "/tmp/attacker-hooks\n", string(out))
}
```
Expected assertion under the current code: the effective `core.hooksPath` resolves to the attacker-supplied value rather than `gitCmdFactory.HooksPath(ctx)`, demonstrating that hook enforcement can be overridden via caller-controlled config. (Confirmation that `GitConfigOptions` is reachable, unmodified, from an actual unprivileged `git push` requires inspecting the `gitlab-shell`/Rails code that populates these RPC fields, which is outside this repository.)

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}

// Validate validates that the Git configuration conforms to a format that Git understands.
func (cfg GitConfig) Validate() error {
	// Even though redundant, this block checks for a few things up front to give better error
	// messages to the administrator in case any of the keys fails validation.
	if cfg.Key == "" {
		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")
	}
	if strings.Contains(cfg.Key, "=") {
		return cfgerror.NewValidationError(
			fmt.Errorf(`key %q cannot contain "="`, cfg.Key),
			"key",
		)
	}
	if !strings.Contains(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must contain at least one section", cfg.Key),
			"key",
		)
	}
	if strings.HasPrefix(cfg.Key, ".") || strings.HasSuffix(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must not start or end with a dot", cfg.Key),
			"key",
		)
	}

	if !configKeyRegex.MatchString(cfg.Key) {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q failed regexp validation", cfg.Key),
			"key",
		)
	}

	return nil
}
