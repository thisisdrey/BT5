### Title
Wild pointer read in ijar's Zip central-directory parser via crafted extra-field length - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` is invoked by Bazel's Java build rules (`java_common.run_ijar`) to strip method bodies from `.jar` files, producing interface jars used for compilation caching [1](#0-0) . It is a C++ tool that parses attacker-influenced jar bytes directly (e.g., a jar fetched via `http_jar`/`http_archive`/Maven-style external dependencies) with pointer arithmetic driven entirely by length fields taken from the file itself, with no defensive bound derived from the mapped file size in the central-directory scan path [2](#0-1) .

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight out of the central directory record and advances the cursor `p` by these values with no check against the size of the mapped input file: [3](#0-2) 

It then walks the extra-field bytes with:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [4](#0-3) 

This loop uses an equality-based termination condition (`extra_p != p`), exactly like the `gss_free_in_token_pages()` bug in the report, which also assumed a well-formed, aligned/terminated structure and looped based on the assumption that the cursor would land exactly on the boundary. If a crafted extra-field record specifies a `data_size` that does not align with the remaining `extra_field_length` (e.g. `data_size` that overshoots `p`), `extra_p` skips past the intended end and the loop condition `extra_p != p` never becomes true, so `get_u2le`/`get_u8le` continue reading arbitrary memory beyond the mapped region (a "wild memory access" identical in kind to the KASAN-detected out-of-bounds read in the report).

Separately, if the Zip64 extra field within this unguarded loop supplies `*offset` (the local-header offset) via `get_u8le`, that fully attacker-controlled 64-bit value is later used unchecked: [5](#0-4) 
`p = zipdata_in_ + in_offset_ + offset;` can point arbitrarily outside the mmap'd file. The only guard, `EnsureRemaining`, computes `remaining = input_file_->Length() - in_offset` using unsigned `size_t` arithmetic: [6](#0-5) 
If `in_offset` (i.e. `p - zipdata_in_`) exceeds `input_file_->Length()`, the subtraction underflows to a huge value, so `n > remaining` is false and the check silently passes, allowing `get_u4le(p)` and subsequent local-file-header parsing to dereference memory far outside the mapped file.

By contrast, `ProcessLocalFileEntry` (which handles the local file header, not the central directory) does call `EnsureRemaining` before consuming `file_name_length_`/`extra_field_length_` [7](#0-6) , showing the central-directory path is the one missing the equivalent containment check — this is not a design choice that "already stops it," it's an inconsistency between the two parsing paths.

### Impact Explanation
A hostile jar (served from an untrusted URL, mirror, or dependency-registry artifact that a victim's build fetches and then processes through `ijar`/`run_ijar`) can trigger out-of-bounds reads in the `ijar` process. Depending on heap layout this can crash the build worker (denial), or cause data adjacent to the mapping to be interpreted as further zip structure/file content, which is then written into the generated interface jar or drives further pointer arithmetic — a genuine memory-safety violation reachable purely from bytes an unprivileged attacker controls, not from any local/MITM/compromised-infra assumption. This matches the required bar of "read outside the ... exec root" surface: an OOB read outside the intended mapped input buffer performed by a build tool invoked on attacker-supplied content.

### Likelihood Explanation
Any Bazel target consuming an externally-fetched `.jar` (via `http_jar`, `http_archive` producing a jar, `java_import`, or `rules_jvm_external`/Maven-fetched artifacts) that is compiled will have `ijar` run over it via `java_common.run_ijar` to produce an interface jar, unconditionally by default in Java toolchains. sha256/integrity checks on the download only guarantee byte-exact reproduction of the attacker's malicious bytes — they do not validate ZIP structural well-formedness, so a checksum-pinned malicious jar reaches this code path unmodified.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry`, validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the remaining bytes in the mapped central directory before advancing `p`, and change the extra-field walking loop to a `<`/`<=` bound (`while (extra_p < p)`) with an explicit check that each `header_id`/`data_size` read and each `extra_p += data_size` stays within `[extra_p_start, p)`, aborting with an error otherwise (mirroring what `ExtraField::find` in `zip_headers.h` already does correctly for the singlejar tool: `while (start < end) { if (...>end) break; ... }` [8](#0-7) ). Additionally, fix `EnsureRemaining` to avoid unsigned underflow, e.g. by checking `p < zipdata_in_ || (size_t)(p - zipdata_in_) > input_file_->Length()` before computing `remaining`, so an out-of-range `p` derived from an attacker-controlled `offset` is rejected rather than silently passing the bounds check.

### Proof of Concept
A `BuildIntegrationTestCase`/shell-integration reproduction:
1. Hand-craft a minimal ZIP whose central directory entry declares `extra_field_length = N` but embeds an extra-field record with `data_size` larger than `N` (so the sub-field overshoots the declared extra-field region), and/or embeds a Zip64 extra field with an `offset` attribute larger than the file size.
2. Serve this file as the artifact for an `http_jar`/`http_archive` rule with a correct `sha256` pinned to the malicious bytes.
3. Depend on it from a `java_library`/`java_import` target so the build invokes `run_ijar` on it.
4. Run `bazel build` (or invoke `third_party/ijar/ijar` directly as `ijar malicious.jar out.jar`) under AddressSanitizer; observe a heap/global-buffer-overflow read report during `ProcessCentralDirEntry`'s extra-field loop or during the subsequent local-file-header signature read at the attacker-controlled `offset`, confirming the OOB read is reachable purely from the malicious archive content.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
