Based on my analysis, the epoch2x `postblock.rs` handler exhibits the exact same pattern (relay gated solely on `data_resp.accepted`, no auth/broadcast check at all in that endpoint), which suggests this is a deliberate, consistent design in this codebase rather than a broken equality unique to `postblock_v3.rs`. However, focusing strictly on the `postblock_v3.rs` code as written:

### Title
Unauthenticated block upload triggers network-wide relay regardless of `broadcast` flag - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_handle_request` gates the call to `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` only on `data_resp.accepted`, not on `self.broadcast` (which reflects whether the request was authenticated with `broadcast=1`). An attacker who posts a valid, acceptable Nakamoto block with no `broadcast` query parameter (and thus no `authorization` header) can still cause the node to queue the block for relay to the rest of the P2P network.

### Finding Description
In `try_parse_request` [1](#0-0) , `broadcast` and `authenticated` are computed and the handler only rejects the request with 401 when `broadcast && !authenticated`; an unauthenticated request with no `broadcast` query arg passes through fine, and `self.broadcast` is set to `false`.

In `try_handle_request`, the block is passed to `Relayer::process_new_nakamoto_block_ext` with `self.broadcast.unwrap_or(false)` as the "should announce/broadcast" argument to internal chain processing [2](#0-1) . Separately, after processing, the code checks only `data_resp.accepted` — which is set from `accepted.is_accepted()` — to decide whether to call `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))`: [3](#0-2) 

This means `self.broadcast` (and thus the authentication requirement tied to it) has no bearing on whether `set_relay_message` fires. Any block that is locally "accepted" by chainstate processing (e.g., a well-formed block building on a known/valid parent) is queued for relay to the P2P network, regardless of whether the poster ever supplied the secret.

### Impact Explanation
This lets an unauthenticated remote party who can reach the node's `/v3/blocks/upload/` RPC endpoint cause the node to relay a `NakamotoBlocksData` message to its P2P peers, using the node as an unauthenticated relay/amplifier for blocks the attacker constructs. This matches the "network-wide propagation of forged data" Critical impact category, provided the block can be made to satisfy `is_accepted()` without requiring the poster to be an authorized miner/signer (note: whether an arbitrary attacker-controlled block can pass full chainstate/signature validation and reach `is_accepted()==true` depends on `process_new_nakamoto_block_ext`/chainstate validation internals, which are explicitly out of scope ["consensus block-validation internals"] for this audit — I could not fully verify within this session whether a truly adversarial, non-canonical block could reach `is_accepted()`).

### Likelihood Explanation
The `/v3/blocks/upload/` RPC endpoint is remotely reachable by any peer connecting to the node's HTTP RPC port, requiring no privileged role, no secret, and no prior relationship with the node — only that the endpoint is exposed (this is the standard node-operator configuration for blocks-upload). The precondition is that the submitted block passes `Relayer::process_new_nakamoto_block_ext`'s acceptance check, which is gated by consensus/chainstate validation logic explicitly out-of-scope for this audit ("consensus block-validation internals"). Because that validation gate is out of scope and its exact strength for a non-signer attacker is not verified here, I cannot confirm that an attacker without any consensus standing (miner/signer keys) can actually produce a block that reaches `is_accepted()==true`.

### Recommendation
Gate the `set_relay_message` call on `self.broadcast == Some(true)` (and implicitly, since parse-time already enforces `authenticated` when `broadcast` is true) in addition to `data_resp.accepted`, e.g. `if data_resp.accepted && self.broadcast.unwrap_or(false) { node.set_relay_message(...) }`, matching the documented intent that only authenticated `broadcast=1` requests cause propagation.

### Proof of Concept
A Rust test in `stackslib::net::api::tests::postblock_v3` should: construct a `RPCPostBlockRequestHandler` with `auth` set to a known secret; build a `StacksHttpRequest` via `StacksHttpRequest::new_post_block_v3` (no `broadcast` query arg, no `authorization` header) carrying a block payload that the test's mocked/mined chainstate will accept; invoke `try_parse_request` and `try_handle_request` against a `StacksNodeState` wrapping that chainstate; and assert that `data_resp.accepted == true` while `node.get_relay_message()` (or equivalent internal relay-message state) remains `None`/unset. Currently this assertion would fail because `set_relay_message` fires whenever `accepted` is true, irrespective of `broadcast`/`authenticated`.

**Caveat:** I could not fully confirm, within the code paths available in this session, whether an attacker lacking any consensus role (miner/signer signatures) can produce a block that satisfies `Relayer::process_new_nakamoto_block_ext`'s acceptance criteria — that validation logic is explicitly out of scope for this audit ("consensus block-validation internals"), so the ultimate exploitability depends on a component I was instructed not to analyze in depth.
