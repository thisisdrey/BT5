Audit Report

## Title
Reentrant CREATE2-style instantiate collision in `pallet-contracts` bypasses the `DuplicateContract` guard during constructor execution - (File: `substrate/frame/contracts/src/exec.rs`)

## Summary
`pallet-contracts` derives salted contract addresses independently of the deployer's nonce via `DefaultAddressGenerator::contract_address` [1](#0-0) , and its sole duplicate-contract guard, `ContractInfo::new`, only checks whether `ContractInfoOf::contains_key(account)` is set in on-chain storage [2](#0-1) . Because `push_frame` only flushes an in-flight `ContractInfo` to `ContractInfoOf` when the parent frame is a `Call` frame, not a `Constructor` frame [3](#0-2) , a reentrant call graph can trigger a second `instantiate` for the same `(sender, code_hash, input_data, salt)` tuple while the first constructor is still executing, and `Ext::instantiate` performs no additional recursion/collision check before calling `push_frame` [4](#0-3) .

## Finding Description
The exploit path is: a factory contract `F`'s `Call` frame instantiates code `C` with salt `S`, producing address `X = contract_address(F, C, [], S)`; `X`'s `Constructor` frame reenters `F` via `ext.call` (a `Call` frame, allowed by default reentrancy settings); this second `F` `Call` frame invokes `ext.instantiate(C, S)` again, which resolves to the same address `X` because the formula is nonce-independent [5](#0-4) . `push_frame` is called with `FrameArgs::Instantiate`, and `ContractInfo::new(&X, ...)` only checks `ContractInfoOf::contains_key(X)`, which is still `false` because the first `Constructor` frame for `X` has never been committed (the write in `push_frame` is gated on `frame.entry_point == ExportedFunction::Call`, and the top frame at that point is `X`'s own uncommitted `Constructor` frame, not a `Call` frame) [6](#0-5) . Unlike `pallet-revive`'s `push_frame`, which explicitly scans `self.frames()` for a colliding in-flight `Constructor` frame and rejects with `DuplicateContract` [7](#0-6) , `pallet-contracts`'s `push_frame` and `Ext::instantiate` have no equivalent stack-scan guard, so a second `Constructor` frame for account `X` is pushed and executed. This is distinct from the existing protection for `Call` reentrancy into a not-yet-constructed contract (`recursive_call_during_constructor_fails`, which relies on `ContractInfoOf::get` failing for `Call` dispatch) [8](#0-7)  — that guard only covers `Call` entry into the same address, not a second `Instantiate` at the same address via a reentrant call graph through an intermediary contract.

## Impact Explanation
A second `Constructor` frame executing for an address whose first constructor is still in-flight duplicates one-time side effects — code refcount increments, storage-deposit charges, and child-trie allocation for `ContractInfo` — for a single account `X`. This matches the "duplicate settlement" / permanent storage-deposit lock impact class: the second child trie allocated for `X` is orphaned once the outer constructor eventually completes and only one `ContractInfo` is retained, while the storage-deposit meter charged the deploying account for both trie allocations.

## Likelihood Explanation
The path requires only an unprivileged account deploying an ordinary factory contract that (a) instantiates a child with a fixed `(code_hash, salt)`, and (b) has that child's constructor call back into the factory's `Call` export, which instantiates again with the identical `(code_hash, salt)`. No special permissions, validator, or relayer involvement is needed — this is reachable purely through the public `instantiate`/`instantiate_with_code` extrinsics and ordinary contract-to-contract calls. The exact analog was serious enough to warrant a dedicated fix in the sibling `pallet-revive` pallet (`prdoc/pr_12645.prdoc`), and `pallet-contracts`'s `push_frame`/`Ext::instantiate` were confirmed to lack the equivalent guard.

## Recommendation
Port the `pallet-revive` fix to `pallet-contracts`: in `push_frame` (`substrate/frame/contracts/src/exec.rs`), after constructing the new frame via `Self::new_frame`, scan `self.frames()` for an existing `Constructor` frame with the same `account_id` as the newly-created frame and return `Error::<T>::DuplicateContract` before pushing it onto `self.frames`, mirroring `substrate/frame/revive/src/exec.rs:1238-1246`.

## Proof of Concept
1. Deploy factory contract `F` whose `Call` export, on its first invocation, calls `seal_instantiate` with fixed `(code_hash = C, salt = S)`, producing child `B` at address `X = contract_address(F, C, [], S)`.
2. `B`'s `Constructor` export calls back into `F`'s `Call` export (`ext.call(F, ...)`, allowed since `allows_reentry` defaults to `true` unless the parent explicitly disables it).
3. `F`'s second `Call` invocation calls `seal_instantiate` again with the same `(C, S)`, resolving to the same address `X`.
4. `push_frame` -> `ContractInfo::new(&X, ...)` passes because `ContractInfoOf::contains_key(X)` is still `false` (first `Constructor` frame for `X` uncommitted), pushing a second `Constructor` frame for account `X` — reproducible as a unit test analogous to `reentrant_instantiate_at_same_address_is_rejected` in `substrate/frame/revive/src/exec/tests.rs:1270-1350`, adapted to `pallet-contracts`'s `MockStack`/`MockLoader` test harness, asserting the second `instantiate` call incorrectly returns `Ok` instead of `Error::<T>::DuplicateContract`.

	/// Formula: `hash("contract_addr_v1" ++ deploying_address ++ code_hash ++ input_data ++ salt)`
	fn contract_address(
		deploying_address: &T::AccountId,
		code_hash: &CodeHash<T>,
		input_data: &[u8],
		salt: &[u8],

	/// Create a subsequent nested frame.
	fn push_frame(
		&mut self,
		frame_args: FrameArgs<T, E>,
		value_transferred: BalanceOf<T>,
		gas_limit: Weight,
		deposit_limit: BalanceOf<T>,
		read_only: bool,
	) -> Result<E, ExecError> {
		if self.frames.len() == T::CallStack::size() {
			return Err(Error::<T>::MaxCallDepthReached.into());
		}

		// We need to make sure that changes made to the contract info are not discarded.
		// See the `in_memory_changes_not_discarded` test for more information.
		// We do not store on instantiate because we do not allow to call into a contract
		// from its own constructor.
		let frame = self.top_frame();
		if let (CachedContract::Cached(contract), ExportedFunction::Call) =
			(&frame.contract_info, frame.entry_point)
		{
			<ContractInfoOf<T>>::insert(frame.account_id.clone(), contract.clone());
		}

		let frame = top_frame_mut!(self);
		let nested_gas = &mut frame.nested_gas;
		let nested_storage = &mut frame.nested_storage;
		let (frame, executable, _) = Self::new_frame(
			frame_args,
			value_transferred,
			nested_gas,
			gas_limit,
			nested_storage,
			deposit_limit,
			self.determinism,
			read_only,
		)?;
		self.frames.push(frame);
		Ok(executable)
	}

	fn instantiate(
		&mut self,
		gas_limit: Weight,
		deposit_limit: BalanceOf<Self::T>,
		code_hash: CodeHash<T>,
		value: BalanceOf<T>,
		input_data: Vec<u8>,
		salt: &[u8],
	) -> Result<(AccountIdOf<T>, ExecReturnValue), ExecError> {
		let executable = E::from_storage(code_hash, self.gas_meter_mut())?;
		let nonce = self.next_nonce();
		let executable = self.push_frame(
			FrameArgs::Instantiate {
				sender: self.top_frame().account_id.clone(),
				nonce,
				executable,
				salt,
				input_data: input_data.as_ref(),
			},
			value,
			gas_limit,
			deposit_limit,
			self.is_read_only(),
		)?;
		let account_id = self.top_frame().account_id.clone();
		self.run(executable, input_data).map(|ret| (account_id, ret))
	}
