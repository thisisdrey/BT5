### Title
No vulnerability found for this question.

### Summary
The question's premise inverts the actual semantics of the `Err(_) => amount.0` branch in `ft_resolve_withdraw`. In that branch, `used` is set to the full `amount.0`, which makes `refund = amount.0.saturating_sub(used) = 0`, meaning the contract deliberately issues **no refund** when the promise result is unreadable — the opposite of the "full refund" the exploit narrative depends on.

### Finding Description
The claimed binding is: `debited_at_withdraw == externally_delivered + refund_by_ft_resolve_withdraw`, with the attack asserting `refund_by_ft_resolve_withdraw == amount.0` in the `Err(_)` branch. Reading the actual code at [1](#0-0)  shows `used` (not `refund`) is set to `amount.0` in the `Err(_)` branch, and `refund = amount.0.saturating_sub(used)`, which evaluates to `0`. The inline comment explicitly documents the rationale: on `PromiseError` (unreadable promise result, e.g. due to insufficient gas to read `ft_on_transfer`'s outcome), the code assumes the transfer succeeded and treats the withdrawal as fully "used" to avoid **double-crediting** the sender — the exact opposite of what the question's exploit needs. This design choice can, in the worst case, cause the signer to lose funds if the transfer actually failed and gas just ran out for reading the result (a conservative/defensive bias), but it can never cause a refund to be issued alongside external delivery of tokens, because no `self.deposit` call happens on that path at all (`refund > 0` is false, so the `if refund > 0` block at [2](#0-1)  never executes).

### Impact Explanation
No funds move, are credited, or are duplicated as a result of this branch; the reentrancy scenario described (attacker's `ft_on_transfer` re-entering `execute_intents`) does not interact with any refund because none is issued.

### Likelihood Explanation
Not applicable — the described binding violation does not occur under the actual code semantics.

### Recommendation
No fix needed for this specific claim. (Separately, note the documented trade-off that the `Err(_)` branch can cause signer fund loss rather than double-credit, but that is an existing, intentional, documented design decision, and represents the opposite risk direction from the one alleged.)

### Proof of Concept
Not applicable; a `cargo test` asserting `refund_by_ft_resolve_withdraw == 0` when `promise_result_checked_json` returns `Err(_)` would directly confirm the actual (safe) behavior and falsify the question's premise.
