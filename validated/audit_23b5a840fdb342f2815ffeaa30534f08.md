Audit Report

## Title
Pre-fundable, deterministic pool account lets an unprivileged attacker permanently grief first-liquidity provision in `pallet-asset-conversion` - (File: substrate/frame/asset-conversion/src/lib.rs, substrate/frame/asset-conversion/src/types.rs)

## Summary
`AccountIdConverter::try_convert` derives a pool's `AccountId` deterministically from `blake2_256(Seed, PoolId)`, where `PoolId` is just the ordered pair of public `AssetKind`s, with no dependency on pool creation state or a nonce. Any unprivileged actor can compute this address ahead of time and transfer funds directly to it before `create_pool`/`add_liquidity` is ever called, corrupting the `reserve1`/`reserve2` values that `do_add_liquidity` reads via live balance lookups and forcing legitimate first-liquidity deposits to revert.

## Finding Description
The pool account is computed purely from public data with `sp_io::hashing::blake2_256(&Encode::encode(&(Seed::get(), id))[..])` [1](#0-0)  which means the address for any asset pair is known before `create_pool` is dispatched.

`do_create_pool` inserts `PoolInfo` and touches asset accounts for `pool_account` but never checks or clears any pre-existing balance already sitting at that address [2](#0-1) .

`do_add_liquidity` then reads `reserve1`/`reserve2` unconditionally from live balances at `pool_account` via `Self::get_balance`, and branches the first-provision logic solely on whether either reserve is zero [3](#0-2) . If an attacker has pre-funded both assets at `pool_account` with a skewed ratio, this branch is bypassed and the code instead falls into the `quote`-based branch, computing `amount1`/`amount2` against the attacker's ratio instead of the caller's desired amounts, which can trip `AssetTwoDepositDidNotMeetMinimum` or `OptimalAmountLessThanDesired`.

Even when that branch doesn't itself revert, `total_supply.is_zero()` still routes into `calc_lp_amount_for_zero_supply` using the now-distorted `amount1`/`amount2`, and the resulting `lp_token_amount` is checked against `T::MintMinLiquidity::get()` [4](#0-3) . By skewing the donated ratio, an attacker can force the legitimate depositor's `lp_token_amount` computation to fall at or below `MintMinLiquidity`, reverting with `InsufficientLiquidityMinted` — the same mechanic exercised (for an unrelated tiny-amount scenario) in the existing test `add_tiny_liquidity_leads_to_insufficient_liquidity_minted_error` [5](#0-4) .

No existing guard prevents this: reserves are derived from a live, attacker-writable balance rather than from dedicated, pallet-controlled reserve accounting, and pool creation performs no sweep/zeroing of the pool account's pre-existing balance.

## Impact Explanation
The bug corrupts the values `reserve1` and `reserve2` (and, downstream, `amount1`/`amount2`/`lp_token_amount`) used by `do_add_liquidity`, which compromises the intended behavior of the permissionless pool-bootstrap flow: "create pool → provide first liquidity" for a targeted asset pair can be made to revert repeatedly for any amount a legitimate user chooses that doesn't match the attacker's imposed ratio. This is a runtime bug that compromises intended pallet behavior for a public, unprivileged extrinsic path, though the effect is a repeatable griefing/DoS of a specific pool's bootstrap rather than a fund theft, duplicate settlement, or an irreversible on-chain fund lock (each failing extrinsic reverts atomically without loss to the victim).

## Likelihood Explanation
No privileged actor, colluding validator, relayer, or compromised prover is required, and no front-running of a specific transaction is needed since the pool address is computable and fundable well in advance of `create_pool`/`add_liquidity`. The attack cost is bounded by existential-deposit-level token amounts and is trivially repeatable after every failed attempt, making it a low-cost, highly repeatable griefing vector against any specific asset pair an attacker chooses to target.

## Recommendation
Do not derive first-liquidity acceptance/mint math from live balances at the pool account. Track pool reserves in dedicated, pallet-controlled storage that is updated only through `do_add_liquidity`/`do_remove_liquidity`/swap logic, or alternatively sweep/burn any un-attributed balance at `pool_account` at `create_pool` time before allowing the first `add_liquidity` call to branch on the "zero reserve" path.

## Proof of Concept
1. Compute `pool_account = AccountIdConverter::try_convert(&(asset1, asset2))` for a target asset pair — this only requires public asset identifiers, no on-chain pool state.
2. Attacker transfers a small amount of `asset1` and a disproportionate amount of `asset2` directly to `pool_account` via ordinary `transfer` calls (not through the pallet), at any time before the victim acts.
3. Victim calls `create_pool(asset1, asset2)`, which succeeds and inserts `Pools` with `lp_token` total_supply still 0 (`do_create_pool`, substrate/frame/asset-conversion/src/lib.rs L729-788).
4. Victim calls `add_liquidity` with a balanced, "normal" `amount1_desired`/`amount2_desired`.
5. Because `reserve1`/`reserve2` are both non-zero from step 2, execution takes the `quote` branch instead of seeding at the victim's desired ratio (substrate/frame/asset-conversion/src/lib.rs L813-844); the deposit reverts on `AssetTwoDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired`, or produces `lp_token_amount <= MintMinLiquidity`, reverting with `InsufficientLiquidityMinted` (substrate/frame/asset-conversion/src/lib.rs L858-877), mirroring the mechanics in `add_tiny_liquidity_leads_to_insufficient_liquidity_minted_error` (substrate/frame/asset-conversion/src/tests.rs L422-466).
6. The attacker can repeat the donation after each failed attempt at negligible cost, indefinitely griefing bootstrap of that specific pool.

impl<Seed, PoolId, AccountId> TryConvert<&PoolId, AccountId> for AccountIdConverter<Seed, PoolId>
where
	PoolId: Encode,
	AccountId: Decode,
	Seed: Get<PalletId>,
{
	fn try_convert(id: &PoolId) -> Result<AccountId, &PoolId> {
		sp_io::hashing::blake2_256(&Encode::encode(&(Seed::get(), id))[..])
			.using_encoded(|e| Decode::decode(&mut TrailingZeroInput::new(e)).map_err(|_| id))
	}
