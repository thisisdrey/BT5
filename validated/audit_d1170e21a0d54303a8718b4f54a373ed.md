## Title
Out-of-bounds read of Central Directory Header fields due to insufficient bounds checking in `InputJar::NextEntry` - ([File: src/tools/singlejar/input_jar.h])

## Summary
`InputJar::NextEntry` in `src/tools/singlejar/input_jar.h` walks the Central Directory of a jar/zip archive by trusting the `size()` computed from a `CDH` record's own fixed fields, then verifies only that the *first byte* of the next record's address is inside the mapped file before dereferencing the full 46-byte `CDH` struct on the following iteration. A crafted archive (e.g. a hostile `http_archive`/`http_jar` download whose declared checksum matches but internal zip structure is malformed, or a crafted `.jar`/`.zip` processed by `singlejar`/`one_version`) can position a truncated/fake `CDH` header exactly at the tail of the mapped file, causing reads of `CDH` fields beyond the end of the mapping.

## Finding Description
`MappedFile::mapped()` only checks a single address against `[mapped_start_, mapped_end_)`: [1](#0-0) 

`InputJar::NextEntry` uses this single-pointer check to validate the *next* `CDH` position, not the full struct extent needed to safely read it: [2](#0-1) 

Specifically:
1. `new_cdr = cdh_ + cdh_->size()` is computed from the *current* record's `file_name_length()/extra_fields_length()/comment_length()` fields, which are attacker-controlled.
2. `mapped_file_.mapped(new_cdr)` verifies only that `new_cdr` (a single byte address) lies within `[mapped_start_, mapped_end_)` — it does **not** verify that `new_cdr + sizeof(CDH)` (46 bytes, per the `static_assert(46 == sizeof(CDH), ...)`) is also within bounds.
3. `cdh_` is then set to `new_cdr`, and on the *next* call to `NextEntry`, `cdh_->is()` immediately dereferences 4 bytes at `cdh_` (the signature), and if that passes, subsequent code (`cdh_->size()`) reads `file_name_length_`, `extra_fields_length_`, and `comment_length_` — fields located at offsets 10, 12, and 14+ bytes into the 46-byte struct: [3](#0-2) 

If `new_cdr` is positioned so that only 1 byte (or any amount less than 46 bytes) remains before `mapped_end_`, the single-pointer check in `mapped()` passes, yet dereferencing `cdh_->is()`, `cdh_->file_name_length()`, etc. reads past `mapped_end_`. This is structurally identical to the CVE-2024-41014 class of bug: `xlog_recover_process_data` validated that some bytes remained before the record boundary, but not that the *entire fixed-size header* fits — here, `mapped()` validates only the start pointer, not that `sizeof(CDH)` bytes are available for the fixed members.

The same missing-full-struct-bounds-check pattern also appears in `InputJar::LocateCentralDirectory`, which dereferences `ECD64Locator`/`ECD64`/`CDH` structs computed from potentially-attacker-controlled offsets (`ecd->cen_offset32()`, `ecd64loc->ecd64_offset()`) with only single-address or coarse size checks: [4](#0-3) 

## Impact Explanation
This is a heap/mmap out-of-bounds *read* triggered by processing an untrusted `.jar`/`.zip` archive — e.g. a maliciously crafted archive fetched via `http_archive`/`http_jar` (whose declared `sha256`/`integrity` only protects file *content* integrity, not the internal zip structural invariants relied upon by `singlejar`, `ijar`, or `one_version` when later processing the archive as a jar), or a crafted `.jar` built from an untrusted branch consumed by `singlejar` during the build. The read can leak adjacent process memory into diagnostics (`diag_errx` prints `file_name_length`, etc., which are read fine, but the OOB read itself may crash the process via SIGSEGV if it crosses a page boundary) — most likely manifesting as a crash/DoS of the `singlejar` tool process, and in the worst case an information leak of adjacent heap/mmap memory content if that content is echoed back (e.g., through error messages including truncated field values, or via memory contents interpreted as subsequent header fields).

## Likelihood Explanation
`singlejar` and related jar-processing tools (`one_version`, `ijar`) are invoked during ordinary Bazel Java builds to merge/process JAR files, including those originating from external dependencies (`http_jar`, `http_archive`, remote registries). An attacker who controls the bytes of a JAR/ZIP file consumed at build time (a dependency artifact) can constructs the ZIP's End-Of-Central-Directory / Central-Directory-Header chain to place a record boundary exactly near the end of the mapped file, satisfying `mapped()`'s single-address check while still causing a full 46-byte-struct read to run off the end of the mapping. This requires only attacker control of file bytes, matching the "unprivileged attacker publishing a dependency artifact" threat model — no MITM or credential access needed. A `sha256`/`integrity` check on the archive as a whole does not validate internal ZIP structural consistency, so it does not prevent this.

## Recommendation
In `InputJar::NextEntry` (and similarly in `LocateCentralDirectory`), replace the single-pointer `mapped_file_.mapped(new_cdr)` check with a check that the *entire* fixed-size `CDH` struct (`sizeof(CDH)`, i.e., 46 bytes) fits within the mapped region before dereferencing any of its fields — e.g., verify `new_cdr + sizeof(CDH) <= mapped_file_.end()` (and, additionally, that `new_cdr + cdh_->size()` — including variable-length name/extra/comment — stays within bounds before advancing further). Apply the same "fixed member space" bounds check pattern used to fix CVE-2024-41014 in xlog_recover_process_data: verify sufficient remaining bytes for the fixed portion of the header *before* accessing any of its fields, not just that the header's start address is in-bounds.

## Proof of Concept
A `BuildIntegrationTestCase`/shell-test style PoC (analogous to existing tests in `src/tools/singlejar/input_jar_random_jars_test.cc` / `input_jar_preambled_test.cc`) would:
1. Construct a minimal valid ZIP with one `CDH` record whose `file_name_length + extra_fields_length + comment_length` is crafted such that `cdh_ + cdh_->size()` equals `mapped_end_ - 1` (one byte before the end of the mapped file) — this passes `mapped_file_.mapped(new_cdr)` because `new_cdr < mapped_end_`.
2. Call `InputJar::Open()` then `InputJar::NextEntry()` twice; the second call dereferences the fabricated `CDH*` at `mapped_end_ - 1`, reading `signature_`, `file_name_length_`, etc., 46 bytes past a 1-byte-remaining region — an out-of-bounds read detectable under ASan (`-fsanitize=address`) as a heap-buffer-overflow / SEGV, mirroring the kernel PoC's technique of placing `xlog_op_header` fields 1 byte from the record boundary.
