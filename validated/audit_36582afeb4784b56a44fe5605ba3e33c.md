Audit Report

## Title
Oracle median aggregation returns the upper-middle element instead of the true average for even-sized operator sets - (File: `substrate/frame/honzon/oracle/src/default_combine_data.rs`)

## Summary
`DefaultCombineData::combine_data` computes `mid_index = count / 2` and then calls `values.select_nth_unstable_by(mid_index, ...)` to select a single value as the "median" of all valid, non-expired operator submissions [1](#0-0) . For an even `count`, this returns only the element at the upper-middle sorted position rather than the average of the two central values, producing a mathematically incorrect and skewed aggregated price that is written to the `Values` storage consumed by all downstream `DataProvider` callers.

## Finding Description
`combine_data` filters expired `TimestampedValue`s, checks the minimum count, and then partitions the remaining values with `select_nth_unstable_by(mid_index as usize, ...)` where `mid_index = count / 2` [2](#0-1) . `select_nth_unstable_by` guarantees that the element placed at the given index is exactly the element that would occupy that index if the slice were fully sorted — it does not perform any averaging. For an even-length sorted sequence, the true median is `(values[count/2 - 1] + values[count/2]) / 2`, but this code returns only `values[count/2]`, which is always the higher of the two central elements. The identical flawed pattern is duplicated in the generic `median()` helper in `traits.rs`, used by the `create_median_value_data_provider!` macro [3](#0-2) , and this is corroborated by the pallet's own unit test, which asserts `get(&0)` returns `7` (not `6`, the true average of `5` and `7`) for the even-count input `[Some(5), Some(13), Some(2), Some(7)]` sorted as `[2,5,7,13]` [4](#0-3) . This test result directly confirms the bug is present and even codified as "expected" behavior in the test suite, rather than being an isolated typo.

The result of `combine_data` is written into the `Values` storage map on every `feed_values`/`feed_value` dispatch via `combined()` [5](#0-4) [6](#0-5) , and is exposed to any consumer through `DataProvider::get`, `DataProviderExtended::get_all_values`, and the pallet's public view functions `get_value`/`all_values` [7](#0-6) [8](#0-7) . There is no existing guard anywhere in `combine_data`, `median()`, or the calling code that corrects for the even-count case.

## Impact Explanation
This is a genuine logic/off-by-one defect in the pallet's core data-aggregation algorithm, matching the "runtime bugs that compromise intended behavior" class in the impact gate. Every downstream consumer that relies on `DataProvider`/`DataProviderExtended`/`get_value` for price-dependent logic (e.g., collateral valuation, liquidation triggers in a CDP-style module built on this oracle) will receive a systematically skewed aggregated value whenever the number of currently valid raw submissions for a key is even, with the deviation magnitude scaling with the spread between the two true middle values (the PoC in the claim demonstrates a ~20% deviation).

## Likelihood Explanation
The trigger condition — an even count of valid, non-expired raw values for a given key — occurs naturally through ordinary use of the permissioned `feed_values` extrinsic by legitimate, authorized oracle members (or expiry of older submissions), and requires no malicious collusion or privileged/administrative action beyond the already-granted operator role. It is deterministic and fully reproducible any time the operator set submitting fresh data for a key is even-sized, which is a common and unremarkable operational state, not an edge case requiring adversarial effort.

## Recommendation
Fix `combine_data` (and the analogous `median()` helper in `traits.rs`) to implement the correct median formula: for odd `count`, return the value at `count/2`; for even `count`, average the values at `count/2 - 1` and `count/2`. Since `OracleValue` is bounded only by `Parameter + Member + Ord` with no arithmetic operations, this requires adding a numeric bound (e.g., `Saturating`/`CheckedAdd` plus a division capability, or a configurable "average" trait) so genuine averaging can be performed generically, or explicitly documenting/adjusting the pallet's semantics if "upper of the two middle values" is the accepted design.

## Proof of Concept
Using the pallet's own test in `traits.rs`: feed values `[Some(5), Some(13), Some(2), Some(7)]` from four providers. Sorted ascending: `[2, 5, 7, 13]`. `count = 4`, `mid_index = 2`. `select_nth_unstable_by(2, ...)` places `7` at index 2 and returns it as the median, while the mathematically correct median is `(5 + 7) / 2 = 6`. The existing assertion `assert_eq!(<Providers as DataProvider<_, _>>::get(&0), Some(7))` in `traits.rs` lines 155/164 [9](#0-8)  confirms this exact deviation is produced by the current implementation. The same flaw applies to `combine_data` in `default_combine_data.rs` for `Values` storage updates on `feed_values`.

/// Returns the median of a list of values.
pub fn median<T: Ord + Clone>(mut items: Vec<T>) -> Option<T> {
	if items.is_empty() {
		return None;
	}

	let mid_index = items.len() / 2;

	// Won't panic as `items` ensured not empty.
	let (_, item, _) = items.select_nth_unstable(mid_index);
	Some(item.clone())
}
