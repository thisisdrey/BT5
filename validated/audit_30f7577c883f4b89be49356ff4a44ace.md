### Title
Precompiled contract array-length helpers allocate unbounded memory from attacker-controlled call data before any length validation - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.java` contains three private helper methods — `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` — that are used to decode dynamic arrays (of `bytes32`, `bytes`, and signatures) out of the raw `data` byte array passed to a TVM precompiled contract call. Each of them reads a 32-byte word from the caller-controlled input, converts it to an `int` via `DataWord.intValueSafe()`, and immediately uses that value as the size of a new array — with no check that the declared length is consistent with the actual size of `data`/`words`.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` decode the "array length" word straight from attacker-supplied `data`: [1](#0-0) [2](#0-1) 

In each function, `int len = words[offset].intValueSafe();` is taken directly from the call data with no validation that `len` is compatible with the remaining bytes of `words`/`data`, and `new byte[len][]` is allocated immediately afterwards — before any loop bound, offset, or bytes-available check is performed. `DataWord.intValueSafe()` only prevents overflow of the Java `int` type; it caps the returned value at `Integer.MAX_VALUE` (~2.1 billion) rather than validating it against the actual payload size, so a single 32-byte word in the call data (e.g. `0xFFFFFFFF...`) is enough to request an object array with over two billion elements.

This mirrors the DeepDiff bug class exactly: a size/length value taken from untrusted, attacker-supplied serialized input is used directly as a memory-allocation size with no upper bound or consistency check against the true amount of available data, producing an extreme amplification between payload size (32 bytes) and memory committed by the JVM (tens of gigabytes for the backing object array alone).

These helpers are used while decoding parameters for precompiled contracts invoked via the TVM `CALL`/`STATICCALL` opcodes to fixed precompile addresses (e.g. multi-signature/array based precompiles). Because any deployed smart contract can invoke a precompiled contract address with attacker-chosen `data`, any unprivileged contract deployer/caller can trigger this code path by simply calling the corresponding precompile with a crafted length word.

### Impact Explanation
An attacker who deploys or calls a contract that invokes the affected precompiled contract with a crafted 32-byte length word can force the executing full node/SR to attempt allocation of an object array with billions of elements. This will trigger an `OutOfMemoryError`/large GC pause on the node evaluating the transaction, up to and including node crash or denial of service for block validation/execution — impacting availability of the network node processing the transaction (and potentially block application in `Manager` if this happens during block replay by validators). This satisfies the "node crash or halt" impact bar.

### Likelihood Explanation
The trigger requires only a single, tiny, well-formed transaction that calls the precompiled contract with a crafted length word — no special privileges, no coordination among validators, and no reliance on chain state. This is directly analogous to the "813,000x amplification" and "any application deserializing untrusted data" characterization in the referenced DeepDiff advisory, making this trivially reachable by any unprivileged transaction broadcaster/contract deployer.

### Recommendation
Bound the decoded `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` against the actual number of remaining `words`/bytes in `data` before allocating any array, and reject (revert) the precompiled-contract call if the declared length is inconsistent with the size of the supplied call data, mirroring the bounds checks already present elsewhere in the codebase (e.g. `RLP.verifyLength` and `ContractEventParser.subBytes`). ### Proof of Concept
1. Deploy any contract that performs a `CALL`/`STATICCALL` to the precompiled contract address whose `execute()` decodes arrays via `extractBytesArray`/`extractSigArray`/`extractBytes32Array`.
2. Craft the call data so that the word at the expected `offset` position is close to `0xFFFFFFFF` (i.e. large enough that `DataWord.intValueSafe()` returns a value near `Integer.MAX_VALUE`), while keeping the total call data tiny (well under 100 bytes).
3. Broadcast the transaction. During execution, `new byte[len][]` (with `len` near 2^31) is executed immediately, forcing the JVM to attempt to allocate a multi-gigabyte object array before any bounds/array-length validation, producing `OutOfMemoryError` and degraded/crashed node execution — same amplification pattern (small payload, huge allocation) demonstrated in the referenced DeepDiff PoC.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
