## Title
Contract owner can instantly and repeatedly change `consumeUserResourcePercent` to frontrun/rug callers into paying energy fees they did not expect - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java`)

### Summary
`UpdateSettingContract` lets the deployer/origin address of a smart contract change, at any time and with no delay, the percentage of TVM energy cost that callers must pay versus the amount the contract's frozen-energy owner subsidizes. This mirrors the Fractional `setRoyalties` bug class: a single privileged-but-otherwise-unprivileged actor (here, any contract deployer, not a validator/SR) unilaterally controls an economic fee-split parameter that directly affects third-party counterparties (callers), and can flip it instantly, right before a victim's transaction lands, then revert it afterward.

### Finding Description
`UpdateSettingContractActuator.execute()` directly overwrites `consume_user_resource_percent` on the `ContractCapsule` as soon as the transaction is processed, with no delay/timelock and no history/limit on how often it may be changed: [1](#0-0) 

The only guard in `validate()` is a static bound check (`0 <= percent <= 100`) and an ownership check against the contract's `originAddress`: [2](#0-1) 

This `consumeUserResourcePercent` value is the parameter that later determines, at the moment a *caller* (a completely different, unprivileged account) invokes the contract, how the energy bill is split between the contract's frozen-energy owner ("origin") and the caller: [3](#0-2) 

and it is fetched fresh from the `ContractStore` at the time of each individual call/bill: [4](#0-3) 

Because there is no restriction on how frequently `UpdateSettingContract` can be broadcast, a malicious dApp owner can:
1. Deploy a contract and set `consumeUserResourcePercent = 0` (i.e., "free to use, the owner pays all energy"), advertising it to attract users/liquidity/large calls.
2. Watch the mempool for a user's large, energy-expensive transaction targeting the contract.
3. Front-run it with `UpdateSettingContract` setting `consumeUserResourcePercent = 100`, shifting the entire energy bill onto the caller.
4. After the victim's transaction executes (and pays unexpectedly high fees, potentially reverting for insufficient energy/balance, wasting bandwidth/TRX or losing funds due to a failed multi-step operation), reset the percent back to 0 to keep advertising "free" usage to the next victim.

This is exactly analogous to the referenced Fractional finding: an owner-controlled fee parameter with no timelock lets the privileged party retroactively extract value from an unsuspecting counterparty at the moment of a high-value transaction.

### Impact Explanation
Victims (any unprivileged account calling the contract) can be forced to pay an arbitrarily large, unexpected energy fee (up to 100% of the transaction's energy cost) that they did not budget for when they built and signed their transaction based on the contract's previously observed 0%/low percent setting. In energy-scarce circumstances this can also cause the caller's transaction to unexpectedly burn TRX balance (per `ReceiptCapsule.payEnergyBill`) or fail entirely after having already committed state changes/side effects, effectively stealing value/fees from the caller and undermining fee predictability guaranteed by the on-chain state at broadcast time. [5](#0-4) 

### Likelihood Explanation
Any account that deploys a smart contract (an unprivileged, permissionless action) is the `originAddress`/owner and can call `UpdateSettingContract` at will — there is no cooldown, no cap on frequency, and no timelock. Mempool front-running of a known high-value call is a standard, low-cost attack pattern, making this readily exploitable by any malicious contract author.

### Recommendation
Introduce a minimum time delay (timelock) between changes to `consumeUserResourcePercent`, and/or restrict how often it can decrease/increase within a window, and/or snapshot the percent used for fee-splitting at the time the caller's transaction was broadcast (e.g., via commitment in the transaction) rather than reading the live value at execution time, so that a contract owner cannot retroactively change the economics of an already-signed and pending transaction.

### Proof of Concept
1. Deployer creates contract `C` and calls `UpdateSettingContract{contract_address=C, consume_user_resource_percent=0}` via `UpdateSettingContractActuator`, so `C.consumeUserResourcePercent = 0` (owner absorbs all energy cost) — see `UpdateSettingContractActuator.execute()` [1](#0-0) .
2. A user, observing this setting, broadcasts a large `TriggerSmartContract` call to `C` expecting zero/near-zero energy cost.
3. Deployer detects the pending transaction in the mempool and broadcasts `UpdateSettingContract{contract_address=C, consume_user_resource_percent=100}` with a higher fee/priority so it lands first.
4. `getTotalEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFloatRatio` now compute the caller's share using `consumeUserResourcePercent=100` [6](#0-5) , and `TransactionTrace.pay()`/`ReceiptCapsule.payEnergyBill()` charge the victim caller for the full energy usage instead of the deployer [7](#0-6) .
5. Deployer reverts the setting back to 0 to continue luring future victims.

  private void payEnergyBill(
      DynamicPropertiesStore dynamicPropertiesStore, AccountStore accountStore,
      ForkController forkController,
      AccountCapsule account,
      long usage,
      contractResult contractResult,
      EnergyProcessor energyProcessor,
      long now) throws BalanceInsufficientException {
    long accountEnergyLeft;
    if (dynamicPropertiesStore.getAllowTvmFreeze() == 1
        || dynamicPropertiesStore.supportUnfreezeDelay()) {
      accountEnergyLeft = callerEnergyLeft;
    } else {
      accountEnergyLeft = energyProcessor.getAccountLeftEnergyFromFreeze(account);
    }
    if (accountEnergyLeft >= usage) {
      energyProcessor.useEnergy(account, usage, now);
      this.setEnergyUsage(usage);
    } else {
      energyProcessor.useEnergy(account, accountEnergyLeft, now);

      if (forkController.pass(ForkBlockVersionEnum.VERSION_3_6_5) &&
          dynamicPropertiesStore.getAllowAdaptiveEnergy() == 1) {
        long blockEnergyUsage =
            dynamicPropertiesStore.getBlockEnergyUsage() + (usage - accountEnergyLeft);
        dynamicPropertiesStore.saveBlockEnergyUsage(blockEnergyUsage);
      }

      long sunPerEnergy = Constant.SUN_PER_ENERGY;
      long dynamicEnergyFee = dynamicPropertiesStore.getEnergyFee();
      if (dynamicEnergyFee > 0) {
        sunPerEnergy = dynamicEnergyFee;
      }
      long energyFee =
          (usage - accountEnergyLeft) * sunPerEnergy;
      this.setEnergyUsage(accountEnergyLeft);
      this.setEnergyFee(energyFee);
      long balance = account.getBalance();
      if (balance < energyFee) {
        throw new BalanceInsufficientException(
            StringUtil.createReadableString(account.createDbKey()) + " insufficient balance");
      }
      account.setBalance(balance - energyFee);

      if (dynamicPropertiesStore.supportTransactionFeePool() &&
          !contractResult.equals(contractResult.OUT_OF_TIME)) {
        dynamicPropertiesStore.addTransactionFeePool(energyFee);
      } else if (dynamicPropertiesStore.supportBlackHoleOptimization()) {
        dynamicPropertiesStore.burnTrx(energyFee);
      } else {
        //send to blackHole
        Commons.adjustBalance(accountStore, accountStore.getBlackhole(),
            energyFee, dynamicPropertiesStore.disableJavaLangMath());
      }

    }

    accountStore.put(account.getAddress().toByteArray(), account);
