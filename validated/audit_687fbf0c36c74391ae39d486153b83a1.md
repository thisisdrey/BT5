### Title
`liquidate-multi` swallows inner `liquidate` failures via `map`, breaking the atomic-revert safety net and letting partial fund transfers/bad-debt state persist - (File: `local-testing/contracts/market/market.clar`, mirrored in `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` batches calls to the private helper `call-liquidate` (which invokes the public `liquidate` function) using Clarity's `map`, and always returns `(ok (map call-liquidate positions))` [1](#0-0) . Because the *outer* transaction always resolves to `ok`, Clarity's automatic whole-transaction rollback-on-error (which normally protects a standalone `liquidate` call) never triggers. Any partial state changes and token transfers already executed inside an individual `liquidate` invocation before it hits a later failure are **not** rolled back, even though that individual liquidation is reported as `(err ...)` in the returned list. This is structurally the same root cause as the reported issue: a batch/loop wrapper that lets an inner call spend/move funds and then "fail" without the failure being surfaced/reverted at the batch level.

### Finding Description
Inside `liquidate`, the execution order is:
1. Health/slippage `asserts!` checks (lines 1511-1516) - occur *before* any funds move.
2. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` (line 1519) - pulls debt tokens from the liquidator into the vault. `vault-system-repay` routes to `contract-call? .vault-* system-repay amount`, which internally calls `receive-underlying` to transfer tokens from `tx-sender` (the liquidator) [2](#0-1) , and this vault-level call permanently commits its own bookkeeping (`principal-scaled`, `total-borrowed`) once it returns `ok` [3](#0-2) .
3. `debt-remove-scaled` and `collateral-remove` contract-calls to `.market-vault` (lines 1522-1535).
4. If the position has no collateral left, a `fold` over `socialize-debt-asset` is run and its aggregate success is checked with `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` (line 1571) [4](#0-3) .

When `liquidate` is called directly, an error at step 4 makes the whole top-level transaction return `err`, so the Clarity VM automatically reverts every prior state change (steps 1-3 included) - no funds are lost.

When `liquidate` is invoked through `liquidate-multi` via `call-liquidate`/`map`, the *inner* `err` from step 4 is merely collected as a list element; `liquidate-multi` itself still returns `(ok list)` [1](#0-0) . Because the outermost public-function response is `ok`, the transaction is not rolled back, so the already-executed contract-calls in steps 1-3 (debt tokens pulled from the liquidator, debt removed for the liquidated asset, collateral paid out) permanently persist, while the bad-debt socialization for the borrower's remaining debt is silently skipped. This is functionally identical to the referenced report's pattern: an inner "spend" happens before an inner "failure" is discovered, and the batch wrapper does not revert/refund that spend.

`socialize-debt-asset` failing is plausible: it chains `vault-socialize-debt` (which asserts `scaled-amount > u0` in each vault, e.g. `ERR-AMOUNT-ZERO` in `vault-stx.clar`) and `debt-remove-scaled` (which asserts the amount does not exceed `current-scaled-debt`, `ERR-INSUFFICIENT-DEBT` in `market-vault.clar`) [5](#0-4)  - either of which can realistically fail on rounding/zero-entry edge cases for the borrower's remaining debt list.

### Impact Explanation
This lands on **protocol insolvency / permanent freezing of funds**: when the bad-debt socialization step fails inside a batched liquidation, the vault ledger (`principal-scaled`, `total-borrowed`, `lindex`) is never written down for the borrower's un-collateralized remaining debt, even though their sole collateral has already been seized. That debt becomes permanently unrecoverable but is never recognized as a loss in the vault's accounting, silently inflating the vault's reported backing (`total-assets`) and corrupting share-price math for all depositors — the atomic all-or-nothing guarantee that the single-call `liquidate` path relies on for correctness is defeated purely by using the batch entry point, which any ordinary liquidator can trigger unintentionally or by front-running/racing conditions in a multi-position batch.

### Likelihood Explanation
`liquidate-multi` is a permissionless, ordinary-principal entry point explicitly designed for batching (its own doc-comment states it exists to avoid front-running that "prevent[s] bad debt socialization") [6](#0-5) . Any liquidator batching several distressed positions in one call can trigger this: as soon as one position's socialization step fails for any reason (zero-scaled-debt rounding edge case, `ERR-INSUFFICIENT-DEBT`, etc.), the resulting inconsistent, unreverted state is committed. No privileged access or external DAO action is required.

### Recommendation
Do not let `liquidate-multi`'s overall response mask inner failures that already mutated state. Either:
- Wrap each `call-liquidate` result and `asserts!`/`try!` it so any inner failure aborts and reverts the entire batch transaction (sacrificing partial-batch success for safety), or
- Refactor `liquidate` so token transfers/vault mutations only occur after all conditions (including bad-debt socialization) are guaranteed to succeed, i.e., move the socialization step before the irreversible fund movements, or perform a pre-flight simulation of socialization before calling `vault-system-repay`/`collateral-remove`.

### Proof of Concept
1. Liquidator calls `liquidate-multi` with two position entries, where position #1 corresponds to a borrower whose remaining (non-liquidated) debt asset entry, after this liquidation, would have `scaled == u0` or an amount just above the borrower's actual remaining scaled debt (achievable through normal rounding behavior of `mul-div-up`/`mul-div-down` used in `scale-debt-for-liquidation`).
2. Inside `liquidate` for position #1: `vault-system-repay` executes (liquidator's debt tokens pulled into vault), `debt-remove-scaled` executes, `collateral-remove` executes (liquidator receives seized collateral) - `no-collateral-left` evaluates true.
3. `socialize-debt-asset`'s fold hits `ERR-AMOUNT-ZERO`/`ERR-INSUFFICIENT-DEBT` on the borrower's other debt entry, `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fails, and `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
4. `call-liquidate` returns this err as one list element; `liquidate-multi` still returns `(ok (list (err ...) (ok ...)))`.
5. Post-transaction inspection shows the vault's `principal-scaled`/`total-borrowed` were reduced for the liquidated debt-aid, and the collateral was transferred to the liquidator, but the borrower's remaining debt on other assets was never socialized/written off in vault ledgers - a state that would have been fully reverted had `liquidate` been called stand-alone.

Note: I was not able to execute this scenario in a live environment; the analysis is based on static reading of `local-testing/contracts/market/market.clar` and the vault contracts, and Clarity's documented rollback semantics (full-transaction revert only on the outermost public-function's own `err` response, with per-`contract-call?` rollback only for that specific call's own failure).

(define-private (remove-user-scaled-debt (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (current-scaled-debt (default-to u0 (get scaled (map-get? debt key)))) ;; graceful default to u0
        (legal? (asserts! (<= amount current-scaled-debt) ERR-INSUFFICIENT-DEBT))
        (updated-scaled-debt (- current-scaled-debt amount)))
    (if (is-eq updated-scaled-debt u0)
        (map-delete debt key)
        (map-set debt key { scaled: updated-scaled-debt }))
