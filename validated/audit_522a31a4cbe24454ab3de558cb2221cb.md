### Title
Missing slippage protection in `ExchangeInjectActuator` enables sandwich attacks that force liquidity providers to overpay - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the amount of the "other" token a liquidity provider must contribute purely from the exchange pool's *current* on-chain balances at execution time, with no user-supplied bound (minimum/maximum) on that computed amount. This is the same bug class described in the external report: an operation whose output/required amount is derived from a manipulable state variable at execution time, with no slippage/limit parameter to protect the caller from state changes that occur between signing and inclusion. Unlike `ExchangeTransactionActuator`, which was hardened with an explicit `expected` parameter, `ExchangeInjectActuator` (and `ExchangeWithdrawActuator`) have no such protection.

### Finding Description
When a user submits an `ExchangeInjectContract`, they specify only `tokenId` and `quant` for one side of the pool. The actuator then derives the required amount of the paired token proportionally from the pool's live balances: [1](#0-0) 

and in validation the same ratio is recomputed from the store state and used to determine how much of the "another token" must be reduced from the account, again with no min/max bound supplied by the caller: [2](#0-1) 

The only checks are that the derived `anotherTokenQuant` is `> 0` and under a global `balanceLimit`, and that the account has enough balance - there is no check comparing the derived amount against a caller-specified maximum/minimum, which is exactly the "insufficient, only checked against zero" pattern flagged in the report (`x/liquidstake/keeper/liquidstake.go:LiquidStake`).

Because `firstTokenBalance`/`secondTokenBalance` are mutable pool state that any unprivileged account can shift via an `ExchangeTransactionContract` swap (broadcastable by anyone), an attacker can:
1. Observe a pending `ExchangeInjectContract` in the mempool.
2. Front-run it with an `ExchangeTransactionContract` swap that skews the `firstTokenBalance`/`secondTokenBalance` ratio.
3. Let the victim's inject execute at the skewed ratio, forcing them to contribute far more of the second token than the fair-market amount (or receive a much less favorable position) since there is no bound.
4. Back-run with a reverse swap to restore the ratio and capture the surplus token the victim was forced to contribute.

This is the same "front-run signed message before execution" root cause identified in the report, applied to `ExchangeInjectActuator` instead of `LiquidStake`. Compare this against `ExchangeTransactionActuator`, which already includes the fix the report recommends - a caller-supplied `expected` amount that is checked before execution: [3](#0-2) 

`ExchangeInjectActuator` and `ExchangeWithdrawActuator` have no equivalent bound, meaning the mitigation applied to trades was never extended to liquidity add/remove operations.

### Impact Explanation
A liquidity provider using `ExchangeInject` can be sandwiched into contributing an amount of the paired token far above the fair-market ratio, with the excess captured by the attacker via a follow-up trade. This is a direct value-extraction/theft vector against any unprivileged account broadcasting an `ExchangeInjectContract`, reachable purely through the standard transaction and actuator validate/execute path (`ExchangeTransactionContract` + `ExchangeInjectContract`), no privileged role required.

### Likelihood Explanation
Likelihood is high given the pool balances (`ExchangeCapsule.firstTokenBalance`/`secondTokenBalance`) are freely and cheaply movable by any account via `ExchangeTransactionContract`, and mempool visibility of pending transactions makes front-running practical for any network participant.

### Recommendation
Add a caller-supplied bound (e.g., `expectedAnotherTokenQuant`/max-slippage parameter) to `ExchangeInjectContract` (and `ExchangeWithdrawContract`) analogous to the `expected` field already present on `ExchangeTransactionContract`, and validate it in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` before execution, rejecting the transaction if the computed `anotherTokenQuant` exceeds (for inject) or falls below (for withdraw) the caller's specified bound.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` for exchange `id` specifying `tokenId=A`, `quant=Q`.
2. Attacker submits an `ExchangeTransactionContract` swap on the same `id` that shifts `firstTokenBalance`/`secondTokenBalance` such that the ratio `secondTokenBalance/firstTokenBalance` (or vice versa) increases sharply, and this transaction is included first.
3. Victim's `ExchangeInjectActuator.execute` runs `anotherTokenQuant = floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` at [4](#0-3) , computing a much larger `anotherTokenQuant` than the victim intended when they signed the transaction, and deducts it from the victim's account with no check against a maximum the victim could have specified.
4. Attacker submits a reverse `ExchangeTransactionContract` swap restoring the original ratio, capturing the surplus token value contributed by the victim. [5](#0-4)
