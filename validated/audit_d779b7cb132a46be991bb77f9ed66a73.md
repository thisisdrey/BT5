### Title
Non-atomic replay-window check-then-update in `ConnectionState.Decrypt`/`VerifyRelay` allows a captured packet to be delivered or forwarded twice - (File: `connection_state.go`)

### Summary
The external report describes a class of bug where a security-relevant *check* (is this claim/counter still valid?) and the corresponding *state update* (mark it consumed) are split into two separate, non-atomic steps, letting an attacker race the gap between them to have the same claim processed twice. Nebula's data-plane anti-replay logic has the same shape: `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` call `window.Check()` under a lock, release the lock, perform the (comparatively expensive) AEAD decrypt/verify, and only afterwards re-acquire the lock and call `window.Update()` to actually record the counter as seen.

### Finding Description
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` both follow this pattern: [1](#0-0) [2](#0-1) 

`window.Check()` only *reads* the replay bitmap to see whether `messageCounter` has already been consumed; the bit is not actually set until the later, separately-locked `window.Update()` call. Between the `Check` and the `Update`, `decryptLock` is unlocked, so a second goroutine that receives the exact same ciphertext (a byte-for-byte network replay of a previously-sent, legitimately authenticated packet — no certificate or key material needed, the attacker only re-injects captured bytes) can also pass `Check()` before the first goroutine's `Update()` commits the counter as seen.

This is reachable in multi-reader mode: `Interface.run()` starts one `listenOut` goroutine per configured reader/queue, each bound to its own underlay socket, all of which can call `readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay` concurrently for the same `hostinfo`/`ConnectionState`: [3](#0-2) [4](#0-3) 

If an attacker replays a captured packet quickly enough (before the first copy's `Update()` runs) and the two copies land on different reader goroutines/sockets, both `Check()` calls can observe "not yet seen," both AEAD operations succeed (it's the same valid ciphertext), and only one `Update()` call will report success — but by then both decrypted/forwarded copies have already been processed. For direct data-plane traffic this results in the same plaintext packet being written to the local `tun` device twice; for `MessageRelay` traffic (`VerifyRelay` → `handleOutsideRelayPacket` with `ForwardingType`) this results in the frame being forwarded to the relay target twice.

This is the structural analog of the reported bug class: the “eligibility check” (`window.Check`) and the “consumption/state commit” (`window.Update`) are not atomic, so an attacker races the gap to get one packet processed more than once.

### Impact Explanation
Successful exploitation defeats the anti-replay guarantee that the sliding-window (`Bits`) mechanism is specifically designed to provide. On the data plane this causes duplicate delivery of decrypted traffic to the local overlay interface (`tun`), which can duplicate application-level effects for a captured packet. On relay tunnels it causes duplicate forwarding of a replayed frame to the relay target, undermining the exact guarantee the `TestRelayReplayProtection` test and CHANGELOG entries ("Advance the replay window on relayed packets…", "Lock replay window updates so concurrent readers can't corrupt it") were meant to establish — those fixes address `Bits` internal consistency and forwarding-vs-updating ordering, but do not make the outer `Check` → decrypt/verify → `Update` sequence atomic. [5](#0-4) 

### Likelihood Explanation
Requires: (1) the attacker can observe/capture at least one legitimate ciphertext packet on the wire (already assumed reachable for any UDP-based overlay attacker without needing a CA-signed cert), and (2) `listen.routines`/multiple reader queues configured so more than one goroutine can process inbound UDP concurrently, and (3) winning a narrow timing race (the gap between the locked `Check()` call and the locked `Update()` call, which spans one AEAD operation). This is a genuine, but timing-dependent, race condition rather than a deterministic bypass.

### Recommendation
Make the replay check-and-commit atomic with respect to a given `messageCounter`: hold `decryptLock` across the full `Check` → decrypt/verify → `Update` sequence (or introduce a single `CheckAndReserve`/`TestAndSet`-style method on `Bits` that atomically checks-and-marks the counter before decryption begins), so that a second concurrent delivery of the same counter is rejected before any decrypt/verify or forwarding work is performed, mirroring the report's recommendation to eliminate the window between eligibility-check and state-commit.

### Proof of Concept
1. Establish a tunnel between two nebula instances with `listen.routines` > 1 (multi-reader/multi-queue mode) so `Interface.run()` starts multiple `listenOut` goroutines, each on its own underlay socket. [3](#0-2) 
2. Capture one legitimate data-plane (or relay) ciphertext packet in flight, as done in the existing `TestRelayReplayProtection` harness which captures a real relay frame via `myControl.GetFromUDP`. [6](#0-5) 
3. Inject two copies of the exact same captured packet in immediate succession such that the underlying sockets/kernel dispatch them to two different reader goroutines before the first `Decrypt`/`VerifyRelay` call completes its `Update()`.
4. Observe that both copies pass `window.Check()` (both see the counter as unseen) and are both decrypted/forwarded — i.e., the packet is delivered to `tun` twice, or forwarded through the relay twice — despite the replay window nominally rejecting duplicates. [1](#0-0)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
