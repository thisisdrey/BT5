### Title
Shielded key material (spending key / viewing keys) accepted via GET query-string parameters in the Wallet HTTP API - (File: `framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java`, `ScanNoteByIvkServlet.java`, `GetIncomingViewingKeyServlet.java`, `GetZenPaymentAddressServlet.java`, `ScanShieldedTRC20NotesByOvkServlet.java`)

### Summary
Several HTTP JSON-RPC-style endpoints exposed by the FullNode Wallet HTTP API accept highly sensitive shielded-transaction key material (`value` spending key, `ivk`/`ovk`/`ak`/`nk` viewing/nullifier keys) as `GET` query-string parameters in addition to `POST` body parameters. This mirrors the reported bug class: secrets that should only travel in a request body are instead placed in the URL, where they are routinely captured in web-server access logs, reverse-proxy logs, CDN/load-balancer logs, browser history, and `Referer` headers.

### Finding Description
Multiple servlets under `org/tron/core/services/http/` implement a `doGet` handler that reads shielded-pool secret key material directly from `request.getParameter(...)`:

- `GetExpandedSpendingKeyServlet.doGet` reads the raw spending key from the `value` query parameter and passes it to `wallet.getExpandedSpendingKey(...)`. [1](#0-0) 

- `ScanNoteByIvkServlet.doGet` reads the incoming viewing key (`ivk`) — which grants full decryption rights over a shielded account's incoming transactions — as a GET parameter. [2](#0-1) 

- `GetIncomingViewingKeyServlet.doGet` reads `ak`/`nk` (the authorizing/nullifier key components used to derive the viewing key) as GET parameters. [3](#0-2) 

- `GetZenPaymentAddressServlet.doGet` and `ScanShieldedTRC20NotesByOvkServlet.doGet` similarly accept `ivk`/`ovk` (outgoing viewing key) via GET. [4](#0-3) [5](#0-4) 

These servlets are registered on the FullNode Wallet HTTP API surface (paths such as `wallet/getexpandedspendingkey`, `wallet/scannotebyivk`, `wallet/getincomingviewingkey`, `wallet/getzenpaymentaddress`), the same anonymous, unauthenticated `Wallet` HTTP interface used for account/contract queries. The `GetSpendingKeyServlet` GET path is comparatively benign since it generates a new key server-side rather than accepting client secrets, but the endpoints above (expanded spending key, ivk/ovk/ak/nk scanning and address-derivation endpoints) all take *caller-supplied* shielded secrets through the URL query string.

The `Util.checkGetParam` helper confirms that for GET requests, values are read straight from `request.getParameter(key)`, i.e., from the URL query string, whereas for POST requests non-form-encoded bodies are parsed from the JSON body instead — showing the GET path is a deliberate but insecure alternate input channel for the same sensitive fields. [6](#0-5) 

### Impact Explanation
Shielded viewing keys (`ivk`, `ovk`) and spending-key material are cryptographic secrets: possession of an `ivk` allows an attacker to decrypt all incoming shielded notes for that address, and possession of the spending key/expanded spending key allows full spend authority over shielded funds. Because these values are transmitted as GET query parameters, they are trivially captured by any intermediary that logs URLs — reverse proxies, CDNs, corporate/ISP monitoring, or the node operator's own web server access logs — and by browser history if triggered from a UI. Disclosure of these keys leads directly to unauthorized decryption of private balances/transactions and, for spending-key exposure, unauthorized movement of shielded funds — i.e., theft of funds and key disclosure, matching the accepted impact categories.

### Likelihood Explanation
Any client of the node's Wallet HTTP API (this includes third-party wallets, exchanges' backend integrations, or explorer services that proxy requests) can trigger these GET endpoints; no authentication or authorization is required to reach them since the Wallet HTTP interface is open to anonymous API clients. The vulnerable code path is a first-class, currently-supported feature (`doGet` is implemented alongside `doPost` on every shielded-key servlet, not a leftover/legacy stub), so it is likely to be exercised in real deployments — e.g., debugging scripts, older SDKs, or simple `curl`/browser usage that default to GET — leading to routine leakage into infrastructure logs.

### Recommendation
Remove (or explicitly deprecate and reject) the `doGet` handlers for all servlets that accept shielded secret key material (`GetExpandedSpendingKeyServlet`, `GetSpendingKeyServlet` symmetric counterparts if they ever accept caller secrets, `GetIncomingViewingKeyServlet`, `GetNkFromNskServlet`, `GetAkFromAskServlet`, `GetZenPaymentAddressServlet`, `ScanNoteByIvkServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanNoteByOvkServlet`, `ScanShieldedTRC20NotesByIvkServlet`, `ScanShieldedTRC20NotesByOvkServlet`). Require these operations to be invoked only via `POST` with the secret carried in the JSON body, and have the GET handler respond with an error (e.g., HTTP 405) instructing callers to use POST. Additionally, ensure access logging for the Wallet HTTP endpoints does not record query strings for any endpoint, and document that any reverse proxy fronting the node must not log full URLs for these paths.

### Proof of Concept
1. Node operator (or any downstream service) runs the FullNode with the default HTTP API enabled (`node.http.fullNodePort`).
2. A client (legitimate or malicious) that already possesses (or is testing) a shielded viewing key sends:
   `GET http://<node>:8090/wallet/scannotebyivk?start_block_index=0&end_block_index=100&ivk=<secret_ivk_hex>`
   or
   `GET http://<node>:8090/wallet/getexpandedspendingkey?value=<secret_spending_key_hex>`
3. The reverse proxy / web server / CDN in front of the node (or the node's own access log, or an on-path network monitor) records the full request line, including the `ivk`/spending-key value, in plaintext.
4. Anyone with read access to those logs (ops team, compromised log-aggregation pipeline, shared hosting neighbor, or an attacker who compromised the proxy) recovers the shielded secret and can decrypt the victim's private transactions or, for the spending-key case, spend the victim's shielded funds.

  private static String checkGetParam(HttpServletRequest request, String key) throws Exception {
    String method = request.getMethod();

    if (HttpMethod.GET.toString().toUpperCase(Locale.ROOT).equalsIgnoreCase(method)) {
      return request.getParameter(key);
    }
    if (HttpMethod.POST.toString().toUpperCase(Locale.ROOT).equals(method)) {
      String contentType = request.getContentType();
      if (StringUtils.isBlank(contentType)) {
        return null;
      }
      if (contentType.contains(MimeTypes.Type.FORM_ENCODED.asString())) {
        return request.getParameter(key);
      } else {
        String value = getRequestValue(request);
        if (StringUtils.isBlank(value)) {
          return null;
        }

        JSONObject jsonObject = JSON.parseObject(value);
        if (jsonObject != null) {
          return jsonObject.getString(key);
        }
        return null;
      }
    }
    return null;
  }
