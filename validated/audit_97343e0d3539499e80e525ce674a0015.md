Audit Report

## Title
Missing `Halted`/`OperatingMode` check in `submit_delivery_receipt` allows continued reward payout while the Snowbridge outbound pipeline should be stoppable - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`pallet-snowbridge-inbound-queue-v2::submit` enforces a halt check via `OperatingMode::<T>::get().is_halted()` before processing any message, backed by a dedicated `OperatingMode` storage item and a root-gated `set_operating_mode` call. The sibling `pallet-snowbridge-outbound-queue-v2` defines the same `BasicOperatingMode` type and an `OperatingModeChanged` event, but never declares an `OperatingMode` storage item or a `set_operating_mode` call, and `submit_delivery_receipt`/`process_delivery_receipt` perform verification and reward payout with no halt gate at all.

## Finding Description
In `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`, `submit` explicitly checks `ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);` before verifying and processing a message, using the `OperatingMode` `StorageValue` and the root-only `set_operating_mode` extrinsic. [1](#0-0) 

`pallet-snowbridge-outbound-queue-v2` imports `BasicOperatingMode` and declares `OperatingModeChanged` in its `Event` enum and even reserves an `Error::Halted` variant, implying the same intent, but its storage section only defines `Messages`, `MessageLeaves`, `Nonce`, and `PendingOrders` — there is no `OperatingMode` storage value and no `set_operating_mode` call anywhere in the pallet. [2](#0-1) [3](#0-2) 

The public `submit_delivery_receipt` extrinsic verifies the event proof and dispatches straight to `process_delivery_receipt` with no operating-mode check, unlike inbound's `submit`. [4](#0-3) 

`process_delivery_receipt` only checks the gateway address and pending-order existence before calling `T::RewardPayment::register_reward` and removing the order from `PendingOrders` — again with no operating-mode gate. [5](#0-4) 

I confirmed via `grep_search` that no `OperatingMode`/`is_halted`/`set_operating_mode` logic exists anywhere in the outbound-queue-v2 pallet source outside of tests/mocks that merely reference the term incidentally; the production `lib.rs` genuinely lacks the storage item and the gate.

## Impact Explanation
This is a legitimate design/implementation asymmetry: the outbound pallet has no self-contained, pallet-local mechanism to halt reward-payout processing, even though its own type imports and event/error definitions (`BasicOperatingMode`, `OperatingModeChanged`, `Error::Halted`) signal that halt semantics were intended. If the pipeline ever needs to be paused independently (e.g., due to a verifier issue or a fee-drain concern specific to outbound processing), the only available lever is external to the pallet (e.g., runtime `BaseCallFilter`), not anything the pallet itself exposes. This matches the "runtime bugs that compromise intended behavior" class in the impact gate, since the pallet's own code signals an intended pause capability that does not exist, leaving `submit_delivery_receipt` unconditionally payable for any pending order regardless of any incident requiring the outbound side to stop. It does not, however, constitute theft, duplicate payout, or fund lock — each order is paid exactly once and removed, so the direct financial-correctness invariants (beneficiary, amount, one-time settlement) remain intact under normal operation.

## Likelihood Explanation
Reaching `submit_delivery_receipt` requires no privileged capability — it is a normal signed extrinsic requiring only a valid Ethereum event proof for an already-queued order, matching the report's claim that no privileged action is needed to trigger the extrinsic itself. However, the "risk" only materializes if/when governance intends to halt the outbound pipeline and discovers no pallet-native way to do so; absent that governance intent, there is no adverse effect from ordinary usage of `submit_delivery_receipt`.

## Recommendation
Add an `OperatingMode` storage item and a root-gated `set_operating_mode` call to `pallet-snowbridge-outbound-queue-v2`, mirroring the inbound pallet, and gate `submit_delivery_receipt` (and ideally `do_process_message`/`process_message_impl`) with `ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);`.

## Proof of Concept
1. Confirm `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` storage section (lines 245–271) contains no `OperatingMode` item, contrasted with `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` lines 170–172/200–210 which do.
2. Observe `submit_delivery_receipt` (lines 298–317) and `process_delivery_receipt` (lines 445–476) contain no `is_halted()`/`Error::Halted` check, while `submit` in the inbound pallet (lines 185–198) does.
3. As a unit test in `outbound-queue-v2/src/test.rs`, enqueue a message to create a `PendingOrders` entry, then call `submit_delivery_receipt` with a valid mock proof for that nonce — payout via `T::RewardPayment::register_reward` succeeds and the order is removed, with no way to have prevented this via any pallet-local halt mechanism (since none exists), confirming the gap relative to the inbound pallet's analogous `Halted` check.

		pub fn submit(origin: OriginFor<T>, event: Box<EventProof>) -> DispatchResult {
			let who = ensure_signed(origin)?;
			ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);

			// submit message for verification
			T::Verifier::verify(&event.event_log, &event.proof)
				.map_err(|e| Error::<T>::Verification(e))?;

			// Decode event log into a bridge message
			let message =
				Message::try_from(&event.event_log).map_err(|_| Error::<T>::InvalidMessage)?;

			Self::process_message(who, message)
		}
