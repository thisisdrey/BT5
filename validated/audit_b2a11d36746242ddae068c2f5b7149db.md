### Title
Unchecked exchange pool balance underflow in legacy `ExchangeCapsule.transaction()` path allows negative token/TRX balances to be silently recorded - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes new Bancor-relay pool balances for a TRX/TRC10 exchange pair and, only when the `hardenedCalc` flag is `true`, checks that the resulting balances are non-negative before persisting them. When `hardenedCalc` is `false` (the legacy/default path, controlled by the `allowHardenExchangeCalculation` dynamic property that must be turned on by a committee proposal), the same underflow can occur but is never checked, and the corrupted (potentially negative) `firstTokenBalance`/`secondTokenBalance` is written straight into the `Exchange` capsule and persisted to the `ExchangeStore`/`ExchangeV2Store`. This mirrors the Flatcoin bug class: a value that is allowed to go out-of-range (the LP's `stableCollateralTotal` going negative, silently clamped instead of keeping trader and LP accounting symmetric) corrupts protocol-tracked state such that later user-facing operations relying on that tracked value break or misbehave, without ever reverting at the point where the divergence is introduced.

### Finding Description
`ExchangeCapsule.transaction()`: [1](#0-0) 

only guards against negative balances inside the `if (hardenedCalc && ...)` branch: [2](#0-1) 

`hardenedCalc` is passed in by `ExchangeTransactionActuator.execute`/`doValidate` as `allowHarden()`, which reads the `allowHardenExchangeCalculation` dynamic property: [3](#0-2) [4](#0-3) 

The legacy `ExchangeProcessor` uses floating-point `Math.pow`-based Bancor-relay math to compute `buyTokenQuant`, and rounding/precision behavior of this formula can, for edge-case pool ratios and quantities (e.g., very small pool balance relative to a large sell quantity, or repeated small trades against a nearly depleted pool), produce a `buyTokenQuant` larger than the actual opposite-side balance. In the legacy branch this yields `newFirstTokenBalance`/`newSecondTokenBalance` that go negative, and that corrupted value is written unconditionally to `this.exchange` and then persisted via `Commons.putExchangeCapsule`: [5](#0-4) 

The doValidate path in `ExchangeTransactionActuator` calls the same `transaction()` a second time during validation purely to compute `anotherTokenQuant` for the `tokenExpected` check, without catching a divergent/negative outcome as an error unless `hardenedCalc` is enabled: [6](#0-5) 

This is directly analogous to the Flatcoin `_getCollateralNet` bug: in Flatcoin, the tracked `stableCollateralTotal` is clamped to zero on loss while the trader's `marginDepositedTotal` isn't correspondingly capped, so tracked totals diverge from real backing collateral and the protocol subsequently reverts/bricks on every user action that runs the invariant check. In java-tron's exchange pool, the same category of asymmetric/unchecked arithmetic on a pooled-balance ledger lets the *tracked* pool balance (`Exchange.firstTokenBalance`/`secondTokenBalance`) diverge from what is actually redeemable, silently, because the safety check that would catch it is feature-flagged off by default.

### Impact Explanation
Once an `Exchange` pool balance record goes negative (or otherwise becomes inconsistent) via the unchecked legacy path, every subsequent action reading that pool (`ExchangeTransactionActuator`, `ExchangeWithdrawActuator`, `ExchangeInjectActuator`) uses these corrupted balances as authoritative inputs to further Bancor-relay math. This can let a trader extract disproportionately large amounts of the opposite token relative to what was deposited (loss of funds for other pool participants / unbacked balance), or can leave the pool in a state where legitimate withdrawals compute nonsensical (e.g., negative) results, effectively freezing user funds locked in that exchange pair. Because `ExchangeTransactionContract` is reachable by any account holding TRX/TRC10 balance without special privilege, this satisfies "unauthorized account operation / theft or permanent freezing of funds" from a single signed transaction.

### Likelihood Explanation
Requires the `allowHardenExchangeCalculation` feature (committee-controlled) to remain disabled (its legacy/default state on many long-lived java-tron networks) and requires the attacker to construct exchange pool state/quantities (via a sequence of `ExchangeTransactionContract` calls, all callable by an ordinary account) that push the floating-point Bancor-relay math into an underflow regime for one of the two pool balances. This is comparable in likelihood framing to the Sherlock issue that was ultimately downgraded to Medium: it needs specific pool state/quantity conditions (analogous to "large price move") rather than being trivially triggerable on every trade, but is reachable purely with ordinary signed transactions and no privileged role.

### Recommendation
- Perform the non-negative-balance check unconditionally in `ExchangeCapsule.transaction()`, not only when `hardenedCalc` is true, i.e. remove the feature-flag gating from the safety check and make it always active as of the current codebase (with a hard-fork flag if backward-compatibility for old-chain replay is required).
- Additionally validate that `buyTokenQuant` never exceeds the current opposing pool balance before mutating the capsule, rather than relying solely on post-hoc balance-sign checks.
- Enable/hard-fork-activate `allowHardenExchangeCalculation` by default for all new deployments so the `SafeExchangeProcessor` (BigDecimal-based, exact-arithmetic) path is always used.

### Proof of Concept
1. Deploy/observe an `Exchange` (via `ExchangeCreateActuator`) with a low-liquidity token pair, and with `allowHardenExchangeCalculation` disabled (default/legacy state).
2. Submit a crafted sequence of `ExchangeTransactionContract` transactions (ordinary signed transactions, no special role) targeting quantities where the legacy `ExchangeProcessor.exchangeFromSupply` floating point Bancor-relay formula rounds/produces `buyTokenQuant` greater than the current opposite-side `secondTokenBalance`/`firstTokenBalance`.
3. Because `hardenedCalc` is `false`, `ExchangeCapsule.transaction()` at [7](#0-6)  skips the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check and persists the negative/corrupted balance via `Commons.putExchangeCapsule`.
4. All subsequent `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` calls against this exchange ID now operate on inconsistent pool balances, producing incorrect trade outputs or preventing correct withdrawal accounting — a divergence between real backing value and tracked pool state directly analogous to the Flatcoin `collateralBalance` vs `trackedCollateral` mismatch.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
