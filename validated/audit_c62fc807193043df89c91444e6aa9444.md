## Analysis

The Pendle report's core invariant break is: **a trade/swap executes with `minTokenOut`/`minLpOut`/`minPtOut` hardcoded to `0`, so the trader has no way to bound acceptable slippage, letting a price-manipulator extract value from the trade.**

Searching the Polkadot SDK for the equivalent pattern (a swap through `pallet-asset-conversion`'s `Swap`/`SwapCredit` traits, which take an `Option<Balance>` slippage bound), I found that most call sites correctly forward a caller-supplied minimum:

- `pallet_asset_conversion::Pallet::swap_exact_tokens_for_tokens` extrinsic requires `amount_out_min` from the signer [1](#0-0) .
- The `pallet-revive` precompile forwards the caller's `amountOutMin`/`amountInMax` [2](#0-1) .
- `SingleAssetExchangeAdapter::exchange_asset` always passes `Some(want_amount)` as the bound in both the `maximal` and `minimal` branches [3](#0-2) .

However, `cumulus_primitives_utility::SwapFirstAssetTrader::refund_weight` hardcodes the minimum bound to `None` when swapping the accumulated fee credit back into the asset the user originally paid with:

```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,   // <-- no slippage bound, unlike buy_weight's Some(fee)
) { ... };
``` [4](#0-3) 

This contrasts directly with the same struct's `buy_weight`, which swaps in the opposite direction and *does* pass an exact target (`fee`) via `swap_tokens_for_exact_tokens` [5](#0-4) .

### Title
Unbounded-slippage refund swap in `SwapFirstAssetTrader::refund_weight` - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader`, the XCM `WeightTrader` used to let users pay execution fees in a non-native asset (configured in Penpal and other runtimes via `AssetConversion`) [6](#0-5) , hardcodes the minimum-output parameter to `None` in `refund_weight` when swapping the unused portion of collected fees back to the asset the user actually held, unlike every other swap call-site in the codebase which forwards a real bound.

### Finding Description
`refund_weight` extracts `refund_amount` of `Target` (e.g. native) fee credit and swaps it back into `refund_swap_asset` (the asset the message's origin originally used) via `SwapCredit::swap_exact_tokens_for_tokens(..., None)` [7](#0-6) . Because `amount_out_min` is `None`, `do_swap_exact_credit_tokens_for_tokens` skips the `ensure!(amount_out >= amount_out_min, ...)` check entirely [8](#0-7)  — the swap accepts whatever `amount_out` the pool's current reserves produce, no matter how unfavorable.

If the pool's reserve ratio for `Target`/`refund_swap_asset` is skewed immediately before this XCM instruction executes (e.g. by preceding extrinsics or XCM messages within the same block that swap against the pool), the refund credited back to the fee-payer can be reduced to a negligible amount, while the value is captured by whoever moved the pool price. `buy_weight` in the same struct correctly avoids this by using `swap_tokens_for_exact_tokens` with an exact target amount, so the asymmetry is specific to the refund path.

### Impact Explanation
This breaks the invariant that "Balances/assets ... must conserve value and settle exactly once to the rightful beneficiary and amount." The refunded value legitimately belongs to the message's fee payer (ultimately returned into the XCM holding register and typically back to the origin/sovereign account); with no floor on the swap, that value can be siphoned into the AMM pool/LP side through price manipulation timed with block execution, resulting in a real, permanent loss of user funds on every runtime that wires `SwapFirstAssetTrader` (e.g. Penpal-style configurations using `AssetConversion` for delivery/execution fees).

### Likelihood Explanation
`refund_weight` runs unconditionally whenever weight bought via a non-Target asset exceeds actually-consumed weight, which is common (most messages don't use their full weight budget). Any actor able to place transactions/XCM in the same block ahead of the refunded message's processing (a normal, unprivileged capability, not requiring a malicious collator/validator/relayer) can shift the pool reserves to minimize the refund credit_out. No governance or validator collusion is required — only ordinary DEX-pool interaction.

### Recommendation
Compute an acceptable minimum for the refund swap (e.g. derived from `QuotePrice::quote_price_exact_tokens_for_tokens` at call time, with a configurable tolerance) and pass `Some(min_refund)` instead of `None` to `SwapCredit::swap_exact_tokens_for_tokens`, mirroring the bound already enforced in `buy_weight` and in `SingleAssetExchangeAdapter`. If no acceptable bound can be met, keep the credit in `total_fee` (as the existing error branch already does) rather than accepting an unbounded-slippage swap.

### Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader` and a shallow `AssetConversion` pool between `Target` (native) and asset `X`.
2. User submits an XCM program paying fees with `X`, buying weight `W` (calls `buy_weight`, correctly bounded).
3. Before the corresponding `refund_weight` executes (same block, subsequent extrinsic/message), attacker swaps a large amount of `X` into the pool for `Target`, skewing reserves so `Target -> X` now yields far less `X` per unit `Target`.
4. `refund_weight` swaps the unused `Target` fee back into `X` with `amount_out_min = None`; the fee payer receives a fraction of the fair refund while the attacker's counter-position captures the difference by reversing their swap afterward.
5. Repeatable per block for any parachain enabling this trader, producing systematic value drain from users paying fees in non-native assets.
