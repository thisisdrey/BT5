### Title
Front-running a deposit through `VesperGateway.deposit` (or `AMO.mintAndDeposit`) with a first-deposit + donation inflates `VPool` share price and steals the depositor's funds - (contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` pulls the user's underlying, calls `vToken_.deposit(amount_)` on a Vesper `VPool`, and credits the user via `msdToken` only for the shares actually received. `VesperGateway.sol:44-65` There is no minimum-shares-out check. If the target `VPool` is empty or near-empty, an attacker can front-run with the classic ERC4626-style first-depositor inflation attack: deposit 1 wei of shares, then donate a large amount of underlying directly to the pool to inflate `pricePerShare`, so the victim's deposit mints ~0 shares while their underlying is absorbed into the pool and redeemable only by the attacker's shares.

### Finding Description
The vulnerable flow:

```solidity
// contracts/VesperGateway.sol:50-64
IERC20 _underlying = IERC20(vToken_.token());
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);                                   // no minSharesOut
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
vToken_.safeApprove(address(_depositToken), _vTokenAmount);
_depositToken.deposit(_vTokenAmount, _msgSender);
```

Vesper pools price shares as `totalValue / totalSupply`, where `totalValue` counts the pool's raw token balance — i.e., direct transfers (donations) are included. The gateway takes `vToken_` as a caller-chosen argument; the only constraint is that `pool_.depositTokenOf(vToken_)` returns a registered deposit token (`DepositToken.deposit` reverts otherwise via `onlyIfDepositTokenExists`, `DepositToken.sol:214`). When a new vToken collateral is onboarded, or any registered `VPool` has negligible share supply, the attack window exists. `deposit` is not `nonReentrant` and has no slippage parameter, so nothing blocks the sandwich.

The identical pattern exists on the protocol-funds side in `AMO.mintAndDeposit` (`AMO.sol:70-83`): a keeper's mint+deposit into a freshly whitelisted `VPool` (set by `updateVesperPool`) can be front-run the same way, so the AMO mints `amoSupply` synths but holds vToken shares redeemable for only a fraction — protocol insolvency rather than user loss.

Note `DepositToken.deposit` itself (`DepositToken.sol:211-237`) mints `msdToken` 1:1 minus fees against a balance delta, so it is not directly vulnerable — the share-price exposure is entirely via the external `VPool` in these two paths.

### Impact Explanation
Direct theft of user funds: the victim's underlying is deposited into the `VPool` but they receive shares redeemable for only a small fraction of it; the remainder accrues to the attacker's dominant share position. In the AMO variant, the protocol mints synthetic supply recorded in `amoSupply` while the backing shares are worth much less — a solvency break.

### Likelihood Explanation
Requires a registered `VPool` collateral with an empty/near-empty share supply at the moment of the victim's (or keeper's) deposit — e.g., newly onboarded Vesper collateral. Attacker cost is roughly the victim's deposit amount (donation), profitable whenever the victim deposit is meaningful. Vesper pools historically use the `totalSupply == 0 → pricePerShare = 1e18` guard only against the *first* deposit's rounding, not against donation-based inflation after a 1-wei seed deposit.

### Recommendation
- Add a `minSharesOut_` (minimum vToken shares) parameter to `VesperGateway.deposit` and revert if `_vTokenAmount < minSharesOut_`.
- In `AMO.mintAndDeposit`, check shares received against `amount_ / expectedPricePerShare` tolerance, or execute via a private relay.
- Prefer onboarding Vesper collaterals whose pools already have material share supply, or seed the pool atomically in the same transaction as whitelisting.

### Proof of Concept
Foundry fork test (mainnet) — sketch:

```solidity
function test_vpoolShareInflation() public {
    // Setup: Pool, DepositToken for vToken (e.g. a Vesper pool),
    // VesperGateway deployed against PoolRegistry; vToken registered in pool.

    // --- Attacker front-runs (same block, before victim tx) ---
    uint256 victimAmount = 1_000_000e6; // e.g. USDC
    deal(address(underlying), attacker, 1 + victimAmount);
    vm.startPrank(attacker);
    underlying.approve(address(vPool), 1);
    vPool.deposit(1);                       // attacker holds 1 share
    underlying.transfer(address(vPool), victimAmount); // donation inflates pricePerShare
    vm.stopPrank();
    // pricePerShare ~= victimAmount + 1 per 1 share

    // --- Victim deposits via gateway ---
    deal(address(underlying), victim, victimAmount);
    vm.startPrank(victim);
    underlying.approve(address(vesperGateway), victimAmount);
    vesperGateway.deposit(pool, IVPool(address(vPool)), victimAmount);
    vm.stopPrank();

    // Victim received ~0 vToken shares -> ~0 msdTokens minted
    uint256 victimMsd = depositToken.balanceOf(victim);
    assertLt(victimMsd, victimAmount / 100); // victim lost >99% of deposit

    // Attacker redeems their 1 share for nearly the whole pool balance
    vm.prank(attacker);
    vPool.withdraw(1);
    assertGt(underlying.balanceOf(attacker), victimAmount * 99 / 100);
}
```

Requires a fork where `vPool` is a real Vesper `VPool` registered as collateral and freshly deployed/empty; the mock `VPoolMock` (`contracts/mock/VPoolMock.sol`) computes `pricePerShare` from `balanceOf(this)/totalSupply` with the same donation surface.
