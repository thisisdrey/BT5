## Finding Confirmed (via `DelayedReceiptQueue`, not `BufferedReceipt`)

Before the writeup: the premise that a **self-receipt** (`predecessor_id == receiver_id`) can end up in `TrieKey::BufferedReceipt` is not correct. Self/local receipts (`receiver_id == signer_id`) never enter `ReceiptSink`/outgoing buffers — those exist only for receipts crossing to a *different* shard [1](#0-0) . `check_actor_permissions` only traps `actor_id == account_id` when the receipt's `predecessor_id` equals its `receiver_id` [2](#0-1) , which by construction is exclusively a **local** receipt, hence only reachable through `TrieKey::DelayedReceipt` (ordinary gas-limit congestion), not `TrieKey::BufferedReceipt`. The `DelayedReceipt` half of the hypothesis, however, is confirmed reachable and exploitable.

### Title
Authorization escalation via delayed-receipt replay against a deleted-then-recreated account (`check_actor_permissions`) - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`check_actor_permissions` authorizes privileged actions (`AddKey`, `Stake`, `DeployContract`, `DeleteKey`, `UseGlobalContract`, `DeployGlobalContract`, `WithdrawFromGasKey`) purely by string-comparing `actor_id == account_id`, where `actor_id` is the queued receipt's frozen `predecessor_id` [3](#0-2)  and `account_id` is `receipt.receiver_id()` [4](#0-3) . Because these are pure account-ID strings with no binding to a specific "account generation," a self-addressed privileged action that is pushed to `DelayedReceiptQueue` because of ordinary gas-limit congestion will still pass this check and execute even if the underlying `Account` was deleted and a completely different party recreated an account with the identical name in the interim.

### Finding Description
`process_local_receipts` pushes any local receipt that can't fit under the chunk's `compute_limit` into the persistent `DelayedReceiptQueue` [5](#0-4) . `process_receipts` always processes **local receipts of the current chunk before draining the delayed backlog** (`process_local_receipts` then `process_delayed_receipts`) [6](#0-5) , so a fresh `DeleteAccount` receipt submitted in a later chunk is guaranteed to execute before an older, still-queued delayed self-receipt is dequeued.

Exploit flow:
1. Attacker controls `victim.near` (a top-level name at/above `min_allowed_top_level_account_length`, so `action_create_account` imposes **no** registrar restriction on who may (re)create it — anyone can — confirmed at `runtime/runtime/src/actions.rs:176-190` [7](#0-6) ).
2. Attacker submits a self-receipt with a privileged action (e.g. `AddKey`, `receiver_id == signer_id == victim.near`) padded behind enough compute-heavy transactions in the same chunk to blow the `compute_limit`, so it is pushed to `DelayedReceiptQueue`.
3. In a subsequent chunk, attacker submits `DeleteAccount(actor=victim.near, account=victim.near)`. `check_actor_permissions` passes (`actor_id == account_id`, self-signed) [8](#0-7) ; `remove_account` deletes `Account`, `AccessKey`, `ContractCode`, `ContractData` — but never touches `DelayedReceipt`/`DelayedReceiptIndices`, since `get_account_id()` returns `None` for those keys (confirmed global, non-account-keyed) [9](#0-8) . This `DeleteAccount` receipt is a new local receipt, so per the local→delayed ordering, it lands and executes in a chunk **before** the queued delayed `AddKey` self-receipt is popped.
4. Any unprivileged third party submits `CreateAccount` for the identical `victim.near` name plus their own `AddKey`, since top-level names of sufficient length require no registrar (`actions.rs:176-190`).
5. In a later chunk, `process_delayed_receipts` pops the stale `AddKey` self-receipt. `check_account_existence` now passes (account exists) [10](#0-9) , and `check_actor_permissions` passes because `actor_id` (frozen as `victim.near` in the receipt's `predecessor_id`) still string-equals `account_id` (`victim.near`, the receiver) [11](#0-10) . The old attacker's `AddKey` executes against the new owner's account, injecting a full-access key the new owner never authorized.

The root cause is identical to the postponed-receipt case: `check_actor_permissions`/`check_account_existence` authorize purely by account-ID string equality with no tie to a specific account "instance," so `remove_account` correctly not touching `DelayedReceiptQueue`/`BufferedReceipt` (they are legitimately global FIFO queues) does not eliminate the exposure — it is inherent to how actor authorization is computed at dequeue time for *any* deferred self-receipt, independent of the four trie keys `remove_account` manages.

### Impact Explanation
Authorization escalation across accounts: a party (old owner or an unrelated attacker who previously controlled the name) can inject a privileged action — most severely `AddKey` with `FullAccess` — into an account now controlled by someone else, without the new owner's key ever countersigning it. This is a full account-takeover / theft primitive (the injected key can then drain balance, since account takeover implies fund control), falling under the "authorization escalation across accounts" and "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions: attacker needs to (a) control an account whose name is reusable (top-level, at/above the min length, or a sub-account of a parent they still control so they can also recreate it themselves and skip needing a genuine third party), (b) be able to force a specific self-receipt into `DelayedReceiptQueue` by exhausting chunk compute, which is fully attacker-controlled (submit enough gas-heavy padding transactions ahead of the target tx in one chunk), and (c) time a `DeleteAccount` tx in a subsequent chunk before the delayed backlog drains that far. All steps are ordinary, unprivileged transactions; no validator/node access, no leaked keys. This is realistic and repeatable — congestion-induced delay is a normal, attacker-inducible protocol behavior, and account name reuse/top-level recreation rules are also standard, documented behavior.

### Recommendation
Bind authorization checks for deferred (delayed/postponed/yielded) self-receipts to the account's identity at the time the *action* is queued, not merely its ID string — e.g., store/verify an account-creation nonce or a snapshot commitment (such as the code/key state hash, or a monotonically increasing "account generation" counter bumped by `CreateAccount`/`DeleteAccount`) and reject `check_actor_permissions` if the account's generation has changed since the receipt was created. Alternatively, invalidate/drop any queued self-receipts targeting an account when it is deleted (which requires walking or tagging queue entries by account, a much larger design change), or forbid recreating an account name while any receipt still references it.

### Proof of Concept
Runtime integration test (`runtime/runtime/src/tests/apply.rs` style, using `Runtime::apply` across multiple simulated chunks):
1. Set up `alice.near` (top-level, length ≥ `min_allowed_top_level_account_length`) with a `FullAccess` key `K1`.
2. Chunk N: submit many compute-heavy local transactions from `alice.near` to `alice.near`, ending with `Action::AddKey(K_attacker, FullAccess)`, sized so the `AddKey` tx is pushed into `DelayedReceiptIndices`/`DelayedReceipt`. Assert via `get(&trie, &TrieKey::DelayedReceiptIndices)` that the queue is non-empty and contains the AddKey receipt.
3. Chunk N+1: submit `DeleteAccount(actor=alice.near, account=alice.near, beneficiary=alice.near)` signed by `K1`. Assert `get_account(state_update, "alice.near")` is `None` and the delayed queue still contains the AddKey receipt (untouched).
4. Chunk N+2: from a distinct third-party account, submit `CreateAccount` + `Action::AddKey(K_new_owner, FullAccess)` for `alice.near`. Assert account exists with only `K_new_owner`.
5. Chunk N+3 (or whenever the delayed backlog reaches that index): let `process_delayed_receipts` drain the queued `AddKey(K_attacker)` receipt. Assert the outcome is `SuccessValue`/no `ActionErrorKind::ActorNoPermission`, and that `get_access_key(state_update, "alice.near", K_attacker)` now returns `Some(FullAccess)` — proving the old attacker key was installed on the new owner's account without their authorization.
