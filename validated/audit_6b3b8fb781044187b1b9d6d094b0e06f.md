### Title
Attacker can fill a victim's per-account token list via dust `DepositToken` transfers/deposits, blocking the victim from using new collateral or debt types - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a per-account cap `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount + debtTokensOfAccount` and reverts any action that would add a new token once the cap is reached (`onlyIfAdditionWillNotReachMaxTokens`, `contracts/Pool.sol:143-148`). The list is keyed by account address, and entries are added to an account not by that account's own action but as a side-effect of *receiving* balance: `DepositToken._transfer` and `_mint` call `pool.addToDepositTokensOfAccount(recipient_/account_)` whenever the recipient's prior balance was zero (`contracts/DepositToken.sol:486-488, 517-520`). An unprivileged attacker can therefore force-push entries into any victim's list by dust-depositing (`deposit(dust, victim)`) or dust-transferring each distinct deposit token to the victim, exactly like the Nouns proposer moving Nouns to fresh addresses to defeat the per-address proposal cap — here the "identity" (the victim's address) absorbs limits it never opted into.

### Finding Description
- `Pool.addToDepositTokensOfAccount` is permissioned only by "caller is a registered deposit token" (`_revertIfSenderIsNotDepositToken`, `contracts/Pool.sol:216-220`), and it reverts with `UserReachedMaxTokens` when the victim's combined list length hits 30.
- `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` (`contracts/DepositToken.sol:211-237`), and `transfer`/`transferFrom`/`seize` go through `_transfer`, which adds the token to the recipient's list (`contracts/DepositToken.sol:498-526`).
- Once the victim's list is full, every code path that would add a *new* token reverts:
  - `deposit()` of any collateral the victim doesn't already hold (`_mint` → `addToDepositTokensOfAccount` → revert).
  - Receiving any new deposit token via `transfer`/`transferFrom`/`seize`.
  - Issuing a debt position in a synthetic the victim doesn't already owe (`DebtToken` mint/issue → `Pool.addToDebtTokensOfAccount`, which shares the same modifier and counter).
- Nothing requires the victim's consent: there is no opt-in, no minimum amount, and no way for the victim to reject incoming tokens.

### Impact Explanation
A victim whose list is stuffed to 30 cannot open a position in any new collateral type and cannot borrow any new synthetic asset. Critically, this can be timed: if the victim's position drifts toward the liquidation threshold and the needed rescue collateral is a token the victim doesn't already hold, `deposit()` reverts with `UserReachedMaxTokens`, temporarily freezing the victim's ability to add collateral while `Pool.liquidate` remains callable against them. Recovery requires the victim to fully withdraw an existing token (`_burn` → `removeFromDepositTokensOfAccount`), costing extra gas and transactions under time pressure — the same "DAO must spend effort to clean up spam" griefing dynamic as the Nouns finding, mapped onto per-account accounting lists.

### Likelihood Explanation
The attack needs only public entry points (`deposit` with `onBehalfOf_ = victim`, or `transfer` of dust msdTOKEN amounts). Cost is bounded by the number of deposit tokens registered in the pool times dust value (each unit of underlying stays in the victim's account; attacker loses only the dust + gas). Feasibility depends on the pool having enough distinct deposit tokens to fill the victim's remaining slots up to 30; pools with many registered collaterals and victims holding several token types are most exposed. No privileged role, oracle manipulation, or timing dependency is required.

### Recommendation
- Skip (rather than revert) or bound additions for forced dust: e.g. have `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` return a boolean and let `_transfer`/`_mint` proceed without adding when the list is full, tracking the position implicitly instead of reverting user funds flows; or
- Only add tokens to an account's list on the account's own actions (`deposit` where `onBehalfOf_ == _msgSender()`, `issue`/`mint` initiated by the account), and handle off-list balances explicitly in `debtPositionOf`/`depositOf`; or
- Enforce a meaningful minimum first-deposit amount so stuffing 30 slots is economically expensive.

### Proof of Concept
Hardhat-style outline against deployed-like fixtures (as in `test/Pool.test.ts`):

```ts
// given: victim holds tokens so that free slots = S (S <= #registeredDepositTokens)
for (const dt of depositTokens.slice(0, S)) {
  if (!victimHolds(dt)) {
    // attacker deposits 1 wei of underlying to victim (or transfers 1 wei msdToken)
    await dt.connect(attacker).deposit(1, victim.address);
  }
}
// victim now has debtTokensOfAccount + depositTokensOfAccount == 30
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// also: borrowing any new synthetic reverts via addToDebtTokensOfAccount
// victim's existing collateral can still be withdrawn, but no NEW token type
// can be added until a token is fully withdrawn (slot freed via removeFrom…)
```

Note: severity is bounded by the pool's registered-token count and by the victim's ability to free a slot by fully withdrawing one token; impact is griefing/temporary blocking of new position types rather than permanent loss.
