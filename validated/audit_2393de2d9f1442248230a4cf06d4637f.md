### Title
Unbounded array allocation from attacker-controlled length word in precompiled-contract input decoding causes node OOM - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a 256-bit "array length" word directly from attacker-controlled precompile call data (`words[offset].intValueSafe()`) and immediately allocate a Java array of that size (`new byte[len][]`) **before** verifying that the declared length is consistent with the actual amount of call data supplied. A contract calling one of the precompiles that use these helpers with a tiny calldata payload but a maliciously large length field can force the node to attempt allocating an array with billions of elements, exhausting heap memory and crashing or stalling the node — the same bug class as the Spring AI PDF `ForkPDFLayoutTextStripper` OOM (CVE-2026-40980), where an attacker-controlled size field drives unreasonable memory allocation.

### Finding Description
The helper methods decode ABI-style dynamic arrays from precompile input: [1](#0-0) [2](#0-1) [3](#0-2) 

In each of these, `len` is taken from a single `DataWord` in the caller-supplied `data` buffer via `intValueSafe()`, which can return values up to `Integer.MAX_VALUE`. The code then does:

```java
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```

with no check that `len` is bounded by the actual size of `words`/`data`, and no cap such as a `MAX_ARRAY_SIZE` sanity check. The only later bound check (`offset > words.length - 1`) validates the *offset*, not the declared *count*. As a result, a transaction that invokes a precompiled contract using this decoding path (batch signature verification / batched byte-array precompiles reachable via `PrecompiledContracts.getContractForAddress`) can supply a small amount of real call data plus one manipulated length word to trigger allocation of an array sized near `Integer.MAX_VALUE * 8` bytes (for the `byte[][]` reference array alone), which throws `OutOfMemoryError` inside JVM heap, or with a large-but-not-immediately-failing size, degrades node performance drastically for every subsequent request handled by that thread pool.

This mirrors the CWE-400 (uncontrolled resource consumption) root cause in the advisory: an external, attacker-supplied length/size field is trusted to size a memory allocation without validating it against the real, bounded amount of underlying data.

### Impact Explanation
Because this decoding happens inside TVM precompiled-contract execution — reachable by any account that can broadcast a `TriggerSmartContract` transaction calling the affected precompile address — an unprivileged transaction sender can trigger an `OutOfMemoryError` on any full node/SR node that executes the transaction (including during block validation by all consensus nodes, since precompile execution is part of consensus-critical VM execution). This can crash node processes or cause the node to become unresponsive, i.e. a node halt/DoS as covered by CWE-400/availability impact in the advisory (CVSS `A:H`).

### Likelihood Explanation
Likelihood is high for any actor able to submit a `TriggerSmartContract` transaction targeting the vulnerable precompiled contract address with crafted call data: crafting the calldata only requires setting one 32-byte length word to a large value while keeping the rest of the payload minimal, so the attack cost (bandwidth/energy for a small calldata buffer) is disproportionate to the resulting server-side memory allocation attempt.

### Recommendation
Before allocating `new byte[len][]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against a sane upper bound (e.g., the maximum sensible signature/element count for the specific precompile) and against the actual remaining size of `data`/`words`, rejecting (returning failure/false) rather than allocating when the declared count cannot possibly be satisfied by the supplied call data length.

### Proof of Concept
1. Construct a `TriggerSmartContract` transaction that calls a precompiled contract address whose implementation invokes `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (e.g., a batch-signature-verification precompile reached through `PrecompiledContracts.getContractForAddress`).
2. Craft the ABI-encoded input so the length word at the expected `offset` decodes (via `intValueSafe()`) to a very large value (close to `Integer.MAX_VALUE`), while the remainder of `data` is kept minimal/short.
3. Submit the transaction; when the node executes the precompile, `new byte[len][]` (or the corresponding array size) is allocated using the attacker-declared length rather than the real payload size, causing an `OutOfMemoryError` / severe memory pressure on the executing node.

Note: I could not directly trace, within the available indexed context, the exact precompile dispatch call sites that invoke `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (their callers were not returned by search), so the precise precompile address/opcode name used in step 1 of the PoC could not be confirmed from the indexed code and would need confirmation via a full repository checkout.
