DepositToken.deposit already uses balance-delta. Checking VesperGateway, NativeTokenGateway, and Treasury pull paths which may not.### Title
`VesperGateway.deposit` ignores fee-on-transfer loss and spends the gateway's pre-existing balance — ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol#L44-L65))

### Summary
`VesperGateway.deposit()` pulls `amount_` of a Vesper pool's underlying token from the caller but then approves and deposits the full nominal `amount_` into the `VPool`, without measuring the actual balance delta received. For a deflationary/fee-on-transfer underlying token, the gateway receives less than `amount_` yet deposits `amount_`, silently covering the shortfall with any tokens already sitting in the gateway contract.

### Finding Description
The relevant code:

```solidity
// contracts/VesperGateway.sol:50-64
IERC20 _underlying = IERC20(vToken_.token());
_underlying.safeTransferFrom(_msgSender, address(this), amount_);

_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);                       // <-- nominal amount, not received amount
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;

IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
vToken_.safeApprove(address(_depositToken), 0);
vToken_.safeApprove(address(_depositToken), _vTokenAmount);
_depositToken.deposit(_vTokenAmount, _msgSender);
```

`amount_` is used verbatim for `vToken_.deposit(amount_)` at line 57. If `underlying` charges a transfer fee `f`, only `amount_ - f` arrives at the gateway, but `vToken_.deposit(amount_)` pulls `amount_` out of the gateway's balance. The deficit `f` is drawn from pre-existing gateway balance — i.e., tokens donated, mistakenly sent, or left behind by prior flows. The attacker then mints `msdVToken` collateral for the full position and can withdraw/withdraw-via-gateway for full value.

By contrast, the core `DepositToken.deposit()` correctly measures the treasury balance delta (`contracts/DepositToken.sol:225-227`) and `SmartFarmingManager._safeTransferFrom` also uses balance-delta (`contracts/SmartFarmingManager.sol:257-261`). The gateway path is the only in-scope surface that skips this check.

### Impact Explanation
The attacker receives vTokens/msdTokens backed partially by tokens that belong to no claim of theirs (stranded/donated underlying in `VesperGateway`). This is direct theft of funds held by the contract — the same "leftover funds" exploitation vector described in the JOJO report. If the Vesper pool's `deposit(amount_)` internally accounts on its own balance delta, the gateway instead just reverts or mis-approves, but for standard `transferFrom`-based pool deposits the vTokens minted to the attacker exceed what they paid in.

### Likelihood Explanation
- Reachable by any unprivileged EOA: `VesperGateway.deposit` is a public function; `pool_` must be a registered pool and `vToken_` is attacker-chosen among registered collaterals (or a pool whose `token()` is a fee-on-transfer asset).
- Requires (a) a whitelisted Vesper collateral whose underlying is deflationary, and (b) a positive stray underlying balance in the gateway. Both are plausible: `TokenHolder.sweep` exists precisely because tokens can get stuck in the gateway, and no code sweeps between calls.
- No modifier (`nonReentrant` is absent on `deposit`, but not needed for this bug), pause flag, or SynthContext check prevents the call.

### Recommendation
Measure the received amount and deposit only that:

```solidity
uint256 _received = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
_received = _underlying.balanceOf(address(this)) - _received;
...
vToken_.deposit(_received);
```

### Proof of Concept
Foundry fork/Hardhat test sketch:

```solidity
// MockFeeOnTransferToken: burns 10% on every transfer
MockFoTToken underlying;      // stands in for vToken_.token()
MockVPool vToken;             // transferFrom-based deposit, mints shares 1:1
VesperGateway gateway;

// 1. Seed stray balance in the gateway (donation / stuck funds)
underlying.transfer(address(gateway), 10e18);

// 2. Attacker deposits 100e18; only 90e18 arrives (10% fee)
underlying.approve(address(gateway), 100e18);
gateway.deposit(pool, IVPool(address(vToken)), 100e18);

// 3. VPool pulled 100e18 from gateway: 90e18 attacker's + 10e18 stranded
//    Attacker received 100 vTokens -> deposited into DepositToken -> msdToken
assertEq(depositToken.balanceOf(attacker), 100e18); // vs. 90e18 actually contributed
assertEq(underlying.balanceOf(address(gateway)), 0); // drained the stranded 10e18
```

Verified path: `VesperGateway.deposit` (no `nonReentrant`, only `UnregisteredPool` check) → `vToken_.deposit(amount_)` with nominal `amount_` → `DepositToken.deposit` mints full msdToken credit.
