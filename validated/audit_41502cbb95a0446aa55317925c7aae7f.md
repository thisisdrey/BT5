### Title
`storage_deposit` intent permanently burns signer's wNEAR on downstream `near_withdraw`/`storage_deposit` promise failure with no refund path - (File: `contracts/defuse/src/contract/intents/state.rs`)

### Summary
`State::storage_deposit` synchronously debits the signer's wNEAR `token_balances` before scheduling `near_withdraw` → `do_storage_deposit` → `ext_storage_management::storage_deposit`, and the resulting promise chain is `.detach()`-ed with no `.then(resolve_*)` callback. Unlike `ft_withdraw`/`ft_resolve_withdraw`, which refunds unsettled amounts back into the sender's ledger, `do_storage_deposit` (and `do_native_withdraw`) has no resolver at all, so if the downstream call fails, the debited wNEAR is never re-credited.

### Finding Description
The invariant that should hold is: `token_balances[signer][wnear] debited == NEAR delivered to storage_deposit.contract_id + amount re-credited to signer on failure`.

In [1](#0-0) , `storage_deposit` calls `self.withdraw(owner_id, [(wnear_token_id, amount)], ...)` which synchronously subtracts the amount from the signer's internal ledger via `internal_sub_balance` ( [2](#0-1) ) in the same receipt as `execute_intents`. This state change commits regardless of what happens to the promises scheduled afterward. The subsequent chain `ext_wnear::near_withdraw(...).then(do_storage_deposit(...))` is `.detach()`-ed with no further callback attached to observe or handle failure.

`do_storage_deposit` itself ( [3](#0-2) ) only `require!`s that `near_withdraw` succeeded (panicking the callback receipt if not) and then fires `ext_storage_management::ext(storage_deposit.contract_id).storage_deposit(...)` as a bare `Promise` with no `.then()` resolver at all.

Two failure paths both permanently destroy the debited balance:
1. If `near_withdraw` fails, `do_storage_deposit` panics via `require!`; the wNEAR is never unwrapped and stays in the wNEAR contract under the Defuse contract's own wNEAR balance, but the signer's internal ledger was already decremented with no re-credit.
2. If `near_withdraw` succeeds but the downstream `ext_storage_management::storage_deposit` call to `storage_deposit.contract_id` fails (e.g., attacker picks a non-existent account or a contract that doesn't implement NEP-145, or one that requires a larger minimum deposit), NEAR protocol refunds the attached deposit to the predecessor (the Defuse contract itself) as raw NEAR — but there is no callback in `do_storage_deposit` to catch that refund and re-credit the signer's `token_balances`.

This is exactly analogous to the pattern correctly handled for `ft_withdraw` (`ft_resolve_withdraw` in [4](#0-3) , which computes `refund = amount - used` and calls `self.deposit(sender_id, ...)` on failure) but is missing entirely for the `storage_deposit` and `native_withdraw` intents ( [5](#0-4) ).

The attacker's payload is simply a signed `MultiPayload` containing a `StorageDeposit` intent whose `contract_id` is chosen (or becomes, e.g. via later deletion) to reject the `storage_deposit` call or an account that doesn't exist, while `amount` is set to the attacker's own wNEAR balance.

### Impact Explanation
The signer's own wNEAR balance is permanently debited from `token_balances` with no corresponding value delivered to any receiver and no re-credit on failure — a direct violation of the "refund or resolver credit that does not match what failed to settle" Critical category. The underlying NEAR ends up either still held by the wNEAR contract (case 1) or refunded as raw native NEAR to the Defuse contract account itself (case 2), unaccounted for and effectively orphaned/lost from the perspective of the Verifier's internal ledger, which breaks the batch-level "balance changes net to zero" invariant since the Verifier's on-chain custodied value no longer matches the sum of `token_balances`. This is repeatable per call and per account.

### Likelihood Explanation
Any unprivileged user holding wNEAR balance in Defuse can trigger this by submitting a `StorageDeposit` intent with a `contract_id`/`deposit_for_account_id`/`amount` combination that they know (or can arrange, e.g. targeting a non-existent account or a contract without `storage_deposit`, or one requiring more than the supplied amount) will make the downstream `ext_storage_management::storage_deposit` call fail. No special privileges, roles, or victim cooperation are required — only a self-authorized signature over the `StorageDeposit` intent. Cost is just the lost amount itself plus gas.

### Recommendation
Add a `#[private]` resolver method chained via `.then()` after the `ext_storage_management::storage_deposit(...)` promise in `do_storage_deposit` (and analogously in `do_native_withdraw`) that inspects `promise_result_checked_*` and calls `self.deposit(owner_id, [(wnear_token_id, amount)], Some(REFUND_MEMO))` when the downstream call did not succeed, mirroring the pattern already used in `ft_resolve_withdraw`.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy Defuse contract with wNEAR configured; fund `signer` account with wNEAR `token_balances[signer][wnear] = X` via a normal deposit flow.
2. Deploy (or reference) a receiver account that does NOT implement `storage_management::storage_deposit` (or simply target a non-existent `contract_id`).
3. Sign and submit `execute_intents` with a `StorageDeposit` intent: `{ contract_id: <bad_contract>, deposit_for_account_id: signer, amount: Y }` where `Y <= X`.
4. Assert immediately after `execute_intents` returns that `token_balances[signer][wnear] == X - Y` (confirming the synchronous debit already committed).
5. Await promise resolution in the sandbox (advance blocks) and assert final state: expected/correct behavior is `token_balances[signer][wnear] == X` (fully refunded since delivery failed); actual behavior is `token_balances[signer][wnear] == X - Y` permanently, with no compensating credit — proving `debited != delivered (0) + re-credited (0)`.

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }

            owner_id,
            [(

            )],
            Some("withdraw"),
            false,

            .with_static_gas(NEAR_WITHDRAW_GAS)

                    .with_unused_gas_weight(0)
                    .do_storage_deposit(storage_deposit),
            )
            .detach();

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
