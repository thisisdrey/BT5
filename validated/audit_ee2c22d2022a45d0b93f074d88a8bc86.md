Audit Report

## Title
Relayer reward ledger entry is irrevocably cleared before XCM delivery to AssetHub is confirmed, permanently losing rewards on remote execution failure - (File: bridges/snowbridge/primitives/core/src/reward.rs)

## Summary
`pallet_bridge_relayers::do_claim_rewards` removes the relayer's `RelayerRewards` entry and then calls `T::PaymentProcedure::pay_reward`, which for `BridgeReward::Snowbridge` resolves to `PayAccountOnLocation::pay_reward`. That function only validates that an XCM *can be sent* to AssetHub (`validate_send`, `charge_fees`, `deliver`) and returns `Ok(())` as soon as the message is handed to the transport layer — it never confirms that the remote `DepositAsset` actually credits the beneficiary. Because the storage removal is committed on local `Ok`, and this XCM (unlike every other Snowbridge inbound XCM program in the codebase) omits an `AssetClaimer` hint, a failed remote deposit permanently and unrecoverably destroys the reward.

## Finding Description
`do_claim_rewards` in [1](#0-0)  takes the reward balance out of `RelayerRewards` via `try_mutate_exists`, calls `T::PaymentProcedure::pay_reward`, and only reverts the storage removal if `pay_reward` returns an `Err`.

For `BridgeReward::Snowbridge`, `pay_reward` dispatches to `snowbridge_core::reward::PayAccountOnLocation::pay_reward`: [2](#0-1) . That implementation builds an XCM containing `ReserveAssetDeposited` followed by `DepositAsset { assets: AllCounted(1), beneficiary }`, then only performs `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver` before returning `Ok(())`: [3](#0-2) . None of these steps observe the actual remote execution outcome on AssetHub, which happens asynchronously in a later block.

Critically, this XCM program is missing the `SetHints { hints: vec![AssetClaimer{..}] }` instruction that the rest of the Snowbridge codebase always inserts before any `DepositAsset` precisely to guard against this scenario. The normal inbound-message converter explicitly does this: [4](#0-3) , and there is a dedicated integration test proving that a user-supplied claimer lets a user recover trapped assets via `pallet_xcm::claim_assets` when `DepositAsset` fails: [5](#0-4) . `PayAccountOnLocation::pay_reward` does not follow this established mitigation pattern: its XCM goes straight from `ReserveAssetDeposited` to `DepositAsset` with no claimer hint set. If `DepositAsset` fails (e.g., the caller-supplied `beneficiary` from `claim_rewards_to` is an unfunded/invalid account that cannot satisfy the ED, per `bridges/modules/relayers/src/lib.rs:224-235`), the asset is trapped under the XCM executor's current context origin at that point — which, after the preceding `DescendOrigin(InboundQueueLocation)` / `UniversalOrigin(GlobalConsensus(EthereumNetwork))` instructions, is an Ethereum-anchored interior location that no local signed account on AssetHub can reproduce via `pallet_xcm::claim_assets`'s `ExecuteXcmOrigin::ensure_origin`. This means the trap is not just unclaimed but structurally unclaimable through the normal user-facing recovery mechanism (`pallet_xcm::claim_assets` / `DropAssets`+`ClaimAssets`, `polkadot/xcm/pallet-xcm/src/lib.rs:1520-1574` and `3901-3985`).

Meanwhile, on BridgeHub, `RelayerRewards::try_mutate_exists` has already committed the removal because `pay_reward` returned `Ok`, so `relayer_reward` returns `None` and `NoRewardForRelayer` blocks any retry.

## Impact Explanation
This matches "permanent user-fund or bridge-state lock" and "duplicate settlement or payout" in the accepted impact list. A relayer's earned, previously-registered reward (`BridgeReward::Snowbridge`) can be permanently and irrecoverably destroyed: the local ledger entry is deleted, and the corresponding value is trapped on AssetHub with no reachable claimer, since the reward-payout XCM path — unlike every other Snowbridge XCM construction path in this repository — omits the `AssetClaimer` hint that would otherwise allow recovery. This breaks the required invariant that "bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically": settlement advances on BridgeHub (ledger cleared) before settlement is confirmed on AssetHub (deposit credited), and unlike the general inbound-message flow, there is no safety net for this particular payout path.

## Likelihood Explanation
No privileged actor or compromised infrastructure is required. Any relayer holding an accrued Snowbridge reward can call the public, signed extrinsic `claim_rewards_to` with a `beneficiary` of `BridgeRewardBeneficiaries::AssetHubLocation(...)` pointing at an account that cannot satisfy AssetHub's existential deposit or otherwise cannot receive the `DepositAsset`. This is fully attacker/relayer-controlled input and reliably triggers permanent loss, because the existing guard in `do_claim_rewards` (reverting only on `Err` from `pay_reward`) cannot detect failures that occur remotely in a later block — `pay_reward` can only report local send/fee/enqueue failures.

## Recommendation
Add a `SetHints { hints: vec![AssetClaimer { location: beneficiary.clone() }] }` instruction to the XCM built in `PayAccountOnLocation::pay_reward` before `DepositAsset`, mirroring the pattern already used in `MessageToXcm::convert` (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`), so a failed remote deposit traps assets under a claimer the relayer/beneficiary can reproduce and recover via `pallet_xcm::claim_assets`. More robustly, avoid treating local delivery as final settlement: keep the `RelayerRewards` entry (or record a pending/claimable marker) until remote execution success is confirmed (e.g., via an XCM query/notify callback), only clearing the ledger entry on confirmed success.

## Proof of Concept
1. A relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward` from processing an inbound message.
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::V5(Location::new(0, [AccountId32 { network: None, id: <fresh, unfunded 32-byte id> }]))))`.
3. `do_claim_rewards` removes the `RelayerRewards` entry; `PayAccountOnLocation::pay_reward` validates/charges/delivers the XCM successfully on BridgeHub and returns `Ok(())`, so the removal commits (`bridges/modules/relayers/src/lib.rs:268-301`).
4. On AssetHub, `ReserveAssetDeposited` mints the reward into holding, but `DepositAsset` to the unfunded beneficiary fails ED checks; because no `AssetClaimer` hint was set (`bridges/snowbridge/primitives/core/src/reward.rs:136-143`, contrast with `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs:386-394`), the asset traps under an Ethereum-anchored origin unreachable by any local signed account.
5. `relayer_reward` now returns `None`; the relayer cannot re-claim, and no account can successfully call `pallet_xcm::claim_assets` to recover the trapped value — confirmable by writing a unit test analogous to `user_supplied_claimer_can_claim_trapped_assets` (`cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_inbound.rs:1158-1276`) but invoking the reward-claim path instead of the inbound-message path, and observing that no `AssetClaimer` hint is emitted and `claim_assets` fails for any candidate origin.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
