### Title
`action_delete_account` permits deleting an account with an outstanding self-targeted postponed receipt, enabling authorization escalation via account recreation - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` (runtime/runtime/src/actions.rs:314-389) validates only `account_storage_usage` against `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` and `gas_key_balance_to_burn` against `GasKeyInfo::MAX_BALANCE_TO_BURN` before calling `remove_account`. It never checks whether the account has outstanding `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, or `TrieKey::PostponedReceiptId` entries keyed to itself. `remove_account` (core/store/src/utils/mod.rs:505-575) confirms this: it only removes the `Account` record, `ContractCode`, access keys/gas-key nonces, and contract data — it does not touch postponed-receipt-related trie keys.

### Finding Description
`process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) postpones an incoming `ActionReceipt` whenever one of its `input_data_ids` has not yet been received, writing `TrieKey::PostponedReceiptId{receiver_id, data_id}` [1](#0-0) , `TrieKey::PendingDataCount{receiver_id, receipt_id}`, and the serialized receipt via `set_postponed_receipt` [2](#0-1) , all keyed by `account_id` (the receiver, i.e. the account itself, since `AddKey` self-targets `X`).

`action_delete_account` performs exactly two economic-safety checks — storage usage and gas-key balance — and nothing else before calling `remove_account` and clearing the account [3](#0-2) . `remove_account` in `core/store/src/utils/mod.rs` only removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and contract data [4](#0-3)  — it does not enumerate or remove any `PendingDataCount`, `PostponedReceipt`, or `PostponedReceiptId` rows for the account being deleted.

Exploit flow: attacker submits `FunctionCall` to `X` producing a self-targeted `AddKey` action receipt with an unresolved input data dependency (so it is postponed and stored under `X`'s key space) → attacker submits `DeleteAccountAction(X)` in a subsequent receipt, which succeeds unconditionally as long as storage/gas-key limits are satisfied, since delete performs no check against `PendingDataCount`/`PostponedReceipt` → attacker submits `CreateAccountAction(X)` to recreate `X` → the deferred `DataReceipt` finally arrives, matches the still-present `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows (never cleaned up by the delete), and the postponed `AddKey` receipt executes against the newly created account. This grants a full-access (or otherwise privileged) key on the new account without the new account's owner (or any current authority) having authorized it — an authorization-exactness violation.

### Impact Explanation
This is authorization escalation across account identity: a receipt authorized under the old incarnation of `X` (self-issued by the original controller) is executed against the new incarnation of `X`, potentially adding an access key or performing other privileged actions the new owner never authorized. This matches NEAR's bounty category for authorization escalation across accounts/promises, and can lead to loss of control of the recreated account and, if funds are subsequently deposited into it, funds theft.

### Likelihood Explanation
Preconditions require an ordinary unprivileged attacker who fully controls their own account `X`: they issue their own `FunctionCall` producing a self-directed `AddKey` promise with a data dependency, then their own `DeleteAccountAction`, then their own `CreateAccountAction` — all standard, permitted actions requiring only that `X` be funded and within delete-eligibility limits (small storage usage, low gas-key balances, locked==0). No validator, node-operator, or leaked-key access is needed; the whole sequence is composed purely of transactions/receipts an ordinary client can submit or trigger via their own contract. This is fully attacker-controlled and repeatable.

### Recommendation
Before allowing `action_delete_account` to succeed, check for and reject deletion (or drain/clear) any outstanding `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, and `TrieKey::PostponedReceiptId` entries keyed to `account_id`. Either add an explicit iteration/check analogous to the storage-usage and gas-key-balance checks that returns an `ActionErrorKind` when pending postponed receipts exist for the account, or extend `remove_account` to purge all such entries as part of deletion (with corresponding compute/storage accounting), and separately ensure `CreateAccountAction` cannot "inherit" postponed receipts left over from a prior incarnation of the same account id.

### Proof of Concept
Unit test in `runtime/runtime/src/actions.rs` test module (near existing `test_delete_account_*` tests):
1. Build a `TrieUpdate` with an account `alice` funded above zero, `storage_usage` under `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, no gas keys.
2. Manually insert `TrieKey::PendingDataCount{receiver_id: alice, receipt_id: some_hash}` = 1, `TrieKey::PostponedReceiptId{receiver_id: alice, data_id: some_data_id}` = some_hash, and a serialized postponed `ActionReceipt` (e.g., containing a self-targeted `AddKey` action) via `set_postponed_receipt`, all before calling `action_delete_account`.
3. Call `action_delete_account(&mut state_update, &mut Some(account), &mut actor_id, &receipt, &mut result, &account_id, &delete_account_action, &config, PROTOCOL_VERSION)`.
4. Assert `result.result.is_ok()` (demonstrating deletion succeeds despite the pending row) and assert that `get::<u32>(&state_update, &TrieKey::PendingDataCount{...})` and `get_postponed_receipt(&state_update, &alice, some_hash)` still return `Some(...)` after the call, proving `remove_account` left the postponed-receipt state intact — confirming the account can be deleted, recreated, and later have the postponed receipt "reattach" and execute against the new account.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
