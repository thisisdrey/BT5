### Title
Meta-transaction (`DelegateAction`) balance refunds are routed to the delegate sender instead of the relayer who actually funded the deposit, letting an unprivileged signer steal the relayer's prepaid balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
In NEP-366 meta-transactions, the relayer (transaction signer) prepays all gas and attached deposits for the inner actions of a `DelegateAction`, while the delegate action's `sender_id` (an ordinary, unprivileged, untrusted end user) becomes the `predecessor_id` of the resulting receipt. When the inner action fails on the receiver's shard, the protocol refunds the attached deposit to the receipt's `predecessor_id` — i.e., the untrusted sender — not to the relayer who actually paid for it. A malicious sender can deliberately construct a `DelegateAction` whose inner action is guaranteed to fail (e.g., targeting a nonexistent method or an account that rejects the call) after attaching a large deposit, causing the relayer's funds to be refunded to the sender instead of back to the relayer.

### Finding Description
`apply_delegate_action` (`runtime/runtime/src/actions.rs:437-519`) builds the inner receipt with `predecessor_id: sender_id.clone()` (the delegate action's `sender_id`, chosen entirely by the unprivileged signer of the `SignedDelegateAction`) while `signer_id`/`gas_price` come from the relayer's outer transaction: [1](#0-0) 

The comment in the code itself acknowledges the asymmetry: "Relayer prepaid all fees and all things required by actions: attached deposits and attached gas... If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer." [2](#0-1) 

The actual refund routing is implemented generically in `refund_unspent_gas_and_deposits`, which on failure pushes a `Receipt::new_balance_refund` addressed to `receipt.balance_refund_receiver()`: [3](#0-2) 

`balance_refund_receiver()` defaults to `predecessor_id()` unless an explicit `refund_to` override was set on the receipt (only possible via the `ActionReceiptV2`/`promise_set_refund_to` host-function path, which `apply_delegate_action` does not use for the receipt it spawns): [4](#0-3) 

The protocol's own documentation confirms this is exploitable: "The relayer can see what the cost will be before submitting the meta transaction and agrees to pay for it, so nothing wrong so far. But what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer... there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [5](#0-4) 

This is structurally the same bug class as the Solidity finding: an unprivileged party (the "creator"/`sender_id`) controls a piece of transaction context (whether the inner action succeeds, and who is recorded as `predecessor_id`) that determines who receives value that another, honest, funding party (the "seller"/relayer) expected to receive back. Just as the Solidity bug let a creator redirect the seller's proceeds to itself by manipulating royalty-recipient membership, here the delegate sender can redirect the relayer's prepaid deposit to itself by manipulating whether/how the inner receipt fails.

### Impact Explanation
Any account can act as `sender_id` in a `SignedDelegateAction` and get an honest relayer to wrap and submit it (relayers are a standard, expected component of the meta-transaction ecosystem, callable from an ordinary client transaction with no special privilege). By choosing an inner `FunctionCall` (or any action) with a large attached deposit that is guaranteed to fail on the receiver's shard (e.g. a nonexistent method name, insufficient gas for the method body, or targeting a contract designed to reject the call), the sender causes the relayer-funded deposit to be refunded entirely back to the sender rather than the relayer. This is concrete theft of the relayer's NEAR balance, executed purely by an ordinary, unprivileged transaction signer.

### Likelihood Explanation
High. No special permissions, validator/node access, or protocol-level trust are required — only a `SignedDelegateAction` from any account and a cooperating (or simply naive) relayer that doesn't pre-simulate the exact deposit-consuming path. This is explicitly called out as a known risk in the project's own documentation, meaning the trigger conditions are well understood and trivially reproducible by any user with an unprivileged access key.

### Recommendation
Route deposit refunds for delegate-action-spawned receipts to the relayer (the outer transaction signer / gas payer) by default, mirroring how gas refunds already go to the signer, rather than to the delegate action's `sender_id`. Alternatively, require an explicit, protocol-enforced `refund_to` on delegate-spawned receipts, or document/require relayers to pre-simulate the exact failure path before funding any deposit, and consider capping/quoting the deposit refund liability per delegate action.

### Proof of Concept
1. Alice (unprivileged) creates a `SignedDelegateAction` with `sender_id = alice`, `receiver_id = bob` (an account with no deployed contract, or a contract lacking the named method), containing one `FunctionCall` action with `method_name: "nonexistent_method"` and `deposit: <large amount>`.
2. Alice signs and forwards this to Relayer, who wraps it into a transaction and pays gas + deposit as documented in `docs/architecture/how/meta-tx.md:44-45`.
3. `apply_delegate_action` spawns a receipt with `predecessor_id = alice`, `signer_id = relayer` toward Bob (`runtime/runtime/src/actions.rs:483-497`).
4. Execution fails on Bob's shard because the method does not exist.
5. `refund_unspent_gas_and_deposits` issues a full deposit refund to `receipt.balance_refund_receiver()` = `predecessor_id()` = Alice (`runtime/runtime/src/lib.rs:1348-1353`, `core/primitives/src/receipt.rs:428-430`), not to Relayer, who funded the deposit and receives nothing back.

    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }
