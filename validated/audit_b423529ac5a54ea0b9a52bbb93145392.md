### Title
Fixed-window stream throttling allows ~2x `max_streams_per_throttling_interval` burst by straddling the reset boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Finding Description
`throttle_stream` enforces a per-connection stream quota using a *fixed* time window rather than a sliding one. `ConnectionStreamCounter::reset_throttling_params_if_needed` only resets `stream_count` to `0` and re-bases `last_throttling_instant` the first time it is called *after* `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since the last reset [1](#0-0) . Between resets, `throttle_stream` simply compares the running `stream_count` against `max_streams_per_throttling_interval` and sleeps only if the count is at/above the cap [2](#0-1) .

Because the window boundary is fixed (not sliding relative to each stream's own timestamp), an attacker can:
1. Open up to `max_streams_per_throttling_interval - 1` streams just before the window naturally expires (near t≈99ms of the 100ms window), all admitted without throttling.
2. Immediately after crossing the boundary (t≈100ms+), the next call to `reset_throttling_params_if_needed` observes `duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL` and resets `stream_count` to `0`, re-basing the window start to "now" [3](#0-2) .
3. The attacker then opens another near-full burst of `max_streams_per_throttling_interval - 1` streams immediately, which are also admitted since the counter was just zeroed.

Within a span of roughly one `STREAM_THROTTLING_INTERVAL` (~100ms) wall-clock time, the attacker can therefore get close to `2 * max_streams_per_throttling_interval` streams admitted through a single connection, because the limiter counts streams per fixed calendar window rather than per any 100ms sliding window anchored to stream arrival times. There is no other mechanism in `throttle_stream`/`ConnectionStreamCounter` that bounds streams over a rolling window; the only guard is the fixed-window counter itself.

### Impact Explanation
This is a QoS-evasion bug: a single unstaked (or low-stake) connection can obtain roughly double its intended per-connection stream/TPS allotment for a short burst by timing traffic around the throttling window edge, at the cost of only its own connection's fairness accounting — it does not corrupt state, panic the node, or bypass sigverify/consensus. The blast radius is bounded to the per-connection stream quota (e.g., `max_unstaked_load_in_throttling_window` for unstaked peers, computed in `StakedStreamLoadEMA::new` [4](#0-3) ), which is intentionally small relative to total capacity; broader protections (connection limits, per-stake proportional shares, EMA-based staked throttling) remain intact. It is a real, reproducible bypass of the stated per-interval limit invariant, but its scoped impact is a bounded (≈2x) throughput amplification for a single connection rather than a systemic DoS.

### Likelihood Explanation
Fully feasible with a single unstaked connection and no special privileges — the attacker only needs to time two bursts of QUIC stream opens around a 100ms boundary, which is trivial to script client-side (open streams, wait, open more streams). It is deterministic given control of local wall-clock-relative timing and requires no races beyond normal client-driven timing (the double-checked-lock in `reset_throttling_params_if_needed` is for thread-safety, not a security boundary).

### Recommendation
Replace the fixed-window counter with a sliding-window or token-bucket algorithm anchored to the current time rather than to the last reset instant, e.g., track individual stream timestamps (or fractional bucket refill) so that at most `max_streams_per_throttling_interval` streams are ever admitted in *any* `STREAM_THROTTLING_INTERVAL`-length window, not just per fixed calendar window. A token-bucket with continuous refill (`tokens += elapsed_ms * rate`) capped at the burst size is the standard fix for this class of issue.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_fixed_window_boundary_burst_doubles_throughput() {
    use std::sync::atomic::Ordering;

    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams: u64 = 10;

    // Burst 1: fill up to just under the cap right before window end.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Advance clock to just past the throttling interval boundary.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // This call triggers reset_throttling_params_if_needed -> resets stream_count to 0.
    throttle_stream(
        &stats,
        ConnectionPeerType::Unstaked,
        "127.0.0.1:0".parse().unwrap(),
        &counter,
        max_streams,
    )
    .await;

    // Burst 2: immediately admit another full burst right after reset.
    let mut admitted_second_burst = 0;
    for _ in 0..max_streams {
        let before = counter.stream_count.load(Ordering::Relaxed);
        if before < max_streams {
            counter.stream_count.fetch_add(1, Ordering::Relaxed);
            admitted_second_burst += 1;
        }
    }

    // Total admitted within ~1 STREAM_THROTTLING_INTERVAL window:
    let total_admitted = max_streams + admitted_second_burst;
    assert_eq!(total_admitted, 2 * max_streams, "expected ~2x burst across the reset boundary");
    // Desired invariant (currently violated): total_admitted should be <= max_streams
    // for any STREAM_THROTTLING_INTERVAL-length sliding window.
}
```

```rust
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
```
