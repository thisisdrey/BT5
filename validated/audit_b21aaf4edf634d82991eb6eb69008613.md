## Analysis Result

### Title
Weight double-counting via malleable multisig signatures in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x0a`), reachable from any smart contract call, aggregates signer weight to satisfy a multi-signature `Permission` threshold. Its de-duplication logic can be bypassed with two distinct-but-valid signatures from a single key over the same hash, allowing that one key's weight to be counted more than once toward the threshold.

### Finding Description
In `ValidateMultiSign.execute`, for each supplied raw signature the code recovers the signer address and checks for prior use: [1](#0-0) 

The de-duplication only skips accumulation (`continue`) when the exact byte-identical `merge(recoveredAddr, sign)` value has already been seen. If the same `recoveredAddr` was already used but the raw signature bytes differ (e.g., a second valid signature over the same hash produced by the same private key — via a different ECDSA nonce or a malleable `(r, n-s, flipped-v)` variant), the code does **not** skip; it falls through, recomputes `getWeight(permission, recoveredAddr)` [2](#0-1) , and adds that key's weight to `totalWeight` again. This lets a single signer submit two differing-but-valid signatures for themselves to be counted as two independent approvers.

This is structurally the same bug class as the reported thirdweb incident: a signature-based authorization check that fails to bind the counted approval to a single unique signer/nonce, letting an attacker manufacture an extra "valid" credential to satisfy a threshold check it should not satisfy — the vulnerability is in the *verification logic itself*, not in the underlying cryptography.

By contrast, `TransactionCapsule.checkWeight` — used for on-chain transaction multisig — keys its duplicate map by `encode58Check(address)` once `VERSION_4_7_1` fork is active [3](#0-2) , i.e. it de-duplicates by signer address, not raw signature bytes. `ValidateMultiSign`, in the TVM precompile, never received an equivalent address-keyed fix; it still de-duplicates by the full `(address||signature)` byte-string, which is bypassable by any second distinct valid signature from the same key.

### Impact Explanation
Any TVM contract that relies on `ValidateMultiSign` (address `0x0a`) to gate privileged operations (e.g., custom multi-sig wallets, DAO-style approval contracts deployed on TRON) can have its threshold satisfied by a single colluding/compromised key providing two distinct signatures instead of the intended number of independent signers. This is an unauthorized-account-operation / permission-bypass primitive directly reachable by an unprivileged contract caller supplying attacker-controlled signature bytes, matching the "concrete unauthorized account operation" impact bar.

### Likelihood Explanation
Reachable by any address issuing a `TriggerSmartContract` call into any contract that invokes the `ValidateMultiSign` precompile — no special privilege, SR/witness role, or node compromise needed. The only precondition is producing two distinct valid signatures for the attacker's own key over the same hash (achievable via non-deterministic `k` in signing, or classic ECDSA `s`/`n-s`, `v` malleability, if the signing implementation does not enforce low-`s` canonicalization end-to-end for this path). I was unable to fully confirm from available index content whether `ECKey`/`SignUtils.fromComponents` and `signature.validateComponents()` in `recoverAddrBySign` enforce canonical low-`s` signatures, which would materially affect exploit difficulty — this should be verified directly in `crypto/src/main/java/org/tron/common/crypto/ECKey.java` in a full checkout.

### Recommendation
Change the duplicate-detection key in `ValidateMultiSign.execute` from `merge(recoveredAddr, sign)` (full signature bytes) to `recoveredAddr` alone, mirroring the address-keyed fix already applied in `TransactionCapsule.checkWeight` post `VERSION_4_7_1`. Any repeat of an already-seen `recoveredAddr` — regardless of whether the raw signature bytes differ — must be skipped (or rejected) rather than re-counted.

### Proof of Concept
1. Deploy a contract that calls the `ValidateMultiSign` precompile (`0x0a`) with an account address `A`, `permissionId`, and `data`, where `A`'s active permission has threshold `T` requiring 2 distinct keys, e.g. `key1` weight 1 and `key2` weight 1.
2. Compute `hash = sha256(A || permissionId || data)` as done in the precompile [4](#0-3) .
3. Using only `key1`, produce two distinct valid signatures over `hash` (e.g., by re-signing with non-deterministic nonce, or by flipping to the malleable `(r, n-s, 1-v)` form if not rejected by `validateComponents`).
4. Submit both signatures as the `signatures` array to `ValidateMultiSign`.
5. Observe: the loop processes signature 1, adds `key1`'s weight (1) and records `merge(addr1, sig1)`; on signature 2 it finds `recoveredAddr` (addr1) already in `executedSignList` but `merge(addr1, sig2)` is not present, so it does **not** `continue` — it adds `key1`'s weight again, yielding `totalWeight = 2 >= threshold(2)`, returning `dataOne()` (success) despite only one real key participating.
