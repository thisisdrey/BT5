This confirms the analog: `validate_deterministic_state_init` (`runtime/runtime/src/action_validation.rs:435-449`) only checks that `derive_near_deterministic_account_id(&action.state_init)` matches the receiver, and `validate_global_contract_identifier` merely validates the identifier's syntactic form — neither rejects `GlobalContractIdentifier::AccountId` in favor of requiring the immutable `CodeHash` form. Since a deterministic account's identity is a commitment over its `DeterministicAccountStateInit` (which embeds a `GlobalContractIdentifier`, not the code itself), using the mutable `AccountId` variant means the code backing the account can be silently swapped after account creation and after users have sent funds to the deterministically-derived address, exactly mirroring the Safe bug where a superficial/structural check (codehash of the proxy shell) doesn't pin the actual mutable logic (singleton) the funds ultimately trust.

### Title
Deterministic accounts can bind identity to a mutable `GlobalContractIdentifier::AccountId`, letting the code backing an already-funded account be swapped post-creation - (File: runtime/runtime/src/action_validation.rs)

### Summary
NEP-616 deterministic accounts (`0s...`) derive their account ID purely from the borsh-encoded `DeterministicAccountStateInit`, which references code via a `GlobalContractIdentifier` that can be either an immutable `CodeHash` or a **mutable** `AccountId` (owner-updatable) global contract. `validate_deterministic_state_init` does not restrict this choice, so a deterministic account's on-chain identity can commit to "whatever code account X currently/later publishes" rather than to specific, audited bytecode — an indirection weakness structurally analogous to the reported Gnosis Safe issue, where a superficial identity check (proxy codehash) fails to pin the actual mutable logic (singleton) controlling funds.

### Finding Description
`DeterministicAccountStateInitV1` embeds `code: GlobalContractIdentifier` [1](#0-0) . `GlobalContractIdentifier` has two variants, and the docs are explicit that the `AccountId` deploy mode "allows the owner to update the contract for all its users" while `CodeHash` "effectively makes the contract immutable" [2](#0-1) .

The account ID itself is `derive_near_deterministic_account_id`, a hash over the entire `DeterministicAccountStateInit` struct (including whichever `GlobalContractIdentifier` variant was chosen) [3](#0-2) . Validation of the `DeterministicStateInitAction` only checks that this derived ID matches the receiver and validates storage-key/value length limits and the identifier's basic well-formedness — it never forbids the mutable `AccountId` global-contract form: [4](#0-3) .

When the account is actually created, `deploy_deterministic_account` resolves the code by calling `use_global_contract`, which for the `AccountId` variant reads whatever code currently lives under `TrieKey::GlobalContractCode{identifier: AccountId(publisher)}` [5](#0-4) . That code is not fixed: any subsequent `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` from the same publisher account overwrites the code at that identifier for *all* referencing accounts, gated only by a freshness nonce, not by content-hash pinning: [6](#0-5) [7](#0-6) . Tests explicitly demonstrate this live-update behavior for regular accounts using such contracts [8](#0-7) .

The consequence for deterministic accounts is that a user (or protocol) deriving a `0s...` address off-chain — trusting the code identified by a publisher's `AccountId` at derivation time — has no on-chain guarantee that the code executing at that address will remain the code they inspected. Because the account ID commitment covers only the *identifier* (a pointer), not the code bytes, the publisher can redeploy different logic under the same `AccountId` identifier at any time, including after the deterministic account is created and funded, changing the account's actual authorization/spending logic without changing its externally-verified address. This is the direct structural analog of the Safe bug: `checkIfBeneficiaryIsATrustedSafe` verified only `beneficiary.codehash` (the immutable proxy shell) and not the mutable singleton pointed to by proxy storage slot 0, allowing an attacker-controlled singleton swap to bypass the intended 2-of-2 trust invariant despite the codehash check passing.

### Impact Explanation
If any protocol, relayer, or user relies on a `0s...` deterministic account ID as a stable commitment to specific contract logic (e.g., to escrow funds, gate withdrawals, or enforce a specific authorization scheme) while using `GlobalContractIdentifier::AccountId` for `code`, the publisher of that global contract can redeploy new code that drains or otherwise misappropriates funds held by every account referencing that identifier — a direct theft/authorization-escalation vector reachable purely through ordinary transactions (`DeployGlobalContractAction`, `DeterministicStateInitAction`), with no privileged/validator access required.

### Likelihood Explanation
High: `DeployGlobalContractAction` with `AccountId` mode and `DeterministicStateInitAction` are both ordinary, permissionless transaction actions available to any account. No protocol feature gate restricts deterministic accounts from referencing the mutable `AccountId` global-contract form [4](#0-3) , and existing tests even build deterministic accounts this way as the normal path [9](#0-8) .

### Recommendation
Require `DeterministicStateInitAction.state_init.code()` to be a `GlobalContractIdentifier::CodeHash` (rejecting `AccountId`) inside `validate_deterministic_state_init`, so a deterministic account's derived identity is always a true commitment to specific, immutable bytecode — mirroring the external report's recommendation to bind trust to the actual, unforgeable implementation rather than an indirection that can be silently swapped.

### Proof of Concept
1. Account `publisher.near` deploys benign code `V1` via `DeployGlobalContractAction{ deploy_mode: AccountId }` (`runtime/runtime/src/global_contracts.rs:24-61`).
2. A user derives `state_init = DeterministicAccountStateInit::V1 { code: GlobalContractIdentifier::AccountId(publisher.near), data }` and computes `det_account = derive_near_deterministic_account_id(&state_init)` (`core/primitives/src/utils.rs:495-503`), inspects/audits `V1`, and sends funds to `det_account`, then executes `DeterministicStateInitAction` to activate it (`runtime/runtime/src/deterministic_account_id.rs:15-94`, resolving code via `use_global_contract`).
3. `publisher.near` later submits another `DeployGlobalContractAction{ code: V2 (malicious), deploy_mode: AccountId }` referencing the same `AccountId` identifier; `initiate_distribution`/`apply_distribution_current_shard` overwrite the code stored under `GlobalContractCode{AccountId(publisher.near)}` once the nonce check passes (`runtime/runtime/src/global_contracts.rs:142-234`).
4. `det_account` — same address, same on-chain ID, no re-derivation possible — now executes `V2` on every subsequent `FunctionCall`, since `AccountContract`/`RuntimeContractIdentifier::resolve` reads the current code for the `AccountId` identifier rather than a hash pinned at creation time (`runtime/runtime/src/contract_code.rs:32-73`), allowing `publisher.near` to steal or redirect any funds/authorization logic tied to `det_account`.

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
