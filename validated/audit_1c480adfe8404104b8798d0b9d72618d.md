### Title
Predictable per-deployer CREATE2 salt in `SmartAccountFactory.deploySmartAccount` allows front-running that permanently DoSes a deployer's account creation and desyncs the `isDeployedSmartAccount` provenance registry - (File: `contracts/SmartAccountFactory.sol`)

### Summary
`SmartAccountFactory.deploySmartAccount` derives the Safe's `CREATE2` salt from `keccak256(msg.sender, nonces[msg.sender]++)`, exactly the analog of the reported `PRBProxyRegistry` pattern where salting alone (without protecting the underlying deployment call itself) is insufficient to stop a griefer from reaching the deployment first and causing the legitimate call to revert.

### Finding Description
`deploySmartAccount` computes the salt and calls the external `SafeProxyFactory` directly: [1](#0-0) 

Both `nonces[deployer]` (public mapping) and the full parameter set needed to reproduce the exact `initializer` bytes (`delegates`, `currencies`, `nftCollections`, `trustedRecipients`, `validUntil`, `owners`, `threshold`) are either publicly readable on-chain or visible in the pending mempool transaction. An observer can therefore compute the exact same `saltNonce` and `initializer` and call `SAFE_PROXY_FACTORY.createProxyWithNonce(SAFE_SINGLETON, initializer, saltNonce)` directly, bypassing `SmartAccountFactory` entirely, before the legitimate `deploySmartAccount` transaction lands. `SafeProxyFactory.createProxyWithNonce` reverts if a contract already exists at the computed `CREATE2` address, so the legitimate `deploySmartAccount` call then reverts inside the external call — **before** `nonces[msg.sender]++` is durably committed (the whole transaction, including the earlier storage write, is rolled back) and **before** `isDeployedSmartAccount[safeAddress] = true` is ever recorded.

Because the front-runner used the exact same `initializer` bytes (same owners/threshold/config — they have no reason or ability to alter it advantageously, since the Safe’s address commits to the full initializer hash), the resulting Safe is deployed correctly with the intended owners. However:
- `isDeployedSmartAccount[safeAddress]` remains permanently `false` for a Safe that is otherwise a fully legitimate, correctly-owned deployment, corrupting the on-chain provenance registry the specs describe as the integration point integrators/tooling rely on (`isDeployedSmartAccount` — "lets integrators and users verify that a Safe account was deployed by this factory"). [2](#0-1) 
- The deployer's `nonces[msg.sender]` counter never advances (the increment is reverted along with the rest of the failed call), so **every subsequent retry with the same parameters recomputes the identical salt**, which is already taken — the deployer is permanently unable to deploy that role Smart Account through `SmartAccountFactory` again unless they pick different configuration/owners entirely.

This is structurally the same root cause the external report flags for `PRBProxyRegistry`: salting the `CREATE2` deployment with attacker-unpredictable-but-still-observable inputs stops address *hijacking* but not front-running of the *deployment call itself*, letting an outsider force the underlying factory (`SafeProxyFactory`) to a state that makes the legitimate, permissioned call revert.

### Impact Explanation
This blocks the onboarding of a role Smart Account (Borrower/Investor/Servicer/Shareholder etc.) through the sanctioned `SmartAccountFactory` path with no recovery other than re-parameterizing the deployment (different owners/threshold/delegates), which is an operational DoS on the production deployment/onboarding flow described in `specs/deployment/production_deployment_runbook.md` (SA configuration and role registration steps depend on Safes deployed and recognized via this factory). It also creates a real, permanently-deployed Safe with correct owners that the protocol's own on-chain provenance check (`isDeployedSmartAccount`) will never recognize as platform-originated, which can block any downstream logic gated on that check.

### Likelihood Explanation
The trigger requires no special privileges — only mempool visibility of a pending `deploySmartAccount` transaction (or knowledge of the deployer's next nonce, which is public) and enough gas to call `SafeProxyFactory.createProxyWithNonce` directly with the copied calldata. No signature or ownership of the Safe is required by the griefer. The only "cost" to the attacker is gas to deploy a Safe they gain nothing from, which is a plausible, cheap griefing vector on a public chain, especially against known, publicly identifiable protocol deployer addresses (e.g., the operational deployer account referenced throughout the production runbook).

### Recommendation
Do not rely solely on `CREATE2` address predictability for correctness. Either:
- Detect the pre-existing deployment (compare `SAFE_PROXY_FACTORY`'s computed address against `predictSmartAccountAddress` before calling `createProxyWithNonce`) and treat an already-deployed Safe with matching `initializer`/owners as a successful outcome (idempotent success) rather than reverting the whole nonce-consuming transaction; or
- Increment/reserve `nonces[msg.sender]` in a way that survives a revert (e.g., commit the nonce reservation in a separate, unconditionally-mined step, or allow explicit nonce skipping), so a griefed deployer is not permanently stuck replaying the same salt; and
- Register `isDeployedSmartAccount` based on actual on-chain code presence/owner match rather than only via the success path of `deploySmartAccount`, so a griefer cannot desync the registry from reality.

### Proof of Concept
1. Deployer `D` (e.g., production `dp` account) submits `deploySmartAccount(delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold)`. `nonces[D]` is currently `n`, so `saltNonce = keccak256(D, n)`, and `initializer` is fully determined by the call's calldata.
2. Attacker `A` observes the pending transaction in the mempool (or simply reads public `nonces(D)` and knows/guesses the intended parameters), reconstructs `initializer` and `saltNonce`, and front-runs by calling `SAFE_PROXY_FACTORY.createProxyWithNonce(SAFE_SINGLETON, initializer, saltNonce)` directly with higher gas.
3. `A`'s transaction lands first and deploys the Safe at the predicted address with the correct owners (since `A` copied the exact calldata) — but `isDeployedSmartAccount` is not set because `A` never called through `SmartAccountFactory`.
4. `D`'s original `deploySmartAccount` transaction now reverts inside `SAFE_PROXY_FACTORY.createProxyWithNonce` (address already has code), and because the whole call reverts, `nonces[D]` is not incremented.
5. Any retry by `D` with the same parameters recomputes the same `saltNonce`, hits the same already-occupied address, and reverts again — `D` is permanently blocked from deploying this specific role Smart Account through `SmartAccountFactory`, and the deployed Safe (with correct owners) is never marked `isDeployedSmartAccount[safeAddress] == true`.
