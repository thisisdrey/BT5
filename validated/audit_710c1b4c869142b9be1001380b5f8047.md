### Title
Bancor-style exchange inject/withdraw computes paired-token amount from live pool ratio with no slippage bound, enabling front-running financial loss - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` derive the amount of the paired token (`anotherTokenQuant`) purely from the exchange's current on-chain pool ratio (`firstTokenBalance`/`secondTokenBalance`) at the moment the transaction is executed, and this ratio can be manipulated between broadcast and block inclusion by any account that trades against the same exchange pair (`ExchangeTransactionActuator`). Unlike `ExchangeTransactionContract`, which has an `expected` field enforced during validation, `ExchangeInjectContract` and `ExchangeWithdrawContract` have no minimum/maximum output bound at all, so the victim's transaction cannot revert on unfavorable price movement — it always executes at whatever ratio exists when the block producer processes it.

### Finding Description
`ExchangeInjectActuator.execute()` reads the pool's `firstTokenBalance`/`secondTokenBalance` and computes `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` (or the inverse), then immediately debits both the specified `tokenQuant` and the computed `anotherTokenQuant` from the caller's account and updates the pool balances. [2](#0-1) 

The same live-ratio computation, with no bound check, is repeated in `doValidate()`. [3](#0-2) 

`ExchangeWithdrawActuator` follows the identical pattern: it computes `anotherTokenQuant` from the live pool ratio and only checks internal computation precision ("Not precise enough"), never a caller-specified acceptable range. [4](#0-3) [5](#0-4) 

In contrast, `ExchangeTransactionActuator` (a swap) explicitly protects the caller by requiring `anotherTokenQuant >= tokenExpected`, reverting the whole transaction if the computed amount is worse than what the caller signed for. [6](#0-5) 

This is the direct analog of the reported Arrakis `addLiquidity` bug: state that determines the economic terms of the operation (the pool ratio) is read and acted upon at execution time rather than being pinned/bounded by the signer, so anyone able to broadcast a transaction that trades against the pool (`ExchangeTransactionContract`) can shift the ratio before the victim's `ExchangeInjectContract`/`ExchangeWithdrawContract` is included, causing the victim to deposit/receive a worse amount of the paired token than intended — with no revert path available.

### Impact Explanation
An attacker (any account holding either token of the exchange pair — no special privilege required to call `ExchangeTransactionContract`) can observe a pending `ExchangeInjectContract` or `ExchangeWithdrawContract` in the mempool and submit a swap with higher energy/bandwidth priority to shift the pool ratio just before the victim's transaction executes. Since neither inject nor withdraw carries a minimum-output bound, the victim's inject will silently deposit an unfavorable amount of the paired token (effectively donating value to the pool/attacker), and the victim's withdraw will silently receive less of the paired token than expected. This is a concrete unauthorized value transfer/financial loss reachable purely through ordinary signed transactions.

### Likelihood Explanation
Exploitation requires only the ability to submit an ordinary `ExchangeTransactionContract` transaction against the same exchange pair and observe the victim's pending inject/withdraw transaction in the mempool — both are permissionless, unprivileged actions available to any account. The Exchange/Bancor market feature is a native, currently-supported contract type in java-tron, so this is reachable in production whenever exchange pools with nontrivial liquidity exist. The only mitigating factor is that inject/withdraw is restricted to `exchangeCapsule.getCreatorAddress()`, so only the pool creator is the victim — but the creator's assets are still directly at risk from any third-party attacker.

### Recommendation
Add a slippage-bound field (analogous to `ExchangeTransactionContract.expected`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, e.g. `min_another_token_quant` / `max_another_token_quant`, and enforce it in `doValidate()`/`execute()` so the transaction fails (rather than silently executing at an unfavorable ratio) if the pool ratio has moved beyond the caller's specified tolerance between signing and execution.

### Proof of Concept
1. Attacker monitors the mempool and observes a pending `ExchangeInjectContract` from the pool creator specifying `tokenID = firstTokenID`, `quant = Q` (computed by the client off-chain against ratio `R0 = secondTokenBalance/firstTokenBalance` at broadcast time).
2. Attacker submits (and gets included first, e.g. via higher bandwidth/energy priority) an `ExchangeTransactionContract` swap against the same pool that shifts the ratio to `R1 != R0`. [7](#0-6) 
3. The victim's `ExchangeInjectContract` is then processed by `ExchangeInjectActuator.execute()`, which recomputes `anotherTokenQuant` from the now-shifted pool balances and unconditionally debits that (unfavorable) amount from the victim's account with no revert check. [8](#0-7) 
4. The victim ends up depositing more of the paired token (or, in the withdraw case, receiving less) than they intended when they signed the transaction at ratio `R0`, and there is no `expected`/minimum field to cause the transaction to fail instead.
