### Title
Unbounded Heap Allocation from Untrusted Length Word in TVM Precompiled-Contract ABI Decoders Causes Memory-Exhaustion DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The ABI-decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` allocate Java arrays whose size is taken directly from an attacker-controlled 256-bit word (`intValueSafe()`) without validating that the declared length is consistent with the actual amount of calldata supplied to the precompile. This mirrors the buffa `decode_unknown_field` flaw: a length field taken from untrusted input is used to size an allocation before the input is checked to actually contain that much data, letting a tiny transaction/contract call trigger a huge allocation and crash the node with `OutOfMemoryError`.

### Finding Description
`extractBytes32Array` reads a length word and immediately allocates an array of that size with no bound check at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` only check that `offset` is within `words.length`, but the `len` value used to size `new byte[len][]` (and, in `extractBytesArray`, the subsequent per-element `bytesLen` used for `extractBytes`) is taken straight from `words[offset].intValueSafe()` with no upper bound relative to the actual size of `words`/`data`: [2](#0-1) 

`intValueSafe()` on `DataWord` converts an arbitrary attacker-supplied 256-bit ABI word into an `int`, so a caller can set this length word to `0x7fffffff` (`Integer.MAX_VALUE`). `new byte[Integer.MAX_VALUE][]` alone (an object-reference array) requires on the order of 16 GB of heap on a 64-bit JVM, and is attempted before any check that the real precompile input (`data`) is anywhere near that size, and before any energy/CPU accounting can reject the call. This is functionally identical to the buffa root cause: the allocation size is derived from an untrusted "length" field with no allocation budget or cross-check against available bytes, enabling large amplification/DoS from a tiny input.

These decoders are used by TVM precompiled contracts (address-dispatched via `PrecompiledContracts.getContractForAddress`) that process array/signature-list ABI parameters — i.e., reachable from any account that can deploy a contract and issue a `CALL`/`STATICCALL` to the corresponding precompile address with crafted calldata, exactly the "TVM opcodes, precompiles and energy metering" surface in scope.

### Impact Explanation
A single crafted transaction that calls into a precompiled contract exercising one of these decoders with a manipulated length word can force the FullNode/SolidityNode JVM to attempt an enormous allocation, throwing `OutOfMemoryError`. Depending on where the OOM is caught (or not caught), this can crash block/transaction processing threads or the whole node process, denying service to legitimate users — matching CWE-400/CWE-770/CWE-789 in the report and the "node crash" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: any unprivileged account can deploy a contract and call the vulnerable precompile with attacker-chosen ABI words, so the path is reachable without special privilege. However, the practical impact depends on which precompile(s) actually invoke these helper functions and whether preceding energy-cost calculations reject the call before the allocation runs; this call-site linkage could not be fully confirmed from the indexed content available, since usages of `extractBytesArray`/`extractBytes32Array`/`extractSigArray` were only located inside `PrecompiledContracts.java` itself and their exact callers/energy gating were not retrievable through the current search tools.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual remaining `words`/`data` length (e.g., `len` must not exceed `(words.length - offset - 1)` and each derived `bytesLen`/`bytesOffset` must be validated against `data.length`) and reject with a defined error rather than allocating. Consider also capping array-parameter counts by a fixed maximum consistent with the energy already charged for the call, so the cost of decoding cannot exceed the energy budget paid by the caller.

### Proof of Concept
1. Craft a transaction that deploys a small contract and, in its constructor or a function, issues a `CALL`/`STATICCALL` to the TVM precompile address that is decoded via `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (per [3](#0-2) ).
2. Encode the call data so the length word at the expected `offset` is `0x7fffffff` while the actual payload is only a few words long.
3. Submit/broadcast the transaction; when the precompile executes, `words[offset].intValueSafe()` yields `Integer.MAX_VALUE`, and `new byte[Integer.MAX_VALUE][]` is attempted, exhausting/crashing the JVM heap.

Note: full confirmation of the specific reachable precompile entry point (its address and whether energy accounting precedes this allocation) could not be completed within the available indexed context and would need direct source inspection in a live session.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
