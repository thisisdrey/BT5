### Title
Unbounded array allocation from attacker-controlled length in precompiled-contract calldata parsing causes OutOfMemoryError - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read a length field directly out of the calldata `words` array supplied to a precompiled contract call and immediately allocate a `byte[len][]` array of that size — with no upper bound check on `len` before the allocation. This mirrors the OpenJPEG pattern in CVE-2019-6988, where a size value parsed from attacker-controlled input is passed to an allocator (`opj_calloc`) before any sanity/consistency check against the actual available data, causing an "attempted excessive memory allocation" denial of service.

### Finding Description
`extractBytesArray` computes `len` from `words[offset].intValueSafe()` and then does `byte[][] bytesArray = new byte[len][];` before validating that `len` corresponds to any real content in the supplied `data`: [1](#0-0) 

`extractBytes32Array` has the identical unchecked pattern: [2](#0-1) 

The only guard present is `if (offset > words.length - 1)`, which bounds the *offset* into the calldata word array, not the *length value itself*. Because `intValueSafe()` only clamps a 256-bit `DataWord` into a safe `int` range (up to `Integer.MAX_VALUE`), an attacker who controls the raw call data passed into a precompiled contract can set this length field to a very large value (e.g., close to `Integer.MAX_VALUE`). The JVM will then attempt to allocate an object-reference array of that size (`new byte[len][]`), which for large `len` immediately exhausts heap and throws `OutOfMemoryError` — an `Error`, not an `Exception`, so it is not caught by typical `catch (Exception e)` blocks used elsewhere in the precompiled-contract dispatch and VM execution paths, as seen in the `ECRecover.execute` pattern nearby that only catches `Throwable` in some cases but not universally across the precompiled contract call chain: [3](#0-2) 

This is directly analogous to the OpenJPEG bug class: a length parsed from untrusted input is used to size an allocation before the input is otherwise validated as internally consistent, producing an attempted excessive/oversized memory allocation.

### Impact Explanation
If reachable from a precompiled contract whose `execute(byte[] data)` is invoked via a normal `CALL`/`STATICCALL` TVM opcode from any smart contract (i.e., data fully attacker-controlled), a single crafted transaction could trigger an uncaught `OutOfMemoryError` inside the TVM execution thread. Depending on how the surrounding runtime handles `Error` versus `Exception` during contract execution, this can crash the node process or destabilize the JVM heap for all concurrently executing transactions, i.e., a remote, low-cost denial-of-service against block-producing/API-serving nodes — matching the "node crash or halt" impact bar for this analog scan.

### Likelihood Explanation
Exploitability depends on: (1) confirming that one of the precompiled contracts calling `extractBytes32Array`/`extractBytesArray` is reachable from ordinary (non-privileged) transactions without a preceding length/energy check that would reject an oversized `len` before reaching the allocation, and (2) whether `OutOfMemoryError` thrown mid-precompile-execution is actually left uncaught along that specific call path. I could not fully verify the exact calling precompiled contract(s) and any pre-checks in my available search budget — this needs to be confirmed with deeper tracing of all `extractBytes32Array(`/`extractBytesArray(` call sites in `PrecompiledContracts.java`.

### Recommendation
Add an explicit upper bound check on `len` immediately after parsing it in both `extractBytes32Array` and `extractBytesArray` (e.g., bound it against the remaining `words.length` or a fixed sane maximum) before allocating `new byte[len][]`, so a malformed/oversized length is rejected with a normal validation failure rather than allowed to reach the JVM allocator.

### Proof of Concept
Conceptually: construct calldata for a precompiled contract that internally calls `extractBytesArray`/`extractBytes32Array`, placing at the expected `offset` word a very large 256-bit integer (e.g., `0x7FFFFFFF`) as the "array length" field, then send a transaction (`CALL`/`STATICCALL`) invoking that precompile address with this calldata. This should be validated end-to-end in a live Devin session to confirm the exact reachable precompile and observe the resulting `OutOfMemoryError`/crash, since I was unable to trace the concrete call sites in this pass.
