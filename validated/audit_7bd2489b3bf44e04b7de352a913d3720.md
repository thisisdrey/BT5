### Title
Multi-signature threshold bypass via duplicate-address signature counting in `ValidateMultiSign` precompile - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
CVE-2016-7444 is a class of bug where a validation routine fails to canonicalize/verify a value before using it to detect equivalence, so semantically identical data with different trailing/incidental bytes escapes an intended dedup/consistency check. The `ValidateMultiSign` TVM precompile in java-tron has the same class of flaw: it deduplicates signer entries by comparing the *raw signature bytes* (address + signature) instead of the *recovered signer address* alone. Because ECDSA signing is non-deterministic, one private key can produce many distinct valid signatures over the same hash, each of which passes the raw-byte inequality check and is counted again toward the permission's weight threshold.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute()` recovers a signer address for every supplied signature and is supposed to reject a signer who has already been counted: [1](#0-0) 

```
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```

The "already counted" check is only a `continue` (skip) when the *exact* `merge(recoveredAddr, sign)` byte string was seen before. If `recoveredAddr` was already seen but the raw signature bytes differ even slightly, the code falls through and adds the weight for that address **again**. Since ECDSA signing uses a random nonce `k`, a single private key can trivially generate arbitrarily many distinct, valid `(r, s)` signatures over the identical 32-byte hash — all recovering to the same address — so an attacker with one key can supply two (or more, up to `MAX_SIZE = 5`) distinct valid signatures from that one key and have the weight counted multiple times.

This is directly analogous to the GnuTLS bug: the routine does not verify/canonicalize the compared value (byte-for-byte signature equality) before using it to decide "is this the same authorization I already accepted," so distinguishable-but-equivalent inputs bypass the intended one-signer-once check.

By contrast, the codebase's own consensus-level multisig check, `TransactionCapsule.checkWeight`, was hardened against exactly this class of bug: post-fork it dedups by the *recovered address* (`encode58Check(address)`), not by raw signature bytes: [2](#0-1) 

The `ValidateMultiSign` precompile never received the equivalent fix, leaving the raw-byte comparison in `PrecompiledContracts.java`.

Also note `recoverAddrBySign` only inspects the first 65 bytes of the supplied signature and otherwise ignores the rest, further underscoring that trailing/varying bytes are not canonicalized before the equality check used for dedup: [3](#0-2) 

### Impact Explanation
Any Tron account can implement an active permission with a threshold requiring multiple distinct key-weights (e.g. `threshold = 2`, two keys each weight 1). `ValidateMultiSign` is the TVM primitive contracts use to verify that an m-of-n multisig authorization has been met on-chain (e.g. custody/DAO/exchange-style contracts). An attacker who controls only a single one of the required keys can call the precompile with two distinct valid signatures produced by that one key over the same hash, and `totalWeight` will be incremented twice, satisfying a threshold that should have required two independent signers. Any smart contract that relies on `ValidateMultiSign` to gate a privileged action (fund transfer, permission change, order execution, etc.) can be tricked into believing a multi-party authorization was met when it was produced by a single key — an unauthorized account operation / potential theft of funds gated by that contract's multisig logic.

### Likelihood Explanation
The bug is reachable by any unprivileged address: deploy or call a contract that invokes the `ValidateMultiSign` (0x66) precompile via `STATICCALL`/`CALL`, supplying a target address, permission id, message hash, and a small array (≤5) of signatures. No special privileges, witness/SR status, or network position are required — only a triggered smart-contract transaction and one private key associated with the target permission. Generating two distinct valid ECDSA signatures from one key over the same hash is trivial (standard non-deterministic ECDSA signing).

### Recommendation
Change the dedup logic in `ValidateMultiSign.execute()` to key exclusively on `recoveredAddr` (or its canonical encoded form), matching the pattern already used in `TransactionCapsule.checkWeight`: once an address has contributed weight, any further signature recovering to that same address must be skipped/rejected outright, regardless of whether the raw signature bytes match. Do not fall through to weight accumulation when `recoveredAddr` has already been seen.

### Proof of Concept
1. Deploy an account/contract that sets an `Active` permission on address `A` with threshold `2`, containing a single key `K` (owned by attacker) with weight `2`, or — to demonstrate the general dedup failure — a permission with a single key `K` weight `1` and threshold `1`, plus another unrelated key `K2` weight `1`, threshold `2` (attacker only controls `K`).
2. Attacker computes `hash = Sha256Hash.hash(merge(address, permissionId, data))` as done in the precompile.
3. Attacker signs `hash` twice with key `K`, using two independent nonces to get two different, both-valid, `(r, s)` pairs — trivial since Tron's ECDSA signing does not enforce RFC 6979 determinism.
4. Attacker builds an ABI call to `batchvalidatesign`/`validatemultisign(bytes32,bytes[],address[])`-style precompile input, `permissionId`, `data`, and `signatures = [sig1_from_K, sig2_from_K]`.
5. `ValidateMultiSign.execute()` recovers `recoveredAddr = address(K)` for both entries; because the merged `sign` bytes differ (different `r,s`), the `matrixContains(executedSignList, sign)` check fails to detect the duplicate, weight for `K` is added twice, `totalWeight` reaches the threshold that should require two independent signers, and the precompile returns success (`dataOne()`), even though only one private key participated.
