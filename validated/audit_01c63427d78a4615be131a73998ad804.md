### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles before size validation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts read an array-length word directly from attacker-supplied smart contract calldata and pass it to `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, which immediately allocate a `byte[][]` of that length, before the `MAX_SIZE` bound is enforced — mirroring the CVE-2023-0809 pattern of allocating memory from an untrusted size field prior to validating it.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` derive `len` from `words[offset].intValueSafe()` — a value fully controlled by the calldata of a TVM `CALL` to the precompile — and immediately do `new byte[len][]`: [1](#0-0) 

In `ValidateMultiSign.execute`, the `sigArraySize > MAX_SIZE` bound check is only performed when the `allowTvmSelfdestructRestriction()` feature switch is enabled; otherwise `extractBytesArray` is invoked unconditionally with the unbounded `len` before any size check exists: [2](#0-1) 

The same pattern exists in `BatchValidateSign.doExecute`, where `extractSigArray`/`extractBytesArray` and `extractBytes32Array` are only pre-checked with `sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE` under the same feature flag; the legacy branch calls `extractBytesArray`/`extractBytes32Array` first and only checks `cnt > MAX_SIZE` afterward: [3](#0-2) 

Since `intValueSafe()` can return values up to `Integer.MAX_VALUE`, a single crafted call can force an attempted allocation of a reference array with up to ~2^31 elements (many GB on a 64-bit JVM), well before the intended `MAX_SIZE` (5 or 16) bound is checked. This is the same bug class as CVE-2023-0809: allocating memory sized from an untrusted field before the message/request is validated.

### Impact Explanation
Both precompiles are reachable by any account issuing a `TriggerSmartContract` transaction (via `CALL`/`STATICCALL` to precompile addresses `0x9`/`0xa`), i.e. an unprivileged transaction broadcaster or contract caller. A crafted calldata blob can trigger an oversized array allocation attempt on the node executing/validating the transaction, producing `OutOfMemoryError` and consuming/fragmenting heap. `BatchValidateSign` additionally hands per-signature work to a shared, node-wide `ExecutorService` (`workers`), so a failure here can also destabilize concurrent TVM executions using that pool. Although the outer `catch (Throwable t)` in `BatchValidateSign.execute` (and the broad catches in `ValidateMultiSign`) swallow the resulting error, catching `OutOfMemoryError` is unsafe: by the time it is thrown, the JVM may have already reclaimed memory from unrelated threads, killed other in-flight work, or left shared native/other structures in an inconsistent state. Repeated invocation (e.g., broadcast by multiple accounts/transactions) can be used to degrade or crash a full node, which matches the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The vulnerable code path is only reachable when `VMConfig.allowTvmSelfdestructRestriction()` is not active for the network/chain in question (the legacy, pre-hardfork branch). Where that hard fork parameter has not been activated (e.g., private chains, some sidechains/test networks running this codebase, or historically prior to activation on mainnet), the size check never runs before allocation, and the exploit requires only a single crafted transaction with no special privileges, making likelihood high in that configuration. On networks where the feature has been activated, the guard mitigates this specific path.

### Recommendation
Move the `MAX_SIZE`/length-bound validation on the length word (`words[offset].intValueSafe()`) unconditionally, before calling `extractBytesArray`, `extractSigArray`, or `extractBytes32Array`, regardless of the `allowTvmSelfdestructRestriction()` flag state. Additionally, avoid catching `OutOfMemoryError` (or `Throwable` broadly) around user-triggerable code paths; catch specific checked/expected exceptions only, and let unrecoverable `Error`s propagate so the node can fail safely instead of continuing in a potentially corrupted state.

### Proof of Concept
Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign`) where the ABI array-length word for the `bytes[]`/`address[]` parameter is set to a very large value (e.g., `0x7fffffff`) while the remainder of the calldata is otherwise minimal/malformed so `allowTvmSelfdestructRestriction()`-gated pre-checks are bypassed (i.e., run on a chain/config where that parameter is `0`). Submit this as the `data` of a `TriggerSmartContract` call to precompile address `0x9` (or `0xa`). `doExecute`/`execute` will call `extractBytesArray`/`extractBytes32Array`, which executes `new byte[0x7fffffff][]`, attempting a multi-gigabyte allocation before any `MAX_SIZE` check occurs, as shown in the code at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1162-1181` and `:390-412`.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
