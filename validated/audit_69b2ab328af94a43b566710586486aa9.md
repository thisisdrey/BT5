### Title
Archive cache key collision via unescaped delimiter joining allows cross-request archive content confusion - (File: internal/gitaly/service/repository/archive.go)

### Summary
`GetArchive` derives its `streamcache` key from `createArchiveCacheKey`, which concatenates the project path, the `git archive` positional args, and the pathspecs using `strings.Join(..., ",")` with no length-prefixing or escaping between the joined segments. Because the RPC's `CommitId`, `Path`, and `Exclude` fields are only checked for control characters (no comma restriction), an ordinary user can craft values whose comma placement shifts across the `args`/`pathspecs` boundary while producing an identical byte stream fed into the SHA-256 hash. This is the same bug class as the `abi.encodePacked()` array-boundary confusion in the reference report: fields that should be distinguishable collapse to the same hash, letting a request "impersonate" another request's cache entry.

### Finding Description
`createArchiveCacheKey` is: [1](#0-0) 

`args` and `pathspecs` are built directly from attacker-controlled `GetArchiveRequest` fields (`CommitId`, `Path`, `Exclude`), validated only by `git.ValidateRevision` (which forbids leading `-`, NUL, whitespace, `:` and `\`, but **not commas**) and `storage.ValidateRelativePath` (which only prevents path escape, not commas): [2](#0-1) [3](#0-2) 

Because `strings.Join` places a plain `,` between elements with no length prefix, two different `(args, pathspecs)` pairs can serialize to the identical byte sequence once concatenated (e.g., `args=["X"], pathspecs=["Y,Z"]` yields the same hash input as `args=["XY,"], pathspecs=["Z"]`). Git ref names may legally contain commas, so a pusher/forker with ordinary write access can create a branch/tag whose name is chosen to realize this collision, then invoke `GetArchive` with a `CommitId`/`Path`/`Exclude` combination engineered to collide with another (past or future) legitimate `GetArchive` request for the same project.

The resulting cache key is passed straight into `s.archiveCache.Fetch`, which serves cached bytes on key match without re-verifying which logical commit/path/excludes produced them: [4](#0-3) 

This mirrors the report's root cause: a hash computed by unescaped concatenation of variable-length, attacker-influenced fields, allowing distinct logical inputs to be treated as equivalent by downstream logic that trusts the hash as identity.

### Impact Explanation
A successful collision causes the streaming archive cache to serve the wrong archive content for a `GetArchive` RPC: a user requesting an archive of commit/path A can receive cached bytes that were actually produced for a different commit/path/exclude combination B (or vice versa), within the same GitLab project. This is an integrity/disclosure issue — content from a different revision or directory tree than the one actually authorized/requested can be returned, and an attacker who can pre-populate the cache (by crafting the colliding request first) can effectively substitute their own chosen archive payload for a victim's subsequent request to the same colliding key. Severity is bounded by the requirement that both requests are scoped to the same `GlProjectPath` and that the collision-crafting party needs a git ref with an attacker-chosen comma-containing name in that project, but it does not require any privileged actor, leaked credential, or MITM — an ordinary contributor with push access is sufficient.

### Likelihood Explanation
Exploitability requires: (1) the ability to push/create a branch or tag with a comma in its name in the target project (a normal, unprivileged git operation — commas are valid in git ref names), and (2) crafting `CommitId`/`Path`/`Exclude` values around that ref to realize the hash collision. Both are reachable purely through the `GetArchive` RPC's user-supplied fields and standard git push, with no reliance on chain re-orgs, malicious peers, or timing races beyond normal cache population — making this a realistic, low-complexity condition for an internal/authenticated GitLab user.

### Recommendation
Do not build the cache key by concatenating `strings.Join`-ed, unescaped, variable-length fields. Instead, hash each field independently with an explicit length prefix (as already done elsewhere in the codebase, e.g. `prefixLen` in `internal/cache/keyer.go`) or hash a length-delimited/structured encoding (e.g., write `len(field)` then `field` for every element of `args` and `pathspecs`, or use a proto-marshaled struct) so that no two distinct `(gitLabProjectPath, args, pathspecs)` tuples can produce the same hash input. [5](#0-4) 

### Proof of Concept
1. As an ordinary project member with push access, create a branch named `XY,` (a syntactically valid git ref name).
2. Issue `GetArchive` with `CommitId="X"`, `ElidePath=false`, `Path="Y,Z"` (assuming `Y,Z` resolves to a valid tree path at revision `X`) — this populates the cache under key `H(gitLabProjectPath || "X" || "Y,Z")`.
3. Issue a second `GetArchive` with `CommitId="XY,"`, `ElidePath=false`, `Path="Z"` (valid tree path at ref `XY,`) — `createArchiveCacheKey` computes `H(gitLabProjectPath || "XY," || "Z")`, which hashes the identical byte stream `gitLabProjectPath || "XY,Z"` as step 2, colliding with the entry from step 1.
4. The second request receives the cached archive bytes generated for the first request's commit/path instead of executing `git archive` against `XY,`/`Z`, demonstrating cross-request content substitution driven purely by RPC-field crafting.

func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}

// prefixLen reduces the risk of collisions due to different combinations of
// concatenated strings producing the same content.
// e.g. f+oobar and foo+bar concatenate to the same thing: foobar
func prefixLen(s string) []byte {
	return []byte(fmt.Sprintf("%08x%s", len(s), s))
}
