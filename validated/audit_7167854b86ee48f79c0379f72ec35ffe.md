### Title
Quarantine snapshot-restoration path trusts a client-supplied `relative-path-bin` header and repository `GitObjectDirectory` field to redirect an accessor RPC to an arbitrary relative path without validation - (File: `internal/gitaly/storage/storagemgr/middleware.go`)

### Summary
`beginTransactionForRepository` special-cases any repository-scoped RPC whose target `Repository` message has a non-empty `GitObjectDirectory`/`GitAlternateObjectDirectories` field: it assumes, purely from that field being set, that "the request is looping back from Rails' access checks" and therefore skips the normal transactional path (including `locator.ValidateRepository`), instead calling `restoreSnapshotRelativePath`, which blindly overwrites `targetRepo.RelativePath` with whatever value is present in the `relative-path-bin` gRPC metadata header. ### Finding Description
The comment in the code explicitly documents the trust assumption: [2](#0-1) 

and `restoreSnapshotRelativePath` implements it: [3](#0-2) 

The only two "authorization" signals that this code relies on are:
1. That `Repository.GitObjectDirectory` / `GitAlternateObjectDirectories` are non-empty — but these are plain, client-settable proto fields with no cryptographic binding to an actual quarantine/transaction; any gRPC caller of Gitaly can populate them on a normal accessor request (e.g. `FindCommit`, `GetBlob`, `ListAllCommits`, etc., all of which are repository-scoped accessors).
2. The `relative-path-bin` metadata key (`MetadataKeySnapshotRelativePath`) — this is ordinary incoming gRPC metadata, not an authenticated/signed value; nothing in this function validates that it correlates to any real snapshot or transaction the caller is entitled to.

Once both conditions are met, `rewritableRequest` clones the request, and `restoreSnapshotRelativePath` overwrites `targetRepo.RelativePath` with the metadata value while leaving `targetRepo.StorageName` unchanged. The rewritten request is then dispatched via `nonTransactionalRequest`, i.e. it bypasses:
- `locator.ValidateRepository` (line 303), which normally checks the relative path for validity/traversal and repository existence conditions,
- the normal partition/transaction `Begin()` call and its snapshot isolation guarantees.

This is architecturally the same class of bug as the reported Tapioca H‑01: a privileged/trusted flow (Rails re-invoking Gitaly during access checks with a quarantine snapshot) is impersonated by supplying the same "marker" fields that the trusted flow would use, without any check that the caller is actually the trusted intermediary or that the supplied identifier (relative path) matches the caller's own transaction/repository context.

### Impact Explanation
An attacker who can reach Gitaly's gRPC surface with a valid repository-scoped accessor request (which is the same level of access any of the RPCs already require) can craft a request that:
- Sets a non-empty `GitObjectDirectory` on the target `Repository` (any placeholder string works, since it is never validated after this),
- Attaches a `relative-path-bin` metadata value pointing at an arbitrary relative path within the same storage.

The RPC handler then executes reads (e.g. blob/commit/tree data) against that attacker-chosen relative path, entirely skipping `ValidateRepository` and the transactional/partition machinery that normally enforces the mapping between authenticated caller and target repository. This is a cross-repository object access / storage-path escape: it lets a caller read the contents of an arbitrary repository on the same storage that they know or can guess the relative path for, without going through the normal transactional and validation guarantees the rest of the system relies on.

### Likelihood Explanation
This does not require compromising Rails, gitlab-shell, or any privileged process — it only requires the ability to issue a Gitaly RPC with a crafted `Repository` message and metadata, which any caller that already reaches Gitaly directly (e.g., through a poorly-isolated internal network boundary or a caller reusing a shared auth token) can do. The trigger condition (`GetGitObjectDirectory() != "" || len(GetGitAlternateObjectDirectories()) > 0`) is a purely client-controlled proto field with no server-side attestation, making the "is this really a Rails access-check loop-back" assumption trivially forgeable.

### Recommendation
Do not infer that a request is Rails' quarantine loop-back purely from the presence of `GitObjectDirectory`/`GitAlternateObjectDirectories` on the request or from an unauthenticated `relative-path-bin` header. Instead, bind the quarantine/snapshot relative path to the actual transaction/session that produced it (e.g., via a signed/opaque token tied to the specific transaction ID rather than a raw path string), and validate that the resolved relative path actually belongs to a snapshot associated with an active transaction for the given repository before skipping `ValidateRepository` and the normal transactional path.

### Proof of Concept
1. As a client with access to any repository-scoped accessor RPC (e.g. `FindCommit`), build a `Repository` message for the target request with `StorageName` set to a storage the caller has some access to, and `GitObjectDirectory` set to any non-empty placeholder value.
2. Attach gRPC metadata `relative-path-bin: <relative-path-of-a-different-repository-on-the-same-storage>`.
3. Send the RPC. In `beginTransactionForRepository`, the non-empty `GitObjectDirectory` check is satisfied, so `restoreSnapshotRelativePath` is invoked, which overwrites the request's `RelativePath` with the value taken from step 2's metadata and returns a `nonTransactionalRequest` — bypassing `locator.ValidateRepository` and normal transaction/partition lookup — and the handler proceeds to read data from the attacker-chosen repository path. func beginTransactionForRepository(ctx context.Context, logger log.Logger, txRegistry *TransactionRegistry, node storage.Node, locator storage.Locator, methodInfo protoregistry.MethodInfo, req proto.Message) (_ transactionalizedRequest, returnedErr error) {
	targetRepo, err := methodInfo.TargetRepo(req)
	if err != nil {
		if errors.Is(err, protoregistry.ErrRepositoryFieldNotFound) {
			// The above error is returned when the repository field is not set in the request.
			// Return instead the error many tests are asserting to be returned from the handlers.
			return transactionalizedRequest{}, structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet)
		}

		return transactionalizedRequest{}, fmt.Errorf("extract target repository: %w", err)
	}

	if targetRepo.GetGitObjectDirectory() != "" || len(targetRepo.GetGitAlternateObjectDirectories()) > 0 {
		// The object directories should only be configured on a repository coming from a request that
		// was already configured with a quarantine directory and is being looped back to Gitaly from Rails'
		// authorization checks. If that's the case, the request should already be running in scope of a
		// transaction and the repository rewritten to point to the snapshot repository. We thus don't start
		// a new transaction if we encounter this.
		//
		// This property is violated in tests which manually configure the object directory or the alternate
		// object directory. This allows for circumventing the transaction management by configuring the either
		// of the object directories. We'll leave this unaddressed for now and later address this by removing
		// the options to configure object directories and alternates in a request.

		if methodInfo.Operation == protoregistry.OpMutator {
			// Accessor requests may come with quarantine configured from Rails' access checks. Since the
			// RPC that triggered these access checks would already run in a transaction and target a
			// snapshot, we won't start another one. Mutators however are rejected to prevent writes
			// unintentionally targeting the main repository.
			return transactionalizedRequest{}, ErrQuarantineConfiguredOnMutator
		}

		rewrittenReq, err := restoreSnapshotRelativePath(ctx, methodInfo, req)
		if err != nil {
			return transactionalizedRequest{}, fmt.Errorf("restore snapshot relative path: %w", err)
		}

		return nonTransactionalRequest(ctx, rewrittenReq), nil
	}

func restoreSnapshotRelativePath(ctx context.Context, methodInfo protoregistry.MethodInfo, req proto.Message) (proto.Message, error) {
	// Rails sends RPCs from its access checks with quarantine applied. The quarantine paths are relative to the
	// snapshot repository of the original transaction. While the relative path of the request is the original relative
	// path of the repository before snapshotting, Rails sends the snapshot repository's path in a header. For the
	// quarantine paths to apply correctly, we must thus rewrite the request to point to the snapshot repository here.
	snapshotRelativePath := metadata.GetValue(ctx, MetadataKeySnapshotRelativePath)
	if snapshotRelativePath == "" {
		return nil, ErrQuarantineWithoutSnapshotRelativePath
	}

	rewrittenReq, targetRepo, err := rewritableRequest(methodInfo, req)
	if err != nil {
		return nil, fmt.Errorf("rewritable request: %w", err)
	}

	targetRepo.RelativePath = snapshotRelativePath

	return rewrittenReq, nil
}
