### Title
Missing bounds validation in `InputZipFile::ProcessCentralDirEntry` allows heap OOB read on malformed ZIP central directory - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` parses ZIP archives directly out of an `mmap`'d input buffer. The local-file-header parser (`ProcessLocalFileEntry`) calls `EnsureRemaining()` before every field read to make sure the cursor `p` never advances past the end of the mapped file. `InputZipFile::ProcessCentralDirEntry` — the function that walks the *central directory* to discover each entry's compressed/uncompressed size, filename, and extra-field length — never calls `EnsureRemaining()` at all.

### Finding Description
`ProcessCentralDirEntry` (`third_party/ijar/zip.cc:493-545`) blindly advances its cursor and dereferences memory based on attacker-controlled length fields read straight from the archive bytes: [1](#0-0) 

- `file_name_length`, `extra_field_length`, and `file_comment_length` are read as raw `u2` values from the archive with no check against the number of bytes actually remaining in the mapped file (`input_file_->Length()`).
- The subsequent `memcpy(filename, p, len)` at line 520 copies up to `file_name_length` bytes from `p`, which may already point past the end of the mapping if the CDH claims a name longer than the remaining file content.
- The extra-field walk (`while (extra_p != p)`) then reads `header_id`/`data_size` u2 values and, for a `ZIP64_EXTRA_FIELD_TAG`, an 8-byte `get_u8le(extra)` — all unguarded by any remaining-length check, unlike the equivalent local-header extra-field logic that is bounds-checked via `EnsureRemaining`.

This mirrors the reported TensorFlow bug class exactly: a size/length field taken from untrusted structured input (there: `sequence_length`/labels shapes; here: ZIP `file_name_length`/`extra_field_length`) is used directly to index/copy memory without validating it against the actual available buffer size, producing an out-of-bounds heap read (CWE-125) rooted in incomplete input validation (CWE-665).

`EnsureRemaining` exists precisely for this purpose and is used everywhere else in the same file (`ProcessLocalFileEntry`, `SkipFile`, `ProcessFile`, `ProcessNext`) — its absence in `ProcessCentralDirEntry` is an inconsistency, not an intentional design choice: [2](#0-1) [3](#0-2) 

### Impact Explanation
An attacker who controls the bytes of a ZIP/JAR file that Bazel's `ijar`/`zipper` C++ tooling parses (`third_party/ijar/zip.cc`, invoked via `ZipExtractor::Create` in `third_party/ijar/zip_main.cc` and `third_party/ijar/ijar.cc`) can craft a central directory with `file_name_length`, `extra_field_length`, or `file_comment_length` values that exceed the true remaining bytes in the mapped file. This causes an out-of-bounds read from the process's heap/mmap region — the copied filename bytes or extra-field values can leak adjacent heap memory into filenames/attributes that end up in build outputs, and in the worst case the OOB read crosses an unmapped page boundary and crashes the tool (info disclosure / crash), matching the CVE-2021-29613 impact class (CWE-125 OOB read, CWE-665 incomplete initialization/validation).

### Likelihood Explanation
Reaching this code path requires that Bazel's `ijar`/`zipper` binary actually parse a ZIP file whose bytes were supplied by the attacker (e.g., a maliciously crafted `.jar`/`.zip` dependency artifact). Whether this is reachable from a fully unprivileged, checksum-verified `http_archive`/`http_jar` fetch is not fully confirmed here — I was not able to trace, within the available context, whether `third_party/ijar/zip.cc` (as opposed to the Java-side archive-extraction code used by `repository_ctx.download_and_extract`) is invoked on downloaded repository archives before or independent of SHA-256/integrity verification, or whether it is only exercised on build-time-generated jars (interface-jar generation, `singlejar`/`zipper` actions) whose inputs are typically already-verified build outputs. If a checksum/integrity attribute is declared and enforced on the whole archive prior to any parsing, this bug would not constitute an integrity bypass under the stated rules; it would only be reachable when no checksum is pinned (already a documented risk) or when the malformed file is a compilation dependency (e.g., a third-party jar) fed into `ijar` for interface-jar stripping.

### Recommendation
Add `EnsureRemaining()` checks in `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, `file_comment_length` bytes and before each extra-field sub-record read (mirroring the checks already present in `ProcessLocalFileEntry`), returning an error instead of advancing the cursor past the end of the mapped file.

### Proof of Concept
Not fully verified end-to-end in this environment (no test harness run). Conceptually: construct a ZIP file whose EOCD/central-directory record is truncated such that a CDH entry near the end of the file declares `file_name_length` (or `extra_field_length`) larger than the number of bytes actually remaining before EOF, then run it through the `ijar`/`zipper` binary (`third_party/ijar/zip_main.cc`) — `ProcessCentralDirEntry`'s unguarded `memcpy`/`get_u2le`/`get_u8le` calls will read past the mmap'd buffer. A `src/test/shell` or C++ unit test analogous to `src/tools/singlejar/output_jar_simple_test.cc`'s `MalformedExtraField` test (which does bounds-check the analogous singlejar path) would need to be authored against `third_party/ijar/zip.cc` to reproduce this deterministically — this was not executed here.

  // Check that at least n bytes remain in the input file, otherwise
  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }
