### Title
Market maker orders can be fully filled with zero payment due to missing zero-output check in the "taker == maker" match branch - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` mirrors the audited pattern of trusting a computed "received amount" without verifying it is greater than zero before finalizing a transfer. In the branch where the taker's remaining demand exactly equals the maker's remaining supply, the code computes `makerBuyTokenQuantityReceive` via integer division and unconditionally closes the maker's order and credits the taker — with no check that the maker actually received a non-zero payment, unlike the sibling "taker > maker" branch which explicitly guards against this case.

### Finding Description
In `matchSingleOrder`, three branches decide how a taker order is matched against a maker order: [1](#0-0) 

In the "taker == maker" branch, `makerBuyTokenQuantityReceive` is computed by `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, a floor-division operation that can legitimately round down to `0` for small remaining quantities and disproportionate original ratios. Immediately after, `makerOrderCapsule.setSellTokenQuantityRemain(0)` closes out the maker's remaining tokens and the order is marked `INACTIVE`: [2](#0-1) 

The trade is then unconditionally settled — the taker receives `takerBuyTokenQuantityReceive` (the maker's full remaining sell quantity, captured *before* it is zeroed at line 434) while the maker is credited only `makerBuyTokenQuantityReceive`, which can be `0`: [3](#0-2) 

Contrast this with the "taker > maker" branch, which computes the same quantity via the same `multiplyAndDivide` helper but explicitly checks for a zero result and aborts the match (returning the maker's remaining tokens instead of giving them away) before any balances are updated: [4](#0-3) 

The "taker == maker" branch has no equivalent guard, so it is possible for a maker's already-escrowed sell-side tokens (deducted from their balance at order creation via `transferBalanceOrToken`) to be fully consumed and handed to the taker while the maker is credited zero buy-side tokens — the exact same class of bug as the reported issue: a value-received check (`> 0`) is missing before the system treats an exchange/transfer as final and successful.

### Impact Explanation
This results in an on-chain, unauthorized transfer of value: the maker's tokens are permanently transferred to the taker for free, and the maker's order is silently closed as if fully and fairly executed. This is a direct loss of user funds (permanent freezing/theft of the maker's escrowed asset) reachable by any unprivileged account that places a `MarketSellAssetContract` order that happens to land on the exact-match branch against a maker order whose remaining ratio floors to zero.

### Likelihood Explanation
Triggering the exact-match branch requires a taker's remaining buy-demand to exactly equal a maker's remaining sell-supply (a common occurrence as orders get partially filled down to a small remainder) combined with a maker order whose sell/buy ratio is large enough that `remain * buyQuantity / sellQuantity` floors to zero. Both conditions are achievable by a market participant crafting orders with a large price ratio and orchestrating fills to leave a small remainder, making this practically exploitable rather than purely theoretical.

### Recommendation
Add the same zero-result guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, abort settlement of that match (return the maker's remaining sell tokens instead of transferring them to the taker) rather than unconditionally zeroing the maker's remaining balance and crediting the taker.

### Proof of Concept
1. Maker creates a sell order: `sellTokenQuantity = 1,000,000` (token A), `buyTokenQuantity = 1` (token B).
2. Through prior partial fills, `makerOrderCapsule.getSellTokenQuantityRemain()` is reduced down to `1` (1 unit of token A remaining), while `makerSellQuantity`/`makerBuyQuantity` (the original order ratio, 1,000,000:1) remain unchanged.
3. A taker submits a `MarketSellAssetContract` selling token B for token A such that `takerBuyTokenQuantityRemain` (computed via `MarketUtils.multiplyAndDivide`) equals exactly `1`, matching the maker's remaining quantity and entering the "taker == maker" branch in `matchSingleOrder`.
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 1, 1_000_000) = 0` (floor division).
5. `makerOrderCapsule.setSellTokenQuantityRemain(0)` closes the maker's order; `addTrxOrToken(makerOrderCapsule, 0)` credits the maker nothing, while `addTrxOrToken(takerOrderCapsule, 1, takerAccountCapsule)` gives the taker the full 1 unit of token A that was reserved from the maker's balance at order placement — the maker's token is transferred for free with no compensation.
