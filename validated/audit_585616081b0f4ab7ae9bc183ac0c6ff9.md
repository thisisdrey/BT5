### Title
Unprivileged attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER` via dust transfers, permanently blocking new collateral/debt positions and rescues - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks per-account deposit and debt tokens in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30`. Entries are added whenever a `DepositToken` or `DebtToken` balance goes `0 -> nonzero`, with no consent from the recipient. Since both tokens are freely transferable (and `DebtToken` balances can even be attributed via `issue`/`flashIssue`-style flows on behalf), an unprivileged attacker can push 1 wei of every whitelisted deposit token to a victim, filling their list and making `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`. Because `DepositToken._revertIfLocked` blocks transfers of locked collateral, a leveraged victim cannot remove the dust entries, so the block can be permanent for that account until their debt is gone.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` revert once `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` (`UserReachedMaxTokens`) at `Pool.sol:143-148, 204-220`. [1](#0-0) 
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is 0, regardless of amount — 1 wei suffices — at `DepositToken.sol:517-520`. [2](#0-1) 
- Removal only happens when the balance returns to exactly 0 (`DepositToken.sol:522-525`), and `transfer`/`transferFrom`/`withdraw` are gated by `_revertIfLocked`, so a victim whose position is at (or pushed to) maximum utilization cannot shed the dust tokens (`DepositToken.sol:348-353, 383-398`). [3](#0-2) 
- Attack path: attacker calls `DepositToken.deposit(1 wei…)` or obtains msdTokens, then `depositTokenX.transfer(victim, 1)` for every registered deposit token (up to the pool's deposit-token cap). Each transfer adds an entry to the victim's list. The same applies to debt tokens minted to a victim-adjacent flow. Once the count reaches 30:
  - `DepositToken.deposit`/`_mint` to the victim reverts for any collateral type they don't already hold (`DepositToken.sol:485-488`), so the victim cannot add new collateral to restore health.
  - `Pool.liquidate`'s `depositToken_.seize(account_, _msgSender, _toLiquidator)` performs `_transfer` to the liquidator; if the liquidator (or the SmartFarmingManager contract when it is the seized-funds recipient) has a full list for a token it never held, liquidation reverts, blocking liquidation of unhealthy positions — a liveness break of the liquidation path (`Pool.sol:589`, `DepositToken.sol:343-345`). [4](#0-3) 
  - `DebtToken.issue`/leverage to a fresh synthetic reverts for the victim once the list is full, blocking refinancing.

### Impact Explanation
Temporary-to-permanent freezing of position management: a victim at high utilization cannot deposit new collateral types nor mint new debt types, and cannot remove the dust entries because `_revertIfLocked` treats their balances as locked. A near-liquidatable victim is denied the ability to de-risk, leading to forced liquidation. Additionally, liquidators whose account list is force-filled cannot receive seized collateral of a new token type, so `Pool.liquidate` reverts and bad debt can accrue — a protocol-liveness/insolvency concern analogous to the availability impact of CVE-2021-2060.

### Likelihood Explanation
Fully unprivileged: only requires dust amounts of whitelisted deposit tokens and ordinary `transfer` calls (or transfers to known liquidator addresses). Cost scales with the number of registered deposit tokens; entries persist indefinitely while the victim is locked. No privileged role, oracle manipulation, or governance action is needed. The main limitation is that damage is per-account and the victim can escape if they have enough unlocked balance to transfer the dust out, or after repaying all debt.

### Recommendation
- Count only economically meaningful positions toward `MAX_TOKENS_PER_USER` (e.g., require a minimum balance/dust threshold before adding to the list), or
- Exclude seized/liquidation transfers from the cap (let `seize` bypass `onlyIfAdditionWillNotReachMaxTokens`), or
- Allow accounts to explicitly remove a token entry via a `Pool.removeFromDepositTokensOfAccount` path callable by the account itself when the balance is below a dust threshold.

### Proof of Concept
Hardhat sketch:

```ts
// setup: pool with N deposit tokens registered, victim deposits collateral
// and borrows up to ~max utilization so balances are locked.

for (const dt of depositTokens) {
  if (dt === victimToken) continue;
  await underlying.connect(attacker).approve(treasuryOrDt, DUST);
  await dt.connect(attacker).deposit(DUST, attacker.address);     // or acquire via transfer
  await dt.connect(attacker).transfer(victim.address, 1);         // adds entry, balance 0 -> 1
}

// victim list now == MAX_TOKENS_PER_USER (30)
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// victim cannot deposit a new collateral type
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// if locked, victim cannot shed dust
await expect(dustToken.connect(victim).transfer(attacker.address, 1))
  .revertedWithCustomError(dustToken, 'NotEnoughFreeBalance');

// oracle price drops -> victim unhealthy; liquidator whose list was also filled
// (or victim needing new collateral) -> liquidate reverts on seize's
// addToDepositTokensOfAccount for a first-time token.
```
