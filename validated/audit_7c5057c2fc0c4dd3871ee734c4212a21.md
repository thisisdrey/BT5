### Title
Attacker can permanently DoS a victim's position management by filling their account token lists to `MAX_TOKENS_PER_USER` via dust deposits/transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks per-account deposit tokens and debt tokens in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30`. Any action that would add a new token to a victim's combined list reverts with `UserReachedMaxTokens` once the cap is hit. Because `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and `_transfer`/`_mint` unconditionally add the token to the *recipient's* list, an unprivileged attacker can force-add entries to any victim's list with dust, permanently (until governance removes a token) preventing the victim from depositing new collateral types, receiving deposit tokens, or minting new synthetic debt.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` [1](#0-0) .
- `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_`, and `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was 0 [2](#0-1) .
- `DepositToken._transfer` does the same on plain `transfer`/`transferFrom` — a 1-wei dust transfer to the victim adds the token to their list [3](#0-2) .
- Removal only happens when the victim's balance of that token returns to 0 (`_burn`/`_transfer` sender side) [4](#0-3) . The victim *can* clear entries by transferring the dust back out, but each new forced token requires a separate cleanup tx the attacker can re-grief cheaply and repeatedly (front-running/griefing loop).

Attack path (unprivileged EOA):
1. Attacker deposits dust of every registered deposit token via `deposit(1, victim)` (or transfers dust they already hold), filling `depositTokensOfAccount[victim]` up to the shared cap of 30 combined with the victim's debt tokens.
2. Any subsequent `deposit(...)` on a *new* deposit token, mint of a new synth (`DebtToken.issue` → `addToDebtTokensOfAccount`), receipt of a deposit-token transfer, or liquidation seize that would add a new entry reverts with `UserReachedMaxTokens`.
3. Re-grief: whenever the victim burns/transfer-outs an entry to free a slot, the attacker re-adds it for ~1 wei plus gas.

### Impact Explanation
Denial of service of the victim's protocol usage, matching the CVE's availability-impact class. The victim cannot open positions in new collateral types, cannot mint new synthetic assets (a new `DebtToken` entry cannot be added), and cannot receive deposit tokens (e.g., payments, liquidation proceeds routed to them, or treasury-less transfers). For a victim with no existing position this is a complete blocking of the protocol; for an active borrower it blocks corrective actions like depositing a *different* collateral type to restore health — leaving them exposed to liquidation while their remediation path reverts. The grief is cheap (dust amounts, recoverable), repeatable, and needs no privileged role.

### Likelihood Explanation
Requires the pool to have enough registered tokens (or the attack to combine forced deposit-token entries with the victim's existing debt/deposit entries) to reach 30. Each forced entry costs the attacker only a dust deposit/transfer; the victim must spend a transaction per slot to clear it, and the attacker can refill slots in the same block the victim frees them. No privileged access, oracle manipulation, or governance action is needed — `deposit`'s `onBehalfOf_` parameter and unrestricted `transfer` are public entry points with no `whenNotPaused` gap that stops the grief.

### Recommendation
- Do not count unsolicited dust toward the cap: e.g., require a minimum amount, or only register a deposit token in the account list on explicit `deposit` by the account itself (use `_msgSender()` as beneficiary or let `onBehalfOf_` opt-in), and skip list-add on plain ERC20 `transfer`/`transferFrom` (lazily compute collateral contribution instead of relying on the enumerable list).
- Alternatively, make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` not revert at cap but let `debtPositionOf`/`depositOf` tolerate it, or allow the victim to clear arbitrary entries via a `removeMyToken`-style function.

### Proof of Concept
Hardhat sketch (extends the existing `Pool.test.ts` fixture):

```ts
it('griefs victim by filling account token list', async function () {
  // attacker holds/registers all pool deposit tokens
  const depositTokens = await pool.getDepositTokens() // N registered deposit tokens
  const debtTokens = await pool.getDebtTokens()

  // victim already uses k tokens; attacker tops victim up to MAX (30)
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber()
  for (const dt of depositTokens) {
    await depositTokenOf[dt].connect(attacker).deposit(1, victim.address) // dust onBehalfOf victim
    // or: depositTokenOf[dt].connect(attacker).transfer(victim.address, 1)
  }
  // fill remaining slots with additional registered tokens until:
  expect((await pool.getDepositTokensOfAccount(victim.address)).length +
         (await pool.getDebtTokensOfAccount(victim.address)).length).eq(max)

  // victim can no longer mint a new synth (adds new debt token entry)
  await expect(
    otherDebtToken.connect(victim).issue(parseEther('1'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // victim cannot deposit into a collateral type they didn't already hold
  await expect(
    newDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // even a plain inbound transfer of a new deposit token reverts
  await expect(
    newDepositToken.connect(attacker).transfer(victim.address, 1)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Note: reproducibility on a given fork depends on the deployed pool's registered token count; if `depositTokens + debtTokens < 30` the attacker can only partially fill the list, so the finding is strongest where the victim already occupies several slots (typical levered/multi-collateral users) or where the pool supports many collaterals. If a concrete deployment shows fewer than ~30 total tokens and victims average few slots, this degrades to a weaker partial DoS; otherwise it is a clean unprivileged availability analog of the CVE class.
