Based on my investigation, the strongest local analog is a "no fallback / no floor guard" defect in Snowbridge's outbound fee pricing pipeline, which mirrors the oracle report's core flaw: a single, unchecked conversion path with no safety floor that can silently produce economically broken output (zero fee) instead of failing safe, leading to under-priced public work that can stall bridge relaying.

### Title
Snowbridge outbound-queue fee calculation can silently round the relayer's remote fee to zero, causing under-priced message delivery - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`Pallet::<T>::calculate_fee` in the Snowbridge outbound-queue pallet converts the ETH-denominated relayer cost into the local currency via a `FixedU128` division by `params.exchange_rate` and a subsequent integer division to adjust decimals, with no minimum-fee floor or fallback safeguard. [1](#0-0)  The pallet's own test suite demonstrates that, even with strictly non-zero, `validate()`-approved pricing parameters, the computed `remote` fee can come out as exactly zero due to precision loss in the division chain. [2](#0-1) 

### Finding Description
`calculate_fee` computes `RemoteFee = gas_used_at_most * fee_per_gas + reward`, then does `FixedU128::from_inner(fee).saturating_mul(multiplier).checked_div(&exchange_rate)`, followed by `convert_from_ether_decimals`, which itself performs `value.checked_div(denom)` where `denom = 10^(ETHER_DECIMALS - T::Decimals)`. [3](#0-2) 

There is no lower-bound check anywhere in this chain analogous to a "fallback" that would reject or re-price a message whose computed fee underflows to zero. `PricingParameters::validate()` only guards against parameters that are exactly zero at the time governance sets them; it does not — and cannot — guard against the interaction between a specific command's `gas_used_at_most` and the fixed-point arithmetic producing a zero result after downcasting and decimal conversion. [4](#0-3) 

The pallet's own unit test confirms this: with `exchange_rate = 1/1`, `fee_per_gas = 1`, `reward = 1`, `multiplier = 1/1` — all valid, non-zero parameters — `OutboundQueue::calculate_fee` returns `fee.remote == 0`, and the test comment explicitly states "the remote fee calculated here is invalid which should be avoided." [5](#0-4) 

This fee is charged upfront in `do_process_message` before the message is committed and forwarded toward Ethereum: `pricing_params.rewards.remote`/`max_fee_per_gas` are baked into the `CommittedMessage` that is queued for relaying. [6](#0-5)  If the fee computed and actually collected from the sender is zero (or negligible) for the remote leg, the relayer who eventually delivers the message to the Ethereum Gateway is not compensated for the real gas cost — the protocol has no fallback pricing mechanism (e.g., a minimum fee floor, alternate on-chain rate source, or re-quote) to guarantee delivery remains economically viable, exactly the missing-fallback pattern described in the source report for Chainlink price feeds.

### Impact Explanation
Under the "public underpriced work that degrades block production or stalls bridge processing" impact category: if the fee computation systematically returns zero or near-zero remote fees for certain message/gas-cost combinations, unprivileged users can queue Snowbridge outbound messages that are effectively free to send but costly to relay. This can lead relayers to stop servicing the outbound queue, causing `MessageLeaves`/`Messages` to accumulate without being picked up, stalling the outbound message pipeline to Ethereum and freezing user funds/commands in transit.

### Likelihood Explanation
The precision-loss condition is deterministic arithmetic (not a race condition or malicious actor requirement) and is already reproduced by the pallet's own regression test, confirming it is reachable with legitimate, validated pricing parameters and standard message gas costs — no admin misbehavior, malicious relayer, or compromised prover is needed to trigger it.

### Recommendation
Add an explicit floor check after computing the remote/local fee components in `calculate_fee` (and in `convert_from_ether_decimals`) that rejects or bumps the fee to a governance-configured minimum whenever the computed value would round to zero, instead of silently returning `Fee { remote: 0, .. }`. Consider rounding up (ceiling division) rather than truncating in the `checked_div` calls so relayer compensation is never systematically underpriced.

### Proof of Concept
The existing test in the repository already demonstrates the flaw end-to-end: [2](#0-1) 
1. Set valid `PricingParameters` (`exchange_rate=1`, `fee_per_gas=1`, `reward=1`, `multiplier=1`) via `set_pricing_parameters` — passes `validate()`.
2. Call `OutboundQueue::calculate_fee(gas_used, price_params)`.
3. Observe `fee.remote == 0` while `fee.local` is non-zero — the sender pays only the local fee and nothing that compensates the relayer for the Ethereum-side execution, with no code path forcing a fallback/minimum charge.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}
