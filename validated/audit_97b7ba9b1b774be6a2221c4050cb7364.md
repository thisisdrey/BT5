### Title
Unsolicited StackerDB push-chunk handler advertises a slot version in its `StackerDBChunkInv` reply before the chunk is actually persisted - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an incoming `StackerDBPushChunkData` and then immediately patches the outgoing `StackerDBChunkInv` reply's `slot_versions` entry to the *new* chunk's version, before the chunk itself has been written to the StackerDB replica. Actual persistence only happens later when the message is forwarded to the relayer for processing. This is structurally the same "record the post-action value before the action is durably committed" ordering bug as the report's oracle update: the inventory (the "observation") is updated to reflect a state that has not yet been made canonical.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`, `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 

The flow is:
1. `validate_received_chunk` checks size, signer signature, freshness (`slot_version` vs `expected_version`), and max-writes — but this only validates that the chunk *would be* acceptable; it never writes the chunk to the `StackerDBs` database here.
2. Immediately after validation passes, the code patches `data.slot_versions[slot_id] = chunk_data.chunk_data.slot_version` — i.e., the `StackerDBChunkInv` reply that is about to be signed and sent back to the peer is updated to declare that this node now holds the new version.
3. Only afterward does the function return `(false, true)`, which causes the message to be forwarded to the relayer for actual storage (via the `process_network_result` / `process_stacker_db_chunks` path in `stackslib/src/net/relay.rs`, using `StackerDBTx::try_replace_chunk`). [2](#0-1) 

Because the inventory reply is constructed and signed *before* `try_replace_chunk` actually runs, there is a window in which the announced inventory and the on-disk state can diverge:
- If the relayer's later `try_replace_chunk` call fails (e.g., a concurrent write already advanced `slot_validation.version` past this chunk between the time the unsolicited handler validated it and the time the relayer processes it, hitting `Error::StaleChunk`, or any other storage error), the chunk is silently dropped (`continue` in `process_stacker_db_chunks`), yet the peer has already been told via a signed `StackerDBChunkInv` that this node holds `slot_version`.
- Any peer that receives that inventory will treat this node as an up-to-date source for that slot/version and may skip trying to fetch it elsewhere or may further propagate that (now false) inventory when itself queried, per the store-and-forward gossip design described in the module docs. [3](#0-2) 

This breaks the intended equality "advertised inventory == what is actually stored," which the StackerDB replication protocol depends on for rarest/newest-first scheduling and for terminating sync.

### Impact Explanation
This matches the High-severity class "steering a node off the tip via false inventory" / serving non-canonical state as canonical: a remote, unauthenticated push of a validly-signed-but-ultimately-unstored chunk can cause this node to sign and gossip an inventory entry that does not correspond to its actual replica contents. Because `StackerDBChunkInv` messages are consumed directly by peers' `StackerDBSync` state machines to decide what to fetch and from whom (`recalculate_chunk_request_schedule`, `expected_versions`), false advertisement can cause peers to under-fetch a chunk (believing it is already replicated by this node) or produce inconsistent expected-version baselines across the network, delaying or preventing replication of legitimate signer/miner messages carried over StackerDB (e.g., block pre-commits, as referenced in the project's own changelog entry about a related "stackerdb-uploaded-chunk-event-loss" bug).

### Likelihood Explanation
Medium likelihood. It requires:
- An attacker (or benign race) to have two writers contending for the same slot/version window (a normal occurrence in StackerDB, since replicas frequently receive both pushes and downloaded chunks for the same slot concurrently), so that the actual `try_replace_chunk` call can fail with `StaleChunk` (or other storage error) after this handler already computed and queued the "accepted" inventory patch.
- No special privileges are needed to send `StackerDBPushChunkData`; any connected, authenticated p2p peer can push chunks, and the signature check inside `validate_received_chunk` only verifies the chunk's own signer, not that storage will actually succeed.

I could not fully trace, within the available context, the exact interleaving guarantees between this handler and `process_stacker_db_chunks`'s later `try_replace_chunk` call (e.g., whether they are serialized by a global lock that would prevent the race), so likelihood should be treated as an upper bound pending confirmation against the full relayer/locking code, which is not indexed here.

### Recommendation
Only patch/sign the `StackerDBChunkInv` slot-version entry (or send the inv reply) after the chunk has actually been durably stored via `try_replace_chunk`, or re-validate against the freshly-committed state immediately before replying. Alternatively, defer sending the `StackerDBChunkInv` reply until the relayer has confirmed storage, mirroring how `process_stacker_db_chunks` already calls `log_stored_stackerdb_chunk` only on success.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
