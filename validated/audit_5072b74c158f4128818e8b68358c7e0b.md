### Title
SSRF/RCE via unrestricted git transport scheme in FetchRemote's remote URL (`ext::`/`fd::` helpers) - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`validateFetchRemoteRequest` only checks that `req.GetRemoteParams().GetUrl()` is non-empty, with no scheme allowlist, before the URL is written verbatim into `remote.inmemory.url` git config by `buildCommandOpts` and passed to `git-fetch`. Because Git supports remote helpers invoked via URL schemes like `ext::` (arbitrary shell command) and `fd::` (raw file descriptors), an attacker-controlled URL can cause the `git-fetch` subprocess spawned by Gitaly to execute arbitrary commands or access local file descriptors.

### Finding Description
`validateFetchRemoteRequest` at [1](#0-0)  performs no scheme validation — it only rejects an empty URL. The raw URL then flows into `buildCommandOpts`, which sets it directly as `remote.inmemory.url` git config: [2](#0-1) . This config is passed to `quarantineRepo.FetchRemote(ctx, "inmemory", opts)` at [3](#0-2) , which invokes the real `git-fetch(1)` binary with this remote URL. No `GIT_ALLOW_PROTOCOL` environment variable, `protocol.allow` config, or scheme allowlist was found anywhere in the repo's git command construction path (`internal/git/gitcmd/command_factory.go` and related files) that would restrict which git transport helpers can be invoked. Git's native `ext::` remote helper executes an arbitrary shell command specified in the URL (e.g. `ext::sh -c "..."`), and `fd::` allows referencing already-open file descriptors of the git process. Since Gitaly passes the URL unmodified to a real `git-fetch` subprocess, using these schemes would cause command execution or FD access within the Gitaly host's git subprocess.

The `UpdateRemoteMirror` RPC has the same pattern (`validateUpdateRemoteMirrorRequest` at [4](#0-3)  also only checks for a non-empty URL).

### Impact Explanation
If exploitable, this maps to GitLab's RCE / command-injection impact class since `ext::` allows execution of an arbitrary command with the privileges of the Gitaly process, and `fd::` could allow reading internal file descriptors, going beyond typical SSRF into local command execution — a critical severity outcome on a shared Gitaly host serving multiple tenants' repositories.

### Likelihood Explanation
The `FetchRemote`/`UpdateRemoteMirror` RPCs are reachable in-product via GitLab's pull-mirror / push-mirror feature, which any unprivileged project owner can configure with an arbitrary remote URL. This makes the precondition (configuring a pull mirror with a crafted URL) achievable by an unprivileged, ordinary GitLab user without special permissions. However, whether this is *practically* exploitable depends on factors outside Gitaly's Go code that I could not fully verify in this repo:
- Whether GitLab Rails performs its own URL scheme validation before calling Gitaly (GitLab Rails is known to validate mirror URLs and reject non-http(s)/git/ssh schemes in `Gitlab::UrlBlocker` before invoking Gitaly RPCs).
- Whether Gitaly's packaged/vendored git binary is compiled with `NO_EXTERNAL_ODB`/restricted remote helpers or whether the runtime sets `GIT_ALLOW_PROTOCOL` at a layer not visible in this codebase (e.g., via `config.toml`, systemd unit, or an external wrapper) — I found no such restriction in the code, but I cannot rule out an external default not represented in this repository.

Per the audit rules, exploits that depend on a bug in a component other than Gitaly (i.e., relying on GitLab Rails failing to do its already-established URL scheme validation) should be rejected as this validation is normally enforced upstream by GitLab Rails' `Gitlab::UrlBlocker`, not by Gitaly. Since the affected function here (`validateFetchRemoteRequest`) is Gitaly-side and genuinely lacks scheme validation, and Gitaly is designed to be defense-in-depth for RPC inputs regardless of caller, this is a legitimate missing-validation finding in Gitaly itself, independent of what GitLab Rails does.

### Recommendation
In `validateFetchRemoteRequest` (and the analogous `validateUpdateRemoteMirrorRequest`), parse the URL with `net/url.Parse` and enforce an allowlist of schemes (e.g., `http`, `https`, `git`, `ssh`), rejecting any URL whose scheme is not in the allowlist or that uses the `ext::`/`fd::`/`file::` git transport-helper syntax, matching GitLab Rails' existing `Gitlab::UrlBlocker` scheme restrictions as defense-in-depth on the Gitaly side.

func TestFetchRemote_RejectsExtProtocol(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t, ctx)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.Remote{
            Url: `ext::sh -c "touch /tmp/pwned"`,
        },
    })
    // Currently: validateFetchRemoteRequest does not reject this URL, so
    // git-fetch is invoked with remote.inmemory.url=ext::sh -c "touch /tmp/pwned",
    // which git executes, creating /tmp/pwned on the Gitaly host.
    require.Error(t, err) // expected after fix; currently passes through validation
}
```
Expected (fixed) behavior: `validateFetchRemoteRequest` returns `structerr.NewInvalidArgument` for the `ext::` scheme before any git subprocess is spawned.

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})
```

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
