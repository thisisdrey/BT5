### Title
Protocol Fee Bypass on NEP-245/IMT Token Diffs via Unit-Sized Intent Splitting - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` exempts NEP-245 (multi-token) and IMT token deltas from the protocol fee whenever the per-intent delta magnitude is `<= 1`. Because `execute_signed_intents` accepts an arbitrary batch of independently-nonced `MultiPayload`s and applies this exemption per individual `TokenDiff` intent rather than on the aggregate value moved, an attacker can convert any arbitrarily large NEP-245/IMT swap into a sequence of unit-sized (`delta == ±1`) `TokenDiff` intents. Each unit intent is fee-exempt, so the attacker pays zero protocol fee on volume that should have been fee-bearing, breaking the "fees owed vs. fees collected" invariant.

### Finding Description
The fee is computed and collected inside `TokenDiff::execute_intent`, strictly on a per-`TokenDiff`-intent basis: [4](#0-3) 

The exemption logic in `token_fee` is:
```rust
TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
// do not take fees on NFTs and MTs with |delta| <= 1
TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
``` [3](#0-2) 

This exemption is intended for genuinely atomic, non-fungible-like transfers (where `amount` can only ever be `1`), but NEP-245/IMT `TokenId`s can also represent fungible balances with arbitrarily large amounts. Since `execute_intents`/`execute_signed_intents` iterate over an unbounded list of independently signed/nonced `MultiPayload`s in a single call [1](#0-0) , and each `TokenDiff` intent is fee-evaluated independently on its own local `amount`, a party who controls both sides of a matched trade (e.g., a solver trading between two accounts it controls, or a self-trade) can decompose a large NEP-245/IMT volume `N` into `N` separate `TokenDiff` intents each moving exactly `1` unit. Every one of those `N` unit intents hits the `amount <= 1` branch and returns `Pips::ZERO`, so `fees_collected` stays empty for the whole batch even though `N` units of value were moved — the fee due on the total delta (based on the aggregate custody change) is never charged, contrary to the fee owed on an equivalent single `TokenDiff` of magnitude `N`.

This breaks the equality that should hold between "fees owed" (a function of total value transferred through the protocol) and "fees collected" (what actually lands with `fee_collector`) for NEP-245/IMT assets.

### Impact Explanation
This directly matches the explicitly allowed Critical impact category "fees bypassed or over-collected." The protocol systematically under-collects (to zero) fees on NEP-245/IMT volume that is economically equivalent to normal fee-bearing swaps, at the expense of the `fee_collector` account and by extension the protocol/DAO that fee accrues to.

### Likelihood Explanation
Any account (or coordinated pair of accounts) capable of signing `MultiPayload`s — i.e., any regular intents user/solver — can trivially construct many unit-delta `TokenDiff` intents in a single `execute_intents` call, since nonces are independent per signed payload and there is no aggregation of `amount` across intents in the same batch or across separate calls. The only limiting factor is transaction gas/size, which bounds how much volume can be shifted per call but does not prevent the exploit itself (repeated calls further amplify the bypassed volume).

### Recommendation
Compute and enforce the NEP-245/IMT fee based on the ledger-level aggregate change to a given `TokenId` for a signer within the whole batch/transfer being settled, not on each individual `TokenDiff`'s local per-token delta. Alternatively, remove or tighten the `amount <= 1` exemption so it only applies to token types that are inherently unit-only (e.g., true `Nep171` NFTs), and require callers to prove/verify that a `Nep245`/`Imt` `TokenId` is non-fungible (supply capped at 1) before waiving the fee, rather than inferring exemption purely from the instantaneous `amount` of a single intent.

### Proof of Concept
1. Attacker controls accounts A and B on the intents contract, each holding balance of a fungible-like NEP-245 `TokenId` `T` with non-trivial protocol fee (`Pips` > 0).
2. Attacker wants to move `N = 100_000` units of `T` from A to B while avoiding fee. A direct `TokenDiff{T: -100_000}` (A) / `TokenDiff{T: +100_000}` (B) pair would charge fee via `Self::token_fee(T, 100_000, fee).fee_ceil(100_000)` since `amount > 1` [5](#0-4) .
3. Instead, attacker signs `100_000` separate `MultiPayload`s, each containing a `TokenDiff{T: -1}` from A and a paired `TokenDiff{T: +1}` to B (200,000 intents total), and submits them all in one `execute_intents(signed)` call (or split across multiple calls if gas-limited).
4. For every one of these unit intents, `Self::token_fee(T, 1, fee)` hits the `amount <= 1` branch and returns `Pips::ZERO` [6](#0-5) , so `fees_collected` remains empty across the whole batch.
5. `execute_signed_intents` finalizes successfully since the batch nets to zero (invariant preserved) [7](#0-6) , but the `fee_collector` account receives `0` instead of the `fee_ceil(100_000)` amount it should have received for an equivalent single-intent transfer of the same total volume.
