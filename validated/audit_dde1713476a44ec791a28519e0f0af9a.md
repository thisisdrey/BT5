### Title
Unprivileged user can permanently brick an account's deposits/borrows by filling `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` via permissionless `deposit(onBehalfOf)` / `transfer` — race-style griefing analog — ([File: contracts/Pool.sol](contracts/Pool.sol) / [contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The reported bug class is: a *permissionless* operation mutates shared per-account state such that a victim's pending/legitimate operation fails, freezing funds or functionality. The strongest reachable analog in Metronome is the `MAX_TOKENS_PER_USER` accounting in `Pool` combined with the fact that adding a token to a victim's account set is triggered by operations any caller can aim at the victim (`DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer(to_)`). An attacker can dust-fill a victim's token list to the cap, after which every code path that needs to add a new deposit or debt token for that account reverts with `UserReachedMaxTokens`.

### Finding Description
`Pool` enforces a hard cap of 30 combined deposit + debt tokens per account: [1](#0-0) 

`DepositToken._mint` and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance transitions from zero: [2](#0-1) [3](#0-2) 

Two unprivileged surfaces push a new entry into a *victim's* set:

1. `DepositToken.deposit(uint256, address onBehalfOf_)` — `onBehalfOf_` is attacker-chosen and only checked for non-zero; anyone can mint dust msdTOKEN to a victim [4](#0-3) 
2. `DepositToken.transfer(to_, amount_)` — the attacker needs only unlocked dust balance of each deposit token type [5](#0-4) 

Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`, every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` for that account reverts inside `onlyIfAdditionWillNotReachMaxTokens`. Because the check runs inside `_mint`/`_transfer`/debt minting, this causes:

- `deposit` of any *new* collateral type to the victim to revert (the mint reverts after Treasury already received funds — the whole tx rolls back, so the deposit is bricked).
- `DebtToken.mint`/`issue` of any *new* synthetic asset to the victim to revert — the victim cannot open new borrow positions.
- `SmartFarmingManager.leverage` on behalf of flows targeting a new deposit/debt token to revert, since step 4 calls `depositToken_.deposit(_depositAmount, _msgSender)` [6](#0-5) 
- Any inbound `transfer`/`seize`/`transferFrom` of a deposit token the victim doesn't already hold reverts.

Like the TON report, a permissionless "sync-like" action (here: dust insertion into the account's token set) races with and silently poisons the victim's legitimate state-changing operations.

### Impact Explanation
- **Temporary freezing of funds / functionality**: the victim cannot deposit new collateral types, mint new synth debt, receive new deposit tokens, or use `leverage`/`flashRepay`-style flows that introduce a new token until they fully withdraw one held deposit token to zero (which calls `removeFromDepositTokensOfAccount`).
- The attacker can *re-fill* the slot the moment the victim frees one — the same front-running property as the report: the attacker watches for `removeFromDepositTokensOfAccount` (balance → 0) and dust-inserts again in the next block, making the freeze effectively permanent for as long as the attacker maintains it.
- Cost to the attacker is ~30 dust deposits/transfers (one per token type); existing balances cannot be withdrawn by the attacker, so this is griefing rather than theft.

### Likelihood Explanation
Fully unprivileged: any EOA with dust underlying (or existing msdTOKEN dust) can execute it via public `deposit`/`transfer` on each registered `DepositToken`. No governor/keeper/oracle required. The only mitigating factor is that it does not trap already-held balances — `withdraw` of existing unlocked positions still succeeds — so impact is a freeze of *new* position activity and inbound transfers rather than permanent loss of existing principal.

### Recommendation
- Do not let third parties grow a victim's account set: skip `addToDepositTokensOfAccount` when the addition would hit the cap (treat the list as best-effort), or replace the revert in `onlyIfAdditionWillNotReachMaxTokens` with a cap check only for *new* entries while allowing balance updates to existing entries.
- Alternatively, restrict `deposit`'s `onBehalfOf_` to `== _msgSender()` or opt-in recipients, and gate unsolicited `transfer` additions similarly.
- Track `depositTokensOfAccount` lazily (derive from held balances at read time) instead of maintaining the set inside `_transfer`/`_mint`.
