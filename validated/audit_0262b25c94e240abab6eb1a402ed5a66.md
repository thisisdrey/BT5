### Title
Attacker can force-fill a victim's bounded per-account token list (`MAX_TOKENS_PER_USER`) via dust `DepositToken.transfer`, reverting all future first-time token additions for the victim - ([File: contracts/Pool.sol])

### Summary
The Metronome analog of CVE-2016-4563 (a bounded output buffer overflowed by an attacker-influenced count) is the fixed-size-capable per-account token list in `Pool`. Each account may hold entries in `depositTokensOfAccount` + `debtTokensOfAccount` totaling `MAX_TOKENS_PER_USER = 30`, enforced by `onlyIfAdditionWillNotReachMaxTokens` in `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` [1](#0-0) [2](#0-1) . Any `DepositToken._transfer` that gives a recipient a nonzero balance for the first time unconditionally pushes the token into that victim's list [3](#0-2) . An unprivileged attacker can therefore "overflow" a victim's list with unsolicited dust, after which every new token type the victim legitimately receives reverts with `UserReachedMaxTokens`.

### Finding Description
`DepositToken.transfer`/`transferFrom` are public, unprivileged entry points that only check the sender's unlocked balance via `_revertIfLocked` [4](#0-3) . `_transfer` then calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero [5](#0-4) . `Pool.addToDepositTokensOfAccount` reverts the entire transfer once the victim already has 30 combined deposit+debt token entries [6](#0-5) .

Attack path:
1. Attacker deposits collateral into each enabled `DepositToken` (or buys/obtains msd tokens) so they hold a transferable balance. Cost is bounded by deposit fees plus dust amounts.
2. Attacker calls `depositToken_i.transfer(victim, 1)` for every enabled deposit token the victim does not yet hold. Each transfer appends the token to `depositTokensOfAccount[victim]`.
3. Once the victim's combined count reaches 30, any subsequent first-time receipt of a deposit token — deposits made on their behalf, rewards/seize proceeds, or a normal ERC20 transfer of a new msd token — reverts inside `_transfer` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.

The analogous "invariant break" is a capacity/consistency violation: the set of tokens the accounting layer (`depositTokensOfAccount`, consumed by `depositOf`/`debtPositionOf` loops [7](#0-6) ) assumes only tokens the user chose to hold, but an outsider controls writes to it. `DepositToken.seize` routes through the same `_transfer` [8](#0-7) , so a saturated liquidator/victim-beneficiary also reverts.

### Impact Explanation
Temporary freezing of funds and blocked protocol operations: while saturated, the victim cannot receive any new deposit-token type — including collateral deposited on their behalf (`deposit` mints call the same `_mint` → `addToDepositTokensOfAccount` path [9](#0-8) ) and seized collateral routed to them. New synthetic issuance is also blocked if it would add a 31st debt-token entry, since `addToDebtTokensOfAccount` enforces the same combined cap [10](#0-9) . The victim can un-stick themselves only by first spending gas to transfer out each dusted token (each zero-balance transfer calls `removeFromDepositTokensOfAccount`), which the attacker can re-saturate by front-running — a repeatable griefing loop. This is a liveness/availability break, not gas-unbounded-loop DoS: the cap is a hard protocol limit, and the revert occurs regardless of gas.

### Likelihood Explanation
- Fully unprivileged: requires only public `transfer` on real `DepositToken` contracts; no governor, oracle, or privileged role.
- Feasibility depends on the number of enabled deposit tokens in the deployed pool — the attacker needs enough distinct tokens (plus the victim's existing debt tokens) to reach 30. On mainnet/Met deployments with several collaterals this is achievable but may not fill the cap alone; partial fills still narrow the victim's remaining capacity.
- Attack cost is low (dust amounts + deposit fees) and repeatable.
- Caveat: severity is limited to temporary freezing/griefing rather than direct theft, since the victim retains a recovery path (transfer the dust out). Whether this crosses the "temporary freezing of funds" bar depends on judging; it is the strongest reachable analog of a bounded-buffer-overflow-by-attacker-controlled-count in this codebase.

### Recommendation
- Do not add entries to `depositTokensOfAccount` on passive receipt, or add a per-account opt-in/`claim` model so a recipient must accept a token before it occupies a slot.
- Alternatively, decouple the cap: track only tokens the account minted/deposited itself in `depositTokensOfAccount` and compute `depositOf` over `balanceOf` rather than the enumerable list, or raise/remove `MAX_TOKENS_PER_USER` (the guard exists to bound `depositOf`/`debtOf` loop gas, so prefer the opt-in model).
- If the list must stay, let users remove entries permissionlessly (e.g., a `Pool.removeMyDepositToken(token)` that requires `balanceOf == 0`... but note dust >0 requires a transfer anyway; better to make transfers of *new* tokens to a saturated account still succeed by skipping list insertion and handling accounting differently).

### Proof of Concept
Hardhat sketch (mirrors the existing `UserReachedMaxTokens` test in `test/Pool.test.ts:1386`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.9;

import "forge-std/Test.sol";
import "../contracts/Pool.sol";
import "../contracts/DepositToken.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool;               // deployed pool proxy
    DepositToken[] tokens;   // pool.getDepositTokens()
    address victim = address(0xVIC);
    address attacker = address(0xATT);

    function test_DustFillBlocksVictim() public {
        // 1. Attacker deposits and acquires balance in every deposit token
        for (uint i; i < tokens.length; ++i) {
            // attacker deposits collateral, receives msdToken balance
            // tokens[i].deposit(...)
            vm.startPrank(attacker);
            // 2. Dust transfer to victim: pushes token into victim's list
            tokens[i].transfer(victim, 1);
            vm.stopPrank();
        }

        // Victim already holds debt tokens too; combined count hits 30
        assertEq(
            pool.getDepositTokensOfAccount(victim).length +
            pool.getDebtTokensOfAccount(victim).length,
            pool.MAX_TOKENS_PER_USER()
        );

        // 3. Anyone depositing a NEW collateral type on victim's behalf reverts
        DepositToken newToken; // newly enabled collateral
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        // depositOnBehalfOf(newToken, victim, amount) -> _mint -> _transfer path
        // -> addToDepositTokensOfAccount(victim) -> revert

        // 4. Direct ERC20 transfer of any new msd token to victim also reverts
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newToken.transfer(victim, 1); // inside _transfer -> addToDepositTokensOfAccount
    }
}
```

Note: I was not able to verify the number of deposit tokens enabled on each live deployment from the index (deployment JSONs list ABIs, not token counts), so whether the cap can be fully saturated on a given chain vs. only partially filled should be confirmed on a fork of the target deployment.
