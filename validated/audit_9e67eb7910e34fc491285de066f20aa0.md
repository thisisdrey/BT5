## Finding

The bug-class in the report — a pause/restriction implemented in one contract path but not enforced in the actual execution path that performs the sensitive operation — has a direct analog in java-tron's freeze/unfreeze resource system.

### Title
Old FreezeBalance mechanism remains executable through the TVM `freeze` opcode after FreezeV2 migration, bypassing the actuator-level deprecation guard - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
`FreezeBalanceActuator.validate()` explicitly blocks the legacy (v1) freeze operation once the network has migrated to FreezeV2, but the equivalent validation used by the TVM `freeze()` opcode (reachable from any smart-contract call) omits this check entirely, allowing the deprecated v1 freeze accounting path to keep running after governance intended to retire it.

### Finding Description
`FreezeBalanceActuator.validate()` contains an explicit migration guard: [1](#0-0) 

This throws `"freeze v2 is open, old freeze is closed"` whenever `dynamicStore.supportUnfreezeDelay()` (FreezeV2 governance flag) is active, ensuring that once the network transitions to the new resource model, the old `FreezeBalanceContract` transaction type can no longer be broadcast.

However, the TVM exposes an internal `freeze` opcode/native contract that performs the *same* legacy v1 freeze accounting, reachable by any account triggering a smart contract: [2](#0-1) 

This opcode delegates validation to `FreezeBalanceProcessor.validate()`, which checks balance sufficiency, frozen count, resource type, and delegatee type — but never checks `dynamicStore.supportUnfreezeDelay()`: [3](#0-2) 

The TVM opcode is gated only by the independent `VMConfig.allowTvmFreeze()` flag, set from the committee's `allowTvmFreeze` parameter, which is unrelated to and not automatically disabled by `supportUnfreezeDelay` (FreezeV2 activation): [4](#0-3) 

So exactly like the reported issue — where the pause check lived in `SpiritFactory` but the actual swap execution in `PancakePair` never consulted it — here the deprecation check lives only in `FreezeBalanceActuator.validate()` (the actuator invoked for user-broadcast `FreezeBalanceContract` transactions), while the actual state-mutating logic is duplicated in `FreezeBalanceProcessor`, invoked from a second, independent entry point (`Program.freeze()`/TVM opcode) that omits the guard.

### Impact Explanation
If FreezeV2 (`supportUnfreezeDelay`) is activated by committee without also disabling `allowTvmFreeze`, any deployed smart contract can still invoke the legacy v1 freeze path via the TVM opcode, continuing to create v1-style `Frozen`/`DelegatedResourceCapsule` entries and modify `TotalNetWeight`/`TotalEnergyWeight` even though the network's intended resource model is v2. This produces bookkeeping divergence between the deprecated and current resource-accounting systems (mixed v1/v2 frozen state, delegated resource records, and weight totals), which the governance decision to "close" old freeze was meant to prevent — potentially skewing bandwidth/energy/vote weight distribution network-wide.

### Likelihood Explanation
Reachable by any unprivileged account that deploys or calls a smart contract invoking the `freeze` opcode — no special privilege required. The only precondition is that the network operator has enabled FreezeV2 while `allowTvmFreeze` remains on (these are independent governance proposals, so this is a plausible and even likely operational configuration during/after a v1→v2 migration window).

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `FreezeBalanceProcessor.validate()` (and any other TVM-reachable v1-freeze native contract paths) that already exists in `FreezeBalanceActuator.validate()`, so the deprecation of the legacy freeze mechanism is enforced consistently regardless of entry point.

### Proof of Concept
1. Committee enables `unfreezeDelayDays` (FreezeV2) while `allowTvmFreeze` remains `1`.
2. Any user deploys/calls a contract that invokes the `freeze` TVM opcode (e.g., via `freezeForSelf`/`freezeForOther` style Solidity bindings), as exercised in [5](#0-4) .
3. `Program.freeze()` calls `FreezeBalanceProcessor.validate()`/`execute()`, which succeeds because it never checks `supportUnfreezeDelay()`, in contrast to a direct `FreezeBalanceContract` broadcast which would be rejected by `FreezeBalanceActuator.validate()`.

  public boolean freeze(DataWord receiverAddress, DataWord frozenBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,
        frozenBalance.longValue(), null,
        "freezeFor" + convertResourceToString(resourceType), nonce, null);

    FreezeBalanceParam param = new FreezeBalanceParam();
    param.setOwnerAddress(owner);
    param.setReceiverAddress(receiver);
    boolean needCheckFrozenTime = CommonParameter.getInstance()
        .getCheckFrozenTime() == 1; // for test
    param.setFrozenDuration(needCheckFrozenTime
        ? repository.getDynamicPropertiesStore().getMinFrozenTime() : 0);
    param.setResourceType(parseResourceCode(resourceType));
    try {
      FreezeBalanceProcessor processor = new FreezeBalanceProcessor();
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM Freeze: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM Freeze: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }

    // validate for delegating resource
    byte[] receiverAddress = param.getReceiverAddress();
    if (!FastByteComparisons.isEqual(ownerAddress, receiverAddress)) {
      param.setDelegating(true);

      // check if receiver account exists. if not, then create a new account
      AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
      if (receiverCapsule == null) {
        receiverCapsule = repo.createNormalAccount(receiverAddress);
      }

      // forbid delegating resource to contract account
      if (receiverCapsule.getType() == Protocol.AccountType.Contract) {
        throw new ContractValidateException(
            "Do not allow delegate resources to contract addresses");
      }
    }
  }
