### Title
Multi-block paginated `updateNav` can finalize a mixed-epoch NAV when loan ledger state mutates mid-cycle — ([File: tare-io__tare-contracts/contracts/PortfolioVault.sol])

### Summary
`updateNav`'s restart logic checks only two "indexes" — `loansNFT.ownershipNonce(vault)` and `calculator.configurationVersion()` — to decide whether an in-progress NAV computation must restart. It never checks whether the underlying `Loans.sol` ledger state of an *already-processed* loan changed since its value was folded into `pendingNav`. This mirrors the Compound/Morpho bug class: only a subset of the relevant "indexes" are refreshed/validated (nonce + config version), while another input that materially affects the computed value (per-loan ledger balances, mutated via `pay`/`accrue`/`applyWaterfall`/`chargeMiscFee`/`returnFunds`/`refundBorrower`) is left stale for loans already swept into the running total.

### Finding Description
`updateNav` ( [1](#0-0) ) paginates over `_navLoanIds` across potentially many transactions/blocks (documented as up to ~87 blocks / ~2.9 minutes for 100k loans). At the start of a cycle it snapshots `lastOwnershipNonce` and `lastCalculatorConfigurationVersion`, and on each subsequent call it restarts the cycle only if the *live* nonce or configuration version diverges from the snapshot, or if `maxNavComputationTime` elapses: [2](#0-1) 

For each batch it calls `calculator.getLoansValue(loans_, owned)` — a live read of `Loans.sol` at that point in time — and accumulates the result into `pendingNav`: [3](#0-2) 

`Loans.sol`'s servicing functions (`pay`, `accrue`, `applyWaterfall`, `chargeMiscFee`, `returnFunds`, `refundBorrower`) are callable directly by the borrower/servicer at any time and have no awareness of, or coordination with, the vault's `navStart`/`navCursor` state — unlike the vault's own mutating functions (`fundLoan`, `acceptSaleOffer`, `collectCashflows`, `addLoansToNav`, etc.), which are explicitly gated by `_requireIdleNav()` per the spec's function table. If a loan already included in an earlier batch of the current cycle (its valuation already baked into `pendingNav`) receives a payment or waterfall allocation before the cycle finalizes, that loan's true value changes (e.g., moving discounted unreturned principal to par-valued collected cash), but the stale, pre-payment value remains locked into `pendingNav` for the remainder of the cycle. Because neither the ownership nonce nor the calculator's `configurationVersion` changes as a result of a loan payment, the restart branch never fires, and the finalized `lastNav` is computed as an inconsistent mix of pre-payment and post-payment loan states — a "mixed-epoch" NAV.

This directly contradicts the invariant documented in `specs/invariants.md`: "A finalized `lastNav` is snapshot-consistent: mid-cycle holdings change (nonce), calculator config change (version), or timeout ⟹ restart, never a mixed-epoch NAV" [4](#0-3) . The invariant is only enforced along the ownership/config axes, not the ledger-state axis — analogous to the Compound bug where only the specific borrow/collateral market indexes were refreshed while other cached market indexes went stale.

### Impact Explanation
The finalized `lastNav` feeds directly into `approveDeposit`/`approveRedemption` share-price calculations once `_requireFreshNav` passes (which it will, since neither the nonce nor version check catches this drift) [5](#0-4) . A materially wrong NAV means new depositors can be minted shares against an understated NAV (diluting existing/other shareholders) or redeeming shareholders can be paid out against an overstated NAV (extracting more value than their pro-rata share) — both are "unfair mint or redeem" outcomes against real USDC/shares, which is an explicitly allowed impact.

### Likelihood Explanation
Likelihood depends on operational cadence: it requires (a) a portfolio large enough that `updateNav` spans multiple transactions, and (b) a borrower/servicer payment landing on an already-processed loan within that window. Under the "single-entity shareholder" trust model documented for the vault, some staleness is explicitly accepted as "self-dilution" (see `specs/vault.md` "NAV Lag / Staleness" section), which may reduce severity if the operator considers this scenario covered by that accepted-risk framing. I was unable to find an explicit statement in `SECURITY.md` or the linked Pashov audit report addressing this specific in-cycle ledger-drift scenario (as opposed to the general `maxNavAge` staleness or the already-fixed NFT-ownership index-shift bug covered by `Vault_PortfolioManager.t.sol`), so its acceptance status is uncertain.

### Recommendation
Extend the restart/staleness detection in `updateNav` to also invalidate/restart when the ledger state of any loan already included in the current cycle's `pendingNav` has changed — e.g., by tracking a per-loan or global "ledger version"/timestamp analogous to `ownershipNonce`, bumped by `Loans.sol` on any balance-mutating call, and checked the same way `currentNonce`/`currentConfigurationVersion` are checked today.

### Proof of Concept
1. Populate `_navLoanIds` with enough loans that `updateNav(batchSize)` requires ≥2 calls to finalize (e.g., `batchSize = 1`, two curated loans A and B).
2. Manager calls `updateNav(1)`: loan A is processed, its (say, DQ90-discounted) value is added to `pendingNav`, `navCursor = 1`.
3. Before the manager's next `updateNav` call, the borrower/servicer of loan A calls `pay` + `applyWaterfall` on `Loans.sol` directly, fully curing the delinquency and converting discounted unreturned principal into par-valued collected cash — a large value increase for loan A that is not reflected in the already-computed `pendingNav`.
4. Neither `loansNFT.ownershipNonce(vault)` nor `calculator.configurationVersion()` changes as a result of step 3.
5. Manager calls `updateNav(1)` again: it processes loan B fresh, then finalizes `lastNav = idleUSDC + adjust(pendingNav_stale_A + fresh_B) - deductions`, baking in loan A's pre-payment (stale, discounted) value alongside loan B's fresh value.
6. `approveDeposit`/`approveRedemption` subsequently use this understated `lastNav`, minting new shareholders more shares than fair and diluting existing holders — no `PortfolioHoldingsChanged`/`CalculatorConfigurationChanged`/`StaleNav` revert fires to prevent it.

  function updateNav(uint256 batchSize) external whenNotPaused {
    _requireManagerRole();
    require(batchSize > 0, ZeroAmount());

    ILoansNFT loansNFT_ = loansNFT;
    INavCalculator calculator_ = calculator;
    ILoans loans_ = loans;

    uint256 currentNonce = loansNFT_.ownershipNonce(address(this));
    uint256 currentConfigurationVersion = calculator_.configurationVersion();
    if (navStart == 0) {
      navStart = block.timestamp;
      lastOwnershipNonce = currentNonce;
      lastCalculatorConfigurationVersion = currentConfigurationVersion;
      emit NavComputationStarted(block.timestamp);
    } else if (
      currentNonce != lastOwnershipNonce ||
      currentConfigurationVersion != lastCalculatorConfigurationVersion ||
      block.timestamp - navStart > maxNavComputationTime
    ) {
      // Restart if the vault's NFT holdings changed mid-cycle, calculator
      // factors changed, or the previous computation took too long. The in-loop
      // ownership check below self-heals the list as it walks.
      navStart = block.timestamp;
      navCursor = 0;
      pendingNav = 0;
      lastOwnershipNonce = currentNonce;
      lastCalculatorConfigurationVersion = currentConfigurationVersion;
      emit NavComputationStarted(block.timestamp);
    }

    uint256 cursor = navCursor;
    uint64[] memory owned = new uint64[](batchSize);
    uint256 ownedCount;

    for (uint256 i; i < batchSize; ++i) {
      if (cursor >= _navLoanIds.length) break;
      uint64 loanId = _navLoanIds[cursor];
      // Treat a reverting `ownerOf` (e.g. burned token) the same as a foreign
      // owner so the list self-heals instead of bricking NAV computation.
      bool owns;
      try loansNFT_.ownerOf(uint256(loanId)) returns (address owner) {
        owns = owner == address(this);
      } catch {
        owns = false;
      }
      if (owns) {
        owned[ownedCount++] = loanId;
        unchecked {
          ++cursor;
        }
      } else {
        // Drop stale entry; swap-and-pop places a new entry at `cursor`, so do
        // not advance — the next iteration re-scans this slot.
        _removeLoanFromNav(loanId);
      }
    }

    if (ownedCount > 0) {
      // Trim the memory array to its used length before passing to the calculator.
      assembly {
        mstore(owned, ownedCount)
      }
      pendingNav += calculator_.getLoansValue(loans_, owned);
    }

    navCursor = cursor;

    // Finalize if we've processed all loans
    if (cursor >= _navLoanIds.length) {
      lastNav =
        assetToken.balanceOf(address(this)) +
        calculator_.applyPortfolioAdjustment(pendingNav) -
        totalPendingDepositAssets -
        totalClaimableRedeemAssets;
      lastNavUpdate = block.timestamp;
      navCursor = 0;
      pendingNav = 0;
      navStart = 0;
      emit NavUpdated(lastNav, block.timestamp);
    }
  }

  function _requireFreshNav() internal view {
    require(navStart == 0, NavComputationInProgress());
    require(lastNav > 0, ZeroNav());
    // Specific staleness signals come before the generic age check so callers
    // see the most informative error (e.g. `PortfolioHoldingsChanged` when an
    // NFT moved, even if `lastNavUpdate` was also explicitly cleared).
    require(loansNFT.ownershipNonce(address(this)) == lastOwnershipNonce, PortfolioHoldingsChanged());
    require(calculator.configurationVersion() == lastCalculatorConfigurationVersion, CalculatorConfigurationChanged());
    require(block.timestamp - lastNavUpdate <= maxNavAge, StaleNav());
  }
