Audit Report

## Title
Ratio-based back-conversion of Ethereum-gas budget into weight/deposit limits in `pallet-revive`'s nested-frame metering can starve legitimate nested calls of weight - ([File: substrate/frame/revive/src/metering/math.rs])

## Summary
`substrate_execution::new_nested_meter`'s `CallResources::Ethereum` branch converts the parent's remaining weight and deposit into a combined ethereum-gas estimate, caps it against the caller-requested `gas`, and then applies a single scalar `ratio = gas_limit / remaining_gas` uniformly to both `weight_left` and `deposit_left` to derive `nested_weight_limit`/`nested_deposit_limit`. [1](#0-0)  When `deposit_gas_left` dominates `remaining_gas` (a normal configuration for a caller with a large deposit budget but modest weight budget), `ratio` collapses toward the deposit share of the sum, so `weight_limit = ratio * weight_left` becomes far smaller than the weight actually needed/available, even for a purely-computational sub-call that never touches storage.

## Finding Description
This code path is reached from `ResourceMeter::new_nested`, which dispatches to `math::substrate_execution::new_nested_meter` for every nested `CallResources` request whenever the top-level transaction uses `TransactionLimits::WeightAndDeposit` (the ordinary Substrate-style extrinsic path, not just `eth_transact`). [2](#0-1)  This means any contract call whose nested execution issues an EVM `CALL` with `CallResources::Ethereum { gas, .. }` inside a regular Substrate-style transaction will go through this ratio computation.

The corrupted value is `ratio`, and consequently `nested_weight_limit`:
- `weight_gas_left` and `deposit_gas_left` are computed via independent fee-conversion functions and summed into `remaining_gas`. [3](#0-2) 
- `gas_limit = remaining_gas.min(*gas)` and `ratio = gas_limit / remaining_gas` are then applied identically to both `weight_left` and `deposit_left`. [4](#0-3) 

Because `ratio` is derived from the *combined* pool rather than from the weight-specific exchange rate, when `deposit_gas_left ≫ weight_gas_left`, a caller requesting a modest `gas` amount (fully payable from `weight_gas_left` alone, with no storage growth expected) receives `nested_weight_limit ≈ ratio * weight_left`, which is a small fraction of `weight_left` — much smaller than the weight actually equivalent to the requested `gas`. The nested `WeightMeter` (constructed with this deflated `weight_limit`) will then reject legitimate weight charges with `Error::OutOfGas`, even though the parent's real `weight_left` was ample. This is confirmed as a real, previously-observed failure mode by PR #10924 for the `deposit_left = u128::MAX` extreme case; [5](#0-4)  that fix only caps `remaining_gas` at `u64::MAX` and does not address the underlying single-ratio proportional split, so any large-but-sub-cap `deposit_left` still reproduces the same skew.

## Impact Explanation
This is a runtime correctness bug in `pallet-revive`'s resource metering that causes legitimate, well-funded nested contract calls to spuriously fail with `Error::OutOfGas`, wasting transaction fees and breaking composable multi-call contracts (proxies, routers) whenever their weight/deposit budgets are asymmetric relative to the eth-gas exchange rate. It is reachable by any unprivileged caller issuing an ordinary contract call/`eth_call` with a nested `CALL` requesting Ethereum-style gas — no privileged, validator, or off-chain assumptions are required. It does not, however, allow theft, unauthorized origin escalation, duplicate settlement, or permanent fund lock; its effect is confined to spurious reverts/wasted execution within `pallet-revive`, which the impact gate characterizes as "public underpriced work that degrades ... execution" in a narrow, per-call sense rather than block-production-level degradation.

## Likelihood Explanation
Triggering requires only a normal, non-adversarial transaction shape: a `WeightAndDeposit`-mode call whose remaining deposit budget's gas-equivalent substantially exceeds its remaining weight budget's gas-equivalent, combined with a nested EVM `CALL` requesting Ethereum-style gas. This is plausible for contracts pre-funded with generous storage-deposit allowances but modest weight budgets, or after several nested frames have consumed weight while deposit remains largely untouched. The exact extreme case (`u128::MAX` deposit) was already found and partially fixed in PR #10924, confirming the pattern is realistically reachable rather than purely theoretical, though the residual skew for smaller (non-`u128::MAX`, sub-`u64::MAX`-gas-equivalent) deposit values described in the claim is a mathematical extrapolation from the same code that I could not independently execute/test in this environment (no runtime execution available); the claim's PoC steps are conceptual rather than a verified, run test.

## Recommendation
Do not use a single combined-gas ratio to split weight and deposit limits. Instead, bound each resource independently against what the requested `gas` can actually cover in that dimension — e.g., compute weight and deposit limits from the requested `gas` using their own individual exchange rates and cap each by its own `_left` value, rather than deriving one scalar ratio from the sum of two heterogeneous quantities and applying it uniformly.

## Proof of Concept
Conceptual reproduction path (adapting the existing harness rather than a verified run in this environment):
1. Set up a root `TransactionMeter` via `substrate_execution::new_root` with a modest `weight_limit` and a large `deposit_limit` (e.g., large enough that `deposit_gas_left ≫ weight_gas_left`, but below `u64::MAX` gas-equivalent so PR #10924's cap doesn't engage).
2. Invoke `new_nested_meter` with `CallResources::Ethereum { gas, .. }` where `gas` is fully satisfiable from `weight_left` alone with no storage growth expected.
3. Observe `ratio = gas_limit / remaining_gas` skewed toward the deposit-dominated `remaining_gas`, producing `nested_weight_limit ≪ weight_left`.
4. Confirm the nested `WeightMeter` created with this limit rejects a weight charge that would have succeeded against the full `weight_left`, per `Error::<T>::OutOfGas`, reusing patterns from `substrate/frame/revive/src/tests/pvm.rs::gas_estimation_for_subcalls` and `substrate/frame/revive/src/metering/tests.rs` but substituting a skewed weight-vs-deposit configuration instead of the `u128::MAX` edge case already tested.     ## Problem

```text
    When calculating resource limits for nested calls through
    `substrate_execution::new_nested_meter`, the ratio-based scaling fails when
    `deposit_left` is very large (e.g., `u128::MAX` default for unlimited deposit).

    The calculation flow:
    1. `remaining_gas = weight_gas + deposit_gas` → huge number (deposit dominates at ~10^38)
    2. Contract requests all gas: `requested_gas = u64::MAX` (~10^19)
    3. `ratio = requested_gas / remaining_gas` ≈ 0.0000000000000027
    4. `nested_weight_limit = ratio × weight_left` ≈ 0
    5. Nested call immediately fails with OutOfGas

    ## Solution

    Cap `remaining_gas` to `u64::MAX` since Ethereum gas is a u64 value. This ensures
    the ratio is 1.0 when a contract requests all gas, giving the nested call the full
    remaining weight.
```
