Attacker-supplied `claimer` in Snowbridge inbound-queue v2 can be pinned to an unclaimable location, permanently locking trapped bridge funds - (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

### Summary
Snowbridge's inbound-queue v2 `MessageToXcm::prepare` accepts an attacker/relayer-controlled `claimer` field from the Ethereum-origin `Message` and, when present, decodes it verbatim into the `Location` used as the XCM `AssetClaimer` hint, with no validation of the encoded location. Only the *fallback* path (no claimer supplied) was hardened in `prdoc/stable2603-3/pr_11919.prdoc` to pin `network: Some(LocalNetwork::get())` so it matches what AssetHub's `SignedToAccountId32` origin converter produces. An explicit, attacker-chosen claimer is never checked against this constraint, so a relayer can submit a message with a syntactically valid but practically unclaimable `Location` (wrong network tag, non-account junction, or a location for which no signed origin on AssetHub can ever convert to a matching `AccountId32`). If message processing later fails (invalid XCM in `payload`, as explicitly exercised by `test_invalid_xcm` which asserts funds may be trapped), the assets are trapped by `pallet_xcm` against that exact, permanently unreachable trap-key, with no path to `claim_assets` succeeding for anyone.

### Finding Description
`MessageToXcm::prepare` in `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs` builds the `claimer` used later as the `AssetClaimer` XCM hint: [1](#0-0) 
This decodes the raw bytes supplied in `Message.claimer` (an untrusted field submitted by any relayer relaying an Ethereum event, ultimately attacker-influenced content on the Ethereum side) into an arbitrary `Location`, with only a fallback guard for the "no claimer" case. The `convert` function then places this claimer into `SetHints { hints: [AssetClaimer { location: message.claimer }] }` before executing the remote XCM on AssetHub: [2](#0-1) 

If the remote XCM subsequently fails to fully consume the holding register — which the pallet explicitly tolerates, as shown by the test asserting `assert_ok!(result.clone())` for an "invalid xcm" that would leave funds trapped — `pallet_xcm`'s trap mechanism stores the trapped assets keyed by the `AssetClaimer` location: [3](#0-2) 

The only fix that was applied (`prdoc/stable2603-3/pr_11919.prdoc`) pinned the *default fallback* claimer (when `message.claimer` is `None`) to `network: Some(LocalNetwork::get())`, matching what AssetHub's `SignedToAccountId32<_, _, LocalNetwork>` converter produces for a signed extrinsic origin, so a signed `claim_assets` call can match the trap key: [4](#0-3) [5](#0-4) 

However, the *explicit* claimer path is completely unguarded — `Location::decode` succeeds for many attacker-chosen encodings (e.g., an `AccountId32` junction with `network: None` or a mismatched network, an `AccountKey20` for which no AssetHub account can be derived by any origin converter, or a multi-junction interior location that cannot be reached by any signed extrinsic origin). This is exactly the same broken invariant as the external report: a state (recoverable trapped-fund claim) is architecturally dependent on a specific privileged actor identity/account being reachable, but the mechanism supplying that identity (`claimer` decoding) allows setting it to an identity that structurally can never sign the recovery call — permanently locking user/bridge funds, matching the "permanent user-fund lock" category in scope.

### Impact Explanation
Whenever the remote XCM constructed from the Ethereum message fails partway (malformed payload, asset-conversion errors, insufficient fees after `PayFees`, etc. — all explicitly acknowledged as non-fatal to message processing by the existing test suite), any reserve-deposited/withdrawn assets left in holding are trapped against the caller-controlled `AssetClaimer` location. If that location is chosen (deliberately or accidentally by a relayer/bridge message) to be one that cannot be produced by any signed AssetHub origin conversion, the trapped funds (ETH, WETH, or any bridged ERC-20 token value) become permanently unrecoverable — no governance override or root call exists to reconstruct the exact trap key and claim on behalf of the intended beneficiary, since `pallet_xcm::claim_assets` requires the calling origin to convert to precisely the trapped location.

### Likelihood Explanation
The `claimer` field is decoded from bytes carried in the inbound Ethereum message and is not constrained to any subset of valid/claimable locations; any relayer submitting a `process_message` call with a message whose `claimer` bytes decode into an unreachable `Location`, combined with an XCM payload that fails to fully drain holding (both independently already demonstrated as accepted, non-erroring paths in the pallet's own tests), triggers the fund lock. No validator, node, or governance compromise is required — only a permissionless relayer submitting a message with attacker-influenced fields, which matches the required "public underpriced work" / "permanent user-fund lock" impact class.

### Recommendation
Validate the decoded `claimer` `Location` against the same constraint applied to the fallback path — i.e., require that any `AccountId32` junction claimer either omits the network (and is normalized to `Some(LocalNetwork::get())`) or explicitly matches `LocalNetwork::get()`, and reject/normalize any claimer location whose junction type cannot be reached by any origin converter registered on AssetHub (e.g., disallow bare `AccountKey20` or multi-junction claimers unless a corresponding converter is proven to exist). Alternatively, always fall back to the hardened bridge-owner default when the supplied claimer cannot be round-tripped through the known origin-to-location converters used for `claim_assets`, and surface a distinct error/event so relayers cannot cause an unrecoverable trap.

### Proof of Concept
Existing test `test_invalid_xcm` at [3](#0-2)  already demonstrates that an invalid XCM payload does not fail message conversion, leaving assets in holding for possible trapping, while using an attacker-supplied `claimer` with `network: None`:
```rust
let claimer_account = AccountId32 { network: None, id: H256::random().into() };
let claimer: Option<Vec<u8>> = Some(claimer_account.clone().encode());
...
let result = Converter::convert(message);
// Invalid xcm does not break the message, allowing funds to be trapped on AH.
assert_ok!(result.clone());
```
Combining this with an execution environment where the resulting XCM leaves assets un-consumed in holding (as reproduced by the integration test `invalid_xcm_traps_funds_on_ah` at [6](#0-5) , which uses `claimer: Some(claimer_bytes)` with an arbitrary random `AccountId32 { network: None, .. }`) confirms assets are trapped against that exact caller-chosen location via `PolkadotXcm::AssetsTrapped`. Because no test or code path verifies that the explicit claimer location can be produced by a signed AssetHub origin (unlike the hardened `None`-claimer fallback validated in `test_missing_claimer_defaults_to_bridge_owner_on_local_network`), no subsequent `claim_assets` call from any real, signable account is guaranteed to match this trap key, demonstrating the fund-lock path is live for the explicit-claimer branch.

doc:
- audience: Runtime Dev
  description: |-
    The inbound-queue v2 message converter falls back to the Snowbridge sovereign
    account on AssetHub as the asset claimer when no explicit claimer is supplied.
    Previously this fallback used `AccountId32 { network: None, .. }`, which did
    not match the location AssetHub's signed-origin converter produces (it sets
    `network: Some(LocalNetwork)`). The trap-key hash stored on `AssetsTrapped`
    therefore could not be matched by a signed `polkadotXcm.claim_assets` call,
    making default-claimer trapped funds effectively unrecoverable without a
    runtime upgrade.

    This PR sets `network: Some(LocalNetwork::get())` on the fallback claimer so
    its `Location` agrees with what `SignedToAccountId32<_, _, LocalNetwork>`
    yields on AssetHub, and adds a test covering the no-claimer-supplied path.

#[test]
fn invalid_xcm_traps_funds_on_ah() {
	let relayer_account = BridgeHubWestendSender::get();
	let relayer_reward = 1_500_000_000_000u128;

	let token: H160 = TOKEN_ID.into();
	let claimer = AccountId32 { network: None, id: H256::random().into() };
	let claimer_bytes = claimer.encode();
	let beneficiary_acc_bytes: [u8; 32] = H256::random().into();

	AssetHubWestend::fund_accounts(vec![(
		sp_runtime::AccountId32::from(beneficiary_acc_bytes),
		3_000_000_000_000,
	)]);

	set_up_eth_and_dot_pool();

	let assets = vec![
		// to transfer assets
		NativeTokenERC20 { token_id: WETH.into(), value: 2_800_000_000_000u128 },
		// the token being transferred
		NativeTokenERC20 { token_id: token.into(), value: 2_000_000_000_000u128 },
	];

	BridgeHubWestend::execute_with(|| {
		type RuntimeEvent = <BridgeHubWestend as Chain>::RuntimeEvent;
		// invalid xcm
		let instructions = hex!("02806c072d50e2c7cd6821d1f084cbb4");
		let origin = EthereumGatewayAddress::get();

		let message = Message {
			gateway: origin,
			nonce: 1,
			origin,
			assets,
			payload: Payload::Raw(instructions.to_vec()),
			claimer: Some(claimer_bytes),
			value: 1_500_000_000_000u128,
			execution_fee: 1_500_000_000_000u128,
			relayer_fee: relayer_reward,
		};

		EthereumInboundQueueV2::process_message(relayer_account.clone(), message).unwrap();

		assert_expected_events!(
			BridgeHubWestend,
			vec![
				RuntimeEvent::XcmpQueue(cumulus_pallet_xcmp_queue::Event::XcmpMessageSent { .. }) => {},
				// Check that the relayer reward was registered.
				RuntimeEvent::BridgeRelayers(pallet_bridge_relayers::Event::RewardRegistered { relayer, reward_kind, reward_balance }) => {

		);
	});

		assert_expected_events!(

	});
