### Title
Reentrant account creation via attacker-controlled `<ft-trait>` transfer hook in `collateral-add` causes stale `reverse` map overwrite, permanently orphaning debt/collateral at a duplicate id - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`collateral-add` captures the caller's obligation entry (via `resolve-or-create`) and the collateral write *before* performing the external, attacker-controlled token transfer (`receive-tokens`), and only persists the entry (`insert`) *after* that external call returns. Because `resolve-or-create`/`create` allocate a new id and set `reverse[account]` only inside `insert`, a reentrant call for the same never-before-seen `account` triggered from inside the malicious `ft`'s `transfer` hook allocates a second id, legitimately deposits collateral and borrows debt against it, and commits `reverse[account]` to that second id — which the outer `collateral-add` call then overwrites back to the first id, permanently orphaning the second id's real collateral and debt.

### Finding Description
In `collateral-add` [1](#0-0) , the `let`-bindings — including `(entry (resolve-or-create account))` and `(result (add-user-collateral user-id asset-id amount))` — are evaluated **before** `receive-tokens` is called, and `(insert updated-entry)` is only called **after** `receive-tokens` returns. `receive-tokens` performs `(contract-call? asset transfer amount account current-contract none)` [2](#0-1) , where `asset` is the attacker-supplied `<ft-trait>` implementation, giving the attacker arbitrary code execution mid-function, before the outer call's `registry`/`reverse` state is committed.

`resolve-or-create` and `create` do not write any state themselves [3](#0-2) ; the `nonce` is incremented immediately via `increment`, but `registry[id]` and `reverse[account]` are only written later by `insert` [4](#0-3) . Consequently, for a brand-new account, `reverse[account]` remains unset for the entire duration of the outer `collateral-add`'s `receive-tokens` call.

Exploit flow:
1. Attacker deploys malicious `ft-A` and `ft-C` (both implementing `<ft-trait>`), and calls the market's deposit path with `ft-A`, causing `market-vault.collateral-add(account, amountA, ft-A, assetA)` to run with `contract-caller == impl` (satisfying `check-impl-auth`).
2. The outer call computes `entry = create(account)` → id `N`, `mask = 0`, writes `collateral{N, assetA} = amountA` via `add-user-collateral`, then calls `receive-tokens(ft-A, amountA, account)`.
3. Inside `ft-A`'s `transfer`, the attacker re-enters the market for the *same* `account`: first depositing real collateral C via `ft-C` (`collateral-add(account, amountC, ft-C, assetC)`), which — since `reverse[account]` is still unset — again calls `create(account)`, allocating id `N+1`, writes `collateral{N+1, assetC}`, and this nested call's own `insert` commits `registry[N+1]` and `reverse[account] = N+1`.
4. Still inside the same hook, the attacker (now legitimately collateralized at id `N+1`) triggers `debt-add-scaled(account, scaled, assetD)` through the market's borrow path. `resolve-or-create` now finds `reverse[account] = N+1` (set in step 3) and resolves to the existing id, so debt is legitimately added against real collateral, passing any health/LTV check in the market layer, and borrowed funds (`assetD`) are transferred out to the attacker.
5. The nested calls return; the outer `collateral-add` resumes with its stale, pre-captured `updated-entry` (id `N`, `mask = {collateral A}`) and calls `insert(updated-entry)`, which does `map-set reverse account N` — overwriting `reverse[account]` from `N+1` back to `N`.

Result: `registry[N+1]`, `collateral{N+1, assetC}`, and `debt{N+1, assetD}` all still exist and hold real value, but `reverse[account]` now points only to `N`. Every id-resolution path keyed off the account (`resolve`, `resolve-safe`, `get-account-scaled-debt`, `get-position`) [5](#0-4)  only ever reaches id `N`, so the real debt at `N+1` becomes permanently unreachable/unliquidatable, while collateral C and the borrowed funds already left/entered accordingly with no consistent, discoverable position backing them from the canonical account entry.

No existing check stops this: `check-impl-auth` only verifies the caller is the market implementation, which is true for every nested call (they are routed back through the legitimate market contract); there is no reentrancy guard on the vault; and the check-effects-interactions ordering (external transfer before `insert`) is the root cause.

### Impact Explanation
This matches **Critical**: protocol insolvency and permanent freezing of funds simultaneously. Debt at orphaned id `N+1` is real (backed by real collateral and real disbursed funds) but becomes permanently invisible to any account-keyed accounting/liquidation logic, meaning the protocol carries an unrecoverable, unliquidatable liability while the corresponding collateral at `N+1` is also frozen from the account's perspective (unreachable via `resolve`/`get-position`).

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: any ordinary principal can deploy an arbitrary `<ft-trait>` implementation and pass it into the market's deposit/borrow entry points, and can choose to be a brand-new account (trivial - use a fresh wallet). The only capital required is the attacker's own collateral (asset C) and repayment/borrow economics of asset D, which the attacker controls. The attack is fully repeatable per fresh account and does not require any privileged role, oracle manipulation, or DAO access.

### Recommendation
Enforce checks-effects-interactions ordering in `collateral-add` (and symmetrically audit `debt-add-scaled`/`collateral-remove`/`debt-remove-scaled`): perform `insert(updated-entry)` (and any other authoritative state commit) **before** invoking the external `receive-tokens`/`send-tokens` call, or add an explicit per-account/global reentrancy lock around vault mutation entry points so a nested call for the same account cannot execute while an outer call's obligation record is still uncommitted. Additionally, consider making `resolve-or-create`'s `create` path immediately commit the new id/`reverse` mapping atomically (single map-set) rather than deferring it to a separate `insert` call performed after unrelated external calls.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy two malicious `<ft-trait>` contracts, `ft-a` and `ft-c`, whose `transfer` function, when called with a specific `amount`/`account` sentinel, re-enters the market: first calling the market's deposit-collateral entry with `ft-c` for the same `account`, then calling the market's borrow entry for `assetD` for the same `account`.
2. From a fresh, never-used principal `account`, call the market's deposit function with `ft-a`, `amountA`, `assetA`, for `account`.
3. Assert: `(map-get? reverse account)` == `N` (the first id).
4. Assert: `debt-scaled(N+1, assetD) > 0` and `collateral(N+1, assetC) > 0`, i.e., real state exists at id `N+1`.
5. Assert: `get-account-scaled-debt(account, assetD)` returns `0` (orphaned, unreachable via canonical resolution).
6. Compute total vault outflow of `assetD` (balance delta) and compare against total discoverable scaled debt reachable via `reverse`/`registry` for `account`; show a shortfall equal to the orphaned `N+1` debt's value, demonstrating insolvency and permanent freezing of the `N+1` collateral/debt record.
