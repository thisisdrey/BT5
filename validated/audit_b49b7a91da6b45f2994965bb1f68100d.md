### Title
Non-constant-time password comparison in `RPCFastCallReadOnlyRequestHandler::try_parse_request` enables timing side-channel recovery of the RPC auth secret - (File: stackslib/src/net/api/fastcallreadonly.rs)

### Summary
The auth check at `RPCFastCallReadOnlyRequestHandler::try_parse_request` compares the caller-supplied `Authorization` header directly against the configured secret with `auth_header != password`, which is standard (non-constant-time) `String`/`&str` equality. Because comparison time (and whether the check even proceeds to byte comparison) depends on length and leading-byte match, a remote unauthenticated attacker can iteratively probe this timing signal over many `POST /v3/contracts/fast-call-read/...` requests to recover the secret without ever knowing it.

### Finding Description
`try_parse_request` reads the operator-configured `self.auth` and requires the request's `authorization` header to equal it exactly: [1](#0-0) 

`auth_header != password` compares a `&String` derived from `preamble.headers.get("authorization")` against `&String` (`password`). Rust's default `PartialEq` for `String`/`&str` first compares lengths, then does a byte-by-byte comparison of the underlying byte slices, short-circuiting (via the underlying `memcmp`-based intrinsic, which is not documented or guaranteed to run in constant time, and in practice differs subtly with matching prefix length on many implementations) rather than using a constant-time comparison primitive (e.g., `subtle::ConstantTimeEq` or `ring::constant_time::verify_slices_are_equal`). This is invoked on every request to this endpoint before any other check (content-length, content-type, body parsing), so the attacker's crafted header value is the only input that reaches the comparison, and the response (401 vs proceeding) is returned quickly and deterministically after this single comparison — no other expensive work interferes with the timing signal for failing requests.

An attacker with no knowledge of the password can:
1. Send repeated `POST /v3/contracts/fast-call-read/<addr>/<contract>/<func>` requests with `Authorization` headers of controlled length/prefix.
2. Statistically measure round-trip time distributions for headers with correct vs incorrect first N bytes and first N+1 bytes.
3. Use timing differences (length leak from the length pre-check, and per-byte leak from the comparison loop) to reconstruct `password` byte-by-byte.

This is exactly the scenario the question describes: `preamble.headers.get('authorization')` feeding into `auth_header != password` is not constant-time, so time-to-401 can correlate with the number of matching leading bytes/length, undermining the auth gate that is otherwise the sole protection for this endpoint (`let Some(password) = &self.auth else { ... }` at line 102, and `let Some(auth_header) = ... else { ... }` at line 105).

### Impact Explanation
If successfully exploited, an attacker recovers the RPC auth secret and gains full unauthenticated access to `POST /v3/contracts/fast-call-read/...`, which executes arbitrary contract-call read-only Clarity code against the node's chainstate. This is an auth-bypass on a gated endpoint — matching the Critical category "request smuggling or auth bypass." It is repeatable indefinitely, targets any node with this endpoint enabled (auth configured), and requires only network reachability to the RPC port.

### Likelihood Explanation
Preconditions: the operator must have enabled the endpoint by configuring `auth` (otherwise the endpoint 400s unconditionally at line 102-104) — this is the intended deployment configuration for any operator wanting to use this endpoint at all, so it is not an unusual precondition. The attacker needs no prior credentials, peer status, or admin role — only network access to the node's RPC port, consistent with the allowed attacker model. Practical exploitation cost depends on network jitter versus the signal size of one string comparison, which in real-world noisy network conditions can require large numbers of samples/statistical averaging to extract a robust signal; this raises the practical cost above a purely theoretical one, but the underlying code defect (non-constant-time secret comparison) is a genuine, fixable weakness rather than a false equality.

### Recommendation
Replace `auth_header != password` with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` trait or `ring::constant_time::verify_slices_are_equal` on the byte representations, after first normalizing/padding to avoid leaking length via early return. For example:
```rust
use subtle::ConstantTimeEq;
let matches = auth_header.as_bytes().ct_eq(password.as_bytes()).into();
if !matches { return Err(Error::Http(401, "Unauthorized".into())); }
```
Additionally consider hashing both values (e.g., HMAC with a random per-process key) before comparison to fully eliminate length-based leakage.

2. Construct two `HttpRequestPreamble`s with `authorization` headers of the same length as the real password: one differing at byte 0 (`"Xecr3t-password-value"`), one differing only at the last byte (`"s3cr3t-password-valuX"`).
3. Call `try_parse_request` in a tight loop (e.g., 100k iterations) for each header, measuring wall-clock time with `std::time::Instant`, discarding outliers, and comparing mean/median latency between the two groups.
4. Assert (or demonstrate) a statistically significant timing difference between "mismatch at position 0" vs "mismatch at position N-1" groups, showing the non-constant-time comparison at `stackslib/src/net/api/fastcallreadonly.rs:108` leaks positional match information.
