### Title
Out-of-bounds read via unchecked Zip64 extra-field attribute index in `CDH::local_header_offset()`/`compressed_file_size()` - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`Zip64ExtraField::attr64(int index)` indexes a flexible array `attr_[]` whose real extent is only bounded by `attr_count()` (`payload_size()/8`), but callers such as `CDH::local_header_offset()` and `CDH::compressed_file_size()` compute the index purely from which of the *other* 32-bit fields (`compressed_file_size32`, `uncompressed_file_size32`) are flagged as `0xFFFFFFFF`, never checking it against the extra field's own declared `attr_count()`.

### Finding Description
`ExtraField::find` only validates that the Zip64 extra-field header itself (`sizeof(ExtraField) + payload_size()`) fits within the `extra_fields()`/`extra_fields_length()` region of the Central Directory Header [1](#0-0) . Once found, `attr64(index)` performs a raw `attr_[index]` read/write without any bound on `index` versus `attr_count()` [2](#0-1) .

`CDH::local_header_offset()` derives `attr_no` from the ext64 flags of `uncompressed_file_size32()` and `compressed_file_size32()` and then calls `z64->attr64(attr_no)` [3](#0-2) . Likewise `compressed_file_size()` calls `z64->attr64(ziph::zfield_has_ext64(uncompressed_file_size32()))` [4](#0-3) . An attacker who controls the bytes of a jar/zip that Bazel processes with `singlejar` (e.g. a prebuilt `.jar`/`.aar` fetched from a dependency URL and later combined by `singlejar`) can set `compressed_file_size32`/`uncompressed_file_size32`/`local_header_offset32` to `0xFFFFFFFF` while providing a Zip64 extra field whose `payload_size` only actually contains 0 or 1 of the expected three 8-byte attributes. This makes the computed `attr_no` exceed the field's real `attr_count()`, so `attr64()` reads memory past the Zip64 extra field's payload — potentially past the whole `extra_fields()`/central-directory buffer boundary that `ExtraField::find` validated, since `find` only validates the *declared* field size, not the index used later.

The resulting garbage value is then trusted as a real 64-bit `local_header_offset()`, which `InputJar::LocalHeader()` uses directly as `mapped_file_.address(cdh->local_header_offset() + preamble_size_)` [5](#0-4)  to compute a pointer into the mapped input file with no visible bounds check at that call site (unlike `NextEntry`, which does call `mapped_file_.mapped(new_cdr)` for the *next* CDH pointer [6](#0-5) , but not for the derived `LocalHeader` pointer). This is analogous to the CVE's core bug class — reading/writing through an index derived from attacker data without validating it against the true bounds of the backing structure, causing memory corruption/out-of-bounds access.

### Impact Explanation
A crafted zip/jar (something that could be an external dependency artifact ingested by `singlejar`, e.g., via a build that concatenates prebuilt jars) can cause `singlejar` to compute a bogus `local_header_offset`, dereferencing outside the memory-mapped input file. This is an out-of-bounds read primitive on the builder's process, which can crash the build or, depending on how the OOB data is subsequently used (attributes, sizes copied into output), potentially leak or corrupt data written to the output jar.

### Likelihood Explanation
Requires a crafted Zip64-marked CDH with an undersized Zip64 extra field to be fed to `singlejar`'s central-directory walking code path, which is a normal part of assembling deploy/interface jars from external artifacts in a Bazel build; no privileged access or MITM is needed — it only requires an attacker-controlled jar to be a build input.

### Recommendation
Add a bound check in `Zip64ExtraField::attr64` (or at each call site) verifying `index < attr_count()` before indexing `attr_[]`, and treat a violation as a corrupt/invalid archive (fail closed) rather than reading past the field.

### Proof of Concept
A `zip_headers_test.cc`-style unit test (as an extension of the existing `EndOfCentralDirectory`/`LocalHeader` tests) can construct a `CDH` in a fixed-size byte buffer with:
- `compressed_file_size32(0xFFFFFFFF)`, `uncompressed_file_size32(0xFFFFFFFF)`, `local_header_offset32(0xFFFFFFFF)`.
- An attached `Zip64ExtraField` with `payload_size` covering only one 8-byte attribute (`attr_count()==1`).

Calling `cdh->local_header_offset()` then computes `attr_no == 2` and calls `attr64(2)`, reading 16 bytes past the single stored attribute — verifiable with ASan/valgrind by placing the `CDH`+extra-field bytes at the end of a heap allocation exactly sized to the declared field, showing a heap-buffer-overflow read.

I was not able to trace `mapped_file_.address()`/`mapped_file_.mapped()` implementations from the index (file contents for `src/tools/singlejar/mapped_file.h` were not returned by search), so I cannot fully confirm whether a later bounds check exists specifically for the `LocalHeader()` pointer dereference; this should be verified directly in that file before relying on the "no bounds check" claim as certain.
