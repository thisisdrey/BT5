### Title
Unauthenticated downgrade of a confirmed Atlas attachment via `INSERT OR REPLACE` in `insert_uninstantiated_attachment` - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`insert_uninstantiated_attachment` unconditionally executes `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)` keyed only on `hash`, with no check of the existing row's `was_instantiated` state. Because the `POST /v2/transactions` handler in `posttransaction.rs` calls this function directly for any contract-call attachment without first checking `find_attachment` (which requires `was_instantiated = 1`), any remote, unauthenticated caller who knows the plaintext content of an already-confirmed attachment (which is public — it was already served over `GET /v2/attachments/{hash}`) can resubmit it and flip the row back to `was_instantiated = 0`.

### Finding Description
The invariant the code relies on is: once an attachment's row has `was_instantiated = 1`, `find_attachment` (stackslib/src/net/atlas/db.rs:641-648) will keep serving it as resolved, since `AtlasDB::find_attachment` filters `WHERE hash = ?1 AND was_instantiated = 1`. `insert_uninstantiated_attachment` (stackslib/src/net/atlas/db.rs:511-536) is the only write path reachable from `POST /v2/transactions` for storing attachment content (via `posttransaction.rs:230-251`), and it always writes `was_instantiated = 0`, using `INSERT OR REPLACE` keyed on `hash` alone — it never checks whether a row for that `hash` already exists with `was_instantiated = 1`.

Exploit flow:
1. Node has previously confirmed an attachment (e.g., a BNS zonefile) with content `C` and `hash = Hash160(C)`, so `attachments.was_instantiated = 1` for that hash, and `GET /v2/attachments/{hash}` resolves it via `find_attachment`.
2. Since `C` was already served publicly, an attacker (any remote, unprivileged party) obtains `C`.
3. The attacker crafts and signs (using their own funded account — no special privilege needed) a `ContractCall` transaction and POSTs it to `/v2/transactions` with `attachment = C` in the JSON body (`docs/rpc/openapi.yaml` shows this endpoint has `security: []`).
4. `RPCPostTransactionRequestHandler::try_handle_request` (`posttransaction.rs:169-254`) accepts the tx into the mempool, then checks `should_keep_attachment` and calls `insert_uninstantiated_attachment(attachment)` — with no check that the hash is already instantiated.
5. The `INSERT OR REPLACE` overwrites the existing row, resetting `was_instantiated` back to `0`.
6. `find_attachment(&hash)` now returns `None` for that hash even though the content is byte-identical to what was previously confirmed and served, and `GET /v2/attachments/{hash}` starts 404ing.

No signature/secret/role is required at any step other than a normally-signed, mempool-acceptable transaction, which any user can produce.

### Impact Explanation
An unauthenticated remote party can cause a previously-resolvable, confirmed Atlas attachment (e.g., BNS zonefile content) to become unresolvable via `GET /v2/attachments/{hash}` on the target node, purely by resubmitting already-public content through `POST /v2/transactions`. This is a legitimate write to internal node state that regresses confirmed data to an "unconfirmed" state, causing a read endpoint to serve wrong results (404) for state that was in fact already confirmed/canonical. It is repeatable at will for any attachment hash the attacker knows the content of, and the attack requires no privileged role — matching the "bounded compute DoS on a read endpoint" / attachment-serving-mismatch High-severity category.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (a) the plaintext content of an already-confirmed attachment, which is public by construction (previously served over the RPC), and (b) the ability to submit one normally-valid, fee-paying, signed transaction (any account, even a fresh one making a trivial contract-call) with an `attachment` field in the JSON POST body. `/v2/transactions` is explicitly unauthenticated (`security: []`). The cost per attack is a single transaction submission, and it can be repeated for every known confirmed attachment hash on the node.

### Recommendation
In `insert_uninstantiated_attachment`, check the existing row's `was_instantiated` state before writing (e.g., `INSERT ... ON CONFLICT(hash) DO UPDATE SET content = excluded.content, created_at = excluded.created_at WHERE was_instantiated = 0`, or explicitly query `find_attachment`/`was_instantiated` first and skip/no-op if the hash is already instantiated). Alternatively, have the `POST /v2/transactions` handler in `posttransaction.rs` call `find_attachment` first and skip calling `insert_uninstantiated_attachment` if the hash is already confirmed.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/db.rs` (or `tests.rs`) test module:
1. Construct `AtlasDB` in-memory, create `Attachment::new(content)` with known bytes.
2. Call `atlasdb.insert_instantiated_attachment(&attachment)` to simulate a confirmed attachment; assert `atlasdb.find_attachment(&attachment.hash()).unwrap().is_some()`.
3. Call `atlasdb.insert_uninstantiated_attachment(&attachment)` (simulating the exact call made by `posttransaction.rs` when the same content is POSTed again in a `PostTransactionRequestBody.attachment` field).
4. Assert `atlasdb.find_attachment(&attachment.hash()).unwrap().is_none()` — the previously-confirmed attachment is no longer resolvable, confirming the downgrade. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
