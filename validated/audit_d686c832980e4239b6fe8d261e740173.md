### Title
Silent negative-balance corruption in `ExchangeCapsule.transaction()` when hardened exchange math is disabled - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The flatcoin bug is a broken invariant check in an accounting routine that is supposed to prevent a state variable from going negative but instead either lets it silently clamp to an incorrect value or underflow. `ExchangeCapsule.transaction()`, which is invoked from every bancor-style TRX/TRC10 market swap (`ExchangeTransactionActuator`), has the analogous defect: it only validates that the post-trade pool balances stay non-negative on the "hardened" code path, and performs **no bounds check at all** on the legacy/default path.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances for the two sides of an AMM-style exchange and only guards against negative results when `hardenedCalc` is true: [1](#0-0) 

```java
public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
    boolean hardenedCalc) throws ContractValidateException {
  ...
  if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
    throw new ContractValidateException("Exchange balance must be >=0 after transaction");
  }
  this.exchange = this.exchange.toBuilder()
      .setFirstTokenBalance(newFirstTokenBalance)
      .setSecondTokenBalance(newSecondTokenBalance)
      .build();
  return buyTokenQuant;
}
```

When `hardenedCalc` is `false` (the legacy path, still reachable whenever `allowHardenExchangeCalculation` is not enabled on the network, per `DynamicPropertiesStore` flag checked in `AbstractExchangeActuator`), the `if` guard is skipped entirely. This means if `ExchangeProcessor.exchange()` — which uses `double`/floating point math internally (`ExchangeProcessor.java`, `exchangeToSupply`/`exchangeFromSupply`) — ever computes a `buyTokenQuant` that exceeds the actual pool balance due to floating-point rounding, `newFirstTokenBalance` or `newSecondTokenBalance` becomes negative and is written directly into on-chain state with **no exception, no revert, and no validation**: [2](#0-1) 

This is structurally identical to the flatcoin bug: an invariant meant to prevent a critical accounting value (pool token balance / `marginDepositedTotal`) from going negative is only enforced along one branch, leaving the other branch to silently write corrupted state.

### Impact Explanation
A corrupted (negative) `firstTokenBalance`/`secondTokenBalance` in an `ExchangeCapsule` breaks the AMM pricing invariant for that pool permanently:
- Subsequent `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` calls compute ratios (`anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance`) against a corrupted balance, producing incorrect (and possibly favorably-skewed) settlement amounts for any subsequent trader — i.e., loss of funds for the pool/LPs or unbacked token issuance to a trader.
- Downstream `subtractExact`/`addExact` checks in `ExchangeWithdrawActuator`/`ExchangeInjectActuator` operate on the corrupted `long` balance, which could cause future legitimate withdrawals to permanently revert (denial of service on that exchange pair) once the negative value propagates through further arithmetic.

This matches the "unbacked balance / permanent freezing of funds" impact bar.

### Likelihood Explanation
Reaching this code requires only a normal, unprivileged `ExchangeTransactionContract` broadcast by any account (`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)`), with `allowHardenExchangeCalculation` not yet enabled by committee proposal — i.e., no special privileges are needed on the attacker side, and the vulnerable code path exists as long as the network has not activated the hardening flag. I was unable to fully confirm the current default/activation state of `allowHardenExchangeCalculation` on mainnet within the available context (its accessors exist in `DynamicPropertiesStore` and are referenced from `ProposalUtil`/`ProposalService`, indicating it is a committee-gated hard fork parameter, similar to other `allow*` flags in this codebase that default to `0`/disabled until activated by governance). This uncertainty affects whether the vulnerable branch is currently live, but the code path itself is present and unconditionally reachable when the flag is off.

### Recommendation
Perform the non-negative invariant check unconditionally in `ExchangeCapsule.transaction()`, not just when `hardenedCalc` is true:

```diff
- if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
+ if (newFirstTokenBalance < 0 || newSecondTokenBalance < 0) {
    throw new ContractValidateException("Exchange balance must be >=0 after transaction");
  }
```

Alternatively, retire the legacy (`useStrictMath=false`/non-hardened) `ExchangeProcessor` double-math path entirely and always route through `SafeExchangeProcessor`.

### Proof of Concept
Not independently executable from the available index (no build/test harness access in ask-only mode), but the defect is directly demonstrable via existing test infrastructure: `ExchangeCapsuleTest.testHardenedTransactionNegativeBalanceThrows` (lines 71-83) shows the negative-balance case is only exercised/asserted for the hardened path (`transaction(..., true, true)`); no equivalent test exists asserting the legacy path (`transaction(..., true, false)` or the 3-arg overload) rejects a negative-balance outcome, confirming the guard is absent for that branch by test-suite omission as well as by direct code inspection.       boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
