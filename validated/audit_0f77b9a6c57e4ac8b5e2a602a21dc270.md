### Title
Unbounded-cardinality HTTP metrics labels allow memory-exhaustion DoS via unauthenticated request paths - (File: framework/src/main/java/org/tron/core/services/filter/HttpInterceptor.java)

### Summary
`HttpInterceptor.doFilter` derives the `endpoint` metric label directly from the raw, attacker-controlled request path (`contextPath + request.getServletPath()`) and uses it, unsanitized and unvalidated against the set of known API routes, both as a Dropwizard metric-registry key suffix and as a Prometheus histogram label value. This mirrors the OpenTelemetry-Go `otelhttp` bug class (GHSA-rcjv-mgp8-qvmr / CVE-2023-45142): request-derived strings of effectively unbounded cardinality are fed straight into long-lived metrics storage that never evicts old series/meters.

### Finding Description
`HttpInterceptor` computes the label from the incoming request: [1](#0-0) 

and then uses this value, for both successful and failing requests, both to build Dropwizard `MetricRegistry` keys (via string concatenation, `MetricsKey.NET_API_DETAIL_*QPS/OUT_TRAFFIC + endpoint`) and as a label on a Prometheus `Histogram` (`HTTP_BYTES`, label `url`): [2](#0-1) 

`RateLimiterServlet` uses the same unvalidated `url` value as the label for another Prometheus histogram (`HTTP_SERVICE_LATENCY`): [3](#0-2) 

Both the Dropwizard `MetricRegistry` (`MetricsUtil.meterMark`) and the Prometheus client library keep one live time-series/meter object per distinct label value for the lifetime of the process — there is no LRU eviction or cap on cardinality: [4](#0-3) [5](#0-4) 

All registered HTTP endpoints in `FullNodeHttpApiService` are exact fixed paths (~139 explicit `addServlet` calls), so a legitimate request to a known route only ever produces one of a small, finite set of `endpoint` values: [6](#0-5) 

However, because `HttpInterceptor` (and `RateLimiterServlet`) compute `endpoint`/`url` from `getServletPath()` before any check that the path actually resolved to a known servlet, any request to a path that does not match one of the fixed servlet mappings still flows through the filter/servlet chain and is recorded with whatever raw path string the client supplied as the label. An unauthenticated remote client can send an arbitrary number of requests to distinct, non-existent paths (e.g. `/wallet/<random-64-char-string>`), each producing a brand-new, permanently retained metric key/series — analogous to the unbounded `http.user_agent`/`http.method` label growth in the referenced advisory.

### Impact Explanation
Every unique request path creates a permanent entry in the process-wide `MetricRegistry` map and/or a permanent Prometheus label combination in `tron:http_service_latency_seconds` / `tron:http_bytes`. Because these maps/label sets are never pruned, sustained flooding with unique, randomly generated paths grows heap usage without bound, eventually leading to `OutOfMemoryError` and node crash — a concrete denial-of-service against the FullNode HTTP API, reachable by any anonymous API client without authentication, matching the CWE-770/"node crash" impact class accepted by this scan.

### Likelihood Explanation
No authentication, signature, or special privilege is required — this is directly reachable over the public FullNode HTTP API port. The attack requires only sending a large volume of HTTP requests with distinct nonexistent paths, which is trivial to script and does not require the node operator to have configured anything unusual (metrics recording via `HttpInterceptor`/`RateLimiterServlet` is on the default request path for every HTTP call, gated only by `Metrics.enabled()`/`CommonParameter.isNodeMetricsEnable()`, which are commonly enabled in production for observability).

### Recommendation
Before using the request path as a metric label, validate it against the known/registered set of API endpoints (e.g., only record the raw path if it matched an actual `HttpServlet` mapping), and fall back to a fixed `MetricLabels.UNDEFINED`/`"unknown"` value for anything else — mirroring the fix pattern in the referenced advisory (restrict to a well-known, bounded set of values). Additionally, consider capping the maximum number of distinct label values / meters retained, or switching the per-endpoint HTTP metrics to use a small enumerated set (e.g., servlet class name) rather than raw request-derived strings.

### Proof of Concept
1. Enable HTTP API metrics (`isNodeMetricsEnable`/Prometheus metrics enabled, both defaults in typical FullNode deployments).
2. From an unauthenticated client, send a large number (e.g., hundreds of thousands) of HTTP requests to the FullNode's HTTP API port, each with a distinct, randomly generated, non-existent path, e.g. `GET /wallet/<random-64-hex-string>`.
3. Each request flows through `HttpInterceptor.doFilter` (and `RateLimiterServlet.service`), which computes `endpoint`/`url` from the raw unmatched path and records it via `MetricsUtil.meterMark(...)` and `Metrics.histogramObserve(HTTP_BYTES, ...)`.
4. Observe heap usage of the java-tron process (or the `MetricRegistry`/Prometheus registry size) grow monotonically with the number of distinct paths sent, with no eviction, eventually leading to memory exhaustion.
