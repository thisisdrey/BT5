### Title
Attacker can saturate `maxBridgedInSupply`/`maxTotalSupply` to make a victim's in-flight cross-chain credit revert, freezing bridged msSynth until the cap frees - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
In the source report, a user's async `receiveQuery()` callback reverts because a shared balance (`nativeTokenAmount`) was drained between the request and the callback. Metronome's analog lives in the LayerZero OFT path: `ProxyOFT._debitFrom()` burns on the source chain immediately, while the corresponding credit on the destination chain (`OFTCore._sendAck` → `ProxyOFT._creditTo` → `SyntheticToken.mint` → `_mint`) executes asynchronously and reverts if `bridgedInSupply() > maxBridgedInSupply` or `totalSupply > maxTotalSupply`. An unprivileged attacker can fill that headroom (by bridging in their own msSynth via `sendFrom`, or by borrowing/minting via any registered `Pool`), so a victim's already-debited inbound transfer fails and is parked in `failedMessages`. [1](#0-0) [2](#0-1) 

### Finding Description
1. Victim calls `ProxyOFT.sendFrom()` on chain A. `_debitFrom` burns `amount_` of the synthetic token immediately (`syntheticToken.burn(from_, amount_)`) and emits a LayerZero packet. The victim's funds are gone from chain A regardless of what happens on chain B. [3](#0-2) 
2. On chain B, when the LayerZero executor delivers the packet, `OFTCore._sendAck` calls `_creditTo` → `SyntheticToken.mint(toAddress_, amount_)`. Inside `_mint`, because `msg.sender` is the `proxyOFT`, `totalBridgedIn += amount_` is applied and the call reverts with `SurpassMaxBridgingSupply` if `bridgedInSupply() > maxBridgedInSupply`, and reverts with `SurpassMaxSynthSupply` if `totalSupply > maxTotalSupply`. [4](#0-3) 
3. `NonblockingLzApp._blockingLzReceive` wraps delivery in `excessivelySafeCall`; on revert it only stores `failedMessages[srcChain][srcAddress][nonce] = keccak256(payload)` and emits `MessageFailed`. The victim's tokens are neither on A (burned) nor on B (not minted). [5](#0-4) 
4. `retryMessage` is permissionless but re-executes `_nonblockingLzReceive` and reverts again while the caps remain saturated. The attacker can keep `bridgedInSupply`/`totalSupply` pinned at the cap: `totalBridgedIn` is only increased by proxyOFT mints and `totalBridgedOut` only grows on outbound burns, so the headroom does not recover unless the attacker (or governor action / other users bridging out) releases it. [6](#0-5) [7](#0-6) 

The invariant broken is bridge conservation: `_debitFrom` commits the burn on the source chain, but the mint on the destination is gated on a mutable shared counter that a third party can manipulate between send and receive.

### Impact Explanation
Temporary freezing of user funds (an accepted impact class). Any user who bridges msX while `maxBridgedInSupply - bridgedInSupply()` or `maxTotalSupply - totalSupply` headroom is smaller than their transfer amount has their tokens burned on the source chain with no credit on the destination. Recovery requires either the attacker to release cap headroom, other users bridging out (which lowers `totalSupply` but not `totalBridgedIn`), or governor raising `maxBridgedInSupply`/`maxTotalSupply` — i.e., the freeze persists as long as the attacker keeps the cap saturated.

### Likelihood Explanation
The attacker is fully unprivileged — `sendFrom` is public and `SyntheticToken.mint` via `proxyOFT` is reachable by anyone bridging their own tokens in, and `totalSupply` headroom can also be consumed by ordinary `Pool` borrowing. Cost to sustain the attack equals holding real msX (capital lockup, not burn), and chains where `maxBridgedInSupply`/`maxTotalSupply` are already close to utilization are perpetually exposed. No privileged actor, malicious endpoint, or oracle manipulation is required; `isBridgingActive`, `onlyIfSyntheticTokenIsActive`, and the reentrancy guards do not mitigate it.

### Recommendation
Do not hard-revert the mint inside `_creditTo`. Options: cap the minted amount and record the shortfall for later reconciliation, or hold inbound amounts in an escrow/pending mapping inside `ProxyOFT` that users can pull once cap headroom exists, so a temporarily saturated cap cannot wedge the burned funds. At minimum, surface `bridgedInSupply`/`totalSupply` headroom in `estimateSendFee`/frontend and alert when headroom is near zero so governance can raise caps before transfers wedge.

### Proof of Concept
Foundry fork sketch on a deployed pool/registry (e.g. optimism):

```solidity
// Setup: pick deployed poolRegistry, registered pool, msToken, proxyOFT
ISyntheticToken ms = proxyOFT.syntheticToken();
uint16 srcChain = /* chain A id */;
uint256 headroom = ms.maxBridgedInSupply() - ms.bridgedInSupply();

// Attacker fills headroom by bridging own msX from another chain,
// simulated here by calling mint from the proxyOFT slot in a fork test,
// or by borrowing via Pool so totalSupply hits maxTotalSupply.
vm.prank(address(proxyOFT));
// (in a real scenario the attacker sends sendFrom() on the other chain)
// ms.mint(attacker, headroom); // -> bridgedInSupply() == maxBridgedInSupply

// Victim's in-flight packet: nonce N, payload = abi.encode(PT_SEND, to, amount)
bytes memory payload = abi.encode(uint16(0), abi.encodePacked(victim), amount);

// Simulate LZ delivery on chain B
vm.prank(address(lzEndpoint));
proxyOFT.lzReceive(srcChain, abi.encodePacked(address(proxyOFT)), nonce, payload);

// Assert: mint reverted with SurpassMaxBridgingSupply internally,
// message stored in failedMessages, victim received nothing.
assertEq(ms.balanceOf(victim), 0);
assert(proxyOFT.failedMessages(srcChain, srcAddr, nonce) != bytes32(0));

// retryMessage reverts while attacker keeps the cap saturated
vm.expectRevert();
proxyOFT.retryMessage(srcChain, srcAddr, nonce, payload);
```

The test demonstrates end-to-end that a debit committed on the source chain cannot be credited on the destination while an unprivileged actor saturates `maxBridgedInSupply`/`maxTotalSupply`, freezing the bridged funds for the duration of the saturation.

```text
    function _mint(address account_, uint256 amount_) private onlyIfSyntheticTokenIsActive {
        if (account_ == address(0)) revert MintToTheZeroAddress();

        address _msgSender = _msgSender();

        if (_isMsgSenderProxyOFT(_msgSender)) {
            totalBridgedIn += amount_;
            if (bridgedInSupply() > maxBridgedInSupply) revert SurpassMaxBridgingSupply();
        } else if (_isMsgSenderAmo(_msgSender)) {
            amoSupply += amount_;
            if (amoSupply > maxAmoSupply) revert SurpassMaxAmoSupply();
        }

        totalSupply += amount_;
        if (totalSupply > maxTotalSupply) revert SurpassMaxSynthSupply();
        balanceOf[account_] += amount_;
        emit Transfer(address(0), account_, amount_);
```

```text
    function retryMessage(
        uint16 _srcChainId,
        bytes calldata _srcAddress,
        uint64 _nonce,
        bytes calldata _payload
    ) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
```
