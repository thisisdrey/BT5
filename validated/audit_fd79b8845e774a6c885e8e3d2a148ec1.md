### Title
Dust-transfer griefing fills victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER`, permanently blocking new deposits and issuances (resource-exhaustion DoS) - (File: contracts/DepositToken.sol)

### Summary
The Metronome analog of CVE-2016-8826's "user-triggered resource exhaustion DoS" is the per-account token-list cap in `Pool`. Any unprivileged user can push dust amounts of `DepositToken` to a victim, and each first-time receipt appends the token to `depositTokensOfAccount[victim]` via `Pool.addToDepositTokensOfAccount`. Once the combined debt+deposit list reaches `MAX_TOKENS_PER_USER = 30`, every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, which bricks `DepositToken.deposit`, `DepositToken.transfer`/`transferFrom` to the victim, `DebtToken.issue`, liquidations seizing into the victim's account (`seize` → `_transfer`), and `SmartFarmingManager.leverage` for any token type the victim does not already hold. There is no way for the victim to remove these entries — removal requires the attacker's dust balance to go to zero, which only the attacker controls.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30` caps `debtTokensOfAccount.length + depositTokensOfAccount.length` per account (`onlyIfAdditionWillNotReachMaxTokens`, `contracts/Pool.sol:143-148`).
- `DepositToken._transfer` and `_mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is 0 and `amount_ > 0` (`contracts/DepositToken.sol:517-520`, `:485-488`).
- `transfer`/`transferFrom` only check the *sender's* locked balance (`_revertIfLocked(sender_, amount_)`, `contracts/DepositToken.sol:350`, `:362`); there is no opt-in, no minimum amount, and no way for a recipient to reject or purge entries.
- Removal only happens in `_burn`/`_transfer` when the holder's balance reaches 0 and calls `pool.removeFromDepositTokensOfAccount` (`contracts/DepositToken.sol:460-462`, `:523-525`), which the victim cannot trigger for dust the attacker sent — actually the victim *can* transfer the dust away, but only by spending gas per token (up to 30 transactions), and the attacker can re-fill at will, making this a persistent, repeatable griefing "storm" analogous to the interrupt storm.
- `DebtToken._mint`/`issue` likewise calls `pool.addToDebtTokensOfAccount` when balance goes 0→nonzero (`DebtToken.sol`), so a victim already using several debt+deposit tokens needs fewer attacker transfers to be frozen.

Trace: attacker deposits minimal underlying into each pool `DepositToken` (or obtains dust via `transfer`), then calls `depositToken.transfer(victim, 1)` for each token → `Pool.addToDepositTokensOfAccount(victim)` appends each → once `length == 30`, `depositToken.deposit(amount, victim)`, `debtToken.issue(...)`, `pool.liquidate(...)` seizing a new token type into victim, and any inbound `transfer` of a new token type all revert with `UserReachedMaxTokens`. None of `whenNotPaused`/`whenNotShutdown`/`nonReentrant`/`onlyIfDepositTokenExists` stop it; the cap modifier is the very mechanism exploited.

### Impact Explanation
Permanent freezing of position-management capability: the victim cannot deposit any collateral type not already in their list, cannot mint new debt-token types, and cannot receive seized collateral of a new type (a liquidation that would credit a new deposit token reverts, which can also block liquidations of accounts near the cap — a secondary bad-debt vector). The victim must spend gas to transfer each dust token out (up to 30 txs) to recover, and the attacker can re-grief. If the victim holds debt and needs a new collateral type to restore health, they are forced toward liquidation — denial of service on a core protocol function from an unprivileged account.

### Likelihood Explanation
Cost is bounded and low: attacker needs 1 wei (post-fee dust) of each of up to N deposit tokens — obtainable by depositing minimal underlying, or even free if dust is already held. No privileged role, oracle manipulation, or timing is required; the attack works on the deployed configuration on any chain where pool deposit tokens exist. Success depends only on the victim having fewer than 30 − (available deposit+debt tokens) list slots.

### Recommendation
- Make list membership opt-in or recipient-agnostic: e.g. only add on `deposit()`/`issue()` (mint path), not on ERC20 `transfer`, since transferred receipts can be recomputed via `balanceOf` checks at use sites.
- Alternatively, allow permissionless removal: let anyone call a `sweepDust`-style function that burns/transfers a zero-value entry, or track membership implicitly instead of enforcing a hard per-account cap.
- If keeping the cap, revert on `add` only for the actor's own actions — i.e. exempt inbound transfers (recipient didn't opt in) or let the transfer succeed while skipping list insertion.

### Proof of Concept
Hardhat fork sketch (pool deployed with ≥N deposit tokens `d0..dK`):

```ts
// attacker acquires dust of each deposit token
for (const dt of depositTokens) {
  await underlying(dt).mint(attacker, dustIn);
  await underlying(dt).connect(attacker).approve(dt.address, dustIn);
  await dt.connect(attacker).deposit(dustIn, attacker.address); // mints msToken
}

// storm: fill victim's list (victim starts with 0 entries)
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();
for (let i = 0; i < Math.min(max, depositTokens.length); i++) {
  await depositTokens[i].connect(attacker).transfer(victim.address, 1);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(
  Math.min(max, depositTokens.length)
);

// victim cannot deposit a collateral type not already held
await underlying0.mint(victim.address, amount);
await underlying0.connect(victim).approve(dtNew.address, amount);
await expect(
  dtNew.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot issue a new debt-token type either
await expect(
  debtTokenNew.connect(victim).issue(1, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot be sent a new deposit token; only recovery is 30 transfer-outs,
// and attacker can re-fill at any time
await expect(
  depositTokens[0].connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Key code: `Pool.sol:79` (`MAX_TOKENS_PER_USER`), `Pool.sol:143-148` (cap modifier), `Pool.sol:204-220` (`addTo*TokensOfAccount`), `DepositToken.sol:348-376` (`transfer`/`transferFrom`), `DepositToken.sol:517-525` (list add/remove in `_transfer`), `DepositToken.sol:485-488` (list add in `_mint`).

Caveat: whether this clears the strict "temporary/permanent freezing of funds" bar depends on judging — the victim's existing deposits remain withdrawable, but all new deposits/issuances and liquidations crediting new token types are bricked until the victim manually ejects dust entries, and re-griefing is trivial.
