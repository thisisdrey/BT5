Audit Report

## Title
Snowbridge relayer reward is marked paid and deleted before the cross-chain settlement XCM is confirmed to execute - permanent reward loss on downstream failure - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`PayAccountOnLocation::pay_reward` treats successful queuing/delivery of an outbound XCM (`validate_send` + `charge_fees` + `XcmSender::deliver`) as final settlement, returning `Ok(())` without any knowledge of whether the `ReserveAssetDeposited`/`DepositAsset` instructions actually execute successfully on AssetHub. `do_claim_rewards` in the relayers pallet then irrevocably deletes the `RelayerRewards` entry and emits `RewardPaid` based solely on that premature `Ok(())`, with no rollback path if the destination-side deposit later fails or traps the asset.

## Finding Description
`do_claim_rewards` takes the reward out of `RelayerRewards` via `try_mutate_exists`, calls `T::PaymentProcedure::pay_reward(...)`, and only rolls back the storage mutation on `Err` — otherwise it deletes the entry and emits `Event::RewardPaid` immediately: [1](#0-0) 

For `BridgeReward::Snowbridge`, the runtime routes the claim through `PayAccountOnLocation::pay_reward`, which builds an XCM containing `UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, and `DepositAsset { assets: AllCounted(1).into(), beneficiary }`, validates it, charges delivery fees, and hands the ticket to `XcmSender::deliver`. The function returns `Ok(())` as soon as delivery succeeds, without any acknowledgment of execution on AssetHub: [2](#0-1) 

This is confirmed by the crate's own error type, which explicitly frames the only two failure modes as *sending* problems, not execution problems: [3](#0-2) 

Because `pay_reward` signals success purely on message delivery, `do_claim_rewards` has no way to distinguish "delivered and about to execute" from "actually settled." If the destination-side `DepositAsset` fails (e.g., beneficiary account not meeting a foreign asset's sufficiency/ED requirements, insufficient execution weight, or any other XCM-execution-time failure) after delivery has already succeeded, the assets are trapped or lost on AssetHub while BridgeHub has already deleted the `RelayerRewards` entry and emitted `RewardPaid`. There is no re-credit, reconciliation, or receipt-based rollback mechanism between the two chains for this path.

## Impact Explanation
This matches the "duplicate/asymmetric settlement" and "permanent bridge-state lock" impact categories in the Required Impacts gate: BridgeHub's local ledger records the reward as paid (`RelayerRewards` entry deleted, `RewardPaid` emitted) while the actual value transfer to the beneficiary on AssetHub can fail, permanently and unrecoverably losing the relayer's earned reward with no compensating state anywhere. The corrupted value is the `RelayerRewards` storage entry for the affected relayer/reward-kind pair, which is deleted despite the beneficiary never actually receiving the minted reward asset.

## Likelihood Explanation
No privileged access or malicious actor is required — a relayer using the standard, public `claim_rewards_to` extrinsic path triggers this whenever the AssetHub-side execution of the `ReserveAssetDeposited`/`DepositAsset` sequence fails for an ordinary reason (asset-sufficiency/ED constraints, execution weight shortfalls, congestion, or configuration changes on the `ForeignAssets` pallet) after BridgeHub has already treated the message as delivered. This is a structural design gap in the payment procedure rather than an edge case requiring adversarial behavior, though it is conditioned on downstream execution failure, which BridgeHub cannot observe or control at the point `pay_reward` returns.

## Recommendation
Do not treat `XcmSender::deliver` success as final settlement in `PayAccountOnLocation::pay_reward`. Either (a) require a delivery/execution confirmation receipt from AssetHub before removing the `RelayerRewards` entry on BridgeHub, or (b) keep the reward in a retryable/pending state that can be reclaimed if the destination-side execution is later observed (via events or a receipt XCM) to have failed or trapped the assets — ensuring `RelayerRewards` state only advances after decode, dispatch, execution, and settlement succeed atomically, consistent with the payout-atomicity pivot.

## Proof of Concept
1. A relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. The relayer calls `claim_rewards_to` with a valid `AssetHubLocation` beneficiary that will fail to receive the `DepositAsset` at execution time on AssetHub (e.g., an account failing the foreign asset's minimum-balance/sufficiency requirement).
3. On BridgeHub: `do_claim_rewards` → `PayAccountOnLocation::pay_reward` returns `Ok(())` because `validate_send`, `charge_fees`, and `XcmSender::deliver` all succeed (message merely queued). The `RelayerRewards` entry is deleted and `RewardPaid` is emitted per [1](#0-0) .
4. On AssetHub: the `ReserveAssetDeposited`/`DepositAsset` sequence fails or traps the asset instead of crediting the beneficiary.
5. Result: the relayer's reward is irrecoverably gone from BridgeHub storage (subsequent claims fail with `NoRewardForRelayer`) and was never actually delivered on AssetHub, demonstrating permanent reward loss without any malicious actor involved.

/// Error related to paying out relayer rewards.
#[derive(Debug, Encode, Decode)]
pub enum RewardPaymentError {
	/// The XCM to mint the reward on AssetHub could not be sent.
	XcmSendFailure,
	/// The delivery fee to send the XCM could not be charged.
	ChargeFeesFailure,
}

impl From<RewardPaymentError> for DispatchError {
	fn from(e: RewardPaymentError) -> DispatchError {
		match e {
			XcmSendFailure => DispatchError::Other("xcm send failure"),
			ChargeFeesFailure => DispatchError::Other("charge fees error"),
		}
	}
}

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
