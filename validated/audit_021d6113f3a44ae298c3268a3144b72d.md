Based on my research, I found a strong analog in Gitaly's `UserCommitFiles` RPC, which accumulates and processes an unbounded number of user-supplied "actions" without any limit on their count — closely mirroring the Mermaid bug's pattern of an unbounded number of individually-valid units causing aggregate resource exhaustion.

### Title
Unbounded Resource Consumption via Unlimited Actions in UserCommitFiles RPC - (File: internal/gitaly/service/operations/commit_files.go)

### Summary
The `UserCommitFiles` RPC accepts a client-controlled stream of `UserCommitFilesRequest` messages, each carrying one file "action" (create/update/move/delete/chmod/create_dir). The handler buffers every action from the stream into an in-memory slice (`pbActions`) with no upper bound on the number of actions, and then sequentially applies each one to an in-memory tree structure (`root.Modify`/`Add`/`Delete`), writing a Git blob object per action along the way.

### Finding Description
In `userCommitFiles`, the receive loop reads action messages until `io.EOF` and appends every one of them to `pbActions` unconditionally: [1](#0-0) . There is no cap on the number of actions per RPC call, nor on the total content size across all actions — only individual field-level validation (e.g., `validatePath`) is performed per action.

After the stream ends, every buffered action is converted and processed: for `CREATE`/`UPDATE`/`MOVE` actions, a Git blob is written per action via `quarantineRepo.WriteBlob` [2](#0-1) [3](#0-2) , and then `applyAction` is called once per entry against the shared in-memory tree (`root`) to mutate the tree structure [4](#0-3) . Each call to `root.Modify`, `root.Add`, or `root.Delete` walks/mutates the tree entry structure, so the aggregate cost scales with the number of actions.

This is structurally the same pattern as the Mermaid DoS bypass: a per-unit safeguard exists (path validation, individual blob writes), but there is no aggregate ceiling on the number of units (actions) that a single request can supply, allowing the attacker to split a large workload into many small, individually-valid pieces that together exhaust CPU/memory/time on the server.

### Impact Explanation
An authenticated user with write access to a repository (an ordinary contributor, which the RPC annotations mark as `MUTATOR`/`REPOSITORY`-scoped, reachable via normal `UserCommitFiles` client calls e.g. from the Web IDE or API) can submit a single `UserCommitFiles` stream with an extremely large number of small actions (e.g., hundreds of thousands of one-byte file creates/updates/moves). Because there is no limit on the number of actions or on cumulative processing, this can consume excessive CPU and memory on the Gitaly node while building the tree and writing blobs, potentially blocking or slowing the RPC handler and the git objects being written, resulting in denial of service for that Gitaly node/repository shard.

### Likelihood Explanation
Likelihood is moderate-to-high: the RPC is reachable by any user with write access to a project (a common, unprivileged capability), requires no special conditions, and the vulnerable code path (unbounded buffering and per-action tree mutation) is exercised on every call. Gitaly's generic concurrency-limiting backpressure (`doc/backpressure.md`) can only throttle concurrent RPCs, not the cost of a single oversized RPC, so it does not mitigate this specific pattern.

### Recommendation
Enforce a maximum number of actions (and/or maximum aggregate content size) per `UserCommitFiles` stream, rejecting the request early (e.g., in the receive loop) once the threshold is exceeded, similar to how GitLab capped Mermaid code-block character counts and later added a cap on the number of blocks. Consider also bounding total processing time/resources for tree-building operations proportional to configured limits.

### Proof of Concept
1. As an authenticated user with push access to a repository, open a gRPC stream to `OperationService/UserCommitFiles`.
2. Send the required `UserCommitFilesRequestHeader` as the first message.
3. Send a very large number (e.g., 500,000) of small `UserCommitFilesAction` messages (each a `CREATE` header for a unique path plus a few bytes of content).
4. Close the stream and observe that Gitaly buffers all actions in memory [1](#0-0) , then sequentially writes a blob per action and mutates the in-memory tree for each one [5](#0-4) , consuming disproportionate CPU/memory/time on the Gitaly node compared to the size of any individual request field.

	actions := make([]commitAction, 0, len(pbActions))
	for _, pbAction := range pbActions {
		if _, ok := gitalypb.UserCommitFilesActionHeader_ActionType_name[int32(pbAction.header.GetAction())]; !ok {
			return structerr.NewInvalidArgument("NoMethodError: undefined method `downcase' for %d:Integer", pbAction.header.GetAction())
		}

		path, err := validatePath(repoPath, string(pbAction.header.GetFilePath()))
		if err != nil {
			return structerr.NewInvalidArgument("validate path: %w", err)
		}

		content := io.Reader(bytes.NewReader(pbAction.content))
		if pbAction.header.GetBase64Content() {
			content = base64.NewDecoder(base64.StdEncoding, content)
		}

		switch pbAction.header.GetAction() {
		case gitalypb.UserCommitFilesActionHeader_CREATE:
			blobID, err := quarantineRepo.WriteBlob(ctx, content, localrepo.WriteBlobConfig{
				Path: path,
			})
			if err != nil {
				return fmt.Errorf("write created blob: %w", err)
			}

			actions = append(actions, createFile{
				OID:            blobID.String(),
				Path:           path,
				ExecutableMode: pbAction.header.GetExecuteFilemode(),
			})
		case gitalypb.UserCommitFilesActionHeader_CHMOD:
			actions = append(actions, changeFileMode{
				Path:           path,
				ExecutableMode: pbAction.header.GetExecuteFilemode(),
			})
		case gitalypb.UserCommitFilesActionHeader_MOVE:
			prevPath, err := validatePath(repoPath, string(pbAction.header.GetPreviousPath()))
			if err != nil {
				return structerr.NewInvalidArgument("validate previous path: %w", err)
			}

			var oid git.ObjectID
			if !pbAction.header.GetInferContent() {
				var err error
				oid, err = quarantineRepo.WriteBlob(ctx, content, localrepo.WriteBlobConfig{
					Path: path,
				})
				if err != nil {
					return err
				}
			}
			actions = append(actions, moveFile{
				Path:    prevPath,
				NewPath: path,
				OID:     oid.String(),
			})
		case gitalypb.UserCommitFilesActionHeader_UPDATE:
			oid, err := quarantineRepo.WriteBlob(ctx, content, localrepo.WriteBlobConfig{
				Path: path,
			})
			if err != nil {
				return fmt.Errorf("write updated blob: %w", err)
			}

			actions = append(actions, updateFile{
				Path: path,
				OID:  oid.String(),
			})
		case gitalypb.UserCommitFilesActionHeader_DELETE:
			actions = append(actions, deleteFile{
				Path: path,
			})
		case gitalypb.UserCommitFilesActionHeader_CREATE_DIR:
			actions = append(actions, createDirectory{
				Path: path,
			})
		}
	}
