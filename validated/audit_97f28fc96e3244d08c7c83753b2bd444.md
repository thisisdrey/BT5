## Analysis

CVE-2025-30402 describes a heap-buffer-overflow while ExecuTorch parses attacker-supplied serialized binary data during "loading of methods," with no bounds validation of length/offset fields taken directly from the untrusted blob. The closest analog in Bazel's own code is the ZIP/JAR **central directory entry parser** used by `ijar` (the interface-jar generator that Bazel invokes as a build action whenever a `.jar` dependency — including one fetched from an external, attacker-controlled source such as an `http_jar`/`http_archive` mirror or a Maven artifact — is consumed by a build).

### Title
Heap-buffer-overflow when parsing an attacker-crafted JAR/ZIP central directory entry - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from a ZIP/JAR central directory entry and advances the parsing cursor `p` by these attacker-controlled values without ever validating that the resulting position stays within the bounds of the mapped input file or even within the (already length-validated) central directory region.

### Finding Description
`FindZipCentralDirectory` bounds-checks only the *aggregate* central directory: `cd.central_dir_offset + cd.central_dir_size > in_length` is rejected [1](#0-0) . It does not validate the size of any individual entry inside that region.

Per-entry parsing in `ProcessCentralDirEntry` then blindly trusts the three 16-bit length fields taken from the entry and advances `p` unconditionally: [2](#0-1) [3](#0-2) 

Unlike the analogous local-file-header parser `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before consuming `file_name_length_`/`extra_field_length_` bytes [4](#0-3) , `ProcessCentralDirEntry` has no equivalent check for `file_name_length`, `extra_field_length`, or `file_comment_length`. A crafted entry can declare a `file_name_length`/`extra_field_length` up to `0xFFFF` (or a Zip64 extra-field value up to 64-bit) that is far larger than the bytes actually remaining in the mapped file, pushing `p` past the end of the `mmap`'d input (`zipdata_in_`/`central_dir_`, mapped via `MappedInputFile`). Subsequent `get_u2le`/`get_u4le`/`get_u8le` reads (including the extra-field-loop reads at line 527-528 and the next-entry signature check on the following `ProcessNext()` iteration) then dereference memory outside the mapped region — an out-of-bounds heap read that ASan flags as heap-buffer-overflow, matching the ExecuTorch analog's bug class exactly.

### Impact Explanation
This code runs inside `ijar`, which Bazel invokes as an ordinary build action to generate interface jars from `.jar` inputs, including externally fetched jar dependencies. An attacker who controls the bytes of a dependency jar (e.g., publishes a malicious version at a `http_jar`/`http_archive` URL, or a Maven coordinate resolved by a build) can craft a ZIP central directory entry whose length fields drive the parser arbitrarily far past the mapped file, causing an out-of-bounds heap read. This can crash the build (denial of service) and, depending on adjacent heap layout, leak adjacent process memory bytes into fields that get copied into the parsed `filename` buffer and subsequently observable in build output/errors.

### Likelihood Explanation
No integrity/checksum mechanism is relevant here: the pinned `sha256`/`integrity` value simply confirms the developer received exactly the bytes the attacker (as the legitimate publisher of that dependency version) chose to publish; it does nothing to prevent the *parsing logic bug* from being triggered by a well-formed-but-malicious ZIP structure. Any project consuming an externally-hosted or third-party-published `.jar` as a build dependency is exposed whenever `ijar` processes it, which is a very common, unattended part of ordinary Bazel Java builds.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` (mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`) to ensure `p + file_name_length`, `p + extra_field_length`, and `p + file_comment_length` never exceed the mapped input file's end (or the bounded central directory region) before advancing the cursor or dereferencing subsequent fields, and fail parsing with an error rather than continuing past validated bounds.

### Proof of Concept
A JUnit/shell reproduction would craft a minimal ZIP file containing:
1. A single local file header, and
2. A central directory entry with a valid `CENTRAL_FILE_HEADER_SIGNATURE` but `file_name_length` (and/or `extra_field_length`) set to `0xFFFF`, while the actual remaining bytes to the computed end-of-central-directory are only a handful of bytes (still satisfying `FindZipCentralDirectory`'s aggregate `central_dir_offset + central_dir_size <= in_length` check).

Running this file through `ijar` (`third_party/ijar/zip_main.cc`'s `extract`/interface-jar generation path, which calls `ZipExtractor::Create` → `InputZipFile::Open` → `ProcessNext` → `ProcessCentralDirEntry`) under AddressSanitizer reproduces a heap-buffer-overflow read when the cursor is advanced past the mapped file's end and dereferenced by the subsequent `get_u2le`/`get_u4le` calls, analogous to the existing extraction bound tests in `src/test/shell/bazel/starlark_repository_test.sh` (e.g. `test_extract_non_readable_file_zip`) but with a corrupted-length central directory entry instead of a valid one. bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
