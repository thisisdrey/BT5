## Analysis

The bug class in M-19 is: a strategy contract hard-depends on an external price-oracle call with no fallback, and if that external oracle degrades/is deprecated, the resulting price-derived health/settlement check unconditionally reverts, permanently locking user funds.

Zest Protocol has a structurally identical single point of failure: the `CALLCODE-STSTX` price transformation used for `ststx`/`zststx` collateral and debt.

### Title
Hard dependency on a single external stSTX-ratio oracle with no fallback path can permanently lock stSTX-related collateral/debt - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Any asset registered with the `CALLCODE-STSTX` or `CALLCODE-ZSTSTX` callcode (i.e. `ststx` and `zststx`) requires a mandatory external call to a single hardcoded contract, `'SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2`, via `call-ststx-ratio`, in order to resolve a price. There is no fallback price source and no way to bypass this dependency once an account's egroup includes such an asset.

### Finding Description
`resolve-ststx` unconditionally calls the external ratio oracle and propagates any failure as `ERR-ORACLE-CALLCODE`: [1](#0-0) 

`resolve-callcode` routes both `CALLCODE-STSTX` and `CALLCODE-ZSTSTX` through this same single external dependency, with `CALLCODE-ZSTSTX` compounding it with the liquidity-index transform: [2](#0-1) 

`price-resolve` propagates any `resolve-callcode` failure with `try!`, so a single failing callcode aborts the entire resolution for that asset: [3](#0-2) 

`price-multi-resolve`/`iter-price-multi` fold over *all* assets in a user's egroup mask and mark the whole batch invalid (`ERR-ORACLE-MULTI`) if any single asset's price resolution fails: [4](#0-3) 

This multi-resolution feeds `get-notional-evaluation`, which underlies the health checks used by `borrow`, `collateral-remove` (debt path), and liquidation. In `collateral-remove`, when the position has debt, `get-assets`/`get-notional-evaluation` is invoked and any oracle failure propagates via `try!`/`unwrap!`, reverting the entire withdrawal: [5](#0-4) 

The external ratio contract is a single hardcoded principal with no admin-settable fallback, no staleness/circuit-breaker degrade-to-Chainlink-equivalent path, and no way for the DAO to reroute price resolution to an alternate source without a full contract upgrade (redeploying `market.clar`, which requires a new implementation and timelocked DAO migration). This directly mirrors the M-19 root cause — a hard dependency on an external price source that can become deprecated/unreliable, with the code reverting outright instead of degrading gracefully to a fallback.

### Impact Explanation
If the external stSTX-ratio contract becomes deprecated, paused, migrated, or otherwise starts reverting or returning errors (analogous to Balancer deprecating its oracle), then for every account holding `ststx` or `zststx` as collateral or debt while also carrying any debt:
- `borrow` reverts (health check requires notional evaluation across the full egroup asset set).
- `collateral-remove` reverts for the debt-bearing path, since price resolution across the egroup mask is mandatory.
- Liquidation of the position also depends on the same price resolution path for a position's enabled collateral.

Because the failure is an unconditional `try!`/`unwrap!` propagation with no fallback price, affected users' collateral and any accrued yield become permanently frozen — they cannot withdraw, repay to reduce exposure, or be resolved through normal liquidation. This is a temporary/permanent freezing of user funds (and yield accrued on frozen positions), matching the in-scope High/Critical impact class (permanent freezing of funds).

### Likelihood Explanation
The likelihood mirrors the real-world precedent cited in the report: single external dependencies used for price derivation (whether Balancer's deprecated oracle or Stacks' `block-info-nakamoto-ststx-ratio-v2`) are subject to upstream deprecation, migration, or governance decisions outside Zest's control. Since this is a hardcoded, non-upgradable-without-full-redeploy dependency baked into `market.clar`'s private functions, any degradation of that specific upstream contract directly and unavoidably locks affected positions — there is no in-protocol mitigation (no deviation-based fallback to a secondary price source, no pause-and-resume with alternate pricing).

### Recommendation
- Add a fallback/secondary price source for the stSTX ratio (e.g., a DAO-configurable oracle-of-last-resort) so that a single external dependency failure does not unconditionally block health checks.
- Consider bounding failures with a grace/degrade mode: if the ratio oracle call fails or is stale beyond a threshold, allow using a cached last-known-good ratio (with appropriate staleness bounds) rather than reverting outright, similar to the recommendation to use Chainlink price instead of reverting in the original report.
- Make the external ratio-oracle contract address DAO-updatable without requiring a full market contract migration, to allow rapid response if the dependency is deprecated.

### Proof of Concept
1. User deposits `ststx`/`zststx` as collateral and borrows another asset, entering an egroup mask that includes the stSTX asset.
2. The external contract `'SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2` becomes deprecated/paused/migrated (out of Zest's control) and its `get-ststx-ratio-v3` call starts failing or returning stale/invalid data such that `call-ststx-ratio` errors.
3. Any subsequent call to `collateral-remove` (with debt), `borrow`, or health-check-gated liquidation for this user's position triggers `get-notional-evaluation` → `price-multi-resolve` → `price-resolve` → `resolve-callcode` → `resolve-ststx`, which fails and propagates `ERR-ORACLE-CALLCODE`/`ERR-ORACLE-MULTI` up through `try!`.
4. The transaction reverts unconditionally; the user cannot withdraw collateral, repay debt to improve health, or have the position normally liquidated — funds are locked as long as the external dependency remains broken.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
