### Title
Permanent freezing of user-frozen TRX at the deterministic TIP-2935 system address on activation - ([File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java])

### Summary
The Munchables incident exploited a state-manipulation flaw in an upgradeable contract: an attacker used privileged storage-write access before the implementation was "locked down" to plant a self-assigned balance that later was cashed out once the contract looked legitimate. The structural analog in java-tron is `HistoryBlockHashUtil.deploy()`: a hard-coded, publicly known account address (`HISTORY_STORAGE_ADDRESS`) is converted in place from a normal account to an unowned `Contract`-type account at proposal-activation time. Any unprivileged user who pre-stages state (self-frozen TRX) at that address before activation has that state carried over into a contract account that no private key ever controls, rendering the TRX unfreezable/unrecoverable forever.

### Finding Description
`HISTORY_STORAGE_ADDRESS` is a fixed constant known to anyone reading the code long before the corresponding TIP-2935 proposal is approved by the committee: [1](#0-0) 

Because it is just a normal 21-byte TRON address, any unprivileged transaction broadcaster can send transactions to it today — most importantly, they can call `FreezeBalanceV2Actuator`/`FreezeBalanceV2Processor` naming this address as `ownerAddress`, since freeze validation only checks that the address is well-formed and has enough balance, not that it is "special": [2](#0-1) [3](#0-2) 

When the TIP-2935 proposal later activates, `HistoryBlockHashUtil.deploy()` is invoked from `ProposalService` during maintenance-time block processing. If an account already exists at the canonical address (e.g., because someone froze TRX there), the code mutates it **in place**: it only flips the account type to `Contract` and clears delegated-resource bookkeping, explicitly preserving "balance/asset state," but the deploy path never rejects, refunds, or unfreezes any self-frozen `FrozenV2` balance that the pre-existing account may be holding: [4](#0-3) 

After this conversion, the address is a `Contract`-type account executing fixed, immutable system bytecode with no associated private key (`HISTORY_DEPLOYER_ADDRESS` is only used as an `originAddress` metadata field, not a signer for this address). Any TRX previously frozen there via `FreezeBalanceV2Contract` can only be recovered through `UnfreezeBalanceV2Actuator`, which requires a validly signed transaction from the `ownerAddress` — impossible for a contract address with no key: [5](#0-4) 

This mirrors the Munchables root cause at a structural level: state that an unprivileged actor can plant ahead of time survives a subsequent "upgrade" event (implementation swap / account-type conversion) performed by a privileged process, and the post-upgrade code has no mechanism to validate or reconcile that pre-staged state, resulting in value that is provably no longer recoverable by anyone.

### Impact Explanation
Any TRX frozen by any user at `HISTORY_STORAGE_ADDRESS` before the TIP-2935 proposal activates becomes permanently locked: the account converts to a keyless `Contract` account, so no unfreeze transaction can ever be validly signed for it. This is a concrete, permanent freezing-of-funds condition triggerable by ordinary users with no special privilege, satisfying the required "permanent freezing of funds" impact bar. It also permanently corrupts the deployed system contract's resource/vote/weight accounting (frozen balances contribute to `TotalNetWeight`/`TotalEnergyWeight` and vote power) tied to an address the protocol did not intend to hold any economic state.

### Likelihood Explanation
The address is a compile-time constant, publicly visible in the open-source repository well before any committee vote on the corresponding proposal activates it, so any user (or bot) can pre-fund/freeze it at will using a normal, unprivileged `FreezeBalanceV2Contract` transaction — no special access, timing race with miners, or insider knowledge is required beyond reading the source. The only precondition is that the proposal for `AllowTvmPrague`/TIP-2935 has not yet activated network-wide, which is the normal window between code release and committee activation.

### Recommendation
Before converting a pre-existing account to `Contract` type in `HistoryBlockHashUtil.deploy()`, explicitly detect and reject (or safely unwind) any economically meaningful pre-existing state beyond a stray TRX balance — specifically `FrozenV2` self-frozen balances, `TronPower`, votes, and delegated-resource records — either by refunding the frozen TRX to the account before conversion, or by having `deploy()` treat any account with non-zero frozen/resource state the same as the "foreign contract" collision case (skip deployment and log a warning) rather than force-converting it.

### Proof of Concept
1. Before the TIP-2935 proposal (`AllowTvmPrague`) is activated by the committee, an attacker (or any user) broadcasts a `FreezeBalanceV2Contract` transaction with `owner_address = HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`) and `frozen_balance = N` TRX, which succeeds because `FreezeBalanceV2Processor.validate` performs no special-address check.
2. The committee activates the proposal; `ProposalService` calls `HistoryBlockHashUtil.deploy(manager)` during maintenance processing.
3. `deploy()` finds an existing account at `HISTORY_STORAGE_ADDRESS`, calls `account.updateAccountType(Contract)` and `account.clearDelegatedResource()`, and stores the account — the `N` TRX in `FrozenV2` remains attributed to this now-keyless contract account.
4. Any subsequent attempt to submit `UnfreezeBalanceV2Contract` for this address fails signature/ownership verification because no private key exists for it, permanently locking the `N` TRX.

```java
  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);
```
