### Title
Deleted-then-recreated account inherits attacker's postponed receipts because `remove_account` never purges `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows - (File: core/store/src/utils/mod.rs)

### Finding Description
`remove_account` (core/store/src/utils/mod.rs:505-575) explicitly removes `TrieKey::Account`, `TrieKey::ContractCode`, all `TrieKey::AccessKey`/gas-key-nonce rows (via `get_raw_prefix_for_access_keys`), and all `TrieKey::ContractData` rows (via `get_raw_prefix_for_contract_data`): [1](#0-0) [2](#0-1) [3](#0-2) 

Nowhere in this function is there any iteration or removal of `TrieKey::PostponedReceipt{receiver_id,receipt_id}`, `TrieKey::PostponedReceiptId{receiver_id,data_id}`, or `TrieKey::PendingDataCount{receiver_id,receipt_id}` — the function's own doc comment even scopes its cleanup to "account, code and all access keys and gas keys" only, silently excluding postponed-receipt state: [4](#0-3) 

Separately, `DeleteAccount`'s only actor check is `actor_id == account_id` plus a zero-locked-balance check; it does not query or block on outstanding `PendingDataCount`/`PostponedReceipt` entries for the target account: [5](#0-4) 

Exploit flow: attacker's contract on `child.attacker.near` issues a promise joining two Promises (`promise_and`), producing an `ActionReceipt` with two `input_data_ids` including an `AddKey` FullAccess action. Because only one `DataReceipt` has arrived, the runtime postpones the receipt, writing `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows keyed to `receiver_id = child.attacker.near`. The attacker then submits `DeleteAccount` on `child.attacker.near` (self-call, satisfies `actor_id == account_id`, and locked balance is zero, so it passes), which calls `remove_account` and clears the account/keys/code/data but leaves the postponed-receipt rows intact in the trie. `attacker.near` then recreates `child.attacker.near` via `CreateAccount` + `AddKey`, handing it to a new owner who reasonably believes the account is "fresh." When the second delayed `DataReceipt` eventually arrives, `PendingDataCount` reaches zero and the runtime promotes and executes the stale `PostponedReceipt` — including the `AddKey` FullAccess action — against the now-recreated account. Because the `AddKey` action's `actor_id` (the receipt's `predecessor_id`, `child.attacker.near` itself from the original self-call) still equals `account_id`, `check_actor_permissions` passes trivially; it has no notion of "account incarnation," so it cannot distinguish the old, deleted incarnation from the new one. `action_add_key` (runtime/runtime/src/access_keys.rs:149-192) then unconditionally installs the attacker's key into whatever account currently exists at that name.

### Impact Explanation
This breaks the "authorization exactness" invariant: a promise created under one incarnation of an account is executed and honored against a completely different, freshly created incarnation with a different owner. Concretely, it lets an attacker plant a backdoor `FullAccess` key on an account that a new owner (buyer of a "fresh" sub-account, or any relying party) believes they solely control, resulting in authorization escalation and theft of control over the recreated account (and any funds/assets subsequently deposited into it). This matches the NEAR bounty category of authorization escalation across accounts/promises.

### Likelihood Explanation
The preconditions are fully within an unprivileged attacker's control: the attacker owns the parent `attacker.near` and can freely create/delete/recreate `child.attacker.near`; deploying a contract that issues a `promise_and` with a deliberately delayed second dependency is standard contract code, not a special privilege; `DeleteAccount` on a zero-locked-balance account is a normal permitted action for the account's own key. The only timing requirement is that the second `DataReceipt` arrive after the recreation transaction is included, which the attacker fully controls by choosing when/if to trigger the second promise dependency. This is deterministic and repeatable, not a race against the network.

### Recommendation
`remove_account` should also enumerate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries scoped to `receiver_id == account_id` before an account can be deleted (or `DeleteAccount` should be rejected/deferred while such pending state exists for the account), so that no in-flight receipt can survive to be executed against a later, differently-owned incarnation of the same account name.

### Proof of Concept
Integration/apply-path test:
1. Create `attacker.near` and deploy a contract to `child.attacker.near` that, when called, issues two cross-contract promises joined with `promise_and`, and attaches an `AddKey` FullAccess action (with a hardcoded attacker public key) to the joined receipt.
2. Trigger the call so that one of the two data dependencies resolves immediately and the other is deliberately delayed (e.g., call a contract method on another account that only responds after N more blocks), causing the runtime to write `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` for `child.attacker.near`.
3. Before the second `DataReceipt` resolves, submit `DeleteAccount` on `child.attacker.near`, then `CreateAccount` + `AddKey` (new owner's key) to recreate `child.attacker.near`.
4. Allow the delayed `DataReceipt` to arrive and be applied.
5. Assert that the post-state `AccessKey` set for `child.attacker.near` contains the attacker's stale FullAccess public key, which the new owner never authorized — demonstrating the escaped, unauthorized key addition.
