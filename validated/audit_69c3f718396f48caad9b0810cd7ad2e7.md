Audit Report

## Title
Reentrancy stipend protection is never applied to non-zero-value `.transfer()`/`.send()` calls due to match-arm ordering bug in EVM `CALL` handling - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

## Summary
In `run_call()`, the match statement selecting the `ReentrancyProtection` mode for a call places `(false, _) => (true, ReentrancyProtection::AllowReentry)` before the stipend-detection arm `(_, true) => (true, ReentrancyProtection::AllowNext)`. Since Rust evaluates match arms in order and `(false, _)` matches any call with `value.is_zero() == false` regardless of `gas_limit`, every non-zero-value call — including the standard `solc`-compiled `.transfer(amount)`/`.send(amount)` with `amount > 0` and `gas_limit == CALL_STIPEND` (2300) — is routed to `AllowReentry` instead of the intended `AllowNext` reentrancy guard.

## Finding Description
The relevant code is: [1](#0-0) 

`AllowReentry` places no restriction on the callee re-entering the caller, whereas only `AllowNext` sets `self.top_frame_mut().allows_reentry = false` in the exec dispatch path, which is the mechanism the code's own doc comment (on `ReentrancyProtection::AllowNext`) states exists specifically because the raw Ethereum stipend gas value (2300) is not automatically a safe reentrancy guard on revive's PVM gas scale. Because the `(false, _)` arm is checked first, any call carrying `value > 0` — i.e., the exact common case of `.transfer()`/`.send()` — short-circuits before the stipend heuristic in `(_, true)` is ever reached, so `AllowNext` is only reachable for zero-value calls, which is not the scenario the stipend exists to protect. This is a straightforward match-arm ordering bug matching the reported description; the fix is to test the stipend condition `(_, true)` before the general non-zero-value fallback.

## Impact Explanation
This falls under "runtime bugs that compromise intended behavior" and enables theft of contract-held value: a Solidity contract on `pallet-revive` using the standard checks-effects-interactions `.transfer()`/`.send()` pattern to defend against reentrancy is not actually protected, since `AllowReentry` is granted instead of `AllowNext` whenever value is transferred. A malicious receiving contract can re-enter the caller's frame during its `receive()`/fallback and potentially drain funds via repeated withdrawals, since the reentrancy-denial check (`allows_reentry`) that should trigger `<Error<T>>::ReentranceDenied` is bypassed.

## Likelihood Explanation
This is reachable by any unprivileged user deploying and calling ordinary Solidity contracts compiled by `solc` through `pallet-revive`'s EVM interpreter, with no privileged or governance action required. `.transfer()`/`.send()` with non-zero value is one of the most common Solidity idioms specifically because developers rely on the stipend-based reentrancy guarantee, making the vulnerable code path trivial to hit by any attacker controlling the receiving contract.

## Recommendation
Reorder the match arms so the stipend/value-scale heuristic is evaluated before the generic non-zero-value fallback:
```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND)) {
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```
This ensures any call carrying the compiler's stipend signal (`gas_limit == CALL_STIPEND`), regardless of whether `value` is zero or non-zero, receives `AllowNext`. Add regression tests mirroring `testTransferReentrancy`/`testSendReentrancy` that specifically exercise non-zero-value `.transfer()`/`.send()` reentrancy attempts to confirm the guard engages.

## Proof of Concept
1. Deploy a `Victim` contract implementing `balances[msg.sender] -= amount; msg.sender.transfer(amount);`.
2. Deploy an `Attacker` contract whose `receive()`/fallback re-enters `Victim.withdraw()` upon receiving funds.
3. Attacker calls `Victim.withdraw()`; solc compiles `.transfer(amount)` with `amount > 0` and pushes `gas_limit = CALL_STIPEND (2300)` on the stack.
4. In `run_call()`, since `value.is_zero() == false`, the first arm `(false, _)` matches and yields `ReentrancyProtection::AllowReentry` even though `gas_limit == CALL_STIPEND` — the stipend-specific `(_, true)` arm is never reached.
5. Because `AllowReentry` is granted, `Attacker.receive()` can re-enter `Victim.withdraw()` before the outer frame's effects are finalized, enabling repeated/duplicate withdrawals beyond `Attacker`'s entitled balance.
