### Title
Unbounded per-extension patch size limit bypasses `maxPatchBytesUpperBound` cap in diff parsing - ([File: internal/gitaly/diff/diff.go])

### Summary
`Limits.enforceUpperBound()` is meant to be the single choke point that clamps every diff-size-related limit a gRPC caller can supply to a fixed, sane upper bound before the diff parser is constructed. It clamps `MaxFiles`, `MaxLines`, `MaxBytes`, `SafeMaxFiles`, `SafeMaxLines`, `SafeMaxBytes`, and `MaxPatchBytes` — but it never clamps `MaxPatchBytesForFileExtension`, even though this map is used as an alternate, higher-precedence source for the exact same "how large may a single patch get" decision that `MaxPatchBytes` is supposed to police.

### Finding Description
`CommitDiffRequest.MaxPatchBytesForFileExtension` is copied verbatim (as `int32` → `int`, with no bound check) from the client request into `diff.Limits.MaxPatchBytesForFileExtension`: [1](#0-0) 

`NewDiffParser` then calls `limits.enforceUpperBound()`, whose job is documented as "ensures every limit value is within its corresponding upperbound": [2](#0-1) 

Notice that `enforceUpperBound()` clamps `MaxPatchBytes` to `maxPatchBytesUpperBound` (500 KB), but does not touch `MaxPatchBytesForFileExtension` at all — the map is passed through completely unbounded.

The per-file "is this patch too large" decision, however, does not use `MaxPatchBytes` directly; it uses `maxPatchBytesForCurrentFile()`, which is documented to let the per-extension map *override* `MaxPatchBytes`: [3](#0-2) 
and it is consumed here: [4](#0-3) 

This is structurally the same class of bug as the Cairo report: two values are supposed to satisfy an invariant (`MaxPatchBytesForFileExtension[ext] <= maxPatchBytesUpperBound`, analogous to `threshold <= MAX_PENALTY_LTV`), the "cheap" bounding function only clamps one of the two paths (`MaxPatchBytes`, analogous to bounding via `MAX_THRESHOLD` alone), and the code that performs the actual security-relevant comparison consults the *other*, unbounded value. Any caller of the public `CommitDiff` RPC — an ordinary, unprivileged Gitaly client — can drive this by supplying an oversized `max_patch_bytes_for_file_extension` value while still setting `enforce_limits = true`, causing the server to believe limits are being enforced while in fact patches for the chosen extension are allowed to grow without the intended cap.

### Impact Explanation
`EnforceLimits`/`MaxPatchBytes` exist specifically to bound the amount of patch data Gitaly buffers and streams per file when serving `CommitDiff`, guarding against resource exhaustion from pathologically large diffs. Because `MaxPatchBytesForFileExtension` is never subjected to `maxPatchBytesUpperBound`, an ordinary caller that believes it is requesting a bounded response (`EnforceLimits: true`) can instead force the server to buffer and process patches of essentially unbounded size (up to `int32` max) for any file extension of the caller's choosing, defeating the very mechanism `MaxPatchBytes`/`enforceUpperBound()` were designed to guarantee. This is a resource-limit bypass on an RPC handler that ordinary users of `DiffService` can reach directly, and it can be used to increase per-request memory/CPU consumption on the Gitaly server well past the intended server-side ceiling.

### Likelihood Explanation
The path is trivially reachable: any client authorized to call `CommitDiff` (a standard, unprivileged RPC used by GitLab web/API diff rendering) can set `EnforceLimits: true` together with a `MaxPatchBytesForFileExtension` map entry with an inflated value (e.g. `2^31-1`) for the extension of a file known to appear in the diff. No special privileges, tokens, or race conditions are required, and the bypass is deterministic.

### Recommendation
Extend `enforceUpperBound()` to also clamp every value in `MaxPatchBytesForFileExtension` to `maxPatchBytesUpperBound` (mirroring how `MaxPatchBytes` itself is clamped), so the per-extension override can only ever be more restrictive than, or equal to, the enforced ceiling rather than able to exceed it. As a defense in depth, `maxPatchBytesForCurrentFile()` should additionally clamp its returned value against `maxPatchBytesUpperBound` regardless of the caller-supplied map, so the two code paths cannot diverge again in the future. Add a unit test analogous to `TestDiffLimitsBeingEnforcedByUpperBound` that explicitly asserts a `MaxPatchBytesForFileExtension` entry larger than `maxPatchBytesUpperBound` gets clamped.

### Proof of Concept
1. Craft a `CommitDiffRequest` against a repository containing a commit that modifies a file with extension `.bin` whose patch is, say, 50 MB.
2. Set `EnforceLimits: true`, `MaxPatchBytes: 1024` (small), and `MaxPatchBytesForFileExtension: {".bin": 2147483647}`.
3. Call `CommitDiff`. Because `enforceUpperBound()` only clamps `MaxPatchBytes` (to 1024, then further to `maxPatchBytesUpperBound`) and leaves `MaxPatchBytesForFileExtension[".bin"]` untouched, `maxPatchBytesForCurrentFile()` returns the attacker-supplied ~2 GB bound for `.bin` files, so `parser.currentDiff.Patch` for that file is never pruned by `maxPatchBytesExceeded` in `Parse()` and the full 50 MB patch is buffered and streamed back — well beyond the intended `maxPatchBytesUpperBound` (500 KB) cap. // enforceUpperBound ensures every limit value is within its corresponding upperbound
func (limit *Limits) enforceUpperBound() {
	limit.MaxFiles = min(limit.MaxFiles, maxFilesUpperBound)
	limit.MaxLines = min(limit.MaxLines, maxLinesUpperBound)
	limit.MaxBytes = min(limit.MaxBytes, maxBytesUpperBound)
	limit.SafeMaxFiles = min(limit.SafeMaxFiles, safeMaxFilesUpperBound)
	limit.SafeMaxLines = min(limit.SafeMaxLines, safeMaxLinesUpperBound)
	limit.SafeMaxBytes = min(limit.SafeMaxBytes, safeMaxBytesUpperBound)
	limit.MaxPatchBytes = min(limit.MaxPatchBytes, maxPatchBytesUpperBound)
}
