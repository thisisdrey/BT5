### Title
`write-freq` StackerDB rate-limit is never enforced on the chunk-write path, allowing any slot owner to spam network-wide StackerDB writes - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
This is the direct network-layer analog of the reported bug class: a protocol-level "delay"/rate-limit is defined and *assumed* to be enforced, but the actual write/authorization path never checks it, so an authorized-but-rate-limited actor can write far more often than the configured limit allows, with the excess writes propagated network-wide.

### Finding Description
StackerDB contracts define a `write-freq` value (seconds) via `stackerdb-get-config`, loaded into `StackerDBConfig.write_freq` [1](#0-0) [2](#0-1) . This is meant to bound how frequently a given slot owner (e.g., a Nakamoto signer) can post a new chunk version, exactly like `blockDelay` in the referenced report.

The only place `write_freq` is actually consulted is in the *pull*-sync scheduler, when a replica decides whether to *request* a chunk from a peer: [3](#0-2) 

However, the authoritative write path — `StackerDBs::try_replace_chunk`, which is what actually stores a new chunk version into the local database — never checks `write_freq` at all. It only validates chunk size, slot signer, staleness (`slot_version <= slot_validation.version`), and `max_writes`: [4](#0-3) 

This function is called directly by the unauthenticated (i.e., not requiring node admin/token, only requiring the slot's own signing key) HTTP write endpoint `POST /v2/stackerdb/:principal/:contract/chunks`: [5](#0-4) 

On acceptance, the node immediately relays the new chunk to the entire p2p network as a `StackerDBPushChunk` message: [6](#0-5) 

On the receiving side, `handle_unsolicited_StackerDBPushChunk` explicitly documents (and implements) that write frequency is *not* checked for pushed chunks, by design, and only validates signer/version/size via `validate_received_chunk`: [7](#0-6) [8](#0-7) 

So the equality that should hold — "actual write interval ≥ contract-configured `write_freq`" — is never enforced anywhere on the write/propagation path; it is only used as a local heuristic to decide whether to *pull* a chunk, which a directly-pushed (POST-then-relay) chunk bypasses entirely.

### Impact Explanation
Any party holding a valid slot signing key for a StackerDB contract (e.g., a registered Nakamoto signer or miner slot) can post new chunk versions as fast as `max_writes` and the version-monotonicity check allow, completely ignoring the contract's `write-freq`. Each accepted write is relayed to, validated, and stored by every replica on the network, since receiving nodes also skip the frequency check for pushed chunks. This defeats the intended per-slot write-rate governance that operators/contract authors configure to bound replication bandwidth, storage churn, and DB write amplification across the network — a bounded-compute/storage DoS vector reachable by any single authorized signer, propagated network-wide.

### Likelihood Explanation
High. No special conditions or races are required: any legitimate slot owner can simply issue repeated signed `POST /v2/stackerdb/.../chunks` requests with incrementing `slot_version`; each one passes `try_replace_chunk`'s checks (signature, monotonic version, size, max_writes) with no timing gate, and each is relayed and accepted network-wide.

### Recommendation
Enforce `write_freq` inside `StackerDBs::try_replace_chunk` (or immediately before it in the write handler) by comparing `get_epoch_time_secs()` against the slot's stored `write_time` (already tracked in the `chunks` table, see `SlotValidation.write_time` at `stackslib/src/net/stackerdb/db.rs:112-128`), rejecting/erroring (e.g. reusing `Error::TooFrequentSlotWrites`) writes that arrive before `write_time + write_freq`. Also apply the same check in `handle_unsolicited_StackerDBPushChunk`/`validate_received_chunk` so pushed chunks cannot bypass it either, rather than relying solely on the pull-sync scheduler's optimistic skip.

### Proof of Concept
1. Register/own a slot for a StackerDB contract with `write-freq = N` seconds.
2. Sign chunk version `v1`, `POST /v2/stackerdb/<addr>/<contract>/chunks` — accepted, relayed to the network.
3. Immediately (no wait) sign chunk version `v2` and repeat the POST — `try_replace_chunk` only checks `slot_version > stored_version` and `slot_version <= max_writes`; there is no `write_time`/`write_freq` check, so it is accepted and relayed again.
4. Repeat as fast as network RTT allows, producing writes at a rate far exceeding `write_freq`, all of which propagate to and are stored by every replica.

    /// Validate chunk data either downloaded (with [`StackerDBSync::validate_downloaded_chunk`]), or
    /// pushed to us (with [`PeerNetwork::handle_unsolicited_StackerDBPushChunk`])
    ///
    /// NOTE: does not check write frequency, since the caller has different ways of doing this.
    /// Returns:
    /// - Ok(true) if the chunk is valid
    /// - Ok(false) if the chunk is invalid
    /// - Err(..) on DB error
    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }
