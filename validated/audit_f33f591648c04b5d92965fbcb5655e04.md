### Title
Uncontrolled Memory Allocation in TVM Precompiled Contracts `BatchValidateSign`/`ValidateMultiSign` via Attacker-Controlled Array Length - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` helper methods in `PrecompiledContracts.java` allocate Java arrays sized directly from an attacker-controlled length field parsed out of the raw call data, before any upper-bound validation is guaranteed to occur.

### Finding Description
`extractBytes32Array` reads a length word from the ABI-encoded input and immediately allocates an array of that size: [1](#0-0) 

`extractBytesArray` and `extractSigArray` do the same: [2](#0-1) 

The length value comes from `DataWord.intValueSafe()`, which caps the *returned* value at `Integer.MAX_VALUE` for any 32-byte word that doesn't fit cleanly as a positive 32-bit int, but does **not** reject or bound the value in any other way: [3](#0-2) 

In `BatchValidateSign.doExecute`, the size check against `MAX_SIZE` (16) is only performed when the `allowTvmSelfdestructRestriction` feature flag is enabled: [4](#0-3) 

Similarly, in `ValidateMultiSign.execute`, the `sigArraySize > MAX_SIZE` guard is also gated behind the same flag: [5](#0-4) 

If this chain parameter is not active (it is a committee-controlled proposal switch, not necessarily on by default on every deployment/private/test chain, and I could not confirm its default state within the DynamicPropertiesStore in the indexed portion of the codebase), the length-bounded path is skipped entirely and `extractBytes32Array`/`extractBytesArray`/`extractSigArray` are invoked with a fully attacker-controlled `len` derived straight from calldata. This is directly analogous to CVE-2025-4605's root cause: a size field taken from untrusted, parsed input drives an allocation with no sanity bound, enabling an uncontrolled memory allocation.

These precompiles are reachable by any unprivileged account: `TriggerSmartContract` (or `TriggerConstantContract`) calling the fixed precompile addresses `0x9` (`batchValidateSign`) or `0xa` (`validateMultiSign`) executes this code inside `PrecompiledContracts.getContractForAddress`: [6](#0-5) 

### Impact Explanation
An attacker can craft calldata whose length-prefix word decodes to a very large value (up to `Integer.MAX_VALUE` via `intValueSafe()`), forcing `new byte[len][]` to attempt an allocation of billions of null-array-reference slots (`Integer.MAX_VALUE * 8 bytes` referencer overhead alone ≈ 16 GB on a 64-bit JVM), which throws `OutOfMemoryError` or causes severe GC pressure/pause. Because this executes inside the node's TVM execution path (during transaction application or constant call handling), a single crafted call could crash the node process or stall block processing for all peers replaying the same transaction, i.e. a denial-of-service against the network's validating/witness nodes and any full node serving `triggerConstantContract` RPC calls.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the `allowTvmSelfdestructRestriction` proposal to be inactive on the target chain (this flag's current mainnet state could not be confirmed from the indexed subset of `DynamicPropertiesStore.java`), and depends on JVM heap limits/behavior on `OutOfMemoryError` (whether it kills the whole process or is contained). On chains/environments where the flag is off (e.g., private/test networks, or a mainnet moment before the corresponding TIP activates), any unprivileged account can trigger it with a single transaction or constant call, with no special permissions required.

### Recommendation
Move the `MAX_SIZE` bound check in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (or immediately before their invocation) unconditionally, independent of `VMConfig.allowTvmSelfdestructRestriction()`, so that array lengths are always validated against a small, fixed cap (matching `MAX_SIZE` in `ValidateMultiSign`/`BatchValidateSign`) before any allocation occurs. Additionally, harden `extractBytes32Array` with the same `offset > words.length - 1` bounds check already present in `extractBytesArray`/`extractSigArray`.

### Proof of Concept
1. Build ABI-encoded calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the `address[]` length word (at the offset referenced by `words[2]`) is set to a large value such as `0x7FFFFFFF`.
2. Ensure the `allowTvmSelfdestructRestriction` chain parameter is not active (its default state is unconfirmed from the indexed code; verify against a running node's `getChainParameters` output).
3. Submit a `TriggerConstantContract`/`TriggerSmartContract` call to precompile address `0x...09` with this calldata.
4. `BatchValidateSign.doExecute` calls `extractBytes32Array(words, offset)` at line 1176-1177, which executes `new byte[0x7FFFFFFF][]`, causing an `OutOfMemoryError` inside the TVM execution thread of the node processing the request.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
