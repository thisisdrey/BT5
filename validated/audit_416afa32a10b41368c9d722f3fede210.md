### Title
Replay-window TOCTOU allows duplicate packet acceptance due to unlocked gap between `Bits.Check` and `Bits.Update` - (File: `connection_state.go`)

### Summary
Nebula's per-tunnel anti-replay mechanism splits the "is this counter allowed" check and the "mark this counter as seen" mutation into two separate lock/unlock critical sections, with the (relatively expensive) AEAD decryption happening in between while the lock is released. This mirrors the root cause of the referenced report: a security-relevant check is validated against state that is stale by the time the corresponding state mutation actually happens, because an unrelated operation is interleaved between the check and the commit.

### Finding Description
`ConnectionState.Decrypt` (and its sibling `VerifyRelay`) implement the replay check as:

1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)`, unlock.
2. Perform `cs.dKey.DecryptDanger(...)` **without holding the lock**.
3. Lock `decryptLock` again, call `cs.window.Update(l, messageCounter)`, unlock. [1](#0-0) 

`Bits.Check` only inspects whether a counter has already been marked in the sliding-window bitmap; it does not itself mark the bit. Only `Bits.Update` actually sets the bit. [2](#0-1) 

Because the lock is released between step 1 and step 3, if two packets carrying the **same messageCounter** (a replayed/duplicated UDP datagram) are processed concurrently on two different worker goroutines/queues, both can call `Check` before either has called `Update`. Neither call observes the other's not-yet-applied state, so both `Check` calls return `true`. Both goroutines then independently decrypt the packet (which succeeds because AEAD decryption does not depend on the anti-replay window) and only afterward call `Update`, so the packet is delivered to the TUN device (or, for `VerifyRelay`, forwarded) twice. This is the exact bug-class analog of the referenced report: a state check is performed, a costly/interleavable operation runs, and only afterward is the check "finalized" into state — but the finalization is not what actually gated the sensitive action, so a second concurrent caller can slip through the same gap.

The project's own test file confirms that "check the window, then apply the effect" ordering is treated as safety-critical: `TestRelayReplayProtection`'s regression comment states the original relay bug was that a "frame was authenticated but never advanced the replay window, so every replay was re-forwarded." [3](#0-2)  That fix apparently relies on the eventual `Update()` call happening, but it does not address the concurrency gap between `Check` and `Update` for genuinely simultaneous duplicate deliveries.

### Impact Explanation
An attacker who can inject or duplicate UDP datagrams toward a Nebula node (no valid CA-signed certificate required — this operates purely on the transport/replay layer of an already-established tunnel, and the attacker only needs to observe/replay ciphertext, not decrypt or forge it) can cause the anti-replay window to be bypassed for a captured packet if they can get two copies of it processed concurrently (e.g., via packet duplication at the network layer, or by racing delivery across multiple listener/worker queues that Nebula uses for UDP receive). This results in the same message being delivered to the TUN device or relay-forwarded more than once, i.e., a genuine replay of encrypted traffic despite the anti-replay window being "correctly" checked on paper. For relay-forwarded traffic this directly reintroduces the class of bug that `TestRelayReplayProtection` was written to prevent.

### Likelihood Explanation
This requires winning a narrow race (two copies of the same counter must be in-flight in the decrypt path concurrently, with the AEAD decrypt time as the race window), which is a real but not trivial network condition to reliably trigger (packet duplication/replay is easy for an on-path or off-path attacker who captures traffic; concurrency is a matter of sending the duplicate quickly enough that both are being processed at once, especially if Nebula uses multiple receive queues/goroutines, which increases the odds of two goroutines racing on the same `ConnectionState`).

### Recommendation
Hold `decryptLock` for the entire `Check → Decrypt → Update` sequence (or otherwise make the window check-and-reserve atomic, e.g., have `Check` tentatively reserve the slot under the same lock held through decryption, rolling back only if decryption fails) so that no second caller can observe the pre-mutation window state while a decrypt for the same counter is in flight.

### Proof of Concept
No PoC was executed against the live system; the vulnerability is inferred from code inspection of `ConnectionState.Decrypt`/`VerifyRelay` [4](#0-3)  and `Bits.Check`/`Bits.Update` [2](#0-1) , plus the existing regression test acknowledging the criticality of check-then-update ordering for replay protection [3](#0-2) .

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
