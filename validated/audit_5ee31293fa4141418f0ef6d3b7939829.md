### Title
Unclamped utilization ratio in `lending_rate_apr` calculation can push the lending (supply) rate above the borrowing rate, breaking pool solvency invariant - ([File: programs/marginfi/src/state/interest_rate.rs])

### Summary
The reported bug shows that when a Compound-fork's utilization rate is allowed to exceed its intended `[0, 1e18]` bound, the supply rate (`utilizationRate * rateToPool`) can be driven above the borrow rate, letting depositors extract more interest than borrowers pay in — an insolvency vector. marginfi has a structurally analogous asymmetry: `InterestRateCalc::calc_interest_rate` clamps the utilization ratio only when it is used to interpolate `base_rate_apr`, but reuses the **unclamped** `utilization_ratio` parameter when computing `lending_rate_apr`, while `borrowing_rate_apr` is derived from the clamped `base_rate_apr`.

### Finding Description
`InterestRateCalc::calc_interest_rate` receives `utilization_ratio` and computes: [1](#0-0) 

- `base_rate_apr` is produced by `interest_rate_multipoint_curve(utilization_ratio)`, which internally clamps its local copy of the ratio to `[0, 1]` before interpolating: `let ur: I80F48 = ur.max(I80F48::ZERO).min(I80F48::ONE);` [2](#0-1) . This clamp is confirmed by the unit test `mpc_clamps_ur_above_one_to_hundred_rate`, which explicitly documents that "ur > 1 clamps to 1.0 → hundred rate" [3](#0-2) .
- However, `lending_rate_apr` is computed as `base_rate_apr.checked_mul(utilization_ratio)` using the **original, unclamped** `utilization_ratio` parameter passed into `calc_interest_rate` — not the clamped local variable used inside `interest_rate_multipoint_curve` [4](#0-3) .
- `borrowing_rate_apr`, by contrast, is derived purely from the (indirectly clamped) `base_rate_apr`: `base_rate_apr * (1 + fee_ir) + fee_fixed` [5](#0-4) .

Under normal conditions `utilization_ratio = total_liabilities_amount / total_assets_amount <= 1`, so `lending_rate_apr = base_rate_apr * utilization_ratio <= base_rate_apr <= borrowing_rate_apr`, preserving the documented invariant that "borrowers always pay more than lenders get" [6](#0-5) . This ratio is computed identically both in `Bank::update_bank_cache` and in `calc_interest_rate_accrual_state_changes`, with no upstream clamp applied before it reaches `calc_interest_rate`: [7](#0-6) [8](#0-7) .

The code's own comment — "Sanity check: clamp the UR in case we somehow exceeded 100% or went negative" — acknowledges that the raw ratio can legitimately go outside `[0,1]` in edge cases (e.g., transient bad debt before a bankruptcy write-off, rounding drift across share-value updates, or independent asset/liability share pools that are not structurally tied together the way Compound's `cash+borrows` model is). If that happens, `base_rate_apr` is correctly capped at the "hundred_util_rate" ceiling, but `lending_rate_apr = base_rate_apr * utilization_ratio` is **not** capped and scales linearly with the excess ratio, while `borrowing_rate_apr` stays bounded near `base_rate_apr * (1+fee_ir) + fee_fixed`. Once `utilization_ratio > 1 + fee_ir` (fee_ir is typically a small single-digit percentage), `lending_rate_apr` exceeds `borrowing_rate_apr`, exactly mirroring the H-03 root cause: an unclamped multiplier feeding the supply-side rate while the borrow-side rate remains capped.

There is no explicit assertion in `calc_interest_rate` enforcing `lending_rate_apr <= borrowing_rate_apr`; the only assertions present check non-negativity of each rate [9](#0-8) , exactly the same gap the original report flagged as missing ("the only check performed... is that borrowRateMantissa > borrowRateMaxMantissa").

### Impact Explanation
If `utilization_ratio` exceeds 1 (or exceeds `1+fee_ir`) even transiently, `calc_interest_rate_accrual_state_changes` will apply `lending_rate_apr` to grow `asset_share_value` faster than `liability_share_value` grows to compensate [10](#0-9) . Because deposit share value increases funds every depositor can redeem, while borrower liability growth (and thus real repayable interest) does not keep pace, the bank pays out more value to lenders than it collects from borrowers plus fees — a direct insolvency/bad-debt vector for the bank, consistent with the "Accept only concrete... insolvency/bad debt" criterion.

### Likelihood Explanation
This requires `total_liabilities_amount` to exceed `total_assets_amount` (or exceed it by more than the fee margin), which the codebase's own comment concedes "we somehow exceeded 100%" can occur. I was not able to fully verify, within the available investigation budget, a concrete unprivileged-user transaction sequence that reliably drives `total_liabilities_amount > total_assets_amount` in the current codebase (marginfi's asset/liability shares are independent pools rather than a single Compound-style `cash+borrows+reserves` balance, and normal borrow flows are gated by available vault liquidity). This is the key uncertainty: the vulnerable code path is proven to exist and is asymmetric by construction, but the reachability of `utilization_ratio > 1` by an unprivileged actor (versus only via rounding/bad-debt edge cases handled elsewhere, e.g., in bankruptcy resolution) needs further live/dynamic verification (e.g., fuzzing rounding edge cases around share-value updates, or bad-debt timing between last borrower repayment and bankruptcy resolution) before concluding it is trivially exploitable.

### Recommendation
- Use the same clamped ratio for `lending_rate_apr` that is used internally for `base_rate_apr` (i.e., clamp `utilization_ratio` to `[0, 1]` once at the top of `calc_interest_rate` and reuse that clamped value everywhere, rather than only inside `interest_rate_multipoint_curve`).
- Add an explicit invariant check/assertion that `lending_rate_apr <= borrowing_rate_apr` before returning `ComputedInterestRates`, mirroring the recommended fix in the referenced report.
- Audit all code paths that can cause `total_liabilities_amount` to (even transiently) exceed `total_assets_amount` (e.g., bankruptcy/bad-debt handling, rounding in share-value math) to confirm whether `utilization_ratio > 1` is actually reachable pre-fix.

### Proof of Concept
Conceptual (not yet dynamically confirmed against a live unprivileged exploit path):
1. Suppose, due to bad debt or rounding drift, a bank's `total_liability_shares` valuation slightly exceeds `total_asset_shares` valuation at the moment `accrue_interest`/`update_bank_cache` runs, so `utilization_ratio = total_liabilities_amount / total_assets_amount = 1.05` (or higher).
2. `interest_rate_multipoint_curve` clamps its local copy to `1.0`, returning `base_rate_apr` capped at `hundred_util_rate` (e.g., `0.30` APR).
3. `borrowing_rate_apr = base_rate_apr * (1 + fee_ir) + fee_fixed` ≈ `0.30 * 1.05 + fixed_fee` ≈ `0.315 + fixed_fee` (fee_ir assumed 5%).
4. `lending_rate_apr = base_rate_apr * utilization_ratio(unclamped) = 0.30 * 1.05 = 0.315`, which can exceed `borrowing_rate_apr` once `utilization_ratio > (1+fee_ir)`, e.g. at `utilization_ratio = 1.20`: `lending_rate_apr = 0.30*1.20 = 0.36 > borrowing_rate_apr ≈ 0.315 + fixed_fee`.
5. `calc_interest_rate_accrual_state_changes` then increases `asset_share_value` (depositor payout) at a rate exceeding what `liability_share_value` growth (borrower repayment) plus fees can cover, siphoning value out of the bank over successive accrual calls — a permissionless, unprivileged-caller-triggerable path (`accrue_interest` is callable by anyone per README: "permissionless").

**Confidence caveat:** the arithmetic asymmetry itself is confirmed directly in the source; what remains unverified within this investigation is a concrete, unprivileged transaction sequence in the current marginfi codebase that produces `total_liabilities_amount > total_assets_amount` outside of already-handled bad-debt/bankruptcy flows. This should be validated with targeted fuzzing/dynamic testing (e.g., against `trident-tests/fuzz_0/invariants/solvency.rs`) before treating this as a fully proven, exploitable High-severity issue.
