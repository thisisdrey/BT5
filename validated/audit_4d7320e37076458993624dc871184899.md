### Title
Unconsented debt assignment via `DebtToken.issue(amount_, to_)` writes debt entries into an arbitrary victim's state, freezing their collateral - (File: contracts/DebtToken.sol)

### Summary

The QEMU bug class is an out-of-bounds write triggered while processing an attacker-influenced command — attacker-controlled input corrupts state belonging to another context. The Metronome analog is `DebtToken.issue(uint256 amount_, address to_)`: an attacker deposits their own collateral and mints a debt position onto *any* address (`to_`), writing entries into the victim's `principalOf`, `debtIndexOf`, and `debtTokensOfAccount` set without the victim's consent. Because `Pool.debtPositionOf`/`DepositToken.unlockedBalanceOf` treat that debt as the victim's own, all of the victim's deposited collateral becomes locked (`_revertIfLocked` reverts on `transfer`, `transferFrom`, `withdraw`, `withdrawFrom`). The victim must repay debt they never took — using synthetic tokens they never received — to unlock their funds. Repeated across debt tokens, the writes also push the victim toward `MAX_TOKENS_PER_USER = 30`, making subsequent legitimate deposits/mints revert with `UserReachedMaxTokens`.

### Finding Description

`DebtToken.issue` accepts an arbitrary beneficiary. There is no check that `to_ == _msgSender()` or that `to_` authorized the debt:

- `issue(amount_, to_)` → `_mint(pool_, masterOracle_, account_ = to_, amount_)` [1](#0-0) 
- `_mint` writes `principalOf[account_] = _balanceBefore + amount_` and `debtIndexOf[account_] = debtIndex` for the victim, then pushes the token into the victim's per-account list via `pool.addToDebtTokensOfAccount(account_)` [2](#0-1) 
- `Pool.addToDebtTokensOfAccount` only verifies the *caller* is a registered debt token; `account_` is fully attacker-chosen [3](#0-2) 
- Once the victim has nonzero debt, `DepositToken.unlockedBalanceOf` computes `Math.min(balance, quoteUsdToToken(_issuableInUsd / collateralFactor))` — with attacker-created debt, `_issuableInUsd` collapses toward 0, so unlocked balance → 0 [4](#0-3) 
- `_revertIfLocked` then blocks every exit path: `transfer` (L350), `transferFrom` (L362), `withdraw` (L409), `withdrawFrom` (L424) [5](#0-4) 
- Debt tokens are non-transferable (`TransferNotSupported`), so the victim cannot shed the entry except by repaying with real synthetic tokens [6](#0-5) 
- The same pattern repeats via `DepositToken._mint`/`_transfer` writing into `depositTokensOfAccount[recipient]` for any `onBehalfOf_`/`recipient_`, filling the shared 30-slot budget (`MAX_TOKENS_PER_USER`), after which all new-position mints to the victim revert [7](#0-6) 

The `DebtLowerThanTheFloor` check forces the debt to be ≥ `debtFloorInUsd`, so the freeze costs the attacker locked collateral proportional to the floor — but a single floor-sized debt (or several across debt tokens) can freeze collateral arbitrarily larger than the debt itself, since the victim's whole balance is collateral-weighted against the foreign debt.

### Impact Explanation

Temporary freezing of user funds and extortion-style griefing: a victim's entire collateral position is locked until they acquire the synthetic token on the open market and repay a debt created by the attacker. The attacker keeps the minted synthetic tokens and can even repay/unwind later to recover collateral. If the victim's combined token list reaches 30 entries via dust `deposit(onBehalfOf)`/`transfer` plus issued debts, the victim is additionally blocked from opening any new position (`UserReachedMaxTokens`), preventing defensive collateral top-ups and pushing them toward liquidation on existing debt. Invariant broken: debt/account-list entries must only reflect positions the account itself opened.

### Likelihood Explanation

Reachable by any unprivileged EOA with collateral: `DepositToken.deposit(amount, attacker)` → `DebtToken.issue(floorAmount, victim)`. No privileged role, oracle manipulation, or governance action needed. Main constraints: the issued debt must satisfy `debtFloorInUsd` (nonzero cost locked as attacker collateral), mint must pass the pool's health check on the *attacker's* collateral, and the pool must have an active debt token. The victim can recover by repaying, so this is temporary freezing rather than permanent loss — matching the accepted impact class. Caveat I could not fully verify: whether any deployed configuration restricts `to_` (e.g., via `Operator`-level policy), and whether the number of registered deposit+debt tokens on a given deployment is large enough to reach the 30-slot cap; the single-debt collateral freeze does not depend on the cap.

### Recommendation

Restrict `issue`/`_mint` so debt can only be created for `_msgSender()` (`to_ == _msgSender()`), or require an explicit opt-in delegation mapping set by the beneficiary. Similarly, consider requiring the recipient's consent (or dropping the `addTo*TokensOfAccount` revert into a non-failing path) so dust `deposit(onBehalfOf_)`/`transfer` cannot grief the `MAX_TOKENS_PER_USER` budget — e.g., skip the list add when `amount_` is below a dust threshold, or make the per-account list non-reverting by computing positions from the global token sets instead.

### Proof of Concept

Hardhat (repo test style):

```ts
// setup: pool, msdMET (deposit token), msUSDDebt (debt token), feeProvider with debtFloorInUsd > 0
const floorUsd = await pool.debtFloorInUsd();

// attacker deposits own collateral
await met.mint(attacker.address, parseEther('1000'));
await met.connect(attacker).approve(msdMET.address, MaxUint256);
await msdMET.connect(attacker).deposit(parseEther('1000'), attacker.address);

// victim deposits own collateral
await met.mint(victim.address, parseEther('500'));
await met.connect(victim).approve(msdMET.address, MaxUint256);
await msdMET.connect(victim).deposit(parseEther('500'), victim.address);
expect(await msdMET.unlockedBalanceOf(victim.address)).to.eq(parseEther('500'));

// attack: issue debt to victim, backed by attacker's collateral
const dust = await msUSDDebt.quoteIssueIn(floorUsd /* >= floor */);
await msUSDDebt.connect(attacker).issue(dust, victim.address);

// victim now has foreign debt → collateral frozen
const {_debtInUsd} = await pool.debtPositionOf(victim.address);
expect(_debtInUsd).to.gt(0);
expect(await msdMET.unlockedBalanceOf(victim.address)).to.lt(parseEther('500'));
await expect(msdMET.connect(victim).withdraw(parseEther('500'), victim.address))
  .to.be.revertedWithCustomError(msdMET, 'NotEnoughFreeBalance');
await expect(msdMET.connect(victim).transfer(attacker.address, 1))
  .to.be.revertedWithCustomError(msdMET, 'NotEnoughFreeBalance');
```

Extension for the list-fill DoS: for each registered `depositToken` call `depositToken.deposit(1, victim.address)` (dust mint writes into `depositTokensOfAccount[victim]`) and for each `debtToken` call `issue(dustFloor, victim)` until `debtTokensOfAccount + depositTokensOfAccount == 30`; then any `deposit(..., victim)` or `issue(..., victim)` reverts with `UserReachedMaxTokens`.
