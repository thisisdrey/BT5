Based on the investigation, I found a valid analog: an unvalidated-length token ID copied into fixed-size buffers in the market/exchange order-key construction path.

### Title
Buffer/Array Over-read (ArrayIndexOutOfBoundsException) via Oversized Token ID in Market Order Actuators - (File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java)

### Summary
`MarketSellAssetActuator.validate()` extracts `sellTokenID`/`buyTokenID` directly from the attacker-controlled `MarketSellAssetContract` and only checks that the bytes are numeric ASCII digits via `isNumber(...)` [1](#0-0) , with no upper bound on the byte-array length. These unbounded-length byte arrays are subsequently fed into `MarketUtils.createPairKey` and `MarketUtils.expandTokenIdToPriceArray`, which copy the raw token-id bytes into fixed-size `TOKEN_ID_LENGTH` buffers using `System.arraycopy` without first checking `tokenId.length <= TOKEN_ID_LENGTH` [2](#0-1) [3](#0-2) .

### Finding Description
This is analogous in root cause to CVE-2022-1533: a length field/parameter taken from external input is trusted without validating it against the size of the destination/source buffer before a raw memory copy is performed. In java-tron's case, `System.arraycopy(tokenId, 0, result, 0, tokenId.length)` will throw `ArrayIndexOutOfBoundsException` if `tokenId.length` exceeds `TOKEN_ID_LENGTH`, because the destination `result` array is fixed at `TOKEN_ID_LENGTH` bytes [2](#0-1) . The same unchecked-length pattern also appears in `decodeKeyToMarketPairKey`, which copies `TOKEN_ID_LENGTH * 2` bytes out of a store key [4](#0-3) .

`createPairKey`/`expandTokenIdToPriceArray` are invoked from `MarketSellAssetActuator.matchOrder` / `createAndSaveOrder` during `execute()`, which is reached directly from a signed `MarketSellAssetContract` transaction broadcast by any account [5](#0-4) . The `validate()` method only bounds-checks that the token ID is numeric [6](#0-5)  and never validates the byte length of `sellTokenID`/`buyTokenID` against `TOKEN_ID_LENGTH`, so a crafted contract with a very long numeric string in `sell_token_id`/`buy_token_id` reaches the fixed-size buffer copy.

Critically, `execute()`'s catch clause only handles `ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException` [7](#0-6) ; `ArrayIndexOutOfBoundsException` is an unchecked `RuntimeException` that is not in that list and will propagate up out of `execute()` during transaction processing.

### Impact Explanation
If the exception is not caught higher up in `Manager.processTransaction`/block application, an uncaught `RuntimeException` during transaction execution can abort block application for the node processing it, differ between nodes depending on defensive catch blocks elsewhere in the pipeline, and at minimum represents a reliable transaction-triggered crash/DoS condition reachable by any account that can broadcast a `MarketSellAssetContract`. I was not able to fully trace whether an outer catch-all in `Manager` (e.g., in `processTransaction`/`applyBlock`) swallows generic `RuntimeException` during actuator execution — this needs to be verified in a full session, since the caught-exception behavior there determines whether the practical impact is "single failed transaction" vs. "block-processing halt".

### Likelihood Explanation
The precondition is trivial: any account can submit an `AssetIssueContract`-issued token ID string, or directly encode an oversized `sell_token_id`/`buy_token_id` field in a `MarketSellAssetContract`, that passes the `isNumber` check but exceeds `TOKEN_ID_LENGTH` bytes. No special privileges, signatures beyond the sender's own key, or witness/committee cooperation are required — this is reachable purely through the public transaction-broadcast path once TVM market transactions are enabled (`dynamicStore.supportAllowMarketTransaction()`) [8](#0-7) .

### Recommendation
Add an explicit length check for `sellTokenID`/`buyTokenID` (and any token ID accepted by other market actuators, e.g., `MarketCancelOrderActuator`) against `TOKEN_ID_LENGTH` in `validate()`, rejecting the contract with a `ContractValidateException` before any `MarketUtils` key-construction helper is invoked. Additionally, harden `MarketUtils.createPairKey`, `expandTokenIdToPriceArray`, and `decodeKeyToMarketPairKey` themselves to throw a checked/validate-time exception (or truncate/reject) rather than relying on callers to pre-validate length, since these are shared low-level helpers.

### Proof of Concept
1. Enable market transactions (`AllowMarketTransaction`, committee/test-config parameter).
2. Craft a `MarketSellAssetContract` where `sell_token_id` is set to a numeric ASCII string longer than `TOKEN_ID_LENGTH` bytes (e.g., 40 ASCII digit characters) while `buy_token_id` is a normal valid token ID (or `"_"` for TRX).
3. Broadcast the transaction from any funded account. `validate()` accepts it because `isNumber(sellTokenID)` returns true and no length bound is enforced [1](#0-0) .
4. During `execute()`, `matchOrder`/`createAndSaveOrder` call `MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID)` or `expandTokenIdToPriceArray`, which perform `System.arraycopy(tokenId, 0, result, 0, tokenId.length)` into the `TOKEN_ID_LENGTH`-sized array, throwing `ArrayIndexOutOfBoundsException` because `tokenId.length > TOKEN_ID_LENGTH` [2](#0-1) .
5. This `RuntimeException` is not caught by `MarketSellAssetActuator.execute()`'s catch clause [7](#0-6)  and propagates to the caller in `Manager`, whose exact handling of generic `RuntimeException` during block/transaction processing needs to be confirmed in a live/full-repo session to determine final blast radius (single tx rejection vs. node crash/halt).
