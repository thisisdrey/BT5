### Title
Unbounded recursion in `debug/dwarf.(*Data).readType` causes stack-exhaustion DoS on crafted DWARF debug info - (File: src/debug/dwarf/type.go)

### Summary
`debug/dwarf`'s type reader recurses through `readType` → `typeOf` → `readType` for every `AttrType` reference (pointers, typedefs, qualifiers, array/struct members, function params/returns) with no depth counter or limit, unlike every other recursive decoder in the tree (`encoding/asn1`, `encoding/gob`, `encoding/xml`, `encoding/json`, `go/parser`, `regexp/syntax`), which all enforce an explicit `maxDecodeDepth`/`maxNestLev`/`maxHeight` guard. A crafted DWARF `.debug_info`/`.debug_abbrev` section with a long chain of distinct-offset type DIEs (e.g. `TagTypedef → TagPointerType → TagTypedef → ...`, each at a unique, never-before-cached offset) drives `readType`'s recursion depth linearly with attacker-controlled input size, exhausting the goroutine stack and crashing the process — the same primitive as `QuickTimeVideo::multipleEntriesDecoder`'s unbounded recursion on nested atom entries in the reported Exiv2 CVE.

### Finding Description
Attacker-controlled input is an ELF/Mach-O/PE/XCOFF binary containing a `.debug_info`/`.debug_types` section. A normal victim workflow consumes such files via `debug/elf.(*File).DWARF()`, `debug/macho.(*File).DWARF()`, `debug/pe.(*File).DWARF()`, or `internal/xcoff.(*File).DWARF()` (each just wraps `dwarf.New`), and then walks types via `dwarf.Data.Type` / `dwarf.Reader`. This is exactly the kind of path taken by tools like `go tool nm`, `go tool objdump`, symbolizers, and other binary-inspection utilities that operate on files a user points them at, including third-party/untrusted binaries.

- Entry: `(*Data).Type(off Offset)` at `src/debug/dwarf/type.go:375-377`, which calls `d.readType("info", d.Reader(), off, d.typeCache, nil)`.
- Sink: `(*Data).readType` at `src/debug/dwarf/type.go:407` recurses via the local closure `typeOf`, defined at `src/debug/dwarf/type.go:480-497`, which calls `d.readType(name, r.clone(), toff, typeCache, fixups)` for every `AttrType` reference — used for `TagPointerType` (`type.go:766`), `TagConstType/VolatileType/RestrictType` (`type.go:712`), `TagTypedef` (`type.go:809`), struct/array/function members, etc.
- Failed check: `readType` only guards against *cycles* by checking `typeCache[off]` (`type.go:408`) before recursing — it never increments or bounds a recursion-depth counter. Every distinct DIE offset in a fresh chain bypasses the cache check and adds one more stack frame, unlike `encoding/asn1.parseField` (`depth++`, capped at `maxDecodeDepth = 10000`), `encoding/gob`'s `decIgnoreOpFor`/struct engine (`maxIgnoreNestingDepth`), `encoding/xml`'s `maxUnmarshalDepth`, `encoding/json`'s `maxNestingDepth`, and `go/parser`'s `incNestLev`/`maxNestLev`, all of which explicitly cap depth to protect against exactly this kind of crafted-input recursion.
- Sink effect: a sufficiently deep type-reference chain (tens of thousands of unique-offset DIEs, well within an achievable file size) exhausts the goroutine's stack, causing a runtime crash (fatal error, not a recoverable panic) of the consuming process.

### Impact Explanation
This is a denial-of-service via stack exhaustion when reading debug information from an untrusted binary — the direct analog of the Exiv2 `QuickTimeVideo::multipleEntriesDecoder` DoS (unbounded recursion parsing untrusted metadata leading to a crash). It qualifies as a genuine Go PUBLIC-track bug per Go's security policy since it is a real, input-driven parser crash reachable from a standard workflow (inspecting an attacker-supplied binary with any tool built on `debug/elf`, `debug/macho`, `debug/pe`, or `internal/xcoff`'s `DWARF()` accessor), not a hypothetical resource-exhaustion/memory scenario — the crash is a stack overflow triggered by recursive function calls, not unbounded allocation.

### Likelihood Explanation
Any tool that parses DWARF debug info from a file supplied by another party (e.g., a binary uploaded for analysis, a build artifact from an untrusted build, a plugin/shared library) is exposed. The attacker only needs to craft a binary with a valid-looking but deeply chained sequence of type DIEs — no special privileges, no server/host control, just a malicious input file consumed by a normal parsing workflow (`Reader.Next()`/`Data.Type()` walking type info), matching the "ordinary/malicious input file consumed by normal victim workflow" premise.

### Recommendation
Add an explicit recursion-depth parameter to `readType` (and its `typeOf` closure) mirroring the pattern already used elsewhere in the standard library (e.g., `encoding/asn1.parseField`'s `depth` parameter and `maxDecodeDepth` constant): increment a depth counter on each recursive call, and return a `DecodeError` once a reasonable maximum (e.g. on the order of thousands) is exceeded, instead of relying solely on the `typeCache` cycle check.

func (d *Data) readType(name string, r typeReader, off Offset, typeCache map[Offset]Type, fixups *typeFixer) (Type, error) {
	if t, ok := typeCache[off]; ok {
		return t, nil
