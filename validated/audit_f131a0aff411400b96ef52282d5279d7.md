### Title
Object pool path reuse after unsafe `DeleteObjectPool` allows cross-repository object substitution for existing pool members - (File: internal/gitaly/service/objectpool/delete.go)

### Summary
`DeleteObjectPool` deletes an object pool's on-disk repository without verifying or unlinking any member repositories that still reference it via `objects/info/alternates`. A new, unrelated object pool can then be created at the exact same relative path (e.g. via `CreateObjectPool`), so any repository that still has a stale alternates entry pointing at that path will silently begin serving objects from the new pool content instead of the original one — the same "same address, different implementation" problem described in the Aquifer/metamorphic-contract report, but manifested as a deterministic, reusable object-pool disk path rather than a `CREATE2` address.

### Finding Description
An object pool is a plain Git repository located at a path such as `@pools/xx/yy/<sha>.git` [1](#0-0) . Member repositories are linked to a pool purely by writing a relative-path string into `objects/info/alternates` [2](#0-1) . There is no persistent, verified identity binding a member's alternates entry to the specific pool "instance"; it is only a path.

`DeleteObjectPool` removes the pool's directory via `repoutil.Remove` with no safety checks: the RPC comment for `DeleteObjectPool` explicitly documents that "there are no safety checks in place, so if any repository is still using this object pool it will become corrupted" [3](#0-2) , and the implementation performs the deletion unconditionally once the pool resolves [4](#0-3) .

Because the pool's relative path is caller-controlled (bounded only by the `IsPoolRepository` naming pattern, not by any allocation/reservation mechanism tied to the deleted pool's identity) [5](#0-4) , `CreateObjectPool` can recreate a brand-new pool repository at the identical relative path immediately after deletion [6](#0-5) . `objectpool.Create` only checks that nothing currently exists at the target path (`os.Stat`), not whether the path was previously used and may still be referenced by other repositories [7](#0-6) .

Any pool member whose `objects/info/alternates` file still contains the old relative path (because it was never explicitly disconnected via `DisconnectGitAlternates`) will now transparently resolve object lookups into the *new* pool's object store, since `FromRepo`/`linkedToRepository` and Git itself resolve the alternate purely by path comparison, not by pool content identity [8](#0-7) [9](#0-8) . This is the direct structural analog of the Aquifer bug: a deterministic "address" (here, a relative filesystem path used as an alternate-object-directory reference) is reused for a different "implementation" (a completely different Git object store) after the original is destroyed, breaking every consumer's implicit trust in address stability.

### Impact Explanation
A stale pool member (e.g. a fork that was never explicitly `DisconnectGitAlternates`'d, or one that was linked before an administrative/faulty pool deletion) can be made to serve objects — blobs, trees, commits — sourced from a completely different, potentially attacker-controlled pool populated at the same reused path. This is a cross-repository object access/confusion vulnerability: readers of the member repository may retrieve content that did not originate from that repository's own history, undermining repository content integrity and potentially disclosing or substituting object data across repository/tenant boundaries. The documentation already acknowledges the member-corruption consequence of unguarded deletion, but the same path-reuse mechanism additionally allows an attacker who controls the recreated pool's content to determine exactly what those confused reads will surface.

### Likelihood Explanation
Likelihood is moderate: `DeleteObjectPool` is an ordinary mutator RPC reachable by any caller with normal repository-management access (not a privileged internal-only path), and pool relative paths follow a discoverable naming scheme (`@pools/<2hex>/<2hex>/<sha>.git`) rather than being kept secret. The main precondition is that a legitimate member repository must still have a live alternates reference to a pool that gets deleted and recreated at the same path — a realistic operational sequence given that `DeleteObjectPool`'s own documentation warns members are not tracked or safeguarded during deletion.

### Recommendation
- Before deleting an object pool, enumerate and forcibly disconnect (or refuse deletion for) any repositories still referencing it via alternates, or record pool identity (e.g., a content/creation nonce) validated by members at read time rather than relying purely on path equality.
- Alternatively, never allow reuse of a previously-used pool relative path; e.g. salt pool paths with a monotonically increasing counter/timestamp component in addition to the content-derived hash, similar to how `DeriveReplicaPath`/`DerivePoolPath` are meant to give repositories stable, non-recycled identity.
- Add a "tombstone" marker at deleted pool paths for a grace period so `CreateObjectPool` cannot silently reuse a fresh pool of unrelated content at that path.

### Proof of Concept
1. Create object pool `P` at path `@pools/aa/bb/<sha>.git` from repo `A`; link repo `A` to `P` via `LinkRepositoryToObjectPool` (writes `../../@pools/aa/bb/<sha>.git/objects` into `A/objects/info/alternates`).
2. Without calling `DisconnectGitAlternates` on `A`, call `DeleteObjectPool` on `P`. Per the RPC's own documentation, this removes `P` without checking or updating `A`'s alternates file [4](#0-3) .
3. Call `CreateObjectPool` again with the exact same target relative path `@pools/aa/bb/<sha>.git`, cloned from a different, attacker-chosen source repository `B`. `objectpool.Create` only verifies the path is currently empty, so this succeeds [7](#0-6) .
4. Any read against repo `A` for an object ID no longer present in `A`'s own object store but reachable via the stale alternate will now be served by the new pool `P'` (i.e., from repository `B`'s history), demonstrating cross-repository content substitution at a reused, deterministic path.

func IsRailsPoolRepository(repo Repository) bool {
	matches := railsPoolDirRegexp.FindStringSubmatch(repo.GetRelativePath())
	if matches == nil || !strings.HasPrefix(matches[3], matches[1]+matches[2]) {

	return true
}

func getRelativeObjectPath(ctx context.Context, pool, repo *localrepo.Repo) (string, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting repository path: %w", err)
	}

	relPath, err := filepath.Rel(filepath.Join(repoPath, "objects"), poolPath)
	if err != nil {
		return "", err
	}

	return filepath.Join(relPath, "objects"), nil
}

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}

func (s *server) CreateObjectPool(ctx context.Context, in *gitalypb.CreateObjectPoolRequest) (*gitalypb.CreateObjectPoolResponse, error) {
	if in.GetOrigin() == nil {
		return nil, errMissingOriginRepository
	}

	poolRepo := in.GetObjectPool().GetRepository()
	if poolRepo == nil {
		return nil, errMissingPool
	}

	if !storage.IsPoolRepository(poolRepo) {
		return nil, errInvalidPoolDir
	}

	// repoutil.Create creates the repositories in a temporary directory. This means the repository is not created in the location
	// expected by the transaction manager. This makes sense without transactions, but with transactions, there's no real point in
	// doing so given a failed transaction's state is anyway removed. Creating the repository in a temporary directory is problematic
	// as the reference transaction hook is invoked for the repository from unexpected location, causing the transaction to fail to
	// associate the reference updates with the repository.
	//
	// Run the repository creation without the transaction in the context. The transactions reads the created repository's state from
	// the disk when committing it, so it's not necessary to capture the updates from the reference-transaction hook. This avoids the
	// problem for now, and later with transactions enabled by default we can stop creating repositories in unexpected locations.
	ctxWithoutTransaction := storage.ContextWithTransactionID(ctx, 0)
	if err := repoutil.Create(ctxWithoutTransaction, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, poolRepo, func(poolRepo *gitalypb.Repository) error {
		if _, err := objectpool.Create(
			ctxWithoutTransaction,
			s.logger,
			s.locator,
			s.gitCmdFactory,
			s.catfileCache,
			s.txManager,
			s.housekeepingManager,
			&gitalypb.ObjectPool{
				Repository: poolRepo,
			},
			s.localRepoFactory.Build(in.GetOrigin()),
		); err != nil {
			return err
		}

		return nil
	}, repoutil.WithSkipInit()); err != nil {
		return nil, structerr.New("creating object pool: %w", err)
	}

// FromRepo returns an instance of ObjectPool that the repository points to
func FromRepo(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	repo *localrepo.Repo,
) (*ObjectPool, error) {
	storagePath, err := locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, err
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return nil, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return nil, ErrAlternateObjectDirNotExist
	}

	absolutePoolObjectDirPath := altInfo.AbsoluteObjectDirectories()[0]
	relativePoolObjectDirPath, err := filepath.Rel(storagePath, absolutePoolObjectDirPath)
	if err != nil {
		return nil, err
	}

	objectPoolProto := &gitalypb.ObjectPool{
		Repository: &gitalypb.Repository{
			StorageName:  repo.GetStorageName(),
			RelativePath: filepath.Dir(relativePoolObjectDirPath),
		},
	}

	if locator.ValidateRepository(ctx, objectPoolProto.GetRepository()) != nil {
		return nil, ErrInvalidPoolRepository
	}

	return FromProto(ctx, logger, locator, gitCmdFactory, catfileCache, txManager, housekeepingManager, objectPoolProto)
}
