Audit Report

## Title
Panic-inducing false assumption in Snowbridge outbound fee calculation can be triggered by any user, DoSing bridge message submission - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`OutboundQueue::calculate_fee` divides a `FixedU128`-encoded fee by `PricingParameters.exchange_rate` and unwraps with `.expect("exchange rate is not zero; qed")` [1](#0-0) , but `FixedU128::checked_div` returns `None` both on a zero divisor and on internal arithmetic overflow of the scaled multiplication [2](#0-1) . `PricingParameters::validate()` only rejects `exchange_rate == FixedU128::zero()`, leaving no bound against small-but-nonzero values that make the division overflow [3](#0-2) . Because `calculate_fee` is invoked from the public `validate()` entrypoint used by every bridge-send extrinsic, once pricing parameters land in this state, any unprivileged user's ordinary cross-chain message triggers a runtime panic.

## Finding Description
`calculate_fee` computes `FixedU128::from_inner(fee).saturating_mul(params.multiplier).checked_div(&params.exchange_rate).expect("exchange rate is not zero; qed")` [4](#0-3) . The `.expect()` message asserts that `checked_div` can only fail due to a zero divisor, but the generic `CheckedDiv` implementation for fixed-point types returns `None` for a zero divisor *or* when `multiply_by_rational_with_rounding` overflows internally [2](#0-1) . `validate()`, called from the root-only `set_pricing_parameters` extrinsic [5](#0-4) , checks only that each field is nonzero and never bounds `exchange_rate` relative to `fee_per_gas`, `rewards.remote`, or `multiplier` to keep the division result within `u128`. `calculate_fee` is reached from `OutboundQueue::validate()` [6](#0-5) , which is itself invoked by the XCM `EthereumBlobExporter` used for ordinary reserve-asset transfers to Ethereum [7](#0-6) . Existing guards (`validate()`'s zero-checks, and the `defensive_unwrap_or`/`saturating_mul` fallbacks used elsewhere in the same function) do not cover this overflow-on-division case, leaving a bare `.expect()` as the only handling.

## Impact Explanation
A panic during dispatch of a routine, permissionless XCM message-send extrinsic surfaces as a runtime trap during block execution rather than a graceful transaction failure. Once pricing parameters enter the unsafe (but "valid" per `validate()`) range, every subsequent bridge-send transaction from any account hits the same panic, persistently stalling the Ethereum outbound message pipeline — matching the impact-gate category of "public underpriced work that ... stalls bridge processing" and runtime bugs that compromise intended behavior. Funds already committed to a pending transfer are effectively stuck until governance corrects the parameters.

## Likelihood Explanation
`exchange_rate`, `fee_per_gas`, `multiplier`, and `rewards.remote` are periodically adjusted by governance via `set_pricing_parameters`, and `validate()` provides no overflow-safety signal to the operator, only a non-zero check [3](#0-2) . An ordinary, well-intentioned parameter update (e.g., a fee-per-gas increase paired with a depressed exchange rate) can land in the unsafe range undetected. From that point, the trigger condition — any user submitting a bridge message — is deterministic and requires no special attacker capability, and repeats for every subsequent send.

## Recommendation
- Replace `.expect("exchange rate is not zero; qed")` in `calculate_fee` with a fallible path (`ok_or`/`checked_div` handling) that returns a proper `SendError`/`DispatchError` instead of panicking, consistent with the `defensive_unwrap_or` pattern already used in the same function.
- Strengthen `PricingParameters::validate()` to reject `exchange_rate`/`fee_per_gas`/`multiplier`/`rewards.remote` combinations that could overflow the fee-scaling arithmetic, e.g. by performing a trial worst-case computation before accepting new parameters or imposing a sane lower bound on `exchange_rate`.
- Add a regression/fuzz test exercising `calculate_fee` with extreme-but-nonzero `exchange_rate` values to confirm graceful degradation instead of panicking.

## Proof of Concept
1. Governance calls `set_pricing_parameters` with `exchange_rate` set to the smallest positive `FixedU128` value (passes `validate()`'s nonzero check) and realistic-to-high `fee_per_gas`/`rewards.remote`/`multiplier`.
2. Any user performs a normal reserve-asset transfer to Ethereum via the XCM `EthereumBlobExporter`, causing `OutboundQueue::validate()` to call `Self::calculate_fee(gas_used_at_most, T::PricingParameters::get())`.
3. Inside `calculate_fee`, `FixedU128::from_inner(fee).saturating_mul(params.multiplier)` produces a large inner value; `.checked_div(&params.exchange_rate)` overflows internally and returns `None`.
4. `.expect("exchange rate is not zero; qed")` panics despite a nonzero `exchange_rate`, aborting that message-send and every subsequent bridge-send transaction until parameters are corrected by governance.

			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {
		if self.exchange_rate == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.local.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.remote.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}
