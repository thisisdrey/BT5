## Analog Vulnerability Found

### Title
Out-of-bounds pointer arithmetic from unchecked central-directory `offset`/extra-field fields leads to OOB read/write when extracting untrusted zip/jar archives - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses attacker-controlled Central Directory Header fields (`compressed_size`, `uncompressed_size`, `offset`, and the ZIP64 extra-field payload) without any bounds validation against the mapped input buffer, and the resulting `offset` is later used to compute a raw memory pointer whose bounds check (`EnsureRemaining`) is defeated by unsigned-integer underflow. This is directly analogous to `ALPINE-CVE-2016-7948` in libXrandr, where untrusted, length-prefixed "reply" data was trusted without validating that the declared lengths/offsets stayed inside the actual buffer, leading to out-of-bounds memory operations.

### Finding Description
`ProcessCentralDirEntry` reads `compressed_size`, `uncompressed_size`, `offset`, `file_name_length`, `extra_field_length`, and `file_comment_length` straight off the mmap'd file bytes with `get_u4le`/`get_u2le`, with no check that these fields keep `p` inside the Central Directory or the file: [1](#0-0) 

It then walks the extra field records in a loop bounded only by `extra_p != p`, and for a declared ZIP64 tag it unconditionally reads 8 bytes via `get_u8le(extra)` regardless of whether the record's own `data_size` is even large enough to contain 8 bytes, or whether `extra + 8` remains inside the extra-field region: [2](#0-1) 

Unlike `src/tools/singlejar/zip_headers.h`'s `ExtraField::find`, which explicitly validates `start + sizeof(ExtraField) <= end` and `start + size() <= end` before touching an extra field (and is exercised by `output_jar_simple_test.cc`'s `MalformedExtraField` death test), this ijar parser has none of that protection: [3](#0-2) [4](#0-3) 

The unchecked `offset` field returned by `ProcessCentralDirEntry` is then used directly to move the file cursor: [5](#0-4) 

The only guard before dereferencing `p` is `EnsureRemaining`, which computes remaining bytes as `input_file_->Length() - in_offset` using unsigned (`size_t`) arithmetic: [6](#0-5) 

If the attacker-supplied `offset` (fully attacker-controlled, no upper-bound check against `in_length`/central directory bounds at line 515) pushes `p` past the end of the mapped file, `in_offset > input_file_->Length()` and the subtraction underflows to a huge `size_t`, so `n > remaining` is always false — `EnsureRemaining` incorrectly reports success. The code then proceeds to read `file_name_length_`, `extra_field_length_`, `compressed_size_`, `uncompressed_size_` from wild memory, sets `file_name_ = p` and `extra_field_ = p`, and ultimately calls `processor->Process(filename, attr, file_data, uncompressed_size_)` with attacker-influenced, unvalidated size/pointer values: [7](#0-6) 

Because `uncompressed_size_`/`compressed_size_` (potentially poisoned by the OOB ZIP64 extra-field read or by directly-supplied CDH values) drive how much data downstream code copies/writes (e.g. into an output buffer sized from `CalculateOutputLength()`, itself computed from the same untrusted per-entry sizes), the broken invariant — "declared sizes/offsets in archive metadata are bounds-checked against the buffer" — propagates from an out-of-bounds *read* into memory-safety violations in whatever consumes `file_data`/size, mirroring the "reply data mishandling → OOB write" pattern of the CVE.

### Impact Explanation
An attacker who controls the contents of a zip/jar archive consumed by Bazel's `ijar`/`zip_main` tooling (e.g., a `.jar` fetched via `http_archive`/`http_jar`, a dependency artifact, or any archive built into a target that gets processed by `ijar`) can craft a Central Directory Header with an out-of-range `offset` and/or a truncated ZIP64 extra field to make `EnsureRemaining`'s check silently pass on out-of-bounds pointers. This can cause the tool to read past the mapped file (crash / memory disclosure) and to derive corrupted size values used for subsequent data copies, which can manifest as heap corruption or out-of-bounds writes in the ijar/singlejar process. This runs on the build machine as part of ordinary archive processing — not inside a sandboxed action only, since `ijar`/`zip_main`/`singlejar` are native host tools invoked directly by Bazel's build graph.

### Likelihood Explanation
Any build that repackages or strips a jar via `ijar`, or extracts/relinks a zip via `zip_main`/`singlejar`, on an attacker-influenced artifact (untrusted `http_archive`/`http_jar` URL content, a malicious dependency, or files from an untrusted branch a CI job builds) reaches this code path. No credentials, sandbox escape, or privileged access are required — only the ability to supply archive bytes that Bazel's build ingests, which matches the attacker model of the CVE (an unprivileged party serving/publishing hostile bytes that a victim's build consumes).

### Recommendation
- In `InputZipFile::ProcessCentralDirEntry`, validate that `p` (after skipping fixed fields) plus `file_name_length + extra_field_length + file_comment_length` does not exceed the Central Directory bounds before consuming them, and validate `offset + <required local header size>` against `input_file_->Length()` before returning it.
- Fix `EnsureRemaining` to avoid unsigned-underflow: compare pointers (`p >= zipdata_in_` and `p <= zipdata_in_ + input_file_->Length()`) before computing `remaining`, and reject if `p` is already outside the mapped range.
- Bounds-check each extra-field record exactly as `ExtraField::find` does in `src/tools/singlejar/zip_headers.h` (verify `data_size` covers the bytes about to be read, e.g., `data_size >= 8` for a ZIP64 field, and that `extra + data_size <= extra field region end`) before calling `get_u8le`.

### Proof of Concept
A reproducible test analogous to the existing `output_jar_simple_test.cc` `MalformedExtraField`/`CreateZipWithMalformedExtraField` pattern (which already demonstrates the malformed-extra-field death test for singlejar) should be added for `third_party/ijar/zip_main.cc`/`zip.cc`: construct a minimal zip whose single Central Directory Header declares an `offset` field pointing past `input_file_->Length()` (e.g., `0xFFFFFFF0`), and/or whose extra field claims a ZIP64 tag with `data_size` less than 8 bytes near the end of the mapped buffer, then run it through `ZipExtractor::Create`/`ProcessAll()` (as exercised by `third_party/ijar/zip_main.cc`'s `extract()`, and covered by `third_party/ijar/test/zip_test.sh`'s existing `test_no_path_traversal`-style harness) and assert the process either crashes (ASAN heap-buffer-overflow / SEGV) instead of cleanly erroring via `EnsureRemaining`.

**Note on verification confidence:** I was not able to fully trace how `processor->Process()`'s `file_data`/`uncompressed_size_` are subsequently written into the output buffer in `src/tools/singlejar/output_jar.cc` (I only confirmed the extra-field copy logic in `AppendToDirectoryBuffer`/`WriteEntry`'s CDH-copy path, not the exact data-write call site for entry payload bytes) within the available iterations. Confirming an actual out-of-bounds *write* (versus a read-only crash) would require tracing `OutputJar::WriteEntry`'s use of `file_data`/size end-to-end, ideally in a live Devin session with full file access.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
