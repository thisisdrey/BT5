No custom `panic` strategy is set in the workspace `Cargo.toml` profiles, so the default `panic = "unwind"` applies; a panic in the `signer_metrics` thread will unwind and terminate only that thread, not the whole process, but the monitoring server is never restarted, so it dies permanently after a single crafted request.

### Title
Remote unauthenticated crash of the signer monitoring server via socket-close mid-response `.expect()` panics - (File: stacks-signer/src/monitoring/server.rs)

### Summary
`MonitoringServer::main_loop` calls `request.respond(...).expect(...)` for every handled route (`/metrics`, `/info`, `/`, `/heartbeat`, and the 404 fallback). `tiny_http`'s `respond()` returns `io::Result<()>`, which is `Err` if writing the response to the client socket fails (e.g., broken pipe from an early-closed connection). Any unprivileged remote client that can reach the configured `metrics_endpoint` can trigger this by sending a valid request and closing the socket before the response body is fully written, panicking the dedicated `signer_metrics` thread and permanently disabling the monitoring server.

### Finding Description
The claimed fault is real: `request.respond(response).expect("Failed to send response")` at server.rs:134 and the equivalent `.expect("Failed to respond to request")` calls at lines 141, 149, 162, 168 all propagate `respond()`'s `io::Result` failure directly into a panic. [1](#0-0) [2](#0-1) [3](#0-2) 

`tiny_http`'s HTTP `respond` writes headers/body over the underlying `TcpStream`; if the peer resets or closes the connection before the write completes, the underlying I/O returns an `Err`, which `.expect()` converts into an unrecoverable panic in the loop that also owns `self.http_server` (the listener). There is no validation, secret, or auth gate on any of these routes — `main_loop` dispatches purely on `request.url()` string equality with no signature/session check, so any TCP peer able to reach the configured `metrics_endpoint` can hit this path. [4](#0-3) 

The server is spawned once, in its own OS thread, with no supervisor/restart logic: [5](#0-4)  Once the thread panics, the listener socket (owned by that thread) is dropped and the entire monitoring server (metrics scraping for Prometheus, `/heartbeat`, `/info`) is permanently gone for the life of the process — the process itself is not restarted automatically, since std threads panic-unwind rather than abort by default and there is no join/restart of `signer_metrics`.

### Impact Explanation
A single crafted TCP interaction (send a valid GET, then reset/close the socket mid-response) permanently kills the monitoring HTTP server thread for that signer, denying all future `/metrics`, `/info`, and `/heartbeat` requests. This blinds operators' Prometheus scraping and heartbeat/liveness checks for the signer, which is an operationally significant unauthenticated DoS reachable by any party who can open a TCP connection to the metrics port, matching the "Critical - remote crash/unauthenticated DoS from few messages" category. It does not touch consensus, StackerDB, or the P2P/RPC ports covered elsewhere, but it fully and irreversibly disables the monitoring subsystem with a single message and zero privileges.

### Likelihood Explanation
Preconditions are minimal: the signer must have `metrics_endpoint` configured (a documented, common operational setup), and the attacker only needs network reachability to that endpoint — no RPC secret, peer key, or StackerDB slot ownership is required. The attack is trivially repeatable (one TCP connect + close per crash, and the server is already dead after the very first successful one) and costs the attacker nothing beyond opening a socket and closing it early (e.g., via `SO_LINGER` reset or simply dropping the connection during response transmission, which is a common, natural network condition, not just an adversarial one).

### Recommendation
Replace the `.expect(...)` calls in `main_loop` with graceful error handling: match on the `Result` from `request.respond(...)`, log a `warn!`/`debug!` on `Err`, and `continue` the loop instead of panicking. Additionally, consider wrapping `main_loop`'s request-handling body in a way that a single bad request can never terminate the listener (e.g., catch_unwind or per-request error containment) and/or add a supervisor that restarts `MonitoringServer::start` if it returns `Err`.

### Proof of Concept
