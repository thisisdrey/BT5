### Title
Handshake key-swap on already-keyed connections skips signature verification - ([File: stackslib/src/net/chat.rs])

### Summary
In `validate_handshake`, `message.verify_secp256k1(&handshake_data.node_public_key)` is only invoked when `self.connection.get_public_key()` is `None`. When a public key is already on file for the connection (the `Some(_)` branch at chat.rs:1072-1091), the code performs no cryptographic verification of the handshake's signature at all — it only checks, and only for *outbound* connections, that the self-reported `addrbytes`/`port` match the observed peer address. `update_from_handshake_data` (chat.rs:1131-1167), called unconditionally after `validate_handshake` succeeds, then installs whatever `node_public_key` was in the message as the peer's new identity.

### Finding Description
The claimed equality — "the node_public_key installed as a peer's identity after any Handshake == a public key that signed *this exact* Handshake message" — holds only for the first handshake on a connection (`None` branch, chat.rs:1058-1071). For the re-key case (`Some(_)` branch, chat.rs:1072-1091), no call to `verify_secp256k1` exists; the branch's only guard is the outbound address/port match, which:
- does not apply at all to inbound connections (explicitly noted in the comment at chat.rs:1073-1078, "not the case for inbound connections"), and
- even for outbound connections, only checks the claimed address, not the signature over the message.

`handle_handshake` (chat.rs:1214-1251) calls `validate_handshake`, and on `Ok(_)` proceeds directly to `update_from_handshake_data`, which compares the new `pubk` to `cur_pubk` and calls `self.connection.set_public_key(Some(pubk.clone()))` (chat.rs:1150-1164) regardless of whether the message was actually signed by `pubk`. Thus an attacker who can reach an inbound P2P connection that already has a peer's public key on file (e.g., after any prior successful handshake) can send a second `Handshake` message with an arbitrary `node_public_key` and an unrelated or garbage `preamble.signature`, and the node will silently swap in the attacker's key as the peer's authenticated identity without ever validating that the attacker holds the corresponding private key for that new key, let alone the original peer's private key.

### Impact Explanation
This allows unauthenticated identity/key replacement on an established P2P connection: the local peer's `NeighborKey`/pubkey table is corrupted to associate a legitimate peer's address with an attacker-controlled public key, without any signature proof. This can be leveraged to impersonate the peer for subsequent message exchanges gated on peer identity (e.g., signed relay/StackerDB or peer-scoped authorization checks that trust `self.connection.get_public_key()`), which matches "unauthenticated/unauthorized write to state" / identity-spoofing impact categories. It is repeatable per connection and requires no more than sending crafted `Handshake` bytes.

### Likelihood Explanation
Preconditions: the attacker must be able to open (or already control) an inbound TCP/P2P connection to the victim node, complete an initial handshake (trivial, no privilege required — this is exactly how a normal peer connects), and then send a second `Handshake` message with a different `node_public_key` and any/no valid signature. All of this is within an unprivileged remote attacker's capability — no secret, private key of another party, or admin role is needed. It is fully remotely reachable via the P2P port.

### Recommendation
Always call `message.verify_secp256k1(&handshake_data.node_public_key)` in `validate_handshake`, in both the `None` and `Some(_)` branches, so that any handshake — whether establishing a new identity or attempting to re-key — is cryptographically proven to be signed by the `node_public_key` it claims to install. Optionally, for genuine re-key flows, additionally require the new key's ownership be corroborated (e.g., signed continuity proof) rather than trusting address match alone.

### Proof of Concept
Add a test in `stackslib/src/net/chat.rs`'s test module:
1. Establish a `ConversationP2P` for an inbound connection and drive an initial valid `Handshake` (signed by key A) through `handle_handshake`, asserting `self.connection.get_public_key() == Some(A)`.
2. Construct a second `StacksMessage` with `StacksMessageType::Handshake` whose `node_public_key` is key B (different keypair), with `preamble.signature` either zeroed/garbage or signed by an unrelated key C (not B, not A).
3. Call `handle_handshake` again with this message and `authenticated = true`.
4. Assert that the call returns an error (e.g., `net_error::InvalidMessage`) and that `self.connection.get_public_key()` still equals `Some(A)`.
5. Current code will instead return `Ok(_)` from `validate_handshake` (since `Some(_)` branch skips `verify_secp256k1`) and `update_from_handshake_data` will set the public key to B, demonstrating the unauthenticated key swap.
