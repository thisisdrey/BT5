### Title
Unauthenticated POST to `/v3/blocks/upload` triggers network-wide block relay despite `broadcast` being unset/`0` - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
`RPCPostBlockRequestHandler::try_parse_request` only requires authentication when the caller explicitly sets `broadcast=1`; if `broadcast` is omitted or `0`, no auth header is required at all. In `try_handle_request`, the decision to call `node.set_relay_message(...)` (which propagates the block to the P2P network) is gated solely on `data_resp.accepted`, not on `self.broadcast` or authentication status, so an unauthenticated block upload that is accepted by the chainstate is still relayed network-wide.

### Finding Description
In `stackslib/src/net/api/postblock_v3.rs`, `try_parse_request` computes `broadcast` and `authenticated` from the query string/header, and only rejects the request with 401 when `broadcast && !authenticated` (line 120-122). When `broadcast` is absent or `0`, the check `broadcast && !authenticated` is false regardless of the `authenticated` value, so the request is accepted with no authorization at all: [1](#0-0) 

The parsed `broadcast` flag is stored in `self.broadcast` and is passed into `Relayer::process_new_nakamoto_block_ext` merely to control internal validation/storage behavior (`NakamotoBlockObtainMethod::Uploaded`), not whether the block should be relayed: [2](#0-1) 

Crucially, after the call returns, the decision to relay the block to the P2P layer only checks `data_resp.accepted`, which is derived from whether the chainstate accepted the block as valid — it does not consult `self.broadcast` or `authenticated` at all: [3](#0-2) 

This breaks the intended equality: the set of blocks relayed via `set_relay_message` should equal the set of blocks submitted with `broadcast=1` by an authenticated caller, but instead it equals the set of *accepted* blocks regardless of authentication or the `broadcast` flag's value. An unprivileged remote attacker who can produce or replay a block that the node's chainstate considers valid and acceptable (e.g., a legitimately-produced/valid Nakamoto block they merely relay through this endpoint without the secret) can cause `set_relay_message` to be invoked, causing the node to gossip `NakamotoBlocksData` to its peers — using the unauthenticated endpoint as a free relay pathway that was intended to be gated by the auth-checked `broadcast=1` path.

### Impact Explanation
This allows an unauthenticated party to cause a node to propagate a `NakamotoBlocks` message to the P2P network without ever presenting the RPC secret, undermining the intended access control that reserves broadcast to authenticated/trusted callers. This is a network-wide propagation of data via an unauthenticated write path, matching the "unauthenticated/unauthorized write to state ... network-wide propagation of forged data" Critical category — the write into `set_relay_message` state (subsequently disseminated by the p2p layer) is entirely gated by the chainstate's acceptance logic, not by any secret/authorization the endpoint is supposed to enforce for propagation. It is repeatable per accepted block; the attacker's control is limited to whichever blocks the node's chainstate would accept (i.e., not fully "forged" content in the sense of invalid blocks, since chainstate validation still applies), but the authorization bypass for the relay decision itself is real and reproducible.

### Likelihood Explanation
The endpoint `/v3/blocks/upload` is reachable by any unprivileged remote party who can reach the node's RPC port — no privileged role or secret is required to trigger it as long as `broadcast` is omitted or `0`. The attacker only needs a `NakamotoBlock` that the chainstate/`Relayer::process_new_nakamoto_block_ext` will accept (this could be any legitimately valid, already-known block — the attacker does not need to forge an invalid one, just needs any node to accept it via `process_new_nakamoto_block_ext`), making it easy to trigger repeatedly with each such block.

### Recommendation
Gate the relay decision on the same authorization the endpoint intends: only call `node.set_relay_message(...)` when `data_resp.accepted && self.broadcast == Some(true)` (which by construction already implies `authenticated == true`, per the `try_parse_request` check). Do not relay solely based on acceptance.

2. Build an HTTP POST request to `/v3/blocks/upload` (no `broadcast` query param, no `authorization` header) with a body containing a valid, chainstate-acceptable `NakamotoBlock`.
3. Call `try_parse_request` and assert it succeeds (no 401) and `handler.broadcast == Some(false)`.
4. Call `try_handle_request` against a `StacksNodeState` whose chainstate will accept the block (`accepted == true`).
5. Assert that `node.relay_message` (the internal field set by `set_relay_message`) is `Some(StacksMessageType::NakamotoBlocks(...))` even though `handler.broadcast == Some(false)` and no authorization header was sent — demonstrating the auth/broadcast-flag bypass at `stackslib/src/net/api/postblock_v3.rs:198-202`.
