### Title
Replay-window TOCTOU in `ConnectionState.Decrypt` allows duplicate packet delivery to tun - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` releases `decryptLock` between the anti-replay `window.Check` call and the `window.Update` call that commits the counter as seen, decrypting in between while unlocked. When `f.routines > 1`, multiple UDP reader goroutines call `Decrypt` concurrently on the same `hostinfo.ConnectionState` for the same peer, so two threads can both pass `Check` for an identical `messageCounter` before either calls `Update`, letting one attacker-replayed packet be decrypted and delivered to the tun device twice.

### Finding Description
`Decrypt` in [1](#0-0)  takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, releases the lock, performs AEAD decryption unlocked, then re-acquires the lock to call `cs.window.Update(l, messageCounter)`. `Bits.Check` at [2](#0-1)  only tests whether the bit is already set (read-only), and `Bits.Update` at [3](#0-2)  is the point that actually marks the counter as seen. Because these two window mutations are split across separate lock acquisitions with unlocked decryption work in between, two concurrent calls with the same `messageCounter` can both observe `Check == true` before either has called `Update`.

This is reachable because `Interface.run` starts `f.routines` independent goroutines via `listenOut` at [4](#0-3) , each of which calls `f.readOutsidePackets` from `li.ListenOut` at [5](#0-4) , and `readOutsidePackets` calls `hostinfo.ConnectionState.Decrypt(f.l, h.MessageCounter, out, packet, nb)` at [6](#0-5)  for every inbound message packet, keyed only by `hostinfo` (shared per remote peer, not per UDP queue). An attacker who has captured one valid ciphertext/counter for an established session (e.g., replaying an already-observed valid encrypted packet, no key material needed) can send it twice in quick succession so the two copies land on different UDP reader queues (`routines`) and race inside `Decrypt`. If both win the `Check` race, `handleOutsideMessagePacket` at [7](#0-6)  runs twice for the same plaintext, delivering a duplicate packet to the tun device — an actual replay bypass of the anti-replay window, not merely a benign duplicate decrypt attempt.

### Impact Explanation
This is a genuine replay-protection bypass: Nebula's anti-replay window is documented and relied upon to enforce "replayed or out-of-window packets are dropped." The TOCTOU allows an attacker-controlled duplicate UDP datagram (no privileged access needed, source address can be as observed on the wire) to be decrypted and injected into the tun device more than once for the same counter, which is a break of the replay-protection invariant. Scoped impact is limited to duplicate delivery of one previously valid message per race window (bounded by `routines`), not full traffic forgery or decryption without the key.

### Likelihood Explanation
Requires `f.routines > 1` (multi-queue enabled, common on Linux with multiqueue tun support) and requires the attacker to already possess a valid captured ciphertext/counter for the session (either from prior legitimate observation or from replaying their own previously-sent packet in a mesh scenario). The attacker must win a narrow race — send two copies nearly simultaneously so they land on different reader goroutines before the first's `Update` call — which is feasible but non-deterministic and requires repeated attempts to reliably trigger.

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence in `Decrypt` (and `VerifyRelay`), or use a single atomic "reserve" operation, so that `window.Check` and `window.Update` execute in the same critical section as the decryption for a given counter, eliminating the window where two goroutines can both pass `Check`.

### Proof of Concept
Add a concurrency test in `connection_state_test.go`:
1. Construct a `ConnectionState` with a real cipher/keys (as in existing handshake test helpers) and a fixed `messageCounter`.
2. Spawn two goroutines that both call `cs.Decrypt(l, N, out1, packet, nb1)` and `cs.Decrypt(l, N, out2, packet, nb2)` with the same `N` and identical valid ciphertext `packet`, using a `sync.WaitGroup`/barrier to maximize interleaving (e.g., insert a `time.Sleep` or channel signal between `Check` and `DecryptDanger` via a test hook, or run with `-race` and loop many iterations to hit the window).
3. Assert that at most one of the two calls returns `(out, nil)` and the other returns `ErrAlreadySeen`; currently both can return success.
4. Extension: wire this into an `Interface`-level test with `routines=2` sending the same UDP payload twice and asserting `f.readers[q].Write` (tun write path in `handleOutsideMessagePacket`) is invoked at most once for that counter.

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
