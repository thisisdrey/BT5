### Title
NULL Pointer Dereference in `BandwidthProcessor.useAssetAccountNet` on Deleted/Self-Destructed Asset Issuer Account - (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

### Summary
`BandwidthProcessor.useAssetAccountNet()` fetches the TRC10 asset issuer's `AccountCapsule` from the `AccountStore` and immediately dereferences it without a null check, unlike every other account lookup in the surrounding bandwidth-accounting code, which consistently null-checks (`ownerCapsule == null`, `receiverCapsule != null`, `toAccount == null`, etc.). If the issuer account referenced by an `AssetIssueCapsule` no longer exists in the `AccountStore` at consumption time, any ordinary `TransferAssetContract` transaction that consumes free asset bandwidth will trigger an unguarded NPE during transaction/block processing.

### Finding Description
`useAssetAccountNet()` is called from `BandwidthProcessor.consume()` whenever a `TransferAssetContract` is broadcast for an asset the sender does not own, in order to charge/refresh the free bandwidth of the token issuer: [1](#0-0) 

After validating the public/free asset net limits, the method fetches the issuer's account directly and dereferences it with no null guard: [2](#0-1) 

Every comparable account lookup in this class and its callers (`AccountStore.get`) is defensively null-checked before use — e.g. `contractCreateNewAccount()` explicitly returns/handles `toAccount == null`: [3](#0-2) 
and `UnDelegateResourceActuator`/`UnfreezeBalanceActuator` explicitly guard `receiverCapsule` for the documented case of "TVM contract suicide can result in no receiving account": [4](#0-3) [5](#0-4) 

This is structurally the same bug class as CVE-2025-22031: a downstream code path (bandwidth/resource accounting) assumes a referenced object (`AccountCapsule` / PCI `subordinate` bus) is always populated, but an earlier system event (account deletion via contract self-destruct / bus-number exhaustion) can leave the reference absent, and the accounting code was never updated to check for it.

### Impact Explanation
`BandwidthProcessor.consume()` runs inside `TransactionCapsule` processing for every `TransferAssetContract`, which is executed by `Manager` during both transaction pre-execution and block application. An unguarded `NullPointerException` thrown here is not caught as a `ContractValidateException`/`ContractExeException` by the surrounding actuator flow (those exceptions are explicit and checked), so it propagates as an unexpected `RuntimeException`. If reachable, this would crash/interrupt transaction processing on every full node and SR node that applies the block containing such a transaction, producing a denial-of-service / potential chain halt — impact class "node crash or halt" explicitly listed as acceptable in scope.

### Likelihood Explanation
Reachability depends on whether a TRC10 asset issuer address can become a deleted account after issuance — the most plausible route being a smart contract that issues an asset and later self-destructs (`SUICIDE`/`selfdestruct`), which java-tron explicitly acknowledges elsewhere as a possible state (see the "TVM contract suicide" comments in `UnDelegateResourceActuator`/`UnfreezeBalanceActuator`). I was not able to fully confirm within the available tool budget whether `AssetIssueActuator.validate()`/`execute()` restricts asset issuance to non-contract owner addresses, or whether TVM exposes an asset-issue precompile callable from contract code — this is the key open question that determines whether the NPE is actually reachable by an unprivileged party. Given the index/tool budget was exhausted before this could be verified, this should be treated as a **candidate finding requiring confirmation**, not a fully proven exploit path.

### Recommendation
Add a null check on `issuerAccountCapsule` in `useAssetAccountNet()` immediately after the `AccountStore.get()` call (chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java, around line 355), mirroring the defensive pattern already used elsewhere in the same file and in `UnDelegateResourceActuator`/`UnfreezeBalanceActuator`. If the issuer account is missing, either fall back to treating the asset transfer as fee-only (deny free bandwidth) or throw a `ContractValidateException`, so the failure is handled gracefully instead of causing an unchecked NPE during block application. Additionally, confirm/restrict whether `AssetIssueContract` can be issued with a contract-account owner address, since that is the precondition for this code path to be reachable.

### Proof of Concept
Conceptual reproduction (unconfirmed due to inability to verify precondition reachability):
1. Issue a TRC10 asset (`AssetIssueContract`) whose owner address is a smart contract account.
2. Cause that contract account to self-destruct (`SUICIDE`), removing it from `AccountStore` while the `AssetIssueCapsule` referencing its address as owner persists in `AssetIssueStore`/`AssetIssueV2Store`.
3. Broadcast a `TransferAssetContract` for that asset from any unrelated account (not the issuer), with `sameTokenName` closed or open, exercising `BandwidthProcessor.useAssetAccountNet()`.
4. During `BandwidthProcessor.consume()` execution, `chainBaseManager.getAccountStore().get(assetIssueCapsule.getOwnerAddress().toByteArray())` returns `null`, and the subsequent `issuerAccountCapsule.getNetUsage()` call throws `NullPointerException`, crashing transaction processing for the node applying the block.
