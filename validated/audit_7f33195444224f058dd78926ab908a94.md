### Title
RPC cost score is computed from wire bytes, not actual work performed, allowing computationally expensive requests to evade the load-management cost signal - (File: internal/grpc/middleware/costhandler/costhandler.go)

### Summary
The reported bug class is a fee formula that is keyed on the wrong proxy metric (order `strike`) instead of the metric that actually reflects the value/cost of the transaction (`premium`), letting cheap-premium/high-strike trades (e.g. deep OTM calls) pay disproportionately, and zero-premium/zero-strike trades pay nothing — "distorting the core system fee gathering." Gitaly's `costhandler` package has the same structural flaw: the `x-gitaly-cost` signal — which is the analog of a "system fee," feeding Rails/Workhorse and Cloudflare's complexity-based rate limiting — is computed from a static per-RPC-type weight plus a dynamic term based solely on wire bytes transferred, not on the actual CPU/IO/computation performed by the handler.

### Finding Description
`computeCost` derives the cost trailer as `static + dynamic`, where `dynamic` is computed purely from `InPayloadBytes + OutPayloadBytes` divided by 1 MiB: [1](#0-0) [2](#0-1) 

The static component is either a hard-coded override or a coarse default keyed only on the RPC's declared `Operation` type (`Accessor`/`Mutator`/`Maintenance`): [3](#0-2) [4](#0-3) 

This design is explicitly acknowledged in the architecture doc as hiding variance ("the same cost whether it serves 1 MB or 10 GB"), but the flaw is more general than payload-size variance: a client can craft RPC input fields (revision ranges, path filters, deep history walks, negative/zero result-producing filters, etc.) that force the handler to perform an expensive graph walk, pack computation, or other CPU/IO-heavy operation while the *wire bytes transferred* remain minimal, because the filtered/matched result set is small or empty. In that case the cost trailer reflects only the tiny static weight (e.g. `defaultAccessorCost = 1`, or a fixed override like `ListCommits: 6`) plus `dynamic = 0`, even though the actual per-request cost incurred by Gitaly (CPU time, disk I/O, memory) was large — exactly analogous to the zero/near-zero-strike call whose fee (tied to `strike`) collapses to near zero while the actual value/cost (`premium`) is unrelated to that proxy. [5](#0-4) 

### Impact Explanation
`x-gitaly-cost` is the sole signal Gitaly exports for downstream, complexity-based rate limiting/circuit breaking (Rails moving-average circuit breaker, Workhorse `X-Score` header, Cloudflare complexity-based rate limiting): [6](#0-5) [7](#0-6) 

Because this signal can be systematically kept low by crafting request fields that decouple "bytes returned" from "work performed," an ordinary authenticated user can repeatedly issue expensive RPCs (large graph walks, filtered enumerations with near-empty results, deep revision-range operations) that are reported as cheap. This lets an attacker's traffic sail through the upstream complexity-based rate limiter/circuit breaker undetected, undermining the intended outer ring of DoS defense that GitLab.com relies on and enabling sustained resource exhaustion on the Gitaly node while it looks "healthy" to consumers of the cost trailer.

### Likelihood Explanation
The cost computation is deterministic and purely a function of client-controlled request shape versus response bytes; no privileged access, malicious peer, or MITM is required — any ordinary user issuing crafted RPC fields (e.g. path/revision filters against `ListCommits`, `ListBlobs`, `GetBlobs`, etc.) that produce large internal work with small output can trigger the mismatch. It requires no cooperation from Gitaly operators and is reproducible via the public RPC surface.

### Recommendation
Base the dynamic cost component on actual resource consumption measured server-side (CPU time, wall-clock handler duration, git subprocess resource usage, or bytes read from disk/objects walked), rather than solely on transferred wire bytes. This mirrors the Putty fix of moving fee computation off an easily-decoupled proxy (`strike`) onto the metric that actually corresponds to real cost/value (`premium`) — here, real handler resource usage rather than payload size.

### Proof of Concept
1. Identify an RPC with a static-cost override or accessor default that also allows revision/path filtering causing an expensive internal graph walk (e.g. `/gitaly.CommitService/ListCommits`, which is fixed at static cost 6 regardless of walk depth).
2. Send a request whose filters (e.g. a path that touches no commits, or `--all --not` type revision ranges) force git to traverse the entire history/object graph internally but return zero or minimal matching results.
3. Observe that `computeCost` returns `static + 0` (e.g. `6`) via `dynamicCostFromContext`, because `InPayloadBytes + OutPayloadBytes` is small, even though the underlying git subprocess performed a full history/object walk consuming significant CPU/IO — the same value/fee-decoupling behavior described in the source finding for zero/near-zero-strike calls avoiding the system fee.

```go
const (
	defaultAccessorCost    = 1
	defaultMutatorCost     = 5
	defaultMaintenanceCost = 3
	defaultUnknownCost     = 1
)

// byteCostDivisor controls how payload bytes contribute to the cost score.
// Every byteCostDivisor bytes adds 1 to the cost.
const byteCostDivisor = 1 << 20 // 1 MiB

// staticCostOverrides allows per-RPC cost overrides for RPCs that are known to
// be especially cheap or expensive relative to their operation type default.
var staticCostOverrides = map[string]int{
	// Streaming RPCs that transfer large amounts of data.
	"/gitaly.SmartHTTPService/PostUploadPackWithSidechannel": 10,
```

```go
// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}
```

```go
// staticCostForMethod returns the static cost weight for the given full method
// name. It first checks per-RPC overrides, then falls back to a default based
// on the method's operation type from the proto registry.
func staticCostForMethod(fullMethod string) int {
	if cost, ok := staticCostOverrides[fullMethod]; ok {
		return cost
	}

	methodInfo, err := protoregistry.GitalyProtoPreregistered.LookupMethod(fullMethod)
	if err != nil {
		return defaultUnknownCost
	}

	switch methodInfo.Operation {
	case protoregistry.OpAccessor:
		return defaultAccessorCost
	case protoregistry.OpMutator:
		return defaultMutatorCost
	case protoregistry.OpMaintenance:
		return defaultMaintenanceCost
	default:
		return defaultUnknownCost
	}
}
```

```go
// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
}
```

```markdown
### RPC Cost Score (`x-gitaly-cost`)

Gitaly returns a cost score for each RPC as a gRPC response trailer.
Gitaly has the most context about the actual cost of each RPC, making it the right
place to own this value. Rails and Workhorse translate the `x-gitaly-cost`
trailer into an `X-Score` HTTP response header, making the cost signal
available to any upstream rate limiter.

> On GitLab.com, the `X-Score` header feeds Cloudflare's
> [complexity-based rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/request-rate/#complexity-based-rate-limiting).
> Self-managed deployments can use the same header with any upstream
> rate limiter or ignore it.

Static scores are derived from historical data per RPC type. A static score hides
variance (e.g. `PostUploadPackWithSidechannel` is the same cost whether it serves
1 MB or 10 GB), but dynamic cost (bytes transferred, object count) is only known
after the RPC completes. The two approaches can be combined: use the static score
as a base, then reconcile actual cost in a follow-up after Gitaly responds.
```

## Connection to Rails and Workhorse

Gitaly's role in the broader DoS mitigation system is to be the innermost
ring of defense and to communicate two signals outward: node health (for
circuit breaking) and per-RPC cost (for rate limiting).

**What Gitaly provides:**

- `x-gitaly-pressure` gRPC trailer on every response (0.0 = healthy,
  1.0 = saturated) — node health signal
- `x-gitaly-cost` gRPC trailer on every response — per-RPC cost score
- `RESOURCE_EXHAUSTED` gRPC errors when requests are rejected by the
  concurrency limiter or load shedder.

**What Rails does with it:**

- Reads the `x-gitaly-pressure` trailer via a gRPC client interceptor
- Maintains a moving average of pressure per Gitaly storage
- Trips a per-node circuit breaker when sustained pressure is detected
- Translates `x-gitaly-cost` into the `X-Score` HTTP response header for
  upstream consumption

For standard requests, Rails is in the response path:

```plaintext
(upstream rate limiter) <- X-Score header <- Rails <- x-gitaly-cost trailer <- Gitaly
```

For Git operations (clone, fetch, push), Workhorse streams directly
to/from Gitaly — Rails is only in the auth path. Workhorse reads the
`x-gitaly-cost` trailer from the Gitaly response and sets `X-Score` on
the HTTP response to the client:

```plaintext
(upstream rate limiter) <- X-Score header <- Workhorse <- x-gitaly-cost trailer <- Gitaly
                                    |
                           Rails auth response
```
