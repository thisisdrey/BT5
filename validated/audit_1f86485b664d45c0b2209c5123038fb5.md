## Title
Delegated resource type-check can be bypassed by pre-delegating to an undeployed CREATE2 address, then deploying a contract there - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
Multiple actuators/processors that implement TRON's resource-delegation feature explicitly forbid delegating bandwidth/energy to contract accounts, but the check only inspects the *current* `AccountType` of the receiver at the moment the transaction executes. An attacker can pre-compute a `CREATE2` address, have resources delegated to it while it is still a plain (non-existent/normal) account, and only afterwards deploy a contract at that exact address — exactly the "contract disappears/reappears at the same address" technique described in the referenced Blocklist.sol report — thereby bypassing the "Do not allow delegate resources to contract addresses" restriction.

### Finding Description
`FreezeBalanceProcessor.validate()` looks up the receiver account and, if it does not exist, silently creates it as a `Normal` account before checking its type: [1](#0-0) 

The equivalent guard exists in `DelegateResourceProcessor.validate()` and `DelegateResourceActuator.validate()`: [2](#0-1) [3](#0-2) 

All three checks are equivalent to `Blocklist.sol`'s `_isContract(addr)`: they answer "is this address a contract *right now*", not "will this address ever be turned into a contract". Because `CREATE2` (`Op.CREATE2`, implemented in `Program.createContractImpl`) makes the deployed address fully deterministic from `(sender, salt, initcode hash)`, an attacker can:

1. Compute the future contract address off-chain (`WalletUtil.generateContractAddress2`) before deploying anything there: [4](#0-3) 
2. Freeze/delegate bandwidth or energy to that address while it is still empty — the code path treats it as `Normal` and creates the account, so the type check passes.
3. Later deploy a contract at that same address via `CREATE2` — `createContractImpl` in `Program.java` only checks the account didn't already contain a `SmartContract` capsule, it does not un-do or reject prior resource delegation: [5](#0-4) 

The already-granted delegated resources remain attached to what is now a contract account. Only *new* delegation attempts after deployment are rejected, but the resource that was routed in during step 2 stays valid and usable/unfreezable normally, as shown by the project's own regression tests exercising this exact scenario (freeze to a not-yet-existing `CREATE2` address, then deploy, then observe that pre-existing delegated balance still unfreezes normally while new delegation attempts throw): [6](#0-5) 

This is functionally the same bug class as the referenced report: a security-relevant "is this address a contract" check is evaluated at a single point in time and can be defeated by controlling *when* code is placed at an address, because TRON (like EVM) allows deterministic, delayed contract creation via `CREATE2`.

### Impact Explanation
The protocol explicitly disallows routing delegated stake-backed resources (bandwidth/energy, which derive from frozen TRX and affect network-wide `TotalNetWeight`/`TotalEnergyWeight`) to contract accounts — this restriction exists to prevent contracts from acquiring delegated resource weight. The bypass lets an attacker's contract end up holding delegated resource balances anyway, undermining that protocol invariant for accounting of frozen/delegated TRX-backed resources. Combined with `Program.suicide()`'s handling of delegated resources on self-destruct (`transferDelegatedResourceToInheritor`), a contract that has acquired delegated resources through this bypass can subsequently self-destruct and redirect that delegated resource entitlement to an arbitrary inheritor address of the attacker's choosing: [7](#0-6) 
allowing repeated relocation/laundering of delegated resource ownership across attacker-controlled accounts, contrary to the intended one-way, non-contract-only delegation model.

### Likelihood Explanation
The attack requires only ordinary, unprivileged transactions available to any account: a `FreezeBalanceContract`/`DelegateResourceContract` to a self-computed address, and later a `CREATE2` deployment to that same address. No special permissions, validator collusion, or non-standard node behavior are required — it is fully reachable from a single signed transaction sequence by any TRX holder able to freeze/delegate resources.

### Recommendation
Do not rely solely on the receiver's *current* `AccountType` to enforce "no delegation to contracts". Options:
- Reserve/mark predicted `CREATE2` addresses that have received delegated resources so that subsequent contract creation at that address is rejected, or
- Re-validate (and reject/forcibly return) delegated resources if the receiving account is later converted to `AccountType.Contract`, or
- Track delegation eligibility using an immutable, deployment-time-independent property instead of the mutable `AccountType` field.

### Proof of Concept
1. Compute `predictedAddr = generateContractAddress2(factoryAddr, salt, initCode)` without deploying anything there.
2. From `ownerAddress`, freeze/delegate bandwidth or energy to `predictedAddr` (`FreezeBalanceContract`/`DelegateResourceContract` with `receiverAddress = predictedAddr`). This succeeds because `repo.getAccount(predictedAddr) == null` → treated as `Normal`.
3. Deploy the actual contract at `predictedAddr` via `CREATE2` (using `factoryAddr` and `salt` from step 1); `WalletUtil.generateContractAddress2` guarantees the address matches.
4. Confirm the delegated resource balance is still attached to `predictedAddr` (now `AccountType.Contract`) and can be unfrozen/used normally, while any *new* delegation attempt to `predictedAddr` now throws `"Do not allow delegate resources to contract addresses"` — demonstrating the restriction was bypassed for the resources delegated in step 2. This exact flow is already reproduced in the repository's test `testFreezeAndUnfreezeToCreate2Contract`: [6](#0-5)
