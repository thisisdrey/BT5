### Title
Heap buffer over-read parsing untrusted jar central directory entries in `InputZipFile::ProcessCentralDirEntry` - (File: third_party/ijar/zip.cc)

### Summary
`ijar` (Bazel's `.jar` → interface-jar tool, used when building against Java dependencies such as `java_import`/downloaded jars) parses each ZIP central directory entry via `InputZipFile::ProcessCentralDirEntry` without validating declared `file_name_length`, `extra_field_length`, or `file_comment_length` against the actual remaining bytes in the mmap'd input buffer, unlike the sibling `ProcessLocalFileEntry` path which calls `EnsureRemaining` before every field read.

### Finding Description
`FindZipCentralDirectory` only validates that the *aggregate* central directory stays inside the file: `cd.central_dir_offset + cd.central_dir_size > in_length` is rejected. [1](#0-0) 

However, `ProcessCentralDirEntry`, which walks each entry inside that region, never re-checks that an individual entry's declared lengths keep the cursor within `bytes + in_length` (or even within `central_dir_size`). It reads `file_name_length`, `extra_field_length`, `file_comment_length`, then unconditionally does `memcpy(filename, p, len)` and advances `p` by `file_name_length`, then walks the extra-field chain reading `header_id`/`data_size` pairs and dereferencing `get_u8le(extra)` for ZIP64 fields, all with no bounds checks: [2](#0-1) 

This is the same bug class as `mobi_parse_index_entry` in libmobi: an index/directory-style structure inside an attacker-supplied file is parsed by trusting length fields taken directly from the file, and the code advances/dereferences past the actual buffer bounds instead of validating the declared length against the remaining input size. Compare with the correctly-guarded local-header parser in the same file, which calls `EnsureRemaining()` before every field access: [3](#0-2) 

The input file is mmap'd (`zipdata_in_`/`MappedInputFile`), so this is a genuine heap/mmap-based over-read: a crafted last entry near the end of the central directory (or of the file) that declares an oversized `file_name_length`/`extra_field_length` causes `get_u2le`/`get_u4le`/`get_u8le`/`memcpy` to read bytes past the mapped region into adjacent heap/mapped memory, which is then copied into the `filename[PATH_MAX]` buffer and can influence downstream `Accept`/`Process` decisions (potential information disclosure of adjacent memory contents, or a crash/segfault if the read crosses an unmapped page boundary).

Note: I could not fully trace, within the available index, every call site that invokes ijar/`InputZipFile` on attacker-controlled jars during a normal Bazel build (e.g., `java_import`/`ijar` action wiring), nor confirm from source whether the mmap uses a guard page that would turn this into an immediate crash instead of a data leak in all cases. This would need to be verified further before relying on the precise impact.

### Impact Explanation
A hostile origin serving a dependency jar (e.g., a `.jar` file fetched via `http_jar`/`http_archive`/registry artifact) whose content matches its declared `sha256`/integrity value — the checksum only certifies the raw bytes, not that the ZIP structure's internal length fields are consistent — can still contain a malformed central directory entry. When `ijar` processes such a header jar during compilation, the malformed length triggers a heap-based over-read, potentially disclosing adjacent process memory (copied into the entry's filename buffer, which is used in file-acceptance/error-reporting logic) or crashing the build worker.

### Likelihood Explanation
Moderate-to-high: `ijar` runs as part of normal Java compilation actions on every `.jar` input reachable from `java_import`/similar rules, and no additional integrity re-parsing occurs beyond the whole-file checksum, so a hash-matching but structurally malformed jar reaches this code path unmodified.

### Recommendation
Add the same `EnsureRemaining`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before reading `file_name_length`, `extra_field_length`, `file_comment_length` bytes and before parsing each extra-field sub-record (`header_id`/`data_size`), verify the cursor plus the declared length does not exceed `bytes + in_length` (or the known `central_dir_size` bound), and fail with an error message instead of proceeding.

### Proof of Concept
Construct a ZIP/JAR file whose central directory contains a single entry positioned at (or near) the very end of the file, where the entry's `file_name_length` and/or `extra_field_length` fields are set to a large value (e.g., `0xFFFF`) that extends past `bytes + in_length`, while `EOCD`/`central_dir_size` bookkeeping is kept internally consistent so `FindZipCentralDirectory`'s aggregate check passes. Feed this file to the `ijar` binary (`third_party/ijar/zip_main.cc` entry point) or any Bazel action invoking ijar on this jar; `ProcessCentralDirEntry`'s `memcpy(filename, p, len)` and the extra-field walk read past the mapped file bounds, producing a heap-based over-read (crash under ASan/heap-guard, or leaked adjacent bytes copied into the `filename` buffer under a plain build). A JUnit/shell reproduction under `src/test/shell/bazel` (or a native `ijar`-focused C++ test) that generates such a crafted jar with ASan enabled and asserts a clean (non-crashing, error-returning) result would confirm the fix.
