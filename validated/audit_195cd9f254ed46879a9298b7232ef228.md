I found significant evidence: `DelegatedResourceAccountIndexCapsule.getToAccountsList()`/`getFromAccountsList()` grows **unboundedly** on the legacy (pre-optimization) path, and this is directly reachable by an unprivileged transaction broadcaster via `FreezeBalanceActuator`/`DelegateResourceActuator`.

### Title
Unbounded growth of `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` lists enables single-account memory/storage exhaustion DoS - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` (legacy freeze-and-delegate path, taken whenever `!dynamicPropertiesStore.supportAllowDelegateOptimization()`) appends a new receiver/owner address to a single `DelegatedResourceAccountIndexCapsule`'s `toAccounts`/`fromAccounts` repeated field on every unique `(owner, receiver)` delegation pair, with **no upper bound on the list size**.

### Finding Description
In the legacy branch of `delegateResource`, the actuator loads the owner's index capsule, and if the receiver address is not already present, unconditionally calls `ownerIndexCapsule.addToAccount(...)`, then persists the whole capsule back to the store: [1](#0-0) 

`DelegatedResourceAccountIndexCapsule.addToAccount`/`addFromAccount` simply rebuild the protobuf message with one more entry appended — there is no `MAX_SIZE`-style cap analogous to what was added for `ValidateMultiSign`/`BatchValidateSign` (`MAX_SIZE = 5/16`) or `AssetIssueActuator`'s frozen-supply list (`MaxFrozenSupplyNumber`): [2](#0-1) 

Because a freeze-and-delegate transaction only requires a trivial amount of TRX to be frozen (the code path is reachable by any account with a small balance, e.g. `FreezeBalanceContract` with a `receiver_address` set), an attacker can create an unbounded number of distinct receiver addresses (freshly generated ECDSA keypairs cost nothing) and issue one delegate transaction per receiver. Each transaction is cheap (bounded by ordinary bandwidth/energy accounting) but permanently grows both:
1. The single `DelegatedResourceAccountIndexCapsule` value stored under the attacker's own address key (unbounded serialized size), and
2. A distinct index capsule created under every *new receiver address* (each holding a `fromAccounts` entry pointing back to the attacker).

Every full node that processes and later re-serves this data (e.g. via `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` in `Wallet.java`, exposed through `GetDelegatedResourceAccountIndexServlet`) must deserialize the full protobuf list into memory, with no size limit enforced by the store, actuator, or HTTP/gRPC serving layer. Repeated attacker transactions therefore directly grow per-node memory/storage on the hot write path and on any subsequent read path (`JsonFormat.printToString` over the full list), unlike other collections in this codebase (market orders, frozen-supply lists, signature arrays) which were explicitly bounded after presumably similar prior findings.

### Impact Explanation
This is a resource-exhaustion analog to CVE-2022-2906's "attacker gradually erodes memory until the process crashes." A cheap, repeatable, unprivileged transaction (`FreezeBalanceContract` delegating tiny frozen balances to a large number of freshly generated receiver addresses) causes unbounded growth of an in-memory/on-disk data structure that every full node must maintain and can be forced to fully deserialize/serialize on read, degrading node memory and potentially leading to OOM/crash over time — a node availability/DoS impact.

### Likelihood Explanation
Likelihood is high on chains/paths where `allowDelegateOptimization` is not enabled (the legacy `DelegatedResourceAccountIndexStore.get/put` path is retained in the codebase and used whenever the dynamic property is off, and remains part of the historical/legacy data format that full nodes must continue to support and serve). The attack requires only minimal TRX to freeze and delegate, and address generation is free, making the attack cheap to sustain over time.

### Recommendation
Bound the size of `toAccounts`/`fromAccounts` in `DelegatedResourceAccountIndexCapsule` analogous to the `MaxFrozenSupplyNumber`/`MAX_SIZE` patterns already used elsewhere in the codebase (e.g. cap the number of unique delegation counterparties per account, enforced in `FreezeBalanceActuator.validate()`/`delegateResource()` before appending), and/or migrate legacy index maintenance fully to the already-existing per-pair `delegate()`/`unDelegate()` storage scheme (`V2_FROM_PREFIX`/`V2_TO_PREFIX`) that avoids storing an ever-growing single list value.

### Proof of Concept
1. Fund an attacker account with the minimum TRX needed to freeze a small `frozen_balance` for bandwidth/energy (e.g. 1 TRX).
2. In a loop, generate a fresh ECKey, and broadcast a `FreezeBalanceContract` transaction from the attacker account with `receiver_address` set to the new key's address and a minimal `frozen_balance`.
3. Each transaction succeeds and appends one more entry to the attacker's `DelegatedResourceAccountIndexCapsule.toAccounts` (persisted via `delegatedResourceAccountIndexStore.put(ownerAddress, ownerIndexCapsule)`), and creates a fresh `fromAccounts`-holding capsule under each new receiver address.
4. Repeating this thousands/millions of times (bounded only by the attacker's available TRX for minimal freezes and transaction throughput) grows the attacker's index capsule without bound; querying `getDelegatedResourceAccountIndex` for that address forces every serving node to deserialize and JSON-serialize the entire unbounded list, consuming increasing CPU/memory per request as the list grows.

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()

        .build();
  }

  public void removeToAccount(ByteString toAccount) {
    if (getToAccountsList().contains(toAccount)) {
      List<ByteString> toList = new ArrayList<>(getToAccountsList());
      toList.remove(toAccount);
      setAllToAccounts(toList);
    }
  }
