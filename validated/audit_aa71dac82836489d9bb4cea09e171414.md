### Title
Dust deposit/transfer fills victim's per-account token list to `MAX_TOKENS_PER_USER`, blocking deposits and issuance - (File: contracts/Pool.sol)

### Summary
The pool enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of `debtTokensOfAccount` and `depositTokensOfAccount`. Any deposit-token transfer or deposit to an account whose balance in that token was zero adds the token to the account's list, reverting with `UserReachedMaxTokens` once the cap is reached. An unprivileged attacker can deposit or transfer dust amounts of every listed deposit token to a victim address, permanently filling the victim's list and blocking the victim from depositing new collateral types, being issued new debt tokens, or receiving seized collateral — a griefing DoS of core pool functions. [1](#0-0) 

### Finding Description
`Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`. [2](#0-1) 

Two permissionless paths add a token to an arbitrary victim's list:

1. `DepositToken.deposit(amount_, onBehalfOf_)` mints to `onBehalfOf_`; `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance is 0. The attacker deposits dust on behalf of the victim — no consent needed. [3](#0-2) [4](#0-3) 
2. `DepositToken.transfer`/`transferFrom` → `_transfer` adds the token to the recipient's list on a dust transfer. [5](#0-4) 

Analogously, `DebtToken.issue(amount_, onBehalfOf_)` fills `debtTokensOfAccount`, pushing the victim toward the shared 30-slot cap with debt they never wanted.

### Impact Explanation
- The victim cannot deposit into any deposit token they don't already hold (each `deposit` → `_mint` → `addToDepositTokensOfAccount` reverts).
- The victim cannot be issued debt in a new synthetic asset (`issue`/`mint` → `addToDebtTokensOfAccount` reverts), blocking borrowing of additional synth types.
- `Pool.liquidate` → `DepositToken.seize` → `_transfer` reverts if the liquidator/recipient list is full, which can degrade liquidation reliability for heavily-griefed accounts.
- Effects are recoverable only by the victim fully zeroing dust balances (`removeFromDepositTokensOfAccount` triggers only when balance hits 0), at cost and friction to the victim — matching the accepted-impact class of temporary freezing/DoS of core functions. [6](#0-5) 

### Likelihood Explanation
Fully permissionless. Cost is only dust underlying for up to 30 deposit calls plus gas — comparable to the fee-only cost of the reported Pontis attack, but cheaper since the attacker retains collateral value. No privileged role, oracle, or governance precondition is needed; it works on deployed configuration (`MAX_TOKENS_PER_USER` is a constant).

### Recommendation
Charge a minimum deposit, or require `onBehalfOf_ == _msgSender()` (or explicit opt-in/allowance) for first-time additions, so third parties cannot grow a victim's per-account list. Alternatively, only add tokens to the list on actions initiated by the account owner and track reward/health membership separately.

### Proof of Concept
```solidity
// Attacker: for each listed deposit token d in pool.getDepositTokens():
//   IERC20(d.underlying()).approve(d, dust);
//   d.deposit(dust, victim);   // mints dust msdTOKEN to victim, adds to victim's list
// After 30 tokens fill the list:
//   victim calls legitDepositToken.deposit(x, victim) -> revert UserReachedMaxTokens
//   debtToken.issue(y, victim)                      -> revert UserReachedMaxTokens
// Victim must spend gas transferring each dust balance to a sink to restore access.
```
Reproducible on a mainnet/Base fork of the deployed `Pool` (see `deployments/base/Pool.json`), exercising `DepositToken.deposit` with `onBehalfOf_ = victim` for each registered deposit token, then asserting `UserReachedMaxTokens` on the victim's next deposit.

    function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
