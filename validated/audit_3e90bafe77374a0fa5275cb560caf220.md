### Title
Unvalidated attacker-controlled length/offset fields in TVM precompiled-contract array extraction cause out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` decode a variable-length array structure out of raw precompiled-contract call data by reading length and offset fields directly from attacker-controlled `DataWord[] words` and then slicing the underlying `data` buffer with `extractBytes`, which performs no bounds checking before calling `Arrays.copyOfRange`. [1](#0-0) 

### Finding Description
`extractBytesArray(DataWord[] words, int offset, byte[] data)` and `extractSigArray(DataWord[] words, int offset, byte[] data)` read a count (`len`) and, per element, an offset (`bytesOffset`) and length (`bytesLen`) purely from `words[...].intValueSafe()`, i.e. values taken verbatim from the calldata a caller supplies to the precompiled contract. These values are then used to compute `(bytesOffset + offset + 2) * WORD_SIZE` and passed straight into `extractBytes`: [2](#0-1) 

`extractBytes` performs `Arrays.copyOfRange(data, offset, offset + len)` with no validation that `offset >= 0`, `len >= 0`, or `offset + len <= data.length`. This mirrors the root cause of CVE-2017-2895: a length/offset field taken from an untrusted, network-reachable message is used to slice a buffer without verifying it stays within the buffer's real bounds. In the MQTT case this caused an out-of-bounds read; here the equivalent operation (`Arrays.copyOfRange` with an out-of-range or negative index) throws an unchecked `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` deep inside precompiled-contract execution that is invoked synchronously as part of TVM opcode dispatch for a `CALL`/`STATICCALL` to a precompiled address.

`extractBytes32Array` has the same unguarded pattern using `words[offset + i + 1]` with no bound check against `words.length`, risking `ArrayIndexOutOfBoundsException` on the `words` array itself. [3](#0-2) 

By contrast, other length-driven parsers in the same codebase area (`RLP.calcLength`/`verifyLength`, `ContractEventParser.subBytes`, `TronJsonRpcImpl.tryDecodeRevertReason`) explicitly validate that the declared length/offset stays within the source buffer before slicing, as shown by their dedicated bounds checks and unit tests for malformed/oversized lengths. [4](#0-3) [5](#0-4) 

`extractBytesArray`/`extractSigArray`/`extractBytes32Array` lack this equivalent validation.

### Impact Explanation
Because these helpers are exercised from precompiled-contract `execute()` paths that are reachable by any contract deployer/caller issuing a `CALL` to the relevant precompiled address with attacker-crafted call data, a malicious but unprivileged transaction sender can trigger an uncaught runtime exception during TVM execution. Depending on how the exception propagates through the `Program`/`Runtime` call stack (which I was not able to fully trace within the available iterations), this is at minimum a contract-execution failure and, if not caught at a sufficiently high layer, could destabilize block processing for the node executing the transaction — a resource/availability impact analogous to the DoS component of CVE-2017-2895.

### Likelihood Explanation
High: the trigger requires only constructing calldata with an out-of-range or negative offset/length word and calling the relevant precompiled contract address — an action available to any unprivileged account able to broadcast a transaction that invokes a smart contract, with no special permissions needed.

### Recommendation
Add explicit bounds validation in `extractBytes`, `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` mirroring the pattern already used in `RLP.verifyLength`/`ContractEventParser.subBytes`: reject (return empty/false or throw a handled `ContractValidateException`) whenever `offset < 0`, `len < 0`, `offset + len > data.length`, or `offset + i + 1 >= words.length`.

### Proof of Concept
I was unable to identify, within the remaining tool budget, the exact precompiled-contract address/selector that invokes `extractBytesArray`/`extractSigArray` (needed to construct a concrete end-to-end transaction PoC), nor to confirm whether an exception thrown from `extractBytes` is caught and safely converted into a reverted transaction somewhere higher in the TVM call stack versus propagating uncaught. This should be verified with a Devin session that has full repository/runtime access before treating this as a confirmed exploitable finding — I flag this explicitly as unverified rather than asserting node crash as proven fact.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }
