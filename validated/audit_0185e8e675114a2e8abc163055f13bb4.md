### Title
Collateral exhaustion leaves permanently uncollectible synthetic debt - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate()` allows a liquidation to seize substantially all of an underwater account’s collateral while repaying only the portion of debt covered by that collateral. Once the account’s `DepositToken` balance reaches zero, there is no collateral left to incentivize repayment of the remaining `DebtToken` balance, leaving permanent bad debt. [1](#0-0) 

### Finding Description
`quoteLiquidateMax()` caps repayment at the lower of `maxLiquidable * debt` and the debt amount purchasable with the account’s full collateral balance. [2](#0-1)  For an underwater account, the collateral-derived amount is lower, so `liquidate()` can burn that partial debt amount while transferring nearly all collateral to the liquidator and fee collector. [3](#0-2) 

The residual debt is not written off, auctioned, covered by a reserve, or otherwise resolved. Because the account no longer holds the seized `DepositToken`, subsequent liquidations cannot recover the remaining debt. Interest also continues to accrue through `DebtToken.accrueInterest()`, increasing the uncollectible obligation and minting the corresponding synthetic-token claim to the fee collector when possible. [4](#0-3) 

An unprivileged borrower can open a maximally leveraged position through `DebtToken.issue()`, retain the issued synthetic tokens, and default after collateral value falls or interest makes the position underwater. [5](#0-4)  A separate unprivileged liquidator can then call the public `Pool.liquidate()` function. The borrower can abandon the residual debt and use another account for future positions.

### Impact Explanation
The protocol’s collateralization invariant breaks: circulating synthetic tokens remain matched to `DebtToken` accounting, but part of that debt has no collateral or realistic repayment incentive backing it. This creates persistent protocol insolvency rather than a recoverable negative balance.

### Likelihood Explanation
Liquidation depends on external callers; no privileged keeper is required to create the condition. Borrowing near the collateral-factor limit, collateral-price movement, and continuous interest accrual can make a position undercollateralized before liquidation completes. Once liquidation exhausts the collateral, the residual debt has no economic mechanism for collection.

### Recommendation
When liquidation consumes the last material collateral of a position, explicitly resolve the remaining debt as bad debt through an insurance reserve, debt auction, controlled write-off, or socialized-loss mechanism. Track uncovered debt separately and prevent abandoned accounts from leaving obligations economically invisible to the protocol. Maintain a collateral buffer and liquidation incentive calibrated to expected interest accrual and oracle update latency.

### Proof of Concept
A Hardhat test can reproduce the condition using the existing `Pool.test.ts` deployment flow:

```ts
// Attacker deposits collateral and borrows near the issuance limit.
await met.connect(attacker).approve(msdMET.address, ethers.constants.MaxUint256);
await msdMET.connect(attacker).deposit(collateralAmount, attacker.address);
await msEthDebtToken.connect(attacker).issue(debtAmount, attacker.address);

// Collateral price falls so debt exceeds the collateral value.
await masterOracle.updatePrice(met.address, underwaterMetPrice);

// A separate liquidator repays only the amount covered by all collateral.
const amountToRepay = await pool.quoteLiquidateMax(
  msEth.address,
  attacker.address,
  msdMET.address
);

await pool.connect(liquidator).liquidate(
  msEth.address,
  attacker.address,
  amountToRepay,
  msdMET.address
);

// Collateral is exhausted, but debt remains.
expect(await msdMET.balanceOf(attacker.address)).to.be.closeTo(0, dust);
expect(await msEthDebtToken.balanceOf(attacker.address)).to.be.gt(0);

// A subsequent attempt to seize collateral cannot clear the remaining debt.
expect(await msdMET.balanceOf(attacker.address)).to.eq(0);
expect(await pool.debtOf(attacker.address)).to.be.gt(0);
```

The repository’s existing underwater-liquidation tests already demonstrate the same end state: the deposit balance approaches zero while the `DebtToken` balance remains greater than zero. [6](#0-5)
