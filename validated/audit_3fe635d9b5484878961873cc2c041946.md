### Title
Internal ledger over-credits deposits of fee-on-transfer NEP-141 tokens, breaking custody conservation and freezing other depositors' funds — (`contracts/defuse/src/contract/tokens/nep141/deposit.rs`)

### Summary
`Contract::ft_on_transfer` credits the internal multi-token ledger with the full `amount` reported in the NEP-141 `ft_on_transfer` callback, without verifying that this amount was actually received by the contract. If the underlying NEP-141 token deducts a transfer fee (a "fee-on-transfer" token), the contract's real balance in that token will be smaller than the sum of balances it credits internally, breaking the invariant that total internal balance for a `TokenId` equals the actual custodied amount.

### Finding Description
`ft_on_transfer` unconditionally credits `amount.0` (the value reported by the sender/token contract in the NEP-141 callback) to the receiver's internal balance via `self.deposit(...)`: [1](#0-0) 

`deposit()` mints exactly that amount into both the receiver's `token_balances` and the global `total_supplies` for that `TokenId`, with no check against the actual FT balance now held by the contract: [2](#0-1) 

Per the NEP-141 pattern (mirroring the ERC-20 fee-on-transfer issue in the referenced Aura report), the `amount` parameter delivered to `ft_on_transfer` reflects what the sender/token contract *claims* to move, not necessarily the net balance increase the contract actually receives if the token applies an internal transfer fee. Since `defuse` accepts arbitrary, unwhitelisted NEP-141 tokens through this permissionless entrypoint, any token with such a fee mechanism will cause `total_supplies[token_id]` (the sum of all users' credited internal balances) to exceed the contract's real on-chain balance of that token.

The mismatch is invisible until withdrawals are attempted. `ft_withdraw`/`ft_force_withdraw` burn the credited amount from the internal ledger and attempt an actual `ft_transfer`/`ft_transfer_call` for that same amount: [3](#0-2) 

Because the contract's real token balance is smaller than the aggregate credited balances, whichever depositor(s) attempt to withdraw once the real balance is depleted will have their `ft_transfer` fail (insufficient FT-contract balance), and the resolver refunds the failed amount back into the internal ledger: [4](#0-3) 

This does not fix the underlying shortfall — it merely restores the phantom internal balance for the affected account, which can now never be redeemed for real tokens because the FT-contract balance backing it no longer exists (it was consumed by earlier withdrawers). Users who withdraw first fully drain the real balance at the expense of users who withdraw later, all while their internal balances were credited symmetrically for the same nominal deposit amount.

### Impact Explanation
This breaks the core custody equality that must hold in `defuse`: `sum(internal balances for token_id) == actual token_id balance held by the contract`. Once a fee-on-transfer NEP-141 token is deposited by any unprivileged user, this equality is violated at credit time. Later, whichever user(s) attempt to withdraw after the shortfall has been consumed by earlier withdrawers will have their withdrawal fail, and their credited internal balance becomes permanently unbacked and irredeemable — funds are effectively frozen for those users, while earlier withdrawers extract more real value than they were entitled to. This matches the High/Critical impact bar of a broken conservation/custody invariant leading to permanently frozen funds for at least some users.

### Likelihood Explanation
No privileged role, DAO action, or special configuration is required: `ft_on_transfer` is a public NEP-141 receiver callback reachable by anyone attaching any NEP-141 token via `ft_transfer_call`, and `defuse` does not restrict deposits to a vetted allowlist of "safe" (non-fee) tokens in this code path. Any fee-on-transfer NEP-141 token deposited by any user (attacker or otherwise) triggers the shortfall; multiple depositors of the same fee-bearing token are sufficient to realize the loss for whichever depositor withdraws last.

### Recommendation
Do not trust the `amount` parameter of `ft_on_transfer`/`mt_on_transfer` as the true received amount. Either: (1) query the token's real balance held by the contract before and after the transfer and credit only the actual delta, or (2) explicitly document and enforce (e.g., via an allowlist checked at deposit time) that only tokens without transfer fees may be deposited, rejecting/panicking on `ft_on_transfer` calls from tokens not on the allowlist.

### Proof of Concept
1. Deploy (or use) a NEP-141 token contract that deducts a transfer fee on `ft_transfer`/`ft_transfer_call` (e.g., burns or redirects X% of each transferred amount).
2. User U1 calls `ft_transfer_call(defuse, 1000, msg)`. The fee token delivers only 900 real tokens to `defuse`'s balance on the token contract, but the token contract's callback still reports `amount = 1000` to `ft_on_transfer`. `defuse` credits U1 with 1000 internal units for that `TokenId`, per `contracts/defuse/src/contract/tokens/nep141/deposit.rs:38-43` and `contracts/defuse/src/contract/tokens/mod.rs:38-64`. Contract's real balance: 900; internal `total_supplies`: 1000.
3. User U2 repeats the same deposit of 1000. Real balance becomes 1800; internal `total_supplies` becomes 2000.
4. U1 withdraws 1000 via `ft_withdraw`. The underlying `ft_transfer(U1, 1000)` succeeds because real balance (1800) still covers it. Real balance drops to 800; `total_supplies` drops to 1000 (U2's remaining phantom credit).
5. U2 attempts to withdraw their credited 1000. The underlying `ft_transfer(U2, 1000)` fails because the contract's real balance is only 800. `ft_resolve_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:157-195`) detects the failure and refunds the full 1000 back into U2's internal ledger — but this internal balance is now permanently unbacked by real tokens, since the shortfall has already been consumed by U1's earlier successful withdrawal.

impl Contract {
    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        if !mint_event.amounts.is_empty() {
            MtEvent::MtMint([mint_event].as_slice().into())
                .check_refund()?
                .emit();
        }

        Ok(())
    }

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
