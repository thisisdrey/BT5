### Title
Replayed handshake stage-1 packet from a spoofed UDP source can redirect an established tunnel's remote address (`ErrAlreadySeen`/`SetRemoteIfPreferred` path) - (File: `handshake_manager.go`)

### Summary
The externally reported bug is a signature/authorization-reuse issue: a validly-signed message (bound only to the signer and amount, not to the intended target instance) can be captured and replayed by a third party into a different context to redirect the outcome. Nebula has an analogous gap in how it treats a *replayed* (not newly forged) handshake stage-1 packet: `HandshakeManager.beginHandshake` → `CheckAndComplete` only compares raw bytes of the incoming packet against the cached stage-1 packet to detect "already seen" handshakes. It does not bind that decision to the actual origin of the packet. When a match is found, `handleCheckAndCompleteError`'s `ErrAlreadySeen` branch calls `existing.SetRemoteIfPreferred(f.hostMap, via)`, where `via.UdpAddr` is simply whatever unauthenticated source address the packet arrived from.

### Finding Description
`HandshakeManager.beginHandshake` builds a responder `Machine`, and once it has parsed the current packet (`packet[header.Len:]`) it calls `CheckAndComplete`, which compares the new packet's raw stage-1 bytes to the ones stored on any existing `HostInfo` for that VPN address: [1](#0-0) 

This is a legitimate optimization for real retransmits, but the equality check is purely on packet bytes — it has no way to distinguish "the real initiator retransmitted because of packet loss" from "an attacker recorded the initiator's stage-1 packet off the wire and replayed it later from a different, spoofed UDP source address." UDP has no source-address authentication at this layer; a stage-1 handshake packet observed on the network path can be resent by anyone.

When `ErrAlreadySeen` is returned, the handler does this: [2](#0-1) 

`SetRemoteIfPreferred` is invoked with `via` — the sender of the replayed packet — and, if that address is judged "preferred" (see `preferredRanges`/promotion logic in `hostmap.go`), it can change the tunnel's active remote address. Additionally, the cached stage-2 response (`existing.HandshakePacket[handshakePacketStage2]`) is unconditionally resent to `via`, i.e., to whatever address supplied the replayed bytes, not to the real initiator's current address.

This mirrors the structural weakness in the reported liquidity-pool bug: a piece of previously-valid authenticated material (there, a permit signature; here, a captured handshake packet) is accepted in a context/identity binding weaker than intended, and a third party who is not the original party can trigger state changes (there, redemption from an unintended pool; here, redirection of where response/data traffic for an established tunnel is sent) using only knowledge of the previously-observed authenticated artifact, without needing any new authentication of their own.

### Impact Explanation
An off-path attacker who can eavesdrop (or otherwise obtain) a single stage-1 handshake packet between two legitimate Nebula peers can replay it, spoofing the UDP source address, to the responder. Depending on the `preferredRanges` configuration and `SetRemoteIfPreferred` logic, this can cause the responder to shift where it sends encrypted traffic for that tunnel (remote-address/state poisoning), and it forces the responder to (re)transmit the cached handshake response toward the attacker-chosen address — an amplification/redirection primitive that requires no valid certificate and no ability to complete the Noise handshake itself, since the attacker only replays previously observed ciphertext.

### Likelihood Explanation
Requires only the ability to observe one legitimate stage-1 packet on the network path (e.g., a shared LAN, a compromised router, or any position with visibility into UDP traffic between two nebula nodes) and to send a UDP packet with a spoofed source address to the responder — both are commonly achievable network-level capabilities and require no CA-signed certificate, no completed handshake, and no possession of any private key.

### Recommendation
Do not treat matching stage-1 packet bytes from an arbitrary source as authorization to mutate `HostInfo` remote-address state or to react to `via` as if it were the original initiator. Any address-promotion / "preferred remote" decision and any decision to resend cached handshake material should require completion of the actual cryptographic handshake (i.e., possession of the private key material, verified via the Noise transcript) from that address, not merely a byte-identical replay of previously-seen ciphertext. At minimum, `SetRemoteIfPreferred` should not be invoked from the `ErrAlreadySeen` branch based solely on packet-byte equality, and resending of the cached stage-2 response should be rate-limited/bound to addresses that have some prior binding to the vpn address (e.g., previously-known/lighthouse-verified addresses) rather than any UDP source.

### Proof of Concept
1. Attacker positioned to observe UDP traffic between node A (initiator) and node B (responder) captures A's stage-1 handshake packet (`header.Handshake`, `MessageCounter == 1`) sent to B.
2. After the real handshake between A and B completes and B has cached `HandshakePacket[handshakePacketStage0]` for the resulting `HostInfo`, the attacker crafts a UDP packet with the exact same payload as the captured stage-1 packet but with a spoofed source `UdpAddr` (e.g., `attacker.example:PORT`), and sends it to B.
3. B's `HandleIncoming` routes it to `beginHandshake` (since `RemoteIndex == 0` for a stage-1 packet), which processes the noise message and reaches `CheckAndComplete`; because the raw bytes match the cached stage-1 packet on the existing `HostInfo`, `ErrAlreadySeen` is returned per `handshake_manager.go:436-444`.
4. `handleCheckAndCompleteError`'s `ErrAlreadySeen` case calls `existing.SetRemoteIfPreferred(f.hostMap, via)` with `via` pointing at the attacker's spoofed address, and resends the cached stage-2 handshake response to that same address (`handshake_manager.go:1103-1113`), demonstrating that a mere byte-for-byte replay — without completing any handshake or presenting a certificate — can influence remote-address decisions and traffic direction for an already-established tunnel.
