### Title
Fee bypass by splitting Nep245/Imt TokenDiff trades into per-unit (delta=-1) intents - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` (lines 206-216) returns `Pips::ZERO` for any `TokenIdType::Nep245`/`TokenIdType::Imt` delta whose absolute value is `<= 1`, and this special-case is evaluated independently for every individual `TokenDiff` intent processed by `execute_intent`. Because the Verifier settles fees per-`TokenDiff`-intent rather than on the aggregate net delta a signer causes for a `TokenId` across a batch, a signer can split one large negative delta into many separate `delta == -1` `TokenDiff` intents to make every call hit the zero-fee branch, paying nothing on what is economically a bulk trade.

### Finding Description
The broken binding: `sum(TokenDiff::token_fee(id, 1, fee).fee_ceil(1) for i in 1..=N)` should equal `TokenDiff::token_fee(id, N, fee).fee_ceil(N)` for the same `TokenId` and aggregate settled amount, but it does not — the left side is always `0` for `Nep245`/`Imt`, while the right side is `fee.fee_ceil(N) > 0` whenever `N > 1` and `fee > 0`.

Root cause, in `contracts/defuse/core/src/intents/token_diff.rs`: [1](#0-0) 
This function is called from `execute_intent` on a per-`TokenDiff`-intent basis: [2](#0-1) 
There is no accumulation of the signer's net delta for a given `TokenId` across multiple `TokenDiff` intents (whether they appear as multiple entries inside one `MultiPayload`/`DefuseIntents` message, or across multiple separately signed `MultiPayload`s executed in the same `execute_intents` call via `Engine::execute_signed_intents`). Each `TokenDiff::execute_intent` call independently computes `Self::token_fee(token_id, amount, protocol_fee)` using only that single intent's `amount = delta.unsigned_abs()`.

An attacker who wants to move `N` units of a Nep245/Imt `TokenId` out of their balance (in exchange for `N` units — or any amount — of counter-value elsewhere, settled via `TransferMatcher::finalize`, which only requires that all deltas across the whole `execute_signed_intents` batch net to zero, not that any single intent be large) can instead submit `N` separate `TokenDiff` intents, each with `delta == -1` on the same `TokenId`, matched by `N` correspondingly small positive counter-deltas (e.g., `+1` each) on the other leg. Because `TransferMatcher::finalize` only cares about the aggregate per-token balance across the whole batch and not about how many separate intents contributed to it, this settles identically to one big trade, but `token_fee` is evaluated at `amount = 1` each time, returning `Pips::ZERO`.

None of the referenced guards prevent this: `MultiPayload::verify`, `has_public_key`, `verify_intent_nonce`, nonce commitment, and `TransferMatcher::finalize`'s zero-sum check are all about signature/replay/balance-conservation, not about per-token fee aggregation. The fee computation is a local, per-call decision inside `TokenDiff::execute_intent` with no cross-intent state, so nothing prevents the split.

### Impact Explanation
Protocol fees on Nep245/Imt token trades are under-collected: the `fee_collector` receives `0` fee_collected instead of `fee.fee_ceil(N)` for a trade equivalent to a single `delta = -N` diff. This matches the "protocol fees bypassed" Critical category since any unprivileged signer can reduce their fee obligation to zero on any Nep245/Imt-denominated leg of a trade simply by chunking it into unit-sized `TokenDiff` intents, and is repeatable across every trade, account, and applicable `TokenId` (any multi-token/Imt asset), scaling the loss to the entire protocol fee revenue on that token class.

However, this is intentional-looking, existing "no fee on `|delta| <= 1`" behavior baked into `token_fee`'s design (per the code comment "do not take fees on NFTs and MTs with `|delta| <= 1`"), and the exploit's practicality is bounded by transaction/gas overhead and complexity of constructing N distinct matched legs in a single settled batch — but the rules explicitly classify "gas or storage consumption" concerns as out of scope, so cost alone doesn't disqualify it if the fee bypass is real and demonstrable.

### Likelihood Explanation
- Preconditions: attacker needs no special role — just their own Verifier balance of the Nep245/Imt token and the ability to construct/sign `MultiPayload`s and call `execute_intents`, all within the stated unprivileged attacker capabilities.
- Feasibility: splitting into `N` `TokenDiff` intents (either as multiple intents inside one signed payload, or multiple `MultiPayload`s in one `execute_signed_intents` batch) requires only routine message construction; each `delta = -1` step needs a matched `+1` (or matched-value) counter-leg, which the attacker can self-provide (self-trading across their own diffs) or arrange with a cooperating counterparty, since `TransferMatcher::finalize` only requires the whole batch nets to zero per token.
- Repeatability: fully repeatable for every trade the attacker wants to execute on any Nep245/Imt `TokenId`, with no rate limiting relevant to fee collection.

### Recommendation
Aggregate the net delta per `TokenId` per signer (or per settlement batch) before evaluating `token_fee`'s `amount <= 1` exemption, rather than evaluating it independently on each individual `TokenDiff` intent's own delta. E.g., compute fees after summing all `TokenDiff` deltas for the same signer/token within `Engine::execute_signed_intents`, or restrict the zero-fee exemption to only apply when the token's `TokenIdType` genuinely represents a non-fractional NFT-like unit (as tracked by token metadata) rather than an arbitrary Nep245/Imt token whose "amount" is a mutable, attacker-chosen decomposition.

### Proof of Concept
```rust
// cargo test in contracts/defuse/core (or tests/ crate) comparing fee outcomes

#[test]
fn split_nep245_delta_bypasses_fee() {
    let fee = Pips::ONE_PERCENT; // nonzero protocol fee
    let token_id: TokenId = Nep245TokenId::new("mt.near".parse().unwrap(), "ft1".into()).into();

    // Single large trade: delta = -100 on Nep245 token
    let single_fee = TokenDiff::token_fee(&token_id, 100, fee).fee_ceil(100);
    assert!(single_fee > 0, "expected nonzero fee on aggregate amount");

    // Split into 100 unit trades: delta = -1 each
    let mut split_fee_total: u128 = 0;
    for _ in 0..100 {
        split_fee_total += TokenDiff::token_fee(&token_id, 1, fee).fee_ceil(1);
    }

    // Binding is violated: aggregated per-unit fees != fee on the true aggregate delta
    assert_ne!(split_fee_total, single_fee);
    assert_eq!(split_fee_total, 0);
}
```
For an end-to-end proof, a `near-workspaces`/sandbox test should execute two `execute_intents` batches on the same Verifier state (same starting balances): (1) one `MultiPayload` with a single `TokenDiff` of `delta = -100` on the Nep245 `TokenId` matched by a counter-leg of `+100` on another token, and (2) 100 separate `MultiPayload`s (or 100 `TokenDiff` entries in one message) each with `delta = -1` matched by `+1` counter-legs, then assert that the `fee_collector`'s balance for that `TokenId` differs between scenario (1) and (2) despite the signer's net token movement being identical.
