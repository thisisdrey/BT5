### Title
Backchannel "Praefect-only" gating relies on transport type, not caller identity, allowing any Gitaly client to spoof Praefect and manipulate `SignalPostReceiveReady` - (File: internal/gitaly/service/hook/signal_post_receive.go)

### Summary
`SignalPostReceiveReady` is documented as callable "only via Praefect's backchannel to prevent abuse," but the enforcement check merely asks whether the incoming connection *is a multiplexed backchannel connection* — it never verifies that the peer on the other end is actually Praefect. Any client capable of speaking the (documented, open) backchannel/yamux multiplexing wire protocol can satisfy this check and call the RPC with an arbitrary, attacker-chosen `transaction_id`, exactly mirroring the reported bug class: an entry point trusts that it is "only called by" a specific privileged component, but performs no real authentication/authorization of that assumption.

### Finding Description
The handler's only access-control gate is: [1](#0-0) 

`backchannel.GetPeerID` does not authenticate the identity of the far end as "Praefect." It only checks that the connection's `AuthInfo` contains a `peerID()` — i.e., that the connection completed the generic backchannel multiplexing handshake: [2](#0-1) 

The handshake itself (`ServerHandshaker.Handshake`) is a purely transport-level negotiation: it detects the `magicBytes` prefix ("backchannel"), opens a yamux multiplexing session, accepts the client's gRPC stream, and dials back a reverse connection — with no cryptographic proof of the caller's role: [3](#0-2) 

Because `magicBytes` and the yamux protocol are just public wire-format details (also documented in `doc/sidechannel.md`), any client already holding the standard Gitaly bearer token used for ordinary RPCs (the same shared secret used by GitLab Rails/Workhorse/any other Gitaly API caller, per `auth/token.go`) can implement this same handshake and be treated as "coming through the backchannel," passing the `GetPeerID` check that `SignalPostReceiveReady` relies on for its entire security guarantee.

Once past that check, the handler performs no further authorization — it accepts any caller-supplied `transaction_id` and either signals success or forces a synthetic failure (`post_transaction_failed`) for whatever waiter is registered under that ID: [4](#0-3) 

`PostReceiveRegistry.Signal` is a bare map/channel keyed only by the numeric transaction ID, with no verification that the *caller* who signals is the same Praefect instance that owns that transaction: [5](#0-4) 

This is the direct analog of the `WithdrawCollateral` bug: the contract function is "designed to be called by the `overseer` contract" but has no on-chain check enforcing that, so any caller can supply `borrower`/`amount` directly. Here, `SignalPostReceiveReady` is "designed to be called ... via Praefect's backchannel" but has no check enforcing that the backchannel peer is genuinely Praefect, so any caller that can speak the backchannel protocol can supply `transaction_id`/`post_transaction_failed` directly.

### Impact Explanation
An ordinary Gitaly client (one that only needs the standard shared auth token every legitimate caller already has, not a Praefect-specific secret) can:
- Prematurely signal `SignalPostReceiveReady` for a transaction ID belonging to another user's concurrent push, unblocking `PostReceiveHook` before Praefect has genuinely finished DB updates/replication bookkeeping — undermining the documented race-condition protection ("prevent a race condition where Rails is notified before all Gitaly replicas have applied the write and before Praefect has updated its database for routing decisions"), or
- Force `post_transaction_failed = true` for an arbitrary transaction ID, causing another user's legitimate `git push` to fail non-deterministically (denial of service against concurrent operations), by guessing/enumerating in-flight transaction IDs.

This is a gating/hook-coordination bypass reachable from any authenticated (but not Praefect-privileged) Gitaly client, i.e., from an ordinary user/service context rather than a genuinely privileged actor.

### Likelihood Explanation
Exploitation requires only: (1) the same Gitaly bearer token any legitimate client already needs for normal RPCs, and (2) implementing the publicly documented backchannel yamux handshake (magic bytes + client-to-server stream), which is described in-repo (`doc/sidechannel.md`, `internal/grpc/backchannel/backchannel.go`) and has no additional secret. No Praefect-specific credential or MITM is needed. The main variable affecting exploitability is guessing a live `transaction_id`; the codebase's own design commentary for a related (but different) transaction ID scheme notes IDs are chosen to be non-sequential specifically "to avoid collisions," which is documented for `RefTransactionServer` transactions — whether the `HooksPayload.Transaction.ID` used here is similarly resistant to enumeration could not be confirmed from the code reachable in this session (see below), so likelihood is assessed as plausible but not fully verified.

### Recommendation
Do not rely solely on "is this a multiplexed backchannel connection" as a proxy for "is this Praefect." Add real authentication of the backchannel peer as Praefect — e.g., bind the backchannel handshake to the same mTLS/token credential validation used for the primary connection and check the resulting principal/identity in `SignalPostReceiveReady` (not just presence of a `peerID()`), and additionally verify that the signaling backchannel connection is the one associated with the specific transaction being signaled (e.g., store and compare the backchannel/session ID that created the transaction against the one calling `Signal`), rather than accepting any backchannel peer for any transaction ID.

### Proof of Concept
1. Obtain the standard Gitaly auth token used by any legitimate client (no Praefect-specific credential required).
2. Implement a minimal client that performs the backchannel handshake: send the `"backchannel"` magic bytes prefix, complete a yamux client handshake against the Gitaly listener, following the pattern shown in `internal/grpc/backchannel/backchannel_example_test.go`'s `invokeWithMuxedClient`.
3. Over the resulting multiplexed gRPC stream, call `HookService.SignalPostReceiveReady` with a `transaction_id` matching (or brute-forced against) a transaction ID currently in flight for another user's push, setting `post_transaction_failed = true`.
4. Because `backchannel.GetPeerID(ctx)` succeeds for any multiplexed connection, the handler proceeds past the "Praefect-only" gate and calls `postReceiveRegistry.Signal(transactionID, errors.New("Praefect post-transaction work failed"))`, causing the victim's legitimate `PostReceiveHook` invocation waiting on that transaction to fail, denying their push.

**Caveat**: I could not fully confirm within this session how predictable/guessable the `transaction_id` used by `SignalPostReceiveReady` (sourced from `HooksPayload.Transaction.ID`) is in practice — the generation logic lives in code paths (`internal/transaction/txinfo/transaction.go`, `internal/git/gitcmd/hooks_payload.go`) that I located but did not have remaining tool calls to fully inspect. This affects the practical ease of targeting a specific victim's transaction, but does not change the core finding that the "Praefect-only" access control itself is not actually enforced.

// GetPeerID gets the ID of the current peer connection.
func GetPeerID(ctx context.Context) (ID, error) {
	peerInfo, ok := peer.FromContext(ctx)
	if !ok {
		return 0, errors.New("no peer info in context")
	}

	wrapper, ok := peerInfo.AuthInfo.(interface{ peerID() ID })
	if !ok {
		return 0, ErrNonMultiplexedConnection
	}

	return wrapper.peerID(), nil
}

// Handshake establishes a gRPC ClientConn back to the backchannel client
// on the other side and stores its ID in the AuthInfo where it can be
// later accessed by the RPC handlers. gRPC sets an IO timeout on the
// connection before calling ServerHandshake, so we don't have to handle
// timeouts separately.
func (s *ServerHandshaker) Handshake(conn net.Conn, authInfo credentials.AuthInfo) (net.Conn, credentials.AuthInfo, error) {
	// It is not necessary to clean up any of the multiplexing-related sessions on errors as the
	// gRPC server closes the conn if there is an error, which closes the multiplexing
	// session as well.

	// Open the server side of the multiplexing session.
	//
	// Gitaly is using custom settings with a lower accept backlog and higher receive
	// buffer size than Praefect and the clients. We should eventually strive to match
	// the settings here to avoid Gitaly from buffering too much.
	cfg := DefaultConfiguration()
	cfg.AcceptBacklog = 1
	cfg.MaximumStreamWindowSizeBytes = 16 * 1024 * 1024
	muxSession, err := newServerMuxSession(newInstrumentedConn(conn), s.logger.WithField("component", "backchannel.YamuxServer"), cfg, s.useLibp2p)
	if err != nil {
		return nil, nil, fmt.Errorf("create multiplexing session: %w", err)
	}

	// Accept the client's stream. This is the client's gRPC session to the server.
	clientToServerStream, err := muxSession.Accept()
	if err != nil {
		return nil, nil, fmt.Errorf("accept client's stream: %w", err)
	}

	// The address does not actually matter but we set it so clientConn.Target returns a meaningful value.
	// Insecure credentials are used as the multiplexer operates within a TLS session already if one is configured.
	//
	// We can't use our client.New() constructor here due to the custom scheme. We also need to prefix the address
	// with the passthrough:// scheme so grpc.NewClient() doesn't attempt DNS resolution.
	backchannelConn, err := grpc.NewClient(
		"passthrough://multiplexed/"+conn.RemoteAddr().String(),
		append(
			s.dialOpts,
			grpc.WithTransportCredentials(insecure.NewCredentials()),
			grpc.WithContextDialer(func(ctx context.Context, _ string) (net.Conn, error) { return muxSession.Open(ctx) }),
		)...,
	)
	if err != nil {
		return nil, nil, fmt.Errorf("dial backchannel: %w", err)
	}

	id := s.registry.RegisterBackchannel(backchannelConn)
	// The returned connection must close the underlying network connection, we redirect the close
	// to the muxSession which also closes the underlying connection.
	return &connCloser{
			Conn: clientToServerStream,
			close: func() error {
				s.registry.RemoveBackchannel(id)

				var firstErr error
				for _, closer := range []io.Closer{
					backchannelConn, muxSession,
				} {
					if err := closer.Close(); err != nil && firstErr == nil {
						firstErr = err
					}
				}

				return firstErr
			},
		},
		withSessionInfo(authInfo, id, muxSession),
		nil
}
