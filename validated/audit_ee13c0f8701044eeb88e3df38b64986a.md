### Title
Legacy `fix_contract_loading_cost=false` ordering lets an attacker get free wasmtime deserialize/link/instantiate_pre work by capping `prepaid_gas` below the loading fee - ([File: runtime/near-vm-runner/src/logic/gas_counter.rs])

### Summary
On mainnet (`fix_contract_loading_cost` is `false`, the fix is nightly-only at PV 129), `add_contract_loading_fee` is charged in `after_loading_executable` instead of `before_loading_executable`, meaning the expensive wasmtime module deserialize/link/`instantiate_pre` work happens *before* the gas for it is charged. An attacker who deploys a large contract and calls it with `prepaid_gas` set just below `contract_loading_base + contract_loading_bytes*len` will always fail with `GasExceeded` (a NOP outcome), but the node still fully pays the deserialization/link/instantiate cost for every call while the attacker is billed near-zero net gas (since the outcome is a NOP under the pre-`FixContractLoadingCost` legacy path).

### Finding Description
`GasCounter::before_loading_executable` (`runtime/near-vm-runner/src/logic/gas_counter.rs:235-255`) only pre-charges `add_contract_loading_fee` when `config.fix_contract_loading_cost` is true. On stable mainnet this flag is false, so the check at line 247 (`if config.fix_contract_loading_cost`) is skipped entirely, and the fee is instead charged in `after_loading_executable` (`gas_counter.rs:258-272`), which per `protocol-model/spec/contract-vm.md` (§3, step 4) runs only after `WasmtimeVM::with_compiled_and_loaded` has already deserialized the cached module, resolved the memory export, built the `Linker`, linked host functions, and called `instantiate_pre`. That work is proportional to the contract's wasm size and is O(size), independent of gas paid.

Attack flow:
1. An unprivileged account deploys a wasm contract near `max_contract_size` via a normal `DeployContract` action (deployment itself is a one-time cost the attacker pays once).
2. The attacker then submits many `FunctionCall` receipts (directly, or via meta-transactions relaying delegate actions) calling an existing method on that contract, each with `prepaid_gas` set just below `contract_loading_base + contract_loading_bytes * wasm_code_bytes`.
3. Static transaction/receipt validation only checks that `prepaid_gas` covers the minimum action send/exec costs (e.g. `function_call` base action cost) — it has no knowledge of the size of the target contract's code and cannot pre-validate against the loading fee, so these receipts pass validation and get included/executed.
4. During execution, `with_compiled_and_loaded` performs the full deserialize/link/`instantiate_pre` sequence (real CPU work, cache-hit or not) before `after_loading_executable` is ever invoked.
5. `after_loading_executable` then calls `add_contract_loading_fee` → `pay_per`/`pay_base` → `burn_gas`, which fails because `prepaid_gas` is insufficient, returning `HostError::GasExceeded`. Per the spec (§ "Loading-phase failures" / protocol-version-gated behavior section), on stable (no `fix_contract_loading_cost`) this becomes a NOP outcome (`abort_but_nop_outcome_in_old_protocol`, `logic.rs:4533`) rather than a charged abort.
6. This violates the METERING_TOTALITY invariant: real, size-proportional deserialization/link/instantiate work is performed by the node before the corresponding gas is deducted, and because the call is engineered to always fail the loading-fee charge, the attacker is billed effectively nothing per call while the node repeats full-cost module loading indefinitely.

This is not stopped by any existing check: nonce/signature/access-key checks are unrelated; the static gas-limit/action-cost validation at receipt-creation time has no visibility into the callee contract's code size (that information only becomes available once the receipt executes and the target contract is loaded); and the storage-staking/size-limit checks bound contract size but not the per-call gas/loading-cost relationship. The near-core team is aware of this asymmetry — the `fix_contract_loading_cost` config flag and `ProtocolFeature::FixContractLoadingCost` exist specifically to move the charge into `before_loading_executable` (pre-charge, load only if paid), but per `protocol-model/spec/contract-vm.md`, that fix is nightly-only (PV 129) and not active on current stable/mainnet (PV 86).

### Impact Explanation
This allows a low-cost/near-free repeated triggering of real (size-proportional) wasmtime deserialize/link/`instantiate_pre` CPU work by any unprivileged account, without paying commensurate gas, since the offending calls are guaranteed to resolve as a nop (no gas burnt, effectively) once the loading-fee charge fails. Repeated at scale (many receipts per block, each near the contract-size limit) this inflates block/chunk apply time relative to gas burnt, a resource-exhaustion/DoS vector against chunk producers and (transitively) chunk validators re-executing the same receipts. This does not directly cause fund theft, inflation, or authorization bypass; the closest matching NEAR bounty category is Denial-of-Service / resource exhaustion (mismetered gas cost enabling disproportionate node work per unit gas paid), which is a lower-severity category than fund loss or consensus divergence, and is already a known, tracked design gap addressed by an existing (not-yet-activated) protocol feature.

### Likelihood Explanation
Preconditions are trivial for any unprivileged account: fund an account, deploy one large contract (one-time cost bounded by storage staking/deploy cost), then submit ordinary `FunctionCall` receipts (or relay delegate actions) with a specifically crafted `prepaid_gas` value just below the known loading-fee formula (`contract_loading_base + contract_loading_bytes * code_len`, both are public protocol parameters). This is fully repeatable — each call is a normal transaction with no special privileges, and the attacker can automate submission at whatever rate the RPC/mempool and gas price allow. The main cost to the attacker is the transaction fee/gas actually burnt before the OOG point (base validation and send costs), which is small relative to the deserialize/link/instantiate cost the node performs for a large contract.

### Recommendation
Backport/activate the `fix_contract_loading_cost` behavior (pre-charging `add_contract_loading_fee` inside `before_loading_executable`, before any deserialize/link/instantiate_pre work, and treating loading-phase failures as a charged `abort` rather than a NOP) to mainnet rather than leaving it gated behind the nightly-only `FixContractLoadingCost` protocol feature (PV 129). Until activated, consider adding an early, size-only pre-check (before compile/link/instantiate) that rejects a `FunctionCall` when `prepaid_gas` cannot possibly cover the known contract code size loading fee, independent of the `fix_contract_loading_cost` flag.

### Proof of Concept
Integration/runtime test plan:
1. Deploy a wasm contract near `max_contract_size` with a valid callable method (e.g., a fast no-op export) via a runtime/test-loop test harness (e.g. `integration-tests` or `runtime/runtime/src/tests`).
2. Compute `loading_fee = contract_loading_base + contract_loading_bytes * code_len` from the active `RuntimeConfig`.
3. Submit N `FunctionCall` receipts targeting that contract with `prepaid_gas = loading_fee - 1` (or another value guaranteed to be below the fee but above the static minimum action gas required to pass validation).
4. Measure wall-clock time for processing the N receipts (or chunk apply time), and record `burnt_gas` reported by each outcome (expected: outcome is `aborted` with `GasExceeded`/nop, burnt gas ≈ 0 or minimal).
5. Compare against a baseline: N receipts to an equivalent-size contract executing an explicit CPU-bound loop calibrated to burn `loading_fee` worth of gas in normal (non-loading) execution, measuring its wall time for the same total burnt gas.
6. Assert: wall time of the loading-fee-exhaustion receipts is comparable to (or a significant fraction of) the wall time of the CPU-bound-loop baseline, while `sum(burnt_gas)` for the loading-fee-exhaustion case is far smaller (assert ratio, e.g. `burnt_gas_sum << loading_fee * N`), demonstrating disproportionate CPU cost per unit of gas paid — repeat with `config.fix_contract_loading_cost = true` (nightly-config test) to show the ratio is corrected once pre-charging is enabled.
