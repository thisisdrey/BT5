Confirmed: `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` — the sole write-acceptance gate used by the HTTP write path (`poststackerdbchunk.rs`) — enforces signer, version-monotonicity, size, and max-writes, but never checks `write_freq` (the configured minimum wall-clock interval between writes to a slot). `write_freq` is only consulted in `stackerdb/sync.rs`'s peer-sync scheduler to decide whether to *fetch* a chunk from a remote replica, and `validate_received_chunk`/`validate_downloaded_chunk` explicitly document that they skip this check "since the caller has different ways of doing this" — but the HTTP write path (`poststackerdbchunk.rs::try_handle_request`) has no such alternate enforcement.

#### Title
StackerDB `write-freq` rate limit is never enforced on the HTTP chunk-write path - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBConfig.write_freq` is documented as "minimum wall-clock time between writes to the same slot" [1](#0-0)  and is checked only inside the sync-scheduling loop to skip *fetching* a chunk that was written too recently [2](#0-1) . The actual chunk-acceptance function, `try_replace_chunk`, checks size, signer, stale-version, and max-writes, but has no `write_freq` check at all [3](#0-2) . The HTTP handler `RPCPostStackerDBChunkRequestHandler::try_handle_request` calls `tx.try_replace_chunk(...)` directly as the only acceptance gate before committing and relaying the chunk [4](#0-3) .

### Finding Description
This is analogous to the Keycloak bug class: a time-bound intended to gate acceptance of data (OTP freshness window vs. StackerDB `write_freq` window) is enforced in one code path but silently absent in the path that actually authorizes/stores the write, letting an authorized signer (who owns a slot) write far more frequently than the DB's configured policy allows. The `validate_received_chunk`/`validate_downloaded_chunk` comments explicitly acknowledge write-frequency is not checked there "because the caller has different ways of doing this" [5](#0-4) [6](#0-5) , but no such alternate write_freq check exists on the HTTP-write acceptance path in `poststackerdbchunk.rs`, breaking the intended invariant "committed write interval >= write_freq" enforced only via `try_replace_chunk`.

### Impact Explanation
An authorized slot owner (holding the slot's private key — not a privileged/admin role, merely one of potentially many StackerDB signers) can bypass the `write_freq` rate limit entirely by writing directly via the `/v2/stackerdb/.../chunks` HTTP RPC endpoint instead of relying on gossip sync. Each accepted write is also relayed as a `StackerDBPushChunk` gossip message to the whole network via `node.set_relay_message` [7](#0-6) , so this allows a bounded-privilege signer to flood the StackerDB replication network with legitimately-signed but overly-frequent chunk updates, exceeding the operator-configured `write_freq` throttle across all replicas network-wide. This is a policy/DoS-adjacent gap rather than a fully unauthenticated write, since it still requires possessing a valid slot-owning key.

### Likelihood Explanation
Moderate: exploitation requires a valid signer key for a StackerDB slot (e.g. a signer participating in the `.signers` StackerDB), which is a realistic but non-trivial precondition (not an anonymous remote attacker). Given such a key, triggering the bypass is trivial — simply issue repeated POST requests to the node's HTTP RPC endpoint instead of waiting for the natural gossip cadence.

### Recommendation
Enforce `config.write_freq` inside `try_replace_chunk` (or equivalently, add an explicit write_freq check in the HTTP handler before calling it) so that the minimum-interval policy is applied uniformly across all StackerDB chunk-acceptance paths (HTTP writes, unsolicited pushes, and downloaded sync chunks).

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u120` (as exercised in `test_reconfigure_stackerdb` / `test_stackerdb_insert_query_chunks`) [8](#0-7) .
2. As a valid slot signer, POST a properly-signed chunk with an incremented `slot_version` to `/v2/stackerdb/{addr}/{contract}/chunks` — accepted immediately per `try_replace_chunk`'s checks (size/signer/version/max_writes only) [9](#0-8) .
3. Immediately (well under 120 seconds later) POST another chunk with the next incremented `slot_version`, still properly signed — this is also accepted, because no `write_time`/`write_freq` comparison exists anywhere in `try_replace_chunk` or `poststackerdbchunk.rs`, despite the configured 120-second minimum interval.
4. Each accepted write is relayed via `StackerDBPushChunk` to the network, propagating writes at a rate that violates the configured `write_freq` policy.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
