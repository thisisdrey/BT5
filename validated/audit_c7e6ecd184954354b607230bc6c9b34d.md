Confirmed key finding: `callConstantContract` in `Wallet.java` is invoked concurrently by RPC/API worker threads (each `TriggerConstantContract`/`estimateEnergy` request runs on a "pooled RPC worker" thread as noted in the code comment), and it calls into `VMActuator`/`Program`, which reads/writes the **process-wide static, non-thread-safe** `LRUMap` `programPrecompileLRUMap` in `Program.getProgramPrecompile()`.

### Title
Unbounded/corrupted growth of the shared `programPrecompileLRUMap` cache due to concurrent unsynchronized access from constant-call RPC threads - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program` maintains a single JVM-wide cache, `programPrecompileLRUMap`, intended to bound memory by evicting least-recently-used entries once `lruCacheSize` is exceeded [1](#0-0) . This is analogous to virglrenderer's `add_shader_program`, which stores `sprog` into an internal table without proper accounting/cleanup, letting the host-side structure grow unexpectedly. In java-tron, `getProgramPrecompile()` reads and writes this map on every non-constant TVM call, computing a `Key` from the contract address and code hash and inserting a freshly compiled `ProgramPrecompile` on a cache miss [2](#0-1) .

### Finding Description
`org.apache.commons.collections4.map.LRUMap` is **not thread-safe**; concurrent `get`/`put`/`containsKey` calls on the same instance can corrupt its internal linked list, breaking the eviction bound and/or causing entries to never be reclaimed. Unlike a block-processing pipeline that is normally sequential, `Wallet.callConstantContract` is explicitly documented and designed to run on **pooled RPC worker threads** ("constant call runs on a pooled RPC worker") [3](#0-2) . Any anonymous JSON-RPC/HTTP/gRPC client can trigger such constant calls (`triggerconstantcontract`, `estimateenergy`, etc.) concurrently through the query paths into `Wallet`. Each such call constructs a `Program`/`VMActuator` and, for any code path where the call is not itself a constant call at that (sub)invocation level (e.g. internal `CALL`/`DELEGATECALL` to other deployed contracts triggered from within the constant call, since only the outermost frame is `isConstantCall()`), the code goes through the shared static map branch rather than the per-instance branch [2](#0-1) . When many such RPC threads execute concurrently and repeatedly invoke arbitrary attacker-deployed contracts with distinct bytecode/addresses (an unlimited, attacker-controlled `Key` space, since `Key` is derived from `codeAddress + codeHash` which any user can vary by deploying new contracts) [4](#0-3) , the unsynchronized structural mutation of the shared `LRUMap` can silently invalidate its internal eviction bookkeeping, so entries accumulate beyond `lruCacheSize` instead of being evicted, retaining `ProgramPrecompile` objects (which grow with contract bytecode size/jump-destination sets) indefinitely, exactly like the `sprog` objects retained in the vulnerable `add_shader_program` hash table.

### Impact Explanation
Because this cache is a single static field shared by every `Program` instance in the JVM (not per-transaction and not cleared on transaction rollback), continuous exploitation drives unbounded native heap growth for as long as the node runs, resulting in host memory exhaustion and denial of service — the exact same class of impact as CVE-2017-6317 (host memory consumption DoS from an unbounded/leaked in-memory table).

### Likelihood Explanation
Likelihood is limited by the fact that reaching the vulnerable racy code path requires: (1) sustained concurrent RPC/API traffic against `triggerconstantcontract`/`estimateenergy`, (2) many distinct contracts (each attacker can deploy trivially many contracts with unique bytecode to generate unique cache keys, which is a normal, permissionless operation), and (3) the race actually corrupting `LRUMap`'s internal state, which is timing-dependent and not guaranteed on every call. This makes it a plausible but non-deterministic DoS vector rather than one triggerable in a single transaction.

### Recommendation
Wrap `programPrecompileLRUMap` accesses in synchronization (or replace it with a thread-safe bounded cache such as Guava's `CacheBuilder`/`LoadingCache` with `maximumSize`), and audit all other process-wide static mutable caches reachable from constant-call/RPC execution paths for the same non-thread-safe-collection-under-concurrent-access pattern.

### Proof of Concept
Concrete exploitation requires a running node under load and cannot be demonstrated as a single deterministic transaction; a full PoC would need a background Devin agent with runtime/terminal access to spin up a java-tron node, deploy many distinct contracts, and drive high-concurrency `triggerconstantcontract`/`estimateenergy` RPC calls invoking `CALL`/`DELEGATECALL` to those contracts while monitoring JVM heap growth for `ProgramPrecompile` retention beyond `lruCacheSize`. I was unable to fully verify at code-review time whether the race reliably corrupts `LRUMap`'s eviction bookkeeping in practice (this depends on `commons-collections4`'s internal implementation details), so this should be treated as an unconfirmed/uncertain finding pending dynamic testing.

      if (programPrecompileLRUMap.containsKey(key)) {
        programPrecompile = programPrecompileLRUMap.get(key);
      } else {

        programPrecompileLRUMap.put(key, programPrecompile);
      }
    }
    return programPrecompile;
  }
