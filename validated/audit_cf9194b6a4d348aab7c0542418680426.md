### Title
Zip extraction path-containment check accepts sibling directories with a common string prefix, allowing path traversal outside the output root - (`third_party/ijar/zip_main.cc`)

### Summary
`UnzipProcessor::Process` in the `ijar` zip extractor verifies that an extracted entry stays inside the extraction root by comparing the *string prefix* of the normalized output path against the normalized output root, but it never checks that the byte immediately following the matched prefix is a path separator (or end-of-string). This is the exact "wrong equals/prefix logic" bug class described in the analog report: a length/prefix check that should assert an exact boundary (`==`, or a following separator) but instead only asserts "at least as long as" / "starts with," so a string that merely shares a prefix - not a real ancestor directory - passes the check.

### Finding Description
The containment check is: [1](#0-0) 

```
char path[PATH_MAX];
if (!concat_path(path, sizeof(path), output_root_, output_file_name)) {
  abort();
}
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  fprintf(stderr, "paths in the zip may not end up outside of the output directory...");
  abort();
}
```

This is structurally identical to the reported ENS bug: `equals(self, offset, other)` returns true whenever `self` merely begins with `other`'s bytes, without checking that the match ends exactly at a boundary. Here, `normalized.compare(0, normalized_root.size(), normalized_root) == 0` is true whenever `normalized` starts with the literal characters of `normalized_root`, with no check that the next character of `normalized` is `'/'` or that `normalized` ends there. A path can be a *string*-prefix match of the root without being a *path*-prefix (ancestor-directory) match. For example, if `output_root_` normalizes to `/tmp/out`, then `/tmp/out-evil/PWNED` or `/tmp/outside/PWNED` both textually start with `/tmp/out` and would incorrectly pass the check even though they resolve to a completely different, sibling directory outside the intended extraction root.

An attacker who controls the contents of a zip archive (e.g. an `http_archive`/`http_jar`/`http_file` download, or any archive whose bytes are consumed by this `ijar` unzip tool) chooses entry names; `concat_path` simply joins `output_root_` and the (attacker-supplied) entry name and `normalize_path` collapses `.`/`..`/redundant separators, but it does not insert a delimiter check when comparing against the root. The existing test suite only exercises classic `../` traversal: [2](#0-1) 

There is no test covering a sibling-directory-with-common-prefix entry name, so this exact boundary bug is not caught by existing tests.

### Impact Explanation
A hostile archive can cause files to be written outside the intended output directory (e.g., a directory adjacent to the real extraction root whose name happens to share the root's string prefix, such as `out` vs `out2`, or `out` vs `outbuild`). This is a write-outside-containment-directory bug matching the accepted impact class (write outside the repository/exec root/output base) for this scan, since the whole purpose of the check being bypassed is to guarantee containment of untrusted archive content within `output_root_`.

### Likelihood Explanation
Reaching this code only requires supplying a maliciously named entry in a zip file that this `ijar` extractor unpacks (attacker controls archive bytes served from an untrusted/dependency URL or similar). No additional privilege or victim-machine access is needed. The bug is a pure string-prefix vs. path-prefix confusion with no other check compensating for it (checksum verification of the whole archive, if any, does not validate individual extracted paths' safety relative to the root).

### Recommendation
Change the containment check to require that the match end at a directory boundary, mirroring the C4 fix pattern of asserting an exact/boundary-safe equality instead of a bare length/prefix comparison:

```diff
- if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
+ if (normalized.compare(0, normalized_root.size(), normalized_root) != 0 ||
+     (normalized.size() > normalized_root.size() &&
+      normalized[normalized_root.size()] != '/')) {
    fprintf(stderr, "paths in the zip may not end up outside of the output directory: %s vs %s\n", path, normalized.c_str());
    abort();
  }
```

### Proof of Concept
Conceptually (to be turned into a `third_party/ijar/test/zip_test.sh` or equivalent shell-integration test):
1. Create output root `${TEST_TMPDIR}/out`.
2. Also note the existence/creatability of a sibling directory whose name has `out` as a literal prefix, e.g. `${TEST_TMPDIR}/out_evil` (this directory need not even pre-exist; the point is `normalize_path` on the concatenated path yields a string that starts with `.../out` without being under it — e.g. entry name `../out_evil/PWNED` collapses via `normalize_path` such that the resulting string still textually starts with the root string while resolving to a different directory).
3. Build a zip archive containing an entry name crafted so that `concat_path(output_root, entry)` followed by `normalize_path` produces a path string that is a strict string-prefix superset of `normalized_root` (e.g. `outXXX/PWNED`) rather than a true subdirectory.
4. Run the `ijar` unzip tool (`zipper x archive.zip -d out`) and observe that `PWNED` is written under `outXXX/` (outside `out/`) instead of being rejected with "paths in the zip may not end up outside of the output directory".

This complements the existing `test_no_path_traversal` test, which only covers `..`-style traversal and does not exercise the boundary-check gap identified here. [3](#0-2)

```text
// Concatene 2 path, path1 and path2, using / as a directory separator and
// putting the result in "out". "size" specify the size of the output buffer. If
// the result would overflow the output buffer, print an error message and
// return false.
bool concat_path(char *out, const size_t size, const char *path1,
                 const char *path2) {
  int len1 = strlen(path1);
  size_t l = len1;
  strncpy(out, path1, size - 1);
  out[size - 1] = 0;
  if (l < size - 1 && path1[len1] != '/' && path2[0] != '/') {
    out[l] = '/';
    l++;
    out[l] = 0;
  }
  if (l >= size - 1) {
    fprintf(stderr, "paths too long to concat: %s + %s", path1, path2);
    return false;
  }
  strncat(out, path2, size - 1 - l);
  return true;
}
```
