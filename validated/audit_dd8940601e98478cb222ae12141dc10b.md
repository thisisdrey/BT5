### Title
Attacker can permanently fill a victim's per-account token list via dust `DepositToken` transfers, blocking collateral top-ups and forcing liquidation - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` on the combined count of an account's deposit tokens and debt tokens [1](#0-0) . Every non-zero `DepositToken._transfer` to a fresh recipient calls `pool.addToDepositTokensOfAccount(recipient_)`, which is guarded by `onlyIfAdditionWillNotReachMaxTokens` and reverts with `UserReachedMaxTokens` once the limit is hit [2](#0-1) [3](#0-2) . Any EOA can transfer msd-tokens, so an unprivileged attacker can dust-fill a victim's account list and prevent them from ever receiving another deposit-token type or issuing another debt-token type.

### Finding Description
`DepositToken._transfer` adds the recipient to `depositTokensOfAccount` whenever their prior balance was zero [4](#0-3) . `Pool.addToDepositTokensOfAccount` reverts if `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` [3](#0-2) . There is no minimum-amount check, no opt-in, and no way for the victim to reject incoming tokens. `DebtToken` minting (`issue`/`flashIssue`) performs the symmetric accounting, so a filled list also blocks the victim from opening debt in any synthetic token they don't already hold [5](#0-4) .

Attack path:
1. Attacker deposits a minimal amount in each distinct `DepositToken` in the pool (or routes via `Operator.execute`).
2. Attacker `transfer`s 1 wei of each msd-token to the victim until `debtTokensOfAccount + depositTokensOfAccount == 30`.
3. From then on, every `deposit()`/`transfer()`/`seize()` that would register a new token for the victim reverts with `UserReachedMaxTokens`, and every `issue()` into a new debt-token type reverts the same way.

The invariant that breaks is per-account liveness: a healthy-position invariant maintained by user action (depositing more collateral) becomes externally unenforceable.

### Impact Explanation
Temporary freezing of funds / forced liquidation. If the victim's position drifts toward unhealthy (price move or interest accrual), the victim cannot deposit a *different* collateral type to restore health — the tx reverts in `addToDepositTokensOfAccount`. An attacker (or any liquidator) can then call `Pool.liquidate` and seize the victim's collateral at the liquidation discount, converting a position the victim could have saved into a realized loss. The victim also cannot receive msd-token payments of new types or open new borrows until they fully burn an existing position to zero (which may itself be impossible if withdrawing would breach health, since `unlockedBalanceOf`/`_revertIfLocked` cap withdrawals [6](#0-5) ).

### Likelihood Explanation
Fully permissionless: `transfer` only requires the sender's unlocked balance and is callable by any EOA directly or via `Operator.execute` [7](#0-6) . Cost is bounded by `MAX_TOKENS_PER_USER` (30) dust transfers plus seed deposits, and on pools with several listed deposit/debt tokens the attacker fills remaining slots cheaply. No privileged role, oracle manipulation, or timing assumption is required. Mitigating factor: if the victim already holds all token types or the pool lists few tokens, the window shrinks; the victim can also burn a token to zero to free a slot, but only for collateral not needed to stay healthy.

### Recommendation
- Let `depositTokensOfAccount`/`debtTokensOfAccount` registration be opt-in for transfers (e.g., only register on `deposit`/`issue`, or credit dust to an unregistered balance), or
- Remove the per-account cap by iterating only over globally registered tokens in `debtPositionOf` and checking per-account balances (set membership instead of a per-account list), or
- Raise the cap to exceed the number of deposit + debt tokens that can ever exist so the list can never be filled.

### Proof of Concept
Hardhat fork outline (Base/mainnet deployments exist; e.g. `Operator` at `0x64b5...9373` on Base):

```ts
// test: fill victim's account list, then show deposit of a new collateral reverts
const pool = await ethers.getContractAt('Pool', POOL)
const depositTokens: DepositToken[] = /* all listed msd tokens */

// attacker seeds 1 wei of each msd token
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, 1n)
  await dt.connect(attacker).deposit(1n, attacker.address)      // mints 1 wei msdX
  await dt.connect(attacker).transfer(victim.address, 1n)       // registers victim
  // repeat until depositTokensOfAccount(victim) + debtTokensOfAccount(victim) == 30
}
expect((await pool.getDepositTokensOfAccount(victim.address)).length
       + (await pool.getDebtTokensOfAccount(victim.address)).length).eq(30)

// victim cannot add a new collateral type or receive one
await expect(otherMsd.connect(attacker).transfer(victim.address, 1n))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(otherMsd.connect(victim).deposit(1n, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// simulate price drop -> victim unhealthy, cannot top up with new collateral,
// attacker liquidates
await pool.connect(attacker).liquidate(synth, victim.address, repayAmt, depositToken)
```

Uncertainty: I did not confirm the exact line range of `DebtToken._mint`'s `addToDebtTokensOfAccount` call (grep shows it exists in `contracts/DebtToken.sol`); the deposit-token path above is fully verified and sufficient on its own.
