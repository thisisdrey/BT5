### Title
Overpaid storage deposit in `AddressRegistrar::register` is permanently locked, not refunded on success - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `#[payable]` `register` function of the `AddressRegistrar` contract (a companion contract used by the eth-implicit wallet contract to map ETH-style addresses to NEAR account IDs) only checks that the attached deposit is *at least* the required storage cost, but never refunds the excess when registration succeeds. Any amount attached above `required_deposit` is silently absorbed by the contract and is unrecoverable, since the contract exposes no withdrawal mechanism for the excess.

### Finding Description
In `register`, the deposit check is a one-sided lower bound: [2](#0-1) 

If `given_deposit < required_deposit` it panics (correctly protecting under-payment), but there is no corresponding branch to compute and refund `given_deposit - required_deposit` when the deposit is *larger* than needed. The success (`Entry::Vacant`) path simply inserts the account mapping and returns, keeping the whole attached deposit: [3](#0-2) 

Notably, the contract *does* implement a refund in the collision (`Entry::Occupied`) failure path, explicitly returning the full deposit to the caller because "no storage was updated": [4](#0-3) 

This asymmetry is exactly the reported bug class: the contract knows how to refund excess/failed-purpose deposits (as shown in the collision branch and generally in NEAR runtime's own deposit-refund model, e.g. `Receipt::new_balance_refund` in `refund_unspent_gas_and_deposits`, `runtime/runtime/src/lib.rs:1348-1353`), but omits the refund specifically on the success path, where any deposit attached beyond `required_deposit` is neither transferred to any recipient nor tracked as owed to the caller. There is no admin/withdraw method in the contract to later recover it (confirmed by reading the full 125-line file), so the excess is permanently stranded in the contract's balance.

### Impact Explanation
Any ordinary user (or a relayer acting through `WalletContract::rlp_execute`, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:412-431`) who calls `register` with a deposit larger than the exact byte-cost calculation permanently loses the difference — a straightforward instance of permanent freezing/loss of user funds. Because storage byte-cost is a precise, easy-to-miscalculate quantity (`bytes_to_store = 20 + account_id.len()`), and callers have no simple way to know the exact yoctoNEAR figure in advance, over-attachment is a realistic and easy user/relayer mistake.

### Likelihood Explanation
Likelihood is moderate-to-high: this is a normal, permissionless entry point (`#[payable] pub fn register`) reachable by any account or by the eth-implicit `WalletContract` relaying an Ethereum-style transaction. No special privilege or attacker cooperation is needed — accidental overpayment (e.g., rounding up out of caution) is sufficient to trigger the loss.

### Recommendation
Compute the excess (`given_deposit - required_deposit`) in the `Entry::Vacant` success branch and issue a transfer back to `env::predecessor_account_id()` for that excess, mirroring the pattern already used in the `Entry::Occupied` branch. Alternatively, require an exact-match deposit (`given_deposit == required_deposit`) and panic otherwise, forcing callers to compute the correct amount and pushing the refund responsibility back onto the transaction's normal failure semantics.

### Proof of Concept
1. Deploy the `AddressRegistrar` contract fresh (empty `addresses` map).
2. Compute `required_deposit` for account `"alice.near"` (`bytes_to_store = 20 + 10 = 30`, `required_deposit = storage_byte_cost * 30`).
3. Call `register("alice.near")` attaching `required_deposit + 1 NEAR`.
4. Observe: call succeeds, `Some(address)` is returned, the address→account mapping is stored — but the caller's balance decreased by `required_deposit + 1 NEAR`, not just `required_deposit`. Query the contract's account balance and confirm it now holds the extra 1 NEAR with no method available to reclaim it. Compare against calling `register` a second time with the same address (triggering the `Entry::Occupied` branch), where the full deposit *is* refunded, confirming the inconsistency is a bug rather than intended design (per the code comment "Transfer the deposit back to the caller since no storage was updated" at [5](#0-4) ).
