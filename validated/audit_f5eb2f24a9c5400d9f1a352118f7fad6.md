## Title
Silently ignored failed payout transfer in `claim_child_bounty` permanently locks child-bounty funds - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`ChildBounties::claim_child_bounty` executes the curator-fee and beneficiary payout transfers via `T::Currency::transfer(..., AllowDeath)`, but only checks the results with `debug_assert!`, which is compiled out entirely in release builds. Regardless of transfer outcome, the function unconditionally emits `Event::Claimed`, decrements `ParentChildBounties`, and deletes the child-bounty record, so a failed transfer permanently strands funds in the child-bounty account with no remaining on-chain reference to recover them.

## Finding Description
In `claim_child_bounty`, `curator_fee` and `payout` are computed from the child-bounty account's `free_balance` [1](#0-0) . Two `T::Currency::transfer` calls move `curator_fee` to the curator and `payout` to the beneficiary, both using `AllowDeath`, but their `Result`s are only checked with `debug_assert!`, which is a no-op in production/release builds [2](#0-1) . Immediately afterward — with no branching on transfer success — the code unconditionally emits `Event::Claimed` with the intended `payout`/`beneficiary` [3](#0-2) , decrements the active child-bounty counter [4](#0-3) , and deletes the child-bounty description and record from storage [5](#0-4) , returning `Ok(())` unconditionally.

The inline comments assume the only failure mode is insufficient balance, which is guarded against by `curator_fee = child_bounty.fee.min(balance)` and `payout = balance.saturating_sub(curator_fee)`. However, `Currency::transfer` with `AllowDeath` can still fail for a reason unrelated to source balance: if the destination account does not yet exist and the transferred amount is below the `ExistentialDeposit`, the deposit into a new account is rejected by the balances pallet's existence-requirement/ED logic, even though the source account has sufficient funds. This is a realistic scenario when a curator sets a small `fee`/`value` split via `award_child_bounty` such that `curator_fee` or `payout` ends up below ED for a beneficiary/curator address that has never held a balance. The existing checks (`ensure!` on `unlock_at`, `min`/`saturating_sub` for balance sufficiency) do nothing to guard against this destination-existence failure mode, and no `?`/`ensure!`/`map_err` propagates the transfer error to abort the `try_mutate_exists`.

## Impact Explanation
This is a permanent user-fund lock: the child-bounty account (`child_bounty_account_id(parent_bounty_id, child_bounty_id)`) retains the failed-transfer amount, but once `*maybe_child_bounty = None` executes, there is no dispatchable path or storage record referencing that account balance to recover it. The chain state falsely reports success via `Event::Claimed` and advances (`ParentChildBounties` decremented, record removed) despite the payout not actually settling to the rightful beneficiary/curator — violating the "advance only after settlement succeeds" and "settle exactly once to the rightful beneficiary and amount" invariants. This matches the accepted impact category of permanent user-fund lock.

## Likelihood Explanation
The trigger condition (a `curator`/`beneficiary` payout below `ExistentialDeposit` for an account that does not yet exist) is reachable by any curator calling the public `award_child_bounty` extrinsic to set the `fee` and `beneficiary`, and then any signed account calling the public `claim_child_bounty` extrinsic once `unlock_at` elapses — no privileged, governance, or off-chain infrastructure access is required. It can be deliberately engineered by a curator or hit accidentally with small child-bounty values, making it practically reachable rather than purely theoretical.

## Recommendation
Replace the `debug_assert!` checks with proper error propagation (`?`, `ensure!`, or `map_err`) inside the `try_mutate_exists` closure so that a failed fee or payout transfer aborts the entire mutation, leaving the child-bounty record, counters, and description intact and allowing a retry. Alternatively, pre-validate that the destination transfer amount satisfies the existential-deposit/`can_deposit` requirement before mutating any storage, or use a currency operation that guarantees atomicity between the transfer and the storage removal.

## Proof of Concept
1. Curator calls `award_child_bounty` on a parent bounty with a `fee` and `value` chosen so that `payout = value - fee` is smaller than `ExistentialDeposit`, and sets `beneficiary` to a brand-new address with zero prior balance.
2. Wait for `unlock_at` (post `BountyDepositPayoutDelay`) to elapse.
3. Any signed account calls `claim_child_bounty(origin, parent_bounty_id, child_bounty_id)`.
4. In a release build, `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)` fails (destination doesn't exist, amount < ED); `debug_assert!(payout_transfer_result.is_ok())` is compiled out and the error is discarded.
5. `Event::Claimed` fires with the unpaid `payout`/`beneficiary`, `ParentChildBounties` is decremented, and the child-bounty record/description are removed from storage.
6. Inspect the child-bounty account's on-chain balance afterward — it still holds `payout`, with no remaining bounty record to reference or recover it, confirming the fund lock against the emitted "success" event.
