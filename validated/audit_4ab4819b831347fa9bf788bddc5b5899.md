### Title
Attacker can permanently fill a victim's bounded `depositTokensOfAccount` list via unsolicited dust transfers, blocking new collateral deposits and list cleanup while the victim has locked collateral - (File: contracts/DepositToken.sol)

### Summary
The external report class is CWE-770: a bounded resource is allocated on request and never released because the cancel/cleanup path is asymmetric. The Metronome analog is the per-account deposit-token registry. `DepositToken._transfer` auto-registers a token in `Pool.depositTokensOfAccount[recipient]` whenever the recipient goes from 0 to non-zero balance, with no opt-in from the recipient [1](#0-0) . Removal only happens when the *holder* sends the balance to zero, which is gated by `_revertIfLocked` [2](#0-1) . An unprivileged attacker can therefore push dust of every registered `DepositToken` into a victim's account until `MAX_TOKENS_PER_USER` is reached; the victim cannot evict the entries while their collateral is locked by debt.

### Finding Description
`Pool` maintains `depositTokensOfAccount` / `debtTokensOfAccount` bounded sets and reverts with `UserReachedMaxTokens` when the combined count reaches `MAX_TOKENS_PER_USER` [3](#0-2) . Entries are added implicitly:

- `_mint` and `_transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance transitions 0 → >0 [4](#0-3) .
- Removal only occurs in `_burn`/`_transfer` when the sender's balance reaches 0 [5](#0-4) , and any outward `transfer`/`transferFrom` is blocked by `_revertIfLocked`, which consults `unlockedBalanceOf` against the victim's open debt position [6](#0-5) .

Attack: for each `DepositToken` registered in `Pool`, the attacker deposits a minimal amount, then calls `transfer(victim, 1)` (or `transferFrom` via an allowance-controlled helper). Each 1-wei transfer inserts a slot into the victim's `depositTokensOfAccount`. Since the victim is a leveraged borrower, the received dust counts as collateral and is locked (`_revertIfLocked` reverts when `amount > unlockedBalanceOf`), so the victim cannot send the dust back out to free slots. Once the cap is hit:

- `deposit()` on any *new* `DepositToken` reverts in `_mint` → `addToDepositTokensOfAccount` [4](#0-3) .
- Any `transfer`/`transferFrom`/`seize` *to* the victim of a token not already in their list reverts — including `Pool.liquidate`'s second `seize` leg if the fee token is not yet in the relevant list [7](#0-6) .
- The SmartFarmingManager `leverage`/`flashRepay` paths that deposit new collateral types on the victim's behalf also revert.

No modifier prevents this: `transfer` has no `nonReentrant` concern, no recipient-consent check, and `onlyIfDepositTokenIsActive` only gates minting. The attack requires only an EOA and public entry points.

### Impact Explanation
Temporary freezing of funds / liveness: a borrower whose list is filled cannot deposit additional collateral types to restore health — if their position approaches liquidation and their existing collateral type is insufficient or they hold the dust-locked cap, they are forced into liquidation they could otherwise have avoided. The freeze persists as long as the victim's collateral remains locked (i.e., while they carry debt), matching the "temporary freezing of funds" acceptance criterion. There is no admin or attacker-funded unblock needed — the victim literally cannot remove the injected entries.

### Likelihood Explanation
The cost is `O(number of registered deposit tokens)` dust transfers plus minimal deposits — bounded by the pool's own `ReachedMaxDepositTokens` cap [8](#0-7) . The attack is fully unprivileged and repeatable against any account holding debt. Likelihood is moderated because the victim retains use of collateral types already in their list, and the griefing yields the attacker no direct profit — the payoff is forced liquidations or blocking a competitor's position management. Not confirmed: whether deployed pools have enough registered deposit tokens for the dust to consume a meaningful fraction of `MAX_TOKENS_PER_USER` (the constant's value was not directly inspected in `Pool.sol`).

### Recommendation
Either (a) allow the account itself to purge entries — e.g., a `Pool.removeDepositTokenFromMyList(token)` callable by the account when its balance is below a dust threshold, or permit `transfer` of locked dust up to a small epsilon — or (b) only register the token on the recipient list on first *deposit/mint* initiated by the account (or on `seize`), not on inbound `transfer`. Option (b) is the minimal change: move the `addToDepositTokensOfAccount` call out of `_transfer` for external transfers, keeping it in `_mint`, `seize`, and any path that must count the token as collateral. Verify that `debtPositionOf`/`depositOf` iterate the list, since unlisted-but-held tokens would otherwise be invisible to health checks — the fix must keep accounting consistent.

### Proof of Concept
Hardhat fork sketch (pool/depositToken addresses from `deployments/mainnet`):

```ts
// Assume: pool has registered deposit tokens dt[0..n], victim holds debt
// so unlockedBalanceOf(victim) < dust on each token.
const attacker = await ethers.getSigner(ATTACKER);

for (const dtAddr of depositTokens) {
  const dt = await ethers.getContractAt('DepositToken', dtAddr);
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  // fund attacker with minimal underlying, deposit dust, transfer 1 wei to victim
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, attacker.address);
  await dt.connect(attacker).transfer(victim.address, 1);
}

// victim's list is now at MAX_TOKENS_PER_USER
expect(await pool.getDepositTokensOfAccount(victim.address))
  .to.have.lengthOf(MAX);

// 1) victim cannot remove entries while collateral locked
await expect(dt0.connect(victim).transfer(attacker.address, 1))
  .to.be.revertedWithCustomError(dt0, 'NotEnoughFreeBalance');

// 2) victim cannot deposit into a new collateral type
const newDt = await ethers.getContractAt('DepositToken', NEW_TOKEN);
await expect(newDt.connect(victim).deposit(AMT, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) liquidation seizing a token absent from liquidator/feeCollector lists
//    reverts if their per-account cap is similarly saturated
await expect(pool.connect(liquidator)
  .liquidate(synth.address, victim.address, REPAY, victimToken.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Run against a mainnet fork at a block where `victim` has an open position; the blocking persists until the victim repays enough debt to unlock the dust.
