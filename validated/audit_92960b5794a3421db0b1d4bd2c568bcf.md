### Title
Uncharged compute cost for `create_program_address` derivation during CPI signer translation — underpriced pre-fee work - ([File: program-runtime/src/cpi.rs])

### Summary
`translate_signers` in `program-runtime/src/cpi.rs` derives one PDA (via `Pubkey::create_program_address`, which performs SHA256 hashing) for every signer-seeds set supplied to a cross-program invocation, but never charges the corresponding `create_program_address_units` cost to the compute meter. This mirrors the GMX bug class: real, non-trivial computational work performed as part of an operation is left out of the cost/fee accounting that is supposed to bound and price it, so a user can obtain "compute" cheaper than its actual cost.

### Finding Description
When a Solana program invokes another program via CPI with signer seeds (`sol_invoke_signed`), `cpi_common` (`program-runtime/src/cpi.rs`, lines 773-806) calls `translate_signers`: [1](#0-0) 

`translate_signers` iterates over every provided signer-seeds set and calls `Pubkey::create_program_address(&seeds_bytes, program_id)` for each one, doing the actual SHA256-based PDA derivation work: [2](#0-1) 

There is no `invoke_context.compute_meter.consume_checked(...)` call anywhere inside `translate_signers` for this hashing work. Compare this to the syscall that exposes the same primitive directly to programs, `SyscallCreateProgramAddress`, which explicitly charges `create_program_address_units` before doing the derivation: [3](#0-2) 

The cost table defines `create_program_address_units: 1500` specifically to price one `create_program_address` call: [4](#0-3) 

The only compute charged in `cpi_common` for the whole CPI setup is the flat `invoke_units` (946 CUs) for "an invoke call (not including the cost incurred by the called program)", plus per-byte translation costs for instruction data, account metas, and account infos — none of which account for the seed-hashing cost that `translate_signers` performs: [5](#0-4) [6](#0-5) 

So while a program that calls the raw `create_program_address` syscall directly pays 1500 CUs per derivation, a program that triggers the identical derivation indirectly through a signed CPI (`sol_invoke_signed`) pays nothing extra for it beyond the flat per-invocation cost — regardless of how many signer-seed sets (and how many seeds per set, each up to `MAX_SEED_LEN`) are supplied, up to the enforced `MAX_SIGNERS` / `MAX_SEEDS` limits.

### Impact Explanation
This is a compute-unit accounting gap analogous to the reported gas-estimation bug: work that has a defined, non-zero unit cost elsewhere in the same cost model (`create_program_address_units`) is silently omitted from the code path that actually performs that work during CPI signer verification. The practical effect is that the on-chain compute-budget accounting under-prices SHA256 hashing performed for PDA derivation inside every signed CPI call. An attacker-controlled program can maximize the number of signer-seed sets and seeds per CPI call (bounded only by `MAX_SIGNERS`/`MAX_SEEDS`) across many CPI invocations within a single transaction's CU budget, causing the validator to perform hashing work that is not reflected in the CU/fee cost the transaction pays for, i.e., grossly underpriced pre-fee compute relative to actual validator CPU expenditure.

### Likelihood Explanation
This is reachable by any unprivileged user/program: any BPF program performing a signed CPI (`invoke_signed`) triggers this code path, and the number/size of signer seeds is fully attacker-controlled input, subject only to the existing `MAX_SIGNERS`/`MAX_SEEDS` structural limits, not to any compute charge. No special validator/operator role or malicious snapshot is required, and this is within the banking/execution path (not out-of-scope loader/sBPF-interpreter internals) — it lives in `program-runtime`'s CPI handling used by the SVM/banking stage during ordinary transaction execution.

### Recommendation
Charge `invoke_context.get_execution_cost().create_program_address_units` (multiplied by the number of signer-seeds sets actually derived) inside `translate_signers` before or as part of each `Pubkey::create_program_address` call, mirroring the charge already performed in `SyscallCreateProgramAddress`, so that CPI-triggered PDA derivation is priced identically to a direct syscall invocation.

### Proof of Concept
Not directly executable from the indexed context (no test harness reproduction was located in this pass), but the code paths establish the root cause deterministically:
1. A BPF program performs `sol_invoke_signed` with the maximum permitted number of signer-seed sets, each with the maximum permitted seeds, repeated across as many CPI calls as fit in the transaction's declared CU limit.
2. Each such call passes through `cpi_common` → `translate_signers` (`program-runtime/src/cpi.rs:801-806`), performing one `create_program_address` (SHA256-based) computation per signer-seeds set with zero compute-meter charge for that specific work, unlike the equivalent direct-syscall path (`syscalls/src/lib.rs:821-858`) which charges 1500 CUs per call.
3. Comparing CU consumption of a transaction using N signed CPIs with max seeds vs. N direct `create_program_address` syscalls of equivalent seed complexity would show the CPI path consuming materially fewer CUs than the actual hashing work performed, demonstrating the underpricing gap.
