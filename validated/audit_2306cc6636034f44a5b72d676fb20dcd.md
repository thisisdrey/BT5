### Title
Asset issuer can front-run pending TRC10 transfers by instantly lowering `free_asset_net_limit`/`public_free_asset_net_limit` via `UpdateAssetContract` - (File: actuator/src/main/java/org/tron/core/actuator/UpdateAssetActuator.java)

### Summary
The reported bug class is a privileged, `restricted`-only parameter (`performanceFee`) that can be changed with no delay and front-run against a specific pending user transaction to increase the fee the protocol extracts from that user. The closest reachable analog in java-tron is `UpdateAssetActuator`, which lets a TRC10 asset issuer instantly change the free-bandwidth allowances of their token (`free_asset_net_limit`, `public_free_asset_net_limit`) with zero fee and zero grace period, and this value is read live at the moment any other user's `TransferAssetContract` for that asset is processed.

### Finding Description
`UpdateAssetActuator.execute()` lets the account that issued a TRC10 asset directly overwrite `AssetIssueCapsule.setFreeAssetNetLimit()` / `setPublicFreeAssetNetLimit()` with values supplied in the `UpdateAssetContract`, with no timelock or grace period: [1](#0-0) 

The only bounds checked in `validate()` are that the new values are non-negative and below `dynamicStore.getOneDayNetLimit()` — there is no restriction preventing the issuer from lowering the limits arbitrarily, and no delay before the change takes effect: [2](#0-1) 

`calcFee()` for this actuator returns 0, so the issuer can broadcast the change cheaply and repeatedly: [3](#0-2) 

These limits are read at the time any other account's `TransferAssetContract` for that token is processed by `BandwidthProcessor.useAssetAccountNet()`, which checks `publicFreeAssetNetLimit`/`freeAssetNetLimit` against the current usage and, if the transfer would exceed them, either fails validation or forces the transfer to be paid for out of the sender's own bandwidth/TRX instead of the free asset-bandwidth quota: [4](#0-3) 

Because both the limit-change transaction and the victim's transfer transaction are ordered within the same block by the block producer/`Manager`, an asset issuer who observes a large pending `TransferAssetContract` for their token in the mempool can broadcast an `UpdateAssetContract` immediately before it (front-running), reducing or zeroing the free-bandwidth quota so the victim's transaction is forced to consume its own account bandwidth/TRX (net fee) instead of the token's free allowance it expected when constructing the transaction.

### Impact Explanation
This lets an unprivileged-but-interested party (any TRC10 asset issuer — explicitly an in-scope, non-SR/non-committee actor) manipulate a fee-relevant parameter with no delay, directly at the expense of a specific counterparty transaction, exactly matching the report's bug class ("front-running to obtain a higher fee/cost from the victim"). The victim either pays unexpected TRX bandwidth fees or has the transaction fail, which is a concrete extraction of value/unbacked cost imposed on an unsuspecting user — a medium-severity issue analogous to the reported one.

### Likelihood Explanation
Likelihood is moderate: it requires the asset issuer to actively monitor the mempool for transfers of their own token and to time a competing `UpdateAssetContract` transaction, which is straightforward given the actuator's zero fee and immediate effect (no cooldown), similar to the original report's scenario of front-running `updatePerformanceFee`.

### Recommendation
Add a grace period / effective-block delay before changes to `free_asset_net_limit` and `public_free_asset_net_limit` take effect (mirroring the report's recommendation for `performanceFee`), or snapshot the free-bandwidth limits per transaction based on the state at broadcast/inclusion boundaries rather than allowing same-block manipulation immediately before a specific victim transaction.

### Proof of Concept
1. Issuer A issues TRC10 asset X with `free_asset_net_limit = L1` and `public_free_asset_net_limit = L2`.
2. User B observes generous free bandwidth and broadcasts `TransferAssetContract` for asset X expecting it to be covered by the free quota (no TRX fee).
3. Issuer A sees B's pending transaction in the mempool and broadcasts `UpdateAssetContract` setting `new_limit = 0` and `new_public_limit = 0` for asset X, with a higher priority/lower fee so it lands in the same block before B's transfer.
4. `UpdateAssetActuator.execute()` immediately zeroes the limits [5](#0-4) .
5. When B's `TransferAssetContract` is then processed, `BandwidthProcessor.useAssetAccountNet()` sees `bytes > (freeAssetNetLimit - newFreeAssetNetUsage)` and returns `false`, causing B's account bandwidth/TRX to be charged instead of the expected free quota [6](#0-5) .
