### Title
TRC10 Exchange (Bancor-curve) legacy floating-point math permits value extraction from the shared liquidity pool that leaves other participants under-collateralized - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Opyn report describes a shared pool (`MarginPool`) whose invariant (collateral backing outstanding obligations) can be broken by adverse conditions with no automatic corrective/liquidation mechanism, letting one user withdraw more value than they contributed at the expense of the pool's other participants. The closest reachable analog in java-tron is the TRC10 `Exchange` (a Bancor-formula AMM) which pools two tokens for many independent traders. By default the calculation uses double-precision floating point (`ExchangeProcessor`), while a `BigDecimal`-based, invariant-checked implementation (`SafeExchangeProcessor`) exists but is only active when the `allowHardenExchangeCalculation` dynamic property/committee proposal is turned on.

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy floating point `ExchangeProcessor` and the exact `SafeExchangeProcessor` based on `hardenedCalc` (i.e., `allowHardenExchangeCalculation()`), a flag read by `AbstractExchangeActuator.allowHarden()`. [1](#0-0) [2](#0-1) 

The legacy `ExchangeProcessor.exchange()` computes the Bancor "relay" supply and payout using `double` arithmetic and `Math.pow`, with no invariant check that the computed `buyTokenQuant` never exceeds the pool's actual reserves: [3](#0-2) 

`ExchangeTransactionActuator.execute()` trusts this result directly and mutates account/pool balances with it — any unrepresentable-in-binary-fraction inputs, or repeated small trades, can accumulate floating-point rounding error in the trader's favor (or against the pool), silently draining reserve balances below what the invariant should permit: [4](#0-3) 

The safe/hardened counterpart, `SafeExchangeProcessor`, uses `BigDecimal` with fixed 18-digit rounding and, per the test suite, guarantees `result <= buyTokenBalance` (never overshoots the pool's reserve) — confirming the legacy path lacks that guarantee: [5](#0-4) [6](#0-5) 

The test suite explicitly demonstrates that the legacy and hardened processors diverge on identical inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), proving the legacy path's numeric output is not equivalent/invariant-safe: [7](#0-6) 

This mirrors the Opyn bug class exactly: a pool that jointly backs multiple independent participants' claims (here, the AMM's `firstTokenBalance`/`secondTokenBalance` reserve, analogous to the `MarginPool`) has an accounting mechanism (`ExchangeProcessor`'s float math, analogous to the absent liquidation-incentive correction) that can drift out of sync with the true invariant, allowing one participant (an unprivileged trader broadcasting `ExchangeTransactionContract`) to extract value the reserve cannot fully back, to the detriment of the liquidity-providing creator who later calls `ExchangeWithdrawActuator`.

### Impact Explanation
If floating-point drift permits a trader to receive more of the buy-token than the Bancor invariant dictates, the pool's reserves become inconsistent with the recorded exchange ratio. The exchange creator (the only account permitted to withdraw, per `ExchangeWithdrawActuator.doValidate()`'s creator check) can subsequently be unable to withdraw the full proportional share it is owed, or worse — repeated exploitation across many small transactions could drain reserves such that later withdrawals fail (`"exchange balance is not enough"`) or return disproportionately smaller amounts. This is an unbacked-value / fund-freezing risk on a broadcastable, unprivileged transaction path (`ExchangeTransactionContract`), matching the "unbacked balance" / "theft of funds" impact criteria.

### Likelihood Explanation
Any unprivileged account can call `ExchangeTransactionActuator` an unlimited number of times against any existing TRC10 exchange without needing the `allowHardenExchangeCalculation` flag disabled — that flag being off (legacy path) is the *default* unless a super-representative/committee proposal has switched it on. Repeated small trades systematically exploiting binary-floating-point rounding could be automated cheaply, making exploitation straightforward to attempt, though the aggregate value extracted per transaction from rounding alone is small and would need many repetitions or larger pools to become material — this is why the underlying Opyn issue was itself rated only "High" difficulty rather than trivial.

### Recommendation
Enable `allowHardenExchangeCalculation` (the `SafeExchangeProcessor` / `BigDecimal` invariant-checked path) by default rather than gating it behind an optional committee proposal, and add an explicit post-trade assertion in `ExchangeCapsule.transaction()` that `buyTokenQuant <= buyTokenBalance` regardless of which processor computed it, throwing `ContractValidateException` otherwise (mirroring the audit's "act as liquidator of last resort" recommendation but implemented as a hard invariant check rather than a market-dependent correction).

### Proof of Concept
1. Create a TRC10 exchange pool with `firstTokenBalance`/`secondTokenBalance` chosen such that the Bancor curve's `Math.pow` computation on `double` produces a rounding-favorable output (values near representable-fraction boundaries, as exercised by the divergence shown in `ExchangeProcessorTest.testStrictMath`, e.g. `{4732214L, 2202692725330L, 29218L}` vs `SafeExchangeProcessor`'s result for the same input).
2. Repeatedly broadcast `ExchangeTransactionContract` transactions (unprivileged, no permission required beyond owning the trade-in tokens) trading small quantities back and forth through `ExchangeTransactionActuator`.
3. Observe that the legacy `ExchangeProcessor` path yields payouts that diverge from the `SafeExchangeProcessor` reference values (confirmed directly by the repo's own test `testStrictMath`), and that no invariant check in `ExchangeCapsule.transaction()` prevents `buyTokenQuant` from exceeding the true proportional entitlement when `hardenedCalc` is false.
4. The exchange creator's subsequent `ExchangeWithdrawActuator` call then either fails with `"exchange balance is not enough"` or returns less than the proportional share, demonstrating the pool has been left under-backed relative to recorded balances — the fund-freezing/unbacked-balance outcome analogous to Eve's over-withdrawal from the Gamma Protocol `MarginPool`.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

      long result = SafeExchangeProcessor.INSTANCE.exchange(row[0], row[1], row[2]);
      Assert.assertTrue("Result must be non-negative", result >= 0);
      Assert.assertTrue("Result must not exceed buy reserve, got " + result + " > " + row[1],
          result <= row[1]);
    }
  }
