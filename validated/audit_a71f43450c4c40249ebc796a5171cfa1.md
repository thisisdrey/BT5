### Title
Malformed `ft_transfer_call` return value causes full refund despite real token transfer, double-crediting `sender_id` - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`ft_resolve_withdraw` treats any non-deserializable JSON result from a successful `ft_transfer_call` promise as `used = 0`, refunding the entire withdrawn `amount` back to `sender_id`'s internal balance. A malicious FT contract that performs the real token transfer to `receiver_id` but returns a malformed (non-`U128`) success value causes Defuse to re-credit `sender_id` the full amount while the tokens have already left custody, breaking the settlement invariant for that token.

### Finding Description
The broken binding: `debited(sender_id, token) == amount` should equal `delivered(receiver_id) == amount` XOR `refunded(sender_id) == amount`, never both. In `ft_resolve_withdraw`: [1](#0-0) 

When `is_call` is true and the promise executes successfully but the returned bytes are not a valid `U128` (`Ok(Err(_deserialize_err)) => 0`), the code assumes none of the tokens were consumed and sets `used = 0`, forcing `refund = amount.0` at line 183, which is credited back to `sender_id` via `self.deposit(...)` at lines 184-191.

This branch assumes NEP-141-compliant semantics: that a token contract only returns a non-parseable value when the receiving contract's `ft_on_transfer` failed and the token contract internally refunded the transfer back to the sender (Defuse's own account in the token contract), so no real custody change occurred. However, since `token` is an attacker-deployed, attacker-controlled contract (explicitly in scope per the rules), nothing enforces this relationship between the contract's actual balance movement and its returned JSON. The attacker's `ft_transfer_call` implementation can unconditionally move `amount` of the token to `receiver_id` (a real balance change reducing Defuse's custodied balance at the token contract) while returning arbitrary malformed data instead of a `U128`.

Exploit flow: attacker (as `sender_id`, having previously deposited `amount` of their own token `token` and holding a Defuse-internal balance of `amount`) calls `ft_withdraw(token, receiver_id, amount, ..., msg=Some(..))` to trigger the `is_call` path. The malicious `token` contract's `ft_transfer_call` transfers `amount` to `receiver_id` unconditionally, then returns e.g. `"not-a-u128"`. `ft_resolve_withdraw` fails to deserialize this as `U128`, hits the `Ok(Err(_))` branch, sets `used = 0`, and re-credits `sender_id`'s Defuse balance with `amount` via `deposit`. Now `sender_id`'s internal ledger shows `amount` (never actually debited-and-not-refunded) even though the real tokens left the Defuse-custodied balance for `receiver_id`.

None of the existing guards prevent this: `#[private]` only restricts the caller to be the contract itself (satisfied via the scheduled callback), and there is no independent verification of the token contract's actual balance change against the returned value — Defuse fully trusts the external contract's return payload.

### Impact Explanation
For the specific `Nep141TokenId(token)` accounting line, `sender_id`'s balance is doubled relative to what is truly custodied: the resolver both allows real assets to leave to `receiver_id` and re-credits the same `amount` back to `sender_id`. If this token type is shared with other depositors (i.e., not solely attacker-minted), this creates an under-collateralized ledger entry for the Verifier — a refund/resolver credit that does not match what failed to settle, matching the Critical category explicitly listed in the rules ("a refund or resolver credit that does not match what failed to settle"). The attack is repeatable per withdrawal call against the same or different malicious token contracts, and the blast radius is bounded to the `TokenId` of the attacker's chosen token, but is systemic to any accounting/liquidity that treats that `TokenId`'s ledger as sound.

### Likelihood Explanation
Preconditions are fully within the unprivileged attacker's control: deploy a custom FT contract, deposit `amount` of it into Defuse, then call `ft_withdraw` with a `msg` to force the `is_call`/`ft_transfer_call` path. No special role, relayer key, or victim signature is needed — cost is only gas and the ability to deploy a contract. This is trivially repeatable across attempts and token types.

### Recommendation
Do not treat a non-deserializable success result as `used = 0`. Either (a) treat any successful-but-unparseable `ft_transfer_call` result the same as the `Err(_)` (promise failure) branch is intentionally *not* treated (i.e., do not refund, since the call succeeded and NEP-141 compliant contracts guarantee a parseable `U128` on success), or (b) require the returned value to parse as `U128` and abort/panic (treat malformed output as a protocol violation) rather than silently assuming `used = 0` and issuing a full refund.

### Proof of Concept
`cargo test` / `near-workspaces` plan:
1. Deploy a stub FT contract `evil_ft` whose `ft_transfer_call` performs the standard internal balance transfer of `amount` from the Defuse account to `receiver_id`, but returns a raw string like `"not-a-u128"` instead of a JSON `U128`.
2. Deploy Defuse contract; have `sender_id` deposit `amount` of `evil_ft` tokens, establishing `token_balances[sender_id][evil_ft] == amount`.
3. Call `ft_withdraw(evil_ft, receiver_id, amount, memo=None, msg=Some("noop"))` from `sender_id` (forcing `is_call = true`).
4. After promise resolution, assert both sides of the binding:
   - `evil_ft.ft_balance_of(receiver_id) == amount` (real tokens delivered), and
   - Defuse's `token_balances[sender_id][evil_ft] == amount` (full refund also credited),
   proving `delivered + refunded == 2 * amount` instead of `amount`.
