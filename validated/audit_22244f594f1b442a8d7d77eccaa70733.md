### Title
Missing access control on `init_global_fee_state` allows front-running to seize the global fee admin role - (File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs)

### Summary
The `init_global_fee_state` instruction, which creates the program-wide `FeeState` PDA singleton, accepts an arbitrary `admin_key` argument and stores it as `global_fee_admin` with no check that the caller (`payer`) is the program's deploying/upgrade authority or any other privileged entity. Anyone who submits this instruction first — e.g., by front-running the legitimate deployer immediately after the program is deployed — permanently becomes the `global_fee_admin` for the entire protocol, since the `FeeState` account is a PDA (`seeds = [FEE_STATE_SEED]`) that can only be initialized once.

### Finding Description
`InitFeeState::fee_state` is a PDA derived solely from `FEE_STATE_SEED` and initialized with Anchor's `init` constraint, so only one `FeeState` can ever exist for the program: [1](#0-0) 

The handler itself performs no validation that `ctx.accounts.payer` matches any privileged key (e.g., the program's upgrade authority); it simply writes the caller-supplied `admin_key` into `fee_state.global_fee_admin`: [2](#0-1) 

The only gating is the Anchor account struct, which requires nothing more than any transaction signer paying rent: [3](#0-2) 

The entrypoint in `lib.rs` is documented as "(Runs once per program)" but this is only an operational convention, not an enforced access-control check: [4](#0-3) 

Once `global_fee_admin` is set, it becomes the sole authority permitted to call `edit_global_fee_state` (`EditFeeState`), which is gated only by `has_one = global_fee_admin`: [5](#0-4) 

This exactly matches the reported bug class: an unprivileged init function that lets "anyone… initialize himself as an admin," rather than being restricted to the deploying/authorized party.

### Impact Explanation
Whoever wins the race to call `init_global_fee_state` becomes `global_fee_admin`, a protocol-wide privileged role (as documented, distinct from any single group's `admin`) that can subsequently call `edit_global_fee_state` to: set/rotate its own admin key, redirect the `global_fee_wallet` (protocol fee destination) to an attacker-controlled account, set `pause_delegate_admin`, and adjust protocol-wide fee parameters (`program_fee_fixed`, `program_fee_rate`, liquidation/order fees) across every group and bank in the protocol. Since `FeeState` is a singleton PDA, this is not scoped to one group — it affects the entire program. This can lead to protocol fee redirection to an attacker (theft) and unauthorized control over global fee/pause configuration (unauthorized state change) once the attacker sets themselves as the permanent `global_fee_admin`.

Unlike `marginfi_group_initialize` — which is intentionally permissionless because each `MarginfiGroup` is a user-created container and the caller only becomes admin of the group they create — `init_global_fee_state` protects a singular, protocol-wide resource, so seizing it has protocol-wide consequences rather than being scoped self-harm.

### Likelihood Explanation
This requires the attacker to front-run the legitimate deployer's call to `init_global_fee_state` immediately after program deployment (or after any redeployment/PDA re-creation scenario), which is a narrow but realistic window on a public mempool/validator network — attackers can monitor for new program deployments and race the initialization transaction. If the deployer already called it first, the PDA `init` constraint prevents re-initialization, so the exposure window is limited to the deployment race.

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) to only be callable by the program's upgrade authority (validated via the `BpfLoaderUpgradeable` `ProgramData` account) or another statically known deployer key, rather than accepting any signer as `payer`. Alternatively, bake the intended admin key into the program constants at build time so the instruction cannot accept an attacker-supplied `admin_key` from an arbitrary caller.

### Proof of Concept
1. Program `marginfi` is deployed on-chain; the `FeeState` PDA (seeds `[FEE_STATE_SEED]`) does not yet exist.
2. An attacker observes the deployment (e.g., via monitoring new program deployments) and submits `init_global_fee_state(admin_key = attacker_pubkey, fee_wallet = attacker_wallet, ...)` before the legitimate deployer's initialization transaction lands, paying the PDA rent themselves as `payer`.
3. Because `InitFeeState` accounts only require `payer: Signer<'info>` with no ownership/authority check (see `init_global_fee_state.rs:37-55`), the transaction succeeds and `fee_state.global_fee_admin = attacker_pubkey`, `fee_state.global_fee_wallet = attacker_wallet` are persisted on-chain.
4. The legitimate deployer's subsequent `init_global_fee_state` call now fails (`init` constraint — account already exists).
5. The attacker now calls `edit_global_fee_state` as `global_fee_admin` (passes the `has_one = global_fee_admin` check in `edit_global_fee.rs:108-121`) to further entrench control, redirect fees, or set a `pause_delegate_admin` of their choosing, affecting every group/bank in the protocol.
