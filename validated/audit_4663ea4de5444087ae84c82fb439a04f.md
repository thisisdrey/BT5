### Title
Unauthenticated `RecvError` packet allows a network observer to force tunnel teardown by replaying a sniffed `RemoteIndex` - (File: `outside.go`)

### Summary
The TON bug in the external report allowed an observer to submit an unauthenticated/unvalidated reference (a tracker hash tied to the wrong nonce) that the protocol trusted to drive a state transition (a refund) without checking that the reference actually corresponded to the CCTX it was claimed to belong to. The same bug class — accepting a bare index/reference from the wire and using it to mutate connection state without any cryptographic binding to the actual session — exists in Nebula's `header.RecvError` handling.

### Finding Description
In `readOutsidePackets`, packets are dispatched on `h.Type` before any AEAD authentication happens: [1](#0-0) 

`header.RecvError` is handled immediately via `f.handleRecvError(via.UdpAddr, h)`, using only the plaintext header fields (`h.RemoteIndex`). Unlike `header.Message`/`header.Handshake` traffic, a `RecvError` packet carries no AEAD tag and is not run through `ConnectionState.Decrypt`/`Bits` replay-window logic, so there is no proof that the sender who produced it is the actual remote peer holding the corresponding `ConnectionState`. Every `Message` packet on the wire carries the recipient's `RemoteIndex` (their own `localIndexId`) in cleartext in the header: [2](#0-1) 

Any passive observer who can see any packet of an established tunnel (satisfying the "malicious observer" threat model — no CA-signed cert required, no participation in the handshake) can read this cleartext index and craft a forged `RecvError` packet carrying it, exactly as the TON tracker bug allowed a hash to be submitted for a nonce/CCTX the submitter did not actually own or verify.

This is structurally the same root cause as the reported issue: the index/reference used to drive a state transition (there: CCTX refund; here: hostinfo teardown / re-handshake) is trusted without validating it is bound to the actual authenticated session that produced it.

### Impact Explanation
An observer who can see traffic between two Nebula nodes (e.g. on a shared network segment, or an ISP-level observer, without needing to hold a CA-signed certificate or be a party to the tunnel) can forge `RecvError` packets addressed to either endpoint using the sniffed `RemoteIndex`, forcing repeated teardown/re-handshake of the tunnel. This is a remote-state-poisoning / availability impact (denial-of-service, forced handshake churn) reachable by an unauthenticated network observer, matching the "remote state poisoning" category called out in the validation criteria. It does not by itself break confidentiality or forge data-plane traffic (the AEAD/replay window in `ConnectionState.Decrypt` still protects actual data), but it does allow an outsider to unilaterally disrupt an established, otherwise-secure tunnel using only information visible on the wire.

### Likelihood Explanation
Likelihood is high for anyone positioned to observe traffic on the path (a "malicious observer" per the given threat model): the `RemoteIndex` needed to forge the packet is transmitted in cleartext in every packet's header, and `RecvError` packets are processed before any authentication check is performed, so no cryptographic material or certificate is needed to mount the attack.

### Recommendation
Bind `RecvError` handling to some proof of session ownership (e.g., require it be authenticated/MACed similarly to relay frames via `VerifyRelay`, or require the reported index be corroborated by an out-of-band signal from the connection manager) rather than acting on the bare `h.RemoteIndex` from an unauthenticated packet type.

### Proof of Concept
Not executed — this is a design-level review of `outside.go`'s dispatch and `header.RecvError` handling; the exact body of `handleRecvError` (in `interface.go`) was not fully inspected before the tool budget was exhausted, so the precise state mutations it performs (e.g., which hostinfo is deleted, whether it also requires a matching local index rather than just any observed one) could not be fully confirmed. A Devin session with full repo access should verify `handleRecvError`'s implementation in `interface.go` to confirm exact impact scope before treating this as a confirmed, high-severity finding.
