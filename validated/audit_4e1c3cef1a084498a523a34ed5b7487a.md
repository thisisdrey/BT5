## Title
AccountPermissionUpdateContract allows an Active-key holder to overwrite Owner permissions and seize full account control - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The LiteLLM bug allowed a caller who was correctly authorized to reach `/user/update` for their *own* account to change an unrestricted field (`user_role`) and escalate to `proxy_admin`. The java-tron analog is `AccountPermissionUpdateContract`: it correctly restricts the target to `owner_address` (the signer's own account) but places no restriction on *which permission fields* a lower-privileged signer is allowed to rewrite. Any key holding only an `Active` permission with the `AccountPermissionUpdateContract` operation bit enabled can submit a transaction that completely replaces the account's `Owner` permission (and Active/Witness permissions), granting itself full account control while meeting only the Active permission's own (typically much lower) signing threshold.

### Finding Description
`AccountPermissionUpdateActuator.validate()` and `execute()` verify that the target account exists and that the new `owner`/`witness`/`actives` permissions are internally well-formed (key counts, thresholds, distinct addresses, operations bitmap sanity), but never checks *what permission the current transaction signer used* to authorize the change: [1](#0-0) 

The actual restriction on which contract types an Active-permission key may invoke is enforced separately and generically at the signature layer, in `TransactionCapsule.checkPermission`: [2](#0-1) 

If `permissionId != 0` (i.e. an Active permission is used to sign), the only gate is `checkPermissionOperations`, which just tests whether the bit for the contract's `type` (e.g. `AccountPermissionUpdateContract` = 46) is set in that Active permission's 32-byte `operations` bitmap: [3](#0-2) 

`AccountPermissionUpdateActuator.checkPermission()` validates the `operations` bitmap of a new Active permission only against the globally *available* contract types (`dynamicStore.getAvailableContractType()`), with no special-casing that excludes `AccountPermissionUpdateContract` itself: [4](#0-3) 

Consequently, once an account owner grants any Active permission with bit 46 set (e.g. to a hot-wallet/automation key intended only for limited operations), the holder of that Active key can sign an `AccountPermissionUpdateContract` transaction themselves. Weight/threshold checking for that transaction uses the *Active permission's own threshold* (`checkWeight(permission, ...)` where `permission` is the Active permission), not the Owner permission's threshold: [5](#0-4) 

This is exactly the LiteLLM bug-class pattern: the endpoint (`AccountPermissionUpdateContract`) is correctly scoped to "your own account" (`owner_address` must match), but there is no field-level authorization separating "grant/modify permission structures" (an Owner-only capability) from "operate under an Active permission with a matching operation bit" — a low-privilege role can flip the account's own `Owner` field to itself.

### Impact Explanation
An account that ever configures an Active permission including the `AccountPermissionUpdateContract` operation bit (bit 46) permanently exposes itself to full takeover by the holder of that Active key: that key can rewrite `owner` permission to contain only its own address/weight, locking out the legitimate owner and any co-signers, and gaining unilateral control of the account's assets and future transactions. This is a concrete unauthorized account takeover / permanent loss-of-control impact.

### Likelihood Explanation
Exploitation requires only that the account owner previously granted an Active permission with the `AccountPermissionUpdateContract` bit set — a configuration choice available through the normal, unprivileged `AccountPermissionUpdateContract` transaction flow itself (no special/malicious-SR access needed). Any wallet, exchange integration, or automation tool that is granted such an Active key (commonly done broadly, e.g. "allow all contract types" bitmaps) can trivially broadcast the takeover transaction; no additional bug needs to be chained.

### Recommendation
Add a hard restriction in `AccountPermissionUpdateActuator.checkPermission()` (and/or in `TransactionUtil.checkPermissionOperations`) that unconditionally forbids setting the `AccountPermissionUpdateContract` bit in any Active permission's operations bitmap, since granting that operation type is equivalent to granting Owner-level control. Alternatively, enforce in `TransactionCapsule.checkPermission`/`validateSignature` that transactions of type `AccountPermissionUpdateContract` must always be signed with `permissionId == 0` (Owner permission), regardless of the operations bitmap of any Active permission.

### Proof of Concept
1. Account `A` is created with a default Owner permission (threshold 1, key `A`).
2. `A` sends an `AccountPermissionUpdateContract` adding an Active permission with `threshold=1`, one key `B` (weight 1), and `operations` bitmap with bit 46 (`AccountPermissionUpdateContract`) set — this passes `checkPermission()` since the bit is only checked against `getAvailableContractType()`, per [6](#0-5) .
3. Key `B` alone (permission_id = the Active permission's id) signs and broadcasts a new `AccountPermissionUpdateContract` for owner address `A`, setting `owner` permission to contain only key `B` with weight 1/threshold 1.
4. Signature validation only checks the Active permission's operation bit and its own threshold, per [2](#0-1) , so the transaction is accepted.
5. `AccountPermissionUpdateActuator.execute()` overwrites `A`'s Owner permission unconditionally: [1](#0-0) . Key `B` now solely controls account `A`.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
