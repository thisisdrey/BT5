### Title
Unbounded PCRE query in `SearchFilesByContent` enables ReDoS via `git grep --perl-regexp` - (File: internal/gitaly/service/repository/search_files.go)

### Summary
`SearchFilesByContent` passes the attacker-controlled `Query` field directly into `git grep --perl-regexp -e <query>` with no length or complexity restriction, unlike the sibling `SearchFilesByName` RPC which caps its `Filter` field at `searchFilesFilterMaxLength = 1000` before compiling it with Go's linear-time `regexp` package. Because `--perl-regexp` invokes PCRE2's backtracking engine rather than RE2, a crafted pattern (e.g. `(a+)+$`) evaluated against attacker-supplied repository content can trigger exponential-time matching in the spawned `git-grep` subprocess.

### Finding Description
In `SearchFilesByContent` (internal/gitaly/service/repository/search_files.go:32-66), `req.GetQuery()` is passed unmodified as the `-e` value to `git grep --perl-regexp`, with only a "non-empty" check performed in `validateSearchFilesRequest` (internal/gitaly/service/repository/search_files.go:174-192). [1](#0-0) [2](#0-1) 

By contrast, `SearchFilesByName` explicitly caps its regex-like `Filter` input at 1000 characters specifically to "thwart excessive resource usage when filtering," and compiles it with Go's `regexp` (RE2, guaranteed linear-time, no catastrophic backtracking). [3](#0-2) 

`git grep --perl-regexp` uses PCRE2's backtracking matcher, which is susceptible to catastrophic backtracking on patterns like `(a+)+$` or `(a|a)*$` when applied to non-matching or partially-matching long lines. An attacker who owns a repository (unprivileged, self-service) can push a large text blob engineered to maximize backtracking and then repeatedly call `SearchFilesByContent` with such a pattern against `HEAD`, causing the spawned `git grep` child process to consume CPU disproportionately to input size.

### Impact Explanation
This is a resource-exhaustion / DoS concern against a shared Gitaly node: excessive CPU consumption by the `git-grep` child process degrades throughput for other tenants/repositories co-located on the same storage node, matching the "Denial of Service" bounty impact class for a multi-tenant Gitaly service.

### Likelihood Explanation
Note: I could not fully verify actual worst-case severity in this codebase/environment. PCRE2 (as compiled into Git) applies internal backtracking/match-count limits by default (`match_limit`/`depth_limit`), which bound worst-case work per invocation to a large but finite number of steps — this mitigates (but does not eliminate) truly unbounded hangs; the practical CPU cost still scales much worse than the RE2-backed `SearchFilesByName` path and there is no complexity/length gate at the Gitaly layer as there is for `Filter`. I was unable to determine from the codebase whether an RPC-level timeout, per-request CPU/wall-clock cap, or concurrency limiter is configured by default for `SearchFilesByContent` (the concurrency limiter framework exists in `internal/grpc/middleware/limithandler`, but whether `SearchFilesByContent` is included in any default per-RPC limit configuration is not evident from this code and would need runtime config inspection). If no such external timeout/limit applies, repeated invocation by an unprivileged repo owner is straightforward and fully repeatable, since the attacker fully controls both `Query` and repository content and needs no privileged access.

### Recommendation
Impose a length/complexity cap on `Query` for `SearchFilesByContent` analogous to `searchFilesFilterMaxLength`, and/or enforce a hard execution timeout on the spawned `git grep` process (e.g., via `context.WithTimeout` wrapping `repo.Exec`) so a single request cannot consume unbounded CPU regardless of pattern complexity. Consider also restricting to non-backtracking regex features or documenting/enforcing PCRE2 `match_limit`/`depth_limit` via `GIT_CONFIG` for the child process.

### Proof of Concept
```go
func TestSearchFilesByContent_ReDoS(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repo, repoPath := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg, cfg.SocketPath)

    // Craft a large line that does not match the pattern quickly,
    // forcing PCRE2 backtracking.
    payload := strings.Repeat("a", 40) + "!"
    content := strings.Repeat(payload+"\n", 5000)
    gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"),
        gittest.WithTreeEntries(gittest.TreeEntry{
            Mode: "100644", Path: "big.txt", Content: content,
        }))

    start := time.Now()
    stream, err := client.SearchFilesByContent(ctx, &gitalypb.SearchFilesByContentRequest{
        Repository: repo,
        Ref:        []byte("main"),
        Query:      "(a+)+$",
    })
    require.NoError(t, err)
    for {
        _, err := stream.Recv()
        if err == io.EOF {
            break
        }
        require.NoError(t, err)
    }
    t.Logf("elapsed: %s", time.Since(start))
    // Assert: no hard timeout/limit exists today; elapsed time scales
    // disproportionately with crafted content size/pattern, unlike
    // SearchFilesByName's Filter which is capped and RE2-backed.
}
```
Expected observation: wall-clock time for the crafted query grows disproportionately compared to equivalent-size benign queries or to `SearchFilesByName`'s bounded `Filter`, with no server-side rejection based on query complexity/length.

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
