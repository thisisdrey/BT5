## Analysis

The Caviar report's core broken invariant is: **an AMM computes swap/liquidity amounts from a balance snapshot, then performs a "token transfer" that is actually a call into attacker-controlled, Turing-complete token logic (an ERC-777 hook), which can re-enter the AMM before its own accounting is settled** — there is no reentrancy guard on the public `buy`/`sell`/`add`/`remove` functions, only a slippage check on a value computed from stale reserves.

The Polkadot SDK analog is structurally identical in `pallet-asset-conversion` once its generic `T::Assets: fungibles::*` bound is satisfied by `pallet-revive`'s ERC20 fungibles adapter.

### Corrupted value
The pool reserve/balance values used by `get_reserves` / `get_amount_out` / `get_amount_in`, and the LP-token mint amount in `do_add_liquidity`, all become attacker-influenceable mid-call.

### Mechanism

1. `pallet-asset-conversion` never talks to a concrete currency — every reserve read and value transfer goes through the generic trait: [1](#0-0) [2](#0-1) 

2. `pallet-revive` supplies a `fungibles::Inspect`/`Mutate` implementation that treats an arbitrary EVM/PVM contract address as an `AssetId`, and implements `balance()`, `mint_into()`, `burn_from()` by issuing a real dispatched `bare_call` into that contract's `balanceOf`/`transfer` functions: [3](#0-2) [4](#0-3) 

3. `pallet-asset-conversion-precompiles` exposes `swapExactTokensForTokens`/`addLiquidity`/etc. to arbitrary Solidity contracts, explicitly to let contracts hold and trade against tokens implemented as contracts: [5](#0-4) 

4. Inside the swap/liquidity logic, reserves are read via `get_reserves`/`get_balance` (which for a contract-backed asset means an external `bare_call` into attacker bytecode), amounts are computed from that snapshot, and only afterwards are transfers/mints executed — themselves further external calls into the same attacker bytecode: [6](#0-5) [7](#0-6) 

5. The only ordering discipline in these functions is `#[transactional]` for storage rollback-on-error, which does **not** prevent reentrant execution mid-call — it only guarantees an all-or-nothing commit, exactly like Caviar's functions had no `nonReentrant` guard: [8](#0-7) 

This reproduces the Caviar CEI violation: `get_reserves` (⇔ `buyQuote`/`sellQuote` using `balanceOf`) is computed, then `T::Assets::transfer`/`mint_into`/`burn_from` (⇔ `safeTransferFrom`/`safeTransfer`) executes arbitrary attacker code (⇔ ERC-777 hook) before the pool's internal state for that operation is finalized, letting a multi-hop swap or a nested `add_liquidity`/`remove_liquidity` call re-enter with a stale/manipulated reserve view and mint or extract more than the true invariant allows.

### Caveat (explicitly unverified)
I could not fully confirm within the available tool budget whether `pallet-revive`'s own reentrancy flag (`executing_contract`, gating `Invokable::run_guarded` and returning `ReenteredPallet`) also wraps the internal `Self::bare_call` helper used by `impl_fungibles.rs`'s `balance`/`mint_into`/`burn_from`, or only the top-level `Call`/`Instantiate` dispatchables. If that guard does cover `bare_call`, the specific reentrant fund-extraction path described above would instead fail with `ReenteredPallet`, and the residual issue becomes a functional break (any pool containing a pallet-revive-backed asset can never be swapped into from within a contract call, defeating the stated purpose of `pallet-asset-conversion-precompiles`). This distinction should be verified with a concrete integration test before treating the finding as fund-theft rather than availability breakage.

### Title
Reentrancy in `pallet-asset-conversion` swap/liquidity paths via contract-backed (`pallet-revive`) fungible assets — (`substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s reserve reads and settlement transfers are performed through the generic `T::Assets: fungibles::*` interface. When an `AssetKind` is backed by `pallet-revive`'s ERC20 fungibles adapter, every `balance`, `transfer`, `mint_into`, and `burn_from` call becomes a real dispatched call (`bare_call`) into attacker-controlled EVM/PVM bytecode. The pallet computes swap/liquidity amounts from a reserve snapshot and only afterward performs these external "asset" calls, with no reentrancy guard beyond `#[transactional]` rollback-on-error — the same CEI violation as the reported Caviar ERC-777 bug.

### Finding Description
`get_reserves`/`get_balance` (`substrate/frame/asset-conversion/src/lib.rs:1499-1514`, `1267-1269`) read pool balances via `T::Assets::balance`. For a pool asset backed by `pallet-revive::impl_fungibles`, this triggers a dispatched `bare_call` into an arbitrary contract's `balanceOf` (`substrate/frame/revive/src/impl_fungibles.rs:100-123`). `credit_swap`/`swap` and `do_add_liquidity`/`do_remove_liquidity` then invoke `T::Assets::transfer`/`resolve`/`mint_into`/`burn_from` (`substrate/frame/asset-conversion/src/lib.rs:1208-1243`, `855-879`, `942-952`), each of which for a contract-backed asset dispatches into the same attacker contract's `transfer` (`substrate/frame/revive/src/impl_fungibles.rs:161-241`). Because `pallet-asset-conversion` never re-checks the invariant after these external calls beyond the initial slippage bound computed from the pre-call snapshot, and provides no per-call reentrancy lock (only transactional rollback on hard failure), a malicious contract acting as one leg of the pool can implement `transfer`/`balanceOf` to call back into the `pallet-asset-conversion-precompiles` (`substrate/frame/asset-conversion/precompiles/src/lib.rs:289-319`) mid-operation and manipulate reserve/LP-token accounting before the outer call finishes, exactly mirroring Caviar's `buy`/`sell` reentrancy through ERC-777 hooks.

### Impact Explanation
If the reentrancy is reachable (not blocked by `pallet-revive`'s dispatch-level guard — see caveat), an attacker can drain a pool or mint excess LP tokens against under-priced/duplicated reserve state, i.e. theft/unbacked value extraction from a public swap/liquidity entrypoint reachable by any unprivileged account — matching "theft or unbacked mint or unlock" and "duplicate settlement" impact categories. If the reentrancy guard does intercept it, the residual impact is a runtime bug that silently breaks the intended contract-to-DEX use case for any pool containing a `pallet-revive`-backed asset.

### Likelihood Explanation
Reaching this path requires only: (1) an asset-conversion pool created against a `pallet-revive`-backed "asset" whose `AssetKind` maps to an EVM/PVM contract address, and (2) that contract being attacker-deployed with malicious `transfer`/`balanceOf` logic — both permissionless operations available to any account, with no privileged/governance/relayer assumptions. This matches the pivot criterion that public wrappers and value-bearing pallets must not permit externally-triggered re-entrant execution to corrupt accounted amounts.

### Recommendation
Add an explicit reentrancy guard around `pallet-asset-conversion`'s state-mutating entrypoints (`do_add_liquidity`, `do_remove_liquidity`, `swap`, `credit_swap`) analogous to `pallet-contracts`/`pallet-revive`'s `allows_reentry`/`ReentranceDenied` mechanism, or restrict `T::AssetKind`/`T::Assets` configurations used with `pallet-asset-conversion` (and its precompile) so that no configured asset can trigger externally-controlled, Turing-complete code during `balance`, `transfer`, `mint_into`, or `burn_from`. At minimum, re-validate reserves/invariants immediately after each external asset call rather than relying solely on a pre-call snapshot and post-hoc slippage bound.

### Proof of Concept
1. Deploy a malicious PVM/EVM contract `M` implementing the ERC20 interface, whose `transfer`/`balanceOf` function, when invoked by the checking account, calls back into the `AssetConversion` precompile (`substrate/frame/asset-conversion/precompiles/src/lib.rs`) to trigger `swapExactTokensForTokens` or `addLiquidity` against the same pool.
2. Create an asset-conversion pool pairing `M` (as a `pallet-revive`-backed `AssetKind`) with a native/asset-based token, and seed it with liquidity.
3. Call `swap_exact_tokens_for_tokens`/`add_liquidity` from within a contract holding `M`; during the nested `T::Assets::mint_into`/`transfer` call into `M`, have `M`'s hook re-invoke the same pool's swap/liquidity precompile call before the outer call's reserve/LP accounting is finalized.
4. Observe that the reserve values read by the nested call reflect the outer call's pre-settlement state, allowing amounts/LP tokens to be computed and withdrawn against a stale invariant — reproducing the Caviar-style "buy 6×, then sell against inflated balance" profit extraction pattern.
