Based on my investigation, I found a valid analog to the reported bug class in the responder-side handshake retransmit handling.

### Title
Duplicate stage-1 handshake retransmit lets a spoofed UDP source silently repoint an established host's remote address, bypassing `remote_allow_list` enforcement - ([File: handshake_manager.go])

### Summary
The `lock`/`increaseLiquidity` bug is a class where a state-changing operation is gated by a security check on one code path but reachable through a second path that performs the same state change without the check. Nebula has the same shape: `handleHostRoaming` (the "primary" path for updating a `HostInfo`'s remote UDP address) enforces `lighthouse.remote_allow_list.AllowAll()` before calling `hostinfo.SetRemote()`, but the `ErrAlreadySeen` branch of `handleCheckAndCompleteError` reaches the exact same state-changing effect — updating the address nebula will subsequently send encrypted traffic to — through `SetRemoteIfPreferred`, which never consults the allow list at all.

### Finding Description
`Firewall.Drop` and `handleHostRoaming` treat `lighthouse.remote_allow_list` as the trust boundary for which underlay (UDP) addresses a `HostInfo`'s remote may be updated to: [1](#0-0) 

But when a responder receives a duplicate/retransmitted stage-1 handshake packet for an already-completed handshake, `CheckAndComplete` returns `ErrAlreadySeen`, and the handler updates the remote address via a different function that skips this check entirely: [2](#0-1) 

```go
case ErrAlreadySeen:
    if existing.SetRemoteIfPreferred(f.hostMap, via) {
        ...
    }
```

`SetRemoteIfPreferred` only compares against `preferredRanges` and unconditionally calls `SetRemote(via.UdpAddr)` if no remote is currently set, or if the new address falls in a preferred range — it performs no `remote_allow_list.AllowAll()` check, unlike `handleHostRoaming`: [3](#0-2) 

`via.UdpAddr` is simply the source address of the received UDP packet — UDP provides no source-address authentication, and the AEAD/Noise verification of the handshake payload does not bind the packet to the address it arrived from. `ErrAlreadySeen` fires purely on replay of a previously valid stage-1 packet (matched by `HandshakePacket[handshakePacketStage0]` content, not by source IP), so an attacker who can passively observe and replay a captured stage-1 packet from a spoofed UDP source can reach `SetRemoteIfPreferred` without holding any CA-signed certificate or completing any handshake of their own.

This is structurally identical to the reported bug: `lock()` enforces the fee, `increaseLiquidity()` doesn't, and both mutate the same underlying liquidity-position state. Here, `handleHostRoaming` enforces `remote_allow_list`, `SetRemoteIfPreferred` doesn't, and both mutate the same `HostInfo.remote` state that governs where the tunnel encrypts and sends traffic.

### Impact Explanation
If a `HostInfo` doesn't yet have a preferred-range remote set (`!currentRemote.IsValid()` — e.g. right after a handshake completes but before real traffic arrives) or the spoofed source address happens to fall in `preferredRanges` (e.g., the whole `0.0.0.0/0`/private-range configs many deployments use for LAN preference), replaying a captured stage-1 packet from a spoofed source lets an off-path attacker redirect where the interface writes encrypted UDP traffic for that tunnel, entirely bypassing the `remote_allow_list` restriction that operators rely on to keep addresses within trusted ranges. This is remote-state poisoning of trusted address material without any certificate.

### Likelihood Explanation
Requires only network-level UDP source-address spoofing plus prior capture/observation of one legitimate stage-1 packet between two peers (no cryptographic break, no CA-signed cert). The window is narrowest right after handshake completion before the remote address stabilizes via normal traffic, but `preferredRanges`-matching spoofed addresses can retrigger `SetRemoteIfPreferred`'s "roam" branch on every replay, making it a repeatable path, not a one-shot race.

### Recommendation
Route the `ErrAlreadySeen` remote-update through the same `remote_allow_list.AllowAll()` gate that `handleHostRoaming` enforces (e.g., have `SetRemoteIfPreferred` take the allow list as a dependency and check it, or have callers filter `via` before invoking it), so every path that can change `HostInfo.remote` is bound to the same trust check.

### Proof of Concept
1. Establish two peers `A` and `B`; capture `A`'s stage-1 handshake UDP packet toward `B` (`handshakePacketStage0`).
2. After the handshake completes and before other traffic is exchanged (so `currentRemote` on `B`'s side toward `A` is unset, or is set but the spoofed source falls in `preferredRanges`), replay the captured stage-1 packet toward `B` with a forged UDP source address `X` (outside the real path, e.g., attacker-controlled).
3. `B`'s `beginHandshake`/`CheckAndComplete` matches the existing hostinfo, returns `ErrAlreadySeen`, and `handleCheckAndCompleteError` calls `existing.SetRemoteIfPreferred(f.hostMap, via)` with `via.UdpAddr == X`, with no `remote_allow_list` check.
4. Observe `B`'s `HostInfo.remote` for `A` is now `X`; subsequent `sendNoMetrics` writes to `X` instead of `A`'s real address, even though `remote_allow_list` was configured to reject `X`.

**Note on confidence**: I was not able to fully trace every caller of `CheckAndComplete`/exact matching semantics for `ErrAlreadySeen` (e.g., whether it strictly requires byte-identical replay of `HandshakePacket[handshakePacketStage0]` or a looser index match) within the available tool budget, so the precise replay window and preconditions should be verified against `handshake_manager.go`'s `CheckAndComplete` implementation directly before treating this as confirmed exploitable in all configurations.

// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}
