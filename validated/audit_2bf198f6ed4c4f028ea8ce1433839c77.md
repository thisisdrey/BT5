Confirmed: `f.routines` spawns multiple concurrent `listenOut` goroutines (one per queue), each independently calling `readOutsidePackets` → eventually `ConnectionState.Decrypt`, and these can race against each other for packets belonging to the *same* `hostinfo`/tunnel since the underlying UDP socket dispatch (multi-queue) does not partition by tunnel/hostinfo identity in a way that prevents this.

### Title
Anti-Replay Window TOCTOU Allows One-Time Packet Replay Bypass - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` (and `VerifyRelay`) check the replay window, decrypt, and then update the replay window as three separate lock-scoped steps rather than a single atomic operation. A remote attacker who captures one ciphertext packet and re-injects a duplicate copy of it in quick succession can cause both copies to pass the `Check` before either has called `Update`, letting the duplicate packet be decrypted and delivered to the tun device a second time, effectively bypassing the anti-replay window by a race rather than a cryptographic weakness.

### Finding Description
`Decrypt` does:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }

out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
...

cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }
return out, nil
``` [1](#0-0) 

The `decryptLock` mutex is released between `Check` and the actual AEAD decrypt, and re-acquired only for `Update`. This mirrors the ERC-4626 "check → external state change → recompute" pattern from the reference finding: the protective invariant (`Bits` window marking a counter as seen) is only durably recorded at `Update` time, not at `Check` time, leaving a window where two concurrent invocations for the *same* `messageCounter` can both pass `Check` and both proceed to decrypt and deliver the same plaintext.

`VerifyRelay` has the identical structure for relay-forwarded frames:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [2](#0-1) 

This code path is reachable purely by packet injection — no valid CA-signed certificate is required by the attacker to *trigger* the race (the tunnel already exists between two legitimate parties; the attacker only needs to intercept/replay a UDP packet on the wire, which is explicitly the threat model this anti-replay mechanism defends against). The `Bits` sliding-window implementation itself is otherwise correct [3](#0-2) , and the project has previously hardened concurrent access to the window bitmap ("Lock replay window updates so concurrent readers can't corrupt it", per the changelog) [4](#0-3) , but that fix only protects the bitmap's internal consistency — it does not close the TOCTOU between `Check` and `Update` around the decrypt call.

Multiple UDP reader goroutines process inbound packets concurrently: `f.routines` queues each run `listenOut` → `readOutsidePackets` → `Decrypt` [5](#0-4) , and `readOutsidePackets` resolves the packet to a `HostInfo`/`ConnectionState` purely from the wire `RemoteIndex` before calling decrypt [6](#0-5) , so two duplicate UDP datagrams landing on different queues at roughly the same time will contend on the same `ConnectionState`.

### Impact Explanation
This allows a network-level attacker (who can capture and duplicate a single legitimate ciphertext) to cause the decrypted payload to be delivered to the tun interface (or forwarded, in the relay case) more than once, i.e., a limited traffic replay bypassing the intended one-packet-per-counter guarantee. It does not break confidentiality of the AEAD scheme (no nonce reuse occurs from the attacker's perspective; the same ciphertext is merely decrypted twice), but it is a genuine violation of the anti-replay guarantee the `Bits` window and its accompanying regression tests (`TestRelayReplayProtection`, `TestBitsDupeCounter`) are meant to provide [7](#0-6) .

### Likelihood Explanation
Exploitation requires precise timing to land two copies of the same UDP datagram on two different reader queues before the first `Update` call completes — a narrow but not implausible race window given `f.routines` > 1 multi-queue configurations and attacker-controlled packet duplication/timing on the underlay network. This is a race-condition bug rather than a deterministic bypass, so likelihood is moderate.

### Recommendation
Hold `decryptLock` across the full `Check → Decrypt → Update` sequence (or perform an atomic "reserve" of the counter in the window before decrypting, and roll it back only on decrypt failure) so that no second copy of the same `messageCounter` can pass `Check` until the first attempt's outcome (success or failure) has been durably recorded in the `Bits` window. Apply the same fix to both `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes with `listen.routines` ≥ 2 (multiple UDP reader queues).
2. Capture one legitimate data-plane UDP packet (`header.Message`) sent from A to B.
3. Immediately re-inject a duplicate of the captured packet, timed so it lands on a different reader queue than the original before B's `Update` call for that counter completes.
4. Observe (matching the intent of `TestRelayReplayProtection`'s methodology but targeting the direct decrypt path rather than the already-fixed relay-forward path) that both the original and the duplicate are decrypted and delivered to B's tun device, i.e., the payload is processed twice despite the replay window being designed to allow it only once.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()

		return ErrAlreadySeen
	}

		return err
	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (b *Bits) strictlyWithinWindow(i uint64) bool {
	// Handle the case where the window hasn't slid yet. This avoids u64 underflow.
	inWarmup := b.current < b.length
	if i < b.length && inWarmup {
		return true
	}

	// Next, if the packet is in-window, see if we've seen it before
	if i > b.current-b.length {
		return true
	}
	return false //not within window!
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
