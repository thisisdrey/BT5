### Title
Storage-quota accounting (`RepositorySize`/`RepositoryInfo`) trusts a manipulable on-disk snapshot instead of an authoritative accounting mechanism, allowing storage-quota bypass - (File: `internal/gitaly/service/repository/size.go`, `internal/gitaly/service/repository/repository_info.go`)

### Summary
`RepositorySize` and `RepositoryInfo` compute the "price" that GitLab uses to enforce a project's storage quota by simply walking the on-disk repository directory (`dirSizeInBytes`). Like the Malt spot-price bug, this value is a raw, momentarily-observable on-disk state rather than a stable, authoritative accounting value, and it can be skewed by mechanisms an ordinary user fully controls (object pool linkage/deduplication timing and Praefect's read distribution across replicas).

### Finding Description
`RepositorySize` returns `dirSizeInBytes(path, filter) / 1024` for the repository's own directory: [1](#0-0) 

`RepositoryInfo` computes the same walk-based size and, only if the repository has alternates (i.e., is linked to an object pool), adds the pool's own size: [2](#0-1) 

The test suite explicitly documents that linking a repository to an object pool and repacking causes the reported size to collapse from the "real" size to a near-zero value once the shared blob is deduplicated into the pool: [3](#0-2) 

Object pools are created and linked entirely through ordinary, unprivileged actions (forking a repository), documented in `doc/object_pools.md`: [4](#0-3) 

Gitaly's own design documentation acknowledges that this size value is inherently inconsistent and gameable: because `RepositorySize`/`RepositoryInfo` are read-only "accessor" RPCs, Praefect load-balances them across replicas that may or may not have completed deduplication/housekeeping yet, so the reported number swings wildly depending on which replica answers and on the timing of pool linkage relative to the read: [5](#0-4) 

Because the "price" (repository size used by GitLab Rails to decide whether a push should be rejected as over-quota) is derived from this raw, momentarily-observable, attacker-timeable on-disk walk instead of a stable ledger-style accounting mechanism, an ordinary user who forks a large repository (thereby creating/joining an object pool) can manipulate when and from which replica the size is read, causing the reported size to understate the true amount of storage they are consuming — the same "spot price vs TWAP" class of bug as the original finding, applied to a storage/fund-quota decision instead of a token-exit decision.

### Impact Explanation
An ordinary user who forks a large public project can exploit the timing between (a) pushing large data into their fork before pool linkage/repack has completed and (b) the pool-deduplication and cross-replica read-distribution windows described in `design_ha.md`, to obtain a `RepositorySize`/`RepositoryInfo` reading dramatically lower than their true on-disk consumption. Since GitLab enforces per-project storage quotas on top of these RPCs, this is a concrete storage-quota bypass ("fund extraction" analog): the user effectively obtains storage they have not paid for, and the inconsistency also undermines any admin/billing decision keyed off this number.

### Likelihood Explanation
Every step is reachable by an ordinary, unprivileged user: forking a repository (creating/joining an object pool) and pushing to that fork are completely standard, un-gated actions. The race window is influenced by push timing, housekeeping cadence, and (in HA/Praefect deployments) replica read distribution, all of which are attacker-observable and at least partially attacker-controllable (e.g., by pushing immediately after fork creation, before dedup/housekeeping completes, or by repeatedly querying until a stale/duplicated replica is hit).

### Recommendation
Do not use a raw, momentarily-observable on-disk directory walk as the authoritative value for quota/billing decisions. Instead:
- Compute repository size from an authoritative, replication-consistent source (e.g., only from the primary/up-to-date replica, or via a walk-based reachable-object calculation like `ObjectsSize` that is stable regardless of pool linkage/dedup state).
- Avoid load-balancing storage-accounting reads (`RepositorySize`/`RepositoryInfo`) across replicas that may be in different deduplication states; route them to a canonical, up-to-date replica.
- Consider decoupling per-project storage accounting from the live on-disk state entirely (e.g., track logical object contributions at push time) rather than deriving it from a value that changes based on unrelated repository/pool housekeeping timing.

### Proof of Concept
1. As an ordinary user, fork a large public repository `R`, creating/joining object pool `P` (per `doc/object_pools.md`).
2. Immediately push a large unique blob to the fork before the object pool's repack/dedup housekeeping runs.
3. Query `RepositorySize`/`RepositoryInfo` for the fork. In an HA/Praefect deployment, repeated queries can be load-balanced to different replicas that are at different points in the replication/dedup pipeline (`doc/design_ha.md` lines 163-176), yielding inconsistent and, at times, artificially low size readings relative to true consumption.
4. If GitLab's storage-quota enforcement relies on this value, the user can continue pushing data while the reported size understates real usage, defeating the quota check — analogous to using a manipulable "spot price" instead of a stable value for a fund-affecting decision.

```go
// RepositorySize returns the size of the specified repository in kibibytes. By default, this
// calculation is performed using the disk usage command.
func (s *server) RepositorySize(ctx context.Context, in *gitalypb.RepositorySizeRequest) (*gitalypb.RepositorySizeResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	path, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	filter := snapshot.NewDefaultFilter(ctx)
	sizeInBytes, err := dirSizeInBytes(path, filter)
	if err != nil {
		return nil, fmt.Errorf("calculating directory size: %w", err)
	}

	return &gitalypb.RepositorySizeResponse{Size: sizeInBytes / 1024}, nil
}
```

```markdown
# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.

## Lifetime of Object Pools

The lifetime of object pools is maintained via the
[ObjectPoolService](../proto/objectpool.proto), which provides various RPCs to
create and delete object pools as well as to add members to or remove members
from the pool.

An object pool is typically created from an existing repository by doing a
[`--local`](https://git-scm.com/docs/git-clone#Documentation/git-clone.txt---local)
clone of the repository, which bypasses the normal transport mechanisms and
instead simply performs a copy of the references and objects.
```

```markdown
##### Replication Process Concerns

The replication process has been tested in production and works well for small
repositories. For larger repositories, such as `www-gitlab-com` and
`gitlab-org/gitlab`, it starts to show signs of stress.

The snapshot process is very resource intensive for fork operations. When
snapshotting a large repo, you end up with n-1 (n == replica count) copies of
the repository being compressed and extracted to secondary replicas.

Adding to this stress is the constraint of storage limitations for GitLab.com
users. The GitLab handbook (`www-gitlab-com`) is now larger than the storage
quota for free users. Until a secondary replica performs housekeeping, it
will consume the storage quota of the extracted snapshot. If Praefect instead
used fast forking (<https://gitlab.com/gitlab-org/gitlab/-/issues/24523>), this
would not be an issue since forked copies would only use a small amount of
additional data.

To complicate matters even more, read distribution can contribute to
inconsistent behavior when attempting to determine how much storage a user has
consumed. Since stating a repository's disk space is a read-only operation, it
is load balanced across all up to date replicas of the repository. If any of
those replicas still has the duplicated fork data, this will lead to a much
higher disk usage being reported than a replica that has been deduplicated.
```
