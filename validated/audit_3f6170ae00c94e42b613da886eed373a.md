### Title
Active-permission holder scoped only for `AccountPermissionUpdateContract` can rewrite the entire account permission structure and self-escalate to full account control - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
Similar to CVE-2019-11270 — where a Cloud Foundry UAA client holding only the `clients.write` scope could create new clients with arbitrary scopes exceeding its own authority — java-tron's multisig permission system allows an account key that was delegated only the narrow `AccountPermissionUpdateContract` operation bit in its Active permission to submit an `AccountPermissionUpdateContract` transaction that rewrites the account's Owner, Witness, and all Active permissions with any scope, key set, and threshold up to the full global set of contract types. The actuator never checks the new permission set against the authority of the permission that authorized the update.

### Finding Description
Any transaction (including `AccountPermissionUpdateContract`) can be authorized by a non-zero `permission_id`, i.e. by an Active permission, as long as that permission's `operations` bitmap has the bit set for the contract type being submitted (bit 46 = `AccountPermissionUpdateContract`): [1](#0-0) [2](#0-1) 

This means an account owner can (intentionally or by social-engineered/leaked-key scenario) delegate a low-trust key an Active permission whose operations bitmap contains *only* the `AccountPermissionUpdateContract` bit, believing that key can merely "manage permissions" in some limited administrative capacity.

However, `AccountPermissionUpdateActuator.validate()`/`checkPermission()` places no restriction tying the *content* of the newly submitted Owner/Witness/Active permissions to the scope or weight of the permission that signed the transaction. It only validates the new permission structurally (key count, threshold, name length, address validity) and validates the `operations` bitmap of any new Active permission against the chain-wide `dynamicStore.getAvailableContractType()` — a global mask of all currently enabled contract types on the network, not the caller's own permission scope: [3](#0-2) [4](#0-3) 

The `execute()` method then unconditionally applies the new Owner/Witness/Active permission set to the account with no additional authority check: [5](#0-4) 

Consequently, a key holder whose only granted authority was "manage permissions" (bit 46) can craft and submit a transaction that sets:
- A new Owner permission containing its own key with full weight/threshold, granting itself unconditional account control, and/or
- A new Active permission with the `operations` bitmap set to cover every contract type currently allowed on chain (transfers, freezes, asset issuance, exchange operations, smart contract creation, etc.) — scopes it never itself possessed.

This is a direct structural analog to the CVE: a narrowly-scoped credential (`clients.write` / the `AccountPermissionUpdateContract` operation bit) is used to mint a broader credential (arbitrary client scopes / arbitrary account permission operations) that the holder does not itself possess, because the validation logic checks against a global allow-list rather than against the actual authority of the requester.

### Impact Explanation
Any multisig account design that intentionally isolates a "permission administrator" key with the sole authorized operation `AccountPermissionUpdateContract` (a documented, legitimate multisig pattern for e.g. delegating permission housekeeping to an ops key without granting fund-moving rights) is completely undermined: that single key can grant itself (or collude to grant an attacker-controlled address) unrestricted Owner-level control of the account, leading to outright theft of all TRX/TRC10/TRC20 balances, permanent loss of legitimate owner control, and defeats the entire threat model of TRON's threshold multisig permission system. This satisfies the "concrete unauthorized account operation / theft of funds" bar.

### Likelihood Explanation
High. This requires only a single signed `AccountPermissionUpdateContract` transaction from an account that has previously delegated Active permission scoped to `AccountPermissionUpdateContract` (id 46) to a sub-key — a standard, encouraged multisig delegation pattern (e.g., separating "permission management" duty from "fund management" duty). No special network conditions, cooperation from validators, or timing is required; it is reachable purely from the actuator's `validate()`/`execute()` path invoked by any broadcast transaction.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`/`validate()`, when the transaction's `permission_id` is non-zero (i.e., authorized by a non-Owner Active permission), restrict the operations/keys/threshold that can be granted in the new Owner/Witness/Active permissions such that they cannot exceed the operations bitmap and weight authority of the signing permission itself (mirroring UAA's post-fix behavior of clamping new scopes to the creator's own scope set). At minimum, require that any account-permission-structure change (Owner permission replacement in particular) be authorized only by the Owner permission (`permission_id == 0`), never by a lesser Active permission.

### Proof of Concept
1. Account `A` sets up multisig: Owner permission held by `A`'s master key; an Active permission (id=2) is delegated to key `K` with `operations` bitmap containing only bit 46 (`AccountPermissionUpdateContract`) — intended to let `K` "manage permission housekeeping" only.
2. `K` builds an `AccountPermissionUpdateContract` for account `A`:
   - New `owner` permission: key = `K`'s own address, weight 1, threshold 1 (full control).
   - New `active` permission: `operations` bitmap = all bits set per `dynamicStore.getAvailableContractType()` (transfers, freezes, asset issue, etc.), key = `K`, weight/threshold trivially satisfiable.
3. `K` signs this transaction using `permission_id=2` (its Active permission). `TransactionCapsule.checkPermission` passes because bit 46 is set in `K`'s Active permission operations.
4. `AccountPermissionUpdateActuator.validate()` accepts the new Owner/Active permission because `checkPermission()` only validates against the global `getAvailableContractType()` mask, not against `K`'s own scope.
5. `execute()` calls `account.updatePermissions(...)`, overwriting `A`'s Owner permission to `K`.
6. `K` now fully controls account `A`, including transferring out all its funds — despite having originally been granted only the "manage account permissions" operation. [6](#0-5)

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
