## Title
Un-hardened `long` multiplication in `DelegateResourceActuator.validate()` bypasses resource-delegation solvency check - (File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java)

### Summary
Unlike the systematically "hardened" arithmetic used throughout the resource-accounting subsystem (`BandwidthProcessor`, `EnergyProcessor`, `RepositoryImpl`, `ResourceProcessor`), the validation logic in `DelegateResourceActuator.validate()` still performs raw `long * long` multiplication before an implicit narrowing cast, exactly the CWE-190 signed-integer-overflow pattern flagged in the iccDEV `parse3DTable()` advisory (CVE-2026-27691). This is reachable directly by any unprivileged account broadcasting a `DelegateResourceContract`.

### Finding Description
`DelegateResourceActuator.validate()` recomputes the account's current bandwidth/energy usage inline instead of delegating to the hardened processor helpers: [1](#0-0) [2](#0-1) 

```java
long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
    (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));
...
long energyUsage = (long) (ownerCapsule.getEnergyUsage() * TRX_PRECISION * ((double)
    (dynamicStore.getTotalEnergyWeight()) / dynamicStore.getTotalEnergyCurrentLimit()));
```

`accountNetUsage`/`ownerCapsule.getEnergyUsage()` is a `long` and `TRX_PRECISION` is `1_000_000` [3](#0-2) . `accountNetUsage * TRX_PRECISION` is evaluated as ordinary two's-complement `long` arithmetic with no overflow check, before being multiplied by the `double` weight ratio and cast back to `long`. If `accountNetUsage` (or `getEnergyUsage()`) is large enough (> ~9.2×10^12, i.e. well within the range representable and reachable through repeated resource usage/estimation, particularly via `TransactionUtil.estimateConsumeBandWidthSize`), the intermediate product silently wraps, producing an arbitrarily small or negative `netUsage`/`energyUsage` value.

This directly parallels the reported bug class: a raw multiplication of user/attacker-influenced magnitudes without overflow protection, unlike every sibling computation in the codebase, which was explicitly hardened for exactly this reason. Compare the equivalent, correctly-hardened logic in `BandwidthProcessor`/`EnergyProcessor`/`ResourceProcessor`/`RepositoryImpl`, all of which route this same formula through `BigInteger` and `multiplyExact`/`addExact` guarded by `allowHardenResourceCalculation()`: [4](#0-3) [5](#0-4) 

`DelegateResourceActuator.validate()` never calls into these hardened helpers for its own usage estimate — it re-implements the formula ad hoc with plain `long`/`double` arithmetic, so it inherits none of the overflow protection added elsewhere in the codebase.

### Impact Explanation
This computed `netUsage`/`energyUsage` feeds directly into the delegation solvency check via `getV2NetUsage`/`getV2EnergyUsage` (`org.tron.core.vm.utils.FreezeV2Util`): [6](#0-5) [7](#0-6) 

```java
long v2NetUsage = getV2NetUsage(ownerCapsule, netUsage, this.disableJavaLangMath());
if (ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance) {
  throw new ContractValidateException(...);
}
```

If the wrapped value produces an artificially small/negative `v2NetUsage`/`v2EnergyUsage`, the "available balance" appears larger than it actually is, allowing `DelegateResourceContract` to pass validation and delegate more BANDWIDTH/ENERGY (`ownerCapsule.addDelegatedFrozenV2BalanceForBandwidth`/`...ForEnergy` in `execute()`) than the account actually has frozen and available. This is an unbacked/overstated resource allocation — the receiver ends up with delegated resource credits not actually backed by the owner's frozen TRX, which is the resource-accounting equivalent of theft/unbacked balance creation on the chain's economic ledger (bandwidth/energy ultimately translate to economic value since they substitute for TRX fee burning).

### Likelihood Explanation
Reaching the overflow requires the account's bandwidth/energy "usage" counter to be large enough that `usage * 1_000_000` wraps a signed 64-bit long (i.e., usage on the order of `Long.MAX_VALUE / 1_000_000 ≈ 9.22 × 10^12`). Ordinary bandwidth/energy usage values from real accounts are far smaller (bandwidth usage is bytes, energy usage is derived from VM gas), so triggering this in practice likely requires accumulating an account's `NetUsage`/`EnergyUsage` counter to an extreme value or another interacting bug that inflates these fields; the codebase's own test suite for the equivalent hardened formulas (`CalculateGlobalLimitHardenTest`, `RepositoryImplHardenTest`) specifically demonstrates that these exact multiplication shapes do overflow at realistic-looking large values and that the fix elsewhere was to harden with `BigInteger`. I could not fully verify within available context whether `NetUsage`/`EnergyUsage` on an `AccountCapsule` can organically reach the required magnitude through the reachable public APIs (this would require deeper analysis of `increase()`/`recovery()` bounds in `ResourceProcessor`, which I did not have iterations left to trace exhaustively).

### Recommendation
Route `DelegateResourceActuator.validate()`'s net/energy usage computation through the same hardened helper already used by `ResourceProcessor`/`RepositoryImpl` (i.e., call `BigInteger`-based, `divideCeilExact`/`multiplyExact`-guarded arithmetic, or reuse `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`-style hardened math) instead of the raw `long * long` multiplication combined with a `double` cast, and gate it behind (or unconditionally use, given precedent) `allowHardenResourceCalculation()` for consistency with the rest of the resource subsystem.

### Proof of Concept
Not independently reproducible from the indexed context alone: doing so would require constructing an account whose `NetUsage`/`EnergyUsage` field reaches ~9.2×10^12, then broadcasting a `DelegateResourceContract` and observing that the balance-sufficiency check in `DelegateResourceActuator.validate()` (lines 162-169 / 176-183) is bypassed due to the wrapped `netUsage`/`energyUsage` value, allowing delegation of resources exceeding the actual frozen balance. Full confirmation requires running the actuator against a crafted `AccountCapsule` state and asserting the delegated amount exceeds `getFrozenV2BalanceForBandwidth()`/`getFrozenV2BalanceForEnergy()`, which I could not execute given the read-only, ask-only scope of this analysis.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
