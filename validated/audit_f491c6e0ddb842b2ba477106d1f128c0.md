### Title
`accrue()` treasury-lp fee minting can underflow and permanently DOS all vault deposits, redeems, and market withdrawals - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The hats-finance report describes a withdraw flow that reverts because a downstream "protocol interaction" step can fail, causing complete denial-of-service on withdrawals. The closest reachable analog in this codebase is the `accrue()` function that every vault (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) runs at the top of `deposit`, `redeem`, `system-borrow`, and `system-repay`. `accrue()` computes a treasury fee-share mint using `(- (total-assets-preview) reserve-inc)` as a divisor with no floor/guard, which can underflow/hit zero and cause every subsequent vault operation — including the withdraw path `market.clar::collateral-remove-redeem` → `vault-redeem` → vault `redeem` — to permanently revert.

### Finding Description
Every vault's `redeem` (and `deposit`, `system-borrow`, `system-repay`) begins with `(u (try! (accrue)))`: [1](#0-0) 

Inside `accrue()`, the treasury fee-share to mint is computed as: [2](#0-1) 

```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```

`reserve-inc` is a fraction (`fee-reserve` bps) of newly-accrued interest (`debt-delta`), while the denominator is `total-assets-preview` (current pooled assets including accrued interest) minus that same `reserve-inc`. There is no assertion that `total-assets-preview >= reserve-inc`, and no floor guarding the subtraction. If the vault's asset base is small relative to freshly accrued interest — e.g. after most liquidity has already been withdrawn/borrowed out and only a thin residual `assets` balance remains, or after a long-untouched period causes a large `debt-delta` jump relative to a shrunk `total-assets-preview` — the subtraction underflows, which panics/reverts the `accrue()` call. Because `accrue()` is invoked unconditionally at the start of every state-mutating vault entrypoint, this single arithmetic path can brick `deposit`, `redeem` (and therefore the market's withdraw composite `collateral-remove-redeem`), `system-borrow`, and `system-repay` for that vault — for every user, not just one withdrawer — until indexes are reset by some other means (there is none exposed publicly).

This mirrors the reported bug class exactly: an internal "protocol interaction" computation embedded in the withdraw call chain can revert unconditionally, turning a single bad state transition into full DOS of the withdraw path (and here, of the entire vault).

### Impact Explanation
Once triggered, this freezes all pending withdrawals (and deposits/borrows/repays) for the affected vault. Users' zTokens/collateral remain locked because `redeem`/`collateral-remove-redeem` cannot execute past `accrue()`. This is a temporary freezing-of-funds impact (In-scope: "temporary freezing of funds"), since no external administrative action is available in the vault or market contracts to bypass or repair the corrupted index state.

### Likelihood Explanation
This requires the vault to reach a state where accrued interest since the last update (`debt-delta`) is large relative to `total-assets-preview`. This can plausibly occur after: (a) large amount of the vault's asset base being withdrawn via `redeem`/`collateral-remove-redeem`, shrinking `assets` and thus `total-assets-preview`, while `principal-scaled` debt (and thus `debt-delta`) remains sizeable, or (b) extended periods without a call to `accrue()`, letting the index (and hence `debt-delta`) grow disproportionately to a since-shrunk asset base. Both are reachable purely through ordinary, unprivileged user calls (`redeem`, `borrow`, `repay`, `collateral-remove-redeem`) plus the passage of time, without any DAO or privileged action.

### Recommendation
Guard the `treasury-lp` computation in `accrue()` (all six vaults) so the subtraction cannot underflow, e.g. clamp with `(if (> (total-assets-preview) reserve-inc) (- (total-assets-preview) reserve-inc) u1)`, or skip minting `treasury-lp` entirely and log/queue the shortfall when `reserve-inc >= total-assets-preview`. Add invariant tests exercising heavy sequential `redeem`/`borrow` draining followed by long-latency `accrue()` calls to ensure the fee-mint path can never revert.

### Proof of Concept
1. Vault (e.g. `v0-vault-usdc.clar`) starts with modest `assets`, `principal-scaled` debt, and non-zero `fee-reserve`.
2. Multiple users call `system-borrow` to raise `total-borrowed`/`principal-scaled` significantly relative to `assets`.
3. Users call `redeem` (directly or via `market.clar::collateral-remove-redeem`) to withdraw most of the remaining `assets`, shrinking `total-assets-preview` while scaled debt (and therefore future `debt-delta` on accrual) stays large.
4. No further `accrue()`-triggering call happens for an extended period, letting `next-index`/`debt-delta` grow.
5. Any user calls `redeem`/`deposit`/`borrow`/`repay` (or `collateral-remove-redeem` via `market.clar`), triggering `accrue()`: `reserve-inc` computed off the now-large `debt-delta` can exceed `total-assets-preview`, causing `(- (total-assets-preview) reserve-inc)` to underflow and the transaction (and every subsequent call to that vault) to revert, denying withdrawals to all remaining depositors.
