### Title
Unbounded attacker-controlled array-length allocation in TVM signature precompiles `ValidateMultiSign`/`BatchValidateSign` - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` in `PrecompiledContracts.java` size internal `byte[][]` buffers directly from an attacker-supplied 32-byte word taken from precompile call-data, with no upper bound unless the `allowTvmSelfdestructRestriction` hard-fork flag is active. This mirrors the Bento4 `AP4_StscAtom` root cause: an untrusted length field read from input data is used to size a buffer/array before any validation, allowing a caller to trigger huge or negative allocations.

### Finding Description
`extractBytes32Array` reads `len` straight from `words[offset].intValueSafe()` and immediately allocates `new byte[len][]`, with no bound at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` have the same pattern, only guarding against `offset` being past the end of `words`, not against `len` itself: [2](#0-1) 

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`. The `MAX_SIZE` bound (5 / 16) is only checked when `VMConfig.allowTvmSelfdestructRestriction()` is true — a dynamic, committee-activated chain parameter that is `0`/disabled by default at genesis on any new java-tron network until the corresponding proposal is passed: [3](#0-2) [4](#0-3) 

When the flag is not enabled, `extractSigArray`/`extractBytesArray`/`extractBytes32Array` are reached with `len` fully attacker-controlled (up to `Integer.MAX_VALUE` via `intValueSafe()`), so `new byte[len][]` can attempt to allocate a huge array (each element itself another array once the loop runs), or `new byte[len]` with a length overflowing available heap. This is directly reachable by any unprivileged account issuing a `TriggerSmartContract` that performs a `CALL`/`STATICCALL` to precompile address `0x9` (`batchValidateSign`) or `0xa` (`validateMultiSign`), which is dispatched via `Program.callToPrecompiledAddress`: [5](#0-4) 

### Impact Explanation
A crafted call-data word forces a massive/negative array allocation inside precompile execution. While `VMActuator.finalization`/`execute` wraps VM execution in a `catch (Throwable e)` that will typically absorb an `OutOfMemoryError` for a single transaction (limiting it to a failed tx rather than an immediate crash), the underlying allocation attempt still stresses the JVM heap during block application. Because the length field is entirely attacker-controlled with no cap, repeated or crafted calls (e.g., embedded in block-included transactions) can be used to force large transient allocations during Manager block application, degrading node availability and potentially triggering `OutOfMemoryError`s in concurrent unrelated threads (e.g., other in-flight transaction execution, RPC handling), a resource-exhaustion/node-instability effect. This is a medium-severity finding: it requires the `allowTvmSelfdestructRestriction` chain parameter to be inactive (true for any newly bootstrapped java-tron network before that proposal is passed) to be exploitable without the length cap.

### Likelihood Explanation
Any unprivileged account can broadcast a `TriggerSmartContract` transaction that performs a `CALL` to the fixed precompile addresses `0x...09` / `0x...0a` with crafted call-data — no special permissions or contract deployment beyond a trivial calling contract are required, and TVM Solidity 0.5.9 features gating these precompiles (`allowTvmSolidity059`) are widely enabled. The only gating condition is that `allowTvmSelfdestructRestriction` not yet be active on the target chain, which is true by default for freshly deployed/private/sidechain java-tron networks (a common deployment scenario for this codebase) until the corresponding committee proposal is passed.

### Recommendation
Add an explicit upper bound check on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating (`byte[len][]`/`byte[len]`), independent of the `allowTvmSelfdestructRestriction` flag, e.g. reject if `len < 0 || len > MAX_SIZE` (or bound by `words.length`) prior to any allocation, matching the fix already gated behind the hard-fork flag but applying it unconditionally.

### Proof of Concept
1. Deploy a trivial contract that performs `staticcall`/`call` to precompile address `0x000000000000000000000000000000000000000a` (`validateMultiSign`) or `0x...09` (`batchValidateSign`).
2. Craft call-data such that the word at the offset used for signature-array length (`words[3]` for `validateMultiSign`, `words[1]`/`words[2]` for `batchValidateSign`) decodes via `intValueSafe()` to a very large value (e.g., close to `Integer.MAX_VALUE`).
3. On a java-tron network/testnet where `allowTvmSelfdestructRestriction` has not yet been activated by committee proposal, broadcast the `TriggerSmartContract` transaction; `extractBytesArray`/`extractBytes32Array`/`extractSigArray` attempts `new byte[len][]` with the attacker-chosen `len`, causing a large/failed allocation inside TVM execution during transaction/block processing.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
