### Title
Cross-chain replay of `ValidateMultiSign`/`BatchValidateSign` precompile signatures due to missing chain-binding in the signed hash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiles `ValidateMultiSign` (address `0x66`) and `BatchValidateSign` compute or accept a signing hash that is never bound to the chain the transaction executes on (no `block.chainid`, genesis hash, or verifying-contract salt is mixed in). Any smart contract that relies on these precompiles to gate privileged operations (multisig-style authorization) can have valid signatures collected on one TRON-compatible network (mainnet, a testnet, or a fork/side-chain sharing the same account address space) replayed verbatim on another network where the identical contract/account state exists, exactly mirroring the `Forwarder._verifySig` cross-chain replay finding.

### Finding Description
`ValidateMultiSign.execute()` builds the digest purely from data supplied in `calldata` and never touches chain identity: [1](#0-0) 

`combine = address || permissionId || data` and `hash = Sha256Hash.hash(combine)`. `address`, `permissionId`, and `data` are all attacker-supplied words taken directly from the precompile's input; the resulting hash is then checked against the on-chain `Permission` weight of `address`: [2](#0-1) 

`BatchValidateSign` is even more direct: the hash to verify is taken verbatim from `words[0]`, with zero chain- or contract-binding at all: [3](#0-2) 

Both precompiles reuse the general-purpose `recoverAddrBySign` routine that simply ECDSA-recovers whatever hash it is given: [4](#0-3) 

This is structurally identical to the reported `Forwarder._verifySig` bug: the digest that a contract treats as an authenticated, chain-specific authorization is actually computed from data that carries no unique-per-chain salt. TRON account addresses are derived purely from the secp256k1 public key and are therefore *identical* across mainnet, Nile/Shasta testnets, and any java-tron-derived fork/side-chain — a stronger version of the precondition the C4 judge required ("deployment at the same address across multiple chains") to raise severity to High in the original report, since on TRON that precondition is guaranteed by construction rather than dependent on `CREATE2`.

### Impact Explanation
Any TVM contract (custody/vault, multisig wallet, gasless-relay/meta-transaction forwarder, exchange order-signing helper, etc.) that uses `ValidateMultiSign`/`BatchValidateSign` to authorize a state-changing action based on an off-chain-collected signature is exposed to cross-chain signature replay if the same contract bytecode/account state is deployed or exists on more than one TRON-compatible network. An attacker who captures a valid authorization signature (e.g., approving a withdrawal, permission-gated transfer, or order placement) on one network can resubmit it unmodified on another network sharing the same account/permission state, resulting in unauthorized account operations or theft of funds on the second network.

### Likelihood Explanation
Exploitation requires only a normal, unprivileged contract-deployer or API client:
1. Deploy (or find already-deployed) identical contract logic using `ValidateMultiSign`/`BatchValidateSign` for authorization on two TRON-compatible networks (e.g., mainnet + Nile/Shasta testnet, or a private/side chain fork of java-tron).
2. Capture any valid signature produced for use on network A.
3. Replay the identical signature/calldata against the same precompile call on network B.

Because TRON addresses are chain-independent by design (unlike EVM chains, no `CREATE2`/deterministic-deployment trick is even needed), the precondition the original C4 report needed to escalate severity to High is trivially satisfied on TRON. This makes the class of bug broadly and reliably reachable by anyone building or interacting with multisig/authorization contracts on TVM.

### Recommendation
Bind the signed digest computed inside `ValidateMultiSign` to chain- and contract-specific context before recovering signer addresses — e.g., include `block.chainid` (already exposed via the `CHAINID` opcode) and/or the calling contract address in the `combine` byte sequence, or require callers to pass and have the precompile enforce a chain-id field that must match the executing network. For `BatchValidateSign`, since the hash is fully caller-defined, document explicitly (and ideally enforce) that consuming contracts must themselves mix `block.chainid` and the verifying contract address into any hash presented to this precompile, to avoid downstream contracts unknowingly building replayable authorization schemes.

### Proof of Concept
1. Deploy a custody contract `V` on TRON mainnet and again (same bytecode/state, same owner account `A`) on Nile testnet; `V` authorizes withdrawals by calling `ValidateMultiSign(A, permissionId, dataHash, sigs)`.
2. Owner signs `sigs` for `dataHash = sha256(withdrawal_details)` against permission `A` to authorize a withdrawal on mainnet.
3. Attacker observes `sigs`/`dataHash` from the mainnet transaction and calls the identical `ValidateMultiSign` sequence against `V` deployed on Nile testnet.
4. Because `combine = address || permissionId || data` never includes any chain-specific salt (as shown in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1058-1065`), the precompile returns the same "authorized" result (`DataWord.ONE`) on Nile as it did on mainnet, letting the attacker trigger the withdrawal logic on the second chain without a fresh authorization from the account owner.
