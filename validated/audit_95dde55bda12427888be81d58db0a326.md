### Title
Integer Overflow in Exchange Balance Arithmetic Bypasses Balance-Limit Validation When `allowHardenExchangeCalculation` Is Disabled - (File: `actuator/src/main/java/org/tron/core/actuator/AbstractExchangeActuator.java`)

### Summary
The CVE-2018-10194 bug class is "arithmetic calculation does not prevent overflow, allowing corrupted state / crash." The same root-cause pattern exists in java-tron's Bancor-style exchange actuators: `addExact`/`subtractExact` in `AbstractExchangeActuator` only perform overflow-checked math when the on-chain `allowHardenExchangeCalculation` governance flag is enabled; otherwise they silently fall back to raw `+`/`-` that can wrap around on overflow. [1](#0-0) 

### Finding Description
`AbstractExchangeActuator.addExact`/`subtractExact` are used throughout `ExchangeInjectActuator` and `ExchangeWithdrawActuator` to update the pool's `firstTokenBalance`/`secondTokenBalance` and the caller's account balance. [1](#0-0) 

In `ExchangeInjectActuator.doValidate`, the injected quantity and the calculated "another token" quantity are added to the pool's current balances using this same conditionally-checked `addExact`, and the *result* of that addition is what's compared against the configured `getExchangeBalanceLimit()`: [2](#0-1) 

When `allowHardenExchangeCalculation` is not active, `addExact` degrades to plain `long` addition, meaning `firstTokenBalance + tokenQuant` can silently overflow to a negative or small value. Since the subsequent limit check is `newTokenBalance > balanceLimit`, a wrapped (now negative or small) `newTokenBalance` will pass validation even though the true (mathematically correct) balance would have exceeded `balanceLimit`, and the actuator will proceed to persist the corrupted, wrapped balance into `ExchangeCapsule` in `execute()`: [3](#0-2) 

This mirrors the Ghostscript bug class precisely: an arithmetic routine intended to prevent overflow in a positioning/quantity calculation is not actually enforced under normal conditions, letting attacker-supplied input push internal state past its intended bounds.

### Impact Explanation
A corrupted (wrapped) `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule` breaks the invariant that pool balances reflect real backing assets. Because subsequent `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` operations trust these stored balances for their own Bancor-formula math (also gated by the same opt-in overflow protection, see `ExchangeCapsule.transaction`), a wrapped balance can be leveraged to withdraw disproportionate amounts of the paired asset relative to what was actually deposited — i.e., unbacked balance creation / theft of exchange pool funds. This satisfies the "unbacked balance" / "theft of funds" impact bar. [4](#0-3) 

### Likelihood Explanation
This is reachable directly by any account that created an exchange pool (`creatorAddress` check in `doValidate`) simply by repeatedly injecting large `tokenQuant` values via a normal `ExchangeInjectContract` transaction — no special privilege beyond being the pool creator is required, and pool creation itself is permissionless via `ExchangeCreateActuator`. The only gating factor is whether `allowHardenExchangeCalculation` is enabled on the running chain; the existence of the flag itself, plus test names like `hardenedAddExactOverflowThrows`, indicate this is a retrofitted mitigation that is off by default/until a committee proposal activates it, exactly like Ghostscript's overflow fix that had to be separately backported. [5](#0-4) [6](#0-5) 

### Recommendation
Make the overflow-checked arithmetic (`StrictMathWrapper.addExact`/`subtractExact`) unconditional in `AbstractExchangeActuator` rather than gating it behind `allowHardenExchangeCalculation`, so `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeCapsule.transaction` always throw on overflow instead of silently wrapping and comparing a corrupted value against `balanceLimit`.

### Proof of Concept
1. Confirm on the target network that `allowHardenExchangeCalculation` is not enabled (default/pre-proposal state).
2. As the creator of an `ExchangeInjectContract`-eligible pool, craft a series of `ExchangeInjectContract` transactions with `quant` values chosen so that `firstTokenBalance + tokenQuant` (plain `long` addition) overflows `Long.MAX_VALUE`, wrapping to a small/negative number that passes the `newTokenBalance > balanceLimit` check in `ExchangeInjectActuator.doValidate` (lines 219, 234).
3. The corrupted balance is persisted via `Commons.putExchangeCapsule` in `execute()` (line 102).
4. Follow up with `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` calls that use the corrupted pool balance in the Bancor formula (`ExchangeCapsule.transaction`) to extract more of the paired asset than was ever deposited.

Note: I was unable to fully confirm the exact default (on-chain) value of the `allowHardenExchangeCalculation` proposal parameter in `DynamicPropertiesStore.java` before running out of tool iterations — this should be verified in a live/staging java-tron network to confirm the flag is disabled by default before treating this as fully exploitable in production.
