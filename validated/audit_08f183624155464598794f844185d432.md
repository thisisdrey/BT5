### Title
Ed25519 signature malleability lets attackers bypass the cheap sigverify-stage packet dedup filter, forcing repeated expensive signature verification of semantically identical transactions - ([File: perf/src/sigverify.rs])

### Summary
The transaction-processing sigverify path (`perf/src/sigverify.rs::verify_packet`) verifies ed25519 signatures using the plain, non-strict `Signature::verify` call rather than `verify_strict`, and the packet-level `Deduper` used ahead of it (`perf/src/deduper.rs`, wired up in `core/src/sigverify.rs`/`core/src/sigverify_stage.rs`) deduplicates on the raw packet bytes (which include the signature). Because ed25519 signatures verified with the non-strict check are malleable — an attacker can derive additional valid `(R, S)` byte encodings for the same message/pubkey without the private key — a single legitimately-signed transaction can be "reflected" into many byte-distinct-but-semantically-identical packets that all pass sigverify while evading the byte-hash Deduper.

### Finding Description
`perf/src/sigverify.rs::verify_packet` verifies the transaction signature with a plain call: [1](#0-0) 

This is the non-strict `Signature::verify`, as opposed to the `verify_strict` used explicitly for the ed25519 precompile program, which the codebase's own test suite documents as necessary specifically to reject malleable signatures: [2](#0-1) [3](#0-2) 

The feature that hardens the precompile (`ed25519_precompile_verify_strict`, SIMD-0152) only covers the `Ed25519SigVerify111...` precompile program, not the base transaction/message signature check performed by `perf/src/sigverify.rs` or `entry/src/entry.rs::batch_verify`: [4](#0-3) [5](#0-4) 

Ahead of that (non-strict) signature check, incoming packets are first passed through a `Deduper` that hashes the raw packet bytes to cheaply discard duplicates before the CPU-expensive ed25519 verification runs: [6](#0-5) [7](#0-6) 

Because the dedup key is the packet's raw bytes (which embed the 64-byte signature), and because the non-strict verify accepts multiple distinct valid signature encodings for the same signed message, an attacker who possesses one valid signature for a transaction can mutate the signature bytes into other still-valid encodings. Each mutated packet:
- Hashes to a different value in the `Deduper`, so it is *not* recognized as a duplicate and is *not* cheaply dropped, and
- Passes the non-strict `verify_packet` check, so it proceeds to full, CPU-expensive signature verification and is forwarded into banking stage.

This defeats the purpose of the pre-sigverify Deduper, which exists specifically to protect the expensive verification step from being repeatedly re-run against the same payload.

### Impact Explanation
The packet dedup step in the sigverify pipeline is a cost-control/QoS mechanism: it is explicitly placed before signature verification so that flooding the same transaction repeatedly is cheap to reject via a hash-bitmap lookup rather than by running full ed25519 verification. Signature malleability breaks the assumption that "same payload ⇒ same hash ⇒ dedup catches it," allowing an attacker to force the node to spend full ed25519-verification CPU cycles on what is, semantically, the exact same transaction repeated arbitrarily many times, each with a differently-encoded (but still valid) signature. This is a QoS-evasion / underpriced-work vector on the unprivileged, unauthenticated TPU/QUIC ingestion path: any client submitting a single valid transaction can amplify the number of distinct-looking packets a validator must fully signature-verify, without needing any additional real fee-bearing transactions or replay of executed state (the bank-level `status_cache` still keys off `message_hash`, so the transaction itself would still only execute once, and this does not bypass execution/replay protection at the runtime level — it specifically evades the cheap sigverify-stage dedup/QoS gate).

### Likelihood Explanation
Deriving an additional valid ed25519 signature encoding for a known message/signature pair under non-strict verification is a well-documented, purely computational manipulation (no private key needed), and is exactly the property that the codebase's own `test_ed25519_malleability` test demonstrates and that motivated using `verify_strict` for the precompile path. Any unprivileged network sender who can submit a single signed transaction to a public TPU/QUIC endpoint can trivially generate many malleated variants and resend them, requiring no special role, no coordination with validators, and no more than the resources needed to send a normal transaction flood.

### Recommendation
Use `verify_strict` (or an equivalent canonical/strict ed25519 verification that rejects non-canonical `S`/cofactored `R` malleations) in the primary transaction sigverify path (`perf/src/sigverify.rs::verify_packet`) and in `entry/src/entry.rs::batch_verify`, matching the approach already taken for the ed25519 precompile. Alternatively/additionally, key the sigverify-stage `Deduper` off the signed message content (e.g., message hash) rather than the raw packet bytes including the signature, so that malleated signature variants of the same message are still recognized as duplicates before expensive verification.

### Proof of Concept
1. Craft or capture a normal, validly-signed transaction packet `P` (signature `sig`, message `m`, pubkey `pk`) such that `sig` verifies against `m`/`pk` under the plain (non-strict) `Signature::verify`, as used by `perf/src/sigverify.rs::verify_packet` (lines 43-55).
2. Using the ed25519 cofactor-multiplication technique demonstrated by the codebase's own `test_ed25519_malleability` (`precompiles/src/ed25519.rs`, lines 454-512), derive one or more alternate byte encodings `sig'` for the same `(m, pk)` pair that also satisfy the non-strict verification equation but differ from `sig` at the byte level.
3. Submit packets containing `(sig, m, pk)` and `(sig', m, pk)` to the TPU/QUIC ingestion path.
4. Because `Deduper::dedup` (`perf/src/deduper.rs`, lines 125-144) hashes the full raw packet bytes, the two packets hash to different bitmap entries and neither is discarded as a duplicate; both proceed to full ed25519 verification in `verify_packet`, both pass, and both are forwarded downstream — demonstrating that repeated re-submission of malleated variants bypasses the intended cheap-dedup/QoS gate ahead of expensive signature verification.

pub fn dedup_packets_and_count_discards<const K: usize>(
    deduper: &Deduper<K, [u8]>,
    batches: &mut [PacketBatch],
) -> u64 {
    batches
        .iter_mut()
        .flat_map(|batch| batch.iter_mut())
        .map(|mut packet| {
            if !packet.meta().discard()
                && packet
                    .data(..)
                    .map(|data| deduper.dedup(data))
                    .unwrap_or(true)
            {
                packet.meta_mut().set_discard(true);
            }
            u64::from(packet.meta().discard())
        })
        .sum()
}
